# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `PeriodicTimer` cho background loop định kỳ thay vì tự ghép `while` + `Task.Delay`

**Mẹo:**
Trong .NET, với background loop chạy theo chu kỳ như refresh cache, polling hoặc health snapshot, cân nhắc `PeriodicTimer` thay vì tự viết `while (!ct.IsCancellationRequested) { await Task.Delay(...); ... }`.

**Tại sao hữu ích:**
`PeriodicTimer` diễn đạt rõ intent “tick theo chu kỳ”, hỗ trợ cancellation trực tiếp và giảm boilerplate. Nó cũng giúp tránh một số lỗi thường gặp như quên truyền `CancellationToken` vào `Task.Delay` hoặc tạo nhiều timer chồng lấn ngoài ý muốn.

**Ví dụ:**
```csharp
public sealed class MetricsWorker(ILogger<MetricsWorker> logger)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await CollectSnapshotAsync(stoppingToken);
        }
    }
}
```

Nếu một iteration mất lâu hơn interval, `PeriodicTimer` không tạo thêm concurrent callback như một số timer API khác; iteration tiếp theo chỉ tiếp tục khi loop quay lại chờ tick.

**Lưu ý:**
`PeriodicTimer` không phải scheduler bền vững. Nếu job phải chạy đúng một thời điểm, survive process restart hoặc cần retry/history, hãy dùng scheduler/durable queue phù hợp. Đồng thời phải quyết định rõ có chấp nhận “missed tick” khi processing kéo dài hay không.

### Tip 2 — Đặt timeout theo operation bằng `HttpClient`/Polly thay vì chỉ dùng một timeout toàn cục

**Mẹo:**
Khi ASP.NET Core gọi nhiều downstream API có latency profile khác nhau, đừng chỉ dựa vào một `HttpClient.Timeout` dùng cho mọi request. Đặt timeout theo operation hoặc typed client dựa trên latency budget thật.

**Tại sao hữu ích:**
Một endpoint đọc profile có thể chỉ nên chờ 500 ms, trong khi export report hợp lệ có thể cần 20 giây. Dùng cùng timeout cho cả hai khiến một operation fail quá sớm hoặc operation khác giữ connection/resource quá lâu. Timeout đúng chỗ giúp giới hạn blast radius khi dependency chậm.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<PaymentClient>(client =>
{
    client.BaseAddress = new Uri(configuration["Payment:BaseUrl"]!);
})
.AddStandardResilienceHandler(options =>
{
    options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
    options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(5);
});
```

Thiết kế timeout nên dựa trên end-to-end request budget: API 3 giây không nên cho downstream riêng lẻ chờ 10 giây.

**Lưu ý:**
Timeout không đồng nghĩa downstream chắc chắn dừng xử lý. Operation có side effect cần idempotency. Ngoài ra đừng thêm retry sau timeout cho non-idempotent operation nếu chưa kiểm soát duplicate processing.

### Tip 3 — Với PostgreSQL queue table, dùng `FOR UPDATE SKIP LOCKED` để nhiều worker claim work mà không block nhau

**Mẹo:**
Nếu một hệ thống dùng PostgreSQL table như work queue đơn giản, nhiều worker có thể claim row bằng `FOR UPDATE SKIP LOCKED` để tránh chờ row mà worker khác đã lock.

**Tại sao hữu ích:**
Không có `SKIP LOCKED`, worker B có thể đứng chờ row đầu tiên mà worker A đang xử lý dù phía sau còn nhiều row chưa ai claim. Bỏ qua row đã lock giúp competing workers phân phối work tốt hơn.

**Ví dụ:**
```sql
BEGIN;

SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;

UPDATE jobs
SET status = 'processing',
    started_at = now()
WHERE id = ANY(@ids);

COMMIT;
```

Sau khi claim, xử lý business work nên có recovery strategy nếu process chết giữa chừng, ví dụ lease timeout hoặc trạng thái reclaimable.

**Lưu ý:**
Database queue phù hợp cho workload vừa phải và khi muốn operational simplicity. Nó không tự cung cấp các capability như delayed delivery, dead-lettering, fan-out hoặc retention semantics của message broker. Đừng biến một relational table thành broker phức tạp nếu workload đã vượt khả năng vận hành đơn giản.

### Tip 4 — Dùng `satisfies` trong TypeScript để kiểm tra shape mà không làm mất type inference

**Mẹo:**
Trong TypeScript, dùng `satisfies` khi muốn xác nhận object tuân theo một contract nhưng vẫn giữ type cụ thể của từng property thay vì ép toàn bộ object thành type rộng hơn.

**Tại sao hữu ích:**
Annotation kiểu trực tiếp có thể làm mất literal information hữu ích. `satisfies` cho compiler kiểm tra contract trong khi vẫn giữ inference chi tiết, rất tiện với route config, feature map, permission matrix hoặc API metadata.

**Ví dụ:**
```ts
type RouteMeta = {
  requiresAuth: boolean
  layout: 'default' | 'admin'
}

const routeMeta = {
  requiresAuth: true,
  layout: 'admin'
} satisfies RouteMeta

// routeMeta.layout vẫn được infer là 'admin'
```

Điều này giúp refactor an toàn hơn mà không cần dùng `as` để ép compiler im lặng.

**Lưu ý:**
`satisfies` chỉ là compile-time check; dữ liệu từ API/localStorage/user input vẫn cần runtime validation. Đừng dùng nó thay cho schema validation như Zod/Valibot khi boundary là dữ liệu không tin cậy.

### Tip 5 — Trên Azure App Service, dùng Managed Identity để truy cập Key Vault thay vì nhét secret vào app settings

**Mẹo:**
Với application chạy trên Azure App Service, ưu tiên Managed Identity để authenticate tới Key Vault, Storage, Service Bus hoặc SQL hỗ trợ Entra authentication thay vì lưu client secret/password trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ secret lifecycle khỏi application: không cần phát hành, phân phối và rotate credential thủ công. Quyền được quản lý ở Azure RBAC/Access Policy, giúp audit và least privilege rõ ràng hơn.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Trong local development, `DefaultAzureCredential` có thể dùng developer identity; trên App Service nó có thể dùng Managed Identity của resource.

**Lưu ý:**
Đừng cấp quyền rộng như Owner/Contributor chỉ để “cho chạy”. Application identity nên chỉ có data-plane permission cần thiết. Cũng cần hiểu credential chain của `DefaultAzureCredential`; local chạy được bằng developer login không chứng minh production identity đã được cấp đúng RBAC.

## 🧠 Software Design

### Design 1 — Saga orchestration vs choreography cho workflow nhiều service

**Khái niệm:**
Saga chia distributed transaction thành nhiều local transaction và dùng compensating action khi bước sau thất bại. Hai cách tổ chức phổ biến là orchestration — một coordinator điều khiển flow — và choreography — các service phản ứng với event của nhau.

**Vấn đề nó giải quyết:**
Một order workflow có thể gồm Reserve Inventory → Authorize Payment → Create Shipment. Không có một ACID transaction chung qua nhiều service, nên failure giữa chừng cần trạng thái và compensation rõ ràng thay vì cố dùng distributed lock/transaction ở mọi nơi.

**Ví dụ thực tế:**
```text
Orchestration:
OrderSaga
  -> ReserveInventory
  -> AuthorizePayment
  -> CreateShipment
  -> nếu shipment fail: RefundPayment + ReleaseInventory

Choreography:
OrderCreated
  -> InventoryReserved
  -> PaymentAuthorized
  -> ShipmentRequested
```

Orchestration làm flow dễ nhìn và debug hơn; choreography giảm central coordinator nhưng coupling qua event graph dễ tăng âm thầm.

**Trade-off:**
Orchestration tập trung flow control và observability nhưng coordinator có thể trở thành component phức tạp. Choreography tăng autonomy nhưng dễ tạo event chain khó theo dõi, cycle dependency và khó biết toàn workflow đang ở trạng thái nào.

**Middle → Senior insight:**
Middle developer cần hiểu compensation không phải database rollback và mỗi step phải idempotent. Senior / Technical developer phải chọn orchestration hay choreography dựa trên workflow complexity, ownership, observability, failure recovery và mức coupling chấp nhận được — không theo xu hướng “event-driven = tốt hơn”.

### Design 2 — Snapshot Isolation / Read Committed Snapshot để giảm reader-writer blocking nhưng vẫn phải hiểu consistency

**Khái niệm:**
Row-versioning isolation cho phép reader đọc một version nhất quán của dữ liệu thay vì phải chờ writer release lock trong nhiều tình huống. Trên SQL Server, `READ_COMMITTED_SNAPSHOT` thay đổi behavior của `READ COMMITTED` để đọc từ row versions.

**Vấn đề nó giải quyết:**
Hệ thống transactional có nhiều read request có thể bị latency spike vì reader và writer block nhau. Row versioning giảm một loại contention mà không cần dùng `NOLOCK` và chấp nhận dirty read.

**Ví dụ thực tế:**
```text
Writer:
UPDATE Orders SET Status = 'Paid' ...
(transaction vẫn chưa commit)

Reader với lock-based READ COMMITTED:
-> có thể chờ writer

Reader với RCSI:
-> đọc committed version trước đó
-> không thấy dữ liệu uncommitted
```

Điều này đặc biệt hữu ích cho read-heavy API có write concurrency cao.

**Trade-off:**
Row versioning giảm blocking nhưng tăng version-store usage trong `tempdb` và không loại bỏ mọi concurrency problem. Nó cũng không ngăn lost update; write-write conflict và business invariant vẫn cần concurrency control riêng.

**Middle → Senior insight:**
Middle developer cần phân biệt “không bị block” với “luôn thấy dữ liệu mới nhất”. Senior / Technical developer phải đánh giá isolation theo workload, transaction duration, `tempdb` pressure, consistency requirement và conflict behavior thay vì chữa blocking bằng `NOLOCK` mặc định.

### Design 3 — Ports & Adapters để cô lập business core khỏi framework/integration, nhưng chỉ khi boundary có giá trị thật

**Khái niệm:**
Ports & Adapters đặt business capability phía trong và giao tiếp với database, HTTP API, message broker hoặc UI qua contract ở boundary. Mục tiêu là giảm coupling với external mechanism, không phải tạo interface cho mọi class.

**Vấn đề nó giải quyết:**
Nếu domain logic gọi trực tiếp EF Core, Azure SDK, HTTP client và framework types ở mọi nơi, thay đổi integration hoặc test business behavior khó vì external concerns len vào core logic. Boundary rõ giúp phần cần ổn định không phụ thuộc chi tiết dễ thay đổi.

**Ví dụ thực tế:**
```text
Application core
  CheckoutService
      |
      +-- IPaymentGateway   (port)
      +-- IInventoryStore   (port)

Adapters
  StripePaymentGateway
  SqlInventoryStore
```

Không nhất thiết phải wrap `DateTime`, `List<T>` hay mọi repository chỉ để đạt “100% dependency inversion”.

**Trade-off:**
Ports & Adapters cải thiện testability và khả năng thay integration, nhưng thêm abstraction, mapping và navigation cost. Với CRUD nhỏ, ít external dependency và framework stable, layered architecture đơn giản có thể dễ bảo trì hơn.

**Middle → Senior insight:**
Middle developer cần giữ business rule khỏi bị trộn với transport/storage concern khi boundary thực sự tồn tại. Senior / Technical developer phải biết chỗ nào đáng abstraction dựa trên volatility, testability, ownership và migration risk — đồng thời tránh interface explosion chỉ để kiến trúc trông “sạch”.
