# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArraySegment<T>` khi cần truyền một vùng con của array mà không copy

**Mẹo:**
Khi API cũ hoặc code hiện tại làm việc với array nhưng chỉ cần một đoạn dữ liệu, dùng `ArraySegment<T>` để biểu diễn `offset + count` thay vì tạo array mới bằng `Skip(...).Take(...).ToArray()`.

**Tại sao hữu ích:**
Tránh allocation và copy không cần thiết trong parsing, buffering hoặc protocol handling, đặc biệt khi xử lý nhiều block dữ liệu nhỏ trên cùng một buffer lớn.

**Ví dụ:**
```csharp
byte[] buffer = ReceiveBuffer();

var header = new ArraySegment<byte>(
    buffer,
    offset: 0,
    count: 32);

ProcessHeader(header);
```

**Lưu ý:**
`ArraySegment<T>` vẫn tham chiếu array gốc. Nếu giữ segment lâu, toàn bộ array lớn cũng tiếp tục sống trong memory. Với API mới, `Span<T>` / `ReadOnlyMemory<T>` thường linh hoạt hơn.

### Tip 2 — Dùng EF Core explicit loading khi navigation chỉ cần trong một nhánh hiếm

**Mẹo:**
Nếu navigation chỉ được dùng trong một branch hiếm của workflow, explicit loading có thể rõ và rẻ hơn eager loading bằng `Include()` cho mọi request.

**Tại sao hữu ích:**
Tránh kéo thêm dữ liệu không cần thiết trong path phổ biến, đồng thời vẫn giữ load behavior explicit thay vì bật lazy loading khó kiểm soát.

**Ví dụ:**
```csharp
var order = await dbContext.Orders
    .SingleAsync(x => x.Id == orderId, cancellationToken);

if (needsAuditDetails)
{
    await dbContext.Entry(order)
        .Collection(x => x.AuditEntries)
        .LoadAsync(cancellationToken);
}
```

**Lưu ý:**
Explicit loading vẫn tạo thêm round-trip. Nếu branch xảy ra thường xuyên hoặc xử lý nhiều entity trong loop, rất dễ thành N+1; khi đó projection hoặc eager loading có thể tốt hơn.

### Tip 3 — Dùng `SET STATISTICS XML ON` khi cần execution plan machine-readable trên SQL Server

**Mẹo:**
Khi điều tra query plan bằng script hoặc cần lưu plan để phân tích sau, dùng `SET STATISTICS XML ON` để SQL Server trả execution plan dạng XML cùng statement.

**Tại sao hữu ích:**
Plan XML chứa operator, estimate, actual runtime metadata và warning ở dạng có thể archive, diff hoặc đọc bằng tooling thay vì chỉ xem graphical plan trong SSMS.

**Ví dụ:**
```sql
SET STATISTICS XML ON;

SELECT Id, Status
FROM Orders
WHERE CustomerId = @CustomerId;

SET STATISTICS XML OFF;
```

**Lưu ý:**
Đừng bật tùy chọn này trong application production path vì output plan lớn và tăng overhead. Dùng có mục đích trong phiên diagnostics hoặc môi trường test.

### Tip 4 — Dùng `git update-index --assume-unchanged` rất thận trọng với file config local

**Mẹo:**
Trong tình huống hiếm khi cần giữ một file tracked khác local nhưng không muốn Git liên tục báo modified, `git update-index --assume-unchanged` có thể giảm noise tạm thời.

**Tại sao hữu ích:**
Có thể hữu dụng với local-only adjustment trên repository cũ chưa tách config development đúng cách.

**Ví dụ:**
```bash
git update-index --assume-unchanged appsettings.Development.json
```

Khôi phục:

```bash
git update-index --no-assume-unchanged appsettings.Development.json
```

**Lưu ý:**
Đây không phải giải pháp configuration tốt. Bạn có thể bỏ lỡ thay đổi upstream quan trọng. Ưu tiên `.gitignore`, user secrets, environment variables hoặc file template riêng khi có thể.

### Tip 5 — Dùng `curl --connect-timeout` tách lỗi kết nối khỏi timeout toàn request

**Mẹo:**
Khi test dependency qua CLI, đặt `--connect-timeout` riêng với `--max-time` để biết vấn đề nằm ở connect phase hay response processing phase.

**Tại sao hữu ích:**
Giúp phân biệt DNS/TCP/TLS connection chậm với server đã nhận request nhưng xử lý quá lâu.

**Ví dụ:**
```bash
curl \
  --connect-timeout 3 \
  --max-time 15 \
  -v \
  https://api.example.com/health
```

**Lưu ý:**
`curl` diagnostics chỉ phản ánh một client và một network path. Application runtime có thể dùng proxy, DNS cache, connection pool hoặc certificate store khác.

## 🧠 Software Design

### Design 1 — Configuration nên là dependency có lifecycle rõ ràng, không phải global bag

**Khái niệm:**
Configuration tốt không chỉ là key-value đọc được ở mọi nơi. Mỗi nhóm setting nên có ownership, validation, reload semantics và phạm vi sử dụng rõ ràng.

**Vấn đề nó giải quyết:**
Khi code gọi trực tiếp `IConfiguration["..."]` khắp solution, typo chỉ lộ ở runtime, business logic phụ thuộc string key và rất khó biết setting nào có thể reload an toàn.

**Ví dụ thực tế:**
Thay vì đọc:

```csharp
configuration["Exchange:RetryCount"]
```

nhiều nơi, bind vào:

```csharp
public sealed class ExchangeOptions
{
    public int RetryCount { get; init; }
}
```

và validate khi startup. Nếu `RetryCount` thay đổi runtime, team phải quyết định rõ service nào dùng `IOptionsMonitor<T>` và behavior đang chạy có nhận config mới hay không.

**Trade-off:**
Typed configuration tăng safety và discoverability nhưng thêm class/validation. Reload động tăng flexibility nhưng tạo state transition khó đoán nếu một operation dùng nửa config cũ, nửa config mới.

**Middle → Senior insight:**
Middle developer nên tránh rải string key configuration. Senior developer phải thiết kế ownership, validation, secret boundary, reload strategy và xác định setting nào cần restart để giữ behavior deterministic.

### Design 2 — Quorum chỉ có ý nghĩa khi bạn hiểu failure model

**Khái niệm:**
Quorum yêu cầu một số lượng node tối thiểu đồng ý trước khi read/write được chấp nhận, thường dùng để tránh hai phía cùng nghĩ mình là nguồn sự thật sau network partition.

**Vấn đề nó giải quyết:**
Distributed system có thể bị chia network nhưng từng node vẫn sống. Nếu cả hai phía đều tiếp tục ghi độc lập mà không có rule majority/leadership, state dễ diverge hoặc tạo split-brain.

**Ví dụ thực tế:**
Cluster 3 node yêu cầu 2 node để elect leader và accept metadata write. Khi 1 node bị cô lập, phía 2 node tiếp tục hoạt động; node đơn lẻ không được tự trở thành leader.

**Trade-off:**
Quorum tăng consistency và giảm split-brain, nhưng availability giảm nếu không còn đủ node reachable. Số node lẻ giúp majority rõ hơn nhưng không thay thế thiết kế placement giữa failure domain.

**Middle → Senior insight:**
Middle developer nên hiểu “3 replicas” không đồng nghĩa luôn available. Senior developer phải phân tích node failure, network partition, region loss, latency giữa replicas và chọn quorum/placement phù hợp với RPO/RTO thay vì chỉ tăng replica count.

### Design 3 — API Composition hợp lý khi ownership giữ nguyên ở downstream

**Khái niệm:**
API Composition tạo một response bằng cách gọi nhiều service/module sở hữu dữ liệu khác nhau rồi tổng hợp kết quả, thay vì replicate tất cả dữ liệu vào một read model riêng ngay từ đầu.

**Vấn đề nó giải quyết:**
Một UI thường cần dữ liệu từ nhiều bounded context. Nếu client tự gọi 5 service, latency, auth và error handling bị đẩy sang frontend; nhưng tạo read model riêng cho mọi màn hình cũng có thể quá nặng.

**Ví dụ thực tế:**
Trang employee detail cần profile từ `Employee`, leave balance từ `Leave` và project assignment từ `Project`. Một composition endpoint gọi ba nguồn song song rồi trả response duy nhất cho frontend.

**Trade-off:**
Composition giữ source-of-truth tại service gốc và triển khai nhanh, nhưng latency phụ thuộc fan-out và failure của nhiều downstream. Read model riêng nhanh và ổn định hơn cho hot path nhưng thêm replication/eventual consistency.

**Middle → Senior insight:**
Middle developer nên biết composition và replicated read model đều là lựa chọn hợp lệ. Senior developer phải dựa trên latency budget, fan-out size, freshness requirement, failure tolerance và traffic volume để quyết định khi nào composition đã đạt giới hạn và cần materialized view/read model.
