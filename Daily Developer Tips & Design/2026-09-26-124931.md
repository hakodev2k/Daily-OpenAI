# Daily Developer Tips & Design — 2026-09-26

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer nóng, nhưng phải trả buffer đúng cách

**Mẹo:**
Trong hot path phải thuê buffer tạm thời nhiều lần, cân nhắc `ArrayPool<T>.Shared.Rent()` thay vì liên tục tạo array lớn. Luôn trả buffer trong `finally` và chỉ xử lý phần dữ liệu thực sự đã ghi, không dựa vào `Length` của array được thuê.

**Tại sao hữu ích:**
`Rent(n)` có thể trả một array lớn hơn `n`. Tái sử dụng buffer giúp giảm allocation và GC pressure ở workload serialization, parsing hoặc streaming có tần suất cao, nhưng lợi ích chỉ đáng kể khi profiler chứng minh allocation là bottleneck.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Buffer thuê có thể chứa dữ liệu từ lần sử dụng trước. Không đọc vùng chưa ghi; với dữ liệu nhạy cảm, cân nhắc `clearArray: true`. Đừng pool các object nhỏ chỉ vì có thể—pooling làm lifecycle phức tạp hơn.

### Tip 2 — Với EF Core, projection trước khi `Include` cả object graph

**Mẹo:**
Endpoint chỉ cần DTO thì ưu tiên `Select` đúng các cột cần thiết thay vì `Include` nhiều navigation rồi map entity sau khi materialize.

**Tại sao hữu ích:**
Projection cho EF Core cơ hội sinh SQL hẹp hơn, giảm dữ liệu truyền từ database, materialization và change-tracking overhead. Nó đặc biệt quan trọng khi collection navigation tạo row multiplication.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.CreatedAt,
        x.Items.Count,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(ct);
```
Khi endpoint chỉ hiển thị summary, không cần load toàn bộ `Order.Items.Product` vào memory.

**Lưu ý:**
Projection phức tạp vẫn có thể tạo SQL đắt. Kiểm tra generated SQL và execution plan; đừng mặc định `Select` luôn nhanh. Nếu cần domain behavior trên aggregate đã load, projection DTO có thể không phù hợp.

### Tip 3 — Theo dõi Service Bus lock khi handler lâu hơn thời gian xử lý dự kiến

**Mẹo:**
Nếu Azure Service Bus message bị xử lý trùng hoặc thường xuyên redeliver, kiểm tra `PeekLock`, lock duration, auto lock renewal và thời gian thực tế của handler trước khi tăng retry.

**Tại sao hữu ích:**
Với `PeekLock`, consumer chưa sở hữu message vĩnh viễn. Nếu lock hết hạn trước khi complete, broker có thể giao lại message dù lần xử lý đầu vẫn đang chạy. Triệu chứng “duplicate” vì thế có thể đến từ processing time hoặc lock renewal chứ không phải producer gửi hai lần.

**Ví dụ:**
Một image-processing handler mất p95 70 giây nhưng lock chỉ đủ cho workload bình thường. Trace cho thấy DB update hoàn tất ở giây 65, sau đó message bị redeliver. Sửa bằng cách giảm critical processing path hoặc cấu hình renewal phù hợp, đồng thời giữ consumer idempotent.

**Lưu ý:**
Kéo dài lock không thay thế idempotency. Handler bị treo có thể giữ work lâu hơn; cần timeout, cancellation, DLQ policy và telemetry cho delivery count.

### Tip 4 — Dùng `EXPLAIN (ANALYZE, BUFFERS)` để tách CPU/query-plan khỏi I/O trong PostgreSQL

**Mẹo:**
Khi PostgreSQL query chậm, đừng chỉ nhìn estimated plan. Trong môi trường an toàn, dùng `EXPLAIN (ANALYZE, BUFFERS)` để so estimated/actual rows và xem lượng buffer hit/read của từng operator.

**Tại sao hữu ích:**
Hai plan có execution time giống nhau có thể có nguyên nhân khác: cardinality estimate sai, đọc quá nhiều pages, sort spill hoặc join strategy không phù hợp. Buffer evidence giúp tránh “thêm index theo cảm giác”.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total
FROM orders
WHERE tenant_id = 42 AND status = 'Pending'
ORDER BY created_at DESC
LIMIT 100;
```
Nếu scan loại bỏ hàng triệu rows và đọc nhiều buffers, đối chiếu query pattern với composite index; nếu estimate lệch lớn, kiểm tra statistics/data skew.

**Lưu ý:**
`ANALYZE` thực sự chạy câu lệnh. Với `UPDATE`/`DELETE` hoặc query rất nặng trên production, không chạy tùy tiện; dùng transaction rollback hoặc môi trường đại diện khi phù hợp.

### Tip 5 — Đo Core Web Vitals bằng dữ liệu người dùng thật, không chỉ Lighthouse

**Mẹo:**
Dùng Lighthouse để tái hiện và chẩn đoán local/lab, nhưng với website/CMS production hãy bổ sung Real User Monitoring cho LCP, INP và CLS theo route, device và release.

**Tại sao hữu ích:**
Lab test chạy trong điều kiện mô phỏng; người dùng thật có network, CPU, cache state và content khác nhau. Một CMS page có thể đạt điểm tốt trong test nhưng LCP xấu trên mobile vì hero image động, backend TTFB cao hoặc third-party JavaScript.

**Ví dụ:**
Sau release, p75 LCP của product page tăng từ 2.1 s lên 3.4 s. Waterfall cho thấy TTFB không đổi nhưng hero image mới lớn hơn và được phát hiện muộn; bằng chứng này hướng fix vào image delivery/preload thay vì tối ưu API không liên quan.

**Lưu ý:**
Đừng tối ưu chỉ để tăng một Lighthouse score. Theo dõi percentile và business-critical routes; performance fix phải giữ accessibility, correctness và cache semantics.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho idempotent message consumption

**Khái niệm:**
Inbox Pattern ghi nhận message identifier đã xử lý trong cùng consistency boundary với business update, để consumer có thể nhận duplicate nhưng không lặp lại side effect nghiệp vụ.

**Vấn đề nó giải quyết:**
At-least-once delivery nghĩa là message có thể được giao lại khi consumer xử lý thành công nhưng acknowledgement thất bại. Chỉ “retry cẩn thận” không loại bỏ cửa sổ failure này.

**Ví dụ thực tế:**
Consumer nhận `PaymentCaptured`. Trong một database transaction, nó kiểm tra/insert `InboxMessages(MessageId)` và cập nhật `Order=Paid`. Delivery lặp với cùng `MessageId` được nhận biết và bỏ qua thay vì cộng payment/order state lần nữa.

**Trade-off:**
Inbox tăng reliability và auditability nhưng thêm write, unique constraint, retention/cleanup và yêu cầu định nghĩa idempotency key đúng. Với handler vốn idempotent tự nhiên hoặc side effect không đáng kể, full Inbox có thể là complexity thừa.

**Middle → Senior insight:**
Middle cần hiểu duplicate delivery là trạng thái bình thường và bảo đảm check + business mutation không có race. Senior / Technical developer phải chọn idempotency boundary, retention, key semantics và xử lý external side effects; Inbox trong database không tự làm một email hoặc third-party payment call trở nên atomic.

### Design 2 — SQL hay MongoDB phải bắt đầu từ access pattern và consistency

**Khái niệm:**
Chọn relational database hay document database dựa trên invariants, query/access patterns, transaction boundary, schema evolution và scale profile—không dựa trên nhãn “structured” hay “unstructured”.

**Vấn đề nó giải quyết:**
Một domain có aggregate tự chứa và đọc theo document có thể phù hợp MongoDB; một workflow cần joins linh hoạt, constraints và transaction xuyên nhiều thực thể thường tự nhiên hơn với SQL. Chọn sai model khiến application phải tự bù các guarantee mà database không cung cấp thuận tiện.

**Ví dụ thực tế:**
Product-content snapshot cho CMS có cấu trúc biến đổi theo loại content và thường đọc nguyên document có thể phù hợp document model. Order/payment/invoice cần uniqueness, referential integrity và transactional invariants có thể phù hợp SQL hơn. Không cần ép cả hệ thống dùng một database duy nhất.

**Trade-off:**
MongoDB cho document locality và schema flexibility nhưng denormalization tạo duplication và consistency work. SQL cung cấp constraints, transactions và query flexibility mạnh nhưng schema/join design vẫn cần tối ưu theo workload; scale không tự động “kém” chỉ vì là relational.

**Middle → Senior insight:**
Middle cần model dữ liệu theo query pattern và hiểu index/transaction semantics của database đang dùng. Senior / Technical developer phải định lượng consistency requirement, operational skill, migration cost, backup/recovery và tránh polyglot persistence nếu lợi ích không vượt chi phí vận hành.

### Design 3 — Strangler Fig cho modernization thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig thay thế legacy system theo từng capability: route một phần traffic/use case sang implementation mới, giữ phần còn lại trên hệ thống cũ và thu hẹp legacy boundary dần.

**Vấn đề nó giải quyết:**
Rewrite toàn bộ .NET Framework/CMS cũ thường kéo dài, trong khi production vẫn thay đổi. Đến ngày cutover, “bản mới” có thể đã lệch requirement và mang rủi ro migration lớn.

**Ví dụ thực tế:**
Một ASP.NET MVC/.NET Framework portal giữ nguyên checkout cũ nhưng tách read-only product API sang ASP.NET Core trước. Reverse proxy hoặc frontend routing chuyển capability mới dần; telemetry so sánh error/latency và rollback boundary rõ trước khi chuyển tiếp chức năng khác.

**Trade-off:**
Incremental migration giảm blast radius và cho feedback sớm, nhưng tạm thời phải vận hành hai stack, đồng bộ identity/data contracts và chịu transitional architecture. Big-bang có thể hợp lý hơn với hệ thống nhỏ, ít tích hợp và có cửa sổ thay thế rõ.

**Middle → Senior insight:**
Middle cần giữ contract tương thích, test integration và tránh coupling mới quay lại legacy. Senior / Technical developer phải chọn seam để tách, quản lý data ownership, migration sequencing, observability và tiêu chí retirement; mục tiêu là giảm rủi ro tổng thể chứ không kéo trạng thái “hybrid” vô hạn.
