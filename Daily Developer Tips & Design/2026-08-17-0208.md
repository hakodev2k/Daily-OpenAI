# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Task.WhenAll` khi các I/O operation thật sự độc lập

**Mẹo:**
Nếu nhiều async operation không phụ thuộc kết quả lẫn nhau, khởi tạo chúng trước rồi `await Task.WhenAll(...)` thay vì `await` tuần tự.

**Tại sao hữu ích:**
Giảm tổng latency của request khi phải gọi nhiều service hoặc database operation độc lập. Ví dụ ba outbound call mất lần lượt 200 ms, 300 ms và 400 ms có thể hoàn thành gần mức 400 ms thay vì khoảng 900 ms.

**Ví dụ:**
```csharp
var profileTask = profileClient.GetAsync(userId, cancellationToken);
var ordersTask = orderClient.GetRecentAsync(userId, cancellationToken);
var permissionsTask = permissionClient.GetAsync(userId, cancellationToken);

await Task.WhenAll(profileTask, ordersTask, permissionsTask);

var response = new DashboardDto(
    await profileTask,
    await ordersTask,
    await permissionsTask);
```

**Lưu ý:**
Không parallelize máy móc. Nếu các operation dùng chung một `DbContext`, hoặc downstream có rate limit / connection limit thấp, chạy đồng thời có thể gây lỗi hoặc làm hệ thống chậm hơn.

### Tip 2 — Dùng `TagWith()` để tìm EF Core query trong production logs

**Mẹo:**
Gắn tag vào các query quan trọng bằng `TagWith()` để SQL sinh ra có comment nhận diện rõ nguồn gốc từ application code.

**Tại sao hữu ích:**
Khi DBA hoặc APM phát hiện một query chậm, bạn có thể nhanh chóng map SQL đó về đúng use case hoặc code path thay vì tìm bằng cách đoán từ câu SQL.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .TagWith("OrderSearch:GetOpenOrders")
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Open)
    .OrderByDescending(x => x.CreatedAt)
    .Take(100)
    .ToListAsync(cancellationToken);
```

SQL có thể chứa comment tương tự:

```sql
-- OrderSearch:GetOpenOrders
SELECT ...
FROM Orders ...
```

**Lưu ý:**
Tag nên ổn định và có ý nghĩa nghiệp vụ. Đừng nhét dữ liệu động, user input hoặc thông tin nhạy cảm vào tag vì nó có thể xuất hiện trong database logs.

### Tip 3 — Dùng `curl -v` và `curl --resolve` để debug HTTP/DNS/TLS nhanh

**Mẹo:**
Khi API chạy trên server nhưng client không kết nối được, dùng `curl -v` để xem DNS, TCP, TLS và HTTP headers. Nếu nghi DNS sai, dùng `--resolve` để ép hostname trỏ về một IP cụ thể mà vẫn giữ đúng `Host` và TLS SNI.

**Tại sao hữu ích:**
Giúp phân biệt nhanh lỗi application với lỗi DNS, reverse proxy, certificate, firewall hoặc routing.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Test trực tiếp một server cụ thể:

```bash
curl -v \
  --resolve api.example.com:443:10.0.2.15 \
  https://api.example.com/health
```

**Lưu ý:**
`--resolve` chỉ override mapping phía client hiện tại. Nó không sửa DNS thật và không chứng minh các client khác sẽ route giống bạn.

### Tip 4 — Tách `Timeout` và `Retry`; đừng retry mọi lỗi

**Mẹo:**
Thiết kế retry chỉ cho lỗi transient như timeout ngắn, HTTP `408`, `429`, hoặc một số `5xx`, và dùng backoff thay vì retry ngay lập tức.

**Tại sao hữu ích:**
Retry đúng cách tăng resilience. Retry sai có thể nhân tải lên downstream đang gặp sự cố và biến lỗi nhỏ thành cascading failure.

**Ví dụ:**
Pseudo policy:

```text
Retry:
- 408 Request Timeout
- 429 Too Many Requests
- 502 Bad Gateway
- 503 Service Unavailable
- 504 Gateway Timeout

Do not retry blindly:
- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
```

Nếu server trả `Retry-After`, ưu tiên tôn trọng giá trị đó.

**Lưu ý:**
Chỉ retry operation có tính idempotent hoặc đã có cơ chế chống duplicate. Retry `POST /payments` không có idempotency key có thể tạo giao dịch trùng.

### Tip 5 — Dùng `git diff --word-diff` khi review thay đổi text-heavy

**Mẹo:**
Với JSON, YAML, Markdown, SQL migration hoặc config có nhiều dòng bị format lại, `git diff --word-diff` có thể giúp nhìn chính xác phần token/text nào thực sự thay đổi.

**Tại sao hữu ích:**
Giảm noise trong code review khi formatter hoặc reflow làm cả dòng bị đánh dấu thay đổi dù semantic change rất nhỏ.

**Ví dụ:**
```bash
git diff --word-diff
```

Hoặc chỉ một file:

```bash
git diff --word-diff HEAD~1 -- appsettings.Production.json
```

**Lưu ý:**
Không phải lựa chọn tốt cho mọi source code. Với C# có refactor lớn, structural diff hoặc IDE diff thường dễ đọc hơn.

## 🧠 Software Design

### Design 1 — Outbox Pattern để tránh “DB đã commit nhưng message chưa gửi”

**Khái niệm:**
Outbox Pattern ghi business data và một outbox message vào cùng một local database transaction. Một background worker sau đó đọc outbox và publish message sang broker như RabbitMQ, Kafka hoặc Azure Service Bus.

**Vấn đề nó giải quyết:**
Nếu application thực hiện:

1. `SaveChanges()` vào database
2. publish event ra message broker

thì có khoảng lỗi giữa hai bước. Database có thể commit thành công nhưng publish thất bại, khiến state nội bộ và downstream không đồng bộ.

**Ví dụ thực tế:**
Khi tạo `Order`, transaction ghi cả:

```text
Orders
OutboxMessages
```

Sau commit, worker đọc `OutboxMessages` chưa xử lý và publish `OrderCreated`. Sau khi broker xác nhận, worker đánh dấu message đã publish.

**Trade-off:**
Lợi ích là tránh phụ thuộc vào distributed transaction và tăng reliability. Chi phí là eventual consistency, cần background processor, retry, cleanup, monitoring và consumer vẫn phải xử lý duplicate vì delivery thường là at-least-once.

**Middle → Senior insight:**
Middle developer cần hiểu vấn đề dual-write và cách outbox loại bỏ khoảng lỗi giữa DB commit và publish. Senior developer phải quyết định polling hay CDC, retention, retry policy, ordering, throughput, duplicate handling và cách quan sát backlog khi publisher gặp sự cố.

### Design 2 — Optimistic Concurrency cho dữ liệu thường đọc nhiều, ghi ít

**Khái niệm:**
Optimistic Concurrency giả định conflict hiếm xảy ra. Thay vì khóa record từ lúc đọc, hệ thống lưu version/token và kiểm tra token đó khi update.

**Vấn đề nó giải quyết:**
Hai user có thể đọc cùng một record rồi cùng update. Nếu không có concurrency control, update sau có thể silently overwrite update trước — classic lost update.

**Ví dụ thực tế:**
Entity có `RowVersion`:

```csharp
public class Employee
{
    public int Id { get; set; }
    public string Title { get; set; } = null!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
```

Nếu row đã bị thay đổi kể từ lần client đọc, EF Core có thể phát sinh `DbUpdateConcurrencyException` thay vì overwrite im lặng.

**Trade-off:**
Lợi ích là không giữ lock lâu, phù hợp hệ thống read-heavy và web request ngắn. Chi phí là application phải xử lý conflict: reload, merge, reject hoặc yêu cầu user thử lại. Với hot row bị update liên tục, retry có thể trở nên tốn kém.

**Middle → Senior insight:**
Middle developer nên nhận diện lost update và biết dùng version token. Senior developer cần chọn conflict strategy theo business semantics: trường hợp nào auto-retry được, trường hợp nào phải merge, và trường hợp nào pessimistic locking hoặc serialization phù hợp hơn.

### Design 3 — Abstraction chỉ nên xuất hiện khi có “reason to vary” rõ ràng

**Khái niệm:**
Abstraction tốt che giấu một điểm biến đổi thực sự: provider, protocol, storage engine, business policy hoặc external dependency. Abstraction không nên tồn tại chỉ vì “có thể sau này sẽ cần”.

**Vấn đề nó giải quyết:**
Codebase thường bị over-engineering với nhiều `IManager`, `IService`, `IRepository`, wrapper và generic layer nhưng không có alternate implementation thực tế. Kết quả là logic khó trace, test phức tạp và mỗi thay đổi phải đi qua nhiều lớp forwarding.

**Ví dụ thực tế:**
Một abstraction hợp lý:

```csharp
public interface IObjectStorage
{
    Task<string> UploadAsync(Stream stream, CancellationToken cancellationToken);
}
```

nếu production dùng Azure Blob Storage nhưng local/test có thể dùng filesystem hoặc in-memory implementation.

Ngược lại, tạo `IEmployeeNameFormatterFactoryProvider` chỉ để gọi một class duy nhất thường là dấu hiệu abstraction không mang giá trị.

**Trade-off:**
Abstraction giúp giảm coupling, test dễ hơn và thay implementation thuận lợi khi variation là thật. Nhưng mỗi layer thêm mental overhead, indirection, API surface và chi phí bảo trì.

**Middle → Senior insight:**
Middle developer thường tập trung vào “có interface hay không”. Senior developer cần trả lời sâu hơn: boundary nào đáng ổn định, cái gì thực sự có khả năng thay đổi, abstraction có giảm coupling hay chỉ di chuyển coupling sang một layer khác, và liệu code concrete đơn giản có phù hợp hơn trong hiện tại hay không.
