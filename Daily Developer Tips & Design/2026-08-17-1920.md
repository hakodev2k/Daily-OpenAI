# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Stopwatch.GetElapsedTime()` thay vì tự chia `Stopwatch.GetTimestamp()`

**Mẹo:**
Khi cần đo thời gian rất ngắn trong hot path hoặc instrumentation nhẹ, dùng `Stopwatch.GetTimestamp()` kết hợp `Stopwatch.GetElapsedTime()` thay vì tự chuyển tick sang milliseconds.

**Tại sao hữu ích:**
Code ít lỗi hơn, tránh nhầm giữa `DateTime.Ticks` và timestamp frequency của `Stopwatch`, đồng thời vẫn dùng monotonic clock phù hợp cho elapsed time.

**Ví dụ:**
```csharp
var started = Stopwatch.GetTimestamp();

await repository.LoadAsync(cancellationToken);

var elapsed = Stopwatch.GetElapsedTime(started);
logger.LogInformation("Repository call took {ElapsedMs} ms", elapsed.TotalMilliseconds);
```

**Lưu ý:**
Đây phù hợp để đo duration, không dùng làm timestamp nghiệp vụ hoặc thời điểm tuyệt đối. Với observability production, đừng tự instrument mọi method nếu tracing/metrics đã cung cấp signal tốt hơn.

### Tip 2 — Dùng `AddDbContextPool()` khi `DbContext` creation có tần suất cao và configuration ổn định

**Mẹo:**
Với ASP.NET Core service tạo rất nhiều `DbContext` ngắn hạn, có thể cân nhắc `AddDbContextPool()` để tái sử dụng instance sau khi EF Core reset state.

**Tại sao hữu ích:**
Giảm một phần allocation và setup cost của `DbContext`, đặc biệt ở workload throughput cao với context sống rất ngắn.

**Ví dụ:**
```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
{
    options.UseNpgsql(connectionString);
});
```

Application code vẫn inject `AppDbContext` như bình thường.

**Lưu ý:**
Pooled context không phù hợp nếu bạn lưu mutable per-request state trực tiếp trên `DbContext`. Tenant-specific state, custom fields hoặc interceptor state phải được reset/thiết kế cẩn thận vì instance có thể được tái sử dụng.

### Tip 3 — Dùng `dotnet test --blame-hang` để bắt test treo trong CI

**Mẹo:**
Khi test suite thỉnh thoảng treo mà không rõ test nào giữ thread/task, dùng hang blame để thu thông tin khi một test vượt quá timeout.

**Tại sao hữu ích:**
Thay vì cả pipeline đứng vô thời hạn, test runner có thể xác định test đang chạy và tạo diagnostic artifacts để điều tra deadlock, wait vô hạn hoặc external dependency không trả về.

**Ví dụ:**
```bash
dotnet test \
  --blame-hang \
  --blame-hang-timeout 2m
```

**Lưu ý:**
Timeout phải đủ lớn cho test hợp lệ trên CI chậm. `--blame-hang` giúp thu bằng chứng, nhưng root cause vẫn cần phân tích synchronization, async flow hoặc dependency thực tế.

### Tip 4 — Dùng `git rev-list --left-right --count` để biết branch lệch nhau bao nhiêu commit

**Mẹo:**
Khi muốn biết nhanh branch đang ahead/behind bao nhiêu commit so với `main`, dùng `git rev-list` thay vì đọc một lịch sử dài bằng `git log`.

**Tại sao hữu ích:**
Rất tiện trước rebase, merge hoặc release để biết mức độ divergence và ước lượng scope cần đồng bộ.

**Ví dụ:**
```bash
git rev-list --left-right --count main...feature/payment
```

Ví dụ output:

```text
12  5
```

Nghĩa là `main` có 12 commit riêng và `feature/payment` có 5 commit riêng kể từ common ancestor.

**Lưu ý:**
Con số commit không phản ánh độ lớn hoặc độ khó của diff. Một commit lớn có thể rủi ro hơn hàng chục commit nhỏ.

### Tip 5 — Chỉ trust `X-Forwarded-*` từ reverse proxy đã biết

**Mẹo:**
Nếu ASP.NET Core chạy sau Nginx, ingress hoặc load balancer, cấu hình `ForwardedHeaders` cùng danh sách proxy/network tin cậy thay vì chấp nhận header forwarding từ bất kỳ client nào.

**Tại sao hữu ích:**
`X-Forwarded-For` và `X-Forwarded-Proto` ảnh hưởng client IP, HTTPS detection, redirect và đôi khi cả security decision. Nếu trust mù quáng, client có thể spoof header.

**Ví dụ:**
```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.0.10"));
});

app.UseForwardedHeaders();
```

**Lưu ý:**
Đừng clear toàn bộ `KnownNetworks`/`KnownProxies` chỉ để “cho chạy”. Topology proxy phải được hiểu rõ, đặc biệt khi có nhiều hop hoặc cloud ingress thay đổi địa chỉ.

## 🧠 Software Design

### Design 1 — DRY có thể gây coupling nếu hai domain chỉ tình cờ giống nhau

**Khái niệm:**
DRY yêu cầu tránh duplicate knowledge, không phải xóa mọi đoạn code trông giống nhau. Hai bounded context có thể có code giống nhưng semantics và tốc độ thay đổi khác nhau.

**Vấn đề nó giải quyết:**
Việc gom mọi logic giống nhau vào shared library có thể buộc các domain không liên quan phải release, version và thay đổi cùng nhau.

**Ví dụ thực tế:**
`Payroll.EmployeeStatus` và `AccessControl.UserStatus` ban đầu đều có `Active/Inactive`. Nếu ép dùng chung enum/package, sau này Payroll thêm `OnLeave` còn Access Control cần `Locked`, shared abstraction bắt đầu méo semantics của cả hai bên.

**Trade-off:**
Duplicate một ít code làm tăng maintenance cục bộ, nhưng giữ domain autonomy. Shared abstraction giảm repetition nhưng tạo coupling và coordination cost nếu concept không thật sự cùng nghĩa.

**Middle → Senior insight:**
Middle developer nên hỏi “đây có phải duplicate knowledge hay chỉ duplicate syntax?”. Senior developer cần đánh giá semantic ownership, change cadence và release coupling trước khi tạo shared component.

### Design 2 — Cell-Based Architecture để giới hạn blast radius theo nhóm user/tenant

**Khái niệm:**
Cell-Based Architecture chia hệ thống thành nhiều cell tương đối độc lập, mỗi cell phục vụ một subset user/tenant và có phần lớn compute/state dependency riêng.

**Vấn đề nó giải quyết:**
Một cluster hoặc database failure trong kiến trúc tập trung có thể ảnh hưởng toàn bộ khách hàng. Cell giúp sự cố chỉ tác động một phần population.

**Ví dụ thực tế:**
Một SaaS có 100.000 tenant được phân vào 20 cell. Mỗi cell có API instances, queue và database partition riêng. Nếu Cell 7 gặp database incident, tenant ở các cell khác vẫn hoạt động bình thường.

**Trade-off:**
Giảm blast radius, hỗ trợ scale ngang và deployment theo cell, nhưng routing, provisioning, data movement, global reporting và capacity balancing phức tạp hơn đáng kể.

**Middle → Senior insight:**
Middle developer nên hiểu high availability không chỉ là thêm replica. Senior developer phải cân nhắc cell size, placement key, shared global dependencies, tenant migration và automation vận hành trước khi chọn mô hình này.

### Design 3 — Event Sourcing cần snapshot khi replay cost bắt đầu trở thành bottleneck

**Khái niệm:**
Trong Event Sourcing, aggregate được rebuild bằng cách replay event. Snapshot lưu state tại một version cụ thể để lần load sau chỉ replay các event phát sinh sau snapshot đó.

**Vấn đề nó giải quyết:**
Aggregate sống lâu có thể tích lũy hàng chục nghìn event; replay toàn bộ mỗi command làm latency tăng dù event store vẫn hoạt động đúng.

**Ví dụ thực tế:**
Một `SubscriptionAccount` có 50.000 billing/plan events. Hệ thống tạo snapshot mỗi 1.000 events. Khi load version 50.320, nó đọc snapshot version 50.000 rồi replay 320 events còn lại.

**Trade-off:**
Snapshot giảm read/rebuild cost nhưng thêm storage, versioning, migration và nguy cơ snapshot không tương thích khi model thay đổi. Snapshot không được trở thành source of truth thay thế event log.

**Middle → Senior insight:**
Middle developer nên hiểu snapshot là performance optimization, không phải yêu cầu cốt lõi của Event Sourcing. Senior developer phải chọn snapshot frequency dựa trên replay cost, aggregate lifetime, schema evolution và khả năng rebuild snapshot từ event log.
