# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống database connection pooling

**Mẹo:**
Phân biệt `AddDbContextPool` của EF Core với connection pooling của database provider. `DbContext` pooling tái sử dụng instance/context infrastructure; connection pooling tái sử dụng physical database connections. Chỉ bật context pooling khi đã đo được lợi ích và bảo đảm state theo request không bị giữ sai.

**Tại sao hữu ích:**
Một `DbContext` thường mở connection khi query cần và trả connection về provider pool sau đó. Pooling `DbContext` không làm tăng số connection khả dụng và không chữa được connection-pool exhaustion. Ngược lại, vì context instance được tái sử dụng, mutable state gắn theo request có thể gây lỗi khó thấy nếu cấu hình sai.

**Ví dụ:**
Nếu API timeout vì 100 requests giữ SQL connections quá lâu, đổi `AddDbContext` thành `AddDbContextPool` không giải quyết root cause. Hãy đo connection usage, query duration và transaction lifetime trước; context pooling chỉ đáng xét sau khi allocation/context-creation overhead thật sự đáng kể.

**Lưu ý:**
Không lưu tenant-specific mutable state tùy tiện trong pooled context. Đồng thời tránh giữ `DbContext` lâu hoặc dùng concurrent từ nhiều threads; pooling không thay đổi nguyên tắc lifetime/thread-safety của EF Core.

### Tip 2 — Redis hot key có thể làm cluster nghẽn dù tổng cache hit ratio rất đẹp

**Mẹo:**
Khi Redis latency tăng, đừng chỉ nhìn hit ratio tổng. Kiểm tra request distribution theo key/command, CPU/network của node và xem một vài key có nhận phần lớn traffic hay không.

**Tại sao hữu ích:**
Một key cực nóng có thể tập trung workload lên một shard/node trong khi các node khác còn rảnh. Dashboard toàn cluster nhìn trung bình vẫn “ổn”, nhưng request tới hot key bị queue và tail latency tăng. Đây là vấn đề phân bố tải, không phải cache miss.

**Ví dụ:**
Trang chủ e-commerce cache một object `homepage:global` được đọc hàng chục nghìn lần/giây. Nếu tất cả traffic tập trung vào một shard, cân nhắc local in-process cache ngắn hạn, CDN phù hợp hoặc redesign data/access pattern thay vì chỉ scale toàn Redis cluster.

**Lưu ý:**
Đừng tùy tiện replicate/shard một key ở application layer nếu consistency yêu cầu chặt. Tối ưu phải dựa trên access pattern, stale tolerance và telemetry; cache nhiều tầng cũng làm invalidation khó hơn.

### Tip 3 — `HttpClient` retry phải phân biệt transient failure với operation không an toàn để lặp

**Mẹo:**
Chỉ retry khi failure có khả năng transient và operation có semantics cho phép. Với `POST` tạo side effect, dùng idempotency key hoặc protocol/business contract tương ứng trước khi tự động retry.

**Tại sao hữu ích:**
Timeout không chứng minh server chưa xử lý request. Caller có thể mất response sau khi payment/order đã được tạo; retry mù sẽ tạo duplicate side effect. Retry policy vì thế phải xét cả transport failure lẫn business semantics.

**Ví dụ:**
Payment API nhận `POST /charges` với `Idempotency-Key: checkout-8472`. Nếu caller timeout rồi retry cùng key, provider/application có thể trả lại kết quả operation cũ thay vì charge lần hai.

**Lưu ý:**
Không retry mọi `5xx`, `429` hay timeout với cùng policy. Tôn trọng `Retry-After` khi contract hỗ trợ, dùng backoff/jitter phù hợp và giới hạn tổng latency budget. Retry nhiều tầng có thể nhân traffic ngoài dự kiến.

### Tip 4 — Playwright test ổn định hơn khi chờ trạng thái nghiệp vụ, không chờ thời gian cố định

**Mẹo:**
Trong E2E test, chờ element/state/network condition có ý nghĩa thay vì `WaitForTimeout(3000)` để “cho UI chạy xong”. Dùng locator assertions và auto-waiting của Playwright.

**Tại sao hữu ích:**
Fixed sleep vừa làm test chậm vừa flaky: máy nhanh phải chờ thừa, CI chậm hơn 3 giây vẫn fail. Condition-based waiting đồng bộ test với observable behavior của application thay vì tốc độ môi trường.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Saved successfully")).ToBeVisibleAsync();
```
Test xác nhận user-visible outcome thay vì đoán thời gian backend/UI hoàn tất.

**Lưu ý:**
Đừng biến mọi wait thành timeout rất lớn để che race condition. Nếu UI không có trạng thái observable rõ, đó có thể là tín hiệu cần cải thiện application/testability. E2E cũng không nên thay thế integration/unit tests cho mọi branch logic.

### Tip 5 — Core Web Vitals phải được điều tra bằng request waterfall và render path

**Mẹo:**
Khi LCP hoặc INP xấu, dùng browser DevTools/Lighthouse như điểm bắt đầu nhưng truy nguyên network waterfall, resource priority, JavaScript long tasks và backend TTFB trước khi chọn optimization.

**Tại sao hữu ích:**
Một LCP chậm có thể đến từ backend response chậm, hero image quá lớn, resource bị discovery muộn hoặc render-blocking CSS/JS. Nén thêm một API payload nhỏ không giúp nếu critical image chỉ bắt đầu tải sau bundle execution.

**Ví dụ:**
CMS page có TTFB 180 ms nhưng LCP 4 giây. Waterfall cho thấy hero image được JavaScript inject sau hydration và file 2 MB. Sửa delivery/loading path có giá trị hơn scale backend vốn không phải bottleneck.

**Lưu ý:**
Lab score không đại diện hoàn toàn cho real-user performance. Theo dõi field telemetry theo device/network/page type và tránh “tối ưu điểm” bằng cách trì hoãn chức năng quan trọng gây UX regression.

## 🧠 Software Design

### Design 1 — Inbox Pattern kiểm soát duplicate message tại consumer boundary

**Khái niệm:**
Inbox Pattern ghi nhận message identifier đã xử lý, thường trong cùng local transaction với business state change, để consumer có thể nhận lại cùng message mà không lặp side effect.

**Vấn đề nó giải quyết:**
Broker dùng at-least-once delivery có thể redeliver sau lock expiration, network failure hoặc crash giữa business commit và acknowledgement. Nếu handler giả định mỗi message chỉ xuất hiện một lần, duplicate delivery trở thành duplicate order, invoice hoặc state transition.

**Ví dụ thực tế:**
Consumer nhận `PaymentCaptured` với `MessageId=abc`. Transaction kiểm tra/inserts Inbox record và cập nhật `Order` thành `Paid`. Nếu broker gửi lại `abc`, consumer nhận ra message đã hoàn tất và không áp dụng transition lần nữa.

**Trade-off:**
Inbox thêm storage, unique constraint/index, retention/cleanup và transaction work. Nó cũng không tự giải quyết duplicate ở external side effect nếu side effect xảy ra ngoài transaction; khi đó cần idempotency contract hoặc workflow khác.

**Middle → Senior insight:**
Middle developer cần implement deduplication atomically với state change và hiểu acknowledgement timing. Senior / Technical developer phải xác định idempotency boundary, message identity, retention window, ordering semantics và nơi deduplication nên nằm để không biến Inbox thành global bottleneck.

### Design 2 — SQL hay NoSQL phải được chọn từ invariants và access patterns

**Khái niệm:**
Database choice nên bắt đầu từ consistency/invariant requirements, query/access patterns, data shape, scale và operational capability thay vì nhãn “relational cũ” hay “NoSQL scale tốt”.

**Vấn đề nó giải quyết:**
Một workload transaction-heavy cần constraints, joins và multi-row consistency có áp lực khác với document workload được đọc/ghi chủ yếu theo aggregate/partition key. Chọn sai model khiến application phải tái tạo tính năng database ở code hoặc trả chi phí query/scaling không cần thiết.

**Ví dụ thực tế:**
Order/payment ledger có strong relational invariants phù hợp SQL Server/PostgreSQL. Product content có document shape thay đổi và access theo product/tenant có thể phù hợp MongoDB/Cosmos DB nếu partition/query model rõ. Một hệ thống hoàn toàn có thể dùng cả hai ở các bounded contexts khác nhau.

**Trade-off:**
Polyglot persistence tăng operational burden, backup/restore, observability và skill requirements. NoSQL denormalization giảm join nhưng làm update consistency khó hơn; relational model mạnh về integrity nhưng một số distribution patterns cần thiết kế scale kỹ.

**Middle → Senior insight:**
Middle developer cần model đúng theo datastore đã chọn và tránh mô phỏng relational joins tùy tiện trong document database. Senior / Technical developer phải chuyển business invariants và access patterns thành storage requirements, đánh giá failure/operations/cost và chỉ thêm datastore mới khi lợi ích vượt complexity.

### Design 3 — Azure Functions hay Worker Service là quyết định về execution model

**Khái niệm:**
Azure Functions cung cấp trigger-driven/serverless execution và platform-managed scaling; Worker Service là long-running process do team kiểm soát lifecycle, concurrency và hosting. Cả hai đều chạy background work nhưng operational model khác nhau.

**Vấn đề nó giải quyết:**
Một workload bursty theo event có thể hưởng lợi từ Functions, trong khi processor liên tục cần stable throughput, connection reuse hoặc fine-grained process control có thể phù hợp Worker Service hơn. Chọn chỉ theo “serverless hiện đại hơn” bỏ qua workload behavior.

**Ví dụ thực tế:**
Blob upload thưa và không đều kích hoạt metadata extraction có thể phù hợp Function trigger. Service Bus processor chạy 24/7 với throughput ổn định, custom backpressure và nhiều long-lived dependencies có thể đơn giản hơn dưới Worker Service trên App Service/Kubernetes tùy hạ tầng sẵn có.

**Trade-off:**
Functions giảm hosting ceremony nhưng có execution/scale/cold-start/plan constraints và platform-specific behavior. Worker Service cho kiểm soát nhiều hơn nhưng team chịu trách nhiệm capacity, deployment và availability. Chi phí thực tế phụ thuộc traffic và hosting plan.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retries, cancellation, poison messages và graceful shutdown của execution model đang dùng. Senior / Technical developer phải so sánh workload shape, latency/SLO, scaling, concurrency, cost, operational ownership và portability; chọn mô hình đơn giản nhất đáp ứng các pressure đó.
