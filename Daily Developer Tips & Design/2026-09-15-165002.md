# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — EF Core: projection trước khi `Include` cả object graph

**Mẹo:**
Với read-only endpoint chỉ cần vài field, ưu tiên `Select` trực tiếp sang DTO thay vì `Include` nhiều navigation rồi materialize toàn bộ entity graph.

**Tại sao hữu ích:**
Projection giúp EF Core chỉ lấy các column cần thiết, giảm dữ liệu truyền từ database, allocation và change-tracking overhead. Nó cũng làm query contract rõ hơn: endpoint cần dữ liệu gì thì query đúng dữ liệu đó.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.CreatedAt,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(ct);
```

**Lưu ý:**
Projection không tự động làm mọi query nhanh. Aggregate hoặc navigation phức tạp vẫn có thể sinh SQL đắt; kiểm tra SQL/execution plan khi workload quan trọng. Nếu cần mutate aggregate, projection DTO không thay thế entity tracking.

### Tip 2 — Redis: thêm jitter vào TTL để tránh nhiều key hết hạn cùng lúc

**Mẹo:**
Khi populate nhiều cache key cùng thời điểm, thêm một lượng TTL jitter nhỏ thay vì cho tất cả key expire chính xác sau cùng một khoảng thời gian.

**Tại sao hữu ích:**
Nếu hàng nghìn key cùng expire lúc 10:00, lượng cache miss có thể tăng đột biến và dồn traffic về SQL/API nguồn. TTL jitter phân tán thời điểm expiration, giảm nguy cơ cache stampede theo cụm.

**Ví dụ:**
```csharp
var ttl = TimeSpan.FromMinutes(10)
          + TimeSpan.FromSeconds(Random.Shared.Next(0, 90));

await cache.SetStringAsync(key, json,
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = ttl
    }, ct);
```

**Lưu ý:**
Jitter chỉ giảm synchronized expiration; nó không giải quyết hot-key stampede khi một key phổ biến hết hạn. Với hot key, cân nhắc request coalescing/single-flight, stale-while-revalidate hoặc strategy phù hợp với consistency requirement.

### Tip 3 — Kubernetes: phân biệt readiness với liveness probe

**Mẹo:**
Dùng readiness để quyết định Pod có nên nhận traffic; dùng liveness để phát hiện process thực sự cần restart. Đừng cho cả hai probe phụ thuộc vào mọi external dependency theo cùng một cách.

**Tại sao hữu ích:**
Nếu SQL tạm chậm và liveness endpoint cũng kiểm tra SQL, Kubernetes có thể restart hàng loạt Pod đang khỏe về process, làm outage nặng hơn. Readiness có thể tạm loại instance khỏi traffic trong khi liveness chỉ xác minh application còn sống và có khả năng tự phục hồi.

**Ví dụ:**
```text
/readiness -> app initialized, critical serving path usable
/liveness  -> process/event loop vẫn healthy
```

Một dependency outage ngắn có thể làm readiness fail mà không nhất thiết làm liveness fail.

**Lưu ý:**
Probe quá nông cũng vô ích: process có thể sống nhưng deadlock hoặc không phục vụ được request. Thiết kế probe theo failure mode thực tế và đặt timeout/failureThreshold tránh restart loop.

### Tip 4 — File upload: đừng tin `Content-Type` và filename từ client

**Mẹo:**
Khi nhận file upload, coi filename, extension và `Content-Type` do client gửi là untrusted input. Sinh storage name riêng, giới hạn kích thước, validate loại file theo requirement và lưu ngoài executable/web-root boundary khi có thể.

**Tại sao hữu ích:**
Client có thể gửi `invoice.pdf.exe` nhưng khai báo `application/pdf`, hoặc filename chứa path/control characters. Nếu backend dùng trực tiếp metadata này để lưu/phục vụ file, attack surface tăng đáng kể.

**Ví dụ:**
```csharp
var storageName = $"{Guid.NewGuid():N}.bin";
// Validate size + expected signature/content policy trước khi persist.
```

Tên hiển thị gốc có thể lưu như metadata đã sanitize; storage identifier không cần giống filename của user.

**Lưu ý:**
Magic-byte validation cũng không chứng minh file an toàn tuyệt đối. Với document/image processing, cân nhắc malware scanning, parser isolation và giới hạn resource; không log hoặc phản chiếu filename chưa encode vào HTML.

### Tip 5 — AI coding agent: yêu cầu chứng minh thay đổi bằng test và repository evidence

**Mẹo:**
Khi giao bug fix cho AI coding agent, cung cấp reproduction/acceptance criteria và yêu cầu agent chỉ dùng API/version tồn tại trong repository, chạy test liên quan và báo rõ evidence thay vì chỉ tạo patch có vẻ hợp lý.

**Tại sao hữu ích:**
Agent có thể hallucinate package API, suy đoán architecture hoặc sửa symptom ở layer sai. Repository grounding cộng với executable verification biến output từ “code plausible” thành thay đổi có bằng chứng kiểm tra được.

**Ví dụ:**
```text
Goal: fix duplicate invoice generation.
Evidence required:
1. identify current processing path,
2. reproduce with failing test,
3. implement minimal fix,
4. run targeted tests,
5. list remaining assumptions.
```

**Lưu ý:**
Test do chính agent viết có thể chỉ xác nhận implementation mới của nó. Review assertion theo business behavior, kiểm tra negative/concurrency cases và đừng cho agent tự thay requirement để làm test pass.

## 🧠 Software Design

### Design 1 — Outbox Pattern nối database commit với message publishing

**Khái niệm:**
Outbox Pattern ghi business change và message/event cần publish vào cùng local database transaction. Một publisher riêng sau đó đọc outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application `SaveChanges` rồi publish Service Bus message, process có thể crash giữa hai bước: database đã commit nhưng message chưa gửi. Đảo thứ tự cũng có failure ngược lại: message được gửi nhưng database rollback.

**Ví dụ thực tế:**
```text
DB transaction:
- INSERT Order
- INSERT OutboxMessage(OrderCreated)
COMMIT

Publisher:
- đọc OutboxMessage
- publish Azure Service Bus
- đánh dấu processed
```

Consumer vẫn phải xử lý duplicate vì publisher có thể gửi thành công rồi crash trước khi đánh dấu outbox đã processed.

**Trade-off:**
Outbox tránh distributed transaction giữa database và broker, nhưng thêm bảng, polling/publisher lifecycle, cleanup, duplicate delivery và observability. Nó không biến hệ thống thành exactly-once end-to-end.

**Middle → Senior insight:**
Middle developer cần giữ business update và outbox insert trong cùng transaction, đồng thời hiểu consumer phải idempotent. Senior / Technical developer phải quyết định ordering, retention, publisher concurrency, failure recovery và liệu integration có thực sự cần reliable asynchronous delivery trước khi thêm pattern này.

### Design 2 — API backward compatibility là contract-management problem

**Khái niệm:**
API evolution nên bảo vệ behavior mà client đang phụ thuộc, không chỉ giữ endpoint compile được. Thay đổi field, nullability, enum, validation, status code hoặc semantics đều có thể là breaking change.

**Vấn đề nó giải quyết:**
Mobile client cũ có thể tồn tại hàng tháng sau release. Backend đổi `status: "Paid"` thành object mới hoặc biến optional field thành required có thể phá client dù URL `/api/orders` không đổi.

**Ví dụ thực tế:**
```text
V1 response:
{ "status": "Paid" }

Thay đổi an toàn hơn trong cùng contract:
{ "status": "Paid", "paymentMethod": "Card" }

Breaking semantic change lớn:
đưa sang version/contract migration có lifecycle rõ.
```

**Trade-off:**
Backward compatibility giảm deployment coupling nhưng buộc server duy trì contract cũ, test matrix và deprecation lifecycle. Version mọi thay đổi nhỏ lại tạo API surface khó vận hành.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking change ngoài signature và viết contract/integration tests. Senior / Technical developer phải thiết kế compatibility policy, versioning/deprecation strategy và cân bằng tốc độ evolution với chi phí duy trì nhiều client generation.

### Design 3 — Bulkhead isolation giới hạn blast radius giữa các dependency

**Khái niệm:**
Bulkhead isolation chia tài nguyên hoặc concurrency budget giữa các workload/dependency để một dependency chậm không tiêu thụ toàn bộ thread, connection hoặc request capacity của hệ thống.

**Vấn đề nó giải quyết:**
Một API gọi Shipping Provider chậm 20 giây. Nếu mọi request đều tiếp tục mở outbound calls không giới hạn, connection/concurrency bị chiếm hết và các endpoint không liên quan cũng suy giảm dù database và application vẫn khỏe.

**Ví dụ thực tế:**
```text
Checkout API
 ├─ Payment dependency: concurrency budget A
 ├─ Shipping dependency: concurrency budget B
 └─ Internal DB pool: independent capacity

Shipping saturated -> reject/queue/fallback theo policy
thay vì hút hết capacity của process.
```

**Trade-off:**
Bulkhead tăng fault isolation và làm overload predictable hơn, nhưng capacity partition sai có thể từ chối request dù tổng tài nguyên còn trống. Thêm queue/concurrency limiter cũng cần metrics, timeout và tuning.

**Middle → Senior insight:**
Middle developer cần hiểu timeout/retry chưa đủ nếu concurrency vẫn tăng không kiểm soát. Senior / Technical developer phải đặt isolation boundary theo criticality, SLO và shared-resource model, đo saturation thực tế và phối hợp bulkhead với backpressure/circuit breaker thay vì xếp chồng resilience pattern máy móc.
