# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `SemaphoreSlim` để giới hạn concurrency thay vì tạo vô hạn `Task`

**Mẹo:**
Khi xử lý nhiều item bất đồng bộ, đừng mặc định `Task.WhenAll()` trên toàn bộ collection nếu mỗi task gọi database, HTTP API hoặc filesystem. Hãy giới hạn số lượng operation chạy song song bằng `SemaphoreSlim` hoặc API concurrency phù hợp.

**Tại sao hữu ích:**
Giúp tránh connection pool exhaustion, rate-limit downstream, spike memory và tình trạng throughput giảm do quá nhiều request cạnh tranh cùng tài nguyên.

**Ví dụ:**
```csharp
var semaphore = new SemaphoreSlim(8);

var tasks = items.Select(async item =>
{
    await semaphore.WaitAsync(cancellationToken);
    try
    {
        await ProcessAsync(item, cancellationToken);
    }
    finally
    {
        semaphore.Release();
    }
});

await Task.WhenAll(tasks);
```

**Lưu ý:**
Concurrency limit không có một con số đúng cho mọi workload. Cần đo throughput, latency và giới hạn của dependency thay vì chọn `8`, `20` hay `100` theo cảm tính.

### Tip 2 — Dùng projection trong EF Core để tránh load entity graph không cần thiết

**Mẹo:**
Nếu endpoint chỉ cần vài field, dùng `Select()` sang DTO thay vì `Include()` nhiều navigation properties rồi map trong memory.

**Tại sao hữu ích:**
Giảm số cột, số row bị nhân lên bởi join, memory usage và chi phí materialization của EF Core.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto
    {
        Id = x.Id,
        CreatedAt = x.CreatedAt,
        Total = x.Items.Sum(i => i.Quantity * i.UnitPrice)
    })
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Đừng tối ưu projection đến mức tạo query SQL quá phức tạp khó kiểm soát. Với aggregate lớn hoặc expression phức tạp, nên kiểm tra SQL và execution plan thực tế.

### Tip 3 — Dùng `git worktree` khi cần làm song song nhiều branch

**Mẹo:**
Thay vì stash liên tục hoặc clone repository nhiều lần, dùng `git worktree` để checkout nhiều branch vào các thư mục riêng nhưng dùng chung object database.

**Tại sao hữu ích:**
Rất tiện khi đang làm feature nhưng phải hotfix production, review PR khác hoặc chạy hai version của ứng dụng song song.

**Ví dụ:**
```bash
git worktree add ../myapp-hotfix hotfix/payment-timeout
```

Liệt kê worktree:

```bash
git worktree list
```

Xóa sau khi xong:

```bash
git worktree remove ../myapp-hotfix
```

**Lưu ý:**
Cùng một branch không thể được checkout đồng thời ở hai worktree. Ngoài ra cần chú ý các file local như `.env`, secrets hoặc database riêng cho từng workspace.

### Tip 4 — Với Redis, tránh `KEYS *` trên production

**Mẹo:**
Khi cần tìm key theo pattern trên production, ưu tiên `SCAN` thay vì `KEYS`, đặc biệt khi Redis chứa nhiều key.

**Tại sao hữu ích:**
`KEYS` phải duyệt toàn bộ keyspace trong một operation và có thể block Redis event loop đủ lâu để gây latency spike cho request khác. `SCAN` duyệt theo cursor và chia công việc thành nhiều bước nhỏ.

**Ví dụ:**
```bash
redis-cli --scan --pattern 'user-session:*'
```

Hoặc:

```bash
SCAN 0 MATCH user-session:* COUNT 1000
```

**Lưu ý:**
`SCAN` không đảm bảo snapshot tuyệt đối trong khi keyspace đang thay đổi và một key có thể xuất hiện nhiều hơn một lần. Code consumer nên xử lý trường hợp duplicate nếu điều đó quan trọng.

### Tip 5 — Tách timeout, retry và cancellation thành ba khái niệm riêng

**Mẹo:**
Khi gọi outbound API, hãy phân biệt rõ: timeout giới hạn thời gian cho một attempt, retry quyết định có thử lại hay không, và `CancellationToken` cho phép caller hủy toàn bộ operation.

**Tại sao hữu ích:**
Nếu gộp ba khái niệm này, hệ thống dễ có request kéo dài ngoài ý muốn, retry cả lỗi không nên retry hoặc tiếp tục chạy dù upstream đã hủy request.

**Ví dụ:**
```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

await httpClient.GetAsync(
    "https://inventory.internal/items/42",
    timeoutCts.Token);
```

Retry nên được quyết định riêng dựa trên loại lỗi, status code và idempotency của operation.

**Lưu ý:**
Không retry tự động mọi `POST`. Nếu operation có side effect và không có idempotency guarantee, retry có thể tạo duplicate transaction.

## 🧠 Software Design

### Design 1 — Retry Budget thay vì retry vô hạn ở mọi layer

**Khái niệm:**
Retry Budget là cách giới hạn tổng số retry được phép trong một request flow hoặc theo một dependency, thay vì để mỗi layer tự retry độc lập.

**Vấn đề nó giải quyết:**
Nếu API Gateway retry 3 lần, service A retry 3 lần và service B lại retry 3 lần, một request ban đầu có thể tạo hàng chục request downstream. Khi dependency đang gặp sự cố, retry amplification làm hệ thống quá tải nhanh hơn.

**Ví dụ thực tế:**
Một request checkout gọi `OrderService`, sau đó gọi `InventoryService`. Thay vì cả ba layer đều dùng `retry = 3`, hệ thống định nghĩa budget tối đa hai retry cho toàn flow. Những retry đó chỉ áp dụng cho lỗi transient và operation phải đủ an toàn để retry.

**Trade-off:**
Lợi ích là kiểm soát load tốt hơn trong incident và tránh retry storm. Chi phí là logic resilience khó hơn vì cần xác định layer nào sở hữu retry, truyền deadline/budget và observability cho từng attempt.

**Middle → Senior insight:**
Middle developer nên hiểu retry không mặc định làm hệ thống resilient hơn. Senior developer cần thiết kế retry policy theo end-to-end latency budget, idempotency, downstream capacity và failure mode thay vì cấu hình retry riêng lẻ ở từng service.

### Design 2 — Optimistic Concurrency để bảo vệ update cạnh tranh

**Khái niệm:**
Optimistic Concurrency giả định conflict không xảy ra thường xuyên. Thay vì lock record trong thời gian dài, hệ thống lưu version hoặc concurrency token và chỉ update nếu dữ liệu chưa bị thay đổi kể từ lúc đọc.

**Vấn đề nó giải quyết:**
Hai user hoặc hai worker có thể đọc cùng một trạng thái rồi cùng update, khiến thay đổi sau vô tình ghi đè thay đổi trước mà không ai nhận ra.

**Ví dụ thực tế:**
Một bảng `Employee` có `rowversion` trong SQL Server. User A và user B cùng mở form. User A lưu trước làm version đổi. Khi user B lưu bằng version cũ, EF Core phát hiện zero rows updated và ném `DbUpdateConcurrencyException` thay vì silently overwrite.

```csharp
public byte[] RowVersion { get; set; } = default!;
```

```csharp
builder.Property(x => x.RowVersion)
    .IsRowVersion();
```

**Trade-off:**
Lợi ích là không giữ lock lâu và phù hợp với web application có thời gian giữa read và update lớn. Chi phí là application phải xử lý conflict rõ ràng: reject, reload, merge hoặc cho user quyết định.

**Middle → Senior insight:**
Middle developer nên nhận biết lost update và biết dùng concurrency token. Senior developer phải quyết định conflict nào có thể auto-merge, conflict nào phải reject, và business invariant nào cần pessimistic locking hoặc transaction mạnh hơn.

### Design 3 — Strangler Pattern khi thay hệ thống cũ từng phần

**Khái niệm:**
Strangler Pattern thay thế legacy system theo từng capability nhỏ. Traffic hoặc chức năng được chuyển dần sang hệ thống mới thay vì rewrite toàn bộ rồi cut over một lần.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó đồng bộ requirement thay đổi và có rủi ro rất lớn vào thời điểm chuyển đổi. Trong thời gian rewrite, hệ thống cũ vẫn tiếp tục phát triển nên khoảng cách giữa hai hệ thống ngày càng rộng.

**Ví dụ thực tế:**
Một monolith quản lý `Employees`, `Timesheets`, `Leave` và `Invoices`. Team bắt đầu bằng việc đưa `Leave` sang module/service mới. Reverse proxy hoặc application router chuyển `/api/leave/*` sang implementation mới trong khi các endpoint còn lại vẫn dùng legacy application. Sau khi ổn định mới tiếp tục tách capability khác.

**Trade-off:**
Lợi ích là giảm migration risk, có thể release sớm và rollback từng phần. Chi phí là trong một thời gian phải vận hành cả hệ thống cũ lẫn mới, đồng bộ dữ liệu, routing và ownership trở nên phức tạp hơn.

**Middle → Senior insight:**
Middle developer nên hiểu migration có thể được thực hiện incremental thay vì rewrite toàn bộ. Senior developer cần xác định seam phù hợp để tách, chiến lược dữ liệu, compatibility, observability và điều kiện rõ ràng để retire phần legacy cũ.
