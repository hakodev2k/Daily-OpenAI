# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` cho bulk update khi không cần materialize entity

**Mẹo:**
Khi cần cập nhật nhiều row theo một điều kiện đơn giản trong EF Core, cân nhắc `ExecuteUpdateAsync()` thay vì query entity vào memory, sửa từng object rồi `SaveChangesAsync()`.

**Tại sao hữu ích:**
Cách truyền thống phải materialize entity, tạo tracking state và phát nhiều work ở application layer. `ExecuteUpdateAsync()` dịch trực tiếp thành câu lệnh SQL `UPDATE`, giảm round trip, allocation và change-tracking overhead.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```

Cách này phù hợp với maintenance job hoặc batch transition không cần business logic trên từng entity.

**Lưu ý:**
`ExecuteUpdateAsync()` bỏ qua change tracker hiện tại và không tự chạy domain logic gắn với entity instance. Nếu `DbContext` đang track cùng các row đó, state trong memory có thể stale. Không dùng nó để né invariant nghiệp vụ cần kiểm tra từng aggregate.

### Tip 2 — Khi deadlock SQL xảy ra, sửa thứ tự lock trước khi tăng retry

**Mẹo:**
Nếu production có deadlock, thu thập deadlock graph và xem hai transaction đang lock resource theo thứ tự nào trước khi chỉ thêm retry policy.

**Tại sao hữu ích:**
Deadlock thường xuất hiện khi transaction A giữ resource 1 rồi chờ resource 2, trong khi transaction B giữ resource 2 rồi chờ resource 1. Retry giúp request có thể thành công lần sau nhưng không loại bỏ contention pattern gốc.

**Ví dụ:**
```text
Transaction A:
UPDATE Accounts ...
UPDATE Ledger ...

Transaction B:
UPDATE Ledger ...
UPDATE Accounts ...

=> hai transaction lấy lock theo thứ tự ngược nhau
```

Một hướng sửa thường là chuẩn hóa thứ tự truy cập resource, rút ngắn transaction và loại bỏ work không cần thiết bên trong transaction boundary.

**Lưu ý:**
Không phải deadlock nào cũng do cùng một code path. Execution plan, missing index hoặc scan lớn có thể làm phạm vi lock rộng hơn. Retry vẫn hữu ích cho resilience, nhưng phải có backoff và telemetry để không che regression.

### Tip 3 — Với Azure Key Vault, ưu tiên `ManagedIdentityCredential`/`DefaultAzureCredential` thay cho client secret cố định

**Mẹo:**
Khi ứng dụng Azure cần đọc secret hoặc certificate từ Key Vault, ưu tiên identity của workload thay vì lưu `client_secret` trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ secret dài hạn phải rotate, copy giữa environment hoặc vô tình xuất hiện trong pipeline/log. Authorization chuyển sang RBAC/Access Policy của workload identity và có thể áp least privilege rõ ràng hơn.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Local development có thể dùng developer identity; production App Service/Function dùng Managed Identity mà không đổi code.

**Lưu ý:**
Không biến Key Vault thành database đọc mỗi request. Cache secret phù hợp với rotation strategy, theo dõi permission failure rõ ràng và đảm bảo identity chỉ có quyền cần thiết với đúng vault/resource.

### Tip 4 — Trong React, tránh stale closure khi async callback dùng state thay đổi liên tục

**Mẹo:**
Khi callback async hoặc timer cần dựa trên state mới nhất, kiểm tra dependency của hook và cân nhắc functional state update thay vì giữ giá trị cũ trong closure.

**Tại sao hữu ích:**
Mỗi render tạo closure riêng. Một callback được tạo ở render cũ có thể chạy sau vài giây và vẫn đọc state tại thời điểm cũ, gây bug kiểu “UI đôi lúc ghi đè dữ liệu mới” rất khó tái hiện.

**Ví dụ:**
```tsx
setItems(current => [...current, newItem]);
```

Cách này an toàn hơn:
```tsx
setItems([...items, newItem]);
```

khi callback có thể chạy sau và `items` đã thay đổi từ render ban đầu.

**Lưu ý:**
Đừng thêm mọi biến vào dependency array một cách máy móc nếu điều đó tạo lại subscription/request không cần thiết. Hãy hiểu lifecycle của effect, callback và source dữ liệu; với async request còn cần cancellation hoặc request identity để tránh stale response.

### Tip 5 — Dùng multi-stage Docker build để tách build toolchain khỏi runtime image

**Mẹo:**
Với ASP.NET Core container, build/publish bằng SDK image rồi copy artifact sang runtime image nhỏ hơn thay vì chạy production trên image chứa full SDK.

**Tại sao hữu ích:**
Runtime image nhỏ hơn giúp giảm attack surface, thời gian pull image và số package không cần thiết trong production. Nó cũng làm rõ ranh giới giữa build-time dependency và runtime dependency.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish src/Web/Web.csproj -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "Web.dll"]
```

Nếu application cho phép, tiếp tục chạy bằng non-root user và chỉ copy file cần thiết.

**Lưu ý:**
Image nhỏ không đồng nghĩa an toàn tuyệt đối. Vẫn phải scan dependency/base image, pin version hợp lý, rebuild khi có security patch và kiểm tra native dependency thực sự cần trong runtime.

## 🧠 Software Design

### Design 1 — Optimistic vs Pessimistic Concurrency theo conflict rate và cost của conflict

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor đọc/làm việc song song rồi phát hiện conflict lúc commit, thường qua version/token. Pessimistic concurrency giữ lock sớm để ngăn actor khác sửa cùng resource trong thời gian transaction.

**Vấn đề nó giải quyết:**
Khi nhiều request cùng sửa inventory, booking hoặc account state, “last write wins” có thể làm mất update. Hệ thống cần chọn giữa phát hiện conflict sau hay ngăn conflict trước.

**Ví dụ thực tế:**
```text
Profile settings:
- conflict hiếm
- optimistic concurrency hợp lý

Seat reservation ngắn hạn:
- cùng một seat bị tranh chấp cao
- có thể cần lock/atomic reservation ở datastore phù hợp
```

Trong EF Core, `rowversion`/concurrency token thường phù hợp với optimistic concurrency cho aggregate thông thường.

**Trade-off:**
Optimistic concurrency giữ throughput tốt khi conflict hiếm nhưng caller phải retry/merge khi conflict xảy ra. Pessimistic locking giảm conflict logic nhưng tăng blocking, deadlock risk và giữ resource lâu hơn.

**Middle → Senior insight:**
Middle developer cần biết phát hiện và xử lý concurrency exception đúng. Senior / Technical developer phải chọn cơ chế theo contention thực tế, transaction duration, UX khi conflict và invariant nghiệp vụ thay vì mặc định một kiểu cho toàn hệ thống.

### Design 2 — API backward compatibility ưu tiên additive change trước khi versioning

**Khái niệm:**
API evolution nên cố giữ consumer hiện tại hoạt động bằng thay đổi additive như thêm optional field/endpoint hoặc mở rộng behavior tương thích trước khi tạo breaking version mới.

**Vấn đề nó giải quyết:**
Versioning API quá sớm tạo nhiều contract phải maintain song song. Nhưng breaking change âm thầm lại làm mobile app, partner integration hoặc frontend cũ lỗi ngay sau deployment backend.

**Ví dụ thực tế:**
```text
Cần thêm Customer.DisplayName

Tốt:
- thêm field mới optional
- giữ `name` trong compatibility window
- migrate consumer
- deprecate có telemetry

Rủi ro:
- rename `name` -> `displayName` trực tiếp trong cùng version
```

Đặc biệt với mobile client, server phải giả định version cũ có thể tồn tại lâu hơn release cycle backend.

**Trade-off:**
Backward compatibility giảm coordination cost nhưng tạo temporary duplication và deprecation debt. Version mới cho contract sạch hơn nhưng tăng routing, testing, documentation và support matrix.

**Middle → Senior insight:**
Middle developer cần phân biệt additive với breaking change và giữ contract test ổn định. Senior / Technical developer phải quyết định compatibility window, deprecation policy, telemetry consumer usage và thời điểm versioning thực sự đáng chi phí.

### Design 3 — Idempotency Key cho create API khi retry có thể tạo side effect trùng

**Khái niệm:**
Idempotency Key cho phép client retry cùng một logical command mà server nhận biết đây là request đã xử lý hoặc đang xử lý, từ đó tránh tạo duplicate side effect.

**Vấn đề nó giải quyết:**
Client có thể timeout sau khi server đã charge payment hoặc tạo order thành công nhưng trước khi response tới nơi. Nếu client retry một `POST` bình thường, hệ thống có thể tạo thêm order hoặc charge lần hai.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: 8f4c...

Lần 1:
- server xử lý payment
- response bị mất

Lần 2 cùng key:
- server trả lại kết quả đã lưu
- không charge lần nữa
```

Server cần bind key với caller + operation và lưu trạng thái/result đủ lâu theo retry window.

**Trade-off:**
Idempotency tăng reliability cho retry nhưng thêm persistence, cleanup, race-condition handling và semantics khi payload cùng key nhưng khác nội dung. Với operation vốn idempotent như `PUT` theo resource ID cố định, cơ chế riêng có thể không cần.

**Middle → Senior insight:**
Middle developer cần hiểu idempotency không chỉ là “check duplicate ID”. Senior / Technical developer phải định nghĩa key scope, retention, concurrent duplicate behavior, payload mismatch policy và consistency giữa idempotency store với business transaction.
