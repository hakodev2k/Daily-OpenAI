# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded Channel để tạo backpressure cho background processing

**Mẹo:**
Khi producer có thể tạo work item nhanh hơn consumer xử lý, ưu tiên `Channel<T>` có capacity giới hạn thay vì một queue tăng vô hạn trong memory.

**Tại sao hữu ích:**
Bounded channel tạo backpressure: khi queue đầy, producer phải chờ hoặc xử lý theo policy đã chọn. Điều này giúp hệ thống tự giới hạn lượng work đang chờ, tránh memory tăng liên tục khi downstream chậm.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait
});

await channel.Writer.WriteAsync(job, cancellationToken);
```

Nếu consumer chỉ xử lý 100 jobs/giây nhưng producer đẩy 5.000 jobs/giây, bounded channel buộc pressure quay trở lại producer thay vì âm thầm tích lũy hàng trăm nghìn object.

**Lưu ý:**
`Channel<T>` không thay thế durable messaging. Nếu process crash mà work không được phép mất, dùng broker hoặc persistent storage như Azure Service Bus thay vì chỉ giữ queue trong memory.

### Tip 2 — Đừng coi parameterized SQL là miễn nhiễm với parameter-sensitive plans

**Mẹo:**
Khi một stored procedure hoặc query có hiệu năng lúc nhanh lúc chậm tùy parameter, kiểm tra execution plan và data distribution thay vì chỉ thêm index theo cảm tính.

**Tại sao hữu ích:**
SQL Server có thể compile một plan phù hợp với một parameter nhưng kém hiệu quả cho parameter khác. Với dữ liệu lệch mạnh, cùng một query shape có thể cần strategy khác tùy selectivity.

**Ví dụ:**
Một query lấy Orders theo `CustomerId` chạy 20 ms cho khách có 10 order nhưng mất 8 giây cho khách enterprise có 2 triệu order. Evidence nên gồm actual execution plan, estimated/actual rows, statistics và wait information trước khi quyết định rewrite hoặc index.

**Lưu ý:**
Không dùng `OPTION (RECOMPILE)` như fix mặc định. Nó có thể giảm plan reuse và tăng CPU compile. Trước tiên cần chứng minh vấn đề thực sự đến từ parameter-sensitive plan.

### Tip 3 — Với Azure Service Bus, xử lý message như thể duplicate delivery chắc chắn sẽ xảy ra

**Mẹo:**
Thiết kế consumer theo idempotency ngay từ đầu: message có business identifier ổn định, consumer kiểm tra trạng thái đã xử lý trước khi tạo side effect không thể lặp lại.

**Tại sao hữu ích:**
Azure Service Bus thường vận hành theo at-least-once delivery. Nếu consumer xử lý xong nhưng fail trước khi hoàn tất message, broker có thể redeliver cùng message.

**Ví dụ:**
`PaymentCaptured` có `EventId = 9f...`. Trước khi cộng điểm loyalty, consumer kiểm tra Inbox table:

```sql
IF EXISTS (SELECT 1 FROM InboxMessages WHERE EventId = @EventId)
    RETURN;
```

Sau đó business change và việc ghi `InboxMessages` nên nằm trong cùng transaction nếu dùng chung database.

**Lưu ý:**
Không dựa duy nhất vào broker duplicate detection cho business idempotency. Duplicate có thể xuất hiện ở nhiều layer khác nhau, kể cả producer retry hoặc integration partner gửi lại request.

### Tip 4 — Hủy request frontend cũ bằng AbortController khi user thay đổi filter liên tục

**Mẹo:**
Trong Vue.js hoặc React.js, khi một component phát nhiều request nối tiếp do search/filter, hủy request trước đó khi request mới đã supersede nó.

**Tại sao hữu ích:**
Nếu không hủy hoặc kiểm soát sequencing, response cũ có thể về sau response mới và ghi đè state bằng dữ liệu stale. Đây là race condition phía client, không chỉ là vấn đề performance.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function loadProducts(query: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/products?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  });

  return response.json();
}
```

**Lưu ý:**
Hủy request ở browser không đảm bảo backend đã dừng xử lý. Backend vẫn nên propagate cancellation và giới hạn resource consumption đúng cách.

### Tip 5 — Integration test cần kiểm tra behavior qua boundary thật, không mock mọi dependency

**Mẹo:**
Với logic phụ thuộc mạnh vào EF Core, serialization, routing hoặc transaction, bổ sung integration test chạy qua infrastructure thật hoặc gần thật thay vì chỉ unit test repository/service bằng mock.

**Tại sao hữu ích:**
Nhiều lỗi production nằm ở interaction giữa framework và infrastructure: LINQ không translate được, migration thiếu constraint, JSON contract lệch, middleware order sai hoặc transaction behavior khác giả định. Mock thường không bắt được những lỗi này.

**Ví dụ:**
Một test tạo order qua HTTP endpoint, đọc lại từ database và xác nhận response contract. Test đó có thể phát hiện cùng lúc routing, model binding, validation, EF Core mapping và database constraint.

**Lưu ý:**
Không biến mọi test thành end-to-end test. Test suite cần phân tầng: unit test cho logic thuần, integration test cho technical boundary quan trọng, và ít end-to-end test cho critical user journeys.

## 🧠 Software Design

### Design 1 — Idempotent API cho command có thể retry

**Khái niệm:**
Idempotent command API đảm bảo cùng một logical request được gửi lại nhiều lần không tạo thêm side effect ngoài kết quả mong muốn ban đầu. Thường request mang một `Idempotency-Key` hoặc business operation ID ổn định.

**Vấn đề nó giải quyết:**
Trong distributed systems, timeout không nói cho caller biết server đã xử lý request hay chưa. Nếu caller retry một `POST /payments`, request thứ hai có thể tạo payment thứ hai nếu API không có cơ chế deduplication.

**Ví dụ thực tế:**
Mobile app gửi `POST /orders` với `Idempotency-Key`. Server lưu key cùng kết quả tạo order. Nếu cùng key được gửi lại, server trả lại kết quả cũ thay vì tạo order mới.

**Trade-off:**
Lợi ích là retry an toàn hơn và giảm duplicate side effects. Chi phí là storage cho idempotency records, retention policy, xử lý concurrent requests cùng key và quy tắc xác định khi nào hai request được coi là cùng operation.

**Middle → Senior insight:**
Middle developer cần implement key validation, unique constraint và replay response đúng cách. Senior / Technical developer cần quyết định boundary của idempotency, retention window, concurrency semantics, conflict behavior và liệu operation nào thực sự cần guarantee này thay vì áp dụng đồng loạt.

### Design 2 — Azure Functions vs Worker Service cho background processing

**Khái niệm:**
Azure Functions phù hợp với workload event-driven có trigger rõ ràng và elastic execution; Worker Service phù hợp với process chạy dài, lifecycle kiểm soát hơn và workload cần behavior ổn định liên tục.

**Vấn đề nó giải quyết:**
Cả hai đều có thể xử lý background work, nhưng operational model khác nhau. Chọn sai platform có thể tạo cold-start latency, scaling behavior khó đoán hoặc lifecycle phức tạp hơn nhu cầu thực tế.

**Ví dụ thực tế:**
Một job resize ảnh chạy khi Blob được upload, thời lượng ngắn và traffic bursty là ứng viên tốt cho Azure Functions. Một consumer liên tục xử lý stream, giữ connection dài và cần kiểm soát batching, shutdown, health checks chặt chẽ có thể phù hợp hơn với Worker Service.

**Trade-off:**
Functions giảm infrastructure management và scale thuận tiện nhưng có runtime/platform constraints và execution characteristics cần hiểu. Worker Service cho quyền kiểm soát nhiều hơn nhưng đòi hỏi deployment, scaling và availability design rõ ràng hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, shutdown và idempotency của từng model. Senior / Technical developer phải chọn dựa trên workload shape, latency, throughput, scaling, cost, failure recovery và operational ownership, không dựa vào việc một option “cloud-native” hơn.

### Design 3 — Direct DbContext vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like capabilities. Một custom Repository chỉ đáng thêm khi nó tạo ra boundary có giá trị rõ ràng, không phải vì pattern được coi là bắt buộc.

**Vấn đề nó giải quyết:**
Team thường tạo repository để tách application code khỏi data access. Nhưng nếu repository chỉ bọc từng method `Add`, `Update`, `GetById`, abstraction có thể che mất khả năng của EF Core mà không giảm coupling thực sự.

**Ví dụ thực tế:**
Trong một CRUD-heavy application, application service dùng trực tiếp `DbContext` với projection và transaction rõ ràng có thể đơn giản hơn hàng chục generic repository methods. Ngược lại, một aggregate có persistence rules phức tạp có thể hưởng lợi từ repository theo domain boundary như `IOrderRepository`.

**Trade-off:**
Direct `DbContext` giảm boilerplate và giữ query expressiveness, nhưng application layer phụ thuộc trực tiếp EF Core. Repository có thể tạo domain-oriented boundary và hỗ trợ test strategy nhất định, nhưng dễ trở thành lớp pass-through hoặc abstraction quá generic.

**Middle → Senior insight:**
Middle developer cần biết dùng `DbContext` đúng lifecycle, query và transaction boundary. Senior / Technical developer cần đánh giá chi phí abstraction, khả năng thay đổi persistence thực tế, testability, domain boundary và team conventions trước khi quyết định thêm Repository layer.
