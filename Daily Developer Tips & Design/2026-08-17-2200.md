# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CollectionsMarshal.GetValueRefOrAddDefault` khi hot path update `Dictionary` nhiều lần

**Mẹo:**
Khi một hot path cần lookup rồi update cùng một key trong `Dictionary<TKey, TValue>` rất thường xuyên, `CollectionsMarshal.GetValueRefOrAddDefault` có thể tránh double lookup và cho phép cập nhật value trực tiếp qua `ref`.

**Tại sao hữu ích:**
Giảm số lần hash/probe trong dictionary ở code performance-sensitive như aggregation, counters hoặc parsers.

**Ví dụ:**
```csharp
using System.Runtime.InteropServices;

var counts = new Dictionary<string, int>();

ref var count = ref CollectionsMarshal.GetValueRefOrAddDefault(
    counts,
    "approved",
    out var exists);

if (!exists)
{
    count = 0;
}

count++;
```

**Lưu ý:**
Đây là API low-level. Không giữ `ref` qua operation có thể làm dictionary resize hoặc mutate cấu trúc, vì reference có thể bị invalid. Chỉ dùng khi profiling chứng minh lookup cost đáng kể.

### Tip 2 — Dùng `AsNoTrackingWithIdentityResolution()` khi query read-only có nhiều navigation trùng entity

**Mẹo:**
Nếu query read-only join nhiều navigation và cùng một entity có thể xuất hiện lặp lại trong result graph, `AsNoTrackingWithIdentityResolution()` có thể tránh tạo nhiều object instance cho cùng một key mà vẫn không bật full change tracking.

**Tại sao hữu ích:**
Giảm duplicate object trong memory và giữ reference consistency trong graph mà không phải trả giá đầy đủ của tracking.

**Ví dụ:**
```csharp
var projects = await dbContext.Projects
    .AsNoTrackingWithIdentityResolution()
    .Include(x => x.Members)
    .Include(x => x.Owner)
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Nó vẫn có overhead hơn `AsNoTracking()`. Với projection DTO phẳng hoặc query đơn giản không có entity lặp, `AsNoTracking()` thường rẻ hơn.

### Tip 3 — Dùng PostgreSQL `pg_stat_activity` để phân biệt query đang chạy, chờ lock hay idle in transaction

**Mẹo:**
Khi database chậm, kiểm tra `pg_stat_activity` trước khi kết luận query execution chậm. Trạng thái `wait_event`, `state` và `xact_start` giúp nhận diện connection đang chờ lock hoặc transaction bị bỏ mở.

**Tại sao hữu ích:**
Giúp phát hiện nhanh `idle in transaction`, lock contention và long-running transaction là nguyên nhân giữ vacuum/backlog hoặc gây latency dây chuyền.

**Ví dụ:**
```sql
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

**Lưu ý:**
Không terminate session chỉ vì query chạy lâu. Cần xác định owner, transaction purpose và downstream impact trước khi dùng `pg_cancel_backend` hoặc `pg_terminate_backend`.

### Tip 4 — Dùng `git worktree` để giữ song song hotfix và feature branch mà không stash liên tục

**Mẹo:**
Khi đang làm feature nhưng cần chuyển sang hotfix gấp, tạo một working tree khác bằng `git worktree` thay vì stash/checkout qua lại trên cùng thư mục.

**Tại sao hữu ích:**
Giữ nguyên local state, build artifact và IDE context của từng branch, giảm rủi ro stash nhầm hoặc mất thời gian restore environment.

**Ví dụ:**
```bash
git worktree add ../myapp-hotfix hotfix/payment-timeout
```

Sau khi xong:

```bash
git worktree remove ../myapp-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree thông thường. Cũng cần để ý disk usage nếu mỗi worktree tạo build output lớn.

### Tip 5 — Dùng `openssl s_client -showcerts` để kiểm tra chain TLS mà reverse proxy đang thực sự trả

**Mẹo:**
Khi browser hoặc client báo certificate chain lỗi, dùng `openssl s_client -showcerts` để xem server đang gửi những certificate nào thay vì chỉ kiểm tra certificate file trong cấu hình.

**Tại sao hữu ích:**
Giúp phát hiện thiếu intermediate certificate, SNI route sai hoặc load balancer đang serve certificate khác với expected config.

**Ví dụ:**
```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com \
  -showcerts </dev/null
```

**Lưu ý:**
Chain server gửi là một phần của trust validation. Client trust store, hostname, protocol và cipher vẫn có thể gây lỗi dù chain nhìn có vẻ đầy đủ.

## 🧠 Software Design

### Design 1 — Conformist chỉ phù hợp khi upstream model đủ ổn định và chi phí chống lại nó không đáng

**Khái niệm:**
Trong DDD context mapping, Conformist nghĩa là downstream chấp nhận model/contract của upstream gần như nguyên bản thay vì tạo translation layer riêng.

**Vấn đề nó giải quyết:**
Không phải integration nào cũng đáng tạo Anti-Corruption Layer. Với upstream mạnh, ổn định và model đủ gần domain của downstream, translation riêng có thể chỉ tăng code mà không tạo giá trị rõ ràng.

**Ví dụ thực tế:**
Một internal reporting service chỉ đọc employee directory để hiển thị `EmployeeId`, `DisplayName`, `OfficeCode`. Nếu contract này ổn định và semantics trùng với nhu cầu report, service có thể conform thay vì xây domain model riêng chỉ để map lại ba field.

**Trade-off:**
Conformist giảm code, mapping và maintenance nhưng làm downstream phụ thuộc mạnh hơn vào upstream terminology/evolution. Khi semantics bắt đầu khác, coupling này trở nên đắt.

**Middle → Senior insight:**
Middle developer nên hiểu không phải lúc nào abstraction thêm cũng tốt. Senior developer cần đánh giá độ ổn định, quyền kiểm soát upstream, semantic mismatch và cost of change để biết khi nào conform là pragmatic và khi nào phải đặt translation boundary.

### Design 2 — Request Collapsing giảm duplicate work nhưng phải chọn đúng key và freshness window

**Khái niệm:**
Request Collapsing gộp nhiều request đồng thời cho cùng một expensive result thành một operation đang chạy, rồi các caller cùng chờ chung kết quả thay vì fan-out xuống dependency.

**Vấn đề nó giải quyết:**
Khi cache vừa miss hoặc một resource trở nên hot, hàng trăm request có thể cùng gọi DB/API cho cùng một key và tạo thundering herd.

**Ví dụ thực tế:**
100 request cùng lúc hỏi `/exchange-rate/USD-VND`. Process chỉ cho một fetch tới provider chạy; 99 request còn lại await cùng task rồi nhận cùng result.

**Trade-off:**
Giảm load và stampede mạnh, nhưng lỗi/latency của một shared operation ảnh hưởng nhiều caller cùng lúc. Key quá rộng có thể gom nhầm request khác semantics; key quá hẹp thì hiệu quả thấp.

**Middle → Senior insight:**
Middle developer nên nhận ra cache miss đồng thời là một failure mode riêng. Senior developer phải thiết kế collapse key, timeout/cancellation semantics, stale fallback và cách tránh một slow leader biến thành head-of-line blocking.

### Design 3 — Separate storage model cho write path và analytics khi workload xung đột nhau

**Khái niệm:**
Operational workload tối ưu cho transaction ngắn, invariant và cập nhật thường xuyên; analytics tối ưu cho scan lớn, aggregation và lịch sử dài. Khi hai workload cạnh tranh mạnh, tách storage/read model có thể hợp lý hơn ép một database phục vụ cả hai.

**Vấn đề nó giải quyết:**
Dashboard/report nặng có thể consume I/O, cache và connection khiến transaction user-facing chậm, trong khi schema OLTP normalized lại không phù hợp cho analytical query lớn.

**Ví dụ thực tế:**
Timesheet API ghi vào PostgreSQL/SQL Server OLTP. Dữ liệu được replicate hoặc ETL sang warehouse/read model dạng star schema để chạy báo cáo tháng, trend và BI mà không quét bảng transaction chính hàng triệu row.

**Trade-off:**
Tách workload bảo vệ OLTP và cho phép schema analytics tối ưu riêng, nhưng thêm pipeline, eventual consistency, monitoring và data reconciliation. Với workload nhỏ, một database + replica/indexing tốt có thể đơn giản hơn nhiều.

**Middle → Senior insight:**
Middle developer nên phân biệt query chậm do index kém với workload thật sự khác bản chất. Senior developer phải dùng số liệu về volume, freshness SLA, query shape và operational cost trước khi quyết định thêm warehouse/read store thay vì tối ưu hệ hiện tại.
