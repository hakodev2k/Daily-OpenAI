## Developer Tips & Tricks

### 1. Đừng dùng `Task.Run` để “làm async” cho I/O trong ASP.NET Core

**Vấn đề thực tế:** Một endpoint gọi database hoặc HTTP service nhưng lại bọc operation bằng `Task.Run`, ví dụ `await Task.Run(() => repository.LoadAsync(...))`. Cách này không làm I/O nhanh hơn; nó chỉ chiếm thêm một ThreadPool worker để chờ một operation vốn đã asynchronous. Khi traffic tăng, ThreadPool có thể bị pressure, latency tăng và request throughput giảm.

**Cơ chế bên dưới:** Với true async I/O, thread được trả về ThreadPool trong lúc kernel/network/database đang xử lý. Continuation chỉ cần thread khi operation hoàn tất. `Task.Run` phù hợp cho CPU-bound work cần chuyển khỏi request thread, không phải để bọc async I/O. Trong ASP.NET Core, sync-over-async như `.Result`, `.Wait()` còn nguy hiểm hơn vì giữ worker thread trong trạng thái blocked.

**Cách làm tốt hơn:** Giữ call chain async end-to-end và propagate `CancellationToken`.

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

**Khi nên dùng:** Áp dụng cho EF Core, `HttpClient`, file/network I/O và mọi API đã cung cấp async primitive. Chỉ cân nhắc `Task.Run` khi thực sự có CPU-bound work đáng kể và bạn hiểu tác động lên ThreadPool.

### 2. Dùng compiled query cho EF Core hot path sau khi đã đo được query-compilation overhead

**Vấn đề thực tế:** Một query EF Core rất đơn giản được gọi hàng chục nghìn lần mỗi phút. Database query đã nhanh, nhưng profiling cho thấy application vẫn mất CPU ở query compilation/cache lookup. Tối ưu SQL không giải quyết được phần overhead này.

**Cơ chế bên dưới:** EF Core phải biến LINQ expression thành query plan nội bộ trước khi gửi SQL. EF Core có query cache, nhưng vẫn cần so khớp expression tree. `EF.CompileAsyncQuery` tạo delegate đã compile trước và có thể giảm overhead ở hot path ổn định.

**Cách làm tốt hơn:** Chỉ compile query có shape ổn định và tần suất gọi đủ cao để benchmark chứng minh lợi ích.

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<Order>>
    GetOrderById = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.Id == id));

await foreach (var order in GetOrderById(db, orderId)
    .WithCancellation(cancellationToken))
{
    return order;
}
```

**Khi nên dùng:** High-throughput read endpoints, cache-miss paths hoặc background processors có query shape cố định. Không dùng như mặc định cho mọi query; network/database latency thường lớn hơn compilation overhead nhiều lần, vì vậy benchmark trước.

### 3. Tránh `SELECT *` trong hot query: projection giúp cả SQL, network và EF Core materialization

**Vấn đề thực tế:** API chỉ cần `Id`, `Name`, `Status` nhưng repository load toàn bộ entity gồm nhiều column lớn. SQL execution có thể vẫn nhanh, nhưng payload từ database lớn, allocation tăng và EF Core phải materialize dữ liệu không dùng đến.

**Cơ chế bên dưới:** Projection bằng `Select` được EF Core translate xuống SQL, nên database chỉ trả về các column cần thiết. Điều này giảm bytes transferred, memory allocation và object materialization. Với read-only query, kết hợp `AsNoTracking` giúp tránh change-tracking overhead.

**Cách làm tốt hơn:** Project trực tiếp thành DTO/read model tại query boundary.

```csharp
var result = await db.Customers
    .AsNoTracking()
    .Where(x => x.IsActive)
    .OrderBy(x => x.Name)
    .Select(x => new CustomerSummary(
        x.Id,
        x.Name,
        x.Status))
    .Take(100)
    .ToListAsync(cancellationToken);
```

**Khi nên dùng:** List/search endpoints, dashboards, exports và bất kỳ read path nào không cần full aggregate để thực hiện domain behavior. Nếu entity sẽ được sửa trong cùng unit of work, load entity với tracking có thể phù hợp hơn.

### 4. Dùng `git bisect` để tìm commit gây regression thay vì đọc diff tuần tự

**Vấn đề thực tế:** Một bug chỉ xuất hiện ở `main`, nhưng vài trăm commit đã đi qua kể từ release tốt gần nhất. Đọc từng commit hoặc checkout thủ công sẽ tốn nhiều thời gian và dễ bỏ sót.

**Cơ chế bên dưới:** `git bisect` thực hiện binary search trên commit graph. Bạn đánh dấu một commit `good`, một commit `bad`; Git checkout commit ở giữa. Mỗi lần bạn phân loại kết quả, search space giảm gần một nửa.

**Cách làm tốt hơn:** Nếu có test hoặc script tái hiện regression, tự động hóa toàn bộ quá trình.

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
git bisect run dotnet test tests/Regression.Tests --filter FullyQualifiedName~CheckoutRegression
git bisect reset
```

Exit code `0` được xem là good; non-zero là bad. Script kiểm thử phải deterministic để kết quả bisect đáng tin cậy.

**Khi nên dùng:** Regression có một known-good commit/tag và có cách phân loại pass/fail tương đối nhanh. Đặc biệt hiệu quả khi lịch sử thay đổi lớn nhưng bug có reproduction rõ ràng.

### 5. Đừng retry mọi HTTP failure: retry sai có thể nhân tải lên dependency đang gặp sự cố

**Vấn đề thực tế:** Service downstream bắt đầu trả `500` hoặc timeout. Client retry 3 lần cho mọi lỗi khiến một request của người dùng biến thành 4 request downstream. Khi dependency đang quá tải, retry storm có thể làm outage kéo dài hơn.

**Cơ chế bên dưới:** Retry chỉ hữu ích với transient failure và operation có semantics phù hợp. Delay cần backoff và jitter để nhiều instance không retry đồng thời. Với non-idempotent operation như tạo payment/order, retry mù có thể tạo duplicate side effect nếu server đã xử lý request nhưng response bị mất.

**Cách làm tốt hơn:** Xác định retryable failures, giới hạn attempts, dùng exponential backoff + jitter và kết hợp timeout/circuit breaker. Với side-effecting API, dùng idempotency key hoặc protocol đảm bảo deduplication.

```csharp
var request = new HttpRequestMessage(HttpMethod.Post, "/payments");
request.Headers.Add("Idempotency-Key", paymentAttemptId.ToString());
request.Content = JsonContent.Create(payload);

using var response = await httpClient.SendAsync(
    request,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);
```

**Khi nên dùng:** Mọi outbound integration qua HTTP, message broker hoặc remote API. Retry policy phải dựa trên failure semantics của dependency, không chỉ dựa vào status code chung chung.

## Software Design

### 6. Transactional Outbox: đóng khoảng trống giữa database commit và message publish

**Vấn đề thực tế:** Service lưu `Order` thành công vào SQL rồi publish `OrderCreated` lên message broker. Nếu process crash sau database commit nhưng trước publish, database nói order tồn tại trong khi downstream không bao giờ nhận event. Đảo thứ tự cũng không giải quyết được vì message có thể publish thành công rồi database rollback.

**Trade-off thiết kế:** Transactional Outbox ghi business data và outbox message trong cùng local database transaction. Một publisher riêng đọc outbox và gửi message sau đó. Bạn đổi distributed atomicity khó đạt được lấy eventual delivery có thể kiểm soát. Đổi lại, hệ thống phải xử lý duplicate delivery, cleanup outbox, lag monitoring và publisher failure.

```text
HTTP Request
    |
    v
Application Service
    |
    +---- SQL Transaction ----------------+
    |                                     |
    |  INSERT Orders                      |
    |  INSERT OutboxMessages              |
    +---------------- COMMIT -------------+
                      |
                      v
              Outbox Publisher
                      |
                      v
                Message Broker
                      |
                      v
                  Consumer
```

**Khi phù hợp:** Khi một business transaction vừa thay đổi relational database vừa phải phát integration event đáng tin cậy. Không cần thiết nếu toàn bộ workflow nằm trong một database transaction hoặc message loss không có business impact đáng kể.

### 7. Anti-Corruption Layer: đừng để model của external system trở thành domain model của bạn

**Vấn đề thực tế:** Một service tích hợp CRM/vendor API và dùng trực tiếp DTO của vendor xuyên suốt application. Sau vài tháng, tên field, enum, null semantics và lifecycle của vendor len vào business logic. Khi vendor đổi API hoặc doanh nghiệp đổi provider, thay đổi lan khắp codebase.

**Trade-off thiết kế:** Anti-Corruption Layer (ACL) đặt adapter/translator ở boundary. External contract được map sang model mà domain hiểu. Bạn phải viết thêm mapping và test contract, nhưng đổi lại domain không bị coupling với vocabulary và lifecycle của hệ thống bên ngoài.

```text
Domain/Application
       |
       v
  ICustomerRiskGateway
       |
       v
Anti-Corruption Layer
  - Vendor DTO mapping
  - Enum translation
  - Error translation
  - Protocol/auth details
       |
       v
 External Risk API
```

**Khi phù hợp:** Legacy integration, SaaS/vendor APIs, migration giữa hai systems, hoặc bounded contexts có model khác nhau. Nếu integration cực nhỏ và external model thực sự trùng khớp stable contract của domain, ACL phức tạp có thể không đáng chi phí.

### 8. Bulkhead pattern: cô lập resource để một dependency chậm không kéo sập toàn service

**Vấn đề thực tế:** API gọi ba downstream systems. Một reporting service bị treo, các request chờ lâu và chiếm connection/thread/concurrency slots. Cuối cùng các endpoint không liên quan cũng chậm dù dependency của chúng hoàn toàn khỏe.

**Trade-off thiết kế:** Bulkhead giới hạn concurrency/resource pool theo dependency hoặc workload. Khi một partition đầy, chỉ workload đó bị reject/queue thay vì tiêu thụ toàn bộ tài nguyên của process. Chi phí là phải chọn capacity, xử lý rejection và quan sát saturation; cấu hình quá thấp lại tự tạo bottleneck.

```text
                    +--> [Bulkhead A: 20] --> Payment API
Incoming Requests --+
                    +--> [Bulkhead B: 10] --> Reporting API
                    |
                    +--> [Bulkhead C: 30] --> Inventory API

Reporting API chậm
        |
        v
Bulkhead B saturated/rejects
        |
        +---- Payment và Inventory vẫn có capacity riêng
```

**Khi phù hợp:** Service có nhiều remote dependencies, multi-tenant workloads, expensive background jobs hoặc shared resource dễ bị exhaustion. Bulkhead hiệu quả nhất khi đi cùng timeout, circuit breaker và metrics như queue depth, rejection count, active concurrency.
