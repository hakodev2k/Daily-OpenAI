# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test code phụ thuộc thời gian

**Mẹo:**
Thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi, inject `TimeProvider` vào service cần thời gian.

**Tại sao hữu ích:**
Giúp test các case như token expiry, timeout window, daily cutoff hoặc retry schedule mà không phải chờ thời gian thật trôi qua.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

**Lưu ý:**
Đừng tạo abstraction riêng quanh clock nếu framework đã cung cấp `TimeProvider`; abstraction thừa chỉ làm tăng maintenance cost.

### Tip 2 — Dùng `ExecuteDeleteAsync` khi cần xóa hàng loạt bằng EF Core

**Mẹo:**
Nếu chỉ cần xóa các rows theo điều kiện và không cần domain logic trên từng entity, dùng `ExecuteDeleteAsync()` thay vì load rồi `RemoveRange()`.

**Tại sao hữu ích:**
Tránh materialize hàng nghìn entity vào memory và giảm số lượng SQL command.

**Ví dụ:**
```csharp
await db.AuditLogs
    .Where(x => x.CreatedAt < cutoff)
    .ExecuteDeleteAsync(cancellationToken);
```

**Lưu ý:**
Operation này bypass change tracking và entity lifecycle logic. Không dùng nếu cần trigger domain event trong application hoặc xử lý từng entity trước khi delete.

### Tip 3 — Dùng `curl -v` để debug TLS, redirect và headers

**Mẹo:**
Khi API “works on my machine” nhưng fail ở server, dùng `curl -v` để xem DNS/TLS handshake, request headers, redirect và response headers.

**Tại sao hữu ích:**
Nhiều lỗi integration không nằm trong business code mà nằm ở proxy, certificate, redirect hoặc authentication header.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Hoặc theo redirect:

```bash
curl -v -L https://api.example.com/login
```

**Lưu ý:**
Verbose output có thể chứa `Authorization`, cookie hoặc token. Không paste nguyên log vào ticket công khai nếu chưa redact.

### Tip 4 — Dùng `SET STATISTICS IO` để nhận ra query đọc quá nhiều page

**Mẹo:**
Trong SQL Server, bật `SET STATISTICS IO ON` khi query có vẻ chậm để xem logical reads thay vì chỉ nhìn execution time.

**Tại sao hữu ích:**
Một query chạy nhanh trong dev vì data nhỏ nhưng logical reads cao có thể trở thành bottleneck khi production data tăng.

**Ví dụ:**
```sql
SET STATISTICS IO ON;

SELECT Id, CustomerId, CreatedAt
FROM Orders
WHERE Status = 'Pending';
```

**Lưu ý:**
Logical reads cao không tự động có nghĩa là cần index mới. Cần xem thêm cardinality, selectivity, execution plan và workload write.

### Tip 5 — Dùng concurrency limit thay vì `Task.WhenAll` không giới hạn

**Mẹo:**
Khi xử lý hàng nghìn item có I/O async, đừng tạo toàn bộ task cùng lúc. Giới hạn số operation chạy song song bằng `Parallel.ForEachAsync` hoặc `SemaphoreSlim`.

**Tại sao hữu ích:**
Tránh làm cạn connection pool, socket, rate limit hoặc memory trong batch processing.

**Ví dụ:**
```csharp
await Parallel.ForEachAsync(
    items,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 8,
        CancellationToken = cancellationToken
    },
    async (item, ct) =>
    {
        await client.ProcessAsync(item, ct);
    });
```

**Lưu ý:**
Không chọn `MaxDegreeOfParallelism` bằng cảm tính. Tối ưu dựa trên latency, downstream capacity, connection pool và rate limit thực tế.

## 🧠 Software Design

### Design 1 — Strangler Fig Pattern khi thay legacy system

**Khái niệm:**
Strangler Fig Pattern thay thế hệ thống cũ theo từng capability nhỏ thay vì rewrite toàn bộ trong một lần. Traffic hoặc feature được chuyển dần sang implementation mới.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó kiểm chứng và tạo giai đoạn nhiều tháng không mang lại business value trong khi legacy system vẫn tiếp tục thay đổi.

**Ví dụ thực tế:**
Một monolith cũ có Orders, Billing và Reporting. Team đầu tiên tách Reporting ra service mới, route endpoint reporting sang hệ thống mới, còn Orders/Billing vẫn chạy legacy. Sau khi ổn định mới tiếp tục migrate capability khác.

**Trade-off:**
Ưu điểm là giảm migration risk và cho phép rollback từng phần. Chi phí là phải duy trì hai hệ thống, routing/integration layer và đôi khi duplicate data trong giai đoạn chuyển tiếp.

**Middle → Senior insight:**
Middle developer cần hiểu migration theo slice an toàn hơn rewrite toàn bộ. Senior developer phải chọn boundary migrate dựa trên dependency, business value và data ownership, đồng thời lập kế hoạch loại bỏ compatibility layer để tránh “temporary architecture” tồn tại vĩnh viễn.

### Design 2 — Saga: orchestration hay choreography?

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction. Có thể điều phối bằng central orchestrator hoặc để các service phản ứng lẫn nhau qua events theo choreography.

**Vấn đề nó giải quyết:**
Trong distributed system, không thể dựa vào một ACID transaction duy nhất để update nhiều database/service độc lập.

**Ví dụ thực tế:**
Checkout gồm `CreateOrder`, `ReserveInventory`, `ChargePayment`, `ArrangeShipment`. Nếu payment thất bại sau khi inventory đã reserve, workflow phải chạy compensation để release inventory.

**Trade-off:**
Orchestration dễ theo dõi flow và compensation nhưng tạo coordinator trung tâm. Choreography giảm coupling trực tiếp nhưng flow business dễ trở nên khó quan sát khi quá nhiều event nối tiếp nhau.

**Middle → Senior insight:**
Middle developer cần hiểu compensation không giống rollback database. Senior developer phải chọn orchestration/choreography dựa trên độ phức tạp workflow, ownership và observability; đồng thời thiết kế idempotency, timeout và partial-failure states ngay từ đầu.

### Design 3 — Consumer-driven contract testing cho API giữa các team

**Khái niệm:**
Consumer-driven contract testing cho phép consumer mô tả những phần contract thực sự phụ thuộc, sau đó provider xác minh contract đó trong CI.

**Vấn đề nó giải quyết:**
Integration test end-to-end thường chậm và không phát hiện sớm breaking change. Trong khi đó, provider có thể vô tình đổi field, status code hoặc semantics mà consumer đang phụ thuộc.

**Ví dụ thực tế:**
Mobile Backend phụ thuộc `GET /employees/{id}` trả `id`, `status`, `email`. Consumer publish contract; Employee Service verify contract trong pipeline trước khi release API mới.

**Trade-off:**
Giúp phát hiện breaking change sớm và giảm phụ thuộc vào shared staging environment, nhưng cần contract lifecycle, versioning và discipline để không biến test thành mirror toàn bộ response schema.

**Middle → Senior insight:**
Middle developer cần biết API compatibility phải được kiểm thử tự động, không chỉ dựa vào documentation. Senior developer cần quyết định contract nào đủ quan trọng để enforce, cách evolve schema tương thích ngược và khi nào contract testing bổ sung — chứ không thay thế — integration test thực tế.
