# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng giữ `DbContext` sống lâu hơn một unit of work

**Mẹo:**
Giữ `DbContext` theo scope ngắn, thường tương ứng một HTTP request hoặc một background-message handling unit. Với batch dài, tạo scope/context theo từng chunk thay vì dùng một context duy nhất cho hàng nghìn entities.

**Tại sao hữu ích:**
`DbContext` giữ change-tracking state cho entities đã materialize. Context sống quá lâu làm tracker phình ra, tăng memory, làm `DetectChanges` tốn hơn và dễ vô tình persist entity đã được sửa từ rất lâu trong workflow.

**Ví dụ:**
```csharp
foreach (var batch in batches)
{
    await using var db = await dbContextFactory.CreateDbContextAsync(ct);
    await ProcessBatchAsync(db, batch, ct);
    await db.SaveChangesAsync(ct);
}
```

**Lưu ý:**
Đừng chữa mọi query bằng `ChangeTracker.Clear()`. Nếu transaction nghiệp vụ thực sự phải atomic xuyên nhiều bước, cần thiết kế transaction boundary trước; chia context tùy tiện có thể phá invariant.

### Tip 2 — Dùng execution plan để phân biệt “index thiếu” với cardinality estimate sai

**Mẹo:**
Khi SQL query chậm, xem actual execution plan và so sánh estimated rows với actual rows trước khi thêm index. Chênh lệch lớn thường chỉ ra statistics, parameter sensitivity hoặc predicate khiến optimizer ước lượng sai.

**Tại sao hữu ích:**
Một index mới có thể che triệu chứng nhưng tăng write cost và storage. Nếu optimizer dự đoán 100 rows nhưng thực tế đọc 2 triệu rows, nguyên nhân có thể nằm ở distribution hoặc plan reuse chứ không đơn giản là “thiếu index”.

**Ví dụ:**
Một API `/orders?tenantId=...` nhanh với tenant nhỏ nhưng chậm với tenant lớn. Execution plan được compile từ distribution không đại diện có thể chọn Nested Loops trong khi workload lớn phù hợp strategy khác.

**Lưu ý:**
Không áp dụng `OPTION (RECOMPILE)` hay hint hàng loạt chỉ vì một plan xấu. Recompile có CPU cost; query hint có thể khóa optimizer vào quyết định tệ khi data distribution thay đổi.

### Tip 3 — Azure Service Bus consumer phải coi duplicate delivery là trạng thái bình thường

**Mẹo:**
Thiết kế message handler sao cho cùng một business message được xử lý lại không tạo side effect lần hai. Dùng stable message/business id và lưu processing state ở boundary phù hợp.

**Tại sao hữu ích:**
Message có thể được redeliver nếu consumer hoàn thành business work nhưng mất lock hoặc crash trước khi settle message. At-least-once delivery nghĩa là duplicate không phải edge case hiếm mà là failure mode phải dự kiến.

**Ví dụ:**
```sql
INSERT INTO ProcessedMessages(MessageId, ProcessedAt)
VALUES (@messageId, SYSUTCDATETIME());
```

Đặt unique constraint trên `MessageId`, và nếu business update nằm cùng SQL database thì cân nhắc ghi deduplication marker trong cùng local transaction.

**Lưu ý:**
Service Bus duplicate detection không thay thế business idempotency trong mọi trường hợp: nó có time window và chỉ giải quyết một lớp duplicate. External side effect như payment hoặc email cần semantics riêng.

### Tip 4 — Dùng `git bisect` khi regression có khoảng commit đủ rõ

**Mẹo:**
Khi biết một commit cũ chạy đúng và HEAD bị lỗi, dùng `git bisect` để thu hẹp commit gây regression theo binary search thay vì checkout từng commit tuần tự.

**Tại sao hữu ích:**
Với hàng trăm commits, số lần kiểm tra giảm mạnh. Nếu có test hoặc script tái hiện lỗi, `git bisect run` biến điều tra regression thành quy trình có thể lặp lại thay vì dựa vào phỏng đoán từ commit message.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests
```

**Lưu ý:**
Test dùng cho bisect phải deterministic và exit code phải phản ánh good/bad chính xác. Commit không build được cần được xử lý/skip hợp lý, nếu không kết luận có thể sai.

### Tip 5 — File upload phải được kiểm tra như dữ liệu không tin cậy

**Mẹo:**
Với ASP.NET Core upload endpoint, giới hạn kích thước, sinh server-side filename, kiểm tra authorization, validate loại nội dung bằng evidence phù hợp và lưu file ngoài web root hoặc vào Blob Storage với quyền tối thiểu.

**Tại sao hữu ích:**
Tin vào filename hoặc `Content-Type` từ client có thể dẫn tới path traversal, overwrite, executable content hoặc lưu payload nguy hiểm. Boundary upload cần tách metadata do client khai báo khỏi quyết định bảo mật của server.

**Ví dụ:**
```csharp
var objectName = $"uploads/{Guid.NewGuid():N}";
await blobClient.UploadAsync(stream, overwrite: false, cancellationToken: ct);
```

Tên hiển thị gốc có thể lưu như metadata đã sanitize thay vì dùng làm storage path.

**Lưu ý:**
Extension allowlist không chứng minh nội dung an toàn. Với domain rủi ro cao cần malware scanning/quarantine workflow; đồng thời tránh đọc toàn bộ file lớn vào memory chỉ để validate.

## 🧠 Software Design

### Design 1 — Outbox Pattern để nối database transaction với message publication

**Khái niệm:**
Outbox ghi business change và một record mô tả event/message trong cùng local database transaction. Một publisher riêng sau đó đọc outbox và gửi message ra broker.

**Vấn đề nó giải quyết:**
Nếu application commit Order vào SQL rồi crash trước khi publish `OrderCreated`, database và messaging state bị lệch. Nếu publish trước rồi database rollback, consumer lại nhìn thấy event cho state chưa tồn tại.

**Ví dụ thực tế:**
Checkout transaction ghi `Orders` và `OutboxMessages`. Worker đọc các outbox rows chưa publish, gửi tới Azure Service Bus rồi đánh dấu trạng thái. Consumer vẫn phải idempotent vì publisher có thể crash sau send nhưng trước khi mark completed.

**Trade-off:**
Outbox loại bỏ dual-write gap giữa local database và broker mà không cần distributed transaction, nhưng thêm table growth, polling/publishing latency, cleanup, monitoring và duplicate-delivery handling.

**Middle → Senior insight:**
Middle developer cần hiểu atomic write và viết publisher/consumer idempotent. Senior / Technical developer phải quyết định khi nào inconsistency window thực sự đáng Outbox, chọn polling hay CDC, thiết kế ordering/retention/recovery và tránh biến Outbox thành event bus framework quá phức tạp.

### Design 2 — Transaction boundary nên bám business invariant, không bám repository method

**Khái niệm:**
Transaction boundary là phạm vi thay đổi phải thành công hoặc thất bại cùng nhau để bảo vệ invariant. Nó nên được xác định từ use case/business rule thay vì mỗi repository tự mở transaction riêng.

**Vấn đề nó giải quyết:**
Một use case tạo Invoice rồi cập nhật AccountBalance. Nếu hai repository commit độc lập, lỗi giữa hai bước để lại state hợp lệ về kỹ thuật nhưng sai nghiệp vụ.

**Ví dụ thực tế:**
Trong một relational database, application service có thể điều phối cả hai thay đổi bằng một `DbContext`/transaction. Nếu boundary đi qua service/database khác, không nên giả vờ có ACID toàn cục; cân nhắc Saga/compensation và eventual consistency.

**Trade-off:**
Transaction rộng đơn giản hóa invariant nhưng giữ locks/resources lâu hơn và giảm concurrency. Transaction quá nhỏ tăng partial-failure complexity. Distributed transaction có semantics mạnh nhưng coupling và operational constraints lớn.

**Middle → Senior insight:**
Middle developer cần biết operation nào phải atomic và không commit ngẫu nhiên trong repository. Senior / Technical developer phải phân biệt invariant thật với convenience, thu nhỏ transaction hợp lý và chọn ACID, compensation hay eventual consistency dựa trên failure semantics.

### Design 3 — Feature Flag tách deployment khỏi release, nhưng tạo thêm state của hệ thống

**Khái niệm:**
Feature Flag cho phép code được deploy nhưng behavior mới chỉ bật cho tenant, cohort hoặc thời điểm xác định. Deployment và business release vì thế không còn là cùng một sự kiện.

**Vấn đề nó giải quyết:**
Một thay đổi checkout lớn cần rollout dần để quan sát error rate và rollback behavior nhanh mà không phải redeploy toàn bộ application.

**Ví dụ thực tế:**
Deploy cả old/new pricing path, bật new path cho internal users rồi 5% traffic. Metrics phân tách theo flag variant giúp phát hiện regression trước khi tăng rollout.

**Trade-off:**
Flag giảm release risk và hỗ trợ progressive delivery, nhưng mỗi flag tạo thêm execution paths, test combinations và operational state. Flag cũ không được dọn sẽ trở thành technical debt và làm code khó suy luận.

**Middle → Senior insight:**
Middle developer cần tránh rải `if (flag)` xuyên domain logic và test cả trạng thái quan trọng. Senior / Technical developer phải thiết kế ownership, expiry/removal policy, telemetry, safe default khi flag provider lỗi và quyết định khi nào blue/green hoặc deployment rollback đơn giản hơn feature flag.
