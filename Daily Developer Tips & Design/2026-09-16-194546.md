# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow`

**Mẹo:**
Với logic phụ thuộc thời gian như token expiry, retry window, cache TTL hoặc scheduled processing, inject `TimeProvider` thay vì rải `DateTime.UtcNow` khắp business code.

**Tại sao hữu ích:**
Clock là một external dependency. Khi đọc system clock trực tiếp, test phải phụ thuộc thời gian thật và dễ flaky ở boundary. `TimeProvider` của modern .NET cho phép production dùng `TimeProvider.System`, còn test kiểm soát thời gian mà không cần `Thread.Sleep`.

**Ví dụ:**
```csharp
public sealed class ResetTokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        timeProvider.GetUtcNow() >= expiresAt;
}
```
Test có thể cung cấp controllable provider và dịch clock qua đúng expiry boundary.

**Lưu ý:**
Đừng tạo abstraction `IClock` riêng nếu `TimeProvider` đã đáp ứng nhu cầu. Nhưng cũng không nên dùng fake time để che logic concurrency thực sự cần kiểm thử với scheduler/timer semantics.

### Tip 2 — Dùng keyset pagination cho feed lớn thay vì OFFSET ngày càng sâu

**Mẹo:**
Với API duyệt tuần tự qua dataset lớn, dùng cursor dựa trên stable sort keys thay vì `Skip(page * size)` khi deep pagination là workload phổ biến.

**Tại sao hữu ích:**
`OFFSET` vẫn buộc database tìm/sắp xếp rồi bỏ qua nhiều rows trước khi trả page hiện tại. Khi offset tăng, work có thể tăng đáng kể. Keyset pagination tiếp tục từ giá trị cuối của page trước và tận dụng ordered index hiệu quả hơn.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp cần theo ordering/query pattern, ví dụ `(CreatedAt DESC, Id DESC)` với include columns cần thiết.

**Lưu ý:**
Cursor phải dựa trên ordering deterministic; chỉ dùng `CreatedAt` có thể bỏ hoặc lặp rows khi nhiều records cùng timestamp. Keyset không phù hợp nếu UX bắt buộc nhảy trực tiếp đến page 4,731 theo số trang.

### Tip 3 — Đừng retry mọi lỗi `HttpClient`; phân loại transient và permanent failure

**Mẹo:**
Retry outbound HTTP chỉ với failure có khả năng tự phục hồi, đồng thời đặt timeout và retry budget rõ ràng.

**Tại sao hữu ích:**
Retry `400`, validation error hoặc authentication failure chỉ nhân tải vô ích. Ngay cả `5xx`/timeout cũng cần giới hạn vì nhiều retry layers có thể khuếch đại traffic khi dependency đang suy yếu.

**Ví dụ:**
```text
Request timeout budget: 3 s
Attempt 1: 700 ms timeout
Backoff: 100 ms
Attempt 2: 700 ms timeout
Backoff: 250 ms
Attempt 3: 700 ms timeout
Remaining budget dành cho application handling
```
Với `429`, tôn trọng `Retry-After` nếu contract cho phép; với command không idempotent, xác định duplicate semantics trước khi retry.

**Lưu ý:**
Không đặt retry ở controller, service, SDK và gateway cùng lúc mà không có tổng budget. Retry storm có thể biến partial outage thành cascading failure.

### Tip 4 — Dùng `git bisect` để tìm commit gây regression thay vì đọc diff tuần tự

**Mẹo:**
Khi biết một commit cũ tốt và HEAD hiện tại lỗi, dùng `git bisect` để binary-search lịch sử commit.

**Tại sao hữu ích:**
Với hàng trăm commits, kiểm tra tuần tự rất tốn thời gian. `git bisect` giảm số lần test xuống xấp xỉ `log2(N)` và có thể tự động hóa nếu regression có command test tái hiện được.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.8.0
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
git bisect reset
```
Một regression trải trên 512 commits về lý thuyết chỉ cần khoảng 9 bước phân đôi nếu test phân loại good/bad ổn định.

**Lưu ý:**
Flaky test làm `bisect` đưa ra kết luận sai. Merge commits, build failures hoặc thay đổi test infrastructure có thể cần `git bisect skip` và manual verification.

### Tip 5 — Với Elasticsearch, filter exact-match đừng đưa vào full-text scoring

**Mẹo:**
Tách điều kiện exact-match như tenant, status, category hoặc permission sang filter context; chỉ dùng full-text query cho trường thực sự cần relevance scoring.

**Tại sao hữu ích:**
`must` full-text clauses tham gia tính `_score`; filter clauses chỉ quyết định match/no-match và phù hợp hơn với structured constraints. Điều này làm query intent rõ hơn và tránh chi phí scoring không cần thiết.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless keyboard" } }
      ],
      "filter": [
        { "term": { "tenantId": "acme" } },
        { "term": { "status": "published" } }
      ]
    }
  }
}
```
`title` cần analyzer/relevance; `tenantId` và `status` là structured constraints.

**Lưu ý:**
Mapping phải đúng: exact-match thường cần `keyword`, không phải analyzed `text`. Đừng chữa mapping sai chỉ bằng cách thay query DSL; reindex có thể cần thiết khi field type không phù hợp.

## 🧠 Software Design

### Design 1 — Bulkhead: cô lập tài nguyên để một dependency không kéo sập toàn service

**Khái niệm:**
Bulkhead giới hạn concurrency/resource dành cho từng workload hoặc dependency thay vì cho tất cả requests tranh chung một pool không kiểm soát.

**Vấn đề nó giải quyết:**
Một third-party pricing API bắt đầu phản hồi trong 20 giây. Nếu mọi request tiếp tục mở outbound operations đến dependency này, threads/connections/queue slots có thể bị chiếm hết và cả những endpoint không liên quan cũng suy giảm.

**Ví dụ thực tế:**
Pricing integration được giới hạn tối đa 40 concurrent calls và bounded queue. Khi capacity đầy, application fail fast hoặc degrade feature theo business rule, trong khi Order History vẫn còn tài nguyên để phục vụ.

**Trade-off:**
Bulkhead giới hạn blast radius và làm overload behavior dự đoán được hơn, nhưng capacity quá thấp gây artificial throttling; quá cao lại không tạo isolation. Nó cũng thêm tuning, telemetry và fallback decisions.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency limits, timeout và cancellation. Senior / Technical developer phải xác định resource nào thực sự shared, đặt capacity dựa trên measurements, quyết định fail-fast/degradation semantics và tránh tạo hàng loạt isolated pools không cần thiết.

### Design 2 — SQL hay document database phải bắt đầu từ access pattern và consistency boundary

**Khái niệm:**
Lựa chọn relational database hay MongoDB/Cosmos DB không nên dựa trên việc dữ liệu “trông giống JSON”. Cần xem aggregate boundary, query patterns, transaction requirements, data distribution và cách hệ thống scale.

**Vấn đề nó giải quyết:**
Một product catalog có document shape linh hoạt và thường đọc toàn aggregate có thể phù hợp document model. Ngược lại, order/payment/reporting có nhiều relational constraints, joins và cross-entity transactions có thể đơn giản hơn đáng kể trên SQL.

**Ví dụ thực tế:**
CMS content item gồm nhiều nested blocks thường được load theo document và thay đổi schema thường xuyên. Document store có thể giảm impedance. Nhưng nếu reporting cần join tự do giữa hàng chục dimensions và strong constraints, relational model có thể cho query/consistency model rõ ràng hơn.

**Trade-off:**
Document model hỗ trợ denormalization và aggregate-local reads tốt nhưng tạo duplication, partition-key pressure và khó khăn với cross-document consistency/query patterns. SQL cung cấp constraints, joins và mature transaction semantics nhưng scale/distribution model có trade-offs riêng.

**Middle → Senior insight:**
Middle developer cần model đúng theo database đã chọn và hiểu indexes/transactions. Senior / Technical developer phải dự báo access patterns, partition growth, consistency requirements, operational skill của team và migration cost; polyglot persistence chỉ đáng giá khi lợi ích vượt chi phí vận hành thêm datastore.

### Design 3 — Feature Flags tách deployment khỏi release nhưng tạo state cần quản trị

**Khái niệm:**
Feature Flag cho phép code được deploy trước nhưng behavior mới chỉ bật cho tenant, cohort hoặc thời điểm phù hợp. Deployment đưa artifact vào production; release quyết định ai thực sự sử dụng capability.

**Vấn đề nó giải quyết:**
Một checkout mới cần rollout 5% traffic, quan sát error/latency rồi tăng dần mà không build/deploy lại mỗi bước. Khi metric xấu, team có thể disable behavior nhanh hơn rollback toàn artifact.

**Ví dụ thực tế:**
Backend deploy cả `LegacyPricing` và `NewPricing`. Flag service quyết định path theo tenant/cohort. Dashboard so sánh latency, error rate và business outcome; rollout tăng 5% → 25% → 100% nếu guardrails ổn.

**Trade-off:**
Flags giảm release risk và hỗ trợ progressive delivery, nhưng mỗi flag tạo thêm runtime states, test combinations và dead code. Flag tồn tại quá lâu trở thành technical debt và có thể khiến incident khó chẩn đoán.

**Middle → Senior insight:**
Middle developer cần đặt flag ở boundary rõ ràng, test cả on/off và có safe default. Senior / Technical developer phải phân loại release/ops/permission flags, xác định owner, expiry/removal policy, telemetry và failure behavior của flag provider; flag không thay thế rollback strategy hay backward-compatible database migration.
