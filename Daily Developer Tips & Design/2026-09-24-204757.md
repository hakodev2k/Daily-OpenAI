# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — Large Object Heap cần được chẩn đoán từ allocation pattern, không chỉ nhìn tổng memory

**Mẹo:**
Khi .NET process tăng memory hoặc GC pause bất thường, kiểm tra các allocation lớn và lifetime của chúng thay vì chỉ nhìn Working Set. Object lớn khoảng 85 KB trở lên thường đi vào Large Object Heap (LOH), nên buffer, JSON payload hoặc array lớn lặp lại có thể tạo GC pressure đáng kể.

**Tại sao hữu ích:**
LOH được thu gom cùng Gen 2 và object lớn tốn chi phí allocate/scan/compact khác với nhiều object nhỏ. Một API export tạo liên tục `byte[]` vài MB có thể có throughput kém dù không có memory leak thực sự.

**Ví dụ:**
Dùng `dotnet-counters` để quan sát allocation rate, Gen 2 GC và LOH size, sau đó dùng profiler hoặc `dotnet-gcdump` xác định type nào đang chiếm vùng nhớ. Nếu nguyên nhân là file export, streaming trực tiếp ra response thường hợp lý hơn việc dựng toàn bộ file trong một `byte[]` trước.

**Lưu ý:**
Đừng chuyển mọi buffer sang pooling chỉ vì thấy LOH. `ArrayPool<T>` yêu cầu quản lý lifetime cẩn thận và có thể giữ buffer lớn lâu hơn dự kiến. Trước tiên phải chứng minh allocation đó nằm trên hot path và liên quan đến symptom production.

### Tip 2 — ASP.NET Core rate limiting nên partition theo identity phù hợp với resource boundary

**Mẹo:**
Khi dùng Rate Limiting middleware, chọn partition key theo resource cần bảo vệ: authenticated user, tenant, API key hoặc IP tùy endpoint; đừng mặc định dùng một global limiter cho mọi traffic.

**Tại sao hữu ích:**
Global limit có thể khiến một tenant nhiều traffic làm các tenant khác bị throttle. Ngược lại, chỉ partition theo IP có thể không phù hợp khi nhiều user đi qua NAT hoặc traffic được phân phối qua nhiều địa chỉ.

**Ví dụ:**
Một B2B API có thể partition theo `TenantId` cho expensive search endpoint, trong khi anonymous endpoint dùng policy riêng. Telemetry nên ghi policy và partition category để biết request bị reject vì giới hạn nào.

**Lưu ý:**
Rate limiting không thay thế authorization, quota/billing hay traffic protection ở edge. Nếu key có cardinality không giới hạn hoặc limiter state không được quản lý phù hợp, chính cơ chế bảo vệ có thể tạo memory/operational cost.

### Tip 3 — Elasticsearch mapping phải được quyết định trước khi dữ liệu lớn lên

**Mẹo:**
Xác định rõ field nào là `text`, field nào là `keyword`, analyzer nào phục vụ search và field nào thực sự cần index trước khi ingest khối lượng lớn dữ liệu.

**Tại sao hữu ích:**
Mapping ảnh hưởng trực tiếp đến tokenization, sorting, aggregation và storage. Một product name cần full-text search thường dùng `text`, nhưng exact filter/aggregation có thể cần `keyword` subfield. Chọn sai mapping thường không thể sửa in-place đơn giản cho dữ liệu đã index.

**Ví dụ:**
Nếu `productName` đang được index chỉ như `keyword`, search theo token trong tên sẽ không có semantics mong muốn. Cách sửa production thường là tạo index mới với mapping đúng, reindex dữ liệu rồi chuyển alias sang index mới thay vì chỉnh tùy tiện index hiện tại.

**Lưu ý:**
Dynamic mapping tiện lúc prototype nhưng có thể gây mapping explosion khi document chứa field names động. Không index mọi field “để sau này tìm”; index design phải bám query patterns và retention/storage cost thực tế.

### Tip 4 — Playwright nên chờ trạng thái người dùng quan sát được, không dùng sleep cố định

**Mẹo:**
Trong end-to-end test, chờ locator, URL, response hoặc UI state cụ thể thay vì `WaitForTimeout` với một số mili giây cố định.

**Tại sao hữu ích:**
Sleep 2 giây có thể vừa làm test chậm trên máy nhanh vừa flaky trên CI chậm. Auto-waiting của Playwright và assertion có retry giúp test đồng bộ với trạng thái thực tế thay vì đoán thời gian hệ thống cần.

**Ví dụ:**
Sau khi submit checkout, dùng assertion như `await expect(page.getByText("Order confirmed")).toBeVisible()` thay vì `await page.waitForTimeout(2000)`. Nếu cần kiểm chứng API call quan trọng, bắt đầu `waitForResponse` trước action gây request để tránh race.

**Lưu ý:**
Đừng biến mọi network request thành synchronization point; analytics hoặc polling background có thể khiến test phụ thuộc implementation detail. Chờ observable behavior gần với contract mà user thực sự cần.

### Tip 5 — Managed Identity giảm secret rotation nhưng không giảm yêu cầu least privilege

**Mẹo:**
Trên Azure, ưu tiên Managed Identity cho App Service, Functions hoặc workload phù hợp khi truy cập Key Vault và Azure resources thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Application lấy token qua Azure identity platform mà không phải sở hữu một credential tĩnh cần phân phối và rotate. Điều này loại bỏ một lớp credential-management failure phổ biến trong deployment pipeline.

**Ví dụ:**
ASP.NET Core production dùng `DefaultAzureCredential` để truy cập Key Vault bằng Managed Identity; local developer có thể authenticate qua development credential phù hợp. Production identity chỉ được cấp quyền đọc đúng resources application cần.

**Lưu ý:**
Managed Identity không tự làm access an toàn. Gán role quá rộng vẫn vi phạm least privilege. Cũng cần phân biệt system-assigned và user-assigned identity theo lifecycle/ownership thay vì chọn tùy tiện.

## 🧠 Software Design

### Design 1 — API backward compatibility là một constraint thiết kế, không phải việc sửa sau khi client vỡ

**Khái niệm:**
Một API contract đã được consumer sử dụng trở thành boundary cần tiến hóa có chủ đích. Thay đổi additive thường dễ tương thích hơn thay đổi tên/xóa field, đổi type hoặc thay semantics của field hiện có.

**Vấn đề nó giải quyết:**
Mobile app phiên bản cũ có thể tồn tại hàng tháng ngoài production control của backend team. Nếu backend đổi `status` từ string sang object trong một deployment, client cũ có thể fail ngay dù server mới và web client mới hoạt động đúng.

**Ví dụ thực tế:**
Thay vì đổi trực tiếp response contract, team thêm field mới hoặc endpoint/version mới, duy trì contract cũ trong migration window và dùng telemetry xác định consumer nào còn gọi phiên bản cũ trước khi deprecate.

**Trade-off:**
Backward compatibility giảm coordinated deployment và outage risk nhưng kéo theo duplicated contract, mapping, test matrix và thời gian deprecation. Versioning quá sớm cho mọi thay đổi cũng tạo API surface khó quản lý; nhiều thay đổi additive không cần một version mới.

**Middle → Senior insight:**
Middle developer cần nhận ra breaking changes và giữ DTO contract tách khỏi persistence model. Senior / Technical developer phải định nghĩa compatibility policy, deprecation window, consumer observability và migration strategy dựa trên khả năng kiểm soát client thay vì áp dụng một versioning scheme máy móc.

### Design 2 — Saga xử lý distributed workflow bằng local transactions và compensation

**Khái niệm:**
Saga chia một business workflow qua nhiều service thành chuỗi local transactions. Khi bước sau thất bại, hệ thống thực hiện compensating actions hoặc chuyển workflow sang trạng thái cần xử lý thay vì kỳ vọng một ACID transaction bao phủ toàn bộ services.

**Vấn đề nó giải quyết:**
Checkout cần reserve inventory, authorize payment và tạo shipment. Nếu inventory đã reserve nhưng payment thất bại, không thể rollback database của Inventory bằng transaction của Checkout service.

**Ví dụ thực tế:**
Workflow thực hiện `ReserveInventory` → `AuthorizePayment` → `CreateShipment`. Nếu payment bị decline, compensation phát `ReleaseInventory`. Nếu compensation tạm thời thất bại, message được retry/idempotent và trạng thái saga cho phép operations thấy workflow đang chờ recovery.

**Trade-off:**
Saga tránh distributed transaction coordinator và cho phép services độc lập hơn, nhưng business phải chấp nhận intermediate states, duplicate delivery, compensation failure và observability phức tạp. Compensation cũng không luôn là “undo”; một số external side effect có thể không thể đảo ngược hoàn toàn.

**Middle → Senior insight:**
Middle developer cần implement handler idempotent và hiểu compensation semantics. Senior / Technical developer phải xác định orchestration hay choreography phù hợp, state ownership, timeout/recovery policy và những invariant nào thực sự có thể eventual-consistent thay vì dùng Saga chỉ vì hệ thống có nhiều services.

### Design 3 — Hexagonal Architecture có giá trị khi boundary thay đổi độc lập, không phải vì số lượng interface

**Khái niệm:**
Hexagonal Architecture đặt application/domain behavior ở trung tâm và giao tiếp với database, messaging, HTTP hoặc external providers qua ports/adapters. Giá trị chính là direction của dependency và khả năng thay đổi/test boundary, không phải tạo interface cho mọi class.

**Vấn đề nó giải quyết:**
Business workflow thanh toán có thể cần chạy với một provider hôm nay, một enterprise provider ngày mai và fake adapter trong integration tests. Nếu domain/application code phụ thuộc trực tiếp SDK/provider types, thay đổi integration lan vào business logic.

**Ví dụ thực tế:**
Application phụ thuộc `IPaymentGateway.Authorize(...)` mô tả capability mà business cần; adapter cụ thể chuyển capability đó sang SDK/API của provider. DTO, exception và retry semantics của provider không được rò rỉ tùy tiện vào domain model.

**Trade-off:**
Ports/adapters làm dependency rõ và tăng testability/evolution nhưng mỗi abstraction có chi phí naming, mapping và navigation. Với CRUD nội bộ đơn giản chỉ có một stable dependency, thêm nhiều layers/interfaces có thể tạo ceremony lớn hơn giá trị nhận được.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction đúng và không để infrastructure types xuyên boundary. Senior / Technical developer phải nhận diện boundary nào có volatility hoặc business significance đủ để đáng abstraction, đồng thời tránh “interface-per-class” và architecture layers không bảo vệ một thay đổi thực tế.
