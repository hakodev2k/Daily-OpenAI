# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Span<T>` khi xử lý buffer ngắn hạn để giảm allocation, không phải để “tối ưu mọi thứ”

**Mẹo:**
Trong hot path cần parse hoặc slice dữ liệu tạm thời, cân nhắc `Span<T>` / `ReadOnlySpan<T>` để thao tác trên vùng nhớ hiện có thay vì tạo `string`, array hoặc substring mới.

**Tại sao hữu ích:**
Các allocation nhỏ nhưng lặp lại với tần suất cao tạo áp lực lên Gen 0 GC. `Span<T>` cho phép tạo view trên memory mà không copy dữ liệu, nên hữu ích trong parser, protocol handling hoặc serialization path có throughput cao.

**Ví dụ:**
```csharp
ReadOnlySpan<char> input = "ORD-2026-000184";
var year = input.Slice(4, 4);
var id = input.Slice(9);
```

Không có `Substring()` nào được tạo chỉ để đọc hai đoạn dữ liệu này.

**Lưu ý:**
`Span<T>` là `ref struct`, không thể lưu tùy ý trên heap, capture vào async state machine hoặc field thông thường. Nếu code không nằm trong hot path hoặc allocation không đáng kể, `string`/array thường dễ đọc hơn.

### Tip 2 — Trong Elasticsearch, dùng `filter` cho điều kiện không cần relevance score

**Mẹo:**
Khi điều kiện chỉ xác định document có được giữ lại hay không, ví dụ `status`, `tenantId`, `price range`, đặt nó trong filter context thay vì query scoring context.

**Tại sao hữu ích:**
Filter không cần tính `_score` và phù hợp hơn cho exact-match/range constraint. Elasticsearch còn có thể tối ưu và cache một số filter hiệu quả hơn so với điều kiện tham gia scoring.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "wireless keyboard" } }
      ],
      "filter": [
        { "term": { "status": "active" } },
        { "range": { "price": { "lte": 100 } } }
      ]
    }
  }
}
```

`name` ảnh hưởng relevance; `status` và `price` chỉ lọc tập kết quả.

**Lưu ý:**
Đừng chuyển mọi điều kiện sang `filter`. Full-text search, boosting hoặc ranking logic vẫn cần query context để tính relevance.

### Tip 3 — Với integration test EF Core, ưu tiên database engine thật thay vì InMemory provider khi kiểm tra query behavior

**Mẹo:**
Nếu test cần xác nhận LINQ translation, constraint, transaction hoặc behavior của SQL Server/PostgreSQL, chạy integration test trên engine thật hoặc container tương ứng.

**Tại sao hữu ích:**
EF Core InMemory provider không thực thi SQL và có semantics khác relational provider. Một query có thể chạy tốt trên InMemory nhưng fail translation hoặc behave khác trên production database.

**Ví dụ:**
```text
Test cần kiểm tra:
- unique constraint
- case sensitivity
- transaction rollback
- SQL translation

=> dùng SQL Server/PostgreSQL test database
```

InMemory phù hợp hơn cho test đơn giản không phụ thuộc relational semantics.

**Lưu ý:**
Database test phải được cô lập và deterministic. Dùng schema/database riêng, transaction rollback hoặc reset strategy rõ ràng; nếu không test suite dễ flaky và chậm.

### Tip 4 — Khi Azure Function xử lý queue fail liên tục, theo dõi poison message thay vì chỉ tăng retry

**Mẹo:**
Với queue-triggered Azure Function, xác định retry policy và nơi message được đưa tới sau khi vượt retry limit. Poison message cần được tách để điều tra hoặc xử lý thủ công/automated recovery.

**Tại sao hữu ích:**
Một payload malformed hoặc vi phạm business rule có thể fail vĩnh viễn. Retry vô hạn chỉ tiêu tốn compute, làm nhiễu telemetry và có thể chặn throughput nếu ordering/concurrency bị ảnh hưởng.

**Ví dụ:**
```text
message received
-> process fail
-> retry N lần
-> vẫn fail
-> move to poison/dead-letter path
-> alert + inspect payload + decide recovery
```

**Lưu ý:**
Không coi mọi message vào poison path là dữ liệu xấu. Failure có thể do dependency outage kéo dài hoặc code regression; cần log correlation ID, exception category và attempt count để phân biệt.

### Tip 5 — Với technical SEO, canonical URL phải phản ánh URL authoritative chứ không phải URL hiện tại một cách máy móc

**Mẹo:**
Nếu cùng một nội dung có thể truy cập qua nhiều URL do query string, sorting hoặc tracking parameter, khai báo canonical URL về phiên bản authoritative ổn định.

**Tại sao hữu ích:**
Search engine có thể thấy nhiều URL gần như trùng nội dung và phân tán ranking signal. Canonical giúp biểu đạt URL ưu tiên mà không cần redirect mọi biến thể.

**Ví dụ:**
```html
<link rel="canonical" href="https://example.com/products/laptop-123" />
```

Trong khi user có thể đang ở:
```text
/products/laptop-123?utm_source=email
```

**Lưu ý:**
Canonical chỉ là signal, không phải access-control hay redirect mechanism. Nếu một URL thực sự không nên tồn tại, dùng redirect hoặc routing rule phù hợp thay vì dựa vào canonical.

## 🧠 Software Design

### Design 1 — Bulkhead Pattern để cô lập failure giữa các dependency

**Khái niệm:**
Bulkhead Pattern giới hạn resource hoặc concurrency theo từng dependency/workload để failure ở một vùng không chiếm hết thread, connection hoặc capacity của toàn application.

**Vấn đề nó giải quyết:**
Nếu một external API chậm và mọi request đều dùng chung pool/concurrency không giới hạn, các call treo có thể tiêu hết resource rồi kéo theo các endpoint không liên quan cũng chậm theo.

**Ví dụ thực tế:**
```text
Payment API concurrency limit: 20
Search API concurrency limit: 50
Internal DB workload: pool riêng theo provider
```

Khi Payment API outage, request payment có thể queue/fail fast nhưng search endpoint vẫn còn capacity.

**Trade-off:**
Bulkhead giảm cascading failure và blast radius nhưng tạo thêm queue, rejection behavior và capacity tuning. Limit quá thấp làm throughput giảm ngay cả khi dependency khỏe.

**Middle → Senior insight:**
Middle developer cần hiểu vì sao shared resource pool có thể lan truyền failure. Senior / Technical developer phải xác định isolation boundary, concurrency budget và fallback dựa trên SLO, traffic pattern và dependency criticality thay vì chọn limit tùy ý.

### Design 2 — Strangler Fig Pattern cho migration legacy system theo từng lát chức năng

**Khái niệm:**
Strangler Fig Pattern thay thế legacy system dần dần bằng cách chuyển từng capability sang implementation mới, trong khi phần còn lại tiếp tục chạy trên hệ thống cũ.

**Vấn đề nó giải quyết:**
Big-bang rewrite tạo khoảng thời gian dài không mang business value và rủi ro cutover rất lớn. Legacy .NET Framework hoặc monolith lớn thường khó thay toàn bộ trong một release.

**Ví dụ thực tế:**
```text
/api/customers  -> legacy app
/api/orders     -> new ASP.NET Core service/module
/api/catalog    -> legacy app
```

Gateway/routing layer dần chuyển endpoint hoặc workflow sang implementation mới khi từng slice hoàn tất.

**Trade-off:**
Migration incremental giảm cutover risk và cho phép rollback theo slice, nhưng trong giai đoạn chuyển tiếp phải vận hành hai hệ thống, đồng bộ data/identity và quản lý contract giữa old/new world.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility và viết adapter rõ ràng. Senior / Technical developer phải chọn migration seam dựa trên business boundary, data ownership, deployment dependency và rollback path; không tách slice chỉ theo controller hoặc table nếu boundary đó không ổn định.

### Design 3 — Event schema evolution cần backward compatibility giống API contract

**Khái niệm:**
Event đã publish là contract giữa producer và nhiều consumer có lifecycle deploy độc lập. Thay đổi schema phải tính đến consumer cũ vẫn đang chạy hoặc replay event lịch sử.

**Vấn đề nó giải quyết:**
Nếu producer đổi tên/xóa field hoặc đổi semantics ngay lập tức, consumer chưa deploy có thể deserialize fail hoặc xử lý sai message. Với event lưu lâu trong broker/event store, incompatibility còn có thể xuất hiện khi replay.

**Ví dụ thực tế:**
Thay vì đổi trực tiếp:
```text
OrderPlaced.Total -> OrderPlaced.Amount
```

có thể thêm `Amount`, giữ `Total` trong migration window, cập nhật consumers rồi mới deprecate schema cũ.

**Trade-off:**
Backward-compatible evolution giảm coordination giữa teams nhưng làm payload tạm thời dư field và cần schema governance. Version event mạnh tay dễ hiểu hơn khi semantics thay đổi lớn nhưng tạo branching logic và migration/replay complexity.

**Middle → Senior insight:**
Middle developer cần coi event như public contract, không như DTO nội bộ. Senior / Technical developer phải thiết kế versioning, compatibility window, default behavior cho field thiếu, schema validation và replay strategy dựa trên ownership và retention policy.
