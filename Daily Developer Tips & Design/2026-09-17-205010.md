# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với một request đơn thuần chạy chậm

**Mẹo:**
Khi ASP.NET Core service có latency tăng mạnh dưới tải nhưng CPU chưa chắc đạt 100%, kiểm tra ThreadPool starvation trước khi chỉ tăng timeout. Đặc biệt rà soát sync-over-async như `.Result`, `.Wait()` và blocking I/O nằm trên request path.

**Tại sao hữu ích:**
Một request block worker thread có vẻ vô hại ở tải thấp. Khi concurrency tăng, nhiều worker cùng bị giữ lại; ThreadPool phải bổ sung thread dần dần, queue dài lên và cả những request vốn nhanh cũng bị chậm. Đây là failure mode mang tính hệ thống chứ không chỉ là một endpoint chậm.

**Ví dụ:**
```csharp
// Dễ gây starvation dưới tải
var profile = httpClient.GetFromJsonAsync<UserProfile>(url).Result;

// Giữ async xuyên suốt call chain
var profile = await httpClient.GetFromJsonAsync<UserProfile>(url, cancellationToken);
```

Khi điều tra, correlate request rate/latency với ThreadPool queue length, thread count và exception/timeout telemetry bằng `dotnet-counters`, tracing hoặc APM đang dùng.

**Lưu ý:**
Không phải mọi blocking đều sai; CPU-bound work hoặc thư viện synchronous có thể cần chiến lược riêng. `Task.Run()` trong ASP.NET Core cũng không tự biến blocking I/O thành scalable I/O.

### Tip 2 — `ExecuteUpdateAsync` của EF Core bỏ qua Change Tracker

**Mẹo:**
Dùng `ExecuteUpdateAsync`/`ExecuteDeleteAsync` khi cần set-based DML hiệu quả, nhưng phải nhớ chúng thực thi trực tiếp trên database và không đồng bộ các entity đang được track trong `DbContext`.

**Tại sao hữu ích:**
Bulk update qua SQL tránh load hàng nghìn entity và giảm round-trip/memory, nhưng nếu cùng context đã track entity liên quan, state trong memory có thể stale. Một `SaveChangesAsync()` phía sau thậm chí có thể ghi lại giá trị cũ hoặc tạo behavior khó đoán nếu developer tưởng tracker đã được cập nhật.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Status, OrderStatus.Expired), cancellationToken);
```

Với workflow có optimistic concurrency, đưa concurrency predicate cần thiết vào `Where` và kiểm tra số rows affected thay vì mặc định bulk API có semantics giống `SaveChanges`.

**Lưu ý:**
Đừng trộn tracked mutation và set-based mutation trong cùng unit of work nếu không có lý do rõ ràng. Nếu phải trộn, xác định transaction boundary và cách refresh/clear tracked state một cách chủ động.

### Tip 3 — MongoDB index phải khớp cả filter và sort của query nóng

**Mẹo:**
Khi MongoDB query có filter nhanh nhưng vẫn sort tốn CPU/memory, kiểm tra compound index theo access pattern thực tế thay vì chỉ tạo index cho từng field riêng lẻ.

**Tại sao hữu ích:**
Hai single-field indexes không mặc nhiên tương đương một compound index có thể phục vụ filter + sort. Query planner có thể vẫn phải scan nhiều documents hoặc thực hiện blocking sort, đặc biệt với feed/history endpoint có pagination liên tục.

**Ví dụ:**
```javascript
db.auditEvents.createIndex({ tenantId: 1, createdAt: -1 })

db.auditEvents.find({ tenantId: tenantId })
  .sort({ createdAt: -1 })
  .limit(100)
  .explain("executionStats")
```

Đọc `keysExamined`, `docsExamined`, winning plan và execution time trên dữ liệu có distribution gần production.

**Lưu ý:**
Compound index tăng write amplification, storage và maintenance cost. Thứ tự field phụ thuộc equality/range/sort pattern; không áp dụng một công thức index cố định cho mọi query.

### Tip 4 — Dùng HTTP ETag để ngăn lost update ở REST API

**Mẹo:**
Với resource có nhiều client cùng chỉnh sửa, cân nhắc expose `ETag` và yêu cầu `If-Match` cho update thay vì để request cuối cùng âm thầm ghi đè request trước.

**Tại sao hữu ích:**
Client A và B có thể cùng đọc version 7. A cập nhật thành version 8; nếu B gửi payload dựa trên version 7 mà server không kiểm tra precondition, thay đổi của A có thể bị mất. Optimistic concurrency ở HTTP boundary giúp contract thể hiện rõ conflict thay vì biến nó thành data corruption logic.

**Ví dụ:**
```http
GET /api/products/42
ETag: "v7"

PUT /api/products/42
If-Match: "v7"
```

Nếu resource hiện đã là `v8`, server có thể trả `412 Precondition Failed`; client phải reload/merge theo business rule.

**Lưu ý:**
ETag không tự giải quyết merge conflict. Cần xác định ETag đại diện cho version nào, canonicalization ra sao và update nào thực sự yêu cầu concurrency protection.

### Tip 5 — `git rerere` hữu ích khi phải resolve cùng conflict nhiều lần

**Mẹo:**
Trong branch dài hoặc workflow rebase/cherry-pick lặp lại, `git rerere` có thể ghi nhớ cách bạn đã resolve một conflict và tái áp dụng resolution khi cùng conflict xuất hiện lại.

**Tại sao hữu ích:**
Khi feature branch thường xuyên rebase lên `main`, developer có thể mất thời gian xử lý cùng một conflict ở project file, dependency registration hoặc generated metadata nhiều lần. `rerere` biến resolution đã kiểm chứng thành reusable local knowledge.

**Ví dụ:**
```bash
git config --global rerere.enabled true
git rerere status
git rerere diff
```

Sau khi Git tái áp dụng resolution, vẫn review diff và chạy tests trước khi tiếp tục rebase.

**Lưu ý:**
`rerere` không biết resolution cũ còn đúng về semantics hay không. Code xung quanh có thể đã thay đổi; coi auto-resolution là candidate cần review, không phải bằng chứng conflict đã được xử lý đúng.

## 🧠 Software Design

### Design 1 — Modular Monolith: boundary rõ trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia hệ thống thành các module có ownership, public contract và dependency direction rõ ràng. Mục tiêu là giảm coupling ở cấp business capability mà chưa nhận operational cost của distributed system.

**Vấn đề nó giải quyết:**
Một ASP.NET Core solution lớn thường xuống cấp thành “shared everything”: controller gọi repository của module khác, mọi project dùng chung entity và database tables, thay đổi nhỏ lan khắp codebase. Tách ngay thành microservices chỉ chuyển coupling đó qua network nếu boundary chưa được hiểu đúng.

**Ví dụ thực tế:**
`Ordering`, `Catalog` và `Billing` nằm trong cùng deployable application nhưng mỗi module expose application-level contract riêng. `Ordering` không truy cập trực tiếp `BillingDbContext`; interaction đi qua explicit interface/message boundary. Architecture tests có thể chặn dependency không hợp lệ.

**Trade-off:**
Deployment và local debugging đơn giản hơn microservices, transaction nội bộ cũng dễ hơn. Đổi lại, isolation không được infrastructure cưỡng chế mạnh như process/network boundary; team phải giữ discipline và có automated architecture checks.

**Middle → Senior insight:**
Middle developer cần tôn trọng module API và tránh shortcut xuyên boundary. Senior / Technical developer phải tìm boundary từ business capability, change cadence và data ownership; đồng thời thiết kế seam đủ tốt để module có thể tách ra sau này nếu scaling/organization thực sự yêu cầu.

### Design 2 — Transactional Outbox cho database state và integration event

**Khái niệm:**
Transactional Outbox ghi business change và message cần publish vào cùng local database transaction. Một background publisher sau đó đọc outbox và gửi message tới broker, giúp tránh dual-write giữa database và message bus.

**Vấn đề nó giải quyết:**
Nếu service commit `Order` rồi crash trước khi publish `OrderCreated`, downstream không bao giờ biết order tồn tại. Nếu publish trước rồi database rollback, downstream lại xử lý một event cho state chưa từng commit. Hai resource độc lập không tạo atomicity chỉ bằng `try/catch`.

**Ví dụ thực tế:**
Trong transaction của `CreateOrder`, service insert `Orders` và `OutboxMessages`. Worker publish các outbox rows chưa gửi, sau đó đánh dấu trạng thái. Consumer dùng message ID/idempotency key để chịu được delivery lặp.

**Trade-off:**
Outbox cải thiện reliability mà không cần distributed transaction, nhưng thêm table growth, publisher, retry/backoff, cleanup và observability. Delivery thường là at-least-once, vì vậy duplicate handling vẫn là yêu cầu thiết kế.

**Middle → Senior insight:**
Middle developer cần hiểu transaction boundary và viết consumer idempotent. Senior / Technical developer phải định nghĩa ordering requirement, retry/dead-letter policy, retention, schema evolution và reconciliation khi broker hoặc publisher lỗi kéo dài.

### Design 3 — CQRS chỉ nên tách nơi read/write model thực sự có lực kéo khác nhau

**Khái niệm:**
CQRS tách model/flow phục vụ command khỏi model/flow phục vụ query. Việc tách có thể chỉ ở code level trong cùng database, hoặc tiến xa tới read store riêng; nó không bắt buộc đồng nghĩa với event sourcing hay microservices.

**Vấn đề nó giải quyết:**
Một domain model tối ưu cho invariant và transactional write đôi khi rất tệ cho dashboard/search/read-heavy API cần denormalized projection. Ép cùng object model phục vụ cả hai phía tạo query phức tạp hoặc làm write model bị thiết kế theo nhu cầu presentation.

**Ví dụ thực tế:**
Checkout command dùng aggregate và transaction để bảo vệ invariant. Order-history endpoint đọc projection đã denormalize theo customer/time để pagination nhanh. Nếu read projection async, API phải chấp nhận và thể hiện rõ eventual consistency.

**Trade-off:**
CQRS cho phép tối ưu hai workload độc lập nhưng tăng số model, mapping, synchronization và debugging surface. Read store riêng còn tạo consistency lag, rebuild/replay concern và operational overhead.

**Middle → Senior insight:**
Middle developer cần phân biệt command semantics với CRUD endpoint và không duplicate model vô cớ. Senior / Technical developer phải chứng minh sự bất đối xứng read/write đủ lớn để trả complexity cost, chọn consistency model và xác định nơi CQRS kết thúc thay vì biến nó thành kiến trúc mặc định toàn hệ thống.
