# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `System.Text.Json` source generation giảm reflection cost khi serialization là hot path

**Mẹo:**
Với API có throughput cao hoặc môi trường cần trimming/AOT-friendly behavior, cân nhắc `System.Text.Json` source generation cho các contract ổn định thay vì luôn dựa vào runtime metadata discovery.

**Tại sao hữu ích:**
Serializer mặc định phải khám phá metadata của type ở runtime. Source-generated metadata chuyển một phần công việc đó sang compile time, có thể giảm startup/runtime overhead và làm dependency với reflection rõ ràng hơn, đặc biệt khi Native AOT hoặc trimming trở thành constraint.

**Ví dụ:**
Một ASP.NET Core API serialize cùng nhóm response DTO hàng triệu lần/ngày. Profiling cho thấy serialization chiếm CPU đáng kể; team tạo `JsonSerializerContext` cho các DTO hot path, benchmark lại allocation/CPU và chỉ giữ optimization nếu số liệu cải thiện có ý nghĩa.

**Lưu ý:**
Đừng source-generate mọi type chỉ vì API tồn tại. Contract động, custom converters và polymorphism cần kiểm tra compatibility; optimization này không cứu được payload quá lớn hoặc query/database bottleneck.

### Tip 2 — SQL window functions tránh nhiều round trips cho ranking và running aggregates

**Mẹo:**
Khi cần rank, running total hoặc chọn row theo nhóm, xem xét `ROW_NUMBER()`, `RANK()`, `SUM() OVER(...)` thay vì tải dữ liệu về application rồi group/sort bằng C#.

**Tại sao hữu ích:**
Database có thể thực hiện set-based computation gần dữ liệu và tránh transfer hàng nghìn rows chỉ để application tính toán lại. Window function cũng giữ từng row trong result thay vì collapse như `GROUP BY`.

**Ví dụ:**
Back-office cần lấy order mới nhất của mỗi customer. Dùng `ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY CreatedAt DESC, Id DESC)` rồi lọc `rn = 1`, sau đó kiểm tra execution plan và index hỗ trợ partition/order keys.

**Lưu ý:**
Window functions vẫn có thể sort lượng dữ liệu lớn và spill ra disk nếu memory grant/index không phù hợp. Đừng coi cú pháp set-based là mặc định nhanh; xem actual plan, logical reads và cardinality.

### Tip 3 — Cosmos DB consistency level là quyết định correctness lẫn latency/cost

**Mẹo:**
Chọn consistency level theo business invariant và read-after-write requirement thay vì mặc định yêu cầu consistency mạnh nhất cho toàn workload.

**Tại sao hữu ích:**
Consistency mạnh hơn có thể tăng coordination, latency hoặc giới hạn availability/throughput tùy topology. Nhiều workload như catalog, telemetry hoặc feed chấp nhận dữ liệu hơi cũ, trong khi workflow vừa ghi rồi phải đọc chính xác state mới có requirement khác.

**Ví dụ:**
Product catalog có thể chấp nhận bounded/stale reads trong một khoảng nhỏ, còn màn hình xác nhận vừa cập nhật customer preference cần semantics đọc phù hợp với session/user flow. Team ghi rõ freshness tolerance trước khi chọn account/request consistency.

**Lưu ý:**
Đừng dùng consistency yếu để che thiết kế partition/query kém. Cũng đừng giả định mọi read trong distributed system nhìn thấy write mới nhất; test failure/failover behavior và hiểu SDK/session token semantics.

### Tip 4 — Kubernetes rollout thành công không có nghĩa application đã sẵn sàng phục vụ traffic

**Mẹo:**
Tách rõ `startupProbe`, `readinessProbe` và `livenessProbe` theo failure semantics; readiness phải phản ánh instance có thể nhận traffic, không chỉ process còn sống.

**Tại sao hữu ích:**
Pod có thể chạy nhưng đang warm cache, apply initialization hoặc chưa kết nối dependency bắt buộc. Nếu readiness xanh quá sớm, Service gửi traffic vào instance chưa sẵn sàng; nếu liveness phụ thuộc dependency ngoài, outage downstream có thể gây restart storm.

**Ví dụ:**
ASP.NET Core container có startup probe cho thời gian khởi động dài, readiness kiểm tra capability tối thiểu để phục vụ request, còn liveness chỉ phát hiện process/app bị kẹt không thể tự hồi phục. Theo dõi rollout cùng 5xx và pod restart count.

**Lưu ý:**
Health endpoint không nên chạy query nặng mỗi vài giây. Optional dependency không nhất thiết làm readiness fail; quyết định phải bám vào degradation contract của service.

### Tip 5 — CMS content model nên tối ưu cho editor intent, không mirror database schema

**Mẹo:**
Khi thiết kế Optimizely CMS hoặc headless CMS, model content theo ý nghĩa biên tập và khả năng tái sử dụng thay vì tạo content type tương ứng từng table/domain entity của backend.

**Tại sao hữu ích:**
Editor cần cấu trúc phản ánh page, campaign, hero, promotion và reusable block. Mirror database schema làm authoring khó hiểu, coupling CMS với persistence model và khiến thay đổi backend kéo theo migration content không cần thiết.

**Ví dụ:**
Một `ProductHeroBlock` chứa heading, media, CTA và presentation options; product price/inventory vẫn lấy từ commerce service qua identifier. CMS sở hữu editorial content, commerce system sở hữu transactional product state.

**Lưu ý:**
Đừng nhét dữ liệu volatile như inventory hoặc live price vào CMS chỉ để editor nhìn thấy mọi thứ một chỗ. Xác định source of truth và cache/invalidation boundary rõ ràng.

## 🧠 Software Design

### Design 1 — BFF chỉ đáng dùng khi consumer có nhu cầu composition khác biệt

**Khái niệm:**
Backend for Frontend (BFF) tạo backend boundary theo một loại client để composition, authentication flow hoặc payload shape phù hợp với client đó, thay vì bắt mọi client dùng cùng một generic aggregation API.

**Vấn đề nó giải quyết:**
Mobile có bandwidth/interaction pattern khác web; web SSR có thể cần composition khác native app. Nếu client phải gọi nhiều services và tự hiểu topology nội bộ, coupling và chatty traffic tăng.

**Ví dụ thực tế:**
Mobile BFF trả một compact home payload từ catalog, promotion và profile services, trong khi web BFF hỗ trợ SSR-specific composition. Core business rules vẫn nằm trong domain services, không copy sang từng BFF.

**Trade-off:**
BFF giảm client coupling và tối ưu trải nghiệm nhưng thêm deployment, observability và nguy cơ duplicate logic giữa BFFs. Nếu clients có nhu cầu gần giống nhau, một API đơn giản có thể tốt hơn.

**Middle → Senior insight:**
Middle developer cần giữ BFF ở orchestration/presentation boundary và tránh nhét domain logic vào đó. Senior / Technical developer phải chứng minh consumer divergence đủ lớn để trả chi phí vận hành thêm một backend boundary.

### Design 2 — Lease cần fencing token khi stale owner vẫn có thể tiếp tục ghi

**Khái niệm:**
Distributed lease/lock có expiry không đảm bảo owner cũ lập tức dừng khi lease hết hạn. Fencing token là số phiên tăng dần được resource downstream dùng để từ chối operation từ owner có token cũ.

**Vấn đề nó giải quyết:**
Worker A giữ lease rồi bị GC pause/network partition. Lease hết hạn và Worker B nhận lease mới, nhưng A tỉnh lại và tiếp tục ghi. Nếu downstream chỉ tin rằng A từng có lock, hai owners có thể cùng tạo side effect.

**Ví dụ thực tế:**
Scheduler cấp token 41 cho worker A; sau expiry, worker B nhận token 42. Storage/update path lưu token mới nhất và từ chối write mang token 41, nên stale worker không thể ghi đè state sau khi mất ownership.

**Trade-off:**
Fencing tăng correctness nhưng yêu cầu downstream resource tham gia protocol và so sánh token atomically. Với job idempotent hoặc single-process scope, complexity này có thể không đáng.

**Middle → Senior insight:**
Middle developer cần hiểu lock timeout không đồng nghĩa code cũ đã dừng. Senior / Technical developer phải phân tích pause/partition failure mode và quyết định khi nào idempotency, unique constraint, lease hay fencing mới là primitive đúng.

### Design 3 — Expand-and-Contract cho schema change qua nhiều phiên bản application

**Khái niệm:**
Expand-and-Contract thay breaking schema migration bằng các bước tương thích: mở rộng schema trước, chạy code hỗ trợ cả cũ/mới, migrate/backfill dữ liệu, chuyển readers/writers rồi mới xóa cấu trúc cũ.

**Vấn đề nó giải quyết:**
Rolling deployment khiến version cũ và mới cùng chạy. Rename/drop column trực tiếp có thể làm một nửa fleet lỗi ngay cả khi migration và application version mới đều đúng khi chạy riêng lẻ.

**Ví dụ thực tế:**
Cần đổi `Customer.Name` thành `DisplayName`: thêm column mới trước, deploy code có compatibility strategy, backfill/verify dữ liệu, chuyển read path, rồi ở release sau mới ngừng ghi và cuối cùng drop column cũ.

**Trade-off:**
Cách này giảm deployment risk và hỗ trợ rollback nhưng kéo dài migration, tạo temporary duplication và cần telemetry để biết khi nào contract phase an toàn. Với hệ thống nhỏ có maintenance window thật sự, migration trực tiếp có thể đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần viết code tương thích với transitional schema. Senior / Technical developer phải thiết kế sequence, rollback point, backfill load, data verification và tiêu chí xóa legacy state theo deployment topology thực tế.
