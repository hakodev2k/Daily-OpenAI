# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `ValueTask` như `Task` mặc định

**Mẹo:**
Chỉ cân nhắc `ValueTask` khi profiling cho thấy một async API thường xuyên hoàn thành đồng bộ và allocation của `Task` thực sự đáng kể trên hot path. Với phần lớn application code, `Task` vẫn là lựa chọn mặc định dễ dùng và an toàn hơn.

**Tại sao hữu ích:**
`ValueTask` có thể tránh allocation trong một số trường hợp, nhưng semantics phức tạp hơn: một instance không nên được await nhiều lần tùy nguồn, không nên cache tùy tiện và dễ bị misuse khi truyền qua nhiều layer. Tối ưu sai chỗ có thể làm code khó bảo trì hơn lợi ích performance nhận được.

**Ví dụ:**
Một cache lookup nội bộ có tỷ lệ hit rất cao có thể là ứng viên:
```csharp
public ValueTask<Product?> GetAsync(string id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out var product))
        return ValueTask.FromResult<Product?>(product);

    return new ValueTask<Product?>(LoadFromDatabaseAsync(id, ct));
}
```

**Lưu ý:**
Không đổi hàng loạt `Task` sang `ValueTask` chỉ để giảm allocation theo lý thuyết. Đo allocation/throughput trước, đặc biệt vì API public dùng `ValueTask` làm tăng cognitive cost cho mọi caller.

### Tip 2 — Dùng `AsSplitQuery` khi nhiều collection `Include` tạo cartesian explosion

**Mẹo:**
Khi EF Core query `Include` nhiều collection và SQL trả số row lớn bất thường, kiểm tra cartesian explosion; khi phù hợp, dùng projection hoặc `AsSplitQuery` thay vì cố giữ một query khổng lồ.

**Tại sao hữu ích:**
Nếu một `Order` có 20 `Lines` và 10 `Adjustments`, join cả hai collection trong một SQL result có thể tạo tới 200 row lặp dữ liệu của cùng order. Network payload, materialization và memory tăng dù số entity thực không lớn.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Adjustments)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == id, ct);
```

Hoặc tốt hơn, nếu chỉ cần DTO cho API, projection trực tiếp đúng field thường rẻ hơn cả `Include`.

**Lưu ý:**
Split query tạo nhiều round trip và consistency giữa các query có thể khác nếu dữ liệu thay đổi giữa chừng. Không bật toàn cục theo phản xạ; đo SQL, row count và latency theo query shape thực tế.

### Tip 3 — Xử lý JWT validation theo issuer/audience/key lifecycle, không chỉ signature

**Mẹo:**
Khi validate JWT trong ASP.NET Core, coi `issuer`, `audience`, expiry và signing key rotation là các phần bắt buộc của trust boundary; đừng chỉ kiểm tra token có chữ ký hợp lệ.

**Tại sao hữu ích:**
Một token có signature đúng vẫn có thể được phát cho application khác hoặc bởi issuer không được service của bạn tin cậy. Sai `audience`/`issuer` là lỗi authorization boundary, không phải chi tiết cấu hình nhỏ.

**Ví dụ:**
Một API nội bộ chỉ nên chấp nhận token thỏa:
```text
iss = https://login.example.com/tenant-a
 aud = api://orders
 exp > now
 signing key thuộc metadata hiện hành
```

Khi identity provider rotate key, middleware cần lấy metadata/JWKS theo cơ chế hỗ trợ rotation thay vì hard-code một certificate mãi mãi.

**Lưu ý:**
Không đặt clock skew quá lớn để “fix” lỗi token hết hạn. Nếu nhiều máy lệch giờ, sửa time synchronization; skew lớn mở rộng cửa sổ chấp nhận token không mong muốn.

### Tip 4 — Với IIS reverse proxy, kiểm tra forwarded headers trước khi debug redirect loop

**Mẹo:**
Nếu ASP.NET Core chạy sau IIS/reverse proxy và production bị redirect HTTP↔HTTPS, callback URL sai hoặc scheme luôn là `http`, kiểm tra cấu hình forwarded headers trước khi sửa routing/authentication logic.

**Tại sao hữu ích:**
TLS có thể terminate ở proxy, nên request tới Kestrel nhìn như HTTP dù client dùng HTTPS. Nếu application không tin đúng `X-Forwarded-Proto`/host từ proxy, URL generation và HTTPS redirection có thể sai.

**Ví dụ:**
Flow thực tế:
```text
Browser --HTTPS--> IIS / proxy --HTTP--> Kestrel
```

Application cần xử lý forwarded headers từ proxy đáng tin cậy để `Request.Scheme` phản ánh request bên ngoài.

**Lưu ý:**
Không blindly trust forwarded headers từ mọi nguồn vì attacker có thể spoof host/scheme/IP. Chỉ trust known proxy/network theo deployment topology.

### Tip 5 — Với AI-generated tests, kiểm tra test có bảo vệ behavior hay chỉ mirror implementation

**Mẹo:**
Khi AI coding agent sinh unit tests, review assertion theo contract/business behavior thay vì số lượng test hoặc coverage tăng. Test tốt phải fail khi behavior quan trọng bị phá, không chỉ xác nhận code hiện tại đang làm đúng theo chính implementation đó.

**Tại sao hữu ích:**
AI thường dễ sinh test bám sát method internals, mock mọi dependency và assert từng lời gọi. Các test này có thể pass sau refactor sai hoặc fail vô ích khi implementation đổi nhưng behavior vẫn đúng.

**Ví dụ:**
Ít giá trị:
```text
assert repository.SaveAsync được gọi đúng 1 lần
```

Có giá trị hơn:
```text
Given payment đã completed
When retry cùng command
Then không charge lần hai và response vẫn nhất quán
```

**Lưu ý:**
Coverage cao không chứng minh test suite mạnh. Với logic quan trọng, cân nhắc mutation testing hoặc intentionally break rule để kiểm tra test có bắt được regression thật hay không.

## 🧠 Software Design

### Design 1 — Materialized View / Read Model vs Runtime Aggregation

**Khái niệm:**
Runtime aggregation tính toán kết quả trực tiếp từ transactional tables mỗi request; materialized view/read model precompute một phần dữ liệu để read path nhanh và ổn định hơn.

**Vấn đề nó giải quyết:**
Dashboard có thể cần join hàng triệu Orders, Payments và Customers rồi aggregate theo ngày trên mỗi request. Query đúng về mặt SQL nhưng latency/cost tăng theo data volume và cạnh tranh tài nguyên với transactional workload.

**Ví dụ thực tế:**
```text
Transactional source:
Orders + Payments + Customers

Read model:
DailyRevenueByTenant
- Date
- TenantId
- Revenue
- OrderCount
```

Read model được update theo batch/event và dashboard chỉ đọc tập dữ liệu đã chuẩn bị.

**Trade-off:**
Runtime aggregation giữ dữ liệu luôn gần source-of-truth và ít sync logic hơn nhưng có thể tốn CPU/I/O cao. Precompute giảm latency và cô lập read workload nhưng thêm freshness lag, rebuild/backfill và synchronization complexity.

**Middle → Senior insight:**
Middle developer cần đọc execution plan và tối ưu query/index trước khi tạo read model mới. Senior / Technical developer phải xác định freshness SLA, update mechanism, rebuild strategy và chi phí vận hành để biết khi nào denormalized read model thực sự đáng giá.

### Design 2 — Strangler Fig cho migration `.NET Framework` sang modern .NET

**Khái niệm:**
Strangler Fig migration thay hệ thống legacy theo từng capability: traffic/chức năng mới dần chuyển sang component modern, trong khi phần cũ vẫn chạy cho tới khi bị thay thế hoàn toàn.

**Vấn đề nó giải quyết:**
Rewrite toàn bộ một enterprise application `.NET Framework` trong một lần có blast radius lớn, thời gian dài không tạo business value và rất khó giữ parity với production behavior đang thay đổi.

**Ví dụ thực tế:**
```text
Legacy ASP.NET MVC / .NET Framework
        |
        +-- /reports --------> giữ legacy
        +-- /orders/v2 ------> ASP.NET Core .NET 10
        +-- /notifications --> service/worker mới
```

Gateway/routing hoặc application boundary chuyển từng flow sang implementation mới, kèm telemetry để so behavior trước khi retire legacy path.

**Trade-off:**
Incremental migration giảm release risk và tạo value sớm, nhưng phải duy trì hai stack, contract compatibility, duplicated infrastructure và đôi khi data synchronization trong giai đoạn chuyển tiếp.

**Middle → Senior insight:**
Middle developer cần tách dependency và contract để một capability có thể migrate độc lập. Senior / Technical developer phải chọn seam migration theo business boundary, data ownership, rollback strategy và team capacity—không chỉ theo controller/project structure hiện có.

### Design 3 — Mutation Testing vs Code Coverage cho critical business rules

**Khái niệm:**
Code coverage cho biết test đã chạy qua dòng/nhánh nào; mutation testing cố tình thay đổi code nhỏ như đảo điều kiện hoặc đổi toán tử để kiểm tra test có thực sự phát hiện behavior sai hay không.

**Vấn đề nó giải quyết:**
Một module có thể đạt 95% coverage nhưng assertion yếu đến mức nhiều bug logic vẫn lọt qua. Coverage đo execution, không đo strength của expectation.

**Ví dụ thực tế:**
Business rule:
```csharp
if (amount > creditLimit)
    reject();
```

Mutation tool đổi thành:
```csharp
if (amount >= creditLimit)
```

Nếu test suite vẫn xanh, boundary condition chưa được bảo vệ đủ tốt.

**Trade-off:**
Mutation testing cho signal chất lượng test mạnh hơn nhưng chạy tốn CPU/thời gian và có thể tạo mutant tương đương khó phân loại. Không phù hợp để chạy toàn solution trên mọi commit nếu codebase lớn.

**Middle → Senior insight:**
Middle developer cần viết assertion dựa trên behavior và boundary cases. Senior / Technical developer phải chọn module/rule có risk cao để áp mutation testing, cân bằng confidence với pipeline cost thay vì biến mutation score thành KPI mới.
