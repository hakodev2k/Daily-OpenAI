# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` để tạo backpressure thay vì spawn task vô hạn

**Mẹo:**
Khi producer tạo work nhanh hơn consumer xử lý được, cân nhắc `System.Threading.Channels` với bounded capacity thay vì cứ `Task.Run` cho từng item.

**Tại sao hữu ích:**
Spawn task không giới hạn làm queue ngầm chuyển thành memory, ThreadPool và connection pressure. Bounded `Channel<T>` tạo backpressure rõ ràng: producer phải chờ khi consumer chưa theo kịp, nhờ đó workload ổn định hơn dưới burst traffic.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait
});

await channel.Writer.WriteAsync(job, cancellationToken);
```

Consumer đọc bằng `ReadAllAsync(cancellationToken)` và xử lý với concurrency có kiểm soát.

**Lưu ý:**
`Channel<T>` là in-memory. Nếu process restart mà job không được phép mất, cần durable queue như Azure Service Bus hoặc storage-backed mechanism thay vì coi `Channel<T>` là message broker.

### Tip 2 — Với EF Core, projection trước khi `Include` khi endpoint chỉ cần DTO

**Mẹo:**
Nếu endpoint chỉ trả một subset field, ưu tiên projection bằng `Select` trực tiếp sang DTO thay vì `Include` toàn bộ entity graph rồi map sau.

**Tại sao hữu ích:**
`Include` có thể kéo nhiều column và row hơn cần thiết, tăng network payload, materialization cost và memory. Projection cho EF Core cơ hội generate SQL đúng với shape response, giảm work cả ở database lẫn application.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.CreatedAt,
        x.Total,
        x.Customer.Name))
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Projection không tự động giải quyết mọi performance issue. Với query phức tạp vẫn cần xem generated SQL và execution plan; tránh projection chứa expression khiến query translation trở nên đắt hoặc không phù hợp.

### Tip 3 — Khi Redis bị hot key, scale-out cache chưa chắc giải quyết được

**Mẹo:**
Nếu một key nhận phần lớn traffic, đo command rate và latency theo key pattern trước khi chỉ tăng số node Redis.

**Tại sao hữu ích:**
Redis cluster phân phối key theo shard, nhưng một hot key vẫn tập trung lên một shard duy nhất. Thêm shard có thể làm tổng capacity tăng mà bottleneck của key nóng gần như không đổi.

**Ví dụ:**
Một homepage cache key:
```text
homepage:global
```

nhận 40% request toàn hệ thống. Giải pháp có thể là local in-process cache ngắn hạn, CDN, request coalescing hoặc tách representation nếu semantics cho phép.

**Lưu ý:**
Không shard một key thành nhiều bản sao nếu consistency requirement không cho phép hoặc invalidation trở nên phức tạp hơn lợi ích đạt được. Luôn dựa trên traffic distribution thực tế.

### Tip 4 — Dùng browser DevTools để đọc network waterfall trước khi blame backend

**Mẹo:**
Khi web page chậm, xem network waterfall, TTFB, resource size, dependency chain và blocking JavaScript trước khi kết luận API là bottleneck.

**Tại sao hữu ích:**
Một page có backend response nhanh vẫn có thể chậm vì bundle lớn, font/image blocking, serial request hoặc cache miss. Waterfall giúp phân biệt server latency với browser execution và delivery cost.

**Ví dụ:**
Nếu API TTFB chỉ 120 ms nhưng page mất 4 giây để interactive, waterfall có thể cho thấy 2 MB JavaScript tải nối tiếp và một third-party script block main thread.

**Lưu ý:**
Không tối ưu theo một lần reload duy nhất. So sánh cold cache, warm cache, throttled network và production build; DevTools mở có thể thay đổi một số timing.

### Tip 5 — Dùng `git reflog` để cứu commit tưởng đã mất sau reset/rebase

**Mẹo:**
Khi local branch bị `reset --hard`, rebase sai hoặc force-move, kiểm tra `git reflog` trước khi cho rằng commit đã biến mất.

**Tại sao hữu ích:**
Reflog lưu lịch sử di chuyển của local refs/HEAD trong một khoảng thời gian, nên commit không còn reachable từ branch hiện tại vẫn thường có thể khôi phục bằng SHA.

**Ví dụ:**
```bash
git reflog

git checkout -b rescue <commit-sha>
```

Sau đó review lại history rồi mới merge/cherry-pick phần cần giữ.

**Lưu ý:**
Reflog là local và không phải backup vĩnh viễn. Nếu repository bị xóa hoặc garbage collection loại object cũ, reflog không đảm bảo cứu được dữ liệu. Với work quan trọng vẫn cần push/backup đúng quy trình.

## 🧠 Software Design

### Design 1 — Synchronous call vs asynchronous messaging theo coupling và failure mode

**Khái niệm:**
Synchronous integration phù hợp khi caller cần kết quả ngay và dependency có latency/reliability phù hợp. Messaging phù hợp khi workflow có thể tách thời gian xử lý, cần buffering hoặc muốn giảm temporal coupling.

**Vấn đề nó giải quyết:**
Nếu service A phải chờ B, C và D trong cùng request, một dependency chậm có thể kéo toàn bộ request chain xuống. Nhưng chuyển tất cả sang messaging lại tạo eventual consistency và operational complexity không cần thiết.

**Ví dụ thực tế:**
Checkout cần xác nhận giá hiện tại trước khi trả kết quả có thể cần synchronous Pricing call. Gửi email xác nhận sau checkout phù hợp hơn với message vì user không cần chờ email gửi xong.

**Trade-off:**
Synchronous flow đơn giản và dễ reason nhưng dễ bị cascading latency/failure. Messaging tăng resilience và decoupling theo thời gian nhưng thêm broker, retry, duplicate delivery, observability và consistency concern.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry và idempotency của từng kiểu integration. Senior / Technical developer phải phân loại operation theo business latency, ownership, failure tolerance và consistency requirement thay vì chọn REST hoặc messaging theo xu hướng.

### Design 2 — CQRS chỉ đáng dùng khi read/write thực sự có pressure khác nhau

**Khái niệm:**
CQRS tách model/flow đọc và ghi khi hai phía có nhu cầu khác biệt đáng kể về shape, performance, scaling hoặc domain behavior. Nó không bắt buộc đồng nghĩa với Event Sourcing hay microservices.

**Vấn đề nó giải quyết:**
Một model duy nhất đôi khi bị kéo theo hai hướng: write side cần invariant/domain logic chặt, trong khi read side cần query denormalized rất nhanh cho dashboard/search.

**Ví dụ thực tế:**
Order write model giữ aggregate và invariant thanh toán. Dashboard operations có thể dùng read model projection tối ưu cho filter/sort mà không ép aggregate phục vụ mọi query.

**Trade-off:**
CQRS cho phép tối ưu độc lập và boundary rõ hơn, nhưng thêm duplicate model, synchronization và eventual consistency nếu read model được cập nhật async. Với CRUD app nhỏ, chi phí này thường không đáng.

**Middle → Senior insight:**
Middle developer cần hiểu command/query responsibility và tránh leak write model sang mọi read case. Senior / Technical developer phải chứng minh pressure đủ lớn để tách, chọn mức CQRS tối thiểu cần thiết và kiểm soát consistency/operational cost.

### Design 3 — Managed Identity vs application secret cho Azure resource access

**Khái niệm:**
Managed Identity cho workload lấy token từ Azure identity platform mà không cần nhúng client secret trong configuration. Secret-based credential vẫn có chỗ dùng nhưng tạo lifecycle rotation và exposure risk lớn hơn.

**Vấn đề nó giải quyết:**
Connection string hoặc client secret lưu trong app settings, pipeline variable hay file cấu hình có thể bị leak qua log, backup hoặc quyền truy cập sai. Managed Identity chuyển trust sang identity + RBAC của workload.

**Ví dụ thực tế:**
ASP.NET Core App Service đọc Azure Blob Storage bằng Managed Identity và cấp role tối thiểu trên đúng storage account/container thay vì lưu account key trong configuration.

**Trade-off:**
Managed Identity giảm secret management và hỗ trợ least privilege tốt hơn, nhưng phụ thuộc Azure identity/RBAC setup và có thể làm local development khác production. Secret credential đôi khi cần cho external system không hỗ trợ federated identity nhưng phải có rotation và secure storage.

**Middle → Senior insight:**
Middle developer cần biết cấu hình identity, credential chain và quyền tối thiểu. Senior / Technical developer phải thiết kế identity boundary, blast radius, local/dev strategy, RBAC ownership và migration khỏi long-lived secrets thay vì chỉ đổi SDK call.
