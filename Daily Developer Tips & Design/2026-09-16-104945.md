# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure cho background pipeline

**Mẹo:**
Khi producer có thể tạo work nhanh hơn consumer xử lý, ưu tiên bounded `Channel<T>` thay vì một queue tăng vô hạn trong memory.

**Tại sao hữu ích:**
`Channel.CreateBounded<T>` buộc hệ thống thể hiện overload thay vì âm thầm tích hàng trăm nghìn item. Với `BoundedChannelFullMode.Wait`, producer phải chờ khi buffer đầy, tạo backpressure và giúp giới hạn memory footprint.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, cancellationToken);
```
Một `BackgroundService` có thể đọc từ `channel.Reader.ReadAllAsync(stoppingToken)` và xử lý theo tốc độ downstream chịu được.

**Lưu ý:**
In-memory `Channel<T>` không phải durable queue. Nếu process restart mà work không được phép mất, dùng broker như Azure Service Bus hoặc lưu work bền vững trước khi enqueue.

### Tip 2 — Idempotency key phải gắn với request semantics, không chỉ lưu response

**Mẹo:**
Với API tạo payment/order có thể bị client retry, lưu `Idempotency-Key` cùng fingerprint của request và kết quả xử lý.

**Tại sao hữu ích:**
Network timeout không cho client biết server đã commit hay chưa. Retry cùng operation có thể tạo duplicate. Mapping key → request fingerprint → result giúp server trả lại kết quả cũ cho cùng request và từ chối việc tái sử dụng key cho payload khác.

**Ví dụ:**
```text
POST /payments
Idempotency-Key: 9b5f...

Store:
key       = 9b5f...
request   = SHA256(customerId + orderId + amount)
status    = Completed
paymentId = pay_123
```
Retry cùng key và fingerprint trả `pay_123`; cùng key nhưng amount khác phải bị reject thay vì vô tình trả kết quả không tương ứng.

**Lưu ý:**
Đừng chỉ dùng distributed lock ngắn hạn: lock hết hạn sau khi commit nhưng trước khi response đến vẫn có thể cho retry tạo duplicate. Cần persistence và transaction boundary phù hợp.

### Tip 3 — Đọc execution plan trước khi ép PostgreSQL dùng index

**Mẹo:**
Khi PostgreSQL chọn sequential scan dù có index, dùng `EXPLAIN (ANALYZE, BUFFERS)` để kiểm tra cardinality estimate và I/O thực tế trước khi thay index hoặc query.

**Tại sao hữu ích:**
Index scan không mặc định nhanh hơn. Nếu predicate trả phần lớn table, random heap access qua index có thể đắt hơn sequential scan. Statistics sai hoặc stale cũng có thể khiến optimizer ước lượng selectivity sai.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, created_at
FROM orders
WHERE status = 'Completed';
```
Nếu 85% rows là `Completed`, sequential scan có thể hoàn toàn hợp lý. Với predicate selective như `customer_id = ? AND created_at >= ?`, composite index phù hợp mới có khả năng giảm work đáng kể.

**Lưu ý:**
Không tắt `enable_seqscan` như một production fix. Hãy kiểm tra statistics, data distribution, query shape, index order và số rows thực tế trước.

### Tip 4 — Playwright nên chờ trạng thái người dùng thấy, không chờ thời gian cố định

**Mẹo:**
Trong E2E test, chờ locator hoặc assertion đạt trạng thái mong muốn thay vì `WaitForTimeout`.

**Tại sao hữu ích:**
Fixed delay vừa làm test chậm vừa flaky: CI chậm hơn máy local có thể chưa load xong sau 2 giây, còn khi hệ thống nhanh thì vẫn lãng phí đủ 2 giây. Playwright assertions có auto-retry phù hợp hơn với UI bất đồng bộ.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Saved successfully")).ToBeVisibleAsync();
```
Assertion mô tả observable behavior thay vì timing implementation detail.

**Lưu ý:**
Auto-wait không giải quyết mọi race condition. Nếu UI phụ thuộc background workflow dài, test vẫn cần một observable completion condition rõ ràng; đừng tăng global timeout để che lỗi synchronization.

### Tip 5 — Upload Blob trực tiếp bằng SAS có phạm vi hẹp thay vì proxy file lớn qua API

**Mẹo:**
Với upload lớn từ browser/mobile, cân nhắc backend cấp short-lived SAS chỉ cho blob/path cần thiết rồi client upload trực tiếp tới Azure Blob Storage.

**Tại sao hữu ích:**
Proxy toàn bộ bytes qua ASP.NET Core làm application chịu thêm bandwidth, connection duration và memory/buffering pressure. Direct upload tách data plane khỏi API; backend vẫn kiểm soát authorization và metadata workflow.

**Ví dụ:**
```text
Client -> API: request upload permission
API -> Client: short-lived write-only SAS
Client -> Blob Storage: upload bytes
Client -> API: confirm upload / create domain record
```
Trong Azure, backend nên dùng Managed Identity để truy cập storage và chỉ phát quyền tối thiểu cần thiết cho client.

**Lưu ý:**
SAS là credential. Giới hạn permission, resource, expiry và HTTPS; không log token. Direct upload cũng cần kiểm tra file type/size, malware workflow và xử lý orphan blob nếu client upload xong nhưng không hoàn tất business transaction.

## 🧠 Software Design

### Design 1 — Transactional Outbox

**Khái niệm:**
Outbox ghi business state và event cần publish vào cùng local database transaction. Một publisher riêng đọc Outbox và gửi event tới broker, thay vì cố commit database rồi publish message như hai thao tác không nguyên tử.

**Vấn đề nó giải quyết:**
Nếu `SaveChanges` thành công nhưng process chết trước khi gửi Service Bus message, dữ liệu đã đổi nhưng downstream không bao giờ biết. Nếu gửi message trước rồi database rollback, downstream lại thấy event cho state chưa tồn tại.

**Ví dụ thực tế:**
Order API tạo `Order` và `OrderCreated` Outbox row trong cùng transaction. Worker publish row đó lên Azure Service Bus rồi đánh dấu processed. Consumer vẫn phải idempotent vì publisher có thể crash sau publish nhưng trước khi đánh dấu processed.

**Trade-off:**
Lợi ích là loại bỏ dual-write gap giữa database và broker mà không cần distributed transaction. Chi phí là thêm Outbox table, publisher, cleanup, monitoring, eventual consistency và duplicate delivery handling.

**Middle → Senior insight:**
Middle developer cần implement atomic write, publisher retry và idempotent consumer đúng. Senior / Technical developer phải quyết định có thật sự cần Outbox hay không, xác định ordering/retention/throughput, failure recovery và observability; với workflow đơn giản không phát event sau transaction, Outbox chỉ tạo ceremony.

### Design 2 — API backward compatibility là một constraint thiết kế

**Khái niệm:**
Public/consumer-facing API contract phải tiến hóa sao cho client cũ tiếp tục hoạt động trong khoảng compatibility đã cam kết. Thiết kế không chỉ là URL versioning; nó bao gồm schema, semantics, validation, defaults và error behavior.

**Vấn đề nó giải quyết:**
Mobile app cũ hoặc third-party client không thể deploy đồng thời với backend. Một thay đổi tưởng nhỏ như đổi optional field thành required, rename enum value hoặc đổi ý nghĩa HTTP status có thể phá client đang chạy ngoài quyền kiểm soát của team.

**Ví dụ thực tế:**
Thay vì rename `customerName` thành `displayName` ngay lập tức, API có thể bổ sung field mới, giữ field cũ trong deprecation window và đo usage trước khi loại bỏ. Breaking redesign lớn có thể cần `/v2`, nhưng additive changes thường không cần tạo version mới.

**Trade-off:**
Compatibility giảm deployment coupling và rủi ro consumer breakage, nhưng kéo theo code/schema cũ, test matrix và deprecation cost. Versioning quá sớm lại khiến nhiều API generations phải vận hành song song.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking changes và giữ contract tests. Senior / Technical developer phải định nghĩa compatibility policy, consumer ownership, deprecation telemetry và chọn additive evolution, tolerant reader hay version mới dựa trên blast radius thực tế.

### Design 3 — Azure Functions vs Worker Service

**Khái niệm:**
Cả Azure Functions và .NET Worker Service đều xử lý background/asynchronous work, nhưng chúng có operational model khác nhau. Functions tối ưu cho trigger-driven serverless execution; Worker Service phù hợp khi cần process lâu dài với lifecycle và resource control rõ hơn.

**Vấn đề nó giải quyết:**
Team cần chọn execution host cho queue consumer, scheduled processing hoặc integration jobs mà không biến mọi background task thành Functions chỉ vì có trigger sẵn.

**Ví dụ thực tế:**
Một image metadata job ngắn, stateless, bursty từ queue có thể hợp với Azure Functions. Một pipeline giữ nhiều long-lived connections, cần kiểm soát concurrency tinh vi và chạy liên tục có thể dễ vận hành hơn bằng Worker Service trên App Service, Container Apps hoặc Kubernetes.

**Trade-off:**
Functions giảm infrastructure ceremony và scale theo trigger nhưng có hosting-plan constraints, cold-start/cost behavior và execution model cần hiểu. Worker Service cho lifecycle/control rõ hơn nhưng team phải chịu nhiều trách nhiệm deployment, scaling và health management hơn.

**Middle → Senior insight:**
Middle developer cần viết handler idempotent, xử lý cancellation/retry và poison message đúng trên host đã chọn. Senior / Technical developer phải so sánh workload duration, traffic shape, scaling, concurrency, cost, observability, deployment model và team operations trước khi chọn; serverless không tự động là kiến trúc tốt hơn.
