# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để loại bỏ `DateTime.UtcNow` khỏi logic cần test

**Mẹo:**
Trong .NET 8+, nếu business logic phụ thuộc vào thời gian hiện tại, inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` hoặc `DateTimeOffset.UtcNow` bên trong service.

**Tại sao hữu ích:**
Code phụ thuộc trực tiếp vào system clock làm unit test khó deterministic: test expiration, retry window, SLA deadline hoặc token timeout có thể phải `Task.Delay`, dễ flaky và chậm. `TimeProvider` biến thời gian thành dependency có thể kiểm soát được.

**Ví dụ:**
```csharp
public sealed class SubscriptionService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => expiresAt <= timeProvider.GetUtcNow();
}
```

Trong test có thể dùng `FakeTimeProvider` từ `Microsoft.Extensions.TimeProvider.Testing` để advance clock mà không phải chờ thời gian thật trôi qua.

**Lưu ý:**
Không cần biến mọi chỗ gọi thời gian thành abstraction riêng. `TimeProvider` có giá trị nhất khi time ảnh hưởng đến business behavior, timeout, scheduled logic hoặc test determinism. Đồng thời phải thống nhất UTC vs local time; abstraction tốt không sửa được timezone semantics sai.

### Tip 2 — Fail fast configuration bằng `ValidateOnStart` thay vì đợi request đầu tiên mới lỗi

**Mẹo:**
Với ASP.NET Core, các option quan trọng như connection endpoints, timeout, credential references hoặc feature-critical settings nên được validate lúc application start bằng Options validation và `ValidateOnStart()`.

**Tại sao hữu ích:**
Nếu config sai nhưng application vẫn start, deployment có thể được đánh dấu thành công rồi chỉ fail khi traffic chạm code path tương ứng. Fail fast giúp health/deployment pipeline phát hiện lỗi trước khi instance nhận traffic.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(o => Uri.TryCreate(o.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be an absolute URI")
    .Validate(o => o.TimeoutSeconds is > 0 and <= 60,
        "Payment timeout is invalid")
    .ValidateOnStart();
```

Có thể kết hợp DataAnnotations hoặc custom `IValidateOptions<T>` khi rule phức tạp hơn.

**Lưu ý:**
Không validate những dependency động bằng cách gọi network trực tiếp trong Options validation; việc đó có thể làm startup phụ thuộc vào hệ thống ngoài và gây outage dây chuyền. Validate syntax/required values ở startup, còn dependency readiness nên được phản ánh qua health check phù hợp.

### Tip 3 — Khi gặp SQL Server deadlock, đọc deadlock graph trước khi thêm retry

**Mẹo:**
Nếu production xuất hiện error `1205`, đừng chỉ thêm retry. Hãy lấy deadlock graph từ Extended Events hoặc telemetry để xác định transaction nào giữ resource gì và thứ tự lock gây cycle.

**Tại sao hữu ích:**
Retry chỉ che symptom và có thể làm tăng tải nếu root cause là transaction quá dài, access order không nhất quán hoặc missing index khiến nhiều row/page bị lock hơn cần thiết. Deadlock graph cho evidence về victim, lock mode, statement và resource đang tranh chấp.

**Ví dụ:**
```text
Transaction A:
1. UPDATE Orders ...
2. UPDATE Inventory ...

Transaction B:
1. UPDATE Inventory ...
2. UPDATE Orders ...

=> cùng resource nhưng access order ngược nhau
=> cycle lock
```

Một hướng sửa có thể là chuẩn hóa thứ tự update `Orders -> Inventory` ở cả hai flow, rút ngắn transaction hoặc cải thiện index để giảm phạm vi lock.

**Lưu ý:**
Retry vẫn hữu ích vì deadlock có thể xảy ra hợp lệ trong workload concurrent, nhưng chỉ nên là resilience layer sau khi hiểu nguyên nhân. Đừng dùng `NOLOCK` như “cách sửa deadlock” mặc định; nó đổi consistency semantics và có thể trả dữ liệu bẩn hoặc không ổn định.

### Tip 4 — Với Azure Service Bus, tune `PrefetchCount` theo processing time và lock duration

**Mẹo:**
Khi consumer Azure Service Bus xử lý message chậm, đừng tăng `PrefetchCount` quá cao chỉ để throughput đẹp hơn. Prefetched message đã được lock và lock timer vẫn chạy trong khi message đang chờ ở client buffer.

**Tại sao hữu ích:**
Nếu buffer nhận nhiều message hơn worker có thể xử lý trước khi lock hết hạn, message có thể bị redelivery dù process chưa thực sự lỗi. Kết quả là duplicate processing, lock-lost exception và backlog khó chẩn đoán.

**Ví dụ:**
```text
Average processing time: 5s
ConcurrentCalls: 8
Lock duration: 60s

Prefetch = 500
=> nhiều message chờ trong memory lâu hơn lock window
=> lock expire trước khi tới lượt xử lý
```

Bắt đầu với prefetch vừa phải, đo throughput, `MessageLockLostException`, processing latency và active-message age rồi mới tăng.

**Lưu ý:**
Auto lock renewal giúp các message đang được xử lý lâu, nhưng không phải lý do để buffer vô hạn. Nếu handler thường mất vài phút, xem lại granularity của message/work item và cách chia processing thay vì chỉ kéo dài lock.

### Tip 5 — Hủy request frontend cũ bằng `AbortController` để tránh stale response ghi đè state mới

**Mẹo:**
Trong Vue/React/TypeScript, khi user thay đổi search/filter nhanh và mỗi thay đổi tạo HTTP request mới, hãy cancel request cũ bằng `AbortController` hoặc cơ chế cancellation tương đương.

**Tại sao hữu ích:**
HTTP response không đảm bảo trả về theo đúng thứ tự request. Query `abc` có thể hoàn thành sau query `abcd` và ghi đè UI bằng dữ liệu cũ dù request `abcd` mới hơn.

**Ví dụ:**
```ts
let controller: AbortController | undefined

async function search(query: string) {
  controller?.abort()
  controller = new AbortController()

  const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  })

  return await response.json()
}
```

Trong component lifecycle cũng nên abort khi unmount nếu response không còn consumer.

**Lưu ý:**
Cancellation phía client không đảm bảo server đã dừng toàn bộ work; backend cũng phải propagate cancellation tới EF Core, `HttpClient` hoặc downstream operation nếu framework hỗ trợ. Với operation có side effect, đừng giả định user đóng tab nghĩa là business transaction phải bị rollback.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read và write thực sự có nhu cầu khác nhau

**Khái niệm:**
CQRS tách model/flow đọc và ghi để mỗi phía tối ưu cho mục tiêu riêng. Điều đó không đồng nghĩa mọi hệ thống cần hai database, event sourcing hoặc một framework mediator phức tạp.

**Vấn đề nó giải quyết:**
Một domain có write model giàu invariant nhưng read side cần projection rất khác, nhiều aggregation hoặc scale độc lập. Nếu ép cả hai dùng cùng một model, query trở nên khó tối ưu và domain model bị biến dạng chỉ để phục vụ UI/reporting.

**Ví dụ thực tế:**
```text
Order write model:
- enforce inventory reservation
- payment state transition
- cancellation rules

Order history read model:
- customer name
- shipment status
- payment summary
- search/filter/sort theo nhiều field
```

Có thể bắt đầu đơn giản: command dùng domain/EF Core, query dùng projection SQL/Dapper/EF Core riêng nhưng vẫn chung database.

**Trade-off:**
CQRS giúp model rõ hơn và cho phép read/write evolve độc lập, nhưng tăng số abstraction, mapping, code path và consistency concern. Nếu CRUD đơn giản và read/write shape gần giống nhau, tách CQRS có thể chỉ tăng ceremony mà không tạo giá trị.

**Middle → Senior insight:**
Middle developer cần hiểu command không nên trả về một object graph khổng lồ chỉ vì UI cần đọc. Senior / Technical developer phải đánh giá divergence của workload, consistency requirement, team complexity và vận hành trước khi quyết định CQRS ở mức code, database hay service boundary.

### Design 2 — Feature flag tách deployment khỏi release nhưng không thay thế architecture tốt

**Khái niệm:**
Feature flag cho phép code được deploy nhưng behavior mới chỉ bật cho một nhóm user, tenant hoặc thời điểm cụ thể. Nhờ đó deployment và business release có thể diễn ra độc lập.

**Vấn đề nó giải quyết:**
Một thay đổi lớn có thể cần rolling deployment, gradual rollout hoặc validation với internal users trước khi mở toàn bộ traffic. Nếu code chỉ có trạng thái “deploy = bật”, rollback duy nhất là redeploy binary cũ.

**Ví dụ thực tế:**
```text
Deploy version mới tới 100% instances
Feature NewCheckout = off

Bật theo rollout:
- internal users
- 5% tenants
- 25%
- 100%

Nếu error rate tăng:
-> disable flag
-> không cần rollback binary ngay
```

Flag cũng có thể dùng để chuyển dần giữa old/new implementation trong cùng release.

**Trade-off:**
Feature flag giảm release risk nhưng tạo nhiều execution path và test matrix. Flag tồn tại quá lâu trở thành technical debt, đặc biệt khi nested flags làm behavior khó reasoning. Security hoặc permission không nên được thay thế bằng flag phía client.

**Middle → Senior insight:**
Middle developer cần viết code sao cho cả trạng thái on/off đều hoạt động và có test tương ứng. Senior / Technical developer phải thiết kế ownership, rollout metric, kill-switch behavior, cleanup date và phân biệt release flag, ops flag, experiment flag với authorization policy.

### Design 3 — Multi-tenant storage: shared schema, schema-per-tenant hay database-per-tenant

**Khái niệm:**
Kiến trúc multi-tenant cần chọn mức isolation dữ liệu phù hợp: tất cả tenant dùng chung table với `TenantId`, tách schema, hoặc tách database. Đây là quyết định về isolation, scale và operations chứ không chỉ là database naming.

**Vấn đề nó giải quyết:**
Một SaaS cần cân bằng giữa chi phí thấp, query đơn giản, tenant isolation, backup/restore riêng, data residency và khả năng xử lý “noisy tenant”. Một mô hình duy nhất hiếm khi tối ưu cho mọi tiêu chí.

**Ví dụ thực tế:**
```text
Shared schema
Orders(TenantId, OrderId, ...)
+ chi phí thấp, vận hành đơn giản
- mọi query phải enforce tenant filter

Database-per-tenant
TenantA_DB
TenantB_DB
+ isolation / restore riêng tốt hơn
- provisioning, migrations, connection management phức tạp hơn
```

Hệ thống lớn đôi khi dùng hybrid: tenant nhỏ ở shared database, tenant enterprise hoặc regulated workload ở database riêng.

**Trade-off:**
Shared schema tối ưu resource utilization nhưng làm authorization/data-leak risk nghiêm trọng hơn nếu tenant filter bị bỏ sót. Database-per-tenant tăng isolation nhưng tăng operational overhead, schema rollout và cost. Schema-per-tenant nằm giữa nhưng không phải lúc nào tooling/cloud service cũng hỗ trợ thuận tiện.

**Middle → Senior insight:**
Middle developer cần luôn coi `TenantId` là security boundary và test query/filter cẩn thận. Senior / Technical developer phải quyết định isolation model dựa trên compliance, backup/restore, scale distribution, migration strategy, connection limits và cost; không chọn database-per-tenant chỉ vì “an toàn hơn” nếu vận hành không chịu nổi.
