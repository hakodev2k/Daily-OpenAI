# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — `IAsyncDisposable` cho resource cần cleanup bất đồng bộ

**Mẹo:**
Khi cleanup thực sự cần I/O async, dùng `IAsyncDisposable` và `await using` thay vì ép operation bất đồng bộ chạy đồng bộ trong `Dispose()`.

**Tại sao hữu ích:**
Cleanup như flush network stream hoặc hoàn tất async protocol có thể block ThreadPool nếu bị chuyển thành `.GetAwaiter().GetResult()`. `await using` cho phép compiler gọi `DisposeAsync()` và await đúng lifecycle.

**Ví dụ:**
```csharp
await using var stream = await OpenRemoteStreamAsync(cancellationToken);
await stream.WriteAsync(payload, cancellationToken);
```
Nếu class sở hữu cả synchronous và asynchronous resources, thiết kế dispose pattern rõ ownership thay vì để caller đoán cách cleanup.

**Lưu ý:**
Không implement `IAsyncDisposable` chỉ vì class có method async. Chỉ cần nó khi cleanup cần async work; đồng thời tránh double-dispose hoặc ownership mơ hồ với resource được inject từ bên ngoài.

### Tip 2 — HTTP conditional GET giảm payload bằng `ETag`

**Mẹo:**
Với resource đọc nhiều nhưng ít thay đổi, cân nhắc trả `ETag` và xử lý `If-None-Match` để client có thể nhận `304 Not Modified` thay vì tải lại representation đầy đủ.

**Tại sao hữu ích:**
Browser/mobile client vẫn revalidate freshness nhưng tránh serialization, bandwidth và payload transfer khi version resource không đổi. Đây là HTTP semantics chuẩn, thường tốt hơn tự phát minh query parameter kiểu `?version=...`.

**Ví dụ:**
```text
GET /api/catalog/42
ETag: "catalog-42-v18"

GET /api/catalog/42
If-None-Match: "catalog-42-v18"

HTTP/1.1 304 Not Modified
```
ETag nên phản ánh representation/version mà endpoint thực sự trả.

**Lưu ý:**
Đừng nhầm conditional GET với optimistic concurrency cho write. Với update, `If-Match` có semantics khác. Cũng cần phối hợp `Cache-Control`, CDN/proxy và authorization để tránh cache dữ liệu riêng tư sai scope.

### Tip 3 — Cosmos DB query rẻ bắt đầu từ partition key

**Mẹo:**
Thiết kế query path để cung cấp partition key khi có thể; đừng chỉ tối ưu LINQ hoặc projection rồi bỏ qua data distribution.

**Tại sao hữu ích:**
Point read với `id` + partition key có thể route trực tiếp tới logical partition, trong khi cross-partition query phải fan out và tiêu thụ RU cao hơn. Với Cosmos DB, partition design thường quyết định performance/cost nhiều hơn micro-optimization trong application.

**Ví dụ:**
```csharp
var response = await container.ReadItemAsync<Order>(
    orderId,
    new PartitionKey(customerId),
    cancellationToken: cancellationToken);
```
Nếu API luôn đọc order theo customer, `customerId` có thể là candidate partition key tốt hơn một field không xuất hiện trong access pattern.

**Lưu ý:**
Partition key chỉ dựa trên query hiện tại có thể tạo hot partition hoặc giới hạn scale sau này. Cần đánh giá cardinality, write distribution, growth và các query quan trọng khác trước khi chốt model.

### Tip 4 — Kubernetes `requests` và `limits` ảnh hưởng runtime khác nhau

**Mẹo:**
Khi container .NET chậm hoặc restart, kiểm tra CPU/memory usage cùng `requests`, `limits`, throttling và OOM events; đừng chỉ nhìn utilization percentage.

**Tại sao hữu ích:**
CPU limit có thể gây throttling mà process không crash, tạo latency cao dù node còn CPU. Memory limit bị vượt có thể khiến container bị OOMKilled. `requests` lại ảnh hưởng scheduling và resource guarantee, không phải hard ceiling giống limit.

**Ví dụ:**
```text
Symptom: p99 tăng mạnh, CPU graph ~100% limit
Evidence: container_cpu_cfs_throttled_* tăng
Hypothesis: CPU throttling
Diagnosis: CPU limit quá thấp so với burst workload
```
Sau đó mới cân nhắc tối ưu code, điều chỉnh resource hoặc scale.

**Lưu ý:**
Xóa toàn bộ limits không phải fix mặc định. Resource policy cần dựa trên profiling/load test và cluster capacity; memory leak vẫn là memory leak dù tăng limit.

### Tip 5 — AI-generated migration cần verify bằng schema diff và dữ liệu thật

**Mẹo:**
Khi dùng AI coding agent tạo EF Core migration hoặc SQL migration, review generated operations, SQL và rollback/data-transition strategy trước khi chạy production.

**Tại sao hữu ích:**
AI có thể tạo migration compile được nhưng rename thành drop+add, đặt default sai, khóa bảng lớn hoặc giả định database version không đúng. Sai migration có blast radius lớn hơn một lỗi application thông thường vì nó thay đổi persistent state.

**Ví dụ:**
```text
AI đề xuất:
DROP COLUMN CustomerName;
ADD FirstName ...;
ADD LastName ...;

Review cần hỏi:
- dữ liệu cũ migrate thế nào?
- old application version còn chạy không?
- operation có lock/rewrite table lớn không?
- rollback có làm mất dữ liệu không?
```
Test migration trên production-like data volume và inspect generated SQL.

**Lưu ý:**
Passing unit tests không chứng minh migration an toàn. Migration cần đánh giá compatibility, execution time, locking, backup/recovery và deployment sequence.

## 🧠 Software Design

### Design 1 — `DbContext` trực tiếp vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp unit-of-work/change-tracking/query abstractions. Repository riêng chỉ có giá trị khi nó tạo boundary có ý nghĩa cho domain/application, không phải khi chỉ bọc lại từng method của EF Core.

**Vấn đề nó giải quyết:**
Team muốn tách application khỏi data-access details, nhưng generic repository kiểu `GetAll`, `Add`, `Update` thường che mất `IQueryable`, transaction semantics và EF features mà không giảm coupling thực tế.

**Ví dụ thực tế:**
Một CRUD admin module có thể inject `AppDbContext` trực tiếp vào application handler. Một pricing domain phức tạp có thể dùng `IPriceBookRepository` với operation mang business meaning như `LoadActivePriceBookAsync`, giữ aggregate loading policy ở boundary rõ ràng.

**Trade-off:**
Direct `DbContext` giảm boilerplate và giữ full EF capability nhưng application phụ thuộc EF Core rõ hơn. Repository có thể cô lập persistence decisions và domain loading rules, nhưng generic wrapper dễ tạo abstraction rỗng, duplicate API và khó tối ưu query.

**Middle → Senior insight:**
Middle developer cần hiểu tracking, query translation và transaction boundary dù dùng abstraction nào. Senior / Technical developer phải hỏi abstraction đang che một volatile dependency/business concept thật hay chỉ thêm layer vì convention; testability không tự động yêu cầu repository.

### Design 2 — Queue vs Topic theo delivery topology

**Khái niệm:**
Queue thường biểu diễn một stream work được cạnh tranh bởi consumers; Topic + subscriptions biểu diễn publish/subscribe, nơi nhiều consumer groups độc lập có thể nhận cùng một message theo subscription của mình.

**Vấn đề nó giải quyết:**
Nếu `OrderPlaced` cần Email, Analytics và Loyalty xử lý độc lập, đưa cả ba consumer vào cùng một queue sẽ khiến message thường chỉ được một competing consumer xử lý thay vì fan-out tới ba capability.

**Ví dụ thực tế:**
`GenerateInvoice` command có thể vào queue dành cho Invoice workers. `OrderPlaced` event publish vào topic; Email, Analytics và Loyalty mỗi hệ thống có subscription riêng, retry/DLQ độc lập.

**Trade-off:**
Queue đơn giản hơn cho work distribution và backpressure của một capability. Topic hỗ trợ fan-out và consumer autonomy nhưng tăng subscription management, duplicate delivery, schema evolution và observability complexity.

**Middle → Senior insight:**
Middle developer cần hiểu PeekLock, retry, DLQ và idempotent processing. Senior / Technical developer phải phân biệt command với event, ownership của consumer, ordering scope, filtering và failure isolation trước khi chọn topology.

### Design 3 — SLO-driven alerting thay vì alert theo mọi metric spike

**Khái niệm:**
Alerting nên tập trung vào triệu chứng ảnh hưởng reliability/user outcome, thường gắn với SLI/SLO như availability hoặc latency, thay vì page team mỗi khi CPU hoặc memory vượt một ngưỡng ngắn hạn.

**Vấn đề nó giải quyết:**
CPU 90% có thể hoàn toàn bình thường khi autoscaling hoạt động và requests vẫn đạt latency target. Ngược lại, dependency timeout có thể phá checkout trong khi CPU thấp. Infrastructure metric không luôn tương đương user impact.

**Ví dụ thực tế:**
Checkout có SLO 99.9% successful requests và p95 dưới 800 ms. Alert ưu tiên error-budget burn hoặc sustained latency breach; CPU saturation, queue depth và DB waits là diagnostic signals để điều tra nguyên nhân sau khi symptom được phát hiện.

**Trade-off:**
SLO-based alerting giảm noise và tập trung on-call vào impact thật, nhưng đòi hỏi định nghĩa SLI đúng, telemetry đáng tin cậy và stakeholder thống nhất mục tiêu. Infrastructure alerts vẫn cần cho một số failure sắp xảy ra như disk exhaustion.

**Middle → Senior insight:**
Middle developer cần instrument status/latency đúng và biết đọc dashboard. Senior / Technical developer phải chọn SLI phản ánh user journey, thiết kế burn-rate windows, phân biệt page-worthy với ticket-worthy signal và dùng resource metrics như evidence thay vì mặc định coi chúng là incident.
