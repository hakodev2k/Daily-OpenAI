# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Propagate `CancellationToken` tới dependency thay vì chỉ kiểm tra ở controller

**Mẹo:**
Trong ASP.NET Core, nếu client đã disconnect hoặc request bị timeout, hãy truyền `CancellationToken` xuyên qua application layer tới EF Core, `HttpClient`, Azure SDK và các thao tác I/O hỗ trợ cancellation thay vì chỉ nhận token ở endpoint rồi bỏ đó.

**Tại sao hữu ích:**
Cancellation chỉ có giá trị khi operation đang chiếm tài nguyên thực sự có thể dừng. Nếu controller bị cancel nhưng query database hoặc outbound HTTP vẫn chạy, request đã vô nghĩa vẫn tiếp tục giữ connection, CPU và memory. Dưới tải cao, những operation “mồ côi” này có thể làm connection pool cạn hoặc khuếch đại incident.

**Ví dụ:**
```csharp
app.MapGet("/api/orders/{id:int}", async (
    int id,
    AppDbContext db,
    HttpClient client,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (order is null)
        return Results.NotFound();

    using var response = await client.GetAsync(
        $"pricing/{order.ProductId}",
        cancellationToken);

    return Results.Ok(order);
});
```

**Lưu ý:**
Không catch `OperationCanceledException` rồi log như application error thông thường. Cancellation do client disconnect hoặc timeout đã dự kiến cần được phân biệt với lỗi thật để tránh alert noise.

### Tip 2 — Dùng partitioned rate limiting theo client/tenant thay vì một global bucket cho mọi request

**Mẹo:**
Khi API phục vụ nhiều tenant hoặc API consumer, dùng partitioned rate limiter theo identity phù hợp như tenant, API key hoặc user thay vì một giới hạn toàn cục nếu mục tiêu là ngăn một consumer làm ảnh hưởng tất cả consumer khác.

**Tại sao hữu ích:**
Global limiter bảo vệ tổng capacity nhưng không tạo fairness. Một tenant có burst traffic lớn có thể chiếm toàn bộ quota và khiến tenant bình thường nhận `429`. Partitioning biến rate limit thành một cơ chế isolation thay vì chỉ là một traffic gate.

**Ví dụ:**
```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
    {
        var tenant = ctx.User.FindFirst("tenant_id")?.Value ?? "anonymous";

        return RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: tenant,
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 100,
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0
            });
    });
});
```

**Lưu ý:**
Partition key phải có cardinality và trust boundary hợp lý. Không dùng raw header do client tự đặt làm partition identity nếu chưa được xác thực; attacker có thể đổi key liên tục để né limit.

### Tip 3 — Khi gặp deadlock SQL Server, đọc deadlock graph trước khi tăng timeout hoặc thêm retry

**Mẹo:**
Nếu production xuất hiện deadlock, lấy deadlock graph từ Extended Events hoặc monitoring tool rồi xác định transaction nào giữ lock, transaction nào chờ lock, access order và index/path liên quan trước khi sửa code.

**Tại sao hữu ích:**
Deadlock không đơn giản là “query chạy lâu”. Nó là chu trình phụ thuộc lock: transaction A chờ resource B giữ, trong khi B lại chờ resource A giữ. Tăng command timeout không phá được chu trình này; retry chỉ giúp request có cơ hội chạy lại nhưng không loại bỏ nguyên nhân.

**Ví dụ:**
Hai transaction cập nhật cùng hai bảng theo thứ tự ngược nhau:

```text
Transaction A: UPDATE Orders -> UPDATE Inventory
Transaction B: UPDATE Inventory -> UPDATE Orders
```

Chuẩn hóa access order thành cùng thứ tự có thể loại bỏ một lớp deadlock mà không cần tăng isolation hay lock hint.

**Lưu ý:**
Không thêm `NOLOCK` hoặc lock hint ngẫu nhiên để “hết deadlock”. Bạn có thể đổi deadlock thành dirty read, lost consistency hoặc blocking dạng khác. Fix phải dựa trên lock graph và business consistency requirement.

### Tip 4 — Dùng TTL jitter để tránh nhiều cache key hết hạn cùng một thời điểm

**Mẹo:**
Nếu nhiều key Redis được populate cùng lúc với cùng TTL cố định, thêm một khoảng jitter ngẫu nhiên nhỏ vào expiration để tránh synchronized expiration tạo burst xuống database.

**Tại sao hữu ích:**
Ngay cả khi mỗi key không đủ “hot” để tạo cache stampede riêng, hàng nghìn key cùng hết hạn lúc 10:00:00 có thể làm miss ratio tăng đột biến và tạo traffic spike xuống source of truth. Jitter phân tán expiration theo thời gian.

**Ví dụ:**
```csharp
var baseTtl = TimeSpan.FromMinutes(10);
var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 90));
await cache.SetStringAsync(key, payload, new DistributedCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = baseTtl + jitter
});
```

**Lưu ý:**
Jitter không thay thế chiến lược cache invalidation đúng. Với dữ liệu cần freshness chính xác, expiration ngẫu nhiên quá lớn có thể làm stale window khó kiểm soát.

### Tip 5 — Với AI coding agent, yêu cầu evidence từ source và test thay vì chấp nhận patch “trông hợp lý”

**Mẹo:**
Khi dùng AI-assisted development, buộc workflow kiểm tra implementation hiện tại, API signature thật, test hiện có và compiler/build output trước khi chấp nhận code được sinh ra.

**Tại sao hữu ích:**
AI có thể tạo API không tồn tại, giả định sai lifecycle, bỏ qua edge case hoặc thêm abstraction không phù hợp kiến trúc repo. Code compile được cũng chưa chắc đúng behavior. Grounding vào source và verification bằng test giảm đáng kể lỗi “plausible but wrong”.

**Ví dụ:**
Thay vì yêu cầu:
```text
Implement retry for this API client.
```

hãy yêu cầu agent:
```text
Inspect the current client registration, existing resilience packages,
HTTP semantics and tests. Reuse the repository's established pattern.
Add or update tests that prove timeout, retry boundaries and non-retryable cases.
Run the relevant test suite and report failures.
```

**Lưu ý:**
Không biến verification thành việc yêu cầu agent tạo thêm nhiều layer hoặc test giả chỉ để “pass”. Test phải kiểm tra observable behavior và phù hợp risk của thay đổi.

## 🧠 Software Design

### Design 1 — Outbox Pattern để giữ database commit và event publication nhất quán

**Khái niệm:**
Outbox Pattern lưu business change và message/event cần publish vào cùng một local database transaction. Một background publisher sau đó đọc outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application commit database rồi publish message bằng hai bước độc lập, có hai failure window nguy hiểm:

1. Database commit thành công nhưng publish thất bại → downstream không biết thay đổi.
2. Publish thành công nhưng database rollback → downstream nhận event cho state không tồn tại.

Outbox loại bỏ dual-write giữa database và broker khỏi request transaction.

**Ví dụ thực tế:**
Khi Order chuyển sang `Paid`, transaction ghi đồng thời:

```text
Orders
- Id = 42
- Status = Paid

OutboxMessages
- Id = 9fd...
- Type = OrderPaid
- Payload = {...}
- ProcessedAt = null
```

Worker publish `OrderPaid` lên Azure Service Bus rồi đánh dấu outbox record đã xử lý.

**Trade-off:**
Outbox tăng consistency và recovery khả năng cao hơn, nhưng tạo thêm table, polling/change-feed mechanism, cleanup policy, monitoring và duplicate delivery. Consumer vẫn cần idempotency vì publisher có thể crash sau khi send nhưng trước khi mark processed.

**Middle → Senior insight:**
Middle developer cần đảm bảo business state và outbox record cùng transaction, publisher retry an toàn và có index phù hợp. Senior / Technical developer phải quyết định polling interval, ordering requirement, cleanup/retention, operational visibility và liệu hệ thống có thực sự có dual-write problem đủ lớn để cần pattern này.

### Design 2 — Feature Flag không phải là configuration lâu dài; phải có lifecycle và removal plan

**Khái niệm:**
Feature Flag tách thời điểm deploy code khỏi thời điểm enable behavior. Code mới có thể tồn tại production nhưng chỉ bật cho internal user, một tenant, một percentage traffic hoặc sau khi dependency sẵn sàng.

**Vấn đề nó giải quyết:**
Nếu deployment đồng nghĩa activation ngay lập tức, rollout có blast radius lớn và rollback thường phải redeploy. Feature flag cho phép progressive delivery và nhanh chóng disable behavior mới khi metrics xấu.

**Ví dụ thực tế:**
Một checkout flow mới được deploy cho toàn bộ App Service nhưng rollout theo stage:

```text
Internal users -> 5% traffic -> 25% -> 100%
```

Mỗi stage theo dõi error rate, conversion, dependency latency và business invariant trước khi tăng exposure.

**Trade-off:**
Feature flags giảm release risk nhưng tạo state-space lớn: old path/new path có thể cùng tồn tại, test matrix tăng và stale flags biến codebase thành maze. Flag evaluation còn có thể trở thành runtime dependency nếu thiết kế kém.

**Middle → Senior insight:**
Middle developer cần giữ hai branch behavior testable và tránh side effect lệch nhau ngoài ý muốn. Senior / Technical developer phải định nghĩa owner, expiration date, observability, kill-switch semantics và bắt buộc xóa flag khi rollout hoàn tất để tránh permanent complexity.

### Design 3 — Bounded Context là boundary nghiệp vụ trước khi là boundary deployment

**Khái niệm:**
Trong Domain-Driven Design, Bounded Context xác định nơi một domain model và ngôn ngữ có nghĩa nhất quán. Nó không bắt buộc mỗi context phải trở thành một microservice riêng.

**Vấn đề nó giải quyết:**
Các hệ thống lớn thường dùng cùng từ nhưng khác nghĩa. `Customer` trong Billing có thể là account chịu thanh toán; trong Marketing có thể là lead/contact; trong Identity có thể là principal đăng nhập. Ép tất cả dùng một shared entity khổng lồ tạo coupling và thay đổi ở một module phá module khác.

**Ví dụ thực tế:**
Trong Modular Monolith:

```text
Modules/
  Identity/
  Catalog/
  Ordering/
  Billing/
```

Mỗi module sở hữu model và persistence boundary của mình, giao tiếp qua contract rõ ràng. Sau này chỉ module có scaling/ownership requirement thật sự mới cần tách deployment.

**Trade-off:**
Boundary rõ giúp cohesion cao và giảm shared-model coupling, nhưng có duplication hợp lý, mapping giữa context và eventual consistency ở một số flow. Boundary quá nhỏ lại làm hệ thống phân mảnh, nhiều contract và workflow cross-context không cần thiết.

**Middle → Senior insight:**
Middle developer cần tôn trọng ownership và không query thẳng table/module khác chỉ vì tiện. Senior / Technical developer phải tìm boundary từ business capability, change pattern, team ownership và consistency requirement; không bắt đầu bằng câu hỏi “chúng ta cần bao nhiêu microservice?”.
