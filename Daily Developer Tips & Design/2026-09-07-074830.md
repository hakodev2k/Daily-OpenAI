# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Kiểm soát connection lifetime của HttpClient thay vì chỉ tăng timeout

**Mẹo:**
Khi một outbound API lúc đầu hoạt động ổn nhưng sau một thời gian lại xuất hiện lỗi kết nối, DNS stale hoặc socket pressure, kiểm tra connection pooling trước khi chỉ tăng timeout. Với `IHttpClientFactory`, có thể cấu hình `SocketsHttpHandler.PooledConnectionLifetime` để buộc connection cũ được tái tạo định kỳ.

**Tại sao hữu ích:**
`HttpClient` tái sử dụng connection để giảm chi phí TCP/TLS handshake. Nhưng connection có thể sống lâu hơn thay đổi DNS của downstream. Nếu service phía sau load balancer thay IP mà connection pool giữ socket cũ quá lâu, application có thể tiếp tục gửi traffic tới endpoint không còn hợp lệ.

**Ví dụ:**
```csharp
builder.Services
    .AddHttpClient("catalog")
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)
    });
```

Khi production có intermittent failure, kiểm tra DNS resolution, connection reuse, dependency telemetry và socket state thay vì mặc định kết luận downstream “chậm”.

**Lưu ý:**
Không tạo `new HttpClient()` cho mỗi request. Cách đó có thể gây socket exhaustion và mất lợi ích của connection pooling.

### Tip 2 — Khi gặp deadlock SQL, đọc deadlock graph trước khi thêm retry

**Mẹo:**
Nếu SQL Server báo deadlock, thu thập deadlock graph để xác định transaction nào giữ lock nào và lock acquisition order ra sao. Retry chỉ nên là lớp resilience cuối cùng, không phải cách thay thế root-cause analysis.

**Tại sao hữu ích:**
Deadlock thường xuất hiện khi hai transaction truy cập tài nguyên theo thứ tự khác nhau. Nếu chỉ retry, hệ thống có thể “có vẻ ổn” ở tải thấp nhưng tiếp tục tạo contention và latency spike khi traffic tăng.

**Ví dụ:**
Transaction A:
```text
UPDATE Orders ...
UPDATE Inventory ...
```

Transaction B:
```text
UPDATE Inventory ...
UPDATE Orders ...
```

Một hướng sửa có thể là chuẩn hóa thứ tự lock acquisition, giảm transaction scope hoặc tối ưu query để khóa ít row hơn.

**Lưu ý:**
Không mặc định dùng isolation level thấp hơn để “chữa” deadlock. Điều đó có thể đổi consistency semantics của nghiệp vụ.

### Tip 3 — Trong Elasticsearch, tách full-text query khỏi exact filter

**Mẹo:**
Dùng `text` field cho full-text search và `keyword` field cho exact match, sorting, aggregation hoặc filter. Đừng dùng cùng một field theo cách mơ hồ nếu access pattern khác nhau.

**Tại sao hữu ích:**
`text` field thường được analyzer tokenization trước khi index. `keyword` giữ nguyên giá trị. Nếu dùng sai mapping, query có thể trả kết quả khó hiểu hoặc aggregation không hoạt động như kỳ vọng.

**Ví dụ:**
```json
{
  "name": {
    "type": "text",
    "fields": {
      "raw": { "type": "keyword" }
    }
  }
}
```

Full-text search dùng `name`; sorting hoặc filter chính xác dùng `name.raw`.

**Lưu ý:**
Mapping thay đổi có thể yêu cầu reindex. Đừng đợi đến khi index đã rất lớn mới kiểm tra access pattern và mapping strategy.

### Tip 4 — Chặn SSRF ở outbound integration bằng allowlist và URL validation có ngữ cảnh

**Mẹo:**
Nếu backend nhận URL từ user rồi tự fetch tài nguyên, coi đó là bề mặt SSRF. Hạn chế scheme, host, port và destination network; ưu tiên allowlist thay vì blacklist.

**Tại sao hữu ích:**
Một URL nhìn vô hại có thể resolve tới loopback, private network hoặc metadata endpoint. SSRF có thể biến server thành proxy để truy cập tài nguyên nội bộ mà attacker không thể gọi trực tiếp.

**Ví dụ:**
Cho phép chỉ:
```text
https://cdn.partner.example/*
```

Từ chối:
```text
http://127.0.0.1/
http://169.254.169.254/
http://internal-admin/
```

Với integration quan trọng, validate cả DNS resolution và destination policy thay vì chỉ kiểm tra chuỗi hostname.

**Lưu ý:**
Blacklist vài hostname phổ biến là chưa đủ. DNS rebinding, redirects và alternate IP formats có thể vượt qua validation yếu.

### Tip 5 — Dùng `git worktree` để xử lý hotfix mà không phá workspace hiện tại

**Mẹo:**
Khi đang làm feature dở nhưng cần chuyển sang hotfix gấp, dùng `git worktree` để checkout branch khác vào thư mục riêng thay vì stash/unstash liên tục.

**Tại sao hữu ích:**
`git worktree` cho phép nhiều working tree cùng trỏ tới một repository object database. Bạn giữ nguyên trạng thái feature hiện tại và mở một workspace sạch cho hotfix, review hoặc test branch khác.

**Ví dụ:**
```bash
git worktree add ../app-hotfix hotfix/payment-timeout
```

Sau khi xong:
```bash
git worktree remove ../app-hotfix
```

**Lưu ý:**
Không dùng cùng một branch trong hai worktree đồng thời. Đồng thời cần nhớ xóa worktree cũ để tránh metadata rác và nhầm workspace.

## 🧠 Software Design

### Design 1 — Saga cho workflow nhiều service thay vì distributed transaction mặc định

**Khái niệm:**
Saga chia một business workflow dài thành nhiều local transaction, mỗi bước có thể có compensating action nếu bước sau thất bại. Nó phù hợp khi một transaction ACID xuyên nhiều service không khả thi hoặc tạo coupling quá lớn.

**Vấn đề nó giải quyết:**
Trong hệ thống phân tán, một order flow có thể đi qua Payment, Inventory và Shipping. Nếu cố giữ một distributed transaction xuyên toàn bộ boundary, hệ thống khó scale, khó vận hành và phụ thuộc hạ tầng transaction coordinator.

**Ví dụ thực tế:**
1. Reserve inventory.
2. Capture payment.
3. Create shipment.

Nếu bước 3 thất bại sau khi payment thành công, Saga có thể chạy compensation như refund payment và release inventory.

**Trade-off:**
Saga cải thiện autonomy và phù hợp distributed systems, nhưng đổi ACID global transaction lấy eventual consistency, state-machine complexity, compensation logic và observability khó hơn.

**Middle → Senior insight:**
Middle developer cần hiểu mỗi local transaction và compensation phải idempotent. Senior / Technical developer phải quyết định bước nào thực sự cần compensation, bước nào có thể retry, workflow nào nên orchestration hay choreography, và business có chấp nhận trạng thái trung gian hay không.

### Design 2 — Hexagonal Architecture chỉ có giá trị khi boundary thực sự được bảo vệ

**Khái niệm:**
Hexagonal Architecture đặt business logic ở trung tâm và giao tiếp với database, HTTP, messaging hoặc file system thông qua ports/adapters. Giá trị nằm ở dependency direction và boundary, không nằm ở việc tạo nhiều project hay folder.

**Vấn đề nó giải quyết:**
Khi domain logic phụ thuộc trực tiếp EF Core, Azure SDK hoặc HTTP client, thay đổi infrastructure dễ lan vào business code và test logic thuần trở nên khó hơn.

**Ví dụ thực tế:**
Application core gọi `IPaymentGateway`. Adapter production triển khai bằng REST API của payment provider; test dùng fake implementation. Business rule không cần biết HTTP status code hay SDK cụ thể.

**Trade-off:**
Boundary rõ giúp testability và thay đổi integration dễ hơn, nhưng thêm interface, mapping và indirection. Với CRUD đơn giản, layered architecture trực tiếp có thể ít ceremony và dễ bảo trì hơn.

**Middle → Senior insight:**
Middle developer cần giữ infrastructure dependency không chảy ngược vào core. Senior / Technical developer phải biết khi nào abstraction tạo option value thật và khi nào chỉ làm codebase phức tạp hơn mà không có khả năng thay đổi thực tế.

### Design 3 — API backward compatibility nên ưu tiên additive evolution

**Khái niệm:**
Khi API đã có consumer production, ưu tiên thay đổi additive: thêm field optional, thêm endpoint hoặc mở rộng enum behavior có kiểm soát thay vì đổi semantics của contract hiện tại.

**Vấn đề nó giải quyết:**
Producer và consumer thường deploy độc lập. Một thay đổi nhỏ ở server như rename field hoặc đổi nullability có thể làm mobile app, CMS frontend hoặc third-party integration đang chạy bị lỗi dù backend deploy thành công.

**Ví dụ thực tế:**
Thay vì đổi:
```json
{ "name": "A" }
```

thành:
```json
{ "displayName": "A" }
```

ngay lập tức, server có thể hỗ trợ cả hai trong giai đoạn migration, đánh dấu field cũ deprecated và theo dõi usage trước khi remove.

**Trade-off:**
Backward compatibility giảm breakage và cho phép rollout độc lập, nhưng tạo contract debt, code hỗ trợ legacy và chi phí versioning nếu kéo dài quá lâu.

**Middle → Senior insight:**
Middle developer cần hiểu optional fields, tolerant readers và contract tests. Senior / Technical developer phải quản lý deprecation lifecycle, telemetry usage, migration window và quyết định khi nào additive change đủ tốt, khi nào cần API version mới.
