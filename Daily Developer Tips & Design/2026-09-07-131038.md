# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Quản lý `HttpClient` theo handler lifetime, không theo request

**Mẹo:**
Trong ASP.NET Core, ưu tiên `IHttpClientFactory` hoặc `SocketsHttpHandler` được quản lý đúng vòng đời thay vì `new HttpClient()` cho từng request. Đồng thời hiểu rằng DNS refresh gắn với connection/handler lifetime, không phải chỉ với object `HttpClient`.

**Tại sao hữu ích:**
Tạo `HttpClient` liên tục có thể làm socket đi vào `TIME_WAIT`, gây socket exhaustion dưới tải cao. Ngược lại, giữ một connection pool quá lâu mà không có lifetime phù hợp có thể khiến application tiếp tục dùng endpoint cũ sau khi DNS thay đổi. `IHttpClientFactory` giải quyết phần lớn lifecycle này bằng cách reuse handler có kiểm soát.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri("https://inventory.internal");
    client.Timeout = TimeSpan.FromSeconds(5);
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

Nếu service phía sau dùng dynamic endpoint/DNS, handler lifetime hợp lý giúp connection pool được tái tạo định kỳ.

**Lưu ý:**
Không đặt `HandlerLifetime` cực ngắn theo thói quen. Recycle connection quá thường xuyên làm tăng TCP/TLS handshake và có thể giảm throughput. Cần cân bằng DNS freshness với connection reuse.

### Tip 2 — Cẩn thận với `DbContext` pooling khi có state theo request

**Mẹo:**
`AddDbContextPool` có thể giảm allocation và setup cost của `DbContext`, nhưng chỉ nên dùng khi context không giữ state thay đổi theo request ngoài state EF Core quản lý.

**Tại sao hữu ích:**
Pooled `DbContext` được reset rồi reuse. Nếu bạn gắn tenant ID, user ID hoặc custom mutable state trực tiếp vào context mà không reset đúng, request sau có thể vô tình kế thừa state của request trước — đây là bug vừa khó debug vừa nguy hiểm trong multi-tenant system.

**Ví dụ:**
Không nên làm kiểu:
```csharp
public sealed class AppDbContext : DbContext
{
    public string? TenantId { get; set; }
}
```

rồi set `TenantId` trực tiếp trên pooled context mà không có cơ chế reset đáng tin cậy.

Nếu cần tenant filtering, tách tenant resolution khỏi mutable context state hoặc dùng factory có lifecycle phù hợp.

**Lưu ý:**
Pooling không phải tối ưu mặc định. Trước tiên đo startup/allocation cost của `DbContext`; nhiều hệ thống bottleneck nằm ở SQL hoặc network, không nằm ở việc khởi tạo context.

### Tip 3 — Chọn partition key của Cosmos DB theo traffic distribution, không chỉ theo domain meaning

**Mẹo:**
Khi chọn partition key cho Cosmos DB, đánh giá đồng thời query pattern, write distribution và cardinality. Một field “đúng nghĩa nghiệp vụ” nhưng có ít giá trị hoặc traffic lệch mạnh có thể tạo hot partition.

**Tại sao hữu ích:**
Cosmos DB phân phối dữ liệu và throughput theo logical partition. Nếu phần lớn request dồn vào một partition key, scale tổng thể của container không giải quyết được bottleneck cục bộ. Kết quả có thể là throttling dù tổng RU provisioned vẫn còn dư.

**Ví dụ:**
Giả sử lưu event theo:
```json
{
  "tenantId": "enterprise-a",
  "deviceId": "d-1042",
  "timestamp": "..."
}
```

Nếu một tenant tạo 70% traffic, chỉ dùng `/tenantId` có thể tạo hot partition. Có thể cần chiến lược như composite/synthetic key tùy query pattern, ví dụ `tenantId + bucket`.

**Lưu ý:**
Đừng thêm random suffix chỉ để “phân tán đều”. Nếu query luôn cần fan-out qua hàng chục partition, RU cost và latency có thể tăng mạnh. Partition strategy phải dựa trên cả write và read path.

### Tip 4 — Trong Playwright, chờ condition thay vì dùng sleep cố định

**Mẹo:**
Thay `Task.Delay`, `setTimeout` hoặc fixed wait bằng auto-waiting và assertion của Playwright khi test UI bất đồng bộ.

**Tại sao hữu ích:**
Sleep cố định tạo test vừa chậm vừa flaky: máy nhanh thì chờ dư, máy CI chậm thì vẫn fail. Playwright có locator auto-wait và assertion retry tới khi condition đạt hoặc timeout.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved successfully')).toBeVisible();
```

Test chỉ chờ đúng condition cần thiết thay vì:
```ts
await page.waitForTimeout(3000);
```

**Lưu ý:**
Không biến timeout thành 60–120 giây để che flaky test. Nếu assertion thường xuyên gần timeout, cần kiểm tra network, test data, animation hoặc race condition thật sự.

### Tip 5 — Dùng browser DevTools để đọc network waterfall trước khi tối ưu frontend bundle

**Mẹo:**
Khi page load chậm, bắt đầu bằng Network panel và waterfall để xác định thời gian nằm ở DNS/TLS, TTFB, blocking request, large asset hay JavaScript execution; đừng mặc định lỗi nằm ở bundle size.

**Tại sao hữu ích:**
Frontend latency là tổng của nhiều lớp. Backend TTFB 1.8 giây không thể được sửa bằng cách minify thêm 30 KB JavaScript. Waterfall giúp khoanh vùng evidence trước khi chọn kỹ thuật tối ưu.

**Ví dụ:**
Một trang CMS mất 3 giây để render:
- HTML TTFB: 1.6 s
- CSS/JS download: 300 ms
- image hero: 900 ms
- main-thread JS: 120 ms

Ưu tiên hợp lý có thể là backend/cache và image delivery, không phải refactor React/Vue component.

**Lưu ý:**
Đừng chỉ đo trên localhost hoặc fast Wi-Fi. Dùng throttling, real-device telemetry và Core Web Vitals thực tế nếu performance ảnh hưởng người dùng production.

## 🧠 Software Design

### Design 1 — Saga thay distributed transaction khi workflow đi qua nhiều service

**Khái niệm:**
Saga chia một business workflow thành nhiều local transaction. Nếu bước sau thất bại, hệ thống thực hiện compensating action thay vì rollback toàn bộ bằng một global ACID transaction.

**Vấn đề nó giải quyết:**
Trong hệ thống có Order, Payment, Inventory và Shipping deploy độc lập, distributed transaction kiểu two-phase commit thường khó triển khai, khó vận hành và tăng coupling giữa các service. Saga chấp nhận eventual consistency để đổi lấy autonomy và fault tolerance tốt hơn.

**Ví dụ thực tế:**
Checkout flow:
1. Order tạo trạng thái `Pending`.
2. Payment authorize thành công.
3. Inventory reservation thất bại.
4. Saga phát compensation để void/refund Payment.
5. Order chuyển sang `Failed`.

Mỗi service chỉ commit local database của mình.

**Trade-off:**
Lợi ích là service autonomy, transaction scope nhỏ và phù hợp distributed systems. Chi phí là business state tạm thời không nhất quán, compensation có thể thất bại, tracing khó hơn và workflow state phải được theo dõi rõ ràng.

**Middle → Senior insight:**
Middle developer cần implement step, retry và compensation idempotent. Senior / Technical developer phải quyết định choreography hay orchestration, xác định failure boundary, timeout, observability, manual recovery và liệu workflow có thực sự cần tách service hay một local transaction trong Modular Monolith đã đủ.

### Design 2 — CQRS chỉ đáng giá khi read và write có áp lực khác nhau thật sự

**Khái niệm:**
CQRS tách model/flow đọc và ghi khi hai phía có requirement khác nhau đáng kể về schema, scaling, consistency hoặc business behavior. Nó không đồng nghĩa bắt buộc phải có hai database hay Event Sourcing.

**Vấn đề nó giải quyết:**
Một transactional model chuẩn hóa có thể phù hợp cho command nhưng bất tiện cho dashboard/search/reporting. Ngược lại, ép mọi read đi qua aggregate/domain model có thể tạo query phức tạp và coupling không cần thiết.

**Ví dụ thực tế:**
Write side của Order giữ invariant chặt trong relational database. Read side của dashboard dùng projection `OrderSummary` tối ưu cho filter/sort và được cập nhật async từ event hoặc background process.

**Trade-off:**
CQRS cho phép tối ưu độc lập read/write và làm intent rõ hơn, nhưng thêm model duplication, synchronization, eventual consistency, debugging complexity và operational overhead. Với CRUD app đơn giản, chi phí này thường lớn hơn lợi ích.

**Middle → Senior insight:**
Middle developer cần phân biệt command với query và tránh business side effect trong read path. Senior / Technical developer phải chứng minh pressure đủ lớn để tách model, xác định consistency SLA và chọn mức CQRS tối thiểu cần thiết thay vì áp full stack MediatR + event bus + read database theo khuôn mẫu.

### Design 3 — Observability phải có cardinality budget

**Khái niệm:**
Metrics và telemetry cần được thiết kế với giới hạn cardinality rõ ràng. Label/tag có quá nhiều giá trị duy nhất làm chi phí lưu trữ, indexing và query tăng rất nhanh.

**Vấn đề nó giải quyết:**
Một metric tưởng đơn giản như request count có thể bùng nổ số time series nếu gắn `userId`, `orderId`, raw URL hoặc exception message làm dimension. Hệ thống observability có thể trở nên đắt, chậm hoặc tự gây sự cố.

**Ví dụ thực tế:**
Tốt:
```text
http_requests_total{route="/orders/{id}",status="200"}
```

Rủi ro cao:
```text
http_requests_total{url="/orders/98374291",userId="u-784..."}
```

ID cụ thể phù hợp hơn với structured logs/traces có sampling, không phải metric label.

**Trade-off:**
Low-cardinality metrics rẻ, aggregate tốt và phù hợp alerting; nhưng mất chi tiết từng request. Logs/traces giữ context sâu hơn nhưng tốn storage và query cost. Thiết kế tốt cần phân vai metrics, logs và traces thay vì nhồi mọi dimension vào một công cụ.

**Middle → Senior insight:**
Middle developer cần biết field nào phù hợp làm metric label và field nào nên ở log/trace. Senior / Technical developer phải đặt telemetry budget, retention, sampling, SLO-driven dashboard và guardrail để observability scale cùng traffic mà không biến thành nguồn chi phí hoặc outage mới.
