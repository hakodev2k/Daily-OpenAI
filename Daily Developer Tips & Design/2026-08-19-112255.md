# Daily Developer Tips & Design — 2026-08-19

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Task.WhenAll` nhưng giữ lại context lỗi riêng cho từng operation

**Mẹo:**
Khi chạy nhiều I/O operation độc lập song song, dùng `Task.WhenAll` để giảm tổng latency, nhưng nên giữ reference tới từng task thay vì tạo mảng vô danh rồi khó biết operation nào thất bại.

**Tại sao hữu ích:**
Bạn vừa tận dụng concurrency, vừa dễ log hoặc xử lý lỗi theo từng dependency thay vì chỉ nhận một exception chung khó truy vết.

**Ví dụ:**
```csharp
var customerTask = customerClient.GetAsync(customerId, ct);
var ordersTask = orderClient.GetRecentAsync(customerId, ct);
var balanceTask = billingClient.GetBalanceAsync(customerId, ct);

await Task.WhenAll(customerTask, ordersTask, balanceTask);

return new Dashboard(
    await customerTask,
    await ordersTask,
    await balanceTask);
```
Nếu cần chẩn đoán chi tiết, có thể kiểm tra trạng thái từng task sau khi `WhenAll` thất bại.

**Lưu ý:**
Không dùng `Task.WhenAll` cho các operation phụ thuộc thứ tự hoặc khi việc chạy đồng thời có thể làm quá tải database/API downstream. Concurrency không đồng nghĩa với “càng nhiều càng tốt”.

### Tip 2 — Tránh `SELECT *` trong production query và API data access

**Mẹo:**
Chỉ select đúng các cột cần dùng, đặc biệt với bảng lớn hoặc endpoint chỉ trả DTO nhỏ.

**Tại sao hữu ích:**
Giảm network payload, memory allocation, I/O và nguy cơ query bị chậm khi schema thêm cột lớn như `nvarchar(max)`, JSON hoặc blob.

**Ví dụ:**
```sql
SELECT Id, CustomerId, TotalAmount, CreatedAt
FROM Orders
WHERE CustomerId = @CustomerId
ORDER BY CreatedAt DESC;
```
Với EF Core:
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.TotalAmount,
        x.CreatedAt))
    .ToListAsync(ct);
```

**Lưu ý:**
Không tối ưu projection quá sớm ở mọi nơi. Với internal admin query nhỏ hoặc prototype, readability đôi khi quan trọng hơn vài cột dư thừa.

### Tip 3 — Dùng `git bisect` để tìm commit gây regression thay vì dò thủ công

**Mẹo:**
Khi biết một phiên bản cũ hoạt động và phiên bản hiện tại bị lỗi, dùng `git bisect` để Git binary-search commit gây regression.

**Tại sao hữu ích:**
Nếu có hàng trăm commit giữa hai mốc, `git bisect` thường chỉ cần vài lần test để tìm commit đầu tiên gây lỗi.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
```
Sau mỗi lần Git checkout một commit trung gian:
```bash
git bisect good
# hoặc
git bisect bad
```
Kết thúc:
```bash
git bisect reset
```
Có thể tự động hóa bằng:
```bash
git bisect run dotnet test
```

**Lưu ý:**
`git bisect run` chỉ hiệu quả nếu test có kết quả ổn định. Flaky tests có thể dẫn Git tới commit sai.

### Tip 4 — Đặt timeout riêng cho outbound HTTP thay vì chỉ dựa vào timeout toàn request

**Mẹo:**
Mỗi dependency bên ngoài nên có timeout phù hợp với SLA của chính nó. Với `HttpClient`, ưu tiên timeout/cancellation rõ ràng ở từng call hoặc qua resilience pipeline.

**Tại sao hữu ích:**
Một downstream API treo 30 giây có thể giữ request thread, connection và memory lâu hơn mức business chấp nhận. Timeout ngắn hợp lý giúp fail fast và bảo vệ hệ thống phía bạn.

**Ví dụ:**
```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

var response = await httpClient.GetAsync(
    "/inventory/123",
    timeoutCts.Token);
```

**Lưu ý:**
Timeout quá thấp sẽ biến spike latency bình thường thành lỗi hàng loạt. Giá trị timeout nên dựa trên observed latency và business SLA, không chọn tùy ý.

### Tip 5 — Dùng `EXPLAIN ANALYZE` hoặc Actual Execution Plan trước khi thêm index

**Mẹo:**
Khi query chậm, kiểm tra execution plan để xác định bottleneck thực tế trước khi tạo index mới.

**Tại sao hữu ích:**
Một query chậm có thể do scan, estimate sai, join strategy, sort lớn, parameter sensitivity hoặc trả quá nhiều row. Thêm index mù quáng có thể không giúp gì nhưng lại tăng chi phí write và storage.

**Ví dụ:**
PostgreSQL:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;
```
SQL Server: bật **Actual Execution Plan** và kiểm tra scan/seek, estimated rows vs actual rows, key lookup và sort.

**Lưu ý:**
`EXPLAIN ANALYZE` thực sự chạy query. Cẩn thận với `UPDATE`, `DELETE`, query rất nặng hoặc production database đang tải cao.

## 🧠 Software Design

### Design 1 — Modular Monolith trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia hệ thống thành các module có boundary rõ, ownership riêng và hạn chế dependency trực tiếp giữa các domain.

**Vấn đề nó giải quyết:**
Nó xử lý coupling trong monolith mà chưa phải trả toàn bộ chi phí vận hành của Microservices như distributed tracing, network failure, deployment orchestration và data consistency giữa services.

**Ví dụ thực tế:**
Một hệ thống thương mại điện tử có `Catalog`, `Ordering`, `Payments` và `Shipping`. Thay vì tạo ngay bốn services, mỗi module có application/domain layer riêng, schema hoặc table ownership rõ và chỉ giao tiếp qua contracts nội bộ hoặc events.

**Trade-off:**
Lợi ích là development, debugging và transaction đơn giản hơn Microservices. Chi phí là deployment vẫn chung và một module có thể ảnh hưởng tài nguyên toàn ứng dụng. Nếu boundary không được enforce, Modular Monolith rất dễ quay lại thành “big ball of mud”.

**Middle → Senior insight:**
Middle developer cần biết module không chỉ là folder. Senior developer phải xác định boundary theo business capability, kiểm soát dependency direction và biết lúc nào pain thực tế về scaling, team autonomy hoặc deployment đủ lớn để justify việc tách service.

### Design 2 — API Versioning không thay thế backward compatibility

**Khái niệm:**
Versioning giúp duy trì nhiều contract song song khi có breaking change, nhưng thiết kế API tốt vẫn nên ưu tiên additive, backward-compatible changes trước khi tạo version mới.

**Vấn đề nó giải quyết:**
Client thường không upgrade đồng thời với server. Breaking change tùy tiện có thể làm mobile app, third-party integration hoặc frontend cũ ngừng hoạt động ngay sau deployment.

**Ví dụ thực tế:**
Thay vì đổi:
```json
{ "name": "Alice" }
```
thành:
```json
{ "fullName": "Alice" }
```
và buộc mọi client migrate, có thể tạm thời trả cả hai field, deprecate `name`, theo dõi usage rồi mới loại bỏ ở version sau.

**Trade-off:**
Backward compatibility giảm disruption nhưng làm contract phình ra và tăng maintenance. Versioning tạo migration path rõ hơn nhưng nếu tạo version cho mọi thay đổi nhỏ, codebase sẽ nhanh chóng chứa nhiều branch logic khó quản lý.

**Middle → Senior insight:**
Middle developer cần phân biệt breaking và non-breaking change. Senior developer cần thiết kế deprecation policy, migration window, usage telemetry và chọn khi nào additive evolution đủ tốt, khi nào cần `/v2`, media type versioning hoặc contract mới hoàn toàn.

### Design 3 — Bulkhead Isolation để một dependency không kéo sập toàn hệ thống

**Khái niệm:**
Bulkhead chia tài nguyên hoặc concurrency thành các vùng độc lập để một workload hoặc dependency bị nghẽn không chiếm hết thread, connection, queue worker hoặc request capacity của hệ thống.

**Vấn đề nó giải quyết:**
Trong production, một downstream service chậm có thể khiến hàng nghìn request cùng chờ, làm connection pool cạn và lan lỗi sang cả những chức năng không liên quan.

**Ví dụ thực tế:**
Một API gọi `RecommendationService` và `PaymentService`. Recommendation chỉ là optional feature, nên có thể giới hạn tối đa 20 concurrent calls riêng cho dependency này. Nếu nó chậm, recommendation bị degrade nhưng payment traffic vẫn còn tài nguyên xử lý.

**Trade-off:**
Bulkhead cải thiện fault isolation và predictable degradation, nhưng làm giảm khả năng chia sẻ tài nguyên linh hoạt và cần tuning capacity cho từng pool. Nếu partition quá cứng, một pool có thể idle trong khi pool khác đang quá tải.

**Middle → Senior insight:**
Middle developer cần hiểu timeout/retry chưa đủ để chống resource exhaustion. Senior developer phải nhìn toàn chuỗi dependency, xác định criticality, capacity budget và chọn isolation theo semaphore, connection pool, queue, worker pool hoặc deployment boundary tùy mức độ rủi ro.
