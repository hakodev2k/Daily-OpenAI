# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow`

**Mẹo:**
Với code có logic phụ thuộc thời gian như expiration, retry window hoặc scheduled processing, inject `TimeProvider` thay vì đọc clock hệ thống trực tiếp.

**Tại sao hữu ích:**
Clock là một external dependency. Gọi `DateTime.UtcNow` rải rác khiến test phải phụ thuộc thời gian thực và dễ flaky quanh boundary. `TimeProvider` trong modern .NET cho phép production dùng system clock nhưng test kiểm soát thời gian mà không cần `Thread.Sleep`.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        timeProvider.GetUtcNow() >= expiresAt;
}
```
Test có thể dùng controllable/fake provider để kiểm tra đúng thời điểm trước, tại và sau expiration.

**Lưu ý:**
Đừng biến mọi timestamp thành abstraction riêng nếu không có time-dependent behavior. Cũng phân biệt wall-clock time với elapsed-time measurement; timeout/performance measurement cần monotonic semantics phù hợp.

### Tip 2 — Dùng keyset pagination cho feed lớn thay vì `Skip/Take` sâu

**Mẹo:**
Với API duyệt tuần tự qua dataset lớn, paginate theo stable ordered key thay vì tăng `OFFSET` vô hạn.

**Tại sao hữu ích:**
`OFFSET 100000` vẫn buộc database tìm/sort rồi bỏ qua lượng lớn rows trước khi trả page. Keyset pagination chuyển bài toán thành range seek trên index và ổn định hơn khi dữ liệu mới được insert giữa các request.

**Ví dụ:**
```csharp
var page = await db.Orders
    .Where(x => x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id < cursor.Id))
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(50)
    .AsNoTracking()
    .ToListAsync(ct);
```
Index tương ứng nên bắt đầu bằng ordering keys phù hợp với query pattern.

**Lưu ý:**
Keyset không phù hợp khi UI bắt buộc nhảy trực tiếp tới page 417. Cursor phải chứa tie-breaker để ordering deterministic; chỉ dùng `CreatedAt` có thể bỏ hoặc lặp rows khi nhiều records cùng timestamp.

### Tip 3 — Khi Redis chậm, kiểm tra hot key trước khi scale cả cluster

**Mẹo:**
Nếu latency Redis tăng trong khi tổng memory/CPU chưa cao, kiểm tra traffic distribution theo key và command thay vì chỉ nhìn aggregate utilization.

**Tại sao hữu ích:**
Partitioned cache scale theo key distribution. Một key cực nóng có thể dồn phần lớn request vào một shard/node, trong khi cluster-wide metrics trông bình thường. Payload lớn hoặc expensive command trên hot key còn làm event loop bị chiếm lâu hơn.

**Ví dụ:**
```text
Symptom -> cache p99 tăng, một shard CPU 90%, các shard khác 20%
Evidence -> phần lớn GET tập trung vào product:homepage
Hypothesis -> hot key
Options -> local cache ngắn hạn, request coalescing, partition value, giảm payload
```

**Lưu ý:**
Đừng randomize key chỉ để phân tải nếu semantics yêu cầu một authoritative cached value; việc nhân bản key tạo invalidation/consistency cost. Trước tiên xác nhận command latency, payload size và network.

### Tip 4 — Với JWT, validate `issuer` và `audience`, không chỉ signature

**Mẹo:**
Cấu hình authentication để xác nhận token được phát bởi issuer mong đợi và dành cho chính API của bạn, ngoài signature và lifetime validation.

**Tại sao hữu ích:**
Một token có chữ ký hợp lệ chưa chắc được cấp cho resource hiện tại. Nếu nhiều APIs tin cùng identity provider/key material, bỏ audience validation có thể cho token dành cho service A được chấp nhận bởi service B.

**Ví dụ:**
```csharp
builder.Services.AddAuthentication()
    .AddJwtBearer(options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = "orders-api";
    });
```
Authorization tiếp theo vẫn phải kiểm tra scopes/roles/policies phù hợp với operation.

**Lưu ý:**
Authentication thành công không đồng nghĩa authorization thành công. Không tự decode JWT rồi tin claims mà bỏ cryptographic validation; đồng thời tránh log raw access token.

### Tip 5 — Dùng `git bisect` để biến regression hunt thành binary search

**Mẹo:**
Khi biết một commit cũ tốt và HEAD hiện tại lỗi, dùng `git bisect` để thu hẹp commit gây regression thay vì đọc tuần tự hàng chục commits.

**Tại sao hữu ích:**
Binary search giảm số lần kiểm tra từ tuyến tính xuống logarithmic. Với 128 commits, về lý thuyết chỉ khoảng 7 lần phân loại good/bad nếu lịch sử phù hợp.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# chạy reproduction/test tại commit Git chọn
git bisect good   # hoặc: git bisect bad

git bisect reset
```
Có thể tự động hóa bằng `git bisect run ./regression-test.sh` nếu test trả exit code đáng tin cậy.

**Lưu ý:**
Bisect kém hiệu quả nếu intermediate commits không build được hoặc bug nondeterministic. Test dùng để phân loại phải thực sự đại diện regression; flaky test sẽ dẫn binary search sai hướng.

## 🧠 Software Design

### Design 1 — CQRS chỉ nên tách khi read/write thật sự có áp lực khác nhau

**Khái niệm:**
CQRS tách model hoặc path xử lý command và query để mỗi phía tối ưu cho nhu cầu riêng. Nó không bắt buộc phải có microservices, message broker hay hai databases.

**Vấn đề nó giải quyết:**
Một domain write model giàu invariants có thể rất khác read model cần projection phẳng, filtering và reporting nhanh. Ép cả hai qua cùng abstraction đôi khi làm query khó tối ưu hoặc domain model bị biến thành DTO đa dụng.

**Ví dụ thực tế:**
Order commands dùng EF Core aggregate để bảo vệ business rules; dashboard query đọc projection trực tiếp, chỉ lấy các cột cần thiết. Ban đầu cả hai vẫn ở cùng Modular Monolith và cùng database. Chỉ khi read scaling/latency yêu cầu mới cân nhắc read store riêng.

**Trade-off:**
CQRS có thể làm responsibility rõ và cho phép tối ưu độc lập, nhưng tăng model duplication, mapping, test surface và nếu tách storage sẽ thêm eventual consistency. CRUD đơn giản thường không hưởng lợi từ full CQRS.

**Middle → Senior insight:**
Middle developer cần phân biệt command/query semantics và tránh để query mutate state. Senior / Technical developer phải chọn mức tách phù hợp: chỉ tách handlers/models, tách modules hay tách storage/services; sophistication chỉ hợp lý khi pressure thực tế trả được complexity cost.

### Design 2 — Bulkhead: cô lập resource để một dependency không làm chìm toàn service

**Khái niệm:**
Bulkhead giới hạn concurrency/resource dành cho từng loại workload hoặc dependency, tương tự các khoang kín trên tàu: một vùng bị overload không chiếm toàn bộ capacity hệ thống.

**Vấn đề nó giải quyết:**
Một third-party API bắt đầu trả chậm. Nếu mọi request đều giữ worker/connections chờ dependency đó, traffic của các endpoint không liên quan cũng có thể bị starvation và timeout.

**Ví dụ thực tế:**
Calls tới recommendation provider được giới hạn một concurrency budget riêng và có bounded queue. Khi budget đầy, feature có thể fail fast/fallback, trong khi checkout vẫn giữ capacity cho dependencies quan trọng hơn.

**Trade-off:**
Isolation giảm blast radius và cascading failure nhưng capacity bị phân mảnh; limit quá thấp tạo artificial bottleneck, quá cao thì không còn isolation. Bulkhead cũng không thay timeout, circuit breaker hay backpressure.

**Middle → Senior insight:**
Middle developer cần giới hạn concurrency và xử lý rejection/fallback đúng. Senior / Technical developer phải phân loại criticality, chọn budget dựa trên measured capacity, xác định degradation policy và theo dõi saturation để điều chỉnh thay vì hard-code tùy ý.

### Design 3 — Composition over Inheritance cho business behavior biến đổi độc lập

**Khái niệm:**
Composition ghép object từ các capability nhỏ thay vì tạo hierarchy kế thừa sâu để tái sử dụng behavior. Mục tiêu không phải cấm inheritance, mà tránh coupling behavior không thực sự có quan hệ subtype ổn định.

**Vấn đề nó giải quyết:**
Một e-commerce system bắt đầu với `StandardOrder`, `VipOrder`, rồi thêm `InternationalVipOrder`, `SubscriptionInternationalOrder`. Khi discount, tax và shipping thay đổi độc lập, class hierarchy nhanh chóng thành tổ hợp khó mở rộng và override khó dự đoán.

**Ví dụ thực tế:**
`OrderPricingService` nhận `IDiscountPolicy`, `ITaxPolicy` và `IShippingPolicy` phù hợp với context. Các policies được test riêng và phối hợp theo business rules thay vì encode mọi tổ hợp bằng subclasses.

**Trade-off:**
Composition giảm hierarchy coupling và cho phép behavior thay đổi độc lập, nhưng quá nhiều tiny interfaces/strategies làm flow khó theo dõi và DI graph phình to. Inheritance vẫn phù hợp khi có quan hệ `is-a` ổn định và substitutability thực sự.

**Middle → Senior insight:**
Middle developer cần nhận ra lúc override hierarchy đang chứa nhiều axes of change. Senior / Technical developer phải xác định variation nào đáng trở thành policy abstraction và variation nào nên giữ trực tiếp trong domain code; abstraction chỉ có giá trị khi nó phản ánh thay đổi thực tế, không phải vì pattern trông sạch.
