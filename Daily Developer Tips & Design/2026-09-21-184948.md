# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `DbContext` sống lâu hơn một unit of work

**Mẹo:**
Giữ `DbContext` theo scope ngắn, thường là một request hoặc một unit of work rõ ràng. Với background processing, tạo scope/context riêng cho từng message hoặc batch thay vì giữ một instance lâu dài trong singleton worker.

**Tại sao hữu ích:**
`DbContext` giữ change tracker và không thread-safe. Context sống quá lâu khiến tracked entities tích tụ, memory tăng, state cũ ảnh hưởng query/update mới và concurrent processing dễ sinh lỗi. Scope ngắn làm transaction/state boundary rõ hơn và giảm hidden coupling giữa các operation.

**Ví dụ:**
Một `BackgroundService` xử lý Service Bus messages không inject `DbContext` trực tiếp vào singleton. Mỗi message tạo DI scope, resolve context, xử lý và dispose scope sau khi hoàn tất; message tiếp theo bắt đầu với tracking state sạch.

**Lưu ý:**
Không tạo context mới tùy tiện giữa các bước phải nằm trong cùng transaction. Ngược lại, đừng dùng một context duy nhất để xử lý hàng nghìn records chỉ để “tiết kiệm connection”; connection pooling và context pooling là concerns khác với lifetime của unit of work.

### Tip 2 — Dùng covering index theo query shape, nhưng tính cả write cost

**Mẹo:**
Khi một query đọc thường xuyên phải lookup thêm columns sau index seek, cân nhắc index có key columns phù hợp filter/sort và `INCLUDE` các columns chỉ cần trả về. Xác nhận bằng actual execution plan và workload metrics trước khi thêm.

**Tại sao hữu ích:**
Covering index có thể cho database trả kết quả hoàn toàn từ index, giảm key lookup và random I/O. Nhưng mỗi index mới làm tăng storage, memory pressure và chi phí `INSERT`/`UPDATE`/`DELETE`; tối ưu read path không miễn phí.

**Ví dụ:**
API thường query orders theo `TenantId`, `Status`, sort theo `CreatedAt` và chỉ trả `OrderId`, `Total`. Một index được thiết kế theo filter/order và include response columns có thể loại bỏ hàng nghìn lookups trên hot endpoint.

**Lưu ý:**
Không đưa mọi column vào `INCLUDE` để biến index thành bản sao table. Theo dõi index size, write rate, usage statistics và execution plan; query ít chạy hoặc write-heavy có thể không đáng đổi lấy covering index.

### Tip 3 — Azure Service Bus lock renewal không thay thế idempotency

**Mẹo:**
Nếu message processing có thể dài hơn lock duration, cấu hình renewal phù hợp và theo dõi thời gian xử lý; đồng thời vẫn thiết kế consumer idempotent vì lock có thể mất do process crash, network partition hoặc renewal failure.

**Tại sao hữu ích:**
Peek-lock ngăn consumer khác xử lý message trong khoảng lock hiện tại, nhưng không tạo exactly-once delivery. Nếu side effect đã commit rồi process chết trước khi complete message, broker có thể redeliver và consumer phải nhận diện operation đã được áp dụng.

**Ví dụ:**
Consumer tạo invoice mất 90 giây. Auto-renew giữ lock trong lúc xử lý bình thường, nhưng `InvoiceId`/message identity vẫn được dùng để chống tạo invoice lần hai nếu worker chết sau database commit nhưng trước `CompleteMessageAsync`.

**Lưu ý:**
Đừng tăng lock/renewal window vô hạn để che handler quá chậm. Đo processing latency, tách long-running work khi phù hợp và xử lý `MessageLockLostException`; duplicate delivery vẫn là failure mode hợp lệ.

### Tip 4 — Production logging phải tránh biến exception thành nơi rò dữ liệu nhạy cảm

**Mẹo:**
Log structured metadata cần thiết cho diagnosis nhưng kiểm soát payload, headers, query strings và exception context có thể chứa token, cookie, password, PII hoặc payment data. Áp dụng allowlist/redaction thay vì log toàn bộ request object.

**Tại sao hữu ích:**
Logs thường được replicate sang nhiều hệ thống, giữ lâu và có phạm vi truy cập rộng hơn database nghiệp vụ. Một lỗi validation hoặc HTTP client exception có thể vô tình đưa Authorization header hoặc body nhạy cảm vào telemetry, biến observability thành data-exposure surface.

**Ví dụ:**
Khi third-party API trả `401`, log dependency name, status code, operation, trace ID và sanitized error category; không dump toàn bộ outbound headers chứa bearer token để “debug nhanh”.

**Lưu ý:**
Redaction bằng regex sau khi log thường mong manh. Thiết kế logging contract tại source, tránh sensitive fields ngay từ đầu và kiểm tra cả telemetry auto-collection của framework/APM, không chỉ các câu `ILogger` do application viết.

### Tip 5 — AI coding agent phải được kiểm tra bằng repository truth, không bằng câu trả lời tự tin

**Mẹo:**
Khi AI đề xuất API, package hoặc refactor, bắt nó bám vào source hiện tại, project files, dependency versions và tests. Sau thay đổi, build/test/static analysis phải là evidence chính thay vì lời giải thích của agent.

**Tại sao hữu ích:**
AI có thể sinh API tồn tại ở version khác, giả định architecture không có trong repository hoặc tạo test chỉ xác nhận implementation vừa sinh. Grounding vào code thực và executable checks giảm hallucination và architectural drift.

**Ví dụ:**
Agent đề xuất một overload của library mới. Trước khi nhận patch, kiểm tra `.csproj`/lock file và compile trên version repository đang dùng; nếu API không tồn tại, sửa giải pháp theo dependency thực thay vì nâng package ngoài scope.

**Lưu ý:**
Build xanh chưa chứng minh behavior đúng. Với thay đổi quan trọng, cần regression test phản ánh requirement, review security/performance và kiểm tra diff có mở rộng scope hoặc abstraction không cần thiết hay không.

## 🧠 Software Design

### Design 1 — Queue và Topic giải quyết hai kiểu phân phối message khác nhau

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer trong nhóm xử lý. Topic + subscriptions phù hợp khi cùng một event cần được nhiều consumer groups độc lập nhận theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Dùng một queue cho nhiều business reactions khiến consumers cạnh tranh và một message chỉ đến một bên; ngược lại, dùng pub/sub cho command đơn lẻ có thể tạo fan-out và ownership mơ hồ không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command đưa vào queue để một billing worker xử lý. `OrderCompleted` là event publish lên topic; subscription của Email, Analytics và Loyalty nhận độc lập, mỗi bên có retry/DLQ riêng.

**Trade-off:**
Queue đơn giản hơn về ownership và work distribution. Topic tăng decoupling/fan-out nhưng thêm subscriptions, filtering, duplicate delivery, schema evolution và operational monitoring. Event fan-out cũng làm impact analysis khó hơn khi nhiều downstream phụ thuộc.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumers, retries và DLQ. Senior / Technical developer phải phân biệt command với event, xác định ownership/delivery semantics, subscription lifecycle và đánh giá liệu fan-out có thực sự cần thiết trước khi thêm messaging topology.

### Design 2 — Normalization và denormalization là trade-off theo invariant và read workload

**Khái niệm:**
Normalization giảm duplication và giúp duy trì consistency ở source of truth; denormalization cố ý lưu dữ liệu lặp hoặc read-oriented shape để giảm join/computation trên read path. Hai kỹ thuật phục vụ pressures khác nhau.

**Vấn đề nó giải quyết:**
Một schema quá normalized có thể khiến hot reporting/query path phải join nhiều bảng và khó scale; denormalize thiếu kỷ luật lại tạo nhiều bản sao dữ liệu mà application không biết bản nào authoritative.

**Ví dụ thực tế:**
Order lưu `ProductId` nhưng cũng snapshot `ProductName` và giá tại thời điểm mua vì lịch sử order phải giữ facts của giao dịch, không tự đổi khi catalog đổi. Đây là denormalization theo business semantics, không chỉ optimization tùy tiện.

**Trade-off:**
Normalization giúp update/invariants đơn giản hơn nhưng có thể tăng query complexity. Denormalization cải thiện read locality và có thể giữ historical snapshot, nhưng cần ownership, synchronization/rebuild strategy và chấp nhận storage duplication.

**Middle → Senior insight:**
Middle developer cần phân biệt duplication có chủ đích với accidental duplication. Senior / Technical developer phải xác định authoritative source, consistency requirement, update frequency, read/write ratio và recovery strategy trước khi denormalize.

### Design 3 — Graceful degradation tốt hơn cascading failure cho dependency không critical

**Khái niệm:**
Graceful degradation cho phép hệ thống giảm một phần chức năng khi dependency phụ thất bại, thay vì biến lỗi cục bộ thành lỗi toàn request. Điều này đòi hỏi phân loại rõ critical và optional dependencies.

**Vấn đề nó giải quyết:**
Một trang sản phẩm có thể phụ thuộc inventory, recommendation, review và personalization. Nếu mọi dependency đều bắt buộc thành công, outage của recommendation có thể làm toàn bộ product page trả `500`, mở rộng blast radius không cần thiết.

**Ví dụ thực tế:**
Product API coi pricing/inventory là critical nhưng recommendation là optional. Khi recommendation timeout, request dùng timeout budget ngắn, ghi telemetry và trả product core data không có recommendation thay vì retry kéo dài rồi fail toàn trang.

**Trade-off:**
Degradation tăng availability nhưng UI/API có nhiều states hơn, cần product agreement và observability để tránh dependency hỏng âm thầm hàng tuần. Không được degrade dữ liệu ảnh hưởng correctness như payment authorization chỉ để giữ status `200`.

**Middle → Senior insight:**
Middle developer cần implement timeout/fallback rõ ràng và không nuốt lỗi vô điều kiện. Senior / Technical developer phải phân loại dependency theo business criticality, SLO, stale-data tolerance và user impact, đồng thời quyết định khi nào fail fast tốt hơn fallback.
