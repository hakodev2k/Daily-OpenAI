# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ValueTask` chỉ khi profiling chứng minh có lợi

**Mẹo:**
`ValueTask<T>` có thể giảm allocation khi một async operation thường xuyên hoàn thành synchronously, nhưng không nên thay `Task<T>` mặc định chỉ vì nghĩ nó “nhanh hơn”.

**Tại sao hữu ích:**
Trên hot path có tần suất rất cao, tránh allocation `Task` lặp lại có thể giảm GC pressure. Nhưng `ValueTask<T>` có semantics phức tạp hơn và dễ bị dùng sai.

**Ví dụ:**
```csharp
public ValueTask<User?> GetCachedUserAsync(Guid id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

**Lưu ý:**
Không nên `await` cùng một `ValueTask` nhiều lần, gọi `.Result` tùy tiện hoặc lưu giữ lâu dài. Với đa số application code, `Task<T>` vẫn đơn giản và an toàn hơn.

### Tip 2 — Tách `COUNT(*)` khỏi query phân trang khi không thực sự cần total

**Mẹo:**
Nhiều API pagination luôn chạy thêm `COUNT(*)` để trả tổng số records, dù UI chỉ cần biết còn trang tiếp theo hay không.

**Tại sao hữu ích:**
Trên bảng lớn, query count có thể tốn I/O đáng kể và đôi khi đắt hơn chính query lấy dữ liệu. Dùng `pageSize + 1` có thể xác định `hasNextPage` mà không cần count toàn bộ.

**Ví dụ:**
```sql
SELECT id, created_at, status
FROM orders
WHERE customer_id = @CustomerId
ORDER BY created_at DESC
LIMIT 51;
```

Nếu page size là 50 và query trả 51 rows, application biết còn trang tiếp theo rồi bỏ row cuối.

**Lưu ý:**
Nếu business/UI thực sự cần exact total pages thì vẫn phải tính count hoặc dùng một chiến lược khác. Đừng bỏ `COUNT(*)` chỉ để đổi API contract ngoài ý muốn.

### Tip 3 — Dùng `git worktree` để làm nhiều branch song song

**Mẹo:**
Khi cần giữ một branch đang debug nhưng đồng thời phải xử lý hotfix khác, dùng `git worktree` thay vì stash/checkout liên tục.

**Tại sao hữu ích:**
Mỗi worktree là một working directory độc lập nhưng dùng chung repository objects, giúp giảm context switching và tránh stash nhầm thay đổi.

**Ví dụ:**
```bash
git worktree add ../myapp-hotfix hotfix/payment-timeout
```

Sau khi xong:

```bash
git worktree remove ../myapp-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree. Ngoài ra cần nhớ xóa worktree cũ để tránh workspace lộn xộn.

### Tip 4 — Đặt timeout ở cả database command, không chỉ HTTP request

**Mẹo:**
Request timeout ở ASP.NET Core không tự đảm bảo một SQL command bị treo sẽ dừng sớm. Cần cấu hình command timeout phù hợp cho database workload.

**Tại sao hữu ích:**
Một query bị block hoặc plan xấu có thể giữ connection rất lâu, làm cạn connection pool dù HTTP layer đã mất client.

**Ví dụ:**
```csharp
services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString, sql =>
        sql.CommandTimeout(30)));
```

Hoặc cho một trường hợp đặc biệt:

```csharp
dbContext.Database.SetCommandTimeout(TimeSpan.FromSeconds(120));
```

**Lưu ý:**
Timeout dài hơn không chữa được query chậm. Nếu thường xuyên chạm timeout, cần kiểm tra blocking, execution plan, index và lượng dữ liệu đọc.

### Tip 5 — Khi debug container, kiểm tra từ bên trong network namespace

**Mẹo:**
Nếu application trong Docker không gọi được database/API nhưng máy host gọi được, chạy diagnostic command bên trong container hoặc một debug container cùng network.

**Tại sao hữu ích:**
DNS, proxy, route, certificate và hostname resolution bên trong container có thể khác hoàn toàn host machine.

**Ví dụ:**
```bash
docker exec -it my-api sh
```

Sau đó kiểm tra:

```bash
getent hosts db
curl -v https://internal-api/health
```

Hoặc dùng container tạm:

```bash
docker run --rm -it --network my-network curlimages/curl:latest sh
```

**Lưu ý:**
Production image tối giản có thể không chứa `curl`, `ping` hoặc shell. Không nên cài đầy debug tools vào production image chỉ để tiện troubleshooting; dùng sidecar/debug container khi phù hợp.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency thay vì khóa mọi update

**Khái niệm:**
Optimistic Concurrency giả định conflict không xảy ra thường xuyên. Khi update, hệ thống kiểm tra version/token của record để xác nhận dữ liệu chưa bị người khác thay đổi kể từ lúc đọc.

**Vấn đề nó giải quyết:**
Nếu hai user cùng sửa một record, update sau có thể ghi đè update trước mà không ai biết. Khóa pessimistic mọi lúc lại làm giảm concurrency và tăng contention.

**Ví dụ thực tế:**
Một màn hình chỉnh sửa Employee đọc `RowVersion`. Khi save, EF Core gửi `UPDATE ... WHERE Id = @Id AND RowVersion = @OldRowVersion`. Nếu affected rows bằng 0, application biết có concurrent update và yêu cầu merge/reload.

**Trade-off:**
Lợi ích là throughput tốt, ít lock và phù hợp với workload conflict thấp. Chi phí là application phải xử lý conflict rõ ràng; nếu conflict xảy ra nhiều, retry liên tục có thể gây UX và performance kém.

**Middle → Senior insight:**
Middle developer nên hiểu lost update và cách dùng concurrency token. Senior developer cần quyết định entity nào cần optimistic concurrency, conflict nào có thể auto-merge, conflict nào phải reject và khi nào pessimistic locking mới hợp lý.

### Design 2 — Retry phải đi kèm Retry Budget

**Khái niệm:**
Retry Budget giới hạn tổng lượng retry mà hệ thống cho phép trong một khoảng thời gian hoặc trên một dependency, thay vì để mọi request retry độc lập không giới hạn.

**Vấn đề nó giải quyết:**
Khi downstream đang quá tải, retry đồng loạt có thể nhân traffic lên nhiều lần và biến sự cố nhỏ thành retry storm.

**Ví dụ thực tế:**
Một service gọi payment provider với tối đa 2 retries cho lỗi transient, nhưng chỉ cho retry traffic chiếm tối đa một tỷ lệ nhỏ so với normal traffic. Khi budget cạn, request fail fast hoặc chuyển sang queue xử lý sau.

**Trade-off:**
Retry tăng xác suất vượt qua lỗi tạm thời nhưng làm tăng latency và tải hệ thống. Retry budget bảo vệ dependency tốt hơn nhưng có nghĩa một số request sẽ thất bại sớm dù retry có thể đã thành công.

**Middle → Senior insight:**
Middle developer nên phân biệt transient failure và permanent failure. Senior developer cần thiết kế retry theo error type, idempotency, backoff, jitter, timeout tổng thể và capacity thực tế của downstream.

### Design 3 — CQRS chỉ đáng dùng khi Read và Write thật sự có nhu cầu khác nhau

**Khái niệm:**
CQRS tách model hoặc pipeline đọc và ghi để mỗi phía tối ưu theo yêu cầu riêng, thay vì buộc toàn bộ hệ thống dùng một domain/persistence model duy nhất.

**Vấn đề nó giải quyết:**
Một hệ thống có write side chứa nhiều business invariants nhưng read side cần query/report cực khác có thể trở nên khó tối ưu nếu cố tái sử dụng cùng abstraction cho cả hai.

**Ví dụ thực tế:**
Write side của Order dùng aggregate và validation chặt chẽ. Read side của dashboard lại cần join/order/filter trên nhiều bảng và trả DTO phẳng. Read path có thể dùng query chuyên biệt thay vì ép qua repository của aggregate.

**Trade-off:**
Lợi ích là read/write có thể tối ưu độc lập và boundary rõ hơn. Chi phí là tăng số model, mapping, code path và đôi khi eventual consistency nếu tách storage. Với CRUD đơn giản, CQRS thường chỉ thêm complexity.

**Middle → Senior insight:**
Middle developer nên hiểu CQRS không đồng nghĩa với bắt buộc dùng message bus hay Event Sourcing. Senior developer phải chứng minh được sự khác biệt thật sự về scalability, consistency, domain complexity hoặc query shape trước khi áp dụng.
