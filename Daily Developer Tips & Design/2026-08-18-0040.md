# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` xuyên suốt async flow

**Mẹo:**
Truyền `CancellationToken` từ API endpoint xuống service, database query và external call.

**Tại sao hữu ích:**
Giúp hệ thống dừng các tác vụ không còn cần thiết khi client timeout hoặc request bị hủy.

**Ví dụ:**
```csharp
public async Task<Order?> GetOrderAsync(Guid id, CancellationToken cancellationToken)
{
    return await db.Orders
        .FirstOrDefaultAsync(x => x.Id == id, cancellationToken);
}
```

**Lưu ý:**
Không nên bỏ qua cancellation trong background job dài hạn nếu task có thể bị dừng an toàn.

### Tip 2 — Sử dụng `ILogger` structured logging thay vì string interpolation

**Mẹo:**
Dùng message template để logging có thể query và phân tích tốt hơn.

**Tại sao hữu ích:**
Log aggregation tools có thể filter theo property thay vì parse text.

**Ví dụ:**
```csharp
logger.LogInformation(
    "Created order {OrderId} for customer {CustomerId}",
    order.Id,
    customer.Id);
```

**Lưu ý:**
Không log sensitive data như password, token hoặc thông tin cá nhân không cần thiết.

### Tip 3 — Dùng SQL execution plan trước khi tối ưu query

**Mẹo:**
Kiểm tra execution plan để biết database đang scan, seek hay thiếu index.

**Tại sao hữu ích:**
Tránh tối ưu dựa trên suy đoán và tìm đúng bottleneck.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Orders WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index cho mọi column vì có thể làm chậm write operation.

### Tip 4 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Sử dụng binary search trên Git history thay vì kiểm tra từng commit thủ công.

**Tại sao hữu ích:**
Rút ngắn thời gian tìm regression trong codebase lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.0.0
```

**Lưu ý:**
Cần có cách test xác định rõ trạng thái good/bad.

### Tip 5 — Áp dụng retry có kiểm soát cho external service

**Mẹo:**
Retry chỉ nên dùng cho lỗi tạm thời như network failure hoặc HTTP 503.

**Tại sao hữu ích:**
Tăng khả năng phục hồi khi phụ thuộc bên ngoài không ổn định.

**Ví dụ:**
```csharp
services.AddHttpClient("payment")
    .AddTransientHttpErrorPolicy(policy =>
        policy.WaitAndRetryAsync(3, retry => TimeSpan.FromSeconds(retry)));
```

**Lưu ý:**
Không retry các lỗi business như invalid request hoặc insufficient balance.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Xác định phạm vi dữ liệu và business operation cần thay đổi cùng nhau trong một transaction.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn gây lock lâu hoặc transaction quá nhỏ làm dữ liệu không nhất quán.

**Ví dụ thực tế:**
Trong hệ thống Order, việc tạo Order và cập nhật trạng thái Payment có thể cần boundary khác nhau vì payment là external process.

**Trade-off:**
Transaction nhỏ giúp scalability tốt hơn nhưng yêu cầu xử lý eventual consistency.

**Middle → Senior insight:**
Middle cần hiểu transaction để tránh bug dữ liệu. Senior cần thiết kế boundary dựa trên business consistency thay vì chỉ dựa trên database table.

### Design 2 — Idempotency trong API Design

**Khái niệm:**
Một request có thể gửi nhiều lần nhưng kết quả cuối cùng vẫn giống như chỉ xử lý một lần.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate action trong distributed system khi client retry hoặc network timeout.

**Ví dụ thực tế:**
API thanh toán sử dụng `Idempotency-Key` để đảm bảo một payment request không bị charge hai lần.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và có chiến lược cleanup.

**Middle → Senior insight:**
Middle cần biết implement idempotent endpoint. Senior cần nhận diện nơi nào bắt buộc có idempotency trong hệ thống phân tán.

### Design 3 — Modular Monolith trước Microservices

**Khái niệm:**
Chia hệ thống thành các module có boundary rõ ràng nhưng vẫn deploy như một application.

**Vấn đề nó giải quyết:**
Giảm complexity của distributed system trong giai đoạn hệ thống chưa cần tách service.

**Ví dụ thực tế:**
Một hệ thống ERP có module Sales, Inventory, Accounting tách namespace, database access và business rule riêng.

**Trade-off:**
Dễ vận hành hơn microservices nhưng vẫn có giới hạn về scaling độc lập.

**Middle → Senior insight:**
Middle cần hiểu cách tạo boundary tốt. Senior cần biết khi nào nên giữ monolith và khi nào chi phí microservices thực sự đáng giá.
