# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` không phải thread-safe: parallel query trên cùng context là sai boundary

**Mẹo:**
Không chạy nhiều EF Core operations đồng thời trên cùng một `DbContext`. Nếu workload thật sự cần parallel database work, mỗi concurrent operation phải có context/lifetime độc lập và concurrency phải được giới hạn theo database capacity.

**Tại sao hữu ích:**
`DbContext` quản lý change tracker, connection và internal query state theo unit-of-work; nó không được thiết kế cho concurrent access. `Task.WhenAll` trên nhiều query dùng cùng context có thể gây `InvalidOperationException` hoặc state khó dự đoán, và ngay cả nhiều context song song cũng có thể làm cạn connection pool.

**Ví dụ:**
```csharp
// Sai: cả hai dùng cùng db
var usersTask = db.Users.CountAsync(ct);
var ordersTask = db.Orders.CountAsync(ct);
await Task.WhenAll(usersTask, ordersTask);
```
Với endpoint đơn giản, chạy tuần tự thường đủ. Nếu reporting thật sự cần concurrency, dùng `IDbContextFactory<TContext>` để tạo context riêng và đo tác động lên SQL Server.

**Lưu ý:**
Tách context không tự động làm query nhanh hơn. Hai query cạnh tranh CPU/I/O/locks ở database có thể khiến tổng latency tệ hơn; ưu tiên tối ưu query hoặc gộp round trip khi hợp lý trước khi thêm parallelism.

### Tip 2 — HTTP retry phải tôn trọng idempotency và timeout budget

**Mẹo:**
Chỉ retry transient failures khi operation có thể lặp lại an toàn hoặc có idempotency mechanism. Giới hạn tổng thời gian retry trong end-to-end latency budget thay vì cấu hình số lần thử độc lập với timeout.

**Tại sao hữu ích:**
Retry có thể biến một dependency chậm thành nhiều request chậm hơn và nhân tải đúng lúc downstream đang suy yếu. Với `POST` tạo payment/order, retry sau timeout còn có thể tạo duplicate nếu request đầu đã được xử lý nhưng response bị mất.

**Ví dụ:**
Client gửi payment với `Idempotency-Key`; provider lưu kết quả theo key. Khi connection timeout sau khi gửi request, client có thể retry cùng key thay vì tạo operation mới. Nếu API request có budget 2 giây, retry policy phải nằm trong budget đó.

**Lưu ý:**
Không retry mọi `5xx`, `TaskCanceledException` hoặc network error một cách mù quáng. Phân biệt caller cancellation, timeout, overload/throttling và permanent failure; dùng jitter/backoff khi retry nhiều client để tránh synchronized retry storm.

### Tip 3 — Redis hot key có thể là bottleneck dù cache hit ratio rất cao

**Mẹo:**
Khi Redis latency tăng nhưng hit ratio vẫn đẹp, kiểm tra traffic distribution theo key, payload size và command latency thay vì chỉ nhìn cache hit/miss.

**Tại sao hữu ích:**
Một key cực nóng có thể tập trung phần lớn request vào cùng shard/node, tạo network/CPU pressure trong khi toàn cluster còn capacity. Hit ratio 99% vì thế không chứng minh cache architecture khỏe.

**Ví dụ:**
Homepage của toàn bộ tenant dùng một key `homepage:global` chứa payload lớn và nhận hàng chục nghìn reads/giây. Tách cache theo thực tế business, giảm payload hoặc dùng edge/CDN cho nội dung phù hợp có thể hiệu quả hơn scale Redis một cách tổng quát.

**Lưu ý:**
Đừng shard một logical key tùy tiện nếu application cần atomic semantics. Trước khi thay đổi topology, xác minh hot-key evidence bằng metrics/slow commands và kiểm tra client-side serialization/network overhead.

### Tip 4 — Playwright test ổn định nhờ chờ trạng thái, không nhờ `Sleep`

**Mẹo:**
Trong E2E test, chờ observable condition như element visible, response hoàn tất hoặc URL/state đạt kỳ vọng; tránh `Task.Delay` cố định để “đợi UI”.

**Tại sao hữu ích:**
Delay 2 giây vừa làm test suite chậm vừa vẫn flaky khi CI chậm hơn 2 giây. Playwright auto-wait và assertions có polling giúp test đồng bộ với behavior thực tế thay vì timing giả định của máy developer.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Saved successfully")).ToBeVisibleAsync();
```
Test xác nhận user-visible outcome thay vì ngủ một khoảng thời gian rồi hy vọng request đã xong.

**Lưu ý:**
Timeout rất dài chỉ che lỗi synchronization. Nếu test vẫn flaky, kiểm tra test-data isolation, animation, background requests và shared environment; đừng tăng timeout trước khi hiểu evidence.

### Tip 5 — `dotnet-counters` dùng để phân loại incident trước khi lấy dump nặng

**Mẹo:**
Khi .NET service có CPU/memory/latency bất thường, bắt đầu bằng runtime counters để phân loại GC pressure, allocation rate, ThreadPool queue và exception activity trước khi thu dump/trace chuyên sâu.

**Tại sao hữu ích:**
Dump là snapshot giàu dữ liệu nhưng tốn thời gian phân tích và có thể lớn. Counters giúp nhanh chóng trả lời “CPU-bound, allocation-heavy hay thread-starved?” để chọn công cụ tiếp theo như `dotnet-trace`, `dotnet-gcdump` hoặc memory dump có chủ đích.

**Ví dụ:**
Nếu memory tăng cùng allocation rate cao và Gen 2 collections dày, hypothesis khác hoàn toàn với trường hợp memory ổn nhưng ThreadPool queue tăng mạnh. Evidence ban đầu giúp tránh debug sai hướng.

**Lưu ý:**
Counters chỉ là aggregate signals, không chỉ ra object/call stack gây vấn đề. Sau khi phân loại, vẫn cần trace/profile/dump và correlation với deployment, traffic, dependency metrics để xác nhận root cause.

## 🧠 Software Design

### Design 1 — Optimistic concurrency bảo vệ invariant mà không giữ lock dài

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor đọc cùng state nhưng khi ghi sẽ kiểm tra version/concurrency token. Nếu state đã thay đổi kể từ lúc đọc, update bị từ chối để application quyết định reload, merge hoặc báo conflict.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng sửa một order có thể tạo lost update: người thứ hai ghi đè thay đổi của người thứ nhất mà không biết. Giữ database lock xuyên thời gian user thao tác UI lại không khả thi.

**Ví dụ thực tế:**
EF Core map SQL Server `rowversion` làm concurrency token. `UPDATE` chứa điều kiện `WHERE Id = @id AND Version = @originalVersion`; nếu affected rows bằng 0, application nhận concurrency conflict và xử lý theo business semantics.

**Trade-off:**
Optimistic concurrency phù hợp khi collision tương đối hiếm; contention cao có thể tạo nhiều retries/conflicts. Auto-retry không phải lúc nào đúng vì hai thay đổi có thể xung đột về business meaning. Pessimistic locking phù hợp hơn cho một số critical section ngắn nhưng tăng blocking/deadlock risk.

**Middle → Senior insight:**
Middle developer cần dùng concurrency token và xử lý conflict thay vì overwrite im lặng. Senior / Technical developer phải xác định invariant nào cần bảo vệ, conflict nào có thể merge/retry, conflict nào phải trả cho user và khi nào contention profile biện minh cho pessimistic coordination.

### Design 2 — Azure Functions và Worker Service khác nhau ở operational model, không chỉ syntax

**Khái niệm:**
Azure Functions cung cấp trigger-driven/serverless execution với platform-managed scaling; Worker Service là long-running process mà team kiểm soát lifecycle, hosting và resource model rõ hơn. Cùng một background task có thể viết được bằng cả hai nhưng operational characteristics khác nhau.

**Vấn đề nó giải quyết:**
Team cần xử lý queue/job nhưng phải chọn giữa elasticity và platform abstraction của Functions với predictability/control của worker. Chọn theo “Functions hiện đại hơn” hoặc “Worker dễ code hơn” bỏ qua execution duration, traffic pattern và deployment/observability requirements.

**Ví dụ thực tế:**
Một event processor bursty, stateless, execution ngắn có thể hợp với Function trigger. Một pipeline xử lý liên tục, cần long-lived connections, controlled concurrency và predictable process lifetime có thể phù hợp Worker Service chạy trên App Service/container/Kubernetes hơn.

**Trade-off:**
Functions giảm infrastructure management và scale theo trigger nhưng có hosting-plan limits, cold-start/scale behavior và platform semantics cần hiểu. Worker tăng operational ownership nhưng cho control rõ hơn về process, concurrency và resource reservation.

**Middle → Senior insight:**
Middle developer cần implement cancellation, idempotency, retries và graceful shutdown đúng với hosting model. Senior / Technical developer phải so sánh workload shape, cost, scaling latency, execution limits, observability và team operational maturity trước khi chọn runtime.

### Design 3 — Abstraction chỉ có giá trị khi che được volatility có thật

**Khái niệm:**
Một abstraction tốt ổn định contract quanh một capability có lý do thay đổi khác implementation. Tạo interface/repository/wrapper chỉ vì “có thể đổi công nghệ sau này” thường không giảm coupling nếu contract vẫn phản chiếu toàn bộ implementation bên dưới.

**Vấn đề nó giải quyết:**
Codebase lớn dễ tích lũy tầng `IOrderRepository -> OrderRepository -> DbContext` chỉ forwarding method, khiến feature cần sửa nhiều file nhưng không tạo business boundary, test seam hữu ích hay portability thực tế.

**Ví dụ thực tế:**
Nếu application query đơn giản và EF Core là data-access boundary đã chấp nhận, dùng `DbContext` trực tiếp trong application handler có thể rõ hơn generic repository. Ngược lại, pricing engine tích hợp vendor ngoài có contract business ổn định đáng có abstraction để cô lập vendor API và failure semantics.

**Trade-off:**
Abstraction đúng chỗ giảm coupling và migration cost; abstraction quá sớm tăng indirection, API surface và maintenance. Không abstraction gì cũng có thể làm vendor/framework concerns lan khắp domain. Chi phí phải được đánh giá theo volatility thực tế, không theo khả năng tưởng tượng.

**Middle → Senior insight:**
Middle developer cần nhận ra interface không tự động tạo loose coupling và tránh wrapper không thêm semantics. Senior / Technical developer phải xác định axis of change, ownership và testing need; chỉ đầu tư abstraction khi boundary đó làm giảm cost của những thay đổi có xác suất hoặc tác động đủ lớn.
