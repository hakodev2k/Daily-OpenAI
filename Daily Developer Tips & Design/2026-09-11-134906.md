# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Khi LOH tăng nhanh, tìm allocation lớn trước khi ép GC

**Mẹo:**
Nếu .NET process tăng memory theo các đợt lớn, kiểm tra allocation của object/array có kích thước lớn và Large Object Heap (LOH) trước khi nghĩ tới việc gọi `GC.Collect()` thủ công.

**Tại sao hữu ích:**
Object lớn được cấp phát trên LOH và việc cấp phát/thu hồi chúng có chi phí khác với object nhỏ. Workload như serialize payload lớn, đọc toàn bộ file vào `byte[]`, tạo `MemoryStream` lớn hoặc buffer ảnh có thể gây allocation pressure và fragmentation dù không có memory leak thực sự.

**Ví dụ:**
```csharp
// Dễ tạo allocation lớn nếu file có kích thước hàng chục MB
var bytes = await File.ReadAllBytesAsync(path, ct);
await blobClient.UploadAsync(new BinaryData(bytes), ct);

// Khi API hỗ trợ streaming, ưu tiên truyền stream
await using var stream = File.OpenRead(path);
await blobClient.UploadAsync(stream, cancellationToken: ct);
```

Khi điều tra, dùng `dotnet-counters`, `dotnet-gcdump`, PerfView hoặc profiler phù hợp để xem allocation rate, GC generation và type nào chiếm phần lớn heap.

**Lưu ý:**
Không chuyển mọi buffer sang `ArrayPool<T>` một cách máy móc. Pooling làm tăng lifecycle complexity và có nguy cơ giữ dữ liệu nhạy cảm trong buffer tái sử dụng. Chỉ tối ưu khi profiling chứng minh allocation là bottleneck.

### Tip 2 — Chuẩn hóa lỗi API bằng `ProblemDetails`, nhưng đừng biến mọi exception thành HTTP 500 giống nhau

**Mẹo:**
Trong ASP.NET Core, dùng `ProblemDetails` làm contract lỗi nhất quán và map từng loại failure sang HTTP semantics phù hợp thay vì trả string tự do hoặc bắt `Exception` rồi luôn trả `500`.

**Tại sao hữu ích:**
Client cần phân biệt validation error, conflict, not found, authentication/authorization failure và lỗi hạ tầng tạm thời. Một error contract ổn định giúp frontend/mobile xử lý lỗi có cấu trúc và làm observability rõ hơn.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();

app.MapPut("/projects/{id}", async (Guid id, UpdateProject request, AppDbContext db) =>
{
    var project = await db.Projects.FindAsync(id);
    if (project is null)
        return Results.NotFound();

    if (project.Version != request.Version)
        return Results.Conflict(new { message = "Project was modified by another request." });

    // update...
    return Results.NoContent();
});
```

Ở application boundary, domain/application exception có thể được map có chủ đích sang `400`, `404`, `409`, `422` hoặc `503` tùy semantics thay vì leak stack trace ra ngoài.

**Lưu ý:**
Không đưa exception message nội bộ, SQL error, connection string, stack trace hoặc secret vào response production. Chi tiết chẩn đoán nên đi vào structured log/trace có correlation ID.

### Tip 3 — Chống cache stampede bằng TTL jitter và request coalescing, không chỉ tăng TTL

**Mẹo:**
Khi nhiều request cùng phụ thuộc một cache key đắt tiền, tránh để tất cả miss cùng lúc. Kết hợp TTL có jitter và cơ chế single-flight/request coalescing để chỉ một request rebuild dữ liệu trong khi các request còn lại chờ hoặc dùng stale value phù hợp.

**Tại sao hữu ích:**
Nếu 5.000 request/giây cùng đọc `catalog:home` và cache hết hạn tại cùng thời điểm, toàn bộ traffic có thể dội xuống SQL/Elasticsearch. Đây là cache stampede: cache vốn để bảo vệ dependency lại tạo load spike đúng lúc key hết hạn.

**Ví dụ:**
```text
Base TTL: 5 phút
Jitter: random 0–45 giây

Miss đầu tiên:
-> acquire per-key refresh gate
-> load dữ liệu từ source
-> populate cache

Các request đồng thời:
-> chờ kết quả refresh
hoặc
-> dùng stale value trong stale-while-revalidate window
```

Với Redis, distributed lock có thể là một phần của giải pháp nhưng phải có timeout, ownership và failure handling rõ ràng.

**Lưu ý:**
Không dùng một global lock cho toàn bộ cache vì sẽ serialize workload không liên quan. Stampede protection nên theo key hoặc nhóm key hợp lý, và stale serving chỉ dùng khi business cho phép dữ liệu cũ trong một khoảng thời gian xác định.

### Tip 4 — Database migration phải tương thích với rolling deployment theo pattern expand-and-contract

**Mẹo:**
Khi production deploy nhiều instance không được thay cùng lúc, thiết kế schema change sao cho version cũ và mới có thể cùng chạy trong một khoảng chuyển tiếp.

**Tại sao hữu ích:**
Trong rolling deployment, có thời điểm pod/node cũ và mới cùng phục vụ traffic. Nếu migration đổi tên/xóa column ngay lập tức nhưng binary cũ vẫn query column đó, deployment có thể fail dù migration và code mới đều đúng khi chạy riêng lẻ.

**Ví dụ:**
```text
Không an toàn:
Release N:
- rename Customer.Name -> DisplayName
- deploy code chỉ dùng DisplayName

Expand-and-contract:
Release N:
- thêm DisplayName nullable
- code mới đọc fallback Name, ghi cả hai
- backfill dữ liệu

Release N+1:
- chuyển toàn bộ read sang DisplayName

Release N+2:
- xóa Name sau khi không còn consumer cũ
```

Pattern này đặc biệt quan trọng khi nhiều service, background worker hoặc job có deployment cadence khác nhau.

**Lưu ý:**
Expand-and-contract làm migration kéo dài hơn và có thể cần dual-write tạm thời. Với thay đổi đơn giản, downtime được chấp nhận và hệ thống nhỏ, chiến lược phức tạp này có thể không cần thiết.

### Tip 5 — Debug CORS bằng preflight request thực tế, đừng chỉ thêm `AllowAnyOrigin`

**Mẹo:**
Khi frontend Vue/React gọi ASP.NET Core API và browser báo CORS, kiểm tra request `OPTIONS` preflight, origin, method và request headers thực tế trước khi nới policy.

**Tại sao hữu ích:**
CORS là cơ chế enforcement của browser. Request có custom header, method như `PUT/DELETE`, hoặc credential có thể kích hoạt preflight. Nếu backend không trả đúng `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods` hoặc `Access-Control-Allow-Headers`, browser sẽ chặn response dù API có thể vẫn chạy bình thường khi gọi từ Postman.

**Ví dụ:**
```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials());
});

app.UseCors("frontend");
```

Trong DevTools Network, kiểm tra `OPTIONS` request trước request thật để thấy chính xác header nào bị từ chối.

**Lưu ý:**
Không thể kết hợp wildcard origin `*` với credential theo semantics chuẩn của CORS. CORS cũng không phải authorization; attacker không cần browser vẫn có thể gọi API nếu endpoint không được bảo vệ bằng authentication/authorization thật sự.

## 🧠 Software Design

### Design 1 — Outbox Pattern giải quyết khoảng trống giữa database commit và message publish

**Khái niệm:**
Outbox Pattern ghi business change và message cần publish vào cùng local database transaction. Một dispatcher riêng sau đó đọc Outbox và gửi message tới broker như Azure Service Bus.

**Vấn đề nó giải quyết:**
Nếu application commit `Order = Paid` rồi publish event sau đó, process có thể crash giữa hai bước. Database đã đúng nhưng event chưa bao giờ được gửi. Nếu publish trước rồi database commit thất bại, consumer lại thấy một event mô tả trạng thái chưa tồn tại.

**Ví dụ thực tế:**
```text
Transaction SQL:
1. UPDATE Orders SET Status = 'Paid'
2. INSERT Outbox(Id, Type, Payload, CreatedAt)
3. COMMIT

Dispatcher:
4. đọc Outbox chưa gửi
5. publish OrderPaid tới Azure Service Bus
6. đánh dấu/ghi thời điểm đã publish
```

Dispatcher phải chấp nhận publish trùng khi crash sau bước 5 nhưng trước bước 6; vì vậy consumer vẫn cần idempotency/Inbox phù hợp.

**Trade-off:**
Outbox loại bỏ dual-write gap giữa database và broker, nhưng thêm bảng, polling/CDC dispatcher, retention, monitoring và eventual delivery delay. Nếu operation không cần message durability hoặc toàn bộ workflow nằm trong một transaction/database, Outbox có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu transaction không thể bao phủ tùy ý SQL database và message broker. Senior / Technical developer phải thiết kế message identity, dispatcher concurrency, retry, ordering, retention, poison handling và observability để Outbox trở thành reliability mechanism thật sự chứ không chỉ là một bảng queue khác.

### Design 2 — Bounded Context bảo vệ ngôn ngữ và model, không phải chỉ chia project theo phòng ban

**Khái niệm:**
Trong Domain-Driven Design, Bounded Context xác định phạm vi mà một domain model và ubiquitous language có nghĩa nhất quán. Cùng một từ có thể có semantics khác nhau ở context khác mà không cần ép thành một entity dùng chung toàn hệ thống.

**Vấn đề nó giải quyết:**
Enterprise system thường tạo một `Customer`, `User` hoặc `Product` model khổng lồ dùng cho mọi module. Theo thời gian, entity này tích tụ field và rule từ billing, identity, CRM, support và commerce, tạo coupling mà không context nào sở hữu rõ.

**Ví dụ thực tế:**
```text
Identity context:
User
- LoginId
- MFA status
- AccountState

Billing context:
CustomerAccount
- BillingName
- TaxId
- PaymentTerms

Commerce context:
Buyer
- ShippingPreferences
- LoyaltyTier
```

Các context có thể tham chiếu nhau bằng ID và contract/event rõ ràng thay vì chia sẻ một object graph duy nhất.

**Trade-off:**
Bounded Context tăng autonomy và làm model tập trung hơn, nhưng tạo mapping, integration contract và duplicated representation. Chia quá nhỏ sẽ tạo distributed complexity và nhiều translation layer không đáng giá.

**Middle → Senior insight:**
Middle developer cần nhận ra cùng một business term không mặc định có cùng model ở mọi nơi. Senior / Technical developer phải tìm boundary dựa trên invariant, language, ownership, change cadence và transaction need; org chart chỉ là tín hiệu tham khảo chứ không phải boundary tự động.

### Design 3 — Architecture Decision Record giúp giữ lại “vì sao”, không chỉ “đã chọn gì”

**Khái niệm:**
Architecture Decision Record (ADR) là tài liệu ngắn ghi context, decision, alternatives và consequences của một quyết định kỹ thuật có ảnh hưởng đáng kể.

**Vấn đề nó giải quyết:**
Sau vài tháng, team thường chỉ còn code hoặc diagram thể hiện trạng thái hiện tại nhưng mất lý do tại sao đã chọn SQL thay vì Cosmos DB, Modular Monolith thay vì Microservices, hay direct Blob upload thay vì proxy qua API. Khi context mất, team dễ đảo quyết định cũ hoặc lặp lại tranh luận mà không biết constraint ban đầu.

**Ví dụ thực tế:**
```text
ADR-014: Store uploaded documents in Azure Blob Storage

Context:
- file 10 MB–2 GB
- API instances cần scale stateless
- download traffic cao

Decision:
- Blob Storage là binary source of truth
- SQL chỉ lưu metadata
- client upload bằng short-lived SAS

Consequences:
+ giảm bandwidth qua API
+ scale storage độc lập
- phải xử lý orphan upload
- cần malware scanning workflow
```

ADR tốt nên có status như Proposed / Accepted / Superseded và liên kết quyết định mới khi context thay đổi.

**Trade-off:**
ADR tăng traceability và onboarding quality nhưng sẽ trở thành documentation debt nếu mọi quyết định nhỏ đều bị ghi hoặc tài liệu không bao giờ được cập nhật/supersede. Chỉ ghi những quyết định có trade-off đáng kể hoặc khó đảo ngược.

**Middle → Senior insight:**
Middle developer nên học cách mô tả constraint và consequence thay vì chỉ đề xuất công nghệ. Senior / Technical / Solution-oriented engineer phải biến decision-making thành tài sản của team: nêu rõ assumptions, alternatives, operational impact, migration cost và điều kiện khiến quyết định cần được xem xét lại.
