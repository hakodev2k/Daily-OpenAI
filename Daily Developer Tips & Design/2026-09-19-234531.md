# Daily Developer Tips & Design — 2026-09-19

## 🛠 Developer Tips & Tricks

### Tip 1 — `TimeProvider` giúp test logic thời gian mà không cần sleep

**Mẹo:**
Với .NET hiện đại, inject `TimeProvider` cho code phụ thuộc thời gian thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi. Trong test có thể dùng clock kiểm soát được để tiến thời gian deterministically.

**Tại sao hữu ích:**
Logic expiration, retry window, scheduled behavior và cache freshness rất dễ tạo flaky test nếu phụ thuộc đồng hồ thật. Tách nguồn thời gian biến thời gian thành dependency có thể kiểm soát và làm test chạy nhanh.

**Ví dụ:**
Một service xác định token nội bộ đã hết hạn bằng `timeProvider.GetUtcNow()`. Test đặt thời điểm ban đầu, tiến clock qua expiration boundary rồi assert behavior mà không `Task.Delay` vài giây.

**Lưu ý:**
Không cần abstract mọi API hệ thống chỉ vì testability. Dùng abstraction chuẩn như `TimeProvider` ở nơi business behavior thực sự phụ thuộc thời gian; vẫn phải thống nhất UTC, timezone và DST semantics.

### Tip 2 — EF Core `SaveChanges` batching không loại bỏ nhu cầu bulk strategy

**Mẹo:**
Khi ghi hàng chục nghìn records, đo generated commands, round trips và transaction duration thay vì giả định `AddRange` + một lần `SaveChangesAsync` đồng nghĩa với một bulk insert.

**Tại sao hữu ích:**
EF Core có batching nhưng vẫn phải track entities và tạo commands. Với ingestion lớn, change tracking, parameter count và transaction duration có thể trở thành bottleneck trước database throughput.

**Ví dụ:**
Import 100.000 product rows: benchmark normal EF batching với provider-native bulk/copy strategy trên dữ liệu đại diện, đồng thời kiểm tra validation, transaction và error-recovery requirement trước khi chọn.

**Lưu ý:**
Bulk path thường bỏ qua một số behavior của normal entity lifecycle. Đừng đổi sang bulk chỉ vì số rows “trông lớn”; complexity, portability và correctness cũng là chi phí.

### Tip 3 — PostgreSQL `EXPLAIN ANALYZE` cần đọc cả rows và loops

**Mẹo:**
Khi phân tích slow query, đừng chỉ nhìn node có thời gian lớn nhất. Đọc `actual rows`, `loops` và so sánh estimated rows với actual rows để hiểu work thực sự bị nhân ở đâu.

**Tại sao hữu ích:**
Một inner node chỉ mất 1 ms nhưng chạy 20.000 loops có thể đóng góp phần lớn latency. Cardinality estimate sai còn dẫn optimizer chọn join strategy phù hợp với tập nhỏ nhưng tệ với dữ liệu thực.

**Ví dụ:**
Nested Loop hiển thị inner index lookup nhanh nhưng `loops=50000`. Điều tra tiếp selectivity, join predicate, statistics và query shape trước khi kết luận index lookup là tối ưu chỉ vì mỗi lần chạy rẻ.

**Lưu ý:**
`EXPLAIN ANALYZE` thực thi query. Với write query hoặc production workload nhạy cảm, dùng môi trường an toàn hoặc phương án quan sát phù hợp; đừng chạy tùy tiện trên operation có side effect lớn.

### Tip 4 — Kubernetes rolling update cần capacity cho cả old và new Pods

**Mẹo:**
Khi cấu hình rolling deployment, đánh giá `maxSurge`, `maxUnavailable`, resource requests và cluster headroom cùng nhau; deployment strategy không thể tạo capacity vật lý nếu cluster đã đầy.

**Tại sao hữu ích:**
Một rollout có `maxUnavailable: 0` cần tạo Pod mới trước khi bỏ Pod cũ. Nếu scheduler không còn CPU/memory phù hợp, rollout có thể đứng dù manifest và application đều đúng.

**Ví dụ:**
API chạy 10 Pods, mỗi Pod request 1 CPU và cluster gần đầy. Rollout cần surge thêm Pods nhưng chúng ở Pending. Evidence từ scheduler events cho thấy insufficient CPU, không phải readiness bug trong application.

**Lưu ý:**
Tăng `maxSurge` không luôn làm deploy nhanh hơn. Nó có thể tăng tải database/downstream và cần thêm cluster capacity; rollout parameters phải phù hợp cả application lẫn infrastructure.

### Tip 5 — XSS defense bắt đầu từ output encoding, không từ regex lọc HTML

**Mẹo:**
Trong frontend/CMS, mặc định render user-controlled data dưới dạng text để framework thực hiện escaping; chỉ render raw HTML khi có requirement rõ và sanitizer đáng tin cậy.

**Tại sao hữu ích:**
Blacklist script tags bằng regex bỏ sót nhiều execution contexts như attributes, URLs hoặc malformed markup. Context-aware output encoding làm dữ liệu được hiểu là dữ liệu thay vì executable markup.

**Ví dụ:**
Comment của user nên bind như text. Nếu CMS cho phép rich text, sanitize theo allowlist ở trust boundary và vẫn áp dụng Content Security Policy như lớp defense-in-depth phù hợp.

**Lưu ý:**
CSP không thay thế encoding/sanitization. Đồng thời tránh bypass API như `dangerouslySetInnerHTML` hoặc tương đương chỉ để hiển thị nội dung thông thường.

## 🧠 Software Design

### Design 1 — Repository abstraction chỉ khi nó tạo boundary có giá trị

**Khái niệm:**
Repository abstraction nên che một data-access boundary có semantics hữu ích cho application/domain, không đơn giản sao chép toàn bộ `DbSet` thành `GetAll`, `Add`, `Update`, `Delete` generic.

**Vấn đề nó giải quyết:**
Data access phức tạp, nhiều sources hoặc domain cần contract ổn định có thể hưởng lợi từ repository. Nhưng wrapper mỏng quanh EF Core thường làm mất `IQueryable` capability, tăng boilerplate và che behavior của ORM mà không giảm coupling thực sự.

**Ví dụ thực tế:**
`IOrderRepository.LoadForFulfillmentAsync(orderId)` có thể encapsulate aggregate-loading rule quan trọng. Ngược lại `IGenericRepository<T>.GetAll()` cho mọi entity thường chỉ tạo một API kém biểu đạt hơn `DbContext`.

**Trade-off:**
Repository có thể làm boundary/test seams rõ hơn nhưng thêm abstraction, mapping và nguy cơ lowest-common-denominator API. Direct `DbContext` đơn giản hơn nhưng application layer phải giữ query/data-access discipline.

**Middle → Senior insight:**
Middle developer cần hiểu EF Core đã cung cấp Unit of Work/change tracking semantics. Senior / Technical developer phải quyết định abstraction dựa trên domain boundary, test strategy và volatility thay vì áp pattern theo template.

### Design 2 — Queue hay Topic phụ thuộc delivery topology, không phụ thuộc tên event

**Khái niệm:**
Queue phù hợp khi một logical work item cần một competing consumer xử lý; Topic + subscriptions phù hợp khi cùng message cần được phân phối độc lập tới nhiều consumer groups.

**Vấn đề nó giải quyết:**
Chọn sai topology có thể làm nhiều consumers tranh nhau một message đáng lẽ tất cả phải nhận, hoặc ngược lại nhân bản processing không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command/work item có thể đi vào queue cho một nhóm workers. `OrderCompleted` có thể publish topic để Billing, Analytics và Notification có subscription, retry và DLQ riêng.

**Trade-off:**
Topic tăng extensibility và isolation giữa subscribers nhưng thêm subscriptions, filters, monitoring và duplicate-delivery concerns. Queue đơn giản hơn khi chỉ có một processing responsibility.

**Middle → Senior insight:**
Middle developer cần phân biệt competing consumers với fan-out. Senior / Technical developer phải thiết kế topology theo ownership, failure isolation, ordering, replay và throughput chứ không chọn Topic chỉ vì message được gọi là event.

### Design 3 — Expand-and-Contract cho schema change không downtime

**Khái niệm:**
Expand-and-Contract chia breaking schema change thành các bước tương thích: thêm cấu trúc mới trước, migrate/dual-read hoặc dual-write khi cần, chuyển consumers, rồi mới loại bỏ cấu trúc cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment, version cũ và mới có thể chạy đồng thời. Rename/drop column trong một bước có thể làm một version lỗi dù migration tự nó thành công.

**Ví dụ thực tế:**
Muốn đổi `CustomerName` thành cấu trúc tên mới: thêm columns mới nullable, deploy code có thể đọc cả hai, backfill dữ liệu, chuyển write/read sang schema mới, xác nhận telemetry rồi drop column cũ ở release sau.

**Trade-off:**
Cách này giảm deployment coupling và downtime nhưng kéo dài migration, tăng temporary code/schema complexity và cần cleanup discipline. Với hệ thống nhỏ có maintenance window thật sự, migration một bước có thể hợp lý hơn.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible với version đang chạy. Senior / Technical developer phải lập sequence giữa database/application versions, backfill capacity, rollback semantics và thời điểm contract an toàn.
