# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán ThreadPool starvation bằng `dotnet-counters` trước khi tăng số thread

**Mẹo:**
Khi ASP.NET Core có latency tăng mạnh nhưng CPU chưa cao, kiểm tra `ThreadPool Queue Length`, `ThreadPool Thread Count` và request rate bằng `dotnet-counters` trước khi kết luận database hoặc network chậm.

**Tại sao hữu ích:**
ThreadPool starvation xảy ra khi nhiều worker thread bị block bởi synchronous I/O, `.Result`, `.Wait()` hoặc work kéo dài. Request mới phải xếp hàng dù máy vẫn còn CPU, nên triệu chứng thường là p95/p99 tăng, timeout xuất hiện và thread count tăng dần.

**Ví dụ:**
```bash
dotnet-counters monitor \
  --process-id 1234 \
  System.Runtime Microsoft.AspNetCore.Hosting
```

Nếu queue length tăng liên tục trong khi CPU vừa phải, hãy tìm synchronous wait trong hot path bằng trace/profiler thay vì chỉ tăng concurrency.

**Lưu ý:**
ThreadPool starvation khác CPU saturation. Tăng `MinThreads` có thể giảm symptom tạm thời nhưng cũng làm tăng contention và không sửa nguyên nhân như blocking I/O hoặc sync-over-async.

### Tip 2 — Persist ASP.NET Core Data Protection keys khi chạy nhiều instance

**Mẹo:**
Nếu ứng dụng dùng cookie authentication, antiforgery token hoặc Data Protection API trên nhiều App Service instance/container, lưu key ring ở shared durable storage và bảo vệ key phù hợp thay vì để mỗi instance tự sinh key cục bộ.

**Tại sao hữu ích:**
Cookie được mã hóa bởi instance A phải giải mã được ở instance B. Nếu key ring không được chia sẻ hoặc bị mất sau restart/deployment, user có thể bị logout ngẫu nhiên, antiforgery validation fail hoặc token cũ trở nên không đọc được.

**Ví dụ:**
```csharp
builder.Services
    .AddDataProtection()
    .PersistKeysToAzureBlobStorage(blobClient)
    .ProtectKeysWithAzureKeyVault(keyIdentifier, credential)
    .SetApplicationName("CustomerPortal");
```

`SetApplicationName` giúp các instance thuộc cùng application dùng chung discriminator khi cần interoperable key ring.

**Lưu ý:**
Đừng chia sẻ cùng key ring giữa các ứng dụng không cần trust nhau. Quyền truy cập Blob/Key Vault nên dùng Managed Identity và least privilege; mất key ring có thể khiến dữ liệu đã protect không thể phục hồi.

### Tip 3 — Dùng partial index trong PostgreSQL khi workload chỉ truy cập một tập con nhỏ

**Mẹo:**
Nếu phần lớn query chỉ tìm các row có một trạng thái hiếm như `Pending` hoặc `IsDeleted = false`, cân nhắc partial index thay vì index toàn bảng.

**Tại sao hữu ích:**
Partial index chỉ chứa row thỏa predicate nên nhỏ hơn, ít tốn write amplification và có thể cache tốt hơn. Nó đặc biệt hữu ích khi tập row “active” nhỏ hơn nhiều so với lịch sử đã hoàn tất.

**Ví dụ:**
```sql
CREATE INDEX idx_jobs_pending_created_at
ON jobs (created_at)
WHERE status = 'Pending';

SELECT id, created_at
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

Kiểm tra bằng `EXPLAIN (ANALYZE, BUFFERS)` để xác nhận planner thực sự dùng index và số buffer read giảm.

**Lưu ý:**
Predicate của query phải tương thích với predicate của index. Nếu trạng thái phân bố không còn selective hoặc workload thay đổi, partial index có thể mất giá trị; luôn cân nhắc chi phí duy trì index trên write path.

### Tip 4 — Hủy request frontend cũ bằng `AbortController` để tránh stale response ghi đè state mới

**Mẹo:**
Trong Vue/React search-as-you-type hoặc filter động, cancel HTTP request cũ khi input thay đổi thay vì chỉ gửi request mới và chờ response.

**Tại sao hữu ích:**
Network response không đảm bảo trả về đúng thứ tự gửi. Request cho từ khóa cũ có thể hoàn thành sau request mới và ghi đè state bằng dữ liệu stale, tạo bug khó tái hiện trên local network nhanh.

**Ví dụ:**
```ts
let controller: AbortController | undefined

async function search(term: string) {
  controller?.abort()
  controller = new AbortController()

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  })

  if (response.ok) {
    results.value = await response.json()
  }
}
```

Có thể kết hợp debounce để giảm request rate và cancellation để bảo đảm response cũ không còn tác động.

**Lưu ý:**
Cancellation phía browser không đảm bảo backend đã dừng work; server cũng phải propagate `CancellationToken` nếu muốn giảm tài nguyên thực sự. Đồng thời xử lý `AbortError` riêng để không log cancellation hợp lệ như production error.

### Tip 5 — Chống Redis cache stampede bằng single-flight và TTL jitter

**Mẹo:**
Với key nóng, khi cache miss xảy ra đừng để hàng trăm request cùng truy vấn database rồi cùng ghi cache. Dùng cơ chế single-flight/per-key lock ngắn hạn và thêm jitter vào TTL để tránh nhiều key hết hạn cùng lúc.

**Tại sao hữu ích:**
Cache stampede biến một cache miss thành traffic spike xuống dependency gốc. Nếu nhiều key có cùng TTL tuyệt đối, sự kiện deploy hoặc warm-up có thể làm hàng loạt key expire cùng thời điểm và tạo thundering herd.

**Ví dụ:**
```text
TTL cơ bản: 10 phút
TTL thực tế: 10 phút + random(0..90 giây)

Cache miss cho product:42
-> request đầu tiên load DB
-> các request còn lại chờ cùng computation
-> chỉ một lần ghi Redis
```

Trong một process có thể dùng single-flight local; trên nhiều instance cần cân nhắc distributed coordination hoặc stale-while-revalidate tùy consistency requirement.

**Lưu ý:**
Distributed lock có failure mode riêng và không nên giữ lâu hơn thời gian fetch dữ liệu dự kiến. Với dữ liệu không critical, phục vụ stale data ngắn hạn đôi khi đơn giản và resilient hơn khóa phân tán.

## 🧠 Software Design

### Design 1 — Anti-Corruption Layer bảo vệ domain khỏi model của hệ thống bên ngoài

**Khái niệm:**
Anti-Corruption Layer (ACL) chuyển đổi contract, terminology và behavior của external system thành model mà application của bạn hiểu, thay vì để DTO/vendor SDK lan trực tiếp vào domain/application layer.

**Vấn đề nó giải quyết:**
CMS, payment provider hoặc legacy ERP thường có naming, trạng thái và lifecycle khác domain hiện tại. Nếu code nghiệp vụ phụ thuộc trực tiếp các type đó, thay provider hoặc nâng version sẽ kéo thay đổi xuyên toàn hệ thống.

**Ví dụ thực tế:**
```text
External CMS:
ContentStatus = "PUBLISHED_LIVE"

Application domain:
DocumentState.Published

CmsContentAdapter
-> gọi SDK
-> map external contract
-> chuẩn hóa lỗi/retry semantics
-> trả model nội bộ
```

ACL đặc biệt hữu ích khi external model phức tạp hoặc có semantics không nên trở thành ngôn ngữ chung của domain.

**Trade-off:**
ACL giảm coupling và cô lập thay đổi provider, nhưng thêm mapping, code và test. Nếu integration rất nhỏ, contract ổn định và không ảnh hưởng business model, một wrapper mỏng có thể đủ.

**Middle → Senior insight:**
Middle developer cần tránh leak vendor-specific DTO vào business logic và viết mapping rõ ràng. Senior / Technical developer phải quyết định boundary nào đáng có ACL, mức abstraction cần thiết và chi phí migration nếu external system thay đổi.

### Design 2 — Transactional Outbox khi database commit và message publish phải nhất quán

**Khái niệm:**
Transactional Outbox ghi business change và message cần publish vào cùng một database transaction. Một dispatcher riêng sau đó đọc outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application `COMMIT` database rồi publish Service Bus message, process có thể crash ở giữa: dữ liệu đã lưu nhưng event không bao giờ được gửi. Nếu publish trước rồi database rollback, consumer lại nhận event cho state chưa tồn tại.

**Ví dụ thực tế:**
```text
Transaction:
1. UPDATE Order SET Status = 'Paid'
2. INSERT Outbox(Id, Type='OrderPaid', Payload=...)
3. COMMIT

Dispatcher:
4. đọc Outbox chưa gửi
5. publish Azure Service Bus
6. đánh dấu đã xử lý
```

Consumer vẫn cần idempotency vì dispatcher có thể publish lại sau crash hoặc timeout.

**Trade-off:**
Outbox loại bỏ dual-write gap nhưng thêm table growth, dispatcher, retry, cleanup và eventual delay. Nếu mọi side effect nằm trong cùng database transaction, pattern này có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu tại sao database transaction không bao phủ message broker và triển khai dispatcher/idempotency đúng. Senior / Technical developer phải chọn delivery semantics, polling/CDC strategy, retention và observability dựa trên throughput và business criticality.

### Design 3 — Expand-and-Contract cho schema migration không downtime

**Khái niệm:**
Expand-and-Contract chia breaking database change thành các bước backward-compatible: mở rộng schema trước, deploy code tương thích cả cũ/mới, migrate dữ liệu rồi mới xóa contract cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment, version cũ và mới của application có thể chạy đồng thời. Rename/drop column trực tiếp có thể làm một nửa instance lỗi ngay cả khi migration và deploy đều “thành công” riêng lẻ.

**Ví dụ thực tế:**
```text
Mục tiêu: đổi Customer.Name -> DisplayName

1. Expand: thêm DisplayName nullable
2. App mới đọc DisplayName fallback Name
3. Dual-write hoặc backfill dữ liệu
4. Xác nhận toàn bộ instance/version đã chuyển
5. Contract: ngừng dùng Name rồi drop ở release sau
```

Cùng nguyên tắc áp dụng cho event schema và API contract khi cần migration nhiều bước.

**Trade-off:**
Cách này giảm deployment risk và hỗ trợ rollback tốt hơn, nhưng tạm thời tồn tại duplicate field/code path và cần discipline để hoàn tất bước cleanup. Với hệ thống nhỏ có maintenance window thật sự, migration trực tiếp có thể đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible và hiểu phiên bản app cũ vẫn có thể chạy. Senior / Technical developer phải thiết kế sequence, data backfill, rollback window, observability và tiêu chí xóa compatibility code theo deployment topology thực tế.
