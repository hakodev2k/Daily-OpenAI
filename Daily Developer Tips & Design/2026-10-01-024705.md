# Daily Developer Tips & Design — 2026-10-01

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `ValueTask` như một `Task` “nhanh hơn”

**Mẹo:**
Chỉ cân nhắc `ValueTask<T>` trên hot path khi operation thường hoàn thành đồng bộ và profiling cho thấy allocation của `Task<T>` đáng kể. Với API thông thường, `Task<T>` vẫn là lựa chọn mặc định đơn giản và an toàn hơn.

**Tại sao hữu ích:**
`ValueTask<T>` có thể tránh allocation khi kết quả có sẵn đồng bộ, nhưng nó là struct lớn hơn và có semantics sử dụng phức tạp hơn. Một `ValueTask` backed bởi `IValueTaskSource` thường chỉ được await một lần; cache hoặc await nhiều lần có thể gây lỗi khó đoán.

**Ví dụ:**
```csharp
public ValueTask<User?> FindCachedAsync(Guid id, CancellationToken ct)
{
    if (_memoryCache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id, ct));
}
```
Pattern này hợp lý khi cache hit rất cao và method nằm trên hot path đã được đo bằng profiler/benchmark.

**Lưu ý:**
Đừng đổi hàng loạt `Task<T>` thành `ValueTask<T>` chỉ để giảm allocation trên lý thuyết. Nếu caller cần lưu task, await nhiều lần hoặc dùng combinator như `Task.WhenAll`, `Task<T>` thường dễ dùng hơn.

### Tip 2 — Điều tra SQL deadlock bằng wait graph, không tăng timeout

**Mẹo:**
Khi SQL Server báo deadlock, lấy deadlock graph và xác định transaction nào giữ resource nào, đang chờ resource nào, cùng thứ tự truy cập bảng/index của các transaction cạnh tranh.

**Tại sao hữu ích:**
Deadlock là chu trình chờ, không phải đơn thuần là query chạy lâu. Tăng command timeout không phá chu trình; SQL Server vẫn phải chọn một victim. Root cause thường nằm ở transaction quá rộng, thứ tự lock không nhất quán, access path kém hoặc isolation behavior không phù hợp.

**Ví dụ:**
```text
Tx A: UPDATE Orders   -> chờ OrderItems
Tx B: UPDATE OrderItems -> chờ Orders
```
Nếu hai code path luôn lấy resource theo cùng thứ tự `Orders -> OrderItems`, chu trình có thể biến mất. Sau đó kiểm tra execution plan/index để giảm số rows bị lock.

**Lưu ý:**
Retry deadlock victim là hữu ích vì deadlock thường transient, nhưng retry chỉ là lớp resilience. Nếu deadlock lặp lại thường xuyên, phải sửa transaction/access pattern; retry không thay thế root-cause analysis.

### Tip 3 — Dùng distributed tracing để tìm dependency làm tăng tail latency

**Mẹo:**
Khi API p50 vẫn ổn nhưng p95/p99 tăng, dùng correlation/trace ID và dependency spans trong Application Insights hoặc OpenTelemetry để xem request chậm đang tiêu thời gian ở SQL, HTTP, Redis hay internal processing.

**Tại sao hữu ích:**
Average latency dễ che một nhóm request rất chậm. Trace giữ quan hệ parent-child giữa request và dependencies, giúp chuyển từ “endpoint chậm” sang evidence cụ thể về dependency, retry hoặc đoạn xử lý tạo tail latency.

**Ví dụ:**
```text
GET /checkout             2.8s
 ├─ SQL Orders              35ms
 ├─ Redis                   4ms
 └─ POST Payment API      2.65s
      ├─ attempt 1        timeout
      └─ attempt 2         420ms
```
Từ trace này, ưu tiên điều tra timeout/retry budget của Payment API thay vì tối ưu SQL 35 ms.

**Lưu ý:**
Sampling có thể làm mất trace hiếm nhưng quan trọng; telemetry cũng cần tránh ghi token, PII hoặc payload nhạy cảm. Correlation tốt không thay thế metrics để phát hiện xu hướng toàn hệ thống.

### Tip 4 — File upload phải kiểm tra nội dung và storage boundary, không chỉ extension

**Mẹo:**
Với ASP.NET Core upload endpoint, coi filename, MIME type và extension từ client là untrusted. Giới hạn kích thước, sinh server-side filename, kiểm tra loại nội dung theo yêu cầu nghiệp vụ và lưu file ngoài executable/web root khi không cần public trực tiếp.

**Tại sao hữu ích:**
Client có thể gửi `invoice.pdf.exe` hoặc khai `Content-Type: application/pdf` cho dữ liệu khác. Dùng filename gốc còn tạo nguy cơ path traversal, collision hoặc unsafe content được phục vụ lại dưới cùng origin.

**Ví dụ:**
```csharp
var safeName = $"{Guid.NewGuid():N}.bin";
await using var stream = blobClient.OpenWrite(overwrite: false);
await file.CopyToAsync(stream, ct);
```
Metadata gốc có thể lưu riêng sau khi sanitize; Blob Storage nên được truy cập bằng Managed Identity và policy phù hợp thay vì biến upload directory thành executable content.

**Lưu ý:**
Magic-byte checking không phải antivirus và không chứng minh file an toàn. Với file từ user có rủi ro cao, cần malware scanning/quarantine flow phù hợp; đồng thời chống decompression bomb và giới hạn request trước khi buffer toàn bộ vào memory.

### Tip 5 — Playwright: chờ trạng thái nghiệp vụ, đừng chèn `WaitForTimeout`

**Mẹo:**
Trong end-to-end test, chờ element, response hoặc trạng thái UI có ý nghĩa thay vì ngủ cố định vài giây bằng `WaitForTimeout`.

**Tại sao hữu ích:**
Fixed sleep vừa làm test chậm vừa flaky: CI nhanh thì lãng phí thời gian, CI chậm thì timeout vẫn chưa đủ. Playwright auto-wait và assertions có retry cho phép test đồng bộ theo trạng thái thực của ứng dụng.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Saved successfully")).ToBeVisibleAsync();
```
Nếu cần kiểm tra backend call, chờ response/event có điều kiện rõ ràng thay vì đoán thời gian xử lý.

**Lưu ý:**
Đừng biến E2E thành nơi kiểm tra mọi branch nghiệp vụ; chúng đắt và dễ chịu ảnh hưởng môi trường. Giữ phần lớn logic ở unit/integration tests và dùng E2E cho critical user journeys cùng integration boundaries quan trọng.

## 🧠 Software Design

### Design 1 — Backward-compatible API evolution trước khi nghĩ đến version mới

**Khái niệm:**
API evolution nên ưu tiên additive changes và contract compatibility khi có thể. API version mới chỉ cần thiết khi semantics hoặc contract buộc phải breaking; versioning không nên là phản xạ cho mọi thay đổi.

**Vấn đề nó giải quyết:**
Mobile app, CMS frontend hoặc third-party consumer có thể deploy theo lịch khác backend. Nếu server đổi tên field, đổi meaning hoặc loại bỏ enum value đột ngột, consumer cũ có thể hỏng ngay cả khi backend deployment thành công.

**Ví dụ thực tế:**
API hiện trả `status: "Pending"`. Requirement mới cần thêm `paymentStatus`. Thêm field mới thường backward-compatible; đổi `status` thành object mới có thể phá consumer. Team có thể chạy contract cũ song song, đo usage rồi mới sunset khi consumer đã migrate.

**Trade-off:**
Giữ compatibility giảm release coupling nhưng làm contract tồn tại lâu hơn và có thể tích lũy compatibility code. Tạo `v2` cho mọi thay đổi làm routing, documentation, testing và deprecation phức tạp; ngược lại, cố giữ một version bằng mọi giá có thể làm model méo mó.

**Middle → Senior insight:**
Middle cần biết additive vs breaking change, OpenAPI contract và test consumer behavior. Senior / Technical phải quyết định khi nào compatibility shim còn rẻ hơn version mới, xác định deprecation window, telemetry về consumer usage, migration path và ownership của việc loại bỏ contract cũ.

### Design 2 — Cache-aside phải có consistency model rõ ràng

**Khái niệm:**
Cache-aside không chỉ là “đọc Redis trước, miss thì đọc database”. Thiết kế phải xác định source of truth, thứ tự update/invalidate, acceptable staleness và behavior khi cache unavailable.

**Vấn đề nó giải quyết:**
Cache giảm database load và latency nhưng tạo thêm một bản sao dữ liệu. Race giữa database write và cache invalidation có thể làm dữ liệu cũ sống lại; Redis outage cũng có thể đẩy toàn bộ traffic xuống database cùng lúc.

**Ví dụ thực tế:**
Product price được đọc rất nhiều nhưng update ít. Database là source of truth; sau update, service invalidate cache. Reader miss thì reload. Nếu business cho phép stale vài giây, TTL là safety net. Với giá dùng để charge tiền, checkout vẫn phải xác nhận authoritative value thay vì tin cache hiển thị.

**Trade-off:**
Cache-aside đơn giản và hiệu quả cho read-heavy workload nhưng thêm stale-data window, stampede risk và operational dependency. Không cache có latency cao hơn nhưng consistency/operations đơn giản hơn; đôi khi tối ưu query/index là đủ và Redis chỉ làm hệ thống phức tạp.

**Middle → Senior insight:**
Middle cần implement TTL, serialization, failure fallback và invalidation đúng. Senior phải định nghĩa freshness SLA theo từng use case, failure mode khi Redis chết, database protection, hot-key strategy và nơi cache tuyệt đối không được quyết định invariant nghiệp vụ.

### Design 3 — Transaction boundary nên theo business invariant, không theo số repository call

**Khái niệm:**
Một transaction nên bao phủ những thay đổi phải cùng thành công hoặc cùng thất bại để giữ invariant trong cùng consistency boundary. Không nên mở transaction rộng chỉ vì một use case gọi nhiều repositories, cũng không nên commit từng repository riêng nếu business state cần atomicity.

**Vấn đề nó giải quyết:**
Transaction quá nhỏ có thể để lại partial state; transaction quá rộng giữ lock lâu, tăng contention và dễ kéo network call vào database transaction. Trong distributed system, cố kéo nhiều service vào một ACID transaction thường làm coupling và failure handling tệ hơn.

**Ví dụ thực tế:**
Tạo Order và OrderItems trong cùng SQL database cần một transaction vì order không được tồn tại ở trạng thái thiếu lines. Gửi email hoặc gọi shipping service không nên nằm trong transaction đó; commit local state trước rồi dùng Outbox/asynchronous workflow nếu reliability requirement cần.

**Trade-off:**
Transaction local rõ ràng giữ invariant mạnh và rollback đơn giản nhưng boundary rộng làm tăng lock duration. Chia nhỏ boundary cải thiện isolation/scalability nhưng có thể cần eventual consistency, compensation và observability phức tạp hơn.

**Middle → Senior insight:**
Middle cần nhận diện các write phải atomic và quản lý `DbContext`/transaction lifecycle đúng. Senior / Technical phải xác định invariant thuộc aggregate/service nào, loại external I/O khỏi transaction khi phù hợp, đánh giá isolation/contention và chọn eventual consistency có chủ đích khi vượt qua local transaction boundary.
