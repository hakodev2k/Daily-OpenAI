# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `async/await` đúng cách để tránh thread blocking

**Mẹo:**
Tránh sử dụng `.Result` hoặc `.Wait()` trong code async, thay vào đó hãy duy trì async flow từ controller đến service.

**Tại sao hữu ích:**
Giảm nguy cơ deadlock, thread starvation và cải thiện khả năng xử lý nhiều request đồng thời.

**Ví dụ:**
```csharp
public async Task<UserDto> GetUserAsync(int id)
{
    return await repository.GetAsync(id);
}
```

**Lưu ý:**
Không phải mọi method đều cần async; tránh biến các thao tác CPU đơn giản thành async không cần thiết.

### Tip 2 — Sử dụng `AsNoTracking()` trong EF Core cho query chỉ đọc

**Mẹo:**
Khi lấy dữ liệu chỉ để hiển thị hoặc báo cáo, dùng `AsNoTracking()` để bỏ qua change tracking.

**Tại sao hữu ích:**
Giảm memory usage và tăng performance cho các query đọc nhiều dữ liệu.

**Ví dụ:**
```csharp
var users = await db.Users
    .AsNoTracking()
    .Where(x => x.IsActive)
    .ToListAsync();
```

**Lưu ý:**
Không dùng khi entity cần được update và lưu lại qua cùng DbContext.

### Tip 3 — Dùng structured logging thay vì nối chuỗi log

**Mẹo:**
Truyền parameter trực tiếp vào logging framework thay vì string interpolation.

**Tại sao hữu ích:**
Giúp hệ thống log có thể search, filter và phân tích tốt hơn trong production.

**Ví dụ:**
```csharp
_logger.LogInformation("User {UserId} logged in", userId);
```

**Lưu ý:**
Không ghi dữ liệu nhạy cảm như password, token hoặc thông tin cá nhân vào log.

### Tip 4 — Dùng Docker multi-stage build để giảm image size

**Mẹo:**
Tách bước build và runtime trong Dockerfile để chỉ giữ artifact cần thiết.

**Tại sao hữu ích:**
Image nhỏ hơn giúp deploy nhanh hơn, giảm attack surface và tiết kiệm storage.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0
COPY --from=build /app .
```

**Lưu ý:**
Không copy toàn bộ source code vào runtime image nếu application không cần.

### Tip 5 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Khi bug xuất hiện trong lịch sử phát triển dài, dùng binary search thay vì kiểm tra từng commit.

**Tại sao hữu ích:**
Giảm đáng kể thời gian tìm regression trong repository lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.0.0
```

**Lưu ý:**
Cần có test hoặc cách xác định rõ commit hiện tại là good/bad.

## 🧠 Software Design

### Design 1 — Dependency Inversion Principle (DIP) trong kiến trúc ứng dụng

**Khái niệm:**
DIP yêu cầu module cấp cao không phụ thuộc trực tiếp vào module cấp thấp mà phụ thuộc vào abstraction.

**Vấn đề nó giải quyết:**
Giảm coupling giữa business logic và infrastructure như database, API provider hoặc message broker.

**Ví dụ thực tế:**
Order service sử dụng `IPaymentGateway` thay vì gọi trực tiếp Stripe API. Khi đổi provider, domain logic không cần thay đổi.

**Trade-off:**
Tăng khả năng test và thay đổi, nhưng có thể tạo thêm interface không cần thiết nếu áp dụng máy móc.

**Middle → Senior insight:**
Middle developer cần biết tạo abstraction khi có dependency thay đổi. Senior developer cần đánh giá boundary nào thực sự thuộc domain và boundary nào chỉ làm code phức tạp hơn.

### Design 2 — Event-Driven Architecture và giới hạn của asynchronous communication

**Khái niệm:**
Event-driven architecture sử dụng event để các component giao tiếp mà không cần phụ thuộc trực tiếp.

**Vấn đề nó giải quyết:**
Giảm coupling và hỗ trợ scale độc lập giữa các phần của hệ thống.

**Ví dụ thực tế:**
Khi OrderCreated event được phát ra, các service Notification, Inventory và Analytics có thể xử lý riêng.

**Trade-off:**
Tăng scalability nhưng đổi lại là eventual consistency, khó debug flow và cần monitoring tốt.

**Middle → Senior insight:**
Middle developer cần hiểu producer/consumer flow. Senior developer cần quyết định event nào thực sự cần async và khi nào synchronous call đơn giản hơn.

### Design 3 — Cache Design: Cache Aside Pattern

**Khái niệm:**
Cache Aside là pattern trong đó application tự kiểm tra cache trước, nếu thiếu dữ liệu thì đọc database rồi cập nhật cache.

**Vấn đề nó giải quyết:**
Giảm tải database và cải thiện latency cho dữ liệu đọc nhiều.

**Ví dụ thực tế:**
API lấy thông tin employee profile đọc Redis trước, nếu không có thì query SQL Server rồi lưu lại Redis với TTL.

**Trade-off:**
Performance tốt hơn nhưng phát sinh vấn đề invalidation, stale data và memory management.

**Middle → Senior insight:**
Middle developer cần biết cách dùng cache. Senior developer cần quyết định dữ liệu nào được cache, TTL bao lâu và consistency level nào phù hợp với business.
