# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Sử dụng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Luôn truyền `CancellationToken` từ HTTP request xuống các tầng xử lý dài như database query, gọi API ngoài hoặc background operation.

**Tại sao hữu ích:**
Giúp giải phóng tài nguyên khi client đã disconnect hoặc request bị timeout, tránh xử lý vô ích.

**Ví dụ:**
```csharp
public async Task<IActionResult> GetData(CancellationToken cancellationToken)
{
    var result = await service.GetAsync(cancellationToken);
    return Ok(result);
}
```

**Lưu ý:**
Không nên bỏ qua `CancellationToken` trong các tác vụ cần hoàn thành bắt buộc như payment processing hoặc transaction quan trọng.

### Tip 2 — Dùng SQL Execution Plan khi tối ưu query thay vì đoán

**Mẹo:**
Kiểm tra execution plan trước khi thêm index hoặc rewrite SQL.

**Tại sao hữu ích:**
Giúp xác định chính xác bottleneck như table scan, missing index, expensive join hoặc sort operation.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Orders
WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo quá nhiều index chỉ vì execution plan đề xuất; index dư thừa làm chậm write operation.

### Tip 3 — Dùng `dotnet-counters` để debug performance .NET production

**Mẹo:**
Sử dụng built-in diagnostic tools của .NET để quan sát runtime metrics.

**Tại sao hữu ích:**
Có thể phát hiện nhanh CPU cao, GC pressure, thread pool starvation mà không cần attach debugger.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234
```

**Lưu ý:**
Metrics chỉ cho biết dấu hiệu; cần kết hợp logging, tracing và profiling để tìm root cause.

### Tip 4 — Dùng Git `rebase -i` để làm sạch commit history

**Mẹo:**
Interactive rebase giúp squash, reorder hoặc edit commit trước khi tạo pull request.

**Tại sao hữu ích:**
Một history rõ ràng giúp review code dễ hơn và rollback chính xác hơn.

**Ví dụ:**
```bash
git rebase -i HEAD~5
```

**Lưu ý:**
Không rebase branch đã được nhiều người khác sử dụng vì có thể gây conflict với lịch sử Git của họ.

### Tip 5 — Dùng `IOptionsSnapshot` khi cần reload configuration theo request

**Mẹo:**
Phân biệt `IOptions`, `IOptionsSnapshot` và `IOptionsMonitor` trong ASP.NET Core.

**Tại sao hữu ích:**
Giúp thiết kế configuration linh hoạt hơn khi thay đổi setting mà không restart application.

**Ví dụ:**
```csharp
public class Service
{
    private readonly IOptionsSnapshot<AppSettings> options;
}
```

**Lưu ý:**
`IOptionsSnapshot` tạo scope theo request, không phù hợp cho singleton service.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau để đảm bảo consistency.

**Vấn đề nó giải quyết:**
Tránh tạo transaction quá lớn hoặc quá nhỏ khiến hệ thống khó bảo trì và dễ lỗi dữ liệu.

**Ví dụ thực tế:**
Trong hệ thống đặt hàng, tạo Order và giảm Inventory có thể cần transaction nếu nằm cùng database. Nhưng gửi email xác nhận nên tách thành asynchronous workflow.

**Trade-off:**
Transaction lớn tăng consistency nhưng giảm scalability. Transaction nhỏ tăng throughput nhưng cần xử lý eventual consistency.

**Middle → Senior insight:**
Middle developer cần biết transaction dùng ở đâu. Senior developer cần quyết định ranh giới transaction dựa trên business invariant thay vì chỉ dựa trên technical convenience.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia application thành các module độc lập trong cùng một deployment unit.

**Vấn đề nó giải quyết:**
Giúp tạo boundary rõ ràng mà không phải trả toàn bộ chi phí vận hành distributed system.

**Ví dụ thực tế:**
Một hệ thống ERP có module Sales, Inventory, Accounting. Mỗi module có domain riêng, database access riêng nhưng vẫn chạy trong một application.

**Trade-off:**
Ưu điểm là đơn giản deployment và debugging. Nhược điểm là cần discipline để tránh module phụ thuộc lẫn nhau.

**Middle → Senior insight:**
Middle developer nên hiểu module boundary. Senior developer cần đánh giá communication pattern, ownership và khả năng scale trước khi tách microservices.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo cùng một request được gửi nhiều lần vẫn tạo ra cùng một kết quả.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate operation trong distributed system khi retry xảy ra.

**Ví dụ thực tế:**
Payment API sử dụng `Idempotency-Key` để tránh việc user bị trừ tiền hai lần khi network timeout.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và xử lý storage overhead.

**Middle → Senior insight:**
Middle developer cần biết retry có thể gây duplicate. Senior developer cần thiết kế API chịu được failure, timeout và retry từ client hoặc message broker.
