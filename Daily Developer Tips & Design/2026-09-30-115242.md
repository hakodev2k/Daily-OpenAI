# Daily Developer Tips & Design — 2026-09-30

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong ASP.NET Core

**Mẹo:**
Khi API latency tăng mạnh nhưng CPU chưa cao, kiểm tra ThreadPool queue/thread count và tìm synchronous blocking như `.Result`, `.Wait()`, lock dài hoặc sync-over-async trước khi scale instance.

**Tại sao hữu ích:**
ASP.NET Core xử lý nhiều request dựa trên ThreadPool. Nếu request giữ worker thread để chờ I/O, request mới phải xếp hàng dù CPU còn rảnh. Đây là failure mode khác CPU saturation và cần cách xử lý khác.

**Ví dụ:**
```csharp
// Có thể block worker thread
var result = httpClient.GetAsync(url).Result;

// Giải phóng thread trong lúc chờ I/O
var result = await httpClient.GetAsync(url, ct);
```
Trong incident, đối chiếu request latency, CPU, ThreadPool queue length và dependency latency để đi từ symptom → evidence → nguyên nhân.

**Lưu ý:**
Không phải mọi blocking đều xấu; code CPU-bound vẫn cần CPU. Đừng chuyển tùy tiện sang `Task.Run` trong web request vì việc đó thường chỉ chuyển work sang cùng ThreadPool và che bottleneck.

### Tip 2 — EF Core projection giúp giảm cả dữ liệu lẫn tracking cost

**Mẹo:**
Với read endpoint, project trực tiếp sang DTO bằng `Select` thay vì `Include` toàn aggregate rồi map trong memory khi response chỉ cần vài field.

**Tại sao hữu ích:**
Projection cho EF Core cơ hội sinh SQL chỉ lấy column cần thiết, giảm network payload, materialization và change-tracking overhead. Với collection lớn, lợi ích thường đáng kể hơn các micro-optimization trong C#.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderListItem(
        x.Id, x.CreatedAt, x.Status, x.Total))
    .Take(50)
    .ToListAsync(ct);
```

**Lưu ý:**
Projection phức tạp vẫn có thể tạo SQL đắt tiền. Kiểm tra generated SQL/execution plan khi query chậm; đừng thêm `AsNoTracking` như một “fix” máy móc nếu query đã project scalar/DTO và không materialize tracked entities.

### Tip 3 — Kubernetes: đọc `Last State` trước khi đoán nguyên nhân pod restart

**Mẹo:**
Khi pod vào `CrashLoopBackOff`, kiểm tra `kubectl describe pod`, container `Last State`, exit code, events và log của instance trước bằng `kubectl logs --previous`.

**Tại sao hữu ích:**
`CrashLoopBackOff` mô tả cơ chế backoff sau nhiều lần container chết, không phải root cause. Exit code, OOMKilled, probe failure hoặc application exception mới là evidence để phân biệt memory limit, startup lỗi hay configuration sai.

**Ví dụ:**
```bash
kubectl describe pod orders-api-abc123
kubectl logs orders-api-abc123 --previous
```
Nếu `Last State: Terminated` cho thấy `Reason: OOMKilled`, tiếp tục so memory working set với requests/limits và heap telemetry thay vì sửa liveness probe.

**Lưu ý:**
Tăng memory limit ngay lập tức có thể chỉ trì hoãn memory leak. Ngược lại, limit quá thấp cũng có thể kill một application khỏe mạnh; cần đối chiếu resource usage và workload thực.

### Tip 4 — JWT: validate issuer và audience, không chỉ signature

**Mẹo:**
API nhận JWT phải xác thực đầy đủ signature, issuer, audience và lifetime theo trust boundary của chính API.

**Tại sao hữu ích:**
Token có chữ ký hợp lệ chỉ chứng minh nó được một key tin cậy ký; không tự động chứng minh token được phát cho API hiện tại. Bỏ audience/issuer validation có thể khiến API chấp nhận token hợp lệ nhưng dành cho resource hoặc tenant khác.

**Ví dụ:**
```csharp
builder.Services.AddAuthentication()
    .AddJwtBearer(o =>
    {
        o.Authority = configuration["Auth:Authority"];
        o.Audience = configuration["Auth:Audience"];
    });
```
Trong production, kiểm tra claim `iss`, `aud`, thời hạn và signing-key metadata trước khi kết luận lỗi authentication là do frontend.

**Lưu ý:**
Không tự decode JWT rồi tin claims mà bỏ validation. Clock skew cần được kiểm soát, và authorization theo resource/tenant vẫn phải thực hiện sau authentication.

### Tip 5 — Contract test bắt breaking change mà unit test của từng service dễ bỏ sót

**Mẹo:**
Với API được nhiều consumer sử dụng, bổ sung contract tests cho schema/status/required semantics quan trọng thay vì chỉ dựa vào unit test của provider.

**Tại sao hữu ích:**
Provider có thể refactor “đúng” theo test nội bộ nhưng vô tình đổi field, nullability hoặc status code mà consumer phụ thuộc. Contract test kiểm tra boundary giữa hai hệ thống, nơi breaking change thực sự xảy ra.

**Ví dụ:**
Mobile backend kỳ vọng `GET /profile` luôn trả `displayName` là string. Một refactor biến field thành nullable. Unit tests của API vẫn xanh, nhưng consumer contract test fail trước deployment.

**Lưu ý:**
Đừng snapshot toàn bộ JSON một cách cứng nhắc nếu consumer không quan tâm mọi field; contract quá chặt sẽ cản backward-compatible evolution. Test những guarantees thực sự thuộc contract.

## 🧠 Software Design

### Design 1 — Transactional Outbox cho database + message broker

**Khái niệm:**
Thay vì commit business data rồi publish message như hai operation độc lập, ghi business change và Outbox record trong cùng database transaction; một publisher riêng gửi Outbox ra broker và đánh dấu trạng thái sau đó.

**Vấn đề nó giải quyết:**
Nếu database commit thành công nhưng process chết trước khi publish, downstream không biết thay đổi đã xảy ra. Nếu publish trước rồi database rollback, downstream lại thấy một event cho state chưa tồn tại.

**Ví dụ thực tế:**
Order API tạo `Order` và `OrderCreated` Outbox record trong cùng transaction. Worker đọc Outbox, publish lên Azure Service Bus rồi cập nhật trạng thái. Consumer vẫn phải idempotent vì publisher có thể crash sau publish nhưng trước khi đánh dấu record đã gửi.

**Trade-off:**
Outbox loại bỏ dual-write gap giữa database và broker nhưng thêm table growth, polling/CDC, retry, ordering và operational monitoring. Với ứng dụng đơn giản không có cross-system event requirement, chi phí này có thể không đáng.

**Middle → Senior insight:**
Middle cần implement transaction và retry mà không mất event. Senior / Technical phải quyết định polling hay CDC, ordering scope, retention, idempotency downstream và SLA từ commit đến publish; Outbox tạo at-least-once reliability chứ không tạo exactly-once end-to-end.

### Design 2 — SQL hay Cosmos DB phải bắt đầu từ access pattern và partition boundary

**Khái niệm:**
Chọn relational hay document/partitioned database dựa trên invariant, query shape, transaction scope, scale distribution và operational constraints thay vì dựa vào nhãn “NoSQL scale tốt hơn”.

**Vấn đề nó giải quyết:**
Một data model có thể hoạt động tốt ở prototype nhưng trở nên đắt hoặc khó bảo toàn consistency khi query xuyên partition, cần nhiều joins hoặc transaction vượt aggregate boundary.

**Ví dụ thực tế:**
Telemetry theo `deviceId` có write volume lớn, lookup chủ yếu theo device/time và ít cross-device transaction có thể phù hợp với partitioned document store. Billing ledger cần relational constraints, joins và transaction chặt giữa nhiều records thường phù hợp SQL hơn.

**Trade-off:**
Cosmos DB cho distribution và elastic scale nhưng partition-key sai có thể tạo hot partition, cross-partition query và RU cost cao. SQL cho constraints/joins/ACID mạnh nhưng scale topology và write contention có giới hạn/chi phí riêng.

**Middle → Senior insight:**
Middle cần model đúng theo query và transaction phổ biến. Senior phải dự báo partition cardinality, growth, hot-key risk, consistency requirement, migration cost và operational skill của team; “polyglot persistence” chỉ đáng dùng khi lợi ích vượt chi phí vận hành thêm một datastore.

### Design 3 — Feature flag tách deployment khỏi release

**Khái niệm:**
Feature flag cho phép deploy code mới nhưng kiểm soát thời điểm và nhóm user được kích hoạt, giúp rollout behavior độc lập với việc binary đã lên production.

**Vấn đề nó giải quyết:**
Một thay đổi lớn thường cần gradual rollout, kiểm chứng telemetry hoặc rollback nhanh mà không muốn build/deploy lại toàn ứng dụng mỗi lần bật/tắt behavior.

**Ví dụ thực tế:**
Checkout mới được deploy ở trạng thái off, sau đó bật cho internal users → 5% traffic → 25% → 100%. Team theo dõi error rate, conversion và latency; nếu regression xuất hiện, flag tắt path mới trong khi artifact vẫn giữ nguyên.

**Trade-off:**
Feature flag giảm release risk nhưng tạo nhiều execution paths, test matrix và “flag debt”. Flag permission/configuration sai cũng có thể trở thành production incident hoặc security issue.

**Middle → Senior insight:**
Middle cần viết hai path có test, default an toàn và telemetry phân biệt flag state. Senior / Technical phải quyết định flag nào là release flag tạm thời, kill switch dài hạn hay entitlement; đặt owner/expiry, kiểm soát quyền thay đổi và xóa code cũ sau rollout để complexity không tích tụ.
