# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Chỉ dùng `ValueTask` khi profiling cho thấy allocation của `Task` đáng tối ưu

**Mẹo:**
Trong C#, đừng thay `Task<T>` bằng `ValueTask<T>` theo thói quen. Chỉ cân nhắc `ValueTask<T>` ở hot path khi operation thường hoàn thành đồng bộ và profiling cho thấy allocation của `Task` thực sự đáng kể.

**Tại sao hữu ích:**
`ValueTask<T>` có thể tránh allocation trong một số trường hợp, nhưng đổi lại state machine và cách sử dụng phức tạp hơn. Một `ValueTask` không phải lúc nào cũng được await nhiều lần hoặc chuyển qua nhiều consumer như `Task` thông thường.

**Ví dụ:**
```csharp
public ValueTask<User?> GetCachedUserAsync(string id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadUserAsync(id));
}
```

Pattern này có ý nghĩa khi cache hit rất cao và method nằm trên hot path đã được đo bằng profiler/benchmark.

**Lưu ý:**
Không dùng `ValueTask` để “tối ưu sẵn”. Nếu caller cần await nhiều lần, store result lâu dài hoặc compose phức tạp, `Task` thường an toàn và dễ maintain hơn.

### Tip 2 — Cẩn thận state rò rỉ khi dùng `AddDbContextPool`

**Mẹo:**
Khi bật EF Core `AddDbContextPool`, coi `DbContext` như object được tái sử dụng. Không lưu tenant ID, user-specific state hoặc mutable request data trực tiếp trong instance nếu state đó không được reset an toàn.

**Tại sao hữu ích:**
Pooling giảm chi phí khởi tạo `DbContext`, nhưng instance sau khi dùng có thể quay lại pool rồi được phục vụ cho request khác. State tự thêm vào context có thể vô tình “đi theo” sang request tiếp theo và tạo bug dữ liệu rất khó phát hiện.

**Ví dụ:**
```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Nếu multi-tenant query phụ thuộc tenant hiện tại, hãy truyền tenant qua service/query boundary rõ ràng hoặc dùng pattern được thiết kế riêng cho pooled context thay vì gán tùy ý vào property mutable của `DbContext`.

**Lưu ý:**
Pooling không phải lúc nào cũng cần thiết. Trước khi bật, đo throughput/latency; nếu bottleneck nằm ở database round trip, query plan hoặc connection pool thì `DbContext` pooling có thể cải thiện rất ít.

### Tip 3 — Chọn Cosmos DB partition key theo write/read distribution, không chỉ theo uniqueness

**Mẹo:**
Với Azure Cosmos DB, partition key phải phân phối request và storage tương đối đều theo access pattern thực tế. Một key rất unique nhưng có traffic tập trung vẫn có thể tạo hot partition.

**Tại sao hữu ích:**
Throughput và request cost được phân phối qua physical partitions. Nếu phần lớn request dồn vào một logical partition, hệ thống có thể bị throttle dù tổng RU/s còn dư ở các partition khác.

**Ví dụ:**
```text
Không tốt cho hệ thống multi-tenant lớn:
partitionKey = tenantId
nếu một tenant chiếm 70% traffic

Có thể cân nhắc:
partitionKey = tenantId + bucket
nếu access pattern cho phép phân tán thêm
```

Khi điều tra `429 Too Many Requests`, kiểm tra request distribution theo partition key thay vì chỉ tăng RU/s ngay lập tức.

**Lưu ý:**
Partition key ảnh hưởng mạnh tới query cost, transaction scope và migration. Không thêm random bucket nếu business query thường xuyên cần đọc toàn bộ tenant vì fan-out query có thể tăng đáng kể.

### Tip 4 — Giữ deployment artifact bất biến giữa các environment

**Mẹo:**
Trong CI/CD, build artifact một lần rồi promote chính artifact đó qua Dev → Staging → Production thay vì rebuild source riêng cho từng environment.

**Tại sao hữu ích:**
Nếu Jenkins, TeamCity hoặc pipeline khác build lại mỗi môi trường, production artifact có thể khác staging do dependency resolution, toolchain version, source state hoặc generated file. Khi đó kết quả test ở staging không còn chứng minh đúng binary được deploy production.

**Ví dụ:**
```text
Build #842
-> myapp-842.zip
-> deploy Dev
-> promote same myapp-842.zip to Staging
-> promote same myapp-842.zip to Production

Environment-specific values:
-> inject qua configuration/secrets lúc deploy hoặc runtime
```

**Lưu ý:**
Artifact bất biến không có nghĩa configuration bất biến. Secrets, connection strings và feature flags vẫn khác theo environment nhưng không nên được “bake” bằng cách compile lại application.

### Tip 5 — Trong CMS multi-node, phân biệt content publish với cache invalidation

**Mẹo:**
Với Optimizely CMS hoặc CMS enterprise chạy nhiều instance, khi content publish nhưng một node vẫn phục vụ dữ liệu cũ, kiểm tra cơ chế cache invalidation giữa nodes thay vì chỉ restart application.

**Tại sao hữu ích:**
CMS thường có memory cache cho content/rendered fragments. Nếu publish event hoặc invalidation message không đến mọi node, một số instance có thể tiếp tục giữ version cũ dù database đã đúng.

**Ví dụ:**
```text
Editor publish Article v12
-> database đã là v12
-> node A invalidates cache
-> node B không nhận invalidation
-> load balancer thỉnh thoảng trả Article v11
```

Điều tra theo chuỗi: publish event → distributed event/cache layer → từng node cache → CDN/browser cache.

**Lưu ý:**
Đừng vô hiệu hóa toàn bộ caching để chữa symptom. CMS traffic thường read-heavy; bỏ cache có thể biến inconsistency nhỏ thành vấn đề CPU/database lớn hơn.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp nhiều capability tương tự Unit of Work và Repository. Một custom Repository chỉ có giá trị khi nó tạo boundary nghiệp vụ hoặc abstraction có ý nghĩa, không phải chỉ bọc lại mọi method của EF Core.

**Vấn đề nó giải quyết:**
Team thường tạo `IRepository<T>` với `Add`, `Update`, `GetAll` cho mọi entity để “clean architecture”, nhưng abstraction này có thể che mất LINQ/query capability và tạo thêm lớp mapping mà không giảm coupling thực sự.

**Ví dụ thực tế:**
```text
CRUD nội bộ đơn giản:
Application service -> AppDbContext

Boundary nghiệp vụ phức tạp:
OrderRepository.LoadForCheckout(orderId)
-> encapsulate query + aggregate loading rule
```

Repository hữu ích hơn khi method thể hiện intent domain thay vì phản chiếu API của `DbSet<T>`.

**Trade-off:**
Direct `DbContext` giảm ceremony, tận dụng đầy đủ EF Core và dễ tối ưu query. Repository có thể tăng encapsulation và testability ở boundary thích hợp, nhưng generic repository thường làm mất tính biểu đạt và tăng indirection.

**Middle → Senior insight:**
Middle developer cần dùng `DbContext` đúng lifetime và tránh leaking query ngoài boundary không kiểm soát. Senior / Technical developer phải đánh giá abstraction theo coupling, domain semantics, test strategy và migration cost — không theo checklist pattern.

### Design 2 — Saga và compensating transaction cho workflow xuyên nhiều service

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction. Nếu một bước sau thất bại, hệ thống chạy compensating action để đưa business state về trạng thái chấp nhận được thay vì cố dùng một distributed ACID transaction xuyên service.

**Vấn đề nó giải quyết:**
Trong workflow như booking, payment và fulfillment, mỗi service sở hữu database riêng. Giữ lock xuyên nhiều hệ thống hoặc dùng distributed transaction thường không thực tế, đặc biệt khi có external provider.

**Ví dụ thực tế:**
```text
1. Reserve inventory
2. Charge payment
3. Create shipment

Nếu bước 3 thất bại:
-> refund payment
-> release inventory
```

Compensation không nhất thiết “undo byte-for-byte”; nó phải tạo trạng thái nghiệp vụ hợp lệ và audit được.

**Trade-off:**
Saga hỗ trợ autonomy và failure recovery trong distributed system, nhưng thêm state machine, idempotency, retry, observability và eventual consistency. Với workflow nằm trong một database, local transaction đơn giản thường tốt hơn.

**Middle → Senior insight:**
Middle developer cần hiểu partial failure và viết handler idempotent. Senior / Technical developer phải quyết định orchestration hay choreography, định nghĩa compensation semantics, timeout, manual recovery và audit trail dựa trên business risk.

### Design 3 — SSR vs CSR cho website CMS: chọn theo content, SEO và interaction model

**Khái niệm:**
Server-Side Rendering (SSR) render HTML trên server trước khi gửi xuống browser; Client-Side Rendering (CSR) để JavaScript xây UI phía client. Với website CMS, lựa chọn nên dựa trên content discoverability, performance và mức độ tương tác chứ không theo framework trend.

**Vấn đề nó giải quyết:**
Content-heavy site cần HTML sớm cho SEO, social preview và perceived performance, trong khi dashboard hoặc application tương tác cao có thể hưởng lợi từ client-side state và navigation linh hoạt.

**Ví dụ thực tế:**
```text
Trang article/law-firm/service page từ CMS
-> SSR hoặc pre-render thường phù hợp

Authenticated analytics dashboard
-> CSR có thể đơn giản hơn cho interaction-heavy UI
```

Hybrid architecture có thể SSR shell/content rồi hydrate component cần tương tác.

**Trade-off:**
SSR cải thiện initial HTML và SEO nhưng tăng server rendering cost, cache complexity và hydration concerns. CSR giảm server render workload nhưng phụ thuộc JavaScript nhiều hơn và có thể làm Core Web Vitals/SEO tệ nếu bundle hoặc data fetching không được kiểm soát.

**Middle → Senior insight:**
Middle developer cần hiểu rendering lifecycle, caching và hydration. Senior / Technical developer phải chọn theo traffic profile, CDN strategy, SEO requirement, personalization, operational cost và khả năng maintain của team thay vì mặc định một rendering mode cho toàn site.
