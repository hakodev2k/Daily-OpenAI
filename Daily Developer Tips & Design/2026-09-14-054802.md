# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup read-heavy sau khi dữ liệu đã ổn định

**Mẹo:**
Trong .NET 8+, nếu một dictionary được xây dựng một lần rồi chỉ đọc với tần suất cao, cân nhắc chuyển nó sang `FrozenDictionary<TKey,TValue>` thay vì giữ `Dictionary<TKey,TValue>` mutable suốt vòng đời application.

**Tại sao hữu ích:**
`FrozenDictionary` tối ưu cấu trúc nội bộ cho lookup sau khi construction hoàn tất. Nó phù hợp với routing table, mapping code, metadata hoặc configuration lookup được khởi tạo lúc startup và không cần thay đổi sau đó. Ngoài hiệu năng, tính immutable còn giúp giảm rủi ro state bị sửa ngoài ý muốn.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

var handlers = new Dictionary<string, Func<string, Task>>
{
    ["order.created"] = HandleOrderCreatedAsync,
    ["payment.failed"] = HandlePaymentFailedAsync
}.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
```

Sau construction, code chỉ lookup:
```csharp
if (handlers.TryGetValue(message.Type, out var handler))
{
    await handler(message.Payload);
}
```

**Lưu ý:**
Construction của frozen collection có cost cao hơn collection thông thường, nên không tạo lại nó liên tục trong request path. Nếu dữ liệu thay đổi thường xuyên, `Dictionary` hoặc concurrent collection phù hợp hơn. Đừng chọn collection chỉ vì benchmark micro-level nếu lookup không phải bottleneck thực tế.

### Tip 2 — Dùng partial index trong PostgreSQL khi chỉ một phần nhỏ dữ liệu thực sự được query thường xuyên

**Mẹo:**
Nếu phần lớn query chỉ quan tâm một subset ổn định như `status = 'Pending'` hoặc `deleted_at IS NULL`, cân nhắc partial index thay vì index toàn bộ bảng.

**Tại sao hữu ích:**
Index nhỏ hơn thường giảm storage, cache pressure và write overhead. Với bảng có hàng triệu row lịch sử nhưng chỉ vài phần trăm row đang active, index toàn bảng có thể tốn nhiều tài nguyên để phục vụ query chỉ đụng tới active subset.

**Ví dụ:**
```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at DESC)
WHERE status = 'Pending';
```

Query phù hợp:
```sql
SELECT id, created_at, customer_id
FROM orders
WHERE status = 'Pending'
ORDER BY created_at DESC
LIMIT 100;
```

Dùng `EXPLAIN (ANALYZE, BUFFERS)` để xác nhận planner thực sự chọn index và lượng page đọc giảm.

**Lưu ý:**
Predicate của query phải tương thích với predicate của partial index. Nếu application có nhiều biến thể filter hoặc status thay đổi liên tục, lợi ích có thể thấp hơn dự kiến. Partial index cũng vẫn tăng write cost cho các row nằm trong subset được index.

### Tip 3 — Trong React, tránh stale closure khi callback async đọc state cũ

**Mẹo:**
Khi callback hoặc timer chạy sau một khoảng thời gian, đừng giả định nó luôn thấy state mới nhất. Nếu state update phụ thuộc state trước đó, ưu tiên functional update hoặc thiết kế dependency rõ ràng thay vì capture giá trị cũ trong closure.

**Tại sao hữu ích:**
Mỗi render tạo một lexical scope riêng. Callback được tạo ở render trước có thể tiếp tục giữ giá trị state của render đó. Bug thường xuất hiện trong timer, subscription, event listener hoặc async flow khi UI đã render state mới nhưng callback cũ vẫn xử lý dữ liệu cũ.

**Ví dụ:**
Tránh:
```tsx
setInterval(() => {
  setCount(count + 1);
}, 1000);
```

Ưu tiên khi update dựa trên state trước:
```tsx
setInterval(() => {
  setCount(current => current + 1);
}, 1000);
```

**Lưu ý:**
Functional update chỉ giải quyết trường hợp update dựa trên previous state; nó không tự sửa mọi stale closure liên quan props hoặc nhiều state khác. Với subscription/event listener, vẫn cần quản lý dependency, cleanup và ownership của callback đúng lifecycle.

### Tip 4 — So sánh OpenAPI contract trong CI để phát hiện breaking API change trước khi deploy

**Mẹo:**
Nếu backend phục vụ mobile app, frontend độc lập hoặc third-party client, export OpenAPI specification trong CI và chạy contract diff so với version đã release để phát hiện breaking changes như remove field, đổi required property hoặc thay response schema.

**Tại sao hữu ích:**
Compile và unit test của backend có thể vẫn pass dù client production sẽ break. Contract diff đưa compatibility check vào release pipeline, biến API evolution từ review thủ công thành một guardrail có thể lặp lại.

**Ví dụ:**
```text
Release hiện tại:
GET /api/orders/{id}
response.total: number

PR mới:
response.total: string

CI contract diff:
BREAKING - response schema changed: number -> string
```

Sau đó team quyết định giữ compatibility, thêm field mới hoặc mở version mới tùy contract policy.

**Lưu ý:**
Schema diff không phát hiện mọi behavioral breaking change, ví dụ cùng status `200` nhưng semantics đổi hoặc enum mới làm client cũ xử lý sai. Contract check phải bổ sung integration/consumer tests và review semantics, không thay thế chúng.

### Tip 5 — Với Optimizely CMS, tránh query content tree lặp lại trong từng component render

**Mẹo:**
Khi nhiều block/component cùng cần navigation, settings hoặc shared content, gom quyền sở hữu việc load vào service/read model phù hợp và tận dụng content cache của platform thay vì mỗi component tự traverse content tree hoặc gọi repository lặp lại.

**Tại sao hữu ích:**
Một page có nhiều component có thể vô tình thực hiện cùng logic lookup nhiều lần. Dù CMS có cache nội bộ, repeated traversal, mapping và permission/language resolution vẫn tạo overhead và làm code khó kiểm soát. Shared read model giúp request path rõ ràng hơn và dễ đo hơn.

**Ví dụ:**
```text
Page render:
- Header block -> load SiteSettings
- Footer block -> load SiteSettings
- Navigation block -> load SiteSettings

Tốt hơn:
Request-level composition/service
-> load SiteSettings một lần
-> map thành read model dùng chung cho các component
```

Nếu platform/API phù hợp, dùng `IContentLoader` cho read access thay vì tạo custom repository chỉ để bọc lại cùng behavior.

**Lưu ý:**
Đừng thêm request cache riêng nếu chưa đo và chưa hiểu cache semantics của Optimizely; cache chồng cache có thể làm invalidation khó hơn. Luôn xét language, site, personalization và publish state để tránh reuse nhầm content giữa context khác nhau.

## 🧠 Software Design

### Design 1 — Consumer-Driven Contract Testing cho service có client deploy độc lập

**Khái niệm:**
Consumer-Driven Contract Testing để consumer mô tả những interaction thực sự cần từ provider, sau đó provider verify các contract đó trong pipeline. Mục tiêu là kiểm tra compatibility tại boundary mà không cần luôn dựng full end-to-end environment.

**Vấn đề nó giải quyết:**
Một backend có thể thay response hợp lệ theo OpenAPI nhưng vô tình phá assumption mà mobile app hoặc service khác đang dùng. Ngược lại, provider không cần giữ mọi field lịch sử chỉ vì “có thể có ai đó dùng”; contract cho biết dependency thực tế nào đang tồn tại.

**Ví dụ thực tế:**
```text
Consumer Checkout cần từ Pricing:
GET /prices/42
-> 200
-> body có:
   productId
   amount
   currency
```

Pricing service verify contract đó trong CI trước khi release. Nếu đổi `amount` thành object mới, verification fail trước khi hai service lệch contract trên production.

**Trade-off:**
Contract test tăng confidence cho integration và cho phép team deploy độc lập hơn, nhưng thêm artifact/versioning/workflow giữa teams. Contract quá chi tiết sẽ khóa implementation của provider; contract quá lỏng lại bỏ sót incompatibility quan trọng. Nó cũng không thay thế E2E cho workflow business xuyên nhiều hệ thống.

**Middle → Senior insight:**
Middle developer cần viết contract theo behavior observable, không theo internal implementation. Senior / Technical developer phải quyết định boundary nào đáng contract-test, quản lý version/ownership và cân bằng provider freedom với compatibility requirement thực tế.

### Design 2 — Singleton scheduled job trong multi-instance app cần ownership phân tán rõ ràng

**Khái niệm:**
Khi application scale thành nhiều instance, một timer hoặc `BackgroundService` nằm trong mỗi process sẽ chạy nhiều bản sao. Nếu business yêu cầu job chỉ có một logical owner tại một thời điểm, cần cơ chế như distributed lease, scheduler có coordination hoặc hạ tầng job chuyên dụng.

**Vấn đề nó giải quyết:**
Một ASP.NET Core app có 4 replica và mỗi replica đều chạy job “GenerateInvoices lúc 01:00”. Nếu không có coordination, cùng invoice có thể được tạo bốn lần hoặc nhiều instance cùng tranh chấp dữ liệu.

**Ví dụ thực tế:**
```text
Option A: distributed lease
- instance A acquire lease `invoice-job`
- renew lease khi đang chạy
- instance B/C/D bỏ qua nếu lease đang thuộc A

Option B: external scheduler
- scheduler enqueue một command
- workers xử lý với idempotency
```

Dù có singleton ownership, operation vẫn nên idempotent để chịu được crash hoặc lease expiry giữa chừng.

**Trade-off:**
Distributed lease đơn giản cho một số workload nhưng thêm expiry, renewal và split-brain edge case. External scheduler/queue tăng operational components nhưng thường observability và retry rõ hơn. Với job không gây hại khi chạy trùng, idempotent multi-instance execution có thể đơn giản hơn cố đạt singleton tuyệt đối.

**Middle → Senior insight:**
Middle developer cần nhận ra “chạy một lần trong code” không đồng nghĩa “chạy một lần trong cluster”. Senior / Technical developer phải chọn ownership model dựa trên side effect, failure semantics, duration, scale và khả năng recovery thay vì mặc định thêm distributed lock.

### Design 3 — Circuit Breaker chỉ nên mở khi failure pattern cho thấy downstream khó phục hồi ngay

**Khái niệm:**
Circuit Breaker tạm ngừng gọi một dependency sau khi failure vượt ngưỡng, sau đó cho phép một số request thăm dò để xem dependency đã hồi phục chưa. Nó bảo vệ capacity bằng cách tránh tiếp tục gửi work vào downstream đang lỗi rõ ràng.

**Vấn đề nó giải quyết:**
Nếu payment provider đang trả timeout hàng loạt, tiếp tục cho mọi request chờ đủ 5 giây có thể giữ connection, task và request slot của service cho tới khi toàn hệ thống nghẽn. Khi circuit mở, service fail fast hoặc dùng fallback có chủ đích thay vì tiếp tục tạo load vô ích.

**Ví dụ thực tế:**
```text
Closed:
- gọi provider bình thường
- 20 request gần nhất có 70% transient failure

Open trong 30s:
- không gọi provider
- fail fast với trạng thái phụ thuộc unavailable

Half-open:
- cho vài probe request
- success ổn định -> Closed
- tiếp tục fail -> Open lại
```

**Trade-off:**
Circuit Breaker giảm cascading failure nhưng có thể từ chối request trong lúc dependency vừa kịp phục hồi. Threshold quá nhạy gây flapping; threshold quá chậm thì bảo vệ muộn. Nó cũng không thay thế timeout, concurrency limit, retry budget hoặc capacity planning.

**Middle → Senior insight:**
Middle developer cần phân biệt retry với circuit breaker: retry cố thử lại một operation, circuit breaker quyết định có nên tiếp tục gọi dependency hay không. Senior / Technical developer phải chọn failure window, recovery probe, fallback và metric theo SLO/downstream behavior thay vì copy một policy chung cho mọi HTTP client.
