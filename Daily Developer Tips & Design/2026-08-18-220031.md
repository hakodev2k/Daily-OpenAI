# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `required` để ép object được khởi tạo đủ dữ liệu quan trọng

**Mẹo:**
Với DTO hoặc configuration object có field bắt buộc, dùng `required` để compiler cảnh báo ngay khi object initializer thiếu property cần thiết.

**Tại sao hữu ích:**
Giảm lỗi runtime do object tồn tại ở trạng thái thiếu dữ liệu, đặc biệt khi refactor constructor hoặc thêm field mới.

**Ví dụ:**
```csharp
public sealed class CreateOrderCommand
{
    public required string CustomerId { get; init; }
    public required IReadOnlyList<OrderItemDto> Items { get; init; }
}

var command = new CreateOrderCommand
{
    CustomerId = "C001",
    Items = items
};
```

**Lưu ý:**
`required` chỉ kiểm tra việc gán property, không đảm bảo giá trị hợp lệ. Vẫn cần validation cho `null`, empty string hoặc business rule.

### Tip 2 — Khi SQL lúc nhanh lúc chậm, kiểm tra parameter sniffing

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có lúc chạy vài ms, lúc lại vài giây, đừng chỉ nhìn index; kiểm tra execution plan được cache có phù hợp với mọi parameter hay không.

**Tại sao hữu ích:**
Một plan tối ưu cho tập dữ liệu rất nhỏ có thể cực tệ với parameter trả về hàng triệu rows, và ngược lại.

**Ví dụ:**
```sql
EXEC sp_helptext 'dbo.GetOrdersByCustomer';
```

Sau đó so sánh actual execution plan với các customer có cardinality rất khác nhau. Trong một số trường hợp có thể cân nhắc:

```sql
OPTION (RECOMPILE)
```

**Lưu ý:**
Không thêm `OPTION (RECOMPILE)` như cách chữa mặc định; recompilation có CPU cost. Cần xác định workload, data skew và SQL Server version trước khi chọn giải pháp.

### Tip 3 — Đặt timeout riêng cho outbound HTTP call

**Mẹo:**
Không phụ thuộc hoàn toàn vào timeout mặc định của `HttpClient`. Đặt timeout theo dependency hoặc dùng cancellation policy cho từng operation.

**Tại sao hữu ích:**
Một API ngoài bị treo lâu có thể giữ request, connection và resource của application cho đến khi toàn hệ thống bị backlog.

**Ví dụ:**
```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
cts.CancelAfter(TimeSpan.FromSeconds(3));

var response = await httpClient.GetAsync("/inventory/42", cts.Token);
```

**Lưu ý:**
Timeout quá ngắn sẽ biến latency bình thường thành failure. Nên dựa trên SLO thực tế và phân biệt timeout với user cancellation khi logging.

### Tip 4 — Dùng Redis Lua script cho thao tác read-modify-write cần atomicity

**Mẹo:**
Khi logic cần đọc một key, kiểm tra điều kiện rồi update nhiều key liên quan, Lua script có thể thực hiện toàn bộ operation atomically trên Redis server.

**Tại sao hữu ích:**
Tránh race condition giữa nhiều client mà không cần round-trip lock riêng.

**Ví dụ:**
```lua
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
local amount = tonumber(ARGV[1])

if current < amount then
    return 0
end

redis.call('DECRBY', KEYS[1], amount)
return 1
```

**Lưu ý:**
Script chạy trên Redis event loop. Script dài hoặc CPU-heavy có thể block các request khác; giữ logic ngắn và deterministic.

### Tip 5 — Dùng `concurrency` trong GitHub Actions để hủy build cũ của cùng branch

**Mẹo:**
Với workflow chạy khi push liên tục, cấu hình concurrency group để commit mới tự hủy run cũ chưa hoàn thành.

**Tại sao hữu ích:**
Tiết kiệm CI minutes và tránh deploy artifact từ commit đã lỗi thời sau khi branch có commit mới hơn.

**Ví dụ:**
```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

**Lưu ý:**
Không bật hủy tùy tiện cho migration, release hoặc production deployment có side effect không thể rollback giữa chừng.

## 🧠 Software Design

### Design 1 — Strangler Fig Pattern khi thay thế legacy system

**Khái niệm:**
Strangler Fig Pattern thay hệ thống cũ từng phần: traffic cho một capability được chuyển dần sang implementation mới thay vì rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó kiểm chứng parity và tạo rủi ro lớn ở ngày chuyển đổi. Strangler cho phép migration theo từng business slice có thể deploy và đo lường độc lập.

**Ví dụ thực tế:**
Một monolith xử lý Customer, Billing và Reporting. Team đặt gateway phía trước, chuyển endpoint Reporting sang service mới trước, trong khi Customer/Billing vẫn chạy trên monolith. Sau khi ổn định mới tiếp tục migrate module khác.

**Trade-off:**
Giảm migration risk và tạo giá trị sớm, nhưng giai đoạn chuyển tiếp có routing logic, duplicate model và integration giữa legacy/new system làm kiến trúc tạm thời phức tạp hơn.

**Middle → Senior insight:**
Middle developer cần hiểu migration có thể thực hiện theo vertical slice thay vì rewrite toàn bộ. Senior developer phải chọn seam phù hợp, quản lý ownership dữ liệu, rollback path và xác định khi nào cần xóa compatibility layer để tránh kiến trúc tạm thời trở thành vĩnh viễn.

### Design 2 — Fencing Token cho distributed lock

**Khái niệm:**
Distributed lock chỉ cho biết một client từng giữ lock; fencing token bổ sung một số sequence tăng dần để downstream có thể từ chối operation đến từ lock holder cũ.

**Vấn đề nó giải quyết:**
Một process có thể pause lâu do GC hoặc network partition, lock hết hạn rồi process khác lấy lock. Khi process cũ tỉnh lại, cả hai có thể cùng ghi dữ liệu dù mỗi bên đều từng “giữ lock hợp lệ”.

**Ví dụ thực tế:**
Worker A nhận token `41`, bị pause. Lock hết hạn, Worker B nhận token `42` và update storage. Khi A quay lại với token `41`, storage chỉ chấp nhận token lớn hơn token cuối cùng nên từ chối write stale.

**Trade-off:**
Bảo vệ tốt hơn trước stale lock holder, nhưng downstream storage phải hiểu và enforce token ordering; thiết kế phức tạp hơn một mutex đơn giản.

**Middle → Senior insight:**
Middle developer cần biết distributed lock có failure mode khác lock trong một process. Senior developer phải xem xét lease expiry, clock assumptions, partition, retry và khả năng enforce fencing ở resource thật thay vì tin rằng “acquire lock thành công” là đủ.

### Design 3 — Cardinality budget trong Observability Design

**Khái niệm:**
Metrics label/tag nên có tập giá trị hữu hạn và kiểm soát được. Cardinality budget là giới hạn có chủ đích cho số lượng time series mà telemetry có thể tạo ra.

**Vấn đề nó giải quyết:**
Tag như `userId`, `requestId` hoặc raw URL chứa ID có thể tạo hàng triệu time series, làm tăng chi phí observability, memory usage và khiến query metrics chậm hoặc không khả dụng.

**Ví dụ thực tế:**
Thay vì metric:

```text
http_requests_total{path="/orders/913842"}
```

chuẩn hóa route thành:

```text
http_requests_total{route="/orders/{id}"}
```

Thông tin `orderId` cụ thể nên nằm trong trace/log thay vì metric label.

**Trade-off:**
Cardinality thấp giúp metrics rẻ và aggregate nhanh, nhưng mất khả năng drill-down trực tiếp theo từng entity. Cần kết hợp metrics với logs/traces cho forensic debugging.

**Middle → Senior insight:**
Middle developer cần phân biệt metric dimension với diagnostic context. Senior developer cần thiết kế telemetry schema, retention và sampling dựa trên câu hỏi vận hành thật sự, đồng thời ngăn application team vô tình thêm high-cardinality tags vào production metrics.
