# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống connection pooling

**Mẹo:**
Khi dùng `AddDbContextPool`, hiểu rằng EF Core tái sử dụng `DbContext` instance; database connection pooling vẫn do ADO.NET provider quản lý riêng. Chỉ bật context pooling sau khi đo được allocation/setup cost đáng kể.

**Tại sao hữu ích:**
Pooled `DbContext` có thể giảm allocation và initialization overhead ở workload nhiều request ngắn, nhưng nó thay đổi lifecycle assumptions. Context được reset rồi tái sử dụng, nên mutable state gắn với request/tenant có thể rò sang lần sử dụng tiếp theo nếu thiết kế sai.

**Ví dụ:**
```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```
Nếu tenant ID ảnh hưởng query filter, đừng lưu tenant state tùy tiện trong pooled context mà không có cơ chế khởi tạo/reset an toàn cho từng scope.

**Lưu ý:**
Context pooling không sửa slow SQL, connection exhaustion hay N+1. Đừng nhầm nó với `SqlConnection` pooling và đừng giữ `DbContext` lâu hơn unit-of-work chỉ vì instance có thể được pool.

### Tip 2 — `IAsyncEnumerable<T>` giúp streaming nhưng phải kiểm soát lifetime

**Mẹo:**
Dùng `IAsyncEnumerable<T>` khi consumer thực sự có thể xử lý từng phần dữ liệu và bạn muốn tránh materialize toàn bộ collection, nhưng giữ resource lifetime và cancellation rõ ràng.

**Tại sao hữu ích:**
Streaming giảm peak memory và cho phép bắt đầu xử lý/response sớm hơn. Tuy nhiên database reader hoặc network stream có thể tồn tại trong suốt quá trình enumeration; consumer chậm sẽ kéo dài thời gian giữ connection/resource.

**Ví dụ:**
```csharp
await foreach (var item in db.AuditEvents
    .AsNoTracking()
    .AsAsyncEnumerable()
    .WithCancellation(cancellationToken))
{
    await writer.WriteAsync(item, cancellationToken);
}
```
Với export lớn, đây có thể tốt hơn `ToListAsync()` rồi mới serialize toàn bộ.

**Lưu ý:**
Streaming không tự tạo backpressure end-to-end và không phải lựa chọn tốt nếu business logic cần sort/group toàn bộ tập dữ liệu trước khi trả. Cũng cần kiểm tra serialization/proxy buffering có vô hiệu hóa lợi ích hay không.

### Tip 3 — Kubernetes readiness probe phải phản ánh khả năng nhận traffic

**Mẹo:**
Thiết kế readiness probe để trả lời “instance này có nên nhận request mới không?”, không dùng cùng một logic với liveness một cách máy móc.

**Tại sao hữu ích:**
Pod có process còn sống nhưng đang warm-up, thiếu critical configuration hoặc tạm thời không thể phục vụ request. Readiness fail sẽ loại pod khỏi Service endpoints mà không nhất thiết restart process, tránh gửi traffic vào instance chưa sẵn sàng.

**Ví dụ:**
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```
Một deployment mới có thể chỉ ready sau khi application initialization hoàn tất.

**Lưu ý:**
Đừng đưa mọi dependency bên ngoài vào readiness. Nếu một optional downstream API chập chờn làm toàn bộ pods đồng loạt unready, bạn có thể tự gây outage lớn hơn. Dependency nào quyết định readiness phải dựa trên khả năng phục vụ thực tế của service.

### Tip 4 — File upload phải validate nội dung và giới hạn resource, không chỉ extension

**Mẹo:**
Với ASP.NET Core/CMS upload, coi filename và `Content-Type` từ client là untrusted. Giới hạn kích thước, kiểm tra loại file bằng nội dung/signature khi phù hợp, tạo server-side storage name và lưu ngoài executable web root nếu không cần public trực tiếp.

**Tại sao hữu ích:**
Đổi tên `payload.exe` thành `image.jpg` hoặc gửi MIME giả rất dễ. Upload không kiểm soát còn có thể gây disk exhaustion, malware propagation hoặc path traversal nếu filename được dùng trực tiếp.

**Ví dụ:**
```text
Client: invoice.pdf
Checks:
1. request/body size limit
2. allowed extension + expected signature
3. generated storage key
4. malware scanning nếu risk model yêu cầu
5. authorization trước download
```
Với Azure Blob Storage, backend có thể cấp SAS ngắn hạn có scope tối thiểu thay vì public container.

**Lưu ý:**
Magic-byte validation không chứng minh file hoàn toàn an toàn. Image/document parsers cũng có vulnerabilities; mức kiểm tra cần theo threat model và loại nội dung được xử lý phía server.

### Tip 5 — AI-generated migration phải được kiểm tra bằng schema diff và data path

**Mẹo:**
Khi AI coding agent tạo EF Core migration hoặc SQL migration, review cả generated DDL, migration ordering và tác động dữ liệu; đừng chỉ thấy project compile rồi chấp nhận.

**Tại sao hữu ích:**
Agent có thể tạo `DropColumn` rồi `AddColumn` thay vì rename, đặt default sai, tạo index blocking hoặc giả định API/version không đúng. Code compile vẫn có thể gây mất dữ liệu hoặc downtime khi deploy.

**Ví dụ:**
```text
Agent đề xuất:
DropColumn("FullName")
AddColumn("DisplayName")

Review phát hiện:
→ đây là rename semantics
→ cần migration bảo toàn dữ liệu
→ cần compatibility với application version cũ trong rolling deployment
```
Chạy migration trên database copy/representative dataset và inspect SQL trước production.

**Lưu ý:**
Generated migration không nên được “sửa cho pass” mà bỏ qua rollback/forward compatibility. Với bảng lớn, operation tưởng đơn giản có thể lock lâu hoặc rewrite table; cần đánh giá engine/version cụ thể.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho idempotent message consumption

**Khái niệm:**
Inbox Pattern lưu message identity đã xử lý cùng với state transition cần bảo vệ, giúp consumer nhận lại cùng message mà không thực thi business effect lần nữa.

**Vấn đề nó giải quyết:**
Broker theo at-least-once delivery có thể redeliver khi consumer xử lý thành công nhưng crash trước lúc acknowledge. Nếu handler gửi refund hoặc tạo invoice lần nữa, duplicate delivery trở thành duplicate business operation.

**Ví dụ thực tế:**
Consumer nhận `PaymentCaptured` với `MessageId=abc`. Trong cùng database transaction, nó kiểm tra/insert `InboxMessages(abc)` và cập nhật Order. Lần redelivery sau thấy `abc` đã tồn tại nên không áp dụng state transition lại.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, unique constraint, cleanup/retention và transaction work. Nó cũng chỉ deduplicate trong phạm vi identity và store được thiết kế; side effect ra hệ thống khác vẫn cần strategy riêng.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là normal condition và dùng stable message ID/unique constraint thay vì check-then-insert dễ race. Senior / Technical developer phải xác định deduplication scope, retention horizon, transaction boundary và cách phối hợp Inbox với Outbox hoặc external side effects.

### Design 2 — Composition over Inheritance trong business behavior

**Khái niệm:**
Composition xây behavior bằng các collaborator/capability có contract rõ ràng thay vì tạo hierarchy kế thừa sâu chỉ để tái sử dụng code. Mục tiêu là giảm coupling giữa các biến thể business không thực sự có quan hệ “is-a” ổn định.

**Vấn đề nó giải quyết:**
Một e-commerce system bắt đầu với `BaseOrderProcessor`, rồi `RetailOrderProcessor`, `VipOrderProcessor`, `InternationalVipOrderProcessor`; mỗi requirement mới override một phần lifecycle và behavior phụ thuộc thứ tự gọi base method, khiến thay đổi khó dự đoán.

**Ví dụ thực tế:**
`OrderProcessor` nhận `IPricingPolicy`, `IFraudPolicy` và `IFulfillmentStrategy`. Một channel mới chọn composition phù hợp thay vì thêm subclass mới vào hierarchy đang phình to.

**Trade-off:**
Composition tăng khả năng thay thế/test từng behavior và tránh fragile base class, nhưng quá nhiều micro-interface/strategy cũng làm navigation và dependency graph phức tạp. Inheritance vẫn hợp lý khi subtype relationship thực sự ổn định và polymorphism tự nhiên.

**Middle → Senior insight:**
Middle developer cần nhận ra inheritance dùng chỉ để reuse code thường là tín hiệu xấu. Senior / Technical developer phải tìm đúng variation axis, tránh tạo abstraction trước khi có biến thể thật và cân bằng extensibility với số lượng moving parts mà team phải hiểu.

### Design 3 — Bulkhead Isolation để một dependency không ăn hết capacity

**Khái niệm:**
Bulkhead giới hạn resource/concurrency theo workload hoặc dependency để failure/slowdown ở một khu vực không tiêu thụ toàn bộ capacity của service.

**Vấn đề nó giải quyết:**
Một third-party recommendation API chậm từ 200 ms lên 20 giây. Nếu mọi request đều chờ không giới hạn, outbound connections, queued work và memory tăng cho đến khi cả checkout API bị ảnh hưởng dù recommendation chỉ là optional feature.

**Ví dụ thực tế:**
Recommendation calls có concurrency limit riêng và timeout ngắn; khi partition đó đầy, request fallback không recommendation. Payment dependency có capacity policy khác vì criticality và latency budget khác.

**Trade-off:**
Bulkhead giảm blast radius và giúp critical traffic sống sót, nhưng giới hạn quá thấp sẽ reject workload hợp lệ; chia quá nhiều pools làm utilization kém và configuration khó vận hành.

**Middle → Senior insight:**
Middle developer cần biết bounded concurrency tốt hơn tạo task/request vô hạn. Senior / Technical developer phải chọn isolation boundary từ criticality, dependency behavior và capacity measurements; đồng thời định nghĩa queue/reject/fallback semantics, metrics và cách điều chỉnh limits khi workload thay đổi.
