# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate `Options` ngay lúc startup thay vì đợi request đầu tiên mới lỗi

**Mẹo:**
Với configuration quan trọng như endpoint, timeout, credential reference hoặc feature setting, dùng Options validation và `ValidateOnStart()` để fail fast khi application khởi động.

**Tại sao hữu ích:**
Nếu cấu hình sai nhưng chỉ được đọc khi request đầu tiên chạy, deployment có thể được đánh dấu “healthy” rồi mới bắt đầu trả lỗi production. Startup validation biến configuration thành một phần của deployment contract và giúp phát hiện lỗi trước khi nhận traffic.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .ValidateDataAnnotations()
    .Validate(x => x.TimeoutSeconds is > 0 and <= 30,
        "TimeoutSeconds must be between 1 and 30")
    .ValidateOnStart();
```

**Lưu ý:**
Không validate bằng cách gọi external dependency thật trong startup nếu việc đó làm application phụ thuộc cứng vào network. Validation nên kiểm tra cấu hình và invariant; health/readiness mới phù hợp hơn cho dependency availability.

### Tip 2 — Với MongoDB, thiết kế compound index theo query pattern chứ không theo thứ tự field trong document

**Mẹo:**
Khi query vừa filter vừa sort, xem lại thứ tự field trong compound index theo predicate thực tế. Equality field thường nên đứng trước range/sort field khi workload phù hợp.

**Tại sao hữu ích:**
MongoDB chỉ khai thác compound index hiệu quả nếu prefix của index khớp access pattern. Một index có đúng tất cả field nhưng sai thứ tự vẫn có thể dẫn tới scan nhiều key hoặc in-memory sort.

**Ví dụ:**
Query:
```javascript
db.orders.find({
  tenantId: "t-42",
  status: "Pending",
  createdAt: { $gte: ISODate("2026-09-01") }
}).sort({ createdAt: -1 })
```

Index phù hợp hơn có thể là:
```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Sau đó dùng `explain("executionStats")` để kiểm tra `keysExamined`, `docsExamined` và stage thực tế.

**Lưu ý:**
Không tạo một compound index cho mọi biến thể filter. Mỗi index tăng storage và write amplification. Chỉ giữ index phục vụ query quan trọng đã được đo.

### Tip 3 — Warm up deployment slot trước khi swap Azure App Service

**Mẹo:**
Khi deploy qua Azure App Service deployment slot, đảm bảo slot mới hoàn tất startup, migration-safe initialization và health check trước khi swap sang production.

**Tại sao hữu ích:**
Swap không tự biến application chưa sẵn sàng thành healthy. Nếu startup cần JIT, load configuration, build cache hoặc connect dependency, traffic có thể gặp latency spike hoặc 5xx ngay sau swap.

**Ví dụ:**
Một release flow an toàn hơn:
```text
deploy -> staging slot
      -> run smoke test
      -> wait readiness/health
      -> verify Application Insights
      -> swap
      -> monitor post-swap
```

Nếu application có expensive initialization, warm-up endpoint hoặc platform health check nên phản ánh readiness thật.

**Lưu ý:**
Không chạy destructive database migration gắn chặt với slot swap nếu old/new version có thể cùng tồn tại. Schema change nên backward-compatible theo expand-and-contract.

### Tip 4 — Dùng OpenAPI diff trong CI để phát hiện breaking API change trước khi merge

**Mẹo:**
Với API có consumer độc lập, generate OpenAPI document trong CI và so sánh với baseline để phát hiện breaking change như xóa endpoint, đổi field required hoặc thay response schema.

**Tại sao hữu ích:**
Code review rất dễ bỏ sót compatibility issue, đặc biệt khi refactor DTO hoặc nullable annotation. Contract diff biến backward compatibility thành một kiểm tra tự động thay vì chỉ dựa vào trí nhớ của reviewer.

**Ví dụ:**
Một PR đổi:
```json
{
  "name": "string"
}
```

thành:
```json
{
  "displayName": "string"
}
```

Nếu consumer vẫn đọc `name`, CI nên flag breaking change trước khi release.

**Lưu ý:**
Không coi mọi schema diff là breaking. Thêm optional field thường an toàn, còn đổi enum semantics hoặc business behavior có thể breaking nhưng OpenAPI diff không tự hiểu được. Automated check hỗ trợ, không thay thế engineering judgment.

### Tip 5 — Khi dùng AI coding agent, bắt nó chứng minh bằng test hoặc source reference

**Mẹo:**
Với thay đổi do AI đề xuất, yêu cầu agent chỉ ra source file/API documentation liên quan và bổ sung test chứng minh behavior thay vì chấp nhận patch chỉ vì compile được.

**Tại sao hữu ích:**
AI thường tạo implementation hợp lý về mặt cú pháp nhưng dựa trên API không tồn tại, version sai hoặc assumption không đúng repository. Grounding vào source thực tế và test giúp giảm hallucination và regression.

**Ví dụ:**
Thay vì prompt:
```text
Fix the retry bug.
```

dùng yêu cầu:
```text
Identify the exact retry path in this repository,
show the files/functions involved,
implement the smallest fix,
and add a regression test that fails before the change.
```

**Lưu ý:**
Test do AI tạo cũng có thể chỉ mirror implementation hiện tại. Review assertion theo observable behavior và production requirement, không chỉ theo code path.

## 🧠 Software Design

### Design 1 — Read-after-write consistency cần được thiết kế theo UX, không mặc định eventual consistency là đủ

**Khái niệm:**
Trong hệ thống dùng cache, replica hoặc async projection, dữ liệu mới ghi có thể chưa xuất hiện ngay ở read path. Read-after-write consistency là quyết định về việc user có cần nhìn thấy chính thay đổi của mình ngay lập tức hay không.

**Vấn đề nó giải quyết:**
Eventual consistency có thể hợp lý cho analytics nhưng gây UX lỗi nếu user vừa cập nhật profile rồi reload và thấy dữ liệu cũ. Hệ thống cần phân biệt read path nào chấp nhận stale data và read path nào phải phản ánh write vừa commit.

**Ví dụ thực tế:**
User đổi shipping address. Write đi vào primary database, nhưng read API mặc định đọc cache 60 giây. Một cách xử lý có thể là:
- invalidate cache ngay sau write
- route read của cùng user về primary trong một khoảng ngắn
- hoặc trả representation mới trực tiếp từ write response

**Trade-off:**
Consistency mạnh hơn cải thiện UX và giảm confusion nhưng tăng coupling, load lên primary hoặc invalidation complexity. Eventual consistency đơn giản và scale tốt hơn nhưng cần business tolerance rõ ràng.

**Middle → Senior insight:**
Middle developer cần hiểu stale read đến từ đâu và tránh “fix” bằng sleep/retry tùy ý. Senior / Technical developer phải phân loại workflow theo consistency requirement, latency budget, cache topology và failure mode thay vì áp một consistency model cho toàn hệ thống.

### Design 2 — Feature Flag tách deployment khỏi release

**Khái niệm:**
Feature Flag cho phép code được deploy nhưng behavior mới chỉ bật cho nhóm user/environment được chọn. Deployment trở thành thao tác kỹ thuật; release trở thành quyết định product/operational riêng.

**Vấn đề nó giải quyết:**
Nếu mọi feature chỉ có trạng thái “chưa deploy” hoặc “deploy cho tất cả”, team khó canary rollout, rollback nhanh hoặc thử nghiệm capability có rủi ro cao mà không redeploy artifact.

**Ví dụ thực tế:**
Một checkout flow mới được deploy cùng release nhưng flag chỉ bật:
```text
internal users -> 100%
pilot tenant   -> 10%
all users      -> 0%
```

Khi telemetry ổn định mới tăng dần rollout.

**Trade-off:**
Feature Flag giảm release risk và hỗ trợ rollback nhanh, nhưng tạo code path song song, test matrix lớn hơn và technical debt nếu flag không được cleanup.

**Middle → Senior insight:**
Middle developer cần viết code để cả flag on/off đều an toàn và test được. Senior / Technical developer phải quyết định flag nào cần runtime control, owner, expiration date, telemetry và cleanup plan để hệ thống không biến thành “flag spaghetti”.

### Design 3 — Composition over Inheritance cho component/CMS extension linh hoạt hơn

**Khái niệm:**
Composition over Inheritance ưu tiên ghép behavior từ các capability nhỏ thay vì tạo cây class sâu chỉ để tái sử dụng code.

**Vấn đề nó giải quyết:**
Inheritance hierarchy thường giả định relationship ổn định. Trong CMS hoặc application extensible, requirement thay đổi theo capability: có block cần image, block khác cần CTA, block khác cần tracking. Cây kế thừa sâu dễ tạo base class chứa quá nhiều responsibility.

**Ví dụ thực tế:**
Thay vì:
```text
BaseBlock
  -> ImageBlock
      -> PromoImageBlock
          -> TrackedPromoImageBlock
```

có thể compose:
```text
PromoBlock
- ImageContent
- LinkContent
- TrackingMetadata
```

Rendering/service layer xử lý từng capability theo contract riêng.

**Trade-off:**
Composition tăng flexibility và giảm coupling với hierarchy, nhưng có thể tạo nhiều object/interface nhỏ và wiring phức tạp. Inheritance vẫn hợp lý khi relationship “is-a” thực sự ổn định và behavior chung rõ ràng.

**Middle → Senior insight:**
Middle developer cần nhận ra khi base class bắt đầu phình to hoặc override behavior khó đoán. Senior / Technical developer phải chọn abstraction dựa trên axis of change của domain, không dựa trên sở thích pattern; đôi khi một class đơn giản vẫn tốt hơn cả inheritance lẫn composition framework phức tạp.
