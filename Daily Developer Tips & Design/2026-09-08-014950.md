# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi Large Object Heap khi memory tăng theo traffic

**Mẹo:**
Khi service .NET có memory tăng mạnh dưới tải, kiểm tra allocation profile và Large Object Heap (LOH), đặc biệt với `byte[]`, `char[]`, JSON payload lớn, image/file buffer hoặc serialization trung gian.

**Tại sao hữu ích:**
Object lớn thường đi thẳng vào LOH thay vì Gen 0. Nếu mỗi request tạo nhiều buffer lớn, working set và GC pause có thể tăng mạnh dù request đã kết thúc.

**Ví dụ:**
Một export API đang tạo file hoàn chỉnh trong memory trước khi trả response. Nếu payload đủ lớn, chuyển sang streaming hoặc chia nhỏ buffer có thể giảm peak memory đáng kể.

**Lưu ý:**
Đừng tối ưu theo cảm giác. Dùng profiler, `dotnet-counters`, `dotnet-trace` hoặc memory dump để xác nhận allocation source trước khi thay đổi code.

### Tip 2 — Với PostgreSQL job queue, dùng `FOR UPDATE SKIP LOCKED` khi nhiều worker tranh cùng row

**Mẹo:**
Nếu nhiều worker cùng lấy job từ một bảng PostgreSQL, `FOR UPDATE SKIP LOCKED` cho phép worker bỏ qua row đang bị lock và xử lý job khác.

**Tại sao hữu ích:**
Không dùng `SKIP LOCKED`, nhiều worker có thể xếp hàng chờ cùng một row dù còn nhiều job khác. Điều này làm throughput giảm và tăng lock contention.

**Ví dụ:**
```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

Worker claim batch và cập nhật trạng thái trong transaction phù hợp với workflow.

**Lưu ý:**
Database-backed queue vẫn cần retry, poison-job handling, timeout và recovery khi worker crash. Với hệ thống phân tán lớn, message broker có thể phù hợp hơn.

### Tip 3 — Kiểm tra sampling trước khi kết luận Application Insights bị mất telemetry

**Mẹo:**
Nếu số request, dependency hoặc trace trong Application Insights thấp hơn traffic thực tế, kiểm tra sampling configuration trước khi nghi ingestion lỗi.

**Tại sao hữu ích:**
Sampling cố ý giảm telemetry volume và chi phí. Raw row count trong backend telemetry vì thế có thể không bằng số request thật.

**Ví dụ:**
Nếu API gateway ghi nhận 1.000.000 request nhưng Application Insights chỉ lưu khoảng 100.000 row vì sampling 10%, cần dùng aggregation có nhận biết sampling thay vì so raw count.

**Lưu ý:**
Sampling quá mạnh có thể làm khó việc điều tra rare failure. Exception, critical dependency hoặc signal dùng cho SLO cần policy rõ ràng.

### Tip 4 — Trong Playwright, đợi state của UI thay vì `waitForTimeout`

**Mẹo:**
Đồng bộ E2E test bằng element state, response hoặc observable outcome thay vì sleep cố định.

**Tại sao hữu ích:**
`waitForTimeout(3000)` vừa làm test chậm vừa flaky: máy nhanh thì chờ thừa, CI chậm thì vẫn chưa đủ.

**Ví dụ:**
```ts
await expect(page.getByRole('status')).toContainText('Saved');
```

Điều này tốt hơn một fixed delay nếu UI chỉ được coi là hoàn tất khi status thực sự xuất hiện.

**Lưu ý:**
Không dùng `networkidle` cho mọi SPA. Long polling, analytics hoặc websocket có thể khiến trạng thái này không ổn định. Chọn signal sát business outcome nhất.

### Tip 5 — Tách content cache khỏi business-data cache trong CMS

**Mẹo:**
Nếu một Optimizely block vừa lấy editorial content vừa gọi product, pricing hoặc inventory API, đừng dùng cùng cache key/lifetime cho tất cả dữ liệu.

**Tại sao hữu ích:**
Headline và image có lifecycle khác price hoặc stock. Một cache boundary chung dễ gây stale data hoặc làm content cache bị invalidation quá thường xuyên.

**Ví dụ:**
```text
CMS content: headline, image, CTA -> cache theo content version
Product price/stock             -> cache ngắn theo business rule
User-specific data              -> không cache public response
```

**Lưu ý:**
Nếu component có personalization, locale hoặc tenant context, cache key phải phản ánh đúng dimension đó. Không cache HTML chung chứa dữ liệu user-specific.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service

**Khái niệm:**
Azure Functions phù hợp với workload event-driven, bursty và execution unit tương đối độc lập. Worker Service phù hợp hơn khi cần process sống lâu, kiểm soát lifecycle hoặc throughput liên tục.

**Vấn đề nó giải quyết:**
Cả hai đều chạy background work nhưng execution model, scaling, startup và operational ownership khác nhau. Chọn sai có thể tạo cold-start issue, connection churn hoặc infrastructure dư thừa.

**Ví dụ thực tế:**
Image resize theo Blob upload thường hợp với Function. Một processor chạy liên tục, giữ nhiều connection hoặc cần concurrency ổn định có thể hợp hơn với Worker Service.

**Trade-off:**
Functions giảm infrastructure management và scale theo event; đổi lại có runtime constraint và startup behavior cần tính đến. Worker Service cho nhiều control hơn nhưng team phải sở hữu hosting và scaling.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và cancellation của từng host. Senior / Technical developer phải đánh giá workload shape, latency, concurrency, cost và operational maturity trước khi chọn.

### Design 2 — Normalization vs Denormalization

**Khái niệm:**
Normalization giảm duplication và giúp invariant dữ liệu rõ hơn; denormalization chủ động duplicate dữ liệu để tối ưu read path hoặc giảm dependency.

**Vấn đề nó giải quyết:**
Schema quá normalized có thể khiến query phổ biến cần nhiều join. Denormalize quá sớm lại tạo nhiều bản sao phải đồng bộ.

**Ví dụ thực tế:**
Order thường nên lưu snapshot như product price hoặc customer display name tại thời điểm mua thay vì luôn join sang dữ liệu hiện tại, vì đây còn là yêu cầu lịch sử nghiệp vụ.

**Trade-off:**
Normalization giúp write consistency; denormalization tăng read efficiency nhưng tạo synchronization logic, stale-data risk và storage duplication.

**Middle → Senior insight:**
Middle developer cần hiểu source of truth và tránh duplicate vô nghĩa. Senior / Technical developer phải phân biệt dữ liệu transactional, snapshot và read model dựa trên consistency SLA và query pressure.

### Design 3 — Strangler Pattern cho modernization legacy .NET

**Khái niệm:**
Strangler Pattern hiện đại hóa hệ thống bằng cách thay từng capability của legacy application, chuyển traffic dần và loại bỏ phần cũ khi replacement ổn định.

**Vấn đề nó giải quyết:**
Full rewrite thường có thời gian dài không tạo business value và rủi ro cutover lớn. Migration theo slice cho phép release, quan sát và rollback từng phần.

**Ví dụ thực tế:**
Một ASP.NET MVC/.NET Framework monolith có module customer profile. Có thể route `/customer/profile` sang ASP.NET Core mới trong khi các route khác vẫn về monolith, sau đó tách data ownership từng bước.

**Trade-off:**
Strangler giảm big-bang risk nhưng tạo giai đoạn routing, duplicate model và compatibility layer phức tạp. Với hệ thống nhỏ sắp retired, chi phí đó có thể không đáng.

**Middle → Senior insight:**
Middle developer cần bảo toàn contract và regression behavior giữa old/new path. Senior / Technical developer phải chọn migration seam, rollback strategy, observability và thời điểm xóa compatibility layer để kiến trúc tạm thời không tồn tại vĩnh viễn.
