# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` cho bulk update khi không cần materialize entity

**Mẹo:**
Trong EF Core, nếu cần cập nhật nhiều row theo cùng một rule mà không cần chạy domain logic trên từng entity, cân nhắc `ExecuteUpdateAsync()` thay vì `ToListAsync()` rồi sửa từng object và `SaveChangesAsync()`.

**Tại sao hữu ích:**
Materialize hàng nghìn entity làm tăng allocation, change-tracking cost và network traffic. Set-based update đẩy phép cập nhật xuống database dưới dạng một `UPDATE`, thường nhanh và tiết kiệm memory hơn nhiều.

**Ví dụ:**
```csharp
var affected = await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now), ct);
```

Nếu chỉ cần thay đổi trạng thái theo predicate, không cần tải toàn bộ `Order` về process.

**Lưu ý:**
`ExecuteUpdateAsync` bỏ qua change tracker và không tự chạy business behavior đang nằm trong entity setter/event pipeline của application. Nếu `DbContext` đã tracking cùng các entity đó, state trong memory có thể stale. Dùng set-based update khi semantics cho phép, không chỉ vì nó nhanh hơn.

### Tip 2 — Tách Kubernetes `startupProbe`, `readinessProbe` và `livenessProbe` theo đúng failure semantics

**Mẹo:**
Đừng dùng một endpoint health check giống nhau cho cả ba probe. `startupProbe` xác định application đã khởi động xong chưa, `readinessProbe` quyết định pod có nên nhận traffic, còn `livenessProbe` chỉ nên phát hiện trạng thái process thực sự cần restart.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc database hoặc external API, một outage downstream có thể khiến Kubernetes restart hàng loạt pod đang hoàn toàn khỏe, làm incident tệ hơn. Ngược lại, readiness cho phép tạm rút pod khỏi traffic mà không nhất thiết restart process.

**Ví dụ:**
```text
/startup
- kiểm tra app initialization hoàn tất

/ready
- app có thể phục vụ request quan trọng
- có thể kiểm tra dependency thiết yếu theo policy

/live
- process/event loop còn hoạt động
- tránh dependency remote dễ fail transient
```

Pod khởi động chậm có thể dùng `startupProbe` để liveness không giết process trước khi initialization hoàn tất.

**Lưu ý:**
Health endpoint quá nặng cũng tự tạo load lên dependency. Probe interval, timeout và failure threshold phải phù hợp startup/latency thực tế. Restart chỉ hữu ích khi process có khả năng tự phục hồi sau restart; nó không chữa được database outage hay configuration sai toàn cluster.

### Tip 3 — Dùng `concurrency` trong GitHub Actions để tránh hai deployment cùng ghi vào một environment

**Mẹo:**
Với workflow deploy từ cùng branch/environment, cấu hình `concurrency` để chỉ một deployment thuộc cùng logical group chạy tại một thời điểm và quyết định rõ run cũ nên bị cancel hay phải hoàn tất.

**Tại sao hữu ích:**
Hai commit được push gần nhau có thể tạo hai pipeline chạy song song. Nếu cả hai cùng migration database, deploy artifact hoặc update infrastructure, run cũ có thể hoàn tất sau run mới và vô tình đưa production quay lại version cũ.

**Ví dụ:**
```yaml
concurrency:
  group: production-${{ github.ref }}
  cancel-in-progress: true
```

Với production deployment có step không thể hủy an toàn, có thể chọn serialize nhưng không `cancel-in-progress`.

**Lưu ý:**
Concurrency group chỉ giải quyết coordination ở workflow level, không thay thế deployment lock hoặc idempotency của infrastructure khi có pipeline khác ngoài GitHub Actions. Đừng cancel một run đang ở giữa migration/destructive step nếu workflow không được thiết kế để chịu interruption.

### Tip 4 — Khi dùng coding agent, yêu cầu nó chứng minh thay đổi bằng repository evidence và test thực tế

**Mẹo:**
Khi giao task cho AI coding agent, yêu cầu agent trước tiên xác định file, call path, test liên quan và version dependency từ repository; sau khi sửa phải chạy build/test/lint phù hợp và báo rõ phần nào chưa verify được.

**Tại sao hữu ích:**
Agent có thể viết code hợp cú pháp nhưng dựa trên API không tồn tại, convention khác codebase hoặc assumption sai về architecture. Grounding vào source hiện tại và verification bằng tool biến AI từ generator thành một phần của engineering workflow có evidence.

**Ví dụ:**
```text
Task: sửa duplicate payment callback

Yêu cầu agent:
1. tìm endpoint + handler hiện tại
2. xác định idempotency mechanism đã có
3. đọc test liên quan
4. patch tối thiểu
5. chạy targeted tests
6. chạy build
7. liệt kê assumption còn chưa xác minh
```

Nếu agent đề xuất package mới, yêu cầu kiểm tra version/framework compatibility trong project trước khi thêm.

**Lưu ý:**
Test xanh không chứng minh thay đổi đúng nếu test thiếu case quan trọng hoặc agent đã sửa test để khớp implementation sai. Review diff, security boundary, migration và behavior production vẫn cần technical judgment của developer.

### Tip 5 — Dùng `TimeProvider` để test logic phụ thuộc thời gian mà không `Thread.Sleep`

**Mẹo:**
Với code .NET phụ thuộc `UtcNow`, timeout hoặc expiration, inject `TimeProvider` thay vì gọi `DateTime.UtcNow` trực tiếp khắp business logic. Test có thể dùng fake time để tiến đồng hồ một cách deterministic.

**Tại sao hữu ích:**
Test expiration thường flaky hoặc chậm nếu phải chờ thời gian thật. Clock abstraction cho phép test boundary như “hết hạn đúng sau 30 phút” ngay lập tức và giảm dependency ẩn vào system clock.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

Trong test, dùng fake `TimeProvider` phù hợp rồi advance thời gian thay vì sleep.

**Lưu ý:**
Không cần abstract mọi API thời gian bằng interface tự viết nếu platform abstraction đã đủ. Với distributed system, fake clock giúp test logic nhưng không loại bỏ vấn đề clock skew giữa host; protocol quan trọng vẫn cần tolerance và server-side source of truth phù hợp.

## 🧠 Software Design

### Design 1 — Idempotency Key cho command có side effect mà client có thể retry

**Khái niệm:**
Idempotency Key cho phép server nhận biết nhiều request thực chất là cùng một logical command. Server lưu kết quả hoặc trạng thái xử lý theo key trong một phạm vi nhất định để retry không tạo side effect mới.

**Vấn đề nó giải quyết:**
Client gửi `POST /payments`, server đã charge thành công nhưng response bị timeout. Client không biết kết quả và retry. Nếu mỗi request được coi là mới, khách hàng có thể bị charge hai lần dù cả client lẫn server đều đang hành xử “hợp lý”.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: checkout-7812-payment-1

Request 1:
- claim key
- thực hiện payment
- lưu response/result

Retry cùng key + cùng payload:
- không charge lại
- trả lại outcome đã biết
```

Record idempotency nên có trạng thái như processing/completed/failed và policy xử lý request đồng thời cùng key.

**Trade-off:**
Idempotency tăng an toàn khi retry nhưng thêm storage, expiry, payload fingerprinting và concurrency handling. Key scope quá rộng gây collision; retention quá ngắn có thể không bao phủ retry window. Không phải mọi operation cần idempotency store riêng: `PUT` theo resource identity đôi khi đã có semantics phù hợp.

**Middle → Senior insight:**
Middle developer cần hiểu retry của `POST` có thể nhân side effect. Senior / Technical developer phải xác định logical operation identity, atomic claim, replay response, TTL, conflict khi cùng key nhưng payload khác và interaction với downstream idempotency trước khi tuyên bố endpoint “retry-safe”.

### Design 2 — Modular Monolith phù hợp khi cần boundary rõ nhưng chưa cần distributed deployment

**Khái niệm:**
Modular Monolith giữ nhiều business module trong một deployable nhưng áp boundary rõ về ownership, dependency và data access. Mục tiêu là modularity trong code/domain trước, distribution chỉ được thêm khi có lý do vận hành hoặc tổ chức đủ mạnh.

**Vấn đề nó giải quyết:**
Team muốn tách Orders, Billing và Catalog để giảm coupling nhưng traffic, team size và release cadence chưa biện minh cho nhiều service. Tách Microservices quá sớm sẽ biến method call/transaction local thành network, retry, observability và eventual-consistency problem.

**Ví dụ thực tế:**
```text
Nexora.Api
Modules/
  Orders/
  Billing/
  Catalog/

Rules:
- module không truy cập trực tiếp table/private type của module khác
- giao tiếp qua public contract hoặc application boundary
- một deployment, một operational unit
```

Khi một module thực sự cần scale hoặc ownership độc lập, boundary đã rõ sẽ giúp extraction ít rủi ro hơn.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment và transaction nhưng vẫn chia sẻ process; một memory leak hoặc deployment lỗi có thể ảnh hưởng toàn application. Boundary chỉ tồn tại nếu được enforce bằng code review/test/analyzer, không phải vì folder được đặt tên đẹp.

**Middle → Senior insight:**
Middle developer cần tránh cross-module shortcut phá encapsulation. Senior / Solution-oriented engineer phải chọn deployable boundary dựa trên team ownership, scaling profile, data consistency, release independence và operational maturity — không dùng Microservices như synonym của kiến trúc tốt.

### Design 3 — Event schema phải tiến hóa độc lập với thời điểm deploy producer và consumer

**Khái niệm:**
Event schema evolution thiết kế message sao cho producer mới và consumer cũ có thể cùng tồn tại trong một khoảng rollout. Thay đổi additive, tolerant reader và schema/version policy giúp giảm yêu cầu deploy đồng thời mọi thành phần.

**Vấn đề nó giải quyết:**
Producer thêm hoặc đổi field trong `OrderCreated` rồi deploy trước Analytics consumer. Nếu consumer deserialize strict hoặc semantics field cũ bị thay đổi âm thầm, message có thể vào dead-letter hoặc tệ hơn: vẫn xử lý nhưng hiểu sai business meaning.

**Ví dụ thực tế:**
```json
// v1
{
  "orderId": "O-42",
  "total": 125.00
}

// additive evolution
{
  "orderId": "O-42",
  "total": 125.00,
  "currency": "USD"
}
```

Consumer cũ bỏ qua `currency`; consumer mới dùng field khi có và áp fallback rõ cho message lịch sử nếu contract cho phép.

**Trade-off:**
Compatibility giúp deployment độc lập nhưng giữ legacy semantics lâu hơn. Version event riêng làm breaking change rõ ràng hơn nhưng tăng số schema/consumer path phải hỗ trợ. Schema registry có thể tăng governance nhưng cũng thêm tooling và quy trình vận hành.

**Middle → Senior insight:**
Middle developer cần coi message đã publish là contract, không phải DTO nội bộ có thể refactor tùy ý. Senior / Technical developer phải xác định compatibility rule, ownership, deprecation window, replay/history behavior và cách rollout producer-consumer để schema evolution không trở thành distributed breaking change.
