# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — LOH allocation có thể biến throughput tốt thành GC pause khó đoán

**Mẹo:**
Khi .NET service xử lý payload/buffer lớn, theo dõi allocation size và Large Object Heap (LOH) thay vì chỉ nhìn tổng memory. Tránh tạo lặp lại các `byte[]`, `char[]` hoặc object graph lớn nếu có thể stream hoặc reuse buffer an toàn.

**Tại sao hữu ích:**
Object lớn đi vào LOH và thường sống đến Gen 2 collection. Một API export/file-processing có allocation rate cao có thể vẫn “không leak” nhưng tạo Gen 2 GC pressure và latency spikes. Vì vậy memory graph ổn định không đồng nghĩa allocation pattern là tốt.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```
Nếu p99 latency tăng đồng thời với allocation rate, LOH size và Gen 2 GC, tiếp tục profile allocation call stacks trước khi tối ưu code ngẫu nhiên. Với file lớn, ưu tiên streaming thay vì `ReadAllBytesAsync()` khi workflow cho phép.

**Lưu ý:**
Đừng pool mọi object để “né GC”; pooling làm tăng lifetime, retained memory và complexity. Chỉ tối ưu sau khi profiling chứng minh allocation/GC là bottleneck thực tế.

### Tip 2 — SQL plan tốt cho một parameter có thể tệ cho parameter khác

**Mẹo:**
Khi stored procedure/query đột nhiên chậm với một số input nhưng nhanh với input khác, kiểm tra data skew và execution plan reuse trước khi kết luận thiếu index.

**Tại sao hữu ích:**
Optimizer có thể compile plan dựa trên cardinality estimate phù hợp với một parameter distribution rồi reuse plan đó cho input có selectivity hoàn toàn khác. Triệu chứng thường là cùng SQL text nhưng latency/reads biến động rất lớn theo parameter.

**Ví dụ:**
```text
Tenant A: 300 rows     → index seek phù hợp
Tenant B: 8,000,000 rows → cùng plan gây hàng triệu lookups
```
So sánh actual execution plan, estimated vs actual rows, logical reads và parameter values. Sau đó mới đánh giá query rewrite, statistics, index design hoặc engine-specific mitigation.

**Lưu ý:**
Không dùng `OPTION (RECOMPILE)` hoặc hint như thuốc chữa mặc định; compile CPU và plan-cache behavior có trade-off. Cần xác nhận nguyên nhân bằng evidence và phiên bản/database engine cụ thể.

### Tip 3 — Cosmos DB partition key phải đi cùng access pattern, không chỉ cardinality cao

**Mẹo:**
Chọn partition key dựa trên cách dữ liệu được đọc/ghi và cách throughput phân bố; “field có nhiều giá trị” chưa đủ để trở thành partition key tốt.

**Tại sao hữu ích:**
Query không có partition key có thể fan-out qua nhiều physical partitions và tăng RU/latency. Ngược lại, một key dồn traffic vào vài logical partitions tạo hot partition dù tổng container còn nhiều capacity.

**Ví dụ:**
```text
SaaS audit events:
Bad candidate:  Country
Candidate:      TenantId
Question tiếp theo:
- tenant lớn nhất tạo bao nhiêu traffic/data?
- query thường scope theo tenant không?
- có tenant “whale” gây hotspot không?
```
Đo RU charge và partition-level workload thay vì chỉ benchmark trên dataset nhỏ đồng đều.

**Lưu ý:**
Partition key là quyết định khó thay đổi sau khi dữ liệu lớn. Một key tốt cho writes chưa chắc tốt cho analytics queries; đôi khi cần read model/container riêng thay vì ép một model phục vụ mọi workload.

### Tip 4 — Trace sampling phải giữ được lỗi và tail latency cần điều tra

**Mẹo:**
Khi volume distributed tracing quá lớn, đừng giảm sampling ngẫu nhiên rồi giả định observability vẫn tương đương. Thiết kế sampling để vẫn giữ signal quan trọng như errors, slow traces hoặc critical operations khi platform hỗ trợ.

**Tại sao hữu ích:**
Head sampling 1% giảm chi phí mạnh nhưng có thể bỏ đúng request hiếm gây p99. Khi incident chỉ xảy ra 0.1% traffic, trace dataset “đẹp” có thể đơn giản vì các trace xấu không được giữ lại.

**Ví dụ:**
```text
Metrics: phát hiện checkout p99 tăng
Trace policy: ưu tiên giữ failed/slow checkout traces
Logs: correlation bằng trace/span ID cho contextual detail
```
Đặt sampling cùng telemetry budget và câu hỏi vận hành, không chỉ theo một tỷ lệ cố định.

**Lưu ý:**
Sampling không sửa high-cardinality instrumentation hoặc logging quá mức. Tail-based sampling cũng cần buffering/collector resources và có operational cost riêng.

### Tip 5 — Legacy jQuery AJAX cần kiểm tra CSRF khi dựa vào cookie authentication

**Mẹo:**
Khi bảo trì ASP.NET MVC/CMS cũ dùng jQuery AJAX và cookie authentication, kiểm tra anti-forgery protection cho các state-changing requests; `same-origin` AJAX không tự biến request thành an toàn trước CSRF.

**Tại sao hữu ích:**
Browser tự gửi authentication cookie theo policy của cookie. Nếu server chấp nhận POST thay đổi dữ liệu mà không có CSRF defense phù hợp, attacker có thể khiến browser của user đã đăng nhập gửi request ngoài ý muốn.

**Ví dụ:**
```javascript
$.ajax({
  method: "POST",
  url: "/account/change-email",
  headers: { "RequestVerificationToken": token },
  data: payload
});
```
Server phải validate token bằng framework mechanism tương ứng; đồng thời cấu hình `SameSite`, `Secure` và cookie policy theo authentication flow thực tế.

**Lưu ý:**
CORS không phải CSRF protection. Với bearer token không tự động được browser attach, threat model khác; đừng copy cùng mitigation mà không hiểu credential transport.

## 🧠 Software Design

### Design 1 — Strangler Fig cho modernization thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig modernization chuyển từng capability khỏi legacy system qua một boundary có kiểm soát, để hệ thống mới dần nhận traffic/responsibility thay vì thay toàn bộ application trong một lần cutover.

**Vấn đề nó giải quyết:**
Một .NET Framework CMS/enterprise application lớn cần lên modern .NET nhưng chứa nhiều business rules ngầm, integration cũ và release dependency. Big-bang rewrite kéo dài feedback cycle và đến ngày cutover mới phát hiện behavior đã bị bỏ sót.

**Ví dụ thực tế:**
Đặt routing/facade trước legacy application. Chuyển `Product Search` sang ASP.NET Core service/module trước, giữ checkout cũ. Contract, telemetry và rollback path được xác nhận trước khi tiếp tục migrate capability kế tiếp.

**Trade-off:**
Giảm migration risk và tạo incremental value, nhưng trong transition phải vận hành hai implementations, routing, duplicated models và compatibility logic. Nếu không có exit criteria, “temporary bridge” có thể tồn tại nhiều năm.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility và regression tests khi tách capability. Senior / Technical developer phải chọn seam theo business ownership/data coupling, thiết kế migration order, observability, rollback và chiến lược loại bỏ legacy thay vì chỉ chia code theo controller/project.

### Design 2 — Contract Testing cho integration boundary, không thay thế Integration/E2E Test

**Khái niệm:**
Contract testing kiểm tra producer và consumer có đồng thuận về interface/behavior observable tại integration boundary. Nó tập trung vào compatibility giữa independently evolving components, không chứng minh toàn workflow production hoạt động.

**Vấn đề nó giải quyết:**
Team API đổi field required, enum hoặc response semantics; unit tests của cả hai repository vẫn pass nhưng consumer chỉ vỡ sau deployment. Full E2E có thể bắt lỗi nhưng thường chậm, brittle và khó chạy cho mọi combination version.

**Ví dụ thực tế:**
Mobile backend phụ thuộc `Catalog API`. Consumer contract xác định request/response thực sự cần; provider verification chạy trong CI trước release. Một smoke/E2E suite nhỏ vẫn kiểm tra authentication, networking và deployment wiring trên environment thật.

**Trade-off:**
Contract tests cho feedback compatibility nhanh và ownership rõ hơn nhưng tạo contract lifecycle/versioning overhead. Contract quá implementation-specific sẽ khóa producer; contract quá lỏng lại không bảo vệ consumer.

**Middle → Senior insight:**
Middle developer cần test observable contract thay vì mock tùy ý theo assumption. Senior / Technical developer phải quyết định boundary nào đáng contract-test, ownership/version policy và cách phối hợp unit, integration, contract và E2E tests để tránh vừa thiếu coverage vừa tạo test pyramid đắt đỏ.

### Design 3 — Saga orchestration vs choreography cho multi-service workflow

**Khái niệm:**
Saga chia business transaction xuyên nhiều service thành local transactions cùng compensating actions. Orchestration dùng coordinator điều khiển flow; choreography để services phản ứng với events mà không có một coordinator trung tâm.

**Vấn đề nó giải quyết:**
Order flow cần reserve inventory, authorize payment và arrange fulfillment nhưng không thể giữ một ACID transaction xuyên các independent databases/services. Partial failure buộc hệ thống phải biết trạng thái nào đã commit và cần bù trừ gì.

**Ví dụ thực tế:**
Order orchestrator gửi `ReserveInventory`, sau đó `AuthorizePayment`; nếu payment thất bại, nó yêu cầu `ReleaseInventory`. Với choreography, `InventoryReserved` kích hoạt payment và các events tiếp theo dẫn workflow tiến lên hoặc compensate.

**Trade-off:**
Orchestration làm flow/state/error handling dễ nhìn hơn nhưng coordinator có thể trở thành coupling hotspot. Choreography giảm central control và hợp event-driven autonomy nhưng flow business dễ bị phân tán qua nhiều handlers, khó quan sát và thay đổi khi workflow dài.

**Middle → Senior insight:**
Middle developer cần hiểu compensation không phải database rollback và handlers phải chịu duplicate/retry. Senior / Technical developer phải chọn coordination model dựa trên workflow complexity, ownership, observability và evolution; đồng thời định nghĩa durable saga state, timeout, idempotency và manual recovery cho trường hợp compensation cũng thất bại.
