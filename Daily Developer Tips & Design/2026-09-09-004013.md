# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán ThreadPool starvation bằng evidence thay vì tăng thread tùy ý

**Mẹo:**
Khi ASP.NET Core API có latency tăng mạnh dưới tải nhưng CPU chưa cao, kiểm tra ThreadPool starvation trước khi kết luận database hoặc network là bottleneck.

**Tại sao hữu ích:**
Nếu nhiều request giữ thread bằng blocking call như .Result, .Wait() hoặc synchronous I/O, ThreadPool phải tạo thêm worker thread dần dần. Trong thời gian đó request mới xếp hàng, latency tăng dù CPU có thể vẫn thấp.

**Ví dụ:**
Một incident có thể có dấu hiệu:

    request p95: 300 ms -> 5 s
    CPU: 35%
    active requests: tăng mạnh
    ThreadPool queue length: tăng
    thread count: tăng dần

Nếu trace cho thấy nhiều call stack chặn tại Task.Wait hoặc synchronous HTTP/DB APIs, nguyên nhân gần với starvation hơn là thiếu CPU.

**Lưu ý:**
Đừng sửa bằng cách tăng MinThreads ngay lập tức. Việc đó có thể che symptom và tăng context switching. Ưu tiên loại blocking work khỏi request path, dùng async end-to-end và đo lại dưới workload thật.

### Tip 2 — Dùng partial index trong PostgreSQL khi chỉ một phần nhỏ dữ liệu được query thường xuyên

**Mẹo:**
Nếu query nóng chỉ nhắm tới một subset rõ ràng như đơn hàng chưa xử lý, cân nhắc partial index thay vì index toàn bộ table.

**Tại sao hữu ích:**
Index nhỏ hơn tiêu tốn ít storage, ít write amplification và có thể nằm trong memory hiệu quả hơn. PostgreSQL optimizer có thể dùng partial index khi WHERE clause của query phù hợp predicate của index.

**Ví dụ:**
Một bảng Orders có hàng chục triệu row nhưng chỉ vài phần trăm ở trạng thái Pending:

    CREATE INDEX idx_orders_pending_created
    ON orders (created_at)
    WHERE status = 'Pending';

Query:

    SELECT id, created_at
    FROM orders
    WHERE status = 'Pending'
    ORDER BY created_at
    LIMIT 100;

**Lưu ý:**
Partial index không hữu ích nếu workload thường query nhiều trạng thái khác nhau. Predicate phải khớp với query pattern thực tế; luôn kiểm tra EXPLAIN ANALYZE thay vì giả định optimizer sẽ chọn index.

### Tip 3 — Với CDN, dùng stale-while-revalidate để giảm latency mà vẫn giữ freshness hợp lý

**Mẹo:**
Với content public có thể chấp nhận stale ngắn, cấu hình Cache-Control với stale-while-revalidate để CDN trả response cũ ngay trong lúc refresh bản mới ở background.

**Tại sao hữu ích:**
Khi cache hết hạn, nếu mọi request đều chờ origin render lại, latency tăng và có thể tạo burst xuống backend. stale-while-revalidate giữ trải nghiệm nhanh trong khoảng refresh ngắn.

**Ví dụ:**
Một response CMS có thể trả:

    Cache-Control: public, max-age=60, stale-while-revalidate=300

Sau 60 giây, CDN có thể phục vụ bản cũ tối đa thêm 300 giây trong khi request refresh được gửi tới origin.

**Lưu ý:**
Không dùng strategy này cho dữ liệu nhạy cảm, user-specific hoặc thông tin cần consistency tức thời. Cũng cần hiểu CDN/proxy đang dùng có hỗ trợ directive và invalidation semantics như mong đợi hay không.

### Tip 4 — Dùng TypeScript discriminated union để model UI state thay vì nhiều boolean mâu thuẫn

**Mẹo:**
Khi component có nhiều trạng thái mutually exclusive như loading, success và error, dùng discriminated union thay vì các boolean độc lập.

**Tại sao hữu ích:**
Các boolean như isLoading, hasError và hasData có thể tạo combination vô nghĩa. Union type ép state chỉ nằm trong các shape hợp lệ và giúp compiler kiểm tra exhaustiveness.

**Ví dụ:**
Thay vì:

    isLoading: boolean
    error?: string
    data?: Product[]

Có thể model:

    type State =
      | { kind: 'loading' }
      | { kind: 'error'; message: string }
      | { kind: 'success'; data: Product[] };

Render logic switch theo kind và compiler có thể cảnh báo khi thiếu case.

**Lưu ý:**
Không cần biến mọi object thành union phức tạp. Dùng khi state machine thực sự có các trạng thái loại trừ nhau và bug từ invalid combinations có ý nghĩa.

### Tip 5 — Với AI coding agent, yêu cầu evidence từ repository trước khi chấp nhận thay đổi kiến trúc

**Mẹo:**
Khi dùng AI để sửa code hoặc đề xuất refactor lớn, yêu cầu nó chỉ ra file, dependency, call path và test hiện có làm evidence trước khi đổi abstraction hoặc module boundary.

**Tại sao hữu ích:**
Agent có thể suy diễn pattern từ code fragment nhỏ rồi đề xuất thêm layer, interface hoặc service không phù hợp với repository thực tế. Grounding vào source giúp giảm hallucinated architecture và accidental complexity.

**Ví dụ:**
Một workflow review tốt:

    1. Tìm tất cả call sites của service cần đổi.
    2. Xác định public contract và test liên quan.
    3. Nêu invariant phải giữ.
    4. Đề xuất patch nhỏ nhất.
    5. Chạy test và so diff trước/sau.

**Lưu ý:**
Không coi việc agent trích được nhiều file là bằng chứng nó hiểu đúng domain. Developer vẫn phải kiểm tra assumption, edge case, security impact và behavior ngoài test coverage.

## 🧠 Software Design

### Design 1 — Schema Compatibility trong Event-Driven Architecture

**Khái niệm:**
Event schema cần evolve sao cho producer mới và consumer cũ có thể cùng tồn tại trong thời gian rollout. Thay đổi additive thường an toàn hơn rename, remove hoặc đổi meaning của field hiện có.

**Vấn đề nó giải quyết:**
Trong distributed system, producer và consumer hiếm khi deploy cùng lúc. Nếu producer đổi event contract đột ngột, một consumer chưa nâng cấp có thể fail hoặc diễn giải sai dữ liệu.

**Ví dụ thực tế:**
Thay vì đổi trực tiếp:

    customerName -> displayName

có thể thêm displayName trước, giữ customerName trong giai đoạn migration, theo dõi consumer usage rồi mới deprecate field cũ.

**Trade-off:**
Compatibility làm schema tồn tại song song lâu hơn và tăng maintenance. Breaking change giúp model sạch nhanh nhưng chuyển migration cost sang mọi consumer và tăng release coordination.

**Middle → Senior insight:**
Middle developer cần nhận diện thay đổi breaking và viết consumer tolerant với field mới. Senior / Technical developer phải thiết kế versioning policy, contract test, deprecation window và rollout sequence theo ownership của producer/consumer.

### Design 2 — KISS/YAGNI vs “framework nội bộ” dùng chung mọi nơi

**Khái niệm:**
KISS và YAGNI nhắc team chỉ thêm abstraction khi có pressure thực tế. Một generic internal framework được xây quá sớm thường encode assumption chưa được chứng minh.

**Vấn đề nó giải quyết:**
Ba module có code hơi giống nhau không nhất thiết cần một generic engine. Nếu business rule của chúng sẽ diverge, abstraction chung có thể tạo coupling và buộc mọi change đi qua cùng một framework.

**Ví dụ thực tế:**
Ba integration cùng có retry, logging và HTTP call nên có thể reuse infrastructure concern. Nhưng business mapping và validation khác nhau nên không nhất thiết ép vào một GenericIntegrationProcessor<TRequest,TResponse,TPolicy>.

**Trade-off:**
Abstraction đúng giảm duplication và tạo consistency. Abstraction sớm làm API khó hiểu, tăng indirection và khiến thay đổi domain phải sửa framework dùng chung.

**Middle → Senior insight:**
Middle developer cần tránh copy-paste mù và cũng tránh generic hóa theo phản xạ. Senior / Technical developer phải nhận biết stable variation point, cost of change và khi nào duplication nhỏ rẻ hơn một abstraction sai.

### Design 3 — Read Replica giúp scale đọc nhưng không loại bỏ consistency trade-off

**Khái niệm:**
Read replica tách một phần workload đọc khỏi primary database bằng cách replicate dữ liệu sang node đọc riêng. Application phải chấp nhận replication lag hoặc route một số read trở lại primary.

**Vấn đề nó giải quyết:**
Dashboard, reporting hoặc search-like read workload có thể gây pressure lên primary vốn đang xử lý transaction write quan trọng. Replica giúp phân tán I/O và connection load.

**Ví dụ thực tế:**
Sau khi user cập nhật profile:

    write -> primary
    immediate read-your-write -> primary
    reporting/dashboard -> replica

Nếu mọi read đều route replica, user có thể vừa save xong nhưng vài giây sau vẫn thấy dữ liệu cũ.

**Trade-off:**
Replica tăng read capacity và isolation workload nhưng thêm cost, topology, failover complexity và stale-read semantics. Nó không sửa query chậm do index/query design kém.

**Middle → Senior insight:**
Middle developer cần hiểu read-after-write không được đảm bảo trên replica. Senior / Technical developer phải phân loại query nào chấp nhận eventual consistency, thiết kế routing/fallback và đo replication lag trước khi coi replica là giải pháp scale mặc định.
