# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — Bounded `Channel<T>` tạo backpressure thay vì để queue ăn hết memory

**Mẹo:**
Khi producer có thể tạo work nhanh hơn consumer xử lý, ưu tiên `Channel.CreateBounded<T>()` với capacity có chủ đích thay vì dùng queue không giới hạn.

**Tại sao hữu ích:**
Unbounded queue che giấu overload: request vẫn enqueue thành công nhưng backlog tăng, latency kéo dài và memory tiếp tục phình. Bounded channel biến capacity thành một phần của flow-control; producer phải chờ, drop hoặc fail theo policy rõ ràng.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, ct);
```
Một `BackgroundService` xử lý thumbnail có thể dùng capacity 500 để giới hạn backlog thay vì nhận vô hạn work trong traffic spike.

**Lưu ý:**
Capacity 500 không tự nhiên là đúng. Cần chọn từ throughput, acceptable queue latency và memory footprint. Với work không được phép mất khi process restart, in-memory `Channel<T>` không thay thế durable broker như Azure Service Bus.

### Tip 2 — Filtered/partial index hữu ích khi query chỉ tập trung vào một tập row nhỏ

**Mẹo:**
Nếu hot query luôn lọc một trạng thái hiếm, cân nhắc filtered index trong SQL Server hoặc partial index trong PostgreSQL thay vì index toàn bộ bảng.

**Tại sao hữu ích:**
Index nhỏ hơn tốn ít storage, cache pages và write maintenance hơn. Khi predicate khớp workload, optimizer có thể tìm tập row cần thiết mà không duy trì index entries cho phần lớn dữ liệu không bao giờ được query theo đường đó.

**Ví dụ:**
SQL Server:
```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON Orders(CreatedAt)
WHERE Status = 'Pending';
```
Nếu worker chỉ poll một tỷ lệ nhỏ `Pending` orders, index này có thể phù hợp hơn index `(Status, CreatedAt)` trên toàn bộ lịch sử orders.

**Lưu ý:**
Predicate của query phải tương thích với điều kiện index và workload phải đủ ổn định. Nếu `Pending` thực tế chiếm phần lớn bảng hoặc nhiều query cần trạng thái khác, lợi ích giảm. Xác nhận bằng execution plan, logical reads và write cost.

### Tip 3 — Đừng đọc Azure Key Vault trên mỗi HTTP request

**Mẹo:**
Với secrets/configuration dùng thường xuyên, tải chúng qua configuration/provider hoặc cache có lifecycle phù hợp thay vì gọi Azure Key Vault trực tiếp trên từng request.

**Tại sao hữu ích:**
Per-request secret lookup biến Key Vault thành synchronous runtime dependency của hot path, thêm network latency, quota pressure và một failure mode mới. Application thường chỉ cần refresh secret theo chu kỳ hoặc khi configuration thay đổi.

**Ví dụ:**
Một payment API cần client secret để gọi provider. Thay vì `GetSecretAsync()` cho mỗi checkout, application lấy secret qua startup/configuration path, giữ trong memory theo policy và hỗ trợ rotation bằng version/refresh strategy phù hợp.

**Lưu ý:**
Cache secret vô thời hạn có thể phá rotation. Không log secret value và không biến fallback thành hard-coded secret. Với Managed Identity-supported dependency, ưu tiên identity-based authentication để giảm số secrets phải quản lý.

### Tip 4 — Playwright test phải sở hữu state của chính nó

**Mẹo:**
E2E test nên tạo dữ liệu cần thiết hoặc dùng fixture/API setup riêng, thay vì phụ thuộc test trước đã tạo user/order/content.

**Tại sao hữu ích:**
Test phụ thuộc thứ tự thường pass khi chạy cả suite nhưng fail khi chạy riêng, parallel hoặc retry. Isolation giúp failure có ý nghĩa hơn và cho phép CI shard/parallelize suite mà không tạo race giữa tests.

**Ví dụ:**
Test `admin can publish article` tạo một draft article bằng API fixture với unique ID, đăng nhập bằng storage state phù hợp, publish rồi verify UI/API. Nó không giả định `create article` test vừa chạy trước đó.

**Lưu ý:**
Tạo dữ liệu qua UI cho mọi test có thể làm suite rất chậm. Dùng UI cho behavior cần kiểm tra; dùng API/database fixture có kiểm soát cho setup. Cleanup cũng phải tránh xóa dữ liệu của test đang chạy song song.

### Tip 5 — CMS cache phải invalidation theo dependency, không chỉ theo TTL

**Mẹo:**
Trong CMS như Optimizely, khi rendered output phụ thuộc content, navigation hoặc shared block, thiết kế cache key/dependency để publish liên quan làm cache mất hiệu lực đúng phạm vi.

**Tại sao hữu ích:**
TTL dài cải thiện latency nhưng dễ phục vụ content cũ sau publish. TTL quá ngắn lại đẩy load về CMS/database. Dependency-aware invalidation giữ cache lâu khi dữ liệu không đổi nhưng phản ứng nhanh với editorial changes.

**Ví dụ:**
Một landing page cache HTML 20 phút nhưng chứa shared promotion block. Khi editor publish promotion mới, cache của các page phụ thuộc block đó cần được invalidated thay vì chờ từng page hết TTL.

**Lưu ý:**
Dependency graph quá rộng có thể biến một publish thành cache flush diện rộng và gây stampede. Phân biệt content cache, application cache và CDN cache; invalidating origin cache không đồng nghĩa Akamai/CDN đã purge.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like access qua `DbSet<T>`. Một custom Repository chỉ có giá trị khi nó tạo boundary hoặc abstraction có ý nghĩa cho application, không phải vì mọi project đều cần thêm một layer.

**Vấn đề nó giải quyết:**
Application có thể cần gom complex persistence policy, giới hạn query surface hoặc cô lập một data source thay đổi. Nhưng generic `IRepository<T>` với `GetAll/Add/Update/Delete` thường chỉ bọc lại EF Core và làm mất `IQueryable`, projection hoặc provider-specific capability.

**Ví dụ thực tế:**
Một CRUD module nhỏ inject `AppDbContext` trực tiếp vào application handler và project DTO bằng LINQ. Một pricing module có persistence rules phức tạp có thể expose `IPriceBookRepository` với operations theo domain như `LoadActivePriceBook()` thay vì generic CRUD methods.

**Trade-off:**
Direct `DbContext` giảm ceremony và giữ đầy đủ EF Core capability nhưng application layer biết persistence technology. Repository có thể tạo boundary/test seam tốt hơn nhưng thêm abstraction, mapping và nguy cơ trở thành pass-through layer.

**Middle → Senior insight:**
Middle developer cần quản lý `DbContext` lifetime, query và transaction đúng. Senior / Technical developer phải hỏi abstraction đang bảo vệ business boundary nào, chi phí thay đổi data access thực sự là gì và liệu repository có giảm coupling hay chỉ di chuyển code sang thêm một folder.

### Design 2 — Azure Functions vs Worker Service

**Khái niệm:**
Azure Functions phù hợp event-driven execution với platform-managed triggers/scaling; Worker Service phù hợp process dài hạn khi team cần kiểm soát lifecycle, hosting, concurrency và runtime behavior nhiều hơn.

**Vấn đề nó giải quyết:**
Background workload không giống nhau. Một Blob-created handler chạy ngắn và bursty có pressure khác service liên tục giữ connections, chạy polling loop hoặc cần predictable process lifetime.

**Ví dụ thực tế:**
Resize ảnh khi Blob được upload có thể hợp với Function trigger. Một pricing engine liên tục consume nhiều streams, giữ local state/cache và cần fine-grained graceful shutdown có thể phù hợp Worker Service chạy trên App Service, container hoặc Kubernetes hơn.

**Trade-off:**
Functions giảm hosting/trigger plumbing và có elastic scaling nhưng mang execution/runtime constraints, cold-start/cost behavior và platform semantics. Worker cho control cao hơn nhưng team sở hữu deployment, scaling, health checks và capacity planning nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, cancellation và idempotency. Senior / Technical developer phải chọn hosting model từ workload duration, traffic shape, state, scaling latency, operational ownership và cost; không chọn Functions chỉ vì task được gọi là “background job”.

### Design 3 — Synchronous REST vs asynchronous messaging

**Khái niệm:**
Synchronous REST phù hợp khi caller cần kết quả ngay trong request/response boundary. Messaging phù hợp khi work có thể hoàn tất sau, cần buffering, fan-out hoặc giảm temporal coupling giữa producer và consumer.

**Vấn đề nó giải quyết:**
Chuỗi synchronous dependencies làm latency và availability bị cộng dồn. Nhưng chuyển mọi call sang message lại đưa vào eventual consistency, retry, duplicate delivery và workflow state mà business có thể không cần.

**Ví dụ thực tế:**
Checkout cần xác nhận payment authorization trước khi trả success nên một synchronous call có thể hợp lý. Sau khi order đã commit, gửi `OrderPlaced` cho analytics/email/fulfillment qua broker giúp các capability đó không nằm trên critical response path.

**Trade-off:**
REST đơn giản hơn về control flow và immediate consistency nhưng caller phụ thuộc availability/latency của callee. Messaging hấp thụ burst và cô lập thời gian tốt hơn nhưng tăng operational complexity, observability requirements và consistency semantics.

**Middle → Senior insight:**
Middle developer cần triển khai timeout/retry cho REST và idempotent consumer cho messaging. Senior / Technical developer phải phân loại interaction là command/query/event, xác định consistency deadline, failure ownership và user-visible semantics trước khi chọn communication style.
