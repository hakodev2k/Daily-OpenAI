# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng ETag để tránh gửi lại resource không thay đổi

**Mẹo:**
Với REST API đọc dữ liệu ít thay đổi nhưng được request thường xuyên, cân nhắc hỗ trợ `ETag` + `If-None-Match` để client kiểm tra freshness mà không cần nhận lại toàn bộ payload.

**Tại sao hữu ích:**
Nếu representation không đổi, server có thể trả `304 Not Modified` thay vì serialize và truyền lại JSON lớn. Điều này giảm bandwidth, serialization cost và latency, đặc biệt hữu ích cho mobile API hoặc CMS content được đọc nhiều hơn ghi.

**Ví dụ:**
```http
GET /api/articles/42

HTTP/1.1 200 OK
ETag: "article-42-v17"
```

Request sau:

```http
GET /api/articles/42
If-None-Match: "article-42-v17"
```

Nếu version vẫn là 17:

```http
HTTP/1.1 304 Not Modified
```

**Lưu ý:**
ETag phải đại diện đúng cho representation mà client nhận. Nếu response thay đổi theo user, locale hoặc permission nhưng ETag không phản ánh các dimension đó, cache validation có thể sai hoặc thậm chí lộ dữ liệu.

### Tip 2 — Dùng keyset pagination khi offset lớn bắt đầu làm query chậm

**Mẹo:**
Với danh sách lớn và navigation tuần tự, ưu tiên keyset pagination dựa trên sort key ổn định thay vì `OFFSET` ngày càng lớn.

**Tại sao hữu ích:**
`OFFSET 100000` thường buộc database vẫn phải scan hoặc walk qua rất nhiều row trước khi trả page hiện tại. Keyset pagination bắt đầu từ giá trị cuối của page trước nên database có thể seek vào index phù hợp hiệu quả hơn.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt, Id) < (@LastCreatedAt, @LastId)
ORDER BY CreatedAt DESC, Id DESC
LIMIT 50;
```

Trong SQL Server có thể biểu diễn điều kiện tương đương bằng so sánh từng cột.

**Lưu ý:**
Sort key phải deterministic; thường cần thêm primary key làm tie-breaker. Keyset pagination cũng không phù hợp nếu UI yêu cầu nhảy trực tiếp đến “page 842” theo số trang cố định.

### Tip 3 — Theo dõi lock duration của Azure Service Bus khi message xử lý lâu

**Mẹo:**
Nếu consumer xử lý message lâu hơn `lock duration`, kiểm tra auto lock renewal hoặc chia nhỏ work thay vì chỉ tăng retry.

**Tại sao hữu ích:**
Trong Peek-Lock mode, message chỉ được giữ độc quyền trong thời gian lock còn hiệu lực. Nếu xử lý chưa xong mà lock hết hạn, broker có thể redeliver message cho consumer khác, tạo duplicate processing dù handler đầu tiên vẫn đang chạy.

**Ví dụ:**
```text
Lock duration: 30s
Processing time: 75s

00s  consumer A nhận message
30s  lock hết hạn
35s  consumer B nhận lại cùng message
75s  consumer A hoàn tất
```

Giải pháp có thể là lock renewal, rút ngắn critical processing, hoặc chuyển phần dài sang workflow phù hợp hơn.

**Lưu ý:**
Lock renewal không biến message processing thành exactly-once. Consumer vẫn cần idempotency vì duplicate delivery còn có thể xảy ra do crash, network failure hoặc acknowledgement thất bại.

### Tip 4 — Trong Optimizely CMS, đừng nhét dữ liệu external thay đổi nhanh vào content cache dài hạn

**Mẹo:**
Tách content editorial tương đối ổn định khỏi dữ liệu external có freshness khác, thay vì cache toàn bộ page model bằng cùng một lifetime.

**Tại sao hữu ích:**
Một trang CMS có thể chứa block editorial cache tốt trong vài phút hoặc lâu hơn, nhưng giá sản phẩm, availability hoặc user-specific data có thể thay đổi từng giây. Cache chung một lifetime dễ tạo stale data hoặc buộc bạn vô hiệu hóa cache quá thường xuyên.

**Ví dụ:**
```text
Landing page:
- Heading, hero image, editorial blocks -> CMS/content cache
- Product stock -> service/API riêng, TTL ngắn hoặc no-cache theo requirement
- User-specific recommendation -> không dùng shared response cache
```

**Lưu ý:**
Không nên tách mọi thứ thành network call nhỏ lẻ vì có thể tạo waterfall latency. Cần cân bằng freshness, cache boundary và số dependency call trên critical path.

### Tip 5 — Dùng mutation testing để phát hiện test “có coverage nhưng không có lực”

**Mẹo:**
Khi một module quan trọng có code coverage cao nhưng vẫn lọt regression, cân nhắc mutation testing để kiểm tra test có thực sự phát hiện thay đổi behavior hay không.

**Tại sao hữu ích:**
Coverage chỉ nói rằng code đã được chạy. Một test có thể execute branch nhưng không assert kết quả quan trọng. Mutation testing cố tình thay toán tử, condition hoặc return value; nếu test vẫn pass, test suite chưa bảo vệ behavior đó đủ tốt.

**Ví dụ:**
```text
Production code:
if (balance >= amount)

Mutation:
if (balance > amount)
```

Nếu toàn bộ test vẫn xanh, edge case `balance == amount` chưa được bảo vệ.

**Lưu ý:**
Mutation testing tốn CPU và không cần chạy toàn solution ở mọi commit. Nên tập trung vào domain logic hoặc module rủi ro cao, và không chạy theo mutation score như một KPI tuyệt đối.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp nhiều đặc tính của Unit of Work và Repository. Việc bọc thêm một repository chỉ có giá trị khi abstraction đó thể hiện boundary hoặc behavior có ý nghĩa, không phải chỉ để che các method như `Add`, `Find` và `SaveChanges`.

**Vấn đề nó giải quyết:**
Team thường thêm generic repository để “decouple khỏi EF Core”, nhưng kết quả có thể là một lớp pass-through làm mất `IQueryable`, projection, batching hoặc API tối ưu của EF Core mà vẫn không tạo khả năng đổi database thực tế.

**Ví dụ thực tế:**
```text
Order application service
-> DbContext trực tiếp
-> query/projection rõ ràng
-> transaction boundary tại use case
```

Repository chuyên biệt có thể đáng giá khi encapsulate query/domain boundary phức tạp như `IOrderRepository.LoadAggregateForPaymentAsync(...)`.

**Trade-off:**
Direct `DbContext` giảm ceremony và giữ toàn bộ capability của EF Core, nhưng coupling tới ORM rõ hơn. Repository có thể củng cố domain boundary và test seam, nhưng dễ trở thành abstraction nghèo nàn hoặc duplicate ORM API.

**Middle → Senior insight:**
Middle developer cần hiểu lifecycle và transaction của `DbContext` thay vì dùng repository theo thói quen. Senior / Technical developer phải đánh giá abstraction có thực sự ổn định boundary, giảm duplication hoặc bảo vệ invariant hay chỉ thêm indirection và maintenance cost.

### Design 2 — Service Bus Queue vs Topic theo ownership của work

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer xử lý; Topic + Subscription phù hợp khi cùng một event cần được nhiều consumer độc lập nhận và xử lý theo mục đích riêng.

**Vấn đề nó giải quyết:**
Dùng queue cho domain event nhiều subscriber khiến publisher phải biết từng downstream queue. Ngược lại, dùng topic cho command/work item có thể vô tình khiến nhiều subscriber cùng thực thi một action chỉ nên xảy ra một lần.

**Ví dụ thực tế:**
```text
GenerateInvoice command
-> Queue
-> một worker xử lý

OrderPlaced event
-> Topic
   -> Inventory subscription
   -> Analytics subscription
   -> Notification subscription
```

**Trade-off:**
Queue đơn giản cho competing consumers và work distribution. Topic hỗ trợ fan-out và loose coupling tốt hơn, nhưng tăng số subscription, filtering rule, dead-letter queue và operational surface cần theo dõi.

**Middle → Senior insight:**
Middle developer cần phân biệt command với event và hiểu competing consumer. Senior / Technical developer phải chọn topology dựa trên ownership, delivery semantics, subscriber independence, replay/recovery và operational complexity chứ không chỉ dựa trên số consumer hiện tại.

### Design 3 — Saga và compensating action khi không thể có một transaction toàn hệ thống

**Khái niệm:**
Saga chia một business workflow dài thành nhiều local transaction. Khi bước sau thất bại, hệ thống thực hiện compensating action cho các bước trước thay vì cố giữ distributed transaction xuyên nhiều service.

**Vấn đề nó giải quyết:**
Trong workflow như booking hoặc checkout, payment, inventory và shipping có thể nằm ở các service/datastore khác nhau. Giữ một ACID transaction xuyên tất cả dependency thường không khả thi hoặc tạo coupling và availability rất tệ.

**Ví dụ thực tế:**
```text
1. ReserveInventory -> success
2. CapturePayment   -> success
3. CreateShipment   -> fail

Compensation:
4. RefundPayment
5. ReleaseInventory
```

Các bước compensation phải được thiết kế như business operation thật, có idempotency và retry riêng.

**Trade-off:**
Saga tăng resilience và cho phép local autonomy, nhưng workflow trở thành eventual consistency, có intermediate state và nhiều failure path hơn. Compensation cũng không phải lúc nào có thể “undo” hoàn hảo, ví dụ email đã gửi hoặc external provider đã xử lý irreversible action.

**Middle → Senior insight:**
Middle developer cần hiểu mỗi bước là local transaction và handler phải idempotent. Senior / Technical developer phải chọn choreography hay orchestration, xác định compensation semantics, timeout/retry policy, observability và manual recovery cho các trạng thái không thể tự động phục hồi.
