# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup table được build một lần rồi đọc rất nhiều

**Mẹo:**
Trong .NET 8+, nếu một tập key/value được khởi tạo một lần rồi chỉ đọc trong suốt lifetime của process, cân nhắc chuyển nó sang `FrozenDictionary<TKey,TValue>` thay vì giữ `Dictionary<TKey,TValue>` mutable.

**Tại sao hữu ích:**
`FrozenDictionary` tối ưu layout cho read-heavy lookup sau khi build xong và đồng thời thể hiện rõ intent bất biến. Điều này phù hợp với mapping code, routing metadata, country/config lookup hoặc rule table được load lúc startup rồi dùng trên hot path.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

var handlers = new Dictionary<string, Func<Order, Task>>
{
    ["paid"] = HandlePaidAsync,
    ["cancelled"] = HandleCancelledAsync,
    ["refunded"] = HandleRefundedAsync
}.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);

if (handlers.TryGetValue(status, out var handler))
{
    await handler(order);
}
```

Điểm quan trọng là hoàn tất build trước, sau đó freeze để tối ưu giai đoạn đọc.

**Lưu ý:**
Việc tạo frozen collection có cost cao hơn dictionary bình thường, nên không phù hợp nếu collection nhỏ, tồn tại rất ngắn hoặc liên tục rebuild. Nếu dữ liệu phải update runtime, `FrozenDictionary` không thay thế concurrent/mutable collection.

### Tip 2 — Dùng `AsSplitQuery` có chọn lọc khi EF Core `Include` nhiều collection gây cartesian explosion

**Mẹo:**
Nếu một EF Core query `Include` nhiều collection và SQL join tạo lượng row trung gian rất lớn, thử `AsSplitQuery()` để tách việc load related collections thành nhiều query có kiểm soát.

**Tại sao hữu ích:**
Giả sử một `Order` có 20 `OrderLines` và 15 `AuditEntries`. Join cả hai collection trong một query có thể tạo 300 row lặp dữ liệu của cùng `Order`. Payload, materialization và memory tăng dù entity thật không nhiều. Split query tránh nhân chéo giữa các collection.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Where(x => x.Id == orderId)
    .Include(x => x.Lines)
    .Include(x => x.AuditEntries)
    .AsSplitQuery()
    .SingleAsync(ct);
```

Hãy so sánh generated SQL, số row, round-trip và total latency trước/sau.

**Lưu ý:**
Split query đổi cartesian explosion lấy nhiều database round-trip hơn và có thể thấy dữ liệu thay đổi giữa các query nếu consistency requirement nghiêm ngặt. Nhiều trường hợp projection DTO bằng `Select` vẫn tốt hơn `Include` một object graph lớn.

### Tip 3 — Với Azure Service Bus, theo dõi `DeliveryCount` và dead-letter reason thay vì chỉ retry vô hạn

**Mẹo:**
Khi consumer Azure Service Bus gặp lỗi lặp lại, log structured field như `MessageId`, `DeliveryCount`, exception category và dead-letter reason. Phân biệt transient failure với poison message thay vì để message quay lại queue cho tới khi chạm `MaxDeliveryCount` mà không có diagnostics.

**Tại sao hữu ích:**
Một message malformed hoặc vi phạm business invariant sẽ không tự hết lỗi sau lần retry thứ 8. Retry vô nghĩa chỉ tiêu thụ compute, làm backlog tăng và che mất root cause. Quan sát delivery count giúp phát hiện message đang mắc vòng redelivery trước khi queue age tăng mạnh.

**Ví dụ:**
```csharp
try
{
    await ProcessAsync(args.Message, ct);
    await args.CompleteMessageAsync(args.Message, ct);
}
catch (InvalidPayloadException ex)
{
    await args.DeadLetterMessageAsync(
        args.Message,
        deadLetterReason: "InvalidPayload",
        deadLetterErrorDescription: ex.Message,
        cancellationToken: ct);
}
```

Transient exception như timeout có thể abandon/retry; lỗi dữ liệu deterministic nên được phân loại rõ và chuyển DLQ sớm hơn nếu policy cho phép.

**Lưu ý:**
Không đưa dữ liệu nhạy cảm nguyên văn vào dead-letter description hoặc log. DLQ cũng không phải nơi “cất lỗi rồi quên”; cần alert, dashboard, replay/runbook và ownership để xử lý message bị dead-letter.

### Tip 4 — Dùng browser DevTools để phân biệt backend chậm với frontend/network waterfall

**Mẹo:**
Khi user báo “trang web chậm”, kiểm tra Network panel và timing breakdown trước khi mặc định đổ lỗi cho API. Tách DNS/connect/TLS, waiting/TTFB, download, blocking và chuỗi request phụ thuộc nhau.

**Tại sao hữu ích:**
Backend có thể trả API trong 120 ms nhưng page vẫn mất 4 giây vì bundle lớn, request nối tiếp, font/image blocking hoặc frontend chờ một request không cần thiết trước khi render. Timing evidence giúp team sửa đúng bottleneck thay vì tối ưu sai tầng.

**Ví dụ:**
```text
/api/product        TTFB: 140 ms
/app.js             download: 1.8 s
/recommendations    start sau /product hoàn tất
/reviews            start sau /recommendations hoàn tất

=> vấn đề chính là bundle + request waterfall,
   không phải database query của /api/product
```

Kết hợp Performance panel, Lighthouse hoặc server trace khi cần correlation sâu hơn.

**Lưu ý:**
Một lần đo trên máy developer không đại diện production. Kiểm tra throttling, cache state, geographic latency và percentile từ RUM/telemetry. DevTools là evidence cục bộ, không thay thế observability hệ thống.

### Tip 5 — Với AI coding agent, yêu cầu kiểm chứng bằng build/test/diff thay vì chỉ tin phần giải thích

**Mẹo:**
Khi dùng AI coding agent để refactor hoặc sửa bug, đánh giá kết quả bằng artifact có thể kiểm chứng: diff nhỏ, build pass, targeted test, static analysis và behavior reproduction. Phần giải thích của agent không phải bằng chứng code đúng.

**Tại sao hữu ích:**
Agent có thể mô tả rất thuyết phục nhưng dùng API không tồn tại, hiểu sai version framework hoặc sửa symptom mà phá invariant khác. Verification loop biến AI thành accelerator trong workflow kỹ thuật thay vì một nguồn thay đổi khó kiểm soát.

**Ví dụ:**
```text
Task: sửa race condition khi reserve inventory

Yêu cầu agent:
1. chỉ rõ file/flow gây race
2. tạo test tái hiện failure
3. sửa minimal diff
4. chạy targeted tests
5. show final diff
6. liệt kê assumption chưa verify
```

Trong PR review, ưu tiên đọc changed behavior, test coverage và dependency/API thực tế trong repository.

**Lưu ý:**
Test pass vẫn chưa chứng minh mọi thứ đúng nếu test do chính agent viết và chỉ verify implementation mới. Với security, transaction hoặc concurrency change, human review và domain reasoning vẫn bắt buộc.

## 🧠 Software Design

### Design 1 — API Composition vs Materialized Read Model cho màn hình cần dữ liệu từ nhiều service

**Khái niệm:**
Khi một UI cần dữ liệu từ nhiều bounded context/service, hai hướng phổ biến là API Composition — runtime gọi nhiều source rồi ghép response — hoặc build một materialized read model/projection phục vụ trực tiếp query đó.

**Vấn đề nó giải quyết:**
Một dashboard Order có thể cần Order, Payment, Shipment và Customer summary. Nếu frontend gọi 4 API hoặc BFF fan-out 4 dependency cho mỗi request, latency và availability của page phụ thuộc vào toàn bộ chain. Nhưng build projection riêng lại thêm eventual consistency và pipeline đồng bộ dữ liệu.

**Ví dụ thực tế:**
```text
API Composition:
Dashboard BFF
  -> Order API
  -> Payment API
  -> Shipping API
  -> Customer API
  -> merge response

Materialized Read Model:
Order/Payment/Shipping events
  -> Dashboard Projection
  -> Dashboard Store
  -> 1 query phục vụ UI
```

API Composition thường hợp với traffic vừa phải, ít source và freshness cao. Projection hợp hơn khi query rất nóng, aggregation phức tạp hoặc fan-out trở thành bottleneck.

**Trade-off:**
Composition đơn giản hơn về data lifecycle và thường thấy dữ liệu mới nhất, nhưng tăng runtime coupling, tail latency và failure surface. Materialized view cho read latency ổn định hơn nhưng cần event delivery, rebuild, reconciliation và chấp nhận stale data trong một khoảng thời gian.

**Middle → Senior insight:**
Middle developer cần nhận ra “ghép 4 API” là một reliability decision, không chỉ code orchestration. Senior / Technical developer phải đánh giá fan-out width, SLO, freshness requirement, event volume, rebuild cost và degraded behavior để chọn composition, projection hoặc hybrid.

### Design 2 — Shared Schema vs Database-per-Tenant trong SaaS multi-tenancy

**Khái niệm:**
Multi-tenant SaaS có thể để nhiều tenant dùng chung schema/table với `TenantId`, tách schema/database theo tenant, hoặc dùng hybrid theo tier. Đây là quyết định về isolation, operations và cost chứ không chỉ schema convention.

**Vấn đề nó giải quyết:**
Shared database đơn giản hóa provisioning và tận dụng resource tốt, nhưng noisy tenant, accidental cross-tenant query và restore từng tenant trở nên khó hơn. Database-per-tenant tăng isolation nhưng số lượng database, migration, connection và monitoring tăng nhanh.

**Ví dụ thực tế:**
```text
Shared model:
Orders
- TenantId
- OrderId
- ...

Enterprise tenant đặc biệt:
Tenant A -> DB-A
Tenant B -> DB-B
Long-tail tenants -> Shared-DB-1 / Shared-DB-2
```

Hybrid model cho phép tenant lớn hoặc yêu cầu compliance riêng được isolate mà không ép mọi tenant trả operational cost như nhau.

**Trade-off:**
Shared schema tối ưu cost và đơn giản deployment nhưng đòi hỏi tenant filtering, index strategy, quota và security cực kỳ chặt. Database-per-tenant tăng blast-radius isolation và restore flexibility nhưng làm migration orchestration, pooling, observability và capacity management phức tạp hơn.

**Middle → Senior insight:**
Middle developer cần bảo đảm tenant context được enforce ở mọi data access path và test cross-tenant leakage. Senior / Solution-level developer phải chọn isolation model dựa trên compliance, tenant size distribution, restore/SLA, cost và automation maturity — không mặc định “mỗi tenant một DB là an toàn nhất nên luôn tốt nhất”.

### Design 3 — Feature Flag tách deployment khỏi release, nhưng flag cũng là technical debt có lifecycle

**Khái niệm:**
Feature Flag cho phép deploy code chưa bật cho toàn bộ user, sau đó release theo tenant, percentage hoặc condition. Nó hỗ trợ progressive delivery, rollback logic nhanh và thử nghiệm có kiểm soát mà không cần deploy lại binary.

**Vấn đề nó giải quyết:**
Một tính năng lớn có thể cần merge sớm để tránh branch dài nhưng chưa thể mở cho mọi khách hàng. Hoặc team muốn bật cho 5% traffic để kiểm tra error rate/latency trước khi rollout toàn bộ.

**Ví dụ thực tế:**
```text
Deploy v42:
NewCheckout code đã có trong production
Feature flag = off

Rollout:
internal users -> 5% -> 25% -> 100%

Nếu error rate tăng:
flag off nhanh hơn rollback toàn deployment
```

Flag nên có owner, expiry date và observability theo variant để biết rollout ảnh hưởng gì.

**Trade-off:**
Feature flag giảm release risk nhưng mỗi flag tạo thêm execution path, test matrix và khả năng config drift. Flag tồn tại lâu có thể biến code thành mê cung `if/else`, đặc biệt nếu nhiều flag tương tác nhau. Kill switch dài hạn và temporary release flag nên được quản lý khác nhau.

**Middle → Senior insight:**
Middle developer cần viết code sao cho cả flag on/off đều an toàn và test được. Senior / Technical developer phải thiết kế rollout metric, default behavior khi flag service lỗi, ownership, cleanup policy và tránh dùng feature flag để trì hoãn việc giải quyết schema/API incompatibility thật sự.
