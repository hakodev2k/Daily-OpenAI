# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Chia sẻ ASP.NET Core Data Protection key ring khi chạy nhiều instance

**Mẹo:**
Nếu ASP.NET Core chạy nhiều replica và dùng cookie authentication, antiforgery token hoặc bất kỳ feature nào dựa trên Data Protection, hãy đảm bảo các instance dùng chung key ring ổn định thay vì mỗi node tự tạo key cục bộ.

**Tại sao hữu ích:**
Cookie hoặc token được mã hóa bởi instance A có thể được request tiếp theo đưa sang instance B. Nếu B không có cùng key, token hợp lệ về mặt business vẫn bị coi là không giải mã được, tạo lỗi đăng nhập ngẫu nhiên hoặc user bị sign-out khi load balancer chuyển node.

**Ví dụ:**
```csharp
builder.Services
    .AddDataProtection()
    .PersistKeysToAzureBlobStorage(blobUri)
    .ProtectKeysWithAzureKeyVaultKey(keyIdentifier, credential)
    .SetApplicationName("Nexora.Web");
```

Trong Kubernetes hoặc App Service scale-out, key persistence phải tồn tại độc lập với lifecycle của từng process/container.

**Lưu ý:**
Không chia sẻ key ring giữa các application không cùng trust boundary chỉ vì tiện. `SetApplicationName` cũng ảnh hưởng isolation giữa app. Rotation và quyền truy cập storage/key-encryption key phải được xem như một phần của security design.

### Tip 2 — Với Cosmos DB, ưu tiên point read khi đã biết `id` và partition key

**Mẹo:**
Khi đã biết chính xác `id` và partition key của document, dùng point read thay vì viết query SQL kiểu `WHERE id = ...`.

**Tại sao hữu ích:**
Point read đi thẳng tới partition và item cần lấy, thường có RU cost thấp và latency ổn định hơn query engine. Query dù chỉ trả một record vẫn phải đi qua query pipeline và có thể trở thành cross-partition query nếu thiếu partition key.

**Ví dụ:**
```csharp
ItemResponse<OrderDocument> response = await container.ReadItemAsync<OrderDocument>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: ct);
```

Nếu access pattern thường xuyên cần tìm order theo `orderId`, hãy bảo đảm partition strategy cho phép application biết partition key mà không cần query toàn container trước.

**Lưu ý:**
Point read chỉ hiệu quả khi bạn có đúng partition key. Nếu phải thực hiện query khác để tìm partition key trước, lợi ích có thể biến mất. Partition-key design phải bắt đầu từ access patterns và data distribution, không phải từ mong muốn dùng API rẻ nhất.

### Tip 3 — Dùng `git reflog` để cứu commit sau reset/rebase nhầm

**Mẹo:**
Nếu vừa `reset --hard`, rebase hoặc amend rồi tưởng commit đã “mất”, kiểm tra `git reflog` trước khi cố viết lại code.

**Tại sao hữu ích:**
Git thường vẫn giữ object commit trong một khoảng thời gian dù branch pointer đã di chuyển. Reflog ghi lịch sử các thay đổi của `HEAD` và local refs, giúp khôi phục state trước thao tác sai nhanh hơn nhiều so với tái tạo thủ công.

**Ví dụ:**
```bash
git reflog

# Ví dụ thấy commit cũ là a1b2c3d
git branch rescue-work a1b2c3d
```

Sau đó kiểm tra diff trên branch cứu hộ trước khi merge/cherry-pick trở lại.

**Lưu ý:**
Reflog là local; nó không phải backup vĩnh viễn và entry có thể bị expire/GC. Với commit chưa từng push và repository đã bị mất hoàn toàn, reflog trên máy khác sẽ không cứu được. Đừng coi reflog là thay thế cho push/backup hợp lý.

### Tip 4 — Trong React, cleanup `useEffect` để tránh stale async result ghi đè state mới

**Mẹo:**
Khi `useEffect` thực hiện fetch phụ thuộc vào props/state, hủy request cũ hoặc bỏ qua result của effect đã obsolete khi dependency thay đổi.

**Tại sao hữu ích:**
Request cho state cũ có thể hoàn tất sau request mới và ghi đè UI bằng dữ liệu cũ. Đây là race condition ở client, không phải chỉ là “API chậm”. Cleanup giúp mỗi render generation chỉ chấp nhận side effect còn hợp lệ.

**Ví dụ:**
```tsx
useEffect(() => {
  const controller = new AbortController();

  loadCustomer(customerId, controller.signal)
    .then(setCustomer)
    .catch(error => {
      if (error.name !== 'AbortError') throw error;
    });

  return () => controller.abort();
}, [customerId]);
```

Khi `customerId` đổi, request cũ bị abort trước khi effect mới tiếp tục.

**Lưu ý:**
Abort ở browser không đảm bảo backend đã rollback side effect. Với `POST`/command, server vẫn cần idempotency và cancellation semantics phù hợp. Đồng thời đừng dùng `useEffect` cho derived state có thể tính trực tiếp trong render.

### Tip 5 — Azure Functions: cấu hình poison-message path thay vì retry vô hạn một message hỏng

**Mẹo:**
Với queue-triggered Azure Functions, xác định rõ retry limit và nơi message sẽ đi khi vượt quá số lần xử lý thất bại, đồng thời log đủ context để điều tra và replay có kiểm soát.

**Tại sao hữu ích:**
Một message không thể xử lý do schema sai hoặc dữ liệu business không hợp lệ có thể bị retry liên tục, tiêu compute và che khuất các message khỏe mạnh. Poison-message handling biến failure lặp lại thành một trạng thái vận hành có thể quan sát và xử lý.

**Ví dụ:**
```text
Queue: invoice-jobs
Message M42 fails repeatedly
-> retry theo policy
-> vượt retry limit
-> chuyển tới poison/dead-letter path
-> alert + điều tra payload/correlationId
-> fix root cause rồi replay nếu an toàn
```

Với Service Bus trigger, dead-letter queue là nơi tự nhiên để xử lý loại lỗi không nên retry tiếp.

**Lưu ý:**
Đưa message vào poison/dead-letter không tự giải quyết business inconsistency. Cần phân biệt lỗi transient với lỗi permanent; retry quá ít có thể bỏ qua lỗi tạm thời, retry quá nhiều có thể gây retry storm. Replay phải idempotent.

## 🧠 Software Design

### Design 1 — Circuit Breaker ngăn dependency lỗi kéo sập capacity của caller

**Khái niệm:**
Circuit Breaker tạm dừng call tới dependency sau khi failure vượt ngưỡng, thay vì để mọi request tiếp tục timeout. Sau một khoảng thời gian, hệ thống cho phép một số call thử để đánh giá dependency đã phục hồi chưa.

**Vấn đề nó giải quyết:**
Payment provider bắt đầu timeout 20 giây. Nếu mọi request của API vẫn gọi xuống provider, thread/socket/connection và request budget bị giữ lâu, khiến một dependency lỗi lan thành outage của toàn service.

**Ví dụ thực tế:**
```text
Closed:
- call bình thường
- failure tăng tới threshold

Open:
- fail fast, không gọi provider

Half-open:
- cho một số request thử
- thành công -> Closed
- tiếp tục lỗi -> Open
```

Circuit Breaker thường phối hợp với timeout, retry có backoff và fallback hợp lý.

**Trade-off:**
Circuit Breaker bảo vệ capacity và giảm latency khi dependency đang hỏng, nhưng có thể từ chối request dù dependency vừa phục hồi nếu policy quá bảo thủ. Kết hợp retry sai thứ tự còn có thể nhân traffic lúc hệ thống yếu. Policy phải dựa trên failure semantics thực tế, không copy một cấu hình cho mọi dependency.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry và circuit breaker giải quyết ba vấn đề khác nhau. Senior / Technical developer phải chọn threshold, sampling window, fallback và retry budget theo SLO, idempotency và blast radius thay vì coi resilience library là “bật lên là an toàn”.

### Design 2 — Backend for Frontend khi Web và Mobile có nhu cầu orchestration khác nhau

**Khái niệm:**
Backend for Frontend (BFF) tạo một backend boundary riêng cho từng loại client lớn khi các client có contract, aggregation và release cadence khác nhau đáng kể.

**Vấn đề nó giải quyết:**
Mobile cần payload nhỏ, ít round trip và compatibility dài hạn; web desktop lại cần dữ liệu phong phú và có thể release nhanh. Một API chung cố phục vụ tất cả dễ trở thành endpoint khổng lồ hoặc buộc client tự orchestration nhiều service.

**Ví dụ thực tế:**
```text
Web App
  -> Web BFF
      -> Orders
      -> Catalog
      -> Recommendations

Mobile App
  -> Mobile BFF
      -> Orders
      -> Catalog
```

Mobile BFF có thể aggregate ít field hơn và giữ contract cũ lâu hơn mà không ép web dùng cùng shape.

**Trade-off:**
BFF giảm coupling giữa client và backend topology, nhưng thêm deployable, auth boundary, observability và khả năng duplicate orchestration logic. Nếu Web và Mobile gần như giống nhau, một API tốt với projection phù hợp có thể đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần giữ BFF tập trung vào client-specific orchestration thay vì nhét core business logic vào đó. Senior / Solution-oriented engineer phải đánh giá số client, divergence của contract, team ownership và operational cost trước khi thêm một backend layer mới.

### Design 3 — Shared Database giữa services tạo coupling mạnh hơn API contract nhìn thấy

**Khái niệm:**
Khi nhiều service cùng đọc/ghi trực tiếp một database schema, database trở thành integration contract ngầm. Dù mỗi service có API riêng, schema, transaction và migration vẫn ràng buộc chúng với nhau.

**Vấn đề nó giải quyết:**
Hai service tách deploy nhưng cùng update bảng `Customer`. Một migration đổi column hoặc invariant có thể làm service kia lỗi dù API contract không đổi. Team tưởng đã có service autonomy nhưng thực tế vẫn phải coordinate release qua database.

**Ví dụ thực tế:**
```text
Orders Service ---> Orders schema
Customer Service -> Customer schema

Tốt hơn cho ownership rõ:
Orders chỉ lưu customer snapshot/reference cần thiết
Customer data thay đổi qua API/event contract
```

Trong Modular Monolith, dùng chung database có thể hoàn toàn hợp lý nếu module boundary vẫn được enforce bằng ownership/schema convention.

**Trade-off:**
Database-per-service tăng autonomy và giảm schema coupling nhưng làm transaction cross-service, reporting và data synchronization khó hơn. Shared database đơn giản cho transaction và query join, nhưng giảm khả năng deploy/scale/evolve độc lập. Không nên tách database chỉ để “đúng Microservices”.

**Middle → Senior insight:**
Middle developer cần tránh query trực tiếp table thuộc ownership của service/module khác chỉ vì tiện. Senior / Technical developer phải cân bằng autonomy, consistency, reporting, migration cost và team structure để chọn boundary dữ liệu phù hợp thay vì áp một rule tuyệt đối.
