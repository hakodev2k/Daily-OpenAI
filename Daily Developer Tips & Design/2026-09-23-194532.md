# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `ValueTask` chỉ đáng dùng khi allocation thực sự là bottleneck

**Mẹo:**
Giữ `Task` làm mặc định cho async API. Chỉ cân nhắc `ValueTask<T>` ở hot path đã profiling, đặc biệt khi operation thường hoàn thành synchronously và việc tránh allocation `Task<T>` tạo khác biệt đo được.

**Tại sao hữu ích:**
`ValueTask<T>` là struct có thể chứa kết quả trực tiếp hoặc bọc một async operation, nhờ đó một số fast path tránh allocation. Đổi lại, consumer semantics và implementation phức tạp hơn; tối ưu này thường nhỏ hơn database, network hoặc serialization latency trong backend thông thường.

**Ví dụ:**
Một in-memory lookup cực nóng trả cache hit phần lớn thời gian có thể là candidate sau benchmark. Một repository luôn gọi SQL bằng `ToListAsync()` thì đổi return type sang `ValueTask` gần như không loại bỏ I/O cost đáng kể.

**Lưu ý:**
Không tùy tiện await cùng một `ValueTask` nhiều lần hoặc lưu giữ nó như reusable `Task`; behavior còn phụ thuộc backing source. Đừng đổi hàng loạt API chỉ vì `ValueTask` trông “nhanh hơn”.

### Tip 2 — EF Core projection giảm cả dữ liệu truyền lẫn change-tracking work

**Mẹo:**
Với read endpoint, project trực tiếp sang response shape bằng `Select` thay vì load nguyên entity graph rồi map trong memory.

**Tại sao hữu ích:**
Projection cho provider cơ hội chỉ SELECT các columns cần thiết và tránh materialize entity/relationship không dùng. Điều này giảm network payload, allocation và tracking overhead; lợi ích thường rõ hơn việc tối ưu vài dòng C# sau khi dữ liệu đã được tải.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Total))
    .Take(50)
    .ToListAsync(ct);
```
API danh sách không cần load `OrderLines`, navigation properties hay toàn bộ columns của `Order`.

**Lưu ý:**
Kiểm tra SQL thực tế khi projection chứa expression phức tạp. Đừng gọi `AsEnumerable()` sớm rồi vô tình chuyển filtering/projection sang client-side; và với update workflow, entity tracking vẫn có giá trị.

### Tip 3 — Git `bisect` biến regression hunt thành tìm kiếm có hệ thống

**Mẹo:**
Khi biết một commit cũ hoạt động và HEAD bị lỗi, dùng `git bisect` để thu hẹp commit gây regression thay vì đọc tuần tự hàng chục hoặc hàng trăm commits.

**Tại sao hữu ích:**
Bisect dùng binary search: mỗi lần test loại bỏ khoảng một nửa khoảng commit nghi vấn. Nếu có deterministic test/script, quá trình có thể tự động hóa và biến production regression thành evidence cụ thể về change set.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.8.0
git bisect run dotnet test tests/Regression.Tests
```
Sau khi tìm được culprit, dùng `git bisect reset` và review diff cùng failure mechanism.

**Lưu ý:**
Bisect kém hiệu quả nếu test flaky, historical commits không build được hoặc lỗi phụ thuộc external state. Đừng coi commit được tìm thấy là root cause cuối cùng trước khi đọc diff và tái hiện mechanism.

### Tip 4 — File upload phải kiểm tra nội dung và storage boundary, không chỉ extension

**Mẹo:**
Với ASP.NET Core upload endpoint, giới hạn kích thước, sinh server-side filename, lưu ngoài web root khi phù hợp và xác minh content theo policy thay vì tin `FileName`/`Content-Type` do client gửi.

**Tại sao hữu ích:**
Metadata từ multipart request do client kiểm soát. Tin extension hoặc MIME header có thể cho phép executable/script payload, path manipulation hoặc file cực lớn tiêu thụ disk/memory. Storage tách biệt và download qua controlled endpoint giảm blast radius.

**Ví dụ:**
CMS cho editor upload ảnh: backend kiểm tra size, decode/validate image bằng thư viện phù hợp, tạo object key mới và lưu Blob Storage; database chỉ giữ metadata/key thay vì dùng tên file gốc làm storage path.

**Lưu ý:**
Magic-byte check một mình không chứng minh file an toàn. Threat model còn có decompression bombs, parser vulnerabilities và malware; với untrusted files có risk cao, cần scanning/sandboxing phù hợp và không phục vụ với executable content type.

### Tip 5 — Cosmos DB partition key phải đi cùng access pattern, không chỉ cardinality cao

**Mẹo:**
Chọn partition key sao cho các request quan trọng có thể route tới ít logical partitions, workload phân bố đều và mỗi logical partition không trở thành hot spot.

**Tại sao hữu ích:**
Cross-partition query cần fan-out và tiêu tốn RU/latency hơn point read hoặc query có partition key. Key có cardinality cao nhưng traffic skew vẫn có thể tạo hot partition; ví dụ một tenant khổng lồ nhận phần lớn traffic.

**Ví dụ:**
SaaS system chủ yếu đọc dữ liệu theo tenant có thể bắt đầu từ `tenantId`, nhưng nếu vài enterprise tenants cực lớn, cần đánh giá hierarchical/synthetic partition strategy theo workload thay vì áp dụng cùng model cho mọi scale.

**Lưu ý:**
Partition-key choice khó thay đổi sau khi hệ thống lớn. Đừng tối ưu chỉ cho write distribution mà làm các query chính thành cross-partition; đo RU, data growth và traffic skew bằng workload representative.

## 🧠 Software Design

### Design 1 — CQRS chỉ nên tách model khi read và write thật sự có áp lực khác nhau

**Khái niệm:**
CQRS tách responsibility của command/write model khỏi query/read model. Mức tách có thể chỉ là code paths riêng trong cùng application/database, không bắt buộc phải có microservices, event sourcing hay hai databases.

**Vấn đề nó giải quyết:**
Một domain có write rules phức tạp nhưng read screens cần projection tối ưu khác hẳn aggregate model. Ép cùng object model phục vụ cả invariant-heavy writes lẫn dashboard queries có thể tạo query khó tối ưu và domain model bị biến dạng vì UI.

**Ví dụ thực tế:**
Ordering dùng aggregate để bảo vệ state transition khi sửa order, còn order-history endpoint query projection trực tiếp theo shape của UI. Cả hai vẫn có thể nằm trong Modular Monolith và cùng SQL Server nếu chưa có nhu cầu scale độc lập.

**Trade-off:**
CQRS tăng số model, mapping và cognitive overhead; nếu read store riêng, còn thêm synchronization/eventual consistency. CRUD system nhỏ với read/write shape gần giống nhau thường không thu được lợi ích tương xứng.

**Middle → Senior insight:**
Middle developer cần tách command/query responsibilities rõ mà không biến mỗi method thành ceremony. Senior / Technical developer phải nhận diện divergence thực sự về model, performance và scaling; chọn mức CQRS tối thiểu đủ giải quyết pressure thay vì mặc định thêm broker/read database.

### Design 2 — Timeout budget phải được phân bổ xuyên suốt dependency chain

**Khái niệm:**
Timeout design đặt deadline cho toàn request và phân bổ budget cho từng downstream operation, thay vì mỗi dependency tự dùng một timeout độc lập lớn hơn end-to-end SLA.

**Vấn đề nó giải quyết:**
API có mục tiêu trả trong 2 giây nhưng gọi ba dependencies, mỗi client timeout 10 giây. Khi một dependency chậm, request giữ connection/concurrency quá lâu; retry còn có thể kéo tổng thời gian vượt xa thời gian caller sẵn sàng chờ.

**Ví dụ thực tế:**
Checkout có budget 2 giây: inventory 300 ms, pricing 300 ms, payment phần còn lại cùng processing overhead. Khi budget gần hết, không bắt đầu retry 1 giây chỉ vì retry policy còn lượt.

**Trade-off:**
Timeout quá ngắn tạo false failures trong latency spike; quá dài làm resource bị giữ và failure lan rộng. Budget còn phải xét operation nào có thể parallelize, cancellation support và business semantics của partial completion.

**Middle → Senior insight:**
Middle developer cần propagate cancellation/deadline và cấu hình timeout/retry nhất quán. Senior / Technical developer phải xây latency budget từ SLO, dependency percentiles và retry cost; quyết định fail-fast, degrade hay tiếp tục theo giá trị business của operation.

### Design 3 — Strangler migration giảm risk khi hiện đại hóa legacy .NET

**Khái niệm:**
Strangler approach chuyển dần capability khỏi legacy system sang implementation mới qua routing/boundary rõ ràng, thay vì rewrite toàn bộ rồi cut over một lần.

**Vấn đề nó giải quyết:**
Một .NET Framework monolith lớn thường chứa undocumented behavior, shared database assumptions và integrations khó tái tạo. Big-bang rewrite kéo dài feedback cycle và đến ngày cutover mới phát hiện behavior quan trọng bị bỏ sót.

**Ví dụ thực tế:**
Team giữ application cũ hoạt động, đưa một API facade/reverse-proxy boundary phía trước và lần lượt chuyển capability ít coupling sang ASP.NET Core/.NET 10. Telemetry so sánh behavior trước khi route toàn bộ traffic sang implementation mới.

**Trade-off:**
Trong giai đoạn migration phải vận hành hai worlds, xử lý routing, duplicated logic/data contract và temporary integration complexity. Nếu hệ thống nhỏ, ít risk và có thể thay thế nhanh, incremental migration có thể đắt hơn rewrite trực tiếp.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility, characterization tests và quan sát behavior cũ trước khi thay thế. Senior / Technical developer phải chọn seam theo dependency/change risk, quản lý data ownership, rollback và migration order, đồng thời có exit plan để temporary bridge không trở thành architecture vĩnh viễn.
