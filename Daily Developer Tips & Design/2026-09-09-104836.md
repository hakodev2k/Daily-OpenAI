# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` khi hot path tạo buffer lớn lặp lại

**Mẹo:**
Trong .NET, nếu profiling cho thấy code liên tục tạo array tạm thời lớn khi parsing, compression hoặc file processing, cân nhắc `ArrayPool<T>` để tái sử dụng buffer.

**Tại sao hữu ích:**
Allocation lớn lặp lại làm tăng GC pressure và có thể đẩy object lên Large Object Heap. Pooling giảm allocation rate khi workload thực sự đủ nóng.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer, cancellationToken);
    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

**Lưu ý:**
Buffer thuê có thể lớn hơn yêu cầu và chứa dữ liệu cũ. Không đọc ngoài vùng hợp lệ, luôn `Return`, và clear buffer nếu xử lý dữ liệu nhạy cảm.

### Tip 2 — Kiểm tra parameter sniffing trước khi thêm index cho query “lúc nhanh lúc chậm”

**Mẹo:**
Nếu cùng một SQL Server query hoặc stored procedure có runtime rất khác nhau theo parameter, kiểm tra execution plan cache và parameter sniffing trước khi lập tức thêm index.

**Tại sao hữu ích:**
SQL Server có thể compile plan từ một parameter rồi reuse cho giá trị có data distribution hoàn toàn khác. Plan tốt cho tenant nhỏ có thể rất tệ cho tenant lớn.

**Ví dụ:**
```text
Tenant A: 500 rows
Tenant B: 8,000,000 rows
```

So actual execution plan, estimated vs actual rows và runtime statistics giữa các parameter đại diện để xác nhận root cause.

**Lưu ý:**
Không dùng `OPTION (RECOMPILE)` hoặc query hint theo phản xạ. Recompile tăng CPU; hint có thể trở thành technical debt nếu workload thay đổi.

### Tip 3 — Stream file lớn từ Azure Blob Storage thay vì load toàn bộ vào memory

**Mẹo:**
Khi backend đọc file lớn từ Azure Blob Storage để trả cho client hoặc xử lý tuần tự, ưu tiên streaming thay vì giữ toàn bộ payload trong memory.

**Tại sao hữu ích:**
Memory usage khi load toàn bộ file tăng gần theo kích thước file × số request đồng thời. Streaming giữ working set ổn định hơn và bắt đầu truyền dữ liệu sớm hơn.

**Ví dụ:**
```csharp
var download = await blobClient.DownloadStreamingAsync(cancellationToken: ct);
await download.Value.Content.CopyToAsync(httpResponse.Body, ct);
```

**Lưu ý:**
Nếu backend không cần transform hay enforce business authorization, direct client download bằng SAS có thể hiệu quả hơn. SAS phải giới hạn permission, scope và expiry.

### Tip 4 — Trong Playwright, chờ trạng thái thật của UI thay vì delay cố định

**Mẹo:**
Thay `Task.Delay`, sleep hoặc `waitForTimeout` bằng assertion/wait dựa trên trạng thái UI mà user thực sự quan sát được.

**Tại sao hữu ích:**
Delay cố định vừa làm test chậm vừa flaky: CI chậm hơn thì timeout, app nhanh hơn thì vẫn chờ vô ích. Playwright có auto-wait cho nhiều interaction.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Saved successfully")).ToBeVisibleAsync();
```

**Lưu ý:**
Nếu test vẫn flaky, điều tra race condition của application hoặc locator kém ổn định thay vì chỉ tăng timeout.

### Tip 5 — Model Optimizely CMS theo editorial intent thay vì layout hiện tại

**Mẹo:**
Đặt property của Page Type/Block Type theo meaning của content như `Heading`, `Media`, `PrimaryAction`, thay vì `LeftColumnText` hoặc `BlueButtonText`.

**Tại sao hữu ích:**
Visual layout thường đổi nhanh hơn content meaning. Model theo intent giúp content tái sử dụng giữa nhiều rendering và giảm data migration khi redesign.

**Ví dụ:**
```text
Không nên: LeftColumnHeading, RightColumnImage
Nên:       Heading, Media
```

Renderer chịu trách nhiệm layout; content model giữ semantics.

**Lưu ý:**
Đừng generic hóa thành `Text1`, `Text2`, `Image1`. Linh hoạt về kỹ thuật nhưng làm editorial UX, validation và maintainability kém.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like behavior. Repository riêng chỉ đáng thêm khi tạo boundary có giá trị thực, không phải chỉ bọc lại từng method của EF Core.

**Vấn đề nó giải quyết:**
Một domain phức tạp có thể cần cô lập persistence hoặc biểu đạt query/aggregate semantics rõ hơn. Nhưng repository pass-through thường chỉ tăng boilerplate.

**Ví dụ thực tế:**
Ít giá trị:
```text
OrderRepository.GetById(id)
-> db.Orders.FindAsync(id)
```

Có ý nghĩa hơn khi repository che persistence phức tạp và dùng language của domain như `LoadAggregateForCheckout`.

**Trade-off:**
Direct `DbContext` đơn giản và giữ đầy đủ khả năng EF Core. Repository tạo boundary/test seam nhưng thêm mapping, indirection và có thể hạn chế query flexibility.

**Middle → Senior insight:**
Middle developer cần dùng `DbContext` đúng lifecycle, transaction và query behavior. Senior / Technical developer phải quyết định abstraction dựa trên domain complexity, persistence volatility và cost bảo trì thay vì áp dụng pattern mặc định.

### Design 2 — Retry vs Circuit Breaker

**Khái niệm:**
Retry xử lý transient fault bằng cách thử lại; Circuit Breaker tạm dừng gọi dependency khi failure rate cao để tránh tiếp tục tạo tải vào hệ thống đang lỗi.

**Vấn đề nó giải quyết:**
Retry hữu ích khi timeout chỉ xảy ra ngẫu nhiên. Khi dependency outage, retry trên mọi request có thể tạo retry storm và làm incident nặng hơn.

**Ví dụ thực tế:**
```text
Timeout đơn lẻ -> retry 2 lần với backoff + jitter
Failure rate cao kéo dài -> circuit open -> fail fast/fallback
```

**Trade-off:**
Retry tăng success rate nhưng có thể duplicate side effect. Circuit Breaker bảo vệ dependency nhưng có thể từ chối request trong thời gian dependency vừa hồi phục nếu cấu hình không phù hợp.

**Middle → Senior insight:**
Middle developer cần retry operation idempotent hoặc có idempotency protection. Senior / Technical developer phải thiết kế timeout budget, retry count, jitter, breaker threshold và fallback semantics theo SLA end-to-end.

### Design 3 — Normalization vs Denormalization

**Khái niệm:**
Normalization giảm duplication và giữ source-of-truth rõ ràng. Denormalization chủ động duplicate hoặc precompute dữ liệu để tối ưu read path khi query pressure thực sự cần nó.

**Vấn đề nó giải quyết:**
Transactional model chuẩn hóa tốt cho correctness, nhưng dashboard hoặc feed lớn có thể phải join và aggregate cùng dữ liệu trên mỗi request.

**Ví dụ thực tế:**
```text
Transactional: Orders + OrderLines + Products
Read model:    DailySalesByCategory
```

Read model được cập nhật riêng thay vì aggregate toàn bộ transaction tables cho mỗi dashboard request.

**Trade-off:**
Normalization giảm inconsistency nhưng query có thể phức tạp hơn. Denormalization tăng read performance nhưng thêm synchronization logic, stale data và chi phí rebuild/backfill.

**Middle → Senior insight:**
Middle developer cần hiểu constraint, key và transaction boundary của normalized model. Senior / Technical developer phải chứng minh bottleneck bằng measurement rồi xác định denormalization scope và consistency expectation rõ ràng.
