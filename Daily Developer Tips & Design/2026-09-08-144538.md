# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Chỉ dùng `ValueTask` khi synchronous completion thực sự phổ biến

**Mẹo:**
Đừng đổi mọi `Task<T>` thành `ValueTask<T>` chỉ để “giảm allocation”. `ValueTask<T>` hữu ích nhất khi method rất thường xuyên hoàn thành đồng bộ, ví dụ cache hit hoặc parser có sẵn dữ liệu trong memory.

**Tại sao hữu ích:**
`Task<T>` là reference type và mỗi asynchronous operation thường tạo object đại diện cho kết quả. `ValueTask<T>` có thể tránh một allocation khi kết quả đã có ngay, nhưng đổi lại caller phải tuân thủ usage semantics chặt hơn và runtime phải mang một struct lớn hơn qua call chain.

**Ví dụ:**
```csharp
public ValueTask<User?> GetUserAsync(Guid id)
{
    if (_memoryCache.TryGetValue(id, out User? cached))
        return ValueTask.FromResult(cached);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

Nếu phần lớn call vẫn phải I/O tới database thì `Task<User?>` thường đơn giản và hợp lý hơn.

**Lưu ý:**
Không nên await cùng một `ValueTask` nhiều lần hoặc lưu giữ nó tùy ý trừ khi API/documentation cho phép. Đừng micro-optimize async abstraction nếu profiling chưa cho thấy allocation ở đây là bottleneck.

### Tip 2 — Khi gặp deadlock SQL, đọc wait graph trước khi đổi isolation level

**Mẹo:**
Nếu production xuất hiện deadlock, lấy deadlock graph/extended event và xác định transaction nào đang giữ resource A rồi chờ B trong khi transaction khác giữ B rồi chờ A.

**Tại sao hữu ích:**
Deadlock không đơn giản là “database quá chậm”. Nó là chu kỳ phụ thuộc lock. Việc hạ isolation level hoặc thêm retry có thể che symptom nhưng không sửa access order hoặc transaction scope gây ra deadlock.

**Ví dụ:**
```text
Transaction 1:
UPDATE Customers ...   -- giữ lock Customer
UPDATE Orders ...      -- chờ Order

Transaction 2:
UPDATE Orders ...      -- giữ lock Order
UPDATE Customers ...   -- chờ Customer
```

Nếu business semantics cho phép, chuẩn hóa thứ tự truy cập:
```text
luôn lock/update Customer trước, rồi Order
```

**Lưu ý:**
Retry deadlock victim vẫn nên có vì deadlock có thể xảy ra ngẫu nhiên, nhưng retry không thay thế root-cause analysis. Transaction quá rộng, index thiếu làm scan nhiều row hoặc access order không nhất quán đều có thể tăng deadlock risk.

### Tip 3 — Trong Elasticsearch, phân biệt `text` và `keyword` để tránh query “đúng cú pháp nhưng sai semantics”

**Mẹo:**
Dùng `text` cho full-text search có analyzer/tokenization; dùng `keyword` cho exact match, filter, sorting và aggregation.

**Tại sao hữu ích:**
Một field mapping sai có thể khiến filter không match như mong đợi hoặc aggregation tạo kết quả kỳ lạ. `text` được phân tích thành token; `keyword` giữ nguyên giá trị logic để so sánh chính xác.

**Ví dụ:**
Mapping:
```json
{
  "title": { "type": "text" },
  "status": { "type": "keyword" }
}
```

Query:
```json
{
  "bool": {
    "must": [
      { "match": { "title": "wireless keyboard" } }
    ],
    "filter": [
      { "term": { "status": "active" } }
    ]
  }
}
```

**Lưu ý:**
Mapping đã dùng sai trên index lớn thường dẫn tới reindex. Đừng thêm cả `text` và `keyword` cho mọi field theo thói quen; mỗi subfield tăng index size và maintenance cost.

### Tip 4 — Với Azure Blob Storage, cân nhắc direct client upload thay vì proxy file lớn qua API

**Mẹo:**
Nếu browser/mobile client upload file lớn, backend có thể cấp quyền upload giới hạn thời gian/phạm vi rồi để client upload trực tiếp vào Blob Storage thay vì stream toàn bộ file qua App Service.

**Tại sao hữu ích:**
Proxy file lớn qua backend tiêu tốn connection, bandwidth, memory buffer và request concurrency của application tier. Direct upload chuyển data plane sang Blob Storage, còn backend tập trung authorization và metadata.

**Ví dụ:**
Flow:
```text
Client -> POST /uploads/request
Backend -> validate user + file policy
Backend -> issue short-lived upload permission
Client -> upload directly to Blob Storage
Client/Storage event -> finalize metadata/process file
```

Backend trên Azure có thể dùng Managed Identity để xin quyền và tạo cơ chế truy cập giới hạn thay vì giữ storage account key trong application config.

**Lưu ý:**
Direct upload không bỏ qua validation. Cần giới hạn container/path, expiry, size/type policy, malware scanning và authorization. Đừng cấp quyền rộng kiểu read/write toàn container chỉ để upload một object.

### Tip 5 — Dùng structured logging theo field, không nhét context vào chuỗi message

**Mẹo:**
Log production nên giữ dữ liệu quan trọng như `OrderId`, `TenantId`, `CorrelationId`, duration hoặc dependency name dưới dạng field có cấu trúc thay vì nối chuỗi thủ công.

**Tại sao hữu ích:**
Structured logging cho phép Application Insights, Elasticsearch/Kibana hoặc hệ thống log khác filter/aggregate theo field. Nếu context bị nhét vào text tự do, query production trở nên chậm và phụ thuộc format message.

**Ví dụ:**
Nên:
```csharp
logger.LogWarning(
    "Payment provider timeout for order {OrderId} after {ElapsedMs} ms",
    orderId,
    elapsedMs);
```

Thay vì:
```csharp
logger.LogWarning($"Payment timeout: order={orderId}, elapsed={elapsedMs}");
```

**Lưu ý:**
Không log secret, access token, password, full payment data hoặc PII không cần thiết. Structured logging làm dữ liệu dễ query hơn, đồng nghĩa sensitive data bị lộ cũng dễ tìm hơn nếu logging policy kém.

## 🧠 Software Design

### Design 1 — Saga Pattern cho workflow nhiều service khi atomic transaction không còn tồn tại

**Khái niệm:**
Saga chia một business workflow dài thành nhiều local transaction; mỗi bước có action riêng và khi failure xảy ra có thể chạy compensating action thay vì cố giữ một distributed transaction xuyên nhiều service.

**Vấn đề nó giải quyết:**
Trong hệ thống phân tán, Order, Payment, Inventory và Shipping thường dùng storage/service khác nhau. Không thể giả định một transaction ACID chung sẽ rollback mọi side effect sau khi một bước downstream lỗi.

**Ví dụ thực tế:**
```text
Create Order
-> Reserve Inventory
-> Authorize Payment
-> Create Shipment
```

Nếu `Create Shipment` thất bại sau khi payment đã authorize:
```text
Cancel Shipment attempt
Release Inventory
Void/Refund Payment
Mark Order = Failed/Compensating
```

Compensation phải phản ánh business semantics, không chỉ “undo SQL”.

**Trade-off:**
Saga tăng recoverability và tránh distributed transaction chặt chẽ, nhưng thêm state machine, eventual consistency, retry, duplicate handling và observability phức tạp. Không nên dùng Saga nếu workflow vẫn nằm trong một database và một local transaction đã giải quyết vấn đề đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần hiểu mỗi step phải idempotent và compensation có thể fail. Senior / Technical developer phải chọn orchestration hay choreography, xác định invariant nào được phép eventual consistent, thiết kế timeout/recovery path và đảm bảo operator có thể nhìn thấy workflow đang kẹt ở bước nào.

### Design 2 — Bounded Context nên bám theo ngôn ngữ và ownership, không bám theo bảng hoặc controller

**Khái niệm:**
Trong DDD, Bounded Context là ranh giới nơi một domain model và ubiquitous language có nghĩa nhất quán. Ranh giới này thường gắn với business capability và ownership, không phải chỉ vì hệ thống đang có một nhóm table hay một API folder riêng.

**Vấn đề nó giải quyết:**
Một từ như `Customer` có thể mang ý nghĩa khác nhau trong Sales, Billing và Support. Nếu mọi module dùng chung một giant `Customer` model, thay đổi cho một team dễ gây ripple effect sang team khác.

**Ví dụ thực tế:**
```text
Sales.Customer
  - LeadStatus
  - AssignedSalesRep

Billing.CustomerAccount
  - BillingAddress
  - CreditLimit
  - PaymentTerms
```

Hai context có thể tham chiếu cùng một business entity ngoài đời nhưng không cần chia sẻ cùng class/database schema.

**Trade-off:**
Boundary rõ giảm coupling và cho phép model evolve độc lập, nhưng tăng mapping, integration contract và đôi khi duplicate data. Nếu domain nhỏ và team duy nhất, tách context quá sớm có thể tạo ceremony không cần thiết.

**Middle → Senior insight:**
Middle developer cần tôn trọng model ownership và không query chéo database/table nội bộ tùy ý. Senior / Technical developer phải xác định boundary dựa trên language, change cadence, team ownership, transaction requirement và migration cost — không chỉ dựa trên sơ đồ tổ chức hoặc tên microservice mong muốn.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo một loại technical debt mới

**Khái niệm:**
Feature Flag cho phép deploy code trước nhưng bật/tắt behavior độc lập theo user, tenant, environment hoặc rollout percentage. Nó giúp giảm blast radius và cho phép progressive delivery.

**Vấn đề nó giải quyết:**
Nếu deployment và release là cùng một hành động, mọi code mới lập tức ảnh hưởng toàn bộ traffic. Với feature rủi ro cao, team cần khả năng rollout dần, rollback logic nhanh hoặc giữ code dormant cho tới khi dependency khác sẵn sàng.

**Ví dụ thực tế:**
```text
Deploy new checkout implementation
Flag off globally
-> enable internal users
-> enable 5% traffic
-> monitor error/latency/conversion
-> 25%
-> 100%
```

Nếu error rate tăng, tắt flag nhanh hơn rollback toàn deployment.

**Trade-off:**
Feature Flag cải thiện release safety nhưng tăng số execution path cần test. Flag tồn tại quá lâu tạo dead code, condition chồng chéo và khó reasoning. Flag system bản thân cũng trở thành dependency vận hành cần availability và audit.

**Middle → Senior insight:**
Middle developer cần viết code sao cho cả flag-on và flag-off đều an toàn, có test phù hợp và không dùng flag như `if` vĩnh viễn. Senior / Technical developer phải phân loại flag, đặt owner/expiry, thiết kế rollout metric và cleanup policy, đồng thời quyết định khi nào rollback deployment vẫn tốt hơn toggle runtime.
