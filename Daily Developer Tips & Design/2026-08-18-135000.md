# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `required` members trong C# để tránh object thiếu dữ liệu

**Mẹo:**
Sử dụng `required` keyword khi model cần bắt buộc khởi tạo property.

**Tại sao hữu ích:**
Giúp phát hiện lỗi thiếu dữ liệu ngay khi compile thay vì phát hiện muộn ở runtime.

**Ví dụ:**
```csharp
public class UserRequest
{
    public required string Email { get; init; }
}
```

**Lưu ý:**
Không nên dùng cho mọi property; chỉ áp dụng với dữ liệu thực sự bắt buộc.

### Tip 2 — Dùng `AsNoTracking` khi chỉ đọc dữ liệu với EF Core

**Mẹo:**
Thêm `AsNoTracking()` cho query chỉ dùng để hiển thị hoặc báo cáo.

**Tại sao hữu ích:**
Giảm memory usage và tăng performance vì EF Core không tạo change tracking snapshot.

**Ví dụ:**
```csharp
var users = await db.Users.AsNoTracking().ToListAsync();
```

**Lưu ý:**
Không dùng nếu entity cần update sau khi query.

### Tip 3 — Debug production bằng correlation ID

**Mẹo:**
Gắn một correlation ID xuyên suốt request, log, và external calls.

**Tại sao hữu ích:**
Giúp trace một lỗi qua nhiều service hoặc nhiều tầng xử lý.

**Ví dụ:**
```http
X-Correlation-ID: 8f1c2d
```

**Lưu ý:**
Không log dữ liệu nhạy cảm chỉ để phục vụ tracing.

### Tip 4 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Sử dụng binary search của Git thay vì kiểm tra từng commit.

**Tại sao hữu ích:**
Tiết kiệm thời gian khi regression xuất hiện trong lịch sử commit dài.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.0
```

**Lưu ý:**
Cần có test hoặc cách xác định rõ trạng thái good/bad.

### Tip 5 — Thiết kế timeout cho HTTP client thay vì chờ vô hạn

**Mẹo:**
Luôn cấu hình timeout và cancellation cho external API call.

**Tại sao hữu ích:**
Ngăn thread bị giữ quá lâu khi dependency gặp sự cố.

**Ví dụ:**
```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(10));
await client.GetAsync(url, cts.Token);
```

**Lưu ý:**
Timeout cần phù hợp với SLA thực tế, không nên đặt quá thấp.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Application Design

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu phải được thay đổi cùng nhau một cách atomic.

**Vấn đề nó giải quyết:**
Tránh trạng thái dữ liệu không nhất quán khi một business operation gồm nhiều bước.

**Ví dụ thực tế:**
Tạo đơn hàng cần lưu Order, OrderItems và cập nhật inventory trong cùng một transaction hoặc có chiến lược xử lý rõ ràng.

**Trade-off:**
Transaction lớn tăng consistency nhưng có thể giảm performance và gây locking.

**Middle → Senior insight:**
Middle cần biết cách dùng transaction. Senior cần quyết định đúng boundary dựa trên business invariant, không chỉ dựa trên database operation.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia hệ thống thành các module độc lập trong cùng một deployment.

**Vấn đề nó giải quyết:**
Giữ được boundary rõ ràng mà không phải chịu toàn bộ complexity của distributed system.

**Ví dụ thực tế:**
Một hệ thống quản lý doanh nghiệp có module Identity, Billing, Notification tách biệt bằng domain boundary.

**Trade-off:**
Đơn giản hơn microservices nhưng vẫn có giới hạn về scaling độc lập.

**Middle → Senior insight:**
Middle nên hiểu microservices không phải mặc định tốt hơn. Senior cần đánh giá team size, deployment, domain complexity trước khi tách service.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo một request lặp lại nhiều lần vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate action trong distributed systems do retry hoặc network failure.

**Ví dụ thực tế:**
API thanh toán sử dụng `Idempotency-Key` để tránh charge khách hàng hai lần.

**Trade-off:**
Tăng độ tin cậy nhưng cần lưu trạng thái request và thiết kế storage phù hợp.

**Middle → Senior insight:**
Middle cần biết implement idempotent endpoint. Senior cần xác định nơi cần consistency cao và nơi có thể chấp nhận eventual consistency.
