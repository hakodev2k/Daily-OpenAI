# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `HttpClient` connection sống lâu hơn DNS topology của dependency

**Mẹo:**
Khi dùng `IHttpClientFactory`, cấu hình connection lifetime phù hợp nếu downstream service có DNS/IP thay đổi theo deployment, failover hoặc load balancing.

**Tại sao hữu ích:**
`HttpClient` nên được reuse để tránh socket exhaustion, nhưng connection trong pool có thể tiếp tục dùng endpoint cũ quá lâu. `PooledConnectionLifetime` cho phép connection được recycle định kỳ để DNS được resolve lại mà không phải tạo `HttpClient` mới cho từng request.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient("catalog")
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)
    });
```

Điều này đặc biệt hữu ích khi gọi service qua DNS có backend thay đổi theo rolling deployment hoặc failover.

**Lưu ý:**
Không đặt lifetime cực ngắn theo phản xạ vì sẽ tăng connection churn và TLS handshake. Giá trị phù hợp phụ thuộc DNS TTL, topology và latency thực tế của dependency.

### Tip 2 — Trong Elasticsearch, phân biệt `text` và `keyword` trước khi sửa query relevance

**Mẹo:**
Dùng `text` cho full-text search cần analyzer/tokenization; dùng `keyword` cho exact match, filtering, sorting và aggregation.

**Tại sao hữu ích:**
Một field được analyze thành nhiều token không phù hợp cho equality hoặc aggregation. Ngược lại, `keyword` không áp dụng analyzer nên không giải quyết tốt search theo từ tự nhiên.

**Ví dụ:**
Mapping thường gặp:
```json
"name": {
  "type": "text",
  "fields": {
    "raw": { "type": "keyword" }
  }
}
```

Search theo nội dung dùng `name`; sort hoặc aggregate dùng `name.raw`.

**Lưu ý:**
Đừng tạo multi-field cho mọi property chỉ vì tiện. Mỗi mapping/indexed field tăng storage và indexing cost; chọn theo query pattern thực tế.

### Tip 3 — Dùng `git bisect` để tìm commit gây regression thay vì đọc diff tuần tự

**Mẹo:**
Khi biết một bản cũ chạy đúng và bản hiện tại bị lỗi, dùng `git bisect` để binary-search lịch sử commit.

**Tại sao hữu ích:**
Nếu có 512 commit giữa good và bad state, binary search chỉ cần khoảng 9 lần kiểm tra thay vì đọc hoặc checkout hàng trăm commit.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v4.6.0
```

Sau mỗi lần Git checkout một commit trung gian:
```bash
git bisect good
# hoặc
git bisect bad
```

Nếu có test tự động tái hiện regression, có thể dùng `git bisect run` để tự động hóa toàn bộ quá trình.

**Lưu ý:**
Bisect chỉ hiệu quả khi có tiêu chí pass/fail deterministic. Flaky test hoặc commit không build được có thể làm kết quả sai; khi cần, đánh dấu commit không kiểm tra được là `skip`.

### Tip 4 — Với cookie authentication, hiểu `SameSite` trước khi sửa lỗi login cross-site

**Mẹo:**
Khi authentication hoạt động local nhưng fail qua external identity provider hoặc cross-site redirect, kiểm tra `SameSite`, `Secure` và HTTPS trước khi nghi ngờ token validation.

**Tại sao hữu ích:**
Browser có thể không gửi cookie trong một số cross-site flow tùy `SameSite` policy. Application khi đó nhìn như mất session dù server-side authentication code hoàn toàn đúng.

**Ví dụ:**
Một OIDC callback từ identity provider quay về application có thể cần cookie phù hợp với flow và luôn chạy qua HTTPS trong production.

```text
Browser -> Identity Provider
        -> callback to app
        -> correlation/session cookie phải còn hợp lệ
```

**Lưu ý:**
Không chuyển mọi cookie sang `SameSite=None` để "fix" nhanh. `None` yêu cầu `Secure` và làm cookie được gửi rộng hơn; cần cấu hình đúng theo từng cookie và flow để tránh tăng CSRF exposure.

### Tip 5 — Theo dõi Large Object Heap khi memory tăng dù allocation rate nhìn không quá cao

**Mẹo:**
Nếu .NET service xử lý file, JSON lớn hoặc buffer lớn và memory tăng bất thường, kiểm tra allocation lên Large Object Heap thay vì chỉ nhìn tổng số object.

**Tại sao hữu ích:**
Object lớn đi vào LOH và có lifecycle/compaction behavior khác với small-object generations. Các buffer lớn tồn tại ngắn nhưng lặp lại có thể gây fragmentation và GC pause đáng kể.

**Ví dụ:**
Scenario:
```text
API nhận file lớn
-> đọc toàn bộ vào byte[]
-> transform
-> tạo byte[] mới
-> trả response
```

Hai hoặc ba buffer lớn tồn tại đồng thời trên nhiều request có thể đẩy working set lên rất nhanh. Streaming hoặc reuse buffer thường đáng xem xét hơn việc tăng memory limit.

**Lưu ý:**
Không tối ưu LOH chỉ dựa trên giả định. Dùng profiler, `dotnet-counters`, dump hoặc allocation trace để xác nhận object type, size và retention path trước khi thay đổi code.

## 🧠 Software Design

### Design 1 — Saga Orchestration vs Choreography cho workflow nhiều service

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction có compensating action. Orchestration dùng một coordinator điều khiển flow; Choreography để các service phản ứng với event của nhau.

**Vấn đề nó giải quyết:**
Trong distributed system, một checkout có thể cần Order, Payment, Inventory và Shipping cùng thay đổi nhưng không thể dùng một ACID transaction xuyên tất cả service một cách thực tế.

**Ví dụ thực tế:**
Orchestration:
```text
CheckoutSaga
-> reserve inventory
-> charge payment
-> create shipment
-> nếu payment fail: release inventory
```

Choreography:
```text
OrderCreated
-> Inventory reserves
-> InventoryReserved
-> Payment charges
-> PaymentFailed
-> Inventory compensates
```

**Trade-off:**
Orchestration làm flow và failure handling dễ quan sát hơn nhưng coordinator có thể trở thành coupling point. Choreography tăng autonomy nhưng flow end-to-end khó hiểu, debug và evolve khi số event/service tăng.

**Middle → Senior insight:**
Middle developer cần hiểu compensation khác rollback và consumer phải idempotent. Senior / Technical developer phải chọn orchestration hay choreography dựa trên workflow complexity, ownership, observability, coupling và khả năng thay đổi business process.

### Design 2 — Optimistic Concurrency cho dữ liệu có nhiều người chỉnh sửa

**Khái niệm:**
Optimistic concurrency giả định conflict hiếm và cho phép nhiều actor đọc cùng state; khi ghi, hệ thống kiểm tra version/token để phát hiện state đã thay đổi từ lúc đọc.

**Vấn đề nó giải quyết:**
Nếu hai user cùng sửa một document hoặc order, update cuối cùng có thể âm thầm ghi đè thay đổi của người trước nếu application chỉ dùng `UPDATE ... WHERE Id = ...`.

**Ví dụ thực tế:**
Entity có `rowversion`:
```text
User A đọc version 12
User B đọc version 12
User A save -> version 13
User B save với version 12 -> conflict
```

Application có thể yêu cầu reload/merge thay vì silently overwrite.

**Trade-off:**
Optimistic concurrency không giữ lock lâu và scale tốt khi conflict thấp, nhưng đẩy complexity sang conflict handling và UX. Pessimistic locking phù hợp hơn trong một số critical section ngắn nhưng tăng blocking và contention.

**Middle → Senior insight:**
Middle developer cần xử lý concurrency exception như một business scenario, không phải generic 500. Senior / Technical developer phải chọn conflict granularity, merge policy và UX dựa trên invariant, frequency of conflict và cost của lost update.

### Design 3 — Hexagonal Architecture: giữ adapter ở boundary, không biến domain thành framework abstraction

**Khái niệm:**
Hexagonal Architecture tách core application/domain khỏi external technology thông qua ports và adapters. Mục tiêu là cô lập dependency direction, không phải tạo interface cho mọi class.

**Vấn đề nó giải quyết:**
Nếu business logic gọi trực tiếp SQL, HTTP SDK, filesystem hoặc framework primitives ở khắp nơi, test và thay đổi integration trở nên khó vì domain bị dính infrastructure concern.

**Ví dụ thực tế:**
```text
Application core
-> IInventoryGateway port

Adapters:
- SqlInventoryGateway
- ExternalApiInventoryGateway
```

Core chỉ biết capability cần dùng, adapter chịu trách nhiệm protocol và technology detail.

**Trade-off:**
Boundary rõ giúp testability và thay adapter dễ hơn, nhưng thêm interface, mapping và indirection. Với CRUD nhỏ, thêm nhiều port/adapter có thể chỉ làm code dài hơn mà không tạo giá trị.

**Middle → Senior insight:**
Middle developer cần giữ infrastructure dependency ở edge và tránh leak DTO/SDK type vào domain. Senior / Technical developer phải xác định boundary nào thực sự có volatility hoặc business value đủ lớn để justify abstraction, thay vì áp dụng Hexagonal Architecture như template bắt buộc.
