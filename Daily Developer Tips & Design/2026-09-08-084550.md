# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsSplitQuery()` khi nhiều `Include` tạo cartesian explosion trong EF Core

**Mẹo:**
Khi một query load nhiều collection navigation bằng `Include`, kiểm tra generated SQL và số row thực tế. Nếu một query join lớn làm dữ liệu bị nhân chéo mạnh, cân nhắc `AsSplitQuery()` để EF Core tách thành nhiều SQL query nhỏ hơn.

**Tại sao hữu ích:**
Nếu một `Order` có 20 `Items` và 15 `Notes`, join cả hai collection có thể tạo tới 300 row trung gian cho cùng một order. Database phải gửi nhiều dữ liệu lặp, application phải materialize và de-duplicate entity, làm tăng latency, network và memory.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(cancellationToken);
```

So sánh số row, execution time và payload giữa single query và split query trước khi quyết định.

**Lưu ý:**
Split query tăng số database round trip và có thể quan sát dữ liệu ở các thời điểm hơi khác nhau nếu concurrent update xảy ra giữa các query. Nếu endpoint chỉ cần DTO, projection bằng `Select` thường còn tốt hơn việc load cả graph.

### Tip 2 — Chẩn đoán Cosmos DB hot partition bằng RU và traffic distribution, không chỉ nhìn tổng RU

**Mẹo:**
Khi Cosmos DB bị throttling dù tổng provisioned RU/s có vẻ đủ, kiểm tra RU consumption theo partition key và phân bố request thay vì chỉ nhìn aggregate throughput.

**Tại sao hữu ích:**
Cosmos DB phân phối dữ liệu và throughput theo physical partition. Nếu một tenant, customer hoặc key nhận phần lớn traffic, partition chứa key đó có thể bị throttled trong khi các partition khác còn capacity dư.

**Ví dụ:**
Một SaaS dùng:
```text
PartitionKey = TenantId
```

Tenant `enterprise-001` tạo 45% traffic toàn hệ thống. Nếu nhiều request bị `429`, cần xác minh partition distribution, RU/request và traffic pattern trước khi chỉ tăng tổng RU.

**Lưu ý:**
Không đổi partition key vội vàng chỉ vì có một tenant nóng. Partition-key migration rất tốn kém và có ảnh hưởng schema/data. Có thể cần workload isolation, synthetic key, dedicated container hoặc cache tùy access pattern.

### Tip 3 — Phân biệt Kubernetes CPU request và CPU limit khi Pod “không lỗi nhưng chạy chậm”

**Mẹo:**
Nếu Pod không restart nhưng latency tăng dưới tải, kiểm tra CPU usage, throttling và cấu hình `requests`/`limits` thay vì chỉ nhìn trạng thái `Running`.

**Tại sao hữu ích:**
`requests` ảnh hưởng scheduling và guaranteed capacity tương đối; `limits` có thể khiến container bị CPU throttling khi vượt ngưỡng. Application vẫn sống nhưng request xử lý chậm hơn, queue tăng và timeout xuất hiện ở upstream.

**Ví dụ:**
Một ASP.NET Core API có:
```yaml
resources:
  requests:
    cpu: "250m"
  limits:
    cpu: "500m"
```

Nếu profiler cho thấy CPU-bound workload và telemetry cho thấy throttling tăng đúng lúc p95 latency tăng, vấn đề có thể là resource limit chứ không phải database.

**Lưu ý:**
Không giải quyết bằng cách bỏ toàn bộ limit hoặc tăng resource vô hạn. Cần phân biệt CPU-bound, ThreadPool starvation và dependency latency, rồi điều chỉnh request/limit dựa trên load test và capacity thực tế.

### Tip 4 — Dùng `ETag` và `If-None-Match` cho content ít thay đổi thay vì luôn trả lại toàn bộ payload

**Mẹo:**
Với CMS content, product metadata hoặc API response có representation ổn định, cân nhắc dùng `ETag` để client thực hiện conditional request và nhận `304 Not Modified` khi dữ liệu chưa đổi.

**Tại sao hữu ích:**
Client vẫn có thể kiểm tra freshness mà không phải tải lại toàn bộ JSON hoặc HTML. Điều này giảm bandwidth, serialization work và latency, đặc biệt với mobile client hoặc content được đọc thường xuyên nhưng thay đổi ít.

**Ví dụ:**
Response:
```http
ETag: "product-8472-v19"
```

Request sau:
```http
If-None-Match: "product-8472-v19"
```

Nếu version chưa đổi, server trả:
```http
304 Not Modified
```

**Lưu ý:**
ETag phải phản ánh đúng representation, không chỉ entity ID. Nếu response thay đổi theo locale, authorization hoặc query parameter, cache key/ETag cũng phải phản ánh các biến thể đó để tránh trả sai dữ liệu.

### Tip 5 — Dùng `dotnet-counters` để phân biệt ThreadPool starvation với CPU saturation

**Mẹo:**
Khi ASP.NET Core latency tăng nhưng CPU chưa chắc đạt 100%, dùng `dotnet-counters` hoặc telemetry runtime tương đương để quan sát ThreadPool queue, thread count, GC và CPU cùng lúc.

**Tại sao hữu ích:**
ThreadPool starvation thường xuất hiện khi code sync-block trên async work, blocking I/O hoặc giữ thread quá lâu. Triệu chứng có thể là request queue tăng, thread count tăng dần và latency cao dù CPU chưa bão hòa hoàn toàn.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Nếu `ThreadPool Queue Length` tăng liên tục trong khi CPU không tương ứng, hãy tìm `Task.Result`, `.Wait()`, blocking I/O hoặc synchronous work trong request path.

**Lưu ý:**
Counter chỉ cho symptom, không tự chỉ ra method gây lỗi. Sau khi xác định starvation là hypothesis hợp lý, tiếp tục dùng trace/profiler để tìm call stack và blocking source trước khi sửa.

## 🧠 Software Design

### Design 1 — API Versioning vs additive evolution

**Khái niệm:**
Không phải mọi thay đổi API đều cần tạo `/v2`. Additive evolution giữ contract hiện tại bằng cách thêm field/endpoint optional và duy trì semantics cũ; versioning phù hợp hơn khi contract thực sự cần breaking change hoặc semantics mới không thể tương thích.

**Vấn đề nó giải quyết:**
Nếu version quá sớm, team phải vận hành nhiều contract song song, duplicate code và migration consumer kéo dài. Nhưng nếu cố nhồi breaking change vào cùng version, consumer cũ có thể hỏng không báo trước.

**Ví dụ thực tế:**
Thêm optional `displayName` vào customer response thường có thể giữ cùng version. Ngược lại, đổi meaning của `status`, bỏ field bắt buộc hoặc thay workflow authentication có thể cần version mới hoặc migration contract rõ ràng.

**Trade-off:**
Additive evolution giảm maintenance cost và giữ adoption đơn giản nhưng đôi khi để lại field cũ lâu hơn mong muốn. Versioning tạo boundary rõ cho breaking change nhưng tăng operational cost, documentation, test matrix và deprecation work.

**Middle → Senior insight:**
Middle developer cần phân biệt additive, compatible và breaking change ở schema/HTTP behavior. Senior / Technical developer phải quyết định khi nào chi phí versioning đáng trả, đặt deprecation policy, telemetry consumer usage và migration window thay vì mặc định “có thay đổi là tạo v2”.

### Design 2 — Saga orchestration vs choreography cho distributed workflow

**Khái niệm:**
Saga chia một business transaction xuyên nhiều service thành các local transaction kèm compensating action. Orchestration dùng một coordinator điều khiển step; choreography để các service phản ứng với event của nhau mà không có central coordinator.

**Vấn đề nó giải quyết:**
Một checkout có Payment, Inventory và Shipping không thể dựa vào một ACID transaction duy nhất nếu các service độc lập. Khi một bước fail sau khi các bước trước đã commit, hệ thống cần biết cách bù trừ và quan sát trạng thái workflow.

**Ví dụ thực tế:**
Flow:
```text
ReserveInventory -> ChargePayment -> CreateShipment
```

Nếu `CreateShipment` fail, saga có thể yêu cầu `RefundPayment` và `ReleaseInventory`. Orchestrator có thể ghi state từng step; choreography có thể dựa trên event như `PaymentCharged`, `ShipmentFailed`.

**Trade-off:**
Orchestration dễ nhìn toàn bộ flow, timeout và recovery hơn nhưng tạo coordinator có ownership lớn. Choreography giảm central coupling nhưng flow dễ trở nên khó trace, event dependency ngầm và vòng phản ứng phức tạp khi số service tăng.

**Middle → Senior insight:**
Middle developer cần hiểu idempotency, retry và compensating action của từng step. Senior / Technical developer phải chọn orchestration/choreography dựa trên workflow complexity, ownership, observability, failure recovery và khả năng thay đổi business flow — không dựa trên sở thích event-driven.

### Design 3 — Authorization boundary nên theo resource và business capability, không chỉ theo role name

**Khái niệm:**
Role-based authorization hữu ích ở mức coarse-grained, nhưng nhiều hệ thống cần kiểm tra quyền trên resource cụ thể và action cụ thể: user nào được sửa order nào, tenant nào được xem document nào, trạng thái business nào cho phép operation nào.

**Vấn đề nó giải quyết:**
Một check như `User.IsInRole("Admin")` có thể quá rộng và làm security rule rải khắp controller. Khi requirement thay đổi, team khó biết rule thật nằm ở đâu và dễ tạo privilege escalation ngoài ý muốn.

**Ví dụ thực tế:**
Thay vì chỉ kiểm tra:
```text
Role = Manager
```

operation `ApproveInvoice` có thể cần:
```text
same tenant
+ invoice amount <= approval limit
+ invoice state = PendingApproval
+ user has ApproveInvoice capability
```

Policy/application authorization service có thể tập trung hóa các rule này gần business boundary.

**Trade-off:**
Fine-grained authorization tăng độ chính xác và auditability nhưng thêm policy complexity, data lookup và test requirement. Với internal tool rất nhỏ, role-based rule đơn giản có thể đủ và dễ vận hành hơn.

**Middle → Senior insight:**
Middle developer cần đảm bảo authorization diễn ra server-side và trên đúng resource/action, không chỉ ẩn button ở UI. Senior / Technical developer phải thiết kế policy ownership, least privilege, cacheability, audit trail và boundary giữa authorization logic với domain rule để security không trở thành một tập `if` phân tán.
