# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure thay vì để queue tăng vô hạn

**Mẹo:**
Khi producer tạo work nhanh hơn consumer xử lý được, dùng bounded `Channel<T>` để giới hạn số item đang chờ và buộc producer chậm lại thay vì để queue trong memory tăng vô hạn.

**Tại sao hữu ích:**
Unbounded queue che giấu overload trong thời gian ngắn nhưng đổi lại memory tăng, latency hàng đợi kéo dài và cuối cùng có thể dẫn tới GC pressure hoặc OOM. Bounded channel biến capacity thành một phần rõ ràng của flow-control.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, cancellationToken);
```

Nếu consumer xử lý 100 job/s nhưng producer đẩy 500 job/s, `WriteAsync` sẽ bắt đầu chờ khi buffer đầy thay vì tiếp tục tích lũy vô hạn.

**Lưu ý:**
Backpressure chỉ hiệu quả nếu upstream có thể chậm lại. Với webhook hoặc message broker không thể “ngừng thế giới”, cần kết hợp broker-level retry, concurrency limit, dead-letter hoặc scale-out phù hợp. Đừng chọn capacity theo cảm tính; đo throughput và latency trước.

### Tip 2 — Dùng filtered index khi chỉ một tập con nhỏ của table thực sự được query thường xuyên

**Mẹo:**
Trong SQL Server, nếu workload chủ yếu truy vấn một trạng thái hiếm như `Status = 'Pending'`, cân nhắc filtered index thay vì index toàn bộ table.

**Tại sao hữu ích:**
Filtered index nhỏ hơn, ít page hơn, tốn ít write-maintenance hơn và có thể có selectivity tốt hơn so với index bao phủ cả hàng triệu row không liên quan.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON Orders (CreatedAt)
INCLUDE (CustomerId, TotalAmount)
WHERE Status = 'Pending';
```

Query phù hợp:
```sql
SELECT CustomerId, TotalAmount
FROM Orders
WHERE Status = 'Pending'
ORDER BY CreatedAt;
```

**Lưu ý:**
Optimizer chỉ dùng filtered index khi predicate của query tương thích với filter. Nếu query parameterization hoặc logic động khiến predicate không rõ tại compile time, plan có thể không chọn index như mong đợi. Luôn kiểm tra execution plan thực tế.

### Tip 3 — Chuẩn hóa lỗi API bằng `ProblemDetails` thay vì mỗi endpoint tự tạo JSON lỗi

**Mẹo:**
Trong ASP.NET Core, dùng `ProblemDetails` và centralized exception handling để trả lỗi có cấu trúc nhất quán cho validation, not-found, conflict và unexpected failure.

**Tại sao hữu ích:**
Khi mỗi controller tự trả một format khác nhau, frontend/mobile client phải viết nhiều nhánh parsing và observability khó correlation. Contract lỗi ổn định giúp client xử lý predictably và backend dễ bổ sung `traceId` hoặc error code.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();

return Results.Problem(
    statusCode: StatusCodes.Status409Conflict,
    title: "Order state conflict",
    extensions: new Dictionary<string, object?>
    {
        ["code"] = "ORDER_ALREADY_PAID"
    });
```

**Lưu ý:**
Đừng trả stack trace, SQL message hoặc internal exception detail cho client production. `ProblemDetails` là contract presentation; business error code vẫn cần được thiết kế ổn định và có semantics rõ.

### Tip 4 — Dùng discriminated union trong TypeScript để loại bỏ state bất hợp lệ của UI

**Mẹo:**
Thay vì nhiều boolean như `isLoading`, `hasError`, `hasData`, mô hình hóa async state bằng union có discriminator rõ ràng.

**Tại sao hữu ích:**
Nhiều boolean dễ tạo trạng thái vô nghĩa như vừa `isLoading = true` vừa `hasError = true`. Discriminated union khiến compiler ép code xử lý đúng từng state và giảm bug ở component logic.

**Ví dụ:**
```ts
type LoadState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string }

function render(state: LoadState<Product[]>) {
  switch (state.status) {
    case 'success':
      return state.data.length
    case 'error':
      return state.error
  }
}
```

**Lưu ý:**
Đừng tạo union quá chi tiết nếu UI chỉ có vài state đơn giản. Mục tiêu là encode invariant hữu ích, không biến state model thành một state machine khó đọc khi chưa cần.

### Tip 5 — Dùng `dotnet-counters` để phân biệt CPU pressure, GC pressure và ThreadPool starvation trước khi dump memory

**Mẹo:**
Khi production .NET API đột nhiên chậm hoặc CPU tăng, bắt đầu bằng runtime counters như CPU usage, allocation rate, GC heap size, ThreadPool queue length và exception rate trước khi thu dump nặng.

**Tại sao hữu ích:**
Counters cho signal nhanh về loại bottleneck. ThreadPool queue tăng nhưng CPU thấp gợi ý blocking/starvation; allocation rate và GC time tăng gợi ý memory churn; CPU cao liên tục lại dẫn tới hướng điều tra khác.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 \
  System.Runtime Microsoft.AspNetCore.Hosting
```

Một pattern đáng chú ý:
```text
CPU Usage: 35%
ThreadPool Queue Length: 2500
ThreadPool Thread Count: tăng liên tục
```

Có thể hypothesis rằng request đang block synchronous I/O hoặc ThreadPool bị starvation thay vì CPU-bound.

**Lưu ý:**
Counter chỉ là evidence ban đầu, không phải root cause cuối cùng. Sau khi khoanh vùng, mới dùng trace, dump, profiler hoặc dependency telemetry phù hợp. Đừng thu memory dump production theo phản xạ nếu signal chưa chỉ tới memory issue.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository: abstraction chỉ có giá trị khi nó che một boundary thật

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work, change tracking và query abstraction. Repository tùy biến chỉ nên thêm khi nó biểu diễn business-oriented data boundary, encapsulate query phức tạp có ownership rõ hoặc hỗ trợ nhiều persistence mechanism thực sự.

**Vấn đề nó giải quyết:**
Nhiều codebase tạo repository CRUD cho mọi entity rồi chỉ forward `Add`, `Find`, `Update`, khiến abstraction không che thêm gì nhưng lại cắt mất khả năng dùng LINQ/projection hiệu quả của EF Core.

**Ví dụ thực tế:**
Với application service đơn giản:
```text
OrderApplicationService
  -> DbContext.Orders
  -> projection / transaction
```

có thể rõ ràng hơn `IOrderRepository.GetById`, `Update`, `Save` nếu repository chỉ wrap EF Core.

Repository có thể đáng giá hơn nếu nó cung cấp contract giàu semantics như:
```text
IInventoryReservationStore.TryReserve(...)
```

và che logic persistence phức tạp phía sau.

**Trade-off:**
Direct `DbContext` giảm boilerplate và giữ sức mạnh EF Core, nhưng dễ để query logic rải rác nếu team thiếu discipline. Repository có thể gom boundary và hỗ trợ testing/ownership, nhưng generic CRUD repository thường thêm indirection mà không giảm coupling thật.

**Middle → Senior insight:**
Middle developer cần biết dùng `DbContext` đúng lifecycle, transaction và query semantics. Senior / Technical developer phải phân biệt abstraction vì domain boundary với abstraction chỉ vì pattern, đồng thời đánh giá migration cost, test strategy và khả năng tối ưu query trước khi thêm repository layer.

### Design 2 — REST đồng bộ vs messaging bất đồng bộ: chọn theo coupling của thời gian và failure

**Khái niệm:**
REST đồng bộ buộc caller chờ dependency phản hồi trong cùng request path. Messaging bất đồng bộ tách thời điểm gửi và xử lý, cho phép producer hoàn thành trước khi consumer xử lý xong.

**Vấn đề nó giải quyết:**
Nếu checkout phải gọi Inventory, Billing, Notification và Analytics tuần tự, latency và failure của từng dependency cộng dồn. Nhưng chuyển mọi thứ sang queue cũng tạo eventual consistency và workflow khó quan sát hơn.

**Ví dụ thực tế:**
Có thể giữ synchronous call cho bước cần kết quả ngay:
```text
Checkout -> Inventory availability check
```

và dùng event cho side effect không cần block response:
```text
OrderPlaced
  -> Analytics
  -> Email
  -> CRM sync
```

**Trade-off:**
REST đơn giản, dễ debug và cho consistency tức thời hơn nhưng coupling latency/availability cao. Messaging tăng resilience và decoupling nhưng thêm broker, retry, duplicate delivery, schema evolution và eventual consistency.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry và idempotency ở cả hai kiểu integration. Senior / Technical developer phải chọn communication style theo business invariant, latency budget, failure tolerance và ownership — không theo khẩu hiệu “async scale tốt hơn”.

### Design 3 — Cache invalidation nên được thiết kế từ source-of-truth và staleness budget

**Khái niệm:**
Caching không chỉ là đặt TTL. Thiết kế cache cần xác định nguồn dữ liệu chuẩn, mức stale chấp nhận được, ai chịu trách nhiệm invalidate và hệ thống làm gì khi cache/backend lỗi.

**Vấn đề nó giải quyết:**
Một catalog page có thể chấp nhận dữ liệu cũ 5 phút, nhưng inventory hoặc permission có thể không chấp nhận stale data tương tự. Dùng cùng một chiến lược TTL cho mọi dữ liệu làm consistency trở nên ngẫu nhiên.

**Ví dụ thực tế:**
Product description:
```text
cache-aside + TTL 10 phút
stale ngắn hạn chấp nhận được
```

User authorization:
```text
TTL ngắn hoặc event-driven invalidation
revocation cần propagation nhanh
```

Nếu Redis unavailable, catalog có thể fallback database; còn authorization cache failure có thể cần fail closed tùy threat model.

**Trade-off:**
Cache giảm latency và load nhưng thêm stale-data risk, invalidation complexity và dependency vận hành. Event-driven invalidation giảm thời gian stale nhưng thêm messaging path và vẫn không loại bỏ hoàn toàn race condition.

**Middle → Senior insight:**
Middle developer cần biết cache key, TTL và invalidation cơ bản. Senior / Technical developer phải định nghĩa staleness budget theo business semantics, failure mode khi cache down, source-of-truth ownership và cách quan sát cache hit ratio, stale data hoặc invalidation lag.
