# Daily Developer Tips & Design — 2026-09-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi LOH trước khi đổ lỗi cho “memory leak”

**Mẹo:**
Khi .NET service tăng memory sau khi xử lý payload/file lớn, kiểm tra allocation rate, GC generations và Large Object Heap (LOH) bằng profiler hoặc `dotnet-counters` trước khi kết luận object bị giữ vĩnh viễn.

**Tại sao hữu ích:**
Object lớn được quản lý khác với allocation nhỏ; workload tạo nhiều `byte[]`, string hoặc serialization buffer lớn có thể làm working set và GC pause tăng dù object cuối cùng vẫn được collect. Evidence từ heap/allocation giúp phân biệt retention leak với allocation pressure.

**Ví dụ:**
Một export endpoint đọc toàn bộ file 20 MB vào `byte[]` cho mỗi request. Thay vì chỉ tăng memory limit, đo allocation rồi chuyển sang streaming nếu API/storage hỗ trợ để tránh giữ nhiều buffer lớn đồng thời.

**Lưu ý:**
Không tối ưu chỉ dựa vào Task Manager working set. GC heap size, committed memory và process working set không đồng nghĩa; cần heap snapshot hoặc counters đúng để xác định object nào sống lâu và vì sao.

### Tip 2 — Rate limiting phải chọn partition key theo abuse model

**Mẹo:**
Trong ASP.NET Core rate limiting, đừng mặc định partition chỉ theo IP. Chọn key theo identity/API key/tenant/endpoint tùy loại tài nguyên cần bảo vệ.

**Tại sao hữu ích:**
NAT có thể khiến hàng nghìn user chung một IP, trong khi attacker có thể phân tán nhiều IP. Partition sai gây false throttling hoặc không bảo vệ được expensive operation thực sự.

**Ví dụ:**
Authenticated reporting API có thể giới hạn theo tenant vì một report tiêu tốn database/CPU đáng kể; login endpoint chưa có identity lại có thể cần kết hợp IP và account identifier với policy riêng.

**Lưu ý:**
Rate limiting không thay thế authorization, quota nghiệp vụ hay DDoS protection ở edge. Với multi-instance deployment, phải hiểu limiter là local hay có shared enforcement trước khi tuyên bố global quota.

### Tip 3 — Dùng SQL constraint để bảo vệ invariant mà application race condition có thể phá

**Mẹo:**
Nếu một invariant có thể biểu diễn chắc chắn bằng `UNIQUE`, `CHECK`, foreign key hoặc atomic statement, hãy để database làm lớp bảo vệ cuối thay vì chỉ `SELECT` kiểm tra rồi `INSERT`.

**Tại sao hữu ích:**
Hai request concurrent có thể cùng vượt qua application-level existence check trước khi một request commit. Database constraint thực thi invariant tại điểm ghi dữ liệu và đóng race window đó.

**Ví dụ:**
Để đảm bảo mỗi tenant chỉ có một external reference, tạo unique constraint/index trên `(TenantId, ExternalReference)` và xử lý duplicate-key result thành domain/API response phù hợp.

**Lưu ý:**
Constraint không thay thế validation thân thiện ở application layer. Đồng thời đừng dùng constraint phức tạp để nhét mọi business rule vào database nếu rule phụ thuộc workflow hoặc external state.

### Tip 4 — Kubernetes requests/limits ảnh hưởng trực tiếp đến scheduling và throttling

**Mẹo:**
Khi Pod chậm hoặc restart dưới tải, kiểm tra CPU/memory usage cùng `requests`, `limits`, throttling và OOM evidence; đừng chỉ nhìn application logs.

**Tại sao hữu ích:**
Scheduler dùng requests để đặt Pod lên node, còn limits có thể giới hạn runtime resource. CPU limit quá thấp có thể gây throttling và tăng latency; memory vượt limit có thể dẫn tới OOM kill dù application không ném managed exception.

**Ví dụ:**
ASP.NET Core API có CPU usage chạm limit và p99 latency tăng sau rollout. Correlate container CPU throttling với request rate trước khi kết luận ThreadPool hoặc SQL là bottleneck.

**Lưu ý:**
Bỏ toàn bộ limits cũng không phải mặc định đúng. Cần load test và production telemetry để đặt resource policy phù hợp workload, cluster capacity và blast radius mong muốn.

### Tip 5 — Correlation ID phải đi qua cả HTTP lẫn message boundary

**Mẹo:**
Khi workflow chuyển từ HTTP request sang Azure Service Bus, propagate trace/correlation context trong message metadata và tiếp tục trace ở consumer thay vì tạo một chuỗi log độc lập.

**Tại sao hữu ích:**
Async boundary thường là nơi production investigation bị đứt. Nếu API trả `202` nhưng background processing thất bại, trace liên tục giúp nối request ban đầu với publish, queue delay, consumer execution và downstream dependency.

**Ví dụ:**
Checkout API ghi `TraceId`, publish `OrderAccepted`, consumer tạo span tiếp nối context và log `MessageId`, `DeliveryCount`, `OrderId` đã được sanitize. Application Insights/OpenTelemetry sau đó có thể hiển thị end-to-end flow.

**Lưu ý:**
Không dùng business identifier nhạy cảm làm trace ID và không giả định mọi broker/library tự propagate context đúng. Kiểm tra instrumentation thực tế và tránh tạo cardinality cao trong metric labels.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database write + event publication

**Khái niệm:**
Outbox Pattern ghi business change và event cần publish vào cùng local database transaction; một publisher riêng đọc outbox và gửi message sau commit. Nó tránh khoảng trống giữa “database đã commit” và “broker chưa nhận event”.

**Vấn đề nó giải quyết:**
Nếu Order được lưu thành công nhưng process crash trước khi publish `OrderCreated`, downstream không bao giờ biết thay đổi. Nếu publish trước rồi database rollback, downstream lại thấy event cho state chưa tồn tại.

**Ví dụ thực tế:**
Trong transaction tạo Order, application insert thêm Outbox row chứa event payload/metadata. Worker publish tới Azure Service Bus và đánh dấu processed; consumer vẫn phải idempotent vì publisher có thể gửi lại khi crash quanh bước acknowledge.

**Trade-off:**
Outbox tăng reliability mà không cần distributed transaction, nhưng thêm bảng, publisher, cleanup, ordering/deduplication và monitoring. Với application đơn giản không có broker hoặc side effect có thể retry trực tiếp, pattern này có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần bảo đảm business row và outbox row commit atomically, đồng thời hiểu duplicate delivery. Senior / Technical developer phải thiết kế event ownership, ordering requirement, retention/replay, failure recovery và quyết định khi nào reliability gain đủ lớn để trả operational cost.

### Design 2 — Readiness degradation thay vì fail toàn service vì optional dependency

**Khái niệm:**
Health/degradation design phân biệt dependency bắt buộc để service phục vụ core capability với dependency tùy chọn có thể degrade. Không phải mọi dependency failure đều nên làm toàn instance unavailable.

**Vấn đề nó giải quyết:**
Một product API phụ thuộc SQL cho dữ liệu chính, Redis cho cache và recommendation provider cho nội dung phụ. Nếu recommendation lỗi mà readiness trả unhealthy, orchestrator có thể loại toàn bộ Pod dù core product endpoint vẫn hoạt động.

**Ví dụ thực tế:**
SQL connectivity mất có thể khiến service không ready. Redis lỗi có thể fallback về database với load guard; recommendation lỗi có thể bỏ section đó và emit metric/alert thay vì trả 500 toàn trang.

**Trade-off:**
Graceful degradation tăng availability nhưng làm code/state phức tạp hơn và có nguy cơ che dependency incident nếu observability yếu. Fail-fast đơn giản hơn và đúng khi dependency là bắt buộc cho correctness/security.

**Middle → Senior insight:**
Middle developer cần implement timeout, fallback và health checks theo contract rõ. Senior / Technical developer phải phân loại criticality, capacity khi fallback, user-visible semantics và blast radius để quyết định dependency nào làm service fail, degrade hay shed load.

### Design 3 — Shared database hay database-per-service không phải quyết định thuần kỹ thuật

**Khái niệm:**
Shared database đơn giản hóa transaction/query nhưng tạo schema/runtime coupling. Database-per-service tăng data ownership và deployment autonomy nhưng buộc integration qua contracts và thường chấp nhận eventual consistency.

**Vấn đề nó giải quyết:**
Khi nhiều modules/services cùng sửa bảng của nhau, migration và release trở nên khó độc lập; ngược lại tách database quá sớm làm reporting, transaction và operations phức tạp không cần thiết.

**Ví dụ thực tế:**
Một Modular Monolith nhỏ có thể dùng cùng SQL Server nhưng mỗi module sở hữu schema/table rõ ràng. Khi Ordering cần scale/deploy độc lập và team ownership tách thật sự, extraction sang datastore riêng có thể được thực hiện qua migration/integration contract thay vì tách ngay từ ngày đầu.

**Trade-off:**
Shared DB có operational simplicity và ACID dễ hơn nhưng boundary dễ bị xuyên thủng. Database-per-service enforce autonomy tốt hơn nhưng thêm duplication, synchronization, observability và data-reconciliation cost.

**Middle → Senior insight:**
Middle developer cần tôn trọng data ownership dù cùng database. Senior / Solution-oriented engineer phải cân nhắc team topology, release independence, consistency requirement, reporting, migration strategy và operational maturity; physical database separation chỉ có giá trị khi autonomy pressure là thật.
