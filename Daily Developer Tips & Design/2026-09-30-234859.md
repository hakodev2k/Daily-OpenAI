# Daily Developer Tips & Design — 2026-09-30

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán SQL plan regression bằng execution plan và statistics

**Mẹo:**
Khi một query SQL Server vốn nhanh bỗng chậm, đừng thêm index ngay. So sánh actual execution plan, estimated/actual row count, statistics freshness và plan trước/sau regression để xác định optimizer đang ước lượng sai hay chọn plan không còn phù hợp.

**Tại sao hữu ích:**
Optimizer chọn join strategy, access path và memory grant dựa trên cardinality estimates. Statistics cũ, data skew hoặc parameter-sensitive workload có thể khiến một plan tốt cho tập dữ liệu này trở nên rất tệ cho tập khác.

**Ví dụ:**
```sql
SET STATISTICS IO, TIME ON;

SELECT Id, Status, CreatedAt
FROM Orders
WHERE TenantId = @tenantId
  AND CreatedAt >= @from;
```
Nếu estimated rows là 100 nhưng actual rows là 800,000, hãy điều tra statistics, data distribution và parameter sensitivity trước khi thay schema.

**Lưu ý:**
`OPTION (RECOMPILE)` hoặc ép plan có thể giảm symptom nhưng tăng CPU hoặc khóa hệ thống vào một plan không còn phù hợp. Chỉ dùng sau khi hiểu workload và đo tác động.

### Tip 2 — Redis cache stampede: thêm jitter và single-flight cho hot key

**Mẹo:**
Với key có traffic cao, tránh để hàng nghìn request cùng thấy cache miss và cùng truy vấn database khi TTL hết. Kết hợp TTL jitter với cơ chế single-flight/per-key coordination khi workload thực sự cần.

**Tại sao hữu ích:**
TTL giống nhau có thể khiến nhiều key hết hạn cùng lúc; với hot key, một miss có thể nhân tải xuống database thành số lượng request đồng thời. Jitter phân tán expiration, còn single-flight giảm duplicate work trong một instance hoặc theo boundary phù hợp.

**Ví dụ:**
```csharp
var ttl = TimeSpan.FromMinutes(5)
        + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

await cache.SetStringAsync(key, json,
    new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl }, ct);
```
Nếu catalog hot key miss, chỉ một execution rebuild dữ liệu; request khác chờ hoặc dùng stale value theo SLA.

**Lưu ý:**
Distributed lock không phải mặc định tốt nhất: lock service cũng có failure mode. Đừng kéo dài TTL tùy tiện nếu dữ liệu có consistency requirement chặt.

### Tip 3 — Vue/React: hủy request cũ khi user thay đổi query

**Mẹo:**
Với autocomplete, filter hoặc route-driven fetch, dùng `AbortController` để hủy request không còn cần thiết thay vì chỉ bỏ qua response sau khi nó quay về.

**Tại sao hữu ích:**
Nếu user gõ nhanh, response của query cũ có thể về sau query mới và ghi đè UI; đồng thời backend vẫn xử lý work vô ích. Cancellation giảm race condition phía client và có thể tiết kiệm downstream work nếu server propagation hỗ trợ.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  });
  return response.json();
}
```

**Lưu ý:**
Client abort không đảm bảo business operation trên server đã rollback. Không dùng cancellation như cơ chế consistency cho command có side effect; server vẫn cần idempotency và transaction semantics đúng.

### Tip 4 — Dùng `git bisect` khi regression có khoảng commit chưa rõ

**Mẹo:**
Khi biết một commit cũ tốt và HEAD đang lỗi, dùng `git bisect` để thu hẹp commit gây regression theo binary search thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Với khoảng 128 commits, binary search chỉ cần khoảng 7 lần phân loại good/bad. Nếu có test hoặc script tái hiện deterministic, `git bisect run` biến điều tra thành quy trình có thể lặp lại.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests
git bisect reset
```

**Lưu ý:**
Bisect chỉ đáng tin khi reproduction deterministic và các commit trung gian build được. Flaky test hoặc thay đổi database/configuration ngoài Git có thể chỉ sai commit.

### Tip 5 — Azure Managed Identity thay secret cho service-to-service authentication

**Mẹo:**
Khi workload trên Azure truy cập Key Vault, Blob Storage hoặc dịch vụ hỗ trợ Microsoft Entra, ưu tiên Managed Identity + RBAC thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời secret khỏi application: không cần copy, rotate hay vô tình log credential. Azure cấp token cho identity của workload, còn authorization được kiểm soát tại resource.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(new Uri(keyVaultUrl), credential);
```
Local development có thể dùng developer credential; production App Service/VM/Function dùng Managed Identity với quyền tối thiểu.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Gán role quá rộng vẫn là security risk; đồng thời cần kiểm tra token acquisition, network access và identity nào thực sự được chọn trong từng environment.

## 🧠 Software Design

### Design 1 — REST hay messaging cho integration boundary

**Khái niệm:**
REST phù hợp khi caller cần response đồng bộ để tiếp tục flow; messaging phù hợp khi producer có thể giao work bất đồng bộ và chấp nhận eventual consistency. Đây là lựa chọn coupling/failure semantics, không chỉ là lựa chọn protocol.

**Vấn đề nó giải quyết:**
Chuỗi synchronous calls làm latency và availability của request phụ thuộc downstream. Ngược lại, queue mọi thứ làm workflow khó quan sát, response không tức thời và tăng complexity cho retry, duplicate, ordering.

**Ví dụ thực tế:**
Checkout cần kiểm tra giá hiện tại trước khi xác nhận có thể gọi Pricing API đồng bộ. Sau khi order đã commit, gửi `OrderConfirmed` qua Azure Service Bus cho email/analytics thường hợp lý hơn bắt request checkout chờ các tác vụ đó.

**Trade-off:**
REST đơn giản, trực quan và consistency tức thời hơn nhưng tạo runtime coupling. Messaging hấp thụ burst và cô lập failure tốt hơn nhưng thêm broker, DLQ, idempotency, tracing và eventual consistency.

**Middle → Senior insight:**
Middle cần implement timeout/retry đúng cho REST và idempotent consumer cho messaging. Senior / Technical phải xác định business operation nào thật sự cần synchronous answer, SLA/failure ownership, backlog behavior và recovery model; không chuyển sang messaging chỉ vì muốn gọi hệ thống là event-driven.

### Design 2 — Normalization vs denormalization theo write invariant và read pressure

**Khái niệm:**
Normalization giảm duplication và giữ source of truth rõ; denormalization cố ý lưu dữ liệu lặp hoặc precomputed để phục vụ read pattern cụ thể. Quyết định phải dựa trên invariant và cost cập nhật, không dựa vào quy tắc “database chuẩn phải 3NF” hoặc “đọc nhanh thì duplicate”.

**Vấn đề nó giải quyết:**
Một schema normalized có thể tạo join/aggregation đắt trên read-heavy dashboard; nhưng denormalized fields lại có nguy cơ stale và yêu cầu cơ chế cập nhật/rebuild.

**Ví dụ thực tế:**
Order giữ snapshot `ProductName` và `UnitPrice` tại thời điểm mua để bảo toàn lịch sử, thay vì join Product hiện tại khi hiển thị invoice. Dashboard doanh thu có thể dùng materialized projection thay vì aggregate hàng triệu order cho mỗi request.

**Trade-off:**
Denormalization giảm read latency nhưng tăng storage, write complexity và consistency work. Normalization đơn giản hóa update invariant nhưng có thể tăng join cost và runtime computation.

**Middle → Senior insight:**
Middle cần phân biệt dữ liệu duplicated vì business history với duplication vô tình. Senior phải xác định source of truth, freshness SLA, rebuild strategy, write amplification và evidence hiệu năng trước khi denormalize.

### Design 3 — Azure Functions vs Worker Service cho background processing

**Khái niệm:**
Azure Functions tối ưu cho event-driven/serverless execution với platform-managed triggers và scaling; Worker Service phù hợp khi cần process sống lâu, kiểm soát host/runtime rõ hơn hoặc workload liên tục.

**Vấn đề nó giải quyết:**
Background work có profile rất khác nhau: burst theo event, job ngắn không đều, consumer chạy liên tục, xử lý dài, dependency nặng hoặc cần kiểm soát concurrency chi tiết. Chọn hosting model sai có thể làm chi phí và vận hành khó hơn.

**Ví dụ thực tế:**
Resize ảnh phát sinh không đều từ Blob upload có thể phù hợp Azure Functions. Một Service Bus consumer có throughput ổn định, xử lý lâu và cần tuning concurrency/resource chặt có thể phù hợp .NET Worker Service chạy trên App Service, Container Apps hoặc Kubernetes.

**Trade-off:**
Functions giảm infrastructure management và scale thuận tiện nhưng có platform/runtime constraints, cold-start/cost characteristics và trigger semantics phải hiểu rõ. Worker Service cho quyền kiểm soát cao hơn nhưng team sở hữu scaling, deployment và health/operational concerns nhiều hơn.

**Middle → Senior insight:**
Middle cần hiểu lifecycle, cancellation, retry và idempotency của hosting model. Senior / Technical phải so workload shape, latency SLA, execution duration, scale pattern, observability, cost và operational maturity của team; serverless không mặc định rẻ hơn hoặc đơn giản hơn cho mọi workload.
