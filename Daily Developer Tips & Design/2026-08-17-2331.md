# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` từ HTTP request xuống các tầng service và database call.

**Tại sao hữu ích:**
Tránh tiếp tục xử lý các request mà client đã huỷ, giảm lãng phí tài nguyên.

**Ví dụ:**
```csharp
public async Task<IActionResult> Get(CancellationToken cancellationToken)
{
    var data = await service.GetAsync(cancellationToken);
    return Ok(data);
}
```

**Lưu ý:**
Không nên swallow `OperationCanceledException` như một lỗi hệ thống.

### Tip 2 — Dùng SQL execution plan thay vì đoán vấn đề performance

**Mẹo:**
Kiểm tra execution plan trước khi tối ưu query SQL.

**Tại sao hữu ích:**
Biết chính xác database đang scan table, thiếu index hay join không hiệu quả.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

**Lưu ý:**
Không tạo index cho mọi column vì có thể làm chậm write operation.

### Tip 3 — Sử dụng structured logging thay vì nối string

**Mẹo:**
Dùng message template trong `ILogger` để log dữ liệu có cấu trúc.

**Tại sao hữu ích:**
Log dễ tìm kiếm trong Application Insights, Seq hoặc Elasticsearch.

**Ví dụ:**
```csharp
logger.LogInformation("Order {OrderId} created by {UserId}", order.Id, user.Id);
```

**Lưu ý:**
Không ghi dữ liệu nhạy cảm như token hoặc password vào log.

### Tip 4 — Tạo commit nhỏ, có mục đích rõ ràng

**Mẹo:**
Mỗi commit nên đại diện cho một thay đổi logic hoàn chỉnh.

**Tại sao hữu ích:**
Dễ review, rollback và tìm nguyên nhân lỗi bằng `git bisect`.

**Ví dụ:**
```bash
git commit -m "Fix duplicate email validation"
```

**Lưu ý:**
Không chia commit quá nhỏ đến mức lịch sử Git khó đọc.

### Tip 5 — Dùng `BenchmarkDotNet` trước khi tối ưu C# code

**Mẹo:**
Đo performance bằng benchmark thay vì dựa trên cảm giác.

**Tại sao hữu ích:**
Giúp xác định code path thực sự chậm và tránh tối ưu sai chỗ.

**Ví dụ:**
```csharp
[Benchmark]
public void ProcessData()
{
    // code to measure
}
```

**Lưu ý:**
Benchmark phải mô phỏng gần với workload thực tế.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Xác định phạm vi dữ liệu và business rule cần thay đổi cùng nhau trong một transaction.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn hoặc dữ liệu thay đổi không nhất quán.

**Ví dụ thực tế:**
Tạo Order và OrderItem cần atomic, nhưng gửi email xác nhận không nên nằm trong cùng transaction database.

**Trade-off:**
Transaction nhỏ giúp scalability tốt hơn nhưng cần cơ chế xử lý failure riêng.

**Middle → Senior insight:**
Middle cần biết transaction hoạt động thế nào. Senior cần quyết định ranh giới transaction dựa trên business consistency.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Chia hệ thống thành các module độc lập trong một deployment unit.

**Vấn đề nó giải quyết:**
Giữ được boundary rõ ràng mà chưa phải trả chi phí vận hành distributed system.

**Ví dụ thực tế:**
Hệ thống HR có module Employee, Payroll, Notification với database access và business rule riêng.

**Trade-off:**
Đơn giản hơn microservices nhưng vẫn cần kỷ luật về dependency giữa module.

**Middle → Senior insight:**
Middle cần biết cách tách module. Senior cần đánh giá khi nào module thực sự cần tách thành service riêng.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Một operation có thể gọi nhiều lần nhưng kết quả cuối cùng vẫn giống nhau.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate request trong hệ thống distributed.

**Ví dụ thực tế:**
Payment API sử dụng `Idempotency-Key` để tránh charge khách hàng hai lần khi retry.

**Trade-off:**
Tăng độ tin cậy nhưng cần lưu trạng thái request và thiết kế storage phù hợp.

**Middle → Senior insight:**
Middle cần biết implement retry-safe API. Senior cần thiết kế idempotency strategy cho toàn bộ workflow.
