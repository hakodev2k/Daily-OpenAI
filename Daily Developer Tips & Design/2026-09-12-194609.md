# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure cho `BackgroundService`

**Mẹo:**
Khi producer tạo work nhanh hơn consumer xử lý, dùng bounded `Channel<T>` thay vì `ConcurrentQueue<T>` không giới hạn để queue có capacity rõ ràng và producer bị chậm lại khi backlog đạt ngưỡng.

**Tại sao hữu ích:**
Queue không giới hạn biến spike traffic thành memory growth. `Channel<T>` cho phép bạn encode backpressure ngay trong process: khi queue đầy, producer có thể chờ, drop theo policy hoặc fail có kiểm soát thay vì tiếp tục allocate vô hạn.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, ct);
```

Consumer trong `BackgroundService` có thể đọc bằng `await foreach` từ `ReadAllAsync(stoppingToken)` và kiểm soát concurrency ở một chỗ.

**Lưu ý:**
In-memory channel không phải durable queue. Nếu process restart, work chưa xử lý sẽ mất. Với business work bắt buộc không được mất, dùng broker/durable storage; `Channel<T>` phù hợp cho coordination nội bộ hoặc buffer ngắn hạn.

### Tip 2 — Với `HttpClient`, dùng `ResponseHeadersRead` khi tải response lớn

**Mẹo:**
Nếu gọi third-party API trả file hoặc payload lớn, dùng `HttpCompletionOption.ResponseHeadersRead` để bắt đầu xử lý stream ngay sau khi nhận headers thay vì chờ buffer toàn bộ body.

**Tại sao hữu ích:**
Mặc định `HttpClient` có thể buffer response content trước khi hoàn tất lời gọi. Với payload lớn, điều này làm tăng memory usage và trì hoãn processing. Streaming giúp giảm peak memory và cải thiện time-to-first-byte ở pipeline proxy/download.

**Ví dụ:**
```csharp
using var response = await httpClient.SendAsync(
    request,
    HttpCompletionOption.ResponseHeadersRead,
    ct);

response.EnsureSuccessStatusCode();
await using var stream = await response.Content.ReadAsStreamAsync(ct);
await stream.CopyToAsync(destination, ct);
```

**Lưu ý:**
Khi streaming, timeout/cancellation của phần đọc body cần được quản lý rõ ràng và response phải được dispose đúng lúc để trả connection về pool. Đừng giữ stream mở lâu hơn cần thiết.

### Tip 3 — Dùng `INCLUDE` trong SQL Server để giảm Key Lookup, nhưng chỉ khi workload chứng minh cần

**Mẹo:**
Nếu execution plan cho thấy một nonclustered index tìm đúng row nhưng phải thực hiện rất nhiều Key Lookup để lấy thêm vài cột, cân nhắc thêm các cột chỉ đọc vào `INCLUDE` thay vì đưa tất cả vào key của index.

**Tại sao hữu ích:**
Covering index có thể giúp query được phục vụ hoàn toàn từ nonclustered index, giảm random lookup về clustered index/heap. Giữ cột không tham gia search/sort ở `INCLUDE` cũng tránh làm key index rộng hơn cần thiết.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Một query lấy `Status` và `Total` theo `CustomerId` + `CreatedAt` có thể tránh nhiều Key Lookup nếu plan và cardinality phù hợp.

**Lưu ý:**
Mỗi cột `INCLUDE` làm index lớn hơn và tăng write amplification. Đừng “cover” mọi query. Xác nhận bằng actual execution plan, logical reads và workload thật trước/sau khi thay đổi.

### Tip 4 — Tối ưu LCP bằng cách ưu tiên resource thực sự nằm trên critical path

**Mẹo:**
Khi Largest Contentful Paint chậm, dùng browser DevTools/Lighthouse để xác định LCP element và network waterfall rồi ưu tiên đúng resource đó thay vì thêm preload hàng loạt.

**Tại sao hữu ích:**
LCP thường chậm do hero image tải muộn, CSS/JS render-blocking hoặc backend response chậm. Nếu preload sai resource, bạn cạnh tranh bandwidth với tài nguyên quan trọng và có thể làm trang chậm hơn.

**Ví dụ:**
```html
<link rel="preload"
      as="image"
      href="/images/hero.avif"
      fetchpriority="high">
```

Nếu hero image thật sự là LCP element và xuất hiện ngay trên initial viewport, preload/fetch priority có thể giúp browser bắt đầu tải sớm hơn.

**Lưu ý:**
Không preload mọi image/font. Kiểm tra cả server TTFB, cache headers, image dimensions/format và JavaScript hydration. LCP là end-to-end metric, không chỉ là bài toán frontend asset.

### Tip 5 — Với migration do AI sinh, luôn kiểm tra SQL thật và đường rollback

**Mẹo:**
Khi AI coding agent tạo EF Core migration hoặc SQL migration, đừng chỉ review file C# migration; hãy generate SQL thực tế và kiểm tra lock behavior, data rewrite, default constraint, index build và khả năng rollback.

**Tại sao hữu ích:**
Migration trông đơn giản trong code có thể thành `ALTER TABLE` đắt đỏ, table scan hoặc operation giữ schema lock lâu trên production. AI thường thiếu context về table size, traffic pattern và deployment topology của hệ thống.

**Ví dụ:**
```bash
dotnet ef migrations script PreviousMigration NewMigration
```

Review các câu `ALTER`, `UPDATE`, `CREATE INDEX`, thời gian dự kiến và backward compatibility trước khi đưa vào release pipeline.

**Lưu ý:**
Rollback database không phải lúc nào cũng an toàn. Nếu migration đã transform/xóa dữ liệu, `Down()` có thể không khôi phục semantics ban đầu. Với breaking schema change, ưu tiên expand-and-contract và backup/recovery plan phù hợp.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic theo delivery topology, không theo tên business event

**Khái niệm:**
Queue phù hợp khi một logical work item cần được xử lý bởi một consumer trong nhóm competing consumers. Topic + subscription phù hợp khi cùng một message cần được phân phối độc lập tới nhiều consumer hoặc policy khác nhau.

**Vấn đề nó giải quyết:**
Nếu dùng một queue cho mọi downstream system, consumer đầu tiên nhận message sẽ lấy mất work của consumer khác. Ngược lại, dùng topic cho command chỉ cần một processor có thể tạo duplication và operational complexity không cần thiết.

**Ví dụ thực tế:**
```text
Queue:
GenerateInvoice
-> nhiều worker cùng cạnh tranh
-> mỗi command chỉ cần một worker xử lý

Topic:
OrderCompleted
-> Billing subscription
-> Analytics subscription
-> Notification subscription
```

Mỗi subscription có thể có retry, dead-letter và filter riêng.

**Trade-off:**
Queue đơn giản, dễ scale competing consumers nhưng không fan-out tự nhiên. Topic hỗ trợ decoupled fan-out tốt nhưng thêm subscription lifecycle, duplicate delivery, schema compatibility và observability cho nhiều consumer độc lập.

**Middle → Senior insight:**
Middle developer cần hiểu delivery semantics, retries và DLQ của queue/subscription. Senior / Technical developer phải chọn topology theo ownership, fan-out requirement, ordering, retry isolation và khả năng consumer phát triển độc lập.

### Design 2 — Clean Architecture vs Layered Architecture: chỉ thêm boundary khi change pressure biện minh

**Khái niệm:**
Layered Architecture thường chia Presentation, Business/Application và Data Access theo technical concern. Clean Architecture đẩy dependency hướng vào domain/application core và cô lập infrastructure qua boundary rõ hơn. Cả hai đều có thể đúng tùy hệ thống.

**Vấn đề nó giải quyết:**
Khi domain phức tạp, nhiều integration thay đổi hoặc cần test business logic độc lập, dependency inversion rõ giúp giảm coupling. Nhưng với CRUD application nhỏ, quá nhiều project/interface/mapper có thể làm tốc độ phát triển giảm mà không tạo giá trị tương ứng.

**Ví dụ thực tế:**
```text
Internal admin CRUD:
Web -> Application -> EF Core
Layered Architecture đơn giản có thể đủ.

Pricing engine tích hợp nhiều provider:
Application core + ports/adapters
Boundary rõ giúp thay provider và test rule độc lập.
```

**Trade-off:**
Clean Architecture tăng testability và isolation nhưng thêm ceremony, mapping và conceptual overhead. Layered Architecture dễ hiểu và nhanh triển khai nhưng có thể bị coupling mạnh nếu layer boundary chỉ tồn tại trên folder name.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và business logic khỏi controller/infrastructure. Senior / Technical developer phải đánh giá domain complexity, team size, rate of change và migration cost để chọn mức kiến trúc tối thiểu đủ dùng thay vì áp template cố định.

### Design 3 — Strangler Fig Pattern cho modernization legacy .NET theo lát cắt business

**Khái niệm:**
Strangler Fig Pattern thay legacy system từng phần bằng cách đưa traffic/capability mới sang implementation mới trong khi phần còn lại vẫn chạy trên hệ thống cũ, thay vì rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Full rewrite kéo dài feedback loop, giữ hai hệ thống không mang giá trị song song và dễ bỏ sót behavior ẩn trong production. Incremental migration giảm blast radius và cho phép kiểm chứng từng capability bằng traffic thật.

**Ví dụ thực tế:**
```text
Legacy .NET Framework monolith

Bước 1: reverse proxy/gateway giữ endpoint cũ
Bước 2: chuyển /api/catalog sang ASP.NET Core mới
Bước 3: đồng bộ data/integration boundary cần thiết
Bước 4: tiếp tục tách capability khác
Bước 5: retire module legacy khi traffic về 0
```

Nên chọn lát cắt có boundary tương đối rõ và đo được success criteria trước.

**Trade-off:**
Migration incremental giảm rủi ro release lớn nhưng tạo giai đoạn coexistence với routing, data synchronization và duplicated operational model. Nếu legacy rất nhỏ, ít thay đổi và replacement đơn giản, rewrite trực tiếp có thể rẻ hơn.

**Middle → Senior insight:**
Middle developer cần giữ compatibility, logging và test khi hai implementation cùng tồn tại. Senior / Technical developer phải xác định migration sequence, data ownership, rollback path, cut-over metric và thời điểm xóa legacy để tránh “temporary architecture” tồn tại vĩnh viễn.
