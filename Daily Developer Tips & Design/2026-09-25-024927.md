# Daily Developer Tips & Design — 2026-09-25

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán ThreadPool starvation thay vì tăng timeout

**Mẹo:**
Khi ASP.NET Core API tăng latency mạnh nhưng CPU chưa đầy, kiểm tra ThreadPool trước khi tăng HTTP/database timeout. Tìm các đoạn sync-over-async như `.Result`, `.Wait()`, blocking I/O và theo dõi runtime counters.

**Tại sao hữu ích:**
ThreadPool starvation làm request chờ worker thread dù dependency vẫn khỏe. Tăng timeout chỉ giữ request lâu hơn và có thể khuếch đại queue. Với production incident, hãy đi theo symptom → counters → stack trace → blocking call thay vì kết luận database chậm.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```
Nếu `thread_pool.queue.length` tăng liên tục trong lúc throughput giảm, kiểm tra call stack và code blocking trước:
```csharp
// Tránh
var result = httpClient.GetAsync(url).Result;

// Ưu tiên async xuyên suốt call chain
var result = await httpClient.GetAsync(url, cancellationToken);
```

**Lưu ý:**
Queue tăng không tự động chứng minh starvation; CPU saturation, lock contention hoặc downstream latency cũng có thể tạo triệu chứng tương tự. Cần đối chiếu traces, CPU và dependency telemetry.

### Tip 2 — Dùng keyset pagination cho tập dữ liệu lớn và thay đổi liên tục

**Mẹo:**
Với SQL Server/PostgreSQL, khi API duyệt sâu qua dữ liệu lớn, cân nhắc keyset pagination thay cho `OFFSET` bằng một sort key ổn định và unique, thường là `CreatedAt + Id`.

**Tại sao hữu ích:**
`OFFSET` buộc database bỏ qua ngày càng nhiều row khi page sâu và dữ liệu insert/delete giữa các request có thể làm item bị lặp hoặc bỏ sót. Keyset biến “page N” thành “đọc tiếp sau cursor”, phù hợp feed, audit log và lịch sử giao dịch.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Status
FROM Orders
WHERE CreatedAt < @CreatedAt
   OR (CreatedAt = @CreatedAt AND Id < @Id)
ORDER BY CreatedAt DESC, Id DESC;
```
Index tương ứng nên bắt đầu bằng các cột phục vụ predicate/order theo query pattern.

**Lưu ý:**
Keyset không phù hợp khi UI bắt buộc nhảy trực tiếp đến page 500. Cursor phải encode đủ sort keys; chỉ dùng `CreatedAt` không unique có thể làm mất record tại boundary.

### Tip 3 — Tách readiness khỏi liveness trong Kubernetes

**Mẹo:**
Đừng dùng cùng một health check cho `livenessProbe` và `readinessProbe`. Readiness trả lời “pod có nên nhận traffic không?”, còn liveness trả lời “process có bị kẹt đến mức cần restart không?”.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp vào SQL hoặc external API, một dependency outage có thể khiến Kubernetes restart toàn bộ pod đang khỏe, tạo restart storm đúng lúc hệ thống cần ổn định nhất.

**Ví dụ:**
ASP.NET Core có thể gắn tag cho dependency checks và map endpoint riêng:
```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new() {
    Predicate = _ => false
});
app.MapHealthChecks("/health/ready", new() {
    Predicate = r => r.Tags.Contains("ready")
});
```

**Lưu ý:**
Liveness quá “nông” cũng có thể bỏ sót process deadlock. Probe design phải phản ánh failure mode thực tế; readiness timeout cần ngắn và không tạo tải lớn lên dependency.

### Tip 4 — Dùng Playwright trace để xử lý E2E flaky có bằng chứng

**Mẹo:**
Với E2E test chỉ fail trên CI, bật Playwright trace cho retry thay vì thêm `WaitForTimeout` ngẫu nhiên.

**Tại sao hữu ích:**
Trace cung cấp DOM snapshot, network, action timeline và screenshot quanh failure. Bạn có thể phân biệt race condition UI, API chậm, selector sai hay test data collision thay vì “chữa” flaky bằng sleep.

**Ví dụ:**
```ts
use: {
  trace: 'on-first-retry'
}
```
Nếu nút chỉ enable sau API response, chờ observable UI state:
```ts
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled();
```

**Lưu ý:**
Trace có chi phí storage và có thể chứa dữ liệu nhạy cảm. Không bật toàn bộ trace vĩnh viễn ở production-like pipeline nếu chưa có retention/redaction phù hợp.

### Tip 5 — Ground AI coding agent bằng source và test, không bằng mô tả chung

**Mẹo:**
Khi giao AI agent sửa repository, cung cấp boundary rõ: file/source-of-truth cần đọc, behavior phải giữ, test phải chạy và tiêu chí acceptance. Yêu cầu agent kiểm chứng API/library version từ source hiện tại trước khi sinh code.

**Tại sao hữu ích:**
Agent dễ tạo API không tồn tại, abstraction không phù hợp hoặc test chỉ xác nhận implementation nó vừa viết. Grounding vào repository và executable tests biến AI từ “code autocomplete lớn” thành workflow có feedback kỹ thuật.

**Ví dụ:**
Thay vì “refactor payment service”, yêu cầu: đọc `PaymentService`, integration tests và contract hiện tại; giữ HTTP contract; thêm test cho duplicate webhook; chạy targeted tests; chỉ sau đó refactor idempotency logic.

**Lưu ý:**
Test xanh không chứng minh thiết kế đúng. Generated test có thể bỏ qua concurrency, security và production constraints; reviewer vẫn phải kiểm tra behavior, diff và architectural impact.

## 🧠 Software Design

### Design 1 — Transactional Outbox cho database + message broker

**Khái niệm:**
Transactional Outbox lưu business change và một outbound message record trong cùng local database transaction. Một publisher riêng đọc outbox rồi gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu service commit `Order=Paid` rồi crash trước khi publish `OrderPaid`, database và message broker bị lệch trạng thái. Distributed transaction thường không khả dụng hoặc không đáng chi phí giữa các thành phần cloud.

**Ví dụ thực tế:**
Checkout API cập nhật `Orders` và insert `OutboxMessages` trong một EF Core transaction. Worker publish outbox sang Azure Service Bus, đánh dấu message đã xử lý; consumer vẫn idempotent vì broker/publisher có thể tạo duplicate delivery.

**Trade-off:**
Lợi ích là tránh “commit DB nhưng mất event” mà không cần 2PC. Chi phí là eventual consistency, outbox growth, polling/publishing latency, duplicate handling và thêm observability/cleanup vận hành.

**Middle → Senior insight:**
Middle cần giữ business update + outbox insert trong cùng transaction và hiểu consumer idempotency. Senior cần quyết định liệu failure window thực sự cần Outbox, chọn polling/CDC, retention, ordering boundary và cân nhắc complexity so với một transaction-local workflow đơn giản.

### Design 2 — Modular Monolith trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployable unit nhưng ép boundary rõ giữa các module nghiệp vụ: ownership của data, public contracts và dependency direction.

**Vấn đề nó giải quyết:**
Một monolith không có boundary dễ thành tightly coupled “big ball of mud”, trong khi tách Microservices quá sớm chuyển coupling trong code thành network calls, distributed failures và operational overhead.

**Ví dụ thực tế:**
Hệ thống CMS/e-commerce có `Catalog`, `Orders`, `Identity` là module riêng. `Orders` không query trực tiếp bảng private của `Catalog`; integration đi qua module contract/event. Chỉ tách `Catalog` thành service khi scale, ownership hoặc deployment independence thực sự yêu cầu.

**Trade-off:**
Modular Monolith giữ transaction/deployment/debugging đơn giản hơn nhưng boundary phải được enforce bằng code/tests. Microservices tăng independent deployment/scaling nhưng kéo theo messaging, tracing, versioning, resilience và data-consistency complexity.

**Middle → Senior insight:**
Middle cần tránh dependency xuyên module và giữ contract rõ. Senior phải dùng team topology, change coupling, scaling profile, reliability và deployment pressure để quyết định thời điểm tách; “nhiều service hơn” không phải thước đo kiến trúc trưởng thành.

### Design 3 — Cache-aside với consistency boundary rõ ràng

**Khái niệm:**
Cache-aside để application đọc cache trước, cache miss thì đọc source-of-truth rồi populate cache. Thiết kế quan trọng không phải lệnh `GET/SET`, mà là xác định dữ liệu nào chấp nhận stale và invalidation xảy ra ở đâu.

**Vấn đề nó giải quyết:**
Redis có thể giảm database latency/load cho read-heavy workload, nhưng cache tạo thêm một bản sao dữ liệu. Nếu consistency requirement không rõ, “tối ưu” này dễ sinh bug khó tái hiện hơn vấn đề performance ban đầu.

**Ví dụ thực tế:**
Product catalog cache theo `product:{id}` với TTL ngắn. Khi back-office cập nhật giá, transaction DB hoàn tất trước rồi invalidation cache; request sau repopulate từ database. Với dữ liệu cần correctness tuyệt đối tại checkout, service đọc lại authoritative price thay vì tin cache catalog.

**Trade-off:**
Lợi ích là giảm latency và database load. Chi phí gồm stale data, stampede, hot keys, Redis outage behavior, invalidation complexity và thêm telemetry. Cache không nên được thêm trước khi measurement chứng minh bottleneck.

**Middle → Senior insight:**
Middle cần triển khai TTL, cache miss và invalidation đúng, đồng thời chịu được cache failure. Senior cần xác định consistency SLA, source-of-truth, stampede strategy, key/version scheme và quyết định dữ liệu nào không nên cache dù technically có thể.
