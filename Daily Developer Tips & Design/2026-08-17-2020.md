# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Array.BinarySearch()` khi lookup lặp lại trên dữ liệu đã sort

**Mẹo:**
Nếu một collection nhỏ hoặc vừa được load một lần, giữ immutable và đã sort, `Array.BinarySearch()` có thể là lựa chọn đơn giản cho lookup nhiều lần mà không cần thêm `Dictionary`/`HashSet`.

**Tại sao hữu ích:**
Không cần hash structure riêng, memory footprint thấp và behavior predictable khi dữ liệu đã có thứ tự tự nhiên.

**Ví dụ:**
```csharp
var codes = new[] { 10, 20, 30, 40, 50 };

var index = Array.BinarySearch(codes, 30);
if (index >= 0)
{
    Console.WriteLine($"Found at {index}");
}
```

**Lưu ý:**
Chỉ dùng khi dữ liệu thực sự được sort theo đúng comparer. Nếu collection thay đổi thường xuyên hoặc lookup là dominant workload, `HashSet<T>` thường phù hợp hơn.

### Tip 2 — Dùng EF Core interceptor để quan sát query chậm thay vì rải timing code khắp repository

**Mẹo:**
Nếu muốn theo dõi query chậm hoặc enrich telemetry thống nhất, cân nhắc `DbCommandInterceptor` thay vì tự `Stopwatch` ở từng repository method.

**Tại sao hữu ích:**
Tạo một observability boundary tập trung cho SQL command duration, failure, command text metadata hoặc correlation mà không pollute business code.

**Ví dụ:**
```csharp
public sealed class SlowQueryInterceptor : DbCommandInterceptor
{
    public override async ValueTask<InterceptionResult<DbDataReader>> ReaderExecutingAsync(
        DbCommand command,
        CommandEventData eventData,
        InterceptionResult<DbDataReader> result,
        CancellationToken cancellationToken = default)
    {
        // Attach timing/correlation here if needed.
        return await base.ReaderExecutingAsync(
            command,
            eventData,
            result,
            cancellationToken);
    }
}
```

**Lưu ý:**
Không log full SQL parameters một cách mù quáng vì có thể chứa PII/secret. Interceptor cũng không nên trở thành nơi nhét business logic.

### Tip 3 — Dùng `git blame -L` để điều tra đúng vài dòng thay vì blame cả file

**Mẹo:**
Khi chỉ cần biết lịch sử của một đoạn code nhỏ, giới hạn `git blame` theo line range hoặc function thay vì đọc toàn bộ file.

**Tại sao hữu ích:**
Nhanh hơn khi điều tra “ai/commit nào đưa đoạn logic này vào” và giảm noise từ những phần file không liên quan.

**Ví dụ:**
```bash
git blame -L 120,160 src/Orders/OrderService.cs
```

Hoặc theo function:

```bash
git blame -L :ApproveOrder src/Orders/OrderService.cs
```

**Lưu ý:**
`blame` chỉ cho commit cuối cùng chạm vào dòng hiện tại. Với refactor/move lớn, cần kết hợp `git log -L`, `-S` hoặc `-G` để theo lịch sử sâu hơn.

### Tip 4 — Dùng `ulimit -n` và `/proc/<pid>/fd` khi nghi file descriptor exhaustion

**Mẹo:**
Nếu Linux service xuất hiện lỗi `Too many open files`, kiểm tra soft limit và số file descriptor process đang giữ trước khi chỉ tăng limit.

**Tại sao hữu ích:**
Giúp phân biệt limit cấu hình quá thấp với leak socket/file thật sự trong application.

**Ví dụ:**
```bash
ulimit -n
```

Đếm descriptor của process:

```bash
ls /proc/<PID>/fd | wc -l
```

Xem loại descriptor:

```bash
ls -l /proc/<PID>/fd | head
```

**Lưu ý:**
Tăng `nofile` chỉ che triệu chứng nếu application leak connection/file handle. Luôn correlate với socket count, connection pool và lifecycle của resource.

### Tip 5 — Dùng `dotnet format --verify-no-changes` để CI bắt formatting drift

**Mẹo:**
Nếu team đã thống nhất `.editorconfig`, cho CI chạy `dotnet format --verify-no-changes` để phát hiện code chưa tuân format/analyzer fix trước khi merge.

**Tại sao hữu ích:**
Giảm review noise về whitespace/style và bảo đảm code từ IDE khác nhau hoặc AI-generated patch vẫn tuân cùng rule.

**Ví dụ:**
```bash
dotnet format --verify-no-changes --no-restore
```

Có thể chạy sau bước `dotnet restore` trong CI.

**Lưu ý:**
Formatting check nên có signal rõ và ổn định. Đừng bật hàng loạt analyzer auto-fix gây churn lớn trên legacy repository trong một lần.

## 🧠 Software Design

### Design 1 — Ownership boundary nên đi theo nơi invariant được quyết định

**Khái niệm:**
Một module/service nên sở hữu state mà nó chịu trách nhiệm quyết định các invariant chính, thay vì chia ownership chỉ theo bảng hoặc theo UI screen.

**Vấn đề nó giải quyết:**
Nếu nhiều module cùng được phép mutate một entity quan trọng, rule dễ bị duplicate, bypass hoặc trở nên phụ thuộc thứ tự call giữa các module.

**Ví dụ thực tế:**
`Timesheet` quyết định một entry có được submit/approve hay không. `Billing` có thể đọc dữ liệu timesheet để tính invoice nhưng không trực tiếp update trạng thái approval; mọi mutation phải quay về owner của invariant.

**Trade-off:**
Ownership rõ giúp giảm coupling và bảo vệ business rule, nhưng đôi khi tạo thêm API/event giữa các module và tăng latency so với shared-table update trực tiếp.

**Middle → Senior insight:**
Middle developer nên hỏi “ai có quyền thay đổi state này?”. Senior developer phải gắn ownership với invariant, transaction boundary và evolution path, không chỉ với sơ đồ database hiện tại.

### Design 2 — Đừng dùng distributed cache làm source of truth

**Khái niệm:**
Cache nên phục vụ performance và có thể bị mất/rebuild. Nếu correctness phụ thuộc vào dữ liệu chỉ tồn tại trong cache, cache đã bị biến thành primary store trá hình.

**Vấn đề nó giải quyết:**
Redis restart, eviction, failover hoặc TTL có thể làm mất state. Nếu state đó là payment status, approval state hoặc inventory reservation duy nhất, business correctness sẽ bị phá vỡ.

**Ví dụ thực tế:**
`EmployeeProfile` lưu trong database, Redis chỉ cache read. Khi key mất, application reload từ database. Ngược lại, idempotency record quan trọng cần durability thì không nên chỉ tồn tại trong cache nếu mất key có thể gây xử lý duplicate nguy hiểm.

**Trade-off:**
Cache-as-optimization giúp hệ thống recover dễ hơn nhưng có thể tăng load vào source of truth khi cache miss hàng loạt. Dùng cache như primary store có latency tốt nhưng yêu cầu durability, replication, backup và consistency semantics nghiêm túc như database thật.

**Middle → Senior insight:**
Middle developer nên phân biệt “temporary acceleration” với “durable state”. Senior developer phải xác định data classification, recovery path, eviction behavior và điều gì xảy ra khi toàn bộ cache biến mất trong 30 giây.

### Design 3 — API Gateway không nên trở thành business orchestrator mặc định

**Khái niệm:**
API Gateway phù hợp cho routing, auth edge, rate limiting, protocol translation và một số cross-cutting concern. Nếu gateway bắt đầu chứa nhiều business branching, nó dần trở thành một application layer trung tâm khó evolve.

**Vấn đề nó giải quyết:**
Gateway tiện vì nằm trước mọi service nên team dễ nhét aggregation, validation, fallback và workflow logic vào đó. Theo thời gian mọi thay đổi business đều phải chạm gateway, tạo coupling và release bottleneck.

**Ví dụ thực tế:**
Gateway có thể xác thực JWT, route `/orders/*` tới Order API và enforce rate limit. Nhưng logic kiểu “nếu order VIP thì gọi Pricing A, nếu region EU thì gọi Compliance B, nếu thất bại thì compensate C” nên thuộc orchestration/application service rõ ownership hơn.

**Trade-off:**
Gateway mỏng giúp edge behavior thống nhất và dễ vận hành, nhưng client có thể cần thêm BFF hoặc orchestration service cho composition phức tạp. Gateway giàu business logic giảm số service lúc đầu nhưng tăng central coupling và blast radius.

**Middle → Senior insight:**
Middle developer nên giữ gateway tập trung vào cross-cutting concern. Senior developer cần nhận biết khi aggregation/orchestration đã vượt edge responsibility và nên chuyển sang BFF, application service hoặc workflow owner phù hợp.
