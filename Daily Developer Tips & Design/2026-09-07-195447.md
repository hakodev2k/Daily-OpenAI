# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho read-mostly lookup sau giai đoạn khởi tạo

**Mẹo:**
Với dữ liệu được build một lần rồi đọc rất nhiều lần trong suốt lifetime của process, cân nhắc `FrozenDictionary<TKey,TValue>` hoặc `FrozenSet<T>` thay vì giữ `Dictionary` mutable mãi mãi.

**Tại sao hữu ích:**
`FrozenDictionary` tối ưu layout nội bộ cho lookup sau khi collection đã “đóng băng”. Nó phù hợp với routing metadata, mapping code → handler, feature metadata hoặc configuration lookup ít thay đổi. Quan trọng hơn, immutable-after-build giúp giảm nguy cơ mutation ngoài ý muốn trong concurrent code.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

var handlers = registrations
    .ToFrozenDictionary(x => x.Code, x => x.Handler);

if (handlers.TryGetValue(command.Code, out var handler))
{
    await handler.HandleAsync(command, cancellationToken);
}
```

**Lưu ý:**
Không dùng frozen collections cho dữ liệu thường xuyên thay đổi. Chi phí build collection và việc phải tạo lại toàn bộ cấu trúc khiến nó không phù hợp với cache mutable hoặc state cập nhật liên tục.

### Tip 2 — Rate limit theo đúng resource contention, không chỉ theo IP

**Mẹo:**
Trong ASP.NET Core, khi endpoint có resource expensive như export report, search nặng hoặc gửi OTP, cân nhắc partition rate limiting theo user, tenant hoặc API key thay vì chỉ theo client IP.

**Tại sao hữu ích:**
IP không luôn đại diện cho một consumer: nhiều user có thể đi qua NAT/proxy, còn một attacker có thể phân tán qua nhiều IP. Partition key nên phản ánh resource ownership hoặc abuse boundary mà hệ thống thực sự cần bảo vệ.

**Ví dụ:**
```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", httpContext =>
        RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: httpContext.User.Identity?.Name ?? "anonymous",
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 20,
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0
            }));
});
```

Một endpoint export có thể giới hạn theo authenticated user hoặc tenant thay vì toàn bộ traffic chung.

**Lưu ý:**
Rate limiting không thay authorization, quota billing hoặc backpressure nội bộ. Ngoài ra, partition key có cardinality cực cao cũng làm tăng state quản lý; cần chọn key có lifecycle hợp lý.

### Tip 3 — Với MongoDB compound index, thiết kế theo Equality → Sort → Range

**Mẹo:**
Khi tạo compound index cho query phổ biến, sắp xếp field dựa trên query pattern: các predicate equality trước, tiếp theo là field sort, cuối cùng mới tới range nếu phù hợp.

**Tại sao hữu ích:**
MongoDB chỉ tận dụng compound index hiệu quả theo prefix. Nếu field range đứng quá sớm, khả năng sử dụng các field phía sau để sort hoặc narrow scan có thể giảm. Thiết kế index theo query shape thường quan trọng hơn việc “index mọi field được filter”.

**Ví dụ:**
Query:
```javascript
db.orders.find({
  tenantId: "t1",
  status: "Pending",
  createdAt: { $gte: ISODate("2026-09-01") }
}).sort({ priority: -1 })
```

Có thể cân nhắc index theo workload thực tế như:
```javascript
{ tenantId: 1, status: 1, priority: -1, createdAt: 1 }
```

sau đó xác nhận bằng `explain("executionStats")` thay vì đoán.

**Lưu ý:**
ESR là heuristic, không phải luật tuyệt đối. Cardinality, selectivity, sort direction, covered query và data distribution có thể làm index khác tốt hơn. Luôn kiểm tra execution stats và write overhead.

### Tip 4 — Dùng `git bisect` khi regression xuất hiện giữa hai commit đã biết

**Mẹo:**
Nếu biết một commit “good” và một commit “bad”, dùng `git bisect` để tìm commit gây regression bằng binary search thay vì checkout từng commit thủ công.

**Tại sao hữu ích:**
Với khoảng 128 commit, binary search thường chỉ cần khoảng 7 lần kiểm tra. Đây là cách đặc biệt hữu ích cho performance regression, build failure hoặc bug chỉ xuất hiện sau một thay đổi cụ thể.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
```

Sau mỗi lần test:
```bash
git bisect good
# hoặc
git bisect bad
```

Có thể tự động hóa nếu có script/test deterministic:
```bash
git bisect run dotnet test tests/Regression.Tests
```

**Lưu ý:**
`git bisect` cho kết quả kém nếu test flaky hoặc commit trung gian không build được. Khi đó cần dùng `git bisect skip` có chọn lọc và bảo đảm tiêu chí good/bad rõ ràng.

### Tip 5 — Khi dùng AI coding agent, buộc nó kiểm chứng assumption bằng repository source

**Mẹo:**
Khi yêu cầu AI sửa bug hoặc thêm feature trong repository lớn, yêu cầu agent đọc implementation, tests, version package và usage hiện tại trước khi đề xuất code; đừng chỉ mô tả framework rồi để nó suy đoán API.

**Tại sao hữu ích:**
AI dễ tạo code hợp lý về mặt khái niệm nhưng sai phiên bản thư viện, sai abstraction có sẵn hoặc bỏ qua convention nội bộ. Grounding vào source giảm hallucinated API và giảm nguy cơ tạo abstraction trùng với codebase.

**Ví dụ:**
Một task tốt cho agent có thể yêu cầu:
```text
1. Locate the current authentication flow.
2. Inspect package versions and existing tests.
3. Identify the smallest change boundary.
4. Implement the fix.
5. Run relevant tests and report remaining uncertainty.
```

**Lưu ý:**
Không coi “agent đã chạy test” là đủ nếu test hiện tại không cover behavior mới. Review diff, dependency changes, security implications và failure path vẫn là trách nhiệm engineering.

## 🧠 Software Design

### Design 1 — Outbox Pattern để đồng bộ database commit và message publishing

**Khái niệm:**
Outbox Pattern ghi business state và message/event cần publish vào cùng local database transaction. Một background publisher đọc outbox sau commit rồi gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application cập nhật database rồi publish Azure Service Bus message như hai operation độc lập, có hai failure window: database commit nhưng publish thất bại, hoặc message publish thành công nhưng database rollback. Cả hai đều gây inconsistency khó sửa.

**Ví dụ thực tế:**
Order service xử lý checkout:
1. Update `Orders` thành `Confirmed`.
2. Insert `OrderConfirmed` vào bảng `OutboxMessages` trong cùng transaction.
3. Commit.
4. Background worker publish message ra Service Bus.
5. Sau khi broker acknowledge, đánh dấu outbox đã gửi.

Consumer vẫn phải idempotent vì publisher có thể retry và gửi duplicate.

**Trade-off:**
Outbox loại bỏ dual-write inconsistency giữa database và broker, nhưng thêm bảng outbox, cleanup, polling/CDC, monitoring và duplicate delivery. Nó cũng không tự giải quyết ordering toàn cục hoặc exactly-once end-to-end.

**Middle → Senior insight:**
Middle developer cần đảm bảo outbox insert nằm đúng transaction, publisher retry an toàn và consumer idempotent. Senior / Technical developer phải chọn polling hay CDC, định nghĩa ordering scope, retention, throughput, failure recovery và xác định nơi nào thực sự cần reliable messaging thay vì thêm Outbox cho mọi CRUD operation.

### Design 2 — Feature Flag vs long-lived feature branch

**Khái niệm:**
Feature Flag cho phép merge code vào mainline nhưng tách thời điểm deploy khỏi thời điểm release. Long-lived feature branch giữ thay đổi ngoài main cho tới khi feature hoàn chỉnh.

**Vấn đề nó giải quyết:**
Feature lớn kéo dài nhiều tuần tạo merge conflict và integration risk nếu team giữ branch quá lâu. Feature flag cho phép integrate sớm, chạy CI liên tục và rollout theo nhóm user mà chưa expose capability cho toàn bộ production.

**Ví dụ thực tế:**
Một checkout flow mới được merge theo từng increment nhưng guarded bởi:
```text
CheckoutV2 = false
```

Production deploy code mới nhưng chỉ internal tester hoặc 5% tenant được bật flag trước khi rollout rộng.

**Trade-off:**
Feature flag giảm integration risk và hỗ trợ gradual rollout/rollback nhanh, nhưng tạo code path song song, test matrix lớn hơn và “flag debt” nếu không xóa flag cũ. Feature branch đơn giản hơn cho thay đổi nhỏ, cô lập rõ, nhưng branch dài làm drift với main tăng nhanh.

**Middle → Senior insight:**
Middle developer cần giữ cả flag-on và flag-off path hoạt động, test đúng behavior và tránh rải condition khắp codebase. Senior / Technical developer phải chọn release strategy theo risk, đặt owner/expiry cho flag, phân biệt release flag với operational kill switch và thiết kế migration để flag có thể xóa sạch sau rollout.

### Design 3 — Hexagonal Architecture chỉ hữu ích khi boundary thay đổi hoặc testability thực sự cần thiết

**Khái niệm:**
Hexagonal Architecture đặt domain/application logic phía trong, giao tiếp với database, HTTP, message broker hoặc external services qua ports và adapters. Mục tiêu là cô lập business logic khỏi infrastructure detail, không phải tạo thêm layer vì sơ đồ kiến trúc đẹp.

**Vấn đề nó giải quyết:**
Khi business logic phức tạp nhưng infrastructure thay đổi độc lập — ví dụ payment provider, persistence hoặc transport — coupling trực tiếp làm test khó và migration tốn kém. Port cho phép application diễn đạt dependency theo capability thay vì vendor API.

**Ví dụ thực tế:**
Application cần:
```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}
```

Adapter production dùng Stripe-like provider; integration test có fake/test adapter. Domain không cần biết HTTP SDK cụ thể.

**Trade-off:**
Boundary rõ giúp testability, thay adapter và giảm infrastructure coupling. Nhưng mỗi port, DTO mapping và adapter thêm code, cognitive load và maintenance. Với CRUD service rất mỏng, abstraction này có thể chỉ che EF Core/HTTP API mà không tạo giá trị thực tế.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction đúng và tránh để infrastructure type rò vào application layer. Senior / Technical developer phải xác định seam nào đáng abstraction dựa trên volatility, business complexity và test need; nếu provider gần như không đổi và logic đơn giản, direct integration có thể là lựa chọn tốt hơn.
