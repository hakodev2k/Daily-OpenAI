# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Partition rate limiting theo đúng resource cần bảo vệ

**Mẹo:**
Với ASP.NET Core Rate Limiting, đừng mặc định partition theo IP cho mọi endpoint. Chọn partition key theo resource và trust boundary: authenticated user, tenant, API key hoặc endpoint class.

**Tại sao hữu ích:**
Rate limit theo IP có thể phạt nhiều user hợp lệ cùng đi qua NAT/proxy, trong khi attacker phân tán IP lại né được quota. Partition đúng giúp giới hạn consumption gần với identity thực sự tạo tải và bảo vệ downstream dependency tốt hơn.

**Ví dụ:**
```csharp
options.AddPolicy("per-user", context =>
    RateLimitPartition.GetFixedWindowLimiter(
        context.User.Identity?.Name ?? context.Connection.RemoteIpAddress?.ToString() ?? "anonymous",
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1)
        }));
```
Một search API đắt tiền có thể cần quota riêng thấp hơn health endpoint hoặc static-content endpoint.

**Lưu ý:**
Không tin trực tiếp `X-Forwarded-For` nếu proxy chain chưa được cấu hình trusted. Rate limiting cũng không thay thế authorization, WAF hoặc capacity protection ở tầng infrastructure.

### Tip 2 — PostgreSQL partial index chỉ index phần dữ liệu query thực sự quan tâm

**Mẹo:**
Nếu workload thường xuyên query một subset nhỏ, ổn định của bảng, cân nhắc partial index thay vì index toàn bộ rows.

**Tại sao hữu ích:**
Index nhỏ hơn giảm storage, cache pressure và write amplification. Với bảng jobs có hàng chục triệu records nhưng worker chủ yếu tìm vài nghìn jobs `Pending`, index toàn bảng theo status/time có thể tốn nhiều hơn mức cần thiết.

**Ví dụ:**
```sql
CREATE INDEX ix_jobs_pending_created_at
ON jobs (created_at)
WHERE status = 'Pending';

SELECT id, created_at
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```
Dùng `EXPLAIN (ANALYZE, BUFFERS)` để xác nhận planner thực sự dùng index và workload được cải thiện.

**Lưu ý:**
Predicate của query phải phù hợp để planner chứng minh được điều kiện của partial index. Nếu business status distribution thay đổi mạnh hoặc nhiều query cần các status khác nhau, lợi ích có thể giảm.

### Tip 3 — Azure Managed Identity loại bỏ secret khỏi application configuration

**Mẹo:**
Khi workload chạy trên Azure và service đích hỗ trợ Microsoft Entra authentication, ưu tiên Managed Identity thay vì lưu client secret trong app settings rồi tự rotate.

**Tại sao hữu ích:**
Managed Identity chuyển credential lifecycle sang Azure và cho application lấy token qua identity platform. Điều này giảm nguy cơ secret bị commit, leak qua configuration dump hoặc hết hạn bất ngờ trong production.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

var secret = await client.GetSecretAsync("PaymentEndpointKey", cancellationToken: ct);
```
Ở production, gán RBAC tối thiểu cho identity của App Service/Function; local development có thể dùng developer credential được `DefaultAzureCredential` hỗ trợ.

**Lưu ý:**
Managed Identity không tự cấp quyền. Identity có token nhưng thiếu RBAC vẫn bị từ chối; cấp role quá rộng lại phá least privilege. Cũng cần phân biệt system-assigned và user-assigned identity theo lifecycle/ownership.

### Tip 4 — Playwright locator nên mô tả hành vi người dùng, không bám DOM implementation

**Mẹo:**
Ưu tiên `GetByRole`, `GetByLabel`, `GetByText` hoặc explicit test id khi cần; tránh selector dài dựa trên class/layout nội bộ.

**Tại sao hữu ích:**
Test E2E thất bại vì CSS refactor không mang giá trị regression. Locator dựa trên accessible role/name thường bền hơn và đồng thời buộc UI có semantics gần với cách user và assistive technology tương tác.

**Ví dụ:**
```csharp
await page.GetByLabel("Email").FillAsync("qa@example.com");
await page.GetByRole(AriaRole.Button, new() { Name = "Sign in" }).ClickAsync();
await Expect(page.GetByRole(AriaRole.Heading, new() { Name = "Dashboard" }))
    .ToBeVisibleAsync();
```

**Lưu ý:**
Đừng biến mọi element thành `data-testid`. Test id hữu ích khi không có user-facing semantic ổn định, nhưng lạm dụng chúng khiến test ít phản ánh trải nghiệm thực tế.

### Tip 5 — Frontend search phải chống stale response, không chỉ debounce

**Mẹo:**
Với Vue.js/React live search, debounce giảm số request nhưng vẫn cần cancellation hoặc sequence guard để response cũ không ghi đè response mới.

**Tại sao hữu ích:**
Request `abc` có thể hoàn thành trước request `ab` dù được gửi sau. Nếu component cập nhật state theo thứ tự response đến, UI có thể hiển thị kết quả không tương ứng với input hiện tại.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  });

  return response.json();
}
```
Backend cũng nên nhận cancellation khi client disconnect nếu operation đắt và framework/dependency hỗ trợ.

**Lưu ý:**
`AbortController` không đảm bảo server đã rollback mọi side effect. Cancellation phù hợp cho read/search; command có side effect cần idempotency và transaction semantics riêng.

## 🧠 Software Design

### Design 1 — Expand-and-Contract cho thay đổi API/database không downtime

**Khái niệm:**
Expand-and-Contract chia breaking change thành các bước tương thích ngược: thêm representation/schema mới trước, migrate consumers/data, rồi mới loại bỏ phần cũ sau khi không còn dependency.

**Vấn đề nó giải quyết:**
Rolling deployment khiến version cũ và mới chạy đồng thời. Nếu release mới rename hoặc xóa column/API field ngay lập tức, instance cũ có thể hỏng trong chính deployment được xem là “thành công”.

**Ví dụ thực tế:**
Cần đổi `Customer.FullName` thành `FirstName` + `LastName`. Release đầu thêm fields/columns mới nhưng vẫn duy trì `FullName`; write path hỗ trợ transition và backfill dữ liệu. Sau khi mọi consumer chuyển sang contract mới và telemetry xác nhận field cũ không còn được dùng, release sau mới remove nó.

**Trade-off:**
Giảm deployment coupling và rollback risk nhưng tạm thời tồn tại duplicate schema/code path, migration logic và cleanup work. Transition kéo dài quá lâu sẽ biến compatibility layer thành technical debt.

**Middle → Senior insight:**
Middle developer cần tránh migration phá version đang chạy và test backward compatibility. Senior / Technical developer phải thiết kế sequence deploy/migrate/cleanup, xác định source of truth trong transition, quan sát consumer adoption và đảm bảo rollback vẫn khả thi ở từng bước.

### Design 2 — Azure Functions vs Worker Service: chọn theo execution model

**Khái niệm:**
Azure Functions tối ưu cho event-triggered/serverless execution với platform-managed scaling; .NET Worker Service phù hợp hơn khi process cần lifecycle, concurrency, resource control hoặc workload dài hạn do application sở hữu rõ ràng.

**Vấn đề nó giải quyết:**
Một team có thể dùng Function cho mọi background task vì deployment nhanh, rồi gặp cold start, execution/runtime constraints hoặc khó kiểm soát long-running processing. Ngược lại, vận hành worker riêng cho vài event hiếm có thể tạo infrastructure overhead không cần thiết.

**Ví dụ thực tế:**
Thumbnail generation ngắn, độc lập, trigger từ Blob có thể hợp với Function. Một ingestion engine giữ nhiều bounded pipelines, điều chỉnh concurrency theo downstream pressure và cần predictable process lifecycle có thể phù hợp Worker Service chạy trên App Service, Container Apps hoặc Kubernetes hơn.

**Trade-off:**
Functions giảm operational setup và scale theo event nhưng tăng phụ thuộc hosting/runtime model và có cost/behavior cần hiểu theo hosting plan. Worker cho quyền kiểm soát cao hơn nhưng team chịu trách nhiệm nhiều hơn về hosting, scaling, health và deployment.

**Middle → Senior insight:**
Middle developer cần implement cancellation, retries và idempotency đúng ở cả hai model. Senior / Technical developer phải đánh giá workload duration, burstiness, scaling signal, state, concurrency control, cost, observability và failure recovery thay vì chọn theo công nghệ quen thuộc.

### Design 3 — Observability cardinality là một quyết định kiến trúc

**Khái niệm:**
Metric labels/dimensions tạo time series riêng cho từng tổ hợp giá trị. Cardinality vì vậy phải được thiết kế: dimension như HTTP method/status thường bounded; `UserId`, `OrderId` hoặc raw URL có thể tạo hàng triệu series.

**Vấn đề nó giải quyết:**
Một hệ thống thêm `customer_id` vào mọi metric để “debug dễ hơn”, rồi telemetry backend tăng memory/storage/cost và query chậm. Dữ liệu chi tiết đúng chỗ nhưng representation sai loại.

**Ví dụ thực tế:**
Metric latency dùng dimensions bounded như `service`, `route`, `status_code`. Khi cần điều tra một order cụ thể, `OrderId` nằm trong structured log hoặc trace span có sampling/retention phù hợp thay vì metric label.

**Trade-off:**
Low-cardinality metrics aggregate nhanh, rẻ và tốt cho alert/SLO nhưng không giữ identity từng request. Logs/traces cho detail tốt hơn nhưng có volume, sampling và query cost riêng. Không có một telemetry signal tối ưu cho mọi câu hỏi.

**Middle → Senior insight:**
Middle developer cần tránh dynamic identifiers trong metric dimensions và giữ route template thay vì raw URL. Senior / Technical developer phải thiết kế telemetry theo câu hỏi vận hành: metric cho detection, trace cho causal path, log cho contextual detail; đồng thời đặt budget về cardinality, retention và cost.
