# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` xuyên suốt từ HTTP request xuống database hoặc background operation.

**Tại sao hữu ích:**
Giúp hủy các tác vụ không còn cần thiết khi client disconnect hoặc request timeout.

**Ví dụ:**
```csharp
public async Task<List<Order>> GetOrdersAsync(CancellationToken cancellationToken)
{
    return await db.Orders.ToListAsync(cancellationToken);
}
```

**Lưu ý:**
Không bỏ qua cancellation trong các tác vụ dài vì có thể gây lãng phí resource.

### Tip 2 — Sử dụng `ExecuteUpdateAsync` thay vì load entity để update hàng loạt

**Mẹo:**
Dùng bulk update của EF Core khi chỉ cần cập nhật dữ liệu mà không cần tracking entity.

**Tại sao hữu ích:**
Giảm memory usage và số lần round-trip tới database.

**Ví dụ:**
```csharp
await db.Users
    .Where(x => x.IsInactive)
    .ExecuteUpdateAsync(x => x
        .SetProperty(u => u.Status, "Disabled"));
```

**Lưu ý:**
Không dùng nếu cần chạy domain logic trên từng entity.

### Tip 3 — Dùng structured logging thay vì nối chuỗi log

**Mẹo:**
Truyền dữ liệu qua message template thay vì string interpolation.

**Tại sao hữu ích:**
Log có cấu trúc dễ tìm kiếm trong Application Insights, Seq hoặc ELK.

**Ví dụ:**
```csharp
_logger.LogInformation("Order {OrderId} created by {UserId}", orderId, userId);
```

**Lưu ý:**
Không log dữ liệu nhạy cảm như token hoặc password.

### Tip 4 — Dùng `docker compose` cho môi trường local phức tạp

**Mẹo:**
Định nghĩa database, cache, message broker bằng `docker-compose.yml` thay vì setup thủ công.

**Tại sao hữu ích:**
Giúp team có môi trường development nhất quán.

**Ví dụ:**
```bash
docker compose up -d
```

**Lưu ý:**
Không nên đưa secret thật vào file compose commit lên repository.

### Tip 5 — Dùng `BenchmarkDotNet` trước khi tối ưu code

**Mẹo:**
Đo lường performance bằng benchmark thay vì dự đoán.

**Tại sao hữu ích:**
Tránh tối ưu sai chỗ và có số liệu trước/sau khi thay đổi.

**Ví dụ:**
```csharp
[Benchmark]
public void ParseData()
{
    Parser.Parse(input);
}
```

**Lưu ý:**
Benchmark cần gần với workload thực tế.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Transaction Boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một business operation.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn gây lock lâu hoặc transaction quá nhỏ làm dữ liệu không nhất quán.

**Ví dụ thực tế:**
Trong hệ thống đặt hàng, tạo Order và OrderItem có thể nằm trong cùng transaction, nhưng gửi email xác nhận nên xử lý riêng.

**Trade-off:**
Boundary tốt giúp consistency cao nhưng yêu cầu hiểu rõ business rule.

**Middle → Senior insight:**
Middle cần biết transaction không chỉ là database concept. Senior cần thiết kế boundary dựa trên business invariant.

### Design 2 — Modular Monolith trước Microservices

**Khái niệm:**
Modular Monolith chia hệ thống thành các module độc lập trong cùng một application deployment.

**Vấn đề nó giải quyết:**
Giảm complexity của microservices nhưng vẫn tạo boundary rõ ràng.

**Ví dụ thực tế:**
Một hệ thống ERP có module Sales, Inventory, Accounting tách biệt nhưng dùng chung deployment.

**Trade-off:**
Đơn giản vận hành hơn microservices nhưng scale từng module riêng sẽ khó hơn.

**Middle → Senior insight:**
Senior cần biết microservices không phải bước mặc định; boundary tốt quan trọng hơn số lượng service.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Một operation idempotent có thể được gọi nhiều lần nhưng vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Xử lý retry an toàn trong distributed system.

**Ví dụ thực tế:**
API thanh toán dùng `Idempotency-Key` để tránh charge khách hàng hai lần khi client retry.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và xử lý cleanup.

**Middle → Senior insight:**
Middle cần hiểu retry có thể gây duplicate action. Senior cần thiết kế API chịu được failure và retry.
