# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsNoTracking()` đúng lúc trong Entity Framework Core

**Mẹo:**
Sử dụng `AsNoTracking()` cho các query chỉ đọc dữ liệu và không cần EF Core theo dõi entity.

**Tại sao hữu ích:**
Giảm memory usage và tăng performance khi đọc nhiều dữ liệu.

**Ví dụ:**
```csharp
var users = await db.Users
    .AsNoTracking()
    .ToListAsync();
```

**Lưu ý:**
Không dùng cho flow cần update entity sau khi query vì EF Core sẽ không track thay đổi.

### Tip 2 — Dùng SQL Execution Plan khi tối ưu query thay vì đoán

**Mẹo:**
Kiểm tra execution plan trước khi thêm index hoặc rewrite SQL.

**Tại sao hữu ích:**
Giúp xác định bottleneck như table scan, missing index hoặc expensive join.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Orders
WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index quá mức vì có thể làm chậm write operation.

### Tip 3 — Dùng `dotnet-counters` để debug performance .NET production

**Mẹo:**
Sử dụng .NET diagnostics tools để quan sát runtime metrics.

**Tại sao hữu ích:**
Phát hiện CPU cao, GC pressure hoặc thread pool starvation mà không cần attach debugger.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234
```

**Lưu ý:**
Metrics chỉ là dấu hiệu, cần kết hợp tracing và profiling để tìm root cause.

### Tip 4 — Dùng Git `rebase -i` để làm sạch commit history

**Mẹo:**
Interactive rebase giúp squash, reorder hoặc chỉnh sửa commit trước pull request.

**Tại sao hữu ích:**
Code review dễ hơn với history rõ ràng.

**Ví dụ:**
```bash
git rebase -i HEAD~5
```

**Lưu ý:**
Không rebase branch đã chia sẻ rộng rãi vì có thể gây conflict history.

### Tip 5 — Dùng `IOptionsMonitor` cho configuration thay đổi runtime

**Mẹo:**
Sử dụng `IOptionsMonitor` khi application cần đọc configuration mới mà không restart.

**Tại sao hữu ích:**
Phù hợp cho feature flags hoặc dynamic settings trong production.

**Ví dụ:**
```csharp
public class Worker
{
    private readonly IOptionsMonitor<AppSettings> options;
}
```

**Lưu ý:**
Không lạm dụng dynamic configuration nếu thay đổi có thể ảnh hưởng consistency.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Transaction Boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một business operation.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn gây lock lâu hoặc transaction quá nhỏ làm dữ liệu không nhất quán.

**Ví dụ thực tế:**
Trong hệ thống đặt hàng, tạo Order và giảm Inventory có thể cùng transaction nếu cùng database, nhưng gửi email nên xử lý asynchronous.

**Trade-off:**
Transaction lớn tăng consistency nhưng giảm scalability. Transaction nhỏ cần xử lý eventual consistency.

**Middle → Senior insight:**
Middle cần biết transaction dùng ở đâu. Senior cần quyết định boundary dựa trên business invariant.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia application thành các module độc lập trong cùng deployment unit.

**Vấn đề nó giải quyết:**
Tạo boundary rõ ràng mà không phải chịu toàn bộ complexity của distributed system.

**Ví dụ thực tế:**
ERP có module Sales, Inventory, Accounting với domain riêng nhưng chạy chung application.

**Trade-off:**
Đơn giản vận hành hơn nhưng cần discipline để tránh module phụ thuộc chéo.

**Middle → Senior insight:**
Senior developer cần đánh giá boundary, ownership và khả năng scale trước khi tách microservices.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo gọi lại cùng một request nhiều lần vẫn tạo ra cùng kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate operation khi retry trong distributed system.

**Ví dụ thực tế:**
Payment API dùng `Idempotency-Key` để tránh charge hai lần khi network timeout.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và xử lý storage overhead.

**Middle → Senior insight:**
Middle cần hiểu retry có thể gây duplicate. Senior cần thiết kế API chịu được timeout, retry và failure scenario.
