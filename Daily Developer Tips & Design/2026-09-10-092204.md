# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate Options ngay khi application startup

**Mẹo:**
Với cấu hình quan trọng trong ASP.NET Core, bind vào strongly typed Options và dùng `ValidateOnStart()` để phát hiện cấu hình sai trước khi nhận traffic.

**Tại sao hữu ích:**
Nếu endpoint, timeout hoặc connection setting chỉ được đọc ở request đầu tiên, deployment có thể trông healthy nhưng fail ngay khi có user thật.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(o => o.TimeoutSeconds is > 0 and <= 60)
    .ValidateOnStart();
```

**Lưu ý:**
Chỉ fail startup với cấu hình thực sự bắt buộc. Capability phụ có thể cần degraded mode thay vì làm toàn application không start.

### Tip 2 — Đo round-trip thật của EF Core trước khi tối ưu bulk write

**Mẹo:**
Khi `SaveChangesAsync` ghi nhiều entity, kiểm tra command logging và số database round-trip thực tế trước khi kết luận EF Core đang gửi từng row một.

**Tại sao hữu ích:**
Provider có thể batch nhiều command. Bottleneck thực tế có thể là index maintenance, trigger, transaction duration hoặc số row quá lớn.

**Ví dụ:**
```csharp
foreach (var item in items)
{
    db.OrderLines.Add(item);
}

await db.SaveChangesAsync(ct);
```

Bật command logging để xem số batch và thời gian từng batch.

**Lưu ý:**
Batching không thay thế bulk API cho workload hàng trăm nghìn row. Chỉ chuyển sang bulk khi measurement chứng minh cần thiết.

### Tip 3 — Tách route template khỏi URL thực khi ghi metric HTTP

**Mẹo:**
Trong metrics, dùng route template như `/orders/{id}` thay vì URL chứa ID thật.

**Tại sao hữu ích:**
ID động tạo high-cardinality metric series, làm tăng chi phí và làm dashboard/query telemetry khó sử dụng.

**Ví dụ:**
```text
Tốt:  route=/orders/{id}
Xấu:  route=/orders/948271
```

Order ID cụ thể nên nằm trong trace hoặc structured log.

**Lưu ý:**
Đừng xóa mọi dimension. Các label hữu hạn như route, status code, region vẫn rất hữu ích cho điều tra production.

### Tip 4 — Dùng Docker layer cache đúng thứ tự trong pipeline .NET

**Mẹo:**
Copy project files và restore dependency trước, sau đó mới copy toàn bộ source để tránh invalidating restore layer sau mỗi thay đổi code nhỏ.

**Tại sao hữu ích:**
Pipeline có thể chậm đáng kể nếu mỗi commit buộc `dotnet restore` và download package lại toàn bộ.

**Ví dụ:**
```dockerfile
COPY *.sln ./
COPY src/MyApp/*.csproj src/MyApp/
RUN dotnet restore

COPY . .
RUN dotnet publish -c Release -o /app/publish
```

**Lưu ý:**
Cache phải phụ thuộc đúng SDK version, lockfile và project file. Cache sai input có thể tạo build không reproducible.

### Tip 5 — Dùng browser DevTools để phân biệt TTFB và rendering bottleneck

**Mẹo:**
Khi user báo trang chậm, xem Network waterfall và Performance trace trước khi tối ưu backend hoặc frontend theo cảm tính.

**Tại sao hữu ích:**
Một page chậm có thể do backend TTFB, bundle JavaScript, image decode, layout hoặc main-thread work. Mỗi nguyên nhân cần hướng xử lý khác nhau.

**Ví dụ:**
```text
TTFB:          180 ms
JS download:  1200 ms
JS execution:  900 ms
```

Trong trường hợp này, tối ưu SQL thêm 20 ms gần như không cải thiện UX đáng kể.

**Lưu ý:**
Đừng chỉ đo trên máy developer mạnh. Dùng network/device profile gần production và xem dữ liệu percentile nếu có.

## 🧠 Software Design

### Design 1 — API additive evolution trước khi tạo version mới

**Khái niệm:**
Ưu tiên thay đổi backward-compatible như thêm field optional hoặc endpoint mới trước khi tạo API version mới cho mọi thay đổi.

**Vấn đề nó giải quyết:**
Mỗi version mới tạo thêm documentation, test matrix, deprecation policy và migration burden cho consumers.

**Ví dụ thực tế:**
Thay vì đổi ngay `customerName` thành `displayName`, có thể thêm field mới, migrate consumers rồi deprecate field cũ ở release sau.

**Trade-off:**
Additive evolution giảm coordination cost nhưng contract tạm thời lớn hơn. Versioning phù hợp hơn khi semantic change thực sự breaking.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking change. Senior / Technical developer phải định nghĩa compatibility window, deprecation policy và thời điểm versioning thực sự đáng chi phí.

### Design 2 — SLO và Error Budget cho quyết định reliability

**Khái niệm:**
SLO định nghĩa reliability target; error budget biểu diễn phần failure còn được phép trong một khoảng thời gian.

**Vấn đề nó giải quyết:**
Không có target cụ thể, team dễ tranh luận cảm tính giữa tốc độ release và độ ổn định.

**Ví dụ thực tế:**
```text
SLO: 99.9% successful checkout / 30 days
Error budget gần hết:
-> giảm rollout risk
-> ưu tiên reliability fixes
```

**Trade-off:**
SLO tạo tiêu chí rõ nhưng target quá cao làm tăng cost; target quá thấp làm user experience kém.

**Middle → Senior insight:**
Middle developer cần hiểu signal nào phản ánh user experience. Senior / Technical developer phải chọn target theo business criticality, dependency chain và cost thực tế.

### Design 3 — MongoDB embedding vs referencing theo access pattern

**Khái niệm:**
Embedding phù hợp khi dữ liệu có lifecycle gần nhau và thường được đọc cùng nhau; referencing phù hợp khi dữ liệu có lifecycle độc lập hoặc được chia sẻ rộng.

**Vấn đề nó giải quyết:**
Embed quá nhiều tạo document lớn và write amplification. Reference quá nhiều lại làm read path cần thêm query hoặc aggregation.

**Ví dụ thực tế:**
```text
Order:
- shippingAddress snapshot -> embed
- orderLines bounded       -> embed
- customer master profile -> reference
```

**Trade-off:**
Embedding giảm round-trip nhưng duplicate data. Referencing giảm duplication nhưng tăng coordination và lookup cost.

**Middle → Senior insight:**
Middle developer cần model theo query/update pattern. Senior / Technical developer phải cân nhắc document size, write frequency, ownership, historical snapshot và partition/shard strategy.
