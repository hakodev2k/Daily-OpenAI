# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test code phụ thuộc thời gian mà không phải `Task.Delay` thật

**Mẹo:**
Trong .NET 8+, nếu business logic phụ thuộc `UtcNow`, timeout hoặc timer, inject `TimeProvider` thay vì gọi trực tiếp `DateTimeOffset.UtcNow` khắp code. Trong test, dùng fake time provider để điều khiển clock deterministically.

**Tại sao hữu ích:**
Code phụ thuộc thời gian thường tạo test chậm và flaky nếu phải chờ thời gian thật trôi qua. `TimeProvider` biến clock thành dependency rõ ràng, giúp test expiration, retry window, cache TTL hoặc scheduled behavior mà không cần sleep vài giây.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => clock.GetUtcNow() >= expiresAt;
}
```

Trong production:
```csharp
builder.Services.AddSingleton(TimeProvider.System);
```

Trong test, dùng fake provider và advance thời gian theo ý muốn.

**Lưu ý:**
Không cần abstraction riêng cho clock nếu `TimeProvider` đã đủ. Nhưng cũng đừng biến mọi `DateTime` trong domain thành dependency nếu chỉ là dữ liệu thuần. Với database-generated timestamp hoặc external timestamp, phải xác định rõ source of truth thay vì giả định application clock luôn đúng.

### Tip 2 — Với Elasticsearch, phân biệt `text` và `keyword` ngay từ mapping để tránh query/sort sai semantics

**Mẹo:**
Dùng `text` cho full-text search cần analyzer/tokenization; dùng `keyword` cho exact match, aggregation, sorting hoặc identifier. Một field thường có thể cần cả hai dưới dạng multi-field.

**Tại sao hữu ích:**
Nếu index `ProductName` chỉ là `text`, query exact hoặc sort có thể không hoạt động như mong đợi vì nội dung đã được analyzer chia token. Ngược lại, nếu chỉ dùng `keyword`, search kiểu người dùng nhập tự nhiên sẽ rất hạn chế.

**Ví dụ:**
```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "raw": { "type": "keyword" }
        }
      }
    }
  }
}
```

Full-text search dùng `name`, còn sort/aggregation dùng `name.raw`.

**Lưu ý:**
Mapping sai thường không sửa được chỉ bằng đổi query; nhiều trường hợp phải reindex. Đừng bật `fielddata` trên `text` chỉ để sort nhanh cho xong vì có thể tốn heap đáng kể. Thiết kế mapping từ query pattern thực tế trước khi dữ liệu phình lớn.

### Tip 3 — Phân biệt `readinessProbe` và `livenessProbe` để Kubernetes không restart pod đang chỉ tạm mất dependency

**Mẹo:**
Dùng readiness để quyết định pod có nên nhận traffic; dùng liveness để phát hiện process thật sự bị kẹt và cần restart. Đừng cho liveness phụ thuộc trực tiếp vào database, Redis hoặc API bên ngoài chỉ vì health endpoint đang có sẵn.

**Tại sao hữu ích:**
Nếu database tạm unavailable và liveness cũng fail, Kubernetes có thể restart hàng loạt pod dù application process vẫn khỏe. Điều này làm recovery khó hơn, tạo cold start và có thể biến outage dependency thành restart storm.

**Ví dụ:**
```text
/readiness
- kiểm tra app đã khởi tạo xong
- có thể kiểm tra dependency bắt buộc để phục vụ request

/liveness
- kiểm tra process/event loop còn hoạt động
- không phụ thuộc external service dễ lỗi tạm thời
```

Với startup chậm, cân nhắc thêm `startupProbe` để tránh liveness giết container trước khi application sẵn sàng.

**Lưu ý:**
Readiness quá lỏng có thể gửi traffic vào pod chưa phục vụ được; quá chặt có thể loại toàn bộ replica khỏi service chỉ vì một dependency phụ. Health check phải phản ánh capability thực tế, không phải danh sách mọi dependency trong hệ thống.

### Tip 4 — Khi backend fetch URL do user cung cấp, coi SSRF là threat mặc định

**Mẹo:**
Nếu application có chức năng import ảnh từ URL, webhook test, URL preview hoặc server-side fetch, không gửi request tới URL arbitrary mà chưa validate. Áp allowlist/domain policy khi có thể, resolve DNS cẩn thận và chặn private/link-local/internal address range.

**Tại sao hữu ích:**
SSRF cho phép attacker lợi dụng server làm HTTP client để truy cập resource mà họ không thể gọi trực tiếp, ví dụ metadata endpoint, internal admin service hoặc port trong private network. Application chạy trong cloud/VNet thường có quyền mạng rộng hơn browser của user.

**Ví dụ:**
```text
User nhập:
http://169.254.169.254/...
hoặc
http://internal-admin.local/

Backend naive:
HttpClient.GetAsync(userUrl)

Hardened flow:
- chỉ cho phép http/https
- validate host/domain policy
- resolve và reject private/link-local IP
- kiểm tra redirect destination lại từ đầu
- giới hạn timeout, response size và content type
```

**Lưu ý:**
Chỉ regex hostname là chưa đủ vì DNS rebinding và redirect có thể đổi destination. Nếu use case chỉ cần fetch từ vài provider cố định, allowlist hẹp an toàn và dễ reasoning hơn một generic URL fetcher.

### Tip 5 — Với enterprise CMS, cache theo content version/publish state thay vì chỉ theo URL

**Mẹo:**
Khi cache page/component trong Optimizely CMS hoặc CMS tương tự, cache key nên phản ánh content identity, language, variation/personalization và publish/version state cần thiết, không chỉ dùng raw URL.

**Tại sao hữu ích:**
Một URL có thể trả nội dung khác nhau theo language, market, visitor group hoặc publish state. Cache chỉ theo URL dễ phục vụ nhầm variant, đặc biệt trong preview/editor mode hoặc site đa ngôn ngữ.

**Ví dụ:**
```text
Rủi ro:
cache key = /products/shoes

Tốt hơn tùy scenario:
page:{contentId}:{language}:{publishedVersion}:{market}
```

Với CDN/output cache, invalidation nên gắn với publish event hoặc surrogate key/tag thay vì purge toàn bộ site mỗi lần editor publish một block.

**Lưu ý:**
Đừng nhét mọi request dimension vào cache key vì sẽ làm hit ratio sụt mạnh. Chỉ đưa dimension thật sự thay đổi response. Preview/editor request thường nên bypass shared cache để tránh rò rỉ draft content.

## 🧠 Software Design

### Design 1 — CQRS read model chỉ đáng dùng khi read và write thực sự có pressure khác nhau

**Khái niệm:**
CQRS tách model xử lý command/write khỏi model phục vụ query/read. Điều này không bắt buộc phải tách thành microservice hay database riêng ngay từ đầu; có thể bắt đầu ngay trong Modular Monolith với boundary logic rõ ràng.

**Vấn đề nó giải quyết:**
Một order domain có invariant phức tạp khi ghi nhưng màn hình dashboard lại cần join/aggregate rất khác domain model. Ép một model vừa bảo vệ invariant vừa tối ưu cho mọi màn hình thường làm cả hai phía khó maintain.

**Ví dụ thực tế:**
```text
Write side:
PlaceOrderCommand
-> domain rules
-> Orders / OrderLines

Read side:
OrderDashboardQuery
-> projection DTO
-> query tối ưu riêng
-> có thể đọc từ read replica/projection nếu cần
```

Ban đầu cả hai vẫn có thể dùng cùng database nhưng query model không cần đi qua aggregate chỉ để render UI.

**Trade-off:**
CQRS làm read/write intent rõ hơn và cho phép scale/query optimization độc lập, nhưng tăng số model, mapping và eventual-consistency concern nếu tách read store. Với CRUD đơn giản, tách command/query chỉ để theo pattern có thể làm codebase phức tạp không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu query không nhất thiết phải hydrate đầy đủ domain aggregate. Senior / Technical developer phải đánh giá read/write asymmetry, consistency requirement, team ownership và operational cost trước khi tiến từ logical separation sang read store riêng hoặc event-driven projection.

### Design 2 — Consumer-Driven Contract Testing để phát hiện integration break sớm hơn full E2E

**Khái niệm:**
Consumer-Driven Contract Testing cho phép consumer mô tả contract tối thiểu mà nó cần từ provider, rồi provider verify các contract đó trong CI. Mục tiêu là phát hiện breaking change ở boundary mà không phụ thuộc hoàn toàn vào môi trường E2E lớn.

**Vấn đề nó giải quyết:**
Trong hệ thống nhiều service, full E2E test thường chậm, flaky và khó biết failure thuộc service nào. Unit test từng service lại không phát hiện provider rename field hoặc đổi semantics mà consumer đang phụ thuộc.

**Ví dụ thực tế:**
```text
Mobile BFF cần từ Catalog API:
GET /products/{id}
- id: string
- name: string
- price.amount: number

Catalog team đổi `price.amount` -> `price.value`

Provider CI verify consumer contract
-> fail trước khi deploy breaking change
```

Contract nên tập trung vào observable behavior consumer thực sự cần, không serialize toàn bộ internal model thành contract khổng lồ.

**Trade-off:**
Contract test nhanh và định vị lỗi tốt hơn E2E, nhưng không thay thế test production-like cho auth, network, deployment config hoặc flow xuyên nhiều hệ thống. Nếu contract được tạo quá chi tiết, provider mất khả năng refactor dù behavior thực tế không đổi.

**Middle → Senior insight:**
Middle developer cần biết mock provider trong unit test không chứng minh provider thật còn tương thích. Senior / Technical developer phải thiết kế contract ownership, versioning, deprecation và CI workflow sao cho contract bảo vệ compatibility mà không biến consumer thành owner toàn bộ provider schema.

### Design 3 — Distributed lock cần fencing token nếu resource bên dưới không tự bảo vệ stale owner

**Khái niệm:**
Lease-based distributed lock có thể hết hạn trong lúc process cũ vẫn đang chạy. Fencing token là sequence tăng dần được cấp mỗi lần acquire lock; downstream chỉ chấp nhận operation có token mới hơn token đã thấy trước đó.

**Vấn đề nó giải quyết:**
Giả sử worker A giữ lease 30 giây nhưng bị GC pause 40 giây. Lease hết hạn, worker B acquire lock và bắt đầu xử lý. Khi A tỉnh lại, A vẫn tưởng mình đang làm việc hợp lệ và có thể ghi đè kết quả của B nếu resource không phân biệt owner cũ/mới.

**Ví dụ thực tế:**
```text
A acquire lock -> fencing token 41
A bị pause

lease 41 hết hạn
B acquire lock -> token 42
B write storage với token 42 -> accepted

A tỉnh lại, write với token 41
storage thấy 41 < 42 -> reject
```

Token phải được resource hoặc write boundary enforce; chỉ giữ token trong memory mà không kiểm tra khi ghi thì không tạo safety guarantee.

**Trade-off:**
Fencing token bảo vệ split-brain/stale-owner tốt hơn lease đơn thuần nhưng đòi hỏi storage/write path hỗ trợ monotonic token check. Với operation đã idempotent hoặc database có atomic claim đủ mạnh, distributed lock riêng có thể không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu distributed lock không tương đương `lock` trong process và lease có thể mất quyền sở hữu. Senior / Technical developer phải phân tích failure mode pause/network partition, quyết định giữa atomic database claim, idempotency, lease, fencing token và tránh thêm coordination component khi storage primitive đơn giản đã giải quyết được bài toán.
