# Daily Developer Tips & Design — 2026-09-27

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwait(false)` có chọn lọc trong library code, không như “thuốc tăng tốc”

**Mẹo:**
Trong ASP.NET Core application code, thường không cần rải `ConfigureAwait(false)` khắp nơi vì mặc định không có `SynchronizationContext` kiểu ASP.NET cũ. Trong reusable library, nó vẫn có thể hữu ích để tránh phụ thuộc vào context của caller.

**Tại sao hữu ích:**
Hiểu cơ chế `await` giúp tránh áp dụng một optimization cũ theo thói quen. `ConfigureAwait(false)` kiểm soát việc continuation có cố quay lại captured context hay không; nó không làm I/O nhanh hơn và không sửa code đang block bằng `.Result`.

**Ví dụ:**
```csharp
public async Task<string> LoadAsync(HttpClient client, CancellationToken ct)
{
    using var response = await client.GetAsync("/data", ct)
        .ConfigureAwait(false);

    return await response.Content.ReadAsStringAsync(ct)
        .ConfigureAwait(false);
}
```

**Lưu ý:**
UI frameworks có thread-affinity khác ASP.NET Core. Đừng xóa hoặc thêm `ConfigureAwait(false)` máy móc trong shared library nếu chưa hiểu caller và execution context.

### Tip 2 — Dùng `ExecuteUpdateAsync` khi cần update theo tập hợp mà không cần materialize entity

**Mẹo:**
Với EF Core, nếu business operation chỉ cần update nhiều row theo predicate và không cần chạy domain behavior trên từng entity, cân nhắc `ExecuteUpdateAsync` thay vì load entities rồi sửa từng object.

**Tại sao hữu ích:**
Cách này gửi set-based `UPDATE` trực tiếp xuống database, giảm round trip, allocation và change-tracking overhead. Nó đặc biệt hữu ích cho maintenance job hoặc bulk state transition có điều kiện rõ.

**Ví dụ:**
```csharp
await db.Sessions
    .Where(x => x.ExpiresAt < cutoff && x.Status == SessionStatus.Active)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Status, SessionStatus.Expired), ct);
```

**Lưu ý:**
Operation này bypass change tracker và không tự chạy logic trong entity instance. Nếu aggregate invariant, audit logic hoặc concurrency semantics phụ thuộc vào tracked entity, cần thiết kế boundary khác; đồng thời kiểm tra số row affected khi correctness yêu cầu.

### Tip 3 — Với MongoDB, thiết kế compound index theo equality → sort → range của query thật

**Mẹo:**
Khi một query vừa filter vừa sort, thiết kế compound index từ access pattern thay vì tạo index riêng cho từng field. Equality fields thường đứng trước, tiếp theo là sort, rồi range khi phù hợp với workload.

**Tại sao hữu ích:**
Một index đúng shape có thể vừa thu hẹp candidate set vừa cung cấp thứ tự kết quả, tránh in-memory sort và scan lớn. Nhiều single-field indexes không đảm bảo đạt cùng hiệu quả cho query kết hợp.

**Ví dụ:**
Một collection `orders` thường chạy:
```javascript
db.orders.find({
  tenantId: 42,
  status: "Pending",
  createdAt: { $lt: cutoff }
}).sort({ createdAt: -1 }).limit(100)
```
Hãy kiểm tra `explain("executionStats")` cho index theo access pattern, ví dụ `{ tenantId: 1, status: 1, createdAt: -1 }`, thay vì đoán từ tên field.

**Lưu ý:**
Index order không có công thức tuyệt đối; selectivity, nhiều query shapes và write cost đều quan trọng. Over-indexing làm insert/update đắt hơn và tăng memory/storage pressure.

### Tip 4 — Khi Kubernetes pod restart, đọc `Last State` trước khi nhìn log hiện tại

**Mẹo:**
Nếu pod liên tục restart, dùng `kubectl describe pod` và kiểm tra container `Last State`, exit code, reason, events; sau đó đọc log của instance trước bằng `kubectl logs --previous`.

**Tại sao hữu ích:**
Container mới có thể vừa khởi động nên log hiện tại trông bình thường, trong khi bằng chứng crash nằm ở instance trước. Exit code, `OOMKilled`, probe failure và events giúp tách application crash khỏi resource/probe/deployment problem.

**Ví dụ:**
```bash
kubectl describe pod api-7d9c...
kubectl logs api-7d9c... --previous
```
Nếu `Last State` là `OOMKilled`, đối chiếu memory usage, container limits và allocation profile trước khi chỉ tăng restart delay.

**Lưu ý:**
Tăng memory limit có thể chỉ che memory leak. Ngược lại, limit quá thấp cũng có thể giết workload hợp lệ; cần telemetry và workload measurement để phân biệt.

### Tip 5 — Không log access token chỉ để debug authentication

**Mẹo:**
Khi JWT authentication lỗi production, log metadata an toàn như authentication scheme, issuer expected, audience expected, token expiry status và correlation ID; không ghi raw access token, refresh token hoặc authorization header.

**Tại sao hữu ích:**
Token thường là bearer credential: ai có token có thể dùng quyền của nó cho tới khi hết hạn hoặc bị revoke theo cơ chế tương ứng. Structured diagnostic metadata thường đủ để phân biệt issuer/audience/expiry/configuration failure mà không tạo secret mới trong log store.

**Ví dụ:**
Thay vì log `Authorization: Bearer eyJ...`, ghi event như:
```text
AuthFailed scheme=Bearer reason=InvalidAudience expected=nistats-api correlationId=...
```
Sau đó đối chiếu cấu hình Microsoft Entra, API registration và validation parameters.

**Lưu ý:**
Ngay cả claims cũng có thể chứa PII hoặc dữ liệu nhạy cảm. Thiết kế logging theo data-classification và retention policy, không mặc định mọi decoded claim đều an toàn.

## 🧠 Software Design

### Design 1 — Transaction boundary nên bám business invariant, không bám số repository

**Khái niệm:**
Transaction boundary xác định những thay đổi nào phải thành công hoặc thất bại cùng nhau để giữ invariant. Nó không nên được chia chỉ vì code đi qua nhiều repository, cũng không nên kéo dài qua external network call nếu không thật sự cần.

**Vấn đề nó giải quyết:**
Một request tạo Order và OrderItems trong hai transaction độc lập có thể để lại dữ liệu nửa vời. Ngược lại, giữ database transaction mở trong lúc gọi payment provider làm lock tồn tại lâu, tăng contention và tạo failure mode khó phục hồi.

**Ví dụ thực tế:**
Checkout có thể commit Order ở trạng thái `PendingPayment` cùng Outbox record trong một local transaction. Payment được xử lý ngoài transaction database; kết quả quay lại qua workflow/idempotent handler để chuyển trạng thái Order.

**Trade-off:**
Transaction rộng cho consistency mạnh hơn trong một database nhưng tăng lock duration và coupling. Transaction hẹp giảm contention và phù hợp distributed workflow hơn, nhưng yêu cầu state machine, idempotency hoặc compensation để quản lý eventual consistency.

**Middle → Senior insight:**
Middle developer cần biết operation nào phải atomic và dùng transaction đúng lifecycle. Senior / Technical developer phải xác định invariant thực sự, tránh distributed transaction theo phản xạ, thiết kế recovery path và chấp nhận eventual consistency chỉ ở nơi business cho phép.

### Design 2 — Queue hay Topic phải xuất phát từ ownership của message

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer trong nhóm xử lý. Topic + subscriptions phù hợp khi cùng một event cần được nhiều consumer độc lập nhận theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Dùng một queue cho nhiều business consumers có thể khiến consumer “tranh” mất message của nhau. Ngược lại, tạo topic cho command point-to-point làm topology và vận hành phức tạp không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command có một owner nên có thể đi vào queue của Billing. `OrderPlaced` là event mà Billing, Analytics và Notification đều cần; Azure Service Bus Topic với subscription riêng cho từng capability giữ consumer lifecycle độc lập.

**Trade-off:**
Topic hỗ trợ fan-out và decoupling nhưng tăng subscription, DLQ, filtering và observability cần quản lý. Queue đơn giản hơn nhưng không cung cấp broadcast semantics; nhân bản message thủ công ở producer lại làm producer biết quá nhiều consumer.

**Middle → Senior insight:**
Middle cần phân biệt command với event và xử lý duplicate/DLQ đúng. Senior / Technical developer phải quyết định ownership, schema evolution, replay/recovery, ordering requirement và liệu fan-out thực sự cần broker hay một synchronous integration đơn giản đã đủ.

### Design 3 — Bounded Context không đồng nghĩa với Microservice

**Khái niệm:**
Bounded Context là ranh giới nơi một domain model và ngôn ngữ nghiệp vụ có nghĩa nhất quán. Nó là modeling boundary; deployment boundary có thể là module trong Modular Monolith hoặc service độc lập tùy constraint vận hành.

**Vấn đề nó giải quyết:**
Một enterprise application dễ tạo “global domain model” nơi `Customer`, `Product` hoặc `Status` mang nhiều nghĩa khác nhau nhưng bị ép dùng chung schema/class. Coupling tăng và thay đổi của một capability lan sang capability khác.

**Ví dụ thực tế:**
Trong e-commerce, Catalog quan tâm Product như nội dung bán hàng; Ordering quan tâm snapshot giá và SKU tại thời điểm mua. Hai model có thể thuộc bounded context khác nhau nhưng vẫn được triển khai trong cùng một .NET application với module boundary rõ trước khi có lý do tách service.

**Trade-off:**
Bounded Context làm ownership và model rõ hơn nhưng ranh giới sai có thể tạo mapping, duplication và coordination cost. Tách thành Microservices còn thêm network, deployment, observability và eventual-consistency complexity.

**Middle → Senior insight:**
Middle developer cần giữ model và dependency không xuyên boundary tùy tiện. Senior / Technical developer phải tìm boundary từ business capability, change cadence và ownership; chỉ chọn Microservices khi independent deployment/scale/organization benefit đủ lớn để trả distributed-systems cost.
