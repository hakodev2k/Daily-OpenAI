# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong .NET

**Mẹo:**
Khi ASP.NET Core đột nhiên tăng latency nhưng CPU chưa cao tương ứng, kiểm tra ThreadPool queue, thread count và blocking call trước khi mặc định scale thêm instance.

**Tại sao hữu ích:**
ThreadPool starvation xảy ra khi request cần worker thread nhưng nhiều thread đang bị block bởi synchronous I/O, `.Result`, `.Wait()` hoặc lock dài. CPU có thể vẫn thấp vì thread đang chờ, trong khi request mới xếp hàng và latency tăng mạnh.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Quan sát các dấu hiệu như thread count tăng dần, work item queue tăng và request latency cao. Sau đó capture trace để tìm stack có synchronous blocking trong code async.

**Lưu ý:**
Không phải cứ nhiều thread là starvation. Workload CPU-bound thật sự cũng có thể cần nhiều thread. Hãy correlate runtime counters với CPU, request rate, dependency latency và call stacks trước khi kết luận.

### Tip 2 — Chặn SSRF khi backend fetch URL do người dùng cung cấp

**Mẹo:**
Nếu API cho phép import ảnh, webhook test hoặc metadata preview từ một URL bên ngoài, đừng gọi trực tiếp mọi URL người dùng gửi. Validate scheme, hostname/IP và network destination trước khi thực hiện outbound request.

**Tại sao hữu ích:**
SSRF cho phép attacker lợi dụng backend để gọi địa chỉ nội bộ mà họ không truy cập trực tiếp được, ví dụ metadata service, admin endpoint hoặc private network resource. Nguy cơ cao hơn khi backend có Managed Identity hoặc network trust rộng.

**Ví dụ:**
```text
User input:
http://169.254.169.254/...
http://localhost:5000/admin
http://10.0.0.12/internal
```

Một policy an toàn thường chỉ cho phép `https`, resolve DNS rồi chặn loopback/private/link-local range, giới hạn redirect và dùng allowlist khi business domain có thể xác định trước.

**Lưu ý:**
Chỉ regex hostname là chưa đủ vì DNS rebinding, redirect và IPv6 representation có thể bypass validation đơn giản. Với chức năng nhạy cảm, tách outbound fetcher sang network zone có egress policy hạn chế sẽ an toàn hơn.

### Tip 3 — Tránh unbounded array trong MongoDB document

**Mẹo:**
Nếu một collection con có thể tăng không giới hạn như audit logs, comments hoặc message history, đừng mặc định embed toàn bộ vào một document cha.

**Tại sao hữu ích:**
MongoDB document có giới hạn kích thước và mỗi lần update array lớn có thể làm document ngày càng nặng, tốn bandwidth, index cost và update cost. Một aggregate nhỏ ban đầu có thể trở thành hotspot sau vài tháng production.

**Ví dụ:**
```text
Không tốt:
Order {
  id,
  status,
  events: [ ... hàng chục nghìn event ... ]
}

Tốt hơn khi history tăng vô hạn:
Orders
OrderEvents
- orderId
- occurredAt
- type
- payload
```

Embed phù hợp khi dữ liệu nhỏ, bounded và thường được đọc cùng nhau; reference phù hợp hơn khi cardinality lớn hoặc lifecycle khác nhau.

**Lưu ý:**
Đừng tách mọi thứ thành nhiều collection theo tư duy relational. MongoDB vẫn hưởng lợi từ denormalization có chủ đích. Quyết định nên dựa trên growth pattern, read/write pattern và transaction boundary.

### Tip 4 — Hủy request frontend cũ bằng `AbortController` để tránh stale response ghi đè state mới

**Mẹo:**
Trong Vue.js hoặc React, khi user thay đổi search/filter liên tục, hủy request trước đó nếu response của nó không còn giá trị.

**Tại sao hữu ích:**
Hai request có thể hoàn thành sai thứ tự. Request cũ chậm hơn có thể trả về sau request mới và ghi đè UI bằng dữ liệu stale dù backend không có lỗi.

**Ví dụ:**
```ts
let controller: AbortController | undefined

async function search(term: string) {
  controller?.abort()
  controller = new AbortController()

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  })

  return response.json()
}
```

Trong component lifecycle, cũng nên abort request khi component unmount nếu kết quả không còn consumer.

**Lưu ý:**
Abort phía browser không đảm bảo server đã dừng mọi công việc. Backend vẫn cần propagation `CancellationToken` nếu muốn ngừng query hoặc outbound call sau khi client disconnect.

### Tip 5 — Dùng `git worktree` khi phải xử lý hotfix mà không muốn stash nhánh đang làm

**Mẹo:**
Khi đang làm feature dở nhưng cần xử lý production hotfix trên branch khác, dùng `git worktree` để mở thêm working directory thay vì stash/chuyển branch liên tục.

**Tại sao hữu ích:**
Một repository có thể có nhiều working tree cùng trỏ tới các branch khác nhau. Bạn giữ nguyên build artifacts, editor state và uncommitted work của feature trong thư mục hiện tại, đồng thời sửa hotfix độc lập.

**Ví dụ:**
```bash
git worktree add ../app-hotfix hotfix/payment-timeout

cd ../app-hotfix
# sửa lỗi, test, commit

cd ../app
git worktree remove ../app-hotfix
```

Cách này đặc biệt hữu ích khi solution lớn và switching branch làm invalid cache/build output đáng kể.

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree thông thường. Cũng cần nhớ cleanup worktree cũ để tránh để lại metadata và thư mục không dùng nữa.

## 🧠 Software Design

### Design 1 — Event Sourcing chỉ đáng dùng khi history của state là dữ liệu nghiệp vụ có giá trị

**Khái niệm:**
Event Sourcing lưu chuỗi sự kiện bất biến làm source of truth rồi dựng state hiện tại bằng cách replay/projection. Giá trị cốt lõi không phải “dùng event”, mà là giữ lịch sử thay đổi như dữ liệu hạng nhất.

**Vấn đề nó giải quyết:**
Một số domain cần biết không chỉ trạng thái hiện tại mà cả quá trình dẫn tới trạng thái đó, ví dụ ledger, audit-heavy workflow hoặc business rule cần reconstruct state tại thời điểm trước đây.

**Ví dụ thực tế:**
```text
AccountOpened
MoneyDeposited +100
MoneyWithdrawn -30
AccountFrozen

Current balance/state
-> projection từ event stream
```

Projection khác có thể phục vụ reporting mà không thay đổi event history gốc.

**Trade-off:**
Event Sourcing mang lại auditability, temporal reconstruction và khả năng build projection mới, nhưng tăng complexity về event schema evolution, replay, eventual consistency, tooling và debugging. Với CRUD thông thường chỉ cần audit log, database state + audit table thường đơn giản hơn nhiều.

**Middle → Senior insight:**
Middle developer cần hiểu event bất biến và projection có thể rebuild. Senior / Technical developer phải chứng minh domain thật sự cần historical truth, thiết kế event evolution, snapshot, replay strategy và operational tooling trước khi chọn Event Sourcing thay cho persistence truyền thống.

### Design 2 — Backend for Frontend (BFF) hữu ích khi mỗi client có interaction model khác nhau

**Khái niệm:**
BFF đặt một backend boundary riêng cho từng loại client như web, mobile hoặc partner UI khi mỗi client cần aggregation, authentication flow và payload khác đáng kể.

**Vấn đề nó giải quyết:**
Nếu một generic API cố phục vụ mọi client, endpoint dễ tích tụ nhiều option, over-fetch/under-fetch và logic presentation-specific. Ngược lại, để frontend gọi trực tiếp hàng chục service làm tăng coupling và network chatter.

**Ví dụ thực tế:**
```text
Web BFF
-> aggregate CMS + pricing + recommendations
-> trả payload tối ưu cho SSR

Mobile BFF
-> payload nhỏ hơn
-> ít round trip
-> token/session flow riêng
```

Core services vẫn giữ business capability; BFF chủ yếu orchestration và client-facing concerns.

**Trade-off:**
BFF giảm coupling giữa client và backend landscape, nhưng thêm deployment, observability và nguy cơ duplicate logic giữa BFFs. Nếu chỉ có một client hoặc khác biệt payload rất nhỏ, một API rõ ràng thường đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần giữ business rule khỏi BFF và tránh biến nó thành monolith mới. Senior / Technical developer phải quyết định khi nào client-specific pressure đủ lớn để biện minh cho boundary riêng, đồng thời quản lý duplicated orchestration và ownership giữa teams.

### Design 3 — Chuẩn hóa dữ liệu ghi, denormalize dữ liệu đọc khi hai workload có nhu cầu khác nhau

**Khái niệm:**
Normalization tối ưu tính nhất quán và giảm duplication ở transactional model; denormalized read model tối ưu query shape và latency cho use case đọc cụ thể. Hai mục tiêu này không nhất thiết phải dùng cùng schema.

**Vấn đề nó giải quyết:**
Dashboard hoặc search page có thể phải join nhiều bảng transactional đúng chuẩn mỗi request. Cố tối ưu bằng cách phá normalization trực tiếp trong write model có thể làm update logic và invariant phức tạp hơn toàn hệ thống.

**Ví dụ thực tế:**
```text
Transactional SQL:
Orders
OrderLines
Customers
Products

Read model:
OrderSearchDocument
- OrderId
- CustomerName
- ProductNames
- Total
- Status
- UpdatedAt
```

Read model có thể được cập nhật qua projection/job/event tùy freshness requirement.

**Trade-off:**
Tách read model giúp query nhanh và đơn giản hơn nhưng tạo duplicated data, synchronization logic và eventual consistency. Nếu query hiện tại đã đáp ứng SLO bằng index/query tuning, thêm projection riêng có thể là over-engineering.

**Middle → Senior insight:**
Middle developer cần hiểu normalization không đồng nghĩa mọi read phải join trực tiếp source tables. Senior / Technical developer phải cân bằng consistency, freshness budget, rebuild capability, operational cost và query SLO để quyết định khi nào denormalization thực sự mang lại giá trị.
