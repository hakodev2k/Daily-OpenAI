# Daily Developer Tips & Design — 2026-10-05

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng buffer toàn bộ response khi chỉ cần stream

**Mẹo:**
Với file lớn hoặc response dài từ third-party API, dùng `HttpCompletionOption.ResponseHeadersRead` và đọc stream thay vì chờ `HttpClient` buffer toàn bộ body.

**Tại sao hữu ích:**
Cách này giảm peak memory và cho phép xử lý dữ liệu sớm hơn. Mặc định, một số cách gọi tiện lợi khiến ứng dụng phải nhận đủ response trước khi tiếp tục, dễ làm tăng allocation khi nhiều request lớn chạy đồng thời.

**Ví dụ:**
```csharp
using var response = await httpClient.GetAsync(
    url,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);

response.EnsureSuccessStatusCode();

await using var stream =
    await response.Content.ReadAsStreamAsync(cancellationToken);

await stream.CopyToAsync(destination, cancellationToken);
```

**Lưu ý:**
Streaming không tự giải quyết timeout, giới hạn kích thước hay backpressure. Phải dispose `HttpResponseMessage` đúng cách và vẫn cần kiểm soát content length, cancellation và nguồn dữ liệu không đáng tin cậy.

### Tip 2 — Dùng keyset pagination cho danh sách lớn, ổn định

**Mẹo:**
Khi API phân trang sâu trên SQL Server/PostgreSQL, cân nhắc keyset pagination thay cho `OFFSET ... FETCH` nếu client chủ yếu đi next/previous.

**Tại sao hữu ích:**
`OFFSET` lớn buộc database bỏ qua ngày càng nhiều rows. Keyset dùng giá trị cuối trang trước làm điểm bắt đầu nên thường tận dụng index tốt hơn và ít bị page drift khi dữ liệu mới được chèn.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)`.

**Lưu ý:**
Luôn có tie-breaker duy nhất như `Id`. Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 500; thiết kế cursor cũng phải tránh để client phụ thuộc vào chi tiết schema.

### Tip 3 — Chặn cache stampede bằng single-flight, không chỉ tăng TTL

**Mẹo:**
Khi một Redis key nóng hết hạn, chỉ cho một request rebuild dữ liệu; các request còn lại chờ hoặc dùng stale value trong một khoảng ngắn.

**Tại sao hữu ích:**
Nếu 500 request cùng cache miss và cùng truy vấn database, cache vốn để bảo vệ database lại tạo ra một traffic spike. Jittered TTL và single-flight giảm khả năng nhiều key/request tái tạo đồng thời.

**Ví dụ:**
Một endpoint catalog có cache 5 phút. Khi key hết hạn, instance thắng lock ngắn hạn rebuild cache; instance khác dùng stale snapshot hoặc retry có backoff thay vì cùng chạy query nặng.

**Lưu ý:**
Distributed lock cũng có failure modes: lock timeout, process chết, clock/lease assumptions. Không giữ lock lâu và không coi lock Redis là transaction guarantee cho business-critical consistency.

### Tip 4 — Dùng `git bisect` khi regression có khoảng commit rõ ràng

**Mẹo:**
Khi production regression xuất hiện giữa một release tốt và release lỗi, dùng `git bisect` để tìm commit đầu tiên gây lỗi thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Binary search giảm số lần kiểm tra từ tuyến tính xuống xấp xỉ `log2(n)`. Nếu có test/script tái hiện lỗi, quá trình có thể tự động hóa.

**Ví dụ:**
```bash
git bisect start
git bisect bad v2.8.0
git bisect good v2.7.3
git bisect run dotnet test tests/Regression.Tests
git bisect reset
```

**Lưu ý:**
Test phải xác định đáng tin cậy good/bad. Flaky test, migration phụ thuộc môi trường hoặc commit không build được có thể làm kết quả sai; khi đó dùng `git bisect skip` có chủ đích.

### Tip 5 — Phân biệt ThreadPool starvation với CPU saturation

**Mẹo:**
Khi ASP.NET Core latency tăng mạnh, đừng kết luận CPU thiếu chỉ từ symptom “request xếp hàng”. Kiểm tra CPU, ThreadPool queue, thread count, request duration và blocking call cùng lúc.

**Tại sao hữu ích:**
Sync-over-async như `.Result`, `.Wait()` hoặc blocking I/O có thể giữ ThreadPool threads trong khi CPU chưa đạt 100%. Runtime thêm thread có độ trễ, khiến p95/p99 tăng và throughput giảm.

**Ví dụ:**
Nếu CPU 45% nhưng request queue tăng, thread count tăng liên tục và trace cho thấy nhiều stack dừng ở `Task<T>.Result`, giả thuyết ThreadPool starvation mạnh hơn “cần scale CPU”.

**Lưu ý:**
Không sửa bằng cách tùy tiện tăng minimum ThreadPool threads. Việc đó có thể che nguyên nhân và tăng contention; cần xác định blocking path bằng metrics, trace hoặc profiler trước.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database + messaging

**Khái niệm:**
Outbox lưu business change và message cần publish trong cùng local database transaction. Một publisher riêng đọc outbox và gửi message tới broker sau đó.

**Vấn đề nó giải quyết:**
Nếu code commit Order rồi mới gửi Azure Service Bus message, process có thể chết giữa hai bước: database đã đổi nhưng event không bao giờ được gửi. Đảo thứ tự cũng tạo nguy cơ gửi event cho transaction sau đó rollback.

**Ví dụ thực tế:**
Checkout ghi `Order` và `OutboxMessage(OrderPlaced)` trong một EF Core transaction. Background worker publish message, rồi đánh dấu outbox đã xử lý. Consumer vẫn phải idempotent vì publisher có thể gửi lại sau failure.

**Trade-off:**
Lợi ích là tránh distributed transaction và thu hẹp “dual-write gap”. Chi phí là thêm bảng, publisher, cleanup, monitoring, duplicate handling và eventual consistency.

**Middle → Senior insight:**
Middle cần hiểu transaction boundary và implement outbox/publisher an toàn. Senior / Technical cần quyết định liệu hệ thống có thật sự cần delivery guarantee này, chọn polling hay CDC, định nghĩa retention/ordering/idempotency và đánh giá operational cost thay vì áp dụng pattern mặc định.

### Design 2 — Modular Monolith trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployable application nhưng chia domain thành modules có boundary rõ ràng, ownership dữ liệu và dependency được kiểm soát.

**Vấn đề nó giải quyết:**
Một monolith thiếu boundary dễ thành “big ball of mud”, nhưng tách Microservices quá sớm đưa network failure, distributed tracing, deployment orchestration và eventual consistency vào hệ thống trước khi domain đủ ổn định.

**Ví dụ thực tế:**
Hệ thống e-commerce có Catalog, Ordering và Reviews là modules trong cùng ASP.NET Core deployment. Ordering không truy cập trực tiếp internal classes của Catalog; giao tiếp qua contract/module API. Khi Catalog cần scale hoặc ownership độc lập thực sự, boundary đã tạo seam để tách.

**Trade-off:**
Lợi ích là deployment và debugging đơn giản hơn Microservices trong khi vẫn ép modularity. Chi phí là process/database resources vẫn có thể chia sẻ và boundary dễ bị phá nếu team không enforce dependency rules.

**Middle → Senior insight:**
Middle cần giữ dependency đúng chiều và tránh cross-module shortcuts. Senior / Technical phải đánh giá scaling profile, team topology, release independence, failure isolation và migration cost để quyết định module nào đáng tách; “nhiều service hơn” không đồng nghĩa kiến trúc trưởng thành hơn.

### Design 3 — Observability là một phần của API contract vận hành

**Khái niệm:**
Observability design xác định trước logs, metrics, traces và correlation context cần thiết để suy luận trạng thái hệ thống từ bên ngoài, thay vì thêm log sau khi incident xảy ra.

**Vấn đề nó giải quyết:**
Một API có thể đúng chức năng nhưng rất khó vận hành nếu chỉ log “request failed”. Khi latency tăng qua nhiều dependency, thiếu correlation và dependency telemetry khiến đội ngũ không phân biệt được app, database hay external API là bottleneck.

**Ví dụ thực tế:**
Request checkout mang trace/correlation context qua ASP.NET Core → SQL → payment API → Service Bus. Dashboard theo dõi request rate, error rate và p50/p95/p99; structured logs chứa `OrderId` nhưng không ghi card/token nhạy cảm.

**Trade-off:**
Telemetry tốt rút ngắn MTTR và hỗ trợ capacity/performance analysis. Đổi lại, tracing/logging có storage cost, runtime overhead, sampling complexity và rủi ro lộ dữ liệu nếu schema log không được kiểm soát.

**Middle → Senior insight:**
Middle cần tạo structured logs, correlation và telemetry đúng chỗ. Senior / Technical cần thiết kế SLI/SLO, sampling, cardinality, retention và ownership của alert; đồng thời quyết định tín hiệu nào đủ để chẩn đoán mà không biến observability thành nguồn chi phí hoặc noise.
