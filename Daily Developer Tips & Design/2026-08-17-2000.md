# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ValueTask` chỉ khi hot path thường hoàn thành đồng bộ

**Mẹo:**
Nếu một async API rất thường xuyên có kết quả sẵn ngay lập tức, `ValueTask<T>` có thể tránh allocation của `Task<T>` trong một số trường hợp.

**Tại sao hữu ích:**
Hữu ích với cache lookup, parser async nhẹ hoặc abstraction nơi phần lớn call trả kết quả đồng bộ nhưng vẫn cần hỗ trợ async fallback.

**Ví dụ:**
```csharp
public ValueTask<User?> GetUserAsync(
    string id,
    CancellationToken cancellationToken)
{
    if (_cache.TryGetValue(id, out var user))
    {
        return ValueTask.FromResult<User?>(user);
    }

    return new ValueTask<User?>(
        LoadFromDatabaseAsync(id, cancellationToken));
}
```

**Lưu ý:**
`ValueTask` làm API và consumption phức tạp hơn; một instance không nên được await nhiều lần. Chỉ dùng khi profiling cho thấy allocation của `Task` đáng kể.

### Tip 2 — Dùng covering index có chọn lọc thay vì thêm mọi cột vào key

**Mẹo:**
Khi query thường xuyên filter/sort theo một số cột nhưng chỉ cần trả thêm vài cột khác, cân nhắc covering index bằng `INCLUDE` thay vì đưa toàn bộ cột vào index key.

**Tại sao hữu ích:**
Có thể giúp database trả kết quả trực tiếp từ index mà không lookup về base table, đồng thời giữ key nhỏ hơn so với việc index mọi cột.

**Ví dụ:**
SQL Server:

```sql
CREATE INDEX IX_Orders_Status_CreatedAt
ON Orders(Status, CreatedAt)
INCLUDE (CustomerId, TotalAmount);
```

Query:

```sql
SELECT CustomerId, TotalAmount
FROM Orders
WHERE Status = 'Pending'
ORDER BY CreatedAt;
```

**Lưu ý:**
`INCLUDE` vẫn tăng storage và write cost. Đừng biến index thành bản sao của cả bảng chỉ để tránh lookup cho mọi query.

### Tip 3 — Dùng `git diff --find-renames` khi refactor làm Git nhìn như delete + add

**Mẹo:**
Khi một refactor lớn đổi tên hoặc di chuyển file, bật rename detection rõ ràng để review tập trung vào thay đổi thực sự thay vì đọc cả file như code mới.

**Tại sao hữu ích:**
Giảm noise trong code review và giúp phân biệt “file được move” với “logic bị rewrite”.

**Ví dụ:**
```bash
git diff --find-renames=50% origin/main...HEAD
```

Hoặc tăng độ nhạy:

```bash
git diff -M20% origin/main...HEAD
```

**Lưu ý:**
Threshold quá thấp có thể ghép nhầm hai file giống nhau thành rename. Với refactor lớn, vẫn nên tách move/rename và behavior change thành commit riêng khi có thể.

### Tip 4 — Dùng `ss -ltnp` để kiểm tra process nào thật sự đang listen port

**Mẹo:**
Khi service báo “port already in use” hoặc reverse proxy không connect được backend, dùng `ss` để xác nhận port nào đang listen và PID/process tương ứng.

**Tại sao hữu ích:**
Giúp phát hiện service cũ chưa shutdown, app bind nhầm interface hoặc container/host đang tranh cùng một port.

**Ví dụ:**
```bash
sudo ss -ltnp | grep ':8080'
```

Có thể xem toàn bộ TCP listening sockets:

```bash
sudo ss -ltnp
```

**Lưu ý:**
Port đang listen chưa đảm bảo application khỏe. Sau đó vẫn cần kiểm tra health endpoint, firewall, reverse proxy và network namespace nếu chạy container.

### Tip 5 — Dùng `ActivitySource` thay vì tự tạo correlation ID riêng cho từng subsystem

**Mẹo:**
Khi instrument distributed tracing trong .NET, dùng `ActivitySource` để span tham gia đúng trace context hiện có thay vì tự sinh ID custom cho từng layer.

**Tại sao hữu ích:**
Trace từ HTTP request → database → external API → background processing dễ nối lại trong OpenTelemetry backend và ít tạo correlation mechanism song song.

**Ví dụ:**
```csharp
private static readonly ActivitySource Source =
    new("Orders.Application");

using var activity = Source.StartActivity("ApproveOrder");
activity?.SetTag("order.id", orderId);

await handler.HandleAsync(cancellationToken);
```

**Lưu ý:**
Không tạo span cho mọi method nhỏ. Quá nhiều span tăng telemetry volume và làm trace khó đọc; ưu tiên operation có latency, dependency hoặc business significance rõ ràng.

## 🧠 Software Design

### Design 1 — Bulkhead theo resource pool, không chỉ theo service boundary

**Khái niệm:**
Bulkhead Isolation chia tài nguyên thành các pool độc lập để một workload không tiêu thụ hết capacity của workload khác. Boundary có thể là thread/concurrency slot, connection pool, queue hoặc worker group.

**Vấn đề nó giải quyết:**
Nếu report nặng, webhook retry và request interactive cùng dùng một resource pool, một loại workload spike có thể kéo toàn hệ thống xuống.

**Ví dụ thực tế:**
Một API có 100 DB connections. Thay vì để export job và user request dùng chung không giới hạn, export chỉ được phép chạy tối đa 10 concurrent queries còn interactive traffic giữ phần capacity còn lại.

**Trade-off:**
Bulkhead giảm blast radius và bảo vệ traffic quan trọng, nhưng capacity bị phân mảnh và có thể bị lãng phí nếu một pool idle trong khi pool khác quá tải.

**Middle → Senior insight:**
Middle developer nên hiểu isolation không chỉ là tách class/service. Senior developer cần xác định resource thực sự gây contention, sizing từng pool theo SLO và quyết định có cho phép borrow capacity hay không.

### Design 2 — Contract Test cho integration boundary giúp giảm phụ thuộc vào end-to-end test

**Khái niệm:**
Contract Test kiểm tra rằng consumer và provider cùng tuân theo một contract đã định nghĩa, tập trung vào boundary giữa service/API thay vì toàn bộ workflow xuyên nhiều hệ thống.

**Vấn đề nó giải quyết:**
End-to-end test thường chậm, flaky và khó xác định lỗi. Unit test lại không phát hiện provider đổi field, status code hoặc semantics mà consumer đang phụ thuộc.

**Ví dụ thực tế:**
`TimesheetService` phụ thuộc `EmployeeService` trả:

```json
{
  "employeeId": 123,
  "status": "Active"
}
```

Contract test bảo đảm provider vẫn trả field/type/status semantics mà consumer dùng, ngay cả khi implementation bên trong EmployeeService thay đổi.

**Trade-off:**
Contract test cho feedback nhanh và boundary rõ hơn, nhưng không thay thế integration test cho network/auth/database behavior thật. Nếu contract quá rộng, test suite lại trở thành coupling chặt giữa hai team.

**Middle → Senior insight:**
Middle developer nên hiểu contract test bảo vệ compatibility, không kiểm tra toàn hệ thống. Senior developer cần xác định contract tối thiểu, ownership, versioning và nơi nào vẫn cần integration/end-to-end coverage.

### Design 3 — State Machine rõ ràng tốt hơn boolean flags chồng chéo

**Khái niệm:**
Khi một entity có nhiều trạng thái và transition hợp lệ, mô hình hóa bằng state machine rõ ràng thường an toàn hơn nhiều boolean độc lập như `IsApproved`, `IsCancelled`, `IsProcessing`, `IsFailed`.

**Vấn đề nó giải quyết:**
Nhiều boolean dễ tạo tổ hợp vô nghĩa như `IsApproved=true` và `IsCancelled=true` cùng lúc, khiến validation bị rải khắp codebase.

**Ví dụ thực tế:**
Thay vì bốn flags cho export job, dùng:

```text
Pending → Running → Completed
              ↘ Failed
Pending → Cancelled
Running → Cancelling → Cancelled
```

Command handler chỉ cho phép transition hợp lệ theo state hiện tại.

**Trade-off:**
State machine làm invariant và workflow rõ hơn, nhưng thêm transition logic, migration state và đôi khi cần state history. Với object chỉ có hai trạng thái đơn giản, enum/state machine có thể là overkill.

**Middle → Senior insight:**
Middle developer nên nhận ra boolean explosion là dấu hiệu domain state chưa được mô hình hóa. Senior developer cần thiết kế transition, invalid transition behavior, concurrency/versioning và recovery path cho state bị kẹt.
