# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — EF Core projection giảm cả dữ liệu truyền lẫn change-tracking overhead

**Mẹo:**
Với read endpoint, project trực tiếp sang DTO bằng `Select` thay vì load nguyên entity graph rồi mới map trong memory. Kết hợp `AsNoTracking` khi không cần update entity.

**Tại sao hữu ích:**
Projection cho EF Core cơ hội sinh SQL chỉ lấy các cột cần thiết, giảm network payload, materialization và memory. Với entity có nhiều navigation/large columns, khác biệt có thể lớn hơn nhiều so với micro-optimization trong C#.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Total))
    .ToListAsync(ct);
```
Endpoint danh sách không cần load `OrderLines`, audit fields hoặc toàn bộ entity chỉ để trả ba trường.

**Lưu ý:**
Đừng thêm `AsNoTracking` theo thói quen vào flow cần modify entity sau đó. Đồng thời kiểm tra SQL thực tế: projection phức tạp hoặc expression không phù hợp vẫn có thể tạo query đắt.

### Tip 2 — MongoDB index phải đi theo query shape, không theo danh sách field “hay dùng”

**Mẹo:**
Thiết kế compound index từ filter + sort thực tế và kiểm tra bằng `explain`, thay vì tạo index riêng cho từng field rồi kỳ vọng database luôn ghép chúng tối ưu.

**Tại sao hữu ích:**
Thứ tự key trong compound index quyết định khả năng thu hẹp range và phục vụ sort. Một collection có đủ index đơn lẻ vẫn có thể scan/sort nhiều dữ liệu nếu query shape không khớp index.

**Ví dụ:**
Query thường xuyên lấy đơn hàng của tenant theo status và mới nhất trước:
```javascript
db.orders.find({ tenantId: t, status: "Paid" })
         .sort({ createdAt: -1 })
         .limit(50)
```
Một index như `{ tenantId: 1, status: 1, createdAt: -1 }` có thể phù hợp hơn ba index độc lập, nhưng phải xác minh theo cardinality và workload thật.

**Lưu ý:**
Mỗi index tăng storage và write amplification. Đừng tạo compound index cho mọi tổ hợp filter; theo dõi query patterns, selectivity và index usage rồi loại index dư thừa.

### Tip 3 — File upload phải kiểm tra nội dung và nơi lưu, không chỉ extension

**Mẹo:**
Với ASP.NET Core upload endpoint, giới hạn kích thước, tạo server-side filename, kiểm tra loại nội dung phù hợp với business rule và lưu file ngoài web root hoặc qua object storage có quyền truy cập kiểm soát.

**Tại sao hữu ích:**
Tên file, extension và `Content-Type` đều do client cung cấp nên không phải trust boundary. Lưu trực tiếp tên người dùng dưới thư mục public có thể dẫn tới overwrite, path issues hoặc phục vụ nội dung nguy hiểm ngoài ý muốn.

**Ví dụ:**
Avatar service nhận `.jpg`, nhưng backend vẫn áp size limit, decode/validate định dạng ảnh, sinh object key mới và upload vào Blob Storage private; client nhận URL/SAS theo authorization policy thay vì đường dẫn file vật lý.

**Lưu ý:**
Không đọc file lớn toàn bộ vào memory nếu có thể stream. Malware scanning, archive expansion và document parsing cần threat model riêng; “magic bytes đúng” không chứng minh file an toàn cho mọi downstream processor.

### Tip 4 — `git bisect` biến regression hunt thành tìm kiếm nhị phân

**Mẹo:**
Khi biết một commit cũ tốt và HEAD hiện tại lỗi, dùng `git bisect` cùng test/script tái hiện để tìm commit đầu tiên gây regression thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Binary search giảm số lần kiểm tra từ tuyến tính xuống logarithmic. Với 128 commits, về lý thuyết chỉ cần khoảng 7 bước phân loại good/bad nếu test deterministic.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test tests/Regression.Tests
```
Khi script trả exit code ổn định, Git có thể tự động thu hẹp commit gây lỗi.

**Lưu ý:**
Flaky test làm kết quả bisect sai. Build-breaking commits hoặc migration/environment dependency có thể cần `git bisect skip` hoặc script setup đáng tin cậy trước khi tự động hóa.

### Tip 5 — CMS cache key phải chứa đúng dimensions ảnh hưởng output

**Mẹo:**
Khi cache rendered content hoặc CMS API response, đưa vào cache key mọi dimension thực sự thay đổi output như content version/language/site/segment; đồng thời định nghĩa invalidation khi content được publish.

**Tại sao hữu ích:**
Cache key quá thô có thể trả nội dung tiếng Anh cho request tiếng Việt hoặc phục vụ bản cũ sau publish. Đây là correctness bug, không chỉ performance issue.

**Ví dụ:**
Thay vì `page:{contentId}`, một site đa ngôn ngữ có thể cần key theo `site + contentId + language + publishedVersion`, tùy content model. Publish event invalidates các entry liên quan thay vì chờ TTL dài một cách mù quáng.

**Lưu ý:**
Đưa quá nhiều dimensions vào key làm giảm hit ratio và tăng cardinality. Với personalization cao, full-page caching có thể không phù hợp; cân nhắc cache phần dữ liệu ổn định hơn hoặc CDN rules có chủ đích.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read/write thật sự có pressure khác nhau

**Khái niệm:**
CQRS tách model/flow xử lý command khỏi query để mỗi phía có thể tối ưu theo nhu cầu riêng. Nó không bắt buộc microservices, message broker hay hai database.

**Vấn đề nó giải quyết:**
Một domain có write model giàu invariants nhưng read screens cần projection phẳng, aggregate và search khác biệt có thể bị ép vào một model chung khó bảo trì hoặc kém hiệu quả.

**Ví dụ thực tế:**
Order command kiểm tra inventory/payment/state transition bằng domain model, trong khi dashboard đọc `OrderSummary` projection tối ưu cho filter và reporting. Ban đầu cả hai vẫn có thể dùng cùng SQL database và transaction boundary đơn giản.

**Trade-off:**
CQRS tăng số model, mapping và mental overhead; nếu read model được cập nhật bất đồng bộ còn xuất hiện eventual consistency. CRUD application nhỏ thường không nhận đủ lợi ích để bù complexity.

**Middle → Senior insight:**
Middle developer cần phân biệt command/query responsibility và không để query làm side effect. Senior / Technical developer phải chứng minh pressure khiến tách model có giá trị, chọn mức CQRS tối thiểu cần thiết và chỉ thêm asynchronous projection/separate store khi scale hoặc modeling requirement biện minh.

### Design 2 — Queue và Topic giải quyết hai kiểu ownership message khác nhau

**Khái niệm:**
Queue thường phân phối mỗi message cho một consumer trong nhóm competing consumers; Topic + subscriptions cho phép nhiều subscriber độc lập nhận cùng event theo subscription của mình.

**Vấn đề nó giải quyết:**
Một background job cần được xử lý một lần về mặt logical work khác với domain event cần kích hoạt nhiều capability độc lập. Dùng sai primitive có thể khiến hai service tranh cùng message hoặc tạo coupling bằng cách producer phải gửi nhiều bản sao thủ công.

**Ví dụ thực tế:**
`GenerateInvoicePdf` là work item phù hợp queue với nhiều worker cùng scale. `OrderPlaced` có thể đi qua topic để Billing, Fulfillment và Analytics có subscription riêng, retry/DLQ độc lập.

**Trade-off:**
Topic tăng fan-out, subscription management, duplicate handling và observability complexity. Queue đơn giản hơn khi chỉ có một logical processor. Cả hai vẫn cần xử lý at-least-once delivery và idempotency theo broker semantics.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumer, subscription, retry và DLQ. Senior / Technical developer phải phân loại command/work/event semantics, ownership và failure isolation trước khi chọn topology; tránh dùng pub/sub chỉ để “decouple” khi business thực tế yêu cầu một owner rõ ràng.

### Design 3 — Normalization và denormalization là trade-off giữa invariant và read cost

**Khái niệm:**
Normalization giảm duplication và giữ fact ở nơi có ownership rõ; denormalization chủ động sao chép/precompute dữ liệu để phục vụ read pattern hiệu quả hơn. Hai kỹ thuật không đối lập tuyệt đối và có thể cùng tồn tại trong một hệ thống.

**Vấn đề nó giải quyết:**
Schema chuẩn hóa cao bảo vệ consistency nhưng một số read path/report có thể cần nhiều joins hoặc aggregation đắt. Denormalization giảm read cost nhưng tạo bài toán đồng bộ khi source fact thay đổi.

**Ví dụ thực tế:**
Order giữ snapshot `ProductName` và `UnitPrice` tại thời điểm mua dù Catalog có product hiện tại riêng. Đây không chỉ là performance optimization: historical order cần bảo toàn fact giao dịch thay vì join sang giá/tên hiện tại.

**Trade-off:**
Duplicated data tăng storage và update complexity; normalized query có thể tăng join/latency. Denormalize tùy tiện làm ownership mơ hồ, còn normalize máy móc có thể khiến hot read path quá đắt.

**Middle → Senior insight:**
Middle developer cần hiểu constraints, keys và lý do dữ liệu nào là source of truth. Senior / Technical developer phải phân biệt historical snapshot với cache/read projection, đo read/write pressure và xác định consistency/invalidation strategy trước khi denormalize.
