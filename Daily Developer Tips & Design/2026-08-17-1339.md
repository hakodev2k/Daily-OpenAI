# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian

**Mẹo:**
Với .NET hiện đại, thay vì gọi trực tiếp `DateTime.UtcNow` khắp business logic, inject `TimeProvider` để code có thể kiểm soát thời gian trong test.

**Tại sao hữu ích:**
Giảm flaky test và giúp kiểm thử chính xác các tình huống như hết hạn token, timeout, grace period hoặc job chạy theo thời điểm.

**Ví dụ:**
```csharp
public sealed class SubscriptionService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

Trong test có thể dùng `FakeTimeProvider` để advance clock thay vì `Thread.Sleep()`.

**Lưu ý:**
Không cần abstraction thời gian cho mọi đoạn code. Chỉ nên áp dụng ở logic mà thời điểm hiện tại thực sự ảnh hưởng đến business behavior hoặc testability.

### Tip 2 — Dùng `EF.CompileAsyncQuery` cho hot query thật sự lặp lại nhiều

**Mẹo:**
Nếu profiling cho thấy cùng một LINQ query được thực thi rất thường xuyên, có thể cân nhắc compiled query để giảm chi phí compile expression/query pipeline của EF Core.

**Tại sao hữu ích:**
Trong high-throughput path, phần overhead nhỏ trên mỗi request có thể trở nên đáng kể khi query được gọi hàng chục nghìn lần.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<User>>
    GetUserById = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Users.Where(x => x.Id == id));
```

Sau đó:

```csharp
await foreach (var user in GetUserById(dbContext, userId))
{
    // use user
}
```

**Lưu ý:**
Đừng dùng compiled query theo thói quen. Với query không nằm trên hot path, complexity tăng thêm thường không đáng so với lợi ích hiệu năng.

### Tip 3 — Dùng `curl -v` hoặc `curl --trace-time` để phân biệt lỗi HTTP với lỗi mạng/TLS

**Mẹo:**
Khi API call thất bại ngoài production hoặc container, kiểm tra trực tiếp bằng `curl` từ đúng môi trường chạy application thay vì chỉ dựa vào exception message phía code.

**Tại sao hữu ích:**
Có thể nhanh chóng thấy DNS resolution, TCP connection, TLS handshake, proxy, redirect và HTTP headers — những thứ thường bị che khuất trong application logs.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Hoặc cần timestamp chi tiết:

```bash
curl --trace-time --trace - https://api.example.com/health
```

**Lưu ý:**
Trace có thể chứa Authorization header, cookie hoặc dữ liệu nhạy cảm. Không paste nguyên output vào ticket/chat nếu chưa kiểm tra và redact secrets.

### Tip 4 — Sắp xếp Dockerfile để tận dụng build cache

**Mẹo:**
Copy các file ít thay đổi như `.csproj` và restore dependency trước, rồi mới copy toàn bộ source code.

**Tại sao hữu ích:**
Khi chỉ code thay đổi nhưng dependencies không đổi, Docker có thể reuse layer restore thay vì chạy `dotnet restore` lại từ đầu.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY MyApp/*.csproj MyApp/
RUN dotnet restore MyApp/MyApp.csproj

COPY . .
RUN dotnet publish MyApp/MyApp.csproj -c Release -o /app/publish
```

**Lưu ý:**
Cache chỉ hiệu quả nếu build context và thứ tự `COPY` hợp lý. Một `COPY . .` quá sớm sẽ invalidate nhiều layer mỗi khi source thay đổi.

### Tip 5 — Khi dùng AI review code, đưa diff và acceptance criteria thay vì cả repository không mục tiêu

**Mẹo:**
Với AI coding tool, hãy cung cấp `git diff`, mục tiêu thay đổi, invariant quan trọng và các test liên quan trước khi yêu cầu review.

**Tại sao hữu ích:**
Context nhỏ nhưng đúng trọng tâm giúp model phát hiện regression, missing validation, race condition hoặc edge case tốt hơn so với việc yêu cầu “review toàn bộ code”.

**Ví dụ:**
```bash
git diff main...HEAD -- src/ tests/
```

Prompt ngắn có thể tập trung vào:

```text
Review this diff for correctness, concurrency issues, backward compatibility,
and missing tests. Requirement: retries must never create duplicate invoices.
```

**Lưu ý:**
AI review không thay thế test, static analysis hay human judgment. Luôn xác minh các nhận xét quan trọng bằng code, documentation hoặc reproduction thực tế.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation để giới hạn blast radius

**Khái niệm:**
Bulkhead Isolation chia tài nguyên như thread, connection, queue hoặc concurrency limit theo workload để một dependency chậm không chiếm hết capacity của hệ thống.

**Vấn đề nó giải quyết:**
Nếu tất cả outbound calls dùng chung một pool không giới hạn, một service downstream bị treo có thể làm request tích tụ cho đến khi toàn bộ application cạn connection, memory hoặc thread-pool capacity.

**Ví dụ thực tế:**
Một API gọi `PaymentService`, `SearchService` và `NotificationService`. `SearchService` đôi lúc latency tăng 30 giây. Thay vì để search requests chiếm toàn bộ concurrency, hệ thống giới hạn tối đa 20 concurrent calls cho search và fail fast phần còn lại.

**Trade-off:**
Lợi ích là failure được cô lập và hệ thống còn capacity cho workload quan trọng. Chi phí là phải chọn limit hợp lý; limit quá thấp gây reject khi hệ thống vẫn còn tài nguyên, limit quá cao lại mất tác dụng isolation.

**Middle → Senior insight:**
Middle developer nên hiểu timeout/retry không đủ để chống resource exhaustion. Senior developer cần thiết kế concurrency budget theo dependency, priority, throughput và failure mode, đồng thời theo dõi saturation bằng metrics.

### Design 2 — Cohesion cao quan trọng hơn việc tạo nhiều layer

**Khái niệm:**
High cohesion nghĩa là các thành phần trong một module cùng phục vụ một responsibility hoặc business capability rõ ràng. Low coupling nghĩa là module ít phụ thuộc không cần thiết vào internals của module khác.

**Vấn đề nó giải quyết:**
Một codebase có nhiều layer vẫn có thể khó maintain nếu logic của một feature bị rải qua hàng chục service/helper/repository không liên quan về mặt domain.

**Ví dụ thực tế:**
Feature `LeaveApproval` có policy, validation, command handler và persistence logic liên quan chặt chẽ. Đặt chúng gần nhau theo module thường dễ thay đổi hơn việc chia toàn hệ thống thành các folder `Services`, `Validators`, `Repositories`, `Helpers` chung.

**Trade-off:**
Feature-oriented grouping tăng local reasoning và ownership nhưng có thể tạo một ít duplication hoặc conventions riêng giữa module. Layer-oriented organization nhìn đồng nhất hơn ban đầu nhưng thường tăng navigation cost khi hệ thống lớn.

**Middle → Senior insight:**
Middle developer nên nhìn dependency direction và responsibility thay vì chỉ theo folder convention. Senior developer phải nhận ra boundary nào giúp thay đổi một capability mà ít kéo theo ripple effect nhất.

### Design 3 — Observability Design: kiểm soát metric cardinality ngay từ đầu

**Khái niệm:**
Observability không chỉ là thêm logs và metrics; metric labels/tags phải được thiết kế sao cho cardinality có giới hạn và phục vụ câu hỏi vận hành cụ thể.

**Vấn đề nó giải quyết:**
Nếu đưa `UserId`, `RequestId`, full URL hoặc exception message làm metric label, số series có thể tăng cực lớn, khiến monitoring backend tốn memory/storage và query chậm hoặc rất đắt.

**Ví dụ thực tế:**
Thay vì:

```text
http_requests_total{user_id="123456", path="/orders/98765"}
```

nên dùng dimension có bounded cardinality:

```text
http_requests_total{method="GET", route="/orders/{id}", status_code="200"}
```

Thông tin request-specific như `RequestId` nên nằm trong logs/traces, không phải metric labels.

**Trade-off:**
Metrics ít dimension hơn giúp hệ thống monitoring ổn định và rẻ hơn nhưng giảm khả năng drill-down trực tiếp. Khi cần điều tra chi tiết, phải correlate metrics với logs hoặc distributed traces.

**Middle → Senior insight:**
Middle developer nên phân biệt metrics, logs và traces dùng cho loại câu hỏi nào. Senior developer cần thiết kế telemetry schema, cardinality budget, retention và correlation strategy trước khi traffic tăng lớn.
