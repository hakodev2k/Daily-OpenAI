# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `required` members trong C# để tránh object thiếu dữ liệu

**Mẹo:**
Sử dụng `required` khi một property bắt buộc phải được khởi tạo.

**Tại sao hữu ích:**
Giảm lỗi runtime do object ở trạng thái không hợp lệ.

**Ví dụ:**
```csharp
public class CreateUserRequest
{
    public required string Email { get; init; }
    public required string Name { get; init; }
}
```

**Lưu ý:**
Không nên dùng cho mọi property; các giá trị optional vẫn nên để nullable hoặc có default.

### Tip 2 — Kiểm tra SQL execution plan trước khi tối ưu query

**Mẹo:**
Dùng Actual Execution Plan trong SQL Server để tìm Index Scan, Key Lookup hoặc Sort không cần thiết.

**Tại sao hữu ích:**
Giúp tối ưu dựa trên nguyên nhân thực tế thay vì đoán.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SELECT * FROM Orders WHERE CustomerId = 100;
```

**Lưu ý:**
Không thêm index chỉ vì một query chậm; cần xem workload tổng thể.

### Tip 3 — Dùng structured logging thay vì nối chuỗi message

**Mẹo:**
Truyền parameter trực tiếp vào logger để giữ dữ liệu có cấu trúc.

**Tại sao hữu ích:**
Log dễ tìm kiếm trong Application Insights, Seq hoặc ELK.

**Ví dụ:**
```csharp
_logger.LogInformation("Order {OrderId} created for {CustomerId}", order.Id, customer.Id);
```

**Lưu ý:**
Không ghi dữ liệu nhạy cảm như token, password hoặc PII.

### Tip 4 — Sử dụng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Dùng binary search của Git khi biết hiện tại lỗi nhưng không biết commit nào tạo ra nó.

**Tại sao hữu ích:**
Giảm thời gian debug regression trong codebase lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.2.0
```

**Lưu ý:**
Cần có cách test rõ ràng để xác định commit good/bad.

### Tip 5 — Thiết kế API error response thống nhất

**Mẹo:**
Định nghĩa một format lỗi chung cho toàn bộ REST API.

**Tại sao hữu ích:**
Client dễ xử lý lỗi, logging và monitoring nhất quán hơn.

**Ví dụ:**
```json
{
  "code": "VALIDATION_ERROR",
  "message": "Email is required",
  "traceId": "abc123"
}
```

**Lưu ý:**
Không expose exception detail nội bộ ra client production.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Application Design

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một thao tác nguyên tử.

**Vấn đề nó giải quyết:**
Tránh trạng thái dữ liệu không nhất quán khi nhiều bước nghiệp vụ thất bại giữa chừng.

**Ví dụ thực tế:**
Thanh toán đơn hàng gồm tạo payment record, cập nhật order status và trừ inventory. Các bước liên quan cần được thiết kế transaction hợp lý.

**Trade-off:**
Transaction lớn tăng consistency nhưng có thể giảm performance và gây lock lâu hơn.

**Middle → Senior insight:**
Middle cần biết cách dùng transaction. Senior cần quyết định đâu là business operation thực sự cần atomicity và đâu nên tách thành workflow/event.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia hệ thống thành các module có boundary rõ ràng nhưng vẫn deploy cùng một application.

**Vấn đề nó giải quyết:**
Giảm coupling trong codebase mà không phải trả toàn bộ chi phí của distributed system.

**Ví dụ thực tế:**
Một hệ thống quản lý doanh nghiệp có module Employee, Payroll, Notification với domain model và dependency riêng.

**Trade-off:**
Đơn giản vận hành hơn microservices nhưng cần kỷ luật để giữ module không phụ thuộc chéo.

**Middle → Senior insight:**
Middle nên tập trung vào boundary và dependency. Senior cần đánh giá khi nào scale team, deployment và ownership mới thực sự cần microservices.

### Design 3 — Idempotency trong Distributed System

**Khái niệm:**
Idempotency đảm bảo một request thực hiện nhiều lần vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Xử lý retry, timeout và duplicate message trong hệ thống phân tán.

**Ví dụ thực tế:**
API tạo payment sử dụng `Idempotency-Key` để tránh charge khách hàng hai lần khi client retry.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và thiết kế storage phù hợp.

**Middle → Senior insight:**
Middle cần hiểu retry có thể gây duplicate. Senior cần thiết kế toàn bộ flow gồm API, database, queue và failure recovery.
