# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian mà không `Thread.Sleep`

**Mẹo:**
Với .NET 8+, inject `TimeProvider` vào service có logic timeout, expiry hoặc scheduling thay vì gọi trực tiếp `DateTime.UtcNow`. Trong test, dùng fake time provider để điều khiển clock một cách deterministic.

**Tại sao hữu ích:**
Code đọc system clock trực tiếp tạo hidden dependency và khiến test expiration/retry phải chờ thời gian thật hoặc mock bằng abstraction tự chế. `TimeProvider` biến thời gian thành dependency rõ ràng, giúp test nhanh và tránh flaky test do clock boundary.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        timeProvider.GetUtcNow() >= expiresAt;
}
```

Production inject `TimeProvider.System`; test có thể advance clock tới đúng boundary cần kiểm tra.

**Lưu ý:**
Không phải mọi timestamp đều nên lấy từ application clock. Database-generated timestamp hoặc event timestamp từ upstream có semantics khác. Cần xác định nguồn thời gian nào là authoritative cho từng invariant.

### Tip 2 — EF Core projection giúp tránh tracking và materialization thừa ở read endpoint

**Mẹo:**
Với endpoint chỉ cần vài field để trả DTO, project trực tiếp bằng `Select` thay vì `Include` cả aggregate rồi map trong memory.

**Tại sao hữu ích:**
Projection cho phép EF Core sinh SQL chỉ lấy column cần thiết, giảm network payload, allocation và change-tracking overhead. Nó cũng tránh cartesian explosion khi `Include` nhiều collection chỉ để lấy một vài giá trị tổng hợp.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.CreatedAt,
        x.Total,
        x.Items.Count))
    .Take(20)
    .ToListAsync(ct);
```

Kiểm tra SQL generated và execution plan nếu projection chứa expression phức tạp.

**Lưu ý:**
Projection không thay thế domain aggregate khi use case cần enforce invariant và update state. Đừng biến mọi business command thành DTO-centric query/update chỉ để giảm allocation.

### Tip 3 — Dùng `AbortController` cho search-as-you-type để loại request obsolete ở frontend

**Mẹo:**
Trong Vue.js hoặc JavaScript/TypeScript frontend, hủy request cũ khi keyword thay đổi thay vì để mọi request search chạy tới completion.

**Tại sao hữu ích:**
Nếu user gõ `lap` rồi nhanh chóng thành `laptop`, response cho `lap` có thể về sau response `laptop` và ghi đè UI bằng kết quả cũ. Cancellation vừa giảm network/backend work vừa ngăn stale response race.

**Ví dụ:**
```ts
let controller: AbortController | undefined

async function search(term: string) {
  controller?.abort()
  controller = new AbortController()

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  })

  return response.json()
}
```

Có thể kết hợp debounce để giảm request khi user vẫn đang gõ.

**Lưu ý:**
Abort phía client không đảm bảo server đã dừng mọi side effect. Search GET thường an toàn, nhưng command endpoint vẫn cần idempotency/cancellation semantics ở backend.

### Tip 4 — Dùng `git bisect` khi regression có khoảng commit đủ lớn

**Mẹo:**
Nếu biết một commit cũ hoạt động tốt và HEAD hiện tại bị regression, dùng `git bisect` để binary-search commit gây lỗi thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Với 128 commit nghi vấn, binary search chỉ cần khoảng 7 lần phân loại good/bad. Nếu có test hoặc script tái hiện lỗi, `git bisect run` còn có thể tự động hóa toàn bộ quá trình tìm culprit.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests
```

Khi hoàn tất:
```bash
git bisect reset
```

**Lưu ý:**
Bisect hiệu quả khi mỗi commit trong khoảng có thể build/test đủ ổn định. Nếu lịch sử chứa nhiều commit broken hoặc test nondeterministic, kết quả có thể nhiễu; lúc đó cần script phân loại tốt hơn hoặc thu hẹp range trước.

### Tip 5 — Phân biệt liveness và readiness để deployment không tự tạo outage

**Mẹo:**
Trong Kubernetes hoặc orchestrated deployment, liveness chỉ nên trả lời “process có cần restart không?”, còn readiness trả lời “instance hiện có nhận traffic được không?”. Không đưa mọi dependency bên ngoài vào liveness probe.

**Tại sao hữu ích:**
Nếu database tạm thời unavailable và liveness phụ thuộc database, toàn bộ pod có thể bị restart liên tục đúng lúc dependency đang yếu, tạo restart storm. Readiness có thể tạm rút pod khỏi traffic mà không giết process.

**Ví dụ:**
```text
/health/live
- process/event loop còn hoạt động

/health/ready
- startup hoàn tất
- critical local initialization OK
- service đủ điều kiện nhận traffic
```

Một dependency outage nên được xử lý bằng resilience/traffic policy phù hợp, không mặc định bằng process restart.

**Lưu ý:**
Readiness quá strict cũng có thể rút toàn bộ replica khỏi load balancer cùng lúc. Probe phải phản ánh khả năng phục vụ thực tế và phối hợp với timeout, failure threshold, rolling update strategy.

## 🧠 Software Design

### Design 1 — Outbox Pattern giữ database change và event publication nhất quán hơn

**Khái niệm:**
Outbox Pattern ghi business change và record cần publish vào cùng local database transaction. Một publisher riêng sau đó đọc outbox và gửi message tới broker, thay vì cố commit database rồi publish message như hai operation độc lập.

**Vấn đề nó giải quyết:**
`SaveChanges()` có thể thành công nhưng process crash trước khi gửi `OrderCreated`; hoặc message được gửi thành công nhưng database transaction rollback. Dual-write như vậy tạo trạng thái mà database và message broker không đồng thuận.

**Ví dụ thực tế:**
```text
Transaction SQL:
1. INSERT Order
2. INSERT OutboxMessage(OrderCreated)
3. COMMIT

Publisher:
4. đọc pending OutboxMessage
5. publish Service Bus
6. đánh dấu published
```

Consumer vẫn phải idempotent vì publisher có thể gửi lại message nếu crash sau bước 5 nhưng trước bước 6.

**Trade-off:**
Outbox giảm dual-write inconsistency nhưng thêm table, polling/CDC publisher, cleanup và delivery latency. Nó không tạo exactly-once end-to-end; duplicate delivery vẫn phải được xử lý. Với workflow đơn giản không cần event integration, thêm Outbox có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu transaction database không bao phủ message broker và phải thiết kế publisher có retry an toàn. Senior / Technical developer phải quyết định outbox boundary, ordering, retention, throughput, failure recovery và liệu polling, CDC hay broker-native integration phù hợp hơn với operational constraints.

### Design 2 — Optimistic Concurrency phù hợp khi conflict hiếm nhưng mất update là không chấp nhận được

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng dữ liệu mà không giữ lock dài, nhưng khi update sẽ kiểm tra version/concurrency token để phát hiện dữ liệu đã bị thay đổi kể từ lúc đọc.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng mở Customer record version 12. Người A đổi email và save; người B vẫn giữ snapshot cũ rồi đổi address. Nếu B update toàn row mà không kiểm tra version, thay đổi email của A có thể bị ghi đè âm thầm.

**Ví dụ thực tế:**
```text
A reads Version=12
B reads Version=12
A updates -> Version=13
B updates WHERE Version=12
-> affected rows = 0
-> concurrency conflict
```

Trong EF Core có thể dùng `rowversion`/concurrency token và xử lý `DbUpdateConcurrencyException` theo business semantics.

**Trade-off:**
Optimistic concurrency tránh lock contention khi conflict hiếm, nhưng application phải có UX/retry/merge policy khi conflict xảy ra. Auto-retry command không phải lúc nào cũng đúng vì business decision có thể dựa trên snapshot cũ. Khi contention rất cao và operation cần serialization chặt, pessimistic locking hoặc thiết kế invariant khác có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần phát hiện và xử lý conflict thay vì swallow exception hoặc retry mù. Senior / Solution-oriented engineer phải xác định aggregate/invariant nào cần concurrency control, conflict nào có thể merge, conflict nào phải trả user và khi nào database constraint là lớp bảo vệ cuối cùng tốt hơn application check.

### Design 3 — Bulkhead Isolation giới hạn blast radius giữa các workload dùng chung service

**Khái niệm:**
Bulkhead Isolation chia capacity thành các pool hoặc quota độc lập để một workload quá tải không tiêu hết tài nguyên của workload khác. Boundary có thể nằm ở worker pool, queue, connection budget, concurrency limiter hoặc deployment riêng.

**Vấn đề nó giải quyết:**
Một API vừa xử lý checkout realtime vừa chạy export/report nặng. Nếu export tạo hàng trăm query dài và chiếm hết database connections/CPU, checkout có thể timeout dù business flow của nó hoàn toàn khỏe mạnh.

**Ví dụ thực tế:**
```text
Checkout requests
-> concurrency budget 80
-> latency-sensitive path

Report jobs
-> queue
-> worker concurrency 8
-> riêng timeout/resource budget
```

Nếu report tiếp tục backlog, checkout vẫn giữ được capacity tối thiểu.

**Trade-off:**
Bulkhead giảm blast radius nhưng capacity bị phân mảnh: pool A có thể idle trong khi pool B đang thiếu tài nguyên. Tách deployment còn tăng infrastructure và observability cost. Với hệ thống nhỏ, một global bounded concurrency policy có thể đủ thay vì nhiều pool phức tạp.

**Middle → Senior insight:**
Middle developer cần nhận diện unbounded concurrency và workload cạnh tranh tài nguyên. Senior / Technical developer phải chọn isolation boundary dựa trên SLO, criticality và bottleneck thật; sizing pool theo load test/telemetry và tránh tạo isolation giả khi tất cả pool cuối cùng vẫn tranh cùng một downstream bottleneck.
