# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup read-only được xây một lần, đọc rất nhiều lần

**Mẹo:**
Nếu application tạo một tập dữ liệu lookup ở startup rồi chỉ đọc trong suốt vòng đời process, cân nhắc `FrozenDictionary<TKey,TValue>` hoặc `FrozenSet<T>` trong modern .NET thay vì giữ một `Dictionary` mutable không bao giờ thay đổi.

**Tại sao hữu ích:**
Các collection “frozen” tối ưu cấu trúc nội bộ cho read-heavy workload sau khi construction hoàn tất. Chúng giúp thể hiện rõ intent bất biến và có thể giảm overhead lookup trong hot path so với collection tổng quát phải hỗ trợ mutation.

**Ví dụ:**
```csharp
private static readonly FrozenDictionary<string, int> CountryCodes =
    new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase)
    {
        ["VN"] = 84,
        ["US"] = 1,
        ["JP"] = 81
    }.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);

var code = CountryCodes["vn"];
```

Phù hợp với metadata, routing table nhỏ, mapping code hoặc rule lookup được build một lần.

**Lưu ý:**
Đừng dùng chỉ vì nghe “nhanh hơn”. Construction có chi phí và collection không phù hợp khi dữ liệu thay đổi thường xuyên. Với lookup nhỏ hoặc không nằm trên hot path, `Dictionary` bình thường có thể đơn giản hơn và đủ tốt.

### Tip 2 — Với ASP.NET Core, tránh sync I/O trong request body/response path

**Mẹo:**
Khi đọc upload, ghi response hoặc xử lý stream trong ASP.NET Core, ưu tiên API async như `ReadAsync`, `CopyToAsync`, `WriteAsync` thay vì thao tác synchronous trên stream trong request path.

**Tại sao hữu ích:**
Sync I/O giữ worker thread bị block cho tới khi I/O hoàn tất. Dưới tải cao, nhiều thao tác kiểu này có thể giảm throughput và góp phần gây ThreadPool pressure ngay cả khi bản thân từng request không quá chậm.

**Ví dụ:**
```csharp
await using var destination = File.Create(tempPath);
await request.Body.CopyToAsync(destination, cancellationToken);
```

Với file lớn, xử lý theo stream còn giúp tránh việc đọc toàn bộ payload vào memory trước khi ghi.

**Lưu ý:**
Async I/O không đồng nghĩa “buffer vô hạn là an toàn”. Vẫn cần giới hạn request size, timeout/cancellation, validation file và capacity control. Nếu thao tác tiếp theo là CPU-bound nặng, async chỉ giải quyết phần chờ I/O chứ không giảm chi phí CPU.

### Tip 3 — Dùng keyset pagination khi offset lớn bắt đầu làm SQL chậm

**Mẹo:**
Với danh sách lớn được sort ổn định, cân nhắc keyset/seek pagination thay cho `OFFSET ... FETCH` ở các page sâu. Query tiếp tục từ giá trị sort cuối cùng của page trước thay vì yêu cầu database bỏ qua hàng chục nghìn row.

**Tại sao hữu ích:**
Offset pagination thường phải scan hoặc walk qua các row trước offset dù cuối cùng không trả chúng về. Chi phí vì thế tăng theo page number. Keyset pagination biến query thành range seek trên index phù hợp và thường giữ latency ổn định hơn.

**Ví dụ:**
```sql
SELECT TOP (50)
    Id, CreatedAt, Total
FROM Orders
WHERE
    CreatedAt < @lastCreatedAt
    OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index nên phù hợp với thứ tự sort, ví dụ `(CreatedAt DESC, Id DESC)` tùy database và workload.

**Lưu ý:**
Keyset pagination không hỗ trợ tự nhiên việc nhảy trực tiếp tới “page 137”. Sort key phải deterministic và thường cần tie-breaker unique như `Id`. Nếu business requirement bắt buộc random page access, offset vẫn có thể cần thiết.

### Tip 4 — Dùng browser DevTools waterfall để tìm JavaScript đang chặn Critical Rendering Path

**Mẹo:**
Khi trang có Largest Contentful Paint hoặc First Contentful Paint xấu, mở Network/Performance panel và xem waterfall trước khi tối ưu backend một cách cảm tính. Tập trung vào render-blocking CSS, JavaScript tải sớm, request chain và tài nguyên lớn nằm trước nội dung chính.

**Tại sao hữu ích:**
Một trang có backend response 150 ms vẫn có thể mất vài giây mới render nội dung chính nếu browser phải tải bundle lớn, parse script, chờ font hoặc thực hiện nhiều request nối tiếp. Waterfall cho thấy dependency thực tế theo thời gian thay vì chỉ nhìn tổng page load.

**Ví dụ:**
```text
HTML                 120 ms
  -> main.css         280 ms
  -> app.js           1.4 s
      -> config API   350 ms
          -> hero API 420 ms

LCP image chỉ bắt đầu tải sau ~2.1 s
```

Một hướng sửa có thể là preload/LCP image, defer script không critical hoặc phá request chain nếu semantics cho phép.

**Lưu ý:**
Không tối ưu chỉ theo một lần đo trên máy local nhanh. Dùng throttling, production build, real-user metrics hoặc Lighthouse/Web Vitals data khi có. Đừng defer script làm hỏng hydration, analytics consent hoặc behavior cần chạy sớm.

### Tip 5 — Với Azure Service Bus, handler dài phải hiểu `PeekLock` và lock renewal

**Mẹo:**
Nếu message handler có thể chạy lâu hơn lock duration, thiết kế processing time, automatic lock renewal hoặc chia nhỏ work rõ ràng. Đừng giả định nhận được message nghĩa là broker sẽ giữ nó độc quyền cho tới khi code kết thúc.

**Tại sao hữu ích:**
Trong `PeekLock`, consumer nhận message nhưng message chỉ bị khóa tạm thời. Nếu lock hết hạn trước khi `Complete`, message có thể được giao lại cho consumer khác trong khi handler đầu tiên vẫn đang chạy, tạo duplicate processing.

**Ví dụ:**
```text
Lock duration: 60s
Handler:
- tải file: 20s
- gọi external API: 50s
- ghi DB: 10s

Tổng: 80s
-> lock có thể hết hạn trước Complete
-> message bị redeliver
```

Giải pháp có thể là renewal phù hợp, giảm thời gian handler, chuyển long-running work sang workflow khác hoặc checkpoint/idempotency rõ ràng.

**Lưu ý:**
Lock renewal không loại bỏ duplicate delivery do crash, network partition hoặc broker redelivery. Consumer vẫn phải idempotent. Đừng giữ lock rất lâu chỉ để che một workflow vốn nên được chia thành các bước nhỏ hơn.

## 🧠 Software Design

### Design 1 — Inbox Pattern giúp consumer xử lý message theo semantics idempotent

**Khái niệm:**
Inbox Pattern lưu dấu vết message đã xử lý, thường dựa trên `MessageId` hoặc business operation key, trong cùng transaction với side effect local. Khi broker redeliver cùng message, consumer nhận ra nó đã được xử lý và không lặp lại tác động nghiệp vụ.

**Vấn đề nó giải quyết:**
Hệ thống messaging thực tế thường là at-least-once. Consumer có thể ghi database thành công nhưng crash trước khi acknowledge message. Broker sau đó giao lại message và nếu handler không có deduplication, invoice có thể được tạo hai lần hoặc điểm thưởng bị cộng hai lần.

**Ví dụ thực tế:**
```text
Transaction:
1. kiểm tra InboxMessages(messageId)
2. nếu chưa có -> áp dụng business change
3. INSERT InboxMessages(messageId, processedAt)
4. COMMIT
5. Complete message

Nếu redelivery:
- messageId đã tồn tại
- bỏ qua side effect
- Complete message
```

**Trade-off:**
Inbox tăng độ an toàn nhưng thêm storage, cleanup/retention policy và lookup trên mỗi message. Message identity phải ổn định; nếu producer tạo ID mới cho cùng logical operation, deduplication theo transport ID sẽ không đủ.

**Middle → Senior insight:**
Middle developer cần biết handler messaging phải chịu duplicate delivery. Senior / Technical developer phải chọn deduplication key, transaction boundary, retention window và cách phối hợp Inbox với business uniqueness constraint thay vì chỉ thêm một bảng “ProcessedMessages”.

### Design 2 — Circuit Breaker dùng để ngăn tiếp tục gọi dependency đang lỗi, không thay thế Retry

**Khái niệm:**
Circuit Breaker theo dõi failure của dependency và tạm thời “mở mạch” để fail fast sau khi lỗi vượt threshold. Sau một khoảng thời gian, hệ thống thử lại có kiểm soát để xem dependency đã phục hồi chưa.

**Vấn đề nó giải quyết:**
Một external API đang timeout 10 giây. Nếu mọi request vẫn tiếp tục gọi và mỗi request retry ba lần, hệ thống có thể giữ hàng nghìn operation đang chờ, làm cạn thread/socket/concurrency budget và lan sự cố sang chính service của mình.

**Ví dụ thực tế:**
```text
Payment provider:
- timeout: 2s
- retry: chỉ lỗi transient, tối đa 1 lần
- circuit breaker: mở sau failure rate vượt threshold

Circuit OPEN:
- request mới fail fast hoặc dùng fallback
- không tiếp tục đập dependency đang lỗi
```

**Trade-off:**
Circuit breaker giảm blast radius nhưng có thể từ chối request trong lúc dependency vừa phục hồi. Threshold và break duration đặt sai có thể tạo oscillation hoặc làm outage kéo dài ở phía client. Fallback cũng không phải lúc nào có nghĩa nghiệp vụ hợp lệ.

**Middle → Senior insight:**
Middle developer cần phân biệt timeout, retry và circuit breaker là ba cơ chế khác nhau. Senior / Technical developer phải thiết kế chúng như một resilience policy thống nhất dựa trên idempotency, SLO, dependency capacity và business consequence của fail-fast/fallback.

### Design 3 — Multi-tenancy: shared schema đơn giản hơn nhưng tenant isolation phải là invariant kiến trúc

**Khái niệm:**
Một SaaS có thể lưu nhiều tenant trong cùng database/schema bằng `TenantId`, tách schema theo tenant hoặc tách database riêng. Shared schema thường có chi phí vận hành thấp nhất nhưng isolation phụ thuộc mạnh vào application và data-access discipline.

**Vấn đề nó giải quyết:**
Hệ thống cần phục vụ hàng trăm tenant với cùng codebase. Tạo database riêng cho từng tenant có thể tăng isolation nhưng cũng tăng migration, connection, backup và operational overhead; shared schema dễ vận hành hơn nhưng rủi ro cross-tenant data leak cao hơn nếu một query quên filter.

**Ví dụ thực tế:**
```text
Shared schema:
Orders(Id, TenantId, ...)
Customers(Id, TenantId, ...)

Invariant:
- mọi aggregate/query thuộc tenant đều gắn TenantId
- unique constraint thường bao gồm TenantId
- authorization và data filtering cùng bảo vệ boundary
- integration test có case cross-tenant access
```

Có thể bổ sung global query filter hoặc database-level row security tùy stack, nhưng vẫn cần review escape hatch và raw SQL.

**Trade-off:**
Shared schema tiết kiệm chi phí và scale tenant count tốt nhưng blast radius lớn hơn và noisy-neighbor khó kiểm soát. Database-per-tenant tăng isolation, backup/restore độc lập nhưng làm deployment, migrations và connection management phức tạp đáng kể.

**Middle → Senior insight:**
Middle developer cần coi `TenantId` là security boundary chứ không chỉ field filter. Senior / Solution-oriented engineer phải chọn tenancy model dựa trên compliance, data residency, tenant size, restore requirement, noisy-neighbor risk và operational maturity — không chỉ dựa trên “kiến trúc sạch”.
