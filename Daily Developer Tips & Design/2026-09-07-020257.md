# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Tách timeout khỏi cancellation trong ASP.NET Core

**Mẹo:**
Phân biệt rõ timeout do hệ thống áp đặt và cancellation do caller chủ động hủy. Khi gọi downstream API, thường nên tạo timeout riêng rồi liên kết với `HttpContext.RequestAborted` thay vì dùng một `CancellationToken` cho mọi nguyên nhân.

**Tại sao hữu ích:**
Hai tín hiệu này có semantics khác nhau. Request bị client ngắt, application shutdown và downstream timeout cần được quan sát, log và xử lý khác nhau. Nếu gom tất cả thành một `OperationCanceledException`, production diagnostics sẽ khó xác định nguyên nhân thật.

**Ví dụ:**
```csharp
using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(3));
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    HttpContext.RequestAborted,
    timeoutCts.Token);

var response = await httpClient.GetAsync(
    "/inventory/42",
    linkedCts.Token);
```

Khi timeout xảy ra, log riêng trạng thái `timeoutCts.IsCancellationRequested` để phân biệt với client disconnect.

**Lưu ý:**
Không retry mù quáng mọi `OperationCanceledException`. Nếu caller đã hủy request thì retry chỉ tạo thêm tải vô ích.

### Tip 2 — Projection trước, Include sau trong EF Core

**Mẹo:**
Với read-only API, ưu tiên projection trực tiếp sang DTO bằng `Select` trước khi nghĩ tới `Include`. Chỉ tải đúng cột và quan hệ thực sự cần trả về.

**Tại sao hữu ích:**
`Include` dễ làm query phình to, tạo nhiều row do join và tăng allocation khi materialize entity graph. Projection giúp EF Core sinh SQL sát với contract của endpoint hơn và thường giảm memory, network payload và change-tracking overhead.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.CreatedAt,
        x.Total,
        x.Items.Count))
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Projection không tự động tốt hơn trong mọi trường hợp. Nếu domain operation thực sự cần đầy đủ aggregate để thay đổi state thì entity loading vẫn phù hợp hơn DTO projection.

### Tip 3 — Dùng keyset pagination cho bảng lớn thay vì OFFSET sâu

**Mẹo:**
Với danh sách lớn và sort ổn định, ưu tiên keyset pagination dựa trên khóa cuối cùng đã đọc thay vì `OFFSET ... FETCH` ở các trang sâu.

**Tại sao hữu ích:**
`OFFSET` buộc database bỏ qua ngày càng nhiều row khi page number tăng. Keyset pagination dùng predicate có thể tận dụng index tốt hơn, nên latency ổn định hơn khi dataset lớn.

**Ví dụ:**
```sql
SELECT TOP (50)
    Id, CreatedAt, Total
FROM Orders
WHERE
    CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)`.

**Lưu ý:**
Keyset pagination không phù hợp khi UX bắt buộc nhảy trực tiếp tới “page 125”. Nó hoạt động tốt nhất với next/previous hoặc infinite scroll.

### Tip 4 — Đừng debug production chỉ bằng log message; dùng correlation và distributed tracing

**Mẹo:**
Mỗi inbound request nên có correlation context xuyên qua outbound HTTP, queue/message và background processing. Với .NET, ưu tiên `Activity` / OpenTelemetry-compatible tracing thay vì tự nối chuỗi ID thủ công ở mọi layer.

**Tại sao hữu ích:**
Khi một API chậm, log riêng lẻ chỉ cho thấy symptom cục bộ. Trace cho phép đi theo toàn bộ critical path để xác định latency nằm ở database, HTTP dependency, Service Bus consumer hay internal processing.

**Ví dụ:**
Một request có p95 tăng từ 300 ms lên 2.4 s. Trace cho thấy:
- API processing: 80 ms
- SQL: 120 ms
- external pricing API: 2.1 s

Khi đó hypothesis chuyển từ “backend code chậm” sang “external dependency latency”.

**Lưu ý:**
Không log token, password, PII hoặc request body nhạy cảm chỉ để tăng observability. Telemetry phải được thiết kế cùng security và data-retention policy.

### Tip 5 — Dùng `git bisect` khi regression xuất hiện sau nhiều commit

**Mẹo:**
Khi biết một commit/tag tốt và một commit xấu, dùng `git bisect` để binary-search commit gây regression thay vì review tuần tự hàng chục commit.

**Tại sao hữu ích:**
Với 128 commit, binary search lý thuyết chỉ cần khoảng 7 vòng kiểm tra. Đây là kỹ thuật đặc biệt hữu ích với performance regression, failing integration test hoặc behavior thay đổi khó nhìn bằng code review.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
```

Sau mỗi checkout, chạy test hoặc benchmark rồi đánh dấu:

```bash
git bisect good
# hoặc
git bisect bad
```

Kết thúc bằng:

```bash
git bisect reset
```

**Lưu ý:**
Nếu test không deterministic, kết quả bisect có thể sai. Trước tiên phải có cách tái hiện regression đủ ổn định.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database transaction + message publishing

**Khái niệm:**
Outbox Pattern ghi business change và event/message cần publish vào cùng một local database transaction. Một background publisher sau đó đọc outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application vừa commit database vừa publish Service Bus message bằng hai thao tác độc lập, có thể xảy ra partial failure: database commit thành công nhưng message publish thất bại, hoặc ngược lại.

**Ví dụ thực tế:**
Order được chuyển sang `Paid`. Thay vì update `Orders` rồi gọi Service Bus ngay, transaction ghi:
- `Orders.Status = Paid`
- một `OrderPaid` record vào `OutboxMessages`

Worker riêng publish record đó và đánh dấu processed.

**Trade-off:**
Lợi ích là tránh dual-write inconsistency và tăng reliability. Chi phí là eventual consistency, thêm storage, polling/publishing logic, cleanup và yêu cầu consumer idempotency vì duplicate delivery vẫn có thể xảy ra.

**Middle → Senior insight:**
Middle developer cần hiểu transaction boundary và implement outbox publisher an toàn. Senior / Technical developer cần quyết định liệu hệ thống có thực sự cần Outbox hay một synchronous workflow đơn giản đã đủ, đồng thời thiết kế retry, deduplication, observability và retention cho toàn bộ delivery pipeline.

### Design 2 — Modular Monolith trước Microservices khi boundary chưa ổn định

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia code thành module có boundary rõ ràng, ownership riêng và hạn chế coupling nội bộ.

**Vấn đề nó giải quyết:**
Một codebase lớn dễ trở thành “big ball of mud”, nhưng chuyển sớm sang Microservices khi domain boundary chưa rõ lại tạo distributed-system complexity trước khi có lợi ích thực tế.

**Ví dụ thực tế:**
Một SaaS có Billing, Identity, Documents và Notifications. Các module có schema/service boundary rõ, nhưng vẫn deploy chung vì team nhỏ, throughput vừa phải và không có nhu cầu scale từng module độc lập.

**Trade-off:**
Modular Monolith giảm deployment, networking và operational overhead so với Microservices, nhưng vẫn có shared-process blast radius và không đạt independent scaling/deployment thực sự.

**Middle → Senior insight:**
Middle developer cần giữ module boundaries, dependency direction và contract nội bộ rõ ràng. Senior / Technical developer phải đánh giá khi nào một module đủ áp lực để tách service: team ownership, scaling profile, release cadence, failure isolation và data boundary — không phải vì “Microservices hiện đại hơn”.

### Design 3 — Cache-aside là bài toán consistency, không chỉ là performance

**Khái niệm:**
Trong cache-aside, application đọc cache trước; miss thì đọc database và populate cache. Khi dữ liệu thay đổi, cache cần được invalidate hoặc refresh theo chiến lược nhất quán.

**Vấn đề nó giải quyết:**
Cache giảm latency và database load, nhưng tạo thêm một bản sao dữ liệu có thể stale. Vì vậy bài toán thật không chỉ là “đặt Redis trước database”, mà là xác định mức stale data chấp nhận được và failure behavior.

**Ví dụ thực tế:**
Product catalog có thể chấp nhận stale price trong vài giây nhưng checkout thì không. Catalog API dùng Redis TTL 30 giây; checkout luôn đọc nguồn authoritative hoặc dùng consistency rule chặt hơn.

**Trade-off:**
Cache tăng throughput và giảm latency nhưng thêm invalidation complexity, cache stampede, hot keys, memory cost và behavior khó đoán khi Redis unavailable.

**Middle → Senior insight:**
Middle developer cần dùng TTL, invalidation và cache key đúng cách. Senior / Technical developer cần phân loại dữ liệu theo consistency requirement, quyết định phần nào có thể stale, thiết kế fallback khi Redis down và tránh biến cache thành hidden source of truth.
