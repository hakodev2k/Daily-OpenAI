# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng thêm `ConfigureAwait(false)` theo thói quen trong ASP.NET Core application code

**Mẹo:**
Trong ASP.NET Core hiện đại, application code thường không có `SynchronizationContext` kiểu UI/ASP.NET cổ điển cần quay lại sau `await`, nên `ConfigureAwait(false)` hiếm khi tạo khác biệt thực tế trong controller/service code.

**Tại sao hữu ích:**
Hiểu cơ chế giúp tránh cargo-cult optimization. `await` trong ASP.NET Core thường tiếp tục trên ThreadPool mà không cần phục hồi request thread cụ thể. `ConfigureAwait(false)` vẫn có ý nghĩa trong reusable library code khi library không nên phụ thuộc context của caller, nhưng không phải “performance switch” bắt buộc cho mọi `await`.

**Ví dụ:**
```csharp
public async Task<OrderDto?> GetAsync(Guid id, CancellationToken ct)
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? null : Map(order);
}
```

Không cần thêm `.ConfigureAwait(false)` chỉ vì method là async trong ASP.NET Core.

**Lưu ý:**
Đừng áp kết luận này cho WinForms, WPF hoặc framework có `SynchronizationContext` riêng. Với library dùng chung nhiều loại application, hãy đánh giá context-capture semantics của caller thay vì mặc định một quy tắc cho toàn bộ solution.

### Tip 2 — Dùng `TagWith` để nối LINQ query với SQL/log trong production troubleshooting

**Mẹo:**
Khi một EF Core query quan trọng khó nhận diện giữa hàng nghìn câu SQL trong Application Insights hoặc database profiler, gắn `TagWith()` bằng tên use case ổn định.

**Tại sao hữu ích:**
EF Core dịch LINQ thành SQL nên stack trace application và execution plan database thường nằm ở hai thế giới khác nhau. Query tag giúp bạn đi từ symptom như slow endpoint tới đúng SQL nhanh hơn mà không phải đoán từ query text dài.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .TagWith("OrderSearch.ListPending")
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .OrderBy(x => x.CreatedAt)
    .Take(100)
    .ToListAsync(ct);
```

Trong SQL log, tag xuất hiện dưới dạng comment và giúp đối chiếu với execution plan/telemetry.

**Lưu ý:**
Không đưa PII, user input hoặc request-specific value vào tag vì nó có thể làm log/cardinality tăng và rò rỉ dữ liệu. Tag nên ổn định theo operation, không phải theo từng request.

### Tip 3 — Với MongoDB, project đúng field để tránh truyền document lớn không cần thiết

**Mẹo:**
Nếu collection có document lớn nhưng endpoint chỉ cần vài field, dùng projection thay vì lấy nguyên document rồi bỏ bớt dữ liệu ở application layer.

**Tại sao hữu ích:**
MongoDB phải đọc và gửi dữ liệu qua network tới application. Với field lớn như description, metadata, history hoặc embedded arrays, lấy toàn document làm tăng bandwidth, deserialization cost và allocation dù response cuối chỉ cần một phần nhỏ.

**Ví dụ:**
```csharp
var items = await collection
    .Find(x => x.TenantId == tenantId && x.IsActive)
    .Project(x => new ProductListItem
    {
        Id = x.Id,
        Name = x.Name,
        Price = x.Price
    })
    .ToListAsync(ct);
```

Kết hợp projection với index phù hợp có thể giảm đáng kể work trên read-heavy listing endpoint.

**Lưu ý:**
Projection không sửa được data model tệ. Nếu document có embedded array tăng không giới hạn hoặc thường xuyên vượt access pattern dự kiến, cần xem lại document boundary thay vì chỉ cắt field lúc đọc.

### Tip 4 — Dùng `ETag` cho conditional GET khi resource thay đổi ít nhưng được đọc nhiều

**Mẹo:**
Với CMS content, product metadata hoặc API resource đọc nhiều, cân nhắc trả `ETag` và xử lý `If-None-Match` để client/CDN xác minh resource còn mới mà không tải lại body.

**Tại sao hữu ích:**
Khi representation chưa thay đổi, server có thể trả `304 Not Modified`, giảm payload, serialization và bandwidth. Đây là validation cache ở HTTP level, khác với server-side cache giữ object trong memory.

**Ví dụ:**
```http
GET /api/products/42
If-None-Match: "product-42-v17"

HTTP/1.1 304 Not Modified
ETag: "product-42-v17"
```

ETag có thể dựa trên version/concurrency token ổn định thay vì hash lại payload lớn ở mỗi request.

**Lưu ý:**
ETag phải phản ánh đúng representation thực tế. Nếu response thay đổi theo locale, tenant, authorization hoặc query option, cùng một ETag cho mọi variant có thể làm client nhận dữ liệu sai. Đừng dùng `304` cho dữ liệu user-specific nếu cache semantics chưa được thiết kế rõ.

### Tip 5 — Dùng Testcontainers cho integration test khi behavior phụ thuộc database/broker thật

**Mẹo:**
Khi test cần xác minh EF Core translation, PostgreSQL behavior, Redis semantics hoặc dependency infrastructure cụ thể, chạy dependency thật trong container thay vì mock API của database.

**Tại sao hữu ích:**
Mock repository không phát hiện được khác biệt về SQL translation, collation, transaction, index, serialization hoặc provider-specific behavior. Testcontainers cho phép test gần production semantics hơn nhưng vẫn tự động tạo môi trường cô lập trong test run.

**Ví dụ:**
```text
Integration test startup
-> start PostgreSQL container
-> apply migrations
-> seed minimal test data
-> run API/repository test
-> dispose container
```

Có thể giữ unit test cho business logic nhanh và dùng container test cho boundary thật sự cần infrastructure.

**Lưu ý:**
Không biến toàn bộ test suite thành container-based E2E. Startup chậm hơn, CI cần Docker/runtime phù hợp và test data phải deterministic. Chỉ dùng ở nơi fake/mock không đủ chứng minh behavior quan trọng.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer cần chống duplicate message một cách bền vững

**Khái niệm:**
Inbox Pattern lưu `MessageId` hoặc processing record vào durable storage cùng với state change của consumer để một message được redeliver có thể được nhận diện và bỏ qua an toàn.

**Vấn đề nó giải quyết:**
Broker như Azure Service Bus thường cung cấp at-least-once delivery. Consumer có thể xử lý business update thành công nhưng crash trước khi hoàn tất message, khiến broker gửi lại cùng message và side effect chạy lần nữa.

**Ví dụ thực tế:**
```text
Receive OrderPaid(messageId=abc)

Transaction:
1. kiểm tra Inbox có abc chưa
2. cập nhật Order = Paid
3. insert Inbox(abc)
4. commit

Message abc được giao lại
-> Inbox đã có abc
-> không chạy business side effect lần hai
```

Nếu business update và Inbox nằm cùng database transaction, duplicate detection gắn chặt với state change hơn việc chỉ dùng in-memory cache.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, unique constraint, cleanup/retention và contention nếu throughput rất cao. Một số operation vốn idempotent tự nhiên có thể không cần full Inbox table.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là bình thường và consumer phải idempotent. Senior / Technical developer phải chọn idempotency boundary, transaction scope, retention, partitioning và cách xử lý message trùng đang concurrent thay vì chỉ thêm `if` kiểm tra trong memory.

### Design 2 — Read Replica cần chiến lược cho read-after-write consistency

**Khái niệm:**
Read replica giúp scale read traffic bằng cách phục vụ query từ bản sao, nhưng replication thường có độ trễ. Vì vậy application phải biết request nào chịu được stale data và request nào cần đọc từ primary sau write.

**Vấn đề nó giải quyết:**
Nếu user vừa cập nhật profile rồi ngay lập tức đọc từ replica đang chậm vài trăm milliseconds hoặc vài giây, UI có thể hiển thị giá trị cũ dù write đã thành công. Đây không phải bug ngẫu nhiên mà là consequence của consistency model.

**Ví dụ thực tế:**
```text
POST /profile
-> write primary
-> 200 OK

GET /profile ngay sau đó
Option A: đọc primary trong consistency window
Option B: route theo session/user token
Option C: chấp nhận stale data nếu use case không yêu cầu immediate consistency
```

Analytics/reporting thường phù hợp với replica hơn checkout hoặc workflow cần đọc state vừa ghi.

**Trade-off:**
Replica tăng read capacity và giảm tải primary nhưng thêm replication lag, routing complexity và operational cost. Ép mọi read quan trọng quay về primary giữ consistency nhưng làm mất một phần lợi ích scale-out.

**Middle → Senior insight:**
Middle developer cần biết replica không đồng nghĩa “cùng dữ liệu ngay lập tức”. Senior / Technical developer phải phân loại read theo consistency requirement, định nghĩa fallback/routing policy và quan sát replication lag thay vì chuyển toàn bộ `SELECT` sang replica theo cấu hình chung.

### Design 3 — Shared Database vs Database-per-Service phải theo ownership và coupling thực tế

**Khái niệm:**
Shared Database cho nhiều module/service cùng dùng một schema hoặc database; Database-per-Service trao quyền sở hữu dữ liệu riêng cho từng service và buộc integration đi qua contract/message thay vì query chéo trực tiếp.

**Vấn đề nó giải quyết:**
Shared database giúp transaction và reporting đơn giản lúc đầu nhưng dễ tạo coupling qua table/schema: service A đổi column có thể làm service B vỡ. Database-per-Service tăng autonomy nhưng làm cross-service query và transaction trở thành bài toán phân tán.

**Ví dụ thực tế:**
```text
Modular Monolith cùng team/release:
- một database
- schema/module boundary rõ
- transaction đơn giản
=> có thể hoàn toàn hợp lý

Microservices deploy độc lập:
- Orders sở hữu order data
- Billing sở hữu payment data
- integration qua API/event
=> giảm schema coupling giữa team
```

Không cần tách database chỉ để gọi hệ thống là microservices nếu ownership và release model chưa thực sự độc lập.

**Trade-off:**
Shared database đơn giản cho join, migration và ACID transaction nhưng tăng coupling và coordination. Database-per-Service tăng autonomy và failure isolation nhưng thêm duplication, eventual consistency, data integration và observability complexity.

**Middle → Senior insight:**
Middle developer cần tôn trọng data ownership và tránh query chéo boundary tùy tiện. Senior / Technical developer phải quyết định mức isolation dựa trên team ownership, release cadence, transaction requirement, reporting need và operational maturity; đôi khi shared database với boundary tốt là lựa chọn Senior hơn việc tách hạ tầng quá sớm.
