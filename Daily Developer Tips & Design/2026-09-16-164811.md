# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncDisposable` khi cleanup bản thân cũng là async I/O

**Mẹo:**
Với resource cần flush hoặc đóng bất đồng bộ, triển khai/tiêu thụ `IAsyncDisposable` bằng `await using` thay vì ép cleanup async thành synchronous blocking.

**Tại sao hữu ích:**
`Dispose()` phù hợp cho cleanup đồng bộ. Nhưng resource như async stream, transaction wrapper hoặc writer có thể cần I/O khi hoàn tất. Blocking bằng `.GetAwaiter().GetResult()` làm thread bị giữ vô ích và có thể tạo failure behavior khó đoán trong shutdown path.

**Ví dụ:**
```csharp
await using var transaction = await db.Database
    .BeginTransactionAsync(cancellationToken);

await db.SaveChangesAsync(cancellationToken);
await transaction.CommitAsync(cancellationToken);
```
`await using` bảo đảm `DisposeAsync()` được gọi ngay cả khi exception xảy ra trong scope.

**Lưu ý:**
Không biến mọi object thành `IAsyncDisposable`. Nếu cleanup chỉ giải phóng memory/native handle đồng bộ, `IDisposable` đơn giản hơn. Cleanup cũng không nên phụ thuộc vào một `CancellationToken` đã bị cancel nếu resource bắt buộc phải được giải phóng.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` cho danh sách lớn

**Mẹo:**
Với feed/order history lớn và UI chỉ cần next/previous, dùng keyset pagination dựa trên sort key ổn định thay vì `OFFSET ... FETCH` sâu.

**Tại sao hữu ích:**
`OFFSET 100000` vẫn buộc database tìm/sort rồi bỏ qua lượng lớn rows. Keyset dùng giá trị cuối trang trước làm boundary nên có thể seek qua index. Nó cũng giảm hiện tượng item bị nhảy/duplicate khi dữ liệu mới được insert giữa hai lần đọc.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)` tùy query workload.

**Lưu ý:**
Sort phải deterministic; chỉ `CreatedAt` thường chưa đủ nếu nhiều rows cùng timestamp. Keyset không thuận tiện cho yêu cầu “nhảy thẳng tới page 417”, nên cần chọn theo UX thực tế.

### Tip 3 — Azure Service Bus DLQ phải có operational workflow, không phải nơi chôn message

**Mẹo:**
Theo dõi Dead-Letter Queue bằng metric/alert và lưu đủ diagnostic metadata để phân loại, sửa nguyên nhân rồi replay có kiểm soát.

**Tại sao hữu ích:**
Message vào DLQ thường biểu thị contract mismatch, poison data, exhausted retries hoặc business condition không thể xử lý. Nếu chỉ cấu hình DLQ mà không có ownership và replay procedure, hệ thống vẫn mất business progress nhưng failure bị giấu khỏi request path.

**Ví dụ:**
```text
DLQ spike after deployment
→ inspect DeadLetterReason + message type/version
→ correlate deployment
→ discover consumer cannot deserialize new enum value
→ deploy backward-compatible fix
→ replay selected messages
```

**Lưu ý:**
Không replay hàng loạt trước khi xác nhận consumer đã idempotent và root cause đã được sửa; nếu không bạn có thể tạo retry storm hoặc duplicate side effects.

### Tip 4 — Với React, đừng lưu derived state nếu có thể tính từ source state

**Mẹo:**
Nếu một giá trị có thể tính trực tiếp từ props/state hiện tại, ưu tiên derive trong render hoặc `useMemo` khi computation thực sự đắt, thay vì đồng bộ thêm một `useState` qua `useEffect`.

**Tại sao hữu ích:**
Hai state representations cho cùng dữ liệu tạo nguy cơ drift và thêm render cycle. Derived value giúp invariant rõ hơn: output luôn được tính từ source-of-truth hiện tại.

**Ví dụ:**
```tsx
const [items, setItems] = useState<Item[]>([]);
const [query, setQuery] = useState("");

const visibleItems = useMemo(
  () => items.filter(x => x.name.includes(query)),
  [items, query]
);
```
Không cần `setVisibleItems(...)` trong một effect chỉ để đồng bộ lại mỗi khi `items` hoặc `query` đổi.

**Lưu ý:**
`useMemo` cũng có chi phí và không phải correctness mechanism. Với phép tính rẻ, tính trực tiếp thường đơn giản hơn. State riêng vẫn hợp lý nếu giá trị có lifecycle độc lập hoặc user có thể chỉnh nó riêng.

### Tip 5 — Kiểm tra generated SQL của EF Core khi LINQ trông vô hại nhưng API chậm

**Mẹo:**
Khi query EF Core có latency bất thường, xem SQL bằng `ToQueryString()`, logging hoặc profiler rồi kiểm tra execution plan thay vì chỉ đọc LINQ.

**Tại sao hữu ích:**
LINQ là abstraction; performance cuối cùng phụ thuộc SQL được translate, indexes và cardinality. Một predicate, navigation hoặc projection có thể tạo subquery/join khác với mental model của developer.

**Ví dụ:**
```csharp
var query = db.Orders
    .Where(x => x.CustomerId == customerId && x.CreatedAt >= from)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderSummary(x.Id, x.Total, x.Status));

var sql = query.ToQueryString();
```
Sau đó dùng SQL thực tế để xem plan và logical reads trên production-like data.

**Lưu ý:**
`ToQueryString()` phục vụ diagnostics, không phải SQL contract để application phụ thuộc vào. Đừng tối ưu bằng cách chuyển sang `AsEnumerable()` quá sớm vì nó có thể kéo lượng dữ liệu lớn về memory.

## 🧠 Software Design

### Design 1 — Optimistic concurrency vs pessimistic locking

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor đọc cùng state và phát hiện conflict lúc ghi, thường qua version/token. Pessimistic locking khóa resource sớm để ngăn actor khác thay đổi trong critical section.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng sửa một order dựa trên version cũ có thể ghi đè thay đổi của nhau. Ngược lại, workflow cạnh tranh rất cao có thể liên tục conflict nếu chỉ retry optimistic update.

**Ví dụ thực tế:**
EF Core có thể dùng `rowversion` làm concurrency token. Update sẽ chứa version cũ trong `WHERE`; nếu affected rows bằng 0, application biết state đã đổi và có thể reload/merge/reject. Với một database workflow cực ngắn và contention cao, explicit lock phù hợp có thể giảm retry churn.

**Trade-off:**
Optimistic concurrency không giữ lock trong thời gian user suy nghĩ và scale tốt khi conflict hiếm, nhưng cần conflict handling. Pessimistic locking giảm write conflict trong critical section nhưng tăng blocking, deadlock risk và làm transaction duration trở thành vấn đề vận hành.

**Middle → Senior insight:**
Middle developer cần xử lý concurrency exception đúng và không silently overwrite. Senior / Technical developer phải đánh giá contention, transaction duration, UX conflict semantics và database capacity để chọn chiến lược; không mặc định locking mạnh hơn là an toàn hơn.

### Design 2 — Bounded Context trước khi tách Microservices

**Khái niệm:**
Bounded Context xác định nơi một domain model và ngôn ngữ nghiệp vụ có nghĩa nhất quán. Nó là boundary về semantics/ownership; Microservice là một lựa chọn deployment boundary và không bắt buộc phải trùng một-một ngay từ đầu.

**Vấn đề nó giải quyết:**
Một model `Customer` dùng chung cho CRM, Billing và Support thường dần chứa field/rule mâu thuẫn. Tách service theo technical layer hoặc table trước khi hiểu domain lại tạo distributed monolith với shared database và cross-service chatter.

**Ví dụ thực tế:**
`Catalog` sở hữu product merchandising; `Ordering` chỉ cần snapshot tên/giá tại thời điểm mua. Ordering không nhất thiết tham chiếu trực tiếp toàn bộ Catalog entity. Hai context ban đầu vẫn có thể là modules trong một Modular Monolith và chỉ tách deployment khi scale/ownership yêu cầu.

**Trade-off:**
Boundary đúng giảm coupling và cho phép model tiến hóa độc lập, nhưng duplication có chủ đích và mapping giữa contexts tăng. Boundary sai tạo integration overhead mà không đem lại autonomy.

**Middle → Senior insight:**
Middle developer cần giữ model/rules trong đúng module và không dùng shared entity như shortcut. Senior / Technical developer phải tìm boundary từ business invariants, change cadence, ownership và data consistency trước khi quyết định có cần process/network boundary hay không.

### Design 3 — Cache consistency bằng versioned keys thay vì xóa wildcard

**Khái niệm:**
Với cache có nhiều derived entries, có thể đưa version của dataset/tenant/content tree vào cache key. Khi dữ liệu thay đổi, tăng version để các reads mới tự chuyển sang namespace mới thay vì cố tìm và xóa mọi key liên quan.

**Vấn đề nó giải quyết:**
CMS hoặc catalog có hàng nghìn cache keys phụ thuộc cùng một content subtree. Wildcard delete thường đắt, khó atomic và dễ bỏ sót derived key, dẫn tới stale data khó tái hiện.

**Ví dụ thực tế:**
```text
catalog-version:tenant-42 = 108
cache key = catalog:tenant-42:v108:category:shoes:page:1

Publish catalog
→ increment version to 109
→ requests mới dùng v109
→ v108 tự hết TTL
```

**Trade-off:**
Versioned keys làm invalidation O(1) về mặt namespace và giảm coupling giữa writers/readers, nhưng old entries tồn tại đến TTL nên tốn memory tạm thời. Version lookup cũng phải nhanh và đáng tin cậy.

**Middle → Senior insight:**
Middle developer cần xây key deterministic và TTL hợp lý. Senior / Technical developer phải cân nhắc invalidation granularity, memory amplification, multi-region propagation và failure mode khi version store unavailable; với vài keys đơn giản, explicit invalidation vẫn dễ vận hành hơn.
