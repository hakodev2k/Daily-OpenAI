# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer lớn, ngắn hạn và lặp lại nhiều lần

**Mẹo:**
Khi một hot path liên tục cần buffer tạm kích thước lớn để đọc stream, transform payload hoặc serialize dữ liệu, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì `new` array ở mỗi lần xử lý.

**Tại sao hữu ích:**
Array lớn tạo allocation áp lực lên GC, đặc biệt khi workload lặp lại với tần suất cao. Pooling cho phép tái sử dụng vùng nhớ và giảm số object phải allocate/collect mà không thay đổi semantics của operation.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

Nếu buffer có dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc tự clear phần đã sử dụng trước khi return.

**Lưu ý:**
Array nhận từ pool có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Không giả định buffer đã zeroed. Với allocation nhỏ hoặc code không nằm trên hot path, pooling có thể làm code phức tạp hơn lợi ích nhận được.

### Tip 2 — Partition ASP.NET Core rate limit theo caller thay vì dùng một global bucket

**Mẹo:**
Khi bảo vệ API có nhiều tenant/user/API key, dùng partitioned rate limiting để mỗi caller có quota riêng thay vì để toàn bộ traffic dùng chung một limiter.

**Tại sao hữu ích:**
Global limiter dễ tạo noisy-neighbor problem: một client tăng đột biến traffic có thể làm client khác bị `429` dù họ vẫn trong mức sử dụng hợp lý. Partition key giúp giới hạn blast radius và phản ánh fairness tốt hơn.

**Ví dụ:**
```csharp
options.AddPolicy("per-tenant", context =>
{
    var tenantId = context.User.FindFirst("tenant_id")?.Value ?? "anonymous";

    return RateLimitPartition.GetFixedWindowLimiter(
        tenantId,
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1),
            QueueLimit = 0
        });
});
```

Quota thực tế nên dựa trên capacity, contract và endpoint cost thay vì một số cố định áp cho mọi operation.

**Lưu ý:**
Partition key phải đáng tin cậy. Không dùng raw header do client tự đặt nếu chưa authenticate/validate. Rate limiting cũng không thay thế authorization, anti-abuse detection hoặc downstream capacity protection.

### Tip 3 — Thêm TTL jitter để tránh Redis cache stampede theo “đợt hết hạn”

**Mẹo:**
Nếu nhiều cache key cùng được tạo trong một batch hoặc cùng TTL, thêm một khoảng random nhỏ vào expiration để tránh hàng nghìn key hết hạn cùng thời điểm.

**Tại sao hữu ích:**
Khi cache miss đồng loạt, application có thể đẩy một burst lớn xuống database/API gốc. Jitter làm thời điểm expire phân tán hơn, giảm synchronized recomputation và peak load.

**Ví dụ:**
```csharp
var baseTtl = TimeSpan.FromMinutes(10);
var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 90));
var ttl = baseTtl + jitter;

await cache.SetStringAsync(key, payload, new DistributedCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = ttl
}, ct);
```

Với key cực nóng, có thể kết hợp thêm single-flight/lock hợp lý hoặc refresh-ahead.

**Lưu ý:**
Jitter không giải quyết cache stampede khi chỉ một key rất nóng hết hạn. Nó cũng không sửa invalidation sai hoặc dữ liệu stale. TTL strategy phải khớp freshness requirement của từng loại dữ liệu.

### Tip 4 — Dùng `git bisect` khi regression nằm giữa nhiều commit khó đoán

**Mẹo:**
Khi một bug xuất hiện sau nhiều commit và chưa rõ commit nào gây ra, dùng `git bisect` để binary-search lịch sử thay vì checkout thủ công từng commit.

**Tại sao hữu ích:**
Với vài trăm commit, kiểm tra tuyến tính rất tốn thời gian. `git bisect` giảm số bước cần thử xuống khoảng `log2(N)` nếu mỗi commit có thể được đánh dấu rõ là good hoặc bad.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# test commit Git checkout tự động
git bisect good   # hoặc bad

# khi xong
git bisect reset
```

Nếu có test/script tái hiện được regression, có thể tự động hóa bằng `git bisect run`.

**Lưu ý:**
Bisect hiệu quả khi lịch sử build/test được ở phần lớn commit. Nếu commit giữa lịch sử không compile hoặc symptom không deterministic, cần script phân loại exit code cẩn thận và có thể phải `skip` một số commit.

### Tip 5 — Bật Playwright trace khi retry để điều tra flaky test bằng evidence

**Mẹo:**
Với E2E test thỉnh thoảng fail trong CI, cấu hình Playwright lưu trace khi retry thay vì chỉ dựa vào screenshot cuối cùng hoặc log text.

**Tại sao hữu ích:**
Trace có timeline của action, DOM snapshot, network request và console information, giúp phân biệt test synchronization lỗi với application thực sự chậm hoặc backend trả sai response.

**Ví dụ:**
```ts
use: {
  trace: 'on-first-retry'
},
retries: 2
```

Khi test fail lần đầu rồi retry, artifact trace giữ evidence của failure mà không tạo trace cho mọi test pass.

**Lưu ý:**
Đừng sửa flaky test bằng cách tăng timeout toàn cục trước khi biết nguyên nhân. Trace artifact có thể lớn và chứa dữ liệu nhạy cảm từ test environment, nên cần retention/access policy phù hợp trong CI.

## 🧠 Software Design

### Design 1 — Strangler Fig cho migration .NET Framework thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig migration thay thế hệ thống legacy theo từng capability hoặc route: traffic mới dần đi qua implementation mới trong khi phần chưa migrate vẫn chạy trên application cũ.

**Vấn đề nó giải quyết:**
Một monolith .NET Framework lớn thường chứa business rule, integration và edge case tích lũy nhiều năm. Big-bang rewrite buộc team tái hiện toàn bộ behavior trước khi nhận giá trị và tạo một cut-over có blast radius rất lớn.

**Ví dụ thực tế:**
```text
Legacy IIS/.NET Framework application

/api/catalog/*   -> ASP.NET Core mới
/api/orders/*    -> legacy
/admin/*         -> legacy

Sau mỗi slice:
- chuyển contract
- route traffic
- đo telemetry
- decommission phần cũ tương ứng
```

Proxy/gateway hoặc routing layer có thể giữ URL bên ngoài ổn định trong quá trình migration.

**Trade-off:**
Migration từng phần giảm release risk và cho phép học dần, nhưng tạo giai đoạn coexistence: hai runtime, duplicated infrastructure, contract compatibility và data ownership phức tạp hơn. Big-bang có kiến trúc cuối sạch hơn trên giấy nhưng rủi ro delivery cao hơn.

**Middle → Senior insight:**
Middle developer cần giữ backward compatibility, test behavior legacy và cô lập dependency khi migrate một slice. Senior / Technical developer phải chọn migration boundary, traffic routing, data ownership, rollback và tiêu chí decommission sao cho hệ thống không mắc kẹt vĩnh viễn ở trạng thái “nửa cũ nửa mới”.

### Design 2 — Backpressure phải đi xuyên suốt pipeline, không chỉ giới hạn consumer

**Khái niệm:**
Backpressure là khả năng hệ thống làm chậm hoặc từ chối upstream khi downstream không còn capacity, thay vì tiếp tục nhận work vô hạn rồi tích backlog ở một điểm khác.

**Vấn đề nó giải quyết:**
Giới hạn `MaxConcurrentCalls` ở consumer không đủ nếu producer vẫn đẩy message nhanh hơn tốc độ xử lý trong nhiều giờ. Queue sẽ tăng, latency kéo dài, retention bị đe dọa và recovery sau incident ngày càng khó.

**Ví dụ thực tế:**
```text
Ingress API
-> queue
-> worker
-> database

Database giảm capacity
-> worker giảm concurrency
-> queue depth tăng
-> autoscale tới ngưỡng an toàn
-> nếu backlog tiếp tục tăng: throttle/reject non-critical ingress
```

Thiết kế tốt cần metric như queue age, queue depth, processing rate và dependency saturation để quyết định hành vi.

**Trade-off:**
Backpressure bảo vệ reliability và tránh overload cascade nhưng có thể làm user thấy `429`, delayed processing hoặc degraded feature. Không áp backpressure có thể giữ UX ngắn hạn nhưng đánh đổi bằng outage lớn hơn khi backlog vượt khả năng phục hồi.

**Middle → Senior insight:**
Middle developer cần biết bounded queue, concurrency limit và timeout. Senior / Technical developer phải thiết kế capacity budget end-to-end, degradation policy, priority class và trigger để upstream giảm tải trước khi hệ thống mất kiểm soát.

### Design 3 — Authorization policy theo resource/context thay vì role explosion

**Khái niệm:**
Khi quyền phụ thuộc vào tenant, ownership, trạng thái resource hoặc relationship nghiệp vụ, authorization nên đánh giá policy trên resource/context thay vì tạo thêm role cho mọi tổ hợp quyền.

**Vấn đề nó giải quyết:**
Mô hình role-only dễ phát triển thành `Admin`, `TenantAdmin`, `ProjectAdmin`, `ProjectEditor`, `ProjectOwner`, `RegionProjectEditor`... nhưng vẫn không diễn đạt tốt rule như “user chỉ sửa invoice thuộc tenant của mình và invoice chưa Approved”.

**Ví dụ thực tế:**
```text
Policy: CanEditInvoice

Allow khi:
- user có permission Invoice.Edit
- invoice.TenantId == user.TenantId
- invoice.Status != Approved
```

Role/claim có thể cung cấp coarse-grained permission, còn resource authorization kiểm tra điều kiện cụ thể của object đang thao tác.

**Trade-off:**
Resource-based policy giữ authorization gần business rule và tránh role explosion, nhưng cần load đúng resource trước khi authorize và làm test matrix phức tạp hơn. Role đơn giản vẫn phù hợp với coarse-grained admin capability ít biến đổi.

**Middle → Senior insight:**
Middle developer cần tránh chỉ ẩn button ở frontend và phải enforce authorization ở backend. Senior / Technical developer phải xác định security boundary, source of truth cho permission, caching semantics và cách audit quyết định authorization mà không rò rỉ dữ liệu nhạy cảm.
