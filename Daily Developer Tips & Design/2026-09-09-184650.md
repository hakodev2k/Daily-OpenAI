# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng trả `ValueTask` chỉ vì nó “nhẹ hơn `Task`”

**Mẹo:**
Chỉ cân nhắc `ValueTask` khi profiling cho thấy một async API hoàn thành đồng bộ rất thường xuyên và allocation của `Task` thực sự nằm trên hot path. Với phần lớn application code, tiếp tục dùng `Task` để giữ semantics đơn giản và an toàn hơn.

**Tại sao hữu ích:**
`ValueTask` có thể tránh allocation trong một số trường hợp, nhưng nó phức tạp hơn: không nên await nhiều lần, không nên cache tùy tiện, và consumer dễ dùng sai hơn `Task`. Một micro-optimization nhỏ có thể đổi lại API khó dùng và khó maintain.

**Ví dụ:**
```csharp
public ValueTask<bool> IsCachedAsync(string key)
{
    if (_cache.ContainsKey(key))
        return ValueTask.FromResult(true);

    return new ValueTask<bool>(CheckRemoteAsync(key));
}
```

Chỉ đáng cân nhắc nếu path cache-hit rất phổ biến và profiling xác nhận allocation đáng kể.

**Lưu ý:**
Không đổi hàng loạt `Task` sang `ValueTask` theo style guide. Nếu operation gần như luôn asynchronous, lợi ích thường không đáng complexity bổ sung.

### Tip 2 — Dùng `ETag`/conditional request để giảm payload cho API đọc nhiều

**Mẹo:**
Với resource ít thay đổi nhưng được đọc thường xuyên, cân nhắc trả `ETag` và xử lý `If-None-Match` để client có thể nhận `304 Not Modified` thay vì tải lại payload đầy đủ.

**Tại sao hữu ích:**
HTTP caching không chỉ là CDN. Conditional request giúp giảm bandwidth, serialization và response body cost trong mobile API, CMS hoặc catalog API, đặc biệt khi payload lớn nhưng thay đổi ít.

**Ví dụ:**
```text
GET /api/products/42
ETag: "v17"

GET /api/products/42
If-None-Match: "v17"

-> 304 Not Modified
```

`ETag` có thể dựa trên version/rowversion hoặc hash ổn định của representation.

**Lưu ý:**
`ETag` phải đại diện đúng cho representation thực tế. Nếu response phụ thuộc tenant, locale hoặc authorization mà dùng chung một ETag không phù hợp, client có thể cache sai nội dung.

### Tip 3 — Khi SQL Server deadlock xảy ra, đọc deadlock graph thay vì chỉ tăng timeout

**Mẹo:**
Nếu production xuất hiện deadlock, lấy deadlock graph từ Extended Events hoặc telemetry rồi xác định hai transaction đang giữ và chờ resource nào; đừng chỉ tăng command timeout hoặc retry vô hạn.

**Tại sao hữu ích:**
Deadlock là vòng chờ tài nguyên, không phải đơn thuần query chậm. Timeout lớn hơn không loại bỏ vòng chờ; database vẫn phải chọn một victim. Root cause thường liên quan access order, transaction scope, index hoặc lượng row bị lock.

**Ví dụ:**
```text
Transaction A:
lock Orders
-> wait OrderLines

Transaction B:
lock OrderLines
-> wait Orders
```

Một fix có thể là chuẩn hóa thứ tự truy cập hoặc giảm transaction scope để hai path khóa resource theo cùng thứ tự.

**Lưu ý:**
Retry victim transaction thường vẫn cần vì deadlock có thể xảy ra ngẫu nhiên, nhưng retry chỉ là resilience layer. Nếu deadlock lặp lại, phải xử lý nguyên nhân trong query/transaction design.

### Tip 4 — Với Kubernetes, đặt `requests` theo workload thực tế trước khi tin vào autoscaling

**Mẹo:**
Khi dùng Horizontal Pod Autoscaler, cấu hình CPU/memory `requests` hợp lý dựa trên measurement. HPA dựa trên resource utilization sẽ cho tín hiệu sai nếu `requests` đặt quá thấp hoặc quá cao so với workload thật.

**Tại sao hữu ích:**
Ví dụ Pod dùng 300m CPU: nếu request là 100m, utilization nhìn như 300%; nếu request là 1000m, chỉ còn 30%. Cùng một workload nhưng autoscaling decision hoàn toàn khác.

**Ví dụ:**
```text
Actual CPU: 300m
request=100m  -> 300% utilization
request=500m  -> 60% utilization
```

Dùng load test và production telemetry để chọn baseline rồi tune threshold/scaling behavior.

**Lưu ý:**
Không dùng HPA để chữa application bottleneck như DB saturation hoặc external dependency limit. Scale Pod thêm có thể làm downstream quá tải nhanh hơn.

### Tip 5 — Dùng mutation testing để phát hiện test chỉ “chạy qua code” nhưng không bảo vệ behavior

**Mẹo:**
Nếu một module có code coverage cao nhưng vẫn thường regression, cân nhắc mutation testing cho phần business-critical. Tool sẽ cố ý thay đổi logic nhỏ rồi xem test có fail hay không.

**Tại sao hữu ích:**
Coverage chỉ cho biết line đã được execute, không chứng minh assertion đủ mạnh. Nếu đổi `>` thành `>=` mà test vẫn pass, test suite có thể chưa bảo vệ boundary condition quan trọng.

**Ví dụ:**
```text
Original: total > creditLimit
Mutation: total >= creditLimit
```

Nếu test không phát hiện mutation, cần bổ sung case tại đúng boundary thay vì chỉ thêm test để tăng coverage percentage.

**Lưu ý:**
Mutation testing tốn thời gian chạy và không nên áp dụng toàn repository theo phản xạ. Ưu tiên domain rule, pricing, authorization hoặc calculation có risk cao.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer cần idempotency mạnh

**Khái niệm:**
Inbox Pattern lưu `MessageId` hoặc delivery identity đã xử lý trong storage cùng transaction với business change, để consumer nhận lại cùng message có thể nhận biết và bỏ qua side effect trùng.

**Vấn đề nó giải quyết:**
Message broker thường cung cấp at-least-once delivery. Consumer có thể xử lý xong business update rồi crash trước khi acknowledgement, khiến broker delivery lại cùng message.

**Ví dụ thực tế:**
```text
Transaction:
- kiểm tra InboxMessages(MessageId)
- nếu chưa có: update Order
- insert InboxMessages(MessageId)
- commit
```

Lần delivery tiếp theo với cùng `MessageId` chỉ return success mà không áp dụng business effect lần hai.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, retention policy, index và transaction cost. Nếu idempotency có thể được đảm bảo tự nhiên bằng unique constraint của business key, một inbox riêng có thể là abstraction thừa.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là behavior bình thường và handler không được assume exactly-once. Senior / Technical developer phải chọn deduplication key, retention, transaction boundary và cleanup strategy dựa trên throughput và replay requirement.

### Design 2 — API Versioning: ưu tiên backward-compatible evolution trước khi tạo version mới

**Khái niệm:**
API versioning là cơ chế quản lý breaking change, không phải lý do để tạo `/v2` cho mọi thay đổi. Nhiều evolution có thể thực hiện bằng additive field, optional behavior hoặc tolerant-reader contract mà không phá consumer cũ.

**Vấn đề nó giải quyết:**
Tạo version mới quá sớm làm tăng số contract phải support, test và document. Ngược lại, thay đổi trực tiếp field semantics hoặc remove field có thể phá consumer production mà provider không biết.

**Ví dụ thực tế:**
Thay vì:
```text
v1: customerName
v2: firstName + lastName
```

Có thể trước tiên thêm `firstName`, `lastName` nhưng vẫn giữ `customerName` trong compatibility window, rồi deprecate có kế hoạch.

**Trade-off:**
Backward compatibility giảm migration pressure nhưng tạo giai đoạn contract dư thừa. Version mới tạo boundary rõ hơn nhưng tăng maintenance, routing, documentation và deprecation complexity.

**Middle → Senior insight:**
Middle developer cần phân biệt additive change và breaking change. Senior / Technical developer phải định nghĩa compatibility window, consumer inventory, deprecation telemetry và migration sequence trước khi quyết định versioning strategy.

### Design 3 — Bounded Context để tránh một “Universal Domain Model” cho toàn hệ thống

**Khái niệm:**
Bounded Context đặt ranh giới nơi một domain model và terminology có nghĩa nhất quán. Cùng một từ như `Customer`, `Order` hoặc `Product` có thể có model khác nhau ở Sales, Billing và Support thay vì ép toàn hệ thống dùng một object chung.

**Vấn đề nó giải quyết:**
Một shared model khổng lồ thường tích lũy field từ nhiều team và business rule không liên quan. Mỗi thay đổi nhỏ tạo coupling giữa module, làm entity trở thành data bag và ownership mơ hồ.

**Ví dụ thực tế:**
```text
Sales.Customer
- LeadScore
- SalesOwner

Billing.Customer
- BillingAccountId
- CreditStatus

Support.Customer
- SupportTier
- OpenTickets
```

Các context trao đổi qua contract rõ thay vì share trực tiếp cùng entity/class.

**Trade-off:**
Bounded Context giảm semantic coupling và làm ownership rõ hơn nhưng có thể duplicate dữ liệu/model và cần mapping/integration giữa context. Với hệ thống nhỏ, chia boundary quá sớm có thể tạo ceremony không cần thiết.

**Middle → Senior insight:**
Middle developer cần giữ rule của từng module trong đúng boundary và tránh truy cập model nội bộ tùy tiện. Senior / Technical developer phải xác định boundary dựa trên business capability, change cadence và team ownership, không chỉ dựa trên folder hay database table.
