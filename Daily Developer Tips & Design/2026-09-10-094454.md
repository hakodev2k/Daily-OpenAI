# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer lớn, ngắn hạn và xuất hiện với tần suất cao

**Mẹo:**
Khi một hot path liên tục tạo các `byte[]` tương đối lớn chỉ để xử lý tạm thời rồi bỏ, cân nhắc `ArrayPool<T>.Shared` thay vì allocation mới ở mỗi request.

**Tại sao hữu ích:**
Allocation lớn và lặp lại tạo thêm áp lực cho Garbage Collector. Với buffer đủ lớn để đi vào Large Object Heap, chi phí còn đáng chú ý hơn. Pooling cho phép tái sử dụng vùng nhớ và giảm allocation rate — nhưng chỉ có ý nghĩa khi profiling cho thấy allocation thực sự là bottleneck.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Buffer thuê có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Không được đọc ngoài vùng dữ liệu hợp lệ. Với dữ liệu nhạy cảm, cân nhắc `clearArray: true`; đổi lại việc clear có CPU cost. Đừng pool object nhỏ chỉ để “tối ưu”.

### Tip 2 — Với SQL composite index, thứ tự column phải theo query pattern chứ không theo thứ tự field trong model

**Mẹo:**
Khi thiết kế composite index, xem predicate, sort và selectivity thực tế của workload thay vì tạo index `(A, B, C)` chỉ vì entity khai báo property theo thứ tự đó.

**Tại sao hữu ích:**
B-tree index được sắp theo key từ trái sang phải. Một index `(TenantId, Status, CreatedAt)` có thể rất hữu ích cho query lọc `TenantId`, `Status` rồi range/order theo `CreatedAt`, nhưng không tự động tối ưu query chỉ lọc `CreatedAt`.

**Ví dụ:**
```sql
SELECT Id, Total, CreatedAt
FROM Orders
WHERE TenantId = @tenantId
  AND Status = @status
  AND CreatedAt >= @from
ORDER BY CreatedAt DESC;
```

Một candidate index có thể bắt đầu bằng:

```sql
(TenantId, Status, CreatedAt DESC)
```

Sau đó kiểm tra execution plan, row estimates và actual workload trước khi giữ index.

**Lưu ý:**
Nhiều index làm read nhanh hơn nhưng tăng storage và write amplification cho `INSERT`, `UPDATE`, `DELETE`. Không tạo mọi permutation của column để bao phủ từng query.

### Tip 3 — Khi gọi third-party API, timeout phải có budget nhỏ hơn timeout của request cha

**Mẹo:**
Trong request chain, đặt timeout cho dependency sao cho còn thời gian để application xử lý lỗi hoặc fallback trước khi deadline của request bên ngoài hết.

**Tại sao hữu ích:**
Nếu ingress cho request 5 giây nhưng application cũng chờ payment API đúng 5 giây, khi dependency timeout thì caller gần như đã hết deadline. Application không còn thời gian serialize `ProblemDetails`, retry hợp lý hoặc fallback. Deadline cần được chia thành budget giữa các bước.

**Ví dụ:**
```text
Client deadline:       5.0 s
Application overhead:  0.5 s
Payment call budget:   2.0 s
Fallback/error path:   0.5 s
Safety margin:         2.0 s
```

Trong .NET, timeout có thể được kiểm soát bằng `HttpClient`/resilience pipeline và `CancellationToken` được propagate từ request.

**Lưu ý:**
Không cộng retry vào một cách vô hạn. Ba lần retry × 2 giây có thể phá toàn bộ deadline. Retry policy phải nằm trong tổng time budget và chỉ retry transient failure phù hợp.

### Tip 4 — Với Vue/React list lớn, stable key là correctness requirement trước khi là performance hint

**Mẹo:**
Khi render collection động, dùng identifier ổn định của entity làm `key`; tránh dùng array index nếu item có thể insert, delete hoặc reorder.

**Tại sao hữu ích:**
Framework dùng key để xác định identity giữa các lần render. Nếu key thay đổi theo vị trí, DOM/component state có thể được tái sử dụng cho item khác, dẫn đến input state, focus hoặc local component state gắn nhầm record.

**Ví dụ:**
```vue
<OrderRow
  v-for="order in orders"
  :key="order.id"
  :order="order"
/>
```

Thay vì:

```vue
:key="index"
```

khi list có reorder/filter/delete.

**Lưu ý:**
Key phải unique trong sibling list và ổn định qua render. Tạo `Guid.NewGuid()` hoặc random key trong mỗi render còn tệ hơn vì framework coi mọi item là mới.

### Tip 5 — Khi dùng AI coding agent, bắt agent chứng minh thay đổi bằng test và diff nhỏ

**Mẹo:**
Với task sửa bug hoặc refactor, yêu cầu AI agent xác định reproduction/acceptance criteria, thực hiện thay đổi giới hạn scope và chạy test liên quan trước khi coi task hoàn tất.

**Tại sao hữu ích:**
AI có thể tạo code compile được nhưng dựa trên API không tồn tại, hiểu sai invariant hoặc sửa symptom thay vì root cause. Một diff nhỏ cộng với executable verification làm review dễ hơn và giảm blast radius.

**Ví dụ:**
```text
1. Reproduce failing behavior
2. Add/identify regression test
3. Make minimum code change
4. Run targeted tests
5. Run broader affected test suite
6. Inspect final diff for unrelated changes
```

**Lưu ý:**
Test pass không chứng minh architecture đúng. Với thay đổi security, concurrency, transaction hoặc public contract, vẫn cần human review về assumptions và failure modes.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation: đừng để một dependency lỗi ăn hết tài nguyên của service

**Khái niệm:**
Bulkhead Isolation chia tài nguyên concurrency giữa các workload hoặc dependency để failure/latency của một vùng không làm toàn service cạn thread, connection hoặc queue capacity.

**Vấn đề nó giải quyết:**
Giả sử API gọi một provider tạo PDF. Provider bắt đầu mất 20 giây cho mỗi request. Nếu mọi request được phép chờ không giới hạn, connection và concurrency slot có thể bị chiếm hết; endpoint không liên quan cũng chậm theo dù database và các dependency khác vẫn khỏe.

**Ví dụ thực tế:**
```text
PDF provider:
- max 20 concurrent operations
- bounded queue
- timeout
- reject/degrade khi capacity đầy

Normal Orders API:
- dùng resource budget riêng
```

Có thể triển khai bằng concurrency limiter, bounded `Channel`, queue riêng hoặc workload isolation ở mức service tùy hệ thống.

**Trade-off:**
Bulkhead bảo vệ blast radius nhưng có thể reject request sớm dù tổng machine capacity vẫn còn. Chia quota quá cứng còn làm resource utilization kém. Capacity phải dựa trên measurement và business priority.

**Middle → Senior insight:**
Middle developer cần hiểu timeout không đủ nếu hàng nghìn operation vẫn được phép chờ đồng thời. Senior / Technical developer phải thiết kế admission control, concurrency budget, queue bound, degradation policy và observability theo từng failure domain.

### Design 2 — Strangler Fig Pattern cho modernization hệ thống .NET Framework

**Khái niệm:**
Strangler Fig Pattern thay thế legacy system từng capability thay vì rewrite toàn bộ trong một lần. Traffic hoặc use case được chuyển dần sang implementation mới trong khi phần cũ vẫn vận hành.

**Vấn đề nó giải quyết:**
Một ứng dụng .NET Framework lớn có thể chứa nhiều business rule chưa được document. Big-bang rewrite kéo dài nhiều tháng, tạo hai hệ thống phát triển song song và chỉ nhận feedback thật ở cuối dự án. Migration theo slice cho phép đưa phần mới vào production sớm hơn và giảm phạm vi mỗi lần chuyển đổi.

**Ví dụ thực tế:**
```text
Legacy ASP.NET MVC (.NET Framework)
        |
        +-- /catalog  -> ASP.NET Core .NET 10 service/module
        +-- /orders   -> legacy
        +-- /account  -> legacy
```

Sau khi `/catalog` ổn định, tiếp tục strangler capability kế tiếp. Routing có thể nằm ở reverse proxy/gateway hoặc application boundary phù hợp.

**Trade-off:**
Migration incremental giảm cutover risk nhưng tạo giai đoạn coexistence: duplicated model, integration adapter, routing, observability và đôi khi data synchronization. Nếu legacy nhỏ và well-tested, direct upgrade/rewrite có thể rẻ hơn.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility giữa legacy và phần mới. Senior / Technical developer phải chọn migration seam, data ownership, rollback strategy và thứ tự capability dựa trên business risk chứ không chỉ chọn module dễ code nhất.

### Design 3 — Authorization boundary phải nằm ở server-side use case, không dựa vào việc UI ẩn nút

**Khái niệm:**
Frontend permission giúp UX, nhưng authorization invariant phải được enforce tại API/application boundary nơi side effect thực sự xảy ra.

**Vấn đề nó giải quyết:**
Ẩn nút `Delete` trong UI không ngăn user gọi endpoint trực tiếp bằng DevTools, Postman hoặc script. Nếu backend chỉ tin rằng frontend đã lọc action, privilege escalation trở thành vấn đề contract chứ không phải UI bug.

**Ví dụ thực tế:**
```text
UI:
CanDeleteOrder == false
-> không hiển thị Delete

API:
DELETE /orders/{id}
-> authenticate
-> load resource context
-> authorize DeleteOrder trên resource
-> mới thực hiện side effect
```

Resource-based authorization đặc biệt quan trọng khi quyền phụ thuộc owner, tenant, trạng thái entity hoặc scope hỗ trợ tạm thời.

**Trade-off:**
Centralized authorization đơn giản hơn để audit nhưng policy có thể trở thành khối logic lớn. Authorization nằm gần domain/use case hiểu context tốt hơn nhưng cần convention và test nhất quán để không bỏ sót endpoint.

**Middle → Senior insight:**
Middle developer cần coi client là untrusted và enforce quyền ở backend. Senior / Technical developer phải thiết kế policy model, tenant/resource boundary, audit trail và cách đảm bảo mọi entry point — HTTP, background job, admin tool — tuân theo cùng security invariant.
