# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Kiểm soát tuổi connection của `HttpClient` để tránh giữ DNS cũ quá lâu

**Mẹo:**
Với service chạy lâu và gọi dependency qua hostname có IP thay đổi, cấu hình `PooledConnectionLifetime` phù hợp thay vì giả định connection pool sẽ tự cập nhật DNS theo mọi thay đổi hạ tầng.

**Tại sao hữu ích:**
`HttpClient` tái sử dụng connection để tránh socket exhaustion và giảm handshake cost. Nhưng connection đang sống có thể tiếp tục đi tới IP cũ sau khi DNS record thay đổi, ví dụ khi failover, scale hoặc blue/green switch.

**Ví dụ:**
```csharp
builder.Services
    .AddHttpClient<PaymentClient>()
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)
    });
```

Nếu production chỉ lỗi sau một lần đổi endpoint nhưng restart app lại hết, hãy kiểm tra DNS resolution và connection reuse trước khi nghi ngờ business logic.

**Lưu ý:**
Không đặt lifetime quá ngắn theo cảm tính vì sẽ tăng TCP/TLS handshake và giảm lợi ích pooling. Giá trị phù hợp phụ thuộc DNS TTL, network topology và traffic pattern.

### Tip 2 — Khi SQL Server deadlock, đọc deadlock graph thay vì chỉ tăng timeout

**Mẹo:**
Nếu application nhận lỗi deadlock, thu deadlock graph từ Extended Events hoặc monitoring tool để xác định transaction nào khóa resource nào và theo thứ tự nào.

**Tại sao hữu ích:**
Deadlock là vòng chờ khóa, không phải đơn thuần query “chạy lâu”. Tăng command timeout không phá được vòng chờ và có thể chỉ làm transaction giữ resource lâu hơn. Root cause thường nằm ở lock order, transaction scope hoặc access path khác nhau giữa hai code path.

**Ví dụ:**
```text
Transaction A:
1. update Orders
2. update Inventory

Transaction B:
1. update Inventory
2. update Orders

=> lock order ngược nhau có thể tạo cycle
```

Sau khi có deadlock graph, so sánh object/index, statement và transaction duration rồi sửa theo evidence, ví dụ chuẩn hóa lock order hoặc thu ngắn transaction.

**Lưu ý:**
Retry deadlock victim thường cần thiết vì deadlock có thể vẫn xảy ra dưới concurrency, nhưng retry không thay thế việc sửa pattern gây deadlock nếu tần suất cao.

### Tip 3 — Với Azure Blob Storage, ưu tiên direct upload bằng SAS ngắn hạn khi file lớn

**Mẹo:**
Nếu browser/mobile client upload file lớn, cân nhắc backend cấp SAS giới hạn quyền và thời gian để client upload trực tiếp lên Blob Storage thay vì proxy toàn bộ byte qua ASP.NET Core.

**Tại sao hữu ích:**
Backend proxy làm application chịu toàn bộ network bandwidth, connection duration và memory/buffering pressure. Direct upload giảm tải web tier và giúp Blob Storage xử lý throughput tốt hơn.

**Ví dụ:**
```text
1. Client gọi POST /uploads/request
2. Backend kiểm tra authorization + filename/size policy
3. Backend cấp SAS chỉ có Create/Write cho một blob cụ thể, hết hạn sau vài phút
4. Client upload trực tiếp lên Blob Storage
5. Backend xử lý metadata/scanning sau upload
```

**Lưu ý:**
SAS phải có scope tối thiểu, expiry ngắn và không cho list/read nếu không cần. Direct upload cũng không loại bỏ malware scanning, content validation hoặc quota enforcement.

### Tip 4 — Trong React, tránh stale closure khi async callback đọc state đã cũ

**Mẹo:**
Khi callback async hoặc timer phụ thuộc state mới nhất, đừng giả định closure luôn nhìn thấy giá trị hiện tại. Hãy dùng dependency đúng, functional state update hoặc `ref` khi thực sự cần giá trị mutable mới nhất.

**Tại sao hữu ích:**
Function component capture giá trị state tại lần render tạo callback. Một timer hoặc promise hoàn tất sau đó có thể dùng state cũ và ghi đè cập nhật mới, tạo bug khó tái hiện dưới timing khác nhau.

**Ví dụ:**
```tsx
setCount(current => current + 1);
```

Thay vì:

```tsx
setCount(count + 1);
```

trong callback có thể chạy sau nhiều render nếu logic cần dựa trên giá trị hiện tại.

**Lưu ý:**
Không dùng `useRef` để né toàn bộ dependency rule. Ref phù hợp cho mutable value không cần trigger render; lạm dụng nó dễ che luồng state và làm component khó reasoning hơn.

### Tip 5 — Dùng `dotnet-trace` khi CPU cao nhưng log không chỉ ra hot path

**Mẹo:**
Khi .NET process có CPU spike mà logs chỉ cho biết triệu chứng, capture runtime trace để tìm method hoặc call stack tiêu tốn CPU thay vì thêm logging ngẫu nhiên.

**Tại sao hữu ích:**
Structured logs cho biết sự kiện gì xảy ra nhưng không nhất thiết cho biết CPU đang bị tiêu ở đâu. Sampling/profile trace có thể chỉ ra JSON serialization, regex, LINQ hot loop, lock contention hoặc library call chiếm phần lớn thời gian.

**Ví dụ:**
```bash
dotnet-trace collect --process-id 1234
```

Sau đó phân tích trace bằng công cụ phù hợp và correlate thời điểm spike với request/deployment/metric.

**Lưu ý:**
Profiling production có overhead. Capture trong khoảng ngắn, có kiểm soát và phù hợp incident policy; đừng bật diagnostic session nặng kéo dài trên hệ thống đang chịu tải cao.

## 🧠 Software Design

### Design 1 — Hexagonal Architecture chỉ đáng giá khi boundary thực sự cần bảo vệ

**Khái niệm:**
Hexagonal Architecture đặt domain/application logic phía trong và giao tiếp với database, HTTP, messaging hoặc file system qua ports/adapters. Giá trị nằm ở việc giữ policy nghiệp vụ độc lập khỏi delivery/infrastructure detail, không nằm ở số lượng interface.

**Vấn đề nó giải quyết:**
Khi business logic bị trộn trực tiếp với EF Core, HTTP client, queue SDK hoặc framework lifecycle, thay đổi integration hoặc test use case trở nên khó vì concern kỹ thuật đã lan vào core logic.

**Ví dụ thực tế:**
```text
Application use case: ApproveInvoice
Port: IInvoiceStore
Port: IPaymentGateway

Adapters:
- EF CoreInvoiceStore
- ExternalPaymentGateway
```

Nếu module chỉ là CRUD mỏng quanh một table, thêm đầy đủ ports/adapters cho mọi operation có thể tạo ceremony lớn hơn giá trị mang lại.

**Trade-off:**
Hexagonal Architecture tăng boundary clarity, testability và khả năng thay adapter, nhưng thêm abstraction, mapping và cognitive load. Với hệ thống nhỏ hoặc logic đơn giản, layered architecture trực tiếp có thể rẻ và dễ vận hành hơn.

**Middle → Senior insight:**
Middle developer cần giữ business rule khỏi phụ thuộc ngẫu nhiên vào infrastructure. Senior / Technical developer phải quyết định boundary nào đủ ổn định và quan trọng để đáng trả abstraction cost, thay vì áp pattern đồng đều lên toàn codebase.

### Design 2 — Inbox Pattern để consumer xử lý duplicate message an toàn

**Khái niệm:**
Inbox Pattern lưu identifier của message đã xử lý cùng với business transaction phía consumer, để message được giao lại không tạo side effect lần hai.

**Vấn đề nó giải quyết:**
Message broker thường cung cấp at-least-once delivery. Consumer có thể commit database thành công nhưng crash trước khi acknowledge broker; cùng message sau đó được redeliver dù business change đã xảy ra.

**Ví dụ thực tế:**
```text
Nhận OrderPaid(messageId=abc)

Transaction:
1. kiểm tra Inbox có abc chưa
2. nếu chưa: update Order -> Paid
3. insert Inbox(abc)
4. commit

Message abc đến lại:
-> phát hiện đã xử lý
-> bỏ qua side effect
```

**Trade-off:**
Inbox giúp consumer idempotent có durability tốt hơn cache-based deduplication, nhưng thêm storage, unique constraint, retention/cleanup và transaction coupling với datastore local.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là behavior bình thường chứ không phải exception hiếm. Senior / Technical developer phải chọn deduplication key, retention window, transaction scope và cách xử lý message có cùng ID nhưng payload không nhất quán.

### Design 3 — Primary database và Elasticsearch cần một synchronization contract rõ ràng

**Khái niệm:**
Khi Elasticsearch phục vụ search còn SQL/MongoDB là source of truth, hệ thống cần xác định rõ cách thay đổi từ transactional store được phản ánh sang search index và cách phục hồi khi synchronization thất bại.

**Vấn đề nó giải quyết:**
Nếu application ghi database rồi gọi Elasticsearch đồng bộ trong cùng request, một dependency failure có thể làm API fail dù transaction chính đã commit. Nếu chỉ cập nhật search theo best effort, index có thể âm thầm lệch dữ liệu trong thời gian dài.

**Ví dụ thực tế:**
```text
Product update
-> commit primary DB
-> ghi outbox/event
-> indexer consume event
-> update Elasticsearch
-> retry/DLQ nếu indexing fail
-> periodic reconciliation phát hiện drift
```

Search có thể chậm vài giây so với source of truth nếu business chấp nhận eventual consistency.

**Trade-off:**
Asynchronous synchronization tách failure và giảm latency của write path, nhưng thêm eventual consistency, replay, ordering và reconciliation. Synchronous dual-write đơn giản hơn về flow nhìn thấy nhưng tạo distributed failure window khó đảm bảo atomicity.

**Middle → Senior insight:**
Middle developer cần hiểu Elasticsearch không phải bản sao tự đồng bộ của database. Senior / Technical developer phải định nghĩa source of truth, freshness SLA, ordering, reindex strategy, replay/reconciliation và behavior người dùng khi search chưa phản ánh write mới nhất.
