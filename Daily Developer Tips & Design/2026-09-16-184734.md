# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` khi cần stream kết quả thay vì buffer toàn bộ

**Mẹo:**
Với endpoint hoặc background pipeline xử lý tập dữ liệu lớn, cân nhắc `IAsyncEnumerable<T>` để đọc và xử lý từng phần thay vì `ToListAsync()` toàn bộ trước.

**Tại sao hữu ích:**
Buffer toàn bộ result làm tăng peak memory và trì hoãn thời điểm consumer nhận item đầu tiên. Async streaming cho phép database/client và application tiến hành theo pipeline, đặc biệt hữu ích khi result lớn hoặc processing mỗi item tốn thời gian.

**Ví dụ:**
```csharp
await foreach (var order in db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .AsAsyncEnumerable()
    .WithCancellation(cancellationToken))
{
    await ProcessAsync(order, cancellationToken);
}
```

**Lưu ý:**
Streaming giữ database reader/connection mở trong thời gian enumeration. Đừng thực hiện outbound call rất chậm cho từng row nếu điều đó giữ connection quá lâu; khi cần, đọc theo bounded batches rồi giải phóng database resource.

### Tip 2 — Đừng dùng `Task.Run` để “làm async” I/O trong ASP.NET Core

**Mẹo:**
Với database, HTTP, file hoặc cloud SDK đã có async API, await trực tiếp thay vì bọc operation bằng `Task.Run`.

**Tại sao hữu ích:**
Async I/O giải phóng thread trong lúc chờ completion. `Task.Run` lại đưa work lên ThreadPool và không biến synchronous I/O thành scalable I/O; dưới load cao, việc bọc blocking calls có thể góp phần gây ThreadPool starvation.

**Ví dụ:**
```csharp
// Tốt
var response = await httpClient.GetAsync(url, cancellationToken);

// Không nên chỉ để "async hóa"
var response = await Task.Run(
    () => httpClient.GetAsync(url, cancellationToken),
    cancellationToken);
```

**Lưu ý:**
`Task.Run` vẫn có chỗ dùng cho CPU-bound work có chủ đích, nhưng trong server request path cần cân nhắc CPU budget và concurrency. Với heavy CPU workloads, dedicated worker/process thường kiểm soát tài nguyên tốt hơn.

### Tip 3 — Kiểm tra lock wait trước khi kết luận database “CPU chậm”

**Mẹo:**
Khi API database-backed tăng latency nhưng query plan nhìn có vẻ ổn, kiểm tra blocking/lock waits và transaction duration trước khi tối ưu SQL text.

**Tại sao hữu ích:**
Một transaction mở quá lâu có thể giữ locks khiến nhiều query khác chờ. Symptoms ở application là request chậm, nhưng CPU database có thể vẫn thấp; thêm index hoặc scale CPU không xử lý nguyên nhân.

**Ví dụ:**
```text
Symptom: p95 API 120 ms -> 8 s
Evidence: DB CPU 35%, connection count tăng
Hypothesis: blocking
Check: active requests + wait type + blocking session + open transaction
Diagnosis: transaction giữ lock trong lúc gọi external API
Fix: thu hẹp transaction boundary
```

**Lưu ý:**
Không kill blocking session một cách máy móc. Xác định transaction owner, rollback cost và business impact; root cause thường nằm ở transaction scope hoặc access pattern chứ không chỉ ở session đang đứng đầu blocking chain.

### Tip 4 — Đặt giới hạn cardinality cho metrics labels

**Mẹo:**
Trong OpenTelemetry/Application Insights metrics, chỉ dùng labels/tags có tập giá trị hữu hạn như route template, status class hoặc operation type; tránh `userId`, `orderId`, raw URL và exception message.

**Tại sao hữu ích:**
Mỗi combination của metric dimensions có thể tạo một time series riêng. High-cardinality labels làm telemetry backend tốn memory/storage, query chậm và tăng chi phí, trong khi dashboard lại khó sử dụng.

**Ví dụ:**
```text
Tốt:
http.server.duration{route="/orders/{id}",status_code="200"}

Không tốt:
http.server.duration{url="/orders/8f2c...",user_id="123456"}
```
Identifiers cụ thể phù hợp hơn với traces/logs có sampling và data-governance phù hợp.

**Lưu ý:**
Đừng loại bỏ dimensions đến mức metric mất khả năng phân tích. Thiết kế telemetry dựa trên câu hỏi vận hành cần trả lời và cardinality budget, không dựa trên việc field nào đang tiện có sẵn.

### Tip 5 — Dùng `AbortController` để hủy request frontend đã lỗi thời

**Mẹo:**
Trong Vue.js/React.js search hoặc filter UI, hủy fetch cũ khi query mới xuất hiện thay vì để mọi request chạy đến hết.

**Tại sao hữu ích:**
Nếu user gõ nhanh, response của query cũ có thể về sau response mới và overwrite state bằng dữ liệu stale. Cancellation vừa giảm network/work không cần thiết vừa loại bỏ một lớp race condition.

**Ví dụ:**
```ts
let controller: AbortController | undefined

async function search(q: string) {
  controller?.abort()
  controller = new AbortController()

  const response = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  })

  return response.json()
}
```

**Lưu ý:**
Client cancellation không đảm bảo server đã rollback mọi side effect. Với command API, correctness vẫn cần idempotency và transaction semantics ở backend; cancellation chủ yếu là signal để ngừng work khi còn hợp lý.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency thay vì “last write wins” âm thầm

**Khái niệm:**
Optimistic Concurrency cho phép nhiều reader làm việc song song nhưng khi update sẽ kiểm tra version/token để phát hiện dữ liệu đã bị thay đổi kể từ lúc đọc.

**Vấn đề nó giải quyết:**
Hai nhân viên mở cùng Order. Người A đổi shipping address, người B đổi status từ bản dữ liệu cũ. Nếu update không kiểm tra concurrency, write sau có thể âm thầm ghi đè thay đổi trước.

**Ví dụ thực tế:**
SQL Server `rowversion` được map thành EF Core concurrency token. `UPDATE` chứa điều kiện cả `Id` và version cũ; nếu affected rows bằng 0, EF Core ném `DbUpdateConcurrencyException`. Application sau đó quyết định reload, merge hoặc yêu cầu user xử lý conflict.

**Trade-off:**
Optimistic Concurrency tránh lock dài và phù hợp khi conflicts hiếm, nhưng conflict handling chuyển thành trách nhiệm application. Pessimistic locking có thể hợp hơn với critical section ngắn và contention cao, nhưng làm tăng blocking/deadlock risk.

**Middle → Senior insight:**
Middle developer cần cấu hình token và xử lý `DbUpdateConcurrencyException` đúng. Senior / Technical developer phải xác định invariant nào cho phép merge, operation nào phải reject, UX conflict ra sao và liệu optimistic hay pessimistic strategy phù hợp với contention thực tế.

### Design 2 — Queue hay Topic phụ thuộc delivery semantics, không phụ thuộc tên nghiệp vụ

**Khái niệm:**
Queue thường biểu diễn một stream work nơi một message được một competing consumer xử lý. Topic + subscriptions fan-out cùng event cho nhiều consumer groups độc lập.

**Vấn đề nó giải quyết:**
Nếu `OrderCreated` cần Inventory, Analytics và Notification cùng nhận nhưng tất cả cùng consume một queue, các consumers sẽ cạnh tranh và mỗi message chỉ đến một trong số chúng thay vì cả ba capability.

**Ví dụ thực tế:**
Azure Service Bus Topic `order-events` có subscription riêng cho Inventory, Analytics và Notification. Ngược lại, `generate-invoice` có thể là queue với nhiều Invoice Worker instances cạnh tranh để scale throughput.

**Trade-off:**
Topic giảm producer-consumer coupling và hỗ trợ fan-out nhưng tăng subscriptions, filtering, DLQ monitoring và duplicate handling. Queue đơn giản hơn cho work distribution nhưng không cung cấp independent fan-out semantics.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumers, retries, DLQ và idempotency. Senior / Technical developer phải chọn topology dựa trên ownership, delivery semantics, ordering, replay/recovery và operational cost; đừng biến mọi command thành event hoặc mọi event thành queue work.

### Design 3 — Strangler Fig cho modernization thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig migration thay thế legacy system từng capability: routing một phần traffic/workflow sang implementation mới trong khi phần cũ tiếp tục phục vụ những capability chưa migrate.

**Vấn đề nó giải quyết:**
Một .NET Framework/CMS monolith lớn có nhiều hidden behaviors và integrations. Big-bang rewrite kéo dài thời gian không tạo business value và thường phát hiện requirements ngầm quá muộn.

**Ví dụ thực tế:**
Team giữ legacy checkout nhưng tách Product Search thành ASP.NET Core service mới. Gateway/routing layer chuyển search traffic sang hệ thống mới; telemetry so sánh behavior, sau đó lần lượt migrate catalog và pricing khi boundaries đã rõ.

**Trade-off:**
Incremental migration giảm cutover risk và cho phép học dần, nhưng trong thời gian chuyển tiếp phải vận hành hai implementations, routing, data synchronization và compatibility adapters. Migration kéo quá lâu có thể tạo permanent hybrid complexity.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility, characterization tests và observability khi thay từng slice. Senior / Technical developer phải chọn migration seam, dependency direction, data ownership, rollback strategy và exit criteria; mục tiêu không phải tạo microservices mà là giảm rủi ro modernization có kiểm soát.
