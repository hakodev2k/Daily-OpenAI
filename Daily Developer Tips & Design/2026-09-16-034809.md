## Developer Tips & Tricks

### 1. .NET GC: đừng gọi `GC.Collect()` để “giải phóng RAM” khi chưa hiểu allocation pressure

**Vấn đề thực tế:** Một ASP.NET Core service tăng memory sau khi xử lý batch lớn. Team thấy working set chưa giảm ngay nên gọi `GC.Collect()` sau mỗi batch. Memory graph có vẻ đẹp hơn trong vài thời điểm, nhưng throughput giảm và latency tail tăng.

**Cơ chế bên dưới:** .NET GC là generational collector. Object sống ngắn thường được thu gom ở Gen 0/Gen 1 với chi phí thấp; object sống lâu được promote lên Gen 2. Forced full collection có thể quét các generation đắt hơn dù runtime chưa cần, làm tăng pause và CPU. Working set của process cũng không đồng nghĩa với managed live objects: runtime có thể giữ segment đã reserve/commit để tái sử dụng thay vì lập tức trả toàn bộ memory về OS.

Large Object Heap thường nhận allocation lớn và được collect cùng Gen 2, nên các buffer lớn sống ngắn có thể tạo pressure đáng kể. Root cause cần được xác nhận bằng metrics/profiling thay vì suy luận từ Task Manager.

```bash
dotnet-counters monitor --process-id <pid> System.Runtime

dotnet-gcdump collect --process-id <pid>
```

Theo dõi các tín hiệu như allocation rate, GC heap size, Gen 2 collections, LOH size và pause time. Nếu buffer lớn được tạo liên tục, cân nhắc streaming, pooling hoặc giảm kích thước allocation trước khi nghĩ đến forced GC.

**Khi nên dùng:** Khi điều tra memory growth, high allocation rate, Gen 2 GC tăng, latency spike hoặc service có workload xử lý payload/buffer lớn.

### 2. Redis cache stampede: TTL không đủ nếu hàng nghìn request cùng rebuild một key hết hạn

**Vấn đề thực tế:** Product catalog được cache 10 phút. Khi key hết hạn, hàng nghìn request gần như đồng thời cache-miss rồi cùng query SQL. Redis vẫn khỏe nhưng database CPU tăng đột biến đúng mỗi chu kỳ TTL.

**Cơ chế bên dưới:** Cache-aside tạo một race window: mọi caller nhìn thấy key không tồn tại trước khi caller đầu tiên rebuild xong. TTL chỉ quyết định khi entry hết hạn, không serialize regeneration. Nếu nhiều hot keys có cùng TTL, expiration đồng bộ còn tạo burst lớn hơn.

**Cách xử lý:** Kết hợp TTL jitter để phân tán expiration và single-flight/per-key locking để chỉ một execution rebuild dữ liệu. Những caller khác có thể đợi ngắn hoặc nhận stale value nếu business cho phép.

```csharp
var ttl = TimeSpan.FromMinutes(10)
          + TimeSpan.FromSeconds(Random.Shared.Next(0, 60));

await cache.SetStringAsync(
    cacheKey,
    JsonSerializer.Serialize(result),
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = ttl
    },
    cancellationToken);
```

Jitter chỉ giảm synchronized expiry; nó không tự giải quyết nhiều request cạnh tranh trên cùng một hot key. Distributed lock cũng cần lease/timeout hợp lý để tránh biến cache thành điểm nghẽn mới.

**Khi nên dùng:** Hot catalog/search/configuration data, expensive aggregation, multi-instance APIs và workload có traffic burst quanh thời điểm cache expiration.

### 3. OpenAPI contract: một thay đổi “compile được” vẫn có thể là breaking change với client

**Vấn đề thực tế:** Backend đổi property `status` từ optional thành required hoặc đổi enum từ string sang integer. Server build và integration tests nội bộ đều pass, nhưng mobile app hoặc generated client cũ bắt đầu deserialize lỗi sau deployment.

**Cơ chế bên dưới:** API compatibility là contract giữa independently deployed components, không phải chỉ là type compatibility trong server code. Breaking change có thể xuất hiện khi rename/remove field, đổi nullability, đổi status code semantics, siết validation, thay enum representation hoặc đổi route/query behavior.

**Cách làm tốt hơn:** Lưu OpenAPI artifact của release trước và chạy contract-diff trong CI. Phân loại breaking changes trước khi deploy; khi cần evolution, ưu tiên additive change và giữ behavior cũ đủ lâu cho consumers migrate.

```text
PR
 |
 +--> Build API
 |
 +--> Generate openapi.json
 |
 +--> Compare with released contract
 |        |
 |        +--> compatible -> continue
 |        |
 |        +--> breaking -> fail/review/version strategy
 |
 +--> integration / consumer tests
```

Đừng mặc định API versioning là lời giải cho mọi thay đổi. Mỗi version mới tạo thêm maintenance, documentation, routing và deprecation cost.

**Khi nên dùng:** Public APIs, mobile backends, partner integrations, frontend/backend deploy độc lập và hệ thống dùng generated SDK/client.

### 4. Application Insights: sampling phải giữ được trace hữu ích, không chỉ giảm telemetry bill

**Vấn đề thực tế:** Production traffic tăng mạnh nên team bật sampling để giảm ingestion cost. Sau đó một lỗi hiếm xuất hiện nhưng trace điều tra thiếu dependency spans hoặc request liên quan, khiến root-cause analysis gần như không thể thực hiện.

**Cơ chế bên dưới:** Distributed trace có giá trị khi spans thuộc cùng trace được giữ hoặc loại một cách nhất quán. Sampling ngẫu nhiên từng telemetry item có thể tạo trace rời rạc. Ngoài ra, error/rare-path telemetry có giá trị điều tra cao hơn request thành công phổ biến.

**Cách làm tốt hơn:** Thiết kế sampling theo mục tiêu observability: giữ correlation, ưu tiên error/critical signals, theo dõi effective sampling rate và đảm bảo metrics quan trọng không bị hiểu sai vì sampled event count.

```text
Incoming Request
      |
      +--> trace-id = abc
      |
      +--> SQL dependency
      |
      +--> HTTP dependency
      |
      +--> exception

Sampling decision nên bảo toàn khả năng nối chuỗi trace-id = abc.
```

Cost control nên bắt đầu từ telemetry quality: loại noisy debug logs, tránh high-cardinality dimensions không cần thiết và xác định signal nào thực sự phục vụ alerting/RCA.

**Khi nên dùng:** High-throughput services, Application Insights/OpenTelemetry pipelines, hệ thống có telemetry cost cao hoặc incident investigation phụ thuộc distributed tracing.

### 5. Optimizely/CMS caching: cache content theo published identity, đừng để editorial update phục vụ dữ liệu stale

**Vấn đề thực tế:** Website cache rendered navigation hoặc content DTO theo URL trong Redis. Editor publish phiên bản mới nhưng cache key vẫn tồn tại đến hết TTL, khiến người dùng tiếp tục thấy nội dung cũ trong nhiều phút. Giảm TTL xuống vài giây chỉ chuyển vấn đề thành cache hit ratio thấp và tăng backend load.

**Cơ chế bên dưới:** CMS content có lifecycle và versioning riêng. Cache correctness cần gắn với publication/invalidation semantics, không chỉ wall-clock expiration. Một publish event có thể ảnh hưởng trực tiếp content vừa sửa và gián tiếp các aggregate như navigation, listing hoặc related-content widgets.

**Cách xử lý:** Xác định dependency graph của cached representation và invalidate theo content event. Có thể version cache key bằng content/version token hoặc phát invalidation event tới các node/cache layer liên quan. TTL vẫn hữu ích như safety net nhưng không nên là cơ chế consistency duy nhất.

```text
Editor publishes Page A
        |
        v
Content Published Event
        |
        +--> invalidate page:A:* 
        +--> invalidate navigation:site:*
        +--> invalidate listing:<affected-container>
        |
        v
Next request rebuilds from published content
```

**Khi nên dùng:** Optimizely CMS, headless CMS, navigation trees, content listings, CDN/Redis caching và hệ thống có editorial publish cần phản ánh nhanh ra website.

## Software Design

### 6. Hexagonal Architecture: port bảo vệ business capability khỏi transport và persistence details

**Vấn đề thực tế:** Application service nhận trực tiếp `HttpContext`, dùng EF Core entity làm request model và gọi Azure SDK trong domain workflow. Business rule “approve refund” chỉ test được khi dựng web host, database và cloud dependency.

**Thiết kế:** Hexagonal Architecture đặt business/application logic ở phía trong. Inbound adapters như HTTP/message consumer gọi application ports; outbound ports mô tả capability mà application cần, còn adapters triển khai SQL, HTTP, Azure Service Bus hoặc vendor API.

```text
        HTTP Adapter
             |
             v
      [ApproveRefund]
       Application Port
             |
       Business Logic
        /          \
       v            v
Payment Port     Refund Store Port
    |                 |
    v                 v
Vendor Adapter     EF Core Adapter
```

**Trade-off:** Boundary rõ giúp test business behavior độc lập và thay infrastructure ít lan truyền. Nhưng mỗi port/adapter tạo abstraction, mapping và naming cost. CRUD module nhỏ không có volatile external boundary có thể trở nên ceremony-heavy nếu áp dụng máy móc.

**Khi phù hợp:** Business logic quan trọng, nhiều external integrations, infrastructure có khả năng thay đổi hoặc cần test domain/application behavior mà không dựng toàn stack.

### 7. Saga orchestration vs choreography: chọn nơi đặt workflow state một cách có chủ đích

**Vấn đề thực tế:** Order workflow đi qua Inventory, Payment và Shipping. Không có distributed ACID transaction. Nếu Payment thành công nhưng Shipping thất bại, hệ thống cần biết bước nào đã hoàn tất và compensation nào phải chạy.

**Thiết kế:** Với choreography, services phản ứng với events của nhau; coupling ở compile-time thấp nhưng workflow tổng thể dễ bị phân tán qua nhiều consumers. Với orchestration, một coordinator giữ workflow state và ra lệnh cho từng participant; flow dễ quan sát hơn nhưng orchestrator trở thành component quan trọng phải được thiết kế resilient.

```text
Orchestration:

Order Saga
   |
   +--> Reserve Inventory
   |        |
   |      success
   v
Capture Payment
   |
   +--> failure
   |
   v
Release Inventory (compensation)
```

**Trade-off:** Choreography phù hợp khi event relationships đơn giản và services thực sự autonomous. Khi workflow dài, nhiều branch/timeout/compensation, orchestration thường làm state machine và operational visibility rõ hơn. Orchestrator không nên chứa domain logic thuộc ownership của participant services.

**Khi phù hợp:** Multi-service business transactions không thể dùng một local database transaction và cần explicit compensation/recovery.

### 8. Architecture Decision Record: lưu “vì sao” của quyết định trước khi context biến mất

**Vấn đề thực tế:** Sáu tháng sau, developer thấy hệ thống dùng PostgreSQL advisory lock thay vì Redis distributed lock và cho rằng đây là code smell cần refactor. Không ai còn nhớ rằng workload có transaction coupling với PostgreSQL, team cố tình tránh thêm Redis dependency và throughput requirement rất thấp.

**Thiết kế:** ADR ghi lại context, decision, alternatives và consequences tại thời điểm quyết định. Nó không phải tài liệu mô tả toàn kiến trúc; mục tiêu là bảo tồn reasoning và trade-off để quyết định sau này có thể được đánh giá dựa trên assumptions ban đầu.

```text
ADR-017: Use PostgreSQL advisory lock for settlement job

Status: Accepted
Context:
- Single PostgreSQL-backed workload
- Low lock throughput
- No existing Redis dependency

Decision:
- Use transaction-scoped advisory lock

Consequences:
+ No new infrastructure
+ Lock follows DB transaction lifecycle
- PostgreSQL-specific
- Revisit if workload is split across databases
```

**Trade-off:** ADR quá dài hoặc bắt buộc cho mọi chi tiết nhỏ sẽ bị bỏ qua. ADR nên dành cho decision có consequence đáng kể, alternative hợp lý hoặc assumption có thể thay đổi. Khi assumption đổi, tạo ADR mới supersede quyết định cũ thay vì âm thầm sửa lịch sử.

**Khi phù hợp:** Architecture boundaries, database/message broker selection, authentication strategy, deployment model, caching consistency, migration strategy và các technical decisions có tác động dài hạn.
