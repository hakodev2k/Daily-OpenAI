# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup table bất biến, đọc nhiều

**Mẹo:**
Nếu một tập key/value được build một lần rồi đọc rất nhiều lần, cân nhắc `FrozenDictionary<TKey,TValue>` thay vì giữ `Dictionary<TKey,TValue>` mutable.

**Tại sao hữu ích:**
Frozen collections tối ưu cho read-heavy workload sau khi construction và đồng thời làm rõ rằng shared state không còn thay đổi.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

var map = new Dictionary<string, int>
{
    ["Pending"] = 1,
    ["Paid"] = 2
}.ToFrozenDictionary();
```

**Lưu ý:**
Chi phí freeze xảy ra lúc tạo collection. Không phù hợp với dữ liệu thay đổi thường xuyên hoặc collection chỉ được đọc ít lần.

### Tip 2 — Với ASP.NET Core, validate `ForwardedHeaders` trước khi tin `RemoteIpAddress`

**Mẹo:**
Nếu ứng dụng chạy sau reverse proxy, load balancer hoặc CDN, cấu hình `ForwardedHeaders` và trusted proxies/networks trước khi dùng client IP cho logging, policy hoặc audit.

**Tại sao hữu ích:**
Nếu proxy chain không được cấu hình đúng, application có thể chỉ thấy IP của proxy hoặc đọc header không đáng tin. Điều này làm telemetry và policy dựa trên client origin bị sai.

**Ví dụ:**
```csharp
app.UseForwardedHeaders();
```

Sau đó xác nhận `X-Forwarded-For`, proxy topology và known networks trong environment thật.

**Lưu ý:**
Không chấp nhận forwarded headers từ mọi nguồn một cách mặc định. Cấu hình trust boundary phải khớp hạ tầng thực tế.

### Tip 3 — Dùng `FOR UPDATE SKIP LOCKED` cho worker cạnh tranh trên PostgreSQL

**Mẹo:**
Khi nhiều worker cùng lấy work từ một bảng PostgreSQL, `FOR UPDATE SKIP LOCKED` giúp worker bỏ qua row đang bị worker khác giữ lock và tiếp tục lấy row khác.

**Tại sao hữu ích:**
Cách này giảm blocking khi nhiều consumer cùng xử lý hàng đợi nội bộ và giúp throughput ổn định hơn trong workload vừa phải.

**Ví dụ:**
```sql
SELECT id
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

**Lưu ý:**
Bạn vẫn cần retry, recovery và trạng thái rõ ràng cho job bị gián đoạn. Database table không thay thế message broker trong mọi trường hợp.

### Tip 4 — Dùng Elasticsearch alias để chuyển index sau reindex

**Mẹo:**
Khi mapping thay đổi buộc phải reindex, tạo index mới rồi chuyển alias sang index mới sau khi validation xong thay vì thay trực tiếp index đang phục vụ traffic.

**Tại sao hữu ích:**
Alias giữ logical index name ổn định cho application và cho phép cut-over nhanh sau khi dữ liệu, mapping và query behavior đã được kiểm tra.

**Ví dụ:**
```text
products -> products-v12

1. tạo products-v13
2. reindex
3. verify
4. switch alias products -> products-v13
```

**Lưu ý:**
Nếu vẫn có write trong lúc reindex, cần chiến lược đồng bộ để tránh data drift trước khi chuyển alias.

### Tip 5 — Dùng `startupProbe` khi container cần startup lâu

**Mẹo:**
Nếu ASP.NET Core container cần thời gian warm-up, migration check hoặc preload cache, dùng `startupProbe` để Kubernetes biết process vẫn đang khởi động thay vì nới lỏng probe khác quá mức.

**Tại sao hữu ích:**
Startup chậm và runtime unhealthy là hai trạng thái khác nhau. Tách chúng giúp rollout ổn định hơn và tránh restart loop chỉ vì application chưa kịp sẵn sàng.

**Ví dụ:**
```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 5
```

**Lưu ý:**
Không biến startup probe thành nơi chạy logic đắt đỏ. Endpoint nên phản ánh trạng thái khởi động thay vì tự tạo thêm tải.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation cho dependency có failure profile khác nhau

**Khái niệm:**
Bulkhead chia tài nguyên như concurrency slot, connection hoặc queue giữa các dependency thay vì để tất cả dùng chung một pool.

**Vấn đề nó giải quyết:**
Một dependency chậm có thể chiếm hết tài nguyên chung và làm feature không liên quan cũng suy giảm.

**Ví dụ thực tế:**
```text
Payment API: concurrency budget riêng
Recommendation API: concurrency budget riêng
Inventory API: pool riêng
```

Nếu Recommendation chậm, checkout vẫn giữ được capacity cần thiết.

**Trade-off:**
Isolation giảm blast radius nhưng có thể làm resource utilization kém linh hoạt hơn và tăng tuning overhead.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency limit và backpressure. Senior / Technical developer phải quyết định boundary nào đáng cô lập, quota bao nhiêu và degraded behavior khi từng partition bão hòa.

### Design 2 — Giữ database transaction ngắn khi workflow có external I/O

**Khái niệm:**
Database transaction nên bao phủ state cần atomicity trong database. External HTTP call thường không nằm trong cùng ACID boundary, nên giữ transaction mở trong lúc chờ network dễ kéo dài lock mà vẫn không tạo atomicity end-to-end.

**Vấn đề nó giải quyết:**
Transaction dài làm blocking tăng, connection bị giữ lâu và failure giữa database với external system vẫn cần recovery riêng.

**Ví dụ thực tế:**
```text
1. lưu Order = PendingPayment
2. commit
3. gọi payment provider
4. lưu kết quả ở transaction mới
5. dùng idempotency/recovery nếu call bị gián đoạn
```

**Trade-off:**
Transaction ngắn tăng throughput nhưng workflow có thể chuyển sang eventual consistency và cần intermediate state rõ ràng.

**Middle → Senior insight:**
Middle developer cần tránh đặt external I/O vào transaction chỉ vì muốn “an toàn”. Senior / Technical developer phải xác định invariant nào cần atomicity thật và chọn compensation, idempotency hoặc messaging khi boundary trải qua nhiều system.

### Design 3 — Feature Flag tách deployment khỏi release nhưng phải có lifecycle

**Khái niệm:**
Feature Flag cho phép code đã deploy nhưng behavior chỉ bật cho một nhóm user, tenant hoặc tỷ lệ traffic nhất định.

**Vấn đề nó giải quyết:**
Team có thể rollout dần, quan sát production metrics và tắt behavior mới nhanh mà không cần build lại binary.

**Ví dụ thực tế:**
```text
SearchV2:
internal users -> 5% -> 25% -> 100%
```

Nếu metric xấu, disable flag trong khi giữ deployment hiện tại.

**Trade-off:**
Flag giảm release risk nhưng tạo nhiều code path, test matrix và technical debt nếu không được cleanup.

**Middle → Senior insight:**
Middle developer cần test cả enabled/disabled path. Senior / Technical developer phải định nghĩa ownership, default behavior khi configuration unavailable, telemetry theo cohort và deadline xóa flag.
