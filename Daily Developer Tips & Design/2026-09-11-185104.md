# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsSplitQuery` khi nhiều `Include` tạo cartesian explosion

**Mẹo:**
Khi EF Core query một aggregate có nhiều collection navigation bằng `Include`, kiểm tra SQL sinh ra và cân nhắc `AsSplitQuery()` nếu một query JOIN lớn làm số row trung gian tăng mạnh.

**Tại sao hữu ích:**
Nếu `Order` có 20 `Items` và 10 `Notes`, một JOIN cùng lúc có thể tạo tới 200 row trung gian cho cùng một `Order`. Application phải nhận nhiều dữ liệu lặp, materialize rồi deduplicate entity, làm tăng network traffic, allocation và CPU dù số entity thực tế không nhiều.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == orderId, ct);
```

Hãy so sánh SQL, row count và latency bằng logging/profiler trước và sau khi đổi.

**Lưu ý:**
`AsSplitQuery` đổi một query lớn thành nhiều query, nên có thêm round trip và có thể quan sát dữ liệu hơi khác giữa các query nếu concurrent update xảy ra. Nếu chỉ cần vài field để hiển thị, projection sang DTO thường tốt hơn cả `Include` lẫn split query.

### Tip 2 — Map lỗi API thành `ProblemDetails` theo loại failure, đừng biến mọi exception thành HTTP 500

**Mẹo:**
Trong ASP.NET Core, xây error-handling boundary để phân biệt validation error, resource not found, conflict và unexpected failure rồi trả `ProblemDetails` phù hợp.

**Tại sao hữu ích:**
Nếu mọi exception đều thành `500 Internal Server Error`, client không biết lỗi nào có thể sửa, lỗi nào nên retry và lỗi nào là bug server. Contract lỗi ổn định giúp frontend/mobile xử lý chính xác hơn và giảm việc parse message text tùy tiện.

**Ví dụ:**
```csharp
app.UseExceptionHandler(handler =>
{
    handler.Run(async context =>
    {
        var feature = context.Features.Get<IExceptionHandlerFeature>();

        var status = feature?.Error switch
        {
            ValidationException => StatusCodes.Status400BadRequest,
            NotFoundException => StatusCodes.Status404NotFound,
            ConcurrencyException => StatusCodes.Status409Conflict,
            _ => StatusCodes.Status500InternalServerError
        };

        await Results.Problem(statusCode: status)
            .ExecuteAsync(context);
    });
});
```

**Lưu ý:**
Không trả stack trace, connection string hoặc internal exception message cho client production. Đồng thời đừng map lỗi programming bug thành `400` chỉ để giảm error rate; unexpected failure vẫn cần telemetry và alerting như server error.

### Tip 3 — Khi query SQL chậm đột ngột, kiểm tra statistics và estimated-vs-actual rows trước khi thêm index

**Mẹo:**
Nếu một query từng nhanh nhưng đột nhiên chọn execution plan xấu, so sánh estimated rows với actual rows và kiểm tra statistics trước khi tạo thêm index.

**Tại sao hữu ích:**
Query optimizer chọn join type, access path và memory grant dựa trên cardinality estimate. Nếu statistics cũ hoặc data distribution thay đổi mạnh, optimizer có thể nghĩ chỉ có vài row trong khi thực tế có hàng triệu row, dẫn tới nested loop, spill hoặc plan không phù hợp.

**Ví dụ:**
```sql
SELECT o.Id, o.Total
FROM Orders o
JOIN Customers c ON c.Id = o.CustomerId
WHERE c.Region = @Region;
```

Trong actual execution plan, nếu estimated rows là `1,000` nhưng actual rows là `800,000`, hãy điều tra statistics, parameter sensitivity và data skew trước khi kết luận “thiếu index”.

**Lưu ý:**
Update statistics không phải thuốc chữa mọi slow query. Plan regression có thể đến từ parameter sniffing/sensitivity, schema change, index change hoặc workload khác. Luôn giữ evidence từ execution plan và runtime metrics.

### Tip 4 — Trong Vue, tránh `deep: true` trên object lớn nếu chỉ cần theo dõi vài field

**Mẹo:**
Khi dùng Vue `watch`, theo dõi trực tiếp những property ảnh hưởng behavior thay vì bật `deep: true` cho một state object lớn theo thói quen.

**Tại sao hữu ích:**
Deep watcher phải traverse dependency graph để theo dõi nested change. Với form hoặc page state lớn, điều này có thể tạo work không cần thiết và làm logic khó hiểu vì bất kỳ mutation nhỏ nào cũng kích hoạt cùng callback.

**Ví dụ:**
```ts
watch(
  () => [filters.categoryId, filters.sortBy, filters.page],
  () => loadProducts(),
  { immediate: true }
)
```

Cách này diễn đạt dependency thật của request rõ hơn so với watch toàn bộ `filters` object với `deep: true`.

**Lưu ý:**
Đừng tối ưu reactivity bằng cảm tính. Với object nhỏ, `deep` có thể hoàn toàn chấp nhận được. Nếu callback gọi API, còn cần debounce/cancellation để tránh request burst hoặc stale response.

### Tip 5 — Chống SSRF bằng cách kiểm soát destination, không chỉ validate URL syntax

**Mẹo:**
Nếu backend nhận URL từ user rồi fetch server-side, hãy giới hạn scheme, hostname/destination được phép và chặn network range nội bộ thay vì chỉ dùng `Uri.TryCreate`.

**Tại sao hữu ích:**
Một URL hoàn toàn hợp lệ về syntax vẫn có thể trỏ tới metadata service, localhost, private subnet hoặc internal admin endpoint. SSRF cho phép attacker lợi dụng quyền mạng của backend để đọc hoặc gọi resource mà client bình thường không truy cập được.

**Ví dụ:**
```text
Không đủ:
https://127.0.0.1:5001/admin
http://169.254.169.254/...

Tốt hơn:
- chỉ cho HTTPS
- allowlist hostname/provider cần thiết
- resolve DNS rồi kiểm tra IP đích
- chặn loopback/private/link-local range
- áp egress/network policy nếu có thể
```

**Lưu ý:**
Chỉ kiểm tra hostname string có thể vẫn dính DNS rebinding hoặc redirect sang destination khác. Validation nên áp dụng cả sau DNS resolution và khi follow redirect; network-level egress restriction cung cấp thêm lớp bảo vệ quan trọng.

## 🧠 Software Design

### Design 1 — Normalization vs Denormalization phải theo write integrity và read shape

**Khái niệm:**
Normalization giảm duplication và giúp constraint/transaction bảo vệ dữ liệu nhất quán. Denormalization cố ý lặp hoặc precompute dữ liệu để phục vụ read path nhanh và đơn giản hơn. Đây là lựa chọn về workload, không phải cuộc thi “schema chuẩn hơn”.

**Vấn đề nó giải quyết:**
Một transactional model được normalize tốt có thể cần nhiều join cho dashboard, search result hoặc reporting. Ngược lại, denormalize mọi thứ ngay từ đầu làm update logic phức tạp và tăng nguy cơ stale data.

**Ví dụ thực tế:**
```text
Write model:
Orders
OrderItems
Customers
Products

Read model cho dashboard:
OrderSummary
- OrderId
- CustomerName
- ItemCount
- Total
- LastUpdatedAt
```

`OrderSummary` có thể được cập nhật bằng application logic, event hoặc scheduled projection tùy freshness requirement.

**Trade-off:**
Normalization giúp integrity, update semantics và storage rõ ràng hơn nhưng read phức tạp hơn. Denormalization giảm join/read latency nhưng tạo synchronization cost, duplicated data và consistency window.

**Middle → Senior insight:**
Middle developer cần biết khi nào join/projection là đủ và không denormalize chỉ vì thấy query dài. Senior / Technical developer phải quyết định source of truth, freshness SLA, rebuild strategy và failure handling của denormalized model dựa trên read volume và consistency requirement.

### Design 2 — REST đồng bộ vs Messaging bất đồng bộ: chọn theo thời điểm business cần acknowledgement

**Khái niệm:**
Synchronous REST phù hợp khi caller cần biết kết quả trực tiếp trong cùng interaction. Messaging phù hợp khi producer chỉ cần xác nhận work đã được chấp nhận và phần xử lý có thể hoàn tất sau.

**Vấn đề nó giải quyết:**
Nếu một HTTP request giữ connection trong 30 giây để chờ nhiều downstream system, availability của endpoint bị ràng buộc vào toàn bộ dependency chain. Nhưng chuyển mọi thứ sang queue cũng làm client mất immediate result và phải xử lý eventual state.

**Ví dụ thực tế:**
```text
GET /products/42
-> cần dữ liệu ngay
-> synchronous HTTP hợp lý

POST /reports/monthly
-> validate request
-> enqueue GenerateReport
-> trả 202 Accepted + status URL
-> worker xử lý sau
```

Điểm quyết định không phải “messaging scale tốt hơn”, mà là business có chấp nhận pending state hay không.

**Trade-off:**
REST đơn giản cho request/response, dễ debug và có immediate feedback nhưng dễ tạo temporal coupling. Messaging giảm coupling về thời gian và hấp thụ burst tốt hơn, nhưng thêm broker, retry, duplicate delivery, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry và idempotency của từng kiểu giao tiếp. Senior / Technical developer phải chọn boundary theo user journey, latency SLO, dependency reliability, failure recovery và semantics của acknowledgement thay vì mặc định “async là hiện đại hơn”.

### Design 3 — Bounded Context nên theo business language và change boundary, không theo bảng database

**Khái niệm:**
Trong DDD, Bounded Context xác định nơi một domain model và ngôn ngữ có nghĩa nhất quán. Boundary thường phản ánh capability, ownership và quy tắc thay đổi, không đơn giản là “mỗi nhóm table thành một service”.

**Vấn đề nó giải quyết:**
Cùng từ như `Customer`, `Order` hoặc `Status` có thể có nghĩa khác nhau giữa Sales, Billing và Support. Nếu ép toàn hệ thống dùng một canonical model khổng lồ, thay đổi của một team dễ lan sang nhiều capability không liên quan.

**Ví dụ thực tế:**
```text
Sales context:
Customer = lead/account với pipeline state

Billing context:
Customer = legal payer với billing profile + tax data

Support context:
Customer = identity phục vụ ticket/history
```

Các context có thể map qua contract rõ ràng thay vì chia sẻ cùng entity object hoặc database model.

**Trade-off:**
Boundary rõ làm ownership và model dễ tiến hóa hơn, nhưng thêm mapping, integration và nguy cơ duplicated concept. Nếu domain nhỏ và team duy nhất, chia quá nhiều context chỉ tạo ceremony.

**Middle → Senior insight:**
Middle developer cần tránh dùng chung entity xuyên module chỉ vì field giống nhau. Senior / Technical developer phải tìm boundary theo vocabulary, invariant, release cadence, ownership và change coupling; chỉ tách deployment/service khi runtime isolation thực sự cần thiết.
