# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — Source Generator nên thay reflection khi metadata có thể xác định lúc compile

**Mẹo:**
Với hot path phải lặp lại việc khám phá metadata bằng reflection, cân nhắc Source Generator để sinh code tại compile time nếu shape dữ liệu đã biết trước.

**Tại sao hữu ích:**
Reflection cần runtime discovery và metadata lookup. Source Generator chuyển một phần công việc sang build time, tạo code strongly typed mà compiler có thể kiểm tra và tối ưu.

**Ví dụ:**
Một serializer nội bộ phải map hàng triệu event theo attribute. Thay vì mỗi lần chạy đều `GetProperties()`, generator có thể sinh mapper cho từng event type ngay khi build.

**Lưu ý:**
Đừng tạo generator cho logic hiếm chạy hoặc không có bằng chứng performance/maintainability. Generator làm build pipeline và debugging phức tạp hơn; generated code phải dễ inspect và có test.

### Tip 2 — `ProblemDetails` nên chuẩn hóa machine-readable error contract

**Mẹo:**
Trong ASP.NET Core API, dùng `ProblemDetails` làm envelope lỗi nhất quán và bổ sung stable application error code thay vì để client parse message text.

**Tại sao hữu ích:**
HTTP status chỉ mô tả lớp lỗi rộng. Code ổn định như `ORDER_ALREADY_SHIPPED` giúp frontend/mobile xử lý business case mà không phụ thuộc câu chữ hoặc localization.

**Ví dụ:**
```json
{
  "status": 409,
  "title": "Order state conflict",
  "code": "ORDER_ALREADY_SHIPPED",
  "traceId": "00-..."
}
```
Client dùng `status` và `code`; `traceId` hỗ trợ production troubleshooting.

**Lưu ý:**
Không trả stack trace, SQL text hoặc exception detail nhạy cảm ra public API. Error code đã public là một phần contract và cần backward compatibility.

### Tip 3 — Cosmos DB partition key phải phân phối cả storage lẫn traffic

**Mẹo:**
Chọn partition key dựa trên access pattern và traffic distribution, không chỉ vì field đó có cardinality cao.

**Tại sao hữu ích:**
Một logical partition nhận phần lớn request có thể trở thành hot partition dù database tổng thể còn capacity. Partition key tốt giúp request và dữ liệu phân bố đều, đồng thời giữ operation cần locality trong boundary hợp lý.

**Ví dụ:**
Hệ thống multi-tenant dùng `/tenantId` có thể tốt khi tenants cân bằng. Nếu một tenant chiếm 70% traffic, cần đánh giá hierarchical partitioning hoặc data model khác thay vì chỉ tăng RU toàn account.

**Lưu ý:**
Đừng chọn random GUID chỉ để phân phối đều nếu query nghiệp vụ luôn cần cross-partition fan-out. Partition key khó thay đổi khi hệ thống lớn; đo RU và partition-level traffic trước khi chốt schema.

### Tip 4 — CI/CD artifact phải immutable từ build đến production

**Mẹo:**
Build một artifact/container image một lần, sau đó promote đúng artifact đó qua staging đến production thay vì rebuild source cho từng environment.

**Tại sao hữu ích:**
Rebuild có thể lấy dependency, toolchain hoặc generated output khác dù cùng commit. Promote artifact giữ binary identity, giúp kết quả test ở staging có ý nghĩa và rollback chính xác hơn.

**Ví dụ:**
Pipeline build image `orders-api@sha256:...`, chạy integration tests rồi deploy cùng digest sang production. Environment-specific configuration được inject lúc deploy/runtime, không bake bằng build mới.

**Lưu ý:**
Immutability không có nghĩa nhét secrets hoặc environment config vào artifact. Cần version/digest traceability và retention policy; tag `latest` không đủ để chứng minh production đang chạy binary nào.

### Tip 5 — Network waterfall giúp tách backend latency khỏi frontend loading cost

**Mẹo:**
Khi trang chậm, dùng browser DevTools Network để tách DNS/connect/TLS, TTFB, download và dependency chain trước khi kết luận JavaScript hoặc backend là nguyên nhân.

**Tại sao hữu ích:**
Một metric tổng như page load time che mất bottleneck. TTFB cao có thể đến từ backend/CDN; nhiều request nối chuỗi có thể do frontend loading strategy; asset lớn lại là vấn đề transfer/compression.

**Ví dụ:**
Trang CMS mất 4 giây. Waterfall cho thấy HTML TTFB chỉ 300 ms nhưng hero image bắt đầu tải muộn sau CSS và script chain. Tối ưu backend database sẽ gần như không cải thiện LCP trong trường hợp này.

**Lưu ý:**
Một lần capture trên máy developer không đại diện production. So sánh với field telemetry, cache state, device/network profile và geography trước khi ưu tiên optimization.

## 🧠 Software Design

### Design 1 — Inbox Pattern bảo vệ consumer trước duplicate delivery

**Khái niệm:**
Inbox Pattern lưu identity của message đã xử lý cùng với state change của consumer để duplicate delivery được nhận diện mà không thực hiện side effect lần nữa.

**Vấn đề nó giải quyết:**
Broker thường có at-least-once delivery. Consumer có thể commit database thành công rồi mất kết nối trước khi acknowledge; message sau đó được redeliver và có nguy cơ cập nhật state lần hai.

**Ví dụ thực tế:**
Handler nhận `PaymentCaptured` với `MessageId`. Trong cùng transaction, nó insert `InboxMessage(MessageId)` với unique constraint và cập nhật Order thành `Paid`. Message lặp lại được nhận diện và bỏ qua business transition đã hoàn tất.

**Trade-off:**
Inbox thêm storage, unique constraint, cleanup/retention và transaction coupling với consumer database. Nó cũng không tự làm external side effect trở thành exactly-once; các boundary khác vẫn cần idempotency phù hợp.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là bình thường và handler phải idempotent. Senior / Technical developer phải xác định idempotency boundary, atomicity giữa inbox và state change, retention window và message identity.

### Design 2 — Strangler Fig giảm rủi ro khi hiện đại hóa legacy system

**Khái niệm:**
Strangler Fig migration chuyển từng capability khỏi legacy application theo các seam rõ ràng, trong khi routing/facade cho phép hệ thống cũ và mới cùng tồn tại trong giai đoạn chuyển đổi.

**Vấn đề nó giải quyết:**
Big-bang rewrite phải tái tạo toàn bộ behavior trước ngày cutover, kéo dài feedback loop và tạo một thời điểm migration có blast radius lớn. Incremental replacement cho phép đưa từng slice vào production sớm hơn.

**Ví dụ thực tế:**
Một .NET Framework CMS cũ giữ checkout và admin, nhưng product-search endpoint được route sang ASP.NET Core service mới. Sau khi observability và correctness ổn định, team chuyển capability kế tiếp.

**Trade-off:**
Giai đoạn coexistence tạo duplicate models, routing rules, data synchronization và operational overhead. Nếu không có roadmap xóa legacy path, kiến trúc tạm thời có thể trở thành trạng thái vĩnh viễn phức tạp hơn ban đầu.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility và test integration giữa old/new path. Senior / Technical developer phải tìm seam theo business capability, lập migration order, data ownership, rollback strategy và exit criteria.

### Design 3 — Build vs Buy là quyết định về ownership dài hạn

**Khái niệm:**
Build vs Buy so sánh việc tự sở hữu capability với dùng managed service/SaaS/library dựa trên differentiation, lifecycle cost, control, compliance, integration và exit cost.

**Vấn đề nó giải quyết:**
Team thường đánh giá sai khi so vài tuần coding với subscription fee mà bỏ qua patching, on-call, scaling, upgrade và specialist knowledge trong nhiều năm.

**Ví dụ thực tế:**
Một product cần identity federation, MFA và enterprise SSO. Tự xây identity stack cho nhiều control hơn, nhưng một identity platform có thể giảm protocol và operational ownership nếu requirements phù hợp.

**Trade-off:**
Buy giảm time-to-market và operational burden nhưng có vendor dependency, pricing change, feature constraints và migration cost. Build cho control sâu hơn nhưng biến capability thành trách nhiệm engineering lâu dài.

**Middle → Senior insight:**
Middle developer cần đánh giá API, integration và technical constraints. Senior / Technical developer phải tính total cost of ownership, strategic differentiation, compliance, SLA dependency, data portability và exit strategy; quyết định tốt không mặc định ưu tiên tự xây hay mua.
