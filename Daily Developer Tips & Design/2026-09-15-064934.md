# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `PeriodicTimer` cho vòng lặp background có cancellation rõ ràng

**Mẹo:**
Trong `BackgroundService`, khi cần chạy một tác vụ định kỳ đơn giản, cân nhắc `PeriodicTimer` thay vì tự ghép `while` + `Task.Delay` rải rác. Nó làm intent của loop rõ hơn và kết hợp tự nhiên với `CancellationToken` khi application shutdown.

**Tại sao hữu ích:**
Background loop thường lỗi ở shutdown semantics: process nhận stop signal nhưng code vẫn delay, giữ resource hoặc bắt đầu thêm một vòng xử lý mới. `PeriodicTimer.WaitForNextTickAsync(stoppingToken)` giúp cancellation đi xuyên trực tiếp vào nhịp chạy thay vì phải tự quản lý nhiều delay/token riêng.

**Ví dụ:**
```csharp
public sealed class CleanupWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await CleanupExpiredDataAsync(stoppingToken);
        }
    }
}
```

**Lưu ý:**
`PeriodicTimer` không tự ngăn nhiều application instance chạy cùng một job. Nếu deploy nhiều replica và job chỉ được phép chạy một lần toàn hệ thống, vẫn cần leader election, distributed lock, scheduler bên ngoài hoặc idempotent processing phù hợp.

### Tip 2 — Dùng `ExecuteUpdateAsync` cho set-based update thay vì load hàng nghìn entity

**Mẹo:**
Với EF Core, nếu cần update nhiều row theo một predicate mà không cần chạy business logic trên từng entity, cân nhắc `ExecuteUpdateAsync` thay vì `ToListAsync()` rồi sửa từng object và `SaveChangesAsync()`.

**Tại sao hữu ích:**
Load entity làm phát sinh round trip đọc, allocation, change tracking và thường nhiều dữ liệu hơn cần thiết. Set-based update chuyển logic thành một lệnh SQL trực tiếp, giảm memory pressure và network overhead đáng kể.

**Ví dụ:**
```csharp
await db.Sessions
    .Where(x => x.ExpiresAt < now && x.Status == SessionStatus.Active)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, SessionStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now), ct);
```

**Lưu ý:**
`ExecuteUpdateAsync` bypass change tracker và không gọi logic nằm trong entity setter, interceptor hoặc workflow mà bạn đang trông chờ. Nó cũng không tự tạo domain event cho từng entity. Chỉ dùng khi semantics thực sự phù hợp với bulk database operation.

### Tip 3 — Ưu tiên Managed Identity cho Azure resource thay vì lưu secret trong config

**Mẹo:**
Khi application chạy trên Azure và cần truy cập Key Vault, Blob Storage hoặc Service Bus, ưu tiên Managed Identity cùng Azure RBAC thay vì lưu connection string hoặc client secret trong `appsettings`, environment variable hoặc pipeline variable nếu dịch vụ hỗ trợ identity-based authentication.

**Tại sao hữu ích:**
Secret tĩnh phải được tạo, phân phối, rotate và bảo vệ. Managed Identity chuyển phần xác thực sang Azure identity platform, giảm secret sprawl và loại bỏ một class sự cố phổ biến: secret hết hạn hoặc bị lộ nhưng không ai biết dependency nào đang dùng nó.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);
```

Trong production, App Service/Function/VM/Pod identity được cấp đúng role trên resource cần truy cập.

**Lưu ý:**
Managed Identity không có nghĩa “khỏi cần security design”. Phải áp dụng least privilege, tách identity theo trust boundary hợp lý và hiểu `DefaultAzureCredential` có credential chain khác nhau giữa local và production. Đừng vô tình để local credential che giấu cấu hình production sai.

### Tip 4 — Giảm Cumulative Layout Shift bằng cách reserve kích thước media trước khi tải

**Mẹo:**
Với image, banner, ad slot hoặc component bất đồng bộ có kích thước dự đoán được, reserve layout space bằng `width`/`height`, `aspect-ratio` hoặc skeleton có kích thước ổn định thay vì để browser chỉ biết chiều cao sau khi content tải xong.

**Tại sao hữu ích:**
Nếu browser chưa biết kích thước asset, nội dung phía dưới bị đẩy xuống khi image hoặc widget xuất hiện. Điều này làm tăng Cumulative Layout Shift (CLS), giảm UX và có thể ảnh hưởng Core Web Vitals dù backend latency hoàn toàn tốt.

**Ví dụ:**
```html
<img
  src="/images/product.webp"
  width="800"
  height="600"
  loading="lazy"
  alt="Product image" />
```

Browser có thể reserve đúng tỷ lệ 4:3 ngay từ bước layout đầu tiên.

**Lưu ý:**
Đừng hard-code kích thước làm méo ảnh hoặc phá responsive layout. Với asset responsive, giữ đúng intrinsic ratio và dùng CSS phù hợp. CLS cũng có thể đến từ font, cookie banner hoặc content inject động, nên cần đo bằng Lighthouse/Chrome DevTools thay vì đoán nguyên nhân.

### Tip 5 — Dùng Testcontainers khi integration test phụ thuộc behavior thật của database hoặc broker

**Mẹo:**
Nếu test cần kiểm tra SQL semantics, migration, transaction, index/constraint hoặc behavior của Redis/message broker, cân nhắc chạy dependency thật trong container thay vì mock repository hoặc giả lập provider quá nhiều.

**Tại sao hữu ích:**
Mock có thể xác nhận code “gọi đúng method” nhưng không phát hiện khác biệt thật như transaction isolation, unique constraint, query translation hoặc database-specific SQL. Containerized integration test giúp kiểm tra behavior gần production hơn mà vẫn tự động hóa được trong CI.

**Ví dụ:**
```text
Integration test flow:
1. start PostgreSQL container
2. apply migrations
3. seed minimal test data
4. call API/use case
5. assert database state
6. dispose container
```

**Lưu ý:**
Không biến toàn bộ test suite thành container test. Chúng chậm và tốn resource hơn unit test. Dùng chúng cho boundary có giá trị cao; domain logic thuần vẫn nên được test nhanh ở process memory.

## 🧠 Software Design

### Design 1 — Queue và Topic giải quyết hai kiểu phân phối message khác nhau

**Khái niệm:**
Queue phù hợp khi một message đại diện cho work cần được một consumer trong nhóm xử lý. Topic + subscription phù hợp khi một event cần được nhiều consumer độc lập nhận theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Nếu `GenerateInvoice` là một command, bạn thường muốn chỉ một worker claim work đó. Nhưng `OrderPaid` có thể cần Billing, Loyalty và Analytics cùng phản ứng. Dùng chung một queue cho cả hai semantics dễ tạo coupling và routing logic khó hiểu.

**Ví dụ thực tế:**
```text
Queue:
GenerateInvoice
-> Worker A hoặc Worker B xử lý một lần theo competing-consumer semantics

Topic:
OrderPaid
-> Billing subscription
-> Loyalty subscription
-> Analytics subscription
```

**Trade-off:**
Queue đơn giản cho work distribution nhưng không fan-out tự nhiên. Topic hỗ trợ nhiều subscriber độc lập nhưng tăng số subscription, retry path, dead-letter queue và operational surface. Không nên dùng topic chỉ vì “event-driven” nếu thật ra chỉ có một consumer và command semantics rõ ràng.

**Middle → Senior insight:**
Middle developer cần phân biệt command và event ở mức delivery intent. Senior / Technical developer phải đánh giá ownership, retry, ordering, subscriber isolation, future extensibility và chi phí vận hành trước khi chọn queue hay pub/sub.

### Design 2 — Saga dùng compensation khi business transaction vượt quá một database boundary

**Khái niệm:**
Saga chia một business workflow dài thành nhiều local transaction và dùng compensating action khi bước sau thất bại. Nó chấp nhận rằng distributed workflow thường không có một ACID transaction bao trùm tất cả service.

**Vấn đề nó giải quyết:**
Checkout có thể phải reserve inventory, charge payment và create shipment ở ba hệ thống khác nhau. Nếu payment thành công nhưng shipment creation thất bại, không thể chỉ `ROLLBACK` tất cả như một database transaction duy nhất.

**Ví dụ thực tế:**
```text
1. ReserveInventory -> success
2. ChargePayment    -> success
3. CreateShipment   -> failed

Compensation:
4. RefundPayment
5. ReleaseInventory
```

Mỗi step cần idempotency và trạng thái workflow có thể quan sát/recover.

**Trade-off:**
Saga tăng khả năng phục hồi cho distributed workflow nhưng đưa eventual consistency, compensation logic, retry và state management vào hệ thống. Compensation cũng không phải luôn là inverse hoàn hảo; refund có thể mất phí hoặc đã phát sinh external side effect.

**Middle → Senior insight:**
Middle developer cần implement step idempotent và hiểu failure có thể xảy ra giữa mọi boundary. Senior / Solution-oriented engineer phải chọn orchestration hay choreography, xác định compensation semantics, timeout, manual recovery và xem liệu workflow có thực sự cần tách service hay có thể giữ transaction trong một boundary đơn giản hơn.

### Design 3 — Bounded Context tách model theo meaning, không chỉ theo bảng hoặc team folder

**Khái niệm:**
Trong Domain-Driven Design, Bounded Context là ranh giới nơi một model và ngôn ngữ có meaning nhất quán. Hai context có thể dùng cùng một từ nhưng mang invariant và lifecycle khác nhau, vì vậy không nhất thiết phải chia sẻ cùng entity class.

**Vấn đề nó giải quyết:**
`Customer` trong Sales có thể chứa lead source, account owner và opportunity state; trong Billing lại cần invoice profile, tax identity và payment terms. Cố ép cả hai vào một `Customer` entity chung thường tạo model khổng lồ, coupling mạnh và thay đổi một domain làm ảnh hưởng domain kia.

**Ví dụ thực tế:**
```text
Sales Context
CustomerAccount
- Owner
- PipelineStatus

Billing Context
BillingCustomer
- TaxId
- PaymentTerms

Integration qua CustomerId + contract/event rõ ràng
```

**Trade-off:**
Bounded Context tăng autonomy và giữ model tập trung vào domain, nhưng tạo mapping, duplicated representation và integration boundary. Nếu hệ thống nhỏ và business rules đơn giản, chia quá nhiều context sẽ làm code và tổ chức phức tạp hơn lợi ích nhận được.

**Middle → Senior insight:**
Middle developer cần hiểu không nên reuse entity xuyên boundary chỉ vì tên giống nhau. Senior / Technical developer phải xác định context dựa trên business capability, invariant, ownership và rate of change; đồng thời tránh biến mỗi module nhỏ thành một bounded context chỉ để “đúng DDD”.
