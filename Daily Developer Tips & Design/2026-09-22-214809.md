# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng giữ SQL transaction trong lúc gọi HTTP service bên ngoài

**Mẹo:**
Giữ database transaction càng ngắn càng tốt. Nếu workflow phải gọi payment, inventory hoặc một REST API khác, tránh mở transaction rồi `await` network I/O trước khi commit.

**Tại sao hữu ích:**
Transaction sống lâu giữ lock/version state lâu hơn, tăng contention và xác suất deadlock/timeout. Network latency lại nằm ngoài quyền kiểm soát của database: một downstream service chậm vài giây có thể biến một transaction vốn chỉ cần vài millisecond thành bottleneck toàn hệ thống.

**Ví dụ:**
Checkout cần lưu `Order` rồi gửi yêu cầu sang payment provider. Thay vì `BeginTransaction` → insert order → HTTP payment → update order → commit, có thể commit trạng thái `PendingPayment` trước, sau đó thực hiện integration bằng durable workflow/outbox và cập nhật kết quả ở transaction riêng.

**Lưu ý:**
Tách transaction làm mất atomicity kiểu ACID xuyên suốt workflow. Phải thiết kế state transition, idempotency và compensation rõ ràng; không đơn giản bỏ transaction rồi hy vọng các bước luôn thành công.

### Tip 2 — `HttpClient.Timeout` không thay thế end-to-end cancellation budget

**Mẹo:**
Propagate `CancellationToken` từ request xuống outbound calls và đặt timeout/budget theo operation, thay vì chỉ dựa vào một `HttpClient.Timeout` toàn cục.

**Tại sao hữu ích:**
Một request đã bị client hủy hoặc đã hết latency budget thì công việc downstream tiếp tục chạy chỉ lãng phí thread, connection và database capacity. Một timeout chung cũng không diễn tả được việc operation còn bao nhiêu thời gian sau các bước trước đó.

**Ví dụ:**
API có SLO 2 giây: validation + DB read đã tốn 700 ms, nên call sang pricing service không nên mặc nhiên được phép chạy thêm 2 giây. Application tạo timeout phù hợp với remaining budget và truyền token vào `SendAsync`, EF Core và các async operation liên quan.

**Lưu ý:**
Phân biệt timeout với caller cancellation trong logging/metrics. Đồng thời không truyền request token mù quáng vào bước bắt buộc phải hoàn tất sau khi đã commit business state; durable side effect thường cần boundary riêng.

### Tip 3 — Query MongoDB phải được thiết kế cùng compound index theo ESR

**Mẹo:**
Khi tạo compound index cho MongoDB, xem xét thứ tự Equality → Sort → Range (ESR) dựa trên query shape thực tế thay vì chỉ gom các field “hay dùng” vào một index.

**Tại sao hữu ích:**
Thứ tự field quyết định index có hỗ trợ filter và sort hiệu quả hay không. Một index chứa đủ field nhưng sai prefix vẫn có thể khiến database scan nhiều keys hoặc phải thực hiện blocking sort.

**Ví dụ:**
Query lấy order của một tenant với `Status = "Paid"`, sort `CreatedAt DESC` và lọc `Total >= x`. Index `{ TenantId: 1, Status: 1, CreatedAt: -1, Total: 1 }` đặt equality trước sort rồi range, phù hợp hơn một thứ tự tùy ý như `{ Total: 1, CreatedAt: -1, TenantId: 1 }`.

**Lưu ý:**
ESR là guideline, không phải luật tuyệt đối. Cardinality, selectivity, `$in`, range rất hẹp và workload ghi có thể thay đổi lựa chọn tối ưu; xác nhận bằng `explain()` và metrics production-like.

### Tip 4 — Tránh `Task.Run` để “làm async” I/O trong ASP.NET Core

**Mẹo:**
Với database, HTTP, file/network I/O đã có API async, `await` trực tiếp API async thay vì bọc chúng trong `Task.Run`.

**Tại sao hữu ích:**
`Task.Run` đẩy delegate sang ThreadPool nhưng không làm I/O nhanh hơn. Trong web server, nó còn thêm scheduling overhead và có thể làm ThreadPool pressure tăng khi traffic cao, đặc biệt nếu bên trong vẫn có blocking call.

**Ví dụ:**
Không dùng `await Task.Run(() => repository.LoadOrders())` để che một synchronous database call. Dùng driver/provider hỗ trợ `LoadOrdersAsync(cancellationToken)` để thread có thể quay lại pool trong lúc chờ I/O.

**Lưu ý:**
`Task.Run` vẫn có chỗ dùng cho CPU-bound work trong một số application boundary, nhưng CPU-heavy workload lớn thường nên được giới hạn concurrency hoặc tách sang background processing thay vì tạo unbounded tasks trong request path.

### Tip 5 — Structured logging cần event shape ổn định, không chỉ string dễ đọc

**Mẹo:**
Log business/operational events bằng message template và property có semantic ổn định như `OrderId`, `TenantId`, `ElapsedMs`, `Outcome`; tránh interpolation biến toàn bộ dữ liệu thành một chuỗi khó query.

**Tại sao hữu ích:**
Structured fields cho phép filter, aggregate và correlate trong Application Insights/Seq/ELK mà không phải parse text. Khi incident xảy ra, câu hỏi “tenant nào có latency > 2s sau deployment?” trở thành query trên field thay vì grep hàng triệu message.

**Ví dụ:**
Dùng `logger.LogInformation("Order {OrderId} completed in {ElapsedMs} ms with {Outcome}", orderId, elapsedMs, outcome)` thay vì `$"Order {orderId} completed in {elapsedMs} ms with {outcome}"` nếu logging provider hỗ trợ structured properties.

**Lưu ý:**
Không log secret, access token, password hoặc PII nhạy cảm chỉ vì structured logging giúp tìm kiếm dễ hơn. High-cardinality fields cũng có cost; log level và telemetry volume phải được thiết kế theo nhu cầu vận hành.

## 🧠 Software Design

### Design 1 — Outbox Pattern đóng khoảng trống giữa database commit và message publish

**Khái niệm:**
Transactional Outbox lưu business change và một outbox message trong cùng local database transaction. Một publisher riêng đọc outbox rồi publish message sang broker, sau đó đánh dấu/ghi nhận trạng thái gửi.

**Vấn đề nó giải quyết:**
Nếu service commit database rồi crash trước khi publish event, downstream không bao giờ biết thay đổi đã xảy ra. Nếu publish trước rồi database rollback, downstream lại nhận event cho state không tồn tại. Outbox loại bỏ dual-write gap này mà không cần distributed transaction giữa database và broker.

**Ví dụ thực tế:**
Order service tạo `Order` và `OrderCreated` outbox row trong cùng transaction. Background publisher gửi event lên Azure Service Bus. Nếu process crash sau commit, row vẫn còn để publisher xử lý lại khi service phục hồi.

**Trade-off:**
Outbox chuyển bài toán từ “có mất event không” sang delivery/reprocessing semantics. Publisher có thể gửi trùng khi crash sau publish nhưng trước khi đánh dấu sent, nên consumer vẫn cần idempotency. Ngoài ra phải xử lý cleanup, ordering, polling/CDC và observability của backlog.

**Middle → Senior insight:**
Middle developer cần hiểu atomic local transaction và tại sao publish trực tiếp sau `SaveChangesAsync()` vẫn có failure window. Senior / Technical developer phải quyết định polling hay CDC, partition/order semantics, retry/dead-letter strategy, idempotent consumer và SLO cho thời gian từ commit đến publish.

### Design 2 — Bulkhead Isolation giới hạn blast radius của dependency chậm

**Khái niệm:**
Bulkhead chia resource/concurrency thành các ngăn độc lập để một dependency hoặc workload bị nghẽn không tiêu thụ toàn bộ capacity của application.

**Vấn đề nó giải quyết:**
Nếu mọi outbound call dùng chung unbounded concurrency, một service chậm có thể làm hàng nghìn requests cùng chờ, chiếm connection, memory và ThreadPool capacity. Khi đó endpoint không liên quan cũng suy giảm và lỗi cục bộ trở thành cascading failure.

**Ví dụ thực tế:**
Một API gọi Recommendation service và Payment service. Recommendation được giới hạn concurrency/queue riêng; khi nó chậm, requests vượt ngưỡng fail fast hoặc degrade sang response không recommendation, trong khi capacity dành cho payment không bị nuốt hết.

**Trade-off:**
Giới hạn quá thấp làm giảm throughput dù downstream còn khỏe; queue quá lớn chỉ biến overload thành latency. Bulkhead cũng thêm configuration và cần metric để tuning theo dependency capacity thực tế.

**Middle → Senior insight:**
Middle developer cần biết timeout/retry không đủ nếu concurrency không có giới hạn. Senior / Technical developer phải thiết kế admission control, queue bound, per-dependency budgets, fallback và telemetry để hệ thống degrade có chủ đích thay vì cùng sập.

### Design 3 — Modular Monolith dùng boundary rõ trước khi trả distributed-systems tax

**Khái niệm:**
Modular Monolith deploy như một application/process nhưng chia domain thành các module có ownership, API và data-access boundary rõ ràng. Mục tiêu là modularity ở code và domain trước, không phải tạo network boundary ngay lập tức.

**Vấn đề nó giải quyết:**
Một codebase monolith thiếu boundary dễ thành tightly coupled “big ball of mud”, nhưng tách microservices quá sớm lại đưa vào network failures, eventual consistency, distributed tracing, deployment orchestration và operational overhead khi team chưa cần chúng.

**Ví dụ thực tế:**
E-commerce application có `Catalog`, `Ordering`, `Payments` modules. `Ordering` không truy cập trực tiếp repository/table nội bộ của `Catalog`; giao tiếp qua contract/application boundary. Toàn hệ thống vẫn có thể deploy một artifact và chạy một database instance với ownership convention rõ.

**Trade-off:**
Process boundary không cưỡng chế isolation mạnh như service boundary; developer vẫn có thể phá module rule nếu architecture tests/review không bảo vệ. Một database vật lý chung cũng cần discipline để tránh cross-module joins và shared schema coupling.

**Middle → Senior insight:**
Middle developer cần tôn trọng dependency direction và public contract của module. Senior / Technical developer phải xác định bounded context, ownership dữ liệu, enforcement bằng architecture tests và chỉ extract service khi có driver cụ thể như independent scaling, deployment cadence, isolation hoặc team autonomy.
