# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync()` khi không cần load entity

**Mẹo:**
Với EF Core, nếu cần update nhiều rows theo cùng một điều kiện, ưu tiên `ExecuteUpdateAsync()` thay vì query toàn bộ entities về memory rồi sửa từng object.

**Tại sao hữu ích:**
Giảm round-trip, memory allocation và chi phí change tracking. Database thực hiện update trực tiếp bằng một câu SQL.

**Ví dụ:**
```csharp
await dbContext.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiredAt < DateTime.UtcNow)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired));
```

Thay vì:

```csharp
var orders = await dbContext.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiredAt < DateTime.UtcNow)
    .ToListAsync();

foreach (var order in orders)
{
    order.Status = OrderStatus.Expired;
}

await dbContext.SaveChangesAsync();
```

**Lưu ý:**
`ExecuteUpdateAsync()` bỏ qua change tracker. Nếu cùng `DbContext` đang giữ entity tương ứng trong memory, state tracked có thể không phản ánh giá trị mới trong database.

### Tip 2 — Dùng `curl -v` để tách lỗi HTTP khỏi lỗi application

**Mẹo:**
Khi debug API, dùng `curl -v` hoặc `curl --trace` để xem DNS resolution, TLS handshake, request headers, redirect và response headers trước khi kết luận lỗi nằm ở backend code.

**Tại sao hữu ích:**
Nhiều lỗi tưởng là API bug thực chất đến từ proxy, certificate, redirect, authentication header, HTTP version hoặc network path.

**Ví dụ:**
```bash
curl -v https://api.example.com/orders/123 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json"
```

Khi cần chi tiết hơn:

```bash
curl --trace-ascii trace.txt https://api.example.com/health
```

**Lưu ý:**
Trace có thể chứa token, cookie hoặc dữ liệu nhạy cảm. Không upload nguyên file trace vào ticket hoặc public chat nếu chưa redact secrets.

### Tip 3 — Dùng `docker inspect` trước khi restart container

**Mẹo:**
Khi container lỗi, kiểm tra state, exit code, health check và restart count bằng `docker inspect` trước khi restart để tránh mất dấu hiệu nguyên nhân.

**Tại sao hữu ích:**
Restart có thể làm hệ thống chạy lại tạm thời nhưng che mất thông tin như `OOMKilled`, exit code hoặc health-check failure.

**Ví dụ:**
```bash
docker inspect my-api --format '{{json .State}}'
```

Hoặc chỉ xem các field quan trọng:

```bash
docker inspect my-api --format \
'Exit={{.State.ExitCode}} OOM={{.State.OOMKilled}} Error={{.State.Error}}'
```

**Lưu ý:**
`docker inspect` chỉ cho biết container state. Với root cause đầy đủ, cần kết hợp `docker logs`, host metrics, memory pressure và application logs.

### Tip 4 — Dùng `FrozenDictionary` cho lookup read-only trên hot path

**Mẹo:**
Nếu một dictionary được xây dựng một lần rồi đọc rất nhiều lần, cân nhắc `FrozenDictionary<TKey,TValue>` trong `System.Collections.Frozen`.

**Tại sao hữu ích:**
Frozen collections tối ưu cấu trúc nội bộ cho read-heavy workload và loại bỏ khả năng sửa nhầm sau khi khởi tạo.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

private static readonly FrozenDictionary<string, int> StatusCodes =
    new Dictionary<string, int>
    {
        ["pending"] = 1,
        ["active"] = 2,
        ["disabled"] = 3
    }.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
```

**Lưu ý:**
Chi phí tạo frozen collection cao hơn dictionary thông thường. Không phù hợp nếu collection thay đổi thường xuyên hoặc chỉ được đọc vài lần.

### Tip 5 — Chạy test song song nhưng cô lập shared state

**Mẹo:**
Cho phép test framework chạy test song song để rút ngắn feedback loop, nhưng tránh để test phụ thuộc vào cùng database row, static state, file path hoặc singleton mutable object.

**Tại sao hữu ích:**
Parallel testing có thể giảm đáng kể thời gian CI, đồng thời buộc test suite phải ít coupling hơn và đáng tin cậy hơn.

**Ví dụ:**
Thay vì tất cả integration test cùng dùng:

```text
Database: TestDb
UserId: 1
File: /tmp/result.json
```

hãy tạo resource riêng theo test run:

```csharp
var testId = Guid.NewGuid().ToString("N");
var databaseName = $"TestDb_{testId}";
var filePath = Path.Combine(Path.GetTempPath(), $"result_{testId}.json");
```

**Lưu ý:**
Không bật parallelization chỉ để CI nhanh hơn nếu hệ thống test hiện còn nhiều shared mutable state. Flaky test khó chịu hơn một test suite chậm nhưng deterministic.

## 🧠 Software Design

### Design 1 — Bulkhead isolation để ngăn một dependency làm nghẽn toàn hệ thống

**Khái niệm:**
Bulkhead Pattern giới hạn tài nguyên dành cho từng dependency hoặc workload, ví dụ connection pool, concurrency slot hoặc worker queue riêng.

**Vấn đề nó giải quyết:**
Nếu một downstream service chậm, request chờ service đó có thể chiếm hết thread, connection hoặc worker và kéo theo các chức năng không liên quan cùng bị ảnh hưởng.

**Ví dụ thực tế:**
Một API gọi cả Payment Service và Recommendation Service. Recommendation đôi lúc chậm 10 giây nhưng không phải chức năng critical. Thay vì để nó chiếm toàn bộ outbound concurrency, hệ thống giới hạn Recommendation tối đa 20 concurrent calls. Khi vượt giới hạn, request fail fast hoặc bỏ qua recommendation, trong khi Payment vẫn còn capacity riêng.

**Trade-off:**
Lợi ích là giảm failure cascade và bảo vệ chức năng quan trọng. Chi phí là phải chọn capacity phù hợp, thêm queue/rejection behavior và có nguy cơ under-utilization nếu chia tài nguyên quá cứng.

**Middle → Senior insight:**
Middle developer nên hiểu timeout và retry không đủ để chống resource exhaustion. Senior developer cần xác định workload nào phải được isolation, capacity nào hợp lý và degradation behavior nào chấp nhận được khi một partition bị đầy.

### Design 2 — CQRS chỉ nên dùng nơi read model và write model thực sự khác nhau

**Khái niệm:**
CQRS tách model xử lý command khỏi model phục vụ query. Nó hữu ích khi hai phía có yêu cầu dữ liệu, scaling hoặc consistency khác biệt rõ rệt.

**Vấn đề nó giải quyết:**
Một domain phức tạp có thể cần write model giàu business invariant nhưng read side lại cần projection phẳng, denormalized và tối ưu riêng cho reporting hoặc UI.

**Ví dụ thực tế:**
Hệ thống order có write model đảm bảo inventory, payment và order state transitions. Dashboard quản trị lại cần query theo ngày, region, sales channel và trạng thái. Thay vì ép một aggregate model phục vụ cả hai, hệ thống duy trì projection riêng cho dashboard.

**Trade-off:**
Lợi ích là mỗi side được tối ưu đúng mục tiêu và có thể scale độc lập. Chi phí là thêm projection, eventual consistency, synchronization logic và operational complexity. Với CRUD đơn giản, CQRS thường làm hệ thống khó hiểu hơn mà không tạo giá trị.

**Middle → Senior insight:**
Middle developer cần hiểu CQRS không đơn giản là tách `Command` và `Query` class. Senior developer phải chứng minh được sự khác biệt thực sự về workload hoặc domain trước khi chấp nhận chi phí consistency và vận hành.

### Design 3 — High cohesion quan trọng hơn việc chia thật nhiều project/layer

**Khái niệm:**
High cohesion nghĩa là những code cùng phục vụ một capability hoặc business concept nên nằm gần nhau và thay đổi cùng nhau. Low coupling nghĩa là module chỉ phụ thuộc tối thiểu vào internals của module khác.

**Vấn đề nó giải quyết:**
Kiến trúc chia theo technical layer quá mạnh có thể khiến một thay đổi nhỏ phải sửa `Controller`, `Service`, `Repository`, `Dto`, `Mapper` và nhiều project khác nhau dù chúng đều thuộc cùng một feature.

**Ví dụ thực tế:**
Thay vì cấu trúc:

```text
Controllers/
Services/
Repositories/
Dtos/
Validators/
```

có thể tổ chức theo feature:

```text
Orders/
  CreateOrder/
  CancelOrder/
  GetOrder/

Employees/
  Offboarding/
  Reactivation/
```

Mỗi feature chứa command, validation, handler và contract cần thiết của nó.

**Trade-off:**
Feature-oriented design tăng locality và giảm coupling theo layer, nhưng nếu boundary kém có thể dẫn tới duplication hoặc inconsistent conventions giữa modules. Layering vẫn hữu ích cho cross-cutting infrastructure và dependency direction.

**Middle → Senior insight:**
Middle developer nên đánh giá code bằng mức độ thay đổi cùng nhau thay vì chỉ nhìn số layer. Senior developer cần thiết kế boundary sao cho business capability có ownership rõ ràng, dependency dễ kiểm soát và thay đổi cục bộ không lan rộng khắp hệ thống.
