# Daily Developer Tips & Design — 2026-10-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh sync-over-async để không làm nghẽn ThreadPool

**Mẹo:**
Trong ASP.NET Core, giữ call chain bất đồng bộ từ endpoint xuống database/HTTP client; tránh dùng `.Result`, `.Wait()` hoặc bọc I/O bằng `Task.Run`.

**Tại sao hữu ích:**
I/O bất đồng bộ giải phóng worker thread trong lúc chờ. Chặn thread bằng sync-over-async làm số request đồng thời tăng nhanh số worker bị giữ, có thể dẫn tới ThreadPool starvation: latency tăng dù CPU chưa chắc đạt 100%.

**Ví dụ:**
```csharp
// Tốt: không giữ worker thread khi chờ downstream I/O
var customer = await client.GetFromJsonAsync<Customer>(
    $"customers/{id}", cancellationToken);
```
Nếu production có request queue tăng, latency tăng theo tải và `dotnet.thread_pool.queue.length` cao, hãy kiểm tra blocking call trước khi tăng instance.

**Lưu ý:**
`Task.Run` có ích cho một số CPU-bound work, nhưng không biến synchronous database/HTTP I/O thành scalable async I/O. Với legacy API chỉ có synchronous method, cần đo capacity và cô lập bottleneck thay vì che nó bằng thread khác.

### Tip 2 — Dùng savepoint/transaction boundary nhỏ thay vì giữ transaction qua HTTP call

**Mẹo:**
Không giữ SQL transaction mở trong lúc gọi payment, email hoặc third-party REST API. Hoàn tất database work cần atomic càng nhanh càng tốt rồi xử lý external side effect theo workflow phù hợp.

**Tại sao hữu ích:**
Transaction dài giữ locks và connection lâu hơn, làm tăng blocking, deadlock risk và pool pressure. External dependency có latency/failure không nằm dưới quyền kiểm soát của database transaction.

**Ví dụ:**
Checkout không nên mở transaction, insert Order rồi chờ Payment API 8 giây trước khi commit. Có thể persist trạng thái `PendingPayment` trong transaction ngắn, sau đó thực hiện payment với idempotency và chuyển trạng thái theo kết quả.

**Lưu ý:**
Tách transaction tạo ra trạng thái trung gian và partial failure; đừng chỉ “commit sớm” mà bỏ qua recovery semantics. Với workflow cần reliability cao, Outbox/Saga có thể cần thiết.

### Tip 3 — Dùng `EXPLAIN (ANALYZE, BUFFERS)` để phân biệt ước lượng sai và I/O thật trên PostgreSQL

**Mẹo:**
Khi PostgreSQL query chậm, so sánh estimated rows với actual rows và xem buffer activity thay vì chỉ nhìn loại scan.

**Tại sao hữu ích:**
Planner chọn plan dựa trên statistics. Nếu estimated rows lệch lớn so với actual rows, root cause có thể là statistics hoặc data distribution; nếu buffers/read cao, vấn đề có thể nằm ở lượng dữ liệu phải đọc. “Thấy Seq Scan → thêm index” là suy luận chưa đủ.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status
FROM orders
WHERE tenant_id = 42 AND status = 'Pending';
```
Nếu planner ước lượng 20 rows nhưng thực tế 300.000 rows, hãy điều tra selectivity, statistics và index/query shape trước khi thử index ngẫu nhiên.

**Lưu ý:**
`ANALYZE` thực sự chạy statement. Với `UPDATE`/`DELETE` hoặc query nặng trên production, không chạy tùy tiện; dùng môi trường an toàn hoặc transaction/diagnostic strategy phù hợp.

### Tip 4 — Khi Elasticsearch trả kết quả “lạ”, kiểm tra analyzer bằng token thực tế

**Mẹo:**
Trước khi sửa query full-text, kiểm tra field mapping và analyzer đã biến input/document thành tokens nào.

**Tại sao hữu ích:**
Elasticsearch tìm trên inverted index chứ không so chuỗi nguyên bản như `LIKE`. Lowercasing, stemming, tokenizer hoặc mapping `text`/ `keyword` có thể khiến cùng một chuỗi cho kết quả rất khác kỳ vọng.

**Ví dụ:**
Search sản phẩm “ASP.NET Core” không match như mong đợi. Dùng Analyze API để xem tokens của index/search analyzer; nếu filter chính xác theo SKU/category, dùng field `keyword` phù hợp thay vì ép full-text query xử lý exact matching.

**Lưu ý:**
Đổi analyzer của field hiện hữu thường đòi hỏi reindex để dữ liệu cũ có tokenization mới. Đừng thay mapping production mà chưa có migration, alias/switchover và rollback plan.

### Tip 5 — Dùng `git bisect` khi regression có khoảng commit rõ ràng

**Mẹo:**
Nếu biết một commit/tag tốt và một commit xấu, dùng `git bisect` để thu hẹp commit gây regression thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Bisect thực hiện binary search trên lịch sử commit. Khi có test/script tái hiện lỗi, quá trình tìm regression có thể tự động hóa và giảm đáng kể số revision cần kiểm tra.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests
```
Một lỗi serialization xuất hiện sau release có thể được truy về commit thay đổi converter thay vì đoán từ danh sách PR.

**Lưu ý:**
Bisect chỉ đáng tin khi tiêu chí good/bad deterministic. Flaky test, migration thiếu hoặc commit trung gian không build được có thể làm kết quả sai; cần `skip` hoặc script setup ổn định.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database state và message publication

**Khái niệm:**
Outbox ghi business change và message cần publish vào cùng local database transaction. Một publisher riêng đọc outbox và gửi message ra broker, thay vì cố làm database commit và broker publish thành hai thao tác “cùng thành công”.

**Vấn đề nó giải quyết:**
Nếu Order đã commit nhưng process crash trước khi publish `OrderPlaced`, downstream không biết Order tồn tại. Nếu publish trước rồi database rollback, downstream lại xử lý event về state chưa tồn tại.

**Ví dụ thực tế:**
Checkout transaction insert `Order` và `OutboxMessage`. Worker publish message lên Azure Service Bus rồi đánh dấu outbox đã xử lý. Consumer vẫn phải idempotent vì publisher có thể crash sau khi broker nhận message nhưng trước khi đánh dấu sent.

**Trade-off:**
Outbox giảm dual-write inconsistency mà không cần distributed transaction, nhưng thêm table growth, polling/CDC, duplicate delivery, cleanup và monitoring. Với ứng dụng đơn giản không có cross-process integration, pattern này có thể là complexity thừa.

**Middle → Senior insight:**
Middle cần đảm bảo business row và outbox row thực sự cùng transaction, publisher retry an toàn và consumer idempotent. Senior / Technical cần quyết định delivery latency, ordering scope, cleanup, operational ownership và liệu broker integration có đủ giá trị để chấp nhận eventual consistency.

### Design 2 — SQL hay MongoDB theo aggregate và access pattern, không theo “schema linh hoạt”

**Khái niệm:**
Chọn relational hay document database dựa trên invariants, query/access patterns, transaction boundary, data evolution và operational capability. MongoDB cho phép document model linh hoạt nhưng không loại bỏ nhu cầu thiết kế schema.

**Vấn đề nó giải quyết:**
Một product catalog có nested attributes thay đổi theo category khác với ledger cần constraints, joins và transactional integrity mạnh. Dùng cùng một database model cho mọi workload thường tạo trade-off khó chịu ở query hoặc consistency.

**Ví dụ thực tế:**
Catalog snapshot được đọc chủ yếu theo product và cập nhật theo aggregate có thể phù hợp document model. Order/payment ledger cần uniqueness, relational constraints, reporting joins và transaction rõ ràng thường phù hợp SQL hơn. Một hệ thống cũng có thể dùng SQL làm source of truth và projection riêng cho search/read workload.

**Trade-off:**
Document model có thể giảm joins và map gần aggregate, nhưng duplication làm update/invalidation khó hơn và cross-document query có thể tốn kém. Relational model cung cấp constraints/query flexibility mạnh nhưng normalization quá mức có thể làm read path phức tạp.

**Middle → Senior insight:**
Middle cần model theo query pattern và hiểu index/transaction của database đã chọn. Senior / Technical phải đánh giá consistency requirement, growth, migration, backup/restore, team expertise và operational cost; “NoSQL scale hơn” không phải lý do đủ để chọn MongoDB.

### Design 3 — Observability là một phần của architecture boundary

**Khái niệm:**
Logs, metrics và traces nên được thiết kế theo business operation và service boundary, không phải thêm logging ngẫu nhiên sau khi incident xảy ra. Correlation context phải đi qua HTTP, messaging và background processing.

**Vấn đề nó giải quyết:**
Trong distributed workflow, một lỗi “checkout failed” có thể đi qua API, Service Bus consumer, payment provider và database. Nếu mỗi component dùng identifiers/log format riêng, team có dữ liệu nhưng không dựng lại được causal path.

**Ví dụ thực tế:**
`checkoutId`/trace context đi từ ASP.NET Core request sang message metadata và outbound payment call. Dashboard theo dõi latency/error theo stage; trace cho phép từ symptom 5xx đi tới dependency span timeout rồi tới retry/duplicate processing evidence.

**Trade-off:**
Observability tốt rút ngắn MTTR và hỗ trợ capacity/performance decisions, nhưng telemetry có ingestion cost, cardinality risk và nguy cơ lộ sensitive data. Instrument quá chi tiết cũng tạo noise và storage cost.

**Middle → Senior insight:**
Middle cần structured logging, correlation, meaningful metrics và không log secrets/PII tùy tiện. Senior / Technical cần xác định SLI/SLO, telemetry contracts qua boundaries, sampling/cardinality policy và đảm bảo hệ thống có đủ evidence để vận hành trước khi production incident xảy ra.
