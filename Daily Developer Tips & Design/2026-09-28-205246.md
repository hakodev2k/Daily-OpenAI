# Daily Developer Tips & Design — 2026-09-28

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `Task.WhenAll` che mất chiến lược xử lý lỗi

**Mẹo:**
Khi gọi nhiều dependency song song trong ASP.NET Core, chỉ dùng `Task.WhenAll` khi các tác vụ thực sự độc lập. Truyền cùng `CancellationToken`, đặt timeout ở boundary của từng dependency và quyết định rõ lỗi nào làm fail toàn request.

**Tại sao hữu ích:**
Parallel I/O có thể giảm latency tổng từ gần tổng các dependency xuống gần dependency chậm nhất, nhưng đồng thời tăng concurrency và blast radius. Một dependency chậm có thể giữ nhiều socket, connection hoặc request đang chờ cùng lúc.

**Ví dụ:**
```csharp
var profileTask = profileClient.GetAsync(userId, ct);
var ordersTask = orderClient.GetRecentAsync(userId, ct);

await Task.WhenAll(profileTask, ordersTask);

return Results.Ok(new {
    Profile = await profileTask,
    Orders = await ordersTask
});
```
Nếu `Orders` chỉ là dữ liệu phụ, có thể thiết kế degradation thay vì biến lỗi của nó thành HTTP 500 cho toàn endpoint.

**Lưu ý:**
Không dùng parallelization theo phản xạ. Hai query chạy song song trên cùng một `DbContext` là sai vì `DbContext` không hỗ trợ nhiều operation đồng thời; concurrency cũng có thể làm cạn connection pool nhanh hơn.

### Tip 2 — Dùng execution plan để xác minh keyset pagination

**Mẹo:**
Với bảng lớn, thay `OFFSET ... FETCH` bằng keyset pagination cho luồng next/previous liên tục, rồi kiểm tra actual execution plan thay vì chỉ nhìn thời gian chạy một lần.

**Tại sao hữu ích:**
Offset lớn buộc database bỏ qua ngày càng nhiều row. Keyset dùng giá trị cuối trang trước làm điểm bắt đầu, cho phép index seek hiệu quả hơn nếu index phù hợp với predicate và ordering.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @LastCreatedAt)
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)`, với các cột cần đọc thêm cân nhắc đưa vào `INCLUDE`.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới “page 347”. Luôn dùng tie-breaker ổn định như `Id`; chỉ sort theo `CreatedAt` có thể làm mất hoặc lặp record khi nhiều row cùng timestamp.

### Tip 3 — Chẩn đoán 5xx bằng trace trước khi đọc log rời rạc

**Mẹo:**
Khi API trên Azure App Service tăng 5xx, bắt đầu từ failed request trong Application Insights và đi theo distributed trace/dependency telemetry bằng correlation context.

**Tại sao hữu ích:**
Một HTTP 500 ở frontend API có thể thực chất bắt nguồn từ SQL timeout, outbound HTTP 503 hoặc dependency latency. Trace nối các span theo request giúp đi theo chuỗi **symptom → evidence → failing dependency** thay vì grep log theo timestamp.

**Ví dụ:**
Một deployment mới khiến p95 tăng từ 300 ms lên 4 s. Trace cho thấy controller chỉ mất 15 ms nhưng dependency SQL mất 3.8 s. So sánh dependency duration và query telemetry trước/sau deployment sẽ thu hẹp hypothesis nhanh hơn việc tối ưu controller.

**Lưu ý:**
Correlation chỉ hữu ích nếu propagation được giữ qua HTTP/messaging và log có structured properties. Không ghi token, password, connection string hoặc PII nhạy cảm chỉ để “debug dễ hơn”.

### Tip 4 — Test hành vi HTTP thật bằng integration test

**Mẹo:**
Với ASP.NET Core endpoint, dùng `WebApplicationFactory` cho các contract quan trọng thay vì mock controller/service đến mức bỏ qua routing, middleware, authentication và serialization.

**Tại sao hữu ích:**
Nhiều regression nằm ở composition layer: DI registration sai, JSON contract đổi, authorization policy thiếu, middleware order sai. Unit test của method không nhìn thấy các lỗi này.

**Ví dụ:**
```csharp
var client = factory.CreateClient();

var response = await client.GetAsync("/api/orders/42");

response.StatusCode.Should().Be(HttpStatusCode.OK);
var body = await response.Content.ReadFromJsonAsync<OrderDto>();
body!.Id.Should().Be(42);
```
Một test cho endpoint quan trọng có thể xác minh đồng thời route, status code và public JSON contract.

**Lưu ý:**
Không biến mọi test thành integration test. Domain logic thuần vẫn nên được test nhanh ở unit level; integration test cần quản lý database/test data để deterministic và isolation tốt.

### Tip 5 — Dùng Network waterfall để phân biệt frontend chậm và backend chậm

**Mẹo:**
Khi Vue.js/React.js page “load chậm”, mở browser DevTools Network và tách DNS/connect/TLS, TTFB, content download, request chaining và bundle loading trước khi sửa component.

**Tại sao hữu ích:**
Cảm giác UI chậm có thể đến từ backend TTFB, waterfall tuần tự, bundle JavaScript lớn hoặc asset không cache. Đo đúng tầng tránh tối ưu rendering khi bottleneck thực tế nằm ở network/API.

**Ví dụ:**
Nếu page gọi `/profile`, chờ xong mới gọi `/permissions`, rồi mới gọi `/dashboard`, ba request 300 ms tạo thành gần 900 ms critical path. Nếu dữ liệu độc lập, có thể fetch song song hoặc thiết kế endpoint aggregation có chủ đích.

**Lưu ý:**
Gộp mọi API thành một “mega endpoint” chỉ để giảm waterfall có thể tăng coupling và payload. Kiểm tra cache headers, payload size, HTTP version và dependency thực tế trước khi thay đổi contract.

## 🧠 Software Design

### Design 1 — Transactional Outbox cho database + messaging

**Khái niệm:**
Transactional Outbox ghi business state và message/event cần publish vào cùng local database transaction. Một publisher riêng đọc Outbox và gửi sang Azure Service Bus, thay vì cố làm database commit và broker publish thành một atomic distributed transaction.

**Vấn đề nó giải quyết:**
Flow “save Order rồi publish `OrderCreated`” có failure window: database commit thành công nhưng publish thất bại, hoặc ngược lại. Retry đơn thuần không loại bỏ dual-write inconsistency.

**Ví dụ thực tế:**
Checkout tạo `Order` và một `OutboxMessage` trong cùng transaction. Background worker publish message, sau đó đánh dấu đã xử lý. Consumer vẫn phải idempotent vì broker/publisher có thể giao lại message.

**Trade-off:**
Lợi ích là tránh mất event giữa database và broker, phù hợp với eventual consistency. Chi phí là thêm bảng Outbox, polling/publishing, cleanup, monitoring, duplicate handling và độ trễ nhỏ giữa commit với publish.

**Middle → Senior insight:**
Middle developer cần hiểu transaction boundary và triển khai publisher/consumer idempotent đúng. Senior / Technical developer phải quyết định Outbox có thực sự cần thiết dựa trên consistency requirement, failure tolerance và operational cost; không đưa pattern này vào CRUD đơn giản chỉ vì hệ thống có Service Bus.

### Design 2 — Modular Monolith trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployable application nhưng chia domain thành module có boundary, ownership và dependency rõ ràng. Boundary tốt có thể trở thành seam để tách service sau này nếu áp lực vận hành thực sự xuất hiện.

**Vấn đề nó giải quyết:**
Một monolith không kiểm soát dễ thành “big ball of mud”, nhưng tách Microservices quá sớm chuyển coupling trong code thành coupling qua network, deployment, observability và dữ liệu phân tán.

**Ví dụ thực tế:**
E-commerce có `Catalog`, `Ordering`, `Customer` và `Content` modules. Ban đầu cùng ASP.NET Core deployment nhưng không cho `Ordering` truy cập trực tiếp internal repository của `Catalog`; integration đi qua explicit contract.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, local development và transaction, nhưng scaling/independent deployment theo module hạn chế hơn. Microservices cho isolation và deployment autonomy tốt hơn nhưng thêm partial failure, messaging, tracing, versioning và platform overhead.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và module encapsulation. Senior / Technical developer phải nhận diện lý do đủ mạnh để tách service—khác scaling profile, ownership, release cadence, compliance hoặc fault isolation—và tính cả migration/data ownership chứ không chọn Microservices theo xu hướng.

### Design 3 — Idempotency boundary cho API tạo tài nguyên

**Khái niệm:**
Idempotency cho command có side effect đảm bảo nhiều lần gửi cùng logical request không tạo nhiều hiệu ứng nghiệp vụ. Client cung cấp idempotency key; server lưu kết quả hoặc trạng thái xử lý gắn với key và scope phù hợp.

**Vấn đề nó giải quyết:**
Mobile client có thể timeout sau khi server đã tạo payment/order rồi retry. Không có idempotency, retry để tăng reliability lại có thể tạo duplicate order hoặc charge.

**Ví dụ thực tế:**
`POST /payments` nhận `Idempotency-Key`. Server atomically kiểm tra/ghi key cùng transaction boundary thích hợp. Request lặp với cùng key và cùng payload nhận lại kết quả trước đó; cùng key nhưng payload khác bị từ chối.

**Trade-off:**
Lợi ích là retry an toàn hơn trước timeout và network ambiguity. Chi phí gồm storage, TTL, concurrency control, scope của key, replay semantics và xử lý request đang ở trạng thái in-progress.

**Middle → Senior insight:**
Middle developer cần triển khai uniqueness và race handling đúng, không chỉ cache response trong memory. Senior / Technical developer phải xác định idempotency boundary theo business operation, retention period, behavior khi payload khác nhau và cách phối hợp với database/messaging để tránh “idempotent HTTP nhưng duplicate downstream effect”.
