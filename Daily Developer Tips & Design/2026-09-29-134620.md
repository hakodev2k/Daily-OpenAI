# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure cho producer/consumer

**Mẹo:**
Khi một `BackgroundService` nhận work nhanh hơn khả năng xử lý, ưu tiên bounded `Channel<T>` với capacity có chủ đích thay vì đẩy vô hạn vào `ConcurrentQueue<T>` hoặc tạo `Task` không kiểm soát.

**Tại sao hữu ích:**
Bounded channel biến overload thành tín hiệu backpressure: producer phải chờ, drop theo policy, hoặc reject sớm. Điều này giữ memory và concurrency trong giới hạn thay vì để backlog trong RAM tăng cho tới khi GC pressure hoặc OOM xuất hiện.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(
    new BoundedChannelOptions(500)
    {
        FullMode = BoundedChannelFullMode.Wait,
        SingleReader = false,
        SingleWriter = false
    });

await channel.Writer.WriteAsync(job, ct);
```
Một image-processing worker có thể giới hạn queue nội bộ ở 500 jobs và chạy số consumer phù hợp với CPU thay vì spawn một task cho mỗi upload.

**Lưu ý:**
In-memory `Channel<T>` không phải durable queue: process restart sẽ mất backlog. Với work cần delivery guarantee hoặc scale qua nhiều instances, dùng broker như Azure Service Bus; capacity và `FullMode` cũng phải phản ánh business semantics.

### Tip 2 — PostgreSQL partial index cho tập dữ liệu “active” nhỏ nhưng được query liên tục

**Mẹo:**
Nếu workload thường xuyên query một subset ổn định như `status = 'Pending'` trong khi phần lớn rows đã hoàn tất, cân nhắc partial index thay vì index toàn bảng.

**Tại sao hữu ích:**
Index nhỏ hơn có thể giảm storage, write amplification và lượng pages phải đọc. Quan trọng hơn, index phản ánh đúng query shape thay vì đánh index mọi row chỉ vì column xuất hiện trong `WHERE`.

**Ví dụ:**
```sql
CREATE INDEX ix_jobs_pending_created
ON jobs (created_at, id)
WHERE status = 'Pending';
```
Worker lấy pending jobs theo `created_at` có thể scan một cấu trúc nhỏ hơn nhiều so với index chứa cả hàng triệu completed jobs.

**Lưu ý:**
Predicate của query phải phù hợp để planner có thể dùng partial index. Nếu trạng thái phân bố thay đổi mạnh hoặc có nhiều query variants, lợi ích có thể giảm; luôn xác minh bằng `EXPLAIN (ANALYZE, BUFFERS)` và workload thực tế.

### Tip 3 — Theo dõi Service Bus lock duration, không chỉ retry count

**Mẹo:**
Với Azure Service Bus Peek-Lock, đo processing duration so với message lock và cấu hình lock renewal phù hợp cho handler dài; đồng thời giữ consumer idempotent.

**Tại sao hữu ích:**
Nếu handler xử lý 70 giây nhưng lock hết hạn ở giây 60, message có thể được giao lại dù lần xử lý đầu vẫn đang chạy. Triệu chứng thường trông như “duplicate message” nhưng nguyên nhân là ownership lock đã mất.

**Ví dụ:**
Một consumer tạo PDF mất 40–90 giây. Trace ghi `messageId`, delivery count, processing duration và lock-lost failures. Team phát hiện p99 processing vượt lock window, rồi giảm work trong handler hoặc điều chỉnh auto-renew thay vì chỉ tăng `MaxDeliveryCount`.

**Lưu ý:**
Gia hạn lock không biến handler thành exactly-once và không nên che một operation kéo dài vô hạn. External side effects vẫn cần idempotency/deduplication; work rất dài có thể cần tách thành workflow hoặc durable state machine.

### Tip 4 — Dùng `git bisect` khi biết “bản tốt” và “bản lỗi”

**Mẹo:**
Khi regression xuất hiện trong một dải commit lớn, dùng `git bisect` để binary-search commit đầu tiên gây lỗi thay vì đọc tuần tự toàn bộ history.

**Tại sao hữu ích:**
Với một test/reproduction deterministic, số lần kiểm tra giảm theo logarithm. Đây là cách biến production regression thành quá trình tìm kiếm có bằng chứng, đặc biệt khi release chứa hàng chục hoặc hàng trăm commits.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.8.0
git bisect run dotnet test tests/Regression.Tests --filter "CheckoutLatencyRegression"
git bisect reset
```
Nếu test trả exit code đúng, Git tự động thu hẹp commit gây regression.

**Lưu ý:**
`bisect` chỉ đáng tin khi mỗi revision có thể build/test và reproduction đủ deterministic. Flaky test, migration phụ thuộc environment hoặc nhiều thay đổi tương tác có thể khiến kết luận sai.

### Tip 5 — Dùng Content Security Policy như lớp giảm blast radius của XSS

**Mẹo:**
Ngoài output encoding/sanitization, cấu hình Content Security Policy (CSP) để giới hạn nguồn script, frame và resource mà browser được phép thực thi hoặc tải.

**Tại sao hữu ích:**
CSP không sửa lỗ hổng XSS, nhưng có thể làm payload khó thực thi hơn và cung cấp violation reports để phát hiện unexpected script sources. Đây là defense-in-depth hữu ích cho CMS/e-commerce có nhiều third-party scripts.

**Ví dụ:**
Một site loại bỏ inline scripts dần, dùng nonce cho script do server cho phép và giới hạn `script-src` vào các origins thực sự cần. Ban đầu triển khai `Content-Security-Policy-Report-Only` để quan sát violations trước khi enforce.

**Lưu ý:**
Policy quá rộng như `unsafe-inline` hoặc wildcard có thể làm giảm đáng kể giá trị bảo vệ. CSP không thay thế escaping, sanitization hay việc vá injection source; third-party script được allow vẫn chạy với quyền của page.

## 🧠 Software Design

### Design 1 — Contract Testing tại boundary giữa các service

**Khái niệm:**
Contract Testing kiểm tra producer và consumer có còn đồng thuận về request/response/message contract hay không mà không cần biến mọi compatibility check thành full E2E test.

**Vấn đề nó giải quyết:**
Một service có thể pass unit/integration tests riêng nhưng deployment vẫn phá consumer vì đổi field semantics, enum, required property hoặc message shape. Shared OpenAPI/schema chỉ mô tả contract nếu pipeline thực sự kiểm tra compatibility với cách consumer đang dùng nó.

**Ví dụ thực tế:**
Pricing API muốn đổi `discount` từ nullable sang required và đổi một enum value. Consumer contract test thể hiện Mobile API chỉ phụ thuộc một subset cụ thể; CI của producer verify contract trước khi release và phát hiện breaking change trước production.

**Trade-off:**
Contract tests cho feedback nhanh và giảm một phần E2E coupling, nhưng tạo artifacts/versioning/workflow phải duy trì. Contract sai hoặc consumer test quá sát implementation vẫn tạo false confidence; các lỗi network, auth, data và deployment topology vẫn cần integration/E2E coverage.

**Middle → Senior insight:**
Middle developer cần giữ contract tests tập trung vào observable behavior và backward compatibility. Senior / Technical developer phải quyết định ownership, versioning, compatibility policy và vị trí contract testing trong test pyramid; không dùng nó như lý do loại bỏ E2E tests cho critical journeys.

### Design 2 — Normalization vs denormalization theo read/write pressure

**Khái niệm:**
Normalization giảm duplication và giữ invariant ở một nguồn dữ liệu rõ ràng; denormalization cố ý duplicate/precompute dữ liệu để phục vụ read path cụ thể nhanh hoặc đơn giản hơn. Đây là trade-off consistency–query cost, không phải lựa chọn “đúng/sai” tuyệt đối.

**Vấn đề nó giải quyết:**
Một normalized transactional model có thể rất tốt cho write correctness nhưng dashboard phải join/aggregate hàng triệu rows mỗi request. Ngược lại, duplicate mọi field để tránh join làm update fan-out và consistency trở nên khó kiểm soát.

**Ví dụ thực tế:**
Order giữ `ProductId` nhưng đồng thời snapshot `ProductName` và `UnitPrice` tại thời điểm mua vì invoice lịch sử không nên thay đổi khi catalog đổi tên/giá. Một analytics read model khác có thể được materialize asynchronously thay vì làm OLTP schema phục vụ mọi dashboard.

**Trade-off:**
Denormalization giảm read latency và dependency lúc đọc nhưng thêm storage, synchronization, rebuild strategy và stale-data risk. Normalization đơn giản hóa authoritative updates nhưng có thể tăng join/aggregation cost ở read-heavy workload.

**Middle → Senior insight:**
Middle developer cần hiểu invariant nào phải nằm ở source of truth và đo query thực tế trước khi duplicate dữ liệu. Senior / Technical developer phải phân loại snapshot nghiệp vụ với cache/read model, xác định consistency SLA, rebuild/backfill path và cân nhắc liệu index/query optimization đã đủ trước khi tăng data duplication.

### Design 3 — Bulkhead Isolation để một dependency không ăn hết tài nguyên hệ thống

**Khái niệm:**
Bulkhead chia giới hạn tài nguyên/concurrency giữa các workload hoặc dependency để failure ở một khu vực không tiêu thụ toàn bộ threads, connections hay request capacity của process.

**Vấn đề nó giải quyết:**
Nếu một third-party shipping API treo và mọi request đều chờ nó, outbound concurrency có thể tăng cho tới khi socket/ThreadPool/request slots bị chiếm, khiến cả endpoint không liên quan cũng chậm theo.

**Ví dụ thực tế:**
Checkout và background shipping-sync dùng concurrency limits riêng. Shipping integration chỉ cho phép một số lượng outbound operations đồng thời; khi đạt ngưỡng, request được queue/reject theo policy trong khi inventory và account endpoints vẫn còn capacity phục vụ.

**Trade-off:**
Bulkhead giảm blast radius và làm degradation có kiểm soát, nhưng capacity partitioning có thể để tài nguyên nhàn rỗi ở một pool trong khi pool khác quá tải. Giới hạn sai còn tạo queueing latency mới và tăng operational tuning.

**Middle → Senior insight:**
Middle developer cần áp dụng timeout, cancellation và concurrency limit đúng tại dependency boundary. Senior / Technical developer phải chọn isolation unit, capacity dựa trên SLO/load test, degradation behavior và telemetry; bulkhead nên bảo vệ scarce resources thực tế, không phải thêm semaphore tùy tiện vào mọi call.
