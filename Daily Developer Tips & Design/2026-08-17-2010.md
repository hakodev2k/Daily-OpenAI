# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TaskCompletionSource` với `RunContinuationsAsynchronously`

**Mẹo:**
Khi bridge callback/event-based API sang `Task`, tạo `TaskCompletionSource<T>` với `TaskCreationOptions.RunContinuationsAsynchronously` để continuation của consumer không chạy inline ngay trên thread đang gọi `SetResult`/`SetException`.

**Tại sao hữu ích:**
Giảm nguy cơ re-entrancy, lock inversion và latency bất ngờ khi code hoàn tất task đang chạy bên trong callback, event handler hoặc critical section.

**Ví dụ:**
```csharp
var tcs = new TaskCompletionSource<string>(
    TaskCreationOptions.RunContinuationsAsynchronously);

legacyClient.Completed += (_, result) =>
    tcs.TrySetResult(result);

legacyClient.Start();

var value = await tcs.Task;
```

**Lưu ý:**
Option này không biến callback API thành thread-safe. Vẫn cần xử lý race giữa success, error, timeout và cancellation bằng `TrySetResult`, `TrySetException`, `TrySetCanceled` phù hợp.

### Tip 2 — Dùng savepoint khi một transaction cần rollback một phần công việc

**Mẹo:**
Nếu nhiều bước phải nằm trong cùng database transaction nhưng một bước phụ có thể retry hoặc bỏ qua, savepoint cho phép rollback về một mốc mà không hủy toàn bộ transaction.

**Tại sao hữu ích:**
Hữu dụng trong batch/import hoặc workflow nhiều bước khi bạn muốn giữ các thay đổi đã hợp lệ trước đó nhưng vẫn xử lý failure cục bộ có kiểm soát.

**Ví dụ:**
EF Core:

```csharp
await using var tx =
    await dbContext.Database.BeginTransactionAsync(cancellationToken);

await SaveOrderAsync();
await tx.CreateSavepointAsync("BeforeAudit", cancellationToken);

try
{
    await SaveAuditAsync();
}
catch
{
    await tx.RollbackToSavepointAsync(
        "BeforeAudit",
        cancellationToken);
}

await tx.CommitAsync(cancellationToken);
```

**Lưu ý:**
Đừng dùng savepoint để che lỗi business quan trọng. Nếu bước thất bại làm invariant toàn transaction không còn đúng, rollback toàn bộ vẫn là lựa chọn đúng.

### Tip 3 — Dùng `dotnet restore --locked-mode` để CI không âm thầm đổi dependency graph

**Mẹo:**
Nếu repository dùng NuGet lock file, chạy restore ở CI với `--locked-mode` để build fail khi dependency resolution khác với lock file đã commit.

**Tại sao hữu ích:**
Giảm tình trạng cùng một commit nhưng build ở thời điểm khác lại lấy transitive dependency khác, gây regression khó tái hiện.

**Ví dụ:**
```bash
dotnet restore --locked-mode
```

Trong project có thể bật:

```xml
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>
```

**Lưu ý:**
Khi chủ động update package, cần regenerate và review lock file. Không coi lock file là thay thế cho vulnerability scanning hoặc dependency update policy.

### Tip 4 — Dùng `tcpdump` để xác nhận packet có thật sự rời máy hay không

**Mẹo:**
Khi DNS đúng, port đúng nhưng request vẫn timeout, dùng `tcpdump` để kiểm tra SYN, retransmission hoặc packet response ở network layer trước khi tiếp tục debug application.

**Tại sao hữu ích:**
Giúp phân biệt nhanh lỗi application với firewall, routing, asymmetric network path hoặc remote endpoint không phản hồi.

**Ví dụ:**
```bash
sudo tcpdump -ni any host 10.20.30.40 and port 443
```

Hoặc chỉ xem TCP SYN:

```bash
sudo tcpdump -ni any 'tcp[tcpflags] & tcp-syn != 0'
```

**Lưu ý:**
Packet capture có thể chứa dữ liệu nhạy cảm và tạo nhiều output. Lọc theo host/port, hạn chế thời gian capture và tuân thủ quy định bảo mật môi trường production.

### Tip 5 — Dùng `git notes` cho metadata nội bộ mà không sửa commit message

**Mẹo:**
Khi cần gắn thêm thông tin như ticket điều tra, benchmark result hoặc production incident reference vào commit đã tồn tại, có thể dùng `git notes` thay vì rewrite history.

**Tại sao hữu ích:**
Giữ nguyên commit SHA nhưng vẫn bổ sung metadata phục vụ tra cứu hoặc automation nội bộ.

**Ví dụ:**
```bash
git notes add -m "Validated against incident INC-4821" <commit-sha>
```

Xem note:

```bash
git show <commit-sha>
```

**Lưu ý:**
Git notes không được push/fetch theo mặc định trong mọi workflow. Nếu team dùng chúng, cần thống nhất ref, CI behavior và cách đồng bộ notes giữa developers.

## 🧠 Software Design

### Design 1 — Fail-open hay Fail-closed phải theo mức độ rủi ro của dependency

**Khái niệm:**
Khi một dependency kiểm tra policy, quota, feature flag hoặc security bị lỗi, hệ thống phải quyết định tiếp tục cho phép operation (fail-open) hay từ chối operation (fail-closed).

**Vấn đề nó giải quyết:**
Không phải mọi dependency failure đều nên biến thành outage toàn hệ thống, nhưng cho phép tiếp tục sai chỗ có thể tạo security hoặc financial incident.

**Ví dụ thực tế:**
Nếu service kiểm tra “recommendation personalization” bị down, e-commerce có thể fail-open và hiển thị default recommendation. Nhưng nếu authorization service không xác nhận user được quyền export payroll, backend nên fail-closed.

**Trade-off:**
Fail-open tăng availability nhưng có thể vi phạm policy hoặc tính đúng đắn. Fail-closed an toàn hơn cho security/invariant nhưng dependency outage có thể làm business operation dừng hoàn toàn.

**Middle → Senior insight:**
Middle developer nên tránh một policy chung kiểu “catch exception rồi cho qua” hoặc “dependency lỗi thì 500 tất cả”. Senior developer cần phân loại dependency theo security, money, data integrity, UX và regulatory impact để xác định fallback behavior rõ ràng.

### Design 2 — Read-your-writes consistency cho trải nghiệm user sau khi vừa cập nhật

**Khái niệm:**
Read-your-writes bảo đảm user nhìn thấy chính thay đổi họ vừa ghi, ngay cả khi hệ thống dùng replica, cache hoặc read model có độ trễ.

**Vấn đề nó giải quyết:**
Sau khi update profile hoặc approve timesheet, user refresh ngay nhưng read replica chưa sync và thấy dữ liệu cũ, tạo cảm giác thao tác vừa thất bại.

**Ví dụ thực tế:**
Sau `POST /profile`, hệ thống có thể tạm route các read của cùng user tới primary trong vài giây, hoặc trả representation mới trực tiếp trong response và dùng version token để tránh đọc stale replica ngay sau đó.

**Trade-off:**
Cải thiện UX và giảm confusion nhưng làm routing/cache logic phức tạp hơn, đồng thời có thể tăng load lên primary nếu consistency window quá rộng.

**Middle → Senior insight:**
Middle developer nên hiểu eventual consistency không đồng nghĩa user luôn phải chấp nhận dữ liệu cũ. Senior developer cần xác định scope, thời lượng consistency window, version propagation và trường hợp nào đáng trả giá để có read-your-writes.

### Design 3 — BFF chỉ nên tồn tại khi client thật sự có orchestration hoặc contract riêng

**Khái niệm:**
Backend for Frontend (BFF) tạo backend riêng cho một loại client như web, mobile hoặc partner portal để gom orchestration, shape response và client-specific behavior.

**Vấn đề nó giải quyết:**
Mobile có thể cần payload nhỏ, ít round-trip và workflow khác web. Nếu mọi client dùng chung một API “universal”, API dễ tích lũy tham số, field và endpoint compromise cho tất cả bên.

**Ví dụ thực tế:**
Mobile home screen cần dữ liệu từ Profile, Notification và Timesheet. BFF mobile gọi ba backend nội bộ rồi trả một response tối ưu cho màn hình thay vì bắt app gọi ba endpoint qua mạng di động.

**Trade-off:**
BFF giảm coupling giữa client và nhiều backend, tối ưu UX từng client nhưng thêm deployment, observability, auth propagation và nguy cơ duplicate business logic giữa nhiều BFF.

**Middle → Senior insight:**
Middle developer nên giữ BFF tập trung vào composition/client concerns, không chuyển domain logic vào đó. Senior developer cần chứng minh client có nhu cầu contract/orchestration riêng đủ lớn trước khi tạo thêm một service boundary phải vận hành lâu dài.
