# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CollectionsMarshal.GetValueRefOrAddDefault` khi update `Dictionary` trên hot path

**Mẹo:**
Nếu profiling cho thấy bạn liên tục `TryGetValue` rồi ghi ngược lại cùng một key trong `Dictionary<TKey,TValue>`, có thể dùng `CollectionsMarshal.GetValueRefOrAddDefault` để thao tác trực tiếp trên value slot và tránh lookup hai lần.

**Tại sao hữu ích:**
Trên hot path như counter aggregation, parser hoặc in-memory indexing, giảm hash lookup lặp lại có thể giúp giảm CPU overhead.

**Ví dụ:**
```csharp
using System.Runtime.InteropServices;

var counts = new Dictionary<string, int>();

ref int count = ref CollectionsMarshal.GetValueRefOrAddDefault(
    counts,
    "pending",
    out bool exists);

if (!exists)
{
    count = 0;
}

count++;
```

**Lưu ý:**
Đây là API low-level. Không giữ `ref` rồi tiếp tục thay đổi cấu trúc dictionary vì resize có thể làm reference không còn hợp lệ. Chỉ dùng khi benchmark chứng minh giá trị thực tế.

### Tip 2 — Dùng `HttpRequestMessage` khi một request cần header/timeout behavior riêng

**Mẹo:**
Đừng nhét mọi header hoặc behavior đặc biệt vào `HttpClient.DefaultRequestHeaders`. Với request có `If-None-Match`, custom correlation header hoặc auth scope riêng, tạo `HttpRequestMessage` theo từng call.

**Tại sao hữu ích:**
Giảm shared mutable state, tránh header vô tình áp dụng sang request khác và làm intent của outbound call rõ ràng hơn.

**Ví dụ:**
```csharp
using var request = new HttpRequestMessage(
    HttpMethod.Get,
    $"/api/orders/{orderId}");

request.Headers.TryAddWithoutValidation("If-None-Match", etag);
request.Headers.TryAddWithoutValidation("X-Correlation-Id", correlationId);

using var response = await httpClient.SendAsync(
    request,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);
```

**Lưu ý:**
`HttpRequestMessage` chỉ nên được gửi một lần. Không reuse cùng instance cho nhiều request song song.

### Tip 3 — Dùng `git show --stat` và `git show --name-status` trước khi đọc toàn bộ patch

**Mẹo:**
Khi review một commit lớn hoặc điều tra regression, xem phạm vi thay đổi trước rồi mới mở patch chi tiết.

**Tại sao hữu ích:**
Bạn nhanh chóng thấy commit chạm bao nhiêu file, file nào bị rename/delete và khu vực nào có churn lớn để ưu tiên review đúng chỗ.

**Ví dụ:**
```bash
git show --stat <commit>
git show --name-status <commit>
```

Sau đó chỉ mở patch cho file quan trọng:

```bash
git show <commit> -- src/Payments/PaymentService.cs
```

**Lưu ý:**
File churn lớn không đồng nghĩa bug nằm ở đó. Đây là bước định hướng review, không thay thế việc hiểu behavior thay đổi.

### Tip 4 — Dùng `SET LOCK_TIMEOUT` hoặc timeout tương đương khi migration có nguy cơ chờ lock quá lâu

**Mẹo:**
Với migration production, tránh để một câu `ALTER TABLE` chờ lock vô hạn rồi làm deployment treo. Đặt lock timeout ngắn và fail có kiểm soát nếu bảng đang bận.

**Tại sao hữu ích:**
Giảm nguy cơ deployment vô tình giữ session chờ rất lâu, tạo blocking chain hoặc làm pipeline đứng mà không biết nguyên nhân.

**Ví dụ:**
SQL Server:

```sql
SET LOCK_TIMEOUT 5000;

ALTER TABLE Orders
ADD ExternalReference nvarchar(100) NULL;
```

Nếu không lấy được lock trong 5 giây, migration fail để team retry ở thời điểm an toàn hơn.

**Lưu ý:**
Timeout không làm schema change an toàn hơn về mặt thiết kế. Với bảng lớn, vẫn phải đánh giá metadata lock, table rewrite, index rebuild và chiến lược deploy riêng.

### Tip 5 — Dùng `jq` để kiểm tra JSON ngay trong incident thay vì đọc bằng mắt

**Mẹo:**
Khi debug API hoặc log JSON trên Linux/CI, dùng `jq` để lọc field, sort, group hoặc validate dữ liệu thay vì copy payload sang editor.

**Tại sao hữu ích:**
Rút ngắn thời gian điều tra và giúp tạo command có thể lặp lại hoặc chia sẻ trong runbook.

**Ví dụ:**
```bash
curl -s https://api.example.com/jobs \
  | jq '.items[] | select(.status == "Failed") | {id, errorCode}'
```

Đếm theo trạng thái:

```bash
jq -r '.items[].status' response.json | sort | uniq -c
```

**Lưu ý:**
Cẩn thận khi pipe response có secrets/token vào terminal history hoặc log CI. Redact dữ liệu nhạy cảm trước khi lưu output.

## 🧠 Software Design

### Design 1 — Deadline propagation thay vì mỗi service tự đặt timeout độc lập

**Khái niệm:**
Deadline propagation truyền “thời gian còn lại” của toàn request xuyên qua các service/dependency thay vì để mỗi tầng tự cấp một timeout đầy đủ mới.

**Vấn đề nó giải quyết:**
Nếu API ngoài có SLA 2 giây nhưng Service A gọi B với timeout 2 giây, B lại gọi C với timeout 2 giây, tổng latency thực tế có thể vượt xa budget ban đầu và retry tiếp tục chạy ngay cả khi client đã bỏ cuộc.

**Ví dụ thực tế:**
Gateway nhận request với deadline còn 1800 ms. Sau validation mất 300 ms, downstream call chỉ còn khoảng 1500 ms. Service tiếp theo tiếp tục trừ thời gian đã tiêu tốn thay vì bắt đầu lại một timeout mới.

**Trade-off:**
Deadline propagation giúp latency predictable hơn và giảm work vô ích sau khi request đã hết giá trị. Đổi lại, hệ thống phải truyền context nhất quán và xử lý trường hợp dependency cần minimum execution time riêng.

**Middle → Senior insight:**
Middle developer nên hiểu timeout phải được propagate và cancel downstream work. Senior developer cần thiết kế latency budget theo từng hop, retry budget, queueing time và fallback để toàn call chain vẫn nằm trong SLO đầu-cuối.

### Design 2 — Expand-and-Contract cho database migration zero/low-downtime

**Khái niệm:**
Expand-and-Contract chia schema change thành nhiều deployment tương thích ngược: đầu tiên mở rộng schema, sau đó migrate traffic/data, cuối cùng mới xóa cấu trúc cũ.

**Vấn đề nó giải quyết:**
Nếu deploy code mới và rename/drop column ngay lập tức, các instance cũ còn chạy trong rolling deployment có thể crash hoặc ghi dữ liệu sai.

**Ví dụ thực tế:**
Cần đổi `FullName` thành `DisplayName`:

1. Add `DisplayName` nhưng vẫn giữ `FullName`.
2. Deploy code có thể đọc cả hai và ghi theo strategy chuyển tiếp.
3. Backfill dữ liệu cũ.
4. Chuyển toàn bộ read/write sang `DisplayName`.
5. Sau khi chắc chắn không còn consumer cũ, drop `FullName`.

**Trade-off:**
Giảm deployment risk và hỗ trợ rollback tốt hơn, nhưng cần nhiều release, dual-read/write tạm thời và cleanup discipline. Nếu bỏ quên bước contract, schema sẽ tích tụ technical debt.

**Middle → Senior insight:**
Middle developer nên tránh coi migration là một bước SQL độc lập với deployment. Senior developer phải thiết kế compatibility window, backfill strategy, rollback path, telemetry và tiêu chí rõ ràng để xóa contract cũ an toàn.

### Design 3 — Versioning event schema: ưu tiên additive change trước khi tạo version mới

**Khái niệm:**
Event contract nên tiến hóa bằng thay đổi tương thích ngược như thêm optional field trước khi chọn breaking version hoặc topic/event type mới.

**Vấn đề nó giải quyết:**
Trong event-driven system, producer và consumer hiếm khi deploy cùng lúc. Breaking change nhỏ ở event có thể làm consumer cũ lỗi hàng loạt hoặc silently parse sai dữ liệu.

**Ví dụ thực tế:**
`OrderCreated` ban đầu có `orderId`, `customerId`, `total`. Nếu cần thêm `salesChannel`, thêm field optional để consumer cũ vẫn hoạt động. Nếu semantics của `total` thay đổi hoàn toàn, nên cân nhắc event version mới thay vì tái sử dụng cùng field với meaning khác.

**Trade-off:**
Additive evolution giảm coordination cost nhưng làm contract có nhiều optional/legacy field theo thời gian. Version mới sạch hơn về semantics nhưng tạo nhiều consumer path, migration và vận hành song song.

**Middle → Senior insight:**
Middle developer nên phân biệt thêm field với thay đổi meaning của field. Senior developer cần quản lý schema compatibility, default behavior, replay dữ liệu cũ, deprecation window và đảm bảo event versioning phản ánh semantic change chứ không chỉ thay đổi DTO.
