# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Giới hạn concurrency khi gọi nhiều dependency thay vì `Task.WhenAll` vô điều kiện

**Mẹo:**
Khi cần xử lý hàng trăm item song song, đừng tạo toàn bộ task rồi `Task.WhenAll()` nếu mỗi task gọi database, HTTP API hoặc storage. Hãy đặt concurrency limit rõ ràng bằng `Parallel.ForEachAsync`, `SemaphoreSlim` hoặc worker queue.

**Tại sao hữu ích:**
Async không làm dependency có capacity vô hạn. Burst 1.000 request cùng lúc có thể làm cạn connection pool, chạm rate limit hoặc tăng tail latency dù CPU application vẫn thấp. Bounded concurrency biến throughput thành tham số có thể kiểm soát thay vì để input size quyết định tải lên downstream.

**Ví dụ:**
```csharp
await Parallel.ForEachAsync(
    customerIds,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 8,
        CancellationToken = ct
    },
    async (customerId, token) =>
    {
        await SyncCustomerAsync(customerId, token);
    });
```

Tune `MaxDegreeOfParallelism` theo latency và capacity của dependency, không theo số core một cách máy móc.

**Lưu ý:**
Concurrency quá thấp làm throughput giảm; quá cao tạo contention và timeout. Nếu work cần durability hoặc backlog lớn, in-process parallelism không thay thế durable queue/message broker.

### Tip 2 — Chỉ dùng EF Core compiled query khi profiling chứng minh query compilation đáng kể

**Mẹo:**
Với hot path gọi cùng query shape rất nhiều lần, có thể cân nhắc `EF.CompileAsyncQuery`, nhưng chỉ sau khi đo và xác nhận query compilation thực sự nằm trong bottleneck.

**Tại sao hữu ích:**
EF Core đã cache nhiều metadata/query plan nội bộ. Compiled query bỏ thêm một phần overhead ở application side, nhưng thường nhỏ so với network latency, database execution hoặc materialization. Nó hữu ích nhất ở query cực nóng, đơn giản và latency-sensitive.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<Order>>
    OrdersByCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, Guid customerId) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.CustomerId == customerId));
```

Hãy benchmark end-to-end trước và sau, thay vì suy luận từ micro-benchmark riêng phần query compilation.

**Lưu ý:**
Compiled query làm code ít linh hoạt hơn khi query shape thay đổi động. Nó không sửa N+1, missing index, projection quá rộng hoặc SQL tệ; những vấn đề đó thường lớn hơn nhiều.

### Tip 3 — Giữ predicate SARGable để SQL Server còn tận dụng index seek

**Mẹo:**
Tránh bọc indexed column trong function khi filter nếu có thể viết điều kiện tương đương theo range hoặc giá trị gốc.

**Tại sao hữu ích:**
Predicate như `YEAR(CreatedAt) = 2026` buộc optimizer phải tính function trên nhiều row và thường khó dùng index seek hiệu quả. Range predicate cho phép engine định vị trực tiếp đoạn index cần đọc.

**Ví dụ:**
```sql
-- Kém SARGable
WHERE YEAR(CreatedAt) = 2026

-- Tốt hơn
WHERE CreatedAt >= '2026-01-01'
  AND CreatedAt <  '2027-01-01';
```

Kiểm tra actual execution plan và logical reads để xác nhận tác động thật.

**Lưu ý:**
SARGability không đảm bảo optimizer luôn chọn index seek. Selectivity thấp, statistics, parameter sensitivity hoặc index design vẫn có thể khiến scan là phương án đúng.

### Tip 4 — Với Azure App Service deployment slot, đánh dấu đúng `slot setting` cho cấu hình không được swap

**Mẹo:**
Khi dùng staging/production slots, phân biệt config nào đi theo application version và config nào phải “dính” với slot, rồi đánh dấu `Deployment slot setting` cho những giá trị environment-specific.

**Tại sao hữu ích:**
Slot swap có thể chuyển application code sang production mà không nên chuyển nhầm secret endpoint, queue name, diagnostic setting hoặc integration dành riêng cho staging. Sai semantics ở đây dễ tạo incident dù deployment bản thân thành công.

**Ví dụ:**
```text
Có thể đi theo version:
- feature defaults
- application behavior config

Thường nên sticky theo slot:
- staging-only endpoint
- environment-specific secret reference
- queue/topic dành riêng staging
```

Sau mỗi thay đổi cấu hình, kiểm tra cả source slot và target slot trước khi swap.

**Lưu ý:**
Không dùng slot setting để che thiếu sót trong configuration governance. Cần tài liệu hóa source of truth, Key Vault reference/Managed Identity và rollback behavior khi swap thất bại.

### Tip 5 — Content Security Policy nên bắt đầu từ report-only rồi siết dần

**Mẹo:**
Khi thêm Content Security Policy cho website/CMS, triển khai `Content-Security-Policy-Report-Only` trước để quan sát script/style/resource nào đang vi phạm rồi mới chuyển sang enforcement.

**Tại sao hữu ích:**
CSP giúp giảm tác động của XSS bằng cách giới hạn nguồn script/resource được phép chạy, nhưng policy quá chặt ngay lập tức có thể phá analytics, CMS widgets, third-party checkout hoặc inline script hợp lệ. Report-only cho evidence trước khi chặn thật.

**Ví dụ:**
```http
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none';
```

Với inline script cần thiết, nonce/hashes thường an toàn hơn mở rộng bằng `'unsafe-inline'`.

**Lưu ý:**
CSP là defense-in-depth, không thay thế output encoding, input validation và framework escaping. Đồng thời tránh allowlist domain quá rộng chỉ để “hết lỗi report”.

## 🧠 Software Design

### Design 1 — Singleton scheduled job: leader election hay idempotent distributed work

**Khái niệm:**
Khi application chạy nhiều instance nhưng một scheduled job chỉ nên thực hiện logical work một lần, có hai hướng phổ biến: chọn một leader/lease owner để chạy job, hoặc cho nhiều instance cùng chạy nhưng làm từng work item idempotent và deduplicate ở storage.

**Vấn đề nó giải quyết:**
Một `BackgroundService` hoặc scheduler chạy đúng trên local có thể chạy 4 lần sau khi App Service/Kubernetes scale lên 4 replicas, dẫn tới gửi email trùng, generate report trùng hoặc cập nhật cùng dữ liệu nhiều lần.

**Ví dụ thực tế:**
```text
Leader election:
instance A giữ lease 30s
-> chỉ A chạy reconciliation job
-> A chết, B lấy lease tiếp

Idempotent distributed work:
A và B cùng scan
-> mỗi item claim bằng atomic update/unique key
-> item chỉ được xử lý một lần về mặt business
```

**Trade-off:**
Leader election đơn giản hóa flow nhưng lease/failover trở thành coordination dependency và có thể giảm parallelism. Idempotent distributed processing scale tốt hơn nhưng đòi hỏi claim semantics, deduplication và recovery rõ ràng.

**Middle → Senior insight:**
Middle developer cần nhận ra scheduled job trên nhiều instance là distributed problem và không dựa vào in-memory lock. Senior / Technical developer phải chọn coordination model theo workload, failure tolerance, throughput, retry semantics và cost của duplicate processing.

### Design 2 — Versioned cache key thay cho invalidation phức tạp khi dữ liệu có generation rõ ràng

**Khái niệm:**
Thay vì tìm và xóa mọi cache key liên quan khi dữ liệu thay đổi, một số hệ thống dùng version/generation trong cache key. Khi version tăng, application tự đọc namespace key mới và dữ liệu cũ hết TTL dần.

**Vấn đề nó giải quyết:**
Cache invalidation theo dependency graph dễ bỏ sót key: update product có thể ảnh hưởng product detail, category listing, search facet và homepage projection. Delete từng key dễ tạo stale data nếu mapping dependency không đầy đủ.

**Ví dụ thực tế:**
```text
CatalogVersion = 42
catalog:42:category:shoes:page:1
catalog:42:product:123

Publish catalog mới
-> CatalogVersion = 43
-> request mới dùng catalog:43:...
-> key version 42 tự expire
```

Pattern này hợp với snapshot/catalog generation hơn dữ liệu cập nhật từng record liên tục.

**Trade-off:**
Versioned key giảm complexity của invalidation nhưng có thể tạo memory spike tạm thời vì hai generation cùng tồn tại và tăng cache miss sau mỗi version bump. Với update nhỏ, xóa đúng key có thể hiệu quả hơn.

**Middle → Senior insight:**
Middle developer cần hiểu cache key là một phần của consistency design. Senior / Technical developer phải chọn invalidation strategy theo update granularity, freshness SLA, cache capacity và khả năng rebuild/warm dữ liệu thay vì áp một pattern cho mọi cache.

### Design 3 — Architecture Decision Record cho quyết định khó đảo ngược, không cho mọi lựa chọn nhỏ

**Khái niệm:**
Architecture Decision Record (ADR) ghi ngắn gọn context, decision, alternatives và consequences của một quyết định kỹ thuật quan trọng để lý do tồn tại lâu hơn người ra quyết định.

**Vấn đề nó giải quyết:**
Sau vài tháng, team thường chỉ thấy “hệ thống đang dùng X” nhưng không biết tại sao không chọn Y, constraint nào từng tồn tại hay điều kiện nào khiến quyết định cần xem lại. Điều này dẫn tới cargo-cult hoặc lặp lại tranh luận cũ.

**Ví dụ thực tế:**
```text
ADR-017: Dùng PostgreSQL thay vì Cosmos DB cho Order workflow
Context:
- transaction nhiều entity
- query relational rõ
- scale hiện tại vừa phải

Consequence:
- đơn giản consistency
- chưa tối ưu cho geo-distributed write
- revisit nếu traffic/region model thay đổi
```

ADR nên gắn với quyết định có impact đáng kể như datastore, integration style, deployment topology hoặc security boundary.

**Trade-off:**
ADR cải thiện traceability và onboarding nhưng sẽ thành bureaucracy nếu mọi package/library nhỏ đều cần một record. Document cũng phải được cập nhật trạng thái khi decision bị supersede.

**Middle → Senior insight:**
Middle developer cần biết đọc decision context trước khi “refactor cho sạch hơn”. Senior / Technical developer phải ghi rõ constraint, rejected alternatives, consequence và trigger để revisit; giá trị nằm ở reasoning có thể kiểm chứng, không phải số lượng tài liệu.
