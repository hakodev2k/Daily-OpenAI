# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` khi cần update hàng loạt mà không cần materialize entity

**Mẹo:**
Trong EF Core, nếu cần update nhiều row theo cùng một rule và không cần chạy business logic trên từng entity trong memory, cân nhắc `ExecuteUpdateAsync` thay vì `ToListAsync` rồi sửa từng object.

**Tại sao hữu ích:**
Cách load entity trước sẽ tốn round trip, memory và change tracking; sau đó EF Core còn phải phát nhiều update theo batch. `ExecuteUpdateAsync` dịch operation thành SQL update trực tiếp trên database, giảm materialization và allocation đáng kể.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```

**Lưu ý:**
Operation này bypass change tracker và không chạy logic nằm trong entity instance. Nếu invariant, domain event hoặc audit phụ thuộc vào việc hydrate từng aggregate, bulk update trực tiếp có thể sai về semantics dù nhanh hơn.

### Tip 2 — Với MongoDB compound index, query pattern phải khớp prefix của index

**Mẹo:**
Khi tạo compound index trong MongoDB, sắp xếp field theo access pattern thực tế và nhớ rằng query thường tận dụng tốt nhất prefix từ trái sang phải của index.

**Tại sao hữu ích:**
Index `{ tenantId: 1, status: 1, createdAt: -1 }` phù hợp cho query có `tenantId`, rồi filter theo `status`, rồi sort theo `createdAt`. Query chỉ theo `createdAt` thường không tận dụng index này hiệu quả như mong đợi.

**Ví dụ:**
```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })
```

Query phù hợp:
```javascript
db.orders.find({ tenantId: "t-42", status: "Open" })
         .sort({ createdAt: -1 })
```

**Lưu ý:**
Đừng tạo compound index cho mọi combination của filter. Mỗi index tăng storage, write amplification và memory pressure. Dùng `explain()` và workload thực tế để quyết định index nào đáng giữ.

### Tip 3 — Ưu tiên Managed Identity khi App Service truy cập Azure Key Vault

**Mẹo:**
Với application chạy trên Azure App Service, ưu tiên Managed Identity để lấy secret từ Azure Key Vault thay vì lưu client secret hoặc access key trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ credential tĩnh khỏi app settings và pipeline. Azure cấp token cho workload identity, còn Key Vault kiểm soát quyền truy cập theo identity đó, giảm rủi ro secret bị leak hoặc hết hạn mà không được rotate.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUrl),
    new DefaultAzureCredential());
```

Ở Azure, credential chain có thể dùng Managed Identity; local development vẫn có thể dùng developer credential phù hợp.

**Lưu ý:**
Managed Identity không tự bảo đảm least privilege. Chỉ cấp đúng secret/action application cần và tách identity giữa environment hoặc workload khi blast radius khác nhau.

### Tip 4 — Dùng `git worktree` khi cần làm song song nhiều branch mà không clone repository lần nữa

**Mẹo:**
Khi đang làm feature nhưng cần hotfix hoặc review một branch khác song song, dùng `git worktree` để tạo working directory thứ hai trỏ tới cùng repository object database.

**Tại sao hữu ích:**
Bạn không cần stash liên tục hoặc clone thêm toàn bộ repository. Mỗi worktree có working tree riêng nhưng chia sẻ Git objects, phù hợp khi build/test hai branch độc lập cùng lúc.

**Ví dụ:**
```bash
git worktree add ../app-hotfix hotfix/login-timeout
cd ../app-hotfix
dotnet test
```

Sau khi xong:
```bash
git worktree remove ../app-hotfix
```

**Lưu ý:**
Một branch thông thường không thể được checkout đồng thời ở hai worktree. Cũng cần chú ý build artifact hoặc external resource dùng chung như port, database local hay Docker container để tránh conflict ngoài Git.

### Tip 5 — Khi INP xấu, tìm long task trong event handler trước khi tối ưu bundle size chung chung

**Mẹo:**
Nếu Core Web Vitals cho thấy Interaction to Next Paint (INP) cao, dùng browser DevTools Performance trace để tìm interaction nào giữ main thread quá lâu thay vì chỉ giảm bundle size theo phản xạ.

**Tại sao hữu ích:**
INP đo độ trễ từ user interaction đến lúc browser có thể paint response tiếp theo. Một click handler chạy synchronous computation, render quá nhiều component hoặc trigger layout work lớn có thể làm INP xấu dù initial page load vẫn nhanh.

**Ví dụ:**
```text
Click "Add to cart"
-> 140 ms JavaScript handler
-> 90 ms style/layout
-> render update
-> interaction latency > 200 ms
```

Từ trace có thể tách computation, giảm work đồng bộ hoặc hoãn phần không cần thiết khỏi critical interaction.

**Lưu ý:**
Bundle size vẫn quan trọng cho startup, nhưng không phải mọi INP issue đều do bundle lớn. Đo interaction cụ thể và main-thread work trước khi chọn optimization.

## 🧠 Software Design

### Design 1 — Shared Database vs Database Ownership theo module/service

**Khái niệm:**
Shared Database cho nhiều module/service cùng đọc ghi một schema chung. Database ownership giới hạn mỗi module/service sở hữu dữ liệu của mình và các boundary khác phải đi qua contract hoặc integration mechanism rõ ràng.

**Vấn đề nó giải quyết:**
Shared database giúp query/join và transaction ban đầu đơn giản, nhưng khi nhiều team hoặc service cùng sửa cùng table, schema trở thành coupling point. Một thay đổi column có thể ảnh hưởng nhiều hệ thống mà không có API boundary bảo vệ.

**Ví dụ thực tế:**
```text
Shared DB:
Orders service -> Orders table
Billing service -> đọc trực tiếp Orders table
Analytics service -> đọc trực tiếp Orders table
```

Khi Billing có ownership riêng, có thể chuyển sang contract/event/read projection thay vì truy cập table của Orders trực tiếp.

**Trade-off:**
Shared database giảm operational complexity và thuận tiện cho transaction local, nhưng tăng coupling và làm ownership mơ hồ. Data ownership rõ giúp evolution độc lập hơn nhưng thêm API/message integration, eventual consistency và duplicated projection.

**Middle → Senior insight:**
Middle developer cần tránh cross-module query tùy tiện khi boundary đã được định nghĩa. Senior / Technical developer phải chọn mức isolation dựa trên team ownership, transaction need, scale và migration cost; không tách database chỉ để "đúng microservices".

### Design 2 — Consumer-Driven Contract Testing cho integration giữa các service

**Khái niệm:**
Consumer-Driven Contract Testing kiểm chứng provider vẫn đáp ứng những contract mà consumer thực sự phụ thuộc, thay vì chỉ test provider theo assumptions nội bộ của provider.

**Vấn đề nó giải quyết:**
Một API change có thể vẫn pass unit/integration tests của provider nhưng làm consumer production hỏng vì field bị rename, status code đổi hoặc nullability thay đổi. Contract test tạo feedback sớm trước khi deploy hai service không tương thích.

**Ví dụ thực tế:**
Consumer khai báo kỳ vọng:
```text
GET /customers/42
-> 200
-> customerId: string
-> status: "Active" | "Disabled"
```

Provider CI verify contract này trước release.

**Trade-off:**
Contract test giảm integration regression nhưng thêm artifact/version workflow và có thể làm provider bị khóa bởi consumer cũ nếu contract governance kém. Nó cũng không thay thế end-to-end test cho authentication, network policy hoặc full business flow.

**Middle → Senior insight:**
Middle developer cần phân biệt contract behavior với implementation detail và viết test theo public behavior. Senior / Technical developer phải thiết kế versioning, deprecation, consumer ownership và compatibility window để contract tests hỗ trợ evolution thay vì đóng băng API.

### Design 3 — Strangler Fig cho modernization từ legacy .NET sang modern .NET

**Khái niệm:**
Strangler Fig modernization thay thế legacy system từng phần bằng cách đưa capability mới hoặc migrated capability ra boundary mới, rồi chuyển traffic dần thay vì rewrite toàn hệ thống trong một lần.

**Vấn đề nó giải quyết:**
Big-bang rewrite có feedback loop dài và dễ bỏ sót hidden behavior của hệ thống cũ. Trong một ứng dụng .NET Framework lớn, có thể migrate từng vertical slice như authentication, reporting hoặc một nhóm API sang .NET 8/.NET 10 trong khi phần còn lại vẫn chạy ổn định.

**Ví dụ thực tế:**
```text
Reverse proxy / gateway
-> /api/orders/*      -> modern ASP.NET Core service
-> /legacy/*          -> existing .NET Framework app
```

Traffic được chuyển dần theo capability, kèm telemetry và rollback path.

**Trade-off:**
Cách này giảm migration risk và cho phép incremental delivery, nhưng tạo giai đoạn coexistence có duplicate infrastructure, integration bridge và data synchronization complexity. Boundary chọn sai có thể khiến legacy/new coupling còn phức tạp hơn trước.

**Middle → Senior insight:**
Middle developer cần giữ behavior compatibility và test migrated slice độc lập. Senior / Technical developer phải chọn migration seam theo domain boundary, dependency graph, deployment risk và data ownership; đồng thời đặt exit criteria rõ để lớp bridge tạm thời không tồn tại vĩnh viễn.
