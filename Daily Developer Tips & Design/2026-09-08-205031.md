# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `ValueTask` như `Task` mặc định chỉ vì muốn giảm allocation

**Mẹo:**
Chỉ dùng `ValueTask` khi profiling cho thấy method thường hoàn thành synchronously và allocation của `Task` thực sự đáng kể. Với đa số application code, `Task` vẫn là lựa chọn mặc định rõ ràng và an toàn hơn.

**Tại sao hữu ích:**
`ValueTask` có thể tránh allocation trong một số hot path, nhưng nó là struct lớn hơn reference `Task` và có usage contract phức tạp hơn. Một `ValueTask` nói chung không nên được await nhiều lần, cache tùy ý hoặc combine như `Task` nếu underlying source không hỗ trợ.

**Ví dụ:**
Một cache lookup thường hit memory có thể hợp lý:
```csharp
public ValueTask<Product?> GetAsync(
    string id,
    CancellationToken cancellationToken)
{
    if (_memoryCache.TryGetValue(id, out Product? product))
        return ValueTask.FromResult(product);

    return new ValueTask<Product?>(LoadAsync(id, cancellationToken));
}
```

Nếu operation gần như luôn đi database/network thì `Task<Product?>` thường đơn giản hơn mà lợi ích allocation của `ValueTask` rất nhỏ.

**Lưu ý:**
Đừng đổi hàng loạt `Task` thành `ValueTask` theo micro-optimization. Đo allocation và throughput trước; complexity ở API contract có thể lớn hơn lợi ích runtime.

### Tip 2 — Điều tra deadlock bằng deadlock graph và lock order, không chỉ tăng retry

**Mẹo:**
Khi SQL Server báo deadlock, thu deadlock graph hoặc Extended Events để xác định transaction nào giữ lock gì và đang chờ resource nào trước khi thêm retry.

**Tại sao hữu ích:**
Retry có thể che symptom nhưng không sửa lock-order inconsistency. Nếu hai transaction lock cùng các resource theo thứ tự ngược nhau, deadlock có thể lặp lại theo tải và trở nên nghiêm trọng hơn khi traffic tăng.

**Ví dụ:**
Hai flow:
```text
Transaction A: lock Order -> lock Inventory
Transaction B: lock Inventory -> lock Order
```

Khi chạy đồng thời, mỗi bên có thể giữ một lock và chờ lock còn lại. Một fix thực tế có thể là chuẩn hóa access order:
```text
Order -> Inventory
```

cho cả hai flow, hoặc rút ngắn transaction và query footprint nếu phù hợp.

**Lưu ý:**
Retry deadlock vẫn hữu ích vì deadlock là transient failure, nhưng chỉ retry mà không điều tra frequency, query plan, index và transaction scope có thể biến lỗi thiết kế thành production noise lâu dài.

### Tip 3 — Partition rate limit theo identity hoặc API key thay vì chỉ theo IP

**Mẹo:**
Với authenticated API, dùng partitioned rate limiting theo user, tenant hoặc API key khi đó mới là đơn vị tiêu thụ tài nguyên thực tế; IP chỉ nên là một signal bổ sung.

**Tại sao hữu ích:**
Nhiều user có thể đi qua cùng NAT/proxy và dùng chung IP, trong khi attacker cũng có thể phân tán request qua nhiều IP. Partition theo identity giúp policy gần với business quota và giảm false positive.

**Ví dụ:**
Trong ASP.NET Core:
```csharp
options.AddPolicy("per-user", context =>
{
    var key = context.User.Identity?.IsAuthenticated == true
        ? context.User.FindFirst("sub")?.Value ?? "unknown"
        : context.Connection.RemoteIpAddress?.ToString() ?? "anonymous";

    return RateLimitPartition.GetFixedWindowLimiter(
        key,
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1)
        });
});
```

**Lưu ý:**
Rate limiting không thay thế authorization hoặc abuse detection. Với multi-tenant SaaS, có thể cần quota theo cả tenant và user; policy quá đơn giản có thể để một user chiếm hết quota tenant.

### Tip 4 — Dùng `git worktree` khi cần làm hotfix mà không muốn stash hoặc đổi branch đang dở

**Mẹo:**
Nếu bạn đang có feature branch với nhiều thay đổi chưa commit nhưng phải sửa production hotfix ngay, dùng `git worktree` để checkout branch khác vào thư mục riêng.

**Tại sao hữu ích:**
Bạn tránh stash lớn, tránh mất context và có thể chạy hai working tree song song từ cùng repository. Điều này hữu ích khi debug release branch trong lúc feature work vẫn đang mở ở IDE khác.

**Ví dụ:**
```bash
git worktree add ../myapp-hotfix -b hotfix/payment main
cd ../myapp-hotfix
```

Sau khi merge và không cần nữa:
```bash
git worktree remove ../myapp-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree. Hãy quản lý build output, local database và environment variables riêng nếu hai instance application chạy song song.

### Tip 5 — Trong CMS, invalidation theo content dependency thường tốt hơn TTL ngắn cho mọi page

**Mẹo:**
Với Optimizely CMS hoặc CMS tương tự, nếu page cache phụ thuộc vào content cụ thể, ưu tiên invalidation khi content publish/update thay vì đặt TTL rất ngắn cho toàn bộ page chỉ để tránh stale data.

**Tại sao hữu ích:**
TTL ngắn tạo cache miss định kỳ ngay cả khi content không đổi, làm tăng rendering và downstream load. Dependency-based invalidation cho phép cache sống lâu nhưng bị xóa ngay khi source content liên quan thay đổi.

**Ví dụ:**
Một landing page dùng:
```text
Page A
  -> Hero Block 17
  -> Campaign Block 42
```

Cache entry của Page A nên biết nó phụ thuộc vào Page A, Block 17 và Block 42. Khi editor publish Block 42, cache liên quan bị invalidate thay vì chờ TTL hết hạn.

**Lưu ý:**
Personalized content, external pricing hoặc user-specific data không nên dùng cùng cache key với public content. Cache dependency chỉ đúng khi bạn xác định đầy đủ source ảnh hưởng đến output.

## 🧠 Software Design

### Design 1 — Anti-Corruption Layer khi tích hợp legacy system có model không phù hợp domain mới

**Khái niệm:**
Anti-Corruption Layer tạo một boundary dịch giữa model/protocol của external hoặc legacy system và model nội bộ. Application không để terminology, DTO hoặc rule kỳ lạ của hệ thống cũ lan trực tiếp vào domain mới.

**Vấn đề nó giải quyết:**
Legacy CRM có thể dùng status code, naming và data shape khác hoàn toàn business model hiện tại. Nếu toàn bộ code mới dùng trực tiếp legacy DTO, coupling sẽ lan rộng và migration sau này trở nên khó hơn.

**Ví dụ thực tế:**
Legacy trả:
```json
{
  "cust_no": "C102",
  "stat": "A",
  "credit_flag": "Y"
}
```

ACL map sang model nội bộ:
```text
CustomerId
CustomerStatus.Active
CreditEligibility.Allowed
```

Business layer chỉ làm việc với language của domain mới.

**Trade-off:**
ACL cô lập coupling và giúp migration dễ hơn, nhưng thêm mapping code, test và đôi khi duplicate model. Với integration nhỏ, ổn định và model gần như giống nhau, một adapter đơn giản có thể đủ.

**Middle → Senior insight:**
Middle developer cần giữ external DTO ở integration boundary và không leak nó vào domain. Senior / Technical developer phải xác định boundary nào đáng cô lập, migration path ra sao và liệu translation cost có thực sự thấp hơn coupling trực tiếp.

### Design 2 — Feature Flag tách deployment khỏi release nhưng tạo lifecycle mới phải quản lý

**Khái niệm:**
Feature Flag cho phép code được deploy trước nhưng capability chỉ bật cho một nhóm user, tenant hoặc environment khi đủ điều kiện. Deployment và business release không còn phải xảy ra cùng thời điểm.

**Vấn đề nó giải quyết:**
Một feature lớn có thể cần rollout 5% user, canary theo tenant hoặc khả năng tắt nhanh nếu metric xấu mà không rollback toàn deployment.

**Ví dụ thực tế:**
```text
Deploy version 4.8
Feature: NewCheckout = OFF
-> enable internal users
-> enable 5% production traffic
-> observe error rate / conversion / latency
-> increase gradually
```

Nếu failure rate tăng, có thể tắt flag trong vài giây trong khi version 4.8 vẫn chạy.

**Trade-off:**
Feature Flag giảm release risk nhưng thêm branch logic, test matrix, stale flag và operational dependency vào flag service/configuration. Flag tồn tại quá lâu trở thành technical debt và làm code path khó hiểu.

**Middle → Senior insight:**
Middle developer cần implement cả ON/OFF path an toàn và test đúng behavior. Senior / Technical developer phải định nghĩa owner, expiry, rollout metric, fallback behavior và cleanup policy để flag không biến thành permanent architecture.

### Design 3 — Event Sourcing chỉ hợp lý khi lịch sử thay đổi là một phần giá trị của domain

**Khái niệm:**
Event Sourcing lưu chuỗi domain events như source-of-truth và tái tạo state hiện tại bằng cách replay events, thay vì chỉ lưu snapshot state cuối cùng.

**Vấn đề nó giải quyết:**
Một số domain cần audit lịch sử đầy đủ, temporal reasoning hoặc khả năng xây projection mới từ lịch sử business event. Ví dụ ledger hoặc workflow có yêu cầu rõ về sequence thay đổi có thể hưởng lợi.

**Ví dụ thực tế:**
Thay vì chỉ lưu:
```text
AccountBalance = 1,250
```

hệ thống lưu:
```text
AccountOpened
MoneyDeposited +1000
MoneyDeposited +500
MoneyWithdrawn -250
```

Balance là projection của event history.

**Trade-off:**
Event Sourcing cung cấp history và projection flexibility nhưng tăng complexity lớn ở event schema evolution, replay, snapshotting, debugging, consistency và GDPR/data-removal concerns. CRUD business application thông thường thường không cần mức này.

**Middle → Senior insight:**
Middle developer cần hiểu event là immutable business fact và projection có thể rebuild. Senior / Technical developer phải chứng minh domain thật sự cần history-as-source-of-truth, thiết kế versioning/migration của event và cân nhắc liệu audit table hoặc change history đơn giản hơn đã đủ chưa.
