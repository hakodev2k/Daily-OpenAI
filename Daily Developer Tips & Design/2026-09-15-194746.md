# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure cho background pipeline

**Mẹo:**
Khi producer có thể tạo work nhanh hơn consumer xử lý, ưu tiên bounded `Channel<T>` thay vì `ConcurrentQueue<T>` tăng vô hạn. Capacity biến overload thành một trạng thái có thể kiểm soát thay vì âm thầm đổi thành memory pressure.

**Tại sao hữu ích:**
Queue không giới hạn có thể trông ổn khi traffic bình thường nhưng tăng hàng trăm nghìn item khi downstream chậm. Bounded channel buộc producer chờ hoặc áp dụng policy rõ ràng, nhờ đó tốc độ nhận việc phản ánh processing capacity thực tế.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, ct);
```

Một export worker có thể giới hạn tối đa 500 job đang chờ thay vì giữ toàn bộ burst trong memory.

**Lưu ý:**
Capacity 500 không phải con số mặc định tốt cho mọi hệ thống. Cần đo throughput, processing time và memory footprint; nếu producer là HTTP request, việc chờ queue cũng cần timeout/rejection policy để không chuyển overload thành request backlog.

### Tip 2 — Dùng keyset pagination khi dataset lớn và cần page ổn định

**Mẹo:**
Với API duyệt tuần tự qua tập dữ liệu lớn, cân nhắc keyset pagination (`WHERE key > lastKey`) thay vì `OFFSET` tăng dần, đặc biệt khi sort key có index phù hợp.

**Tại sao hữu ích:**
`OFFSET 100000` vẫn buộc database tìm/bỏ qua lượng lớn row trước khi trả page. Keyset cho optimizer một boundary có thể seek và thường ổn định hơn khi dữ liệu được insert/delete giữa các request.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt, Id) > (@lastCreatedAt, @lastId)
ORDER BY CreatedAt, Id
LIMIT 50;
```

`Id` làm tie-breaker để cursor có ordering deterministic khi nhiều order có cùng `CreatedAt`.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới “page 742”. Cursor phải encode đầy đủ sort boundary, và index order cần khớp query; chỉ đổi syntax mà thiếu index phù hợp không đảm bảo performance.

### Tip 3 — Cosmos DB: chọn partition key theo traffic distribution, không chỉ theo domain field

**Mẹo:**
Trước khi chọn partition key, phân tích cả cardinality lẫn read/write distribution. Một field có vẻ tự nhiên về business nhưng có thể tạo hot partition nếu phần lớn traffic dồn vào vài giá trị.

**Tại sao hữu ích:**
Cosmos DB scale phân tán dựa trên partitioning. Nếu 80% write thuộc một tenant cực lớn, partition key chỉ là `tenantId` có thể khiến workload bị giới hạn bởi một logical partition dù tổng account còn capacity.

**Ví dụ:**
```text
Candidate: tenantId
Tenant A: 75% writes
10,000 tenants còn lại: 25%

Cần đánh giá liệu workload có cần hierarchical/composite distribution
hoặc model khác thay vì mặc định tenantId là đủ.
```

**Lưu ý:**
Partition key ảnh hưởng query routing, transaction scope và data model nên rất khó đổi muộn. Đừng tối ưu distribution bằng random key nếu application thường xuyên cần query theo tenant; fan-out query có thể chuyển chi phí sang read path.

### Tip 4 — JWT: validate issuer, audience, signature và lifetime như một bộ contract

**Mẹo:**
Đừng coi token “decode được” là authenticated. Resource API phải validate cryptographic signature cùng issuer, audience và lifetime theo identity provider/configuration đáng tin cậy.

**Tại sao hữu ích:**
JWT payload chỉ là Base64Url-encoded data và client có thể tự tạo payload tùy ý. Authentication chỉ có ý nghĩa khi API chứng minh token được issuer tin cậy ký, dành cho đúng resource và còn hiệu lực.

**Ví dụ:**
```csharp
builder.Services.AddAuthentication()
    .AddJwtBearer(options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = "orders-api";
    });
```

API nên dựa vào validated claims sau authentication middleware thay vì tự parse `Authorization` header để lấy `userId`.

**Lưu ý:**
Authentication không thay thế authorization. Token hợp lệ vẫn có thể không được phép đọc order của tenant khác; đồng thời clock skew, key rotation và metadata availability phải được tính đến trong production.

### Tip 5 — Docker/Kubernetes: health check phải phản ánh đúng loại failure

**Mẹo:**
Tách readiness khỏi liveness. Readiness trả lời “instance có nhận traffic được không?”, còn liveness trả lời “process có bị kẹt đến mức cần restart không?”.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp vào database, một database outage có thể khiến toàn bộ pods restart liên tục dù restart application không giải quyết gì. Readiness có thể rút instance khỏi traffic mà không tạo restart storm.

**Ví dụ:**
```text
/readiness:
- application initialized
- critical dependency state phù hợp để phục vụ request

/liveness:
- process/event loop vẫn hoạt động
- không kiểm tra mọi external dependency
```

Khi SQL tạm unavailable, readiness có thể fail tùy service semantics trong khi liveness vẫn pass.

**Lưu ý:**
Health endpoint quá nặng cũng trở thành workload riêng. Không chạy query lớn hoặc gọi hàng loạt third-party API mỗi vài giây; probe timeout/failure threshold phải phù hợp startup và transient-failure characteristics.

## 🧠 Software Design

### Design 1 — Transactional Outbox nối database transaction với message publishing

**Khái niệm:**
Transactional Outbox ghi business state và message/event cần publish vào cùng local database transaction. Một publisher riêng đọc outbox rồi gửi message tới broker, thay vì cố commit database và broker như hai thao tác độc lập.

**Vấn đề nó giải quyết:**
Order được commit vào SQL nhưng process crash trước khi publish `OrderCreated`; hoặc message được publish trước rồi database transaction rollback. Hai resource không có atomic commit mặc định nên dual-write tạo trạng thái lệch.

**Ví dụ thực tế:**
```text
SQL transaction:
1. INSERT Orders(...)
2. INSERT Outbox(Id, Type, Payload, OccurredAt)
3. COMMIT

Publisher:
Outbox -> Azure Service Bus -> mark published
```

Nếu publisher crash sau khi gửi nhưng trước khi mark, message có thể được gửi lại nên consumer vẫn cần idempotency.

**Trade-off:**
Outbox loại bỏ khoảng trống “database committed nhưng event bị mất” nhưng thêm table growth, polling/publishing process, duplicate delivery và operational monitoring. Nó không tạo exactly-once end-to-end semantics.

**Middle → Senior insight:**
Middle developer cần giữ business write và outbox insert trong cùng transaction, đồng thời xử lý duplicate. Senior / Technical developer phải quyết định event boundary, retention, ordering, publisher scaling, failure recovery và liệu consistency requirement có thực sự cần Outbox thay vì một integration đơn giản hơn.

### Design 2 — Data ownership quan trọng hơn việc service có database riêng về mặt vật lý

**Khái niệm:**
Data ownership nghĩa là một module/service chịu trách nhiệm authoritative cho dữ liệu và các invariant của nó; consumer khác truy cập qua contract được phép thay vì tự sửa bảng của owner. Database vật lý riêng chỉ là một cách enforce boundary.

**Vấn đề nó giải quyết:**
Trong enterprise monolith hoặc giai đoạn migration, nhiều module cùng truy cập trực tiếp bảng của nhau khiến schema trở thành public API ngầm. Một thay đổi column nhỏ có thể phá nhiều consumer và business rule bị bypass bởi direct update.

**Ví dụ thực tế:**
```text
Finance owns Invoice.
Tasks cần trạng thái invoice:
- gọi module contract/read model được công bố
- không UPDATE Finance.Invoices trực tiếp
```

Trong Modular Monolith, hai module có thể tạm dùng cùng SQL Server nhưng schema/API ownership vẫn được enforce ở code và tests.

**Trade-off:**
Ownership rõ giảm coupling và giúp extraction sau này, nhưng strict boundary có thể thêm mapping, duplicated read model và eventual consistency. Tách database quá sớm cũng làm transaction/query đơn giản trở thành distributed problem.

**Middle → Senior insight:**
Middle developer cần tôn trọng write boundary và không bypass contract vì tiện. Senior / Solution-oriented engineer phải cân bằng invariant ownership, reporting/query needs, transaction boundary và migration cost; không đồng nhất “microservice tốt” với “mỗi service bắt buộc một server database ngay lập tức”.

### Design 3 — SLO biến observability thành quyết định reliability có đo lường

**Khái niệm:**
Service Level Objective (SLO) đặt mục tiêu đo được cho reliability mà người dùng quan tâm, chẳng hạn tỷ lệ request thành công hoặc latency trong một cửa sổ thời gian. Observability sau đó được thiết kế để đo và điều tra những mục tiêu đó thay vì chỉ thu thập càng nhiều metric càng tốt.

**Vấn đề nó giải quyết:**
Một team có hàng chục dashboard CPU, memory và request count nhưng vẫn không trả lời được “checkout có đang đủ reliable không?”. Infrastructure metric là evidence hữu ích nhưng không trực tiếp mô tả user-visible reliability.

**Ví dụ thực tế:**
```text
Checkout API SLO, 30 ngày:
- 99.9% request hợp lệ không trả 5xx
- 99% request hoàn thành < 800 ms

Alert ưu tiên burn rate của error budget,
sau đó trace/log/dependency metrics phục vụ diagnosis.
```

**Trade-off:**
SLO tạo ngôn ngữ chung cho reliability và release risk nhưng cần metric semantics chính xác. Objective quá nghiêm tạo alert fatigue/cost; quá lỏng che degradation. Không phải mọi endpoint đều cần cùng target.

**Middle → Senior insight:**
Middle developer cần instrument request/dependency đúng và hiểu correlation giữa metrics, traces, logs. Senior / Technical developer phải chọn SLI/SLO theo user journey, error budget và business impact, rồi dùng chúng để cân bằng feature velocity với reliability investment thay vì tối ưu dashboard theo cảm tính.
