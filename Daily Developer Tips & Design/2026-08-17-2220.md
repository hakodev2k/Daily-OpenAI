# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationTokenSource.CancelAfter` cho timeout cục bộ thay vì tự `Task.Delay` race

**Mẹo:**
Khi một operation cần timeout riêng ngoài cancellation token từ caller, tạo linked `CancellationTokenSource` rồi dùng `CancelAfter()` thay vì tự viết `Task.WhenAny(operation, Task.Delay(...))` ở mọi nơi.

**Tại sao hữu ích:**
Giữ cancellation semantics nhất quán, truyền timeout xuống toàn bộ I/O con và tránh để operation thật tiếp tục chạy âm thầm sau khi caller đã trả timeout.

**Ví dụ:**
```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(
    cancellationToken);

cts.CancelAfter(TimeSpan.FromSeconds(5));

var result = await client.FetchAsync(cts.Token);
```

**Lưu ý:**
Timeout chỉ hiệu quả nếu dependency thực sự tôn trọng `CancellationToken`. Nếu library bỏ qua token, operation bên dưới vẫn có thể tiếp tục chạy và giữ resource.

### Tip 2 — Dùng `AddPooledDbContextFactory` khi background worker cần nhiều `DbContext` ngắn hạn

**Mẹo:**
Với background service hoặc parallel worker không có HTTP request scope tự nhiên, cân nhắc `AddPooledDbContextFactory<TContext>()` để tạo `DbContext` ngắn hạn theo từng unit of work.

**Tại sao hữu ích:**
Tránh share một `DbContext` qua nhiều task, giảm lỗi concurrency và giảm một phần chi phí khởi tạo context nhờ pooling.

**Ví dụ:**
```csharp
await using var dbContext =
    await dbContextFactory.CreateDbContextAsync(cancellationToken);

var jobs = await dbContext.Jobs
    .Where(x => x.Status == JobStatus.Pending)
    .Take(100)
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Pooled context được tái sử dụng nên state custom gắn trên instance phải được reset đúng. Không giữ context lâu hoặc lưu per-request state tùy ý trong `DbContext`.

### Tip 3 — Dùng `READPAST` có chọn lọc cho worker queue trên SQL Server

**Mẹo:**
Khi nhiều worker lấy job độc lập từ cùng bảng queue, `READPAST` có thể giúp một worker bỏ qua row đang bị lock thay vì chờ nó.

**Tại sao hữu ích:**
Giảm lock contention và giúp worker tiếp tục xử lý job khác khi một row đang được worker khác claim.

**Ví dụ:**
```sql
SELECT TOP (1) *
FROM JobQueue WITH (UPDLOCK, READPAST, ROWLOCK)
WHERE Status = 'Pending'
ORDER BY CreatedAt;
```

Sau đó update trạng thái job trong cùng transaction.

**Lưu ý:**
`READPAST` thay đổi semantics đọc và có thể làm một row bị bỏ qua tạm thời nhiều lần. Cần thiết kế retry, ordering và starvation rõ ràng; không dùng cho query nghiệp vụ thông thường chỉ để “né lock”.

### Tip 4 — Dùng `git ls-files -v` để phát hiện file đang bị `assume-unchanged` hoặc `skip-worktree`

**Mẹo:**
Nếu Git không báo thay đổi trên một file tracked dù bạn chắc chắn file đã sửa, kiểm tra index flags bằng `git ls-files -v`.

**Tại sao hữu ích:**
Giúp tìm nhanh các file từng bị đánh dấu local bằng `assume-unchanged` hoặc `skip-worktree`, vốn rất dễ gây cảm giác “Git bị lỗi”.

**Ví dụ:**
```bash
git ls-files -v | grep '^[a-zS]'
```

Sau khi xác định file, có thể bỏ flag tương ứng:

```bash
git update-index --no-assume-unchanged path/to/file
```

**Lưu ý:**
Các flag index này không nên thay thế configuration strategy đúng. Chúng dễ bị quên và khiến developer bỏ lỡ thay đổi quan trọng từ repository.

### Tip 5 — Dùng `pidstat` để xem CPU/I/O theo process theo thời gian

**Mẹo:**
Khi Linux service lúc nhanh lúc chậm, dùng `pidstat` để quan sát CPU, context switch hoặc I/O theo từng khoảng thời gian thay vì chỉ chụp một snapshot bằng `ps` hoặc `top`.

**Tại sao hữu ích:**
Giúp phát hiện spike theo chu kỳ, CPU saturation cục bộ hoặc process đang chờ I/O mà snapshot ngắn dễ bỏ sót.

**Ví dụ:**
```bash
pidstat -p <PID> 1
```

Theo dõi I/O:

```bash
pidstat -d -p <PID> 1
```

**Lưu ý:**
`pidstat` chỉ cho tín hiệu hệ điều hành. Để tìm root cause trong .NET, vẫn cần correlate với `dotnet-counters`, trace, log, database metrics hoặc profiler.

## 🧠 Software Design

### Design 1 — Concurrency Limit khác Rate Limit

**Khái niệm:**
Rate Limit giới hạn số request trong một khoảng thời gian; Concurrency Limit giới hạn số request đắt đang chạy đồng thời tại một thời điểm.

**Vấn đề nó giải quyết:**
Một endpoint có thể chỉ nhận 20 request/second nhưng mỗi request giữ DB connection 10 giây. Rate limit vẫn cho phép hàng trăm request chồng lên nhau và làm cạn connection pool.

**Ví dụ thực tế:**
Endpoint export có thể cho tối đa 5 request chạy đồng thời dù tenant vẫn được phép 100 request/phút ở các endpoint nhẹ khác. Request thứ 6 chờ, bị reject hoặc chuyển thành background job.

**Trade-off:**
Concurrency limit bảo vệ resource tức thời tốt hơn nhưng có thể tăng queueing latency và cần chọn policy khi đầy. Rate limit kiểm soát fairness/abuse theo thời gian nhưng không phản ánh cost của request đang chạy.

**Middle → Senior insight:**
Middle developer nên hiểu rate limit không phải circuit breaker cho capacity. Senior developer phải xác định bottleneck thật như thread, DB connection, CPU hoặc downstream quota và kết hợp rate, concurrency, queueing, timeout theo SLO.

### Design 2 — Event-Carried State Transfer khác Event Notification

**Khái niệm:**
Event Notification chỉ báo “đã có thay đổi” và consumer phải gọi lại owner để lấy dữ liệu mới; Event-Carried State Transfer mang luôn phần state consumer cần trong event.

**Vấn đề nó giải quyết:**
Notification event đơn giản nhưng dễ tạo callback storm và coupling runtime. State-carrying event giảm read-back nhưng tăng payload, duplication và trách nhiệm versioning.

**Ví dụ thực tế:**
`EmployeeChanged { EmployeeId }` buộc Payroll gọi Employee service sau mỗi event. Một event giàu hơn như `EmployeeEmploymentChanged { EmployeeId, Status, EffectiveDate, Version }` có thể đủ để Payroll cập nhật read model mà không gọi ngược.

**Trade-off:**
State transfer giảm synchronous dependency và latency fan-out nhưng dữ liệu duplicate có thể stale và contract lớn hơn. Notification giữ source-of-truth tập trung nhưng làm consumer phụ thuộc availability của owner tại thời điểm xử lý.

**Middle → Senior insight:**
Middle developer nên hiểu event payload quyết định coupling runtime. Senior developer cần cân bằng freshness, payload size, consumer autonomy, schema evolution và quyền sở hữu dữ liệu thay vì mặc định event càng nhỏ càng tốt.

### Design 3 — Tách Control Plane và Data Plane để blast radius nhỏ hơn

**Khái niệm:**
Control Plane quản lý cấu hình, policy, metadata và orchestration; Data Plane xử lý traffic hoặc workload chính. Hai plane có failure profile và scaling pattern khác nhau.

**Vấn đề nó giải quyết:**
Nếu cùng một component vừa phục vụ request user-facing vừa xử lý cấu hình/admin nặng, lỗi hoặc overload ở control path có thể kéo sập traffic production.

**Ví dụ thực tế:**
Một API gateway có Data Plane xử lý request tốc độ cao; Control Plane nhận route config, certificate và policy update. Nếu control service tạm mất, data plane vẫn tiếp tục chạy với config cuối cùng hợp lệ.

**Trade-off:**
Tách plane tăng resilience và scale độc lập nhưng thêm replication config, versioning, rollout và operational complexity. Với hệ thống nhỏ, tách vật lý quá sớm có thể không đáng.

**Middle → Senior insight:**
Middle developer nên phân biệt đường xử lý traffic với đường quản trị. Senior developer phải thiết kế cache/config snapshot, update propagation, rollback và behavior khi control plane unavailable để data plane tiếp tục phục vụ an toàn.
