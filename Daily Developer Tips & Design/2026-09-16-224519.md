# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `Task.Run` để “làm async” I/O trong ASP.NET Core

**Mẹo:**
Với database, HTTP, file hoặc network API đã có asynchronous API, `await` trực tiếp operation đó; không bọc nó trong `Task.Run`.

**Tại sao hữu ích:**
I/O async không cần giữ một ThreadPool thread trong lúc chờ kernel/network hoàn tất. `Task.Run` lại đưa delegate lên ThreadPool, thêm scheduling overhead mà không biến synchronous I/O thành scalable I/O. Dưới tải cao, kiểu bọc này còn góp phần gây ThreadPool starvation.

**Ví dụ:**
```csharp
// Không cần:
var users = await Task.Run(() => db.Users.ToList());

// Đúng cho I/O async:
var users = await db.Users
    .AsNoTracking()
    .ToListAsync(cancellationToken);
```
Nếu API chậm sau deployment, kiểm tra request rate, ThreadPool queue, blocking calls và dependency latency trước khi tăng thread count.

**Lưu ý:**
`Task.Run` vẫn hữu ích cho một số CPU-bound work cần đẩy khỏi caller context, nhưng ASP.NET Core server không tự có thêm CPU vì bạn tạo task. CPU-heavy workload lớn nên được giới hạn concurrency hoặc tách khỏi request path.

### Tip 2 — EF Core projection nên cắt object graph ngay tại SQL boundary

**Mẹo:**
Với read endpoint, project trực tiếp sang response/read model bằng `Select` thay vì `Include` toàn aggregate rồi map trong memory.

**Tại sao hữu ích:**
Projection cho EF Core cơ hội chỉ SELECT các cột và expression thực sự cần. Nó giảm materialization, change-tracking pressure, network payload và nguy cơ vô tình load collection lớn. Đây thường là tối ưu có giá trị hơn các micro-optimization phía C#.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Where(x => x.Id == orderId)
    .Select(x => new OrderDetailsDto(
        x.Id,
        x.Customer.Name,
        x.Items.Count,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .SingleAsync(cancellationToken);
```
Hãy inspect generated SQL và execution plan nếu projection chứa expression phức tạp hoặc aggregate lớn.

**Lưu ý:**
Đừng ép mọi business operation thành projection. Command cần thay đổi aggregate và enforce invariants thường vẫn cần entity state phù hợp; read optimization và write model có mục tiêu khác nhau.

### Tip 3 — Elasticsearch analyzer của lúc index phải khớp search semantics

**Mẹo:**
Thiết kế analyzer/tokenization dựa trên kiểu tìm kiếm thực tế trước khi ingest lượng dữ liệu lớn; đừng coi mapping text là chi tiết có thể sửa rẻ sau này.

**Tại sao hữu ích:**
Elasticsearch xây inverted index từ tokens tại index time. Nếu product name được tokenize/lowercase/stem theo cách không phù hợp với search semantics, đổi query code sau đó không thể tái tạo tokens đã không được index. Nhiều thay đổi analyzer cần index mới và reindex dữ liệu.

**Ví dụ:**
```text
Requirement:
- full-text: "wireless headphones"
- exact filter/sort: SKU, brand

Mapping idea:
name        -> text + analyzer phù hợp
name.keyword -> keyword nếu cần exact operation
sku         -> keyword
brand       -> keyword
```
Dùng `_analyze` và representative queries để kiểm tra tokens trước khi chốt mapping.

**Lưu ý:**
Không thêm `.keyword` hoặc multi-field cho mọi field theo thói quen; chúng tăng index size. Search relevance cần test bằng dữ liệu/domain thật, không chỉ vài sample dễ đoán.

### Tip 4 — Đừng log exception thành string rồi làm mất structured telemetry

**Mẹo:**
Truyền `Exception` vào logging API và dùng message template có named properties thay vì nối chuỗi hoặc chỉ log `ex.Message`.

**Tại sao hữu ích:**
Structured logging giữ exception type, stack trace và properties thành dữ liệu truy vấn được. Khi production lỗi tăng sau release, bạn có thể group theo exception, endpoint, dependency hoặc operation thay vì grep chuỗi text không ổn định.

**Ví dụ:**
```csharp
try
{
    await paymentClient.ChargeAsync(order.Id, cancellationToken);
}
catch (Exception ex)
{
    logger.LogError(
        ex,
        "Payment charge failed for OrderId {OrderId}",
        order.Id);
    throw;
}
```
Kết hợp trace context để liên kết log với request/dependency spans trong Application Insights hoặc OpenTelemetry backend.

**Lưu ý:**
Structured không có nghĩa là log mọi object. Không đưa access token, password, payment data hoặc payload chứa PII vào properties; cardinality và data-governance vẫn cần kiểm soát.

### Tip 5 — Dùng Network waterfall để tách frontend chậm khỏi backend chậm

**Mẹo:**
Khi người dùng báo trang chậm, bắt đầu bằng browser DevTools Network/Performance để xác định thời gian nằm ở TTFB, download, JavaScript execution hay render thay vì tối ưu ngẫu nhiên backend.

**Tại sao hữu ích:**
Một page load 4 giây có thể do API TTFB 2.5 giây, bundle JavaScript 3 MB, request waterfall tuần tự hoặc ảnh blocking LCP. Mỗi nguyên nhân cần một fix khác nhau; metric tổng “page slow” không đủ để chẩn đoán.

**Ví dụ:**
```text
Document TTFB:       180 ms
API /products:       240 ms
JS bundle download:  900 ms
Main-thread execute: 1.6 s
LCP:                 3.2 s
```
Evidence này hướng investigation về bundle/execution thay vì scale ASP.NET Core API vốn đang đáp ứng nhanh.

**Lưu ý:**
Một lần đo trên máy developer không đại diện production. Kiểm tra throttling, cache state, geography và Real User Monitoring/Core Web Vitals nếu cần đánh giá user experience thực tế.

## 🧠 Software Design

### Design 1 — REST vs Messaging cho integration boundary

**Khái niệm:**
REST phù hợp khi caller cần một response trực tiếp trong request flow; messaging phù hợp khi producer có thể giao work/event bất đồng bộ và chấp nhận temporal decoupling. Đây là lựa chọn về interaction semantics, không phải cuộc thi công nghệ.

**Vấn đề nó giải quyết:**
Checkout cần biết ngay inventory có cho phép order hay không, nhưng analytics không cần block checkout chỉ để ghi nhận `OrderPlaced`. Dùng synchronous call cho mọi integration tạo dependency chain; dùng messaging cho mọi thứ lại làm workflow đơn giản trở nên eventual và khó debug.

**Ví dụ thực tế:**
Checkout gọi Pricing synchronously vì kết quả quyết định response hiện tại. Sau khi order commit, `OrderPlaced` được publish để Email và Analytics xử lý độc lập. Nếu Email down, checkout không nhất thiết phải thất bại.

**Trade-off:**
REST đơn giản về mental model và consistency tức thời hơn nhưng tăng runtime coupling và cascading-failure risk. Messaging tăng resilience/fan-out và temporal decoupling nhưng thêm broker, duplicate delivery, ordering, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần implement timeout, cancellation, retry/idempotency đúng theo protocol. Senior / Technical developer phải phân loại interaction là query, command hay event; đánh giá latency budget, consistency, ownership và failure semantics trước khi chọn synchronous hay asynchronous boundary.

### Design 2 — Database normalization vs read-performance denormalization

**Khái niệm:**
Normalization giảm duplication và update anomalies trong source-of-truth model. Denormalization cố ý lưu hoặc materialize dữ liệu dư thừa để phục vụ read pattern cụ thể nhanh hơn. Hai hướng tối ưu cho các áp lực khác nhau.

**Vấn đề nó giải quyết:**
Một reporting/dashboard query phải join nhiều bảng và aggregate hàng triệu rows ở mỗi request. Giữ transactional model sạch là đúng cho writes, nhưng bắt mọi read workload chạy trực tiếp trên model đó có thể tạo latency và database pressure không cần thiết.

**Ví dụ thực tế:**
Order database giữ `CustomerId` và normalized customer data. Dashboard có projection/materialized read model chứa `CustomerDisplayName`, daily totals và status counts được cập nhật theo workflow phù hợp, thay vì duplicate các field đó ngẫu nhiên vào mọi transactional table.

**Trade-off:**
Normalization giữ consistency và write logic đơn giản hơn nhưng một số reads cần join/compute đắt. Denormalization tăng read speed nhưng tạo synchronization, stale-data, rebuild và ownership cost. Duplicate data không miễn phí.

**Middle → Senior insight:**
Middle developer cần thiết kế keys/constraints và query/index đúng trước khi denormalize. Senior / Technical developer phải chứng minh bottleneck bằng workload thực tế, xác định acceptable staleness và chọn projection, materialized view, cache hay schema denormalization với recovery strategy rõ ràng.

### Design 3 — Feature Flags không thay thế deployment strategy

**Khái niệm:**
Feature Flag tách thời điểm deploy code khỏi thời điểm bật behavior. Nó cho phép rollout theo user/cohort và kill-switch nhanh, nhưng code mới vẫn phải deploy an toàn trước khi flag được sử dụng.

**Vấn đề nó giải quyết:**
Một checkout algorithm mới cần thử trên 5% traffic và rollback behavior nhanh nếu conversion/error rate xấu, trong khi binary đã được deploy lên toàn bộ instances.

**Ví dụ thực tế:**
Cả old/new pricing path được deploy backward-compatible. Flag service chọn 5% users vào new path; metrics so sánh error/latency/business outcome. Khi lỗi, flag chuyển traffic về old path mà không cần emergency redeploy.

**Trade-off:**
Flags giảm release risk và cho progressive delivery, nhưng tạo branching logic, test matrix, configuration dependency và technical debt nếu flag không được xóa. Một flag sai hoặc unavailable cũng có thể trở thành production failure mode.

**Middle → Senior insight:**
Middle developer cần code default/fallback rõ ràng và test cả hai trạng thái. Senior / Technical developer phải thiết kế flag ownership, rollout metrics, fail-open/fail-closed semantics, lifecycle/cleanup và phối hợp với blue/green hoặc rolling deployment; feature flag không cứu được breaking database migration hay binary không khởi động.
