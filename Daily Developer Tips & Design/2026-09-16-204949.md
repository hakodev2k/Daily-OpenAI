# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng giữ `DbContext` qua nhiều message trong `BackgroundService`

**Mẹo:**
Trong long-running worker, tạo DI scope riêng cho từng message hoặc một transaction unit rõ ràng; không inject rồi giữ một scoped `DbContext` cho toàn vòng đời worker.

**Tại sao hữu ích:**
`DbContext` giữ change tracker và không thread-safe. Nếu sống quá lâu, tracked entities tích lũy, memory tăng, state cũ có thể ảnh hưởng xử lý sau và concurrent handlers dễ dùng chung context sai cách. Scope-per-message làm lifetime khớp transaction boundary hơn.

**Ví dụ:**
```csharp
public sealed class OrderWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var message in ReadMessagesAsync(stoppingToken))
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var handler = scope.ServiceProvider.GetRequiredService<OrderHandler>();
            await handler.HandleAsync(message, stoppingToken);
        }
    }
}
```

**Lưu ý:**
Scope-per-message không tự giải quyết duplicate delivery hay transaction với broker. Nếu chạy handlers song song, mỗi handler vẫn cần scope riêng và concurrency phải được giới hạn có chủ đích.

### Tip 2 — Đo connection-pool exhaustion từ dependency latency, không chỉ nhìn SQL CPU

**Mẹo:**
Khi API đột nhiên chậm nhưng SQL Server CPU bình thường, kiểm tra thời gian chờ lấy connection và số connection đang giữ trước khi kết luận database thiếu compute.

**Tại sao hữu ích:**
ADO.NET connection pooling có giới hạn. Query chậm, transaction mở lâu hoặc code giữ connection trong lúc gọi external API có thể làm pool cạn. Request mới sau đó chờ connection, khiến latency tăng dây chuyền dù database chưa quá tải.

**Ví dụ:**
```text
Symptom: p95 API 180 ms -> 8 s
SQL CPU: 35%
Active DB calls: không tăng tương ứng
Timeout: "Timeout expired prior to obtaining a connection from the pool"

Hypothesis -> connection lifetime quá dài
Check -> transaction duration, slow query, leaked reader/connection, pool metrics
```

**Lưu ý:**
Tăng `Max Pool Size` chỉ tăng khoảng đệm và có thể đẩy overload xuống database. Tìm nguyên nhân connection bị giữ lâu trước khi thay pool configuration.

### Tip 3 — Dùng `AbortController` để hủy request frontend đã lỗi thời

**Mẹo:**
Trong Vue.js/React.js search UI, hủy `fetch` cũ khi query mới xuất hiện thay vì để nhiều request cạnh tranh cập nhật cùng state.

**Tại sao hữu ích:**
Response không đảm bảo về đúng thứ tự gửi. Request cho `lap` có thể hoàn thành sau request cho `laptop`, khiến UI hiển thị dữ liệu cũ. Cancellation giảm network work và loại một lớp race condition phía client.

**Ví dụ:**
```typescript
let controller: AbortController | undefined;

async function search(term: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  });

  return response.json();
}
```

**Lưu ý:**
Client abort không đảm bảo server đã dừng business operation. Backend vẫn phải propagate cancellation khi phù hợp và command có side effect vẫn cần idempotency/consistency riêng.

### Tip 4 — Phân biệt Kubernetes readiness với liveness để tránh restart làm outage nặng hơn

**Mẹo:**
Dùng readiness để quyết định Pod có nhận traffic hay không; chỉ dùng liveness cho trạng thái process thực sự không thể tự phục hồi.

**Tại sao hữu ích:**
Nếu liveness probe phụ thuộc database hoặc external API, outage downstream có thể khiến Kubernetes restart toàn bộ Pods. Restart không sửa dependency nhưng làm mất warm state, tăng reconnect traffic và có thể biến partial failure thành cascading failure.

**Ví dụ:**
```text
/readiness -> app initialized, có khả năng phục vụ request
/liveness  -> process/event loop còn hoạt động

Database tạm unavailable:
readiness có thể fail theo service semantics
liveness không nên mặc định fail chỉ vì database fail
```

**Lưu ý:**
Health-check policy phụ thuộc workload. Một service hoàn toàn vô dụng khi mất dependency có thể cần readiness phản ánh điều đó, nhưng đừng biến mọi dependency check thành liveness check.

### Tip 5 — Khi AI sinh migration, kiểm tra generated SQL chứ đừng chỉ review C# migration

**Mẹo:**
Nếu dùng AI coding agent để tạo EF Core migration, review cả migration source lẫn SQL sẽ chạy trên production schema/data volume.

**Tại sao hữu ích:**
Code migration trông hợp lý vẫn có thể tạo table rewrite, lock lâu, destructive column change hoặc index build gây blocking. AI thường không biết data distribution, deployment topology và compatibility window thực tế của hệ thống.

**Ví dụ:**
```bash
dotnet ef migrations script PreviousMigration NewMigration --idempotent
```
Review script để tìm `DROP COLUMN`, data conversion, default constraint trên bảng lớn, index creation và operations cần expand/contract deployment.

**Lưu ý:**
Generated SQL trên staging dataset nhỏ không đại diện production. Với bảng lớn, cần estimate lock duration, transaction-log growth và rollback/recovery trước release.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency vs Pessimistic Concurrency

**Khái niệm:**
Optimistic concurrency cho phép nhiều actors đọc cùng state rồi phát hiện conflict khi ghi; pessimistic concurrency giữ lock sớm để ngăn actor khác thay đổi state trong critical section.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng sửa một order từ version 7. Nếu cả hai update mà không phát hiện conflict, người ghi sau có thể âm thầm ghi đè thay đổi trước. Ngược lại, giữ database lock xuyên một user interaction dài sẽ làm throughput và availability xấu đi.

**Ví dụ thực tế:**
EF Core dùng `rowversion`/concurrency token cho back-office edit: `UPDATE ... WHERE Id=@id AND Version=@originalVersion`; zero affected rows nghĩa là state đã đổi và application quyết định reload, merge hoặc báo conflict. Pessimistic lock phù hợp hơn với critical section ngắn nơi conflict rất đắt và transaction có thể hoàn tất nhanh.

**Trade-off:**
Optimistic concurrency giữ lock ngắn và scale tốt khi conflict hiếm nhưng đẩy conflict resolution lên application. Pessimistic concurrency giảm concurrent conflicts trong critical section nhưng tăng blocking, deadlock risk và phụ thuộc transaction duration.

**Middle → Senior insight:**
Middle developer cần implement concurrency token và xử lý conflict thay vì catch rồi retry mù quáng. Senior / Technical developer phải đánh giá conflict frequency, business semantics, lock duration và user experience để chọn chiến lược; không có lựa chọn mặc định đúng cho mọi aggregate.

### Design 2 — Queue vs Topic trong Azure Service Bus

**Khái niệm:**
Queue biểu diễn một stream công việc mà mỗi message thường được một consumer cạnh tranh xử lý. Topic + subscriptions biểu diễn publish/subscribe: một event có thể được fan-out thành nhiều subscription độc lập.

**Vấn đề nó giải quyết:**
`InvoiceRequested` là command cho một capability cụ thể khác với `OrderCompleted` là event mà Billing, Analytics và Notification đều có thể quan tâm. Dùng một queue cho fan-out khiến consumers tranh mất message; dùng topic cho command đơn lẻ có thể tạo topology phức tạp không cần thiết.

**Ví dụ thực tế:**
`generate-invoice` queue có nhiều Billing workers competing consumers. `order-events` topic có subscriptions `analytics`, `email` và `loyalty`, mỗi subscription có retry/DLQ riêng và nhận bản sao logic của event phù hợp filter.

**Trade-off:**
Queue đơn giản hơn cho work distribution và ownership rõ. Topic giảm coupling giữa publisher và nhiều consumers nhưng tăng subscription lifecycle, schema evolution, duplicate handling, monitoring và chi phí vận hành.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumers, retries, DLQ và idempotency. Senior / Technical developer phải phân biệt command/event semantics, ownership, fan-out growth và failure isolation trước khi thiết kế topology; broker topology nên phản ánh business communication chứ không chỉ tiện code.

### Design 3 — Expand/Contract cho database schema evolution

**Khái niệm:**
Expand/Contract thay breaking schema change thành nhiều bước backward-compatible: mở rộng schema trước, chuyển application/data dần, rồi mới loại bỏ cấu trúc cũ khi không còn consumer sử dụng.

**Vấn đề nó giải quyết:**
Trong rolling deployment, version cũ và mới của application có thể chạy đồng thời. Rename/drop column trực tiếp khiến một version hoạt động còn version kia lỗi, biến database migration thành deployment coupling cứng.

**Ví dụ thực tế:**
Cần đổi `CustomerName` thành `DisplayName`: release 1 thêm `DisplayName` và code tương thích hai fields; backfill dữ liệu; release 2 chuyển reads/writes hoàn toàn sang field mới; sau khi telemetry xác nhận không còn consumer cũ, release sau mới drop `CustomerName`.

**Trade-off:**
Cách này giảm downtime và rollback risk nhưng cần nhiều releases, temporary duplication, backfill, telemetry và cleanup discipline. Với hệ thống nhỏ có maintenance window chấp nhận được, migration trực tiếp có thể đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible và tránh giả định deployment atomic. Senior / Technical developer phải thiết kế compatibility window, sequencing giữa app/schema/data, rollback direction và cách chứng minh old contract đã hết usage trước bước contract.
