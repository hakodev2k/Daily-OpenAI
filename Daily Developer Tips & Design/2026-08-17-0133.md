# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwait(false)` có chọn lọc trong library code

**Mẹo:**
Trong application code hiện đại như ASP.NET Core, thường không cần `ConfigureAwait(false)`. Nhưng trong reusable library code, nó vẫn hữu ích để tránh phụ thuộc không cần thiết vào `SynchronizationContext` của caller.

**Tại sao hữu ích:**
Giúp library ít bị ràng buộc với UI context hoặc môi trường đặc thù, đồng thời giảm nguy cơ deadlock trong một số host cũ.

**Ví dụ:**
```csharp
public async Task<string> LoadAsync(CancellationToken cancellationToken)
{
    var response = await _httpClient
        .GetAsync("api/data", cancellationToken)
        .ConfigureAwait(false);

    return await response.Content
        .ReadAsStringAsync(cancellationToken)
        .ConfigureAwait(false);
}
```

**Lưu ý:**
Không thêm `ConfigureAwait(false)` máy móc vào mọi nơi. Với ASP.NET Core application code, lợi ích thường rất nhỏ vì không có classic `SynchronizationContext` như ASP.NET cũ hoặc WinForms/WPF.

### Tip 2 — Dùng `EXPLAIN ANALYZE` để kiểm tra query PostgreSQL thực sự chạy thế nào

**Mẹo:**
Khi query PostgreSQL chậm, dùng `EXPLAIN (ANALYZE, BUFFERS)` để xem actual execution time, row estimates và buffer usage thay vì chỉ đo tổng thời gian từ application.

**Tại sao hữu ích:**
Bạn có thể phát hiện sequential scan, estimate sai, nested loop tốn kém, sort spill hoặc index không được sử dụng như kỳ vọng.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, customer_id, created_at
FROM orders
WHERE customer_id = 12345
ORDER BY created_at DESC
LIMIT 50;
```

Hãy chú ý các điểm như:

```text
actual rows
estimated rows
shared hit
shared read
Sort Method
```

**Lưu ý:**
`ANALYZE` thực thi query thật. Với `UPDATE`, `DELETE` hoặc query nặng trên production, cần đặc biệt cẩn trọng và thường nên dùng môi trường an toàn trước.

### Tip 3 — Dùng `HttpClientFactory` nhưng vẫn phải thiết kế timeout theo từng loại request

**Mẹo:**
`IHttpClientFactory` giải quyết nhiều vấn đề lifecycle và connection pooling, nhưng không có nghĩa một timeout chung phù hợp cho mọi outbound request.

**Tại sao hữu ích:**
API lookup 500 ms và export file 30 giây là hai workload khác nhau. Timeout đúng giúp hệ thống fail fast ở request ngắn nhưng không làm hỏng operation dài hợp lệ.

**Ví dụ:**
```csharp
services.AddHttpClient("UserProfile", client =>
{
    client.BaseAddress = new Uri("https://profile.internal/");
    client.Timeout = TimeSpan.FromSeconds(3);
});

services.AddHttpClient("ReportExport", client =>
{
    client.BaseAddress = new Uri("https://report.internal/");
    client.Timeout = TimeSpan.FromSeconds(60);
});
```

**Lưu ý:**
Không chỉ tăng timeout khi thấy timeout exception. Nếu downstream bị chậm, timeout dài hơn có thể làm connection và request tích tụ, khiến sự cố lan rộng.

### Tip 4 — Dùng `git reflog` để cứu commit tưởng như đã mất

**Mẹo:**
Khi lỡ `reset --hard`, rebase sai hoặc checkout làm mất reference tới commit, kiểm tra `git reflog` trước khi nghĩ rằng code đã mất.

**Tại sao hữu ích:**
Git thường vẫn giữ object của commit trong một khoảng thời gian dù branch pointer đã thay đổi.

**Ví dụ:**
```bash
git reflog
```

Bạn có thể thấy:

```text
91ab12c HEAD@{0}: reset: moving to HEAD~3
44fe291 HEAD@{1}: commit: Fix payment retry
```

Khôi phục bằng:

```bash
git checkout 44fe291
git switch -c recover-payment-fix
```

**Lưu ý:**
`reflog` là local metadata và không tồn tại mãi mãi. Đừng coi nó là backup strategy thay cho remote repository hoặc backup thực sự.

### Tip 5 — Đo allocation khi tối ưu .NET, đừng chỉ nhìn CPU time

**Mẹo:**
Khi tối ưu code hot path, xem cả allocation rate và GC pressure bằng `dotnet-counters`, profiler hoặc BenchmarkDotNet.

**Tại sao hữu ích:**
Một đoạn code có vẻ nhanh ở từng call nhưng tạo rất nhiều object ngắn hạn có thể gây Gen 0/Gen 1 GC liên tục và giảm throughput đáng kể dưới tải cao.

**Ví dụ:**
Theo dõi runtime counters:

```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Quan sát các metric như:

```text
Allocation Rate
GC Heap Size
Gen 0 GC Count
Gen 1 GC Count
Gen 2 GC Count
```

**Lưu ý:**
Đừng tối ưu allocation ở code hiếm khi chạy. Chỉ nên đầu tư khi profiling chứng minh đó là bottleneck hoặc hot path thực sự.

## 🧠 Software Design

### Design 1 — Cache-Aside và bài toán dữ liệu stale

**Khái niệm:**
Cache-Aside là mô hình application đọc cache trước, cache miss thì đọc database rồi ghi kết quả vào cache. Đây là pattern đơn giản và phổ biến với Redis.

**Vấn đề nó giải quyết:**
Giảm database load và latency cho dữ liệu được đọc thường xuyên nhưng không cần mỗi lần đều truy vấn nguồn dữ liệu chính.

**Ví dụ thực tế:**
Một API đọc `ProductDetail` hàng nghìn lần mỗi phút. Application kiểm tra Redis trước, nếu miss mới query PostgreSQL và cache trong 5 phút. Khi product được update, application xóa cache key tương ứng.

**Trade-off:**
Lợi ích là triển khai đơn giản và hiệu quả cho read-heavy workload. Rủi ro là stale data, cache stampede và inconsistency giữa cache với database. TTL ngắn giảm stale data nhưng tăng cache miss; TTL dài cải thiện hit rate nhưng tăng độ cũ dữ liệu.

**Middle → Senior insight:**
Middle developer nên hiểu cache không phải source of truth và phải có invalidation strategy. Senior developer cần đánh giá acceptable staleness, TTL, cache stampede protection, hot-key risk và hành vi khi Redis unavailable.

### Design 2 — API evolution: additive change trước breaking change

**Khái niệm:**
API evolution ưu tiên thay đổi tương thích ngược như thêm optional field, endpoint mới hoặc behavior mới được opt-in thay vì sửa trực tiếp contract mà client hiện tại đang phụ thuộc.

**Vấn đề nó giải quyết:**
Một API production thường có nhiều client release cycle khác nhau. Breaking change nhỏ phía server có thể khiến mobile app cũ, integration partner hoặc service chưa deploy đồng loạt bị hỏng.

**Ví dụ thực tế:**
Thay vì đổi:

```json
{
  "fullName": "Alice Nguyen"
}
```

thành:

```json
{
  "firstName": "Alice",
  "lastName": "Nguyen"
}
```

ngay lập tức, server có thể tạm thời trả cả `fullName`, `firstName`, `lastName`, đánh dấu field cũ deprecated và đo usage trước khi xóa.

**Trade-off:**
Additive evolution giúp deployment độc lập và giảm rủi ro nhưng làm contract phình ra, tăng thời gian duy trì backward compatibility và có thể kéo dài technical debt nếu không có deprecation policy rõ ràng.

**Middle → Senior insight:**
Middle developer cần nhận biết thay đổi nào là breaking change. Senior developer phải thiết kế versioning/deprecation strategy, telemetry để biết client nào còn dùng contract cũ và migration window phù hợp.

### Design 3 — Chọn synchronous call hay messaging giữa các module/service

**Khái niệm:**
Synchronous communication phù hợp khi caller cần kết quả ngay để hoàn thành request. Messaging phù hợp hơn khi công việc có thể xử lý bất đồng bộ, cần decoupling hoặc cần hấp thụ burst traffic.

**Vấn đề nó giải quyết:**
Nếu mọi service đều gọi synchronous qua nhiều tầng, một request có thể tạo dependency chain dài, tăng latency và làm failure cascade. Nhưng dùng message cho mọi thứ lại làm flow khó theo dõi và tăng eventual consistency complexity.

**Ví dụ thực tế:**
Khi checkout, service cần kiểm tra giá hiện tại trước khi xác nhận order nên synchronous call có thể hợp lý. Sau khi order được tạo, gửi email, analytics và loyalty points có thể phát event `OrderCreated` qua RabbitMQ để xử lý độc lập.

**Trade-off:**
Synchronous call đơn giản hơn về mental model và consistency tức thời nhưng coupling cao hơn và nhạy với downstream failure. Messaging tăng resilience và decoupling nhưng thêm retry, duplicate message, ordering, dead-letter queue và observability complexity.

**Middle → Senior insight:**
Middle developer cần hiểu khác biệt giữa request/response và event-driven flow. Senior developer cần chọn communication style theo business requirement, latency, consistency, failure mode và operational cost thay vì dùng một pattern cho toàn hệ thống.
