# Daily Developer Tips & Design — 2026-09-25

## 🛠 Developer Tips & Tricks

### Tip 1 — EF Core projection giảm cả dữ liệu truyền lẫn change-tracking cost

**Mẹo:**
Với read-only API, project trực tiếp sang DTO bằng `Select` thay vì load toàn bộ entity graph rồi mới map trong memory.

**Tại sao hữu ích:**
EF Core có thể dịch projection thành SQL chỉ lấy các cột cần thiết. Điều này giảm network payload, materialization và allocation; kết hợp `AsNoTracking()` khi không cần update còn tránh tạo tracking state không cần thiết.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Total))
    .ToListAsync(cancellationToken);
```
Đối chiếu generated SQL hoặc execution plan nếu endpoint vẫn chậm thay vì giả định projection đã giải quyết mọi bottleneck.

**Lưu ý:**
Projection phức tạp có thể tạo SQL khó tối ưu hoặc translation không như mong đợi. Đừng thêm `Include` khi projection đã lấy đúng dữ liệu cần thiết; luôn kiểm tra SQL thực tế trên hot path.

### Tip 2 — PostgreSQL composite index phải bám query pattern, không bám danh sách cột

**Mẹo:**
Thiết kế composite index từ predicate và sort thực tế. Thứ tự cột quyết định khả năng database thu hẹp search space và phục vụ `ORDER BY`.

**Tại sao hữu ích:**
Một index chứa đúng các cột chưa chắc hữu ích nếu leading columns không phù hợp với access pattern. Execution plan mới là bằng chứng cho việc index được dùng hiệu quả.

**Ví dụ:**
API thường chạy:
```sql
SELECT id, created_at, total
FROM orders
WHERE tenant_id = $1 AND status = $2
ORDER BY created_at DESC
LIMIT 50;
```
Một candidate index có thể bắt đầu bằng `(tenant_id, status, created_at DESC)`; sau đó dùng `EXPLAIN (ANALYZE, BUFFERS)` để xác nhận rows scanned, sort và I/O.

**Lưu ý:**
Không tạo index cho mọi biến thể filter. Mỗi index làm tăng storage và write amplification; selectivity, workload và query frequency phải được đo trước.

### Tip 3 — Service Bus lock expiration có thể biến xử lý chậm thành duplicate processing

**Mẹo:**
Khi Azure Service Bus consumer xử lý lâu, theo dõi message lock và thiết kế handler idempotent thay vì giả định một message chỉ chạy một lần.

**Tại sao hữu ích:**
Với at-least-once delivery, worker có thể hoàn thành side effect nhưng mất lock trước khi complete message; broker sau đó giao lại message. Retry lúc này có thể tạo duplicate payment, email hoặc inventory update.

**Ví dụ:**
Consumer nhận `PaymentRequested` với stable `MessageId`. Trước side effect, kiểm tra Inbox/idempotency record trong cùng consistency boundary; telemetry ghi delivery count và processing duration để phát hiện handler tiến sát lock budget.

**Lưu ý:**
Tăng lock duration chỉ kéo dài cửa sổ, không tạo exactly-once semantics. Auto lock renewal cũng không thay thế idempotency và có thể che handler quá chậm hoặc dependency bị treo.

### Tip 4 — Dùng Git bisect để tìm regression thay vì đọc hàng chục commit bằng mắt

**Mẹo:**
Khi biết một commit cũ hoạt động và HEAD bị lỗi, dùng `git bisect` để thu hẹp commit gây regression theo binary search.

**Tại sao hữu ích:**
Với lịch sử lớn, bisect giảm mạnh số commit cần kiểm tra và đặc biệt hiệu quả khi có test hoặc script tái hiện bug tự động.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
git bisect reset
```
Một production regression có 128 candidate commits về lý thuyết chỉ cần khoảng 7 bước phân đôi nếu test phân loại ổn định.

**Lưu ý:**
Bisect kém tin cậy khi test flaky, build của commit cũ không chạy được hoặc bug phụ thuộc dữ liệu/môi trường ngoài Git. Khi đó cần script phân loại rõ `good`, `bad` và `skip`.

### Tip 5 — CORS không phải cơ chế Authorization

**Mẹo:**
Xem CORS là browser-enforced cross-origin policy; mọi API nhạy cảm vẫn phải Authentication/Authorization ở server cho từng request.

**Tại sao hữu ích:**
Non-browser client như curl, backend service hoặc attacker-controlled script ngoài browser không bị CORS bảo vệ. Một endpoint chỉ dựa vào allowed origin nhưng thiếu authorization vẫn có thể bị gọi trực tiếp.

**Ví dụ:**
Admin SPA được phép origin `https://admin.example.com`, nhưng `DELETE /api/users/{id}` vẫn phải validate access token và role/permission. CORS chỉ quyết định browser có cho frontend đọc/gửi request cross-origin theo policy hay không.

**Lưu ý:**
Không kết hợp `AllowAnyOrigin` với credential assumptions tùy tiện. Với cookie authentication, còn phải phân tích CSRF, `SameSite` và credential behavior riêng; CORS không thay thế CSRF protection.

## 🧠 Software Design

### Design 1 — REST hay messaging phải xuất phát từ temporal coupling

**Khái niệm:**
REST phù hợp khi caller cần kết quả đồng bộ và hai phía có thể cùng available trong latency budget. Messaging giảm temporal coupling khi producer không cần consumer hoàn tất ngay và workflow chấp nhận asynchronous completion.

**Vấn đề nó giải quyết:**
Chuỗi synchronous calls dài làm availability và latency của request phụ thuộc nhiều downstream services. Ngược lại, biến mọi interaction thành event tạo eventual consistency và operational complexity không cần thiết.

**Ví dụ thực tế:**
Checkout cần validate request và trả `OrderId` ngay bằng local transaction; việc gửi email và cập nhật analytics đi qua messaging. Nhưng price validation cần phản hồi tức thời có thể vẫn là synchronous call nếu authoritative pricing nằm ở service khác.

**Trade-off:**
REST đơn giản về control flow và immediate error handling nhưng tăng runtime coupling. Messaging hấp thụ burst và cô lập outage tốt hơn, đổi lại phải xử lý duplicate, ordering, retries, DLQ, observability và trạng thái “đang xử lý”.

**Middle → Senior insight:**
Middle developer cần hiểu timeout/retry của HTTP và delivery semantics của broker. Senior / Technical developer phải phân loại interaction theo consistency, latency, ownership và failure requirements rồi chọn sync/async; không dùng event-driven chỉ để tránh một HTTP call.

### Design 2 — Optimistic concurrency bảo vệ invariant mà không khóa dài

**Khái niệm:**
Optimistic concurrency cho phép nhiều request đọc cùng trạng thái nhưng chỉ update nếu version/token vẫn như lúc đọc; conflict được phát hiện tại write boundary.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng sửa một order có thể tạo lost update nếu request sau ghi đè request trước. Giữ pessimistic lock xuyên user think-time lại không thực tế cho web application.

**Ví dụ thực tế:**
`Order` có `rowversion`. API nhận version cùng command; EF Core update với concurrency predicate. Nếu zero rows affected, API trả conflict phù hợp và client reload/merge thay vì âm thầm overwrite dữ liệu mới hơn.

**Trade-off:**
Optimistic concurrency giữ throughput tốt khi conflict hiếm nhưng buộc application thiết kế conflict semantics và retry/merge. Với contention cao hoặc invariant cần serialization chặt, database locking hay một coordination strategy khác có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần xử lý `DbUpdateConcurrencyException` và không auto-retry business update mù quáng. Senior / Technical developer phải xác định aggregate/invariant boundary, conflict probability và UX/recovery policy để chọn optimistic, pessimistic hoặc serialized processing.

### Design 3 — Observability phải được thiết kế theo failure questions

**Khái niệm:**
Observability tốt không phải “log thật nhiều”; telemetry phải giúp trả lời các câu hỏi vận hành cụ thể bằng metrics, traces và structured logs có correlation.

**Vấn đề nó giải quyết:**
Khi p95 API tăng từ 300 ms lên 2 s, hàng triệu text logs không giúp nhiều nếu không biết thời gian nằm ở application, SQL, Redis hay external API và không thể nối các dependency calls vào cùng request.

**Ví dụ thực tế:**
Checkout dashboard theo dõi request rate/error/p95, dependency latency và Service Bus backlog. Trace giữ `Activity/traceId` xuyên HTTP và messaging; structured log thêm `OrderId` có kiểm soát. Incident bắt đầu từ metric anomaly → trace chậm → dependency span → log/error cụ thể.

**Trade-off:**
Telemetry giàu context rút ngắn MTTR nhưng tăng ingestion/storage cost và có rủi ro sensitive data/high-cardinality. Sampling quá mạnh lại có thể mất rare failure; logging mọi payload thì vừa đắt vừa nguy hiểm.

**Middle → Senior insight:**
Middle developer cần tạo structured logs, correlation và instrumentation đúng. Senior / Technical developer phải chọn SLI, cardinality, retention, sampling và telemetry boundary dựa trên failure modes và operational budget, đồng thời bảo đảm hệ thống quan sát được cả degraded state chứ không chỉ exception.
