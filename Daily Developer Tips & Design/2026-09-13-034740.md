# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `rowversion` với EF Core để phát hiện lost update thay vì âm thầm ghi đè

**Mẹo:**
Với entity có khả năng bị nhiều request/user cập nhật cùng lúc, dùng optimistic concurrency token như SQL Server `rowversion` để EF Core phát hiện dữ liệu đã thay đổi kể từ lúc được đọc.

**Tại sao hữu ích:**
Không có concurrency check, flow `read -> edit -> save` có thể làm request đến sau ghi đè thay đổi của request trước mà không có lỗi. `rowversion` khiến `UPDATE` mang thêm điều kiện version cũ; nếu không còn row nào match, EF Core ném `DbUpdateConcurrencyException` thay vì coi thao tác là thành công.

**Ví dụ:**
```csharp
public sealed class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = [];
}
```

EF Core sẽ tạo SQL theo dạng:
```sql
UPDATE Products
SET Price = @Price
WHERE Id = @Id
  AND Version = @OriginalVersion;
```

Khi conflict xảy ra, application phải quyết định reload, merge, reject bằng `409 Conflict`, hoặc yêu cầu user xác nhận lại.

**Lưu ý:**
Optimistic concurrency chỉ phát hiện conflict; nó không tự biết cách merge business state. Retry mù toàn bộ operation có thể lại ghi đè dữ liệu mới. Với workflow cần serialize access thật sự, pessimistic locking hoặc business-level coordination có thể phù hợp hơn.

### Tip 2 — Phân biệt readiness và liveness để Kubernetes/App Service không restart nhầm instance đang chỉ phụ thuộc downstream lỗi

**Mẹo:**
Thiết kế health check theo mục đích: liveness trả lời “process còn sống không?”, readiness trả lời “instance hiện có nên nhận traffic không?”. Không nhét mọi external dependency vào liveness.

**Tại sao hữu ích:**
Nếu database hoặc third-party API tạm lỗi mà liveness cũng fail, orchestrator có thể restart hàng loạt instance dù application process hoàn toàn khỏe. Điều này tạo restart storm và làm incident nặng hơn. Readiness cho phép rút instance khỏi traffic mà chưa nhất thiết kill process.

**Ví dụ:**
```text
/liveness
- process responsive
- internal event loop/thread state cơ bản

/readiness
- config đã load
- database cần thiết cho request path đang reachable
- required local initialization hoàn tất
```

Trong ASP.NET Core có thể tag health check theo nhóm rồi map thành endpoint riêng.

**Lưu ý:**
Đừng biến readiness thành một dependency graph khổng lồ. Nếu service có degraded mode hợp lệ, dependency không critical có thể không nên làm readiness fail. Health semantics phải phản ánh behavior mà load balancer/orchestrator thực sự cần.

### Tip 3 — Với Elasticsearch, dùng `keyword` cho exact filter/aggregation và `text` cho full-text search

**Mẹo:**
Khi thiết kế mapping, đừng dùng một field analyzed cho mọi mục đích. Các giá trị như SKU, status, category code hoặc email thường cần `keyword`; nội dung cần search ngôn ngữ tự nhiên mới dùng `text`.

**Tại sao hữu ích:**
`text` được analyzer tách/tokenize trước khi index. Vì vậy exact filter hoặc aggregation trên field này có thể cho kết quả không như mong đợi hoặc tốn tài nguyên hơn. `keyword` giữ nguyên giá trị và phù hợp với term query, sorting và aggregation.

**Ví dụ:**
```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "raw": { "type": "keyword" }
        }
      },
      "status": { "type": "keyword" }
    }
  }
}
```

Search text:
```json
{ "match": { "name": "wireless mouse" } }
```

Exact filter:
```json
{ "term": { "status": "ACTIVE" } }
```

**Lưu ý:**
Mapping sai thường không sửa được chỉ bằng đổi query; nhiều thay đổi cần tạo index mới và reindex dữ liệu. Đồng thời phải xem analyzer, case normalization và cardinality thực tế thay vì áp `keyword` cho mọi string.

### Tip 4 — Trong CMS, cache theo content version/published state thay vì chỉ theo URL

**Mẹo:**
Với Optimizely CMS hoặc hệ thống content tương tự, cache response/component nên gắn với content identity/version hoặc publication state khi dữ liệu biên tập có thể thay đổi độc lập với URL.

**Tại sao hữu ích:**
Nếu key chỉ là `/products/shoes`, cùng URL có thể trỏ tới content mới sau publish nhưng cache cũ vẫn còn TTL. Khi cache key hoặc invalidation hiểu publication/version, việc publish content có thể làm cache chuyển sang generation mới rõ ràng hơn.

**Ví dụ:**
```text
Kém an toàn:
page:/products/shoes

Tốt hơn trong một số CMS flow:
page:{contentId}:{publishedVersion}:{culture}
```

Một publish event có thể invalidate đúng content/component hoặc tăng generation thay vì flush toàn bộ site cache.

**Lưu ý:**
Không cache trực tiếp object graph CMS lớn nếu object lifecycle/serialization không được đảm bảo. Nếu page có personalization, authentication hoặc tenant-specific data, cache key phải phản ánh đúng variation; nếu không rất dễ leak nội dung giữa user/tenant.

### Tip 5 — Khi dùng AI coding agent, bắt nó chứng minh API/package version từ source trước khi chấp nhận code

**Mẹo:**
Với code do AI tạo, đặc biệt ở .NET, Azure SDK, frontend framework hoặc package đang thay đổi nhanh, yêu cầu agent kiểm tra repository, project file và documentation/version thực tế trước khi dùng API mới.

**Tại sao hữu ích:**
AI thường tạo code “trông đúng” nhưng gọi API không tồn tại ở version hiện tại, dùng option đã deprecated hoặc giả định package đã được cài. Nếu grounding vào `*.csproj`, lockfile và source hiện hành, lỗi kiểu này giảm đáng kể.

**Ví dụ:**
```text
Trước khi implement:
1. đọc TargetFramework trong .csproj
2. đọc PackageReference / package-lock / pnpm-lock
3. search API đang được dùng trong repo
4. chỉ sau đó mới generate patch
5. build + test để xác nhận
```

Nếu agent đề xuất `SomeNewApi()` nhưng repository đang ở package version cũ, quyết định đúng có thể là dùng API hiện có thay vì tự động upgrade dependency.

**Lưu ý:**
Build xanh vẫn chưa chứng minh behavior đúng, security đúng hoặc architecture đúng. AI-generated migration, SQL, retry policy và authorization code cần review như code của một developer khác, thậm chí kỹ hơn ở boundary nhạy cảm.

## 🧠 Software Design

### Design 1 — Transactional Outbox khi database commit và publish message phải nhất quán

**Khái niệm:**
Transactional Outbox lưu business change và message cần publish trong cùng local database transaction. Một publisher riêng sau đó đọc outbox và gửi message ra broker.

**Vấn đề nó giải quyết:**
Nếu code làm:
```text
1. UPDATE Order = Paid
2. publish PaymentCaptured
```
thì crash giữa bước 1 và 2 khiến database đã commit nhưng event không bao giờ được publish. Đảo thứ tự lại tạo rủi ro event được publish nhưng database rollback.

**Ví dụ thực tế:**
```text
BEGIN TRANSACTION
  UPDATE Orders SET Status = 'Paid' ...
  INSERT Outbox(MessageId, Type, Payload, CreatedAt)
COMMIT

Background publisher:
- đọc outbox chưa gửi
- publish Azure Service Bus
- đánh dấu processed
```

Consumer vẫn nên idempotent vì publisher có thể gửi lại nếu publish thành công nhưng chưa kịp đánh dấu processed.

**Trade-off:**
Outbox loại bỏ dual-write inconsistency giữa database và broker nhưng thêm table, polling/change-capture mechanism, cleanup, ordering concern và observability. Nếu use case không cần message reliability cao hoặc tất cả thay đổi nằm trong cùng transactional datastore, pattern này có thể là quá mức cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu vì sao `SaveChangesAsync()` rồi `SendMessageAsync()` không atomic. Senior / Technical developer phải quyết định polling strategy, ordering scope, deduplication, retention, throughput và failure recovery, đồng thời tránh gọi Outbox là “exactly once” cho toàn hệ thống.

### Design 2 — Primary database và Elasticsearch cần consistency contract rõ ràng, không chỉ “sync bằng background job”

**Khái niệm:**
Khi Elasticsearch là search projection của SQL/MongoDB primary store, hệ thống phải xác định rõ source of truth, propagation mechanism và mức stale data chấp nhận được.

**Vấn đề nó giải quyết:**
Nếu user update product nhưng search index cập nhật chậm hoặc thất bại, API detail có thể trả dữ liệu mới trong khi search vẫn hiển thị dữ liệu cũ. Nếu không có consistency contract, team dễ coi đây là bug ngẫu nhiên thay vì behavior kiến trúc cần quản lý.

**Ví dụ thực tế:**
```text
SQL = source of truth
   │
   ├─ transaction + outbox
   ▼
indexer
   ▼
Elasticsearch

SLO nội bộ:
95% change xuất hiện trong search < 10s
99.9% < 2 phút
```

Cần metric cho indexing lag, failed documents, retry backlog và khả năng reindex toàn bộ từ source of truth.

**Trade-off:**
Search projection cho query/search capability mạnh và giảm tải primary DB, nhưng đổi lại có eventual consistency, duplicated storage và pipeline vận hành riêng. Với dataset nhỏ và search requirement đơn giản, SQL full-text hoặc query trực tiếp có thể rẻ và dễ vận hành hơn.

**Middle → Senior insight:**
Middle developer cần không write trực tiếp business truth vào Elasticsearch rồi coi đó là dữ liệu authoritative. Senior / Technical developer phải thiết kế replay/reindex, schema migration, lag SLO, failure recovery và UX khi search result tạm lệch với transactional state.

### Design 3 — Azure Functions hay Worker Service phải chọn theo execution model, không theo độ “serverless” nghe hấp dẫn

**Khái niệm:**
Azure Functions phù hợp với event-driven execution có lifecycle ngắn và scale theo trigger; Worker Service phù hợp hơn khi cần process dài, control vòng đời, connection lâu dài hoặc throughput ổn định có tuning riêng.

**Vấn đề nó giải quyết:**
Team thường chọn Functions cho mọi background job vì deployment đơn giản, nhưng sau đó gặp long-running processing, cold start, timeout, lock renewal, dependency initialization hoặc concurrency tuning khó kiểm soát.

**Ví dụ thực tế:**
```text
Azure Function phù hợp:
- Blob uploaded -> generate thumbnail
- HTTP/webhook nhỏ
- Service Bus message xử lý độc lập, ngắn

Worker Service phù hợp hơn:
- stream processor chạy liên tục
- batch lớn kéo dài hàng giờ
- cần connection/session lâu dài
- cần custom backpressure/concurrency loop
```

Cả hai đều có thể chạy background work; khác biệt chính là operational model và mức control.

**Trade-off:**
Functions giảm infrastructure management và scale tốt theo event nhưng có runtime/platform constraints và execution semantics cần hiểu kỹ. Worker Service tăng trách nhiệm deployment/scale nhưng cho control rõ hơn về process lifetime, resource budget và concurrency.

**Middle → Senior insight:**
Middle developer cần biết trigger, retry và idempotency behavior của runtime mình dùng. Senior / Technical developer phải chọn dựa trên workload duration, traffic pattern, scale characteristic, cold-start tolerance, observability, cost và failure semantics; không chọn Functions chỉ vì ít code cấu hình hơn.
