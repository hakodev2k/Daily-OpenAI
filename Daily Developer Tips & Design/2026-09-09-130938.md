# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh captive dependency khi `Singleton` giữ `Scoped` service

**Mẹo:**
Trong .NET Dependency Injection, đừng để một service đăng ký `Singleton` giữ trực tiếp dependency có lifetime `Scoped` như `DbContext`, request-scoped service hoặc tenant context.

**Tại sao hữu ích:**
`Singleton` sống suốt vòng đời process, còn `Scoped` thường chỉ hợp lệ trong một request hoặc scope. Nếu scoped object bị giữ lâu ngoài scope, state có thể bị dùng sai giữa request, `DbContext` không còn đúng unit-of-work và lỗi concurrency/lifetime trở nên khó chẩn đoán.

**Ví dụ:**
Không nên:
```csharp
builder.Services.AddSingleton<ReportScheduler>();
builder.Services.AddScoped<AppDbContext>();

public sealed class ReportScheduler(AppDbContext db)
{
    // db bị giữ bởi singleton
}
```

Nếu background singleton cần scoped dependency, tạo scope cho từng operation:
```csharp
using var scope = scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
```

**Lưu ý:**
Đừng tạo scope mới tùy tiện trong application service chỉ để né lifetime mismatch. Lifetime phải phản ánh ownership thật; với background work, scope per message/job thường rõ hơn.

### Tip 2 — Khi PostgreSQL table phình to, kiểm tra dead tuples và autovacuum trước khi thêm disk

**Mẹo:**
Nếu PostgreSQL table/index tăng dung lượng nhanh hoặc query scan chậm dần dù row count không tăng tương ứng, kiểm tra dead tuples, autovacuum activity và long-running transaction.

**Tại sao hữu ích:**
MVCC không overwrite row tại chỗ; `UPDATE`/`DELETE` tạo version cũ cần được VACUUM dọn. Nếu autovacuum không theo kịp hoặc transaction cũ giữ snapshot quá lâu, dead tuples tích tụ, làm tăng I/O và index/table bloat.

**Ví dụ:**
Điều tra bằng các signal như:
```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Nếu một table có dead tuples rất cao và autovacuum ít chạy, kiểm tra threshold/configuration và transaction đang mở lâu trước khi quyết định `VACUUM FULL`.

**Lưu ý:**
`VACUUM FULL` lấy lock mạnh và rewrite table; không phải fix mặc định cho production. Root cause có thể là workload update-heavy, autovacuum tuning hoặc long-running transaction.

### Tip 3 — Dùng Azure App Service deployment slot để warm-up trước khi swap production

**Mẹo:**
Khi deploy ASP.NET Core lên Azure App Service, dùng staging slot để deploy, warm-up và health-check version mới trước khi swap traffic sang production.

**Tại sao hữu ích:**
Startup có thể bao gồm JIT, dependency initialization, configuration validation hoặc cache warm-up. Nếu deploy trực tiếp, user đầu tiên có thể gánh startup failure/latency. Slot giúp verify application ở environment gần production trước cutover.

**Ví dụ:**
```text
Deploy v5.4 -> staging slot
-> run smoke test /health/ready
-> verify Key Vault, DB, external dependencies
-> warm application
-> swap staging <-> production
```

Configuration nhạy với environment cần được đánh dấu slot-specific khi phù hợp.

**Lưu ý:**
Slot swap không tự giải quyết breaking database migration. Cả version cũ và mới có thể tồn tại trong rollout/rollback window, nên schema change vẫn cần backward compatibility.

### Tip 4 — Dùng SonarQube complexity như tín hiệu để review design, không phải KPI để “chơi điểm”

**Mẹo:**
Khi SonarQube báo cyclomatic/cognitive complexity cao, dùng warning để tìm logic có quá nhiều nhánh hoặc responsibility trộn lẫn, thay vì refactor cơ học chỉ để metric xuống dưới threshold.

**Tại sao hữu ích:**
Complexity cao thường làm test matrix lớn, reasoning khó và regression risk tăng. Nhưng tách một method thành mười method nhỏ mà vẫn giữ cùng control flow có thể chỉ phân tán complexity, không giảm nó.

**Ví dụ:**
Một checkout method có:
```text
region rule
+ payment type rule
+ discount rule
+ fraud rule
+ shipping rule
```

nên được xem lại theo business responsibility/policy boundary, không chỉ extract từng `if` thành helper.

**Lưu ý:**
Metric không hiểu domain context. Một parser/state machine có thể hợp lý khi complexity cao. Ưu tiên readability, testability và change cost hơn việc tối ưu một con số riêng lẻ.

### Tip 5 — Trong Vue, dùng `computed` cho derived state; `watch` cho side effect

**Mẹo:**
Nếu một giá trị chỉ được suy ra từ reactive state khác, ưu tiên `computed`. Dùng `watch` khi thay đổi state cần kích hoạt side effect như gọi API, ghi storage hoặc integration với browser API.

**Tại sao hữu ích:**
`computed` biểu diễn dependency declaratively và được cache theo dependency. Dùng `watch` để đồng bộ một derived value tạo thêm mutable state, dễ sinh stale state hoặc vòng lặp update.

**Ví dụ:**
Nên:
```ts
const fullName = computed(() => `${firstName.value} ${lastName.value}`)
```

Thay vì:
```ts
const fullName = ref('')
watch([firstName, lastName], () => {
  fullName.value = `${firstName.value} ${lastName.value}`
})
```

`watch` hợp lý hơn khi cần gọi `/api/search` khi query đổi.

**Lưu ý:**
Đừng nhét async side effect vào `computed`. Với watcher gọi API, cần cleanup/cancellation để tránh stale response khi dependency đổi nhanh.

## 🧠 Software Design

### Design 1 — Synchronous REST vs Asynchronous Messaging

**Khái niệm:**
REST synchronous phù hợp khi caller cần kết quả ngay để tiếp tục flow. Messaging asynchronous phù hợp khi producer có thể tách khỏi thời điểm consumer xử lý và chấp nhận eventual consistency.

**Vấn đề nó giải quyết:**
Nếu một request checkout gọi tuần tự nhiều downstream service, latency và availability của tất cả dependency cộng dồn vào user request. Ngược lại, biến mọi interaction thành message khiến workflow đơn giản bị khó debug và UX khó trả kết quả tức thời.

**Ví dụ thực tế:**
```text
GET product detail -> REST vì UI cần dữ liệu ngay

OrderPlaced -> message
  -> analytics
  -> notification
  -> loyalty
```

Payment authorization cần quyết định tức thời có thể vẫn synchronous, trong khi email receipt không cần nằm trên critical path.

**Trade-off:**
REST đơn giản, dễ hiểu và có consistency tức thời hơn nhưng tạo temporal coupling và dễ cascading failure. Messaging giảm coupling về thời gian và hấp thụ burst tốt hơn nhưng thêm broker, retry, duplicates, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần nhận biết operation nào cần response ngay và xử lý timeout/retry đúng. Senior / Technical developer phải chọn boundary theo user latency budget, failure isolation, consistency requirement, ownership và operational cost thay vì mặc định REST hoặc event-driven.

### Design 2 — Feature Flag là release mechanism có lifecycle, không phải `if` vĩnh viễn

**Khái niệm:**
Feature Flag tách deployment khỏi release: code có thể được deploy nhưng capability chỉ bật cho một nhóm user/tenant hoặc percentage traffic. Flag phải có owner, mục đích và thời điểm cleanup.

**Vấn đề nó giải quyết:**
Rollout big-bang làm blast radius lớn. Feature flag cho phép canary, internal testing hoặc kill-switch nhanh khi metric xấu mà không cần rollback toàn deployment.

**Ví dụ thực tế:**
```text
NewCheckout = off
-> internal users
-> 5% tenants
-> 25%
-> 100%
-> remove old path + delete flag
```

Rollout có thể dựa trên error rate, latency và business metric đã định nghĩa trước.

**Trade-off:**
Flag giảm release risk nhưng tăng số code path, test matrix và configuration dependency. Flag cũ không được dọn tạo technical debt và làm behavior production khó hiểu.

**Middle → Senior insight:**
Middle developer cần test cả ON/OFF path và không assume flag cố định. Senior / Technical developer phải định nghĩa ownership, expiry, rollout criteria, fallback và cleanup để feature flags không trở thành permanent architecture.

### Design 3 — Anti-Corruption Layer khi legacy model không nên lan vào domain mới

**Khái niệm:**
Anti-Corruption Layer (ACL) là boundary dịch terminology, data shape và protocol của legacy/external system sang model mà domain mới hiểu, thay vì để DTO và rule của hệ thống cũ xuất hiện khắp codebase.

**Vấn đề nó giải quyết:**
Một legacy CRM có thể dùng code như `STAT=A`, field naming cũ và semantics khác domain hiện tại. Nếu application mới dùng trực tiếp legacy DTO, migration sau này trở thành thay đổi xuyên nhiều module.

**Ví dụ thực tế:**
Legacy response:
```json
{ "cust_no": "C102", "stat": "A", "credit_flag": "Y" }
```

ACL chuyển thành:
```text
CustomerId = C102
Status = Active
CreditEligibility = Allowed
```

Core domain không cần biết `stat` hay `credit_flag` tồn tại.

**Trade-off:**
ACL cô lập coupling và giúp thay integration dễ hơn nhưng thêm mapping, tests và một model trung gian. Với integration nhỏ và model gần như giống nhau, adapter mỏng có thể đủ.

**Middle → Senior insight:**
Middle developer cần giữ external DTO ở integration boundary. Senior / Technical developer phải xác định khi nào translation cost đáng đổi lấy isolation, đồng thời thiết kế error mapping, versioning và migration path để ACL không biến thành một mini-domain không cần thiết.
