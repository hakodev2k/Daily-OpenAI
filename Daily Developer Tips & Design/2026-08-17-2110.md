# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `MemoryCacheEntryOptions` để kiểm soát lifetime của cache

**Mẹo:**
Khi dùng `IMemoryCache`, cấu hình expiration theo semantics của dữ liệu thay vì cache vô thời hạn rồi trông chờ manual invalidation.

**Tại sao hữu ích:**
Giảm stale data và hạn chế memory tăng dần nếu key space lớn hoặc key động theo user/request.

**Ví dụ:**
```csharp
var options = new MemoryCacheEntryOptions()
    .SetAbsoluteExpiration(TimeSpan.FromMinutes(5))
    .SetSlidingExpiration(TimeSpan.FromMinutes(1));

cache.Set($"employee:{employeeId}", employee, options);
```

**Lưu ý:**
Absolute + sliding expiration không thay thế invalidation đúng nghiệp vụ. Với dữ liệu phải phản ánh thay đổi gần như ngay lập tức, cần event-based invalidation, versioning hoặc không cache ở layer này.

### Tip 2 — Dùng `ROW_NUMBER()` để deduplicate có kiểm soát thay vì `DISTINCT`

**Mẹo:**
Khi cần giữ đúng một row trong mỗi nhóm duplicate, dùng window function để định nghĩa rõ row nào được giữ thay vì dùng `DISTINCT` và hy vọng dữ liệu tự đúng.

**Tại sao hữu ích:**
Cho phép chọn bản ghi mới nhất, ưu tiên nhất hoặc đáng tin cậy nhất theo business rule rõ ràng.

**Ví dụ:**
```sql
WITH Ranked AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY EmployeeId, WorkDate
            ORDER BY UpdatedAt DESC, Id DESC
        ) AS rn
    FROM TimesheetEntries
)
SELECT *
FROM Ranked
WHERE rn = 1;
```

**Lưu ý:**
Nếu duplicate là dữ liệu bất hợp lệ thì query deduplicate chỉ che symptom. Cần thêm unique constraint hoặc sửa write path nếu invariant cho phép.

### Tip 3 — Dùng `git status --short --branch` cho preflight nhanh

**Mẹo:**
Khi cần trạng thái repo dạng compact nhưng vẫn thấy branch và ahead/behind, dùng `git status --short --branch`.

**Tại sao hữu ích:**
Tiện trước rebase, merge hoặc release mà không phải đọc toàn bộ output của `git status` thường.

**Ví dụ:**
```bash
git status --short --branch
```

Ví dụ:
```text
## feature/payment...origin/feature/payment [ahead 2]
 M src/PaymentService.cs
?? notes.txt
```

**Lưu ý:**
Số commit ahead/behind không phản ánh mức độ rủi ro của thay đổi. Vẫn cần xem diff và test phù hợp.

### Tip 4 — Dùng `dotnet test --filter` để cô lập nhanh nhóm test lỗi

**Mẹo:**
Khi pipeline có nhiều test nhưng failure chỉ liên quan một category, namespace hoặc tên test, dùng `--filter` để rút ngắn vòng lặp debug.

**Tại sao hữu ích:**
Giảm thời gian tái hiện lỗi, đặc biệt với integration test chậm hoặc test dùng container.

**Ví dụ:**
```bash
dotnet test --filter "Category=Integration"
```

Hoặc:
```bash
dotnet test --filter "FullyQualifiedName~Payment"
```

**Lưu ý:**
Filter chỉ giúp cô lập. Trước khi merge vẫn cần chạy coverage phù hợp với scope thay đổi để tránh bỏ sót regression ngoài nhóm đang debug.

### Tip 5 — Dùng `docker logs --since` để khoanh đúng cửa sổ incident

**Mẹo:**
Khi container có log rất dài, dùng `docker logs --since` và `--timestamps` để chỉ lấy đúng khoảng thời gian xảy ra sự cố.

**Tại sao hữu ích:**
Giảm noise khi debug restart loop, timeout hoặc exception vừa xuất hiện sau deploy.

**Ví dụ:**
```bash
docker logs \
  --since 20m \
  --timestamps \
  myapp
```

Theo dõi tiếp:
```bash
docker logs -f --since 5m myapp
```

**Lưu ý:**
Container logs có thể đã rotate hoặc không chứa toàn bộ application telemetry. Với production cần kết hợp centralized logging, metrics và trace.

## 🧠 Software Design

### Design 1 — Cache invalidation nên gắn với ownership của dữ liệu

**Khái niệm:**
Component sở hữu dữ liệu nguồn nên là nơi phát tín hiệu invalidation hoặc version change rõ nhất, thay vì để mọi consumer tự đoán khi cache cần xóa.

**Vấn đề nó giải quyết:**
Nếu mỗi service tự đặt TTL tùy ý cho cùng một loại dữ liệu, độ stale khác nhau và bug consistency rất khó giải thích.

**Ví dụ thực tế:**
`EmployeeService` là owner của employee profile. Khi profile thay đổi, service phát event `EmployeeProfileChanged` chứa `EmployeeId` và version. Consumer xóa cache hoặc bỏ qua entry version cũ.

**Trade-off:**
Ownership-based invalidation giảm stale window và làm semantics rõ hơn, nhưng tăng coupling qua event contract và failure path của invalidation. TTL vẫn cần làm fallback nếu event bị mất.

**Middle → Senior insight:**
Middle developer nên biết cache không chỉ là thêm TTL. Senior developer phải xác định source of truth, invalidation trigger, versioning, fallback TTL và behavior khi invalidation chậm hoặc mất.

### Design 2 — Shared Database không đồng nghĩa Shared Ownership

**Khái niệm:**
Nhiều module/service có thể tạm dùng chung một database vật lý nhưng vẫn nên có ownership logic rõ ràng theo table/schema và quyền mutation.

**Vấn đề nó giải quyết:**
Khi service A, B, C cùng update trực tiếp table của nhau, schema trở thành coupling ngầm mạnh hơn API và mọi migration đều khó an toàn.

**Ví dụ thực tế:**
`Payroll` và `Employee` cùng ở một SQL Server instance. `Employee` sở hữu schema `employee.*`; Payroll chỉ đọc qua view/read model hoặc contract được định nghĩa, không tự `UPDATE employee.Employees`.

**Trade-off:**
Shared database giảm operational cost và latency, nhưng cần discipline ownership rất cao. Database-per-service cho isolation mạnh hơn nhưng tăng migration, observability, transaction và deployment complexity.

**Middle → Senior insight:**
Middle developer nên phân biệt “cùng database” với “được phép sửa mọi bảng”. Senior developer phải thiết kế mutation boundary, migration ownership, read access và lộ trình tách nếu coupling tăng.

### Design 3 — Publish-Subscribe chỉ tốt khi side effect có tính độc lập

**Khái niệm:**
Publish-Subscribe phù hợp khi nhiều subscriber phản ứng độc lập với một event và publisher không cần điều phối chặt thứ tự hoặc rollback giữa họ.

**Vấn đề nó giải quyết:**
Nếu publisher gọi trực tiếp logging, notification, analytics và cache invalidation, dependency fan-out tăng và feature phụ có thể làm operation chính fail.

**Ví dụ thực tế:**
Sau `OrderApproved`, các subscriber độc lập có thể cập nhật analytics, gửi notification và warm cache. Core approval không cần biết implementation của từng side effect.

**Trade-off:**
Giảm coupling và mở rộng subscriber dễ, nhưng failure trở nên phân tán, ordering khó kiểm soát và observability phức tạp hơn. Nếu các bước phải chạy đúng thứ tự và có compensation chung, orchestration thường phù hợp hơn.

**Middle → Senior insight:**
Middle developer nên tránh dùng event chỉ để “né dependency injection”. Senior developer phải đánh giá independence, delivery guarantee, ordering, retry và observability trước khi chọn pub/sub thay cho direct call hoặc orchestrator.
