# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsSplitQuery` khi `Include` nhiều collection gây cartesian explosion

**Mẹo:**
Trong EF Core, nếu một query `Include` nhiều collection cùng lúc và số row trả về tăng bất thường, kiểm tra SQL thực tế và cân nhắc `AsSplitQuery()` để tách việc load thành nhiều query có kiểm soát.

**Tại sao hữu ích:**
Một query duy nhất join nhiều collection có thể nhân bản dữ liệu theo tích số lượng phần tử. Ví dụ một `Order` có 20 `Lines` và 10 `Payments` có thể tạo tới 200 row trung gian cho cùng một order. Điều này làm tăng network payload, materialization cost và memory dù số entity thực tế nhỏ hơn nhiều.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

Trước khi đổi, so sánh SQL, row count, duration và payload giữa single query với split query.

**Lưu ý:**
`AsSplitQuery` đổi một query thành nhiều round-trip và có thể thấy dữ liệu thay đổi giữa các query nếu consistency requirement chặt. Với projection DTO đơn giản, `Select` thường tốt hơn việc `Include` toàn graph.

### Tip 2 — Dùng HTTP `ETag` cho conditional request thay vì luôn trả lại payload đầy đủ

**Mẹo:**
Với resource đọc nhiều nhưng thay đổi ít, hỗ trợ `ETag` + `If-None-Match` để client kiểm tra phiên bản resource trước khi tải lại toàn bộ response.

**Tại sao hữu ích:**
Nếu resource chưa đổi, server có thể trả `304 Not Modified` mà không gửi body. Điều này giảm bandwidth, serialization cost và thời gian tải, đặc biệt hữu ích cho CMS content, configuration hoặc catalog API.

**Ví dụ:**
```http
GET /api/products/123
ETag: "v42"
```

Request sau:
```http
GET /api/products/123
If-None-Match: "v42"
```

Nếu dữ liệu chưa đổi:
```http
304 Not Modified
```

**Lưu ý:**
ETag phải phản ánh đúng version của representation, không chỉ timestamp ngẫu nhiên. Nếu response phụ thuộc language, user permission hoặc query parameter, cần đảm bảo cache validator không làm lộ hoặc reuse nhầm dữ liệu giữa các representation khác nhau.

### Tip 3 — Với Azure Blob Storage, ưu tiên upload trực tiếp từ client bằng SAS ngắn hạn khi file lớn

**Mẹo:**
Nếu browser/mobile upload file lớn, cân nhắc để backend phát SAS token giới hạn quyền và thời gian, sau đó client upload trực tiếp lên Blob Storage thay vì stream toàn bộ file qua API server.

**Tại sao hữu ích:**
Proxy file lớn qua backend làm tốn bandwidth hai lần, giữ connection lâu và tăng memory/CPU pressure nếu implementation buffer không đúng. Direct upload chuyển data plane sang Blob Storage trong khi backend vẫn giữ control plane như authorization, metadata và business validation.

**Ví dụ:**
```text
1. Client -> API: yêu cầu upload session
2. API kiểm tra quyền và tạo SAS chỉ có quyền Write cho blob cụ thể, hết hạn sau 10 phút
3. Client -> Blob Storage: upload trực tiếp
4. Client/API xác nhận completion và lưu metadata
```

**Lưu ý:**
Không phát SAS rộng cho cả container nếu chỉ cần một blob. Cần validate loại file, size, ownership và xử lý orphaned upload. SAS không thay thế authorization của business flow.

### Tip 4 — Trong Vue, dùng `key` ổn định theo identity để tránh state component bị gán nhầm

**Mẹo:**
Khi render danh sách bằng `v-for`, dùng `:key` dựa trên identity ổn định như database ID thay vì array index nếu item có thể reorder, insert hoặc delete.

**Tại sao hữu ích:**
Virtual DOM dùng `key` để xác định node/component nào đại diện cho cùng một item giữa hai lần render. Dùng index có thể khiến component state, input value hoặc focus bị giữ ở vị trí cũ nhưng gán sang dữ liệu mới sau reorder.

**Ví dụ:**
```vue
<UserRow
  v-for="user in users"
  :key="user.id"
  :user="user"
/>
```

Tránh:
```vue
<UserRow
  v-for="(user, index) in users"
  :key="index"
  :user="user"
/>
```

**Lưu ý:**
`key` phải unique trong cùng sibling list và ổn định qua các render. Đừng tạo `Math.random()` làm key; điều đó buộc framework coi component là mới mỗi lần và phá lợi ích reuse/state preservation.

### Tip 5 — Kiểm soát trace sampling dựa trên signal, không chỉ một tỷ lệ cố định

**Mẹo:**
Trong hệ thống có traffic lớn, thay vì giữ 100% distributed trace hoặc sample ngẫu nhiên một tỷ lệ duy nhất, cân nhắc policy ưu tiên giữ trace lỗi, latency cao hoặc route quan trọng.

**Tại sao hữu ích:**
Giữ mọi trace có thể tăng telemetry cost đáng kể, nhưng random sampling thấp có nguy cơ bỏ mất đúng trace của incident hiếm. Tail-based hoặc rule-based sampling giúp giữ signal có giá trị chẩn đoán cao hơn trong cùng budget observability.

**Ví dụ:**
```text
Giữ 100%:
- HTTP 5xx
- request > 2s
- checkout/payment route

Giữ 5%:
- request 2xx thông thường
```

Khi incident xảy ra, team vẫn có trace chi tiết cho failure path thay vì chỉ nhìn aggregate metric.

**Lưu ý:**
Sampling ở nhiều tầng không đồng bộ có thể làm trace bị mất span hoặc khó ghép. Luôn giữ metric tổng hợp độc lập với trace sampling; sampled trace không nên được dùng trực tiếp để suy ra chính xác error rate toàn hệ thống.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng áp dụng khi read và write có áp lực khác nhau

**Khái niệm:**
CQRS tách model/path xử lý command khỏi query khi hai phía có nhu cầu khác nhau về model, performance, consistency hoặc scaling. Nó không đồng nghĩa bắt buộc dùng message broker, Event Sourcing hay nhiều database.

**Vấn đề nó giải quyết:**
Một hệ thống transactional có write model giàu invariant nhưng dashboard cần projection phẳng, aggregate lớn hoặc scale đọc cao. Ép cả hai dùng cùng một model có thể làm domain model méo theo nhu cầu reporting hoặc query trở nên phức tạp.

**Ví dụ thực tế:**
```text
Write side:
Order aggregate
- kiểm tra invariant
- update transactionally

Read side:
OrderDashboardRow
- dữ liệu đã denormalize
- tối ưu cho filtering/sorting
```

Ở mức đơn giản, hai side vẫn có thể dùng cùng SQL database nhưng query model khác nhau.

**Trade-off:**
CQRS tăng freedom tối ưu read/write độc lập nhưng thêm mapping, duplication và có thể dẫn tới eventual consistency nếu dùng projection async. Với CRUD đơn giản, CQRS framework hóa toàn bộ request thường chỉ tăng ceremony.

**Middle → Senior insight:**
Middle developer cần phân biệt command, query và invariant mà không biến mọi handler thành boilerplate. Senior / Technical developer phải quyết định mức tách phù hợp dựa trên workload, consistency, team ownership và operational cost thay vì chọn CQRS chỉ vì kiến trúc “sạch”.

### Design 2 — Expand-and-Contract giúp database schema thay đổi mà không buộc deploy đồng thời

**Khái niệm:**
Expand-and-Contract là cách rollout schema theo nhiều bước để version cũ và mới của application cùng hoạt động trong giai đoạn deployment. Trước tiên thêm capability mới theo hướng backward-compatible, sau đó migrate traffic/data, cuối cùng mới xóa phần cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment, nhiều version app có thể chạy đồng thời. Nếu migration rename hoặc xóa column ngay khi code mới deploy, instance cũ có thể fail trước khi rollout hoàn tất hoặc khi cần rollback.

**Ví dụ thực tế:**
```text
Bước 1 - Expand:
- thêm column DisplayName nullable
- app mới ghi cả Name và DisplayName

Bước 2 - Migrate:
- backfill DisplayName
- chuyển read sang DisplayName

Bước 3 - Contract:
- ngừng ghi Name
- sau khi xác nhận không còn version cũ, xóa Name
```

**Trade-off:**
Cách này giảm deployment risk và hỗ trợ rollback tốt hơn nhưng tạo giai đoạn schema/logic tạm thời phức tạp hơn. Backfill lớn còn cần throttle và observability để không làm database quá tải.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible và hiểu thứ tự deploy. Senior / Technical developer phải thiết kế migration window, dual-write/read transition, rollback boundary và tiêu chí chứng minh column/contract cũ thực sự không còn được dùng.

### Design 3 — Rate limiting phải đặt theo resource cần bảo vệ, không chỉ theo API endpoint

**Khái niệm:**
Rate limiting giới hạn lượng work theo một dimension như user, tenant, IP, API key hoặc resource cost. Thiết kế tốt bắt đầu từ capacity hoặc abuse scenario cần bảo vệ thay vì áp cùng một con số cho mọi endpoint.

**Vấn đề nó giải quyết:**
Một endpoint search có thể tiêu CPU/Elasticsearch nhiều hơn endpoint health check hàng trăm lần. Nếu cùng dùng giới hạn `100 req/min`, hệ thống vẫn có thể bị overload bởi một loại request đắt dù tổng request count chưa lớn.

**Ví dụ thực tế:**
```text
/login
- limit theo IP + account để chống brute force

/search
- limit theo tenant và query cost

/export
- concurrency limit thấp vì giữ DB/CPU lâu
```

Trong multi-instance deployment, limiter có thể cần shared state hoặc gateway-level enforcement tùy consistency requirement.

**Trade-off:**
Rate limiting bảo vệ capacity và fairness nhưng policy quá chặt gây false rejection và trải nghiệm xấu. Distributed limiter chính xác hơn nhưng thêm coordination/latency; local limiter đơn giản hơn nhưng không đảm bảo quota toàn cluster tuyệt đối.

**Middle → Senior insight:**
Middle developer cần trả status/header phù hợp như `429 Too Many Requests` và test policy đúng key. Senior / Technical developer phải chọn dimension, algorithm, burst allowance, distributed consistency và quota dựa trên cost model thực tế của downstream resource.
