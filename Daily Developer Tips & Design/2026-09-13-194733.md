# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Stream dữ liệu lớn bằng `IAsyncEnumerable<T>` nhưng phải kiểm soát lifetime của `DbContext`

**Mẹo:**
Khi API hoặc background process cần xử lý nhiều record theo luồng, cân nhắc `IAsyncEnumerable<T>` để đọc từng phần thay vì materialize toàn bộ bằng `ToListAsync()`.

**Tại sao hữu ích:**
Streaming giảm peak memory và cho phép bắt đầu xử lý trước khi toàn bộ result được tải xong. Tuy nhiên với EF Core, query chỉ thực sự đọc dữ liệu khi enumeration diễn ra, nên `DbContext` và connection phải còn sống trong suốt quá trình đó.

**Ví dụ:**
```csharp
await foreach (var order in db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .AsAsyncEnumerable()
    .WithCancellation(ct))
{
    await ProcessAsync(order, ct);
}
```

**Lưu ý:**
Không trả một `IAsyncEnumerable<T>` rồi dispose `DbContext` trước khi consumer enumerate. Streaming cũng giữ database connection lâu hơn; với API rất chậm ở phía client, cần cân nhắc pagination hoặc buffer theo batch để không chiếm connection quá lâu.

### Tip 2 — Khi SQL Server deadlock, lấy deadlock graph trước khi thêm retry

**Mẹo:**
Nếu production xuất hiện deadlock, thu thập deadlock graph bằng Extended Events hoặc công cụ tương đương rồi xác định resource, lock mode và thứ tự truy cập trước khi chỉ thêm retry.

**Tại sao hữu ích:**
Retry có thể làm request thành công ở lần sau nhưng không loại bỏ root cause. Deadlock thường xuất hiện khi hai transaction khóa resource theo thứ tự khác nhau hoặc giữ lock quá lâu. Deadlock graph cung cấp evidence để biết transaction nào victim, statement nào giữ/chờ lock và object/index liên quan.

**Ví dụ:**
```text
Transaction A:
1. UPDATE Orders
2. UPDATE Inventory

Transaction B:
1. UPDATE Inventory
2. UPDATE Orders

=> hai transaction có thể chờ nhau theo vòng tròn
```

Giải pháp có thể là thống nhất thứ tự truy cập, rút ngắn transaction, thêm index để giảm phạm vi lock hoặc thay đổi isolation strategy phù hợp.

**Lưu ý:**
Không phải mọi blocking đều là deadlock. Deadlock bị SQL Server chủ động chọn victim và rollback; blocking có thể chỉ là chờ lock lâu. Retry chỉ nên áp dụng khi operation idempotent hoặc có semantics retry an toàn.

### Tip 3 — Build một artifact rồi promote qua các environment thay vì rebuild mỗi lần deploy

**Mẹo:**
Trong CI/CD, ưu tiên mô hình build once, deploy many: tạo một artifact bất biến, sau đó promote chính artifact đó qua test, staging và production.

**Tại sao hữu ích:**
Nếu mỗi environment tự build lại source, dependency resolution, tool version hoặc build-time configuration có thể tạo binary khác nhau. Khi production lỗi, bạn không còn chắc artifact đã được test có đúng artifact đang chạy hay không.

**Ví dụ:**
```text
Commit abc123
  -> Build
  -> artifact: webapp-abc123.zip
  -> Deploy Test
  -> Deploy Staging
  -> Deploy Production
```

Environment-specific configuration được inject lúc deploy/runtime thay vì compile khác nhau cho từng môi trường.

**Lưu ý:**
Không nhét secret hoặc environment-specific endpoint cứng vào artifact chỉ để đạt “immutability”. Build once hiệu quả nhất khi configuration được tách khỏi binary và artifact có version/hash rõ ràng để trace ngược về commit.

### Tip 4 — Với Elasticsearch deep pagination, dùng `search_after` thay vì tăng `from`

**Mẹo:**
Khi user hoặc batch process cần đi sâu qua hàng chục nghìn search result, cân nhắc `search_after` với sort key ổn định thay vì `from + size` ngày càng lớn.

**Tại sao hữu ích:**
Deep pagination bằng `from` buộc shard phải thu thập và giữ nhiều hit phía trước chỉ để bỏ chúng đi. Cost tăng theo offset và có thể làm heap/latency tăng mạnh. `search_after` tiếp tục từ sort value của page trước nên tránh phải bỏ qua toàn bộ kết quả cũ.

**Ví dụ:**
```json
{
  "size": 100,
  "sort": [
    { "createdAt": "desc" },
    { "_id": "asc" }
  ],
  "search_after": ["2026-09-13T10:15:00Z", "order-9821"]
}
```

**Lưu ý:**
Sort phải deterministic; thường cần tie-breaker như `_id`. `search_after` không phù hợp cho random page access kiểu “nhảy thẳng tới page 500”. Nếu cần snapshot nhất quán khi index thay đổi, cân nhắc Point in Time cùng `search_after`.

### Tip 5 — Canonical URL phải được tạo từ routing rule, không copy nguyên URL hiện tại

**Mẹo:**
Trong website/CMS có nhiều đường dẫn dẫn đến cùng một nội dung, sinh canonical URL từ route chuẩn hoặc content identity thay vì dùng nguyên `Request.Path` hiện tại.

**Tại sao hữu ích:**
Query tracking, alias cũ, filter hoặc nhiều route có thể tạo duplicate URL cho cùng nội dung. Canonical nhất quán giúp search engine hiểu URL ưu tiên và tránh index phân tán tín hiệu giữa các biến thể.

**Ví dụ:**
```text
Các URL truy cập được:
/products/red-shoe?utm_source=email
/sale/red-shoe
/products/red-shoe

Canonical:
https://example.com/products/red-shoe
```

Trong CMS, canonical nên dựa trên published canonical route/content link thay vì URL mà editor hoặc request tình cờ đi vào.

**Lưu ý:**
Canonical không thay thế redirect khi URL cũ thực sự phải biến mất. Cũng không canonical mọi variant về một page nếu nội dung khác đáng kể; sai canonical có thể làm search engine bỏ qua page hợp lệ.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic: chọn theo ownership của work, không theo “cần messaging”

**Khái niệm:**
Queue phù hợp khi một logical work item nên được một consumer xử lý. Topic + Subscription phù hợp khi cùng một event cần được nhiều consumer độc lập nhận theo fan-out.

**Vấn đề nó giải quyết:**
Nếu dùng queue cho domain event mà Billing, Analytics và Notification đều cần nhận, các consumer sẽ cạnh tranh và chỉ một bên nhận message. Ngược lại, dùng topic cho command xử lý duy nhất có thể tạo duplicate workflow không cần thiết.

**Ví dụ thực tế:**
```text
Command:
GenerateInvoice
-> Queue
-> một Invoice Worker xử lý

Event:
OrderPlaced
-> Topic
   -> Billing subscription
   -> Analytics subscription
   -> Notification subscription
```

**Trade-off:**
Queue đơn giản hơn cho work distribution và competing consumers. Topic tăng decoupling và fan-out nhưng thêm subscription lifecycle, filtering, monitoring và duplicate handling. Cả hai vẫn cần idempotency vì delivery thường là at-least-once.

**Middle → Senior insight:**
Middle developer cần phân biệt command với event và cấu hình consumer đúng semantics. Senior / Technical developer phải quyết định ownership, fan-out, failure isolation, replay, filtering và operational cost trước khi chọn queue hay topic.

### Design 2 — Authorization policy nên tập trung business permission, không rải `if (role == ...)` khắp codebase

**Khái niệm:**
Policy-based authorization gom điều kiện quyền truy cập thành requirement/handler hoặc một authorization boundary rõ, thay vì để controller, service và UI tự kiểm tra role theo cách riêng.

**Vấn đề nó giải quyết:**
Khi permission phức tạp hơn một role tĩnh, ví dụ “Manager chỉ sửa employee trong cùng department”, role check đơn thuần không đủ. Logic rải rác dễ lệch nhau và tạo lỗ hổng khi một endpoint mới quên kiểm tra điều kiện tương tự.

**Ví dụ thực tế:**
```text
Policy: CanEditEmployee
- user có permission Employee.Edit
- và employee.DepartmentId thuộc phạm vi user quản lý
```

API gọi authorization policy tại resource boundary thay vì tự ghép nhiều `if` theo từng endpoint.

**Trade-off:**
Policy tập trung giúp consistency và testability tốt hơn, nhưng framework authorization quá generic có thể che mất rule domain quan trọng. Với invariant business thực sự, validation vẫn cần nằm ở domain/application layer chứ không chỉ ở HTTP authorization layer.

**Middle → Senior insight:**
Middle developer cần tách Authentication, Authorization và validation, đồng thời gọi policy đúng resource. Senior / Technical developer phải xác định permission model, resource ownership, policy evaluation cost và nơi nào là security boundary so với domain invariant.

### Design 3 — Normalization vs Denormalization: tối ưu theo invariant và read pattern, không theo giáo điều

**Khái niệm:**
Normalization giảm duplication và bảo vệ consistency bằng cách tách dữ liệu thành các quan hệ có cấu trúc. Denormalization chủ động lưu dữ liệu lặp hoặc projection để phục vụ read pattern nhanh hơn.

**Vấn đề nó giải quyết:**
Một transactional model chuẩn hóa tốt có thể yêu cầu nhiều join để dựng dashboard hoặc search result. Ngược lại, denormalize trực tiếp vào source-of-truth table có thể khiến cùng một giá trị bị cập nhật ở nhiều nơi và drift theo thời gian.

**Ví dụ thực tế:**
```text
Transactional model:
Orders -> Customers -> Addresses

Read model cho dashboard:
OrderSummary {
  OrderId,
  CustomerName,
  Region,
  Total,
  Status
}
```

Projection có thể được rebuild từ source of truth thay vì ép mọi query dashboard join toàn bộ transactional schema.

**Trade-off:**
Normalization đơn giản hóa consistency nhưng có thể tăng query complexity và read cost. Denormalization cải thiện read performance nhưng thêm synchronization, storage và stale-data risk. Không nên denormalize chỉ vì một query “trông nhiều join”.

**Middle → Senior insight:**
Middle developer cần hiểu index/query plan trước khi thay đổi schema. Senior / Technical developer phải cân nhắc invariant, read/write ratio, consistency tolerance, rebuild strategy và ownership của derived data để chọn mức denormalization phù hợp.
