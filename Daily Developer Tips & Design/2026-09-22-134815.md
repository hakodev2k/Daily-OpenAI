# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` để shutdown `BackgroundService` đúng cách

**Mẹo:**
Trong `BackgroundService`, truyền `stoppingToken` xuyên suốt vòng lặp, delay và các I/O operations thay vì chỉ kiểm tra token ở đầu vòng lặp.

**Tại sao hữu ích:**
Khi host shutdown hoặc deployment thay instance, cancellation là tín hiệu để worker dừng nhận việc mới và thoát trong grace period. Nếu `Task.Delay`, EF Core query hoặc outbound HTTP không nhận token, process có thể giữ shutdown lâu hơn dự kiến và bị platform kill giữa side effect.

**Ví dụ:**
Một worker xử lý cleanup dùng `await Task.Delay(interval, stoppingToken)` và truyền cùng token vào `ToListAsync(stoppingToken)`. Khi shutdown xảy ra trong lúc chờ, delay kết thúc ngay thay vì giữ process thêm toàn bộ interval.

**Lưu ý:**
Cancellation không phải rollback tự động. Với operation đã tạo side effect, cần transaction/idempotency/checkpoint phù hợp; đồng thời phân biệt `OperationCanceledException` do shutdown với lỗi nghiệp vụ thực sự.

### Tip 2 — Kiểm tra EF Core change tracker khi update tạo SQL ngoài dự kiến

**Mẹo:**
Khi `SaveChanges` phát sinh nhiều `UPDATE` hoặc thay đổi quan hệ bất ngờ, inspect `ChangeTracker.DebugView` và entity states trước khi sửa SQL hoặc database.

**Tại sao hữu ích:**
EF Core tạo commands từ tracked graph và detected changes. Entity bị attach với state sai, graph được map lại từ DTO hoặc relationship fixup có thể khiến ORM coi nhiều properties/entities là modified dù business operation chỉ muốn đổi một field.

**Ví dụ:**
Endpoint đổi trạng thái order nhưng AutoMapper dựng lại cả graph rồi gọi `Update(order)`. Debug view cho thấy child entities đều `Modified`; thay vào đó load aggregate cần thiết và thay đúng state, hoặc attach entity rồi mark chính property cần update khi semantics cho phép.

**Lưu ý:**
Đừng tối ưu bằng cách mark properties thủ công nếu không hiểu concurrency/invariants. Với aggregate cần validation dựa trên state hiện tại, load đúng dữ liệu vẫn an toàn hơn một “partial update” mù.

### Tip 3 — Dùng covering index theo query shape, không theo danh sách columns của bảng

**Mẹo:**
Khi một read query quan trọng thường xuyên lookup theo cùng predicate/order và trả một số columns nhỏ, cân nhắc index có key columns phục vụ seek/sort và included columns phục vụ output.

**Tại sao hữu ích:**
Nếu database có thể đáp ứng query từ index mà không quay lại base table/clustered index cho từng row, logical reads có thể giảm đáng kể. Nhưng thứ tự key phải theo access pattern; thêm mọi column vào index chỉ làm index lớn và write đắt hơn.

**Ví dụ:**
Query lấy các pending jobs theo `Status`, `NextAttemptAt`, trả `Id` và `PayloadType`. Index key `(Status, NextAttemptAt)` cùng included columns cần thiết có thể phù hợp hơn một index riêng lẻ trên từng column.

**Lưu ý:**
Covering index không miễn phí: insert/update, storage và maintenance tăng. Xác nhận bằng actual execution plan và I/O metrics; đừng tạo index chỉ vì query text “trông giống” sẽ dùng nó.

### Tip 4 — Giới hạn kích thước request trước khi parse payload lớn

**Mẹo:**
Với upload hoặc JSON endpoint có khả năng nhận payload lớn, đặt request/body limits ở server/reverse proxy và validate metadata trước khi buffer/deserialize toàn bộ nội dung.

**Tại sao hữu ích:**
Một endpoint có validation nghiệp vụ tốt vẫn có thể bị memory/CPU pressure nếu framework phải đọc hàng trăm MB trước khi validation chạy. Giới hạn sớm giảm blast radius của accidental oversized requests và một số dạng resource-exhaustion attack.

**Ví dụ:**
API import catalogue giới hạn body phù hợp với use case, kiểm tra content type và streaming file thay vì `ReadToEndAsync` vào memory. Reverse proxy và ASP.NET Core cùng có limits nhất quán để request quá lớn bị từ chối trước processing sâu.

**Lưu ý:**
Limit quá thấp có thể phá client hợp lệ, còn chỉ cấu hình application layer có thể chưa đủ nếu upstream proxy đã buffer request. Cần kiểm tra toàn delivery path và trả lỗi rõ ràng như `413 Payload Too Large`.

### Tip 5 — Đo frontend long tasks khi UI lag dù API nhanh

**Mẹo:**
Nếu Network panel cho thấy API nhanh nhưng interaction vẫn giật, dùng browser Performance tooling để tìm long tasks, scripting và rendering work trên main thread thay vì tiếp tục tối ưu backend.

**Tại sao hữu ích:**
JavaScript parsing/execution, synchronous computation hoặc render quá nhiều nodes có thể chặn input hàng chục đến hàng trăm milliseconds. Backend latency thấp không đảm bảo responsive UI nếu main thread bị chiếm dụng.

**Ví dụ:**
Trang Vue nhận response trong 120 ms nhưng filter/sort 30.000 records và render toàn bộ table trên client tạo long task hơn 500 ms. Pagination/virtualization hoặc chuyển computation hợp lý giải quyết đúng bottleneck hơn cache API thêm lần nữa.

**Lưu ý:**
Đừng suy luận từ development build duy nhất; profiling nên dùng production-like build và realistic device/data. Web Worker cũng không tự giải quyết DOM rendering vì DOM vẫn thuộc main thread.

## 🧠 Software Design

### Design 1 — Queue hay Topic phụ thuộc semantics phân phối message

**Khái niệm:**
Queue thường biểu diễn một stream công việc nơi một message được một competing consumer xử lý; Topic + subscriptions biểu diễn publish/subscribe khi nhiều consumer groups độc lập cần nhận cùng logical event.

**Vấn đề nó giải quyết:**
Chọn sai primitive dễ tạo coupling. Nếu nhiều downstream cùng đọc một queue, chúng cạnh tranh và mỗi message chỉ tới một consumer; nếu dùng topic cho work queue đơn giản, infrastructure và vận hành có thể phức tạp không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` command đi vào queue để một billing worker xử lý. `OrderCompleted` event đi vào topic để Billing, Loyalty và Analytics có subscriptions riêng, mỗi bên retry/DLQ theo lifecycle của mình.

**Trade-off:**
Topic tăng khả năng fan-out và ownership độc lập nhưng thêm subscriptions, monitoring và duplicated processing cost. Queue đơn giản hơn cho work distribution nhưng không phù hợp khi nhiều capabilities đều phải quan sát cùng event.

**Middle → Senior insight:**
Middle developer cần hiểu delivery, retry, DLQ và idempotent processing của primitive đang dùng. Senior / Technical developer phải phân biệt command với event, ownership của consumer, replay/evolution requirements và chọn topology tối thiểu đáp ứng business semantics.

### Design 2 — Snapshot không phải source of truth mặc định

**Khái niệm:**
Snapshot/read projection lưu một representation đã tính trước để đọc nhanh, nhưng source of truth vẫn là state hoặc event history có authority rõ ràng. Snapshot là optimization có lifecycle và khả năng rebuild.

**Vấn đề nó giải quyết:**
Các màn hình/report phức tạp có thể quá đắt nếu mỗi request join/aggregate nhiều nguồn. Precomputed view giảm read latency, nhưng nếu coi bản sao là authoritative mà không thiết kế synchronization, hệ thống dễ có hai nơi cùng “đúng”.

**Ví dụ thực tế:**
Dashboard order lưu projection gồm customer summary, payment status và fulfillment status. Projection được cập nhật từ domain changes và có thể rebuild; command thay đổi order vẫn đi qua owner của transactional state thay vì update dashboard table trực tiếp.

**Trade-off:**
Projection cải thiện read performance và tách query model, đổi lại có eventual consistency, rebuild/backfill và operational complexity. Với query đơn giản, SQL trực tiếp có thể tốt hơn việc dựng cả projection pipeline.

**Middle → Senior insight:**
Middle developer cần không ghi ngược vào read projection và phải xử lý stale state rõ ràng. Senior / Technical developer phải quyết định freshness SLA, rebuild strategy, schema evolution và liệu lợi ích latency có thực sự đáng với consistency/operations cost.

### Design 3 — Capability-based authorization thay vì rải role checks khắp code

**Khái niệm:**
Authorization nên biểu diễn policy/capability gắn với hành động và resource, thay vì business code tự kiểm tra chuỗi role ở nhiều nơi. Role có thể là input vào policy nhưng không nhất thiết là contract authorization cuối cùng.

**Vấn đề nó giải quyết:**
Các check như `Admin || Manager || Support` bị copy khắp controllers sẽ khó thay đổi khi quyền phụ thuộc tenant, ownership, trạng thái resource hoặc claim. Logic phân tán tạo security drift giữa endpoints.

**Ví dụ thực tế:**
Thay vì mỗi endpoint tự kiểm tra `Manager`, application định nghĩa policy `CanApproveOrder`; authorization handler đánh giá identity, tenant và order state. Khi business thêm delegated approver, rule thay đổi ở boundary authorization thay vì sửa nhiều controllers.

**Trade-off:**
Policy-based design tăng consistency và testability nhưng có thể thành framework abstraction quá phức tạp nếu capability model không rõ. Resource-based checks cũng cần tránh tải dữ liệu lặp lại hoặc giấu business invariants vào security layer.

**Middle → Senior insight:**
Middle developer cần áp dụng policy ở đúng boundary và test cả allow/deny cases. Senior / Technical developer phải phân biệt authentication, coarse-grained role mapping, resource authorization và domain invariant; đồng thời thiết kế least privilege mà vẫn giữ model đủ đơn giản để audit.
