# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `PeriodicTimer` thay cho vòng lặp `Task.Delay` khi xây worker định kỳ

**Mẹo:**
Trong `BackgroundService` cần chạy công việc theo chu kỳ, cân nhắc `PeriodicTimer` để biểu diễn timer lifecycle rõ ràng và truyền `CancellationToken` từ host vào `WaitForNextTickAsync`.

**Tại sao hữu ích:**
Một vòng `while` với `Task.Delay` rất dễ quên cancellation hoặc xử lý shutdown không nhất quán. `PeriodicTimer` cho phép worker chờ tick theo asynchronous API và dừng tự nhiên khi application shutdown. Điều này đặc biệt hữu ích với housekeeping job, cache refresh hoặc polling nhẹ.

**Ví dụ:**
```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

    while (await timer.WaitForNextTickAsync(stoppingToken))
    {
        await RefreshCacheAsync(stoppingToken);
    }
}
```

**Lưu ý:**
`PeriodicTimer` không biến worker thành distributed scheduler. Nếu application có 5 replica, cả 5 có thể chạy cùng job. Với job phải chạy duy nhất một lần toàn hệ thống, cần leader election, scheduler bên ngoài hoặc idempotent/distributed coordination phù hợp. Ngoài ra, đừng giả định timer sẽ “bù” mọi tick bị bỏ lỡ khi một iteration chạy quá lâu.

### Tip 2 — EF Core projection giúp tránh tracking và materialization dữ liệu không cần thiết

**Mẹo:**
Với read endpoint chỉ cần vài field, project trực tiếp sang DTO bằng `Select` thay vì `Include` cả entity graph rồi map trong memory.

**Tại sao hữu ích:**
Projection cho EF Core cơ hội sinh SQL chỉ lấy các column cần thiết và thực hiện phần lớn shaping ở database. Điều này giảm network payload, materialization, allocation và nguy cơ vô tình load collection lớn. Với read-only DTO projection, change tracking entity thường cũng không cần thiết.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Where(x => x.Id == id)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.Customer.Name,
        x.Total,
        x.Items.Count))
    .SingleOrDefaultAsync(ct);
```

Thay vì `Include(x => x.Customer).Include(x => x.Items)` rồi tạo DTO sau khi toàn bộ graph đã được materialize.

**Lưu ý:**
Không giả định mọi expression C# đều translate tốt sang SQL. Kiểm tra generated SQL và execution plan với query quan trọng. Projection quá phức tạp cũng có thể tạo SQL khó tối ưu; đôi khi tách query hoặc dùng SQL chuyên biệt cho reporting sẽ rõ hơn.

### Tip 3 — Redis production: tránh `KEYS` trên keyspace lớn, dùng `SCAN` cho tác vụ khám phá

**Mẹo:**
Khi cần tìm key theo pattern trong Redis production, tránh `KEYS pattern` trên database lớn. Dùng `SCAN` theo cursor hoặc capability tương ứng của client để duyệt incremental.

**Tại sao hữu ích:**
`KEYS` phải quét toàn bộ keyspace trong một operation và có thể block event loop đủ lâu để latency của request bình thường tăng mạnh. `SCAN` chia công việc thành nhiều bước nhỏ, giảm thời gian block của từng lần xử lý.

**Ví dụ:**
```text
Nguy hiểm trên production lớn:
KEYS session:*

Phù hợp hơn cho maintenance tooling:
SCAN 0 MATCH session:* COUNT 500
```

Nếu application thường xuyên cần truy vấn “tất cả key của tenant X”, tốt hơn là thiết kế explicit index/set hoặc data model phục vụ access pattern đó thay vì biến key scan thành business query.

**Lưu ý:**
`SCAN` không cung cấp snapshot transactionally consistent; key có thể xuất hiện, biến mất hoặc được thấy theo semantics của iteration trong lúc dataset thay đổi. `COUNT` chỉ là hint, không phải số lượng tuyệt đối mỗi batch. Không nên chạy scan diện rộng trong hot request path.

### Tip 4 — File upload phải kiểm tra nội dung và giới hạn tài nguyên, không tin `Content-Type`

**Mẹo:**
Với ASP.NET Core endpoint nhận file, coi filename và `Content-Type` từ client là metadata không đáng tin cậy. Áp dụng size limit, allowlist loại file cần thiết, kiểm tra signature/content khi phù hợp và lưu file ngoài web root với tên do server tạo.

**Tại sao hữu ích:**
Attacker có thể gửi executable hoặc payload độc hại nhưng khai báo `image/png`. File cực lớn hoặc archive có tỷ lệ giải nén bất thường còn có thể gây disk/memory exhaustion. Validation phải bảo vệ cả security boundary lẫn resource boundary.

**Ví dụ:**
```text
POST /documents
1. authenticate + authorize
2. enforce request/file size
3. generate server-side storage name
4. inspect allowed content/signature
5. store vào quarantine/private storage
6. malware scan nếu threat model yêu cầu
7. chỉ publish sau khi validation hoàn tất
```

**Lưu ý:**
Magic-byte checking không chứng minh file hoàn toàn an toàn; nhiều format có cấu trúc phức tạp. Không nối trực tiếp `IFormFile.FileName` vào filesystem path. Với file lớn, ưu tiên streaming/direct-to-object-storage thay vì buffer toàn bộ trong memory.

### Tip 5 — Tối ưu LCP bằng cách ưu tiên hero image thay vì lazy-load mọi ảnh

**Mẹo:**
Nếu ảnh hero phía trên fold là Largest Contentful Paint candidate, đừng áp `loading="lazy"` máy móc. Đảm bảo browser phát hiện resource sớm, kích thước ảnh phù hợp và dùng responsive source/caching đúng cách.

**Tại sao hữu ích:**
Lazy-loading resource quan trọng có thể trì hoãn thời điểm browser bắt đầu fetch, làm LCP xấu dù backend trả HTML nhanh. Với CMS website, editor thường thay ảnh hero nên pipeline image resizing và metadata kích thước cần được thiết kế thay vì dựa vào ảnh gốc dung lượng lớn.

**Ví dụ:**
```html
<img
  src="/media/hero-1280.webp"
  srcset="/media/hero-640.webp 640w, /media/hero-1280.webp 1280w"
  sizes="100vw"
  width="1280"
  height="720"
  fetchpriority="high"
  alt="...">
```

Sau đó xác nhận bằng Lighthouse và browser DevTools network waterfall thay vì chỉ dựa vào markup.

**Lưu ý:**
Không đặt `fetchpriority="high"` cho nhiều ảnh; nếu mọi resource đều ưu tiên thì không còn ưu tiên thực sự. LCP cũng có thể bị chi phối bởi TTFB, render-blocking CSS/JS hoặc client-side rendering, nên phải đo toàn chuỗi trước khi kết luận ảnh là bottleneck.

## 🧠 Software Design

### Design 1 — Transactional Outbox nối database transaction với message publishing an toàn hơn dual-write

**Khái niệm:**
Transactional Outbox ghi business change và message/event cần publish vào cùng một local database transaction. Một publisher riêng đọc outbox và gửi message tới broker sau khi transaction đã commit.

**Vấn đề nó giải quyết:**
Flow `SaveChanges -> publish Service Bus` có failure window: database commit thành công nhưng process crash trước khi publish. Đảo thứ tự cũng không an toàn: message có thể được consumer xử lý trong khi database transaction sau đó rollback. Đây là dual-write problem giữa hai resource không cùng transaction.

**Ví dụ thực tế:**
```text
Transaction SQL:
1. UPDATE Orders SET Status = 'Paid'
2. INSERT Outbox(MessageId, Type, Payload, CreatedAt)
3. COMMIT

Outbox publisher:
4. đọc message chưa publish
5. gửi Azure Service Bus
6. đánh dấu published
```

Consumer vẫn cần idempotency vì publisher có thể gửi thành công rồi crash trước bước đánh dấu, dẫn tới publish lại.

**Trade-off:**
Outbox loại bỏ khoảng trống giữa business commit và việc ghi nhận intent publish, nhưng thêm table, polling/CDC, cleanup, monitoring và eventual delivery delay. Với application nhỏ không có cross-resource messaging requirement, thêm Outbox có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu database transaction không tự bao phủ message broker và phải xử lý duplicate delivery. Senior / Technical developer phải thiết kế ordering, retry, retention, publisher concurrency, observability và recovery semantics; đồng thời quyết định khi nào eventual consistency của Outbox phù hợp hơn synchronous integration đơn giản.

### Design 2 — Bulkhead giới hạn blast radius giữa các dependency hoặc workload

**Khái niệm:**
Bulkhead isolation chia capacity thành các vùng độc lập hoặc đặt concurrency limit riêng cho workload/dependency, để một thành phần chậm không tiêu hết tài nguyên chung của application.

**Vấn đề nó giải quyết:**
Một API gọi cả Payment và Recommendation service. Recommendation bắt đầu treo 20 giây; nếu request tới dependency này chiếm toàn bộ outbound connection/concurrency budget, payment flow quan trọng cũng có thể bị nghẽn dù Payment hoàn toàn khỏe.

**Ví dụ thực tế:**
```text
Payment outbound concurrency:       50
Recommendation outbound concurrency: 10

Recommendation bị timeout
-> tối đa 10 operation bị giữ
-> Payment vẫn còn capacity riêng
```

Isolation có thể nằm ở concurrency limiter, connection pool, queue, worker pool, process hoặc thậm chí service boundary tùy mức criticality.

**Trade-off:**
Bulkhead giảm cascading failure nhưng capacity bị chia nhỏ có thể làm utilization kém hơn và cấu hình sai có thể throttle workload khỏe. Quá nhiều pool/queue riêng còn tăng operational complexity. Cần kết hợp với timeout, backpressure và telemetry thay vì coi isolation là giải pháp độc lập.

**Middle → Senior insight:**
Middle developer cần nhận ra shared resource exhaustion là failure mode hệ thống, không chỉ lỗi của dependency. Senior / Solution-oriented engineer phải phân loại workload theo criticality, SLO và resource consumption để đặt isolation boundary phù hợp, thay vì tạo một pool riêng cho mọi integration.

### Design 3 — Database constraint là lớp bảo vệ invariant cuối cùng cho dữ liệu cạnh tranh

**Khái niệm:**
Một số invariant có thể và nên được enforce tại database boundary bằng `UNIQUE`, `FOREIGN KEY`, `CHECK` hoặc constraint tương đương, ngay cả khi application đã validate trước đó.

**Vấn đề nó giải quyết:**
Hai request đồng thời đều chạy `SELECT` và thấy email chưa tồn tại, sau đó cùng `INSERT`. Validation ở application có race window; chỉ constraint atomic tại storage boundary mới đảm bảo không có hai row vi phạm uniqueness.

**Ví dụ thực tế:**
```sql
CREATE UNIQUE INDEX UX_Users_NormalizedEmail
ON Users (NormalizedEmail);
```

Application vẫn có thể check trước để trả UX tốt, nhưng phải xử lý unique-constraint violation khi race thực sự xảy ra.

**Trade-off:**
Constraint tăng data integrity và bảo vệ cả dữ liệu được ghi từ nhiều code path, nhưng không biểu diễn thuận tiện mọi business invariant phức tạp. Constraint sai hoặc quá rộng có thể chặn workflow hợp lệ; distributed invariant xuyên nhiều database lại cần thiết kế khác.

**Middle → Senior insight:**
Middle developer cần biết application validation không thay thế database integrity và phải map constraint violation thành behavior phù hợp. Senior / Technical developer phải quyết định invariant nào thuộc storage boundary, invariant nào thuộc domain/workflow, cách migration dữ liệu hiện hữu trước khi thêm constraint và cách giữ correctness khi hệ thống được phân tán qua nhiều data store.
