# Daily Developer Tips & Design — 2026-09-18

## 🛠 Developer Tips & Tricks

### Tip 1 — `ConfigureAwait(false)` không phải tối ưu mặc định cho ASP.NET Core

**Mẹo:**
Trong application code ASP.NET Core hiện đại, đừng rải `ConfigureAwait(false)` chỉ vì quy tắc từ .NET Framework cũ. Hiểu `SynchronizationContext` của môi trường trước khi áp dụng.

**Tại sao hữu ích:**
ASP.NET Core không cài request `SynchronizationContext` kiểu ASP.NET cổ điển, nên continuation sau `await` thường không cần quay lại request thread cụ thể. Việc thêm `ConfigureAwait(false)` khắp business code thường không mang lại lợi ích đáng kể nhưng làm code nhiễu và dễ tạo quy ước sai.

**Ví dụ:**
```csharp
var order = await db.Orders
    .SingleAsync(x => x.Id == id, cancellationToken);
```
Trong reusable library có thể có lý do riêng để dùng `ConfigureAwait(false)`, nhưng đó là quyết định của library boundary chứ không phải ritual của mọi controller/service.

**Lưu ý:**
Đừng suy ra rằng context capture không bao giờ quan trọng. UI frameworks và một số legacy environments vẫn có synchronization context; migration từ .NET Framework cần đánh giá behavior cụ thể.

### Tip 2 — PostgreSQL index có thể vô dụng nếu predicate không sargable

**Mẹo:**
Khi query có index nhưng vẫn sequential scan, kiểm tra expression trên indexed column trước khi tạo thêm index.

**Tại sao hữu ích:**
Function/cast đặt lên column có thể khiến planner không dùng B-tree index thông thường theo access pattern mong muốn. Vấn đề nằm ở hình dạng predicate chứ không nhất thiết ở thiếu index.

**Ví dụ:**
```sql
-- Có thể khó tận dụng index trên created_at
WHERE DATE(created_at) = DATE '2026-09-18'

-- Range predicate thường phù hợp hơn
WHERE created_at >= TIMESTAMP '2026-09-18 00:00:00'
  AND created_at <  TIMESTAMP '2026-09-19 00:00:00'
```
Xác nhận bằng `EXPLAIN (ANALYZE, BUFFERS)` trên dữ liệu đại diện.

**Lưu ý:**
Expression index có thể hợp lý nếu expression đó là access pattern ổn định. Đừng rewrite query chỉ để ép index khi sequential scan thực sự rẻ hơn vì query trả phần lớn bảng.

### Tip 3 — Cosmos DB: đo RU theo query shape, không chỉ số document trả về

**Mẹo:**
Khi Cosmos DB endpoint đắt bất thường, ghi nhận request charge và partition behavior cho từng query thay vì suy luận chi phí từ số item trong response.

**Tại sao hữu ích:**
Hai query cùng trả 10 documents có thể tiêu tốn RU rất khác nếu một query là point read/partition-targeted còn query kia fan-out qua nhiều partitions hoặc scan index rộng.

**Ví dụ:**
Một lookup biết cả `id` và partition key nên ưu tiên point read. Với search API, telemetry nên lưu query category, RU charge và latency để phát hiện access pattern làm cost tăng sau release.

**Lưu ý:**
Đừng chọn partition key chỉ để tối ưu một query hiện tại. Phải cân bằng cardinality, distribution, transaction scope, hot-partition risk và các access patterns dài hạn.

### Tip 4 — `git rerere` hữu ích khi phải giải cùng conflict nhiều lần

**Mẹo:**
Với branch dài hoặc chuỗi rebase/cherry-pick thường lặp lại cùng conflict, cân nhắc bật `git rerere` để Git ghi nhớ resolution đã áp dụng.

**Tại sao hữu ích:**
Git có thể nhận diện conflict shape đã gặp và tái áp dụng resolution, giảm thao tác thủ công trong migration branch hoặc backport nhiều release lines.

**Ví dụ:**
```bash
git config --global rerere.enabled true
```
Sau khi bạn resolve và commit conflict lần đầu, lần conflict tương tự sau có thể được Git pre-resolve để bạn review lại.

**Lưu ý:**
Luôn review diff sau khi rerere áp dụng resolution. Code xung quanh có thể đã thay đổi semantic dù conflict text trông giống nhau; automation không thay thế verification.

### Tip 5 — App Service 5xx sau deployment: so deployment marker trước khi scale

**Mẹo:**
Khi Azure App Service tăng 5xx ngay sau release, correlate error rate với deployment marker, startup logs, configuration diff và dependency telemetry trước khi tăng instance count.

**Tại sao hữu ích:**
Nếu lỗi do missing configuration, migration mismatch hoặc startup dependency, scale-out chỉ nhân bản cùng lỗi. Timeline deployment là evidence mạnh để thu hẹp regression nhanh.

**Ví dụ:**
Triệu chứng: 5xx tăng từ 17:02; deployment hoàn tất 17:01. Kiểm tra Application Insights exceptions theo version, startup logs và App Settings/slot settings khác biệt; rollback nếu regression được xác nhận và blast radius lớn.

**Lưu ý:**
Correlation không tự động chứng minh causation. External dependency cũng có thể lỗi cùng thời điểm; dùng traces và version dimensions để xác nhận trước khi kết luận.

## 🧠 Software Design

### Design 1 — CQRS chỉ khi read/write có áp lực khác nhau

**Khái niệm:**
CQRS tách model hoặc path xử lý command và query khi hai phía có nhu cầu khác biệt đáng kể; nó không bắt buộc phải có hai databases hay event sourcing.

**Vấn đề nó giải quyết:**
Một domain có write model bảo vệ invariant phức tạp nhưng read side cần projection tối ưu cho dashboard/search. Ép cùng một model phục vụ cả hai có thể làm cả domain lẫn query khó duy trì.

**Ví dụ thực tế:**
Order aggregate xử lý transition `Pending → Paid → Fulfilled`, trong khi operations dashboard chỉ cần read model phẳng gồm status, customer, SLA và timestamps. Query side có thể dùng projection riêng mà vẫn cùng database nếu scale chưa yêu cầu tách storage.

**Trade-off:**
CQRS làm model rõ theo intent và cho phép tối ưu độc lập, nhưng thêm mapping, synchronization và cognitive load. Với CRUD đơn giản, service/query methods tách rõ thường đủ.

**Middle → Senior insight:**
Middle developer cần phân biệt command thay đổi state với query đọc state. Senior / Technical developer phải chứng minh áp lực read/write thực tế trước khi thêm CQRS, và chọn mức tách nhỏ nhất giải quyết được vấn đề.

### Design 2 — Cache consistency phải bắt đầu từ business tolerance

**Khái niệm:**
Cache không chỉ là performance layer; mỗi cache tạo một bản sao dữ liệu với độ trễ consistency. Thiết kế cache cần xác định dữ liệu được phép stale bao lâu và failure nào business chấp nhận.

**Vấn đề nó giải quyết:**
Team thường đặt TTL tùy ý như 5 hoặc 30 phút mà không liên hệ với semantics. Điều đó có thể ổn cho CMS content nhưng nguy hiểm cho inventory, permissions hoặc pricing.

**Ví dụ thực tế:**
Product description có thể chấp nhận stale vài phút. Authorization decision nhạy cảm có thể cần TTL rất ngắn, version-based invalidation hoặc không cache ở layer đó. Price promotion có thể dùng explicit invalidation khi publish.

**Trade-off:**
TTL dài tăng hit ratio và giảm backend load nhưng tăng stale window. Invalidation chủ động cải thiện freshness nhưng thêm coupling và failure paths. Stronger consistency thường đổi lấy latency, complexity hoặc availability.

**Middle → Senior insight:**
Middle developer cần hiểu TTL/invalidation và không cache dữ liệu tùy tiện. Senior / Technical developer phải biến business freshness requirement thành cache policy, fallback behavior và observability thay vì chọn TTL theo cảm giác.

### Design 3 — Deployment strategy phải phù hợp khả năng rollback của schema

**Khái niệm:**
Blue/green hoặc rolling deployment chỉ an toàn khi application versions và database schema có khoảng tương thích đủ để old/new code cùng hoạt động trong giai đoạn chuyển tiếp.

**Vấn đề nó giải quyết:**
Code rollback nhanh không giúp ích nếu deployment vừa rename/drop column mà phiên bản cũ cần. Database trở thành điểm khóa khiến chiến lược release tưởng là zero-downtime thực tế không rollback được.

**Ví dụ thực tế:**
Thay vì rename trực tiếp `CustomerName` thành `DisplayName`, release đầu thêm column mới và code tương thích hai schema; backfill; chuyển reads/writes; chỉ drop column cũ ở release sau khi không còn consumer phụ thuộc.

**Trade-off:**
Compatibility window làm migration nhiều bước và giữ technical debt tạm thời, nhưng giảm blast radius và cho rollback thực tế. Direct breaking migration đơn giản hơn trong maintenance window nhỏ nơi downtime được chấp nhận.

**Middle → Senior insight:**
Middle developer cần viết migration và application code backward-compatible trong rollout. Senior / Technical developer phải thiết kế release sequence dựa trên deployment topology, rollback objective, data migration cost và thời gian coexistence giữa versions.
