# Daily Developer Tips & Design — 2026-09-25

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded Channel để tạo backpressure cho background pipeline

**Mẹo:**
Khi producer tạo work nhanh hơn consumer xử lý, ưu tiên `Channel<T>` có bounded capacity thay vì đẩy vô hạn item vào memory. Chọn `FullMode` theo semantics nghiệp vụ: chờ, bỏ item cũ, bỏ item mới hoặc từ chối write.

**Tại sao hữu ích:**
Unbounded queue che giấu overload cho đến khi memory tăng, GC pressure cao và process mất ổn định. Bounded channel biến giới hạn tài nguyên thành tín hiệu rõ: producer phải chậm lại hoặc hệ thống phải có policy xử lý overload.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, cancellationToken);
```
Một `BackgroundService` đọc từ `channel.Reader.ReadAllAsync(stoppingToken)` và xử lý theo throughput thực tế của downstream dependency.

**Lưu ý:**
In-memory `Channel<T>` không bền vững qua process restart và không thay thế message broker khi cần durability, retry độc lập hoặc multi-instance coordination. Capacity cũng phải được đo theo workload, không chọn tùy ý.

### Tip 2 — Khi SQL query đột nhiên chậm, kiểm tra statistics và execution plan trước khi thêm index

**Mẹo:**
Nếu cùng query từng nhanh nhưng bỗng chậm sau khi dữ liệu tăng hoặc phân bố thay đổi, so actual execution plan, estimated rows với actual rows và tình trạng statistics trước khi tạo index mới.

**Tại sao hữu ích:**
Optimizer chọn join strategy, access path và memory grant dựa trên cardinality estimate. Statistics không phản ánh phân bố hiện tại có thể khiến estimate sai lớn, dẫn tới scan, lookup hoặc join strategy tốn kém dù index cần thiết đã tồn tại.

**Ví dụ:**
Một query dự đoán 100 rows nhưng thực tế trả 800.000 rows. Thay vì lập tức thêm index thứ sáu cho bảng, kiểm tra plan, statistics freshness, parameter sensitivity và workload trước/sau bằng Query Store hoặc công cụ tương đương.

**Lưu ý:**
Không chạy update statistics hoặc rebuild index như “thuốc chữa mọi slow query”. Regression cũng có thể đến từ blocking, parameter-sensitive plan, I/O, data growth hoặc query change; cần evidence trước khi can thiệp production.

### Tip 3 — Chống Redis cache stampede bằng single-flight có giới hạn

**Mẹo:**
Khi một hot key hết TTL, tránh để hàng trăm request cùng lúc query database rồi cùng rebuild cache. Dùng request coalescing/single-flight trong instance hoặc distributed coordination khi thật sự cần, kết hợp TTL jitter.

**Tại sao hữu ích:**
Cache miss đồng loạt có thể chuyển traffic burst trực tiếp xuống database, làm dependency chậm hơn và kéo dài vòng miss. Đây là failure amplification: cache vốn giảm tải lại khiến backend nhận spike đúng lúc key hết hạn.

**Ví dụ:**
Product catalog có key `catalog:tenant-42` được đọc hàng nghìn lần/phút. Khi cache miss, một execution load dữ liệu; các request cùng instance chờ cùng task. TTL thêm jitter nhỏ để nhiều hot keys không hết hạn đúng một thời điểm.

**Lưu ý:**
Distributed lock không miễn phí và lock sai có thể tạo bottleneck mới. Với dữ liệu chấp nhận stale, stale-while-revalidate thường đơn giản hơn; luôn định nghĩa behavior khi Redis hoàn toàn unavailable.

### Tip 4 — File upload phải xác thực nội dung và giới hạn resource, không chỉ extension

**Mẹo:**
Với ASP.NET Core upload endpoint, giới hạn request/file size, tạo server-side filename, lưu ngoài web root khi phù hợp và kiểm tra content theo policy thay vì tin `.jpg`, `Content-Type` hoặc tên file từ client.

**Tại sao hữu ích:**
Extension và MIME header đều do client cung cấp. Upload thiếu kiểm soát có thể dẫn tới resource exhaustion, path traversal, stored malicious content hoặc file được phục vụ lại với content type nguy hiểm.

**Ví dụ:**
API nhận avatar qua stream, reject file vượt quota, xác minh magic bytes cho format được hỗ trợ, sinh object key bằng GUID và lưu Blob Storage private. Client chỉ nhận identifier/URL được cấp quyền thay vì quyết định filesystem path.

**Lưu ý:**
Magic-byte validation không phải malware scanning. Với tài liệu từ nguồn không tin cậy, threat model có thể yêu cầu quarantine, scanning và Content-Disposition/CSP phù hợp. Không buffer file lớn toàn bộ vào memory nếu không cần.

### Tip 5 — Dùng browser Network waterfall để tìm frontend latency trước khi tối ưu component

**Mẹo:**
Khi Vue.js/React.js page “cảm giác chậm”, mở browser DevTools và phân tích waterfall: request nào bắt đầu muộn, request nào nối tiếp không cần thiết, payload nào lớn và main resource nào chặn rendering.

**Tại sao hữu ích:**
Frontend latency thường là tổng của network sequencing, backend latency, bundle execution và rendering. Nếu component mount rồi mới gọi API A, sau A mới biết để gọi B dù hai request độc lập, micro-optimize render không giải quyết critical path.

**Ví dụ:**
Trang dashboard gọi profile 300 ms, sau đó mới gọi permissions 250 ms và metrics 600 ms. Nếu permissions/metrics không phụ thuộc profile, khởi chạy song song có thể giảm critical path; trace backend tiếp tục xác định 600 ms của metrics nằm ở SQL hay application.

**Lưu ý:**
Không parallelize mọi request máy móc: có dependency thực, browser connection constraints và backend burst cost. Cũng tránh bundle splitting quá nhỏ khiến số request và orchestration overhead tăng.

## 🧠 Software Design

### Design 1 — Saga và compensating action cho workflow không thể dùng một transaction

**Khái niệm:**
Saga chia một business workflow xuyên nhiều consistency boundaries thành các local transactions; khi bước sau thất bại, hệ thống thực hiện compensating action phù hợp thay vì cố giữ một distributed ACID transaction dài.

**Vấn đề nó giải quyết:**
Checkout có thể cần tạo order, reserve inventory và authorize payment ở các service khác nhau. Không có một database transaction đơn giản bao phủ toàn bộ, và partial failure là trạng thái bình thường phải được thiết kế.

**Ví dụ thực tế:**
Order được tạo ở trạng thái `Pending`; Inventory reserve thành công nhưng payment bị từ chối. Workflow phát lệnh release reservation rồi chuyển order sang `PaymentFailed`. Nếu compensation cũng lỗi, trạng thái được retry/đưa vào operational queue thay vì giả định rollback đã xảy ra.

**Trade-off:**
Saga tránh distributed transaction coupling và cho phép service ownership độc lập, nhưng thêm eventual consistency, intermediate states, idempotency, retry và observability phức tạp. Với dữ liệu cùng một database/boundary, local transaction thường đơn giản và an toàn hơn.

**Middle → Senior insight:**
Middle developer cần viết step/compensation idempotent và xử lý duplicate/retry đúng. Senior / Technical developer phải xác định consistency boundary, irreversible side effects, timeout/recovery policy và khi nào nên giữ capability trong cùng transaction thay vì đưa Saga vào quá sớm.

### Design 2 — Modular Monolith trước khi tách Microservices theo deployment pressure thực

**Khái niệm:**
Modular Monolith giữ một deployable application nhưng áp boundary rõ giữa các business modules. Microservices đưa một số boundary đó thành process/deployment/network boundary độc lập khi autonomy hoặc scaling thực sự cần thiết.

**Vấn đề nó giải quyết:**
Một monolith không có module boundaries dễ trở thành tightly coupled codebase; nhưng tách service quá sớm biến method calls thành network calls và đưa distributed failure, observability, deployment, data ownership vào hệ thống trước khi có lợi ích tương xứng.

**Ví dụ thực tế:**
CRM có Sales, Billing và Support modules với contracts rõ, không truy cập bảng nội bộ của nhau tùy tiện. Chỉ khi Billing cần release cadence, compliance boundary hoặc scale profile khác rõ rệt, team mới đánh giá tách module đó thành service.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, transaction và local debugging nhưng đòi hỏi discipline để boundary không bị phá. Microservices tăng independent deployment/scaling nhưng thêm network latency, eventual consistency, platform cost và cross-team operational ownership.

**Middle → Senior insight:**
Middle developer cần tôn trọng module API và dependency direction. Senior / Technical developer phải dùng change coupling, team ownership, scaling, reliability và deployment constraints làm bằng chứng; số lượng project hoặc “hệ thống lớn” không tự động là lý do để chọn Microservices.

### Design 3 — Security boundary phải theo resource ownership, không chỉ theo role name

**Khái niệm:**
Authorization design nên kiểm tra cả capability của principal và quan hệ với resource/tenant cụ thể. Role như `Manager` thường chỉ là một phần của quyết định, không phải toàn bộ policy.

**Vấn đề nó giải quyết:**
Một user có role `Manager` của tenant A không nên sửa employee của tenant B. Endpoint chỉ kiểm tra `[Authorize(Roles = "Manager")]` có thể đúng về authentication nhưng sai về object-level authorization.

**Ví dụ thực tế:**
`PUT /tenants/{tenantId}/employees/{id}` xác minh caller có permission `Employee.Edit` và resource thuộc tenant caller được phép quản lý. Data query cũng scope theo tenant để giảm khả năng truy xuất object ngoài boundary trước khi authorization hoàn tất.

**Trade-off:**
Resource-based/policy-based authorization diễn đạt least privilege tốt hơn nhưng cần policy model, test matrix và ownership semantics rõ. Nhồi mọi rule vào controller lại làm logic phân tán; abstraction quá generic thì khó audit và hiểu.

**Middle → Senior insight:**
Middle developer cần phân biệt Authentication, role/claim và resource authorization, đồng thời test negative paths. Senior / Technical developer phải xác định trust/tenant boundaries, centralize policy hợp lý, thiết kế least privilege và đánh giá cách authorization được enforce nhất quán qua API, background jobs và internal services.
