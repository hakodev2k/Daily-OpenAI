# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IOptionsMonitor<T>` khi configuration cần thay đổi trong runtime

**Mẹo:**
Trong ASP.NET Core, nếu một service singleton cần đọc configuration có thể thay đổi sau khi application đã start, cân nhắc `IOptionsMonitor<T>` thay vì inject `IOptions<T>` rồi giữ snapshot cố định.

**Tại sao hữu ích:**
`IOptions<T>` phù hợp với cấu hình gần như immutable trong lifetime của process. `IOptionsMonitor<T>` cung cấp giá trị hiện tại và callback thay đổi, giúp feature flag, throttling threshold hoặc integration setting có thể cập nhật mà không buộc restart toàn app.

**Ví dụ:**
```csharp
public sealed class PricingClient
{
    private readonly IOptionsMonitor<PricingOptions> _options;

    public PricingClient(IOptionsMonitor<PricingOptions> options)
        => _options = options;

    public TimeSpan GetTimeout()
        => TimeSpan.FromSeconds(_options.CurrentValue.TimeoutSeconds);
}
```

**Lưu ý:**
Dynamic reload không đồng nghĩa mọi dependency sẽ tự reconfigure an toàn. Với connection pool, `HttpClient` handler hoặc object có lifecycle riêng, thay option có thể cần recreate component thay vì chỉ đọc giá trị mới.

### Tip 2 — Khi EF Core query chậm, kiểm tra cardinality explosion trước khi thêm index

**Mẹo:**
Nếu một query dùng nhiều `Include` trên collection navigation và response đột nhiên rất lớn, kiểm tra số row SQL thực tế được materialize trước khi tối ưu bằng index.

**Tại sao hữu ích:**
Nhiều collection join có thể nhân số row trung gian theo kiểu Cartesian explosion. Một aggregate chỉ có 100 entity thực tế vẫn có thể khiến database trả hàng chục nghìn row để EF Core ghép lại trong memory.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Payments)
    .Include(x => x.Shipments)
    .SingleAsync(x => x.Id == id, cancellationToken);
```

Nếu mỗi order có 20 lines, 5 payments và 4 shipments, join có thể tạo khoảng `20 x 5 x 4 = 400` row cho một order. Có thể cân nhắc projection hoặc `AsSplitQuery()` tùy workload.

**Lưu ý:**
`AsSplitQuery()` giảm row duplication nhưng tăng database round trip. Không nên bật mặc định cho mọi query; đo latency, payload và transaction consistency requirement trước.

### Tip 3 — Với Elasticsearch, tách `filter` khỏi full-text `query` để tránh scoring không cần thiết

**Mẹo:**
Dùng `filter` cho điều kiện exact-match như status, tenant, category hoặc date range; chỉ dùng full-text `query` cho field thực sự cần relevance scoring.

**Tại sao hữu ích:**
Filter context không cần tính score và phù hợp với structured constraints. Trộn mọi điều kiện vào scoring query làm search khó tune hơn và tiêu tốn tài nguyên cho công việc không tạo giá trị.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless headphones" } }
      ],
      "filter": [
        { "term": { "status": "published" } },
        { "range": { "price": { "lte": 200 } } }
      ]
    }
  }
}
```

**Lưu ý:**
Đừng dùng `term` query trên analyzed text field rồi kỳ vọng behavior như exact keyword. Mapping phải phân biệt rõ `text` và `keyword` theo access pattern.

### Tip 4 — Dùng `git bisect` khi regression xuất hiện trong một khoảng commit lớn

**Mẹo:**
Khi production bug được biết là không tồn tại ở một commit cũ nhưng xuất hiện ở HEAD, dùng `git bisect` để tìm commit đầu tiên gây regression thay vì đọc tuần tự hàng chục diff.

**Tại sao hữu ích:**
`git bisect` dùng binary search, nên khoảng 128 commit chỉ cần khoảng 7 lần đánh dấu good/bad nếu test cho kết quả rõ ràng.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v4.2.0
```

Sau mỗi checkout tự động, chạy test hoặc reproduction script rồi đánh dấu:
```bash
git bisect good
# hoặc
git bisect bad
```

**Lưu ý:**
Bisect chỉ đáng tin khi reproduction deterministic. Nếu test flaky hoặc environment thay đổi theo commit, kết quả có thể trỏ sai root cause.

### Tip 5 — Với JWT, validate `issuer`, `audience` và signing key chứ không chỉ signature

**Mẹo:**
Khi cấu hình JWT Bearer authentication, đảm bảo token được kiểm tra đúng issuer, audience, lifetime và signing key theo trust boundary của API.

**Tại sao hữu ích:**
Một token có chữ ký hợp lệ nhưng được cấp cho application khác hoặc tenant khác vẫn có thể không hợp lệ với API hiện tại. Signature chỉ chứng minh token do một key đáng tin ký, không tự chứng minh token được phát hành cho đúng resource.

**Ví dụ:**
```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters.ValidateIssuer = true;
        options.TokenValidationParameters.ValidateAudience = true;
        options.TokenValidationParameters.ValidateLifetime = true;
    });
```

**Lưu ý:**
Đừng tự parse JWT rồi đọc claim để authorize trước khi middleware hoàn tất validation. Với multi-tenant hoặc nhiều identity provider, issuer/audience policy cần thiết kế rõ thay vì mở rộng wildcard tùy tiện.

## 🧠 Software Design

### Design 1 — Repository abstraction chỉ nên tồn tại khi nó che giấu một boundary có giá trị

**Khái niệm:**
Repository Pattern hữu ích khi application cần một abstraction ổn định trước persistence concern thực sự khác biệt, nhưng EF Core `DbContext` đã cung cấp Unit of Work và repository-like behavior cơ bản.

**Vấn đề nó giải quyết:**
Nếu mọi query đều bị bọc qua generic repository chỉ để gọi `GetAll`, `Find` và `Update`, abstraction không che giấu complexity mà chỉ chuyển API của EF Core sang một API ít expressive hơn.

**Ví dụ thực tế:**
Một `OrderRepository` có thể có giá trị nếu nó encapsulate business-specific persistence như:
```text
LoadAggregateForCheckout(orderId)
FindOrdersRequiringFraudReview()
```

Ngược lại, `IGenericRepository<T>.GetAll()` thường chỉ tạo thêm indirection rồi cuối cùng vẫn expose `IQueryable` hoặc thiếu khả năng projection.

**Trade-off:**
Repository chuyên biệt có thể giữ persistence logic nhất quán và cô lập boundary. Generic repository thêm test seam nhưng dễ tạo abstraction leak, duplicate EF Core feature và làm query optimization khó hơn.

**Middle → Senior insight:**
Middle developer cần biết dùng `DbContext` trực tiếp không phải anti-pattern tự động. Senior / Technical developer phải xác định abstraction nào thực sự giảm coupling, abstraction nào chỉ tăng code, và impact lên query performance, testing và maintainability.

### Design 2 — Synchronous API vs asynchronous messaging cho third-party integration

**Khái niệm:**
Synchronous integration giữ caller chờ kết quả trực tiếp; asynchronous messaging tách caller khỏi thời điểm xử lý thực tế bằng queue hoặc broker.

**Vấn đề nó giải quyết:**
Một external CRM hoặc payment-adjacent service có latency không ổn định có thể làm request path của application trở nên mong manh nếu business flow không thực sự cần kết quả ngay lập tức.

**Ví dụ thực tế:**
```text
User updates profile
-> save local transaction
-> publish CustomerProfileChanged
-> integration worker syncs to CRM
```

Nếu CRM fail, retry có thể diễn ra độc lập mà user không phải chờ request 10 giây.

**Trade-off:**
Async messaging tăng resilience và giảm temporal coupling nhưng mang theo eventual consistency, retry, duplicate processing và observability complexity. Synchronous call đơn giản hơn khi caller thực sự cần kết quả ngay để quyết định transaction hiện tại.

**Middle → Senior insight:**
Middle developer cần xử lý timeout, retry và idempotency đúng với integration style. Senior / Technical developer phải phân biệt business dependency thật sự synchronous với dependency chỉ đang synchronous vì implementation hiện tại, rồi cân nhắc UX, consistency, operational cost và failure recovery.

### Design 3 — Separate write model và read projection khi query pressure khác domain model

**Khái niệm:**
Không nhất thiết áp dụng full CQRS, nhưng có thể giữ write model giàu invariant và tạo read projection riêng tối ưu cho screen/report có query shape khác biệt.

**Vấn đề nó giải quyết:**
Một domain model tốt cho transaction thường không phải model tốt nhất cho dashboard. Ép UI đọc trực tiếp aggregate phức tạp dễ tạo `Include` sâu, N+1 hoặc mapping logic lặp lại.

**Ví dụ thực tế:**
```text
Write side:
Order aggregate
- Lines
- Payment state
- Shipping rule

Read side:
OrderSummary
- OrderNumber
- CustomerName
- Total
- PaymentStatus
- ShipmentStatus
```

`OrderSummary` có thể được projection trực tiếp từ SQL/EF Core query mà không cần materialize toàn aggregate.

**Trade-off:**
Read projection giảm coupling với domain object và cải thiện query performance, nhưng tạo thêm model và mapping cần giữ nhất quán. Nếu read side được materialize riêng, hệ thống còn phải quản lý synchronization và eventual consistency.

**Middle → Senior insight:**
Middle developer cần phân biệt query DTO với domain entity và tránh dùng entity làm API contract mặc định. Senior / Technical developer phải chọn mức separation vừa đủ: projection trực tiếp, read model riêng hay materialized view dựa trên scale, latency và complexity thật sự.
