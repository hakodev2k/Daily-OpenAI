# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwait(false)` đúng chỗ trong library code

**Mẹo:**
Trong reusable library không phụ thuộc UI/request context, có thể dùng `ConfigureAwait(false)` để tránh cố resume continuation trên captured context.

**Tại sao hữu ích:**
Giảm coupling với synchronization context và tránh một số deadlock pattern trong môi trường có context đặc biệt.

**Ví dụ:**
```csharp
public async Task<string> LoadAsync(CancellationToken cancellationToken)
{
    var response = await httpClient.GetAsync("/data", cancellationToken)
        .ConfigureAwait(false);

    return await response.Content.ReadAsStringAsync(cancellationToken)
        .ConfigureAwait(false);
}
```

**Lưu ý:**
Trong ASP.NET Core hiện đại thường không có `SynchronizationContext` kiểu cũ, nên không cần thêm `ConfigureAwait(false)` máy móc vào mọi `await`. Ưu tiên dùng nó có chủ đích trong library code.

### Tip 2 — Dùng `EXPLAIN ANALYZE` để phân biệt estimate và runtime thực tế trong PostgreSQL

**Mẹo:**
Khi query PostgreSQL chậm, dùng `EXPLAIN ANALYZE` để xem cả execution plan lẫn thời gian và số rows thực tế.

**Tại sao hữu ích:**
Nếu `estimated rows` khác xa `actual rows`, optimizer có thể chọn sai join strategy hoặc scan strategy. Đây thường là dấu hiệu cần kiểm tra statistics, data distribution hoặc query shape.

**Ví dụ:**
```sql
EXPLAIN ANALYZE
SELECT o.id, o.created_at
FROM orders o
WHERE o.customer_id = 123
  AND o.created_at >= now() - interval '30 days';
```

**Lưu ý:**
`EXPLAIN ANALYZE` thực sự chạy query. Không dùng thiếu thận trọng với `UPDATE`, `DELETE` hoặc query nặng trên production.

### Tip 3 — Dùng `HttpClientFactory` thay vì tạo `new HttpClient()` liên tục

**Mẹo:**
Trong ASP.NET Core, đăng ký `HttpClient` bằng `IHttpClientFactory` hoặc typed client thay vì tạo và dispose `HttpClient` cho từng request.

**Tại sao hữu ích:**
Giúp quản lý connection pooling, DNS refresh và cấu hình resilience tập trung hơn, đồng thời tránh socket exhaustion do lifecycle sai.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<GitHubClient>(client =>
{
    client.BaseAddress = new Uri("https://api.github.com/");
    client.DefaultRequestHeaders.UserAgent.ParseAdd("MyApp/1.0");
});
```

```csharp
public sealed class GitHubClient(HttpClient httpClient)
{
    public Task<HttpResponseMessage> GetRepoAsync(
        string owner,
        string repo,
        CancellationToken cancellationToken)
        => httpClient.GetAsync($"repos/{owner}/{repo}", cancellationToken);
}
```

**Lưu ý:**
`IHttpClientFactory` không tự động làm retry đúng cho mọi API. Retry các operation không idempotent có thể tạo duplicate side effects.

### Tip 4 — Dùng `git reflog` để cứu commit tưởng đã mất

**Mẹo:**
Khi reset nhầm branch, rebase lỗi hoặc checkout làm bạn tưởng commit biến mất, kiểm tra `git reflog` trước khi hoảng.

**Tại sao hữu ích:**
`reflog` lưu lịch sử thay đổi của `HEAD` và branch references cục bộ, nên thường có thể khôi phục commit chưa bị garbage collection.

**Ví dụ:**
```bash
git reflog
```

Sau khi thấy commit cần cứu:

```bash
git checkout -b recover-work a1b2c3d
```

hoặc:

```bash
git reset --hard a1b2c3d
```

**Lưu ý:**
`reflog` chủ yếu là local history và không tồn tại mãi. Không xem nó là backup strategy.

### Tip 5 — Đo allocation, không chỉ đo execution time

**Mẹo:**
Khi tối ưu .NET code chạy thường xuyên, theo dõi cả allocated bytes và GC pressure thay vì chỉ benchmark elapsed time.

**Tại sao hữu ích:**
Một đoạn code nhanh trong micro-benchmark nhưng allocate nhiều có thể gây Gen 0/Gen 1 GC liên tục dưới production load và làm latency biến động mạnh.

**Ví dụ:**
Với BenchmarkDotNet:

```csharp
[MemoryDiagnoser]
public class SerializationBenchmarks
{
    [Benchmark]
    public string Serialize()
        => JsonSerializer.Serialize(new { Id = 1, Name = "Order" });
}
```

Sau đó so sánh cả `Mean` và `Allocated` thay vì chỉ nhìn thời gian.

**Lưu ý:**
Đừng tối ưu allocation ở code path hiếm chạy nếu không có bằng chứng nó ảnh hưởng workload thực tế. Ưu tiên profiling trước.

## 🧠 Software Design

### Design 1 — Cache-Aside và bài toán stale data

**Khái niệm:**
Với Cache-Aside, application kiểm tra cache trước; nếu miss thì đọc database, trả dữ liệu và ghi kết quả vào cache.

**Vấn đề nó giải quyết:**
Giảm tải database và latency cho dữ liệu được đọc nhiều hơn ghi, nhưng đổi lại hệ thống phải chấp nhận hoặc kiểm soát stale data.

**Ví dụ thực tế:**
Một API lấy `ProductDetail` đọc Redis trước. Khi cache miss, API query PostgreSQL và cache trong 5 phút. Khi product được cập nhật, service có thể xóa cache key ngay hoặc chấp nhận dữ liệu cũ tối đa 5 phút.

**Trade-off:**
Lợi ích là implementation tương đối đơn giản và giảm database load. Chi phí là cache invalidation, cache stampede, stale reads và việc phải chọn TTL phù hợp. TTL quá ngắn làm cache ít giá trị; quá dài làm dữ liệu cũ tồn tại lâu.

**Middle → Senior insight:**
Middle developer nên hiểu cache không phải source of truth và biết dùng TTL/invalidation. Senior developer cần đánh giá mức stale chấp nhận được, cache key design, stampede protection và cách hệ thống hành xử khi Redis unavailable.

### Design 2 — API evolution: ưu tiên backward compatibility trước versioning

**Khái niệm:**
API evolution là thay đổi API theo thời gian mà không phá vỡ consumer hiện tại. Versioning chỉ là một công cụ, không phải phản xạ mặc định cho mọi thay đổi.

**Vấn đề nó giải quyết:**
Client thường deploy độc lập với server. Một rename field, đổi semantics hoặc biến optional field thành required có thể làm client cũ hỏng ngay cả khi API vẫn trả HTTP 200.

**Ví dụ thực tế:**
Thay vì đổi:

```json
{
  "name": "Hanoi"
}
```

thành:

```json
{
  "displayName": "Hanoi"
}
```

ngay lập tức, server có thể tạm thời trả cả hai field, deprecate `name`, theo dõi usage rồi mới remove ở major version sau.

**Trade-off:**
Backward compatibility giảm rủi ro rollout nhưng khiến contract tạm thời phình to và phải duy trì legacy behavior lâu hơn. Versioning tạo boundary rõ nhưng tăng maintenance, documentation và testing cho nhiều phiên bản song song.

**Middle → Senior insight:**
Middle developer nên nhận biết additive change thường an toàn hơn breaking change. Senior developer cần quản lý contract lifecycle, deprecation policy, telemetry usage và xác định khi nào version mới thực sự đáng chi phí.

### Design 3 — Event-driven communication không có nghĩa mọi thứ đều phải async

**Khái niệm:**
Event-driven architecture phù hợp khi producer không cần response tức thời từ consumer và muốn giảm coupling theo thời gian hoặc deployment. Nó không thay thế request/response trong mọi interaction.

**Vấn đề nó giải quyết:**
Synchronous chain dài giữa nhiều services tạo temporal coupling: một downstream service lỗi có thể làm toàn bộ request thất bại. Event giúp producer hoàn tất công việc riêng và consumer xử lý sau.

**Ví dụ thực tế:**
Sau khi `Order` được tạo thành công, hệ thống publish `OrderCreated`. `Email`, `Analytics` và `InventoryProjection` xử lý riêng. Nhưng kiểm tra `CurrentStock` trước khi xác nhận order có thể vẫn cần synchronous query hoặc transaction-local decision tùy business invariant.

**Trade-off:**
Event-driven giúp loose coupling, retry và independent processing nhưng thêm duplicate delivery, eventual consistency, ordering, dead-letter handling và observability complexity. Synchronous calls dễ reasoning hơn nhưng tăng runtime dependency giữa components.

**Middle → Senior insight:**
Middle developer nên hiểu khác biệt giữa command, event và request/response. Senior developer cần xác định interaction nào thật sự cần immediate consistency, interaction nào có thể eventual, và thiết kế idempotency, retry, tracing cùng failure recovery trước khi đưa messaging vào hệ thống.
