# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArgumentNullException.ThrowIfNull` để guard clause ngắn và rõ

**Mẹo:**
Với public API hoặc boundary cần kiểm tra `null`, dùng `ArgumentNullException.ThrowIfNull(...)` thay vì lặp lại `if (x is null) throw ...` ở nhiều nơi.

**Tại sao hữu ích:**
Code guard ngắn hơn, nhất quán hơn và vẫn giữ đúng exception type/parameter name cho caller.

**Ví dụ:**
```csharp
public OrderService(IOrderRepository repository)
{
    ArgumentNullException.ThrowIfNull(repository);
    _repository = repository;
}
```

Hoặc trong method:

```csharp
public Task ProcessAsync(Order order)
{
    ArgumentNullException.ThrowIfNull(order);
    // ...
}
```

**Lưu ý:**
Không biến mọi business validation thành guard clause. `ThrowIfNull` phù hợp với programming contract; rule nghiệp vụ như “order phải ở trạng thái Pending” nên được biểu diễn bằng domain validation riêng.

### Tip 2 — Đọc deadlock graph thay vì chỉ tăng transaction timeout

**Mẹo:**
Khi gặp database deadlock, thu deadlock graph hoặc equivalent diagnostic data để xem chính xác transaction nào khóa resource nào và theo thứ tự nào.

**Tại sao hữu ích:**
Deadlock thường đến từ lock ordering, transaction scope quá rộng hoặc query plan khác nhau. Tăng timeout không giải quyết vòng chờ; deadlock detector vẫn sẽ phải kill một transaction.

**Ví dụ:**
Một flow cập nhật theo thứ tự:

```text
Transaction A: Orders → OrderItems
Transaction B: OrderItems → Orders
```

Nếu hai transaction chạy đồng thời, thứ tự lock ngược nhau có thể tạo cycle. Giải pháp bền hơn là chuẩn hóa lock/update order hoặc giảm scope transaction.

**Lưu ý:**
Đừng kết luận “database bị lỗi” chỉ từ một exception deadlock. Cần kiểm tra graph, index, access order và retry policy; retry chỉ là lớp resilience sau khi đã giảm nguyên nhân hệ thống.

### Tip 3 — Dùng `git patch-id` để nhận biết patch đã tồn tại sau cherry-pick/rebase

**Mẹo:**
Khi lịch sử commit bị rewrite và SHA không còn giống nhau, `git patch-id` có thể giúp kiểm tra hai commit có chứa thay đổi code tương đương hay không.

**Tại sao hữu ích:**
Hữu dụng khi điều tra “commit này đã được cherry-pick sang release branch chưa?” mà không thể dựa vào SHA.

**Ví dụ:**
```bash
git show <commit-a> | git patch-id --stable
git show <commit-b> | git patch-id --stable
```

Nếu patch-id giống nhau, nội dung patch về cơ bản tương đương dù commit metadata khác.

**Lưu ý:**
Patch-id không chứng minh runtime behavior hoàn toàn giống nhau vì context xung quanh có thể đã thay đổi. Vẫn cần review/test trên branch đích.

### Tip 4 — Dùng CI concurrency group để hủy build/deploy cũ không còn giá trị

**Mẹo:**
Với workflow chạy trên cùng branch hoặc environment, cấu hình concurrency để run mới có thể hủy run cũ đang chờ/chạy nếu kết quả cũ không còn cần thiết.

**Tại sao hữu ích:**
Giảm lãng phí CI minutes và tránh tình huống commit cũ deploy sau commit mới chỉ vì queue timing khác nhau.

**Ví dụ:**
GitHub Actions:

```yaml
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true
```

**Lưu ý:**
Không nên bật `cancel-in-progress` cho job có side effect không thể dừng an toàn như database migration đang chạy hoặc release signing. Chỉ cancel khi workflow có semantics rõ ràng.

### Tip 5 — Chặn SSRF bằng allow-list destination, không chỉ validate URL format

**Mẹo:**
Nếu backend cho phép user nhập URL để server fetch, validate scheme/host/IP thực tế và dùng allow-list hoặc policy mạng thay vì chỉ kiểm tra `Uri.TryCreate`.

**Tại sao hữu ích:**
URL hợp lệ về syntax vẫn có thể trỏ tới `localhost`, metadata service, private network hoặc host resolve về internal IP.

**Ví dụ:**
Một webhook tester không nên chỉ làm:

```csharp
Uri.TryCreate(input, UriKind.Absolute, out var uri);
```

Nó nên giới hạn protocol, port, domain/IP range được phép và re-check DNS resolution trước khi kết nối.

**Lưu ý:**
Chỉ block chuỗi `127.0.0.1` hoặc `localhost` là chưa đủ. Cần xét IPv6, DNS rebinding, redirect chain và private/link-local ranges.

## 🧠 Software Design

### Design 1 — Single-flight để chống Cache Stampede

**Khái niệm:**
Single-flight đảm bảo nhiều request cùng miss một cache key không đồng thời gọi xuống database/API để rebuild cùng dữ liệu; chỉ một request thực hiện work, các request còn lại chờ kết quả đó.

**Vấn đề nó giải quyết:**
Khi một hot key hết TTL, hàng trăm request có thể cùng cache miss và tạo “thundering herd”, khiến dependency phía sau bị spike đúng lúc cache mất tác dụng.

**Ví dụ thực tế:**
`ProductCatalog:Top100` hết hạn lúc 10:00:00. Nếu 500 request cùng tới, thay vì 500 query database, hệ thống cho một request refresh cache còn các request khác await cùng task/result.

**Trade-off:**
Single-flight giảm load spike và ổn định latency, nhưng tạo coordination state trong process/distributed layer. Nếu request leader treo, các waiter có thể cùng bị ảnh hưởng; cần timeout và fallback rõ ràng.

**Middle → Senior insight:**
Middle developer nên hiểu TTL đơn thuần chưa đủ cho hot key. Senior developer cần kết hợp single-flight, TTL jitter, stale-while-revalidate và failure fallback dựa trên traffic pattern thực tế.

### Design 2 — Authorization phải đặt tại command/use-case boundary, không chỉ ở UI/controller

**Khái niệm:**
Authorization rule quan trọng nên được kiểm tra ở boundary thực thi business action, nơi mọi entry point đều phải đi qua, thay vì chỉ dựa vào việc frontend ẩn nút hoặc controller cụ thể có attribute.

**Vấn đề nó giải quyết:**
Một use case có thể được gọi từ REST API, background job, SignalR, admin tool hoặc internal endpoint. Nếu authorization chỉ nằm ở một transport layer, đường gọi khác có thể bypass rule.

**Ví dụ thực tế:**
Rule “chỉ manager của employee hoặc HR Admin mới được approve leave” nên được enforce trong `ApproveLeave` use case/policy dựa trên actor context và resource, không chỉ kiểm tra role ở UI.

**Trade-off:**
Centralized authorization tăng consistency và testability nhưng đòi hỏi truyền actor/resource context rõ ràng, và có thể tạo thêm policy code. Với endpoint purely technical/internal, policy có thể đơn giản hơn nhưng vẫn cần trust boundary rõ.

**Middle → Senior insight:**
Middle developer nên phân biệt authentication, role check và resource-level authorization. Senior developer cần thiết kế policy theo business capability, chống privilege escalation và đảm bảo mọi alternate entry point dùng cùng rule.

### Design 3 — Event ordering chỉ nên đảm bảo trong phạm vi thật sự cần thiết

**Khái niệm:**
Trong messaging, global ordering rất đắt và thường không cần. Thay vào đó, hệ thống nên xác định phạm vi ordering nhỏ nhất như theo `OrderId`, `AccountId` hoặc partition key.

**Vấn đề nó giải quyết:**
Nếu consumer cần xử lý `OrderCreated` trước `OrderCancelled` cho cùng order, mất thứ tự có thể tạo state sai. Nhưng yêu cầu mọi event toàn hệ thống có thứ tự tuyệt đối sẽ bóp throughput và scalability.

**Ví dụ thực tế:**
Publish event với partition key = `OrderId` để các event của cùng order vào cùng partition và giữ thứ tự cục bộ, trong khi các order khác vẫn xử lý song song.

**Trade-off:**
Ordering theo key giữ được invariant quan trọng và vẫn scale tốt hơn global ordering, nhưng hot key có thể tạo partition hotspot. Re-delivery cũng yêu cầu consumer idempotent dù thứ tự được đảm bảo.

**Middle → Senior insight:**
Middle developer nên hỏi “thứ tự của cái gì so với cái gì?” thay vì yêu cầu ordered queue chung. Senior developer phải chọn partition key, xử lý late/out-of-order message, hot partition và recovery/replay mà không phá invariant.
