# Daily Developer Tips & Design — 2026-10-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Giới hạn tuổi connection của HttpClient để thích nghi với DNS thay đổi

**Mẹo:**
Với outbound HTTP call tới service có IP thay đổi sau deployment/failover, cấu hình `PooledConnectionLifetime` trên `SocketsHttpHandler`. Giữ tái sử dụng connection nhưng buộc connection cũ được thay thế định kỳ, từ đó DNS được phân giải lại khi mở connection mới.

**Tại sao hữu ích:**
`HttpClient` không tự theo dõi TTL của DNS record trên connection đang mở. Một ứng dụng chạy lâu có thể tiếp tục dùng kết nối tới endpoint cũ. `IHttpClientFactory` đã có cơ chế luân chuyển handler mặc định; cấu hình lifetime riêng hữu ích khi cần kiểm soát rõ vòng đời connection.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient("inventory")
    .ConfigurePrimaryHttpMessageHandler(() =>
        new SocketsHttpHandler
        {
            PooledConnectionLifetime = TimeSpan.FromMinutes(5)
        });
```
Khi inventory service đổi IP, connection mới sau khi connection cũ hết tuổi sẽ phân giải DNS lại. Theo dõi connection errors, DNS changes và latency trước/sau failover để xác nhận giả thuyết.

**Lưu ý:**
`PooledConnectionLifetime` không hủy request đang chạy và không thay thế timeout, retry hay circuit breaker. Lifetime quá ngắn làm tăng TCP/TLS handshakes; không tạo `new HttpClient()` mỗi request để “sửa DNS”.

### Tip 2 — MongoDB: kiểm tra cả filter lẫn sort trước khi tạo compound index

**Mẹo:**
Thiết kế compound index theo query thực tế, đặc biệt các field equality, sort và range. Dùng `explain("executionStats")` để kiểm tra liệu MongoDB có phải sort trong memory hoặc đọc quá nhiều document hay không.

**Tại sao hữu ích:**
Một index hỗ trợ `tenantId` nhưng không hỗ trợ thứ tự `createdAt` có thể khiến trang lịch sử đơn hàng chậm khi dữ liệu tăng. Số document được đọc và các stage trong execution plan thường hữu ích hơn cảm giác “đã có index”.

**Ví dụ:**
```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1, _id: -1 });

db.orders.find({ tenantId: "t42", status: "Paid" })
  .sort({ createdAt: -1, _id: -1 })
  .limit(30)
  .explain("executionStats");
```
Kiểm tra `totalKeysExamined`, `totalDocsExamined`, `nReturned` và có `SORT` stage hay không. `_id` tạo tie-breaker ổn định cho nhiều đơn hàng cùng timestamp.

**Lưu ý:**
Thứ tự field chỉ phù hợp với một nhóm query cụ thể; index thêm làm tăng chi phí ghi và dung lượng. Nếu filter có range, hãy đánh giá lại khả năng hỗ trợ sort thay vì áp dụng máy móc quy tắc equality–sort–range.

### Tip 3 — Azure Blob Storage: dùng ETag để tránh lost update

**Mẹo:**
Khi nhiều worker cùng sửa một blob cấu hình hoặc manifest, dùng conditional write với `IfMatch` thay vì ghi đè vô điều kiện.

**Tại sao hữu ích:**
ETag thay đổi khi blob được cập nhật. Nếu worker B đã sửa blob sau lúc worker A đọc, request ghi của A với ETag cũ sẽ thất bại với HTTP 412 thay vì âm thầm xóa thay đổi của B.

**Ví dụ:**
```csharp
var props = await blob.GetPropertiesAsync(ct);
var options = new BlobUploadOptions
{
    Conditions = new BlobRequestConditions
    {
        IfMatch = props.Value.ETag
    }
};
await blob.UploadAsync(BinaryData.FromString(updatedJson), options, ct);
```
Khi nhận 412, đọc lại blob, merge theo business rule rồi retry có giới hạn; không chỉ lặp lại payload cũ.

**Lưu ý:**
ETag bảo vệ một blob, không tạo transaction xuyên nhiều blob hay database. Nếu nội dung được tính từ bản đọc ban đầu, phải đọc và xác thực lại trạng thái trước khi retry.

### Tip 4 — Git range-diff: review lại patch sau rebase mà không bỏ sót thay đổi

**Mẹo:**
Khi một PR được rebase/chỉnh sửa nhiều commit, dùng `git range-diff` để so sánh hai phiên bản của chuỗi patch, thay vì chỉ nhìn diff cuối cùng so với `main`.

**Tại sao hữu ích:**
Rebase đổi commit SHA và có thể vô tình làm mất một fix nhỏ. `range-diff` ghép các commit tương ứng theo nội dung patch, giúp reviewer phát hiện commit bị thêm, xóa hoặc sửa khác dự kiến.

**Ví dụ:**
```bash
git branch review-before-rebase
# Sau khi hoàn tất rebase, feature là HEAD mới
git range-diff origin/main..review-before-rebase origin/main..HEAD
```
Trong PR xử lý lỗi thanh toán, xem liệu commit thêm kiểm tra idempotency có còn giữ nguyên logic sau rebase.

**Lưu ý:**
Kết quả là heuristic để hỗ trợ review, không thay thế `git diff`, test hay kiểm tra merge-base. Nếu `main` thay đổi trong lúc rebase, cần chọn đúng base của từng chuỗi commit để tránh nhiễu.

### Tip 5 — Quality Gate: ưu tiên regression trên new code, không chạy theo coverage tổng

**Mẹo:**
Trong CI/CD, kết hợp SonarQube Quality Gate trên new code với test kiểm tra hành vi quan trọng. Đặt mục tiêu ngăn lỗi mới, không chỉ nâng tỷ lệ coverage toàn repository.

**Tại sao hữu ích:**
Hệ thống legacy có thể có coverage thấp nhưng tăng coverage tổng vài phần trăm chưa chắc giảm rủi ro. Một test chứng minh đơn hàng không bị thanh toán hai lần thường giá trị hơn nhiều test chỉ xác nhận mock được gọi.

**Ví dụ:**
Một PR sửa endpoint `POST /payments`: integration test gửi lại cùng idempotency key và xác nhận chỉ một payment record được commit; Quality Gate kiểm tra issue mới, duplicated code và coverage của phần thay đổi. Nếu test đỏ hoặc gate fail, pipeline không promote artifact.

**Lưu ý:**
Coverage không đo chất lượng assertion; test có thể đi qua dòng code mà không bắt được bug. Quality Gate cần baseline và exception process minh bạch để không khóa mọi hotfix vì cảnh báo không liên quan.

## 🧠 Software Design

### Design 1 — Multi-tenant data isolation: shared schema hay database riêng?

**Khái niệm:**
Trong SaaS, dữ liệu tenant có thể dùng chung database/table với `TenantId`, tách schema hoặc tách database. Đây là quyết định về isolation, vận hành và chi phí, không đơn thuần là cách đặt tên bảng.

**Vấn đề nó giải quyết:**
Một bug thiếu tenant filter trong API có thể lộ dữ liệu khách hàng khác; đồng thời một tenant có workload lớn có thể ảnh hưởng latency của tenant còn lại.

**Ví dụ thực tế:**
Hệ thống CRM phục vụ 500 doanh nghiệp nhỏ dùng shared schema với `TenantId`, authorization ở application layer và test cross-tenant. Một khách hàng enterprise yêu cầu backup/restore, retention và data residency riêng có thể được chuyển sang dedicated database theo routing của tenant.

**Trade-off:**
Shared schema tiết kiệm tài nguyên, migration đơn giản hơn nhưng cần kiểm soát data access cực chặt, kể cả background jobs và raw SQL. Database riêng tăng isolation, cho phép tuning/restore độc lập nhưng làm phức tạp provisioning, connection management và schema rollout trên nhiều database.

**Middle → Senior insight:**
- **Middle:** luôn lấy tenant từ trusted identity context; kiểm tra quyền với tenant và viết test chống truy cập chéo, không tin `tenantId` do client tự gửi.
- **Senior / Technical:** chọn isolation model theo compliance, số tenant, workload skew, backup RPO/RTO và chi phí vận hành; thiết kế migration path khi tenant tăng trưởng thay vì mặc định “mỗi tenant một database”.

### Design 2 — Event Sourcing không đồng nghĩa với Audit Log

**Khái niệm:**
Audit Log ghi lại ai đã thay đổi gì để điều tra. Event Sourcing lưu chuỗi domain events làm nguồn sự thật, và tái dựng state từ các event đó. Hai cách phục vụ nhu cầu khác nhau.

**Vấn đề nó giải quyết:**
Đội phát triển muốn biết vì sao trạng thái hợp đồng đổi từ Approved sang Cancelled. Nếu chỉ cần lịch sử phục vụ compliance, audit log có thể đủ; nếu business cần tái dựng state tại mọi thời điểm và phát lại projection, Event Sourcing mới có thể đáng cân nhắc.

**Ví dụ thực tế:**
CMS lưu `ContentPublished` và `ContentUnpublished` vào audit stream để editor tra cứu. Một hệ thống pricing với nhiều bước phê duyệt có thể dùng event-sourced aggregate nếu cần rebuild state và kiểm tra chính xác chuỗi quyết định; read model được cập nhật từ event stream.

**Trade-off:**
Event Sourcing hỗ trợ temporal analysis và rebuild projection nhưng làm tăng độ khó của event versioning, schema evolution, snapshot, replay, privacy deletion và debugging. Audit Log kết hợp bảng state hiện tại đơn giản hơn nhiều nếu không có yêu cầu tái dựng domain state.

**Middle → Senior insight:**
- **Middle:** phân biệt event dùng làm nguồn dữ liệu với log dùng để theo dõi; không sửa event lịch sử tùy tiện.
- **Senior / Technical:** chỉ chấp nhận Event Sourcing khi lợi ích nghiệp vụ vượt chi phí replay, upcasting, consistency và vận hành; xác định trước chính sách retention và xử lý dữ liệu nhạy cảm.

### Design 3 — Resumable batch import: checkpoint thay cho một transaction khổng lồ

**Khái niệm:**
Một batch import lớn có thể được chia thành các đơn vị xử lý nhỏ, lưu checkpoint và trạng thái từng item để resume an toàn sau failure, thay vì giữ một database transaction xuyên toàn bộ file.

**Vấn đề nó giải quyết:**
Import 300.000 sản phẩm từ ERP chạy 40 phút. Nếu worker restart ở phút 39, transaction lớn rollback toàn bộ; nếu retry toàn bộ mà không có idempotency, sản phẩm hoặc side effect có thể bị tạo trùng.

**Ví dụ thực tế:**
Lưu `ImportJob(Id, FileHash, Cursor, Status)` và `ImportItem(JobId, ExternalProductId, Result)`. Mỗi chunk 500 bản ghi chạy trong transaction ngắn, upsert theo business key và commit checkpoint cùng trạng thái item. Khi worker restart, đọc checkpoint, xác minh item đã xử lý và tiếp tục; lỗi từng item được đưa vào report.

**Trade-off:**
Chunking giảm lock duration, giới hạn rollback và tăng khả năng phục hồi, nhưng có trạng thái partial completion; consumer phải chấp nhận dữ liệu cập nhật dần hoặc dùng staging table rồi atomic publish. Checkpoint không tự đảm bảo exactly-once cho external side effects.

**Middle → Senior insight:**
- **Middle:** thiết kế unique constraint/idempotent upsert, log lỗi theo item và retry có giới hạn.
- **Senior / Technical:** chọn giữa atomic staging-and-swap và eventual publication theo yêu cầu business; xác định isolation, visibility, backpressure, recovery semantics và cách đối soát khi source file thay đổi giữa hai lần chạy.
