## Developer Tips & Tricks

### 1. Đừng đổi mọi `Task<T>` thành `ValueTask<T>` chỉ để giảm allocation

**Vấn đề thực tế:** Sau khi thấy `ValueTask<T>` có thể tránh allocation khi kết quả thường hoàn thành synchronously, team thay hàng loạt API từ `Task<T>` sang `ValueTask<T>`. Code phức tạp hơn nhưng benchmark gần như không cải thiện, thậm chí caller bắt đầu dùng sai bằng cách await cùng một `ValueTask` nhiều lần.

**Cơ chế bên dưới:** `Task<T>` là reference type và có semantics rất quen thuộc: có thể cache, await nhiều lần, truyền qua combinators. `ValueTask<T>` là struct có thể chứa trực tiếp kết quả hoặc wrap `Task<T>`/`IValueTaskSource<T>`. Nó hữu ích khi synchronous completion xảy ra thường xuyên và allocation của `Task<T>` thực sự nằm trên hot path. Nhưng struct lớn hơn reference, copy nhiều hơn và một số backing source chỉ cho phép consume một lần.

**Cách làm tốt hơn:** Giữ `Task<T>` làm mặc định. Chỉ dùng `ValueTask<T>` sau profiling/benchmark, đặc biệt cho low-level APIs có synchronous fast path rõ ràng.

```csharp
public ValueTask<User?> GetUserAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    if (_cache.TryGetValue(id, out var cached))
    {
        return ValueTask.FromResult<User?>(cached);
    }

    return new ValueTask<User?>(LoadFromDatabaseAsync(id, cancellationToken));
}
```

Nếu cần await nhiều lần hoặc lưu operation để dùng sau, convert một lần bằng `.AsTask()` thay vì giả định mọi `ValueTask` đều reusable.

**Khi nên dùng:** High-throughput libraries, serializers, pipelines hoặc cache-heavy code nơi benchmark cho thấy `Task` allocation đáng kể. Với application/service code thông thường, `Task<T>` thường đơn giản và an toàn hơn.

### 2. Dùng `AsSplitQuery` có chủ đích khi nhiều collection `Include` tạo cartesian explosion

**Vấn đề thực tế:** Bạn load `Order` cùng `Items` và `Payments` bằng hai collection `Include`. Một order có 20 items và 5 payments có thể tạo 100 rows ở SQL result dù object graph cuối cùng chỉ có 1 order, 20 items và 5 payments. Payload phình to và duplicated columns của principal bị truyền lại nhiều lần.

**Cơ chế bên dưới:** Khi nhiều sibling collection được JOIN trong một SQL query, relational result phải biểu diễn tích Descartes giữa các collection. EF Core có thể materialize object graph đúng, nhưng database/network vẫn phải xử lý result set lớn. `AsSplitQuery()` tách collection loading thành nhiều SQL queries, tránh nhân rows nhưng đổi lại có thêm round trips và consistency considerations giữa các query.

**Cách làm tốt hơn:** Projection là lựa chọn đầu tiên cho read API. Nếu thực sự cần entity graph với nhiều collection, benchmark `AsSingleQuery` và `AsSplitQuery` trên cardinality production-like.

```csharp
var order = await db.Orders
    .AsNoTracking()
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == orderId, cancellationToken);
```

**Khi nên dùng:** Aggregate/read graph có nhiều collection với cardinality đủ lớn để JOIN result bùng nổ. Không bật split query máy móc cho mọi query; với graph nhỏ, extra round trips có thể tốn hơn JOIN.

### 3. Khi SQL plan lúc nhanh lúc chậm, kiểm tra parameter-sensitive plan trước khi sửa LINQ

**Vấn đề thực tế:** Cùng một stored procedure/query parameterized có lúc chạy 20 ms, lúc mất vài giây. Index tồn tại và SQL text không đổi. Restart/recompile tạm thời làm query nhanh trở lại nên team tưởng EF Core hoặc connection pool có lỗi.

**Cơ chế bên dưới:** SQL Server optimizer xây execution plan dựa trên cardinality estimates. Với dữ liệu skewed, giá trị parameter trả vài rows và giá trị khác trả hàng triệu rows có thể cần hai plan rất khác nhau. Một cached plan tối ưu cho distribution này có thể tệ cho distribution khác. Đây thường được gọi là parameter-sensitive plan/parameter sniffing problem; phiên bản SQL Server mới có cơ chế Parameter Sensitive Plan optimization trong các điều kiện phù hợp.

**Cách làm tốt hơn:** Xác nhận bằng actual execution plan, Query Store và runtime statistics trước khi thêm hint. Kiểm tra data distribution, statistics, index và compatibility level. Chỉ dùng `OPTION (RECOMPILE)`, `OPTIMIZE FOR` hoặc query-shape separation khi đã hiểu trade-off CPU compilation và plan stability.

```sql
SELECT Id, CustomerId, CreatedAt, Total
FROM dbo.Orders
WHERE CustomerId = @customerId
  AND CreatedAt >= @fromDate;
```

Nếu một số customer có vài orders còn một số customer có hàng triệu orders, đừng giả định một plan luôn tối ưu cho cả hai.

**Khi nên dùng:** Production query có latency variance lớn theo parameter value dù SQL shape giống nhau. Đây là bài toán cần database evidence; đừng chữa bằng random index hoặc `AsEnumerable()` để né translation.

### 4. Dùng `git worktree` khi phải sửa hotfix mà không muốn phá working tree hiện tại

**Vấn đề thực tế:** Bạn đang giữa một refactor lớn với nhiều file chưa commit thì production cần hotfix từ `main`. `git stash`, switch branch, sửa, rồi restore stash dễ tạo conflict hoặc làm mất mental context.

**Cơ chế bên dưới:** `git worktree` cho phép một repository có nhiều working directories cùng chia sẻ object database nhưng checkout các branch khác nhau. Bạn giữ nguyên workspace feature hiện tại và tạo workspace thứ hai cho hotfix mà không clone lại toàn repo.

**Cách làm tốt hơn:** Tạo worktree riêng từ branch phù hợp, hoàn thành hotfix rồi remove worktree khi xong.

```bash
git fetch origin

git worktree add ../Daily-OpenAI-hotfix -b hotfix/order-timeout origin/main

cd ../Daily-OpenAI-hotfix
# sửa, test, commit, push tại workspace độc lập

git worktree remove ../Daily-OpenAI-hotfix
```

**Khi nên dùng:** Hotfix song song với feature work, review nhiều branches, benchmark hai implementations hoặc chạy nhiều versions cạnh nhau. Tránh tạo nhiều worktree không quản lý vì build artifacts và IDE indexes vẫn tiêu tốn disk/resource riêng.

### 5. Propagate trace context qua `Activity`; đừng tự phát minh `Correlation-Id` cho mọi hop

**Vấn đề thực tế:** Mỗi service tự tạo một `Correlation-Id` header và log nó, nhưng khi request đi qua HTTP, queue và background worker, một số hop quên copy header. Trace bị đứt và bạn không phân biệt được parent-child spans hay parallel downstream calls.

**Cơ chế bên dưới:** .NET `System.Diagnostics.Activity` tích hợp với W3C Trace Context và là nền tảng instrumentation của OpenTelemetry. `TraceId` nhận diện distributed trace; `SpanId` nhận diện operation cụ thể; parent context mô tả causal tree. Instrumented `HttpClient`/ASP.NET Core có thể propagate context chuẩn mà không cần custom header riêng cho tracing.

**Cách làm tốt hơn:** Instrument boundary bằng `ActivitySource`, thêm tags có bounded cardinality và để OpenTelemetry exporter xử lý telemetry.

```csharp
private static readonly ActivitySource ActivitySource =
    new("Orders.Application");

public async Task ProcessAsync(Guid orderId, CancellationToken ct)
{
    using var activity = ActivitySource.StartActivity("orders.process");
    activity?.SetTag("order.operation", "process");

    await _processor.ProcessAsync(orderId, ct);
}
```

Không đưa secrets, raw tokens hoặc identifiers có cardinality cực cao vào metric labels. Trace tags và logs cũng cần data-governance rõ ràng.

**Khi nên dùng:** Distributed systems, asynchronous workflows và production debugging cần end-to-end causality. Business correlation ID vẫn có thể tồn tại nếu domain thực sự cần nó, nhưng đừng dùng nó để thay thế tracing semantics chuẩn.

## Software Design

### 6. Saga: distributed transaction bằng compensating actions, không phải rollback ACID xuyên services

**Vấn đề thực tế:** Checkout cần reserve inventory, charge payment và create shipment. Nếu payment thành công nhưng shipment thất bại, không có một SQL transaction chung để rollback ba services độc lập.

**Trade-off thiết kế:** Saga chia workflow thành các local transactions và định nghĩa compensation khi bước sau thất bại. Orchestration dùng coordinator quyết định bước tiếp theo; choreography để services phản ứng qua events. Bạn nhận được khả năng scale/ownership độc lập nhưng phải chấp nhận intermediate states, idempotency, retries và compensation không phải lúc nào cũng là inverse hoàn hảo.

```text
Order Saga
   |
   +--> Reserve Inventory ---- success ----+
   |                                      |
   +--> Charge Payment ------- success ----+--> Create Shipment
                                              |
                                              +-- failure
                                                   |
                         +-------------------------+
                         v
                  Refund Payment
                         |
                         v
                 Release Inventory
```

**Khi phù hợp:** Business workflow kéo dài qua nhiều services/resource managers và không thể dùng một local ACID transaction. Nếu operations nằm trong cùng database boundary, transaction thông thường đơn giản và mạnh hơn.

### 7. Ports and Adapters: domain phụ thuộc capability, không phụ thuộc framework/infrastructure

**Vấn đề thực tế:** Business logic gọi trực tiếp `DbContext`, `HttpClient`, SDK cloud và static clock. Unit test phải dựng quá nhiều infrastructure; đổi vendor hoặc protocol khiến logic nghiệp vụ cũng bị sửa.

**Trade-off thiết kế:** Hexagonal Architecture/Ports and Adapters đặt application/domain ở trung tâm. Core định nghĩa ports mô tả capability cần thiết; adapters triển khai các ports bằng SQL, HTTP, queue hoặc external SDK. Boundary rõ hơn và test dễ hơn, nhưng abstraction quá nhỏ hoặc interface-per-class sẽ tạo ceremony mà không tạo decoupling thực sự.

```text
              HTTP Adapter
                   |
                   v
        +-----------------------+
        |   Application Core    |
        |                       |
        |  IOrderRepository     |----> SQL Adapter
        |  IPaymentGateway      |----> Stripe Adapter
        |  IClock               |----> System Clock Adapter
        +-----------------------+
                   ^
                   |
              Worker Adapter
```

**Khi phù hợp:** Domain logic có tuổi thọ dài hơn infrastructure, nhiều adapters cho cùng capability hoặc cần test business rules độc lập. Với CRUD service rất nhỏ, layering tối giản có thể tốt hơn một kiến trúc nhiều interfaces.

### 8. Cache-Aside cần chống cache stampede, không chỉ thêm Redis rồi coi như xong

**Vấn đề thực tế:** Một key phổ biến hết TTL lúc traffic cao. Hàng trăm requests cùng cache miss và đồng thời query database để rebuild cùng dữ liệu. Cache vốn để bảo vệ database lại tạo load spike đúng lúc expiration.

**Trade-off thiết kế:** Cache-Aside cho application quyền kiểm soát read-through logic: đọc cache, miss thì load source rồi populate cache. Để chống stampede, có thể dùng per-key single-flight/local lock, distributed lock có timeout, stale-while-revalidate hoặc TTL jitter. Mỗi lựa chọn đổi consistency, complexity và failure behavior khác nhau.

```text
Requests (same key)
      |
      v
   Cache Miss
      |
      v
 Per-key Single Flight
      |
      +---- one loader ----> Database ----> Cache Set
      |
      +---- waiters ----------------------> shared result

TTL = base TTL + random jitter
=> popular keys không expire đồng loạt
```

**Khi phù hợp:** Read-heavy workloads có expensive source query và hot keys. Nếu dữ liệu rẻ để load hoặc consistency phải mạnh đến mức cache invalidation quá phức tạp, không cache có thể là thiết kế tốt hơn.
