# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` khi cần producer/consumer trong process thay vì tự quản `ConcurrentQueue`

**Mẹo:**
Khi một ASP.NET Core app hoặc Worker Service có nhiều producer tạo work và một hoặc nhiều consumer xử lý bất đồng bộ, cân nhắc `System.Threading.Channels` thay vì tự ghép `ConcurrentQueue`, semaphore và polling loop.

**Tại sao hữu ích:**
`Channel<T>` cung cấp async coordination, bounded capacity và backpressure rõ ràng. Với queue tự chế, producer thường đẩy work vô hạn rồi memory tăng dần khi consumer chậm hơn traffic đầu vào.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait
});

await channel.Writer.WriteAsync(job, cancellationToken);

await foreach (var item in channel.Reader.ReadAllAsync(cancellationToken))
{
    await ProcessAsync(item, cancellationToken);
}
```

**Lưu ý:**
`Channel<T>` chỉ là in-memory queue. Nếu process restart thì work chưa xử lý có thể mất. Với durability, cross-instance delivery hoặc retry cần bảo đảm, dùng broker như Azure Service Bus phù hợp hơn.

### Tip 2 — Với MongoDB compound index, thứ tự field phải theo query pattern chứ không theo model class

**Mẹo:**
Khi tạo compound index, sắp xếp field theo cách query thực tế lọc và sort; đừng chọn thứ tự chỉ vì property trong document được khai báo như vậy.

**Tại sao hữu ích:**
MongoDB có thể tận dụng prefix của compound index. Một index đúng field nhưng sai thứ tự có thể không hỗ trợ hiệu quả cả equality filter lẫn sort, khiến query phải scan nhiều document hoặc sort thêm trong memory.

**Ví dụ:**
Query thường gặp:
```javascript
db.orders.find({ tenantId: "t-42", status: "Paid" })
         .sort({ createdAt: -1 })
```

Index hợp lý có thể là:
```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Nếu tenant luôn là equality predicate, đặt nó đầu index giúp thu hẹp phạm vi trước khi sort theo `createdAt`.

**Lưu ý:**
Không có index tối ưu cho mọi query. Mỗi index làm tăng storage và write amplification. Luôn kiểm tra `explain()` và workload thật trước khi thêm nhiều compound index gần giống nhau.

### Tip 3 — Với Azure Functions, poison message cần workflow riêng thay vì retry vô hạn

**Mẹo:**
Khi một trigger xử lý message thất bại lặp lại, thiết kế rõ đường đi tới poison queue hoặc dead-letter queue cùng metadata đủ để điều tra và replay có kiểm soát.

**Tại sao hữu ích:**
Retry vô hạn giữ một message lỗi trong hot path, làm tăng cost, noise và có thể chặn throughput. Một message malformed hoặc vi phạm business invariant thường không tự sửa chỉ bằng cách thử lại.

**Ví dụ:**
```text
message received
-> transient failure -> retry with backoff
-> max attempts exceeded
-> move to DLQ / poison queue
-> alert + inspect payload + root cause
-> fix / replay explicitly
```

Log nên có `MessageId`, correlation ID, attempt count và failure category.

**Lưu ý:**
Đừng coi mọi failure là poison ngay. Timeout hoặc throttling có thể transient; schema invalid hoặc missing required data thường là permanent failure. Retry policy phải phân loại lỗi thay vì dùng cùng một rule cho tất cả exception.

### Tip 4 — Dùng Network waterfall để phân biệt frontend chậm do JavaScript với backend chậm

**Mẹo:**
Khi user báo page chậm, mở browser DevTools Network/Performance và xác định request nào chậm, request nào bị queue, asset nào block render và JavaScript nào giữ main thread.

**Tại sao hữu ích:**
Một trang render sau 4 giây có thể do API TTFB cao, bundle lớn, waterfall tuần tự hoặc long task trên main thread. Nếu không tách các thành phần này, team dễ tối ưu nhầm backend khi bottleneck thực sự ở frontend hoặc ngược lại.

**Ví dụ:**
```text
HTML TTFB              180 ms
main.js download       350 ms
main.js execution     1200 ms
GET /api/search        160 ms
hero.jpg              1700 ms
```

Ở đây API không phải nguyên nhân chính; JavaScript execution và image delivery đáng điều tra trước.

**Lưu ý:**
DevTools local chưa phản ánh đầy đủ production device/network. Kết hợp lab profiling với real-user telemetry như Core Web Vitals khi quyết định ưu tiên tối ưu.

### Tip 5 — Giữ build artifact immutable giữa các environment

**Mẹo:**
Build một artifact duy nhất rồi promote cùng artifact đó qua test, staging và production; chỉ thay configuration bên ngoài thay vì rebuild code cho từng environment.

**Tại sao hữu ích:**
Nếu production chạy binary được build khác staging, bạn không còn kiểm thử chính artifact đã được approve. Rebuild có thể kéo dependency khác, generated file khác hoặc biến môi trường build thành một phần không kiểm soát của release.

**Ví dụ:**
```text
Commit abc123
-> CI build artifact app-4.9.2.zip
-> deploy Test
-> promote same app-4.9.2.zip to Staging
-> promote same app-4.9.2.zip to Production
```

Secrets, connection strings và feature flags được inject theo environment khi deploy/runtime.

**Lưu ý:**
Không nhúng environment-specific secret vào artifact rồi gọi đó là immutable deployment. Artifact nên bất biến; configuration và secret management phải tách khỏi binary/package.

## 🧠 Software Design

### Design 1 — BFF vs API Gateway: đừng dùng một component cho hai trách nhiệm khác nhau

**Khái niệm:**
API Gateway thường xử lý cross-cutting concerns như routing, authentication, rate limiting và TLS termination. Backend for Frontend (BFF) tạo API contract tối ưu cho một client cụ thể như Web hoặc Mobile và có thể aggregate nhiều backend call.

**Vấn đề nó giải quyết:**
Nếu frontend phải gọi 8 service để render một màn hình, client trở nên phụ thuộc vào topology backend. Nhưng nếu gateway chứa toàn bộ orchestration và business-specific composition, nó dễ biến thành một monolith ở edge.

**Ví dụ thực tế:**
```text
Mobile App
-> Mobile BFF
   -> Profile API
   -> Orders API
   -> Recommendation API

Gateway
-> auth
-> routing
-> rate limiting
-> forwards to BFF/services
```

BFF chịu trách nhiệm client-specific composition; gateway giữ policy dùng chung.

**Trade-off:**
BFF giảm coupling giữa client và backend topology nhưng thêm service, deployment và duplication nếu nhiều client có nhu cầu gần giống nhau. API Gateway đơn giản hóa edge policy nhưng không nên trở thành nơi chứa domain logic phức tạp.

**Middle → Senior insight:**
Middle developer cần phân biệt cross-cutting concern với client-specific orchestration. Senior / Technical developer phải quyết định khi nào BFF đáng tồn tại dựa trên số client, divergence của contract, latency, ownership team và operational cost.

### Design 2 — Cache invalidation bằng versioned key vs explicit delete

**Khái niệm:**
Explicit delete xóa từng cache key khi source data đổi. Versioned key gắn version hoặc generation vào namespace cache, để dữ liệu mới dùng key mới còn key cũ tự hết hạn.

**Vấn đề nó giải quyết:**
Khi một business object ảnh hưởng hàng trăm cache entry, việc tìm và xóa đúng toàn bộ key có thể khó và dễ bỏ sót. Versioning cho phép invalidate cả nhóm bằng cách thay một generation token.

**Ví dụ thực tế:**
```text
catalog:v17:category:42
catalog:v17:product:1001
```

Khi publish một catalog snapshot mới:
```text
catalogVersion = v18
```

Request mới đọc namespace `v18`; key `v17` không còn được dùng và tự expire theo TTL.

**Trade-off:**
Versioned key làm invalidation nhóm đơn giản nhưng tạm thời giữ dữ liệu cũ trong cache và tăng memory usage. Explicit delete tiết kiệm hơn nhưng cần dependency tracking chính xác và xử lý race condition giữa read/write.

**Middle → Senior insight:**
Middle developer cần hiểu cache key ownership, TTL và stale-data semantics. Senior / Technical developer phải chọn strategy theo số lượng dependency, consistency requirement, memory budget và khả năng rollback giữa các version dữ liệu.

### Design 3 — Build vs Buy: đánh giá theo capability lifecycle, không chỉ chi phí implementation ban đầu

**Khái niệm:**
Build vs Buy là quyết định giữa tự phát triển capability và dùng product/service bên ngoài. So sánh đúng phải tính toàn bộ lifecycle: integration, vận hành, security, compliance, upgrade, vendor dependency và khả năng thay đổi về sau.

**Vấn đề nó giải quyết:**
Team có thể tự build một search, authentication hoặc workflow engine trong vài sprint rồi nhận ra chi phí thật nằm ở monitoring, edge cases, security patches, scaling và support trong nhiều năm.

**Ví dụ thực tế:**
Một công ty cần full-text search với typo tolerance, faceting và relevance tuning. Tự viết trên SQL có vẻ rẻ lúc đầu, nhưng nếu roadmap cần multilingual analyzers, reindexing và scale lớn, Elasticsearch/OpenSearch hoặc managed search service có thể giảm capability risk.

Ngược lại, nếu requirement chỉ là vài filter/query đơn giản, mua một platform lớn có thể tạo vendor cost và operational complexity không cần thiết.

**Trade-off:**
Buy rút ngắn time-to-capability nhưng tạo recurring cost, vendor lock-in và constraint theo product. Build cho control và fit tốt hơn nhưng team phải sở hữu toàn bộ reliability, security và evolution cost.

**Middle → Senior insight:**
Middle developer cần đánh giá integration boundary và technical fit. Senior / Technical developer phải tính total cost of ownership, strategic differentiation, exit cost, compliance, operational ownership và xác suất requirement thay đổi trước khi chọn build hay buy.
