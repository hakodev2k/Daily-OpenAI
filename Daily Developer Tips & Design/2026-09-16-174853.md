# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `HttpClient` timeout và retry nhân latency ngoài dự kiến

**Mẹo:**
Khi gọi third-party API, thiết kế một timeout budget tổng thể rồi phân bổ cho từng attempt; đừng cấu hình mỗi retry có một timeout dài bằng toàn bộ SLA của request.

**Tại sao hữu ích:**
Nếu endpoint có 3 retries và mỗi attempt được phép chờ 10 giây, một dependency lỗi có thể giữ request hơn 30 giây chưa kể backoff. Điều này giữ connection, tăng concurrent work và có thể biến lỗi downstream thành resource exhaustion ở chính API của bạn.

**Ví dụ:**
```csharp
var resilience = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddTimeout(TimeSpan.FromSeconds(2))
    .AddRetry(new HttpRetryStrategyOptions
    {
        MaxRetryAttempts = 2,
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true
    })
    .Build();
```
Trong production, xác định rõ timeout per-attempt và timeout toàn operation theo SLA thay vì copy một con số cho mọi dependency.

**Lưu ý:**
Không retry mọi lỗi. Validation failure, authentication failure hoặc non-idempotent operation có side effect có thể không an toàn để retry. Thứ tự timeout/retry trong resilience pipeline cũng ảnh hưởng semantics.

### Tip 2 — Dùng `ExecuteUpdateAsync` khi cần update hàng loạt mà không cần materialize entities

**Mẹo:**
Với bulk update đơn giản trên EF Core, cân nhắc `ExecuteUpdateAsync` thay vì query hàng nghìn entities vào memory rồi sửa từng object và `SaveChangesAsync`.

**Tại sao hữu ích:**
Materialization + change tracking tạo allocation, round trips và tracking overhead không cần thiết khi business operation thực chất chỉ là một set-based SQL update. `ExecuteUpdateAsync` gửi update trực tiếp tới database.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now), cancellationToken);
```

**Lưu ý:**
Operation này không đi qua normal change tracker semantics. Tracked entities đã load có thể trở thành stale, và domain logic/event nằm trong entity setters sẽ không tự chạy. Chỉ dùng khi set-based update phù hợp với invariant nghiệp vụ.

### Tip 3 — Phân biệt readiness và liveness để tránh restart ứng dụng chỉ vì dependency tạm thời lỗi

**Mẹo:**
Thiết kế health checks sao cho liveness trả lời “process có cần restart không?”, còn readiness trả lời “instance có sẵn sàng nhận traffic không?”.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp SQL Server hoặc external API, một outage downstream có thể khiến orchestrator restart toàn bộ healthy application instances. Restart storm vừa không sửa dependency vừa làm recovery khó hơn.

**Ví dụ:**
```text
/liveness
  process/event-loop/runtime health

/readiness
  critical configuration
  database connectivity when required to serve requests
  startup initialization state
```
Kubernetes có thể tạm loại pod khỏi Service khi readiness fail mà không nhất thiết kill process.

**Lưu ý:**
Đừng đưa mọi external dependency vào readiness. Một optional recommendation API bị lỗi không nhất thiết khiến checkout API phải ngừng nhận traffic. Health semantics phải phản ánh capability thực tế của service.

### Tip 4 — Với Vue, tránh deep watcher trên object lớn nếu chỉ quan tâm vài dependency

**Mẹo:**
Trong Vue.js, watch đúng reactive source cần thiết thay vì dùng `deep: true` trên một state tree lớn để bắt mọi thay đổi.

**Tại sao hữu ích:**
Deep watcher phải traverse nested properties để theo dõi thay đổi, làm cost tăng theo kích thước object và khiến side effect bị kích hoạt bởi những field không liên quan. Dependency cụ thể cũng giúp code dễ reasoning hơn.

**Ví dụ:**
```ts
watch(
  () => [filters.categoryId, filters.sortBy],
  () => reloadProducts(),
  { flush: 'post' }
)
```
Thay vì watch toàn bộ `filters`, chỉ các field thực sự thay đổi query mới trigger reload.

**Lưu ý:**
Đừng biến watcher thành nơi chứa business workflow phức tạp. Nếu nhiều state transitions phối hợp với nhau, explicit action/composable thường dễ test và kiểm soát hơn.

### Tip 5 — Dùng `git bisect` khi biết regression nằm giữa hai commit nhưng không biết commit nào

**Mẹo:**
Khi một behavior từng hoạt động và hiện tại bị lỗi, dùng `git bisect` để binary-search lịch sử thay vì checkout từng commit thủ công.

**Tại sao hữu ích:**
Với hàng trăm commits, binary search giảm đáng kể số lần kiểm tra. Nếu có automated test tái hiện regression, `git bisect run` còn có thể tự động tìm commit đầu tiên làm test fail.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests

git bisect reset
```

**Lưu ý:**
Test dùng cho bisect phải deterministic và exit code phải phản ánh good/bad đúng. Nếu intermediate commits không build được, cần xử lý `skip` hoặc script phù hợp; đừng kết luận culprit chỉ từ một flaky test.

## 🧠 Software Design

### Design 1 — Circuit Breaker không thay thế Retry

**Khái niệm:**
Retry xử lý failure có khả năng transient bằng cách thử lại có kiểm soát. Circuit Breaker quan sát failure và tạm thời chặn calls khi dependency có dấu hiệu unhealthy, tránh tiếp tục gửi traffic vô ích trong một khoảng recovery.

**Vấn đề nó giải quyết:**
Payment provider bắt đầu timeout. Nếu mọi request đều retry nhiều lần, service của bạn nhân traffic vào dependency đang lỗi, giữ threads/connections lâu hơn và làm latency lan sang toàn hệ thống.

**Ví dụ thực tế:**
Checkout chỉ retry một số network/transient failures với exponential backoff + jitter. Khi failure ratio vượt threshold trong sampling window, circuit mở và fail fast; sau break duration, một số calls được phép thử lại để kiểm tra recovery.

**Trade-off:**
Retry có thể vượt qua lỗi ngắn nhưng tăng load và latency. Circuit Breaker bảo vệ resource và giảm cascading failure nhưng có thể reject calls trong lúc dependency vừa hồi phục. Threshold, sampling window và fallback behavior cần telemetry thực tế.

**Middle → Senior insight:**
Middle developer cần phân loại lỗi retryable và hiểu trạng thái circuit. Senior / Technical developer phải thiết kế resilience theo end-to-end latency budget, idempotency, dependency capacity và failure domain; xếp chồng retry ở nhiều tầng có thể tạo retry amplification nguy hiểm.

### Design 2 — Database per service vs shared database

**Khái niệm:**
Database per service trao quyền sở hữu data/schema cho một service boundary và buộc integrations đi qua contract. Shared database cho nhiều modules/services đọc ghi cùng schema, đơn giản hơn ban đầu nhưng tạo coupling ở tầng dữ liệu.

**Vấn đề nó giải quyết:**
Khi nhiều independently deployed services sửa cùng tables, một schema migration hoặc query trực tiếp có thể phá service khác mà không có API contract bảo vệ. Tuy nhiên, tách database quá sớm lại biến joins và transactions đơn giản thành distributed workflows.

**Ví dụ thực tế:**
Trong Modular Monolith, Ordering và Catalog có thể cùng SQL Server instance nhưng sở hữu schema/tables riêng và không ghi chéo. Khi Ordering thật sự cần scale/deploy độc lập, ownership rõ giúp tách physical database dễ hơn so với một shared relational model hỗn hợp.

**Trade-off:**
Database per service tăng autonomy nhưng kéo theo eventual consistency, duplicated data, integration events và operational overhead. Shared database hỗ trợ ACID transaction và reporting/query đơn giản nhưng làm deployment coupling tăng nếu ownership không được kiểm soát.

**Middle → Senior insight:**
Middle developer cần tôn trọng data ownership và không bypass boundary bằng SQL tiện tay. Senior / Technical developer phải phân biệt logical ownership với physical database separation, đánh giá transaction needs, reporting, team ownership và migration cost trước khi tách.

### Design 3 — Anti-Corruption Layer khi tích hợp legacy hoặc third-party domain

**Khái niệm:**
Anti-Corruption Layer (ACL) dịch model, terminology và protocol của external/legacy system sang model mà application của bạn hiểu, thay vì để external concepts lan trực tiếp vào domain core.

**Vấn đề nó giải quyết:**
Một legacy ERP dùng `CustType`, magic status codes và nullable monetary fields với semantics riêng. Nếu toàn bộ application dùng trực tiếp DTO đó, business logic mới bị khóa vào naming, quirks và lifecycle của hệ thống bên ngoài.

**Ví dụ thực tế:**
Integration adapter nhận ERP response `status = "A"`, `cust_type = 7`, rồi map thành `CustomerStatus.Active` và domain-specific `CustomerCategory`. Khi ERP đổi protocol hoặc được thay thế, phần lớn domain/application code không cần biết.

**Trade-off:**
ACL bảo vệ domain model, tập trung mapping và giúp migration dễ hơn, nhưng thêm code, mapping tests và nguy cơ duplicate concepts. Với integration nhỏ chỉ truyền dữ liệu thuần túy, một adapter đơn giản có thể đủ; không cần dựng layer phức tạp.

**Middle → Senior insight:**
Middle developer cần giữ external DTO ở integration boundary và test mapping semantics. Senior / Technical developer phải xác định chỗ nào thực sự cần translation, ownership của canonical model và cách xử lý semantic mismatch; ACL không nên trở thành một “god mapper” chứa mọi business rule.
