# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `dotnet-counters` để phân biệt CPU pressure với ThreadPool starvation

**Mẹo:**
Khi ASP.NET Core API chậm nhưng CPU chưa chắc đã cao, quan sát đồng thời CPU usage, ThreadPool queue length, thread count và request rate bằng `dotnet-counters` hoặc telemetry tương đương trước khi tăng instance.

**Tại sao hữu ích:**
ThreadPool starvation thường xuất hiện khi request threads bị block bởi synchronous I/O, `.Result`, `.Wait()` hoặc workload blocking kéo dài. Latency có thể tăng mạnh trong khi CPU vẫn còn capacity, nên chỉ nhìn CPU dễ dẫn đến chẩn đoán sai.

**Ví dụ:**
Sau deployment, p99 tăng từ 300 ms lên 8 s; CPU chỉ 45% nhưng ThreadPool queue tăng liên tục. Trace chỉ ra một SDK mới được gọi bằng synchronous wrapper trong request path. Loại bỏ blocking call giúp queue trở về bình thường mà không cần scale-out.

**Lưu ý:**
Thread count cao không tự động chứng minh starvation. Luôn ghép counters với traces, request latency và stack evidence; tăng minimum worker threads chỉ có thể che triệu chứng nếu nguyên nhân là blocking I/O.

### Tip 2 — EF Core optimistic concurrency cần xử lý conflict như business outcome

**Mẹo:**
Với dữ liệu có concurrent updates, dùng concurrency token như `rowversion` và xử lý `DbUpdateConcurrencyException` có chủ đích thay vì retry toàn bộ command một cách mù quáng.

**Tại sao hữu ích:**
Optimistic concurrency cho phép database phát hiện entity đã thay đổi kể từ lúc đọc. Nhưng framework chỉ phát hiện conflict; application vẫn phải quyết định reload, merge, reject hay yêu cầu người dùng xác nhận lại dựa trên business semantics.

**Ví dụ:**
Hai nhân viên cùng sửa giá sản phẩm. Người thứ hai save với `rowversion` cũ và nhận conflict. Back-office UI có thể tải current values và cho người dùng so sánh thay vì silently overwrite giá mới nhất.

**Lưu ý:**
Không phải conflict nào cũng nên auto-retry. Retry phù hợp với operation có thể tính lại an toàn; với user-authored state, retry có thể biến lost update thành silent overwrite.

### Tip 3 — Elasticsearch mapping sai thường phải sửa bằng reindex, không chỉ update query

**Mẹo:**
Xác định trước field nào cần full-text search, exact filtering, sorting hoặc aggregation và thiết kế `text`/`keyword` mapping tương ứng. Khi mapping semantics đã sai trên dữ liệu hiện hữu, chuẩn bị reindex strategy.

**Tại sao hữu ích:**
Analyzer biến text thành tokens phục vụ relevance search, trong khi filter/sort thường cần exact values. Chọn mapping sai có thể gây kết quả tìm kiếm kỳ lạ, aggregation không đúng hoặc query tốn tài nguyên; nhiều thay đổi mapping không thể sửa in-place cho dữ liệu đã index.

**Ví dụ:**
`ProductName` dùng `text` cho search nhưng thêm `keyword` subfield cho exact sort/filter. Khi analyzer cần đổi, tạo index version mới, reindex dữ liệu, validate rồi chuyển alias thay vì mutate production index trực tiếp.

**Lưu ý:**
Đừng duplicate mọi field thành nhiều variants nếu không có query requirement. Mapping explosion làm tăng cluster state, storage và operational cost.

### Tip 4 — Kubernetes readiness probe không nên kiểm tra mọi dependency như liveness probe

**Mẹo:**
Tách rõ liveness và readiness: liveness trả lời process có cần restart không; readiness trả lời instance có nên nhận traffic không.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp vào database hoặc external API, outage downstream có thể khiến Kubernetes restart hàng loạt healthy application processes, tạo restart storm và làm recovery khó hơn.

**Ví dụ:**
ASP.NET Core process vẫn sống nhưng database tạm unavailable. Readiness có thể loại pod khỏi traffic nếu request không thể phục vụ, trong khi liveness vẫn healthy để pod không bị restart vô ích.

**Lưu ý:**
Readiness quá nhạy cũng có thể loại toàn bộ replicas cùng lúc. Health checks cần timeout ngắn, dependency semantics rõ và được load-test dưới failure conditions.

### Tip 5 — File upload phải được coi là untrusted input kể cả khi extension hợp lệ

**Mẹo:**
Với API/CMS upload, kiểm tra size limit, authorization, generated storage name, content validation phù hợp và lưu file ngoài executable web root khi có thể; không tin filename, extension hoặc client-provided MIME type.

**Tại sao hữu ích:**
Filename có thể chứa path tricks, MIME type có thể giả mạo và file quá lớn có thể gây memory/disk exhaustion. Upload pipeline là security boundary chứ không chỉ là form handling.

**Ví dụ:**
CMS nhận ảnh, tạo server-side object key mới, giới hạn kích thước, validate định dạng thực tế, scan theo policy rồi lưu Blob Storage bằng private access; client chỉ nhận controlled URL/SAS theo authorization.

**Lưu ý:**
Đừng đọc toàn bộ file lớn vào memory nếu có thể stream. Validation cũng không thay thế malware scanning hoặc downstream content-safety controls khi threat model yêu cầu.

## 🧠 Software Design

### Design 1 — Optimistic vs Pessimistic Concurrency phải dựa trên contention

**Khái niệm:**
Optimistic concurrency cho phép nhiều actors làm việc song song rồi phát hiện conflict lúc commit; pessimistic concurrency giữ lock sớm để ngăn conflict xảy ra. Đây là lựa chọn về contention, latency và failure semantics chứ không phải preference framework.

**Vấn đề nó giải quyết:**
Concurrent writes có thể gây lost update hoặc vi phạm invariant. Hệ thống cần quyết định nên chấp nhận conflict hiếm và xử lý sau, hay serialize access ngay từ đầu vì conflict quá đắt.

**Ví dụ thực tế:**
CMS content editing thường phù hợp optimistic concurrency vì hai editors sửa cùng item tương đối hiếm. Một allocation workflow với inventory cực khan hiếm có thể cần database locking hoặc atomic conditional update chặt hơn để bảo vệ invariant.

**Trade-off:**
Optimistic approach tăng concurrency và tránh giữ lock lâu nhưng buộc application xử lý conflict/retry. Pessimistic locking đơn giản hóa một số critical sections nhưng tăng blocking, deadlock risk và giảm throughput nếu transaction kéo dài.

**Middle → Senior insight:**
Middle developer cần implement concurrency token/transaction đúng và không nuốt conflict. Senior / Technical developer phải đo contention, xác định invariant, failure cost và chọn atomic update, optimistic retry hay locking theo workload thực tế.

### Design 2 — Bulkhead Pattern giới hạn blast radius của dependency failure

**Khái niệm:**
Bulkhead cô lập capacity giữa các workload hoặc dependencies để một thành phần bị chậm không tiêu thụ toàn bộ threads, connections hay concurrency slots của application.

**Vấn đề nó giải quyết:**
Nếu một third-party recommendation API treo và mọi request đều chờ nó, shared connection/concurrency resources có thể cạn, khiến cả checkout hoặc account API cũng suy giảm dù chúng không phụ thuộc trực tiếp vào recommendation.

**Ví dụ thực tế:**
E-commerce backend đặt timeout và concurrency limit riêng cho recommendation calls. Khi dependency bão hòa, recommendation degrade/fallback sớm trong khi capacity cho payment và order flows vẫn được bảo vệ.

**Trade-off:**
Isolation giảm blast radius nhưng capacity partitioning có thể làm tài nguyên nhàn rỗi ở một pool trong khi pool khác bão hòa. Quá nhiều bulkheads cũng tăng configuration và observability complexity.

**Middle → Senior insight:**
Middle developer cần hiểu timeout/concurrency limit và fallback semantics. Senior / Technical developer phải xác định failure domains, capacity budgets và criticality để cô lập đúng nơi thay vì áp policy đồng nhất cho mọi dependency.

### Design 3 — Schema evolution cho events cần consumer-first thinking

**Khái niệm:**
Event contract là integration boundary sống lâu hơn một deployment. Evolution an toàn thường ưu tiên additive changes, tolerant readers và rollout order phù hợp thay vì sửa payload rồi deploy tất cả cùng lúc.

**Vấn đề nó giải quyết:**
Producer và consumers không luôn release đồng thời. Rename/remove field hoặc thay semantics có thể làm consumer cũ hỏng, đưa messages vào dead-letter queue hoặc tệ hơn là xử lý sai mà không báo lỗi.

**Ví dụ thực tế:**
`OrderPlaced` cần thêm `SalesChannel`. Producer trước tiên thêm field optional; consumers mới được deploy để hiểu field; chỉ khi compatibility window kết thúc mới cân nhắc thay đổi contract cũ hoặc phát event version mới nếu semantics thật sự khác.

**Trade-off:**
Backward compatibility làm schema tích lũy fields và migration kéo dài. Version mới cho boundary rõ hơn nhưng tăng routing, duplicate handlers và operational burden khi nhiều versions cùng tồn tại.

**Middle → Senior insight:**
Middle developer cần tránh breaking changes và test serialization/consumer compatibility. Senior / Technical developer phải thiết kế ownership, compatibility window, rollout sequence, observability và deprecation policy cho toàn ecosystem.
