# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng JSON source generation cho hot path serialization ổn định

**Mẹo:**
Với model JSON được serialize/deserialize thường xuyên và shape ổn định, cân nhắc `System.Text.Json` source generation thay vì để runtime luôn dựa vào reflection metadata.

**Tại sao hữu ích:**
Giảm startup/runtime metadata overhead, phù hợp với Native AOT và giúp contract serialization được khai báo rõ hơn ở compile time.

**Ví dụ:**
```csharp
[JsonSerializable(typeof(OrderDto))]
internal partial class AppJsonContext : JsonSerializerContext
{
}

var json = JsonSerializer.Serialize(
    order,
    AppJsonContext.Default.OrderDto);
```

**Lưu ý:**
Không cần áp dụng cho mọi DTO nhỏ. Nếu model rất dynamic hoặc dùng custom converter phức tạp, hãy kiểm tra compatibility trước khi chuyển sang source-generated context.

### Tip 2 — Dùng SQL Server Query Store để điều tra regression theo thời gian

**Mẹo:**
Khi một query “hôm qua nhanh, hôm nay chậm”, dùng Query Store để so sánh execution plan và runtime statistics theo khoảng thời gian thay vì chỉ xem plan hiện tại.

**Tại sao hữu ích:**
Giúp phát hiện plan regression, thay đổi cardinality estimate hoặc một plan mới có CPU/duration cao hơn sau deploy hay statistics update.

**Ví dụ:**
Scenario: cùng `query_id` có plan A chạy trung bình 80 ms tuần trước nhưng plan B chạy 2.5 s từ sáng nay. Query Store cho phép đối chiếu plan history trước khi quyết định force plan hay sửa query/index.

**Lưu ý:**
Force plan chỉ là biện pháp kiểm soát tạm thời nếu root cause chưa rõ. Vẫn cần kiểm tra data distribution, statistics, parameter sensitivity và index design.

### Tip 3 — Dùng `git cherry-pick -x` khi backport fix sang release branch

**Mẹo:**
Khi cherry-pick một bug fix sang release branch, dùng `-x` để Git thêm reference tới commit gốc trong commit message.

**Tại sao hữu ích:**
Sau này dễ audit một fix production đến từ commit nào trên main và tránh backport cùng thay đổi hai lần.

**Ví dụ:**
```bash
git cherry-pick -x <commit-sha>
```

Commit mới sẽ có dòng tham chiếu tới commit nguồn.

**Lưu ý:**
`-x` chỉ tạo traceability, không đảm bảo patch tương thích với release branch. Luôn test lại vì code context có thể khác main.

### Tip 4 — Dùng BuildKit secret mount thay vì `ARG`/`ENV` cho secret lúc Docker build

**Mẹo:**
Nếu build cần private NuGet feed, npm token hoặc credential tạm thời, dùng BuildKit secret mount để secret không bị ghi vào layer history.

**Tại sao hữu ích:**
Giảm nguy cơ token xuất hiện trong image layer, `docker history`, cache hoặc build logs.

**Ví dụ:**
Dockerfile:

```dockerfile
RUN --mount=type=secret,id=nuget_token \
    TOKEN=$(cat /run/secrets/nuget_token) && \
    ./restore-private-packages.sh "$TOKEN"
```

Build:

```bash
docker build \
  --secret id=nuget_token,env=NUGET_TOKEN \
  -t myapp .
```

**Lưu ý:**
Script vẫn có thể làm lộ secret nếu echo command hoặc ghi token ra file thuộc layer. Secret mount chỉ an toàn khi downstream command cũng xử lý credential đúng cách.

### Tip 5 — Dùng cancellation trong test để bắt async code bị treo

**Mẹo:**
Với integration test hoặc test background workflow, đặt timeout/cancellation rõ ràng để test fail nhanh thay vì treo CI vô thời hạn.

**Tại sao hữu ích:**
Giúp phát hiện deadlock, uncompleted task, message không bao giờ tới hoặc wait condition sai mà không làm cả pipeline đứng hàng chục phút.

**Ví dụ:**
```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(10));

var result = await service
    .ProcessAsync(cts.Token)
    .WaitAsync(cts.Token);
```

**Lưu ý:**
Timeout quá ngắn sẽ tạo flaky test trên CI chậm. Chọn budget dựa trên behavior thực tế và log đủ context khi timeout xảy ra.

## 🧠 Software Design

### Design 1 — Retry Budget để resilience không biến thành traffic amplification

**Khái niệm:**
Retry Budget giới hạn số retry mà một request, service hoặc khoảng thời gian được phép tạo ra, thay vì cho mỗi tầng retry độc lập không giới hạn.

**Vấn đề nó giải quyết:**
Khi dependency chậm, Gateway retry 3 lần, Service A retry 3 lần và Service B cũng retry 3 lần có thể biến một request thành hàng chục downstream calls đúng lúc hệ thống đang quá tải.

**Ví dụ thực tế:**
Một request có tổng budget 2 retry cho toàn call chain. Nếu Service A đã dùng cả hai lần để gọi Payment API, downstream khác không tiếp tục retry thêm mà phải fail hoặc fallback theo policy.

**Trade-off:**
Retry budget giảm retry storm và giúp latency/capacity predictable hơn, nhưng có thể làm một số transient failure không được thử lại nhiều như trước. Cần chọn budget dựa trên SLO và failure profile thực tế.

**Middle → Senior insight:**
Middle developer nên hiểu retry không phải “càng nhiều càng an toàn”. Senior developer phải phối hợp retry count, backoff, jitter, deadline và budget xuyên service boundary để resilience không tự phá hệ thống.

### Design 2 — Backward-compatible database contract giữa nhiều phiên bản application

**Khái niệm:**
Trong rolling deployment, database schema phải hỗ trợ đồng thời phiên bản application cũ và mới trong một compatibility window.

**Vấn đề nó giải quyết:**
Nếu code mới deploy 50% instance rồi schema migration đổi semantics ngay, 50% instance cũ còn chạy có thể đọc sai, ghi lỗi hoặc crash.

**Ví dụ thực tế:**
Muốn thay cột `Status` string bằng `StatusCode` integer:

- Add `StatusCode` trước.
- Deploy code mới đọc được cả hai và ghi theo strategy chuyển tiếp.
- Backfill dữ liệu.
- Chuyển toàn bộ traffic sang version mới.
- Sau compatibility window mới remove `Status` cũ.

**Trade-off:**
Giảm deployment risk và hỗ trợ rollback, nhưng tăng code chuyển tiếp, dual-write/read và cleanup work. Nếu compatibility window kéo dài, temporary design dễ biến thành permanent debt.

**Middle → Senior insight:**
Middle developer nên hiểu schema migration và application deployment là một workflow chung. Senior developer phải định nghĩa compatibility matrix, rollout order, rollback path và exit criteria trước khi production change bắt đầu.

### Design 3 — Bounded Staleness khi không cần Strong Consistency tuyệt đối

**Khái niệm:**
Bounded Staleness cho phép dữ liệu đọc chậm hơn source of truth trong một giới hạn được xác định, ví dụ tối đa 5 giây hoặc tối đa 100 versions.

**Vấn đề nó giải quyết:**
Strong consistency trên mọi read có thể làm tăng latency, coordination và giảm availability, trong khi nhiều use case chỉ cần dữ liệu “gần mới nhất”.

**Ví dụ thực tế:**
Dashboard operational có thể chấp nhận số liệu trễ tối đa 10 giây, nhưng endpoint xác nhận số dư trước khi chuyển tiền thì không. Hai use case không nên dùng cùng consistency strategy chỉ vì cùng đọc một domain.

**Trade-off:**
Bounded staleness giúp scale read và giảm coupling với primary state, nhưng cần đo được freshness và xử lý rõ khi lag vượt giới hạn. User experience cũng phải phù hợp với dữ liệu có thể hơi cũ.

**Middle → Senior insight:**
Middle developer nên phân biệt strong consistency với eventual consistency chung chung. Senior developer phải lượng hóa freshness requirement, chọn replication/cache/read-model strategy và thiết kế fallback khi staleness vượt SLO.
