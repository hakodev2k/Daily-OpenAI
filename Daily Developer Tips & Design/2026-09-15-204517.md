# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — EF Core: projection trước, `Include` sau khi thật sự cần entity graph

**Mẹo:**
Với read endpoint chỉ trả DTO, ưu tiên `Select` đúng các field cần thiết thay vì `Include` cả entity graph rồi map trong memory.

**Tại sao hữu ích:**
Projection cho EF Core tạo SQL hẹp hơn, giảm dữ liệu truyền từ database, allocation và change-tracking overhead. `Include` đặc biệt dễ tạo result set lớn khi nhiều collection navigation được join cùng lúc.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(x.Id, x.CreatedAt, x.Total))
    .ToListAsync(ct);
```

Một API danh sách order không cần materialize `Customer`, `OrderItems` và `Product` nếu response chỉ hiển thị summary.

**Lưu ý:**
Projection không phải luôn tốt hơn `Include`: nếu business operation thực sự cần aggregate/entity graph để thay đổi state, entity loading có thể đúng hơn. Luôn xem SQL thực tế khi query phức tạp thay vì suy đoán từ LINQ.

### Tip 2 — Redis: thêm jitter vào TTL để giảm cache stampede đồng thời

**Mẹo:**
Khi nhiều cache key được tạo cùng lúc, tránh đặt cùng một TTL cố định cho tất cả. Thêm một khoảng jitter ngẫu nhiên hợp lý để các key không expire đồng loạt.

**Tại sao hữu ích:**
Nếu 20.000 key cùng hết hạn ở phút thứ 30, lượng cache miss có thể đổ đồng thời xuống SQL hoặc external API. Jitter phân tán thời điểm refresh, làm load downstream mượt hơn mà không thay đổi cache-aside architecture.

**Ví dụ:**
```csharp
var ttl = TimeSpan.FromMinutes(30)
        + TimeSpan.FromSeconds(Random.Shared.Next(0, 180));

await cache.SetStringAsync(key, payload,
    new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl }, ct);
```

**Lưu ý:**
TTL jitter không giải quyết hoàn toàn hot-key stampede. Với một key cực nóng, có thể cần request coalescing/single-flight, stale-while-revalidate hoặc distributed coordination phù hợp. Không thêm jitter lớn hơn freshness requirement của dữ liệu.

### Tip 3 — File upload: đừng tin `Content-Type` và filename từ client

**Mẹo:**
Khi ASP.NET Core nhận file upload, coi filename, extension và `Content-Type` là dữ liệu không đáng tin cậy. Tạo storage name phía server, giới hạn kích thước và xác minh loại file theo policy thực tế.

**Tại sao hữu ích:**
Client có thể gửi `Content-Type: image/png` cho nội dung không phải PNG hoặc filename chứa dữ liệu gây lỗi path/logging. Việc tách user-visible filename khỏi storage identifier giảm khả năng path traversal, overwrite và xử lý file sai loại.

**Ví dụ:**
```csharp
var storageName = $"{Guid.NewGuid():N}.bin";

if (file.Length is 0 or > 10 * 1024 * 1024)
    return Results.BadRequest();
```

Với image/document workflow, validation có thể kiểm tra signature/magic bytes và xử lý file trong isolated storage thay vì thực thi/phục vụ trực tiếp từ upload directory.

**Lưu ý:**
Magic-byte validation cũng không biến file thành an toàn tuyệt đối. Tùy threat model còn cần malware scanning, image re-encoding, authorization, quota và tránh public execution permission trên upload storage.

### Tip 4 — AI coding agent: yêu cầu evidence từ repository trước khi chấp nhận refactor

**Mẹo:**
Khi dùng AI coding agent để sửa codebase, buộc proposal bám vào source hiện tại: exact file, call path, tests và version dependency; sau đó xác minh diff bằng build/test thay vì chỉ đánh giá lời giải thích.

**Tại sao hữu ích:**
Agent có thể tạo API không tồn tại, áp dụng pattern từ version khác hoặc thêm abstraction dựa trên assumption sai. Grounding vào repository biến câu trả lời từ “có vẻ hợp lý” thành hypothesis có evidence kiểm tra được.

**Ví dụ:**
```text
Yêu cầu agent:
1. chỉ ra call path gây duplicate query;
2. trích file/method liên quan;
3. đề xuất minimal diff;
4. thêm regression test;
5. chạy build/test và báo failure còn lại.
```

**Lưu ý:**
Test pass không chứng minh architecture hoặc security đúng. Review boundary, generated SQL, authorization và operational behavior vẫn cần engineering judgment; tránh để agent tự mở rộng scope ngoài requirement.

### Tip 5 — Kubernetes: kiểm tra `requests` trước khi kết luận autoscaling thiếu pod

**Mẹo:**
Khi Horizontal Pod Autoscaler phản ứng bất thường với CPU, kiểm tra container `resources.requests.cpu` cùng metric trước khi chỉ tăng `maxReplicas`.

**Tại sao hữu ích:**
CPU utilization của HPA thường được diễn giải tương đối với requested CPU. Nếu request đặt quá thấp hoặc không phản ánh workload, utilization có thể luôn cao dù node còn tài nguyên; ngược lại request quá lớn có thể làm signal scale kém nhạy và ảnh hưởng scheduling.

**Ví dụ:**
```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

Điều tra nên nối `traffic -> per-pod throughput -> CPU usage -> request -> HPA target -> scheduling`, không chỉ nhìn số pod.

**Lưu ý:**
Scale-out không sửa bottleneck ở SQL, lock hoặc external dependency. Nếu mỗi pod mới chỉ tạo thêm database connections và contention, tăng replica có thể làm latency tệ hơn.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency cho business update có xung đột hiếm

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng state nhưng phát hiện conflict tại thời điểm update bằng version/token thay vì giữ lock dài từ lúc đọc đến lúc ghi.

**Vấn đề nó giải quyết:**
Hai nhân viên mở cùng customer record. Người A cập nhật địa chỉ, người B lưu form cũ vài phút sau và vô tình ghi đè thay đổi của A. Last-write-wins âm thầm làm mất dữ liệu dù cả hai request đều “thành công”.

**Ví dụ thực tế:**
```csharp
public class Customer
{
    public int Id { get; set; }
    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
```

EF Core đưa concurrency token vào `UPDATE`; nếu row đã đổi, affected rows bằng 0 và application có thể trả conflict/reload workflow thay vì overwrite.

**Trade-off:**
Optimistic concurrency không giữ lock lâu và phù hợp khi conflict hiếm, nhưng application phải định nghĩa cách resolve conflict. Nếu contention cực cao và operation không thể merge/retry hợp lý, pessimistic coordination hoặc redesign workflow có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần xử lý `DbUpdateConcurrencyException` như business conflict chứ không retry vô hạn. Senior / Technical developer phải chọn conflict boundary, UX/API semantics, merge policy và đánh giá contention thực tế trước khi chọn optimistic hay pessimistic strategy.

### Design 2 — Azure Functions hay Worker Service dựa trên execution model

**Khái niệm:**
Azure Functions phù hợp với event-driven/serverless execution khi platform-managed scaling và trigger model mang lại giá trị. Worker Service phù hợp hơn khi cần process sống lâu, lifecycle kiểm soát rõ hoặc workload liên tục có resource profile ổn định.

**Vấn đề nó giải quyết:**
Team cần xử lý background workload và dễ mặc định “background = Function”. Nhưng một processor chạy liên tục, giữ connection/resource dài hạn và cần kiểm soát concurrency chi tiết có thể không hưởng lợi từ serverless execution model.

**Ví dụ thực tế:**
```text
Blob upload không thường xuyên -> Function trigger có thể đơn giản.

Service Bus processor liên tục,
custom batching + long-lived coordination + predictable load
-> Worker Service/App Service/container có thể dễ vận hành hơn.
```

**Trade-off:**
Functions giảm infrastructure management và tích hợp trigger tốt nhưng có execution/scaling/runtime constraints và cần hiểu retry/idempotency. Worker Service cho lifecycle/control rõ hơn nhưng team chịu trách nhiệm deployment, scaling và capacity nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retries, cancellation và graceful shutdown của execution model mình dùng. Senior / Solution-oriented engineer phải so sánh workload shape, latency, scaling, cost, observability, deployment và operational ownership thay vì chọn theo độ “cloud-native”.

### Design 3 — Anti-Corruption Layer khi tích hợp legacy domain khác ngôn ngữ

**Khái niệm:**
Anti-Corruption Layer (ACL) đặt translation boundary giữa model nội bộ và external/legacy system để domain bên ngoài không lan trực tiếp vào core model của application.

**Vấn đề nó giải quyết:**
Một legacy ERP gọi khách hàng là `Account`, trạng thái dùng numeric code và monetary field có semantics khác hệ thống mới. Nếu DTO ERP được truyền xuyên application, business code mới bắt đầu phụ thuộc vào naming, nullability và quirks của external contract.

**Ví dụ thực tế:**
```text
ERP payload
{ acct_no, status: 7, credit_amt }
        |
        v
ERP Adapter / ACL
        |
        v
CustomerCreditSnapshot
{ CustomerId, CreditLimit, Status }
```

Mapping và external failure semantics được giữ tại integration boundary thay vì rải `if (status == 7)` khắp domain code.

**Trade-off:**
ACL giảm coupling và bảo vệ domain model nhưng thêm mapping code, test và maintenance. Với integration rất nhỏ, ổn định và model gần như đồng nhất, một adapter mỏng có thể đủ; dựng layer phức tạp không tự tạo giá trị.

**Middle → Senior insight:**
Middle developer cần giữ external DTO và translation logic ở boundary rõ ràng. Senior / Technical developer phải xác định phần semantics nào cần cách ly, ownership của mapping/versioning và cân bằng chi phí ACL với khả năng external system thay đổi hoặc được thay thế trong tương lai.
