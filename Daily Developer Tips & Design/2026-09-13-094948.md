# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Hiểu `IHttpClientFactory` để tránh stale DNS và quản lý handler lifetime đúng cách

**Mẹo:**
Trong ASP.NET Core, ưu tiên `IHttpClientFactory` hoặc typed client cho outbound HTTP thay vì tạo `new HttpClient()` cho mỗi request hoặc giữ một client tùy tiện mà không hiểu lifetime của underlying handler.

**Tại sao hữu ích:**
`HttpClient` tái sử dụng connection qua `SocketsHttpHandler`. Tạo client liên tục có thể gây socket churn, còn giữ handler quá lâu có thể khiến application dùng DNS cũ sau khi downstream đổi IP. `IHttpClientFactory` quản lý handler pool/lifetime để cân bằng connection reuse và DNS refresh.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri("https://inventory.internal");
    client.Timeout = TimeSpan.FromSeconds(3);
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

Sau đó inject `InventoryClient` thay vì tự quản lý connection lifecycle ở từng service.

**Lưu ý:**
`IHttpClientFactory` không tự biến mọi retry thành an toàn. Với `POST` hoặc operation có side effect, retry phải đi cùng idempotency semantics. Handler lifetime cũng không nên chỉnh ngẫu nhiên; cần dựa trên DNS/network behavior thực tế.

### Tip 2 — Dùng SQL Server Query Store để phát hiện plan regression thay vì đoán từ code

**Mẹo:**
Khi một query vốn chạy nhanh bỗng chậm sau deployment, statistics update hoặc data growth, kiểm tra Query Store để so execution plan, duration, CPU và read history theo thời gian.

**Tại sao hữu ích:**
Nhiều regression không đến từ thay đổi query text mà từ optimizer chọn plan khác do parameter distribution hoặc statistics. Query Store cung cấp evidence lịch sử để phân biệt code regression với plan regression.

**Ví dụ:**
```text
Triệu chứng:
- API /orders/search tăng p95 từ 120 ms lên 2.4 s

Query Store cho thấy:
- query_id không đổi
- plan_id đổi lúc 08:15
- logical reads tăng 25x
- plan mới dùng scan thay vì seek
```

Từ đó mới điều tra parameter sensitivity, statistics, index hoặc plan forcing như một biện pháp tạm thời.

**Lưu ý:**
Đừng force plan rồi coi incident đã xong. Plan cũ có thể chỉ tốt với data distribution trước đây. Cần xác định root cause và theo dõi storage/retention của Query Store trong production.

### Tip 3 — Giảm Redis round-trip bằng pipelining hoặc multi-key operation khi access pattern cho phép

**Mẹo:**
Nếu một request cần đọc nhiều Redis key độc lập, tránh `await` tuần tự từng `GET`. Dùng `MGET`, pipelining hoặc batch phù hợp để giảm network round-trip.

**Tại sao hữu ích:**
Redis command thường rất nhanh; latency tổng nhiều khi bị chi phối bởi network. Mười lệnh 0.3 ms server-side nhưng mỗi lệnh mất 1 ms round-trip có thể chậm hơn đáng kể so với gửi chúng theo batch/pipeline.

**Ví dụ:**
```text
Kém:
GET product:1
await
GET product:2
await
GET product:3
await

Tốt hơn khi semantics phù hợp:
MGET product:1 product:2 product:3
```

Với client hỗ trợ multiplexing, có thể phát nhiều operation trước rồi await kết quả cùng lúc.

**Lưu ý:**
Đừng batch vô hạn. Payload lớn làm tăng memory và tail latency. Với Redis Cluster, multi-key command còn bị ràng buộc bởi hash slot; thiết kế key phải phù hợp nếu cần atomic/multi-key behavior.

### Tip 4 — Hủy request cũ trong React khi dependency đổi để tránh stale response ghi đè state mới

**Mẹo:**
Trong React, khi `useEffect` gọi API theo search/filter, dùng `AbortController` hoặc cancellation mechanism của data library để hủy request trước đó khi dependency thay đổi hoặc component unmount.

**Tại sao hữu ích:**
Request A có thể bắt đầu trước request B nhưng trả về sau. Nếu cả hai cùng cập nhật state, UI có thể hiển thị dữ liệu cũ dù user đã nhập query mới. Đây là race condition ở frontend chứ không chỉ là vấn đề “cleanup”.

**Ví dụ:**
```tsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  })
    .then(r => r.json())
    .then(setResults)
    .catch(err => {
      if (err.name !== 'AbortError') throw err;
    });

  return () => controller.abort();
}, [query]);
```

**Lưu ý:**
Cancellation phía client không đảm bảo server đã dừng work nếu backend không propagate disconnect/cancellation. Với data-fetching library như TanStack Query, ưu tiên dùng cơ chế cancellation/cache built-in thay vì tự viết lại toàn bộ lifecycle.

### Tip 5 — Dùng Managed Identity cho Azure resource access thay vì phát secret dài hạn cho application

**Mẹo:**
Khi App Service, Function hoặc VM cần đọc Key Vault, Blob Storage hoặc Service Bus, ưu tiên Managed Identity + RBAC thay vì lưu connection string/password dài hạn trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời phân phối/rotate secret ở application level. Token được cấp động bởi Azure identity platform, giảm nguy cơ secret bị commit nhầm, log ra hoặc tồn tại quá lâu trong pipeline.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Local development có thể dùng developer credential, production chuyển sang Managed Identity mà không đổi business code.

**Lưu ý:**
Managed Identity không tự tạo least privilege. RBAC vẫn phải giới hạn đúng resource/action. Cũng cần tránh việc application đọc quá nhiều secret vì “không còn password”; identity compromise vẫn có blast radius tương ứng với quyền đã cấp.

## 🧠 Software Design

### Design 1 — Saga Orchestration vs Choreography cho workflow phân tán nhiều bước

**Khái niệm:**
Saga chia workflow business dài thành nhiều local transaction kèm compensation. Orchestration dùng một coordinator điều khiển thứ tự bước; Choreography để service phản ứng với event của nhau mà không có central coordinator.

**Vấn đề nó giải quyết:**
Order workflow có thể cần reserve inventory, authorize payment, tạo shipment và gửi notification. Không thể giữ một ACID transaction xuyên nhiều service, nhưng failure giữa các bước vẫn cần được xử lý nhất quán ở mức business.

**Ví dụ thực tế:**
```text
Orchestration:
Order Saga
  -> ReserveInventory
  -> AuthorizePayment
  -> CreateShipment
  -> nếu payment fail: ReleaseInventory

Choreography:
OrderPlaced
  -> InventoryReserved
  -> PaymentAuthorized
  -> ShipmentRequested
```

**Trade-off:**
Orchestration làm flow, timeout và compensation dễ quan sát hơn nhưng coordinator có thể trở thành nơi tập trung logic quá mức. Choreography giảm central coupling nhưng event chain dài dễ khó trace, khó hiểu ownership và tạo cyclic dependency ngầm.

**Middle → Senior insight:**
Middle developer cần hiểu eventual consistency và viết handler idempotent. Senior / Technical developer phải chọn orchestration hay choreography dựa trên workflow complexity, ownership, observability, compensation semantics và khả năng vận hành khi một bước stuck giữa chừng.

### Design 2 — Hexagonal Architecture chỉ hữu ích khi boundary thực sự bảo vệ domain khỏi external detail

**Khái niệm:**
Hexagonal Architecture tách application/domain khỏi adapter bên ngoài bằng ports. Giá trị chính không nằm ở số project/folder mà ở việc business logic không phụ thuộc trực tiếp vào database SDK, HTTP vendor model hoặc framework-specific detail.

**Vấn đề nó giải quyết:**
Nếu core checkout logic nhận trực tiếp `StripeCharge`, `SqlConnection` hoặc Optimizely object ở mọi layer, thay integration hoặc test business rule sẽ kéo theo dependency ngoài ở khắp codebase.

**Ví dụ thực tế:**
```text
CheckoutApplication
  -> IPaymentGateway port
  -> IInventoryRepository port

Adapters:
  StripePaymentGateway
  EfInventoryRepository
```

Core quyết định `AuthorizePayment`, còn adapter chịu trách nhiệm translate vendor/API semantics.

**Trade-off:**
Ports/adapters giảm coupling và tăng testability tại integration boundary, nhưng nếu áp cho CRUD đơn giản sẽ tạo interface/mapping boilerplate vô ích. Một abstraction chỉ đáng tồn tại khi nó bảo vệ một boundary có khả năng thay đổi hoặc có semantics riêng.

**Middle → Senior insight:**
Middle developer cần phân biệt domain contract với infrastructure DTO. Senior / Technical developer phải nhận ra boundary nào đủ quan trọng để abstract, boundary nào nên dùng framework trực tiếp và khi nào “Clean/Hexagonal” đang biến thành accidental complexity.

### Design 3 — SLO và Error Budget như input cho quyết định reliability, không chỉ là dashboard metric

**Khái niệm:**
Service Level Objective xác định mức reliability mục tiêu theo signal như availability hoặc latency. Error Budget là phần failure được phép trong khoảng đo và có thể dùng để điều chỉnh tốc độ release, thử nghiệm và đầu tư reliability.

**Vấn đề nó giải quyết:**
Nếu team chỉ nói “API phải luôn nhanh và không được lỗi”, mọi incident đều thành emergency và mọi optimization đều có vẻ quan trọng. SLO biến yêu cầu mơ hồ thành constraint đo được để ưu tiên engineering work.

**Ví dụ thực tế:**
```text
Checkout API SLO:
99.9% request thành công trong 30 ngày
p95 latency < 500 ms

Nếu error budget burn quá nhanh:
- dừng risky rollout
- ưu tiên fix dependency timeout
- tăng observability/capacity

Nếu budget còn dư lớn:
- có thể chấp nhận controlled experiment hoặc migration nhanh hơn
```

**Trade-off:**
SLO giúp trade-off rõ ràng nhưng metric sai hoặc target quá cao sẽ dẫn tới engineering cost không cần thiết. SLO cũng không thay thế business impact analysis; một endpoint ít quan trọng không nên có reliability target giống payment path chỉ vì dễ đo.

**Middle → Senior insight:**
Middle developer cần hiểu code change ảnh hưởng SLI nào và đọc telemetry đúng. Senior / Solution-level developer phải thiết kế SLO theo user journey, xác định dependency budget, burn-rate alert và dùng error budget trong release/reliability decision thay vì chỉ báo cáo con số đẹp.
