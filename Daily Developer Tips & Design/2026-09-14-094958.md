# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng tin `X-Forwarded-For` nếu ASP.NET Core chưa cấu hình trusted proxy

**Mẹo:**
Khi application chạy sau reverse proxy, ingress hoặc load balancer, chỉ đọc `X-Forwarded-For` / `X-Forwarded-Proto` thông qua `ForwardedHeadersMiddleware` đã cấu hình `KnownProxies` hoặc `KnownNetworks`. Đừng lấy header trực tiếp từ request rồi dùng nó cho authorization, rate limiting hoặc audit.

**Tại sao hữu ích:**
Forwarded headers do client gửi hoàn toàn có thể bị giả mạo nếu proxy phía trước không strip/rewrite và application không xác định rõ proxy nào được tin cậy. Điều này có thể làm sai client IP, scheme, redirect URL hoặc policy dựa trên network origin.

**Ví dụ:**
```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.0.10"));
});

app.UseForwardedHeaders();
```

Sau middleware, `HttpContext.Connection.RemoteIpAddress` và `Request.Scheme` mới phản ánh chain proxy theo policy đã cấu hình.

**Lưu ý:**
Không thêm mọi network vào trusted list chỉ để “cho chạy được”. Nếu có nhiều proxy hop, cần hiểu thứ tự header và `ForwardLimit`. Sai cấu hình có thể tạo open redirect, log sai IP hoặc phá HTTPS redirect/auth callback.

### Tip 2 — PostgreSQL query chậm dần dù index vẫn tồn tại: kiểm tra dead tuples và autovacuum

**Mẹo:**
Với PostgreSQL workload có nhiều `UPDATE` / `DELETE`, nếu latency tăng dần dù execution plan không thay đổi đáng kể, kiểm tra dead tuples, table/index bloat và trạng thái autovacuum thay vì chỉ thêm index mới.

**Tại sao hữu ích:**
Do MVCC, `UPDATE` thường tạo row version mới thay vì ghi đè tại chỗ. Version cũ trở thành dead tuple và chỉ được reclaim khi vacuum xử lý. Nếu autovacuum không theo kịp workload, table/index phình to, cache efficiency giảm và query phải đọc nhiều page hơn.

**Ví dụ:**
```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Nếu một bảng update-heavy có `n_dead_tup` tăng liên tục, tiếp tục kiểm tra autovacuum threshold, transaction chạy quá lâu và index bloat trước khi quyết định tuning.

**Lưu ý:**
Không chạy `VACUUM FULL` trong production như phản xạ mặc định: nó cần lock mạnh và rewrite table. Long-running transaction còn có thể giữ old tuple không được reclaim dù autovacuum chạy bình thường.

### Tip 3 — Hủy request frontend cũ bằng `AbortController` để tránh response đến sai thứ tự

**Mẹo:**
Khi UI gửi request mới mỗi lần user thay filter/search, hủy request trước đó bằng `AbortController` hoặc dùng cơ chế cancellation tương đương của framework/query library.

**Tại sao hữu ích:**
Nếu user gõ `lap` rồi nhanh chóng gõ `laptop`, request `lap` có thể chậm hơn và trả về sau request `laptop`. Nếu code chỉ gán response cuối cùng nhận được vào state, UI sẽ hiển thị kết quả cũ dù request mới đã hoàn tất trước đó.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(term: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  });

  return response.json();
}
```

Trong Vue/React, cleanup cancellation khi component unmount hoặc dependency thay đổi.

**Lưu ý:**
Abort ở browser không đảm bảo server đã dừng toàn bộ work; backend cũng cần propagate cancellation xuống EF Core, HTTP dependency hoặc long-running operation khi có thể. Đồng thời phân biệt abort chủ động với network error để không hiển thị thông báo lỗi sai cho user.

### Tip 4 — Với Optimizely CMS, cache invalidation phải bám theo content dependency chứ không chỉ TTL

**Mẹo:**
Khi render page/block từ nhiều content item trong Optimizely CMS, cache output hoặc dữ liệu tổng hợp nên có dependency rõ với content được dùng để xây response. Chỉ đặt TTL dài mà không có invalidation theo publish event dễ tạo stale content sau khi editor cập nhật.

**Tại sao hữu ích:**
CMS workload thường read-heavy nên cache rất có giá trị, nhưng freshness là một phần của editorial contract. Một component homepage có thể phụ thuộc page hiện tại, referenced block và settings content; nếu chỉ invalidate page chính, block mới publish vẫn không xuất hiện cho tới khi TTL hết.

**Ví dụ:**
```text
Homepage cache key:
home:v3:en

Dependencies:
- HomePage ContentReference
- HeroBlock ContentReference
- SiteSettings ContentReference

Publish HeroBlock
-> invalidation signal
-> remove/rebuild homepage cache
```

Thiết kế cache dependency theo graph content thực tế thay vì chỉ theo route URL.

**Lưu ý:**
Invalidating quá rộng sẽ làm cache churn và tạo spike về database/CMS API. Nếu chạy nhiều instance, local memory cache cần cơ chế invalidation phân tán hoặc dùng distributed cache phù hợp; đừng giả định publish event trên một node tự động làm sạch cache của node khác.

### Tip 5 — Khi log production, giữ label/cardinality thấp cho metric và đưa chi tiết vào log/trace

**Mẹo:**
Không gắn các giá trị gần như unique như `userId`, `orderId`, full URL hoặc exception message vào metric label/tag. Metric nên dùng dimension có tập giá trị hữu hạn như endpoint template, status class, dependency name; chi tiết request cụ thể để trong structured log hoặc trace.

**Tại sao hữu ích:**
Mỗi combination của metric labels tạo một time series riêng. Cardinality tăng không kiểm soát có thể làm backend observability tốn memory/storage, query dashboard chậm và tăng chi phí telemetry đáng kể.

**Ví dụ:**
```text
Tốt:
http_server_duration{route="/orders/{id}",status="200"}

Rủi ro cao:
http_server_duration{url="/orders/9834721",userId="u-918273"}
```

Khi cần điều tra order cụ thể, dùng trace/span hoặc structured log với correlation ID.

**Lưu ý:**
Đừng loại bỏ mọi dimension vì sợ cardinality; metric quá ít chiều cũng không chẩn đoán được. Hãy chọn tag theo câu hỏi vận hành cần trả lời và đặt guardrail cho cardinality trước khi production traffic tăng.

## 🧠 Software Design

### Design 1 — Backward-compatible API evolution ưu tiên additive change trước breaking change

**Khái niệm:**
API evolution an toàn thường bắt đầu bằng thay đổi additive: thêm field optional, endpoint mới hoặc enum handling có fallback, trong khi contract cũ vẫn hoạt động. Breaking change chỉ nên xuất hiện khi có migration plan và version boundary rõ.

**Vấn đề nó giải quyết:**
Mobile app, third-party integration hoặc frontend CDN-cached bundle không phải lúc nào deploy cùng backend. Nếu backend rename field hoặc đổi semantics ngay lập tức, client cũ có thể fail dù deployment server hoàn toàn thành công.

**Ví dụ thực tế:**
```text
Hiện tại:
GET /api/orders/{id}
{ "status": "Pending" }

Cần thêm payment state:
{ "status": "Pending", "paymentStatus": "Authorized" }
```

Client cũ bỏ qua field mới; client mới bắt đầu sử dụng nó. Chỉ sau khi telemetry chứng minh client cũ đã biến mất mới cân nhắc loại contract cũ.

**Trade-off:**
Additive evolution giảm coordination cost nhưng giữ compatibility code lâu hơn và có thể làm contract phình to. API versioning cho phép thay đổi mạnh hơn nhưng tăng số version phải test/support. Không phải mọi thay đổi đều cần `/v2`; đôi khi migration additive đơn giản hơn nhiều.

**Middle → Senior insight:**
Middle developer cần tránh đổi contract public tùy tiện và viết test compatibility. Senior / Technical developer phải xác định consumer lifecycle, deprecation window, telemetry, schema evolution và chi phí vận hành nhiều version trước khi chọn versioning strategy.

### Design 2 — Leader Election cho scheduled job khi application chạy nhiều instance

**Khái niệm:**
Leader Election đảm bảo tại một thời điểm chỉ một instance chịu trách nhiệm cho một loại coordination work như scheduler, cleanup hoặc batch dispatch. Các instance khác vẫn phục vụ request nhưng không cùng chạy job độc quyền đó.

**Vấn đề nó giải quyết:**
Một `BackgroundService` chạy mỗi 5 phút hoạt động đúng trên laptop một instance, nhưng khi scale App Service/Kubernetes lên 6 replicas thì cùng một job có thể chạy 6 lần. Nếu job gửi invoice hoặc close accounting period, duplicate execution có thể gây side effect nghiêm trọng.

**Ví dụ thực tế:**
```text
6 replicas
-> tất cả cố acquire lease "daily-invoice-dispatch"
-> instance B giữ lease 60s và renew định kỳ
-> chỉ B dispatch batch
-> B crash
-> lease hết hạn
-> instance D acquire và tiếp tục
```

Lease có thể dựa trên database advisory lock, Blob lease, distributed lock service hoặc scheduler có persistence tùy hạ tầng.

**Trade-off:**
Leader election giảm duplicate coordinator nhưng thêm lease lifecycle, clock/failure assumptions và failover delay. Nó cũng không loại bỏ nhu cầu idempotency: process có thể crash sau side effect nhưng trước khi checkpoint được ghi.

**Middle → Senior insight:**
Middle developer cần nhận ra “timer chạy một lần” chỉ đúng trong phạm vi process. Senior / Technical developer phải chọn giữa leader election, external scheduler, partitioned workers và idempotent competing consumers dựa trên semantics của job, HA requirement và operational complexity.

### Design 3 — Consumer-Driven Contract Test giúp phát hiện integration break trước khi deploy

**Khái niệm:**
Consumer-Driven Contract Testing ghi lại những interaction mà consumer thực sự phụ thuộc từ provider và verify provider vẫn đáp ứng chúng. Nó nằm giữa unit test và end-to-end test: không cần chạy toàn hệ thống nhưng vẫn kiểm tra compatibility giữa service boundaries.

**Vấn đề nó giải quyết:**
Provider có thể đổi JSON field, nullability hoặc status code mà unit test của chính provider vẫn xanh. Full E2E có thể phát hiện nhưng thường chậm, khó cô lập và không chạy đủ mọi consumer combination.

**Ví dụ thực tế:**
```text
Checkout consumer expects:
GET /inventory/SKU-42
200
{
  "sku": "SKU-42",
  "available": true
}

Provider pipeline verify:
- route còn tồn tại
- field `available` vẫn có semantics tương thích
- response example/schema thỏa contract
```

Contract được version cùng consumer và provider verify trong CI trước release.

**Trade-off:**
Contract test phát hiện compatibility tốt nhưng không chứng minh network, authentication, routing hoặc production configuration thực sự hoạt động; integration/E2E test vẫn cần ở mức phù hợp. Nếu contract mô tả quá nhiều implementation detail, nó sẽ khóa provider và làm thay đổi nhỏ cũng gây churn.

**Middle → Senior insight:**
Middle developer cần viết contract theo behavior consumer cần, không snapshot toàn response. Senior / Technical developer phải xác định ownership contract, versioning, breaking-change workflow và phạm vi test sao cho tăng confidence mà không biến CI thành coupling giữa mọi service.
