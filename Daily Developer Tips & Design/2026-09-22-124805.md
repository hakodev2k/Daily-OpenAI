# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — `ConfigureAwait(false)` không phải tối ưu mặc định cho ASP.NET Core

**Mẹo:**
Trong ASP.NET Core hiện đại, đừng thêm `ConfigureAwait(false)` khắp application code chỉ vì quy tắc từ .NET Framework cũ. Hãy hiểu execution context thực tế trước khi áp dụng.

**Tại sao hữu ích:**
ASP.NET Core không cài request `SynchronizationContext` kiểu ASP.NET cổ điển, nên continuation sau `await` thường không cần quay lại một request thread đặc biệt. Việc rải `ConfigureAwait(false)` vì thói quen làm code nhiễu mà hiếm khi mang lại lợi ích đáng kể ở application layer.

**Ví dụ:**
Một controller gọi `await service.GetOrderAsync(id)` không cần đổi thành `await service.GetOrderAsync(id).ConfigureAwait(false)` chỉ để tránh deadlock. Deadlock kiểu `.Result` + captured UI/ASP.NET context không có cùng cơ chế trong ASP.NET Core.

**Lưu ý:**
Library code dùng được trong nhiều host vẫn có thể chủ động dùng `ConfigureAwait(false)`. Quan trọng hơn là tránh sync-over-async như `.Result`/`.Wait()` và đo performance thay vì áp dụng micro-optimization theo cargo cult.

### Tip 2 — EF Core `AsNoTrackingWithIdentityResolution` hữu ích khi projection chưa phù hợp

**Mẹo:**
Với read-only query cần materialize entity graph nhưng không cần update, cân nhắc `AsNoTrackingWithIdentityResolution()` khi cùng entity có thể xuất hiện nhiều lần trong result.

**Tại sao hữu ích:**
`AsNoTracking()` giảm change-tracking overhead nhưng có thể tạo nhiều object instances cho cùng database row trong một graph. Identity resolution dùng tracker tạm thời chỉ trong quá trình materialization để tái sử dụng instance mà không đưa entities vào `DbContext` tracking lâu dài.

**Ví dụ:**
Một read model tạm thời load orders cùng shared product references để chạy business-formatting code hiện có. Nếu chưa thể chuyển sang DTO projection, identity resolution có thể giảm duplicate object instances so với pure no-tracking query.

**Lưu ý:**
Nó vẫn có overhead và không phải lựa chọn nhanh nhất mặc định. Nếu endpoint chỉ cần response shape cụ thể, `Select` projection thường rõ và tiết kiệm hơn; hãy benchmark query thực tế.

### Tip 3 — Redis eviction là capacity signal, không chỉ là cache miss

**Mẹo:**
Theo dõi eviction rate cùng memory usage, hit ratio và configured eviction policy. Khi evictions tăng, đừng chỉ tăng TTL hoặc retry cache reads.

**Tại sao hữu ích:**
Eviction nghĩa là Redis phải loại keys để tuân theo memory policy. Nếu working set lớn hơn capacity, hot data có thể bị đẩy ra liên tục, hit ratio giảm và traffic dồn ngược về database, tạo cascading load đúng lúc cache đang chịu áp lực.

**Ví dụ:**
Sau chiến dịch marketing, API latency tăng và SQL CPU tăng. Redis vẫn “up”, nhưng `evicted_keys` tăng nhanh và hit ratio giảm. Root cause là cache working set vượt memory budget; điều tra cần xem key sizes, TTL distribution, policy và workload trước khi scale database.

**Lưu ý:**
Không phải mọi eviction đều là incident; với cache thuần túy, eviction là hành vi hợp lệ. Vấn đề là khi eviction pattern phá latency/capacity assumptions hoặc policy như `allkeys-lru` không phù hợp dữ liệu đang lưu.

### Tip 4 — CI artifact phải bất biến giữa build và deploy

**Mẹo:**
Build application một lần, version artifact rõ ràng và promote chính artifact đó qua các environment thay vì rebuild source riêng cho staging và production.

**Tại sao hữu ích:**
Rebuild có thể kéo dependency khác, toolchain khác hoặc generated output khác dù Git commit giống nhau. Artifact bất biến làm rollback, audit và diagnosis chính xác hơn vì binary/container đã test chính là thứ được deploy.

**Ví dụ:**
Pipeline tạo container image `app:<commit-sha>`, chạy tests/scans trên image đó rồi promote cùng digest từ staging sang production. Environment-specific values đi qua configuration/secrets, không được bake bằng một lần build mới.

**Lưu ý:**
“Build once” không có nghĩa mọi configuration phải giống nhau. Tách artifact khỏi runtime configuration; đồng thời pin toolchain/dependencies để build vẫn reproducible khi cần điều tra.

### Tip 5 — AI-generated migration phải được kiểm tra trên schema thật

**Mẹo:**
Khi dùng AI coding agent để tạo EF Core migration hoặc SQL migration, luôn đối chiếu model snapshot/schema hiện tại, generated SQL và upgrade path từ production version gần nhất.

**Tại sao hữu ích:**
AI có thể viết migration hợp cú pháp nhưng giả định sai constraint, nullability, data volume hoặc database engine. Một `ALTER COLUMN` tưởng đơn giản có thể lock bảng lớn; rename sai có thể bị sinh thành drop/create và gây mất dữ liệu.

**Ví dụ:**
Agent đề xuất đổi `CustomerName` thành non-null bằng một migration duy nhất. Review schema thật phát hiện hàng triệu rows có `NULL`; rollout đúng cần backfill theo batch, kiểm chứng dữ liệu rồi mới thêm constraint.

**Lưu ý:**
Test migration trên database rỗng là chưa đủ. Cần kiểm tra upgrade từ schema/data đại diện production, rollback/forward-fix strategy và thời gian lock đối với thay đổi lớn.

## 🧠 Software Design

### Design 1 — Lease thay cho “boolean lock” trong distributed job ownership

**Khái niệm:**
Lease cấp quyền sở hữu một resource trong thời gian hữu hạn và yêu cầu holder gia hạn. Nếu process chết, lease hết hạn để instance khác tiếp quản, thay vì để một cờ `IsRunning=true` tồn tại vô thời hạn.

**Vấn đề nó giải quyết:**
Scheduled job chạy trên nhiều instances cần tránh xử lý đồng thời, nhưng distributed lock không có expiry/recovery semantics dễ tạo stuck ownership sau crash hoặc network partition.

**Ví dụ thực tế:**
Một reconciliation job lấy lease 60 giây, gia hạn khi còn chạy và ghi owner/version. Nếu pod chết, instance khác chỉ takeover sau expiry. Side effects vẫn được thiết kế idempotent vì lease không thể biến distributed execution thành exactly-once tuyệt đối.

**Trade-off:**
Lease cải thiện recovery nhưng thêm clock/expiry, renewal, fencing và split-brain considerations. TTL quá ngắn gây false takeover; quá dài làm failover chậm.

**Middle → Senior insight:**
Middle developer cần implement acquire/renew/release và idempotency đúng. Senior / Technical developer phải reasoning về partition, stale owner, fencing token, job duration và quyết định khi queue-based competing consumers phù hợp hơn distributed lease.

### Design 2 — Schema ownership quan trọng hơn việc “service nào gọi database nào”

**Khái niệm:**
Data ownership xác định component nào chịu trách nhiệm thay đổi schema, enforce invariants và cung cấp contract truy cập dữ liệu. Tách services nhưng cho nhiều services ghi trực tiếp cùng tables vẫn tạo coupling mạnh.

**Vấn đề nó giải quyết:**
Shared writes khiến deployment độc lập trở nên giả tạo: một migration hoặc invariant change của service A có thể phá service B mà không đi qua API/event contract.

**Ví dụ thực tế:**
Ordering và Billing chạy thành hai services nhưng đều update bảng `Orders`. Thay vì coi đó là microservices độc lập, architecture cần xác định owner của order state và để service khác tương tác qua contract phù hợp hoặc projection riêng.

**Trade-off:**
Ownership rõ tăng autonomy và evolvability nhưng có thể tạo duplicated read data, messaging và eventual consistency. Shared schema đơn giản hơn cho hệ thống nhỏ, nhưng coordination cost tăng nhanh khi team/service boundaries phát triển.

**Middle → Senior insight:**
Middle developer cần tránh bypass owner chỉ vì direct SQL nhanh hơn. Senior / Technical developer phải chọn ownership boundary dựa trên invariants, change cadence và team responsibility, không dựa đơn thuần vào số lượng deployables.

### Design 3 — Graceful degradation thay vì biến mọi dependency thành hard dependency

**Khái niệm:**
Graceful degradation xác định chức năng nào có thể giảm chất lượng hoặc tạm bỏ khi dependency lỗi, thay vì để toàn request/system thất bại chỉ vì một capability phụ không khả dụng.

**Vấn đề nó giải quyết:**
Distributed systems có partial failure. Nếu Product Details bắt buộc Recommendations, Reviews và Personalization đều thành công, availability của trang bị nhân theo availability của nhiều dependencies không cùng mức business criticality.

**Ví dụ thực tế:**
E-commerce product page vẫn trả product/price khi recommendation service timeout, nhưng bỏ recommendation block và ghi telemetry. Payment dependency thì vẫn là hard dependency của checkout vì bỏ qua nó sẽ vi phạm business correctness.

**Trade-off:**
Degradation tăng availability nhưng làm response semantics và UI states phức tạp hơn; fallback stale hoặc thiếu dữ liệu cũng có thể gây quyết định sai nếu áp dụng vào critical domain.

**Middle → Senior insight:**
Middle developer cần implement timeout, fallback và observable partial state rõ ràng. Senior / Technical developer phải phân loại dependency theo business criticality, xác định acceptable stale/missing behavior và tránh dùng fallback để che lỗi correctness nghiêm trọng.
