# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng optimistic concurrency để ngăn “last write wins” âm thầm trong EF Core

**Mẹo:**
Với entity có khả năng bị nhiều user hoặc process cập nhật đồng thời, dùng concurrency token như `rowversion` thay vì để update sau cùng ghi đè thay đổi trước mà không phát hiện conflict.

**Tại sao hữu ích:**
Mặc định, hai request có thể cùng đọc một version của record rồi lần lượt update. Request thứ hai có thể ghi đè thay đổi của request thứ nhất dù cả hai đều “thành công” về mặt HTTP/SQL. Concurrency token khiến `UPDATE` chỉ thành công nếu version vẫn còn đúng, biến lost update thành conflict có thể xử lý rõ ràng.

**Ví dụ:**
```csharp
public class Product
{
    public Guid Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
```

Khi version không còn khớp, EF Core có thể ném:
```text
DbUpdateConcurrencyException
```

Ứng dụng sau đó có thể reload dữ liệu mới nhất, merge hoặc trả `409 Conflict` tùy business semantics.

**Lưu ý:**
Không retry mù mọi concurrency conflict. Nếu hai người sửa cùng một giá trị business quan trọng, retry tự động có thể vẫn ghi đè dữ liệu mới. Cần phân biệt conflict có thể retry với conflict cần user/business decision.

### Tip 2 — Với Cosmos DB, partition key sai có thể tạo hot partition dù tổng RU còn dư

**Mẹo:**
Khi thiết kế container Cosmos DB, chọn partition key theo access pattern và phân bố traffic, không chỉ theo thuộc tính “có vẻ unique”.

**Tại sao hữu ích:**
Cosmos DB phân phối storage và throughput theo logical/physical partitions. Nếu một partition key nhận phần lớn request, workload có thể bị throttling tại partition đó dù tổng throughput provisioned của container chưa dùng hết.

**Ví dụ:**
Giả sử event system dùng:
```text
partition key = /tenantId
```

Nếu một enterprise tenant phát sinh 70% traffic, tenant đó có thể trở thành hot partition.

Một strategy khác có thể là:
```text
/tenantId + bucket
```

hoặc chọn key theo entity/access pattern nếu query semantics cho phép.

**Lưu ý:**
Partition key ảnh hưởng cả query cost, transaction scope và khả năng scale. Đừng đổi sang random GUID chỉ để phân bố đều nếu mọi query sau đó phải fan-out toàn container. Thiết kế phải cân bằng locality với distribution.

### Tip 3 — Azure Functions retry phải đi cùng idempotency và poison-message strategy

**Mẹo:**
Khi Azure Function xử lý queue/message trigger, luôn giả định cùng một message có thể được xử lý nhiều lần và thiết kế handler idempotent ngay từ đầu.

**Tại sao hữu ích:**
Function có thể fail sau khi side effect đã xảy ra nhưng trước khi runtime xác nhận message thành công. Retry sau đó có thể tạo duplicate order, email hoặc external API call. Retry tăng reliability của delivery nhưng không đảm bảo exactly-once processing.

**Ví dụ:**
Một Function xử lý `PaymentCaptured` có thể ghi `EventId` vào table deduplication cùng transaction với business update:
```text
if EventId already processed:
    return

apply update
store EventId
commit
```

Nếu message vượt retry threshold, chuyển sang poison/dead-letter path để operator điều tra thay vì retry vô hạn.

**Lưu ý:**
Đừng coi poison queue chỉ là “nơi chứa message lỗi”. Cần alerting, dashboard, replay process và retention rõ ràng. Nếu replay không idempotent, poison handling có thể gây sự cố lần hai.

### Tip 4 — Kubernetes readiness probe không nên kiểm tra mọi dependency theo cách làm pod tự loại mình hàng loạt

**Mẹo:**
Dùng readiness probe để trả lời câu hỏi “pod này có nhận traffic được không?”, nhưng tránh biến probe thành chuỗi health check sâu tới mọi external dependency.

**Tại sao hữu ích:**
Nếu Redis hoặc một API downstream chập chờn và mọi pod cùng đánh readiness fail, Kubernetes có thể rút toàn bộ pod khỏi Service dù application vẫn có degraded mode hoặc endpoint khác vẫn hoạt động. Điều này biến dependency incident thành full outage.

**Ví dụ:**
Readiness có thể kiểm tra:
```text
- app initialized
- required local configuration loaded
- database connection khả dụng nếu DB là bắt buộc cho mọi request
```

Không nhất thiết phải fail readiness chỉ vì:
```text
recommendation API unavailable
```

nếu application có fallback hợp lệ.

**Lưu ý:**
Liveness và readiness có mục đích khác nhau. Liveness sai có thể tạo restart loop; readiness sai có thể rút pod khỏi traffic. Health check phải phản ánh failure model thực tế, không chỉ “ping tất cả dependency”.

### Tip 5 — Dùng AI coding agent để review hypothesis, không giao luôn quyền quyết định root cause

**Mẹo:**
Khi dùng AI-assisted debugging hoặc code review, yêu cầu agent chỉ ra bằng chứng từ source, log, test hoặc execution path cho mỗi kết luận thay vì chấp nhận một fix nghe hợp lý.

**Tại sao hữu ích:**
AI có thể tạo explanation rất thuyết phục nhưng dựa trên API không tồn tại, version library khác hoặc assumption sai về repository. Buộc agent grounding vào source giúp biến AI thành công cụ tăng tốc phân tích thay vì nguồn “phỏng đoán có vẻ kỹ thuật”.

**Ví dụ:**
Thay vì hỏi:
```text
Why is checkout slow? Fix it.
```

hãy yêu cầu:
```text
Trace the checkout call path from controller to database/external APIs.
For each suspected bottleneck, cite the exact file/method and evidence.
Do not propose code changes until the hypothesis is supported.
```

Sau đó verify bằng profiler, telemetry hoặc test trước khi merge.

**Lưu ý:**
Không để generated tests chỉ assert implementation detail mà agent vừa tạo. Test phải bảo vệ behavior và edge cases độc lập với implementation cụ thể.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read/write model thực sự chịu áp lực khác nhau

**Khái niệm:**
CQRS tách command model và query model khi hai phía có lifecycle, performance requirement hoặc domain complexity khác nhau. Nó không đơn giản là đổi tên service thành `CommandHandler` và `QueryHandler`.

**Vấn đề nó giải quyết:**
Một hệ thống có write side giàu invariant nhưng read side cần projection lớn, denormalized view hoặc search-oriented model có thể bị ép vào cùng một entity model khó tối ưu cho cả hai.

**Ví dụ thực tế:**
Order write side:
```text
CreateOrder
CancelOrder
ReserveInventory
```

cần validate invariant và transaction chặt.

Dashboard read side lại cần:
```text
customer + order summary + payment status + shipment status
```

và có thể dùng projection riêng hoặc read database tối ưu cho truy vấn.

**Trade-off:**
CQRS tăng flexibility và scale độc lập nhưng thêm model duplication, synchronization, eventual consistency và observability complexity. Với CRUD application nhỏ, cùng một EF Core model thường đơn giản và tốt hơn.

**Middle → Senior insight:**
Middle developer cần phân biệt command/query semantics và tránh side effect trong query. Senior / Technical developer phải chứng minh áp lực thực tế đủ lớn để biện minh cho CQRS, xác định consistency tolerance, ownership của projection và migration path nếu read model thay đổi.

### Design 2 — Idempotent webhook consumer là boundary design, không chỉ là thêm unique index

**Khái niệm:**
Webhook consumer idempotent phải đảm bảo cùng một event được gửi lại nhiều lần nhưng business outcome chỉ xảy ra một lần theo semantics mong muốn.

**Vấn đề nó giải quyết:**
Provider có thể retry khi timeout, network failure hoặc nhận response không rõ ràng. Nếu endpoint xử lý trực tiếp mà không có deduplication và transaction boundary hợp lý, cùng payment event có thể tạo nhiều invoice hoặc nhiều notification.

**Ví dụ thực tế:**
Flow an toàn hơn:
```text
receive webhook
-> validate signature
-> persist event with provider EventId (unique)
-> acknowledge quickly
-> process asynchronously
-> mark processed
```

Nếu cùng `EventId` tới lại, application nhận biết duplicate và không lặp side effect.

**Trade-off:**
Deduplication tăng reliability nhưng cần retention policy, replay handling và semantics rõ cho trường hợp provider gửi event mới với cùng business entity nhưng EventId khác. Acknowledge sớm cũng chuyển failure recovery sang background processing.

**Middle → Senior insight:**
Middle developer cần xử lý signature, unique event ID và retry-safe handler. Senior / Technical developer phải thiết kế delivery contract, dedup window, ordering, replay tooling, auditability và quyết định khi nào response phải chờ business processing hoàn tất hay chỉ cần durable acceptance.

### Design 3 — Schema evolution cho event phải được coi là compatibility contract dài hạn

**Khái niệm:**
Event-driven system cần coi schema của event là public contract giữa producer và consumer. Producer có thể deploy độc lập với consumer, vì vậy thay đổi schema phải được thiết kế cho mixed-version operation.

**Vấn đề nó giải quyết:**
Nếu producer rename field, đổi enum semantics hoặc xóa property mà consumer cũ vẫn đang chạy, message mới có thể làm consumer fail hàng loạt hoặc silently interpret sai dữ liệu.

**Ví dụ thực tế:**
Thay vì đổi trực tiếp:
```json
{
  "customerName": "Alice"
}
```

sang:
```json
{
  "displayName": "Alice"
}
```

có thể thêm field mới trong phase chuyển tiếp:
```json
{
  "customerName": "Alice",
  "displayName": "Alice"
}
```

sau đó migrate consumer, đo usage và chỉ remove field cũ khi contract lifecycle cho phép.

**Trade-off:**
Backward-compatible evolution làm event payload và producer code phức tạp hơn trong thời gian chuyển đổi. Versioned event type rõ ràng hơn cho breaking change nhưng tăng số schema/consumer path cần support.

**Middle → Senior insight:**
Middle developer cần nhận diện additive vs breaking change và viết consumer tolerant với field mới khi phù hợp. Senior / Technical developer phải thiết kế versioning policy, deprecation window, contract test, ownership và rollout sequence giữa nhiều team/service.
