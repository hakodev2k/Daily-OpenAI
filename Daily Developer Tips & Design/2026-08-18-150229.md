# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ValueTask` chỉ khi thật sự có lợi

**Mẹo:**
Ưu tiên `Task` mặc định. Chỉ cân nhắc `ValueTask` khi method được gọi rất thường xuyên và có tỷ lệ hoàn thành đồng bộ cao, ví dụ cache hit.

**Tại sao hữu ích:**
`ValueTask` có thể giảm allocation trong hot path, nhưng đổi lại API phức tạp hơn và dễ dùng sai.

**Ví dụ:**
```csharp
public ValueTask<User?> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

**Lưu ý:**
Không dùng `ValueTask` chỉ vì nghĩ nó “nhanh hơn”. Một `ValueTask` không nên được `await` nhiều lần hoặc lưu trữ tùy tiện như `Task`.

### Tip 2 — Dùng projection trong EF Core để tránh load thừa dữ liệu

**Mẹo:**
Khi API chỉ cần vài field, dùng `Select(...)` để project trực tiếp sang DTO thay vì load toàn bộ entity rồi mới map.

**Tại sao hữu ích:**
Giảm lượng dữ liệu đọc từ database, network payload giữa DB và application, memory allocation và tracking overhead.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.Status == OrderStatus.Pending)
    .Select(x => new OrderSummaryDto
    {
        Id = x.Id,
        CustomerName = x.Customer.Name,
        Total = x.Total
    })
    .ToListAsync();
```

**Lưu ý:**
Đừng projection quá sớm nếu sau đó cần domain behavior hoặc nhiều field phát sinh; nếu không, query có thể trở nên khó đọc và khó reuse.

### Tip 3 — Dùng `git bisect` để tìm commit gây regression

**Mẹo:**
Khi biết một phiên bản cũ còn tốt và phiên bản hiện tại đã lỗi, dùng `git bisect` thay vì kiểm tra từng commit thủ công.

**Tại sao hữu ích:**
Git thực hiện binary search qua lịch sử commit, giúp thu hẹp regression rất nhanh trên branch có nhiều thay đổi.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0

# test commit hiện tại rồi đánh dấu
git bisect good
# hoặc
git bisect bad

# kết thúc
git bisect reset
```

**Lưu ý:**
Kết quả chỉ đáng tin khi có cách xác định rõ commit nào “good” và “bad”. Nếu test flaky, `bisect` có thể dẫn tới kết luận sai.

### Tip 4 — Đọc query bằng `EXPLAIN ANALYZE` thay vì chỉ nhìn thời gian tổng

**Mẹo:**
Với PostgreSQL, dùng `EXPLAIN ANALYZE` để xem actual execution time, row count và plan node thực tế của query chậm.

**Tại sao hữu ích:**
Bạn có thể phát hiện sai lệch cardinality estimate, nested loop quá lớn, sequential scan không mong muốn hoặc sort tràn chi phí.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, customer_id, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;
```

**Lưu ý:**
`EXPLAIN ANALYZE` thực sự chạy query. Không dùng thiếu kiểm soát với `UPDATE`, `DELETE` hoặc query production có side effect.

### Tip 5 — Dùng `Retry-After` thay vì retry với delay cố định

**Mẹo:**
Khi gọi external API trả `429 Too Many Requests` hoặc `503 Service Unavailable`, kiểm tra `Retry-After` trước khi tự áp dụng delay.

**Tại sao hữu ích:**
Giảm nguy cơ retry storm và tuân theo thời điểm server cho phép client thử lại.

**Ví dụ:**
```csharp
if (response.StatusCode == HttpStatusCode.TooManyRequests &&
    response.Headers.RetryAfter?.Delta is TimeSpan delay)
{
    await Task.Delay(delay, cancellationToken);
}
```

**Lưu ý:**
`Retry-After` không thay thế retry policy đầy đủ. Production code vẫn cần giới hạn số lần retry, jitter, timeout và cancellation.

## 🧠 Software Design

### Design 1 — Cache-Aside và bài toán invalidation

**Khái niệm:**
Cache-Aside để application đọc cache trước; nếu miss thì đọc nguồn dữ liệu thật rồi ghi lại vào cache. Khi dữ liệu thay đổi, application chịu trách nhiệm invalidate hoặc cập nhật cache.

**Vấn đề nó giải quyết:**
Giảm latency và tải lên database cho dữ liệu đọc nhiều, nhưng không buộc database phải biết về caching layer.

**Ví dụ thực tế:**
API product catalog đọc `ProductDetail` từ Redis. Khi admin cập nhật giá, service commit database trước rồi xóa cache key để request tiếp theo load giá mới.

**Trade-off:**
Ưu điểm là đơn giản, linh hoạt và dễ áp dụng theo từng use case. Rủi ro lớn là stale data, cache stampede và race condition giữa database update với cache invalidation.

**Middle → Senior insight:**
Middle developer cần biết TTL và invalidate cache khi write. Senior developer phải xác định mức stale data business chấp nhận được, chiến lược chống stampede, key design, failure mode khi Redis down và thứ tự update DB/cache để giảm inconsistency.

### Design 2 — Optimistic Concurrency thay vì giữ lock dài

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request cùng đọc dữ liệu, nhưng khi update sẽ kiểm tra version để phát hiện dữ liệu đã bị request khác thay đổi.

**Vấn đề nó giải quyết:**
Tránh giữ database lock dài trong các workflow có user interaction hoặc request latency không đoán trước được.

**Ví dụ thực tế:**
Hai nhân viên cùng mở một Order. User A cập nhật trước làm `Version` thay đổi; khi User B save trên dữ liệu cũ, API trả conflict thay vì âm thầm overwrite thay đổi của A.

**Trade-off:**
Tăng concurrency và throughput, nhưng application phải có chiến lược xử lý conflict: reject, retry, merge hoặc yêu cầu user refresh dữ liệu.

**Middle → Senior insight:**
Middle developer cần hiểu lost update và cách dùng `rowversion`, ETag hoặc concurrency token. Senior developer cần chọn conflict policy dựa trên semantics của business thay vì retry mù quáng mọi concurrency exception.

### Design 3 — Outbox Pattern cho database + message broker

**Khái niệm:**
Outbox Pattern lưu business change và event cần publish trong cùng database transaction. Một publisher riêng sau đó đọc Outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Tránh dual-write failure khi application commit database thành công nhưng publish RabbitMQ/Kafka thất bại, hoặc ngược lại.

**Ví dụ thực tế:**
Khi tạo Order, transaction ghi cả `Orders` và `OutboxMessages`. Background worker publish `OrderCreated` lên broker rồi đánh dấu Outbox record đã xử lý.

**Trade-off:**
Tăng reliability nhưng thêm bảng Outbox, background publisher, cleanup, monitoring và khả năng message được gửi nhiều hơn một lần.

**Middle → Senior insight:**
Middle developer cần hiểu tại sao không thể coi database transaction và message publish là một atomic operation thông thường. Senior developer phải thiết kế consumer idempotency, retry/backoff, ordering, cleanup và observability để biến Outbox thành giải pháp production chứ không chỉ là thêm một bảng trung gian.
