# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng projection trong EF Core để giảm dữ liệu và tracking không cần thiết

**Mẹo:**
Khi endpoint chỉ cần một subset của entity, ưu tiên `Select` projection trực tiếp sang DTO thay vì `Include` nhiều navigation rồi materialize toàn bộ entity graph.

**Tại sao hữu ích:**
Projection giúp EF Core sinh SQL chỉ lấy các column cần thiết, giảm network payload, allocation và change-tracking overhead. Với read-heavy API, đây thường là tối ưu an toàn hơn so với tải entity đầy đủ rồi map trong memory.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.CreatedAt,
        x.Total,
        x.Customer.Name))
    .ToListAsync(cancellationToken);
```

Nếu response chỉ cần bốn field trên, không cần `Include(x => x.Customer)` rồi map sau.

**Lưu ý:**
Đừng projection quá sớm nếu business logic phía sau thực sự cần entity behavior hoặc tracked changes. Đồng thời kiểm tra SQL được generate; expression phức tạp có thể bị dịch thành query không tối ưu.

### Tip 2 — Với PostgreSQL job queue, `FOR UPDATE SKIP LOCKED` giúp nhiều worker tránh tranh cùng row

**Mẹo:**
Nếu một bảng PostgreSQL được dùng như lightweight job queue, nhiều worker có thể claim job bằng `FOR UPDATE SKIP LOCKED` để bỏ qua row đang bị worker khác giữ lock thay vì chờ blocking.

**Tại sao hữu ích:**
Nếu tất cả worker cùng `SELECT` job đầu tiên rồi chờ lock, throughput bị serialize. `SKIP LOCKED` cho phép mỗi worker lấy một tập row khác nhau, giảm contention trong workload cạnh tranh consumer.

**Ví dụ:**
```sql
BEGIN;

SELECT id
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;

-- update selected rows to processing
COMMIT;
```

Pattern này phù hợp khi job có thể được claim bằng transaction ngắn.

**Lưu ý:**
Một relational table không tự nhiên trở thành message broker đầy đủ. Nếu cần retry policy phức tạp, dead-lettering, partitioning, delivery semantics hoặc throughput rất lớn, broker chuyên dụng như Azure Service Bus có thể phù hợp hơn.

### Tip 3 — Tách liveness và readiness để deployment không gửi traffic quá sớm

**Mẹo:**
Trong container/Kubernetes hoặc platform có health probe, phân biệt liveness với readiness. Liveness trả lời “process còn sống không?”, readiness trả lời “instance đã sẵn sàng nhận traffic chưa?”.

**Tại sao hữu ích:**
Nếu cùng một probe kiểm tra mọi dependency và được dùng cho liveness, sự cố database ngắn có thể khiến orchestrator restart hàng loạt pod dù process hoàn toàn khỏe. Ngược lại, nếu readiness quá đơn giản, pod có thể nhận traffic trước khi startup migration/cache warmup hoàn tất.

**Ví dụ:**
```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("ready", tags: new[] { "ready" })
    .AddCheck<SelfHealthCheck>("live", tags: new[] { "live" });
```

Expose hai endpoint với predicate theo tag để platform dùng đúng mục đích.

**Lưu ý:**
Không đưa mọi external dependency vào liveness. Một dependency bên ngoài hỏng không nhất thiết có nghĩa process cần restart; restart storm có thể làm incident nặng hơn.

### Tip 4 — Với technical SEO, redirect chain là vấn đề engineering chứ không chỉ SEO

**Mẹo:**
Khi đổi URL trong CMS hoặc e-commerce, kiểm tra redirect chain và canonical URL. Cố gắng đưa URL cũ tới đích cuối bằng một redirect thay vì `A -> B -> C -> D`.

**Tại sao hữu ích:**
Mỗi hop thêm network round trip, tăng latency, làm cache/CDN phức tạp hơn và có thể làm crawler tốn crawl budget. Redirect chain còn dễ xuất hiện sau nhiều lần redesign hoặc content migration nếu rule cũ không được cleanup.

**Ví dụ:**
```text
/products/old-phone
  -> /phones/old-phone
  -> /catalog/phones/old-phone
```

Nếu URL cuối cùng là `/catalog/phones/old-phone`, nên cập nhật rule cũ để redirect trực tiếp tới đích cuối và đảm bảo canonical cũng trỏ tới URL chuẩn.

**Lưu ý:**
Không đổi hàng loạt redirect chỉ dựa trên pattern string mà không kiểm tra query string, locale, tracking parameter và route đặc biệt. Redirect sai có thể tạo loop hoặc mất semantic URL quan trọng.

### Tip 5 — Chặn SSRF bằng allowlist đích outbound, không chỉ validate URL syntax

**Mẹo:**
Nếu backend nhận URL từ user hoặc từ content để server-side fetch, đừng chỉ dùng `Uri.TryCreate`. Hãy kiểm soát hostname/protocol được phép, resolve DNS cẩn thận và chặn private/internal address ranges nếu use case không cần truy cập chúng.

**Tại sao hữu ích:**
SSRF xảy ra khi attacker khiến server gọi tới tài nguyên mà client bình thường không truy cập được, ví dụ metadata endpoint, localhost hoặc internal service. URL hoàn toàn hợp lệ về syntax vẫn có thể nguy hiểm.

**Ví dụ:**
Một image-import endpoint nhận:
```text
https://example-cdn.com/image.jpg
```

Thay vì cho phép mọi `https://...`, service có thể chỉ chấp nhận domain trong allowlist và từ chối hostname resolve tới loopback/private network.

**Lưu ý:**
Đừng validate hostname trước rồi dùng DNS resolve khác ở thời điểm request mà bỏ qua DNS rebinding risk. Với hệ thống nhạy cảm, outbound network policy/firewall vẫn nên là lớp bảo vệ bổ sung thay vì chỉ dựa vào application code.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like access thông qua `DbSet<T>`. Một custom Repository chỉ đáng thêm khi nó tạo ra boundary có giá trị rõ ràng, không phải vì mọi project “đều phải có Repository Pattern”.

**Vấn đề nó giải quyết:**
Repository có thể hữu ích khi domain/application layer cần contract ổn định, query logic phức tạp cần tập trung hoặc persistence implementation cần được che giấu có chủ đích. Nhưng generic repository kiểu `GetAll`, `Add`, `Update` thường chỉ wrap lại API EF Core mà không thêm semantics.

**Ví dụ thực tế:**
Một application service đơn giản có thể inject `AppDbContext` trực tiếp và dùng projection/query rõ ràng. Ngược lại, domain có operation như `IOrderRepository.GetPendingForSettlementAsync(...)` có thể đáng abstraction vì method diễn đạt use case và giữ query invariant ở một nơi.

**Trade-off:**
Direct `DbContext` giảm ceremony, giữ access tới capability mạnh của EF Core và dễ tối ưu query. Repository có thể giảm coupling vào ORM ở một số boundary nhưng thêm abstraction, code mapping và nguy cơ tạo API quá generic hoặc che mất feature quan trọng của EF Core.

**Middle → Senior insight:**
Middle developer cần hiểu transaction, tracking và query behavior của EF Core trước khi wrap nó. Senior / Technical developer phải hỏi abstraction này bảo vệ boundary nào, giảm coupling nào và có thực sự tạo giá trị hay chỉ tăng indirection; lựa chọn tốt phụ thuộc complexity của domain, test strategy và khả năng thay đổi persistence.

### Design 2 — Cache-aside cần consistency contract, không chỉ TTL

**Khái niệm:**
Cache-aside là flow trong đó application đọc cache trước, cache miss thì đọc source of truth rồi populate cache. Thiết kế đúng phải xác định rõ dữ liệu được phép stale bao lâu và invalidation xảy ra khi nào.

**Vấn đề nó giải quyết:**
Nếu chỉ đặt TTL mà không định nghĩa consistency requirement, cùng một hệ thống có thể trả dữ liệu cũ 30 phút cho field nhạy cảm như permission hoặc inventory. Cache không chỉ là performance concern; nó thay đổi semantics của read path.

**Ví dụ thực tế:**
Product description có thể chấp nhận stale 5 phút và dùng TTL. Nhưng product stock sau checkout có thể cần invalidate ngay theo event hoặc tránh cache hoàn toàn ở critical confirmation path.

**Trade-off:**
Cache-aside đơn giản, scale read tốt và không buộc source of truth biết cache. Chi phí là cache miss latency, stale data, invalidation complexity, stampede risk và nhiều failure mode hơn khi Redis không khả dụng.

**Middle → Senior insight:**
Middle developer cần implement cache key, serialization, TTL và fallback an toàn. Senior / Technical developer phải phân loại dữ liệu theo freshness SLA, chọn invalidate/update/TTL strategy, quyết định behavior khi cache down và chứng minh rằng complexity cache đáng với bottleneck thực tế.

### Design 3 — API Gateway và BFF giải quyết hai loại boundary khác nhau

**Khái niệm:**
API Gateway thường tập trung concern cross-cutting như routing, authentication edge, rate limiting hoặc observability. Backend for Frontend (BFF) được thiết kế theo nhu cầu cụ thể của một client experience như web, mobile hoặc partner portal.

**Vấn đề nó giải quyết:**
Nếu mobile app phải gọi 8 backend service rồi tự hợp nhất dữ liệu, client bị coupling vào topology nội bộ và chịu nhiều round trip. Nhưng đưa mọi composition logic vào một gateway chung có thể biến gateway thành monolith trung tâm chứa business logic cho tất cả client.

**Ví dụ thực tế:**
Gateway xử lý TLS termination, auth và route `/mobile/*` tới Mobile BFF. Mobile BFF gọi Catalog, Pricing và Profile rồi trả payload tối ưu cho màn hình mobile; Web BFF có thể có shape và caching khác.

**Trade-off:**
Gateway giảm duplication cho edge concern; BFF giảm client/backend coupling và tối ưu payload theo client. Đổi lại, BFF thêm service, deployment và duplication có chủ đích giữa client experiences; gateway quá thông minh lại trở thành bottleneck và ownership hotspot.

**Middle → Senior insight:**
Middle developer cần giữ business rule khỏi gateway và thiết kế BFF contract rõ ràng. Senior / Technical developer phải quyết định logic nào là cross-cutting, logic nào là client-specific, khi nào một API backend chung đã đủ và khi nào thêm BFF thực sự giảm complexity tổng thay vì chỉ chuyển complexity sang layer mới.
