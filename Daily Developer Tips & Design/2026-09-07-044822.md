# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Partition rate limiting theo tenant hoặc user, không chỉ theo IP

**Mẹo:**
Với ASP.NET Core Rate Limiting, chọn partition key phản ánh đúng identity hoặc business boundary của traffic. Với API đã authenticate, `TenantId`, `UserId` hoặc API key thường hữu ích hơn IP thuần túy.

**Tại sao hữu ích:**
Nhiều user có thể đi qua cùng NAT hoặc reverse proxy, trong khi một user có thể thay đổi IP. Nếu limit chỉ theo IP, hệ thống dễ block nhầm nhiều user hợp lệ hoặc để một tenant tiêu thụ quá nhiều quota. Partition đúng giúp bảo vệ capacity theo business boundary.

**Ví dụ:**
```csharp
options.AddPolicy("tenant", context =>
{
    var tenantId = context.User.FindFirst("tenant_id")?.Value ?? "anonymous";

    return RateLimitPartition.GetFixedWindowLimiter(
        tenantId,
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 200,
            Window = TimeSpan.FromMinutes(1)
        });
});
```

**Lưu ý:**
Không tin trực tiếp header do client tự gửi để làm partition key nếu header đó chưa được authenticate/validated. Với hệ thống distributed nhiều instance, cần hiểu limiter đang local trong process hay được enforced ở gateway/shared layer.

### Tip 2 — Giảm cache stampede bằng TTL jitter và single-flight

**Mẹo:**
Khi nhiều request có thể cùng miss một Redis key nóng, thêm TTL jitter và chỉ cho một execution refresh dữ liệu tại một thời điểm thay vì để mọi request cùng đánh vào database.

**Tại sao hữu ích:**
Nếu 10.000 request cùng thấy cache hết hạn trong một khoảng rất ngắn, backend có thể nhận một spike lớn dù traffic bình thường. TTL jitter làm các key không hết hạn đồng loạt; single-flight giảm số lần recompute cùng dữ liệu.

**Ví dụ:**
```csharp
var ttl = TimeSpan.FromMinutes(5)
          + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

await cache.SetStringAsync(key, json, new DistributedCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = ttl
});
```

Với hot key quan trọng, có thể kết hợp distributed lock ngắn hoặc application-level single-flight quanh bước rebuild cache.

**Lưu ý:**
Distributed lock không phải giải pháp miễn phí. Lock timeout, crash giữa chừng và contention có thể tạo failure mode mới. Chỉ thêm khi đo được stampede thực sự đáng kể.

### Tip 3 — Upload Blob trực tiếp bằng short-lived SAS thay vì proxy file lớn qua API

**Mẹo:**
Với upload file lớn lên Azure Blob Storage, cân nhắc để backend cấp short-lived SAS có scope tối thiểu, sau đó client upload trực tiếp vào Blob thay vì stream toàn bộ file qua App Service.

**Tại sao hữu ích:**
Backend proxying làm application instance chịu thêm network throughput, connection lifetime và memory/buffer pressure. Direct upload giúp tách data plane khỏi API server và scale hiệu quả hơn.

**Ví dụ:**
Backend authenticate user, tạo tên blob server-side, rồi phát SAS chỉ cho phép `Write` vào đúng blob trong vài phút. Backend dùng Managed Identity để tạo user delegation SAS thay vì giữ storage account key dài hạn.

**Lưu ý:**
Không cấp SAS ở container scope nếu user chỉ cần upload một file. Sau upload vẫn phải validate metadata, content type, kích thước và nếu cần thì scan malware trước khi file được publish cho người dùng khác.

### Tip 4 — Trong CMS, model content theo editorial intent chứ không theo layout hiện tại

**Mẹo:**
Khi thiết kế content type hoặc block trong Optimizely CMS, ưu tiên mô hình phản ánh ý nghĩa nội dung như `Promo`, `ArticleTeaser`, `ProductReference` thay vì tên gắn chặt với layout như `LeftBlueBox` hoặc `ThreeColumnCard`.

**Tại sao hữu ích:**
Layout thay đổi nhanh hơn business meaning. Nếu schema bám vào UI hiện tại, redesign sẽ kéo theo migration content hoặc tạo hàng loạt content type trùng semantics. Model theo intent giúp reuse tốt hơn giữa web, mobile và headless delivery.

**Ví dụ:**
Một `PromoBlock` có `Heading`, `Body`, `Image`, `Link`, `Theme` có thể render thành card, hero nhỏ hoặc carousel item tùy presentation layer, thay vì tạo ba block riêng chỉ vì vị trí hiển thị khác nhau.

**Lưu ý:**
Đừng làm content model quá generic đến mức editor không hiểu cách dùng. Reusability phải cân bằng với editorial clarity, validation và workflow thực tế.

### Tip 5 — Trong Playwright, chờ condition thay vì dùng delay cố định

**Mẹo:**
Ưu tiên locator và web-first assertions của Playwright thay vì `Thread.Sleep`, `Task.Delay` hoặc timeout cố định để chờ UI ổn định.

**Tại sao hữu ích:**
Delay cố định làm test vừa chậm vừa flaky: quá ngắn thì fail ngẫu nhiên, quá dài thì lãng phí thời gian. Playwright tự retry assertion đến khi condition đạt hoặc timeout thật sự xảy ra.

**Ví dụ:**
```csharp
await Expect(page.GetByRole(AriaRole.Button, new() { Name = "Save" }))
    .ToBeEnabledAsync();

await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
```

**Lưu ý:**
Không tăng global timeout chỉ để che flaky test. Hãy xác định condition nào chưa deterministic: network, animation, test data, race condition hay selector yếu.

## 🧠 Software Design

### Design 1 — CQRS chỉ khi read và write thực sự có áp lực khác nhau

**Khái niệm:**
CQRS tách model hoặc flow xử lý command khỏi query khi hai phía có nhu cầu khác nhau về domain logic, scaling, schema hoặc tối ưu dữ liệu. Nó không đồng nghĩa với việc bắt buộc phải có hai database hoặc event sourcing.

**Vấn đề nó giải quyết:**
Một model duy nhất có thể trở nên khó tối ưu khi write cần bảo vệ invariant phức tạp còn read cần projection nhanh, nhiều join hoặc shape hoàn toàn khác domain model.

**Ví dụ thực tế:**
Order write side giữ aggregate và transaction boundary chặt. Dashboard read side dùng denormalized projection để đọc nhanh theo customer, status và date range mà không hydrate aggregate.

**Trade-off:**
CQRS có thể tăng clarity và cho phép tối ưu read/write độc lập, nhưng thêm command/query models, synchronization, eventual consistency và operational complexity nếu tách storage.

**Middle → Senior insight:**
Middle developer cần tách command/query responsibility rõ và tránh đưa business invariant vào read model. Senior / Technical developer phải chứng minh áp lực khiến CQRS đáng giá; với CRUD thông thường, một model đơn giản có thể tốt hơn rất nhiều.

### Design 2 — Chọn SQL hay document database theo aggregate và access pattern

**Khái niệm:**
Quyết định SQL vs MongoDB/Cosmos DB nên xuất phát từ transaction boundary, relationship, query pattern, scale distribution và consistency requirement, không phải từ việc dữ liệu “trông giống JSON”.

**Vấn đề nó giải quyết:**
Relational model mạnh ở joins, constraints và multi-row transactions. Document model phù hợp khi aggregate có thể đọc/ghi gần như nguyên khối và cần scale theo partition key rõ ràng.

**Ví dụ thực tế:**
Billing ledger có quan hệ và consistency chặt thường phù hợp SQL. Product catalog với document giàu thuộc tính khác nhau theo category và access chủ yếu theo product/tenant có thể phù hợp document database hơn.

**Trade-off:**
SQL đem lại relational integrity và query flexibility nhưng có thể khó scale một số workload phân tán. Document database đơn giản hóa aggregate retrieval và horizontal distribution, nhưng denormalization, cross-partition query và consistency trade-off phải được quản lý rõ.

**Middle → Senior insight:**
Middle developer cần biết model và index đúng cho công nghệ đã chọn. Senior / Technical developer phải đánh giá migration cost, operational skills của team, data growth, query evolution và failure semantics trước khi chọn database.

### Design 3 — Tách deployment khỏi release bằng Feature Flags

**Khái niệm:**
Feature Flags cho phép code được deploy vào production nhưng chưa được bật cho toàn bộ user. Deployment trở thành thao tác đưa artifact lên môi trường; release là quyết định mở capability cho audience cụ thể.

**Vấn đề nó giải quyết:**
Nếu mọi deployment đồng nghĩa với bật feature ngay lập tức, rollback thường phải redeploy artifact cũ. Với change rủi ro cao, team cần khả năng rollout dần hoặc tắt nhanh mà không rebuild.

**Ví dụ thực tế:**
Một checkout flow mới được deploy nhưng chỉ bật cho internal users, sau đó 5%, 25%, 100% traffic. Khi error rate tăng, flag được tắt trong vài giây trong khi code vẫn giữ nguyên deployment.

**Trade-off:**
Feature Flags giảm release risk và hỗ trợ progressive delivery, nhưng tạo branch logic, test matrix, config dependency và technical debt nếu flag cũ không được dọn.

**Middle → Senior insight:**
Middle developer cần implement flag ở boundary hợp lý và test cả enabled/disabled path. Senior / Technical developer cần thiết kế ownership, kill switch, rollout metrics, auditability và lifecycle xóa flag để tránh biến hệ thống thành mạng lưới condition khó hiểu.
