## Developer Tips & Tricks

### 1. SQL deadlock: sửa thứ tự truy cập resource trước khi nghĩ đến tăng timeout

**Vấn đề thực tế:** Hai request cập nhật `Orders` và `Inventory` đồng thời. Request A lock `Orders` rồi chờ `Inventory`; request B lock `Inventory` rồi chờ `Orders`. SQL Server phát hiện cycle và chọn một transaction làm deadlock victim. Tăng command timeout không giải quyết được vì đây không phải đơn thuần là query chạy chậm.

**Cơ chế bên dưới:** Deadlock xuất hiện khi các transaction giữ resource mà transaction khác cần và tạo thành vòng chờ. Database phải phá vòng bằng cách rollback một transaction. Root cause thường nằm ở access order, transaction scope quá rộng, index không phù hợp khiến lock footprint lớn, hoặc isolation behavior không phù hợp.

**Cách xử lý:** Thu thập deadlock graph trước khi sửa. Chuẩn hóa thứ tự truy cập resource giữa các code path, giữ transaction ngắn, tránh gọi HTTP trong transaction, và kiểm tra execution plan/index để giảm số row/page bị lock.

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(cancellationToken);

// Giữ cùng access order ở mọi workflow: Inventory -> Orders.
var inventory = await db.Inventory
    .SingleAsync(x => x.ProductId == productId, cancellationToken);

var order = await db.Orders
    .SingleAsync(x => x.Id == orderId, cancellationToken);

inventory.Available -= quantity;
order.Status = OrderStatus.Confirmed;

await db.SaveChangesAsync(cancellationToken);
await transaction.CommitAsync(cancellationToken);
```

Retry deadlock victim có thể là lớp resilience bổ sung vì deadlock là transient failure, nhưng retry không thay thế việc sửa contention pattern.

**Khi nên dùng:** Khi production xuất hiện SQL error `1205`, latency spike quanh write-heavy endpoint, hoặc transaction failures khó tái hiện dưới tải thấp.

### 2. ASP.NET Core rate limiting: partition theo identity phù hợp, không chỉ theo IP

**Vấn đề thực tế:** API áp fixed-window limiter theo IP. Một doanh nghiệp có hàng trăm user đi qua cùng NAT gateway nên họ vô tình chia sẻ quota; ngược lại attacker có thể đổi IP để né giới hạn.

**Cơ chế bên dưới:** Rate limiting hiệu quả phụ thuộc vào partition key. IP là network identity, không nhất thiết là business identity. Với authenticated API, `tenantId`, `clientId`, API key hoặc user identifier thường phản ánh quota boundary tốt hơn. Anonymous endpoint vẫn có thể cần IP hoặc composite key.

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("tenant-api", httpContext =>
    {
        var tenantId = httpContext.User.FindFirst("tenant_id")?.Value
                       ?? $"ip:{httpContext.Connection.RemoteIpAddress}";

        return RateLimitPartition.GetTokenBucketLimiter(
            tenantId,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                AutoReplenishment = true,
                QueueLimit = 20
            });
    });
});
```

**Trade-off:** Per-user partition bảo vệ fairness nhưng có thể tạo rất nhiều limiter instances. Per-tenant partition dễ quản lý quota nhưng một noisy user có thể ảnh hưởng user khác trong tenant. Chọn key theo business contract và threat model.

**Khi nên dùng:** Public APIs, expensive endpoints, login/recovery flows, third-party integrations và multi-tenant SaaS.

### 3. Azure Managed Identity: bỏ secret khỏi application thay vì chỉ “cất secret tốt hơn”

**Vấn đề thực tế:** Application chạy trên Azure App Service dùng connection string chứa credential hoặc client secret trong configuration. Đưa secret vào Azure Key Vault tốt hơn source control, nhưng application vẫn cần một credential khác để đọc Key Vault nếu thiết kế identity chưa đúng.

**Cơ chế bên dưới:** Managed Identity cung cấp workload identity do Azure quản lý. Application lấy token từ Microsoft Entra ID cho resource được hỗ trợ mà không cần lưu password/client secret. Quyền truy cập được cấp cho identity bằng RBAC hoặc resource-specific authorization.

```csharp
var credential = new DefaultAzureCredential();

var secretClient = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

KeyVaultSecret secret = await secretClient.GetSecretAsync(
    "ThirdPartyApiKey",
    cancellationToken: cancellationToken);
```

`DefaultAzureCredential` cũng hỗ trợ developer identity khi chạy local, giúp cùng code path hoạt động local và Azure mà không hard-code production credential.

**Điểm cần chú ý:** Managed Identity không tự cấp authorization. Identity tồn tại nhưng thiếu RBAC vẫn nhận `403`. Ngược lại, cấp role quá rộng biến identity thành blast-radius lớn nếu workload bị compromise.

**Khi nên dùng:** App Service, Functions, VM, containerized Azure workloads truy cập Key Vault, Storage, Service Bus, SQL hoặc các Azure resources hỗ trợ Entra authentication.

### 4. Playwright flaky test: chờ trạng thái người dùng quan sát được, đừng chèn `WaitForTimeout`

**Vấn đề thực tế:** E2E test thỉnh thoảng fail vì UI chưa load xong. Team thêm `WaitForTimeout(3000)` và test “ổn hơn” trên laptop nhưng vẫn fail trên CI, đồng thời suite chạy chậm đáng kể.

**Cơ chế bên dưới:** Fixed sleep giả định timing thay vì synchronization với application state. CI load, network latency và rendering time thay đổi nên 3 giây có lúc quá dài, có lúc vẫn chưa đủ. Playwright locators và assertions có auto-wait/retry dựa trên trạng thái thực tế.

```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

await Expect(page.GetByText("Saved successfully"))
    .ToBeVisibleAsync();

await Expect(page.GetByTestId("order-status"))
    .ToHaveTextAsync("Confirmed");
```

Nếu UI phụ thuộc request cụ thể, có thể đợi response hoặc observable UI state thay vì ngủ một khoảng cố định. Test nên xác nhận behavior mà user thấy, không coupling quá sâu với implementation timing.

**Khi nên dùng:** CI E2E suites, SPA/API integration tests và mọi test có intermittent timeout hoặc phụ thuộc network/rendering.

### 5. Vue/TypeScript: hủy request cũ để tránh stale response ghi đè state mới

**Vấn đề thực tế:** Search box gọi API mỗi khi query thay đổi. User gõ `redis`, request cho `re` chậm hơn request cho `redis`; response cũ về sau cùng và ghi đè kết quả mới. Debounce giảm số request nhưng không loại bỏ race condition.

**Cơ chế bên dưới:** HTTP requests hoàn thành không đảm bảo theo thứ tự khởi tạo. UI cần định nghĩa request nào còn authoritative. `AbortController` cho phép hủy request cũ khi state đầu vào thay đổi.

```ts
import { ref, watch } from 'vue'

const query = ref('')
const results = ref<SearchResult[]>([])
let controller: AbortController | undefined

watch(query, async value => {
  controller?.abort()
  controller = new AbortController()

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(value)}`,
      { signal: controller.signal }
    )

    results.value = await response.json()
  } catch (error) {
    if (!(error instanceof DOMException && error.name === 'AbortError')) {
      throw error
    }
  }
})
```

Ở backend, cancellation propagation vẫn quan trọng để client disconnect/abort có cơ hội dừng work không còn giá trị.

**Khi nên dùng:** Autocomplete, filters, route-driven data loading, live search và UI có nhiều request cạnh tranh cập nhật cùng state.

### 6. Strangler Fig: hiện đại hóa legacy system theo capability thay vì big-bang rewrite

**Vấn đề thực tế:** Một .NET Framework monolith lớn cần chuyển sang modern .NET. Rewrite toàn bộ trong một project mới nghe có vẻ sạch, nhưng business vẫn thay đổi trong nhiều tháng hoặc nhiều năm rewrite. Hai hệ thống lệch behavior, migration date liên tục trượt và risk dồn vào một cutover lớn.

**Thiết kế:** Strangler Fig chuyển từng capability qua boundary mới. Traffic được route sang implementation mới khi capability đó đủ an toàn; phần còn lại tiếp tục chạy legacy.

```text
Clients
   |
   v
Routing / Facade
   |----------------------|
   v                      v
Legacy .NET Framework   Modern .NET
   |                      |
Orders (old)          Catalog (new)
Customers (old)       Search (new)
Payments (old)
```

**Trade-off:** Migration risk nhỏ hơn và tạo value sớm, nhưng giai đoạn chuyển tiếp có duplicated infrastructure, data synchronization, routing complexity và temporary architecture. Boundary chọn sai có thể tạo distributed monolith thay vì modernization.

**Khi phù hợp:** Legacy system lớn, business không thể dừng feature delivery, có capability boundaries tương đối rõ và rewrite toàn bộ có risk cao. Với application nhỏ, rewrite ngắn hạn có thể đơn giản hơn.

### 7. Inbox / Idempotent Consumer: at-least-once delivery đòi hỏi business side effect chịu được duplicate

**Vấn đề thực tế:** Consumer nhận `PaymentCaptured`, cập nhật order thành công nhưng crash trước khi message broker ghi nhận completion. Message được deliver lại. Nếu consumer gửi email, cộng điểm hoặc tạo invoice lần nữa mà không deduplicate, một event logic biến thành nhiều side effects.

**Thiết kế:** Lưu `MessageId` đã xử lý cùng transaction với business change. Khi message được redeliver, consumer nhận diện duplicate và bỏ qua business operation.

```text
Message Broker
     |
     v
 Consumer
     |
     +---- DB Transaction ----------------+
     | Check Inbox(MessageId)             |
     | Apply business change              |
     | Insert Inbox(MessageId)            |
     +--------------- COMMIT -------------+
     |
     v
Complete/Ack message
```

**Trade-off:** Inbox tăng storage, cleanup và transaction work. Idempotency cũng phải được thiết kế ở business level: một số operation có thể tự nhiên idempotent, số khác cần unique constraint hoặc idempotency key. “Exactly once” ở broker không nên được hiểu là mọi external side effect tự động exactly-once.

**Khi phù hợp:** Azure Service Bus hoặc broker dùng at-least-once delivery, đặc biệt với financial/business side effects không được phép lặp.

### 8. Modular Monolith: boundary phải được enforce bằng dependency direction, không chỉ bằng folder

**Vấn đề thực tế:** Codebase được chia thành `Orders`, `Catalog`, `Customers`, nhưng project nào cũng reference project nào, truy cập trực tiếp DbContext/table của module khác và dùng internal entity xuyên boundary. Về tên gọi đây là modular monolith; về coupling nó vẫn là monolith khó thay đổi.

**Thiết kế:** Mỗi module sở hữu model và persistence boundary của nó. Cross-module interaction đi qua explicit contract, application API hoặc domain/integration event. Có thể dùng architecture tests để ngăn dependency bị phá trở lại.

```text
Host
 |
 +--> Orders.Module ----> Orders.Infrastructure
 |        |
 |        +--> Contracts
 |
 +--> Catalog.Module ---> Catalog.Infrastructure
          |
          +--> Contracts

Orders không reference Catalog.Infrastructure
Catalog không expose internal entities ra ngoài module
```

**Trade-off:** Boundary rõ giúp independent evolution, giảm cognitive load và tạo đường chuyển sang service riêng nếu sau này thực sự cần. Đổi lại, team phải chấp nhận mapping, explicit contracts và đôi khi duplicate concept có chủ đích. Nếu ép mọi interaction thành asynchronous messaging ngay từ đầu, modular monolith có thể bị over-engineered.

**Khi phù hợp:** Domain đủ lớn để cần module boundaries nhưng operational cost của microservices chưa được biện minh. Đây thường là điểm khởi đầu tốt hơn microservices khi team vẫn đang khám phá domain boundaries.
