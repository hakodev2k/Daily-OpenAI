# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán `ThreadPool` starvation bằng metric trước khi tăng thread

**Mẹo:**
Khi ASP.NET Core API có latency tăng mạnh nhưng CPU chưa cao, kiểm tra `ThreadPool` queue length, thread count và request latency bằng `dotnet-counters` hoặc Application Insights trước khi thay đổi cấu hình.

**Tại sao hữu ích:**
`ThreadPool` starvation thường xảy ra khi nhiều request chặn thread bằng synchronous I/O, `.Result`, `.Wait()` hoặc workload blocking kéo dài. Runtime sẽ từ từ bổ sung thread, nhưng trong thời gian đó request bị xếp hàng nên p95/p99 tăng rất nhanh dù CPU chưa bão hòa.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id <pid> System.Runtime
```

Một pattern đáng nghi:
```text
ThreadPool Queue Length tăng
ThreadPool Thread Count tăng dần
CPU chỉ 40-50%
request p95 tăng từ 200 ms lên 4 s
```

Sau đó tìm synchronous blocking trong request path thay vì chỉ tăng `MinThreads`.

**Lưu ý:**
Tăng `ThreadPool.SetMinThreads` có thể che triệu chứng và làm memory/context switching tăng. Chỉ tuning sau khi đã hiểu workload; fix tốt hơn thường là loại bỏ blocking I/O hoặc giới hạn concurrency của dependency chậm.

### Tip 2 — Chống Redis cache stampede bằng jitter và single-flight

**Mẹo:**
Với cache key có traffic cao, đừng để hàng nghìn request cùng miss khi TTL hết đúng một thời điểm. Dùng TTL có jitter và, khi cần, cơ chế single-flight/lock ngắn để chỉ một request rebuild dữ liệu.

**Tại sao hữu ích:**
Cache hoạt động tốt có thể che tải lớn khỏi database. Khi một hot key hết hạn, toàn bộ request cùng đổ về database tạo spike CPU, connection pool exhaustion hoặc timeout—đây là cache stampede.

**Ví dụ:**
```text
TTL cơ sở: 10 phút
TTL thực tế: 10 phút + random(0..90 giây)
```

Với key đặc biệt nóng:
```text
request A miss -> lấy lease ngắn -> rebuild cache
request B/C/... -> chờ ngắn hoặc dùng stale value
```

**Lưu ý:**
Distributed lock không nên giữ lâu hơn thời gian rebuild cần thiết và vẫn phải có expiry. Với dữ liệu cho phép stale, stale-while-revalidate thường đơn giản hơn việc bắt mọi request chờ lock.

### Tip 3 — Phân biệt Kubernetes `readinessProbe` và `livenessProbe`

**Mẹo:**
Dùng `readinessProbe` để quyết định Pod có nên nhận traffic; dùng `livenessProbe` để phát hiện process thực sự cần restart. Đừng dùng cùng một dependency check cho cả hai theo mặc định.

**Tại sao hữu ích:**
Nếu database tạm thời lỗi và `livenessProbe` cũng fail theo, Kubernetes có thể restart hàng loạt Pod dù process vẫn khỏe, tạo restart storm. Trong nhiều trường hợp application chỉ cần tạm rời load balancer cho tới khi dependency hồi phục.

**Ví dụ:**
```text
/readiness
- app initialized
- critical dependency đủ điều kiện phục vụ request

/liveness
- process/event loop còn hoạt động
- không kiểm tra mọi external service
```

**Lưu ý:**
Readiness quá nhạy cũng có thể loại toàn bộ replica khỏi traffic cùng lúc. Health check phải phản ánh khả năng phục vụ thực tế và cần được test trong failure scenario, không chỉ ở happy path.

### Tip 4 — Diff OpenAPI contract trong CI để bắt breaking change sớm

**Mẹo:**
Nếu REST API có nhiều consumer, tạo OpenAPI document trong pipeline và so với baseline/released contract để phát hiện breaking change trước merge hoặc release.

**Tại sao hữu ích:**
Một thay đổi tưởng nhỏ như đổi field required, xóa enum value, đổi status code hoặc rename property có thể compile bình thường nhưng làm mobile/frontend/third-party client hỏng sau deploy.

**Ví dụ:**
Các change cần flag:
```text
- remove response property
- optional -> required request field
- string -> integer
- remove enum member
- remove endpoint/status contract
```

Sau đó reviewer quyết định dùng versioning, expand-and-contract hoặc deprecation thay vì phát hiện sau production.

**Lưu ý:**
Contract diff không chứng minh semantic compatibility. API có thể giữ schema nhưng đổi business meaning. Integration/contract tests vẫn cần bảo vệ behavior quan trọng.

### Tip 5 — Trong Optimizely CMS, tham chiếu content bằng model/reference thay vì hard-code URL

**Mẹo:**
Khi Page hoặc Block liên kết tới content khác trong Optimizely CMS, ưu tiên `ContentReference`/typed content property hoặc content-link abstraction phù hợp thay vì lưu URL string cố định trong business content model.

**Tại sao hữu ích:**
Editor có thể move, rename hoặc thay route của page. Reference theo content identity cho CMS cơ hội resolve URL hiện tại, hỗ trợ editorial workflow tốt hơn và giảm broken link sau restructuring.

**Ví dụ:**
```csharp
[Display(Name = "CTA target")]
public virtual ContentReference? TargetPage { get; set; }
```

Renderer resolve URL tại thời điểm render thay vì editor nhập `/products/old-path` thủ công.

**Lưu ý:**
External URL vẫn cần string/URL field riêng. Đừng ép mọi link thành internal content reference; model phải phân biệt rõ internal content, media và external destination.

## 🧠 Software Design

### Design 1 — Contract Testing vs End-to-End Testing

**Khái niệm:**
Contract Testing kiểm tra producer và consumer đồng ý về interface/protocol; End-to-End Testing kiểm tra flow xuyên nhiều component đang chạy cùng nhau. Hai loại test giải quyết rủi ro khác nhau và không thay thế nhau.

**Vấn đề nó giải quyết:**
Một microservice/API có thể pass unit test nhưng đổi response khiến consumer hỏng. E2E có thể bắt lỗi này nhưng thường chậm, flaky và khó chạy cho mọi combination version. Contract test tập trung trực tiếp vào compatibility boundary.

**Ví dụ thực tế:**
```text
Consumer Order UI kỳ vọng:
GET /api/orders/{id}
-> id, status, total
```

Contract test xác nhận producer vẫn đáp ứng expectation đó. Một E2E test riêng xác nhận user thực sự mở Order page, authentication hoạt động và data flow end-to-end đúng.

**Trade-off:**
Contract tests nhanh và cô lập compatibility tốt nhưng không chứng minh network/configuration/deployment thực tế. E2E có confidence rộng hơn nhưng đắt, chậm và khó debug khi fail.

**Middle → Senior insight:**
Middle developer cần biết test nào bảo vệ boundary nào và tránh dùng E2E cho mọi rule. Senior / Technical developer phải thiết kế test pyramid theo failure cost, release independence và ownership, đồng thời quyết định contract nào đủ quan trọng để trở thành compatibility gate.

### Design 2 — Cache-Aside và failure semantics khi Redis không khả dụng

**Khái niệm:**
Cache-Aside để application tự đọc cache, miss thì đọc source-of-truth rồi populate cache. Quan trọng nhất không chỉ là cache hit path mà là định nghĩa hệ thống phải làm gì khi cache chậm, timeout hoặc unavailable.

**Vấn đề nó giải quyết:**
Nếu Redis là optimization nhưng application coi cache failure là fatal, một cache outage có thể làm toàn bộ business API down. Ngược lại, bypass cache vô hạn có thể dồn toàn bộ traffic xuống database và gây cascading failure.

**Ví dụ thực tế:**
```text
Redis timeout
-> fail nhanh sau 50 ms
-> fallback DB nếu DB budget còn đủ
-> giới hạn concurrency
-> không retry Redis 5 lần trong request
```

Với endpoint không critical, có thể trả stale data hoặc degrade feature thay vì ép source database chịu toàn bộ peak load.

**Trade-off:**
Cache-Aside đơn giản và giữ database là source-of-truth nhưng có stale-data window, stampede và invalidation complexity. Fallback tăng availability nhưng phải có capacity planning; database có thể không chịu nổi traffic vốn được cache hấp thụ.

**Middle → Senior insight:**
Middle developer cần xử lý miss/timeout khác nhau và đặt timeout ngắn cho cache. Senior / Technical developer phải thiết kế degraded mode, capacity headroom, stale policy, backpressure và observability để cache outage không biến thành database outage.

### Design 3 — Bounded Context thay vì một shared domain model cho toàn hệ thống

**Khái niệm:**
Trong Domain-Driven Design, Bounded Context xác định nơi một domain model và terminology có nghĩa nhất quán. Cùng một từ như `Customer` có thể cần model khác trong Sales, Billing và Support thay vì một `Customer` object khổng lồ dùng chung toàn công ty.

**Vấn đề nó giải quyết:**
Shared domain model toàn hệ thống dễ tạo coupling: Billing thêm field phục vụ invoice, Support thêm trạng thái riêng, Sales thêm lead metadata; cuối cùng mọi team phụ thuộc một entity lớn khó thay đổi và khó sở hữu.

**Ví dụ thực tế:**
```text
Sales Customer:
- LeadScore
- AccountOwner

Billing Customer:
- BillingAddress
- TaxProfile
- PaymentTerms

Support Customer:
- SLA
- SupportTier
```

Các context trao đổi qua contract rõ ràng thay vì cùng sửa một database/entity model.

**Trade-off:**
Bounded Context tăng autonomy và giảm semantic coupling nhưng tạo duplication có chủ đích, mapping và integration boundaries. Với hệ thống nhỏ, chia quá nhiều context có thể chỉ thêm ceremony.

**Middle → Senior insight:**
Middle developer cần tránh leak entity/database model của module này sang module khác. Senior / Technical developer phải xác định boundary từ business capability, language, ownership và change pattern—không chia context chỉ theo technical layer hoặc số lượng table.
