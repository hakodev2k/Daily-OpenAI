# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `HttpCompletionOption.ResponseHeadersRead` khi tải payload lớn

**Mẹo:**
Khi ASP.NET Core service tải file lớn hoặc stream response từ third-party API, dùng `ResponseHeadersRead` để bắt đầu xử lý stream ngay sau khi nhận headers thay vì đợi toàn bộ body được buffer.

**Tại sao hữu ích:**
Mặc định, một số cách dùng `HttpClient` khiến application chờ response body hoàn tất trước khi tiếp tục. Với payload lớn, điều này tăng memory usage và thời gian giữ buffer. Streaming giúp giảm peak memory và cho phép xử lý dữ liệu theo luồng.

**Ví dụ:**
```csharp
using var response = await httpClient.GetAsync(
    url,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);

response.EnsureSuccessStatusCode();

await using var stream = await response.Content
    .ReadAsStreamAsync(cancellationToken);

await stream.CopyToAsync(destination, cancellationToken);
```

**Lưu ý:**
Streaming không tự giới hạn kích thước payload. Vẫn cần timeout, cancellation, kiểm tra `Content-Length` khi phù hợp và giới hạn tổng bytes nếu nguồn không đáng tin cậy.

### Tip 2 — Với EF Core, dùng `AsSplitQuery` khi nhiều collection `Include` gây cartesian explosion

**Mẹo:**
Nếu một query load nhiều collection navigation bằng `Include`, kiểm tra SQL và số row thực tế. Khi join tạo cartesian explosion, cân nhắc `AsSplitQuery()` hoặc projection phù hợp hơn.

**Tại sao hữu ích:**
Một parent có 20 items và 15 comments có thể tạo tới 300 row trung gian dù object graph cuối chỉ có 35 child records. Network payload và materialization cost tăng nhanh khi nhiều collection được join trong cùng query.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .ToListAsync(cancellationToken);
```

`AsSplitQuery` tách một số collection load thành nhiều SQL query để tránh multiplication của row.

**Lưu ý:**
Split query tăng số round trip và có consistency trade-off nếu dữ liệu thay đổi giữa các query. Đừng dùng theo mặc định; projection sang DTO thường tốt hơn nếu endpoint chỉ cần một subset dữ liệu.

### Tip 3 — Trong Elasticsearch, dùng `filter` cho điều kiện không cần relevance scoring

**Mẹo:**
Khi query chỉ cần lọc chính xác theo tenant, status, category hoặc date range, đặt chúng trong `bool.filter` thay vì `must` nếu không cần ảnh hưởng `_score`.

**Tại sao hữu ích:**
Filter context bỏ qua relevance scoring cho điều kiện đó và phù hợp hơn với exact constraints. Nó giúp query intent rõ hơn và có thể tận dụng caching tốt hơn tùy workload.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless keyboard" } }
      ],
      "filter": [
        { "term": { "tenantId": "t-42" } },
        { "term": { "isActive": true } }
      ]
    }
  }
}
```

`match` quyết định relevance; `tenantId` và `isActive` chỉ giới hạn tập document.

**Lưu ý:**
Đừng dùng full-text query cho field kiểu keyword nếu chỉ cần exact match. Mapping sai giữa `text` và `keyword` thường gây cả semantic bug lẫn performance issue.

### Tip 4 — Dùng test container hoặc database thật cho query behavior quan trọng

**Mẹo:**
Với logic phụ thuộc SQL translation, constraint, transaction hoặc isolation behavior, ưu tiên integration test trên database thật hoặc disposable container thay vì chỉ mock `DbSet`.

**Tại sao hữu ích:**
Mock có thể xác nhận method được gọi nhưng không chứng minh LINQ translate được, constraint chạy đúng hay transaction behavior giống production. Nhiều lỗi data access chỉ xuất hiện khi query đi qua provider thật.

**Ví dụ:**
Một test cho unique email nên kiểm tra database constraint thật:
```text
insert user A: alice@example.com -> success
insert user B: alice@example.com -> unique violation
```

Test này có giá trị hơn mock repository trả về exception giả.

**Lưu ý:**
Integration test chậm hơn unit test và cần quản lý test data tốt. Không cần biến toàn bộ test suite thành database test; chỉ dùng ở boundary nơi behavior phụ thuộc infrastructure thật.

### Tip 5 — Khi App Service trả 5xx sau deployment, kiểm tra startup và dependency trước khi rollback mù

**Mẹo:**
Nếu Azure App Service bắt đầu trả 5xx ngay sau deployment, đi theo chuỗi `symptom → evidence → hypothesis`: xem deployment log, startup log, Application Insights exception và health endpoint trước khi kết luận code business bị lỗi.

**Tại sao hữu ích:**
Nhiều incident sau deploy đến từ configuration thiếu, secret không resolve, migration lỗi, assembly mismatch hoặc dependency không reachable. Rollback có thể khôi phục nhanh nhưng không cho biết nguyên nhân và đôi khi rollback vẫn lỗi nếu environment đã thay đổi.

**Ví dụ:**
```text
5xx tăng ngay sau deploy
-> startup exception: KeyVault secret not found
-> compare slot settings
-> secret reference sai tên
-> fix configuration
```

Nếu process chưa start thành công, request-level debugging thường không giúp nhiều.

**Lưu ý:**
Rollback vẫn là lựa chọn đúng khi blast radius lớn và root cause chưa rõ. Nhưng song song phải giữ evidence như logs, deployment version và configuration diff để RCA sau incident không dựa vào phỏng đoán.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency khi nhiều user cùng sửa một resource

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng dữ liệu nhưng kiểm tra version khi update. Nếu state đã thay đổi từ lúc đọc, update bị từ chối thay vì âm thầm ghi đè dữ liệu mới hơn.

**Vấn đề nó giải quyết:**
Trong CRM hoặc CMS, hai editor có thể mở cùng record. Editor A lưu trước, editor B lưu sau với dữ liệu cũ và vô tình overwrite thay đổi của A nếu hệ thống chỉ chạy `UPDATE` theo primary key.

**Ví dụ thực tế:**
Entity có concurrency token:
```text
Id = 42
Version = 8
```

Update chỉ thành công nếu:
```sql
UPDATE ...
WHERE Id = 42 AND Version = 8;
```

Nếu row đã lên version 9, application nhận conflict và có thể yêu cầu user reload/merge.

**Trade-off:**
Optimistic concurrency tránh lock dài và phù hợp khi conflict hiếm, nhưng buộc application có UX/flow xử lý conflict. Với resource bị tranh chấp liên tục, retry hoặc merge có thể phức tạp.

**Middle → Senior insight:**
Middle developer cần implement concurrency token và xử lý conflict đúng thay vì nuốt exception. Senior / Technical developer phải quyết định conflict resolution strategy, retry semantics và liệu business cần merge, reject hay serialized workflow.

### Design 2 — Saga Orchestration vs Choreography cho workflow phân tán

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction. Orchestration dùng một coordinator điều khiển các bước; Choreography để services phản ứng với events của nhau mà không có coordinator trung tâm.

**Vấn đề nó giải quyết:**
Một order workflow có thể cần Payment, Inventory và Shipping nhưng không thể giữ một ACID transaction xuyên ba service/database. Hệ thống cần quản lý partial failure và compensating action.

**Ví dụ thực tế:**
Orchestration:
```text
Order Saga
-> ReserveInventory
-> ChargePayment
-> CreateShipment
-> nếu payment fail: ReleaseInventory
```

Choreography:
```text
OrderCreated
-> InventoryReserved
-> PaymentCharged
-> ShipmentCreated
```

Mỗi service publish event để bước tiếp theo phản ứng.

**Trade-off:**
Orchestration làm flow, timeout và compensation rõ hơn nhưng tạo coordinator cần vận hành. Choreography giảm central control nhưng dễ tạo event chain khó quan sát và coupling ngầm giữa services.

**Middle → Senior insight:**
Middle developer cần hiểu local transaction, idempotency và compensation. Senior / Technical developer phải chọn coordination model dựa trên workflow complexity, ownership team, observability, failure recovery và mức coupling chấp nhận được.

### Design 3 — Modular Monolith với boundary rõ trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ deployment unit chung nhưng chia application thành các module có ownership, contract và data access boundary rõ. Mục tiêu là giảm coupling mà chưa trả chi phí vận hành của distributed system.

**Vấn đề nó giải quyết:**
Một monolith lớn thường trở nên khó thay đổi vì mọi module gọi trực tiếp vào table, service và internal type của nhau. Tách ngay thành Microservices có thể chỉ chuyển coupling trong process thành coupling qua network mà chưa cải thiện domain boundary.

**Ví dụ thực tế:**
```text
Modules/
  Orders/
  Catalog/
  Customers/
```

`Orders` không query trực tiếp table nội bộ của `Catalog`; giao tiếp qua contract/application API của module. Database có thể vẫn chung nhưng ownership schema được quy ước rõ.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, tracing và transaction nhưng vẫn chia sẻ process và có thể chia sẻ database. Microservices cho independent scaling/deployment nhưng thêm network failure, messaging, observability và operational overhead.

**Middle → Senior insight:**
Middle developer cần tôn trọng module boundary và tránh shortcut bằng direct cross-module access. Senior / Technical developer phải đánh giá team topology, scaling pressure, release independence và data ownership trước khi quyết định boundary nào thật sự cần tách thành service riêng.
