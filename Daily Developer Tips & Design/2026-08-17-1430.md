# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup read-only nhiều lần

**Mẹo:**
Nếu một tập key/value được khởi tạo một lần rồi đọc rất nhiều lần trong suốt vòng đời process, cân nhắc `FrozenDictionary<TKey, TValue>` thay vì `Dictionary<TKey, TValue>` thông thường.

**Tại sao hữu ích:**
`FrozenDictionary` tối ưu cấu trúc dữ liệu cho read-heavy lookup sau giai đoạn khởi tạo. Với hot path hoặc bảng mapping lớn, nó có thể giảm chi phí lookup so với collection mutable thông thường.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

private static readonly FrozenDictionary<string, int> StatusCodes =
    new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase)
    {
        ["Pending"] = 1,
        ["Approved"] = 2,
        ["Rejected"] = 3
    }
    .ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);

var code = StatusCodes["approved"];
```

**Lưu ý:**
Chi phí tạo collection ban đầu có thể cao hơn. Không nên dùng nếu dữ liệu thay đổi thường xuyên hoặc collection rất nhỏ và không nằm trên hot path.

### Tip 2 — Dùng `ExecuteUpdateAsync` khi không cần load entity vào memory

**Mẹo:**
Với EF Core, khi cần update nhiều rows theo cùng một rule, dùng `ExecuteUpdateAsync` thay vì query toàn bộ entities, sửa từng object rồi `SaveChangesAsync()`.

**Tại sao hữu ích:**
Giảm round trip, memory allocation và change-tracking overhead. Database thực hiện update trực tiếp bằng một câu SQL.

**Ví dụ:**
```csharp
await dbContext.Jobs
    .Where(x => x.Status == JobStatus.Running && x.HeartbeatAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, JobStatus.Failed)
        .SetProperty(x => x.FinishedAt, now),
        cancellationToken);
```

**Lưu ý:**
`ExecuteUpdateAsync` bỏ qua change tracker của các entity đã được load trong `DbContext`. Nếu context đang giữ cùng entities, state trong memory có thể stale và cần được quản lý cẩn thận.

### Tip 3 — Dùng filtered index cho tập dữ liệu active nhỏ nhưng bảng tổng rất lớn

**Mẹo:**
Nếu query production chủ yếu truy cập một subset nhỏ như `IsDeleted = 0`, `Status = 'Pending'` hoặc `ProcessedAt IS NULL`, filtered index có thể hiệu quả hơn index toàn bảng.

**Tại sao hữu ích:**
Index nhỏ hơn, ít I/O hơn, cập nhật rẻ hơn và optimizer có thể tìm dữ liệu mục tiêu nhanh hơn khi predicate khớp điều kiện filter.

**Ví dụ:**
```sql
CREATE INDEX IX_Jobs_Pending_CreatedAt
ON Jobs (CreatedAt)
INCLUDE (Id, Type)
WHERE Status = 'Pending';
```

Query:

```sql
SELECT Id, Type, CreatedAt
FROM Jobs
WHERE Status = 'Pending'
ORDER BY CreatedAt;
```

**Lưu ý:**
Filtered index chỉ hữu ích khi query predicate tương thích với filter. Nếu application thường query nhiều trạng thái khác nhau, lợi ích có thể nhỏ hoặc cần chiến lược index khác.

### Tip 4 — Test ASP.NET Core bằng `WebApplicationFactory` để bắt lỗi wiring thật

**Mẹo:**
Ngoài unit test handler/service, hãy có integration test chạy application pipeline thật bằng `WebApplicationFactory<TEntryPoint>` cho các endpoint quan trọng.

**Tại sao hữu ích:**
Loại test này bắt được lỗi mà unit test thường bỏ sót: DI registration thiếu, middleware order sai, authentication config sai, serialization mismatch hoặc routing lỗi.

**Ví dụ:**
```csharp
public sealed class OrdersApiTests(
    WebApplicationFactory<Program> factory)
{
    [Fact]
    public async Task GetOrder_Returns404_WhenOrderDoesNotExist()
    {
        using var client = factory.CreateClient();

        var response = await client.GetAsync(
            "/api/orders/00000000-0000-0000-0000-000000000001");

        Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
    }
}
```

**Lưu ý:**
Đừng biến mọi test thành full integration test. Suite quá nặng sẽ chạy chậm và khó debug; giữ unit test cho logic thuần và integration test cho boundaries quan trọng.

### Tip 5 — Dùng `ss`, `lsof` và `ps` để debug process/port trên Linux trước khi đoán

**Mẹo:**
Khi service không bind được port hoặc health check không tới được process, kiểm tra process và socket thực tế từ máy/container thay vì chỉ đọc application log.

**Tại sao hữu ích:**
Giúp phân biệt nhanh các tình huống như port đã bị chiếm, process không chạy, bind sai interface hoặc service đang listen trên port khác.

**Ví dụ:**
```bash
ss -ltnp
```

Tìm process dùng port 8080:

```bash
lsof -i :8080
```

Kiểm tra process:

```bash
ps aux | grep dotnet
```

**Lưu ý:**
Trong container tối giản, một số tool có thể không được cài sẵn. Ngoài ra, quyền hạn thấp có thể làm bạn không thấy đầy đủ process/socket metadata.

## 🧠 Software Design

### Design 1 — Strong consistency hay Eventual consistency phải xuất phát từ business invariant

**Khái niệm:**
Strong consistency yêu cầu các consumer nhìn thấy state mới một cách đồng bộ hoặc gần như tức thời trước khi operation được coi là hoàn thành. Eventual consistency chấp nhận khoảng thời gian các replica/module chưa đồng bộ hoàn toàn.

**Vấn đề nó giải quyết:**
Distributed systems khó giữ tất cả thành phần đồng bộ mà vẫn đạt latency thấp và availability cao. Việc ép mọi dữ liệu thành strongly consistent thường làm hệ thống phức tạp và chậm hơn mức business thực sự cần.

**Ví dụ thực tế:**
Khi trừ tồn kho để xác nhận đơn hàng cuối cùng, hệ thống có thể cần consistency mạnh quanh invariant `AvailableQuantity >= 0`. Nhưng analytics dashboard hoặc search index có thể chấp nhận cập nhật chậm vài giây.

**Trade-off:**
Strong consistency đơn giản hóa reasoning ở những invariant quan trọng nhưng có thể tăng latency, lock contention hoặc dependency vào coordination. Eventual consistency tăng availability và decoupling nhưng cần xử lý stale reads, duplicate events và user experience khi dữ liệu chưa đồng bộ.

**Middle → Senior insight:**
Middle developer cần hiểu consistency không phải lựa chọn “càng mạnh càng tốt”. Senior developer phải xác định invariant nào thực sự cần atomicity, dữ liệu nào chấp nhận stale, thời gian stale tối đa bao nhiêu và cách hệ thống phục hồi khi đồng bộ thất bại.

### Design 2 — Saga thay Distributed Transaction cho workflow xuyên nhiều service

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transactions. Nếu bước sau thất bại, hệ thống thực hiện compensating action cho các bước trước thay vì giữ một distributed transaction xuyên nhiều database/service.

**Vấn đề nó giải quyết:**
Một workflow như Order → Payment → Inventory → Shipping khó dùng transaction ACID duy nhất khi mỗi capability có database và deployment boundary riêng.

**Ví dụ thực tế:**
Checkout flow:

1. Tạo Order ở trạng thái `Pending`.
2. Reserve inventory.
3. Charge payment.
4. Confirm order.

Nếu payment thất bại, Saga release inventory và chuyển order sang `PaymentFailed` thay vì rollback một transaction phân tán toàn hệ thống.

**Trade-off:**
Saga tránh coupling mạnh và distributed lock nhưng đổi lại phải thiết kế compensation, retry, idempotency, ordering và observability. Không phải mọi side effect đều có thể “undo” hoàn hảo.

**Middle → Senior insight:**
Middle developer nên hiểu compensation khác rollback database. Senior developer phải chọn orchestration hay choreography, định nghĩa state machine rõ ràng, xử lý duplicate message và xác định failure nào retry, failure nào compensate, failure nào cần human intervention.

### Design 3 — Abstraction chỉ đáng tạo khi nó che được volatility thật

**Khái niệm:**
Abstraction tốt che giấu một phần implementation có khả năng thay đổi độc lập và cung cấp contract ổn định cho caller. Abstraction kém chỉ thêm một layer không có semantic value.

**Vấn đề nó giải quyết:**
Codebase lớn thường tích tụ interface, wrapper và generic repository được tạo “để sau này dễ thay đổi”, nhưng cuối cùng chỉ tăng navigation cost và làm logic business khó đọc.

**Ví dụ thực tế:**
Một `IPaymentGateway` có ý nghĩa nếu hệ thống thực sự hỗ trợ nhiều provider hoặc cần isolate external SDK. Nhưng tạo `IUserService` chỉ để wrap một `UserService` duy nhất với cùng method signature, không có policy hay boundary khác biệt, có thể không mang giá trị.

**Trade-off:**
Abstraction đúng giúp testability, isolation và thay đổi implementation dễ hơn. Abstraction quá sớm gây indirection, API design overhead và làm refactoring khó vì phải sửa nhiều contract giả tạo.

**Middle → Senior insight:**
Middle developer nên phân biệt abstraction với việc chỉ tạo interface. Senior developer cần nhận diện volatility axis thực tế, tránh YAGNI, và chỉ tạo boundary khi nó bảo vệ domain, dependency hoặc change pattern có bằng chứng rõ ràng.
