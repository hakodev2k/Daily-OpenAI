# Daily Developer Tips & Design — 2026-09-30

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng exception filter để chỉ bắt exception khi thật sự xử lý được

**Mẹo:**
Trong C#, dùng `catch (...) when (...)` khi quyết định xử lý phụ thuộc vào metadata của exception hoặc trạng thái hiện tại, thay vì bắt rộng rồi kiểm tra bên trong `catch`.

**Tại sao hữu ích:**
Exception filter được đánh giá trước khi stack unwinding đi vào handler. Nếu filter trả `false`, runtime tiếp tục tìm handler phù hợp và giữ đường đi của exception rõ ràng hơn. Điều này đặc biệt hữu ích khi một SDK dùng cùng exception type cho nhiều status/error code.

**Ví dụ:**
```csharp
try
{
    await blobClient.GetPropertiesAsync(cancellationToken: ct);
}
catch (RequestFailedException ex) when (ex.Status == 404)
{
    return Results.NotFound();
}
```
Các lỗi `401`, `403`, `500` không bị biến nhầm thành `404` và vẫn đi qua error handling chung.

**Lưu ý:**
Filter phải nhanh và không có side effect đáng kể. Đừng dùng filter để che một `catch (Exception)` quá rộng; cancellation, authorization và transient failure thường cần semantics khác nhau.

### Tip 2 — MongoDB compound index phải bám theo query shape, không bám theo danh sách field

**Mẹo:**
Khi thiết kế compound index, nhìn vào equality filters, sort và range của workload thực tế thay vì chỉ gom các field thường xuất hiện trong query vào một index.

**Tại sao hữu ích:**
Thứ tự key quyết định prefix nào của B-tree có thể được khai thác hiệu quả. Với query có equality trên tenant, sort theo thời gian và range, index phù hợp có thể vừa thu hẹp tập dữ liệu vừa tránh in-memory sort.

**Ví dụ:**
```javascript
db.orders.createIndex({ tenantId: 1, createdAt: -1, _id: -1 })

db.orders.find({
  tenantId: "t-42",
  createdAt: { $lt: ISODate("2026-09-30T00:00:00Z") }
}).sort({ createdAt: -1, _id: -1 }).limit(50)
```
Dùng `explain("executionStats")` để kiểm tra `keysExamined`, `docsExamined` và stage sort thay vì suy luận từ tên index.

**Lưu ý:**
Một compound index phục vụ tốt query này chưa chắc tốt cho query khác; mỗi index còn tăng storage và write amplification. Cardinality, sort direction và actual workload mới quyết định thiết kế.

### Tip 3 — Azure Functions: poison message phải có đường điều tra, không chỉ retry

**Mẹo:**
Với queue/message-triggered Function, thiết kế ngay cách quan sát message thất bại nhiều lần: lưu correlation/business ID, exception category và đưa message sang dead-letter/poison path có quy trình xử lý rõ ràng.

**Tại sao hữu ích:**
Retry chỉ hữu ích với transient failure. Nếu payload vi phạm invariant hoặc dependency trả lỗi permanent, retry lặp lại vừa tốn compute vừa che nguyên nhân. Poison path tách failure khỏi luồng bình thường để backlog vẫn tiến triển.

**Ví dụ:**
Một Function xử lý `InvoiceRequested` thất bại vì currency code không hợp lệ. Sau ngưỡng delivery, message vào DLQ; dashboard hiển thị `MessageId`, `InvoiceId`, delivery count và failure category để operator sửa dữ liệu hoặc replay có kiểm soát.

**Lưu ý:**
Không log toàn bộ payload nếu chứa PII/secret. Replay message sau khi sửa lỗi vẫn có thể tạo duplicate side effect, nên consumer cần idempotency và phải phân biệt transient với permanent failure.

### Tip 4 — AI coding agent: khóa giả định bằng repository evidence trước khi sửa code

**Mẹo:**
Khi giao bug cho AI coding agent, yêu cầu nó đọc implementation, tests, project/package versions và call sites liên quan trước khi đề xuất patch; sau đó xác minh bằng build/test thực tế.

**Tại sao hữu ích:**
Agent có thể sinh API tồn tại ở version khác, đoán sai architecture hoặc “sửa” symptom tại layer không sở hữu invariant. Grounding vào source hiện tại giảm hallucination và giúp patch phù hợp với conventions của repository.

**Ví dụ:**
Thay vì yêu cầu “fix EF Core concurrency”, cung cấp reproduction và yêu cầu agent truy vết từ endpoint → application service → `DbContext` → migration/schema, chỉ dùng APIs có trong target framework, rồi chạy test tái hiện conflict trước và sau patch.

**Lưu ý:**
Test xanh không chứng minh patch đúng nếu agent cũng viết test theo implementation sai. Review security, transaction boundary, migration impact và edge cases như với code do người viết; AI là accelerator, không phải authority.

### Tip 5 — Core Web Vitals: tìm resource gây LCP thay vì chỉ nhìn Lighthouse score

**Mẹo:**
Khi LCP xấu, dùng browser DevTools/Lighthouse để xác định chính xác LCP element và network dependency chain của nó trước khi tối ưu bundle hoặc backend một cách chung chung.

**Tại sao hữu ích:**
LCP có thể bị chi phối bởi TTFB, ảnh hero tải muộn, CSS blocking hoặc JavaScript trì hoãn render. Score tổng hợp chỉ báo symptom; waterfall và timing breakdown mới chỉ ra phần latency có thể tác động.

**Ví dụ:**
Trang CMS có LCP 4.2 giây. Trace cho thấy HTML về trong 350 ms nhưng hero image chỉ được phát hiện sau khi một client-side component chạy. Chuyển resource quan trọng vào HTML ban đầu và cấu hình kích thước/priority phù hợp giải quyết đúng critical path thay vì thêm cache vào API không liên quan.

**Lưu ý:**
Đừng tối ưu chỉ từ một lần chạy local. Kiểm tra field data khi có thể, nhiều device/network profiles và tránh preload quá nhiều resource vì chính preload có thể cạnh tranh bandwidth với tài nguyên quan trọng.

## 🧠 Software Design

### Design 1 — Strangler Fig cho modernization hệ thống legacy

**Khái niệm:**
Thay vì rewrite toàn bộ một hệ thống .NET Framework trong một lần, đặt boundary/routing phù hợp để chức năng mới hoặc đã migration dần đi qua implementation mới, còn phần chưa chuyển tiếp tục chạy trên hệ thống cũ.

**Vấn đề nó giải quyết:**
Big-bang rewrite có feedback cycle dài, khó chứng minh behavioral parity và dồn migration risk vào một cutover lớn. Incremental replacement cho phép migration theo capability có thể kiểm chứng.

**Ví dụ thực tế:**
Một ASP.NET MVC/.NET Framework CMS giữ checkout cũ nhưng chuyển `/api/catalog` sang ASP.NET Core trước. Gateway/routing giữ contract bên ngoài ổn định; telemetry so sánh error rate và latency trước khi tiếp tục tách capability kế tiếp.

**Trade-off:**
Migration từng phần giảm cutover risk nhưng tạm thời phải vận hành hai stacks, routing, compatibility và đôi khi duplicate model/data integration. Nếu hệ thống nhỏ, ít thay đổi và rewrite có phạm vi thật sự kiểm soát được, strangler infrastructure có thể không đáng chi phí.

**Middle → Senior insight:**
Middle cần giữ contract, regression tests và dependency direction khi di chuyển từng slice. Senior / Technical phải chọn seam có thể tách, thứ tự migration, data ownership, rollback/cutover strategy và thời điểm xóa legacy; mục tiêu là giảm risk tổng thể chứ không kéo dài dual-running vô hạn.

### Design 2 — Saga orchestration vs choreography cho transaction xuyên service

**Khái niệm:**
Saga chia workflow thành local transactions và compensating actions. Orchestration có một coordinator điều khiển các bước; choreography để services phản ứng với events mà không có coordinator trung tâm.

**Vấn đề nó giải quyết:**
Order, payment và inventory thuộc các service/database khác nhau không thể dựa vào một ACID transaction đơn giản. Khi bước giữa thất bại, hệ thống cần trạng thái workflow và cách bù trừ có chủ đích.

**Ví dụ thực tế:**
Checkout reserve inventory → authorize payment → confirm order. Với orchestration, workflow service biết bước hiện tại và gọi compensation khi payment thất bại. Với choreography, `InventoryReserved` kích hoạt payment và các events tiếp theo dẫn workflow tiến triển.

**Trade-off:**
Orchestration làm flow, timeout và recovery dễ nhìn hơn nhưng coordinator có thể trở thành coupling hub. Choreography tăng autonomy nhưng flow dễ bị phân tán qua nhiều handlers, khó trace và có nguy cơ event chain ngoài kiểm soát.

**Middle → Senior insight:**
Middle cần hiểu local transaction, idempotency và compensation không đồng nghĩa rollback tuyệt đối. Senior phải chọn coordination model theo độ phức tạp workflow, ownership, observability và evolution; đồng thời thiết kế timeout, stuck-state recovery và manual intervention thay vì chỉ vẽ happy path.

### Design 3 — Authorization boundary theo resource, không chỉ theo role

**Khái niệm:**
Authorization nên bảo vệ operation trên resource cụ thể dựa trên policy và ownership/tenant/context cần thiết, thay vì chỉ kiểm tra user có role như `Admin` hoặc `Editor` ở controller rồi tin mọi ID được gửi lên.

**Vấn đề nó giải quyết:**
Role-level check có thể cho phép IDOR/BOLA: user hợp lệ với chức năng nhưng truy cập resource của tenant hoặc owner khác bằng cách đổi identifier trong request.

**Ví dụ thực tế:**
Endpoint `PUT /tenants/{tenantId}/orders/{orderId}` không chỉ yêu cầu `OrderEditor`; application còn xác minh order thuộc tenant mà principal được phép quản lý. Policy/authorization service nhận resource đã load và đánh giá quyền trước mutation.

**Trade-off:**
Resource-based authorization bảo vệ invariant tốt hơn nhưng thêm query/context propagation và cần policy ownership rõ ràng. Nhồi mọi business rule vào authorization framework cũng làm boundary khó hiểu; domain invariant và access-control rule vẫn phải được phân biệt.

**Middle → Senior insight:**
Middle cần kiểm tra authorization ở server cho từng operation/resource và không tin route/body claims từ client. Senior / Technical phải xác định trust boundary, tenant isolation, policy composition, caching an toàn và nơi enforcement phải lặp lại ở downstream service; security phải tồn tại tại boundary sở hữu resource, không chỉ ở UI hay gateway.
