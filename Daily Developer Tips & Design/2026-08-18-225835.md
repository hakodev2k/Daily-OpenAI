# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CollectionsMarshal.GetValueRefOrAddDefault` cho dictionary hot path

**Mẹo:**
Trong code cực kỳ nhạy performance, có thể dùng `CollectionsMarshal.GetValueRefOrAddDefault` để lấy `ref` trực tiếp tới value trong `Dictionary<TKey,TValue>` và tránh lookup hai lần.

**Tại sao hữu ích:**
Hữu ích với counter, aggregation hoặc parser chạy hàng triệu lần, nơi pattern `TryGetValue` rồi gán lại tạo thêm lookup và copy.

**Ví dụ:**
```csharp
using System.Runtime.InteropServices;

ref int count = ref CollectionsMarshal.GetValueRefOrAddDefault(
    counters,
    key,
    out var exists);

if (!exists)
    count = 0;

count++;
```

**Lưu ý:**
Đây là low-level API. Không giữ `ref` qua thao tác có thể resize dictionary và không dùng khi code thông thường chưa có bằng chứng performance bottleneck.

### Tip 2 — Tìm deadlock SQL bằng deadlock graph thay vì chỉ retry

**Mẹo:**
Khi gặp deadlock, thu thập deadlock graph để xem transaction nào giữ lock, transaction nào chờ lock và thứ tự access resource.

**Tại sao hữu ích:**
Retry chỉ che triệu chứng. Deadlock graph giúp sửa root cause như update bảng theo thứ tự khác nhau, transaction quá dài hoặc index không phù hợp.

**Ví dụ:**
Với SQL Server, có thể dùng Extended Events session `system_health` để xem `xml_deadlock_report` thay vì chỉ dựa vào exception `1205`.

**Lưu ý:**
Đừng kết luận deadlock chỉ vì query chậm. Blocking, timeout và deadlock là ba vấn đề khác nhau và cần bằng chứng riêng.

### Tip 3 — Dùng `curl --trace-time` khi debug request chậm

**Mẹo:**
Khi nghi ngờ latency nằm ở DNS, TLS hoặc server response, dùng `curl` với timing/trace thay vì chỉ nhìn tổng thời gian.

**Tại sao hữu ích:**
Giúp phân biệt chậm trước khi kết nối, chậm trong handshake hay chậm sau khi request đã gửi.

**Ví dụ:**
```bash
curl --trace-time --trace-ascii - https://api.example.com/health
```

Hoặc đo từng phase:

```bash
curl -s -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} start=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/health
```

**Lưu ý:**
Trace có thể chứa header hoặc token nhạy cảm. Không paste nguyên trace vào ticket/public channel nếu chưa sanitize.

### Tip 4 — Dùng compiled query cho EF Core query cực nóng

**Mẹo:**
Nếu cùng một query shape được gọi rất nhiều lần, cân nhắc `EF.CompileAsyncQuery` để giảm chi phí compile expression/query pipeline lặp lại.

**Tại sao hữu ích:**
Có thể giảm CPU overhead ở hot path có tần suất cao, đặc biệt khi query đơn giản nhưng được gọi liên tục.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, int, IAsyncEnumerable<User>>
    GetUsersByTenant = EF.CompileAsyncQuery(
        (AppDbContext db, int tenantId) =>
            db.Users
              .Where(x => x.TenantId == tenantId)
              .AsNoTracking());
```

**Lưu ý:**
Đừng áp dụng đại trà. Database I/O thường lớn hơn query compilation cost; benchmark trước khi tăng complexity.

### Tip 5 — Dùng `ss` và `lsof` để debug port/process trên Linux

**Mẹo:**
Khi service không bind được port hoặc nghi có process giữ connection, kiểm tra socket và process trực tiếp từ command line.

**Tại sao hữu ích:**
Nhanh hơn việc đoán lỗi application, đặc biệt trong VM, container host hoặc production server.

**Ví dụ:**
```bash
ss -ltnp | grep :8080
```

Hoặc:

```bash
lsof -i :8080
```

**Lưu ý:**
Một số thông tin process yêu cầu quyền cao hơn. Trong container, bạn có thể đang nhìn network namespace khác với host nên cần kiểm tra đúng môi trường.

## 🧠 Software Design

### Design 1 — Saga: Orchestration vs Choreography

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction và dùng compensation khi một bước thất bại. Có hai hướng phổ biến: Orchestration với một coordinator điều khiển flow, hoặc Choreography nơi các service phản ứng qua event.

**Vấn đề nó giải quyết:**
Trong distributed system, không thể dựa vào một database transaction để bao trùm nhiều service độc lập nhưng business flow vẫn cần tiến triển hoặc rollback logic hợp lý.

**Ví dụ thực tế:**
Flow đặt hàng gồm Order, Payment, Inventory và Shipping. Nếu Payment thành công nhưng Inventory thất bại, Saga có thể phát lệnh hoàn tiền thay vì cố dùng distributed transaction.

**Trade-off:**
Orchestration dễ nhìn flow và debug nhưng coordinator có thể trở thành điểm tập trung logic. Choreography giảm coupling trực tiếp nhưng flow khó quan sát, dễ tạo event chain phức tạp và hidden dependency.

**Middle → Senior insight:**
Middle developer cần hiểu compensation không phải rollback database thực sự. Senior developer phải chọn orchestration hay choreography dựa trên độ phức tạp flow, ownership, observability, failure handling và khả năng thay đổi business process.

### Design 2 — Expand-and-Contract cho database schema evolution

**Khái niệm:**
Expand-and-Contract thay đổi schema qua nhiều bước tương thích ngược: trước tiên thêm cấu trúc mới, sau đó deploy code hỗ trợ cả cũ và mới, migrate dữ liệu, rồi cuối cùng xóa cấu trúc cũ.

**Vấn đề nó giải quyết:**
Tránh deployment kiểu “đổi schema và code cùng lúc” gây downtime hoặc làm version cũ của application crash trong rolling deployment.

**Ví dụ thực tế:**
Muốn đổi `CustomerName` thành `FirstName` + `LastName`. Thay vì drop cột cũ ngay, thêm hai cột mới, dual-write hoặc backfill, chuyển read path sang field mới, rồi chỉ xóa `CustomerName` khi toàn bộ instance đã dùng schema mới.

**Trade-off:**
Tăng safety và hỗ trợ zero-downtime deployment nhưng kéo dài thời gian tồn tại duplicated fields, migration code và cleanup work.

**Middle → Senior insight:**
Middle developer cần hiểu migration không chỉ là `ALTER TABLE`. Senior developer phải thiết kế deployment sequence, backward compatibility, backfill strategy, rollback và thời điểm cleanup dựa trên release topology thực tế.

### Design 3 — Observability Cardinality Budget

**Khái niệm:**
Cardinality budget giới hạn số lượng giá trị duy nhất được dùng trong metric labels/tags, đặc biệt với Prometheus hoặc time-series backend.

**Vấn đề nó giải quyết:**
Label như `userId`, `requestId` hoặc raw URL có thể tạo hàng triệu time series, khiến monitoring tốn memory, storage và query chậm hoặc sập.

**Ví dụ thực tế:**
Metric tốt:
```text
http_requests_total{method="GET",route="/orders/{id}",status="200"}
```

Metric nguy hiểm:
```text
http_requests_total{user_id="918273",request_id="...",url="/orders/12345"}
```

**Trade-off:**
Cardinality thấp giúp metrics rẻ và ổn định nhưng mất chi tiết theo từng request/user. Chi tiết đó nên chuyển sang logs hoặc traces thay vì metric labels.

**Middle → Senior insight:**
Middle developer cần biết metric, log và trace phục vụ mục đích khác nhau. Senior developer phải thiết kế telemetry schema có budget rõ ràng cho cardinality, retention, sampling và cost thay vì để mỗi team tự thêm label tùy ý.
