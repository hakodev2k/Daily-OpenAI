# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` cho bulk update không cần materialize entity

**Mẹo:**
Với EF Core, nếu cần update nhiều rows bằng cùng một rule và không cần chạy domain behavior trên từng entity, cân nhắc `ExecuteUpdateAsync` thay vì load toàn bộ entities vào memory rồi sửa từng object.

**Tại sao hữu ích:**
Cách load → track → modify → `SaveChanges` tạo nhiều allocation, change-tracking work và round trip không cần thiết. `ExecuteUpdateAsync` dịch trực tiếp thành SQL `UPDATE`, phù hợp với administrative job, cleanup hoặc status transition đơn giản.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```

**Lưu ý:**
Bulk update bỏ qua tracked entity state và không tự chạy domain event/business logic trong entity. Nếu invariant cần xử lý từng aggregate, đừng dùng chỉ vì nhanh hơn.

### Tip 2 — Khi gặp SQL Server deadlock, đọc deadlock graph trước khi chỉ thêm retry

**Mẹo:**
Nếu production xuất hiện deadlock, lấy deadlock graph từ Extended Events/Application Insights/monitoring để xác định transaction nào giữ lock, chờ lock và thứ tự access resource.

**Tại sao hữu ích:**
Retry có thể làm request thành công ở lần sau nhưng không giải quyết root cause. Deadlock thường đến từ hai transaction lấy cùng resource theo thứ tự khác nhau, transaction quá dài hoặc index/query plan khiến lock footprint lớn hơn cần thiết.

**Ví dụ:**
```text
Transaction A: lock Orders -> chờ Payments
Transaction B: lock Payments -> chờ Orders
```

Một fix bền vững có thể là thống nhất access order, rút ngắn transaction hoặc giảm số row bị lock bằng query/index phù hợp.

**Lưu ý:**
Không phải mọi deadlock đều cần redesign lớn. Một mức retry nhỏ vẫn hợp lý cho lỗi transient, nhưng phải có telemetry để biết retry đang che tần suất deadlock tăng dần hay không.

### Tip 3 — Chống SSRF bằng cách kiểm soát destination, không chỉ validate URL format

**Mẹo:**
Nếu ASP.NET Core endpoint nhận URL từ user để fetch webhook, image hoặc external resource, validate scheme/host theo allowlist hoặc business rule; đừng coi `Uri.TryCreate` là đủ.

**Tại sao hữu ích:**
Một URL hợp lệ về syntax vẫn có thể trỏ tới `localhost`, metadata endpoint, private IP hoặc internal service. SSRF cho phép attacker dùng server của bạn làm proxy tới network mà họ không truy cập trực tiếp được.

**Ví dụ:**
```text
Không đủ:
https://127.0.0.1/admin
http://169.254.169.254/...

Tốt hơn:
- chỉ cho phép https
- allowlist domain cần thiết
- block loopback/private/link-local destination
- re-check sau DNS resolution/redirect khi threat model yêu cầu
```

**Lưu ý:**
Chỉ regex hostname không đủ để xử lý DNS rebinding, redirect hoặc alternate IP representation. Với use case rủi ro cao, nên dùng outbound proxy/network policy ngoài application validation.

### Tip 4 — Dùng `PerformanceObserver` để đo Web Vitals từ browser thật thay vì chỉ dựa Lighthouse local

**Mẹo:**
Khi tối ưu website, bổ sung Real User Monitoring bằng browser performance APIs hoặc telemetry SDK để quan sát LCP, INP, CLS theo user/device/network thực tế.

**Tại sao hữu ích:**
Lighthouse là synthetic measurement trong điều kiện kiểm soát. Production user có device yếu, network chậm, cache state và content khác nhau; p75 Web Vitals ngoài thực tế mới phản ánh trải nghiệm phổ biến.

**Ví dụ:**
```text
Lighthouse local LCP: 1.8s
Production p75 LCP: 3.6s

Trace production cho thấy hero image + backend TTFB là bottleneck chính.
```

Từ đó tối ưu đúng layer thay vì chỉ giảm bundle dựa trên lab result.

**Lưu ý:**
Đừng gắn user-specific ID hoặc high-cardinality field vào mọi performance metric. Sampling, privacy và aggregation strategy cần được thiết kế từ đầu.

### Tip 5 — Dùng `git worktree` khi cần sửa hotfix song song mà không stash workspace hiện tại

**Mẹo:**
Khi đang làm feature dở nhưng cần checkout branch khác để hotfix, dùng `git worktree` tạo working directory thứ hai thay vì stash/reset liên tục.

**Tại sao hữu ích:**
Mỗi worktree dùng cùng repository object database nhưng có working tree và branch riêng. Điều này giảm context switching, tránh stash conflict và rất hữu ích khi cần chạy hai version cạnh nhau.

**Ví dụ:**
```bash
git worktree add ../app-hotfix hotfix/payment-timeout

# sau khi xong
git worktree remove ../app-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree. Đừng để worktree cũ tồn tại lâu mà quên cleanup vì dễ gây nhầm branch/path trong script hoặc IDE.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho idempotent message consumer

**Khái niệm:**
Inbox Pattern lưu message identifier đã xử lý cùng trạng thái cần thiết ở phía consumer để phát hiện delivery lặp và tránh chạy business side effect nhiều lần.

**Vấn đề nó giải quyết:**
Message broker thường cung cấp at-least-once delivery. Consumer có thể xử lý xong database change nhưng crash trước khi acknowledge; broker sau đó redeliver cùng message.

**Ví dụ thực tế:**
```text
MessageId = order-123-paid

DB transaction:
- kiểm tra InboxMessages chưa có MessageId
- update Order = Paid
- insert InboxMessages(MessageId)
COMMIT
```

Lần delivery tiếp theo thấy MessageId đã tồn tại và bỏ qua business mutation.

**Trade-off:**
Inbox tăng correctness nhưng thêm storage, unique constraint, cleanup/retention và transaction coordination. Nếu operation vốn idempotent tự nhiên nhờ unique key/state transition, một inbox riêng có thể không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là behavior bình thường và dùng transaction/unique constraint đúng. Senior / Technical developer phải chọn deduplication key, retention horizon, ordering semantics và cách recovery khi inbox ghi thành công nhưng downstream side effect ngoài database chưa hoàn tất.

### Design 2 — Primary Database vs Elasticsearch: eventual consistency phải là contract rõ ràng

**Khái niệm:**
Khi Elasticsearch làm search/read index còn SQL/MongoDB là source-of-truth, hệ thống phải chấp nhận một khoảng trễ giữa write thành công và search index phản ánh thay đổi đó.

**Vấn đề nó giải quyết:**
Search engine tối ưu full-text/query nhưng không nên bị đối xử như transactional source-of-truth. Nếu application giả định write DB xong thì search lập tức thấy dữ liệu mới, user sẽ gặp behavior “lúc có lúc không” khó giải thích.

**Ví dụ thực tế:**
```text
POST /products -> DB commit thành công
-> outbox/event
-> indexer cập nhật Elasticsearch sau 1-3 giây

Product detail đọc DB: thấy ngay
Search results: có thể trễ ngắn
```

UI có thể hiển thị “đang cập nhật chỉ mục” hoặc đọc-after-write từ primary store cho flow vừa tạo.

**Trade-off:**
Tách search index giúp query/search scale tốt nhưng thêm synchronization, replay, backfill và stale-data handling. Strong consistency giả tạo bằng dual-write trực tiếp thường tạo failure mode khó hơn.

**Middle → Senior insight:**
Middle developer cần biết dữ liệu nào là source-of-truth và không sửa index như database chính. Senior / Technical developer phải định nghĩa freshness SLA, sync mechanism, rebuild strategy, monitoring lag và UX cho read-after-write thay vì để eventual consistency là một bất ngờ production.

### Design 3 — Shared Database vs Database per Service

**Khái niệm:**
Shared Database cho nhiều module/service cùng truy cập một schema/database; Database per Service giữ ownership dữ liệu riêng và buộc cross-service access qua contract/integration.

**Vấn đề nó giải quyết:**
Shared DB giúp join và transaction đơn giản khi hệ thống còn nhỏ, nhưng các service có thể coupling trực tiếp qua table/schema. Database per Service tăng autonomy nhưng biến cross-boundary transaction/query thành distributed-system problem.

**Ví dụ thực tế:**
```text
Shared DB:
OrderService -> Orders, Customers
BillingService -> Orders, Payments

Database per Service:
Order DB
Billing DB
-> trao đổi qua API/event
```

Nếu Billing cần một số Order data, nó có thể giữ projection riêng thay vì query trực tiếp Order DB.

**Trade-off:**
Shared DB đơn giản hóa operations và reporting nhưng giảm ownership/isolation. Database per Service hỗ trợ independent evolution và fault boundary tốt hơn nhưng tăng eventual consistency, duplicated read models, migrations và operational overhead.

**Middle → Senior insight:**
Middle developer cần tôn trọng ownership boundary ngay cả khi tạm dùng chung database. Senior / Technical developer phải quyết định dựa trên team autonomy, independent deployment, scaling, compliance và change frequency—không tách database chỉ vì kiến trúc Microservices “chuẩn” hơn.
