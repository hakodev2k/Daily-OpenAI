# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong .NET

**Mẹo:**
Khi ASP.NET Core latency tăng mạnh nhưng CPU chưa chạm trần, kiểm tra ThreadPool queue, thread count và request duration trước khi kết luận phải scale out. `dotnet-counters` có thể giúp đối chiếu `thread_pool.queue.length`, `thread_pool.thread.count`, CPU và exception rate.

**Tại sao hữu ích:**
Code sync-over-async như `.Result`, `.Wait()` hoặc blocking I/O giữ ThreadPool thread trong lúc không làm CPU work. Runtime có thể bổ sung thread, nhưng quá trình này không tức thời; request mới phải xếp hàng và latency tăng dù CPU còn rảnh. Đây là failure mode khác với CPU saturation nên cách xử lý cũng khác.

**Ví dụ:**
```csharp
// Có thể block request thread
var profile = httpClient.GetFromJsonAsync<UserProfile>(url).Result;

// Cho phép thread phục vụ work khác trong lúc chờ I/O
var profile = await httpClient.GetFromJsonAsync<UserProfile>(url, ct);
```
Nếu sau deployment queue length tăng cùng số ThreadPool thread nhưng CPU vẫn trung bình, hãy tìm blocking call trong hot path trước khi tăng instance.

**Lưu ý:**
Không phải mọi synchronous code đều xấu và `Task.Run` không phải cách sửa blocking I/O trong ASP.NET Core. Đẩy blocking work sang `Task.Run` vẫn tiêu thụ ThreadPool capacity; ưu tiên async API thật sự hoặc cô lập workload không thể async hóa.

### Tip 2 — Deadlock phải được đọc như một chu kỳ dependency, không chỉ retry

**Mẹo:**
Khi SQL Server báo deadlock, thu deadlock graph và xác định transaction nào giữ resource nào, đang chờ resource nào, cùng thứ tự truy cập object/index. Retry chỉ nên là lớp resilience sau khi hiểu root cause.

**Tại sao hữu ích:**
Deadlock xảy ra khi các transaction tạo wait cycle; database buộc chọn một victim để phá chu kỳ. Nếu hai code path luôn lock cùng resource theo thứ tự ngược nhau, retry có thể giảm lỗi nhìn thấy nhưng contention và deadlock vẫn tiếp tục dưới tải.

**Ví dụ:**
Transaction A update `Orders` rồi `Inventory`, trong khi transaction B update `Inventory` rồi `Orders`. Chuẩn hóa thứ tự truy cập thành `Orders → Inventory`, rút ngắn transaction và bảo đảm predicate/index hợp lý có thể loại bỏ hoặc giảm đáng kể wait cycle.

**Lưu ý:**
Đừng tự động chuyển isolation level hoặc thêm `NOLOCK` để “sửa deadlock”. Điều đó có thể đổi consistency semantics hoặc tạo dirty/inconsistent reads. Xác minh lock mode, execution plan, transaction scope và business invariant trước.

### Tip 3 — Azure Service Bus lock expiration có thể tạo duplicate processing dù handler chưa lỗi

**Mẹo:**
Với message handler chạy lâu, theo dõi message lock duration, auto-lock renewal và thời gian xử lý thực tế. Thiết kế consumer idempotent vì message có thể được giao lại nếu lock hết trước khi `Complete` thành công.

**Tại sao hữu ích:**
Peek-lock không phải ownership vĩnh viễn. Consumer nhận message, broker khóa tạm thời; nếu processing vượt lease hoặc process mất kết nối, message có thể trở lại queue và một consumer khác xử lý. Handler đầu tiên vẫn có thể đang thực hiện side effect ở external system.

**Ví dụ:**
Worker nhận `GenerateInvoice`, gọi provider mất 90 giây trong khi lock không được renew đủ lâu. Broker redeliver message; worker thứ hai tạo invoice lần nữa. Dùng business key/Inbox record để claim operation idempotently thay vì dựa vào assumption “mỗi message chỉ chạy một lần”.

**Lưu ý:**
Tăng lock duration rất lớn chỉ kéo dài failure window và không tạo exactly-once semantics. Nếu task kéo dài nhiều phút, cân nhắc chia workflow, persist state hoặc chuyển long-running work sang mô hình phù hợp hơn.

### Tip 4 — Elasticsearch `filter` phù hợp cho điều kiện yes/no hơn `must` có scoring

**Mẹo:**
Khi điều kiện chỉ dùng để thu hẹp tập document như `tenantId`, `status`, range hoặc permission scope, đặt nó trong filter context thay vì bắt Elasticsearch tính relevance score không cần thiết.

**Tại sao hữu ích:**
Full-text query cần scoring để xếp hạng mức độ liên quan; structured filter chỉ cần xác định match hay không. Tách hai concern giúp query rõ semantics hơn và có thể tận dụng optimization/caching phù hợp của filter context.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "title": "wireless keyboard" }}],
      "filter": [
        { "term": { "tenantId": "acme" }},
        { "term": { "status": "published" }}
      ]
    }
  }
}
```
Text quyết định relevance; tenant và status chỉ giới hạn search domain.

**Lưu ý:**
Đừng tối ưu query DSL theo cảm giác. Mapping sai (`text` vs `keyword`), high-cardinality aggregation hoặc shard layout không phù hợp có thể quan trọng hơn việc chuyển một clause sang filter. Dùng profiler và latency metrics khi query thực sự có vấn đề.

### Tip 5 — AI code review phải xác minh behavior bằng source và test, không bằng lời giải thích của agent

**Mẹo:**
Khi dùng AI coding agent review PR, yêu cầu nó trỏ tới code path cụ thể, invariant bị vi phạm và test tái hiện; sau đó tự kiểm tra diff/source và chạy test liên quan trước khi chấp nhận kết luận.

**Tại sao hữu ích:**
Agent có thể tạo nhận xét nghe hợp lý nhưng dựa trên API không tồn tại, version khác hoặc assumption thiếu context. Evidence-driven review biến AI từ “người phán quyết” thành công cụ tìm hypothesis nhanh, trong khi repository và executable tests vẫn là ground truth.

**Ví dụ:**
Thay vì chấp nhận nhận xét “race condition có thể xảy ra”, yêu cầu chỉ rõ hai execution path cạnh tranh trên state nào và thêm concurrency test thất bại trước fix. Nếu không thể chứng minh bằng source, runtime behavior hoặc specification, issue cần được hạ confidence.

**Lưu ý:**
Generated test cũng có thể sai: mock quá nhiều, assert implementation detail hoặc vô tình encode behavior lỗi hiện tại. Review chất lượng test độc lập với review code fix.

## 🧠 Software Design

### Design 1 — Saga dùng compensation cho workflow phân tán, không giả lập ACID

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction giữa các service/capability. Khi bước sau thất bại, hệ thống thực hiện compensating action cho các bước đã hoàn tất thay vì cố rollback bằng một distributed database transaction duy nhất.

**Vấn đề nó giải quyết:**
Checkout có thể liên quan Order, Payment và Inventory thuộc các boundary khác nhau. Giữ distributed lock/2PC xuyên suốt external services thường không khả thi; nhưng để partial success không kiểm soát cũng làm business state sai.

**Ví dụ thực tế:**
Order được tạo → inventory được reserve → payment authorization thất bại. Workflow phát lệnh release inventory và chuyển order sang `PaymentFailed`. Compensation là business action mới có audit trail, không phải quay ngược thời gian như database rollback.

**Trade-off:**
Saga đưa eventual consistency, intermediate state, retry, duplicate message và compensation failure vào hệ thống. Một số action không thể đảo ngược hoàn toàn, ví dụ email đã gửi hoặc external transfer đã settled. Với workflow nằm trong một database boundary, local ACID transaction thường đơn giản và an toàn hơn.

**Middle → Senior insight:**
Middle developer cần implement state transition, idempotent handler và retry đúng. Senior / Technical developer phải xác định consistency boundary, chọn orchestration hay choreography, thiết kế compensation theo business semantics, quan sát stuck saga và quyết định nơi nào không nên phân tán transaction ngay từ đầu.

### Design 2 — Cache-aside cần định nghĩa consistency window trước khi chọn TTL

**Khái niệm:**
Cache-aside để application đọc cache trước, miss thì đọc source of truth và populate cache. Khi dữ liệu thay đổi, application thường invalidate hoặc update cache theo policy riêng; vì cache và database không nằm trong cùng atomic transaction nên stale window là một phần của design.

**Vấn đề nó giải quyết:**
Read-heavy endpoint có thể tạo database load và latency không cần thiết cho dữ liệu được đọc lặp lại. Cache giảm round trip tới database, nhưng nếu business không định nghĩa mức stale chấp nhận được thì “thêm Redis” chỉ chuyển vấn đề performance thành consistency bug.

**Ví dụ thực tế:**
Product description có thể stale 5 phút, nhưng available inventory sau checkout không thể dùng cùng TTL một cách tùy tiện. Catalog có thể cache-aside với TTL + invalidation event; inventory availability cần source/consistency strategy chặt hơn tùy business promise.

**Trade-off:**
TTL ngắn tăng miss và database load; TTL dài tăng stale data. Invalidation event có thể bị mất/chậm, còn cache stampede xuất hiện khi hot key hết hạn đồng thời. Không cache đôi khi là lựa chọn tốt hơn nếu query đã nhanh và traffic thấp.

**Middle → Senior insight:**
Middle developer cần implement key, serialization, TTL, invalidation và fallback đúng. Senior / Technical developer phải bắt đầu từ consistency requirement, failure behavior khi Redis down, hot-key/stampede risk và telemetry hit ratio/latency; sau đó mới quyết định dữ liệu nào đáng cache và cache ở layer nào.

### Design 3 — Modular Monolith cần boundary thực sự, không chỉ nhiều project trong một solution

**Khái niệm:**
Modular Monolith deploy như một application nhưng chia domain capability thành module có ownership, public contract và data-access boundary rõ. Mục tiêu là giữ deployment/operations đơn giản trong khi hạn chế coupling giữa các phần của hệ thống.

**Vấn đề nó giải quyết:**
Monolith lớn dễ biến thành shared-everything: module nào cũng gọi internal class và join trực tiếp bảng của module khác. Microservices có thể cưỡng ép network boundary nhưng kéo theo distributed failure, deployment và observability cost chưa chắc cần thiết.

**Ví dụ thực tế:**
`Orders` và `Catalog` nằm cùng process nhưng `Orders` không truy cập trực tiếp `CatalogDbContext` hoặc table nội bộ của Catalog. Nó dùng contract/module API rõ ràng; transaction nội bộ vẫn có thể đơn giản hơn microservices trong những use case cần strong consistency.

**Trade-off:**
Boundary trong cùng process chủ yếu được enforce bằng architecture discipline/tooling, nên team có thể phá vỡ dễ hơn network boundary. Tách schema/database quá sớm cũng có thể làm development phức tạp. Ngược lại, shared database không kiểm soát sẽ khiến module chỉ tồn tại trên sơ đồ.

**Middle → Senior insight:**
Middle developer cần tuân thủ dependency direction và public contract giữa module. Senior / Technical developer phải chọn boundary theo business capability/change coupling, quyết định mức data isolation hợp lý, thiết lập architecture tests/ownership rules và chỉ tách module thành service khi scaling, deployment hoặc organizational pressure thực sự biện minh cho distributed-system cost.
