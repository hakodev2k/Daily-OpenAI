# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `PeriodicTimer` thay vì vòng lặp `Task.Delay` thủ công cho background polling

**Mẹo:**
Khi viết background worker cần chạy định kỳ, cân nhắc `PeriodicTimer` để biểu diễn polling loop rõ ràng hơn thay vì tự ghép `while` + `Task.Delay`.

**Tại sao hữu ích:**
Code dễ đọc, hỗ trợ `CancellationToken` tự nhiên và giảm lỗi kiểu quên delay khi exception xảy ra hoặc tạo nhiều timer chồng nhau.

**Ví dụ:**
```csharp
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));

while (await timer.WaitForNextTickAsync(stoppingToken))
{
    await processor.RunOnceAsync(stoppingToken);
}
```

**Lưu ý:**
`PeriodicTimer` không đảm bảo job bắt đầu đúng tuyệt đối mỗi 30 giây nếu lần chạy trước kéo dài. Nếu cần cron semantics hoặc lịch cố định, dùng scheduler phù hợp hơn.

### Tip 2 — Dùng `AsNoTrackingWithIdentityResolution()` khi read-only query có object graph lặp entity

**Mẹo:**
Nếu query read-only có nhiều join/include khiến cùng một entity xuất hiện nhiều lần trong result graph, cân nhắc `AsNoTrackingWithIdentityResolution()` thay vì `AsNoTracking()` thuần túy.

**Tại sao hữu ích:**
Vẫn tránh full change tracking nhưng EF Core sẽ reuse cùng instance cho cùng identity trong result materialization, giúp giảm duplicate object trong memory.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .Include(x => x.Items)
    .ThenInclude(x => x.Product)
    .AsNoTrackingWithIdentityResolution()
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Identity resolution có thêm overhead so với `AsNoTracking()`. Nếu projection DTO đơn giản hoặc không có duplication đáng kể, `AsNoTracking()` thường rẻ hơn.

### Tip 3 — Dùng `git log --first-parent` để đọc lịch sử release branch sạch hơn

**Mẹo:**
Khi branch chính merge nhiều feature branch, dùng `git log --first-parent` để xem chuỗi merge/release chính mà không bị chìm trong toàn bộ commit con.

**Tại sao hữu ích:**
Hữu ích khi điều tra “feature nào vào release nào”, đọc lịch sử deployment hoặc viết changelog từ merge commits.

**Ví dụ:**
```bash
git log --first-parent --oneline main
```

Hoặc xem khoảng giữa hai release tag:

```bash
git log --first-parent v2.4.0..v2.5.0 --oneline
```

**Lưu ý:**
Cách nhìn này ẩn chi tiết commit bên trong feature branch. Khi cần root cause cụ thể vẫn phải mở merge commit hoặc patch đầy đủ.

### Tip 4 — Dùng `SET STATEMENT_TIMEOUT`/command timeout để ngăn query runaway

**Mẹo:**
Với query có rủi ro chạy rất lâu, đặt timeout rõ ràng ở application hoặc database thay vì để request chiếm connection vô hạn.

**Tại sao hữu ích:**
Giúp giới hạn blast radius của query plan xấu, lock wait dài hoặc report bất thường, đồng thời giải phóng connection pool sớm hơn.

**Ví dụ:**
Với Npgsql:

```csharp
await using var command = new NpgsqlCommand(sql, connection)
{
    CommandTimeout = 10
};
```

Hoặc PostgreSQL session-level:

```sql
SET statement_timeout = '10s';
```

**Lưu ý:**
Timeout chỉ cắt operation, không sửa nguyên nhân chậm. Cần phân biệt query execution timeout với lock timeout và đảm bảo cancellation/rollback được xử lý đúng.

### Tip 5 — So sánh AI-generated patch bằng test + diff invariant thay vì chỉ đọc code

**Mẹo:**
Khi AI coding tool tạo patch lớn, review theo ba lớp: diff scope, behavior test, và invariant/business rule phải giữ nguyên.

**Tại sao hữu ích:**
AI có thể viết code nhìn hợp lý nhưng vô tình đổi semantics, bỏ edge case hoặc thêm dependency không cần thiết. Review theo invariant giúp giảm “looks correct” bias.

**Ví dụ:**
Trước khi chấp nhận patch sửa payment flow, kiểm tra:

```text
- Không charge hai lần cùng Idempotency-Key
- Failed payment không chuyển Order sang Paid
- Retry network timeout không duplicate side effect
- Existing integration tests vẫn pass
```

Sau đó mới review implementation chi tiết.

**Lưu ý:**
Đừng giao cho AI tự xác nhận toàn bộ patch của chính nó mà không có test hoặc acceptance criteria độc lập. Verification phải dựa trên nguồn truth ngoài generated code.

## 🧠 Software Design

### Design 1 — Lease-based ownership cho background worker cạnh tranh cùng một công việc

**Khái niệm:**
Lease cho phép một worker sở hữu tạm thời một task/resource trong khoảng thời gian giới hạn. Worker phải renew lease; nếu chết hoặc mất kết nối, lease hết hạn để worker khác tiếp quản.

**Vấn đề nó giải quyết:**
Nếu dùng flag `IsProcessing = true` không có expiry, một worker crash có thể để job bị khóa mãi. Ngược lại, nếu không có ownership, nhiều worker có thể xử lý cùng job đồng thời.

**Ví dụ thực tế:**
Job table có:

```text
Status
LeaseOwner
LeaseExpiresAt
```

Worker claim job bằng atomic update khi `LeaseExpiresAt < now()`, xử lý trong 30 giây và renew định kỳ. Nếu process chết, worker khác có thể claim sau khi lease hết hạn.

**Trade-off:**
Lease tăng khả năng recovery và scale-out, nhưng không tự bảo đảm exactly-once. Worker cũ có thể tiếp tục chạy sau khi lease mất, nên operation quan trọng vẫn cần idempotency, version check hoặc fencing.

**Middle → Senior insight:**
Middle developer nên hiểu lease khác lock vĩnh viễn và phải có expiry/renewal. Senior developer cần thiết kế lease duration, heartbeat, clock assumptions, duplicate execution semantics và recovery khi worker bị pause lâu.

### Design 2 — API Pagination contract phải ổn định trước dữ liệu thay đổi liên tục

**Khái niệm:**
Pagination không chỉ là SQL `LIMIT/OFFSET`; API contract phải định nghĩa ordering, cursor semantics và behavior khi dữ liệu được insert/update giữa các page request.

**Vấn đề nó giải quyết:**
Nếu client lấy page 1 rồi dữ liệu mới được insert, page 2 theo offset có thể lặp hoặc bỏ sót record. Điều này đặc biệt nghiêm trọng với sync/export và processing pipeline.

**Ví dụ thực tế:**
API events có thể dùng cursor gồm `(CreatedAt, Id)` và sort cố định:

```text
ORDER BY CreatedAt ASC, Id ASC
```

Client gửi cursor cuối cùng đã đọc thay vì `page=42`, giúp tiếp tục ổn định hơn khi có record mới phía sau.

**Trade-off:**
Cursor pagination ổn định và scale tốt cho stream lớn nhưng khó hỗ trợ random page jump và total page count. Offset đơn giản hơn cho admin UI nhỏ nhưng kém ổn định với dataset biến động.

**Middle → Senior insight:**
Middle developer nên luôn xác định deterministic ordering. Senior developer phải chọn pagination theo access pattern, consistency requirement, mutable sort fields và nhu cầu snapshot hay near-real-time traversal.

### Design 3 — Chọn synchronous validation hay asynchronous verification theo cost và trust boundary

**Khái niệm:**
Không phải mọi validation đều nên thực hiện đồng bộ trong request path. Rule rẻ và quyết định trực tiếp tính hợp lệ nên sync; verification đắt hoặc phụ thuộc external system có thể cần async workflow.

**Vấn đề nó giải quyết:**
Nếu mỗi request phải gọi nhiều external API chỉ để “validate”, latency và availability của write path bị phụ thuộc vào toàn bộ downstream. Nhưng nếu bỏ validation hoàn toàn, hệ thống có thể chấp nhận dữ liệu không hợp lệ.

**Ví dụ thực tế:**
Khi tạo employee:

- Validate email format, required fields, duplicate internal employee code: sync.
- Verify mailbox tồn tại trên Exchange Online hoặc enrich profile từ Microsoft Graph: có thể chạy async sau khi record được tạo ở trạng thái `PendingVerification`.

**Trade-off:**
Async verification giảm latency/coupling nhưng làm xuất hiện trạng thái trung gian và cần retry, compensation hoặc UX xử lý “pending”. Sync validation đơn giản về semantics nhưng tăng latency và dependency sensitivity.

**Middle → Senior insight:**
Middle developer nên phân biệt pure validation với remote verification. Senior developer phải xác định rule nào là hard invariant trước commit, rule nào có thể eventual, trạng thái trung gian nào cần expose và failure nào phải rollback hay chỉ cảnh báo.
