# Daily Developer Tips & Design — 2026-10-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng projection để giảm chi phí EF Core query

**Mẹo:**
Khi endpoint chỉ cần một phần dữ liệu, project trực tiếp sang DTO bằng `Select` thay vì load toàn bộ entity graph rồi mapping trong memory.

**Tại sao hữu ích:**
EF Core có thể dịch projection thành SQL chỉ lấy các columns cần thiết. Điều này giảm network payload, materialization, allocation và tránh change tracking không cần thiết.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(x.Id, x.CreatedAt, x.Total))
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Đừng chuyển sang `IEnumerable` quá sớm rồi mới `Select`; khi đó phần xử lý có thể chạy phía application. Với expression phức tạp, luôn kiểm tra SQL được generate và execution plan khi query quan trọng.

### Tip 2 — Phân biệt timeout với retry trong third-party API

**Mẹo:**
Đặt timeout theo latency budget trước khi thêm retry. Retry chỉ dành cho transient failure có khả năng thành công ở lần sau.

**Tại sao hữu ích:**
Nếu request ngoài có timeout 30 giây và retry 3 lần, một dependency lỗi có thể giữ request của bạn rất lâu, chiếm connection/thread/resource và làm failure lan rộng. Timeout giới hạn thời gian chờ; retry thay đổi số lần thử — hai cơ chế giải quyết hai vấn đề khác nhau.

**Ví dụ:**
Payment API có p99 bình thường 700 ms. Checkout budget dành 2 giây cho payment, vì vậy timeout 1.5 giây với một retry ngắn có jitter có thể hợp lý hơn ba lần timeout 10 giây.

**Lưu ý:**
Không retry mù `POST` không idempotent. Phải hiểu semantics của API, dùng idempotency key khi được hỗ trợ và tránh retry các lỗi 4xx mang tính business/validation.

### Tip 3 — Chẩn đoán Kubernetes restart từ trạng thái trước đó

**Mẹo:**
Khi Pod restart liên tục, xem `Last State`, exit code và log của container trước đó thay vì chỉ đọc log instance hiện tại.

**Tại sao hữu ích:**
Container mới có thể khởi động bình thường vài giây, che mất bằng chứng của lần crash trước. Exit code và previous logs giúp phân biệt application exception, OOMKilled, probe failure hay termination do deployment.

**Ví dụ:**
```bash
kubectl describe pod <pod>
kubectl logs <pod> --previous
```
Nếu `Last State` là `OOMKilled`, bước tiếp theo là đối chiếu memory usage, request/limit và allocation profile thay vì sửa liveness probe.

**Lưu ý:**
Đừng tăng memory limit ngay lập tức nếu chưa xác định workload tăng hợp lệ hay memory leak. Limit lớn hơn có thể chỉ trì hoãn incident.

### Tip 4 — Contract test cho integration quan trọng hơn mock “đúng ý mình”

**Mẹo:**
Với API contract giữa frontend/backend hoặc service-to-service, bổ sung integration/contract test dựa trên schema và behavior thực thay vì chỉ mock client interface.

**Tại sao hữu ích:**
Mock có thể tiếp tục pass khi provider đổi field, status code hoặc nullability. Contract test phát hiện mismatch ở boundary mà unit test của từng service không nhìn thấy.

**Ví dụ:**
Backend đổi `totalPrice` từ required thành nullable nhưng TypeScript client vẫn giả định `number`. Một OpenAPI-based compatibility check trong CI có thể bắt breaking change trước deployment.

**Lưu ý:**
Contract test không thay thế end-to-end test và không chứng minh dependency production đang khỏe. Tránh snapshot toàn bộ response nếu những field không quan trọng khiến test quá brittle.

### Tip 5 — Đừng đưa secrets vào configuration chỉ vì đã dùng environment variable

**Mẹo:**
Trên Azure, ưu tiên Managed Identity để truy cập Key Vault, Storage, Service Bus hoặc database khi dịch vụ hỗ trợ identity-based authentication.

**Tại sao hữu ích:**
Environment variable vẫn là nơi chứa secret nếu giá trị bên trong là password/key. Managed Identity loại bỏ việc phát hành, phân phối và rotate credential ở application layer, đồng thời cho phép kiểm soát quyền bằng Azure RBAC.

**Ví dụ:**
ASP.NET Core trên App Service dùng `DefaultAzureCredential` để lấy secret từ Key Vault hoặc token cho Azure service; local development có thể dùng developer credential, production dùng Managed Identity mà không nhúng key vào repository/pipeline.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Phải giới hạn role/scope, hiểu credential chain theo môi trường và tránh cấp quyền rộng như subscription-level Contributor chỉ để application đọc một resource.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency thay vì khóa dài

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng dữ liệu nhưng phát hiện conflict tại thời điểm update, thường bằng version/`rowversion`, thay vì giữ database lock trong suốt thời gian user hoặc workflow xử lý.

**Vấn đề nó giải quyết:**
Trong CMS/CRM, hai người có thể sửa cùng record. “Last write wins” âm thầm làm mất thay đổi; pessimistic lock dài lại giảm concurrency và khó áp dụng khi interaction kéo dài qua HTTP requests.

**Ví dụ thực tế:**
EF Core map `rowversion` của `Customer`. Khi hai request update version cũ, request thứ hai nhận `DbUpdateConcurrencyException`; application có thể trả conflict và yêu cầu merge/reload thay vì ghi đè.

**Trade-off:**
Lợi ích là không giữ lock dài và scale tốt khi conflict hiếm. Chi phí là application phải thiết kế conflict handling; nếu contention rất cao, retry liên tục có thể tốn kém hơn chiến lược serialization/locking phù hợp.

**Middle → Senior insight:**
Middle cần implement concurrency token và xử lý conflict đúng. Senior / Technical phải đánh giá tần suất conflict, business semantics, UX merge, transaction boundary và quyết định optimistic hay pessimistic strategy dựa trên contention thực tế.

### Design 2 — Azure Functions vs Worker Service

**Khái niệm:**
Cả Azure Functions và Worker Service đều xử lý background workload, nhưng có execution model và operational boundary khác nhau. Lựa chọn nên dựa trên workload chứ không dựa trên việc “serverless hiện đại hơn”.

**Vấn đề nó giải quyết:**
Một hệ thống cần xử lý message, scheduled task hoặc event mà không làm request API chờ. Vấn đề là chọn runtime/deployment model phù hợp với duration, throughput, scaling và mức kiểm soát cần thiết.

**Ví dụ thực tế:**
Thumbnail generation ngắn, event-driven và traffic biến động có thể phù hợp Azure Functions. Một processor chạy liên tục, giữ pipeline phức tạp, cần kiểm soát concurrency/shutdown và predictable resources có thể phù hợp .NET Worker Service hơn.

**Trade-off:**
Functions giảm infrastructure management và scale theo event nhưng có hosting/runtime constraints, cold-start/cost behavior tùy plan. Worker Service cho kiểm soát lifecycle/resource tốt hơn nhưng bạn phải vận hành compute, scaling và deployment rõ ràng hơn.

**Middle → Senior insight:**
Middle cần hiểu trigger, retry, cancellation và idempotency của workload. Senior / Technical phải so sánh execution duration, traffic shape, cost model, scaling, observability, operational ownership và failure recovery trước khi chọn platform.

### Design 3 — API backward compatibility như một constraint kiến trúc

**Khái niệm:**
API evolution nên coi consumer đang chạy ngoài quyền kiểm soát của provider là một constraint. Thay đổi contract cần được thiết kế để phiên bản cũ và mới có thể cùng tồn tại trong khoảng migration cần thiết.

**Vấn đề nó giải quyết:**
Mobile app, frontend cache hoặc external partner không thể luôn upgrade đồng thời với backend. Một rename/remove field tưởng nhỏ có thể biến deployment backend thành breaking production incident.

**Ví dụ thực tế:**
Thay vì đổi ngay `customerName` thành object `customer`, API có thể bổ sung field mới, giữ field cũ trong compatibility window, đo usage rồi deprecate theo policy. Với semantic break lớn, versioning có thể hợp lý hơn.

**Trade-off:**
Backward compatibility giảm coordinated deployment và rủi ro consumer breakage, nhưng tạo code path cũ, testing matrix, documentation và deprecation cost. Giữ compatibility vô thời hạn cũng trở thành technical debt.

**Middle → Senior insight:**
Middle cần nhận biết breaking changes và giữ contract ổn định. Senior / Technical cần định nghĩa compatibility policy, telemetry về consumer adoption, deprecation timeline và quyết định additive change, versioning hay coordinated migration dựa trên ownership và business constraints.
