# Daily Developer Tips & Design — 2026-10-01

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` có bounded capacity để tạo backpressure

**Mẹo:**
Với producer/consumer chạy trong cùng process, ưu tiên `Channel.CreateBounded<T>` khi tốc độ producer có thể vượt consumer. Capacity hữu hạn buộc hệ thống thể hiện overload thay vì âm thầm tích queue trong memory.

**Tại sao hữu ích:**
Unbounded queue biến chênh lệch throughput thành memory growth. Bounded channel cho phép producer chờ khi buffer đầy, nhờ đó áp lực được truyền ngược về nơi tạo work và dễ kiểm soát hơn.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, ct);
```
Nếu consumer xử lý 100 jobs/s nhưng producer tạo 500 jobs/s liên tục, capacity 500 làm overload xuất hiện sớm thay vì giữ hàng trăm nghìn object.

**Lưu ý:**
In-memory `Channel<T>` không phải durable queue: process restart sẽ mất buffered work. Với business job cần durability, retry hoặc nhiều instances, dùng broker như Azure Service Bus phù hợp hơn.

### Tip 2 — Elasticsearch: sửa mapping bằng reindex, đừng kỳ vọng đổi type tại chỗ

**Mẹo:**
Thiết kế mapping/index template trước khi ingest production data; khi field đã có type không phù hợp, tạo index mới với mapping đúng rồi reindex và chuyển alias.

**Tại sao hữu ích:**
Elasticsearch xây inverted index/doc values dựa trên mapping lúc index document. Một field đã index dưới type cũ không thể đơn giản đổi sang type khác mà giữ cấu trúc index hiện tại.

**Ví dụ:**
```text
products-v3 -> alias products
products-v4 -> mapping mới -> reindex -> kiểm tra -> chuyển alias
```
Nếu `price` từng bị map thành `text`, reindex sang `scaled_float` hoặc numeric type phù hợp trước khi dùng range query/aggregation.

**Lưu ý:**
Reindex có CPU, I/O và storage cost, đồng thời writes phát sinh trong lúc migration cần strategy đồng bộ rõ ràng. Đừng dùng dynamic mapping không kiểm soát cho dữ liệu có schema nghiệp vụ quan trọng.

### Tip 3 — CORS không phải cơ chế authorization

**Mẹo:**
Cấu hình CORS theo origins/methods/headers cần thiết cho browser client, nhưng vẫn bắt buộc authentication và authorization ở API.

**Tại sao hữu ích:**
CORS là browser security policy quyết định JavaScript từ origin khác có được đọc/gửi một số cross-origin requests hay không. Nó không ngăn Postman, backend service hoặc attacker gọi endpoint trực tiếp.

**Ví dụ:**
```csharp
builder.Services.AddCors(o => o.AddPolicy("frontend", p =>
    p.WithOrigins("https://app.example.com")
     .AllowAnyHeader()
     .AllowAnyMethod()));
```
Endpoint `/api/orders/{id}` vẫn phải kiểm tra principal có quyền với order đó.

**Lưu ý:**
Không kết hợp `AllowAnyOrigin()` với credential semantics một cách tùy tiện. Khi dùng cookies cross-origin, cần xem cả `SameSite`, CSRF và exact origin policy; CORS không thay thế các lớp này.

### Tip 4 — CI/CD: build artifact một lần, promote cùng artifact qua các environment

**Mẹo:**
Build và test một immutable artifact, sau đó promote đúng version đó từ staging sang production; inject environment-specific configuration lúc deploy/runtime thay vì rebuild source cho từng environment.

**Tại sao hữu ích:**
Nếu production được rebuild riêng, binary đã test ở staging không còn chắc là binary đang chạy production. Immutable artifact làm rollback, audit và đối chiếu commit → package → deployment rõ hơn.

**Ví dụ:**
```text
commit a13f... -> orders-api:2026.10.1.17
                     |-> staging
                     |-> production
```
Connection string, Key Vault URI và feature configuration đến từ environment, không được bake thành source-specific build.

**Lưu ý:**
“Cùng artifact” không có nghĩa environments giống hệt nhau; configuration, identity và infrastructure vẫn có thể tạo regression. Cần validate configuration và deployment health riêng cho từng environment.

### Tip 5 — Browser DevTools: đọc network waterfall trước khi tối ưu frontend theo cảm giác

**Mẹo:**
Khi trang Vue.js/React.js chậm, dùng Network/Performance panel để phân tách DNS/connect, TTFB, download, request chaining và main-thread work trước khi giảm bundle hoặc tối ưu API.

**Tại sao hữu ích:**
Một trang “render chậm” có thể do backend TTFB, sequential API calls, oversized JavaScript hoặc long task trên main thread. Waterfall biến cảm nhận thành evidence và chỉ ra critical path.

**Ví dụ:**
```text
document       180 ms
config API     220 ms
user API       240 ms   <- chỉ bắt đầu sau config
dashboard API  900 ms   <- chỉ bắt đầu sau user
```
Nếu ba request không phụ thuộc dữ liệu nhau, thay dependency chain bằng parallel fetch có thể giảm latency đáng kể mà không cần micro-optimize component.

**Lưu ý:**
Đừng parallelize mọi request: có thể tăng contention, rate-limit pressure và tải backend. Chỉ phá dependency khi business/data dependency thực sự không tồn tại.

## 🧠 Software Design

### Design 1 — Modular Monolith: boundary mạnh trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia hệ thống thành modules có ownership, dependency direction và data/API boundary rõ ràng. Boundary logic không nhất thiết phải đồng nghĩa network boundary.

**Vấn đề nó giải quyết:**
Một monolith không có module boundaries dễ trở thành shared-database/shared-code spaghetti; nhưng tách Microservices quá sớm lại thêm network failure, deployment coordination, observability và distributed consistency trước khi domain boundary ổn định.

**Ví dụ thực tế:**
Hệ thống CRM có `Customers`, `Sales` và `Billing` modules. Billing không đọc trực tiếp repository nội bộ của Sales; interaction đi qua contract/application boundary. Khi Billing cần scale hoặc release độc lập thực sự, boundary sẵn có làm extraction ít rủi ro hơn.

**Trade-off:**
Modular Monolith giữ deployment/transaction/operations đơn giản hơn Microservices nhưng process và database infrastructure vẫn có thể là shared failure/scaling boundary. Boundary chỉ có giá trị nếu dependency rules được enforce; folder naming đơn thuần không tạo modularity.

**Middle → Senior insight:**
Middle cần giữ module API rõ, tránh bypass boundary và viết tests quanh contracts. Senior / Technical phải đánh giá domain coupling, team ownership, scaling/deployment pressure và operational maturity để quyết định module nào đáng tách; “có thể tách” không đồng nghĩa “nên tách”.

### Design 2 — Inbox Pattern cho idempotent message consumption

**Khái niệm:**
Inbox Pattern lưu dấu message đã xử lý trong cùng consistency boundary với business write, giúp consumer nhận lại cùng message nhưng không lặp business side effect.

**Vấn đề nó giải quyết:**
Broker với at-least-once delivery có thể redeliver khi consumer xử lý thành công nhưng crash trước khi acknowledge. Chỉ dựa vào “broker sẽ gửi một lần” tạo duplicate order, payment hoặc email.

**Ví dụ thực tế:**
Consumer nhận `PaymentCaptured` với `MessageId=abc`. Trong một database transaction, nó kiểm tra/insert Inbox `abc` và cập nhật Order. Delivery thứ hai thấy `abc` đã tồn tại nên không apply state transition lần nữa.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, unique constraint, cleanup và transaction contention. Nếu operation vốn idempotent tự nhiên, một idempotency key trực tiếp trên business entity có thể đơn giản hơn.

**Middle → Senior insight:**
Middle cần hiểu duplicate delivery là normal failure mode và enforce uniqueness atomically. Senior phải chọn deduplication scope/key, retention window, transaction boundary và behavior khi cùng logical event có message ID khác; idempotency là business semantics, không chỉ là middleware checkbox.

### Design 3 — Observability boundary phải đi theo critical business flow

**Khái niệm:**
Thiết kế observability quanh request/message/business operation xuyên components: correlation, structured events, metrics và traces phải giúp trả lời “flow nào hỏng, ở đâu, ảnh hưởng bao nhiêu” thay vì chỉ tạo nhiều log.

**Vấn đề nó giải quyết:**
Trong distributed workflow, từng service có thể “healthy” theo CPU/error riêng nhưng checkout vẫn thất bại do timeout, retry amplification hoặc stuck message giữa các boundaries.

**Ví dụ thực tế:**
Checkout mang `traceId` và `orderId` qua API → database → Service Bus → payment consumer. Dashboard theo dõi success rate và p95 end-to-end; trace cho biết phần latency nằm ở payment dependency, còn structured log giữ business identifier để support truy vết order cụ thể.

**Trade-off:**
Telemetry tốt rút ngắn MTTR nhưng có cost ingestion/storage, cardinality và privacy risk. Ghi mọi payload/span không kiểm soát có thể vừa đắt vừa làm lộ dữ liệu; sampling và retention phải phù hợp signal.

**Middle → Senior insight:**
Middle cần tạo structured logs, correlation và spans đúng boundary. Senior / Technical phải xác định SLI cho critical flow, telemetry budget, cardinality, sampling và ownership của alerts; observability tốt được thiết kế từ failure questions, không phải từ số lượng log lines.
