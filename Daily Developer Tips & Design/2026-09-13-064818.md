# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwait(false)` có chọn lọc trong library code, không áp dụng máy móc cho ASP.NET Core

**Mẹo:**
Trong reusable library không phụ thuộc synchronization context, `ConfigureAwait(false)` có thể thể hiện rõ rằng continuation không cần quay lại context ban đầu. Nhưng trong ASP.NET Core hiện đại thường không có request `SynchronizationContext` kiểu ASP.NET cũ, nên thêm nó vào mọi `await` thường không tạo khác biệt đáng kể.

**Tại sao hữu ích:**
Nhiều codebase mang thói quen từ .NET Framework sang .NET hiện đại và biến `ConfigureAwait(false)` thành nghi thức. Hiểu đúng execution context giúp tránh review noise và tập trung vào vấn đề async thực sự như blocking call, sync-over-async hoặc cancellation propagation.

**Ví dụ:**
```csharp
public async Task<string> ReadPayloadAsync(
    Stream stream,
    CancellationToken ct)
{
    using var reader = new StreamReader(stream);
    return await reader.ReadToEndAsync(ct).ConfigureAwait(false);
}
```

Trong library này không có yêu cầu tiếp tục trên UI/request context. Ngược lại, trong ASP.NET Core application code:
```csharp
var order = await repository.GetAsync(id, ct);
return Results.Ok(order);
```
thường đã đủ rõ ràng.

**Lưu ý:**
`ConfigureAwait(false)` không sửa deadlock do code gọi `.Result`/`.Wait()` một cách tùy tiện. Với UI framework như WPF/WinForms, continuation có thể thực sự cần quay lại UI context. Quyết định theo execution model của code, không theo rule tuyệt đối.

### Tip 2 — Dùng HTTP `ETag` + `If-Match` để bảo vệ update API khỏi lost update giữa nhiều client

**Mẹo:**
Với REST API nơi nhiều client có thể sửa cùng resource, expose một version qua `ETag` và yêu cầu client gửi `If-Match` khi update. Server chỉ chấp nhận thay đổi nếu version client đang giữ vẫn là version hiện tại.

**Tại sao hữu ích:**
Nếu hai user cùng mở một document, user A save trước rồi user B save từ snapshot cũ, update của B có thể âm thầm ghi đè A. Conditional request đưa optimistic concurrency ra HTTP contract thay vì chỉ xử lý kín trong persistence layer.

**Ví dụ:**
```http
GET /api/documents/42
ETag: "v17"
```

Client update:
```http
PUT /api/documents/42
If-Match: "v17"
Content-Type: application/json
```

Nếu resource đã thành `v18`, server trả:
```http
412 Precondition Failed
```

Backend có thể map `rowversion`, revision number hoặc hash ổn định sang ETag.

**Lưu ý:**
Đừng dùng timestamp độ phân giải thấp làm version nếu có thể xảy ra nhiều update gần nhau. `ETag` cũng cần semantics nhất quán qua cache/proxy. Nếu business cho phép merge field độc lập, reject toàn bộ update có thể quá thô và cần conflict-resolution strategy tốt hơn.

### Tip 3 — Với SQL Server, tránh transaction bao quanh network call

**Mẹo:**
Không giữ database transaction mở trong lúc gọi HTTP API, gửi email, upload blob hoặc chờ external dependency nếu không thật sự cần atomicity ở mức đó. Hoàn thành database work càng nhanh càng tốt rồi xử lý integration bằng pattern phù hợp.

**Tại sao hữu ích:**
Transaction mở lâu giữ lock/version lâu hơn, tăng blocking, deadlock probability và connection-pool pressure. External call 2–5 giây có thể biến một update SQL vài millisecond thành transaction dài nhiều giây.

**Ví dụ:**
```text
Rủi ro:
BEGIN TRANSACTION
  UPDATE Orders ...
  gọi Payment API 3 giây
  INSERT Audit ...
COMMIT

Tốt hơn trong nhiều workflow:
BEGIN TRANSACTION
  UPDATE Orders ...
  ghi integration intent/outbox
COMMIT

sau đó xử lý external call ngoài transaction DB
```

Nếu integration phải đồng bộ với business state, thiết kế state machine, outbox hoặc compensation thay vì kéo dài local transaction qua network boundary.

**Lưu ý:**
Không phải cứ tách external call ra ngoài transaction là xong; bạn phải xác định failure semantics khi database commit nhưng integration chưa thành công. Mục tiêu là transaction boundary ngắn và rõ, không phải đánh đổi consistency một cách vô thức.

### Tip 4 — Trong Vue, dùng `shallowRef` cho object lớn từ library ngoài khi không cần deep reactivity

**Mẹo:**
Nếu state giữ object lớn hoặc instance từ chart/map/editor library và Vue không cần track thay đổi sâu bên trong, cân nhắc `shallowRef` thay vì `ref`/`reactive` deep-reactive mặc định.

**Tại sao hữu ích:**
Deep reactivity có thể tạo proxy cho object graph lớn và thêm overhead không cần thiết, đặc biệt với third-party instance vốn tự quản lý state. `shallowRef` chỉ track việc thay reference ở cấp trên cùng.

**Ví dụ:**
```ts
import { shallowRef, onMounted, onBeforeUnmount } from 'vue'

const editor = shallowRef<Editor | null>(null)

onMounted(() => {
  editor.value = new Editor(/* ... */)
})

onBeforeUnmount(() => {
  editor.value?.destroy()
  editor.value = null
})
```

Nếu cần báo Vue rằng nội dung bên trong đã đổi nhưng reference không đổi, có thể cân nhắc `triggerRef` trong trường hợp phù hợp.

**Lưu ý:**
`shallowRef` không phù hợp nếu template/computed phải phản ứng với mutation sâu bên trong object. Đừng dùng nó chỉ để “tối ưu” khi chưa có vấn đề; hãy ưu tiên khi object rõ ràng thuộc external imperative API hoặc có graph lớn.

### Tip 5 — Dùng `git rerere` để tái sử dụng cách resolve conflict lặp lại trên branch dài

**Mẹo:**
Khi thường xuyên rebase/cherry-pick một branch dài và gặp lại cùng conflict, bật Git `rerere` để Git ghi nhớ cặp conflict + cách bạn đã resolve, rồi tự áp lại resolution khi conflict tương tự xuất hiện.

**Tại sao hữu ích:**
Long-lived migration branch hoặc backport series có thể bắt developer resolve cùng một conflict nhiều lần qua các rebase. `rerere` giảm công việc lặp lại nhưng vẫn để bạn review diff trước khi commit.

**Ví dụ:**
```bash
git config --global rerere.enabled true

# Lần đầu: resolve conflict thủ công rồi commit/rebase continue.
# Lần sau Git nhận ra conflict tương tự và reuse resolution.

git rerere status
git rerere diff
```

Nên kiểm tra lại working tree và chạy test như bình thường sau khi Git tự áp resolution.

**Lưu ý:**
Resolution cũ có thể không còn đúng nếu surrounding logic đã thay đổi. `rerere` là công cụ tái sử dụng patch, không phải bằng chứng semantic correctness. Với conflict nhạy cảm như migration/schema/security, review lại từng lần vẫn cần thiết.

## 🧠 Software Design

### Design 1 — Single-Writer Principle để giảm conflict trên dữ liệu có nhiều producer

**Khái niệm:**
Single-Writer Principle quy định một loại state hoặc aggregate có một authority chịu trách nhiệm mutation. Các component khác gửi command/request thay đổi thay vì cùng ghi trực tiếp vào datastore đó.

**Vấn đề nó giải quyết:**
Khi API, batch job, integration worker và admin tool đều update trực tiếp cùng bảng theo rule riêng, invariant dễ bị phân mảnh. Schema giống nhau không có nghĩa mọi component nên có quyền write như nhau.

**Ví dụ thực tế:**
```text
Order state owner: Order Service

Storefront ------> PlaceOrder command ┐
Admin Portal ----> CancelOrder command ├-> Order Service -> Orders DB
ERP Adapter -----> MarkExported command┘

Không phải:
Storefront -> Orders DB
Admin      -> Orders DB
ERP worker -> Orders DB
```

Read replica/search projection vẫn có thể được consumer khác đọc hoặc build độc lập; principle chủ yếu nói về mutation authority.

**Trade-off:**
Single writer làm ownership và invariant rõ hơn nhưng có thể thêm hop, queue/API dependency và bottleneck nếu writer không scale đúng. Với script vận hành rất nhỏ trong cùng bounded context, ép mọi thứ qua một service network riêng có thể là ceremony không cần thiết.

**Middle → Senior insight:**
Middle developer cần biết “có quyền truy cập DB” không đồng nghĩa “nên update table này”. Senior / Technical developer phải xác định ownership theo invariant và business capability, thiết kế command path, emergency/admin write policy và scale writer mà không biến central owner thành distributed monolith.

### Design 2 — Brownout / Graceful Degradation để giữ core journey khi hệ thống thiếu capacity

**Khái niệm:**
Brownout chủ động tắt hoặc giảm các feature không critical khi hệ thống quá tải hoặc dependency suy giảm, nhằm bảo toàn capacity cho core business path thay vì để mọi feature cùng fail.

**Vấn đề nó giải quyết:**
Trang checkout có thể gọi recommendation, loyalty balance, personalization, fraud enrichment và analytics. Nếu một dependency chậm hoặc toàn hệ thống gần saturation, tiếp tục cố phục vụ mọi enhancement có thể làm checkout chính cũng timeout.

**Ví dụ thực tế:**
```text
Normal mode:
Checkout
  + pricing
  + inventory
  + payment
  + recommendations
  + loyalty preview

Degraded mode khi latency/error budget vượt ngưỡng:
Checkout
  + pricing
  + inventory
  + payment
  - recommendations
  - loyalty preview tạm ẩn
```

Trigger nên dựa trên observable signal như saturation, dependency error rate hoặc latency, và behavior phải được test trước incident.

**Trade-off:**
Graceful degradation tăng availability của core journey nhưng làm UX không đồng nhất và thêm state vận hành. Nếu feature bị tắt có compliance/security impact thì không được degrade theo kiểu “bỏ qua kiểm tra”. Chỉ optional capability mới phù hợp.

**Middle → Senior insight:**
Middle developer cần phân biệt critical và optional dependency trong request path. Senior / Technical developer phải xác định degradation hierarchy, activation signal, recovery hysteresis, user-visible behavior và SLO để hệ thống giảm chất lượng có kiểm soát thay vì sập toàn bộ.

### Design 3 — Cell-Based Architecture để giới hạn blast radius theo tenant/traffic shard

**Khái niệm:**
Cell-Based Architecture chia hệ thống thành nhiều cell gần như độc lập, mỗi cell chứa đủ application/storage/dependency cần thiết để phục vụ một subset user hoặc tenant. Routing layer đưa traffic vào cell tương ứng.

**Vấn đề nó giải quyết:**
Trong một deployment/database cluster chung, memory leak, bad deployment hoặc hot tenant có thể ảnh hưởng toàn bộ khách hàng. Chia cell giới hạn failure domain: sự cố ở cell A không nhất thiết làm cell B/C mất dịch vụ.

**Ví dụ thực tế:**
```text
Global routing / tenant directory
        │
        ├── Cell A: API + workers + DB shard
        ├── Cell B: API + workers + DB shard
        └── Cell C: API + workers + DB shard

Tenant 001-500  -> Cell A
Tenant 501-1000 -> Cell B
```

Cell mới cũng có thể được thêm khi capacity tăng thay vì scale một shared cluster vô hạn.

**Trade-off:**
Cell architecture giảm blast radius và hỗ trợ horizontal scale nhưng tăng deployment count, capacity fragmentation, routing metadata, cross-cell operation và operational tooling. Với hệ thống nhỏ, một topology shared đơn giản thường hiệu quả hơn nhiều.

**Middle → Senior insight:**
Middle developer cần hiểu availability không chỉ đến từ retry/replica mà còn từ failure-domain design. Senior / Solution-level developer phải chọn cell boundary, tenant placement, rebalancing strategy, cross-cell dependency và deployment policy sao cho cell thực sự độc lập; nếu mọi cell vẫn phụ thuộc một central database bắt buộc, blast radius chưa được giảm đáng kể.
