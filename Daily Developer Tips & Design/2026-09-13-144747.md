# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` khi buffer lớn được tạo lặp lại trong hot path

**Mẹo:**
Trong các path xử lý serialization, compression, file/chunk hoặc protocol parsing có buffer lớn được cấp phát liên tục, cân nhắc `ArrayPool<T>.Shared` để tái sử dụng array thay vì `new byte[...]` cho mỗi operation.

**Tại sao hữu ích:**
Array lớn có thể tạo áp lực allocation và GC, đặc biệt khi kích thước vượt ngưỡng Large Object Heap. Pooling giảm số allocation và lượng memory phải được GC xử lý, hữu ích khi throughput cao và profiling đã chỉ ra allocation là bottleneck.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await ProcessAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Array được rent có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Không đọc ngoài vùng hợp lệ; với dữ liệu nhạy cảm, cân nhắc `clearArray: true`. Đừng pool object nhỏ hoặc path ít chạy nếu profiling chưa chứng minh allocation đáng kể — complexity và lifetime bug có thể đắt hơn lợi ích.

### Tip 2 — Dùng partial index trong PostgreSQL khi workload chỉ truy vấn một tập con ổn định

**Mẹo:**
Nếu phần lớn query chỉ quan tâm các row có trạng thái cụ thể như `IsDeleted = false` hoặc `Status = 'Pending'`, cân nhắc partial index thay vì index toàn bảng.

**Tại sao hữu ích:**
Index nhỏ hơn thường giảm storage, write amplification và số page phải đọc. Nếu predicate của query khớp điều kiện index, PostgreSQL có thể dùng index hiệu quả hơn so với việc duy trì index chứa cả dữ liệu hiếm khi được truy vấn.

**Ví dụ:**
```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at DESC)
WHERE status = 'Pending';

SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at DESC
LIMIT 100;
```

**Lưu ý:**
Partial index chỉ hữu ích khi predicate query phù hợp với predicate index và phân bố dữ liệu đủ có ý nghĩa. Nếu status thay đổi liên tục hoặc gần như mọi row đều nằm trong tập được index, lợi ích có thể nhỏ. Luôn kiểm tra `EXPLAIN (ANALYZE, BUFFERS)` trước và sau khi thay đổi.

### Tip 3 — Với Azure Service Bus, theo dõi `LockLost` như tín hiệu processing vượt quá thiết kế

**Mẹo:**
Nếu message handler mất lock thường xuyên, đừng chỉ tăng lock duration. Đo thời gian xử lý, dependency latency, concurrency và khả năng auto-renew để xác định vì sao processing vượt quá lock window.

**Tại sao hữu ích:**
Service Bus dùng peek-lock để cho phép redelivery khi consumer không hoàn tất message. Khi lock hết hạn trước khi `Complete`, message có thể được xử lý lại. Đây thường là tín hiệu rằng handler đang làm quá nhiều việc, downstream chậm hoặc concurrency không phù hợp.

**Ví dụ:**
```text
Message lock: 60s
p95 handler duration: 18s
p99 handler duration: 95s
LockLost spike sau khi Payment API chậm
```

Giải pháp có thể là bật/tune auto lock renewal, giảm work trong handler, tách bước dài sang workflow khác hoặc điều chỉnh concurrency dựa trên dependency capacity.

**Lưu ý:**
Tăng lock duration không tạo exactly-once processing. Consumer vẫn phải idempotent vì duplicate delivery có thể xảy ra do network failure, process crash hoặc completion acknowledgement bị mất.

### Tip 4 — Dùng architecture test để chặn dependency sai ngay trong CI

**Mẹo:**
Nếu solution có boundary rõ giữa Domain, Application, Infrastructure hoặc các module, dùng architecture test để enforce dependency rule thay vì chỉ ghi convention trong README.

**Tại sao hữu ích:**
Boundary thường bị phá dần bởi những shortcut nhỏ như Domain reference EF Core, module A gọi internal type của module B hoặc Application phụ thuộc web framework. Một test tự động biến architectural intent thành regression check có thể fail ngay trong pull request.

**Ví dụ:**
```csharp
var result = Types
    .InAssembly(typeof(DomainMarker).Assembly)
    .ShouldNot()
    .HaveDependencyOn("Microsoft.EntityFrameworkCore")
    .GetResult();

Assert.True(result.IsSuccessful);
```

Có thể áp dụng tương tự cho namespace/module dependency hoặc các forbidden reference quan trọng.

**Lưu ý:**
Đừng biến architecture test thành danh sách rule khổng lồ khó bảo trì. Chỉ enforce những boundary có giá trị thật và ổn định. Rule quá chi tiết có thể khóa refactoring hợp lý và khiến team tìm cách lách test thay vì cải thiện design.

### Tip 5 — Với Optimizely CMS, invalidation cache phải bám theo content dependency thay vì TTL tùy ý

**Mẹo:**
Khi cache output hoặc dữ liệu được tạo từ CMS content, ưu tiên invalidation dựa trên thay đổi content/dependency nếu platform hỗ trợ thay vì đặt TTL dài và hy vọng dữ liệu tự hết hạn.

**Tại sao hữu ích:**
CMS có editor publish nội dung bất kỳ lúc nào. Cache TTL 30 phút có thể làm production tiếp tục hiển thị content cũ dù publish đã thành công. Dependency-based invalidation giúp freshness phản ánh lifecycle của content thay vì clock.

**Ví dụ:**
```text
Homepage cache phụ thuộc:
- HomePage content
- Navigation root
- Promotion block IDs

Editor publish Promotion block
-> dependency invalidated
-> homepage cache được rebuild ở request tiếp theo
```

Cách này hữu ích hơn việc xóa toàn bộ site cache sau mỗi publish.

**Lưu ý:**
Dependency graph quá rộng có thể tạo cache churn lớn; dependency thiếu lại gây stale content. Với distributed deployment, phải đảm bảo invalidation propagate tới mọi instance hoặc dùng shared/distributed cache phù hợp.

## 🧠 Software Design

### Design 1 — Cache-aside cần xác định rõ ai sở hữu invalidation

**Khái niệm:**
Cache-aside cho phép application đọc cache trước, miss thì đọc source of truth rồi populate cache. Điểm khó không phải `GET/SET`, mà là xác định component nào chịu trách nhiệm invalidation khi dữ liệu thay đổi.

**Vấn đề nó giải quyết:**
Nếu nhiều service hoặc admin tool cùng có thể thay đổi dữ liệu nhưng chỉ một service biết xóa cache, stale data sẽ xuất hiện ngẫu nhiên. Nếu mọi nơi đều tự invalidate theo cách riêng, logic consistency bị phân tán và khó audit.

**Ví dụ thực tế:**
```text
Product DB là source of truth
Product API cập nhật product
  -> commit DB
  -> publish ProductChanged
Cache consumer
  -> invalidate product:{id}
  -> invalidate affected category/search fragments
```

Một hệ thống đơn giản hơn có thể invalidate trực tiếp sau commit nếu chỉ một application sở hữu mọi write.

**Trade-off:**
Cache-aside đơn giản và hiệu quả cho read-heavy workload, nhưng chấp nhận window stale và tăng complexity invalidation. Event-based invalidation scale tốt hơn khi nhiều consumer tồn tại nhưng thêm messaging, retry và eventual consistency. TTL vẫn nên tồn tại như safety net, không phải strategy duy nhất.

**Middle → Senior insight:**
Middle developer cần implement key, TTL và invalidation đúng với write path. Senior / Technical developer phải xác định ownership, source of truth, consistency requirement, blast radius của invalidation và behavior khi event/cache infrastructure bị lỗi.

### Design 2 — Contract testing bảo vệ integration tốt hơn mock nội bộ khi hai service tiến hóa độc lập

**Khái niệm:**
Contract testing kiểm tra producer và consumer cùng tuân thủ một interface/HTTP/message contract đã thỏa thuận. Mục tiêu là phát hiện breaking change giữa các component deploy độc lập mà không cần chạy toàn bộ end-to-end environment.

**Vấn đề nó giải quyết:**
Consumer test có thể mock response cũ mãi mãi trong khi producer đã rename field, đổi status code hoặc thay semantic. Unit test cả hai bên vẫn xanh nhưng integration production fail sau deployment.

**Ví dụ thực tế:**
```text
Consumer kỳ vọng:
GET /customers/{id}
200
{
  "id": "...",
  "displayName": "..."
}

Producer CI phải verify contract này trước khi release.
```

Với message broker, contract có thể kiểm tra schema, required field và compatibility của event version.

**Trade-off:**
Contract tests nhanh và xác định boundary rõ hơn full E2E, nhưng không chứng minh network, auth, routing hoặc toàn workflow production hoạt động. Quá nhiều consumer-specific contract cũng có thể làm producer khó tiến hóa nếu không có version/deprecation policy.

**Middle → Senior insight:**
Middle developer cần hiểu contract nào là externally observable behavior và tránh test implementation detail. Senior / Technical developer phải chọn ownership contract, compatibility policy, CI gating và cách cân bằng consumer safety với khả năng evolution của producer.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo state cần được quản trị

**Khái niệm:**
Feature Flag cho phép deploy code trước nhưng chỉ bật behavior mới cho một nhóm user, environment hoặc tỷ lệ traffic nhất định. Nó tách việc đưa binary lên production khỏi quyết định expose functionality.

**Vấn đề nó giải quyết:**
Release lớn có thể khó rollback chỉ vì một phần nhỏ có vấn đề. Flag cho phép canary rollout, disable nhanh hoặc thử nghiệm với internal users mà không cần redeploy toàn application.

**Ví dụ thực tế:**
```text
NewCheckoutV2
- dev: 100%
- staging: 100%
- production internal users: 100%
- production customers: 5% -> 25% -> 100%

Metric theo dõi:
- error rate
- conversion
- p95 latency
```

Nếu error tăng, flag có thể đưa traffic về flow cũ trong khi team điều tra.

**Trade-off:**
Feature Flag tăng release safety nhưng tạo nhiều execution path, test matrix và technical debt. Flag tồn tại quá lâu trở thành configuration branch khó hiểu; flag ảnh hưởng schema/data migration còn cần thiết kế kỹ vì không phải mọi thay đổi có thể rollback chỉ bằng boolean.

**Middle → Senior insight:**
Middle developer cần viết code/test cho cả trạng thái on/off và không để flag logic rải khắp domain. Senior / Technical developer phải thiết kế rollout strategy, observability, owner, expiry date và phân biệt release flag ngắn hạn với operational/configuration flag dài hạn.
