# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Giảm allocation lớn bằng `ArrayPool<T>` khi buffer chỉ sống trong một operation

**Mẹo:**
Khi xử lý payload lớn hoặc transform dữ liệu theo buffer tạm thời, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì liên tục tạo `new byte[...]`, đặc biệt khi operation chạy với throughput cao.

**Tại sao hữu ích:**
Các array lớn tạo áp lực lên GC; object từ khoảng 85 KB trở lên thường đi vào Large Object Heap (LOH). Nếu mỗi request đều cấp phát buffer lớn rồi bỏ, application có thể tăng GC pause và memory pressure dù business logic không thực sự cần giữ buffer lâu dài.

**Ví dụ:**
```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(128 * 1024);

try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, buffer.Length), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Chỉ xử lý phần dữ liệu thực sự đã đọc, không giả định `Rent(128 * 1024)` trả đúng array có chiều dài 128 KB.

**Lưu ý:**
Buffer thuê từ pool có thể chứa dữ liệu của operation trước. Nếu dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc tự xóa vùng đã dùng. Luôn `Return` trong `finally`; đừng giữ reference đến buffer sau khi trả về pool.

### Tip 2 — Khi SQL Server query “lúc nhanh lúc chậm”, kiểm tra execution plan và parameter sensitivity trước khi thêm index

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có latency chênh lệch rất lớn theo giá trị parameter, kiểm tra actual execution plan, estimated/actual row count và plan reuse trước khi kết luận database thiếu index.

**Tại sao hữu ích:**
Một execution plan tốt cho parameter chọn rất ít row có thể không phù hợp với parameter trả hàng triệu row. Nếu chỉ nhìn query text rồi thêm index, bạn có thể tăng write cost mà không sửa đúng nguyên nhân của plan instability hoặc parameter sensitivity.

**Ví dụ:**
```sql
SELECT Id, CustomerId, Status, CreatedAt
FROM Orders
WHERE CustomerId = @customerId
  AND Status = @status;
```

Khi điều tra, so sánh ít nhất:
```text
- Actual Rows vs Estimated Rows
- Index Seek / Scan
- Key Lookup count
- memory grant
- plan được reuse hay compile lại
- distribution của CustomerId + Status
```

**Lưu ý:**
`OPTION (RECOMPILE)` có thể giúp một số query rất nhạy với parameter nhưng đổi lại CPU compile và mất lợi ích plan reuse. Không dùng hint như một “fix mặc định”; lựa chọn phải dựa trên workload, data skew và evidence từ Query Store/execution plan.

### Tip 3 — Với MongoDB compound index, thứ tự field phải theo query pattern chứ không theo model class

**Mẹo:**
Thiết kế compound index dựa trên filter, sort và selectivity thực tế. Với query có equality + sort + range, thường bắt đầu phân tích theo nguyên tắc ESR: Equality → Sort → Range, rồi xác nhận bằng `explain()`.

**Tại sao hữu ích:**
Index `{ tenantId: 1, createdAt: -1, status: 1 }` và `{ status: 1, tenantId: 1, createdAt: -1 }` không tương đương. Thứ tự field quyết định prefix nào có thể được tận dụng và liệu MongoDB có phải sort in-memory hay scan nhiều key không cần thiết.

**Ví dụ:**
```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })

db.orders.find({
  tenantId: "t-42",
  status: "Pending"
}).sort({ createdAt: -1 }).limit(50)
```

Sau đó kiểm tra:
```javascript
db.orders.find({
  tenantId: "t-42",
  status: "Pending"
}).sort({ createdAt: -1 }).limit(50).explain("executionStats")
```

Quan sát `keysExamined`, `docsExamined`, số document trả về và stage của execution plan.

**Lưu ý:**
ESR là heuristic, không phải luật tuyệt đối. Data distribution, range selectivity, sort direction và query variation có thể làm index khác tốt hơn. Mỗi index cũng tăng storage và write amplification, nên tránh tạo index riêng cho mọi biến thể query.

### Tip 4 — Dùng `git worktree` để xử lý hotfix mà không phá working tree đang làm dở

**Mẹo:**
Khi đang có một feature branch với nhiều thay đổi chưa commit nhưng cần xử lý hotfix gấp, dùng `git worktree` để checkout branch khác vào thư mục riêng thay vì stash/unstash liên tục.

**Tại sao hữu ích:**
`git worktree` cho phép nhiều working directory dùng chung một repository object database. Bạn có thể giữ nguyên IDE, build output và thay đổi hiện tại của feature branch trong khi mở một working tree sạch cho hotfix hoặc code review.

**Ví dụ:**
```bash
git fetch origin
git worktree add ../app-hotfix -b hotfix/payment-timeout origin/main

cd ../app-hotfix
# sửa, test, commit, push hotfix
```

Sau khi hoàn tất:
```bash
git worktree remove ../app-hotfix
git branch -d hotfix/payment-timeout
```

**Lưu ý:**
Một branch thông thường không thể được checkout đồng thời ở hai worktree. Đừng xóa thư mục worktree trực tiếp nếu Git vẫn đang quản lý nó; dùng `git worktree remove` và `git worktree prune` khi cần dọn metadata cũ.

### Tip 5 — Với `HttpClientFactory`, phân biệt timeout của request với lifetime của connection

**Mẹo:**
Khi outbound HTTP gặp DNS change, stale connection hoặc latency bất thường, đừng chỉ chỉnh `HttpClient.Timeout`. Kiểm tra cả connection pooling trong `SocketsHttpHandler`, đặc biệt `PooledConnectionLifetime`, và đặt policy dựa trên đặc tính của downstream service.

**Tại sao hữu ích:**
`IHttpClientFactory` giải quyết việc quản lý handler tốt hơn so với tạo `new HttpClient()` cho từng request, nhưng TCP connection vẫn được pool và reuse. Một connection có thể sống lâu hơn thay đổi DNS hoặc load-balancer topology nếu lifetime không phù hợp với môi trường.

**Ví dụ:**
```csharp
builder.Services
    .AddHttpClient("catalog", client =>
    {
        client.BaseAddress = new Uri("https://catalog.internal");
        client.Timeout = TimeSpan.FromSeconds(3);
    })
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)
    });
```

`Timeout` giới hạn thời gian operation; `PooledConnectionLifetime` giới hạn thời gian một connection được giữ để tái sử dụng.

**Lưu ý:**
Không chọn lifetime tùy ý quá thấp vì sẽ tăng connection churn, TLS handshake và nguy cơ port pressure. Nếu dùng retry, timeout và circuit breaker cùng nhau, phải tính tổng latency budget để tránh một request bị nhân thời gian chờ qua nhiều tầng policy.

## 🧠 Software Design

### Design 1 — Transactional Outbox khi database update và publish message phải “đi cùng nhau”

**Khái niệm:**
Transactional Outbox lưu business change và một outbox record trong cùng local database transaction. Một background publisher sau đó đọc outbox và gửi event/message ra broker, rồi đánh dấu đã xử lý.

**Vấn đề nó giải quyết:**
Nếu code commit `Order` vào SQL trước rồi publish `OrderCreated` lên broker, process có thể crash giữa hai bước: database đã đổi nhưng message không bao giờ xuất hiện. Làm ngược lại cũng có thể publish message cho transaction cuối cùng bị rollback.

**Ví dụ thực tế:**
```text
SQL transaction:
1. INSERT Orders(...)
2. INSERT OutboxMessages(Id, Type, Payload, CreatedAt)
3. COMMIT

Background publisher:
4. đọc OutboxMessages chưa gửi
5. publish lên Service Bus/Kafka
6. đánh dấu PublishedAt
```

Consumer vẫn nên idempotent vì publisher có thể gửi lại message nếu crash sau bước publish nhưng trước khi đánh dấu hoàn tất.

**Trade-off:**
Outbox tránh distributed transaction giữa database và broker nhưng thêm table, publisher, cleanup, observability và eventual consistency. Nó phù hợp khi message delivery là một phần quan trọng của workflow; với integration không cần durability cao, kiến trúc đơn giản hơn có thể đủ.

**Middle → Senior insight:**
Middle developer cần hiểu vì sao `SaveChangesAsync()` rồi `PublishAsync()` không tạo atomicity xuyên hai hệ thống. Senior / Technical developer phải thiết kế delivery semantics, retry, deduplication, ordering, cleanup và operational monitoring thay vì chỉ thêm một bảng `Outbox` rồi coi vấn đề đã xong.

### Design 2 — Strangler Fig Pattern để thay legacy system theo từng capability thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig Pattern di chuyển từng route, business capability hoặc integration từ hệ thống cũ sang hệ thống mới trong khi cả hai cùng tồn tại. Một gateway/router hoặc façade quyết định request nào vẫn đi legacy và request nào đã được chuyển sang implementation mới.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó chứng minh parity và chỉ tạo giá trị khi gần hoàn tất. Với hệ thống production lớn, team còn phải sửa bug và thêm feature trong legacy trong suốt thời gian rewrite, khiến khoảng cách giữa hai codebase tiếp tục tăng.

**Ví dụ thực tế:**
```text
/api/customers/*  -> Legacy ASP.NET app
/api/orders/*     -> New ASP.NET Core service
/api/catalog/*    -> New module

Sau mỗi migration:
- route traffic sang implementation mới
- đo error/latency/business metrics
- giữ rollback path
- xóa capability cũ khi đã ổn định
```

Migration boundary có thể là module trong Modular Monolith chứ không nhất thiết phải là Microservice.

**Trade-off:**
Pattern này giảm migration risk nhưng tạm thời tăng complexity: hai implementation, routing, data synchronization và compatibility layer cùng tồn tại. Nếu boundary chọn sai hoặc không có kế hoạch retire legacy, “temporary architecture” có thể tồn tại nhiều năm.

**Middle → Senior insight:**
Middle developer cần giữ contract tương thích và test behavior giữa legacy/new path. Senior / Solution-oriented engineer phải chọn migration slice theo business capability, data ownership và rollbackability; mục tiêu là giảm rủi ro theo từng bước chứ không dùng rewrite như cơ hội mặc định để đổi toàn bộ công nghệ.

### Design 3 — Chống cache stampede bằng single-flight hoặc refresh có kiểm soát

**Khái niệm:**
Cache stampede xảy ra khi một key phổ biến hết hạn và nhiều request đồng thời đều miss cache, sau đó cùng đánh vào database hoặc downstream service để rebuild cùng một dữ liệu. Single-flight/coalescing cho phép một request làm công việc refresh trong khi các request khác chờ hoặc dùng dữ liệu cũ theo policy.

**Vấn đề nó giải quyết:**
Một homepage configuration được đọc 20.000 lần/phút có TTL 5 phút. Khi key hết hạn, hàng trăm instance/request có thể đồng thời query database. Cache vốn dùng để giảm tải lại tạo một traffic spike đúng lúc entry biến mất.

**Ví dụ thực tế:**
```text
Request A: cache miss -> lấy refresh lock -> query DB -> set cache
Request B: cache miss -> thấy refresh đang chạy -> chờ ngắn
Request C: cache miss -> phục vụ stale value nếu policy cho phép
```

Có thể kết hợp TTL có jitter để nhiều key không hết hạn cùng một thời điểm.

**Trade-off:**
Lock/coalescing giảm duplicate work nhưng thêm coordination và failure mode nếu owner của refresh bị treo. Phục vụ stale data tăng availability nhưng giảm freshness. Distributed lock chính xác hơn giữa nhiều instance nhưng phức tạp hơn local single-flight; chọn giải pháp theo mức độ nóng của key và consistency requirement.

**Middle → Senior insight:**
Middle developer cần nhận ra cache miss không phải lúc nào cũng là một request độc lập. Senior / Technical developer phải thiết kế TTL, stale window, refresh ownership, failure fallback và downstream capacity dựa trên traffic shape thực tế thay vì chỉ “thêm Redis” rồi giả định cache luôn bảo vệ database.
