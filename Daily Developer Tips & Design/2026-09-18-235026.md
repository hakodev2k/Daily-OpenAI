# Daily Developer Tips & Design — 2026-09-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Span<T>` khi profiling chứng minh allocation trên hot path

**Mẹo:**
Với parsing hoặc slicing dữ liệu chạy rất thường xuyên, cân nhắc `Span<T>`/`ReadOnlySpan<T>` để thao tác trên vùng nhớ hiện có thay vì tạo substring hoặc array trung gian.

**Tại sao hữu ích:**
Mỗi allocation nhỏ có vẻ rẻ, nhưng trên hot path hàng trăm nghìn lần/giây chúng làm tăng allocation rate và GC pressure. `Span<T>` cho phép tạo view trên buffer mà không cần copy dữ liệu.

**Ví dụ:**
```csharp
ReadOnlySpan<char> input = "ORD-2026-00125";
var year = input.Slice(4, 4);
var number = input.Slice(9);
```
Nếu profiler cho thấy parser tạo lượng lớn temporary strings, cách này có thể giảm allocation đáng kể.

**Lưu ý:**
Đừng đưa `Span<T>` vào business code thông thường chỉ để “nhanh hơn”. Đây là `ref struct` với lifetime constraints; complexity tăng lên chỉ đáng giá khi benchmark/profiling xác nhận allocation thực sự là bottleneck.

### Tip 2 — Phân biệt blocking với deadlock trước khi sửa SQL

**Mẹo:**
Khi SQL Server request treo lâu, xác định đó là blocking chain hay deadlock. Blocking có thể kéo dài mà không có exception; deadlock thường khiến database chọn một transaction làm victim để phá chu kỳ.

**Tại sao hữu ích:**
Hai hiện tượng có symptom gần giống ở application nhưng cách điều tra khác nhau. Blocking cần tìm blocker, transaction duration và lock đang giữ; deadlock cần phân tích deadlock graph và thứ tự resource acquisition.

**Ví dụ:**
Một API update Order mở transaction, gọi external API rồi mới commit. Request khác update cùng Order phải chờ. Evidence cần đi từ wait type/session → blocker → transaction đang mở → code path giữ transaction quá lâu.

**Lưu ý:**
Không dùng `NOLOCK` như thuốc chữa blocking mặc định. Dirty/non-repeatable reads có thể phá correctness. Trước tiên giảm transaction scope, tối ưu query/index và xem isolation strategy phù hợp workload.

### Tip 3 — Cosmos DB partition key phải xuất phát từ access pattern và cardinality

**Mẹo:**
Khi chọn partition key cho Cosmos DB, đánh giá query routing, write distribution và cardinality; đừng chọn một field chỉ vì nó xuất hiện trong mọi document.

**Tại sao hữu ích:**
Partition key quyết định cách dữ liệu và request được phân phối. Một key có ít giá trị hoặc một tenant cực lớn có thể tạo hot partition, làm throughput bị giới hạn dù tổng RU provisioned còn nhiều.

**Ví dụ:**
Với multi-tenant event store, `TenantId` có thể tốt nếu tenant tương đối cân bằng và query thường theo tenant. Nếu một tenant tạo phần lớn traffic, cần xem lại data model/partition strategy thay vì chỉ tăng RU toàn container.

**Lưu ý:**
Không chọn key chỉ để tối ưu một query hiện tại. Thay đổi partition strategy sau khi hệ thống lớn thường tốn migration đáng kể; cần xem cả growth pattern và giới hạn logical partition.

### Tip 4 — Playwright test nên chờ trạng thái nghiệp vụ, không chờ thời gian cố định

**Mẹo:**
Trong UI automation, chờ locator, response hoặc trạng thái UI cụ thể thay vì `WaitForTimeout` cố định.

**Tại sao hữu ích:**
Sleep 2 giây vừa làm suite chậm vừa flaky: môi trường nhanh thì lãng phí, môi trường chậm thì vẫn fail. Condition-based waiting đồng bộ test với behavior thực tế của application.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved successfully')).toBeVisible();
```
Test xác nhận outcome mà user nhìn thấy thay vì đoán backend sẽ hoàn thành sau bao lâu.

**Lưu ý:**
Không tăng global timeout để che flaky test. Nếu trạng thái không deterministic vì test data, async job hoặc shared environment, cần sửa isolation/synchronization ở đúng nguyên nhân.

### Tip 5 — CMS cache invalidation phải gắn với content lifecycle

**Mẹo:**
Trong Optimizely CMS hoặc CMS tương tự, thiết kế cache key/invalidation dựa trên content identity, language, published version và dependency thay vì chỉ đặt TTL dài cho rendered fragment.

**Tại sao hữu ích:**
CMS có editorial workflow: publish, unpublish, language variant và scheduled content changes. Cache không hiểu lifecycle dễ phục vụ nội dung cũ dù origin đã cập nhật đúng.

**Ví dụ:**
Một product landing page cache fragment theo `ContentId + Language`. Khi editor publish block phụ thuộc, invalidation phải làm mất cache của page/fragment liên quan; chỉ chờ TTL 30 phút có thể vi phạm kỳ vọng publishing.

**Lưu ý:**
Invalidation quá rộng làm cache hit ratio sụt và tạo burst load. Cần đo dependency granularity, CDN/application cache layers và yêu cầu freshness trước khi chọn purge toàn site.

## 🧠 Software Design

### Design 1 — API backward compatibility bằng additive evolution

**Khái niệm:**
API evolution an toàn ưu tiên thay đổi additive: thêm optional field/endpoint hoặc mở rộng contract theo cách consumer cũ vẫn hoạt động. Versioning là công cụ khi breaking change thực sự cần thiết, không phải lý do để tùy ý phá contract.

**Vấn đề nó giải quyết:**
Mobile app, CMS frontend và third-party consumer không deploy cùng nhịp với backend. Một rename hoặc thay đổi semantics tưởng nhỏ có thể làm client production hỏng ngay sau backend release.

**Ví dụ thực tế:**
Thay vì đổi `customerName` thành `displayName` ngay, backend có thể thêm field mới, migrate consumers, theo dõi usage rồi deprecate field cũ theo policy. Nếu semantics thay đổi căn bản, API version mới có thể rõ ràng hơn.

**Trade-off:**
Additive evolution giảm coordination và deployment risk nhưng contract tích lũy legacy fields. Versioning tạo boundary rõ cho breaking change nhưng tăng số contract cần test, document và vận hành song song.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking changes và giữ serialization/validation tương thích. Senior / Technical developer phải thiết kế deprecation window, telemetry về consumer usage, migration strategy và quyết định khi nào compatibility debt lớn hơn chi phí version mới.

### Design 2 — Optimistic vs pessimistic concurrency theo contention thực tế

**Khái niệm:**
Optimistic concurrency giả định conflict hiếm và phát hiện xung đột khi ghi; pessimistic concurrency khóa resource sớm để ngăn concurrent modification. Lựa chọn phụ thuộc contention, correctness và chi phí giữ lock.

**Vấn đề nó giải quyết:**
Hai user hoặc worker có thể đọc cùng state rồi cùng cập nhật, dẫn tới lost update hoặc vi phạm business invariant nếu application không có concurrency strategy.

**Ví dụ thực tế:**
Employee profile editing thường conflict thấp: `rowversion`/concurrency token và trả conflict để reload/merge có thể phù hợp. Một operation phân bổ inventory cực kỳ cạnh tranh có thể cần atomic database statement hoặc locking strategy chặt hơn tùy invariant.

**Trade-off:**
Optimistic concurrency cho throughput tốt khi conflict hiếm nhưng buộc xử lý retry/merge. Pessimistic locking giảm conflict window nhưng tăng blocking, deadlock risk và giảm concurrency nếu transaction dài.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency token, transaction và xử lý conflict đúng. Senior / Technical developer phải đo contention, xác định invariant và cân nhắc atomic SQL, optimistic retry, serialization hoặc queueing thay vì chọn locking theo thói quen.

### Design 3 — Feature flags tách deployment khỏi release

**Khái niệm:**
Feature flag cho phép deploy code trước nhưng chỉ enable behavior cho nhóm user/environment mong muốn. Nó tách thời điểm artifact vào production khỏi thời điểm tính năng được phát hành.

**Vấn đề nó giải quyết:**
Một feature lớn cần rollout dần, kiểm chứng telemetry hoặc phối hợp nhiều component nhưng team không muốn giữ long-lived branch hay thực hiện deployment khẩn chỉ để bật/tắt behavior.

**Ví dụ thực tế:**
Checkout flow mới được deploy ở trạng thái off, sau đó enable 5% traffic, theo dõi error rate/latency rồi tăng dần. Khi metric xấu, flag có thể tắt behavior mà không rollback toàn artifact chứa các thay đổi khác.

**Trade-off:**
Feature flags giảm release risk và hỗ trợ progressive delivery nhưng tạo nhiều execution paths, test matrix và configuration debt. Flag tồn tại lâu có thể biến code thành mạng lưới điều kiện khó hiểu.

**Middle → Senior insight:**
Middle developer cần test cả on/off path và không dùng flag để bỏ qua authorization/security invariant. Senior / Technical developer phải thiết kế ownership, expiry/removal, rollout metrics, failure behavior và quyết định khi nào cần flag thay vì deployment strategy đơn giản hơn.
