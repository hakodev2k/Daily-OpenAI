# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian mà không cần `Task.Delay`

**Mẹo:**
Với code .NET có logic expiry, timeout nghiệp vụ hoặc scheduled behavior, inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi.

**Tại sao hữu ích:**
Đồng hồ hệ thống là một dependency. Nếu business logic đọc thời gian trực tiếp, test thường phải chờ thật hoặc phụ thuộc timing, làm test chậm và flaky. `TimeProvider` giúp production dùng clock thật còn test kiểm soát thời gian một cách deterministic.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        expiresAt <= timeProvider.GetUtcNow();
}
```

Trong test, dùng fake time provider phù hợp để advance clock thay vì `await Task.Delay(...)`.

**Lưu ý:**
Không cần abstract mọi lần đọc thời gian nếu code không có behavior cần kiểm thử quanh clock. Quan trọng là giữ một nguồn thời gian nhất quán tại boundary nghiệp vụ, đặc biệt tránh trộn local time với UTC.

### Tip 2 — Dùng `AsSplitQuery` khi nhiều collection `Include` tạo Cartesian explosion

**Mẹo:**
Nếu EF Core query `Include` nhiều collection và result set phình bất thường, kiểm tra SQL và số row truyền qua network; cân nhắc projection hoặc `AsSplitQuery()` thay vì chỉ nhìn thời gian `ToListAsync()`.

**Tại sao hữu ích:**
Join nhiều collection một-nhiều có thể nhân số row. Một aggregate chỉ vài chục entity logic nhưng SQL result có thể hàng nghìn row do tổ hợp giữa các collection, làm tăng network, materialization và memory cost.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == orderId, ct);
```

Trước khi đổi, so sánh generated SQL, row count, round trips và latency thực tế. Projection DTO thường còn tốt hơn nếu endpoint chỉ cần một subset dữ liệu.

**Lưu ý:**
Split query đổi một query lớn thành nhiều query, nên tăng round trips và cần cân nhắc consistency nếu dữ liệu thay đổi giữa các query. Không bật mặc định chỉ vì có `Include`.

### Tip 3 — Với Azure Service Bus, handler chạy lâu phải tính đến message lock

**Mẹo:**
Nếu consumer xử lý message lâu hơn lock duration, theo dõi lock renewal và thời gian xử lý thay vì mặc định rằng một handler chỉ chạy một lần.

**Tại sao hữu ích:**
Trong peek-lock mode, broker chỉ giữ quyền xử lý message trong một khoảng thời gian. Nếu lock hết hạn trước khi complete, message có thể được giao lại cho consumer khác dù handler cũ vẫn đang chạy, dẫn tới duplicate side effect.

**Ví dụ:**
```text
Lock duration: 60s
Image processing: 95s

T=60s  lock hết hạn
T=65s  message được redeliver
T=95s  consumer đầu tiên vẫn hoàn tất công việc
```

Giải pháp có thể là auto lock renewal, chia nhỏ work, chuyển tác vụ dài sang worker/job model khác và vẫn giữ consumer idempotent.

**Lưu ý:**
Lock renewal không biến Service Bus thành exactly-once delivery. Process vẫn có thể crash sau side effect nhưng trước `Complete`, nên idempotency vẫn là yêu cầu cốt lõi.

### Tip 4 — Cache nội dung CMS theo dependency, không chỉ theo TTL

**Mẹo:**
Trong CMS như Optimizely, nếu một page được compose từ nhiều block/content item, thiết kế invalidation dựa trên content dependency thay vì chỉ cache HTML vài phút rồi chờ TTL hết.

**Tại sao hữu ích:**
TTL đơn thuần tạo hai lựa chọn xấu: TTL dài thì editor publish nhưng user tiếp tục thấy nội dung cũ; TTL ngắn thì cache hit ratio thấp và origin/rendering chịu tải cao. Dependency-aware invalidation cho phép giữ cache lâu nhưng xóa đúng entry khi content liên quan thay đổi.

**Ví dụ:**
```text
Home page cache phụ thuộc:
- HomePage content
- HeroBlock
- FeaturedArticlesBlock

Editor publish HeroBlock
-> invalidate Home page render cache
-> không purge toàn site
```

**Lưu ý:**
Dependency graph quá chi tiết cũng có maintenance cost. Với content có fan-out rất lớn, invalidation hàng loạt có thể tạo traffic spike; cần cân nhắc stale-while-revalidate hoặc regeneration strategy.

### Tip 5 — Log authorization failure theo decision context nhưng không log token

**Mẹo:**
Khi API trả `403`, log structured fields như policy, resource type, actor/tenant identifier an toàn và correlation ID để điều tra, nhưng không ghi raw JWT, cookie hoặc authorization header.

**Tại sao hữu ích:**
`403` production thường khó debug nếu log chỉ có status code. Decision context giúp phân biệt thiếu role, sai tenant boundary hay resource ownership. Nhưng credential trong log biến observability system thành nơi lưu secret ngoài ý muốn.

**Ví dụ:**
```csharp
logger.LogWarning(
    "Authorization denied Policy={Policy} UserId={UserId} Resource={Resource} TraceId={TraceId}",
    policyName,
    userId,
    resourceType,
    Activity.Current?.TraceId);
```

**Lưu ý:**
Ngay cả user ID, tenant ID hoặc resource ID cũng có thể là dữ liệu nhạy cảm theo domain. Xác định logging policy, retention và access control trước khi thêm high-cardinality identity fields.

## 🧠 Software Design

### Design 1 — Strangler Fig để hiện đại hóa legacy system theo từng capability

**Khái niệm:**
Strangler Fig migration đặt hệ thống mới cạnh hệ thống cũ và chuyển từng route/capability sang implementation mới theo thời gian, thay vì rewrite toàn bộ rồi cut over một lần.

**Vấn đề nó giải quyết:**
Legacy .NET/CMS application lớn thường chứa business rule chưa được tài liệu hóa. Big-bang rewrite kéo dài feedback loop và đến ngày cutover mới phát hiện các behavior mà hệ thống mới bỏ sót.

**Ví dụ thực tế:**
```text
/publications/*  -> legacy app
/search/*        -> service mới
/profile/*       -> legacy app

Sau khi search ổn định:
/publications/*  -> module mới tiếp theo
```

Proxy/router giữ entry point ổn định trong khi capability được migrate dần và so sánh telemetry giữa cũ/mới.

**Trade-off:**
Cách này giảm migration risk, cho phép rollback từng capability và tạo giá trị sớm, nhưng trong một thời gian phải vận hành hai hệ thống, đồng bộ identity/data và quản lý routing phức tạp hơn.

**Middle → Senior insight:**
Middle developer cần giữ contract và test regression khi chuyển từng endpoint. Senior / Technical developer phải chọn seam phù hợp, data ownership, migration order, observability và tiêu chí retire legacy; không nên strangler theo technical layer nếu boundary business không rõ.

### Design 2 — Service Bus Queue vs Topic theo ownership của công việc

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer xử lý; Topic với subscriptions phù hợp khi một event cần được nhiều consumer độc lập quan sát và xử lý theo mục đích riêng.

**Vấn đề nó giải quyết:**
Dùng một queue cho broadcast khiến consumers cạnh tranh và chỉ một bên nhận message. Ngược lại, dùng topic cho command có một owner có thể tạo ambiguity về service nào chịu trách nhiệm thực hiện công việc.

**Ví dụ thực tế:**
```text
GenerateInvoice command
-> Queue: Billing worker xử lý

OrderPlaced event
-> Topic:
   Subscription A: Email
   Subscription B: Analytics
   Subscription C: Fulfillment
```

Mỗi subscription có retry, DLQ và backlog riêng nên failure của Analytics không cần chặn Fulfillment.

**Trade-off:**
Queue đơn giản hóa ownership và competing consumers nhưng không broadcast tự nhiên. Topic tăng decoupling và fan-out nhưng thêm subscription management, duplicate processing, schema evolution và operational cost cho từng consumer.

**Middle → Senior insight:**
Middle developer cần phân biệt command với event và hiểu delivery semantics. Senior / Technical developer phải quyết định topology dựa trên ownership, fan-out, ordering, retry isolation, replay và future consumers — không dựa trên việc topic “linh hoạt hơn”.

### Design 3 — SQL vs NoSQL bắt đầu từ invariant và access pattern, không từ scale slogan

**Khái niệm:**
Chọn relational hay document/partitioned database dựa trên transaction/invariant cần bảo vệ, query pattern, data shape và cách hệ thống cần phân phối dữ liệu. “NoSQL để scale” hoặc “SQL để consistency” đều là mô tả quá đơn giản.

**Vấn đề nó giải quyết:**
Một domain có nhiều quan hệ, constraint và transaction chéo entity có thể trở nên khó quản lý nếu ép vào document model. Ngược lại, workload truy cập chủ yếu theo một aggregate/partition key với schema thay đổi linh hoạt có thể không cần join-heavy relational model.

**Ví dụ thực tế:**
```text
Finance ledger:
- strong transactional invariants
- constraints và audit quan trọng
-> relational database thường là baseline hợp lý

Device telemetry:
- write volume lớn
- đọc chủ yếu theo deviceId + time range
- partition boundary rõ
-> document/partitioned store có thể phù hợp hơn
```

**Trade-off:**
Relational database cho constraint, join và transaction semantics mạnh nhưng horizontal distribution có thể cần thiết kế thêm. NoSQL có thể tối ưu distribution và aggregate-shaped access nhưng đẩy nhiều consistency, denormalization và query trade-off vào application/data model.

**Middle → Senior insight:**
Middle developer cần model dữ liệu theo query và invariant thực tế thay vì map object máy móc. Senior / Technical developer phải đánh giá transaction boundary, partition key, growth distribution, operational skill, migration cost và failure recovery trước khi chọn datastore; đôi khi giải pháp tốt nhất là dùng hai datastore cho hai workload khác nhau.
