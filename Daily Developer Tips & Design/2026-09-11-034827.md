# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Truyền cancellation vào `IAsyncEnumerable` khi stream dữ liệu dài

**Mẹo:**
Khi API hoặc worker xử lý dữ liệu theo `IAsyncEnumerable<T>`, đảm bảo cancellation đi tới quá trình enumerate, không chỉ tới method tạo sequence.

**Tại sao hữu ích:**
Async stream có thể tiếp tục đọc database, network hoặc file sau khi client đã disconnect hoặc host đang shutdown. Nếu token không được quan sát trong vòng enumerate, tài nguyên vẫn bị tiêu tốn dù kết quả không còn ai sử dụng.

**Ví dụ:**
```csharp
await foreach (var item in service
    .StreamOrdersAsync(ct)
    .WithCancellation(ct))
{
    await response.WriteAsJsonAsync(item, ct);
}
```

Với iterator tự viết, có thể dùng `[EnumeratorCancellation] CancellationToken` để token từ consumer được truyền đúng vào iterator.

**Lưu ý:**
Cancellation là cooperative. Nếu bên trong iterator gọi API hoặc thư viện không nhận `CancellationToken`, thêm token ở `await foreach` không tự động dừng operation đó.

### Tip 2 — Dùng ETag để tránh ghi đè resource khi client sửa dữ liệu cũ

**Mẹo:**
Với REST API cho phép nhiều client sửa cùng resource, cân nhắc trả `ETag` khi đọc và yêu cầu `If-Match` khi update để phát hiện stale write ở HTTP boundary.

**Tại sao hữu ích:**
Nếu hai client cùng đọc version 10 rồi lần lượt `PUT`, request sau có thể âm thầm ghi đè thay đổi trước. Conditional request biến conflict thành tín hiệu rõ ràng thay vì lost update.

**Ví dụ:**
```text
GET /profiles/42
ETag: "v10"

PUT /profiles/42
If-Match: "v10"

Nếu resource đã là v11
-> 412 Precondition Failed
```

Backend có thể ánh xạ ETag tới `rowversion`, version column hoặc concurrency token phù hợp.

**Lưu ý:**
ETag không thay thế transaction hoặc domain invariant. Cũng cần phân biệt strong/weak validator; weak ETag thường không phù hợp cho concurrency control của write.

### Tip 3 — Với PostgreSQL pagination lớn, ưu tiên keyset thay vì `OFFSET` sâu

**Mẹo:**
Khi user duyệt tuần tự qua tập dữ liệu lớn, dùng keyset pagination dựa trên sort key ổn định thay vì tăng `OFFSET` đến hàng trăm nghìn row.

**Tại sao hữu ích:**
`OFFSET` sâu vẫn buộc database tìm và bỏ qua nhiều row trước khi trả trang hiện tại. Keyset cho phép index seek tiếp từ vị trí cuối cùng của trang trước, thường giữ latency ổn định hơn khi dataset tăng.

**Ví dụ:**
```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@last_created_at, @last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Composite index tương ứng với thứ tự filter/sort giúp query tận dụng access path hiệu quả.

**Lưu ý:**
Keyset khó hỗ trợ nhảy trực tiếp tới “trang 500” và cần sort key deterministic. Nếu UI thật sự cần random page access, `OFFSET` vẫn có thể là trade-off chấp nhận được.

### Tip 4 — Trong Playwright, dùng web-first assertion thay vì `WaitForTimeout`

**Mẹo:**
Khi test UI bất đồng bộ, chờ điều kiện người dùng thực sự quan sát được bằng locator/assertion thay vì sleep cố định.

**Tại sao hữu ích:**
`WaitForTimeout(2000)` vừa làm test chậm khi UI phản hồi nhanh, vừa flaky khi CI chậm hơn 2 giây. Web-first assertion retry tới khi condition đạt hoặc timeout có ý nghĩa.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click()
await expect(page.getByText('Saved successfully')).toBeVisible()
```

Test giờ đồng bộ theo behavior thay vì theo một con số timing giả định.

**Lưu ý:**
Không tăng global timeout để che test flaky. Nếu assertion vẫn timeout, kiểm tra race condition, selector không ổn định, network dependency hoặc product behavior trước.

### Tip 5 — Dùng `Cache-Control` và `Age` để debug CDN stale content trước khi purge toàn bộ

**Mẹo:**
Khi production website qua CDN như Akamai phục vụ nội dung cũ, kiểm tra response headers và cache key trước khi chọn purge toàn site.

**Tại sao hữu ích:**
Stale content có thể đến từ browser cache, CDN edge, origin output cache hoặc header cấu hình sai. Purge toàn bộ có thể tạm che symptom nhưng làm giảm hit ratio và tạo load spike lên origin.

**Ví dụ:**
```text
Cache-Control: public, max-age=60, s-maxage=600
Age: 487
Vary: Accept-Encoding
```

Từ evidence này, xác định layer nào đang giữ object, TTL còn bao lâu và request variants có dùng cùng cache key hay không.

**Lưu ý:**
Đừng cache response chứa dữ liệu cá nhân chỉ vì endpoint là `GET`. Cacheability phải xét authorization, cookies, `private/no-store`, `Vary` và policy của CDN.

## 🧠 Software Design

### Design 1 — Modular Monolith vs Microservices theo organizational boundary và failure isolation

**Khái niệm:**
Modular Monolith giữ deployment unit chung nhưng chia code/data ownership theo module rõ ràng; Microservices đưa một số boundary đó thành process/deployment độc lập. Khác biệt quan trọng nằm ở runtime và operational boundary, không chỉ cấu trúc folder.

**Vấn đề nó giải quyết:**
Một monolith thiếu boundary dễ biến thành codebase coupling cao. Nhưng tách service quá sớm lại chuyển coupling trong code thành network calls, distributed transactions và nhiều pipeline phải vận hành.

**Ví dụ thực tế:**
```text
Modules:
- Catalog
- Orders
- Billing

Giai đoạn đầu:
-> cùng application deployment
-> interface/module boundary rõ

Khi Billing thật sự cần scale, compliance hoặc release cadence độc lập:
-> cân nhắc extract Billing thành service
```

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, transaction và local debugging nhưng các module vẫn chia sẻ blast radius của process/release. Microservices tăng isolation và autonomy nhưng thêm latency, messaging, observability, deployment và data-consistency cost.

**Middle → Senior insight:**
Middle developer cần giữ module boundary và tránh cross-module access tùy tiện. Senior / Technical developer phải chứng minh nhu cầu runtime isolation, team autonomy, scaling hoặc compliance trước khi trả distributed-systems tax của Microservices.

### Design 2 — Webhook reliability cần idempotency và durable retry ở cả hai phía

**Khái niệm:**
Webhook là asynchronous HTTP delivery: sender phải chấp nhận network failure và retry; receiver phải chấp nhận cùng event được gửi nhiều lần và xử lý idempotently.

**Vấn đề nó giải quyết:**
HTTP `200` có thể bị mất trên đường về sender sau khi receiver đã commit side effect. Sender thấy timeout rồi retry, nên “gửi đúng một lần” không thể được giả định chỉ dựa trên request/response.

**Ví dụ thực tế:**
```text
Event: payment.completed
EventId: evt_123

Receiver:
1. verify signature
2. kiểm tra evt_123 đã xử lý chưa
3. commit business change + dedupe record
4. trả 2xx

Sender:
- retry timeout/5xx với backoff
- giữ event trong durable delivery store
```

**Trade-off:**
Thiết kế này tăng reliability nhưng cần event identity, signature verification, retention, retry policy và operational tooling cho failed deliveries. Với integration ít quan trọng, mức durability quá cao có thể không đáng chi phí.

**Middle → Senior insight:**
Middle developer cần hiểu timeout không đồng nghĩa operation chưa xảy ra. Senior / Technical developer phải thiết kế delivery guarantee, dedupe window, replay, security, backoff và cách tránh retry storm theo business criticality.

### Design 3 — Observability boundary phải bám theo user journey, không chỉ theo service

**Khái niệm:**
Observability hiệu quả liên kết telemetry theo một business flow xuyên API, queue, worker, database và external dependency thay vì mỗi component chỉ có dashboard riêng biệt.

**Vấn đề nó giải quyết:**
Khi checkout chậm, từng service có thể vẫn báo CPU và error rate “bình thường”, nhưng tổng journey vượt SLO do nhiều latency nhỏ cộng lại hoặc một asynchronous stage backlog tăng.

**Ví dụ thực tế:**
```text
Checkout trace:
API request        120 ms
Inventory call     180 ms
Payment call       900 ms
Outbox dispatch     40 ms
Fulfillment queue  12 s wait
```

Trace/correlation, metrics và structured events cho phép đi từ symptom người dùng tới dependency hoặc queue stage gây bottleneck.

**Trade-off:**
Journey-oriented telemetry cải thiện root-cause analysis và SLO reasoning nhưng tăng yêu cầu context propagation, naming convention, cardinality control và data cost. Instrument mọi chi tiết không chọn lọc có thể tạo nhiều noise hơn signal.

**Middle → Senior insight:**
Middle developer cần propagate trace context và ghi telemetry có cấu trúc đúng boundary. Senior / Technical developer phải chọn SLI, sampling, correlation strategy và telemetry budget dựa trên failure modes quan trọng của business flow, không phải số lượng dashboard.
