# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng EF Core compiled query khi cùng một query hot-path chạy với tần suất rất cao

**Mẹo:**
Nếu cùng một LINQ query được thực thi lặp lại với shape cố định trên hot path, cân nhắc `EF.CompileQuery` hoặc `EF.CompileAsyncQuery` sau khi profiling cho thấy chi phí query compilation thực sự đáng kể.

**Tại sao hữu ích:**
EF Core cache query plan nội bộ, nhưng mỗi lần thực thi vẫn phải xử lý một phần expression pipeline để xác định cache entry tương ứng. Compiled query bỏ bớt overhead đó bằng cách chuẩn bị delegate trước. Lợi ích rõ nhất khi query đơn giản, chạy cực nhiều lần và database latency thấp đến mức overhead phía application trở nên đáng kể.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<Order>>
    GetOrdersByCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, Guid customerId) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.CustomerId == customerId)
              .OrderByDescending(x => x.CreatedAt));
```

Trước khi áp dụng, benchmark cả query bình thường và compiled query trên workload thực tế.

**Lưu ý:**
Đây không phải cách sửa query SQL chậm. Nếu bottleneck nằm ở scan, join, index hoặc network/database latency, compiled query gần như không giúp gì. Đừng đổi toàn bộ repository sang compiled query chỉ vì đây là một optimization có sẵn.

### Tip 2 — Trên Redis production, tránh `KEYS` cho namespace lớn; dùng `SCAN` hoặc index riêng

**Mẹo:**
Khi cần tìm nhiều key theo pattern trong production, tránh dùng `KEYS pattern` trên dataset lớn. Nếu việc duyệt key là thật sự cần thiết, dùng `SCAN` theo từng batch hoặc duy trì một data structure/index phục vụ lookup chủ động.

**Tại sao hữu ích:**
`KEYS` phải duyệt toàn bộ keyspace trong một lần và có thể block Redis event loop đủ lâu để làm latency của toàn hệ thống tăng vọt. `SCAN` chia công việc thành nhiều bước nên giảm thời gian block mỗi lượt, dù tổng lượng công việc vẫn tồn tại.

**Ví dụ:**
```text
Không nên:
KEYS session:tenant-42:*

Tốt hơn cho maintenance/debug:
SCAN 0 MATCH session:tenant-42:* COUNT 500
```

Nếu application thường xuyên cần "liệt kê tất cả session của tenant", hãy cân nhắc thêm `Set` chứa session IDs thay vì phụ thuộc vào key-pattern scan.

**Lưu ý:**
`SCAN` không cung cấp snapshot mạnh; key có thể xuất hiện hoặc biến mất trong lúc iteration. `COUNT` chỉ là hint, không phải số lượng chính xác. Đừng xây business-critical query logic dựa trên full keyspace scanning nếu có thể thiết kế access pattern rõ ràng hơn.

### Tip 3 — Với ASP.NET Core Minimal API, đừng để contract HTTP bị ẩn trong anonymous lambda lớn

**Mẹo:**
Khi Minimal API endpoint bắt đầu có validation, authorization, mapping và nhiều dependency, tách handler thành method/class có tên rõ ràng và khai báo response contract bằng typed results hoặc metadata thay vì tiếp tục nhồi logic vào lambda dài.

**Tại sao hữu ích:**
Minimal API giúp giảm ceremony, nhưng lambda lớn dễ trộn transport concern với application logic. Contract trả về cũng trở nên khó đọc và khó test nếu endpoint có nhiều nhánh `200`, `400`, `404`, `409`. Typed results giúp compiler và OpenAPI hiểu rõ hơn tập kết quả hợp lệ.

**Ví dụ:**
```csharp
static async Task<Results<Ok<OrderDto>, NotFound, Conflict>>
    GetOrder(Guid id, AppDbContext db, CancellationToken ct)
{
    var order = await db.Orders.FindAsync([id], ct);
    if (order is null) return TypedResults.NotFound();

    return TypedResults.Ok(Map(order));
}

app.MapGet("/orders/{id:guid}", GetOrder);
```

**Lưu ý:**
Không cần biến mọi endpoint thành một architecture nhiều layer. Endpoint CRUD đơn giản vẫn có thể giữ rất gọn. Mục tiêu là giữ contract và behavior dễ hiểu, không phải tái tạo MVC ceremony bên trong Minimal API.

### Tip 4 — Dùng Playwright route interception để test frontend khi dependency API lỗi hoặc chậm

**Mẹo:**
Trong E2E test, dùng network interception để mô phỏng timeout, `500`, payload malformed hoặc response chậm từ API thay vì chỉ test happy path với backend luôn khỏe.

**Tại sao hữu ích:**
Frontend production thường hỏng ở state chuyển tiếp: loading kéo dài, retry loop, stale data, button bị enable sai hoặc error message không xuất hiện. Những behavior này khó tái tạo ổn định nếu phụ thuộc vào việc backend thật sự gặp sự cố đúng lúc test chạy.

**Ví dụ:**
```ts
await page.route('**/api/orders/42', async route => {
  await new Promise(r => setTimeout(r, 1500));
  await route.fulfill({ status: 500, body: '{"error":"boom"}' });
});

await page.goto('/orders/42');
await expect(page.getByText('Không thể tải đơn hàng')).toBeVisible();
```

**Lưu ý:**
Interception không thay thế integration test giữa frontend và backend contract thật. Nếu mock payload sai schema, test vẫn xanh nhưng production có thể lỗi. Giữ một lớp contract/integration test riêng để xác nhận hai phía thực sự tương thích.

### Tip 5 — Với Key Vault, dùng Managed Identity và cache secret hợp lý thay vì đọc secret mỗi request

**Mẹo:**
Ứng dụng Azure nên ưu tiên Managed Identity để authenticate tới Azure Key Vault và chỉ load secret/configuration ở lifecycle phù hợp, thay vì gọi Key Vault cho mỗi HTTP request.

**Tại sao hữu ích:**
Managed Identity loại bỏ việc lưu client secret dài hạn trong config. Đồng thời, Key Vault là remote dependency có latency, throttling và failure mode riêng; đọc secret mỗi request biến control-plane/security dependency thành bottleneck của request path.

**Ví dụ:**
```text
App startup / configuration refresh:
Managed Identity
   -> Key Vault
   -> load secret/config cần thiết
   -> cache trong process theo policy

HTTP request:
   -> dùng giá trị đã resolve
```

Với secret cần rotation, thiết kế refresh interval hoặc provider hỗ trợ reload thay vì restart thủ công vô thời hạn.

**Lưu ý:**
Cache quá lâu có thể làm rotation không có hiệu lực kịp thời. Cache quá ngắn lại tăng request tới Key Vault. Phải cân bằng TTL, rotation SLA và behavior khi Key Vault tạm unavailable; đồng thời giới hạn quyền Managed Identity theo least privilege.

## 🧠 Software Design

### Design 1 — Dùng trực tiếp `DbContext` hay thêm Repository phụ thuộc vào boundary thật sự cần bảo vệ

**Khái niệm:**
EF Core `DbContext` đã cung cấp nhiều capability giống Unit of Work và Repository. Việc bọc nó bằng generic repository chỉ có giá trị khi abstraction mới thể hiện một boundary hữu ích hơn, không phải chỉ đổi tên `DbSet` thành `GetAll()` và `Add()`.

**Vấn đề nó giải quyết:**
Team muốn application logic không phụ thuộc trực tiếp vào persistence detail, hoặc có một domain/use case cần interface rõ để test và kiểm soát query. Nhưng generic repository quá mỏng có thể che mất LINQ, projection và transaction semantics mà không tạo lợi ích tương xứng.

**Ví dụ thực tế:**
```text
Không nhiều giá trị:
IGenericRepository<Order>
- Add
- Update
- Delete
- GetById

Có thể có giá trị hơn:
IOrderStore
- LoadForCancellation(orderId)
- Save(order)
```

Nếu use case chỉ cần query DTO đơn giản, dùng trực tiếp `DbContext` với projection có thể rõ ràng hơn.

**Trade-off:**
Repository chuyên biệt có thể bảo vệ domain boundary và gom persistence logic quan trọng, nhưng tăng abstraction và mapping. Dùng `DbContext` trực tiếp giảm boilerplate và giữ toàn bộ sức mạnh EF Core, nhưng application layer sẽ biết nhiều hơn về persistence model.

**Middle → Senior insight:**
Middle developer cần hiểu EF Core đã là abstraction mạnh và tránh tạo repository theo thói quen. Senior / Technical developer phải quyết định boundary dựa trên domain complexity, test strategy, persistence volatility và ownership, chứ không theo rule “mọi project đều phải có Repository Pattern”.

### Design 2 — Queue và Topic giải quyết hai kiểu fan-out khác nhau

**Khái niệm:**
Queue thường phù hợp khi một logical message cần được xử lý bởi một consumer group duy nhất theo mô hình competing consumers. Topic phù hợp khi cùng một event cần được phân phối độc lập tới nhiều subscriber với lifecycle và retry riêng.

**Vấn đề nó giải quyết:**
Nếu `OrderCreated` cần đồng thời kích hoạt Inventory, Analytics và Email, dùng một queue duy nhất khiến các consumer tranh cùng message thay vì mỗi hệ thống nhận bản sao logical riêng. Ngược lại, dùng topic cho command chỉ nên xử lý một lần có thể tạo semantics khó kiểm soát.

**Ví dụ thực tế:**
```text
Command:
GenerateInvoice
 -> Queue
 -> một worker bất kỳ xử lý

Event:
OrderCreated
 -> Topic
    -> Inventory subscription
    -> Analytics subscription
    -> Email subscription
```

Mỗi subscription có thể có filter, retry và dead-letter riêng.

**Trade-off:**
Topic tăng decoupling và fan-out nhưng làm số consumer, subscription, retry path và observability phức tạp hơn. Queue đơn giản hơn cho work distribution nhưng không phù hợp nếu nhiều bounded context đều cần cùng event.

**Middle → Senior insight:**
Middle developer cần phân biệt command “hãy làm việc này” với event “việc này đã xảy ra”. Senior / Solution-oriented engineer phải thiết kế ownership, delivery semantics, duplicate handling, filtering và failure isolation trước khi chọn queue hay topic.

### Design 3 — Normalize dữ liệu để bảo vệ invariant, denormalize có chủ đích để phục vụ read path

**Khái niệm:**
Normalization giảm duplication và giữ nguồn sự thật nhất quán; denormalization cố tình sao chép một phần dữ liệu để tối ưu query, latency hoặc autonomy. Hai kỹ thuật không loại trừ nhau nếu mỗi bên được dùng đúng boundary.

**Vấn đề nó giải quyết:**
Một reporting endpoint phải join nhiều bảng lớn mỗi request và trở thành bottleneck. Thay vì phá toàn bộ schema transactional, có thể giữ write model normalized rồi xây read model denormalized cho nhu cầu cụ thể.

**Ví dụ thực tế:**
```text
Transactional model:
Orders
OrderItems
Customers
Products

Read model:
OrderSummary
- OrderId
- CustomerNameSnapshot
- Total
- ItemCount
- Status
```

Read model có thể được cập nhật qua transaction nội bộ, background projection hoặc event tùy consistency requirement.

**Trade-off:**
Normalization giúp update semantics rõ và giảm inconsistency nhưng query phức tạp hơn ở một số workload. Denormalization tăng read performance và giảm join nhưng tạo duplication, synchronization và stale-data risk.

**Middle → Senior insight:**
Middle developer cần hiểu duplication không tự động là sai và normalization không tự động là tối ưu. Senior / Technical developer phải xác định source of truth, consistency SLA, update frequency, rebuild strategy và xem liệu index/query tuning có đủ trước khi thêm một read model denormalized.
