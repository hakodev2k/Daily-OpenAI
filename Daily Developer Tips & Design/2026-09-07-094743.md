# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure trong background processing

**Mẹo:**
Khi producer có thể tạo work nhanh hơn consumer xử lý, đừng mặc định dùng collection không giới hạn. Với .NET, `Channel.CreateBounded<T>` giúp giới hạn queue in-memory và tạo backpressure rõ ràng.

**Tại sao hữu ích:**
Unbounded queue có thể che giấu overload cho tới khi memory tăng mạnh hoặc GC pressure xuất hiện. Bounded channel buộc hệ thống thể hiện capacity limit sớm hơn: producer chờ, từ chối, hoặc áp dụng drop policy theo thiết kế.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, cancellationToken);
```

Một `BackgroundService` đọc từ `channel.Reader` và xử lý tuần tự hoặc với concurrency có kiểm soát.

**Lưu ý:**
Bounded queue không tự giải quyết durability. Nếu mất process mà job không được phép mất, dùng message broker hoặc persistent job store thay vì chỉ giữ queue trong memory.

### Tip 2 — Với PostgreSQL, dùng `EXPLAIN (ANALYZE, BUFFERS)` để phân biệt CPU, I/O và estimate sai

**Mẹo:**
Khi query chậm, đừng dừng ở `EXPLAIN`. Với môi trường an toàn để chạy query thật, dùng `EXPLAIN (ANALYZE, BUFFERS)` để xem actual timing, actual rows và mức đọc buffer.

**Tại sao hữu ích:**
Execution plan chỉ có estimate không cho biết bottleneck thật. `ANALYZE` cho actual cardinality; `BUFFERS` cho biết query chủ yếu hit shared buffers hay phải đọc nhiều block. Từ đó có thể phân biệt query shape xấu, statistics sai hoặc I/O pressure.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;
```

Nếu actual rows lệch lớn so với estimated rows, kiểm tra statistics và data distribution trước khi thêm index mới.

**Lưu ý:**
`EXPLAIN ANALYZE` thực thi query thật. Với `UPDATE`, `DELETE` hoặc query nặng trên production, phải cực kỳ thận trọng và có transaction/rollback strategy phù hợp.

### Tip 3 — Ưu tiên Managed Identity hơn secret tĩnh khi ứng dụng Azure truy cập Key Vault

**Mẹo:**
Nếu workload chạy trên Azure App Service, Azure Functions, VM hoặc dịch vụ hỗ trợ identity, ưu tiên Managed Identity để truy cập Key Vault thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Secret tĩnh cần rotate, dễ bị copy sang environment khác và có thể xuất hiện trong pipeline hoặc deployment setting. Managed Identity chuyển authentication sang identity do Azure quản lý, giảm secret-management surface.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey");
```

Trong local development, `DefaultAzureCredential` có thể dùng developer identity; trên Azure, cùng code có thể dùng Managed Identity.

**Lưu ý:**
Managed Identity không loại bỏ authorization design. Vẫn phải cấp RBAC tối thiểu cần thiết và tránh cho application quyền đọc toàn bộ vault nếu chỉ cần một nhóm secret cụ thể.

### Tip 4 — Trong Vue.js, hủy request cũ để tránh stale response ghi đè state mới

**Mẹo:**
Với search-as-you-type hoặc filter thay đổi nhanh, dùng `AbortController` để hủy request trước khi gửi request mới. Điều này ngăn response cũ về muộn rồi ghi đè dữ liệu mới hơn.

**Tại sao hữu ích:**
HTTP request chạy bất đồng bộ và thứ tự response không đảm bảo giống thứ tự request. Bug dạng race condition này thường chỉ xuất hiện ở network chậm và khó tái hiện local.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  });

  results.value = await response.json();
}
```

**Lưu ý:**
Phải phân biệt `AbortError` với lỗi network thật để không hiển thị error toast cho request bị hủy chủ động.

### Tip 5 — Dùng `TimeProvider` để loại bỏ test phụ thuộc đồng hồ hệ thống

**Mẹo:**
Với code có expiration, retry window hoặc scheduled behavior, inject `TimeProvider` thay vì gọi `DateTime.UtcNow` trực tiếp ở khắp nơi.

**Tại sao hữu ích:**
Test dựa vào thời gian thực dễ flaky, phải `Task.Delay` và chạy chậm. `TimeProvider` cho phép test kiểm soát clock mà không sửa domain logic hoặc đợi thời gian thật trôi qua.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        expiresAt <= timeProvider.GetUtcNow();
}
```

Test có thể dùng fake time provider để kiểm tra boundary trước và sau expiration một cách deterministic.

**Lưu ý:**
Không cần inject clock abstraction vào mọi class. Chỉ áp dụng ở nơi thời gian ảnh hưởng behavior nghiệp vụ hoặc khả năng test.

## 🧠 Software Design

### Design 1 — Direct-to-Blob upload vs backend proxy upload

**Khái niệm:**
Với file lớn, client có thể upload trực tiếp tới Azure Blob Storage bằng SAS ngắn hạn thay vì stream toàn bộ file qua backend. Backend vẫn giữ quyền kiểm soát bằng cách cấp token có scope và thời hạn giới hạn.

**Vấn đề nó giải quyết:**
Nếu backend proxy mọi byte, application server chịu thêm bandwidth, connection duration và scaling pressure dù business logic chỉ cần authorize upload và lưu metadata.

**Ví dụ thực tế:**
Mobile app yêu cầu backend tạo upload session. Backend kiểm tra quyền user, tạo blob name server-side và trả SAS chỉ cho phép `Write` vào đúng blob trong 10 phút. Client upload trực tiếp, sau đó backend nhận callback hoặc client báo hoàn tất để verify metadata.

**Trade-off:**
Direct upload giảm tải backend và phù hợp file lớn, nhưng client flow phức tạp hơn và cần thiết kế CORS, SAS scope, cleanup file orphan, validation và post-upload scanning. Proxy upload đơn giản hơn và cho backend kiểm soát stream trực tiếp nhưng tốn tài nguyên hơn.

**Middle → Senior insight:**
Middle developer cần triển khai SAS an toàn, không cho quyền rộng và không để client tự chọn path tùy ý. Senior / Technical developer phải quyết định boundary kiểm soát nào cần nằm ở backend, threat model của upload, cost egress/ingress và chiến lược xử lý file chưa hoàn tất hoặc độc hại.

### Design 2 — Optimistic concurrency vs pessimistic locking

**Khái niệm:**
Optimistic concurrency giả định conflict hiếm và phát hiện xung đột khi update, thường qua version/token. Pessimistic locking khóa tài nguyên sớm để ngăn concurrent modification trong thời gian transaction.

**Vấn đề nó giải quyết:**
Hai user có thể đọc cùng một record rồi cùng update. Nếu không có concurrency control, update sau có thể âm thầm ghi đè update trước.

**Ví dụ thực tế:**
Trong EF Core, entity có `rowversion`. User A và B cùng mở Order. A lưu trước; khi B lưu với version cũ, EF Core phát hiện zero rows affected và ném `DbUpdateConcurrencyException` để application quyết định reload, merge hoặc báo conflict.

**Trade-off:**
Optimistic concurrency giữ transaction ngắn và scale tốt khi conflict thấp, nhưng cần conflict-handling UX/logic. Pessimistic locking giảm conflict tại commit nhưng tăng blocking, deadlock risk và giữ resource lâu hơn.

**Middle → Senior insight:**
Middle developer cần biết cách detect và xử lý conflict thay vì retry vô hạn. Senior / Technical developer phải đánh giá contention rate, transaction duration, business criticality và user experience để chọn strategy — không mặc định optimistic hoặc pessimistic là tốt hơn trong mọi trường hợp.

### Design 3 — Strangler migration cho legacy CMS thay vì big-bang rewrite

**Khái niệm:**
Strangler migration thay thế legacy system theo từng capability hoặc route. Traffic được chuyển dần sang implementation mới trong khi phần cũ vẫn tiếp tục phục vụ các chức năng chưa migrate.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó xác nhận parity và buộc doanh nghiệp chờ tới khi toàn bộ hệ thống mới hoàn thiện. Với CMS/e-commerce lớn, dependency và editorial workflow thường phức tạp hơn tài liệu mô tả.

**Ví dụ thực tế:**
Một CMS cũ phục vụ content pages, search và product integration. Team trước tiên tách search API sang service mới, sau đó migrate content delivery cho một nhóm page type, trong khi authoring workflow cũ vẫn hoạt động cho phần chưa chuyển đổi.

**Trade-off:**
Strangler giảm migration risk và cho phép release giá trị sớm, nhưng tạo giai đoạn coexistence với routing, data synchronization, duplicate logic và operational complexity. Big-bang có kiến trúc cuối cùng sạch hơn nhanh hơn nếu scope thực sự nhỏ và hiểu rõ, nhưng blast radius lớn hơn.

**Middle → Senior insight:**
Middle developer cần giữ contract giữa old/new rõ ràng và tránh business logic bị copy vô kiểm soát. Senior / Technical developer phải chọn migration seam phù hợp, xác định source of truth trong từng giai đoạn, đo traffic/feature parity và đặt exit criteria để trạng thái hybrid không tồn tại vô thời hạn.
