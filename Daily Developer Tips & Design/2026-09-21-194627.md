# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — EF Core concurrency token phải bảo vệ business conflict, không chỉ bắt exception

**Mẹo:**
Dùng optimistic concurrency (`rowversion`/concurrency token) khi nhiều requests có thể sửa cùng một record, nhưng khi `DbUpdateConcurrencyException` xảy ra hãy quyết định theo business semantics: reload, merge, reject hoặc retry có kiểm soát.

**Tại sao hữu ích:**
Nếu hai users cùng đọc một version rồi cùng update, request đến sau có thể âm thầm ghi đè thay đổi trước nếu không có concurrency check. Token biến lost update thành conflict quan sát được, nhưng framework không thể tự quyết định dữ liệu nào đúng.

**Ví dụ:**
Hai nhân viên cùng sửa Order. Request A đổi địa chỉ, request B đổi trạng thái dựa trên version cũ. `rowversion` khiến B fail khi save; API trả conflict kèm state mới để client quyết định reload thay vì overwrite dữ liệu của A.

**Lưu ý:**
Không retry `DbUpdateConcurrencyException` mù quáng bằng cùng values cũ; như vậy chỉ biến conflict thành overwrite muộn. Với aggregate có nhiều invariants, conflict resolution phải nằm ở business boundary phù hợp.

### Tip 2 — PostgreSQL `EXPLAIN ANALYZE` phải đọc cả estimate và actual rows

**Mẹo:**
Khi query chậm, so sánh estimated rows với actual rows tại các plan nodes thay vì chỉ nhìn node có execution time lớn nhất. Sai lệch cardinality lớn thường giải thích vì sao optimizer chọn join/order/access path không phù hợp.

**Tại sao hữu ích:**
Optimizer ra quyết định dựa trên statistics và estimates. Nếu estimate là 100 rows nhưng thực tế 2 triệu rows, một nested loop hợp lý trên giấy có thể trở thành hàng triệu index probes trong runtime.

**Ví dụ:**
API search đột nhiên chậm sau khi data distribution thay đổi. `EXPLAIN (ANALYZE, BUFFERS)` cho thấy estimate thấp hơn actual hàng nghìn lần ở filter theo status; investigation tiếp tục vào statistics, correlation và index/query shape thay vì thêm index theo cảm tính.

**Lưu ý:**
`ANALYZE` thực sự chạy query; cẩn thận với statements có side effects và production workload nặng. Đừng tối ưu một plan snapshot mà bỏ qua parameter/data distribution khác.

### Tip 3 — Kubernetes `OOMKilled` và CPU throttling cần hai hướng điều tra khác nhau

**Mẹo:**
Khi pod chậm hoặc restart, phân biệt memory limit breach với CPU throttling bằng container status và resource metrics trước khi tăng requests/limits.

**Tại sao hữu ích:**
Memory vượt limit thường khiến container bị kill; CPU vượt limit thường bị throttle chứ không kill. Cả hai có thể biểu hiện thành timeout, nhưng nguyên nhân và remediation khác nhau: leak/working-set sizing khác với CPU saturation hoặc limit quá thấp.

**Ví dụ:**
API có latency spike nhưng không restart; metrics cho thấy CPU throttling tăng mạnh ở 500m limit. Một service khác restart với reason `OOMKilled` và memory sát 512Mi. Hai incidents không nên nhận cùng một fix “tăng resources”.

**Lưu ý:**
Tăng limits chỉ có thể trì hoãn leak hoặc che inefficient code. So sánh usage, requests, limits, GC/runtime metrics và node capacity; resource sizing phải dựa trên load test và production evidence.

### Tip 4 — Vue/React list key phải đại diện identity ổn định của item

**Mẹo:**
Với list có thể reorder, insert hoặc delete, dùng business/entity identity ổn định làm `key`, không dùng array index chỉ vì nó luôn có sẵn.

**Tại sao hữu ích:**
Virtual DOM dùng key để liên kết element/component cũ với item mới. Index thay đổi khi list reorder có thể khiến local component state, input value hoặc animation được tái sử dụng cho item sai.

**Ví dụ:**
Danh sách editable users dùng `user.id` làm key. Nếu dùng index và xóa user đầu tiên, component state của các rows sau có thể dịch sang user khác dù data array đúng.

**Lưu ý:**
Key cần stable và unique trong sibling list; tạo random key mỗi render cũng sai vì buộc framework remount components, làm mất state và tăng work.

### Tip 5 — Incident debugging nên bắt đầu từ deployment diff và telemetry timeline

**Mẹo:**
Khi error/latency tăng sau release, đặt deployment marker cạnh metrics/logs/traces rồi so sánh trước-sau theo endpoint, dependency, version và instance trước khi đọc code ngẫu nhiên.

**Tại sao hữu ích:**
Production incident có nhiều nhiễu. Timeline và dimension giúp thu hẹp hypothesis: lỗi chỉ ở version mới gợi regression; lỗi đồng thời ở cả versions nhưng chỉ một dependency gợi external failure.

**Ví dụ:**
Sau rollout, 5xx tăng từ 0.2% lên 8%. Application Insights cho thấy chỉ instances chạy build mới lỗi ở một SQL dependency; trace dẫn tới query mới được thêm trong release, giúp rollback có evidence và RCA tập trung.

**Lưu ý:**
Correlation không chứng minh causation. Deployment có thể trùng với traffic spike hoặc downstream outage; xác minh bằng traces, dependency metrics và reproduction trước khi kết luận.

## 🧠 Software Design

### Design 1 — Strangler Fig giúp modernization theo lát cắt thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig chuyển dần capabilities từ legacy system sang implementation mới, dùng routing/facade/boundary để traffic từng phần đi sang hệ thống mới trong khi phần còn lại vẫn hoạt động.

**Vấn đề nó giải quyết:**
Big-bang rewrite giữ business value bị khóa lâu, khó đạt feature parity và tạo cutover risk lớn. Migration theo lát cắt cho phép ship, đo và rollback từng capability.

**Ví dụ thực tế:**
Một .NET Framework CMS cũ vẫn phục vụ site. Team tách search API sang ASP.NET Core trước, route `/api/search` sang service mới, rồi tiếp tục migrate account và catalog theo business boundaries thay vì viết lại toàn site trong một release.

**Trade-off:**
Migration kéo dài tạo temporary duplication, routing complexity và integration giữa legacy/new. Nếu không có target boundaries và retirement plan, tổ chức có thể mắc kẹt vĩnh viễn ở trạng thái hai hệ thống.

**Middle → Senior insight:**
Middle developer cần giữ compatibility, tests và observability ở migration seam. Senior / Technical developer phải chọn migration slices theo dependency/risk/business value, thiết kế rollback và quyết định khi nào xóa legacy path để tránh permanent complexity.

### Design 2 — Distributed lock cần fencing khi stale owner vẫn có thể ghi

**Khái niệm:**
Distributed lock chỉ chứng minh quyền sở hữu trong một khoảng thời gian. Fencing token là sequence tăng dần được downstream resource kiểm tra để từ chối writes từ lock holder cũ sau khi lease hết hạn.

**Vấn đề nó giải quyết:**
Process A giữ lock rồi pause lâu do GC/network; lease hết và B lấy lock mới. A tỉnh lại và vẫn ghi dữ liệu. Nếu resource chỉ tin rằng A “đã từng có lock”, hai owners có thể cùng tạo side effect.

**Ví dụ thực tế:**
Scheduled job lấy lease kèm token 41; sau expiry worker mới nhận token 42. Database/storage chỉ chấp nhận write có fencing token lớn hơn token cuối, nên write muộn từ worker 41 bị reject.

**Trade-off:**
Fencing yêu cầu resource cuối cùng hỗ trợ compare/order semantics và làm protocol phức tạp hơn. Với operation idempotent hoặc single-node coordination đơn giản, mức bảo vệ này có thể không đáng chi phí.

**Middle → Senior insight:**
Middle developer cần hiểu lease expiry và không giả định lock tạo exactly-once. Senior / Technical developer phải phân tích pause/network failure model, chọn fencing/idempotency/unique constraint phù hợp và tránh dùng distributed lock như cách che boundary thiết kế kém.

### Design 3 — API versioning là chiến lược evolution, không phải license để phá contract

**Khái niệm:**
API versioning tạo boundary cho breaking changes khi compatibility không thể giữ, nhưng chiến lược tốt vẫn ưu tiên additive evolution và deprecation có kiểm soát thay vì tạo version mới cho mọi thay đổi.

**Vấn đề nó giải quyết:**
Clients deploy độc lập với server. Breaking rename, semantic change hoặc removal có thể làm mobile app, partner integration hay frontend cũ ngừng hoạt động ngay khi backend deploy.

**Ví dụ thực tế:**
Thêm optional field vào response giữ nguyên v1. Khi business semantics của pricing thay đổi không thể tương thích, v2 được giới thiệu song song; telemetry đo traffic v1, clients có migration window và v1 chỉ bị retire sau policy đã công bố.

**Trade-off:**
Nhiều versions tăng code paths, tests, documentation và security maintenance. Không versioning lại đẩy migration risk sang clients. Chi phí thật nằm ở thời gian coexistence và support contract, không chỉ ở route `/v2`.

**Middle → Senior insight:**
Middle developer cần phân biệt additive với breaking change và test contract. Senior / Technical developer phải thiết kế compatibility/deprecation policy, client migration, observability và sunset criteria; đôi khi giữ một version lâu bằng additive changes tốt hơn tạo v2 sớm.
