# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh `Task.Run` cho I/O-bound work trong ASP.NET Core

**Mẹo:**
Nếu operation đã có API async thật sự như database, HTTP, file I/O hoặc message broker, hãy `await` trực tiếp thay vì bọc bằng `Task.Run`.

**Tại sao hữu ích:**
`Task.Run` không làm I/O nhanh hơn mà chỉ đẩy việc sang thread pool, có thể làm tăng thread usage và giảm throughput khi server chịu tải lớn.

**Ví dụ:**
```csharp
// Không cần thiết
var users = await Task.Run(() =>
    dbContext.Users.ToListAsync(cancellationToken));

// Tốt hơn
var users = await dbContext.Users
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
`Task.Run` vẫn có thể phù hợp cho CPU-bound work cần tách khỏi request thread, nhưng không nên dùng như cách “biến code thành async”.

### Tip 2 — Dùng `TagWith()` để truy vết EF Core query trong production

**Mẹo:**
Thêm `TagWith()` vào các query quan trọng để SQL sinh ra mang theo comment nhận diện nguồn gọi.

**Tại sao hữu ích:**
Khi xem slow-query log, SQL Profiler hoặc database monitoring, bạn dễ biết query đến từ feature nào thay vì phải reverse-engineer từ SQL dài.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .TagWith("OrdersApi.GetRecentOrders")
    .AsNoTracking()
    .Where(x => x.CreatedAt >= fromDate)
    .ToListAsync(cancellationToken);
```

SQL sẽ chứa comment tương tự:

```sql
-- OrdersApi.GetRecentOrders
SELECT ...
```

**Lưu ý:**
Không đưa dữ liệu nhạy cảm hoặc giá trị động như email, token, user input vào tag vì chúng có thể xuất hiện trong database logs.

### Tip 3 — Dùng `curl -v` để phân biệt lỗi application và lỗi HTTP/TLS

**Mẹo:**
Khi một API “không gọi được”, dùng `curl -v` hoặc `curl -I` để kiểm tra DNS, TLS handshake, redirect, headers và status code trước khi debug application code.

**Tại sao hữu ích:**
Nó giúp nhanh chóng tách lỗi thành các nhóm: DNS, certificate, proxy, authentication, redirect hoặc server response.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Hoặc chỉ lấy headers:

```bash
curl -I https://api.example.com/health
```

**Lưu ý:**
`-v` có thể in headers chứa thông tin nhạy cảm. Không paste nguyên output chứa `Authorization`, cookie hoặc token vào issue/public chat.

### Tip 4 — Dùng SQL window function thay cho loop hoặc query lặp

**Mẹo:**
Khi cần ranking, running total, previous/next row hoặc top-N per group, xem xét window functions như `ROW_NUMBER()`, `LAG()`, `LEAD()` hoặc `SUM() OVER(...)`.

**Tại sao hữu ích:**
Giảm số round-trip và tránh phải tải dữ liệu về application rồi tự group/sort bằng code.

**Ví dụ:**
```sql
SELECT
    EmployeeId,
    WorkDate,
    Hours,
    SUM(Hours) OVER (
        PARTITION BY EmployeeId
        ORDER BY WorkDate
    ) AS RunningHours
FROM TimesheetEntries;
```

**Lưu ý:**
Window function vẫn có thể tốn sort và memory trên dataset lớn. Hãy kiểm tra execution plan và index phù hợp thay vì giả định nó luôn nhanh hơn.

### Tip 5 — Dùng `git range-diff` sau rebase để kiểm tra semantic change

**Mẹo:**
Sau khi rebase hoặc chỉnh lại chuỗi commit, dùng `git range-diff` để so sánh hai phiên bản commit series thay vì chỉ nhìn diff cuối cùng.

**Tại sao hữu ích:**
Bạn có thể phát hiện commit nào bị thay đổi, mất hoặc vô tình mang thêm logic trong quá trình rebase.

**Ví dụ:**
```bash
git range-diff origin/main...feature-before \
               origin/main...feature-after
```

Một workflow thực tế là tag hoặc lưu SHA trước rebase rồi so sánh sau khi hoàn thành.

**Lưu ý:**
`range-diff` so sánh chuỗi patch, không thay thế test hoặc code review. Hai patch trông tương đương vẫn có thể tạo behavior khác nếu context thay đổi.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database + message publishing

**Khái niệm:**
Outbox Pattern lưu business change và message/event cần publish trong cùng một local database transaction. Một background worker sau đó đọc Outbox và gửi message ra broker.

**Vấn đề nó giải quyết:**
Nếu application vừa `SaveChanges()` vừa publish RabbitMQ/Kafka message trực tiếp, có thể xảy ra trạng thái database commit thành công nhưng publish thất bại, hoặc ngược lại.

**Ví dụ thực tế:**
Khi tạo `Order`, transaction ghi đồng thời:

```text
Orders
OutboxMessages(OrderCreated)
```

Sau commit, worker lấy `OutboxMessages` chưa gửi, publish `OrderCreated`, rồi đánh dấu đã xử lý.

**Trade-off:**
Lợi ích là tránh dual-write inconsistency và hỗ trợ retry an toàn hơn. Chi phí là thêm bảng Outbox, background processor, retention/cleanup, duplicate delivery handling và monitoring.

**Middle → Senior insight:**
Middle developer nên hiểu tại sao `SaveChanges()` + `PublishAsync()` không atomic. Senior developer cần thiết kế message identity, retry, idempotent consumer, ordering, cleanup và cách vận hành khi Outbox backlog tăng mạnh.

### Design 2 — Optimistic Concurrency thay cho lock dài

**Khái niệm:**
Optimistic Concurrency giả định conflict hiếm xảy ra. Hệ thống cho phép nhiều request đọc cùng dữ liệu nhưng khi update sẽ kiểm tra version/token để phát hiện dữ liệu đã bị thay đổi.

**Vấn đề nó giải quyết:**
Giữ database lock lâu để ngăn mọi conflict có thể làm giảm throughput và tăng contention, nhất là với web request có thời gian xử lý không đoán trước.

**Ví dụ thực tế:**
Entity có `rowversion`:

```csharp
public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; } = null!;

    [Timestamp]
    public byte[] Version { get; set; } = null!;
}
```

Nếu hai người cùng sửa Employee, request commit sau có thể nhận `DbUpdateConcurrencyException` thay vì âm thầm ghi đè dữ liệu mới hơn.

**Trade-off:**
Lợi ích là không giữ lock lâu và scale tốt khi conflict thấp. Chi phí là application phải xử lý conflict UX, retry hoặc merge logic. Với workload conflict rất cao, optimistic concurrency có thể tạo nhiều retry lãng phí.

**Middle → Senior insight:**
Middle developer cần biết cách phát hiện và xử lý concurrency conflict. Senior developer phải quyết định dữ liệu nào cần versioning, conflict nào có thể retry, conflict nào cần user resolve và khi nào pessimistic locking hợp lý hơn.

### Design 3 — Read Model riêng khi query bắt đầu làm méo domain model

**Khái niệm:**
Một hệ thống không bắt buộc dùng cùng một model cho cả write behavior và mọi read screen. Khi query/reporting ngày càng khác với transactional model, có thể tạo read model hoặc projection riêng mà chưa cần áp dụng full CQRS phức tạp.

**Vấn đề nó giải quyết:**
Nếu domain aggregate bị thêm hàng loạt navigation property, join và DTO logic chỉ để phục vụ dashboard/report, write model sẽ dần bị thiết kế theo nhu cầu UI thay vì business invariants.

**Ví dụ thực tế:**
`Timesheet` write model tập trung vào rules sửa giờ và approval. Dashboard manager cần tổng hợp theo Employee, Project, Office và Month. Thay vì ép aggregate phục vụ report, có thể tạo query model hoặc materialized projection tối ưu riêng cho dashboard.

**Trade-off:**
Lợi ích là write model giữ rõ business behavior, còn read path có thể tối ưu độc lập. Chi phí là duplicated shape, thêm mapping/projection và nếu read model được materialize bất đồng bộ thì phải chấp nhận eventual consistency.

**Middle → Senior insight:**
Middle developer nên hiểu DTO/read projection không nhất thiết phải phản chiếu entity 1:1. Senior developer cần nhận ra thời điểm tách read model mang lại giá trị thật, đồng thời tránh biến một nhu cầu query đơn giản thành CQRS infrastructure quá mức.
