## Developer Tips & Tricks

### 1. `ArrayPool<T>` chỉ đáng dùng khi allocation profile chứng minh buffer ngắn hạn đang tạo GC pressure

**Vấn đề thực tế:** Một parser hoặc serializer tạo `byte[]` vài chục KB cho mỗi request. Khi throughput tăng, allocation rate cao làm Gen 0/Gen 1 collection dày hơn; với buffer đủ lớn còn có thể chạm Large Object Heap. Team thấy `ArrayPool<T>` và thay mọi `new byte[]` bằng pool, nhưng lại vô tình giữ dữ liệu nhạy cảm hoặc dùng buffer sau khi đã trả về pool.

**Cơ chế bên dưới:** `ArrayPool<T>.Shared.Rent(n)` trả về một array có độ dài **ít nhất** `n`, không bảo đảm đúng bằng `n` và nội dung cũ có thể còn tồn tại. Sau `Return`, caller không còn ownership; giữ `Span`, `Memory` hoặc reference để tiếp tục dùng là correctness bug. Pool giảm allocation churn nhưng đổi lại lifecycle phức tạp hơn.

```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(32 * 1024);
try
{
    int read = await stream.ReadAsync(
        buffer.AsMemory(0, 32 * 1024),
        cancellationToken);

    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
}
```

`clearArray: true` có CPU cost; dùng khi buffer có secret/PII hoặc threat model yêu cầu. Với buffer nhỏ, ít allocation hoặc code không nằm trên hot path, `new` thường đơn giản và an toàn hơn.

**Khi nên dùng:** High-throughput parsers, compression, protocol handling, serialization và pipelines sau khi profiling cho thấy temporary arrays là nguồn allocation đáng kể.

### 2. EF Core optimistic concurrency: `DbUpdateConcurrencyException` là tín hiệu business conflict, không phải lỗi để retry mù

**Vấn đề thực tế:** Hai request cùng đọc `Order`, cùng sửa trạng thái rồi `SaveChangesAsync`. Nếu không có concurrency token, update đến sau có thể silently overwrite thay đổi trước. Khi thêm `rowversion`, team bắt `DbUpdateConcurrencyException` rồi retry nguyên command, vô tình áp quyết định dựa trên stale state lên state mới.

**Cơ chế bên dưới:** Với SQL Server `rowversion`, EF Core đưa original concurrency token vào `WHERE` của `UPDATE`. Nếu row đã đổi, affected rows bằng 0 và EF phát hiện conflict. Retry kỹ thuật chỉ hợp lệ nếu business operation có thể được re-evaluate trên state mới.

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = default!;

    [Timestamp]
    public byte[] Version { get; set; } = default!;
}
```

```csharp
try
{
    order.Status = "Approved";
    await db.SaveChangesAsync(cancellationToken);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "order_changed",
        message = "Order was modified by another operation. Reload and retry the business decision."
    });
}
```

Đối với command tự nhiên commutative hoặc có thể recompute, application có thể reload rồi thử lại có giới hạn. Với approval, balance, inventory hoặc state machine, conflict thường phải quay lại business layer.

**Khi nên dùng:** Aggregate có concurrent writers, workflow/state transitions, admin editing và APIs cần chống lost update.

### 3. SQL keyset pagination ổn định hơn `OFFSET/FETCH` cho deep pages

**Vấn đề thực tế:** Endpoint `/orders?page=5000&pageSize=50` ngày càng chậm. Query dùng `ORDER BY CreatedAt DESC OFFSET 249950 ROWS FETCH NEXT 50 ROWS ONLY`. Database vẫn phải đi qua lượng lớn rows trước khi bỏ chúng đi; concurrent inserts còn làm page boundaries dịch chuyển, gây duplicate hoặc missing rows giữa các request.

**Cơ chế bên dưới:** Keyset/seek pagination dùng giá trị cuối của page trước làm cursor và seek trực tiếp vào ordered index. Sort key phải deterministic; nếu `CreatedAt` không unique, thêm `Id` làm tie-breaker.

```sql
SELECT TOP (50)
    Id, CreatedAt, Status, Total
FROM dbo.Orders
WHERE
    CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index nên align với filter/order thực tế, ví dụ `(CreatedAt DESC, Id DESC)` cộng `INCLUDE` cho projection cần thiết. Cursor nên encode cả hai values và được validate, thay vì expose một page number giả tạo.

**Khi nên dùng:** Infinite scroll, activity feeds, audit logs, order/history APIs và tables lớn cần sequential navigation. `OFFSET` vẫn phù hợp cho shallow pages hoặc UX bắt buộc random page jumps.

### 4. `git rerere` giảm công sức giải lại cùng một merge conflict trên long-lived branches

**Vấn đề thực tế:** Một feature branch sống lâu phải rebase lên `main` nhiều lần. Cùng một conflict ở project file hoặc dependency registration xuất hiện lặp lại; developer giải giống nhau mỗi lần và dễ tạo resolution khác nhau.

**Cơ chế bên dưới:** `rerere` là “reuse recorded resolution”. Git ghi lại conflict shape và resolution đã được commit/stage. Khi conflict tương tự xuất hiện lần sau, Git có thể áp lại resolution trước để bạn review thay vì giải từ đầu.

```bash
git config --global rerere.enabled true

git rebase main
# resolve conflict normally
git add src/MyProject/MyProject.csproj
git rebase --continue
```

Lần sau, kiểm tra kỹ auto-applied resolution bằng `git diff` và test suite; `rerere` tái sử dụng quyết định cũ chứ không hiểu semantic change mới.

**Khi nên dùng:** Long-lived feature branches, repeated rebases/cherry-picks, release branches và repositories có conflict patterns lặp lại. Không xem nó là lý do để giữ branch sống quá lâu.

### 5. Structured logging: log template ổn định, data ở property — đừng tạo message động bằng string interpolation

**Vấn đề thực tế:** Code log `logger.LogWarning($"Payment {paymentId} failed for {customerId}")`. Log backend nhận hàng triệu message strings khác nhau; query theo `PaymentId` khó hơn, cardinality/indexing có thể xấu và alert dựa trên message text trở nên brittle.

**Cơ chế bên dưới:** `Microsoft.Extensions.Logging` dùng message template để giữ event shape ổn định và attach values thành structured properties. Observability system có thể filter/group theo field thay vì parse text.

```csharp
logger.LogWarning(
    "Payment {PaymentId} failed for customer {CustomerId} with provider status {ProviderStatus}",
    paymentId,
    customerId,
    providerStatus);
```

Đừng log access token, password, full payment data hoặc PII chỉ vì structured fields dễ query. Với hot logging paths, source-generated logging bằng `[LoggerMessage]` còn có thể giảm boxing/template parsing overhead.

**Khi nên dùng:** Production APIs, distributed services, incident investigation và bất kỳ hệ thống nào gửi logs sang centralized observability platform.

## Software Design

### 6. Lease-based distributed lock: lock có timeout vẫn chưa đủ nếu không có fencing token

**Vấn đề thực tế:** Worker A lấy distributed lock với lease 30 giây rồi bị GC pause/network partition trong 40 giây. Lease hết hạn, worker B lấy lock mới và bắt đầu ghi. A tỉnh lại, không biết lock đã mất và tiếp tục ghi; lúc này hai workers cùng có thể gây side effect dù lock service hoạt động đúng.

**Thiết kế:** Lease giải quyết abandoned lock nhưng không tự ngăn stale owner. Fencing token là số tăng đơn điệu cấp cho mỗi lock acquisition. Resource nhận write chỉ chấp nhận token mới hơn token đã thấy trước đó, nên owner cũ bị fence out.

```text
Worker A acquires lock -> token 41
        |
        +---- long pause -------------------+
                                            |
Lease expires                                |
Worker B acquires lock -> token 42           |
        |                                    |
        +--> Storage accepts token 42        |
                                             |
Worker A resumes ----------------------------+
        |
        +--> write with token 41
             Storage rejects: 41 < 42
```

**Trade-off:** Fencing yêu cầu downstream resource tham gia protocol và lưu/so sánh token; nếu resource không thể validate token, distributed lock vẫn có stale-owner window. Đôi khi thiết kế idempotent/partitioned ownership tốt hơn lock toàn cục.

**Khi phù hợp:** Distributed schedulers, singleton jobs, file/object mutation, leader-like workers và critical side effects nơi duplicate concurrent execution không chấp nhận được.

### 7. Cache-Aside không tự giải quyết stale data: phải thiết kế invalidation và stampede control

**Vấn đề thực tế:** API đọc product từ cache; cache miss thì query database rồi populate cache. Khi product update, cache cũ sống thêm 10 phút. Đến lúc key hết hạn, hàng trăm requests đồng thời miss và cùng đánh database, tạo cache stampede.

**Thiết kế:** Cache-Aside giữ cache ngoài transaction path nên application phải quyết định consistency policy. Update có thể invalidate key sau database commit; read miss nên có request coalescing/single-flight hoặc probabilistic early refresh cho hot keys. TTL là safety net, không phải invalidation strategy duy nhất.

```text
READ
Client -> Cache -- hit --> return
           |
          miss
           v
       single-flight
           |
           v
        Database
           |
           v
       populate cache

WRITE
Client -> Database commit -> invalidate cache key
```

**Trade-off:** Invalidate-after-write có một cửa sổ race với concurrent readers; distributed invalidation/event propagation tăng complexity. Strong consistency thường không nên được giả lập bằng một cache design quá phức tạp — critical reads có thể bypass cache.

**Khi phù hợp:** Read-heavy APIs, catalog/reference data và expensive queries nơi bounded staleness được chấp nhận. Không dùng cache để che một query/index design chưa được sửa.

### 8. Saga orchestration: compensation không phải database rollback xuyên service

**Vấn đề thực tế:** Checkout gồm ReserveInventory → ChargePayment → CreateShipment. Shipment thất bại sau khi payment đã charge. Team gọi thao tác refund là “rollback transaction”, dẫn tới giả định sai rằng hệ thống có thể quay về trạng thái y hệt trước đó.

**Thiết kế:** Saga chia workflow thành local transactions và định nghĩa compensating actions cho failure. Orchestrator giữ state machine, correlation và quyết định bước tiếp theo. Compensation là **business action mới** — ví dụ refund có audit trail, có thể thất bại và bản thân nó cần retry/idempotency.

```text
Start Order
    |
    v
Reserve Inventory ----fail----> Cancel Order
    |
    v
Charge Payment -------fail----> Release Inventory
    |
    v
Create Shipment ------fail----> Refund Payment
    |                              |
 success                           v
    |                         Release Inventory
    v
Complete Order
```

**Trade-off:** Orchestration làm control flow dễ quan sát hơn choreography khi workflow dài, nhưng tạo một coordinator cần durability, versioning và recovery semantics. Mỗi step phải idempotent vì timeout có thể khiến orchestrator không biết remote step đã commit hay chưa.

**Khi phù hợp:** Multi-service business workflows có nhiều local transactions, cần explicit recovery/compensation và cần biết workflow đang mắc ở bước nào.
