# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống database connection pooling

**Mẹo:**
Phân biệt `AddDbContextPool` của EF Core với connection pooling của database provider. `DbContext` pooling tái sử dụng instance/context state đã reset; connection pooling tái sử dụng physical database connections. Tối ưu một lớp không tự động giải quyết bottleneck ở lớp còn lại.

**Tại sao hữu ích:**
Khi API chậm vì connection pool cạn, bật `AddDbContextPool` có thể giảm allocation/context initialization nhưng không tạo thêm database capacity. Ngược lại, tạo `DbContext` liên tục có overhead riêng dù connection pool vẫn khỏe. Chẩn đoán đúng resource đang bị pressure giúp tránh tối ưu nhầm tầng.

**Ví dụ:**
Nếu telemetry cho thấy request chờ lâu khi `OpenAsync` và concurrent DB operations gần pool limit, hãy điều tra query duration, transaction lifetime và connection pool trước. Nếu DB latency thấp nhưng allocation/profile cho thấy context initialization đáng kể ở workload cực lớn, lúc đó `AddDbContextPool` mới đáng benchmark.

**Lưu ý:**
Pooled `DbContext` phải tránh giữ request-specific mutable state không được reset đúng cách. Đừng tăng `Max Pool Size` để che slow query hoặc transaction giữ connection quá lâu; việc đó có thể chỉ chuyển áp lực sang SQL Server.

### Tip 2 — Dùng `git bisect` khi regression có phạm vi commit chưa rõ

**Mẹo:**
Khi biết một commit cũ hoạt động và HEAD bị lỗi, dùng `git bisect` để tìm commit đầu tiên gây regression thay vì đọc tuần tự hàng chục diff.

**Tại sao hữu ích:**
Binary search giảm đáng kể số revision cần kiểm tra. Nếu có test hoặc script tái hiện deterministic, `git bisect run` còn biến quá trình điều tra thành executable diagnosis thay vì phỏng đoán dựa trên commit message.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
```
Một regression nằm trong 128 commits về lý thuyết chỉ cần khoảng 7 bước phân đôi nếu phép kiểm tra đáng tin cậy.

**Lưu ý:**
Flaky test làm `bisect` đưa ra kết luận sai. Commit trung gian cũng có thể không build vì lịch sử không giữ từng commit ở trạng thái runnable; khi đó cần skip hoặc dùng script phân loại exit code cẩn thận.

### Tip 3 — MongoDB document model nên theo atomicity và access pattern, không theo ER diagram

**Mẹo:**
Embed dữ liệu khi nó có lifecycle gắn chặt, kích thước bị giới hạn và thường được đọc/cập nhật cùng aggregate; reference khi dữ liệu tăng không giới hạn, được chia sẻ rộng hoặc có lifecycle độc lập.

**Tại sao hữu ích:**
Copy cấu trúc normalized của SQL sang MongoDB thường tạo nhiều round trip hoặc application-side joins. Ngược lại, embed mọi thứ có thể tạo document khổng lồ và write amplification. Document boundary còn là atomic update boundary quan trọng trong thiết kế.

**Ví dụ:**
`Order` có thể embed immutable line-item snapshots vì checkout cần đọc chúng cùng order và lịch sử phải giữ giá tại thời điểm mua. Nhưng toàn bộ lịch sử shipment events tăng vô hạn có thể cần collection riêng tùy query pattern và retention.

**Lưu ý:**
Denormalization tạo duplicate data và yêu cầu strategy khi source thay đổi. Đừng chọn embed/reference chỉ theo quan hệ one-to-many; hãy đo cardinality, update frequency, query shape và document growth.

### Tip 4 — Playwright test nên chờ trạng thái người dùng quan sát được, không `sleep`

**Mẹo:**
Trong E2E test, chờ locator, URL, network-driven UI state hoặc assertion có auto-wait thay vì `WaitForTimeout` với thời gian cố định.

**Tại sao hữu ích:**
Fixed sleep vừa làm suite chậm vừa flaky: 2 giây là lãng phí khi UI hoàn tất sau 100 ms nhưng vẫn thiếu khi CI chậm mất 3 giây. Chờ observable condition khiến test đồng bộ với behavior thực tế thay vì tốc độ máy.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Saved successfully")).ToBeVisibleAsync();
```
Test xác nhận outcome mà user thấy thay vì đoán backend/UI cần bao nhiêu milliseconds.

**Lưu ý:**
Auto-wait không sửa được test architecture tệ. Nếu assertion phụ thuộc dữ liệu dùng chung hoặc asynchronous backend job không có observable completion contract, test vẫn có thể flaky; cần kiểm soát test data và system boundary.

### Tip 5 — File upload phải kiểm tra nội dung và storage boundary, không chỉ extension

**Mẹo:**
Với ASP.NET Core upload endpoint, giới hạn kích thước, tạo server-side filename/key, xác thực loại nội dung phù hợp với use case và lưu file ngoài web root hoặc vào object storage với quyền tối thiểu.

**Tại sao hữu ích:**
Tên file và `Content-Type` do client gửi không phải trust boundary. Nếu lưu trực tiếp filename người dùng vào executable/static path, attacker có thể lợi dụng path, overwrite hoặc khiến nội dung nguy hiểm được phục vụ từ trusted origin.

**Ví dụ:**
API nhận avatar, kiểm tra size và decode/validate định dạng ảnh thực tế, sinh GUID storage key, lưu vào Azure Blob Storage private container rồi cấp controlled access thay vì dùng `wwwroot/uploads/{originalName}`.

**Lưu ý:**
Magic-byte validation cũng không phải malware scanner hoàn chỉnh. Với tài liệu do người dùng tải lên rồi chia sẻ, threat model có thể cần antivirus/content scanning, quarantine và asynchronous processing. Không load file lớn toàn bộ vào memory nếu có thể stream.

## 🧠 Software Design

### Design 1 — Optimistic concurrency bảo vệ business invariant tốt hơn “last write wins” trong nhiều CRUD flow

**Khái niệm:**
Optimistic concurrency cho phép nhiều reader làm việc song song nhưng từ chối hoặc phát hiện write nếu dữ liệu đã thay đổi kể từ lúc client đọc. Trong EF Core/SQL Server, concurrency token như `rowversion` có thể biến silent overwrite thành conflict có thể xử lý.

**Vấn đề nó giải quyết:**
Hai nhân viên mở cùng order. Người A đổi shipping address; người B dựa trên snapshot cũ đổi status rồi gửi toàn bộ entity. Nếu update cuối ghi đè tất cả columns, thay đổi hợp lệ của A có thể biến mất mà không có lỗi.

**Ví dụ thực tế:**
API trả `version` cùng order. Update gửi version cũ; EF Core phát hiện `UPDATE ... WHERE Id = @id AND Version = @originalVersion` ảnh hưởng 0 rows và application trả conflict/merge workflow thay vì silently overwrite.

**Trade-off:**
Optimistic concurrency không ngăn conflict; nó làm conflict nhìn thấy được. Application cần policy retry, merge hoặc yêu cầu user refresh. Với contention cực cao quanh một invariant cần serialization, pessimistic locking hoặc thiết kế command khác có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần cấu hình concurrency token và xử lý `DbUpdateConcurrencyException` đúng. Senior / Technical developer phải xác định invariant nào cần conflict detection, granularity của token, UX/API semantics khi conflict và khi nào retry tự động là nguy hiểm vì operation mang business intent không thể merge máy móc.

### Design 2 — Azure Functions vs Worker Service: chọn theo execution model và operational control

**Khái niệm:**
Azure Functions phù hợp với event/trigger-driven workloads nơi platform quản lý phần lớn activation và scaling. Worker Service phù hợp khi application cần process lifetime, concurrency loop, resource control hoặc hosting model ổn định do team chủ động quản lý.

**Vấn đề nó giải quyết:**
Background workload không đồng nhất. Một Blob-created handler chạy ngắn có pressure khác với processor duy trì nhiều long-running sessions, custom batching và connection lifecycle. Chọn hosting model chỉ vì “serverless scale” hoặc vì team quen `BackgroundService` dễ tạo operational mismatch.

**Ví dụ thực tế:**
Thumbnail generation độc lập theo blob event có thể hợp với Function. Một ingestion processor giữ protocol connection lâu, cần fine-grained backpressure và predictable process lifetime có thể hợp với Worker Service trên App Service/Kubernetes hơn.

**Trade-off:**
Functions giảm infrastructure management và tích hợp trigger tốt nhưng có hosting/runtime constraints, cold-start/cost behavior tùy plan và ít process control hơn. Worker Service cho nhiều control nhưng team phải chịu deployment, scaling, health và capacity planning rõ hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, idempotency và graceful shutdown của hosting model mình dùng. Senior / Technical developer phải so sánh workload duration, burstiness, concurrency, scaling signal, network requirements, cost, observability và team operational maturity trước khi chọn platform.

### Design 3 — Anti-Corruption Layer bảo vệ domain khỏi semantics của hệ thống ngoài

**Khái niệm:**
Anti-Corruption Layer (ACL) đặt translation boundary giữa domain model nội bộ và model/protocol của external hoặc legacy system. Nó không chỉ map DTO; nó chuyển semantics để dependency bên ngoài không lan trực tiếp vào core business model.

**Vấn đề nó giải quyết:**
Một ERP có thể dùng status codes, identifiers và lifecycle khác hoàn toàn với application mới. Nếu toàn bộ domain dùng trực tiếp `ERPOrderDto`, mỗi thay đổi vendor schema hoặc legacy convention sẽ lan qua business logic và làm ownership boundary mờ đi.

**Ví dụ thực tế:**
Integration layer nhận `ERP_STATUS=40`, mapping thành domain transition `ShipmentConfirmed` sau khi kiểm tra các field cần thiết. Domain không biết code `40`, SOAP payload hay vendor-specific naming; adapter chịu trách nhiệm dịch và validation.

**Trade-off:**
ACL thêm code, mapping và đôi khi duplicated model. Với integration nhỏ, stable và semantics gần như trùng khớp, một adapter đơn giản có thể đủ; xây framework mapping phức tạp sẽ là over-engineering. Boundary cũng cần test vì mapping sai có thể âm thầm đổi business meaning.

**Middle → Senior insight:**
Middle developer cần giữ external DTO ở integration boundary và test mapping/validation. Senior / Technical developer phải nhận diện semantic mismatch, quyết định nơi translation thuộc về, quản lý versioning/failure của external contract và cân bằng isolation benefit với maintenance cost của một model trung gian.
