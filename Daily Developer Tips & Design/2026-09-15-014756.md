# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncDisposable` khi cleanup bản thân cũng là I/O

**Mẹo:**
Nếu resource cần cleanup bằng thao tác asynchronous, ví dụ flush network stream, hoàn tất async writer hoặc đóng resource có I/O, triển khai và sử dụng `IAsyncDisposable` với `await using` thay vì ép cleanup chạy synchronous.

**Tại sao hữu ích:**
`Dispose()` phù hợp khi cleanup nhanh và synchronous. Nếu cleanup phải chờ I/O mà lại block bằng `.GetAwaiter().GetResult()` hoặc `.Result`, bạn có thể kéo dài request thread, gây deadlock trong một số môi trường hoặc làm ThreadPool pressure tăng. `DisposeAsync()` cho phép cleanup giữ đúng async flow.

**Ví dụ:**
```csharp
await using var writer = new SomeAsyncWriter(stream);
await writer.WriteAsync(payload, ct);
// DisposeAsync được await khi ra khỏi scope.
```

Nếu class sở hữu cả resource sync và async, có thể cần hỗ trợ cả `IDisposable` và `IAsyncDisposable` với ownership semantics rõ ràng.

**Lưu ý:**
Đừng triển khai `IAsyncDisposable` chỉ vì method khác trong class là async. Cleanup phải thực sự có async work đáng kể. Đồng thời tránh dispose resource mà class không sở hữu; ownership sai dễ tạo bug khi resource được chia sẻ qua DI hoặc factory.

### Tip 2 — Dùng keyset pagination khi dataset lớn và user đi tuần tự qua nhiều trang

**Mẹo:**
Với bảng lớn, nếu client chủ yếu đi “trang tiếp theo”, cân nhắc keyset pagination dựa trên sort key ổn định thay vì `OFFSET ... FETCH` với offset ngày càng lớn.

**Tại sao hữu ích:**
Offset pagination thường buộc database phải bỏ qua ngày càng nhiều row trước khi trả trang tiếp theo. Keyset pagination dùng vị trí cuối của trang trước làm boundary nên database có thể seek theo index, giúp latency ổn định hơn khi dataset tăng.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp cần theo đúng ordering, ví dụ `(CreatedAt DESC, Id DESC)` cùng các column cần cover nếu workload yêu cầu.

**Lưu ý:**
Keyset pagination khó hỗ trợ “nhảy thẳng tới trang 500” và cần sort key deterministic. Nếu chỉ sort theo `CreatedAt` mà nhiều row cùng timestamp, phải thêm tie-breaker như `Id` để tránh duplicate hoặc skip row giữa các page.

### Tip 3 — Validate đầy đủ JWT `issuer`, `audience`, signature và lifetime; đừng chỉ decode token

**Mẹo:**
Khi ASP.NET Core API nhận JWT, luôn cấu hình validation cho signature, issuer, audience và expiration theo identity provider thực tế. Việc base64-decode payload để đọc claim không phải là xác thực token.

**Tại sao hữu ích:**
JWT chỉ đáng tin sau khi signature và trust boundary được kiểm tra. Một token có cấu trúc hợp lệ nhưng phát hành cho application khác, tenant khác hoặc đã hết hạn vẫn có thể chứa claim “đúng hình dạng”. Nếu API chỉ đọc claim, attacker có thể lợi dụng token không dành cho service này.

**Ví dụ:**
```csharp
builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer(options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = configuration["Auth:Audience"];
    });
```

Sau đó authorization policy nên dựa trên claim đã được framework validate, không tự tin vào payload từ request.

**Lưu ý:**
Clock skew, key rotation và multi-tenant issuer cần được thiết kế đúng thay vì hard-code tùy tiện. Không log raw access token. Và `ValidateLifetime = false` chỉ để debug có kiểm soát; tuyệt đối không dùng như production workaround cho token hết hạn.

### Tip 4 — Dùng browser DevTools waterfall để phân biệt backend chậm với frontend chặn render

**Mẹo:**
Khi page load chậm, mở Network và Performance panel để xem request nào thực sự chiếm thời gian, dependency nào chạy nối tiếp, JavaScript task nào block main thread và resource nào trì hoãn rendering.

**Tại sao hữu ích:**
Một trang “cảm giác chậm” có thể do backend TTFB cao, bundle JavaScript lớn, ảnh nặng, request waterfall nối tiếp hoặc long task trên main thread. Nếu chỉ tối ưu API mà bottleneck nằm ở render/network scheduling, kết quả gần như không đổi.

**Ví dụ:**
```text
Navigation
  HTML TTFB        120 ms
  app.js download  180 ms
  JS long task     900 ms
  API /products    140 ms
```

Trong trường hợp này, API không phải bottleneck chính; long-running JavaScript mới là mục tiêu cần profile tiếp.

**Lưu ý:**
DevTools trên máy developer không phản ánh đầy đủ thiết bị yếu hoặc mạng di động. Hãy kết hợp Lighthouse/Core Web Vitals, throttling và production RUM khi có thể. Đừng kết luận chỉ từ một lần load khi cache còn lạnh hoặc extension trình duyệt gây nhiễu.

### Tip 5 — Dùng `git rerere` khi phải resolve cùng một conflict nhiều lần

**Mẹo:**
Trong branch dài hoặc chuỗi rebase/cherry-pick phức tạp, bật `rerere` để Git ghi nhớ cách bạn đã resolve một conflict và có thể tái áp dụng resolution đó khi conflict tương tự xuất hiện lại.

**Tại sao hữu ích:**
Khi một feature branch thường xuyên rebase lên main, cùng một vùng code có thể conflict lặp đi lặp lại. Resolve thủ công mỗi lần vừa tốn thời gian vừa dễ không nhất quán. `rerere` biến resolution trước thành reusable local knowledge.

**Ví dụ:**
```bash
git config --global rerere.enabled true
```

Sau lần đầu resolve conflict và commit, nếu conflict tương tự xuất hiện trong rebase sau, Git có thể tự đề xuất hoặc áp lại resolution đã lưu.

**Lưu ý:**
Luôn review diff sau khi `rerere` áp dụng; context code có thể đã thay đổi nên resolution cũ không còn đúng về semantics. Đây là trợ giúp workflow, không phải guarantee correctness. Đừng auto-commit conflict resolution mà không chạy test/build phù hợp.

## 🧠 Software Design

### Design 1 — Synchronous call hay asynchronous messaging phụ thuộc vào business dependency của kết quả

**Khái niệm:**
Synchronous communication phù hợp khi caller cần kết quả ngay để tiếp tục business flow. Asynchronous messaging phù hợp khi work có thể tách khỏi request hiện tại và chấp nhận eventual consistency, retry độc lập hoặc xử lý nền.

**Vấn đề nó giải quyết:**
Nếu mọi integration đều dùng HTTP synchronous, một dependency chậm có thể kéo latency và failure lên toàn request chain. Ngược lại, nếu mọi thứ đều chuyển sang queue, user flow cần phản hồi tức thì có thể trở nên khó hiểu và phải xử lý nhiều trạng thái “đang xử lý”.

**Ví dụ thực tế:**
```text
Checkout cần xác nhận giá hiện tại
-> synchronous call tới Pricing

Sau khi order tạo thành công:
-> publish OrderCreated
-> Email / Analytics / Loyalty xử lý async
```

Không cần buộc các downstream không ảnh hưởng trực tiếp tới response phải nằm trên critical path.

**Trade-off:**
Synchronous flow đơn giản hơn về consistency và error propagation nhưng coupling về availability/latency cao hơn. Async messaging tăng resilience và decoupling nhưng thêm duplicate delivery, observability, retry, ordering và eventual consistency.

**Middle → Senior insight:**
Middle developer cần biết dependency nào thực sự phải hoàn tất trước khi trả response. Senior / Technical developer phải phân loại business criticality, consistency SLA, failure semantics và operational cost để chọn communication style cho từng boundary, không dùng một pattern cho mọi integration.

### Design 2 — Azure Functions và Worker Service phù hợp với hai operational model khác nhau

**Khái niệm:**
Azure Functions tối ưu cho event-driven execution và managed scaling; .NET Worker Service phù hợp hơn khi application cần process dài hạn, lifecycle chủ động, resource reservation ổn định hoặc background loop phức tạp.

**Vấn đề nó giải quyết:**
Một team cần xử lý message, scheduled jobs và background workflow. Nếu chọn Functions chỉ vì “serverless” nhưng workload chạy liên tục, startup/runtime constraint và cost model có thể kém phù hợp. Ngược lại, dùng Worker Service cho bursty event nhỏ có thể phải vận hành hạ tầng nhiều hơn cần thiết.

**Ví dụ thực tế:**
```text
Phù hợp với Azure Functions:
- Blob uploaded -> xử lý metadata
- Timer chạy vài phút mỗi giờ
- Queue-triggered task ngắn, stateless

Phù hợp với Worker Service:
- consumer chạy 24/7 với throughput ổn định
- long-running orchestration
- cần kiểm soát concurrency/lifecycle chi tiết
```

**Trade-off:**
Functions giảm infrastructure management và scale theo event nhưng thêm platform constraints, cold-start/cost considerations và execution model đặc thù. Worker Service cho nhiều quyền kiểm soát hơn nhưng bạn phải quản lý hosting, scaling, health checks và deployment rõ ràng.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và cancellation model của platform đang dùng. Senior / Solution-oriented engineer phải so workload duration, traffic shape, scaling requirement, cost và operational ownership trước khi quyết định serverless hay long-running worker.

### Design 3 — Transaction boundary nên bao quanh invariant cần atomicity, không bao quanh toàn bộ workflow phân tán

**Khái niệm:**
Database transaction nên bảo vệ một nhóm thay đổi dữ liệu phải cùng thành công hoặc cùng rollback trong cùng transactional resource. Khi workflow đi qua external API, message broker hoặc nhiều service, cố kéo tất cả vào một transaction chung thường không thực tế hoặc quá đắt.

**Vấn đề nó giải quyết:**
Một order flow cần lưu `Order`, `OrderItems`, reserve inventory qua service khác và gửi payment request. Nếu transaction database bị giữ trong lúc chờ network call, lock duration tăng, throughput giảm và failure handling trở nên khó đoán. Nhưng nếu commit quá sớm mà không có recovery strategy, partial failure lại để system ở trạng thái dở dang.

**Ví dụ thực tế:**
```text
Local transaction:
- Insert Order
- Insert OrderItems
- Insert integration intent / state
- Commit

Sau commit:
- gọi hoặc publish bước tiếp theo
- nếu failure, retry/compensate theo workflow semantics
```

Atomicity mạnh nên giữ ở nơi invariant thực sự sống; phần distributed cần explicit state machine, idempotency hoặc compensation khi phù hợp.

**Trade-off:**
Transaction rộng giảm số trạng thái trung gian nhưng tăng lock time, contention và coupling. Transaction nhỏ tăng throughput và autonomy nhưng bắt buộc thiết kế partial failure, retry và consistency rõ ràng. Không có cách miễn phí để biến workflow phân tán thành ACID toàn cục.

**Middle → Senior insight:**
Middle developer cần đặt `SaveChanges` và transaction boundary theo use case thay vì theo từng repository call ngẫu nhiên. Senior / Technical developer phải xác định invariant nào cần atomicity tuyệt đối, phần nào chấp nhận eventual consistency, và recovery mechanism nào đủ đơn giản để vận hành lâu dài.
