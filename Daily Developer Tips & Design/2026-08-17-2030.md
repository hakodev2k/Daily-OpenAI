# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `GC.GetAllocatedBytesForCurrentThread()` để đo allocation cục bộ trước khi tối ưu

**Mẹo:**
Khi nghi một đoạn code tạo quá nhiều object tạm, có thể đo nhanh lượng managed allocation của thread hiện tại trước và sau đoạn code bằng `GC.GetAllocatedBytesForCurrentThread()`.

**Tại sao hữu ích:**
Cho một tín hiệu rẻ và trực tiếp để xác nhận optimization như loại bỏ LINQ trung gian, reuse buffer hoặc đổi parsing strategy có thực sự giảm allocation hay không.

**Ví dụ:**
```csharp
var before = GC.GetAllocatedBytesForCurrentThread();

ProcessBatch(items);

var allocated = GC.GetAllocatedBytesForCurrentThread() - before;
Console.WriteLine($"Allocated: {allocated:N0} bytes");
```

**Lưu ý:**
Đây không phải benchmark đầy đủ và chỉ đo allocation trên thread hiện tại. Async continuation có thể chuyển thread; với đánh giá nghiêm túc hãy dùng BenchmarkDotNet, profiler hoặc runtime diagnostics.

### Tip 2 — Dùng `CREATE INDEX CONCURRENTLY` khi thêm index lớn trên PostgreSQL production

**Mẹo:**
Với bảng production lớn cần tiếp tục nhận read/write trong lúc tạo index, cân nhắc `CREATE INDEX CONCURRENTLY` thay vì `CREATE INDEX` thông thường.

**Tại sao hữu ích:**
Giảm thời gian giữ lock gây block write, phù hợp với migration online trên bảng đang có traffic.

**Ví dụ:**
```sql
CREATE INDEX CONCURRENTLY IX_Orders_Status_CreatedAt
ON orders(status, created_at);
```

Sau khi hoàn tất, kiểm tra index hợp lệ trước khi phụ thuộc vào nó trong rollout tiếp theo.

**Lưu ý:**
Concurrent index build lâu hơn, tốn thêm I/O và không thể chạy bên trong transaction block thông thường. Nếu build fail, có thể để lại invalid index cần cleanup.

### Tip 3 — Dùng `git branch --contains` để biết fix đã có trong branch nào

**Mẹo:**
Khi cần xác nhận một bug fix đã được merge/backport vào `main`, `release/*` hay hotfix branch nào, dùng `git branch --contains <commit>` thay vì dò history bằng mắt.

**Tại sao hữu ích:**
Rất tiện khi xử lý production issue, backport hoặc chuẩn bị release và cần biết commit đã tồn tại ở đâu.

**Ví dụ:**
```bash
git branch --contains <commit-sha>
```

Kiểm tra cả remote branch:

```bash
git branch -r --contains <commit-sha>
```

**Lưu ý:**
Nếu fix được cherry-pick, commit SHA ở branch khác sẽ khác nên `--contains` không tìm thấy patch tương đương. Khi đó cần kiểm tra commit message, `git patch-id` hoặc diff thực tế.

### Tip 4 — Dùng `dotnet format --verify-no-changes` như một quality gate trong CI

**Mẹo:**
Nếu team đã thống nhất `.editorconfig`, chạy `dotnet format --verify-no-changes` trong CI để build fail khi code chưa tuân thủ formatting/analyzer rule có thể auto-fix.

**Tại sao hữu ích:**
Giảm comment review về whitespace/style, giữ output của developer và AI-generated code nhất quán, đồng thời phát hiện rule drift giữa IDE khác nhau.

**Ví dụ:**
```bash
dotnet format --verify-no-changes --no-restore
```

Có thể chạy sau `dotnet restore` và trước test trong pipeline.

**Lưu ý:**
Không nên để formatter thay đổi code tự động trong release pipeline rồi commit ngầm. CI nên verify; việc sửa nên diễn ra ở local hoặc PR workflow rõ ràng.

### Tip 5 — Kiểm tra file-descriptor limit khi service lỗi `Too many open files`

**Mẹo:**
Khi Linux service bắt đầu fail socket/file operation với lỗi `EMFILE` hoặc `Too many open files`, kiểm tra limit thực tế của process trước khi chỉ tăng timeout hoặc restart.

**Tại sao hữu ích:**
Giúp phân biệt leak file/socket descriptor với cấu hình `nofile` quá thấp và xác định vì sao service hoạt động bình thường lúc đầu nhưng hỏng sau thời gian dài.

**Ví dụ:**
```bash
cat /proc/<PID>/limits | grep "open files"
```

Xem descriptor đang mở:

```bash
ls /proc/<PID>/fd | wc -l
```

Kiểm tra shell limit:

```bash
ulimit -n
```

**Lưu ý:**
Chỉ tăng limit có thể che resource leak. Cần kiểm tra connection disposal, file stream, socket, watcher và library behavior nếu descriptor count tăng liên tục.

## 🧠 Software Design

### Design 1 — Read Replica chỉ hữu ích khi routing hiểu mức freshness của từng use case

**Khái niệm:**
Read Replica tách read workload khỏi primary database, nhưng mỗi replica có replication lag nên không phải mọi query đều nên được route sang replica.

**Vấn đề nó giải quyết:**
Report, search và dashboard có thể gây tải lớn lên primary, trong khi transaction path lại cần state mới nhất để giữ correctness.

**Ví dụ thực tế:**
Trang analytics có thể đọc replica với lag vài giây. Nhưng ngay sau khi user approve timesheet, endpoint kiểm tra trạng thái để phát hành payroll nên đọc primary hoặc dùng consistency token/version phù hợp.

**Trade-off:**
Replica tăng read capacity và giảm pressure trên primary, nhưng thêm replication lag, routing logic, failover complexity và nguy cơ user nhìn thấy stale data.

**Middle → Senior insight:**
Middle developer nên hiểu “read-only” không đồng nghĩa “đọc replica luôn an toàn”. Senior developer phải phân loại query theo freshness SLA, read-your-writes requirement, failover behavior và khả năng chịu stale data trước khi thiết kế routing.

### Design 2 — Append-only Audit Log khác với Business History

**Khái niệm:**
Audit log ghi lại ai làm gì, khi nào và từ đâu; business history mô tả trạng thái nghiệp vụ đã thay đổi như thế nào. Hai loại dữ liệu có mục đích và retention khác nhau.

**Vấn đề nó giải quyết:**
Nếu dùng chung một bảng history cho cả debugging, compliance và business UI, schema thường phình lớn, semantics mơ hồ và rất khó xác định dữ liệu nào được phép sửa/xóa.

**Ví dụ thực tế:**
`EmployeeSalaryChanged` trong business history có old/new salary để UI hiển thị timeline. Audit log lại ghi thêm actor, IP, request ID, permission context và timestamp bất biến phục vụ điều tra/compliance.

**Trade-off:**
Tách hai loại log làm ownership và retention rõ hơn nhưng tăng storage, ingestion và query path. Append-only log cũng cần kiểm soát PII, access và lifecycle rất chặt.

**Middle → Senior insight:**
Middle developer nên tránh coi mọi bảng `History` là audit log. Senior developer phải xác định threat model, immutability, retention, tamper evidence, access control và dữ liệu nào thực sự cần lưu cho business so với compliance.

### Design 3 — Priority Queue cần chống starvation cho công việc ưu tiên thấp

**Khái niệm:**
Priority Queue cho phép job quan trọng được xử lý trước, nhưng scheduler cần cơ chế fairness để low-priority work không bị chờ vô hạn khi high-priority traffic liên tục xuất hiện.

**Vấn đề nó giải quyết:**
Một queue FIFO duy nhất có thể làm request khẩn cấp chờ sau hàng nghìn batch job, nhưng strict priority lại có thể khiến batch/background job không bao giờ được chạy.

**Ví dụ thực tế:**
Hệ thống có ba class: `Interactive`, `Normal`, `Bulk`. Worker có thể dùng weighted scheduling như 6:3:1 thay vì luôn drain `Interactive` hoàn toàn trước khi chạm tới `Bulk`.

**Trade-off:**
Priority cải thiện latency cho workload quan trọng nhưng scheduler, metrics và capacity planning phức tạp hơn. Weight sai có thể làm backlog tích tụ âm thầm ở tier thấp.

**Middle → Senior insight:**
Middle developer nên hiểu priority không chỉ là thêm cột `Priority`. Senior developer cần thiết kế fairness, aging, quota, per-tenant isolation, backlog SLO và admission control để ưu tiên không biến thành starvation.
