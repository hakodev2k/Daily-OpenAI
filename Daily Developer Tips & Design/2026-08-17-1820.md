# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TryGetNonEnumeratedCount()` trước khi ép `IEnumerable<T>` chạy toàn bộ

**Mẹo:**
Khi cần biết kích thước của một `IEnumerable<T>`, thử `TryGetNonEnumeratedCount()` trước thay vì gọi `Count()` ngay lập tức nếu nguồn có thể là sequence đắt hoặc lazy.

**Tại sao hữu ích:**
Nếu nguồn thực chất là collection/list, runtime có thể lấy count mà không enumerate. Với pipeline lazy, bạn tránh vô tình chạy toàn bộ query chỉ để biết số lượng.

**Ví dụ:**
```csharp
if (source.TryGetNonEnumeratedCount(out var count))
{
    logger.LogInformation("Count={Count}", count);
}
else
{
    logger.LogInformation("Count is not cheaply available");
}
```

**Lưu ý:**
Method này không “tính count nhanh” cho mọi sequence. Nếu trả `false`, bạn vẫn phải quyết định có thực sự cần enumerate hay không.

### Tip 2 — Dùng `SELECT ... FOR UPDATE SKIP LOCKED` cho nhiều worker cùng claim job

**Mẹo:**
Với queue nằm trong database, nhiều worker có thể dùng row locking kết hợp `SKIP LOCKED` để claim job mà không chờ nhau trên cùng record.

**Tại sao hữu ích:**
Giảm contention và tránh hai worker cùng xử lý một job trong khi vẫn cho phép scale-out bằng nhiều consumer.

**Ví dụ:**
PostgreSQL:

```sql
SELECT id
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

Sau đó update các row đã claim trong cùng transaction.

**Lưu ý:**
Đây không tự giải quyết worker crash sau khi claim. Cần thêm lease/timeout hoặc cơ chế recover job bị bỏ dở.

### Tip 3 — Dùng `git log -G` khi cần tìm semantic change theo regex trong diff

**Mẹo:**
Nếu muốn biết commit nào đã thay đổi một pattern code, dùng `git log -G'<regex>' -p` thay vì chỉ tìm string cố định bằng `-S`.

**Tại sao hữu ích:**
Hữu dụng khi API/method đổi tên nhẹ, logic thay đổi theo pattern hoặc bạn cần tìm commit chạm vào một loại expression cụ thể.

**Ví dụ:**
```bash
git log -G'HttpClient.*Timeout' -p -- src/
```

Hoặc:

```bash
git log -G'catch\s*\(Exception' --oneline
```

**Lưu ý:**
Regex rộng có thể trả về rất nhiều commit. Thu hẹp path và pattern để kết quả có giá trị thực tế.

### Tip 4 — Dùng `dig` để tách lỗi DNS khỏi lỗi HTTP/TLS

**Mẹo:**
Khi service không gọi được domain ngoài, kiểm tra DNS từ đúng máy/container bằng `dig` trước khi đổ lỗi cho `HttpClient` hoặc certificate.

**Tại sao hữu ích:**
Giúp phát hiện nhanh DNS timeout, record sai, split-horizon DNS hoặc container dùng resolver khác máy host.

**Ví dụ:**
```bash
dig api.example.com
```

Kiểm tra resolver cụ thể:

```bash
dig @8.8.8.8 api.example.com
```

Xem trace resolution:

```bash
dig +trace api.example.com
```

**Lưu ý:**
DNS resolve thành công chưa chứng minh endpoint reachable. Sau đó vẫn cần kiểm tra routing, firewall, TCP và TLS.

### Tip 5 — Đưa analyzer vào CI thay vì chỉ trông chờ IDE cảnh báo

**Mẹo:**
Các rule quan trọng về nullability, async, security hoặc code quality nên chạy trong build/CI, không chỉ hiện warning trong Visual Studio của từng developer.

**Tại sao hữu ích:**
Đảm bảo cùng một rule được áp dụng cho mọi contributor, kể cả AI-generated code hoặc commit từ môi trường khác.

**Ví dụ:**
Trong `.csproj`:

```xml
<PropertyGroup>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  <Nullable>enable</Nullable>
</PropertyGroup>
```

Có thể kết hợp `.editorconfig` để nâng một số diagnostic thành error.

**Lưu ý:**
Không nên bật toàn bộ warning thành error một cách mù quáng trên legacy codebase. Hãy rollout theo baseline và ưu tiên rule có signal tốt.

## 🧠 Software Design

### Design 1 — Choreography hay Orchestration cho workflow nhiều service

**Khái niệm:**
Choreography để mỗi service phản ứng với event và tự quyết định bước tiếp theo. Orchestration dùng một coordinator điều khiển rõ thứ tự các bước trong workflow.

**Vấn đề nó giải quyết:**
Workflow như `Create Order → Reserve Inventory → Charge Payment → Arrange Shipping` cần phối hợp nhiều bounded context mà không dùng distributed transaction.

**Ví dụ thực tế:**
Với choreography, `OrderCreated` kích hoạt Inventory; `InventoryReserved` kích hoạt Payment; `PaymentSucceeded` kích hoạt Shipping. Với orchestration, `OrderWorkflow` gọi hoặc phát command cho từng bước và giữ state tiến trình.

**Trade-off:**
Choreography giảm central coordinator và coupling trực tiếp nhưng flow dễ bị phân tán, khó quan sát và khó reasoning khi nhiều nhánh. Orchestration làm flow rõ, compensation dễ quản lý hơn nhưng coordinator trở thành component quan trọng cần scale và maintain.

**Middle → Senior insight:**
Middle developer nên hiểu event-driven không đồng nghĩa mọi workflow phải choreography. Senior developer cần chọn theo độ dài workflow, số nhánh, compensation, observability và ownership thay vì theo sở thích kiến trúc.

### Design 2 — Noisy Neighbor Isolation trong multi-tenant system

**Khái niệm:**
Noisy Neighbor Isolation giới hạn việc một tenant hoặc workload tiêu thụ quá nhiều CPU, connection, queue capacity hoặc external quota khiến tenant khác bị ảnh hưởng.

**Vấn đề nó giải quyết:**
Một tenant chạy bulk import lớn có thể chiếm toàn bộ worker pool hoặc database connections, làm request bình thường của tenant khác timeout.

**Ví dụ thực tế:**
Thay vì một global queue duy nhất, hệ thống có thể áp dụng per-tenant concurrency limit, weighted queue hoặc quota riêng cho export/import nặng.

**Trade-off:**
Isolation tăng fairness và reliability nhưng làm scheduler, quota state và capacity planning phức tạp hơn. Partition quá cứng cũng có thể lãng phí tài nguyên khi tenant khác đang idle.

**Middle → Senior insight:**
Middle developer nên nhận ra resource saturation cần nhìn theo tenant/workload class. Senior developer phải thiết kế fairness, burst policy, premium tier, shared spare capacity và telemetry để biết ai đang gây pressure.

### Design 3 — `PATCH` chỉ phù hợp khi partial update semantics thật sự rõ

**Khái niệm:**
Partial update cho phép client chỉ gửi field muốn thay đổi, nhưng API phải định nghĩa rõ khác biệt giữa “field không gửi”, “field = null” và “reset về default”.

**Vấn đề nó giải quyết:**
Nếu dùng `PUT` với object lớn, client có thể phải gửi lại dữ liệu không liên quan và vô tình overwrite field mới. Nhưng `PATCH` mơ hồ có thể tạo bug nếu semantics từng field không rõ.

**Ví dụ thực tế:**
Cập nhật employee profile:

```json
{
  "displayName": "Ha Dinh"
}
```

Nếu `managerId` không xuất hiện thì giữ nguyên. Nếu cần xóa manager, contract phải định nghĩa rõ `managerId: null` có nghĩa gì.

**Trade-off:**
Partial update giảm payload và accidental overwrite nhưng validation, authorization theo field và audit phức tạp hơn. Full replacement đơn giản hơn nếu resource nhỏ và client luôn sở hữu toàn bộ representation.

**Middle → Senior insight:**
Middle developer nên phân biệt omitted field với explicit null. Senior developer cần thiết kế patch semantics, concurrency control bằng ETag/version, field-level authorization và compatibility khi resource model tiến hóa.
