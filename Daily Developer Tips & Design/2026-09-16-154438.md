# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `DbContext` sống lâu hơn một business operation

**Mẹo:**
Giữ `DbContext` theo unit-of-work ngắn, thường tương ứng một request hoặc một message handling operation; tránh cache hoặc giữ context trong singleton/background loop dài hạn.

**Tại sao hữu ích:**
`DbContext` giữ change tracker và không thread-safe. Context sống quá lâu làm tracked entities tích lũy, tăng memory, khiến `DetectChanges` tốn hơn và dễ ghi nhầm state cũ. Trong background worker, scope mới cho từng message giúp transaction/state boundary rõ ràng.

**Ví dụ:**
```csharp
public async Task ProcessAsync(Message message, CancellationToken ct)
{
    await using var scope = _scopeFactory.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

    var order = await db.Orders.SingleAsync(x => x.Id == message.OrderId, ct);
    order.MarkProcessed();
    await db.SaveChangesAsync(ct);
}
```

**Lưu ý:**
Không tạo context mới cho từng repository call trong cùng business transaction; như vậy lại phá transaction boundary và identity tracking cần thiết.

### Tip 2 — Đo connection-pool exhaustion trước khi tăng pool size

**Mẹo:**
Khi API timeout và database connections cạn, kiểm tra thời gian giữ connection, query latency và transaction duration trước khi tăng `Max Pool Size`.

**Tại sao hữu ích:**
Pool exhaustion thường là triệu chứng: slow query, transaction mở quá lâu, streaming reader chưa dispose hoặc traffic vượt khả năng database. Tăng pool có thể chỉ chuyển bottleneck xuống SQL Server và làm database quá tải mạnh hơn.

**Ví dụ:**
```text
Symptom: request timeout tăng
Evidence: wait-for-connection tăng, DB CPU 45%
Hypothesis: connection bị giữ lâu
Diagnosis: transaction gọi external HTTP trước Commit
Fix: đưa external call ra khỏi DB transaction
```

**Lưu ý:**
Pool size vẫn là tuning parameter hợp lệ khi concurrency thực sự cần thiết và database còn capacity; nhưng phải dựa trên telemetry thay vì dùng như first fix.

### Tip 3 — Với Elasticsearch, filter điều kiện chính xác thay vì đưa mọi thứ vào full-text query

**Mẹo:**
Các điều kiện exact như `status`, `tenantId`, date range nên nằm trong filter context; chỉ dùng full-text query cho trường cần relevance scoring.

**Tại sao hữu ích:**
Filter không cần tính relevance score và thể hiện đúng intent. Một search sản phẩm thường cần text relevance cho tên/mô tả nhưng category, availability và tenant chỉ là điều kiện boolean.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "name": "wireless keyboard" } }],
      "filter": [
        { "term": { "status": "active" } },
        { "term": { "tenantId": "t-42" } }
      ]
    }
  }
}
```

**Lưu ý:**
Mapping phải đúng: exact filtering thường cần `keyword`, không phải analyzed `text`. Đừng sửa query trước khi kiểm tra mapping và analyzer thực tế.

### Tip 4 — Dùng browser Network waterfall để tách frontend chậm khỏi backend chậm

**Mẹo:**
Khi page “load chậm”, mở DevTools Network và phân biệt DNS/connect/TLS, TTFB, download, request chaining và main-thread rendering trước khi tối ưu code ngẫu nhiên.

**Tại sao hữu ích:**
Một Core Web Vitals regression có thể đến từ API TTFB, JavaScript bundle lớn, ảnh blocking hoặc chuỗi request phụ thuộc. Waterfall giúp xác định thời gian thực sự nằm ở đâu.

**Ví dụ:**
```text
/document      TTFB 120 ms
/app.js        1.8 MB / 900 ms
/api/profile   starts after app.js / 350 ms
hero.webp      2.4 MB / 1.2 s
```
Ở đây chỉ tối ưu ASP.NET Core query có thể không cải thiện trải nghiệm đáng kể bằng giảm bundle và tối ưu image/loading strategy.

**Lưu ý:**
DevTools local không thay thế Real User Monitoring. CPU/network của máy developer thường khác thiết bị và mạng production.

### Tip 5 — Managed Identity tốt hơn secret tĩnh cho service-to-service access trên Azure

**Mẹo:**
Khi Azure-hosted application truy cập Key Vault, Blob Storage hoặc resource hỗ trợ Microsoft Entra authentication, ưu tiên Managed Identity và RBAC thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời secret khỏi application: không cần distribute, rotate hay vô tình log secret. SDK Azure có thể lấy token thông qua `DefaultAzureCredential` trong production và developer credential phù hợp ở local.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

**Lưu ý:**
Managed Identity không tự tạo least privilege. Phải cấp RBAC tối thiểu cần thiết và phân biệt identity giữa workloads; cấp quyền rộng ở subscription/resource group vẫn tạo blast radius lớn.

## 🧠 Software Design

### Design 1 — Repository abstraction chỉ có giá trị khi nó tạo boundary có ý nghĩa

**Khái niệm:**
EF Core `DbContext` đã cung cấp nhiều semantics của Repository và Unit of Work. Một custom Repository nên tồn tại khi nó che giấu data-access policy hoặc tạo domain/application boundary có ích, không phải chỉ để đổi tên `DbSet` methods.

**Vấn đề nó giải quyết:**
Application phức tạp có thể cần tập trung query policy, aggregate loading hoặc tách domain khỏi persistence concerns. Nhưng generic repository kiểu `GetAll/Add/Update/Delete` thường làm mất khả năng projection, composition và EF Core features mà không giảm coupling thực sự.

**Ví dụ thực tế:**
`IOrderRepository.LoadForFulfillmentAsync(orderId)` có thể diễn đạt aggregate-loading rule rõ ràng. Ngược lại `IGenericRepository<Order>.GetAll()` trả `IQueryable` chỉ chuyển `DbContext` sang một interface khác.

**Trade-off:**
Repository có thể làm boundary/testability rõ hơn nhưng thêm abstraction, mapping và API maintenance. Direct `DbContext` trong application layer thường đơn giản hơn cho CRUD/read-heavy systems.

**Middle → Senior insight:**
Middle developer cần tránh repository chỉ pass-through EF Core. Senior / Technical developer phải quyết định boundary dựa trên domain complexity, query needs, testing strategy và khả năng thay đổi persistence, thay vì áp pattern theo template.

### Design 2 — Synchronous REST vs asynchronous messaging theo failure coupling

**Khái niệm:**
REST phù hợp khi caller cần kết quả ngay và hai bên có thể chịu temporal coupling. Messaging phù hợp khi workflow chấp nhận eventual completion và cần hấp thụ burst hoặc cô lập failure.

**Vấn đề nó giải quyết:**
Một checkout gọi tuần tự Inventory, Email và Analytics khiến latency/failure của các service phụ làm request chính thất bại. Nhưng chuyển mọi call sang queue lại làm workflow khó quan sát và không phù hợp khi user cần câu trả lời tức thời.

**Ví dụ thực tế:**
Kiểm tra giá hiện tại trước checkout có thể là synchronous call. Sau khi order đã được commit, gửi confirmation email và analytics events có thể asynchronous vì user không cần chờ chúng hoàn tất.

**Trade-off:**
REST đơn giản về request-response và consistency tức thời nhưng tăng temporal coupling. Messaging tăng resilience và buffering nhưng thêm duplicate delivery, ordering, retries, DLQ, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần hiểu timeout/retry cho REST và idempotency cho consumer. Senior / Technical developer phải phân loại operation theo latency requirement, consistency, ownership và failure semantics; không chọn messaging chỉ vì “microservices nên event-driven”.

### Design 3 — Observability là một phần của architecture contract

**Khái niệm:**
Một component production-ready không chỉ có functional API; nó còn cần telemetry đủ để trả lời request nào lỗi, dependency nào chậm, backlog ở đâu và deployment nào tạo regression.

**Vấn đề nó giải quyết:**
Hệ thống có thể pass test nhưng khi latency tăng production, team chỉ có log text rời rạc và không nối được request → SQL → external API → message processing. Khi đó mean time to recovery phụ thuộc đoán mò.

**Ví dụ thực tế:**
Order flow chuẩn hóa trace context qua HTTP/message headers, structured logs chứa operation/result, metrics theo bounded-cardinality dimensions và dashboard theo latency/error/backlog. Alert dựa trên user-impact signal thay vì chỉ CPU threshold.

**Trade-off:**
Telemetry tốt giảm thời gian điều tra và hỗ trợ capacity/reliability decisions nhưng tăng ingestion cost, instrumentation effort và rủi ro sensitive-data leakage nếu tagging thiếu kiểm soát.

**Middle → Senior insight:**
Middle developer cần instrument operation và giữ trace/log correlation đúng. Senior / Technical developer phải thiết kế telemetry contract, cardinality budget, sampling, retention, SLO/alerts và privacy để observability vẫn hữu ích khi hệ thống scale.
