# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Chặn cache stampede thay vì chỉ tăng Redis TTL

**Mẹo:**
Khi một cache key rất nóng hết hạn, đừng để hàng trăm request cùng miss rồi đồng thời query SQL. Dùng request coalescing/single-flight trong từng instance, TTL có jitter, hoặc cơ chế distributed coordination khi workload thực sự cần.

**Tại sao hữu ích:**
Cache stampede biến một lần expiry thành burst tải lên source of truth. Redis vẫn khỏe nhưng database có thể bị quá tải vì mọi application instance cùng tái tạo một giá trị đắt tiền. Jitter làm các key không hết hạn cùng thời điểm; single-flight giảm số lần recompute trong cùng process.

**Ví dụ:**
Một endpoint product catalog có key `catalog:home` nhận 2.000 req/s. Khi key hết hạn, thay vì 2.000 request cùng chạy query aggregation, một request rebuild cache còn các request cùng instance chờ cùng task. TTL 5 phút có thêm jitter ngẫu nhiên nhỏ để tránh nhiều key đồng loạt expire.

**Lưu ý:**
Distributed lock không phải mặc định tốt nhất: lock timeout, owner crash và contention tạo failure mode mới. Với dữ liệu cho phép stale, stale-while-revalidate hoặc serving stale data khi backend lỗi có thể đơn giản và ổn định hơn.

### Tip 2 — Dùng `git bisect` để tìm commit gây regression

**Mẹo:**
Khi biết một phiên bản tốt và một phiên bản lỗi, dùng `git bisect` để thu hẹp commit gây regression theo binary search thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Với lịch sử 128 commit, binary search thường chỉ cần khoảng 7 lần phân loại good/bad. Nếu có test hoặc script tái hiện lỗi, `git bisect run` còn biến việc điều tra thành quy trình có thể lặp lại.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.8.0
git bisect run dotnet test tests/Regression.Tests --filter CheckoutLatencyRegression
git bisect reset
```
Một regression về serialization sau release có thể được khoanh vùng tới commit đổi converter thay vì suy đoán từ diff lớn.

**Lưu ý:**
Bisect chỉ đáng tin khi phép thử deterministic. Flaky test, migration database không tương thích giữa commit hoặc build environment thay đổi có thể đánh dấu sai commit; khi đó cần ổn định reproduction trước.

### Tip 3 — Elasticsearch mapping phải phản ánh cách search, không chỉ schema nguồn

**Mẹo:**
Thiết kế field theo search behavior: dùng `text` cho full-text analysis, `keyword` cho exact match/filter/aggregation và multi-field khi cùng dữ liệu cần cả hai cách truy vấn.

**Tại sao hữu ích:**
Elasticsearch xây inverted index dựa trên mapping và analyzer. Nếu product name chỉ là `keyword`, search theo từ tự nhiên kém hiệu quả; nếu status chỉ là `text`, filter/aggregation có thể không mang semantics mong muốn.

**Ví dụ:**
```json
"name": {
  "type": "text",
  "fields": {
    "raw": { "type": "keyword" }
  }
},
"status": { "type": "keyword" }
```
Search dùng `name`; sorting/aggregation exact có thể dùng `name.raw`.

**Lưu ý:**
Thay mapping của field đã index thường không phải thao tác in-place đơn giản; nhiều thay đổi cần tạo index mới, reindex và chuyển alias. Vì vậy mapping evolution phải tính cả rollout, storage và thời gian đồng bộ.

### Tip 4 — Rate limit theo tài nguyên cần bảo vệ, không chỉ theo IP

**Mẹo:**
Trong ASP.NET Core, chọn partition key của rate limiter theo abuse model và resource pressure: authenticated user, tenant, API key hoặc endpoint class thường có ý nghĩa hơn chỉ dùng client IP.

**Tại sao hữu ích:**
Nhiều người dùng hợp lệ có thể chung NAT/proxy nên per-IP limit gây false positive; ngược lại attacker có thể phân tán IP. Rate limiting hiệu quả phải bảo vệ dependency cụ thể như expensive search, login hoặc report generation.

**Ví dụ:**
Một SaaS API cho phép tenant thường chạy tối đa 20 report requests/phút, trong khi read endpoint nhẹ có budget cao hơn. Policy được gắn theo endpoint và partition theo tenant ID đã xác thực, đồng thời trả `429 Too Many Requests` khi vượt giới hạn.

**Lưu ý:**
Rate limiting không thay authorization, quota/billing hay DDoS protection ở edge. Nếu application chạy nhiều replicas, in-memory limiter chỉ thấy traffic của từng instance; global quota cần coordination hoặc enforcement ở gateway phù hợp.

### Tip 5 — Đo cache headers của CMS/CDN bằng request thật

**Mẹo:**
Khi Optimizely CMS hoặc website sau CDN phục vụ content cũ, kiểm tra `Cache-Control`, `Age`, `ETag`, `Vary` và response headers của CDN trước khi xóa cache hàng loạt.

**Tại sao hữu ích:**
Stale content có thể nằm ở browser, CDN, reverse proxy hoặc application cache. Purge sai tầng vừa không sửa lỗi vừa làm cache hit ratio tụt và tạo origin traffic spike.

**Ví dụ:**
Editor publish banner mới nhưng một số user vẫn thấy bản cũ. Response có `Age: 1700` và CDN cache HIT trong khi origin đã trả nội dung mới. Evidence này chuyển hướng điều tra sang invalidation/cache key ở delivery layer thay vì CMS database.

**Lưu ý:**
Không đặt `no-store` cho toàn site chỉ để tránh stale content. Bạn sẽ mất lợi ích CDN/browser caching. Xác định rõ content nào public, personalized, versioned hoặc cần purge khi publish.

## 🧠 Software Design

### Design 1 — Synchronous REST vs asynchronous messaging theo failure semantics

**Khái niệm:**
REST đồng bộ phù hợp khi caller cần kết quả ngay trong cùng interaction; messaging bất đồng bộ phù hợp khi công việc có thể được chấp nhận trước và hoàn tất sau. Quyết định không nên dựa đơn thuần vào việc “microservices nên dùng message”.

**Vấn đề nó giải quyết:**
Chuỗi synchronous calls dài làm latency cộng dồn và khiến partial failure lan ngược về caller. Nhưng chuyển mọi thứ sang queue lại tạo eventual consistency, khó theo dõi trạng thái và thay đổi UX/API contract.

**Ví dụ thực tế:**
Checkout cần kiểm tra giá hiện tại trước khi xác nhận order nên một số validation có thể synchronous. Sau khi order đã commit, gửi email và analytics không cần chặn response; chúng phù hợp với integration events qua Azure Service Bus.

**Trade-off:**
Synchronous flow đơn giản về request/response và consistency tức thời nhưng nhạy với latency/availability dependency. Asynchronous flow giảm temporal coupling và hấp thụ burst tốt hơn nhưng thêm broker, duplicate delivery, idempotency, DLQ, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần xử lý timeout/cancellation ở REST và idempotency/retry ở messaging. Senior / Technical developer phải xác định business operation nào thực sự cần immediate answer, failure nào được phép deferred, SLA nào áp dụng và complexity vận hành nào team có khả năng sở hữu.

### Design 2 — CQRS chỉ khi read/write pressure thực sự khác nhau

**Khái niệm:**
CQRS tách model hoặc path xử lý command khỏi query khi hai phía có nhu cầu khác đáng kể. Nó không bắt buộc phải có hai database, Event Sourcing hay một framework mediator.

**Vấn đề nó giải quyết:**
Một domain write model giàu invariant có thể không phù hợp cho dashboard cần join/aggregate dữ liệu theo shape hoàn toàn khác. Ép cùng một model phục vụ cả hai phía dễ làm domain hoặc query trở nên phức tạp.

**Ví dụ thực tế:**
Order command dùng relational transaction để bảo vệ inventory reservation và trạng thái. Dashboard vận hành đọc projection tối ưu riêng, được cập nhật từ events và chấp nhận trễ vài giây. Query path không cần hydrate aggregate chỉ để hiển thị bảng thống kê.

**Trade-off:**
CQRS cho phép tối ưu và evolve read/write độc lập nhưng thêm model duplication, synchronization, eventual consistency và operational debugging. Với CRUD thông thường, projection trực tiếp từ EF Core có thể rẻ và rõ ràng hơn rất nhiều.

**Middle → Senior insight:**
Middle developer cần hiểu command/query semantics và không để query vô tình mutate state. Senior / Technical developer phải chứng minh pressure đủ lớn trước khi tách model/storage, xác định freshness SLA, rebuild strategy và cách vận hành khi projection bị lag hoặc sai.

### Design 3 — Direct-to-Blob upload vs proxy file qua backend

**Khái niệm:**
Với file lớn, client có thể upload trực tiếp tới Azure Blob Storage bằng quyền hạn ngắn hạn như SAS được backend cấp, thay vì bắt toàn bộ byte stream đi qua ASP.NET Core. Backend vẫn kiểm soát authorization và metadata/business workflow.

**Vấn đề nó giải quyết:**
Proxy mọi upload qua API làm application chịu bandwidth, connection duration, memory/buffer pressure và scaling cost dù nhiệm vụ chính chỉ là chuyển byte sang storage.

**Ví dụ thực tế:**
Mobile app xin upload session cho video 500 MB. Backend xác thực user, tạo blob name server-side và cấp SAS chỉ cho phép write trong thời gian ngắn. Client upload trực tiếp; sau đó backend xác nhận metadata hoặc xử lý event khi blob xuất hiện.

**Trade-off:**
Direct upload giảm tải application và scale data plane tốt hơn, nhưng tăng complexity ở CORS, SAS scope/expiry, orphan files, validation và workflow completion. Backend proxy đơn giản hơn về policy enforcement và phù hợp file nhỏ hoặc yêu cầu inspection inline.

**Middle → Senior insight:**
Middle developer cần cấp quyền tối thiểu, giới hạn file/type/size và xử lý upload failure an toàn. Senior / Technical developer phải thiết kế control plane so với data plane, threat model, malware scanning, lifecycle cleanup, observability và quyết định khi nào lợi ích bandwidth đủ để biện minh cho flow phức tạp hơn.
