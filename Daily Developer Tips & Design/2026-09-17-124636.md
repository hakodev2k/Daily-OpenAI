# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — `TimeProvider` giúp test logic thời gian mà không chờ clock thật

**Mẹo:**
Với .NET 8+, inject `TimeProvider` cho logic phụ thuộc thời gian thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi.

**Tại sao hữu ích:**
Clock toàn cục làm test expiry, retry window hoặc scheduled behavior phụ thuộc thời gian thực và dễ flaky. `TimeProvider` biến clock thành dependency có thể kiểm soát, đồng thời giữ production code dùng system time chuẩn.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        clock.GetUtcNow() >= expiresAt;
}
```
Trong test, dùng fake time provider để advance clock thay vì `Task.Delay` hoặc chỉnh timestamp thủ công khắp test.

**Lưu ý:**
Đừng tạo abstraction `IClock` riêng nếu `TimeProvider` đã đáp ứng nhu cầu. Với business timezone, vẫn phải tách rõ instant UTC khỏi calendar/time-zone rules; fake clock không sửa được modeling sai.

### Tip 2 — SQL Server blocking: tìm blocker trước khi tăng command timeout

**Mẹo:**
Khi API database call đột nhiên timeout, kiểm tra wait type, blocking session và transaction duration trước khi tăng `CommandTimeout`.

**Tại sao hữu ích:**
Query vốn chạy 50 ms có thể chờ 30 giây vì một transaction khác giữ lock. Tăng timeout chỉ làm request giữ connection lâu hơn và có thể đẩy hệ thống tới connection-pool exhaustion mà không xử lý nguyên nhân.

**Ví dụ:**
```text
Symptom: UPDATE Orders timeout
Evidence: request wait = LCK_M_X
Blocker: session 81, transaction age = 45s
Hypothesis: transaction giữ lock quá lâu
Diagnosis: external HTTP call nằm bên trong DB transaction
Solution: thu hẹp transaction boundary, rồi đánh giá index/isolation nếu vẫn cần
```

**Lưu ý:**
Không kill blocker theo phản xạ trên production. Xác định ownership và rollback cost trước; blocking có thể là hành vi ACID hợp lệ, còn vấn đề thật là transaction scope hoặc access pattern.

### Tip 3 — Redis TTL cần jitter để tránh synchronized expiration

**Mẹo:**
Khi nhiều cache keys được tạo cùng lúc với cùng TTL, thêm một lượng jitter hợp lý vào expiration để tránh chúng hết hạn đồng loạt.

**Tại sao hữu ích:**
Một deployment hoặc warm-up job có thể populate hàng nghìn keys cùng thời điểm. Nếu tất cả TTL 10 phút, phút thứ 10 có thể tạo burst cache miss và dồn traffic xuống database/API, dù cache bình thường có hit ratio cao.

**Ví dụ:**
```csharp
var ttl = TimeSpan.FromMinutes(10)
          + TimeSpan.FromSeconds(Random.Shared.Next(0, 60));

await cache.SetStringAsync(key, payload,
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = ttl
    }, ct);
```

**Lưu ý:**
Jitter chỉ phân tán expiration; nó không thay thế single-flight/stampede protection cho hot key. Với dữ liệu có expiry business chính xác, không được tùy tiện làm lệch thời hạn hợp lệ.

### Tip 4 — OpenAPI contract nên được kiểm tra trong CI, không chỉ mở Swagger UI bằng mắt

**Mẹo:**
Export OpenAPI document trong pipeline và chạy contract/lint hoặc breaking-change check trước khi merge API thay đổi.

**Tại sao hữu ích:**
Rename field, đổi nullable thành required hoặc thay response schema có thể compile và unit test vẫn xanh nhưng phá mobile/client đã deploy. Contract diff biến API evolution thành signal kiểm tra được thay vì phụ thuộc reviewer nhớ toàn bộ consumer contract.

**Ví dụ:**
```text
PR thay đổi:
response.customerName -> response.displayName

CI:
1. generate openapi.json
2. compare với contract baseline
3. flag breaking schema change
4. yêu cầu migration/versioning decision
```

**Lưu ý:**
Schema diff không hiểu toàn bộ business semantics. Một thay đổi “non-breaking” về JSON shape vẫn có thể phá consumer nếu meaning, enum behavior hoặc ordering assumptions thay đổi; cần contract tests cho integration quan trọng.

### Tip 5 — `dotnet-counters` dùng để phân loại incident trước khi attach profiler nặng

**Mẹo:**
Khi .NET service chậm hoặc memory tăng, dùng runtime counters để xác định hướng điều tra trước: CPU, allocation rate, GC heap, ThreadPool queue hoặc exception rate.

**Tại sao hữu ích:**
Profiler/trace sâu tạo nhiều dữ liệu và đôi khi có overhead. Counters cho tín hiệu nhanh để phân biệt CPU saturation với GC pressure hoặc ThreadPool starvation, giúp chọn công cụ tiếp theo đúng hơn.

**Ví dụ:**
```bash
dotnet-counters monitor -p <PID> System.Runtime
```
Nếu CPU thấp nhưng ThreadPool queue tăng và thread count leo dần, điều tra blocking sync-over-async/I/O trước khi tối ưu thuật toán CPU.

**Lưu ý:**
Counters là evidence định hướng, không phải root cause. Allocation rate cao chưa nói object nào gây ra nó; sau bước phân loại vẫn có thể cần `dotnet-trace`, dump hoặc profiler.

## 🧠 Software Design

### Design 1 — Pessimistic locking chỉ hợp khi conflict cost biện minh cho việc chờ

**Khái niệm:**
Pessimistic concurrency giữ lock để ngăn concurrent writers tiến vào vùng dữ liệu cần bảo vệ, thay vì cho phép cùng làm rồi phát hiện conflict ở cuối như optimistic concurrency.

**Vấn đề nó giải quyết:**
Một workflow phân bổ inventory cực khan hiếm có conflict cao; nhiều request cùng đọc stock rồi liên tục thất bại/retry ở optimistic write có thể tạo retry storm và wasted work.

**Ví dụ thực tế:**
Trong một transaction rất ngắn, service lock inventory row, kiểm tra quantity, decrement và commit. Không gọi payment/external API trong lúc lock; side effect dài được xử lý ngoài critical section bằng workflow phù hợp.

**Trade-off:**
Pessimistic locking giảm conflict retry và đơn giản hóa một số invariant cục bộ, nhưng tăng blocking, deadlock risk và giảm concurrency. Lock dài qua user interaction hoặc network call là thiết kế nguy hiểm.

**Middle → Senior insight:**
Middle developer cần hiểu isolation/lock duration và giữ transaction ngắn. Senior / Technical developer phải định lượng conflict rate, contention, retry cost và invariant scope để chọn optimistic, pessimistic hay atomic database operation; “dữ liệu quan trọng” không tự động đồng nghĩa phải lock.

### Design 2 — Headless CMS tách content delivery khỏi rendering nhưng tăng integration ownership

**Khái niệm:**
Headless CMS quản lý content và expose qua API, còn website/mobile/frontend sở hữu rendering. Boundary này hữu ích khi cùng content cần nhiều channels hoặc frontend release cadence độc lập với CMS presentation layer.

**Vấn đề nó giải quyết:**
Một doanh nghiệp cần dùng cùng campaign/product editorial content cho website Vue/React, mobile app và kiosk. Coupling content vào server-rendered CMS templates khiến mỗi channel phải đi qua cùng rendering stack.

**Ví dụ thực tế:**
Optimizely quản lý content model/editor workflow; delivery API trả structured content. Web frontend render SSR/CSR theo nhu cầu SEO, mobile dùng cùng content contract nhưng presentation riêng. Preview và cache invalidation được thiết kế như capability rõ ràng.

**Trade-off:**
Headless tăng channel flexibility và frontend autonomy nhưng chuyển complexity sang API contract, preview, personalization, cache, localization và frontend orchestration. Với một website đơn giản, traditional CMS rendering có thể rẻ và dễ vận hành hơn.

**Middle → Senior insight:**
Middle developer cần xử lý content contract, fallback và caching đúng. Senior / Technical developer phải đánh giá số channels, editorial experience, SEO, personalization, latency, ownership và deployment topology trước khi chọn headless; không chọn chỉ vì frontend framework hiện đại.

### Design 3 — Retry policy phải dựa trên failure semantics, không phải số lần cố định

**Khái niệm:**
Retry chỉ phù hợp với transient failure và operation có semantics an toàn khi thực hiện lại. Policy phải xét loại lỗi, idempotency, timeout budget và backoff thay vì `retry 3 lần` cho mọi exception.

**Vấn đề nó giải quyết:**
Một external API trả `503` ngắn hạn có thể thành công ở lần sau, nhưng retry `400`, authentication failure hoặc non-idempotent payment command có thể tăng tải hoặc tạo side effect trùng lặp.

**Ví dụ thực tế:**
Catalog GET có thể retry một số network/5xx failures với exponential backoff + jitter trong latency budget. Payment POST chỉ retry khi provider hỗ trợ idempotency key và failure state đủ rõ; ambiguous timeout cần reconciliation thay vì gửi lại mù.

**Trade-off:**
Retry cải thiện resilience trước lỗi tạm thời nhưng tăng latency, downstream load và duplicate risk. Backoff giảm synchronized retries nhưng vẫn không cứu dependency outage kéo dài; circuit breaker/load shedding có thể cần ở cấp hệ thống.

**Middle → Senior insight:**
Middle developer cần classify retryable result và propagate cancellation/timeout. Senior / Technical developer phải thiết kế end-to-end retry ownership để tránh mỗi layer tự retry, tính retry amplification, idempotency và recovery path cho kết quả không xác định.
