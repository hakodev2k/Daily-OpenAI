# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `dotnet-counters` để phân biệt GC pressure với memory leak

**Mẹo:**
Khi memory của ASP.NET Core tăng, đừng kết luận ngay là memory leak. Quan sát runtime counters như GC Heap Size, Allocation Rate, Gen 2 GC Count và Working Set để xác định process đang allocation mạnh nhưng GC vẫn reclaim được hay object thực sự sống lâu bất thường.

**Tại sao hữu ích:**
Working Set tăng có thể đến từ managed heap, native memory, JIT, buffers hoặc runtime giữ memory để tái sử dụng. Nếu allocation rate rất cao nhưng heap giảm sau GC, vấn đề có thể là allocation pressure gây CPU/latency chứ không phải leak. Ngược lại, heap sau các Gen 2 GC vẫn tăng đều là evidence đáng điều tra sâu hơn.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 18420 System.Runtime
```

Một incident có thể được reasoning theo chuỗi:

```text
Working Set tăng
-> GC Heap Size tăng sau nhiều Gen 2 GC
-> capture dump
-> inspect retained object graph
-> tìm singleton giữ cache không giới hạn
```

**Lưu ý:**
Một snapshot memory đơn lẻ hiếm khi chứng minh leak. Cần quan sát xu hướng theo thời gian và workload. `dotnet-counters` giúp triage nhanh nhưng để tìm retention root thường vẫn cần dump/profiler như `dotnet-dump`, Visual Studio Profiler hoặc công cụ tương đương.

### Tip 2 — Dùng keyset pagination khi OFFSET lớn trở thành bottleneck

**Mẹo:**
Với danh sách lớn được sort ổn định, cân nhắc keyset/seek pagination thay vì `OFFSET ... FETCH` hoặc `Skip()` với page number ngày càng lớn. Client gửi khóa cuối của page trước để database tiếp tục từ vị trí đó.

**Tại sao hữu ích:**
Offset pagination thường buộc database đi qua hoặc sort nhiều row trước khi bỏ chúng đi. Page 10.000 vì vậy có thể đắt hơn page 1 rất nhiều. Keyset pagination cho phép index seek từ boundary gần vị trí cần đọc.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)` tùy filter và workload thực tế.

**Lưu ý:**
Keyset pagination không phù hợp nếu UX bắt buộc nhảy trực tiếp tới page 437 theo số trang. Sort phải deterministic; nếu chỉ sort theo `CreatedAt` có giá trị trùng, cần tie-breaker như `Id`. Cursor cũng nên được validate thay vì tin dữ liệu client gửi lên.

### Tip 3 — Azure Service Bus lock expiration có thể tạo duplicate processing dù handler vẫn đang chạy

**Mẹo:**
Khi xử lý message lâu, theo dõi `LockDuration`, auto lock renewal và thời gian thực thi handler. Nếu message lock hết hạn trước khi hoàn tất, broker có thể giao lại message cho consumer khác trong khi consumer đầu vẫn tiếp tục side effect.

**Tại sao hữu ích:**
At-least-once delivery nghĩa là duplicate không chỉ xuất hiện khi code throw exception. Một handler gọi external API 90 giây nhưng lock chỉ tồn tại 30 giây có thể tạo hai execution đồng thời nếu lock không được renew đúng cách.

**Ví dụ:**
```text
00s Consumer A nhận PaymentRequested
30s lock hết hạn
35s Consumer B nhận lại cùng message
60s A charge payment thành công
65s B cũng chuẩn bị charge
```

Thiết kế consumer idempotent theo `MessageId` hoặc business operation identity giúp ngăn side effect lặp ngay cả khi redelivery xảy ra.

**Lưu ý:**
Tăng lock duration vô hạn chỉ che giấu handler quá chậm. Với work dài, cân nhắc tách orchestration, checkpoint hoặc background workflow phù hợp. Auto-renew cũng có giới hạn và không thay thế idempotency.

### Tip 4 — Trong Vue, tránh deep watcher cho object lớn nếu chỉ cần theo dõi vài dependency

**Mẹo:**
Khi component có state lớn, ưu tiên `computed`, watcher trên getter cụ thể hoặc tách state thay vì `watch(..., { deep: true })` cho toàn bộ object chỉ để phản ứng với một vài field.

**Tại sao hữu ích:**
Deep watcher phải traverse nested properties để theo dõi thay đổi. Với form/CMS editor lớn hoặc state chứa nhiều item, việc này có thể tạo work không cần thiết và làm khó xác định chính xác dependency nào thực sự kích hoạt side effect.

**Ví dụ:**
```ts
watch(
  () => [filters.categoryId, filters.sortBy],
  () => reloadProducts()
)
```

thay vì:

```ts
watch(filters, reloadProducts, { deep: true })
```

khi `reloadProducts()` chỉ phụ thuộc hai field trên.

**Lưu ý:**
Deep watcher vẫn hợp lý khi requirement thực sự là phản ứng với mọi nested change. Đừng tối ưu theo cảm giác; dùng Vue DevTools/browser profiler nếu UI thực sự có performance issue và nhớ debounce/cancel network request khi watcher có thể fire nhanh.

### Tip 5 — Không đưa secret vào Docker image layer dù đã xóa ở layer sau

**Mẹo:**
Không `COPY` secret, `.env`, certificate private key hoặc package credential vào Docker image rồi xóa ở một `RUN` tiếp theo. Dữ liệu có thể vẫn tồn tại trong layer trước của image history. Dùng build secrets, runtime secret injection hoặc identity-based authentication phù hợp.

**Tại sao hữu ích:**
Docker image là chuỗi immutable layers. Việc tạo file ở layer A rồi xóa ở layer B không nhất thiết loại bytes khỏi layer A. Nếu image được push lên registry, credential có thể bị trích xuất dù container cuối cùng không nhìn thấy file đó.

**Ví dụ:**
```dockerfile
# Tránh
COPY NuGet.Config /root/.nuget/NuGet.Config
RUN dotnet restore
RUN rm /root/.nuget/NuGet.Config
```

Với BuildKit, có thể mount secret chỉ trong build step hoặc dùng credential provider phù hợp để secret không trở thành nội dung của image layer.

**Lưu ý:**
Multi-stage build giảm nhiều artifact không cần thiết nhưng không tự biến cách xử lý secret sai thành an toàn. Đồng thời kiểm tra build logs và CI variables vì secret còn có thể bị lộ qua command output dù image sạch.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer cần deduplicate message một cách bền vững

**Khái niệm:**
Inbox Pattern lưu identity của message đã xử lý vào persistent store, thường cùng transaction với business state mà consumer thay đổi. Khi cùng message được giao lại, consumer nhận biết nó đã hoàn tất và không thực hiện side effect lần nữa.

**Vấn đề nó giải quyết:**
Message broker thường cung cấp at-least-once delivery. Consumer có thể cập nhật database thành công rồi crash trước khi complete/ack message. Broker sau đó redeliver, khiến cùng command được xử lý lần hai.

**Ví dụ thực tế:**
```text
Receive OrderPaid message M-812

DB transaction:
1. nếu Inbox(M-812) tồn tại -> bỏ qua
2. UPDATE Orders SET PaymentStatus = 'Paid'
3. INSERT Inbox(MessageId='M-812')
4. COMMIT

5. complete message trên broker
```

Nếu process crash sau bước 4, lần redelivery tiếp theo thấy `M-812` trong Inbox và không cập nhật business state lần nữa.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, unique constraint, cleanup/retention và transaction cost. Deduplication theo broker `MessageId` chỉ đúng nếu producer giữ cùng identity cho retry của cùng logical message; đôi khi business idempotency key phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là normal failure mode, không phải edge case hiếm. Senior / Technical developer phải chọn deduplication identity, atomic boundary, retention window và interaction giữa Inbox, business transaction và broker acknowledgement dựa trên failure semantics thực tế.

### Design 2 — Hexagonal Architecture hữu ích khi domain cần sống độc lập với nhiều adapter

**Khái niệm:**
Hexagonal Architecture đặt application/domain behavior phía trong và giao tiếp với database, HTTP, message broker hoặc external service thông qua ports và adapters. Mục tiêu chính là dependency direction và replaceable boundaries, không phải tạo thật nhiều project/interface.

**Vấn đề nó giải quyết:**
Một pricing engine ban đầu được gọi từ REST API nhưng sau đó còn phải chạy từ Service Bus worker và batch job. Nếu business logic phụ thuộc trực tiếp `HttpContext`, EF-specific query hoặc vendor SDK, reuse và testing trở nên khó khăn.

**Ví dụ thực tế:**
```text
REST Adapter ─┐
ServiceBus Adapter ─> Pricing Application Core ─> ProductPrice Port
Batch Adapter ─┘                              └─> Promotion Port

Infrastructure adapters:
- EF Core ProductPriceRepository
- ExternalPromotionApiClient
```

Core mô tả capability cần thiết; adapter chịu trách nhiệm protocol/framework cụ thể.

**Trade-off:**
Boundary rõ giúp testability và thay integration dễ hơn, nhưng interface cho mọi class có thể tạo indirection vô ích. CRUD application nhỏ với một database có thể dùng layered architecture/direct DbContext đơn giản hơn mà vẫn maintainable.

**Middle → Senior insight:**
Middle developer cần giữ business logic khỏi framework concern không cần thiết. Senior / Solution-oriented engineer phải nhận diện boundary nào có volatility hoặc nhiều adapters đủ lớn để đáng trả abstraction cost, thay vì áp Hexagonal Architecture như template bắt buộc.

### Design 3 — Circuit Breaker bảo vệ capacity khi dependency đang thất bại liên tục

**Khái niệm:**
Circuit Breaker theo dõi failure của một dependency và tạm thời từ chối call mới khi failure vượt policy. Sau một khoảng thời gian, breaker cho một số request thử nghiệm để xác định dependency đã phục hồi hay chưa.

**Vấn đề nó giải quyết:**
Nếu external recommendation API đang timeout 10 giây, hàng nghìn request của website vẫn tiếp tục gọi nó có thể giữ socket, task và request capacity cho những call gần như chắc chắn thất bại. Retry không kiểm soát còn nhân tải lên dependency đang yếu.

**Ví dụ thực tế:**
```text
Closed:
request đi qua bình thường

5 failures liên tiếp
-> Open 30s
-> fail fast / dùng fallback

Sau 30s
-> Half-open
-> cho một số probe request
-> success: Closed
-> failure: Open lại
```

Với ASP.NET Core, policy cần được đặt quanh đúng outbound dependency và quan sát trạng thái breaker bằng telemetry.

**Trade-off:**
Circuit breaker giảm cascading failure và giải phóng capacity nhưng có thể từ chối request trong lúc dependency vừa phục hồi. Threshold quá nhạy gây false opening; threshold quá chậm không bảo vệ được hệ thống. Fallback còn có thể trả dữ liệu stale hoặc giảm chức năng.

**Middle → Senior insight:**
Middle developer cần phân biệt retry với circuit breaker: retry thử lại một operation, breaker quyết định có nên tiếp tục gửi operation mới hay không. Senior / Technical developer phải phối hợp timeout, retry, breaker, concurrency limit và fallback theo latency budget/SLO thay vì xếp nhiều resilience policy mặc định lên nhau.
