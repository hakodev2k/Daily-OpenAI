# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Sử dụng `required` trong C# để tránh object thiếu dữ liệu

**Mẹo:**
Dùng `required` property trong C# để bắt buộc caller khởi tạo các field quan trọng.

**Tại sao hữu ích:**
Giảm lỗi runtime do object không đầy đủ dữ liệu.

**Ví dụ:**
```csharp
public class UserRequest
{
    public required string Email { get; init; }
}
```

**Lưu ý:**
Không dùng cho mọi property vì có thể làm API model khó sử dụng.

### Tip 2 — Kiểm tra log correlation bằng `TraceId`

**Mẹo:**
Luôn gắn correlation id hoặc trace id vào log của request.

**Tại sao hữu ích:**
Giúp theo dõi một request xuyên suốt nhiều service hoặc background job.

**Ví dụ:**
```csharp
logger.LogInformation("Processing order {OrderId}", orderId);
```

**Lưu ý:**
Không log dữ liệu nhạy cảm như token, password hoặc personal data.

### Tip 3 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Dùng binary search của Git khi biết code hiện tại lỗi nhưng không biết commit nào gây ra.

**Tại sao hữu ích:**
Tiết kiệm thời gian debug regression trong lịch sử code lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good <commit>
```

**Lưu ý:**
Cần có test hoặc cách xác định bad/good rõ ràng.

### Tip 4 — Dùng `AsNoTracking` khi đọc dữ liệu chỉ để hiển thị

**Mẹo:**
Trong EF Core, dùng `AsNoTracking()` cho query không cần update entity.

**Tại sao hữu ích:**
Giảm memory usage và tăng tốc query read-only.

**Ví dụ:**
```csharp
var users = await db.Users
    .AsNoTracking()
    .ToListAsync();
```

**Lưu ý:**
Không dùng nếu entity cần được EF Core tracking để update.

### Tip 5 — Dùng health check để phát hiện dependency lỗi sớm

**Mẹo:**
Expose health endpoint cho database, cache hoặc external dependency quan trọng.

**Tại sao hữu ích:**
Hỗ trợ monitoring và tự động restart khi service unhealthy.

**Ví dụ:**
```csharp
builder.Services.AddHealthChecks();
```

**Lưu ý:**
Health check không nên tạo tải lớn lên dependency production.

## 🧠 Software Design

### Design 1 — Separation of Concerns trong Backend Architecture

**Khái niệm:**
Tách business logic, infrastructure logic và presentation logic thành các trách nhiệm riêng biệt.

**Vấn đề nó giải quyết:**
Giảm coupling và giúp thay đổi một phần hệ thống mà không ảnh hưởng toàn bộ.

**Ví dụ thực tế:**
Controller chỉ xử lý HTTP, service xử lý nghiệp vụ, repository hoặc data layer xử lý persistence.

**Trade-off:**
Boundary rõ ràng giúp maintain tốt hơn nhưng có thể tạo thêm abstraction nếu thiết kế quá mức.

**Middle → Senior insight:**
Middle cần biết chia trách nhiệm. Senior cần xác định boundary dựa trên khả năng thay đổi của hệ thống.

### Design 2 — Outbox Pattern cho Event-Driven System

**Khái niệm:**
Outbox Pattern lưu event cùng transaction với business data trước khi publish message.

**Vấn đề nó giải quyết:**
Tránh tình trạng database commit thành công nhưng message publish thất bại.

**Ví dụ thực tế:**
Khi tạo Order, hệ thống lưu Order và OrderCreatedEvent vào outbox table rồi background worker publish RabbitMQ.

**Trade-off:**
Tăng reliability nhưng thêm storage và xử lý retry.

**Middle → Senior insight:**
Senior cần hiểu distributed transaction không chỉ là code problem mà là consistency problem.

### Design 3 — Cache Aside Pattern trong hệ thống có tải cao

**Khái niệm:**
Application tự đọc cache trước, nếu miss thì lấy database rồi cập nhật cache.

**Vấn đề nó giải quyết:**
Giảm database load với dữ liệu đọc nhiều nhưng thay đổi ít.

**Ví dụ thực tế:**
Product catalog sử dụng Redis để cache thông tin sản phẩm phổ biến.

**Trade-off:**
Tăng performance nhưng phải xử lý cache invalidation và stale data.

**Middle → Senior insight:**
Senior không chỉ thêm cache để nhanh hơn mà phải xác định dữ liệu nào chấp nhận eventual consistency.
