## Developer Tips & Tricks

### 1. ASP.NET Core Rate Limiting: partition theo identity đúng, nếu không một client có thể làm nghẽn tất cả người dùng

**Vấn đề thực tế:** API thêm rate limiter để bảo vệ endpoint đắt tiền, nhưng dùng một global fixed-window limiter. Một integration client gửi burst lớn và tiêu hết quota chung; các user bình thường bắt đầu nhận `429 Too Many Requests` dù họ gần như không tạo tải.

**Cơ chế bên dưới:** Rate limiting chỉ hiệu quả khi resource accounting phản ánh đúng contention boundary. ASP.NET Core hỗ trợ partitioned limiter: mỗi API key, tenant, user hoặc IP có limiter riêng. Chọn partition key sai cũng nguy hiểm: chỉ dùng IP có thể gom hàng nghìn user sau NAT vào cùng quota; tin trực tiếp `X-Forwarded-For` khi proxy chưa được cấu hình đúng lại cho phép spoof identity.

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("tenant-api", httpContext =>
    {
        var tenantId = httpContext.User.FindFirst("tenant_id")?.Value
            ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: tenantId,
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                AutoReplenishment = true,
                QueueLimit = 0
            });
    });
});
```

Token bucket cho phép burst có kiểm soát nhưng vẫn giới hạn sustained rate. Rate limit không thay thế authorization, concurrency limit hay downstream capacity protection; đây là các control khác nhau.

**Khi nên dùng:** Public APIs, partner integrations, expensive search/report endpoints và multi-tenant systems cần fairness hoặc protection theo caller.

### 2. MongoDB compound index phải đi theo query shape; “có index cho từng field” không đồng nghĩa query được tối ưu

**Vấn đề thực tế:** Collection `orders` có index riêng trên `tenantId`, `status` và `createdAt`, nhưng query `tenantId + status` rồi sort `createdAt DESC` vẫn chậm. Team thấy các field đều “đã có index” nên nghi MongoDB hoặc driver có vấn đề.

**Cơ chế bên dưới:** Một compound index có thể phục vụ filter và sort trong cùng ordered index traversal. Nhiều single-field indexes đôi khi có index intersection, nhưng không mặc nhiên giải quyết sort hiệu quả và thường không tốt bằng index khớp query shape. Với pattern equality → sort → range, thứ tự key phải được thiết kế từ workload thực tế.

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1,
  _id: -1
})

// Query shape
db.orders.find({
  tenantId: tenantId,
  status: "Paid"
})
.sort({ createdAt: -1, _id: -1 })
.limit(50)
```

Kiểm tra bằng `explain("executionStats")`: xem `totalKeysExamined`, `totalDocsExamined`, returned documents và có blocking `SORT` hay không. Đừng tạo compound index cho mọi combination; mỗi index làm tăng storage và write amplification.

**Khi nên dùng:** Collections lớn có query patterns ổn định, multi-tenant filtering, feeds/history và workloads vừa filter vừa sort.

### 3. Playwright: locator theo semantics bền hơn CSS selector bám vào DOM implementation

**Vấn đề thực tế:** UI automation dùng selector như `.checkout-form > div:nth-child(3) > button`. Một refactor CSS hoặc thêm wrapper không đổi behavior nhưng làm hàng chục tests fail. Test suite trở thành chi phí bảo trì thay vì regression safety net.

**Cơ chế bên dưới:** Playwright locators như `GetByRole`, `GetByLabel` và `GetByTestId` mô tả user-facing contract hoặc explicit testing contract. Locator còn có auto-waiting và actionability checks; việc tự `Task.Delay(2000)` chỉ che race condition và làm test vừa chậm vừa flaky.

```csharp
await page.GetByLabel("Email").FillAsync("qa@example.com");
await page.GetByRole(AriaRole.Button, new() { Name = "Place order" }).ClickAsync();

await Expect(page.GetByRole(AriaRole.Heading, new() { Name = "Order confirmed" }))
    .ToBeVisibleAsync();
```

Nếu element không có semantic role/name ổn định, `data-testid` là fallback tốt hơn selector phụ thuộc layout. Nhưng đừng biến test thành bản sao implementation bằng cách gắn test id cho mọi node.

**Khi nên dùng:** End-to-end tests cho critical user journeys, regression suites chạy CI và UI thường xuyên refactor presentation nhưng giữ behavior.

### 4. Vue async search: hủy request cũ để response đến muộn không ghi đè state mới

**Vấn đề thực tế:** User gõ `asp`, rồi nhanh chóng gõ `asp.net`. Request đầu tiên chậm hơn request thứ hai. Response `asp.net` render đúng trước, sau đó response cũ `asp` đến và overwrite results — UI hiển thị dữ liệu không tương ứng với input hiện tại.

**Cơ chế bên dưới:** Đây là race giữa nhiều asynchronous effects, không phải lỗi Vue. Debounce chỉ giảm số request; nó không đảm bảo thứ tự completion. Mỗi effect mới nên invalidate/hủy effect trước bằng `AbortController`, hoặc dùng request sequence/version để bỏ response stale.

```ts
let controller: AbortController | undefined

async function search(query: string) {
  controller?.abort()
  controller = new AbortController()

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal }
    )

    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    results.value = await response.json()
  } catch (error) {
    if (error instanceof DOMException && error.name === 'AbortError') return
    throw error
  }
}
```

Ở backend, cancellation chỉ tiết kiệm tài nguyên nếu cancellation signal thực sự được propagate tiếp xuống HTTP/database operations; frontend abort không đảm bảo remote side effect chưa xảy ra.

**Khi nên dùng:** Autocomplete, live filters, route-driven data loading và components nơi dependency thay đổi nhanh tạo nhiều request cạnh tranh.

### 5. Azure Key Vault + Managed Identity: secret rotation chỉ có giá trị nếu application không cache secret vô thời hạn

**Vấn đề thực tế:** Team chuyển connection secret khỏi `appsettings.json` sang Azure Key Vault và dùng Managed Identity. Sau đó secret được rotate nhưng application vẫn giữ giá trị đọc lúc startup; instance chỉ nhận secret mới sau restart, biến rotation thành một deployment dependency không được dự tính.

**Cơ chế bên dưới:** Managed Identity loại bỏ credential để application truy cập Key Vault; nó không tự quyết định lifecycle của secret value mà application đã đọc. Nếu configuration provider hoặc code cache secret, cần hiểu refresh semantics. Với service hỗ trợ identity trực tiếp như Azure Storage hoặc Azure SQL trong cấu hình phù hợp, ưu tiên token-based access để loại bỏ secret cần rotate hoàn toàn.

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

KeyVaultSecret secret = await client.GetSecretAsync(
    "PartnerApiKey",
    cancellationToken: cancellationToken);
```

Đừng gọi Key Vault trên mọi request chỉ để “luôn mới”: điều đó thêm network dependency, latency và quota pressure vào hot path. Chọn refresh/cache policy dựa trên rotation requirement và failure behavior.

**Khi nên dùng:** Azure-hosted applications cần secrets cho third-party systems hoặc legacy dependencies chưa hỗ trợ identity-based authentication.

### 6. Modular Monolith: boundary phải được enforce trong code và data access, không chỉ thể hiện bằng folder

**Vấn đề thực tế:** Solution được gọi là Modular Monolith vì có folders `Orders`, `Catalog`, `Payments`, nhưng mọi module đều inject cùng `AppDbContext`, query table của nhau và gọi trực tiếp internal services. Sau một năm, thay đổi schema của Catalog làm Orders fail; “module” chỉ còn là cách sắp file.

**Thiết kế:** Một module có public contract rõ ràng và ownership đối với domain/data của nó. Cross-module interaction đi qua application contract, domain/integration event hoặc query contract có chủ đích. Có thể vẫn dùng cùng physical database để giữ operational simplicity, nhưng schema/table ownership và access rules phải rõ.

```text
                Modular Monolith Process

+----------------+      contract/event      +----------------+
| Orders Module  | -----------------------> | Payments Module|
|                |                          |                |
| Orders domain  |                          | Payments domain|
| Orders data    |                          | Payments data  |
+----------------+                          +----------------+
        |
        | contract/event
        v
+----------------+
| Catalog Module |
| Catalog domain |
| Catalog data   |
+----------------+

Không cho Orders query trực tiếp Payments tables chỉ vì cùng database.
```

**Trade-off:** Boundary enforcement tạo thêm contracts, mapping và đôi khi duplicate read data. Đổi lại, coupling được nhìn thấy sớm và module có khả năng tiến hóa độc lập hơn. Tách thành Microservices sau này dễ hơn nhưng không phải mục tiêu bắt buộc.

**Khi phù hợp:** Domain đủ lớn cần boundaries nhưng team chưa cần hoặc chưa muốn operational complexity của Microservices. Với application nhỏ, Layered Architecture đơn giản có thể kinh tế hơn.

### 7. Webhook Inbox: trả `2xx` nhanh, lưu delivery trước rồi xử lý side effect bất đồng bộ

**Vấn đề thực tế:** Payment provider gửi webhook. Endpoint verify signature rồi thực hiện nhiều database/API calls trước khi trả response. Khi xử lý mất 15 giây, provider timeout và retry; hai deliveries chạy song song, cùng tạo shipment hoặc gửi email hai lần.

**Thiết kế:** Webhook endpoint làm tối thiểu các bước cần thiết: verify authenticity, validate envelope, persist delivery với provider event ID trong durable store rồi trả `2xx`. Worker xử lý inbox sau đó. Unique constraint trên event ID biến duplicate delivery thành no-op ở ingestion boundary.

```text
Provider
   |
   v
Webhook Endpoint
   |-- verify signature
   |-- INSERT Inbox(EventId, Payload) [unique EventId]
   +-- return 2xx
              |
              v
         Inbox Worker
              |
        business handler
              |
        mark processed
```

**Trade-off:** Business effect trở thành eventually consistent và cần worker/retry/dead-letter/monitoring. Persist-before-ack quan trọng: trả `2xx` trước khi durable write có thể làm mất event nếu process crash ngay sau response.

**Khi phù hợp:** Payment, identity, commerce, GitHub/SaaS webhooks và integrations có at-least-once delivery hoặc retry behavior từ provider.

### 8. CQRS chỉ đáng giá khi read/write models thực sự có nhu cầu khác nhau

**Vấn đề thực tế:** Một CRUD application tạo `CreateCustomerCommand`, `UpdateCustomerCommand`, `GetCustomerQuery`, handlers, mediator behaviors và hàng chục DTO chỉ vì “CQRS là architecture tốt”. Flow đơn giản trở thành khó trace, trong khi read và write vẫn dùng cùng entity, cùng database và cùng transaction semantics.

**Thiết kế:** CQRS là tách **responsibility/model** của commands và queries, không bắt buộc tách service hay database. Giá trị xuất hiện khi write side cần invariant-rich domain behavior còn read side cần projection tối ưu riêng; hoặc hai phía có scaling, security, consistency hay data-shape khác nhau.

```text
                 Application
                    |
          +---------+---------+
          |                   |
       Commands             Queries
          |                   |
          v                   v
  Domain / invariants    Read projections
          |                   |
          v                   v
      Write model          Read model
```

**Trade-off:** Tách models giảm compromise giữa transactional model và query model nhưng tăng concepts, mapping, synchronization và có thể tạo eventual consistency nếu read store riêng. MediatR không tự biến application thành CQRS; nó chỉ là một dispatch mechanism.

**Khi phù hợp:** Complex domains, read-heavy systems với projections khác write model, hoặc workflows cần command semantics rõ. Với straightforward CRUD, direct application services + EF Core thường dễ hiểu và rẻ hơn.
