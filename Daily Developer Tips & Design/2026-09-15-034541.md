# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup immutable được xây một lần, đọc rất nhiều lần

**Mẹo:**
Trong .NET 8+, nếu một lookup table được tạo ở startup rồi chỉ đọc trong suốt lifetime của process, cân nhắc chuyển sang `FrozenDictionary<TKey,TValue>` sau khi build xong.

**Tại sao hữu ích:**
`FrozenDictionary` tối ưu cấu trúc dữ liệu cho read-heavy immutable lookup. Nó chấp nhận chi phí tạo ban đầu cao hơn để giảm overhead ở các lần đọc sau, phù hợp với route metadata, mapping code, feature definition hoặc bảng cấu hình tĩnh được truy cập rất nhiều lần.

**Ví dụ:**
```csharp
var handlers = new Dictionary<string, Func<Request, Task>>
{
    ["create"] = HandleCreateAsync,
    ["cancel"] = HandleCancelAsync
}.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
```

Nếu lookup được gọi hàng triệu lần trong hot path, benchmark giữa `Dictionary`, `ImmutableDictionary` và `FrozenDictionary` trên workload thật trước khi quyết định.

**Lưu ý:**
Không dùng `FrozenDictionary` cho dữ liệu cần mutate runtime. Chi phí freeze có thể không đáng nếu collection nhỏ hoặc ít được truy cập. Đây là optimization có chủ đích, không phải replacement mặc định cho mọi `Dictionary`.

### Tip 2 — Stream response lớn bằng `IAsyncEnumerable<T>` thay vì materialize toàn bộ collection

**Mẹo:**
Với endpoint trả tập dữ liệu lớn, cân nhắc stream dần bằng `IAsyncEnumerable<T>` hoặc response stream thay vì `ToListAsync()` toàn bộ dữ liệu trước khi bắt đầu gửi response.

**Tại sao hữu ích:**
Materialize hàng trăm nghìn row làm tăng memory pressure, thời gian chờ trước byte đầu tiên và có thể tạo allocation spike. Streaming cho phép pipeline bắt đầu gửi dữ liệu sớm hơn và giữ working set thấp hơn khi serializer hỗ trợ streaming.

**Ví dụ:**
```csharp
app.MapGet("/api/audit/export", (AppDbContext db, CancellationToken ct) =>
    db.AuditEntries
      .AsNoTracking()
      .OrderBy(x => x.Id)
      .AsAsyncEnumerable()
      .WithCancellation(ct));
```

Với file export rất lớn, có thể stream CSV/JSON trực tiếp ra response thay vì tạo một `byte[]` hoặc `List<T>` khổng lồ trước.

**Lưu ý:**
Streaming giữ database reader/connection mở lâu hơn. Client chậm có thể làm connection bị giữ trên toàn bộ thời gian truyền. Đừng dùng streaming nếu business cần sort/aggregate toàn bộ data trong memory trước khi trả kết quả; cân nhắc export background job cho workload cực lớn.

### Tip 3 — Dùng `FOR UPDATE SKIP LOCKED` khi PostgreSQL được dùng như work queue nhỏ có nhiều worker

**Mẹo:**
Nếu nhiều worker lấy job trực tiếp từ PostgreSQL, `FOR UPDATE SKIP LOCKED` có thể giúp mỗi worker claim row chưa bị worker khác lock mà không phải chờ lock hiện tại được giải phóng.

**Tại sao hữu ích:**
Nếu worker A đang xử lý job đầu tiên và worker B chạy cùng query `FOR UPDATE`, B có thể block dù còn nhiều job khác sẵn sàng. `SKIP LOCKED` cho phép B bỏ qua row đã bị claim và lấy row tiếp theo, tăng concurrency cho queue nhỏ dựa trên database.

**Ví dụ:**
```sql
BEGIN;

SELECT id
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;

-- update row vừa claim sang processing
COMMIT;
```

Index trên `(status, created_at)` thường cần thiết để worker không scan phần lớn bảng mỗi lần lấy job.

**Lưu ý:**
Database-backed queue phù hợp với workload vừa phải và transaction đơn giản, nhưng không tự cung cấp retry policy, dead-letter queue, visibility timeout hay telemetry như message broker. Nếu volume/failure semantics phức tạp, Azure Service Bus hoặc broker chuyên dụng có thể đúng hơn.

### Tip 4 — Trong Vue, tránh `deep: true` watcher cho object lớn nếu chỉ cần theo dõi vài field

**Mẹo:**
Khi watcher chỉ quan tâm một số thuộc tính, watch chính xác các source đó thay vì bật `deep: true` trên cả object reactive lớn.

**Tại sao hữu ích:**
Deep watcher phải traverse dependency tree rộng hơn và cũng làm intent của code mơ hồ: bất kỳ nested change nào cũng có thể trigger side effect. Watch field cụ thể giúp giảm work không cần thiết và làm dependency của side effect rõ ràng hơn.

**Ví dụ:**
```ts
watch(
  () => [filters.status, filters.categoryId],
  () => reloadProducts(),
  { flush: 'post' }
)
```

Thay vì:
```ts
watch(filters, reloadProducts, { deep: true })
```

nếu thay đổi `filters.ui.expandedPanel` hoàn toàn không liên quan tới API query.

**Lưu ý:**
Nếu object thực sự là một cấu hình nested mà mọi thay đổi đều phải được persist, deep watch có thể hợp lý. Với side effect gọi API, vẫn cần debounce/cancellation khi user thay đổi filter liên tục.

### Tip 5 — Quét package vulnerability trong CI và phân biệt “có CVE” với “có đường khai thác”

**Mẹo:**
Thêm bước kiểm tra dependency vulnerability vào CI, ví dụ với `dotnet list package --vulnerable --include-transitive`, nhưng review kết quả theo runtime path và exploitability thay vì chỉ fail pipeline theo số lượng CVE.

**Tại sao hữu ích:**
Một package transitive cũ có thể kéo CVE vào build dù code không sử dụng capability bị ảnh hưởng. Ngược lại, một dependency nằm trực tiếp trên request path có thể là risk cao dù severity chỉ ở mức trung bình trong bối cảnh chung. CI nên cung cấp evidence để team quyết định remediation ưu tiên.

**Ví dụ:**
```bash
dotnet list MySolution.sln package \
  --vulnerable \
  --include-transitive
```

Sau đó kiểm tra package nào kéo dependency vào, version fixed là gì, có breaking change không và application có thực sự chạm tới vulnerable feature hay không.

**Lưu ý:**
Đừng bỏ qua CVE chỉ vì “chưa thấy exploit”. Nhưng cũng đừng tự động upgrade major version giữa production incident mà không test compatibility. Security remediation cần cân bằng exposure, exploitability, patch risk và rollout speed.

## 🧠 Software Design

### Design 1 — Branch by Abstraction giúp thay implementation lớn mà không giữ long-lived branch

**Khái niệm:**
Branch by Abstraction cho phép đưa abstraction seam vào production code rồi chuyển dần traffic hoặc use case từ implementation cũ sang implementation mới trong cùng mainline, thay vì phát triển nhiều tuần trên một branch tách biệt.

**Vấn đề nó giải quyết:**
Team cần thay payment SDK, search engine hoặc legacy module nhưng migration kéo dài qua nhiều sprint. Long-lived branch dễ diverge khỏi `main`, tạo merge conflict lớn và buộc cutover kiểu big bang vào cuối dự án.

**Ví dụ thực tế:**
```text
IProductSearch
   ├─ LegacySqlSearch
   └─ ElasticsearchProductSearch

Giai đoạn 1: 100% Legacy
Giai đoạn 2: shadow compare kết quả
Giai đoạn 3: rollout theo tenant
Giai đoạn 4: 100% Elasticsearch
Giai đoạn 5: xóa Legacy adapter
```

Abstraction chỉ cần đủ để che phần đang migrate, không cần biến thành framework chung cho mọi integration.

**Trade-off:**
Cách này giảm merge risk và hỗ trợ migration từng bước, nhưng tạm thời phải duy trì hai implementation, test hai path và có cleanup discipline. Nếu abstraction seam được thiết kế quá tổng quát, team có thể trả chi phí complexity lâu dài cho một migration chỉ diễn ra một lần.

**Middle → Senior insight:**
Middle developer cần giữ hai implementation behavior-compatible và viết test quanh abstraction boundary. Senior / Technical developer phải chọn migration seam, rollout strategy, telemetry, rollback criteria và thời điểm loại bỏ abstraction tạm thời thay vì để migration code sống vĩnh viễn.

### Design 2 — Materialized View phù hợp khi read cost cao nhưng freshness không cần tức thời

**Khái niệm:**
Materialized View hoặc precomputed read model lưu sẵn kết quả của query/aggregation tốn kém để read path không phải join và aggregate lại từ đầu mỗi request.

**Vấn đề nó giải quyết:**
Dashboard doanh thu phải join nhiều bảng lớn và aggregate theo ngày, region, product. Query trực tiếp source-of-truth mỗi request có thể tạo CPU/I/O lớn dù dữ liệu chỉ cần cập nhật mỗi vài phút.

**Ví dụ thực tế:**
```text
Source tables:
Orders + OrderItems + Products + Customers

Precomputed:
DailySalesByRegion
- Date
- Region
- Revenue
- OrderCount

Refresh mỗi 5 phút hoặc khi batch ingestion hoàn tất.
```

Application đọc read model nhỏ, còn source transactional tiếp tục được tối ưu cho write/invariant.

**Trade-off:**
Read nhanh và ổn định hơn, nhưng dữ liệu có thể stale và cần refresh/rebuild strategy. Incremental refresh phức tạp hơn full refresh; nếu freshness requirement gần real-time và dataset nhỏ, index/query tuning đơn giản có thể hợp lý hơn.

**Middle → Senior insight:**
Middle developer cần hiểu read model là derived data và source-of-truth vẫn nằm ở transactional storage. Senior / Solution-oriented engineer phải quyết định freshness SLA, refresh mechanism, rebuildability, failure handling và xem chi phí vận hành có thực sự thấp hơn việc tối ưu query gốc hay không.

### Design 3 — Progressive degradation giúp hệ thống giữ core flow khi dependency phụ bị lỗi

**Khái niệm:**
Progressive degradation thiết kế application để một số capability không critical có thể bị tắt, trả dữ liệu stale hoặc fallback khi dependency phụ gặp sự cố, trong khi core transaction vẫn tiếp tục hoạt động.

**Vấn đề nó giải quyết:**
Checkout cần Order và Payment hoạt động, nhưng recommendation, review score hoặc loyalty enrichment chỉ là phụ. Nếu mọi dependency đều bắt buộc thành công, một service ít quan trọng có thể kéo toàn bộ checkout xuống.

**Ví dụ thực tế:**
```text
Checkout:
- Pricing: required -> failure thì stop
- Payment: required -> failure thì stop
- Recommendations: optional -> timeout thì bỏ qua
- Loyalty balance: optional -> hiển thị trạng thái tạm unavailable
```

Mỗi dependency cần classification rõ về criticality, timeout budget và fallback behavior.

**Trade-off:**
Degradation tăng availability cho core flow nhưng làm UX và data semantics phức tạp hơn. Fallback sai có thể che incident hoặc tạo quyết định business không an toàn. Không phải dependency nào cũng được phép “bỏ qua”; authorization, pricing hoặc compliance check thường không thể degrade mềm.

**Middle → Senior insight:**
Middle developer cần phân biệt required và optional dependency trong use case, đồng thời xử lý fallback rõ ràng. Senior / Technical developer phải định nghĩa failure budget, degraded-mode semantics, observability và điều kiện tự động phục hồi sao cho hệ thống không biến “resilient” thành “âm thầm sai”.
