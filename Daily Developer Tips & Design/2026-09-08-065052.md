# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian mà không cần chạm clock thật

**Mẹo:**
Với code mới trên modern .NET, inject `TimeProvider` vào business logic có phụ thuộc thời gian thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi.

**Tại sao hữu ích:**
Clock thật là một hidden dependency. Khi rule phụ thuộc expiry, grace period hoặc scheduled cutoff, test thường dễ flaky nếu phải chờ thời gian thực. `TimeProvider` biến clock thành dependency kiểm soát được và giúp test deterministic hơn.

**Ví dụ:**
```csharp
public sealed class SubscriptionService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        timeProvider.GetUtcNow() >= expiresAt;
}
```

Production dùng `TimeProvider.System`; test có thể dùng fake provider để advance thời gian chủ động.

**Lưu ý:**
Không cần đưa `TimeProvider` vào mọi class chỉ để ghi timestamp log. Dùng nó khi thời gian ảnh hưởng behavior cần kiểm thử.

### Tip 2 — So sánh `estimated rows` và `actual rows` trước khi đổ lỗi cho index

**Mẹo:**
Khi SQL query chậm, đọc execution plan và so sánh cardinality estimate với số row thực tế trước khi thêm index mới.

**Tại sao hữu ích:**
Nếu optimizer dự đoán 50 rows nhưng thực tế trả 500.000 rows, nó có thể chọn join strategy hoặc access path không phù hợp. Vấn đề có thể nằm ở statistics, data skew hoặc predicate chứ không phải thiếu index.

**Ví dụ:**
Một query có plan:
```text
Estimated Rows: 120
Actual Rows:    420000
```

Đây là tín hiệu nên kiểm tra statistics, filter selectivity và parameter distribution trước khi thay đổi schema.

**Lưu ý:**
Không update statistics hoặc rebuild index theo thói quen mà không đo lại. Mục tiêu là xác nhận hypothesis bằng plan và runtime metrics.

### Tip 3 — Với Vue.js, cleanup request cũ khi watcher chạy lại

**Mẹo:**
Nếu `watch` hoặc `watchEffect` tạo request phụ thuộc vào search/filter state, hủy request cũ khi dependency thay đổi thay vì để nhiều request chạy song song.

**Tại sao hữu ích:**
Response cũ có thể về sau response mới và ghi đè state đúng bằng dữ liệu stale. Cleanup giúp mỗi watcher execution sở hữu rõ lifecycle của side effect nó tạo ra.

**Ví dụ:**
```ts
watch(searchTerm, async (value, _, onCleanup) => {
  const controller = new AbortController();
  onCleanup(() => controller.abort());

  const response = await fetch(`/api/search?q=${encodeURIComponent(value)}`, {
    signal: controller.signal
  });

  results.value = await response.json();
});
```

**Lưu ý:**
Cancellation không thay thế debounce. Nếu input thay đổi rất nhanh và API cost cao, có thể cần cả hai.

### Tip 4 — Dùng `git worktree` khi cần làm hotfix mà không phá working tree hiện tại

**Mẹo:**
Khi đang có thay đổi dở dang trên feature branch nhưng cần chuyển sang hotfix gấp, dùng `git worktree` để checkout thêm một working directory thay vì stash/reset liên tục.

**Tại sao hữu ích:**
Bạn giữ nguyên context hiện tại, tránh stash nhầm file và có thể chạy hai branch song song trong hai thư mục độc lập nhưng dùng chung repository object database.

**Ví dụ:**
```bash
git worktree add ../project-hotfix main
cd ../project-hotfix
git checkout -b hotfix/payment-timeout
```

Sau khi hoàn tất:
```bash
git worktree remove ../project-hotfix
```

**Lưu ý:**
Không dùng cùng một branch trong hai worktree cùng lúc. Đồng thời chú ý port, local database và generated artifact nếu hai instance chạy song song.

### Tip 5 — Kiểm tra telemetry sampling trước khi kết luận production “không có lỗi”

**Mẹo:**
Khi điều tra incident bằng Application Insights hoặc hệ thống observability tương tự, kiểm tra sampling và ingestion policy trước khi dựa vào raw event count.

**Tại sao hữu ích:**
Nếu telemetry được sample để giảm volume, 100 request thực tế có thể chỉ còn một phần được lưu. Vì vậy số trace/log tuyệt đối có thể không phản ánh chính xác traffic hay error count nếu bạn bỏ qua sampling metadata.

**Ví dụ:**
Một dashboard cho thấy chỉ 20 dependency failures, nhưng telemetry đang sample 10%. Khi đó cần xem metric đã được corrected/weighted chưa và dùng signal phù hợp như server metrics hoặc aggregate counters để xác nhận impact.

**Lưu ý:**
Không tắt sampling toàn hệ thống chỉ để debug một incident. Cách đó có thể làm tăng cost và ingestion pressure. Nên dùng targeted diagnostics hoặc điều chỉnh sampling có kiểm soát.

## 🧠 Software Design

### Design 1 — Queue vs Topic trong Azure Service Bus theo ownership của consumer

**Khái niệm:**
Queue phù hợp khi một message đại diện một unit of work cần một consumer xử lý. Topic + subscription phù hợp khi cùng một event cần nhiều consumer độc lập nhận bản sao riêng.

**Vấn đề nó giải quyết:**
Nếu dùng một queue cho workflow thực chất là broadcast, consumer cạnh tranh nhau và chỉ một bên nhận message. Ngược lại, dùng topic cho command chỉ có một owner có thể tạo routing và operational complexity không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command có một owner rõ ràng nên phù hợp queue. `OrderPlaced` có thể cần Billing, Analytics và Notification cùng phản ứng nên phù hợp topic với ba subscription độc lập.

**Trade-off:**
Queue đơn giản hơn và ownership rõ. Topic tăng extensibility và fan-out nhưng thêm subscription lifecycle, filtering, monitoring và duplicate-processing concern ở từng consumer.

**Middle → Senior insight:**
Middle developer cần phân biệt command và event theo intent. Senior / Technical developer phải đánh giá ownership, fan-out, delivery guarantee, retry isolation và khả năng thêm consumer trong tương lai trước khi chọn broker topology.

### Design 2 — Normalization vs denormalization theo write integrity và read pressure

**Khái niệm:**
Normalization ưu tiên dữ liệu nhất quán và giảm duplication; denormalization chấp nhận duplicate hoặc precomputed data để giảm join/query cost cho read path quan trọng.

**Vấn đề nó giải quyết:**
Một schema tối ưu cho transaction write không phải lúc nào cũng tối ưu cho dashboard/search. Nhưng copy dữ liệu sang nhiều nơi lại tạo synchronization và stale-data problem.

**Ví dụ thực tế:**
Order transaction tables giữ `CustomerId` và quan hệ chuẩn hóa. Một read model cho dashboard có thể lưu thêm `CustomerDisplayName` để tránh join nhiều bảng trên mỗi request, miễn là business chấp nhận việc tên hiển thị cập nhật trễ.

**Trade-off:**
Normalization giữ source of truth rõ và update đơn giản hơn nhưng có thể tăng join cost. Denormalization tăng read performance và đơn giản hóa query nhưng thêm storage, sync logic và consistency concern.

**Middle → Senior insight:**
Middle developer cần hiểu functional dependency và tránh duplicate dữ liệu tùy tiện. Senior / Technical developer phải định lượng read/write ratio, freshness requirement, query cost và operational complexity trước khi denormalize.

### Design 3 — Contract testing giữa service boundaries thay vì mock mọi integration

**Khái niệm:**
Contract testing xác minh producer và consumer thống nhất về request/response hoặc event schema mà không cần chạy toàn bộ end-to-end environment cho mọi test.

**Vấn đề nó giải quyết:**
Unit test với mock có thể pass dù consumer kỳ vọng field khác production. Full end-to-end test bắt lỗi integration tốt hơn nhưng chậm, khó cô lập và dễ flaky khi dependency nhiều.

**Ví dụ thực tế:**
Mobile backend tiêu thụ `CustomerUpdated` event. Contract test xác nhận event vẫn có các field và semantics consumer yêu cầu trước khi producer release breaking change.

**Trade-off:**
Contract test cho feedback nhanh và bảo vệ boundary tốt hơn mock thuần túy, nhưng cần governance về version, ownership và pipeline publication. Nó cũng không thay thế hoàn toàn integration/end-to-end test cho behavior xuyên nhiều service.

**Middle → Senior insight:**
Middle developer cần hiểu contract là behavior được chia sẻ chứ không chỉ DTO shape. Senior / Technical developer phải quyết định boundary nào đáng có contract test, cách version contract và cách xử lý backward compatibility mà không tạo test infrastructure quá nặng.
