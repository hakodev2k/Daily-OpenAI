# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate `Options` ngay lúc startup để fail fast thay vì lỗi giữa request

**Mẹo:**
Với configuration quan trọng như endpoint, timeout, credential reference hoặc business limit, dùng Options validation và `ValidateOnStart()` để application từ chối khởi động nếu config không hợp lệ.

**Tại sao hữu ích:**
Nếu config sai chỉ được phát hiện khi một request cụ thể chạy qua code path đó, deployment có thể “healthy” trong vài phút hoặc vài giờ rồi mới lỗi production. Fail fast ở startup giúp biến lỗi cấu hình thành deployment failure rõ ràng, dễ rollback và dễ quan sát hơn.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(o => Uri.TryCreate(o.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be an absolute URL")
    .Validate(o => o.TimeoutSeconds is > 0 and <= 30,
        "Payment:TimeoutSeconds must be between 1 and 30")
    .ValidateOnStart();
```

Khi config từ environment variable hoặc secret provider bị thiếu, process fail ngay thay vì nhận traffic rồi mới trả `500`.

**Lưu ý:**
Không phải mọi config đều cần startup validation. Giá trị dynamic có thể reload runtime thì cần validation ở refresh boundary phù hợp. Đồng thời, đừng log secret value khi validation fail; chỉ log tên field và reason an toàn.

### Tip 2 — Với Elasticsearch, dùng `filter` cho điều kiện exact-match không cần relevance scoring

**Mẹo:**
Trong `bool` query, đặt điều kiện như status, tenant, category ID hoặc date range vào `filter` thay vì `must` khi chúng chỉ dùng để loại dữ liệu và không cần ảnh hưởng `_score`.

**Tại sao hữu ích:**
`must` tham gia query scoring; `filter` chạy theo filter context, không tính relevance score và có thể tận dụng caching phù hợp hơn. Điều này làm intent của query rõ hơn và thường giảm overhead cho workload có nhiều điều kiện exact-match kết hợp full-text search.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "wireless headset" } }
      ],
      "filter": [
        { "term": { "tenantId": "t-42" } },
        { "term": { "status": "active" } },
        { "range": { "price": { "lte": 200 } } }
      ]
    }
  }
}
```

Full-text search vẫn được score, còn các business constraints chỉ giới hạn candidate documents.

**Lưu ý:**
Đừng kỳ vọng chuyển mọi clause sang `filter` sẽ tự động làm query nhanh đáng kể. Mapping, cardinality, shard count, analyzer, segment state và query shape vẫn quan trọng. Nếu field cần exact filter, đảm bảo mapping phù hợp như `keyword` hoặc numeric/date type.

### Tip 3 — Dùng immutable build artifact để rollback chính xác thay vì rebuild lại source cũ

**Mẹo:**
Trong CI/CD, artifact đã build cho một commit nên được version hóa và giữ immutable. Khi rollback, deploy lại đúng artifact cũ thay vì checkout commit cũ rồi build lại từ đầu.

**Tại sao hữu ích:**
Rebuild cùng source code không đảm bảo cho ra cùng binary nếu dependency, base image, package feed hoặc build tool đã thay đổi. Artifact immutability giúp rollback thật sự quay về thứ đã từng chạy, giảm một biến số lớn khi production đang có incident.

**Ví dụ:**
```text
Commit: a1b2c3d
Artifact: orders-api_2026.09.15.17.zip
Container image: registry/orders-api:a1b2c3d

Deploy lỗi version mới:
-> rollback bằng artifact/image version trước
-> không chạy pipeline build lại commit cũ
```

Kết hợp checksum, commit SHA và release metadata để truy vết binary đang chạy.

**Lưu ý:**
Artifact immutable không thay thế database rollback strategy. Nếu deployment mới đã chạy destructive migration hoặc thay external contract, deploy binary cũ có thể vẫn không hoạt động. Rollback cần được thiết kế cùng schema compatibility và config compatibility.

### Tip 4 — Khi IIS/App Service recycle, đảm bảo background work dừng có kiểm soát bằng `CancellationToken`

**Mẹo:**
Với `BackgroundService` hoặc hosted worker chạy trong web application, luôn propagate `stoppingToken` xuống các operation dài và xử lý shutdown trong thời gian grace period thay vì giả định process sẽ chạy tới khi job hoàn tất.

**Tại sao hữu ích:**
IIS recycle, App Service restart, deployment slot swap hoặc host shutdown có thể yêu cầu process dừng trong lúc background work đang xử lý. Nếu worker bỏ qua cancellation, job có thể bị terminate giữa chừng, giữ lock lâu, tạo duplicate processing hoặc làm deployment kéo dài bất thường.

**Ví dụ:**
```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var job = await queue.ReceiveAsync(stoppingToken);
        await ProcessAsync(job, stoppingToken);
    }
}
```

Nếu job không thể hoàn thành trong shutdown window, lưu checkpoint hoặc thiết kế processing idempotent để lần chạy sau tiếp tục an toàn.

**Lưu ý:**
Cancellation là cooperative; truyền token không đảm bảo operation tự dừng nếu implementation bên dưới bỏ qua nó. Đồng thời, không dùng web host cho critical long-running workload nếu lifecycle của web app không phù hợp; Worker Service riêng có thể đúng hơn.

### Tip 5 — Giảm CLS bằng cách reserve kích thước ảnh và component trước khi content tải xong

**Mẹo:**
Với website/CMS, luôn khai báo width/height hoặc `aspect-ratio` cho ảnh, banner và embed có kích thước dự đoán được để browser reserve layout space trước khi resource tải xong.

**Tại sao hữu ích:**
Nếu browser chưa biết kích thước ảnh, nội dung phía dưới có thể bị đẩy xuống sau khi ảnh xuất hiện, làm Cumulative Layout Shift (CLS) tăng. Đây là lỗi UX và Core Web Vitals thường đến từ cách render/layout hơn là backend latency.

**Ví dụ:**
```html
<img
  src="/media/product-123.webp"
  width="800"
  height="600"
  alt="Product"
  loading="lazy" />
```

Hoặc CSS:
```css
.product-card__image {
  aspect-ratio: 4 / 3;
  object-fit: cover;
}
```

Trong CMS, content model nên lưu metadata kích thước ảnh để renderer có thể reserve space ngay từ HTML đầu tiên.

**Lưu ý:**
Không hard-code ratio sai chỉ để giảm CLS; ảnh có thể bị crop hoặc distort. Với ad/personalized component có chiều cao biến động, cần placeholder/min-height hợp lý và đo bằng Lighthouse hoặc Real User Monitoring thay vì tối ưu theo cảm giác.

## 🧠 Software Design

### Design 1 — Bounded Context giúp tách model theo business meaning, không chỉ theo folder hoặc service

**Khái niệm:**
Bounded Context xác định phạm vi nơi một model và vocabulary có một nghĩa nhất quán. Cùng một từ như `Customer`, `Order` hoặc `Product` có thể có model khác nhau giữa Sales, Billing và Fulfillment mà không cần ép thành một “enterprise model” khổng lồ.

**Vấn đề nó giải quyết:**
Khi nhiều business area cùng dùng một shared domain model, model thường tích lũy field và rule của tất cả bên. Thay đổi nhỏ cho Billing có thể làm Sales bị ảnh hưởng, ownership mơ hồ và invariant của từng domain bị trộn vào nhau.

**Ví dụ thực tế:**
```text
Sales context:
Customer
- Leads
- Segment
- SalesOwner

Billing context:
BillingAccount
- InvoiceAddress
- CreditTerms
- TaxProfile
```

Hai context có thể tham chiếu nhau bằng ID/event/API contract thay vì dùng chung một class `Customer` khổng lồ.

**Trade-off:**
Bounded Context tăng autonomy và clarity nhưng thêm mapping, integration contract và khả năng duplicated data. Nếu domain nhỏ và team nhỏ, chia context quá sớm có thể tạo ceremony không cần thiết. Boundary phải phản ánh business capability thực sự, không chỉ technical layer.

**Middle → Senior insight:**
Middle developer cần nhận ra cùng một noun không nhất thiết phải dùng chung một entity class ở mọi nơi. Senior / Technical developer phải xác định boundary theo business rules, ownership, change cadence và integration cost; đồng thời biết khi nào một shared model đơn giản vẫn hợp lý hơn.

### Design 2 — Retry cần exponential backoff và jitter để tránh biến transient failure thành retry storm

**Khái niệm:**
Retry phù hợp với lỗi transient, nhưng các lần retry nên giãn dần bằng exponential backoff và thường thêm jitter để nhiều client không retry cùng một thời điểm.

**Vấn đề nó giải quyết:**
Khi dependency gặp outage ngắn, hàng trăm instance có thể cùng nhận lỗi và cùng retry sau đúng 1 giây. Traffic dồn thành từng đợt đồng bộ khiến dependency vừa hồi phục lại bị đánh quá tải, kéo dài outage.

**Ví dụ thực tế:**
```text
Không tốt:
retry sau 1s, 1s, 1s

Tốt hơn:
~250ms
~600ms
~1.4s
~3.1s
(mỗi lần có jitter ngẫu nhiên)
```

Retry budget phải nằm trong timeout tổng của request/workflow; không nên để ba layer mỗi layer retry ba lần rồi nhân số call ngoài dự kiến.

**Trade-off:**
Backoff + jitter giảm synchronized load nhưng tăng thời gian recovery cho từng request. Retry cũng có thể gây duplicate side effect nếu operation không idempotent. Với lỗi permanent như `400` validation hoặc authorization failure, retry thường chỉ lãng phí capacity.

**Middle → Senior insight:**
Middle developer cần phân loại lỗi transient/permanent và không retry mù quáng. Senior / Technical developer phải thiết kế retry budget xuyên call chain, chọn nơi duy nhất nên retry, phối hợp timeout/circuit breaker và đánh giá idempotency trước khi bật policy.

### Design 3 — Build vs Buy là quyết định về total cost và strategic differentiation, không chỉ chi phí license

**Khái niệm:**
Build vs Buy so sánh việc tự xây capability với dùng SaaS/vendor/product có sẵn. Quyết định đúng phải tính cả development, vận hành, security, compliance, integration, vendor lock-in và khả năng capability đó tạo khác biệt cạnh tranh cho sản phẩm.

**Vấn đề nó giải quyết:**
Team có thể mất nhiều tháng xây authentication, search, feature-flag platform hoặc document processing trong khi đó không phải core differentiator. Ngược lại, mua vendor cho capability rất đặc thù có thể tạo giới hạn contract, cost tăng theo scale hoặc làm roadmap phụ thuộc bên ngoài.

**Ví dụ thực tế:**
```text
Capability: transactional email

Build:
- SMTP infrastructure
- reputation/deliverability
- bounce handling
- monitoring
- abuse prevention

Buy:
- integrate provider API
- trả usage fee
- phụ thuộc provider contract/SLA
```

Nếu email delivery không phải lợi thế cạnh tranh, Buy thường hợp lý hơn; nhưng cần escape plan nếu provider trở thành dependency critical.

**Trade-off:**
Buy rút ngắn time-to-market và giảm operational burden nhưng thêm recurring cost, lock-in và external failure modes. Build cho quyền kiểm soát cao hơn nhưng đòi hỏi đội ngũ duy trì lâu dài, không chỉ chi phí implementation ban đầu.

**Middle → Senior insight:**
Middle developer cần biết đánh giá integration complexity và giới hạn kỹ thuật của vendor. Senior / Solution-oriented engineer phải so total cost of ownership, strategic value, compliance, exit strategy, SLA và team capability trước khi quyết định thay vì mặc định “tự build linh hoạt hơn” hoặc “SaaS luôn rẻ hơn”.
