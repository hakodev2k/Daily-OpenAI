# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — `Task.WhenAll` không biến mọi I/O thành concurrency an toàn

**Mẹo:**
Chỉ chạy nhiều async operations song song khi các operations thực sự độc lập và dependency phía dưới chịu được mức concurrency đó. Với danh sách lớn, dùng bounded concurrency thay vì tạo hàng nghìn `Task` rồi `Task.WhenAll` một lần.

**Tại sao hữu ích:**
Async giúp không block thread trong lúc chờ I/O, nhưng vẫn tiêu thụ sockets, database connections, rate-limit quota và memory. Unbounded fan-out có thể làm connection pool cạn hoặc khiến downstream throttling, biến tối ưu latency thành production incident.

**Ví dụ:**
Worker cần gọi REST API cho 10.000 records. Thay vì tạo 10.000 requests đồng thời, giới hạn 20–50 operations bằng `SemaphoreSlim` hoặc `Parallel.ForEachAsync`, rồi đo throughput và `429`/timeout để điều chỉnh.

**Lưu ý:**
Không dùng cùng một EF Core `DbContext` cho concurrent operations; `DbContext` không thread-safe. Concurrency limit cũng phải dựa trên capacity thực tế, không phải một con số cố định sao chép từ hệ thống khác.

### Tip 2 — Điều tra connection pool exhaustion từ thời gian giữ connection

**Mẹo:**
Khi API báo timeout lấy database connection, đừng chỉ tăng pool size. Đo thời gian connection được giữ, query latency, transaction duration và số requests đồng thời để tìm nguyên nhân giữ connection quá lâu.

**Tại sao hữu ích:**
Pool exhaustion thường là triệu chứng: slow query, transaction kéo dài, connection không được dispose đúng cách hoặc concurrency tăng đột biến. Tăng pool có thể chỉ chuyển bottleneck sang SQL Server/PostgreSQL và làm database chịu nhiều concurrent work hơn.

**Ví dụ:**
Sau deployment, p95 API tăng mạnh và logs xuất hiện timeout khi mở connection. Trace cho thấy một transaction mới giữ connection trong lúc gọi external HTTP API. Tách network call khỏi database transaction làm connection quay lại pool sớm hơn và giảm contention.

**Lưu ý:**
Không suy luận pool exhaustion chỉ từ số connection cao. Cần đối chiếu pool metrics, database waits, query plans và request concurrency; transaction boundary phải vẫn bảo toàn invariant nghiệp vụ.

### Tip 3 — Azure Service Bus consumer phải coi duplicate delivery là bình thường

**Mẹo:**
Thiết kế message handler idempotent bằng business key/message ID và lưu trạng thái xử lý ở boundary phù hợp. Đừng giả định một message chỉ được xử lý đúng một lần vì handler đã `Complete` thành công ở hầu hết các lần chạy.

**Tại sao hữu ích:**
At-least-once delivery cho phép message xuất hiện lại khi lock hết hạn, process crash hoặc acknowledgement không hoàn tất. Nếu side effect không idempotent, retry có thể tạo hai invoices, hai emails hoặc hai payment attempts.

**Ví dụ:**
`OrderPaid` consumer dùng `PaymentId` làm idempotency key. Trước khi tạo fulfillment, application kiểm tra/ghi processing record trong cùng transaction với state change; delivery lặp lại nhận ra operation đã hoàn tất và không tạo side effect lần hai.

**Lưu ý:**
Deduplication của broker không thay thế idempotency nghiệp vụ và có window/constraint riêng. Với side effect bên ngoài như payment provider, cần phối hợp idempotency mechanism của provider nếu có.

### Tip 4 — Contract test bắt lỗi API mà unit test thường không thấy

**Mẹo:**
Với API được nhiều frontend/service tiêu thụ, thêm tests kiểm tra serialized contract thực tế: property names, nullability, status codes, headers và representative payloads thay vì chỉ unit-test controller/service methods.

**Tại sao hữu ích:**
Refactor C# vẫn compile và unit tests vẫn xanh nhưng thay `JsonPropertyName`, enum serialization hoặc `ProblemDetails` shape có thể phá consumer. Contract test kiểm tra boundary mà hệ thống khác thực sự nhìn thấy.

**Ví dụ:**
Integration test gọi `/api/products/{id}` qua test server, deserialize bằng client contract và snapshot/verify các fields bắt buộc. Một thay đổi từ string enum sang numeric enum bị phát hiện trước deployment.

**Lưu ý:**
Đừng snapshot toàn bộ response một cách mù quáng vì tests sẽ brittle với fields không quan trọng. Contract cần tập trung vào behavior và compatibility guarantees mà consumers phụ thuộc.

### Tip 5 — Dùng `git bisect` để tìm regression thay vì đọc hàng chục commits

**Mẹo:**
Khi biết một commit cũ hoạt động và HEAD bị lỗi, dùng `git bisect` để binary-search commit gây regression; nếu có test/script tái hiện lỗi ổn định, dùng `git bisect run` để tự động hóa.

**Tại sao hữu ích:**
Với 128 commits, binary search lý tưởng chỉ cần khoảng 7 lần kiểm tra thay vì review tuần tự toàn bộ history. Đây là công cụ production-debugging đặc biệt hữu ích khi symptom xuất hiện sau nhiều merges.

**Ví dụ:**
Một endpoint bắt đầu trả sai timezone. Developer đánh dấu release trước là `good`, HEAD là `bad`, rồi chạy script integration test qua `git bisect run`; Git thu hẹp regression về commit thay đổi mapping configuration.

**Lưu ý:**
Bisect chỉ đáng tin khi phép kiểm tra deterministic. Database state, feature flags hoặc external dependencies không ổn định có thể khiến commit bị phân loại sai; merge commits và build-breaking commits cũng cần xử lý cẩn thận.

## 🧠 Software Design

### Design 1 — Saga không biến distributed workflow thành ACID transaction

**Khái niệm:**
Saga chia workflow nhiều services thành chuỗi local transactions và dùng events/commands cùng compensating actions để xử lý failure. Nó quản lý tiến trình và recovery thay vì cung cấp atomic rollback xuyên services.

**Vấn đề nó giải quyết:**
Checkout có thể cần Order, Payment và Inventory thuộc các boundaries khác nhau. Distributed transaction/2PC thường không khả dụng hoặc không đáng chi phí, nhưng hệ thống vẫn cần biết phải làm gì khi bước thứ ba thất bại sau khi hai bước trước đã commit.

**Ví dụ thực tế:**
Order được tạo, payment được authorize, nhưng inventory reservation thất bại. Saga chuyển Order sang failed/cancelled state và gửi command void/refund payment theo business rule, đồng thời ghi nhận trạng thái để retry compensation nếu payment provider tạm lỗi.

**Trade-off:**
Saga tăng khả năng phục hồi workflow phân tán nhưng đưa eventual consistency, intermediate states, duplicate messages và compensation logic vào domain. Compensation không phải lúc nào cũng hoàn tác hoàn hảo; email đã gửi hoặc shipment đã rời kho có thể không thể “rollback”.

**Middle → Senior insight:**
Middle developer cần implement idempotent steps và hiểu state chuyển qua nhiều trạng thái hợp lệ. Senior / Technical developer phải xác định orchestration/choreography, failure matrix, compensation semantics, observability và cân nhắc liệu workflow có thật sự cần tách service hay một local transaction đơn giản sẽ an toàn hơn.

### Design 2 — Cache invalidation nên bắt đầu từ consistency requirement

**Khái niệm:**
Cache strategy phải xác định dữ liệu được phép stale bao lâu và ai chịu trách nhiệm invalidation/update. TTL, explicit invalidation và event-driven refresh là các cơ chế với guarantees khác nhau, không phải lựa chọn thuần hiệu năng.

**Vấn đề nó giải quyết:**
Caching giảm database/API load nhưng tạo bản sao dữ liệu. Nếu không định nghĩa consistency window, team thường thêm cache trước rồi gặp bugs khó tái hiện khi users nhìn thấy giá, permission hoặc content cũ.

**Ví dụ thực tế:**
CMS article cho phép stale 5 phút nên cache-aside + TTL đơn giản là đủ. Nhưng user permission thay đổi cần hiệu lực gần như ngay lập tức; cache entry được namespace/version theo authorization data và invalidated theo security-sensitive workflow thay vì chờ TTL dài.

**Trade-off:**
TTL đơn giản và resilient nhưng cho phép stale data; explicit/event invalidation giảm staleness nhưng thêm coupling, message failure và race conditions. Cache càng gần user như CDN/browser thì invalidation càng khó kiểm soát tức thời.

**Middle → Senior insight:**
Middle developer cần chọn cache key đầy đủ và xử lý miss/failure an toàn. Senior / Technical developer phải phân loại dữ liệu theo staleness tolerance, security impact và source of truth, rồi quyết định cache layer/invalidation mechanism thay vì áp một policy cho toàn hệ thống.

### Design 3 — Database transaction boundary nên bám theo business invariant

**Khái niệm:**
Transaction boundary nên bao quanh các thay đổi phải cùng thành công để giữ invariant, không mặc định trùng với toàn bộ HTTP request hoặc một application service dài. Transaction càng rộng, lock/resource lifetime và contention càng lớn.

**Vấn đề nó giải quyết:**
Nếu transaction quá nhỏ, business state có thể commit một nửa; nếu quá lớn, application giữ locks/connections trong lúc gọi external systems hoặc thực hiện work không cần atomicity, làm throughput và reliability giảm.

**Ví dụ thực tế:**
Đặt Order và OrderLines cần commit atomically trong SQL transaction. Gửi confirmation email không nằm trong transaction đó; thay vào đó, transaction ghi Outbox record và asynchronous publisher xử lý email/event sau commit.

**Trade-off:**
Boundary nhỏ giảm contention và failure surface nhưng có thể cần Outbox/eventual consistency cho side effects. Boundary lớn dễ reasoning về atomicity cục bộ nhưng tăng deadlock risk, connection occupancy và coupling với operations chậm.

**Middle → Senior insight:**
Middle developer cần biết chính xác `SaveChanges`/transaction nào bảo vệ các writes liên quan. Senior / Technical developer phải bắt đầu từ invariant và failure scenarios, tách external I/O khỏi local transaction khi có thể, rồi thiết kế recovery cho phần không thể atomic thay vì kéo transaction xuyên mọi layer.
