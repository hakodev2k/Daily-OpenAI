# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi Large Object Heap khi memory tăng dù Gen 0/1 vẫn bình thường

**Mẹo:**
Khi .NET process tăng memory sau khi xử lý file, JSON payload hoặc buffer lớn, kiểm tra Large Object Heap (LOH) thay vì chỉ nhìn số lần Gen 0/1 collection.

**Tại sao hữu ích:**
Object lớn thường đi vào LOH và được thu gom cùng Gen 2, nên allocation burst của array/string lớn có thể giữ memory lâu hơn và làm full GC đắt hơn. Điều này dễ xuất hiện ở API xử lý export, image, serialization hoặc batch data.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Theo dõi các metric như heap size, allocation rate và Gen 2 GC; nếu incident liên quan allocation lớn, capture trace/dump rồi xem object type nào chiếm phần lớn memory.

**Lưu ý:**
Đừng mặc định mọi object lớn đều là memory leak. Pooling buffer hoặc streaming có thể giảm allocation, nhưng pool quá lớn lại giữ memory cố định lâu hơn. Cần phân biệt live object, retained object và allocation churn bằng profiler.

### Tip 2 — Dùng projection trong EF Core để tránh kéo cả entity graph cho read-only API

**Mẹo:**
Với endpoint chỉ trả một tập field cố định, project trực tiếp sang DTO trong LINQ thay vì `Include` nhiều navigation rồi map sau khi materialize.

**Tại sao hữu ích:**
Projection giúp EF Core sinh SQL chỉ lấy cột cần thiết, giảm dữ liệu truyền, allocation và change-tracking overhead. Nó đặc biệt hữu ích cho list API, dashboard hoặc CMS listing có quan hệ sâu.

**Ví dụ:**
```csharp
var items = await db.Products
    .AsNoTracking()
    .Where(x => x.IsActive)
    .Select(x => new ProductListItem(
        x.Id,
        x.Name,
        x.Category.Name,
        x.Price))
    .ToListAsync(ct);
```

Thay vì `Include(x => x.Category)` rồi map toàn bộ entity, SQL có thể chỉ chọn các cột cần cho response.

**Lưu ý:**
Projection không tự động giải quyết mọi query chậm. Hãy kiểm tra generated SQL và execution plan; projection quá phức tạp cũng có thể tạo SQL khó tối ưu hoặc phần expression không translate được.

### Tip 3 — Dùng `explain()` để kiểm tra Elasticsearch query có filter đúng context hay không

**Mẹo:**
Khi Elasticsearch trả kết quả chậm hoặc relevance lạ, tách rõ full-text query khỏi exact filtering và kiểm tra query DSL thay vì nhét tất cả condition vào scoring query.

**Tại sao hữu ích:**
Các điều kiện như tenant, status, category thường không cần ảnh hưởng score. Đưa chúng vào `filter` context giúp Elasticsearch bỏ qua scoring cho phần đó và có thể tận dụng caching tốt hơn, trong khi `must`/`should` dành cho relevance.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "distributed tracing" } }
      ],
      "filter": [
        { "term": { "tenantId": "tenant-42" } },
        { "term": { "isPublished": true } }
      ]
    }
  }
}
```

Nếu score không như mong đợi, dùng Elasticsearch `_explain` cho một document cụ thể để xem contribution của từng clause.

**Lưu ý:**
Không dùng `_explain` hàng loạt trong production vì chi phí cao. Nếu query chậm, profile API và mapping/analyzer thường quan trọng hơn chỉ nhìn score explanation.

### Tip 4 — Đặt Kubernetes resource request theo dữ liệu đo được, không copy limit từ môi trường khác

**Mẹo:**
Khi container ASP.NET Core chạy trên Kubernetes, đặt CPU/memory `requests` dựa trên workload thực tế và percentiles thay vì lấy cùng một con số cho mọi service.

**Tại sao hữu ích:**
Scheduler dùng `requests` để quyết định đặt Pod vào node nào. Request quá cao làm cluster lãng phí capacity; quá thấp khiến nhiều Pod bị dồn lên cùng node và cạnh tranh CPU/memory khi traffic tăng.

**Ví dụ:**
```yaml
resources:
  requests:
    cpu: "250m"
    memory: "384Mi"
  limits:
    memory: "768Mi"
```

Sau khi chạy load test và xem production telemetry, điều chỉnh theo mức sử dụng bền vững thay vì peak ngắn bất thường.

**Lưu ý:**
CPU limit có thể tạo throttling khó nhìn thấy trong application metrics. Memory limit vượt ngưỡng có thể dẫn đến OOMKill thay vì GC tự cứu được, nên phải correlating container metrics với runtime metrics.

### Tip 5 — Khi dùng AI coding agent, bắt nó chứng minh thay đổi bằng test hoặc source reference

**Mẹo:**
Với task sửa bug hoặc refactor, yêu cầu AI coding agent chỉ ra file nguồn liên quan, assumption chính và test chứng minh behavior trước khi chấp nhận patch.

**Tại sao hữu ích:**
Agent có thể tạo code compile được nhưng dựa trên API không tồn tại, hiểu sai convention của repository hoặc viết test chỉ xác nhận implementation mới chứ không xác nhận requirement. Grounding vào source và executable evidence giảm loại lỗi này.

**Ví dụ:**
```text
Yêu cầu agent:
1. xác định root cause từ code hiện có
2. liệt kê files/contract bị ảnh hưởng
3. tạo regression test fail trước patch
4. sửa tối thiểu
5. chạy test liên quan
6. nêu assumption chưa xác minh
```

Flow này đặc biệt hữu ích cho migration, concurrency bug hoặc thay đổi có nhiều integration boundary.

**Lưu ý:**
Test do AI sinh cũng có thể sai. Đừng chấp nhận chỉ vì suite xanh; review xem test có tái hiện failure mode thực tế và có assert behavior quan trọng hay không.

## 🧠 Software Design

### Design 1 — Retry budget thay vì retry vô hạn ở mọi layer

**Khái niệm:**
Retry budget giới hạn tổng lượng retry một request hoặc workflow được phép tạo, thay vì để HTTP client, service, queue consumer và database layer mỗi nơi tự retry độc lập.

**Vấn đề nó giải quyết:**
Nếu một dependency chậm, nested retry có thể khuếch đại traffic: API retry 3 lần, service bên dưới retry 3 lần nữa, worker cũng retry broker message. Một request business nhỏ có thể biến thành hàng chục dependency calls đúng lúc hệ thống đang quá tải.

**Ví dụ thực tế:**
```text
Request gốc: 1
API layer: tối đa 2 attempts
Payment client: không retry riêng khi caller đã quản lý retry
Queue consumer: retry độc lập theo message lifecycle
```

Có thể kết hợp deadline/cancellation để toàn workflow dừng khi thời gian hữu ích đã hết.

**Trade-off:**
Retry giúp vượt transient failure nhưng tăng latency và load lên dependency đang lỗi. Budget quá nhỏ làm giảm khả năng phục hồi; quá lớn tạo retry storm và kéo dài incident.

**Middle → Senior insight:**
Middle developer cần biết chỉ retry operation an toàn hoặc idempotent và dùng backoff phù hợp. Senior / Technical developer phải thiết kế retry ownership, deadline, budget, circuit breaker và observability xuyên các layer để tránh retry amplification.

### Design 2 — Anti-Corruption Layer bảo vệ domain khỏi model của hệ thống legacy

**Khái niệm:**
Anti-Corruption Layer (ACL) chuyển đổi contract, terminology và semantics từ hệ thống bên ngoài sang model riêng của application thay vì để external model lan sâu vào domain.

**Vấn đề nó giải quyết:**
Legacy ERP, CMS hoặc vendor API thường có field name, status code và lifecycle khác business model mới. Nếu application dùng trực tiếp các type đó ở mọi layer, thay đổi provider hoặc migration sẽ kéo theo coupling lớn.

**Ví dụ thực tế:**
```text
Legacy CMS:
ContentStatus = 7
PublishDateUtc = null

ACL:
LegacyContentAdapter
-> map thành Domain ContentState.Draft
-> normalize timezone
-> translate missing fields theo business rule
```

Application layer chỉ thấy contract theo ngôn ngữ nghiệp vụ của mình.

**Trade-off:**
ACL giảm coupling và cô lập migration complexity, nhưng thêm mapping code, test và đôi khi duplicate model. Với integration nhỏ, stable và thuần CRUD, lớp translation dày có thể không đáng chi phí.

**Middle → Senior insight:**
Middle developer cần tránh leak vendor-specific type ra ngoài boundary. Senior / Technical developer phải xác định chỗ nào cần semantic translation thật sự, ownership của mapping và chiến lược chuyển đổi khi legacy system dần bị thay thế.

### Design 3 — Contract Testing cho integration quan trọng nhưng không thay thế end-to-end test

**Khái niệm:**
Contract Testing kiểm tra producer và consumer có cùng kỳ vọng về API/message contract mà không cần dựng toàn bộ production topology cho mọi test run.

**Vấn đề nó giải quyết:**
Microservice hoặc third-party integration thường fail vì field bị đổi, enum semantics khác hoặc consumer dựa vào behavior chưa được producer đảm bảo. Unit test từng service riêng lẻ không phát hiện drift contract này.

**Ví dụ thực tế:**
```text
Consumer kỳ vọng:
GET /customers/{id}
- id: string
- status: Active | Suspended

Producer pipeline:
- verify provider implementation vẫn đáp ứng contract
- reject breaking change trước deployment
```

Với message broker, contract có thể bao gồm schema, required field và backward-compatible evolution rule.

**Trade-off:**
Contract Testing phát hiện mismatch sớm và chạy nhanh hơn full E2E, nhưng không chứng minh network, authentication, routing, deployment config hay data migration thực tế đều đúng.

**Middle → Senior insight:**
Middle developer cần phân biệt unit, integration, contract và E2E test theo boundary chúng bảo vệ. Senior / Technical developer phải quyết định integration nào đáng đầu tư contract testing, ai sở hữu contract, versioning/deprecation ra sao và phần nào vẫn cần E2E coverage.
