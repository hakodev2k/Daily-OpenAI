# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate configuration lúc startup thay vì đợi request đầu tiên mới vỡ

**Mẹo:**
Với configuration bắt buộc trong ASP.NET Core, dùng strongly typed Options cùng validation và `ValidateOnStart()` để application fail fast khi environment thiếu hoặc sai giá trị quan trọng.

**Tại sao hữu ích:**
Nếu connection endpoint, timeout, tenant setting hoặc API credential bị cấu hình sai nhưng chỉ được đọc khi request đầu tiên đi qua một code path hiếm, deployment có thể được đánh dấu “healthy” dù thực tế chưa sẵn sàng phục vụ đầy đủ. Fail fast biến configuration error thành deployment error rõ ràng, dễ rollback và dễ phát hiện trong CI/CD hơn.

**Ví dụ:**
```csharp
public sealed class PaymentOptions
{
    [Required]
    public string BaseUrl { get; init; } = string.Empty;

    [Range(1, 120)]
    public int TimeoutSeconds { get; init; } = 10;
}

builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

Nếu `Payment:BaseUrl` bị thiếu, process không nên tiếp tục như thể deployment hợp lệ.

**Lưu ý:**
Không validate secret bằng cách log giá trị secret khi lỗi. Validation chỉ nên xác nhận presence/format cần thiết; tránh biến startup diagnostics thành nơi rò rỉ credential.

### Tip 2 — Khi query SQL Server “lúc nhanh lúc chậm”, nghĩ đến parameter sensitivity trước khi sửa index

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có performance rất khác nhau theo parameter, kiểm tra execution plan, data distribution và parameter sensitivity thay vì mặc định thêm index.

**Tại sao hữu ích:**
Optimizer có thể compile plan phù hợp cho một parameter có selectivity cao nhưng plan đó lại tệ cho parameter trả về lượng row rất lớn. Ví dụ một tenant nhỏ có 50 order trong khi tenant lớn có 8 triệu order; cùng một access path có thể không phù hợp cho cả hai.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Status
FROM Orders
WHERE TenantId = @tenantId
  AND CreatedAt >= @fromDate;
```

Nếu `TenantId = 12` trả 100 rows nhưng `TenantId = 9001` trả hàng triệu rows, hãy so sánh actual plan của cả hai trường hợp, cardinality estimate, statistics và plan cache behavior.

**Lưu ý:**
Không dùng `OPTION (RECOMPILE)` hoặc `OPTIMIZE FOR UNKNOWN` như thuốc chữa chung. Recompile tăng CPU compile cost; generic plan có thể làm mọi trường hợp chỉ “trung bình”. Cần chọn mitigation theo workload thật và version SQL Server đang chạy.

### Tip 3 — Với Azure Service Bus, lock timeout không đồng nghĩa message chỉ được xử lý một lần

**Mẹo:**
Khi dùng Peek-Lock, thiết kế consumer với giả định message có thể được delivery lại nếu xử lý lâu hơn lock duration, process crash, lock renewal thất bại hoặc completion thất bại.

**Tại sao hữu ích:**
Azure Service Bus cung cấp at-least-once delivery trong các flow phổ biến. Nếu consumer đã gọi external API tạo side effect nhưng chết trước khi `CompleteMessageAsync`, broker có thể giao message lại và side effect bị lặp nếu handler không idempotent.

**Ví dụ:**
```csharp
processor.ProcessMessageAsync += async args =>
{
    var command = args.Message.Body.ToObjectFromJson<GenerateInvoice>();

    if (await inbox.HasProcessedAsync(command.MessageId))
    {
        await args.CompleteMessageAsync(args.Message);
        return;
    }

    await invoiceService.GenerateAsync(command);
    await inbox.MarkProcessedAsync(command.MessageId);
    await args.CompleteMessageAsync(args.Message);
};
```

`MessageId` hoặc business idempotency key phải gắn với operation thực sự, không chỉ với một lần receive.

**Lưu ý:**
Auto lock renewal giúp workload dài nhưng không biến delivery thành exactly-once. Nếu side effect đi qua hệ thống ngoài transaction boundary, vẫn cần deduplication/idempotency strategy.

### Tip 4 — Đừng giữ derived state trong Vue/React nếu có thể tính từ source state

**Mẹo:**
Nếu một giá trị có thể tính hoàn toàn từ state hiện có, ưu tiên `computed` trong Vue hoặc derived value/memoization phù hợp trong React thay vì lưu thêm một bản state rồi phải đồng bộ thủ công.

**Tại sao hữu ích:**
Duplicated state tạo nhiều source of truth. Khi một update path quên cập nhật bản sao, UI có thể hiển thị dữ liệu cũ dù state gốc đã đúng. Bug này thường xuất hiện khi filter, sort, pagination và async update kết hợp với nhau.

**Ví dụ với Vue:**
```ts
const products = ref<Product[]>([])
const search = ref('')

const filteredProducts = computed(() => {
  const q = search.value.trim().toLowerCase()
  return products.value.filter(x => x.name.toLowerCase().includes(q))
})
```

Không cần `watch` rồi copy kết quả vào một `ref` thứ hai chỉ để render.

**Lưu ý:**
Không memoize mọi phép tính nhỏ. Memoization cũng có lifecycle và invalidation cost. Chỉ dùng khi computation đáng kể hoặc identity stability thực sự cần thiết.

### Tip 5 — Dùng `git bisect` để thu hẹp regression thay vì đọc hàng chục commit bằng mắt

**Mẹo:**
Khi biết một phiên bản cũ còn tốt và HEAD đã lỗi, dùng `git bisect` để binary-search commit gây regression; nếu có test/command tái hiện lỗi, có thể tự động hóa toàn bộ quá trình.

**Tại sao hữu ích:**
Với 128 commit nghi vấn, binary search chỉ cần khoảng 7 lần kiểm tra để tìm candidate thay vì review tuần tự 128 commit. Đây là công cụ đặc biệt hữu ích với performance regression, rendering bug hoặc behavior thay đổi mà log không chỉ thẳng nguyên nhân.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj --filter CheckoutRegression
```

Git sẽ checkout các midpoint commit và dùng exit code của test để thu hẹp phạm vi.

**Lưu ý:**
Test dùng cho `bisect run` phải deterministic. Nếu test flaky, bisect có thể chỉ ra sai commit và làm investigation lệch hướng.

## 🧠 Software Design

### Design 1 — Retry và Circuit Breaker giải quyết hai failure mode khác nhau

**Khái niệm:**
Retry xử lý transient failure bằng cách thử lại sau một khoảng delay/backoff. Circuit Breaker ngừng gửi request tạm thời khi dependency đang fail liên tục, cho dependency thời gian phục hồi và bảo vệ caller khỏi tích tụ thêm work vô ích.

**Vấn đề nó giải quyết:**
Nếu external API đang timeout diện rộng, retry ba lần trên mỗi request có thể biến 1.000 request thành gần 3.000 outbound attempt, làm dependency càng quá tải và giữ connection/thread/resource lâu hơn. Circuit Breaker giảm amplification khi failure không còn mang tính transient đơn lẻ.

**Ví dụ thực tế:**
Pricing API thỉnh thoảng trả `503` trong vài trăm milliseconds: retry với exponential backoff + jitter có thể hợp lý. Nhưng nếu error rate vượt threshold trong một khoảng thời gian, circuit mở trong 20 giây và caller dùng fallback hoặc trả degraded response thay vì tiếp tục bắn request.

**Trade-off:**
Retry tăng khả năng vượt qua lỗi ngắn nhưng tăng latency và load. Circuit Breaker giảm load khi dependency hỏng nhưng có thể từ chối request trong lúc dependency vừa phục hồi. Policy sai có thể tạo retry storm hoặc circuit flap.

**Middle → Senior insight:**
Middle developer cần phân biệt lỗi retryable/non-retryable và tôn trọng timeout/cancellation. Senior / Technical developer phải thiết kế timeout budget, retry count, jitter, circuit threshold, fallback semantics và observability theo SLO của toàn request path — không cấu hình từng policy độc lập mà bỏ qua latency budget tổng.

### Design 2 — Module ownership trong Modular Monolith phải bao gồm cả data boundary

**Khái niệm:**
Modular Monolith chỉ thực sự modular khi mỗi module sở hữu business model và data access của mình. Module khác không nên query trực tiếp table nội bộ chỉ vì tất cả cùng nằm trong một database.

**Vấn đề nó giải quyết:**
Nếu `Ordering` đọc trực tiếp bảng của `Catalog`, còn `Billing` update trực tiếp bảng `Orders`, compile-time folder boundary chỉ mang tính trang trí. Schema trở thành shared global model, thay đổi ở một module có blast radius trên toàn hệ thống và việc tách service sau này gần như không có seam rõ ràng.

**Ví dụ thực tế:**
```text
Modules/
  Catalog/
    Application/
    Domain/
    Infrastructure/
  Ordering/
    Application/
    Domain/
    Infrastructure/
```

`Ordering` cần product snapshot thì gọi contract/query public của `Catalog` hoặc nhận event để duy trì dữ liệu cần thiết, thay vì lấy `CatalogDbContext` và join trực tiếp bảng `Products`.

**Trade-off:**
Data ownership tăng cohesion và khả năng evolution, nhưng có thể dẫn tới duplicate read data, mapping và eventual consistency. Với một monolith nhỏ, boundary quá cứng cho mọi lookup đơn giản cũng có thể tạo ceremony không cần thiết.

**Middle → Senior insight:**
Middle developer cần tuân thủ public contract của module. Senior / Technical developer phải quyết định nơi nào cần strict ownership, nơi nào shared reference data chấp nhận được, transaction nào cần giữ local và cách tiến hóa database schema mà không biến monolith thành distributed system giả lập trong cùng process.

### Design 3 — Expand–Migrate–Contract cho database migration không downtime

**Khái niệm:**
Thay vì deploy một schema breaking change cùng lúc với code mới, chia migration thành các bước tương thích ngược: mở rộng schema, chuyển dữ liệu/traffic, rồi mới loại bỏ schema cũ sau khi mọi phiên bản application không còn phụ thuộc vào nó.

**Vấn đề nó giải quyết:**
Trong rolling deployment, code cũ và code mới có thể chạy đồng thời. Nếu migration rename/drop column ngay lập tức, instance cũ có thể crash trong khi instance mới vẫn healthy. Database vì vậy cần contract tương thích qua giai đoạn coexistence.

**Ví dụ thực tế:**
Muốn đổi `Customers.FullName` thành `FirstName` + `LastName`:

1. **Expand:** thêm `FirstName`, `LastName`, vẫn giữ `FullName`.
2. **Migrate:** backfill data và deploy code có thể đọc schema mới, đồng thời dual-write nếu cần trong giai đoạn chuyển tiếp.
3. **Switch:** toàn bộ read path dùng fields mới; theo dõi telemetry và rollback window.
4. **Contract:** ở deployment sau, xóa `FullName` khi chắc chắn không còn consumer cũ.

**Trade-off:**
Cách này giảm deployment blast radius và hỗ trợ rollback, nhưng tạo migration nhiều bước, temporary duplication và cleanup discipline. Dual-write kéo dài quá lâu có thể tạo inconsistency giữa hai representation.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible và hiểu thứ tự deploy code/schema. Senior / Technical developer phải thiết kế compatibility window, backfill strategy, lock/transaction impact trên bảng lớn, rollback plan và exit criteria để temporary schema không trở thành technical debt vĩnh viễn.
