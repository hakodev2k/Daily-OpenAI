# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer lớn, sống ngắn và xuất hiện thường xuyên

**Mẹo:**
Khi xử lý stream, serialization hoặc network payload có buffer tương đối lớn và được tạo lặp lại với tần suất cao, cân nhắc thuê buffer từ `ArrayPool<T>` thay vì liên tục cấp phát mảng mới.

**Tại sao hữu ích:**
Mảng lớn tạo allocation pressure và có thể đẩy object lên Large Object Heap. Reuse buffer giúp giảm số lần GC phải xử lý, đặc biệt trong hot path có throughput cao.

**Ví dụ:**
```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);

try
{
    var read = await stream.ReadAsync(
        buffer.AsMemory(0, buffer.Length),
        cancellationToken);

    Process(buffer.AsSpan(0, read));
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Buffer trả về pool có thể lớn hơn kích thước yêu cầu và có thể còn dữ liệu cũ. Không dùng dữ liệu ngoài phạm vi đã ghi; với dữ liệu nhạy cảm có thể cần clear buffer trước khi trả lại pool.

### Tip 2 — Với SQL Server, kiểm tra parameter sensitivity trước khi ép một execution plan cố định

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query lúc nhanh lúc chậm tùy input, kiểm tra execution plan theo nhiều giá trị parameter thay vì chỉ nhìn một lần chạy.

**Tại sao hữu ích:**
Một plan tốt cho parameter trả vài row có thể rất tệ cho parameter trả hàng triệu row. Cardinality khác biệt có thể khiến optimizer chọn nested loops, hash join, seek hoặc scan không phù hợp với mọi trường hợp.

**Ví dụ:**
```sql
SELECT Id, CustomerId, Status, CreatedAt
FROM Orders
WHERE CustomerId = @CustomerId;
```

`CustomerId` A có 20 order nhưng B có 2 triệu order. Trong incident, so sánh actual execution plan, estimated/actual row count, Query Store history và runtime theo nhiều nhóm parameter trước khi áp dụng hint.

**Lưu ý:**
Đừng coi `OPTION (RECOMPILE)` hay plan forcing là fix mặc định. Recompile tăng CPU; plan cố định có thể trở nên tệ khi data distribution thay đổi.

### Tip 3 — Dùng deployment slot để kiểm tra App Service trước khi chuyển traffic

**Mẹo:**
Với Azure App Service, deploy version mới vào staging slot, chạy smoke test và health check trước khi swap sang production thay vì deploy trực tiếp lên slot đang phục vụ user.

**Tại sao hữu ích:**
Deployment thành công không đồng nghĩa application đã sẵn sàng nhận traffic. Slot cho phép warm-up application, kiểm tra configuration và dependency trước khi cutover.

**Ví dụ:**
```text
Build artifact v5.3.0
-> deploy Staging slot
-> warm-up
-> smoke test /health/ready
-> verify key dependency
-> swap Staging -> Production
```

Nếu version mới có regression rõ ngay sau swap, team có thể swap ngược nhanh hơn so với rebuild một artifact khác.

**Lưu ý:**
Phải phân biệt setting nào là slot-specific. Connection string hoặc secret gắn nhầm slot có thể khiến staging dùng production dependency ngoài ý muốn. Database migration cũng phải tương thích với cả hai version trong giai đoạn chuyển đổi.

### Tip 4 — Integration test database nên kiểm tra SQL thật thay vì mock `DbSet` quá sâu

**Mẹo:**
Với query EF Core quan trọng, dùng integration test chạy trên database engine thật hoặc environment tương thích cao thay vì chỉ mock repository/`DbSet`.

**Tại sao hữu ích:**
Mock thường không phát hiện lỗi query translation, collation, transaction, constraint hoặc khác biệt giữa LINQ-to-Objects và SQL thật.

**Ví dụ:**
Một test có thể:
```text
1. tạo database test sạch
2. apply migrations
3. seed dataset có edge case
4. gọi query/application service thật
5. assert result và transaction behavior
```

Nếu production dùng PostgreSQL hoặc SQL Server, test quan trọng trên đúng engine giúp bắt lỗi mà in-memory provider không thể mô phỏng.

**Lưu ý:**
Không cần biến toàn bộ test suite thành integration test. Unit test vẫn phù hợp cho domain rule thuần; integration test nên tập trung vào boundary có behavior phụ thuộc database/framework thật.

### Tip 5 — Trong CMS, content type nên model theo ý nghĩa nội dung thay vì layout cụ thể của một page

**Mẹo:**
Khi thiết kế Optimizely CMS hoặc CMS tương tự, tạo content type dựa trên semantic role như `Hero`, `ArticleTeaser`, `ContactCard` thay vì tên layout quá cụ thể như `LeftColumnBlueBox`.

**Tại sao hữu ích:**
Content model gắn với layout làm nội dung khó reuse và khiến redesign frontend buộc migration content dù business meaning không đổi. Semantic modeling giúp presentation thay đổi độc lập hơn.

**Ví dụ:**
Thay vì:
```text
ThreeColumnPromoBlock
```

có thể model:
```text
PromoCard
- Heading
- Summary
- Image
- Link
```

Layout ba cột là concern của rendering/container, không nhất thiết là identity của content.

**Lưu ý:**
Đừng tạo block siêu-generic có hàng chục option layout. Nếu editor phải hiểu quá nhiều presentation flag, content model lại trở thành một page builder khó kiểm soát.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency khi nhiều user có thể sửa cùng một record

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng dữ liệu nhưng phát hiện conflict tại thời điểm update bằng version/token thay vì giữ lock dài từ lúc đọc đến lúc ghi.

**Vấn đề nó giải quyết:**
Trong web application, user A và B cùng mở một record. A save trước, B save sau với dữ liệu cũ. Nếu không kiểm tra version, thay đổi của A có thể bị B ghi đè âm thầm.

**Ví dụ thực tế:**
```text
Read Product: Version = 17
A updates -> Version = 18
B submits update expecting Version = 17
-> update affects 0 rows
-> report concurrency conflict
```

EF Core có thể dùng concurrency token như `rowversion` trên SQL Server hoặc một version field phù hợp.

**Trade-off:**
Optimistic concurrency tránh lock lâu và phù hợp workload conflict thấp, nhưng application phải có UX/merge/retry strategy khi conflict xảy ra. Pessimistic locking phù hợp hơn khi conflict rất đắt hoặc critical section thực sự cần serialize.

**Middle → Senior insight:**
Middle developer cần không nuốt `DbUpdateConcurrencyException` và phải trả conflict rõ cho caller. Senior / Technical developer phải quyết định conflict resolution là reject, retry, merge hay serialize dựa trên business invariant và cost của lost update.

### Design 2 — Saga Orchestration vs Choreography cho workflow xuyên nhiều service

**Khái niệm:**
Saga chia một business workflow thành nhiều local transaction và compensating action. Orchestration dùng một coordinator điều khiển sequence; Choreography để service phản ứng với event của nhau mà không có coordinator trung tâm.

**Vấn đề nó giải quyết:**
Một workflow như đặt hàng có thể chạm Order, Payment, Inventory và Shipping nhưng không thể dựa vào một ACID transaction xuyên nhiều service một cách đơn giản và đáng tin cậy.

**Ví dụ thực tế:**
Orchestration:
```text
Order Saga
-> reserve inventory
-> charge payment
-> create shipment
-> nếu payment fail: release inventory
```

Choreography:
```text
OrderPlaced
-> Inventory reserves -> InventoryReserved
-> Payment reacts -> PaymentCaptured
-> Shipping reacts
```

**Trade-off:**
Orchestration làm flow và recovery rõ hơn nhưng tạo coordinator cần vận hành. Choreography giảm central coordination nhưng flow có thể khó nhìn, khó debug và dễ tạo event-chain coupling khi số bước tăng.

**Middle → Senior insight:**
Middle developer cần hiểu local transaction, idempotency và compensating action. Senior / Technical developer phải chọn coordination style theo workflow complexity, observability, ownership team, failure recovery và mức coupling chấp nhận được.

### Design 3 — Contract Testing cho integration boundary thay vì chỉ test implementation nội bộ

**Khái niệm:**
Contract Testing kiểm tra producer và consumer có cùng hiểu một API/message contract hay không, tập trung vào boundary giữa hệ thống thay vì cách từng service implement bên trong.

**Vấn đề nó giải quyết:**
Một service có thể pass toàn bộ unit test nhưng vẫn phá consumer bằng cách đổi field, status code hoặc event schema. End-to-end test toàn hệ thống thường chậm và khó bao phủ mọi tổ hợp version.

**Ví dụ thực tế:**
Consumer kỳ vọng:
```json
{
  "id": "123",
  "status": "Paid"
}
```

Contract test xác nhận producer vẫn cung cấp field và semantics cần thiết hoặc schema evolution tương thích với consumer hiện tại.

**Trade-off:**
Contract test cho feedback nhanh và giảm integration regression nhưng thêm artifact/version management và không thay thế end-to-end test cho behavior xuyên nhiều dependency. Contract quá chặt cũng có thể khóa implementation không cần thiết.

**Middle → Senior insight:**
Middle developer cần phân biệt public contract với implementation detail. Senior / Technical developer phải thiết kế ownership, compatibility policy, CI verification và quyết định boundary nào đáng có contract test dựa trên release independence và blast radius.
