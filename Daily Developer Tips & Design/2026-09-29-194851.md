# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian

**Mẹo:**
Với .NET 8+, inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` trong business logic cần kiểm thử thời gian.

**Tại sao hữu ích:**
Clock toàn cục làm test phụ thuộc thời điểm thật, dễ flaky ở logic expiration, retry window hoặc scheduled processing. `TimeProvider` biến thời gian thành dependency có thể kiểm soát mà không cần tạo abstraction riêng chỉ để mock clock.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => clock.GetUtcNow() >= expiresAt;
}
```
Trong test có thể dùng controllable/fake time provider để tiến thời gian qua expiry boundary mà không `Task.Delay`.

**Lưu ý:**
Đừng biến mọi chỗ đọc thời gian thành abstraction phức tạp. Cần thống nhất UTC cho persistence/comparison và chỉ chuyển timezone ở boundary phù hợp; fake clock cũng không thay thế test concurrency thực tế.

### Tip 2 — Đọc execution plan khi predicate làm index mất khả năng seek

**Mẹo:**
Khi SQL query chậm dù column đã có index, kiểm tra predicate có biến indexed column bằng function/cast hay không thay vì kết luận “index không hoạt động”.

**Tại sao hữu ích:**
Predicate không sargable như `CAST(CreatedAt AS date) = @day` có thể khiến optimizer khó seek trực tiếp theo range trên B-tree. Viết predicate theo range giúp engine xác định vùng index cần đọc.

**Ví dụ:**
```sql
-- Tránh khi cần tận dụng index CreatedAt
WHERE CAST(CreatedAt AS date) = @day

-- Thường phù hợp hơn
WHERE CreatedAt >= @day
  AND CreatedAt < DATEADD(day, 1, @day)
```
Sau đó so sánh actual execution plan, logical reads và row estimates trước/sau.

**Lưu ý:**
Không rewrite query chỉ dựa trên “rule”. Optimizer, computed indexes và data distribution có thể thay đổi kết quả; execution plan và workload thật mới là bằng chứng.

### Tip 3 — Redis cache stampede: bảo vệ lúc key nóng hết hạn

**Mẹo:**
Với key đắt tiền và traffic cao, đừng chỉ đặt TTL giống nhau rồi để mọi request cache-miss cùng lúc. Dùng jitter cho TTL và cân nhắc single-flight/per-key coordination ở nơi phù hợp.

**Tại sao hữu ích:**
Khi một hot key hết hạn, hàng trăm request có thể đồng thời truy vấn database hoặc upstream để rebuild cùng dữ liệu. Cache vẫn “hoạt động”, nhưng thời điểm expiration tạo load spike đủ làm dependency sập.

**Ví dụ:**
Catalog API cache một navigation tree tốn 800 ms để dựng. TTL được random nhẹ quanh baseline; khi miss, một request rebuild còn các request cùng instance chờ cùng operation thay vì cùng đánh SQL.

**Lưu ý:**
Distributed lock không phải mặc định tốt nhất: lock failure, lease expiry và nhiều region làm complexity tăng. Với dữ liệu cho phép stale, stale-while-revalidate có thể đơn giản và resilient hơn.

### Tip 4 — Vue/React: hủy request cũ khi search input thay đổi

**Mẹo:**
Với autocomplete/search-as-you-type, dùng `AbortController` để cancel request không còn cần thiết và bảo vệ UI khỏi response cũ ghi đè response mới.

**Tại sao hữu ích:**
Network response không đảm bảo về đúng thứ tự gửi. Query `"ca"` chậm có thể về sau `"cat"` và ghi state bằng kết quả lỗi thời; cancellation còn giảm work vô ích ở client và có thể truyền tín hiệu abort xuống backend.

**Ví dụ:**
```ts
controller?.abort();
controller = new AbortController();

const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
  signal: controller.signal
});
```
UI cũng có thể giữ request sequence để bỏ qua stale response nếu downstream không thực sự dừng được work.

**Lưu ý:**
Abort ở browser không đồng nghĩa mọi downstream operation đã rollback. Backend vẫn cần propagate cancellation có chủ đích và side-effecting request phải có semantics riêng.

### Tip 5 — Dùng `git reflog` để cứu commit tưởng đã mất

**Mẹo:**
Sau `reset --hard`, rebase hoặc branch deletion nhầm, kiểm tra `git reflog` trước khi cho rằng commit đã biến mất.

**Tại sao hữu ích:**
Reflog ghi lại chuyển động của local refs/HEAD, nên commit không còn reachable từ branch hiện tại thường vẫn có thể được tìm lại trước khi Git garbage-collect object.

**Ví dụ:**
```bash
git reflog
git show <sha>
git branch recovery/<name> <sha>
```
Sau một interactive rebase sai, developer có thể tạo recovery branch từ SHA cũ rồi đối chiếu thay đổi thay vì cố tái tạo code thủ công.

**Lưu ý:**
Reflog chủ yếu là local và có retention; nó không phải backup strategy. Đừng chạy cleanup/aggressive GC khi đang phục hồi repository và luôn kiểm tra SHA trước khi reset tiếp.

## 🧠 Software Design

### Design 1 — Cache-aside và consistency boundary

**Khái niệm:**
Cache-aside để application đọc cache trước, cache miss thì đọc source of truth rồi populate cache. Điều quan trọng không phải API Redis, mà là xác định consistency nào business thực sự yêu cầu.

**Vấn đề nó giải quyết:**
Read-heavy workload có thể gây latency và tải database cao, nhưng cache thêm một bản sao dữ liệu có thể stale. Nếu không định nghĩa tolerance, invalidation trở thành tập hợp các “fix” ngẫu nhiên.

**Ví dụ thực tế:**
Product description có thể chấp nhận stale vài phút nên TTL cache đơn giản phù hợp. Inventory dùng để quyết định checkout lại cần authoritative validation gần transaction boundary; không nên tin cache chỉ vì product page vừa đọc từ Redis.

**Trade-off:**
Cache giảm latency/load nhưng thêm invalidation, stampede, serialization, memory cost và failure mode. Khi Redis lỗi, hệ thống còn phải quyết định bypass, fail closed hay degrade theo từng loại dữ liệu.

**Middle → Senior insight:**
Middle cần implement cache key, TTL, invalidation và fallback đúng. Senior / Technical phải phân loại dữ liệu theo consistency requirement, chọn nơi cache nằm trong request path, định nghĩa behavior khi cache outage và chứng minh rằng cache giải quyết bottleneck đo được.

### Design 2 — Optimistic vs pessimistic concurrency theo mức contention

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor làm việc mà không giữ lock dài rồi phát hiện conflict khi commit; pessimistic concurrency giữ quyền truy cập sớm hơn để ngăn conflict xảy ra trong critical section.

**Vấn đề nó giải quyết:**
Khi nhiều request cùng thay đổi một resource, hệ thống phải bảo vệ invariant mà không tạo contention hoặc silent lost update.

**Ví dụ thực tế:**
Chỉnh sửa customer profile ít conflict phù hợp với version token và trả `409 Conflict` khi stale. Một thao tác cấp một tài nguyên khan hiếm có contention cao có thể cần database locking/atomic update phù hợp thay vì liên tục retry optimistic conflicts.

**Trade-off:**
Optimistic approach giảm lock duration nhưng conflict cao sẽ tạo retry/rework. Pessimistic locking dễ reasoning cho một số critical section nhưng tăng blocking, deadlock risk và giảm throughput nếu transaction giữ lock lâu.

**Middle → Senior insight:**
Middle cần xử lý conflict/transaction đúng API. Senior / Technical phải đánh giá contention thực, invariant, lock scope, retry economics và failure behavior; lựa chọn concurrency strategy theo workload thay vì áp một pattern cho toàn hệ thống.

### Design 3 — Observability là một phần của API/integration design

**Khái niệm:**
Thiết kế integration nên xác định ngay correlation, metrics và trace boundaries cần để vận hành, thay vì thêm logging sau khi production đã có incident.

**Vấn đề nó giải quyết:**
Trong chuỗi API → Service Bus → worker → third-party, một lỗi “order chưa đồng bộ” không thể chẩn đoán đáng tin nếu mỗi component chỉ có log text rời rạc và không có stable business/correlation identifiers.

**Ví dụ thực tế:**
Order flow propagate trace context qua HTTP/message metadata, log structured `OrderId` và `MessageId`, đo processing latency, delivery count, DLQ count và dependency failures. Khi backlog tăng, team đi theo symptom → metric → trace → dependency evidence thay vì grep ngẫu nhiên.

**Trade-off:**
Telemetry tăng storage/cost và có nguy cơ high cardinality hoặc lộ sensitive data. Quá nhiều log không cấu trúc cũng làm signal-to-noise tệ hơn chứ không tạo observability.

**Middle → Senior insight:**
Middle cần tạo structured telemetry và correlation đúng boundary. Senior / Technical phải định nghĩa SLI/SLO, sampling, cardinality, privacy, alert semantics và telemetry contract xuyên service để incident có thể được điều tra mà không phụ thuộc “người nhớ hệ thống”.
