# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng tăng ThreadPool khi chưa chứng minh được ThreadPool starvation

**Mẹo:**
Khi ASP.NET Core latency tăng nhưng CPU chưa bão hòa, kiểm tra ThreadPool queue, thread count và blocking calls trước khi chỉnh `ThreadPool.SetMinThreads`. Tìm đặc biệt các đoạn sync-over-async như `.Result`, `.Wait()` hoặc synchronous I/O trên request path.

**Tại sao hữu ích:**
Worker threads bị giữ bởi blocking work khiến request mới phải xếp hàng. Runtime có thể bổ sung threads nhưng ramp-up không tức thời, nên latency tăng mạnh dù CPU còn rảnh. Loại bỏ blocking thường xử lý nguyên nhân tốt hơn việc chỉ cấp thêm threads.

**Ví dụ:**
Sau deployment, p95 tăng từ 200 ms lên 7 giây trong khi CPU chỉ 40%. `dotnet-counters` cho thấy ThreadPool queue tăng liên tục; trace phát hiện middleware gọi asynchronous SDK bằng `.Result`. Chuyển call chain sang `await` làm queue và latency trở lại bình thường.

**Lưu ý:**
Queue tăng không tự động chứng minh starvation; downstream latency hoặc CPU saturation cũng có thể tạo backlog. Tăng minimum threads đôi khi hữu ích cho workload đặc thù, nhưng có thể che nguyên nhân và tăng contention nếu dùng như fix mặc định.

### Tip 2 — Keyset pagination tránh chi phí và sai lệch của `OFFSET` ở dataset lớn

**Mẹo:**
Với feed hoặc danh sách lớn, cân nhắc keyset pagination dựa trên ordering deterministic như `(CreatedAt, Id)` thay vì tăng `OFFSET` theo page number.

**Tại sao hữu ích:**
Offset lớn thường buộc database đi qua nhiều rows trước khi trả page cần thiết. Insert/delete giữa hai requests còn có thể làm records bị lặp hoặc bỏ sót. Keyset tiếp tục từ vị trí cuối đã đọc và có thể tận dụng index range hiệu quả hơn.

**Ví dụ:**
Thay vì `ORDER BY CreatedAt DESC OFFSET 100000 ROWS FETCH NEXT 50 ROWS ONLY`, API nhận cursor chứa `CreatedAt` và `Id` cuối page trước, rồi query records đứng sau cursor theo cùng composite ordering/index.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp đến page bất kỳ. Ordering phải unique và ổn định; chỉ dùng `CreatedAt` có thể làm mất records khi nhiều rows có cùng timestamp.

### Tip 3 — Redis distributed lock cần lease semantics, không chỉ `SET NX`

**Mẹo:**
Nếu dùng Redis để coordination, lock nên có expiration và ownership token; khi release phải chỉ xóa lock nếu token vẫn thuộc caller. Thiết kế luôn trường hợp process chạy lâu hơn lease hoặc Redis/network xảy ra partial failure.

**Tại sao hữu ích:**
Một process có thể pause hoặc mất kết nối đến khi lock hết hạn; process khác sau đó sở hữu lock mới. Nếu process cũ thức dậy và `DEL` key vô điều kiện, nó có thể xóa lock của owner mới và cho hai workers chạy critical section đồng thời.

**Ví dụ:**
Scheduled job dùng key `jobs:billing` với random token và TTL. Release thực hiện compare-and-delete atomically bằng script. Nếu job có thể chạy lâu, team phải xác định renewal/fencing strategy thay vì chỉ kéo TTL lên một giá trị rất lớn.

**Lưu ý:**
Distributed lock không biến distributed workflow thành transaction. Với correctness-critical state, database constraint, idempotency hoặc fencing token thường cần thiết hơn; đừng dùng lock như lớp bảo vệ duy nhất cho business invariant.

### Tip 4 — CORS không phải cơ chế authorization

**Mẹo:**
Dùng CORS để kiểm soát browser origin nào được phép đọc/gửi cross-origin requests theo browser policy, nhưng vẫn xác thực và authorize mọi API request ở server bằng identity/permission thực sự.

**Tại sao hữu ích:**
CORS được browser thực thi; `curl`, backend service hoặc attacker-controlled client không bị CORS ngăn gọi API. Một endpoint chỉ dựa vào `AllowedOrigins` mà không có authorization vẫn có thể bị truy cập trực tiếp ngoài browser.

**Ví dụ:**
Admin SPA chạy ở một origin được allow gọi `/api/admin/users`. API vẫn yêu cầu authenticated token và policy `Admin`; origin hợp lệ nhưng user không có quyền vẫn nhận `403`.

**Lưu ý:**
Không kết hợp wildcard origin với credential semantics một cách tùy tiện. Cũng đừng nhầm CORS với CSRF: chúng liên quan browser security nhưng giải quyết các threat khác nhau.

### Tip 5 — CI artifact phải immutable giữa các environment

**Mẹo:**
Build application một lần, version artifact/image rõ ràng rồi promote đúng artifact đó qua test, staging và production. Inject environment configuration lúc deploy/runtime thay vì rebuild source cho từng environment.

**Tại sao hữu ích:**
Nếu production được rebuild riêng, thứ đã test không còn chính xác là thứ được deploy: dependency resolution, toolchain hoặc source state có thể khác. Immutable artifact tạo traceability và làm rollback đáng tin cậy hơn.

**Ví dụ:**
Pipeline build ASP.NET Core container image `orders:git-sha`, chạy tests/security checks rồi promote cùng digest qua staging và production. App settings, Key Vault references và connection configuration được cung cấp theo environment, không bake vào image.

**Lưu ý:**
Không nhúng secrets hoặc environment-specific endpoints vào artifact chỉ để đạt “build once”. Nếu frontend cần compile-time configuration, cân nhắc runtime configuration strategy hoặc coi generated bundle là artifact riêng có provenance rõ ràng.

## 🧠 Software Design

### Design 1 — REST vs messaging là quyết định về coupling và failure semantics

**Khái niệm:**
REST phù hợp khi caller cần response đồng bộ và dependency có thể tham gia trực tiếp vào request latency budget. Messaging phù hợp khi workflow có thể asynchronous, cần buffering hoặc muốn tách availability giữa producer và consumer.

**Vấn đề nó giải quyết:**
Chuỗi synchronous calls làm latency và availability phụ thuộc nhiều services; nhưng chuyển mọi thứ sang message lại tạo eventual consistency, khó trả kết quả tức thời và tăng complexity trong retry, ordering, observability và reconciliation.

**Ví dụ thực tế:**
Checkout cần kiểm tra một rule tức thời có thể dùng synchronous call nếu boundary hợp lý. Sau khi order được commit, gửi email, analytics và downstream fulfillment có thể đi qua events để không giữ HTTP request chờ các consumers hoàn tất.

**Trade-off:**
REST đơn giản về mental model và request/response nhưng tăng runtime coupling. Messaging giảm temporal coupling và hấp thụ burst tốt hơn, đổi lại phải xử lý duplicate delivery, poison messages, eventual consistency và operational tooling.

**Middle → Senior insight:**
Middle developer cần implement timeout/retry cho HTTP và idempotent consumer cho messaging. Senior / Technical developer phải chọn interaction style theo consistency, latency, ownership và failure requirements; không biến “decoupling” thành lý do mặc định để thêm broker.

### Design 2 — Feature Flag tách deployment khỏi release nhưng tạo state cần quản trị

**Khái niệm:**
Feature Flag cho phép code được deploy nhưng behavior chỉ bật cho user/tenant/environment được chọn. Nó hỗ trợ progressive rollout, experimentation và giảm blast radius mà không cần tạo binary khác cho mỗi nhóm.

**Vấn đề nó giải quyết:**
Một release lớn có thể technically deploy thành công nhưng business behavior mới vẫn có defect. Nếu deployment và exposure là một bước duy nhất, rollback toàn artifact có thể là lựa chọn duy nhất dù chỉ một feature gây lỗi.

**Ví dụ thực tế:**
Checkout engine mới được deploy cùng version hiện tại nhưng flag chỉ bật cho 5% tenants. Metrics về error rate và latency được so sánh trước khi tăng rollout; nếu có regression, flag tắt behavior mới mà không cần redeploy.

**Trade-off:**
Flags tăng safety nhưng tạo nhiều execution paths, test matrix và configuration state. Flag sống quá lâu trở thành technical debt; authorization hoặc security control cũng không nên được thay bằng một release flag không có guarantee phù hợp.

**Middle → Senior insight:**
Middle developer cần viết code/test cho cả trạng thái flag và tránh logic rải rác. Senior / Technical developer phải thiết kế ownership, rollout metrics, kill-switch semantics, cleanup deadline và interaction với database/schema changes để rollback thực sự khả thi.

### Design 3 — Database constraint là lớp bảo vệ invariant, không chỉ validation cuối cùng

**Khái niệm:**
Invariant có thể được kiểm tra ở application layer để cho UX/error tốt, nhưng những rule có thể biểu diễn an toàn bằng unique, foreign key, check constraint hoặc transaction semantics nên cân nhắc được bảo vệ tại database boundary.

**Vấn đề nó giải quyết:**
Hai requests concurrent có thể cùng vượt qua `if (!Exists(...))` trước khi một request commit. Application validation đơn thuần không atomic với write và vì vậy không đủ bảo vệ uniqueness hoặc referential integrity dưới concurrency.

**Ví dụ thực tế:**
Registration kiểm tra email trước để trả lỗi thân thiện, nhưng database vẫn có unique constraint trên normalized email. Nếu hai requests race, một insert thắng và request còn lại map unique-violation thành conflict thay vì tạo duplicate account.

**Trade-off:**
Constraints cung cấp correctness mạnh và tập trung nhưng không biểu diễn tốt mọi business rule; constraint phức tạp có thể tăng coupling vào database và migration difficulty. Application vẫn cần translate database errors thành domain/API semantics rõ ràng.

**Middle → Senior insight:**
Middle developer cần hiểu validation không thay thế concurrency-safe constraint và phải xử lý violation đúng. Senior / Technical developer phải quyết định invariant nào thuộc domain code, database constraint hay coordination mechanism dựa trên transaction boundary, concurrency và ownership của dữ liệu.
