# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `ArrayPool<T>` chỉ đáng dùng khi allocation thật sự nằm trên hot path

**Mẹo:**
Với buffer tạm có kích thước đáng kể và được tạo với tần suất cao, `ArrayPool<T>.Shared` có thể giảm allocation/GC pressure bằng cách tái sử dụng arrays. Chỉ áp dụng sau khi profiler cho thấy buffer allocation là bottleneck thực tế.

**Tại sao hữu ích:**
Các arrays ngắn hạn tạo liên tục làm tăng allocation rate và GC frequency; buffer lớn còn có thể đi vào Large Object Heap. Pooling giảm số object mới, nhưng đổi lại application phải quản lý lifecycle chặt hơn.

**Ví dụ:**
Một endpoint xử lý binary payload hàng nghìn lần mỗi giây cho thấy profiler ghi nhận phần lớn allocations từ temporary byte arrays. Rent buffer từ pool, dùng trong `try/finally`, rồi `Return` có thể giảm allocation rate; sau đó đo lại throughput và GC pause.

**Lưu ý:**
Buffer được rent có thể lớn hơn requested size và chứa dữ liệu cũ. Không đọc vùng chưa ghi; cân nhắc clear khi dữ liệu nhạy cảm. Không return buffer khi code khác vẫn giữ reference.

### Tip 2 — EF Core migration production cần tách khỏi application startup khi blast radius lớn

**Mẹo:**
Với production database quan trọng, đừng mặc định chạy `Database.Migrate()` từ mọi application instance lúc startup. Cân nhắc migration step riêng trong deployment pipeline với quyền, timeout và rollback/recovery plan rõ ràng.

**Tại sao hữu ích:**
Schema migration có thể lock table, chạy lâu hoặc thất bại giữa deployment. Nếu nhiều replicas đồng thời cố migrate, startup behavior và incident diagnosis trở nên khó kiểm soát; application runtime cũng thường không cần DDL privileges.

**Ví dụ:**
Pipeline tạo migration artifact/script đã review, chạy một lần trước rollout, kiểm tra schema version rồi mới deploy application compatible với cả trạng thái cũ/mới khi cần zero-downtime migration.

**Lưu ý:**
Tách migration không tự tạo zero downtime. Breaking schema changes vẫn cần Expand-and-Contract hoặc compatibility window giữa các application versions.

### Tip 3 — Application Insights sampling phải bảo vệ signal hiếm nhưng quan trọng

**Mẹo:**
Khi telemetry volume lớn, dùng sampling có chủ đích thay vì giảm log ngẫu nhiên. Giữ error/critical traces và các dimensions cần cho incident investigation, đồng thời sampling mạnh hơn cho high-volume successful requests nếu phù hợp.

**Tại sao hữu ích:**
Telemetry không giới hạn làm tăng cost và query noise, nhưng sampling sai có thể làm biến mất failure hiếm hoặc khiến latency/error statistics bị hiểu sai. Observability phải tối ưu signal-to-cost, không chỉ giảm ingestion.

**Ví dụ:**
Một API có hàng triệu successful health/read requests nhưng rất ít payment failures. Policy giảm sample rate của traffic thành công phổ biến trong khi giữ exception/dependency failure và correlation cần thiết để reconstruct failed transaction.

**Lưu ý:**
Hiểu sampling xảy ra ở đâu và metric nào được hiệu chỉnh theo sampling. Tránh high-cardinality dimensions như raw user ID/order ID trong metrics chỉ để bù cho thiếu trace detail.

### Tip 4 — Vue `watch` cần cleanup khi tạo async side effect

**Mẹo:**
Khi `watch`/`watchEffect` khởi tạo fetch, timer hoặc subscription theo reactive state, cleanup effect cũ trước khi effect mới chạy để tránh stale result và resource leak.

**Tại sao hữu ích:**
User thay đổi search/filter nhanh có thể tạo nhiều requests đồng thời. Response cũ về sau response mới có thể ghi đè UI bằng state lỗi thời dù backend hoàn toàn đúng.

**Ví dụ:**
Watcher theo search term tạo `AbortController`; callback cleanup abort request trước khi phát request kế tiếp. UI chỉ nhận result thuộc lifecycle hiện tại thay vì dựa vào timing network.

**Lưu ý:**
Đừng dùng `watch` cho giá trị thuần có thể biểu diễn bằng `computed`. `watch` phù hợp hơn cho side effects; dependency và cleanup phải explicit.

### Tip 5 — IIS 502/503 cần tách reverse-proxy failure khỏi application failure

**Mẹo:**
Khi ASP.NET Core sau IIS trả 502/503, bắt đầu bằng evidence ở từng boundary: IIS logs, ASP.NET Core Module/stdout khi phù hợp, process state, Event Viewer và application telemetry thay vì sửa controller code ngay.

**Tại sao hữu ích:**
502/503 có thể xuất hiện trước khi request tới middleware: process không start, crash loop, port/process forwarding lỗi, app pool recycle hoặc startup configuration fail. Chỉ nhìn application logs có thể không thấy request nào.

**Ví dụ:**
Sau deployment, 503 tăng nhưng Application Insights không có request tương ứng. IIS/process evidence cho thấy worker process không khởi động vì missing runtime/configuration; root cause nằm ở hosting/deployment boundary, không phải endpoint logic.

**Lưu ý:**
Không bật verbose stdout logging lâu dài trên production nếu không cần; log volume và sensitive data phải được kiểm soát. Sau incident, bổ sung startup/health telemetry để lần sau phân loại nhanh hơn.

## 🧠 Software Design

### Design 1 — Bulkhead cô lập capacity để một dependency không kéo sập toàn service

**Khái niệm:**
Bulkhead Pattern chia tài nguyên hoặc concurrency budget theo workload/dependency để saturation ở một vùng không tiêu thụ toàn bộ threads, connections hoặc request slots của hệ thống.

**Vấn đề nó giải quyết:**
Nếu một third-party API chậm và mọi requests đều được phép chờ nó không giới hạn, các operations không liên quan cũng có thể mất capacity, dẫn tới cascading failure dù chúng không cần dependency đó.

**Ví dụ thực tế:**
Product service giới hạn riêng số concurrent calls tới recommendation provider. Khi provider chậm, recommendation bị degrade/skip sau budget nhưng checkout/catalog core path vẫn còn capacity phục vụ.

**Trade-off:**
Isolation cải thiện resilience nhưng reserved capacity có thể làm utilization kém hơn và cần tuning theo workload. Bulkhead cũng không thay timeout/circuit breaker; chúng giải quyết các failure dimension khác nhau.

**Middle → Senior insight:**
Middle developer cần nhận ra shared pool tạo failure coupling. Senior / Technical developer phải phân bổ capacity theo criticality/SLO, chọn degradation behavior và theo dõi queueing/rejection để tránh biến bulkhead thành bottleneck vô hình.

### Design 2 — Repository abstraction chỉ nên tồn tại khi nó tạo boundary có giá trị

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work/change tracking/query abstractions. Một custom Repository nên encapsulate domain-specific persistence semantics hoặc boundary có lý do rõ, không chỉ mirror `Add`, `Update`, `GetAll` cho mọi entity.

**Vấn đề nó giải quyết:**
Generic repository quá mỏng thường che mất `IQueryable`, transaction/query capabilities và sinh thêm abstraction mà không giảm coupling thực tế. Ngược lại, persistence query phức tạp rải khắp application cũng làm ownership khó kiểm soát.

**Ví dụ thực tế:**
`IOrderRepository` có thể cung cấp operation mang semantics như load aggregate cần cho fulfillment với concurrency state đúng. CRUD screen đơn giản có thể dùng `DbContext` trực tiếp trong application handler thay vì ép qua generic repository.

**Trade-off:**
Repository tốt tạo seam và tập trung persistence knowledge; repository hình thức tạo boilerplate và hạn chế EF Core. Direct `DbContext` đơn giản hơn nhưng cần discipline để query/data concerns không rò vào mọi layer.

**Middle → Senior insight:**
Middle developer cần tránh coi pattern là rule. Senior / Technical developer phải đánh giá volatility, test boundary, domain semantics và query complexity để quyết định abstraction nào thực sự trả lại giá trị lớn hơn chi phí.

### Design 3 — Graceful degradation cần được thiết kế theo business criticality

**Khái niệm:**
Graceful degradation giữ core capability hoạt động khi optional dependency hoặc secondary feature lỗi bằng fallback, omission hoặc reduced functionality đã định nghĩa trước.

**Vấn đề nó giải quyết:**
Nếu mọi dependency đều được coi là bắt buộc, lỗi của recommendations, reviews hoặc personalization có thể làm toàn product page thất bại dù dữ liệu catalog và checkout vẫn khỏe.

**Ví dụ thực tế:**
Product page đặt catalog/price là critical nhưng reviews là optional. Reviews service timeout thì UI trả page không có reviews và telemetry ghi degraded state; price service lỗi thì request fail theo policy vì không thể bán với giá không xác định.

**Trade-off:**
Degradation tăng availability nhưng có thể che lỗi kéo dài hoặc tạo trải nghiệm không nhất quán. Fallback data cũ cũng có correctness risk; mỗi capability cần freshness và failure semantics riêng.

**Middle → Senior insight:**
Middle developer cần phân biệt required và optional dependency trong code path. Senior / Solution-oriented engineer phải map business criticality sang SLO, timeout budget, fallback policy và alerting để degradation có kiểm soát thay vì silent failure.
