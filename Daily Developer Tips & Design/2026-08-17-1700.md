# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Chỉ dùng `ValueTask` khi hot path thực sự có lợi

**Mẹo:**
`ValueTask<T>` có thể tránh allocation của `Task<T>` khi operation thường hoàn thành đồng bộ, nhưng chỉ nên dùng khi profiling cho thấy đây là hot path đáng tối ưu.

**Tại sao hữu ích:**
Trong API hoặc library có throughput rất cao, việc tránh tạo hàng triệu `Task` ngắn hạn có thể giảm allocation và GC pressure.

**Ví dụ:**
```csharp
public ValueTask<User?> GetCachedUserAsync(Guid id)
{
    if (_cache.TryGetValue(id, out User? user))
    {
        return ValueTask.FromResult(user);
    }

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

**Lưu ý:**
`ValueTask` phức tạp hơn `Task`: không nên await nhiều lần, cache tùy tiện hoặc expose rộng nếu không cần. Mặc định vẫn nên dùng `Task` cho code dễ hiểu và an toàn hơn.

### Tip 2 — Dùng keyset pagination cho deep paging thay vì `OFFSET`

**Mẹo:**
Khi bảng lớn và user thường đi sâu nhiều trang, dùng keyset/cursor pagination dựa trên cột sort ổn định thay vì `OFFSET ... FETCH` hoặc `Skip()` lớn.

**Tại sao hữu ích:**
`OFFSET 100000` vẫn buộc database bỏ qua rất nhiều rows trước khi trả trang kế tiếp. Keyset pagination cho database seek tiếp từ record cuối cùng đã thấy.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @LastCreatedAt)
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC
LIMIT 50;
```

**Lưu ý:**
Phải có sort order deterministic và index phù hợp với cursor columns. Keyset pagination không tiện nếu UI cần nhảy trực tiếp tới “trang 437”.

### Tip 3 — Dùng `git rerere` để Git nhớ cách bạn từng resolve conflict

**Mẹo:**
Nếu thường xuyên rebase hoặc merge các branch dài ngày và gặp lại cùng loại conflict, bật `git rerere` để Git ghi nhớ conflict resolution trước đó.

**Tại sao hữu ích:**
Giảm việc lặp lại cùng một thao tác resolve conflict khi rebase nhiều commit hoặc duy trì release branch song song.

**Ví dụ:**
```bash
git config --global rerere.enabled true
```

Sau khi bạn resolve conflict một lần và commit/rebase tiếp, Git có thể tự áp dụng lại resolution khi cùng conflict xuất hiện.

**Lưu ý:**
Vẫn phải review phần Git tự resolve. Context code có thể đã thay đổi dù conflict text trông giống nhau.

### Tip 4 — Dùng `dotnet-trace` khi cần profile CPU mà không attach debugger

**Mẹo:**
Khi production hoặc staging có CPU cao, dùng `dotnet-trace` để thu EventPipe trace trong khoảng ngắn rồi phân tích call stack thay vì bật verbose logging hàng loạt.

**Tại sao hữu ích:**
Cho biết method nào đang tiêu CPU, thread nào chạy nhiều và execution path thực tế mà không cần sửa code hoặc attach full debugger.

**Ví dụ:**
```bash
dotnet-trace collect -p <PID> --duration 00:00:30
```

Sau đó mở file trace bằng PerfView, Visual Studio hoặc công cụ hỗ trợ EventPipe.

**Lưu ý:**
Tracing vẫn có overhead. Thu trong khoảng thời gian ngắn, đúng lúc issue xảy ra và bảo vệ trace file vì có thể chứa tên method hoặc metadata nhạy cảm.

### Tip 5 — Đừng để JSON serialization âm thầm kéo cả object graph

**Mẹo:**
Với API response, projection DTO rõ ràng tốt hơn serialize trực tiếp EF entity hoặc domain object có navigation properties phức tạp.

**Tại sao hữu ích:**
Giảm payload ngoài ý muốn, tránh circular reference, lazy-loading surprise và giúp API contract ổn định hơn khi internal model thay đổi.

**Ví dụ:**
```csharp
var result = await dbContext.Orders
    .Where(x => x.Id == id)
    .Select(x => new OrderDto(
        x.Id,
        x.Status,
        x.Total,
        x.Customer.Name))
    .SingleOrDefaultAsync(cancellationToken);
```

**Lưu ý:**
Không phải DTO nào cũng cần class riêng nếu projection rất nhỏ. Điều quan trọng là API contract không phụ thuộc trực tiếp vào toàn bộ persistence model.

## 🧠 Software Design

### Design 1 — Consumer-Driven Contract Testing cho integration giữa services

**Khái niệm:**
Consumer-Driven Contract Testing để consumer mô tả contract mà nó thực sự phụ thuộc, còn provider xác minh rằng implementation hiện tại vẫn đáp ứng các contract đó.

**Vấn đề nó giải quyết:**
Integration test end-to-end toàn hệ thống thường chậm và khó chạy thường xuyên, trong khi unit test riêng từng service lại không phát hiện breaking change ở JSON field, status code hoặc event schema.

**Ví dụ thực tế:**
`OrderService` phụ thuộc `CustomerService` trả `customerId`, `name`, `status`. Contract test xác nhận provider vẫn trả đúng shape và semantics cần thiết mà không cần dựng toàn bộ production topology.

**Trade-off:**
Lợi ích là feedback nhanh hơn và phát hiện breaking contract sớm. Chi phí là phải quản lý contract version, provider verification pipeline và tránh biến contract test thành bản sao cứng nhắc của implementation.

**Middle → Senior insight:**
Middle developer nên hiểu integration boundary cần được test ở contract level, không chỉ mock. Senior developer phải quyết định contract nào đáng formalize, ownership của compatibility, cách versioning và khi nào full end-to-end test vẫn cần thiết.

### Design 2 — Strangler Fig Pattern để thay legacy system theo từng lát cắt

**Khái niệm:**
Strangler Fig Pattern thay thế hệ thống cũ dần dần bằng cách chuyển từng capability hoặc traffic slice sang implementation mới, thay vì rewrite toàn bộ rồi cutover một lần.

**Vấn đề nó giải quyết:**
Big-bang rewrite kéo dài nhiều tháng hoặc nhiều năm, trong thời gian đó business vẫn thay đổi và cả hệ thống cũ lẫn mới đều phải tiến hóa song song.

**Ví dụ thực tế:**
Một legacy monolith xử lý employee, timesheet và reporting. Team có thể giữ monolith chạy, nhưng route riêng `Reporting` sang module/service mới trước, sau đó tiếp tục migrate capability khác khi boundary đã rõ.

**Trade-off:**
Giảm risk và cho phép deliver giá trị sớm hơn, nhưng giai đoạn chuyển tiếp có routing, data sync, duplicated logic và operational complexity giữa cũ và mới.

**Middle → Senior insight:**
Middle developer nên hiểu migration có thể incremental thay vì rewrite. Senior developer cần chọn seam phù hợp, xác định source of truth, chiến lược dữ liệu, rollback path và tiêu chí xóa bỏ phần legacy cũ.

### Design 3 — Distributed Lock cần fencing token nếu resource có thể bị stale owner ghi tiếp

**Khái niệm:**
Một distributed lock có lease có thể hết hạn trong khi process cũ vẫn tiếp tục chạy. Fencing token là sequence tăng dần được cấp mỗi lần lock ownership thay đổi để downstream resource từ chối writer cũ.

**Vấn đề nó giải quyết:**
Nếu worker A giữ lock rồi bị pause do GC/network, lease hết hạn và worker B lấy lock mới. Khi A chạy lại, cả A và B có thể cùng ghi dù mỗi bên tưởng mình từng sở hữu lock hợp lệ.

**Ví dụ thực tế:**
Mỗi lần acquire lock, hệ thống cấp token `101`, rồi `102`. Storage layer chỉ chấp nhận write có token lớn hơn token cuối cùng đã thấy. Worker A với token `101` sẽ bị reject sau khi worker B đã ghi bằng `102`.

**Trade-off:**
Fencing tăng an toàn cho critical resource nhưng cần downstream storage hiểu token/order và làm design phức tạp hơn. Với workload chỉ cần best-effort deduplication, cơ chế này có thể quá nặng.

**Middle → Senior insight:**
Middle developer nên hiểu “đã acquire lock” không đồng nghĩa ownership còn hợp lệ mãi. Senior developer cần đánh giá lease expiry, clock assumptions, pause/failure mode và dùng fencing hoặc atomic storage primitive khi invariant không được phép vi phạm.
