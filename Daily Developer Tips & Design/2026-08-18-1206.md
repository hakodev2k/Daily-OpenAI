# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` cho dữ liệu streaming

**Mẹo:**
Sử dụng `IAsyncEnumerable<T>` khi cần xử lý dữ liệu theo từng phần thay vì load toàn bộ collection vào memory.

**Tại sao hữu ích:**
Giảm memory usage và cải thiện khả năng xử lý dữ liệu lớn.

**Ví dụ:**
```csharp
await foreach (var item in service.GetItemsAsync())
{
    Process(item);
}
```

**Lưu ý:**
Không phù hợp nếu business logic cần toàn bộ dữ liệu trước khi xử lý.

### Tip 2 — Sử dụng `AsNoTracking()` cho EF Core read-only query

**Mẹo:**
Dùng `AsNoTracking()` với các query chỉ đọc dữ liệu.

**Tại sao hữu ích:**
EF Core không cần tạo change tracker, giúp giảm memory và tăng performance.

**Ví dụ:**
```csharp
var users = await db.Users
    .AsNoTracking()
    .ToListAsync();
```

**Lưu ý:**
Không dùng khi cần update entity sau khi query.

### Tip 3 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Dùng binary search trong Git history thay vì kiểm tra từng commit thủ công.

**Tại sao hữu ích:**
Giảm thời gian tìm regression bug trong project lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.0.0
```

**Lưu ý:**
Cần có test hoặc cách xác định rõ commit nào tốt/xấu.

### Tip 4 — Dùng health checks để phát hiện dependency failure

**Mẹo:**
Expose health endpoint kiểm tra database, Redis, external API hoặc message broker.

**Tại sao hữu ích:**
Giúp monitoring system phát hiện vấn đề trước khi người dùng báo lỗi.

**Ví dụ:**
```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString);
```

**Lưu ý:**
Không đưa quá nhiều dependency chậm vào liveness check.

### Tip 5 — Tách configuration khỏi code bằng Options Pattern

**Mẹo:**
Dùng `IOptions<T>` để quản lý application settings thay vì đọc trực tiếp từ configuration.

**Tại sao hữu ích:**
Code dễ test hơn và giảm coupling với environment configuration.

**Ví dụ:**
```csharp
services.Configure<JwtOptions>(configuration.GetSection("Jwt"));
```

**Lưu ý:**
Không lưu secret nhạy cảm trực tiếp trong source code.

## 🧠 Software Design

### Design 1 — Transaction Boundary Design

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu nào phải thành công hoặc rollback cùng nhau.

**Vấn đề nó giải quyết:**
Tránh trạng thái dữ liệu không nhất quán trong business workflow.

**Ví dụ thực tế:**
Tạo order cần lưu Order và OrderItem trong cùng transaction database.

**Trade-off:**
Transaction lớn tăng consistency nhưng có thể giảm performance và gây lock lâu.

**Middle → Senior insight:**
Middle cần biết cách dùng transaction. Senior cần quyết định boundary dựa trên business invariant thay vì chỉ dựa trên technical flow.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia hệ thống thành các module độc lập trong cùng deployment unit.

**Vấn đề nó giải quyết:**
Giữ được boundary rõ ràng mà không phải chịu toàn bộ complexity của distributed system.

**Ví dụ thực tế:**
Hệ thống ERP có module Sales, Inventory, Accounting với domain riêng nhưng dùng chung application.

**Trade-off:**
Đơn giản vận hành hơn nhưng cần discipline để tránh module phụ thuộc chéo.

**Middle → Senior insight:**
Senior cần đánh giá communication pattern, team structure và operational cost trước khi chọn Microservices.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo cùng một request được gửi nhiều lần vẫn tạo ra cùng một kết quả.

**Vấn đề nó giải quyết:**
Xử lý retry trong network failure mà không tạo duplicate data.

**Ví dụ thực tế:**
Payment API sử dụng `Idempotency-Key` để tránh charge khách hàng hai lần.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và xử lý lifecycle của key.

**Middle → Senior insight:**
Senior cần xem retry, timeout và failure scenario như một phần của API contract.
