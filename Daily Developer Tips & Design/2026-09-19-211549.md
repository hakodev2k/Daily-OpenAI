# Daily Developer Tips & Design — 2026-09-19

## 🛠 Developer Tips & Tricks

### Tip 1 — Scoped dependency trong BackgroundService

**Mẹo:**
BackgroundService là singleton. Nếu worker cần DbContext hoặc service scoped, tạo scope cho từng unit of work bằng IServiceScopeFactory thay vì giữ scoped service suốt lifetime process.

**Tại sao hữu ích:**
DbContext không thread-safe và lifetime dài làm change tracker tích lũy state. Scope theo message/job giúp lifetime dependency trùng transaction boundary thực tế.

**Ví dụ:**
Worker tạo CreateAsyncScope(), resolve JobProcessor, xử lý một message với stoppingToken rồi dispose scope trước message kế tiếp.

**Lưu ý:**
Đừng tạo scope cho từng row nếu một batch mới là unit of work hợp lý. Luôn propagate stoppingToken để shutdown không bị treo vì I/O còn chạy.

### Tip 2 — ExecuteDeleteAsync cho set-based delete

**Mẹo:**
Khi cần xóa nhiều rows theo predicate mà không cần domain logic trên từng entity, cân nhắc EF Core ExecuteDeleteAsync thay vì load entities rồi RemoveRange.

**Tại sao hữu ích:**
Set-based delete gửi lệnh trực tiếp xuống database, tránh materialization, tracking và allocation; rất hữu ích cho cleanup jobs hoặc retention policy.

**Ví dụ:**
Một scheduled job xóa AuditEvents cũ hơn retention cutoff bằng một predicate trực tiếp trên IQueryable rồi gọi ExecuteDeleteAsync(cancellationToken).

**Lưu ý:**
Operation không đi qua change tracker như entity-by-entity deletion. Nếu application dựa vào domain events hoặc lifecycle logic khi xóa, phải xử lý rõ ràng.

### Tip 3 — Connection-pool exhaustion thường là triệu chứng

**Mẹo:**
Khi API timeout chờ database connection, đừng chỉ tăng pool size. Correlate active connections, query duration, transaction duration và request concurrency.

**Tại sao hữu ích:**
Slow query, transaction chứa network call hoặc traffic spike giữ connection lâu hơn. Tăng pool chỉ cho phép nhiều work cùng dồn vào database và có thể làm incident nặng hơn.

**Ví dụ:**
Sau deployment, p99 SQL duration tăng từ 80 ms lên 2 s và pool wait xuất hiện. Evidence chỉ ra query regression; sửa query/transaction boundary có giá trị hơn tăng Max Pool Size ngay lập tức.

**Lưu ý:**
Pool size vẫn là capacity parameter hợp lệ, nhưng phải dựa trên database capacity và workload; pool lớn hơn không phải scalability miễn phí.

### Tip 4 — Stable key cho React/Vue list có reorder

**Mẹo:**
Dùng business-stable key như product.id cho list component khi items có thể insert, delete hoặc reorder; tránh array index làm key cho danh sách có state con.

**Tại sao hữu ích:**
Virtual DOM dùng key để xác định identity giữa các render. Index thay đổi khi reorder có thể khiến component/input state bị gắn nhầm item.

**Ví dụ:**
Render ProductRow với key bằng product.id thay vì vị trí của product trong array.

**Lưu ý:**
Không tạo random key mỗi render vì sẽ remount component. Index chỉ hợp lý khi list thực sự tĩnh và không reorder/insert/delete.

### Tip 5 — Secret rotation phải tính behavior của application

**Mẹo:**
Khi dùng Azure Key Vault, xác định application đọc secret lúc startup, cache trong configuration hay refresh runtime; thiết kế rotation theo behavior thực tế đó.

**Tại sao hữu ích:**
Secret đã rotate ở vault không có nghĩa process đang chạy tự dùng value mới. Client giữ credential cũ có thể bắt đầu authentication failure khi credential đó bị revoke.

**Ví dụ:**
Với external API key, dùng khoảng overlap: publish key mới, cập nhật/reload consumers, xác nhận telemetry rồi mới revoke key cũ.

**Lưu ý:**
Managed Identity thường tốt hơn secret cho Azure-to-Azure authentication khi được hỗ trợ. Không log secret để debug rotation.

## 🧠 Software Design

### Design 1 — Load shedding trước saturation

**Khái niệm:**
Load shedding chủ động từ chối hoặc giảm một phần workload khi capacity gần bão hòa, thay vì nhận mọi request rồi để queue, connection pool và latency tăng vô hạn.

**Vấn đề nó giải quyết:**
Nếu database xử lý ổn 500 operations/s nhưng application nhận 1.500 operations/s, nhận toàn bộ có thể tạo timeout và retry storm khiến cả critical request thất bại.

**Ví dụ thực tế:**
Reporting endpoint có thể trả 429/503 sớm khi concurrency budget đầy, trong khi checkout giữ capacity riêng. Background work không quan trọng có thể giảm tốc.

**Trade-off:**
Load shedding bảo vệ latency và recovery nhưng chấp nhận một phần request fail/degrade. Threshold sai có thể từ chối traffic khi hệ thống còn capacity.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency limit, status semantics và client backoff. Senior / Technical developer phải xác định workload priority, capacity budget và degradation contract để giảm blast radius.

### Design 2 — Event schema cần evolution strategy

**Khái niệm:**
Event đã publish là contract giữa producer và consumer. Schema evolution phải cho phép deploy lệch nhịp, đặc biệt vì message cũ có thể còn trong queue hoặc được replay.

**Vấn đề nó giải quyết:**
Producer đổi field hoặc semantics có thể làm consumer cũ lỗi. Payload tạo từ tuần trước vẫn có thể được xử lý bởi code hôm nay qua retry, DLQ hoặc replay.

**Ví dụ thực tế:**
Thêm optional Currency vào OrderCompleted an toàn hơn đổi kiểu Total ngay lập tức. Breaking semantic change có thể cần event type/version mới và migration period.

**Trade-off:**
Backward-compatible events giảm coordinated deployment nhưng giữ legacy fields lâu. Version mới rõ semantics hơn nhưng tăng routing, mapping, test và operational burden.

**Middle → Senior insight:**
Middle developer cần tolerant deserialization và test payload cũ. Senior / Technical developer phải thiết kế ownership, compatibility window, replay semantics và deprecation dựa trên consumer inventory.

### Design 3 — Architecture Fitness Functions bảo vệ boundary

**Khái niệm:**
Architecture Fitness Function là automated check bảo vệ architectural property quan trọng như dependency direction, module isolation hoặc forbidden reference thay vì chỉ ghi nguyên tắc trong tài liệu.

**Vấn đề nó giải quyết:**
Boundary thường bị phá dần vì shortcut: module A reference trực tiếp internal/infrastructure type của module B. Code vẫn compile nhưng coupling tăng qua mỗi PR.

**Ví dụ thực tế:**
Architecture test assert Ordering.Domain không reference Infrastructure, hoặc Catalog chỉ được truy cập qua public contracts; CI fail khi dependency rule bị vi phạm.

**Trade-off:**
Fitness functions biến architectural intent thành feedback tự động, nhưng chỉ kiểm tra rule formalize được. Test quá cứng có thể khóa evolution hợp lệ.

**Middle → Senior insight:**
Middle developer cần hiểu và tuân thủ boundary. Senior / Technical developer phải chọn vài fitness functions bảo vệ risk thật, review chúng khi architecture tiến hóa và không dùng tool thay thế design judgment.
