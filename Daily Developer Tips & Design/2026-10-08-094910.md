# Daily Developer Tips & Design — 2026-10-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Rate limiting theo identity, không gom mọi request vào một bucket

**Mẹo:**
Trong ASP.NET Core, dùng partitioned rate limiting theo user ID đã xác thực; với request anonymous, cân nhắc IP hoặc khóa phù hợp với threat model. Áp dụng policy ở endpoint tốn tài nguyên thay vì đặt cùng một hạn mức cho mọi API.

**Tại sao hữu ích:**
Một global limit có thể khiến một client ồn ào làm người dùng khác nhận HTTP 429. Partition theo identity tạo giới hạn độc lập, giúp bảo vệ endpoint đặt hàng hoặc tìm kiếm mà vẫn giữ fairness. Rate limiter chỉ giới hạn lưu lượng; nó không thay thế authorization hay chống gian lận.

**Ví dụ:**
```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("orders", context =>
        RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: context.User.FindFirst("sub")?.Value
                ?? context.Connection.RemoteIpAddress?.ToString()
                ?? "unknown",
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 20,
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0
            }));
});

app.UseAuthentication();
app.UseRateLimiter();
app.UseAuthorization();

app.MapPost("/orders", HandleOrder)
   .RequireAuthorization()
   .RequireRateLimiting("orders");
```

**Lưu ý:**
Đừng tin `X-Forwarded-For` do client tự gửi; chỉ cấu hình Forwarded Headers cho reverse proxy đáng tin cậy. Khi chạy nhiều instance, limiter trong memory không tạo hạn mức toàn cụm. Endpoint yêu cầu login nên dùng claim ổn định và tránh khóa fallback dùng chung cho mọi user.

### Tip 2 — SQL Server: chẩn đoán parameter-sensitive plan trước khi thêm index

**Mẹo:**
Khi cùng một stored procedure có lúc chạy 30 ms, có lúc 8 giây, so sánh execution plan, logical reads và phân bố giá trị parameter bằng Query Store và actual execution plan.

**Tại sao hữu ích:**
SQL Server có thể cache plan tối ưu cho giá trị parameter đầu tiên nhưng kém với giá trị có độ chọn lọc rất khác. Thêm index không giải quyết triệt để nếu vấn đề là lựa chọn plan theo phân bố dữ liệu; trên các phiên bản phù hợp, Parameter Sensitive Plan optimization cũng có thể hỗ trợ.

**Ví dụ:**
```sql
SELECT OrderId, CreatedAt
FROM dbo.Orders
WHERE TenantId = @TenantId AND Status = @Status;
```
Tenant nhỏ có vài chục đơn, tenant lớn có hàng triệu đơn. Đối chiếu Query Store theo `query_id`/`plan_id`, thời gian, số lần thực thi và logical reads; kiểm tra statistics, cardinality estimate, index và plan regression trước khi chọn giải pháp.

**Lưu ý:**
`OPTION (RECOMPILE)` có thể cải thiện một truy vấn nhưng tăng CPU compile khi tần suất gọi cao. Không force plan chỉ vì một lần benchmark nhanh; phải kiểm chứng trên các nhóm parameter và workload thực tế.

### Tip 3 — Azure Blob Storage: cấp quyền upload ngắn hạn thay vì lộ account key

**Mẹo:**
Với frontend upload file lớn, backend xác thực user rồi cấp user delegation SAS giới hạn đúng blob, permission và thời gian; client upload trực tiếp lên Azure Blob Storage.

**Tại sao hữu ích:**
Dữ liệu không phải đi qua bộ nhớ và băng thông của ASP.NET Core API. User delegation SAS được ký bằng delegation key lấy qua Microsoft Entra credentials, giảm nhu cầu phát tán storage account key. Backend vẫn quản lý quyền truy cập ở mức nghiệp vụ.

**Ví dụ:**
Luồng upload ảnh sản phẩm: `POST /uploads/authorize` → backend kiểm tra quyền sửa sản phẩm, tạo tên blob không đoán được, cấp SAS chỉ có quyền `Create/Write` hết hạn sau vài phút → browser upload → backend xác minh blob, kích thước, loại file thực tế rồi mới đánh dấu attachment hợp lệ.

**Lưu ý:**
SAS là bearer credential: ai có URL còn hiệu lực có thể sử dụng quyền được cấp. Cấu hình CORS, giới hạn kích thước, kiểm tra nội dung và quy trình dọn orphan blobs. Đừng coi upload thành công là file đã an toàn hoặc đã thuộc đúng product.

### Tip 4 — Vue.js: hủy request cũ để tránh kết quả tìm kiếm bị đảo thứ tự

**Mẹo:**
Trong `watch` của Vue 3, gắn `AbortController` với từng request và đăng ký cleanup trước điểm `await`.

**Tại sao hữu ích:**
Người dùng gõ “lap” rồi “laptop”; response cho “lap” có thể về sau response “laptop” và ghi đè state bằng dữ liệu cũ. Đây là race condition theo thứ tự hoàn tất, không phải lỗi API.

**Ví dụ:**
```ts
watch(searchTerm, async (term, _, onCleanup) => {
  const controller = new AbortController();
  onCleanup(() => controller.abort());

  try {
    const response = await fetch(
      `/api/products?q=${encodeURIComponent(term)}`,
      { signal: controller.signal }
    );
    if (!response.ok) throw new Error("Search failed");
    results.value = await response.json();
  } catch (error) {
    if ((error as Error).name !== "AbortError") {
      searchError.value = "Không tải được kết quả";
    }
  }
});
```

**Lưu ý:**
Abort phía browser không bảo đảm server ngừng xử lý. Có thể kết hợp debounce để giảm request; khi dùng thư viện không hỗ trợ cancellation, dùng request sequence ID để bỏ qua response cũ.

### Tip 5 — Playwright: giữ trace của lần retry để điều tra flaky test

**Mẹo:**
Trong CI, bật `trace: 'on-first-retry'` để thu timeline, DOM snapshot và network activity của lần chạy lại khi test thất bại.

**Tại sao hữu ích:**
Flaky test thường do race giữa rendering, API response và thao tác UI. Trace giúp phân biệt locator không ổn định, dữ liệu test dùng chung và request thất bại thay vì tăng `waitForTimeout` theo cảm tính.

**Ví dụ:**
```ts
export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  use: { trace: "on-first-retry" }
});
```
Khi test checkout thất bại, mở trace và kiểm tra thời điểm click “Pay”, trạng thái nút, response của `POST /checkout` và navigation.

**Lưu ý:**
Retry không sửa được flaky test, chỉ hỗ trợ thu bằng chứng. Ưu tiên locator theo role, assertion tự chờ, dữ liệu độc lập và mock có kiểm soát. Trace có thể chứa dữ liệu nhạy cảm; kiểm soát artifact retention và quyền truy cập.

## 🧠 Software Design

### Design 1 — Backend for Frontend (BFF) cho ứng dụng web cần session an toàn

**Khái niệm:**
BFF là backend phục vụ riêng một frontend, xử lý OAuth/OIDC và giữ access token phía server; browser sử dụng session cookie thay vì tự quản lý token dài hạn.

**Vấn đề nó giải quyết:**
SPA tích hợp nhiều API thường phải xử lý token lifecycle, CORS và nguy cơ token bị đánh cắp qua XSS. BFF tập trung quản lý token và có thể tổng hợp response phù hợp từng giao diện.

**Ví dụ thực tế:**
Portal quản trị CMS đăng nhập qua Microsoft Entra ID. Browser gọi `/bff/products` bằng cookie `HttpOnly`, còn BFF lấy token phía server để gọi Product API. BFF kiểm tra authorization của request, không chỉ chuyển tiếp token.

**Trade-off:**
Giảm token exposure trong browser và đơn giản hóa frontend, nhưng thêm server state hoặc session infrastructure, network hop và chi phí vận hành. Cookie-based authentication phải thiết kế `SameSite`, CSRF protection, session expiry và logout; BFF không loại bỏ XSS.

**Middle → Senior insight:**
- **Middle:** Hiểu cookie/session, CSRF, OIDC callback và vì sao `HttpOnly` không đủ để bảo vệ mọi request.
- **Senior / Technical:** Chọn BFF hay SPA dùng Authorization Code + PKCE theo threat model, số frontend, hạ tầng, scale và ownership; không thêm BFF chỉ vì đó là pattern mới.

### Design 2 — Elasticsearch là read model có thể rebuild, không phải nguồn sự thật

**Khái niệm:**
Giữ SQL Server hoặc PostgreSQL làm authoritative transactional store; Elasticsearch là projection tối ưu cho full-text search, filtering và relevance. Xem index như dữ liệu có thể tái tạo.

**Vấn đề nó giải quyết:**
Nếu ghi trực tiếp cả database lẫn search index trong cùng request, partial failure dễ tạo dữ liệu lệch. Nếu coi index là nguồn duy nhất, reindex hoặc mapping migration có thể gây mất tính nhất quán nghiệp vụ.

**Ví dụ thực tế:**
Hệ thống e-commerce lưu giá và tồn kho trong SQL. Pipeline đồng bộ product documents sang Elasticsearch; search trả danh sách ứng viên, còn checkout kiểm tra lại giá và inventory từ nguồn chính. Khi đổi analyzer, xây index phiên bản mới, backfill, kiểm chứng count/sample và chuyển alias.

**Trade-off:**
Search nhanh và linh hoạt, nhưng chấp nhận eventual consistency, độ trễ indexing, chi phí hạ tầng và quy trình reconciliation. Không nên đưa dữ liệu cần consistency tức thì vào search response mà không có bước xác thực.

**Middle → Senior insight:**
- **Middle:** Hiểu mapping, index lag, retry, idempotent update và cách kiểm tra lệch dữ liệu.
- **Senior / Technical:** Định nghĩa freshness SLO, cơ chế rebuild, versioning, reconciliation và hành vi khi Elasticsearch unavailable; quyết định lúc nào SQL full-text search đã đủ để tránh thêm một distributed component.

### Design 3 — Expand–Contract để thay đổi database schema không downtime

**Khái niệm:**
Thay schema qua các phiên bản tương thích ngược: **expand** cấu trúc trước, chuyển application/data dần, rồi mới **contract** bỏ cấu trúc cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment, version cũ và mới cùng truy cập database. Rename hoặc drop column ngay khi deploy có thể làm pod chưa cập nhật lỗi SQL, dù migration thành công.

**Ví dụ thực tế:**
Đổi `Customers.FullName` thành `FirstName` và `LastName`:
1. Thêm hai cột nullable, giữ `FullName`.
2. Deploy code đọc được cả cấu trúc cũ/mới và ghi theo chiến lược chuyển tiếp nhất quán.
3. Backfill theo batch, đo lock và kiểm tra các bản ghi thiếu dữ liệu.
4. Chuyển tất cả readers/writers sang schema mới; xác minh không còn instance cũ.
5. Ở release sau mới drop `FullName` và siết constraint cần thiết.

**Trade-off:**
Giảm rủi ro downtime và rollback ứng dụng, nhưng tăng số release, logic tương thích và công việc data migration. Dual-write kéo dài có thể tạo divergence; cần quy định nguồn dữ liệu ưu tiên và kiểm chứng tính nhất quán.

**Middle → Senior insight:**
- **Middle:** Viết migration tương thích, kiểm tra NULL/default, tránh migration phá vỡ contract đang được sử dụng.
- **Senior / Technical:** Thiết kế rollout/rollback nhiều phiên bản, xác định điểm không thể rollback dữ liệu, lập kế hoạch backfill an toàn với bảng lớn và phối hợp giữa application, database, CI/CD.
