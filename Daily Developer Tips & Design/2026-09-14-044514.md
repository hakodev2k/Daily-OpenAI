# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `await using` khi resource có cleanup bất đồng bộ

**Mẹo:**
Khi một resource implement `IAsyncDisposable`, dùng `await using` để cleanup bằng `DisposeAsync()` thay vì ép resource đi qua cleanup đồng bộ nếu teardown có I/O hoặc flush bất đồng bộ.

**Tại sao hữu ích:**
Một số resource cần hoàn tất work bất đồng bộ trước khi giải phóng hoàn toàn, ví dụ flush buffer, đóng stream hoặc kết thúc operation network. Nếu chỉ dựa vào `IDisposable`, cleanup có thể block thread hoặc bỏ lỡ đường teardown mà library thiết kế cho async flow.

**Ví dụ:**
```csharp
await using var stream = await OpenLargeExportStreamAsync(ct);

await WriteExportAsync(stream, ct);
```

Compiler sẽ gọi `DisposeAsync()` khi rời scope, kể cả khi exception xảy ra trong phần xử lý.

**Lưu ý:**
Không phải mọi object nên implement cả `IDisposable` và `IAsyncDisposable`. Chỉ dùng async disposal khi resource thực sự cần cleanup bất đồng bộ; nếu cleanup thuần memory, `IDisposable` đơn giản hơn. Đồng thời vẫn cần truyền `CancellationToken` cho work chính vì dispose không thay thế cancellation.

### Tip 2 — Dùng `INCLUDE` để tạo covering index mà không làm key index phình không cần thiết

**Mẹo:**
Trong SQL Server, nếu query filter/sort tốt bằng một số column nhưng vẫn phải `Key Lookup` nhiều lần chỉ để lấy thêm column trả về, cân nhắc đưa các column chỉ dùng để đọc vào `INCLUDE` thay vì thêm tất cả chúng vào key của index.

**Tại sao hữu ích:**
Key column quyết định thứ tự và cấu trúc tìm kiếm của index; thêm quá nhiều key làm index lớn, tăng chi phí write và giảm density. Included column có thể giúp query được “cover” mà không thay đổi key order cần cho seek.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Customer_Status
ON dbo.Orders(CustomerId, Status)
INCLUDE (CreatedAt, TotalAmount);
```

Query:
```sql
SELECT CreatedAt, TotalAmount
FROM dbo.Orders
WHERE CustomerId = @customerId
  AND Status = @status;
```

Nếu execution plan trước đó có nhiều `Key Lookup`, index trên có thể giảm random lookup vào clustered index.

**Lưu ý:**
Covering index không phải lúc nào cũng đáng giá. Mỗi included column làm index lớn hơn và tăng write amplification. Luôn kiểm tra execution plan, row count, read/write ratio và usage trước khi thêm index chỉ vì thấy một lookup.

### Tip 3 — Với Azure Service Bus, handler dài phải tính cả message lock chứ không chỉ timeout business logic

**Mẹo:**
Khi consumer xử lý message lâu, kiểm tra `LockDuration`, auto lock renewal và thời gian xử lý thực tế. Nếu lock hết hạn trước khi handler hoàn tất, cùng message có thể được broker giao lại trong khi lần xử lý đầu vẫn đang chạy.

**Tại sao hữu ích:**
Service Bus dùng message lock để đảm bảo một consumer sở hữu message tạm thời trong `PeekLock` mode. Nếu processing vượt lock window và renewal không thành công, `Complete` có thể thất bại và message bị redeliver, dẫn tới duplicate side effect.

**Ví dụ:**
```text
Message lock: 60s
Handler thực tế: 95s

T = 0s   Consumer A nhận message
T = 60s  Lock hết hạn
T = 65s  Consumer B nhận lại message
T = 95s  Consumer A vẫn cố Complete
```

Với work dài, nên chia nhỏ operation, cấu hình lock renewal phù hợp và giữ handler idempotent.

**Lưu ý:**
Tăng lock duration thật lớn chỉ che bottleneck nếu handler vốn không nên chạy lâu. Auto-renew cũng không bảo vệ mọi failure như process crash hoặc network partition. Thiết kế consumer vẫn phải chấp nhận duplicate delivery.

### Tip 4 — Mock ít hơn khi test orchestration; kiểm tra behavior observable nhiều hơn interaction nội bộ

**Mẹo:**
Khi unit test application service, đừng mặc định mock mọi dependency rồi verify từng method call. Với logic orchestration quan trọng, ưu tiên assert kết quả hoặc side effect có ý nghĩa business; chỉ verify interaction khi interaction đó chính là contract cần bảo vệ.

**Tại sao hữu ích:**
Test phụ thuộc quá chặt vào implementation dễ vỡ khi refactor dù behavior không đổi. Ví dụ đổi hai helper thành một service mới có thể làm hàng chục test fail chỉ vì sequence call thay đổi, trong khi business outcome vẫn đúng.

**Ví dụ:**
Thay vì chỉ kiểm tra:
```csharp
emailMock.Verify(x => x.SendAsync(...), Times.Once);
repoMock.Verify(x => x.SaveAsync(...), Times.Once);
```

hãy kiểm tra behavior như:
```text
Given order hợp lệ
When CompleteOrder chạy
Then order chuyển sang Completed
And notification được phát đúng một lần
```

Với database rule hoặc integration boundary, integration test thường có giá trị hơn mock sâu.

**Lưu ý:**
Interaction test vẫn đúng khi contract là “phải gọi đúng một lần”, ví dụ payment capture hoặc external command không được duplicate. Mục tiêu không phải loại bỏ mock, mà tránh để test phản chiếu implementation detail thay vì behavior.

### Tip 5 — Chạy các HTTP call độc lập song song để tránh frontend network waterfall không cần thiết

**Mẹo:**
Trong Vue/React/TypeScript, nếu nhiều request không phụ thuộc dữ liệu của nhau, khởi tạo chúng trước rồi `await Promise.all(...)` thay vì `await` tuần tự từng call.

**Tại sao hữu ích:**
Ba request độc lập lần lượt mất 300 ms, 400 ms và 250 ms có thể tạo gần 950 ms chờ tuần tự. Chạy song song khiến tổng thời gian gần dependency chậm nhất thay vì tổng của tất cả dependency.

**Ví dụ:**
```ts
const [profile, permissions, notifications] = await Promise.all([
  api.getProfile(),
  api.getPermissions(),
  api.getNotifications()
]);
```

Network panel sẽ cho thấy ba request bắt đầu gần nhau thay vì tạo waterfall do code phía client.

**Lưu ý:**
Không song song hóa nếu request sau phụ thuộc kết quả request trước hoặc backend có rate/concurrency limit thấp. `Promise.all` cũng fail-fast khi một promise reject; nếu partial success hợp lệ, cân nhắc `Promise.allSettled` và xử lý failure semantics rõ ràng.

## 🧠 Software Design

### Design 1 — Chỉ định một tầng sở hữu retry để tránh retry amplification

**Khái niệm:**
Trong call chain nhiều tầng, retry nên có owner rõ ràng thay vì để client, API, service nội bộ và SDK đều tự retry cùng một failure. Retry amplification xảy ra khi mỗi tầng nhân số lần gọi của tầng bên dưới.

**Vấn đề nó giải quyết:**
Giả sử ba tầng đều retry tối đa 3 lần. Một request ngoài tưởng chỉ thử 3 lần có thể tạo tới `3 × 3 × 3 = 27` lần gọi xuống dependency cuối. Khi downstream đang quá tải, retry kiểu này làm incident nặng hơn thay vì giúp recovery.

**Ví dụ thực tế:**
```text
Mobile client -> API -> Pricing Service -> external provider

Policy:
- Mobile: không retry operation không idempotent
- API: retry transient Pricing failure tối đa 2 lần
- Pricing SDK: retry disabled hoặc được tính chung vào budget
```

Retry chỉ nên áp cho lỗi transient và phải phối hợp timeout, backoff, jitter cùng idempotency.

**Trade-off:**
Centralize retry giúp reasoning và capacity planning dễ hơn, nhưng tầng sở hữu retry phải hiểu semantics của dependency. Retry quá ít có thể giảm success rate với transient fault; retry quá nhiều tăng latency và load khi dependency đang lỗi.

**Middle → Senior insight:**
Middle developer cần tránh thêm retry máy móc quanh mọi HTTP/database call. Senior / Technical developer phải thiết kế retry budget toàn call chain, xác định operation nào idempotent, tầng nào có đủ context để retry và cách ngăn retry storm trong failure lớn.

### Design 2 — Module boundary trong Modular Monolith phải thể hiện cả ownership dữ liệu, không chỉ namespace

**Khái niệm:**
Modular Monolith chỉ có ý nghĩa khi mỗi module có ownership rõ về business capability và dữ liệu. Tách folder/project nhưng cho mọi module query/update trực tiếp table của nhau vẫn tạo coupling gần giống một monolith không boundary.

**Vấn đề nó giải quyết:**
Một hệ thống có `Orders`, `Catalog` và `Billing`. Nếu `Billing` tự join thẳng bảng `Orders` và `Catalog` ở nhiều nơi, thay schema của Order có thể phá Billing dù code nằm ở project riêng. Boundary trên source code không đủ nếu data access vẫn xuyên module tùy ý.

**Ví dụ thực tế:**
```text
Orders module owns:
- Orders
- OrderLines

Billing module owns:
- Invoices
- Payments

Billing cần order summary:
- gọi application contract của Orders
hoặc
- consume projection/event phù hợp
```

Cùng một physical database vẫn có thể dùng được nếu ownership và access rule được enforce rõ.

**Trade-off:**
Module ownership giảm coupling và tạo migration path tốt hơn, nhưng thêm contract, mapping và đôi khi duplicate read model. Với application CRUD rất nhỏ, boundary quá cứng có thể tạo ceremony lớn hơn giá trị mang lại.

**Middle → Senior insight:**
Middle developer cần không bypass module API chỉ vì “query trực tiếp nhanh hơn”. Senior / Solution-oriented engineer phải chọn boundary theo business capability, transaction need, team ownership và khả năng evolve; mục tiêu là modularity thực tế chứ không phải số lượng project.

### Design 3 — Soft Delete không thay thế audit history hoặc temporal modeling

**Khái niệm:**
Soft Delete thường chỉ đánh dấu record như `IsDeleted = true` hoặc có `DeletedAt`. Nó giải quyết nhu cầu “ẩn nhưng còn giữ record”, nhưng không lưu đầy đủ lịch sử thay đổi của entity qua thời gian.

**Vấn đề nó giải quyết:**
Một hệ thống cần khôi phục customer bị xóa nhầm có thể dùng soft delete. Nhưng nếu requirement là biết ai đổi địa chỉ từ A sang B lúc nào, soft delete hoàn toàn không đủ vì nó chỉ biểu diễn trạng thái hiện tại cùng dấu hiệu xóa.

**Ví dụ thực tế:**
```text
Soft Delete:
Customer(Id=42, IsDeleted=true, DeletedAt=...)

Audit/Temporal requirement:
- 09:00 Address = A
- 10:15 Address = B
- ChangedBy = user-17
- Reason = "customer request"
```

Tùy requirement, có thể dùng audit table, SQL Server temporal table, event log hoặc application-level history.

**Trade-off:**
Soft Delete đơn giản và hỗ trợ restore nhưng làm mọi query phải xử lý record đã xóa, ảnh hưởng unique constraint và data-retention policy. Audit/temporal history cung cấp traceability tốt hơn nhưng tăng storage, schema/process complexity và yêu cầu governance rõ ràng.

**Middle → Senior insight:**
Middle developer cần hiểu global query filter không tự giải quyết restore, uniqueness hay retention. Senior / Technical developer phải phân biệt delete semantics, compliance/audit requirement, retention period và quyền thực sự xóa dữ liệu trước khi chọn soft delete như một mặc định kiến trúc.
