# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Span<T>` cho xử lý buffer ngắn hạn, không escape khỏi stack frame

**Mẹo:**
Khi parse hoặc transform một đoạn dữ liệu ngắn trong hot path, cân nhắc `Span<T>`/`ReadOnlySpan<T>` để làm việc trên vùng nhớ hiện có thay vì tạo thêm substring, array hoặc object trung gian.

**Tại sao hữu ích:**
`Span<T>` là ref struct biểu diễn một vùng nhớ liên tục mà không cần copy dữ liệu. Với parsing nhiều request hoặc xử lý protocol/text, việc giảm allocation tạm thời có thể giảm GC pressure đáng kể.

**Ví dụ:**
```csharp
ReadOnlySpan<char> input = "ORD-2026-00981";

var prefix = input[..3];
var year = input.Slice(4, 4);
var sequence = input[9..];
```

Không có `Substring` nào tạo string mới trong đoạn code trên.

**Lưu ý:**
`Span<T>` không thể được giữ trong field của class thông thường, dùng qua `await` hoặc escape khỏi lifetime hợp lệ. Đừng đưa nó vào business code chỉ để micro-optimize; profiling phải cho thấy allocation nằm trên hot path đáng quan tâm.

### Tip 2 — Với ASP.NET Core, giới hạn request body trước khi validation business chạy

**Mẹo:**
Nếu endpoint nhận JSON hoặc upload, đặt giới hạn kích thước request ở HTTP/server boundary trước khi deserialize hoặc chạy validation domain.

**Tại sao hữu ích:**
Một payload rất lớn có thể tiêu tốn memory, CPU và connection time trước khi application kịp kết luận dữ liệu không hợp lệ. Đây vừa là vấn đề reliability vừa là attack surface cho resource exhaustion.

**Ví dụ:**
Với endpoint upload riêng, có thể cấu hình giới hạn phù hợp use case thay vì để mọi endpoint dùng cùng một mức rất lớn:
```csharp
app.MapPost("/imports", async (HttpRequest request) =>
{
    // validate content type, size and stream progressively
});
```

Ở production, giới hạn còn có thể nằm ở Kestrel, reverse proxy hoặc ingress để chặn sớm hơn.

**Lưu ý:**
Không dùng một limit cứng cho mọi loại request. Upload video và JSON command có profile hoàn toàn khác nhau. Đồng thời kích thước request không thay thế kiểm tra MIME type, extension, malware hoặc authorization.

### Tip 3 — Đọc Actual Execution Plan để tìm implicit conversion làm mất index seek

**Mẹo:**
Khi SQL Server query đáng lẽ dùng index nhưng lại scan, kiểm tra warning về implicit conversion giữa parameter và column trước khi thêm index mới.

**Tại sao hữu ích:**
Nếu database phải convert column cho từng row vì kiểu dữ liệu không khớp, predicate có thể trở nên non-sargable hoặc làm cardinality estimation kém. Index tồn tại nhưng optimizer không thể seek hiệu quả như mong đợi.

**Ví dụ:**
Column:
```sql
CustomerCode varchar(20)
```

Application gửi parameter kiểu `nvarchar(4000)`. Execution plan có thể xuất hiện conversion quanh `CustomerCode`.

Fix nên bắt đầu bằng việc đồng bộ type/length của parameter với schema thay vì tạo thêm một index gần giống index cũ.

**Lưu ý:**
Không phải mọi scan đều xấu; scan có thể đúng khi query trả phần lớn table. Luôn so estimated row, actual row, predicate và logical reads trước khi kết luận index usage là vấn đề.

### Tip 4 — Dùng Docker multi-stage build để tách build toolchain khỏi runtime image

**Mẹo:**
Với .NET container, compile/publish trong SDK stage rồi copy artifact sang ASP.NET runtime image thay vì ship cả SDK vào production container.

**Tại sao hữu ích:**
Runtime image nhỏ hơn, ít package hơn và giảm attack surface. Build dependency cũng không tồn tại trong container chạy production, giúp artifact boundary rõ hơn.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

**Lưu ý:**
Multi-stage build không tự đảm bảo image tối ưu. Nếu `COPY . .` quá sớm, cache restore có thể bị invalidated liên tục. Cũng cần pin base image policy, scan vulnerability và không bake secret vào layer.

### Tip 5 — Với background job nhiều instance, dùng distributed ownership thay vì `Timer` đơn thuần

**Mẹo:**
Nếu cùng application chạy trên nhiều App Service instance, container hoặc Pod, đừng giả định một `Timer`/`BackgroundService` sẽ chỉ chạy một lần toàn hệ thống.

**Tại sao hữu ích:**
Mỗi process có lifecycle riêng và có thể kích hoạt cùng scheduled work. Một job gửi invoice, cleanup hoặc settlement có thể bị chạy N lần khi scale-out nếu không có ownership hoặc idempotency ở distributed level.

**Ví dụ:**
```text
3 application instances
-> 08:00 mỗi instance kích hoạt job
-> cùng đọc 100 records chưa xử lý
-> duplicate side effects
```

Các hướng xử lý gồm scheduler bên ngoài, queue-based dispatch, distributed lease hoặc idempotent claim trên database tùy requirement.

**Lưu ý:**
Distributed lock không phải luôn là lựa chọn tốt nhất. Với workload lớn, claim từng work item hoặc queue consumer thường scale tốt hơn một global lock. Dù dùng cơ chế nào, side effect quan trọng vẫn nên idempotent.

## 🧠 Software Design

### Design 1 — Idempotency Key cho API có side effect và retry từ client

**Khái niệm:**
Idempotency Key cho phép server nhận biết nhiều request retry thuộc cùng một logical operation và trả lại kết quả nhất quán thay vì tạo side effect mới mỗi lần.

**Vấn đề nó giải quyết:**
Client có thể timeout sau khi server đã tạo payment/order nhưng chưa nhận response. Nếu client retry một POST thông thường, server có thể tạo record hoặc charge lần hai.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: 0d847d...
```

Server lưu key cùng fingerprint request và kết quả đã commit. Retry với cùng key trả lại kết quả cũ; cùng key nhưng payload khác phải bị reject.

**Trade-off:**
Idempotency giảm duplicate side effect nhưng thêm storage, expiry policy, request fingerprinting và race-condition handling. Nó cũng không thay thế uniqueness constraint hoặc idempotent consumer ở downstream.

**Middle → Senior insight:**
Middle developer cần hiểu retry không an toàn với mọi POST và phải xử lý duplicate request đúng contract. Senior / Technical developer phải xác định scope của key, retention, concurrency semantics và interaction với transaction/database constraint trước khi công bố API là idempotent.

### Design 2 — Observability boundary: metric cho phát hiện, trace cho localization, log cho forensic detail

**Khái niệm:**
Metrics, traces và logs giải quyết các câu hỏi khác nhau. Một hệ thống observability tốt không cố dùng logging làm mọi thứ mà thiết kế từng signal theo mục tiêu điều tra.

**Vấn đề nó giải quyết:**
Nếu incident chỉ có hàng triệu log line nhưng không có latency percentile, dependency span hoặc correlation, team biết "có lỗi" nhưng khó xác định phạm vi và root cause nhanh.

**Ví dụ thực tế:**
```text
Metric: checkout p95 vượt 2s
-> Trace: 85% latency nằm ở Pricing API
-> Log: Pricing request bị 429 với tenant cụ thể
```

Chuỗi này đi từ symptom tới localization rồi forensic detail.

**Trade-off:**
Nhiều telemetry tăng khả năng chẩn đoán nhưng cũng tăng ingestion cost, storage và privacy risk. Instrument quá chi tiết ở mọi nơi tạo noise tương tự thiếu telemetry.

**Middle → Senior insight:**
Middle developer cần tạo structured log và correlation đúng. Senior / Technical developer phải thiết kế signal nào dùng cho SLO/alert, sampling strategy, cardinality budget và retention dựa trên failure mode thực tế chứ không thu thập mọi thứ vô hạn.

### Design 3 — Modular Monolith trước Microservices khi boundary chưa ổn định

**Khái niệm:**
Modular Monolith giữ deployment unit chung nhưng ép domain/module boundary rõ trong code và data access. Microservices đưa boundary đó sang network, deployment và operational ownership riêng.

**Vấn đề nó giải quyết:**
Một hệ thống mới có domain còn thay đổi mạnh thường chưa biết ranh giới service nào thực sự ổn định. Tách microservice quá sớm biến refactor nội bộ thành schema/message migration và distributed consistency problem.

**Ví dụ thực tế:**
Một SaaS mới có các module:
```text
Orders
Catalog
Billing
Notifications
```

Ban đầu có thể giữ chúng trong một deployable application nhưng cấm cross-module data access tùy tiện và expose contract rõ. Khi Billing có scale, compliance hoặc ownership khác biệt thật sự, boundary đó mới là ứng viên tách service.

**Trade-off:**
Modular Monolith đơn giản hóa deployment, transaction và local debugging nhưng scale/ownership vẫn gắn nhiều hơn vào một runtime. Microservices tăng independent deployment và isolation nhưng thêm network failure, observability, CI/CD, data ownership và eventual consistency cost.

**Middle → Senior insight:**
Middle developer cần giữ module boundary thật thay vì chỉ chia folder. Senior / Technical developer phải chứng minh lý do tách service bằng scale, team autonomy, fault isolation hoặc regulatory boundary; không chọn Microservices chỉ vì đó là kiến trúc "cao cấp" hơn.
