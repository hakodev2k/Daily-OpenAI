# Daily Developer Tips & Design — 2026-08-19

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwait(false)` đúng chỗ trong library code

**Mẹo:**
Trong reusable library hoặc infrastructure code không phụ thuộc vào synchronization context, có thể dùng `await someTask.ConfigureAwait(false)` để tránh yêu cầu continuation quay lại context ban đầu.

**Tại sao hữu ích:**
Điều này giúp giảm coupling với execution context, tránh một số deadlock pattern trong legacy UI/ASP.NET code và làm library behavior rõ ràng hơn. Với ASP.NET Core, lợi ích hiệu năng thường nhỏ vì không có `SynchronizationContext` kiểu cũ, nên đây chủ yếu là vấn đề library semantics và portability.

**Ví dụ:**
```csharp
public async Task<string> LoadAsync(CancellationToken ct)
{
    using var response = await _httpClient.GetAsync("/data", ct)
        .ConfigureAwait(false);

    return await response.Content.ReadAsStringAsync(ct)
        .ConfigureAwait(false);
}
```

**Lưu ý:**
Không áp dụng máy móc trong application code. Nếu continuation thực sự cần quay lại UI thread hoặc một context cụ thể thì `ConfigureAwait(false)` có thể gây lỗi hành vi.

### Tip 2 — Chẩn đoán query EF Core bằng `ToQueryString()` trước khi đổ lỗi cho database

**Mẹo:**
Khi một LINQ query chậm hoặc trả kết quả bất ngờ, gọi `ToQueryString()` để xem SQL mà EF Core thực sự sinh ra.

**Tại sao hữu ích:**
Nó giúp phát hiện sớm các vấn đề như join dư thừa, predicate bị translate khác kỳ vọng, subquery lồng sâu, `LIKE` không dùng index tốt hoặc filter bị đặt sai vị trí.

**Ví dụ:**
```csharp
var query = db.Orders
    .Where(x => x.Status == OrderStatus.Pending)
    .Include(x => x.Items)
    .OrderByDescending(x => x.CreatedAt)
    .Take(50);

Console.WriteLine(query.ToQueryString());
```
Sau đó chạy SQL này trực tiếp trong SQL Server/PostgreSQL cùng execution plan để phân biệt vấn đề nằm ở ORM hay database.

**Lưu ý:**
`ToQueryString()` không cho bạn execution plan và cũng không phản ánh đầy đủ runtime parameter values. Đừng kết luận về performance chỉ dựa vào chuỗi SQL.

### Tip 3 — Dùng `git range-diff` khi review một branch vừa rebase

**Mẹo:**
Khi một PR đã được rebase hoặc force-push, dùng `git range-diff` để so sánh hai phiên bản của chuỗi commit thay vì đọc lại toàn bộ diff từ đầu.

**Tại sao hữu ích:**
Nó cho thấy commit nào thay đổi, commit nào giữ nguyên và reviewer cần tập trung lại vào đâu. Đặc biệt hữu ích với PR lớn đã qua nhiều vòng review.

**Ví dụ:**
```bash
git range-diff origin/main...old-branch origin/main...new-branch
```
Hoặc nếu lưu được hai commit base/head cũ và mới:
```bash
git range-diff oldBase..oldHead newBase..newHead
```

**Lưu ý:**
Kết quả hữu ích nhất khi lịch sử commit có cấu trúc tốt. Nếu branch thường xuyên squash mọi thứ thành một commit lớn thì giá trị của `range-diff` giảm đáng kể.

### Tip 4 — Truyền `CancellationToken` xuyên suốt call chain

**Mẹo:**
Nếu entry point đã nhận `CancellationToken`, hãy truyền nó xuống HTTP call, database call, delay, stream và các async operation hỗ trợ cancellation.

**Tại sao hữu ích:**
Khi client đóng kết nối hoặc request timeout, server có thể dừng công việc không còn giá trị, giảm CPU, DB connections và outbound calls bị lãng phí.

**Ví dụ:**
```csharp
app.MapGet("/reports/{id}", async (
    Guid id,
    AppDbContext db,
    HttpClient http,
    CancellationToken ct) =>
{
    var report = await db.Reports
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    if (report is null)
        return Results.NotFound();

    var metadata = await http.GetFromJsonAsync<Metadata>(
        $"/metadata/{id}", ct);

    return Results.Ok(new { report, metadata });
});
```

**Lưu ý:**
Không nuốt `OperationCanceledException` rồi ghi log ở mức Error như lỗi hệ thống thông thường. Cancellation hợp lệ thường nên được xử lý hoặc log ở mức thấp hơn.

### Tip 5 — Gắn correlation data bằng logging scope thay vì nhét thủ công vào mọi log message

**Mẹo:**
Dùng `ILogger.BeginScope()` để gắn các field như `OrderId`, `UserId`, `TenantId` hoặc `JobId` cho toàn bộ log phát sinh trong một operation.

**Tại sao hữu ích:**
Structured logging giúp query production logs theo context mà không phải lặp lại cùng dữ liệu trong từng message, đồng thời giảm nguy cơ một log line bị thiếu correlation identifier.

**Ví dụ:**
```csharp
using (_logger.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = order.Id,
    ["TenantId"] = tenantId
}))
{
    _logger.LogInformation("Starting payment processing");
    await ProcessPaymentAsync(order, ct);
    _logger.LogInformation("Payment processing completed");
}
```

**Lưu ý:**
Scope chỉ hữu ích nếu logging provider/exporter giữ structured properties. Tránh đưa secret, access token hoặc PII nhạy cảm vào scope vì chúng sẽ xuất hiện trên nhiều log records.

## 🧠 Software Design

### Design 1 — Transaction Boundary phải theo business invariant, không theo số repository call

**Khái niệm:**
Transaction boundary nên bao trọn tập thay đổi phải thành công hoặc thất bại cùng nhau để bảo vệ một business invariant. Nó không nên được quyết định đơn giản bởi việc method đang gọi một hay nhiều repositories.

**Vấn đề nó giải quyết:**
Nếu transaction quá nhỏ, hệ thống có thể lưu trạng thái dở dang. Nếu transaction quá lớn, lock giữ lâu, contention tăng và code khó scale hoặc tích hợp với external systems.

**Ví dụ thực tế:**
Khi xác nhận đơn hàng, việc giảm tồn kho và chuyển `Order.Status` sang `Confirmed` có thể phải nằm trong cùng database transaction. Nhưng gửi email xác nhận không nên nằm trong transaction đó vì SMTP/API bên ngoài có thể chậm hoặc lỗi. Một thiết kế tốt hơn là commit business state cùng một Outbox record, rồi gửi email bất đồng bộ sau commit.

**Trade-off:**
Transaction rộng giúp consistency mạnh và code dễ suy luận hơn, nhưng tăng lock duration và coupling. Transaction hẹp scale tốt hơn nhưng có thể yêu cầu Outbox, retry, idempotency và eventual consistency.

**Middle → Senior insight:**
Middle developer cần nhận biết thao tác nào thực sự phải atomic. Senior developer cần xác định invariant, chọn boundary tối thiểu đủ an toàn, đồng thời thiết kế cách phối hợp external side effects mà không biến distributed workflow thành một transaction khổng lồ.

### Design 2 — Cache-Aside không chỉ là “get rồi set cache”

**Khái niệm:**
Cache-Aside để application đọc cache trước, miss thì đọc source of truth rồi ghi cache. Thiết kế đúng phải quyết định cả invalidation, TTL, stampede control, stale-data tolerance và behavior khi cache hỏng.

**Vấn đề nó giải quyết:**
Nó giảm tải database và latency cho dữ liệu đọc thường xuyên, nhưng nếu chỉ thêm Redis trước database mà không xác định consistency model thì cache rất dễ trả dữ liệu cũ hoặc gây thundering herd.

**Ví dụ thực tế:**
Một API product catalog có 5.000 request/giây nhưng giá sản phẩm chỉ đổi vài lần mỗi giờ. Có thể dùng Cache-Aside với TTL 5 phút và explicit invalidation khi update. Với key nóng, thêm distributed lock hoặc single-flight mechanism để chỉ một request rebuild cache khi key hết hạn.

**Trade-off:**
Cache giảm latency và database load, nhưng thêm operational dependency, memory cost và consistency complexity. TTL ngắn giảm stale data nhưng tăng miss rate; TTL dài tiết kiệm database hơn nhưng kéo dài thời gian dữ liệu cũ tồn tại.

**Middle → Senior insight:**
Middle developer cần hiểu cache miss, TTL và invalidation. Senior developer cần định nghĩa acceptable staleness, failure mode khi Redis down, chống cache stampede, chọn cache key/versioning và biết khi nào cache tạo nhiều complexity hơn giá trị nó mang lại.

### Design 3 — API idempotency cho operation có side effect

**Khái niệm:**
Một operation idempotent cho phép client retry cùng logical request mà không tạo thêm side effect ngoài ý muốn. Với `POST` tạo thanh toán, đơn hàng hoặc job, điều này thường cần một `Idempotency-Key` và persistent record phía server.

**Vấn đề nó giải quyết:**
Trong distributed systems, timeout không cho biết request đã thất bại hay server đã xử lý thành công nhưng response bị mất. Nếu client retry mù quáng, hệ thống có thể charge hai lần hoặc tạo hai resource.

**Ví dụ thực tế:**
Client gửi:
```http
POST /payments
Idempotency-Key: 7bb23d51-2afe-4d7e-a3a1-631519bf54cf
```
Server lưu key cùng request fingerprint và result trong database. Nếu key xuất hiện lại với cùng payload, server trả lại kết quả trước đó thay vì chạy payment workflow lần nữa. Nếu cùng key nhưng payload khác, server nên reject.

**Trade-off:**
Idempotency cải thiện reliability và retry safety, nhưng cần storage, cleanup policy, concurrency control và xác định scope của key. Nếu triển khai sơ sài chỉ check key rồi insert sau, hai request đồng thời vẫn có thể vượt qua kiểm tra.

**Middle → Senior insight:**
Middle developer cần biết retry có thể tạo duplicate side effect. Senior developer phải thiết kế atomic uniqueness, request fingerprint, retention period, response replay, xử lý concurrent duplicate requests và xác định operation nào thực sự cần idempotency thay vì áp dụng cho mọi endpoint.
