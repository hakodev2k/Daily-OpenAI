# Daily Developer Tips & Design — 2026-09-28

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt timeout với cancellation trong outbound HTTP

**Mẹo:**
Với `HttpClient`, hãy tách rõ timeout do policy của dependency với cancellation do request phía client hoặc application shutdown. Truyền `CancellationToken` xuyên suốt và đặt timeout có chủ đích tại integration boundary.

**Tại sao hữu ích:**
Cả hai đều có thể kết thúc dưới dạng `OperationCanceledException`, nhưng ý nghĩa vận hành khác nhau. Client hủy request không nhất thiết là lỗi dependency; dependency vượt SLA lại là tín hiệu cần metrics, retry hoặc circuit breaker phù hợp.

**Ví dụ:**
```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

try
{
    return await httpClient.GetAsync("/inventory", timeoutCts.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    throw new TimeoutException("Inventory API exceeded 2s.");
}
```

**Lưu ý:**
Không retry mọi timeout theo phản xạ. Với POST không idempotent, request đầu tiên có thể đã thành công ở server dù client chưa nhận response; retry có thể tạo duplicate side effect.

### Tip 2 — Dùng projection để tránh EF Core materialize object graph không cần thiết

**Mẹo:**
Với read endpoint, ưu tiên `Select` trực tiếp sang DTO thay vì `Include` nhiều navigation rồi map sau khi query hoàn tất.

**Tại sao hữu ích:**
Projection cho database chỉ trả các cột cần thiết, giảm network payload, allocation và change-tracking overhead. Nó cũng tránh Cartesian explosion khi nhiều collection navigation được join trong một query.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.CreatedAt,
        x.Items.Count,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(ct);
```
Kiểm tra SQL sinh ra bằng logging hoặc `ToQueryString()` khi query trở nên phức tạp.

**Lưu ý:**
Projection không tự động làm mọi query nhanh. Aggregate correlated subquery, predicate không sargable hoặc thiếu index vẫn có thể đắt; hãy kiểm tra generated SQL và execution plan.

### Tip 3 — Điều tra connection-pool exhaustion từ thời gian giữ connection

**Mẹo:**
Khi API bắt đầu timeout vì SQL connection pool cạn, đừng chỉ tăng pool size. Đo số connection active, thời gian query/transaction và các request giữ connection lâu để tìm nguyên nhân.

**Tại sao hữu ích:**
Pool exhaustion thường là triệu chứng: slow query, transaction kéo dài, concurrency tăng hoặc code không giải phóng resource đúng lúc. Tăng pool chỉ cho phép nhiều workload hơn cùng dồn vào database và có thể làm bottleneck nặng hơn.

**Ví dụ:**
Một endpoint mở transaction, query database rồi gọi external payment API 5 giây trước khi commit. Connection có thể bị giữ trong suốt network wait. Tách external I/O khỏi database transaction có thể giảm đáng kể connection occupancy.

**Lưu ý:**
Không suy luận “pool leak” chỉ từ timeout. Xác minh dependency duration, database waits, request concurrency và transaction scope; đồng thời dùng `await using`/DI lifecycle đúng cho resource cần dispose.

### Tip 4 — Dùng readiness khác liveness trong Kubernetes

**Mẹo:**
Thiết kế liveness probe để trả lời “process có cần restart không?”, còn readiness probe trả lời “instance có nên nhận traffic không?”. Đừng để cả hai phụ thuộc vào mọi downstream service theo cùng một cách.

**Tại sao hữu ích:**
Nếu SQL tạm thời unavailable mà liveness cũng fail, Kubernetes có thể restart hàng loạt Pods dù restart không chữa được database outage. Readiness có thể tạm rút Pod khỏi traffic mà không tạo restart storm.

**Ví dụ:**
ASP.NET Core health checks có thể tách endpoint:
```text
/health/live   -> process/runtime health
/health/ready  -> dependencies cần thiết để phục vụ request
```
Deployment chỉ route traffic khi readiness đạt yêu cầu.

**Lưu ý:**
Readiness quá nghiêm cũng có thể loại toàn bộ replicas khỏi Service khi một dependency phụ bị lỗi. Chỉ đưa dependency vào probe nếu trạng thái của nó thực sự quyết định khả năng phục vụ workload đó.

### Tip 5 — Với AI coding agent, yêu cầu bằng chứng từ repository trước khi sửa code

**Mẹo:**
Khi dùng AI agent để fix bug hoặc refactor, yêu cầu nó xác định call path, version package, tests liên quan và source files làm bằng chứng trước khi đề xuất thay đổi.

**Tại sao hữu ích:**
Agent có thể sinh API tồn tại ở version khác, giả định sai architecture hoặc thêm abstraction không phù hợp. Grounding vào repository biến task từ “generate plausible code” thành “thay đổi code dựa trên constraints thực tế”.

**Ví dụ:**
Thay vì yêu cầu “fix retry”, scope task thành: tìm nơi tạo `HttpClient`, xác định retry hiện tại, đọc package versions, tái hiện failure bằng test, sau đó chỉ sửa boundary liên quan và chạy test suite bị ảnh hưởng.

**Lưu ý:**
Tests do chính agent sinh không phải bằng chứng độc lập nếu chúng chỉ mirror implementation mới. Review observable behavior, security, migration impact và diff cuối cùng như với code của một developer khác.

## 🧠 Software Design

### Design 1 — Retry budget thay vì retry vô hạn ở mọi layer

**Khái niệm:**
Retry là cơ chế resilience cho transient failure, nhưng cần một budget về số lần thử và tổng thời gian. Mỗi layer không nên tự retry độc lập mà không biết deadline tổng của operation.

**Vấn đề nó giải quyết:**
Nếu API gateway retry 3 lần, service retry 3 lần và database/client bên dưới cũng retry 3 lần, một request lỗi có thể khuếch đại thành nhiều lần tải lên dependency đang gặp sự cố, gây retry storm.

**Ví dụ thực tế:**
Checkout có deadline 5 giây. Payment dependency chỉ được phép retry lỗi transient nếu còn đủ deadline và operation có idempotency. Backoff có jitter giảm việc nhiều instances retry đồng thời.

**Trade-off:**
Retry cải thiện success rate trước lỗi ngắn hạn nhưng tăng latency, traffic và duplicate risk. Budget quá nhỏ làm mất khả năng tự hồi phục; quá lớn kéo dài failure và gây overload.

**Middle → Senior insight:**
Middle developer cần phân loại lỗi retryable, dùng backoff/cancellation và tránh retry operation không an toàn. Senior / Technical developer phải thiết kế retry ownership xuyên các layer, deadline propagation, idempotency và telemetry để resilience không trở thành load amplifier.

### Design 2 — Cache-aside với stale tolerance có chủ đích

**Khái niệm:**
Cache-aside để application đọc cache trước, miss thì đọc source of truth và populate cache. Thiết kế tốt phải xác định dữ liệu được phép stale bao lâu và behavior khi Redis lỗi, không chỉ chọn một TTL.

**Vấn đề nó giải quyết:**
Các read-heavy endpoint như product catalog có thể gây tải lớn lên SQL. Nhưng cache tạo thêm consistency boundary: database thay đổi trong khi cache vẫn giữ giá trị cũ.

**Ví dụ thực tế:**
Product description có thể chấp nhận stale 5 phút, trong khi inventory availability cần policy chặt hơn. Khi Redis unavailable, catalog API có thể fallback SQL có rate protection thay vì biến cache outage thành outage toàn site.

**Trade-off:**
Cache giảm latency và database load nhưng thêm invalidation, stampede, stale data và một dependency vận hành. TTL ngắn tăng freshness nhưng tăng miss; TTL dài giảm load nhưng kéo dài inconsistency.

**Middle → Senior insight:**
Middle developer cần implement key/TTL/invalidation và tránh cache stampede cơ bản. Senior / Technical developer phải phân loại dữ liệu theo consistency requirement, xác định degradation strategy, capacity khi cache mất và quyết định dữ liệu nào không đáng cache.

### Design 3 — Strangler migration cho hệ thống .NET legacy

**Khái niệm:**
Strangler migration thay thế legacy system theo từng capability: traffic hoặc use case được chuyển dần sang implementation mới trong khi phần cũ vẫn hoạt động, thay vì rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Một ASP.NET/.NET Framework monolith lớn có thể chứa nhiều business rule không được tài liệu hóa. Big-bang rewrite tạo khoảng thời gian dài không mang lại giá trị và dồn discovery risk tới cuối dự án.

**Ví dụ thực tế:**
Tách module document download trước: reverse proxy/router đưa route mới sang ASP.NET Core, giữ các CMS/admin routes trên legacy application. Contract, telemetry và rollback path được giữ rõ trong giai đoạn coexistence.

**Trade-off:**
Migration từng phần giảm blast radius và cho phép release sớm, nhưng tạm thời phải vận hành hai stacks, quản lý routing, shared identity/data và tránh logic bị duplicate lâu dài.

**Middle → Senior insight:**
Middle developer cần bảo toàn contract, viết characterization/integration tests và tránh làm hỏng interoperability. Senior / Technical developer phải chọn seam theo business capability, lập data-ownership migration, observability và decommission criteria; nếu coexistence không có exit plan, “temporary bridge” dễ trở thành technical debt vĩnh viễn.
