# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — `IAsyncDisposable` quan trọng khi cleanup cũng là I/O

**Mẹo:**
Khi resource cần flush hoặc đóng bất đồng bộ, dùng `await using`/`IAsyncDisposable` thay vì ép cleanup I/O vào `Dispose()` đồng bộ.

**Tại sao hữu ích:**
Cleanup của stream, transaction wrapper hoặc client có thể cần chờ network/storage. Chặn thread bằng `.Wait()`/`.Result` trong `Dispose()` làm tăng ThreadPool pressure và dễ tạo latency bất thường dưới tải.

**Ví dụ:**
```csharp
await using var stream = await blobClient.OpenWriteAsync(
    overwrite: true,
    cancellationToken: ct);

await payload.CopyToAsync(stream, ct);
```
Compiler bảo đảm `DisposeAsync()` được await khi scope kết thúc, kể cả khi exception xảy ra.

**Lưu ý:**
Không implement `IAsyncDisposable` chỉ vì class có method async. Chỉ dùng khi chính quá trình release resource cần async work; đồng thời hiểu ownership để tránh dispose dependency do DI container quản lý.

### Tip 2 — EF Core transaction nên bao quanh database invariant, không bao quanh cả workflow

**Mẹo:**
Giữ database transaction ngắn và không đặt outbound HTTP/message processing dài bên trong transaction nếu invariant không yêu cầu.

**Tại sao hữu ích:**
Transaction mở lâu giữ locks/version state và connection lâu hơn. Một payment API mất 8 giây trong transaction có thể biến traffic bình thường thành blocking, deadlock hoặc connection-pool exhaustion.

**Ví dụ:**
```text
Sai boundary:
BEGIN -> update Order -> gọi Payment API 8s -> insert Audit -> COMMIT

Tốt hơn:
BEGIN -> update Order + durable workflow state -> COMMIT
-> thực hiện external step
-> tiếp tục workflow bằng idempotent state transition
```

**Lưu ý:**
Không đơn giản “commit sớm” nếu điều đó phá business invariant. Khi workflow vượt một database transaction, phải thiết kế failure/recovery semantics rõ ràng thay vì giả vờ có atomicity end-to-end.

### Tip 3 — Azure Service Bus Prefetch phải khớp processing time và lock semantics

**Mẹo:**
Tăng Prefetch chỉ sau khi đo throughput, message processing time và lock duration; đừng coi Prefetch lớn là tuning miễn phí.

**Tại sao hữu ích:**
Prefetch đưa messages về client buffer trước khi handler xử lý. Nếu buffer quá lớn so với concurrency và processing time, lock của message có thể tiêu hao trong lúc chờ local queue, dẫn tới lock expiry/redelivery dù handler chưa thực sự bắt đầu.

**Ví dụ:**
```text
MaxConcurrentCalls = 8
Average processing = 2s
Prefetch = 500
Lock duration = 30s
```
Một lượng lớn messages có thể nằm trong buffer đủ lâu để lock trở thành vấn đề. Bắt đầu từ workload thực tế rồi tune Prefetch/concurrency cùng nhau.

**Lưu ý:**
Auto lock renewal không biến processing vô hạn thành an toàn. Handler vẫn phải idempotent vì at-least-once delivery và process crash có thể tạo duplicate.

### Tip 4 — Kubernetes memory limit không giống GC heap limit

**Mẹo:**
Khi .NET container bị `OOMKilled`, xem cả container memory working set và GC/runtime metrics; đừng chỉ nhìn managed heap rồi kết luận “không thể hết RAM”.

**Tại sao hữu ích:**
Process memory gồm managed heap, native allocations, thread stacks, JIT/code, buffers và runtime overhead. Kubernetes enforce cgroup memory limit ở process/container level, nên managed heap 600 MB trong pod limit 1 GB vẫn có thể OOM nếu native/other memory tăng.

**Ví dụ:**
```text
Pod limit:          1 GiB
GC heap:            620 MiB
Native + stacks:    210 MiB
Other/runtime:      140 MiB
Peak total:         > 1 GiB
Result:             OOMKilled
```
Đối chiếu pod metrics, restart reason và .NET counters/dump trước khi tăng limit.

**Lưu ý:**
Tăng memory limit có thể chỉ trì hoãn leak. Ngược lại, limit quá thấp cũng khiến GC chạy aggressive và giảm throughput; cần sizing theo load test và production evidence.

### Tip 5 — AI-generated migration phải được review như production data code

**Mẹo:**
Khi AI coding agent tạo EF Core/SQL migration, kiểm tra generated SQL, lock behavior, data volume và rollback/recovery plan thay vì chỉ thấy project build thành công.

**Tại sao hữu ích:**
Agent có thể tạo migration đúng schema về mặt logic nhưng nguy hiểm ở production: rewrite bảng lớn, thêm `NOT NULL` không có backfill, tạo index blocking hoặc drop/rename làm mất dữ liệu.

**Ví dụ:**
```text
AI đề xuất:
ALTER TABLE Orders ADD ExternalId nvarchar(100) NOT NULL DEFAULT '';

Review cần hỏi:
- bảng có bao nhiêu rows?
- operation có lock/rewrite lớn không?
- existing rows được backfill thế nào?
- app version cũ có tương thích không?
- deploy có cần expand-and-contract không?
```

**Lưu ý:**
Test trên database nhỏ không phản ánh migration cost production. AI giúp tạo draft và checklist, nhưng schema/data migration vẫn cần evidence từ engine/version/workload thực tế.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work/change tracking và `DbSet` cung cấp query/data-access abstraction. Repository riêng chỉ đáng có khi nó tạo boundary có giá trị thực, không phải vì mọi project “phải có repository”.

**Vấn đề nó giải quyết:**
Application có thể cần che một persistence model phức tạp, enforce aggregate access hoặc cung cấp business-oriented query boundary. Nhưng generic repository kiểu `GetAll/Add/Update` thường chỉ bọc EF Core, làm mất `IQueryable` capability hoặc tạo thêm layer không có semantics.

**Ví dụ thực tế:**
Một CRUD admin module có thể inject `DbContext` trực tiếp trong application handler. Một domain phức tạp có `IOrderRepository.LoadForFulfillment()` để bảo vệ cách aggregate được load và persistence details cần thiết cho invariant.

**Trade-off:**
Direct `DbContext` giảm boilerplate và tận dụng EF Core đầy đủ nhưng tăng coupling application layer với persistence framework. Repository có thể tạo domain boundary/test seam tốt hơn nhưng dễ trở thành abstraction rỗng, query explosion hoặc duplicated API.

**Middle → Senior insight:**
Middle developer cần hiểu lifetime, query translation và transaction behavior của `DbContext`. Senior / Technical developer phải hỏi abstraction đang che volatility/domain complexity nào, ai sở hữu query semantics và chi phí thay đổi; pattern không có mục đích cụ thể là technical debt sớm.

### Design 2 — Queue vs Topic theo ownership của message

**Khái niệm:**
Queue thường biểu diễn work cần một consumer logic xử lý; Topic/pub-sub cho phép một published event được fan-out tới nhiều subscriptions độc lập. Lựa chọn phản ánh semantics và ownership, không chỉ số lượng consumers hiện tại.

**Vấn đề nó giải quyết:**
Sau `OrderPlaced`, Email, Analytics và Loyalty đều cần phản ứng độc lập. Nếu producer gửi ba queue commands, producer biết quá nhiều downstream consumers. Nếu một command `GenerateInvoice` lại broadcast như event, nhiều handlers có thể vô tình tranh ownership của cùng work.

**Ví dụ thực tế:**
`GenerateInvoice` vào queue do Billing sở hữu. `OrderPlaced` publish lên topic; Email/Loyalty/Analytics có subscription riêng với retry/DLQ độc lập và có thể được thêm mà không sửa Order service.

**Trade-off:**
Queue đơn giản hóa single-work ownership và competing consumers. Topic giảm producer coupling và hỗ trợ fan-out nhưng tăng subscription lifecycle, duplicated delivery, schema evolution và observability complexity.

**Middle → Senior insight:**
Middle developer cần hiểu settlement, retry, DLQ và idempotency. Senior / Technical developer phải phân biệt command với event, xác định ownership, delivery guarantees, replay needs và hậu quả khi một subscription chậm hoặc mất dữ liệu.

### Design 3 — Modular Monolith trước Microservices khi boundary chưa đủ chín

**Khái niệm:**
Modular Monolith giữ một deployable unit nhưng ép boundaries nội bộ rõ ràng giữa modules. Nó cho phép phát triển domain separation mà chưa trả toàn bộ distributed-systems tax của Microservices.

**Vấn đề nó giải quyết:**
Một sản phẩm đang thay đổi nhanh có 6 developers và domain boundaries còn biến động. Tách sớm thành nhiều services khiến mỗi thay đổi xuyên boundary kéo theo API contracts, deployment coordination, tracing, messaging và eventual consistency trước khi lợi ích independent scaling/deployment xuất hiện.

**Ví dụ thực tế:**
Commerce application có `Catalog`, `Ordering`, `Identity` modules với schema/code ownership và public module APIs rõ ràng nhưng deploy chung. Khi `Catalog` thực sự cần scaling/release cadence/team ownership độc lập, boundary đã được quan sát đủ để cân nhắc extraction.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, transactions và local debugging nhưng vẫn có shared-process blast radius và cần discipline để tránh cross-module coupling. Microservices tăng autonomy/scaling isolation nhưng thêm network failure, observability, data ownership và operational cost.

**Middle → Senior insight:**
Middle developer cần tôn trọng module boundaries dù compiler/database cho phép đi tắt. Senior / Technical developer phải đánh giá team topology, scaling pressure, release independence, failure isolation và domain maturity; khả năng tách service sau này thường đáng giá hơn việc phân tán hệ thống ngay hôm nay.
