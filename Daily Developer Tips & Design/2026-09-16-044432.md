## Developer Tips & Tricks

### 1. `HttpClient` timeout không thay thế deadline propagation giữa các service

**Vấn đề thực tế:** API A có request budget 2 giây nhưng gọi B với `HttpClient.Timeout = 100s`. Client đã disconnect hoặc upstream deadline đã hết, trong khi A vẫn tiếp tục giữ connection và chờ B. Khi chuỗi A → B → C dài, mỗi service tự đặt timeout độc lập có thể khiến work vô ích tiếp tục rất lâu.

**Cơ chế bên dưới:** Timeout của một dependency chỉ giới hạn riêng call đó. Deadline là budget của toàn request và phải giảm dần khi request đi qua các hop. ASP.NET Core cung cấp `RequestAborted`; outbound operation nên nhận cancellation token liên kết với request và timeout/deadline cục bộ.

```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(
    httpContext.RequestAborted);
timeoutCts.CancelAfter(TimeSpan.FromMilliseconds(750));

using var response = await httpClient.GetAsync(
    $"/inventory/{sku}",
    HttpCompletionOption.ResponseHeadersRead,
    timeoutCts.Token);
```

Cancellation không bảo đảm remote server đã dừng xử lý; protocol/service downstream cũng phải hỗ trợ cancellation/deadline semantics. Với side effects, cancellation còn cần được thiết kế cùng idempotency.

**Khi nên dùng:** Service-to-service HTTP, fan-out APIs và request paths có latency SLO rõ ràng.

### 2. SQL Server parameter sniffing: query nhanh trong SSMS nhưng chậm production có thể do cached plan

**Vấn đề thực tế:** Stored procedure/query dùng parameter chạy vài millisecond với một customer nhỏ nhưng hàng chục giây với customer rất lớn. Developer copy SQL sang SSMS và thấy nhanh, nên nghi ngờ EF Core hoặc network.

**Cơ chế bên dưới:** SQL Server có thể compile execution plan dựa trên parameter values ở lần compilation và reuse plan đó cho các lần sau. Khi data distribution skew mạnh, plan tốt cho selective value có thể rất tệ cho non-selective value và ngược lại. SSMS execution có thể nhận plan khác vì SET options, recompilation hoặc cache state khác production.

**Cách điều tra:** So sánh actual execution plan, estimated/actual row counts, Query Store history và parameter values. Đừng chữa bằng `OPTION (RECOMPILE)` trên mọi query vì recompilation tăng CPU.

```sql
SELECT CustomerId, COUNT_BIG(*) AS OrderCount
FROM dbo.Orders
GROUP BY CustomerId
ORDER BY OrderCount DESC;
```

Nếu skew là root cause, lựa chọn có thể gồm query shape khác theo workload class, `OPTIMIZE FOR`, recompilation có chọn lọc, index phù hợp hoặc SQL Server Parameter Sensitive Plan optimization ở phiên bản hỗ trợ.

**Khi nên dùng:** Production-only SQL latency, stored procedures có cardinality skew, multi-tenant tables và query có performance biến động lớn dù input shape giống nhau.

### 3. `Channel<T>` giúp bounded producer/consumer thay vì tạo hàng nghìn `Task` cùng lúc

**Vấn đề thực tế:** Background worker đọc 50.000 records rồi tạo một task cho mỗi record bằng `Task.WhenAll`. Throughput ban đầu cao nhưng memory, outbound connections và dependency load tăng mạnh; khi downstream chậm, process có thể tự gây overload.

**Cơ chế bên dưới:** `System.Threading.Channels` cho phép tách producer và consumers, đồng thời đặt bounded capacity. Khi queue đầy, producer có thể chờ thay vì tiếp tục sinh work không giới hạn. Đây là backpressure ở application level.

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(200)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleWriter = true
});

await foreach (var job in source.WithCancellation(cancellationToken))
    await channel.Writer.WriteAsync(job, cancellationToken);

channel.Writer.Complete();
```

Consumer count phải dựa trên bottleneck thực tế. I/O concurrency 32 không có nghĩa database connection pool hoặc vendor rate limit chịu được 32 concurrent calls.

**Khi nên dùng:** Background processing, ingestion pipeline, file import, bounded parallel I/O và workloads cần explicit backpressure nhưng chưa cần durable broker.

### 4. MongoDB compound index phải theo query shape, không phải theo danh sách field “hay dùng”

**Vấn đề thực tế:** Collection có index riêng cho `tenantId`, `status`, `createdAt`, nhưng query phổ biến `{tenantId, status}` rồi sort `createdAt desc` vẫn scan nhiều keys và phải sort tốn memory.

**Cơ chế bên dưới:** Compound index có ordering. Equality predicates thường nên đứng trước range/sort fields để index có thể thu hẹp prefix và phục vụ ordering. Ba single-field indexes không mặc nhiên tương đương một compound index phù hợp với filter + sort thực tế.

```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })

db.orders.find({
  tenantId: tenant,
  status: "Pending"
}).sort({ createdAt: -1 }).limit(100).explain("executionStats")
```

Đọc `totalKeysExamined`, `totalDocsExamined`, returned rows và execution stages. Mỗi index thêm write amplification và storage cost, nên index portfolio phải được quản lý theo workload.

**Khi nên dùng:** MongoDB collections lớn, multi-tenant queries, pagination/sorting và endpoints có scan-to-return ratio cao.

### 5. Debug async deadlock bằng thread dump: nhìn “ai đang chờ ai” thay vì chỉ nhìn exception

**Vấn đề thực tế:** Process không crash nhưng request throughput về gần zero. Logs không có exception đáng kể. Nhiều thread đang blocked tại `.Result`, `.Wait()` hoặc lock, trong khi continuations cần worker threads để tiến triển.

**Cơ chế bên dưới:** Liveness failure thường không tạo exception. Thread dump cho thấy stacks tại một thời điểm: thread nào đang monitor-wait, semaphore-wait, sync-over-async hoặc chạy CPU. Kết hợp với ThreadPool counters giúp phân biệt deadlock, starvation và dependency stall.

```bash
dotnet-counters monitor --process-id <pid> System.Runtime
dotnet-dump collect --process-id <pid>
dotnet-dump analyze <dump-file>
```

Trong analyzer, kiểm tra thread stacks và repeated blocking frames. Một dump duy nhất đôi khi chưa đủ; hai dump cách nhau vài giây giúp xác định stacks có thực sự không tiến triển.

**Khi nên dùng:** Hung process, request queue tăng, ThreadPool queue dài, CPU thấp bất thường hoặc production incident không có exception rõ ràng.

## Software Design

### 6. CQRS không có nghĩa phải tách database hay dùng message broker

**Vấn đề thực tế:** Team muốn áp dụng CQRS nên lập tức tạo hai databases, event bus và eventual consistency dù application chỉ cần tách read model khỏi write behavior. Complexity vận hành tăng trước khi có nhu cầu thực tế.

**Thiết kế:** CQRS cốt lõi là tách command model và query model vì chúng có nhu cầu khác nhau. Mức đơn giản nhất vẫn có thể dùng cùng process và cùng database nhưng command đi qua domain/application behavior, còn query projection trực tiếp DTO tối ưu cho đọc.

```text
             API
          /       \
         v         v
     Commands     Queries
         |           |
         v           v
 Domain behavior   Read DTO
         |           |
         +-----+-----+
               v
          Same Database
```

**Trade-off:** Tách model giúp write invariants không bị ép theo UI read shape và query có thể tối ưu độc lập. Nhưng nếu thêm separate stores/event propagation, bạn phải trả giá bằng consistency lag, synchronization, replay/rebuild và operational complexity.

**Khi phù hợp:** Read/write có model hoặc scaling profile khác nhau. Bắt đầu với logical CQRS trước; chỉ physical separation khi requirements chứng minh cần thiết.

### 7. Strangler Fig pattern: migrate legacy theo capability thay vì big-bang rewrite

**Vấn đề thực tế:** Monolith cũ khó thay đổi nhưng vẫn tạo doanh thu. Rewrite toàn bộ mất nhiều tháng và chỉ tạo value khi gần hoàn thành; meanwhile legacy tiếp tục thay đổi nên target luôn dịch chuyển.

**Thiết kế:** Đặt routing/facade ở boundary rồi chuyển từng capability sang implementation mới. Traffic cho phần đã migrate đi vào new system; phần còn lại vẫn vào legacy. Sau khi capability cũ không còn caller, nó được retire.

```text
Clients
   |
   v
Routing / Facade
   |          \
   |           \
   v            v
New Orders    Legacy System
Service       - Customers
              - Billing
              - Reports
```

**Trade-off:** Migration tạo giai đoạn coexistence: duplicated models, integration bridges, data ownership ambiguity và observability qua hai systems. Boundary migration phải được chọn theo business capability, không chỉ theo technical layer như “rewrite repositories trước”.

**Khi phù hợp:** Legacy modernization, framework/runtime migration, monolith decomposition và hệ thống không thể dừng feature delivery để rewrite toàn bộ.

### 8. Idempotent Consumer: “exactly once” thường phải được xây từ business state, không chỉ tin broker

**Vấn đề thực tế:** Consumer xử lý `PaymentCaptured`, update order rồi crash trước khi acknowledge message. Broker redeliver message và consumer chạy side effect lần hai. At-least-once delivery biến một event logic thành nhiều delivery vật lý.

**Thiết kế:** Consumer lưu message identity hoặc business operation identity cùng transaction với state change. Nếu message đã xử lý, lần delivery tiếp theo trở thành no-op. Với một số aggregate, natural idempotency tốt hơn bảng inbox riêng: ví dụ chỉ chuyển `PendingPayment → Paid` nếu state transition còn hợp lệ.

```text
Receive message M42
      |
      v
Begin DB transaction
      |
      +--> Is M42 processed? -- yes --> no-op
      |
      no
      |
      +--> apply business change
      +--> record M42 processed
      |
    COMMIT
      |
      v
Acknowledge broker
```

**Trade-off:** Deduplication store cần retention/cleanup và message IDs ổn định. Natural idempotency giảm infrastructure nhưng chỉ dùng được khi domain transition thực sự an toàn khi lặp.

**Khi phù hợp:** Message brokers với at-least-once delivery, Outbox/Inbox architecture, payment/order workflows và consumers có non-trivial side effects.
