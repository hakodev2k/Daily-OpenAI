# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Nhận diện ThreadPool starvation trước khi đổ lỗi cho CPU

**Mẹo:**
Khi ASP.NET Core API có latency tăng mạnh nhưng CPU chưa chạm 100%, kiểm tra ThreadPool starvation và các điểm sync-over-async như `.Result`, `.Wait()` hoặc blocking I/O trong request path.

**Tại sao hữu ích:**
ASP.NET Core dựa nhiều vào ThreadPool. Nếu request thread bị block trong lúc chờ I/O, ThreadPool phải bổ sung worker thread dần dần. Trong khoảng đó request mới xếp hàng, p95/p99 tăng dù CPU tổng thể còn thấp. Đây là lý do code “vẫn chạy đúng” ở dev nhưng sụp dưới concurrency cao.

**Ví dụ:**
Theo dõi runtime counters:

```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Nếu `thread_pool.queue.length` tăng cùng latency và số thread tiếp tục tăng, tìm các call blocking như:

```csharp
var response = httpClient.GetAsync(url).Result;
```

Thay bằng async xuyên suốt:

```csharp
var response = await httpClient.GetAsync(url, cancellationToken);
```

**Lưu ý:**
Không kết luận mọi queue tăng đều là starvation. Dependency chậm, connection pool cạn hoặc rate limit cũng có thể làm request backlog. Luôn đối chiếu ThreadPool metrics với dependency latency và CPU.

### Tip 2 — Dùng keyset pagination khi OFFSET bắt đầu quét ngày càng nhiều row

**Mẹo:**
Với bảng lớn và luồng “next page” tuần tự, cân nhắc keyset pagination thay vì `OFFSET ... FETCH` hoặc `Skip()` rất sâu.

**Tại sao hữu ích:**
Offset pagination thường phải xác định rồi bỏ qua toàn bộ row trước vị trí cần lấy. Khi page number tăng, database có thể đọc/sort nhiều dữ liệu hơn chỉ để bỏ chúng đi. Keyset pagination tiếp tục từ giá trị sort cuối cùng và có thể tận dụng index hiệu quả hơn.

**Ví dụ:**
Thay vì:

```sql
SELECT id, created_at, total
FROM orders
ORDER BY created_at DESC, id DESC
OFFSET 100000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Dùng cursor từ page trước:

```sql
SELECT id, created_at, total
FROM orders
WHERE created_at < @lastCreatedAt
   OR (created_at = @lastCreatedAt AND id < @lastId)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Composite index phù hợp với thứ tự sort giúp query seek gần vị trí cần đọc.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 742 hoặc cần total page chính xác liên tục. Cursor cũng phải bao gồm tie-breaker ổn định như `id` để tránh duplicate/missing row.

### Tip 3 — Trong Elasticsearch, phân biệt `text` và `keyword` ngay từ mapping

**Mẹo:**
Dùng `text` cho full-text search cần analyzer/tokenization và `keyword` cho exact match, filter, sort hoặc aggregation. Đừng dựa vào dynamic mapping rồi sửa sau khi index đã chứa dữ liệu production.

**Tại sao hữu ích:**
`text` được phân tích thành token nên không phù hợp cho exact aggregation/sort như một giá trị nguyên khối. `keyword` giữ nguyên giá trị nhưng không cung cấp behavior full-text tương tự. Mapping sai thường chỉ lộ ra khi query hoặc aggregation tăng tải.

**Ví dụ:**
```json
{
  "properties": {
    "productName": {
      "type": "text",
      "fields": {
        "raw": { "type": "keyword" }
      }
    }
  }
}
```

Search dùng `productName`, còn sort/aggregation dùng `productName.raw`.

**Lưu ý:**
Đừng tạo `.keyword` cho mọi string không giới hạn. High-cardinality fields, oversized values và field explosion làm index nặng hơn. Mapping nên phản ánh query pattern thực tế.

### Tip 4 — Với Azure App Service deployment slots, tách code deployment khỏi configuration promotion

**Mẹo:**
Khi dùng deployment slots, đánh dấu đúng các setting cần “slot-sticky” như connection string hoặc endpoint dành riêng cho staging, và kiểm tra warm-up/health trước khi swap.

**Tại sao hữu ích:**
Slot swap đổi traffic và một phần configuration theo rule của App Service. Nếu secret hoặc endpoint môi trường bị swap nhầm, production có thể kết nối vào staging dependency dù artifact hoàn toàn đúng. Ngược lại, warm-up tốt giúp giảm cold-start sau swap.

**Ví dụ:**
Một staging slot có:

```text
ASPNETCORE_ENVIRONMENT=Staging
PaymentApi=https://sandbox-payment.example
```

Các setting đặc thù slot phải được cấu hình là deployment slot setting. Pipeline deploy artifact vào staging, chạy health check rồi mới swap sang production.

**Lưu ý:**
Slot swap không thay thế database migration strategy. Nếu version mới yêu cầu schema breaking change, cả old và new slot có thể cùng tồn tại trong thời gian swap; migration cần backward-compatible hoặc có rollout plan riêng.

### Tip 5 — Trong Vue.js, đừng dùng `watch` để duy trì state có thể tính trực tiếp

**Mẹo:**
Nếu một giá trị chỉ là hàm thuần của state khác, ưu tiên `computed` thay vì dùng `watch` để copy và đồng bộ state thủ công.

**Tại sao hữu ích:**
Duplicated derived state tạo thêm nguồn sự thật. `watch` có thể chạy lệch thứ tự, quên cập nhật một dependency hoặc tạo loop. `computed` biểu diễn dependency trực tiếp và chỉ recompute khi dependency liên quan thay đổi.

**Ví dụ:**
Không cần:

```ts
const firstName = ref('An');
const lastName = ref('Nguyen');
const fullName = ref('');

watch([firstName, lastName], () => {
  fullName.value = `${firstName.value} ${lastName.value}`;
});
```

Dùng:

```ts
const fullName = computed(
  () => `${firstName.value} ${lastName.value}`
);
```

**Lưu ý:**
`watch` vẫn đúng khi cần side effect như gọi API, ghi `localStorage` hoặc tương tác external system. Không ép side effect vào `computed` chỉ để tránh `watch`.

## 🧠 Software Design

### Design 1 — Timeout, Retry và Circuit Breaker phải chia sẻ cùng latency budget

**Khái niệm:**
Timeout giới hạn thời gian một attempt; Retry thử lại lỗi transient; Circuit Breaker ngăn tiếp tục gọi dependency đang có dấu hiệu hỏng. Ba cơ chế này chỉ hiệu quả khi được thiết kế như một policy tổng thể thay vì bật độc lập.

**Vấn đề nó giải quyết:**
Một API có SLA 2 giây nhưng outbound call timeout 2 giây và retry 3 lần có thể giữ request 6–8 giây hoặc lâu hơn. Retry đúng về mặt resilience nhưng phá latency budget và làm dependency đang quá tải nhận thêm traffic.

**Ví dụ thực tế:**
Checkout API có 1.5 giây dành cho Pricing service. Thiết kế có thể là:

```text
overall budget: 1500 ms
attempt timeout: 400 ms
max retries: 2
backoff: ngắn + jitter
circuit breaker: mở khi failure rate vượt threshold
```

Nếu budget gần hết, không bắt đầu retry mới.

**Trade-off:**
Retry giúp vượt transient failure, timeout ngăn request treo, circuit breaker giảm load lên dependency lỗi. Chi phí là policy interaction phức tạp, false-open/false-timeout và nguy cơ retry amplification nếu nhiều tầng cùng retry.

**Middle → Senior insight:**
Middle developer cần cấu hình timeout, retry condition và cancellation đúng; không retry mọi lỗi. Senior / Technical developer phải phân bổ end-to-end latency budget, quyết định layer nào được retry, giới hạn amplification và xác định fallback/degraded behavior theo business criticality.

### Design 2 — Event schema evolution phải ưu tiên consumer compatibility

**Khái niệm:**
Trong Event-Driven Architecture, producer và consumer thường deploy độc lập. Event contract vì thế cần tiến hóa theo cách consumer cũ vẫn xử lý được trong giai đoạn chuyển tiếp, thường bằng additive change trước khi removal hoặc semantic change.

**Vấn đề nó giải quyết:**
Nếu producer đổi `amount` từ number thành object hoặc rename field ngay lập tức, consumer chưa deploy có thể deserialize lỗi hoặc hiểu sai dữ liệu. Broker giúp decouple runtime, nhưng contract incompatibility lại tạo coupling theo thời gian.

**Ví dụ thực tế:**
Event cũ:

```json
{
  "orderId": "123",
  "total": 100.0
}
```

Thay vì đổi `total` thành object ngay, producer có thể thêm field mới:

```json
{
  "orderId": "123",
  "total": 100.0,
  "money": { "amount": 100.0, "currency": "USD" }
}
```

Consumer migrate dần sang `money`, sau đó mới deprecate field cũ theo policy rõ ràng.

**Trade-off:**
Additive evolution giảm breaking change và cho phép rollout độc lập, nhưng tạo giai đoạn contract dư thừa và cần governance/version ownership. Version event mới hoàn toàn có thể rõ semantics hơn nhưng buộc producer duy trì nhiều version hoặc migration path.

**Middle → Senior insight:**
Middle developer cần viết serializer/deserializer tolerant với field bổ sung và tránh assumption không cần thiết. Senior / Technical developer phải quyết định compatibility policy, schema registry/versioning strategy, deprecation window và cách xử lý semantic change mà không làm consumer ecosystem bị khóa chặt.

### Design 3 — Shared schema vs database-per-tenant trong multi-tenant systems

**Khái niệm:**
Multi-tenant application có thể dùng chung database/schema với `TenantId`, tách schema, hoặc database riêng cho từng tenant. Lựa chọn là trade-off giữa isolation, operational scale, cost và khả năng tùy biến.

**Vấn đề nó giải quyết:**
Tenant nhỏ hàng nghìn khách hàng cần chi phí thấp và vận hành đơn giản; tenant enterprise lại có thể yêu cầu isolation, backup/restore riêng hoặc data residency. Một storage model duy nhất không luôn phù hợp cho cả hai nhóm.

**Ví dụ thực tế:**
SaaS CRM có 5.000 tenant nhỏ dùng shared PostgreSQL với mọi query bắt buộc filter `TenantId`. Một số khách hàng regulated được đặt vào database riêng để đáp ứng restore, encryption key hoặc residency requirement.

**Trade-off:**
Shared database tối ưu cost, pooling và migration nhưng tăng blast radius và yêu cầu tenant isolation cực kỳ chặt. Database-per-tenant tăng isolation và lifecycle control nhưng làm provisioning, migrations, connection management, monitoring và backup phức tạp hơn đáng kể.

**Middle → Senior insight:**
Middle developer cần đảm bảo mọi data access path enforce tenant scope, test cross-tenant leakage và không tin tenant ID từ client một cách mù quáng. Senior / Technical developer phải đánh giá compliance, noisy-neighbor risk, migration fleet, cost, restore requirement và khả năng dùng hybrid model thay vì chọn một mô hình chỉ vì “sạch” về kiến trúc.
