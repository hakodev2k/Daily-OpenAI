# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test code phụ thuộc thời gian mà không cần `Thread.Sleep`

**Mẹo:**
Trong .NET 8+, nếu business logic phụ thuộc `DateTime.UtcNow`, timeout hoặc thời điểm hết hạn, inject `TimeProvider` thay vì gọi clock hệ thống trực tiếp. Production dùng `TimeProvider.System`; test có thể dùng fake time để điều khiển thời gian một cách deterministic.

**Tại sao hữu ích:**
Code đọc clock trực tiếp thường khó test vì kết quả thay đổi theo thời gian thực. Developer dễ phải chèn `Task.Delay`/`Thread.Sleep`, làm test chậm và flaky. Tách clock thành dependency giúp test expiry, retry window, cache lifetime hoặc scheduled behavior bằng cách advance thời gian chủ động.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

Trong production:
```csharp
builder.Services.AddSingleton(TimeProvider.System);
```

Trong test, dùng fake time provider phù hợp rồi advance clock thay vì chờ thời gian thật trôi qua.

**Lưu ý:**
Đừng biến mọi nơi đọc thời gian thành abstraction riêng nếu framework đã cung cấp `TimeProvider`. Ngoài ra, luôn phân biệt wall-clock time với elapsed time; đo duration nên dựa trên cơ chế monotonic như timestamp của `TimeProvider`, không dựa vào chênh lệch `DateTime.Now` có thể bị ảnh hưởng bởi clock adjustment.

### Tip 2 — `ExecuteUpdateAsync` giúp update hàng loạt trong EF Core nhưng bỏ qua Change Tracker

**Mẹo:**
Khi cần update nhiều row theo một predicate mà không cần load entity vào memory, cân nhắc `ExecuteUpdateAsync` thay vì `ToListAsync` rồi sửa từng entity và `SaveChangesAsync`.

**Tại sao hữu ích:**
Load hàng nghìn entity chỉ để đổi một field tạo thêm database round trip, allocation và Change Tracker overhead. `ExecuteUpdateAsync` dịch thao tác thành một câu `UPDATE` chạy trực tiếp trong database.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.CreatedAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now), ct);
```

Thay vì load toàn bộ orders rồi loop trong application, database thực hiện set-based update.

**Lưu ý:**
`ExecuteUpdateAsync` không đồng bộ các entity cùng loại đang được track trong `DbContext`. Nếu context đã load một `Order`, giá trị trong memory có thể stale sau bulk update. Nó cũng không tự chạy logic domain nằm trong entity method hoặc interceptor theo cùng cách `SaveChanges`. Dùng khi semantics thực sự phù hợp với direct set-based operation.

### Tip 3 — Trong Elasticsearch, phân biệt `text` và `keyword` trước khi debug search “không khớp” hoặc aggregation lỗi

**Mẹo:**
Dùng `text` cho full-text search cần analyzer/tokenization; dùng `keyword` cho exact match, sorting, aggregation hoặc identifier. Với field cần cả hai behavior, dùng multi-field mapping.

**Tại sao hữu ích:**
Một field `text` có thể được analyzer tách và normalize trước khi index, nên query exact theo chuỗi gốc có thể cho kết quả khác mong đợi. Ngược lại, `keyword` giữ toàn bộ giá trị như một term, phù hợp với `status`, `sku`, `tenantId` hoặc facet.

**Ví dụ:**
```json
{
  "properties": {
    "productName": {
      "type": "text",
      "fields": {
        "raw": { "type": "keyword" }
      }
    }
  }
}
```

Full-text search dùng `productName`; sort/aggregation exact dùng `productName.raw`.

**Lưu ý:**
Mapping sai không phải lúc nào sửa được bằng cách đổi query. Thay mapping thường cần index mới + reindex dữ liệu. Đồng thời đừng map mọi string thành cả `text` và `keyword` mặc định nếu không cần, vì mỗi sub-field tăng index size và indexing cost.

### Tip 4 — Kubernetes `readinessProbe` và `livenessProbe` bảo vệ hai failure mode khác nhau

**Mẹo:**
Dùng `readinessProbe` để quyết định Pod có nên nhận traffic hay không; dùng `livenessProbe` để phát hiện process bị kẹt và cần restart. Đừng dùng cùng một deep dependency check cho cả hai probe một cách máy móc.

**Tại sao hữu ích:**
Nếu database tạm thời down và liveness probe cũng fail theo database, Kubernetes có thể restart hàng loạt Pod dù process vẫn khỏe. Điều đó tạo restart storm và làm recovery khó hơn. Readiness có thể rút Pod khỏi traffic trong khi process vẫn tiếp tục sống để dependency hồi phục.

**Ví dụ:**
```text
/readiness
- kiểm tra app đã startup xong
- có thể kiểm tra dependency thiết yếu ở mức phù hợp
- fail => ngừng nhận traffic

/liveness
- kiểm tra process/event loop không bị deadlock
- fail => restart container
```

Với ASP.NET Core, có thể tách health check registrations theo tags và expose endpoint riêng cho readiness/liveness.

**Lưu ý:**
Probe quá nhạy hoặc interval quá ngắn có thể tự tạo outage. Startup chậm nên cân nhắc `startupProbe` hoặc threshold phù hợp. Health endpoint cũng phải nhẹ; đừng khiến mỗi probe thực hiện nhiều query đắt xuống database hoặc third-party service.

### Tip 5 — Khi dùng AI coding agent, khóa task bằng repository evidence thay vì để agent tự suy đoán architecture

**Mẹo:**
Trước khi yêu cầu AI sửa feature hoặc bug, buộc agent đọc các source-of-truth như solution structure, project references, existing tests, configuration và implementation tương tự trong repository. Yêu cầu nó kiểm chứng API/library version bằng code thực tế trước khi sinh patch.

**Tại sao hữu ích:**
Coding agent thường tạo code “hợp lý về mặt tổng quát” nhưng không khớp convention, framework version hoặc architectural boundary của repository. Grounding vào source giúp giảm hallucinated API, duplicate abstraction và thay đổi lan rộng không cần thiết.

**Ví dụ:**
```text
Task: thêm validation cho CreateOrder

Agent phải đọc trước:
- CreateOrder endpoint hiện tại
- validation pattern ở các feature lân cận
- csproj/package versions
- integration tests của Orders

Sau khi sửa:
- build solution
- chạy test liên quan
- kiểm tra diff chỉ chứa file cần thiết
```

**Lưu ý:**
Build/test pass không chứng minh patch đúng business requirement hoặc secure. Developer vẫn phải review assumptions, edge case, migration, authorization, logging và performance. AI nên tăng tốc inspection/implementation chứ không thay thế engineering ownership.

## 🧠 Software Design

### Design 1 — Idempotency Key cho command có side effect mà client có thể gửi lại

**Khái niệm:**
Idempotency Key cho phép server nhận biết hai request cùng đại diện cho một logical command. Server lưu kết quả hoặc trạng thái xử lý theo key để retry từ client không tạo side effect lần thứ hai.

**Vấn đề nó giải quyết:**
Client gửi `POST /payments`, server đã charge thành công nhưng response bị mất vì network timeout. Client không biết kết quả và retry. Nếu endpoint không có cơ chế deduplication, payment có thể bị charge hai lần.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: 8e4f...

Request 1:
- reserve key
- execute payment
- lưu response/result theo key

Request retry cùng key:
- không charge lại
- trả lại outcome tương ứng
```

Key nên gắn với caller/tenant và request semantics, có retention window rõ ràng.

**Trade-off:**
Idempotency giúp retry an toàn hơn nhưng cần persistence, concurrency control, expiry và rule xử lý khi cùng key được gửi với payload khác. Lưu mọi response vô thời hạn cũng tăng storage. Với operation vốn đã idempotent tự nhiên như `PUT` đặt resource về một state xác định, cơ chế riêng có thể không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu retry network có thể xảy ra sau khi side effect đã commit và phải test duplicate request. Senior / Technical developer phải thiết kế atomicity giữa key và business transaction, retention, payload fingerprint, concurrent duplicate handling và failure recovery thay vì chỉ thêm một header rồi coi endpoint là idempotent.

### Design 2 — Feature Flag tách deployment khỏi release nhưng phải có lifecycle quản trị

**Khái niệm:**
Feature Flag cho phép code mới được deploy lên production nhưng chỉ bật cho một nhóm user, tenant hoặc tỷ lệ traffic nhất định. Nó tách thời điểm đưa code lên môi trường khỏi thời điểm business capability được expose.

**Vấn đề nó giải quyết:**
Một feature lớn cần rollout dần để giảm rủi ro hoặc cần backend/frontend deploy khác thời điểm. Nếu mọi deploy đồng nghĩa release ngay, team buộc phải coordinate chặt hoặc giữ branch lâu, làm tăng merge risk.

**Ví dụ thực tế:**
```text
NewCheckout flag
- internal users: ON
- tenant beta: ON
- 10% traffic: ON
- phần còn lại: OFF
```

Khi metric ổn định, rollout tăng dần; khi có regression, disable flag nhanh hơn rollback toàn deployment.

**Trade-off:**
Feature Flag tăng rollout control nhưng tạo nhiều execution path và test matrix. Flag cũ không được xóa sẽ trở thành technical debt, khiến code khó hiểu và có thể tạo configuration drift giữa environment. Flag cũng không thay thế database backward compatibility nếu schema đã thay đổi không thể rollback.

**Middle → Senior insight:**
Middle developer cần giữ behavior ở cả trạng thái ON/OFF có test phù hợp và tránh rải condition khắp codebase. Senior / Technical developer phải định nghĩa owner, expiry/removal date, rollout metric, kill-switch semantics và cách flag tương tác với migration/deployment strategy.

### Design 3 — Elasticsearch nên là read projection khi source of truth nằm ở transactional database

**Khái niệm:**
Trong hệ thống cần full-text search, Elasticsearch thường phù hợp hơn khi đóng vai trò search/read projection được xây từ nguồn dữ liệu authoritative như SQL hoặc domain events, thay vì trở thành nơi duy nhất giữ state transactional.

**Vấn đề nó giải quyết:**
Search engine tối ưu cho indexing và query văn bản, nhưng application vẫn cần transaction, constraint và consistency semantics của primary database. Nếu hai hệ thống cùng được update theo kiểu “best effort” từ request path, dữ liệu search dễ lệch mà không có cách rebuild đáng tin cậy.

**Ví dụ thực tế:**
```text
SQL Server
- source of truth cho Product
- transaction commit

Event/Outbox/Change feed
- phát thay đổi

Indexer
- transform thành SearchProductDocument
- upsert vào Elasticsearch

Rebuild:
- tạo index version mới
- backfill từ source of truth
- đổi alias khi hoàn tất
```

Search có thể chấp nhận eventual consistency trong vài giây nếu business requirement cho phép.

**Trade-off:**
Projection model cho phép search schema tối ưu độc lập và hỗ trợ rebuild, nhưng thêm pipeline đồng bộ, lag, duplicate processing và operational monitoring. Với dataset nhỏ và search đơn giản, SQL full-text hoặc query relational có thể ít complexity hơn việc vận hành Elasticsearch cluster.

**Middle → Senior insight:**
Middle developer cần hiểu search document không phải domain entity và consumer/indexer phải chịu duplicate update. Senior / Solution-oriented engineer phải quyết định source of truth, consistency SLA, replay/reindex strategy, alias cutover, failure recovery và chi phí vận hành trước khi thêm search infrastructure.
