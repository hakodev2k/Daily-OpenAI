# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi LOH allocation khi object lớn làm GC pause tăng bất thường

**Mẹo:**
Khi process .NET có memory tăng và latency xuất hiện theo từng đợt, kiểm tra Large Object Heap (LOH) thay vì chỉ nhìn tổng managed heap. Object lớn như byte array, JSON buffer hoặc image buffer có thể tạo áp lực GC đáng kể nếu được allocate liên tục.

**Tại sao hữu ích:**
Object lớn thường được quản lý khác với object nhỏ và việc allocate/reclaim chúng có thể làm fragmentation hoặc tăng thời gian GC. Một API xử lý file có thể vẫn “không leak” nhưng tạo allocation rate quá cao, khiến throughput giảm khi load tăng.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Kết hợp với profiler để kiểm tra allocation source, Gen 2 collections và LOH size. Nếu endpoint liên tục tạo `byte[]` lớn, cân nhắc streaming hoặc reuse buffer thay vì load toàn bộ payload vào memory.

**Lưu ý:**
Đừng tối ưu chỉ vì thấy LOH có dữ liệu. Vấn đề cần được xác nhận bằng allocation rate, GC pause và latency thực tế. Pooling buffer cũng có chi phí và có thể giữ memory lâu hơn nếu dùng không đúng.

### Tip 2 — Trong ASP.NET Core, áp dụng request size limit trước khi đọc toàn bộ file upload

**Mẹo:**
Với endpoint upload file, giới hạn kích thước request ở middleware/server layer và validate content trước khi buffer toàn bộ file vào memory.

**Tại sao hữu ích:**
Nếu application nhận file rất lớn rồi mới kiểm tra size trong business logic, request đã tiêu tốn network, memory hoặc temporary storage. Giới hạn sớm giảm blast radius của accidental upload và abuse.

**Ví dụ:**
```csharp
[RequestSizeLimit(20 * 1024 * 1024)]
public async Task<IActionResult> Upload(IFormFile file, CancellationToken ct)
{
    if (file.Length == 0)
        return BadRequest();

    await using var stream = file.OpenReadStream();
    await storage.SaveAsync(stream, ct);
    return Ok();
}
```

Ở workload lớn hơn, có thể stream trực tiếp tới Blob Storage thay vì giữ toàn bộ file trong application memory.

**Lưu ý:**
Size limit không thay thế malware scanning, MIME/content validation hoặc authorization. Đừng tin filename hay `Content-Type` do client gửi như nguồn sự thật tuyệt đối.

### Tip 3 — Với Elasticsearch, dùng `filter` cho điều kiện không cần relevance score

**Mẹo:**
Nếu điều kiện chỉ mang tính đúng/sai như tenant, status, category hoặc date range, đặt nó trong filter context thay vì query scoring context khi relevance không cần thiết.

**Tại sao hữu ích:**
Full-text query cần tính `_score`, trong khi filter chỉ quyết định document có match hay không. Tách hai concern giúp query rõ hơn và thường hiệu quả hơn cho các điều kiện cấu trúc.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless keyboard" } }
      ],
      "filter": [
        { "term": { "status": "published" } },
        { "range": { "price": { "lte": 100 } } }
      ]
    }
  }
}
```

`title` ảnh hưởng relevance; `status` và `price` chỉ giới hạn tập kết quả.

**Lưu ý:**
Không phải mọi field đều phù hợp cho `term` query. Với analyzed text field, cần hiểu mapping và thường dùng `keyword` subfield cho exact match.

### Tip 4 — Trong integration test, dùng database thật cho behavior phụ thuộc transaction và SQL translation

**Mẹo:**
Nếu test cần xác nhận query EF Core, transaction, constraint hoặc concurrency behavior, ưu tiên database provider gần production thay vì mock `DbSet` hoặc chỉ dùng in-memory collection.

**Tại sao hữu ích:**
LINQ chạy trên `IEnumerable` có thể pass nhưng EF Core provider lại không translate được. Constraint, isolation, collation và transaction semantics cũng không thể được kiểm chứng bằng mock đơn giản.

**Ví dụ:**
```text
Test cần xác nhận:
- unique constraint
- query translation
- transaction rollback
- optimistic concurrency

=> dùng SQL Server/PostgreSQL test container hoặc test database phù hợp
```

**Lưu ý:**
Không cần biến mọi unit test thành integration test. Domain logic thuần vẫn nên test nhanh và isolated; database test chỉ dùng cho behavior thực sự phụ thuộc data-access engine.

### Tip 5 — Khi review code AI-generated, tìm “silent assumption” trước khi tìm syntax bug

**Mẹo:**
Sau khi AI sinh patch, kiểm tra các assumption ẩn như transaction boundary, authorization scope, nullability, concurrency, package version và failure behavior trước khi chỉ chạy build.

**Tại sao hữu ích:**
Code generated có thể compile hoàn hảo nhưng sai vì agent giả định repository dùng một pattern, framework version hoặc invariant không tồn tại. Những lỗi này thường nguy hiểm hơn syntax error vì dễ lọt qua review sơ sài.

**Ví dụ:**
```text
Patch thêm retry cho POST payment API

Cần kiểm tra:
- endpoint có idempotency key không?
- retry có thể charge hai lần không?
- timeout hiện tại là bao nhiêu?
- SDK có built-in retry không?
- test failure path đã tồn tại chưa?
```

**Lưu ý:**
Không mặc định reject code do AI sinh. Mục tiêu là áp dụng cùng quality gate như code con người viết, nhưng tăng mức kiểm tra ở nơi agent có thể hallucinate context hoặc API.

## 🧠 Software Design

### Design 1 — Synchronous API call vs asynchronous messaging theo latency và consistency requirement

**Khái niệm:**
Synchronous communication phù hợp khi caller cần kết quả ngay để tiếp tục flow; asynchronous messaging phù hợp khi công việc có thể tách khỏi request lifecycle và chấp nhận eventual consistency.

**Vấn đề nó giải quyết:**
Nếu mọi service gọi nhau đồng bộ theo chuỗi, latency và failure propagate qua toàn call graph. Nhưng chuyển mọi thứ sang queue lại làm workflow khó quan sát và buộc business xử lý trạng thái trung gian.

**Ví dụ thực tế:**
```text
Checkout cần xác nhận giá hiện tại
-> synchronous call có thể phù hợp

Gửi email sau khi order hoàn tất
-> publish event / queue thường phù hợp hơn
```

Nếu Email service down, order không nhất thiết phải fail chỉ vì notification chưa gửi.

**Trade-off:**
Synchronous flow đơn giản về mental model và cho response tức thì, nhưng coupling runtime cao. Messaging tăng resilience và decoupling nhưng thêm retry, duplicate delivery, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần biết không nên dùng queue chỉ để “trông giống Microservices”. Senior / Technical developer phải phân loại interaction theo business dependency, latency budget, consistency requirement, failure isolation và recovery model trước khi chọn protocol.

### Design 2 — Normalize dữ liệu để bảo vệ invariant, denormalize có chủ đích để tối ưu read path

**Khái niệm:**
Normalization giảm duplication và giúp giữ một nguồn dữ liệu canonical; denormalization sao chép hoặc precompute dữ liệu để read nhanh hơn khi access pattern yêu cầu.

**Vấn đề nó giải quyết:**
Một schema quá normalized có thể khiến read-heavy endpoint cần nhiều join hoặc aggregate đắt tiền. Ngược lại, duplicate dữ liệu ở quá nhiều nơi làm update phức tạp và dễ inconsistency.

**Ví dụ thực tế:**
```text
Canonical:
Customer(Id, Name)
Order(CustomerId, ...)

Read model:
OrderSummary giữ thêm CustomerDisplayName snapshot
```

Nếu business muốn order lịch sử giữ tên tại thời điểm mua, snapshot còn là requirement chứ không chỉ optimization.

**Trade-off:**
Normalization đơn giản hóa update consistency nhưng có thể tăng read cost. Denormalization giảm latency/read complexity nhưng thêm synchronization, storage và failure mode khi dữ liệu sao chép không được cập nhật đúng.

**Middle → Senior insight:**
Middle developer cần tránh duplicate data vô lý và hiểu foreign key/constraint. Senior / Technical developer phải phân biệt snapshot nghiệp vụ, materialized read model và accidental duplication; quyết định dựa trên access pattern, invariant và update frequency.

### Design 3 — Feature Flag không phải chỉ là `if` statement; cần lifecycle và ownership rõ ràng

**Khái niệm:**
Feature Flag tách thời điểm deploy code khỏi thời điểm enable behavior. Nó hữu ích cho staged rollout, rollback nhanh và experiment, nhưng chỉ khi flag có owner, scope và kế hoạch remove.

**Vấn đề nó giải quyết:**
Không có flag, release một capability rủi ro có thể yêu cầu redeploy để rollback. Với flag, team có thể deploy code dormant rồi enable cho subset user hoặc environment.

**Ví dụ thực tế:**
```text
new-checkout-flow
- dev: 100%
- staging: 100%
- production: 5% users
- rollback: disable flag ngay nếu error rate tăng
```

Telemetry nên phân biệt request chạy path cũ và path mới để điều tra regression.

**Trade-off:**
Feature Flag giảm deployment risk nhưng tạo branch logic, test matrix và technical debt. Flag sống quá lâu có thể biến code thành nhiều execution path khó hiểu.

**Middle → Senior insight:**
Middle developer cần implement flag mà không phá invariant và test cả hai path. Senior / Technical developer phải định nghĩa rollout criteria, observability, kill switch, ownership và removal date; không để temporary flag trở thành permanent architecture.
