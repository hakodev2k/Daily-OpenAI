# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Stream HTTP response lớn bằng `ResponseHeadersRead` thay vì buffer toàn bộ body

**Mẹo:**
Khi ASP.NET Core service tải file lớn, export, media hoặc response JSON rất lớn từ downstream API, dùng `HttpCompletionOption.ResponseHeadersRead` và xử lý response stream thay vì để `HttpClient` đọc toàn bộ body vào memory trước khi trả control về caller.

**Tại sao hữu ích:**
Mặc định, `HttpClient` thường hoàn tất request sau khi response content đã được buffer. Với payload lớn, nhiều request concurrent có thể làm memory tăng mạnh, tạo allocation lớn và tăng GC pressure. `ResponseHeadersRead` cho phép application bắt đầu xử lý ngay khi headers tới và áp backpressure tự nhiên hơn qua stream.

**Ví dụ:**
```csharp
using var request = new HttpRequestMessage(HttpMethod.Get, url);
using var response = await httpClient.SendAsync(
    request,
    HttpCompletionOption.ResponseHeadersRead,
    ct);

response.EnsureSuccessStatusCode();

await using var source = await response.Content.ReadAsStreamAsync(ct);
await source.CopyToAsync(destination, ct);
```

Nếu endpoint ASP.NET Core chỉ proxy file, có thể stream trực tiếp tới response thay vì tạo `byte[]` trung gian.

**Lưu ý:**
Khi dùng streaming, connection có thể bị giữ lâu hơn nên phải dispose `HttpResponseMessage`/stream đúng cách và propagate `CancellationToken`. Với JSON nhỏ, buffering mặc định thường đơn giản và hoàn toàn hợp lý; đừng thêm streaming complexity nếu profiling không cho thấy nhu cầu.

### Tip 2 — Dùng filtered index khi chỉ một tập nhỏ row thực sự nằm trên hot query path

**Mẹo:**
Với SQL Server, nếu query production thường chỉ truy cập một subset nhỏ và ổn định như `Status = 'Pending'` hoặc `DeletedAt IS NULL`, cân nhắc filtered index thay vì index toàn bộ table.

**Tại sao hữu ích:**
Index nhỏ hơn thường cần ít storage, ít page hơn để đọc và ít maintenance hơn khi phần lớn row không thuộc filter. Điều này đặc biệt hữu ích với bảng lịch sử lớn nhưng workload operational chỉ quan tâm tập active/pending nhỏ.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON dbo.Orders (CreatedAt, Id)
INCLUDE (CustomerId, Total)
WHERE Status = 'Pending';
```

Query tương ứng:
```sql
SELECT TOP (100) Id, CustomerId, Total, CreatedAt
FROM dbo.Orders
WHERE Status = 'Pending'
ORDER BY CreatedAt, Id;
```

Hãy kiểm tra actual execution plan, logical reads và write overhead trước/sau khi thêm index.

**Lưu ý:**
Filtered index không phải lựa chọn tốt nếu predicate thay đổi liên tục hoặc application parameterization khiến optimizer khó chứng minh query phù hợp với filter. Over-indexing vẫn làm `INSERT`/`UPDATE` đắt hơn; index phải xuất phát từ workload thật.

### Tip 3 — Upload file lớn trực tiếp tới Azure Blob bằng SAS thay vì luôn proxy qua backend

**Mẹo:**
Với browser/mobile client upload file lớn, cân nhắc để backend cấp SAS ngắn hạn với quyền tối thiểu, sau đó client upload trực tiếp tới Azure Blob Storage thay vì gửi toàn bộ file qua ASP.NET Core server.

**Tại sao hữu ích:**
Proxy file qua backend làm application instance chịu toàn bộ bandwidth, connection duration và memory/buffer pressure dù business logic chỉ cần cấp quyền upload. Direct upload giảm tải backend và scale tốt hơn với media/file workload.

**Ví dụ:**
```text
1. Client -> API: POST /uploads/request
2. API kiểm tra authorization, file policy, quota
3. API -> Client: blob URI + SAS hết hạn sau vài phút
4. Client -> Azure Blob: PUT file trực tiếp
5. Client/API xác nhận upload hoàn tất
6. Backend xử lý metadata/virus scan/workflow tiếp theo
```

SAS nên giới hạn container/blob cụ thể, operation cần thiết và expiration ngắn.

**Lưu ý:**
Direct upload không có nghĩa client được tin cậy. Backend vẫn phải validate metadata, ownership, expected size/type và trạng thái blob sau upload. Với dữ liệu nhạy cảm, cân nhắc User Delegation SAS/Managed Identity và workflow quarantine/scan trước khi file được sử dụng.

### Tip 4 — Trong Vue, dùng `computed` cho derived state và `watch` cho side effect

**Mẹo:**
Nếu một giá trị chỉ được suy ra từ reactive state khác, ưu tiên `computed`. Dùng `watch` khi thay đổi state cần kích hoạt side effect như gọi API, ghi storage hoặc tương tác với imperative library.

**Tại sao hữu ích:**
Dùng `watch` để đồng bộ một state dẫn xuất sang state khác tạo hai source of truth và dễ sinh trạng thái lệch nhau. `computed` khai báo dependency trực tiếp, được cache theo reactive dependency và dễ reasoning hơn.

**Ví dụ:**
```ts
const firstName = ref('Ha')
const lastName = ref('Dinh')

const fullName = computed(() => `${firstName.value} ${lastName.value}`)
```

Thay vì:
```ts
const fullName = ref('')
watch([firstName, lastName], () => {
  fullName.value = `${firstName.value} ${lastName.value}`
})
```

`watch` phù hợp hơn khi cần debounce search request hoặc đồng bộ ra hệ thống bên ngoài component state.

**Lưu ý:**
Async `watch` cần xử lý stale request/cancellation nếu dependency thay đổi nhanh. Đừng biến `watch` thành nơi chứa business workflow dài; khi side effect phức tạp, tách nó sang composable/service rõ ràng.

### Tip 5 — Kiểm soát metric cardinality trước khi thêm label/tag mới

**Mẹo:**
Khi instrument metric trong Application Insights/OpenTelemetry/Prometheus-style systems, chỉ dùng dimension có tập giá trị hữu hạn và tương đối nhỏ như `endpoint`, `status_code`, `region`; tránh `user_id`, `request_id`, raw URL hoặc exception message làm metric label.

**Tại sao hữu ích:**
Mỗi combination của label values tạo một time series riêng. Một metric tưởng đơn giản có thể bùng nổ thành hàng trăm nghìn series, tăng storage/cost, làm query dashboard chậm và gây áp lực lên telemetry backend.

**Ví dụ:**
```text
Tốt cho metric:
http_server_duration{route="/orders/{id}", status_code="200"}

Rủi ro cao:
http_server_duration{url="/orders/8f2a...", user_id="123456", trace_id="..."}
```

High-cardinality context phù hợp hơn với logs/traces, nơi bạn có thể drill down từ metric anomaly sang request cụ thể.

**Lưu ý:**
Đừng loại bỏ mọi dimension để tiết kiệm cost rồi mất khả năng phân tích. Thiết kế telemetry theo câu hỏi vận hành cần trả lời và đặt cardinality budget rõ ràng cho từng signal.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation để một dependency lỗi không chiếm hết capacity của application

**Khái niệm:**
Bulkhead Isolation chia resource/concurrency budget theo dependency hoặc workload class để failure hoặc latency spike ở một khu vực không làm cạn toàn bộ thread, connection hoặc request capacity của hệ thống.

**Vấn đề nó giải quyết:**
Giả sử API gọi cả Payment provider và Recommendation provider. Nếu Recommendation bắt đầu timeout và hàng trăm request cùng chờ nó, toàn bộ outbound connection/concurrency budget có thể bị chiếm, khiến Payment cũng chậm dù Payment vẫn khỏe.

**Ví dụ thực tế:**
```text
Order API
├─ Payment dependency
│  └─ concurrency budget: 40
└─ Recommendation dependency
   └─ concurrency budget: 10

Recommendation treo
-> chỉ budget 10 bị saturated
-> request có thể bỏ recommendation/degrade
-> Payment path vẫn còn capacity
```

Bulkhead thường đi cùng timeout, circuit breaker, queue limit và fallback/degradation policy.

**Trade-off:**
Isolation giảm blast radius nhưng chia nhỏ capacity có thể làm một pool idle trong khi pool khác quá tải. Quá nhiều bulkhead cũng tăng tuning và operational complexity. Boundary nên phản ánh criticality và failure independence thực tế.

**Middle → Senior insight:**
Middle developer cần biết timeout/retry không đủ để bảo vệ resource. Senior / Technical developer phải phân bổ concurrency budget theo SLO, dependency capacity và business priority, đồng thời thiết kế degraded mode khi một bulkhead đầy.

### Design 2 — Aggregate boundary trong DDD nên bám invariant và transaction boundary

**Khái niệm:**
Aggregate là consistency boundary: một nhóm entity/value object được thay đổi cùng nhau để giữ invariant trong một transaction. Không nên tạo aggregate chỉ vì các table có foreign key hoặc vì object graph trông “thuộc về nhau”.

**Vấn đề nó giải quyết:**
Aggregate quá lớn buộc nhiều workflow phải load/update một graph lớn, tăng contention và làm transaction nặng. Aggregate quá nhỏ có thể khiến invariant cần strong consistency bị chia ra nhiều transaction và trở thành race condition.

**Ví dụ thực tế:**
```text
Order aggregate có thể giữ invariant:
- OrderLine thuộc Order
- Total phải khớp các line
- Cancelled order không nhận thêm line

Nhưng Shipment có lifecycle riêng, cập nhật bởi logistics service
=> không nhất thiết nằm trong cùng aggregate chỉ vì Shipment tham chiếu OrderId
```

Cross-aggregate rule thường cần application workflow, domain event hoặc eventual consistency thay vì một transaction khổng lồ.

**Trade-off:**
Aggregate lớn đơn giản hóa invariant cục bộ nhưng tăng lock/contention và coupling. Aggregate nhỏ tăng autonomy/throughput nhưng đòi hỏi xử lý eventual consistency và compensation rõ hơn.

**Middle → Senior insight:**
Middle developer cần tránh mapping database relationship trực tiếp thành domain aggregate. Senior / Technical developer phải xác định invariant nào thực sự cần atomicity, ai sở hữu state và conflict rate ra sao trước khi chốt boundary.

### Design 3 — Expand-and-Contract cho database migration không downtime

**Khái niệm:**
Expand-and-Contract thay đổi schema qua nhiều bước backward-compatible: đầu tiên mở rộng schema để cả code cũ và mới cùng chạy, sau đó migrate traffic/data, cuối cùng mới xóa cấu trúc cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment hoặc nhiều application instance, không thể giả định toàn bộ code đổi version cùng một thời điểm. Rename/drop column trực tiếp có thể làm instance cũ đang chạy lỗi ngay giữa deployment.

**Ví dụ thực tế:**
```text
Mục tiêu: rename Customer.Name -> DisplayName

Phase 1 — Expand
- thêm DisplayName nullable
- code mới đọc fallback DisplayName ?? Name
- write cả hai field nếu cần

Phase 2 — Migrate
- backfill DisplayName
- deploy toàn bộ consumer sang field mới
- verify telemetry

Phase 3 — Contract
- ngừng dual-write
- drop Name ở release sau
```

Cùng nguyên tắc áp dụng cho table split, type change hoặc thay đổi event/API contract liên quan dữ liệu.

**Trade-off:**
Expand-and-Contract tăng số deployment và tạo giai đoạn schema/code tạm thời phức tạp hơn, nhưng đổi lại rollback an toàn hơn và giảm blast radius. Với maintenance window thật sự chấp nhận downtime, quy trình đơn giản hơn có thể hợp lý.

**Middle → Senior insight:**
Middle developer cần viết migration tương thích với version code đang coexist. Senior / Technical developer phải thiết kế deployment order, backfill strategy, rollback point, observability và cleanup để trạng thái transitional không tồn tại vô thời hạn.
