# Daily Developer Tips & Design — 2026-09-18

## 🛠 Developer Tips & Tricks

### Tip 1 — `CancellationToken` phải đi xuyên suốt call chain

**Mẹo:**
Trong ASP.NET Core, nhận `CancellationToken` từ request và truyền nó xuống EF Core, `HttpClient`, service layer và các operation hỗ trợ cancellation thay vì tạo token mới hoặc bỏ qua token ở giữa.

**Tại sao hữu ích:**
Khi client hủy request hoặc request hết ý nghĩa, công việc phía server có thể dừng sớm. Nếu một layer làm mất token, SQL query hoặc outbound HTTP call vẫn tiếp tục tiêu tốn connection, CPU và downstream capacity dù response không còn người nhận.

**Ví dụ:**
```csharp
app.MapGet("/orders/{id}", async (
    int id,
    AppDbContext db,
    CancellationToken cancellationToken) =>
{
    return await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);
});
```

**Lưu ý:**
Cancellation không phải rollback tự động cho mọi side effect. Sau khi payment đã được gửi hoặc transaction đã commit, hủy token không thể làm lịch sử biến mất; boundary của operation vẫn phải được thiết kế rõ.

### Tip 2 — SQL covering index phải xuất phát từ access pattern

**Mẹo:**
Khi query thường xuyên seek theo một số cột nhưng chỉ đọc thêm vài cột khác, cân nhắc covering index với key columns và included columns thay vì tạo index chứa mọi field.

**Tại sao hữu ích:**
Nếu index chứa đủ dữ liệu query cần, database có thể tránh lookup về base table/clustered index cho nhiều row. Điều này đặc biệt đáng kể với endpoint đọc nhiều nhưng trả payload nhỏ.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Status_CreatedAt
ON Orders(Status, CreatedAt DESC)
INCLUDE (CustomerId, TotalAmount);
```
Một query lọc `Status`, sort `CreatedAt` và chỉ trả `CustomerId`, `TotalAmount` có thể được phục vụ hiệu quả hơn.

**Lưu ý:**
Included columns vẫn làm index lớn hơn và tăng write/storage cost. Đừng tạo covering index cho từng query riêng lẻ; kiểm tra execution plan, frequency và write workload trước.

### Tip 3 — Phân biệt connection pool exhaustion với database chậm

**Mẹo:**
Khi API bắt đầu timeout ở data-access layer, kiểm tra thời gian chờ lấy connection và pool metrics trước khi kết luận SQL query chậm.

**Tại sao hữu ích:**
Một connection bị giữ quá lâu, transaction không kết thúc hoặc concurrency tăng đột biến có thể làm pool cạn. Request sau đó chờ connection ngay cả khi database xử lý từng query khá nhanh.

**Ví dụ:**
Triệu chứng: p99 tăng, SQL server CPU bình thường, query duration thấp nhưng application timeout tăng. Kiểm tra active connections, request concurrency, transaction duration và code path giữ `DbContext`/connection quá lâu để tìm nguyên nhân.

**Lưu ý:**
Tăng `Max Pool Size` chỉ tăng ngưỡng trước khi lỗi xuất hiện và có thể đẩy áp lực xuống database. Sửa leak/long transaction hoặc giới hạn concurrency thường quan trọng hơn.

### Tip 4 — CMS cache key phải phản ánh đúng content variation

**Mẹo:**
Trong CMS/e-commerce, cache rendered fragment hoặc API response theo các dimension thực sự ảnh hưởng output như locale, site, currency hoặc personalization segment; không dùng một key toàn cục cho nội dung biến thiên.

**Tại sao hữu ích:**
Cache hit cao nhưng key thiếu variation có thể trả đúng dữ liệu kỹ thuật nhưng sai ngữ cảnh người dùng, ví dụ tiếng Anh cho site Việt Nam hoặc giá của market khác.

**Ví dụ:**
```text
content:{contentId}:lang:{language}:market:{market}:v:{contentVersion}
```
Thiết kế invalidation theo publish/version thay vì chỉ dựa vào TTL dài.

**Lưu ý:**
Thêm mọi thuộc tính user vào key sẽ làm cardinality bùng nổ và cache gần như vô dụng. Chỉ vary theo dimension có ảnh hưởng thực sự đến representation.

### Tip 5 — Mutation testing tìm test suite “xanh nhưng yếu”

**Mẹo:**
Dùng mutation testing có chọn lọc cho business logic quan trọng để kiểm tra test có thực sự phát hiện hành vi sai hay chỉ chạy qua code.

**Tại sao hữu ích:**
Coverage 90% vẫn có thể bỏ sót assertion quan trọng. Nếu tool đổi `>` thành `>=` hoặc đảo boolean mà test vẫn pass, test suite chưa bảo vệ behavior đó.

**Ví dụ:**
Rule giảm giá: `total >= 1_000_000`. Một mutant đổi thành `total > 1_000_000`; nếu không có boundary test tại đúng 1.000.000, mutant sống sót và chỉ ra khoảng trống cụ thể.

**Lưu ý:**
Mutation testing tốn thời gian và có thể sinh equivalent mutants. Không cần chạy toàn solution ở mọi commit; ưu tiên domain/risk-critical modules hoặc chạy theo pipeline phù hợp.

## 🧠 Software Design

### Design 1 — Optimistic vs Pessimistic Concurrency

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor làm việc song song rồi phát hiện conflict lúc ghi; pessimistic concurrency giữ lock sớm để ngăn actor khác thay đổi cùng resource.

**Vấn đề nó giải quyết:**
Hai request cùng chỉnh một entity có thể tạo lost update hoặc vi phạm business invariant nếu hệ thống giả định chỉ có một writer.

**Ví dụ thực tế:**
Một back-office CMS có editor cùng sửa metadata. Row version/ETag cho phép request thứ hai nhận conflict và reload thay vì âm thầm ghi đè. Với một critical database operation rất ngắn và contention cao, lock có chủ đích đôi khi phù hợp hơn retry liên tục.

**Trade-off:**
Optimistic concurrency giữ throughput tốt khi conflict hiếm nhưng yêu cầu conflict handling/retry UX. Pessimistic locking đơn giản hóa một số invariant nhưng tăng blocking, deadlock risk và giảm concurrency nếu lock giữ lâu.

**Middle → Senior insight:**
Middle developer cần biết phát hiện và xử lý concurrency conflict đúng. Senior / Technical developer phải đánh giá contention rate, transaction duration, user experience và invariant để chọn chiến lược thay vì mặc định một kiểu locking.

### Design 2 — Layered Architecture vs Clean Architecture theo độ phức tạp thật

**Khái niệm:**
Layered Architecture tổ chức application theo các tầng quen thuộc; Clean Architecture nhấn mạnh dependency direction và bảo vệ domain/use cases khỏi infrastructure. Cả hai chỉ có giá trị khi boundary phản ánh nhu cầu thay đổi thực tế.

**Vấn đề nó giải quyết:**
Application tăng kích thước có thể bị business logic rải vào controller, EF queries và integration code, khiến test/refactor khó. Tuy nhiên thêm nhiều projects/interfaces cho CRUD đơn giản cũng tạo ceremony mà không giảm coupling có ý nghĩa.

**Ví dụ thực tế:**
Một internal CRUD service nhỏ có thể dùng API → Application → Data đơn giản. Một pricing engine với business rules độc lập, nhiều adapters và long-lived domain có thể hưởng lợi từ dependency inversion rõ hơn.

**Trade-off:**
Clean boundaries tăng testability và khả năng thay adapter nhưng thêm mapping, abstractions và learning cost. Layered design đơn giản hơn nhưng dễ trở thành dependency chain cứng nếu discipline yếu.

**Middle → Senior insight:**
Middle developer cần giữ business logic khỏi controller/infrastructure khi hợp lý. Senior / Technical developer phải chọn mức abstraction tương xứng với volatility, domain complexity, team size và expected lifetime, không dựa trên architecture diagram đẹp.

### Design 3 — Retry Budget thay vì retry ở mọi layer

**Khái niệm:**
Retry là resilience mechanism nhưng mỗi retry làm tăng tổng số request và latency. Retry budget giới hạn số lần thử lại ở cấp hệ thống thay vì để HTTP client, service, queue consumer và caller đều retry độc lập.

**Vấn đề nó giải quyết:**
Một dependency đang quá tải có thể nhận traffic lớn hơn nhiều lần nếu mỗi layer retry ba lần. “Resilience” cục bộ lúc đó biến thành retry storm toàn hệ thống.

**Ví dụ thực tế:**
Mobile backend gọi Payment Adapter, adapter gọi provider. Nếu cả gateway và adapter đều retry 3 lần, một request business có thể tạo nhiều provider calls. Chọn một layer sở hữu retry, dùng exponential backoff/jitter và chỉ retry failure được xác định là transient.

**Trade-off:**
Retry cải thiện success rate với transient fault nhưng tăng latency, load và nguy cơ duplicate side effect. Giới hạn retry có thể làm một số request fail sớm hơn nhưng bảo vệ system capacity trong incident.

**Middle → Senior insight:**
Middle developer cần biết exception/status nào retry được và đảm bảo operation idempotent khi cần. Senior / Technical developer phải thiết kế timeout/retry budget xuyên dependency chain, cân bằng success probability với load amplification và recovery behavior.
