# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `ValueTask` như lựa chọn mặc định

**Mẹo:**
Chỉ cân nhắc `ValueTask` khi hot path thường hoàn thành synchronously và profiling cho thấy allocation của `Task` thực sự đáng kể. Với phần lớn application code, `Task` đơn giản và an toàn hơn.

**Tại sao hữu ích:**
`ValueTask` có thể tránh allocation trong một số trường hợp, nhưng đổi lại có semantics phức tạp hơn: không nên await nhiều lần, không nên cache tùy tiện và một số consumer API sẽ phải chuyển lại thành `Task`. Micro-optimization sai chỗ có thể tăng complexity mà không cải thiện latency thực tế.

**Ví dụ:**
```csharp
public ValueTask<User?> FindCachedAsync(int id)
{
    if (_cache.TryGetValue(id, out var user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

Trường hợp này chỉ hợp lý nếu cache hit rất cao và method nằm trên hot path đã được đo.

**Lưu ý:**
Không đổi hàng loạt `Task` sang `ValueTask` chỉ để “giảm allocation”. Benchmark và profiler phải chứng minh lợi ích đủ lớn so với chi phí maintainability.

### Tip 2 — Dùng `ExecuteUpdateAsync` cho bulk update không cần hydrate entity

**Mẹo:**
Trong EF Core, khi cần update nhiều row theo một predicate mà không cần chạy domain logic trên từng entity, ưu tiên set-based update như `ExecuteUpdateAsync` thay vì load hàng nghìn entity vào memory rồi sửa từng object.

**Tại sao hữu ích:**
Load entity tạo round trip đọc dữ liệu, allocation, change tracking và sau đó nhiều update operation. Set-based update để database xử lý trực tiếp, thường giảm network, memory và thời gian transaction đáng kể.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired), cancellationToken);
```

**Lưu ý:**
`ExecuteUpdateAsync` bỏ qua change tracker và không chạy logic nằm trong entity setter/domain method. Không dùng nó nếu mỗi row cần invariant, event hoặc business side effect riêng.

### Tip 3 — So sánh estimated rows với actual rows khi đọc execution plan

**Mẹo:**
Khi query đột nhiên chậm, đừng chỉ nhìn operator cost. Kiểm tra chênh lệch giữa estimated rows và actual rows để phát hiện statistics sai, data skew hoặc predicate mà optimizer ước lượng kém.

**Tại sao hữu ích:**
Optimizer chọn join type, memory grant và access path dựa trên cardinality estimate. Nếu estimate 100 row nhưng thực tế 2 triệu row, một plan hợp lý trên giấy có thể trở thành bottleneck lớn ở production.

**Ví dụ:**
Một nested loop được chọn vì estimate chỉ 50 rows, nhưng actual execution trả 800.000 rows. Evidence tiếp theo nên gồm statistics freshness, histogram, parameter distribution và predicate selectivity trước khi quyết định thêm index.

**Lưu ý:**
Không update statistics hoặc rebuild index một cách máy móc mỗi khi query chậm. Hãy xác định estimate sai do statistics, parameter sensitivity, data skew hay query shape trước.

### Tip 4 — Phân biệt CPU throttling với application chậm trong Kubernetes

**Mẹo:**
Khi latency tăng nhưng CPU usage nhìn vẫn “không cao”, kiểm tra CPU limits và throttling. Container có thể bị kernel giới hạn CPU dù dashboard chỉ cho thấy usage trung bình chưa đạt mức bạn kỳ vọng.

**Tại sao hữu ích:**
CPU limit quá thấp có thể làm request queue dài, ThreadPool xử lý chậm và p95/p99 tăng mà không có exception rõ ràng. Đây là infrastructure pressure, không nhất thiết là bug trong code.

**Ví dụ:**
Một API có request CPU burst ngắn. Pod đặt:
```yaml
resources:
  requests:
    cpu: "250m"
  limits:
    cpu: "500m"
```

Nếu load test cho thấy throttling tăng cùng latency, cần đánh giá lại limit, autoscaling và workload profile thay vì chỉ tối ưu C#.

**Lưu ý:**
Không đơn giản xóa mọi CPU limit. Điều đó có thể làm một workload noisy chiếm tài nguyên của workload khác. Quyết định phải dựa trên cluster policy và đo đạc.

### Tip 5 — File upload phải được coi là dữ liệu không tin cậy kể cả khi extension hợp lệ

**Mẹo:**
Với upload từ user, tạo tên file server-side, lưu ngoài web root, giới hạn kích thước và kiểm tra content thực tế thay vì tin vào extension hoặc `Content-Type` do client gửi.

**Tại sao hữu ích:**
Attacker có thể đổi tên executable thành `.jpg`, gửi MIME giả hoặc lợi dụng filename để path traversal. Upload pipeline cần bảo vệ storage và downstream processor, không chỉ validation ở UI.

**Ví dụ:**
Backend nhận `invoice.pdf`, nhưng lưu thành ID ngẫu nhiên như:
```text
7f6d8f35-2f75-4fb2-a37f-9a87d5c1f21a
```

Metadata gốc được lưu riêng; file chỉ được publish sau khi kiểm tra signature, size và malware scan nếu risk profile yêu cầu.

**Lưu ý:**
Không tự viết parser phức tạp cho mọi định dạng nếu thư viện hoặc scanning service đáng tin cậy đã tồn tại. Parser file là bề mặt security khó.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic

**Khái niệm:**
Queue phù hợp khi một message đại diện cho một unit of work cần một consumer logic xử lý; Topic phù hợp khi một event cần được phân phối độc lập tới nhiều subscription với lifecycle và filter riêng.

**Vấn đề nó giải quyết:**
Nếu dùng một queue cho mọi consumer, các consumer sẽ cạnh tranh message thay vì mỗi bên nhận bản sao. Ngược lại, dùng topic cho command đơn nhất có thể thêm topology và operational overhead không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command: một queue với competing consumers thường phù hợp. `OrderCompleted` là event: Billing, Analytics và Loyalty có thể cần ba subscription độc lập trên cùng topic.

**Trade-off:**
Queue đơn giản hơn và phù hợp work distribution; Topic tăng decoupling cho fan-out nhưng thêm subscription management, filter rules, monitoring và nhiều failure path hơn.

**Middle → Senior insight:**
Middle developer cần hiểu delivery, lock, retry và dead-letter behavior. Senior / Technical developer phải phân biệt command với event, ownership của consumer, fan-out requirement và chi phí vận hành trước khi chọn queue hay topic.

### Design 2 — Contract Testing cho service deploy độc lập

**Khái niệm:**
Contract Testing kiểm tra producer và consumer có còn đồng ý về API/message contract mà không cần chạy toàn bộ end-to-end environment cho mọi thay đổi.

**Vấn đề nó giải quyết:**
Trong hệ thống nhiều service, một producer có thể deploy thay đổi JSON, nullability hoặc enum semantics làm consumer khác hỏng dù unit test của cả hai đều pass. End-to-end test toàn hệ thống thường chậm, flaky và khó bao phủ mọi compatibility case.

**Ví dụ thực tế:**
Mobile Backend mong `/products/{id}` luôn trả `price` dạng number và `currency` không null. Contract test chạy trong CI của producer để đảm bảo các assumption đó vẫn đúng trước khi release.

**Trade-off:**
Contract Testing phát hiện integration breakage sớm và nhanh hơn E2E, nhưng yêu cầu quản lý version contract, ownership và tránh test quá sát implementation. Nó cũng không thay thế test runtime behavior thật như network, auth hoặc deployment config.

**Middle → Senior insight:**
Middle developer cần viết contract tập trung vào observable behavior. Senior / Technical developer phải quyết định contract nào đáng bảo vệ, cách version/deprecate chúng và cân bằng contract tests với integration/E2E tests để không tạo test suite trùng lặp.

### Design 3 — Bulkhead Isolation để giới hạn blast radius

**Khái niệm:**
Bulkhead Isolation chia tài nguyên hoặc concurrency budget giữa các workload/dependency để failure hoặc saturation ở một khu vực không làm cạn kiệt toàn bộ process.

**Vấn đề nó giải quyết:**
Nếu mọi outbound dependency dùng cùng concurrency pool không giới hạn, một API chậm có thể giữ hàng nghìn request, làm ThreadPool, connection pool hoặc memory bị chiếm và kéo cả service xuống.

**Ví dụ thực tế:**
Product API gọi Pricing và Reviews. Pricing là dependency critical, Reviews là optional. Hệ thống đặt concurrency limit riêng cho Reviews; nếu Reviews chậm, request có thể degrade gracefully thay vì làm cạn connection và khiến Pricing cũng thất bại.

**Trade-off:**
Bulkhead giảm blast radius và tăng resilience nhưng có thể làm một partition bị từ chối request dù tài nguyên ở partition khác đang rảnh. Nó cũng thêm policy, metrics và capacity tuning.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, concurrency limit và fallback behavior. Senior / Technical developer phải xác định boundary cần cô lập dựa trên criticality, tenant/workload profile, shared resource và failure propagation thay vì thêm bulkhead ở mọi dependency.
