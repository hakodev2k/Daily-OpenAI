# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `IAsyncDisposable` khi cleanup bản thân cần I/O bất đồng bộ

**Mẹo:**
Khi resource cần flush/close bằng async I/O, ưu tiên `IAsyncDisposable` và `await using` thay vì ép cleanup bất đồng bộ chạy đồng bộ trong `Dispose()`.

**Tại sao hữu ích:**
Blocking trên async cleanup bằng `.Result`/`.GetAwaiter().GetResult()` có thể giữ thread không cần thiết và làm shutdown/request path khó dự đoán. `await using` cho phép compiler tạo `try/finally` và await `DisposeAsync()` đúng semantics.

**Ví dụ:**
```csharp
await using var stream = await OpenExportStreamAsync(ct);
await WriteExportAsync(stream, ct);
```
Nếu custom component sở hữu một resource async-disposable, component đó nên propagate lifecycle thay vì che nó sau synchronous dispose giả tạo.

**Lưu ý:**
Không implement `IAsyncDisposable` chỉ vì class có method async. Chỉ cần nó khi cleanup thực sự cần asynchronous work; ownership của resource vẫn phải rõ để tránh double-dispose hoặc lifetime khó reasoning.

### Tip 2 — Redis cache stampede cần coordination ở cache-miss path

**Mẹo:**
Với key nóng có TTL, đừng để hàng trăm request cùng thấy cache miss rồi đồng thời query database. Cân nhắc request coalescing/single-flight, TTL jitter hoặc stale-while-revalidate tùy freshness requirement.

**Tại sao hữu ích:**
Một key hết hạn đúng lúc traffic cao có thể biến cache từ lớp bảo vệ thành bộ khuếch đại tải: mọi request cùng đánh source of truth, latency tăng rồi timeout/retry tiếp tục làm tải lớn hơn.

**Ví dụ:**
Product configuration được đọc 2.000 lần/giây và mất 150 ms để rebuild. Khi key expire, chỉ một execution rebuild value còn request cùng process chờ kết quả; TTL thêm jitter để nhiều hot keys không hết hạn cùng giây.

**Lưu ý:**
Distributed lock không phải lựa chọn mặc định cho mọi cache miss. Lock cũng có failure/expiry semantics; nếu stale data trong vài giây chấp nhận được, stale-while-revalidate thường đơn giản và resilient hơn.

### Tip 3 — Dùng `git bisect` để biến regression hunt thành binary search

**Mẹo:**
Khi biết một commit cũ tốt và HEAD đang lỗi, dùng `git bisect` cùng một test/script có thể xác định pass/fail để thu hẹp commit gây regression thay vì đọc tuần tự hàng chục PR.

**Tại sao hữu ích:**
Binary search giảm số revision cần kiểm tra từ tuyến tính xuống logarithmic. Với 128 commits, về lý thuyết chỉ khoảng 7 bước phân loại đã đủ cô lập candidate nếu test deterministic.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test tests/Regression.Tests
```
Sau khi tìm được culprit, dùng `git bisect reset` rồi review diff và reproduction để xác nhận causal change.

**Lưu ý:**
Một flaky test làm `bisect` đưa ra kết luận sai. Nếu một revision không build được vì thay đổi tooling/schema, dùng `git bisect skip` có chủ đích thay vì đánh dấu good/bad tùy tiện.

### Tip 4 — EF Core compiled query chỉ đáng dùng sau khi đo query-compilation overhead

**Mẹo:**
Với query shape chạy cực kỳ thường xuyên và ổn định, có thể đánh giá `EF.CompileQuery`/`EF.CompileAsyncQuery`; trước đó hãy profile để chắc query compilation thực sự đáng kể so với database/network latency.

**Tại sao hữu ích:**
EF Core đã cache nhiều phần của query pipeline. Compiled query bỏ thêm một số work khi thực thi lặp lại, nhưng không sửa SQL chậm, missing index, excessive rows hay network round trip.

**Ví dụ:**
Một lookup endpoint chạy hàng chục nghìn lần/giây với query đơn giản theo `TenantId + ExternalId` có thể benchmark compiled query so với query bình thường. Nếu database chiếm 95% latency, tối ưu compilation gần như không thay đổi p99.

**Lưu ý:**
Compiled query làm code ít linh hoạt hơn với dynamic query shape. Đừng dùng nó như performance ritual; benchmark end-to-end và allocation/CPU trước khi nhận thêm complexity.

### Tip 5 — CSP phải được rollout bằng telemetry, không bật policy nghiêm ngặt một lần

**Mẹo:**
Với website/CMS có nhiều script bên thứ ba, triển khai Content Security Policy ở `Content-Security-Policy-Report-Only` trước, thu violation evidence rồi mới enforce policy tối thiểu cần thiết.

**Tại sao hữu ích:**
CSP giúp giảm impact của XSS bằng cách giới hạn nguồn script/resource được phép thực thi. Nhưng enterprise site thường có analytics, consent manager, payment hoặc CMS-injected resources; policy sai có thể làm production UI hỏng ngay lập tức.

**Ví dụ:**
Bắt đầu với nonce/hash cho first-party script, report violations của checkout/CMS pages, phân loại source hợp lệ rồi loại dần broad directives như `unsafe-inline` thay vì allowlist mọi domain thấy trong log.

**Lưu ý:**
CSP là defense-in-depth, không thay thế output encoding, sanitization và việc loại bỏ XSS source. Report endpoint cũng cần chống noise và không nên thu payload nhạy cảm ngoài nhu cầu điều tra.

## 🧠 Software Design

### Design 1 — Saga compensation không phải distributed rollback

**Khái niệm:**
Saga chia business workflow thành các local transactions; khi bước sau thất bại, hệ thống thực hiện compensating action cho các bước đã hoàn thành thay vì rollback ACID xuyên nhiều services.

**Vấn đề nó giải quyết:**
Order, payment và inventory thuộc các consistency boundary khác nhau. Giữ distributed transaction qua tất cả dependency thường không khả thi, trong khi partial failure là trạng thái bình thường cần được model rõ.

**Ví dụ thực tế:**
Checkout reserve inventory, authorize payment rồi tạo shipment. Nếu shipment creation thất bại vĩnh viễn, workflow có thể release inventory và void/refund payment theo business rules; trạng thái trung gian vẫn phải quan sát và retry được.

**Trade-off:**
Saga tăng autonomy và chịu partial failure tốt hơn nhưng thêm state machine, idempotency, compensation failure và operational visibility. Compensation cũng không luôn đảo ngược hoàn toàn tác động thực tế — email đã gửi hoặc hàng đã rời kho không thể “rollback” như row database.

**Middle → Senior insight:**
Middle developer cần implement từng step idempotent và phân biệt retry với compensation. Senior / Technical developer phải xác định business invariants, irreversible steps, timeout/recovery policy và chọn orchestration/choreography dựa trên khả năng vận hành chứ không theo pattern preference.

### Design 2 — Strangler Fig cho modernization thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig migration chuyển từng capability/traffic slice từ legacy system sang implementation mới qua một routing/facade boundary, để hệ thống cũ co lại dần thay vì bị thay thế trong một release lớn.

**Vấn đề nó giải quyết:**
Rewrite toàn bộ .NET Framework/CMS legacy application thường kéo dài, requirements tiếp tục thay đổi và business phải chờ đến cuối mới nhận giá trị. Incremental migration tạo checkpoint có thể deploy và rollback.

**Ví dụ thực tế:**
Giữ legacy checkout đang chạy nhưng route product-read API sang ASP.NET Core mới trước. Sau khi telemetry và compatibility ổn định, tiếp tục tách pricing rồi order history; write-heavy capability khó hơn được để sau với migration plan riêng.

**Trade-off:**
Incremental migration giảm delivery risk nhưng tạm thời phải vận hành hai stacks, routing, duplicated models và synchronization. Nếu boundary chọn sai, transitional architecture có thể tồn tại nhiều năm và trở thành technical debt mới.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility và viết regression/integration tests quanh seam. Senior / Solution-oriented engineer phải chọn migration slice theo dependency graph, business value, rollbackability và data ownership — không chỉ theo module dễ code nhất.

### Design 3 — Metric cardinality là một phần của observability architecture

**Khái niệm:**
Metric labels/dimensions cho phép aggregate theo thuộc tính, nhưng mỗi tổ hợp label value tạo thêm time series. Cardinality phải được thiết kế như resource budget chứ không phải log field nào cũng biến thành metric dimension.

**Vấn đề nó giải quyết:**
Gắn `UserId`, `OrderId`, raw URL hoặc exception message vào metric labels có thể tạo hàng triệu series, tăng chi phí ingestion/storage và làm query/dashboard chậm hoặc bị backend observability giới hạn.

**Ví dụ thực tế:**
HTTP latency metric nên dimension theo route template, method, status class và service; `TraceId`/`OrderId` để trong trace/log phục vụ drill-down. Alert phát hiện route bất thường rồi exemplar/trace dẫn tới request cụ thể.

**Trade-off:**
Cardinality thấp giữ metric rẻ và aggregate nhanh nhưng giảm khả năng slice tùy ý. Cardinality quá cao cho chi tiết lớn nhưng biến metrics thành một dạng log đắt tiền; cần phối hợp metrics, traces và logs theo vai trò khác nhau.

**Middle → Senior insight:**
Middle developer cần tránh unbounded label values và hiểu route template khác raw path. Senior / Technical developer phải đặt telemetry schema/cardinality budget, retention và sampling strategy để observability vẫn hữu ích khi traffic tăng nhiều lần.
