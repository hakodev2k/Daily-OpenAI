# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` khi xử lý stream dữ liệu lớn

**Mẹo:**
Khi dữ liệu có thể được xử lý từng phần, dùng `IAsyncEnumerable<T>` thay vì load toàn bộ collection vào memory rồi mới xử lý.

**Tại sao hữu ích:**
Giảm peak memory, cho phép consumer bắt đầu xử lý sớm hơn và phù hợp với pipeline đọc database, file hoặc API theo từng item/batch.

**Ví dụ:**
```csharp
await foreach (var item in repository.StreamPendingItemsAsync(cancellationToken))
{
    await processor.ProcessAsync(item, cancellationToken);
}
```

Repository có thể yield dữ liệu dần:

```csharp
public async IAsyncEnumerable<Order> StreamPendingItemsAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken)
{
    await foreach (var order in dbContext.Orders
        .Where(x => x.Status == OrderStatus.Pending)
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken))
    {
        yield return order;
    }
}
```

**Lưu ý:**
Streaming không tự động làm mọi thứ nhanh hơn. Nếu consumer xử lý rất chậm, connection/database reader có thể bị giữ lâu; đôi khi batch processing sẽ cân bằng tài nguyên tốt hơn.

### Tip 2 — Kiểm tra plan cache khi SQL đột nhiên chậm do parameter-sensitive behavior

**Mẹo:**
Nếu cùng một query lúc nhanh lúc chậm rất khác nhau tùy parameter, hãy nghi ngờ execution plan không phù hợp với distribution dữ liệu thay vì chỉ thêm index ngay.

**Tại sao hữu ích:**
Một plan tối ưu cho tenant nhỏ có thể rất tệ cho tenant cực lớn, hoặc ngược lại. Đây là dạng production issue dễ bị hiểu nhầm là database “randomly slow”.

**Ví dụ:**
Scenario:

```sql
SELECT *
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status;
```

Nếu `TenantId=1` có vài trăm rows nhưng `TenantId=999` có hàng triệu rows, cùng một cached plan có thể không tối ưu cho cả hai trường hợp.

Kiểm tra execution plan thực tế, row estimates và runtime metrics trước khi chọn giải pháp như rewrite query, statistics, recompilation hoặc plan strategy phù hợp.

**Lưu ý:**
Đừng dùng `OPTION (RECOMPILE)` hoặc tương đương như thuốc chữa mọi query chậm; compile cost và CPU có thể tăng mạnh trên workload tần suất cao.

### Tip 3 — Dùng `CancellationTokenSource.CreateLinkedTokenSource` khi operation có nhiều nguồn hủy

**Mẹo:**
Khi một operation phải dừng nếu client disconnect, app shutdown hoặc internal timeout xảy ra, gộp nhiều token thành một token duy nhất.

**Tại sao hữu ích:**
Giúp propagation rõ ràng hơn và tránh code phải tự kiểm tra nhiều cancellation source ở từng tầng.

**Ví dụ:**
```csharp
using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(10));
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    requestAborted,
    timeoutCts.Token,
    stoppingToken);

await worker.ExecuteAsync(linkedCts.Token);
```

**Lưu ý:**
Linked token source cần được dispose. Ngoài ra, cancellation chỉ có tác dụng nếu các downstream API thực sự nhận và tôn trọng token đó.

### Tip 4 — Dùng `docker history` và image inspection để tìm layer phình to

**Mẹo:**
Khi Docker image lớn bất thường, kiểm tra layer nào chiếm nhiều dung lượng thay vì đoán từ Dockerfile.

**Tại sao hữu ích:**
Có thể phát hiện file build artifact, package cache, source không cần thiết hoặc command tạo file lớn trong layer rồi xóa ở layer sau nhưng dung lượng vẫn còn trong image history.

**Ví dụ:**
```bash
docker history myapp:latest
```

Kiểm tra metadata:

```bash
docker inspect myapp:latest
```

Nếu thấy layer quá lớn, thường nên gộp cleanup cùng `RUN` hoặc chuyển artifact cần thiết sang final stage bằng multi-stage build.

**Lưu ý:**
Xóa file ở layer sau không làm layer trước nhỏ đi. Muốn giảm image size thực sự, phải thay đổi cách build layer hoặc dùng multi-stage build đúng cách.

### Tip 5 — Dùng snapshot nhỏ của production shape cho performance test, không chỉ random data

**Mẹo:**
Khi benchmark query hoặc API, tạo test data phản ánh distribution thực tế: hot tenant, skewed status, null rate, record size và cardinality tương tự production.

**Tại sao hữu ích:**
Performance bug thường đến từ data shape chứ không chỉ số lượng rows. Dataset “đẹp và đều” trong test dễ làm query plan hoặc cache behavior trông tốt hơn thực tế.

**Ví dụ:**
Thay vì seed 1 triệu Orders chia đều 100 tenant, hãy mô phỏng:

```text
Tenant A: 600,000 rows
Tenant B: 200,000 rows
98 tenants còn lại: 200,000 rows
90% Status = Completed
8% Status = Pending
2% Status = Failed
```

Sau đó benchmark đúng các query production hay chạy.

**Lưu ý:**
Không copy raw production data có PII/secrets vào môi trường test. Hãy synthetic/anonymize nhưng giữ lại distribution và relational shape quan trọng.

## 🧠 Software Design

### Design 1 — Backpressure trong pipeline producer-consumer

**Khái niệm:**
Backpressure là cơ chế buộc producer chậm lại, chờ hoặc reject khi consumer không xử lý kịp, thay vì tiếp tục tạo vô hạn work item trong memory hoặc queue.

**Vấn đề nó giải quyết:**
Nếu producer tạo 20,000 jobs/giây nhưng consumer chỉ xử lý 5,000 jobs/giây, backlog sẽ tăng liên tục cho đến khi memory, queue storage hoặc downstream dependency bị quá tải.

**Ví dụ thực tế:**
Một service đọc sự kiện từ API ngoài rồi đẩy vào worker pool. Thay vì `ConcurrentQueue` không giới hạn, dùng bounded `Channel<T>` capacity 1,000. Khi channel đầy, producer phải chờ hoặc áp dụng drop/retry policy rõ ràng.

**Trade-off:**
Backpressure giúp hệ thống ổn định và giới hạn resource usage, nhưng có thể làm tăng upstream latency hoặc yêu cầu quyết định rõ khi nào block, reject, drop hay persist tạm.

**Middle → Senior insight:**
Middle developer nên hiểu queue không giới hạn chỉ trì hoãn failure. Senior developer phải thiết kế capacity theo throughput thực, memory budget, retry behavior và SLO, đồng thời quyết định nơi đặt backpressure để blast radius nhỏ nhất.

### Design 2 — Database-per-service hay Shared Database là quyết định về ownership trước khi là kỹ thuật

**Khái niệm:**
Database-per-service trao quyền sở hữu schema/data rõ ràng cho từng service. Shared Database cho nhiều service cùng truy cập một database hoặc schema chung.

**Vấn đề nó giải quyết:**
Khi nhiều service cùng sửa trực tiếp một schema, coupling dữ liệu tăng mạnh: deploy độc lập khó hơn, migration dễ phá nhau và business rule có thể bị bypass qua SQL trực tiếp.

**Ví dụ thực tế:**
`OrderService` và `BillingService` dùng chung bảng `Orders`. Billing bắt đầu thêm column và query trực tiếp vào bảng Order, khiến Order team không thể thay schema mà không phối hợp. Tách ownership có thể chuyển Billing sang contract/event/API thay vì direct table access.

**Trade-off:**
Database-per-service tăng autonomy và boundary rõ nhưng làm join/reporting, transaction xuyên service và data duplication phức tạp hơn. Shared Database đơn giản hơn ở hệ thống nhỏ nhưng dễ trở thành coupling bottleneck khi tổ chức và domain lớn lên.

**Middle → Senior insight:**
Middle developer cần nhận ra direct DB access giữa services là coupling rất mạnh. Senior developer phải cân nhắc team ownership, deployment independence, transaction needs, reporting requirements và operational maturity trước khi ép mọi service có database riêng.

### Design 3 — Rate Limiting phải thiết kế theo fairness, không chỉ theo tổng request count

**Khái niệm:**
Rate Limiting giới hạn lượng request trong một khoảng thời gian, nhưng boundary giới hạn có thể theo IP, user, API key, tenant, endpoint hoặc workload class.

**Vấn đề nó giải quyết:**
Một global limit duy nhất có thể để một tenant lớn chiếm hết capacity, khiến tenant nhỏ bị throttled dù họ không gây ra tải bất thường.

**Ví dụ thực tế:**
API có capacity 10,000 req/s. Nếu chỉ dùng global limit, một customer chạy batch import có thể dùng 9,500 req/s. Thiết kế tốt hơn có thể kết hợp global safety limit với per-tenant quota và limit riêng cho endpoint đắt như report/export.

**Trade-off:**
Rate limit nhiều tầng bảo vệ fairness và tài nguyên tốt hơn nhưng tăng complexity, state management và nguy cơ reject nhầm workload hợp lệ nếu threshold không dựa trên traffic thực tế.

**Middle → Senior insight:**
Middle developer nên biết chọn key phù hợp và trả `429 Too Many Requests` nhất quán. Senior developer cần thiết kế quota theo cost của operation, tenant tier, burst tolerance, retry guidance và đảm bảo throttling không tạo synchronized retry storm.
