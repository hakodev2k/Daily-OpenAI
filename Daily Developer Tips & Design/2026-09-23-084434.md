# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `IAsyncEnumerable` giúp streaming nhưng phải giữ lifetime đúng

**Mẹo:**
Dùng `IAsyncEnumerable<T>` khi muốn xử lý hoặc trả dữ liệu theo từng phần thay vì materialize toàn bộ collection, nhưng bảo đảm `DbContext`, stream hoặc resource nguồn còn sống trong suốt quá trình enumeration.

**Tại sao hữu ích:**
`ToListAsync()` buộc application đợi và giữ toàn bộ result trong memory trước khi xử lý tiếp. Async streaming có thể giảm peak memory và time-to-first-item. Tuy nhiên query thường chỉ thực sự chạy khi consumer enumerate, nên dispose resource quá sớm sẽ gây lỗi ở thời điểm tưởng như method đã hoàn tất.

**Ví dụ:**
```csharp
await foreach (var row in db.AuditLogs
    .AsNoTracking()
    .Where(x => x.CreatedAt >= from)
    .AsAsyncEnumerable()
    .WithCancellation(ct))
{
    await writer.WriteAsync(row, ct);
}
```
Export audit log lớn có thể ghi từng record thay vì tạo một `List<AuditLog>` hàng trăm MB.

**Lưu ý:**
Streaming giữ database reader/connection lâu hơn. Với consumer chậm, điều này có thể làm connection pool chịu áp lực. Đừng mặc định streaming luôn tốt hơn batching; chọn theo memory, connection lifetime và backpressure của workload.

### Tip 2 — Dùng `Activity`/distributed tracing để tìm latency bị mất giữa các service

**Mẹo:**
Khi request đi qua nhiều service, database và external API, truyền trace context và dùng distributed tracing thay vì cố ghép log bằng timestamp thủ công.

**Tại sao hữu ích:**
Một API tổng latency 2 giây không cho biết thời gian nằm ở application code, SQL hay dependency. Trace biểu diễn parent/child spans và duration của từng operation, giúp đi từ symptom → evidence → dependency gây chậm nhanh hơn.

**Ví dụ:**
Một checkout request có trace: API 2.1 s, SQL 80 ms, inventory 120 ms, payment 1.7 s. Thay vì tối ưu EF Core vì thấy endpoint chậm, team tập trung vào payment dependency và timeout budget.

**Lưu ý:**
Trace không thay thế metrics/logs. Sampling quá mạnh có thể bỏ mất request hiếm nhưng quan trọng; ngược lại ghi mọi tag có thể tăng cost và rò rỉ dữ liệu nhạy cảm. Thiết kế telemetry fields và sampling theo mục đích vận hành.

### Tip 3 — Keyset pagination ổn định hơn `OFFSET` cho tập dữ liệu lớn

**Mẹo:**
Với feed/list lớn được duyệt tuần tự, cân nhắc keyset pagination dựa trên cột sort ổn định thay vì `OFFSET ... FETCH` ở page sâu.

**Tại sao hữu ích:**
`OFFSET` lớn vẫn buộc database tìm/sắp xếp rồi bỏ qua nhiều rows trước khi trả page. Keyset bắt đầu từ giá trị cuối của page trước và có thể tận dụng index để seek trực tiếp, đồng thời ít bị dịch page khi dữ liệu mới được chèn.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Composite ordering bằng `CreatedAt, Id` tạo cursor deterministic ngay cả khi nhiều order có cùng timestamp.

**Lưu ý:**
Keyset không phù hợp khi UI cần nhảy trực tiếp tới page 137 hoặc tính page number chính xác. Cursor phải chứa đủ sort keys và query cần index phù hợp với filter/order; chỉ đổi syntax mà không xem execution plan có thể không đem lại lợi ích.

### Tip 4 — Elasticsearch mapping phải được thiết kế trước khi dữ liệu lớn

**Mẹo:**
Xác định field nào cần full-text search, exact filtering/sorting/aggregation và thiết kế `text`/`keyword`, analyzer, normalizer tương ứng trước khi index tăng lớn.

**Tại sao hữu ích:**
Elasticsearch tạo inverted index dựa trên mapping/analyzer tại index time. Đổi analyzer hoặc kiểu field thường không thể “sửa tại chỗ” cho dữ liệu đã index; bạn thường phải tạo index mới và reindex. Mapping sai sớm trở thành migration vận hành tốn kém về sau.

**Ví dụ:**
Tên sản phẩm có thể dùng `text` cho search và subfield `keyword` cho exact sort/filter. `ProductCode` thường không nên bị tokenizer tách thành token như natural language.

**Lưu ý:**
Đừng bật dynamic mapping không kiểm soát cho payload tùy ý; field explosion có thể tăng cluster state và resource usage. Elasticsearch cũng không nên trở thành source of truth cho transaction chỉ vì search nhanh.

### Tip 5 — Feature flag cần cleanup plan, không chỉ nút bật/tắt

**Mẹo:**
Khi dùng feature flag cho rollout, ghi rõ owner, mục tiêu, default behavior và thời điểm xóa flag sau khi rollout ổn định.

**Tại sao hữu ích:**
Feature flag giúp deploy code tách khỏi release behavior và hỗ trợ canary/rollback nhanh. Nhưng flag tồn tại lâu tạo thêm execution paths, test combinations và dead code; vài chục boolean flags có thể biến behavior production thành khó suy luận.

**Ví dụ:**
Release checkout mới cho 5% tenant, theo dõi error rate/p95 rồi tăng dần. Sau khi 100% ổn định qua observation window, xóa implementation cũ và flag thay vì để `if (NewCheckout)` tồn tại vĩnh viễn.

**Lưu ý:**
Flag không phải security boundary. Backend vẫn phải authorization đúng dù UI ẩn feature. Với migration database, cả code path cũ và mới cần tương thích schema trong rollout window nếu deployment có overlap.

## 🧠 Software Design

### Design 1 — Bounded Context quan trọng hơn việc chia service theo bảng dữ liệu

**Khái niệm:**
Trong DDD, Bounded Context là ranh giới nơi một domain model và ngôn ngữ có ý nghĩa nhất quán. Nó không đồng nghĩa với một microservice hay một nhóm bảng; mục tiêu là tách các business concepts có semantics và lifecycle khác nhau.

**Vấn đề nó giải quyết:**
Một `Customer` trong Sales có thể mang nghĩa prospect/account, trong Billing là payer, còn Support quan tâm contact và entitlement. Ép toàn doanh nghiệp dùng một mega-entity chung tạo coupling: thay đổi phục vụ một capability kéo theo schema/code của capability khác.

**Ví dụ thực tế:**
E-commerce có Catalog quản lý product description/pricing display, Ordering quản lý order snapshot và Fulfillment quản lý shipment. Ordering không cần phụ thuộc trực tiếp vào mutable Catalog entity; nó giữ dữ liệu cần thiết tại transaction boundary của order.

**Trade-off:**
Boundary rõ giảm coupling và ownership ambiguity nhưng có thể tạo duplicated data, mapping và eventual consistency. Chia context quá nhỏ lại sinh integration overhead. Bounded Context cũng không yêu cầu deploy riêng; nhiều context có thể cùng nằm trong Modular Monolith.

**Middle → Senior insight:**
Middle developer cần giữ model và dependency đúng boundary, tránh dùng entity chung như DTO toàn hệ thống. Senior / Technical developer phải tìm boundary từ business invariants, change cadence và ownership, rồi quyết định boundary nào chỉ cần module và boundary nào thật sự đáng tách deployment/service.

### Design 2 — Circuit Breaker bảo vệ failure recovery, không phải cơ chế retry

**Khái niệm:**
Circuit Breaker ngừng gửi request tới dependency đang có xác suất thất bại cao trong một khoảng thời gian, sau đó cho phép probe có kiểm soát để đánh giá recovery. Retry thì thử lại operation; hai pattern giải quyết hai áp lực khác nhau.

**Vấn đề nó giải quyết:**
Khi dependency outage, tiếp tục gửi full traffic có thể lãng phí connection/concurrency, tăng timeout và cản dependency phục hồi. Retry không kiểm soát còn nhân traffic đúng lúc hệ thống yếu nhất.

**Ví dụ thực tế:**
Payment provider liên tục timeout. Sau ngưỡng failure, circuit mở và checkout fail-fast/fallback theo business policy thay vì mỗi request chờ 10 giây. Sau break duration, một lượng probe nhỏ kiểm tra provider đã hồi phục chưa.

**Trade-off:**
Circuit quá nhạy có thể ngắt dependency vẫn dùng được; quá chậm thì không bảo vệ được capacity. Trong multi-instance deployment, mỗi process thường có state circuit riêng nên behavior không hoàn toàn global. Fallback cũng có thể che lỗi hoặc trả dữ liệu không phù hợp nếu business semantics không cho phép.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry, circuit states và tránh retry operation không idempotent. Senior / Technical developer phải thiết kế latency budget, failure threshold, retry amplification, fallback semantics và telemetry để policy phản ánh dependency SLO thay vì dùng default tùy ý.

### Design 3 — Schema evolution cho zero-downtime deployment nên dùng Expand–Migrate–Contract

**Khái niệm:**
Expand–Migrate–Contract thay schema qua nhiều bước tương thích: trước tiên mở rộng schema để cả code cũ/mới chạy được, sau đó migrate/backfill dữ liệu và traffic, cuối cùng mới xóa contract/schema cũ.

**Vấn đề nó giải quyết:**
Rolling deployment khiến nhiều application versions cùng chạy trong một khoảng thời gian. Nếu migration rename/drop column ngay khi deploy code mới, instance cũ vẫn đang phục vụ traffic có thể fail. Database rollback cũng khó nếu migration phá hủy dữ liệu ngay lập tức.

**Ví dụ thực tế:**
Muốn đổi `FullName` thành `FirstName`/`LastName`: thêm cột mới trước, deploy code có khả năng đọc/ghi tương thích, backfill dữ liệu, chuyển toàn bộ traffic sang version mới, quan sát rồi mới xóa `FullName` ở release sau.

**Trade-off:**
Quy trình nhiều release chậm hơn migration một bước, có temporary duplication và cần kiểm soát dual-write/backfill. Nhưng nó giảm coupling giữa application rollout và destructive schema change. Với hệ thống nhỏ có maintenance window thật sự, quy trình đầy đủ có thể không cần thiết.

**Middle → Senior insight:**
Middle developer cần tránh destructive migration không tương thích và test application với schema chuyển tiếp. Senior / Technical developer phải lập compatibility matrix giữa app versions/schema versions, đánh giá lock/backfill cost, định nghĩa rollback/roll-forward và quyết định khi nào zero-downtime complexity thực sự đáng giá.
