# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsSplitQuery()` khi `Include` nhiều collection gây cartesian explosion

**Mẹo:**
Trong EF Core, nếu một query `Include` nhiều collection cùng cấp và SQL trả về rất nhiều row lặp do join chéo, cân nhắc `AsSplitQuery()` để tách thành nhiều SQL query thay vì một query khổng lồ.

**Tại sao hữu ích:**
Một aggregate có 20 `OrderLines` và 15 `Tags` có thể tạo hàng trăm row trung gian chỉ để materialize một `Order`. Điều này làm network payload lớn, tăng memory allocation và khiến query trông chậm dù số entity thực tế không nhiều. Split query giảm duplication ở result set.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Tags)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == orderId, ct);
```

Hãy so sánh generated SQL, số row trả về và tổng latency trước/sau.

**Lưu ý:**
Split query tăng số round trip tới database và có thể quan sát dữ liệu ở các thời điểm hơi khác nhau nếu không nằm trong isolation phù hợp. Với projection DTO gọn hoặc chỉ một collection nhỏ, single query có thể vẫn tốt hơn.

### Tip 2 — Cấu hình `ForwardedHeaders` đúng khi ASP.NET Core chạy sau reverse proxy

**Mẹo:**
Khi ASP.NET Core chạy sau Azure Front Door, Application Gateway, Nginx, IIS hoặc reverse proxy khác, xử lý `X-Forwarded-For` / `X-Forwarded-Proto` bằng `ForwardedHeadersMiddleware` và chỉ trust proxy/network đã biết.

**Tại sao hữu ích:**
Nếu application không hiểu scheme/client IP thật, có thể generate redirect HTTP thay vì HTTPS, ghi sai audit IP hoặc policy phụ thuộc scheme hoạt động sai. Ngược lại, trust forwarded header từ mọi nguồn cho phép client giả mạo IP/scheme.

**Ví dụ:**
```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.0.4"));
});

app.UseForwardedHeaders();
```

Đặt middleware đủ sớm trước redirect/authentication logic phụ thuộc scheme hoặc remote IP.

**Lưu ý:**
Không gọi `KnownNetworks.Clear()` / `KnownProxies.Clear()` chỉ để “cho chạy” nếu application có thể bị truy cập trực tiếp từ Internet. Trust boundary của proxy là security configuration, không phải convenience setting.

### Tip 3 — Phân biệt trace attribute với baggage để tránh phát tán dữ liệu không cần thiết

**Mẹo:**
Trong OpenTelemetry, dùng span attribute/tag cho dữ liệu chỉ cần gắn vào span hiện tại; chỉ dùng baggage khi giá trị thật sự cần propagate qua service boundary.

**Tại sao hữu ích:**
Baggage có thể được truyền qua nhiều hop và làm tăng header/context size. Nếu nhét `user_id`, raw query, email hoặc metadata lớn vào baggage, bạn vừa tăng overhead vừa mở rộng phạm vi dữ liệu nhạy cảm đi qua nhiều service.

**Ví dụ:**
```csharp
using var activity = ActivitySource.StartActivity("ProcessOrder");
activity?.SetTag("order.type", order.Type);
activity?.SetTag("tenant.plan", tenant.Plan);
```

Chỉ khi downstream thực sự cần một context như `tenant-region` để routing/diagnostics thì mới cân nhắc baggage.

**Lưu ý:**
Không biến telemetry thành nơi chứa PII hoặc secret. Attribute cardinality cao cũng có cost riêng ở backend quan sát; baggage càng cần kiểm soát chặt vì nó còn được propagate qua request chain.

### Tip 4 — Validate file upload bằng content signature và policy, không chỉ extension/MIME header

**Mẹo:**
Với API upload file, đừng tin `Content-Type` hoặc extension do client gửi. Kiểm tra magic bytes/file signature, giới hạn kích thước, tên file, storage location và scan nếu threat model yêu cầu.

**Tại sao hữu ích:**
Client có thể đổi tên `malware.exe` thành `invoice.pdf` hoặc gửi `Content-Type: application/pdf`. Nếu backend chỉ kiểm tra metadata, file độc hại có thể lọt vào storage rồi được phục vụ lại cho user khác.

**Ví dụ:**
```text
Upload flow:
1. reject file vượt size limit
2. generate server-side object name
3. inspect signature / parser phù hợp loại file
4. lưu vào quarantine/private storage
5. malware scan nếu cần
6. chỉ publish sau khi pass policy
```

Với image, decode/re-encode bằng thư viện an toàn có thể loại bỏ một số payload bất thường tốt hơn chỉ copy raw bytes.

**Lưu ý:**
Magic-byte validation không chứng minh file hoàn toàn an toàn. Parser vulnerability, decompression bomb, polyglot file và macro document vẫn cần threat-specific controls. Không lưu upload trực tiếp trong web root với filename do user cung cấp.

### Tip 5 — Dùng Query Store để điều tra plan regression thay vì đoán index mới ngay lập tức

**Mẹo:**
Khi SQL Server query từng nhanh nhưng đột nhiên chậm sau deployment/data growth/statistics change, dùng Query Store để so sánh execution plan, runtime statistics và plan history trước khi thêm index hoặc rewrite query.

**Tại sao hữu ích:**
Một query có thể chậm vì optimizer chuyển sang plan khác do parameter distribution, statistics hoặc cardinality estimate. Nếu chỉ nhìn query hiện tại, bạn mất bằng chứng về “plan tốt trước đó” và dễ chữa sai nguyên nhân.

**Ví dụ:**
```text
Symptom:
P95 /orders/search tăng từ 120 ms -> 2.8 s

Query Store:
- plan 17: Index Seek + Nested Loops, median 90 ms
- plan 24: Scan + Hash Match, median 2.4 s
- plan 24 bắt đầu sau statistics update
```

Từ đó mới quyết định update statistics, sửa predicate/index, xử lý parameter sensitivity hoặc tạm force plan nếu phù hợp.

**Lưu ý:**
Plan forcing là mitigation, không phải root-cause fix mặc định. Data distribution thay đổi có thể khiến plan cũ không còn tốt. Luôn kiểm tra logical reads, CPU, duration và parameter pattern thực tế.

## 🧠 Software Design

### Design 1 — Retry budget để tránh retry amplification giữa nhiều layer

**Khái niệm:**
Retry budget giới hạn tổng số retry mà một request/workflow được phép tạo ra, thay vì để API gateway, service, SDK và database client mỗi layer tự retry độc lập.

**Vấn đề nó giải quyết:**
Nếu 3 layer đều retry 3 lần, một failure nhỏ có thể nhân số call lên rất lớn. Khi dependency đang quá tải, retry amplification biến transient fault thành overload cascade.

**Ví dụ thực tế:**
```text
Client -> API -> Payment Service -> Provider

Mỗi layer retry 3 lần
=> một user request có thể tạo nhiều chục downstream attempts

Thiết kế tốt hơn:
- timeout end-to-end
- retry ở layer hiểu idempotency rõ nhất
- budget tối đa, ví dụ 2 retry cho toàn workflow
- exponential backoff + jitter
```

Có thể truyền deadline/cancellation thay vì để mỗi layer tự đặt timeout dài riêng.

**Trade-off:**
Retry đúng chỗ tăng resilience với transient fault, nhưng retry budget quá chặt có thể làm giảm success rate khi dependency hồi phục nhanh. Budget cần dựa trên SLO, latency budget và semantics của operation.

**Middle → Senior insight:**
Middle developer cần không thêm retry vào mọi client chỉ vì thư viện hỗ trợ. Senior / Technical developer phải thiết kế retry ownership end-to-end, xác định operation nào idempotent, tổng latency budget và cách ngăn retry storm khi dependency suy giảm.

### Design 2 — Database constraint như safety net cho invariant quan trọng

**Khái niệm:**
Một số invariant nên được enforce cả trong application logic lẫn database constraint khi violation sẽ làm dữ liệu trở nên không hợp lệ hoặc khó sửa.

**Vấn đề nó giải quyết:**
Validation trong service có thể bị bypass bởi race condition, migration script, admin tool hoặc code path mới. Nếu invariant chỉ sống trong code, hai request concurrent vẫn có thể cùng pass validation rồi commit dữ liệu sai.

**Ví dụ thực tế:**
```text
Rule: mỗi tenant chỉ có một active slug giống nhau

Application:
- kiểm tra duplicate để trả lỗi thân thiện

Database:
- unique constraint/index trên (TenantId, Slug)

Race condition:
Request A và B cùng check -> đều thấy chưa tồn tại
-> database unique constraint chặn một request khi commit
```

Application xử lý unique violation thành lỗi domain/API phù hợp.

**Trade-off:**
Constraint tăng data integrity nhưng có thể làm migration phức tạp hơn và không diễn đạt tốt invariant trải qua nhiều aggregate/service. Một số business rule vẫn phải nằm ở domain/application layer.

**Middle → Senior insight:**
Middle developer cần biết validation UX không thay thế database integrity. Senior / Technical developer phải chọn invariant nào cần hard guarantee ở storage, cách map constraint violation về domain semantics và cách migrate dữ liệu cũ trước khi bật constraint.

### Design 3 — Backend for Frontend (BFF) khi mỗi client có nhu cầu orchestration khác nhau

**Khái niệm:**
BFF tạo backend boundary riêng cho một loại client như web, mobile hoặc partner portal, chịu trách nhiệm aggregate/orchestrate data theo nhu cầu UI thay vì ép mọi client dùng một generic API giống nhau.

**Vấn đề nó giải quyết:**
Mobile có bandwidth/latency constraint khác web; admin portal cần dữ liệu và permission khác storefront. Nếu một generic API cố phục vụ tất cả, contract dễ phình to hoặc client phải gọi quá nhiều endpoint rồi tự ghép state.

**Ví dụ thực tế:**
```text
Web Storefront -> Web BFF -> Catalog / Pricing / Review services
Mobile App     -> Mobile BFF -> Catalog / Profile / Push settings
Admin Portal   -> Admin BFF -> CMS / Inventory / Audit
```

BFF có thể tối ưu payload, orchestration và auth flow theo từng client mà không buộc domain service biết chi tiết presentation.

**Trade-off:**
BFF giảm coupling giữa UI và domain APIs nhưng thêm deployment, observability và duplicated orchestration logic. Nếu chỉ có một client hoặc nhu cầu gần giống nhau, một API layer chung đơn giản hơn thường hợp lý.

**Middle → Senior insight:**
Middle developer cần tránh nhét business rule cốt lõi vào BFF chỉ vì gần UI. Senior / Technical developer phải quyết định boundary nào thuộc presentation orchestration, ownership theo team/client, caching strategy và cách ngăn BFF biến thành một monolith proxy mới.
