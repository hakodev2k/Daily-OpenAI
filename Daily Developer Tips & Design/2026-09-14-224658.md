# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi Large Object Heap khi allocation lớn gây GC pause khó hiểu

**Mẹo:**
Khi .NET service có memory tăng nhanh hoặc GC pause bất thường, đừng chỉ nhìn tổng heap. Kiểm tra riêng Large Object Heap (LOH), đặc biệt với `byte[]`, `char[]`, JSON payload hoặc buffer lớn được tạo liên tục.

**Tại sao hữu ích:**
Object lớn đi vào LOH và có vòng đời/compaction khác object nhỏ. Nếu code liên tục tạo buffer lớn, heap có thể phân mảnh hoặc tạo áp lực GC đáng kể dù object cuối cùng vẫn được collect. Đây là lý do một API xử lý file hoặc serialization lớn có thể chậm dần mà CPU business logic không hề tăng nhiều.

**Ví dụ:**
```text
Triệu chứng:
- p95 latency tăng khi upload/export
- memory dao động mạnh
- Gen 2 GC tăng
- allocation profile cho thấy nhiều byte[] lớn

Hướng xử lý:
- đo bằng dotnet-counters / dotnet-gcdump / profiler
- tránh materialize payload lớn nếu có thể stream
- tái sử dụng buffer hợp lý, ví dụ ArrayPool<byte>
```

**Lưu ý:**
Không dùng `ArrayPool<T>` máy móc cho mọi allocation. Buffer thuê phải được trả đúng chỗ, dữ liệu nhạy cảm có thể cần clear, và giữ buffer quá lâu lại làm memory usage khó đoán hơn. Đo trước khi tối ưu.

### Tip 2 — SQL Server query lúc nhanh lúc chậm: kiểm tra parameter-sensitive plan trước khi thêm index

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có lúc chạy vài ms, lúc vài giây với cùng execution path logic, kiểm tra execution plan theo từng parameter distribution thay vì lập tức thêm index.

**Tại sao hữu ích:**
SQL Server có thể compile plan dựa trên giá trị parameter tại thời điểm tối ưu. Một plan tốt cho tenant nhỏ có thể rất tệ cho tenant cực lớn, hoặc ngược lại. Vấn đề nằm ở data skew và plan choice chứ không nhất thiết do thiếu index.

**Ví dụ:**
```sql
SELECT *
FROM Orders
WHERE TenantId = @tenantId
  AND Status = @status;
```

Nếu `TenantId = 1` có 10 triệu row còn tenant khác chỉ vài nghìn, cùng một plan không phải lúc nào cũng tối ưu. Hãy so sánh actual execution plan, estimated rows và actual rows cho các parameter đại diện.

**Lưu ý:**
`OPTION (RECOMPILE)` có thể giải quyết một số trường hợp nhưng đổi CPU compile lấy plan tốt hơn mỗi lần chạy. Không nên dùng như default. Với SQL Server mới, Parameter Sensitive Plan optimization có thể giúp, nhưng vẫn cần xác nhận bằng evidence thay vì giả định engine tự xử lý mọi skew.

### Tip 3 — Azure Blob upload lớn: cân nhắc direct upload bằng User Delegation SAS thay vì proxy toàn bộ qua API

**Mẹo:**
Khi browser/mobile cần upload file lớn, backend có thể cấp short-lived User Delegation SAS để client upload trực tiếp vào Azure Blob Storage thay vì stream toàn bộ file qua ASP.NET Core API.

**Tại sao hữu ích:**
Proxy file qua backend làm application chịu thêm bandwidth, connection lifetime và memory/buffer pressure. Direct upload giảm tải compute layer và thường scale tốt hơn, trong khi backend vẫn kiểm soát container, blob path, permission và expiry của SAS.

**Ví dụ:**
```text
1. Client gọi POST /uploads/request
2. Backend authorize user
3. Backend dùng Managed Identity tạo User Delegation SAS chỉ cho blob cụ thể
4. Client upload trực tiếp lên Blob Storage
5. Client/backend xác nhận upload hoàn tất
```

SAS chỉ nên có quyền cần thiết như `Create`/`Write` và TTL ngắn.

**Lưu ý:**
Direct upload không có nghĩa bỏ validation. Backend vẫn cần policy về size/type, naming, lifecycle và có thể cần quarantine/scanning sau upload. Không cấp account SAS quyền rộng cho client nếu User Delegation SAS đáp ứng được use case.

### Tip 4 — Dùng `WebApplicationFactory` để integration test ASP.NET Core ở đúng middleware/routing pipeline

**Mẹo:**
Với behavior phụ thuộc authentication, middleware, routing, filters hoặc serialization, dùng `WebApplicationFactory<TEntryPoint>` thay vì chỉ unit test controller/service riêng lẻ.

**Tại sao hữu ích:**
Nhiều bug production không nằm trong method business logic mà nằm ở wiring: middleware sai thứ tự, endpoint không map, auth policy sai, JSON options khác kỳ vọng hoặc dependency registration thiếu. Integration test chạy qua HTTP pipeline giúp bắt đúng lớp lỗi này.

**Ví dụ:**
```csharp
await using var factory = new WebApplicationFactory<Program>();
var client = factory.CreateClient();

var response = await client.GetAsync("/api/orders/42");

response.StatusCode.Should().Be(HttpStatusCode.OK);
```

Có thể override service/database cho test environment nhưng vẫn giữ phần lớn application bootstrap thật.

**Lưu ý:**
Đừng biến mọi test thành integration test; chúng chậm hơn và khó cô lập hơn unit test. Giữ số lượng đủ để bảo vệ boundary quan trọng, còn domain logic thuần vẫn nên test ở tầng nhỏ hơn.

### Tip 5 — Khi dùng AI coding agent, yêu cầu diff tối thiểu và cấm “cleanup tiện tay” ngoài scope

**Mẹo:**
Với task sửa bug hoặc thay đổi production code, yêu cầu agent chỉ sửa các file cần thiết, không refactor diện rộng, không đổi naming/style unrelated và phải giải thích từng thay đổi ngoài scope nếu thực sự bắt buộc.

**Tại sao hữu ích:**
AI agent thường có xu hướng “improve” code xung quanh. Diff lớn làm review khó hơn, tăng regression surface và che khuất thay đổi business quan trọng. Một patch nhỏ, có evidence và test rõ ràng dễ đánh giá correctness hơn nhiều.

**Ví dụ:**
```text
Constraint cho agent:
- giữ public contract hiện tại
- không thêm package nếu chưa cần thiết
- không đổi unrelated files
- sửa root cause tối thiểu
- chạy targeted tests + build
- báo rõ file nào thay đổi và vì sao
```

Nếu patch vượt phạm vi, yêu cầu agent tách thành đề xuất riêng thay vì trộn vào fix hiện tại.

**Lưu ý:**
“Diff nhỏ” không được biến thành lý do né refactor bắt buộc để sửa đúng root cause. Mục tiêu là kiểm soát scope, không phải giữ code xấu bằng mọi giá. Senior review cần phân biệt minimal safe change với superficial patch.

## 🧠 Software Design

### Design 1 — Distributed Lock cần fencing token nếu stale owner vẫn có thể ghi dữ liệu

**Khái niệm:**
Distributed lock chỉ nói ai đang được coi là owner tại một thời điểm. Với hệ thống có pause, network delay hoặc lease expiry, một owner cũ vẫn có thể tỉnh lại và tiếp tục ghi. Fencing token thêm một sequence tăng dần để downstream từ chối operation đến từ owner cũ.

**Vấn đề nó giải quyết:**
Worker A acquire lease rồi bị pause 60 giây. Lease hết hạn, worker B acquire lock mới và bắt đầu xử lý. Sau đó A tiếp tục chạy và ghi dữ liệu. Nếu chỉ kiểm tra “đã từng acquire lock”, cả A và B đều có thể tạo side effect.

**Ví dụ thực tế:**
```text
A acquires lock -> token 41
A pauses
B acquires lock -> token 42
B writes with token 42 -> accepted
A resumes, writes with token 41 -> rejected as stale
```

Storage/resource nhận write phải nhớ token cao nhất hoặc có versioning tương đương.

**Trade-off:**
Fencing token tăng correctness trong failure mode lease expiry nhưng yêu cầu resource downstream tham gia kiểm tra token. Nếu resource không hỗ trợ conditional write/version check, lock đơn thuần vẫn có race. Với workload đơn giản, database unique constraint hoặc idempotent command có thể rẻ hơn distributed lock.

**Middle → Senior insight:**
Middle developer cần hiểu “acquire lock thành công” không đảm bảo exclusive ownership mãi mãi. Senior / Technical developer phải reasoning về lease expiry, process pause, stale writer và chọn cơ chế correctness ở storage boundary thay vì chỉ tin vào lock provider.

### Design 2 — CQRS không bắt buộc phải có hai database

**Khái niệm:**
CQRS tách command model và query model theo trách nhiệm, nhưng mức tách có thể chỉ nằm ở code/application layer. Không cần tự động triển khai separate read database, event bus hay eventual consistency chỉ để được gọi là CQRS.

**Vấn đề nó giải quyết:**
Một application có write flow giàu invariant nhưng read flow chủ yếu projection/reporting. Ép cả hai dùng cùng domain model có thể tạo query phức tạp hoặc làm domain model bị méo để phục vụ UI.

**Ví dụ thực tế:**
```text
Command:
CancelOrderHandler
-> load aggregate
-> validate invariant
-> SaveChanges

Query:
GetOrderSummary
-> EF Core projection trực tiếp DTO
-> cùng một database
```

Chỉ khi read scale, latency hoặc ownership thực sự khác biệt mới cân nhắc read store riêng.

**Trade-off:**
CQRS ở mức code có thể cải thiện clarity mà chi phí thấp. Tách database/read model riêng giúp scale và tối ưu độc lập nhưng thêm synchronization, eventual consistency, replay và operational complexity. Không nên nhảy thẳng tới full event-driven CQRS nếu bài toán chưa cần.

**Middle → Senior insight:**
Middle developer cần hiểu command và query có thể có model khác nhau. Senior / Solution-oriented engineer phải chọn mức độ tách dựa trên complexity, scale và consistency requirement, không dựa trên pattern purity.

### Design 3 — Strangler Fig phù hợp khi modernize legacy system theo từng capability

**Khái niệm:**
Strangler Fig migration thay thế legacy system từng phần bằng cách route dần capability sang implementation mới, thay vì rewrite toàn bộ rồi cutover một lần.

**Vấn đề nó giải quyết:**
Một .NET Framework application lớn có nhiều module, integration và business rule ít tài liệu. Full rewrite trong một dự án dài tạo risk rất cao: business thay đổi trong lúc rewrite, parity khó chứng minh và cutover cuối cùng trở thành một “big bang”.

**Ví dụ thực tế:**
```text
Legacy IIS app
   |
   +-- /customers/* -> ASP.NET Core module mới
   +-- /orders/*    -> legacy hiện tại
   +-- /reports/*   -> legacy hiện tại

Sau khi Customers ổn định:
- chuyển Orders
- giảm dependency ngược về legacy
- retire capability cũ dần dần
```

Có thể dùng reverse proxy/API gateway hoặc routing layer để chuyển traffic theo capability.

**Trade-off:**
Strangler giảm cutover risk và cho phép tạo value sớm, nhưng trong giai đoạn chuyển tiếp phải vận hành hai thế giới, xử lý data synchronization, identity và duplicated integration. Nếu boundary legacy quá rối, bước đầu tiên có thể là tạo facade/ACL thay vì migrate ngay.

**Middle → Senior insight:**
Middle developer cần giữ behavior compatibility và test regression khi tách capability. Senior / Technical developer phải chọn migration seam, data ownership, rollback strategy và thứ tự module sao cho giảm coupling dần thay vì tạo một legacy mới bên cạnh legacy cũ.
