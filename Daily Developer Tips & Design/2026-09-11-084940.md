# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` cho bulk update khi không cần materialize entity

**Mẹo:**
Với EF Core, nếu cần cập nhật nhiều row theo cùng một rule và không cần chạy domain logic trên từng entity, cân nhắc `ExecuteUpdateAsync` thay vì `ToListAsync` rồi sửa từng object.

**Tại sao hữu ích:**
Materialize hàng nghìn entity làm tăng allocation, change-tracking cost và số lượng dữ liệu phải truyền từ database về application. `ExecuteUpdateAsync` dịch update thành SQL chạy trực tiếp tại database và thường chỉ cần một round trip.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now), ct);
```

Operation này phù hợp với batch maintenance hoặc state transition đơn giản có thể biểu diễn hoàn toàn bằng SQL.

**Lưu ý:**
`ExecuteUpdateAsync` không đi qua change tracker và không tự chạy domain event, entity callback hoặc logic bạn thường thực hiện sau khi load entity. Nếu invariant phụ thuộc behavior trong aggregate, bulk update có thể bypass rule quan trọng.

### Tip 2 — Dùng `git bisect` để tìm commit gây regression thay vì checkout thủ công từng phiên bản

**Mẹo:**
Khi biết một phiên bản cũ còn tốt và phiên bản hiện tại bị lỗi, dùng `git bisect` để binary-search commit đầu tiên gây regression.

**Tại sao hữu ích:**
Nếu có hàng trăm commit giữa trạng thái good và bad, kiểm tra tuần tự rất tốn thời gian. `git bisect` giảm số lần kiểm tra xuống gần `log2(n)` và biến việc tìm regression thành quy trình có thể lặp lại.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# chạy test tại commit Git chọn
git bisect good   # hoặc: git bisect bad

# khi hoàn tất
git bisect reset
```

Nếu có test tự động tái hiện lỗi, có thể dùng `git bisect run ./scripts/regression-test.sh` để tự động hóa toàn bộ quá trình.

**Lưu ý:**
Một số commit trung gian có thể không build được. Khi đó dùng `git bisect skip`, nhưng quá nhiều commit không kiểm thử được sẽ làm kết luận kém chính xác hơn.

### Tip 3 — Với MongoDB compound index, kiểm tra thứ tự field theo Equality → Sort → Range

**Mẹo:**
Khi thiết kế compound index cho MongoDB, bắt đầu từ access pattern thực tế và kiểm tra quy tắc ESR: field equality thường đứng trước, tiếp theo là sort, rồi mới tới range khi phù hợp.

**Tại sao hữu ích:**
Một index chứa đúng các field nhưng sai thứ tự vẫn có thể khiến query scan nhiều key hoặc phải sort in-memory. Prefix của compound index quyết định phần nào của index có thể được tận dụng hiệu quả.

**Ví dụ:**
```javascript
// Query
// tenantId = equality
// createdAt = sort
// total > 100 = range

db.orders.createIndex({ tenantId: 1, createdAt: -1, total: 1 })

db.orders.find({
  tenantId: "tenant-42",
  total: { $gt: 100 }
}).sort({ createdAt: -1 }).explain("executionStats")
```

Khi review `executionStats`, so sánh `totalKeysExamined`, `totalDocsExamined` và số document thực sự trả về.

**Lưu ý:**
ESR là heuristic chứ không phải luật tuyệt đối. Selectivity, `$in`, range lớn, sort direction và workload ghi đều có thể làm thứ tự index tối ưu thay đổi; hãy xác nhận bằng `explain()` trên dữ liệu gần production.

### Tip 4 — Tạo custom span bằng `ActivitySource` để trace đoạn business logic mà auto-instrumentation không thấy

**Mẹo:**
Trong .NET observability, dùng `ActivitySource` cho operation quan trọng nằm giữa các span HTTP/database mặc định, ví dụ pricing calculation, cache fallback hoặc batch processing.

**Tại sao hữu ích:**
Auto-instrumentation thường cho biết request gọi SQL hay HTTP dependency nào, nhưng không giải thích thời gian bị tiêu tốn trong một bước business nội bộ. Custom span đúng chỗ giúp trace trả lời “đoạn nào của use case chậm” mà không cần thêm log timing thủ công khắp codebase.

**Ví dụ:**
```csharp
private static readonly ActivitySource Source = new("Nexora.Orders");

using var activity = Source.StartActivity("orders.calculate-total");
activity?.SetTag("pricing.rule_set", ruleSetVersion);

var total = pricingService.Calculate(order);
```

Khi OpenTelemetry listener được cấu hình, span này có thể xuất hiện cùng trace với ASP.NET Core request và dependency spans.

**Lưu ý:**
Không đưa user ID, email, token hoặc dữ liệu có cardinality cực cao vào tag một cách tùy tiện. Instrumentation tốt phải cân bằng diagnostic value, telemetry cost và privacy.

### Tip 5 — Khi dùng Azure Service Bus `PeekLock`, thiết kế xử lý theo lock duration chứ không chỉ theo timeout của handler

**Mẹo:**
Nếu consumer dùng `PeekLock`, đảm bảo thời gian xử lý, auto lock renewal và retry policy tương thích với nhau. Handler chạy lâu hơn lock có thể khiến message được giao lại khi lần xử lý đầu vẫn đang tiếp tục.

**Tại sao hữu ích:**
`PeekLock` không xóa message ngay khi nhận. Consumer phải complete trước khi lock hết hạn hoặc gia hạn lock đủ lâu. Nếu lock bị mất, cùng message có thể xuất hiện ở consumer khác, tạo duplicate side effect dù code ban đầu chưa hề throw.

**Ví dụ:**
```text
Lock duration: 60s
Handler processing: 95s
Auto-renew: disabled

T=0s   Consumer A nhận message
T=60s  Lock hết hạn
T=70s  Consumer B nhận lại message
T=95s  Consumer A vẫn cố commit side effect
```

Giải pháp thường gồm rút ngắn handler, cấu hình lock renewal hợp lý và làm side effect idempotent.

**Lưu ý:**
Tăng lock duration vô hạn không phải giải pháp tổng quát. Long-running workload đôi khi nên được tách thành durable job/workflow thay vì giữ một broker message lock quá lâu.

## 🧠 Software Design

### Design 1 — CQRS nên bắt đầu từ read/write model khác nhau, không phải từ hai hệ thống riêng biệt

**Khái niệm:**
CQRS tách model phục vụ command khỏi model phục vụ query khi hai phía có nhu cầu khác nhau. Sự tách biệt này có thể chỉ nằm ở code/query model trong cùng application và database; không bắt buộc phải có microservices, event sourcing hoặc hai datastore ngay từ đầu.

**Vấn đề nó giải quyết:**
Một domain model giàu invariant thường không phù hợp để phục vụ dashboard, search hoặc projection nhiều bảng. Ngược lại, ép write path dùng DTO/query shape của UI có thể làm business model bị méo theo nhu cầu đọc.

**Ví dụ thực tế:**
```text
Write side:
CompleteProjectCommand
-> load Project aggregate
-> validate task states
-> enforce invariant
-> commit transaction

Read side:
ProjectDashboardQuery
-> SELECT/projection trực tiếp thành ProjectDashboardDto
-> không cần reconstruct aggregate
```

Có thể giữ cả hai trong cùng ASP.NET Core application và cùng SQL database cho tới khi scale hoặc ownership thực sự yêu cầu tách xa hơn.

**Trade-off:**
CQRS giúp read model tối ưu theo consumer và giữ write model tập trung vào invariant, nhưng tăng số model, mapping và consistency concern. Nếu CRUD đơn giản và read/write shape gần nhau, CQRS đầy đủ chỉ tạo thêm ceremony.

**Middle → Senior insight:**
Middle developer cần hiểu command và query có mục tiêu khác nhau, tránh reuse entity như universal DTO. Senior / Technical developer phải quyết định mức độ tách dựa trên domain complexity, read scale, consistency requirement và operational cost — không đồng nhất CQRS với distributed architecture.

### Design 2 — Optimistic vs Pessimistic Concurrency phải chọn theo xác suất conflict và chi phí giữ lock

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor làm việc song song rồi phát hiện conflict khi commit, thường bằng version/rowversion. Pessimistic concurrency giữ lock sớm để ngăn actor khác thay đổi cùng resource trong critical section.

**Vấn đề nó giải quyết:**
Hai request cùng sửa một record có thể gây lost update hoặc vi phạm invariant. Tuy nhiên khóa resource quá sớm lại giảm throughput và tăng blocking/deadlock risk, nên concurrency strategy phải phù hợp với contention thực tế.

**Ví dụ thực tế:**
```text
Profile editing:
- conflict hiếm
- dùng rowversion + retry/409 Conflict

Limited inventory allocation:
- contention cao trong flash sale
- có thể cần atomic database operation hoặc lock/serialization mạnh hơn
```

Điểm quan trọng là bảo vệ invariant ở nơi dữ liệu được commit, không chỉ disable nút trên UI.

**Trade-off:**
Optimistic concurrency scale tốt khi conflict hiếm nhưng caller phải xử lý retry/merge/conflict UX. Pessimistic locking đơn giản hóa một số critical section nhưng giữ resource lâu hơn, giảm concurrency và có thể tạo deadlock.

**Middle → Senior insight:**
Middle developer cần biết phát hiện `DbUpdateConcurrencyException` hoặc conflict tương đương và không âm thầm overwrite dữ liệu. Senior / Technical developer phải định lượng contention, transaction duration, retry cost và business invariant để chọn cơ chế concurrency phù hợp cho từng use case.

### Design 3 — Backpressure là một phần của kiến trúc, không phải chỉ là tăng queue capacity

**Khái niệm:**
Backpressure là cơ chế buộc producer giảm tốc, bị giới hạn hoặc nhận tín hiệu overload khi consumer không xử lý kịp. Mục tiêu là giữ hệ thống trong capacity envelope thay vì để backlog tăng vô hạn.

**Vấn đề nó giải quyết:**
Nếu API có thể enqueue 20.000 job/giây nhưng worker chỉ xử lý 5.000 job/giây, queue sẽ tăng liên tục. Latency của job, storage cost và recovery time đều xấu đi; cuối cùng hệ thống có thể fail ở một điểm khó kiểm soát hơn.

**Ví dụ thực tế:**
```text
Ingress: 20k jobs/s
Worker capacity: 5k jobs/s

Không có backpressure:
-> backlog +15k/s
-> queue delay tăng không giới hạn

Có backpressure:
-> giới hạn admission
-> trả 429/503 hoặc defer producer
-> autoscale trong giới hạn đã định
-> cảnh báo theo queue age, không chỉ queue length
```

Với asynchronous pipeline, `oldest message age` thường phản ánh trải nghiệm thực tế tốt hơn chỉ nhìn số message đang chờ.

**Trade-off:**
Backpressure bảo vệ dependency và giữ failure có kiểm soát, nhưng đồng nghĩa một phần request phải bị delay hoặc reject khi quá tải. Queue lớn có thể hấp thụ burst ngắn, song dùng queue như capacity vô hạn chỉ trì hoãn incident.

**Middle → Senior insight:**
Middle developer cần hiểu bounded channel, queue limit và retry có thể tạo hoặc giảm pressure như thế nào. Senior / Technical developer phải thiết kế admission control, capacity budget, autoscaling signal, overload response và SLO cho cả synchronous lẫn asynchronous path.
