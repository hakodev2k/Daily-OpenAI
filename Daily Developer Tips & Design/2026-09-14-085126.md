# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure thay vì để queue trong memory tăng vô hạn

**Mẹo:**
Khi một `BackgroundService` nhận work nhanh hơn tốc độ xử lý, dùng bounded `Channel<T>` với capacity rõ ràng thay vì `ConcurrentQueue<T>` tăng không giới hạn. Khi queue đầy, producer có thể chờ, drop theo policy hoặc trả tín hiệu overload.

**Tại sao hữu ích:**
Một queue in-memory không giới hạn có thể che giấu bottleneck trong thời gian ngắn nhưng cuối cùng chuyển overload thành memory pressure, GC tăng mạnh hoặc OutOfMemory. Bounded channel biến capacity thành một phần rõ ràng của design và buộc hệ thống thể hiện backpressure sớm hơn.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, ct);
```

Worker đọc từ `channel.Reader.ReadAllAsync(stoppingToken)` với concurrency được kiểm soát thay vì spawn task không giới hạn.

**Lưu ý:**
In-memory `Channel<T>` không durable: process restart sẽ mất các item chưa xử lý. Nếu work phải survive restart hoặc cần retry/visibility timeout, message broker hay persistent job store thường phù hợp hơn. Capacity cũng phải dựa trên throughput và memory budget chứ không chọn tùy ý.

### Tip 2 — Khi gặp SQL deadlock, đọc deadlock graph trước khi đổi isolation level

**Mẹo:**
Nếu SQL Server báo deadlock, thu thập deadlock graph hoặc Extended Events để xác định transaction nào giữ lock, transaction nào chờ lock và thứ tự resource bị acquire. Đừng phản xạ bằng cách tăng timeout hoặc chuyển isolation level ngay lập tức.

**Tại sao hữu ích:**
Deadlock là một chu trình chờ lock, không chỉ là “query chậm”. Hai transaction đều có thể nhanh khi chạy riêng nhưng deadlock khi acquire cùng các resource theo thứ tự khác nhau. Evidence từ graph giúp tìm đúng statement, index, lock mode và transaction boundary gây chu trình.

**Ví dụ:**
```text
Transaction A:
1. UPDATE Orders
2. UPDATE Inventory

Transaction B:
1. UPDATE Inventory
2. UPDATE Orders
```

Nếu hai flow chạy đồng thời, mỗi transaction có thể giữ một resource và chờ resource còn lại. Một hướng sửa là chuẩn hóa thứ tự access `Orders -> Inventory` cho cả hai flow nếu business flow cho phép.

**Lưu ý:**
Retry deadlock victim có thể cần thiết vì SQL Server chủ động hủy một transaction, nhưng retry chỉ xử lý symptom nếu contention lặp lại liên tục. Index thiếu, transaction quá dài, scan quá rộng hoặc application giữ transaction qua network call cũng cần được xem xét.

### Tip 3 — Với Azure App Service deployment slot, kiểm tra warm-up và slot setting trước khi swap

**Mẹo:**
Khi dùng staging slot để deploy ASP.NET Core, xác nhận application đã warm-up, health check thành công và các setting môi trường đúng trước khi swap sang production. Những configuration chỉ thuộc từng slot nên được đánh dấu deployment slot setting.

**Tại sao hữu ích:**
Swap giúp giảm downtime nhưng không tự đảm bảo application đã sẵn sàng. Nếu app còn chạy migration nặng, lazy-load dependency hoặc staging đang dùng nhầm production-specific configuration, swap có thể biến một deployment “thành công” thành 5xx ngay sau cutover.

**Ví dụ:**
```text
Deploy staging
-> startup
-> warm-up critical endpoint
-> health check PASS
-> smoke test DB / external dependency
-> swap staging -> production
-> quan sát error rate + latency
```

Các giá trị như environment-specific secret reference hoặc endpoint cần giữ nguyên theo slot phải được cấu hình đúng sticky setting.

**Lưu ý:**
Deployment slot không thay thế backward-compatible database migration. Nếu code mới yêu cầu schema mới không tương thích với version cũ, rollback bằng swap vẫn có thể thất bại. Luôn xem application version và database version như hai phần của cùng release strategy.

### Tip 4 — Không tin `Content-Type` hoặc extension khi validate file upload

**Mẹo:**
Với endpoint upload, coi filename, extension và `Content-Type` do client gửi là dữ liệu không tin cậy. Validate size, allowed format, magic bytes/signature khi phù hợp, lưu file ngoài executable path và tạo tên storage riêng thay vì dùng filename gốc làm path.

**Tại sao hữu ích:**
Client có thể upload file thực thi nhưng đặt tên `.jpg` hoặc gửi header `image/jpeg`. Nếu backend chỉ kiểm tra metadata từ request, file độc hại có thể vượt validation và được lưu/phục vụ lại theo cách nguy hiểm.

**Ví dụ:**
```text
Upload avatar:
- giới hạn 5 MB
- allow JPEG/PNG
- kiểm tra signature thực tế
- decode/re-encode ảnh nếu requirement cho phép
- generate blob key mới
- lưu original filename chỉ như metadata đã sanitize
```

Nếu file cần download lại, response nên đặt header phù hợp và tránh để browser thực thi nội dung ngoài ý muốn.

**Lưu ý:**
Magic-byte validation không phát hiện mọi malware. Với tài liệu hoặc file từ user không tin cậy, có thể cần antivirus/content scanning và quarantine workflow. Đừng parse file phức tạp trong request thread nếu parser tốn CPU hoặc có attack surface lớn.

### Tip 5 — Dùng mutation testing để phát hiện test “xanh nhưng không bảo vệ behavior”

**Mẹo:**
Khi một module quan trọng có code coverage cao nhưng vẫn thường regression, thử mutation testing trên phạm vi nhỏ. Tool sẽ cố ý thay đổi logic như `>` thành `>=`, đảo boolean hoặc bỏ branch rồi kiểm tra test có fail hay không.

**Tại sao hữu ích:**
Coverage chỉ nói test đã đi qua dòng code; nó không chứng minh assertion đủ mạnh để phát hiện behavior sai. Nếu một mutation sống sót, test suite có thể đang execute code nhưng không thực sự verify invariant quan trọng.

**Ví dụ:**
```csharp
if (balance >= amount)
{
    Approve();
}
```

Mutation:
```csharp
if (balance > amount)
{
    Approve();
}
```

Nếu test vẫn pass, có thể thiếu case `balance == amount` dù line coverage vẫn 100%.

**Lưu ý:**
Mutation testing tốn CPU và có thể tạo nhiều noise nếu chạy toàn solution. Dùng có mục tiêu cho domain logic, validation, pricing hoặc authorization quan trọng. Mutation score cũng không nên trở thành KPI máy móc; mục tiêu là tìm lỗ hổng trong test reasoning.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation để một dependency lỗi không ăn hết capacity của cả service

**Khái niệm:**
Bulkhead Isolation chia capacity như concurrency, connection, queue hoặc worker pool theo workload/dependency để một loại công việc bị chậm không chiếm hết resource dùng chung. Ý tưởng tương tự khoang kín trên tàu: một vùng hỏng không làm toàn hệ thống chìm ngay.

**Vấn đề nó giải quyết:**
Một API gọi ba downstream service. Search provider đột nhiên latency 10 giây. Nếu tất cả outbound call dùng cùng concurrency không giới hạn, request search có thể chiếm phần lớn socket/task/request capacity và làm cả endpoint không liên quan cũng timeout.

**Ví dụ thực tế:**
```text
Search dependency:
- max 40 concurrent calls
- queue 100

Payment dependency:
- max 20 concurrent calls
- queue nhỏ, ưu tiên fail fast

Internal DB workload:
- connection pool độc lập theo datasource
```

Khi Search chậm, request của Search bị giới hạn trước khi nó chiếm toàn bộ capacity của Payment hoặc core API path.

**Trade-off:**
Bulkhead tăng failure isolation và predictable capacity nhưng có thể làm resource bị “nhàn rỗi” ở một partition trong khi partition khác overload. Chia quá nhỏ còn làm throughput tổng giảm. Capacity phải được điều chỉnh theo SLO, workload và downstream behavior thực tế.

**Middle → Senior insight:**
Middle developer cần hiểu rằng timeout/retry không kiểm soát được bao nhiêu operation đang đồng thời tiêu resource. Senior / Technical developer phải xác định isolation boundary, concurrency budget, queue policy và priority dựa trên blast radius thay vì dùng một global semaphore cho toàn application.

### Design 2 — Saga dùng compensation khi một business transaction trải qua nhiều hệ thống độc lập

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction. Nếu bước sau thất bại, hệ thống thực hiện compensating action phù hợp thay vì cố giữ một ACID transaction xuyên nhiều service/database.

**Vấn đề nó giải quyết:**
Workflow đặt hàng có thể cần reserve inventory, authorize payment và tạo shipment. Các hệ thống này không chia sẻ cùng database transaction. Nếu payment thành công nhưng shipment thất bại, application cần một trạng thái recoverable thay vì giả định rollback kỹ thuật có thể hoàn tác mọi side effect bên ngoài.

**Ví dụ thực tế:**
```text
1. Create Order
2. Reserve Inventory
3. Authorize Payment
4. Create Shipment -> FAIL

Compensation:
5. Void Payment Authorization
6. Release Inventory
7. Mark Order = Failed/RequiresReview
```

Mỗi bước cần idempotency và state transition rõ để chịu retry hoặc duplicate message.

**Trade-off:**
Saga giúp workflow phân tán có recovery model rõ nhưng tăng state machine, eventual consistency, retry và observability complexity. Compensation cũng không phải lúc nào là “undo” hoàn hảo; email đã gửi hoặc giao dịch bên ngoài đã settlement có thể cần quy trình nghiệp vụ khác.

**Middle → Senior insight:**
Middle developer cần model từng step và compensation rõ ràng, không dùng `try/catch` như thể mọi side effect có thể rollback. Senior / Solution-oriented engineer phải quyết định orchestration hay choreography, timeout, manual intervention, audit trail và invariant nào có thể tạm thời bị phá vỡ trong eventual consistency window.

### Design 3 — Architecture Decision Record nên ghi quyết định và constraint, không biến thành tài liệu kiến trúc khổng lồ

**Khái niệm:**
Architecture Decision Record (ADR) là bản ghi ngắn cho một quyết định kỹ thuật có ảnh hưởng đáng kể: context, lựa chọn, quyết định, lý do và consequence. Nó giúp giữ lại “tại sao” khi code chỉ cho thấy “đã làm gì”.

**Vấn đề nó giải quyết:**
Sáu tháng sau, team thấy hệ thống dùng PostgreSQL nhưng không biết vì sao không chọn Cosmos DB, hoặc thấy một module cố tình không tách microservice rồi tưởng đó là technical debt. Thiếu context khiến team dễ lặp lại tranh luận cũ hoặc phá constraint quan trọng.

**Ví dụ thực tế:**
```text
ADR-012: Giữ Orders và Payments trong Modular Monolith ở Release 1

Context:
- 1 team sở hữu cả hai capability
- transaction consistency quan trọng
- traffic chưa cần scale độc lập

Decision:
- cùng deployable, boundary module rõ

Revisit when:
- ownership tách team
- scale profile diverges
- release cadence độc lập trở thành bottleneck
```

ADR nên liên kết tới evidence hoặc metric quan trọng thay vì kể lại toàn bộ hệ thống.

**Trade-off:**
ADR tăng khả năng hiểu và review decision nhưng trở thành noise nếu ghi mọi chi tiết nhỏ hoặc không cập nhật trạng thái khi quyết định bị supersede. Tài liệu quá dài cũng làm người đọc bỏ qua; giá trị nằm ở decision context và consequence đủ rõ.

**Middle → Senior insight:**
Middle developer cần biết đọc ADR trước khi thay boundary hoặc pattern quan trọng. Senior / Technical developer phải biến trade-off thành quyết định có điều kiện, nêu trigger để revisit và chấp nhận consequence rõ ràng thay vì chỉ ghi “chọn công nghệ X vì best practice”.
