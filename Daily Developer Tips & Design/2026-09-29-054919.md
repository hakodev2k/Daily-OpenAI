# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong .NET

**Mẹo:**
Khi ASP.NET Core latency tăng mạnh nhưng CPU chưa cao, kiểm tra ThreadPool queue, thread count và blocking calls trước khi scale CPU. `async` chỉ giúp khi call chain thực sự không block thread trong lúc chờ I/O.

**Tại sao hữu ích:**
Nếu request dùng `.Result`, `.Wait()` hoặc synchronous I/O trên hot path, worker threads bị giữ trong lúc chờ. Request mới xếp hàng, ThreadPool phải tăng thread dần và p95/p99 có thể tăng dù CPU còn dư.

**Ví dụ:**
Một endpoint gọi HTTP bằng `client.GetAsync(url).Result`. Sau deployment, traffic tăng và request duration nhảy từ 200 ms lên vài giây trong khi CPU chỉ 45%. Trace cho thấy outbound call chờ I/O; runtime metrics cho thấy ThreadPool queue tăng. Chuyển toàn call chain sang `await` xử lý đúng nguyên nhân thay vì tăng instance ngay lập tức.

**Lưu ý:**
Thread count cao không tự động chứng minh starvation. CPU-bound work cũng có thể làm queue tăng. Correlate runtime counters, CPU profile, request latency và blocking stacks trước khi kết luận.

### Tip 2 — Dùng savepoint/concurrency boundary thay vì kéo transaction qua external API

**Mẹo:**
Giữ database transaction ngắn và chỉ bao quanh state cần atomicity. Không mở EF Core transaction rồi chờ HTTP call, user interaction hoặc message broker nếu không có lý do consistency rõ ràng.

**Tại sao hữu ích:**
Transaction dài giữ locks và connection lâu hơn, tăng blocking/deadlock probability và làm connection pool chịu áp lực. Database transaction cũng không thể biến một REST API bên ngoài thành cùng một atomic resource.

**Ví dụ:**
Thay vì mở transaction → insert Order → gọi shipping API 4 giây → update Order → commit, hãy commit local state phù hợp trước rồi orchestration bước tiếp theo bằng trạng thái nghiệp vụ/Outbox khi workflow cho phép.

**Lưu ý:**
Không tách transaction mù quáng nếu invariant bắt buộc nhiều database writes phải atomic. Hãy xác định business invariant và failure recovery trước khi thay đổi boundary.

### Tip 3 — Azure Service Bus: xử lý lock expiration như một failure mode bình thường

**Mẹo:**
Nếu consumer xử lý message lâu, đo processing duration so với message lock và thiết kế renewal/idempotency thay vì giả định mỗi message chỉ chạy một lần.

**Tại sao hữu ích:**
Với peek-lock processing, consumer có thể mất lock trước khi complete. Message sau đó được delivery lại trong khi lần xử lý đầu đã tạo một phần side effect. Đây là lý do at-least-once delivery phải đi cùng duplicate-safe processing.

**Ví dụ:**
Worker xử lý export mất 90 giây nhưng lock thực tế ngắn hơn workload. Telemetry cho thấy delivery count tăng và hai file cùng được tạo. Giải pháp có thể là auto lock renewal phù hợp, chia nhỏ workload, hoặc lưu operation ID để side effect được deduplicate.

**Lưu ý:**
Tăng lock duration/renewal không chữa workload bị treo vô hạn. Cần timeout, cancellation, DLQ policy và metric cho processing duration, delivery count, lock-lost errors.

### Tip 4 — Contract test cho third-party API nên khóa assumptions quan trọng

**Mẹo:**
Với integration bên ngoài, test contract ở boundary mà code thực sự phụ thuộc: status codes, required fields, nullable behavior, enum evolution và authentication headers. Đừng mock một DTO lý tưởng rồi coi integration đã được test.

**Tại sao hữu ích:**
Third-party API có thể thêm enum value, trả field null trong edge case hoặc thay error payload mà compile-time checks của bạn không thấy. Boundary tests giúp assumptions trở nên executable.

**Ví dụ:**
Payment adapter deserialize fixture thực tế có `status: "pending_review"` mà enum cũ chưa biết. Test nên chứng minh client xử lý unknown value an toàn thay vì throw và biến một contract extension thành production 500.

**Lưu ý:**
Fixture test không chứng minh provider hiện tại vẫn đúng contract. Với integration quan trọng, kết hợp sandbox/smoke test có kiểm soát và monitoring production; tránh test phụ thuộc live service trong mọi CI run.

### Tip 5 — Vue/React: tránh duplicate fetch do component lifecycle không được kiểm soát

**Mẹo:**
Khi page phát nhiều request giống nhau, dùng Network waterfall và component lifecycle để xác định request được kích hoạt từ đâu trước khi thêm cache. Đặc biệt kiểm tra re-render/remount, watcher/effect dependencies và route transitions.

**Tại sao hữu ích:**
Duplicate fetch làm tăng backend load và có thể tạo race: response cũ về sau response mới rồi ghi đè state. Cache chỉ che triệu chứng nếu nguyên nhân là lifecycle hoặc dependency không ổn định.

**Ví dụ:**
Một search page gọi API trong effect phụ thuộc object filter được tạo mới mỗi render. Network tab cho thấy cùng query chạy nhiều lần. Chuẩn hóa dependency, debounce input và cancel request cũ giúp giảm traffic đồng thời tránh stale response cập nhật UI.

**Lưu ý:**
Đừng debounce mọi interaction. Với action cần phản hồi ngay hoặc mutation nghiệp vụ, debounce có thể thay đổi semantics. Phân biệt duplicate read, rapid user input và command có side effect.

## 🧠 Software Design

### Design 1 — Saga orchestration vs choreography cho workflow phân tán

**Khái niệm:**
Saga chia business transaction dài thành các local transactions và compensating actions. Orchestration có coordinator quyết định bước tiếp theo; choreography để services phản ứng với events mà không có một coordinator trung tâm.

**Vấn đề nó giải quyết:**
Order, payment và fulfillment nằm ở các service/database khác nhau nên không thể dựa vào một ACID transaction đơn giản. Khi payment thành công nhưng inventory reservation thất bại, hệ thống cần trạng thái và recovery semantics rõ ràng.

**Ví dụ thực tế:**
Order workflow có thể orchestrate: reserve inventory → authorize payment → confirm order; nếu bước cuối thất bại, coordinator yêu cầu release inventory/cancel authorization. Với flow đơn giản, services có thể choreography qua events, nhưng chuỗi dài dễ khó nhìn toàn bộ state machine.

**Trade-off:**
Orchestration làm workflow, timeout và compensation dễ quan sát hơn nhưng coordinator trở thành component quan trọng và có thể tập trung quá nhiều domain logic. Choreography giảm central coupling nhưng dễ tạo event chain khó truy vết, hidden dependencies và cyclic reactions.

**Middle → Senior insight:**
Middle developer cần hiểu idempotent handlers, compensation và eventual consistency. Senior / Technical developer phải chọn ownership của workflow, xác định irreversible steps, timeout/manual recovery và observability; không dùng Saga nếu một local transaction đơn giản vẫn đáp ứng invariant.

### Design 2 — SQL vs document database theo aggregate và query pressure

**Khái niệm:**
Chọn relational hay document storage từ consistency boundary, query patterns và evolution pressure, không từ khẩu hiệu “NoSQL scale tốt hơn”. Document model phù hợp khi dữ liệu thường được đọc/ghi như một aggregate; relational model mạnh khi relationships, constraints và ad-hoc joins là trọng tâm.

**Vấn đề nó giải quyết:**
Một schema normalized có thể cần nhiều joins cho read shape cố định, trong khi document hóa quá mức lại duplicate dữ liệu và làm cross-document consistency khó quản lý.

**Ví dụ thực tế:**
Product catalog có attributes thay đổi theo category và thường đọc nguyên product document có thể phù hợp MongoDB/Cosmos DB. Ledger/payment records cần constraints, transactions và reconciliation queries mạnh thường phù hợp relational database hơn.

**Trade-off:**
Document storage có thể đơn giản hóa aggregate reads và schema evolution nhưng denormalization tạo synchronization cost. SQL cung cấp constraints, joins và transactional semantics mạnh nhưng schema/query design vẫn phải được tối ưu cho workload.

**Middle → Senior insight:**
Middle developer cần model theo access pattern và hiểu index/transaction semantics của database đã chọn. Senior / Technical developer phải đánh giá data ownership, consistency, partition strategy, migration, operational expertise và cost; đôi khi một SQL database đủ tốt là lựa chọn ít rủi ro nhất.

### Design 3 — Observability là một phần của contract vận hành

**Khái niệm:**
Thiết kế observability nghĩa là xác định trước signals nào giúp chứng minh hệ thống đang đúng hoặc sai: structured logs, metrics, traces và business identifiers. Nó không phải việc “thêm logging” sau khi production có incident.

**Vấn đề nó giải quyết:**
Một distributed workflow có thể trả HTTP 202 thành công nhưng message bị backlog, consumer lỗi hoặc downstream processing kéo dài. Request logs riêng lẻ không trả lời được operation đang ở đâu và vì sao.

**Ví dụ thực tế:**
Flow import file gắn `operationId` xuyên API → Service Bus message → worker. Dashboard theo dõi accepted count, processing duration, failure/DLQ count và trace liên kết dependency. Khi SLA bị vi phạm, team có evidence để xác định queue backlog hay dependency chậm.

**Trade-off:**
Observability tốt giảm MTTR và làm SLO đo được, nhưng telemetry có storage/query cost, instrumentation overhead và privacy risk. Quá nhiều high-cardinality labels có thể làm metrics đắt hoặc khó vận hành.

**Middle → Senior insight:**
Middle developer cần propagate correlation context, log có cấu trúc và không ghi secrets/PII. Senior / Technical developer phải chọn telemetry theo failure modes và SLO, định nghĩa cardinality/retention/sampling, ownership dashboard/alerts và đảm bảo hệ thống có thể được vận hành chứ không chỉ chạy được.
