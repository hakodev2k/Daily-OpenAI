# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `ArrayPool<T>` chỉ đáng dùng khi allocation thực sự nằm trên hot path

**Mẹo:**
Khi profiling xác nhận large hoặc frequent temporary arrays gây allocation/GC pressure, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì tạo array mới cho mỗi operation.

**Tại sao hữu ích:**
Pooling tái sử dụng backing arrays nên giảm allocation rate và áp lực lên GC. Lợi ích rõ nhất ở serialization, parsing, compression hoặc streaming path có throughput cao; với request nhỏ và ít allocation, complexity bổ sung thường không đáng.

**Ví dụ:**
Một service xử lý binary payload liên tục cần temporary 64 KB buffer. Profiling cho thấy allocation rate và Gen 0 collections cao; chuyển buffer tạm sang `ArrayPool<byte>` rồi benchmark lại allocation, CPU và p99 latency trước khi giữ optimization.

**Lưu ý:**
Luôn `Return` buffer trong `finally`; buffer thuê có thể lớn hơn kích thước yêu cầu và chứa dữ liệu từ lần dùng trước. Không giữ reference sau khi trả pool và cân nhắc clear dữ liệu nhạy cảm khi cần.

### Tip 2 — SQL Server parameter sniffing không nên được “sửa” bằng `OPTION (RECOMPILE)` theo phản xạ

**Mẹo:**
Khi cùng một parameterized query lúc nhanh lúc chậm tùy input, kiểm tra actual execution plan, cardinality distribution và cached plan trước khi thêm hint.

**Tại sao hữu ích:**
Optimizer có thể compile plan dựa trên parameter values/cardinality assumptions không đại diện cho các lần chạy khác. Dữ liệu skew lớn khiến một plan tốt cho customer nhỏ trở nên rất tệ cho customer cực lớn.

**Ví dụ:**
Query lấy Orders theo `TenantId` chạy 20 ms cho hầu hết tenants nhưng vài giây cho tenant lớn. So sánh plans, estimated/actual rows, statistics và index access trước khi cân nhắc query rewrite, plan strategy hoặc targeted recompilation.

**Lưu ý:**
`OPTION (RECOMPILE)` đổi runtime cost lấy plan quality và làm giảm plan reuse; dùng bừa có thể tăng CPU. Đừng chẩn đoán parameter sniffing chỉ từ một slow query sample.

### Tip 3 — Application Insights sampling có thể làm sai cách đọc telemetry nếu không hiểu aggregation

**Mẹo:**
Khi production traffic lớn và telemetry được sampling, kiểm tra sampling configuration trước khi dùng raw event count để kết luận request/error volume.

**Tại sao hữu ích:**
Sampling giảm ingestion cost và telemetry volume nhưng một record quan sát được có thể đại diện cho nhiều operations. Nếu dashboard/query bỏ qua item count hoặc sampling semantics, incident analysis có thể đánh giá sai traffic và error frequency.

**Ví dụ:**
Sau deployment, engineer đếm trực tiếp số request records và nghĩ traffic giảm mạnh. Kiểm tra telemetry cho thấy adaptive sampling tăng; query/dashboard được sửa để dùng aggregation phù hợp và correlation/traces quan trọng vẫn được kiểm tra theo sampling behavior.

**Lưu ý:**
Không phải telemetry nào cũng nên sample giống nhau. Security/audit events hoặc rare critical failures có retention requirement khác high-volume request traces; thiết kế observability theo câu hỏi cần trả lời và cost budget.

### Tip 4 — Playwright locator nên dựa vào user-facing semantics thay vì DOM implementation

**Mẹo:**
Trong UI automation, ưu tiên role, accessible name, label hoặc stable test contract thay vì CSS chain dài và nth-child phụ thuộc layout.

**Tại sao hữu ích:**
Test bám DOM structure dễ vỡ khi refactor markup dù behavior người dùng không đổi. Semantic locator vừa gần cách user tương tác vừa khuyến khích accessibility tốt hơn, giảm flaky maintenance.

**Ví dụ:**
Thay selector `.checkout > div:nth-child(3) button.primary` bằng locator theo role `button` và accessible name `Place order`. Nếu có nhiều control giống nhau, scope theo region/form có semantics rõ.

**Lưu ý:**
Không biến `data-testid` thành mặc định cho mọi element; dùng nó khi UI không có semantic identifier ổn định. UI test vẫn phải chờ observable state, không thêm arbitrary sleep để chữa race condition.

### Tip 5 — Optimizely CMS publish path cần tránh synchronous integration chậm

**Mẹo:**
Nếu publish content phải đồng bộ search index, purge CDN hoặc gọi commerce/external APIs, tránh đặt toàn bộ remote work trực tiếp trên synchronous publish transaction khi business không yêu cầu completion tức thì.

**Tại sao hữu ích:**
Editor experience sẽ phụ thuộc latency/availability của downstream systems. Một integration timeout có thể làm publish chậm hoặc thất bại dù content storage khỏe, đồng thời tăng coupling giữa editorial workflow và infrastructure ngoài.

**Ví dụ:**
Sau khi content publish thành công, application phát durable event/job để cập nhật search index và purge delivery cache. UI hiển thị trạng thái propagation nếu cần; retry/dead-letter xử lý failure ngoài publish transaction.

**Lưu ý:**
Async propagation tạo eventual consistency. Với legal banner hoặc emergency content cần visibility ngay, phải xác định explicit completion/SLA thay vì áp cùng một strategy cho mọi content type.

## 🧠 Software Design

### Design 1 — CQRS không bắt buộc hai database hay Event Sourcing

**Khái niệm:**
CQRS tách read model và write model theo responsibility khi nhu cầu query và command khác nhau đáng kể. Mức tách có thể chỉ là handlers/models khác nhau trong cùng application và cùng database; Event Sourcing là một quyết định độc lập.

**Vấn đề nó giải quyết:**
Một domain write model giàu invariant thường không phải shape tối ưu cho reporting/search. Ép cả read và write đi qua cùng generic model có thể tạo query phức tạp hoặc làm domain model bị biến dạng vì nhu cầu UI.

**Ví dụ thực tế:**
Ordering commands thao tác aggregate qua EF Core, trong khi order-history screen dùng projection SQL tối ưu cho filtering/pagination. Hai paths vẫn dùng cùng SQL database ban đầu; chỉ tách storage khi scale, latency hoặc ownership evidence thực sự yêu cầu.

**Trade-off:**
CQRS tăng clarity khi read/write pressure khác biệt nhưng thêm models, mapping và consistency considerations. Với CRUD đơn giản, tách command/query layers quá mức chỉ tạo ceremony mà không giải quyết vấn đề thực tế.

**Middle → Senior insight:**
Middle developer cần hiểu separation theo behavior chứ không theo folder naming. Senior / Technical developer phải chọn mức CQRS tối thiểu đáp ứng complexity hiện tại và chỉ thêm asynchronous projection/separate stores khi operational evidence biện minh.

### Design 2 — Circuit Breaker bảo vệ recovery, không thay thế timeout

**Khái niệm:**
Circuit Breaker ngừng gửi requests tới dependency đang lỗi sau một threshold và thử phục hồi có kiểm soát. Timeout giới hạn thời gian của từng attempt; hai mechanisms giải quyết hai failure dimensions khác nhau.

**Vấn đề nó giải quyết:**
Khi dependency đang outage, tiếp tục gửi full traffic làm lãng phí connection/thread/concurrency budget và cản dependency phục hồi. Chỉ timeout vẫn cho phép mọi request tiếp tục đập vào hệ thống lỗi.

**Ví dụ thực tế:**
Recommendation service có timeout ngắn phù hợp latency budget; sau failure rate đủ cao, circuit mở và checkout bỏ qua recommendation trong thời gian ngắn. Half-open probes kiểm tra recovery trước khi khôi phục traffic bình thường.

**Trade-off:**
Circuit breaker tăng failure isolation nhưng threshold sai có thể mở circuit do transient spike hoặc giữ dependency healthy ngoài traffic lâu hơn cần thiết. Nó cần metrics, fallback semantics và tuning theo dependency/SLO.

**Middle → Senior insight:**
Middle developer cần phân biệt timeout, retry và circuit breaker. Senior / Technical developer phải thiết kế chúng như một resilience budget thống nhất để tránh retry amplification và bảo vệ end-to-end latency.

### Design 3 — Feature Flag cần lifecycle, nếu không sẽ trở thành permanent branching debt

**Khái niệm:**
Feature Flag tách code deployment khỏi feature release, cho phép gradual rollout, kill switch hoặc experiment. Nhưng flag là temporary runtime branch cần owner, expiry và removal plan.

**Vấn đề nó giải quyết:**
Release lớn có thể cần rollout theo percentage/tenant và rollback behavior nhanh mà không redeploy. Flag giảm blast radius, nhưng nhiều flags tồn tại lâu tạo combinatorial states khó test và code paths chết.

**Ví dụ thực tế:**
Checkout v2 được deploy disabled, mở cho internal users rồi 5%, 25%, 100% traffic dựa trên error/latency metrics. Khi rollout ổn định, team xóa old path và flag thay vì để hai implementations sống vô thời hạn.

**Trade-off:**
Feature flags tăng release control nhưng thêm configuration dependency, observability và test matrix. Permission/security decisions không nên chỉ dựa vào client-side flag; server vẫn phải enforce authorization.

**Middle → Senior insight:**
Middle developer cần viết flag branch có test cho cả on/off state và tránh duplicate logic. Senior / Technical developer phải phân loại release/ops/experiment flags, đặt ownership/expiry và tích hợp cleanup vào delivery process.
