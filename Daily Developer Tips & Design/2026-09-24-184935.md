# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — LOH allocation có thể làm memory tăng dù GC vẫn chạy bình thường

**Mẹo:**
Khi API xử lý payload hoặc buffer lớn và memory tăng theo traffic, kiểm tra Large Object Heap (LOH) allocation trước khi kết luận có memory leak. Tránh materialize các buffer lớn không cần thiết; ưu tiên streaming hoặc reuse buffer khi workload phù hợp.

**Tại sao hữu ích:**
Object lớn được cấp phát trên LOH và việc cấp phát liên tục có thể tạo GC pressure, fragmentation và pause cost. Một endpoint download/upload tạo nhiều `byte[]` lớn có thể gây vấn đề dù mọi object cuối cùng vẫn được collect.

**Ví dụ:**
Thay vì đọc file 200 MB hoàn toàn vào `byte[]` rồi trả response, stream từ Blob Storage tới response khi business flow không cần giữ toàn bộ nội dung trong memory. Dùng `dotnet-counters` hoặc profiler để quan sát allocation rate, heap size và GC trước khi sửa code.

**Lưu ý:**
Đừng dùng pooling hoặc `ArrayPool<T>` một cách máy móc; buffer thuê phải được trả đúng cách và dữ liệu nhạy cảm có thể cần được xóa. Memory cao cũng có thể đến từ cache, pinned objects hoặc native memory nên cần evidence từ profiler.

### Tip 2 — `ProblemDetails` nên là contract lỗi ổn định, không phải nơi leak exception

**Mẹo:**
Chuẩn hóa lỗi ASP.NET Core bằng `ProblemDetails` và machine-readable error code; giữ stack trace, SQL error và internal exception trong telemetry thay vì response public.

**Tại sao hữu ích:**
Frontend/mobile client cần contract có thể xử lý ổn định, còn exception message thường thay đổi theo implementation và có thể lộ schema, filesystem path hoặc thông tin nhạy cảm. Tách public error contract khỏi diagnostic detail giúp API vừa dễ tích hợp vừa an toàn hơn.

**Ví dụ:**
Response validation có thể chứa `type`, `title`, `status`, `traceId` và `errorCode: "ORDER_INVALID_STATE"`. Support dùng `traceId` để tìm distributed trace tương ứng thay vì trả nguyên `InvalidOperationException` cho client.

**Lưu ý:**
Không biến mọi lỗi thành HTTP 500. Mapping phải giữ đúng HTTP semantics: validation, authentication, authorization, conflict và not-found cần status phù hợp. Đồng thời tránh để client phụ thuộc vào human-readable `detail`.

### Tip 3 — Elasticsearch analyzer phải khớp giữa index-time và search-time intent

**Mẹo:**
Khi search trả kết quả thiếu hoặc relevance kỳ lạ, kiểm tra analyzer/token stream thay vì chỉ tăng fuzziness. Thiết kế mapping dựa trên cách dữ liệu được index và cách người dùng thực sự tìm kiếm.

**Tại sao hữu ích:**
Full-text search hoạt động trên tokens chứ không so sánh raw string như SQL equality. Lowercasing, stemming, synonym, edge n-gram hoặc language analyzer thay đổi token được lưu và token của query; mismatch có thể khiến document tồn tại nhưng không match như mong đợi.

**Ví dụ:**
Autocomplete cho product name có thể dùng field riêng với analyzer phù hợp thay vì áp wildcard `*term*` lên toàn bộ catalog. Dùng `_analyze` để xem `"Running Shoes"` được tokenize ra sao trước khi thay query DSL.

**Lưu ý:**
Thay analyzer của field hiện hữu thường đòi hỏi reindex để dữ liệu cũ có token mới. N-gram quá rộng làm index phình lớn và tăng indexing/search cost; relevance phải được kiểm thử bằng tập query đại diện.

### Tip 4 — Playwright test ổn định phải chờ trạng thái nghiệp vụ, không chờ thời gian cố định

**Mẹo:**
Trong E2E test, chờ element, response hoặc UI state có ý nghĩa thay vì `WaitForTimeout(3000)` để “cho trang chạy xong”.

**Tại sao hữu ích:**
Fixed sleep làm test vừa chậm vừa flaky: CI nhanh thì lãng phí 3 giây, CI chậm thì 3 giây vẫn chưa đủ. Condition-based waiting đồng bộ test với trạng thái thật của application.

**Ví dụ:**
Sau khi submit order, chờ confirmation heading hoặc API response liên quan rồi assert order number. Nếu UI có loading indicator, assert nó biến mất trước khi kiểm tra trạng thái cuối thay vì sleep một khoảng đoán trước.

**Lưu ý:**
Auto-wait của Playwright không thay thế mọi synchronization. Background polling, eventual consistency hoặc websocket update vẫn cần assertion/polling có timeout rõ ràng. Đừng tăng global timeout để che một race condition chưa hiểu.

### Tip 5 — Managed Identity giảm secret rotation nhưng không thay thế authorization design

**Mẹo:**
Trên Azure, ưu tiên Managed Identity cho application truy cập Key Vault, Blob Storage hoặc service hỗ trợ Microsoft Entra authentication thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Application không phải phân phối và rotate credential tĩnh. Azure quản lý identity credential, còn access được kiểm soát bằng RBAC hoặc policy phù hợp, giảm nguy cơ secret bị commit, log hoặc copy giữa environments.

**Ví dụ:**
App Service dùng system-assigned Managed Identity và `DefaultAzureCredential` để đọc secret cần thiết từ Key Vault; local development có thể dùng developer identity mà không nhét production credential vào `appsettings.json`.

**Lưu ý:**
Managed Identity chỉ giải quyết authentication credential lifecycle. Identity cấp quyền quá rộng vẫn là security risk; áp dụng least privilege, tách identity khi blast radius yêu cầu và kiểm tra behavior khi quyền bị revoke hoặc token acquisition thất bại.

## 🧠 Software Design

### Design 1 — Strangler Fig giúp modernization theo capability thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig dần chuyển traffic/capability từ legacy system sang implementation mới qua một routing hoặc integration boundary, trong khi hệ thống cũ vẫn phục vụ phần chưa migrate.

**Vấn đề nó giải quyết:**
Một .NET Framework monolith lớn cần modernization nhưng rewrite toàn bộ trước khi release tạo thời gian feedback dài, migration risk cao và khó chứng minh parity. Incremental replacement cho phép đưa từng capability mới vào production và học từ traffic thật.

**Ví dụ thực tế:**
Bắt đầu chuyển `/api/catalog` từ legacy IIS application sang ASP.NET Core service qua gateway, giữ checkout trên monolith. Catalog mới đọc dữ liệu qua boundary được kiểm soát; sau khi telemetry và behavior ổn định mới chuyển capability tiếp theo.

**Trade-off:**
Migration từng phần giảm cutover risk nhưng tạo giai đoạn coexistence: routing, duplicated models, data ownership và observability phức tạp hơn. Nếu không có exit criteria, “temporary” integration layer có thể tồn tại nhiều năm.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility và test parity khi di chuyển một feature. Senior / Technical developer phải chọn seam theo business capability, xác định data ownership, migration sequence, rollback path và thời điểm xóa legacy path thay vì chỉ tách code theo controller hoặc project.

### Design 2 — Observability boundary phải đi theo failure boundary

**Khái niệm:**
Observability design nên cho phép phân biệt failure và latency theo dependency, capability và critical path; không chỉ gom toàn bộ hệ thống thành một dashboard CPU/error-rate chung.

**Vấn đề nó giải quyết:**
Checkout chậm có thể do SQL, payment provider, Service Bus hoặc chính application. Nếu metrics và traces không giữ dependency/capability context, team biết “API chậm” nhưng không biết latency budget bị tiêu ở đâu hay component nào tạo blast radius.

**Ví dụ thực tế:**
Checkout trace có spans cho database, inventory và payment; dashboard hiển thị p50/p95/p99, dependency error rate và saturation theo service. Alert ưu tiên user-visible SLO thay vì chỉ báo CPU > 80% mà chưa có impact.

**Trade-off:**
Telemetry chi tiết tăng ingestion cost, schema governance và operational complexity. Quá nhiều labels/high-cardinality attributes có thể làm monitoring đắt và khó dùng; quá ít context lại kéo dài incident diagnosis.

**Middle → Senior insight:**
Middle developer cần instrument request/dependency đúng và giữ correlation xuyên async flow. Senior / Technical developer phải xác định signals từ SLO/failure modes, cardinality budget, sampling strategy và ownership để telemetry phục vụ quyết định vận hành chứ không chỉ tạo nhiều dữ liệu.

### Design 3 — Contract Testing bảo vệ integration boundary nhưng không thay thế E2E

**Khái niệm:**
Contract Testing xác minh provider và consumer đồng ý về request/response/message contract mà không cần chạy toàn bộ distributed system trong mỗi test.

**Vấn đề nó giải quyết:**
Một provider đổi enum, field bắt buộc hoặc message schema có thể compile và pass unit tests riêng nhưng phá consumer đang deploy độc lập. Chỉ dựa vào staging E2E khiến incompatibility được phát hiện muộn và test suite thường chậm, khó cô lập nguyên nhân.

**Ví dụ thực tế:**
Mobile backend consumer định nghĩa expectation cho `GET /products/{id}`; provider CI verify contract trước khi release. Với event, schema compatibility check ngăn producer đổi `OrderPlaced` theo cách consumer hiện tại không deserialize được.

**Trade-off:**
Contract tests thêm artifact/version management và có thể tạo false confidence nếu chỉ kiểm tra shape mà bỏ qua business semantics. E2E vẫn cần cho critical journeys, authentication, infrastructure wiring và behavior xuyên nhiều boundaries.

**Middle → Senior insight:**
Middle developer cần viết contract tập trung vào observable behavior thay vì implementation detail. Senior / Technical developer phải quyết định boundary nào đáng contract-test, compatibility policy, provider/consumer version strategy và cách phối hợp contract tests với integration/E2E để có feedback nhanh mà không nhân đôi test cost.
