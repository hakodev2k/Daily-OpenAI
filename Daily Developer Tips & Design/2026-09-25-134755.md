# Daily Developer Tips & Design — 2026-09-25

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` thay vì khóa logic vào đồng hồ hệ thống

**Mẹo:**
Trong .NET 8+, inject `TimeProvider` cho logic phụ thuộc thời gian thay vì gọi trực tiếp `DateTime.UtcNow`. Với test, dùng một implementation kiểm soát được thời gian để kiểm thử expiration, retry window hoặc scheduled behavior mà không phải `Task.Delay`.

**Tại sao hữu ích:**
Thời gian là một dependency. Ẩn dependency này sau `TimeProvider` làm test deterministic và giảm flaky test, đặc biệt với token expiry, cache TTL và background processing.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => clock.GetUtcNow() >= expiresAt;
}
```

**Lưu ý:**
Không biến mọi chỗ đọc timestamp thành abstraction riêng. `TimeProvider` hữu ích khi thời gian ảnh hưởng business behavior hoặc testability; với telemetry đơn giản, abstraction bổ sung có thể không đáng giá.

### Tip 2 — Chẩn đoán connection-pool exhaustion trước khi tăng pool size

**Mẹo:**
Khi API bắt đầu timeout ở database, kiểm tra thời gian giữ connection, query latency, transaction kéo dài và connection bị leak trước khi tăng `Max Pool Size`.

**Tại sao hữu ích:**
Pool exhaustion thường là triệu chứng. Nếu query tăng từ 50 ms lên 5 s, mỗi request giữ connection lâu hơn khoảng 100 lần; tăng pool chỉ có thể chuyển áp lực xuống SQL Server và làm sự cố nặng hơn.

**Ví dụ:**
Triệu chứng: latency tăng, CPU application bình thường, nhiều request chờ database. Đối chiếu Application Insights dependency duration với active DB sessions và execution plan; nếu một query mới scan hàng triệu rows sau deployment, tối ưu query/index trước khi chỉnh pool.

**Lưu ý:**
Pool size vẫn có thể cần tuning cho workload đã đo được, nhưng phải xét giới hạn connection của database và concurrency thực tế.

### Tip 3 — Với Elasticsearch, filter các điều kiện không cần relevance score

**Mẹo:**
Đưa các điều kiện như `tenantId`, trạng thái, category cố định hoặc range vào filter context thay vì query context khi chúng không cần tính `_score`.

**Tại sao hữu ích:**
Filter chỉ quyết định document có match hay không, tránh scoring không cần thiết và có khả năng tận dụng caching tốt hơn. Full-text clauses như `match` vẫn nên nằm ở query context khi relevance quan trọng.

**Ví dụ:**
Một catalog search có `match` cho "wireless keyboard", nhưng `tenantId = 42` và `isActive = true` là filters. Tách hai loại điều kiện giúp intent của query rõ và tránh tính relevance cho business constraints.

**Lưu ý:**
Đừng chuyển mọi clause sang filter: nếu thứ tự kết quả phụ thuộc relevance của clause đó, filter sẽ làm mất tín hiệu scoring.

### Tip 4 — Dùng `git bisect` cho regression có test tái hiện được

**Mẹo:**
Khi một regression xuất hiện giữa một commit tốt và HEAD, tạo test/script trả exit code ổn định rồi để `git bisect run` tìm commit đầu tiên gây lỗi.

**Tại sao hữu ích:**
Binary search giảm mạnh số commit cần kiểm tra và thay thế việc đọc diff theo cảm tính bằng bằng chứng thực thi.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test --filter FullyQualifiedName~CheckoutRegression
git bisect reset
```

**Lưu ý:**
Test flaky hoặc phụ thuộc external service không ổn định sẽ khiến bisect kết luận sai. Hãy làm reproduction deterministic trước.

### Tip 5 — Phân biệt CORS failure với authentication failure bằng browser DevTools

**Mẹo:**
Khi frontend gọi API thất bại, kiểm tra Network tab để xác định request thực tế có được gửi hay bị chặn ở preflight `OPTIONS`; đừng mặc định mọi lỗi browser là JWT sai.

**Tại sao hữu ích:**
CORS là cơ chế browser, còn authentication/authorization xảy ra phía server. Một preflight bị 401/403 hoặc thiếu `Access-Control-Allow-Origin` có đường chẩn đoán khác hoàn toàn với access token hết hạn.

**Ví dụ:**
Nếu `OPTIONS /api/orders` thất bại trước khi `GET /api/orders` xuất hiện, kiểm tra CORS middleware/order và allowed headers/origins. Nếu GET thực sự trả 401, kiểm tra token validation, issuer, audience và expiry.

**Lưu ý:**
Postman không thực thi browser CORS policy, nên "Postman chạy được" không chứng minh cấu hình CORS của web application đúng.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service cho background processing

**Khái niệm:**
Cả Azure Functions và .NET Worker Service đều xử lý background workload, nhưng khác về execution model, hosting, scaling và mức kiểm soát vòng đời process.

**Vấn đề nó giải quyết:**
Một hệ thống cần xử lý event hoặc job ngoài HTTP request path nhưng phải chọn giữa serverless convenience và một long-running process có lifecycle chủ động.

**Ví dụ thực tế:**
Xử lý Blob upload thưa và bursty có thể phù hợp Azure Functions trigger. Một processor luôn chạy, giữ nhiều in-memory state hoặc cần kiểm soát concurrency/lifecycle tinh chỉnh có thể phù hợp Worker Service chạy trên App Service/Kubernetes hơn.

**Trade-off:**
Functions giảm hosting boilerplate và scale thuận tiện nhưng mang constraints về runtime, cold start và execution behavior. Worker Service cho kiểm soát cao hơn nhưng đội ngũ phải sở hữu deployment, scaling và health management nhiều hơn.

**Middle → Senior insight:**
Middle cần triển khai cancellation, retry và idempotency đúng trong execution model đã chọn. Senior cần chọn model dựa trên workload shape, failure semantics, operability, cost và năng lực vận hành của team, không dựa trên việc công nghệ nào "modern" hơn.

### Design 2 — Outbox Pattern để nối transaction database với message publishing

**Khái niệm:**
Outbox lưu business change và message-to-publish trong cùng local database transaction; một publisher riêng chuyển outbox record sang broker sau đó.

**Vấn đề nó giải quyết:**
Nếu application commit Order rồi publish Service Bus message, process có thể crash giữa hai bước: database đã đổi nhưng event chưa bao giờ được gửi. Đảo thứ tự lại tạo failure mode ngược lại.

**Ví dụ thực tế:**
Checkout transaction ghi `Order` và `OutboxMessage(OrderPlaced)`. Worker publish message lên Azure Service Bus rồi đánh dấu outbox đã xử lý. Consumer vẫn phải idempotent vì publish/ack có thể tạo duplicate delivery.

**Trade-off:**
Outbox tránh distributed transaction và cải thiện reliability, nhưng thêm storage, polling/publishing logic, cleanup, observability và eventual consistency.

**Middle → Senior insight:**
Middle cần bảo đảm business row và outbox row thực sự nằm trong cùng transaction. Senior phải quyết định liệu failure risk có đủ lớn để trả operational cost của Outbox, đồng thời thiết kế deduplication, ordering và recovery end-to-end.

### Design 3 — API backward compatibility thay vì versioning theo phản xạ

**Khái niệm:**
API evolution nên ưu tiên additive, backward-compatible change khi có thể; version mới chỉ là một công cụ khi contract semantics thực sự không thể duy trì tương thích.

**Vấn đề nó giải quyết:**
Mobile app, CMS frontend và third-party clients thường nâng cấp không đồng thời với backend. Breaking change có thể biến một deployment hợp lệ thành production incident ở client cũ.

**Ví dụ thực tế:**
Thêm optional field `displayName` thường không cần `/v2`. Nhưng đổi ý nghĩa `status`, loại bỏ field bắt buộc hoặc thay đổi workflow có thể cần version boundary và migration window rõ ràng.

**Trade-off:**
Backward compatibility giảm client disruption nhưng làm contract cũ tồn tại lâu hơn. Versioning tạo ranh giới rõ nhưng tăng số contract, test matrix, documentation và deprecation burden.

**Middle → Senior insight:**
Middle cần tránh rename/remove field tùy tiện và có contract/integration tests. Senior cần quản lý lifecycle của contract: consumer inventory, compatibility policy, deprecation telemetry, migration timeline và thời điểm chi phí duy trì legacy vượt quá lợi ích.
