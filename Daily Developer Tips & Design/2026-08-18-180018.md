# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TryGetNonEnumeratedCount` trước khi enumerate collection đắt đỏ

**Mẹo:**
Khi cần biết số phần tử của một `IEnumerable<T>`, ưu tiên kiểm tra `TryGetNonEnumeratedCount` trước thay vì gọi `Count()` một cách mù quáng.

**Tại sao hữu ích:**
`Count()` có thể buộc toàn bộ sequence phải được enumerate nếu nguồn không expose count trực tiếp. Với pipeline LINQ lớn hoặc custom iterator, việc này có thể gây thêm CPU, I/O hoặc thậm chí query lại nguồn dữ liệu.

**Ví dụ:**
```csharp
if (!source.TryGetNonEnumeratedCount(out var count))
{
    count = source.Count();
}
```

**Lưu ý:**
Không dùng để “tối ưu” query EF Core. Với `IQueryable<T>`, nên để provider dịch `CountAsync()` thành SQL phù hợp thay vì chuyển sang `IEnumerable<T>` sớm.

### Tip 2 — Dùng `AsSplitQuery()` khi `Include` tạo cartesian explosion

**Mẹo:**
Nếu một EF Core query `Include` nhiều collection và kết quả SQL tạo lượng row nhân chéo rất lớn, cân nhắc `AsSplitQuery()`.

**Tại sao hữu ích:**
Nó tách một query join rất lớn thành nhiều query nhỏ hơn, giảm duplicate data truyền từ database về application và có thể giảm memory pressure.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Split query tăng số round-trip tới database và cần cân nhắc consistency nếu dữ liệu thay đổi giữa các query. Đừng bật toàn cục chỉ vì một endpoint bị chậm.

### Tip 3 — Dùng `curl --trace-time` khi debug latency HTTP

**Mẹo:**
Khi một API “chậm” nhưng chưa rõ chậm ở DNS, TLS, network hay server, dùng `curl` với timing/trace thay vì chỉ nhìn tổng thời gian.

**Tại sao hữu ích:**
Giúp phân biệt latency trước khi request tới server với latency do application xử lý, từ đó tránh tối ưu sai layer.

**Ví dụ:**
```bash
curl --trace-time -v https://api.example.com/orders
```

Hoặc đo từng phase:

```bash
curl -s -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} start=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/orders
```

**Lưu ý:**
Một lần đo không đủ để kết luận. Cần lặp lại và so sánh từ đúng network path tương ứng với production.

### Tip 4 — Dùng `EXCEPT`/`INTERSECT` để kiểm tra chênh lệch dữ liệu giữa hai tập

**Mẹo:**
Khi đối chiếu dữ liệu migration, sync hoặc ETL, dùng set operators của SQL thay vì tự join phức tạp.

**Tại sao hữu ích:**
Giúp nhanh chóng tìm record có ở tập A nhưng không có ở tập B, hoặc record giao nhau giữa hai tập.

**Ví dụ:**
```sql
SELECT Id, Email
FROM NewUsers
EXCEPT
SELECT Id, Email
FROM OldUsers;
```

**Lưu ý:**
`EXCEPT` so sánh theo toàn bộ cột được select và thường loại duplicate. Nếu cần xử lý duplicate hoặc so sánh theo key với quy tắc riêng, hãy dùng `JOIN` rõ ràng hơn.

### Tip 5 — Đưa invariant quan trọng vào test bằng property-based testing

**Mẹo:**
Với logic có nhiều tổ hợp input, cân nhắc property-based testing thay vì chỉ viết vài test case mẫu.

**Tại sao hữu ích:**
Framework sẽ tạo nhiều input khác nhau để tìm edge case mà developer khó nghĩ tới, đặc biệt hữu ích với parser, calculation, serializer hoặc domain rule.

**Ví dụ:**
Một rule quan trọng của money transfer có thể là: tổng số dư trước và sau giao dịch không đổi nếu không có fee. Test nên kiểm tra invariant đó trên hàng trăm input hợp lệ thay vì chỉ 3–4 case cụ thể.

**Lưu ý:**
Property-based testing không thay thế example-based tests. Nó mạnh nhất khi invariant được định nghĩa rõ; property mơ hồ sẽ chỉ tạo ra nhiều test khó hiểu.

## 🧠 Software Design

### Design 1 — Strangler Fig Pattern khi thay thế legacy system

**Khái niệm:**
Strangler Fig Pattern thay thế hệ thống cũ từng phần bằng cách route từng capability sang implementation mới, thay vì rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó kiểm chứng và tạo rủi ro lớn vì business vẫn thay đổi trong lúc hệ thống mới chưa hoàn thiện.

**Ví dụ thực tế:**
Một legacy monolith xử lý Customer, Order và Billing. Team có thể chuyển endpoint Customer sang service/module mới trước, giữ Order và Billing trong hệ thống cũ, rồi tiếp tục dịch chuyển từng boundary khi đủ ổn định.

**Trade-off:**
Giảm rủi ro migration và cho phép release incremental, nhưng trong giai đoạn chuyển đổi phải duy trì routing layer, duplicate model và integration giữa old/new system.

**Middle → Senior insight:**
Middle developer cần hiểu migration không chỉ là copy code sang project mới. Senior developer phải chọn boundary dễ tách, xác định source of truth trong từng giai đoạn, thiết kế rollback path và tránh để “temporary integration” tồn tại vĩnh viễn.

### Design 2 — Hedging chỉ dành cho read operation an toàn

**Khái niệm:**
Hedging gửi thêm một request dự phòng tới cùng hoặc một replica khác khi request đầu tiên vượt quá một latency threshold, rồi lấy response thành công sớm nhất.

**Vấn đề nó giải quyết:**
Trong hệ thống distributed, tail latency đôi khi đến từ một instance chậm bất thường dù phần lớn request vẫn nhanh. Hedging giảm ảnh hưởng của các outlier đó.

**Ví dụ thực tế:**
Một read-only search API gọi replica A. Nếu sau 200 ms chưa có response, client gửi cùng request sang replica B và dùng kết quả nào về trước.

**Trade-off:**
Giảm p95/p99 latency nhưng tăng traffic và load lên downstream. Nếu áp dụng cho write operation không idempotent, hedging có thể tạo duplicate side effect nghiêm trọng.

**Middle → Senior insight:**
Middle developer cần hiểu retry và hedging không giống nhau. Senior developer phải xác định latency threshold, request eligibility, cancellation của request thừa và capacity headroom trước khi áp dụng để tránh chữa tail latency bằng cách làm hệ thống quá tải hơn.

### Design 3 — Data ownership quan trọng hơn “shared database tiện hơn”

**Khái niệm:**
Mỗi module/service nên có ownership rõ ràng đối với dữ liệu mà nó chịu trách nhiệm thay đổi. Module khác truy cập thông qua contract thay vì update trực tiếp bảng không thuộc quyền sở hữu của mình.

**Vấn đề nó giải quyết:**
Shared database dễ tạo coupling ngầm: một module thay schema hoặc business rule có thể phá module khác dù API contract không đổi.

**Ví dụ thực tế:**
Inventory sở hữu stock level. Order module không nên chạy trực tiếp `UPDATE Inventory SET Quantity = ...`; nó nên gọi một application service hoặc gửi command/event qua boundary đã định nghĩa.

**Trade-off:**
Boundary dữ liệu rõ giúp maintainability, autonomy và migration dễ hơn, nhưng có thể phải trả giá bằng thêm API call, messaging hoặc eventual consistency thay vì join/update trực tiếp cực tiện trong một database.

**Middle → Senior insight:**
Middle developer cần hiểu “cùng database” không đồng nghĩa với “mọi bảng đều dùng tự do”. Senior developer phải chọn ownership dựa trên business capability, quyết định khi nào cross-module query được phép và thiết kế read model/reporting mà không phá write boundary.
