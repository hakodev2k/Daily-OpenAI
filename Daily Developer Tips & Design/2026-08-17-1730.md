# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `SearchValues<T>` khi phải tìm cùng một tập ký tự nhiều lần

**Mẹo:**
Khi parser hoặc text-processing hot path liên tục tìm cùng một nhóm ký tự, cân nhắc `SearchValues<char>` thay vì tạo lại nhiều điều kiện `IndexOfAny` hoặc collection tạm thời.

**Tại sao hữu ích:**
Runtime có thể tối ưu cấu trúc tìm kiếm và tái sử dụng nó cho nhiều lần scan, giảm overhead trong code parsing tần suất cao.

**Ví dụ:**
```csharp
using System.Buffers;

private static readonly SearchValues<char> Separators =
    SearchValues.Create(",;|");

ReadOnlySpan<char> input = "pending;approved|rejected";
var index = input.IndexOfAny(Separators);
```

**Lưu ý:**
Đây là micro-optimization. Với code business thông thường, ưu tiên readability; chỉ áp dụng khi workload thật sự scan dữ liệu nhiều và profiling cho thấy parsing là bottleneck.

### Tip 2 — Gắn `TagWith()` vào EF Core query để tìm SQL từ application code

**Mẹo:**
Với query quan trọng hoặc khó lần ngược từ database monitoring về code, dùng `TagWith()` để thêm comment nhận dạng vào SQL do EF Core sinh ra.

**Tại sao hữu ích:**
Khi xem slow-query log, Query Store hoặc tracing, bạn có thể nhanh chóng biết query đến từ use case nào thay vì chỉ nhìn SQL dài và đoán source code.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .TagWith("OrdersDashboard:GetPendingOrders")
    .Where(x => x.Status == OrderStatus.Pending)
    .OrderBy(x => x.CreatedAt)
    .Take(100)
    .ToListAsync(cancellationToken);
```

SQL sẽ chứa comment tương ứng trước statement.

**Lưu ý:**
Tag chỉ giúp diagnostics, không làm query nhanh hơn. Tránh đưa PII, token hoặc dữ liệu runtime nhạy cảm vào tag.

### Tip 3 — Dùng `strace` khi process Linux “không nói gì” nhưng vẫn lỗi

**Mẹo:**
Khi process trên Linux fail do file, permission, DNS/socket hoặc syscall mà application log không đủ rõ, dùng `strace` để quan sát system calls thực tế.

**Tại sao hữu ích:**
Bạn có thể thấy process đang mở file nào, nhận `EACCES`, `ENOENT`, connect tới đâu hoặc syscall nào fail ngay trước exception.

**Ví dụ:**
```bash
strace -f -e trace=file,network -p <PID>
```

Hoặc chạy command dưới `strace`:

```bash
strace -f -o trace.log dotnet MyApp.dll
```

**Lưu ý:**
Output rất lớn và có thể chứa path hoặc dữ liệu nhạy cảm. Chỉ trace phạm vi cần thiết và tránh bật lâu trên production traffic cao.

### Tip 4 — Dùng `git log -S` để tìm commit đã thêm hoặc xóa một đoạn logic

**Mẹo:**
Khi muốn biết “behavior này xuất hiện từ commit nào?”, dùng pickaxe search `git log -S` thay vì chỉ `git blame` dòng hiện tại.

**Tại sao hữu ích:**
`git blame` chỉ cho biết commit cuối chạm dòng; `-S` tìm commit làm thay đổi số lần xuất hiện của một chuỗi, hữu ích khi code đã bị move/refactor nhiều lần.

**Ví dụ:**
```bash
git log -S"DeliverToMailboxAndForward" --oneline --all
```

Xem patch cụ thể:

```bash
git log -S"DeliverToMailboxAndForward" -p -- src/
```

**Lưu ý:**
`-S` tìm theo thay đổi số lượng chuỗi, không phải semantic change. Nếu cần tìm pattern trong diff, có thể dùng `git log -G` với regex.

### Tip 5 — Dùng `dotnet-counters` để nhìn live ThreadPool, GC và exception rate

**Mẹo:**
Khi ứng dụng chậm nhưng chưa biết bottleneck ở CPU, GC hay ThreadPool, xem runtime counters trực tiếp trước khi thu dump/trace nặng hơn.

**Tại sao hữu ích:**
Bạn có thể nhanh chóng nhận ra GC heap tăng liên tục, allocation rate cao, ThreadPool queue dài hoặc exception rate bất thường ngay khi incident đang xảy ra.

**Ví dụ:**
```bash
dotnet-counters monitor -p <PID> System.Runtime
```

Các metric đáng chú ý gồm:

```text
alloc-rate
cpu-usage
gc-heap-size
threadpool-queue-length
exception-count
```

**Lưu ý:**
Counters giúp khoanh vùng vấn đề, không chỉ ra chính xác method gây lỗi. Khi đã xác định hướng, dùng `dotnet-trace`, profiler hoặc dump để đào sâu.

## 🧠 Software Design

### Design 1 — Hedged Requests để giảm tail latency, không phải để retry mọi thứ

**Khái niệm:**
Hedged request gửi một request thứ hai tới replica/endpoint khác nếu request đầu tiên vượt một ngưỡng latency ngắn, sau đó lấy response thành công đầu tiên và hủy phần còn lại.

**Vấn đề nó giải quyết:**
Trong distributed systems, p99 latency đôi khi bị kéo dài bởi một replica chậm, network jitter hoặc queue tạm thời dù phần lớn request vẫn nhanh.

**Ví dụ thực tế:**
Một read-only service gọi một trong ba replica. Nếu sau 120 ms chưa có response trong khi p50 chỉ 40 ms, client gửi thêm request tới replica khác. Response nào về trước được dùng.

**Trade-off:**
Hedging có thể giảm tail latency đáng kể nhưng tăng số request và tải lên downstream. Với write operation hoặc API có side effect, gửi trùng có thể nguy hiểm nếu không idempotent.

**Middle → Senior insight:**
Middle developer nên phân biệt hedging với retry sau failure. Senior developer cần chọn hedge delay dựa trên latency distribution, chỉ áp dụng cho operation an toàn/idempotent và đặt budget để không biến latency spike thành traffic amplification.

### Design 2 — Aggregate boundary nên dựa trên invariant, không phải quan hệ bảng

**Khái niệm:**
Trong DDD, Aggregate nhóm các entity/value object phải nhất quán trong cùng một transaction. Quan hệ foreign key hoặc navigation property không tự động có nghĩa chúng phải nằm trong cùng Aggregate.

**Vấn đề nó giải quyết:**
Aggregate quá lớn khiến mỗi command phải load nhiều dữ liệu, lock rộng, transaction dài và khó scale. Aggregate quá nhỏ lại có thể làm business invariant bị phá vì nhiều phần phải cập nhật rời rạc.

**Ví dụ thực tế:**
`Order` và `Customer` có quan hệ dữ liệu, nhưng việc thêm `OrderItem` thường chỉ cần invariant của Order như tổng tiền và trạng thái. Không cần load toàn bộ Customer Aggregate chỉ vì Order có `CustomerId`.

**Trade-off:**
Aggregate nhỏ giúp transaction ngắn và concurrency tốt hơn nhưng một số workflow xuyên aggregate phải dùng eventual consistency hoặc application coordination. Aggregate lớn đơn giản hóa invariant cục bộ nhưng tăng contention và coupling.

**Middle → Senior insight:**
Middle developer nên hỏi “dữ liệu nào bắt buộc phải đúng cùng lúc?”. Senior developer cần dùng invariant, contention, transaction cost và change frequency để quyết định boundary thay vì map 1:1 từ ER diagram sang domain model.

### Design 3 — Materialized Read Model khi read query quá đắt so với freshness requirement

**Khái niệm:**
Materialized Read Model lưu sẵn dữ liệu đã join/aggregate theo shape mà UI hoặc API cần, thay vì chạy lại query phức tạp trên transactional schema cho mỗi request.

**Vấn đề nó giải quyết:**
Dashboard hoặc report có thể cần join nhiều bảng, aggregate hàng triệu rows và sort/filter liên tục, gây tải lớn lên database phục vụ transaction.

**Ví dụ thực tế:**
Một dashboard timesheet cần tổng giờ theo employee, project và tháng. Thay vì mỗi request aggregate trực tiếp hàng triệu entries, background process cập nhật bảng/read model `MonthlyTimesheetSummary`, rồi endpoint đọc dữ liệu đã tổng hợp.

**Trade-off:**
Read latency và database load giảm mạnh, nhưng dữ liệu có thể stale và cần cơ chế rebuild, update, versioning và xử lý khi projection bị lỗi.

**Middle → Senior insight:**
Middle developer nên hiểu denormalization có thể là lựa chọn có chủ đích cho read path. Senior developer phải xác định freshness SLA, nguồn sự thật, cách rebuild toàn bộ projection, idempotency của updater và khi nào query trực tiếp vẫn đơn giản hơn materialization.
