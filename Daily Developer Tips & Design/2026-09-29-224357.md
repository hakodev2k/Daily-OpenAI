# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` khi buffer lớn được tạo lặp lại trên hot path

**Mẹo:**
Với code xử lý serialization, protocol hoặc stream tạo nhiều buffer tạm có kích thước đáng kể, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì liên tục `new byte[]`.

**Tại sao hữu ích:**
Allocation lặp lại tạo áp lực lên GC; buffer đủ lớn còn có thể đi vào Large Object Heap. Pooling tái sử dụng vùng nhớ và giảm allocation rate, nhưng chỉ đáng dùng sau khi profiler cho thấy allocation thực sự là bottleneck.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    // process buffer[..read]
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Array được thuê có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Không giữ reference sau khi `Return`; với dữ liệu nhạy cảm, cân nhắc `clearArray: true`. Pooling cho object nhỏ hoặc cold path thường chỉ làm code phức tạp hơn.

### Tip 2 — EF Core: `ExecuteUpdateAsync` tránh load entity chỉ để update hàng loạt

**Mẹo:**
Khi một command cập nhật nhiều rows bằng cùng một biểu thức và không cần domain logic trên từng entity, dùng `ExecuteUpdateAsync` thay vì query entities, mutate rồi `SaveChangesAsync`.

**Tại sao hữu ích:**
Cách này phát sinh SQL `UPDATE` trực tiếp, tránh materialization, change tracking và nhiều dữ liệu đi qua application process. Nó giảm memory, CPU và database round trips.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending &&
                x.ExpiresAt < now)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```

**Lưu ý:**
Bulk update này không đồng bộ state của entities đang được track trong cùng `DbContext`, không chạy logic C# trên từng aggregate và cần xem xét concurrency/audit semantics. Đừng dùng nó để bypass invariant của domain chỉ vì nhanh hơn.

### Tip 3 — Elasticsearch: alias giúp reindex mà không buộc consumer đổi index name

**Mẹo:**
Cho application query qua alias ổn định, ví dụ `products-read`, thay vì hard-code index vật lý như `products-v7`. Khi mapping thay đổi, build index mới rồi chuyển alias.

**Tại sao hữu ích:**
Một số mapping change không thể sửa an toàn in-place. Alias cho phép chuẩn bị dữ liệu mới, validate trước rồi cut over nhanh, giảm coupling giữa deployment của application và lifecycle của search index.

**Ví dụ:**
```text
products-v7  <- products-read
     |
reindex
     v
products-v8  <- switch alias after validation
```
Trước khi switch, so sánh document count, sample queries, relevance và indexing lag.

**Lưu ý:**
Alias switch không tự giải quyết dual-write hoặc dữ liệu phát sinh trong lúc reindex. Cần chiến lược đồng bộ delta và rollback; nếu schema không thay đổi đáng kể thì reindex toàn bộ có thể là chi phí không cần thiết.

### Tip 4 — CI/CD: artifact phải immutable giữa các environment

**Mẹo:**
Build application một lần, tạo artifact/image có version cố định rồi promote chính artifact đó từ test → staging → production; chỉ inject configuration theo environment.

**Tại sao hữu ích:**
Nếu mỗi environment rebuild source, production có thể chạy binary khác với thứ đã được test do dependency resolution, toolchain hoặc source state thay đổi. Promote cùng artifact giúp provenance và rollback rõ ràng hơn.

**Ví dụ:**
```text
commit abc123
   -> build
   -> app:2026.09.29.42
      -> deploy DEV
      -> promote TEST
      -> promote PROD
```
Pipeline lưu commit SHA, artifact digest và deployment version để trace regression.

**Lưu ý:**
Không bake production secrets vào image/artifact. Configuration khác nhau vẫn có thể làm behavior khác nhau giữa environments, nên immutable artifact không thay thế configuration validation và smoke test.

### Tip 5 — CMS: tránh cache page HTML theo URL khi output phụ thuộc identity

**Mẹo:**
Trước khi cache HTML ở CDN hoặc server, xác định response có phụ thuộc user, role, cookie, locale, experiment hoặc personalization hay không. Cache key phải phản ánh đúng các dimension thực sự làm output thay đổi.

**Tại sao hữu ích:**
Một cache key quá rộng có thể trả nội dung cá nhân hóa của user này cho user khác; key quá chi tiết lại phá cache hit ratio. Đây vừa là bài toán correctness/security vừa là performance engineering.

**Ví dụ:**
Một trang Optimizely hiển thị giá theo market và ngôn ngữ. Cache chỉ theo `/products/42` là sai; tối thiểu phải xác định các dimension như market/locale, hoặc không cache shared response nếu nội dung phụ thuộc identity.

**Lưu ý:**
Không thêm mọi header/cookie vào cache key một cách máy móc vì sẽ tạo gần như một entry cho mỗi request. Tách phần public cacheable khỏi personalized fragment thường tốt hơn cache toàn trang theo user.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer cần chống duplicate bền vững

**Khái niệm:**
Consumer ghi `MessageId` đã xử lý vào durable store trong cùng transaction với business state. Khi broker redeliver cùng message, consumer nhận diện duplicate và không áp dụng side effect lần nữa.

**Vấn đề nó giải quyết:**
Hệ thống messaging thường có at-least-once delivery. Crash sau khi commit database nhưng trước khi complete/ack message có thể khiến cùng message được giao lại.

**Ví dụ thực tế:**
Worker nhận `PaymentCaptured`, cập nhật `Order` rồi process chết trước khi complete Service Bus message. Lần delivery sau kiểm tra Inbox; nếu `MessageId` đã tồn tại thì bỏ qua business mutation và complete message.

**Trade-off:**
Đổi lại khả năng deduplication bền vững là thêm write, unique constraint, retention/cleanup và transaction coordination. Với operation vốn đã idempotent tự nhiên, Inbox có thể là abstraction thừa.

**Middle → Senior insight:**
Middle cần hiểu duplicate delivery là bình thường và handler không được giả định exactly-once. Senior cần quyết định idempotency đặt ở business key, Inbox hay downstream boundary; đồng thời thiết kế retention, transaction scope và behavior khi cùng message được xử lý cạnh tranh.

### Design 2 — Modular Monolith trước khi tách Microservices

**Khái niệm:**
Một deployable application vẫn có các module với ownership, dependency direction và data boundary rõ ràng. Boundary được thiết kế trước, network distribution chỉ xuất hiện khi có lý do vận hành đủ mạnh.

**Vấn đề nó giải quyết:**
Codebase monolith dễ thành tightly coupled “big ball of mud”, nhưng tách Microservices sớm lại thêm network failure, deployment orchestration, observability và distributed consistency.

**Ví dụ thực tế:**
Hệ thống e-commerce giữ Catalog, Ordering và Reviews trong một ASP.NET Core application nhưng cấm module truy cập trực tiếp internals của nhau. Khi Ordering cần scale/deploy độc lập vì workload và team ownership khác biệt, boundary đã đủ rõ để cân nhắc extraction.

**Trade-off:**
Modular Monolith giữ transaction và deployment đơn giản hơn, nhưng vẫn chia sẻ process và có thể chia sẻ failure/resource pressure. Microservices tăng autonomy nhưng đổi lại operational cost và distributed-system failure modes.

**Middle → Senior insight:**
Middle cần giữ module cohesion và dependency boundary thay vì chỉ chia project theo layer. Senior phải chứng minh việc extraction bằng scaling, ownership, release cadence, isolation hoặc compliance pressure; “hệ thống lớn” tự nó chưa phải lý do đủ để chọn Microservices.

### Design 3 — API Composition vs materialized read model

**Khái niệm:**
Để tạo một view cần dữ liệu từ nhiều domain, có thể compose synchronously từ nhiều APIs lúc request, hoặc duy trì một read model đã denormalize từ events/CDC để query trực tiếp.

**Vấn đề nó giải quyết:**
Frontend/dashboard thường cần dữ liệu vượt qua service boundary. Join trực tiếp database của service khác phá ownership, nhưng gọi chuỗi APIs có thể làm latency và availability phụ thuộc vào nhiều downstream services.

**Ví dụ thực tế:**
Trang “Order detail” cần Order, Payment và Shipment. Với traffic thấp và yêu cầu dữ liệu rất mới, BFF có thể gọi ba APIs song song. Với dashboard đọc lớn, một projection cập nhật bất đồng bộ có thể giảm fan-out và ổn định latency.

**Trade-off:**
API composition đơn giản hơn về consistency nhưng tạo runtime coupling và tail latency. Materialized read model đọc nhanh, độc lập hơn nhưng thêm storage, event pipeline, rebuild logic và eventual consistency.

**Middle → Senior insight:**
Middle cần tránh cross-service database joins và xử lý timeout/partial failure khi composition. Senior phải chọn dựa trên freshness SLA, read volume, failure tolerance, ownership và operational cost; không tạo projection chỉ để tránh vài API calls nếu hệ thống chưa có pressure tương ứng.
