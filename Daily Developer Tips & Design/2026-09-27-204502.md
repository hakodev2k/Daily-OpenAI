# Daily Developer Tips & Design — 2026-09-27

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng retry mọi lỗi HTTP theo cùng một cách

**Mẹo:**
Khi tích hợp third-party API bằng `HttpClient`, chỉ retry lỗi có tính transient như timeout, `408`, `429` hoặc một số `5xx`. Đặt timeout cho từng operation và dùng exponential backoff có jitter thay vì retry tức thì.

**Tại sao hữu ích:**
Retry sai có thể khuếch đại sự cố: upstream đang quá tải nhưng mỗi request của bạn lại sinh thêm nhiều request. Jitter giúp các instance không đồng loạt retry cùng thời điểm, giảm nguy cơ thundering herd.

**Ví dụ:**
Một payment API trả `429 Too Many Requests`. Thay vì retry 3 lần ngay lập tức, client tôn trọng `Retry-After` hoặc backoff 200 ms → 500 ms → 1.2 s có jitter. Với `400 Bad Request`, không retry vì request không tự trở nên hợp lệ.

**Lưu ý:**
Không retry operation không idempotent một cách mù quáng. Một `POST /payments` timeout có thể đã được xử lý ở server; cần idempotency key trước khi retry an toàn.

### Tip 2 — Chẩn đoán query EF Core bằng SQL thực tế, không bằng LINQ nhìn “đẹp”

**Mẹo:**
Khi query EF Core chậm, kiểm tra SQL được translate bằng `ToQueryString()`, sau đó xem execution plan và số rows thực tế thay vì chỉ refactor biểu thức LINQ.

**Tại sao hữu ích:**
Một LINQ expression ngắn vẫn có thể tạo SQL chứa join lớn, correlated subquery hoặc projection dư thừa. Bottleneck nằm ở execution plan, cardinality, I/O và round trip chứ không nằm ở độ dài code C#.

**Ví dụ:**
```csharp
var query = db.Orders
    .Where(x => x.Status == OrderStatus.Pending)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new { x.Id, x.CreatedAt, x.Customer.Name });

Console.WriteLine(query.ToQueryString());
```
Nếu production chậm, lấy SQL tương ứng để kiểm tra index, estimated/actual rows và operators trong plan.

**Lưu ý:**
`ToQueryString()` phục vụ diagnostics; SQL hiển thị không thay thế việc đo execution plan trên workload/data distribution thực tế.

### Tip 3 — Dùng structured logging để điều tra lỗi xuyên request

**Mẹo:**
Log dữ liệu dưới dạng property có cấu trúc và truyền `CorrelationId`/trace context xuyên API, database dependency và background processing.

**Tại sao hữu ích:**
Chuỗi text như `"Order failed: " + orderId` khó query và aggregate. Structured fields cho phép lọc theo `OrderId`, `TraceId`, dependency hoặc deployment version trong Application Insights/Kibana và tái dựng timeline của incident.

**Ví dụ:**
```csharp
logger.LogError(ex,
    "Payment processing failed for {OrderId} via {Provider}",
    order.Id, providerName);
```
Khi error rate tăng sau deployment, lọc theo `TraceId` và version để xác định request nào bắt đầu lỗi và dependency nào kéo latency lên.

**Lưu ý:**
Không log access token, password, connection string, payment data hoặc PII không cần thiết. Structured logging không có nghĩa là log mọi object.

### Tip 4 — Playwright: chờ trạng thái nghiệp vụ, đừng “sleep cho chắc”

**Mẹo:**
Trong E2E test, chờ locator hoặc trạng thái UI có ý nghĩa thay vì dùng delay cố định như `WaitForTimeoutAsync(3000)`.

**Tại sao hữu ích:**
Fixed delay vừa làm suite chậm vừa gây flaky test: 3 giây có thể thừa trên máy nhanh nhưng vẫn thiếu trên CI chậm. Auto-waiting của Playwright đồng bộ test với điều kiện UI thực tế.

**Ví dụ:**
Sau khi submit form tạo employee, chờ notification hoặc row mới:
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByText("Employee created")).ToBeVisibleAsync();
```

**Lưu ý:**
Auto-waiting không sửa được race condition nghiệp vụ. Nếu UI báo thành công trước khi backend transaction hoàn tất, cần sửa contract/flow thay vì tăng timeout test.

### Tip 5 — Dùng Git bisect khi regression không có thủ phạm rõ ràng

**Mẹo:**
Khi một regression xuất hiện giữa một commit “good” và một commit “bad”, dùng `git bisect` để thu hẹp commit gây lỗi theo binary search.

**Tại sao hữu ích:**
Đọc tuần tự hàng chục hoặc hàng trăm commits tốn thời gian và dễ bị bias. `git bisect` giảm số lần kiểm tra xuống xấp xỉ `log2(N)`, đặc biệt hiệu quả khi có test/script tái hiện lỗi.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test --filter FullyQualifiedName~CheckoutRegression
git bisect reset
```

**Lưu ý:**
Bisect chỉ đáng tin khi test tái hiện lỗi deterministic. Với flaky test hoặc lỗi phụ thuộc external state, kết quả `good/bad` sai sẽ dẫn binary search sang nhánh sai.

## 🧠 Software Design

### Design 1 — Outbox Pattern thay cho “DB commit rồi publish event”

**Khái niệm:**
Outbox lưu business change và integration message trong cùng local database transaction. Một publisher riêng đọc outbox rồi gửi message ra broker, tránh yêu cầu distributed transaction giữa database và Azure Service Bus.

**Vấn đề nó giải quyết:**
Nếu application commit `Order` thành công rồi crash trước khi publish `OrderCreated`, database và downstream systems bị lệch trạng thái. Đảo thứ tự publish trước rồi commit cũng tạo failure window ngược lại.

**Ví dụ thực tế:**
Checkout transaction ghi `Orders` và `OutboxMessages` cùng lúc. Background worker publish message; nếu Service Bus tạm unavailable, message vẫn còn trong outbox để retry. Consumer vẫn phải idempotent vì broker/publisher có thể giao trùng.

**Trade-off:**
Lợi ích là atomicity tại boundary của database và khả năng recovery tốt hơn. Chi phí là thêm storage, polling/publisher, cleanup, monitoring, duplicate handling và eventual consistency.

**Middle → Senior insight:**
Middle developer cần implement transaction, publisher và idempotent consumer đúng. Senior / Technical developer phải quyết định liệu failure risk có đủ lớn để biện minh cho Outbox hay một integration đơn giản hơn đã đủ, đồng thời thiết kế retention, throughput, ordering và operational monitoring.

### Design 2 — Modular Monolith trước khi tách Microservices

**Khái niệm:**
Modular Monolith giữ một deployable unit nhưng chia hệ thống thành module có ownership, dependency direction và data boundary rõ ràng. Boundary được thiết kế trước khi network được đưa vào giữa các phần của hệ thống.

**Vấn đề nó giải quyết:**
Một monolith không có boundary dễ trở thành tightly coupled “big ball of mud”; nhưng tách Microservices quá sớm biến method calls thành network calls và thêm deployment, observability, messaging, consistency cùng operational complexity.

**Ví dụ thực tế:**
Một e-commerce system có `Catalog`, `Ordering`, `Payments` và `Content` modules. Ban đầu chúng chạy cùng ASP.NET Core application nhưng không truy cập trực tiếp internal model của nhau. Chỉ khi `Catalog` cần scale/deploy/ownership độc lập mới cân nhắc extraction.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment và transaction nhưng vẫn chia sẻ failure/scaling boundary ở mức process. Microservices tăng autonomy và independent scaling nhưng trả giá bằng distributed-system complexity.

**Middle → Senior insight:**
Middle developer cần giữ dependency/module boundary và tránh cross-module shortcuts. Senior / Technical developer phải chứng minh nhu cầu tách service bằng scaling, release cadence, team ownership, fault isolation hoặc domain boundary — không phải vì Microservices “hiện đại hơn”.

### Design 3 — Cache-aside: hiệu năng đổi lấy bài toán consistency

**Khái niệm:**
Với cache-aside, application đọc Redis trước; cache miss thì đọc source of truth rồi populate cache. Cache là optimization layer, không phải authoritative transactional state.

**Vấn đề nó giải quyết:**
Dữ liệu đọc nhiều như product summary hoặc CMS content có thể tạo tải lớn lên database và tăng latency. Cache giảm repeated computation/I/O nhưng tạo thêm trạng thái cần đồng bộ.

**Ví dụ thực tế:**
Product API cache `product:{id}` trong Redis. Khi product được cập nhật, application invalidate key; TTL đóng vai trò safety net. Nếu nhiều request cùng miss một hot key, dùng request coalescing hoặc controlled refresh để tránh cache stampede.

**Trade-off:**
Cache giảm latency và database load nhưng thêm stale-data risk, invalidation complexity, serialization cost, hot keys và failure mode khi Redis unavailable. TTL ngắn không tự động giải quyết correctness.

**Middle → Senior insight:**
Middle developer cần implement key, TTL, invalidation và fallback đúng. Senior / Technical developer phải xác định dữ liệu nào chịu được stale bao lâu, hành vi khi cache down, stampede strategy và liệu lợi ích đo được có đáng với consistency/operational complexity hay không.
