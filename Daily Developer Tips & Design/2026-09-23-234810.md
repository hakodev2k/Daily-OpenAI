# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — EF Core projection thường tốt hơn `Include` khi API chỉ cần DTO

**Mẹo:**
Với read endpoint chỉ cần một phần dữ liệu, project trực tiếp sang DTO bằng `Select` thay vì load cả entity graph bằng nhiều `Include` rồi mới map trong memory.

**Tại sao hữu ích:**
Projection cho EF Core cơ hội sinh SQL chỉ lấy các cột và quan hệ thực sự cần. `Include` trên nhiều collection có thể tạo result set lớn do cartesian multiplication, tăng network payload, materialization và memory dù response cuối cùng rất nhỏ.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.CreatedAt,
        x.Items.Count,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(ct);
```
Endpoint summary không cần materialize toàn bộ `OrderItem` entities.

**Lưu ý:**
Projection phức tạp vẫn có thể sinh SQL đắt. Kiểm tra generated SQL/execution plan khi query quan trọng; đừng chuyển sang client-side evaluation hoặc tạo một “mega DTO query” khó bảo trì chỉ để giảm số round trip.

### Tip 2 — SSRF không được chặn chỉ bằng cách kiểm tra URL bắt đầu bằng `https://`

**Mẹo:**
Nếu backend tải URL do user hoặc external payload cung cấp, dùng allowlist host/scheme, kiểm soát redirect và network egress thay vì chỉ parse URL hoặc yêu cầu HTTPS.

**Tại sao hữu ích:**
Một URL hợp lệ vẫn có thể trỏ tới loopback, private network, cloud metadata endpoint hoặc redirect tới đích nội bộ. Khi server thực hiện request, attacker lợi dụng network privileges của chính application để truy cập tài nguyên mà client bên ngoài không nhìn thấy.

**Ví dụ:**
Image-import API chỉ nên gọi các media domains đã được business cho phép. Resolve/validate destination theo policy, giới hạn redirect và timeout; ở infrastructure layer, chặn workload truy cập các network ranges không cần thiết.

**Lưu ý:**
Blocklist chuỗi như `localhost` là chưa đủ vì DNS, IPv6, alternate address representation và redirect có thể phá assumption. Với URL arbitrary thật sự cần hỗ trợ, SSRF defense phải có cả application validation lẫn network-level controls.

### Tip 3 — MongoDB compound index phải đi theo query shape, không theo danh sách field “hay dùng”

**Mẹo:**
Thiết kế compound index từ filter, sort và cardinality của query thực tế; dùng `explain()` để xác nhận số document/key được scan thay vì thêm index cho từng field riêng lẻ.

**Tại sao hữu ích:**
MongoDB không tự động biến nhiều single-field indexes thành compound index tối ưu cho mọi query. Một index đúng prefix có thể vừa thu hẹp candidate set vừa hỗ trợ sort, tránh scan/sort lớn trong memory.

**Ví dụ:**
Query thường xuyên:
```javascript
db.orders.find({ tenantId: t, status: "Pending" })
         .sort({ createdAt: -1 })
         .limit(50)
```
Có thể đánh giá index `{ tenantId: 1, status: 1, createdAt: -1 }` dựa trên distribution và `explain("executionStats")` thay vì tạo ba index độc lập rồi đoán optimizer sẽ ghép chúng hiệu quả.

**Lưu ý:**
Mỗi index tăng write/storage cost. Thứ tự field không thể chọn chỉ bằng câu thần chú “field selectivity cao nhất trước”; equality/range/sort pattern và workload tổng thể mới quyết định thiết kế phù hợp.

### Tip 4 — `git bisect` biến regression hunt thành binary search có bằng chứng

**Mẹo:**
Khi biết một commit cũ tốt và HEAD lỗi, dùng `git bisect` để thu hẹp commit gây regression; nếu có test/script tái hiện ổn định, cho bisect chạy tự động.

**Tại sao hữu ích:**
Đọc tuần tự hàng chục hoặc hàng trăm commits dễ bị bias bởi commit message và tốn thời gian. Binary search giảm số lần kiểm tra đáng kể và buộc mỗi bước dựa trên behavior tái hiện được.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test --filter FullyQualifiedName~CheckoutRegression
git bisect reset
```
Một regression test deterministic có thể tự tìm candidate commit thay vì checkout thủ công từng revision.

**Lưu ý:**
Bisect chỉ đáng tin khi tiêu chí good/bad deterministic. Build hỏng hoặc test flaky cần được xử lý/skip đúng cách; commit đầu tiên làm test fail cũng chưa chắc là root cause cuối cùng nếu test hoặc environment assumption sai.

### Tip 5 — CMS cache key phải chứa các dimensions làm thay đổi nội dung

**Mẹo:**
Khi cache rendered fragment hoặc API response của CMS, đưa các dimensions thực sự ảnh hưởng output như site, language, content version/route và personalization scope vào cache key hoặc invalidation strategy.

**Tại sao hữu ích:**
Cache hit cao không có giá trị nếu key thiếu context. Một key chỉ theo content ID có thể khiến bản tiếng Việt được trả cho request tiếng Anh, preview content rò sang published traffic hoặc tenant/site này nhận content của site khác.

**Ví dụ:**
Thay vì `content:{id}`, một fragment cache có thể cần semantic key tương đương `site:{site}:lang:{culture}:content:{id}:variant:{variant}` và invalidation khi content publish/change làm output tương ứng mất hiệu lực.

**Lưu ý:**
Đừng đưa mọi request attribute vào key vì sẽ phá cache hit ratio và gây cardinality explosion. Xác định dimension từ rendering semantics; dữ liệu per-user nhạy cảm thường không nên dùng shared cache nếu isolation không được chứng minh rõ.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency bảo vệ invariant mà không giữ lock xuyên thời gian người dùng suy nghĩ

**Khái niệm:**
Optimistic Concurrency cho phép nhiều actor đọc cùng state nhưng yêu cầu update chứng minh rằng version mình đã đọc vẫn còn hiện hành. Nếu version thay đổi, update bị từ chối và application quyết định retry, merge hoặc yêu cầu user xử lý conflict.

**Vấn đề nó giải quyết:**
Một user mở màn hình chỉnh sửa Order, user khác cập nhật Order trước, rồi user đầu tiên save dữ liệu cũ. Nếu update chỉ dựa trên `Id`, thay đổi mới có thể bị lost update mà không có lỗi nào.

**Ví dụ thực tế:**
EF Core map `rowversion`/concurrency token. `UPDATE` bao gồm cả `Id` và version cũ; nếu affected rows bằng 0, EF Core phát hiện `DbUpdateConcurrencyException`. Application có thể reload current values và áp business policy thay vì âm thầm overwrite.

**Trade-off:**
Optimistic concurrency phù hợp khi conflict tương đối hiếm và transaction không nên giữ lock lâu. Khi contention rất cao hoặc invariant yêu cầu serialize access chặt, repeated conflicts/retries có thể đắt và một chiến lược khác phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần xử lý concurrency token và conflict path thay vì catch rồi retry vô hạn. Senior / Technical developer phải xác định invariant nào cần bảo vệ, conflict nào có thể merge, UX khi conflict xảy ra và khi nào database constraint, atomic statement hoặc pessimistic coordination đơn giản/an toàn hơn.

### Design 2 — Azure Functions vs Worker Service nên chọn theo execution model, không theo độ “cloud-native”

**Khái niệm:**
Azure Functions cung cấp trigger-driven/serverless execution và managed scaling; Worker Service là long-running process cho phép kiểm soát lifecycle, concurrency và hosting model trực tiếp hơn. Cả hai đều có thể xử lý background work nhưng operational model khác nhau.

**Vấn đề nó giải quyết:**
Team cần xử lý queue/event/schedule nhưng dễ chọn Functions chỉ vì có trigger tiện, hoặc Worker chỉ vì quen .NET hosting. Sai execution model có thể tạo cold-start sensitivity, scaling behavior khó kiểm soát hoặc infrastructure phải tự vận hành quá mức cần thiết.

**Ví dụ thực tế:**
Một event handler ngắn, stateless, bursty có thể phù hợp với Function + Service Bus trigger. Một processor cần giữ long-lived connection, kiểm soát bounded concurrency tinh chỉnh và chạy pipeline kéo dài có thể phù hợp Worker Service hơn.

**Trade-off:**
Functions giảm hosting boilerplate và có elastic execution nhưng thêm platform constraints/cost model và behavior retry/scaling phải hiểu rõ. Worker cho nhiều control hơn nhưng team chịu trách nhiệm deployment, scaling và process health nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, cancellation và idempotency của runtime mình dùng. Senior / Technical developer phải so workload duration, burst pattern, latency requirement, scaling semantics, operational ownership và cost; không biến lựa chọn hosting thành quyết định kiến trúc theo trend.

### Design 3 — CQRS chỉ đáng giá khi read/write pressures thực sự khác nhau

**Khái niệm:**
CQRS tách model/path xử lý command khỏi model/path phục vụ query ở mức phù hợp với hệ thống. Nó không bắt buộc microservices, event sourcing hay hai database; mức tách có thể từ application handlers riêng tới read model vật lý riêng.

**Vấn đề nó giải quyết:**
Một domain có write model giàu invariant nhưng read screens cần projections hoàn toàn khác, hoặc read/write có scaling và optimization pressure khác nhau. Ép một entity model phục vụ cả hai có thể tạo query khó tối ưu và domain model bị kéo theo UI concerns.

**Ví dụ thực tế:**
Order write path kiểm soát state transitions và payment invariant; dashboard chỉ cần denormalized order summaries. Ban đầu cả command/query có thể dùng cùng SQL database nhưng model/query code tách rõ. Chỉ khi evidence yêu cầu mới xây asynchronous read model riêng.

**Trade-off:**
CQRS ở mức sâu thêm synchronization, eventual consistency, duplicate processing, monitoring và mental overhead. CRUD application với read/write đơn giản thường không thu được lợi ích tương xứng; “mỗi request một command/query class” cũng chưa tự động tạo kiến trúc tốt.

**Middle → Senior insight:**
Middle developer cần tách mutation intent khỏi query side effects và giữ validation/invariant đúng nơi. Senior / Technical developer phải quyết định mức CQRS tối thiểu đủ giải quyết pressure hiện tại, đánh giá consistency tolerance và tránh kéo Event Sourcing/distributed infrastructure vào hệ thống khi chưa có nhu cầu thực tế.
