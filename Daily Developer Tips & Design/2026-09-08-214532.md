# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Chuẩn hóa API error bằng `ProblemDetails` thay vì trả object lỗi tùy ý

**Mẹo:**
Với ASP.NET Core API, dùng `ProblemDetails`/`IProblemDetailsService` hoặc exception handler tập trung để biến lỗi validation, not-found và unexpected exception thành contract nhất quán thay vì mỗi endpoint tự dựng JSON lỗi riêng.

**Tại sao hữu ích:**
Client dễ xử lý hơn khi error response có cấu trúc ổn định như `status`, `title`, `detail`, `type` và extension fields. Quan trọng hơn, centralized handling giúp tách HTTP concern khỏi business logic và giảm nguy cơ vô tình lộ stack trace hoặc dữ liệu nhạy cảm ra production.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();

app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);

    return order is null
        ? Results.Problem(
            statusCode: StatusCodes.Status404NotFound,
            title: "Order not found")
        : Results.Ok(order);
});
```

**Lưu ý:**
Đừng dùng HTTP 500 cho mọi lỗi business. Validation, conflict, authorization và dependency failure có semantics khác nhau. Đồng thời không nên nhét internal exception message trực tiếp vào `detail` ở production.

### Tip 2 — Chọn Cosmos DB partition key theo traffic distribution, không chỉ theo data model đẹp

**Mẹo:**
Khi thiết kế container Cosmos DB, hãy kiểm tra partition key có phân tán cả storage lẫn request volume hay không. Một key có cardinality cao nhưng traffic dồn vào vài giá trị vẫn có thể tạo hot partition.

**Tại sao hữu ích:**
Cosmos DB scale theo physical partition. Nếu phần lớn request tập trung vào một logical partition, RU/s khả dụng của toàn container không giúp nhiều cho workload đó; latency và throttling có thể xuất hiện dù tổng capacity nhìn vẫn còn dư.

**Ví dụ:**
Với event system multi-tenant, chọn:
```text
partition key = tenantId
```

có thể ổn khi tenant tương đối cân bằng. Nhưng nếu một tenant chiếm 70% traffic, có thể cần key phân tán hơn, chẳng hạn strategy kết hợp tenant với bucket thời gian hoặc shard identifier tùy access pattern.

**Lưu ý:**
Đừng chọn partition key chỉ để tránh hot partition rồi làm query phải fan-out toàn container. Partition strategy phải cân bằng write distribution, query locality, transaction boundary và khả năng thay đổi schema sau này.

### Tip 3 — Phân biệt Kubernetes `readinessProbe` và `livenessProbe` để tránh restart sai nguyên nhân

**Mẹo:**
Dùng `readinessProbe` để xác định Pod có sẵn sàng nhận traffic hay chưa; dùng `livenessProbe` để phát hiện process bị kẹt và cần restart. Hai probe không nên mặc định gọi cùng một health check sâu.

**Tại sao hữu ích:**
Nếu dependency như database chậm tạm thời mà `livenessProbe` cũng fail theo, Kubernetes có thể restart application liên tục đúng lúc dependency đang gặp sự cố, làm incident nặng hơn. Readiness fail thường chỉ cần rút Pod khỏi Service endpoint.

**Ví dụ:**
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
```

`/health/ready` có thể kiểm tra dependency tối thiểu cần để phục vụ request, còn `/health/live` nên tập trung vào việc process có còn sống đúng nghĩa hay không.

**Lưu ý:**
Probe quá aggressive gây restart loop hoặc traffic flapping. Cần tính startup time, transient dependency failure, timeout và `failureThreshold`; với startup chậm có thể cần `startupProbe` riêng.

### Tip 4 — Dùng `git reflog` để cứu commit sau reset, rebase hoặc branch deletion nhầm

**Mẹo:**
Khi vừa `reset --hard`, rebase sai hoặc xóa branch và tưởng commit đã mất, kiểm tra `git reflog` trước khi kết luận phải làm lại code.

**Tại sao hữu ích:**
Git thường vẫn giữ object commit một thời gian dù branch ref đã di chuyển. Reflog ghi lại lịch sử thay đổi của `HEAD` và refs local, giúp tìm SHA cũ rồi tạo branch hoặc reset trở lại.

**Ví dụ:**
```bash
git reflog
```

Có thể thấy:
```text
8ab1c2d HEAD@{0}: reset: moving to HEAD~2
91f2e44 HEAD@{1}: commit: fix checkout race
```

Khôi phục:
```bash
git switch -c recover-checkout 91f2e44
```

**Lưu ý:**
Reflog là local và không phải backup vĩnh viễn; object không còn reachable cuối cùng có thể bị garbage collection. Với lịch sử đã push/shared, đừng force-push phục hồi mà không hiểu ảnh hưởng tới người khác.

### Tip 5 — Chặn SSRF khi backend nhận URL từ user rồi tự fetch tài nguyên

**Mẹo:**
Nếu application có feature import image, webhook test, PDF preview hoặc fetch metadata từ URL do user cung cấp, hãy coi đó là SSRF boundary và validate destination trước khi backend gửi request.

**Tại sao hữu ích:**
Attacker có thể đưa URL trỏ tới localhost, private network, cloud metadata endpoint hoặc internal service mà họ không truy cập trực tiếp được. Backend trở thành proxy có quyền mạng cao hơn client.

**Ví dụ:**
Thay vì nhận bất kỳ URL nào:
```text
POST /preview
{ "url": "http://127.0.0.1:8080/admin" }
```

hãy áp dụng policy như allowlist scheme/host, chặn private/link-local address sau DNS resolution, giới hạn redirect và timeout, đồng thời kiểm tra lại destination sau redirect.

**Lưu ý:**
Chỉ regex hostname là chưa đủ vì DNS rebinding, redirect hoặc IPv6 representation có thể vượt qua check đơn giản. Với use case kiểm soát được, allowlist destination cụ thể thường an toàn hơn blocklist.

## 🧠 Software Design

### Design 1 — CQRS không đồng nghĩa phải có hai database hay Event Sourcing

**Khái niệm:**
CQRS tách model/flow xử lý command khỏi query khi hai phía có nhu cầu khác nhau. Mức triển khai có thể rất nhẹ: cùng application, cùng database nhưng command và query có model riêng; không bắt buộc phải thêm broker, read database hay Event Sourcing.

**Vấn đề nó giải quyết:**
Một domain có write logic nhiều invariant nhưng read side chủ yếu là dashboard/projection thường bị ép vào cùng entity model. Kết quả là query phải load aggregate không cần thiết hoặc domain entity bị thêm field chỉ để phục vụ UI.

**Ví dụ thực tế:**
Trong một Modular Monolith:
```text
PlaceOrderCommand
-> Order aggregate
-> EF Core transaction

GetOrderSummaryQuery
-> projection trực tiếp từ SQL/EF Core
-> OrderSummaryDto
```

Hai flow vẫn có thể dùng cùng SQL Server database nhưng không bắt buộc chung model.

**Trade-off:**
CQRS giúp model rõ theo intent và read side tối ưu hơn, nhưng thêm command/query types, mapping và mental overhead. Với CRUD đơn giản, split này có thể chỉ làm code dài hơn mà không tạo giá trị.

**Middle → Senior insight:**
Middle developer cần hiểu command thay đổi state còn query không nên tạo side effect. Senior / Technical developer phải chọn mức CQRS phù hợp với domain pressure và chỉ tách datastore/event pipeline khi scaling, consistency hoặc ownership thực sự yêu cầu.

### Design 2 — Azure Service Bus Queue vs Topic: chọn theo ownership của consumer

**Khái niệm:**
Queue phù hợp khi một message đại diện cho work cần được một consumer logical xử lý. Topic + subscriptions phù hợp khi cùng một event cần được nhiều consumer độc lập nhận và xử lý theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Dùng queue cho domain event có nhiều downstream consumer buộc producer biết từng destination hoặc phải duplicate send. Ngược lại, dùng topic cho command có một owner duy nhất có thể làm ownership mơ hồ và vô tình tạo nhiều handler cạnh tranh semantics.

**Ví dụ thực tế:**
```text
GenerateInvoiceCommand
-> Queue: billing-commands
```

nhưng:
```text
OrderCompleted
-> Topic: order-events
   -> analytics subscription
   -> loyalty subscription
   -> notification subscription
```

Mỗi subscription có retry/DLQ riêng.

**Trade-off:**
Queue đơn giản hơn cho work distribution và competing consumers. Topic tăng extensibility và consumer autonomy nhưng thêm subscription management, duplicate delivery, schema evolution và observability cho nhiều downstream path.

**Middle → Senior insight:**
Middle developer cần phân biệt command với event và xử lý message idempotently. Senior / Technical developer phải quyết định ownership, fan-out semantics, ordering, retry isolation và tác động khi thêm consumer mới vào production.

### Design 3 — Blue/Green vs Rolling Deployment: chọn theo rollback và capacity constraint

**Khái niệm:**
Blue/Green giữ hai environment/version riêng và chuyển traffic từ bản cũ sang bản mới khi đã verify. Rolling Deployment thay dần instance cũ bằng instance mới trong cùng fleet.

**Vấn đề nó giải quyết:**
Cả hai đều giảm downtime so với stop-all deployment, nhưng chúng tối ưu khác nhau: Blue/Green ưu tiên cutover/rollback nhanh; Rolling ưu tiên sử dụng infrastructure tiết kiệm hơn và rollout từng phần.

**Ví dụ thực tế:**
Blue/Green:
```text
Blue = v4.2 đang phục vụ 100%
Green = v4.3 đã deploy + smoke test
switch traffic -> Green
```

Rolling:
```text
10 pods v4.2
-> thay 2 pods bằng v4.3
-> tiếp tục từng batch cho tới 100%
```

**Trade-off:**
Blue/Green cần capacity gần gấp đôi trong thời gian rollout và database migration phải backward-compatible với cả hai version. Rolling tiết kiệm hơn nhưng trong lúc rollout có nhiều version chạy đồng thời, khiến compatibility và rollback phức tạp hơn.

**Middle → Senior insight:**
Middle developer cần đảm bảo health check và backward compatibility trong thời gian deploy. Senior / Technical developer phải tính capacity, migration sequence, session/state behavior, rollback speed và blast radius để chọn strategy phù hợp thay vì mặc định một kiểu cho mọi service.
