# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncDisposable` khi cleanup thực sự có I/O bất đồng bộ

**Mẹo:**
Nếu resource cleanup cần flush network stream, đóng async writer hoặc hoàn tất I/O bất đồng bộ, triển khai `IAsyncDisposable` và dùng `await using` thay vì ép toàn bộ cleanup vào `Dispose()` đồng bộ.

**Tại sao hữu ích:**
`Dispose()` đồng bộ không thể `await`. Nếu cleanup chứa async I/O nhưng bị ép chạy sync-over-async, code có thể block thread, tăng latency hoặc gây deadlock trong môi trường có synchronization context. `IAsyncDisposable` cho phép resource kết thúc lifecycle đúng semantics.

**Ví dụ:**
```csharp
await using var writer = await auditStore.OpenWriterAsync(ct);
await writer.WriteAsync(entry, ct);
```

Resource có thể flush dữ liệu bất đồng bộ trong `DisposeAsync()` trước khi scope kết thúc.

**Lưu ý:**
Không thêm `IAsyncDisposable` chỉ vì class có async method. Cleanup phải thực sự cần async I/O. Nếu chỉ release memory handle hoặc object managed đơn giản, `IDisposable` vẫn phù hợp hơn.

### Tip 2 — Khi SQL Server deadlock xảy ra, đọc deadlock graph thay vì chỉ tăng retry

**Mẹo:**
Nếu production có deadlock, thu deadlock graph/XML để xác định transaction nào giữ lock, transaction nào chờ và thứ tự access resource gây cycle trước khi chỉnh timeout hoặc retry count.

**Tại sao hữu ích:**
Deadlock là chu trình phụ thuộc lock. Retry chỉ giúp request có cơ hội chạy lại, nhưng nếu hai code path luôn lock table/index theo thứ tự ngược nhau thì deadlock sẽ tiếp tục xuất hiện khi concurrency tăng.

**Ví dụ:**
```text
Transaction A: lock Orders -> chờ Inventory
Transaction B: lock Inventory -> chờ Orders
```

Giải pháp thường là thống nhất access order, rút ngắn transaction, giảm lock footprint hoặc sửa query/index làm scan quá rộng.

**Lưu ý:**
Không phải mọi blocking đều là deadlock. Blocking dài có thể do transaction mở quá lâu nhưng không tạo cycle. Dùng evidence từ Extended Events/deadlock graph để phân biệt.

### Tip 3 — Với Redis hot key, scale-out application không giải quyết bottleneck ở một shard

**Mẹo:**
Nếu một Redis key nhận traffic cực lớn, kiểm tra key distribution và command latency thay vì chỉ tăng số instance của application. Một hot key có thể dồn hầu hết request vào cùng Redis node/shard.

**Tại sao hữu ích:**
Distributed cache chỉ scale tốt khi workload cũng phân bố. Một key như `homepage:global` hoặc `product:top-1` có thể trở thành single hotspot, làm CPU/network trên một node tăng trong khi shard khác nhàn rỗi.

**Ví dụ:**
```text
80% cache traffic -> key "catalog:featured"
-> một shard chịu phần lớn GET
-> app scale từ 10 lên 30 instances
-> Redis hotspot còn nặng hơn
```

Có thể cân nhắc local cache ngắn hạn, key replication/read strategy hoặc thay đổi data shape tùy consistency requirement.

**Lưu ý:**
Đừng shard một key lớn thành nhiều key theo phản xạ nếu operation cần atomicity. Trước tiên xác nhận hot key bằng metrics/slowlog và hiểu consistency trade-off của giải pháp.

### Tip 4 — Kubernetes readiness probe phải phản ánh “có nhận traffic được không”, không phải “process còn sống không”

**Mẹo:**
Tách readiness và liveness theo mục đích: readiness trả lời Pod đã sẵn sàng phục vụ traffic chưa; liveness chỉ xác định process có mắc kẹt tới mức cần restart hay không.

**Tại sao hữu ích:**
Nếu readiness probe chỉ trả 200 ngay khi process start, Service có thể gửi traffic trước khi app load config, warm cache hoặc hoàn tất migration dependency. Ngược lại, nếu liveness kiểm tra dependency ngoài quá chặt, outage của database có thể khiến Kubernetes restart toàn bộ Pod liên tục.

**Ví dụ:**
```text
/readiness -> app initialized + critical local startup complete
/liveness  -> process/event loop còn hoạt động
```

Dependency downstream có thể được thể hiện qua degraded readiness tùy architecture, không mặc định đưa hết vào liveness.

**Lưu ý:**
Probe quá nhạy tạo restart storm hoặc traffic flapping. Timeout, failure threshold và startup duration phải dựa trên behavior thực tế của application.

### Tip 5 — Với Optimizely CMS, tách cache theo content dependency để invalidate chính xác hơn

**Mẹo:**
Khi cache output hoặc view model từ content CMS, gắn cache dependency vào content/version liên quan thay vì dùng TTL dài cho mọi thứ rồi chấp nhận dữ liệu stale sau publish.

**Tại sao hữu ích:**
CMS có editorial workflow: content có thể được publish bất kỳ lúc nào. Nếu cache không biết content nào đã thay đổi, team thường chọn TTL ngắn làm cache hit thấp hoặc TTL dài làm editor thấy nội dung cập nhật chậm.

**Ví dụ:**
```text
Homepage cache
depends on:
- HomePage content version
- HeroBlock version
- FeaturedArticles collection
```

Khi một dependency publish version mới, chỉ cache liên quan bị invalidated thay vì clear toàn site.

**Lưu ý:**
Dependency graph quá chi tiết có thể phức tạp và tốn invalidation cost. Với dữ liệu ít quan trọng, TTL đơn giản vẫn có thể là lựa chọn tốt hơn.

## 🧠 Software Design

### Design 1 — Transaction Boundary: đừng giữ database transaction mở qua external API call

**Khái niệm:**
Database transaction nên bao quanh phần thay đổi dữ liệu cần atomicity trong database. External HTTP/API call thường không thuộc cùng ACID boundary và không nên bị “nhét” vào transaction chỉ để code nhìn tuần tự.

**Vấn đề nó giải quyết:**
Nếu application mở SQL transaction, update dữ liệu rồi gọi payment API mất 3 giây trước khi commit, lock bị giữ suốt thời gian network call. Khi dependency chậm, blocking và deadlock risk tăng; rollback cũng không thể undo side effect đã xảy ra ở external system.

**Ví dụ thực tế:**
Không tốt:
```text
BEGIN TRANSACTION
update Order
call Payment API
update PaymentStatus
COMMIT
```

Một design tốt hơn có thể commit state chuyển tiếp rồi xử lý external side effect qua workflow/idempotency/outbox tùy consistency requirement.

**Trade-off:**
Transaction ngắn giảm lock contention và tách failure domain, nhưng buộc system xử lý trạng thái trung gian/eventual consistency. Giữ mọi thứ synchronous đơn giản hơn về mental model nhưng không tạo atomicity thật với external service.

**Middle → Senior insight:**
Middle developer cần hiểu transaction chỉ bảo vệ resource manager tương ứng và tránh gọi network trong transaction dài. Senior / Technical developer phải thiết kế state machine, retry, compensation và idempotency để business invariant vẫn đúng khi external call thành công/thất bại ở mọi điểm.

### Design 2 — Shared Database vs Database-per-Service

**Khái niệm:**
Shared Database cho nhiều module/service dùng chung schema/database, trong khi Database-per-Service giao ownership dữ liệu riêng cho từng service và giao tiếp qua contract thay vì query trực tiếp table của nhau.

**Vấn đề nó giải quyết:**
Shared DB giúp transaction/reporting đơn giản lúc đầu nhưng tạo coupling mạnh: service A phụ thuộc schema nội bộ của service B, deploy độc lập khó và ownership mơ hồ. Database-per-Service tăng isolation nhưng làm cross-service query/transaction phức tạp hơn.

**Ví dụ thực tế:**
```text
Shared DB:
Orders service đọc trực tiếp Customers table

Database-per-Service:
Orders giữ CustomerSnapshot cần thiết
Customer changes -> event/API contract
```

Không nhất thiết phải có server database riêng; logical schema/ownership boundary cũng có thể là bước đầu.

**Trade-off:**
Shared DB đơn giản cho join, ACID transaction và operations nhỏ nhưng tăng coupling/migration risk. Database-per-Service tăng autonomy và fault isolation nhưng thêm replication, eventual consistency, observability và data synchronization cost.

**Middle → Senior insight:**
Middle developer cần tôn trọng ownership boundary ngay cả khi cùng database. Senior / Technical developer phải chọn mức isolation dựa trên deployment autonomy, team ownership, scale, compliance và cost vận hành—không tách database chỉ vì dùng Microservices.

### Design 3 — Build vs Buy cho capability không tạo lợi thế cạnh tranh

**Khái niệm:**
Build vs Buy là quyết định xem capability nên tự phát triển hay dùng managed service/SaaS/package bên ngoài. Quyết định không chỉ so chi phí license với effort coding mà phải tính vận hành, security, lock-in và tốc độ thay đổi.

**Vấn đề nó giải quyết:**
Team có thể mất nhiều tháng tự xây authentication, search, email delivery hoặc monitoring trong khi các capability này không tạo khác biệt business. Ngược lại, mua vendor cho core workflow đặc thù có thể tạo constraint và migration cost lớn.

**Ví dụ thực tế:**
```text
Email delivery:
Buy -> managed provider, reputation/bounce handling có sẵn

Core pricing engine:
Build -> business rule đặc thù, thay đổi thường xuyên, cần kiểm soát sâu
```

**Trade-off:**
Buy rút ngắn time-to-market và giảm operational burden nhưng thêm recurring cost, vendor dependency và giới hạn customization. Build tăng control và domain fit nhưng đòi hỏi engineering, security, reliability và maintenance lâu dài.

**Middle → Senior insight:**
Middle developer cần đánh giá integration surface và failure handling của vendor. Senior / Technical developer phải tính total cost of ownership, exit strategy, compliance, SLA, lock-in và strategic differentiation thay vì mặc định “tự build mới linh hoạt”.
