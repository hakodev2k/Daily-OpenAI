# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `ValueTask` chỉ vì nghĩ nó luôn nhanh hơn `Task`

**Mẹo:**
Chỉ cân nhắc `ValueTask` khi một API hot path thường hoàn thành synchronously và profiling cho thấy allocation của `Task` thực sự đáng kể. Với phần lớn application code, `Task` đơn giản và an toàn hơn.

**Tại sao hữu ích:**
`ValueTask` có thể tránh allocation trong một số trường hợp, nhưng nó là struct lớn hơn reference `Task`, có semantics sử dụng phức tạp hơn và có thể làm code khó compose. Một `ValueTask` không nên bị `await` nhiều lần hoặc lưu giữ tùy tiện nếu implementation dùng `IValueTaskSource`.

**Ví dụ:**
```csharp
public ValueTask<User?> GetCachedUserAsync(int id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadUserAsync(id));
}
```

Trường hợp cache hit rất cao có thể hưởng lợi vì không cần tạo `Task` mới cho path sync.

**Lưu ý:**
Không đổi hàng loạt `Task` thành `ValueTask` theo style guideline. Nếu method gần như luôn chạy async thật sự, lợi ích có thể bằng không hoặc âm. Đo allocation và throughput trước khi tối ưu.

### Tip 2 — SQL Server đổi execution plan sau khi dữ liệu thay đổi: kiểm tra statistics trước khi ép hint

**Mẹo:**
Nếu một query từng nhanh nhưng đột nhiên chậm dù code không đổi, kiểm tra estimated/actual row count, statistics age và data distribution trước khi thêm query hint hoặc ép index.

**Tại sao hữu ích:**
Optimizer chọn plan dựa trên cardinality estimate. Khi statistics không phản ánh distribution mới, estimate sai có thể khiến SQL Server chọn nested loop, scan, memory grant hoặc join order không còn phù hợp.

**Ví dụ:**
```sql
SELECT s.name, o.name, sp.last_updated, sp.rows, sp.rows_sampled
FROM sys.stats AS s
JOIN sys.objects AS o ON s.object_id = o.object_id
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE o.name = 'Orders';
```

Trong execution plan, nếu estimated rows là `100` nhưng actual rows là `500000`, đó là evidence đáng điều tra.

**Lưu ý:**
Không `UPDATE STATISTICS` toàn database một cách máy móc mỗi khi query chậm. Root cause còn có thể là parameter sensitivity, index change, data skew hoặc workload mới. Query hint có thể khóa hệ thống vào một plan chỉ phù hợp tạm thời.

### Tip 3 — Với Azure Functions, thiết kế poison-message path trước khi bật retry mạnh

**Mẹo:**
Với trigger từ queue hoặc Service Bus, xác định rõ retry count, dead-letter/poison destination và thông tin cần log để replay message thất bại. Đừng chỉ tăng số lần retry rồi hy vọng lỗi transient tự biến mất.

**Tại sao hữu ích:**
Một message hỏng dữ liệu hoặc vi phạm business rule có thể fail giống hệt nhau ở mọi lần retry. Retry quá nhiều làm tốn compute, gây log noise và chặn throughput cho message hợp lệ.

**Ví dụ:**
```text
Process InvoiceRequested
-> attempt 1: validation fails
-> attempt 2: validation fails
-> max delivery reached
-> dead-letter

DLQ metadata:
- MessageId
- CorrelationId
- failure reason
- application version
- first/last failure time
```

Runbook sau đó có thể phân biệt message cần sửa dữ liệu, replay hay bỏ vĩnh viễn.

**Lưu ý:**
Dead-letter queue không phải thùng rác. Nếu không có alert, dashboard và quy trình xử lý, message chỉ bị chuyển từ “đang lỗi” sang “bị quên”. Phân biệt lỗi transient với permanent trước khi thiết kế retry policy.

### Tip 4 — Trong Playwright, lưu auth state để giảm setup nhưng không chia sẻ state làm test phụ thuộc nhau

**Mẹo:**
Nếu nhiều test UI cần cùng trạng thái đăng nhập, có thể login một lần trong setup project rồi lưu `storageState`; các test sau reuse state đó thay vì lặp login qua UI.

**Tại sao hữu ích:**
UI login thường chậm và dễ flaky hơn API/setup trực tiếp. Reuse auth state rút ngắn suite và giảm phụ thuộc vào login page trong mọi test.

**Ví dụ:**
```ts
// setup
await page.goto('/login');
await page.getByLabel('Email').fill(user);
await page.getByLabel('Password').fill(password);
await page.getByRole('button', { name: 'Sign in' }).click();
await page.context().storageState({ path: 'playwright/.auth/user.json' });
```

Sau đó project test dùng:

```ts
use: { storageState: 'playwright/.auth/user.json' }
```

**Lưu ý:**
Không dùng cùng account nếu test thay đổi shared server state như cart, profile hoặc permissions. Khi đó cần account riêng, tenant riêng hoặc test-data isolation. File auth cũng có thể chứa token/cookie nhạy cảm, không commit vào Git.

### Tip 5 — Dùng Managed Identity để application truy cập Azure Key Vault thay vì giữ client secret

**Mẹo:**
Khi workload chạy trên Azure service hỗ trợ Managed Identity, ưu tiên cấp identity cho workload và RBAC tới Key Vault thay vì lưu `client_secret` trong config hoặc pipeline variable.

**Tại sao hữu ích:**
Client secret có lifecycle riêng: phải tạo, phân phối, rotate và tránh bị log/lộ. Managed Identity để Azure quản lý credential nền, còn application chỉ yêu cầu token cho resource cần truy cập.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Trên local, `DefaultAzureCredential` có thể dùng developer identity; trên Azure, workload dùng Managed Identity.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Nếu identity được cấp quyền quá rộng trên cả vault hoặc subscription, blast radius vẫn lớn. Đồng thời phân biệt secret thật sự cần trong Key Vault với configuration không nhạy cảm nên nằm ở nơi khác.

## 🧠 Software Design

### Design 1 — Dùng trực tiếp `DbContext` hay thêm Repository abstraction phải dựa trên boundary thật sự

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like behavior cho aggregate/query. Repository riêng chỉ đáng giá khi nó tạo abstraction có ý nghĩa cho domain hoặc use case, không phải vì mọi project “phải có Repository Pattern”.

**Vấn đề nó giải quyết:**
Team có thể muốn gom query phức tạp, bảo vệ aggregate boundary hoặc cô lập persistence khỏi application core. Nhưng repository CRUD mỏng chỉ wrap `Add`, `Find` và `SaveChanges` thường thêm indirection mà không giảm coupling thực tế.

**Ví dụ thực tế:**
```text
Hợp lý:
IOrderRepository
- GetForCheckout(orderId)
- Add(order)

Không nhiều giá trị:
IGenericRepository<T>
- GetAll()
- Find(id)
- Update(entity)
- Delete(entity)
```

Với query-heavy application service, direct `DbContext` + projection đôi khi rõ hơn generic repository.

**Trade-off:**
Repository có thể bảo vệ domain semantics và hỗ trợ testing boundary, nhưng cũng dễ che mất khả năng mạnh của EF Core, tạo API generic nghèo nàn và tăng boilerplate. Direct `DbContext` đơn giản hơn nhưng application layer sẽ biết rõ persistence technology hơn.

**Middle → Senior insight:**
Middle developer cần tránh tạo repository chỉ để pass checklist kiến trúc. Senior / Technical developer phải xác định abstraction nào thực sự ổn định, query nào thuộc application read model và boundary persistence nào cần che giấu dựa trên domain complexity, testing strategy và migration risk.

### Design 2 — Azure Service Bus Queue và Topic giải quyết hai kiểu ownership khác nhau

**Khái niệm:**
Queue phù hợp khi một logical work item cần được xử lý bởi một consumer group; Topic + Subscription phù hợp khi cùng một event cần được nhiều consumer độc lập nhận theo fan-out semantics.

**Vấn đề nó giải quyết:**
Nếu `InvoiceGenerationRequested` chỉ cần một worker xử lý, queue giúp competing consumers chia workload. Nếu `OrderPlaced` phải đồng thời kích hoạt Inventory, Analytics và Notification, một queue duy nhất sẽ khiến các consumer tranh cùng message thay vì mỗi hệ thống nhận bản riêng.

**Ví dụ thực tế:**
```text
Queue: invoice-jobs
Worker A/B/C cạnh tranh xử lý từng message

Topic: order-events
├─ inventory subscription
├─ analytics subscription
└─ notification subscription
```

Mỗi subscription có retry, DLQ và filter riêng.

**Trade-off:**
Topic tăng khả năng mở rộng consumer độc lập nhưng tạo nhiều subscription state, duplicate delivery path và observability complexity. Queue đơn giản hơn nhưng không phù hợp cho broadcast event. Đừng dùng Topic chỉ vì nghe “event-driven” hơn.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumer khác fan-out consumer. Senior / Solution-oriented engineer phải xác định ownership của message, delivery semantics, ordering, retry/DLQ policy và consumer lifecycle trước khi chọn queue hay topic.

### Design 3 — Normalization và denormalization phải bám theo write integrity và read pattern

**Khái niệm:**
Normalization giảm duplication và giúp duy trì consistency trong transactional model; denormalization chấp nhận duplication có kiểm soát để đọc nhanh hơn hoặc đơn giản hóa read path.

**Vấn đề nó giải quyết:**
Một hệ thống order normalized tốt cho write nhưng dashboard phải join nhiều bảng lớn để tạo report mỗi request. Ngược lại, lưu mọi dữ liệu duplicated trong bảng chính có thể khiến update một thuộc tính phải sửa hàng triệu row và tăng nguy cơ inconsistency.

**Ví dụ thực tế:**
```text
Transactional model:
Orders -> OrderLines -> Products

Reporting read model:
DailySales
- Date
- ProductId
- ProductNameSnapshot
- Quantity
- Revenue
```

Read model được cập nhật từ transaction/event pipeline thay vì bắt dashboard join toàn bộ OLTP schema mỗi lần.

**Trade-off:**
Normalization tối ưu integrity nhưng có thể làm read query phức tạp. Denormalization cải thiện read performance nhưng thêm synchronization, storage và eventual-consistency concerns. Duplication chỉ hợp lý khi ownership và refresh mechanism rõ.

**Middle → Senior insight:**
Middle developer cần hiểu “ít join hơn” không tự động nghĩa schema tốt hơn. Senior / Technical developer phải phân tách transactional invariant với read workload, đo bottleneck thực tế và quyết định nơi denormalize dựa trên consistency requirement, write amplification và operational cost.
