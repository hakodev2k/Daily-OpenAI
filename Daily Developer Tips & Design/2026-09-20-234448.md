# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — Đọc GC counters trước khi đổ lỗi cho “memory leak”

**Mẹo:**
Khi memory của .NET service tăng, quan sát allocation rate, Gen 0/1/2 collections, GC heap size và LOH trước khi kết luận có leak. Kết hợp `dotnet-counters`, dump hoặc profiler để phân biệt high allocation, retained objects và native memory.

**Tại sao hữu ích:**
Working Set tăng không đồng nghĩa managed objects bị giữ vĩnh viễn. GC có thể giữ committed memory để tái sử dụng; ngược lại, allocation rate cao có thể tạo GC pressure dù heap cuối cùng không tăng liên tục.

**Ví dụ:**
Một API tăng latency sau deployment. Heap size khá ổn nhưng allocation rate tăng mạnh và Gen 2 collections xuất hiện thường xuyên. Trace chỉ ra response mapping tạo nhiều temporary strings; nguyên nhân là allocation pressure chứ không phải collection bị giữ vô hạn.

**Lưu ý:**
Đừng tối ưu allocation chỉ vì thấy nhiều Gen 0 collections. Cần liên hệ counters với latency, CPU và memory budget; native allocations, sockets hoặc image libraries cũng có thể làm process memory tăng ngoài managed heap.

### Tip 2 — EF Core projection thường tốt hơn `Include` khi endpoint chỉ cần DTO

**Mẹo:**
Với read endpoint, dùng `Select` để projection trực tiếp các fields cần thiết thay vì load toàn bộ entity graph rồi map sang DTO trong memory.

**Tại sao hữu ích:**
Projection cho phép EF Core tạo SQL chỉ lấy columns và relationships cần dùng, giảm network payload, materialization và Change Tracker overhead. Nó cũng làm query intent rõ hơn.

**Ví dụ:**
Product listing chỉ cần `Id`, `Name`, `Price` và category name. Projection trực tiếp thành DTO tránh load description, audit fields và toàn bộ navigation collections mà response không sử dụng.

**Lưu ý:**
Projection phức tạp vẫn có thể tạo SQL xấu. Kiểm tra generated SQL và execution plan cho query quan trọng; đừng tạo một DTO khổng lồ chỉ để thay entity graph bằng một graph khác.

### Tip 3 — Managed Identity loại bỏ secret nhưng không loại bỏ authorization design

**Mẹo:**
Trên Azure, ưu tiên Managed Identity khi App Service, Function hoặc workload cần truy cập Key Vault, Blob Storage hay resource hỗ trợ Microsoft Entra authentication; sau đó cấp đúng role tối thiểu cần thiết.

**Tại sao hữu ích:**
Application không phải lưu client secret và không cần tự xoay credential. Azure quản lý identity lifecycle, giảm một lớp secret-management risk.

**Ví dụ:**
ASP.NET Core App Service đọc Blob Storage bằng Managed Identity được cấp quyền đọc container cần thiết, thay vì lưu storage account key trong configuration hoặc CI/CD variable.

**Lưu ý:**
Managed Identity không có nghĩa “secure by default”. Gán role quá rộng vẫn tạo blast radius lớn; local development cũng cần credential chain rõ ràng và không được fallback sang embedded secret.

### Tip 4 — `git range-diff` hữu ích khi review một branch sau rebase

**Mẹo:**
Khi một PR được rebase hoặc commit history bị rewrite, dùng `git range-diff` để so sánh hai chuỗi commits thay vì cố đối chiếu SHA cũ với SHA mới bằng mắt.

**Tại sao hữu ích:**
Rebase tạo commit IDs mới dù logical changes có thể gần như giống nhau. `range-diff` tập trung vào sự thay đổi giữa hai patch series, giúp reviewer thấy commit nào bị sửa, thêm hoặc mất.

**Ví dụ:**
Sau khi author rebase 12 commits lên `main`, reviewer chạy `git range-diff old-base..old-tip new-base..new-tip` để xác định chính xác những patch nào thay đổi kể từ vòng review trước.

**Lưu ý:**
Đây không thay thế review final diff và tests. Nếu commits bị squash/reorder mạnh, mapping có thể khó đọc; luôn xác nhận behavior cuối cùng trên branch hiện tại.

### Tip 5 — Correlation ID không thay thế distributed trace context

**Mẹo:**
Trong distributed application, ưu tiên propagate chuẩn trace context qua HTTP/messaging và dùng correlation/business IDs như metadata bổ sung thay vì tự phát minh một ID duy nhất cho mọi mục đích.

**Tại sao hữu ích:**
Distributed tracing cần parent/child relationship giữa spans để tái dựng critical path và dependency latency. Một correlation string giúp tìm logs nhưng không tự mô tả causal tree giữa các operations.

**Ví dụ:**
Checkout request tạo trace đi qua API, Service Bus và payment worker. `OrderId` được gắn làm attribute để tìm theo business transaction, trong khi trace/span context giữ quan hệ kỹ thuật giữa từng hop.

**Lưu ý:**
Không ghi sensitive identifiers tùy tiện vào baggage/logs. Trace sampling cũng có thể làm mất một số traces, nên metrics và structured logs vẫn cần cho production diagnosis.

## 🧠 Software Design

### Design 1 — Repository abstraction chỉ đáng giá khi nó tạo boundary có ý nghĩa

**Khái niệm:**
Repository có thể biểu diễn collection/capability theo domain và che data-access details, nhưng EF Core `DbContext`/`DbSet` đã cung cấp nhiều Unit of Work và Repository-like semantics. Thêm generic repository không tự động cải thiện kiến trúc.

**Vấn đề nó giải quyết:**
Một domain phức tạp có thể cần boundary như `IOrderRepository` để encapsulate aggregate loading và persistence rules. Ngược lại, CRUD application có thể chỉ nhận thêm một lớp forwarding methods không tạo thêm invariants hay isolation.

**Ví dụ thực tế:**
Ordering module có repository method tải Order aggregate với concurrency semantics cụ thể. Reporting endpoints dùng trực tiếp query service/`DbContext` projection thay vì ép mọi query qua `GenericRepository<T>`.

**Trade-off:**
Repository domain-specific có thể giảm coupling với persistence decisions và tập trung invariants, nhưng abstraction thừa làm mất khả năng dùng EF Core hiệu quả, tăng boilerplate và thường dẫn tới leaky query interfaces.

**Middle → Senior insight:**
Middle developer cần hiểu `DbContext` lifecycle và tránh repository chỉ forwarding CRUD. Senior / Technical developer phải xác định abstraction dựa trên domain boundary, testability và volatility thực tế, không dựa trên template kiến trúc.

### Design 2 — Feature Flag tách deployment khỏi release nhưng tạo state cần quản trị

**Khái niệm:**
Feature Flag cho phép deploy code trước rồi bật capability cho một nhóm users/environment sau, giúp rollout và rollback behavior mà không cần deploy lại artifact.

**Vấn đề nó giải quyết:**
Một feature lớn có thể cần production validation, gradual rollout hoặc coordination với business date. Nếu deployment và release là một hành động duy nhất, mỗi thay đổi exposure đều kéo theo deployment risk.

**Ví dụ thực tế:**
Checkout flow mới được deploy ở trạng thái off, sau đó bật 5% traffic, quan sát error rate và conversion, rồi tăng dần. Nếu dependency mới lỗi, flag chuyển về old flow trong khi artifact vẫn giữ nguyên.

**Trade-off:**
Flags tạo nhiều runtime states, test combinations và dead code. Long-lived flags làm reasoning khó hơn và có thể trở thành configuration debt; kill switch cũng phải được kiểm thử trước incident.

**Middle → Senior insight:**
Middle developer cần implement cả on/off paths và tests đúng. Senior / Technical developer phải thiết kế ownership, rollout metrics, fail-safe default, expiry/removal policy và tránh dùng flags để che architecture chưa hoàn tất vô thời hạn.

### Design 3 — Read Model nên tối ưu cho nhu cầu đọc, không nhất thiết phản chiếu write model

**Khái niệm:**
Trong hệ thống có read requirements khác biệt rõ với transactional writes, read model có thể được projection/denormalize theo query shape thay vì bắt UI/reporting truy vấn trực tiếp aggregate hoặc normalized write schema.

**Vấn đề nó giải quyết:**
Write model thường tối ưu invariants và transactional consistency; dashboard/search/listing lại cần joins, aggregation hoặc shape khác. Ép một model phục vụ cả hai có thể làm query phức tạp và domain model bị kéo theo nhu cầu presentation.

**Ví dụ thực tế:**
Order write model giữ normalized transactional data. Back-office dashboard có read table/index chứa Order summary, customer display name và fulfillment status được cập nhật từ events, giúp list/filter nhanh mà không cần join nhiều bounded contexts ở request time.

**Trade-off:**
Read model cải thiện query simplicity và scaling nhưng thêm synchronization, eventual consistency, rebuild logic và operational monitoring. Với CRUD system nhỏ, projection trực tiếp từ relational database thường đơn giản hơn nhiều.

**Middle → Senior insight:**
Middle developer cần hiểu read model có thể stale và UI phải chịu được consistency window. Senior / Technical developer phải chứng minh read pressure đủ lớn, chọn update mechanism, recovery/rebuild strategy và quyết định khi nào CQRS-style separation đáng chi phí vận hành.
