# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Task.WhenAll` nhưng giới hạn concurrency

**Mẹo:**
Khi cần chạy nhiều I/O operation song song, `Task.WhenAll` có thể giảm tổng latency, nhưng với danh sách lớn nên giới hạn số operation đồng thời bằng `SemaphoreSlim` hoặc `Parallel.ForEachAsync`.

**Tại sao hữu ích:**
Tránh pattern tuần tự không cần thiết, đồng thời không làm cạn connection pool, socket hoặc quota của downstream service.

**Ví dụ:**
```csharp
await Parallel.ForEachAsync(
    userIds,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 8,
        CancellationToken = cancellationToken
    },
    async (userId, ct) =>
    {
        await client.SyncUserAsync(userId, ct);
    });
```

**Lưu ý:**
Không đặt concurrency thật cao chỉ vì workload là async. Giới hạn nên dựa trên capacity của database, API ngoài và connection pool.

### Tip 2 — Gắn `TagWith()` vào EF Core query để truy vết SQL production

**Mẹo:**
Dùng `TagWith()` cho các query quan trọng để SQL sinh ra chứa comment nhận diện use case hoặc endpoint.

**Tại sao hữu ích:**
Khi DBA hoặc APM phát hiện query chậm, tag giúp liên kết SQL về đúng đoạn application code mà không phải đoán từ câu SQL đã được ORM sinh ra.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .TagWith("OrdersApi:GetPendingOrders")
    .Where(x => x.Status == OrderStatus.Pending)
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Tag nên ngắn và ổn định. Không đưa `UserId`, token hoặc dữ liệu request động vào tag vì có thể làm query text biến đổi quá nhiều và lộ dữ liệu.

### Tip 3 — Dùng `FOR UPDATE SKIP LOCKED` cho nhiều worker lấy job từ database

**Mẹo:**
Nếu nhiều worker cùng poll một bảng queue trong PostgreSQL, có thể dùng `FOR UPDATE SKIP LOCKED` để mỗi worker lấy batch riêng mà không chờ row đang bị worker khác lock.

**Tại sao hữu ích:**
Giảm contention và cho phép xử lý song song mà không cần một distributed lock chung cho toàn queue.

**Ví dụ:**
```sql
BEGIN;

SELECT id
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 50;

-- update selected jobs to Processing
COMMIT;
```

**Lưu ý:**
Đây không phải message broker hoàn chỉnh. Bạn vẫn cần retry, timeout, recovery cho job bị kẹt và cơ chế tránh starvation.

### Tip 4 — Dùng `git range-diff` để review branch sau khi rebase

**Mẹo:**
Sau khi rebase hoặc rewrite nhiều commit, dùng `git range-diff` để xem commit series mới khác series cũ ở đâu.

**Tại sao hữu ích:**
Nó giúp reviewer kiểm tra xem rebase chỉ giải conflict hay vô tình thay đổi logic, hữu ích hơn việc đọc lại toàn bộ PR từ đầu.

**Ví dụ:**
```bash
git range-diff origin/main...feature-before origin/main...feature-after
```

**Lưu ý:**
`range-diff` so sánh chuỗi patch, không thay thế test hoặc code review cuối cùng của trạng thái branch.

### Tip 5 — Dùng `HttpCompletionOption.ResponseHeadersRead` khi tải response lớn

**Mẹo:**
Với file hoặc response body lớn, yêu cầu `HttpClient` trả quyền điều khiển ngay sau khi nhận headers rồi stream body thay vì buffer toàn bộ response trước.

**Tại sao hữu ích:**
Giảm peak memory và cho phép bắt đầu xử lý dữ liệu sớm hơn.

**Ví dụ:**
```csharp
using var response = await httpClient.GetAsync(
    url,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);

response.EnsureSuccessStatusCode();

await using var stream = await response.Content
    .ReadAsStreamAsync(cancellationToken);

await stream.CopyToAsync(targetStream, cancellationToken);
```

**Lưu ý:**
Khi stream trực tiếp, code của bạn chịu trách nhiệm dispose response/stream đúng cách và kiểm soát timeout, cancellation cũng như giới hạn kích thước dữ liệu.

## 🧠 Software Design

### Design 1 — Saga và Compensating Action cho transaction xuyên service

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction. Nếu bước sau thất bại, hệ thống chạy compensating action để đảo ngược hoặc bù trừ các bước đã hoàn thành.

**Vấn đề nó giải quyết:**
Trong Microservices, bạn thường không thể giữ một ACID transaction xuyên Order, Payment, Inventory và Shipping database.

**Ví dụ thực tế:**
Flow đặt hàng gồm reserve inventory → charge payment → tạo shipment. Nếu tạo shipment thất bại, saga có thể refund payment và release inventory thay vì rollback bằng một distributed database transaction.

**Trade-off:**
Tăng scalability và tránh distributed lock dài, nhưng flow phức tạp hơn: compensation có thể thất bại, state trung gian tồn tại lâu và debugging khó hơn.

**Middle → Senior insight:**
Middle developer cần hiểu compensation không phải luôn là “undo” hoàn hảo. Senior developer phải xác định step nào có thể bù trừ, step nào irreversible, cách persist saga state, idempotency của từng command và chiến lược recovery khi orchestrator bị restart.

### Design 2 — Backend for Frontend khi client có nhu cầu khác nhau

**Khái niệm:**
Backend for Frontend (BFF) tạo backend riêng hoặc API composition layer riêng cho từng loại client như web, mobile hoặc partner portal thay vì ép tất cả dùng cùng một API shape.

**Vấn đề nó giải quyết:**
Mobile có thể cần payload nhỏ và ít round-trip, trong khi admin portal cần dữ liệu tổng hợp lớn và capability khác hoàn toàn.

**Ví dụ thực tế:**
Mobile Home Screen cần một request trả profile, notification count và vài order gần nhất. BFF có thể aggregate nhiều downstream API thành response tối ưu cho mobile mà không làm domain service phụ thuộc UI.

**Trade-off:**
Giảm coupling giữa client và core services, nhưng thêm deployment unit, duplicate orchestration logic và nguy cơ biến BFF thành một monolith mới chứa business rule.

**Middle → Senior insight:**
Middle developer cần giữ BFF tập trung vào composition và client-specific concerns. Senior developer phải quyết định khi nào nhu cầu client đủ khác biệt để đáng thêm BFF, đồng thời ngăn business logic quan trọng bị phân tán sang nhiều BFF.

### Design 3 — Giảm Temporal Coupling trong chuỗi synchronous service calls

**Khái niệm:**
Temporal Coupling xảy ra khi một operation chỉ thành công nếu nhiều component hoặc service phải cùng online và phản hồi đúng thời điểm.

**Vấn đề nó giải quyết:**
Chuỗi synchronous `A → B → C → D` làm availability tổng thể giảm và latency cộng dồn; chỉ một dependency chậm cũng có thể làm request đầu vào timeout.

**Ví dụ thực tế:**
Sau khi user cập nhật profile, API đồng bộ gọi Audit Service, Notification Service và Analytics Service trước khi trả `200 OK`. Nếu notification bị down, một thay đổi profile hợp lệ cũng thất bại. Có thể chỉ commit profile trong critical path rồi publish event cho các side effect không bắt buộc xử lý asynchronous.

**Trade-off:**
Giảm temporal coupling giúp availability và response time tốt hơn, nhưng chuyển sang asynchronous flow tạo eventual consistency, duplicate message, retry và observability complexity.

**Middle → Senior insight:**
Middle developer cần phân biệt dependency nào nằm trong business invariant và dependency nào chỉ là side effect. Senior developer phải quyết định critical path dựa trên business semantics, failure tolerance và SLO thay vì chuyển mọi call sang message broker một cách máy móc.
