# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenSet<T>` cho tập lookup chỉ xây một lần nhưng đọc rất nhiều

**Mẹo:**
Nếu một tập dữ liệu được khởi tạo một lần rồi chỉ dùng để `Contains`, cân nhắc `FrozenSet<T>` thay vì giữ `HashSet<T>` mutable suốt vòng đời application.

**Tại sao hữu ích:**
`FrozenSet<T>` tối ưu layout cho read-heavy lookup và đồng thời thể hiện rõ intent: dữ liệu đã “đóng băng”, không còn thay đổi sau startup.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

private static readonly FrozenSet<string> AllowedActions =
    new[] { "read", "write", "approve", "export" }
        .ToFrozenSet(StringComparer.OrdinalIgnoreCase);

if (!AllowedActions.Contains(action))
{
    return Results.Forbid();
}
```

**Lưu ý:**
Chi phí tạo frozen collection cao hơn collection thường. Không phù hợp nếu dữ liệu thay đổi thường xuyên hoặc collection rất nhỏ và không nằm trên hot path.

### Tip 2 — Dùng `HttpRequestMessage.Options` thay vì nhét metadata nội bộ vào header

**Mẹo:**
Khi custom `DelegatingHandler` cần metadata nội bộ như tenant, retry policy hint hoặc audit context cho từng request, dùng `HttpRequestMessage.Options` thay vì tạo HTTP header giả.

**Tại sao hữu ích:**
Metadata chỉ tồn tại trong client pipeline, không vô tình bị gửi ra external service và không làm nhiễu HTTP contract.

**Ví dụ:**
```csharp
static readonly HttpRequestOptionsKey<string> TenantKey =
    new("TenantId");

var request = new HttpRequestMessage(
    HttpMethod.Get,
    "/api/orders");

request.Options.Set(TenantKey, tenantId);
```

Trong handler:

```csharp
if (request.Options.TryGetValue(TenantKey, out var tenantId))
{
    logger.LogDebug("Tenant={TenantId}", tenantId);
}
```

**Lưu ý:**
`Options` chỉ sống trong process hiện tại. Nếu downstream thực sự cần metadata đó, phải truyền qua contract/header phù hợp và có security review rõ ràng.

### Tip 3 — Xem `wait_type` trước khi kết luận SQL query “chậm vì thiếu index”

**Mẹo:**
Khi SQL Server query chạy lâu, kiểm tra request hiện tại đang chờ gì trước khi thêm index hoặc rewrite SQL.

**Tại sao hữu ích:**
Query có thể chậm vì lock, I/O, memory grant, parallelism hoặc network chứ không phải execution plan tệ. `wait_type` giúp khoanh vùng đúng hướng điều tra.

**Ví dụ:**
```sql
SELECT
    session_id,
    status,
    wait_type,
    wait_time,
    blocking_session_id,
    cpu_time,
    total_elapsed_time
FROM sys.dm_exec_requests
WHERE session_id <> @@SPID;
```

**Lưu ý:**
Một snapshot đơn lẻ chỉ cho thấy trạng thái tại thời điểm đó. Với incident kéo dài, cần correlate thêm execution plan, blocking chain, Query Store và resource metrics.

### Tip 4 — Dùng `git diff --dirstat` để biết thay đổi tập trung ở module nào

**Mẹo:**
Khi PR hoặc branch có rất nhiều file, dùng `git diff --dirstat` để xem tỷ trọng thay đổi theo folder trước khi đọc từng patch.

**Tại sao hữu ích:**
Giúp reviewer hiểu nhanh blast radius và phát hiện thay đổi bất thường lan sang module không liên quan.

**Ví dụ:**
```bash
git diff --dirstat=files,0 origin/main...HEAD
```

Ví dụ output:

```text
  65.0% src/Payments/
  20.0% tests/Payments/
  15.0% src/Shared/
```

**Lưu ý:**
Dirstat chỉ đo distribution của diff, không phản ánh risk. Một thay đổi nhỏ trong shared infrastructure vẫn có thể ảnh hưởng toàn hệ thống.

### Tip 5 — Dùng `journalctl` theo unit và time window khi debug Linux service

**Mẹo:**
Nếu service chạy bằng `systemd`, dùng `journalctl` với đúng unit và khoảng thời gian thay vì grep toàn bộ log hệ thống.

**Tại sao hữu ích:**
Nhanh chóng cô lập startup failure, restart loop, permission issue hoặc crash xảy ra đúng thời điểm deploy.

**Ví dụ:**
```bash
journalctl -u myapp.service \
  --since "30 minutes ago" \
  --no-pager
```

Theo dõi realtime:

```bash
journalctl -u myapp.service -f
```

**Lưu ý:**
Log retention của journal phụ thuộc cấu hình máy. Nếu incident cũ đã bị rotate, cần xem thêm centralized logging hoặc application log riêng.

## 🧠 Software Design

### Design 1 — Multi-tenant isolation: shared rows, schema riêng hay database riêng

**Khái niệm:**
Multi-tenant data isolation có nhiều mức: cùng bảng với `TenantId`, schema riêng theo tenant hoặc database riêng. Mỗi lựa chọn đổi khác cost, isolation và vận hành.

**Vấn đề nó giải quyết:**
Tenant cần được tách dữ liệu đủ an toàn trong khi hệ thống vẫn phải scale, deploy và vận hành với chi phí hợp lý.

**Ví dụ thực tế:**
Một SaaS nhỏ có hàng nghìn tenant dùng shared tables với `TenantId` + row-level filtering. Một enterprise tenant có yêu cầu compliance cao có thể được đưa sang database riêng nhưng vẫn dùng cùng application code.

**Trade-off:**
Shared database tiết kiệm tài nguyên và migration đơn giản hơn nhưng blast radius và risk query thiếu tenant filter cao hơn. Database-per-tenant tăng isolation, backup/restore độc lập nhưng provisioning, migration và connection management phức tạp hơn.

**Middle → Senior insight:**
Middle developer nên hiểu tenant isolation là security + operational decision, không chỉ thêm cột `TenantId`. Senior developer phải cân nhắc compliance, noisy neighbor, backup/restore, schema rollout, per-tenant customization và cost trước khi chọn model.

### Design 2 — Test nondeterministic boundaries thay vì cố mock toàn bộ hệ thống

**Khái niệm:**
Các boundary như clock, random number, network, filesystem và external API là nguồn nondeterminism chính. Thiết kế seam tại đây giúp test ổn định mà không cần mock mọi class trung gian.

**Vấn đề nó giải quyết:**
Test dễ trở nên brittle khi mock sâu implementation detail nhưng vẫn flaky vì thời gian, random hoặc dependency ngoài thay đổi.

**Ví dụ thực tế:**
Thay vì mock 8 service chỉ để kiểm tra expiry logic, inject `TimeProvider` vào use case. Test đặt thời gian cố định rồi kiểm tra rule `ExpiresAt <= now` một cách deterministic.

**Trade-off:**
Boundary seam đúng làm test rõ và ít coupling implementation hơn, nhưng tạo thêm abstraction ở nơi thực sự nondeterministic. Nếu lạm dụng interface cho mọi class, test lại trở nên mock-heavy và khó refactor.

**Middle → Senior insight:**
Middle developer nên ưu tiên kiểm soát clock/network/random trước khi mock implementation nội bộ. Senior developer cần thiết kế test boundary theo source of nondeterminism và giữ business behavior test gần với production path nhất có thể.

### Design 3 — Separate command acceptance khỏi command completion cho operation dài

**Khái niệm:**
Với operation mất nhiều thời gian, API có thể chỉ xác nhận command đã được chấp nhận rồi xử lý async, thay vì giữ HTTP request mở đến khi toàn bộ công việc hoàn tất.

**Vấn đề nó giải quyết:**
Export lớn, bulk import, provisioning hoặc external workflow kéo dài dễ vượt HTTP timeout và giữ thread/connection/resource lâu không cần thiết.

**Ví dụ thực tế:**
Client gọi:

```http
POST /exports
```

Server trả:

```http
202 Accepted
Location: /exports/job-123
```

Worker xử lý sau đó; client query status hoặc nhận notification khi hoàn tất.

**Trade-off:**
Giảm coupling với request timeout và scale background work tốt hơn, nhưng thêm job state, retry, idempotency, progress tracking và cleanup. Với operation dưới vài trăm milliseconds, async job chỉ làm hệ thống phức tạp hơn.

**Middle → Senior insight:**
Middle developer nên phân biệt HTTP request lifetime với business operation lifetime. Senior developer phải định nghĩa acceptance semantics, duplicate submission, status model, cancellation, retention và failure recovery trước khi chuyển sang async workflow.
