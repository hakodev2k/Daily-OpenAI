# Daily Developer Tips & Design — 2026-09-19

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt timeout với cancellation trong outbound HTTP

**Mẹo:**
Khi ASP.NET Core gọi downstream service, tách rõ request bị hủy bởi caller với timeout do policy/client. Propagate `CancellationToken` của request nhưng vẫn đặt timeout budget riêng cho dependency.

**Tại sao hữu ích:**
Hai failure có ý nghĩa vận hành khác nhau. Client disconnect thì tiếp tục work thường vô ích; downstream timeout lại là tín hiệu dependency chậm hoặc budget không phù hợp. Gộp cả hai thành một lỗi chung làm telemetry và retry decision sai.

**Ví dụ:**
Một checkout API có budget 3 giây cho pricing service. Nếu caller hủy request sau 500 ms, outbound call nên dừng theo token. Nếu pricing vượt 3 giây trong khi caller vẫn chờ, ghi nhận dependency timeout riêng để điều tra latency.

**Lưu ý:**
Đừng retry tự động mọi timeout. Operation có side effect cần idempotency, và retry phải nằm trong end-to-end latency budget thay vì nhân tổng thời gian chờ ngoài ý muốn.

### Tip 2 — EF Core query shape quan trọng hơn số dòng entity ban đầu

**Mẹo:**
Khi endpoint chậm, kiểm tra SQL thực tế và số rows được nhân lên bởi joins/includes thay vì chỉ nhìn số root entities trả về.

**Tại sao hữu ích:**
Một query trả 100 Orders nhưng include hai collection có thể tạo result set lớn do cartesian multiplication. Database, network và materializer phải xử lý nhiều rows hơn đáng kể so với số object cuối cùng.

**Ví dụ:**
Dùng logging/query inspection để so sánh row count và payload khi `Include` nhiều collections. Nếu semantics phù hợp, projection hoặc split query có thể giảm dữ liệu trung gian; quyết định dựa trên round trips và kích thước result thực tế.

**Lưu ý:**
`AsSplitQuery()` không phải fix mặc định: nó đổi một query lớn thành nhiều query và có consistency/round-trip trade-off. Đo workload trước khi chọn.

### Tip 3 — Redis TTL cần jitter khi nhiều keys hết hạn cùng thời điểm

**Mẹo:**
Với cache-aside có lượng lớn keys được populate theo batch hoặc cùng lúc, thêm một khoảng jitter nhỏ vào TTL thay vì để tất cả hết hạn đúng một mốc.

**Tại sao hữu ích:**
Nếu hàng nghìn hot keys cùng expire, request đồng thời sẽ dồn về database/downstream tạo expiration storm. Jitter phân tán thời điểm refresh và làm tải backend đều hơn.

**Ví dụ:**
Thay vì mọi product cache có TTL chính xác 10 phút, đặt TTL quanh 10 phút cộng/trừ một khoảng ngẫu nhiên nhỏ phù hợp freshness requirement. Theo dõi cache miss rate và backend latency để xác nhận hiệu quả.

**Lưu ý:**
Jitter không giải quyết stampede trên cùng một hot key; trường hợp đó có thể cần single-flight/locking hoặc stale-while-revalidate. Không làm jitter vượt quá business freshness window.

### Tip 4 — Git `reflog` là công cụ phục hồi local history trước khi hoảng

**Mẹo:**
Khi lỡ `reset --hard`, rebase hoặc chuyển branch làm “mất” commit local, kiểm tra `git reflog` trước khi viết lại code.

**Tại sao hữu ích:**
Git thường vẫn giữ object và ghi lại chuyển động của `HEAD` trong reflog một thời gian. Bạn có thể tìm commit trước thao tác phá history rồi tạo branch phục hồi từ SHA đó.

**Ví dụ:**
Sau một rebase sai, chạy `git reflog`, xác định `HEAD@{n}` trước rebase rồi tạo `git branch recovery <sha>` để kiểm tra code trước khi sửa history chính.

**Lưu ý:**
Reflog chủ yếu là local và không phải backup vĩnh viễn. Đừng dựa vào nó thay cho remote branch, review hoặc backup; đặc biệt cẩn thận trước force-push lên branch dùng chung.

### Tip 5 — AI-generated migration phải được kiểm tra bằng schema diff và dữ liệu thật

**Mẹo:**
Khi AI coding agent tạo EF Core/database migration, review generated SQL, lock impact, data transformation và rollback path thay vì chỉ thấy project compile rồi chấp nhận.

**Tại sao hữu ích:**
AI có thể tạo migration hợp cú pháp nhưng rename thành drop/add, thêm non-null column không có backfill, hoặc tạo index gây lock lâu trên bảng lớn. Những lỗi này thường chỉ lộ khi deploy với production-scale data.

**Ví dụ:**
Trước merge, generate SQL script, kiểm tra `ALTER TABLE`, index operations và default/backfill strategy; chạy migration trên bản sao dữ liệu có kích thước đại diện và đo thời gian/locking nếu thay đổi lớn.

**Lưu ý:**
Unit tests không chứng minh migration production-safe. Cần xem engine/version thực tế, deployment strategy và khả năng chạy expand-contract khi schema được nhiều application versions dùng đồng thời.

## 🧠 Software Design

### Design 1 — Timeout budget là quyết định end-to-end, không phải từng service độc lập

**Khái niệm:**
Timeout budget phân bổ tổng thời gian một user operation được phép tiêu tốn qua nhiều dependency. Mỗi hop không nên tự chọn timeout mà bỏ qua deadline của request cha.

**Vấn đề nó giải quyết:**
Một API có SLA 5 giây nhưng gọi tuần tự ba services, mỗi service timeout 5 giây, có thể khiến request giữ resource lâu hơn SLA nhiều lần và tạo cascading saturation khi dependency chậm.

**Ví dụ thực tế:**
Checkout dành một phần budget cho inventory, pricing và payment. Nếu budget còn lại quá nhỏ trước payment, hệ thống có thể fail sớm theo contract thay vì bắt đầu một call chắc chắn vượt deadline.

**Trade-off:**
Budget rõ giúp latency predictable và recovery nhanh hơn, nhưng timeout quá chặt làm tăng false failures khi dependency có tail latency tạm thời. Cần telemetry p95/p99 và business SLA để tuning.

**Middle → Senior insight:**
Middle developer cần propagate cancellation/deadline và phân loại timeout đúng. Senior / Technical developer phải thiết kế latency budget giữa services, retry allowance và degradation path dựa trên criticality thay vì cấu hình từng client riêng lẻ.

### Design 2 — Data ownership trước physical database separation

**Khái niệm:**
Một module có thể sở hữu dữ liệu và cấm module khác truy cập trực tiếp tables của nó ngay cả khi tất cả vẫn dùng chung SQL Server. Ownership logic có thể được thiết lập trước khi tách database vật lý.

**Vấn đề nó giải quyết:**
Nếu mọi module query/update tables của nhau, schema trở thành shared internal API và việc tách service sau này rất khó. Nhưng tách database ngay từ đầu lại thêm operational/distributed complexity khi chưa có nhu cầu.

**Ví dụ thực tế:**
Trong Modular Monolith, Ordering sở hữu order tables; Reporting lấy dữ liệu qua contract/projection được xác định thay vì join tùy ý vào internals. Khi Ordering cần deploy độc lập, boundary đã rõ hơn để migrate datastore.

**Trade-off:**
Logical ownership giữ deployment đơn giản nhưng cần discipline vì database vẫn cho phép truy cập chéo. Physical separation enforce boundary mạnh hơn nhưng thêm synchronization, eventual consistency và operations.

**Middle → Senior insight:**
Middle developer cần tôn trọng module API và ownership. Senior / Technical developer phải quyết định lúc nào organizational/scaling/release pressure đủ lớn để chuyển logical boundary thành physical separation.

### Design 3 — Consumer-driven contract testing cho integration do nhiều team sở hữu

**Khái niệm:**
Consumer-driven contract test mô tả những interaction mà consumer thực sự phụ thuộc và kiểm tra provider còn đáp ứng chúng, nhằm phát hiện breaking integration trước khi deploy.

**Vấn đề nó giải quyết:**
Provider có thể thay response mà unit/integration tests nội bộ vẫn xanh vì chúng không biết consumer khác đang dựa vào field, status code hoặc semantics nào.

**Ví dụ thực tế:**
Mobile backend phụ thuộc Pricing API trả `200` với `amount` và `currency` cho product hợp lệ. Contract được publish/verify trong CI để provider change gây incompatibility bị phát hiện trước release.

**Trade-off:**
Contract tests giảm integration regression nhưng tạo contract lifecycle, versioning và CI coordination. Nếu consumer tests encode toàn bộ implementation detail, chúng làm provider khó tiến hóa hơn thay vì bảo vệ behavior cần thiết.

**Middle → Senior insight:**
Middle developer cần viết contract quanh observable behavior tối thiểu. Senior / Technical developer phải xác định ownership, compatibility policy, provider verification và khi nào contract testing đáng giá hơn một integration test đơn giản trong cùng team.
