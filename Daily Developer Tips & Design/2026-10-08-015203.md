# Daily Developer Tips & Design — 2026-10-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure

**Mẹo:**
Khi producer có thể tạo work nhanh hơn consumer xử lý, dùng bounded `Channel<T>` thay vì một queue tăng vô hạn trong memory.

**Tại sao hữu ích:**
Bounded channel biến giới hạn capacity thành một phần của flow-control. Khi đầy, producer có thể chờ thay vì tiếp tục allocate work, giúp hệ thống giữ memory ổn định và thể hiện overload sớm hơn.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(
    new BoundedChannelOptions(500)
    {
        FullMode = BoundedChannelFullMode.Wait
    });

await channel.Writer.WriteAsync(job, cancellationToken);
```
Một import API có thể đưa jobs vào channel trong một process, còn `BackgroundService` đọc với concurrency có kiểm soát.

**Lưu ý:**
In-memory `Channel<T>` không phải durable queue: process restart sẽ mất work chưa xử lý. Nếu job cần durability, multi-instance coordination hoặc retry bền vững, dùng broker như Azure Service Bus phù hợp hơn.

### Tip 2 — Keyset pagination cho bảng lớn thay vì OFFSET sâu

**Mẹo:**
Với danh sách lớn được duyệt tuần tự, cân nhắc keyset pagination dựa trên cột sort ổn định thay vì `OFFSET ... FETCH` ở page sâu.

**Tại sao hữu ích:**
OFFSET buộc database bỏ qua ngày càng nhiều rows trước khi trả page cần thiết. Keyset dùng giá trị cuối của page trước làm boundary nên thường tận dụng index hiệu quả hơn và ít bị dịch page khi dữ liệu mới được insert.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp cần bắt đầu theo ordering/query pattern, ví dụ `(CreatedAt DESC, Id DESC)`.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 937. Sort key phải deterministic; chỉ dùng `CreatedAt` khi có duplicates mà không thêm tie-breaker có thể bỏ hoặc lặp rows.

### Tip 3 — Đặt sampling observability theo loại telemetry, không cắt đồng đều

**Mẹo:**
Khi telemetry volume lớn, ưu tiên giữ errors, traces quan trọng và requests bất thường; sample traffic thành công có kiểm soát thay vì giảm mọi loại telemetry cùng tỷ lệ.

**Tại sao hữu ích:**
Sampling giảm ingestion cost và noise, nhưng sampling sai có thể xóa chính evidence cần cho incident. Một request lỗi cần correlation giữa request, dependency và trace; giữ riêng một log lỗi mà mất context thường không đủ để RCA.

**Ví dụ:**
API có hàng triệu health-check requests thành công mỗi ngày nhưng rất ít checkout failures. Giảm telemetry của health checks mạnh hơn, trong khi giữ failure traces và dependency spans của checkout, giúp giảm cost mà vẫn bảo toàn diagnostic value.

**Lưu ý:**
Nếu sampling diễn ra độc lập ở nhiều tầng, một distributed trace có thể bị đứt. Kiểm tra cách Application Insights/OpenTelemetry propagation và sampling hoạt động trước khi dựa vào số đếm sampled để tính business totals.

### Tip 4 — File upload phải xác thực nội dung, không tin extension hay `Content-Type`

**Mẹo:**
Với upload endpoint, coi filename, extension và client-supplied `Content-Type` là untrusted metadata; áp dụng size limit, allowlist, kiểm tra nội dung phù hợp và lưu file ngoài executable web root.

**Tại sao hữu ích:**
Client có thể đổi tên payload nguy hiểm thành `.jpg` hoặc gửi MIME type giả. Upload pipeline là security boundary, đặc biệt với CMS nơi file sau đó có thể được public hoặc xử lý bởi thư viện khác.

**Ví dụ:**
Một CMS nhận avatar: giới hạn kích thước request, generate storage name phía server, kiểm tra định dạng ảnh thực, scan theo policy nếu cần, rồi lưu Blob bằng identity có quyền tối thiểu thay vì dùng filename từ request làm path trực tiếp.

**Lưu ý:**
“Magic bytes” cũng không chứng minh file hoàn toàn an toàn. Nếu hệ thống parse/transcode tài liệu, phải xét vulnerability của parser, decompression bombs và quyền truy cập storage; đừng log nội dung hoặc token/SAS nhạy cảm.

### Tip 5 — Phân biệt content cache với output cache trong CMS

**Mẹo:**
Khi CMS page trả nội dung cũ, xác định stale data nằm ở content/object cache, application output cache, CDN hay browser cache trước khi “clear all caches”.

**Tại sao hữu ích:**
Mỗi cache có key, TTL và invalidation boundary khác nhau. Clear toàn bộ có thể tạm che lỗi invalidation, tạo cache stampede và không cho biết tầng nào thực sự sai.

**Ví dụ:**
Editor publish một Optimizely CMS page nhưng user vẫn thấy bản cũ. So sánh content version ở origin, response headers và CDN status: nếu origin đã mới nhưng edge vẫn cũ, sửa purge/cache-control ở delivery layer thay vì đụng content repository.

**Lưu ý:**
Đừng cache personalized response bằng shared key nếu output phụ thuộc user, role, locale hoặc experiment. Cache key phải phản ánh đúng các dimensions ảnh hưởng response.

## 🧠 Software Design

### Design 1 — Dùng trực tiếp DbContext hay thêm Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và `DbSet<T>` mang nhiều đặc tính repository. Thêm custom Repository chỉ có giá trị khi abstraction biểu diễn boundary/use case có ý nghĩa, không phải vì mọi data access đều bắt buộc có một wrapper.

**Vấn đề nó giải quyết:**
Team muốn tách application logic khỏi persistence, tái sử dụng query hoặc kiểm soát aggregate access. Nhưng generic repository kiểu `GetAll/Add/Update` thường chỉ mirror EF Core, che mất khả năng projection/query và tạo thêm layer phải bảo trì.

**Ví dụ thực tế:**
Một application service có thể inject `AppDbContext` và project query trực tiếp cho read model. Với domain phức tạp, `IOrderRepository.LoadForCheckout(id)` có thể hợp lý nếu nó bảo vệ cách aggregate Order được load và persistence detail cần được cô lập.

**Trade-off:**
Direct `DbContext` giảm ceremony và giữ đầy đủ EF Core capability, nhưng application coupling với persistence technology rõ hơn. Repository có thể tạo boundary/test seam tốt, nhưng abstraction kém thiết kế dẫn đến leaky methods, duplicate LINQ và khó tối ưu SQL.

**Middle → Senior insight:**
Middle cần hiểu tracking, query translation và transaction của `DbContext` dù có Repository hay không. Senior / Technical phải chọn abstraction dựa trên domain boundary, testing strategy, query complexity và khả năng thay đổi thực tế; không thêm layer chỉ để đạt “Clean Architecture”.

### Design 2 — Service Bus Queue vs Topic theo semantics phân phối

**Khái niệm:**
Queue thường biểu diễn một stream công việc mà một message được một competing consumer xử lý; Topic + Subscription biểu diễn publish/subscribe, nơi nhiều subscriber độc lập có thể nhận cùng một event theo filter riêng.

**Vấn đề nó giải quyết:**
Nếu một business event cần kích hoạt Billing, Analytics và Notification, nhét cả ba trách nhiệm vào một queue consumer làm coupling tăng. Ngược lại, dùng Topic cho một job chỉ cần một worker pool có thể tạo topology phức tạp không cần thiết.

**Ví dụ thực tế:**
`GenerateMonthlyInvoice` là command/work item phù hợp queue với nhiều workers cạnh tranh. `OrderPlaced` có thể publish lên topic để Inventory, Loyalty và Analytics sở hữu subscription riêng và retry/DLQ độc lập.

**Trade-off:**
Queue đơn giản hơn và phù hợp load balancing một responsibility. Topic tăng extensibility và consumer autonomy nhưng tăng số subscription, duplicate delivery paths, monitoring, schema evolution và operational cost.

**Middle → Senior insight:**
Middle cần cấu hình handler, retry, DLQ và idempotency đúng. Senior / Technical phải phân biệt command với event, xác định ownership/fan-out, failure isolation và lifecycle của subscribers; topology phải phản ánh business semantics chứ không chỉ khả năng của broker.

### Design 3 — Feature Flag tách deployment khỏi release

**Khái niệm:**
Feature Flag cho phép code được deploy nhưng capability chưa nhất thiết được bật cho toàn bộ user. Điều này tách việc đưa binary vào production khỏi quyết định expose behavior mới.

**Vấn đề nó giải quyết:**
Một thay đổi lớn có thể cần rollout theo tenant, internal users hoặc phần trăm traffic. Nếu deployment và release luôn là một bước, rollback binary trở thành công cụ duy nhất khi business behavior có vấn đề.

**Ví dụ thực tế:**
Checkout engine mới được deploy cùng phiên bản cũ. Flag bật trước cho internal tenant, sau đó 5%, 25% rồi 100% traffic trong khi theo dõi error rate và latency. Khi metric xấu, disable flag nhanh hơn rollback toàn bộ deployment.

**Trade-off:**
Flags giảm release risk và hỗ trợ progressive delivery, nhưng tạo nhiều code paths, test combinations và “temporary” branches dễ trở thành technical debt. Flag system cũng trở thành operational dependency cần audit và quyền thay đổi phù hợp.

**Middle → Senior insight:**
Middle cần implement flag mà không rải conditional khó kiểm soát và test cả hai behavior trong migration window. Senior / Technical phải thiết kế rollout/rollback criteria, ownership, expiration cleanup và quyết định khi nào blue/green hoặc canary deployment phù hợp hơn feature-level switching.
