# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup read-only có tần suất cao

**Mẹo:**
Nếu một dictionary được xây dựng một lần rồi đọc rất nhiều lần trong suốt vòng đời application, cân nhắc `FrozenDictionary<TKey, TValue>` từ `System.Collections.Frozen`.

**Tại sao hữu ích:**
Nó tối ưu cấu trúc dữ liệu cho lookup read-only, phù hợp với các bảng mapping, metadata hoặc configuration ít thay đổi nhưng được truy cập thường xuyên.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

var handlers = new Dictionary<string, Func<string>>
{
    ["email"] = () => "Email handler",
    ["sms"] = () => "SMS handler"
}.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);

var handler = handlers["EMAIL"];
```

**Lưu ý:**
Chi phí tạo frozen collection cao hơn collection thông thường. Không nên dùng nếu collection thay đổi liên tục hoặc chỉ được đọc vài lần.

### Tip 2 — Dùng built-in Rate Limiting của ASP.NET Core trước khi tự viết middleware

**Mẹo:**
Với các API cần giới hạn request theo IP, user hoặc endpoint, ưu tiên `Microsoft.AspNetCore.RateLimiting` thay vì tự quản lý counter bằng middleware thủ công.

**Tại sao hữu ích:**
Framework đã hỗ trợ các thuật toán như Fixed Window, Sliding Window, Token Bucket và Concurrency Limiter, giúp giảm bug concurrency và dễ cấu hình hơn.

**Ví dụ:**
```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("api", limiter =>
    {
        limiter.PermitLimit = 100;
        limiter.Window = TimeSpan.FromMinutes(1);
        limiter.QueueLimit = 0;
    });
});

app.UseRateLimiter();

app.MapGet("/reports", GetReports)
   .RequireRateLimiting("api");
```

**Lưu ý:**
In-memory limiter chỉ bảo vệ từng instance riêng lẻ. Với nhiều replicas, cần cân nhắc gateway-level rate limiting hoặc cơ chế distributed phù hợp.

### Tip 3 — Dùng filtered/partial index khi chỉ một tập nhỏ dữ liệu được query thường xuyên

**Mẹo:**
Nếu query production chủ yếu truy cập một subset ổn định như `IsDeleted = 0`, `Status = 'Pending'`, hãy xem xét filtered index trong SQL Server hoặc partial index trong PostgreSQL.

**Tại sao hữu ích:**
Index nhỏ hơn thường giảm storage, write amplification và số page phải đọc so với index toàn bộ bảng.

**Ví dụ:**
SQL Server:

```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON Orders (CreatedAt)
INCLUDE (CustomerId, TotalAmount)
WHERE Status = 'Pending';
```

PostgreSQL:

```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at)
WHERE status = 'Pending';
```

**Lưu ý:**
Predicate của query phải tương thích với điều kiện index. Nếu trạng thái phân bố thay đổi mạnh theo thời gian, lợi ích của index cũng có thể thay đổi.

### Tip 4 — Dùng multi-stage Docker build để giảm image runtime

**Mẹo:**
Tách build environment và runtime environment thành nhiều stage, chỉ copy artifact publish cuối cùng sang image chạy production.

**Tại sao hữu ích:**
Image nhỏ hơn giúp pull/deploy nhanh hơn, giảm attack surface và tránh mang theo SDK, source code hoặc build tools không cần thiết.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish MyApi.csproj -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

**Lưu ý:**
Image nhỏ không đồng nghĩa container an toàn tuyệt đối. Vẫn cần non-root user, dependency scanning, secret management và patching base image.

### Tip 5 — Capture dump khi process .NET bị treo thay vì chỉ đọc log

**Mẹo:**
Khi service vẫn sống nhưng request treo, CPU cao hoặc thread pool có dấu hiệu bất thường, capture process dump bằng `dotnet-dump` để kiểm tra thread stacks và managed heap.

**Tại sao hữu ích:**
Log thường không cho thấy deadlock, lock contention, thread starvation hoặc object retention. Dump cho phép xem trạng thái process tại thời điểm sự cố.

**Ví dụ:**
```bash
dotnet-dump collect -p <PID>
dotnet-dump analyze core_*.dmp
```

Trong analyzer:

```text
clrthreads
clrstack
syncblk
dumpheap -stat
```

**Lưu ý:**
Dump có thể chứa dữ liệu nhạy cảm như tokens, request payload hoặc user data. Phải bảo vệ file dump như production data và xóa khi không còn cần.

## 🧠 Software Design

### Design 1 — Bulkhead Pattern để cô lập failure

**Khái niệm:**
Bulkhead Pattern chia tài nguyên như connection, thread hoặc concurrency slot thành các vùng độc lập để một dependency lỗi không chiếm toàn bộ capacity của hệ thống.

**Vấn đề nó giải quyết:**
Nếu một downstream service trở nên chậm, request chờ service đó có thể dùng hết connection pool hoặc worker capacity, khiến các chức năng không liên quan cũng ngừng hoạt động.

**Ví dụ thực tế:**
Một API gọi cả Payment Service và Recommendation Service. Recommendation chỉ là tính năng phụ nhưng đôi lúc phản hồi rất chậm. Hệ thống giới hạn tối đa 20 concurrent calls cho Recommendation, trong khi Payment dùng capacity riêng. Khi Recommendation đầy, request có thể bỏ qua recommendation thay vì kéo toàn bộ API xuống.

**Trade-off:**
Lợi ích là failure được cô lập và hệ thống graceful degradation tốt hơn. Chi phí là phải chọn capacity hợp lý; giới hạn quá thấp gây reject không cần thiết, quá cao lại không còn tác dụng bảo vệ.

**Middle → Senior insight:**
Middle developer nên hiểu timeout và retry không đủ để chống resource exhaustion. Senior developer cần thiết kế isolation boundary dựa trên criticality, dependency behavior, throughput và degradation strategy thực tế.

### Design 2 — Data ownership quan trọng hơn việc chia database vật lý

**Khái niệm:**
Data ownership nghĩa là một module hoặc service chịu trách nhiệm duy nhất cho việc thay đổi một loại dữ liệu. Các thành phần khác truy cập thông qua contract thay vì sửa trực tiếp bảng thuộc ownership của nhau.

**Vấn đề nó giải quyết:**
Nếu nhiều module cùng đọc/ghi trực tiếp cùng schema, coupling rất nhanh lan sang database level. Sau đó việc refactor, tách service hoặc thay đổi invariant trở nên khó vì không biết ai đang phụ thuộc dữ liệu nào.

**Ví dụ thực tế:**
Module `Billing` sở hữu invoice và payment status. Module `Orders` cần biết một invoice đã được thanh toán nhưng không được chạy trực tiếp:

```sql
UPDATE BillingInvoices
SET Status = 'Paid'
WHERE Id = @Id;
```

Thay vào đó, `Orders` gọi contract của `Billing` hoặc phản ứng với event do `Billing` publish.

**Trade-off:**
Ownership rõ ràng tăng maintainability và khả năng tách hệ thống sau này. Đổi lại, query xuyên module khó hơn và có thể cần API composition, read model hoặc duplicated data.

**Middle → Senior insight:**
Middle developer cần tránh truy cập chéo repository/table tùy tiện. Senior developer phải xác định ownership dựa trên business invariant, không chỉ theo tên bảng hoặc cấu trúc team hiện tại.

### Design 3 — Optimistic Concurrency thay vì khóa dữ liệu quá sớm

**Khái niệm:**
Optimistic Concurrency giả định conflict xảy ra tương đối hiếm. Thay vì khóa record từ lúc đọc, hệ thống kiểm tra version khi update và reject nếu dữ liệu đã bị thay đổi bởi transaction khác.

**Vấn đề nó giải quyết:**
Trong hệ thống nhiều user hoặc nhiều worker cùng cập nhật một entity, thao tác "read → modify → save" có thể làm mất thay đổi của người khác nếu không kiểm tra concurrency.

**Ví dụ thực tế:**
Trong EF Core, entity có `rowversion`:

```csharp
public class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = default!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
```

Nếu hai request cùng sửa order, request save sau có thể nhận `DbUpdateConcurrencyException` thay vì silently overwrite dữ liệu mới hơn.

**Trade-off:**
Optimistic locking giữ throughput tốt và tránh lock dài, nhưng application phải định nghĩa cách resolve conflict: retry, merge hoặc yêu cầu user reload. Với conflict xảy ra liên tục, pessimistic locking hoặc serialization strategy khác có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần biết cách phát hiện lost update và xử lý `DbUpdateConcurrencyException`. Senior developer phải chọn concurrency model theo contention thực tế, business invariant và trải nghiệm người dùng thay vì mặc định một cơ chế cho mọi entity.
