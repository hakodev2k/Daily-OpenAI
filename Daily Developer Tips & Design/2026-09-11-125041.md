# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Không inject scoped service trực tiếp vào `BackgroundService`

**Mẹo:**
Trong .NET Worker hoặc `BackgroundService`, nếu cần dùng `DbContext`, repository hoặc service có scoped lifetime, tạo scope bên trong mỗi vòng xử lý bằng `IServiceScopeFactory` thay vì inject scoped dependency thẳng vào singleton worker.

**Tại sao hữu ích:**
`BackgroundService` được đăng ký như singleton. Scoped service thường được thiết kế theo một đơn vị công việc ngắn như HTTP request hoặc message handling. Giữ scoped dependency trong singleton có thể kéo dài lifetime ngoài ý muốn, làm `DbContext` giữ change tracker quá lâu hoặc dùng cùng instance cho nhiều operation.

**Ví dụ:**
```csharp
public sealed class CleanupWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var service = scope.ServiceProvider.GetRequiredService<CleanupService>();

            await service.RunAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

Mỗi iteration có scope riêng, nên transaction/lifetime của dependency được giới hạn rõ ràng.

**Lưu ý:**
Đừng tạo một scope duy nhất rồi giữ suốt lifetime của worker. Với batch rất dài, scope quá lớn vẫn có thể tích tụ tracked entity, connection hoặc state. Hãy chọn scope theo đơn vị công việc thực tế.

### Tip 2 — Khi SQL Server query lúc nhanh lúc chậm, kiểm tra parameter-sensitive plan trước khi thêm index

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có lúc chạy vài ms, lúc lại vài giây, kiểm tra execution plan và distribution của parameter thay vì mặc định thiếu index.

**Tại sao hữu ích:**
SQL Server có thể cache một execution plan phù hợp với parameter đầu tiên nhưng không phù hợp với parameter có selectivity rất khác. Ví dụ một tenant có 10 row còn tenant khác có vài triệu row; cùng một plan có thể hoạt động tốt cho nhóm này nhưng tệ cho nhóm kia.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @TenantId
  AND CreatedAt >= @FromDate;
```

Khi điều tra, so sánh estimated vs actual rows, cached plan và parameter distribution. Với SQL Server version phù hợp, Parameter Sensitive Plan optimization có thể giúp; trong trường hợp khác có thể cần rewrite query, `OPTION (RECOMPILE)` có chọn lọc hoặc thiết kế index theo workload thực tế.

**Lưu ý:**
Không thêm `OPTION (RECOMPILE)` cho mọi query vì nó tăng compilation CPU và mất lợi ích plan cache. Cũng không nên gọi mọi biến động plan là parameter sniffing nếu chưa có evidence từ execution plan/runtime stats.

### Tip 3 — Với JWT, validate cả `issuer` và `audience`, không chỉ signature

**Mẹo:**
Khi cấu hình authentication cho ASP.NET Core API, đảm bảo token được kiểm tra `issuer`, `audience`, lifetime và signing key theo đúng identity provider của hệ thống.

**Tại sao hữu ích:**
Một token có chữ ký hợp lệ chưa chắc được phát hành cho API của bạn. Nếu bỏ `audience` hoặc `issuer` validation, backend có thể chấp nhận token hợp lệ nhưng dành cho application/resource khác trong cùng identity ecosystem.

**Ví dụ:**
```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = config["Auth:Authority"];
        options.Audience = config["Auth:Audience"];
    });
```

Trong production, nên kiểm tra claim thực tế và metadata của Microsoft Entra ID / identity provider thay vì copy cấu hình từ môi trường khác.

**Lưu ý:**
Đừng tự parse JWT rồi tin claim mà bỏ qua middleware validation. Authentication cũng không thay thế authorization; token hợp lệ vẫn phải được kiểm tra role, scope, tenant hoặc policy theo use case.

### Tip 4 — Dùng OpenTelemetry baggage/tag có kiểm soát, tránh biến telemetry thành nguồn cardinality explosion

**Mẹo:**
Khi thêm tag cho trace/metric, ưu tiên dimension có tập giá trị hữu hạn như endpoint, dependency type, outcome hoặc region thay vì user ID, order ID hoặc URL động nguyên bản.

**Tại sao hữu ích:**
Metric backend thường tạo time series theo tổ hợp label. Nếu một label có hàng triệu giá trị khác nhau, số series tăng rất nhanh, làm chi phí observability tăng và query/dashboard chậm hơn.

**Ví dụ:**
```text
Tốt cho metric:
http.route = /orders/{id}
result = success|failure
region = southeastasia

Không tốt cho metric:
order.id = 9f3d...
user.email = ...
raw.url = /orders/938271?...
```

High-cardinality data có thể phù hợp hơn trong trace/log khi cần drill-down, miễn là sampling và privacy policy được kiểm soát.

**Lưu ý:**
Không loại bỏ toàn bộ context chỉ để giảm chi phí. Mục tiêu là chọn dimension có giá trị chẩn đoán cao và cardinality hữu hạn; trace ID vẫn cần thiết để correlation nhưng không nên trở thành metric label.

### Tip 5 — Trong Optimizely/CMS, model content theo editorial intent thay vì mirror layout pixel-by-pixel

**Mẹo:**
Khi tạo content type/block cho CMS, mô hình hóa theo ý nghĩa nội dung như Hero, Promo, Article Teaser hoặc Product Reference thay vì tạo field tương ứng từng khoảng cách, màu sắc hoặc cấu trúc DOM cụ thể.

**Tại sao hữu ích:**
Content model gắn chặt với layout làm editor khó tái sử dụng nội dung và khiến redesign frontend kéo theo migration CMS lớn. Model theo editorial semantics giúp Vue/React/SSR layer thay đổi presentation mà content vẫn giữ giá trị.

**Ví dụ:**
```text
Nên:
HeroBlock
- Heading
- Body
- Image
- CTA

Hạn chế:
HeroBlock
- LeftPaddingDesktop
- HeadingTopMargin
- RedButtonEnabled
- ColumnWidthPx
```

Presentation-specific option chỉ nên xuất hiện khi editor thật sự cần kiểm soát nó như một business/editorial choice.

**Lưu ý:**
Không cực đoan loại bỏ mọi presentation field. Một số variant như `Theme`, `Alignment` hoặc `LayoutStyle` có thể hợp lý nếu chúng là lựa chọn ổn định mà editor cần dùng, không phải chi tiết CSS ngẫu nhiên.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service theo execution model và operational ownership

**Khái niệm:**
Azure Functions phù hợp với workload event-driven, trigger-based và có khả năng scale theo event source; Worker Service phù hợp khi bạn cần process sống lâu, control lifecycle rõ hoặc workload chạy liên tục với dependency/resource state ổn định.

**Vấn đề nó giải quyết:**
Team thường chọn Functions chỉ vì “serverless” hoặc Worker chỉ vì quen .NET, nhưng hai mô hình có behavior khác nhau về cold start, retry, concurrency, hosting cost, deployment và giới hạn execution.

**Ví dụ thực tế:**
```text
Azure Function:
- xử lý BlobCreated event
- nhận Service Bus message bursty
- timer nhỏ, độc lập

Worker Service:
- process luôn mở connection tới hệ thống legacy
- xử lý stream liên tục
- cần in-memory state hoặc custom scheduling phức tạp
```

Nếu một workload Function phải giữ execution hàng chục phút, quản lý state phức tạp và cần nhiều control custom, Worker có thể đơn giản hơn về vận hành.

**Trade-off:**
Functions giảm infrastructure management và tích hợp trigger tốt, nhưng behavior scale/retry/cold start phụ thuộc hosting model. Worker cho lifecycle/control dễ dự đoán hơn nhưng bạn tự chịu nhiều hơn về hosting, scaling và capacity planning.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và idempotency của từng model. Senior / Technical developer phải chọn dựa trên traffic shape, execution duration, statefulness, cost model, observability, failure recovery và mức operational control cần thiết — không theo nhãn “serverless” hay “microservice”.

### Design 2 — Shared database giữa module có thể chấp nhận được, nhưng shared ownership thì nguy hiểm

**Khái niệm:**
Nhiều module trong Modular Monolith có thể dùng cùng một physical database, nhưng mỗi module vẫn nên sở hữu schema/table và không cho module khác sửa trực tiếp dữ liệu nội bộ nếu muốn giữ boundary có ý nghĩa.

**Vấn đề nó giải quyết:**
Nếu mọi module đọc/ghi tùy ý mọi table, coupling ở database sẽ phá vỡ boundary dù code được chia folder rất đẹp. Thay đổi schema ở một module có thể làm hỏng nhiều capability mà owner không biết.

**Ví dụ thực tế:**
```text
Projects module sở hữu:
projects.*

Documents module sở hữu:
documents.*

Projects cần document count:
- gọi contract/read model của Documents
- hoặc dùng projection được công bố
- không UPDATE documents.Document trực tiếp
```

Physical database vẫn có thể dùng chung transaction khi thật sự cần, nhưng access rule phải rõ và hiếm khi bypass boundary.

**Trade-off:**
Shared database giữ deployment và transaction đơn giản, nhưng yêu cầu discipline mạnh để ownership không bị xói mòn. Database tách riêng tăng isolation nhưng kéo theo distributed transaction, latency và operational complexity.

**Middle → Senior insight:**
Middle developer cần tránh cross-module query/write tùy tiện vì “nhanh hơn”. Senior / Technical developer phải xác định data ownership, public read model, transaction boundary và tiêu chí khi nào physical separation mang lại giá trị đủ lớn để trả distributed-systems cost.

### Design 3 — Consistency level của cache phải xuất phát từ business tolerance, không từ công nghệ Redis

**Khái niệm:**
Cache architecture nên bắt đầu bằng câu hỏi dữ liệu được phép stale bao lâu và hậu quả của stale data là gì, rồi mới quyết định TTL, invalidation, cache-aside, write-through hoặc bypass cache.

**Vấn đề nó giải quyết:**
Team thường áp dụng cùng một Redis pattern cho mọi dữ liệu. Nhưng product description stale 2 phút và account permission stale 2 phút có mức rủi ro hoàn toàn khác nhau.

**Ví dụ thực tế:**
```text
Product catalog:
- chấp nhận stale 5 phút
- cache-aside + TTL + async invalidation

Authorization permission:
- cần freshness cao
- TTL rất ngắn hoặc không cache decision nhạy cảm

Dashboard analytics:
- chấp nhận stale 15 phút
- precomputed/cache-heavy
```

SLA về freshness nên là một phần của contract giữa business và engineering.

**Trade-off:**
Cache tăng throughput và giảm dependency load nhưng luôn tạo thêm state cần đồng bộ. Freshness cao đòi invalidation chặt hơn, tăng complexity và dependency coupling; stale tolerance lớn cho phép hệ thống đơn giản và resilient hơn.

**Middle → Senior insight:**
Middle developer cần hiểu TTL không phải giải pháp consistency đầy đủ và biết cache invalidation failure có thể xảy ra. Senior / Technical developer phải xác định stale-data budget theo business impact, chọn invalidation strategy, fallback behavior và quyết định khi nào không cache là lựa chọn đúng hơn.
