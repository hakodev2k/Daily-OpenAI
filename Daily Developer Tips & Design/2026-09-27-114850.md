# Daily Developer Tips & Design — 2026-09-27

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure cho background pipeline

**Mẹo:**
Khi request hoặc message producer có thể tạo work nhanh hơn `BackgroundService` xử lý, ưu tiên `Channel.CreateBounded<T>` với capacity có chủ đích thay vì một queue tăng vô hạn trong memory.

**Tại sao hữu ích:**
Bounded channel biến overload thành tín hiệu có thể kiểm soát. Khi buffer đầy, `WriteAsync` có thể chờ, từ chối hoặc áp dụng policy phù hợp; nhờ đó tốc độ producer bị ràng buộc bởi khả năng xử lý thực tế thay vì để memory tăng cho tới khi GC pressure hoặc OOM xuất hiện.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, cancellationToken);
```
Một API import có thể giới hạn queue nội bộ ở 500 jobs và trả overload signal ở boundary phù hợp thay vì nhận vô hạn work rồi crash vài phút sau.

**Lưu ý:**
In-memory `Channel<T>` không phải durable queue: process restart sẽ mất work chưa xử lý. Nếu yêu cầu durability, retry xuyên restart hoặc multi-instance coordination, dùng broker như Azure Service Bus thay vì biến Channel thành message broker tự chế.

### Tip 2 — Chuẩn hóa API error bằng `ProblemDetails`, nhưng giữ error code ổn định cho client

**Mẹo:**
Trong ASP.NET Core, dùng `ProblemDetails` cho error contract nhất quán và thêm một machine-readable application error code thay vì để frontend parse `detail` hoặc exception message.

**Tại sao hữu ích:**
HTTP status mô tả lớp lỗi giao thức, còn application code mô tả nguyên nhân nghiệp vụ mà client cần xử lý. Tách hai lớp giúp message có thể đổi/ngôn ngữ hóa mà không phá logic frontend và tránh lộ stack trace ra API.

**Ví dụ:**
```json
{
  "type": "https://example/errors/order-conflict",
  "title": "Order cannot be updated",
  "status": 409,
  "code": "ORDER_VERSION_CONFLICT",
  "traceId": "00-..."
}
```
Frontend xử lý `ORDER_VERSION_CONFLICT`; support dùng `traceId` để nối request với telemetry.

**Lưu ý:**
Đừng tạo hàng trăm error code phản ánh từng exception implementation. Contract phải ổn định, không chứa secret/PII, và mapping status code phải giữ đúng HTTP semantics.

### Tip 3 — Tách Elasticsearch `filter` khỏi `must` khi điều kiện không cần relevance score

**Mẹo:**
Trong Elasticsearch, đặt các điều kiện exact như tenant, status, category hoặc range không tham gia relevance vào `bool.filter`; chỉ dùng query clauses có scoring cho phần full-text thực sự cần xếp hạng.

**Tại sao hữu ích:**
Filter context không tính `_score`, thể hiện đúng intent và có thể tận dụng caching/optimization của Elasticsearch tốt hơn. Quan trọng hơn, nó ngăn business constraints vô tình ảnh hưởng relevance của kết quả search.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "name": "wireless keyboard" } }],
      "filter": [
        { "term": { "tenantId": 42 } },
        { "term": { "isActive": true } }
      ]
    }
  }
}
```

**Lưu ý:**
Không phải chuyển mọi clause sang `filter` sẽ làm query nhanh đáng kể. Mapping, analyzer, cardinality, shard layout và query profile vẫn phải được đo; filter sai field kiểu `text` cũng có thể cho kết quả không như mong đợi.

### Tip 4 — Dùng Playwright để chặn regression ở contract UI/API, không chỉ click happy path

**Mẹo:**
Với flow frontend quan trọng, ngoài việc assert DOM cuối cùng, hãy kiểm tra request/response quan trọng và trạng thái loading/error để bắt lỗi integration mà unit test component không nhìn thấy.

**Tại sao hữu ích:**
Một UI có thể render đúng với mock nhưng production hỏng vì route API đổi, authorization trả 401 hoặc payload thiếu field. E2E ở boundary thật giúp phát hiện wiring regression, trong khi assertion vào trạng thái người dùng vẫn giữ test gần behavior.

**Ví dụ:**
```ts
const response = page.waitForResponse(r =>
  r.url().includes("/api/orders") && r.request().method() === "POST");

await page.getByRole("button", { name: "Place order" }).click();

const result = await response;
expect(result.status()).toBe(201);
await expect(page.getByText("Order confirmed")).toBeVisible();
```

**Lưu ý:**
Đừng biến Playwright thành bản sao của toàn bộ unit/integration suite. Quá nhiều E2E làm pipeline chậm và flaky; giữ chúng cho critical journeys và failure boundaries có giá trị cao.

### Tip 5 — Upload file lớn trực tiếp lên Blob Storage bằng SAS có scope hẹp

**Mẹo:**
Nếu browser/mobile client upload file lớn, cân nhắc để backend cấp SAS ngắn hạn cho đúng container/blob rồi client upload trực tiếp lên Azure Blob Storage thay vì proxy toàn bộ bytes qua ASP.NET Core.

**Tại sao hữu ích:**
Direct upload loại backend khỏi data path lớn, giảm bandwidth, memory pressure, request duration và nhu cầu scale web instances chỉ để chuyển tiếp bytes. Backend vẫn giữ quyền quyết định blob name, permission và thời hạn truy cập.

**Ví dụ:**
Backend xác thực user, tạo blob path `uploads/{tenant}/{id}`, cấp SAS chỉ có quyền create/write trong vài phút; client upload trực tiếp, sau đó backend nhận completion command và xác minh blob metadata trước khi đưa file vào workflow xử lý.

**Lưu ý:**
SAS là credential. Giới hạn permission, resource, expiry và HTTPS; không tin filename/content-type do client gửi. Với file không tin cậy, vẫn cần size limit, malware/content validation và trạng thái quarantine trước khi publish.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service: chọn theo execution model

**Khái niệm:**
Azure Functions tối ưu cho event-driven execution với platform-managed scaling và trigger/binding; Worker Service phù hợp hơn khi process cần lifecycle dài, polling/control loop riêng hoặc kiểm soát runtime/resource ổn định. Hai lựa chọn giải quyết execution model khác nhau, không phải “serverless mới hơn nên tốt hơn”.

**Vấn đề nó giải quyết:**
Background workload thường bị chọn hosting model theo thói quen. Một job bursty chạy khi Blob xuất hiện khác đáng kể với consumer luôn hoạt động, giữ local state/cache hoặc cần kiểm soát concurrency và shutdown chặt.

**Ví dụ thực tế:**
Thumbnail generation phát sinh theo Blob event và có workload không đều có thể hợp Azure Functions. Một pricing engine liên tục consume stream, warm cache lớn và cần predictable process lifecycle có thể hợp .NET Worker chạy trên App Service, Container Apps hoặc Kubernetes hơn.

**Trade-off:**
Functions giảm infrastructure management và scale tốt cho event workload, nhưng có hosting limits, cold-start/scale behavior và platform semantics cần hiểu. Worker cho quyền kiểm soát lớn hơn nhưng team phải sở hữu deployment, scaling, health và capacity nhiều hơn.

**Middle → Senior insight:**
Middle developer cần implement cancellation, retries, idempotency và graceful shutdown đúng hosting model. Senior / Technical developer phải so workload shape, latency SLO, cost, concurrency, operational ownership và failure recovery trước khi chọn; không dùng serverless chỉ vì ít code bootstrap hơn.

### Design 2 — Normalize write model, denormalize read model khi áp lực đọc thực sự yêu cầu

**Khái niệm:**
Normalization bảo vệ consistency và giảm duplication ở transactional model; denormalization có thể tạo representation tối ưu cho read path. Đây là trade-off có chủ đích, không phải lựa chọn “database chuẩn” đối đầu “database nhanh”.

**Vấn đề nó giải quyết:**
Một e-commerce API có write model Order/Customer/Product đúng invariant nhưng trang reporting phải join và aggregate khối lượng lớn liên tục. Ép cùng một model phục vụ cả transaction lẫn mọi read shape có thể làm query phức tạp hoặc gây tải lên OLTP database.

**Ví dụ thực tế:**
Checkout giữ normalized relational schema và transaction rõ. Dashboard có thể dùng projection/materialized view chứa `OrderId, CustomerName, Total, Region` được cập nhật theo pipeline; read không cần join lại toàn bộ domain mỗi request.

**Trade-off:**
Denormalized read model giảm read latency và coupling với query phức tạp nhưng tạo duplication, refresh/rebuild logic và eventual consistency. Nếu workload nhỏ và SQL query/index đã đáp ứng SLO, thêm projection pipeline chỉ làm hệ thống khó vận hành hơn.

**Middle → Senior insight:**
Middle developer cần hiểu constraints và không denormalize tùy tiện vì một query chậm. Senior / Technical developer phải đo workload, xác định staleness tolerance, ownership và rebuild strategy; chỉ tách read model khi lợi ích vượt chi phí đồng bộ và vận hành.

### Design 3 — Observability phải được thiết kế theo failure question, không theo số lượng log

**Khái niệm:**
Observability tốt kết hợp metrics, traces và structured logs để trả lời các câu hỏi vận hành cụ thể: request nào chậm, dependency nào gây lỗi, release nào tạo regression và business operation nào bị ảnh hưởng.

**Vấn đề nó giải quyết:**
Hệ thống có hàng GB log vẫn có thể không debug được incident nếu thiếu correlation, latency breakdown hoặc business identifiers an toàn. Ngược lại, log mọi thứ làm tăng cost và che mất signal.

**Ví dụ thực tế:**
Sau deployment, p99 checkout tăng. Dashboard cho thấy latency tăng ở payment dependency; distributed trace nối request với outbound call; structured log mang `orderId`, dependency result và deployment version giúp khoanh vùng thay đổi mà không cần grep exception ngẫu nhiên.

**Trade-off:**
Telemetry giàu context rút ngắn MTTR nhưng tăng storage/cost, instrumentation effort và rủi ro thu thập dữ liệu nhạy cảm. Sampling giảm cost nhưng có thể bỏ mất rare failure nếu policy không phù hợp.

**Middle → Senior insight:**
Middle developer cần tạo structured logs, correlation và telemetry ở dependency boundary đúng cách. Senior / Technical developer phải thiết kế SLI/SLO, cardinality budget, sampling, retention và incident queries từ trước; mục tiêu là khả năng trả lời failure hypothesis nhanh, không phải tối đa hóa số event được ghi.
