# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncDisposable` khi cleanup bản thân cũng là I/O

**Mẹo:**
Nếu resource cần flush, commit hoặc đóng kết nối bằng asynchronous I/O, triển khai hoặc sử dụng `IAsyncDisposable` với `await using` thay vì ép cleanup chạy synchronously.

**Tại sao hữu ích:**
`Dispose()` không thể `await`. Khi cleanup cần network/disk I/O, việc block bằng `.GetAwaiter().GetResult()` có thể giữ ThreadPool thread không cần thiết và làm shutdown chậm dưới tải. `DisposeAsync()` cho phép lifecycle tiếp tục bất đồng bộ.

**Ví dụ:**
```csharp
await using var stream = new FileStream(
    path,
    FileMode.Create,
    FileAccess.Write,
    FileShare.None,
    bufferSize: 64 * 1024,
    useAsync: true);

await JsonSerializer.SerializeAsync(stream, payload, cancellationToken: ct);
```
Resource được dispose sau khi operation hoàn tất mà không cần sync-over-async.

**Lưu ý:**
Không tạo `IAsyncDisposable` chỉ vì class có method async. Chỉ dùng khi cleanup thực sự cần asynchronous work; nếu cleanup chỉ giải phóng memory state hoặc handle synchronously thì `IDisposable` đơn giản hơn.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` cho dataset lớn

**Mẹo:**
Với API duyệt tuần tự qua bảng lớn, ưu tiên keyset/seek pagination dựa trên sort key ổn định thay vì tăng `OFFSET` theo page number.

**Tại sao hữu ích:**
`OFFSET 100000` vẫn buộc database tìm và bỏ qua lượng rows lớn trước khi trả page. Keyset pagination tiếp tục từ giá trị cuối cùng và có thể seek qua index, đồng thời ít bị duplicate/missing rows hơn khi dữ liệu thay đổi giữa các page.

**Ví dụ:**
```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@lastCreatedAt, @lastId)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```
`id` đóng vai trò tie-breaker để ordering deterministic khi nhiều rows có cùng `created_at`.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 237 hoặc cần exact page count. Sort columns phải có ordering ổn định và index phù hợp với query pattern.

### Tip 3 — Phân biệt readiness với liveness trong Kubernetes

**Mẹo:**
Readiness probe nên trả lời “instance có nhận traffic được không?”, còn liveness probe chỉ nên xác định process có bị kẹt đến mức cần restart hay không.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp vào database hoặc external API, một outage downstream có thể khiến toàn bộ Pods restart đồng loạt, làm sự cố nặng hơn. Readiness có thể tạm rút Pod khỏi Service mà không phá process state.

**Ví dụ:**
```text
/readiness -> app initialized + critical local state ready
/liveness  -> process/event loop vẫn hoạt động
```
Một dependency chậm có thể ảnh hưởng readiness nếu instance thực sự không thể phục vụ request, nhưng không nhất thiết là lý do để kubelet kill process.

**Lưu ý:**
Probe quá nhạy cũng gây restart loop khi startup lâu. Cần cấu hình `startupProbe`, thresholds và timeout theo behavior đo được thay vì copy cấu hình mặc định giữa mọi service.

### Tip 4 — Vue `computed` dành cho derived state, `watch` dành cho side effect

**Mẹo:**
Trong Vue.js, biểu thức được suy ra từ reactive state nên ưu tiên `computed`; chỉ dùng `watch` khi thay đổi state cần kích hoạt side effect như gọi API, ghi storage hoặc đồng bộ hệ thống ngoài component.

**Tại sao hữu ích:**
`computed` cache kết quả dựa trên dependency và mô tả quan hệ dữ liệu trực tiếp. Dùng nhiều `watch` để cập nhật state dẫn xuất dễ tạo duplicated state, ordering dependency và feedback loop khó debug.

**Ví dụ:**
```ts
const subtotal = computed(() =>
  cart.value.items.reduce((sum, x) => sum + x.price * x.quantity, 0)
)

watch(searchTerm, async (value, _, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())
  await search(value, controller.signal)
})
```

**Lưu ý:**
`watch` cho network request vẫn cần cancellation/debounce khi input thay đổi nhanh. Không biến `computed` thành nơi thực hiện side effect vì evaluator có thể chạy lại theo dependency lifecycle.

### Tip 5 — Với AI-generated migration, kiểm tra generated SQL chứ đừng chỉ đọc C# migration

**Mẹo:**
Khi AI coding agent hoặc developer tạo EF Core migration, review cả SQL được sinh ra bằng `dotnet ef migrations script`, đặc biệt với rename, type change, index và large-table migration.

**Tại sao hữu ích:**
Migration C# có thể trông hợp lý nhưng SQL thực tế lại rebuild table/index, lock lâu hoặc biến rename thành drop-and-create làm mất dữ liệu. AI càng dễ đưa ra migration “compile được” nhưng không hiểu data volume và deployment constraints.

**Ví dụ:**
```bash
dotnet ef migrations script PreviousMigration NewMigration \
  --idempotent \
  --output migration.sql
```
Review `ALTER`, lock implications, default/backfill và khả năng rollback trước khi đưa vào pipeline production.

**Lưu ý:**
Không coi generated SQL là portable giữa mọi provider/version. Với bảng lớn, schema migration và data backfill có thể cần tách thành nhiều release theo Expand-and-Contract thay vì một migration duy nhất.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency vs Pessimistic Locking

**Khái niệm:**
Optimistic concurrency cho nhiều request đọc/làm việc song song rồi phát hiện conflict khi ghi; pessimistic locking giữ lock sớm để ngăn concurrent modification. Đây là lựa chọn theo contention và business semantics, không phải hai mức “tốt/xấu”.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng sửa một Order từ version 7. Nếu cả hai ghi đè không kiểm tra, người lưu sau âm thầm làm mất thay đổi của người trước. Ngược lại, giữ database lock suốt một workflow dài có thể gây blocking và giảm throughput.

**Ví dụ thực tế:**
EF Core có thể dùng `rowversion`/concurrency token để `UPDATE ... WHERE Id = @id AND Version = @version`. Nếu affected rows bằng 0, application phát hiện conflict và quyết định reload, merge hoặc yêu cầu user thử lại. Với thao tác rất ngắn và contention cực cao như allocation một scarce resource, lock có thể hợp lý hơn.

**Trade-off:**
Optimistic concurrency tăng throughput khi conflict hiếm nhưng đẩy conflict resolution vào application. Pessimistic locking đơn giản hóa một số critical section nhưng tăng blocking, deadlock risk và coupling vào transaction duration.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency token và xử lý conflict thay vì catch rồi retry vô hạn. Senior / Technical developer phải đánh giá contention rate, invariant, transaction length, UX và failure mode để chọn optimistic, lock hoặc thiết kế atomic operation ở database.

### Design 2 — Queue vs Topic theo ownership của message

**Khái niệm:**
Queue phù hợp khi một logical consumer group cần xử lý một work item; Topic/pub-sub phù hợp khi cùng một event cần được nhiều subscriber độc lập quan sát. Sự khác biệt quan trọng là delivery semantics và ownership, không chỉ tên resource trên broker.

**Vấn đề nó giải quyết:**
Nếu `OrderPlaced` phải kích hoạt Inventory, Analytics và Notification, đặt tất cả consumers cạnh tranh trên cùng queue sẽ khiến chỉ một consumer nhận mỗi message. Ngược lại, tạo Topic cho command `GenerateInvoice` có thể khiến nhiều subscriber vô tình thực thi cùng một business action.

**Ví dụ thực tế:**
`GenerateInvoice` → queue `billing-work`; nhiều Billing workers là competing consumers. `OrderPlaced` → topic `orders`; subscriptions `inventory`, `analytics`, `notifications` mỗi bên có retry/DLQ độc lập.

**Trade-off:**
Topic giảm coupling giữa publisher và nhiều observers nhưng tăng fan-out, monitoring, schema-evolution và duplicate-processing concerns. Queue đơn giản hơn cho work distribution nhưng không tự cung cấp independent delivery cho nhiều bounded contexts.

**Middle → Senior insight:**
Middle developer cần chọn đúng primitive và viết consumer idempotent. Senior / Technical developer phải phân biệt command với event, xác định ownership, ordering, retry isolation, subscription lifecycle và tránh biến broker thành một mạng integration không có governance.

### Design 3 — Expand-and-Contract cho database schema evolution

**Khái niệm:**
Expand-and-Contract thay breaking schema change bằng nhiều bước tương thích: thêm cấu trúc mới trước, chuyển dần read/write, rồi chỉ xóa cấu trúc cũ khi mọi phiên bản application không còn phụ thuộc vào nó.

**Vấn đề nó giải quyết:**
Trong rolling/blue-green deployment, old và new application versions có thể chạy đồng thời. Rename/drop column trực tiếp khiến một version fail ngay cả khi deployment pipeline vẫn đang chuyển traffic.

**Ví dụ thực tế:**
Cần đổi `Customer.Name` thành `DisplayName`: release 1 thêm `DisplayName` nullable và backfill; release 2 ghi field mới và đọc fallback; sau khi telemetry xác nhận old version không còn chạy, release sau mới remove `Name`.

**Trade-off:**
Thiết kế này giảm deployment coupling và cho phép rollback an toàn hơn, nhưng tạm thời tồn tại duplicated schema/code, cần backfill và đòi hỏi discipline để hoàn tất phase “contract”.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible và hiểu nhiều app versions có thể coexist. Senior / Technical developer phải thiết kế rollout, backfill, observability, rollback point và cleanup ownership; nếu hệ thống deploy atomically và downtime được chấp nhận, multi-release migration có thể là complexity không cần thiết.
