# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Chỉ dùng EF Core compiled query cho hot path có query shape ổn định

**Mẹo:**
Nếu profiling cho thấy cùng một EF Core query được thực thi với tần suất rất cao và query shape gần như không đổi, có thể cân nhắc `EF.CompileQuery` hoặc `EF.CompileAsyncQuery` để giảm chi phí compile expression/query pipeline lặp lại.

**Tại sao hữu ích:**
EF Core đã cache nhiều phần của query compilation, nên phần lớn application không cần compiled query thủ công. Nhưng ở hot path rất nóng, nơi query nhỏ nhưng chạy hàng chục nghìn lần, chi phí expression processing và cache lookup vẫn có thể đáng kể so với chính database call.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<Order>>
    GetOrdersByCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, Guid customerId) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.CustomerId == customerId)
              .OrderByDescending(x => x.CreatedAt)
              .Take(20));
```

Chỉ áp dụng sau khi benchmark cho thấy query compilation overhead thực sự đáng chú ý.

**Lưu ý:**
Compiled query không sửa được SQL tệ, N+1, thiếu index hay round trip quá nhiều. Nếu query thay đổi shape động theo nhiều filter, abstraction này còn có thể làm code khó maintain hơn. Ưu tiên tối ưu database/query shape trước micro-optimization ở EF layer.

### Tip 2 — Khi Redis hit ratio giảm, kiểm tra eviction trước khi tăng TTL

**Mẹo:**
Nếu cache hit ratio giảm bất thường hoặc dữ liệu liên tục bị miss dù TTL vẫn còn dài, kiểm tra `maxmemory`, eviction policy và số lượng key bị evict thay vì mặc định tăng TTL.

**Tại sao hữu ích:**
TTL chỉ nói key được phép sống bao lâu; Redis vẫn có thể xóa key sớm nếu memory chạm giới hạn và eviction policy yêu cầu giải phóng bộ nhớ. Tăng TTL trong tình huống memory pressure còn có thể làm eviction nặng hơn.

**Ví dụ:**
```text
Triệu chứng:
- cache hit ratio từ 92% xuống 55%
- database load tăng
- key TTL vẫn còn vài giờ

Evidence:
- used_memory gần maxmemory
- evicted_keys tăng nhanh

Diagnosis:
Redis thiếu capacity hoặc key/value quá lớn, không phải TTL quá ngắn.
```

Sau đó kiểm tra object size, key cardinality, serialization format và policy như `allkeys-lru`/`volatile-lru` phù hợp với workload hay không.

**Lưu ý:**
Đừng đổi eviction policy giữa production incident mà chưa hiểu semantics. Một policy sai có thể giữ key ít giá trị nhưng đẩy key business-critical ra ngoài. Cache cần observability về hit, miss, eviction, memory và latency chứ không chỉ uptime.

### Tip 3 — JWT phải được validate, không chỉ decode payload

**Mẹo:**
Khi backend nhận JWT, luôn validate signature, issuer, audience, expiration và các policy claim cần thiết bằng authentication middleware/framework phù hợp. Việc Base64-decode payload chỉ để đọc claim không chứng minh token là hợp lệ.

**Tại sao hữu ích:**
JWT payload có thể được đọc và sửa rất dễ vì nó không được mã hóa theo mặc định. Security đến từ cryptographic signature và validation rules. Nếu code chỉ đọc `sub` hoặc `role` mà không verify signature/issuer/audience, attacker có thể tự tạo token giả với claim mong muốn.

**Ví dụ:**
```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = "orders-api";
        options.RequireHttpsMetadata = true;
    });
```

Authorization policy sau đó nên kiểm tra scope/role phù hợp cho từng endpoint.

**Lưu ý:**
Signature hợp lệ không đồng nghĩa user được phép làm mọi việc. Authentication và authorization là hai bước khác nhau. Cũng cần xử lý key rotation, clock skew, token lifetime và tránh log nguyên access token vào telemetry.

### Tip 4 — Với Playwright, đợi theo condition thay vì `WaitForTimeout`

**Mẹo:**
Trong end-to-end test, ưu tiên locator auto-waiting và assertion có condition thay vì chèn `WaitForTimeout(2000)` để “đợi UI ổn định”.

**Tại sao hữu ích:**
Sleep cố định làm test vừa chậm vừa flaky: 2 giây có thể thừa ở máy nhanh nhưng vẫn thiếu trên CI chậm. Playwright có cơ chế chờ element actionable/visible và retry assertion tới timeout, phù hợp hơn với UI bất đồng bộ.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

await Expect(page.GetByText("Saved successfully"))
    .ToBeVisibleAsync();
```

Nếu UI phải chờ network call, có thể chờ response hoặc trạng thái business cụ thể thay vì sleep theo thời gian ước đoán.

**Lưu ý:**
Auto-wait không cứu được test có selector mơ hồ hoặc state không deterministic. Tránh test dựa vào timing nội bộ của implementation; hãy đợi observable outcome mà user thực sự nhìn thấy hoặc workflow thực sự cần.

### Tip 5 — Trên IIS, phân biệt application recycle với process crash khi điều tra restart

**Mẹo:**
Khi ASP.NET application trên IIS “tự restart”, kiểm tra Windows Event Viewer, IIS Application Pool settings và process exit reason trước khi kết luận application bị crash.

**Tại sao hữu ích:**
Application Pool có thể recycle vì schedule, idle timeout, config change, memory threshold hoặc deployment. Những trường hợp này nhìn từ application đều giống process bị mất state nhưng root cause hoàn toàn khác crash do unhandled exception hoặc native failure.

**Ví dụ:**
```text
Symptom:
- in-memory cache biến mất
- background job đang chạy bị dừng
- request đầu tiên sau đó chậm hơn

Evidence cần kiểm tra:
- Event Viewer / WAS events
- App Pool recycle settings
- deployment timestamp
- process exit code
- memory/private bytes trước restart
```

Từ evidence mới quyết định đây là expected recycle, memory pressure hay application crash.

**Lưu ý:**
Không nên lưu state quan trọng chỉ trong process nếu application có thể recycle bất kỳ lúc nào. Session, distributed cache, job checkpoint và lock cần thiết kế theo lifecycle thực tế của host.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service nên chọn theo lifecycle và workload, không theo “serverless hay không”

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có trigger rõ, execution ngắn/trung bình và khả năng scale theo event. Worker Service phù hợp hơn khi process cần lifecycle dài, polling/control loop riêng, connection lâu dài hoặc resource behavior cần kiểm soát ổn định.

**Vấn đề nó giải quyết:**
Team thường chọn Functions chỉ vì muốn “serverless”, rồi sau đó handler chạy hàng chục phút, giữ nhiều connection, có orchestration phức tạp và phụ thuộc mạnh vào host limits. Ngược lại, một Worker luôn bật cho vài event mỗi giờ có thể lãng phí vận hành/cost.

**Ví dụ thực tế:**
```text
Image resize theo Blob trigger
-> Azure Functions phù hợp

Consumer giữ TCP connection lâu dài + batch xử lý liên tục
-> Worker Service thường rõ lifecycle hơn
```

Với Service Bus consumer đơn giản, cả hai có thể đúng; quyết định phụ thuộc scale pattern, execution time, hosting model và operational control.

**Trade-off:**
Functions giảm server management và hỗ trợ trigger/binding thuận tiện, nhưng có cold start, execution/host semantics và scaling behavior phải hiểu rõ. Worker Service cho nhiều quyền kiểm soát hơn nhưng cần hosting, deployment, scaling và monitoring chủ động hơn.

**Middle → Senior insight:**
Middle developer cần hiểu lifecycle, retry và shutdown semantics của từng hosting model. Senior / Technical developer phải chọn dựa trên workload shape, reliability, latency, cost, observability và operational ownership thay vì chọn theo trend hoặc framework familiarity.

### Design 2 — Normalization vs Denormalization là trade-off giữa write correctness và read efficiency

**Khái niệm:**
Normalization giảm duplication và giữ invariant tập trung; denormalization chấp nhận lưu lặp hoặc precompute một phần dữ liệu để read path đơn giản/nhanh hơn. Cả hai đều là công cụ, không phải trạng thái “đúng” hoặc “sai” tuyệt đối.

**Vấn đề nó giải quyết:**
Một e-commerce database có thể normalize `Product`, `Category`, `Price`, `Inventory` rất sạch nhưng trang listing phải join nhiều bảng và aggregate liên tục. Khi read volume lớn hơn nhiều write volume, denormalized read model có thể giảm cost đáng kể.

**Ví dụ thực tế:**
```text
Transactional model:
Products
Prices
Inventory
Categories

Read model:
ProductSearchDocument
- ProductId
- Name
- CurrentPrice
- StockStatus
- CategoryNames
```

Transactional database giữ source-of-truth; read model có thể được rebuild từ event/batch nếu cần.

**Trade-off:**
Normalization đơn giản hóa consistency nhưng có thể làm read query phức tạp và tốn join. Denormalization tăng read performance nhưng thêm synchronization, stale-data risk và update complexity. Nếu dữ liệu nhỏ, một query/index tốt có thể rẻ hơn cả một pipeline đồng bộ riêng.

**Middle → Senior insight:**
Middle developer cần biết duplication luôn kéo theo update semantics. Senior / Solution-oriented engineer phải đánh giá read/write ratio, freshness requirement, rebuildability, failure recovery và operational cost trước khi thêm denormalized model.

### Design 3 — Webhook nên tách durable ingestion khỏi business processing dài

**Khái niệm:**
Webhook receiver nên xác thực request, ghi nhận event một cách durable rồi phản hồi nhanh; business processing dài hoặc dễ lỗi nên chạy bất đồng bộ phía sau. Boundary này tách availability của sender khỏi thời gian xử lý nội bộ của hệ thống nhận.

**Vấn đề nó giải quyết:**
Payment provider gửi webhook và yêu cầu response trong vài giây. Nếu endpoint đồng bộ update nhiều bảng, gọi email service và CRM trước khi trả `200`, một dependency chậm có thể làm provider timeout rồi retry cùng event, tạo duplicate processing.

**Ví dụ thực tế:**
```text
POST /webhooks/payment
1. verify signature
2. kiểm tra event identity
3. persist event / enqueue durable message
4. trả 2xx nhanh

Worker:
5. apply business transition
6. gọi downstream integrations
7. retry / dead-letter nếu cần
```

Deduplication key thường lấy từ event ID của provider hoặc business identity có semantics rõ.

**Trade-off:**
Thiết kế này tăng reliability và giảm webhook latency, nhưng đưa eventual consistency vào hệ thống và cần queue/inbox, monitoring, replay, deduplication. Với webhook đơn giản, ít traffic và xử lý chỉ một transaction rất ngắn, xử lý đồng bộ có thể vẫn đủ.

**Middle → Senior insight:**
Middle developer cần implement signature validation, idempotency và response semantics chính xác. Senior / Technical developer phải thiết kế durable boundary, retry policy, ordering, duplicate handling, replay tooling và quyết định phần nào bắt buộc hoàn thành trước khi trả `2xx`.
