# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Task.WhenEach` khi muốn xử lý kết quả theo thứ tự hoàn thành

**Mẹo:**
Khi chạy nhiều task độc lập và muốn xử lý task nào hoàn thành trước thì consume trước, dùng `Task.WhenEach` thay vì chờ `Task.WhenAll` rồi mới xử lý toàn bộ kết quả.

**Tại sao hữu ích:**
Giảm latency cảm nhận và tránh giữ kết quả của các task nhanh chỉ vì một task chậm chưa xong. Phù hợp với fan-out I/O như gọi nhiều API độc lập.

**Ví dụ:**
```csharp
var tasks = endpoints.Select(
    endpoint => FetchAsync(endpoint, cancellationToken));

await foreach (var completed in Task.WhenEach(tasks))
{
    try
    {
        var result = await completed;
        Process(result);
    }
    catch (Exception ex)
    {
        logger.LogWarning(ex, "One endpoint failed");
    }
}
```

**Lưu ý:**
Đừng dùng pattern này nếu business logic yêu cầu giữ đúng thứ tự input hoặc chỉ được commit khi toàn bộ task thành công. Khi đó `Task.WhenAll` hoặc orchestration khác phù hợp hơn.

### Tip 2 — Dùng `ExecuteSqlInterpolatedAsync` thay vì tự nối chuỗi SQL động

**Mẹo:**
Khi cần chạy raw SQL trong EF Core với giá trị runtime, ưu tiên API parameterized như `ExecuteSqlInterpolatedAsync` hoặc `FromSqlInterpolated` thay vì string concatenation.

**Tại sao hữu ích:**
Giảm nguy cơ SQL injection và tránh lỗi escaping thủ công, đồng thời vẫn cho phép viết SQL rõ ràng khi LINQ không phù hợp.

**Ví dụ:**
```csharp
var cutoff = DateTime.UtcNow.AddDays(-30);

await dbContext.Database.ExecuteSqlInterpolatedAsync(
    $"DELETE FROM AuditLogs WHERE CreatedAt < {cutoff}",
    cancellationToken);
```

**Lưu ý:**
Interpolation chỉ parameterize giá trị, không parameterize identifier như table/column name. Nếu identifier là dynamic, cần whitelist rõ ràng thay vì nhận trực tiếp từ input.

### Tip 3 — Dùng `EXPLAIN (ANALYZE, WAL)` khi tối ưu write-heavy PostgreSQL query

**Mẹo:**
Với `INSERT`/`UPDATE`/`DELETE` nặng, thêm `WAL` vào `EXPLAIN (ANALYZE, ...)` để xem lượng write-ahead log phát sinh bên cạnh execution time và buffer usage.

**Tại sao hữu ích:**
Hai query có runtime gần nhau nhưng một query có thể tạo nhiều WAL hơn đáng kể, ảnh hưởng replication bandwidth, checkpoint pressure và storage I/O.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
UPDATE orders
SET status = 'Archived'
WHERE created_at < now() - interval '1 year';
```

**Lưu ý:**
`ANALYZE` thực sự chạy statement. Với write query production, phải test trên môi trường an toàn hoặc dùng transaction/rollback có chủ đích nếu semantics cho phép.

### Tip 4 — Dùng `git show :path/to/file` để đọc file đang ở index

**Mẹo:**
Khi đã `git add` nhưng muốn xem chính xác version đang staged mà không bị lẫn với working tree, đọc file trực tiếp từ index bằng `git show :<path>`.

**Tại sao hữu ích:**
Rất tiện khi review partial staging hoặc khi working tree đã tiếp tục thay đổi sau lần `git add` gần nhất.

**Ví dụ:**
```bash
git show :src/PaymentService.cs
```

So với working tree:

```bash
git diff -- src/PaymentService.cs
```

So staged với HEAD:

```bash
git diff --cached -- src/PaymentService.cs
```

**Lưu ý:**
Cú pháp này đọc index hiện tại, không phải file trong commit gần nhất. Nếu file chưa được stage thì nội dung có thể không tồn tại trong index theo trạng thái bạn mong đợi.

### Tip 5 — Dùng `systemctl show` để xem nguyên nhân restart loop thay vì chỉ nhìn status ngắn

**Mẹo:**
Khi Linux service restart liên tục, dùng `systemctl show` để xem `Restart`, `RestartUSec`, `NRestarts`, `ExecMainStatus` và các property runtime khác.

**Tại sao hữu ích:**
Giúp xác định service đang fail vì process exit code, watchdog, restart policy hay systemd throttling mà `systemctl status` đôi khi chỉ hiển thị một phần.

**Ví dụ:**
```bash
systemctl show myapp.service \
  -p Restart \
  -p RestartUSec \
  -p NRestarts \
  -p ExecMainCode \
  -p ExecMainStatus
```

**Lưu ý:**
Thông tin này cho biết symptom và policy của systemd, không thay thế application log/core dump. Nếu process crash, vẫn cần correlate với `journalctl`, dump hoặc runtime diagnostics.

## 🧠 Software Design

### Design 1 — Anti-Corruption Layer cho external model có semantics khác domain nội bộ

**Khái niệm:**
Anti-Corruption Layer chuyển đổi model, terminology và behavior của hệ thống ngoài sang model của bounded context nội bộ thay vì để SDK/vendor DTO lan xuyên domain.

**Vấn đề nó giải quyết:**
External API thường có naming, lifecycle và constraint khác business model của bạn. Nếu domain phụ thuộc trực tiếp vào model đó, mọi thay đổi vendor dễ kéo theo refactor rộng.

**Ví dụ thực tế:**
Exchange Online trả mailbox state theo `RecipientTypeDetails`, forwarding fields và permission model riêng. Application có thể map sang domain capability như `MailboxMode`, `ForwardingPolicy`, `DelegationPolicy` trước khi business logic xử lý.

**Trade-off:**
ACL giảm vendor coupling và làm domain rõ semantics hơn, nhưng thêm mapping, translation error và code phải maintain. Với integration cực nhỏ, mapping layer quá dày có thể tạo ceremony không cần thiết.

**Middle → Senior insight:**
Middle developer nên nhận ra external DTO không phải domain model. Senior developer cần quyết định boundary translation, ownership và mức abstraction đủ để bảo vệ domain mà không cố che mọi chi tiết hữu ích của dependency.

### Design 2 — Queue per tenant hay shared queue là quyết định fairness và isolation

**Khái niệm:**
Workload multi-tenant có thể dùng một queue chung với tenant metadata hoặc queue riêng theo tenant/tier. Lựa chọn này ảnh hưởng trực tiếp đến noisy neighbor, ordering và operational cost.

**Vấn đề nó giải quyết:**
Một tenant gửi burst hàng trăm nghìn job có thể làm tenant khác chờ lâu nếu tất cả nằm trong một FIFO queue không có fairness control.

**Ví dụ thực tế:**
Một SaaS export service có thể dùng shared queue nhưng scheduler áp dụng per-tenant concurrency quota. Với vài enterprise tenant có SLA riêng, hệ thống có thể tách queue riêng cho tier đó để đảm bảo capacity và monitoring độc lập.

**Trade-off:**
Shared queue đơn giản và tận dụng worker tốt hơn nhưng cần fairness/admission control. Queue riêng tăng isolation và SLA control nhưng làm provisioning, monitoring và capacity fragmentation phức tạp hơn.

**Middle → Senior insight:**
Middle developer nên hiểu queue topology là một phần của resource isolation. Senior developer phải cân nhắc tenant count, traffic skew, SLA, ordering scope và operational overhead trước khi chọn shared hay dedicated queue.

### Design 3 — Prefer explicit idempotency key hơn suy đoán duplicate từ payload

**Khái niệm:**
Với command có thể được retry qua network, client gửi một `Idempotency-Key` ổn định để server nhận diện cùng một logical operation thay vì cố suy đoán duplicate bằng hash payload hoặc timestamp.

**Vấn đề nó giải quyết:**
Timeout có thể xảy ra sau khi server đã commit nhưng trước khi client nhận response. Retry mù có thể tạo duplicate payment, booking hoặc job.

**Ví dụ thực tế:**
Client gửi:

```http
POST /payments
Idempotency-Key: 8db8c1c0-...
```

Server lưu key cùng trạng thái/result của operation. Retry cùng key trả lại kết quả cũ thay vì tạo payment mới.

**Trade-off:**
Explicit key làm semantics retry rõ và đáng tin hơn, nhưng cần storage, TTL, conflict rule khi cùng key đi với payload khác và concurrency control khi hai request cùng key tới đồng thời.

**Middle → Senior insight:**
Middle developer nên biết retry an toàn cần identity của operation, không chỉ retry policy. Senior developer phải định nghĩa scope key, retention, payload mismatch behavior, race handling và khi nào idempotency nên được enforce ở API gateway, application hay domain boundary.
