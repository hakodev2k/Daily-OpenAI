# Daily Developer Tips & Design — 2026-09-25

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt timeout với cancellation trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` của request xuyên suốt các lời gọi I/O, nhưng đặt timeout riêng cho outbound dependency. Cancellation thể hiện caller không còn cần kết quả; timeout thể hiện dependency vượt quá ngân sách thời gian của ứng dụng.

**Tại sao hữu ích:**
Hai tín hiệu có nguyên nhân và cách quan sát khác nhau. Tách chúng giúp tránh giữ connection, DB query hoặc HTTP request vô ích, đồng thời cho phép telemetry phân biệt client disconnect với dependency chậm.

**Ví dụ:**
```csharp
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    HttpContext.RequestAborted, timeout.Token);

var response = await httpClient.GetAsync("/inventory/42", linked.Token);
```
Trong production, log nguyên nhân cancellation dựa trên token nào đã bị kích hoạt thay vì gom mọi `OperationCanceledException` thành lỗi 500.

**Lưu ý:**
Không tạo timeout tùy tiện ở từng layer. Timeout phải phù hợp với end-to-end latency budget; retry một request đã timeout còn có thể làm dependency quá tải nặng hơn.

### Tip 2 — Dùng keyset pagination khi OFFSET bắt đầu trở thành chi phí

**Mẹo:**
Với danh sách lớn và sort ổn định, ưu tiên keyset pagination dựa trên khóa cuối cùng thay vì `OFFSET ... FETCH` ngày càng sâu.

**Tại sao hữu ích:**
Database không phải bỏ qua hàng chục nghìn row trước khi trả page tiếp theo. Với index phù hợp, predicate có thể seek trực tiếp tới vùng dữ liệu cần đọc và giảm latency khi page number tăng.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index bắt đầu bằng `(CreatedAt DESC, Id DESC)` có thể hỗ trợ access pattern này.

**Lưu ý:**
Keyset pagination không phù hợp khi UI bắt buộc nhảy trực tiếp tới page 317. Sort phải deterministic; nếu chỉ sort theo `CreatedAt` không unique, record có thể bị bỏ sót hoặc lặp.

### Tip 3 — Điều tra Kubernetes restart bằng trạng thái trước đó, không chỉ log hiện tại

**Mẹo:**
Khi Pod liên tục restart, kiểm tra `Last State`, exit code, events và log của container trước đó trước khi sửa application code.

**Tại sao hữu ích:**
Container mới có thể chạy bình thường trong vài giây và che mất bằng chứng của lần crash trước. Exit code 137, failed liveness probe và application exception dẫn tới ba hướng chẩn đoán rất khác nhau.

**Ví dụ:**
```bash
kubectl describe pod api-7d9f...
kubectl logs api-7d9f... --previous
kubectl get events --sort-by=.lastTimestamp
```
Nếu `Last State: Terminated` cho thấy `OOMKilled`, tiếp tục đối chiếu memory usage và limits thay vì tăng restart delay.

**Lưu ý:**
Tăng memory limit có thể chỉ che memory leak. Đồng thời đừng kết luận `OOMKilled` chỉ từ exit code nếu chưa đối chiếu Pod status và node/container telemetry.

### Tip 4 — Dùng correlation context để nối frontend, API và dependency telemetry

**Mẹo:**
Giữ trace context xuyên browser → ASP.NET Core → database/outbound HTTP, và thêm business identifiers có kiểm soát vào structured logs.

**Tại sao hữu ích:**
Một lỗi “checkout quay mãi” hiếm khi được giải quyết bằng một log line. Distributed tracing cho phép đi từ user request tới dependency span chậm, thay vì tìm timestamp thủ công giữa nhiều hệ thống.

**Ví dụ:**
Trong Application Insights/OpenTelemetry, bắt đầu từ request có p95 cao, mở dependency spans và xác định một HTTP call chiếm 2.8 giây. Log thêm `OrderId` như structured property để liên hệ trace với nghiệp vụ mà không log payload nhạy cảm.

**Lưu ý:**
Không dùng email, access token hoặc dữ liệu cá nhân làm correlation key. Cardinality quá cao trong metrics cũng có thể làm chi phí observability tăng mạnh.

### Tip 5 — Dùng AI coding agent để tạo hypothesis, không giao quyền kết luận

**Mẹo:**
Khi nhờ AI phân tích bug, cung cấp code path, version, failing test/log và yêu cầu agent chỉ ra evidence cho từng hypothesis; sau đó xác minh bằng test hoặc source chính thức.

**Tại sao hữu ích:**
Agent rất nhanh trong việc nối các dấu hiệu rời rạc, nhưng có thể giả định API tồn tại hoặc áp dụng behavior của version khác. Evidence-driven prompting biến AI thành công cụ thu hẹp search space thay vì nguồn sự thật.

**Ví dụ:**
Thay vì “fix lỗi EF Core này”, yêu cầu: “Từ stack trace và generated SQL này, đưa tối đa 3 hypotheses; với mỗi hypothesis chỉ ra dòng code/evidence, cách falsify bằng test, rồi đề xuất patch nhỏ nhất.”

**Lưu ý:**
Generated test cũng có thể chỉ xác nhận implementation mà agent vừa viết. Với security, migration và data-loss risk, luôn review source/documentation và chạy test độc lập.

## 🧠 Software Design

### Design 1 — Transactional Outbox cho thay đổi DB và publish message

**Khái niệm:**
Outbox ghi business change và message-to-be-published trong cùng local database transaction. Một publisher riêng đọc outbox và gửi message ra broker, thay vì cố làm database commit và broker publish thành một thao tác “gần như atomic”.

**Vấn đề nó giải quyết:**
Nếu `SaveChangesAsync()` thành công nhưng publish tới Azure Service Bus thất bại, hệ thống có dữ liệu mới nhưng downstream không nhận event. Đảo thứ tự publish trước cũng tạo lỗi ngược lại nếu DB transaction rollback.

**Ví dụ thực tế:**
Checkout tạo `Order` và `OrderCreated` outbox record trong cùng transaction. Worker publish record chưa xử lý lên Service Bus; consumer dùng idempotency key vì message vẫn có thể được giao lại.

**Trade-off:**
Lợi ích là loại bỏ dual-write gap mà không cần distributed transaction. Chi phí là eventual consistency, thêm publisher, cleanup, monitoring backlog và yêu cầu idempotent consumer. Outbox không tự tạo exactly-once processing.

**Middle → Senior insight:**
Middle developer cần triển khai transaction và publisher đúng, xử lý retry/deduplication. Senior / Technical developer phải quyết định liệu consistency risk có đủ lớn để biện minh cho Outbox, thiết kế ownership/ordering/retention và vận hành khi backlog tăng hàng triệu record thay vì mặc định thêm pattern vào mọi service.

### Design 2 — Cache-aside với degraded mode thay vì biến Redis thành dependency bắt buộc

**Khái niệm:**
Trong cache-aside, application đọc cache trước, cache miss thì lấy dữ liệu từ source of truth rồi populate cache. Với dữ liệu có thể tái tạo, thiết kế thường nên cho phép request tiếp tục khi Redis tạm thời unavailable.

**Vấn đề nó giải quyết:**
Một cache được thêm để giảm latency có thể vô tình trở thành single point of failure: Redis outage khiến toàn bộ API fail dù SQL database vẫn khỏe.

**Ví dụ thực tế:**
Product catalog thử Redis trong vài millisecond; khi cache timeout, circuit breaker tạm bỏ qua cache và đọc SQL. Hệ thống đồng thời giới hạn concurrency hoặc dùng request coalescing để tránh hàng nghìn cache miss cùng đập xuống database.

**Trade-off:**
Degraded mode tăng availability nhưng có thể chuyển tải đột ngột sang database và tăng latency. Fail-open cũng không đúng với cache dùng cho security-sensitive state hoặc dữ liệu mà source không thể chịu tải trực tiếp.

**Middle → Senior insight:**
Middle developer cần xử lý cache miss, TTL, serialization và fallback đúng. Senior / Technical developer phải xác định cache nào là optimization hay system-of-record-like dependency, tính capacity của fallback path, kiểm soát stampede và quyết định khi nào fail-open nguy hiểm hơn fail-closed.

### Design 3 — Contract testing tại ranh giới frontend/backend

**Khái niệm:**
Contract test xác minh producer và consumer đồng ý về shape và semantics của API mà không cần biến mọi kiểm tra thành full E2E test. Với REST, OpenAPI có thể là contract nền nhưng test vẫn cần kiểm tra behavior quan trọng.

**Vấn đề nó giải quyết:**
Backend đổi nullable field, enum hoặc status code có thể vẫn pass unit tests nhưng phá Vue/React client sau deployment. E2E test đơn thuần thường chậm và không bao phủ hết các biến thể contract.

**Ví dụ thực tế:**
Mobile/Web client phụ thuộc `GET /api/orders/{id}`. Pipeline kiểm tra response schema, required fields, enum compatibility và ProblemDetails cho 404. Breaking contract bị chặn trước khi backend deploy độc lập.

**Trade-off:**
Contract testing phát hiện integration drift sớm và nhanh hơn E2E, nhưng tạo thêm artifact/versioning discipline và không chứng minh toàn bộ workflow chạy đúng trong môi trường thật. Contract quá chi tiết còn khóa chặt implementation không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu backward-compatible change và viết test cho contract thực sự được consumer dùng. Senior / Technical developer phải thiết kế versioning/deprecation policy, phân định contract test với integration/E2E test và cân bằng deployment independence với chi phí duy trì nhiều consumer contracts.
