# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `StringComparer` rõ ràng cho identifier thay vì phụ thuộc culture mặc định

**Mẹo:**
Khi so sánh key kỹ thuật như username chuẩn hóa, route token, header name nội bộ hoặc cache key, chọn `StringComparer.Ordinal` / `StringComparer.OrdinalIgnoreCase` rõ ràng thay vì dùng so sánh culture-sensitive mặc định.

**Tại sao hữu ích:**
Giảm bug khó đoán khi application chạy dưới culture khác nhau và giúp semantics của dictionary/set nhất quán với loại dữ liệu đang xử lý.

**Ví dụ:**
```csharp
var handlers = new Dictionary<string, IHandler>(
    StringComparer.OrdinalIgnoreCase);

handlers["approve"] = approveHandler;

if (handlers.TryGetValue("APPROVE", out var handler))
{
    await handler.HandleAsync();
}
```

**Lưu ý:**
Không dùng `OrdinalIgnoreCase` cho text hiển thị cho user hoặc sorting ngôn ngữ tự nhiên. Những trường hợp đó cần culture-aware comparison phù hợp.

### Tip 2 — Tắt `AutoDetectChanges` tạm thời trong EF Core khi batch cực lớn

**Mẹo:**
Với batch insert/update rất lớn, nếu profiling cho thấy change detection chiếm đáng kể CPU, có thể tạm tắt `ChangeTracker.AutoDetectChangesEnabled` trong vùng code kiểm soát chặt.

**Tại sao hữu ích:**
Tránh EF Core lặp lại việc scan toàn bộ tracked graph ở nhiều operation liên tiếp, giúp batch throughput tốt hơn khi số entity tracked lớn.

**Ví dụ:**
```csharp
var tracker = dbContext.ChangeTracker;
var original = tracker.AutoDetectChangesEnabled;

try
{
    tracker.AutoDetectChangesEnabled = false;

    foreach (var entity in entities)
    {
        dbContext.Add(entity);
    }

    tracker.DetectChanges();
    await dbContext.SaveChangesAsync(cancellationToken);
}
finally
{
    tracker.AutoDetectChangesEnabled = original;
}
```

**Lưu ý:**
Đây là optimization nâng cao. Nếu quên gọi `DetectChanges()` đúng lúc hoặc code path phụ thuộc automatic detection, dữ liệu có thể không được persist như mong đợi.

### Tip 3 — Dùng `FOR UPDATE NOWAIT` khi lock contention nên fail nhanh

**Mẹo:**
Trong PostgreSQL, nếu một operation không nên chờ lock lâu, dùng `FOR UPDATE NOWAIT` để fail ngay khi row đang bị transaction khác khóa.

**Tại sao hữu ích:**
Giúp API hoặc worker phản hồi nhanh với trạng thái conflict/busy thay vì chiếm connection và chờ đến timeout.

**Ví dụ:**
```sql
SELECT id, status
FROM orders
WHERE id = @id
FOR UPDATE NOWAIT;
```

Application có thể bắt lock exception rồi trả `409 Conflict` hoặc retry có kiểm soát.

**Lưu ý:**
Fail-fast chỉ phù hợp khi caller có chiến lược xử lý conflict rõ ràng. Nếu business operation bắt buộc phải đợi resource, `NOWAIT` chỉ chuyển latency thành retry storm.

### Tip 4 — Dùng `git diff --color-moved` để review refactor có nhiều code bị di chuyển

**Mẹo:**
Khi PR chủ yếu move method/block giữa file, bật moved-code highlighting để phân biệt code thực sự thay đổi với code chỉ được chuyển vị trí.

**Tại sao hữu ích:**
Giảm review noise và giúp tập trung vào semantic change thay vì đọc lại hàng trăm dòng unchanged code.

**Ví dụ:**
```bash
git diff --color-moved=dimmed-zebra origin/main...HEAD
```

Có thể kết hợp:

```bash
git diff --color-moved --word-diff origin/main...HEAD
```

**Lưu ý:**
Highlight chỉ dựa trên similarity. Nếu code vừa move vừa rewrite mạnh, vẫn cần đọc logic đầy đủ và chạy test phù hợp.

### Tip 5 — Dùng `openssl x509` để kiểm tra certificate metadata nhanh

**Mẹo:**
Khi nghi certificate hết hạn, sai issuer hoặc SAN, lấy certificate rồi xem metadata thay vì chỉ dựa vào browser warning.

**Tại sao hữu ích:**
Giúp xác định nhanh lỗi TLS nằm ở expiry, chain, hostname hay certificate deployment sai.

**Ví dụ:**
```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com </dev/null 2>/dev/null \
| openssl x509 -noout -dates -issuer -subject -ext subjectAltName
```

**Lưu ý:**
Certificate metadata đúng không đảm bảo toàn bộ TLS handshake/chain đều hợp lệ. Với lỗi phức tạp vẫn cần kiểm tra intermediate CA, trust store, protocol và cipher negotiation.

## 🧠 Software Design

### Design 1 — Domain Service và Application Service có trách nhiệm khác nhau

**Khái niệm:**
Application Service điều phối use case, transaction, authorization và I/O boundary; Domain Service chứa business logic thuộc domain nhưng không tự nhiên thuộc về một entity/value object cụ thể.

**Vấn đề nó giải quyết:**
Nếu mọi logic đều nằm ở application layer, domain model trở nên anemic. Nhưng nếu entity tự gọi database, API hay queue, domain lại bị phụ thuộc infrastructure.

**Ví dụ thực tế:**
Use case `ApproveTimesheet` có thể do `TimesheetApplicationService` load aggregate, check permission và commit transaction. Một `OvertimePolicy` domain service tính rule overtime từ nhiều domain object nhưng không tự query database.

**Trade-off:**
Tách đúng giúp domain thuần và dễ test hơn, nhưng quá nhiều service nhỏ sẽ làm flow khó theo dõi. Không phải mọi function business đều cần một “DomainService” class riêng.

**Middle → Senior insight:**
Middle developer nên phân biệt orchestration với domain decision. Senior developer phải đặt logic vào nơi thể hiện ownership tốt nhất, giữ I/O ngoài domain core và tránh cả hai cực đoan: anemic model lẫn fat domain service.

### Design 2 — Snapshot Isolation giảm blocking nhưng có thể tạo write skew

**Khái niệm:**
Snapshot Isolation cho transaction đọc một snapshot nhất quán mà không block writer theo cách truyền thống, nhưng hai transaction có thể cùng đọc state cũ và cập nhật các row khác nhau tạo ra invariant sai.

**Vấn đề nó giải quyết:**
Giảm read/write contention và tăng concurrency, nhưng không tự bảo vệ mọi invariant liên quan nhiều row hoặc predicate.

**Ví dụ thực tế:**
Có rule “luôn phải có ít nhất một doctor on-call”. Hai transaction cùng đọc thấy còn 2 doctor, mỗi transaction cho một người nghỉ và update hai row khác nhau. Cả hai commit thành công, cuối cùng còn 0 doctor dù mỗi transaction riêng lẻ thấy invariant hợp lệ.

**Trade-off:**
Snapshot Isolation giảm blocking và cải thiện throughput, nhưng cần constraint, explicit locking hoặc serialization cho invariant nhạy cảm. Serializable mạnh hơn nhưng tăng retry/conflict cost.

**Middle → Senior insight:**
Middle developer nên hiểu isolation level không chỉ là tên cấu hình. Senior developer phải phân tích invariant nào dựa trên nhiều row/predicate, nhận diện write skew và chọn locking/constraint/isolation phù hợp thay vì mặc định “snapshot = an toàn hơn”.

### Design 3 — Schema Registry chỉ có giá trị khi compatibility được enforce trong delivery pipeline

**Khái niệm:**
Schema Registry lưu contract của event/message và policy compatibility như backward/forward compatibility. Giá trị lớn nhất xuất hiện khi producer change được kiểm tra tự động trước khi deploy.

**Vấn đề nó giải quyết:**
Trong event-driven system, producer dễ thêm/xóa/đổi field làm consumer cũ hỏng âm thầm nếu contract chỉ tồn tại dưới dạng document không được enforce.

**Ví dụ thực tế:**
`EmployeeUpdated.v3` được định nghĩa bằng Avro/JSON Schema/Protobuf. CI của producer kiểm tra schema mới có tương thích với version đang được consumer sử dụng trước khi publish artifact hoặc deploy.

**Trade-off:**
Registry + compatibility gate giảm breaking change và làm contract governance rõ ràng, nhưng thêm tooling, version policy và quy trình rollout. Nếu event rất ít và team nhỏ, ceremony có thể lớn hơn lợi ích.

**Middle → Senior insight:**
Middle developer nên hiểu schema version không chỉ là thêm `v2` vào topic. Senior developer phải quyết định compatibility mode, ownership, rollout order, deprecation window và cách enforce contract trong CI/CD để registry không biến thành kho metadata bị bỏ quên.
