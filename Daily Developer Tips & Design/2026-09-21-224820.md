# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — Chỉ dùng `Span<T>` khi profiling chứng minh allocation là bottleneck

**Mẹo:**
Trong hot path parsing/buffer processing, `Span<T>` và `ReadOnlySpan<T>` có thể thao tác trên memory hiện có thay vì tạo array hoặc substring mới.

**Tại sao hữu ích:**
Giảm temporary allocations có thể hạ GC pressure khi operation chạy với tần suất rất cao. Giá trị đến từ workload thực, không phải vì `Span<T>` luôn nhanh hơn code thông thường.

**Ví dụ:**
Telemetry ingestion parse hàng triệu dòng bằng `string.Split`. Profiler cho thấy temporary strings chiếm phần lớn Gen0 allocations; chuyển riêng parser sang `ReadOnlySpan<char>` rồi benchmark xác nhận allocation và throughput cải thiện.

**Lưu ý:**
`Span<T>` là `ref struct` và có lifetime restrictions. Không đổi business code dễ đọc thành low-level code nếu profiler không cho thấy bottleneck đáng kể.

### Tip 2 — EF Core optimistic concurrency cần business decision, không phải retry mù quáng

**Mẹo:**
Dùng concurrency token như SQL Server `rowversion` cho dữ liệu có concurrent edits và xử lý `DbUpdateConcurrencyException` bằng reload, merge hoặc reject tùy nghiệp vụ.

**Tại sao hữu ích:**
Optimistic concurrency phát hiện record đã thay đổi sau lần đọc. Retry tự động với state cũ có thể biến conflict hợp lệ thành lost update.

**Ví dụ:**
Hai nhân viên cùng sửa một order. Người A save trước; request của B mang `rowversion` cũ nên API trả conflict cùng state mới nhất thay vì âm thầm ghi đè thay đổi của A.

**Lưu ý:**
Concurrency token không thay transaction cho invariant liên quan nhiều records. API cũng nên map database exception thành contract rõ ràng thay vì expose exception nội bộ.

### Tip 3 — Elasticsearch dùng `filter` cho điều kiện không cần relevance score

**Mẹo:**
Đưa các constraint như `tenantId`, `status`, category hoặc range vào `bool.filter`; giữ full-text clauses cần relevance trong query/scoring context.

**Tại sao hữu ích:**
Exact constraints chỉ cần xác định document có hợp lệ hay không. Tách chúng khỏi scoring làm query intent rõ hơn và cho Elasticsearch tối ưu filter phù hợp.

**Ví dụ:**
Product search dùng `match` cho `name` và `description`, nhưng `filter` cho `tenantId`, `isPublished=true` và price range. Ranking text chỉ diễn ra trong tập documents hợp lệ.

**Lưu ý:**
Không chuyển full-text search sang filter nếu cần relevance. Query chậm còn có thể do mapping, shard layout hoặc aggregations; hãy profile trước khi kết luận.

### Tip 4 — Kubernetes readiness và liveness phải trả lời hai câu hỏi khác nhau

**Mẹo:**
Readiness quyết định Pod có nhận traffic hay không; liveness quyết định process có ở trạng thái cần restart hay không. Không sao chép dependency-heavy check cho cả hai.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc database, một database outage có thể khiến hàng loạt Pods khỏe bị restart. Readiness có thể tạm rút Pod khỏi traffic mà không phá process đang hoạt động.

**Ví dụ:**
Service mất dependency bắt buộc nên readiness unhealthy. Liveness vẫn healthy nếu process còn hoạt động; chỉ internal fatal state mới khiến liveness yêu cầu restart.

**Lưu ý:**
Probe quá nhạy có thể tạo restart loop. Cân nhắc `startupProbe`, thresholds và startup time; health endpoint phải nhẹ.

### Tip 5 — Với AI-generated code, verify API và dependency trước khi review style

**Mẹo:**
Kiểm tra package/version, API signature, framework behavior và khả năng build/test trước; sau đó mới review naming, abstraction và style.

**Tại sao hữu ích:**
Generated code có thể trông hợp lý nhưng dựa trên API không tồn tại hoặc version khác. Factual verification trước giúp loại premise sai với chi phí thấp.

**Ví dụ:**
Agent đề xuất extension method được cho là thuộc .NET 10. Build và source inspection cho thấy method thực tế thuộc package chưa được reference; finding được phát hiện trước khi team refactor quanh solution đó.

**Lưu ý:**
Build xanh không chứng minh logic đúng. Tests do cùng agent tạo vẫn cần đối chiếu requirements, edge cases và behavior độc lập.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository: abstraction phải mua được giá trị thực

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like access. Custom Repository đáng dùng khi nó tạo domain/persistence boundary có ý nghĩa, không phải chỉ bọc lại từng method EF Core.

**Vấn đề nó giải quyết:**
Generic Repository thường bắt đầu để giảm coupling nhưng cuối cùng leak `IQueryable` hoặc nhân đôi API của EF Core, tạo ceremony mà không tạo isolation thực.

**Ví dụ thực tế:**
Một modular monolith dùng `DbContext` trực tiếp cho CRUD/query đơn giản, nhưng pricing module dùng domain-specific repository vì aggregate loading và concurrency rules cần boundary ổn định.

**Trade-off:**
Direct `DbContext` đơn giản và giữ đầy đủ capability; Repository có thể tạo boundary/test seam tốt nhưng tăng maintenance nếu chỉ là abstraction mỏng.

**Middle → Senior insight:**
Middle developer cần hiểu tracking, query và transaction behavior ở cả hai cách. Senior / Technical developer phải chọn abstraction dựa trên cost of change, domain boundary và test strategy thay vì áp pattern mặc định.

### Design 2 — Service Bus queue vs topic: chọn theo ownership của consumption

**Khái niệm:**
Queue phù hợp khi một logical work item cần một consumer trong competing-consumer group xử lý. Topic + subscriptions phù hợp khi cùng event cần nhiều consumer groups độc lập nhận.

**Vấn đề nó giải quyết:**
Dùng queue cho integration event nhiều consumers làm producer/relay phải biết downstream. Dùng topic cho command lại có thể fan-out một operation ngoài ý muốn.

**Ví dụ thực tế:**
`GenerateInvoice` đi vào queue cho invoice workers. `OrderCompleted` publish lên topic để Billing, Analytics và Loyalty có subscriptions riêng.

**Trade-off:**
Queue đơn giản cho work distribution; topic decouple fan-out tốt hơn nhưng thêm subscription lifecycle, filtering, monitoring và schema-evolution concerns. Cả hai vẫn cần idempotency với at-least-once delivery.

**Middle → Senior insight:**
Middle developer cần hiểu retry, DLQ và duplicate processing. Senior / Technical developer phải xác định command/event semantics, ownership, ordering và failure isolation trước khi chọn topology.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo thêm system state

**Khái niệm:**
Feature Flag cho phép deploy code trước rồi bật behavior theo user, tenant hoặc percentage. Đổi lại, mỗi flag tạo thêm trạng thái phải vận hành và kiểm thử.

**Vấn đề nó giải quyết:**
Một thay đổi lớn không nhất thiết phải bật cho toàn bộ traffic ngay sau deployment. Progressive rollout giảm blast radius và cho phép tắt behavior mà không cần build artifact mới.

**Ví dụ thực tế:**
Checkout mới được bật lần lượt cho internal users, 5%, 25% rồi 100% traffic trong khi theo dõi error rate và latency. Nếu metrics xấu, team tắt feature để điều tra trên cùng binary.

**Trade-off:**
Feature Flag cải thiện release control nhưng tạo combinatorial states, dead code và configuration dependency. Flag không cleanup sẽ trở thành technical debt.

**Middle → Senior insight:**
Middle developer cần test enabled/disabled paths và default behavior. Senior / Technical developer phải thiết kế ownership, expiration, rollout metrics và cleanup policy, đồng thời phân biệt release flag ngắn hạn với operational configuration dài hạn.
