# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic thời gian mà không phụ thuộc clock thật

**Mẹo:**
Với .NET 8+, inject `TimeProvider` vào service có logic expiration, retry window hoặc scheduled behavior thay vì gọi `DateTime.UtcNow` rải rác. Trong test, dùng clock có thể điều khiển để dịch chuyển thời gian deterministically.

**Tại sao hữu ích:**
Clock thật là external dependency. Test dựa vào `Task.Delay`, thời điểm chạy hoặc boundary giây/phút dễ flaky và chậm. Tách time source giúp business logic kiểm thử được mà không phải chờ thời gian thực trôi qua.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        clock.GetUtcNow() >= expiresAt;
}
```
Test có thể cố định thời điểm trước/sau expiration boundary thay vì sleep rồi hy vọng scheduler chạy đúng lúc.

**Lưu ý:**
Đừng tạo abstraction `IClock` riêng theo thói quen nếu `TimeProvider` đã đáp ứng nhu cầu. Với database timestamp hoặc distributed workflow, vẫn phải xác định authoritative clock và tolerance cho clock skew; injectable clock không giải quyết consistency giữa nhiều máy.

### Tip 2 — Kiểm tra connection pool exhaustion từ thời gian giữ connection, không chỉ pool size

**Mẹo:**
Khi ASP.NET Core bắt đầu timeout với database, đo concurrent requests, thời gian query/transaction và thời gian connection bị giữ trước khi tăng `Max Pool Size`.

**Tại sao hữu ích:**
Pool exhaustion thường là triệu chứng: query chậm, transaction quá dài, connection không được dispose đúng hoặc traffic vượt database capacity. Tăng pool chỉ cho phép nhiều work dồn vào database hơn và có thể chuyển bottleneck thành CPU/locking ở SQL Server.

**Ví dụ:**
Sau deployment, p95 SQL tăng từ 80 ms lên 4 s và API xuất hiện timeout khi lấy connection. Chuỗi chẩn đoán hợp lý là request telemetry → dependency duration → active DB sessions/locks → execution plan, thay vì lập tức tăng pool từ 100 lên 500.

**Lưu ý:**
Pool size vẫn là tuning parameter hợp lệ khi workload và database capacity chứng minh cần concurrency cao hơn. Nhưng phải đo cả throughput và saturation; một pool lớn không tạo thêm database capacity.

### Tip 3 — Elasticsearch mapping sai nên được sửa bằng index mới + reindex, không vá dữ liệu tại chỗ

**Mẹo:**
Với thay đổi mapping không tương thích như `keyword` → analyzed `text` hoặc thay analyzer, tạo index version mới, reindex dữ liệu, validate rồi chuyển alias thay vì cố mutate mapping hiện tại.

**Tại sao hữu ích:**
Inverted index được xây dựng lúc indexing; nhiều thay đổi analyzer/type không thể biến đổi dữ liệu đã index bằng một metadata update. Versioned index + alias tạo migration boundary và cho phép rollback routing nhanh hơn.

**Ví dụ:**
`products-v3` dùng analyzer mới cho autocomplete. Pipeline reindex từ primary source hoặc `products-v2`, chạy query parity/performance checks, sau đó atomically chuyển alias `products-read` sang v3.

**Lưu ý:**
Reindex trên dataset lớn tiêu tốn CPU/I/O và có race với writes đang diễn ra. Cần chiến lược đồng bộ delta/dual-write hoặc event replay phù hợp; Elasticsearch không nên trở thành source of truth chỉ vì reindex tiện.

### Tip 4 — Dùng correlation context để nối request với background message

**Mẹo:**
Khi HTTP request tạo message cho background processing, propagate correlation/trace context vào message metadata và tạo child activity khi consumer xử lý.

**Tại sao hữu ích:**
Nếu chỉ log `OrderId`, incident xuyên nhiều service vẫn khó dựng timeline. Distributed tracing cho phép thấy HTTP ingress → database dependency → publish → consumer → external API, giúp phân biệt latency nằm ở request path hay asynchronous processing.

**Ví dụ:**
Checkout trả `202 Accepted`, nhưng fulfillment chậm 12 phút. Trace/message telemetry cho thấy publish diễn ra ngay, queue wait chỉ 2 giây nhưng consumer dành 11 phút retry Shipping API. Evidence chuyển investigation khỏi ASP.NET Core sang đúng dependency.

**Lưu ý:**
Không nhét PII hoặc token vào baggage/log scope. Correlation ID tự tạo không thay thế chuẩn trace context; đồng thời sampling có thể khiến một số trace không tồn tại, nên metrics và structured logs vẫn cần thiết.

### Tip 5 — AI-generated migration phải được kiểm tra trên schema thật và dữ liệu representative

**Mẹo:**
Khi dùng AI coding agent tạo EF Core/SQL migration, bắt agent grounding vào entity configuration, migration history và database constraints hiện tại; sau đó review generated SQL và chạy migration trên bản dữ liệu representative trước production.

**Tại sao hữu ích:**
Migration có thể compile nhưng vẫn gây table scan, long lock, data truncation hoặc phá backward compatibility giữa app version cũ và mới. AI thường suy luận schema từ code hiện tại nhưng bỏ qua historical data shape và deployment overlap.

**Ví dụ:**
Agent đề xuất đổi cột nullable thành `NOT NULL` ngay. Database thật còn hàng triệu row `NULL`; safe rollout có thể cần add/backfill theo batch, verify, rồi enforce constraint ở deployment sau.

**Lưu ý:**
Generated unit test không đủ để chứng minh migration an toàn. Cần kiểm tra lock duration, rollback/forward-fix strategy, application compatibility và execution trên database engine/version tương ứng.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency bảo vệ lost update mà không giữ lock dài

**Khái niệm:**
Optimistic Concurrency cho phép nhiều actor đọc cùng state nhưng yêu cầu write chứng minh state chưa đổi kể từ lúc đọc, thường bằng `rowversion`, version number hoặc concurrency token.

**Vấn đề nó giải quyết:**
Hai user cùng mở một order, A đổi địa chỉ và B đổi trạng thái dựa trên cùng version. Nếu mỗi update ghi đè state hiện tại mà không kiểm tra version, thay đổi của A hoặc B có thể bị mất âm thầm.

**Ví dụ thực tế:**
EF Core map `rowversion` cho `Order`. `UPDATE` bao gồm cả `Id` và version cũ trong predicate. Nếu affected rows = 0, application nhận concurrency conflict và có thể reload, merge hoặc yêu cầu user xác nhận thay vì silently overwrite.

**Trade-off:**
Không giữ lock lâu nên phù hợp khi conflict hiếm, nhưng conflict handling chuyển complexity lên application. Với contention cực cao hoặc invariant cần serialize chặt, retry optimistic liên tục có thể tệ hơn locking/atomic database operation.

**Middle → Senior insight:**
Middle developer cần xử lý `DbUpdateConcurrencyException` đúng và không biến conflict thành generic 500. Senior / Technical developer phải xác định aggregate/invariant nào cần concurrency boundary, chọn merge/reject/retry semantics và cân nhắc atomic SQL hoặc pessimistic control khi contention profile thay đổi.

### Design 2 — Azure Functions và Worker Service khác nhau ở operational model, không chỉ cách viết code

**Khái niệm:**
Azure Functions cung cấp trigger-driven serverless execution và platform-managed scaling; Worker Service là long-running process do team kiểm soát lifecycle, hosting và scaling rõ hơn. Cả hai đều có thể xử lý background work nhưng operational contract khác nhau.

**Vấn đề nó giải quyết:**
Team cần chọn runtime phù hợp cho workload: event-driven bursty jobs có thể hưởng lợi từ Functions; workload liên tục, cần process-level control hoặc predictable resource model có thể phù hợp Worker Service hơn.

**Ví dụ thực tế:**
Một Blob-created thumbnail job chạy thất thường theo upload traffic có thể dùng Function trigger. Một pricing engine giữ warm in-memory model, chạy liên tục và cần controlled concurrency có thể dễ vận hành hơn trong Worker Service/container.

**Trade-off:**
Functions giảm hosting boilerplate và scale thuận tiện nhưng có cold-start/execution/trigger semantics và platform coupling cần hiểu. Worker Service cho control lớn hơn nhưng team chịu trách nhiệm deployment, scaling, health, resource sizing và availability nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu cancellation, retries, poison handling và idempotency ở cả hai model. Senior / Technical developer phải chọn theo workload shape, latency SLO, scaling behavior, state/resource needs, cost và operational maturity thay vì mặc định “background job = Function”.

### Design 3 — Anti-Corruption Layer bảo vệ domain khỏi model của hệ thống bên ngoài

**Khái niệm:**
Anti-Corruption Layer (ACL) là boundary dịch contract và semantics của external/legacy system sang model mà domain nội bộ hiểu, thay vì để DTO, status code và naming bên ngoài lan xuyên application.

**Vấn đề nó giải quyết:**
Third-party API thường có lifecycle và semantics khác domain nội bộ. Nếu business code trực tiếp phụ thuộc `vendor_status = 7`, payload shape hoặc exception của SDK, thay provider hoặc nâng version sẽ kéo thay đổi qua nhiều layer.

**Ví dụ thực tế:**
Shipping provider trả `status: "IN_TRANSIT_X"`. Adapter chuyển nó thành internal `ShipmentState.InTransit` và map vendor errors sang result taxonomy của application. Domain không biết provider dùng REST, SDK hay mã trạng thái nào.

**Trade-off:**
ACL thêm mapping code và có nguy cơ che mất capability quan trọng nếu abstraction quá chung. Với integration nhỏ, stable và không đi vào core domain, một adapter mỏng có thể đủ; xây một canonical model khổng lồ cho mọi provider dễ trở thành lowest-common-denominator architecture.

**Middle → Senior insight:**
Middle developer cần giữ vendor DTO/SDK ở integration boundary và test mapping. Senior / Technical developer phải xác định semantics nào thuộc domain, semantics nào nên giữ provider-specific, thiết kế failure taxonomy và quyết định mức abstraction dựa trên volatility/criticality thay vì cố “provider-agnostic” tuyệt đối.
