# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — TimeProvider cho logic phụ thuộc thời gian

**Mẹo:**
Inject TimeProvider vào code có business rule phụ thuộc thời gian thay vì gọi DateTime.UtcNow rải rác. Trong test, dùng controllable time để dịch chuyển clock deterministic.

**Tại sao hữu ích:**
Clock là external dependency. Nếu code đọc system time trực tiếp, test expiry, timeout window hoặc scheduled behavior dễ flaky và phải chờ thời gian thật.

**Ví dụ:**
Service quyết định Order reservation hết hạn sau 15 phút bằng GetUtcNow(). Test đặt clock cố định, advance 16 phút rồi xác nhận trạng thái expired mà không sleep.

**Lưu ý:**
Phân biệt wall-clock time với elapsed duration; đo duration nên dùng monotonic timestamp semantics khi cần.

### Tip 2 — PostgreSQL partial index theo hot subset

**Mẹo:**
Nếu query thường xuyên truy cập một subset nhỏ và ổn định, cân nhắc partial index thay vì index toàn bảng.

**Tại sao hữu ích:**
Index nhỏ hơn cần ít storage, cache footprint và maintenance. Khi phần lớn rows là historical nhưng production chủ yếu đọc active rows, partial index tập trung tài nguyên vào hot set.

**Ví dụ:**
Jobs table có hàng triệu completed rows nhưng worker chỉ query status pending theo created_at. Tạo candidate partial index cho pending rows rồi xác nhận bằng EXPLAIN (ANALYZE, BUFFERS).

**Lưu ý:**
Optimizer chỉ dùng partial index khi query predicate phù hợp. Luôn đo write overhead và execution plan thực tế.

### Tip 3 — Azure Service Bus sessions cho ordering có scope

**Mẹo:**
Khi business yêu cầu xử lý tuần tự theo một entity/workflow, cân nhắc Service Bus sessions với SessionId đại diện ordering scope thay vì global ordering.

**Tại sao hữu ích:**
Global ordering giảm concurrency mạnh. Session cho phép messages của cùng Order được xử lý tuần tự trong khi orders khác vẫn chạy song song.

**Ví dụ:**
OrderCreated, PaymentConfirmed và OrderCancelled của cùng Order dùng SessionId = OrderId; consumer giữ thứ tự trong session nhưng xử lý nhiều orders đồng thời.

**Lưu ý:**
Ordering không sửa duplicate delivery và không thay idempotency. Session quá nóng cũng thành bottleneck.

### Tip 4 — DevTools Coverage chỉ là tín hiệu điều tra bundle

**Mẹo:**
Khi frontend tải JavaScript lớn, dùng DevTools Coverage và network waterfall để tìm code không dùng trong critical flow, rồi xác minh bằng bundle analyzer trước khi split/remove dependency.

**Tại sao hữu ích:**
Bundle lớn tăng transfer, parse và execution cost. Nhưng unused bytes trong một capture không chứng minh code vô dụng ở mọi route.

**Ví dụ:**
Landing page tải charting library dù chart chỉ ở admin route. Route-level lazy loading hoặc dynamic import có thể đưa dependency khỏi initial bundle.

**Lưu ý:**
Đừng chia bundle thành quá nhiều chunks theo cảm tính. Đo Core Web Vitals và real-user telemetry sau thay đổi.

### Tip 5 — Integration test database cho behavior mock không chứng minh được

**Mẹo:**
Dùng database thật hoặc production-compatible test container cho behavior phụ thuộc SQL translation, constraint, transaction hoặc isolation thay vì mock data access.

**Tại sao hữu ích:**
Mock không chứng minh LINQ translate được, unique constraint hoạt động, collation đúng hay concurrent transaction tạo behavior mong đợi.

**Ví dụ:**
Test duplicate external reference chạy schema thật, insert hai records cạnh tranh và xác nhận database invariant cùng error mapping của application.

**Lưu ý:**
Không biến mọi test thành integration test. Pure domain logic vẫn nên test nhanh ở unit level.

## 🧠 Software Design

### Design 1 — Anti-Corruption Layer bảo vệ domain

**Khái niệm:**
Anti-Corruption Layer chuyển external/legacy model sang model có semantics phù hợp với domain nội bộ thay vì để vendor DTO lan xuyên application.

**Vấn đề nó giải quyết:**
Hai hệ thống có thể dùng cùng một tên như Customer nhưng mang semantics khác nhau; dùng chung model tạo coupling và business rule sai lệch.

**Ví dụ thực tế:**
Adapter nhận ERP AccountRecord, map thành internal BillingParty và chỉ expose capability Ordering cần. Khi ERP đổi contract, thay đổi tập trung ở integration boundary.

**Trade-off:**
ACL thêm mapping code và types. Với integration nhỏ, stable và semantics gần giống nhau, abstraction dày có thể không đáng.

**Middle → Senior insight:**
Middle developer cần tránh đưa vendor DTO trực tiếp vào domain. Senior / Technical developer phải đánh giá semantic mismatch, ownership và volatility để chọn độ dày của ACL.

### Design 2 — Saga choreography và orchestration

**Khái niệm:**
Saga chia distributed workflow thành local transactions và compensating actions. Choreography để services phản ứng với events; orchestration có coordinator điều khiển sequence và workflow state.

**Vấn đề nó giải quyết:**
Order, payment và inventory ở các services khác nhau không thể dựa vào một SQL transaction chung; failure giữa các bước cần recovery semantics.

**Ví dụ thực tế:**
Checkout reserve inventory rồi charge payment. Nếu payment fail, workflow release reservation. Orchestrator có thể giữ state và phát commands; choreography dùng events giữa participants.

**Trade-off:**
Choreography giảm central coordinator nhưng flow khó quan sát khi nhiều participants. Orchestration explicit hơn nhưng thêm coordinator/state machine phải vận hành.

**Middle → Senior insight:**
Middle developer cần hiểu local transaction, idempotency và compensation. Senior / Technical developer phải chọn coordination style theo complexity, ownership, observability và recovery.

### Design 3 — ADR lưu rationale và trade-off

**Khái niệm:**
Architecture Decision Record ghi context, options, decision và consequences để người đến sau hiểu vì sao hệ thống được thiết kế như hiện tại.

**Vấn đề nó giải quyết:**
Code cho thấy cái gì nhưng không luôn cho thấy vì sao. Team có thể lặp lại tranh luận hoặc phá constraint vì mất context ban đầu.

**Ví dụ thực tế:**
ADR cho quyết định giữ Modular Monolith ghi team size, deployment cadence, transaction needs, scaling evidence và trigger conditions để xem xét lại sau này.

**Trade-off:**
ADR tạo institutional memory nhưng có thể thành documentation graveyard nếu mọi thay đổi nhỏ đều tạo record hoặc record không được supersede.

**Middle → Senior insight:**
Middle developer cần đọc ADR trước thay đổi boundary lớn. Senior / Technical developer phải ghi assumptions, rejected alternatives và review trigger để hỗ trợ evolutionary architecture.
