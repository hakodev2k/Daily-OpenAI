# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống connection pooling

**Mẹo:**
Phân biệt `AddDbContextPool` với database connection pooling. `DbContext` pooling tái sử dụng instance/context infrastructure; connection pooling thuộc database provider và tái sử dụng physical connections. Chỉ bật context pooling khi đã đo thấy allocation/setup của `DbContext` đáng kể và context không giữ state theo request một cách nguy hiểm.

**Tại sao hữu ích:**
Một API chậm vì connection pool exhaustion sẽ không được sửa bằng `AddDbContextPool`. Ngược lại, context pooling có thể giảm allocation ở high-throughput workload, nhưng pooled context được reset và tái sử dụng nên state tùy biến gắn với tenant/request cần được quản lý rất cẩn thận.

**Ví dụ:**
Nếu telemetry cho thấy request chờ lâu khi `OpenAsync` và số connection active chạm pool limit, hãy điều tra query duration, transaction lifetime và concurrency. Đừng đổi sang `AddDbContextPool` rồi kỳ vọng database connections tăng.

**Lưu ý:**
Không cache `DbContext` hoặc dùng nó đồng thời giữa threads. Với multi-tenant filter/state được set thủ công trên context, phải xác minh lifecycle/reset semantics trước khi pooling; optimization nhỏ không đáng đổi lấy data-isolation bug.

### Tip 2 — MongoDB document nên được thiết kế theo atomic boundary và access pattern

**Mẹo:**
Embed dữ liệu khi nó thường được đọc/cập nhật cùng aggregate và có bounded growth; reference khi lifecycle độc lập, cardinality lớn hoặc duplication/update fan-out trở thành vấn đề.

**Tại sao hữu ích:**
MongoDB cho atomicity mạnh trong một document, nên document boundary ảnh hưởng trực tiếp tới consistency và số round trip. Mô phỏng relational schema bằng collection cho mọi entity có thể tạo application-side joins; ngược lại nhét unbounded history vào một document làm document phình lớn và update ngày càng tốn kém.

**Ví dụ:**
`Order` có thể embed snapshot của shipping address và line items vì chúng thuộc transaction/history của order. Nhưng toàn bộ `ProductReviews` tăng vô hạn không nên trở thành một array bên trong Product chỉ để “đọc một document”.

**Lưu ý:**
Denormalization là trade-off, không phải mục tiêu. Trước khi model, liệt kê query/update patterns, growth rate, consistency requirement và index cần thiết; đừng chọn embed/reference chỉ dựa trên quan hệ 1-N trên sơ đồ dữ liệu.

### Tip 3 — Test database behavior bằng database thật thay vì mock `IQueryable`

**Mẹo:**
Với code phụ thuộc EF Core query translation, transaction, constraint hoặc concurrency, ưu tiên integration test với database engine thật tương ứng production thay vì mock `DbSet`/`IQueryable`.

**Tại sao hữu ích:**
Mock LINQ thường chạy LINQ-to-Objects nên không kiểm tra SQL translation, collation, null semantics, indexes, constraints hay transaction behavior. Test xanh có thể che query mà provider thật không translate hoặc semantics khác production.

**Ví dụ:**
Một repository dùng expression phức tạp và PostgreSQL-specific behavior nên được test bằng PostgreSQL test instance/container với schema thật. Unit test vẫn phù hợp cho pure domain logic không cần database semantics.

**Lưu ý:**
Integration test cần isolation và deterministic data. Không dùng chung mutable database state giữa tests rồi chữa flaky test bằng retry. Đồng thời đừng biến mọi test thành E2E; giữ test pyramid theo loại risk cần bắt.

### Tip 4 — `Cache-Control` sai có thể biến CDN thành nguồn phát dữ liệu cũ

**Mẹo:**
Khi API/page đi qua CDN hoặc reverse proxy, thiết kế `Cache-Control`, cache key và invalidation cùng nhau. Phân biệt browser cache với shared cache và chỉ đánh dấu response cacheable khi dữ liệu thực sự cho phép chia sẻ.

**Tại sao hữu ích:**
Một response có TTL dài có thể tiếp tục được CDN phục vụ sau deployment hoặc content update. Nếu cache key bỏ sót locale, tenant hay query parameter quan trọng, cache còn có thể trả đúng response của context khác dù origin hoàn toàn chính xác.

**Ví dụ:**
CMS public article có thể dùng shared caching và purge khi publish. Endpoint `/api/profile` chứa dữ liệu user-specific không được cache như public asset chỉ vì muốn giảm backend latency.

**Lưu ý:**
Đừng dùng cache purge như giải pháp duy nhất cho thiết kế cache key sai. Với authenticated/personalized content, xem kỹ `private`, `no-store`, `Vary` và behavior thực tế của CDN đang dùng; cấu hình edge có thể khác browser semantics.

### Tip 5 — Dùng heap evidence trước khi kết luận .NET có memory leak

**Mẹo:**
Khi memory tăng, phân biệt managed heap, native memory, working set và expected cache growth. Thu metrics/GC counters theo thời gian rồi dùng dump/heap analysis để tìm type/root giữ object sống lâu bất thường.

**Tại sao hữu ích:**
GC chỉ thu object không còn reachable; “GC không trả RAM ngay” không tự động là leak. Static collections, event subscriptions, unbounded caches hoặc queued work có thể giữ object reachable, trong khi native buffers hoặc container accounting lại nằm ngoài managed heap.

**Ví dụ:**
Nếu Gen 2 heap tăng sau mỗi traffic cycle và dump cho thấy hàng triệu `SessionSnapshot` được root bởi một static dictionary không có eviction, evidence chỉ ra retention bug. Nếu managed heap ổn nhưng working set tăng, hướng điều tra phải mở rộng sang native allocations/buffers.

**Lưu ý:**
Đừng gọi `GC.Collect()` định kỳ để “sửa leak”; object còn root vẫn không được thu và forced GC có thể làm latency xấu hơn. Dump production cần cân nhắc kích thước, pause/cost và dữ liệu nhạy cảm trong memory.

## 🧠 Software Design

### Design 1 — Optimistic concurrency bảo vệ lost update mà không khóa record suốt user workflow

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor đọc cùng state nhưng yêu cầu update xác nhận version/concurrency token chưa đổi. Nếu token khác, operation thất bại có chủ đích để application retry, merge hoặc yêu cầu user giải quyết conflict.

**Vấn đề nó giải quyết:**
Hai nhân viên mở cùng customer record, người A cập nhật email rồi người B lưu màn hình cũ và vô tình ghi đè thay đổi của A. Giữ database lock từ lúc mở form tới lúc user bấm Save là không thực tế và làm giảm concurrency.

**Ví dụ thực tế:**
EF Core map SQL Server `rowversion` làm concurrency token. `UPDATE` chứa cả primary key và version cũ; nếu affected rows bằng 0, application nhận concurrency conflict thay vì silently overwriting newer state.

**Trade-off:**
Optimistic concurrency phù hợp khi conflict tương đối hiếm, nhưng application phải có conflict UX/retry semantics. Blind retry có thể vẫn ghi đè business intent. Với hot resource có contention cực cao, serialization/pessimistic strategy hoặc redesign workflow đôi khi hợp lý hơn.

**Middle → Senior insight:**
Middle developer cần cấu hình token, bắt concurrency exception và không biến conflict thành generic 500. Senior / Technical developer phải xác định invariant nào cần bảo vệ, conflict có thể auto-merge hay không, API contract nên expose version thế nào và khi nào contention đủ cao để đổi concurrency strategy.

### Design 2 — Queue và Topic giải quyết hai kiểu ownership khác nhau

**Khái niệm:**
Queue thường biểu diễn work mà một consumer trong nhóm cạnh tranh xử lý; Topic + subscriptions biểu diễn event cần được nhiều consumer groups nhận độc lập. Cả hai có thể dùng broker nhưng semantics ownership khác nhau.

**Vấn đề nó giải quyết:**
Nếu `GenerateInvoice` chỉ cần một worker thực thi, broadcast tới nhiều subscriber tạo duplicate work. Ngược lại, `OrderPlaced` có thể cần Billing, Analytics và Notification cùng phản ứng; đặt tất cả vào một competing-consumer queue khiến chỉ một capability nhìn thấy event.

**Ví dụ thực tế:**
Azure Service Bus queue `invoice-jobs` có nhiều worker để scale throughput. Topic `order-events` có subscription riêng cho fulfillment, analytics và email; mỗi subscription có retry/DLQ độc lập.

**Trade-off:**
Topic tăng fan-out, số subscription, monitoring và schema-evolution responsibility. Queue đơn giản hơn nhưng không phù hợp khi nhiều business capabilities cần cùng event. Đừng dùng broker topology để che boundary mơ hồ giữa command và event.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumers, duplicate delivery, DLQ và idempotency. Senior / Technical developer phải phân biệt command ownership với event publication, thiết kế subscription/filter, ordering và failure isolation, đồng thời cân nhắc liệu synchronous call đơn giản hơn có đáp ứng yêu cầu hay không.

### Design 3 — Clean Architecture chỉ có giá trị khi dependency boundary phản ánh change pressure

**Khái niệm:**
Clean Architecture giữ business policy ít phụ thuộc vào delivery/infrastructure details thông qua dependency direction và explicit boundaries. Giá trị nằm ở khả năng cô lập thay đổi và test policy, không nằm ở số project hay việc tạo interface cho mọi class.

**Vấn đề nó giải quyết:**
Business rule quan trọng bị trộn với EF Core, HTTP DTO và vendor SDK khiến thay đổi persistence/integration kéo theo domain logic và test phải dựng nhiều infrastructure. Tuy nhiên CRUD application nhỏ có thể không có đủ change pressure để biện minh cho nhiều layer.

**Ví dụ thực tế:**
Pricing policy có business rules phức tạp nên domain/application layer không cần biết controller hoặc payment SDK cụ thể. Nhưng endpoint admin chỉ CRUD một lookup table có thể dùng vertical slice đơn giản thay vì ép qua repository, service, mapper và mediator chỉ để đúng sơ đồ.

**Trade-off:**
Boundary tốt giảm coupling nhưng mỗi abstraction có navigation/cognitive cost. Quá nhiều interfaces, DTO mappings và indirection làm feature đơn giản khó theo dõi; quá ít boundary lại khiến infrastructure concerns lan vào core policy.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và tránh để infrastructure detail xâm nhập business rule quan trọng. Senior / Technical developer phải nhận diện axis of change, chọn boundary có lợi ích thực tế, cho phép shortcut có kiểm soát ở low-risk CRUD và đánh giá architecture bằng maintainability/evolution cost thay vì độ “đúng pattern”.
