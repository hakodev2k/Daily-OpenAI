# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — `IAsyncEnumerable<T>` giúp streaming kết quả nhưng DbContext phải sống đủ lâu

**Mẹo:**
Dùng `IAsyncEnumerable<T>` khi endpoint có thể xử lý hoặc truyền từng phần dữ liệu thay vì materialize toàn bộ bằng `ToListAsync()`, nhưng phải giữ lifetime của `DbContext` và database reader cho đến khi enumeration hoàn tất.

**Tại sao hữu ích:**
Streaming giảm peak memory và cho phép bắt đầu xử lý dữ liệu sớm hơn. Tuy nhiên LINQ query chưa thực thi khi chỉ tạo `IAsyncEnumerable<T>`; database connection thường vẫn được giữ trong lúc consumer đang enumerate.

**Ví dụ:**
```csharp
await foreach (var row in db.AuditLogs
    .AsNoTracking()
    .OrderBy(x => x.Id)
    .AsAsyncEnumerable()
    .WithCancellation(ct))
{
    await writer.WriteAsync(row, ct);
}
```
Với export lớn, cách này tránh giữ hàng trăm nghìn rows trong một `List<T>`.

**Lưu ý:**
Đừng stream một query rồi thực hiện network call chậm cho từng row trong cùng vòng lặp: connection có thể bị giữ rất lâu và làm cạn pool. Nếu downstream chậm, cân nhắc paging/batching hoặc tách database read khỏi external I/O.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` khi dữ liệu lớn và liên tục thay đổi

**Mẹo:**
Với API list lớn, ưu tiên keyset/cursor pagination dựa trên một ordering ổn định thay vì `OFFSET ... FETCH` ở các trang sâu.

**Tại sao hữu ích:**
`OFFSET` buộc database bỏ qua ngày càng nhiều rows trước khi lấy page tiếp theo và dữ liệu insert/delete giữa hai request có thể làm record bị lặp hoặc bị bỏ sót. Keyset tiếp tục từ key cuối đã thấy nên thường có cost ổn định hơn.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Composite index theo ordering/filter phù hợp giúp query seek từ cursor thay vì scan qua hàng trăm nghìn rows.

**Lưu ý:**
Ordering phải deterministic; `CreatedAt` một mình có thể trùng nên cần tie-breaker như `Id`. Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới “trang 137” hoặc cần total-page semantics chính xác.

### Tip 3 — Kubernetes `readinessProbe` và `livenessProbe` không nên kiểm tra cùng một thứ

**Mẹo:**
Thiết kế readiness để quyết định pod có nhận traffic hay không; liveness chỉ nên phát hiện trạng thái process thực sự không thể tự phục hồi và cần restart.

**Tại sao hữu ích:**
Nếu liveness gọi database hoặc external API, một dependency outage có thể khiến toàn bộ pods bị restart đồng loạt dù application process vẫn khỏe. Readiness có thể tạm rút pod khỏi traffic, còn restart không sửa được database đang down.

**Ví dụ:**
ASP.NET Core app có `/health/ready` kiểm tra các điều kiện cần để phục vụ request và `/health/live` chỉ xác nhận process/event loop cơ bản còn hoạt động. Khi SQL tạm thời unavailable, readiness có thể fail theo policy nhưng liveness vẫn pass.

**Lưu ý:**
Readiness cũng không nên phụ thuộc mù quáng vào mọi downstream service; nếu application vẫn có thể degraded-mode thì đánh dấu toàn pod unready có thể làm outage lớn hơn. Probe phải phản ánh khả năng phục vụ thực tế của workload.

### Tip 4 — Vue component nên hủy request cũ khi user thay đổi search nhanh

**Mẹo:**
Với autocomplete/filter UI, dùng `AbortController` hoặc cơ chế cancellation tương đương để hủy request cũ khi query mới supersede query trước.

**Tại sao hữu ích:**
Nếu user gõ `lap` rồi `laptop`, request `lap` có thể hoàn thành sau request `laptop` và ghi đè state bằng dữ liệu cũ. Đây là race condition phía client, không phải chỉ là vấn đề debounce.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  });

  results.value = await response.json();
}
```
Debounce có thể giảm số request; cancellation bảo vệ correctness khi request đã được gửi.

**Lưu ý:**
Abort phía browser không đảm bảo backend đã dừng công việc. ASP.NET Core endpoint vẫn phải propagate `RequestAborted` xuống EF Core/outbound calls nếu muốn giải phóng resource sớm.

### Tip 5 — AI-generated test phải được review xem đang kiểm tra behavior hay chỉ mirror implementation

**Mẹo:**
Khi coding agent sinh unit tests, kiểm tra assertion có mô tả observable behavior/business rule hay chỉ lặp lại cấu trúc code hiện tại bằng mock interactions chi tiết.

**Tại sao hữu ích:**
AI dễ đọc implementation rồi tạo test “khóa” chính implementation đó: verify từng internal method call, số lần gọi hoặc private flow. Test vẫn xanh nhưng refactor hợp lệ trở nên khó, trong khi bug business có thể không được phát hiện.

**Ví dụ:**
Thay vì chỉ `Verify(repo => repo.Save(...), Times.Once)`, test checkout nên xác minh outcome như order state, emitted integration intent hoặc error contract với các boundary quan trọng. Sau đó mutation/refactor nhỏ có thể kiểm tra test có thật sự bắt behavior sai hay không.

**Lưu ý:**
Interaction verification vẫn hữu ích khi interaction chính là contract, ví dụ không được charge payment hai lần. Không loại bỏ mocks máy móc; hãy phân biệt implementation detail với externally meaningful collaboration.

## 🧠 Software Design

### Design 1 — Optimistic concurrency bảo vệ business state khỏi lost update

**Khái niệm:**
Optimistic concurrency cho phép nhiều request đọc cùng state nhưng yêu cầu update chỉ thành công nếu version/token vẫn giống lúc đọc. Nó phù hợp khi conflict có thể xảy ra nhưng không đủ thường xuyên để khóa pessimistic từ đầu.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng mở một order ở trạng thái `Pending`. Người A chuyển thành `Approved`; người B dựa trên snapshot cũ chuyển thành `Cancelled`. Nếu update cuối cùng ghi đè im lặng, hệ thống mất một quyết định nghiệp vụ mà không có dấu hiệu lỗi.

**Ví dụ thực tế:**
SQL Server dùng `rowversion`, EF Core cấu hình concurrency token. `UPDATE` bao gồm cả `Id` và version cũ; nếu affected rows bằng 0, application nhận concurrency conflict và quyết định reload, merge hoặc trả HTTP 409 tùy semantics.

**Trade-off:**
Không giữ lock dài nên throughput tốt trong workload conflict thấp, nhưng application phải định nghĩa cách xử lý conflict. Auto-retry mù quáng có thể ghi đè quyết định của user; pessimistic locking phù hợp hơn cho một số critical section ngắn với contention đặc thù.

**Middle → Senior insight:**
Middle developer cần cấu hình token và xử lý `DbUpdateConcurrencyException` đúng. Senior / Technical developer phải xác định conflict nào có thể retry, conflict nào cần user/business resolution, boundary transaction và liệu optimistic hay pessimistic concurrency phù hợp với contention thực tế.

### Design 2 — Backend-for-Frontend đáng dùng khi client có nhu cầu orchestration khác nhau

**Khái niệm:**
Backend-for-Frontend (BFF) tạo backend boundary theo loại client để gom orchestration, authentication/session handling hoặc response shaping đặc thù thay vì ép web, mobile và các client khác dùng cùng một API facade cho mọi nhu cầu.

**Vấn đề nó giải quyết:**
Mobile cần payload nhỏ và ít round trips; web cần composition dữ liệu khác; server-rendered frontend có thể cần giữ token ở server. Một generic gateway chứa hàng loạt điều kiện theo client dễ trở thành coupling point khó tiến hóa.

**Ví dụ thực tế:**
Web BFF gọi Catalog, Pricing và Recommendation rồi trả view model phù hợp cho trang sản phẩm; mobile BFF trả representation gọn hơn và workflow riêng. Domain services phía sau vẫn giữ business ownership thay vì đẩy logic domain vào BFF.

**Trade-off:**
BFF giảm client orchestration và cho phép evolution độc lập nhưng tăng số deployable components, duplicated plumbing và operational ownership. Với một client đơn giản, một API bình thường có thể tốt hơn nhiều.

**Middle → Senior insight:**
Middle developer cần giữ BFF tập trung vào client-specific composition, không biến nó thành domain service mới. Senior / Technical developer phải cân nhắc số client, team ownership, security model, latency, duplication và deployment cost trước khi thêm boundary này.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo state cần quản trị

**Khái niệm:**
Feature Flag cho phép code được deploy trước nhưng chỉ kích hoạt capability theo environment, cohort hoặc điều kiện cụ thể. Deployment trở thành việc đưa artifact lên production; release là quyết định cho user sử dụng behavior mới.

**Vấn đề nó giải quyết:**
Một checkout flow lớn cần rollout dần, quan sát metrics và rollback nhanh mà không redeploy. Flag cho phép bật 1% traffic, internal users hoặc một tenant trước khi mở rộng.

**Ví dụ thực tế:**
`NewCheckout` được deploy cùng code cũ. Traffic routing dựa trên stable user/tenant key; telemetry tách success rate và latency giữa control/treatment. Nếu error rate tăng, team tắt flag trong khi điều tra thay vì rollback toàn release chứa các thay đổi không liên quan.

**Trade-off:**
Flags tạo nhiều runtime states, tăng test matrix và có thể để lại dead code. Flag system cũng trở thành operational dependency; permission/audit cho flag quan trọng phải được quản lý như production change.

**Middle → Senior insight:**
Middle developer cần implement default/fallback rõ ràng và test cả hai nhánh quan trọng. Senior / Technical developer phải thiết kế rollout metric, ownership, expiration/removal policy, dependency giữa flags và failure behavior để feature flags giảm release risk thay vì trở thành permanent configuration debt.
