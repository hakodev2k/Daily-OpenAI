# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate `Options` ngay khi startup thay vì đợi request đầu tiên mới vỡ

**Mẹo:**
Với cấu hình quan trọng trong ASP.NET Core, dùng `Validate`, `ValidateDataAnnotations` và `ValidateOnStart` để phát hiện config sai ngay lúc application khởi động.

**Tại sao hữu ích:**
Nếu secret, endpoint hoặc timeout bị thiếu nhưng validation chỉ xảy ra khi service lần đầu được resolve, deployment có thể báo healthy rồi mới fail khi traffic thật đi vào. Fail-fast giúp lỗi cấu hình xuất hiện trong startup log và rollback sớm hơn.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(x => Uri.TryCreate(x.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be absolute")
    .Validate(x => x.TimeoutSeconds is > 0 and <= 30,
        "TimeoutSeconds must be between 1 and 30")
    .ValidateOnStart();
```

Trong CI/CD, một deployment có config sai sẽ fail startup thay vì trở thành lỗi runtime ngẫu nhiên.

**Lưu ý:**
Không validate bằng cách gọi dependency thật như database hoặc third-party API trong `Options` validation. Validation nên kiểm tra shape/range/config semantics; dependency availability thuộc health checks và runtime resilience.

### Tip 2 — Khi gặp deadlock SQL Server, đọc deadlock graph trước khi tăng timeout

**Mẹo:**
Nếu production có lỗi deadlock, lấy deadlock graph từ Extended Events hoặc telemetry rồi xác định resource, lock mode và thứ tự truy cập của từng transaction.

**Tại sao hữu ích:**
Deadlock không phải đơn giản là “query chạy chậm”. Hai transaction đang giữ resource mà transaction kia cần. Tăng command timeout thường không giải quyết cycle; cần sửa lock order, transaction scope, query/index hoặc mức isolation phù hợp.

**Ví dụ:**
```text
Transaction A:
1. UPDATE Orders
2. UPDATE Inventory

Transaction B:
1. UPDATE Inventory
2. UPDATE Orders
```

Nếu cả hai cùng chạy, mỗi transaction có thể giữ một lock và chờ lock còn lại. Một giải pháp thường là chuẩn hóa thứ tự truy cập resource hoặc giảm transaction scope.

**Lưu ý:**
Đừng kết luận mọi deadlock đều do thiếu index. Index tốt có thể giảm thời gian giữ lock, nhưng root cause vẫn cần được xác nhận bằng deadlock graph và execution plan.

### Tip 3 — Upload file lớn trực tiếp lên Blob Storage khi backend không cần chạm vào bytes

**Mẹo:**
Nếu browser/mobile client cần upload file lớn và backend chỉ quản lý metadata/quyền truy cập, cân nhắc cấp SAS ngắn hạn để client upload trực tiếp tới Azure Blob Storage.

**Tại sao hữu ích:**
Proxy toàn bộ file qua ASP.NET Core làm application trả network cost hai lần, giữ connection lâu và tăng memory/IO pressure. Direct upload tách data plane khỏi API plane và giúp backend scale theo request metadata thay vì byte throughput.

**Ví dụ:**
```text
1. Client gọi POST /uploads/request
2. Backend authorize user + tạo blob name
3. Backend trả SAS chỉ có quyền Create/Write, TTL 10 phút
4. Client upload trực tiếp Blob Storage
5. Client/backend xác nhận completion và lưu metadata
```

Với workload nội bộ Azure, backend nên dùng Managed Identity để tạo quyền truy cập thay vì giữ Storage Account key lâu dài.

**Lưu ý:**
SAS phải có scope tối thiểu, thời hạn ngắn và blob path do server kiểm soát. Direct upload không thay thế file-size limit, malware scanning, content validation hoặc quy trình cleanup upload dang dở.

### Tip 4 — Dùng browser DevTools Network waterfall để tìm frontend chậm trước khi tối ưu JavaScript

**Mẹo:**
Khi một trang Vue/React tải chậm, mở Network panel và phân tách thời gian DNS/connect/TTFB/download, request chaining và bundle loading trước khi đổ lỗi cho rendering.

**Tại sao hữu ích:**
Một page có Largest Contentful Paint kém có thể do backend TTFB cao, ảnh hero quá lớn, request bị serialize theo waterfall hoặc JavaScript bundle tải muộn. CPU profiling không giúp nếu bottleneck thật nằm ở network dependency chain.

**Ví dụ:**
```text
HTML          450 ms TTFB
 -> app.js    900 KB
    -> /api/home 700 ms
       -> hero image 2.4 MB
```

Từ evidence này, ưu tiên có thể là SSR/data prefetch, bundle splitting hoặc image optimization thay vì micro-optimize component render.

**Lưu ý:**
Một lần đo local không đại diện production. Kiểm tra cache state, throttling, device class và telemetry thực tế như Core Web Vitals trước khi chốt optimization.

### Tip 5 — Dùng `dotnet-trace` khi CPU spike nhưng log không chỉ ra code path nóng

**Mẹo:**
Khi .NET process có CPU cao kéo dài, capture trace ngắn bằng `dotnet-trace` rồi phân tích call stack/hot methods thay vì thêm logging bừa vào nhiều chỗ.

**Tại sao hữu ích:**
CPU spike thường đến từ tight loop, serialization, regex, contention hoặc workload tăng. Trace cung cấp evidence về nơi CPU thực sự tiêu tốn, giúp tách application code khỏi GC/runtime/dependency symptoms.

**Ví dụ:**
```bash
dotnet-trace collect --process-id 1234 --profile cpu-sampling
```

Sau đó mở trace trong PerfView hoặc công cụ hỗ trợ để xem call tree và hot stack trong khoảng incident.

**Lưu ý:**
Diagnostic tool vẫn tạo overhead. Capture trong khoảng thời gian ngắn, hiểu policy production của hệ thống và ưu tiên sampling profile trước khi bật event quá chi tiết.

## 🧠 Software Design

### Design 1 — Saga dùng compensating action khi một business transaction đi xuyên nhiều service

**Khái niệm:**
Saga chia workflow phân tán thành nhiều local transaction. Khi một bước sau thất bại, hệ thống thực hiện compensating action cho các bước trước thay vì cố giữ distributed transaction xuyên nhiều service.

**Vấn đề nó giải quyết:**
Trong workflow như Order → Payment → Inventory → Shipping, mỗi service sở hữu datastore riêng. Không thể dựa vào một ACID transaction đơn giản để rollback tất cả nếu một bước fail sau khi các bước trước đã commit.

**Ví dụ thực tế:**
```text
1. Create Order       -> success
2. Reserve Inventory  -> success
3. Charge Payment     -> fail

Compensation:
4. Release Inventory
5. Mark Order = PaymentFailed
```

Các command/event phải idempotent vì retry hoặc duplicate delivery có thể xảy ra trong từng bước.

**Trade-off:**
Saga tăng khả năng vận hành workflow phân tán mà không cần distributed lock/2PC, nhưng đổi lấy eventual consistency, state machine phức tạp hơn, compensation không phải lúc nào cũng hoàn nguyên được hoàn hảo và observability khó hơn.

**Middle → Senior insight:**
Middle developer cần hiểu mỗi bước phải có transaction boundary và idempotency rõ. Senior / Technical developer phải quyết định orchestration hay choreography, thiết kế compensation semantics, timeout, retry, manual recovery và trạng thái business có thể quan sát được trong suốt workflow.

### Design 2 — Hexagonal Architecture hữu ích nhất ở integration boundary, không phải để tạo thêm layer cho mọi class

**Khái niệm:**
Hexagonal Architecture giữ business logic phụ thuộc vào port/contract, còn database, CMS, payment provider hoặc message broker được triển khai dưới dạng adapter bên ngoài core.

**Vấn đề nó giải quyết:**
Enterprise application thường bị khóa chặt vào SDK hoặc data model của provider. Khi logic nghiệp vụ gọi trực tiếp Optimizely, Stripe hoặc Azure Service Bus API ở khắp nơi, thay đổi provider hoặc test business rule trở nên khó khăn.

**Ví dụ thực tế:**
```text
Application core:
IProductCatalog
- GetProductAsync(id)

Adapters:
- OptimizelyProductCatalogAdapter
- MockProductCatalogAdapter
- FutureCommercePlatformAdapter
```

Core làm việc với contract theo ngôn ngữ của ứng dụng thay vì leak type của vendor vào domain/application layer.

**Trade-off:**
Boundary rõ giúp testability và thay đổi integration dễ hơn, nhưng abstraction quá sớm có thể tạo interface chỉ mirror SDK mà không có giá trị. Với dependency ổn định và usage đơn giản, wrapper mỏng có thể chỉ tăng ceremony.

**Middle → Senior insight:**
Middle developer cần giữ vendor-specific concern khỏi business logic khi boundary đã được xác định. Senior / Technical developer phải biết abstraction nào bảo vệ system evolution thật sự và abstraction nào chỉ dự đoán tương lai không có evidence.

### Design 3 — Modernize legacy .NET theo Strangler pattern thay vì big-bang rewrite khi rủi ro vận hành cao

**Khái niệm:**
Strangler pattern thay dần capability của hệ thống legacy bằng implementation mới, route một phần traffic/use case sang hệ thống mới rồi thu hẹp legacy theo từng slice.

**Vấn đề nó giải quyết:**
Rewrite toàn bộ .NET Framework application sang modern .NET trong một release kéo theo rủi ro về hidden business rules, migration data, integration compatibility và thời gian dài không tạo giá trị production.

**Ví dụ thực tế:**
```text
Legacy ASP.NET MVC (.NET Framework)

Phase 1: đưa reverse proxy/gateway phía trước
Phase 2: tách Search sang ASP.NET Core .NET 10
Phase 3: tách Document API
Phase 4: migrate authentication/session boundary
Phase 5: retire phần legacy tương ứng
```

Mỗi slice cần telemetry và rollback path để so sánh behavior cũ/mới.

**Trade-off:**
Incremental migration giảm blast radius và cho phép học dần, nhưng trong thời gian chuyển đổi phải vận hành hai stack, quản lý routing, duplicated capability và integration boundary tạm thời. Big-bang đôi khi vẫn hợp lý nếu hệ thống nhỏ, ít dependency và test coverage mạnh.

**Middle → Senior insight:**
Middle developer cần đảm bảo feature parity, regression test và compatibility ở slice mình migrate. Senior / Technical developer phải chọn migration seam, sequence, data ownership, rollback strategy và tiêu chí retirement dựa trên business risk chứ không chỉ framework preference.
