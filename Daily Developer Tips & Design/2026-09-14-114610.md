# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong ASP.NET Core

**Mẹo:**
Khi API có latency tăng mạnh nhưng CPU chưa chắc đã 100%, kiểm tra ThreadPool starvation trước khi kết luận server “thiếu CPU”. Một dấu hiệu thường gặp là request bị giữ bởi synchronous blocking như `.Result`, `.Wait()`, `Thread.Sleep()` hoặc I/O sync trong code path vốn nên async.

**Tại sao hữu ích:**
ASP.NET Core xử lý nhiều request dựa trên ThreadPool. Nếu nhiều worker thread bị block trong lúc chờ database, HTTP hoặc lock, request mới phải đợi ThreadPool bổ sung thread. Hệ thống có thể xuất hiện latency cao, queue dài và throughput giảm dù CPU vẫn còn headroom.

**Ví dụ:**
```csharp
// Rủi ro: block worker thread trong request path
var customer = customerClient.GetCustomerAsync(id).Result;

// Tốt hơn: giải phóng thread trong lúc chờ I/O
var customer = await customerClient.GetCustomerAsync(id, ct);
```

Khi điều tra production, kết hợp runtime counters như ThreadPool queue length, active thread count, request rate, CPU và dependency latency thay vì chỉ nhìn một metric.

**Lưu ý:**
`async` không tự làm code nhanh hơn và cũng không chữa được CPU-bound workload. Nếu CPU thực sự bão hòa vì serialization, compression hoặc thuật toán nặng, thêm `await` không giải quyết root cause. Senior debugging cần phân biệt resource đang cạn là CPU, thread, connection, lock hay downstream capacity.

### Tip 2 — Với MongoDB, projection nhỏ vẫn cần index phù hợp để tránh scan lớn

**Mẹo:**
Đừng giả định chỉ lấy vài field bằng projection thì query sẽ rẻ. Hãy kiểm tra filter, sort và index cùng nhau bằng `explain()`; projection chỉ giảm lượng dữ liệu trả về, còn query vẫn có thể scan rất nhiều document nếu access path không tốt.

**Tại sao hữu ích:**
Một endpoint chỉ trả `Name` và `Status` có thể nhìn rất nhẹ ở application layer nhưng vẫn gây `COLLSCAN` trên hàng triệu document. Nếu index còn cover được cả filter/sort/projection, MongoDB đôi khi có thể trả kết quả chủ yếu từ index mà không phải fetch document đầy đủ.

**Ví dụ:**
```javascript
db.orders.find(
  { tenantId: "t-42", status: "Pending" },
  { orderNo: 1, createdAt: 1, _id: 0 }
).sort({ createdAt: -1 })
```

Một index có thể cân nhắc theo access pattern:

```javascript
{ tenantId: 1, status: 1, createdAt: -1, orderNo: 1 }
```

Sau đó dùng `explain("executionStats")` để xem `totalKeysExamined`, `totalDocsExamined` và số result thực tế.

**Lưu ý:**
Đừng biến mọi query thành covered query bằng cách nhét quá nhiều field vào compound index. Index lớn làm tăng storage, RAM pressure và write amplification. Thiết kế index phải dựa trên workload quan trọng, selectivity, sort pattern và chi phí write thực tế.

### Tip 3 — Dùng ETag / `If-Match` để ngăn lost update ở REST API

**Mẹo:**
Khi nhiều client có thể sửa cùng một resource, cân nhắc optimistic concurrency ở HTTP layer bằng ETag. Client đọc resource cùng version, sau đó gửi `If-Match` khi update; server chỉ chấp nhận nếu version vẫn còn khớp.

**Tại sao hữu ích:**
Nếu hai user cùng mở một profile, user A cập nhật trước rồi user B submit dữ liệu cũ sau, một `PUT`/`PATCH` không có concurrency check có thể ghi đè thay đổi của A mà không ai biết. Đây là lost update, không phải lỗi transport.

**Ví dụ:**
```http
GET /api/customers/42
ETag: "v17"
```

Client cập nhật:

```http
PATCH /api/customers/42
If-Match: "v17"
```

Nếu database đã sang `v18`, server có thể trả `412 Precondition Failed` để client reload/merge thay vì overwrite im lặng.

**Lưu ý:**
ETag chỉ hữu ích khi version token phản ánh đúng concurrency boundary. Với EF Core có thể map row version/concurrency token xuống HTTP contract. Đừng dùng timestamp có độ phân giải không đủ hoặc hash không ổn định rồi coi đó là version đáng tin cậy.

### Tip 4 — Dùng `git bisect` khi regression có khoảng commit đủ lớn

**Mẹo:**
Khi biết một commit cũ còn tốt và commit hiện tại bị lỗi, dùng `git bisect` để tìm commit đầu tiên gây regression theo binary search thay vì đọc tuần tự hàng chục hoặc hàng trăm commit.

**Tại sao hữu ích:**
Với 128 commit nghi vấn, binary search lý tưởng chỉ cần khoảng 7 lần kiểm tra. Nếu có test/script tái hiện lỗi, `git bisect run` còn có thể tự động hóa toàn bộ quá trình và đưa investigation từ cảm tính về evidence.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0

git bisect run dotnet test tests/Regression.Tests \
  --filter FullyQualifiedName~InvoiceRounding

git bisect reset
```

Mỗi lần test pass/fail giúp Git thu hẹp nửa khoảng tìm kiếm còn lại.

**Lưu ý:**
Bisect hiệu quả nhất khi từng commit trong khoảng có thể build/test tương đối độc lập. Nếu lịch sử chứa commit trung gian không build được, generated artifacts thay đổi lớn hoặc bug phụ thuộc external state, cần script kiểm tra đủ robust và có thể phải đánh dấu commit `skip`.

### Tip 5 — Tránh EF Core cartesian explosion khi `Include` nhiều collection cùng cấp

**Mẹo:**
Khi query một aggregate có nhiều collection navigation cùng cấp, kiểm tra SQL thực tế và số row được trả. Một query duy nhất với nhiều `LEFT JOIN` có thể nhân số row theo tích số phần tử; cân nhắc `AsSplitQuery()` hoặc projection đúng use case.

**Tại sao hữu ích:**
Nếu một `Blog` có 20 `Posts` và 15 `Contributors`, join cả hai collection cùng cấp có thể tạo 300 row cho chỉ một blog. Database, network và materializer đều phải xử lý dữ liệu lặp dù application cuối cùng chỉ tạo một object graph.

**Ví dụ:**
```csharp
var blogs = await db.Blogs
    .Include(x => x.Posts)
    .Include(x => x.Contributors)
    .AsSplitQuery()
    .ToListAsync(ct);
```

Nếu endpoint chỉ cần summary, projection thường tốt hơn nữa:

```csharp
var result = await db.Blogs
    .Select(x => new
    {
        x.Id,
        x.Name,
        PostCount = x.Posts.Count
    })
    .ToListAsync(ct);
```

**Lưu ý:**
Split query đổi một query lớn thành nhiều query và có trade-off về round trip cũng như consistency giữa các query nếu dữ liệu thay đổi đồng thời. Không bật máy móc cho mọi query; đo row amplification, payload và latency để chọn strategy.

## 🧠 Software Design

### Design 1 — Transactional Outbox để database state và event không bị “lệch pha”

**Khái niệm:**
Transactional Outbox lưu business change và message cần publish vào cùng một local database transaction. Một worker riêng đọc outbox và publish message ra broker, sau đó đánh dấu trạng thái gửi.

**Vấn đề nó giải quyết:**
Một service lưu `Order = Paid` thành công rồi publish `OrderPaid` ra broker. Nếu process crash giữa hai bước, database nói đã thanh toán nhưng downstream không bao giờ nhận event. Làm ngược thứ tự cũng có thể publish event rồi database rollback.

**Ví dụ thực tế:**
```text
DB transaction:
1. UPDATE Orders SET Status = 'Paid'
2. INSERT OutboxMessages(Id, Type, Payload, CreatedAt)
3. COMMIT

Publisher worker:
4. đọc OutboxMessages chưa gửi
5. publish OrderPaid
6. đánh dấu sent / checkpoint
```

Consumer vẫn phải idempotent vì publisher có thể crash sau khi broker nhận message nhưng trước khi outbox được đánh dấu sent.

**Trade-off:**
Outbox loại bỏ dual-write gap giữa database và broker nhưng thêm bảng outbox, polling/change-data-capture strategy, cleanup, retry và observability. Nó không tạo exactly-once end-to-end; phần thực tế thường là at-least-once delivery kết hợp idempotent processing.

**Middle → Senior insight:**
Middle developer cần nhận ra `SaveChangesAsync()` rồi `PublishAsync()` là hai commit độc lập. Senior / Technical developer phải thiết kế atomicity boundary, ordering, retry, deduplication, retention và failure recovery trước khi gọi flow event-driven là reliable.

### Design 2 — Anti-Corruption Layer bảo vệ domain khỏi model của hệ thống bên ngoài

**Khái niệm:**
Anti-Corruption Layer (ACL) là lớp adapter/translation nằm giữa domain của mình và external/legacy system. Nó chuyển contract, terminology và failure semantics bên ngoài thành model mà domain nội bộ hiểu, thay vì để external DTO lan xuyên application.

**Vấn đề nó giải quyết:**
Một ERP gọi khách hàng là `Account`, trạng thái dùng code `A/I/S`, tiền tệ biểu diễn bằng integer cents và lỗi trả về bằng mã riêng. Nếu application dùng nguyên các DTO đó trong domain, mọi thay đổi hoặc oddity của ERP sẽ rò rỉ vào business model và làm coupling tăng dần.

**Ví dụ thực tế:**
```text
ERP response
{ accountNo, state: "A", credit: 125000 }
        ↓
ERP Adapter / ACL
        ↓
CustomerCredit
{ customerId, status: Active, limit: Money(1250, "USD") }
```

Domain chỉ biết `CustomerCredit`; mapping code, retry/error translation và compatibility với ERP nằm ở integration boundary.

**Trade-off:**
ACL thêm code mapping và đôi khi trông như boilerplate, đặc biệt khi hai model hiện tại gần giống nhau. Nhưng chi phí này mua isolation. Không cần tạo layer phức tạp cho mọi API nhỏ; giá trị tăng mạnh khi external model có lifecycle, semantics hoặc ownership độc lập.

**Middle → Senior insight:**
Middle developer cần tránh dùng vendor DTO như domain entity chỉ vì tiện. Senior / Solution-oriented engineer phải xác định đâu là bounded context, semantic mismatch nào cần translation và phần integration nào nên được cô lập để thay vendor không kéo theo refactor toàn core domain.

### Design 3 — Feature Flag phải có lifecycle, owner và kế hoạch xóa

**Khái niệm:**
Feature Flag tách việc deploy code khỏi việc enable behavior. Code mới có thể nằm production nhưng chỉ bật cho một cohort, tenant hoặc phần trăm traffic. Tuy nhiên flag là temporary decision point, không nên trở thành configuration vĩnh viễn không ai sở hữu.

**Vấn đề nó giải quyết:**
Team muốn release checkout mới dần cho 5% user, theo dõi error/latency rồi tăng rollout mà không redeploy. Flag cho phép progressive delivery và rollback hành vi nhanh nếu signal xấu.

**Ví dụ thực tế:**
```text
Flag: checkout-v2
Owner: Payments Team
Created: 2026-09-14
Expiry target: 2026-10-15

Rollout:
internal -> 5% -> 25% -> 100%

Success criteria:
- payment error rate không tăng
- p95 latency trong budget
- conversion không giảm quá threshold

Sau ổn định:
- giữ nhánh v2
- xóa nhánh v1
- xóa flag
```

Test cần cover cả hai branch trong thời gian flag tồn tại, đặc biệt với authorization, pricing hoặc data-write path.

**Trade-off:**
Feature flag giảm deployment risk nhưng mỗi flag thêm state-space cần test. Nhiều flag tương tác có thể tạo tổ hợp behavior khó reasoning và dead code kéo dài. Operational kill switch có thể cần sống lâu hơn release flag, nhưng hai loại nên có ownership và governance khác nhau.

**Middle → Senior insight:**
Middle developer cần biết flag không chỉ là `if` lấy từ config. Senior / Technical developer phải quản lý rollout metrics, default behavior khi flag service lỗi, audit/permissions, interaction giữa flags và thời điểm cleanup để progressive delivery không biến thành permanent complexity.
