# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Chọn đúng lifetime cho `IOptions`, `IOptionsSnapshot` và `IOptionsMonitor`

**Mẹo:**
Trong ASP.NET Core, đừng dùng ba API Options như nhau về mặt semantics. `IOptions<T>` phù hợp cho cấu hình gần như bất biến trong vòng đời process, `IOptionsSnapshot<T>` tạo snapshot theo scope/request, còn `IOptionsMonitor<T>` phù hợp khi cần quan sát thay đổi cấu hình lúc runtime.

**Tại sao hữu ích:**
Sai lifetime có thể tạo bug khó thấy: service singleton phụ thuộc cấu hình cần reload nhưng lại dùng snapshot cũ, hoặc code request-scoped vô tình kéo thêm complexity chỉ để đọc config tĩnh. Hiểu behavior của từng abstraction giúp cấu hình nhất quán với lifetime của consumer.

**Ví dụ:**
```csharp
public sealed class PricingClient(IOptionsMonitor<PricingOptions> options)
{
    public Uri GetEndpoint()
        => new(options.CurrentValue.BaseUrl);
}
```

Nếu configuration provider hỗ trợ reload, `CurrentValue` có thể phản ánh giá trị mới mà không restart process.

**Lưu ý:**
Reloadable configuration không có nghĩa mọi dependency bên dưới tự cập nhật an toàn. Nếu option thay đổi connection, credential hoặc endpoint quan trọng, cần xem xét thread safety, validation và cách recreate resource đang cache. Với config cần ổn định trong toàn request, snapshot semantics có thể phù hợp hơn monitor đọc giá trị thay đổi giữa chừng.

### Tip 2 — Dùng keyset pagination khi `OFFSET` bắt đầu trở thành bottleneck

**Mẹo:**
Với bảng lớn và danh sách được sort theo key ổn định, cân nhắc keyset pagination thay vì `OFFSET ... FETCH` cho các trang sâu. Client gửi lại cursor từ row cuối cùng thay vì yêu cầu database bỏ qua hàng trăm nghìn row.

**Tại sao hữu ích:**
`OFFSET 500000` vẫn buộc database tìm và bỏ qua một lượng lớn row trước khi trả page tiếp theo. Keyset pagination cho phép execution plan seek từ vị trí đã biết, thường ổn định hơn theo kích thước dữ liệu.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, TotalAmount
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)` tùy workload thực tế.

**Lưu ý:**
Keyset pagination không phù hợp khi UI cần nhảy trực tiếp tới “page 237” theo số trang tuyệt đối. Cursor cũng phải dựa trên sort order deterministic; nếu sort chỉ theo `CreatedAt` có nhiều giá trị trùng, cần thêm tie-breaker như `Id`.

### Tip 3 — Ưu tiên Managed Identity thay vì lưu secret khi Azure service gọi tài nguyên Azure khác

**Mẹo:**
Nếu App Service, Function hoặc workload Azure cần truy cập Key Vault, Storage hoặc Service Bus, ưu tiên Managed Identity + RBAC thay vì lưu connection string hoặc client secret trong configuration.

**Tại sao hữu ích:**
Secret tĩnh phải được tạo, phân phối, rotate và bảo vệ khỏi log/leak. Managed Identity cho workload một identity do Azure quản lý; application xin token động qua Azure Identity thay vì giữ credential lâu dài trong source hoặc deployment settings.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);
```

Production dùng Managed Identity; local development có thể dùng developer credential phù hợp qua cùng credential chain.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Vẫn phải gán đúng RBAC role và scope; tránh cấp quyền ở subscription/resource group khi workload chỉ cần một resource cụ thể. `DefaultAzureCredential` cũng cần được kiểm soát để production không vô tình fallback sang credential không mong muốn.

### Tip 4 — Dùng browser DevTools để tách frontend chậm do network, rendering hay JavaScript

**Mẹo:**
Khi page “chậm”, đừng chỉ nhìn total load time. Dùng Network waterfall, Performance trace và Core Web Vitals để xác định bottleneck nằm ở TTFB, resource loading, main-thread JavaScript hay rendering/layout.

**Tại sao hữu ích:**
Một trang có thể có backend nhanh nhưng vẫn tương tác chậm vì bundle lớn hoặc long task; ngược lại frontend code nhẹ nhưng TTFB cao vì API/database chậm. Phân loại đúng bottleneck giúp tránh tối ưu sai tầng.

**Ví dụ:**
```text
Network:
- document TTFB: 1.8s
- JS bundle: 300ms

Performance:
- không có long task đáng kể
```

Trường hợp này nên điều tra backend/CDN trước khi dành thời gian micro-optimize React/Vue rendering.

**Lưu ý:**
Một lần profile trên máy developer không đại diện production traffic hoặc thiết bị người dùng. Kiểm tra cả throttling, mobile CPU, cache state và real-user telemetry nếu có. Lighthouse score là signal hỗ trợ, không phải mục tiêu duy nhất.

### Tip 5 — Dùng `git bisect` để tìm commit gây regression thay vì đọc diff theo cảm tính

**Mẹo:**
Khi biết một version cũ chạy đúng và version hiện tại bị regression, dùng `git bisect` để binary-search lịch sử commit. Nếu có test hoặc script tái hiện bug, kết hợp `git bisect run` để tự động hóa quá trình.

**Tại sao hữu ích:**
Với 256 commit nghi ngờ, binary search thường chỉ cần khoảng 8 lần kiểm tra để thu hẹp commit đầu tiên gây lỗi. Điều này đặc biệt hữu ích với performance regression, startup failure hoặc behavior thay đổi mà diff hiện tại quá lớn để review thủ công hiệu quả.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
```

Git sẽ checkout các commit trung gian và đánh dấu good/bad dựa trên exit code của test command.

**Lưu ý:**
`git bisect` chỉ đáng tin khi phép kiểm tra deterministic. Flaky test, dependency external thay đổi hoặc migration không tương thích lịch sử có thể dẫn đến commit kết luận sai. Sau khi tìm được commit, vẫn cần hiểu root cause thay vì revert máy móc.

## 🧠 Software Design

### Design 1 — Ports and Adapters để cô lập dependency ngoài khỏi business logic

**Khái niệm:**
Ports and Adapters (Hexagonal Architecture) giữ business/application logic phụ thuộc vào contract do hệ thống sở hữu, còn database, HTTP client, message broker hoặc vendor SDK nằm ở adapter phía ngoài. Mục tiêu chính là kiểm soát direction của dependency, không phải tạo nhiều project nhất có thể.

**Vấn đề nó giải quyết:**
Nếu use case trực tiếp gọi SDK của payment provider hoặc chứa EF-specific query ở mọi nơi, thay provider, test failure path hoặc migrate data access sẽ kéo thay đổi xuyên business code. Boundary rõ giúp external technology trở thành implementation detail có kiểm soát.

**Ví dụ thực tế:**
```text
Application port:
IPaymentGateway.AuthorizeAsync(...)

Adapters:
- StripePaymentGateway
- FakePaymentGateway cho test

Use case:
CheckoutService -> IPaymentGateway
```

Business flow không cần biết vendor trả HTTP status hay SDK exception cụ thể; adapter map chúng sang model lỗi nội bộ có ý nghĩa.

**Trade-off:**
Boundary tốt giảm coupling và tăng khả năng test/migrate, nhưng abstraction cho mọi dependency nhỏ có thể tạo ceremony và interface vô nghĩa. Với CRUD đơn giản, direct EF Core usage trong application layer có thể hợp lý hơn việc bọc lại toàn bộ `DbContext` bằng repository generic.

**Middle → Senior insight:**
Middle developer cần giữ vendor/framework detail ở boundary phù hợp. Senior / Technical developer phải quyết định dependency nào đáng tạo port dựa trên volatility, semantic mismatch, testing need và business criticality; architecture tốt tối ưu change cost chứ không tối đa số abstraction.

### Design 2 — Read Replica tăng throughput đọc nhưng đổi consistency semantics

**Khái niệm:**
Read Replica tách một phần read traffic khỏi primary database bằng cách replicate dữ liệu sang node chỉ đọc. Đây là kỹ thuật scale/read isolation, không phải bản sao luôn đồng bộ tuyệt đối tại mọi thời điểm.

**Vấn đề nó giải quyết:**
Một hệ thống reporting hoặc catalog có lượng đọc lớn có thể làm primary chịu CPU/I/O pressure trong khi write workload vẫn quan trọng. Đẩy query phù hợp sang replica giúp bảo vệ primary và mở rộng read capacity.

**Ví dụ thực tế:**
```text
POST /orders
-> ghi Primary

GET /orders/{id} ngay sau đó
-> nếu đọc Replica có replication lag 2s
-> có thể chưa thấy order vừa tạo
```

Các flow cần read-your-write consistency có thể tiếp tục đọc primary trong một khoảng thời gian hoặc theo operation context.

**Trade-off:**
Replica tăng read capacity và isolation nhưng thêm replication lag, routing logic, failover concern và cost vận hành. Không phải query nào cũng nên chuyển sang replica; workflow cần consistency mạnh hoặc transaction liên quan write thường vẫn cần primary.

**Middle → Senior insight:**
Middle developer cần hiểu “read-only” không đồng nghĩa “fresh”. Senior / Solution-oriented engineer phải phân loại query theo consistency requirement, replication lag tolerance, failover behavior và cost trước khi dùng replica như giải pháp scale mặc định.

### Design 3 — Queue và Topic giải quyết hai kiểu ownership message khác nhau

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer xử lý; Topic + Subscription phù hợp khi cùng một event cần được nhiều consumer độc lập nhận và xử lý theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Nếu `OrderCreated` cần cả Billing, Analytics và Email cùng phản ứng, đặt tất cả consumer cạnh tranh trên một queue sẽ khiến chỉ một consumer nhận mỗi message. Ngược lại, dùng topic cho work item chỉ cần một worker xử lý có thể tạo duplicate business processing không cần thiết.

**Ví dụ thực tế:**
```text
Queue: image-resize-jobs
- nhiều worker cạnh tranh
- mỗi job được một worker xử lý logic chính

Topic: order-events
Subscriptions:
- billing
- analytics
- notifications
```

Mỗi subscription có retry, dead-letter và filter riêng nếu broker hỗ trợ.

**Trade-off:**
Queue đơn giản hơn cho work distribution nhưng không broadcast. Topic tăng decoupling giữa publisher và nhiều subscriber nhưng tăng số luồng vận hành, duplicate delivery, schema/versioning và observability cần quản lý. Event fan-out cũng có thể tạo eventual consistency giữa các subsystem.

**Middle → Senior insight:**
Middle developer cần chọn queue/topic theo semantics của message thay vì tên service. Senior / Technical developer phải xác định message là command hay event, ownership side effect, subscription lifecycle, ordering, idempotency và failure isolation trước khi thiết kế topology broker.
