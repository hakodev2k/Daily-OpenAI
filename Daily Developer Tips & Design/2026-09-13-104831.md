# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Nhận diện ThreadPool starvation thay vì chỉ tăng timeout

**Mẹo:**
Khi ASP.NET Core API đột nhiên tăng latency dù CPU chưa chạm 100%, kiểm tra khả năng ThreadPool starvation trước khi tăng timeout. Các dấu hiệu thường đến từ sync-over-async như `.Result`, `.Wait()`, blocking I/O hoặc quá nhiều work đồng bộ chạy trên ThreadPool.

**Tại sao hữu ích:**
ASP.NET Core cần ThreadPool thread để tiếp tục xử lý continuation và request mới. Nếu thread bị block hàng loạt, request có thể xếp hàng dù database hoặc downstream vẫn còn khỏe. Tăng timeout chỉ làm nhiều request mắc kẹt lâu hơn và có thể khuếch đại incident.

**Ví dụ:**
```bash
dotnet-counters monitor -p <PID> System.Runtime
```

Quan sát các signal như:
```text
thread_pool.thread.count      tăng liên tục
thread_pool.queue.length      tăng
CPU                           không tăng tương ứng
request latency               tăng mạnh
```

Sau đó tìm các call path kiểu:
```csharp
var result = httpClient.GetStringAsync(url).Result;
```

và chuyển thành async end-to-end:
```csharp
var result = await httpClient.GetStringAsync(url, ct);
```

**Lưu ý:**
Thread count tăng không tự động chứng minh starvation. Cần correlate với queue length, latency, trace và blocking stack. Đừng dùng `Task.Run` để bọc I/O blocking rồi coi đó là async; bạn vẫn đang tiêu ThreadPool thread.

### Tip 2 — Dùng EF Core interceptor cho cross-cutting concern, không nhét business rule vào đó

**Mẹo:**
`SaveChangesInterceptor` hữu ích cho concern kỹ thuật xuyên suốt như audit metadata, telemetry hoặc policy kiểm tra chung. Nhưng tránh đặt business workflow phức tạp trong interceptor vì execution flow trở nên khó nhìn thấy và khó test.

**Tại sao hữu ích:**
Nếu mọi entity cần tự động cập nhật `ModifiedAt`, interceptor giúp tránh lặp code ở nhiều service. Tuy nhiên nếu interceptor bắt đầu gửi email, publish event hoặc thay đổi aggregate khác theo business rule, side effect bị giấu khỏi application flow và transaction semantics trở nên khó reasoning.

**Ví dụ:**
```csharp
public sealed class AuditInterceptor(TimeProvider clock)
    : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData,
        InterceptionResult<int> result)
    {
        if (eventData.Context is { } db)
        {
            foreach (var entry in db.ChangeTracker.Entries<IAuditable>())
            {
                if (entry.State == EntityState.Modified)
                    entry.Entity.ModifiedAt = clock.GetUtcNow();
            }
        }

        return result;
    }
}
```

**Lưu ý:**
Interceptor chạy ở tầng persistence, nên đừng giả định nó luôn có đủ user/business context. Nếu cần domain event, authorization hoặc workflow phụ thuộc aggregate state, thường nên thể hiện rõ ở application/domain layer thay vì “ẩn” trong interceptor.

### Tip 3 — Giới hạn concurrency của Azure Functions theo capacity downstream, không theo khả năng scale của Function

**Mẹo:**
Với Azure Functions xử lý queue/message, tune concurrency dựa trên database, API hoặc Service Bus dependency phía sau thay vì để Function mở rộng song song tối đa rồi mới phản ứng khi downstream quá tải.

**Tại sao hữu ích:**
Serverless scale-out không có nghĩa dependency cũng scale vô hạn. Nếu mỗi Function instance mở nhiều concurrent handler và platform đồng thời tăng instance, tổng số connection/query có thể vượt capacity SQL hoặc API downstream, gây timeout và retry storm.

**Ví dụ:**
```text
10 instances
x 16 concurrent messages/instance
= tối đa ~160 message đang xử lý

Nếu SQL chỉ chịu ổn định khoảng 80 concurrent operations,
Function có thể tự tạo overload dù bản thân compute còn dư.
```

Theo dõi queue age, processing rate, database saturation và dependency latency để tune concurrency/scale policy.

**Lưu ý:**
Concurrency quá thấp làm backlog tăng và lãng phí capacity. Cũng đừng chỉ giảm concurrency mà bỏ qua query chậm, connection leak hoặc partition/hot-key problem. Đây là capacity-control decision end-to-end.

### Tip 4 — Trong Playwright, ưu tiên locator + auto-waiting thay vì `waitForTimeout`

**Mẹo:**
Khi test UI cần chờ element có thể tương tác, dùng locator/assertion có auto-waiting thay vì chèn sleep cố định như `page.waitForTimeout(2000)`.

**Tại sao hữu ích:**
Sleep cố định tạo hai thất bại đối nghịch: nếu app nhanh, test vẫn lãng phí thời gian; nếu CI chậm hơn 2 giây, test vẫn fail. Auto-waiting chờ đúng condition như visible, enabled hoặc expected text trong giới hạn timeout.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click()
await expect(page.getByText('Saved successfully')).toBeVisible()
```

Thay vì:
```ts
await page.waitForTimeout(2000)
await page.locator('.toast-success').isVisible()
```

**Lưu ý:**
Auto-waiting không sửa application race condition hoặc test data bị nondeterministic. Nếu test vẫn flaky, kiểm tra network, state isolation, animation, background job và backend readiness thay vì tăng global timeout một cách máy móc.

### Tip 5 — Với SPA/mobile OAuth, dùng Authorization Code + PKCE thay vì nhét client secret vào client

**Mẹo:**
Với SPA hoặc mobile app, dùng Authorization Code Flow với PKCE. Public client không thể bảo vệ client secret, nên đừng embed secret trong JavaScript bundle hoặc mobile binary để cố “bảo mật” token exchange.

**Tại sao hữu ích:**
PKCE tạo một verifier chỉ client đang thực hiện flow biết và gửi challenge ở bước authorize. Khi authorization code bị intercept, attacker không thể đổi code lấy token nếu không có verifier tương ứng.

**Ví dụ:**
```text
Client tạo:
code_verifier = random secret
code_challenge = SHA256(code_verifier)

Authorize request:
/authorize?...&code_challenge=...

Token request:
/token
  code=...
  code_verifier=...
```

Identity provider kiểm tra verifier khớp challenge trước khi phát token.

**Lưu ý:**
PKCE không thay thế redirect URI validation, state/nonce, token validation hoặc XSS protection. Với web app có backend tin cậy, Backend-for-Frontend có thể giữ token phía server và giảm exposure token trong browser; chọn mô hình theo threat model thay vì áp một flow cho mọi client.

## 🧠 Software Design

### Design 1 — Modular Monolith cần ownership boundary thật, không chỉ chia project/folder

**Khái niệm:**
Modular Monolith giữ deployment chung nhưng chia hệ thống thành module có responsibility, API và data ownership rõ. Giá trị nằm ở dependency direction và ownership, không phải việc tạo nhiều class library tên `Orders`, `Payments`, `Catalog`.

**Vấn đề nó giải quyết:**
Một monolith dễ trở thành “distributed spaghetti trong cùng process” nếu module nào cũng query table của module khác, gọi internal class tùy ý và cùng sửa shared model. Khi đó deployment vẫn đơn giản nhưng coupling cao và migration về microservice sau này rất khó.

**Ví dụ thực tế:**
```text
Orders module
- sở hữu Orders/OrderLines schema
- expose command/query contract

Payments module
- không update Orders table trực tiếp
- gửi payment result qua module contract/event
```

Có thể dùng cùng SQL Server instance nhưng tách schema/DbContext hoặc enforce rule bằng architecture test để giảm accidental coupling.

**Trade-off:**
Modular Monolith giữ operational simplicity và transaction nội bộ thuận tiện hơn microservices, nhưng boundary chỉ có giá trị nếu team thực sự tuân thủ. Enforce quá cứng cho CRUD nhỏ có thể tăng boilerplate; enforce quá lỏng khiến module chỉ là folder đẹp.

**Middle → Senior insight:**
Middle developer cần tôn trọng public contract của module và tránh “đi đường tắt” vào internal data. Senior / Technical developer phải xác định boundary theo business capability/invariant, dependency rule, data ownership và tiêu chí khi một module thật sự cần tách deployment độc lập.

### Design 2 — Retry Budget để tránh retry amplification trong hệ thống nhiều tầng

**Khái niệm:**
Retry Budget giới hạn tổng số lần thử lại được phép trong một request/workflow thay vì để mỗi tầng tự retry độc lập. Mục tiêu là kiểm soát load bổ sung khi dependency đang lỗi.

**Vấn đề nó giải quyết:**
Nếu API Gateway retry 2 lần, service A retry service B 3 lần và B retry database 3 lần, một request ban đầu có thể nhân thành rất nhiều attempt. Khi dependency đã quá tải, retry amplification làm tình hình tệ hơn đúng lúc hệ thống yếu nhất.

**Ví dụ thực tế:**
```text
Client request
  -> Gateway: tối đa 2 attempts
    -> Order API: không retry thêm nếu budget đã dùng nhiều
      -> Payment API: 1 retry chỉ cho transient/idempotent operation
```

Có thể truyền deadline/attempt metadata hoặc định nghĩa policy theo boundary để tổng retry nằm trong latency budget.

**Trade-off:**
Retry có thể che transient fault ngắn và tăng success rate, nhưng retry quá nhiều tăng latency, load và duplicate side effect. Budget quá thấp lại làm failure recoverable bị trả về sớm. Cần kết hợp timeout, jitter/backoff, idempotency và circuit breaker phù hợp.

**Middle → Senior insight:**
Middle developer cần biết operation nào được retry an toàn và tránh nested retry vô thức. Senior / Technical developer phải thiết kế retry ownership theo call graph, latency SLO, dependency capacity và failure mode để toàn hệ thống có một resilience policy nhất quán.

### Design 3 — Elasticsearch nên là derived read model có khả năng rebuild, không phải bản sao “không thể mất”

**Khái niệm:**
Trong nhiều hệ thống, Elasticsearch phục vụ search/read optimization còn relational database hoặc document store khác là system of record. Search index nên được xem như projection có thể đồng bộ lại hoặc rebuild từ nguồn dữ liệu chính.

**Vấn đề nó giải quyết:**
Nếu application dual-write trực tiếp vào database và Elasticsearch trong cùng request, một bên có thể thành công còn bên kia fail. Khi index bị drift mà không có reconciliation/rebuild strategy, search result sẽ khác dữ liệu thật và team không biết nguồn nào đúng.

**Ví dụ thực tế:**
```text
Primary DB transaction
  -> update Product
  -> ghi Outbox event

Background indexer
  -> đọc ProductChanged
  -> update Elasticsearch

Reconciliation job
  -> kiểm tra version/count/hash theo partition

Full rebuild khi mapping thay đổi lớn:
  new-index-v2
  -> bulk reindex
  -> verify
  -> alias switch
```

**Trade-off:**
Derived index cho phép query/search tối ưu và rebuild an toàn, nhưng chấp nhận eventual consistency và thêm pipeline vận hành. Nếu business yêu cầu read-after-write tuyệt đối cho một path, path đó có thể cần đọc source of truth hoặc overlay dữ liệu mới thay vì tin index ngay lập tức.

**Middle → Senior insight:**
Middle developer cần biết search result có thể trễ và không dùng Elasticsearch để thực thi invariant giao dịch. Senior / Technical developer phải thiết kế sync mechanism, idempotent indexing, mapping/version strategy, reconciliation, rebuild và alias cutover để index drift trở thành failure có thể phục hồi thay vì incident bí ẩn.
