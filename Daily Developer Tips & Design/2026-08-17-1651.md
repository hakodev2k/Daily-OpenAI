# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Span<T>` cho hot path xử lý buffer mà không cần allocation

**Mẹo:**
Khi xử lý slice của array/string/buffer trên hot path, cân nhắc `Span<T>` hoặc `ReadOnlySpan<T>` để tránh tạo object trung gian và copy dữ liệu không cần thiết.

**Tại sao hữu ích:**
Giảm allocation, giảm áp lực GC và phù hợp với parser, protocol handler, serialization hoặc xử lý text/binary có tần suất cao.

**Ví dụ:**
```csharp
ReadOnlySpan<char> input = "order:12345";
var separator = input.IndexOf(':');

ReadOnlySpan<char> prefix = input[..separator];
ReadOnlySpan<char> idPart = input[(separator + 1)..];
```

Thay vì tạo nhiều `Substring()` mới chỉ để đọc các phần nhỏ của chuỗi.

**Lưu ý:**
`Span<T>` là `ref struct`, không thể lưu trong heap, field thông thường hoặc dùng xuyên `await`. Chỉ dùng khi profiling cho thấy allocation thực sự đáng tối ưu; đừng làm code khó đọc chỉ để tiết kiệm vài allocation nhỏ.

### Tip 2 — Dùng `ToQueryString()` để xem SQL EF Core trước khi chạy

**Mẹo:**
Khi nghi ngờ LINQ được dịch thành SQL không như mong đợi, gọi `ToQueryString()` trên `IQueryable` để xem câu SQL EF Core chuẩn bị sinh ra.

**Tại sao hữu ích:**
Giúp phát hiện join thừa, predicate bị biến đổi, projection quá lớn, N+1 gián tiếp hoặc query shape không phù hợp trước khi phải bật full database tracing.

**Ví dụ:**
```csharp
var query = dbContext.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new
    {
        x.Id,
        x.Status,
        x.Total
    });

var sql = query.ToQueryString();
_logger.LogDebug("Generated SQL: {Sql}", sql);
```

**Lưu ý:**
`ToQueryString()` không thay thế execution plan hay runtime metrics. SQL nhìn hợp lý vẫn có thể chậm do data distribution, statistics, index hoặc parameter-sensitive behavior.

### Tip 3 — Dùng `git diff --word-diff` khi review thay đổi text/config lớn

**Mẹo:**
Với JSON, YAML, Markdown, SQL script hoặc file config có line dài, dùng `git diff --word-diff` để thấy thay đổi ở mức token/word thay vì cả dòng bị tô là thay đổi.

**Tại sao hữu ích:**
Review dễ hơn đáng kể khi chỉ một giá trị trong dòng dài thay đổi, đặc biệt với pipeline config, generated-ish text hoặc documentation kỹ thuật.

**Ví dụ:**
```bash
git diff --word-diff main...HEAD -- .github/workflows/app.yml
```

Hoặc:

```bash
git diff --word-diff-regex='[^[:space:]]+' -- appsettings.json
```

**Lưu ý:**
Đây chỉ là cách hiển thị diff. Với format có cấu trúc như JSON/YAML, vẫn cần validate syntax và semantics bằng parser/linter thay vì dựa vào diff visual.

### Tip 4 — Tách readiness và liveness health check

**Mẹo:**
Đừng để một health endpoint duy nhất kiểm tra mọi dependency rồi dùng nó cho cả liveness và readiness. Liveness nên trả lời “process còn sống không?”, còn readiness trả lời “instance có sẵn sàng nhận traffic không?”.

**Tại sao hữu ích:**
Nếu database tạm thời down mà liveness cũng fail, orchestrator có thể restart hàng loạt instance dù restart không giải quyết được dependency outage. Readiness fail sẽ hợp lý hơn vì instance chỉ cần tạm ngừng nhận traffic.

**Ví dụ:**
Trong ASP.NET Core có thể phân loại check bằng tag:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<ProcessHealthCheck>("self", tags: ["live"])
    .AddCheck<DatabaseHealthCheck>("database", tags: ["ready"]);
```

Sau đó expose hai endpoint với predicate khác nhau.

**Lưu ý:**
Health check không nên thực hiện operation đắt hoặc timeout quá lâu. Một check nặng chạy mỗi vài giây có thể tự tạo thêm tải cho dependency đang yếu.

### Tip 5 — Dùng `EXPLAIN` cho `DELETE`/`UPDATE`, không chỉ `SELECT`

**Mẹo:**
Khi batch `UPDATE` hoặc `DELETE` chậm, phân tích execution plan cho phần lọc của statement thay vì chỉ tập trung vào query đọc.

**Tại sao hữu ích:**
Write statement cũng phải tìm row cần sửa. Predicate không có index phù hợp có thể scan hàng triệu rows trước khi update vài trăm records, kéo theo lock duration và transaction log tăng mạnh.

**Ví dụ:**
PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE jobs
SET status = 'expired'
WHERE status = 'running'
  AND heartbeat_at < now() - interval '10 minutes';
```

**Lưu ý:**
`EXPLAIN ANALYZE` thực sự chạy statement. Với `UPDATE`/`DELETE`, không chạy tùy tiện trên production. Dùng transaction rollback, staging, bản sao dữ liệu hoặc `EXPLAIN` không `ANALYZE` khi cần an toàn hơn.

## 🧠 Software Design

### Design 1 — Pessimistic Locking hay Optimistic Concurrency phải dựa vào contention

**Khái niệm:**
Optimistic Concurrency cho phép nhiều actor làm việc song song rồi phát hiện conflict khi commit. Pessimistic Locking khóa resource sớm để ngăn actor khác cùng thay đổi trong thời gian critical section.

**Vấn đề nó giải quyết:**
Một số workload có conflict hiếm, nên lock sớm chỉ làm giảm throughput. Nhưng với resource cực kỳ hot, retry do optimistic conflict liên tục có thể còn tốn kém hơn việc serialize access có kiểm soát.

**Ví dụ thực tế:**
Cập nhật profile nhân viên thường ít conflict → optimistic versioning phù hợp. Nhưng một batch worker đang phân phối 100 slot giới hạn cho hàng nghìn request đồng thời có thể cần `SELECT ... FOR UPDATE`, atomic database operation hoặc một coordination strategy chặt hơn.

**Trade-off:**
Optimistic approach scale tốt khi conflict thấp nhưng cần retry/merge. Pessimistic locking đơn giản hóa invariant trong critical section nhưng làm tăng lock wait, deadlock risk và giảm concurrency nếu lock scope quá rộng.

**Middle → Senior insight:**
Middle developer nên hiểu cả hai cơ chế và không mặc định “lock là xấu”. Senior developer phải đánh giá conflict rate, transaction duration, hot-row pattern, retry cost và failure mode trước khi chọn chiến lược concurrency.

### Design 2 — Anti-Corruption Layer khi tích hợp external/legacy model

**Khái niệm:**
Anti-Corruption Layer (ACL) là lớp chuyển đổi giữa domain model nội bộ và model/contract của hệ thống ngoài, để terminology và quirks của bên ngoài không lan sâu vào core business code.

**Vấn đề nó giải quyết:**
Legacy API hoặc vendor SDK thường có naming, trạng thái và rule khác domain hiện tại. Nếu application dùng trực tiếp model đó khắp nơi, external contract sẽ trở thành dependency kiến trúc khó thay đổi.

**Ví dụ thực tế:**
Một hệ thống ngoài trả trạng thái nhân viên `A`, `I`, `T`. Domain nội bộ dùng `Active`, `Inactive`, `Terminated` cùng business rule riêng. ACL map external DTO sang domain value object trước khi logic nghiệp vụ xử lý.

**Trade-off:**
ACL bảo vệ domain và giảm coupling với vendor nhưng thêm mapping code, test và maintenance. Với integration rất nhỏ, ổn định và không chạm core domain, một mapping layer lớn có thể là overengineering.

**Middle → Senior insight:**
Middle developer nên tránh để DTO/vendor type chạy xuyên toàn codebase. Senior developer phải quyết định boundary nào cần bảo vệ, ownership của mapping, error semantics và cách xử lý khi external contract thay đổi hoặc trả dữ liệu không hợp lệ.

### Design 3 — Chọn synchronous API hay asynchronous job theo latency budget và failure semantics

**Khái niệm:**
Không phải operation nào được trigger bằng HTTP cũng nên hoàn thành trong cùng request. Với công việc lâu, nhiều bước hoặc phụ thuộc external systems, có thể chuyển sang asynchronous job và trả `202 Accepted` cùng resource để theo dõi trạng thái.

**Vấn đề nó giải quyết:**
Giữ request mở vài phút làm tăng timeout, connection usage, retry ambiguity và trải nghiệm khó đoán khi client mất kết nối nhưng server vẫn đang xử lý.

**Ví dụ thực tế:**
Export báo cáo 2 triệu rows không nên buộc client chờ request 180 giây. API có thể tạo `ExportJob`, trả `202` + `jobId`, background worker sinh file, rồi client polling/webhook để biết khi hoàn tất.

**Trade-off:**
Async job giảm áp lực request path và xử lý retry tốt hơn, nhưng thêm state machine, persistence, progress tracking, idempotency, cleanup và UX phức tạp hơn. Với operation chỉ mất vài trăm milliseconds, async hóa chỉ tăng complexity.

**Middle → Senior insight:**
Middle developer nên biết khi nào endpoint bắt đầu vượt quá latency budget của request-response. Senior developer phải thiết kế rõ acceptance semantics, duplicate submission, cancellation, progress, timeout, retry và trạng thái cuối cùng để client không rơi vào tình trạng “không biết request đã chạy hay chưa”.
