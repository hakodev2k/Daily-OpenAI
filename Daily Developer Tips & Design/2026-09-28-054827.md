# Daily Developer Tips & Design — 2026-09-28

## 🛠 Developer Tips & Tricks

### Tip 1 — Giảm allocation với `Span<T>` chỉ sau khi profiler chỉ ra hot path

**Mẹo:**
Trong code parsing hoặc xử lý buffer có tần suất rất cao, cân nhắc `Span<T>` / `ReadOnlySpan<T>` để thao tác trên một vùng nhớ mà không cần tạo thêm array hoặc substring. Hãy bắt đầu từ profiler và allocation metrics, không refactor toàn bộ application chỉ vì API này tồn tại.

**Tại sao hữu ích:**
Các operation như `Substring`, copy array hoặc tạo temporary buffer lặp hàng triệu lần có thể tạo allocation pressure, khiến GC chạy thường xuyên hơn. `Span<T>` cung cấp một view lên memory hiện có và được runtime/JIT tối ưu cho nhiều thao tác slicing, nên có thể loại bỏ allocation trung gian ở hot path.

**Ví dụ:**
```csharp
static (ReadOnlySpan<char> Key, ReadOnlySpan<char> Value) SplitHeader(
    ReadOnlySpan<char> input)
{
    var separator = input.IndexOf(':');
    return (input[..separator].Trim(), input[(separator + 1)..].Trim());
}
```
Với parser chạy trên lượng lớn records, đo allocation trước/sau bằng profiler hoặc `dotnet-counters`/trace phù hợp để xác nhận lợi ích thực tế.

**Lưu ý:**
`Span<T>` là `ref struct`, có lifetime restrictions và không thể được dùng như object thông thường hoặc tùy ý sống qua `await`. Với business code không nằm trên hot path, string/array thông thường thường dễ đọc và bảo trì hơn.

### Tip 2 — Với Cosmos DB, chọn partition key từ access pattern chứ không từ field “có vẻ unique”

**Mẹo:**
Khi thiết kế container Cosmos DB, chọn partition key sao cho request phổ biến có thể route tới ít partition, đồng thời phân phối storage và throughput đủ đều. Đánh giá cardinality, write distribution và khả năng xuất hiện hot partition cùng nhau.

**Tại sao hữu ích:**
Partition key ảnh hưởng trực tiếp đến data distribution và query routing. Một key có cardinality thấp hoặc traffic lệch mạnh có thể tạo hot partition; ngược lại, query không có partition key thường phải fan-out qua nhiều physical partitions, làm RU và latency tăng.

**Ví dụ:**
Một SaaS order store thường truy vấn theo tenant. `tenantId` có thể là ứng viên tốt nếu tenants tương đối cân bằng; nhưng nếu một tenant tạo 70% traffic, cần xem xét hierarchical partition key hoặc mô hình phân phối khác thay vì mặc định dùng `tenantId`.

**Lưu ý:**
Đừng chọn partition key chỉ dựa trên uniqueness. Một `orderId` phân phối đẹp nhưng có thể khiến query “all orders for tenant” trở thành cross-partition query đắt. Partition-key decision rất khó thay đổi sau khi hệ thống lớn, nên phải dựa trên workload dự kiến và đo RU thực tế.

### Tip 3 — Dùng Managed Identity để loại secret khỏi kết nối Azure Key Vault

**Mẹo:**
Khi ASP.NET Core chạy trên Azure resource hỗ trợ Managed Identity, ưu tiên identity của workload để truy cập Azure Key Vault thay vì lưu client secret trong configuration hoặc CI/CD variable.

**Tại sao hữu ích:**
Managed Identity chuyển việc cấp và xoay credential sang Azure identity platform. Application xin token cho resource đích thay vì giữ một long-lived secret, giảm secret sprawl và rủi ro credential bị copy vào log, deployment manifest hoặc developer machine.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```
Ở Azure, `DefaultAzureCredential` có thể sử dụng Managed Identity; local development có thể dùng developer identity phù hợp. Cấp RBAC chỉ cho các secrets mà workload cần.

**Lưu ý:**
Managed Identity không loại bỏ authorization design. Identity có quyền quá rộng vẫn nguy hiểm; đồng thời tránh gọi Key Vault trên mọi request nếu secret/configuration có thể cache an toàn theo lifecycle phù hợp.

### Tip 4 — Dùng browser DevTools waterfall để tách frontend chậm khỏi backend chậm

**Mẹo:**
Khi trang Vue/React “load chậm”, mở Network waterfall và phân tách DNS/connect/TLS, TTFB, content download, request sequencing và JavaScript execution trước khi tối ưu component hoặc API theo cảm giác.

**Tại sao hữu ích:**
Một trang mất 4 giây có thể do API TTFB 3 giây, bundle lớn, requests bị serialize, image quá nặng hoặc main thread bận. Waterfall tạo evidence để biết latency nằm ở network/backend hay frontend scheduling/rendering.

**Ví dụ:**
Nếu `/api/product` có TTFB 120 ms nhưng request chỉ bắt đầu sau 2 giây vì bundle và JavaScript work, tăng database index không giải quyết vấn đề. Nếu request bắt đầu ngay nhưng TTFB 2.5 giây, trace backend/dependency tiếp theo mới hợp lý.

**Lưu ý:**
Một lần đo trên máy developer không đại diện production. Kiểm tra throttling, cache state, CDN và Real User Monitoring/Core Web Vitals khi quyết định optimization có ảnh hưởng người dùng thật.

### Tip 5 — Integration test database constraint, đừng mock away tính đúng đắn của persistence

**Mẹo:**
Với behavior phụ thuộc unique constraint, foreign key, transaction hoặc provider-specific SQL, dùng integration test với database engine thực tế thay vì chỉ mock repository/DbContext.

**Tại sao hữu ích:**
Mock có thể xác nhận method được gọi nhưng không tái hiện isolation level, constraint, query translation hoặc transaction behavior. Nhiều persistence bug chỉ xuất hiện khi SQL thực sự chạy trên đúng provider.

**Ví dụ:**
Một API đăng ký username phải chống duplicate ở database, không chỉ `AnyAsync` trước `Insert`. Integration test chạy hai attempts cạnh tranh và xác nhận unique constraint chặn duplicate, sau đó application map lỗi thành contract phù hợp.

**Lưu ý:**
Không cần biến mọi unit test thành database test. Giữ domain logic thuần ở unit tests; dùng integration tests có chọn lọc cho boundary nơi database semantics là một phần của correctness.

## 🧠 Software Design

### Design 1 — Saga cho workflow phân tán khi không thể có một ACID transaction

**Khái niệm:**
Saga chia một business workflow xuyên nhiều service/resource thành các local transactions có state transition rõ ràng; khi bước sau thất bại, hệ thống retry hoặc thực hiện compensating action phù hợp thay vì cố giữ một distributed database transaction dài.

**Vấn đề nó giải quyết:**
Một booking flow có thể cần giữ reservation, charge payment và tạo fulfillment ở các hệ thống khác nhau. Nếu payment thành công nhưng fulfillment thất bại, không có một local SQL transaction nào rollback được cả ba hệ thống.

**Ví dụ thực tế:**
Workflow chuyển qua `ReservationCreated → PaymentCaptured → FulfillmentRequested`. Nếu fulfillment thất bại vĩnh viễn, policy có thể refund payment và release reservation. State của Saga được persist để process có thể tiếp tục sau restart và mọi handler phải chịu được duplicate delivery.

**Trade-off:**
Saga tránh coupling vào distributed transaction và hỗ trợ recovery dài hạn, nhưng đổi lại có eventual consistency, state-machine complexity, compensation semantics, duplicate handling và observability khó hơn. Compensation cũng không phải “rollback”: refund payment là một business action mới có thể tự thất bại.

**Middle → Senior insight:**
Middle developer cần implement idempotent steps, persisted state và retry/compensation đúng. Senior / Technical developer phải xác định invariant nào thật sự cho phép eventual consistency, bước nào có thể compensate, điểm nào cần human intervention và liệu workflow đủ phức tạp để cần Saga hay một local transaction + simple queue đã đủ.

### Design 2 — Contract testing nằm giữa unit test và full E2E

**Khái niệm:**
Contract testing kiểm tra producer và consumer có cùng hiểu một interface/API/message schema mà không cần dựng toàn bộ distributed system cho mọi test. Nó bảo vệ compatibility boundary, không thay thế business tests của từng service.

**Vấn đề nó giải quyết:**
Service A có thể pass unit tests và Service B cũng pass unit tests nhưng deployment vẫn hỏng vì field đổi tên, enum semantics đổi hoặc response không còn thỏa expectation của consumer. Full E2E có thể bắt lỗi nhưng thường chậm, khó cô lập và phụ thuộc nhiều môi trường.

**Ví dụ thực tế:**
Mobile/backend consumer contract yêu cầu `GET /orders/{id}` luôn có `id`, `status` và nullable `cancelledAt`. CI của producer verify contract trước release; additive field mới không phá contract, nhưng xóa `status` sẽ fail trước deployment.

**Trade-off:**
Contract tests cho feedback nhanh và giảm integration regression nhưng tạo contract artifacts/versioning và không chứng minh toàn bộ runtime topology hoạt động. Nếu contract bám quá sát implementation, suite trở nên brittle và cản evolution.

**Middle → Senior insight:**
Middle developer cần viết contract theo observable behavior và hiểu compatibility. Senior / Technical developer phải quyết định boundary nào đáng contract-test, ownership/version lifecycle ra sao, và cân bằng unit/integration/contract/E2E để có confidence mà không nhân đôi cùng một test ở mọi layer.

### Design 3 — Build vs Buy là quyết định về lifecycle cost, không chỉ effort ban đầu

**Khái niệm:**
Build vs Buy so sánh khả năng tự xây với sản phẩm/platform bên ngoài trên toàn lifecycle: differentiation, integration, security, operations, migration, vendor dependency, cost và tốc độ thay đổi.

**Vấn đề nó giải quyết:**
Team thường đánh giá “tự code mất hai tuần” so với license cost nhưng bỏ qua patching, compliance, on-call, scaling và maintenance nhiều năm. Chiều ngược lại, mua platform có thể tạo lock-in hoặc ép domain vào capability không phù hợp.

**Ví dụ thực tế:**
Thay vì tự xây identity provider cho enterprise application, team có thể dùng Microsoft Entra/ZITADEL nếu authentication không phải năng lực tạo khác biệt. Nhưng cần đánh giá protocol support, custom login requirements, tenancy, SLA, export/migration path và operational ownership trước khi chọn.

**Trade-off:**
Buy thường giảm time-to-market và chuyển một phần operational burden cho platform, nhưng thêm license, vendor roadmap và migration risk. Build cho quyền kiểm soát cao hơn nhưng team phải sở hữu security, reliability và evolution lâu dài.

**Middle → Senior insight:**
Middle developer cần đánh giá API/SDK fit và integration constraints thay vì chỉ prototype happy path. Senior / Technical developer phải lượng hóa total cost of ownership, strategic differentiation, exit cost, compliance/SLA và failure dependency; lựa chọn tốt nhất có thể là mua, tự xây hoặc hybrid tùy business constraint.
