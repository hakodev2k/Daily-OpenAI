# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` thay vì gọi `DateTime.UtcNow` trực tiếp trong logic cần test

**Mẹo:**
Trong .NET 8+, nếu business logic phụ thuộc thời gian như token expiry, retry window, subscription renewal hoặc scheduled action, inject `TimeProvider` thay vì rải `DateTime.UtcNow` / `DateTimeOffset.UtcNow` trực tiếp trong code.

**Tại sao hữu ích:**
Clock là một dependency. Nếu đọc thời gian hệ thống trực tiếp, test phải chờ thời gian thật hoặc dùng workaround khó kiểm soát. `TimeProvider` biến clock thành dependency có thể thay thế, giúp test deterministic và tránh flaky test quanh boundary như hết hạn, midnight hoặc DST.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => expiresAt <= timeProvider.GetUtcNow();
}
```

Trong test có thể dùng fake time provider để advance thời gian mà không `Task.Delay` thật.

**Lưu ý:**
Đừng abstract mọi call tới thời gian chỉ vì “clean architecture”. Giá trị lớn nhất nằm ở logic mà thời gian ảnh hưởng behavior. Đồng thời phân biệt rõ UTC timestamp với local display time để tránh bug timezone.

### Tip 2 — Với Cosmos DB, đo RU theo query shape trước khi đổ lỗi cho “NoSQL chậm”

**Mẹo:**
Khi một query Cosmos DB tốn kém hoặc latency tăng, kiểm tra `RequestCharge`, partition fan-out và query metrics trước khi thêm cache hoặc scale throughput.

**Tại sao hữu ích:**
Chi phí Cosmos DB phụ thuộc mạnh vào partition key, số partition bị quét, index và lượng document đọc. Một query trả 20 record vẫn có thể tốn nhiều RU nếu phải fan-out toàn container. Scale RU chỉ che access pattern kém và tăng cost.

**Ví dụ:**
```csharp
using var iterator = container
    .GetItemQueryIterator<Order>(queryDefinition);

while (iterator.HasMoreResults)
{
    var page = await iterator.ReadNextAsync(ct);
    logger.LogInformation(
        "RU={RequestCharge} Count={Count}",
        page.RequestCharge,
        page.Count);
}
```

Nếu query luôn biết `TenantId`, truyền partition key phù hợp để tránh cross-partition scan khi data model cho phép.

**Lưu ý:**
RU thấp không đồng nghĩa query luôn tốt; hot partition vẫn có thể giới hạn throughput. Ngược lại, cross-partition query không phải lúc nào cũng sai — analytics/search workload có thể chấp nhận cost đó nếu đã budget rõ.

### Tip 3 — Dùng `Server-Timing` để nối browser waterfall với latency backend

**Mẹo:**
Khi frontend thấy request chậm nhưng khó biết thời gian nằm ở browser, CDN, API hay database, thêm `Server-Timing` header cho các phase backend quan trọng.

**Tại sao hữu ích:**
Browser DevTools có thể hiển thị timing do server gửi, giúp developer correlate một request cụ thể với các stage phía backend mà không cần đoán từ tổng duration. Đây là cách nhẹ để nối frontend troubleshooting với server-side observability.

**Ví dụ:**
```http
Server-Timing: db;dur=82.4, cache;dur=3.1, downstream;dur=145.0
```

Một response 320 ms có thể cho thấy downstream API chiếm phần lớn latency thay vì rendering hoặc database.

**Lưu ý:**
Không đưa dữ liệu nhạy cảm, SQL text, internal hostname hoặc customer identifier vào header. `Server-Timing` chỉ nên là diagnostic summary; root-cause analysis vẫn cần trace/log/metric đầy đủ ở backend.

### Tip 4 — Phân biệt Kubernetes memory request, limit và `OOMKilled` trước khi tăng RAM

**Mẹo:**
Khi pod restart với `OOMKilled`, kiểm tra memory working set, configured `requests`/`limits`, GC behavior và traffic pattern trước khi tăng limit một cách phản xạ.

**Tại sao hữu ích:**
`request` ảnh hưởng scheduling/capacity planning; `limit` đặt trần memory cho container. Nếu process vượt limit, kernel có thể kill container dù node vẫn còn memory. Ngược lại, request quá thấp làm scheduler nhồi quá nhiều pod lên cùng node và tạo resource contention.

**Ví dụ:**
```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

Nếu pod thường dùng 430 MiB nhưng spike lên 650 MiB sau một endpoint export lớn, cần xác định đây là leak, buffering không cần thiết hay workload hợp lệ trước khi chọn giới hạn mới.

**Lưu ý:**
Tăng limit có thể chỉ trì hoãn crash nếu application leak memory. Với .NET trong container, cũng cần hiểu GC nhận biết container limit và theo dõi allocation/heap bằng runtime counters hoặc dump khi cần.

### Tip 5 — Khi dùng AI coding agent, bắt nó xác minh API từ source/package version trước khi sửa code

**Mẹo:**
Với task liên quan framework/library cụ thể, yêu cầu AI agent kiểm tra package version, source code hoặc official API surface trong repository trước khi đề xuất implementation.

**Tại sao hữu ích:**
AI có thể nhớ API từ version khác, invent overload không tồn tại hoặc áp pattern đã deprecated. Grounding trên `csproj`, lock file, source và test hiện tại giảm hallucination và giúp change phù hợp codebase thật thay vì “mẫu chung trên Internet”.

**Ví dụ:**
```text
Trước khi sửa:
1. đọc *.csproj / Directory.Packages.props
2. xác định version package
3. search usage hiện tại trong repo
4. kiểm tra signature thực tế
5. sửa code
6. chạy build/test liên quan
```

Với migration lớn, yêu cầu agent liệt kê assumption chưa xác minh trước khi coding.

**Lưu ý:**
Agent đọc source vẫn có thể hiểu sai semantics. Build pass cũng không chứng minh behavior đúng. Với security, persistence hoặc distributed workflow, vẫn cần review trade-off, edge case và test behavior thủ công/automated phù hợp.

## 🧠 Software Design

### Design 1 — Async Request-Reply với `202 Accepted` cho workflow không thể hoàn thành trong một HTTP request

**Khái niệm:**
Khi operation mất lâu hoặc phụ thuộc nhiều background step, API có thể nhận request, tạo một operation resource, trả `202 Accepted` kèm location/status endpoint rồi hoàn thành xử lý bất đồng bộ.

**Vấn đề nó giải quyết:**
Giữ HTTP connection mở 2–5 phút cho import lớn, report generation hoặc media processing dễ chạm timeout ở client, proxy hoặc load balancer. Retry từ client cũng có thể vô tình tạo duplicate work nếu operation không idempotent.

**Ví dụ thực tế:**
```text
POST /reports
-> 202 Accepted
Location: /operations/op-123

GET /operations/op-123
-> Running

GET /operations/op-123
-> Succeeded
-> resultUrl: /reports/r-77
```

Operation ID có thể gắn với idempotency key để cùng request logic không tạo nhiều job trùng.

**Trade-off:**
Pattern này tăng resilience với long-running work và giảm coupling với HTTP timeout, nhưng làm client flow phức tạp hơn, cần status persistence, cleanup, auth cho operation resource và policy retry/cancel rõ ràng. Nếu work luôn hoàn thành trong vài trăm millisecond, sync response thường đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần implement status endpoint, idempotency và error state đúng. Senior / Technical developer phải quyết định SLA, polling vs push notification, retention, cancellation, duplicate submission và semantics khi backend hoàn thành nhưng client không nhận được result.

### Design 2 — Lease-based work claiming thay cho distributed lock bao trùm cả worker pipeline

**Khái niệm:**
Với nhiều worker cùng xử lý backlog, mỗi work item có thể được claim bằng lease có thời hạn thay vì đặt một distributed lock toàn cục cho cả pipeline. Worker phải renew hoặc hoàn tất trước khi lease hết hạn; nếu chết, item có thể được worker khác reclaim.

**Vấn đề nó giải quyết:**
Global distributed lock giữ toàn bộ job chỉ chạy trên một node làm giảm throughput và tạo single coordination bottleneck. Nhưng không có ownership mechanism lại khiến hai worker xử lý cùng item đồng thời.

**Ví dụ thực tế:**
```text
Job row:
Id = 42
Status = Processing
LeaseOwner = worker-B
LeaseUntil = 11:52:00

worker-B crash lúc 11:50
-> sau 11:52 worker-C có thể claim lại
```

Claim nên dùng atomic update/compare-and-set để chỉ một worker thắng.

**Trade-off:**
Lease cho phép scale-out và tự phục hồi tốt hơn lock toàn cục, nhưng không đảm bảo exactly-once. Work có thể được chạy lại sau timeout, nên handler vẫn cần idempotency và recovery semantics. Lease duration quá ngắn gây duplicate; quá dài làm recovery chậm.

**Middle → Senior insight:**
Middle developer cần implement atomic claim, timeout và retry an toàn. Senior / Technical developer phải chọn lease duration, heartbeat/renewal, poison-item policy, idempotency boundary và metric như queue age/lease expiry để vận hành hệ thống ổn định.

### Design 3 — Event schema evolution phải thiết kế cho producer/consumer chạy lệch version

**Khái niệm:**
Trong hệ thống event-driven, producer và consumer hiếm khi deploy đồng thời. Event contract cần tiến hóa theo hướng backward/forward compatible để nhiều version có thể coexist trong giai đoạn rollout.

**Vấn đề nó giải quyết:**
Nếu producer rename hoặc xóa field ngay lập tức, consumer cũ có thể fail deserialize hoặc hiểu sai business meaning. Ngược lại, consumer mới có thể deploy trước khi producer bắt đầu gửi field mới.

**Ví dụ thực tế:**
```text
V1:
OrderPlaced { orderId, total }

V2 compatible:
OrderPlaced { orderId, total, currency? }
```

Consumer mới xử lý `currency` nếu có; consumer cũ bỏ qua field lạ. Với breaking semantic change, tạo event/version mới thay vì âm thầm đổi ý nghĩa field cũ.

**Trade-off:**
Compatible evolution giảm coupling deploy và rollback risk, nhưng yêu cầu schema discipline, contract test và giai đoạn hỗ trợ nhiều version. Giữ compatibility quá lâu cũng tạo legacy contract debt; cần deprecation policy và telemetry để biết consumer cũ đã biến mất chưa.

**Middle → Senior insight:**
Middle developer cần tránh breaking serialization change và viết consumer tolerant với optional field hợp lệ. Senior / Technical developer phải quản lý schema ownership, versioning strategy, rollout order, replay compatibility và policy xóa field cũ dựa trên evidence thay vì giả định mọi consumer đã nâng cấp.
