# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup read-heavy đã ổn định

**Mẹo:**
Trong .NET 8+, nếu một tập key/value được tạo một lần rồi đọc rất nhiều lần, cân nhắc `FrozenDictionary<TKey,TValue>` thay vì giữ `Dictionary<TKey,TValue>` thông thường.

**Tại sao hữu ích:**
`FrozenDictionary` tối ưu cấu trúc nội bộ cho lookup sau khi dữ liệu đã được “đóng băng”. Nó phù hợp với mapping cấu hình, code table hoặc metadata được build lúc startup và không thay đổi trong runtime.

**Ví dụ:**
```csharp
var handlers = source
    .ToFrozenDictionary(x => x.Code, x => x.Handler);

var handler = handlers[request.Code];
```

**Lưu ý:**
Đừng dùng khi collection thay đổi thường xuyên. Chi phí tạo cấu trúc frozen chỉ đáng giá nếu read volume đủ lớn; hãy benchmark trước khi coi đây là optimization mặc định.

### Tip 2 — Với PostgreSQL, đọc `EXPLAIN (ANALYZE, BUFFERS)` khi query chậm

**Mẹo:**
Khi query production chậm, ngoài execution plan hãy xem actual timing và buffer usage để biết database đang đọc bao nhiêu page từ cache hoặc storage.

**Tại sao hữu ích:**
Hai query có cùng plan shape vẫn có thể khác performance mạnh vì số row thực tế, cache state hoặc lượng page phải đọc. `BUFFERS` giúp phân biệt CPU/query-shape issue với I/O pressure.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;
```

So sánh estimated rows, actual rows, shared hit/read và node tốn thời gian nhất trước khi đổi index.

**Lưu ý:**
`ANALYZE` thực sự chạy query. Với `UPDATE`, `DELETE` hoặc query đắt, hãy dùng môi trường an toàn hoặc transaction phù hợp thay vì chạy tùy ý trên production.

### Tip 3 — Với Cosmos DB, tìm hot partition thay vì chỉ nhìn tổng RU

**Mẹo:**
Nếu Cosmos DB xuất hiện `429` dù tổng throughput chưa cao, kiểm tra RU distribution theo partition và xem partition key có bị skew hay không.

**Tại sao hữu ích:**
Một logical partition có traffic vượt trội có thể trở thành bottleneck cục bộ trong khi phần còn lại của container gần như rảnh. Chỉ tăng tổng RU đôi khi không giải quyết được data-access pattern lệch.

**Ví dụ:**
Một hệ thống dùng `TenantId` làm partition key. Nếu một tenant tạo phần lớn request, telemetry có thể cho thấy throttling tập trung ở tenant đó. Khi đó cần đánh giá partition strategy, workload isolation hoặc key distribution thay vì chỉ scale throughput.

**Lưu ý:**
Đổi partition key là thay đổi lớn và thường kéo theo migration. Chỉ làm sau khi đã hiểu query pattern, transaction boundary, data volume và growth profile.

### Tip 4 — Dùng Playwright Trace Viewer cho flaky E2E test

**Mẹo:**
Khi test chỉ fail trên CI, bật trace cho retry hoặc failed test để xem DOM snapshot, network, console và action timeline thay vì chỉ đọc screenshot cuối cùng.

**Tại sao hữu ích:**
Screenshot chỉ cho biết trạng thái tại một thời điểm. Trace giúp tái dựng sequence trước failure: request nào chậm, element nào đổi state, navigation nào xảy ra và assertion fail sau action nào.

**Ví dụ:**
```ts
use: {
  trace: 'on-first-retry'
}
```

Khi test fail, mở trace artifact bằng Playwright Trace Viewer để so sánh state trước và sau action.

**Lưu ý:**
Không bật trace đầy đủ cho mọi test nếu suite lớn vì artifact và thời gian xử lý tăng. Chọn policy cân bằng giữa khả năng chẩn đoán và chi phí CI.

### Tip 5 — Trong Vue.js, dùng `computed` cho derived state thay vì copy bằng `watch`

**Mẹo:**
Nếu một giá trị hoàn toàn được suy ra từ reactive state khác, ưu tiên `computed` thay vì `watch` rồi ghi kết quả vào một `ref` khác.

**Tại sao hữu ích:**
Duplicate derived state tạo thêm nguồn sự thật và dễ bị lệch nếu watcher thiếu dependency hoặc lifecycle thay đổi. `computed` mô tả dependency trực tiếp và cache kết quả cho tới khi dependency thay đổi.

**Ví dụ:**
```ts
const firstName = ref('Ada')
const lastName = ref('Lovelace')

const fullName = computed(() =>
  `${firstName.value} ${lastName.value}`
)
```

**Lưu ý:**
`watch` vẫn phù hợp với side effect như gọi API, analytics hoặc sync external state. Không nhét side effect vào `computed` getter.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic

**Khái niệm:**
Queue phù hợp khi một logical message cần được xử lý bởi một consumer group. Topic + subscription phù hợp khi cùng một event cần được phân phối độc lập tới nhiều capability.

**Vấn đề nó giải quyết:**
Nếu `OrderPlaced` cần được Billing, Notification và Analytics xử lý độc lập, một queue duy nhất khiến các consumer cạnh tranh cùng message. Topic cho mỗi subscriber một subscription và lifecycle riêng.

**Ví dụ thực tế:**
`GenerateInvoice` là command có một owner rõ ràng nên hợp với queue. `OrderPlaced` là integration event có nhiều subscriber nên hợp với topic.

**Trade-off:**
Queue đơn giản hơn và dễ hiểu ownership. Topic hỗ trợ fan-out nhưng thêm subscription management, retry, filtering và observability cho từng subscriber.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumer và pub/sub semantics. Senior / Technical developer phải chọn topology dựa trên ownership, fan-out, ordering, retry isolation và khả năng hệ thống tiến hóa.

### Design 2 — Optimistic vs Pessimistic Concurrency

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor cùng đọc rồi phát hiện conflict khi update. Pessimistic concurrency giữ lock sớm để giảm khả năng actor khác thay đổi resource trong critical section.

**Vấn đề nó giải quyết:**
Khi hai user cùng sửa một record, “last write wins” có thể làm mất thay đổi mà không ai biết. Hệ thống cần một concurrency policy phù hợp với business invariant và mức contention.

**Ví dụ thực tế:**
Back-office edit customer profile thường phù hợp với `rowversion` hoặc version column và trả `409 Conflict` khi dữ liệu đã thay đổi. Một critical allocation cực ngắn đôi khi có thể cần lock có chủ đích nếu contention thấp và invariant rất chặt.

**Trade-off:**
Optimistic concurrency scale tốt khi conflict hiếm nhưng cần conflict-handling UX. Pessimistic locking giảm conflict window nhưng tăng blocking và deadlock risk nếu transaction kéo dài.

**Middle → Senior insight:**
Middle developer cần implement version check và xử lý conflict đúng semantics. Senior / Technical developer phải cân nhắc conflict rate, transaction duration, user experience và throughput trước khi chọn strategy.

### Design 3 — Clean Architecture vs Layered Architecture: boundary phải tạo giá trị thực

**Khái niệm:**
Layered Architecture tổ chức code theo presentation, business và data. Clean Architecture nhấn mạnh dependency hướng vào core và cô lập infrastructure sau boundary rõ ràng. Mức độ abstraction nên phản ánh complexity thực tế.

**Vấn đề nó giải quyết:**
Domain phức tạp thường cần bảo vệ business rule khỏi framework coupling. Nhưng một CRUD internal app nhỏ có thể bị chậm phát triển nếu mọi operation đều đi qua nhiều project, interface, mapper và mediator chỉ để tuân pattern.

**Ví dụ thực tế:**
Một pricing engine có rule phức tạp và nhiều integration có thể hưởng lợi từ domain/application boundary rõ. Một admin portal chủ yếu CRUD trên vài bảng có thể dùng layered architecture đơn giản hơn mà vẫn maintainable.

**Trade-off:**
Clean Architecture tăng isolation và testability nhưng có ceremony và cognitive cost. Layered Architecture đơn giản hơn nhưng dễ để coupling lan rộng nếu dependency discipline yếu.

**Middle → Senior insight:**
Middle developer cần hiểu dependency direction và separation of concerns, không chỉ tên project. Senior / Technical developer phải chọn số boundary tối thiểu đủ bảo vệ phần có volatility/risk cao và tránh abstraction không tạo leverage.
