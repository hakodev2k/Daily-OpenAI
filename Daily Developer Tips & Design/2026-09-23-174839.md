# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `ExecuteUpdateAsync` không đồng bộ lại entity đang được track

**Mẹo:**
Dùng `ExecuteUpdateAsync` khi cần update trực tiếp nhiều rows mà không load entity, nhưng hãy nhớ operation này bypass EF Core change tracker. Nếu cùng `DbContext` đang track các entity liên quan, state trong memory có thể trở nên stale.

**Tại sao hữu ích:**
`ExecuteUpdateAsync` dịch update thành SQL trực tiếp nên tránh materialization và per-entity update. Tuy nhiên change tracker không biết database vừa thay đổi; một `SaveChangesAsync` sau đó có thể ghi state cũ trở lại hoặc code tiếp tục ra quyết định trên dữ liệu lỗi thời.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.ExpiresAt < now && x.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```
Với batch job, nên dùng scope/`DbContext` riêng cho bulk operation hoặc reload/clear tracking có chủ đích trước khi tiếp tục xử lý cùng entities.

**Lưu ý:**
Đừng coi bulk update là thay thế mặc định cho domain logic. Nó bỏ qua logic chạy trên entity instance và cần được xem xét kỹ nếu hệ thống phụ thuộc vào concurrency token, domain events hoặc side effects ở application layer.

### Tip 2 — Chống cache stampede bằng single-flight, không chỉ tăng TTL

**Mẹo:**
Khi một hot key hết hạn, giới hạn số request được phép rebuild cache cùng lúc; các request còn lại nên chờ kết quả hoặc dùng stale value theo policy phù hợp.

**Tại sao hữu ích:**
Nếu 1.000 request cùng miss một key, cache-aside thông thường có thể tạo 1.000 query giống nhau xuống database. Database chậm hơn làm request sống lâu hơn, tạo thêm concurrency và biến một cache miss thành cascading failure.

**Ví dụ:**
Một endpoint catalog cache `home:featured-products`. Khi TTL hết, dùng per-key lock/single-flight để một execution đọc database và populate Redis; các execution khác reuse kết quả thay vì cùng rebuild.

**Lưu ý:**
Distributed lock cũng có failure mode: lock timeout, owner chết, stale lock và contention. Đừng dùng một global lock cho mọi key. Với dữ liệu cho phép stale, stale-while-revalidate đôi khi đơn giản và resilient hơn.

### Tip 3 — Rate limit theo đúng identity thay vì chỉ theo IP

**Mẹo:**
Với authenticated API, cân nhắc partitioned rate limiting theo tenant, user, API key hoặc operation thay vì mặc định giới hạn toàn bộ theo client IP.

**Tại sao hữu ích:**
Nhiều user có thể đi qua cùng NAT/proxy nên IP-only limiter gây false throttling; ngược lại attacker có thể phân tán traffic qua nhiều IP. Partition key nên phản ánh resource hoặc fairness boundary thực tế của hệ thống.

**Ví dụ:**
ASP.NET Core có thể partition request theo `TenantId` cho API tạo report đắt tiền, trong khi endpoint public login dùng policy khác. Response `429` cần rõ retry semantics và telemetry phải cho biết partition nào bị throttle.

**Lưu ý:**
Rate limiting không thay thế authorization, quota accounting hay protection ở edge/WAF. Nếu lấy partition key từ header do client tự khai mà không xác thực, client có thể đổi key để né limiter.

### Tip 4 — `git bisect` biến regression hunting thành binary search

**Mẹo:**
Khi biết một commit cũ chạy tốt và HEAD bị regression, dùng `git bisect` để thu hẹp commit gây lỗi thay vì checkout tuần tự hàng chục commit.

**Tại sao hữu ích:**
Bisect chọn commit ở giữa khoảng good/bad nên số lần kiểm tra tăng theo logarithm. Nếu có test/script tái hiện deterministic, `git bisect run` có thể tự động hóa toàn bộ quá trình tìm first bad commit.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
git bisect run dotnet test tests/Regression.Tests
```
Một regression trải qua 128 commits về lý thuyết chỉ cần khoảng 7 bước phân đôi nếu test phân loại commit đáng tin cậy.

**Lưu ý:**
Bisect chỉ tốt bằng reproduction. Flaky test, commit trung gian không build được hoặc thay đổi migration/config có thể làm kết quả sai; dùng `git bisect skip` khi commit không thể phân loại hợp lệ.

### Tip 5 — File upload phải được coi là dữ liệu không tin cậy kể cả khi extension hợp lệ

**Mẹo:**
Validate size, content type/signature theo nhu cầu, tạo server-side filename, lưu ngoài web root và chỉ cấp quyền truy cập theo policy. Với workload phù hợp, scan malware trước khi file được downstream system sử dụng.

**Tại sao hữu ích:**
Tên file và `Content-Type` do client gửi không chứng minh nội dung thật. Lưu trực tiếp `invoice.pdf` theo tên client vào public directory có thể dẫn tới overwrite, path manipulation hoặc phục vụ nội dung nguy hiểm dưới trusted origin.

**Ví dụ:**
API nhận ảnh sản phẩm: enforce size limit, decode/validate định dạng ảnh, sinh object key ngẫu nhiên, lưu Blob Storage private bằng Managed Identity và trả identifier thay vì filesystem path do client kiểm soát.

**Lưu ý:**
Không đọc toàn bộ file lớn vào memory chỉ để validate. Streaming, request limits và timeout cần được thiết kế để tránh memory pressure/DoS; antivirus scan cũng cần failure policy rõ nếu scanner unavailable.

## 🧠 Software Design

### Design 1 — Inbox Pattern xử lý duplicate delivery ở consumer boundary

**Khái niệm:**
Inbox Pattern lưu message identity đã xử lý cùng trạng thái cần thiết để consumer nhận biết redelivery và tránh thực hiện business side effect lần nữa. Nó bổ sung cho at-least-once messaging thay vì giả định broker cung cấp exactly-once business semantics.

**Vấn đề nó giải quyết:**
Consumer có thể commit database rồi crash trước khi acknowledge message. Broker redeliver là hành vi hợp lệ; nếu handler tạo invoice hoặc trừ inventory lần nữa, hệ thống tạo duplicate side effect.

**Ví dụ thực tế:**
Consumer nhận `PaymentCaptured` với `MessageId`. Trong transaction database, nó kiểm tra/insert Inbox record và cập nhật Order. Khi cùng message quay lại, Inbox cho biết operation đã hoàn tất và handler có thể acknowledge mà không apply business change lần hai.

**Trade-off:**
Inbox thêm storage, unique constraint, retention/cleanup và transaction logic. Nếu operation vốn idempotent tự nhiên theo business key, một abstraction Inbox đầy đủ có thể không cần thiết. External side effects ngoài database vẫn cần idempotency strategy riêng.

**Middle → Senior insight:**
Middle developer cần enforce unique message identity và transaction boundary đúng. Senior / Technical developer phải xác định deduplication key, retention window, ordering implications và nơi business idempotency tốt hơn infrastructure deduplication; đồng thời thiết kế recovery khi handler dừng giữa nhiều side effects.

### Design 2 — CQRS chỉ đáng giá khi read/write pressures thực sự khác nhau

**Khái niệm:**
CQRS tách model/path xử lý command khỏi query để mỗi phía có thể tối ưu theo semantics riêng. Nó không bắt buộc microservices, event sourcing hay hai database; mức tách nên phù hợp với pressure thực tế.

**Vấn đề nó giải quyết:**
Một domain phức tạp có write model bảo vệ invariants nhưng read UI cần projection rất khác, nhiều joins hoặc denormalized views. Ép cùng model phục vụ cả hai có thể làm command model bị biến dạng bởi nhu cầu presentation và query trở nên khó tối ưu.

**Ví dụ thực tế:**
Ordering dùng aggregate để kiểm soát transition `Draft → Submitted → Paid`, trong khi dashboard cần query projection theo customer/date/status. Có thể giữ cùng SQL database nhưng tách command handlers và optimized read queries trước khi nghĩ tới read store riêng.

**Trade-off:**
CQRS tăng số model, mapping, code path và cognitive load. Nếu thêm asynchronous projection/read database, hệ thống còn có eventual consistency và operational complexity. CRUD application đơn giản thường không nhận đủ lợi ích để bù chi phí này.

**Middle → Senior insight:**
Middle developer cần hiểu command không phải query trá hình và giữ validation/invariant đúng nơi. Senior / Technical developer phải nhận diện pressure nào thật sự cần separation, chọn mức CQRS tối thiểu, định nghĩa consistency expectation và tránh biến pattern thành framework ceremony.

### Design 3 — Azure Functions và Worker Service khác nhau ở operational model, không chỉ syntax

**Khái niệm:**
Azure Functions phù hợp với event-driven execution được platform quản lý trigger/scale; .NET Worker Service cho process dài hạn với lifecycle và concurrency control chủ động hơn. Cả hai đều xử lý background work nhưng có operational constraints khác nhau.

**Vấn đề nó giải quyết:**
Team cần chọn runtime model cho queue processing, scheduled jobs hoặc integration workload. Chọn chỉ vì “serverless hiện đại hơn” hoặc “Worker dễ code hơn” bỏ qua scale behavior, execution duration, cold start, deployment và ownership.

**Ví dụ thực tế:**
Một Service Bus handler ngắn, stateless và bursty có thể phù hợp Azure Functions. Một pipeline xử lý liên tục cần in-memory coordination, custom backpressure, long-running lifecycle và predictable process behavior có thể phù hợp Worker Service trên App Service/Kubernetes hơn.

**Trade-off:**
Functions giảm infrastructure management và scale thuận tiện nhưng platform/runtime behavior, cold start và hosting-plan constraints cần được hiểu. Worker cho nhiều control hơn nhưng team sở hữu scaling, health, deployment và capacity planning nhiều hơn.

**Middle → Senior insight:**
Middle developer cần implement cancellation, retry, idempotency và graceful shutdown đúng với hosting model. Senior / Technical developer phải so sánh workload shape, latency/SLA, scale pattern, cost, operational maturity và failure recovery trước khi chọn; không để hosting technology quyết định architecture thay cho workload requirements.
