# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `MemoryMarshal.TryGetArray` chỉ khi thật sự cần tối ưu interop với array-backed memory

**Mẹo:**
Khi API nhận `ReadOnlyMemory<T>` nhưng downstream legacy API chỉ nhận `ArraySegment<T>` hoặc raw array, có thể dùng `MemoryMarshal.TryGetArray` để tránh copy nếu memory thực sự backed bởi array.

**Tại sao hữu ích:**
Giúp giảm allocation và copy trên hot path tích hợp với thư viện cũ mà chưa hỗ trợ `Memory<T>`/`Span<T>`.

**Ví dụ:**
```csharp
using System.Runtime.InteropServices;

ReadOnlyMemory<byte> payload = GetPayload();

if (MemoryMarshal.TryGetArray(payload, out ArraySegment<byte> segment))
{
    LegacySend(segment.Array!, segment.Offset, segment.Count);
}
else
{
    LegacySend(payload.ToArray(), 0, payload.Length);
}
```

**Lưu ý:**
Đây là optimization mang tính implementation detail. Không giả định mọi `ReadOnlyMemory<T>` đều backed bởi array; luôn có fallback an toàn.

### Tip 2 — Dùng `SET XACT_ABORT ON` cho transaction SQL Server cần fail-fast khi runtime error xảy ra

**Mẹo:**
Trong stored procedure hoặc migration script có transaction nhiều bước, cân nhắc `SET XACT_ABORT ON` để phần lớn runtime error khiến transaction tự động rollback thay vì để transaction ở trạng thái khó đoán.

**Tại sao hữu ích:**
Giảm nguy cơ script dừng giữa chừng nhưng transaction vẫn mở hoặc một phần thay đổi đã commit logic sai do error handling không đầy đủ.

**Ví dụ:**
```sql
SET XACT_ABORT ON;

BEGIN TRANSACTION;

UPDATE Accounts
SET Balance = Balance - 100
WHERE Id = 1;

UPDATE Accounts
SET Balance = Balance + 100
WHERE Id = 2;

COMMIT;
```

**Lưu ý:**
Vẫn nên dùng `TRY...CATCH` khi cần logging hoặc compensation logic. Không coi `XACT_ABORT` là thay thế cho transaction design và error handling rõ ràng.

### Tip 3 — Dùng `git range-diff` sau rebase để kiểm tra series commit có bị đổi semantics

**Mẹo:**
Sau khi rebase một feature branch dài, dùng `git range-diff` để so sánh series commit cũ và mới thay vì chỉ nhìn final diff.

**Tại sao hữu ích:**
Giúp phát hiện commit nào bị thay đổi, drop, reorder hoặc resolve conflict theo cách làm lệch behavior.

**Ví dụ:**
```bash
git range-diff origin/main...feature-before-rebase \
               origin/main...feature-after-rebase
```

**Lưu ý:**
`range-diff` rất hữu ích với commit series, nhưng không thay thế test. Conflict resolution có thể vẫn tạo bug runtime dù patch nhìn tương đương.

### Tip 4 — Dùng `docker build --progress=plain` để debug layer build bị fail trong CI

**Mẹo:**
Khi Docker BuildKit output bị rút gọn khiến khó thấy command nào fail, chạy build với `--progress=plain` để xem log đầy đủ từng step.

**Tại sao hữu ích:**
Giúp điều tra package restore, certificate, network, permission hoặc script lỗi trong layer build mà không phải chỉnh Dockerfile chỉ để thêm debug output.

**Ví dụ:**
```bash
docker build --progress=plain -t myapp:debug .
```

**Lưu ý:**
Log chi tiết có thể lộ secret nếu Dockerfile hoặc script echo token/credential. Không in secret vào build output; dùng BuildKit secret mount khi cần.

### Tip 5 — Dùng `Task.WaitAsync` để áp deadline cục bộ mà không tự viết `Task.WhenAny`

**Mẹo:**
Khi cần giới hạn thời gian chờ một async operation ở call site, dùng `Task.WaitAsync(...)` thay vì tự dựng `Task.Delay` + `Task.WhenAny`.

**Tại sao hữu ích:**
Code ngắn hơn, intent rõ hơn và giảm lỗi quên xử lý task thua cuộc hoặc cancellation token.

**Ví dụ:**
```csharp
var result = await externalCall
    .WaitAsync(TimeSpan.FromSeconds(3), cancellationToken);
```

**Lưu ý:**
`WaitAsync` chỉ giới hạn thời gian caller chờ. Nếu operation bên dưới không hỗ trợ cancellation, nó có thể vẫn tiếp tục chạy ngầm sau timeout.

## 🧠 Software Design

### Design 1 — Read Repair cho dữ liệu phân tán có replica lệch nhau

**Khái niệm:**
Read Repair là chiến lược phát hiện replica trả dữ liệu cũ trong lúc đọc và đồng thời sửa replica đó bằng version mới hơn.

**Vấn đề nó giải quyết:**
Trong hệ thống replicated với eventual consistency, một node có thể miss update do network partition hoặc replication lag và tiếp tục trả dữ liệu stale.

**Ví dụ thực tế:**
Ba replica trả version `42`, `42`, `39` cho cùng customer profile. Coordinator trả version `42` cho caller và async cập nhật replica version `39` để giảm inconsistency ở lần đọc sau.

**Trade-off:**
Read Repair cải thiện convergence mà không cần block mọi write trên đồng bộ replica, nhưng làm read path phức tạp và có thể tăng latency/write amplification khi nhiều replica stale.

**Middle → Senior insight:**
Middle developer nên hiểu eventual consistency cần cơ chế convergence chứ không chỉ “đợi rồi sẽ đúng”. Senior developer cần chọn giữa read repair, background anti-entropy, quorum read/write và cost của từng chiến lược theo consistency SLA.

### Design 2 — Separate operational database và analytics workload khi query pattern xung đột nhau

**Khái niệm:**
OLTP và analytics thường có workload khác nhau: transactional path cần query nhỏ, latency thấp; analytics cần scan/aggregate dữ liệu lớn. Tách workload giúp mỗi bên tối ưu độc lập.

**Vấn đề nó giải quyết:**
Dashboard/report nặng chạy trên cùng database production có thể chiếm CPU, I/O, memory grant và lock/resource pool, làm request nghiệp vụ chậm theo.

**Ví dụ thực tế:**
Order API ghi vào PostgreSQL primary. CDC hoặc batch replication đẩy dữ liệu sang warehouse/read replica cho BI, dashboard và ad-hoc query thay vì để report scan trực tiếp bảng giao dịch nóng.

**Trade-off:**
Tách workload bảo vệ OLTP và cho phép schema/index phù hợp analytics, nhưng tăng data pipeline, replication lag, cost vận hành và complexity khi đối chiếu số liệu.

**Middle → Senior insight:**
Middle developer nên nhận ra “query đúng” chưa chắc “chạy đúng chỗ”. Senior developer phải đánh giá workload isolation, freshness SLA, source of truth, reconciliation và chi phí trước khi quyết định thêm warehouse/read replica.

### Design 3 — Capability-based permissions tốt hơn role explosion

**Khái niệm:**
Thay vì tạo ngày càng nhiều role cho mọi tổ hợp quyền, hệ thống có thể mô hình hóa permission theo capability/resource action như `Employee.Edit`, `Payroll.Approve`, `Report.Export` rồi gán chúng cho role hoặc policy.

**Vấn đề nó giải quyết:**
Role-based access control dễ bị “role explosion” khi cần các biến thể như HR Viewer, HR Editor, HR Editor Without Salary, Regional HR Approver...

**Ví dụ thực tế:**
User A có các capability:

```text
Employee.Read
Employee.Edit
Leave.Approve
```

User B có:

```text
Employee.Read
Payroll.Read
```

UI và backend cùng dựa trên capability nhưng backend vẫn là nơi enforce bắt buộc.

**Trade-off:**
Capability model linh hoạt và dễ tái sử dụng hơn, nhưng permission catalog có thể phình lớn và khó audit nếu naming/ownership không rõ. Role vẫn hữu ích như bundle quản trị cho người dùng.

**Middle → Senior insight:**
Middle developer nên hiểu role chỉ là một cách nhóm quyền, không phải business rule cuối cùng. Senior developer cần thiết kế permission taxonomy, resource-level checks, inheritance/tenancy và auditability để tránh một hệ thống quyền linh hoạt nhưng không kiểm soát được.
