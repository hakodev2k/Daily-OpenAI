# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CallerArgumentExpression` để guard clause báo đúng expression bị lỗi

**Mẹo:**
Nếu bạn có custom guard/validation helper dùng nhiều nơi, `CallerArgumentExpression` giúp tự lấy expression mà caller truyền vào thay vì bắt developer gõ thêm tên parameter thủ công.

**Tại sao hữu ích:**
Thông báo lỗi rõ hơn, giảm duplicate string và tránh trường hợp rename biến nhưng message/parameter name không được cập nhật.

**Ví dụ:**
```csharp
using System.Runtime.CompilerServices;

public static void NotNull<T>(
    T? value,
    [CallerArgumentExpression(nameof(value))] string? expression = null)
{
    if (value is null)
    {
        throw new ArgumentNullException(expression);
    }
}

NotNull(order.Customer);
```

Exception có thể báo trực tiếp `order.Customer` thay vì một tên hard-code dễ sai.

**Lưu ý:**
Đây là compile-time convenience, không thay thế business validation. Đừng biến guard helper thành framework validation quá generic và khó debug.

### Tip 2 — Với EF Core transaction + retry, dùng `CreateExecutionStrategy()` đúng boundary

**Mẹo:**
Nếu provider bật transient retry và bạn tự mở transaction, hãy chạy toàn transaction bên trong execution strategy để toàn unit-of-work có thể retry đúng cách.

**Tại sao hữu ích:**
Một transaction tự mở bên ngoài retry strategy có thể gây lỗi hoặc khiến retry chỉ chạy lại một command thay vì toàn chuỗi operation cần tính nhất quán.

**Ví dụ:**
```csharp
var strategy = dbContext.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await dbContext.Database.BeginTransactionAsync(cancellationToken);

    await UpdateOrderAsync(dbContext, cancellationToken);
    await InsertAuditAsync(dbContext, cancellationToken);
    await dbContext.SaveChangesAsync(cancellationToken);

    await transaction.CommitAsync(cancellationToken);
});
```

**Lưu ý:**
Retry toàn transaction chỉ an toàn khi side effect bên ngoài database cũng được thiết kế idempotent hoặc nằm ngoài retry scope phù hợp. Không gửi email/payment trực tiếp bên trong block rồi mong retry “tự đúng”.

### Tip 3 — Dùng `git merge-base` để biết hai branch thật sự tách nhau từ đâu

**Mẹo:**
Khi điều tra diff giữa hai branch dài ngày, dùng `git merge-base` để tìm common ancestor thay vì đoán commit base bằng mắt.

**Tại sao hữu ích:**
Giúp review đúng range, hiểu divergence và tạo diff phù hợp khi branch đã merge/rebase nhiều lần.

**Ví dụ:**
```bash
git merge-base main feature/payment
```

Sau đó:

```bash
BASE=$(git merge-base main feature/payment)
git diff $BASE..feature/payment
```

**Lưu ý:**
Sau rebase, common ancestor có thể khác lịch sử trước đó. `merge-base` cho topology hiện tại, không phải lịch sử logic trước khi rewrite.

### Tip 4 — Dùng `lsof +L1` khi disk đầy nhưng `du` không thấy file lớn

**Mẹo:**
Trên Linux, nếu filesystem gần đầy nhưng `du` không giải thích được, kiểm tra file đã bị xóa khỏi directory nhưng vẫn đang được process giữ open bằng `lsof +L1`.

**Tại sao hữu ích:**
File log lớn có thể đã `rm` nhưng process chưa đóng file descriptor, nên disk space chưa được giải phóng dù file không còn xuất hiện trong filesystem tree.

**Ví dụ:**
```bash
sudo lsof +L1
```

Output có thể cho thấy một process vẫn giữ file `(deleted)` hàng chục GB.

**Lưu ý:**
Đừng kill process ngay nếu chưa hiểu impact. Có thể cần graceful restart hoặc rotate/reopen log đúng cách để giải phóng descriptor an toàn.

### Tip 5 — Dùng `curl --resolve` để test endpoint với IP cụ thể nhưng vẫn giữ Host/SNI đúng

**Mẹo:**
Khi nghi DNS đang route sai hoặc muốn test một backend node trước cutover, dùng `curl --resolve` để ép domain trỏ tới IP cụ thể trong request đó.

**Tại sao hữu ích:**
Khác với gọi trực tiếp IP, `--resolve` vẫn giữ hostname trong HTTP `Host` header và TLS SNI, nên phù hợp để test HTTPS virtual host/certificate thực tế.

**Ví dụ:**
```bash
curl -v \
  --resolve api.example.com:443:203.0.113.20 \
  https://api.example.com/health
```

**Lưu ý:**
Kết quả chỉ chứng minh route tới IP đó hoạt động từ máy đang test. Nó không phản ánh DNS caching, load balancer behavior hoặc traffic path của user khác.

## 🧠 Software Design

### Design 1 — Error Budget biến reliability thành quyết định kỹ thuật có thể cân bằng

**Khái niệm:**
Error Budget là phần “được phép không đạt” còn lại từ SLO. Nếu SLO availability là 99.9%, hệ thống có khoảng 0.1% budget cho failure/unavailability trong window đã định nghĩa.

**Vấn đề nó giải quyết:**
Không có error budget, team thường tranh luận cảm tính giữa “ship feature nhanh” và “đầu tư reliability”. Một phía muốn zero failure tuyệt đối, phía kia lại chấp nhận quá nhiều risk.

**Ví dụ thực tế:**
Một API có SLO 99.9% theo tháng. Nếu nửa đầu tháng đã tiêu gần hết error budget vì incident, team có thể tạm dừng risky rollout, ưu tiên fix retry storm, dependency timeout hoặc capacity issue trước khi tiếp tục feature lớn.

**Trade-off:**
Error budget giúp quyết định dựa trên dữ liệu và gắn engineering work với SLO, nhưng chỉ có giá trị khi metric/SLO phản ánh đúng trải nghiệm user. SLO đặt sai sẽ tạo behavior tối ưu sai mục tiêu.

**Middle → Senior insight:**
Middle developer nên hiểu reliability không đồng nghĩa “không bao giờ lỗi”. Senior developer phải chọn SLI/SLO đúng business outcome, theo dõi burn rate và dùng budget để điều chỉnh release velocity, không chỉ làm dashboard cho đẹp.

### Design 2 — Compensation phải đảo ngược business effect, không phải giả lập database rollback

**Khái niệm:**
Trong workflow phân tán, compensation là một business action mới nhằm trung hòa effect của bước đã hoàn tất, không phải quay ngược thời gian như rollback transaction cục bộ.

**Vấn đề nó giải quyết:**
Một bước đã gọi external system thành công thì transaction database của service hiện tại không thể tự rollback effect đó. Workflow cần hành động bù có semantics nghiệp vụ rõ ràng.

**Ví dụ thực tế:**
Flow booking:

```text
Reserve room → Charge card → Create booking
```

Nếu `Create booking` thất bại sau khi charge thành công, compensation có thể là `Refund payment` và `Release room`. Đây là các operation thật, có thể fail và cần retry riêng.

**Trade-off:**
Compensation giúp workflow recover mà không cần distributed transaction, nhưng thêm state machine, failure path và business complexity. Một số effect không thể đảo ngược hoàn toàn, ví dụ email đã gửi hoặc notification user đã thấy.

**Middle → Senior insight:**
Middle developer nên hiểu compensation không phải `DELETE` record vừa tạo. Senior developer phải định nghĩa semantic inverse, partial compensation, retry/idempotency và trạng thái cuối cùng khi compensation cũng thất bại.

### Design 3 — Shared Kernel chỉ nên tồn tại khi shared model thật sự ổn định

**Khái niệm:**
Trong DDD, Shared Kernel là một phần model/code được nhiều bounded context dùng chung có chủ đích. Nó tạo coupling được chấp nhận để tránh duplicate một khái niệm thực sự giống nhau.

**Vấn đề nó giải quyết:**
Hai context đôi khi cùng cần một khái niệm rất ổn định như `Money`, `CountryCode` hoặc một contract nhỏ. Duplicate hoàn toàn có thể tạo inconsistency không cần thiết.

**Ví dụ thực tế:**
`Payroll` và `Billing` cùng dùng value object `Money` với currency + amount và cùng rule rounding chuẩn của công ty. Một package nhỏ, versioned rõ có thể hợp lý hơn việc mỗi context tự triển khai khác nhau.

**Trade-off:**
Giảm duplication và giữ semantics nhất quán, nhưng mọi thay đổi shared kernel có thể ảnh hưởng nhiều context cùng lúc. Shared kernel lớn rất dễ biến thành “common” project chứa mọi thứ và phá bounded context autonomy.

**Middle → Senior insight:**
Middle developer nên tránh nhét code vào `Shared` chỉ vì hai nơi đang dùng giống nhau. Senior developer phải đánh giá semantic stability, ownership, versioning và chi phí coordination trước khi chấp nhận coupling qua shared kernel.
