# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng source-generated JSON serialization khi hot path bị giới hạn bởi reflection và startup cost

**Mẹo:**
Với ASP.NET Core hoặc worker phải serialize/deserialize DTO rất thường xuyên, cân nhắc `System.Text.Json` source generation cho các contract ổn định thay vì luôn dựa vào reflection metadata ở runtime.

**Tại sao hữu ích:**
Source generation tạo serialization metadata khi build, nhờ đó giảm một phần runtime reflection, startup work và có thể phù hợp hơn với Native AOT hoặc workload nhạy với allocation/latency. Giá trị lớn nhất xuất hiện khi serialization thực sự nằm trên hot path đã được đo.

**Ví dụ:**
```csharp
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(List<OrderDto>))]
internal partial class ApiJsonContext : JsonSerializerContext;

var json = JsonSerializer.Serialize(order, ApiJsonContext.Default.OrderDto);
```

Trong ASP.NET Core, có thể đăng ký context vào `JsonOptions` thay vì gọi trực tiếp từng nơi.

**Lưu ý:**
Đừng chuyển toàn bộ codebase sang source generation chỉ vì “nhanh hơn”. Contract dynamic, polymorphism phức tạp hoặc plugin model có thể làm cấu hình khó hơn. Hãy benchmark throughput/startup trước khi tăng maintenance cost.

### Tip 2 — Dùng `SET TRANSACTION ISOLATION LEVEL` có chủ đích khi điều tra blocking, không đổi isolation theo cảm tính

**Mẹo:**
Khi SQL Server có blocking hoặc inconsistent read, xác định isolation level hiện tại, loại lock đang giữ và invariant cần bảo vệ trước khi chuyển sang `READ COMMITTED SNAPSHOT`, `SNAPSHOT` hoặc mức mạnh hơn.

**Tại sao hữu ích:**
Isolation level quyết định cách transaction nhìn dữ liệu đồng thời và mức độ dùng lock/versioning. Một thay đổi có thể giảm read/write blocking nhưng tăng `tempdb` version-store usage hoặc thay semantics mà application đang vô tình dựa vào.

**Ví dụ:**
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;

SELECT Id
FROM Inventory
WHERE Sku = @Sku;

-- critical update
COMMIT;
```

Nếu mục tiêu chỉ là giảm reader chặn writer trên workload read-heavy, database-level `READ_COMMITTED_SNAPSHOT` có thể phù hợp hơn so với nâng từng transaction lên `SERIALIZABLE`.

**Lưu ý:**
Không coi `NOLOCK` là “performance switch”. Dirty read, missing row hoặc duplicate row có thể xuất hiện. Isolation phải được chọn theo consistency requirement và đo bằng lock waits, blocking chain, version-store pressure và transaction duration.

### Tip 3 — Với Elasticsearch, dùng `filter` cho điều kiện không cần relevance score

**Mẹo:**
Trong Elasticsearch, đưa điều kiện như tenant, status, category hoặc date boundary vào `bool.filter` thay vì `must` nếu chúng chỉ là điều kiện đúng/sai và không cần ảnh hưởng `_score`.

**Tại sao hữu ích:**
Filter context bỏ qua scoring và có thể tận dụng caching/optimization tốt hơn cho điều kiện lặp lại. Điều này giúp query intent rõ hơn: full-text clause quyết định relevance, còn filter chỉ thu hẹp tập document.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "azure architecture" } }
      ],
      "filter": [
        { "term": { "tenantId": "tenant-42" } },
        { "term": { "status": "published" } }
      ]
    }
  }
}
```

Cách tách này cũng giúp phân tích query profile dễ hơn khi relevance bất thường.

**Lưu ý:**
Đừng mặc định mọi `term` đều nên cache hoặc mọi filter đều rẻ. High-cardinality field, script query hoặc mapping sai vẫn có thể tốn CPU/memory. Kiểm tra mapping và dùng Profile API khi search latency tăng.

### Tip 4 — Trong Kubernetes, đặt `requests` và `limits` dựa trên telemetry thay vì copy template

**Mẹo:**
Khi deploy ASP.NET Core container lên Kubernetes, chọn CPU/memory `requests` và `limits` từ usage percentile và behavior thực tế, không copy cùng một con số cho mọi service.

**Tại sao hữu ích:**
Scheduler dùng `requests` để bố trí Pod; `limits` quyết định trần resource. Request quá cao làm cluster kém sử dụng, request quá thấp gây contention; memory limit quá thấp dẫn tới OOMKill, còn CPU limit thấp có thể tạo throttling và latency spike dù node vẫn còn CPU.

**Ví dụ:**
```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Sau rollout, correlate CPU throttling, working set, GC metrics và p95/p99 latency trước khi điều chỉnh.

**Lưu ý:**
Không chỉ nhìn average usage. Memory burst, startup spike và traffic burst quan trọng hơn trung bình. Với .NET, memory limit cũng ảnh hưởng behavior của GC trong container, nên cần test dưới production-like load.

### Tip 5 — Khi dùng AI coding agent, bắt agent trích nguồn từ repo trước khi sửa API contract

**Mẹo:**
Nếu yêu cầu AI sửa endpoint, DTO hoặc integration contract, trước tiên buộc nó xác định controller/handler hiện tại, consumer, OpenAPI/schema và test liên quan trong repository rồi mới đề xuất patch.

**Tại sao hữu ích:**
Agent thường sinh code hợp lý cục bộ nhưng bỏ qua hidden contract: mobile app vẫn dùng field cũ, serializer option khác môi trường, hoặc integration test đang bảo vệ behavior legacy. Grounding vào source làm giảm hallucinated assumption và accidental breaking change.

**Ví dụ:**
```text
Yêu cầu agent:
1. Tìm tất cả consumer của UpdateCustomerRequest.
2. Tìm OpenAPI/schema và contract test liên quan.
3. Liệt kê breaking-change risk.
4. Chỉ sau đó mới tạo patch.
```

Một review tốt nên kiểm tra diff, test behavior và generated SQL/HTTP contract thay vì chỉ nhìn code compile.

**Lưu ý:**
Repo grounding không đảm bảo agent đúng. Dynamic usage, reflection, external consumer hoặc runtime config có thể không xuất hiện trong static search. Human review và integration/contract test vẫn là quality gate bắt buộc.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service: chọn theo execution model, không theo mức độ “serverless”

**Khái niệm:**
Azure Functions phù hợp với event-triggered execution có lifecycle do platform quản lý; Worker Service phù hợp khi bạn cần process sống lâu, control loop rõ, custom concurrency hoặc dependency/lifecycle phức tạp hơn.

**Vấn đề nó giải quyết:**
Team thường chọn Functions chỉ vì có queue trigger, hoặc chọn Worker chỉ vì quen .NET. Nhưng workload khác nhau về startup sensitivity, execution duration, scaling model, retry semantics và operational control.

**Ví dụ thực tế:**
```text
Image thumbnail generation:
- mỗi message độc lập
- burst traffic
- execution ngắn
-> Azure Functions phù hợp

Market-data processor:
- kết nối lâu dài
- state/cache trong process
- cần custom backpressure + graceful shutdown
-> Worker Service phù hợp hơn
```

Cả hai đều có thể đọc Azure Service Bus; khác biệt nằm ở runtime ownership và failure model.

**Trade-off:**
Functions giảm operational burden và scale theo trigger, nhưng có platform constraints, cold-start/hosting considerations và ít control hơn. Worker Service linh hoạt hơn nhưng bạn phải tự vận hành scaling, health, deployment và resource sizing.

**Middle → Senior insight:**
Middle developer cần hiểu trigger/retry/lifecycle của từng hosting model. Senior / Technical developer phải chọn dựa trên workload duration, burstiness, statefulness, latency SLO, concurrency control, cost và operational ownership — không dựa trên buzzword.

### Design 2 — Contract Testing hữu ích nhất ở integration boundary có team hoặc release cadence độc lập

**Khái niệm:**
Contract Testing xác minh producer và consumer cùng tuân thủ một interface kỳ vọng mà không cần luôn chạy full end-to-end environment. Nó đặc biệt hữu ích khi hai service được phát hành độc lập.

**Vấn đề nó giải quyết:**
Một API có thể vẫn pass unit/integration test nội bộ nhưng vô tình đổi field, status code hoặc enum semantics làm consumer khác hỏng sau deployment. Full E2E thường chậm, brittle và khó bao phủ mọi consumer combination.

**Ví dụ thực tế:**
```text
Consumer expectation:
GET /customers/{id}
200
{
  "id": "...",
  "status": "active"
}

Producer pipeline:
- verify implementation vẫn thỏa contract consumer đã publish
- block release nếu response trở thành `state` hoặc enum đổi semantics
```

Contract test có thể áp dụng cả synchronous HTTP lẫn message schema/event contract.

**Trade-off:**
Contract Testing giảm integration regression và cho phép deploy độc lập hơn, nhưng thêm artifact/version management và không thay thế test end-to-end cho workflow thật. Contract quá chi tiết có thể khóa implementation và làm evolution khó hơn.

**Middle → Senior insight:**
Middle developer cần phân biệt behavior contract với implementation detail. Senior / Technical developer phải quyết định boundary nào đáng có contract test, ai sở hữu compatibility policy, cách deprecate version và làm sao tránh biến contract suite thành coupling mới.

### Design 3 — Graceful Degradation cần định nghĩa trước feature nào fail-open, feature nào fail-closed

**Khái niệm:**
Graceful Degradation cho phép hệ thống tiếp tục cung cấp phần giá trị cốt lõi khi dependency phụ bị lỗi. Tuy nhiên behavior phải được xác định theo business/security semantics: một số chức năng có thể bỏ qua, một số bắt buộc phải dừng.

**Vấn đề nó giải quyết:**
Nếu Recommendation API, review service hoặc analytics backend hỏng, việc làm toàn bộ checkout/page fail có thể không hợp lý. Nhưng nếu authorization, fraud check hoặc pricing source critical bị lỗi, “bỏ qua cho chạy tiếp” có thể gây hậu quả nghiêm trọng.

**Ví dụ thực tế:**
```text
Product page:
- Recommendation API timeout
-> ẩn recommendation, vẫn render product

Checkout:
- Authorization service unavailable
-> fail closed, không cho phép action nhạy cảm

Analytics event publish lỗi
-> buffer/retry async, không chặn user request nếu business cho phép
```

Điểm quan trọng là dependency criticality phải được mô hình hóa chứ không xử lý ad-hoc trong catch block.

**Trade-off:**
Graceful Degradation tăng availability và giảm blast radius, nhưng tạo nhiều trạng thái degraded phải test, monitor và support. Fail-open có thể gây security/data-quality risk; fail-closed có thể làm giảm availability không cần thiết nếu dependency chỉ là phụ trợ.

**Middle → Senior insight:**
Middle developer cần implement fallback rõ ràng, timeout và telemetry cho degraded path. Senior / Technical developer phải phân loại dependency theo criticality, xác định fail-open/fail-closed, freshness budget, fallback data source và SLO cho từng user journey thay vì chỉ tối ưu uptime tổng thể.
