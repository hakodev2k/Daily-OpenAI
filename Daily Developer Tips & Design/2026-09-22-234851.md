# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi allocation trước khi tối ưu GC trong .NET

**Mẹo:**
Khi API .NET có latency spike hoặc CPU tăng do GC, hãy đo allocation rate, Gen 0/1/2 collections và Large Object Heap (LOH) trước khi chỉnh GC mode hay pool mọi thứ. Tìm allocation hotspot bằng `dotnet-counters`, `dotnet-trace` hoặc profiler rồi tối ưu đúng đường nóng.

**Tại sao hữu ích:**
GC cost phụ thuộc lượng object được cấp phát, lifetime và generation. Những buffer lớn, JSON payload hoặc `byte[]` trên khoảng LOH có thể tạo áp lực memory khác hẳn nhiều object nhỏ sống ngắn. Chuyển sang Server GC hay tăng heap limit không sửa được nguyên nhân nếu application liên tục tạo dữ liệu tạm không cần thiết.

**Ví dụ:**
Endpoint export tạo nhiều `byte[]` lớn để ghép file trước khi trả response. Metrics cho thấy allocation rate và Gen 2/LOH tăng mạnh theo request. Thay vì chỉ tăng memory container, có thể stream output, tránh materialize toàn bộ file hoặc dùng pooling có kiểm soát cho buffer phù hợp.

**Lưu ý:**
Pooling không miễn phí: buffer giữ lại làm tăng retained memory, dữ liệu nhạy cảm có thể còn trong buffer, và object pool sai kích thước có thể làm memory footprint tệ hơn. Chỉ tối ưu sau khi có measurement và benchmark representative.

### Tip 2 — SQL execution plan phải được đọc cùng cardinality estimate

**Mẹo:**
Khi SQL query chậm, đừng chỉ nhìn xem index có được dùng hay không. So sánh Estimated Rows với Actual Rows tại các operator quan trọng để phát hiện cardinality estimation sai dẫn tới join strategy, memory grant hoặc access path không phù hợp.

**Tại sao hữu ích:**
Optimizer chọn plan dựa trên số row nó dự đoán. Nếu dự đoán vài chục rows nhưng thực tế hàng triệu rows, Nested Loops hợp lý trên estimate có thể trở thành cực đắt; memory grant quá nhỏ cũng có thể làm sort/hash spill xuống tempdb.

**Ví dụ:**
Query lọc `TenantId`, `Status` và khoảng ngày có Estimated Rows = 50 nhưng Actual Rows = 800,000. Thay vì lập tức thêm index mới, kiểm tra statistics, data skew, parameter sensitivity và predicate trước. Có thể vấn đề nằm ở distribution của một tenant lớn chứ không phải thiếu index chung.

**Lưu ý:**
Không dùng một execution plan duy nhất để kết luận cho mọi parameter. Workload có data skew mạnh có thể tạo plan tốt cho tenant nhỏ nhưng xấu cho tenant lớn; cần xem Query Store/runtime stats và nhiều parameter representative trước khi chọn remediation.

### Tip 3 — Idempotency key phải gắn với request semantics, không chỉ cache response

**Mẹo:**
Với POST tạo payment/order hoặc operation có side effect, nhận một `Idempotency-Key`, lưu trạng thái xử lý cùng fingerprint của request và đảm bảo cùng key không thể tạo side effect lần hai.

**Tại sao hữu ích:**
Client có thể timeout sau khi server đã commit rồi retry vì không biết request đầu thành công hay chưa. Nếu endpoint không idempotent, retry hợp lệ ở tầng transport có thể tạo hai order hoặc charge hai lần.

**Ví dụ:**
`POST /payments` nhận key `checkout-123-attempt-1`. Server lưu key + hash của payload + payment result trong durable store. Retry cùng key và cùng payload trả lại kết quả cũ; cùng key nhưng payload khác bị reject vì đó không còn là cùng operation.

**Lưu ý:**
Một dictionary/cache in-memory không đủ cho multi-instance hoặc process restart. Cần unique constraint/atomic claim, retention policy và behavior rõ cho trạng thái `Processing`, `Succeeded`, `Failed`. Không giữ key mãi nếu business không yêu cầu.

### Tip 4 — Dùng `git bisect` để thu hẹp regression thay vì đọc commit bằng mắt

**Mẹo:**
Khi biết một phiên bản cũ chạy đúng và phiên bản mới bị regression, dùng `git bisect` để binary-search commit gây lỗi; nếu có test/script tái hiện ổn định, có thể dùng `git bisect run` để tự động hóa việc phân loại good/bad.

**Tại sao hữu ích:**
Với hàng trăm commit, kiểm tra tuần tự tốn thời gian và dễ bỏ sót. Binary search giảm số lần checkout/test xuống khoảng log2(N), biến debugging lịch sử thành quy trình có bằng chứng thay vì đoán commit đáng ngờ từ message.

**Ví dụ:**
Một integration test bắt đầu fail đâu đó trong 256 commits gần nhất. Đánh dấu release cũ là `good`, HEAD là `bad`, rồi để bisect chọn midpoint. Trong trường hợp lý tưởng chỉ khoảng 8 vòng test đã thu hẹp được first bad commit.

**Lưu ý:**
Bisect chỉ đáng tin khi test phân loại deterministic. Nếu build ở commit trung gian không chạy được, dùng `git bisect skip` có chủ đích; flaky test có thể khiến bisect chỉ thẳng vào commit vô tội.

### Tip 5 — Redis distributed lock cần ownership token và atomic release

**Mẹo:**
Nếu buộc phải dùng Redis lock, lưu một random ownership token bằng atomic acquire có TTL và chỉ release lock khi token hiện tại vẫn thuộc owner đó, thường bằng một atomic server-side operation/script.

**Tại sao hữu ích:**
Pattern `SETNX` rồi `DEL` đơn giản có race: worker A giữ lock nhưng bị pause quá TTL; worker B acquire lock mới; A tỉnh lại và `DEL` key, vô tình xóa lock của B. Ownership token ngăn owner cũ release lease mới của process khác.

**Ví dụ:**
Worker A `SET job:42 <uuid-A> NX PX 30000`. Khi hoàn tất, operation release chỉ xóa key nếu value vẫn bằng `<uuid-A>`. Nếu lease đã hết và B đã ghi `<uuid-B>`, A không được phép xóa key.

**Lưu ý:**
Distributed lock không tự biến workflow thành exactly-once. Process có thể tiếp tục side effect sau khi lease hết, clock/network/process pause tạo nhiều failure mode, và một lock không bảo vệ external system nếu không có fencing/idempotency phù hợp. Ưu tiên database constraint hoặc business-level idempotency khi chúng giải quyết được invariant trực tiếp.

## 🧠 Software Design

### Design 1 — Rate Limiting là admission control, không chỉ chống abuse

**Khái niệm:**
Rate Limiting giới hạn số request/work được nhận theo một policy như fixed window, sliding window, token bucket hoặc concurrency limit. Trong backend production, nó còn là cơ chế bảo vệ capacity và latency SLO khi demand vượt khả năng xử lý.

**Vấn đề nó giải quyết:**
Nếu application nhận vô hạn work rồi xếp hàng nội bộ, overload có thể làm latency tăng, connection pool cạn và timeout lan sang dependency. Rate limit cho phép từ chối sớm một phần traffic để phần được chấp nhận vẫn có cơ hội hoàn thành trong budget.

**Ví dụ thực tế:**
Public API cho mỗi API key một token bucket để hấp thụ burst nhỏ nhưng giới hạn sustained rate. Đồng thời endpoint gọi một dependency đắt có concurrency limit riêng; khi capacity đầy, API trả `429 Too Many Requests` cùng retry guidance thay vì tạo thêm hàng nghìn operation đang chờ.

**Trade-off:**
Policy quá chặt làm mất throughput và ảnh hưởng user hợp lệ; policy global có thể để một tenant lớn chiếm hết quota. Distributed rate limiter còn cần consistency, partitioning và failure behavior rõ. `429` cũng phải đi cùng client retry/backoff hợp lý để tránh retry storm.

**Middle → Senior insight:**
Middle developer cần hiểu middleware/policy, status code và client retry semantics. Senior / Technical developer phải xác định quota theo tenant/endpoint/cost, chọn algorithm theo burst profile, liên kết admission control với downstream capacity và theo dõi rejected rate, queue time, saturation để tuning bằng dữ liệu.

### Design 2 — CQRS chỉ đáng dùng khi read và write thật sự có nhu cầu khác nhau

**Khái niệm:**
Command Query Responsibility Segregation (CQRS) tách model/path thay đổi state khỏi model/path đọc dữ liệu. Mức tách có thể chỉ ở application code hoặc đi xa tới read store riêng được cập nhật bất đồng bộ.

**Vấn đề nó giải quyết:**
Một domain write model giàu invariant thường không phải representation tốt nhất cho dashboard/search/read-heavy API. Ngược lại, ép mọi query đi qua aggregate và object graph phục vụ write có thể tạo query phức tạp, coupling và chi phí không cần thiết.

**Ví dụ thực tế:**
Ordering dùng aggregate để enforce transition `Pending -> Paid -> Shipped`, còn màn hình operations cần bảng phẳng kết hợp order, customer summary và shipment status để filter nhanh. Read model có thể được projection thành schema tối ưu riêng cho truy vấn thay vì bắt write aggregate phục vụ mọi UI query.

**Trade-off:**
Nếu tách store, CQRS đưa vào eventual consistency, projection rebuild, duplicate/out-of-order event và observability mới. Với CRUD application nhỏ, hai model có thể chỉ nhân đôi code mà không đem lại lợi ích. CQRS cũng không đồng nghĩa bắt buộc phải dùng Event Sourcing.

**Middle → Senior insight:**
Middle developer cần phân biệt command thay đổi state với query không có side effect và tránh business rule bị copy vào read path. Senior / Technical developer phải chứng minh nhu cầu bằng domain/read profile, chọn mức separation tối thiểu cần thiết, định nghĩa consistency expectation cho UI và thiết kế replay/recovery cho projection nếu dùng asynchronous read store.

### Design 3 — Strangler Fig Pattern giúp thay legacy theo lát cắt có thể kiểm soát

**Khái niệm:**
Strangler Fig Pattern thay hệ thống legacy dần dần bằng cách đặt một routing/facade boundary phía trước, chuyển từng capability hoặc traffic slice sang implementation mới cho tới khi phần cũ không còn được dùng.

**Vấn đề nó giải quyết:**
Big-bang rewrite có khoảng thời gian dài không tạo business value và rủi ro cao vì team phải tái hiện nhiều behavior ẩn cùng lúc. Migration theo lát cắt cho phép release, quan sát và rollback từng phần nhỏ trong khi hệ thống cũ vẫn phục vụ phần chưa chuyển.

**Ví dụ thực tế:**
Một ASP.NET Framework monolith có `/catalog`, `/orders`, `/customers`. Team trước tiên route read-only `/catalog` sang ASP.NET Core service mới qua gateway, giữ orders/customers ở legacy. Sau khi parity và telemetry đạt yêu cầu, tiếp tục chuyển write path và capability kế tiếp.

**Trade-off:**
Trong giai đoạn chuyển tiếp phải vận hành cả hai hệ thống, routing phức tạp hơn và data ownership dễ bị nhập nhằng. Nếu code mới vẫn đọc/ghi trực tiếp schema legacy tùy tiện, migration có thể tạo distributed monolith thay vì giảm coupling.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility, test regression và instrumentation ở từng migrated slice. Senior / Technical developer phải chọn seam có giá trị, lập kế hoạch data migration/ownership, shadow/dual-read khi cần, đặt rollback criteria và có exit plan rõ để legacy thật sự được retire thay vì tồn tại vĩnh viễn.
