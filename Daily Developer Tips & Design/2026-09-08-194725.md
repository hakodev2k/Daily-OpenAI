# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `dotnet-counters` để phân biệt GC pressure với ThreadPool starvation

**Mẹo:**
Khi API .NET đột nhiên chậm hoặc CPU tăng, dùng `dotnet-counters` để xem nhanh GC heap size, allocation rate, exception rate, ThreadPool queue length và thread count trước khi đọc log theo cảm tính.

**Tại sao hữu ích:**
Hai incident đều có thể biểu hiện bằng latency tăng nhưng cơ chế khác nhau. Allocation rate cao và Gen 2 GC tăng gợi ý memory pressure; ThreadPool queue length tăng trong khi CPU chưa bão hòa lại nghiêng về blocking hoặc starvation. Counter giúp thu hẹp hypothesis trước khi profile sâu hơn.

**Ví dụ:**
```bash
dotnet-counters monitor \
  --process-id 1234 \
  System.Runtime Microsoft.AspNetCore.Hosting
```

Nếu thấy:
```text
ThreadPool Queue Length: tăng liên tục
ThreadPool Thread Count: tăng chậm
CPU Usage: 35%
```

hãy điều tra sync-over-async, blocking I/O hoặc lock contention thay vì tối ưu GC ngay lập tức.

**Lưu ý:**
Counters chỉ cho signal tổng quan, không chỉ ra chính xác method gây lỗi. Sau khi có hypothesis, dùng trace/profiler như `dotnet-trace`, PerfView hoặc Application Insights để xác nhận root cause.

### Tip 2 — Với EF Core, tránh `Include()` khi endpoint chỉ cần aggregate hoặc vài field liên quan

**Mẹo:**
Nếu endpoint chỉ cần số lượng, tổng tiền hoặc một vài field từ navigation, hãy để database tính qua projection thay vì `Include()` toàn bộ collection rồi aggregate trong memory.

**Tại sao hữu ích:**
`Include()` trên collection lớn có thể tạo result set phình to do join duplication, tăng network transfer và materialization cost. Database vốn tối ưu tốt cho `COUNT`, `SUM`, `EXISTS` và projection có chọn lọc.

**Ví dụ:**
Thay vì:
```csharp
var order = await db.Orders
    .Include(x => x.Items)
    .SingleAsync(x => x.Id == id);

var totalQty = order.Items.Sum(x => x.Quantity);
```

Dùng:
```csharp
var result = await db.Orders
    .Where(x => x.Id == id)
    .Select(x => new
    {
        x.Id,
        TotalQty = x.Items.Sum(i => i.Quantity)
    })
    .SingleAsync(cancellationToken);
```

**Lưu ý:**
Đừng mặc định projection luôn nhanh hơn trong mọi trường hợp. Hãy kiểm tra SQL được sinh, execution plan và số round trip. Nếu thực sự cần aggregate đầy đủ để update domain state, load entity có thể vẫn đúng.

### Tip 3 — Trong Elasticsearch, dùng filter cho điều kiện không cần relevance scoring

**Mẹo:**
Với điều kiện chính xác như `status`, `tenantId`, `categoryId`, range hoặc permission constraint, đặt chúng vào filter context thay vì query context nếu không cần ảnh hưởng `_score`.

**Tại sao hữu ích:**
Filter chỉ quyết định document có match hay không và thường có thể được tối ưu/cached tốt hơn. Query context phải tính relevance score, tạo overhead không cần thiết cho điều kiện mang tính boolean.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "wireless keyboard" } }
      ],
      "filter": [
        { "term": { "status": "active" } },
        { "term": { "tenantId": "t-42" } },
        { "range": { "price": { "lte": 100 } } }
      ]
    }
  }
}
```

`match` phục vụ relevance; `term/range` chỉ giới hạn tập document.

**Lưu ý:**
Đừng dùng `term` cho analyzed text field rồi ngạc nhiên vì không match. Cần hiểu mapping, analyzer và `.keyword` field trước khi tối ưu query shape.

### Tip 4 — Với Azure Blob Storage, ưu tiên direct upload bằng SAS ngắn hạn cho file lớn

**Mẹo:**
Nếu browser/mobile upload file lớn lên Azure Blob Storage, cân nhắc cấp SAS có scope hẹp và thời hạn ngắn để client upload trực tiếp thay vì proxy toàn bộ payload qua ASP.NET Core backend.

**Tại sao hữu ích:**
Backend proxy khiến application phải chịu bandwidth, connection duration và memory/network pressure cho traffic mà Blob Storage có thể nhận trực tiếp. Direct upload giảm tải compute và thường scale tốt hơn.

**Ví dụ:**
Flow điển hình:
```text
Client -> API: xin upload permission
API -> tạo SAS chỉ cho blob đích, quyền Write/Create, TTL 10 phút
Client -> Blob Storage: upload trực tiếp
Client -> API: báo hoàn tất / tạo metadata record
```

Backend vẫn kiểm soát filename logic, ownership và metadata trước khi cấp permission.

**Lưu ý:**
Không cấp SAS quá rộng như container-level write lâu dài. Cần giới hạn resource, permission, expiry và nếu cần content type/size policy. File upload vẫn phải có malware scanning hoặc quarantine workflow nếu business yêu cầu.

### Tip 5 — Khi sửa bug bằng AI coding agent, yêu cầu regression test theo behavior chứ không theo implementation

**Mẹo:**
Khi agent tạo test cho bug fix, mô tả behavior bị lỗi và expected outcome thay vì chỉ yêu cầu “test method X”. Sau đó review để chắc test fail trước fix và pass sau fix.

**Tại sao hữu ích:**
AI thường tạo test bám sát implementation hiện tại, ví dụ mock đúng internal call sequence. Test như vậy có thể xanh dù bug business vẫn tồn tại và sẽ cản trở refactor vô ích.

**Ví dụ:**
Tốt hơn:
```text
Reproduce this bug: submitting the same payment command twice with the same idempotency key must create exactly one payment record.
Add a regression test that fails on the current code.
Do not assert private method calls; assert observable database/API behavior.
```

**Lưu ý:**
Đừng tin test chỉ vì agent báo “all tests pass”. Kiểm tra test setup, assertion, concurrency condition và chạy suite thật. Với race condition, có thể cần integration test thay vì unit test thuần mock.

## 🧠 Software Design

### Design 1 — Idempotency Key cho API tạo side effect

**Khái niệm:**
Idempotency Key cho phép client retry một operation tạo side effect mà server vẫn nhận diện đó là cùng một logical request. Server lưu trạng thái/kết quả theo key và tránh xử lý business action lần thứ hai.

**Vấn đề nó giải quyết:**
Client có thể timeout sau khi server đã tạo payment/order nhưng trước khi nhận response. Nếu client retry `POST` mà server không có cơ chế deduplicate, cùng một hành động có thể xảy ra hai lần.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: 7f4d...
```

Server:
```text
key chưa có -> reserve key -> xử lý payment -> lưu response
key đã hoàn tất -> trả lại response cũ
key đang xử lý -> trả trạng thái phù hợp hoặc chờ theo policy
```

**Trade-off:**
Pattern này tăng reliability cho retry nhưng thêm storage, retention, concurrency control và semantics cho trường hợp cùng key nhưng payload khác. Key scope và thời gian giữ phải được thiết kế rõ.

**Middle → Senior insight:**
Middle developer cần đảm bảo unique constraint và không xử lý duplicate request hai lần. Senior / Technical developer phải quyết định key ownership, payload fingerprinting, retention window, response replay, race handling và interaction với downstream system không idempotent.

### Design 2 — Saga chỉ nên dùng khi business transaction thực sự vượt qua nhiều consistency boundary

**Khái niệm:**
Saga chia một business transaction phân tán thành nhiều local transaction, mỗi bước có event/command tiếp theo và có thể có compensating action nếu workflow thất bại giữa chừng.

**Vấn đề nó giải quyết:**
Trong microservices, Order, Payment và Inventory thường không chia sẻ cùng database transaction. Cố kéo một distributed transaction xuyên nhiều service làm coupling và operational risk tăng mạnh.

**Ví dụ thực tế:**
```text
Create Order
-> Reserve Inventory
-> Authorize Payment
-> Confirm Order
```

Nếu payment fail:
```text
Release Inventory
-> Cancel Order
```

Compensation không nhất thiết là “rollback” tuyệt đối; nó là business action mới để đưa hệ thống về trạng thái chấp nhận được.

**Trade-off:**
Saga tránh distributed transaction và hỗ trợ long-running workflow, nhưng thêm eventual consistency, retry, duplicate message, state machine và khó debug hơn. Nếu tất cả thay đổi nằm trong cùng database/module, local transaction thường đơn giản hơn nhiều.

**Middle → Senior insight:**
Middle developer cần viết step idempotent và hiểu compensation không giống database rollback. Senior / Technical developer phải xác định consistency boundary, failure policy, orchestration vs choreography, observability và trạng thái manual intervention khi compensation cũng thất bại.

### Design 3 — Database ownership nên đi theo bounded context thay vì chia sẻ schema tự do giữa service

**Khái niệm:**
Mỗi bounded context nên sở hữu dữ liệu và invariant của mình. Context khác truy cập qua contract, event hoặc read model được thiết kế rõ thay vì query trực tiếp table nội bộ của nhau.

**Vấn đề nó giải quyết:**
Shared database giúp tích hợp ban đầu nhanh nhưng tạo coupling ngầm: một service đổi schema có thể phá service khác; transaction boundary và ownership business trở nên mơ hồ; việc tách hoặc scale độc lập khó dần theo thời gian.

**Ví dụ thực tế:**
`Ordering` sở hữu:
```text
Orders
OrderItems
OrderStatus transitions
```

`Reporting` không query trực tiếp các table đó nếu cần autonomy cao; nó có thể nhận event và xây read model riêng phù hợp dashboard.

**Trade-off:**
Ownership rõ giảm coupling và giúp evolution độc lập, nhưng có thể tạo duplicate data, eventual consistency và integration overhead. Với modular monolith nhỏ, dùng chung physical database nhưng enforce schema/module ownership có thể là lựa chọn thực dụng hơn tách database ngay.

**Middle → Senior insight:**
Middle developer cần tôn trọng ownership và tránh dependency bằng SQL “đi tắt”. Senior / Technical developer phải cân bằng autonomy với operational cost, chọn synchronous query, replicated read model hay shared database theo latency, consistency, team topology và migration path thực tế.
