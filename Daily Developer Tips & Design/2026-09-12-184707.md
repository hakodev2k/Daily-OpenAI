# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Cẩn thận khi dùng `AddDbContextPool`: `DbContext` được tái sử dụng nhưng state của bạn không được tự reset

**Mẹo:**
Nếu bật `AddDbContextPool` để giảm allocation và setup cost của EF Core, chỉ giữ trong `DbContext` những state mà EF Core biết cách reset. Không lưu tenant ID, user ID hoặc request-specific flag trong field mutable của context rồi giả định mỗi request luôn nhận instance hoàn toàn mới.

**Tại sao hữu ích:**
Pooled `DbContext` có thể được trả lại pool và dùng cho request khác. EF Core reset internal tracking state, nhưng custom mutable state do application thêm vào có thể sống lâu hơn request nếu bạn không quản lý đúng, dẫn tới bug cross-tenant hoặc behavior rất khó tái hiện.

**Ví dụ:**
```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Thay vì gắn trực tiếp `TenantId` mutable vào pooled context, cân nhắc truyền tenant boundary qua query/service rõ ràng hoặc dùng factory/scoped abstraction kiểm soát state cho từng operation.

**Lưu ý:**
Pooling không phải mặc định luôn nhanh hơn đáng kể. Hãy đo allocation, throughput và startup cost trước. Với context nhẹ hoặc application ít tải, complexity về state isolation có thể không đáng đổi lấy lợi ích nhỏ.

### Tip 2 — Khi trace quá nhiều, dùng sampling có chủ đích thay vì tắt distributed tracing

**Mẹo:**
Nếu Application Insights/OpenTelemetry sinh quá nhiều trace và chi phí telemetry tăng, dùng sampling policy giữ lại toàn bộ error/slow trace quan trọng và giảm tỷ lệ trace bình thường thay vì tắt tracing trên production.

**Tại sao hữu ích:**
Không có tracing, incident xuyên API → Service Bus → database → external API rất khó điều tra. Sampling giữ observability hữu ích nhưng kiểm soát volume. Quan trọng nhất là sample theo rule có ý nghĩa thay vì random mọi thứ một cách mù quáng.

**Ví dụ:**
```text
Giữ 100%:
- request 5xx
- dependency timeout
- trace > 2s
- transaction quan trọng

Sample 5-10%:
- request 2xx latency bình thường
```

Nếu dùng head sampling, quyết định được đưa ra từ đầu trace; tail sampling mạnh hơn cho incident vì có thể nhìn kết quả cuối cùng nhưng cần collector/infrastructure phức tạp hơn.

**Lưu ý:**
Sampling sai có thể làm mất chính trace cần điều tra. Đồng thời metrics tổng hợp không nên suy ra trực tiếp từ trace đã sample nếu backend telemetry không có cơ chế correction phù hợp.

### Tip 3 — Thêm Content Security Policy để giảm blast radius của XSS, nhưng rollout theo report-only trước

**Mẹo:**
Với web application có nhiều script, third-party widget hoặc CMS content, triển khai Content Security Policy (CSP) dần bằng `Content-Security-Policy-Report-Only` trước khi enforce.

**Tại sao hữu ích:**
CSP giới hạn nguồn script/style/resource browser được phép thực thi. Nếu một XSS lọt qua input/output encoding, policy tốt có thể ngăn inline script hoặc script từ domain ngoài allowlist chạy được.

**Ví dụ:**
```http
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  object-src 'none';
  base-uri 'self';
```

Thu thập violation report, sửa inline script/third-party dependency rồi mới chuyển sang enforce.

**Lưu ý:**
Đừng thêm `'unsafe-inline'` rộng chỉ để hết lỗi vì nó làm CSP yếu đi đáng kể. CSP là defense-in-depth, không thay thế output encoding, sanitization và XSS prevention chuẩn.

### Tip 4 — Dùng `git worktree` khi cần làm hotfix mà không muốn stash branch đang dang dở

**Mẹo:**
Khi đang làm feature dài nhưng cần xử lý bug/hotfix trên branch khác, dùng `git worktree` để có working directory thứ hai thay vì stash toàn bộ hoặc clone repository mới.

**Tại sao hữu ích:**
`git worktree` dùng chung object database của repository nên nhanh và tiết kiệm disk. Bạn có thể giữ feature branch nguyên trạng trong một folder và checkout hotfix branch ở folder khác cùng lúc.

**Ví dụ:**
```bash
git worktree add ../app-hotfix -b hotfix/payment-timeout origin/main
```

Sau khi merge hoặc hoàn tất:
```bash
git worktree remove ../app-hotfix
```

**Lưu ý:**
Không checkout cùng một branch vào hai worktree cùng lúc. Đồng thời nhớ build artifact, IDE settings hoặc local database có thể vẫn dùng chung external resource dù source nằm ở hai folder khác nhau.

### Tip 5 — Với Optimizely CMS, tách content projection khỏi presentation để giảm coupling với CMS model

**Mẹo:**
Khi backend hoặc headless API đọc content từ Optimizely CMS, map content type sang DTO/view model phù hợp use case thay vì trả trực tiếp `IContent` hoặc page/block model xuyên nhiều layer.

**Tại sao hữu ích:**
CMS model thường mang metadata, versioning và platform-specific concern. Nếu frontend/API contract phụ thuộc trực tiếp vào đó, thay content model hoặc nâng CMS version có thể tạo breaking change rộng hơn cần thiết.

**Ví dụ:**
```text
Optimizely ProductPage
-> ProductContentProjection
-> ProductSummaryDto
-> REST/headless response
```

Projection layer có thể xử lý language fallback, published state và URL resolution trước khi dữ liệu ra khỏi CMS boundary.

**Lưu ý:**
Không tạo mapper tầng tầng lớp lớp cho mọi block nhỏ. Với use case nội bộ đơn giản, mapping trực tiếp trong application layer có thể đủ. Mục tiêu là cô lập platform coupling nơi nó thực sự gây change pressure.

## 🧠 Software Design

### Design 1 — `DbContext` trực tiếp vs Repository abstraction: chọn theo abstraction value, không theo thói quen

**Khái niệm:**
EF Core đã cung cấp Unit of Work và Repository-like capability qua `DbContext`/`DbSet`. Repository riêng chỉ có giá trị khi nó tạo boundary hoặc behavior có ý nghĩa, không phải chỉ bọc lại từng method CRUD.

**Vấn đề nó giải quyết:**
Một repository kiểu `GetById`, `Add`, `Update`, `Delete` thường chỉ che EF Core mà không giảm coupling thật, đồng thời làm mất khả năng projection, composition và query optimization. Nhưng trong domain có query/aggregate boundary rõ, repository vẫn có thể diễn đạt intent tốt.

**Ví dụ thực tế:**
```text
CRUD admin module:
Application service -> AppDbContext trực tiếp
=> đơn giản, ít ceremony

Complex domain aggregate:
IOrderRepository.GetForCheckoutAsync(orderId)
=> encapsulate aggregate loading/invariant-specific persistence
```

Repository có ích khi contract của nó phản ánh domain operation hoặc infrastructure boundary, không phải mirror `DbSet` API.

**Trade-off:**
Dùng `DbContext` trực tiếp giảm abstraction và giữ EF Core capability đầy đủ nhưng application layer biết rõ ORM hơn. Repository giảm persistence coupling ở một số boundary nhưng dễ tạo generic abstraction nghèo nàn và query inefficiency nếu thiết kế quá cứng.

**Middle → Senior insight:**
Middle developer cần biết EF Core đã làm gì sẵn và tránh wrapper CRUD vô nghĩa. Senior / Technical developer phải đánh giá test strategy, domain complexity, query needs, migration likelihood và team conventions để quyết định abstraction nào thật sự trả lại giá trị.

### Design 2 — Event schema evolution cần compatibility contract, không chỉ “thêm version number”

**Khái niệm:**
Event trong Event-Driven Architecture có thể sống lâu trong broker, log hoặc consumer độc lập. Schema evolution phải đảm bảo consumer cũ và mới hiểu được message trong compatibility window.

**Vấn đề nó giải quyết:**
Nếu producer đổi tên field, đổi meaning hoặc xóa property rồi deploy trước consumer, downstream có thể fail hoặc hiểu sai event dù message vẫn deserialize được.

**Ví dụ thực tế:**
```text
OrderCreated v1:
{ orderId, customerName }

Nhu cầu mới:
customerName -> customer.displayName

Cách an toàn hơn:
- thêm field mới theo hướng additive
- producer ghi cả cũ + mới trong transition window
- migrate consumer
- telemetry consumer usage
- retire field cũ sau khi xác nhận
```

Version mới chỉ cần thiết khi semantics thực sự breaking và compatibility additive không còn hợp lý.

**Trade-off:**
Compatibility giữ deployment độc lập và giảm coordination nhưng tạo temporary duplication, schema governance và cleanup work. Versioning mạnh giúp contract rõ nhưng có thể khiến producer phải phát nhiều event version song song.

**Middle → Senior insight:**
Middle developer cần hiểu additive vs breaking change và viết consumer tolerant với field mới. Senior / Technical developer phải định nghĩa compatibility policy, ownership, retention, replay behavior và migration sequence cho toàn event ecosystem.

### Design 3 — Blue/Green vs Rolling Deployment: chọn theo rollback semantics và capacity budget

**Khái niệm:**
Rolling Deployment thay instance dần dần trong cùng environment. Blue/Green giữ hai environment/version song song rồi chuyển traffic giữa chúng. Cả hai đều nhằm giảm downtime nhưng có cost và failure mode khác nhau.

**Vấn đề nó giải quyết:**
Một deployment có thể build thành công nhưng chỉ lỗi dưới production traffic. Team cần cách rollout và rollback phù hợp với khả năng giữ capacity, database compatibility và traffic routing.

**Ví dụ thực tế:**
```text
Rolling:
10 pods
-> thay 2 pods mỗi batch
-> version cũ/mới cùng chạy trong vài phút

Blue/Green:
Blue = v1 đang phục vụ
Green = v2 đã warm-up + health check
-> switch traffic sang Green
-> rollback bằng route về Blue nếu cần
```

Cả hai đều yêu cầu database/API migration backward-compatible khi version cũ và mới có thể cùng tồn tại hoặc khi rollback cần quay lại binary cũ.

**Trade-off:**
Rolling tiết kiệm capacity và phù hợp Kubernetes/App Service phổ biến nhưng rollback chậm hơn và mixed-version behavior phải an toàn. Blue/Green rollback traffic rất nhanh nhưng gần như cần gấp đôi capacity tạm thời, routing phức tạp hơn và không tự rollback database change.

**Middle → Senior insight:**
Middle developer cần hiểu health checks, graceful shutdown và backward-compatible deployment. Senior / Technical developer phải chọn strategy theo traffic criticality, rollback objective, infrastructure cost, stateful dependency và schema migration plan thay vì coi deployment strategy chỉ là setting của pipeline.
