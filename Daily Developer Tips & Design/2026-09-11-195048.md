# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` khi buffer lớn được tạo lặp lại trên hot path

**Mẹo:**
Khi code .NET thường xuyên cần buffer tạm kích thước lớn cho parsing, compression hoặc serialization, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì tạo `new byte[...]` cho mỗi operation.

**Tại sao hữu ích:**
Các array lớn có thể đi vào Large Object Heap và tạo áp lực GC nếu được allocate liên tục. Pooling tái sử dụng memory đã cấp phát, giảm allocation rate và GC pressure trong workload throughput cao.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
}
```

`clearArray: true` hữu ích nếu buffer chứa dữ liệu nhạy cảm hoặc nếu reuse dữ liệu cũ có thể gây bug.

**Lưu ý:**
Buffer được `Rent` có thể lớn hơn kích thước yêu cầu và chứa dữ liệu từ lần dùng trước. Không được giữ reference sau khi `Return`, và không nên dùng pooling cho object nhỏ hoặc path ít chạy nếu complexity tăng nhiều hơn lợi ích.

### Tip 2 — Với ASP.NET Core Output Caching, thiết kế cache key trước khi bật cache rộng

**Mẹo:**
Khi dùng Output Caching cho endpoint đọc nhiều, xác định rõ response thay đổi theo route, query string, header hoặc identity nào trước khi cache.

**Tại sao hữu ích:**
Output cache có thể giảm backend work mạnh, nhưng cache key thiếu dimension cần thiết sẽ trả sai nội dung cho request khác. Ngược lại, vary theo quá nhiều giá trị tạo cache fragmentation và hit ratio thấp.

**Ví dụ:**
```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy => policy
        .Expire(TimeSpan.FromSeconds(30))
        .SetVaryByQuery("category", "page"));
});

app.MapGet("/products", GetProducts)
   .CacheOutput("catalog");
```

Nếu response phụ thuộc locale, tenant hoặc authorization, các dimension đó phải được xử lý rõ trong policy thay vì giả định mọi `GET` đều cache-safe.

**Lưu ý:**
Không cache response chứa dữ liệu user-specific chỉ vì endpoint là read-only. Kiểm tra authorization, cookies, headers và invalidation semantics trước khi bật cache cho production.

### Tip 3 — Trong Elasticsearch, dùng `keyword` cho exact match và `text` cho full-text search

**Mẹo:**
Khi thiết kế mapping, phân biệt field cần search theo ngôn ngữ với field cần filter/sort/aggregate chính xác. `text` thường được analyzer xử lý; `keyword` giữ giá trị gần như nguyên bản cho exact operations.

**Tại sao hữu ích:**
Nếu filter theo `status`, `email`, `productCode` hoặc aggregate theo category mà field chỉ là `text`, query có thể không hoạt động như mong đợi hoặc phải dựa vào multi-field mặc định. Mapping đúng giúp query semantics rõ và giảm lỗi khó hiểu.

**Ví dụ:**
```json
{
  "mappings": {
    "properties": {
      "title": { "type": "text" },
      "status": { "type": "keyword" },
      "productCode": { "type": "keyword" }
    }
  }
}
```

`title` phù hợp với full-text search; `status` và `productCode` phù hợp với filter, sort và aggregation.

**Lưu ý:**
Mapping không thể thay đổi tùy ý sau khi index đã có dữ liệu. Sai mapping thường dẫn tới reindex. Trước khi tạo index production, xác định access pattern và test analyzer/mapping bằng dữ liệu thực tế.

### Tip 4 — Khi Kubernetes pod bị `OOMKilled`, kiểm tra memory limit và working set trước khi tăng RAM

**Mẹo:**
Nếu pod restart với reason `OOMKilled`, đọc container status, memory metrics và workload pattern trước khi tăng memory limit.

**Tại sao hữu ích:**
`OOMKilled` nghĩa là container vượt memory boundary hoặc node chịu memory pressure. Root cause có thể là memory leak, batch size quá lớn, cache tăng không giới hạn hoặc limit quá thấp. Tăng limit chỉ che vấn đề nếu working set tiếp tục tăng.

**Ví dụ:**
```bash
kubectl describe pod api-7d8f9c
kubectl top pod api-7d8f9c --containers
```

Nếu memory tăng dần qua thời gian sau mỗi deployment, kết hợp metrics với heap dump hoặc `dotnet-gcdump` để phân biệt leak với peak workload hợp lệ.

**Lưu ý:**
Không đặt memory request/limit chỉ dựa trên peak quan sát một lần. Request ảnh hưởng scheduling, limit ảnh hưởng kill behavior; cần dựa trên baseline, percentile và headroom phù hợp với workload.

### Tip 5 — Khi AI coding agent đề xuất API hoặc package, xác minh version và source trước khi merge

**Mẹo:**
Nếu AI sinh code dùng API/library không quen thuộc, kiểm tra trực tiếp package version, official docs hoặc source repository thay vì tin vào method signature được đề xuất.

**Tại sao hữu ích:**
AI có thể trộn API giữa nhiều version, nhớ nhầm overload hoặc dùng package đã đổi namespace. Code có thể trông hợp lý nhưng không compile hoặc, tệ hơn, compile với behavior khác assumptions ban đầu.

**Ví dụ:**
```text
AI đề xuất:
services.AddSomeFeature(options => ...)

Kiểm tra trước khi merge:
- package nào cung cấp API này?
- version hiện tại trong repo là gì?
- overload có tồn tại trong version đó không?
- behavior có thay đổi giữa major versions không?
- test nào xác nhận semantics thật?
```

Với migration lớn, yêu cầu agent ground reasoning vào `.csproj`, lock file và source hiện tại thay vì dựa trên kiến thức chung.

**Lưu ý:**
Không biến verification thành việc đọc docs thủ công cho mọi dòng code. Tập trung vào boundary rủi ro cao: security, data access, migrations, infrastructure, breaking API và package version changes.

## 🧠 Software Design

### Design 1 — Cache failure policy: fail-open hay fail-closed phải theo vai trò của cache

**Khái niệm:**
Khi Redis hoặc distributed cache lỗi, application phải biết nên bỏ qua cache và tiếp tục gọi source of truth hay chặn request. Quyết định này phụ thuộc cache là optimization hay là thành phần mang semantics bắt buộc.

**Vấn đề nó giải quyết:**
Nếu mọi cache outage đều làm toàn bộ API 500, hệ thống biến dependency tối ưu thành single point of failure. Nhưng nếu cache chứa rate-limit counter, distributed lock hoặc security-sensitive state, bỏ qua cache tùy tiện có thể phá invariant.

**Ví dụ thực tế:**
```text
Product catalog cache:
Redis down
-> fallback SQL
-> latency tăng nhưng service vẫn hoạt động

Distributed lock bảo vệ settlement job:
Redis down
-> không được chạy job song song như chưa có gì xảy ra
-> cần fail/hold hoặc chuyển sang cơ chế coordination khác
```

Cùng một Redis cluster có thể phục vụ nhiều use case với failure policy khác nhau.

**Trade-off:**
Fail-open tăng availability nhưng có thể đẩy load xuống database hoặc làm mất protection. Fail-closed bảo vệ invariant nhưng giảm availability. Thiết kế tốt cần rate limit fallback traffic, timeout ngắn cho cache và observability rõ khi degraded mode được kích hoạt.

**Middle → Senior insight:**
Middle developer cần phân biệt cache optimization với distributed coordination và xử lý timeout/fallback đúng. Senior / Technical developer phải định nghĩa failure semantics, capacity của source of truth, degradation policy và blast radius khi cache cluster unavailable.

### Design 2 — Azure Functions vs Worker Service theo execution model, không theo độ “serverless”

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có trigger rõ, scale theo event và execution tương đối độc lập. Worker Service phù hợp khi process cần lifecycle dài, continuous loop, control tài nguyên hoặc stateful coordination trong process nhiều hơn.

**Vấn đề nó giải quyết:**
Team thường chọn Functions vì deployment đơn giản hoặc chọn Worker vì quen .NET, nhưng execution model mới là yếu tố quyết định. Sai lựa chọn có thể tạo cold start, timeout, khó debug hoặc ngược lại phải vận hành service luôn chạy cho workload rất thưa.

**Ví dụ thực tế:**
```text
Azure Function:
- xử lý Blob upload
- Service Bus trigger
- chạy vài giây/phút mỗi event
- scale theo backlog

Worker Service:
- long-running consumer
- cần custom concurrency loop
- cần connection/session sống lâu
- cần kiểm soát shutdown và backpressure chi tiết
```

Với Service Bus, cả hai đều có thể đúng; khác biệt nằm ở control và operational model mà workload cần.

**Trade-off:**
Functions giảm infrastructure management và scale thuận tiện, nhưng execution/runtime constraints có thể hạn chế workload dài hoặc control thấp-level. Worker Service cho control cao hơn nhưng phải vận hành capacity, deployment và scaling rõ ràng.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, idempotency và graceful shutdown của nền tảng mình dùng. Senior / Technical developer phải chọn theo traffic shape, execution duration, concurrency control, cost model, observability và operational ownership.

### Design 3 — Contract Test bổ sung E2E test khi integration boundary thay đổi độc lập

**Khái niệm:**
Contract Test xác minh producer và consumer đồng ý về shape và semantics của interface mà không cần chạy toàn bộ hệ thống end-to-end. Nó đặc biệt hữu ích khi các service hoặc team release độc lập.

**Vấn đề nó giải quyết:**
E2E test có thể phát hiện integration failure nhưng thường chậm, flaky và chỉ chạy sau khi nhiều component đã được ghép lại. Unit test lại không phát hiện producer đổi field, enum hoặc status code khiến consumer vỡ.

**Ví dụ thực tế:**
```text
Consumer Mobile API kỳ vọng:
GET /customers/{id}
200
{
  "id": "...",
  "displayName": "..."
}

Producer vô tình rename `displayName` -> `name`.
Contract test fail trong pipeline trước khi hai hệ thống được deploy cùng nhau.
```

Contract Test không thay thế integration test với database, auth hoặc network behavior; nó bảo vệ boundary contract ở mức phù hợp.

**Trade-off:**
Contract testing rút ngắn feedback loop và giảm phụ thuộc vào full E2E environment, nhưng thêm artifact/schema lifecycle và không chứng minh toàn bộ user journey hoạt động. Nếu hệ thống nhỏ, release cùng nhau và contract đơn giản, thêm framework contract testing có thể là overhead không cần thiết.

**Middle → Senior insight:**
Middle developer cần biết test contract ổn định, tránh assert implementation detail và giữ backward compatibility. Senior / Technical developer phải quyết định boundary nào đáng có contract test, ownership của schema, compatibility policy và tỷ lệ hợp lý giữa unit, integration, contract và E2E tests.
