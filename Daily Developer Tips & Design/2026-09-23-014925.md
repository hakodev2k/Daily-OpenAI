# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `HttpClient` timeout không thay thế end-to-end cancellation budget

**Mẹo:**
Khi ASP.NET Core gọi third-party API, truyền `CancellationToken` từ request xuống `HttpClient` và đặt timeout theo latency budget của operation, thay vì chỉ dựa vào một `HttpClient.Timeout` lớn dùng chung cho mọi endpoint.

**Tại sao hữu ích:**
Client có thể đã disconnect hoặc request upstream đã hết deadline nhưng backend vẫn tiếp tục chờ dependency. Propagate cancellation giúp giải phóng work không còn giá trị; timeout riêng cho dependency giúp một call chậm không tiêu hết toàn bộ budget của request.

**Ví dụ:**
```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

using var response = await httpClient.GetAsync(
    $"inventory/{productId}", timeoutCts.Token);
```
Nếu endpoint có SLO 3 giây, dành 2 giây cho inventory còn hợp lý hơn để outbound call tự chờ 100 giây rồi mới fail.

**Lưu ý:**
Phân biệt caller cancellation với timeout khi telemetry; nếu gom tất cả thành một lỗi `TaskCanceledException`, incident analysis sẽ khó biết user hủy request hay dependency vượt budget. Retry cũng phải nằm trong tổng deadline, không reset budget sau mỗi attempt.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` khi bảng lớn và dữ liệu thay đổi liên tục

**Mẹo:**
Với feed hoặc danh sách lớn, dùng keyset/seek pagination dựa trên một ordering deterministic như `(CreatedAt, Id)` thay vì tăng `OFFSET` theo page number.

**Tại sao hữu ích:**
`OFFSET 100000` buộc database bỏ qua lượng lớn rows trước khi lấy page tiếp theo. Ngoài ra, insert/delete giữa hai lần request có thể làm item bị lặp hoặc bị bỏ qua. Keyset bắt đầu từ khóa cuối cùng đã nhìn thấy nên thường scale tốt hơn và ổn định hơn dưới concurrent writes.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp trên `(CreatedAt DESC, Id DESC)` giúp database seek tới vị trí tiếp theo thay vì scan rồi discard một offset lớn.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới “page 237”. Cursor cũng phải chứa đủ tie-breaker để ordering deterministic; chỉ dùng `CreatedAt` có thể bỏ sót rows có cùng timestamp.

### Tip 3 — Structured logging giữ dữ liệu có thể query, string interpolation thì không

**Mẹo:**
Trong ASP.NET Core, log bằng message template và property riêng thay vì ghép chuỗi để telemetry có field có thể filter, aggregate và correlate.

**Tại sao hữu ích:**
`logger.LogInformation("Order {OrderId} failed for tenant {TenantId}", orderId, tenantId)` giữ `OrderId` và `TenantId` dưới dạng structured properties. Khi production có hàng triệu log entries, query theo property đáng tin cậy hơn tìm kiếm text và giúp dashboard/alerting hoạt động tốt hơn.

**Ví dụ:**
```csharp
logger.LogWarning(
    "Inventory reservation failed for {OrderId} after {ElapsedMs} ms",
    orderId,
    stopwatch.ElapsedMilliseconds);
```
Trong Application Insights hoặc Elasticsearch/Kibana, có thể group theo `OrderId`, percentile của `ElapsedMs`, hoặc correlate với trace.

**Lưu ý:**
Không log access token, password, connection string, full payment payload hoặc PII không cần thiết. Structured logging làm dữ liệu dễ query hơn nhưng cũng làm sensitive data dễ được index và lưu lâu hơn nếu logging policy sai.

### Tip 4 — Kiểm tra MongoDB query shape cùng compound index order

**Mẹo:**
Thiết kế compound index dựa trên query pattern thực tế — equality, sort và range — thay vì tạo index cho từng field riêng lẻ rồi kỳ vọng database tự ghép tối ưu mọi trường hợp.

**Tại sao hữu ích:**
Thứ tự field trong compound index quyết định prefix nào có thể được sử dụng hiệu quả. Query multi-tenant thường cần `TenantId` đứng ở phần equality prefix; sort/range phía sau phải phù hợp với access pattern để tránh scan hoặc in-memory sort lớn.

**Ví dụ:**
Query thường xuyên là `TenantId = X`, `Status = Active`, sort `CreatedAt DESC`. Index `{ TenantId: 1, Status: 1, CreatedAt: -1 }` có thể phù hợp hơn ba single-field indexes độc lập. Dùng `explain()` để xác nhận keys/docs examined và sort behavior.

**Lưu ý:**
Không áp dụng một công thức index-order cứng nhắc cho mọi query. Cardinality, optional predicates, sort direction và workload write đều ảnh hưởng. Mỗi index tăng storage, RAM pressure và write amplification, nên index thừa cũng là một performance bug.

### Tip 5 — AI-generated migration phải được kiểm tra bằng schema diff và dữ liệu thật

**Mẹo:**
Khi dùng AI coding agent để tạo EF Core migration hoặc SQL migration, coi output là proposal: review generated SQL, schema diff, rollback/forward path và chạy trên dataset representative trước khi merge.

**Tại sao hữu ích:**
Agent có thể viết code compile đúng nhưng không hiểu volume production, lock duration hoặc compatibility giữa application versions. Một `ALTER COLUMN` vô hại trên local database vài nghìn rows có thể lock/rewrite bảng hàng trăm triệu rows trong production.

**Ví dụ:**
Agent đề xuất đổi `nvarchar(max)` sang `nvarchar(200)` và thêm non-null constraint. Trước khi deploy, kiểm tra dữ liệu vượt 200 ký tự, execution behavior của DDL, default/backfill strategy và liệu phiên bản application cũ còn ghi dữ liệu không tương thích hay không.

**Lưu ý:**
Generated migration không nên được “tin vì test xanh”. Integration test thường không mô phỏng lock, table size, replication hoặc zero-downtime rollout. Với migration rủi ro, cần deployment plan và observability riêng.

## 🧠 Software Design

### Design 1 — Saga quản lý workflow phân tán bằng local transaction và compensation

**Khái niệm:**
Saga chia một business transaction dài qua nhiều service thành chuỗi local transactions. Khi bước sau thất bại, workflow chạy compensating action cho những bước đã hoàn thành thay vì cố dùng một ACID transaction xuyên nhiều service.

**Vấn đề nó giải quyết:**
Checkout có thể liên quan Order, Payment và Inventory thuộc các service/database khác nhau. Giữ distributed transaction lâu hoặc yêu cầu atomic commit xuyên mọi dependency thường không khả thi và làm coupling vận hành rất cao.

**Ví dụ thực tế:**
Order được tạo ở trạng thái `Pending`, Inventory reserve hàng, Payment authorize tiền. Nếu payment thất bại, saga release reservation và chuyển order sang `PaymentFailed`. Compensation không nhất thiết “undo” tuyệt đối; nó đưa business về một state hợp lệ khác.

**Trade-off:**
Saga chấp nhận intermediate state và eventual consistency. Compensation có thể fail, message có thể duplicate/out-of-order, và debugging workflow dài khó hơn transaction local. Với logic chỉ nằm trong một database, ACID transaction đơn giản thường tốt hơn.

**Middle → Senior insight:**
Middle developer cần viết step idempotent, state transition rõ và xử lý retry/compensation. Senior / Technical developer phải chọn choreography hay orchestration, định nghĩa invariant nào được phép tạm thời vi phạm, recovery manual/automatic, observability và business semantics của compensation thay vì giả định mọi operation đều reversible.

### Design 2 — SQL hay NoSQL phải xuất phát từ invariant và access pattern

**Khái niệm:**
Chọn relational database hay document/NoSQL store không nên dựa vào “scale lớn thì NoSQL”. Quyết định phải xét transaction boundary, relationship, query shape, consistency, partitioning và cách dữ liệu thay đổi theo thời gian.

**Vấn đề nó giải quyết:**
Một model ép sai storage paradigm tạo complexity ở application. Dữ liệu có nhiều cross-entity invariant và ad-hoc relational query có thể trở nên khó quản lý khi denormalize quá mạnh; ngược lại, aggregate document tự chứa và truy cập theo partition key có thể không cần join/schema relational phức tạp.

**Ví dụ thực tế:**
Ledger/payment core cần constraint và transaction mạnh có thể phù hợp PostgreSQL/SQL Server. Product catalog có document attributes khác nhau theo category và chủ yếu đọc theo product/category có thể phù hợp document model — miễn query/index/partition strategy được chứng minh bằng workload.

**Trade-off:**
SQL đem lại relational integrity và query flexibility nhưng scale/distribution có operational trade-off. NoSQL có thể tối ưu access pattern và horizontal distribution nhưng thường chuyển trách nhiệm consistency, denormalization và query limitation sang application. Polyglot persistence lại tăng vận hành và skill cost.

**Middle → Senior insight:**
Middle developer cần model đúng schema/index và hiểu transaction guarantee của store đang dùng. Senior / Technical developer phải bắt đầu từ invariant, workload, failure mode, data growth và team capability; chỉ thêm loại database thứ hai khi lợi ích đủ lớn để trả chi phí backup, monitoring, migration, security và expertise.

### Design 3 — Observability phải được thiết kế theo service boundary và business flow

**Khái niệm:**
Observability design xác định logs, metrics và traces nào giúp suy luận trạng thái hệ thống từ bên ngoài. Mục tiêu không phải “log thật nhiều”, mà tạo evidence đủ để nối một business operation qua API, database, cache, queue và external dependency.

**Vấn đề nó giải quyết:**
Khi order processing chậm, dashboard CPU bình thường không nói được bottleneck nằm ở SQL, Service Bus lag hay payment provider. Nếu mỗi component dùng identifier khác nhau hoặc không propagate trace context, incident team phải ghép bằng timestamp và phỏng đoán.

**Ví dụ thực tế:**
Checkout propagate trace context qua HTTP và message, log `OrderId` như business correlation, đo request latency, dependency latency, queue age và failure rate. Khi p95 tăng, trace cho thấy phần lớn thời gian nằm ở inventory dependency trong khi CPU application vẫn thấp.

**Trade-off:**
Telemetry có storage/cost overhead, high-cardinality dimension có thể rất đắt và sampling có thể bỏ mất trace hiếm. Log quá chi tiết còn tăng security/privacy risk. Instrumentation phải ưu tiên câu hỏi vận hành thực tế thay vì thu mọi thứ có thể thu.

**Middle → Senior insight:**
Middle developer cần structured logging, correlation, trace propagation và metric cơ bản đúng. Senior / Technical developer phải thiết kế SLI/SLO, cardinality budget, sampling strategy, ownership dashboard/alert và đảm bảo telemetry hỗ trợ symptom → evidence → hypothesis → diagnosis trên toàn business flow, không chỉ từng process riêng lẻ.
