# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` khi cần stream dữ liệu thay vì buffer toàn bộ

**Mẹo:**
Với ASP.NET Core endpoint xử lý tập dữ liệu lớn, cân nhắc `IAsyncEnumerable<T>` hoặc streaming khi consumer có thể xử lý tuần tự. Mục tiêu là tránh materialize toàn bộ result vào `List<T>` trước khi bắt đầu gửi hoặc xử lý.

**Tại sao hữu ích:**
Buffer toàn bộ dữ liệu làm tăng peak memory và time-to-first-byte. Streaming cho phép pipeline bắt đầu xử lý sớm hơn và tạo backpressure tự nhiên hơn, đặc biệt với export hoặc data feed lớn.

**Ví dụ:**
Một endpoint export hàng trăm nghìn audit records có thể project dữ liệu cần thiết từ EF Core rồi enumerate bất đồng bộ thay vì `ToListAsync()` toàn bộ trước. Client nhận dữ liệu dần, còn server tránh giữ toàn bộ result set trong memory.

**Lưu ý:**
Streaming giữ database reader/connection lâu hơn và lỗi giữa stream không còn dễ chuyển thành một HTTP error response sạch. Không dùng chỉ vì dataset “có vẻ lớn”; đo memory, connection duration và client semantics trước.

### Tip 2 — Keyset pagination cho bảng lớn thay vì OFFSET ngày càng sâu

**Mẹo:**
Khi API duyệt dữ liệu theo thứ tự ổn định và không cần nhảy trực tiếp tới trang 5000, dùng keyset/seek pagination dựa trên sort key cuối cùng thay vì `OFFSET ... FETCH` ngày càng lớn.

**Tại sao hữu ích:**
OFFSET sâu thường buộc database vẫn phải tìm/sắp xếp rồi bỏ qua rất nhiều rows. Keyset dùng predicate trên indexed ordering key để bắt đầu gần vị trí cần đọc, nên chi phí ổn định hơn khi dataset tăng.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp với `(CreatedAt DESC, Id DESC)` giúp API lấy “trang tiếp theo” mà không scan qua hàng trăm nghìn rows đã xem.

**Lưu ý:**
Sort phải deterministic; một `CreatedAt` không unique cần tie-breaker như `Id`. Keyset không phù hợp nếu UX bắt buộc random page access chính xác theo số trang.

### Tip 3 — Kubernetes readiness probe không phải liveness probe

**Mẹo:**
Dùng readiness để quyết định Pod có nên nhận traffic; dùng liveness chỉ khi process thực sự cần restart để hồi phục. Đừng cấu hình cả hai probe cùng một dependency check một cách máy móc.

**Tại sao hữu ích:**
Nếu SQL hoặc external API tạm thời lỗi và liveness cũng fail, Kubernetes có thể restart hàng loạt Pods đang khỏe về process, làm incident nặng hơn. Readiness có thể tạm rút Pod khỏi Service mà không phá process state.

**Ví dụ:**
ASP.NET Core app vẫn chạy nhưng startup cache chưa warm xong: readiness trả unhealthy nên chưa nhận traffic. Nếu process deadlock thật sự và endpoint liveness không phản hồi, kubelet mới restart container.

**Lưu ý:**
Probe quá nặng hoặc gọi nhiều downstream dependencies có thể tự tạo tải và cascading failure. Thiết kế probe theo khả năng phục vụ của chính workload và failure mode cần phát hiện.

### Tip 4 — Dùng browser Performance/Network để tách backend latency khỏi frontend rendering

**Mẹo:**
Khi Vue.js/React.js page “chậm”, tách thời gian thành DNS/connect, TTFB, download, JavaScript execution và rendering trước khi tối ưu component hoặc API.

**Tại sao hữu ích:**
Một cảm giác chậm có thể đến từ API TTFB 1.5 giây, bundle lớn, long task trên main thread hoặc ảnh blocking layout. Không có waterfall/timeline, team dễ tối ưu sai tầng.

**Ví dụ:**
Network cho thấy API chỉ 120 ms nhưng click-to-render mất 1.8 giây; Performance trace xuất hiện long task do transform 30.000 rows trên main thread. Giảm payload, paginate/virtualize và tránh xử lý toàn dataset hiệu quả hơn việc cache API.

**Lưu ý:**
Dev build và browser extension có thể làm profile sai lệch. Reproduce bằng production-like build, realistic data và thiết bị/network phù hợp với user thật.

### Tip 5 — AI coding agent: bắt nó chứng minh thay đổi bằng repository evidence

**Mẹo:**
Khi giao bug cho AI coding agent, yêu cầu nó đọc call sites, version/package hiện tại và tests liên quan trước khi sửa; sau đó chạy test/build cụ thể chứng minh behavior thay vì chỉ trả diff “có vẻ đúng”.

**Tại sao hữu ích:**
Agent dễ suy diễn API theo version khác, tạo abstraction không khớp codebase hoặc sửa symptom ở một call site. Grounding vào source và executable verification biến AI thành accelerator có kiểm soát.

**Ví dụ:**
Thay vì “fix authentication bug”, giao scope: trace middleware → endpoint authorization → token validation configuration, chỉ ra evidence, sửa tối thiểu, rồi chạy integration tests cho expired token, wrong audience và valid token.

**Lưu ý:**
Tests generated cùng lúc với implementation có thể chỉ xác nhận assumption của agent. Với bug quan trọng, ưu tiên reproduction test từ observed behavior/specification và review security/performance implications thủ công.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database write + integration event

**Khái niệm:**
Outbox Pattern ghi business state và event cần publish vào cùng local database transaction. Một publisher riêng đọc Outbox và gửi event tới broker, sau đó đánh dấu trạng thái xử lý.

**Vấn đề nó giải quyết:**
Nếu application commit Order rồi publish `OrderCreated`, process có thể crash giữa hai bước: database đã đổi nhưng event biến mất. Nếu publish trước rồi transaction rollback, consumer lại thấy một event cho state chưa tồn tại.

**Ví dụ thực tế:**
Checkout transaction insert `Order` và `OutboxMessage` cùng lúc. Background worker publish message lên Azure Service Bus. Nếu worker crash sau khi send nhưng trước khi mark published, message có thể được gửi lại nên consumer vẫn phải idempotent.

**Trade-off:**
Outbox loại bỏ “dual-write gap” giữa local database và broker nhưng thêm table growth, polling/publisher, cleanup, duplicate delivery và operational monitoring. Nó không tạo exactly-once processing end-to-end.

**Middle → Senior insight:**
Middle developer cần đảm bảo business write và Outbox record thật sự cùng transaction, đồng thời consumer chịu được duplicate. Senior / Technical developer phải quyết định ordering, retry/backoff, retention, backlog alerts và liệu consistency requirement có đủ quan trọng để biện minh complexity này hay không.

### Design 2 — Bounded Context thay vì một enterprise domain model dùng chung

**Khái niệm:**
Bounded Context đặt ranh giới nơi một domain language/model có nghĩa nhất quán. Cùng từ “Customer” có thể mang semantics khác nhau trong Sales, Billing và Support thay vì bị ép vào một class chung khổng lồ.

**Vấn đề nó giải quyết:**
Shared model giữa nhiều business capabilities thường tích tụ optional fields, conditional rules và coupling release. Một thay đổi cho Billing có thể làm Sales phải cập nhật dù business responsibility không liên quan.

**Ví dụ thực tế:**
Sales quan tâm lead status và account owner; Billing quan tâm legal entity, tax profile và payment terms. Hai context trao đổi qua explicit contract/identifier thay vì cùng tham chiếu một `CustomerEntity` với mọi field.

**Trade-off:**
Boundaries tăng autonomy và giảm semantic coupling nhưng tạo mapping, duplicated representations và integration contracts. Chia context quá nhỏ khiến hệ thống phân mảnh và coordination cost vượt lợi ích.

**Middle → Senior insight:**
Middle developer cần giữ model và rules đúng boundary đã định. Senior / Technical developer phải phát hiện semantic ownership từ business capability, team ownership và change patterns; bounded context không đồng nghĩa microservice và có thể nằm trong một Modular Monolith.

### Design 3 — Feature flags tách deployment khỏi release

**Khái niệm:**
Feature flag cho phép deploy code trước nhưng kiểm soát khi nào capability được bật cho user/tenant/cohort. Nó tạo một control plane cho rollout chứ không thay thế version control.

**Vấn đề nó giải quyết:**
Một thay đổi lớn cần production verification hoặc rollout dần nhưng deployment toàn bộ một lần làm blast radius lớn. Flag cho phép dark deployment, canary theo cohort và disable nhanh khi metrics xấu.

**Ví dụ thực tế:**
Search implementation mới được deploy cùng bản cũ. 5% tenant dùng path mới; team so sánh error rate, p95 latency và business correctness trước khi tăng rollout. Khi regression xuất hiện, disable flag nhanh hơn rollback toàn release chứa nhiều thay đổi khác.

**Trade-off:**
Feature flags giảm release risk nhưng mỗi flag tạo thêm execution paths, test matrix và technical debt. Flag lâu ngày có thể khiến code khó hiểu và behavior giữa environments không nhất quán.

**Middle → Senior insight:**
Middle developer cần test cả trạng thái on/off và tránh rải conditional logic khắp domain. Senior / Technical developer phải thiết kế ownership, rollout metrics, kill-switch semantics, auditability và expiry/removal policy; không dùng flag để che migration không tương thích hoặc invariant dữ liệu chưa được thiết kế.
