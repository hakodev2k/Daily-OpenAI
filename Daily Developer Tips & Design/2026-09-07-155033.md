# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Tạo scope đúng cách trong `BackgroundService`

**Mẹo:**
`BackgroundService` mặc định được đăng ký như singleton. Nếu cần dùng service scoped như `DbContext`, đừng inject trực tiếp scoped dependency vào constructor; hãy inject `IServiceScopeFactory` rồi tạo scope cho từng unit of work hoặc batch hợp lý.

**Tại sao hữu ích:**
Scoped service thường gắn với lifetime ngắn như request hoặc transaction. Giữ một `DbContext` trong singleton worker quá lâu có thể làm change tracker phình lớn, connection/transaction state khó kiểm soát và dữ liệu tracked trở nên stale. Tạo scope rõ ràng giúp mỗi lần xử lý có dependency lifecycle độc lập.

**Ví dụ:**
```csharp
public sealed class InvoiceWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<InvoiceProcessor>();

            await processor.ProcessBatchAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}
```

**Lưu ý:**
Không tạo một scope duy nhất ở đầu `ExecuteAsync` rồi giữ tới khi process shutdown. Khi worker chạy nhiều giờ hoặc nhiều ngày, cách đó gần như biến scoped dependency thành singleton trên thực tế.

### Tip 2 — Dùng keyset pagination khi offset bắt đầu trở nên đắt

**Mẹo:**
Với bảng lớn và luồng pagination tuần tự, cân nhắc keyset pagination thay vì `OFFSET ... FETCH` hoặc `Skip/Take` trên page sâu.

**Tại sao hữu ích:**
Offset pagination thường buộc database phải tìm rồi bỏ qua lượng row ngày càng lớn trước khi trả page hiện tại. Keyset pagination dùng giá trị cuối của page trước làm điểm bắt đầu, giúp database seek theo index thay vì scan/skip nhiều row.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
LIMIT 50;
```

Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)` tùy engine và query pattern.

**Lưu ý:**
Keyset pagination không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 437 theo số trang tuyệt đối. Cũng phải dùng tie-breaker ổn định như `Id`; chỉ cursor theo `CreatedAt` có thể bỏ sót hoặc lặp row khi nhiều record có cùng timestamp.

### Tip 3 — Khi latency tăng, so sánh p50 với p95/p99 trước khi nhìn average

**Mẹo:**
Trong Application Insights, Azure Monitor hoặc hệ thống metrics tương tự, đừng đánh giá API latency chỉ bằng average. So sánh p50, p95 và p99 để biết vấn đề ảnh hưởng toàn bộ traffic hay chỉ tail latency.

**Tại sao hữu ích:**
Average có thể che giấu một nhóm request rất chậm. Ví dụ p50 vẫn 90 ms nhưng p99 tăng từ 400 ms lên 8 giây thường gợi ý contention, dependency timeout, GC pause, cold path hoặc một nhóm query đặc biệt thay vì slowdown đồng đều toàn hệ thống.

**Ví dụ:**
```text
Before deployment:
p50 = 85 ms
p95 = 220 ms
p99 = 410 ms

After deployment:
p50 = 92 ms
p95 = 310 ms
p99 = 7.8 s
```

Bước tiếp theo nên segment theo route, dependency, region, instance hoặc operation name để tìm nhóm request tạo tail.

**Lưu ý:**
Percentile chỉ có giá trị khi aggregation window và traffic volume phù hợp. Đừng so p99 của một endpoint có 20 request với endpoint có hàng triệu request rồi kết luận trực tiếp về reliability.

### Tip 4 — `AllowCredentials` và wildcard origin không phải tổ hợp hợp lệ cho CORS an toàn

**Mẹo:**
Nếu browser gửi cookie hoặc credential cross-origin, cấu hình CORS phải whitelist origin cụ thể thay vì cho phép mọi origin. Với ASP.NET Core, đừng thiết kế policy theo kiểu “mọi website đều gọi được API nhưng vẫn mang credential”.

**Tại sao hữu ích:**
CORS là browser enforcement boundary cho cross-origin access. Khi credential được gửi, server phải biết origin nào được tin cậy; cho phép origin tùy ý sẽ phá mô hình trust và có thể làm session-authenticated API bị gọi từ site không mong muốn.

**Ví dụ:**
```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("Frontend", policy =>
    {
        policy
            .WithOrigins("https://app.example.com")
            .AllowCredentials()
            .AllowAnyHeader()
            .AllowAnyMethod();
    });
});
```

**Lưu ý:**
CORS không thay thế authentication, authorization hoặc CSRF protection. Request ngoài browser vẫn có thể gọi API trực tiếp; CORS không phải firewall cho backend.

### Tip 5 — Với Elasticsearch, tránh thay mapping field type trực tiếp trên index đang dùng

**Mẹo:**
Khi cần đổi mapping không tương thích, ví dụ từ `text` sang `keyword` hoặc thay analyzer, chuẩn bị index mới rồi reindex dữ liệu và chuyển alias thay vì cố sửa field type tại chỗ.

**Tại sao hữu ích:**
Elasticsearch xây inverted index theo mapping/analyzer tại thời điểm index document. Nhiều thay đổi mapping không thể áp ngược vào dữ liệu đã index vì tokenization và representation trên disk đã khác. Alias giúp chuyển consumer sang index mới mà application không cần đổi tên index cứng trong code.

**Ví dụ:**
```text
products-v1  <- alias: products
products-v2  <- reindex + validate

switch alias:
products -> products-v2
```

Trước khi switch, so sánh document count, query behavior, analyzer output và performance giữa hai index.

**Lưu ý:**
Reindex có thể tiêu tốn CPU, I/O và storage lớn. Với index production lớn, cần throttle, capacity planning và rollback path; không nên reindex toàn bộ cluster vào giờ cao điểm chỉ vì một mapping change nhỏ.

## 🧠 Software Design

### Design 1 — API backward compatibility nên được coi là contract, không phải chi tiết implementation

**Khái niệm:**
Khi API đã có consumer độc lập, response shape, field semantics, status code và behavior observable trở thành contract. Thay đổi “refactor nội bộ” có thể là breaking change nếu consumer nhìn thấy khác biệt.

**Vấn đề nó giải quyết:**
Backend và mobile/web client thường không deploy cùng thời điểm. Nếu server rename field, đổi nullability hoặc đổi enum semantics ngay lập tức, client cũ vẫn đang chạy có thể lỗi dù backend build và test đều pass.

**Ví dụ thực tế:**
API hiện trả:
```json
{
  "id": 42,
  "status": "paid"
}
```

Thay vì rename `status` thành `paymentStatus` ngay, có thể thêm field mới theo kiểu additive, giữ field cũ trong compatibility window, đo usage rồi mới deprecate và loại bỏ ở version phù hợp.

**Trade-off:**
Backward compatibility giảm coordination cost và production breakage, nhưng làm schema phải hỗ trợ transitional state lâu hơn, tăng test matrix và đôi khi giữ technical debt tạm thời.

**Middle → Senior insight:**
Middle developer cần tránh breaking changes vô ý và biết viết contract/integration test cho public behavior. Senior / Technical developer phải xác định compatibility policy, deprecation window, versioning strategy, telemetry để biết consumer nào còn dùng contract cũ và khi nào chi phí duy trì compatibility vượt quá lợi ích.

### Design 2 — Composition over Inheritance giúp giảm coupling khi behavior thay đổi theo nhiều chiều

**Khái niệm:**
Composition xây behavior bằng cách kết hợp các component có trách nhiệm nhỏ thay vì tạo hierarchy kế thừa sâu. Nó đặc biệt hữu ích khi requirement thay đổi theo nhiều dimension không tạo thành quan hệ “is-a” ổn định.

**Vấn đề nó giải quyết:**
Inheritance hierarchy dễ phình thành các lớp như `CachedRetryingAuthenticatedProductClient`, nơi mỗi variation cần thêm subclass mới. Khi concern như retry, caching, authentication và logging thay đổi độc lập, inheritance tạo coupling giữa những behavior vốn không thuộc cùng một domain hierarchy.

**Ví dụ thực tế:**
Một HTTP client có thể được cấu thành từ các concern riêng:
```text
ProductClient
  -> Authentication handler
  -> Retry/resilience handler
  -> Telemetry handler
  -> HttpClient transport
```

Mỗi concern có thể thay đổi hoặc test riêng mà không tạo subclass cho mọi tổ hợp.

**Trade-off:**
Composition tăng flexibility và testability nhưng có thể tạo nhiều object nhỏ, wiring phức tạp và indirection khó theo dõi nếu abstraction quá mức. Inheritance vẫn hợp lý khi quan hệ subtype thực sự ổn định và polymorphism là bản chất domain.

**Middle → Senior insight:**
Middle developer cần nhận ra khi subclass chỉ đang được dùng để tái sử dụng code. Senior / Technical developer phải đánh giá axis of change: behavior nào biến thiên độc lập, abstraction nào đáng tách, và khi nào một hierarchy nhỏ, rõ ràng đơn giản hơn cả một graph composition nhiều layer.

### Design 3 — Synchronous REST vs asynchronous messaging là quyết định về failure coupling

**Khái niệm:**
REST đồng bộ tạo request/response trực tiếp giữa caller và dependency; messaging bất đồng bộ tách thời điểm producer tạo work khỏi thời điểm consumer xử lý. Khác biệt quan trọng không chỉ là performance mà là cách failure và availability lan truyền giữa các thành phần.

**Vấn đề nó giải quyết:**
Nếu Checkout phải đồng bộ gọi Email, Analytics và Loyalty trước khi trả response, availability và latency của ba dependency phụ sẽ nằm trên critical path. Messaging có thể đưa các side effect không cần hoàn tất tức thời ra khỏi request path.

**Ví dụ thực tế:**
Checkout cần đồng bộ xác nhận Payment vì user phải biết thanh toán thành công hay thất bại. Nhưng sau khi Order đã commit, `OrderCompleted` có thể được publish để Email và Analytics xử lý riêng thay vì Checkout chờ cả hai service trả `200`.

**Trade-off:**
REST đơn giản hơn về flow, debugging và consistency tức thời nhưng tạo temporal coupling và dễ lan truyền timeout. Messaging tăng resilience và decoupling nhưng thêm broker, duplicate delivery, eventual consistency, observability, retry và dead-letter handling.

**Middle → Senior insight:**
Middle developer cần biết timeout, retry và idempotency cho cả hai kiểu integration. Senior / Technical developer phải phân loại operation nào thuộc critical synchronous path, operation nào chấp nhận eventual consistency, xác định failure semantics và tránh dùng messaging chỉ vì “microservices nên event-driven” khi một synchronous call đơn giản đã phù hợp constraint.
