# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng exception filter để chỉ catch lỗi đúng điều kiện

**Mẹo:**
Trong C#, dùng `catch (...) when (...)` khi chỉ muốn xử lý một subset của exception thay vì catch toàn bộ rồi `if` bên trong.

**Tại sao hữu ích:**
Giữ stack/unhandled behavior rõ hơn và làm intent của error handling chính xác ngay tại `catch` boundary.

**Ví dụ:**
```csharp
try
{
    await client.SendAsync(request, cancellationToken);
}
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
{
    return null;
}
```

**Lưu ý:**
Đừng dùng exception filter để che các lỗi không mong đợi. Nếu điều kiện filter quá phức tạp, nên đưa logic phân loại lỗi vào một policy riêng.

### Tip 2 — Dùng rate limiter ngay tại endpoint đắt tiền

**Mẹo:**
Với ASP.NET Core, không nhất thiết mọi endpoint phải dùng cùng một limit. Endpoint export, search nặng hoặc login có thể áp dụng policy riêng phù hợp với cost của operation.

**Tại sao hữu ích:**
Giúp bảo vệ tài nguyên thực sự nhạy cảm thay vì đặt một global limit quá thấp cho toàn API hoặc quá cao cho endpoint đắt.

**Ví dụ:**
```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("exports", limiter =>
    {
        limiter.PermitLimit = 5;
        limiter.Window = TimeSpan.FromMinutes(1);
    });
});

app.MapPost("/exports", HandleExport)
   .RequireRateLimiting("exports");
```

**Lưu ý:**
Rate limiting không thay thế authorization, quota billing hoặc backpressure phía downstream. Cần chọn key phù hợp như user, tenant hoặc API key.

### Tip 3 — Dùng window function thay vì query lồng khi cần ranking hoặc running total

**Mẹo:**
Khi cần `ROW_NUMBER`, top-N theo group, running total hoặc lag/lead, ưu tiên SQL window function thay vì nhiều subquery hoặc xử lý ở application.

**Tại sao hữu ích:**
Database xử lý trên một result set duy nhất, thường rõ hơn và hiệu quả hơn so với tải dữ liệu về rồi group/rank bằng code.

**Ví dụ:**
```sql
SELECT
    EmployeeId,
    WorkDate,
    Hours,
    SUM(Hours) OVER (
        PARTITION BY EmployeeId
        ORDER BY WorkDate
    ) AS RunningHours
FROM Timesheets;
```

**Lưu ý:**
Window function vẫn có thể cần sort lớn và memory grant đáng kể. Hãy kiểm tra execution plan/index nếu dataset lớn.

### Tip 4 — Dùng `git restore --staged` để bỏ stage mà không làm mất file đang sửa

**Mẹo:**
Khi lỡ `git add` file chưa muốn commit, dùng `git restore --staged <file>` thay vì reset hoặc thao tác mạnh hơn.

**Tại sao hữu ích:**
Bạn giữ nguyên working tree nhưng loại file khỏi staging area, giảm nguy cơ mất thay đổi khi đang chuẩn bị commit chọn lọc.

**Ví dụ:**
```bash
git restore --staged appsettings.json
```

Sau đó kiểm tra:

```bash
git status
```

**Lưu ý:**
`git restore --staged` chỉ bỏ stage. Nếu muốn bỏ luôn thay đổi trong working tree thì semantics khác và cần cẩn thận vì có thể mất code chưa commit.

### Tip 5 — Load test theo latency percentile, không chỉ average

**Mẹo:**
Khi benchmark API, theo dõi p50/p95/p99 và error rate thay vì chỉ average response time.

**Tại sao hữu ích:**
Average có thể trông ổn dù một nhóm nhỏ request cực chậm. Tail latency mới thường phản ánh contention, GC pause, connection pool saturation hoặc downstream spike.

**Ví dụ:**
Với `k6`:

```javascript
export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1000'],
    http_req_failed: ['rate<0.01']
  }
};
```

**Lưu ý:**
Một bài load test không giống production nếu data shape, think time, concurrency pattern hoặc dependency behavior khác thực tế.

## 🧠 Software Design

### Design 1 — Hexagonal Architecture: bảo vệ core khỏi framework và external systems

**Khái niệm:**
Hexagonal Architecture tổ chức business core quanh các port (contract) và adapter (implementation), để framework, database, queue hoặc external API nằm ngoài boundary nghiệp vụ.

**Vấn đề nó giải quyết:**
Khi domain logic phụ thuộc trực tiếp EF Core, HTTP client hoặc vendor SDK ở mọi nơi, test khó, thay implementation khó và business rule bị trộn với infrastructure concern.

**Ví dụ thực tế:**
Use case `ApproveLeave` phụ thuộc `ILeaveRepository` và `INotificationPort`. EF Core repository và email sender là adapter bên ngoài; domain/use case không biết cụ thể chúng dùng SQL Server hay Microsoft Graph.

**Trade-off:**
Boundary rõ giúp testability và thay infrastructure dễ hơn, nhưng thêm interface, mapping và wiring. Với CRUD nhỏ, áp dụng đầy đủ có thể tạo ceremony lớn hơn giá trị nhận được.

**Middle → Senior insight:**
Middle developer nên hiểu dependency direction phải hướng vào business core. Senior developer cần biết port nào thực sự ổn định và tránh tạo abstraction giả chỉ để “đúng kiến trúc”.

### Design 2 — Graceful Degradation thay vì biến dependency phụ thành single point of failure

**Khái niệm:**
Graceful Degradation cho phép hệ thống giảm một phần functionality khi dependency phụ bị lỗi, thay vì làm toàn request thất bại.

**Vấn đề nó giải quyết:**
Một request chính có thể phụ thuộc analytics, recommendation, email hoặc audit enrichment không bắt buộc để hoàn thành business outcome chính.

**Ví dụ thực tế:**
Trang Order Details vẫn trả order data nếu recommendation service timeout; phần gợi ý sản phẩm có thể để trống và log metric thay vì trả HTTP 500 cho toàn trang.

**Trade-off:**
Tăng availability và giảm blast radius nhưng có nguy cơ che lỗi nếu fallback im lặng quá lâu. Cần telemetry, alert và giới hạn rõ feature nào được phép degrade.

**Middle → Senior insight:**
Middle developer nên phân loại dependency nào critical và non-critical. Senior developer phải định nghĩa degradation policy theo business impact, SLO và user experience thay vì catch exception rồi bỏ qua tùy tiện.

### Design 3 — Temporal Coupling: giảm số bước phải xảy ra đúng thứ tự và đúng thời điểm

**Khái niệm:**
Temporal Coupling xảy ra khi nhiều component chỉ hoạt động đúng nếu được gọi theo một thứ tự hoặc timing ngầm định.

**Vấn đề nó giải quyết:**
Code có thể compile và nhìn đúng nhưng dễ hỏng nếu caller quên gọi `Initialize()`, `Load()`, `Validate()` rồi mới `Execute()`, hoặc nếu hai service phải deploy/chạy đồng thời theo một trình tự khó kiểm soát.

**Ví dụ thực tế:**
Thay vì API object yêu cầu:

```text
client.Connect()
client.Authenticate()
client.LoadProfile()
client.Send()
```

một abstraction tốt hơn có thể tạo object ở trạng thái hợp lệ ngay từ đầu hoặc encapsulate sequence trong một operation duy nhất.

**Trade-off:**
Giảm temporal coupling làm API an toàn và dễ dùng hơn, nhưng đôi khi tăng state management hoặc cần thêm object/state machine. Một số workflow tự nhiên vẫn có trình tự bắt buộc.

**Middle → Senior insight:**
Middle developer nên nhận ra các method order dependency ẩn trong code. Senior developer cần thiết kế state transition rõ ràng, enforce invariant bằng type/API shape và giảm số assumptions mà caller phải nhớ.
