# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Stream dữ liệu lớn bằng `IAsyncEnumerable<T>` thay vì materialize toàn bộ kết quả

**Mẹo:**
Khi endpoint hoặc background process xử lý tập dữ liệu lớn theo kiểu tuần tự, cân nhắc `IAsyncEnumerable<T>` để đọc và xử lý từng phần thay vì gọi `ToListAsync()` rồi giữ toàn bộ result set trong memory.

**Tại sao hữu ích:**
Materialize hàng trăm nghìn row làm tăng allocation, GC pressure và thời gian chờ trước khi consumer nhận được dữ liệu đầu tiên. Async streaming cho phép pipeline bắt đầu xử lý sớm hơn và giữ working set nhỏ hơn, đặc biệt khi kết hợp với EF Core query hoặc file processing.

**Ví dụ:**
```csharp
await foreach (var order in db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .AsAsyncEnumerable()
    .WithCancellation(cancellationToken))
{
    await ProcessAsync(order, cancellationToken);
}
```

**Lưu ý:**
Streaming giữ database connection và reader mở lâu hơn. Nếu consumer xử lý chậm hoặc gọi external API bên trong loop, transaction/connection lifetime có thể kéo dài quá mức. Khi cần throughput cao, có thể phải batch hoặc tách read phase khỏi processing phase.

### Tip 2 — Khi gặp deadlock SQL, đọc deadlock graph thay vì chỉ tăng retry

**Mẹo:**
Nếu production xuất hiện deadlock, lấy deadlock graph hoặc Extended Events và xác định chính xác transaction nào giữ lock nào, transaction nào chờ lock nào, cùng thứ tự access resource của chúng.

**Tại sao hữu ích:**
Deadlock không đơn giản là “database quá tải”. Nó thường xuất phát từ hai transaction truy cập cùng resource theo thứ tự khác nhau, transaction kéo dài quá lâu hoặc query plan đọc phạm vi lớn hơn dự kiến. Retry chỉ giảm tác động tạm thời nhưng không sửa nguyên nhân.

**Ví dụ:**
Transaction A:
```text
UPDATE Orders ...
UPDATE Inventory ...
```

Transaction B:
```text
UPDATE Inventory ...
UPDATE Orders ...
```

Nếu hai transaction khóa resource theo thứ tự ngược nhau, chúng có thể tạo cycle. Một giải pháp có thể là chuẩn hóa thứ tự truy cập hoặc rút ngắn transaction boundary.

**Lưu ý:**
Không mặc định thêm `NOLOCK` để “hết deadlock”. `NOLOCK` thay đổi consistency semantics, không áp dụng cho mọi operation và có thể trả dữ liệu bẩn hoặc thiếu. Phải sửa contention dựa trên evidence.

### Tip 3 — Theo dõi `lock duration` khi xử lý message Azure Service Bus lâu

**Mẹo:**
Nếu handler có thể chạy lâu hơn message lock, phải hiểu cơ chế lock renewal và giới hạn thời gian xử lý. Với workload dài, cân nhắc chia nhỏ work hoặc chuyển phần nặng sang durable workflow thay vì chỉ tăng lock duration.

**Tại sao hữu ích:**
Azure Service Bus dùng peek-lock để đảm bảo at-least-once delivery. Nếu handler chưa `Complete` trước khi lock hết hạn, message có thể được redeliver trong khi lần xử lý đầu vẫn đang chạy, dẫn tới duplicate side effect.

**Ví dụ:**
Một handler nhận message `GenerateQuarterlyReport`, xử lý 8 phút nhưng lock chỉ 1 phút. Nếu auto-renew không được cấu hình phù hợp hoặc process mất renewal, consumer thứ hai có thể nhận lại cùng message. Handler vì vậy cần idempotent và workload nên được chia thành step nhỏ nếu có thể.

**Lưu ý:**
Không dựa vào lock renewal như cơ chế duy nhất để tránh duplicate. Network failure, process crash hoặc broker redelivery vẫn có thể xảy ra. Business side effect quan trọng phải có idempotency hoặc deduplication strategy.

### Tip 4 — Trong Vue.js, cleanup side effect của `watch` để tránh race và leak

**Mẹo:**
Khi `watch` tạo request, timer hoặc subscription, dùng cleanup callback để hủy side effect cũ trước khi watcher chạy lại.

**Tại sao hữu ích:**
Nếu filter thay đổi nhanh, nhiều request hoặc timer cũ có thể tiếp tục chạy và response cũ về muộn sẽ ghi đè state mới. Cleanup giúp mỗi watcher execution sở hữu rõ lifecycle của side effect nó tạo ra.

**Ví dụ:**
```ts
watch(searchTerm, async (value, _, onCleanup) => {
  const controller = new AbortController();
  onCleanup(() => controller.abort());

  const response = await fetch(`/api/search?q=${encodeURIComponent(value)}`, {
    signal: controller.signal
  });

  results.value = await response.json();
});
```

**Lưu ý:**
Cleanup không thay thế debounce nếu input thay đổi rất nhanh. Có thể cần cả debounce lẫn cancellation tùy UX và API cost.

### Tip 5 — Thiết kế structured logging để không ghi lộ dữ liệu nhạy cảm

**Mẹo:**
Xác định rõ field nào được phép xuất hiện trong log và tránh ghi trực tiếp access token, password, connection string, payment data hoặc payload chứa PII. Với object phức tạp, log các field cần cho diagnosis thay vì serialize toàn bộ object.

**Tại sao hữu ích:**
Log thường được gửi tới hệ thống tập trung, giữ lâu và có nhiều người hoặc service truy cập hơn database production. Một dòng log hữu ích cho debugging có thể vô tình biến thành kênh rò rỉ dữ liệu nếu chứa credential hoặc thông tin nhạy cảm.

**Ví dụ:**
Thay vì:
```csharp
logger.LogInformation("Login request: {@Request}", request);
```

hãy chọn dữ liệu cần thiết:
```csharp
logger.LogInformation(
    "Login failed for UserId {UserId}, CorrelationId {CorrelationId}",
    userId,
    correlationId);
```

**Lưu ý:**
Không redaction bằng cách thay vài field name rồi giả định mọi payload an toàn. DTO và exception từ third-party có thể chứa dữ liệu nhạy cảm ngoài dự kiến; logging policy cần được review như một phần security design.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like behavior. Repository riêng chỉ nên thêm khi nó tạo boundary hữu ích cho domain, query reuse hoặc thay đổi data source — không phải vì pattern luôn “đúng kiến trúc”.

**Vấn đề nó giải quyết:**
Team thường tạo repository generic cho mọi entity nhằm “decouple EF Core”, nhưng kết quả có thể là một abstraction chỉ wrap `Add`, `Update`, `GetAll` và làm mất khả năng dùng projection, `Include`, compiled query hoặc feature mới của EF Core.

**Ví dụ thực tế:**
Một application service chỉ cần query order và update status có thể dùng `AppDbContext` trực tiếp trong application layer. Ngược lại, một domain có logic truy vấn phức tạp như `IOrderReadModel` hoặc source dữ liệu thay đổi theo tenant có thể hưởng lợi từ abstraction riêng có intent rõ ràng.

**Trade-off:**
Direct `DbContext` giảm boilerplate, giữ toàn bộ sức mạnh EF Core và dễ tối ưu query. Repository có thể cô lập data-access concern và tạo contract rõ hơn, nhưng thêm layer, dễ rơi vào generic abstraction vô nghĩa và làm debugging SQL khó hơn.

**Middle → Senior insight:**
Middle developer cần hiểu lifecycle, tracking và query semantics của `DbContext` trước khi che chúng sau abstraction. Senior / Technical developer phải đánh giá coupling thực tế, test strategy, query complexity và khả năng thay đổi data source để quyết định abstraction có tạo giá trị hay chỉ tăng ceremony.

### Design 2 — Cache invalidation bằng TTL, event hay version key

**Khái niệm:**
Cache invalidation không có một chiến lược duy nhất. TTL phù hợp khi stale data trong một khoảng thời gian chấp nhận được; event-driven invalidation phù hợp khi cần phản ứng nhanh hơn; versioned key hữu ích khi muốn tránh race giữa write và cache refresh.

**Vấn đề nó giải quyết:**
Cache-aside đơn giản nhưng tạo khoảng thời gian cache chứa dữ liệu cũ sau khi database thay đổi. Nếu business requirement yêu cầu consistency chặt hơn, chỉ tăng TTL hoặc gọi `DEL` sau update có thể chưa đủ vì concurrent request có thể repopulate dữ liệu cũ.

**Ví dụ thực tế:**
Product detail cho phép stale 5 phút có thể dùng TTL. Price promotion cần cập nhật nhanh hơn có thể publish `ProductPriceChanged` để invalidator xóa key. Nếu race vẫn là vấn đề, key dạng `product:{id}:v{version}` có thể giúp reader không dùng lại representation cũ.

**Trade-off:**
TTL đơn giản và resilient nhưng stale window lớn hơn. Event invalidation giảm độ trễ cập nhật nhưng thêm messaging, retry và failure mode. Version key tránh một số race nhưng tạo nhiều key cũ và cần cleanup strategy.

**Middle → Senior insight:**
Middle developer cần hiểu stale-data tolerance và race trong cache-aside. Senior / Technical developer phải chọn strategy dựa trên consistency SLA, failure tolerance, traffic profile và operational cost thay vì áp một cơ chế invalidation cho mọi loại dữ liệu.

### Design 3 — Expand-and-Contract migration cho schema thay đổi không downtime

**Khái niệm:**
Expand-and-Contract thay đổi database schema theo nhiều bước tương thích ngược: trước tiên mở rộng schema để old/new application cùng chạy được, sau đó migrate traffic/data, cuối cùng mới loại bỏ cấu trúc cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment hoặc blue/green deployment, version cũ và mới của application có thể chạy đồng thời. Một migration kiểu rename/drop column ngay lập tức có thể làm version cũ lỗi trong lúc rollout chưa hoàn tất.

**Ví dụ thực tế:**
Muốn đổi `Customer.FullName` thành `FirstName` + `LastName`:
1. Thêm hai column mới nhưng giữ `FullName`.
2. Version mới ghi cả old và new fields hoặc dùng compatibility layer.
3. Backfill dữ liệu cũ.
4. Chuyển read sang fields mới.
5. Sau khi không còn version cũ, drop `FullName` trong release sau.

**Trade-off:**
Cách này giảm deployment risk và hỗ trợ rollback tốt hơn, nhưng migration kéo dài qua nhiều release, tạm thời duplicate schema/data và cần theo dõi trạng thái chuyển đổi rõ ràng.

**Middle → Senior insight:**
Middle developer cần viết migration backward-compatible và tránh assumption rằng deploy là atomic. Senior / Technical developer phải thiết kế sequence release, backfill strategy, rollback point, data verification và ownership để trạng thái compatibility tạm thời không tồn tại vô thời hạn.
