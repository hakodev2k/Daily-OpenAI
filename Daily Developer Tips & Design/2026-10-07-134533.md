# Daily Developer Tips & Design — 2026-10-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Projection trước, Include sau

**Mẹo:**
Với read-only API dùng EF Core, ưu tiên `Select` projection đúng shape response thay vì `Include` cả entity graph rồi mới map.

**Tại sao hữu ích:**
Projection giúp database chỉ trả các columns cần thiết, giảm materialization, change-tracking overhead và dữ liệu truyền qua network. Quan trọng hơn, SQL sinh ra phản ánh trực tiếp nhu cầu của endpoint thay vì cấu trúc domain object.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.CreatedAt,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Đừng mặc định thêm `AsNoTracking` nếu entities sau đó cần được update trong cùng `DbContext`. Projection phức tạp cũng phải kiểm tra SQL thực tế và execution plan; LINQ trông gọn không đảm bảo query rẻ.

### Tip 2 — Chẩn đoán connection pool exhaustion từ symptom, không tăng pool ngay

**Mẹo:**
Khi API bắt đầu timeout lúc lấy database connection, kiểm tra thời gian query, transaction duration, connection lifetime và concurrency trước khi tăng `Max Pool Size`.

**Tại sao hữu ích:**
Pool exhaustion thường là hậu quả: slow query giữ connection lâu, transaction bị mở quá rộng hoặc traffic vượt capacity. Tăng pool có thể chỉ chuyển bottleneck xuống SQL Server và làm database quá tải nhanh hơn.

**Ví dụ:**
Nếu p95 SQL tăng từ 80 ms lên 4 s, request concurrency không đổi nhưng số connection active chạm giới hạn, chuỗi suy luận hợp lý là: query chậm → connection bị giữ lâu → pool cạn → request mới chờ connection. Hãy tìm slow query/blocking trước.

**Lưu ý:**
Đừng nhầm `DbContext pooling` với ADO.NET connection pooling. Chúng tối ưu hai lớp khác nhau và không sửa được query/blocking kém.

### Tip 3 — Kubernetes readiness probe không phải liveness probe

**Mẹo:**
Dùng readiness để quyết định Pod có nên nhận traffic; dùng liveness để phát hiện process thực sự cần restart. Không biến mọi dependency check thành liveness condition.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp vào database tạm thời unavailable, Kubernetes có thể restart hàng loạt Pods đang khỏe, tạo restart storm đúng lúc dependency đang gặp sự cố.

**Ví dụ:**
ASP.NET Core service có thể expose health endpoints riêng: readiness kiểm tra các điều kiện cần để phục vụ traffic; liveness chỉ xác nhận process/event loop vẫn hoạt động. Khi database chập chờn, Pod có thể bị rút khỏi traffic mà không bị restart liên tục.

**Lưu ý:**
Readiness quá nhạy cũng gây traffic oscillation. Health check phải có timeout nhỏ, chi phí thấp và phản ánh khả năng phục vụ request chứ không phải kiểm tra toàn bộ hệ sinh thái.

### Tip 4 — Dùng browser Network waterfall để tách frontend chậm khỏi backend chậm

**Mẹo:**
Khi Vue.js/React.js page “load chậm”, xem Network waterfall và Timing trước khi tối ưu component hoặc API.

**Tại sao hữu ích:**
Một symptom phía UI có thể đến từ DNS/TLS, TTFB backend, request bị serialize, bundle lớn hoặc asset blocking. Waterfall cho bằng chứng để xác định thời gian đang mất ở network, server hay browser.

**Ví dụ:**
Nếu API TTFB là 120 ms nhưng request chỉ bắt đầu sau 2.5 s vì JavaScript bundle parse/execution, tối ưu SQL gần như không cải thiện user experience. Ngược lại TTFB 3 s với payload nhỏ chỉ về backend/dependency path.

**Lưu ý:**
DevTools trên máy developer không đại diện hoàn toàn production user. Kết hợp throttling, Core Web Vitals/RUM và server telemetry khi đánh giá vấn đề thực tế.

### Tip 5 — AI code review phải kiểm tra assumption, không chỉ syntax

**Mẹo:**
Khi dùng AI coding agent review PR, yêu cầu nó chỉ ra assumptions và dẫn chiếu file/API/version trong repository trước khi chấp nhận đề xuất.

**Tại sao hữu ích:**
AI có thể tạo nhận xét nghe hợp lý nhưng dựa trên API không tồn tại, version khác hoặc architecture assumption sai. Grounding vào source và tests biến AI thành bộ tăng tốc phân tích thay vì nguồn “best practice” không kiểm chứng.

**Ví dụ:**
Với PR thay retry policy, yêu cầu agent xác định nơi đăng ký `HttpClient`, package/version resilience đang dùng, existing timeout policy và tests liên quan; sau đó mới đánh giá duplicate retry hoặc timeout layering.

**Lưu ý:**
Generated tests có thể chỉ xác nhận implementation hiện tại thay vì business behavior. Human reviewer vẫn phải kiểm tra security, failure modes và trade-off mà repository context không thể hiện đầy đủ.

## 🧠 Software Design

### Design 1 — Optimistic concurrency vs pessimistic locking

**Khái niệm:**
Optimistic concurrency cho phép nhiều actors đọc cùng dữ liệu và phát hiện conflict khi ghi; pessimistic locking ngăn conflict sớm bằng lock trong transaction.

**Vấn đề nó giải quyết:**
Hai request cùng sửa một Order có thể gây lost update. Nhưng giữ database lock lâu để ngăn mọi conflict lại làm giảm concurrency và tăng blocking/deadlock risk.

**Ví dụ thực tế:**
Một CMS editor cập nhật content với `rowversion`. Nếu editor khác đã publish version mới, EF Core nhận concurrency conflict và UI yêu cầu merge/reload. Với workflow tài chính rất ngắn, contention cao và invariant bắt buộc, lock có thể hợp lý hơn nếu transaction được kiểm soát chặt.

**Trade-off:**
Optimistic concurrency scale tốt khi conflict hiếm nhưng cần conflict handling rõ ràng. Pessimistic locking đơn giản hóa một số critical sections nhưng giữ resource, tăng blocking và dễ tạo deadlock.

**Middle → Senior insight:**
Middle cần implement concurrency token, transaction và xử lý conflict đúng. Senior / Technical cần đánh giá conflict frequency, invariant, latency, retry semantics và user experience để chọn chiến lược; không chọn lock chỉ vì muốn “an toàn hơn”.

### Design 2 — Azure Functions vs Worker Service

**Khái niệm:**
Cả hai đều xử lý background workload, nhưng Azure Functions tối ưu cho event-driven/serverless execution còn Worker Service cho process dài hạn với lifecycle và resource control rõ hơn.

**Vấn đề nó giải quyết:**
Team thường chọn Functions vì triển khai nhanh hoặc Worker vì quen .NET, nhưng workload characteristics mới là yếu tố quyết định: burstiness, execution duration, connection reuse, scaling, scheduling và operational model.

**Ví dụ thực tế:**
Image metadata extraction từ Blob với workload thất thường có thể phù hợp Function trigger. Một consumer giữ nhiều long-lived connections, cần kiểm soát concurrency chi tiết và chạy liên tục có thể phù hợp Worker Service trên App Service/Kubernetes hơn.

**Trade-off:**
Functions giảm infrastructure management và scale theo event nhưng có cold-start/execution/runtime constraints tùy hosting plan. Worker cho nhiều quyền kiểm soát hơn nhưng team chịu trách nhiệm capacity, deployment và scaling nhiều hơn.

**Middle → Senior insight:**
Middle cần hiểu trigger, retry, idempotency và graceful shutdown. Senior / Technical cần so sánh cost model, workload shape, failure recovery, observability, scaling behavior và operational ownership trước khi chọn hosting model.

### Design 3 — API backward compatibility thay vì version hóa mọi thay đổi

**Khái niệm:**
API evolution ưu tiên thay đổi additive và contract-compatible; API versioning chỉ là một công cụ khi contract thật sự phải thay đổi không tương thích.

**Vấn đề nó giải quyết:**
Mobile app, CMS frontend và third-party clients không upgrade đồng thời với backend. Breaking change nhỏ ở JSON contract có thể làm client cũ lỗi ngay sau deployment.

**Ví dụ thực tế:**
Thêm optional field `displayName` thường không cần `/v2`. Nhưng đổi semantics của `status`, xóa field đang được consumer dùng hoặc thay authentication flow có thể cần migration window/version mới với telemetry để biết client cũ còn hoạt động.

**Trade-off:**
Backward compatibility giảm coordinated deployment nhưng giữ legacy contract lâu hơn. Versioning tạo đường migration rõ nhưng tăng code paths, tests, documentation và support burden nếu versions không có lifecycle.

**Middle → Senior insight:**
Middle cần tránh breaking serialization/schema changes và viết contract tests. Senior / Technical cần quản lý consumer inventory, deprecation policy, telemetry, migration window và quyết định khi nào compatibility cost lớn hơn việc tạo version mới.
