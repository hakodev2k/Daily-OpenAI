# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExceptionDispatchInfo` khi cần rethrow exception sau một boundary mà vẫn giữ original stack trace

**Mẹo:**
Nếu exception phải được capture ở một thời điểm nhưng rethrow ở context khác, dùng `ExceptionDispatchInfo.Capture(ex)` thay vì lưu exception rồi `throw ex;` sau đó.

**Tại sao hữu ích:**
`throw ex;` làm stack trace bắt đầu lại tại vị trí rethrow, khiến investigation production khó thấy call path gốc đã gây lỗi. `ExceptionDispatchInfo` giữ thông tin exception ban đầu và phù hợp cho các flow như handoff giữa callback, worker hoặc deferred error propagation.

**Ví dụ:**
```csharp
using System.Runtime.ExceptionServices;

ExceptionDispatchInfo? captured = null;

try
{
    await ProcessAsync(ct);
}
catch (Exception ex)
{
    captured = ExceptionDispatchInfo.Capture(ex);
}

// Có thể thực hiện cleanup / chuyển context trước khi propagate lỗi.
captured?.Throw();
```

Nếu chỉ catch để log rồi propagate ngay trong cùng scope, dùng `throw;` là đủ và đơn giản hơn.

**Lưu ý:**
Đừng dùng pattern này để trì hoãn exception tùy tiện hoặc biến exception thành control flow. Khi xử lý async thông thường, hãy để `await` propagate exception tự nhiên. Mục tiêu là bảo toàn diagnostic evidence khi thật sự có boundary cần capture/rethrow.

### Tip 2 — Dùng `ExecuteUpdateAsync` / `ExecuteDeleteAsync` cho bulk mutation không cần materialize entity

**Mẹo:**
Trong EF Core, khi cần update/delete nhiều row theo predicate nhưng không cần domain logic trên từng entity, cân nhắc `ExecuteUpdateAsync` hoặc `ExecuteDeleteAsync` thay vì query toàn bộ entity về memory rồi gọi `SaveChangesAsync`.

**Tại sao hữu ích:**
Materialize hàng nghìn entity tạo allocation, change-tracking overhead và thường sinh nhiều thao tác update. Set-based mutation được dịch thành SQL chạy trực tiếp ở database, giảm round-trip và memory pressure ở application.

**Ví dụ:**
```csharp
var cutoff = DateTimeOffset.UtcNow.AddDays(-30);

await db.Sessions
    .Where(x => x.RevokedAt == null && x.LastSeenAt < cutoff)
    .ExecuteUpdateAsync(
        setters => setters.SetProperty(
            x => x.RevokedAt,
            _ => DateTimeOffset.UtcNow),
        ct);
```

Với delete:
```csharp
await db.AuditStagingRows
    .Where(x => x.CreatedAt < cutoff)
    .ExecuteDeleteAsync(ct);
```

**Lưu ý:**
Các API này bypass change tracker và không tự chạy domain behavior gắn với entity lifecycle trong application. Nếu `DbContext` đang tracking cùng entity, state trong memory có thể trở nên stale. Chỉ dùng khi semantics của set-based SQL đúng với business rule và transaction boundary mong muốn.

### Tip 3 — Dùng keyset pagination cho feed lớn thay vì `OFFSET` tăng dần

**Mẹo:**
Với endpoint đọc tuần tự qua dataset lớn, ưu tiên keyset/seek pagination dựa trên sort key ổn định thay vì `OFFSET ... FETCH` với page number ngày càng lớn.

**Tại sao hữu ích:**
`OFFSET 500000` vẫn buộc database phải đi qua một lượng lớn row trước khi trả page tiếp theo. Keyset pagination bắt đầu từ last-seen key, thường tận dụng index hiệu quả hơn và ổn định hơn khi dữ liệu được insert/delete trong lúc client đang paginate.

**Ví dụ:**
```sql
-- Index phù hợp: (CreatedAt DESC, Id DESC)
SELECT TOP (50)
    Id, CreatedAt, CustomerId, Total
FROM dbo.Orders
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Cursor trả cho client có thể encode cặp `(CreatedAt, Id)` thay vì expose page number.

**Lưu ý:**
Keyset pagination không phù hợp nếu UX bắt buộc nhảy thẳng tới “page 237” hoặc cần arbitrary random access. Sort key phải deterministic; nếu `CreatedAt` có duplicate, thêm tie-breaker duy nhất như `Id` để tránh missing/duplicate row giữa các page.

### Tip 4 — Thiết kế compound index MongoDB theo query shape, không theo từng field độc lập

**Mẹo:**
Khi MongoDB query thường filter nhiều field rồi sort, hãy thiết kế compound index theo query shape thực tế thay vì tạo nhiều single-field index và kỳ vọng index intersection luôn tối ưu.

**Tại sao hữu ích:**
Một compound index đúng thứ tự có thể phục vụ equality filter, range và sort trong cùng access path, giảm số document/key phải scan. Với workload ổn định, đây thường là lựa chọn predictable hơn so với phụ thuộc vào optimizer ghép nhiều index riêng lẻ.

**Ví dụ:**
Query:
```javascript
db.orders.find({
  tenantId: "t-42",
  status: "Pending",
  createdAt: { $gte: ISODate("2026-09-01") }
}).sort({ createdAt: -1 }).limit(100)
```

Index có thể bắt đầu bằng các equality field rồi tới field phục vụ range/sort:
```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})
```

Xác nhận bằng `explain("executionStats")`, đặc biệt quan sát `totalKeysExamined`, `totalDocsExamined` và stage của plan.

**Lưu ý:**
Thứ tự index phụ thuộc workload, selectivity và query variants; không áp dụng một công thức máy móc. Mỗi index làm write/storage đắt hơn. Nếu projection, sort hoặc predicate khác đáng kể giữa các endpoint, có thể cần tách index hoặc điều chỉnh query model.

### Tip 5 — Dùng `git worktree` khi cần làm song song trên nhiều branch mà không clone repository lần nữa

**Mẹo:**
Khi đang xử lý một feature dài nhưng cần mở branch khác để hotfix, review hoặc chạy comparison build, dùng `git worktree` để có thêm working directory dùng chung object database của repository.

**Tại sao hữu ích:**
Stash/chuyển branch liên tục dễ làm mất context và tốn thời gian restore build state. Clone thêm repository lại nhân đôi object data và configuration. Worktree cho phép hai branch được checkout đồng thời ở hai thư mục riêng.

**Ví dụ:**
```bash
# Từ repository chính
git worktree add ../app-hotfix hotfix/payment-timeout

# Xem các worktree
git worktree list

# Sau khi xong
git worktree remove ../app-hotfix
```

Có thể tạo branch mới ngay khi add:
```bash
git worktree add -b fix/order-race ../app-order-race main
```

**Lưu ý:**
Một branch thông thường không thể được checkout đồng thời ở nhiều worktree. Các thư mục worktree vẫn dùng chung Git repository metadata, nên cần hiểu lifecycle trước khi xóa thư mục thủ công; ưu tiên `git worktree remove` và `git worktree prune` khi cleanup.

## 🧠 Software Design

### Design 1 — Inbox / Idempotent Consumer để message redelivery không biến thành duplicate business action

**Khái niệm:**
Trong message-driven system, broker thường cung cấp at-least-once delivery: cùng message có thể được giao lại khi consumer xử lý xong nhưng acknowledgement bị mất hoặc process crash đúng thời điểm xấu. Inbox/Idempotent Consumer lưu dấu message đã xử lý để business effect chỉ được áp dụng một lần về mặt logic.

**Vấn đề nó giải quyết:**
Giả sử `PaymentCaptured` được giao hai lần. Nếu consumer mỗi lần đều cộng credit hoặc tạo shipment mới, retry cơ chế reliability lại trở thành duplicate transaction.

**Ví dụ thực tế:**
```text
Consumer nhận messageId = msg-781

BEGIN TRANSACTION
  INSERT Inbox(MessageId = 'msg-781')
    -> unique constraint bảo vệ duplicate

  UPDATE Orders
    SET PaymentStatus = 'Captured'
    WHERE Id = ...
COMMIT

Broker redeliver msg-781
-> INSERT Inbox vi phạm unique key / phát hiện đã xử lý
-> bỏ qua business mutation
-> acknowledge message
```

Điểm quan trọng là deduplication record và business mutation nên có atomicity phù hợp, thường trong cùng database transaction nếu cùng datastore.

**Trade-off:**
Inbox tăng storage, index maintenance và cleanup requirement. Nó cũng không biến toàn bộ distributed workflow thành exactly-once: external side effect như gọi API bên thứ ba cần idempotency semantics riêng. Nếu operation vốn idempotent tự nhiên, một inbox table riêng có thể không cần thiết.

**Middle → Senior insight:**
Middle developer cần giả định message có thể bị deliver lại và tránh viết consumer theo happy-path “mỗi message chỉ đến một lần”. Senior / Technical developer phải thiết kế deduplication key, transaction boundary, retention/cleanup và idempotency xuyên qua external side effect thay vì tin vào marketing term “exactly once”.

### Design 2 — Anti-Corruption Layer khi tích hợp domain mới với legacy model không cùng ngôn ngữ nghiệp vụ

**Khái niệm:**
Anti-Corruption Layer (ACL) là boundary chuyển đổi contract và semantics giữa domain của hệ thống mình với external/legacy system, để model bên ngoài không lan trực tiếp vào core domain.

**Vấn đề nó giải quyết:**
Legacy ERP có thể gọi một trạng thái là `CLOSED` nhưng semantics thực tế gồm cả “fulfilled” và “cancelled”. Nếu domain mới dùng trực tiếp enum/string của ERP ở mọi nơi, business logic nội bộ bị khóa vào những khái niệm không chính xác và migration về sau trở nên khó khăn.

**Ví dụ thực tế:**
```text
Legacy ERP
  status = "CLOSED"
  type   = "C" / "R"
       │
       ▼
Anti-Corruption Layer
  - parse legacy contract
  - map terminology
  - validate incompatible state
       │
       ▼
Order Domain
  Fulfilled | Cancelled | Returned
```

ACL có thể là adapter/service/module riêng; giá trị cốt lõi nằm ở translation boundary rõ ràng chứ không phải bắt buộc tạo thêm microservice.

**Trade-off:**
ACL thêm mapping code và cần test contract hai phía. Với integration rất đơn giản, stable và terminology đã tương thích, layer riêng có thể là ceremony không cần thiết. Nhưng khi external model thay đổi độc lập hoặc có semantics “bẩn”, boundary này giảm coupling đáng kể.

**Middle → Senior insight:**
Middle developer cần tránh để DTO/vendor SDK trở thành domain model một cách vô thức. Senior / Technical developer phải xác định ownership của ubiquitous language, nơi đặt translation, cách version contract và chiến lược khi một external concept không map 1-1 vào model nội bộ.

### Design 3 — Separate control plane và data plane khi operation quản trị có failure/capacity profile khác traffic chính

**Khái niệm:**
Control plane quản lý configuration, policy, provisioning hoặc orchestration; data plane xử lý traffic/business data chính. Tách hai plane giúp operation quản trị không nằm chung critical path và resource budget với request throughput cao.

**Vấn đề nó giải quyết:**
Nếu mỗi request phải gọi một central configuration/admin service để quyết định tenant routing hoặc feature policy, outage của service quản trị có thể làm toàn bộ request path dừng dù data service vẫn khỏe. Ngược lại, traffic spike ở data path cũng có thể làm admin/provisioning operation không thực hiện được.

**Ví dụ thực tế:**
```text
Control plane
Admin API -> config store -> publish versioned config
                         │
                         ▼
                  distribution/cache
                         │
Data plane               ▼
Client -> API instances -> local/cached config -> business datastore
```

Data plane có thể tiếp tục chạy bằng last-known-good configuration trong một khoảng thời gian khi control plane tạm unavailable, tùy consistency/security requirement.

**Trade-off:**
Tách plane tăng architectural complexity, config propagation delay và yêu cầu versioning/observability rõ ràng. Với application nhỏ, load thấp và deployment đơn giản, một service chung có thể là lựa chọn đúng. Separation đáng giá khi availability, blast radius hoặc scale profile của hai loại operation thực sự khác nhau.

**Middle → Senior insight:**
Middle developer cần nhận ra config/admin dependency cũng có thể trở thành runtime dependency nguy hiểm. Senior / Technical developer phải quyết định consistency model cho config propagation, stale tolerance, fail-safe behavior, security boundary và SLO riêng cho control plane/data plane thay vì chỉ tách component theo tên.
