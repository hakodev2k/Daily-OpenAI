# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Điều tra Large Object Heap trước khi tối ưu GC bằng cảm giác

**Mẹo:**
Khi .NET service có memory tăng mạnh hoặc GC pause bất thường, kiểm tra allocation profile và xem application có tạo nhiều object lớn như `byte[]`, `char[]`, JSON buffer hoặc image buffer hay không trước khi chỉnh GC settings.

**Tại sao hữu ích:**
Object lớn thường đi vào Large Object Heap (LOH). Nếu request path liên tục tạo buffer lớn, memory pressure và full GC có thể tăng dù code không có memory leak thực sự. Root cause thường là allocation pattern hơn là GC configuration.

**Ví dụ:**
Một API download file đọc toàn bộ payload vào memory:

```csharp
var bytes = await httpClient.GetByteArrayAsync(url, cancellationToken);
return Results.File(bytes, "application/pdf");
```

Với file hàng chục MB và nhiều request đồng thời, mỗi request giữ một buffer lớn. Streaming từ source tới response có thể giảm peak allocation đáng kể.

**Lưu ý:**
Đừng kết luận LOH là nguyên nhân chỉ vì process dùng nhiều RAM. Dùng profiler, `dotnet-counters`, memory dump hoặc allocation trace để xác nhận object type, allocation rate và GC behavior trước khi thay đổi implementation.

### Tip 2 — Khi SQL Server query lúc nhanh lúc chậm, kiểm tra execution plan theo parameter thật

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có latency dao động lớn, kiểm tra actual execution plan, cardinality estimate và parameter values thay vì chỉ nhìn query text.

**Tại sao hữu ích:**
Một cached plan tốt cho parameter có ít row có thể không phù hợp với parameter trả về hàng triệu row. Data skew, statistics và parameter-sensitive behavior có thể khiến optimizer chọn nested loops, hash join hoặc index access rất khác nhau.

**Ví dụ:**
Một query:

```sql
SELECT Id, Total
FROM Orders
WHERE CustomerId = @CustomerId;
```

`CustomerId = 42` có 30 orders nhưng `CustomerId = 9001` có 3 triệu orders. Nếu production symptom chỉ xuất hiện với tenant lớn, hãy so actual rows với estimated rows và plan được reuse.

**Lưu ý:**
Đừng dùng `OPTION (RECOMPILE)` hoặc clear plan cache như fix mặc định. Recompile tăng CPU và plan-cache reset ảnh hưởng workload khác. Cần xác định data skew, statistics, index design và SQL Server version trước khi chọn strategy.

### Tip 3 — Với Playwright, ưu tiên locator theo semantics thay vì CSS selector mong manh

**Mẹo:**
Trong end-to-end test, ưu tiên `getByRole`, `getByLabel`, `getByText` hoặc stable test id thay vì selector phụ thuộc sâu vào DOM structure hay CSS class sinh tự động.

**Tại sao hữu ích:**
Selector kiểu `.checkout > div:nth-child(3) button` dễ vỡ khi UI refactor dù behavior không đổi. Semantic locator gần với cách user tương tác và giúp test phản ánh contract UI tốt hơn.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Place order' }).click();
await expect(page.getByRole('heading', { name: 'Order confirmed' }))
  .toBeVisible();
```

Test vẫn ổn nếu team thay layout hoặc CSS nhưng giữ semantics của action.

**Lưu ý:**
Không nên lạm dụng `data-testid` cho mọi element. Nếu accessibility role/label đã đủ rõ, dùng chúng trước. Test id phù hợp khi không có semantic selector ổn định hoặc UI component quá động.

### Tip 4 — Cấu hình Kubernetes requests/limits dựa trên telemetry, không copy một con số cho mọi service

**Mẹo:**
Dùng historical CPU/memory usage, load test và headroom yêu cầu để đặt `requests` và `limits` cho từng workload thay vì sao chép cấu hình mẫu giữa các service.

**Tại sao hữu ích:**
`requests` ảnh hưởng scheduling và capacity planning; `limits` ảnh hưởng runtime behavior. CPU limit quá thấp có thể gây throttling, còn memory limit quá thấp có thể dẫn tới OOMKill dù node vẫn còn memory.

**Ví dụ:**
Một API có telemetry:

```text
CPU p95: 350m
Memory p95: 420Mi
Memory peak under load: 610Mi
```

Cấu hình có thể bắt đầu từ evidence này rồi validate bằng load test, thay vì đặt mặc định `100m/128Mi` chỉ vì template có sẵn.

**Lưu ý:**
Đừng tối ưu chỉ cho average usage. Burst workload, GC, startup và traffic spike đều cần headroom. Sau deployment phải tiếp tục quan sát throttling, OOMKill và saturation để hiệu chỉnh.

### Tip 5 — Với Optimizely CMS, tách content model khỏi presentation concern

**Mẹo:**
Khi định nghĩa Page Type hoặc Block Type, model content theo ý nghĩa biên tập và domain content thay vì encode trực tiếp layout hiện tại như `LeftColumnText`, `BlueButtonText` hoặc `DesktopImageOnly`.

**Tại sao hữu ích:**
Presentation thay đổi thường xuyên hơn meaning của content. Nếu schema bị khóa vào layout, redesign UI sẽ kéo theo migration content, editor confusion và khó reuse content cho headless/API channels.

**Ví dụ:**
Thay vì field:

```text
BlueButtonText
BlueButtonUrl
```

có thể dùng model có ý nghĩa hơn:

```text
PrimaryAction.Label
PrimaryAction.Url
```

UI layer quyết định màu, vị trí và responsive behavior.

**Lưu ý:**
Không cần abstract hóa mọi field thành generic content primitive. Nếu một component thực sự chỉ tồn tại cho một experience cụ thể, model chuyên biệt có thể rõ hơn. Mục tiêu là tránh coupling presentation không cần thiết.

## 🧠 Software Design

### Design 1 — Dùng trực tiếp `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và collection-style access qua `DbSet`. Repository abstraction chỉ đáng thêm khi nó tạo boundary hoặc capability có giá trị, không phải vì mọi project cần một lớp bọc quanh EF Core.

**Vấn đề nó giải quyết:**
Team thường tạo `IGenericRepository<T>` với `GetAll`, `Add`, `Update` rồi cuối cùng vẫn phải thêm method đặc biệt cho mọi query. Abstraction này có thể che mất LINQ/query capability mà không giảm coupling thực tế.

**Ví dụ thực tế:**
Một application service đơn giản có thể dùng trực tiếp:

```text
Application use case
-> AppDbContext
-> EF Core
```

Trong khi một bounded module cần encapsulate aggregate loading hoặc data source có thể thay đổi thì repository business-specific như `IOrderRepository` có thể tạo contract hữu ích hơn generic CRUD repository.

**Trade-off:**
Dùng trực tiếp `DbContext` giảm ceremony và giữ toàn bộ EF Core capability, nhưng application layer phụ thuộc rõ vào EF Core. Repository có thể tạo boundary tốt hơn, nhưng dễ trở thành abstraction rỗng, duplicate query API và tăng maintenance.

**Middle → Senior insight:**
Middle developer cần hiểu transaction scope, query composition và không tạo repository chỉ để bọc từng method của `DbSet`. Senior / Technical developer phải quyết định abstraction dựa trên domain boundary, test strategy, khả năng thay data source và cost của việc che mất ORM capability.

### Design 2 — Synchronous REST vs Asynchronous Messaging

**Khái niệm:**
REST đồng bộ phù hợp khi caller cần kết quả ngay để tiếp tục flow. Messaging phù hợp khi work có thể xử lý bất đồng bộ, cần decouple thời gian xử lý hoặc cần hấp thụ burst và retry độc lập.

**Vấn đề nó giải quyết:**
Nếu checkout gọi tuần tự nhiều service và tất cả đều phải trả lời trước khi request hoàn tất, latency và failure coupling tăng. Nhưng chuyển mọi call thành message cũng làm UX, consistency và debugging phức tạp hơn.

**Ví dụ thực tế:**
Có thể giữ đồng bộ:

```text
Checkout API -> Pricing API
```

vì user cần total trước khi xác nhận.

Nhưng sau order commit:

```text
OrderPlaced -> notification / analytics / loyalty consumers
```

có thể xử lý qua messaging vì không cần chặn response checkout.

**Trade-off:**
REST đơn giản về request/response và immediate consistency nhưng tạo temporal coupling và dễ lan truyền timeout. Messaging tăng resilience và decoupling nhưng thêm eventual consistency, duplicate delivery, broker operations và observability complexity.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry, idempotency và failure semantics của cả hai model. Senior / Technical developer phải chọn dựa trên business latency requirement, ownership, consistency, failure isolation và operational cost thay vì mặc định “microservices thì phải messaging”.

### Design 3 — Normalization vs Denormalization theo read/write pressure

**Khái niệm:**
Normalization giảm duplication và giữ source-of-truth rõ bằng cách tách dữ liệu theo quan hệ. Denormalization chủ động duplicate hoặc precompute dữ liệu để tối ưu read path khi query cost hoặc latency requirement biện minh cho nó.

**Vấn đề nó giải quyết:**
Một schema quá normalized có thể buộc dashboard chạy nhiều join nặng. Ngược lại, duplicate dữ liệu quá sớm khiến mọi update phải đồng bộ nhiều nơi và dễ sinh inconsistency.

**Ví dụ thực tế:**
Transactional order data giữ chuẩn hóa:

```text
Orders
OrderLines
Products
```

Nhưng reporting screen có thể dùng projection/materialized view chứa sẵn:

```text
OrderId
CustomerName
ItemCount
GrossTotal
```

được rebuild hoặc update theo workflow rõ ràng.

**Trade-off:**
Normalization giúp consistency và update model rõ hơn nhưng có thể tăng join cost. Denormalization giúp read nhanh và contract đơn giản hơn nhưng tăng storage, synchronization logic và nguy cơ stale data.

**Middle → Senior insight:**
Middle developer cần hiểu index/query plan trước khi denormalize. Senior / Technical developer phải đánh giá read/write ratio, freshness requirement, rebuild strategy, ownership của duplicated data và khả năng hệ thống chấp nhận eventual consistency.
