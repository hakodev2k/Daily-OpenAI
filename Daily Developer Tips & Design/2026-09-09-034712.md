# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `await using` khi resource có cleanup bất đồng bộ

**Mẹo:**
Với resource implement `IAsyncDisposable`, dùng `await using` để cleanup theo async path thay vì ép cleanup đồng bộ hoặc quên dispose.

**Tại sao hữu ích:**
Một số resource cần flush hoặc release tài nguyên qua I/O. Nếu dispose đồng bộ trong hot path, thread có thể bị block; nếu không dispose, connection, stream hoặc unmanaged resource có thể sống lâu hơn cần thiết.

**Ví dụ:**
```csharp
await using var stream = await blobClient.OpenWriteAsync(
    overwrite: true,
    cancellationToken: cancellationToken);

await source.CopyToAsync(stream, cancellationToken);
```

Compiler sẽ gọi `DisposeAsync()` khi scope kết thúc, kể cả khi exception xảy ra.

**Lưu ý:**
Không phải object nào implement `IDisposable` cũng cần `IAsyncDisposable`. Đừng tự thêm async disposal nếu cleanup không có I/O hoặc không có lợi ích thực tế; complexity API sẽ tăng mà không cải thiện behavior.

### Tip 2 — Dùng `FOR UPDATE SKIP LOCKED` khi nhiều worker lấy job từ PostgreSQL

**Mẹo:**
Nếu nhiều worker cùng poll một bảng job và cần mỗi job chỉ được một worker lấy tại một thời điểm, cân nhắc `FOR UPDATE SKIP LOCKED` trong transaction ngắn.

**Tại sao hữu ích:**
Không có locking strategy, hai worker có thể cùng đọc một row `Pending` rồi cùng xử lý. `SKIP LOCKED` cho phép worker bỏ qua row đã bị worker khác lock thay vì chờ, giúp competing consumers giữ throughput tốt hơn.

**Ví dụ:**
```sql
BEGIN;

SELECT id
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;

UPDATE jobs
SET status = 'Processing'
WHERE id = @id;

COMMIT;
```

**Lưu ý:**
Pattern này không thay thế message broker khi cần durability, retry semantics, fan-out hoặc cross-service delivery. Transaction phải ngắn; giữ lock trong lúc thực hiện network I/O dài sẽ làm giảm concurrency.

### Tip 3 — Với Azure Service Bus, theo dõi lock duration khi handler xử lý lâu

**Mẹo:**
Nếu message handler có thể chạy lâu hơn lock duration, bật hoặc kiểm soát lock renewal và đo thời gian xử lý thực tế thay vì giả định một message chỉ được giao một lần.

**Tại sao hữu ích:**
Service Bus dùng peek-lock để cho consumer thời gian xử lý. Nếu lock hết hạn trước khi message được complete, message có thể được delivery lại cho consumer khác dù handler đầu tiên vẫn đang chạy.

**Ví dụ:**
```text
Message received at 10:00:00
Lock expires at 10:00:30
Processing takes 45s
-> lock expires
-> another consumer receives same message
-> duplicate side effect possible
```

Nếu operation có thể dài, cần auto-renew hợp lý và consumer idempotent.

**Lưu ý:**
Tăng lock duration vô hạn không phải giải pháp. Work quá dài có thể nên tách nhỏ hoặc chuyển sang orchestration khác. Luôn thiết kế cho duplicate delivery vì at-least-once delivery vẫn tồn tại.

### Tip 4 — Dùng `git bisect` để tìm commit gây regression thay vì đọc diff thủ công hàng chục commit

**Mẹo:**
Khi biết một version cũ chạy tốt và version hiện tại bị lỗi, dùng `git bisect` để binary-search commit gây regression.

**Tại sao hữu ích:**
Nếu có 128 commit giữa good và bad, binary search thường chỉ cần khoảng 7 lần test thay vì kiểm tra từng commit. Đây là cách rất hiệu quả cho bug xuất hiện sau nhiều thay đổi nhỏ.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v4.2.0
```

Sau mỗi checkout tự động, chạy test hoặc reproduce bug rồi đánh dấu:
```bash
git bisect good
# hoặc
git bisect bad
```

**Lưu ý:**
`git bisect` hiệu quả nhất khi có test/reproduction deterministic. Nếu bug flaky hoặc mỗi commit giữa chừng không build được, quá trình sẽ khó tin cậy hơn; có thể cần script hóa test và dùng `git bisect skip` khi cần.

### Tip 5 — File upload cần xác thực nội dung, không chỉ extension và `Content-Type`

**Mẹo:**
Khi API nhận upload, kiểm tra kích thước, file signature/magic bytes, loại nội dung cho phép và nơi lưu file; không tin hoàn toàn extension hoặc `Content-Type` do client gửi.

**Tại sao hữu ích:**
Client có thể đổi tên executable thành `.jpg` hoặc gửi header giả. Nếu backend lưu file vào web root hoặc cho browser render trực tiếp, payload nguy hiểm có thể trở thành XSS, malware distribution hoặc code execution tùy platform.

**Ví dụ:**
Một policy upload ảnh có thể gồm:
```text
- max size: 10 MB
- allowlist: JPEG/PNG
- verify magic bytes
- generate server-side filename
- store outside executable/web-root path
- malware scanning nếu risk profile yêu cầu
```

**Lưu ý:**
Magic-byte validation cũng không chứng minh file hoàn toàn an toàn. Với định dạng phức tạp như PDF hoặc Office documents, cần cân nhắc sandboxing, scanning và content-disposition phù hợp khi download lại.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation để một dependency lỗi không kéo toàn hệ thống xuống

**Khái niệm:**
Bulkhead Isolation chia resource như concurrency, connection hoặc worker capacity theo dependency/workload thay vì để mọi request dùng chung một pool không giới hạn.

**Vấn đề nó giải quyết:**
Nếu một third-party API chậm, hàng trăm request có thể cùng chờ nó và chiếm hết thread, connection hoặc semaphore của application. Khi đó những endpoint không liên quan cũng bắt đầu fail.

**Ví dụ thực tế:**
```text
Checkout API
  -> Payment API: max 30 concurrent calls
  -> Recommendation API: max 10 concurrent calls
```

Nếu Recommendation API treo, nó chỉ làm đầy bulkhead 10 slots thay vì giữ toàn bộ outbound capacity.

**Trade-off:**
Bulkhead giảm blast radius và bảo vệ core workload nhưng giới hạn concurrency có thể làm request bị reject sớm hoặc queue lâu hơn. Cần chọn capacity dựa trên SLA, dependency throughput và fallback behavior.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, concurrency limit và fallback của từng dependency. Senior / Technical developer phải xác định resource nào cần tách, mức capacity nào hợp lý và ưu tiên business nào phải được bảo vệ khi hệ thống chịu partial failure.

### Design 2 — Idempotency Key cho API tạo giao dịch

**Khái niệm:**
Idempotency Key cho phép client retry một request tạo side effect mà không vô tình tạo duplicate transaction. Server ghi nhận key cùng kết quả hoặc trạng thái xử lý để request lặp lại được nhận diện.

**Vấn đề nó giải quyết:**
Client gửi `POST /payments`, server đã charge thành công nhưng response bị timeout. Client không biết kết quả và retry. Nếu API không idempotent, khách hàng có thể bị charge hai lần.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: 7d8f...
```

Server lưu:
```text
(key, request fingerprint, status, response)
```

Request cùng key và cùng payload nhận lại kết quả cũ thay vì thực thi payment lần nữa.

**Trade-off:**
Idempotency tăng reliability nhưng cần storage, TTL, collision policy, request fingerprint và xử lý trạng thái “đang thực thi”. Key reuse với payload khác phải bị từ chối rõ ràng.

**Middle → Senior insight:**
Middle developer cần implement key uniqueness và duplicate detection đúng. Senior / Technical developer phải quyết định phạm vi key, retention, consistency boundary, behavior khi request đầu tiên crash giữa chừng và cách phối hợp với downstream system cũng có idempotency riêng.

### Design 3 — Shared Database giữa modules: chấp nhận được nếu ownership boundary vẫn rõ

**Khái niệm:**
Nhiều module có thể cùng dùng một physical database mà vẫn giữ ownership logic riêng, miễn là module này không tùy tiện đọc/ghi table nội bộ của module khác.

**Vấn đề nó giải quyết:**
Tách database quá sớm làm tăng migration, transaction và vận hành. Nhưng dùng shared database không có ownership rule lại tạo coupling schema mạnh: một module thay column có thể phá module khác mà không ai nhận ra.

**Ví dụ thực tế:**
```text
Orders module -> owns Orders.*, OrderLines.*
Catalog module -> owns Products.*, Categories.*
```

Nếu Orders cần product information, ưu tiên contract rõ như application API, read model hoặc controlled view thay vì join trực tiếp mọi table Catalog trong business code.

**Trade-off:**
Shared database đơn giản về deployment, backup và local transaction, nhưng giảm isolation và dễ tạo shortcut coupling. Database-per-service tăng autonomy nhưng thêm distributed consistency, operational cost và migration complexity.

**Middle → Senior insight:**
Middle developer cần tôn trọng schema ownership và tránh direct cross-module writes. Senior / Technical developer phải quyết định khi physical database separation thực sự tạo giá trị dựa trên team ownership, scaling, compliance, failure isolation và nhu cầu independent deployment.
