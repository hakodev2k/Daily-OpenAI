# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt timeout với caller cancellation trong ASP.NET Core

**Mẹo:**
Khi gọi dependency, đừng gom mọi `OperationCanceledException` thành “request timeout”. Tách cancellation do client/request bị hủy khỏi timeout do dependency vượt latency budget, rồi ghi telemetry khác nhau.

**Tại sao hữu ích:**
Cả timeout và cancellation thường biểu hiện qua cancellation token, nhưng ý nghĩa vận hành khác nhau. Client đóng kết nối không nhất thiết là lỗi backend; dependency timeout lại là tín hiệu reliability cần theo dõi. Gộp chúng làm error rate và root-cause analysis sai lệch.

**Ví dụ:**
```csharp
using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    httpContext.RequestAborted, timeoutCts.Token);

try
{
    await paymentClient.CheckAsync(linked.Token);
}
catch (OperationCanceledException) when (timeoutCts.IsCancellationRequested &&
                                         !httpContext.RequestAborted.IsCancellationRequested)
{
    // dependency timeout
}
```
Telemetry có thể phân biệt `client_cancelled` và `dependency_timeout` thay vì báo chung một exception type.

**Lưu ý:**
Đừng tạo timeout riêng ở từng layer mà không tính end-to-end budget. Nhiều timeout chồng nhau có thể khiến layer ngoài hủy trước layer trong và làm diagnosis khó hơn; timeout policy nên có ownership rõ.

### Tip 2 — Dùng optimistic concurrency cho lost update trong EF Core

**Mẹo:**
Với record có thể bị nhiều user/process sửa đồng thời, dùng concurrency token như SQL Server `rowversion` thay vì giả định lần `SaveChangesAsync` cuối cùng luôn hợp lệ.

**Tại sao hữu ích:**
Hai request có thể đọc cùng version của entity, sửa các giá trị khác nhau rồi lần ghi sau âm thầm đè lần trước. EF Core đưa concurrency token vào `WHERE` của `UPDATE`; nếu record đã đổi, affected rows bằng 0 và EF Core ném `DbUpdateConcurrencyException` để application quyết định conflict policy.

**Ví dụ:**
```csharp
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }
    [Timestamp]
    public byte[] Version { get; set; } = default!;
}
```
Admin A và B cùng mở Product. A lưu trước; khi B lưu version cũ, backend trả conflict hoặc reload/merge theo business rule thay vì silently overwrite.

**Lưu ý:**
Không retry `DbUpdateConcurrencyException` một cách mù quáng. Retry chỉ có ý nghĩa nếu application reload state và xác định cách merge/reapply intent; với business conflict thật sự, `409 Conflict` có thể đúng hơn.

### Tip 3 — Kiểm tra connection-pool saturation trước khi tăng pool size

**Mẹo:**
Khi API xuất hiện timeout lấy database connection, đo thời gian giữ connection, query latency, transaction duration và số request đồng thời trước khi tăng `Max Pool Size`.

**Tại sao hữu ích:**
Connection pool cạn thường là triệu chứng: query chậm, transaction giữ connection quá lâu, workload concurrency tăng hoặc connection bị leak. Tăng pool có thể chuyển bottleneck xuống database và làm SQL Server/PostgreSQL chịu nhiều concurrent work hơn thay vì sửa nguyên nhân.

**Ví dụ:**
Sau deployment, p95 API tăng từ 300 ms lên 8 s và log có lỗi chờ connection. Trace cho thấy một query mới giữ connection 6 s. Tối ưu query/index hoặc giảm work trong transaction giải quyết throughput tốt hơn việc tăng pool từ 100 lên 500.

**Lưu ý:**
Pool size vẫn là capacity parameter hợp lệ, nhưng phải sizing cùng database capacity và workload. Đảm bảo connection/reader/transaction được dispose đúng; đừng dùng pool tuning để che resource lifetime sai.

### Tip 4 — File upload phải kiểm tra nội dung và giới hạn resource, không chỉ extension

**Mẹo:**
Với ASP.NET Core file upload, áp dụng size limit, allowlist loại file theo business need, kiểm tra content/signature khi phù hợp, tạo tên lưu trữ phía server và lưu file ngoài web root hoặc qua object storage.

**Tại sao hữu ích:**
Filename và `Content-Type` do client cung cấp không phải trust boundary. Chỉ kiểm tra `.jpg` không ngăn payload giả mạo, path manipulation hoặc file quá lớn gây memory/disk pressure. Streaming và quota giúp giới hạn blast radius.

**Ví dụ:**
CMS nhận ảnh editorial: backend giới hạn kích thước, bỏ filename gốc khỏi storage key, xác thực format ảnh trước xử lý, scan theo security policy rồi ghi Blob Storage bằng identity có quyền tối thiểu. Metadata hiển thị cho editor được tách khỏi physical object name.

**Lưu ý:**
Magic-byte validation cũng không chứng minh file hoàn toàn an toàn. Parser/decoder có thể có vulnerability và archive có thể gây decompression bomb. Mức kiểm tra phải phù hợp threat model; không parse format không cần thiết.

### Tip 5 — AI-generated migration cần được kiểm chứng bằng schema và dữ liệu thật

**Mẹo:**
Khi dùng AI coding agent để tạo EF Core/SQL migration, yêu cầu agent đối chiếu entity configuration, migration history và database constraints; sau đó chạy migration trên database representative và review SQL trước production.

**Tại sao hữu ích:**
Agent có thể sinh migration compile được nhưng suy đoán sai nullability, default, index uniqueness hoặc data backfill. Schema migration là state transition của dữ liệu, nên correctness không thể xác nhận chỉ bằng việc solution build thành công.

**Ví dụ:**
Agent đề xuất đổi `Customer.ExternalId` từ nullable sang required. Trước khi áp dụng, kiểm tra production-like data có `NULL`, tạo explicit backfill/validation phase rồi mới enforce `NOT NULL`; review generated SQL để tránh table rewrite/lock ngoài dự kiến.

**Lưu ý:**
Không giao quyền tự động apply production migration chỉ vì test pass. Với bảng lớn, cần đánh giá lock duration, online-operation support, rollback/roll-forward strategy và deployment compatibility giữa phiên bản application cũ/mới.

## 🧠 Software Design

### Design 1 — Azure Functions hay Worker Service phải chọn theo execution model

**Khái niệm:**
Azure Functions phù hợp với event-driven execution được platform quản lý trigger/scaling; Worker Service phù hợp khi application cần process dài hạn, lifecycle và concurrency control chủ động hơn. Đây là quyết định operational model, không chỉ là chọn project template.

**Vấn đề nó giải quyết:**
Background workload có hình dạng rất khác nhau: xử lý Blob event ngắn, Service Bus message bursty, scheduler định kỳ, hoặc processor luôn chạy với connection/state dài hạn. Chọn sai hosting model có thể làm cold start, execution constraint, scaling behavior hoặc operational complexity không phù hợp workload.

**Ví dụ thực tế:**
Một pipeline thumbnail chạy theo Blob event và workload biến động mạnh có thể phù hợp Azure Functions. Một message processor cần kiểm soát concurrency chặt, warm state, custom shutdown và predictable long-running behavior có thể phù hợp .NET Worker chạy trên App Service/container hơn.

**Trade-off:**
Functions giảm infrastructure management và tích hợp trigger tốt nhưng tăng phụ thuộc hosting semantics/cost model. Worker Service cho control lớn hơn nhưng team phải sở hữu deployment, scaling, health và capacity nhiều hơn. Không có lựa chọn mặc định tốt cho mọi background job.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, cancellation và graceful shutdown của hosting model đang dùng. Senior / Technical developer phải đánh giá workload duration, burst profile, scaling, cold start, delivery guarantee, operational ownership và cost trước khi chọn Functions hay Worker Service.

### Design 2 — SQL hay NoSQL nên bắt đầu từ access pattern và consistency boundary

**Khái niệm:**
Chọn relational database hay document/partitioned NoSQL dựa trên invariant, transaction boundary, query pattern, scale và cách dữ liệu phân bố; không dựa trên khẩu hiệu “NoSQL scale tốt hơn” hoặc “SQL luôn an toàn hơn”.

**Vấn đề nó giải quyết:**
Một model có nhiều relationship, ad-hoc query và transaction đa entity thường hưởng lợi từ relational semantics. Ngược lại, aggregate có access pattern rõ, partition key ổn định và cần phân phối throughput lớn có thể phù hợp document store như Cosmos DB/MongoDB.

**Ví dụ thực tế:**
Order/payment ledger cần relational constraints và transaction chặt có thể ở SQL Server/PostgreSQL. Một read-heavy customer activity document được truy cập chủ yếu theo `CustomerId`, chấp nhận denormalization và partition tốt có thể nằm ở document store. Không cần ép cả hệ thống dùng một database type.

**Trade-off:**
NoSQL thường chuyển một phần complexity sang partition-key design, denormalization và consistency; relational database có thể gặp scale/query bottleneck nếu schema và workload không được thiết kế đúng. Polyglot persistence lại tăng backup, monitoring và skill-set vận hành.

**Middle → Senior insight:**
Middle developer cần hiểu transaction/query/index model của datastore. Senior / Technical developer phải xác định invariant và access pattern trước, dự báo partition growth/hotspot, đánh giá operational cost và chỉ thêm datastore thứ hai khi lợi ích vượt complexity của việc vận hành nhiều nguồn dữ liệu.

### Design 3 — Anti-Corruption Layer bảo vệ domain khỏi contract của hệ thống ngoài

**Khái niệm:**
Anti-Corruption Layer (ACL) đặt mapping/translation boundary giữa domain của mình và model/protocol của external hoặc legacy system, để thuật ngữ và quirks bên ngoài không lan trực tiếp vào core business model.

**Vấn đề nó giải quyết:**
Third-party API thường có naming, status, null semantics và lifecycle khác domain nội bộ. Nếu entity/application service phụ thuộc trực tiếp DTO bên ngoài, mỗi thay đổi vendor có thể lan rộng và domain dần phản ánh constraint của integration thay vì business của chính hệ thống.

**Ví dụ thực tế:**
ERP trả `CustomerStatus = "A"/"H"/"D"` và nhiều field legacy. Integration adapter chuyển chúng thành `CustomerState.Active/Hold/Disabled` cùng model nội bộ tối thiểu. Khi ERP đổi contract hoặc được thay vendor, phần lớn domain không cần biết.

**Trade-off:**
ACL tạo mapping code, test và đôi khi duplication. Với integration rất nhỏ, ổn định và model gần như trùng khớp, một abstraction lớn có thể là ceremony. Boundary nên tỷ lệ với mức volatility và semantic mismatch thực tế.

**Middle → Senior insight:**
Middle developer cần tránh đưa vendor DTO sâu vào domain và test mapping/error handling. Senior / Technical developer phải xác định integration boundary, ownership của canonical model, chiến lược versioning/failure và cân nhắc khi nào adapter mỏng là đủ thay vì dựng một integration framework quá mức.
