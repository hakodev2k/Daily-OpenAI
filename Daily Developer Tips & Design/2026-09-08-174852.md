# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Stream file lớn trong ASP.NET Core thay vì buffer toàn bộ vào memory

**Mẹo:**
Với upload/download file lớn, ưu tiên streaming trực tiếp giữa request/response stream và storage thay vì đọc toàn bộ file thành `byte[]`, `MemoryStream` hoặc object lớn trong memory trước khi xử lý.

**Tại sao hữu ích:**
Buffer toàn bộ payload làm memory tăng theo kích thước file và số request đồng thời. Chỉ vài chục upload 200 MB có thể tạo allocation pressure, Large Object Heap pressure và GC pause lớn dù CPU không cao. Streaming giữ memory gần như ổn định theo buffer size.

**Ví dụ:**
```csharp
app.MapPost("/uploads", async (
    HttpRequest request,
    BlobContainerClient container,
    CancellationToken cancellationToken) =>
{
    var blob = container.GetBlobClient(Guid.NewGuid().ToString("N"));

    await blob.UploadAsync(
        request.Body,
        overwrite: false,
        cancellationToken);

    return Results.Accepted();
});
```

Với download:
```csharp
return Results.Stream(
    blobStream,
    contentType: "application/octet-stream");
```

**Lưu ý:**
Streaming không thay thế giới hạn file size, authorization, malware scanning và validation. Nếu cần inspect toàn bộ file trước khi lưu, có thể phải dùng temporary storage thay vì memory. Cũng cần propagate `CancellationToken` để client disconnect không làm backend tiếp tục transfer vô ích.

### Tip 2 — Với PostgreSQL, dùng `EXPLAIN (ANALYZE, BUFFERS)` để phân biệt CPU-bound với I/O-bound query

**Mẹo:**
Khi một query chậm, xem execution plan cùng buffer statistics thay vì chỉ nhìn tổng duration. `BUFFERS` cho biết query đọc page từ shared cache hay phải lấy nhiều dữ liệu từ storage.

**Tại sao hữu ích:**
Hai query cùng mất 2 giây nhưng nguyên nhân có thể rất khác. Một query có thể scan quá nhiều row và tốn CPU; query khác có thể chờ I/O vì working set không nằm trong cache. Giải pháp index, rewrite query, memory tuning hoặc storage tuning vì vậy cũng khác nhau.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, customer_id, total_amount
FROM orders
WHERE status = 'Pending'
ORDER BY created_at DESC
LIMIT 100;
```

Một plan đáng chú ý có thể cho thấy:
```text
Seq Scan on orders
Rows Removed by Filter: 4,800,000
Buffers: shared hit=3200 read=42000
```

Đây là evidence tốt hơn nhiều so với kết luận chung chung rằng “database đang chậm”.

**Lưu ý:**
`ANALYZE` thực sự chạy query. Với `UPDATE`, `DELETE` hoặc query cực nặng trên production, phải cẩn thận và có thể dùng transaction/replica phù hợp. Không thêm index chỉ dựa trên một plan đơn lẻ nếu workload thực tế có nhiều query shape khác nhau.

### Tip 3 — Redis hot key có thể làm một node nghẽn dù cluster vẫn còn capacity

**Mẹo:**
Khi Redis latency tăng nhưng tổng memory/CPU cluster nhìn có vẻ ổn, kiểm tra key distribution và request frequency để tìm hot key thay vì chỉ scale thêm node.

**Tại sao hữu ích:**
Redis Cluster phân chia key theo hash slot. Nếu phần lớn traffic dồn vào một vài key, node sở hữu các slot đó có thể thành bottleneck trong khi node khác nhàn rỗi. Horizontal scaling không tự động giải quyết workload bị skew.

**Ví dụ:**
Một homepage cache:
```text
home:global
```

nhận 80% read traffic có thể thành hot key. Tùy semantics, có thể phân tán load bằng local cache ngắn hạn phía application, replica read strategy hoặc chia data thành nhiều key phù hợp hơn.

Một pattern phổ biến:
```text
request
-> L1 in-memory cache 1-5s
-> Redis
-> source-of-truth
```

có thể giảm lượng read dồn trực tiếp xuống Redis cho dữ liệu cực nóng.

**Lưu ý:**
Đừng shard một key chỉ để “phân tải” nếu application sau đó phải đọc và merge tất cả shard cho mỗi request. Cần đo command latency, hit rate và node-level CPU/network trước khi thay đổi model. Hot key là vấn đề traffic shape, không chỉ là vấn đề cache size.

### Tip 4 — Dùng `git rerere` để Git ghi nhớ cách bạn đã resolve conflict lặp lại

**Mẹo:**
Nếu team thường xuyên rebase/cherry-pick các branch dài và gặp cùng kiểu merge conflict nhiều lần, bật `git rerere` để Git ghi lại resolution trước đó và đề xuất lại khi conflict tương tự xuất hiện.

**Tại sao hữu ích:**
Các migration branch hoặc release branch có thể va chạm lặp lại trên cùng file cấu hình, dependency version hoặc generated metadata. Resolve cùng conflict thủ công nhiều lần vừa mất thời gian vừa tăng khả năng sửa không nhất quán.

**Ví dụ:**
```bash
git config --global rerere.enabled true
```

Lần đầu:
```text
rebase -> conflict -> resolve manually -> commit
```

Lần sau khi cùng conflict pattern xuất hiện, Git có thể tự áp resolution đã ghi nhớ và bạn chỉ cần review lại diff trước khi tiếp tục.

**Lưu ý:**
Không được xem `rerere` như auto-merge đáng tin tuyệt đối. Context business có thể đã thay đổi dù conflict text giống nhau. Luôn review staged diff và chạy test sau khi Git tái sử dụng resolution cũ.

### Tip 5 — Chặn SSRF bằng cách kiểm soát destination, không chỉ validate URL syntax

**Mẹo:**
Nếu backend nhận URL từ user rồi gọi outbound HTTP, hãy kiểm soát domain/IP destination được phép thay vì chỉ kiểm tra chuỗi có phải URL hợp lệ hay không.

**Tại sao hữu ích:**
Một URL hoàn toàn hợp lệ về syntax vẫn có thể trỏ tới metadata endpoint, localhost, internal admin service hoặc private network. SSRF xảy ra vì attacker lợi dụng network trust của backend để truy cập resource mà client bên ngoài không tới được.

**Ví dụ:**
Một image-import API không nên chấp nhận tùy ý:
```text
http://127.0.0.1:5000/admin
http://169.254.169.254/...
http://internal-service.local/
```

Thiết kế an toàn hơn có thể dùng:
```text
allowlist hostname
-> resolve DNS
-> reject private/link-local/loopback IP
-> connect
-> kiểm tra redirect destination lại ở mỗi hop
```

**Lưu ý:**
Chỉ regex hostname là chưa đủ vì DNS rebinding và redirect có thể đổi destination sau validation. Nếu use case không thực sự cần arbitrary outbound URL, allowlist provider/domain cố định thường đơn giản và an toàn hơn.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic: chọn theo ownership của message

**Khái niệm:**
Queue phù hợp khi một logical work item nên được xử lý bởi một consumer group. Topic + Subscription phù hợp khi cùng một event cần được phân phối độc lập tới nhiều consumer với lifecycle và filter riêng.

**Vấn đề nó giải quyết:**
Nếu dùng một queue cho `OrderPlaced` nhưng cả Billing, Analytics và Notification đều cần event, các consumer sẽ cạnh tranh nhau và chỉ một bên nhận message. Ngược lại, tạo topic cho một background job chỉ có một worker group có thể tăng operational complexity không cần thiết.

**Ví dụ thực tế:**
Background resize image:
```text
image-resize queue
-> nhiều competing workers
-> mỗi message được một worker xử lý
```

Domain event:
```text
OrderPlaced topic
  -> Billing subscription
  -> Analytics subscription
  -> Email subscription
```

Mỗi subscription có retry, dead-letter và filter policy riêng.

**Trade-off:**
Queue đơn giản hơn và phù hợp work distribution. Topic tăng decoupling và extensibility cho pub/sub nhưng thêm subscription management, duplicate processing path, schema compatibility và monitoring overhead.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumer khác fan-out như thế nào. Senior / Technical developer phải chọn topology dựa trên ownership, replay requirement, ordering, filter semantics và failure isolation — không đơn giản vì “topic linh hoạt hơn queue”.

### Design 2 — Hexagonal Architecture hữu ích nhất ở nơi integration thay đổi nhiều

**Khái niệm:**
Hexagonal Architecture dùng port để diễn tả capability mà application cần và adapter để kết nối capability đó với database, broker, filesystem hoặc third-party API cụ thể.

**Vấn đề nó giải quyết:**
Nếu business workflow gọi trực tiếp SDK của payment provider, Blob Storage hoặc Elasticsearch ở mọi nơi, domain/application logic nhanh chóng phụ thuộc vào infrastructure detail và khó test, thay thế hoặc migrate.

**Ví dụ thực tế:**
Application cần capability:
```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> AuthorizeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}
```

Infrastructure có thể cung cấp:
```text
StripePaymentGateway
LegacyBankGateway
FakePaymentGateway for tests
```

Application không cần biết HTTP endpoint, SDK hoặc credential flow cụ thể.

**Trade-off:**
Port/adapter giảm infrastructure coupling và giúp testability, nhưng mỗi abstraction thêm contract, mapping và indirection. Với CRUD nhỏ hoặc dependency rất ổn định, interface cho mọi class có thể trở thành ceremony không tạo giá trị.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction đúng và không leak SDK type vào core layer. Senior / Technical developer phải xác định boundary nào thật sự volatile/strategic để abstract, và chấp nhận direct dependency ở nơi abstraction cost lớn hơn khả năng thay đổi thực tế.

### Design 3 — Build vs Buy phải tính cả operational ownership, không chỉ development effort

**Khái niệm:**
Quyết định tự xây hay dùng product/service có sẵn phải so sánh tổng chi phí vòng đời: development, security, compliance, vận hành, upgrade, incident response, vendor lock-in và khả năng tùy biến.

**Vấn đề nó giải quyết:**
Team thường đánh giá “tự build mất 3 sprint, mua SaaS mất 1 tuần tích hợp” rồi kết luận quá sớm. Nhưng component như authentication, search, payment hay feature flag có hidden cost lớn ở scale, reliability và security maintenance.

**Ví dụ thực tế:**
Một team cần full-text search cho e-commerce:
```text
Option A: tự xây search layer trên PostgreSQL
Option B: vận hành Elasticsearch
Option C: dùng managed search service
```

Nếu requirement chỉ là prefix/exact search trên 100k product, PostgreSQL có thể đủ và đơn giản nhất. Nếu cần relevance tuning, typo tolerance, autocomplete, analytics và scale lớn, dedicated search platform có thể đáng chi phí hơn.

**Trade-off:**
Build cho control và tùy biến cao nhưng team sở hữu toàn bộ reliability/security/upgrade burden. Buy giảm implementation time nhưng tạo recurring cost, vendor dependency, data-governance constraint và integration boundary lâu dài.

**Middle → Senior insight:**
Middle developer cần biết đánh giá technical fit của từng lựa chọn. Senior / Technical developer phải đưa ra decision dựa trên business differentiation, TCO, exit strategy, compliance, operational skill của team và hậu quả nếu vendor/service trở thành critical dependency.
