# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` cho lookup read-only hot path

**Mẹo:**
Nếu một dictionary được khởi tạo một lần rồi đọc rất nhiều lần, cân nhắc `FrozenDictionary` thay vì `Dictionary` thông thường.

**Tại sao hữu ích:**
Nó tối ưu cấu trúc nội bộ cho workload read-only, phù hợp với lookup table, routing map hoặc metadata cache được build lúc startup.

**Ví dụ:**
```csharp
using System.Collections.Frozen;

var handlers = new Dictionary<string, Func<Task>>
{
    ["create"] = HandleCreateAsync,
    ["delete"] = HandleDeleteAsync
}.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
```

**Lưu ý:**
Không dùng nếu collection thay đổi thường xuyên. Chi phí build ban đầu cao hơn và collection là immutable sau khi tạo.

### Tip 2 — Dùng filtered index cho dữ liệu “hot subset”

**Mẹo:**
Khi query thường xuyên chỉ đọc một tập con nhỏ như `Status = 'Pending'`, cân nhắc filtered index thay vì index toàn bảng.

**Tại sao hữu ích:**
Index nhỏ hơn giúp giảm storage, tăng cache efficiency và giảm write overhead so với index chứa toàn bộ rows.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON Orders (CreatedAt)
INCLUDE (CustomerId, Total)
WHERE Status = 'Pending';
```

**Lưu ý:**
Chỉ hiệu quả khi predicate ổn định và query thực sự match điều kiện filter. Đừng tạo nhiều filtered index cho mọi trạng thái nhỏ lẻ.

### Tip 3 — Dùng `git worktree` khi cần làm nhiều branch song song

**Mẹo:**
Thay vì `stash` rồi checkout qua lại liên tục, dùng `git worktree` để mở nhiều working directory cho cùng repository.

**Tại sao hữu ích:**
Rất tiện khi vừa fix production bug vừa giữ nguyên branch feature hiện tại, hoặc cần so sánh hai branch song song.

**Ví dụ:**
```bash
git worktree add ../project-hotfix hotfix/payment-timeout
```

Sau khi xong:

```bash
git worktree remove ../project-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời trong nhiều worktree. Cũng nên cleanup worktree cũ để tránh nhầm path.

### Tip 4 — Dùng `dotnet-dump` khi process production bị memory leak

**Mẹo:**
Khi memory tăng bất thường nhưng không thể attach debugger, capture process dump để phân tích heap offline.

**Tại sao hữu ích:**
Cho phép điều tra retained objects, exception state và thread state mà không cần tái hiện lỗi trong local environment.

**Ví dụ:**
```bash
dotnet-dump collect -p 1234

dotnet-dump analyze core_*.dmp
```

Trong analyzer:

```text
dumpheap -stat
```

**Lưu ý:**
Dump có thể rất lớn và chứa dữ liệu nhạy cảm trong memory. Cần lưu trữ, truyền và xóa file theo quy trình bảo mật.

### Tip 5 — Test retry logic bằng failure injection thay vì mock “happy path”

**Mẹo:**
Khi code có retry, timeout hoặc circuit breaker, viết test mô phỏng lỗi transient thật sự ở lần gọi đầu rồi success ở lần sau.

**Tại sao hữu ích:**
Giúp phát hiện lỗi như retry sai exception, retry quá nhiều, không honor `CancellationToken` hoặc tạo duplicate side effect.

**Ví dụ:**
```csharp
var attempts = 0;

mock.Setup(x => x.SendAsync(It.IsAny<CancellationToken>()))
    .ReturnsAsync(() =>
    {
        attempts++;
        if (attempts < 3)
            throw new HttpRequestException("Transient failure");

        return new HttpResponseMessage(HttpStatusCode.OK);
    });
```

**Lưu ý:**
Không test retry bằng `Task.Delay` thật với thời gian dài. Dùng injectable delay/time provider hoặc policy configuration ngắn cho test.

## 🧠 Software Design

### Design 1 — Bulkhead Pattern để cô lập failure

**Khái niệm:**
Bulkhead Pattern chia tài nguyên thành các vùng độc lập để một workload bị nghẽn không chiếm hết connection, thread hoặc concurrency slot của toàn hệ thống.

**Vấn đề nó giải quyết:**
Một downstream service chậm có thể làm request pile-up, gây thread pool starvation hoặc connection pool exhaustion và kéo sập cả application.

**Ví dụ thực tế:**
API có hai integration: Payment và Reporting. Reporting thường chậm. Nếu cả hai dùng chung concurrency pool không giới hạn, Reporting có thể chiếm hết outbound connections khiến Payment cũng timeout. Tách semaphore hoặc connection policy cho từng integration giúp Payment tiếp tục hoạt động.

**Trade-off:**
Ưu điểm là failure isolation và predictability tốt hơn. Chi phí là phải phân bổ resource limit hợp lý; đặt limit quá thấp có thể tự tạo bottleneck, còn quá cao thì mất tác dụng bảo vệ.

**Middle → Senior insight:**
Middle developer cần hiểu rằng timeout/retry không đủ nếu resource đã bị exhaustion. Senior developer phải xác định concurrency budget theo dependency criticality, throughput, latency và failure behavior, đồng thời monitor queue depth và rejection rate.

### Design 2 — Read Model riêng cho query phức tạp mà chưa cần full CQRS

**Khái niệm:**
Không nhất thiết áp dụng CQRS toàn hệ thống. Có thể giữ write model hiện tại nhưng tạo read model hoặc materialized view riêng cho một số query nặng.

**Vấn đề nó giải quyết:**
Domain model tối ưu cho business invariants thường không phù hợp với dashboard, reporting hoặc search query cần join nhiều bảng và aggregate lớn.

**Ví dụ thực tế:**
Order domain lưu dữ liệu normalized để đảm bảo consistency. Dashboard quản trị cần tổng doanh thu theo ngày, region và product. Thay vì ép repository domain chạy query cực phức tạp, hệ thống cập nhật một bảng `DailySalesSummary` phục vụ riêng cho read path.

**Trade-off:**
Query nhanh và code đọc đơn giản hơn, nhưng phát sinh duplication dữ liệu và có thể có độ trễ đồng bộ giữa source of truth với read model.

**Middle → Senior insight:**
Middle developer cần phân biệt model phục vụ write và model phục vụ read. Senior developer phải quyết định lúc nào một projection riêng đáng giá hơn việc thêm cache/index hoặc tối ưu SQL, và xác định mức eventual consistency business chấp nhận được.

### Design 3 — Backpressure trong messaging và background processing

**Khái niệm:**
Backpressure là cơ chế giới hạn tốc độ producer hoặc consumer intake khi downstream xử lý chậm hơn tốc độ dữ liệu đi vào.

**Vấn đề nó giải quyết:**
Nếu queue hoặc in-memory buffer tăng không giới hạn, hệ thống có thể hết memory, tăng latency cực lớn hoặc tạo retry storm khi dependency phía sau đang degraded.

**Ví dụ thực tế:**
Một worker nhận 10.000 message/phút nhưng database chỉ xử lý ổn định 2.000 message/phút. Thay vì đọc toàn bộ message vào memory, worker giới hạn concurrency, prefetch nhỏ và để broker giữ backlog cho tới khi consumer bắt kịp.

**Trade-off:**
Tăng stability nhưng latency của backlog tăng và throughput bị giới hạn có chủ đích. Nếu cấu hình quá bảo thủ, hệ thống không tận dụng hết capacity khi tải tăng ngắn hạn.

**Middle → Senior insight:**
Middle developer cần hiểu queue không đồng nghĩa với “xử lý vô hạn”. Senior developer phải thiết kế giới hạn concurrency, prefetch, retry/dead-letter, autoscaling signal và capacity planning dựa trên tốc độ producer/consumer thay vì chỉ nhìn CPU usage.
