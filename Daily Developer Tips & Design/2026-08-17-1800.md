# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IOptionsMonitor<T>` khi cấu hình cần thay đổi trong runtime

**Mẹo:**
Nếu một service cần đọc config có thể reload trong lúc application vẫn chạy, cân nhắc `IOptionsMonitor<T>` thay vì cache giá trị từ `IOptions<T>` ngay khi khởi tạo.

**Tại sao hữu ích:**
Phù hợp với feature configuration, threshold, endpoint hoặc policy có thể được cập nhật mà không cần restart process.

**Ví dụ:**
```csharp
public sealed class ReportService
{
    private readonly IOptionsMonitor<ReportOptions> _options;

    public ReportService(IOptionsMonitor<ReportOptions> options)
        => _options = options;

    public int GetBatchSize()
        => _options.CurrentValue.BatchSize;
}
```

Có thể đăng ký callback khi config đổi:

```csharp
_options.OnChange(options =>
{
    logger.LogInformation("BatchSize changed to {BatchSize}", options.BatchSize);
});
```

**Lưu ý:**
Không giả định mọi configuration provider đều hỗ trợ reload. Ngoài ra callback có thể chạy nhiều lần; tránh đặt side effect nặng hoặc logic không idempotent trong `OnChange`.

### Tip 2 — Dùng `ExecuteDeleteAsync()` cho bulk delete không cần load entity

**Mẹo:**
Khi cần xóa nhiều rows theo predicate và không cần domain logic trên từng entity, dùng EF Core `ExecuteDeleteAsync()` thay vì query toàn bộ rồi `RemoveRange()`.

**Tại sao hữu ích:**
Tránh materialize hàng nghìn entity, giảm memory, change-tracking overhead và số command gửi xuống database.

**Ví dụ:**
```csharp
await dbContext.Sessions
    .Where(x => x.ExpiresAt < cutoff)
    .ExecuteDeleteAsync(cancellationToken);
```

**Lưu ý:**
`ExecuteDeleteAsync()` bypass change tracker và không chạy logic in-memory trên entity. Nếu việc xóa cần domain event, audit đặc biệt hoặc cascade behavior ở application layer, cần thiết kế flow khác.

### Tip 3 — Dùng `git diff --check` để bắt whitespace lỗi trước commit

**Mẹo:**
Trước khi commit hoặc trong CI, chạy `git diff --check` để phát hiện trailing whitespace và whitespace error trong patch.

**Tại sao hữu ích:**
Giảm noise trong review, tránh diff bẩn và ngăn các lỗi format nhỏ tích tụ ở file script/config.

**Ví dụ:**
```bash
git diff --check
```

Kiểm tra staged changes:

```bash
git diff --cached --check
```

**Lưu ý:**
Lệnh này chỉ bắt một số whitespace problem, không thay thế formatter/linter như `dotnet format`, ESLint hay Prettier.

### Tip 4 — Dùng `Redis` pipelining khi có nhiều command độc lập

**Mẹo:**
Nếu application cần gửi nhiều command Redis độc lập trong cùng một flow, pipelining giúp giảm số network round trip thay vì chờ từng command hoàn thành tuần tự.

**Tại sao hữu ích:**
Với latency mạng 1–2 ms, hàng trăm command tuần tự có thể tốn phần lớn thời gian chỉ vì round trip, dù Redis xử lý từng command rất nhanh.

**Ví dụ:**
Scenario: cần lấy 100 cache keys. Thay vì:

```text
GET key1 -> wait
GET key2 -> wait
...
```

client library có thể queue nhiều command rồi đọc response sau khi chúng đã được gửi liên tiếp.

**Lưu ý:**
Pipelining không đảm bảo atomicity. Nếu nhiều command phải thực hiện như một unit logic, cần transaction/Lua script hoặc data model khác phù hợp hơn.

### Tip 5 — Dùng `curl -w` để đo DNS, connect, TLS và TTFB riêng biệt

**Mẹo:**
Khi một HTTP call chậm, dùng `curl -w` để tách latency thành DNS lookup, TCP connect, TLS handshake và time-to-first-byte thay vì chỉ nhìn tổng thời gian.

**Tại sao hữu ích:**
Giúp biết bottleneck nằm ở network, TLS hay server processing mà không cần profiler phía application ngay từ đầu.

**Ví dụ:**
```bash
curl -s -o /dev/null \
  -w 'dns=%{time_namelookup}\nconnect=%{time_connect}\ntls=%{time_appconnect}\nttfb=%{time_starttransfer}\ntotal=%{time_total}\n' \
  https://api.example.com/health
```

**Lưu ý:**
Một lần đo đơn lẻ có thể bị ảnh hưởng bởi DNS cache, connection reuse hoặc transient network condition. Nên chạy nhiều lần từ đúng môi trường production/container.

## 🧠 Software Design

### Design 1 — Load Shedding khi hệ thống đã vượt khả năng xử lý

**Khái niệm:**
Load Shedding chủ động reject, delay hoặc bỏ bớt workload khi hệ thống vượt capacity thay vì nhận toàn bộ request rồi để mọi thứ cùng timeout chậm.

**Vấn đề nó giải quyết:**
Khi thread pool, database connection pool hoặc queue đã saturated, tiếp tục nhận thêm work chỉ làm latency tăng, timeout lan rộng và recovery khó hơn.

**Ví dụ thực tế:**
Một API report có concurrency budget 20. Khi 20 report đang chạy, request mới có thể nhận `429` hoặc `503` cùng retry guidance thay vì mở thêm query nặng và kéo database xuống cùng.

**Trade-off:**
Load shedding giữ hệ thống sống và bảo vệ critical traffic, nhưng đồng nghĩa một phần request sẽ bị từ chối. Cần policy rõ request nào được ưu tiên và UX/retry semantics phù hợp.

**Middle → Senior insight:**
Middle developer nên hiểu saturation không thể giải quyết bằng cách tăng timeout. Senior developer phải xác định capacity signal, admission control, priority class và nơi shed load sao cho bảo vệ business flow quan trọng nhất.

### Design 2 — Data Ownership quan trọng hơn việc module “cùng dùng chung bảng”

**Khái niệm:**
Mỗi domain/module nên có ownership rõ đối với dữ liệu mà nó chịu trách nhiệm thay đổi. Module khác có thể đọc qua contract, projection hoặc integration flow nhưng không nên tự ý mutate schema/data của owner.

**Vấn đề nó giải quyết:**
Khi nhiều module cùng update trực tiếp một bảng, business rule bị phân tán, migration khó phối hợp và không còn nơi duy nhất chịu trách nhiệm cho invariant.

**Ví dụ thực tế:**
`Employee` thuộc HR module. Timesheet có thể cần `EmployeeId`, `DisplayName`, `WorkingSchedule`, nhưng việc thay đổi employment status nên đi qua HR capability thay vì Timesheet update trực tiếp bảng `Employees`.

**Trade-off:**
Ownership rõ giúp giảm coupling và tăng maintainability, nhưng có thể cần duplicate read data hoặc thêm API/event synchronization. Shared read access đôi khi đơn giản hơn trong monolith nhỏ nếu write ownership vẫn được giữ chặt.

**Middle → Senior insight:**
Middle developer nên phân biệt “có thể query được” với “có quyền thay đổi”. Senior developer cần thiết kế ownership dựa trên invariant, team/module responsibility và change boundary, không chỉ theo database schema hiện tại.

### Design 3 — KISS và YAGNI trong kiến trúc: tối ưu cho complexity hiện tại, không phải tương lai tưởng tượng

**Khái niệm:**
KISS và YAGNI không có nghĩa tránh mọi abstraction; chúng yêu cầu chỉ thêm complexity khi có requirement hoặc pressure thực tế chứng minh giá trị của nó.

**Vấn đề nó giải quyết:**
Team dễ xây message bus, plugin framework, generic repository, distributed cache hoặc microservices “để sau này cần” dù hiện tại system chỉ có một use case đơn giản.

**Ví dụ thực tế:**
Một internal CRUD app có 3 module và vài nghìn request/ngày chưa cần event sourcing, distributed lock và service mesh. Modular Monolith với boundary rõ có thể đáp ứng tốt hơn và dễ vận hành hơn.

**Trade-off:**
Thiết kế đơn giản giảm cost phát triển/vận hành và tăng tốc thay đổi, nhưng nếu bỏ qua signal scale/complexity quá lâu, refactor sau này có thể đắt. Vấn đề là chọn đúng thời điểm nâng cấp kiến trúc.

**Middle → Senior insight:**
Middle developer nên tránh pattern theo thói quen. Senior developer phải phân biệt complexity cần thiết với speculative complexity, đồng thời để lại seam hợp lý để hệ thống có thể tiến hóa khi requirement thực sự thay đổi.
