# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt parameter sniffing với “index bị hỏng” khi SQL Server chậm thất thường

**Mẹo:**
Khi cùng một stored procedure hoặc query lúc nhanh lúc chậm tùy input, kiểm tra execution plan được cache cho parameter đầu vào trước khi vội rebuild index hoặc tăng hardware.

**Tại sao hữu ích:**
SQL Server có thể compile plan dựa trên giá trị parameter tại thời điểm đầu tiên rồi reuse plan đó cho các giá trị sau. Một plan tốt cho customer có vài row có thể rất tệ cho customer có hàng triệu row.

**Ví dụ:**
```sql
EXEC dbo.GetOrdersByCustomer @CustomerId = 42;      -- 10 rows
EXEC dbo.GetOrdersByCustomer @CustomerId = 900001;  -- 2,000,000 rows
```

So sánh actual execution plan, estimated rows và actual rows. Có thể cân nhắc `OPTION (RECOMPILE)`, `OPTIMIZE FOR`, query split hoặc thiết kế index phù hợp tùy workload.

**Lưu ý:**
Đừng dùng `RECOMPILE` mặc định cho mọi query. Nó tăng compilation cost và có thể làm CPU cao hơn; chỉ dùng khi benefit lớn hơn chi phí.

### Tip 2 — Với Azure Functions, poison message phải có đường xử lý riêng

**Mẹo:**
Nếu Azure Function xử lý queue/message liên tục thất bại với cùng một payload, cần dead-letter hoặc poison-message path rõ ràng thay vì retry vô hạn.

**Tại sao hữu ích:**
Retry chỉ hữu ích cho transient fault. Với message sai schema, thiếu dữ liệu hoặc vi phạm invariant, retry không thay đổi kết quả mà chỉ tiêu tốn compute, tăng queue latency và che lấp lỗi thực sự.

**Ví dụ:**
```text
Message A
-> retry 1: fail validation
-> retry 2: fail validation
-> retry 3: fail validation
-> move to poison/dead-letter queue
-> alert + inspect + repair/replay
```

**Lưu ý:**
Đưa message vào dead-letter queue chưa phải hoàn tất thiết kế. Cần metadata đủ để điều tra, dashboard, retention policy và quy trình replay an toàn.

### Tip 3 — Trong Vue.js, hủy request cũ để tránh stale response ghi đè UI mới

**Mẹo:**
Với search/filter thay đổi nhanh, hủy request trước khi gửi request mới để response cũ không quay về muộn và ghi đè state hiện tại.

**Tại sao hữu ích:**
Hai request có thể hoàn tất không theo thứ tự gửi. Nếu user gõ `app` rồi `apple`, request `app` có thể trả về sau và overwrite kết quả đúng của `apple`.

**Ví dụ:**
```ts
let controller: AbortController | null = null

async function search(q: string) {
  controller?.abort()
  controller = new AbortController()

  const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  })

  results.value = await res.json()
}
```

**Lưu ý:**
Cancellation ở browser không đảm bảo backend đã dừng xử lý. Backend vẫn cần `CancellationToken` propagation nếu operation tốn tài nguyên đáng kể.

### Tip 4 — Dùng Managed Identity thay vì lưu secret của Azure resource trong cấu hình

**Mẹo:**
Khi application trên Azure cần truy cập Key Vault, Storage hoặc Service Bus, ưu tiên Managed Identity và RBAC thay vì lưu connection string hoặc client secret trong app settings.

**Tại sao hữu ích:**
Secret tĩnh phải được tạo, lưu, rotate và bảo vệ. Managed Identity cho phép Azure cấp identity cho workload và phát token ngắn hạn mà application không phải giữ credential bí mật.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);
```

**Lưu ý:**
Managed Identity không loại bỏ nhu cầu least privilege. Identity vẫn phải chỉ được cấp đúng role/scope cần thiết và access phải được audit.

### Tip 5 — Dùng `git worktree` khi cần làm hotfix mà không phá working tree hiện tại

**Mẹo:**
Nếu đang dở một feature nhưng cần chuyển nhanh sang branch hotfix, dùng `git worktree` để tạo working directory thứ hai thay vì stash/cherry-pick liên tục.

**Tại sao hữu ích:**
Bạn có thể giữ nguyên trạng thái feature đang làm trong một folder và checkout branch khác trong folder riêng, giảm nguy cơ stash nhầm, mất untracked file hoặc lẫn dependency/build artifact.

**Ví dụ:**
```bash
git worktree add ../myapp-hotfix hotfix/payment-timeout
cd ../myapp-hotfix
```

Sau khi xong:

```bash
git worktree remove ../myapp-hotfix
```

**Lưu ý:**
Không checkout cùng một branch trong hai worktree cùng lúc. Cũng cần chú ý tool/editor có thể giữ cache hoặc environment khác nhau giữa các folder.

## 🧠 Software Design

### Design 1 — CQRS chỉ nên tách read/write khi hai phía thật sự có nhu cầu khác nhau

**Khái niệm:**
CQRS tách model hoặc pipeline xử lý command khỏi query. Giá trị của nó xuất hiện khi read và write có lifecycle, scale, authorization hoặc data shape khác nhau đáng kể.

**Vấn đề nó giải quyết:**
Một model duy nhất đôi khi bị kéo theo hai hướng: write cần bảo vệ invariant và transaction, còn read cần projection phẳng, query nhanh và scale độc lập.

**Ví dụ thực tế:**
```text
Write model:
Order Aggregate
- kiểm tra trạng thái
- enforce invariant
- transaction

Read model:
OrderDashboardRow
- precomputed fields
- search/filter nhanh
- không cần domain behavior
```

**Trade-off:**
CQRS tăng clarity và khả năng tối ưu độc lập, nhưng thêm model, mapping, synchronization và eventual consistency. Với CRUD đơn giản, nó có thể chỉ tạo ceremony.

**Middle → Senior insight:**
Middle developer cần hiểu command và query có mục tiêu khác nhau. Senior / Technical developer phải quyết định mức tách phù hợp: tách handler trong cùng database, tách read model riêng, hay hoàn toàn tách datastore — dựa trên scale, consistency và complexity budget.

### Design 2 — Retry và Circuit Breaker giải quyết hai failure mode khác nhau

**Khái niệm:**
Retry thử lại transient failure; Circuit Breaker tạm ngừng gọi dependency đang lỗi để tránh tiếp tục gây tải và kéo failure lan sang hệ thống gọi nó.

**Vấn đề nó giải quyết:**
Nếu dependency down thực sự, retry từ hàng trăm request có thể tạo retry storm. Circuit Breaker giúp fail fast trong một khoảng thời gian và cho dependency cơ hội phục hồi.

**Ví dụ thực tế:**
```text
Payment API timeout tăng mạnh

Retry:
- 1 hoặc 2 lần với backoff cho transient failure

Circuit Breaker:
- nếu failure rate vượt threshold
- mở circuit 30 giây
- request mới fail fast/fallback
```

**Trade-off:**
Retry tăng xác suất thành công nhưng tăng latency và tải. Circuit Breaker bảo vệ hệ thống nhưng có thể từ chối request trong lúc dependency vừa phục hồi. Threshold và fallback cần dựa trên business semantics.

**Middle → Senior insight:**
Middle developer cần tránh retry vô hạn và biết operation nào idempotent. Senior / Technical developer phải thiết kế retry budget, timeout hierarchy, circuit threshold và observability để tránh cascading failure.

### Design 3 — Expand-and-Contract giúp schema migration an toàn khi deploy không đồng thời

**Khái niệm:**
Expand-and-Contract chia breaking schema change thành nhiều bước backward-compatible để version cũ và mới của application có thể chạy song song trong rolling deployment.

**Vấn đề nó giải quyết:**
Nếu rename hoặc drop column ngay trong cùng release, instance cũ chưa restart có thể tiếp tục đọc/write schema cũ và fail giữa deployment.

**Ví dụ thực tế:**
```text
Release 1: add NewEmail column, app ghi cả OldEmail + NewEmail
Release 2: migrate/backfill, app đọc NewEmail
Release 3: ngừng ghi OldEmail
Release 4: drop OldEmail
```

**Trade-off:**
Cách này giảm deployment risk nhưng kéo dài thời gian migration, tạo temporary duplication và yêu cầu tracking trạng thái migration cẩn thận.

**Middle → Senior insight:**
Middle developer cần tránh migration breaking với code đang chạy. Senior / Technical developer phải lập deployment order, rollback strategy, backfill plan, observability và tiêu chí xác nhận trước khi contract schema cũ.
