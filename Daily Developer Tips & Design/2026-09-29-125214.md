# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt timeout, cancellation và retry khi gọi HTTP

**Mẹo:**
Với outbound HTTP trong .NET, hãy coi timeout, caller cancellation và transient failure là ba tín hiệu khác nhau. Propagate `CancellationToken` từ request, đặt timeout có chủ đích cho dependency, và chỉ retry lỗi thực sự transient.

**Tại sao hữu ích:**
Nếu mọi `TaskCanceledException` đều bị retry, một request mà client đã bỏ đi vẫn có thể tiếp tục tạo tải lên downstream. Ngược lại, timeout quá dài làm request giữ socket, memory và execution context lâu hơn cần thiết. Reliability tốt bắt đầu từ một time budget rõ ràng xuyên suốt call chain.

**Ví dụ:**
Một API có SLA 2 giây gọi pricing service. Controller truyền `HttpContext.RequestAborted` xuống application service và `HttpClient.SendAsync(..., ct)`. Dependency được cấp budget 700 ms; telemetry phân biệt timeout của dependency với cancellation do client đóng kết nối. Retry chỉ áp dụng cho failure transient và vẫn phải nằm trong budget tổng.

**Lưu ý:**
Không retry mù quáng `POST` có side effect nếu operation không idempotent. Ba lần retry với timeout 2 giây cũng có thể biến một dependency chậm thành latency hơn 6 giây và khuếch đại tải trong incident.

### Tip 2 — EF Core: projection trước khi nghĩ tới `Include`

**Mẹo:**
Với read endpoint chỉ cần một phần dữ liệu, ưu tiên `Select` thành DTO/read model thay vì `Include` cả object graph rồi map trong memory.

**Tại sao hữu ích:**
`Include` có thể kéo nhiều columns và related rows hơn contract thực sự cần. Khi nhiều collection được join, result set còn có thể bị nhân bản theo quan hệ, tăng network payload, materialization cost và allocation. Projection cho database biết chính xác shape cần trả.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderSummary(
        x.Id,
        x.CreatedAt,
        x.Total,
        x.Items.Count))
    .Take(50)
    .ToListAsync(ct);
```
Endpoint danh sách không cần materialize toàn bộ `Order.Items` chỉ để lấy số lượng.

**Lưu ý:**
Projection không mặc định nhanh hơn trong mọi trường hợp. Kiểm tra SQL được sinh ra và execution plan. Với aggregate cần tracking để cập nhật domain state, load entity graph phù hợp vẫn có thể là lựa chọn đúng.

### Tip 3 — Application Insights: điều tra latency bằng percentile và dependency breakdown

**Mẹo:**
Khi API “trung bình vẫn nhanh” nhưng user báo chậm, đừng chỉ nhìn average latency. So sánh p50, p95, p99 rồi drill down theo dependency, operation, instance và deployment version.

**Tại sao hữu ích:**
Average che mất tail latency. Chỉ 2–5% request bị SQL blocking hoặc external API timeout vẫn có thể tạo trải nghiệm rất xấu nhưng ít ảnh hưởng mean. Phân rã request duration thành dependency spans giúp chuyển từ triệu chứng sang evidence.

**Ví dụ:**
Sau deployment, average của `GET /search` tăng từ 180 ms lên 210 ms nhưng p99 tăng từ 600 ms lên 4,8 giây. Trace chậm cho thấy một Elasticsearch dependency chiếm 4,2 giây và tập trung ở một query shape mới. Team có thể kiểm tra query/mapping thay vì scale App Service theo phản xạ.

**Lưu ý:**
Percentile phải được đọc cùng traffic volume và aggregation window. High-cardinality dimensions cũng có cost; không biến user ID hoặc request ID thành metric dimension chỉ để dễ filter.

### Tip 4 — Docker image cho .NET: tách build image khỏi runtime image

**Mẹo:**
Dùng multi-stage build để compile/publish bằng .NET SDK image nhưng chạy artifact trên ASP.NET runtime image phù hợp. Pin version/tag có chủ đích và giữ runtime image tối thiểu.

**Tại sao hữu ích:**
SDK chứa compiler và tooling không cần trong production. Tách build/runtime giảm image size và attack surface, đồng thời làm rõ dependency nào thực sự cần lúc chạy. Artifact cũng dễ tái sử dụng nhất quán giữa các environment hơn việc build lại ở từng nơi.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish src/Web/Web.csproj -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "Web.dll"]
```

**Lưu ý:**
Image nhỏ không đồng nghĩa image an toàn. Vẫn phải patch base image, scan dependencies và xác minh native libraries/timezone/certificates mà ứng dụng cần. Tránh dùng tag floating thiếu kiểm soát trong pipeline cần reproducibility.

### Tip 5 — File upload: validate content và giới hạn tài nguyên, không tin filename

**Mẹo:**
Với ASP.NET Core file upload, áp dụng size limit, authorization, server-generated storage name và content validation phù hợp với loại file. Xem filename, extension và client-supplied `Content-Type` là metadata không đáng tin.

**Tại sao hữu ích:**
Attacker có thể đổi extension hoặc MIME header, dùng path-like filename, gửi file cực lớn hoặc nội dung chủ động nguy hiểm. Boundary upload phải bảo vệ cả storage, memory, downstream parser và nơi file được phục vụ lại.

**Ví dụ:**
CMS cho editor upload ảnh: API giới hạn kích thước, kiểm tra signature/decoder của định dạng được cho phép, sinh object key riêng, lưu Blob Storage ngoài web root và chỉ trả URL theo policy. Original filename có thể giữ làm display metadata sau khi normalize, không dùng trực tiếp làm storage path.

**Lưu ý:**
Magic-byte check không chứng minh file hoàn toàn an toàn. Với document phức tạp có macro/script hoặc workflow tải file từ URL, cần threat model bổ sung như malware scanning, SSRF protection và isolation khi parse.

## 🧠 Software Design

### Design 1 — Idempotency Key cho command API có thể bị gửi lại

**Khái niệm:**
Idempotency Key biến nhiều lần gửi cùng một logical command thành một kết quả nghiệp vụ duy nhất bằng cách gắn request với một identity ổn định và lưu trạng thái/kết quả xử lý ở server.

**Vấn đề nó giải quyết:**
Client có thể timeout sau khi server đã tạo payment/order nhưng chưa nhận response. Nếu client retry cùng payload như một request hoàn toàn mới, hệ thống có thể tạo duplicate side effect dù cả client lẫn server đều “hoạt động đúng” theo góc nhìn riêng.

**Ví dụ thực tế:**
Mobile app gửi `POST /orders` với `Idempotency-Key: 7f...`. Server lưu key cùng request fingerprint và OrderId trong transaction phù hợp. Retry cùng key trả lại kết quả đã tạo; cùng key nhưng payload khác bị reject thay vì âm thầm tái sử dụng.

**Trade-off:**
Idempotency làm retry an toàn hơn nhưng cần storage, uniqueness constraint, retention/expiry, concurrency handling và semantics cho request đang xử lý dở. Giữ key mãi mãi cũng tạo chi phí dữ liệu; giữ quá ngắn có thể không bao phủ retry window thực tế.

**Middle → Senior insight:**
Middle developer cần bảo đảm duplicate request không tạo side effect lần hai và test concurrent retries. Senior / Technical developer phải xác định logical operation identity, scope key theo tenant/user, retention, response replay, transaction boundary và cách phối hợp với downstream systems; không nhầm HTTP method idempotency với business idempotency end-to-end.

### Design 2 — Azure Functions vs Worker Service theo workload ownership

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có execution tương đối độc lập và muốn tận dụng trigger/binding/scaling platform. Worker Service phù hợp hơn khi cần process dài sống lâu, lifecycle chủ động, connection/state management hoặc operational behavior được kiểm soát chặt.

**Vấn đề nó giải quyết:**
Cùng một background job có thể triển khai bằng nhiều compute model. Chọn Functions chỉ vì “serverless scale tự động” hoặc Worker chỉ vì team quen .NET có thể bỏ qua cold start, execution pattern, hosting cost và cách workload cần scale.

**Ví dụ thực tế:**
Một BlobCreated event kích hoạt xử lý thumbnail ngắn, độc lập và bursty có thể phù hợp Azure Functions. Một ingestion processor duy trì nhiều long-lived connections, kiểm soát concurrency theo partition và cần graceful drain phức tạp có thể dễ vận hành hơn dưới Worker Service trên App Service/Kubernetes/container platform.

**Trade-off:**
Functions giảm boilerplate trigger và có mô hình scale tiện lợi nhưng platform/runtime constraints, cold start và retry semantics cần được hiểu rõ. Worker cho lifecycle/control rõ hơn nhưng team phải sở hữu hosting, scaling, health checks và deployment nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu cancellation, retries, poison messages và idempotency trong model đã chọn. Senior / Technical developer phải đánh giá workload duration, burst profile, latency target, state/connection behavior, scaling unit, observability, cost và năng lực vận hành; compute model là quyết định workload, không phải preference framework.

### Design 3 — Strangler Fig cho modernization hệ thống legacy

**Khái niệm:**
Strangler Fig hiện đại hóa hệ thống theo lát cắt: capability mới được đưa ra boundary mới và traffic dần chuyển khỏi legacy, thay vì yêu cầu rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Một .NET Framework/CMS legacy lớn thường chứa business rules không được tài liệu hóa, integration cũ và dữ liệu dùng chung. Big-bang rewrite có feedback cycle dài và rủi ro phát hiện missing behavior quá muộn.

**Ví dụ thực tế:**
Một commerce site legacy giữ checkout hiện tại nhưng tách product-read API trước. Reverse proxy/routing đưa product traffic sang ASP.NET Core service mới, đo correctness/latency và có rollback path. Sau khi ownership dữ liệu và integration ổn định, capability tiếp theo mới được di chuyển.

**Trade-off:**
Migration tăng khả năng giao từng bước và giảm blast radius, nhưng trong giai đoạn chuyển tiếp phải vận hành hai thế giới: routing, duplicate models, data synchronization, compatibility và observability phức tạp hơn. Nếu boundary chọn sai, hệ thống mới chỉ trở thành façade phụ thuộc sâu vào legacy.

**Middle → Senior insight:**
Middle developer cần giữ contract compatibility, regression tests và telemetry khi chuyển từng flow. Senior / Technical developer phải chọn seam theo business capability/change pressure, thiết kế data ownership và rollback, xác định tiêu chí xóa legacy, đồng thời tránh biến “temporary bridge” thành dependency vĩnh viễn.
