# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — `ExecuteUpdateAsync` nhanh hơn load entity, nhưng không đồng bộ Change Tracker

**Mẹo:**
Với bulk update đơn giản trong EF Core, cân nhắc `ExecuteUpdateAsync()` thay vì load entity vào memory rồi sửa từng object. Nó tạo trực tiếp một câu `UPDATE` ở database và bỏ qua materialization/change tracking.

**Tại sao hữu ích:**
Nếu cần cập nhật hàng nghìn row, cách load entity rồi `SaveChangesAsync()` làm tăng round trip, allocation và chi phí Change Tracker. `ExecuteUpdateAsync()` thường phù hợp hơn cho update set-based.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.CreatedAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, DateTimeOffset.UtcNow), ct);
```

Nếu cùng `DbContext` đã track các `Order` đó trước đó, object đang track không tự động nhận giá trị mới từ database.

**Lưu ý:**
`ExecuteUpdateAsync()` bypass Change Tracker nên không chạy logic dựa trên entity state giống `SaveChanges()`. Đừng dùng nếu business invariant, domain event hoặc concurrency handling đang phụ thuộc vào lifecycle của tracked entity mà chưa thiết kế lại rõ ràng.

### Tip 2 — Khi production chậm, xem p95/p99 dependency latency thay vì chỉ average

**Mẹo:**
Trong Application Insights/Azure Monitor, khi API có cảm giác “thỉnh thoảng rất chậm”, phân tích percentile như p95/p99 của dependency thay vì chỉ nhìn average duration.

**Tại sao hữu ích:**
Average có thể che tail latency. Ví dụ 95% request mất 100 ms nhưng 5% request mất 5 giây thì average vẫn có thể trông chấp nhận được, trong khi user thực tế gặp timeout hoặc trải nghiệm rất tệ.

**Ví dụ:**
```kusto
dependencies
| where timestamp > ago(1h)
| summarize
    p50 = percentile(duration, 50),
    p95 = percentile(duration, 95),
    p99 = percentile(duration, 99)
  by target, name
| order by p99 desc
```

Sau đó correlate dependency chậm với request, exception, deployment version hoặc một downstream cụ thể.

**Lưu ý:**
Percentile cần đủ sample để có ý nghĩa. Đừng kết luận chỉ từ p99 của một nhóm có vài request; luôn xem volume, error rate và phân bố latency cùng nhau.

### Tip 3 — Dùng `AbortController` để tránh stale frontend request ghi đè state mới

**Mẹo:**
Trong Vue/React, nếu user thay đổi filter/search liên tục, hủy request cũ bằng `AbortController` để response chậm của request trước không ghi đè kết quả mới hơn.

**Tại sao hữu ích:**
Async request hoàn thành không đảm bảo theo thứ tự gửi. Nếu query `a` mất 800 ms còn query `ab` mất 100 ms, kết quả `ab` có thể render trước rồi bị response cũ của `a` ghi đè sau đó.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(term: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  });

  return response.json();
}
```

**Lưu ý:**
Cancellation phía browser không có nghĩa server chắc chắn dừng work ngay. Backend vẫn cần propagation/cancellation phù hợp nếu operation tốn tài nguyên. Ngoài ra phải phân biệt `AbortError` với lỗi network thực sự để không hiển thị error sai cho user.

### Tip 4 — Kubernetes `requests` và `limits` ảnh hưởng trực tiếp tới scheduling và throttling

**Mẹo:**
Khi container chậm hoặc bị restart, kiểm tra `resources.requests` và `resources.limits` trước khi chỉ tăng số replica. `requests` ảnh hưởng scheduler; `limits` có thể dẫn tới CPU throttling hoặc OOM kill.

**Tại sao hữu ích:**
Một pod có CPU limit quá thấp có thể bị throttled dù node vẫn còn CPU. Memory limit quá thấp có thể khiến process bị `OOMKilled`. Ngược lại, requests đặt quá cao làm cluster khó schedule pod và lãng phí capacity reservation.

**Ví dụ:**
```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

Khi điều tra, xem `kubectl describe pod`, restart reason, metrics CPU/memory và throttling thay vì đoán application bị memory leak ngay lập tức.

**Lưu ý:**
Không copy một cấu hình resources cho mọi service. Giá trị hợp lý phải dựa trên load test, production telemetry, startup behavior và headroom cần thiết cho traffic spike.

### Tip 5 — Với AI coding agent, khóa phạm vi bằng repository evidence và executable verification

**Mẹo:**
Khi giao cho AI coding agent sửa code, cung cấp phạm vi file/module rõ ràng, yêu cầu đọc implementation hiện tại trước và bắt buộc xác minh bằng build/test/lint thay vì chỉ đánh giá code bằng reasoning text.

**Tại sao hữu ích:**
AI có thể tạo API không tồn tại, giả định sai version package hoặc “cải tiến” kiến trúc ngoài yêu cầu. Grounding bằng source thật và executable checks giúp giảm hallucination và uncontrolled refactor.

**Ví dụ:**
```text
Task:
- Chỉ sửa module Billing.
- Đọc csproj + implementation hiện tại trước.
- Không thêm package nếu chưa chứng minh cần thiết.
- Chạy dotnet build và targeted tests sau thay đổi.
- Báo rõ test nào chưa chạy được và vì sao.
```

Nếu agent đề xuất API mới, đối chiếu với package/version thật trong repository thay vì chấp nhận vì code “trông hợp lý”.

**Lưu ý:**
Test pass không chứng minh thiết kế đúng toàn bộ. Vẫn cần review security, transaction boundary, backwards compatibility và behavior không được test. AI nên tăng tốc engineering loop, không thay thế technical judgment.

## 🧠 Software Design

### Design 1 — Keyset Pagination khi dataset lớn và dữ liệu thay đổi liên tục

**Khái niệm:**
Keyset Pagination dùng giá trị của row cuối cùng ở page hiện tại làm cursor cho page tiếp theo, thay vì dùng `OFFSET` để bỏ qua N row. Cursor thường dựa trên một ordering ổn định như `(CreatedAt, Id)`.

**Vấn đề nó giải quyết:**
Với bảng lớn, `OFFSET 500000` có thể buộc database đọc/bỏ qua rất nhiều row trước khi trả page. Đồng thời, nếu dữ liệu mới được insert giữa hai request, offset pagination có thể gây duplicate hoặc skip item.

**Ví dụ thực tế:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE
    CreatedAt < @lastCreatedAt
    OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

API có thể trả cursor opaque được encode từ `CreatedAt + Id` thay vì expose raw offset.

**Trade-off:**
Keyset Pagination thường ổn định và nhanh hơn trên dataset lớn, nhưng không hỗ trợ tốt nhu cầu “nhảy trực tiếp tới page 347” và yêu cầu ordering/cursor contract rõ ràng. Admin UI nhỏ với dataset ít vẫn có thể dùng offset cho đơn giản.

**Middle → Senior insight:**
Middle developer cần triển khai ordering deterministic và cursor đúng. Senior / Technical developer phải chọn pagination strategy dựa trên UX, dataset size, write frequency, index design và API compatibility thay vì áp keyset cho mọi danh sách.

### Design 2 — Bulkhead Isolation để một dependency lỗi không kéo sập toàn service

**Khái niệm:**
Bulkhead Isolation chia resource/concurrency budget giữa các loại work hoặc dependency thay vì để mọi request dùng chung toàn bộ thread, connection hoặc queue capacity.

**Vấn đề nó giải quyết:**
Giả sử service gọi cả Search API và Payment API. Nếu Search API treo và hàng trăm request đồng thời giữ connection/task chờ, nó có thể tiêu hết resource và làm payment path cũng chậm dù Payment API vẫn khỏe.

**Ví dụ thực tế:**
```text
Search integration:
- max concurrent calls: 30
- queue nhỏ

Payment integration:
- max concurrent calls: 10
- resource pool riêng

Background export:
- concurrency limit: 2
```

Khi Search quá tải, request search bị reject/timeout có kiểm soát thay vì chiếm toàn bộ capacity của process.

**Trade-off:**
Bulkhead tăng fault isolation nhưng capacity bị phân mảnh; một partition có thể rảnh trong khi partition khác quá tải. Giới hạn quá thấp còn tạo bottleneck nhân tạo, nên cần dựa trên SLO, downstream capacity và telemetry.

**Middle → Senior insight:**
Middle developer cần biết giới hạn concurrency ở đúng integration boundary. Senior / Technical developer phải thiết kế resource budget xuyên thread pool, HTTP connection, queue và downstream quota để tránh một failure domain lan sang capability khác.

### Design 3 — Architecture Decision Record cho quyết định khó đảo ngược, không phải mọi thay đổi nhỏ

**Khái niệm:**
Architecture Decision Record (ADR) ghi lại context, decision, alternatives và consequence của một quyết định kỹ thuật quan trọng. Giá trị chính không phải “documentation cho đẹp”, mà là lưu reasoning để team sau này hiểu vì sao hệ thống đang như vậy.

**Vấn đề nó giải quyết:**
Sau vài tháng, team chỉ thấy kết quả như “dùng Service Bus”, “không dùng Microservices”, “chọn SQL Server”, nhưng mất context về scale, deadline, skill set, compliance hoặc operational constraints lúc quyết định được đưa ra. Khi context mất đi, team dễ lặp lại tranh luận hoặc refactor sai lý do.

**Ví dụ thực tế:**
```text
ADR-017: Dùng Modular Monolith cho Release 1

Context:
- 1 team nhỏ
- shared transaction nhiều
- deployment cần đơn giản

Alternatives:
- Microservices
- Modular Monolith

Decision:
- Modular Monolith

Consequences:
- deployment đơn giản
- cần enforce module boundary trong code
- có migration path nếu boundary đủ rõ
```

**Trade-off:**
ADR cải thiện traceability nhưng nếu ghi mọi quyết định nhỏ sẽ nhanh chóng thành bureaucracy và không ai đọc. ADR cũng phải được supersede khi context thay đổi; nó không phải “luật vĩnh viễn”.

**Middle → Senior insight:**
Middle developer nên hiểu và tuân thủ reasoning của các quyết định hiện hành, đồng thời nêu evidence khi thấy assumption không còn đúng. Senior / Technical developer phải phân biệt reversible vs hard-to-reverse decision, ghi lại trade-off quan trọng và chủ động cập nhật/supersede ADR khi constraints thay đổi.
