# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Theo dõi allocation trước khi tối ưu GC

**Mẹo:**
Khi API có latency spike hoặc GC activity cao, đừng bắt đầu bằng việc chỉnh GC mode. Trước tiên đo allocation rate và xác định object nào được tạo nhiều trên hot path bằng `dotnet-counters`, profiler hoặc Application Insights profiling.

**Tại sao hữu ích:**
Garbage Collector chỉ phản ứng với lượng allocation mà application tạo ra. Nếu mỗi request allocate nhiều buffer, string hoặc object graph ngắn hạn, GC phải chạy thường xuyên hơn. Tối ưu nguyên nhân tạo allocation thường hiệu quả và ít rủi ro hơn việc can thiệp runtime configuration.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Quan sát các metric như allocation rate, Gen 0/1/2 collections và heap size. Nếu allocation tăng mạnh sau một deployment, tiếp tục profile call path tạo object thay vì kết luận ngay rằng GC “có vấn đề”.

**Lưu ý:**
Không dùng `ArrayPool<T>`, `Span<T>` hoặc object pooling khắp codebase chỉ để giảm allocation. Những kỹ thuật này tăng complexity và chỉ nên áp dụng ở hot path đã được đo.

### Tip 2 — Dùng ETag để tránh gửi lại tài nguyên không thay đổi

**Mẹo:**
Với REST API trả resource ít thay đổi nhưng được đọc thường xuyên, cân nhắc `ETag` cùng `If-None-Match` để client xác nhận version thay vì tải lại toàn bộ payload.

**Tại sao hữu ích:**
Conditional request giảm bandwidth và serialization cost. Server vẫn kiểm tra trạng thái resource, nhưng nếu version không đổi có thể trả `304 Not Modified` mà không gửi lại body lớn.

**Ví dụ:**
```http
GET /api/products/42
If-None-Match: "product-42-v17"
```

Nếu version hiện tại vẫn là `v17`, server trả:

```http
HTTP/1.1 304 Not Modified
ETag: "product-42-v17"
```

**Lưu ý:**
ETag phải đại diện đúng cho representation mà client nhận. Nếu response thay đổi theo locale, permission hoặc query parameters, một ETag dùng chung có thể gây cache sai dữ liệu.

### Tip 3 — Chống cache stampede bằng single-flight hoặc lock có thời hạn

**Mẹo:**
Khi một key Redis phổ biến hết TTL, đừng để hàng trăm request cùng lúc đều query database rồi repopulate cache. Dùng single-flight trong process hoặc distributed lock ngắn hạn nếu nhiều instance cùng tranh refresh.

**Tại sao hữu ích:**
Cache stampede làm database nhận burst load đúng lúc cache mất tác dụng. Hệ thống có thể từ trạng thái bình thường chuyển sang saturation dù traffic không tăng đáng kể.

**Ví dụ:**
Một product catalog key có TTL 5 phút. Khi miss:

1. Request đầu tiên nhận quyền refresh.
2. Các request khác chờ ngắn hoặc dùng stale value có kiểm soát.
3. Sau khi cache được populate, tất cả đọc lại từ Redis.

**Lưu ý:**
Distributed lock không nên trở thành dependency cứng cho mọi cache read. Phải có timeout, lock expiry và behavior khi lock holder chết; nếu không, cơ chế chống stampede có thể tự tạo outage.

### Tip 4 — Dùng `git worktree` khi cần xử lý nhiều branch song song

**Mẹo:**
Nếu đang làm feature nhưng cần hotfix gấp, dùng `git worktree` để checkout branch khác vào thư mục riêng thay vì stash, switch branch rồi khôi phục context liên tục.

**Tại sao hữu ích:**
Mỗi worktree có working directory riêng nhưng dùng chung repository object database. Điều này giảm context switching và tránh lỗi do stash chưa apply hoặc file generated bị lẫn giữa hai branch.

**Ví dụ:**
```bash
git worktree add ../app-hotfix hotfix/payment-timeout
```

Bạn có thể giữ feature branch ở thư mục hiện tại và xử lý hotfix ở `../app-hotfix`.

**Lưu ý:**
Không checkout cùng một branch vào hai worktree cùng lúc. Đồng thời phải quản lý IDE, local configuration và service port để hai instance không tranh tài nguyên.

### Tip 5 — Tách content model khỏi rendering concern trong CMS

**Mẹo:**
Trong Optimizely CMS hoặc CMS tương tự, model content theo ý nghĩa nghiệp vụ thay vì theo layout cụ thể của một page template. Block nên đại diện cho capability nội dung có thể tái sử dụng, không phải chỉ là “cột trái”, “cột phải”.

**Tại sao hữu ích:**
Nếu content schema gắn chặt với presentation hiện tại, mỗi redesign sẽ kéo theo migration content và phá reuse. Model theo intent giúp frontend, headless API và editor workflow tiến hóa độc lập hơn.

**Ví dụ:**
Thay vì tạo block `HomepageThreeColumnPromo`, có thể dùng `PromoCard` với fields như `Heading`, `Image`, `Link`, `Theme`, rồi để rendering layer quyết định grid theo context.

**Lưu ý:**
Đừng generic hóa block quá mức thành một “universal content block” chứa hàng chục tùy chọn. Quá nhiều flexibility làm validation yếu, editor UX kém và domain intent biến mất.

## 🧠 Software Design

### Design 1 — Idempotency Key cho API tạo resource

**Khái niệm:**
Idempotency Key cho phép client gửi một identifier ổn định cùng request tạo resource. Server lưu kết quả của lần xử lý đầu và trả lại cùng kết quả nếu nhận duplicate request với cùng key.

**Vấn đề nó giải quyết:**
Trong distributed systems, client có thể timeout sau khi server đã commit. Nếu client retry `POST /payments` mà server không nhận biết duplicate, cùng một business operation có thể bị xử lý hai lần.

**Ví dụ thực tế:**
Mobile app gửi:

```http
POST /api/payments
Idempotency-Key: 18fe7d3c-6d0c-43e2-a82c-8e5d78b56190
```

Server atomically liên kết key với payment result. Retry với cùng key trả lại payment đã tạo thay vì charge lần nữa.

**Trade-off:**
Lợi ích là retry an toàn hơn và giảm duplicate side effect. Chi phí là phải lưu key, response/result state, expiration policy và xử lý concurrent requests dùng cùng key.

**Middle → Senior insight:**
Middle developer cần implement uniqueness và replay behavior đúng. Senior / Technical developer cần xác định idempotency boundary, TTL, payload mismatch policy, transaction semantics và storage strategy thay vì chỉ thêm một header rồi coi bài toán đã xong.

### Design 2 — Azure Functions vs Worker Service

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có execution độc lập, scale theo trigger và ít yêu cầu control lifecycle. Worker Service phù hợp hơn khi cần process chạy dài, concurrency control chi tiết hoặc stateful coordination trong process.

**Vấn đề nó giải quyết:**
Cả hai đều có thể xử lý background work, nhưng operational model khác nhau. Chọn sai có thể tạo cold start, execution constraint hoặc ngược lại phải vận hành một service liên tục cho workload rất thưa.

**Ví dụ thực tế:**
Một hệ thống nhận vài nghìn BlobCreated event rải rác trong ngày để generate thumbnail có thể hợp với Azure Functions. Một message processor cần giữ 20 consumer song song, custom batching, graceful shutdown và backpressure phức tạp có thể phù hợp Worker Service hơn.

**Trade-off:**
Functions giảm infrastructure management và scale tốt theo event, nhưng runtime/hosting behavior ít linh hoạt hơn và cost có thể thay đổi theo workload. Worker Service cho lifecycle control rõ hơn nhưng cần deployment, scaling và availability planning riêng.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và shutdown behavior. Senior / Technical developer phải đánh giá workload duration, throughput profile, scaling requirement, operational ownership, cold-start tolerance và cost trước khi chọn hosting model.

### Design 3 — Chuẩn hóa dữ liệu vs read model tối ưu truy vấn

**Khái niệm:**
Normalized relational schema ưu tiên consistency và tránh duplication. Read model có thể denormalize dữ liệu theo query pattern để giảm join hoặc aggregation cost, nhưng chấp nhận thêm synchronization logic.

**Vấn đề nó giải quyết:**
Một schema tối ưu cho transactional integrity không phải lúc nào cũng tối ưu cho dashboard, search hoặc reporting read path có throughput cao.

**Ví dụ thực tế:**
Order database giữ `Orders`, `OrderItems`, `Customers` chuẩn hóa. Dashboard cần hiển thị doanh thu theo customer và region với latency dưới 200 ms. Thay vì thêm hàng loạt join/index vào OLTP path, hệ thống có thể duy trì read model `CustomerRevenueSummary` cập nhật async.

**Trade-off:**
Normalized model đơn giản hơn về source of truth và update consistency. Denormalized read model tăng read performance và giảm query complexity nhưng tạo eventual consistency, storage duplication và operational burden cho synchronization/rebuild.

**Middle → Senior insight:**
Middle developer cần hiểu normalization, index và query plan trước khi denormalize. Senior / Technical developer cần chứng minh read bottleneck bằng measurement, xác định tolerance cho stale data và chọn giữa index/query tuning, materialized view, cache hoặc dedicated read model theo constraint thực tế.
