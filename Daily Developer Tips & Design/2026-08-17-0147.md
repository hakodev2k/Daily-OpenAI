# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ValueTask` chỉ khi profiling chứng minh có lợi

**Mẹo:**
`ValueTask<T>` có thể giảm allocation khi một async method thường xuyên hoàn thành synchronously, nhưng không nên dùng thay `Task<T>` theo thói quen.

**Tại sao hữu ích:**
Trong hot path có tần suất gọi rất cao, việc tránh tạo `Task` object cho các kết quả có sẵn có thể giảm GC pressure.

**Ví dụ:**
```csharp
public ValueTask<User?> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out var user))
    {
        return ValueTask.FromResult<User?>(user);
    }

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

**Lưu ý:**
`ValueTask` phức tạp hơn `Task`: không nên await nhiều lần hoặc lưu giữ tùy tiện. Nếu method gần như luôn bất đồng bộ, `Task<T>` thường đơn giản và đủ tốt.

### Tip 2 — Dùng `TagWith()` để truy ngược SQL về source code trong EF Core

**Mẹo:**
Khi có nhiều query giống nhau trong production, dùng `TagWith()` để thêm comment vào SQL do EF Core sinh ra.

**Tại sao hữu ích:**
Giúp DBA hoặc developer nhìn execution plan, slow query log hay monitoring và biết query đến từ use case nào mà không phải đoán dựa trên SQL shape.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .TagWith("OrdersController.GetRecentOrders")
    .Where(x => x.CreatedAt >= fromDate)
    .OrderByDescending(x => x.CreatedAt)
    .Take(100)
    .ToListAsync();
```

SQL sẽ chứa comment tương tự:

```sql
-- OrdersController.GetRecentOrders
SELECT ...
```

**Lưu ý:**
Tag nên ổn định và không chứa dữ liệu nhạy cảm hoặc giá trị động theo từng request, nếu không log/query cache có thể trở nên khó quản lý.

### Tip 3 — Dùng `curl -v` và `openssl s_client` để tách lỗi HTTP khỏi lỗi TLS

**Mẹo:**
Khi API gọi được ở local nhưng fail trên server, kiểm tra riêng DNS, TCP, TLS và HTTP thay vì chỉ nhìn exception từ application.

**Tại sao hữu ích:**
Giúp phân biệt nhanh lỗi certificate chain, SNI, proxy, firewall, DNS hay chính API response.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Kiểm tra TLS chi tiết:

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com
```

**Lưu ý:**
Đừng tắt certificate validation để “fix” lỗi production. Nếu TLS fail, cần sửa certificate trust, hostname, proxy hoặc chain đúng cách.

### Tip 4 — Dùng optimistic concurrency thay vì lock dài cho update cạnh tranh

**Mẹo:**
Với các entity thường được nhiều request chỉnh sửa, dùng concurrency token như SQL Server `rowversion` để phát hiện update conflict.

**Tại sao hữu ích:**
Tránh việc request sau âm thầm ghi đè dữ liệu request trước mà không biết, đồng thời không cần giữ database lock trong suốt thời gian người dùng thao tác.

**Ví dụ:**
```csharp
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
```

Khi version đã thay đổi, EF Core có thể ném:

```csharp
DbUpdateConcurrencyException
```

**Lưu ý:**
Concurrency exception chỉ phát hiện conflict; bạn vẫn phải quyết định business behavior: retry, merge, reject hay yêu cầu người dùng reload dữ liệu.

### Tip 5 — Dùng `docker exec` và `/proc` để debug container trước khi rebuild image

**Mẹo:**
Khi container chạy nhưng application có vấn đề, kiểm tra process, environment, network và filesystem ngay trong container trước khi sửa Dockerfile.

**Tại sao hữu ích:**
Nhiều lỗi production thực tế đến từ runtime configuration, mounted volume, DNS hoặc environment variable chứ không phải image build.

**Ví dụ:**
```bash
docker exec -it my-api sh
```

Sau đó:

```bash
printenv
cat /proc/1/cmdline
cat /etc/resolv.conf
ls -la /app
```

Kiểm tra logs:

```bash
docker logs --tail 200 my-api
```

**Lưu ý:**
Thay đổi file trực tiếp bên trong running container chỉ mang tính tạm thời và sẽ mất khi container được recreate. Root cause phải được sửa ở image, config hoặc deployment definition.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database + message broker

**Khái niệm:**
Outbox Pattern lưu business change và message cần publish vào cùng một database transaction. Một background publisher sau đó đọc Outbox và gửi message sang broker.

**Vấn đề nó giải quyết:**
Nếu application vừa `SaveChanges()` vừa publish RabbitMQ/Kafka trực tiếp, có thể xảy ra trạng thái database commit thành công nhưng publish message thất bại, hoặc ngược lại.

**Ví dụ thực tế:**
Khi tạo `Order`, transaction ghi đồng thời:

```text
Orders
OutboxMessages(OrderCreated)
```

Worker đọc `OutboxMessages`, publish `OrderCreated`, rồi đánh dấu message đã xử lý.

**Trade-off:**
Lợi ích là tránh dual-write inconsistency mà không cần distributed transaction. Chi phí là thêm Outbox table, background publisher, cleanup, retry và xử lý duplicate delivery phía consumer.

**Middle → Senior insight:**
Middle developer nên hiểu tại sao database transaction không thể tự động bao phủ message broker. Senior developer cần thiết kế delivery semantics, retry/backoff, idempotent consumer, ordering và chiến lược cleanup để Outbox không trở thành bottleneck.

### Design 2 — Bulkhead Isolation để giới hạn blast radius

**Khái niệm:**
Bulkhead chia tài nguyên như connection pool, worker, queue hoặc concurrency limit theo workload để một dependency hoặc feature bị nghẽn không chiếm toàn bộ capacity của hệ thống.

**Vấn đề nó giải quyết:**
Một downstream service chậm có thể khiến hàng trăm request cùng chờ, ăn hết thread, connection hoặc socket và kéo những chức năng không liên quan cùng chết theo.

**Ví dụ thực tế:**
Một hệ thống có hai outbound integration: Payment và Analytics. Payment được cấp concurrency riêng, Analytics có queue và worker riêng. Nếu Analytics timeout hàng loạt, Payment vẫn còn resource để phục vụ checkout.

**Trade-off:**
Lợi ích là tăng fault isolation và giảm cascading failure. Chi phí là capacity bị chia nhỏ, cấu hình phức tạp hơn và có nguy cơ một partition thiếu tài nguyên trong khi partition khác còn dư.

**Middle → Senior insight:**
Middle developer nên hiểu timeout/retry không đủ để ngăn failure lan rộng. Senior developer phải xác định blast radius, phân bổ resource theo criticality và theo dõi saturation để điều chỉnh bulkhead dựa trên workload thực tế.

### Design 3 — CQRS chỉ khi read/write thực sự có nhu cầu khác nhau

**Khái niệm:**
CQRS tách mô hình xử lý command khỏi mô hình query để mỗi phía có thể tối ưu theo nhu cầu riêng. Nó không đồng nghĩa bắt buộc phải dùng Microservices, Event Sourcing hoặc hai database.

**Vấn đề nó giải quyết:**
Một domain có write model phức tạp để bảo vệ invariant nhưng read model cần query phẳng, denormalized và tối ưu cho dashboard/reporting có thể trở nên khó duy trì nếu ép chung một mô hình.

**Ví dụ thực tế:**
Hệ thống order dùng aggregate để validate thao tác `ConfirmOrder`, nhưng dashboard cần đọc nhanh tổng doanh thu theo ngày, trạng thái và khu vực. Query side có thể dùng projection/read model riêng thay vì load aggregate cho từng dòng báo cáo.

**Trade-off:**
Lợi ích là tách concern và tối ưu read/write độc lập. Chi phí là duplicate model, mapping, synchronization, eventual consistency và nhiều code/operational complexity hơn.

**Middle → Senior insight:**
Middle developer nên hiểu CQRS là separation of responsibilities, không phải template phải áp dụng cho mọi endpoint. Senior developer phải chứng minh read/write asymmetry đủ lớn để biện minh cho complexity, đồng thời quyết định mức tách phù hợp: chỉ tách handler/model trong cùng application hay tách cả storage và deployment.
