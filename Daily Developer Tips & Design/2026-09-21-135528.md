# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán ThreadPool starvation bằng evidence, không bằng cách tăng thread ngay lập tức

**Mẹo:**
Khi ASP.NET Core latency tăng mạnh nhưng CPU chưa bão hòa, kiểm tra ThreadPool queue, thread count, request latency và blocking call trước khi kết luận hệ thống thiếu tài nguyên. Đặc biệt tìm các đoạn sync-over-async như `.Result`, `.Wait()` hoặc synchronous I/O nằm trên request path.

**Tại sao hữu ích:**
ThreadPool starvation xảy ra khi worker threads bị giữ bởi công việc blocking trong khi work mới tiếp tục xếp hàng. Runtime có thể bổ sung threads nhưng quá trình ramp-up không tức thời; latency vì vậy có thể tăng mạnh dù CPU còn rảnh. Chuyển đúng I/O path sang async thường xử lý nguyên nhân tốt hơn việc chỉ tăng minimum threads.

**Ví dụ:**
Sau deployment, p95 API tăng từ 200 ms lên 8 giây trong khi CPU chỉ 35%. `dotnet-counters` cho thấy ThreadPool queue tăng và thread count liên tục leo lên. Trace cuối cùng phát hiện middleware gọi một SDK asynchronous bằng `.Result`; sửa call chain thành `await` làm queue trở lại bình thường.

**Lưu ý:**
Không phải queue tăng nào cũng là starvation; CPU saturation hoặc downstream chậm cũng có thể tạo triệu chứng tương tự. `ThreadPool.SetMinThreads` đôi khi hữu ích cho workload đặc thù nhưng không nên dùng để che blocking I/O chưa được điều tra.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` khi dữ liệu lớn và liên tục thay đổi

**Mẹo:**
Với feed hoặc danh sách lớn, cân nhắc keyset pagination bằng một ordering deterministic như `(CreatedAt, Id)` thay vì tăng `OFFSET` theo page number.

**Tại sao hữu ích:**
Database thường vẫn phải đi qua hoặc loại bỏ nhiều rows trước khi trả một page có offset lớn. Ngoài ra, insert/delete giữa hai requests có thể khiến offset pagination bỏ sót hoặc lặp records. Keyset dùng vị trí cuối cùng đã đọc để tiếp tục từ index range phù hợp.

**Ví dụ:**
Thay vì `ORDER BY CreatedAt DESC OFFSET 100000 ROWS FETCH NEXT 50 ROWS ONLY`, API truyền cursor chứa `CreatedAt` và `Id` cuối page trước rồi query điều kiện lexicographic tương ứng, với composite index hỗ trợ cùng ordering.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 437 hoặc cần tổng số page chính xác. Ordering phải unique/deterministic; chỉ dùng `CreatedAt` có thể làm mất records khi nhiều rows có cùng timestamp.

### Tip 3 — Managed Identity loại bỏ secret, nhưng không loại bỏ authorization design

**Mẹo:**
Trên Azure, ưu tiên Managed Identity cho App Service, Functions hoặc workload phù hợp khi truy cập Key Vault và các Azure resources hỗ trợ Microsoft Entra authentication. Sau đó cấp đúng role/quyền tối thiểu cho identity đó thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Secret tĩnh phải được tạo, phân phối, bảo vệ và rotate. Managed Identity chuyển credential lifecycle cho Azure, giảm nguy cơ secret bị commit hoặc rò qua deployment variables. Tuy nhiên identity vẫn cần authorization đúng scope; credential-less không đồng nghĩa permission-less.

**Ví dụ:**
Một ASP.NET Core API đọc secrets từ Key Vault bằng `DefaultAzureCredential`: local development dùng developer identity phù hợp, còn production dùng Managed Identity của App Service. Production identity chỉ có quyền đọc đúng vault cần thiết thay vì quyền rộng ở subscription.

**Lưu ý:**
Đừng cấp role quá rộng để “cho chạy được”. Kiểm tra propagation delay của role assignment, network restrictions/private endpoints và phân biệt lỗi authentication với authorization khi production trả `403`.

### Tip 4 — Frontend phải hủy hoặc loại bỏ response cũ khi request mới đã thay thế nó

**Mẹo:**
Trong Vue.js hoặc React.js, khi user thay đổi search/filter nhanh, dùng `AbortController` hoặc request identity để ngăn response của request cũ ghi đè state của request mới.

**Tại sao hữu ích:**
HTTP responses không đảm bảo hoàn thành theo thứ tự gửi. Request cho từ khóa `lap` có thể trả sau request `laptop`; nếu component cập nhật state vô điều kiện, UI hiển thị kết quả stale dù backend hoàn toàn đúng.

**Ví dụ:**
Search component tạo `AbortController` mới cho mỗi query và abort controller trước đó. Chỉ response thuộc request hiện hành được phép cập nhật results/loading state, nhờ đó typing nhanh không gây “nhảy ngược” dữ liệu.

**Lưu ý:**
Abort phía browser không đảm bảo server đã rollback hoặc dừng mọi side effect. Với write operations, vẫn cần idempotency/concurrency semantics ở backend; đừng coi client cancellation là consistency mechanism.

### Tip 5 — Playwright test nên chờ trạng thái nghiệp vụ, không chờ thời gian cố định

**Mẹo:**
Trong end-to-end tests, ưu tiên locator assertions, network/UI state hoặc domain-visible condition thay vì `waitForTimeout(3000)` để “đợi UI ổn định”.

**Tại sao hữu ích:**
Fixed sleep làm test vừa chậm vừa flaky: 3 giây là dư trên máy nhanh nhưng vẫn thiếu trên CI chậm. Auto-waiting và condition-based assertions đồng bộ test với trạng thái thực mà người dùng quan sát được.

**Ví dụ:**
Sau khi submit order, test chờ heading `Order confirmed` hoặc response/state cụ thể thay vì ngủ 5 giây rồi kiểm tra DOM. Nếu hệ thống mất 20 giây vì regression, test thất bại với signal rõ hơn thay vì ngẫu nhiên pass/fail theo timing.

**Lưu ý:**
Không đợi implementation detail không ổn định chỉ để làm test xanh. Nếu UI không có một trạng thái quan sát được đáng tin cậy, đó có thể là dấu hiệu cần cải thiện contract/testability thay vì thêm sleep dài hơn.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service: chọn theo execution model, không theo độ “cloud-native”

**Khái niệm:**
Azure Functions phù hợp với event-driven execution có trigger/binding và khả năng scale theo platform; Worker Service phù hợp khi cần process dài hạn, lifecycle/control rõ, polling hoặc resource behavior ổn định. Hai lựa chọn giải quyết các execution models khác nhau chứ không phải cấp độ hiện đại khác nhau.

**Vấn đề nó giải quyết:**
Team thường chọn Functions chỉ vì workload chạy nền, rồi gặp cold start, execution/runtime constraints hoặc khó kiểm soát long-running behavior; chiều ngược lại, vận hành Worker Service cho workload thưa và event-driven có thể thêm deployment/scale overhead không cần thiết.

**Ví dụ thực tế:**
Xử lý Blob mới upload thành thumbnail có thể phù hợp với Function trigger. Một engine đồng bộ catalog chạy liên tục, duy trì nhiều stateful coordination rules và cần graceful shutdown/control chi tiết có thể phù hợp hơn với Worker Service chạy trên App Service/container platform.

**Trade-off:**
Functions giảm infrastructure ceremony và tích hợp trigger tốt nhưng tăng phụ thuộc execution model của platform. Worker Service cho lifecycle/control rõ hơn nhưng team phải chịu trách nhiệm nhiều hơn về hosting, scaling, health và deployment.

**Middle → Senior insight:**
Middle developer cần implement retry, cancellation, idempotency và shutdown đúng cho model đã chọn. Senior / Technical developer phải đánh giá traffic shape, duration, scaling, failure recovery, cost, observability và operational ownership trước khi chọn Functions hay Worker Service.

### Design 2 — Chọn SQL hay Cosmos DB bắt đầu từ access pattern và consistency requirement

**Khái niệm:**
Database choice nên xuất phát từ invariants, query patterns, transaction boundaries, scale/distribution và consistency cần thiết. “Schema linh hoạt” hoặc “cần scale” riêng lẻ không đủ để kết luận nên dùng NoSQL.

**Vấn đề nó giải quyết:**
Đưa relational domain có nhiều cross-entity constraints vào document database có thể chuyển complexity sang application; ngược lại, ép workload key-value/document phân tán khổng lồ vào relational model có thể tạo scaling và operational pressure không cần thiết.

**Ví dụ thực tế:**
Order/payment ledger cần transaction và relational reporting mạnh có thể phù hợp SQL Server/PostgreSQL. Một globally distributed device-state store truy cập chủ yếu theo `DeviceId`/tenant partition, với document aggregate rõ và consistency requirement phù hợp, có thể là ứng viên tốt cho Cosmos DB.

**Trade-off:**
Relational database cung cấp joins, constraints và transaction semantics mạnh nhưng horizontal distribution có thể phức tạp hơn. Cosmos DB cung cấp partitioned distribution và tunable consistency nhưng partition-key mistakes, cross-partition queries và RU cost có thể trở thành vấn đề kiến trúc lâu dài.

**Middle → Senior insight:**
Middle developer cần model/query đúng theo database đã chọn và hiểu index/transaction limitations. Senior / Technical developer phải chứng minh lựa chọn bằng access patterns, data growth, hot-partition risk, consistency, migration/operational cost và khả năng thay đổi requirements trong tương lai.

### Design 3 — Observability cardinality là một phần của architecture

**Khái niệm:**
Metrics, logs và traces cần đủ dimensions để chẩn đoán nhưng phải kiểm soát cardinality. Một label có số lượng giá trị gần như vô hạn như `UserId`, raw URL hoặc request ID có thể biến metric system thành nguồn chi phí và instability.

**Vấn đề nó giải quyết:**
Team thường thêm mọi context vào metric labels để “debug dễ hơn”, nhưng mỗi combination tạo time series mới. Khi cardinality bùng nổ, ingestion/storage/query cost tăng và dashboard/alert có thể chậm đúng lúc incident cần chúng nhất.

**Ví dụ thực tế:**
Metric HTTP latency dùng route template, status class, service và region; `CorrelationId`/`UserId` được giữ trong structured logs/traces để drill-down. Nhờ vậy dashboard vẫn aggregate hiệu quả trong khi investigation vẫn có đường sang dữ liệu chi tiết.

**Trade-off:**
Giảm dimensions quá mức làm mất khả năng phân đoạn sự cố; thêm quá nhiều dimensions làm telemetry đắt và khó vận hành. Cần quyết định dữ liệu nào thuộc metrics, logs hay traces thay vì coi ba loại telemetry là nơi chứa cùng một context.

**Middle → Senior insight:**
Middle developer cần dùng structured telemetry và tránh high-cardinality labels rõ ràng. Senior / Technical developer phải thiết kế telemetry schema theo SLO, incident workflows, retention/cost budget và privacy, đồng thời bảo đảm observability vẫn hoạt động khi traffic hoặc failure volume tăng mạnh.
