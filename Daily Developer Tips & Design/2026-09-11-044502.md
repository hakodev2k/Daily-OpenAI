# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `FrozenDictionary` khi dữ liệu chỉ đọc sau khởi tạo

**Mẹo:**
Với lookup table lớn được build một lần rồi đọc rất nhiều lần trong suốt lifetime của process, cân nhắc `FrozenDictionary<TKey,TValue>` hoặc `FrozenSet<T>` thay vì giữ `Dictionary` thông thường nếu workload phù hợp.

**Tại sao hữu ích:**
Frozen collections tối ưu cấu trúc nội bộ cho read-heavy access sau khi construction hoàn tất. Bạn đánh đổi chi phí tạo ban đầu cao hơn để có lookup ổn định và giảm nhu cầu bảo vệ mutation trong runtime.

**Ví dụ:**
```csharp
private static readonly FrozenDictionary<string, int> StatusCodes =
    new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase)
    {
        ["active"] = 1,
        ["disabled"] = 2,
        ["pending"] = 3
    }.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);
```

Phù hợp với mapping, routing metadata hoặc reference data ít thay đổi nhưng được đọc ở hot path.

**Lưu ý:**
Không dùng frozen collection nếu dữ liệu cần mutation thường xuyên. Hãy đo benchmark trong workload thật; với collection nhỏ hoặc ít truy cập, lợi ích có thể không đáng kể.

### Tip 2 — Partition rate limit theo tenant hoặc user thay vì chỉ theo IP

**Mẹo:**
Trong ASP.NET Core, với SaaS hoặc API đa tenant, thiết kế limiter theo identity phù hợp như tenant, API key hoặc user thay vì chỉ dùng source IP.

**Tại sao hữu ích:**
Nhiều user có thể đi qua cùng NAT/proxy, còn một client độc hại có thể phân tán request qua nhiều IP. Partition key gần với business identity giúp quota phản ánh đúng consumer và tránh chặn nhầm nhóm user hợp lệ.

**Ví dụ:**
```csharp
options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
{
    var tenantId = ctx.User.FindFirst("tenant_id")?.Value ?? "anonymous";

    return RateLimitPartition.GetFixedWindowLimiter(
        tenantId,
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1),
            QueueLimit = 0
        });
});
```

**Lưu ý:**
Rate limit không thay thế authorization hay abuse detection. Partition key phải khó spoof và quota cần xét endpoint cost; 100 request tìm kiếm nặng có thể đắt hơn 100 health checks.

### Tip 3 — Khi gặp deadlock SQL Server, đọc deadlock graph thay vì đoán bằng thứ tự query

**Mẹo:**
Nếu production xuất hiện error 1205, thu thập deadlock graph qua Extended Events hoặc tooling tương đương để biết session nào giữ resource nào và đang chờ resource nào.

**Tại sao hữu ích:**
Deadlock không chỉ do “hai query chạy cùng lúc”. Nó liên quan lock mode, access path, transaction scope, index usage và thứ tự resource acquisition. Deadlock graph cho evidence trực tiếp để sửa nguyên nhân thay vì thêm retry rồi bỏ qua vấn đề.

**Ví dụ:**
```text
Transaction A:
- giữ X lock trên Orders
- chờ X lock trên Inventory

Transaction B:
- giữ X lock trên Inventory
- chờ X lock trên Orders
```

Giải pháp có thể là thống nhất thứ tự truy cập resource, rút ngắn transaction hoặc thay đổi query/index để giảm lock footprint.

**Lưu ý:**
Retry sau deadlock thường vẫn cần vì victim transaction phải chạy lại, nhưng retry không phải root-cause fix nếu deadlock xảy ra thường xuyên.

### Tip 4 — Upload file lớn lên Azure Blob bằng direct client upload khi backend không cần chạm vào bytes

**Mẹo:**
Nếu browser/mobile client cần upload file lớn và backend chỉ chịu trách nhiệm authorization/metadata, cân nhắc cấp SAS ngắn hạn để client upload trực tiếp tới Azure Blob Storage.

**Tại sao hữu ích:**
Proxy toàn bộ file qua ASP.NET Core làm backend chịu bandwidth, connection duration, memory/buffer pressure và scale cost không cần thiết. Direct upload chuyển data path sang storage service, còn backend giữ control plane.

**Ví dụ:**
```text
1. Client -> API: xin upload permission
2. API: validate user + file policy
3. API -> Client: SAS URL ngắn hạn
4. Client -> Blob Storage: upload trực tiếp
5. Client -> API: xác nhận hoàn tất / metadata
```

**Lưu ý:**
SAS phải scope tối thiểu, thời hạn ngắn và không cho quyền thừa. Vẫn cần validate filename/metadata, giới hạn kích thước, malware scanning hoặc post-upload verification tùy risk profile.

### Tip 5 — Khi AI sinh migration hoặc SQL, luôn kiểm tra execution plan và lock impact trước khi merge

**Mẹo:**
Nếu AI coding agent đề xuất index, migration hoặc query optimization, đừng chỉ kiểm tra syntax và test result; review cả execution plan, lock duration, table size và deployment behavior.

**Tại sao hữu ích:**
SQL do AI sinh có thể đúng về logic nhưng gây table scan, blocking kéo dài, rebuild index lớn hoặc lock schema trong giờ cao điểm. Những lỗi này thường chỉ lộ khi dữ liệu và concurrency đủ lớn.

**Ví dụ:**
```text
AI đề xuất:
ALTER TABLE Orders ADD NewColumn NVARCHAR(200) NOT NULL DEFAULT '';

Cần kiểm tra:
- bảng có bao nhiêu row?
- operation có metadata-only hay rewrite data?
- lock duration?
- rolling deployment có tương thích?
- cần expand-and-contract không?
```

**Lưu ý:**
Không mặc định code AI là rủi ro hơn code người viết, nhưng database change cần quality gate nghiêm vì blast radius và rollback cost cao.

## 🧠 Software Design

### Design 1 — Inbox Pattern để xử lý message trùng mà vẫn giữ business transaction nhất quán

**Khái niệm:**
Inbox Pattern lưu dấu message đã xử lý trong cùng transaction với business change của consumer. Nếu broker redeliver cùng message, consumer nhận ra duplicate và bỏ qua side effect lần hai.

**Vấn đề nó giải quyết:**
Hệ thống message thường cung cấp at-least-once delivery. Consumer có thể commit database nhưng crash trước khi acknowledge message, khiến broker gửi lại và gây double charge, duplicate email hoặc update trạng thái hai lần.

**Ví dụ thực tế:**
```text
MessageId: order-paid-123

Transaction:
1. kiểm tra Inbox chưa có MessageId
2. cập nhật Order = Paid
3. INSERT Inbox(MessageId)
4. COMMIT
5. acknowledge message
```

Nếu message được giao lại, bước 1 phát hiện nó đã được xử lý.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, cleanup, unique constraint và retention strategy. Với side effect ngoài database như gửi email hay gọi payment provider, bạn vẫn cần thiết kế idempotency hoặc thêm outbox ở phía phát side effect.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là bình thường chứ không phải anomaly. Senior / Technical developer phải xác định idempotency boundary, transaction scope, retention window, message identity và cách phối hợp Inbox với Outbox khi workflow có nhiều side effect.

### Design 2 — API Versioning chỉ nên dùng khi compatibility không thể duy trì bằng evolution thông thường

**Khái niệm:**
API versioning tạo explicit contract lineage khi có breaking change thực sự. Nhưng nhiều thay đổi có thể xử lý bằng additive evolution: thêm field optional, thêm endpoint mới hoặc giữ semantics cũ trong migration window.

**Vấn đề nó giải quyết:**
Nếu version mọi thay đổi nhỏ, hệ thống nhanh chóng có nhiều `/v1`, `/v2`, `/v3` cùng sống, tăng test matrix, support cost và khó deprecate. Ngược lại, cố giữ một version duy nhất bằng mọi giá có thể làm contract ngày càng méo mó.

**Ví dụ thực tế:**
```text
Thêm optional field `displayName`
-> thường không cần version mới

Đổi `amount` từ integer cents sang decimal currency semantics
-> có thể cần contract/version mới
```

**Trade-off:**
Versioning cho boundary rõ và migration có kiểm soát, nhưng tăng duplication, documentation và maintenance. Additive evolution đơn giản hơn nhưng đòi consumer tolerant và discipline về backward compatibility.

**Middle → Senior insight:**
Middle developer cần phân biệt additive với breaking change. Senior / Technical developer phải cân nhắc consumer diversity, release cadence, deprecation policy và operational cost trước khi quyết định tạo version mới.

### Design 3 — Domain Service và Application Service giải quyết hai loại responsibility khác nhau

**Khái niệm:**
Application Service điều phối use case, transaction, authorization và integration flow; Domain Service chứa business rule có ý nghĩa domain nhưng không thuộc tự nhiên về một entity/value object cụ thể.

**Vấn đề nó giải quyết:**
Nếu mọi business logic bị nhét vào controller/application handler, domain model trở nên anemic. Nhưng nếu mọi orchestration đều bị gọi là Domain Service, domain layer lại bị nhiễm repository, HTTP client và infrastructure concern.

**Ví dụ thực tế:**
```text
Application Service:
- load Order
- gọi PricingPolicy
- save transaction
- publish event

Domain Service / Policy:
- tính discount dựa trên customer tier + order value
- không gọi database hoặc HTTP trực tiếp
```

**Trade-off:**
Tách đúng boundary tăng testability và clarity, nhưng tạo thêm abstraction nếu business logic đơn giản. Không phải mọi phép tính cần một Domain Service riêng.

**Middle → Senior insight:**
Middle developer cần đặt business rule đúng layer và tránh service phụ thuộc infrastructure vô cớ. Senior / Technical developer phải quyết định khi nào behavior nên nằm trong entity, value object, domain service hay application orchestration dựa trên cohesion, invariant và dependency direction.
