# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer hot-path thay vì allocate mảng lớn liên tục

**Mẹo:**
Khi một đoạn code hiệu năng cao liên tục cần buffer tạm có kích thước tương đối lớn, cân nhắc `ArrayPool<T>.Shared.Rent()` / `Return()` thay vì tạo `new byte[...]` ở mỗi request hoặc mỗi iteration.

**Tại sao hữu ích:**
Các mảng lớn hoặc được tạo với tần suất cao làm tăng allocation rate và áp lực lên Garbage Collector. Pooling cho phép tái sử dụng vùng nhớ giữa nhiều operation, đặc biệt hữu ích với parsing, serialization, compression hoặc stream processing trong hot path.

**Ví dụ:**
```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

Chỉ phần `0..read` là dữ liệu hợp lệ của operation hiện tại; mảng được `Rent` có thể lớn hơn kích thước yêu cầu.

**Lưu ý:**
Buffer lấy từ pool có thể chứa dữ liệu của lần sử dụng trước, vì vậy không được giả định nó đã zeroed. Với secret hoặc dữ liệu nhạy cảm, cần cân nhắc `clearArray: true` hoặc chủ động xóa phần đã dùng. Luôn `Return` trong `finally`; pooling sai lifecycle có thể tạo memory retention hoặc data-corruption bug khó tìm.

### Tip 2 — Dùng filtered index khi workload chỉ truy vấn một tập con nhỏ nhưng rất “nóng”

**Mẹo:**
Trong SQL Server, nếu phần lớn query quan trọng chỉ nhắm tới một subset nhỏ và ổn định của bảng, ví dụ order đang `Pending`, cân nhắc filtered index thay vì index toàn bộ bảng.

**Tại sao hữu ích:**
Một bảng có 50 triệu order nhưng chỉ 100 nghìn order ở trạng thái `Pending` không nhất thiết cần index chứa cả 50 triệu row để phục vụ worker lấy pending work. Filtered index nhỏ hơn, thường cache tốt hơn và giảm chi phí maintenance cho các row không thuộc workload mục tiêu.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON dbo.Orders (CreatedAt, Id)
INCLUDE (CustomerId, Total)
WHERE Status = 'Pending';
```

Query tương ứng:

```sql
SELECT TOP (100) Id, CustomerId, Total
FROM dbo.Orders
WHERE Status = 'Pending'
ORDER BY CreatedAt, Id;
```

**Lưu ý:**
Filtered index chỉ hữu ích khi predicate của query cho phép optimizer chứng minh nó phù hợp với filter. Parameterization, kiểu dữ liệu hoặc predicate khác nhau có thể làm index không được chọn. Đừng tạo nhiều filtered index cho từng trạng thái nếu write cost và operational complexity vượt lợi ích.

### Tip 3 — Với MongoDB update đồng thời, đưa expected state vào filter thay vì “đọc rồi mới quyết định”

**Mẹo:**
Khi một state transition chỉ hợp lệ từ trạng thái hiện tại cụ thể, encode expected state trực tiếp trong filter của `UpdateOneAsync()` và kiểm tra `ModifiedCount` thay vì đọc document trước rồi update bằng một lệnh riêng.

**Tại sao hữu ích:**
Flow `Find -> kiểm tra Status -> Update` có race window: hai worker có thể cùng đọc `Pending`, cùng kết luận được phép xử lý rồi cùng ghi side effect. Atomic conditional update biến state transition thành một compare-and-set ở database boundary.

**Ví dụ:**
```csharp
var filter = Builders<Order>.Filter.And(
    Builders<Order>.Filter.Eq(x => x.Id, orderId),
    Builders<Order>.Filter.Eq(x => x.Status, OrderStatus.Pending));

var update = Builders<Order>.Update
    .Set(x => x.Status, OrderStatus.Processing)
    .Set(x => x.UpdatedAt, now);

var result = await collection.UpdateOneAsync(filter, update, cancellationToken: ct);

if (result.ModifiedCount != 1)
{
    // Document không tồn tại hoặc state đã thay đổi bởi worker khác.
}
```

**Lưu ý:**
Atomic update trên một document không biến toàn bộ workflow nhiều document/external side effect thành transaction. Nếu sau khi claim state còn gọi payment, gửi message hoặc sửa collection khác, vẫn cần idempotency, recovery và transaction boundary phù hợp.

### Tip 4 — Dùng `git worktree` khi cần làm nhiều branch song song mà không muốn stash liên tục

**Mẹo:**
Khi đang sửa feature nhưng cần mở ngay hotfix hoặc review branch khác, dùng `git worktree` để checkout branch thứ hai ở một thư mục riêng, cùng chia sẻ object database của repository.

**Tại sao hữu ích:**
Việc `stash -> checkout -> review -> checkout -> stash pop` dễ làm mất context, gây conflict hoặc khiến developer vô tình chạy build trên state chưa sạch. Worktree cho phép mỗi branch có working directory và build artifacts riêng trong khi vẫn dùng chung repository history.

**Ví dụ:**
```bash
git worktree add ../Daily-OpenAI-review origin/main

# Hoặc tạo branch hotfix mới
git worktree add -b hotfix/payment-timeout ../payment-hotfix main

# Khi xong
git worktree remove ../payment-hotfix
```

Một terminal/IDE có thể giữ feature hiện tại, terminal/IDE khác mở hotfix hoặc PR review độc lập.

**Lưu ý:**
Cùng một local branch thông thường không thể checkout đồng thời ở hai worktree. Các thư mục build/cache có thể chiếm disk đáng kể nếu solution lớn. Kiểm tra `git worktree list` và cleanup worktree cũ thay vì xóa thư mục thủ công rồi để metadata dangling.

### Tip 5 — Với ASP.NET Core rate limiting, partition theo identity có ý nghĩa thay vì chỉ theo IP

**Mẹo:**
Nếu API đã authenticate user, tenant hoặc API client, cân nhắc partition rate limit theo identity đó thay vì dùng duy nhất client IP. IP thường chỉ là tín hiệu transport, không phải business identity.

**Tại sao hữu ích:**
Hàng nghìn user có thể đi qua cùng NAT/proxy và chia sẻ một IP; rate limit theo IP có thể khiến một user gây throttling cho cả văn phòng. Ngược lại, attacker có nhiều IP có thể vượt quota nếu hệ thống chỉ nhìn network origin.

**Ví dụ:**
```csharp
options.AddPolicy("per-tenant", httpContext =>
{
    var tenantId = httpContext.User.FindFirst("tenant_id")?.Value
                   ?? "anonymous";

    return RateLimitPartition.GetFixedWindowLimiter(
        partitionKey: tenantId,
        factory: _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 500,
            Window = TimeSpan.FromMinutes(1),
            QueueLimit = 0
        });
});
```

Có thể kết hợp quota per-tenant với guardrail per-IP cho anonymous endpoint tùy threat model.

**Lưu ý:**
Rate limit ở một process không tự động tạo quota toàn cluster nếu limiter dùng state local. Với nhiều replica và quota cần chính xác toàn hệ thống, cần thiết kế distributed enforcement hoặc đặt policy ở API gateway phù hợp. Trả `429` cũng nên kèm retry semantics rõ để client không retry storm.

## 🧠 Software Design

### Design 1 — Expand-and-Contract giúp database migration tương thích khi deploy không diễn ra tức thời

**Khái niệm:**
Expand-and-Contract là chiến lược thay schema theo nhiều bước tương thích: trước tiên thêm cấu trúc mới mà code cũ vẫn chạy được, sau đó chuyển application sang cấu trúc mới, cuối cùng mới xóa cấu trúc cũ khi chắc chắn không còn consumer phụ thuộc.

**Vấn đề nó giải quyết:**
Trong rolling deployment, version cũ và version mới có thể cùng chạy vài phút hoặc lâu hơn. Nếu migration rename/drop column ngay trước khi code mới deploy hoàn tất, instance cũ có thể bắt đầu lỗi giữa rollout; rollback code cũng trở nên nguy hiểm vì schema cũ đã biến mất.

**Ví dụ thực tế:**
```text
Mục tiêu: đổi Customer.FullName -> FirstName + LastName

Expand:
1. thêm FirstName, LastName nullable
2. deploy code có thể đọc cả schema cũ và mới
3. bắt đầu dual-write nếu cần
4. backfill dữ liệu lịch sử

Migrate:
5. chuyển read path hoàn toàn sang field mới
6. theo dõi telemetry để xác nhận field cũ không còn được dùng

Contract:
7. dừng dual-write
8. xóa FullName ở release/migration sau
```

**Trade-off:**
Chiến lược này làm migration kéo dài qua nhiều release và tạm thời tạo duplicated data/code path. Đổi lại, nó giảm coupling giữa schema rollout và application rollout, giúp rollback an toàn hơn và giảm downtime.

**Middle → Senior insight:**
Middle developer cần tránh migration destructive trong cùng release mà code cũ vẫn có thể chạy. Senior / Technical developer phải thiết kế compatibility window, backfill, dual-write semantics, observability và rollback path như một phần của release architecture chứ không chỉ như một file migration.

### Design 2 — Ports and Adapters giữ business logic độc lập với transport và vendor integration

**Khái niệm:**
Ports and Adapters (Hexagonal Architecture) đặt business/application core ở trung tâm. Core định nghĩa các port mà nó cần; HTTP endpoint, database, message broker hoặc third-party SDK là adapter ở rìa triển khai các port đó.

**Vấn đề nó giải quyết:**
Nếu use case `PlaceOrder` trực tiếp gọi `HttpClient`, EF Core, Azure Service Bus SDK và đọc `HttpContext`, business flow bị trộn với transport/infrastructure detail. Test khó cô lập và mỗi thay đổi vendor có thể lan vào core logic.

**Ví dụ thực tế:**
```text
HTTP Endpoint ──> PlaceOrder use case ──> IPaymentGateway
                                   ├──> IOrderStore
                                   └──> IOrderEventPublisher

Adapters:
IPaymentGateway      -> StripePaymentAdapter
IOrderStore          -> EfCoreOrderStore
IOrderEventPublisher -> ServiceBusPublisher
```

Core phụ thuộc vào capability cần thiết, không phụ thuộc trực tiếp vào SDK cụ thể.

**Trade-off:**
Boundary rõ giúp testability và thay integration dễ hơn, nhưng abstraction quá mức tạo interface một-method vô nghĩa và mapping boilerplate. Không cần che mọi framework API; chỉ tạo port tại nơi có business boundary, volatility hoặc testing value thực sự.

**Middle → Senior insight:**
Middle developer cần học cách giữ use case không bị transport/framework detail điều khiển. Senior / Solution-oriented engineer phải chọn boundary dựa trên ownership và volatility, đồng thời tránh biến Hexagonal Architecture thành nghi lễ “interface cho mọi class”.

### Design 3 — Token Bucket cho phép burst có kiểm soát tốt hơn quota cứng theo cửa sổ thời gian

**Khái niệm:**
Token Bucket mô hình hóa capacity bằng một bucket chứa token. Token được bổ sung theo tốc độ cố định; mỗi request tiêu một hoặc nhiều token. Hệ thống cho phép burst khi bucket còn token nhưng vẫn giới hạn average rate dài hạn.

**Vấn đề nó giải quyết:**
Fixed-window limiter có thể tạo edge effect: client gửi toàn bộ quota ở cuối phút rồi ngay lập tức gửi quota mới ở đầu phút tiếp theo. Backend nhận burst gần gấp đôi dù về mặt từng cửa sổ client không vi phạm giới hạn.

**Ví dụ thực tế:**
```text
Bucket capacity: 100 tokens
Refill: 20 tokens/second
Cost: 1 token/request

Client im lặng 5 giây
-> bucket có thể đầy tới 100
-> được burst tối đa 100 request
-> sau đó throughput bền vững ~20 request/s
```

Với API tốn tài nguyên khác nhau, operation đắt có thể tiêu nhiều token hơn operation nhẹ nếu limiter hỗ trợ cost semantics phù hợp.

**Trade-off:**
Token Bucket cho burst tự nhiên nhưng state và refill logic phức tạp hơn fixed window, đặc biệt khi enforcement phân tán. Bucket quá lớn cho phép burst làm downstream quá tải; quá nhỏ triệt tiêu lợi ích của burst tolerance.

**Middle → Senior insight:**
Middle developer cần hiểu rate limit không chỉ là “N request mỗi phút”. Senior / Technical developer phải chọn algorithm, partition key, burst budget, distributed consistency và response/backoff semantics dựa trên capacity thật và fairness requirement của hệ thống.
