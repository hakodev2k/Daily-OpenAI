# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Đọc allocation trước khi tối ưu GC trong .NET

**Mẹo:**
Khi memory tăng hoặc GC chạy dày, đo allocation rate và object lifetime trước khi đổi GC mode hay tăng memory. Dùng `dotnet-counters`, `dotnet-gcdump` hoặc profiler để xem Gen 0/1/2, LOH và allocation hotspots.

**Tại sao hữu ích:**
GC thường chỉ phản ánh áp lực allocation. Nếu application tạo nhiều object ngắn hạn do serialization, mapping hoặc buffering, tuning GC không xử lý nguyên nhân gốc. Quan sát allocation giúp đi từ symptom → evidence → hypothesis thay vì đoán.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Nếu `Allocation Rate` tăng mạnh sau deployment trong khi request rate gần như không đổi, hãy so sánh code path mới trước khi nghĩ tới scale-up.

**Lưu ý:**
Không dùng `GC.Collect()` như biện pháp chữa memory pressure thông thường. Nó có thể làm latency xấu hơn và che giấu lifetime problem thật sự.

### Tip 2 — Bật response compression có chọn lọc trong ASP.NET Core

**Mẹo:**
Với JSON, HTML, CSS hoặc JavaScript đủ lớn, dùng `ResponseCompression` để giảm network payload; nhưng chỉ đánh giá bằng dữ liệu thực tế, đặc biệt với API latency p95/p99 và CPU.

**Tại sao hữu ích:**
Compression đổi CPU lấy bandwidth. Trên payload lớn qua mạng chậm, lợi ích rõ rệt; với payload rất nhỏ hoặc CPU-bound service, chi phí compression có thể lớn hơn phần tiết kiệm.

**Ví dụ:**
```csharp
builder.Services.AddResponseCompression();
app.UseResponseCompression();
```

So sánh payload size, server CPU và latency trước/sau bằng load test thay vì chỉ nhìn kích thước response.

**Lưu ý:**
Không mặc định compress mọi content type. Dữ liệu đã nén như JPEG, PNG hoặc ZIP thường không có lợi đáng kể.

### Tip 3 — Chọn partition key theo access pattern trong Cosmos DB

**Mẹo:**
Thiết kế partition key dựa trên truy vấn và phân bố traffic, không chỉ dựa trên field “có vẻ unique”. Mục tiêu là tránh cross-partition query và hot partition.

**Tại sao hữu ích:**
Partition key quyết định data distribution, scalability và request cost. Một key có cardinality thấp hoặc traffic lệch có thể làm một logical partition quá nóng dù tổng throughput của account còn dư.

**Ví dụ:**
Với multi-tenant SaaS, `TenantId` có thể phù hợp nếu tenant tương đối cân bằng và phần lớn query nằm trong tenant. Nếu một tenant rất lớn, cần cân nhắc hierarchical partitioning hoặc key strategy khác.

**Lưu ý:**
Partition key khó thay đổi sau khi hệ thống đã có dữ liệu lớn. Hãy mô phỏng query pattern, growth và worst-case tenant trước khi chốt schema.

### Tip 4 — Phân biệt readiness và liveness trong Kubernetes

**Mẹo:**
Dùng `readinessProbe` để quyết định Pod có nên nhận traffic; dùng `livenessProbe` để phát hiện process bị kẹt và cần restart. Hai probe không nên kiểm tra cùng một thứ một cách máy móc.

**Tại sao hữu ích:**
Nếu database tạm thời chậm mà liveness phụ thuộc database, Kubernetes có thể restart hàng loạt Pod và khuếch đại incident. Readiness có thể tạm rút Pod khỏi load balancing mà không phá process đang khỏe.

**Ví dụ:**
API vẫn chạy nhưng dependency startup chưa hoàn tất: readiness trả fail, liveness vẫn pass. Khi dependency sẵn sàng, Pod mới nhận traffic.

**Lưu ý:**
Probe quá nhạy có thể tạo restart loop. Cần thiết kế timeout, failure threshold và startup behavior dựa trên đặc tính thực tế của service.

### Tip 5 — Kiểm chứng AI-generated code bằng source và tests, không bằng vẻ hợp lý

**Mẹo:**
Khi AI đề xuất API, package hoặc cấu hình framework, xác minh version, signature và behavior bằng source repository, official docs hoặc test chạy được trong project.

**Tại sao hữu ích:**
AI-generated code có thể compile không được, dùng API đã deprecated hoặc tạo abstraction thừa dù lời giải thích nghe hợp lý. Verification biến AI thành accelerator thay vì nguồn technical debt.

**Ví dụ:**
Nếu AI đề xuất một extension method cho .NET 10, kiểm tra package/version thực tế rồi viết test nhỏ xác nhận behavior trên target framework của solution.

**Lưu ý:**
Không chỉ kiểm tra compilation. Code vẫn có thể đúng cú pháp nhưng sai concurrency, security, SQL performance hoặc failure handling.

## 🧠 Software Design

### Design 1 — REST vs messaging cho integration boundary

**Khái niệm:**
REST phù hợp khi caller cần response đồng bộ và coupling thời gian là chấp nhận được; messaging phù hợp khi cần decouple producer/consumer, chịu tải bất đồng bộ và xử lý partial failure tốt hơn.

**Vấn đề nó giải quyết:**
Một workflow synchronous dài dễ thất bại dây chuyền khi downstream chậm. Ngược lại, dùng messaging cho mọi thứ có thể làm business flow khó theo dõi và tạo eventual consistency không cần thiết.

**Ví dụ thực tế:**
Checkout cần kiểm tra inventory tức thời có thể dùng REST. Sau khi order được xác nhận, gửi email và analytics có thể publish event bất đồng bộ.

**Trade-off:**
REST đơn giản hơn về mental model và debugging nhưng tăng temporal coupling. Messaging tăng resilience và throughput nhưng thêm broker, retry, duplicate handling, observability và eventual consistency.

**Middle → Senior insight:**
Middle developer cần implement timeout, retry và message handling đúng cách. Senior / Technical developer phải chọn interaction style theo business latency, consistency requirement, failure mode và operational cost thay vì áp dụng một pattern cho toàn hệ thống.

### Design 2 — Optimistic concurrency cho dữ liệu có xung đột thấp

**Khái niệm:**
Optimistic concurrency cho phép nhiều request đọc cùng dữ liệu nhưng phát hiện conflict tại thời điểm update bằng version/token thay vì khóa record dài hạn.

**Vấn đề nó giải quyết:**
Trong web application, giữ pessimistic lock qua toàn bộ user interaction thường không thực tế. Version check giúp ngăn lost update mà không giữ database lock quá lâu.

**Ví dụ thực tế:**
Hai admin cùng sửa Product. Request sau gửi `RowVersion`; nếu record đã thay đổi, update ảnh hưởng 0 row và API trả conflict để user reload/merge.

**Trade-off:**
Giảm lock contention và phù hợp hệ thống read-heavy, nhưng application phải xử lý conflict UX, retry hoặc merge. Với contention rất cao, retry liên tục có thể tốn kém.

**Middle → Senior insight:**
Middle developer cần cấu hình concurrency token và xử lý conflict đúng. Senior / Technical developer cần đánh giá conflict frequency, business semantics và liệu optimistic, pessimistic hay serialized workflow mới phù hợp.

### Design 3 — Observability là một phần của architecture contract

**Khái niệm:**
Observability nên được thiết kế như capability xuyên suốt service boundary: logs có cấu trúc, metrics có mục tiêu và traces mang correlation context đủ để tái dựng request flow.

**Vấn đề nó giải quyết:**
Một hệ thống có chức năng đúng nhưng không thể chẩn đoán khi production lỗi sẽ có MTTR cao. Logging rời rạc sau khi incident xảy ra thường không đủ để biết dependency nào, tenant nào hoặc deployment nào gây vấn đề.

**Ví dụ thực tế:**
Mỗi checkout trace mang `TraceId`, tenant, order operation và dependency spans. Dashboard theo dõi error rate, p95 latency và Service Bus backlog giúp khoanh vùng regression sau release.

**Trade-off:**
Observability cải thiện diagnostics và reliability nhưng tăng telemetry volume, storage cost, instrumentation effort và rủi ro lộ dữ liệu nếu tagging thiếu kiểm soát.

**Middle → Senior insight:**
Middle developer cần tạo structured logs và propagate context đúng. Senior / Technical developer cần quyết định telemetry contract, sampling, cardinality, retention, alert thresholds và dữ liệu nào tuyệt đối không được ghi log.
