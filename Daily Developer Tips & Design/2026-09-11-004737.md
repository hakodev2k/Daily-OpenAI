# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng exception filter để chỉ bắt exception mà bạn thực sự xử lý được

**Mẹo:**
Trong C#, dùng `catch (...) when (...)` khi cùng một exception type có nhiều nguyên nhân nhưng chỉ một số trường hợp nên được xử lý cục bộ.

**Tại sao hữu ích:**
Exception filter được đánh giá trước khi stack unwinding hoàn tất, giúp giữ logic bắt lỗi sát với điều kiện thực tế và tránh `catch` rộng rồi tự rethrow sau đó.

**Ví dụ:**
```csharp
try
{
    await client.SendAsync(request, ct);
}
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    metrics.IncrementRateLimited();
    throw;
}
```

Trong production, filter có thể giúp phân biệt lỗi transient, rate limit hoặc lỗi contract mà không biến toàn bộ `HttpRequestException` thành cùng một recovery path.

**Lưu ý:**
Không đặt side effect phức tạp trong biểu thức `when`. Filter nên đơn giản, deterministic và không che mất exception gốc.

### Tip 2 — Rate limiting nên partition theo actor phù hợp, không chỉ theo IP

**Mẹo:**
Với ASP.NET Core API đã authenticated, cân nhắc partition rate limit theo user hoặc tenant thay vì chỉ theo IP.

**Tại sao hữu ích:**
Nhiều user có thể đi chung NAT/proxy nên IP-based limit có thể throttle nhầm cả nhóm. Ngược lại, một user độc hại có thể phân tán request qua nhiều IP. Partition key nên phản ánh resource ownership hoặc abuse boundary thực tế.

**Ví dụ:**
```csharp
options.AddPolicy("per-user", context =>
    RateLimitPartition.GetFixedWindowLimiter(
        partitionKey: context.User.Identity?.Name ?? context.Connection.RemoteIpAddress?.ToString() ?? "anonymous",
        factory: _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1)
        }));
```

**Lưu ý:**
Rate limiting không thay thế authorization hoặc quota nghiệp vụ. Với hệ thống multi-tenant, cần cân nhắc cả limit theo user và tổng budget của tenant.

### Tip 3 — Với Cosmos DB, phát hiện hot partition bằng distribution chứ không chỉ tổng RU

**Mẹo:**
Khi latency hoặc throttling (`429`) tăng dù tổng RU provisioned còn vẻ đủ, kiểm tra traffic theo logical/physical partition thay vì chỉ nhìn aggregate RU.

**Tại sao hữu ích:**
Cosmos DB phân phối throughput theo partition. Một partition key có phân bố lệch có thể trở thành hot partition và bị throttle trong khi phần còn lại của container gần như nhàn rỗi.

**Ví dụ:**
```text
Partition key hiện tại: /tenantId
Tenant A: 70% traffic
Tenant B..Z: 30% traffic
```

Nếu một tenant chiếm phần lớn request, cần xem lại partition strategy, workload isolation hoặc data model thay vì chỉ tăng RU toàn container.

**Lưu ý:**
Đổi partition key thường không phải thao tác nhỏ; có thể cần container mới và migration dữ liệu. Vì vậy partition key phải được chọn từ access pattern và growth model ngay từ đầu.

### Tip 4 — Dùng `git bisect` để tìm commit gây regression thay vì kiểm tra thủ công từng commit

**Mẹo:**
Khi biết một commit cũ hoạt động tốt và HEAD bị lỗi, dùng `git bisect` để binary search lịch sử commit.

**Tại sao hữu ích:**
Với 128 commit nghi ngờ, binary search lý thuyết chỉ cần khoảng 7 lần kiểm tra thay vì test tuần tự toàn bộ lịch sử.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
# chạy test ở commit Git chọn
git bisect good   # hoặc bad
git bisect reset
```

Có thể kết hợp `git bisect run` với test script tự động để tìm regression nhanh hơn.

**Lưu ý:**
Bisect hiệu quả nhất khi có test/reproduction deterministic. Nếu bug phụ thuộc dữ liệu production, timing hoặc external service, kết quả có thể nhiễu.

### Tip 5 — Dùng Network panel để phân biệt frontend chậm với backend chậm

**Mẹo:**
Khi UI phản hồi chậm, mở browser DevTools Network panel và phân tách DNS/connect, TTFB, download và thời gian xử lý frontend trước khi tối ưu code React/Vue.

**Tại sao hữu ích:**
Một trang “chậm” có thể do API TTFB 2 giây, payload lớn, request waterfall hoặc JavaScript render. Nếu không tách các pha, team dễ tối ưu sai tầng.

**Ví dụ:**
```text
GET /api/products
TTFB: 1.8s
Download: 80ms
Render sau response: 40ms
```

Trong trường hợp này, bottleneck chính nằm ở backend/dependency chứ không phải component rendering.

**Lưu ý:**
Một lần đo trên máy local không đại diện production. Hãy kết hợp browser trace với backend telemetry và latency percentile thực tế.

## 🧠 Software Design

### Design 1 — Saga dùng compensation, không giả vờ có distributed transaction

**Khái niệm:**
Saga chia một business workflow thành nhiều local transaction. Nếu bước sau thất bại, hệ thống chạy compensating action cho các bước đã hoàn thành thay vì rollback atomically toàn bộ hệ thống.

**Vấn đề nó giải quyết:**
Trong distributed system, một order workflow có thể chạm Order DB, Payment service và Inventory service. Giữ transaction lock xuyên nhiều service thường không thực tế hoặc không được hỗ trợ.

**Ví dụ thực tế:**
```text
1. Create Order
2. Reserve Inventory
3. Charge Payment

Nếu bước 3 fail:
- release inventory
- mark order payment_failed
```

Compensation là business action mới, không phải luôn là phép đảo hoàn hảo của thao tác trước.

**Trade-off:**
Saga tăng khả năng xử lý workflow phân tán mà không cần distributed transaction, nhưng thêm intermediate state, retry, duplicate handling, observability và logic compensation. Người dùng có thể thấy trạng thái eventual consistency trong một khoảng thời gian.

**Middle → Senior insight:**
Middle developer cần hiểu mỗi step phải idempotent và failure có thể xảy ra ở mọi ranh giới. Senior / Technical developer phải quyết định orchestration vs choreography, compensation semantics, timeout, recovery và cách xử lý khi chính compensation cũng thất bại.

### Design 2 — Direct `DbContext` vs Repository abstraction dựa trên abstraction value

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like behavior. Repository riêng chỉ tạo giá trị khi nó che một boundary có ý nghĩa, không phải vì architecture template yêu cầu.

**Vấn đề nó giải quyết:**
Một số codebase bọc mọi `DbSet` bằng interface CRUD generic, dẫn đến tầng abstraction chỉ forward method và làm query khó tối ưu. Ngược lại, có domain cần repository để bảo vệ aggregate boundary hoặc tách persistence concern thật sự.

**Ví dụ thực tế:**
```text
Không giá trị:
IOrderRepository.GetAllAsync()
IOrderRepository.AddAsync()
-> chỉ gọi DbSet tương ứng

Có thể có giá trị:
LoadOrderAggregateForCheckout(orderId)
-> enforce query shape + aggregate boundary
```

**Trade-off:**
Direct `DbContext` giảm ceremony và giữ full capability của EF Core, nhưng application layer biết rõ persistence technology hơn. Repository có thể tạo domain-focused boundary nhưng cũng dễ thành abstraction rò rỉ và gây N+1 interface method.

**Middle → Senior insight:**
Middle developer cần tránh generic repository chỉ để “đúng pattern”. Senior / Technical developer phải đánh giá test strategy, query complexity, aggregate boundary, migration risk và team conventions trước khi quyết định abstraction level.

### Design 3 — Blue/Green deployment chỉ an toàn khi shared dependencies cũng backward-compatible

**Khái niệm:**
Blue/Green deployment chạy song song version cũ và mới rồi chuyển traffic nhanh giữa hai môi trường. Khả năng rollback phụ thuộc không chỉ application binary mà còn database schema, message contract và external side effect.

**Vấn đề nó giải quyết:**
Team có thể deploy version mới vào Green, health-check đầy đủ rồi switch traffic từ Blue sang Green. Nhưng nếu Green đã chạy migration breaking hoặc phát message mới mà Blue không hiểu, switch traffic ngược lại không còn là rollback thực sự.

**Ví dụ thực tế:**
```text
Blue: app v12
Green: app v13
Shared DB: schema phải đọc/ghi được cho cả v12 và v13 trong migration window
```

Thay đổi schema nên theo expand-and-contract hoặc compatibility strategy tương đương trước khi traffic switch.

**Trade-off:**
Blue/Green giảm downtime và cho rollback traffic nhanh, nhưng cần gấp đôi environment capacity trong thời gian deploy, đồng thời tăng yêu cầu synchronization cho database, cache, queue và background jobs.

**Middle → Senior insight:**
Middle developer cần hiểu health check và traffic switch chưa đủ để đảm bảo rollback. Senior / Technical developer phải thiết kế compatibility window, migration order, worker duplication, message versioning và rollback criteria cho toàn hệ thống, không chỉ web app.
