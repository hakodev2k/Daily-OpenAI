# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — `ValueTask` không phải bản nâng cấp mặc định của `Task`

**Mẹo:**
Chỉ cân nhắc `ValueTask<T>` trên hot path khi operation thường xuyên hoàn thành synchronously và profiling cho thấy allocation của `Task<T>` thực sự đáng kể. Với application code thông thường, ưu tiên `Task<T>` vì semantics đơn giản hơn.

**Tại sao hữu ích:**
`ValueTask<T>` có thể tránh allocation trong một số đường chạy, nhưng nó là struct lớn hơn reference của `Task<T>` và có usage constraints phức tạp hơn. Tối ưu sai chỗ có thể làm API khó dùng mà không cải thiện latency hay throughput đo được.

**Ví dụ:**
```csharp
public ValueTask<User?> GetCachedAsync(int id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

Cache hit rất cao có thể là candidate; một repository luôn gọi database thì thường không được lợi tương tự.

**Lưu ý:**
Không await cùng một `ValueTask` nhiều lần hoặc tùy tiện gọi `AsTask()` rồi kỳ vọng vẫn giữ lợi ích allocation. Đo bằng profiler/benchmark trước khi đưa `ValueTask` vào public abstraction.

### Tip 2 — EF Core projection giúp giảm cả dữ liệu truyền lẫn tracking overhead

**Mẹo:**
Với read endpoint chỉ cần vài field, project trực tiếp sang DTO bằng `Select` thay vì load toàn bộ entity graph rồi map trong memory.

**Tại sao hữu ích:**
Projection cho phép EF Core sinh SQL chỉ lấy các column cần thiết, tránh materialize entity dư thừa và thường không cần change tracking. Điều này đặc biệt đáng kể với list/search endpoint có nhiều row hoặc entity chứa column lớn.

**Ví dụ:**
```csharp
var items = await db.Products
    .Where(x => x.IsActive)
    .Select(x => new ProductListItem(
        x.Id,
        x.Name,
        x.Price))
    .ToListAsync(ct);
```

Thay vì `Include` nhiều navigation rồi map sang ba field, để query shape phản ánh đúng response contract.

**Lưu ý:**
Đừng tạo projection cực kỳ phức tạp mà không kiểm tra SQL được translate. Với logic không translate được hoặc query sinh SQL bất thường, xem `ToQueryString()`/execution plan và tách logic hợp lý.

### Tip 3 — Cosmos DB: partition key phải đi theo access pattern quan trọng

**Mẹo:**
Khi thiết kế container, chọn partition key dựa trên cách dữ liệu được đọc/ghi và phân bố tải, không chỉ vì field đó luôn có giá trị.

**Tại sao hữu ích:**
Query có partition key có thể được route tới phạm vi nhỏ hơn; cross-partition query phải fan out và thường tốn RU/latency hơn. Ngược lại, key có cardinality thấp hoặc workload lệch mạnh có thể tạo hot partition và giới hạn khả năng scale thực tế.

**Ví dụ:**
```text
Container: Orders
Common access: tất cả order của một tenant
Candidate key: /tenantId

Tenant A: 45% toàn bộ traffic
=> cần đánh giá nguy cơ hot partition trước khi chốt model.
```

Có thể cần hierarchical/compound modeling hoặc thay đổi aggregate/access pattern tùy workload thực tế.

**Lưu ý:**
Partition key là quyết định khó thay đổi hơn index thông thường. Đừng chọn chỉ dựa trên query hiện tại; cân nhắc data growth, write distribution, transactional boundary và tenant skew.

### Tip 4 — Kubernetes: phân biệt `CrashLoopBackOff` với nguyên nhân process thực sự chết

**Mẹo:**
Khi Pod ở `CrashLoopBackOff`, xem container exit reason, previous logs và events trước khi sửa probe hoặc tăng restart delay. `CrashLoopBackOff` mô tả Kubernetes đang back off việc restart, không phải root cause.

**Tại sao hữu ích:**
Process có thể chết vì unhandled exception, config thiếu, `OOMKilled`, migration lỗi hoặc dependency unavailable. Nếu chỉ thấy trạng thái `CrashLoopBackOff` rồi chỉnh liveness probe, bạn có thể che triệu chứng thay vì xử lý lỗi ứng dụng.

**Ví dụ:**
```bash
kubectl describe pod api-7f8c9
kubectl logs api-7f8c9 --previous
```

Nếu `Last State` cho thấy `Reason: OOMKilled`, investigation nên chuyển sang memory usage và container limits, không phải HTTP probe.

**Lưu ý:**
Pod có nhiều container thì phải xem đúng container. Events cũng có retention hữu hạn; production observability nên giữ application/container evidence ngoài việc phụ thuộc hoàn toàn vào `kubectl` sau sự cố.

### Tip 5 — AI-generated migration cần kiểm tra data semantics, không chỉ compile

**Mẹo:**
Khi dùng AI coding agent để tạo EF Core/database migration, review cả SQL/data transformation và rollback behavior thay vì chỉ xác nhận solution build thành công.

**Tại sao hữu ích:**
Migration có thể compile nhưng vẫn lock bảng lớn, đặt default sai, truncate dữ liệu, thêm `NOT NULL` không tương thích dữ liệu cũ hoặc tạo destructive rollback. AI thường suy luận schema intent từ code hiện tại nhưng không biết distribution và production constraints nếu không được cung cấp evidence.

**Ví dụ:**
```text
Agent đề xuất:
ALTER TABLE Customers ADD Region nvarchar(20) NOT NULL DEFAULT 'Unknown';

Review cần hỏi:
- bảng có bao nhiêu row?
- default này có đúng business semantics?
- deployment có cần expand/backfill/contract?
- migration lock bảng bao lâu?
```

**Lưu ý:**
Không cho agent tự động apply production migration chỉ vì generated diff trông hợp lý. Validate trên dữ liệu đại diện, inspect generated SQL và có rollout/rollback strategy phù hợp.

## 🧠 Software Design

### Design 1 — Database-per-module để enforce ownership trong Modular Monolith

**Khái niệm:**
Trong Modular Monolith, module có thể sở hữu schema/table riêng và module khác truy cập dữ liệu qua explicit contract thay vì join trực tiếp vào internal tables. Mục tiêu là bảo vệ ownership boundary dù deployment vẫn là một application.

**Vấn đề nó giải quyết:**
Nếu `Orders` đọc trực tiếp bảng của `Identity`, mọi thay đổi schema Identity có thể phá Orders. Code nhìn như modular nhưng database trở thành shared integration surface, khiến việc evolve hoặc extract module sau này rất khó.

**Ví dụ thực tế:**
```text
Identity owns: identity.Users
Orders owns:   orders.Orders

Orders cần tên người mua:
- gọi module query contract, hoặc
- giữ read model/snapshot cần thiết

Không: SELECT ... JOIN identity.Users từ repository của Orders như dependency mặc định.
```

**Trade-off:**
Ownership rõ giảm coupling và hỗ trợ evolution, nhưng cross-module reporting/query trở nên khó hơn và có thể cần read model hoặc integration mechanism. Enforce boundary quá cứng cho hệ thống nhỏ cũng có thể tạo ceremony không đáng giá.

**Middle → Senior insight:**
Middle developer cần tôn trọng data ownership và explicit module API. Senior / Technical developer phải quyết định boundary nào cần enforce ở database, khi nào direct join có chi phí chấp nhận được, và cân bằng khả năng evolution với query/reporting complexity.

### Design 2 — Optimistic Concurrency phù hợp khi conflict hiếm nhưng correctness quan trọng

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng trạng thái mà không giữ lock dài; khi ghi, hệ thống kiểm tra version/token để phát hiện dữ liệu đã bị thay đổi kể từ lúc đọc.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng sửa một customer profile. Nếu request thứ hai ghi đè mà không biết request thứ nhất đã cập nhật dữ liệu, hệ thống tạo lost update dù cả hai request đều trả success.

**Ví dụ thực tế:**
```text
Read: Customer version = 12
User A update -> version = 13
User B update WHERE version = 12 -> 0 rows affected
=> conflict, không silently overwrite
```

EF Core có thể dùng concurrency token như `rowversion` trên SQL Server và xử lý `DbUpdateConcurrencyException`.

**Trade-off:**
Không giữ pessimistic lock nên scale tốt cho workload conflict thấp, nhưng application phải có conflict UX/retry/merge semantics. Nếu contention rất cao, retry liên tục có thể tốn kém và pessimistic strategy hoặc serialization boundary khác có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần xử lý concurrency exception như một business-relevant outcome thay vì generic 500. Senior / Technical developer phải xác định invariant, conflict frequency và chọn reject, merge, retry hay serialize operation dựa trên semantics thực tế.

### Design 3 — Hexagonal Architecture có giá trị khi boundary thật sự cần thay đổi hoặc test độc lập

**Khái niệm:**
Hexagonal Architecture đặt business/application logic phía trong và giao tiếp với database, messaging, HTTP hay external systems qua ports/adapters. Giá trị chính là làm dependency direction và integration boundary rõ, không phải tạo nhiều project/folder.

**Vấn đề nó giải quyết:**
Business workflow bị trộn trực tiếp với EF Core, Service Bus và third-party SDK khiến unit behavior khó test và thay integration tốn kém. Một explicit port có thể cô lập dependency có volatility hoặc business significance cao.

**Ví dụ thực tế:**
```text
CheckoutService
  -> IPaymentGateway (port)
       -> StripePaymentAdapter
  -> IInventoryGateway (port)
       -> InventoryHttpAdapter
```

Domain không cần biết SDK cụ thể của payment provider.

**Trade-off:**
Ports/adapters tăng testability và giảm coupling tới volatile integrations, nhưng abstraction cho mọi class tạo interface explosion và navigation cost. CRUD application nhỏ có thể đơn giản hơn với layered architecture và direct framework usage.

**Middle → Senior insight:**
Middle developer cần hiểu dependency direction và không leak SDK-specific model vào core logic vô cớ. Senior / Technical developer phải nhận ra boundary nào có đủ volatility, test pressure hoặc business importance để đáng abstraction, và tránh áp dụng Hexagonal Architecture như template bắt buộc cho mọi service.
