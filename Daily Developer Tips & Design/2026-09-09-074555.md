# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test code phụ thuộc thời gian mà không cần `DateTime.UtcNow`

**Mẹo:**
Với code .NET có logic dựa vào thời gian như expiration, retry delay, scheduling hoặc token validity, inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi.

**Tại sao hữu ích:**
Thời gian hệ thống là dependency toàn cục và khó kiểm soát trong test. `TimeProvider` biến clock thành dependency rõ ràng, giúp test deterministic và giảm nhu cầu `Thread.Sleep` hoặc chờ thời gian thật trôi qua.

**Ví dụ:**
```csharp
public sealed class SessionService(TimeProvider timeProvider)
{
    public bool IsExpired(Session session)
        => session.ExpiresAt <= timeProvider.GetUtcNow();
}
```

Trong test có thể dùng fake time provider để dịch clock tới thời điểm mong muốn rồi assert behavior ngay lập tức.

**Lưu ý:**
Đừng tạo một abstraction clock riêng nếu `TimeProvider` đã đáp ứng yêu cầu. Nhưng với domain cần semantics thời gian đặc biệt, vẫn nên giữ business rule tách khỏi infrastructure concern.

### Tip 2 — Với Cosmos DB, projection nhỏ không cứu được partition key sai

**Mẹo:**
Khi Cosmos DB query tốn RU cao, đừng chỉ giảm số field trả về. Kiểm tra đầu tiên xem query có chứa đúng partition key hay đang fan-out qua nhiều partition.

**Tại sao hữu ích:**
Payload nhỏ giúp giảm network và serialization, nhưng RU chủ yếu phụ thuộc vào lượng dữ liệu/index work mà engine phải scan. Một cross-partition query có thể vẫn đắt dù response chỉ trả vài field.

**Ví dụ:**
Query tốt:
```text
partition key = tenantId
WHERE tenantId = 'tenant-42' AND status = 'Open'
```

Query rủi ro:
```text
WHERE status = 'Open'
```

nếu `status` không xác định partition và dữ liệu phân tán trên nhiều tenant.

**Lưu ý:**
Không ép mọi query phải single-partition nếu business cần global search/reporting. Khi đó cần chấp nhận cost, precompute projection khác, dùng analytical store hoặc thay đổi read model phù hợp workload.

### Tip 3 — Dùng Playwright Trace Viewer cho flaky UI test thay vì chỉ chụp screenshot cuối cùng

**Mẹo:**
Khi E2E test thỉnh thoảng fail trên CI, bật Playwright tracing để thu network, DOM snapshots, console và action timeline thay vì chỉ lưu screenshot tại thời điểm lỗi.

**Tại sao hữu ích:**
Screenshot chỉ cho biết trạng thái cuối. Trace giúp biết click xảy ra trước hay sau request, element bị detach, navigation chậm, request trả 500 hay selector match sai element.

**Ví dụ:**
Một failure có thể được phân tích theo chuỗi:
```text
click Submit
-> POST /api/orders = 201
-> redirect starts
-> loading overlay remains
-> test clicks Next too early
-> element intercepted
```

Từ đó fix synchronization dựa trên application state thay vì tăng timeout tùy ý.

**Lưu ý:**
Trace artifact có thể chứa dữ liệu nhạy cảm từ request/response. Cần kiểm soát retention và masking trong CI, đặc biệt với test gần production data.

### Tip 4 — Stream file từ Azure Blob Storage thay vì load toàn bộ vào memory

**Mẹo:**
Khi ASP.NET Core API trả file lớn từ Azure Blob Storage, stream dữ liệu trực tiếp tới response hoặc client thay vì tải toàn bộ blob vào `byte[]` trước.

**Tại sao hữu ích:**
Load file lớn vào memory làm tăng allocation, GC pressure và nguy cơ nhiều concurrent download cùng lúc đẩy process tới memory exhaustion. Streaming giữ memory footprint gần như ổn định theo buffer size.

**Ví dụ:**
```csharp
var response = await blobClient.DownloadStreamingAsync(cancellationToken: ct);
return Results.Stream(
    response.Value.Content,
    contentType: response.Value.Details.ContentType,
    enableRangeProcessing: true);
```

Với file public hoặc client đủ tin cậy, direct client access bằng SAS ngắn hạn còn có thể bỏ backend khỏi data path.

**Lưu ý:**
Backend proxy vẫn cần thiết nếu phải enforce authorization, audit hoặc transform nội dung. SAS phải scope tối thiểu, expiry ngắn và không cấp quyền rộng hơn use case.

### Tip 5 — Structured logging không có nghĩa được phép log toàn bộ object

**Mẹo:**
Khi dùng structured logging, log field cần cho điều tra như `OrderId`, `TenantId`, `CorrelationId`, status và latency; tránh serialize nguyên request/user object chỉ vì logger hỗ trợ object destructuring.

**Tại sao hữu ích:**
Log toàn bộ object dễ làm lộ token, email, address, payment metadata hoặc secret; đồng thời tăng ingestion cost và làm query telemetry nhiễu hơn.

**Ví dụ:**
Nên ưu tiên:
```csharp
logger.LogInformation(
    "Order submission failed. OrderId={OrderId} TenantId={TenantId} Status={Status}",
    orderId,
    tenantId,
    status);
```

thay vì:
```csharp
logger.LogInformation("Order request: {@Request}", request);
```

**Lưu ý:**
Masking ở logging pipeline không thay thế data classification. Developer cần biết field nào được phép log ngay từ design và kiểm tra telemetry sink, retention, access control tương ứng.

## 🧠 Software Design

### Design 1 — Bulkhead Isolation để một dependency lỗi không ăn hết tài nguyên của service

**Khái niệm:**
Bulkhead Isolation giới hạn lượng concurrency hoặc resource mà một workload/dependency được phép sử dụng, giống như chia khoang tàu để một khoang bị ngập không làm chìm toàn bộ hệ thống.

**Vấn đề nó giải quyết:**
Nếu một third-party API chậm, hàng trăm request có thể cùng chờ nó, chiếm thread, connection hoặc memory cho tới khi toàn service suy giảm dù các endpoint khác không phụ thuộc API đó.

**Ví dụ thực tế:**
```text
Pricing dependency
-> max 20 concurrent calls
-> queue tối đa 100
-> vượt giới hạn: fail fast / fallback
```

Trong khi các request không dùng Pricing vẫn còn capacity riêng để hoạt động.

**Trade-off:**
Bulkhead giảm blast radius và bảo vệ throughput tổng thể, nhưng limit quá thấp có thể gây reject dù dependency vẫn xử lý được. Nó cũng thêm queueing, tuning và observability requirement.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency limit khác timeout/retry và phải xử lý rejection rõ ràng. Senior / Technical developer phải phân bổ resource budget theo SLA, dependency capacity, workload priority và failure mode thay vì đặt một global limit tùy ý.

### Design 2 — Normalization vs Denormalization: tối ưu cho invariant trước, query sau

**Khái niệm:**
Normalization giảm duplication và giữ nguồn dữ liệu nhất quán. Denormalization cố ý duplicate hoặc precompute data để tối ưu read path khi join hoặc aggregation trở thành bottleneck thật sự.

**Vấn đề nó giải quyết:**
Một schema normalized tốt có thể tạo query nhiều join cho dashboard lớn. Nhưng denormalize quá sớm khiến cùng một business fact tồn tại ở nhiều nơi và mỗi update phải giữ chúng đồng bộ.

**Ví dụ thực tế:**
Transactional tables giữ:
```text
Order
Customer
OrderLine
Product
```

Dashboard có thể dùng projection riêng:
```text
DailySalesSummary
- Date
- TenantId
- Revenue
- OrderCount
```

thay vì duplicate toàn bộ customer/product data vào mỗi order chỉ để tránh join.

**Trade-off:**
Normalization đơn giản hóa consistency và update semantics nhưng có thể làm read query phức tạp. Denormalization tăng read performance nhưng thêm synchronization, stale-data risk và storage/write cost.

**Middle → Senior insight:**
Middle developer cần thiết kế schema giữ đúng key, constraint và invariant. Senior / Technical developer phải dùng execution plan, workload profile và latency target để quyết định denormalize ở đâu, rồi xác định source-of-truth và recovery strategy rõ ràng.

### Design 3 — Composition over Inheritance cho business rule có nhiều chiều thay đổi

**Khái niệm:**
Composition over Inheritance ưu tiên ghép behavior từ các component nhỏ thay vì tạo hierarchy class sâu khi business rule có nhiều variation độc lập.

**Vấn đề nó giải quyết:**
Một hierarchy như `PremiumInternationalDiscountedCustomerProcessor` nhanh chóng bùng nổ khi customer type, region, pricing policy và channel thay đổi độc lập.

**Ví dụ thực tế:**
Có thể compose:
```text
OrderPricingService
-> IDiscountPolicy
-> ITaxPolicy
-> IShippingPolicy
```

Mỗi policy thay đổi độc lập và được chọn theo context thay vì tạo subclass cho mọi combination.

**Trade-off:**
Composition giảm coupling và tránh inheritance explosion, nhưng có thể tạo nhiều small types và indirection. Inheritance vẫn hợp lý khi thật sự có quan hệ "is-a" ổn định và polymorphism đơn giản.

**Middle → Senior insight:**
Middle developer cần nhận diện khi subclass chỉ tồn tại để thay vài rule. Senior / Technical developer phải xác định variation axis nào ổn định, tránh strategy-pattern hóa mọi `if`, và cân bằng extensibility với độ phức tạp mà team phải vận hành.
