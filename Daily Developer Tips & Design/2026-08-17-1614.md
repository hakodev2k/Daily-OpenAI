# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `dotnet-dump` khi production treo nhưng CPU không cao

**Mẹo:**
Khi process .NET bị treo, latency tăng mạnh hoặc request không hoàn thành nhưng CPU lại thấp, lấy dump rồi phân tích thread stacks thay vì chỉ nhìn log.

**Tại sao hữu ích:**
Có thể phát hiện deadlock, thread-pool starvation, lock contention hoặc rất nhiều request đang chờ cùng một dependency.

**Ví dụ:**
```bash
dotnet-dump collect -p <PID>
dotnet-dump analyze core_*.dmp
```

Trong analyzer:

```text
threads
clrstack
syncblk
```

**Lưu ý:**
Dump có thể rất lớn và chứa dữ liệu nhạy cảm trong memory. Cần kiểm soát quyền truy cập, nơi lưu và thời gian retention.

### Tip 2 — Giữ SQL predicate SARGable để index có cơ hội được dùng

**Mẹo:**
Tránh bọc indexed column trong function khi có thể viết điều kiện theo range tương đương.

**Tại sao hữu ích:**
Predicate SARGable giúp optimizer dùng index seek/range scan thay vì phải tính function cho từng row rồi scan diện rộng.

**Ví dụ:**
Không tối ưu:

```sql
WHERE CAST(CreatedAt AS DATE) = '2026-08-17'
```

Tốt hơn:

```sql
WHERE CreatedAt >= '2026-08-17'
  AND CreatedAt <  '2026-08-18'
```

**Lưu ý:**
Không phải function nào cũng phá index usage trong mọi database. Hãy kiểm tra execution plan thay vì áp dụng máy móc.

### Tip 3 — Chuẩn hóa error response bằng `ProblemDetails`

**Mẹo:**
Với ASP.NET Core API, dùng `ProblemDetails` làm contract lỗi chung thay vì mỗi endpoint trả một JSON lỗi khác nhau.

**Tại sao hữu ích:**
Client dễ parse hơn, log/correlation nhất quán hơn và giảm việc lặp code xử lý error mapping trong controller.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();
```

Response có thể thống nhất các field như:

```json
{
  "type": "https://example.com/problems/order-not-found",
  "title": "Order not found",
  "status": 404,
  "traceId": "00-..."
}
```

**Lưu ý:**
Đừng trả exception message, stack trace hoặc internal SQL details trực tiếp cho client production.

### Tip 4 — Dùng Testcontainers cho integration test cần dependency thật

**Mẹo:**
Khi test behavior phụ thuộc PostgreSQL, SQL Server, Redis hoặc RabbitMQ, chạy dependency thật bằng Testcontainers thay vì mock protocol hoặc giả lập behavior quá nhiều.

**Tại sao hữu ích:**
Bắt được lỗi về SQL dialect, transaction, index, serialization, connection string, migrations và messaging semantics mà mock không thể phản ánh chính xác.

**Ví dụ:**
Một integration test có thể khởi động PostgreSQL container, apply migration, seed dữ liệu rồi chạy repository/API test trên database thật.

```csharp
var container = new PostgreSqlBuilder()
    .WithDatabase("app_test")
    .Build();

await container.StartAsync();
```

**Lưu ý:**
Container test chậm hơn unit test. Nên giới hạn cho boundary quan trọng và tái sử dụng fixture hợp lý thay vì spin up container mới cho từng test nhỏ.

### Tip 5 — Dùng Redis Lua script khi cần thao tác nhiều bước phải atomic

**Mẹo:**
Nếu một operation Redis cần đọc rồi cập nhật nhiều key/value dựa trên state hiện tại, Lua script có thể đảm bảo toàn bộ logic chạy atomically trên Redis server.

**Tại sao hữu ích:**
Tránh race condition kiểu `GET` → xử lý ở application → `SET`, nơi hai instance có thể cùng đọc state cũ rồi ghi đè nhau.

**Ví dụ:**
Pseudo-flow cho rate limit:

```lua
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return current
```

**Lưu ý:**
Script chạy trên Redis event loop; script quá nặng hoặc chạy lâu có thể block các request khác. Giữ logic ngắn, deterministic và có giới hạn rõ ràng.

## 🧠 Software Design

### Design 1 — Retry và Circuit Breaker giải quyết hai failure mode khác nhau

**Khái niệm:**
Retry thử lại một operation khi lỗi được kỳ vọng là transient. Circuit Breaker tạm ngừng gọi dependency khi tỷ lệ lỗi vượt ngưỡng để tránh tiếp tục tạo tải vô ích.

**Vấn đề nó giải quyết:**
Nếu downstream đang outage thật sự, retry từ hàng nghìn request có thể biến lỗi ban đầu thành retry storm, làm dependency càng khó phục hồi.

**Ví dụ thực tế:**
`PaymentGateway` thỉnh thoảng timeout một lần do network jitter: retry 1–2 lần với backoff có thể hợp lý. Nhưng nếu gateway trả 5xx liên tục trong 30 giây, Circuit Breaker nên mở và fail fast thay vì mỗi request đều retry.

**Trade-off:**
Retry tăng khả năng thành công với transient failure nhưng làm tăng latency và load. Circuit Breaker bảo vệ hệ thống nhưng có thể reject request trong lúc dependency vừa hồi phục nếu threshold/reset policy thiết kế kém.

**Middle → Senior insight:**
Middle developer cần phân biệt lỗi nào retry được và luôn dùng backoff/jitter. Senior developer phải thiết kế retry budget xuyên nhiều layer, tránh nested retries và đặt breaker threshold dựa trên SLO, traffic và đặc tính dependency.

### Design 2 — Bounded Context để boundary phản ánh ngôn ngữ nghiệp vụ

**Khái niệm:**
Trong DDD, Bounded Context là ranh giới mà một model và vocabulary có ý nghĩa nhất quán. Cùng một từ có thể mang meaning khác nhau ở context khác.

**Vấn đề nó giải quyết:**
Một domain model khổng lồ dùng chung toàn hệ thống thường tạo coupling mạnh, entity phình to và business rule của nhiều team/module trộn vào nhau.

**Ví dụ thực tế:**
`Employee` trong HR context có `Contract`, `LeaveBalance`, `Manager`. Trong Timesheet context, cùng con người đó có thể chỉ cần `EmployeeId`, `WorkingSchedule`, `CostCenter`. Không nhất thiết hai context phải dùng chung một entity class.

**Trade-off:**
Boundary rõ giúp model dễ hiểu và deploy/change độc lập hơn, nhưng có duplication dữ liệu và cần mapping/integration giữa contexts.

**Middle → Senior insight:**
Middle developer nên hiểu boundary không phải chỉ là folder/project. Senior developer cần nhận ra language, ownership, change cadence và invariant để quyết định context boundary, đồng thời tránh tách context quá nhỏ thành microservices không cần thiết.

### Design 3 — Tách Read Model khỏi Write Model mà chưa cần full CQRS

**Khái niệm:**
Không phải hệ thống nào cũng cần CQRS hoàn chỉnh. Có thể giữ cùng database và transaction model nhưng dùng query model riêng cho read-heavy use case thay vì ép mọi read qua aggregate/repository dùng cho write.

**Vấn đề nó giải quyết:**
Domain model tối ưu cho business invariant thường không phù hợp với dashboard, report hoặc endpoint cần join/projection dữ liệu lớn.

**Ví dụ thực tế:**
Write path của Order đi qua aggregate để đảm bảo trạng thái hợp lệ. Nhưng endpoint `GET /orders/dashboard` có thể dùng một SQL projection/Dapper query trực tiếp để trả `OrderId`, `CustomerName`, `Total`, `Status` mà không load toàn bộ aggregate graph.

**Trade-off:**
Read path đơn giản và nhanh hơn, nhưng tạo hai cách truy cập dữ liệu và cần discipline để read model không vô tình trở thành đường tắt cho business writes.

**Middle → Senior insight:**
Middle developer nên phân biệt query cần projection với command cần invariant. Senior developer phải biết khi nào tách read/write chỉ ở code level là đủ, và khi nào scale/consistency requirements mới thực sự biện minh cho CQRS với storage hoặc pipeline riêng.
