# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng nullable flow attributes để compiler hiểu validation helper của bạn

**Mẹo:**
Khi viết helper kiểm tra null hoặc predicate, dùng các attribute như `NotNullWhen`, `MaybeNullWhen`, `MemberNotNull` để nullable analysis của C# hiểu state sau lời gọi thay vì phải dùng `!` khắp nơi.

**Tại sao hữu ích:**
Giảm false-positive warning, hạn chế null-forgiving operator và giữ safety của nullable reference types ngay cả khi validation nằm trong helper riêng.

**Ví dụ:**
```csharp
using System.Diagnostics.CodeAnalysis;

static bool HasValue(
    [NotNullWhen(true)] string? value)
{
    return !string.IsNullOrWhiteSpace(value);
}

string? name = GetName();

if (HasValue(name))
{
    Console.WriteLine(name.Length);
}
```

Compiler biết `name` không null trong block `if`.

**Lưu ý:**
Attribute chỉ mô tả contract cho compiler; nếu implementation nói sai sự thật thì runtime vẫn có thể lỗi. Chỉ annotate khi contract thực sự được đảm bảo.

### Tip 2 — Dùng EF Core interceptor cho diagnostics/policy thật sự cross-cutting

**Mẹo:**
Khi cần quan sát hoặc áp dụng logic xuyên mọi database command như logging query duration, tagging, audit connection hoặc policy kỹ thuật, cân nhắc `DbCommandInterceptor` thay vì rải code ở repository/service.

**Tại sao hữu ích:**
Giữ concern kỹ thuật ở một chỗ, giảm duplicate instrumentation và cho phép quan sát cả query do application code vô tình tạo ra.

**Ví dụ:**
```csharp
public sealed class SlowQueryInterceptor : DbCommandInterceptor
{
    public override async ValueTask<InterceptionResult<DbDataReader>>
        ReaderExecutingAsync(
            DbCommand command,
            CommandEventData eventData,
            InterceptionResult<DbDataReader> result,
            CancellationToken cancellationToken = default)
    {
        // Ghi metadata hoặc start timing tại đây.
        return await base.ReaderExecutingAsync(
            command,
            eventData,
            result,
            cancellationToken);
    }
}
```

**Lưu ý:**
Interceptor là global behavior nên rất dễ tạo “magic”. Tránh nhét business rule hoặc mutate SQL phức tạp vào interceptor nếu developer khó nhìn ra behavior khi đọc code.

### Tip 3 — Dùng Redis `SCAN` thay vì `KEYS` trên production

**Mẹo:**
Nếu cần duyệt key theo pattern trong Redis production, dùng `SCAN` theo cursor thay vì `KEYS` để tránh block server trong một lần quét toàn bộ keyspace.

**Tại sao hữu ích:**
`KEYS` có thể gây latency spike lớn khi database có nhiều key; `SCAN` chia công việc thành nhiều batch nhỏ và phù hợp hơn cho maintenance/diagnostics.

**Ví dụ:**
```bash
redis-cli --scan --pattern 'session:*'
```

Hoặc trong loop logic, tiếp tục gọi `SCAN <cursor>` đến khi cursor trở về `0`.

**Lưu ý:**
`SCAN` không cung cấp snapshot nhất quán tuyệt đối; key có thể xuất hiện hoặc biến mất trong lúc scan. Không dùng nó để implement business invariant yêu cầu tập kết quả hoàn chỉnh tức thời.

### Tip 4 — Dùng `git merge-tree` để preflight conflict trước khi merge thật

**Mẹo:**
Khi muốn biết hai branch có khả năng conflict hay không nhưng chưa muốn thay đổi working tree/index, dùng `git merge-tree` để mô phỏng merge result.

**Tại sao hữu ích:**
Hữu ích trong script, CI hoặc trước release merge để phát hiện conflict sớm mà không cần checkout branch rồi chạy merge thử thủ công.

**Ví dụ:**
```bash
git merge-tree $(git merge-base main feature/payments) \
  main \
  feature/payments
```

Với Git mới hơn, có thể dùng dạng đơn giản hơn tùy version:

```bash
git merge-tree main feature/payments
```

**Lưu ý:**
Conflict text chỉ cho thấy merge-level conflict. Semantic conflict vẫn có thể tồn tại dù Git merge sạch, ví dụ hai branch thay business rule liên quan ở file khác nhau.

### Tip 5 — Dùng `curl --fail-with-body` để script vẫn giữ error body

**Mẹo:**
Trong shell/CI, dùng `curl --fail-with-body` khi muốn non-2xx làm command fail nhưng vẫn giữ response body để chẩn đoán.

**Tại sao hữu ích:**
`--fail` truyền thống dễ làm mất nội dung lỗi hữu ích; `--fail-with-body` vừa trả exit code lỗi vừa cho bạn thấy JSON/problem details từ server.

**Ví dụ:**
```bash
curl --fail-with-body \
  -H "Authorization: Bearer $TOKEN" \
  https://api.example.com/deployments
```

Trong CI, exit code khác 0 có thể fail step nhưng log vẫn chứa error payload.

**Lưu ý:**
Response body có thể chứa secret, PII hoặc internal detail. Đừng bật log đầy đủ một cách vô điều kiện trong pipeline công khai.

## 🧠 Software Design

### Design 1 — Domain Event và Integration Event không nên là cùng một contract

**Khái niệm:**
Domain Event mô tả điều vừa xảy ra bên trong bounded context và phục vụ model nội bộ; Integration Event là public contract gửi sang context/service khác và cần ổn định hơn theo thời gian.

**Vấn đề nó giải quyết:**
Nếu publish domain object/event nội bộ trực tiếp ra message bus, mọi refactor trong domain có thể trở thành breaking change cho consumer ngoài context.

**Ví dụ thực tế:**
Trong `Payroll`, domain event có thể là:

```text
SalaryRecalculated
```

với nhiều field nội bộ. Integration event gửi sang `Notification` có thể chỉ là:

```text
PayslipReady
- EmployeeId
- PayrollPeriod
- DocumentId
```

Hai event có mục tiêu và lifecycle khác nhau.

**Trade-off:**
Tách hai loại event giảm coupling và giúp public contract ổn định, nhưng thêm mapping, versioning và code. Với monolith rất nhỏ, tách quá sớm có thể là ceremony không cần thiết.

**Middle → Senior insight:**
Middle developer nên hiểu “event” không đồng nghĩa mọi subscriber đều nên thấy cùng payload. Senior developer phải xác định ownership, compatibility, schema evolution và nơi translation giữa domain event với integration event nên xảy ra.

### Design 2 — Active-Passive và Active-Active giải quyết hai bài toán availability khác nhau

**Khái niệm:**
Active-Passive giữ một site/region chính xử lý traffic và site dự phòng chờ failover. Active-Active cho nhiều site cùng xử lý traffic đồng thời.

**Vấn đề nó giải quyết:**
Hệ thống cần sống sót khi region/datacenter lỗi, nhưng mức RTO/RPO, latency toàn cầu và complexity chấp nhận được khác nhau giữa từng sản phẩm.

**Ví dụ thực tế:**
Một internal HR system có thể dùng Active-Passive: primary ở Singapore, standby ở Japan và failover khi disaster. Một global consumer API yêu cầu latency thấp ở nhiều châu lục có thể dùng Active-Active với routing theo region.

**Trade-off:**
Active-Passive đơn giản hơn về write ownership và consistency nhưng failover có downtime/RPO nhất định. Active-Active giảm regional latency và tăng availability nhưng làm conflict resolution, replication, routing và operational testing phức tạp hơn nhiều.

**Middle → Senior insight:**
Middle developer nên biết multi-region không tự động đồng nghĩa Active-Active. Senior developer phải quyết định dựa trên business RTO/RPO, write pattern, data residency, consistency requirement và khả năng vận hành failure thực tế.

### Design 3 — Characterization Test trước khi refactor legacy code

**Khái niệm:**
Characterization Test ghi nhận behavior hiện tại của legacy code trước khi thay đổi implementation, kể cả khi behavior đó chưa đẹp hoặc chưa được document đầy đủ.

**Vấn đề nó giải quyết:**
Refactor code cũ thiếu test rất dễ vô tình sửa luôn behavior mà production hoặc downstream đang phụ thuộc, đặc biệt khi business rule nằm rải rác và không ai còn nhớ toàn bộ edge case.

**Ví dụ thực tế:**
Trước khi tách một class 2.000 dòng xử lý offboarding, team viết test cho các input/output hiện đang xảy ra: active → inactive, forwarding target thiếu, expired config, duplicate retry, v.v. Sau đó mới tách module từng bước.

**Trade-off:**
Characterization test tạo safety net nhanh nhưng có thể “đóng băng” cả bug cũ. Test phải phân biệt behavior cần giữ với behavior được phép sửa có chủ đích.

**Middle → Senior insight:**
Middle developer nên ưu tiên bảo vệ behavior trước khi refactor mạnh. Senior developer phải xác định đâu là compatibility contract thực tế, đâu là bug có thể thay đổi và cách tiến hóa test từ snapshot behavior sang specification rõ ràng hơn.
