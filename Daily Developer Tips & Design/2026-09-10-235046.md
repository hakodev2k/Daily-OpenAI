# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Chỉ dùng `ValueTask` khi có lý do đo được, không thay `Task` theo thói quen

**Mẹo:**
Giữ `Task` làm mặc định cho async API. Chỉ cân nhắc `ValueTask` khi profiling cho thấy allocation của `Task` đáng kể và operation thường hoàn tất synchronously, ví dụ đọc từ cache hoặc buffer nội bộ.

**Tại sao hữu ích:**
`ValueTask` có thể tránh một số allocation nhưng đổi lại caller phải tuân theo nhiều quy tắc hơn. Một `ValueTask` không nên được await nhiều lần, cache tùy tiện hoặc convert qua lại không cần thiết. Dùng sai có thể tăng complexity mà không tạo lợi ích thực tế.

**Ví dụ:**
```csharp
public ValueTask<User?> TryGetCachedUserAsync(
    string id,
    CancellationToken ct)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromStoreAsync(id, ct));
}
```

Nếu phần lớn call vẫn đi xuống database, `Task` thường đơn giản và đủ tốt.

**Lưu ý:**
Đừng đổi public API sang `ValueTask` chỉ để “tối ưu”. Hãy đo allocation rate, throughput và call pattern trước; benefit rất dễ nhỏ hơn maintenance cost.

### Tip 2 — Khi PostgreSQL chọn plan xấu, kiểm tra cardinality estimate trước khi thêm index mới

**Mẹo:**
Nếu query có index nhưng planner vẫn chọn plan chậm, xem `EXPLAIN (ANALYZE, BUFFERS)` và so sánh estimated rows với actual rows trước khi kết luận index thiếu.

**Tại sao hữu ích:**
Planner chọn strategy dựa trên statistics và ước lượng số row. Nếu estimate sai lớn, PostgreSQL có thể chọn nested loop, hash join hoặc scan không phù hợp dù index tồn tại. Root cause có thể là statistics cũ, data skew hoặc correlation giữa cột.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE tenant_id = 42
  AND status = 'Pending';
```

Nếu planner ước lượng 50 row nhưng thực tế trả 500,000 row, hãy điều tra statistics, distribution và query shape trước khi tạo thêm index.

**Lưu ý:**
`ANALYZE` và tăng statistics target có chi phí. Đừng cấu hình cao toàn database nếu chỉ vài cột có skew mạnh hoặc cần estimate chi tiết hơn.

### Tip 3 — Playwright nên chờ trạng thái người dùng nhìn thấy, không chờ thời gian cố định

**Mẹo:**
Thay `waitForTimeout(2000)` bằng assertion hoặc locator chờ đúng UI state mà test thực sự cần.

**Tại sao hữu ích:**
Fixed sleep làm test vừa chậm vừa flaky: máy nhanh thì chờ thừa, CI chậm thì 2 giây vẫn chưa đủ. Playwright có auto-waiting và retry assertion, giúp test đồng bộ với behavior thực tế thay vì đoán timing.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved successfully')).toBeVisible();
```

Nếu flow phụ thuộc request cụ thể, có thể chờ response/network event liên quan thay vì sleep.

**Lưu ý:**
Auto-wait không sửa được test design sai. Nếu selector phụ thuộc DOM implementation dễ thay đổi hoặc môi trường test có shared state, test vẫn có thể flaky.

### Tip 4 — Khi CDN trả nội dung cũ, đọc cache headers trước khi purge toàn bộ

**Mẹo:**
Khi production báo CDN/Akamai phục vụ nội dung stale, kiểm tra `Cache-Control`, `Age`, `ETag`, surrogate/cache key và origin response trước khi purge toàn site.

**Tại sao hữu ích:**
Purge diện rộng có thể tạo origin traffic spike và chỉ che root cause. Nội dung stale thường đến từ TTL sai, cache key thiếu dimension, invalidation không chạy hoặc origin gửi header không đúng.

**Ví dụ:**
```http
Cache-Control: public, max-age=300
Age: 287
ETag: "article-42-v9"
```

Nếu nội dung vừa publish nhưng `Age` vẫn tăng trên object cũ, hãy kiểm tra invalidation path và cache key của resource đó.

**Lưu ý:**
Đừng cache shared response nếu representation phụ thuộc user, authorization hoặc cookie mà cache key không phản ánh đầy đủ các yếu tố này.

### Tip 5 — Khi dùng AI coding agent, khóa phạm vi bằng repository evidence trước khi cho phép sửa nhiều file

**Mẹo:**
Trước khi yêu cầu agent refactor lớn, bắt nó xác định file liên quan, framework/package version, test hiện có và invariant từ source thật trong repository.

**Tại sao hữu ích:**
Agent dễ suy diễn từ convention phổ biến thay vì codebase thực tế. Nếu context sai ngay đầu, patch lớn có thể compile nhưng phá transaction boundary, security rule hoặc architecture convention mà repository đang dùng.

**Ví dụ:**
```text
Trước khi sửa:
1. đọc csproj/package versions
2. xác định entry point và dependency registration
3. tìm test liên quan
4. tìm existing pattern tương tự
5. chỉ sau đó mới đề xuất patch
```

Với PR lớn, yêu cầu thay đổi theo slice nhỏ giúp review assumption dễ hơn.

**Lưu ý:**
Grounding không thay thế code review. Agent vẫn có thể hiểu sai behavior dù đã đọc source; test, static analysis và human judgment vẫn là quality gate bắt buộc.

## 🧠 Software Design

### Design 1 — Idempotency key cho command API có side effect

**Khái niệm:**
Idempotency key cho phép server nhận lại cùng một logical command nhiều lần nhưng chỉ tạo side effect một lần, thường bằng cách lưu key cùng trạng thái/kết quả đã xử lý.

**Vấn đề nó giải quyết:**
Client có thể retry vì timeout dù request đầu tiên thực tế đã thành công. Với payment, order creation hoặc external provisioning, retry mù có thể tạo duplicate charge hoặc duplicate resource.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: 8f4c...

Lần 1:
- xử lý payment
- lưu key + response

Lần 2 cùng key:
- không charge lại
- trả kết quả cũ hoặc trạng thái hiện tại
```

Key nên gắn với caller và request semantics phù hợp, không chỉ là một chuỗi tồn tại trong cache vài giây.

**Trade-off:**
Idempotency giảm duplicate side effect và làm retry an toàn hơn, nhưng thêm storage, retention policy, concurrency control và rule xử lý khi cùng key đi kèm payload khác nhau.

**Middle → Senior insight:**
Middle developer cần hiểu retry không đồng nghĩa an toàn và biết lưu/check key atomically. Senior / Technical developer phải xác định idempotency scope, retention, conflict semantics, persistence guarantee và cách phối hợp với downstream system cũng có thể retry hoặc duplicate.

### Design 2 — Modular Monolith trước khi tách Microservices khi boundary chưa ổn định

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia code, dependency và data ownership theo module rõ ràng. Nó cho phép học domain boundary trước khi trả chi phí vận hành của distributed system.

**Vấn đề nó giải quyết:**
Team thường tách Microservices quá sớm trong khi domain boundary còn thay đổi. Kết quả là chatty network calls, shared database trá hình, transaction phức tạp và ownership mơ hồ.

**Ví dụ thực tế:**
```text
Nexora-like system:
- Tasks module
- Calendar module
- Documents module

Ban đầu:
1 deployable
3 module boundaries rõ
API/internal contract rõ
không truy cập table của nhau trực tiếp
```

Nếu sau này Calendar có scale profile, team ownership hoặc release cadence khác hẳn, boundary đã ổn định sẽ giúp extraction dễ hơn.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, debugging và transaction, nhưng không cho independent scaling/deployment giữa module. Microservices tăng autonomy nhưng thêm network failure, observability, messaging, deployment và data consistency cost.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và module boundary thật sự. Senior / Technical developer phải quyết định thời điểm extraction dựa trên scale, ownership, release coupling và domain stability thay vì coi Microservices là mục tiêu kiến trúc mặc định.

### Design 3 — Observability phải được thiết kế theo câu hỏi vận hành, không theo số lượng log

**Khái niệm:**
Observability tốt bắt đầu từ các câu hỏi cần trả lời khi hệ thống gặp sự cố: request nào chậm, dependency nào gây lỗi, tenant nào bị ảnh hưởng, deployment nào bắt đầu regression. Sau đó mới chọn logs, metrics và traces cần thiết.

**Vấn đề nó giải quyết:**
Một hệ thống có hàng triệu log vẫn có thể khó debug nếu thiếu correlation, latency histogram, dependency telemetry hoặc business dimension phù hợp. “Log nhiều hơn” không đồng nghĩa “quan sát tốt hơn”.

**Ví dụ thực tế:**
```text
Symptom: checkout p95 tăng từ 800ms lên 3.5s

Cần có:
- request latency percentile
- trace theo request
- dependency spans
- DB duration
- external API duration
- deployment/version dimension
```

Từ đó có thể xác định bottleneck nằm ở database, payment provider hay code mới deploy.

**Trade-off:**
Telemetry tốt rút ngắn MTTR và giúp capacity planning, nhưng tăng storage, ingestion cost và rủi ro lộ dữ liệu nếu tag/log không được kiểm soát. Sampling quá mạnh cũng có thể làm mất trace hiếm nhưng quan trọng.

**Middle → Senior insight:**
Middle developer cần tạo structured logs, correlation và metric đúng chỗ. Senior / Technical developer phải thiết kế telemetry schema, cardinality budget, sampling, retention và alerting theo SLO/business impact để observability hữu ích cả khi hệ thống scale lớn.
