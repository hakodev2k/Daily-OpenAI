# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `DbContext` sống lâu hơn một unit of work

**Mẹo:**
Giữ `DbContext` theo scope ngắn, thường là một request hoặc một unit of work rõ ràng. Với background processing, tạo scope/context mới cho từng message hoặc batch thay vì giữ một context singleton hoặc dùng lại vô thời hạn.

**Tại sao hữu ích:**
`DbContext` giữ change tracker và identity map. Context sống quá lâu làm số entity tracked tăng, tăng memory/DetectChanges cost, giữ state cũ và dễ phát sinh concurrency bugs vì `DbContext` không thread-safe.

**Ví dụ:**
Một `BackgroundService` xử lý Service Bus messages. Thay vì inject một `DbContext` và dùng mãi, mỗi message tạo DI scope, resolve context scoped, xử lý transaction rồi dispose scope. Message tiếp theo bắt đầu với tracking state sạch.

**Lưu ý:**
Không tạo context mới tùy tiện giữa các bước phải nằm trong cùng transaction. Lifetime phải theo transaction boundary; mục tiêu là context ngắn và có chủ đích, không phải “càng ngắn càng tốt”.

### Tip 2 — Elasticsearch mapping phải được thiết kế trước khi dữ liệu lớn lên

**Mẹo:**
Xác định field nào cần full-text search, exact filtering, sorting và aggregation rồi thiết kế `text`/`keyword`, analyzer và mapping tương ứng. Đừng dựa hoàn toàn vào dynamic mapping cho production index quan trọng.

**Tại sao hữu ích:**
Elasticsearch xây inverted index theo mapping lúc ingest. Mapping sai có thể khiến exact filter hoạt động không như mong muốn, aggregation không dùng được hoặc tokenization phá search semantics. Sửa mapping thường yêu cầu index mới và reindex dữ liệu.

**Ví dụ:**
`ProductName` cần full-text search nên dùng `text`, đồng thời có subfield `keyword` cho exact sort/filter. `Sku` chỉ cần exact lookup nên dùng `keyword`; nếu để dynamic mapping quyết định mọi thứ, contract search có thể thay đổi khó kiểm soát khi schema phát triển.

**Lưu ý:**
Không index mọi field theo mọi kiểu “để phòng khi cần”; index size và ingest cost sẽ tăng. Mapping phải xuất phát từ query patterns thực tế và có version/reindex strategy.

### Tip 3 — Health check không nên biến thành dependency cascade

**Mẹo:**
Tách liveness khỏi readiness. Liveness chỉ trả lời process có còn sống/khả năng tự phục hồi hay không; readiness xác định instance có nên nhận traffic và có thể kiểm tra những dependency thực sự bắt buộc để phục vụ request.

**Tại sao hữu ích:**
Nếu liveness probe gọi SQL, Redis và nhiều external APIs, một dependency outage có thể khiến orchestrator restart toàn bộ healthy instances, tạo restart storm và làm incident nặng hơn. Readiness cho phép rút instance khỏi traffic mà không nhất thiết giết process.

**Ví dụ:**
Kubernetes liveness endpoint chỉ kiểm tra application loop cơ bản. Readiness kiểm tra configuration initialization và dependency thiết yếu với timeout rất ngắn. Khi database tạm unavailable, pod ngừng nhận traffic nhưng không bị restart liên tục chỉ vì DB đang lỗi.

**Lưu ý:**
Readiness quá sâu cũng có thể tạo tải lên dependency hoặc làm toàn fleet đồng thời unavailable. Không gọi hàng chục downstream services trong mỗi probe; chọn checks theo failure semantics thực tế.

### Tip 4 — Với file upload, validate content chứ đừng tin extension hay `Content-Type`

**Mẹo:**
Giới hạn kích thước, whitelist loại file, kiểm tra signature/magic bytes khi phù hợp, tạo tên lưu trữ phía server và lưu file ngoài web root hoặc trong Blob Storage với quyền tối thiểu.

**Tại sao hữu ích:**
Tên file và MIME type do client cung cấp có thể giả mạo. Nếu backend lưu trực tiếp file có tên/path từ user hoặc phục vụ file như executable content, attacker có thể gây path traversal, stored XSS hoặc upload nội dung nguy hiểm.

**Ví dụ:**
CMS cho editor upload ảnh: API kiểm tra size, decode/validate image thực tế, sinh object key mới, lưu Blob private và chỉ expose qua controlled delivery URL. Original filename chỉ được giữ như metadata đã sanitize.

**Lưu ý:**
Magic-byte validation không phải antivirus. Với tài liệu từ nguồn không tin cậy, threat model có thể cần malware scanning, content disarm hoặc asynchronous quarantine trước khi publish.

### Tip 5 — AI-generated test chỉ có giá trị khi nó kiểm tra behavior độc lập với implementation

**Mẹo:**
Khi dùng AI coding agent sinh tests, yêu cầu nó dựa trên requirement/public contract và edge cases, sau đó review assertions để bảo đảm test không chỉ mirror code hiện tại hoặc mock toàn bộ logic cần kiểm chứng.

**Tại sao hữu ích:**
Agent có thể đọc implementation rồi viết test tái diễn cùng assumption sai. Suite đạt coverage cao nhưng vẫn không phát hiện bug vì implementation và test cùng “đồng ý” về hành vi sai.

**Ví dụ:**
Với API tính discount, cung cấp business rules và boundary cases cho agent trước khi cho xem implementation. Sau đó mutation hoặc cố tình thay điều kiện `>=` thành `>`; nếu generated tests vẫn xanh, test chưa bảo vệ behavior quan trọng.

**Lưu ý:**
Không chấp nhận test chỉ vì build xanh hoặc coverage tăng. Kiểm tra failure mode: test có fail khi behavior bị phá không, có deterministic không và có phụ thuộc implementation detail dễ refactor không.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer xử lý at-least-once delivery an toàn hơn

**Khái niệm:**
Inbox Pattern lưu message identity hoặc processing record ở phía consumer để nhận biết message đã được xử lý. Nó thường được phối hợp với transaction của consumer nhằm làm business update và deduplication state trở nên atomic trong phạm vi local database.

**Vấn đề nó giải quyết:**
Message broker như Azure Service Bus có thể redeliver khi consumer hoàn tất business transaction nhưng crash trước khi acknowledge. Nếu handler không idempotent, cùng message có thể tạo invoice, shipment hoặc notification side effect nhiều lần.

**Ví dụ thực tế:**
Consumer nhận `OrderPaid` với `MessageId`. Trong một database transaction, nó kiểm tra Inbox, tạo fulfillment state và insert Inbox record. Nếu broker redeliver message, consumer thấy ID đã xử lý và bỏ qua business mutation lặp.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, cleanup, unique constraints và quyết định retention. Nó chỉ deduplicate trong phạm vi identity/retention đã thiết kế; external side effects ngoài transaction vẫn cần idempotency hoặc orchestration riêng.

**Middle → Senior insight:**
Middle developer cần implement unique message identity, transaction và retry đúng. Senior / Technical developer phải định nghĩa deduplication scope, retention, ordering, external side effects và cách Inbox phối hợp với Outbox để tạo delivery semantics có ý nghĩa end-to-end.

### Design 2 — Modular Monolith có thể là boundary tốt trước khi Microservices thực sự cần thiết

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia domain thành modules có ownership, API và dependency boundaries rõ. Mục tiêu là modularity trong code/domain mà chưa trả operational cost của distributed deployment.

**Vấn đề nó giải quyết:**
Một monolith không boundary dễ trở thành tightly coupled codebase; nhưng tách microservices quá sớm tạo network failure, distributed tracing, deployment coordination, eventual consistency và platform overhead trước khi team có nhu cầu scale/ownership tương ứng.

**Ví dụ thực tế:**
E-commerce system có Catalog, Orders và Identity modules trong cùng ASP.NET Core deployment. Modules không truy cập trực tiếp internal tables/classes của nhau mà giao tiếp qua explicit contracts. Nếu Catalog sau này có scaling/ownership khác biệt rõ, boundary đã có giúp extraction ít rủi ro hơn.

**Trade-off:**
Modular Monolith đơn giản vận hành và transaction local dễ hơn, nhưng vẫn scale/deploy chung và boundaries có thể bị phá nếu team thiếu discipline. Microservices cho independent deployment/scaling nhưng đổi lấy distributed-system complexity đáng kể.

**Middle → Senior insight:**
Middle developer cần tôn trọng module boundaries và dependency direction. Senior / Technical developer phải quyết định khi nào pressure về scaling, release cadence, ownership hoặc isolation đủ lớn để biện minh cho service extraction thay vì coi Microservices là trạng thái đích mặc định.

### Design 3 — Optimistic concurrency bảo vệ lost update nhưng cần conflict policy ở cấp business

**Khái niệm:**
Optimistic concurrency cho phép nhiều readers làm việc song song và phát hiện khi state đã thay đổi trước lúc update, thường bằng version/rowversion/ETag. Phát hiện conflict chỉ là bước đầu; hệ thống vẫn phải quyết định xử lý conflict như thế nào.

**Vấn đề nó giải quyết:**
Hai users đọc cùng customer record. User A cập nhật address, User B cập nhật credit limit từ snapshot cũ. Nếu update cuối cùng ghi đè toàn row, thay đổi của A có thể mất mà không có lỗi nào.

**Ví dụ thực tế:**
EF Core map SQL Server `rowversion` làm concurrency token. Khi `SaveChanges` ảnh hưởng 0 rows vì version đã đổi, API trả conflict phù hợp hoặc reload rồi áp business-specific merge; không tự động retry toàn bộ update với dữ liệu stale.

**Trade-off:**
Optimistic concurrency tránh giữ lock dài và phù hợp khi conflict hiếm, nhưng đẩy complexity sang conflict handling/user experience. Pessimistic locking có thể hợp lý khi conflict rất đắt hoặc contention semantics yêu cầu serialization, nhưng tăng blocking/deadlock risk.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency token và xử lý `DbUpdateConcurrencyException` đúng. Senior / Technical developer phải chọn conflict granularity và policy—reject, merge, retry hay serialize—dựa trên invariant, contention rate và hậu quả business của lost update.
