# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Với `Task.WhenAll`, giữ được đầy đủ failure thay vì chỉ nhìn exception đầu tiên

**Mẹo:**
Khi chạy nhiều I/O operation song song bằng `Task.WhenAll`, đừng assume chỉ có một task có thể fail. Nếu cần troubleshooting production, giữ reference tới các task riêng và inspect trạng thái/exception của từng task thay vì chỉ log một exception tổng quát.

**Tại sao hữu ích:**
Nhiều dependency có thể fail cùng lúc trong cùng một request hoặc batch. Nếu log chỉ exception đầu tiên, bạn có thể bỏ sót signal quan trọng như cả Pricing API và Inventory API đều timeout do network issue chung.

**Ví dụ:**
```csharp
var pricingTask = pricingClient.GetAsync(orderId, ct);
var inventoryTask = inventoryClient.GetAsync(orderId, ct);

try
{
    await Task.WhenAll(pricingTask, inventoryTask);
}
catch
{
    logger.LogWarning(
        "Pricing={PricingStatus}, Inventory={InventoryStatus}",
        pricingTask.Status,
        inventoryTask.Status);

    throw;
}
```

Nếu cần sâu hơn, log/trace exception của từng task theo correlation ID thay vì chỉ message chung của request.

**Lưu ý:**
Đừng dùng `Task.WhenAll` chỉ để “tăng tốc” khi downstream có rate limit hoặc database connection pool nhỏ. Parallelism làm latency giảm nhưng có thể tăng pressure lên dependency.

### Tip 2 — Thiết kế MongoDB compound index theo query shape, không theo thứ tự field trong document

**Mẹo:**
Khi tạo compound index cho MongoDB, dựa trên pattern filter/sort thực tế thay vì thứ tự property trong model. Equality field thường nên đứng trước range/sort field theo workload cụ thể.

**Tại sao hữu ích:**
MongoDB dùng prefix của compound index để thu hẹp search space. Một index có đúng field nhưng sai order vẫn có thể không phục vụ tốt query cần equality trên tenant và sort theo thời gian.

**Ví dụ:**
Query:
```javascript
db.orders.find({ tenantId: "t42", status: "Open" })
  .sort({ createdAt: -1 })
  .limit(50)
```

Index phù hợp có thể là:
```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Xác nhận bằng `explain()` thay vì chỉ nhìn tên index.

**Lưu ý:**
Không tạo một compound index cho mọi query variant. Mỗi index tăng write amplification, memory/storage và maintenance cost. Ưu tiên query quan trọng theo traffic và latency target.

### Tip 3 — Với Azure Functions, poison message cần flow riêng thay vì retry vô hạn

**Mẹo:**
Nếu Azure Function xử lý queue/message liên tục fail với cùng payload, phải có cơ chế dead-letter/poison handling rõ ràng thay vì tăng retry count vô hạn.

**Tại sao hữu ích:**
Retry hữu ích cho transient fault, nhưng payload invalid hoặc business state không thể xử lý sẽ tiếp tục tiêu tốn compute, làm queue backlog tăng và che các message khỏe mạnh phía sau.

**Ví dụ:**
```text
Message nhận lần 1 -> validation fail
Retry 1 -> vẫn fail
Retry 2 -> vẫn fail
-> chuyển dead-letter / poison queue
-> alert + lưu reason + correlation metadata
```

Sau khi fix code hoặc data, có thể replay có kiểm soát từ dead-letter source.

**Lưu ý:**
Đừng dead-letter ngay mọi exception. Timeout hoặc dependency 503 có thể là transient fault hợp lệ. Classification giữa transient và permanent failure phải dựa trên error semantics.

### Tip 4 — Khi dùng AI coding agent, verify package/API version từ repository trước khi chấp nhận code

**Mẹo:**
Trước khi merge code do AI sinh, kiểm tra package version, target framework và API thực sự tồn tại trong repository hiện tại thay vì tin vào syntax có vẻ hợp lý.

**Tại sao hữu ích:**
AI có thể sinh API chỉ có ở version mới hơn, package chưa được cài hoặc extension method thuộc namespace/library khác. Code trông “đúng .NET” nhưng vẫn fail build hoặc kéo theo dependency upgrade ngoài ý muốn.

**Ví dụ:**
```text
Agent đề xuất:
- API chỉ có trong .NET 10
- repo target net8.0
- package lock chưa có dependency tương ứng

Verification:
1. đọc *.csproj / Directory.Packages.props
2. build repository
3. chạy focused tests
4. inspect official package/source nếu API đáng ngờ
```

**Lưu ý:**
Build pass chưa đủ. Generated code vẫn có thể sai security, transaction boundary hoặc performance behavior. Review phải kiểm tra assumption chứ không chỉ compiler error.

### Tip 5 — Dùng browser DevTools `Initiator` và waterfall để tìm request nào thật sự gây chậm UI

**Mẹo:**
Khi trang Vue.js/React.js tải chậm, dùng Network waterfall và cột `Initiator` trong browser DevTools để xác định request nào được kích hoạt bởi script/component nào, thay vì chỉ nhìn request lâu nhất.

**Tại sao hữu ích:**
Một request chậm có thể chỉ là hậu quả. Root cause có thể là JavaScript bundle tải muộn rồi mới trigger API, request bị serialize do code `await` tuần tự hoặc một resource blocking render trước đó.

**Ví dụ:**
```text
main.js tải 900 ms
-> component mount
-> config API 500 ms
-> sau đó mới gọi products API 700 ms

Tổng perceived latency > 2 s dù từng API riêng lẻ không quá chậm.
```

Waterfall giúp thấy dependency chain để quyết định preload, parallelize hoặc giảm bundle đúng chỗ.

**Lưu ý:**
Đừng chỉ test trên máy dev có cache nóng và network nhanh. Throttle network/CPU và so với RUM production để tránh tối ưu sai bottleneck.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có execution rời rạc, scaling theo trigger và operational model serverless. Worker Service phù hợp hơn khi cần process dài hạn, lifecycle kiểm soát rõ hoặc resource/concurrency behavior ổn định.

**Vấn đề nó giải quyết:**
Nhiều team chọn Functions cho mọi background job vì setup nhanh, nhưng workload chạy liên tục, giữ connection lâu hoặc cần custom scheduling/concurrency đôi khi phù hợp với Worker Service hơn.

**Ví dụ thực tế:**
```text
Functions:
- xử lý Blob upload rời rạc
- Service Bus trigger theo event
- traffic biến động mạnh

Worker Service:
- poll/protocol connection dài hạn
- batch processor chạy liên tục
- cần custom lifecycle + predictable resource allocation
```

**Trade-off:**
Functions giảm infrastructure management và scale thuận tiện nhưng có execution/runtime constraints, cold-start/cost model và behavior phụ thuộc hosting plan. Worker Service kiểm soát tốt hơn nhưng phải tự vận hành deployment, scaling và availability.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và idempotency của workload. Senior / Technical developer phải chọn hosting model dựa trên execution duration, traffic shape, scaling, cost, operability và failure recovery thay vì preference framework.

### Design 2 — CQRS: tách read/write khi pressure thực tế khác nhau, không phải vì muốn nhiều layer

**Khái niệm:**
CQRS tách command model khỏi query model khi hai phía có nhu cầu khác nhau về domain logic, schema, performance hoặc scaling. Nó không bắt buộc phải có microservices, event sourcing hay hai database.

**Vấn đề nó giải quyết:**
Một domain write path cần invariant chặt chẽ có thể trở nên khó tối ưu nếu cùng model đó phải phục vụ dashboard/read query nhiều join, projection và search khác biệt.

**Ví dụ thực tế:**
```text
Write side:
Order aggregate
- validate transition
- enforce payment invariant

Read side:
OrderListDto
- projection trực tiếp
- denormalized fields cho table/search
```

Có thể vẫn dùng cùng database nhưng query model khác command model.

**Trade-off:**
CQRS giúp mỗi side tối ưu đúng mục tiêu nhưng thêm model duplication, mapping và cognitive load. Nếu CRUD đơn giản và read/write shape gần giống nhau, CQRS có thể chỉ làm code dài hơn.

**Middle → Senior insight:**
Middle developer cần tránh dùng domain entity như DTO cho mọi query. Senior / Technical developer phải chứng minh read/write pressure đủ khác để justify separation và chọn mức CQRS tối thiểu cần thiết.

### Design 3 — Rate limiting ở edge vs application

**Khái niệm:**
Rate limiting có thể đặt ở API gateway/reverse proxy để chặn traffic sớm, hoặc trong application để áp rule có business context sâu hơn. Hai layer thường phục vụ mục tiêu khác nhau.

**Vấn đề nó giải quyết:**
Nếu chỉ rate-limit trong application, request độc hại vẫn tiêu tốn connection, TLS và app resources trước khi bị reject. Nếu chỉ giới hạn ở edge, gateway có thể không biết tenant plan, operation cost hoặc user-specific quota.

**Ví dụ thực tế:**
```text
Edge:
- 500 req/s mỗi IP
- chống burst/DDoS cơ bản

Application:
- Free tenant: 100 exports/ngày
- Premium tenant: 5 concurrent report jobs
```

Critical endpoint có thể dùng cả hai layer với metric/retry-after semantics rõ ràng.

**Trade-off:**
Edge limiting giảm blast radius và bảo vệ infrastructure nhưng context hạn chế. Application limiting linh hoạt hơn nhưng thêm state, distributed coordination và cost trên hot path.

**Middle → Senior insight:**
Middle developer cần trả status/headers đúng và tránh race condition trong quota logic. Senior / Technical developer phải thiết kế rate-limit key, burst policy, distributed state, bypass rule, degraded mode và placement theo threat model + business SLA.
