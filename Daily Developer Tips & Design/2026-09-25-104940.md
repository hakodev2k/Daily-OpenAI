# Daily Developer Tips & Design — 2026-09-25

## 🛠 Developer Tips & Tricks

### Tip 1 — Giảm allocation khi xử lý buffer với Span và ArrayPool

**Mẹo:**
Với hot path xử lý dữ liệu nhị phân hoặc text buffer ngắn hạn, đo allocation trước; nếu GC pressure đáng kể, cân nhắc `Span<T>`, `Memory<T>` hoặc thuê buffer từ `ArrayPool<T>` thay vì tạo array mới liên tục.

**Tại sao hữu ích:**
Allocation nhỏ nhưng lặp với throughput cao có thể tăng Gen 0 collections và tail latency. `Span<T>` cho phép thao tác trên một vùng memory mà không cần copy; `ArrayPool<T>` tái sử dụng array giữa các operation.

**Ví dụ:**
```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096);
try
{
    Memory<byte> memory = buffer.AsMemory(0, 4096);
    int read = await stream.ReadAsync(memory, cancellationToken);
    Process(memory.Span[..read]);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
}
```
Nếu endpoint upload có allocation rate cao, xác nhận bằng profiler/counters trước và sau thay đổi.

**Lưu ý:**
Pooled buffer có ownership phức tạp hơn: không dùng sau khi `Return`, không giữ reference lâu và cân nhắc xóa dữ liệu nhạy cảm. Với code không phải hot path, array thông thường thường dễ bảo trì hơn.

### Tip 2 — EF Core compiled query chỉ đáng dùng sau khi query execution không còn là bottleneck chính

**Mẹo:**
Đừng mặc định dùng compiled query cho mọi EF Core query. Trước hết đo tổng latency, SQL execution và database round trip; chỉ tối ưu query-compilation overhead trên hot path được gọi rất thường xuyên.

**Tại sao hữu ích:**
Trong nhiều API, thời gian database/network lớn hơn nhiều so với chi phí EF Core chuẩn bị query. Tối ưu sai tầng làm code phức tạp nhưng không cải thiện p95 đáng kể.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, Guid, Task<Customer?>>
    GetCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Customers.AsNoTracking().FirstOrDefault(x => x.Id == id));
```
Dùng benchmark hoặc trace để so sánh trước/sau trên endpoint có throughput cao.

**Lưu ý:**
Compiled query không sửa SQL tệ, thiếu index, N+1 hay connection-pool exhaustion. Query shape động cũng có thể không phù hợp với cách tối ưu này.

### Tip 3 — Dùng ETag/If-Match để ngăn lost update ở HTTP boundary

**Mẹo:**
Với resource có nhiều client cùng chỉnh sửa, expose version dưới dạng `ETag` và yêu cầu update gửi `If-Match` thay vì âm thầm ghi đè trạng thái mới hơn.

**Tại sao hữu ích:**
Concurrency token trong database chỉ bảo vệ tốt khi contract HTTP mang version của trạng thái client đã đọc. Nếu client không gửi version, server khó phân biệt update hợp lệ với stale update.

**Ví dụ:**
```http
GET /api/articles/42
ETag: "v17"

PUT /api/articles/42
If-Match: "v17"
```
Nếu resource hiện là `v18`, API trả `412 Precondition Failed`; client reload hoặc thực hiện merge theo nghiệp vụ.

**Lưu ý:**
Không tự động retry update stale nếu command phụ thuộc dữ liệu người dùng đã nhìn thấy. `ETag` cho caching và concurrency có semantics liên quan nhưng cần thiết kế representation/version rõ ràng.

### Tip 4 — Elasticsearch filter cho điều kiện exact, query cho relevance

**Mẹo:**
Tách điều kiện cần scoring khỏi điều kiện boolean/exact. Dùng full-text `query` cho title/description và `filter` cho tenant, status, category hoặc khoảng thời gian khi relevance không cần thay đổi.

**Tại sao hữu ích:**
Filter context không tính relevance score cho điều kiện đó và diễn đạt đúng intent. Query rõ ràng hơn, đồng thời tránh việc một điều kiện nghiệp vụ vô tình ảnh hưởng ranking.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "name": "wireless keyboard" } }],
      "filter": [
        { "term": { "tenantId": "acme" } },
        { "term": { "isActive": true } }
      ]
    }
  }
}
```
Khi search chậm, kiểm tra mapping, analyzer, cardinality và profile query thay vì chỉ tăng cluster size.

**Lưu ý:**
`term` trên analyzed text thường không có semantics như người dùng mong đợi; mapping `keyword`/text phải phù hợp use case. Elasticsearch vẫn không nên trở thành transactional source of truth chỉ vì search thuận tiện.

### Tip 5 — Phân biệt lỗi deployment với lỗi configuration bằng artifact bất biến

**Mẹo:**
Build một artifact/container image một lần rồi promote cùng artifact qua các environment; inject environment-specific configuration/secrets lúc deploy thay vì rebuild source cho production.

**Tại sao hữu ích:**
Nếu staging và production chạy binary khác nhau do rebuild, bạn mất bằng chứng rằng artifact đã test chính là artifact đang release. Immutable artifact giúp thu hẹp incident thành code/artifact, configuration hoặc infrastructure.

**Ví dụ:**
CI tạo image `orders-api:8f31c2a`, integration tests chạy trên image đó, rồi CD promote đúng digest sang production. Connection string và credentials đến từ environment/secret store, không bake vào image.

**Lưu ý:**
“Build once” không có nghĩa configuration không cần validation. Startup nên fail rõ với config bắt buộc sai; secrets không được ghi vào logs hoặc artifact metadata.

## 🧠 Software Design

### Design 1 — Azure Functions hay Worker Service dựa trên workload lifecycle

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có trigger/binding và nhu cầu scale theo sự kiện; Worker Service phù hợp hơn khi process cần lifecycle dài, kiểm soát execution loop, connection hoặc resource behavior chặt chẽ.

**Vấn đề nó giải quyết:**
Đội ngũ thường chọn Functions vì “serverless” hoặc Worker vì quen .NET mà không xét duration, throughput, cold start, deployment model và operational control.

**Ví dụ thực tế:**
Resize ảnh phát sinh không đều từ Blob có thể phù hợp với Function. Một consumer xử lý stream liên tục, giữ nhiều connection và cần tuning concurrency/health lifecycle riêng có thể dễ vận hành hơn dưới Worker Service trên App Service/Kubernetes.

**Trade-off:**
Functions giảm infrastructure management và tích hợp trigger tốt nhưng có platform/runtime constraints, scaling behavior và cost profile cần hiểu. Worker cho nhiều quyền kiểm soát hơn nhưng đội ngũ phải sở hữu hosting, scaling, health và deployment nhiều hơn.

**Middle → Senior insight:**
Middle developer cần triển khai cancellation, retry và idempotency đúng ở cả hai mô hình. Senior / Technical developer phải so workload shape, latency, execution duration, scale pattern, cost và operational ownership; không biến “serverless” thành quyết định kiến trúc mặc định.

### Design 2 — Schema evolution cho event phải ưu tiên compatibility

**Khái niệm:**
Event contract là API bất đồng bộ. Producer và consumer có thể deploy lệch thời điểm, vì vậy schema phải tiến hóa sao cho consumer cũ và mới có khoảng tương thích hợp lý.

**Vấn đề nó giải quyết:**
Đổi tên/xóa field hoặc thay semantics của `OrderCreated` có thể phá consumer mà producer không nhìn thấy ngay; message còn nằm trong queue cũng có thể được tạo bởi phiên bản cũ.

**Ví dụ thực tế:**
Thay vì đổi `customerName` thành object bắt buộc ngay lập tức, producer thêm field mới có semantics rõ, consumer chấp nhận cả contract cũ trong migration window, telemetry đo version còn lưu hành trước khi deprecate.

**Trade-off:**
Backward compatibility giúp deploy độc lập và rollback an toàn hơn nhưng kéo theo schema discipline, migration window và đôi khi duplicate fields. Tạo event version mới cho mọi thay đổi lại có thể làm ecosystem phân mảnh.

**Middle → Senior insight:**
Middle developer cần tránh breaking changes và test serialization/consumer compatibility. Senior / Technical developer phải định nghĩa ownership, versioning/deprecation policy, retention horizon và quyết định khi nào additive evolution đủ, khi nào semantics thay đổi lớn cần event mới.

### Design 3 — Bounded Context quan trọng hơn việc chia project theo technical layer

**Khái niệm:**
Bounded Context đặt boundary quanh một mô hình nghiệp vụ có ngôn ngữ, invariant và ownership nhất quán. Nó không đồng nghĩa với Microservice; một Modular Monolith có thể chứa nhiều bounded contexts.

**Vấn đề nó giải quyết:**
Một entity `Customer` dùng chung cho CRM, Billing và Support thường tích lũy field và rule mâu thuẫn. Shared domain model tạo coupling: thay đổi của một nhóm làm ảnh hưởng các nhóm không liên quan.

**Ví dụ thực tế:**
Trong CRM, Customer tập trung lead/contact lifecycle; trong Billing, account cần payment terms và invoice identity. Hai context trao đổi stable identifiers/contracts thay vì cùng reference một giant `Customer` entity và database model.

**Trade-off:**
Boundary rõ tăng autonomy và giảm semantic coupling nhưng tạo mapping, duplication và integration cost. Với domain nhỏ, chia context quá sớm có thể chỉ tạo ceremony và khó navigation.

**Middle → Senior insight:**
Middle developer cần giữ business rules trong đúng module/context và tránh cross-boundary data access tùy tiện. Senior / Technical developer phải tìm boundary từ language, change coupling, invariants và team ownership; sau đó mới quyết định boundary đó nên ở namespace, module, database hay process riêng.
