# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống connection pooling

**Mẹo:**
Nếu dùng `AddDbContextPool`, hiểu rằng EF Core tái sử dụng instance `DbContext`; còn database connection pooling thường do ADO.NET provider quản lý riêng. Chỉ bật context pooling sau khi đo và đảm bảo context không giữ state theo request một cách nguy hiểm.

**Tại sao hữu ích:**
Tạo `DbContext` thường khá nhẹ, nhưng workload throughput cao có thể hưởng lợi từ việc giảm allocation/setup. Tuy nhiên pooled context được reset rồi tái sử dụng, nên state custom như tenant identifier được gán sai lifecycle có thể rò sang request khác.

**Ví dụ:**
Một SaaS API đặt `TenantId` mutable trực tiếp trên pooled `DbContext`. Nếu initialization/reset không đúng, request tenant B có thể nhận state còn lại từ tenant A. An toàn hơn là đưa tenant scope vào query/service theo lifecycle rõ ràng và kiểm thử isolation.

**Lưu ý:**
Đừng dùng `DbContext` pooling để chữa connection pool exhaustion. Hai pool giải quyết hai lớp khác nhau; connection leak, transaction dài hoặc SQL chậm phải được chẩn đoán ở database/ADO.NET path.

### Tip 2 — Dùng `Channel<T>` để tạo bounded producer-consumer trong .NET

**Mẹo:**
Khi process cần nhận work nhanh rồi xử lý nền, dùng bounded `Channel<T>` thay vì `ConcurrentQueue<T>` không giới hạn kết hợp polling thủ công.

**Tại sao hữu ích:**
Bounded channel tạo backpressure: khi consumer không theo kịp producer, hệ thống có thể chờ, từ chối hoặc áp dụng policy rõ ràng thay vì để queue trong memory tăng vô hạn đến OOM. `Channel<T>` cũng hỗ trợ async wait mà không cần loop + `Task.Delay`.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait
});

await channel.Writer.WriteAsync(job, ct);
await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
    await ProcessAsync(item, stoppingToken);
```
Một image-processing API có thể giới hạn work đang chờ thay vì nhận vô hạn file rồi giữ tất cả trong RAM.

**Lưu ý:**
In-memory channel mất dữ liệu khi process restart và không thay thế durable broker như Azure Service Bus. Nếu work phải sống qua deployment/crash hoặc cần multi-instance coordination, dùng durable messaging.

### Tip 3 — Phân biệt blocking với deadlock khi SQL API bị “đứng”

**Mẹo:**
Khi request chờ database lâu, xác định session đang bị blocking hay đã xảy ra deadlock trước khi sửa query hoặc tăng timeout. Blocking là một transaction giữ lock khiến transaction khác chờ; deadlock là vòng phụ thuộc mà database phải chọn victim để phá vòng.

**Tại sao hữu ích:**
Hai triệu chứng đều có thể xuất hiện như API chậm/fail nhưng remediation khác nhau. Blocking dài thường liên quan transaction scope, query/index hoặc user interaction giữ transaction; deadlock cần xem lock order và deadlock graph.

**Ví dụ:**
Transaction A update `Orders` rồi `Inventory`, transaction B update `Inventory` rồi `Orders`. Dưới concurrency, hai transaction có thể tạo cycle. Chuẩn hóa thứ tự access hoặc thu nhỏ transaction có thể loại nguyên nhân thay vì retry vô hạn.

**Lưu ý:**
Retry deadlock victim có thể hợp lý cho transient conflict, nhưng retry chỉ che thiết kế lock-order xấu nếu deadlock xảy ra thường xuyên. Với blocking, tăng command timeout chỉ khiến request chờ lâu hơn.

### Tip 4 — File upload cần kiểm tra nội dung và giới hạn tài nguyên, không chỉ extension

**Mẹo:**
Với ASP.NET Core upload endpoint, giới hạn kích thước, stream dữ liệu khi phù hợp, tạo server-side filename/object key và kiểm tra loại nội dung theo policy thay vì tin `FileName` hoặc `Content-Type` từ client.

**Tại sao hữu ích:**
Metadata multipart do client kiểm soát. File tên `.jpg` có thể không phải ảnh; filename có thể chứa path hoặc ký tự nguy hiểm; buffer file lớn vào memory có thể gây resource exhaustion. Storage public còn biến upload thành đường phát tán active content.

**Ví dụ:**
Backend nhận avatar, giới hạn 5 MB, kiểm tra signature/decoder ảnh, tạo GUID làm Blob key, lưu ngoài web root và chỉ trả URL qua controlled delivery path. Original filename nếu cần chỉ được lưu như metadata đã sanitize.

**Lưu ý:**
Không tự viết malware scanner sơ sài rồi coi là đủ. Threat model phụ thuộc loại file và cách file được consume. Office/PDF/archive cần policy khác ảnh; archive còn có decompression bomb và nested content risk.

### Tip 5 — Dùng browser DevTools waterfall để tìm bottleneck trước khi tối ưu frontend code

**Mẹo:**
Khi trang Vue.js/React.js chậm, mở Network/Performance waterfall và tách thời gian DNS/connect/TTFB/download/render trước khi kết luận JavaScript là nguyên nhân.

**Tại sao hữu ích:**
Một Core Web Vitals regression có thể đến từ backend TTFB, image quá lớn, render-blocking resource hoặc bundle JavaScript. Tối ưu component rendering sẽ không sửa được 1.5 giây TTFB từ API/CMS.

**Ví dụ:**
Trang product có LCP 3.8 giây. Waterfall cho thấy HTML TTFB 1.4 giây và hero image 2 MB bắt đầu tải muộn. Ưu tiên backend/cache và image loading trước khi micro-optimize computed properties trong Vue.

**Lưu ý:**
Một lần test trên máy developer không đại diện production. So sánh cold/warm cache, throttled network/CPU và field telemetry nếu có; CDN/browser cache có thể che bottleneck trong local test.

## 🧠 Software Design

### Design 1 — Repository abstraction chỉ có giá trị khi nó tạo boundary hữu ích

**Khái niệm:**
Repository Pattern tạo abstraction cho cách application truy cập/persist domain data. Với EF Core, `DbContext`/`DbSet` đã cung cấp nhiều semantics tương tự, nên thêm generic repository chỉ đáng giá khi boundary mới thực sự mang business/query abstraction hoặc isolation cần thiết.

**Vấn đề nó giải quyết:**
Application có thể cần che data source phức tạp, gom query business có semantics rõ hoặc bảo vệ domain/application layer khỏi infrastructure contract. Nhưng wrapper CRUD `GetAll/Add/Update/Delete` quanh `DbSet` thường chỉ thêm forwarding layer và làm mất capability của EF Core.

**Ví dụ thực tế:**
`IOrderRepository.GetPendingForFulfillment(...)` có thể thể hiện một domain-oriented query quan trọng. Ngược lại `IGenericRepository<T>.GetAll()` trả `IQueryable<T>` vừa leak EF semantics vừa không tạo boundary thực tế.

**Trade-off:**
Repository hữu ích có thể giảm coupling và tập trung persistence policy; repository dư thừa tăng code, mock-heavy test và hạn chế query optimization. Direct `DbContext` đơn giản hơn nhưng application layer sẽ biết EF Core nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu lifetime, query và transaction của EF Core thay vì che chúng bằng abstraction. Senior / Technical developer phải quyết định boundary dựa trên domain complexity, testing strategy, persistence volatility và team conventions; không áp dụng Repository vì template kiến trúc yêu cầu.

### Design 2 — Queue và Topic giải quyết hai distribution semantics khác nhau

**Khái niệm:**
Queue thường phân phối một message cho một consumer logic trong nhóm competing consumers; Topic + subscriptions fan-out cùng event tới nhiều subscriber độc lập, mỗi subscription có lifecycle/filter/retry riêng.

**Vấn đề nó giải quyết:**
Nếu một business event cần kích hoạt Billing, Analytics và Notification độc lập, một queue chung khiến các consumer cạnh tranh lấy message thay vì mỗi capability nhận bản riêng. Ngược lại, tạo topic cho một command chỉ có đúng một owner có thể tăng topology không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command gửi tới Billing queue. `OrderCompleted` là event publish lên topic; subscription của Loyalty, Analytics và Email xử lý độc lập. Email outage không nên lấy mất event của Analytics.

**Trade-off:**
Topic tăng số subscription, DLQ, monitoring và duplicate processing paths. Queue đơn giản hơn nhưng không hỗ trợ fan-out semantics tự nhiên. Cả hai vẫn có at-least-once delivery nên consumer cần idempotency.

**Middle → Senior insight:**
Middle developer cần phân biệt command ownership với event notification và xử lý retry/DLQ đúng. Senior / Technical developer phải thiết kế topology theo bounded context, throughput, ordering, subscription ownership và failure isolation, tránh biến broker thành mạng event không ai quản lý.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo state mới phải quản lý

**Khái niệm:**
Feature Flag cho phép code được deploy nhưng capability chỉ được bật cho cohort, tenant hoặc tỷ lệ traffic cụ thể. Nó giảm coupling giữa thời điểm đưa binary lên production và thời điểm business feature được expose.

**Vấn đề nó giải quyết:**
Một thay đổi lớn cần rollout dần, canary theo tenant hoặc kill switch khi dependency mới gặp lỗi. Không có flag, rollback thường đồng nghĩa redeploy toàn application, chậm hơn và ảnh hưởng cả thay đổi không liên quan.

**Ví dụ thực tế:**
Checkout v2 được deploy cùng v1 nhưng chỉ bật cho internal users, sau đó 5%, 25%, 100% traffic khi metrics ổn định. Nếu error rate tăng, flag đưa traffic về v1 mà không cần build artifact mới.

**Trade-off:**
Mỗi flag tạo thêm execution paths và test matrix. Flag sống lâu trở thành technical debt; flag dùng cho schema/side effect mà không thiết kế compatibility có thể không rollback an toàn dù UI đã tắt.

**Middle → Senior insight:**
Middle developer cần viết hai path có test và không hard-code flag evaluation rải rác. Senior / Technical developer phải phân loại release/ops/experiment flags, thiết kế ownership + expiry, xác định rollback semantics và bảo đảm database/message contracts tương thích trong toàn rollout window.
