# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate `Options` ngay lúc startup thay vì chờ request đầu tiên mới lỗi

**Mẹo:**
Với configuration quan trọng trong ASP.NET Core như API endpoint, timeout, queue name hoặc feature settings, dùng `Validate` / `ValidateDataAnnotations` kết hợp `ValidateOnStart()` để fail fast khi application khởi động.

**Tại sao hữu ích:**
Nếu configuration sai chỉ được phát hiện khi một code path hiếm chạy, deployment có thể nhìn như thành công nhưng lỗi xuất hiện nhiều giờ sau. Startup validation chuyển lỗi cấu hình thành deployment failure rõ ràng và dễ rollback hơn.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(x => Uri.TryCreate(x.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be an absolute URL")
    .Validate(x => x.TimeoutSeconds is > 0 and <= 30,
        "Payment:TimeoutSeconds must be between 1 and 30")
    .ValidateOnStart();
```

**Lưu ý:**
Không phải setting nào cũng nên bắt application fail startup. Optional integration hoặc feature đang tắt có thể cần validation có điều kiện; nếu validate quá cứng, một dependency không dùng cũng có thể chặn toàn bộ service khởi động.

### Tip 2 — Dùng `ExecuteUpdateAsync` cho bulk update khi không cần materialize entity

**Mẹo:**
Trong EF Core, nếu cần cập nhật nhiều row bằng cùng một rule và không cần domain behavior trên từng entity, cân nhắc `ExecuteUpdateAsync` thay vì load hàng nghìn entity vào memory rồi gọi `SaveChanges`.

**Tại sao hữu ích:**
Bulk update server-side tránh materialization, change tracking và nhiều parameterized updates. Database thực hiện một câu lệnh `UPDATE` trực tiếp, giảm memory, network round trips và thời gian giữ `DbContext`.

**Ví dụ:**
```csharp
await db.Sessions
    .Where(x => x.ExpiresAt < now && x.Status == SessionStatus.Active)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, SessionStatus.Expired),
        cancellationToken);
```

**Lưu ý:**
`ExecuteUpdateAsync` bypass change tracker và không chạy logic nằm trong entity instance. Nếu aggregate cần invariant, domain event hoặc concurrency handling riêng trên từng entity, bulk update có thể phá semantic dù SQL rất nhanh.

### Tip 3 — Dùng Elasticsearch alias để reindex mà không buộc client đổi index name

**Mẹo:**
Khi cần thay mapping hoặc analyzer, tạo index version mới, reindex dữ liệu rồi chuyển alias sang index mới thay vì để application gọi trực tiếp tên index vật lý.

**Tại sao hữu ích:**
Mapping quan trọng thường không thể sửa tùy ý trên index đang chạy. Alias tạo indirection ổn định cho application và cho phép cutover nhanh giữa `products-v12` và `products-v13` sau khi validation hoàn tất.

**Ví dụ:**
```text
Application -> alias: products-current

products-current -> products-v12
reindex -> products-v13
validate count/search behavior
atomic alias switch
products-current -> products-v13
```

**Lưu ý:**
Alias switch không tự giải quyết data change xảy ra trong lúc reindex. Với write-active system, cần dual-write, change capture hoặc một catch-up phase để tránh index mới thiếu document vừa cập nhật.

### Tip 4 — Với Vue/React, đừng lưu state có thể tính trực tiếp từ state khác

**Mẹo:**
Nếu một giá trị UI hoàn toàn có thể derive từ source state/props, ưu tiên computed value, selector hoặc calculation tại render thay vì tạo thêm state rồi đồng bộ bằng effect/watch.

**Tại sao hữu ích:**
Duplicate state tạo hai source-of-truth. Một update path bị bỏ sót có thể khiến UI hiển thị dữ liệu không nhất quán dù từng biến riêng lẻ đều hợp lệ.

**Ví dụ:**
Không cần lưu cả:
```text
items
filteredItems
```

nếu `filteredItems` luôn bằng `items` sau khi áp dụng `searchTerm`. Trong Vue có thể dùng `computed`; trong React có thể derive trong render hoặc `useMemo` khi computation thực sự đắt.

**Lưu ý:**
Không dùng `useMemo` hoặc computed caching theo phản xạ cho mọi phép tính nhỏ. Mục tiêu chính là giảm duplicated state; optimization chỉ nên thêm khi profiling hoặc workload biện minh.

### Tip 5 — CORS không phải cơ chế authorization

**Mẹo:**
Khi cấu hình ASP.NET Core CORS, coi nó là browser-origin policy chứ không phải lớp bảo vệ API. Endpoint vẫn phải authentication/authorization độc lập.

**Tại sao hữu ích:**
CORS chủ yếu được browser enforce. Script chạy từ origin không được phép có thể bị chặn đọc response, nhưng attacker vẫn có thể gọi API bằng server-side client, curl hoặc công cụ khác nếu endpoint không có authorization đúng.

**Ví dụ:**
Một API chỉ cho frontend `https://app.example.com` gọi từ browser:
```csharp
policy.WithOrigins("https://app.example.com")
      .AllowAnyHeader()
      .AllowAnyMethod();
```

Endpoint admin vẫn phải có policy như:
```csharp
.RequireAuthorization("AdminOnly");
```

**Lưu ý:**
Khi dùng credentials/cookies, không cấu hình wildcard origin tùy tiện. Đồng thời CORS sai có thể làm frontend production lỗi, nhưng việc “fix” bằng `AllowAnyOrigin` không giải quyết authentication hay CSRF risk.

## 🧠 Software Design

### Design 1 — API backward compatibility bằng additive evolution

**Khái niệm:**
Khi public hoặc multi-client API phải evolve, ưu tiên thay đổi additive như thêm optional field, endpoint hoặc capability mới thay vì rename/remove field đang được consumer sử dụng.

**Vấn đề nó giải quyết:**
Web, mobile app và third-party consumer không deploy đồng thời với backend. Một breaking change nhỏ ở JSON contract có thể làm client cũ lỗi ngay cả khi server deployment thành công.

**Ví dụ thực tế:**
Thay vì đổi:
```text
fullName -> displayName
```

ngay lập tức, có thể thêm `displayName`, tiếp tục trả `fullName` trong deprecation window, theo dõi usage rồi mới loại bỏ trong version phù hợp.

**Trade-off:**
Additive evolution giảm coordination và rollout risk nhưng khiến contract mang legacy field lâu hơn. Versioning mạnh giúp contract sạch hơn nhưng tăng số version, test matrix và maintenance cost.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking change và giữ serializer/DTO contract ổn định. Senior / Technical developer phải thiết kế deprecation policy, telemetry về consumer usage, compatibility test và quyết định khi nào một breaking version thực sự đáng chi phí migration.

### Design 2 — Retry vs Circuit Breaker: một cái thử lại, một cái ngăn thử vô ích

**Khái niệm:**
Retry xử lý transient failure bằng cách thử lại sau delay/backoff. Circuit Breaker ngừng gọi tạm thời khi dependency đang fail liên tục để giảm load và cho dependency thời gian phục hồi.

**Vấn đề nó giải quyết:**
Nếu một downstream API đang outage, retry từ hàng nghìn request có thể nhân traffic lỗi và kéo tài nguyên của caller xuống theo. Nhưng nếu mọi failure đều fail-fast, một lỗi transient rất ngắn lại không được hấp thụ.

**Ví dụ thực tế:**
```text
Request -> timeout
-> retry 1 after backoff
-> retry 2
-> failure rate vượt threshold
-> circuit opens
-> subsequent calls fail fast / fallback
-> half-open probe sau khoảng chờ
```

**Trade-off:**
Retry tăng khả năng vượt qua transient fault nhưng tăng latency và duplicate side-effect risk. Circuit Breaker bảo vệ hệ thống nhưng có thể từ chối request trong khi dependency vừa phục hồi nếu threshold/window không phù hợp.

**Middle → Senior insight:**
Middle developer cần chỉ retry operation an toàn/idempotent và dùng timeout rõ ràng. Senior / Technical developer phải phối hợp retry, circuit breaker, concurrency limit và SLA để tránh retry amplification giữa nhiều service layer.

### Design 3 — Bounded Context nên theo business language và ownership, không theo table

**Khái niệm:**
Trong DDD, Bounded Context là ranh giới nơi một model và business language có nghĩa nhất quán. Nó không nhất thiết tương ứng một table, một entity hay một CRUD screen.

**Vấn đề nó giải quyết:**
Một từ như `Customer` có thể mang nghĩa khác giữa Sales, Billing và Support. Nếu toàn hệ thống ép dùng một mega-model chung, mỗi module thêm field/rule riêng và coupling tăng dần.

**Ví dụ thực tế:**
```text
Sales: Customer = lead/account + sales status
Billing: Customer = legal party + payment terms
Support: Customer = requester + entitlement
```

Các context có thể chia sẻ identifier nhưng giữ model và rule riêng, giao tiếp qua contract rõ ràng.

**Trade-off:**
Boundary rõ tăng autonomy và giảm semantic coupling nhưng tạo mapping, integration contract và đôi khi duplicate data. Chia quá nhỏ lại tăng coordination và operational complexity mà domain chưa cần.

**Middle → Senior insight:**
Middle developer cần không kéo entity của context khác vào business logic chỉ vì cùng tên. Senior / Technical developer phải tìm boundary dựa trên language, change cadence, team ownership và transaction pressure, rồi chọn mức tách code/database/deployment phù hợp thay vì áp DDD hình thức.
