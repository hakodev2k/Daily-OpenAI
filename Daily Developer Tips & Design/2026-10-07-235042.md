# Daily Developer Tips & Design — 2026-10-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian

**Mẹo:**
Với .NET 8+, inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` trong business logic cần kiểm thử.

**Tại sao hữu ích:**
Clock là một dependency. Khi code đọc thời gian hệ thống trực tiếp, test cho expiration, retry window hoặc scheduled behavior dễ phụ thuộc timing thật và trở nên flaky. `TimeProvider` cho phép production dùng system clock còn test điều khiển thời gian một cách deterministic.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        clock.GetUtcNow() >= expiresAt;
}
```
Trong test có thể dùng controllable/fake time provider để dịch clock thay vì `Task.Delay`.

**Lưu ý:**
Không phải mọi timestamp đều nên lấy từ application clock; dữ liệu cần nhất quán với database transaction có thể cần database-generated time. Cũng đừng trộn `DateTime.Now`, UTC và local time không có quy ước rõ ràng.

### Tip 2 — Dùng `TagWith` để nối EF Core query với telemetry

**Mẹo:**
Với query quan trọng, thêm `TagWith` để SQL trace/execution diagnostics cho biết query đến từ use case nào thay vì phải đoán từ SQL generated.

**Tại sao hữu ích:**
Production thường có nhiều LINQ expressions sinh SQL gần giống nhau. Query tag tạo một dấu vết nhẹ giúp liên kết slow SQL trong database telemetry với endpoint/job cụ thể, rút ngắn bước symptom → evidence → source code.

**Ví dụ:**
```csharp
var items = await db.Products
    .TagWith("Catalog/SearchProducts")
    .Where(x => x.IsActive && x.CategoryId == categoryId)
    .OrderBy(x => x.Name)
    .Take(50)
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Tag không thay thế distributed tracing hoặc query metrics. Tránh đưa user input, token, email hay dữ liệu nhạy cảm vào tag vì chúng có thể xuất hiện trong database logs/monitoring.

### Tip 3 — Kiểm tra hot partition trước khi tăng throughput Cosmos DB

**Mẹo:**
Khi Cosmos DB xuất hiện 429 hoặc latency tăng, xem RU consumption theo physical/logical partition và distribution của partition key trước khi chỉ tăng provisioned throughput.

**Tại sao hữu ích:**
Tổng RU còn dư không đảm bảo từng partition còn capacity. Một tenant/key nhận phần lớn traffic có thể trở thành hot partition, nên tăng tổng throughput đôi khi tốn tiền nhưng không giải quyết data/traffic skew.

**Ví dụ:**
Một event store partition theo `tenantId`; một khách hàng import hàng triệu events trong khi tenant khác gần như idle. Telemetry cho thấy throttling tập trung vào một key. Hướng xử lý có thể là thay đổi workload distribution hoặc partition strategy cho dữ liệu mới, không chỉ scale RU.

**Lưu ý:**
Partition key là quyết định khó thay đổi sau khi dữ liệu lớn. Đừng chọn key chỉ vì cardinality cao; phải xét access pattern, transaction boundary, data growth và khả năng tạo hot key.

### Tip 4 — Dùng `git reflog` để cứu commit tưởng đã mất

**Mẹo:**
Sau `reset --hard`, rebase hoặc branch deletion nhầm, kiểm tra `git reflog` trước khi kết luận commit đã mất.

**Tại sao hữu ích:**
Git giữ lịch sử di chuyển của local refs trong reflog một thời gian. Commit không còn reachable từ branch hiện tại vẫn có thể được tìm lại bằng SHA và tạo branch mới, giúp phục hồi nhanh mà không cần reconstruct code thủ công.

**Ví dụ:**
```bash
git reflog
git switch -c recovery <commit-sha>
```
Sau đó review diff và chỉ merge/cherry-pick phần cần thiết.

**Lưu ý:**
Reflog chủ yếu là local và có retention; nó không phải backup lâu dài. Nếu object đã bị garbage collection hoặc commit chỉ tồn tại trên máy khác, reflog hiện tại không đảm bảo cứu được.

### Tip 5 — Đo serialization khi API CPU cao nhưng SQL vẫn nhanh

**Mẹo:**
Khi endpoint trả payload lớn có CPU/latency cao nhưng database nhanh, profile JSON serialization và response size trước khi tiếp tục tối ưu query.

**Tại sao hữu ích:**
Materialization, object graph lớn và `System.Text.Json` serialization có thể chiếm đáng kể CPU/allocation. Database latency thấp không có nghĩa request path đã rẻ; trace/profiler giúp tách query, mapping, serialization và network transfer.

**Ví dụ:**
Search API lấy 5.000 products trong 90 ms nhưng request mất 1.2 s và allocation tăng mạnh. Giảm response bằng pagination/projection, tránh fields không cần thiết và đo lại p95 có thể hiệu quả hơn thêm index.

**Lưu ý:**
Đừng chuyển sang custom serializer hoặc source generation chỉ dựa trên microbenchmark. Trước tiên giảm payload và đo production-like workload; maintainability thường đáng giá hơn vài microseconds.

## 🧠 Software Design

### Design 1 — Saga và compensating transaction cho workflow phân tán

**Khái niệm:**
Saga chia một business workflow qua nhiều services/resources thành các local transactions; khi bước sau thất bại, hệ thống thực hiện compensating actions phù hợp thay vì cố giữ một distributed ACID transaction dài.

**Vấn đề nó giải quyết:**
Checkout có thể liên quan Order, Payment và Inventory. Một transaction database duy nhất không thể bao trùm an toàn các service độc lập, còn failure có thể xảy ra sau khi một số side effects đã thành công.

**Ví dụ thực tế:**
Order được tạo → inventory được reserve → payment thất bại. Workflow chuyển Order sang failed và phát lệnh release inventory. Nếu refund/payment có semantics riêng, compensation phải phản ánh business operation chứ không đơn giản là “rollback row”.

**Trade-off:**
Saga cho phép service autonomy và xử lý partial failure mà không cần distributed lock, nhưng tăng state management, eventual consistency, retry/idempotency và observability complexity. Compensation cũng có thể thất bại và cần recovery path.

**Middle → Senior insight:**
Middle cần implement step, retry và idempotent compensation đúng. Senior / Technical phải xác định workflow state machine, irreversible side effects, timeout/recovery policy và cân nhắc liệu một transaction trong Modular Monolith đơn giản hơn có đủ trước khi phân tán workflow.

### Design 2 — Cache-aside với stale tolerance theo business semantics

**Khái niệm:**
Cache-aside để application đọc cache trước, cache miss thì đọc source of truth rồi populate cache. Thiết kế quan trọng không chỉ là TTL mà là xác định dữ liệu nào được phép stale và trong bao lâu.

**Vấn đề nó giải quyết:**
Cache giảm latency/load nhưng tạo thêm một bản sao dữ liệu. Nếu mọi key dùng cùng TTL hoặc invalidate theo kiểu best-effort mà không xét business semantics, hệ thống có thể trả dữ liệu cũ ở nơi hậu quả rất khác nhau.

**Ví dụ thực tế:**
Product description có thể chấp nhận stale vài phút, trong khi authorization entitlement vừa bị revoke có yêu cầu freshness nghiêm ngặt hơn. Hai loại dữ liệu không nên dùng cùng cache policy chỉ vì đều nằm trong Redis.

**Trade-off:**
Cache-aside đơn giản và hiệu quả cho read-heavy workload, nhưng có cache miss, stampede, stale data và invalidation complexity. TTL ngắn tăng source load; TTL dài tăng inconsistency window.

**Middle → Senior insight:**
Middle cần implement key/TTL/invalidation và fallback đúng. Senior / Technical phải phân loại freshness requirement, failure behavior khi Redis/downstream lỗi, ownership của invalidation và quyết định dữ liệu nào không nên cache dù có lợi về latency.

### Design 3 — Build vs Buy cho capability không tạo khác biệt kinh doanh

**Khái niệm:**
Build vs Buy là quyết định kiến trúc về việc tự xây capability hay dùng managed service/product. So sánh phải tính total cost of ownership, lock-in, compliance, integration và operational burden chứ không chỉ license cost.

**Vấn đề nó giải quyết:**
Team thường tự xây vì prototype có vẻ đơn giản, nhưng authentication, search, messaging hoặc observability có nhiều failure modes và maintenance cost xuất hiện sau production. Ngược lại, mua dịch vụ có thể ép hệ thống vào constraints không phù hợp.

**Ví dụ thực tế:**
Thay vì tự xây identity platform cho enterprise app, team đánh giá Microsoft Entra/existing IdP về SSO, MFA, audit, lifecycle và integration. Nếu yêu cầu business chỉ là authentication tiêu chuẩn, tự sở hữu credential/security stack có thể tạo rủi ro lớn hơn giá trị.

**Trade-off:**
Buy rút ngắn delivery và chuyển một phần vận hành cho vendor nhưng tạo recurring cost, dependency và migration/lock-in risk. Build cho control cao hơn nhưng team phải sở hữu security, upgrades, reliability, support và roadmap lâu dài.

**Middle → Senior insight:**
Middle cần tích hợp product/service đúng contract và hiểu constraints. Senior / Technical phải lượng hóa lifecycle cost, exit strategy, SLA, compliance, data ownership và strategic differentiation; lựa chọn “ít code hơn” hay “nhiều control hơn” chỉ đúng khi phù hợp constraints thực tế.
