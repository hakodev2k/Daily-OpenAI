# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — `IOptionsMonitor<T>` cho configuration cần thay đổi lúc runtime

**Mẹo:**
Trong ASP.NET Core, phân biệt `IOptions<T>`, `IOptionsSnapshot<T>` và `IOptionsMonitor<T>` theo lifecycle. Với long-lived service cần phản ứng khi configuration provider hỗ trợ reload, `IOptionsMonitor<T>` thường phù hợp hơn việc cache `Value` thủ công lúc startup.

**Tại sao hữu ích:**
`IOptions<T>` về cơ bản cho một giá trị ổn định theo application lifetime; `IOptionsSnapshot<T>` hữu ích cho scoped/request-oriented code; `IOptionsMonitor<T>` có current value và change notification cho singleton/long-lived components. Chọn sai abstraction khiến configuration tưởng đã đổi nhưng process vẫn dùng giá trị cũ.

**Ví dụ:**
Một background worker đọc giới hạn batch từ configuration. Thay vì copy giá trị vào field tại constructor rồi giữ mãi, worker đọc `monitor.CurrentValue.BatchSize`; nếu cần rebuild resource khi cấu hình đổi, đăng ký `OnChange` với cleanup rõ ràng.

**Lưu ý:**
Không phải mọi configuration source đều reload động. Callback cũng có thể chạy nhiều lần và cần thread-safe; đừng dùng hot reload cho secrets hoặc thay đổi đòi hỏi transactional reconfiguration nếu hệ thống không có cơ chế chuyển trạng thái an toàn.

### Tip 2 — Dùng filtered unique index để đưa business invariant xuống database

**Mẹo:**
Khi invariant có thể biểu diễn bằng constraint/index, hãy để database bảo vệ nó thay vì chỉ `SELECT` kiểm tra trước rồi `INSERT`.

**Tại sao hữu ích:**
Hai requests đồng thời có thể cùng vượt qua application-level existence check. Unique constraint/index biến race condition thành một atomic guarantee tại nơi dữ liệu được ghi.

**Ví dụ:**
Hệ thống chỉ cho phép một active subscription cho mỗi customer. Với SQL Server có thể tạo filtered unique index trên `CustomerId` với điều kiện `Status = 'Active'`; application bắt unique violation và chuyển thành domain conflict phù hợp.

**Lưu ý:**
Database constraint phải phản ánh đúng invariant. Nếu điều kiện phụ thuộc nhiều rows/tables hoặc thời gian, index có thể không đủ. Đừng trả raw database exception cho client; map lỗi persistence thành contract nghiệp vụ ổn định.

### Tip 3 — Điều tra pod restart bằng termination reason trước khi sửa probe

**Mẹo:**
Khi Kubernetes pod restart liên tục, kiểm tra `kubectl describe pod`, container last state, exit code, events và resource metrics trước khi tăng probe timeout hoặc restart policy.

**Tại sao hữu ích:**
`CrashLoopBackOff` chỉ mô tả vòng restart, không nói root cause. `OOMKilled`, process exit do configuration, failed startup dependency và liveness probe failure cần cách xử lý hoàn toàn khác nhau.

**Ví dụ:**
API restart sau khi traffic tăng. Events cho thấy container bị `OOMKilled`, memory usage chạm limit; tăng `livenessProbe.failureThreshold` không giải quyết gì. Investigation tiếp tục vào heap/native memory và memory limit/request mới dẫn đến nguyên nhân thực.

**Lưu ý:**
Không tăng resource limits vô điều kiện. Nếu memory leak hoặc unbounded buffering tồn tại, limit lớn hơn chỉ trì hoãn failure. Đồng thời phân biệt startup/readiness/liveness để probe không tự tạo outage.

### Tip 4 — Dùng accessibility tree để debug UI trước khi thêm selector riêng cho test

**Mẹo:**
Khi Playwright hoặc người dùng khó tương tác với control, kiểm tra semantic role, accessible name và label trước khi thêm `data-testid` để né vấn đề.

**Tại sao hữu ích:**
Selector dựa trên role/name vừa gần với cách người dùng và assistive technology nhìn UI, vừa phát hiện markup thiếu semantic. Một button chỉ là `<div onclick>` có thể “test được” bằng CSS selector nhưng vẫn kém accessibility và keyboard navigation.

**Ví dụ:**
Thay vì `page.locator("#btn42")`, form dùng `<button>` với accessible name rõ ràng và test `GetByRole(AriaRole.Button, new() { Name = "Lưu" })`. Nếu locator không tìm thấy, developer kiểm tra semantic markup thay vì thêm ID tùy ý.

**Lưu ý:**
`data-testid` vẫn hợp lý cho element không có semantic identity ổn định. Không thay đổi accessible name chỉ để chiều test; accessibility contract phải phục vụ người dùng trước.

### Tip 5 — Khi AI sửa bug, yêu cầu chứng minh failure trước khi chấp nhận patch

**Mẹo:**
Với AI coding agent, yêu cầu nó xác định reproduction/test failing trước, giải thích root cause dựa trên source hiện tại, rồi tạo minimal patch và chạy lại test liên quan.

**Tại sao hữu ích:**
Agent có thể tạo patch “hợp lý” nhưng sửa sai layer, hallucinate API hoặc làm test pass bằng cách thay assertion. Failure-first workflow tạo evidence chain: bug tồn tại → nguyên nhân → patch → regression test.

**Ví dụ:**
PR báo duplicate order khi webhook retry. Agent trước hết thêm integration test gửi cùng event hai lần và xác nhận có hai records; sau đó sửa idempotency handling. Review tập trung vào invariant và test thay vì tin mô tả của agent.

**Lưu ý:**
Test do AI tạo cũng cần review: nó có thể mock mất chính failure path hoặc assert implementation detail. Luôn kiểm tra diff, dependency versions, generated SQL/API behavior và security impact khi có liên quan.

## 🧠 Software Design

### Design 1 — Idempotent Consumer cho at-least-once delivery

**Khái niệm:**
Trong message broker có at-least-once delivery, consumer phải giả định cùng một logical message có thể được xử lý nhiều lần. Idempotent Consumer thiết kế side effects để duplicate delivery không tạo duplicate business outcome.

**Vấn đề nó giải quyết:**
Consumer có thể commit database rồi crash trước khi broker nhận acknowledgement. Message được redeliver dù business write trước đã thành công; nếu handler luôn `INSERT` hoặc charge payment lần nữa, retry biến thành corruption.

**Ví dụ thực tế:**
Payment event có stable `MessageId`. Consumer lưu processed ID cùng transaction với business update hoặc dùng business-level unique key. Redelivery gặp record đã xử lý thì acknowledge mà không lặp side effect.

**Trade-off:**
Deduplication tăng storage, lookup và cleanup complexity; giữ mọi message ID vô hạn không thực tế. Business-key idempotency thường mạnh hơn transport ID nhưng cần hiểu domain semantics chính xác.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là behavior bình thường, không phải broker bug. Senior / Technical developer phải chọn idempotency boundary, atomicity giữa dedupe và business write, retention strategy và cách xử lý external side effects không nằm trong local transaction.

### Design 2 — Dependency Inversion không đồng nghĩa interface cho mọi class

**Khái niệm:**
Dependency Inversion hướng high-level policy phụ thuộc vào abstraction ổn định thay vì volatile implementation detail. Nó không yêu cầu tạo `IFoo` cho từng `Foo` bất kể có boundary hay variation thực tế hay không.

**Vấn đề nó giải quyết:**
Business logic bị gắn trực tiếp vào SMTP SDK, payment provider hoặc filesystem khó thay đổi/test và làm infrastructure concerns lan vào domain/application layer. Abstraction đặt đúng boundary giữ policy độc lập với mechanism.

**Ví dụ thực tế:**
Checkout phụ thuộc `IPaymentGateway` mô tả capability nghiệp vụ; adapter Stripe triển khai interface đó. Ngược lại, một pure deterministic `PriceCalculator` không cần `IPriceCalculator` chỉ để mock nếu không có volatility/boundary đáng kể.

**Trade-off:**
Abstraction đúng chỗ giảm coupling và hỗ trợ substitution; abstraction vô nghĩa tăng files, indirection và làm navigation/refactoring khó hơn. Interface phản chiếu nguyên xi implementation thường không tạo architectural value.

**Middle → Senior insight:**
Middle developer cần inject external dependencies thay vì hard-code infrastructure. Senior / Technical developer phải nhận diện axis of change và ownership boundary, rồi chỉ tạo abstraction nơi nó bảo vệ policy hoặc cho phép alternative có ý nghĩa.

### Design 3 — Graceful degradation cho dependency không critical

**Khái niệm:**
Graceful degradation cho phép hệ thống giữ core capability khi dependency phụ trợ lỗi, bằng cách giảm chức năng có kiểm soát thay vì biến partial failure thành total outage.

**Vấn đề nó giải quyết:**
Một product page có thể phụ thuộc recommendation, review và analytics services. Nếu mọi dependency đều bắt buộc thành công trước khi trả trang, một service phụ trợ lỗi có thể kéo toàn bộ customer journey xuống.

**Ví dụ thực tế:**
Product API coi catalog/price là critical nhưng recommendation là optional. Khi recommendation timeout, response vẫn trả product chính, ghi telemetry và bỏ section recommendation; UI render fallback state thay vì trả 500 toàn trang.

**Trade-off:**
Degradation tăng availability nhưng tạo nhiều runtime modes, UX states và observability requirements. Không được degrade silently với capability critical như authorization, payment correctness hoặc data integrity.

**Middle → Senior insight:**
Middle developer cần phân biệt optional/required dependency và implement fallback rõ ràng. Senior / Technical developer phải xác định business criticality, latency budget, stale/fallback policy, telemetry và bảo đảm degradation không vô tình bypass security hay correctness invariant.
