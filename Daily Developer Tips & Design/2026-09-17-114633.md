# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — `ArrayPool<T>` chỉ đáng dùng khi allocation thực sự là bottleneck

**Mẹo:**
Với buffer tạm thời lớn và được tạo liên tục trên hot path, cân nhắc `ArrayPool<T>.Shared` để tái sử dụng array thay vì cấp phát mới mỗi lần; nhưng chỉ sau khi profiler cho thấy allocation/GC pressure đáng kể.

**Tại sao hữu ích:**
Array lớn hoặc allocation tần suất cao làm tăng GC work và có thể đẩy object vào Large Object Heap. Pooling giảm allocation rate, nhưng đổi lại application phải quản lý lifecycle buffer chính xác.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, buffer.Length), ct);
    await ProcessAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```
Dùng `dotnet-counters`, profiler hoặc allocation trace để xác nhận tác động trước/sau.

**Lưu ý:**
Array được `Rent` có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Không giữ reference sau khi `Return`; với dữ liệu nhạy cảm, cân nhắc clearing phù hợp dù có thêm cost.

### Tip 2 — EF Core query translation phải được kiểm tra trước khi kéo logic về memory

**Mẹo:**
Khi LINQ phức tạp không translate như mong muốn, inspect generated SQL và tách expression hợp lý; đừng chữa bằng `AsEnumerable()` quá sớm rồi vô tình tải cả dataset về application.

**Tại sao hữu ích:**
`IQueryable` cho provider xây SQL để filter/aggregate ở database. Chuyển sang LINQ-to-Objects trước predicate quan trọng khiến database không còn giảm dữ liệu, tăng network, memory và latency.

**Ví dụ:**
```csharp
var query = db.Orders
    .Where(o => o.CreatedAt >= from && o.Status == OrderStatus.Paid)
    .Select(o => new { o.Id, o.Total });

var sql = query.ToQueryString();
```
Nếu cần xử lý C# không translate được, trước hết project/filter tối đa ở SQL rồi mới xử lý phần nhỏ còn lại trong memory.

**Lưu ý:**
SQL translate được chưa chắc SQL tốt. Kiểm tra execution plan và row count cho query quan trọng; đừng tối ưu dựa trên LINQ nhìn “gọn”.

### Tip 3 — Service Bus lock renewal không sửa được handler không bounded

**Mẹo:**
Nếu Azure Service Bus handler thường xuyên vượt `LockDuration`, điều tra processing time và chia nhỏ workload trước khi chỉ tăng auto lock renewal.

**Tại sao hữu ích:**
PeekLock là lease tạm thời. Handler chạy quá lâu có thể mất lock, message được giao lại và cùng business operation chạy lần nữa. Auto-renew kéo dài lease nhưng không giải quyết downstream call treo, unbounded batch hoặc handler thiếu timeout.

**Ví dụ:**
```text
Symptom: duplicate processing + MessageLockLostException
Evidence: handler p95 = 70s, lock = 60s
Hypothesis: processing vượt lease
Diagnosis: một external API đôi khi mất 50s
Solution: đặt timeout, idempotency, giảm work trong handler; sau đó mới tune lock renewal
```

**Lưu ý:**
Ngay cả khi renewal tốt, at-least-once delivery vẫn cho phép duplicate. Consumer phải idempotent theo business identity; lock không phải exactly-once guarantee.

### Tip 4 — `Content-Security-Policy` giảm blast radius của XSS

**Mẹo:**
Với web application, dùng CSP như một defense-in-depth layer để hạn chế script/resource origins và giảm khả năng injected markup thực thi arbitrary JavaScript.

**Tại sao hữu ích:**
Output encoding và framework escaping vẫn là defense chính, nhưng một XSS bug lọt qua có thể bị CSP chặn hoặc hạn chế nếu policy không cho inline script/eval và chỉ trust nguồn cần thiết.

**Ví dụ:**
```text
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://trusted-cdn.example;
  object-src 'none';
  base-uri 'self';
```
Triển khai `Content-Security-Policy-Report-Only` trước để quan sát violations rồi tighten policy.

**Lưu ý:**
Policy chứa rộng `'unsafe-inline'` hoặc `*` có thể làm mất phần lớn giá trị. CSP không thay thế encode/sanitize input-output và cần test kỹ với third-party scripts, CMS/editor và analytics.

### Tip 5 — Optimizely content model cần tách editorial shape khỏi integration DTO

**Mẹo:**
Đừng dùng trực tiếp DTO của ERP/PIM/third-party API làm CMS content type. Tạo content model phục vụ editor experience và mapping tại integration boundary.

**Tại sao hữu ích:**
External contract thay đổi theo provider, còn CMS model cần ổn định theo cách editor tạo và preview nội dung. Ghép hai model khiến API rename field có thể kéo theo migration content, UI editor khó hiểu và coupling lan vào rendering.

**Ví dụ:**
```text
PIM DTO: product_title, merchandising_copy_v2, supplier_code
CMS block: Heading, Intro, ProductReference
Mapper: PIM/Catalog data -> view model/rendering model
```
CMS chỉ lưu reference khi dữ liệu sản phẩm thuộc ownership của commerce/PIM.

**Lưu ý:**
Không duplicate toàn bộ product data vào CMS nếu không có ownership/lifecycle rõ ràng. Cần xác định source of truth, cache strategy và behavior khi integration unavailable.

## 🧠 Software Design

### Design 1 — Timeout budget phải được phân bổ xuyên dependency chain

**Khái niệm:**
Timeout không nên được đặt độc lập ở từng HTTP/database call. Request có một latency budget tổng; mỗi dependency cần budget nhỏ hơn và phải chừa thời gian cho application xử lý, retry có kiểm soát và response.

**Vấn đề nó giải quyết:**
API gateway timeout 5 giây nhưng service gọi ba dependencies, mỗi dependency timeout 10 giây. Khi dependency đầu treo, caller đã bỏ request trong khi backend vẫn giữ connection/thread/resource và tiếp tục work vô ích.

**Ví dụ thực tế:**
Checkout có budget 2 giây. Pricing được cấp 400 ms, inventory 500 ms, payment authorization 700 ms, phần còn lại dành cho local processing và network variance. Cancellation từ inbound request được propagate xuống EF Core/HttpClient khi phù hợp.

**Trade-off:**
Budget ngắn giúp fail fast và bảo vệ capacity nhưng có thể tăng false timeout với dependency có latency variance cao. Budget dài tăng success chance cho slow call nhưng giữ resource lâu và làm cascading latency nặng hơn.

**Middle → Senior insight:**
Middle developer cần phân biệt timeout với cancellation và propagate token đúng. Senior / Technical developer phải xây latency budget từ user SLO, dependency percentiles, retry policy và fallback semantics thay vì chọn con số tùy ý cho từng client.

### Design 2 — Bounded Context quan trọng hơn việc chia project theo entity

**Khái niệm:**
Trong DDD, Bounded Context tạo boundary nơi một domain model và ubiquitous language có nghĩa nhất quán. Nó không đơn giản là tạo một service/project cho mỗi bảng hoặc entity.

**Vấn đề nó giải quyết:**
`Customer` trong Sales có thể mang nghĩa lead/account/contact, trong Billing lại là legal payer. Ép cả tổ chức dùng một mega `Customer` model tạo coupling và field/invariant mâu thuẫn giữa capabilities.

**Ví dụ thực tế:**
Sales context sở hữu sales profile và pipeline; Billing context sở hữu billing account, tax identity và payment terms. Hai context tích hợp qua explicit contract thay vì cùng sửa một shared entity library/database model.

**Trade-off:**
Boundary đúng tăng autonomy và model clarity nhưng tạo mapping, integration và duplicated representations. Chia context quá nhỏ lại tăng operational/team overhead và biến modular design thành distributed monolith.

**Middle → Senior insight:**
Middle developer cần giữ business rules trong đúng module/context. Senior / Technical developer phải tìm boundary từ language, invariants, change cadence, ownership và transaction needs; deployment boundary có thể đến sau domain boundary.

### Design 3 — Testing Pyramid phải phản ánh risk, không phải quota test cố định

**Khái niệm:**
Testing Pyramid khuyến khích nhiều test nhanh ở tầng thấp và ít test end-to-end đắt hơn, nhưng tỷ lệ cụ thể phải theo loại rủi ro và kiến trúc thay vì áp một con số chuẩn cho mọi hệ thống.

**Vấn đề nó giải quyết:**
Một team có 90% unit tests với mocks nhưng production bug nằm ở EF mappings, serialization, authentication và browser/API integration. Test suite nhanh nhưng không kiểm chứng các boundary nơi failure thực sự xảy ra.

**Ví dụ thực tế:**
Pricing calculation thuần domain có nhiều unit tests. Repository/query quan trọng dùng database integration tests. API authentication/serialization có integration tests qua real host. Một số checkout journeys quan trọng được bảo vệ bằng Playwright E2E.

**Trade-off:**
Unit tests nhanh, localize failure tốt nhưng không phát hiện integration mismatch. Integration/E2E tăng confidence ở boundary thật nhưng chậm hơn, cần infrastructure/test data và dễ flaky nếu thiết kế kém.

**Middle → Senior insight:**
Middle developer cần chọn test double đúng và giữ test deterministic. Senior / Technical developer phải lập test portfolio theo failure cost, boundary risk và feedback speed; coverage percentage chỉ là signal phụ, không phải mục tiêu kiến trúc test.
