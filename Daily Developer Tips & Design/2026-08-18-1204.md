# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Sử dụng `IAsyncEnumerable<T>` cho dữ liệu lớn

**Mẹo:** Stream dữ liệu thay vì load toàn bộ collection vào memory.

**Tại sao hữu ích:** Giảm memory usage và cải thiện khả năng xử lý batch.

**Ví dụ:**
```csharp
await foreach (var item in GetItemsAsync()) Process(item);
```

**Lưu ý:** Không phù hợp khi cần xử lý toàn bộ dataset trong một transaction.

### Tip 2 — Dùng `AsNoTracking()` cho EF Core query chỉ đọc

**Mẹo:** Tắt tracking khi entity không cần update.

**Tại sao hữu ích:** Giảm overhead trong read-heavy workload.

**Ví dụ:**
```csharp
var data = await db.Users.AsNoTracking().ToListAsync();
```

**Lưu ý:** Không dùng nếu cần thay đổi entity sau query.

### Tip 3 — Dùng Correlation ID khi debug production

**Mẹo:** Trace request qua nhiều service bằng một identifier.

**Tại sao hữu ích:** Giúp tìm root cause trong distributed system.

**Ví dụ:**
```http
X-Correlation-ID: abc-123
```

**Lưu ý:** Không ghi dữ liệu nhạy cảm vào ID.

### Tip 4 — Kiểm tra SQL execution plan trước khi thêm index

**Mẹo:** Dựa trên execution plan để tối ưu query.

**Tại sao hữu ích:** Tránh index dư thừa và tối ưu đúng bottleneck.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
```

**Lưu ý:** Test với dữ liệu gần production.

### Tip 5 — Sử dụng `git bisect` tìm regression

**Mẹo:** Binary search trong Git history để tìm commit lỗi.

**Tại sao hữu ích:** Tiết kiệm thời gian debug.

**Ví dụ:**
```bash
git bisect start
```

**Lưu ý:** Cần tiêu chí xác định good/bad commit.

## 🧠 Software Design

### Design 1 — Transaction Boundary Design

**Khái niệm:** Xác định phạm vi dữ liệu phải thay đổi cùng nhau.

**Vấn đề nó giải quyết:** Tránh transaction quá lớn và coupling cao.

**Ví dụ thực tế:** Order và OrderItem cùng transaction, gửi email xử lý async.

**Trade-off:** Tăng scalability nhưng cần retry và eventual consistency.

**Middle → Senior insight:** Senior quyết định boundary dựa trên business invariant.

### Design 2 — Modular Monolith

**Khái niệm:** Chia monolith thành module có boundary rõ ràng.

**Vấn đề nó giải quyết:** Giảm complexity trước khi dùng microservices.

**Ví dụ thực tế:** Billing, Identity, Notification là các module độc lập.

**Trade-off:** Đơn giản deployment nhưng cần kiểm soát dependency.

**Middle → Senior insight:** Boundary quan trọng hơn việc tách service sớm.

### Design 3 — Idempotency trong API Design

**Khái niệm:** Request lặp lại vẫn tạo cùng kết quả cuối.

**Vấn đề nó giải quyết:** Xử lý retry an toàn trong distributed system.

**Ví dụ thực tế:** Payment API dùng `Idempotency-Key`.

**Trade-off:** Tăng reliability nhưng cần lưu trạng thái request.

**Middle → Senior insight:** Xác định workflow nào bắt buộc cần idempotency.
