# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `await using` khi resource cần cleanup bất đồng bộ

**Mẹo:**
Nếu một resource implement `IAsyncDisposable`, ưu tiên `await using` để cleanup có thể thực hiện I/O bất đồng bộ thay vì ép cleanup chạy synchronous trong request hoặc worker path.

**Tại sao hữu ích:**
Một số resource phải flush buffer, gửi frame cuối, đóng transaction hoặc giải phóng connection qua I/O. `DisposeAsync()` cho phép hoàn tất phần cleanup đó mà không block thread hiện tại, đặc biệt hữu ích trong server workload có concurrency cao.

**Ví dụ:**
```csharp
await using var stream = await blobClient.OpenWriteAsync(
    overwrite: true,
    cancellationToken: ct);

await JsonSerializer.SerializeAsync(stream, payload, cancellationToken: ct);
```

Khi ra khỏi scope, `DisposeAsync()` được await trước khi method hoàn tất.

**Lưu ý:**
Không phải resource nào cũng cần async disposal. Nếu cleanup chỉ giải phóng memory/native handle nhanh, `IDisposable` là đủ. Cũng cần tránh giữ resource sống quá lâu chỉ vì `await using` tiện; lifetime vẫn phải bám theo transaction/request boundary hợp lý.

### Tip 2 — Gắn `TagWith` vào EF Core query để nối production trace với SQL dễ hơn

**Mẹo:**
Với các query quan trọng hoặc khó truy vết, dùng `TagWith()` để thêm comment nhận diện use case vào SQL mà EF Core phát sinh. Khi xem database activity, Query Store hoặc slow-query capture, bạn có thêm context để biết câu SQL đến từ code path nào.

**Tại sao hữu ích:**
Production thường có nhiều LINQ query sinh SQL khá giống nhau. Chỉ nhìn câu SQL có thể khó biết request, handler hoặc feature nào tạo ra nó. Một tag ngắn, ổn định giúp rút ngắn bước mapping từ database symptom về application code.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .TagWith("Checkout:GetPendingOrders")
    .Where(x => x.CustomerId == customerId && x.Status == OrderStatus.Pending)
    .Select(x => new { x.Id, x.Total })
    .ToListAsync(ct);
```

SQL phát sinh sẽ chứa comment tương ứng, giúp DBA/developer nhận diện source nhanh hơn khi điều tra latency.

**Lưu ý:**
Đừng đưa `userId`, email, token hoặc dữ liệu nhạy cảm vào tag. Tag cũng không thay thế distributed tracing hay metrics; nó chỉ là một mảnh evidence bổ sung. Nếu tag thay đổi theo từng request, bạn còn có thể làm Query Store/plan analysis khó đọc hơn.

### Tip 3 — Trong Elasticsearch, phân biệt `text` và `keyword` ngay từ lúc thiết kế mapping

**Mẹo:**
Dùng `text` cho full-text search cần analyzer/tokenization; dùng `keyword` cho exact match, filter, sorting và aggregation. Với field cần cả hai mục đích, dùng multi-field thay vì cố dùng một mapping cho mọi query.

**Tại sao hữu ích:**
Một field `productName` được map chỉ là `text` có thể search tốt nhưng không phù hợp để sort/aggregate chính xác. Ngược lại, `keyword` giữ nguyên toàn bộ chuỗi và không tạo token, nên query full-text kiểu người dùng nhập từ khóa sẽ kém hiệu quả.

**Ví dụ:**
```json
"productName": {
  "type": "text",
  "fields": {
    "raw": {
      "type": "keyword"
    }
  }
}
```

Search dùng `productName`; sort hoặc aggregation dùng `productName.raw`.

**Lưu ý:**
Mapping sai không phải lúc nào sửa tại chỗ được; nhiều thay đổi cần tạo index mới rồi reindex. Vì vậy mapping nên dựa trên query pattern thực tế. Tránh tạo quá nhiều multi-fields vì mỗi field làm index lớn hơn và tăng chi phí ingest/storage.

### Tip 4 — Log production phải redact secret trước khi dữ liệu rời process

**Mẹo:**
Thiết kế logging để password, bearer token, refresh token, connection string, API key và dữ liệu nhạy cảm bị loại bỏ hoặc mask trước khi log được gửi tới Application Insights, Elasticsearch hay SIEM.

**Tại sao hữu ích:**
Log thường được lưu lâu, replicate qua nhiều hệ thống và có phạm vi người đọc rộng hơn database production. Một exception hoặc object dump vô tình chứa `Authorization` header có thể biến hệ thống observability thành nơi rò credential.

**Ví dụ:**
```text
Không an toàn:
Request failed: Authorization=Bearer eyJhbGciOi...

An toàn hơn:
Request failed: authScheme=Bearer, tokenPresent=true, correlationId=abc-123
```

Với HTTP logging middleware, chỉ allow-list header cần thiết thay vì log toàn bộ request/response mặc định.

**Lưu ý:**
Mask sau khi log đã được export là quá muộn. Structured logging cũng không tự động an toàn; nếu object chứa PII/secret, serializer vẫn có thể ghi hết. Cần policy rõ cho field nào được phép log và test những code path dễ lộ dữ liệu như exception, third-party error và request diagnostics.

### Tip 5 — Dùng hashed asset filename để browser cache JavaScript/CSS lâu mà vẫn deploy an toàn

**Mẹo:**
Với frontend production build, tạo filename chứa content hash như `app.8f3c1a.js` rồi trả `Cache-Control` dài hạn cho asset immutable. Khi content thay đổi, filename mới tự tạo cache key mới.

**Tại sao hữu ích:**
Nếu deploy vẫn dùng `app.js` nhưng browser/CDN cache lâu, user có thể chạy JavaScript cũ với HTML/API contract mới. Content hash cho phép cache mạnh mà không phải purge mọi asset mỗi lần release.

**Ví dụ:**
```text
index.html
Cache-Control: no-cache

/assets/app.8f3c1a.js
Cache-Control: public, max-age=31536000, immutable

/assets/site.2a91de.css
Cache-Control: public, max-age=31536000, immutable
```

HTML được revalidate để trỏ tới asset hash mới; asset cũ có thể tiếp tục cache an toàn vì tên file không đổi nội dung.

**Lưu ý:**
Chỉ đặt `immutable` khi URL thực sự thay đổi theo content. Đừng áp dụng cùng policy cho HTML hoặc JSON runtime config thường xuyên thay đổi. Nếu CDN rewrite URL hoặc build pipeline không tạo hash ổn định, cache policy này có thể làm rollback/debug khó hơn.

## 🧠 Software Design

### Design 1 — Vertical Slice Architecture giảm coupling theo use case, nhưng không loại bỏ nhu cầu boundary rõ

**Khái niệm:**
Vertical Slice Architecture tổ chức code theo feature/use case như `CreateOrder`, `CancelOrder`, `GetOrderDetails` thay vì gom toàn bộ controller, service và repository theo layer kỹ thuật. Mỗi slice chứa phần application logic cần thiết cho một flow cụ thể.

**Vấn đề nó giải quyết:**
Trong codebase layer-first lớn, một thay đổi nhỏ có thể phải sửa controller, service, mapping, repository và nhiều shared abstraction dù feature không liên quan tới phần còn lại. Vertical slice giúp code thay đổi cùng nhau nằm gần nhau và giảm coupling giữa các use case.

**Ví dụ thực tế:**
```text
Features/
  Orders/
    CreateOrder/
      Endpoint.cs
      Command.cs
      Handler.cs
      Validator.cs
    GetOrderDetails/
      Endpoint.cs
      Query.cs
      Handler.cs
```

Shared domain/infrastructure vẫn có thể tồn tại, nhưng slice không cần phụ thuộc vào một “God service” dùng chung cho mọi feature.

**Trade-off:**
Vertical slice tăng locality và autonomy nhưng có thể tạo duplication nhỏ giữa use case. Nếu team cố DRY mọi dòng code bằng shared abstraction, lợi ích của slice lại mất. Ngược lại, nếu không có domain boundary, slice có thể biến thành nhiều folder độc lập nhưng vẫn cùng thao tác trực tiếp vào mọi thứ.

**Middle → Senior insight:**
Middle developer cần biết tổ chức use case để dependency của từng flow dễ hiểu và test. Senior / Technical developer phải quyết định phần nào nên shared, phần nào nên duplicate có chủ đích, và cách giữ domain/infrastructure boundary mà không quay lại layered architecture quá nặng.

### Design 2 — Change Data Capture phù hợp khi nhiều read model cần bám theo database nhưng application event chưa đủ tin cậy

**Khái niệm:**
Change Data Capture (CDC) đọc thay đổi từ transaction log hoặc cơ chế database tương đương rồi chuyển chúng thành stream thay đổi cho downstream như search index, analytics hoặc integration pipeline.

**Vấn đề nó giải quyết:**
Một hệ thống legacy ghi trực tiếp nhiều chỗ vào SQL Server nhưng không phát domain event nhất quán. Elasticsearch hoặc data warehouse cần đồng bộ thay đổi mà không muốn polling toàn bảng hoặc sửa ngay mọi write path cũ.

**Ví dụ thực tế:**
```text
SQL Server
  -> transaction log / CDC
  -> connector
  -> event stream
  -> Search Indexer
  -> Elasticsearch
```

Indexer lưu checkpoint và xử lý insert/update/delete theo thứ tự phù hợp với partition/key.

**Trade-off:**
CDC giảm nhu cầu sửa từng application writer và thường bắt change đáng tin cậy hơn polling, nhưng event tạo ra mang semantics dữ liệu thấp hơn domain event. Consumer phải hiểu schema database, migration có thể ảnh hưởng stream, và delete/reorder/replay cần được thiết kế cẩn thận.

**Middle → Senior insight:**
Middle developer cần hiểu CDC không tự biến database row change thành business event. Senior / Solution-oriented engineer phải chọn giữa domain event, Outbox, CDC hoặc kết hợp chúng dựa trên ownership write path, semantic richness, legacy constraints, replay requirement và operational tooling.

### Design 3 — Load Shedding giúp hệ thống giữ phần traffic quan trọng khi đã vượt capacity

**Khái niệm:**
Load Shedding chủ động từ chối, trì hoãn hoặc giảm chất lượng một phần workload khi hệ thống gần hoặc đã vượt capacity, thay vì cố nhận tất cả request rồi cùng nhau timeout.

**Vấn đề nó giải quyết:**
Một API chịu được khoảng 2.000 request/s nhưng traffic đột ngột tăng lên 8.000 request/s. Nếu mọi request đều vào queue, connection pool và thread/concurrency slot có thể bị chiếm hết; latency tăng từ 200 ms lên 30 giây và cuối cùng cả request quan trọng cũng fail.

**Ví dụ thực tế:**
```text
Capacity pressure tăng
-> từ chối endpoint search không critical bằng 429/503
-> giữ budget riêng cho checkout/payment
-> vô hiệu hóa recommendation phụ
-> giảm fan-out tới downstream optional
-> phục hồi dần khi queue/latency quay về ngưỡng an toàn
```

Load shedding có thể kết hợp rate limit, queue bound, concurrency limit và priority class.

**Trade-off:**
Chủ động bỏ traffic làm giảm availability bề mặt nhưng có thể tăng availability cho chức năng cốt lõi. Nếu threshold quá thấp, hệ thống từ chối traffic dù vẫn còn capacity; quá cao thì shedding đến quá muộn. Business priority và retry behavior của client cũng phải được tính vào.

**Middle → Senior insight:**
Middle developer cần hiểu overload không nên được giải quyết bằng queue vô hạn hoặc retry vô hạn. Senior / Technical developer phải xác định capacity signal, priority, rejection semantics, client backoff và SLO để hệ thống degrade có kiểm soát thay vì collapse đồng loạt.
