# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Với `AddDbContextPool`, đừng để state theo request rò sang request khác

**Mẹo:**
Khi dùng EF Core `AddDbContextPool`, coi `DbContext` như một object được tái sử dụng giữa nhiều request. Không lưu tenant ID, user ID hoặc state thay đổi theo request trực tiếp trong field/property của context nếu state đó không được reset an toàn trước khi context quay lại pool.

**Tại sao hữu ích:**
`DbContext` pooling giảm allocation và chi phí khởi tạo context, nhưng instance có thể được dùng lại cho request khác sau khi EF Core reset internal state. State tùy biến do application tự thêm không tự động được EF Core hiểu và làm sạch, nên một giá trị tenant cũ có thể vô tình ảnh hưởng query của request kế tiếp.

**Ví dụ:**
Tránh thiết kế kiểu:
```csharp
public sealed class AppDbContext : DbContext
{
    public string? CurrentTenantId { get; set; }
}
```

rồi set `CurrentTenantId` theo request và giả định context mới luôn được tạo.

Với multi-tenant filter, ưu tiên đưa tenant context qua abstraction scoped rõ ràng hoặc factory thiết lập state có kiểm soát trước mỗi lần sử dụng.

**Lưu ý:**
Pooling không phải lúc nào cũng cần thiết. Nếu application chưa có evidence rằng việc tạo `DbContext` là bottleneck, `AddDbContext` thông thường đơn giản và ít rủi ro hơn. Đừng đánh đổi isolation chỉ để lấy micro-optimization chưa được đo.

### Tip 2 — Khi gặp SQL deadlock, đọc deadlock graph thay vì chỉ tăng retry

**Mẹo:**
Nếu SQL Server báo deadlock, thu thập deadlock graph bằng Extended Events hoặc tooling tương đương, xác định hai transaction đang giữ/chờ resource nào, rồi sửa access order hoặc transaction scope trước khi chỉ tăng số lần retry.

**Tại sao hữu ích:**
Retry có thể che symptom nhưng không loại bỏ root cause. Deadlock thường xảy ra khi hai transaction acquire lock theo thứ tự ngược nhau hoặc giữ transaction quá lâu. Deadlock graph cho evidence cụ thể về victim, lock mode, statement và resource đang cạnh tranh.

**Ví dụ:**
```text
Transaction A:
1. UPDATE Orders
2. UPDATE Inventory

Transaction B:
1. UPDATE Inventory
2. UPDATE Orders
```

Nếu hai transaction chạy đồng thời, mỗi bên có thể giữ một lock và chờ lock còn lại. Chuẩn hóa thứ tự access thành `Orders -> Inventory` ở cả hai luồng thường đáng xem xét hơn việc tăng retry vô hạn.

**Lưu ý:**
Không phải mọi blocking đều là deadlock. Blocking dài cần điều tra transaction duration, isolation level, index và query plan riêng. Retry deadlock vẫn hữu ích vì deadlock có thể xảy ra ngẫu nhiên, nhưng retry nên có giới hạn và operation phải an toàn khi thực thi lại.

### Tip 3 — JWT phải được validate, không phải chỉ decode để đọc claims

**Mẹo:**
Khi nhận JWT, luôn để authentication middleware/library xác minh signature, `issuer`, `audience`, thời hạn và các validation parameter cần thiết trước khi tin vào claims. Decode Base64 payload chỉ giúp đọc dữ liệu, không chứng minh token hợp lệ.

**Tại sao hữu ích:**
JWT payload không được mã hóa mặc định và bất kỳ ai cũng có thể tạo một chuỗi JWT nhìn hợp lệ về mặt cấu trúc. Nếu backend chỉ decode rồi tin vào `sub`, `role` hoặc `tenantId`, attacker có thể tự tạo claims giả mà không cần private key của issuer.

**Ví dụ:**
```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://login.example.com/";
        options.Audience = "orders-api";
    });
```

Sau khi middleware xác thực token thành công, authorization policy mới nên dùng claims để quyết định quyền truy cập.

**Lưu ý:**
Đừng tắt `ValidateAudience` hoặc `ValidateIssuer` chỉ để “cho token chạy được” nếu chưa hiểu trust boundary. Clock skew quá lớn cũng có thể kéo dài hiệu lực token ngoài mong muốn. Với nhiều issuer/tenant, validation phải phản ánh đúng security model thay vì chấp nhận mọi token cùng format.

### Tip 4 — Trong CMS/CDN, invalidate theo cache tag thay vì purge toàn bộ site

**Mẹo:**
Khi một content item thay đổi, nếu platform hỗ trợ cache tag/surrogate key, gắn response với logical dependency như `content:123` hoặc `category:news` rồi invalidate đúng nhóm liên quan thay vì purge toàn bộ CDN/cache.

**Tại sao hữu ích:**
Purge toàn site làm cache hit ratio rơi mạnh và có thể tạo traffic spike về origin. Tag-based invalidation giữ phần lớn nội dung nóng trong cache nhưng vẫn cho phép cập nhật đúng những page phụ thuộc vào content vừa publish.

**Ví dụ:**
```text
/article/abc
Tags: content:123, category:engineering

/home
Tags: homepage, category:engineering
```

Khi `content:123` được publish lại, chỉ purge các response mang tag đó. Nếu category listing thay đổi, purge thêm `category:engineering` theo dependency thực tế.

**Lưu ý:**
Cache tag chỉ hiệu quả nếu dependency graph chính xác. Gắn tag quá rộng sẽ gần giống purge toàn bộ; gắn thiếu tag lại tạo stale content. Với CMS có publish workflow, cần phân biệt draft, preview và public cache để không làm lộ nội dung chưa publish.

### Tip 5 — Dùng browser DevTools waterfall để tìm duplicate fetch trước khi tối ưu frontend code

**Mẹo:**
Khi một page load chậm hoặc gọi API nhiều hơn dự kiến, mở Network panel và kiểm tra waterfall, Initiator, request timing và cache status trước khi refactor component hoặc thêm memoization.

**Tại sao hữu ích:**
Duplicate fetch thường đến từ lifecycle chạy lại, watcher phụ thuộc sai, route transition hoặc component mount nhiều lần. Waterfall cho thấy request nào bắt đầu lúc nào và script nào khởi tạo nó, giúp đi từ symptom → evidence thay vì đoán state management bị lỗi.

**Ví dụ:**
```text
GET /api/products?id=42   200   180 ms   Initiator: ProductView.vue:74
GET /api/products?id=42   200   175 ms   Initiator: useProduct.ts:31
```

Hai request cùng resource xuất phát từ hai đường code khác nhau cho thấy cần hợp nhất ownership của data fetching hơn là chỉ tăng cache ở backend.

**Lưu ý:**
Không phải request trùng nào cũng sai: prefetch, revalidation hoặc retry có thể có chủ đích. Khi debug, tắt cache trong DevTools chỉ để phân tích có thể làm behavior khác production, nên cần xác nhận lại với cache hoạt động bình thường.

## 🧠 Software Design

### Design 1 — Saga cho workflow nhiều service khi không thể có một transaction ACID duy nhất

**Khái niệm:**
Saga chia một business workflow dài thành nhiều local transaction. Mỗi bước commit trong service của nó; nếu bước sau thất bại, hệ thống thực hiện compensating action hoặc chuyển workflow sang trạng thái cần xử lý thay vì cố giữ distributed database transaction xuyên mọi service.

**Vấn đề nó giải quyết:**
Một order có thể cần giữ inventory, authorize payment và tạo shipment ở ba hệ thống khác nhau. Không có một database transaction đơn giản nào bao phủ an toàn cả SQL database, payment provider và shipping API. Nếu bước thứ ba fail sau khi hai bước đầu đã thành công, hệ thống cần một recovery model rõ ràng.

**Ví dụ thực tế:**
```text
1. Reserve inventory        -> success
2. Authorize payment        -> success
3. Create shipment          -> fail
4. Compensation:
   - release inventory
   - void payment authorization
5. Order -> FulfillmentFailed
```

Saga có thể được orchestrated bởi một coordinator hoặc choreographed qua events, tùy mức độ coupling và observability cần thiết.

**Trade-off:**
Saga tăng khả năng xử lý partial failure nhưng đổi ACID transaction thành eventual consistency và thêm state machine, retry, idempotency, compensation cùng observability. Compensation cũng không phải lúc nào hoàn tác được hoàn toàn; gửi email hoặc gọi external provider có thể chỉ có “semantic undo”.

**Middle → Senior insight:**
Middle developer cần hiểu mỗi step phải idempotent và failure không đồng nghĩa rollback tự động toàn workflow. Senior / Technical developer phải chọn orchestration hay choreography, định nghĩa compensation semantics, timeout, manual recovery và business state khi recovery chỉ thành công một phần.

### Design 2 — Hexagonal Architecture chỉ có giá trị khi ports bảo vệ boundary thực sự biến động

**Khái niệm:**
Hexagonal Architecture đặt business logic phía trong và giao tiếp với database, HTTP client, message broker hoặc UI thông qua ports/adapters. Giá trị chính là cô lập dependency volatility và giữ domain/application logic không bị kéo theo chi tiết infrastructure.

**Vấn đề nó giải quyết:**
Nếu business rule tính giá phụ thuộc trực tiếp vào SDK của payment provider, EF Core type hoặc controller model, đổi provider hay test logic sẽ kéo theo nhiều infrastructure concern. Một port nhỏ ở boundary đúng chỗ giúp business code phụ thuộc vào capability thay vì vendor detail.

**Ví dụ thực tế:**
```csharp
public interface IExchangeRateProvider
{
    Task<decimal> GetRateAsync(
        string from,
        string to,
        CancellationToken ct);
}
```

Application service phụ thuộc `IExchangeRateProvider`; adapter bên ngoài gọi provider thật. Không cần tạo interface cho mọi class chỉ để đạt “100% abstraction”.

**Trade-off:**
Boundary rõ giúp testability và thay đổi integration dễ hơn, nhưng quá nhiều ports/adapters cho CRUD đơn giản làm tăng ceremony, mapping và cognitive load. Một layered architecture đơn giản có thể tốt hơn nếu dependency ít biến động và team nhỏ.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction đúng và tránh để vendor type tràn vào core logic. Senior / Technical developer phải nhận diện boundary nào thực sự cần bảo vệ, cân bằng cost abstraction với probability/cost of change và không biến Hexagonal Architecture thành template áp dụng máy móc.

### Design 3 — Feature Flag tách deployment khỏi release nhưng phải có lifecycle rõ ràng

**Khái niệm:**
Feature Flag cho phép deploy code mới nhưng kiểm soát việc capability có được bật cho user/tenant hay không. Điều này hỗ trợ progressive rollout, canary behavior hoặc rollback logic nhanh mà không cần deploy lại ngay.

**Vấn đề nó giải quyết:**
Một checkout flow mới đã qua CI nhưng vẫn có rủi ro production. Team muốn deploy artifact chứa code mới, bật cho 1% traffic, quan sát metric rồi tăng dần. Nếu error rate tăng, flag có thể tắt behavior mới trong khi artifact vẫn giữ nguyên.

**Ví dụ thực tế:**
```text
checkout-v2:
- internal users: on
- tenant A: on
- 5% public traffic: on
- default: off
```

Rollout phải đi cùng metric như conversion, latency, error rate và dependency failure thay vì chỉ “bật dần cho đủ”.

**Trade-off:**
Feature Flag giảm release risk nhưng tạo hai hoặc nhiều execution path, tăng test matrix và có thể để lại dead code lâu dài. Flag dùng cho business entitlement cũng khác release flag tạm thời; hai loại này nên có ownership và lifecycle khác nhau.

**Middle → Senior insight:**
Middle developer cần test cả flag on/off và tránh logic flag rải rác khắp codebase. Senior / Technical developer phải xác định owner, expiry date, rollout criteria, observability, fallback và thời điểm xóa flag để release safety không biến thành permanent complexity.
