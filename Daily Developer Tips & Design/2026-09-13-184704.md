# Daily Developer Tips & Design — 2026-09-13

## 🛠 Developer Tips & Tricks

### Tip 1 — Partition rate limiting theo tenant hoặc user thay vì chỉ theo IP

**Mẹo:**
Trong ASP.NET Core, khi API phục vụ nhiều tenant hoặc authenticated user, cân nhắc `PartitionedRateLimiter` theo `TenantId`, `UserId` hoặc API key thay vì chỉ limit theo IP.

**Tại sao hữu ích:**
IP không phải lúc nào cũng đại diện đúng một caller. Nhiều user có thể đi qua cùng NAT/proxy, trong khi một attacker có thể phân tán request qua nhiều IP. Partition theo identity/business boundary giúp giới hạn công bằng và sát với capacity thực tế hơn.

**Ví dụ:**
```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
    {
        var key = ctx.User.FindFirst("tenant_id")?.Value ?? "anonymous";

        return RateLimitPartition.GetFixedWindowLimiter(
            key,
            _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 100,
                Window = TimeSpan.FromMinutes(1)
            });
    });
});
```

**Lưu ý:**
Rate limit key phải khó giả mạo và có cardinality được kiểm soát. Đừng lấy header tùy ý từ client làm partition key nếu chưa được authentication/validation. Với hệ thống phân tán nhiều instance, limiter in-memory chỉ bảo vệ từng instance, không phải toàn cụm.

### Tip 2 — Dùng compiled query của EF Core khi profiling chứng minh query compilation là hot path

**Mẹo:**
Với query rất thường xuyên, shape ổn định và chạy ở throughput cao, cân nhắc `EF.CompileQuery` hoặc `EF.CompileAsyncQuery` để giảm overhead compile expression/query pipeline lặp lại.

**Tại sao hữu ích:**
EF Core đã cache query theo shape, nên đa số ứng dụng không cần compiled query thủ công. Nhưng ở hot path cực kỳ thường xuyên, việc bỏ thêm lookup/processing trong query pipeline có thể giảm CPU nhỏ nhưng đo được.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, int, IAsyncEnumerable<Order>>
    GetRecentOrders = EF.CompileAsyncQuery(
        (AppDbContext db, int customerId) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.CustomerId == customerId)
              .OrderByDescending(x => x.CreatedAt)
              .Take(20));
```

**Lưu ý:**
Đây là optimization sau profiling, không phải default pattern. Query dynamic nhiều điều kiện thường không phù hợp. Nếu bottleneck nằm ở SQL plan, network hoặc missing index, compiled query gần như không giải quyết vấn đề chính.

### Tip 3 — Upload file lớn trực tiếp vào Azure Blob bằng SAS ngắn hạn thay vì proxy toàn bộ qua API

**Mẹo:**
Với file lớn từ browser/mobile, cân nhắc để backend cấp SAS scoped, thời hạn ngắn rồi client upload trực tiếp vào Azure Blob Storage thay vì stream toàn bộ file qua App Service.

**Tại sao hữu ích:**
Backend proxy file làm application chịu bandwidth, memory/buffer pressure và connection duration không cần thiết. Direct upload chuyển data path sang storage service được thiết kế cho throughput lớn, còn backend giữ vai trò authorization và metadata orchestration.

**Ví dụ:**
```text
1. Client -> POST /uploads/request
2. API kiểm tra quyền, tạo blob name + SAS 10 phút
3. Client -> PUT trực tiếp tới Blob Storage
4. Client/API xác nhận hoàn tất
5. Background job scan/validate/process file
```

**Lưu ý:**
SAS phải giới hạn đúng blob/container, permission và expiry. Không cấp SAS ghi cả container cho client không tin cậy. File upload vẫn cần validation, malware scanning, size/type policy và cơ chế cleanup cho upload bỏ dở.

### Tip 4 — Trong Vue, tránh reactive hóa object lớn nếu UI chỉ cần đọc bất biến

**Mẹo:**
Nếu một object lớn như configuration, schema, static catalog hoặc third-party instance không cần reactive tracking sâu, dùng `markRaw`, `shallowRef` hoặc cấu trúc phù hợp thay vì đưa toàn bộ object vào deep reactivity.

**Tại sao hữu ích:**
Vue tạo proxy và dependency tracking cho reactive object. Với tree lớn hoặc object từ library ngoài, deep reactivity có thể tạo overhead không mang lại giá trị và đôi khi làm identity comparison khó hiểu.

**Ví dụ:**
```ts
const chartInstance = shallowRef<Chart | null>(null)

onMounted(() => {
  chartInstance.value = new Chart(canvas, options)
})
```

Hoặc với object không bao giờ cần reactive:
```ts
const schema = markRaw(largeSchema)
```

**Lưu ý:**
Đừng dùng `markRaw` chỉ để “tối ưu” theo cảm giác. Nếu nested state thật sự cần drive UI, bỏ reactivity sẽ tạo bug khó thấy. Profile rendering/update trước khi thay đổi model state.

### Tip 5 — Đừng để telemetry sampling che mất error hiếm nhưng quan trọng

**Mẹo:**
Khi dùng Application Insights/OpenTelemetry sampling để giảm volume, kiểm tra policy để exception, failed request hoặc trace quan trọng không bị loại ngẫu nhiên cùng với traffic bình thường.

**Tại sao hữu ích:**
Sampling giúp giảm cost và noise, nhưng incident hiếm có thể trở nên gần như vô hình nếu trace chứa error bị drop. Một hệ thống “có observability” nhưng mất đúng evidence cần điều tra vẫn rất khó vận hành.

**Ví dụ:**
```text
Normal successful requests: sample 10%
5xx / exceptions: retain 100%
High-value checkout trace: retain theo rule riêng
```

Khi dùng distributed tracing, cần đảm bảo sampling decision nhất quán để không giữ span con nhưng mất root span quan trọng.

**Lưu ý:**
Giữ 100% mọi telemetry cũng không phải giải pháp lâu dài vì chi phí và signal-to-noise. Thiết kế sampling dựa trên traffic, SLO, incident pattern và compliance; kiểm tra actual ingestion thay vì chỉ tin config.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho idempotent consumer trong hệ thống at-least-once delivery

**Khái niệm:**
Inbox Pattern lưu dấu message/event đã xử lý trong cùng transactional boundary với business update của consumer. Nếu broker redeliver cùng message, consumer phát hiện duplicate và bỏ qua hoặc trả kết quả idempotent.

**Vấn đề nó giải quyết:**
Azure Service Bus và nhiều broker cung cấp at-least-once delivery. Consumer có thể commit database thành công nhưng crash trước khi acknowledge message, khiến broker gửi lại và business side effect bị chạy lần hai.

**Ví dụ thực tế:**
```text
MessageId = evt-123

DB transaction:
- kiểm tra Inbox(evt-123)
- nếu chưa có:
  - apply PaymentConfirmed
  - insert Inbox(evt-123)
- commit

Sau đó Complete message
```

**Trade-off:**
Inbox tăng reliability và cho phép xử lý duplicate có hệ thống, nhưng thêm storage, cleanup policy và transaction logic. Nếu side effect nằm ngoài database như gọi third-party API, vẫn cần idempotency key hoặc workflow riêng ở boundary đó.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là bình thường và implement deduplication đúng transaction. Senior / Technical developer phải chọn idempotency boundary, retention của Inbox, unique constraint, failure recovery và cách xử lý side effect ngoài transaction.

### Design 2 — CQRS chỉ nên áp dụng khi read/write model thực sự có áp lực khác nhau

**Khái niệm:**
CQRS tách command model và query model khi hai phía có semantics, scale hoặc data shape khác nhau đáng kể. Nó không đồng nghĩa bắt buộc phải có hai database, event sourcing hoặc message broker.

**Vấn đề nó giải quyết:**
Một domain phức tạp có write model bảo vệ invariant nhưng read model lại cần projection denormalized cho dashboard/search. Ép cả hai dùng cùng object model có thể làm domain model méo mó hoặc query trở nên khó tối ưu.

**Ví dụ thực tế:**
```text
Write:
PlaceOrderCommand
-> Aggregate kiểm tra invariant
-> SQL transaction

Read:
GET /orders/dashboard
-> projection DTO tối ưu riêng
-> query trực tiếp/read model
```

Ở bước đầu, cả command và query vẫn có thể dùng cùng SQL Server nếu chưa cần tách hạ tầng.

**Trade-off:**
CQRS làm responsibility rõ hơn và cho phép tối ưu độc lập, nhưng tăng số model, mapping và consistency concern. Với CRUD đơn giản, tách command/query quá sớm chỉ tạo boilerplate và cognitive load.

**Middle → Senior insight:**
Middle developer cần phân biệt command thay đổi state với query đọc dữ liệu và tránh reuse model vô tội vạ. Senior / Technical developer phải đánh giá domain complexity, query pressure, consistency requirement và team cost trước khi quyết định mức độ CQRS phù hợp.

### Design 3 — Expand/Contract migration để deploy database không downtime

**Khái niệm:**
Expand/Contract chia breaking schema change thành nhiều release tương thích ngược: trước tiên mở rộng schema để cả code cũ và mới cùng chạy, sau đó migrate traffic/data, cuối cùng mới xóa cấu trúc cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment hoặc nhiều instance chạy lệch version, rename/drop column trực tiếp có thể làm instance cũ crash ngay khi migration hoàn tất. Database schema phải coexist với nhiều application version trong một khoảng thời gian.

**Ví dụ thực tế:**
```text
Release A:
- thêm column `display_name`
- code vẫn đọc `name`, đồng thời bắt đầu ghi cả hai

Backfill:
- copy dữ liệu lịch sử sang `display_name`

Release B:
- code mới đọc `display_name`

Sau khi không còn instance cũ:
- stop dual-write
- drop `name`
```

**Trade-off:**
Expand/Contract giảm deployment risk và hỗ trợ rollback tốt hơn, nhưng migration kéo dài qua nhiều release, có temporary duplication và cần telemetry để biết khi nào dependency cũ đã biến mất. Với hệ thống nhỏ có maintenance window, quy trình này có thể quá nặng.

**Middle → Senior insight:**
Middle developer cần tránh migration phá compatibility với version đang chạy. Senior / Technical developer phải lập rollout sequence, dual-read/write strategy, backfill, rollback plan, data validation và tiêu chí an toàn để bước sang phase contract.
