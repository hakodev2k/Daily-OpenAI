# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer lớn được tạo lặp lại

**Mẹo:**
Nếu một hot path thường xuyên tạo mảng tạm lớn, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì `new` mỗi lần.

**Tại sao hữu ích:**
Giảm allocation và GC pressure, đặc biệt trong serialization, stream processing hoặc protocol parsing.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024));
    // process buffer
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Luôn `Return` buffer trong `finally`. Không giả định kích thước mảng trả về đúng bằng kích thước yêu cầu, và tránh trả buffer chứa dữ liệu nhạy cảm nếu không clear phù hợp.

### Tip 2 — Dùng `TagWith()` để truy ngược SQL từ EF Core

**Mẹo:**
Gắn tag cho query EF Core quan trọng bằng `TagWith()` để SQL sinh ra có comment nhận diện.

**Tại sao hữu ích:**
Khi xem slow query log, Query Store hoặc database monitoring, bạn có thể biết query đó đến từ use case nào trong application mà không cần đoán từ SQL dài.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .TagWith("OrdersController.GetPendingOrders")
    .Where(x => x.Status == OrderStatus.Pending)
    .ToListAsync();
```

**Lưu ý:**
Tag chỉ hỗ trợ observability; nó không làm query nhanh hơn. Tránh đưa dữ liệu runtime nhạy cảm hoặc cardinality cao vào tag.

### Tip 3 — Dùng `curl --fail-with-body` trong CI thay vì chỉ kiểm tra exit code mặc định

**Mẹo:**
Khi smoke test HTTP endpoint trong pipeline, dùng `--fail-with-body` để HTTP 4xx/5xx làm command fail nhưng vẫn giữ response body để debug.

**Tại sao hữu ích:**
Pipeline không bị báo thành công khi endpoint thực tế trả lỗi, đồng thời log vẫn đủ thông tin để tìm root cause.

**Ví dụ:**
```bash
curl --fail-with-body --retry 3 https://api.example.com/health/ready
```

**Lưu ý:**
Không retry mọi lỗi một cách mù quáng. Với endpoint có side effect, retry có thể tạo duplicate operation nếu API không idempotent.

### Tip 4 — Dùng `git range-diff` khi review branch sau rebase

**Mẹo:**
Sau khi một PR được rebase hoặc force-push nhiều commit, dùng `git range-diff` để so sánh “series commit cũ” với “series commit mới”.

**Tại sao hữu ích:**
Reviewer có thể thấy commit nào thực sự thay đổi thay vì phải review lại toàn bộ diff từ đầu.

**Ví dụ:**
```bash
git range-diff origin/main...old-head origin/main...new-head
```

**Lưu ý:**
`range-diff` so sánh patch series, không phải trạng thái cuối cùng của filesystem. Với thay đổi lớn bị squash mạnh, kết quả có thể khó đọc.

### Tip 5 — Đặt timeout riêng cho từng dependency thay vì dùng một timeout chung

**Mẹo:**
Cấu hình timeout dựa trên đặc tính của từng downstream service thay vì dùng một giá trị chung cho mọi `HttpClient`.

**Tại sao hữu ích:**
Payment API có thể cần phản hồi trong 2 giây, còn reporting API có thể chấp nhận 10 giây. Timeout đúng giúp fail fast ở dependency quan trọng và tránh giữ resource quá lâu.

**Ví dụ:**
```csharp
services.AddHttpClient<PaymentClient>(client =>
{
    client.Timeout = TimeSpan.FromSeconds(2);
});

services.AddHttpClient<ReportingClient>(client =>
{
    client.Timeout = TimeSpan.FromSeconds(10);
});
```

**Lưu ý:**
Timeout không nên được chọn tùy ý. Cần dựa trên latency percentile, SLA/SLO và tổng time budget của request; retry cũng phải nằm trong cùng budget.

## 🧠 Software Design

### Design 1 — Time Budget cho distributed request

**Khái niệm:**
Time Budget phân bổ tổng thời gian cho một request end-to-end thành các phần dành cho từng dependency, retry và processing nội bộ.

**Vấn đề nó giải quyết:**
Nếu mỗi service tự đặt timeout độc lập mà không tính tổng, request có thể kéo dài vượt xa SLA. Ví dụ API gateway timeout 5 giây nhưng service A gọi ba dependency, mỗi dependency timeout 5 giây thì deadline tổng thể trở nên vô nghĩa.

**Ví dụ thực tế:**
Một API phải trả trong 3 giây. Team dành 300 ms cho validation và DB, 1 giây cho Payment, 800 ms cho Fraud Check, phần còn lại làm headroom. Khi còn ít thời gian, service không bắt đầu retry mới mà trả lỗi sớm.

**Trade-off:**
Ưu điểm là latency predictable hơn và hạn chế cascading failure. Chi phí là implementation phức tạp hơn, cần propagate deadline hoặc cancellation xuyên service và phải đo latency thực tế để chia budget hợp lý.

**Middle → Senior insight:**
Middle developer cần hiểu timeout của một call không tồn tại độc lập. Senior developer phải thiết kế end-to-end deadline, retry budget và cancellation propagation dựa trên SLO thay vì cấu hình từng service riêng lẻ.

### Design 2 — Strangler Fig Pattern khi thay thế legacy system

**Khái niệm:**
Strangler Fig Pattern thay hệ thống cũ từng phần bằng cách đặt routing/facade phía trước, rồi chuyển dần từng capability sang implementation mới.

**Vấn đề nó giải quyết:**
Rewrite toàn bộ legacy system thường kéo dài, rủi ro cao và khó rollback. Strangler cho phép chuyển đổi incremental trong khi hệ thống cũ vẫn phục vụ phần chưa migrate.

**Ví dụ thực tế:**
Một monolith cũ xử lý Customer, Order và Billing. Team bắt đầu đưa `/customers/*` sang service mới qua API gateway, giữ `/orders/*` và `/billing/*` ở monolith. Khi Customer ổn định, tiếp tục migrate capability tiếp theo.

**Trade-off:**
Giảm migration risk và tạo checkpoint rollback rõ ràng, nhưng trong giai đoạn chuyển tiếp phải duy trì routing, duplicate model, integration giữa old/new system và đôi khi cả data synchronization.

**Middle → Senior insight:**
Middle developer cần hiểu migration không nhất thiết đồng nghĩa big-bang rewrite. Senior developer phải chọn seam phù hợp, ownership dữ liệu, cách routing, rollback và tiêu chí kết thúc để transitional architecture không trở thành kiến trúc vĩnh viễn.

### Design 3 — Consumer-driven contract testing cho API giữa các service

**Khái niệm:**
Consumer-driven contract testing để consumer mô tả những phần contract mà nó thực sự phụ thuộc; provider chạy verify để đảm bảo thay đổi không phá consumer.

**Vấn đề nó giải quyết:**
Integration test end-to-end thường chậm và flaky, còn unit test riêng lẻ không phát hiện breaking change như rename field, thay enum hoặc đổi status code mà consumer đang dựa vào.

**Ví dụ thực tế:**
Order Service phụ thuộc Payment API trả `paymentId`, `status` và HTTP 200 cho payment thành công. Contract test ghi lại expectation này. Khi Payment team thay `status` thành object mới, CI provider phát hiện incompatibility trước khi deploy.

**Trade-off:**
Cho feedback nhanh và giảm phụ thuộc vào full environment, nhưng cần quản lý version contract, provider state và tránh biến contract test thành bản sao cứng nhắc của toàn bộ response schema.

**Middle → Senior insight:**
Middle developer cần biết API compatibility không chỉ là compile-time concern. Senior developer phải quyết định đâu là contract thật sự cần bảo vệ, cách version hóa expectation và kết hợp contract test với integration/e2e test để cân bằng tốc độ và confidence.
