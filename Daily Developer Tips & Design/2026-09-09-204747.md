# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` để tạo backpressure thay vì để producer bơm việc vô hạn

**Mẹo:**
Khi một .NET service có producer tạo work nhanh hơn consumer xử lý, cân nhắc `Channel<T>` dạng bounded để giới hạn lượng work đang chờ thay vì đẩy vô hạn vào memory.

**Tại sao hữu ích:**
Queue không giới hạn có thể che giấu overload trong thời gian ngắn nhưng cuối cùng đổi thành memory pressure, GC tăng mạnh và latency kéo dài. Bounded channel buộc hệ thống thể hiện backpressure rõ ràng khi capacity bị dùng hết.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, ct);
```

Producer sẽ chờ khi queue đầy thay vì tiếp tục allocate work vô hạn.

**Lưu ý:**
Capacity 500 không phải giá trị mặc định tốt cho mọi hệ thống. Chọn dựa trên throughput, processing time và memory budget; nếu producer là HTTP request, còn phải xác định có nên wait, reject hay persist work ra broker bền vững hơn.

### Tip 2 — Với MongoDB compound index, thứ tự field phải bám query pattern thật

**Mẹo:**
Khi tạo compound index trong MongoDB, chọn thứ tự field dựa trên equality, sort và range của query thực tế thay vì gom các field “hay dùng” vào cùng một index.

**Tại sao hữu ích:**
Index `{ tenantId: 1, status: 1, createdAt: -1 }` hiệu quả cho query lọc theo `tenantId`, `status` rồi sort theo `createdAt`. Nếu bỏ prefix quan trọng hoặc đổi thứ tự không phù hợp, database có thể scan nhiều key hơn hoặc không hỗ trợ sort như mong muốn.

**Ví dụ:**
```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })
```

Query phù hợp:
```javascript
db.orders.find({ tenantId: "t1", status: "Open" })
         .sort({ createdAt: -1 })
```

**Lưu ý:**
Đừng tạo nhiều compound index gần giống nhau mà không đo `explain()` và write cost. Mỗi index làm insert/update đắt hơn và tăng storage, cache pressure.

### Tip 3 — Dùng Managed Identity để truy cập Azure Key Vault thay vì lưu client secret trong app config

**Mẹo:**
Khi workload chạy trên Azure App Service, Azure Functions hoặc resource hỗ trợ identity, ưu tiên Managed Identity để authenticate tới Azure Key Vault thay vì nhúng client secret vào configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời phân phối, rotate và bảo vệ secret dùng để lấy secret khác. Access được quản lý qua Azure identity/RBAC và token được cấp động cho workload.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUrl),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Local development có thể dùng developer credential; production dùng Managed Identity mà không đổi application code.

**Lưu ý:**
Managed Identity không có nghĩa cấp quyền rộng. Áp dụng least privilege, tách identity theo workload khi cần và không log secret value. Đồng thời tránh gọi Key Vault trên mọi request nếu secret có thể cache an toàn trong process theo rotation policy.

### Tip 4 — Khi CDN trả nội dung cũ, kiểm tra `Cache-Control`, cache key và invalidation trước khi blame application

**Mẹo:**
Nếu website qua Akamai/CDN vẫn phục vụ asset hoặc HTML cũ sau deployment, điều tra response headers và cache key trước khi sửa backend code.

**Tại sao hữu ích:**
Một object có thể đang tồn tại ở nhiều lớp: browser cache, CDN edge, reverse proxy và origin. Nếu `Cache-Control: max-age=86400` hoặc cache key không bao gồm variation cần thiết, origin đã đúng nhưng user vẫn thấy dữ liệu cũ.

**Ví dụ:**
```text
Browser -> CDN HIT -> old app.js
Origin   -> new app.js
```

Với static asset, content-hashed filename như `app.a83f2.js` thường an toàn hơn purge liên tục vì URL đổi theo nội dung.

**Lưu ý:**
Không đặt `no-store` cho mọi thứ để né cache bug; sẽ mất lợi ích performance. Với authenticated/personalized response, phải đặc biệt cẩn thận với shared-cache semantics và `Vary`/cache key để tránh rò dữ liệu giữa user.

### Tip 5 — Khi dùng AI coding agent review PR, bắt nó đối chiếu source và test thay vì chỉ “đọc diff”

**Mẹo:**
Với AI-assisted code review, yêu cầu agent kiểm tra implementation mới với contract hiện tại, call sites, library version và test behavior trong repository; không chấp nhận nhận xét chỉ dựa trên diff cô lập.

**Tại sao hữu ích:**
Một diff có thể nhìn hợp lý nhưng gọi API không tồn tại ở version đang dùng, phá invariant ở module khác hoặc thêm test chỉ verify implementation detail. Grounding vào source giúp giảm hallucination và false positive.

**Ví dụ:**
```text
1. Xác định contract/interface liên quan
2. Tìm tất cả call sites
3. Kiểm tra package/framework version
4. Chạy/đọc test bảo vệ behavior
5. Chỉ report issue có evidence
```

**Lưu ý:**
AI review không thay thế compiler, static analysis, test suite hay reviewer chịu trách nhiệm. Đừng auto-merge chỉ vì agent trả “LGTM”; cần evidence cho các claim ảnh hưởng correctness/security.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read/write model thật sự có pressure khác nhau

**Khái niệm:**
CQRS tách command model và query model để mỗi phía có thể tối ưu cho invariant/write workflow hoặc read shape riêng. Nó không đồng nghĩa bắt buộc dùng event sourcing, message broker hay hai database.

**Vấn đề nó giải quyết:**
Một domain có write logic phức tạp nhưng read side cần nhiều dashboard/projection khác nhau dễ bị ép vào một model vừa khó bảo vệ invariant vừa khó query hiệu quả.

**Ví dụ thực tế:**
```text
Write:
PlaceOrderCommand -> Order aggregate -> transactional tables

Read:
OrderSummaryQuery -> projection tối ưu cho UI
```

Trong một Modular Monolith, hai model vẫn có thể dùng cùng SQL database nhưng boundary code khác nhau.

**Trade-off:**
CQRS giúp read/write concern rõ và cho phép optimize độc lập, nhưng thêm model, mapping, duplication và consistency complexity. Với CRUD đơn giản, tách command/query layer quá mức chỉ tăng ceremony.

**Middle → Senior insight:**
Middle developer cần hiểu command thay đổi state và query không nên chứa side effect. Senior / Technical developer phải chứng minh pressure đủ lớn—domain complexity, read shape, scaling hoặc ownership—trước khi chấp nhận cost của CQRS và eventual consistency nếu có.

### Design 2 — Azure Functions vs Worker Service cho background processing dài hạn

**Khái niệm:**
Azure Functions phù hợp với event-driven/serverless workload cần scale theo trigger và ít quản lý host. Worker Service phù hợp khi cần process sống lâu, control lifecycle/concurrency chi tiết hoặc workload ổn định liên tục.

**Vấn đề nó giải quyết:**
Một team có thể chọn Functions cho mọi background job chỉ vì deployment đơn giản, rồi gặp cold start, execution/lifecycle constraint hoặc khó kiểm soát long-running process. Ngược lại, chạy Worker 24/7 cho workload rất thưa có thể tốn vận hành và compute không cần thiết.

**Ví dụ thực tế:**
```text
Blob upload vài lần/giờ -> Azure Function trigger phù hợp

Service Bus consumer chạy liên tục,
custom batching + backpressure + long connection lifecycle
-> Worker Service có thể phù hợp hơn
```

**Trade-off:**
Functions giảm infrastructure management và scale linh hoạt nhưng execution model phụ thuộc platform. Worker Service cho control cao hơn nhưng team phải chịu deployment, scaling, health check và capacity planning rõ hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger/retry/idempotency của Functions và lifecycle của Worker. Senior / Technical developer phải so workload shape, latency, execution duration, scale pattern, operational control và cost thay vì chọn theo sở thích framework.

### Design 3 — Strangler Fig cho modernization legacy thay vì rewrite toàn hệ thống một lần

**Khái niệm:**
Strangler Fig modernize hệ thống bằng cách đặt boundary mới quanh legacy application rồi chuyển từng capability sang implementation mới theo từng bước, thay vì big-bang rewrite.

**Vấn đề nó giải quyết:**
Một .NET Framework monolith lớn thường chứa behavior ẩn, integration cũ và business rule chưa được document đầy đủ. Rewrite toàn bộ dễ kéo dài nhiều năm và mất parity trước khi tạo business value.

**Ví dụ thực tế:**
```text
Traffic -> routing layer

/customer-search -> ASP.NET Core service mới
/legacy-orders   -> .NET Framework app cũ
```

Sau khi customer-search ổn định, tiếp tục migrate capability khác và thu hẹp legacy footprint.

**Trade-off:**
Incremental migration giảm delivery risk và cho rollback theo capability, nhưng tạo giai đoạn hai hệ thống cùng tồn tại, duplicate integration, routing và data ownership phức tạp hơn. Một module nhỏ, cô lập có thể rewrite trực tiếp đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần giữ contract tương thích và test parity giữa old/new path. Senior / Technical developer phải chọn migration seam, ownership dữ liệu, traffic cutover, observability và decommission plan để trạng thái hybrid không trở thành kiến trúc vĩnh viễn.
