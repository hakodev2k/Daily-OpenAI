# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate configuration ngay lúc startup thay vì chờ request đầu tiên mới nổ lỗi

**Mẹo:**
Với configuration bắt buộc trong ASP.NET Core, dùng Options validation và `ValidateOnStart()` để phát hiện thiếu hoặc sai giá trị ngay khi application khởi động.

**Tại sao hữu ích:**
Nếu connection string, API endpoint hoặc credential name sai nhưng chỉ được đọc khi một request cụ thể chạy, deployment có thể trông “healthy” trong vài phút rồi mới phát sinh lỗi production. Startup validation biến configuration error thành lỗi triển khai có thể phát hiện sớm.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(x => Uri.TryCreate(x.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be an absolute URL")
    .Validate(x => x.TimeoutSeconds is > 0 and <= 30,
        "TimeoutSeconds must be between 1 and 30")
    .ValidateOnStart();
```

Khi cấu hình sai, process fail startup thay vì nhận traffic rồi mới lỗi ngẫu nhiên.

**Lưu ý:**
Không dùng startup validation để gọi hàng loạt external dependency chỉ nhằm “test connectivity”; điều đó có thể làm startup phụ thuộc vào outage tạm thời của hệ thống khác. Validate cấu trúc và invariant của configuration; dependency health nên được xử lý bằng health checks hoặc runtime resilience phù hợp.

### Tip 2 — SQL Server query lúc nhanh lúc chậm: kiểm tra parameter-sensitive plan trước khi thêm index

**Mẹo:**
Khi cùng một stored procedure/query có lúc chạy vài chục ms, có lúc vài giây với parameter khác nhau, kiểm tra execution plan và cardinality estimate trước khi kết luận database thiếu index.

**Tại sao hữu ích:**
Một plan tốt cho parameter có selectivity cao có thể rất tệ cho parameter trả về phần lớn bảng. SQL Server có thể reuse cached plan trong khi phân bố dữ liệu giữa các parameter rất khác nhau, tạo hiện tượng latency không ổn định.

**Ví dụ:**
```sql
SELECT Id, CustomerId, Status, CreatedAt
FROM Orders
WHERE CustomerId = @customerId
  AND Status = @status;
```

Nếu một customer có 20 order còn customer khác có 2 triệu order, cùng một access strategy không nhất thiết phù hợp cho cả hai. Khi điều tra, so sánh actual vs estimated rows và plan của parameter “nhanh” với parameter “chậm”.

**Lưu ý:**
Đừng phản xạ bằng `OPTION (RECOMPILE)` cho mọi query; compile lại liên tục cũng có chi phí. Tùy workload có thể cần schema/index tốt hơn, query rewrite, filtered index, Query Store evidence hoặc cơ chế parameter-sensitive plan của SQL Server hiện đại.

### Tip 3 — Redis cache stampede: thêm TTL jitter thay vì để hàng nghìn key hết hạn cùng lúc

**Mẹo:**
Khi nhiều cache entry được tạo cùng thời điểm, thêm một lượng jitter nhỏ vào TTL để chúng không đồng loạt expire và cùng quay về database/backend.

**Tại sao hữu ích:**
Nếu 50.000 key đều có TTL chính xác 30 phút và được warm cùng một đợt deployment, 30 phút sau chúng có thể cùng miss. Database đột nhiên nhận burst rất lớn dù traffic người dùng không tăng.

**Ví dụ:**
```csharp
var baseTtl = TimeSpan.FromMinutes(30);
var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 180));

await cache.SetStringAsync(
    key,
    json,
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = baseTtl + jitter
    },
    ct);
```

Với hot key đặc biệt, có thể kết hợp request coalescing/single-flight hoặc refresh-ahead.

**Lưu ý:**
TTL jitter chỉ phân tán thời điểm expire, không giải quyết mọi stampede. Nếu một key cực nóng vừa hết hạn, hàng nghìn request vẫn có thể cùng miss. Cũng không nên tăng TTL quá lớn đến mức stale-data vượt business tolerance.

### Tip 4 — Trong Playwright, chờ theo state của UI thay vì `Task.Delay`

**Mẹo:**
Trong end-to-end test, đừng dùng delay cố định để “đợi trang load”. Hãy chờ locator, network outcome hoặc state mà user thực sự quan sát được.

**Tại sao hữu ích:**
`Task.Delay(3000)` vừa làm test chậm, vừa flaky: máy CI nhanh thì lãng phí 3 giây, máy chậm thì 3 giây vẫn chưa đủ. Playwright có auto-waiting và locator semantics giúp test bám vào điều kiện thực tế.

**Ví dụ:**
```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

await Expect(page.GetByText("Saved successfully"))
    .ToBeVisibleAsync();
```

Nếu cần chờ request, chờ response/request cụ thể thay vì ngủ theo thời gian đoán trước.

**Lưu ý:**
Đừng chờ selector kỹ thuật quá gắn với implementation như class CSS ngẫu nhiên nếu test đang mô phỏng hành vi người dùng. Đồng thời, auto-waiting không thay thế việc seed test data ổn định và cô lập external dependency dễ flaky.

### Tip 5 — Với Azure Blob Storage, ưu tiên direct upload khi backend không cần xử lý nội dung file

**Mẹo:**
Nếu client chỉ cần upload file lớn lên Blob Storage và backend không cần inspect nội dung trước khi lưu, cân nhắc cấp quyền upload có giới hạn thời gian thay vì proxy toàn bộ file qua ASP.NET Core API.

**Tại sao hữu ích:**
Proxy file qua backend làm application phải tiêu bandwidth, connection và memory/buffer cho dữ liệu mà Blob Storage vốn có thể nhận trực tiếp. Direct upload giảm tải application tier và thường scale tốt hơn với file lớn.

**Ví dụ:**
```text
1. Client gọi API xin upload permission
2. Backend authorize user + tạo blob name
3. Backend cấp short-lived SAS có quyền Create/Write cho đúng blob
4. Client upload trực tiếp tới Blob Storage
5. Backend lưu metadata / nhận callback hoặc client confirm
```

Nếu có Managed Identity, backend có thể dùng identity-based access để tạo user-delegation SAS thay vì giữ storage account key lâu dài.

**Lưu ý:**
Direct upload không bỏ qua security validation. Vẫn cần giới hạn blob path, content length, loại file theo business rule, expiration và post-upload scanning nếu file không tin cậy. Không cấp SAS rộng cho cả container khi user chỉ cần ghi một object.

## 🧠 Software Design

### Design 1 — Strangler Fig Pattern phù hợp để hiện đại hóa hệ thống lớn theo từng capability

**Khái niệm:**
Strangler Fig Pattern cho phép xây functionality mới quanh hệ thống legacy rồi dần chuyển traffic từng capability sang implementation mới, thay vì rewrite toàn bộ trong một lần.

**Vấn đề nó giải quyết:**
Một ASP.NET/.NET Framework monolith 10 năm tuổi cần chuyển sang modern .NET nhưng chứa hàng trăm flow nghiệp vụ, integration và rule chưa được document đầy đủ. Big-bang rewrite làm thời gian feedback quá dài và rủi ro parity rất cao.

**Ví dụ thực tế:**
```text
Client
  -> routing layer
      -> /catalog/*  -> new .NET 10 service/module
      -> /orders/*   -> legacy application
      -> /account/*  -> legacy application
```

Sau khi Catalog ổn định, team tiếp tục chuyển capability tiếp theo và loại dần code cũ.

**Trade-off:**
Cách này giảm migration risk và cho phép release giá trị từng phần, nhưng trong giai đoạn chuyển đổi phải vận hành hai thế giới: routing, data ownership, authentication, duplicated logic và observability phức tạp hơn. Nếu không có exit plan, “temporary bridge” có thể trở thành permanent architecture.

**Middle → Senior insight:**
Middle developer cần giữ behavior tương thích và tránh làm migration phá contract hiện tại. Senior / Technical developer phải xác định seam, thứ tự capability nên tách, data ownership, cutover criteria, rollback path và thời điểm xóa legacy dependency.

### Design 2 — CQRS chỉ đáng dùng khi read và write thực sự có áp lực khác nhau

**Khái niệm:**
CQRS tách model hoặc path xử lý command và query khi yêu cầu của hai phía khác nhau đáng kể. Nó không đồng nghĩa bắt buộc dùng Microservices, Event Sourcing hay message broker.

**Vấn đề nó giải quyết:**
Một hệ thống commerce có write model giàu invariant cho checkout nhưng màn hình catalog/search cần read model denormalized, query cực nhanh và scale độc lập. Ép cả hai dùng chung domain model có thể làm query phức tạp hoặc domain bị biến dạng để phục vụ UI.

**Ví dụ thực tế:**
```text
Write side:
Checkout command
-> domain rules
-> relational transaction

Read side:
ProductProjection
-> denormalized table / search index
-> optimized cho filter + sort + display
```

Hai phía có thể vẫn nằm trong cùng Modular Monolith nếu chưa có nhu cầu deploy độc lập.

**Trade-off:**
CQRS cho phép tối ưu read/write riêng nhưng thêm mapping, synchronization, eventual consistency và nhiều model phải duy trì. Với CRUD application đơn giản, tách command/query quá mức chỉ làm tăng boilerplate mà không tạo lợi ích thực tế.

**Middle → Senior insight:**
Middle developer cần hiểu khác biệt giữa “tách handler command/query cho code rõ hơn” và full CQRS có separate model/storage. Senior / Solution-oriented engineer phải chứng minh pressure thực tế như scale, domain complexity, query shape hoặc ownership trước khi chấp nhận consistency và operational cost bổ sung.

### Design 3 — Observability phải được thiết kế theo câu hỏi vận hành, không chỉ “log thật nhiều”

**Khái niệm:**
Observability design xác định metrics, traces và logs dựa trên các câu hỏi mà team cần trả lời khi production có vấn đề: request nào chậm, dependency nào gây lỗi, tenant nào bị ảnh hưởng, deployment nào tạo regression.

**Vấn đề nó giải quyết:**
Một hệ thống có gigabyte log nhưng khi p95 latency tăng vẫn không biết thời gian bị tiêu ở API, database hay external service. Dữ liệu telemetry nhiều nhưng không có correlation hoặc dimension đúng thì vẫn khó chẩn đoán.

**Ví dụ thực tế:**
```text
Metric:
- request rate / error rate / p95 latency theo route

Trace:
- API -> EF Core -> SQL -> external payment API

Structured log:
- correlationId
- orderId khi cần điều tra
- deploymentVersion
- failure category
```

Khi latency tăng sau release, team có thể so deployment version, tìm trace chậm và xác định dependency span nào thay đổi.

**Trade-off:**
Telemetry chi tiết tăng khả năng chẩn đoán nhưng cũng tăng storage cost, cardinality và rủi ro lộ dữ liệu nhạy cảm. Sampling quá mạnh lại có thể bỏ mất incident hiếm. Thiết kế cần cân bằng signal, cost, privacy và retention.

**Middle → Senior insight:**
Middle developer cần emit telemetry có cấu trúc và giữ correlation xuyên call chain. Senior / Technical developer phải xác định SLI/SLO, cardinality budget, sampling, retention và telemetry contract đủ để incident response dựa trên evidence thay vì thêm log ngẫu nhiên sau mỗi sự cố.
