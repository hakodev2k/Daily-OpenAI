# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` cho buffer lớn, sống ngắn và lặp lại nhiều lần để giảm GC pressure

**Mẹo:**
Trong hot path phải cấp phát buffer tương đối lớn liên tục, ví dụ xử lý file, compression hoặc network payload, cân nhắc thuê buffer từ `ArrayPool<T>.Shared` thay vì tạo array mới cho mỗi operation.

**Tại sao hữu ích:**
Array mới tạo allocation trên managed heap. Với buffer đủ lớn, allocation còn có thể đi vào Large Object Heap, làm tăng GC pressure và memory fragmentation. Pooling tái sử dụng vùng nhớ đã cấp phát, giảm số allocation và lượng công việc GC phải xử lý.

**Ví dụ:**
```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);

try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, buffer.Length), ct);
    await ProcessAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
`Rent()` có thể trả array lớn hơn kích thước yêu cầu. Không được giữ reference lâu hơn cần thiết, không dùng dữ liệu ngoài range thực tế, và cân nhắc `clearArray: true` nếu buffer từng chứa dữ liệu nhạy cảm. Pooling cũng không đáng dùng cho allocation nhỏ, hiếm hoặc không nằm trên hot path.

### Tip 2 — Dùng `ETag` và conditional request để tránh truyền lại response không thay đổi

**Mẹo:**
Với resource HTTP được đọc thường xuyên nhưng thay đổi ít, cân nhắc trả `ETag` và xử lý `If-None-Match` để server có thể trả `304 Not Modified` thay vì gửi lại toàn bộ payload.

**Tại sao hữu ích:**
Caching không chỉ là Redis hay in-memory cache. HTTP đã có cơ chế validation cache giữa browser/client, CDN và origin. Conditional request vẫn cần round-trip đến server nhưng giảm bandwidth, serialization và transfer cost khi representation chưa đổi.

**Ví dụ:**
```text
GET /api/products/42
-> 200 OK
ETag: "product-42-v17"

GET /api/products/42
If-None-Match: "product-42-v17"
-> 304 Not Modified
```

ETag nên đại diện cho version của representation, ví dụ row version hoặc hash ổn định của output.

**Lưu ý:**
Không tạo ETag bằng dữ liệu thay đổi vô nghĩa ở mỗi request như timestamp hiện tại. Cũng cần phân biệt validation cache với freshness cache qua `Cache-Control`; hai cơ chế giải quyết các phần khác nhau của HTTP caching.

### Tip 3 — Với Cosmos DB, partition key sai có thể làm RU và latency tăng dù tổng dữ liệu chưa lớn

**Mẹo:**
Khi một Cosmos DB container có latency hoặc throttling không đều, kiểm tra request distribution theo partition key trước khi chỉ tăng provisioned throughput.

**Tại sao hữu ích:**
Throughput phân tán hiệu quả khi workload cũng phân tán. Nếu phần lớn request tập trung vào một logical partition, hệ thống có thể tạo hot partition: một vùng chịu nhiều request trong khi capacity ở vùng khác chưa được tận dụng tốt.

**Ví dụ:**
```text
Partition key = /country

VN: 78% requests
US: 12%
Others: 10%

=> workload dễ tập trung vào partition của VN
```

Một key như `/tenantId` hoặc composite/hierarchical strategy phù hợp hơn hay không phải được quyết định dựa trên cardinality, access pattern và transaction boundary thực tế.

**Lưu ý:**
Partition key không thể chọn chỉ theo cardinality cao. Query thường xuyên thiếu partition key có thể biến thành cross-partition query và tăng request cost. Hãy model từ read/write pattern, growth projection và locality requirement.

### Tip 4 — Trong Application Insights, sampling sai có thể làm bạn hiểu sai tỷ lệ lỗi hiếm

**Mẹo:**
Khi dùng telemetry sampling để giảm volume và cost, kiểm tra loại telemetry nào được sample, tỷ lệ sampling và cách hệ thống giữ correlation trước khi dùng raw event count để kết luận production behavior.

**Tại sao hữu ích:**
Sampling giúp giảm lượng trace/log lớn, nhưng nếu analyst nhìn số record thô mà không hiểu sampling weight, họ có thể kết luận sai rằng chỉ có 10 lỗi trong khi telemetry thực tế đại diện cho lượng traffic lớn hơn. Một số signal quan trọng như exception hoặc dependency failure cũng cần strategy phù hợp để không mất evidence hiếm.

**Ví dụ:**
```text
Observed records: 20 failed requests
Sampling: 10%

Raw count != estimated production count
```

Trong incident investigation, correlate request, dependency, exception và trace ID thay vì chỉ đếm từng bảng telemetry độc lập.

**Lưu ý:**
Không tắt sampling toàn bộ chỉ để “đủ log” nếu traffic lớn; chi phí và noise có thể tăng mạnh. Thay vào đó, xác định signal nào phải giữ đầy đủ, signal nào có thể sample và retention nào thực sự cần cho SLO/incident response.

### Tip 5 — Với Optimizely CMS, đừng đưa mọi field biên tập vào một `PageData` khổng lồ

**Mẹo:**
Khi thiết kế content model, tách capability tái sử dụng thành Block hoặc cấu trúc content phù hợp thay vì thêm liên tục property vào một Page Type duy nhất chỉ vì editor cần thêm section mới.

**Tại sao hữu ích:**
Page Type quá lớn làm editorial UI khó dùng, tăng coupling giữa layout và content model, khiến component khó tái sử dụng và migration content khó hơn. Content model tốt phản ánh semantic boundary của nội dung, không chỉ cấu trúc pixel của một trang hiện tại.

**Ví dụ:**
```text
Không tốt:
HomePage
- HeroTitle
- HeroImage
- HeroLink
- Promo1Title
- Promo1Image
- Promo1Link
- Promo2Title
- ...

Tốt hơn:
HomePage
- MainContentArea

HeroBlock
PromoCardBlock
ArticleListBlock
```

**Lưu ý:**
Không biến mọi đoạn text nhỏ thành Block riêng. Quá nhiều block siêu nhỏ làm editor thao tác chậm và content tree phức tạp. Boundary nên dựa trên reuse, lifecycle, permission, personalization và editorial workflow.

## 🧠 Software Design

### Design 1 — Deadline propagation tốt hơn việc mỗi service tự chọn timeout độc lập

**Khái niệm:**
Trong distributed request chain, deadline biểu diễn thời điểm cuối cùng mà toàn operation còn giá trị. Mỗi downstream call nên biết remaining budget thay vì tự đặt timeout cố định không liên quan tới deadline của caller.

**Vấn đề nó giải quyết:**
Giả sử frontend chỉ chờ 2 giây nhưng API A gọi B với timeout 5 giây và B gọi C với timeout 10 giây. Khi caller đã bỏ cuộc, downstream vẫn có thể tiếp tục tiêu thụ thread, connection và compute cho công việc không còn ai cần, làm overload nặng hơn trong incident.

**Ví dụ thực tế:**
```text
Client deadline:        2000 ms
API A xử lý:             250 ms
Remaining budget:       1750 ms
API B xử lý:             500 ms
Remaining budget:       1250 ms
Call tới C phải <= remaining budget
```

Trong .NET, deadline thường được chuyển thành `CancellationToken`/timeout phù hợp ở boundary và propagate xuống dependency call.

**Trade-off:**
Deadline propagation giảm wasted work và cascading latency, nhưng cần contract/context propagation xuyên service, clock/timeout semantics rõ ràng và handling cancellation đúng. Timeout quá ngắn có thể làm operation fail dù dependency vẫn khỏe nhưng hơi chậm dưới load.

**Middle → Senior insight:**
Middle developer cần truyền `CancellationToken` xuyên call chain thay vì tạo token mới tùy tiện. Senior / Technical developer phải thiết kế latency budget theo SLO, reserve thời gian cho retry/fallback, và đảm bảo cancellation không làm business state dở dang hoặc vi phạm invariant.

### Design 2 — Anti-Corruption Layer bảo vệ domain mới khỏi model của legacy hoặc vendor

**Khái niệm:**
Anti-Corruption Layer trong Domain-Driven Design đặt một translation boundary giữa domain của hệ thống và model/contract của hệ thống bên ngoài. Mục tiêu là không để vocabulary và constraint của legacy/vendor lan trực tiếp vào core domain.

**Vấn đề nó giải quyết:**
Nếu application dùng trực tiếp DTO, enum và status code của một ERP hoặc CMS vendor ở khắp business logic, mọi thay đổi vendor sẽ lan rộng. Tệ hơn, domain model nội bộ bị ép phản ánh những khái niệm không phù hợp với business của chính hệ thống.

**Ví dụ thực tế:**
```text
Vendor API:
status = 7
customer_type = "P"

Anti-Corruption Layer:
VendorCustomerMapper
    -> CustomerStatus.Active
    -> CustomerKind.Person

Core domain chỉ biết model nội bộ
```

**Trade-off:**
ACL thêm mapping code, test và maintenance cost. Với integration rất nhỏ hoặc contract gần như trùng hoàn toàn và ổn định, abstraction dày có thể không đáng. Nhưng ở integration chiến lược, nó giảm coupling và tạo migration seam rõ ràng.

**Middle → Senior insight:**
Middle developer cần tránh truyền vendor DTO xuyên application layer. Senior / Technical developer phải xác định boundary nào đáng bảo vệ, ownership của mapping, error semantics, version compatibility và cách xử lý khi external model không ánh xạ 1:1 sang domain nội bộ.

### Design 3 — Elasticsearch index nên được xem là derived read model, không phải source of truth

**Khái niệm:**
Trong phần lớn hệ thống transactional, Elasticsearch index là projection được xây từ dữ liệu authoritative ở SQL/MongoDB hoặc domain events. Vì vậy thiết kế phải chấp nhận index có thể tạm thời stale, thiếu document hoặc cần rebuild.

**Vấn đề nó giải quyết:**
Nếu business workflow phụ thuộc vào assumption rằng database và search index luôn atomic, partial failure sẽ tạo inconsistency khó sửa: transaction DB commit nhưng indexing fail, hoặc index update thành công rồi database rollback.

**Ví dụ thực tế:**
```text
Order/Product DB commit
-> Outbox/Event
-> Indexer consumer
-> Elasticsearch projection

Indexer fail
-> retry / dead-letter / replay

Index hỏng toàn bộ
-> rebuild từ authoritative source
```

Search result có thể eventual consistent, nhưng checkout hoặc permission decision quan trọng vẫn nên xác nhận lại ở authoritative store nếu correctness yêu cầu.

**Trade-off:**
Derived index cho phép full-text search, aggregation và query model tối ưu mà không bóp méo transactional schema, nhưng thêm synchronization pipeline, lag, replay, observability và rebuild cost. Dual-write trực tiếp đơn giản hơn lúc đầu nhưng tạo failure window khó kiểm soát.

**Middle → Senior insight:**
Middle developer cần hiểu Elasticsearch không phải nơi duy nhất giữ business state. Senior / Technical developer phải thiết kế indexing contract, idempotency, ordering, replay, freshness SLO, zero-downtime reindex và reconciliation để system tự phục hồi khi projection lệch khỏi source of truth.
