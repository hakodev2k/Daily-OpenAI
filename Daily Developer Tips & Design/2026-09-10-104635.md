# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure cho background processing

**Mẹo:**
Khi API hoặc producer tạo work nhanh hơn consumer xử lý, dùng bounded `Channel<T>` thay vì queue không giới hạn để giới hạn số item đang chờ và tạo backpressure rõ ràng.

**Tại sao hữu ích:**
Queue không giới hạn có thể che giấu overload cho đến khi memory tăng mạnh hoặc latency của job lên hàng phút. Bounded channel buộc hệ thống thể hiện capacity limit sớm hơn, giúp bạn chọn rõ behavior khi đầy: chờ, reject hoặc drop theo business requirement.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<WorkItem>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(item, ct);
```

**Lưu ý:**
Không chọn capacity tùy ý. Capacity phải dựa trên throughput, processing time và memory footprint. Nếu producer là HTTP request, việc chờ queue quá lâu có thể chỉ chuyển overload thành request timeout.

### Tip 2 — Khi EF Core query chạy rất thường xuyên, cân nhắc compiled query sau khi đã đo translation cost

**Mẹo:**
Với query shape ổn định và được gọi ở hot path với tần suất cao, có thể cân nhắc `EF.CompileQuery` hoặc `EF.CompileAsyncQuery` nếu profiling cho thấy query compilation/translation là chi phí đáng kể.

**Tại sao hữu ích:**
EF Core đã cache query compilation theo query shape, nên compiled query thủ công không phải mặc định nhanh hơn đáng kể. Lợi ích rõ nhất xuất hiện khi cùng một query được gọi cực nhiều lần và overhead phía client thực sự đáng đo.

**Ví dụ:**
```csharp
private static readonly Func<AppDbContext, int, IAsyncEnumerable<Order>>
    GetRecentOrders = EF.CompileAsyncQuery(
        (AppDbContext db, int customerId) =>
            db.Orders
              .Where(x => x.CustomerId == customerId)
              .OrderByDescending(x => x.CreatedAt)
              .Take(20));
```

**Lưu ý:**
Đừng dùng compiled query để che query SQL tệ, thiếu index hoặc N+1. Database execution time thường lớn hơn nhiều so với translation overhead.

### Tip 3 — Khi SQL query lúc nhanh lúc chậm, kiểm tra parameter-sensitive plan trước khi đổ lỗi cho database load

**Mẹo:**
Nếu cùng một stored procedure hoặc parameterized query có latency thay đổi lớn theo input, kiểm tra execution plan và data distribution để xác định plan có phù hợp cho mọi parameter hay không.

**Tại sao hữu ích:**
Một parameter có thể trả vài row trong khi parameter khác trả hàng triệu row. Plan tối ưu cho trường hợp nhỏ có thể rất tệ cho trường hợp lớn. Symptom thường là query “đột nhiên chậm” dù SQL text không thay đổi.

**Ví dụ:**
```text
Tenant A: 800 rows
Tenant B: 18,000,000 rows

Cùng query, cùng plan
-> Tenant A: 20 ms
-> Tenant B: 7 s
```

Điều tra bằng actual execution plan, row estimates, statistics và Query Store trước khi chọn biện pháp như recompile, plan strategy hoặc thay đổi query shape.

**Lưu ý:**
Không dùng `OPTION (RECOMPILE)` cho mọi query theo phản xạ. Recompile giảm plan reuse và tăng CPU compilation; phải cân nhắc frequency và workload.

### Tip 4 — Dùng Managed Identity để ứng dụng Azure truy cập Key Vault thay vì lưu credential dài hạn

**Mẹo:**
Khi App Service, Function hoặc workload Azure cần đọc secret từ Azure Key Vault, ưu tiên Managed Identity và RBAC thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ lifecycle của credential dài hạn khỏi application: không cần nhúng secret vào pipeline, appsettings hoặc secret store khác chỉ để truy cập Key Vault. Azure quản lý credential rotation ở phía identity.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Trong Azure, `DefaultAzureCredential` có thể sử dụng Managed Identity của workload; local development có thể dùng developer credential phù hợp.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Identity vẫn phải được cấp đúng scope, và application không nên có quyền đọc toàn bộ secret nếu chỉ cần một phạm vi nhỏ.

### Tip 5 — Trong frontend, hủy request cũ khi search-as-you-type để tránh race condition hiển thị dữ liệu cũ

**Mẹo:**
Với autocomplete hoặc live search, dùng `AbortController` hoặc cancellation mechanism tương đương để hủy request trước khi gửi request mới.

**Tại sao hữu ích:**
Response không đảm bảo về đúng thứ tự gửi. Request cho `rea` có thể trả sau request `react`, khiến UI ghi đè kết quả mới bằng dữ liệu cũ dù backend hoàn toàn đúng.

**Ví dụ:**
```ts
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  });

  return await res.json();
}
```

**Lưu ý:**
Cancellation phía client không đảm bảo server đã dừng xử lý. Backend vẫn nên propagate cancellation khi có thể và không dựa vào việc client abort để bảo vệ business invariant.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read/write model thực sự có pressure khác nhau

**Khái niệm:**
CQRS tách mô hình xử lý command khỏi mô hình phục vụ query. Giá trị của nó nằm ở việc cho phép hai phía tiến hóa khác nhau, không phải ở việc tạo thêm `CommandHandler` và `QueryHandler` cho mọi CRUD endpoint.

**Vấn đề nó giải quyết:**
Một hệ thống có write model giàu invariant nhưng read side cần projection khác hoàn toàn cho dashboard, search hoặc reporting. Nếu ép cả hai dùng chung entity model, query trở nên phức tạp hoặc domain model bị bóp méo theo nhu cầu UI.

**Ví dụ thực tế:**
```text
Write side:
Order aggregate
- validate state transition
- enforce payment invariant

Read side:
OrderDashboardView
- customer name
- payment status
- shipment status
- denormalized summary
```

Read model có thể vẫn nằm trong cùng database và transaction boundary; CQRS không bắt buộc Microservices hay Event Sourcing.

**Trade-off:**
CQRS tăng khả năng tối ưu từng phía và giữ domain model sạch hơn, nhưng thêm model, mapping, synchronization và cognitive load. Với CRUD đơn giản, một model trực tiếp thường rẻ và dễ maintain hơn.

**Middle → Senior insight:**
Middle developer cần hiểu command và query có mục tiêu khác nhau nhưng không tách lớp máy móc. Senior / Technical developer phải nhận diện khi read/write pressure, consistency requirement và team complexity đủ lớn để justify CQRS.

### Design 2 — Idempotency key cho API tạo side effect dưới retry

**Khái niệm:**
Idempotency key cho phép server nhận biết nhiều request retry thuộc cùng một logical operation và tránh thực hiện side effect lặp lại.

**Vấn đề nó giải quyết:**
Client có thể timeout sau khi server đã tạo order hoặc charge payment nhưng chưa nhận response. Nếu client retry cùng request mà server không có deduplication, hệ thống có thể tạo hai order hoặc charge hai lần.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: checkout-8f312

Lần 1:
- payment thành công
- response bị mất

Lần 2:
- server tìm thấy key đã hoàn tất
- trả lại kết quả cũ
- không charge lại
```

Server cần lưu key cùng request fingerprint, trạng thái xử lý và result trong một retention window phù hợp.

**Trade-off:**
Idempotency tăng reliability dưới retry nhưng thêm storage, concurrency control, expiry policy và handling cho request cùng key nhưng payload khác. Key scope cũng phải được định nghĩa theo user/tenant/use case.

**Middle → Senior insight:**
Middle developer cần hiểu retry có thể tạo duplicate side effect. Senior / Technical developer phải thiết kế atomicity giữa deduplication record và business write, xử lý concurrent duplicate request, retention và semantics khi operation đang `InProgress`.

### Design 3 — Chọn transaction isolation level theo invariant, không mặc định tăng lên mức cao nhất

**Khái niệm:**
Isolation level kiểm soát loại anomaly mà transaction có thể quan sát hoặc tạo ra. Mức isolation cao hơn thường tăng tính nhất quán nhưng có thể tăng blocking, version-store pressure hoặc giảm concurrency.

**Vấn đề nó giải quyết:**
Một workflow như “chỉ còn một slot cuối cùng” có invariant khác hoàn toàn một màn hình reporting chấp nhận snapshot hơi cũ. Dùng cùng isolation strategy cho cả hai có thể hoặc quá yếu về correctness, hoặc quá đắt về throughput.

**Ví dụ thực tế:**
```text
Booking cuối cùng:
- cần chống hai transaction cùng xác nhận một capacity
- có thể dùng atomic update, optimistic concurrency hoặc isolation phù hợp

Dashboard doanh thu:
- thường ưu tiên read consistency đủ tốt và không block transaction ghi
```

Không nên chỉ tăng lên `Serializable` khi gặp race condition; có thể invariant được enforce tốt hơn bằng unique constraint, conditional update hoặc concurrency token.

**Trade-off:**
Isolation mạnh hơn giảm một số anomaly nhưng thường tăng contention hoặc resource cost. Isolation thấp hơn cải thiện concurrency nhưng application phải chấp nhận hoặc tự xử lý một số inconsistency.

**Middle → Senior insight:**
Middle developer cần hiểu transaction không tự giải quyết mọi race condition. Senior / Technical developer phải bắt đầu từ business invariant, chọn database primitive phù hợp và đánh giá blocking, retry behavior, throughput cũng như failure mode trước khi quyết định isolation level.
