# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian

**Mẹo:**
Với .NET 8+, inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` ở business logic cần test deterministic như expiration, retry window hoặc scheduled behavior.

**Tại sao hữu ích:**
Clock toàn cục làm test phụ thuộc thời gian thực, dễ flaky ở boundary và buộc test phải `Delay`. `TimeProvider` biến thời gian thành dependency có thể kiểm soát, giúp mô phỏng expiration hoặc time jump mà không chờ thật.

**Ví dụ:**
```csharp
public sealed class TokenPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        clock.GetUtcNow() >= expiresAt;
}
```

Trong test có thể dùng controllable/fake time provider để đưa clock qua expiration boundary.

**Lưu ý:**
Không cần abstraction clock riêng cho mọi class nếu framework abstraction đã đủ. Đồng thời phân biệt wall-clock time với elapsed-time measurement; đo duration nên dùng monotonic timestamp API phù hợp thay vì trừ hai thời điểm tùy tiện.

### Tip 2 — EF Core: dùng optimistic concurrency để tránh lost update âm thầm

**Mẹo:**
Với record có khả năng bị nhiều request chỉnh sửa đồng thời, cấu hình concurrency token như SQL Server `rowversion` và xử lý `DbUpdateConcurrencyException` thay vì mặc định “last write wins”.

**Tại sao hữu ích:**
Hai user có thể cùng đọc version 10 của một Order. User A cập nhật shipping address, user B cập nhật từ snapshot cũ và vô tình ghi đè thay đổi của A. Concurrency token khiến `UPDATE` chỉ thành công nếu version database vẫn đúng với version đã đọc.

**Ví dụ:**
```csharp
public class Order
{
    public int Id { get; set; }
    [Timestamp]
    public byte[] Version { get; set; } = [];
}
```

Khi version đã đổi, application có thể reload, merge hoặc trả conflict theo business rule.

**Lưu ý:**
Đừng tự động retry concurrency conflict bằng cách ghi lại toàn bộ state cũ; như vậy chỉ trì hoãn lost update. Conflict resolution phải hiểu field nào merge được và invariant nào cần user/business quyết định.

### Tip 3 — Elasticsearch: filter exact-value khác với full-text query

**Mẹo:**
Dùng filter/`keyword` field cho điều kiện exact như tenant, status, category; dùng analyzed text query cho full-text search. Đừng áp cùng một kiểu query cho cả hai nhu cầu.

**Tại sao hữu ích:**
`text` field thường qua analyzer/tokenization để phục vụ relevance, còn `keyword` giữ giá trị exact cho filtering, sorting và aggregation. Query sai mapping có thể cho kết quả khó hiểu hoặc tốn scoring không cần thiết.

**Ví dụ:**
```json
{
  "bool": {
    "filter": [
      { "term": { "tenantId": "acme" } },
      { "term": { "status": "published" } }
    ],
    "must": [
      { "match": { "title": "wireless keyboard" } }
    ]
  }
}
```

**Lưu ý:**
Mapping là contract dữ liệu quan trọng; đổi analyzer/mapping thường cần reindex. Đừng cố sửa relevance issue chỉ bằng query nếu index-time analysis đã không phù hợp với search semantics.

### Tip 4 — CI/CD: artifact phải immutable giữa các environment

**Mẹo:**
Build application một lần, tạo versioned artifact/container image rồi promote chính artifact đó qua test, staging và production. Environment-specific configuration nên được inject lúc deploy/runtime thay vì rebuild source cho từng môi trường.

**Tại sao hữu ích:**
Nếu production được build lại riêng, artifact đã test không còn chính xác là artifact được release. Dependency resolution, generated files hoặc build settings có thể khác và tạo regression khó tái hiện.

**Ví dụ:**
```text
commit abc123
 -> build app-2.7.41.zip
 -> deploy Test
 -> promote app-2.7.41.zip to Staging
 -> promote app-2.7.41.zip to Production
```

Secrets và endpoint URL nằm ngoài artifact.

**Lưu ý:**
Immutable artifact không có nghĩa configuration không cần version/control. Schema migration, feature flags và environment compatibility vẫn phải được kiểm tra trước promotion; rollback binary cũng có thể thất bại nếu database change không backward-compatible.

### Tip 5 — ASP.NET Core: giới hạn request body trước khi parse dữ liệu lớn

**Mẹo:**
Với endpoint upload/import/webhook, đặt request-size policy phù hợp và tránh materialize payload lớn vào memory nếu có thể stream hoặc parse incremental.

**Tại sao hữu ích:**
Một endpoint chấp nhận body không giới hạn có thể tạo memory pressure hoặc làm worker bận xử lý payload vượt xa business requirement. Giới hạn ở HTTP boundary giúp reject sớm trước khi allocation và downstream work tăng mạnh.

**Ví dụ:**
```text
Requirement: CSV import tối đa 25 MB
Boundary:
- reject body > 25 MB
- stream file tới parser/storage
- giới hạn số record và processing time riêng
```

Size limit chỉ là lớp đầu; record count và decompressed size cũng có thể quan trọng.

**Lưu ý:**
Đừng đặt global limit quá thấp nếu application có endpoint legitimately cần file lớn. Reverse proxy/IIS/App Service và ASP.NET Core có thể có limit ở nhiều layer; production configuration phải đồng bộ để tránh lỗi chỉ xuất hiện sau deploy.

## 🧠 Software Design

### Design 1 — Optimistic hay pessimistic concurrency phụ thuộc contention và cost của conflict

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor làm việc song song rồi phát hiện conflict khi commit; pessimistic concurrency khóa resource sớm để ngăn actor khác tạo conflict trong critical section.

**Vấn đề nó giải quyết:**
Hệ thống booking có thể có nhiều request tranh cùng một slot, trong khi profile editing thường có contention thấp. Dùng cùng một locking strategy cho cả hai workload có thể hoặc tạo lock overhead không cần thiết, hoặc gây quá nhiều failed commits ở hot resource.

**Ví dụ thực tế:**
```text
Employee profile:
contention thấp -> rowversion + detect conflict thường hợp lý.

Flash-sale inventory:
contention rất cao -> cần thiết kế atomic database operation/locking/reservation
phù hợp với invariant "không bán âm kho".
```

**Trade-off:**
Optimistic concurrency tăng parallelism và tránh giữ lock lâu nhưng conflict cần retry/merge/reject. Pessimistic locking giảm conflict ở critical section nhưng tăng blocking, deadlock risk và giảm throughput nếu transaction kéo dài.

**Middle → Senior insight:**
Middle developer cần hiểu lost update, transaction scope và cách framework/database báo conflict. Senior / Technical developer phải đánh giá contention distribution, invariant, lock duration, retry cost và user experience để chọn strategy; không mặc định optimistic hay pessimistic là tốt hơn.

### Design 2 — Azure Functions hay Worker Service dựa trên workload lifecycle

**Khái niệm:**
Azure Functions phù hợp với event-driven execution có hosting/scaling do platform quản lý; Worker Service phù hợp khi cần process dài hạn với lifecycle, resource model và execution control rõ hơn.

**Vấn đề nó giải quyết:**
Một team cần xử lý Blob-created events và đồng thời có một processor duy trì pipeline dài, nhiều in-memory state hoặc polling behavior đặc thù. Chọn hosting model chỉ vì “serverless rẻ hơn” hoặc “Worker dễ code hơn” bỏ qua operational characteristics thực tế.

**Ví dụ thực tế:**
```text
Blob upload -> resize thumbnail ngắn, độc lập:
Azure Function là candidate tốt.

Continuous ingestion processor với connection dài,
custom backpressure và controlled shutdown:
Worker Service có thể đơn giản hơn để vận hành.
```

**Trade-off:**
Functions giảm infrastructure management và scale theo trigger nhưng có platform/runtime constraints, cold-start/cost characteristics và retry semantics phải hiểu rõ. Worker Service cho nhiều control hơn nhưng team chịu trách nhiệm hosting, scaling, health và deployment capacity.

**Middle → Senior insight:**
Middle developer cần implement idempotency, cancellation và failure handling đúng với hosting model. Senior / Technical developer phải so workload duration, burstiness, scaling, cost, retry semantics, observability và operational ownership trước khi chọn compute model.

### Design 3 — Strangler Fig giảm rủi ro khi hiện đại hóa legacy system

**Khái niệm:**
Strangler Fig migration chuyển từng capability hoặc traffic slice khỏi legacy system sang implementation mới theo thời gian, thay vì rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Một ASP.NET/.NET Framework monolith lớn có nhiều business rule ẩn, integration cũ và release pressure liên tục. Big-bang rewrite kéo dài feedback loop và dễ phát hiện requirement bị bỏ sót quá muộn.

**Ví dụ thực tế:**
```text
Existing IIS application
        |
   routing boundary
    /          \
legacy       new ASP.NET Core
orders       product-search

Sau khi product-search ổn định,
tiếp tục migrate capability kế tiếp.
```

Database có thể vẫn shared ở giai đoạn đầu nếu tách data ownership ngay làm migration quá rủi ro, nhưng đó phải là transitional constraint có kế hoạch.

**Trade-off:**
Incremental migration giảm blast radius và tạo value sớm, nhưng trong một thời gian phải vận hành hai stack, routing/integration phức tạp hơn và dễ hình thành trạng thái “tạm thời vĩnh viễn”.

**Middle → Senior insight:**
Middle developer cần giữ behavior compatibility và xây characterization/integration tests quanh phần đang migrate. Senior / Solution-oriented engineer phải chọn seam theo business capability, thiết kế coexistence/data migration, observability và exit criteria để modernization thực sự hội tụ thay vì chỉ thêm một hệ thống mới cạnh legacy.
