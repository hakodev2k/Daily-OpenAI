# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` để stream kết quả lớn thay vì buffer toàn bộ trong memory

**Mẹo:**
Khi endpoint hoặc background pipeline đọc nhiều record nhưng không cần có toàn bộ dữ liệu cùng lúc, cân nhắc `IAsyncEnumerable<T>` để xử lý hoặc stream từng phần tử khi dữ liệu đến thay vì `ToListAsync()` rồi giữ cả collection trong memory.

**Tại sao hữu ích:**
Buffer toàn bộ 100.000 record làm tăng peak memory, GC pressure và thời gian chờ trước byte đầu tiên được gửi. Streaming cho phép producer và consumer tiến triển đồng thời, đặc biệt hữu ích với export lớn, data pipeline hoặc API trả sequence dài.

**Ví dụ:**
```csharp
await foreach (var order in db.Orders
    .AsNoTracking()
    .Where(x => x.CreatedAt >= from)
    .AsAsyncEnumerable()
    .WithCancellation(ct))
{
    await writer.WriteLineAsync($"{order.Id},{order.Total}");
}
```

Không cần materialize toàn bộ `Orders` trước khi bắt đầu ghi file.

**Lưu ý:**
Streaming giữ database reader/connection mở lâu hơn. Nếu consumer đọc rất chậm, bạn có thể giữ tài nguyên quý trong thời gian dài. Đồng thời phải propagate cancellation và tránh gọi navigation lazy-loading trong loop vì có thể tạo N+1 queries.

### Tip 2 — Trong Elasticsearch, dùng `filter` cho điều kiện exact-match không cần relevance score

**Mẹo:**
Khi điều kiện chỉ là constraint như `tenantId`, `status`, date range hoặc category exact-match, ưu tiên `bool.filter` thay vì đặt tất cả vào `must` như full-text query.

**Tại sao hữu ích:**
`filter` không tính relevance score cho điều kiện không cần ranking và có thể tận dụng caching/query execution tối ưu hơn. Nó cũng thể hiện intent rõ: đây là điều kiện lọc, không phải tín hiệu xếp hạng.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "wireless headset" } }
      ],
      "filter": [
        { "term": { "tenantId": "t-42" } },
        { "term": { "status": "active" } },
        { "range": { "price": { "lte": 200 } } }
      ]
    }
  }
}
```

Full-text nằm trong scoring query; business constraints nằm trong filter context.

**Lưu ý:**
Muốn `term` exact-match hoạt động đúng, mapping phải phù hợp, thường là field kiểu `keyword`. Dùng `term` lên field `text` đã qua analyzer có thể cho kết quả sai kỳ vọng. Đừng tối ưu DSL trước khi kiểm tra mapping và query profile thực tế.

### Tip 3 — Khi production chậm, xem dependency latency riêng trước khi đổ lỗi cho API code

**Mẹo:**
Với Application Insights hoặc OpenTelemetry, tách request latency khỏi dependency latency: SQL, HTTP outbound, Redis, Service Bus hoặc external API. Một endpoint chậm không có nghĩa code ASP.NET Core bên trong endpoint đang tốn CPU.

**Tại sao hữu ích:**
Nếu p95 request tăng từ 300 ms lên 2,5 s nhưng span SQL vẫn 40 ms và external payment API tăng từ 120 ms lên 2,2 s, bottleneck đã khá rõ. Việc tối ưu serialization hoặc refactor controller trong trường hợp đó chỉ tạo noise.

**Ví dụ:**
```text
GET /checkout p95 = 2.6s

Trace breakdown:
- validation: 8ms
- SQL: 55ms
- pricing service: 140ms
- payment provider: 2.31s
- serialization: 12ms
```

Reasoning hợp lý là kiểm tra timeout, dependency telemetry, recent changes và provider health trước khi thay code business.

**Lưu ý:**
Telemetry có thể bị sampling hoặc thiếu instrumentation. Một trace đẹp chưa chắc đại diện toàn bộ traffic. Luôn đối chiếu với metric tổng, error rate, dependency failure, deployment timeline và sample đủ lớn trước khi kết luận root cause.

### Tip 4 — Chỉ dùng `Cache-Control: immutable` cho asset có fingerprint trong URL

**Mẹo:**
Với CSS, JavaScript, font hoặc image build artifact, chỉ đặt cache rất dài + `immutable` khi filename hoặc URL thay đổi theo content hash, ví dụ `app.8f3c21.js`.

**Tại sao hữu ích:**
Browser/CDN có thể cache asset trong nhiều tháng mà không cần revalidate, giảm network round trip và cải thiện load time. Content hash đảm bảo khi file thay đổi, URL mới cũng thay đổi nên cache cũ không làm user nhận code stale.

**Ví dụ:**
```http
/app.8f3c21.js
Cache-Control: public, max-age=31536000, immutable
```

Trong khi HTML shell thường nên có policy ngắn hơn hoặc revalidation để nhanh chóng tham chiếu sang bundle version mới.

**Lưu ý:**
Đặt `immutable` cho `/app.js` nhưng deploy nội dung mới dưới cùng URL có thể khiến user giữ version cũ rất lâu. Caching strategy phải thiết kế đồng bộ giữa bundler, CDN, HTML và deployment rollback.

### Tip 5 — Khi review authorization bug, kiểm tra resource-level permission thay vì chỉ role

**Mẹo:**
Nếu endpoint đã yêu cầu user đăng nhập và có role phù hợp nhưng vẫn có nguy cơ truy cập dữ liệu của user khác, kiểm tra authorization theo resource ownership/tenant boundary chứ không chỉ `[Authorize(Roles = ...)]`.

**Tại sao hữu ích:**
Role thường trả lời “user thuộc nhóm nào”, nhưng nhiều business rule cần trả lời “user này có được phép thao tác đúng resource này không”. Một user hợp lệ có thể đổi `/orders/42` thành `/orders/43` và truy cập order của tenant khác nếu query không gắn identity boundary.

**Ví dụ:**
```csharp
var order = await db.Orders
    .SingleOrDefaultAsync(
        x => x.Id == orderId && x.TenantId == currentTenantId,
        ct);

if (order is null)
    return Results.NotFound();
```

Với policy phức tạp, dùng resource-based authorization để gom rule vào một nơi thay vì rải điều kiện thủ công ở nhiều controller.

**Lưu ý:**
Đừng chỉ load resource theo `Id` rồi kiểm tra tenant quá muộn nếu dữ liệu nhạy cảm đã bị log, map hoặc dùng trước đó. Authorization boundary nên xuất hiện càng sớm càng tốt trong data access/application flow và phải có test cho cross-tenant access.

## 🧠 Software Design

### Design 1 — Load Shedding giúp hệ thống từ chối có kiểm soát trước khi quá tải toàn bộ

**Khái niệm:**
Load Shedding là chủ động từ chối hoặc giảm bớt một phần workload khi capacity sắp cạn, thay vì cố nhận mọi request cho tới khi thread, connection, memory hoặc downstream bị kéo sập.

**Vấn đề nó giải quyết:**
Một API có capacity ổn định khoảng 2.000 request/giây nhưng traffic spike lên 6.000. Nếu server vẫn queue tất cả request, latency tăng, timeout lan rộng, retry từ client tạo thêm tải và cuối cùng cả request quan trọng cũng fail.

**Ví dụ thực tế:**
```text
Checkout API

- request quan trọng: payment confirmation
- request ít quan trọng: recommendation widgets

Khi CPU/queue vượt threshold:
- giữ capacity cho payment path
- recommendation trả degraded response hoặc 503 nhanh
- không queue vô hạn
```

Admission control, bounded queue và priority policy có thể cùng tham gia load shedding.

**Trade-off:**
Load shedding bảo vệ availability nhưng chấp nhận một số request thất bại sớm. Threshold đặt quá thấp làm giảm throughput không cần thiết; quá cao thì hệ thống đã rơi vào overload trước khi policy hoạt động. Client retry không có backoff còn có thể phá tác dụng của shedding.

**Middle → Senior insight:**
Middle developer cần hiểu fail-fast đôi khi tốt hơn timeout hàng loạt. Senior / Technical developer phải xác định capacity signal, priority workload, retry contract, SLO và degraded mode để bảo vệ business-critical path thay vì dùng một global rate limit đơn giản cho mọi request.

### Design 2 — Read Replica tăng read throughput nhưng tạo consistency trade-off

**Khái niệm:**
Read Replica tách một phần query đọc khỏi primary database bằng cách replicate dữ liệu sang node chỉ đọc. Nó hữu ích cho report, search-like read hoặc traffic đọc lớn, nhưng replica thường có replication lag.

**Vấn đề nó giải quyết:**
Primary đang chịu cả transaction writes và nhiều dashboard/query đọc nặng. Chuyển workload read phù hợp sang replica có thể giảm contention và tăng headroom cho write path mà không phải scale primary vô hạn.

**Ví dụ thực tế:**
```text
POST /orders
-> write Primary

GET /reports/daily-sales
-> Read Replica

GET /orders/123 ngay sau khi POST
-> Primary nếu cần read-your-writes
```

Route query theo consistency requirement thay vì mặc định “mọi GET đều đọc replica”.

**Trade-off:**
Replica tăng read capacity và isolation nhưng dữ liệu có thể stale vài giây hoặc lâu hơn khi replication chậm. Failover, lag monitoring, connection routing và schema change cũng phức tạp hơn. Không phù hợp cho flow cần strong read-after-write consistency.

**Middle → Senior insight:**
Middle developer cần biết replica không phải bản sao đồng bộ tuyệt đối. Senior / Solution-oriented engineer phải phân loại read path theo freshness requirement, xác định fallback khi lag tăng và cân bằng scale benefit với operational complexity trước khi thêm replica.

### Design 3 — Tách Domain Event và Integration Event để không rò rỉ internal model ra ngoài boundary

**Khái niệm:**
Domain Event mô tả một sự kiện có ý nghĩa bên trong bounded context; Integration Event là contract được publish cho hệ thống khác. Hai event có thể liên quan nhưng không nhất thiết là cùng một object hoặc cùng schema.

**Vấn đề nó giải quyết:**
Nếu publish thẳng internal domain event ra broker, một refactor trong domain có thể vô tình trở thành breaking change cho consumer bên ngoài. Internal model và external contract khi đó bị coupling chặt.

**Ví dụ thực tế:**
```text
Domain event:
OrderPaymentCaptured
- OrderId
- PaymentAttempt
- InternalPolicyData

Integration event:
OrderPaidV1
- OrderId
- PaidAt
- Amount
- Currency
```

Application layer có thể chuyển domain event thành integration event sau khi transaction phù hợp được commit, thường kết hợp Outbox khi cần reliability.

**Trade-off:**
Tách hai loại event tăng mapping và số contract phải quản lý, nhưng đổi lại boundary rõ và khả năng evolve độc lập tốt hơn. Với monolith nhỏ không có external consumer, việc tạo integration event riêng cho mọi domain event có thể là abstraction thừa.

**Middle → Senior insight:**
Middle developer cần phân biệt “event xảy ra trong domain” với “contract công khai cho hệ thống khác”. Senior / Technical developer phải quyết định event nào thực sự đáng expose, versioning strategy, transaction boundary và mức semantic stability mà consumer bên ngoài có thể dựa vào.
