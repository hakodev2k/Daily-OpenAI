# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong ASP.NET Core

**Mẹo:**
Khi API latency tăng mạnh nhưng CPU chưa chạm trần, kiểm tra ThreadPool queue length, thread count và các điểm sync-over-async trước khi kết luận máy chủ thiếu CPU.

**Tại sao hữu ích:**
ThreadPool starvation xảy ra khi request đang chờ thread rảnh để tiếp tục xử lý. Các lệnh như `.Result`, `.Wait()` hoặc blocking I/O có thể giữ worker thread quá lâu, khiến throughput sụt dù CPU vẫn còn dư.

**Ví dụ:**
```csharp
// Không tốt trong async request pipeline
var result = httpClient.GetStringAsync(url).Result;

// Tốt hơn
var result = await httpClient.GetStringAsync(url, ct);
```

Trong production, correlate latency spike với `dotnet-counters`, Application Insights và thread dump để xác nhận hypothesis.

**Lưu ý:**
Thread count tăng không tự động chứng minh starvation. CPU-bound workload thật sự cũng có thể cần nhiều thread. Luôn kiểm tra queue, blocking stack và utilization cùng nhau.

### Tip 2 — Partition ASP.NET Core rate limiting theo identity có ý nghĩa

**Mẹo:**
Khi áp dụng rate limiting, chọn partition key theo security và business boundary như user, API key hoặc tenant thay vì chỉ dựa vào IP.

**Tại sao hữu ích:**
Nhiều user có thể đi qua cùng NAT/proxy, còn attacker có thể phân tán request qua nhiều IP. Partition sai làm legitimate traffic bị throttle hoặc khiến limit dễ bị né.

**Ví dụ:**
```csharp
options.AddPolicy("per-user", context =>
    RateLimitPartition.GetFixedWindowLimiter(
        partitionKey: context.User.Identity?.Name
            ?? context.Connection.RemoteIpAddress?.ToString()
            ?? "anonymous",
        factory: _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1)
        }));
```

**Lưu ý:**
Rate limiting không thay thế authorization hoặc abuse detection. Với endpoint login/password reset, cần policy riêng và có thể phải kết hợp nhiều signal.

### Tip 3 — Dùng partial index khi chỉ một tập nhỏ row thực sự cần được index

**Mẹo:**
Trong PostgreSQL, nếu query chủ yếu truy cập một subset ổn định như `Status = 'Pending'`, cân nhắc partial index thay vì index toàn bảng.

**Tại sao hữu ích:**
Index nhỏ hơn giảm storage, cache footprint và write maintenance cost. Nó đặc biệt hiệu quả khi điều kiện lọc chỉ bao phủ tỷ lệ nhỏ dữ liệu.

**Ví dụ:**
```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at)
WHERE status = 'Pending';
```

Query tương ứng:
```sql
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

**Lưu ý:**
Partial index chỉ hữu ích khi predicate của query tương thích với predicate của index. Nếu workload thay đổi hoặc distribution không còn selective, lợi ích có thể biến mất.

### Tip 4 — Upload file lớn lên Azure Blob bằng direct upload thay vì proxy toàn bộ qua API

**Mẹo:**
Với file lớn, cân nhắc để backend cấp SAS ngắn hạn rồi client upload trực tiếp lên Azure Blob Storage thay vì stream toàn bộ byte qua ASP.NET Core API.

**Tại sao hữu ích:**
Backend proxy làm application chịu thêm bandwidth, connection time và memory/buffer pressure. Direct upload giảm tải application tier và tận dụng storage service cho data plane.

**Ví dụ:**
```text
Client -> API: xin upload permission
API -> Client: SAS scoped cho 1 blob, expiry 10 phút
Client -> Blob Storage: upload trực tiếp
Client -> API: báo hoàn tất / finalize metadata
```

**Lưu ý:**
SAS phải giới hạn permission, path và thời gian sống. Không cấp container-wide write access chỉ để đơn giản hóa code. Backend vẫn cần validate metadata và ownership.

### Tip 5 — Với file upload, kiểm tra content thực tế thay vì tin `Content-Type` hoặc extension

**Mẹo:**
Khi nhận file từ user, coi filename, extension và HTTP `Content-Type` là dữ liệu không đáng tin; validate kích thước, signature/magic bytes và policy lưu trữ phù hợp.

**Tại sao hữu ích:**
Client có thể gửi `image/png` cho một file thực tế không phải PNG. Nếu backend chỉ tin metadata, file nguy hiểm có thể được lưu hoặc xử lý bằng pipeline không phù hợp.

**Ví dụ:**
```text
upload avatar.png
Content-Type: image/png

Backend:
1. kiểm tra size limit
2. đọc header/magic bytes
3. decode bằng image library an toàn
4. tạo tên lưu trữ riêng
5. không phục vụ trực tiếp từ executable path
```

**Lưu ý:**
Magic-byte validation không đủ để phát hiện mọi malware. Với use case rủi ro cao, cần malware scanning, quarantine và policy serving/downloading phù hợp.

## 🧠 Software Design

### Design 1 — Circuit Breaker không phải là Retry nâng cấp

**Khái niệm:**
Retry thử lại một operation vì failure có thể transient; Circuit Breaker tạm ngừng gọi dependency khi failure rate cho thấy dependency đang unhealthy.

**Vấn đề nó giải quyết:**
Nếu một payment provider đang outage, retry liên tục từ hàng nghìn request có thể tăng load lên dependency, giữ connection lâu hơn và làm latency lan sang toàn hệ thống.

**Ví dụ thực tế:**
```text
Request -> timeout
Retry 1 -> timeout
Retry 2 -> timeout

Failure rate vượt threshold
-> circuit OPEN
-> fail fast trong 30 giây
-> HALF-OPEN thử một số request probe
```

Retry phù hợp cho transient fault nhỏ; Circuit Breaker bảo vệ hệ thống khi failure kéo dài.

**Trade-off:**
Circuit Breaker giảm cascading failure và latency tích tụ, nhưng có thể từ chối request ngay cả khi dependency vừa hồi phục. Threshold và open duration phải dựa trên traffic, SLO và dependency behavior.

**Middle → Senior insight:**
Middle developer cần hiểu retry và circuit breaker giải quyết hai vấn đề khác nhau. Senior / Technical developer phải thiết kế resilience pipeline theo deadline, idempotency, fallback, concurrency và failure amplification thay vì ghép policy theo template.

### Design 2 — Database constraint là lớp bảo vệ cuối cùng cho invariant có thể biểu diễn ở database

**Khái niệm:**
Business validation trong application giúp UX và error handling, nhưng invariant như uniqueness, referential integrity hoặc giá trị hợp lệ nên được enforce thêm bằng database constraint khi có thể.

**Vấn đề nó giải quyết:**
Hai request concurrent có thể cùng vượt qua check trong application rồi cùng ghi dữ liệu. Nếu database không có unique constraint, race condition tạo state sai dù code validation trông đúng.

**Ví dụ thực tế:**
```text
Request A: email chưa tồn tại
Request B: email chưa tồn tại
A insert
B insert
```

Unique index/constraint trên normalized email khiến database bảo vệ invariant nguyên tử; application bắt violation và trả lỗi domain phù hợp.

**Trade-off:**
Constraint tăng correctness và chống race condition nhưng làm schema trở thành một phần business contract. Migration, error mapping và compatibility cần được quản lý cẩn thận.

**Middle → Senior insight:**
Middle developer cần biết validation trước insert không thay thế constraint. Senior / Technical developer phải quyết định invariant nào nên ở database, domain model hoặc distributed workflow dựa trên transaction boundary và ownership dữ liệu.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo thêm state cần quản trị

**Khái niệm:**
Feature Flag cho phép deploy code trước nhưng kiểm soát thời điểm hoặc đối tượng được kích hoạt feature sau đó.

**Vấn đề nó giải quyết:**
Một thay đổi lớn có thể cần rollout dần theo tenant, percentage hoặc internal user. Nếu release luôn đồng nghĩa với deployment, rollback duy nhất thường là redeploy toàn application.

**Ví dụ thực tế:**
```text
Deploy checkout-v2: code đã có production
Flag checkout-v2:
- 0% users
- internal users
- 5%
- 25%
- 100%
```

Metrics và error rate được theo dõi ở từng giai đoạn rollout.

**Trade-off:**
Feature Flag giảm release risk và hỗ trợ progressive delivery, nhưng mỗi flag tạo thêm nhánh runtime, test matrix và technical debt. Flag cũ không được dọn sẽ làm code khó hiểu và khó kiểm thử.

**Middle → Senior insight:**
Middle developer cần viết code hoạt động đúng ở cả flag on/off và tránh logic rải rác. Senior / Technical developer phải thiết kế ownership, expiry, observability, rollback semantics và cleanup lifecycle cho flag thay vì coi flag là `if` tạm thời vô thời hạn.
