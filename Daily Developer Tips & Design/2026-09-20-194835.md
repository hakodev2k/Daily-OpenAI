# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống database connection pooling

**Mẹo:**
Khi tối ưu EF Core throughput, phân biệt `AddDbContextPool` với ADO.NET connection pooling. `DbContext` pooling tái sử dụng context instances; connection pooling tái sử dụng physical database connections và thường hoạt động ở provider level.

**Tại sao hữu ích:**
Nhầm hai cơ chế dễ dẫn tới tuning sai. Pooling `DbContext` có thể giảm allocation/setup cost ở workload nhiều requests ngắn, nhưng không tự giải quyết database connection exhaustion, slow query hoặc transaction giữ connection quá lâu.

**Ví dụ:**
API có p99 cao và báo connection pool timeout. Bật `AddDbContextPool` không chữa nguyên nhân nếu query giữ connections 20 giây. Cần đo active connections, command duration, transaction lifetime và pool wait trước; context pooling chỉ đáng benchmark sau khi bottleneck thật đã rõ.

**Lưu ý:**
Pooled `DbContext` được tái sử dụng nên state tùy request/tenant không được cấu hình theo cách có thể rò sang lần dùng sau. Context vẫn không thread-safe và không được chia sẻ đồng thời giữa operations.

### Tip 2 — SQL deadlock phải đọc deadlock graph, không đoán từ query chậm

**Mẹo:**
Khi SQL Server báo deadlock, lấy deadlock graph/XML để xác định resources, lock modes, victim và thứ tự acquisition trước khi sửa code hoặc thêm index.

**Tại sao hữu ích:**
Deadlock là cycle của dependencies, không đơn giản là “query chạy lâu”. Hai transactions có thể đều nhanh nhưng khóa resources theo thứ tự ngược nhau. Evidence từ graph giúp phân biệt key/page locks, conversion deadlock và access path gây cycle.

**Ví dụ:**
Transaction A update Order rồi Inventory; transaction B update Inventory rồi Order. Graph cho thấy mỗi transaction giữ một lock và chờ lock còn lại. Chuẩn hóa acquisition order hoặc thu hẹp transaction có thể giải quyết root cause tốt hơn việc tăng command timeout.

**Lưu ý:**
Retry deadlock victim thường cần thiết cho resilience nhưng chỉ là safety net. Nếu deadlock rate đáng kể, phải sửa access pattern/index/transaction boundary; retry vô hạn có thể khuếch đại contention.

### Tip 3 — Managed Identity tốt hơn secret khi Azure resource hỗ trợ identity-based access

**Mẹo:**
Với App Service, Functions hoặc workload Azure truy cập Key Vault, Storage hay các services hỗ trợ Microsoft Entra authentication, ưu tiên Managed Identity thay vì lưu client secret trong configuration.

**Tại sao hữu ích:**
Secret có lifecycle: tạo, phân phối, rotate và tránh leak. Managed Identity chuyển credential issuance/rotation cho platform và application lấy token theo identity, giảm secret material phải quản lý.

**Ví dụ:**
ASP.NET Core trên App Service đọc Blob Storage bằng `DefaultAzureCredential`; production dùng Managed Identity được cấp RBAC tối thiểu, local development dùng developer credential phù hợp. Không cần nhúng storage account key vào appsettings hoặc pipeline variable.

**Lưu ý:**
Managed Identity không tự tạo least privilege. RBAC quá rộng vẫn là security risk. Đồng thời phải thiết kế local-development credential chain và kiểm tra production không vô tình fallback sang credential không mong muốn.

### Tip 4 — Kubernetes readiness probe không phải liveness probe

**Mẹo:**
Thiết kế readiness để trả lời “pod có nên nhận traffic không?”, còn liveness để phát hiện process cần restart. Đừng dùng cùng một deep dependency check cho cả hai theo mặc định.

**Tại sao hữu ích:**
Nếu database tạm outage và liveness phụ thuộc database, Kubernetes có thể restart hàng loạt pods đang hoàn toàn khỏe về process, tạo restart storm đúng lúc dependency đang lỗi. Readiness có thể loại pod khỏi traffic mà không giết process.

**Ví dụ:**
ASP.NET Core app có liveness endpoint kiểm tra process/runtime tối thiểu; readiness kiểm tra initialization hoặc capability cần thiết để serve traffic. Database outage policy được thiết kế theo failure mode thay vì để mọi probe trả cùng một kết quả.

**Lưu ý:**
Probe quá nặng có thể tự tạo tải. Startup chậm nên dùng startup probe hoặc cấu hình phù hợp thay vì tăng liveness delay tùy tiện. Luôn quan sát restart count và probe latency khi tuning.

### Tip 5 — API authorization phải test negative paths, không chỉ happy path

**Mẹo:**
Với endpoint nhạy cảm, thêm integration/API tests cho anonymous user, authenticated-but-wrong-role, wrong tenant/resource owner và malformed/expired credential thay vì chỉ test user hợp lệ nhận `200`.

**Tại sao hữu ích:**
Security regression thường nằm ở boundary bị bỏ sót: endpoint mới quên policy, resource ownership check thiếu hoặc route khác expose cùng operation. Happy-path test không chứng minh unauthorized access bị chặn.

**Ví dụ:**
`GET /tenants/{tenantId}/invoices/{id}` có test xác nhận user tenant A không đọc invoice tenant B dù biết ID; test đi qua authentication/authorization pipeline thật thay vì gọi service method trực tiếp.

**Lưu ý:**
Đừng assert quá chặt vào token implementation nếu mục tiêu là authorization behavior. Phân biệt `401` authentication failure với `403` authenticated nhưng không đủ quyền và tránh leak resource existence nếu threat model yêu cầu.

## 🧠 Software Design

### Design 1 — Bulkhead Pattern giới hạn blast radius giữa workloads

**Khái niệm:**
Bulkhead Pattern chia tài nguyên/concurrency thành các vùng giới hạn để một workload hoặc dependency bị nghẽn không tiêu thụ toàn bộ capacity của process/system.

**Vấn đề nó giải quyết:**
Nếu background export, checkout và third-party synchronization cùng dùng một unbounded concurrency pool, một integration chậm có thể chiếm hết sockets, connections hoặc worker capacity khiến critical request path cũng thất bại.

**Ví dụ thực tế:**
Checkout outbound calls có concurrency budget riêng, còn low-priority catalog synchronization dùng limiter khác. Khi catalog vendor chậm, sync backlog tăng nhưng checkout vẫn giữ capacity cần thiết để đáp ứng SLO.

**Trade-off:**
Isolation tăng resilience nhưng capacity bị phân mảnh; một partition rảnh không nhất thiết cứu partition đang quá tải. Quá nhiều bulkheads làm configuration phức tạp, nên boundary phải dựa trên priority, dependency và failure domain thực tế.

**Middle → Senior insight:**
Middle developer cần nhận ra shared resource exhaustion và dùng bounded concurrency. Senior / Technical developer phải thiết kế capacity budgets theo criticality, SLO và failure propagation, đồng thời theo dõi saturation để điều chỉnh partitions dựa trên evidence.

### Design 2 — API backward compatibility là bài toán consumer contract, không chỉ version number

**Khái niệm:**
Backward compatibility nghĩa là existing consumers tiếp tục hoạt động với observable contract đã cam kết. URL `/v2` hay header version chỉ là mechanism; compatibility phụ thuộc schema, semantics, status codes và behavioral assumptions.

**Vấn đề nó giải quyết:**
Một thay đổi tưởng nhỏ như đổi enum value, biến optional field thành required hoặc đổi `404` thành `200` với empty object có thể phá mobile/client cũ dù JSON vẫn deserialize được.

**Ví dụ thực tế:**
Product API cần thêm trạng thái mới. Trước khi release, team kiểm tra consumers có xử lý unknown enum hay không, contract tests và telemetry về client versions; nếu không thể evolve additive an toàn, versioning hoặc compatibility translation được dùng có chủ đích.

**Trade-off:**
Giữ compatibility kéo dài support cost và hạn chế cleanup. Version quá thường xuyên lại nhân đôi endpoints/models và migration burden. Cần deprecation policy, consumer inventory và sunset evidence thay vì giữ mọi contract mãi mãi.

**Middle → Senior insight:**
Middle developer cần phân biệt additive với breaking changes và viết contract tests cho behavior quan trọng. Senior / Solution-oriented engineer phải quản lý lifecycle xuyên nhiều consumers, rollout order, deprecation window và observability để biết khi nào contract cũ có thể xóa.

### Design 3 — Modular Monolith cần enforce boundaries bằng code và build, không chỉ folder

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia application thành modules có ownership, public contracts và dependency rules rõ. Boundary chỉ có giá trị nếu cross-module access bị kiểm soát.

**Vấn đề nó giải quyết:**
Một monolith chia folders nhưng module nào cũng query table, reference internals và gọi service của module khác tùy ý sẽ dần trở thành tightly coupled codebase. Khi cần thay đổi hoặc tách capability, dependency graph không còn rõ.

**Ví dụ thực tế:**
Ordering chỉ reference public contracts của Catalog; internal EF entities/repositories của Catalog không được expose. Architecture tests kiểm tra forbidden references và integration giữa modules đi qua explicit interfaces/events tùy consistency requirement.

**Trade-off:**
Boundary enforcement thêm projects, contracts, mapping và architecture tests. Nếu domain nhỏ, chia quá nhiều modules gây ceremony. Ngược lại, module boundary tốt thường cho phần lớn lợi ích về maintainability mà chưa phải trả network/operations cost của Microservices.

**Middle → Senior insight:**
Middle developer cần tôn trọng module public surface và tránh shortcut qua database/internal types. Senior / Technical developer phải chọn boundaries theo business capability/change coupling, enforce dependency direction và chỉ tách service khi scaling, autonomy hoặc failure isolation tạo đủ áp lực.
