# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Truyền `CancellationToken` xuyên suốt call chain thay vì chỉ nhận ở Controller

**Mẹo:**
Khi endpoint ASP.NET Core nhận `CancellationToken`, hãy truyền token đó qua service, repository, EF Core và HTTP client call thay vì bỏ mất giữa chừng.

**Tại sao hữu ích:**
Nếu client đóng kết nối, reverse proxy timeout hoặc request bị hủy, application có thể dừng công việc không còn giá trị. Nếu token bị bỏ qua, database query, HTTP call hoặc background work vẫn tiếp tục tiêu tốn thread, connection và I/O dù kết quả không còn ai cần.

**Ví dụ:**
```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    CancellationToken cancellationToken) =>
{
    var order = await service.GetAsync(id, cancellationToken);
    return order is null ? Results.NotFound() : Results.Ok(order);
});

public Task<Order?> GetAsync(Guid id, CancellationToken cancellationToken)
{
    return dbContext.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);
}
```

Nếu service gọi external API:
```csharp
await httpClient.GetAsync(uri, cancellationToken);
```

**Lưu ý:**
`CancellationToken` là cooperative cancellation, không phải cưỡng chế kill code đang chạy. Code CPU-bound hoặc library không quan sát token sẽ không dừng ngay. Không nuốt `OperationCanceledException` rồi log như application error nếu cancellation là expected control flow.

### Tip 2 — Khi SQL query chậm bất thường, kiểm tra cardinality estimate và execution plan trước khi thêm index

**Mẹo:**
Nếu một query đôi lúc chạy vài chục millisecond nhưng đôi lúc thành vài giây, hãy xem actual execution plan, estimated rows so với actual rows, statistics và parameter-dependent plan behavior trước khi phản xạ bằng cách thêm index mới.

**Tại sao hữu ích:**
Optimizer chọn join strategy, memory grant và access path dựa trên cardinality estimate. Nếu estimate sai lớn, SQL Server có thể chọn Nested Loops khi thực tế cần Hash Join, cấp thiếu memory làm spill sang tempdb hoặc chọn index access path không phù hợp.

**Ví dụ:**
Một query:
```sql
SELECT o.Id, o.TotalAmount
FROM Orders o
WHERE o.CustomerId = @customerId
  AND o.CreatedAt >= @fromDate;
```

Có thể chạy tốt với customer có 20 orders nhưng rất chậm với customer có vài triệu rows nếu cached plan được compile từ parameter có selectivity hoàn toàn khác.

Khi điều tra, xem:
```text
Estimated Rows: 10
Actual Rows: 480,000
```

Khoảng cách lớn này là signal cần phân tích statistics, data skew, parameter sniffing/parameter-sensitive plan behavior hoặc query shape.

**Lưu ý:**
Thêm index có thể tăng write cost, storage, maintenance và vẫn không xử lý nguyên nhân nếu optimizer estimate sai. Performance tuning tốt bắt đầu bằng evidence từ plan và runtime metrics, không bắt đầu bằng danh sách index giả định.

### Tip 3 — Dùng `IHttpClientFactory` nhưng vẫn phải đặt timeout và retry theo operation semantics

**Mẹo:**
`IHttpClientFactory` giúp quản lý handler lifecycle và tránh socket exhaustion, nhưng nó không tự biến outbound call thành resilient. Hãy cấu hình timeout, retry/backoff và circuit-breaking theo tính chất của từng integration.

**Tại sao hữu ích:**
Một dependency chậm có thể giữ request của bạn mở hàng chục giây, chiếm connection, memory và request concurrency. Retry thiếu kiểm soát còn có thể nhân traffic đúng lúc downstream đang lỗi.

**Ví dụ:**
Với operation đọc idempotent, retry ngắn có thể hợp lý:
```text
Attempt 1 -> timeout/transient 503
wait 200 ms + jitter
Attempt 2
wait 500 ms + jitter
Attempt 3
```

Nhưng với operation:
```http
POST /payments
```

retry mù có thể tạo duplicate payment nếu API phía ngoài không hỗ trợ idempotency key.

**Lưu ý:**
Timeout nên phản ánh end-to-end latency budget. Nếu request inbound chỉ có SLA 2 giây thì timeout 30 giây cho downstream là vô nghĩa. Retry chỉ dành cho transient failure và phải xét idempotency, retry amplification và khả năng downstream đang overload.

### Tip 4 — Với Vue, tránh destructure trực tiếp reactive object khi cần giữ reactivity

**Mẹo:**
Trong Vue 3 Composition API, destructure property trực tiếp từ `reactive()` có thể làm mất reactive connection. Dùng `toRefs()`, `toRef()` hoặc truy cập qua object gốc khi cần property tiếp tục phản ứng với thay đổi.

**Tại sao hữu ích:**
Đây là lỗi khó nhìn vì giá trị ban đầu vẫn đúng, nhưng UI không update sau mutation. Developer có thể tưởng API state, watcher hoặc render pipeline lỗi trong khi nguyên nhân là đã tách primitive khỏi reactive proxy.

**Ví dụ:**
Không nên:
```ts
const state = reactive({ count: 0, status: 'idle' })
const { count } = state

state.count++
console.log(count) // vẫn là giá trị cũ
```

Nên:
```ts
const state = reactive({ count: 0, status: 'idle' })
const { count, status } = toRefs(state)

state.count++
console.log(count.value)
```

Hoặc đơn giản giữ:
```ts
state.count
```

**Lưu ý:**
Không phải mọi state đều cần `reactive()`. Với primitive độc lập, `ref()` thường rõ hơn. Khi thiết kế composable, chọn representation giúp caller hiểu rõ ownership và reactivity semantics thay vì trộn `ref`, `reactive` và plain object tùy ý.

### Tip 5 — Trên Azure, ưu tiên Managed Identity thay vì lưu client secret trong configuration

**Mẹo:**
Khi workload chạy trên Azure App Service, Azure Functions, VM hoặc tài nguyên hỗ trợ Managed Identity, ưu tiên identity-based authentication tới Key Vault, Blob Storage, Service Bus hoặc database thay vì nhúng secret vào appsettings/environment variables.

**Tại sao hữu ích:**
Secret-based authentication tạo lifecycle riêng: phát hành, lưu trữ, rotation, expiration và nguy cơ leakage qua pipeline/log/config dump. Managed Identity chuyển phần credential issuance/rotation cho Azure và application chỉ cần request token cho target resource.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);
```

Ở local, `DefaultAzureCredential` có thể dùng developer credential phù hợp; khi deploy Azure, nó có thể dùng Managed Identity của workload.

**Lưu ý:**
Managed Identity không tự động cấp quyền. Bạn vẫn phải thiết kế RBAC/role assignment theo least privilege. Đừng cấp Contributor chỉ để application đọc Blob hoặc lấy secret. Authentication tốt mà authorization quá rộng vẫn là security risk.

## 🧠 Software Design

### Design 1 — Retry và Circuit Breaker giải quyết hai failure mode khác nhau

**Khái niệm:**
Retry giả định failure có khả năng transient và operation có thể thành công nếu thử lại. Circuit Breaker giả định dependency đang unhealthy đủ lâu để việc tiếp tục gọi chỉ làm lãng phí resource hoặc tăng tải cho hệ thống đang lỗi.

**Vấn đề nó giải quyết:**
Nếu mọi request đều retry 3 lần khi downstream đang down hoàn toàn, hệ thống có thể biến 1,000 request thành 4,000 outbound attempts. Điều này tăng latency, thread/connection pressure và kéo dài recovery của dependency.

**Ví dụ thực tế:**
Một Product API thỉnh thoảng trả 503 trong vài trăm millisecond:
```text
Request -> transient 503 -> retry with jitter -> success
```

Nhưng nếu API lỗi liên tục:
```text
Failures vượt threshold
-> circuit OPEN
-> reject nhanh trong 30s
-> HALF-OPEN probe
-> nếu healthy thì CLOSE
```

**Trade-off:**
Retry cải thiện success rate cho lỗi ngắn nhưng làm tăng latency và load. Circuit Breaker giảm cascading failure nhưng có thể reject request dù dependency vừa hồi phục trước thời điểm probe. Hai pattern thường phối hợp nhưng phải có budget và policy rõ ràng.

**Middle → Senior insight:**
Middle developer cần biết không retry mọi exception và hiểu idempotency. Senior / Technical developer phải thiết kế resilience theo latency budget, traffic volume, dependency capacity và failure amplification; đồng thời quyết định fallback hoặc degraded mode khi circuit mở.

### Design 2 — Modular Monolith nên có boundary thực thi được, không chỉ chia folder theo module

**Khái niệm:**
Modular Monolith vẫn deploy như một application, nhưng module phải có ownership rõ về domain logic, data access và public contract. Nếu module A có thể query trực tiếp table hoặc gọi internal class của module B tùy ý thì đó chỉ là layered monolith với folder đẹp hơn.

**Vấn đề nó giải quyết:**
Monolith thường xuống cấp vì dependency lan ngang: Order gọi class nội bộ của Catalog, Catalog đọc table Customer, Reporting reuse entity của mọi module. Sau vài năm, mọi thay đổi đều có blast radius lớn và gần như không thể tách module.

**Ví dụ thực tế:**
Một boundary tốt hơn:
```text
Catalog
  - owns Product model/table
  - exposes query contract / integration event

Ordering
  - does not access Catalog DbSet directly
  - stores only product snapshot needed for Order invariant
```

Nếu cần synchronous interaction, expose module API/application contract rõ ràng thay vì reference infrastructure class nội bộ.

**Trade-off:**
Boundary chặt tạo thêm contract, mapping và đôi khi duplicate data. Boundary quá lỏng thì phát triển ban đầu nhanh hơn nhưng coupling tăng dần. Modular Monolith phù hợp khi cần domain modularity nhưng chưa muốn chịu distributed-system cost của Microservices.

**Middle → Senior insight:**
Middle developer cần tuân thủ module ownership và dependency direction. Senior / Technical developer phải thiết kế enforcement mechanism, transaction boundary, integration style và migration path sao cho module có thể evolve độc lập mà không biến nội bộ application thành một mạng dependency vô kiểm soát.

### Design 3 — API backward compatibility là một constraint kiến trúc, không chỉ là vấn đề version number

**Khái niệm:**
Backward compatibility nghĩa là consumer cũ tiếp tục hoạt động khi provider evolve. API versioning chỉ là một kỹ thuật quản lý thay đổi; nó không thay thế việc thiết kế contract evolution có kỷ luật.

**Vấn đề nó giải quyết:**
Một thay đổi tưởng nhỏ như rename JSON field, đổi enum value, thay nullability hoặc đổi pagination semantics có thể phá Mobile App chưa update, partner integration hoặc frontend được cache/deploy độc lập.

**Ví dụ thực tế:**
Thay vì đổi:
```json
{
  "name": "Alice"
}
```

thành:
```json
{
  "displayName": "Alice"
}
```

ngay lập tức, có thể thêm field mới trong giai đoạn migration:
```json
{
  "name": "Alice",
  "displayName": "Alice"
}
```

sau đó đo consumer usage, deprecate contract cũ và chỉ remove khi lifecycle cho phép.

Một thay đổi additive thường an toàn hơn breaking change, nhưng vẫn phải xét consumer parser có reject unknown field hay không.

**Trade-off:**
Giữ compatibility làm contract phức tạp hơn và kéo dài technical debt. Versioning tạo chi phí support nhiều version, test matrix và documentation. Breaking change giúp model sạch nhanh nhưng chuyển migration cost sang tất cả consumers.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking change ở HTTP/JSON contract. Senior / Technical developer phải quản lý consumer lifecycle, deprecation policy, observability cho version usage, contract tests và rollout sequence giữa backend, frontend, mobile và third-party clients.
