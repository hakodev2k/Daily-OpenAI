# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` khi cần stream kết quả thay vì materialize toàn bộ

**Mẹo:**
Khi pipeline xử lý nhiều item theo kiểu tuần tự và consumer có thể xử lý từng item ngay khi có, cân nhắc `IAsyncEnumerable<T>` thay vì tạo toàn bộ `List<T>` trước rồi mới trả kết quả.

**Tại sao hữu ích:**
Streaming giảm peak memory và cho phép consumer bắt đầu xử lý sớm hơn. Với hàng chục nghìn record, materialize toàn bộ vừa tăng allocation vừa kéo dài time-to-first-item. `await foreach` giữ asynchronous backpressure tự nhiên hơn so với việc tạo một collection lớn trong memory.

**Ví dụ:**
```csharp
await foreach (var order in repository.StreamOrdersAsync(ct))
{
    await exporter.WriteAsync(order, ct);
}
```

Một export job có thể đọc từng batch/row và ghi ra stream thay vì giữ toàn bộ dataset trước khi tạo file.

**Lưu ý:**
Streaming giữ resource như database reader/connection lâu hơn. Không trả `IAsyncEnumerable` rồi để consumer xử lý cực chậm nếu điều đó giữ connection quý giá trong nhiều phút. Với HTTP response, lỗi xảy ra sau khi response đã bắt đầu cũng khó chuyển thành status code khác.

### Tip 2 — EF Core: tránh `SaveChanges` trong vòng lặp khi một transaction/batch là đủ

**Mẹo:**
Nếu nhiều thay đổi thuộc cùng một unit of work, đừng gọi `SaveChangesAsync()` sau từng entity chỉ vì code dễ viết. Gom thay đổi hợp lý rồi commit theo transaction boundary thực sự của business operation.

**Tại sao hữu ích:**
Mỗi `SaveChanges` có thể tạo thêm database round trip và transaction overhead. Với 500 entity, commit từng item vừa chậm vừa tạo trạng thái partial completion khó phục hồi nếu operation thất bại giữa chừng.

**Ví dụ:**
```csharp
foreach (var item in command.Items)
{
    db.OrderItems.Add(Map(item));
}

await db.SaveChangesAsync(ct);
```

Với import rất lớn, thay vì giữ hàng trăm nghìn tracked entity, hãy xử lý theo batch có kích thước đo được hoặc dùng bulk strategy phù hợp.

**Lưu ý:**
Một `SaveChanges` khổng lồ cũng không phải tối ưu mặc định: change tracker, transaction log và lock duration có thể tăng mạnh. Batch size phải dựa trên workload và correctness boundary; đừng chia batch nếu business invariant yêu cầu atomicity toàn bộ operation.

### Tip 3 — Azure Key Vault: dùng Managed Identity thay vì lưu client secret trong configuration

**Mẹo:**
Khi workload chạy trên Azure và cần đọc secret/key/certificate từ Azure Key Vault, ưu tiên Managed Identity để authentication thay vì đặt service-principal client secret trong `appsettings`, environment variable hoặc pipeline variable dài hạn.

**Tại sao hữu ích:**
Managed Identity loại bỏ credential bootstrap mà application phải tự lưu và rotate. Azure cấp identity cho workload; Key Vault authorization quyết định identity đó được phép làm gì. Điều này giảm nguy cơ secret bị leak qua repository, deployment configuration hoặc log.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Production có thể dùng Managed Identity, trong khi local development dùng developer credential thông qua `DefaultAzureCredential` chain.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Nếu identity được cấp quyền đọc toàn bộ vault dù application chỉ cần vài secret, blast radius vẫn lớn. Cũng cần thiết kế behavior khi Key Vault tạm unavailable và tránh gọi vault cho mỗi request nếu secret có thể cache an toàn.

### Tip 4 — Dùng Playwright trace để điều tra E2E test flaky thay vì chỉ tăng timeout

**Mẹo:**
Khi Playwright test thỉnh thoảng fail trong CI, thu trace/screenshot/network evidence cho lần retry hoặc failure trước khi tăng timeout. Xác định test đang chờ sai condition, selector không ổn định hay backend thực sự chậm.

**Tại sao hữu ích:**
Flaky test thường là race giữa UI state và assertion, không đơn thuần là “CI chậm”. Auto-wait của Playwright đã xử lý nhiều timing case; thêm `WaitForTimeout(5000)` thường chỉ làm suite chậm và vẫn không deterministic.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click()
await expect(page.getByText('Saved successfully')).toBeVisible()
```

Nếu fail, trace có thể cho thấy request `/api/profile` trả `500`, button bị overlay che hoặc assertion chạy trên UI state khác kỳ vọng.

**Lưu ý:**
Không bật trace/video cho mọi test ở mọi run nếu storage và execution cost lớn; có thể giữ artifact khi failure/retry. Selector nên dựa trên role/test contract ổn định thay vì CSS structure dễ đổi.

### Tip 5 — Với Akamai/CDN, debug stale content từ response headers trước khi purge toàn bộ cache

**Mẹo:**
Khi production website trả content cũ, kiểm tra `Cache-Control`, `Age`, `ETag`/validator và CDN-specific cache headers trước khi thực hiện global purge. Xác định stale response đến từ browser, CDN hay origin/application cache.

**Tại sao hữu ích:**
Một page có thể đi qua nhiều cache layer. Purge CDN không giúp nếu origin cache vẫn trả bản cũ; ngược lại restart application không giúp nếu edge vẫn giữ object với TTL dài. Điều tra theo từng layer giúp tìm đúng invalidation boundary.

**Ví dụ:**
```text
Browser -> Akamai edge -> ASP.NET Core output cache -> CMS

Symptom: editor publish lúc 09:00 nhưng page vẫn cũ
Evidence:
- Age: 1800
- Cache-Control: public, max-age=3600
- origin trả content mới
Diagnosis: edge object chưa expire/invalidate
```

**Lưu ý:**
Global purge là công cụ vận hành mạnh nhưng có thể làm cache hit ratio sụt và tạo traffic spike về origin. Thiết kế cache key, TTL và targeted invalidation ngay từ đầu tốt hơn phụ thuộc vào purge thủ công.

## 🧠 Software Design

### Design 1 — Saga dùng compensation khi workflow trải qua nhiều transaction boundary

**Khái niệm:**
Saga chia một business workflow phân tán thành nhiều local transaction. Khi bước sau thất bại, hệ thống thực hiện compensating action cho các bước đã hoàn tất thay vì cố giữ một distributed database transaction xuyên nhiều service.

**Vấn đề nó giải quyết:**
Checkout cần tạo order, reserve inventory và authorize payment ở các service riêng. Database transaction của Order Service không thể atomic cùng database của Inventory và external payment provider. Nếu payment thất bại sau khi inventory đã reserve, hệ thống cần một recovery path rõ ràng.

**Ví dụ thực tế:**
```text
Create Order
-> Reserve Inventory
-> Authorize Payment  X failed

Compensation:
-> Release Inventory
-> Mark Order = PaymentFailed
```

Saga có thể orchestration tập trung hoặc choreography bằng event, tùy độ phức tạp và ownership của workflow.

**Trade-off:**
Saga tránh distributed transaction coupling và phù hợp với eventual consistency, nhưng compensation không phải rollback vật lý. Một email đã gửi hoặc external side effect có thể không thể “undo” hoàn toàn. Workflow state, retries, idempotency và observability làm implementation phức tạp hơn local transaction.

**Middle → Senior insight:**
Middle developer cần hiểu từng step phải idempotent và failure phải có trạng thái rõ ràng. Senior / Technical developer phải xác định compensation semantics, timeout/recovery policy, orchestration vs choreography và những business invariant nào có thể chấp nhận eventual consistency thay vì cố phân tán một ACID transaction.

### Design 2 — Modular Monolith phù hợp khi cần boundary rõ nhưng chưa cần distributed deployment

**Khái niệm:**
Modular Monolith giữ application trong một deployable nhưng chia domain/capability thành module có ownership và dependency boundary rõ. Module có thể có schema, application API và internal model riêng mà không cần biến mỗi boundary thành network service.

**Vấn đề nó giải quyết:**
Một hệ thống đang lớn dần cần tránh codebase kiểu “mọi service gọi mọi repository”, nhưng team và scale chưa đủ để biện minh cho Microservices. Nếu tách service quá sớm, complexity chuyển từ method call sang network, deployment, tracing và eventual consistency mà business chưa nhận được lợi ích tương ứng.

**Ví dụ thực tế:**
```text
Nexora.Host
 ├─ Modules/Identity
 ├─ Modules/Tasks
 ├─ Modules/Finance
 └─ Modules/Vault

Tasks không truy cập trực tiếp bảng/internal class của Finance;
interaction đi qua explicit module contract.
```

Sau này module có nhu cầu scale/ownership độc lập thực sự mới là candidate để extract thành service.

**Trade-off:**
Modular Monolith giữ deployment và transaction đơn giản hơn Microservices, nhưng boundary phải được enforce bằng code/test/convention; nếu không, nó dễ suy thoái thành monolith coupling cao. Một deployable cũng có nghĩa module không thể scale hoặc release hoàn toàn độc lập.

**Middle → Senior insight:**
Middle developer cần tôn trọng module API và không bypass boundary để “tiện query”. Senior / Solution-oriented engineer phải chọn module seam theo business capability, quản lý data ownership và đánh giá extraction dựa trên scaling/team/deployment pressure thực tế thay vì số lượng class hay mong muốn dùng Microservices.

### Design 3 — Cache-aside cần thiết kế invalidation theo ownership, không chỉ chọn TTL

**Khái niệm:**
Cache-aside để application đọc cache trước, cache miss thì đọc source of truth rồi populate cache. Correctness của pattern phụ thuộc mạnh vào cách cache được invalidate hoặc chấp nhận stale data khi source thay đổi.

**Vấn đề nó giải quyết:**
Product detail được đọc hàng nghìn lần nhưng thay đổi ít. Redis giảm database load, nhưng khi giá sản phẩm được cập nhật, cache cũ có thể tiếp tục phục vụ dữ liệu sai nếu write path không có chiến lược invalidation rõ ràng.

**Ví dụ thực tế:**
```text
Read:
GET product:42
miss -> SQL -> SET product:42 TTL 10m

Write:
UPDATE Product 42
commit SQL
-> invalidate product:42

Nếu invalidate thất bại:
TTL đóng vai trò safety net, không phải guarantee tuyệt đối.
```

Với nhiều cache key derived từ cùng entity, có thể cần versioned key, event-driven invalidation hoặc cache granularity khác.

**Trade-off:**
Cache-aside đơn giản và giảm read load, nhưng tạo stale-data window, cache stampede và invalidation complexity. TTL ngắn giảm staleness nhưng tăng miss/load; TTL dài tăng hit ratio nhưng kéo dài lỗi dữ liệu cũ. Không phải dữ liệu nào cũng đáng cache.

**Middle → Senior insight:**
Middle developer cần hiểu cache là bản sao có thể stale và phải xử lý cache miss/failure an toàn. Senior / Technical developer phải xác định source of truth, owner của invalidation, consistency requirement, failure behavior khi Redis unavailable và liệu bottleneck có thực sự cần cache trước khi thêm một distributed state mới.
