# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` khi cần buffer lớn, ngắn hạn và lặp lại nhiều

**Mẹo:**
Với hot path thường xuyên cần mảng tạm tương đối lớn, cân nhắc `ArrayPool<T>.Shared` để thuê và trả lại buffer thay vì tạo array mới mỗi lần.

**Tại sao hữu ích:**
Giảm allocation và áp lực GC, đặc biệt trong parsing, serialization, compression hoặc xử lý stream có throughput cao.

**Ví dụ:**
```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

try
{
    var read = await stream.ReadAsync(
        buffer.AsMemory(0, 64 * 1024),
        cancellationToken);

    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Buffer thuê có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Nếu chứa secret/PII, cân nhắc `clearArray: true`. Tuyệt đối không giữ reference sau khi đã `Return`.

### Tip 2 — Dùng `ChangeTracker.Clear()` cho batch EF Core dài nếu vẫn phải dùng một `DbContext`

**Mẹo:**
Khi một batch job xử lý nhiều nhóm entity bằng cùng `DbContext`, gọi `ChangeTracker.Clear()` sau mỗi batch đã `SaveChangesAsync()` để tránh tracker phình dần.

**Tại sao hữu ích:**
Giảm memory usage và chi phí change detection khi job chạy hàng chục nghìn hoặc hàng trăm nghìn records.

**Ví dụ:**
```csharp
foreach (var batch in batches)
{
    foreach (var item in batch)
    {
        dbContext.Entities.Update(item);
    }

    await dbContext.SaveChangesAsync(cancellationToken);
    dbContext.ChangeTracker.Clear();
}
```

**Lưu ý:**
Sau `Clear()`, mọi entity đang tracked đều bị detach. Nếu logic phía sau còn dựa vào navigation fix-up hoặc entity state cũ, cần tổ chức lại scope `DbContext` hoặc reload rõ ràng.

### Tip 3 — Dùng `ETag` và conditional request để tránh tải lại dữ liệu không đổi

**Mẹo:**
Với resource đọc nhiều nhưng thay đổi ít, trả `ETag` rồi hỗ trợ `If-None-Match` để client không phải tải lại payload khi dữ liệu chưa đổi.

**Tại sao hữu ích:**
Giảm bandwidth, serialization cost và response body size, đặc biệt với config, metadata, catalog hoặc large JSON response.

**Ví dụ:**
Response đầu tiên:

```http
HTTP/1.1 200 OK
ETag: "order-123-v17"
```

Request tiếp theo:

```http
If-None-Match: "order-123-v17"
```

Nếu resource chưa đổi, server trả:

```http
HTTP/1.1 304 Not Modified
```

**Lưu ý:**
ETag phải phản ánh đúng version của representation. Đừng tạo ETag từ timestamp kém ổn định hoặc hash cực đắt nếu chi phí tính hash còn lớn hơn lợi ích caching.

### Tip 4 — Dùng `git check-ignore -v` khi không hiểu vì sao file bị ignore

**Mẹo:**
Khi một file không xuất hiện trong `git status`, dùng `git check-ignore -v` để xem chính xác rule nào và file `.gitignore` nào đang loại nó.

**Tại sao hữu ích:**
Nhanh hơn nhiều so với đọc thủ công nhiều `.gitignore`, global excludes và nested ignore rules.

**Ví dụ:**
```bash
git check-ignore -v appsettings.Development.json
```

Hoặc kiểm tra nhiều file:

```bash
git check-ignore -v **/*.generated.cs
```

**Lưu ý:**
Một file đã được track sẽ không bị bỏ track chỉ vì thêm vào `.gitignore`. Khi đó cần xử lý index riêng bằng `git rm --cached` nếu đúng mục tiêu.

### Tip 5 — Dùng `openssl s_client` để debug TLS/certificate từ đúng môi trường chạy

**Mẹo:**
Khi HTTPS call lỗi vì certificate chain, SNI hoặc TLS negotiation, kiểm tra trực tiếp từ máy/container bằng `openssl s_client`.

**Tại sao hữu ích:**
Giúp phân biệt nhanh application bug với lỗi CA bundle, expired certificate, hostname mismatch hoặc server gửi thiếu intermediate certificate.

**Ví dụ:**
```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com \
  -showcerts
```

**Lưu ý:**
Kết quả handshake thành công chưa đảm bảo HTTP request sẽ thành công. TLS chỉ là một tầng; vẫn cần kiểm tra DNS, proxy, authentication và application protocol khi cần.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer cần chống xử lý trùng

**Khái niệm:**
Inbox Pattern lưu `MessageId` của event/message đã xử lý cùng với transaction business của consumer, để message redelivery không tạo side effect lặp lại.

**Vấn đề nó giải quyết:**
Broker thường đảm bảo at-least-once delivery. Nếu consumer xử lý xong nhưng crash trước khi ack, cùng message có thể được gửi lại và tạo duplicate invoice, email hoặc database update.

**Ví dụ thực tế:**
Consumer nhận `PaymentSucceeded`:

1. Bắt đầu DB transaction.
2. Kiểm tra `InboxMessages` theo `MessageId`.
3. Nếu đã tồn tại → bỏ qua.
4. Nếu chưa có → cập nhật Order và insert `InboxMessages`.
5. Commit rồi mới ack broker.

**Trade-off:**
Inbox tăng reliability và làm idempotency có bằng chứng rõ ràng, nhưng thêm storage, unique constraint, retention/cleanup và transaction overhead.

**Middle → Senior insight:**
Middle developer cần hiểu deduplication phải gắn với cùng transaction business, không chỉ cache `MessageId` trong memory. Senior developer cần thiết kế key dedup, retention, replay semantics và phân biệt technical duplicate với business operation hợp lệ lặp lại.

### Design 2 — Branch by Abstraction để thay implementation lớn mà không cần big-bang switch

**Khái niệm:**
Branch by Abstraction đặt một abstraction ổn định trước implementation cũ, sau đó đưa implementation mới vào song song và chuyển traffic dần qua abstraction đó.

**Vấn đề nó giải quyết:**
Khi thay một subsystem lớn ngay trên main branch, feature branch kéo dài dễ diverge, khó merge và chỉ phát hiện integration problem rất muộn.

**Ví dụ thực tế:**
Một hệ thống muốn thay thư viện export Excel cũ:

```text
IExcelExporter
 ├─ LegacyExporter
 └─ NewExporter
```

Ban đầu production dùng `LegacyExporter`. Sau khi `NewExporter` đủ test, có thể bật theo feature flag, tenant hoặc use case trước khi xóa code cũ.

**Trade-off:**
Giảm merge risk và hỗ trợ migration incremental, nhưng tạm thời phải duy trì hai implementation, abstraction layer và test matrix rộng hơn.

**Middle → Senior insight:**
Middle developer nên hiểu abstraction có thể là migration seam chứ không chỉ design pattern. Senior developer cần chọn seam đủ nhỏ, tránh abstraction “rỗng”, xác định exit criteria và đảm bảo legacy path thực sự bị xóa sau migration.

### Design 3 — Chọn sharding key theo access pattern, không chỉ theo cardinality

**Khái niệm:**
Sharding key quyết định dữ liệu được phân phối sang partition/node nào. Key tốt không chỉ có nhiều giá trị mà còn phải phân phối tải và phù hợp với query/transaction boundary thực tế.

**Vấn đề nó giải quyết:**
Một key tưởng như hợp lý nhưng có hot tenant, sequential traffic hoặc query xuyên shard nhiều có thể làm một partition quá tải trong khi các partition khác nhàn rỗi.

**Ví dụ thực tế:**
Shard theo `TenantId` giúp giữ dữ liệu tenant cùng một nơi và đơn giản hóa query theo tenant. Nhưng nếu một enterprise tenant chiếm 50% traffic, shard đó sẽ thành hotspot. Có thể cần strategy như sub-shard theo `TenantId + Bucket` hoặc tách riêng tenant lớn.

**Trade-off:**
Shard key tốt tăng khả năng scale ngang và localize query, nhưng rất khó thay đổi sau khi dữ liệu lớn. Key phân phối đều quá mức lại có thể làm join/transaction phải đi qua nhiều shard.

**Middle → Senior insight:**
Middle developer nên hiểu sharding không đồng nghĩa `hash(id)` là xong. Senior developer phải cân nhắc traffic skew, query pattern, transaction locality, rebalancing, hot-key handling và migration cost trước khi khóa partition strategy.
