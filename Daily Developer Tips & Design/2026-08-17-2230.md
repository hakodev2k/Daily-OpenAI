# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ValueTask` đúng chỗ trong async hot path

**Mẹo:**
Sử dụng `ValueTask` cho các API async có khả năng trả kết quả đồng bộ thường xuyên, ví dụ cache hit hoặc object pool.

**Tại sao hữu ích:**
Giảm allocation của `Task` trong các đường chạy hiệu năng cao.

**Ví dụ:**
```csharp
public ValueTask<User?> GetUserAsync(string id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return LoadFromDatabaseAsync(id);
}
```

**Lưu ý:**
Không thay toàn bộ `Task` bằng `ValueTask`. Nó phức tạp hơn và chỉ phù hợp khi có profiling chứng minh allocation là vấn đề.

### Tip 2 — Dùng `AsNoTrackingWithIdentityResolution` khi đọc dữ liệu EF Core phức tạp

**Mẹo:**
Khi query read-only nhưng có nhiều quan hệ lặp entity, dùng `AsNoTrackingWithIdentityResolution()` thay vì tracking đầy đủ.

**Tại sao hữu ích:**
Giữ lợi ích của no-tracking nhưng tránh tạo nhiều instance cho cùng một entity trong graph kết quả.

**Ví dụ:**
```csharp
var users = await context.Users
    .Include(x => x.Roles)
    .AsNoTrackingWithIdentityResolution()
    .ToListAsync();
```

**Lưu ý:**
Không dùng cho update flow vì entity không được tracked bởi DbContext.

### Tip 3 — Dùng correlation ID xuyên suốt request và background job

**Mẹo:**
Gắn một identifier duy nhất cho request, log, message queue và background processing.

**Tại sao hữu ích:**
Giúp trace một business operation qua nhiều service hoặc worker.

**Ví dụ:**
```csharp
using var scope = logger.BeginScope(new Dictionary<string, object>
{
    ["CorrelationId"] = correlationId
});
```

**Lưu ý:**
Không log dữ liệu nhạy cảm chỉ vì correlation ID được truyền rộng rãi.

### Tip 4 — Dùng `git bisect` để tìm commit gây regression

**Mẹo:**
Khi bug xuất hiện nhưng không biết commit nào gây ra, dùng binary search của Git thay vì kiểm tra từng commit.

**Tại sao hữu ích:**
Giảm thời gian điều tra regression trong repository lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.5.0
```

**Lưu ý:**
Cần có test hoặc cách xác định trạng thái good/bad đáng tin cậy.

### Tip 5 — Dùng `CancellationToken` xuyên suốt pipeline xử lý

**Mẹo:**
Truyền `CancellationToken` từ API endpoint tới database, HTTP client và background operation.

**Tại sao hữu ích:**
Tránh tiếp tục xử lý khi client đã disconnect hoặc operation không còn cần thiết.

**Ví dụ:**
```csharp
await repository.SaveAsync(entity, cancellationToken);
```

**Lưu ý:**
Không nuốt `OperationCanceledException` như lỗi hệ thống thông thường.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Distributed System

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau để đảm bảo business consistency.

**Vấn đề nó giải quyết:**
Transaction quá lớn làm giảm scalability; transaction quá nhỏ có thể tạo trạng thái không hợp lệ.

**Ví dụ thực tế:**
Order creation cần lưu order và payment status. Có thể giữ transaction trong Order service, sau đó phát event cho Payment service.

**Trade-off:**
Local transaction đơn giản nhưng giới hạn boundary. Distributed transaction mạnh hơn nhưng tăng complexity và coupling.

**Middle → Senior insight:**
Middle developer cần biết transaction không chỉ là database feature. Senior developer phải xác định aggregate boundary, consistency requirement và eventual consistency strategy.

### Design 2 — Idempotency trong API Design

**Khái niệm:**
Idempotent operation cho phép cùng một request được thực hiện nhiều lần mà kết quả cuối cùng không bị tạo duplicate.

**Vấn đề nó giải quyết:**
Network retry, timeout và message redelivery có thể khiến một command chạy nhiều lần.

**Ví dụ thực tế:**
Payment API nhận `Idempotency-Key` để đảm bảo retry không tạo thêm giao dịch.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và xử lý lifecycle của key.

**Middle → Senior insight:**
Senior developer cần thiết kế retry policy, storage strategy và xác định operation nào bắt buộc idempotent.

### Design 3 — Modular Monolith trước Microservices

**Khái niệm:**
Modular Monolith chia hệ thống thành module có boundary rõ trong cùng một deployment.

**Vấn đề nó giải quyết:**
Tránh complexity của distributed system khi domain chưa đủ lớn để cần nhiều service độc lập.

**Ví dụ thực tế:**
Hệ thống HR có module Employee, Payroll, Leave với database boundary và dependency rule rõ ràng.

**Trade-off:**
Đơn giản deployment nhưng cần kỷ luật architecture để tránh module gọi trực tiếp lẫn nhau.

**Middle → Senior insight:**
Senior developer không chọn Microservices vì xu hướng mà dựa trên team structure, scaling requirement, domain boundary và operational maturity.
