# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `ArrayPool<T>` giảm allocation nhưng tăng trách nhiệm ownership

**Mẹo:**
Với hot path cần buffer tạm lớn, cân nhắc `ArrayPool<T>.Shared.Rent()` thay vì liên tục tạo array mới, nhưng chỉ sau khi profiler chứng minh allocation/GC là bottleneck.

**Tại sao hữu ích:**
Pool tái sử dụng arrays nên giảm allocation rate và GC pressure, đặc biệt với buffer lớn. Đổi lại, application phải quản lý lifetime của buffer cẩn thận.

**Ví dụ:**
Worker parse hàng nghìn payload mỗi giây thấy allocation rate cao. Nó rent buffer, xử lý trong `try`, rồi `Return()` trong `finally`; sau đó benchmark lại throughput và GC pause.

**Lưu ý:**
Array được rent có thể lớn hơn requested size. Không giữ reference sau khi return; đừng thêm pooling nếu complexity lớn hơn lợi ích đo được.

### Tip 2 — Elasticsearch mapping sai không sửa được chỉ bằng đổi query

**Mẹo:**
Khi search behavior sai, kiểm tra mapping/analyzer trước khi tinh chỉnh query. `text` và `keyword` phục vụ semantics khác nhau và index-time analysis quyết định representation đã lưu.

**Tại sao hữu ích:**
Full-text field thường được tokenize, còn exact filtering, sorting và aggregation cần representation không analyzed. Query đúng cú pháp vẫn có thể sai intent nếu mapping không phù hợp.

**Ví dụ:**
Product name dùng `text` cho full-text search và multi-field `keyword` cho exact aggregation. Nếu analyzer cần đổi, tạo index version mới và reindex thay vì mong runtime query thay đổi tokens cũ.

**Lưu ý:**
Reindex có storage, compute và cutover cost. Test representative queries và relevance trước khi đổi analyzer.

### Tip 3 — Application Insights sampling có thể làm sai cách đọc telemetry count

**Mẹo:**
Khi điều tra production bằng Application Insights, xác định sampling đang áp dụng trước khi lấy số telemetry items thô làm request/error count.

**Tại sao hữu ích:**
Sampling giảm telemetry volume và cost bằng cách giữ một phần events. Nếu bỏ qua sampling semantics, engineer có thể kết luận sai rằng traffic hoặc lỗi giảm.

**Ví dụ:**
Sau deployment, request telemetry rows giảm bất thường. Trước khi kết luận load giảm, kiểm tra sampling configuration và correlate với metrics, dependency latency và failure rate.

**Lưu ý:**
Không tắt sampling toàn production chỉ để có nhiều dữ liệu hơn mà không đánh giá ingestion cost và mục tiêu quan sát.

### Tip 4 — File upload phải giới hạn tài nguyên và xác thực nội dung

**Mẹo:**
Với ASP.NET Core upload endpoint, coi filename, extension và client-provided `Content-Type` là untrusted metadata. Giới hạn kích thước, stream dữ liệu phù hợp và lưu ngoài executable web root khi có thể.

**Tại sao hữu ích:**
Chỉ whitelist extension không chứng minh payload đúng loại. Upload không giới hạn còn có thể tiêu thụ memory/disk, còn filename từ client không nên được dùng trực tiếp làm storage identity.

**Ví dụ:**
CMS nhận ảnh: server sinh storage key riêng, enforce size limit, xác thực format theo requirement rồi lưu Blob Storage; database chỉ giữ metadata cần thiết.

**Lưu ý:**
Validation format không thay thế việc cập nhật parser/library và thiết kế processing boundary phù hợp với mức rủi ro của ứng dụng.

### Tip 5 — `git worktree` giúp xử lý hotfix mà không phá working tree hiện tại

**Mẹo:**
Dùng `git worktree` để checkout branch khác vào directory riêng khi feature work chưa hoàn tất nhưng cần xử lý hotfix/review song song.

**Tại sao hữu ích:**
Không cần stash working tree phức tạp hoặc clone thêm toàn repository. Các worktrees chia sẻ Git object database nhưng có working directory riêng.

**Ví dụ:**
Đang sửa `feature/search`, cần hotfix từ `main`: tạo worktree cho `hotfix/payment-timeout`, sửa/test/commit ở directory đó rồi quay lại feature directory vẫn giữ nguyên state.

**Lưu ý:**
Một branch thông thường không checkout đồng thời ở nhiều worktrees. Sau khi xong cần remove/prune worktree đúng cách.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read/write có áp lực khác nhau rõ

**Khái niệm:**
CQRS tách model/path command khỏi query để mỗi phía tối ưu theo semantics riêng. Nó không bắt buộc đi cùng Microservices, Event Sourcing hay hai databases.

**Vấn đề nó giải quyết:**
Domain có write invariants phức tạp nhưng read screens cần projections khác hẳn aggregate model có thể bị ép vào một CRUD abstraction chung, làm cả hai phía khó tối ưu.

**Ví dụ thực tế:**
Ordering giữ command path bảo vệ invariant, còn dashboard query dùng projection riêng để lấy đúng columns và joins cần cho UI. Cả hai vẫn có thể nằm trong cùng Modular Monolith.

**Trade-off:**
Tách read/write tăng flexibility nhưng thêm models, mapping và consistency considerations. Với CRUD đơn giản, CQRS có thể chỉ tăng ceremony.

**Middle → Senior insight:**
Middle developer cần phân biệt command có side effect với query. Senior / Technical developer phải đánh giá divergence của models, consistency requirement và operational cost trước khi chọn mức độ CQRS.

### Design 2 — Feature flags tách deployment khỏi release

**Khái niệm:**
Feature flag cho phép deploy code trước rồi bật capability cho cohort/environment cụ thể, khiến release decision không buộc trùng với deployment event.

**Vấn đề nó giải quyết:**
Thay đổi lớn có thể cần rollout dần hoặc disable nhanh khi business behavior sai mà không rollback toàn deployment chứa các fixes khác.

**Ví dụ thực tế:**
Checkout mới deploy ở trạng thái off, bật cho internal users rồi 5% traffic. Metrics về error rate và latency quyết định tăng rollout hay disable flag.

**Trade-off:**
Flags giảm release risk nhưng tạo combinatorial states, dead code và operational dependency. Long-lived flags trở thành technical debt.

**Middle → Senior insight:**
Middle developer cần test enabled/disabled paths. Senior / Technical developer phải xác định ownership, default behavior, rollout metrics và expiry/removal policy.

### Design 3 — Observability phải được thiết kế quanh câu hỏi vận hành

**Khái niệm:**
Observability design chọn logs, metrics và traces để suy luận trạng thái hệ thống. Mục tiêu không phải log càng nhiều càng tốt mà là trả lời nhanh câu hỏi về failure, latency và saturation.

**Vấn đề nó giải quyết:**
Hàng triệu log lines vẫn khó debug nếu thiếu correlation và dependency context. Signals được thiết kế theo request/message lifecycle giúp thu hẹp incident nhanh hơn.

**Ví dụ thực tế:**
Order pipeline chuẩn hóa `TraceId`, dependency span, queue processing duration và outcome metric. Khi p99 tăng, engineer đi từ metric sang trace rồi dependency/query cụ thể.

**Trade-off:**
Telemetry tăng ingestion/storage cost và high-cardinality risk. Sampling có thể làm mất detail, nên signal, retention và cardinality phải bám theo SLO.

**Middle → Senior insight:**
Middle developer cần tạo structured telemetry có correlation. Senior / Technical developer phải thiết kế telemetry contract, SLO-driven alerts và cost budgets để incident workflow đi từ symptom → evidence → diagnosis.
