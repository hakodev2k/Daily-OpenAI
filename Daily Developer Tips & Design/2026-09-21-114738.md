# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `DateTime.Now` làm nền tảng cho logic timeout và elapsed time

**Mẹo:**
Tách wall-clock time khỏi elapsed-time measurement. Dùng `TimeProvider`/UTC cho business time cần kiểm thử và dùng monotonic timing như `Stopwatch` cho duration, timeout hoặc performance measurement thay vì lấy hai lần `DateTime.Now` rồi trừ nhau.

**Tại sao hữu ích:**
Wall clock có thể nhảy do NTP adjustment, daylight-saving transition hoặc thay đổi clock của host. Logic retry/timeout dựa vào clock có thể chạy sớm, muộn hoặc tạo test khó kiểm soát. `TimeProvider` cũng cho phép inject thời gian trong tests thay vì `Thread.Sleep`.

**Ví dụ:**
Một token cache hết hạn sau 5 phút. Service nhận `TimeProvider` qua DI và lưu expiration theo UTC; unit test dùng fake provider để advance 5 phút tức thời, xác minh refresh xảy ra mà không phải chờ thời gian thật.

**Lưu ý:**
`DateTimeOffset.UtcNow` vẫn là wall clock, không phải monotonic clock. Với duration chính xác hãy dùng API chuyên cho elapsed time; với timestamp nghiệp vụ hãy chuẩn hóa UTC và chỉ convert timezone ở presentation boundary.

### Tip 2 — EF Core projection thường tốt hơn `Include` cho read-only API

**Mẹo:**
Khi endpoint chỉ cần một response shape cụ thể, project trực tiếp bằng `Select` sang DTO thay vì load toàn bộ entity graph bằng nhiều `Include` rồi mapping trong memory.

**Tại sao hữu ích:**
Projection giúp SQL chỉ lấy columns cần thiết, giảm materialization/tracking cost và hạn chế Cartesian explosion khi include nhiều collections. Query shape cũng thể hiện rõ contract dữ liệu mà endpoint thực sự cần.

**Ví dụ:**
Trang order history chỉ cần `OrderId`, `CreatedAt`, tổng tiền và 3 sản phẩm đầu tiên. Thay vì `Include(o => o.Items).ThenInclude(i => i.Product)`, query project trực tiếp các fields cần thiết và dùng `AsNoTracking` cho read path.

**Lưu ý:**
Đừng mặc định mọi projection đều nhanh. Kiểm tra SQL được generate và execution plan, đặc biệt với nested collections, aggregates hoặc provider-specific translation. Nếu cần sửa entity sau query, tracking/entity loading có thể phù hợp hơn.

### Tip 3 — MongoDB index phải khớp với query shape, không chỉ với từng field riêng lẻ

**Mẹo:**
Thiết kế compound index dựa trên filter, sort và cardinality thực tế của workload. Có index riêng trên từng field không đồng nghĩa query kết hợp nhiều điều kiện sẽ có plan tối ưu.

**Tại sao hữu ích:**
Một endpoint lọc `TenantId`, `Status` rồi sort `CreatedAt desc` có thể vẫn scan/sort nhiều dữ liệu nếu index không hỗ trợ đúng prefix và ordering. Index phù hợp giảm documents examined, memory sort và latency tail.

**Ví dụ:**
Query thường xuyên là `{ TenantId, Status }` + sort `CreatedAt: -1`. Sau khi xem `explain("executionStats")`, team cân nhắc compound index `{ TenantId: 1, Status: 1, CreatedAt: -1 }` thay vì ba single-field indexes độc lập.

**Lưu ý:**
Mỗi index làm tăng storage và write amplification. Không tạo index chỉ vì một query tồn tại; đo query frequency, selectivity và `keysExamined/docsExamined`, đồng thời kiểm tra index prefix có phục vụ các workload khác hay không.

### Tip 4 — `HttpClient` resilience cần phân biệt transient failure với semantic failure

**Mẹo:**
Retry chỉ những failures có khả năng thành công khi thử lại và chỉ khi operation an toàn để lặp. Phân loại timeout, connection failure, `429`, selected `5xx` khác với `400`, authentication failure hoặc domain rejection.

**Tại sao hữu ích:**
Retry mù quáng làm tăng tải đúng lúc downstream đang suy yếu và có thể nhân đôi side effects. Backoff, jitter, timeout budget và idempotency phải được thiết kế cùng nhau chứ không phải thêm một retry policy mặc định cho mọi request.

**Ví dụ:**
GET catalog gặp `503` có thể retry với exponential backoff + jitter trong tổng latency budget. POST tạo payment chỉ retry khi provider hỗ trợ idempotency key và failure mode không xác nhận được kết quả lần gọi trước.

**Lưu ý:**
Không retry indefinitely và không để mỗi layer tự retry độc lập, vì retry amplification có thể bùng nổ. Ghi metrics theo attempt count, final outcome và downstream dependency để biết resilience policy đang cứu hệ thống hay làm nó tệ hơn.

### Tip 5 — Debug memory leak bằng retention path, không chỉ nhìn heap size

**Mẹo:**
Khi process memory tăng liên tục, chụp heap dumps ở nhiều thời điểm và tìm object types tăng cùng GC roots/retention paths giữ chúng sống. Câu hỏi quan trọng là “ai đang giữ reference?” chứ không chỉ “object nào chiếm nhiều byte?”.

**Tại sao hữu ích:**
Managed memory cao chưa chắc là leak; GC có thể giữ committed memory hoặc workload có legitimate cache. Retention analysis giúp phân biệt cache có giới hạn, static/event-handler references, unbounded collections và objects đang chờ finalization.

**Ví dụ:**
Worker tăng vài trăm MB mỗi ngày. Heap comparison cho thấy hàng trăm nghìn request contexts được giữ qua event subscription của singleton. Unsubscribe/dispose đúng lifecycle loại bỏ retention path thay vì tăng container memory limit.

**Lưu ý:**
Đừng kết luận từ một snapshot duy nhất. Quan sát sau full GC, allocation rate, LOH/POH và native memory khi cần; một .NET process có thể tăng RSS vì native buffers hoặc runtime structures mà managed heap dump không giải thích hết.

## 🧠 Software Design

### Design 1 — Outbox Pattern giải quyết khoảng trống giữa database commit và message publish

**Khái niệm:**
Transactional Outbox ghi business state và outbound message record trong cùng local database transaction. Một publisher riêng đọc Outbox và gửi message ra broker, sau đó đánh dấu trạng thái xử lý.

**Vấn đề nó giải quyết:**
Nếu application commit Order rồi crash trước khi publish `OrderCreated`, database và messaging system bất đồng. Nếu publish trước rồi database rollback, consumer lại thấy event cho state chưa tồn tại. Outbox loại bỏ dual-write window trong phạm vi local transaction.

**Ví dụ thực tế:**
Checkout transaction insert `Order` và `OutboxMessage(OrderCreated)` cùng lúc. Background worker publish message lên Azure Service Bus; nếu process chết sau publish nhưng trước khi mark sent, message có thể được gửi lại nên consumer vẫn phải idempotent.

**Trade-off:**
Outbox cải thiện reliability nhưng thêm table growth, publisher, retry, cleanup, observability và eventual delay. Nó không tạo exactly-once end-to-end; duplicate publication vẫn có thể xảy ra và ordering giữa aggregate/messages cần được thiết kế rõ.

**Middle → Senior insight:**
Middle developer cần implement atomic write, retry và idempotent consumer đúng cách. Senior / Technical developer phải xác định delivery semantics, ordering requirement, partition key, retention/cleanup và failure recovery; đồng thời tránh áp Outbox vào workflow không có dual-write consistency problem.

### Design 2 — CQRS là tách model theo responsibility, không đồng nghĩa phải dùng microservices

**Khái niệm:**
CQRS tách command/write concerns khỏi query/read concerns khi hai phía có requirements khác nhau. Mức tách có thể chỉ là classes/query models trong cùng application và cùng database, không bắt buộc event sourcing hay infrastructure riêng.

**Vấn đề nó giải quyết:**
Một domain model tối ưu cho invariants và state transitions thường không phải shape tốt nhất cho dashboard/search/reporting. Ép mọi read đi qua aggregate graph có thể làm query phức tạp, còn nhồi reporting concerns vào write model làm domain model mất tập trung.

**Ví dụ thực tế:**
Order commands load aggregate để enforce rule “không ship order chưa paid”. Order-list screen dùng read projection tối ưu trực tiếp từ SQL, trả DTO đúng shape UI mà không hydrate aggregate chỉ để hiển thị dữ liệu.

**Trade-off:**
CQRS nhẹ có thể làm code rõ hơn; CQRS với separate stores/events tăng eventual consistency, synchronization, deployment và operational complexity. Nếu CRUD đơn giản, việc nhân đôi models/handlers có thể chỉ tăng ceremony.

**Middle → Senior insight:**
Middle developer cần hiểu command/query semantics và tránh để query vô tình mutate state. Senior / Technical developer phải chọn mức separation theo complexity thật, consistency requirement và team operations maturity thay vì coi CQRS là template kiến trúc mặc định.

### Design 3 — API idempotency key là một business contract, không chỉ là cache key

**Khái niệm:**
Idempotency cho write API đảm bảo nhiều requests đại diện cùng một logical operation không tạo side effect lặp. Server thường gắn client-provided key với request fingerprint, processing state và kết quả đủ lâu cho retry window.

**Vấn đề nó giải quyết:**
Client có thể timeout sau khi server đã commit nhưng trước khi response đến. Khi client retry, server không biết đó là operation mới hay cùng operation cũ nếu contract không có identity ổn định.

**Ví dụ thực tế:**
`POST /payments` nhận `Idempotency-Key`. Lần đầu server reserve key, thực hiện payment và persist result; retry cùng key + cùng request trả lại semantic result trước đó. Cùng key nhưng payload khác bị reject thay vì âm thầm dùng kết quả sai.

**Trade-off:**
Idempotency storage cần TTL, concurrency control và policy cho failed/in-progress requests. Key scope quá rộng gây collision; quá ngắn có thể cho duplicate operation sau expiration. Response replay cũng phải cân nhắc dữ liệu nhạy cảm và thay đổi representation.

**Middle → Senior insight:**
Middle developer cần xử lý race giữa hai requests cùng key và validate request fingerprint. Senior / Technical developer phải định nghĩa operation identity, retention window, state machine, cross-region behavior và interaction với database/message side effects để guarantee có ý nghĩa ở cấp business.
