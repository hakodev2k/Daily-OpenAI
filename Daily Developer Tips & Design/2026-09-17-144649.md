# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — `HttpClient.Timeout` không thay thế timeout budget theo từng dependency

**Mẹo:**
Với ASP.NET Core gọi nhiều downstream services, đặt timeout dựa trên latency budget của từng dependency và propagation của `CancellationToken`; đừng chỉ dựa vào một `HttpClient.Timeout` rất lớn cho mọi request.

**Tại sao hữu ích:**
Một request có SLA 2 giây nhưng dependency được phép chờ 100 giây sẽ giữ connection, memory và request resources sau khi kết quả đã không còn giá trị. Timeout budget rõ ràng giúp hệ thống fail sớm và giữ capacity cho traffic còn hữu ích.

**Ví dụ:**
```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
timeoutCts.CancelAfter(TimeSpan.FromMilliseconds(800));

using var response = await httpClient.GetAsync(
    $"inventory/{productId}",
    timeoutCts.Token);
```
Nếu request còn phải gọi Pricing và Shipping, mỗi dependency cần budget phù hợp với tổng end-to-end latency target.

**Lưu ý:**
Timeout không đồng nghĩa operation phía server chắc chắn đã dừng. Với command có side effect, retry sau timeout phải đi cùng idempotency; nếu không có thể tạo duplicate operation.

### Tip 2 — SQL Server statistics stale có thể làm execution plan xấu dù index vẫn đúng

**Mẹo:**
Khi query đột nhiên chậm mà schema/index không đổi, kiểm tra estimated rows so với actual rows và statistics trước khi thêm index mới.

**Tại sao hữu ích:**
Optimizer chọn join type, access path và memory grant dựa trên cardinality estimate. Data distribution thay đổi mạnh nhưng statistics không phản ánh đúng có thể khiến plan chọn Nested Loops cho tập dữ liệu lớn hoặc cấp memory không phù hợp.

**Ví dụ:**
```text
Actual rows:    850,000
Estimated rows: 1,200
Plan:           Nested Loops + repeated lookups
Symptom:        CPU và logical reads tăng mạnh
```
Kiểm tra Actual Execution Plan, statistics properties và workload/data distribution trước khi quyết định `UPDATE STATISTICS`, index change hoặc query rewrite.

**Lưu ý:**
Đừng chạy full-scan statistics update trên mọi bảng như phản xạ đầu tiên; operation có cost và plan regression vẫn có thể đến từ parameter sensitivity, schema change hoặc workload khác.

### Tip 3 — Redis cache stampede cần single-flight hoặc request coalescing, không chỉ TTL

**Mẹo:**
Với hot key có regeneration đắt, khi cache miss hãy giới hạn số request cùng rebuild value thay vì để tất cả cùng đánh database/API.

**Tại sao hữu ích:**
Nếu một key hết hạn lúc 10.000 requests đang tới, TTL đúng vẫn có thể tạo 10.000 cache misses gần đồng thời. Database bị spike chính vào thời điểm cache đáng lẽ bảo vệ nó.

**Ví dụ:**
```text
Hot key: product-homepage
TTL expires
→ 2,000 concurrent misses
→ chỉ 1 request rebuild
→ các request khác chờ ngắn hoặc dùng stale value
→ cache được populate lại
```
Trong một process có thể dùng keyed lock/single-flight; nhiều instances cần strategy phù hợp hơn như distributed coordination hoặc stale-while-revalidate.

**Lưu ý:**
Distributed lock không phải mặc định cho mọi cache key. Lock có failure modes riêng và có thể biến cache thành coordination bottleneck. Chỉ áp dụng khi regeneration cost và concurrency thực sự biện minh.

### Tip 4 — Optimizely CMS content cache phải được invalidate theo content dependency

**Mẹo:**
Khi cache dữ liệu render từ CMS, xác định content/version/language dependencies thay vì đặt một TTL tùy ý và hy vọng editor changes sẽ xuất hiện đúng lúc.

**Tại sao hữu ích:**
Enterprise CMS thường có publish workflow, language branches và dependent blocks. Cache không gắn với dependency có thể tiếp tục phục vụ content cũ sau publish hoặc invalidate quá rộng khiến hit ratio sụt mạnh.

**Ví dụ:**
```text
LandingPage
 ├─ HeroBlock
 └─ PromotionBlock

PromotionBlock được publish
→ cache entry của page phụ thuộc block cần invalidation
→ không cần flush toàn bộ site cache
```
Theo dõi cache hit/miss và publish-to-visible latency để xác nhận strategy hoạt động như mong muốn.

**Lưu ý:**
Không cache object/context có lifecycle không phù hợp hoặc assumption rằng content ID duy nhất đủ cho mọi language/version. Preview/editor mode cũng thường cần behavior khác public delivery.

### Tip 5 — Production memory investigation: dùng `dotnet-counters` trước khi chụp dump lớn

**Mẹo:**
Khi .NET process tăng memory, bắt đầu bằng runtime counters để phân loại GC heap, allocation rate, GC frequency và ThreadPool behavior trước khi lấy memory dump nặng.

**Tại sao hữu ích:**
Memory tăng không luôn là managed leak. Counters giúp nhanh chóng phân biệt allocation churn, heap growth, high Gen 2 collections hoặc vấn đề không nằm trong managed heap, từ đó chọn công cụ tiếp theo có mục tiêu hơn.

**Ví dụ:**
```bash
dotnet-counters monitor \
  --process-id 1234 \
  System.Runtime
```
Nếu GC heap tăng đều sau mỗi Gen 2 GC, mới tiếp tục với `dotnet-gcdump`/dump và object retention analysis. Nếu process memory tăng nhưng GC heap ổn định, điều tra native memory/buffers/thread stacks.

**Lưu ý:**
Một snapshot đơn lẻ không chứng minh leak. Cần quan sát theo thời gian và tương quan với traffic/workload; dump production cũng có CPU, pause, disk và dữ liệu nhạy cảm cần cân nhắc.

## 🧠 Software Design

### Design 1 — Retry budget thay vì retry ở mọi layer

**Khái niệm:**
Retry là một phần của end-to-end resilience budget. Nếu API gateway, service A, service B và database client đều tự retry ba lần, failure amplification có thể lớn hơn nhiều so với ý định của từng layer.

**Vấn đề nó giải quyết:**
Một dependency đang quá tải trả transient error. Mỗi layer retry độc lập khiến một user request sinh ra hàng chục downstream attempts, làm dependency càng khó hồi phục và tăng tail latency.

**Ví dụ thực tế:**
Gateway không retry application command. Service A có một retry ngắn cho idempotent read tới Service B; Service B không tiếp tục retry database timeout nhiều lần. Tổng attempt count, deadline và backoff được thiết kế theo end-to-end request budget.

**Trade-off:**
Retry có thể che transient fault và tăng success rate, nhưng tiêu tốn latency/capacity và có thể tạo retry storm. Ít retry hơn giảm amplification nhưng có thể làm lộ transient failures cho caller sớm hơn.

**Middle → Senior insight:**
Middle developer cần phân biệt transient/permanent failure, dùng backoff/jitter và không retry non-idempotent operation mù quáng. Senior / Technical developer phải thiết kế retry ownership giữa các layers, deadline propagation, attempt budget và behavior khi dependency đang degraded.

### Design 2 — Bounded Context không đồng nghĩa Microservice

**Khái niệm:**
DDD Bounded Context xác định boundary nơi một domain model và ubiquitous language có nghĩa nhất quán. Deployment boundary là quyết định khác; một Bounded Context có thể là module trong Modular Monolith hoặc service độc lập.

**Vấn đề nó giải quyết:**
Trong e-commerce, `Customer` của Marketing có segmentation/preferences khác `Customer` của Billing có invoicing/credit semantics. Ép cả hai dùng một shared entity tạo coupling và model ngày càng khó hiểu.

**Ví dụ thực tế:**
`Ordering` sở hữu Order aggregate và customer snapshot cần cho fulfillment. `CRM` sở hữu lead/profile data. Hai context trao đổi contract rõ ràng nhưng ban đầu vẫn có thể deploy trong cùng application nếu team/scale chưa cần phân tán.

**Trade-off:**
Context boundaries giảm semantic coupling và ownership ambiguity nhưng tạo mapping/integration giữa models. Chia quá nhỏ làm tăng translation overhead; chia quá rộng khiến model trở thành shared database schema không ai thực sự sở hữu.

**Middle → Senior insight:**
Middle developer cần tránh dùng entity/database model xuyên context như shared DTO. Senior / Technical developer phải tìm boundary từ business language, invariants, change cadence và ownership trước khi quyết định có tách thành process/service riêng hay không.

### Design 3 — Contract Testing cho integration boundary, không thay thế E2E

**Khái niệm:**
Contract test xác minh producer và consumer đồng ý về request/response/event contract mà không cần chạy toàn bộ distributed system. Nó tập trung vào compatibility ở integration boundary.

**Vấn đề nó giải quyết:**
Service Catalog đổi `price` từ number sang object hoặc xóa field mà Checkout vẫn phụ thuộc. Unit tests của cả hai service đều pass vì mỗi codebase tự đúng, nhưng integration production bị vỡ.

**Ví dụ thực tế:**
Checkout định nghĩa expectations cho `GET /products/{id}` hoặc event schema. CI của Catalog verify provider đáp ứng contract của active consumers trước khi release; một breaking contract change bị phát hiện trước deployment.

**Trade-off:**
Contract tests nhanh hơn full E2E và định vị compatibility failure tốt, nhưng không kiểm chứng networking, authentication configuration, deployment wiring, database state hay complete user journey. E2E vẫn cần cho một số critical flows.

**Middle → Senior insight:**
Middle developer cần viết contract theo externally observable behavior thay vì internal implementation. Senior / Technical developer phải quyết định boundary nào đáng contract-test, version/evolution policy, consumer lifecycle và cách phối hợp contract tests với integration/E2E để tránh một test pyramid vừa chậm vừa trùng lặp.
