# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng retry mọi `HttpClient` failure như nhau

**Mẹo:**
Khi gọi third-party REST API, chỉ retry lỗi có khả năng transient và kết hợp retry với timeout rõ ràng. Phân biệt timeout, network failure, `429 Too Many Requests`, `5xx` và lỗi `4xx` do request không hợp lệ.

**Tại sao hữu ích:**
Retry mù có thể biến một dependency đang quá tải thành sự cố lớn hơn. Một request timeout 30 giây được retry 3 lần có thể giữ request của người dùng gần 2 phút; retry `400` hoặc `401` thường chỉ lặp lại lỗi deterministic. Với `429`, server có thể cung cấp `Retry-After` để client back off đúng hơn.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<PaymentClient>(client =>
{
    client.Timeout = TimeSpan.FromSeconds(5);
});
```

Nếu payment provider trả `503`, retry có backoff có thể hợp lý; nếu trả `400 InvalidCard`, trả lỗi business ngay thay vì retry.

**Lưu ý:**
Không retry operation có side effect nếu API không có idempotency guarantee. Một `POST /payments` bị timeout có thể đã tạo payment ở server dù client chưa nhận response.

### Tip 2 — SQL: kiểm tra cardinality estimate khi execution plan chọn strategy bất thường

**Mẹo:**
Khi query đột nhiên chậm, đừng chỉ nhìn xem index có tồn tại hay không. So sánh estimated rows với actual rows trong execution plan; chênh lệch lớn thường chỉ ra statistics, predicate hoặc data distribution đang khiến optimizer đánh giá sai workload.

**Tại sao hữu ích:**
Optimizer chọn join type, access path và memory grant dựa trên cardinality estimate. Nếu estimate là 50 rows nhưng thực tế trả 500.000 rows, một plan hợp lý cho dataset nhỏ có thể trở thành bottleneck nghiêm trọng.

**Ví dụ:**
```sql
SELECT o.Id, o.CreatedAt
FROM Orders o
WHERE o.TenantId = @tenantId
  AND o.Status = 'Pending';
```

Nếu một tenant có 10 record còn tenant khác có 2 triệu record, cùng một plan không nhất thiết phù hợp cho cả hai workload.

**Lưu ý:**
Đừng mặc định `UPDATE STATISTICS` hoặc thêm index là fix cuối cùng. Parameter sensitivity, skewed data, implicit conversion và non-sargable predicate cũng có thể tạo estimate sai; cần đối chiếu evidence trước khi sửa.

### Tip 3 — Git `bisect` giúp tìm commit gây regression bằng binary search

**Mẹo:**
Khi biết một phiên bản cũ hoạt động và phiên bản mới bị regression, dùng `git bisect` thay vì checkout từng commit thủ công.

**Tại sao hữu ích:**
`git bisect` thu hẹp phạm vi commit theo binary search. Với khoảng 1.000 commit, thường chỉ cần khoảng 10 lần phân loại `good`/`bad`, đặc biệt hữu ích cho regression có test hoặc script tái hiện ổn định.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
# chạy reproduction/test
git bisect good   # hoặc: git bisect bad
```

Có thể tự động hóa bằng `git bisect run <test-script>` nếu exit code của test phản ánh pass/fail đáng tin cậy.

**Lưu ý:**
Bisect kém hiệu quả nếu bug nondeterministic, phụ thuộc dữ liệu production hoặc nhiều commit trung gian không build được. Sau khi tìm candidate commit vẫn phải xác minh root cause, không coi correlation là diagnosis.

### Tip 4 — Vue/React: abort request cũ khi UI state đã chuyển sang query mới

**Mẹo:**
Với search-as-you-type hoặc component đổi route/filter nhanh, dùng `AbortController` để hủy fetch không còn cần thiết thay vì để response cũ có cơ hội ghi đè state mới.

**Tại sao hữu ích:**
Hai request không đảm bảo hoàn thành theo thứ tự gửi. Query `lap` có thể trả sau query `laptop`, khiến UI hiển thị kết quả stale dù backend hoàn toàn đúng. Cancellation vừa giảm công việc thừa vừa ngăn race ở client.

**Ví dụ:**
```ts
let controller: AbortController | undefined

async function search(q: string) {
  controller?.abort()
  controller = new AbortController()
  const r = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  })
  return r.json()
}
```

**Lưu ý:**
Client abort không đảm bảo server đã dừng mọi công việc. Backend cũng cần propagate cancellation khi phù hợp; đồng thời UI phải phân biệt `AbortError` với failure thực sự để không hiện thông báo lỗi giả.

### Tip 5 — Production debugging: bắt đầu từ latency percentile và dependency breakdown

**Mẹo:**
Khi API “chậm”, xác định phạm vi bằng p50/p95/p99 và dependency telemetry trước khi mở profiler hoặc sửa code. Tách thời gian request thành database, outbound HTTP, cache và application processing.

**Tại sao hữu ích:**
Average latency có thể che tail latency. Nếu p50 vẫn 120 ms nhưng p99 tăng từ 800 ms lên 8 giây, chỉ một nhóm request/dependency đang gặp vấn đề. Application Insights dependency telemetry và distributed trace giúp tìm segment gây delay thay vì đoán từ controller code.

**Ví dụ:**
```text
GET /checkout
p50 = 180 ms
p95 = 420 ms
p99 = 7.4 s

p99 trace:
SQL              35 ms
Redis             4 ms
Shipping API   6.9 s
Application      90 ms
```

Evidence này chuyển investigation sang external dependency/timeout policy thay vì tối ưu SQL vô căn cứ.

**Lưu ý:**
Telemetry sampling, missing correlation hoặc instrumentation không đầy đủ có thể làm kết luận sai. Kiểm tra coverage của traces và correlation IDs trước khi coi dashboard là toàn bộ sự thật.

## 🧠 Software Design

### Design 1 — Idempotency Key cho API có side effect

**Khái niệm:**
Idempotency Key cho phép client retry một logical command mà server vẫn nhận diện đây là cùng operation, thay vì tạo side effect mới mỗi lần request được gửi lại.

**Vấn đề nó giải quyết:**
Trong distributed system, client có thể timeout sau khi server đã commit nhưng trước khi response quay về. Client không biết operation thất bại hay chỉ mất response. Retry một `POST` không idempotent có thể tạo hai order hoặc charge hai lần.

**Ví dụ thực tế:**
```text
POST /payments
Idempotency-Key: checkout-9f71

Request #1: server commit payment, response bị mất
Request #2: cùng key -> trả lại outcome của operation #1
```

Server cần lưu key cùng request identity/outcome trong một scope và retention window được xác định rõ.

**Trade-off:**
Pattern tăng reliability cho retry nhưng thêm persistent state, concurrency handling và lifecycle cleanup. Key reuse với payload khác phải bị phát hiện; nếu chỉ cache response trong memory thì multi-instance deployment có thể phá guarantee.

**Middle → Senior insight:**
Middle developer cần biết retry không đồng nghĩa operation an toàn và implement key validation đúng. Senior / Technical developer phải xác định idempotency boundary, storage/transaction semantics, retention, concurrent duplicate behavior và liệu downstream side effects có cùng guarantee hay không.

### Design 2 — Queue hay Topic phụ thuộc vào delivery semantics, không phải tên nghiệp vụ

**Khái niệm:**
Queue phù hợp khi một message cần được một consumer trong nhóm xử lý; Topic + subscriptions phù hợp khi cùng event phải được fan-out độc lập tới nhiều consumer concern.

**Vấn đề nó giải quyết:**
Một hệ thống e-commerce cần xử lý command `GenerateInvoice` đúng một logical workflow, nhưng event `OrderCompleted` có thể cần Billing, Analytics và Notification phản ứng độc lập. Dùng một queue chung cho ba concern sẽ khiến consumers cạnh tranh lấy message thay vì mỗi concern nhận bản riêng.

**Ví dụ thực tế:**
```text
Queue: invoice-generation
  -> Invoice Worker instances (competing consumers)

Topic: order-completed
  -> billing subscription
  -> analytics subscription
  -> notification subscription
```

Mỗi subscription có retry và dead-letter lifecycle riêng.

**Trade-off:**
Topic giảm coupling giữa publisher và subscribers nhưng tăng số delivery path, duplicate handling, monitoring và schema-evolution responsibility. Queue đơn giản hơn khi chỉ có một processing responsibility và scale-out workers cùng làm một loại việc.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumers, subscriptions và at-least-once delivery. Senior / Technical developer phải chọn topology theo ownership và delivery semantics, dự đoán failure isolation, replay, ordering, cost và tránh biến mọi internal action thành event chỉ vì broker có sẵn.

### Design 3 — Contract Testing bảo vệ integration boundary nhưng không thay thế E2E

**Khái niệm:**
Contract Testing xác minh producer và consumer đồng ý về interface observable như endpoint, payload, required fields và semantics quan trọng mà không cần dựng toàn bộ hệ thống end-to-end cho mọi test.

**Vấn đề nó giải quyết:**
Team API thay đổi field hoặc status code và unit tests của cả hai repository vẫn pass vì mỗi bên test theo assumption riêng. Lỗi chỉ xuất hiện sau deployment khi mobile/web client gọi API thật.

**Ví dụ thực tế:**
```text
Consumer expects:
GET /api/products/42
200
{ "id": 42, "price": 19.99 }

Producer change:
{ "id": 42, "unitPrice": 19.99 }
```

Contract verification có thể phát hiện breaking change trước khi release producer.

**Trade-off:**
Contract tests chạy nhanh và cô lập integration compatibility tốt hơn nhiều E2E test, nhưng không chứng minh networking, authentication infrastructure, database migration hay workflow nhiều service hoạt động thật. Contract suite quá chi tiết cũng có thể khóa implementation không cần thiết.

**Middle → Senior insight:**
Middle developer cần viết contract dựa trên behavior mà consumer thực sự phụ thuộc. Senior / Technical developer phải quyết định boundary nào đáng contract-test, quản lý version/evolution giữa teams và phối hợp contract, integration và E2E tests để có confidence mà không tạo test pyramid đắt đỏ.
