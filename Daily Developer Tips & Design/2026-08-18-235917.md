# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh tạo `HttpClient` mới cho từng request

**Mẹo:**
Dùng `IHttpClientFactory` hoặc typed client thay vì `new HttpClient()` trong mỗi operation.

**Tại sao hữu ích:**
Giúp tái sử dụng connection pool, giảm nguy cơ socket exhaustion và cho phép cấu hình timeout, handler, logging hoặc resilience policy theo từng external service.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<PaymentClient>(client =>
{
    client.BaseAddress = new Uri("https://payments.example.com");
    client.Timeout = TimeSpan.FromSeconds(10);
});
```

**Lưu ý:**
Không đặt timeout quá dài rồi phụ thuộc hoàn toàn vào retry. Timeout và retry phải phối hợp để tổng latency vẫn nằm trong SLA.

### Tip 2 — Dùng `ActivitySource` để thêm custom tracing span

**Mẹo:**
Khi một business operation khó debug bằng log đơn thuần, thêm custom span bằng `ActivitySource` để trace thời gian từng bước.

**Tại sao hữu ích:**
Giúp xác định chính xác latency nằm ở database, external API hay processing nội bộ khi xem distributed trace trong OpenTelemetry backend.

**Ví dụ:**
```csharp
private static readonly ActivitySource Source = new("OrderService");

using var activity = Source.StartActivity("CalculateOrderTotal");
activity?.SetTag("order.id", orderId);
```

**Lưu ý:**
Không tạo span cho mọi method nhỏ. Quá nhiều span làm trace nhiễu và tăng telemetry cost.

### Tip 3 — Dùng `git rerere` để tái sử dụng cách resolve conflict

**Mẹo:**
Bật `rerere` nếu thường xuyên rebase hoặc merge một branch dài và gặp lại cùng conflict.

**Tại sao hữu ích:**
Git có thể ghi nhớ cách bạn resolve conflict trước đó và tự áp dụng lại khi conflict tương tự xuất hiện lần sau.

**Ví dụ:**
```bash
git config --global rerere.enabled true
```

**Lưu ý:**
Vẫn phải review kết quả auto-resolution. Context code có thể đã thay đổi dù conflict trông giống nhau.

### Tip 4 — Kiểm tra lock khi SQL chậm bất thường dù execution plan ổn

**Mẹo:**
Khi query vốn nhanh đột nhiên chậm ở production, kiểm tra blocking/lock trước khi vội thêm index.

**Tại sao hữu ích:**
Một query có execution plan tốt vẫn có thể đứng chờ transaction khác giữ lock quá lâu.

**Ví dụ:**
Trong SQL Server, có thể kiểm tra session đang bị block qua DMV:

```sql
SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_time,
    wait_resource
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;
```

**Lưu ý:**
Đừng xử lý bằng cách kill session ngay lập tức nếu chưa hiểu transaction đó đang làm gì. Root cause thường nằm ở transaction boundary hoặc query giữ lock lâu.

### Tip 5 — Dùng `TimeProvider` để test code phụ thuộc thời gian

**Mẹo:**
Inject `TimeProvider` thay vì gọi trực tiếp `DateTime.UtcNow` ở business logic cần test.

**Tại sao hữu ích:**
Cho phép test expiration, retry window, scheduling rule hoặc token lifetime mà không phải chờ thời gian thật trôi qua.

**Ví dụ:**
```csharp
public class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => expiresAt <= timeProvider.GetUtcNow();
}
```

**Lưu ý:**
Không cần abstract mọi lần đọc thời gian. Chỉ áp dụng ở logic mà thời gian ảnh hưởng trực tiếp đến behavior và testability.

## 🧠 Software Design

### Design 1 — Feature Flags không nên trở thành business logic vĩnh viễn

**Khái niệm:**
Feature Flag cho phép bật/tắt behavior tại runtime mà không cần deploy lại, thường dùng cho gradual rollout, experiment hoặc kill switch.

**Vấn đề nó giải quyết:**
Giảm rủi ro release bằng cách tách deployment khỏi activation và cho phép rollback logic nhanh khi có sự cố.

**Ví dụ thực tế:**
Một API checkout có payment flow mới. Team deploy code trước nhưng chỉ bật cho 5% traffic, sau đó tăng dần lên 25%, 50% và 100% khi metrics ổn định.

**Trade-off:**
Ưu điểm là rollout an toàn và linh hoạt. Chi phí là số lượng execution path tăng mạnh, test matrix phức tạp và code dễ tích tụ flag cũ.

**Middle → Senior insight:**
Middle developer cần biết feature flag không chỉ là `if` trong code. Senior developer cần thiết kế ownership, expiration date, telemetry, fallback behavior và cleanup plan để tránh biến hệ thống thành mạng lưới condition khó kiểm soát.

### Design 2 — Saga cho workflow xuyên nhiều service

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction, mỗi bước có action và có thể có compensating action khi bước sau thất bại.

**Vấn đề nó giải quyết:**
Trong distributed system, không thể dễ dàng dùng một ACID transaction bao trùm nhiều database hoặc service độc lập.

**Ví dụ thực tế:**
Flow đặt vé gồm `ReserveSeat → ChargePayment → IssueTicket`. Nếu payment thành công nhưng issue ticket thất bại, hệ thống cần compensation như refund payment và release seat.

**Trade-off:**
Ưu điểm là giữ service độc lập và tránh distributed transaction. Nhược điểm là workflow phức tạp hơn, compensation không phải lúc nào cũng hoàn tác tuyệt đối và trạng thái trung gian phải được quản lý rõ.

**Middle → Senior insight:**
Middle developer cần hiểu retry không giải quyết mọi failure. Senior developer phải quyết định orchestration hay choreography, thiết kế state machine, idempotency, timeout, compensation và observability cho toàn workflow.

### Design 3 — Schema Evolution trong event-driven system

**Khái niệm:**
Schema Evolution là cách thay đổi cấu trúc event theo thời gian mà không phá consumer cũ đang đọc message đã tồn tại hoặc được publish bởi producer phiên bản khác.

**Vấn đề nó giải quyết:**
Producer và consumer thường deploy độc lập. Một thay đổi field thiếu compatibility có thể làm consumer lỗi hàng loạt dù producer vẫn hoạt động bình thường.

**Ví dụ thực tế:**
Event `CustomerCreated` ban đầu có `name`. Phiên bản mới muốn thêm `preferredLanguage`. Thay vì đổi semantics của field cũ, producer thêm field optional để consumer cũ vẫn deserialize được.

**Trade-off:**
Backward-compatible change giúp deploy độc lập nhưng có thể giữ legacy field lâu hơn dự kiến. Version event quá thường xuyên lại làm tăng operational complexity và mapping code.

**Middle → Senior insight:**
Middle developer cần phân biệt additive change với breaking change. Senior developer phải thiết kế compatibility policy, ownership, schema registry hoặc contract test, đồng thời cân nhắc dữ liệu cũ trong queue/event store chứ không chỉ message mới.
