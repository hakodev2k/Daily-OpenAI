# Daily Developer Tips & Design — 2026-08-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsNoTracking()` cho read-only query trong EF Core

**Mẹo:**
Khi query chỉ để đọc dữ liệu và không cần update entity sau đó, dùng `AsNoTracking()` để EF Core không tạo tracking state cho từng entity.

**Tại sao hữu ích:**
Giảm memory allocation và chi phí change tracking, đặc biệt hữu ích với query trả về nhiều records hoặc endpoint chỉ phục vụ GET.

**Ví dụ:**
```csharp
var users = await dbContext.Users
    .AsNoTracking()
    .Where(x => x.IsActive)
    .Select(x => new UserDto(x.Id, x.Name))
    .ToListAsync();
```

**Lưu ý:**
Không dùng nếu bạn cần sửa các entity vừa query rồi gọi `SaveChanges()`. Với projection trực tiếp sang DTO, lợi ích tracking đôi khi đã nhỏ hơn nhiều.

### Tip 2 — Dùng `git bisect` để tìm commit gây regression

**Mẹo:**
Thay vì checkout thủ công hàng chục commit, dùng `git bisect` để Git thực hiện binary search giữa một commit tốt và một commit lỗi.

**Tại sao hữu ích:**
Giảm đáng kể thời gian tìm nguyên nhân khi bug xuất hiện sau một chuỗi dài thay đổi.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# test commit hiện tại rồi đánh dấu
git bisect good
# hoặc
git bisect bad

# sau khi tìm được commit
git bisect reset
```

Có thể tự động hóa bằng test command:

```bash
git bisect run dotnet test
```

**Lưu ý:**
`git bisect` hiệu quả nhất khi mỗi commit trong khoảng kiểm tra có thể build/test độc lập. Commit bị broken vì lý do không liên quan có thể làm kết quả khó phân tích.

### Tip 3 — Đừng log exception bằng string interpolation

**Mẹo:**
Với `ILogger`, truyền exception trực tiếp và dùng structured logging thay vì đưa toàn bộ exception vào interpolated string.

**Tại sao hữu ích:**
Giữ nguyên stack trace, exception metadata và các structured fields để hệ thống như Application Insights, Seq hoặc Elasticsearch có thể query chính xác.

**Ví dụ:**
```csharp
try
{
    await paymentService.ProcessAsync(orderId);
}
catch (Exception ex)
{
    logger.LogError(ex,
        "Failed to process payment for OrderId {OrderId}",
        orderId);
    throw;
}
```

Tránh:

```csharp
logger.LogError($"Payment failed: {ex}");
```

**Lưu ý:**
Không log cùng một exception ở mọi layer nếu không bổ sung thêm context; việc đó thường tạo nhiều log trùng cho cùng một failure.

### Tip 4 — Kiểm tra execution plan thay vì đoán SQL chậm vì đâu

**Mẹo:**
Khi một SQL query chậm, xem actual execution plan và các chỉ số logical reads trước khi vội thêm index hoặc rewrite query.

**Tại sao hữu ích:**
Bạn có thể phân biệt được vấn đề thực sự là table scan, bad cardinality estimate, key lookup, sort, spill, parameter sensitivity hay chỉ đơn giản là đọc quá nhiều dữ liệu.

**Ví dụ:**
Trong SQL Server:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT Id, CustomerId, CreatedAt
FROM Orders
WHERE CustomerId = @CustomerId
  AND CreatedAt >= @FromDate;
```

Sau đó kiểm tra actual execution plan và lượng logical reads thay vì chỉ nhìn execution time của một lần chạy.

**Lưu ý:**
Một execution plan nhanh với dataset nhỏ hoặc parameter cụ thể chưa chắc đại diện cho production workload. Cần xem cả data distribution và parameter thực tế.

### Tip 5 — Truyền `CancellationToken` xuyên suốt async call chain

**Mẹo:**
Trong ASP.NET Core, truyền `HttpContext.RequestAborted` hoặc `CancellationToken` của action xuống database, HTTP client và các async operation hỗ trợ cancellation.

**Tại sao hữu ích:**
Khi client ngắt kết nối hoặc request timeout, server có thể dừng công việc không còn cần thiết thay vì tiếp tục chiếm connection, CPU hoặc thread-pool resources.

**Ví dụ:**
```csharp
app.MapGet("/orders/{id}", async (
    Guid id,
    AppDbContext db,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

**Lưu ý:**
Cancellation không phải rollback tự động. Nếu operation đã tạo side effect bên ngoài như gửi message hoặc gọi payment API, cần thiết kế riêng cho consistency và idempotency.

## 🧠 Software Design

### Design 1 — Idempotency cho API tạo giao dịch

**Khái niệm:**
Idempotency đảm bảo nhiều request tương đương không tạo nhiều side effects ngoài ý muốn. Với API tạo resource hoặc thực hiện payment, client thường gửi một `Idempotency-Key` duy nhất cho logical operation.

**Vấn đề nó giải quyết:**
Trong distributed systems, timeout không cho client biết request đã thất bại hay server đã xử lý thành công nhưng response bị mất. Retry mù có thể tạo duplicate order, payment hoặc message.

**Ví dụ thực tế:**
Một API thanh toán nhận:

```http
POST /payments
Idempotency-Key: order-98231-payment-1
```

Server lưu key cùng trạng thái/result. Nếu cùng key được gửi lại, hệ thống trả lại kết quả trước đó thay vì charge lần thứ hai.

**Trade-off:**
Lợi ích là retry an toàn hơn và giảm duplicate side effects. Chi phí là phải lưu idempotency state, xác định TTL, xử lý concurrent request cùng key và quyết định payload khác nhau với cùng key sẽ bị reject thế nào.

**Middle → Senior insight:**
Middle developer nên hiểu retry có thể tạo duplicate và biết triển khai idempotency key. Senior developer cần xác định đúng idempotency boundary, storage strategy, concurrency control và hành vi khi operation chỉ hoàn thành một phần.

### Design 2 — Transaction boundary không nên mặc định trùng với service method

**Khái niệm:**
Transaction boundary nên bao quanh một business invariant cần thay đổi atomically, không phải đơn giản bao toàn bộ một application service vì đó là một method thuận tiện.

**Vấn đề nó giải quyết:**
Transaction quá rộng giữ lock lâu, tăng contention và dễ kéo external calls vào database transaction. Transaction quá hẹp lại có thể làm business state rơi vào trạng thái không hợp lệ.

**Ví dụ thực tế:**
Khi tạo order, việc insert `Order` và `OrderItems` có thể nằm trong một DB transaction. Nhưng gửi email hoặc publish message sang hệ thống khác không nên giữ transaction mở trong lúc chờ network call. Một lựa chọn tốt hơn là Outbox Pattern.

**Trade-off:**
Transaction lớn giúp reasoning về atomicity đơn giản hơn nhưng giảm scalability và tăng lock duration. Transaction nhỏ cải thiện throughput nhưng đòi hỏi thiết kế eventual consistency, retries hoặc compensating actions rõ ràng hơn.

**Middle → Senior insight:**
Middle developer cần biết dùng transaction để bảo vệ thay đổi dữ liệu liên quan. Senior developer phải xác định invariant thực sự, tránh distributed transaction không cần thiết và lựa chọn giữa atomicity, availability và operational complexity.

### Design 3 — Modular Monolith trước Microservices khi boundary chưa ổn định

**Khái niệm:**
Modular Monolith giữ deployment unit duy nhất nhưng chia hệ thống thành các module có boundary, ownership và dependency rõ ràng. Nó cho phép enforce kiến trúc mà chưa phải chịu toàn bộ chi phí vận hành của Microservices.

**Vấn đề nó giải quyết:**
Nhiều hệ thống tách Microservices quá sớm khi domain boundaries còn thay đổi, dẫn đến distributed calls dày đặc, duplicated models, khó debug và deployment phức tạp hơn giá trị thu được.

**Ví dụ thực tế:**
Một SaaS mới có các module `Billing`, `Identity`, `Orders` và `Notifications`. Các module có database schema hoặc abstraction riêng và không truy cập trực tiếp internals của nhau, nhưng vẫn được deploy cùng một ASP.NET Core application. Khi `Billing` có nhu cầu scale, release cadence hoặc compliance thực sự khác biệt, module đó mới là ứng viên tách service.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, transactions và debugging nhưng không cho independent scaling/deployment thực sự. Microservices tăng autonomy và isolation nhưng thêm network failure, observability, messaging, consistency và DevOps complexity.

**Middle → Senior insight:**
Middle developer nên hiểu sự khác nhau giữa code organization và service boundary. Senior developer cần chứng minh được lý do kinh doanh hoặc vận hành đủ mạnh trước khi tách service, đồng thời thiết kế module boundary sao cho việc tách sau này vẫn khả thi.
