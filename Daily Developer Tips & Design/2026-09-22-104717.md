# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsNoTrackingWithIdentityResolution` khi read model có entity lặp lại

**Mẹo:**
Với EF Core query chỉ đọc nhưng materialize graph có cùng entity xuất hiện nhiều lần, cân nhắc `AsNoTrackingWithIdentityResolution()` thay vì `AsNoTracking()` thuần nếu duplication trong object graph gây allocation đáng kể.

**Tại sao hữu ích:**
`AsNoTracking()` bỏ change tracking nên giảm overhead, nhưng cùng một database row xuất hiện nhiều lần có thể tạo nhiều object instances. Identity resolution dùng tracker tạm thời chỉ trong quá trình materialization để tái sử dụng instance mà không đưa entity vào `DbContext` tracking lâu dài.

**Ví dụ:**
Màn hình báo cáo load nhiều `Order` cùng tham chiếu một `Customer`. Nếu query thực sự cần entity graph thay vì DTO projection, identity resolution có thể tránh tạo nhiều `Customer` objects giống nhau trong kết quả.

**Lưu ý:**
Nó vẫn có overhead so với `AsNoTracking()`. Với API DTO thông thường, projection bằng `Select` thường tốt hơn; hãy đo allocation và SQL trước khi chọn cơ chế này.

### Tip 2 — Kiểm tra SQL Server implicit conversion khi index có mà query vẫn scan

**Mẹo:**
Khi execution plan không dùng index như kỳ vọng, kiểm tra kiểu dữ liệu của parameter và column có khớp nhau không. Implicit conversion trên indexed column có thể làm predicate kém sargable.

**Tại sao hữu ích:**
Nếu database phải convert từng giá trị của column trước khi so sánh, engine có thể không seek hiệu quả trên index. Đây là lỗi dễ bị bỏ qua vì query vẫn trả kết quả đúng và schema vẫn có index.

**Ví dụ:**
Column `CustomerCode` là `varchar`, nhưng application truyền parameter kiểu Unicode khiến plan xuất hiện conversion trên column. Symptom là CPU/reads tăng và index scan ở endpoint lookup vốn phải rất nhanh. Sửa mapping/parameter type đúng với schema rồi so sánh execution plan và logical reads.

**Lưu ý:**
Không phải mọi conversion đều phá index usage. Đọc actual execution plan và warnings thay vì kết luận chỉ từ SQL text; đồng thời tránh sửa bằng cách cast column trong predicate vì có thể làm tình hình tệ hơn.

### Tip 3 — Tách configuration validation khỏi lỗi runtime bằng `ValidateOnStart`

**Mẹo:**
Với ASP.NET Core options bắt buộc cho service hoạt động, cấu hình validation và gọi `ValidateOnStart()` để deployment fail sớm thay vì chờ request đầu tiên mới phát hiện configuration sai.

**Tại sao hữu ích:**
Sai endpoint, thiếu required setting hoặc giá trị ngoài range là deployment/configuration defect. Phát hiện lúc startup làm health signal rõ hơn và tránh instance được đưa vào traffic rồi mới trả 500 ở một code path hiếm.

**Ví dụ:**
`PaymentOptions` yêu cầu `BaseUrl` hợp lệ và timeout nằm trong giới hạn. Deployment thiếu `BaseUrl` sẽ không trở thành ready instance, thay vì lỗi `HttpClient` khi khách hàng checkout.

**Lưu ý:**
Không dùng startup validation để gọi mọi external dependency. Validate configuration semantics tại startup; dependency availability là concern khác và cần readiness/resilience phù hợp.

### Tip 4 — Dùng Redis TTL jitter để tránh synchronized expiration

**Mẹo:**
Khi nhiều cache entries được tạo cùng thời điểm và có cùng TTL, thêm một lượng jitter nhỏ vào expiration để chúng không đồng loạt hết hạn.

**Tại sao hữu ích:**
Synchronized expiration có thể biến cache hit ratio cao thành một burst lớn xuống database hoặc external API. Jitter phân tán thời điểm refresh, giảm nguy cơ cache stampede ở cấp hệ thống mà không cần thay đổi business semantics lớn.

**Ví dụ:**
Product cache có TTL cơ sở 10 phút; application thêm random jitter trong một khoảng nhỏ phù hợp. Thay vì hàng nghìn keys từ batch import cùng expire đúng phút thứ 10, refresh load được trải ra theo thời gian.

**Lưu ý:**
TTL jitter không giải quyết hot key đơn lẻ hoặc expensive miss concurrency. Với key rất nóng, vẫn cần single-flight/request coalescing, stale-while-revalidate hoặc chiến lược refresh chủ động.

### Tip 5 — Với AI coding agent, khóa phạm vi bằng acceptance evidence chứ không chỉ mô tả task

**Mẹo:**
Khi giao bug fix cho AI coding agent, cung cấp reproduction, expected behavior, test command và các file/boundary được phép thay đổi; sau đó kiểm tra diff và chạy evidence thay vì chỉ đọc lời giải thích của agent.

**Tại sao hữu ích:**
Agent có thể tạo code compile được nhưng mở rộng abstraction, sửa unrelated files hoặc viết test khớp implementation sai. Acceptance evidence biến task từ “hãy sửa lỗi” thành một thay đổi có điều kiện kiểm chứng cụ thể.

**Ví dụ:**
Bug pagination yêu cầu: reproduction test đang fail, API contract không đổi, chỉ data-access/application layer được sửa, `dotnet test` phải pass và generated SQL phải giữ keyset predicate. Review tập trung vào evidence đó thay vì tin summary của agent.

**Lưu ý:**
Không để generated test tự định nghĩa expected behavior khi requirement chưa rõ. Nếu agent vừa thay production code vừa thay assertion để test xanh, cần đối chiếu requirement/source-of-truth trước khi chấp nhận.

## 🧠 Software Design

### Design 1 — Queue và Topic phục vụ hai kiểu ownership khác nhau

**Khái niệm:**
Queue phù hợp khi một logical message cần được một consumer trong nhóm xử lý; Topic + subscriptions phù hợp khi nhiều capability độc lập cần nhận cùng một event theo contract riêng.

**Vấn đề nó giải quyết:**
Dùng một queue cho mọi downstream consumer tạo cạnh tranh ngoài ý muốn: Billing nhận message thì Analytics không còn thấy nó. Ngược lại, dùng pub/sub cho command có một owner có thể khiến nhiều consumer cùng thực thi side effect.

**Ví dụ thực tế:**
`GenerateInvoice` là command gửi vào queue của Billing. `OrderCompleted` là event publish lên Azure Service Bus topic; Billing, Loyalty và Analytics có subscription riêng, retry/DLQ riêng và có thể tiến hóa độc lập.

**Trade-off:**
Topic tăng decoupling và fan-out nhưng thêm subscription management, duplicate delivery, schema evolution và observability. Queue đơn giản hơn cho work distribution nhưng không biểu diễn đúng nhu cầu broadcast.

**Middle → Senior insight:**
Middle developer cần phân biệt command với event và implement idempotent consumer. Senior / Technical developer phải quyết định ownership, delivery semantics, filtering, failure isolation và contract evolution trước khi chọn queue hay topic.

### Design 2 — Schema ownership quan trọng hơn việc chia database vật lý quá sớm

**Khái niệm:**
Một module/service nên có ownership rõ đối với dữ liệu và invariants của mình. Database-per-service là một cách enforce boundary, nhưng ownership có thể được thiết lập trước bằng schema/module boundaries trong kiến trúc đơn giản hơn.

**Vấn đề nó giải quyết:**
Nếu nhiều modules tự do join/update cùng tables, code boundary chỉ tồn tại trên sơ đồ. Mọi thay đổi schema trở thành coordinated release và business invariants bị sửa từ nhiều nơi.

**Ví dụ thực tế:**
Trong Modular Monolith, Ordering sở hữu schema `ordering`; Reporting không update trực tiếp tables đó mà đọc qua projection/read model được thiết kế cho reporting. Khi cần tách service sau này, data ownership đã rõ hơn.

**Trade-off:**
Ownership rõ giảm coupling nhưng có thể tạo duplication và thêm integration paths. Tách database vật lý ngay lập tức tăng deployment, migration, backup và distributed-consistency complexity mà hệ thống nhỏ có thể chưa cần.

**Middle → Senior insight:**
Middle developer cần tôn trọng write ownership và contract giữa modules. Senior / Technical developer phải cân nhắc mức enforcement phù hợp với scale, team topology và migration path thay vì coi database-per-service là mục tiêu mặc định.

### Design 3 — SLO-driven reliability thay vì cố làm mọi dependency “highly available”

**Khái niệm:**
Reliability design nên xuất phát từ user-visible objective như latency/availability SLO và failure budget, rồi phân bổ yêu cầu xuống critical path thay vì mặc định mọi component phải có mức HA tối đa.

**Vấn đề nó giải quyết:**
Một hệ thống có thể tốn nhiều tiền cho redundancy nhưng vẫn vi phạm trải nghiệm người dùng vì critical dependency chậm; ngược lại, một non-critical feature outage có thể không cần làm fail toàn request.

**Ví dụ thực tế:**
Checkout cần pricing và payment nhưng recommendations là optional. Khi recommendation service timeout, request bỏ qua phần đó trong budget ngắn; payment có timeout/resilience chặt hơn vì nằm trên critical path của business transaction.

**Trade-off:**
SLO giúp đầu tư reliability có mục tiêu và kiểm soát cost, nhưng đòi hỏi telemetry đáng tin, business alignment và quyết định degradation rõ ràng. SLO sai có thể tối ưu hệ thống theo metric không phản ánh trải nghiệm thật.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, fallback và health behavior của dependency mình tích hợp. Senior / Technical developer phải map critical path, đặt reliability target theo business impact và quyết định nơi nào cần redundancy, degradation hay chấp nhận failure thay vì áp một tiêu chuẩn HA đồng đều.
