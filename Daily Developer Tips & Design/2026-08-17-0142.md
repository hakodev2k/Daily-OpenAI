# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TagWith()` để truy ngược SQL từ EF Core

**Mẹo:**
Khi có nhiều query giống nhau trong production, thêm `TagWith()` vào LINQ query để SQL sinh ra có comment nhận diện nguồn gọi.

**Tại sao hữu ích:**
Giúp nối từ slow query trong database monitoring ngược về đúng use case hoặc đoạn code thay vì đoán dựa trên SQL gần giống nhau.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .TagWith("OrdersApi:GetPendingOrders")
    .Where(x => x.Status == OrderStatus.Pending)
    .ToListAsync(cancellationToken);
```

SQL sẽ chứa comment tương tự:

```sql
-- OrdersApi:GetPendingOrders
SELECT ...
```

**Lưu ý:**
Tag chỉ giúp observability, không làm query nhanh hơn. Tránh đưa dữ liệu nhạy cảm hoặc giá trị động có cardinality cao vào tag.

### Tip 2 — Dùng `ValueTask` chỉ khi profiling chứng minh allocation đáng kể

**Mẹo:**
`ValueTask<T>` hữu ích khi operation rất thường xuyên hoàn thành synchronously và allocation của `Task<T>` trở thành chi phí thực sự.

**Tại sao hữu ích:**
Trong hot path, giảm số lượng `Task` allocation có thể giảm GC pressure. Nhưng dùng đúng chỗ mới có giá trị.

**Ví dụ:**
```csharp
public ValueTask<User?> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out var user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

**Lưu ý:**
`ValueTask` có semantics phức tạp hơn `Task` và thường không nên await nhiều lần hoặc lưu trữ tùy ý. Với code bình thường, ưu tiên `Task` để giữ API đơn giản.

### Tip 3 — Dùng `curl -v` hoặc `curl -I` để debug HTTP trước khi đổ lỗi cho application

**Mẹo:**
Khi API gặp lỗi redirect, TLS, proxy, header hoặc status code bất thường, kiểm tra trực tiếp bằng `curl` để tách vấn đề network/protocol khỏi application logic.

**Tại sao hữu ích:**
Giúp xác định nhanh server có thực sự trả response như application ghi nhận hay không, đồng thời thấy request/response headers và redirect chain.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Chỉ xem headers:

```bash
curl -I https://api.example.com/resource
```

Theo redirect:

```bash
curl -L -v https://example.com/login
```

**Lưu ý:**
Kết quả từ máy local không đảm bảo giống container hoặc production host vì DNS, proxy, certificate store và network policy có thể khác.

### Tip 4 — Dùng `git range-diff` sau rebase để kiểm tra mình có làm mất thay đổi không

**Mẹo:**
Sau một rebase lớn, dùng `git range-diff` để so sánh chuỗi commit trước và sau rebase thay vì chỉ nhìn diff cuối cùng.

**Tại sao hữu ích:**
Bạn có thể phát hiện commit bị mất, patch bị thay đổi ngoài ý muốn hoặc conflict resolution làm biến dạng logic.

**Ví dụ:**
```bash
git range-diff origin/main...feature-before-rebase \
               origin/main...feature-after-rebase
```

**Lưu ý:**
`range-diff` so sánh patch series, không thay thế test suite hoặc code review. Nó đặc biệt hữu ích với branch nhiều commit có chủ đích.

### Tip 5 — Tách readiness và liveness health check

**Mẹo:**
Trong service chạy dưới Kubernetes hoặc orchestrator, đừng dùng cùng một health check cho cả liveness và readiness.

**Tại sao hữu ích:**
Readiness trả lời “instance có sẵn sàng nhận traffic không?”, còn liveness trả lời “process có bị kẹt đến mức cần restart không?”. Gộp hai khái niệm có thể gây restart loop khi dependency ngoài tạm thời down.

**Ví dụ:**
```csharp
builder.Services.AddHealthChecks()
    .AddCheck<ProcessHealthCheck>("self", tags: new[] { "live" })
    .AddSqlServer(connectionString, tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("ready")
});
```

**Lưu ý:**
Không nên để liveness phụ thuộc trực tiếp vào database hoặc third-party API nếu việc restart process không thể sửa dependency failure đó.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database + message broker

**Khái niệm:**
Outbox Pattern lưu business data và integration event trong cùng một local database transaction. Một worker sau đó đọc Outbox và publish message sang broker.

**Vấn đề nó giải quyết:**
Nếu application `SaveChanges()` thành công nhưng publish RabbitMQ thất bại, hoặc ngược lại, database và broker có thể lệch trạng thái. Distributed transaction thường không đáng dùng hoặc không được hỗ trợ xuyên các thành phần.

**Ví dụ thực tế:**
Khi tạo order:

```text
Transaction
  INSERT Order
  INSERT OutboxMessage(OrderCreated)
Commit
```

Background worker lấy `OutboxMessage`, publish `OrderCreated`, rồi đánh dấu message đã xử lý.

**Trade-off:**
Lợi ích là tránh mất integration event khi database transaction đã commit. Chi phí là eventual consistency, thêm worker, retry logic, cleanup và khả năng publish duplicate nếu worker crash sau publish nhưng trước khi mark processed.

**Middle → Senior insight:**
Middle developer nên hiểu tại sao `SaveChanges()` rồi `Publish()` không atomic. Senior developer cần thiết kế deduplication, retry, ordering, batch processing, cleanup và observability cho toàn bộ Outbox pipeline.

### Design 2 — Optimistic Concurrency thay vì lock mọi thứ

**Khái niệm:**
Optimistic Concurrency giả định conflict hiếm và cho nhiều transaction đọc/sửa song song, sau đó phát hiện conflict khi update bằng version/token.

**Vấn đề nó giải quyết:**
Pessimistic lock có thể giữ database lock lâu, giảm throughput và tạo deadlock khi nhiều request cùng thao tác dữ liệu. Với workload conflict thấp, optimistic strategy thường hiệu quả hơn.

**Ví dụ thực tế:**
Một entity có version:

```csharp
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
```

Nếu hai user sửa cùng record, EF Core có thể ném `DbUpdateConcurrencyException` cho request commit sau.

**Trade-off:**
Ưu điểm là tránh lock dài và scale tốt khi conflict hiếm. Nhược điểm là application phải quyết định retry, reject hay merge khi conflict xảy ra. Với resource cực kỳ tranh chấp, retry liên tục có thể tệ hơn lock có kiểm soát.

**Middle → Senior insight:**
Middle developer cần biết cách phát hiện và xử lý concurrency conflict. Senior developer phải đánh giá conflict rate, invariant, user experience và chọn giữa retry tự động, merge, version check hay serialized processing.

### Design 3 — Bulkhead: cô lập resource để một dependency không kéo sập toàn hệ thống

**Khái niệm:**
Bulkhead Pattern chia resource hoặc concurrency limit theo workload/dependency, giống các khoang kín trên tàu. Một nhóm request bị quá tải không nên chiếm toàn bộ thread, connection hoặc worker capacity của service.

**Vấn đề nó giải quyết:**
Nếu một third-party API chậm và mọi request đều chờ nó, connection/task backlog có thể tăng đến mức các endpoint không liên quan cũng mất khả năng phục vụ.

**Ví dụ thực tế:**
Một service gọi `PaymentProvider` và `RecommendationProvider`. Recommendation là tính năng phụ. Có thể giới hạn tối đa 20 concurrent calls cho Recommendation, trong khi Payment có pool/concurrency policy riêng. Khi Recommendation quá tải, chỉ phần đó degrade thay vì toàn service bị saturation.

**Trade-off:**
Lợi ích là failure isolation và predictable resource usage. Chi phí là phải chọn limit phù hợp; limit quá thấp làm giảm throughput, limit quá cao mất tác dụng. Ngoài ra cần quyết định queue, timeout và fallback behavior.

**Middle → Senior insight:**
Middle developer nên hiểu timeout/retry không đủ khi resource vẫn có thể bị chiếm hết. Senior developer phải nhìn toàn bộ resource budget — connection pool, thread pool, broker consumers, downstream limits — và thiết kế isolation theo business criticality.
