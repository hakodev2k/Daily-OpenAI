# Daily Developer Tips & Design — 2026-09-28

## 🛠 Developer Tips & Tricks

### Tip 1 — Giữ `DbContext` ngắn hạn để tránh change tracker phình to

**Mẹo:**
Trong worker hoặc batch xử lý hàng nghìn records, đừng giữ một `DbContext` duy nhất sống suốt job. Chia workload thành batch và tạo scope/`DbContext` mới theo batch; với dữ liệu chỉ đọc, dùng projection và `AsNoTracking()`.

**Tại sao hữu ích:**
`DbContext` theo dõi entity đã materialize để phát hiện thay đổi. Khi một context sống quá lâu, change tracker giữ ngày càng nhiều object, làm tăng memory, chi phí `DetectChanges` và nguy cơ vô tình persist state từ batch trước.

**Ví dụ:**
```csharp
foreach (var batch in ids.Chunk(500))
{
    await using var db = await factory.CreateDbContextAsync(ct);

    var rows = await db.Orders
        .Where(x => batch.Contains(x.Id))
        .ToListAsync(ct);

    foreach (var row in rows)
        row.ProcessedAt = DateTimeOffset.UtcNow;

    await db.SaveChangesAsync(ct);
}
```
Batch size nên được đo theo query plan, transaction duration và memory thay vì chọn một con số cố định cho mọi workload.

**Lưu ý:**
Không dùng nhiều `DbContext` tùy tiện nếu toàn bộ operation phải nằm trong một transaction atomic. `AsNoTracking()` cũng không phù hợp khi chính các entity đó cần được sửa rồi `SaveChanges`.

### Tip 2 — Khi PostgreSQL/SQL Server “bỗng” chậm, kiểm tra cardinality estimate trước khi thêm index

**Mẹo:**
Khi execution plan thay đổi và latency tăng, so sánh estimated rows với actual rows ở các operator quan trọng. Nếu chênh lệch lớn, điều tra statistics, data skew, parameter sensitivity và predicate trước khi kết luận thiếu index.

**Tại sao hữu ích:**
Optimizer chọn join strategy, access path và memory grant dựa trên cardinality estimate. Estimate sai có thể khiến một query dùng nested loop cho tập dữ liệu lớn hoặc cấp memory không phù hợp dù index hiện tại hoàn toàn hợp lý.

**Ví dụ:**
Một query Orders theo `TenantId` thường trả 100 rows nhưng một tenant lớn trả 2 triệu rows. Plan tối ưu cho tenant nhỏ có thể rất tệ với tenant lớn. Evidence cần gồm actual execution plan, parameter thực tế, statistics và distribution của dữ liệu.

**Lưu ý:**
Đừng “fix” bằng cách tạo thêm index sau mỗi slow query. Over-indexing làm write chậm, tăng storage và maintenance. Query hint hoặc ép plan cũng là quyết định vận hành cần lifecycle rõ ràng, không phải default fix.

### Tip 3 — Với Azure Service Bus, coi duplicate delivery là trạng thái bình thường

**Mẹo:**
Thiết kế consumer sao cho xử lý lại cùng message không làm lặp business effect. Lưu một business/idempotency key hoặc inbox record trong cùng transaction với state change khi correctness yêu cầu.

**Tại sao hữu ích:**
Messaging thường có at-least-once delivery semantics: consumer có thể commit database rồi crash trước khi message được complete, khiến broker giao lại. Retry policy không thể loại bỏ hoàn toàn failure window này.

**Ví dụ:**
Consumer nhận `PaymentCaptured { PaymentId, OrderId }`. Trước khi cộng payment vào Order, transaction kiểm tra `PaymentId` đã được áp dụng chưa; nếu đã có thì operation trở thành no-op và message có thể complete an toàn.

**Lưu ý:**
Azure Service Bus duplicate detection không thay thế business idempotency cho mọi trường hợp; nó có window và semantics riêng. Cũng đừng dùng message ID ngẫu nhiên mới ở mỗi retry nếu mục tiêu là nhận diện cùng một logical operation.

### Tip 4 — Với file upload, đừng tin filename và Content-Type từ client

**Mẹo:**
Ở ASP.NET Core, coi filename, extension và `Content-Type` do client gửi là untrusted metadata. Sinh storage key phía server, giới hạn kích thước, kiểm tra loại file theo policy và lưu ngoài executable web root khi không cần public serving trực tiếp.

**Tại sao hữu ích:**
Client có thể gửi `invoice.pdf.exe`, path-like filename hoặc khai báo `image/png` cho dữ liệu khác. Dùng metadata này trực tiếp có thể dẫn đến overwrite, path traversal, unsafe content serving hoặc lưu file nguy hiểm.

**Ví dụ:**
Backend nhận upload, tạo key như `uploads/{tenantId}/{Guid.NewGuid():N}`, lưu original filename chỉ như display metadata đã sanitize, rồi scan/validate theo risk của nghiệp vụ trước khi file được phát hành cho người khác.

**Lưu ý:**
Kiểm tra magic bytes đơn thuần không chứng minh file an toàn. Với tài liệu có rủi ro cao cần malware scanning, authorization khi download, giới hạn decompression và policy riêng cho active content như HTML/SVG.

### Tip 5 — Dùng `git worktree` khi cần sửa hotfix mà không phá working tree hiện tại

**Mẹo:**
Khi đang có feature branch với thay đổi chưa hoàn tất nhưng cần kiểm tra hoặc sửa hotfix ở branch khác, dùng `git worktree` để có working directory thứ hai thay vì stash/unstash liên tục.

**Tại sao hữu ích:**
Mỗi worktree có checkout riêng nhưng dùng chung repository object database. Bạn có thể giữ build/debug state của feature hiện tại và đồng thời mở hotfix trong IDE khác, giảm context switching và lỗi do stash conflict.

**Ví dụ:**
```bash
git worktree add ../app-hotfix origin/main
cd ../app-hotfix
git switch -c hotfix/payment-timeout
```
Sau khi hoàn tất và không còn cần directory:
```bash
git worktree remove ../app-hotfix
```

**Lưu ý:**
Không coi worktree là bản backup; commit hoặc push thay đổi quan trọng. Git cũng không cho cùng một local branch được checkout đồng thời ở nhiều worktree theo cách thông thường.

## 🧠 Software Design

### Design 1 — Transaction boundary theo business invariant, không theo số repository

**Khái niệm:**
Transaction boundary nên bao quanh tập thay đổi phải cùng thành công hoặc cùng thất bại để bảo vệ một business invariant. Số bảng, repository hay application service được gọi không tự quyết định transaction boundary.

**Vấn đề nó giải quyết:**
Nếu tạo Order và reserve inventory phải atomic trong cùng database nhưng mỗi repository tự `SaveChanges`, hệ thống có thể persist Order rồi thất bại trước khi cập nhật inventory. Ngược lại, giữ transaction xuyên HTTP call dài làm lock tồn tại lâu và kết hợp hai failure domain.

**Ví dụ thực tế:**
Trong một Modular Monolith dùng cùng SQL database, application command có thể cập nhật `Orders`, `Inventory` và Outbox trong một local transaction. Việc gọi payment provider được tách khỏi transaction database và phối hợp bằng state transition/message nếu không thể atomic.

**Trade-off:**
Transaction rộng bảo vệ invariant dễ hơn nhưng tăng lock duration, contention và coupling. Transaction nhỏ tăng throughput và fault isolation nhưng có thể yêu cầu eventual consistency, compensation hoặc idempotency.

**Middle → Senior insight:**
Middle developer cần biết operation nào đang nằm trong cùng transaction và tránh `SaveChanges` rải rác làm mất atomicity. Senior / Technical developer phải xác định invariant thực sự, chọn local transaction hay asynchronous coordination, và tránh kéo network I/O vào transaction chỉ để có cảm giác “an toàn”.

### Design 2 — Queue hay Topic: chọn theo ownership của message, không theo tên công nghệ

**Khái niệm:**
Queue phù hợp khi một logical work item cần một consumer group xử lý; Topic + subscriptions phù hợp khi cùng một event cần được nhiều consumer độc lập quan sát với lifecycle và retry riêng.

**Vấn đề nó giải quyết:**
Nếu gửi `OrderCreated` vào một queue rồi Billing và Analytics cùng cạnh tranh đọc, chỉ một bên nhận message — sai với broadcast event. Ngược lại, tạo Topic cho command chỉ có một owner có thể thêm topology và vận hành không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` là command hướng tới Billing worker nên dùng queue là lựa chọn tự nhiên. `OrderCreated` có thể có subscriptions riêng cho Analytics, Notification và Fulfillment; lỗi ở Notification không nên ngăn Fulfillment nhận event của nó.

**Trade-off:**
Topic tăng decoupling và cho mỗi subscriber retry/filter độc lập, nhưng tăng số subscription, dead-letter queue, monitoring và schema consumers phải quản lý. Queue đơn giản hơn nhưng không phải cơ chế broadcast.

**Middle → Senior insight:**
Middle developer cần phân biệt command với event và cấu hình retry/DLQ đúng. Senior / Technical developer phải quyết định ownership, delivery semantics, ordering, fan-out cost và evolution của contract; không chọn Topic chỉ vì “có thể có nhiều consumer trong tương lai”.

### Design 3 — BFF khi các client có nhu cầu contract khác nhau

**Khái niệm:**
Backend for Frontend (BFF) đặt một backend boundary tối ưu cho một loại client hoặc trải nghiệm cụ thể, thay vì buộc web, mobile và CMS frontend cùng phụ thuộc vào một API aggregate khổng lồ.

**Vấn đề nó giải quyết:**
Mobile có bandwidth/round-trip constraints khác web; CMS preview cần metadata mà public storefront không cần. Nếu mọi client dùng chung endpoint tổng quát, API dễ tích tụ flags, payload thừa và coupling giữa release cycles.

**Ví dụ thực tế:**
Storefront web BFF tổng hợp Catalog, Pricing và Personalization thành view model phù hợp SSR. Mobile BFF trả payload nhỏ hơn và contract ổn định theo mobile release cadence. Core services vẫn giữ business capability, BFF chủ yếu orchestration/client adaptation.

**Trade-off:**
BFF giảm client complexity và cho contract phù hợp từng experience, nhưng thêm deployable component, duplicate orchestration và nguy cơ business logic bị rải sang nhiều BFF. Với một client đơn giản, API trực tiếp thường rẻ hơn.

**Middle → Senior insight:**
Middle developer cần giữ BFF tập trung vào client-specific composition, authentication/session concerns và mapping thay vì copy domain logic. Senior / Technical developer phải chứng minh divergence giữa clients đủ lớn để đáng thêm boundary, xác định ownership và tránh biến mỗi BFF thành một monolith mới.
