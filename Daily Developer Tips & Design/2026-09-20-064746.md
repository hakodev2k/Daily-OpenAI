# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — Chuẩn hóa lỗi API bằng `ProblemDetails`, đừng để exception shape rò ra contract

**Mẹo:**
Trong ASP.NET Core, map các failure đã phân loại sang `ProblemDetails`/`ValidationProblemDetails` ở một boundary tập trung thay vì mỗi endpoint tự trả một anonymous error object hoặc serialize exception.

**Tại sao hữu ích:**
Client cần contract lỗi ổn định hơn stack trace nội bộ. Một error boundary thống nhất giúp tách domain/application failure khỏi HTTP representation, đồng thời giữ `status`, `type`, `title` và correlation information nhất quán giữa các endpoint.

**Ví dụ:**
Một `OrderNotFoundException` được exception handler map thành `404`; conflict do concurrency thành `409`; lỗi không dự kiến thành `500` với `traceId` để support tra cứu telemetry. Stack trace chỉ xuất hiện trong server logs.

**Lưu ý:**
Đừng biến mọi exception thành `400`. Status code phải phản ánh HTTP semantics, và error response không được lộ SQL, token, internal hostname hoặc implementation details.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` cho tập dữ liệu lớn

**Mẹo:**
Với feed/list lớn được đọc tuần tự, cân nhắc keyset pagination dựa trên sort key ổn định thay vì `OFFSET ... LIMIT` tăng dần.

**Tại sao hữu ích:**
Offset lớn buộc database bỏ qua ngày càng nhiều rows và dữ liệu insert/delete giữa hai requests có thể làm item bị lặp hoặc bỏ sót. Keyset tiếp tục từ giá trị cuối đã thấy và thường tận dụng composite index tốt hơn.

**Ví dụ:**
Nếu sort theo `CreatedAt DESC, Id DESC`, trang kế tiếp dùng điều kiện `(CreatedAt < @lastCreatedAt) OR (CreatedAt = @lastCreatedAt AND Id < @lastId)` với index tương ứng, thay vì `OFFSET 100000`.

**Lưu ý:**
Keyset không phù hợp khi UI bắt buộc nhảy trực tiếp tới “page 417”. Sort key phải deterministic; chỉ dùng timestamp không unique có thể tạo boundary mơ hồ.

### Tip 3 — Azure Functions queue trigger cần thiết kế cho poison message

**Mẹo:**
Với queue/message-triggered Azure Functions, coi retry exhaustion và poison/dead-letter path là một phần của feature, không phải trường hợp hiếm để xử lý sau.

**Tại sao hữu ích:**
Một message lỗi vĩnh viễn có thể bị retry nhiều lần, tiêu tốn compute và che backlog thật. Tách transient failure khỏi permanent failure giúp hệ thống tiếp tục xử lý message tốt trong khi message xấu được giữ lại để điều tra/replay có kiểm soát.

**Ví dụ:**
Consumer thất bại vì downstream timeout thì retry với policy phù hợp; payload vi phạm invariant được đưa tới failure path cùng `MessageId`, reason và correlation metadata. Dashboard theo dõi retry count, DLQ/poison depth và message age.

**Lưu ý:**
Đừng tự động replay toàn bộ poison messages sau khi deploy fix. Handler phải idempotent và cần xác minh side effects trước đó để replay không tạo duplicate processing.

### Tip 4 — CLS thường đến từ việc browser chưa biết kích thước media

**Mẹo:**
Khi Core Web Vitals báo Cumulative Layout Shift cao, kiểm tra image, banner, embed và async content có reserved space trước khi tối ưu JavaScript theo cảm tính.

**Tại sao hữu ích:**
Nếu browser chưa biết kích thước phần tử trước khi resource tải xong, layout phải dịch chuyển khi content xuất hiện. Khai báo intrinsic dimensions hoặc giữ aspect ratio cho phép browser dành chỗ ngay từ layout đầu.

**Ví dụ:**
Một CMS hero image được render với `width`/`height` đúng tỷ lệ hoặc CSS `aspect-ratio`; Lighthouse/DevTools Performance sau đó được dùng để xác nhận layout-shift entries giảm ở đúng element.

**Lưu ý:**
Không hard-code kích thước làm méo responsive layout. Cookie banner, web font và client-rendered personalization cũng có thể gây CLS; cần dựa trên shift evidence thay vì chỉ nhìn tổng score.

### Tip 5 — AI-generated code phải được kiểm tra theo repository version thực tế

**Mẹo:**
Khi dùng AI coding agent để thêm API/package usage, xác minh generated code với `.csproj`, lock/dependency files, compiler và tests của repository thay vì tin API name nghe hợp lý.

**Tại sao hữu ích:**
Model có thể sinh API thuộc version khác, extension method từ package chưa cài hoặc pattern đúng về cú pháp nhưng sai convention/architecture của codebase. Repository source và executable checks là ground truth tốt hơn câu trả lời tự tin.

**Ví dụ:**
Agent đề xuất một EF Core API mới. Trước khi nhận patch, kiểm tra target framework/package version, chạy build + relevant integration tests và xem generated SQL nếu thay đổi nằm trên query path quan trọng.

**Lưu ý:**
Test xanh không chứng minh design đúng. Vẫn phải review authorization, failure semantics, performance, migration impact và abstraction mới mà agent đưa vào.

## 🧠 Software Design

### Design 1 — Hexagonal Architecture chỉ có giá trị khi ports bảo vệ boundary thật

**Khái niệm:**
Hexagonal Architecture đặt business/application capability phía trong và giao tiếp với database, HTTP, messaging hoặc external systems qua ports/adapters. Giá trị nằm ở dependency boundary, không nằm ở việc tạo nhiều interface/folder.

**Vấn đề nó giải quyết:**
Business workflow dễ bị gắn chặt vào EF Core entity, SDK cloud hoặc HTTP client details, khiến test, migration và thay đổi integration kéo logic nghiệp vụ đi theo infrastructure.

**Ví dụ thực tế:**
Pricing application cần “lấy exchange rate” qua một port có semantics nghiệp vụ; adapter production gọi third-party API, còn test dùng deterministic fake. Không cần tạo interface cho mọi class chỉ để đạt hình dạng kiến trúc.

**Trade-off:**
Boundary rõ giúp isolation và thay adapter dễ hơn, nhưng quá nhiều ports cho CRUD đơn giản tạo indirection và mapping cost. Layered architecture trực tiếp có thể phù hợp hơn khi integration volatility thấp và domain đơn giản.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và không để infrastructure types rò vào core tùy tiện. Senior / Technical developer phải nhận ra seam nào có volatility/testability pressure đủ lớn để đáng abstraction, và seam nào nên giữ đơn giản.

### Design 2 — Transaction boundary không nên bao quanh remote call nếu không có lý do mạnh

**Khái niệm:**
Database transaction bảo vệ local consistency; kéo một HTTP/service call chậm vào giữa transaction thường làm lock và connection lifetime phụ thuộc vào network latency mà transaction không thể rollback ở remote system.

**Vấn đề nó giải quyết:**
Một workflow update database rồi gọi payment/shipping dễ bị thiết kế như một synchronous block “atomic”, nhưng thực tế local SQL transaction không tạo atomicity xuyên dependency và còn làm tăng blocking khi remote call chậm.

**Ví dụ thực tế:**
Order creation commit local state/outbox trong transaction ngắn, sau đó integration được xử lý ngoài transaction với idempotency và recovery semantics. Với workflow cần immediate response, vẫn phải model rõ failure window thay vì giữ SQL lock trong lúc chờ HTTP.

**Trade-off:**
Transaction ngắn tăng concurrency và giảm lock risk nhưng buộc hệ thống xử lý intermediate state/eventual consistency. Giữ mọi thứ synchronous đơn giản hơn về mental model khi operation thật sự local, nhưng không biến remote side effect thành ACID.

**Middle → Senior insight:**
Middle developer cần nhận diện network I/O nằm trong transaction và hiểu lock duration. Senior / Technical developer phải xác định business invariant, failure windows và chọn outbox, compensation, idempotency hoặc synchronous coordination theo yêu cầu thực tế.

### Design 3 — Contract tests nằm giữa unit test và full E2E

**Khái niệm:**
Contract testing xác minh producer và consumer đồng ý về interface observable như HTTP schema/message payload mà không cần dựng toàn bộ hệ thống end-to-end cho mọi trường hợp.

**Vấn đề nó giải quyết:**
Unit tests của từng service có thể đều xanh nhưng integration vẫn vỡ vì field bị đổi, enum semantics khác hoặc consumer kỳ vọng response mà producer không còn cung cấp. Full E2E bắt được một phần lỗi nhưng thường chậm và khó bao phủ mọi consumer contract.

**Ví dụ thực tế:**
Mobile backend consumer lưu expectation cho Product API; CI của producer kiểm tra thay đổi OpenAPI/behavior có phá contract đang được sử dụng trước khi release. Các critical journeys vẫn giữ E2E tests riêng.

**Trade-off:**
Contract tests cho feedback nhanh và ownership rõ hơn nhưng thêm contract lifecycle, versioning và test infrastructure. Chúng không phát hiện mọi lỗi runtime như auth configuration, networking hay database failure nên không thay thế integration/E2E hoàn toàn.

**Middle → Senior insight:**
Middle developer cần viết contract quanh behavior consumer thực sự phụ thuộc, không snapshot mọi field vô nghĩa. Senior / Technical developer phải thiết kế test portfolio theo failure risk: unit cho logic, integration cho boundary thật, contract cho compatibility và một số E2E cho critical journeys.
