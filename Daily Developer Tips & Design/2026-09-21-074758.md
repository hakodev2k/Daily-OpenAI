# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncDisposable` khi cleanup bản thân cũng là I/O

**Mẹo:**
Khi resource cần asynchronous cleanup, ưu tiên `IAsyncDisposable` và `await using` thay vì ép cleanup qua `Dispose()` synchronous. Ví dụ thường gặp là stream/writer cần flush asynchronous hoặc resource wrapper có teardown liên quan đến I/O.

**Tại sao hữu ích:**
Nếu cleanup phải chờ I/O nhưng bị ép thành synchronous wait, request thread có thể bị block đúng lúc hệ thống đang chịu tải. `await using` cho phép compiler tạo `try/finally` và await `DisposeAsync()` đúng lifecycle mà không biến asynchronous work thành blocking work.

**Ví dụ:**
```csharp
await using var writer = CreateAsyncWriter();
await writer.WriteAsync(payload, cancellationToken);
```
Trong một export endpoint, writer có thể flush buffered output asynchronously khi scope kết thúc thay vì gọi `.GetAwaiter().GetResult()` trong `Dispose()`.

**Lưu ý:**
Không implement `IAsyncDisposable` chỉ vì class có async methods. Cleanup chỉ cần async khi thực sự có asynchronous release work; đồng thời phải xác định rõ ownership để tránh caller dispose một dependency được DI container quản lý.

### Tip 2 — Rate limiting nên phân vùng theo identity phù hợp với tài nguyên

**Mẹo:**
Trong ASP.NET Core, đừng áp một global request count giống nhau cho mọi endpoint. Chọn partition key và policy theo tài nguyên cần bảo vệ: authenticated user, API key, tenant, client IP hoặc operation cụ thể.

**Tại sao hữu ích:**
Một limit toàn cục có thể cho phép một tenant chiếm phần lớn capacity hoặc ngược lại khóa nhầm nhiều users sau cùng NAT. Rate limiting hiệu quả phải phản ánh đơn vị tiêu thụ tài nguyên và abuse model thực tế.

**Ví dụ:**
Search API có policy theo tenant vì Elasticsearch capacity được chia theo tenant, trong khi password-reset endpoint có thêm policy theo account/IP để hạn chế abuse. Khi limit bị vượt, API trả `429 Too Many Requests` và telemetry ghi policy/partition bị throttled.

**Lưu ý:**
Rate limiter không thay thế authorization, quota billing hay DDoS protection ở edge. Partition key có cardinality không kiểm soát cũng gây memory pressure; proxy/load balancer có thể làm IP detection sai nếu forwarded headers không được cấu hình an toàn.

### Tip 3 — PostgreSQL/SQL Server statistics có thể khiến plan xấu dù index vẫn tồn tại

**Mẹo:**
Khi query đột nhiên chậm, kiểm tra estimated rows so với actual rows và statistics trước khi kết luận index bị thiếu. Optimizer chọn join/order/access strategy dựa mạnh vào cardinality estimates.

**Tại sao hữu ích:**
Một index phù hợp không đảm bảo optimizer sẽ dùng đúng cách nếu distribution đã thay đổi hoặc predicate có skew lớn. Estimate sai có thể dẫn tới nested loop trên tập dữ liệu lớn, memory grant không phù hợp hoặc scan ngoài dự kiến.

**Ví dụ:**
Sau bulk import, API lọc `Status = 'Pending'` tăng từ vài nghìn lên hàng triệu rows. Execution plan vẫn dùng schema/index cũ nhưng estimate thấp hơn actual rất nhiều. Team xác nhận statistics/data distribution trước khi thêm một index mới có thể làm write cost tăng mà không chữa root cause.

**Lưu ý:**
Không chạy update statistics/rebuild index như nghi thức cho mọi slow query. Parameter sensitivity, predicate shape, stale plan và schema/index design cũng phải được xem xét bằng execution plan và workload thật.

### Tip 4 — `readiness` và `liveness` phải trả lời hai câu hỏi khác nhau

**Mẹo:**
Trong Kubernetes, dùng readiness để quyết định Pod có nên nhận traffic; dùng liveness để phát hiện process bị kẹt và cần restart. Đừng copy cùng một dependency-heavy health check cho cả hai probe.

**Tại sao hữu ích:**
Nếu database tạm thời lỗi và liveness phụ thuộc database, Kubernetes có thể restart hàng loạt healthy processes, làm incident nặng hơn. Readiness có thể rút instance khỏi traffic trong khi process vẫn sống để dependency phục hồi.

**Ví dụ:**
ASP.NET Core service có liveness kiểm tra process/event loop cơ bản, còn readiness xác nhận startup hoàn tất và các điều kiện bắt buộc để phục vụ request. Khi downstream DB mất kết nối ngắn hạn, instance ngừng nhận traffic theo policy nhưng không bị restart loop vô ích.

**Lưu ý:**
Readiness cũng không nên gọi hàng loạt external services ở mỗi probe nếu điều đó tạo thêm tải hoặc coupling. Probe thresholds, startup time và graceful shutdown cần được thiết kế cùng deployment strategy.

### Tip 5 — Dùng browser DevTools để tách backend latency khỏi frontend rendering

**Mẹo:**
Khi người dùng báo “trang chậm”, bắt đầu bằng Network waterfall và Performance trace để tách DNS/TLS, TTFB, payload download, JavaScript execution, rendering và long tasks trước khi tối ưu backend hoặc bundle theo cảm tính.

**Tại sao hữu ích:**
Cùng một triệu chứng UX có thể đến từ API TTFB 2 giây, bundle 4 MB, main-thread blocking hoặc ảnh chưa tối ưu. Đo từng phase giúp team sửa đúng bottleneck và tránh chuyển complexity sang layer không gây vấn đề.

**Ví dụ:**
Product page mất 3 giây mới tương tác được. Network cho thấy API trả trong 180 ms nhưng một third-party script tạo long task hơn 1 giây và bundle parse/execute chiếm phần lớn thời gian. Backend optimization lúc này gần như không cải thiện Interaction to Next Paint.

**Lưu ý:**
DevTools local không đại diện đầy đủ thiết bị/network production. Kết hợp lab measurement với Real User Monitoring/Core Web Vitals và kiểm tra cache state, throttling, device class trước khi kết luận.

## 🧠 Software Design

### Design 1 — Outbox Pattern giải quyết khoảng trống giữa database commit và message publish

**Khái niệm:**
Outbox Pattern ghi business state và một outbox record trong cùng local database transaction. Một publisher riêng sau đó gửi message ra broker và đánh dấu/ghi nhận trạng thái xử lý, thay vì cố commit database và publish broker như hai hành động độc lập.

**Vấn đề nó giải quyết:**
Nếu application commit Order rồi crash trước khi publish `OrderPlaced`, downstream không bao giờ biết order tồn tại. Nếu publish trước rồi database rollback, consumer lại thấy một event cho state chưa được commit.

**Ví dụ thực tế:**
Checkout transaction insert `Order` và `OutboxMessage(OrderPlaced)` cùng lúc. Background worker đọc pending outbox records, publish lên Azure Service Bus và retry khi broker tạm lỗi. Consumer vẫn phải idempotent vì publish có thể xảy ra nhiều lần.

**Trade-off:**
Outbox loại bỏ dual-write inconsistency giữa local DB và broker nhưng thêm table growth, polling/CDC, cleanup, delivery latency và operational monitoring. Nó không tạo exactly-once end-to-end và không cần thiết cho mọi CRUD operation không phát integration event.

**Middle → Senior insight:**
Middle developer cần hiểu transaction boundary và không đánh dấu outbox thành công trước khi broker operation thực sự hoàn tất. Senior / Technical developer phải chọn polling hay CDC, thiết kế deduplication, ordering, retention, failure recovery và quyết định nơi nào consistency requirement đủ quan trọng để trả chi phí Outbox.

### Design 2 — API backward compatibility là một quyết định về contract ownership

**Khái niệm:**
Một API contract không chỉ là shape JSON hiện tại; nó là cam kết giữa provider và consumers về fields, semantics, status codes và behavior trong một khoảng thời gian. Evolution strategy phải phản ánh khả năng phối hợp release giữa hai phía.

**Vấn đề nó giải quyết:**
Backend deploy nhanh hơn mobile app, partner integration hoặc nhiều frontend độc lập. Một rename field tưởng nhỏ có thể làm clients cũ hỏng ngay cả khi server code mới hoàn toàn đúng.

**Ví dụ thực tế:**
Mobile API cần thay `customerName` bằng cấu trúc `customer`. Server giữ field cũ trong compatibility window, thêm contract tests cho client versions đang support và chỉ loại bỏ khi telemetry/adoption cho thấy không còn consumers phụ thuộc contract cũ.

**Trade-off:**
Backward compatibility giảm coordinated deployment risk nhưng giữ legacy surface, test matrix và maintenance cost. Versioning mọi thay đổi cũng gây fragmentation; additive evolution thường đơn giản hơn khi semantics cũ vẫn đúng.

**Middle → Senior insight:**
Middle developer cần phân biệt breaking với non-breaking changes và test serialized contract. Senior / Technical developer phải xác định ownership, deprecation policy, consumer visibility, compatibility window và khi nào version mới thực sự đáng chi phí vận hành.

### Design 3 — Multi-tenant data isolation phải được thiết kế ở nhiều lớp

**Khái niệm:**
Tenant isolation là invariant xuyên suốt authentication context, authorization, application queries, database constraints/policies, cache keys, messaging và observability. Chỉ thêm `TenantId` vào một số tables chưa tạo thành isolation model an toàn.

**Vấn đề nó giải quyết:**
Một query thiếu tenant predicate, cache key dùng chung hoặc background message thiếu tenant context có thể làm dữ liệu của tenant A xuất hiện trong tenant B dù từng component riêng lẻ vẫn hoạt động “đúng”.

**Ví dụ thực tế:**
SaaS API lấy tenant từ trusted identity claim, application layer truyền tenant context, EF Core/query layer enforce scope, unique constraints bao gồm tenant khi phù hợp, Redis keys namespace theo tenant và Service Bus messages mang tenant metadata được validate trước xử lý.

**Trade-off:**
Shared database/schema có chi phí vận hành thấp hơn nhưng đòi hỏi isolation controls rất chặt; database/schema per tenant tăng isolation và migration/backup flexibility nhưng tăng provisioning, connection management và operational complexity.

**Middle → Senior insight:**
Middle developer cần không nhận `TenantId` từ request body như nguồn tin cậy và phải viết tests chống cross-tenant access. Senior / Technical developer phải chọn isolation model dựa trên security/compliance, scale, noisy-neighbor risk, backup/restore requirements và khả năng vận hành, đồng thời thiết kế defense-in-depth thay vì dựa vào một query filter duy nhất.
