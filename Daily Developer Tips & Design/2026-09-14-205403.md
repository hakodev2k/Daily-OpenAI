# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Cẩn thận state leakage khi dùng `AddDbContextPool`

**Mẹo:**
`AddDbContextPool` có thể giảm chi phí tạo `DbContext`, nhưng pooled context được tái sử dụng giữa nhiều request. Chỉ dùng khi mọi state gắn với request hoặc tenant được reset đúng cách và không bị lưu trực tiếp trong instance của `DbContext`.

**Tại sao hữu ích:**
Pooling giảm allocation và setup cost, nhưng lifecycle khác với việc luôn tạo instance mới. Nếu bạn gán `TenantId`, flag hoặc interceptor state trực tiếp vào context rồi quên reset, request sau có thể thừa hưởng state của request trước — một bug đặc biệt nguy hiểm trong multi-tenant system.

**Ví dụ:**
```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Thay vì lưu tenant mutable trong context lâu dài, truyền tenant qua service/scoped abstraction và đảm bảo query filter lấy đúng state theo request lifecycle.

**Lưu ý:**
Đừng bật pooling chỉ vì nó “nhanh hơn”. Trước tiên đo chi phí tạo `DbContext`. Nếu context chứa mutable per-request state, pooling có thể làm correctness phức tạp hơn lợi ích hiệu năng nhận được.

### Tip 2 — Với Azure Service Bus `PeekLock`, handler dài phải tính đến lock expiry

**Mẹo:**
Khi consumer xử lý message lâu, theo dõi `LockDuration`, automatic lock renewal và thời gian xử lý thực tế. Nếu lock hết hạn trước khi `CompleteMessageAsync()`, cùng message có thể được giao lại dù handler đầu tiên vẫn đang chạy.

**Tại sao hữu ích:**
Azure Service Bus dùng at-least-once delivery. Lock chỉ tạm thời giữ quyền xử lý message; nó không phải transaction lock vĩnh viễn. Một handler chạy 8 phút với lock ngắn hơn có thể gây duplicate processing nếu lock renewal không đủ hoặc bị gián đoạn.

**Ví dụ:**
```text
Message received at 10:00:00
Lock expires at 10:01:00
Handler calls slow external API for 90s

10:01:00 -> lock expires
10:01:10 -> broker redelivers message
10:01:30 -> original handler tries Complete -> lock lost
```

Với xử lý dài, cấu hình renewal phù hợp hoặc tách work dài sang workflow khác rồi acknowledge message sớm khi semantics cho phép.

**Lưu ý:**
Tăng lock duration không thay thế idempotency. Process có thể crash sau side effect nhưng trước `Complete`; duplicate vẫn xảy ra. Consumer phải chịu được redelivery.

### Tip 3 — Trong Elasticsearch, chọn đúng `text` và `keyword` để tránh query sai semantics

**Mẹo:**
Dùng `text` cho full-text search cần analyzer/tokenization; dùng `keyword` cho exact match, filter, aggregation, sorting hoặc identifier. Một field đôi khi cần multi-field để phục vụ cả hai kiểu truy vấn.

**Tại sao hữu ích:**
Nếu map `ProductName` chỉ là `text` rồi dùng aggregation hoặc exact filter trên field đó, kết quả có thể không như mong đợi vì dữ liệu đã qua analyzer. Ngược lại, map toàn bộ nội dung mô tả thành `keyword` sẽ làm full-text search mất khả năng tokenization và relevance scoring.

**Ví dụ:**
```json
"name": {
  "type": "text",
  "fields": {
    "raw": { "type": "keyword" }
  }
}
```

- Search: `match` trên `name`
- Sort/aggregation: dùng `name.raw`

**Lưu ý:**
Mapping là quyết định gần như schema-level. Đổi analyzer hoặc field type thường cần reindex. Đừng đợi tới production mới phát hiện field mapping không phù hợp với query pattern.

### Tip 4 — Trong Vue, dùng `computed` cho derived state thay vì đồng bộ state bằng `watch`

**Mẹo:**
Nếu một giá trị có thể được tính trực tiếp từ state hiện tại, ưu tiên `computed`. Chỉ dùng `watch` khi cần side effect như gọi API, ghi storage hoặc trigger integration bên ngoài.

**Tại sao hữu ích:**
Dùng `watch` để cập nhật một state khác tạo thêm mutable state và nguy cơ hai giá trị lệch nhau. `computed` giữ dependency graph rõ hơn và tự cache theo reactive dependency.

**Ví dụ:**
```ts
const firstName = ref('Ha')
const lastName = ref('Dinh')

const fullName = computed(() => `${firstName.value} ${lastName.value}`)
```

Không cần `watch([firstName, lastName], ...)` chỉ để cập nhật `fullName`.

**Lưu ý:**
`computed` không phù hợp cho side effect asynchronous. Với search-as-you-type, `watch` có thể đúng chỗ, nhưng cần cancellation/debounce để tránh race và request thừa.

### Tip 5 — Chặn SSRF ở outbound HTTP bằng policy, không chỉ bằng validate URL string

**Mẹo:**
Nếu backend nhận URL từ user rồi gọi bằng `HttpClient`, hãy coi đó là SSRF attack surface. Chỉ cho phép scheme/host cần thiết, resolve DNS cẩn thận và chặn truy cập tới private/internal address range khi business không yêu cầu.

**Tại sao hữu ích:**
Attacker có thể ép server gọi tới `localhost`, metadata endpoint, internal admin service hoặc private network mà Internet không truy cập trực tiếp được. Backend trở thành proxy có quyền truy cập nội bộ thay attacker.

**Ví dụ:**
```text
User input:
https://example.com/webhook   -> có thể hợp lệ
http://127.0.0.1:5000/admin   -> phải chặn
http://169.254.169.254/...    -> phải chặn
```

Tốt nhất là allowlist domain hoặc integration target đã đăng ký thay vì cho user nhập URL tùy ý.

**Lưu ý:**
Regex kiểm tra chuỗi URL không đủ để chống DNS rebinding, redirect hoặc hostname resolve sang private IP. Nếu use case bắt buộc gọi arbitrary URL, cần network egress control và validation ở nhiều lớp.

## 🧠 Software Design

### Design 1 — Inbox Pattern giúp consumer xử lý message idempotent

**Khái niệm:**
Inbox Pattern lưu `MessageId` hoặc processing record tại consumer trước hoặc cùng transaction với business change để nhận biết message đã được xử lý. Khi broker redeliver cùng message, consumer có thể bỏ qua hoặc replay kết quả an toàn.

**Vấn đề nó giải quyết:**
Message broker thường đảm bảo at-least-once delivery. Consumer có thể cập nhật database thành công nhưng crash trước khi acknowledge message. Broker sau đó gửi lại message; nếu consumer không deduplicate, cùng side effect có thể chạy lần hai.

**Ví dụ thực tế:**
```text
Receive OrderPaid message M123

Transaction:
1. kiểm tra Inbox(M123)
2. nếu chưa có -> update Order
3. insert Inbox(M123)
4. commit

Broker redelivers M123
-> Inbox đã tồn tại
-> skip duplicate business update
```

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, cleanup policy và transaction coordination. Nếu message rate rất cao, inbox table có thể lớn nhanh. Có thể dùng unique constraint trên message identity để biến duplicate detection thành invariant ở database.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là trạng thái bình thường của messaging, không phải exception hiếm. Senior / Technical developer phải xác định deduplication key, retention window, transaction boundary và semantics khi cùng business event được phát lại với payload khác.

### Design 2 — Vertical Slice Architecture tối ưu theo use case, không theo technical layer

**Khái niệm:**
Vertical Slice Architecture tổ chức code theo feature/use case như `CreateOrder`, `GetOrderDetails`, `CancelOrder` thay vì gom toàn bộ controller, service, repository vào các layer lớn. Mỗi slice chứa phần cần thiết để hoàn thành một behavior cụ thể.

**Vấn đề nó giải quyết:**
Trong layered application lớn, một thay đổi nhỏ có thể buộc developer nhảy qua Controller → Service → Repository → Mapper → DTO folder dù logic thực tế rất đơn giản. Coupling theo layer làm ownership của feature khó thấy và refactor use case tốn context switching.

**Ví dụ thực tế:**
```text
Features/
  Orders/
    Create/
      Endpoint.cs
      Command.cs
      Handler.cs
      Validator.cs
    GetDetails/
      Endpoint.cs
      Query.cs
      Handler.cs
```

Shared concern chỉ được tách ra khi thực sự có reuse hoặc invariant chung.

**Trade-off:**
Vertical Slice giảm coupling giữa feature và tăng locality, nhưng có thể tạo duplication nhỏ giữa slices. Nếu team cố DRY mọi thứ quá sớm, kiến trúc lại quay về shared service khổng lồ. Với domain giàu invariant, vẫn cần domain model hoặc shared domain concepts phù hợp.

**Middle → Senior insight:**
Middle developer cần giữ một slice cohesive và tránh xuyên qua boundary tùy tiện. Senior / Technical developer phải quyết định đâu là duplication chấp nhận được, đâu là domain rule cần centralize và khi nào layered/shared abstraction vẫn có giá trị hơn.

### Design 3 — Read Replica cải thiện read scale nhưng đưa replication lag vào consistency model

**Khái niệm:**
Read replica cho phép tách một phần read workload khỏi primary database. Application ghi vào primary, còn query ít yêu cầu strong consistency có thể đọc từ replica.

**Vấn đề nó giải quyết:**
Một hệ thống báo cáo hoặc catalog có rất nhiều read nhưng write ít hơn. Nếu mọi query đều đi primary, connection/CPU/I/O của primary có thể trở thành bottleneck dù workload đọc không cần dữ liệu vừa ghi tức thì.

**Ví dụ thực tế:**
```text
POST /orders
-> write Primary

GET /reports/daily-sales
-> read Replica

GET /orders/{id} ngay sau khi tạo
-> vẫn đọc Primary nếu cần read-your-own-write
```

Không nên route mọi GET sang replica một cách máy móc.

**Trade-off:**
Replica tăng read capacity và isolation, nhưng replication lag tạo stale read. Failover, routing và monitoring cũng phức tạp hơn. Một query cần dữ liệu vừa commit có thể trả kết quả cũ nếu đọc replica quá sớm.

**Middle → Senior insight:**
Middle developer cần biết read replica không phải bản sao synchronous mặc định. Senior / Solution-oriented engineer phải phân loại endpoint theo consistency requirement, đo lag, thiết kế fallback/read-your-own-write và cân nhắc liệu tối ưu query/index trên primary có rẻ hơn việc thêm topology mới hay không.
