# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` để tạo backpressure cho producer/consumer trong .NET

**Mẹo:**
Khi một producer tạo work nhanh hơn consumer xử lý, dùng bounded `Channel<T>` thay vì `ConcurrentQueue<T>` không giới hạn để kiểm soát lượng work đang chờ.

**Tại sao hữu ích:**
Queue không giới hạn có thể che overload cho tới khi memory tăng mạnh hoặc latency backlog kéo dài. Bounded channel tạo backpressure: producer phải chờ khi buffer đầy, giúp throughput bám sát capacity xử lý thực tế.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait
});

await channel.Writer.WriteAsync(job, ct);

await foreach (var item in channel.Reader.ReadAllAsync(ct))
{
    await ProcessAsync(item, ct);
}
```

Theo dõi queue depth, processing rate và wait time để biết hệ thống đang ổn định hay chỉ đẩy latency sang backlog.

**Lưu ý:**
Backpressure không tự giải quyết capacity shortage. Nếu producer là HTTP endpoint, cần quyết định khi nào nên chờ, trả `429/503`, hoặc chuyển work sang durable broker thay vì giữ trong memory.

### Tip 2 — Trong Elasticsearch, filter context giúp tránh tính relevance khi không cần score

**Mẹo:**
Với điều kiện kiểu `status`, `tenantId`, `categoryId`, date range hoặc permission filter, dùng filter context thay vì full-text query nếu bạn không cần relevance score.

**Tại sao hữu ích:**
Filter chỉ trả lời document có match hay không, thường dễ cache và không phải tính `_score`. Full-text query phù hợp với search theo nội dung, nhưng dùng nó cho exact constraints làm semantics khó đọc và có thể tốn thêm work không cần thiết.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless keyboard" } }
      ],
      "filter": [
        { "term": { "status": "active" } },
        { "term": { "tenantId": "t1" } }
      ]
    }
  }
}
```

`match` quyết định relevance; `term` trong `filter` chỉ giới hạn tập document hợp lệ.

**Lưu ý:**
Filter context không cứu được mapping sai. Nếu field exact match đang là `text` thay vì `keyword`, query vẫn có thể cho kết quả không đúng kỳ vọng hoặc buộc dùng subfield khác.

### Tip 3 — Với Azure Functions, thiết kế poison-message path ngay từ đầu

**Mẹo:**
Khi Function xử lý Service Bus/queue message, định nghĩa rõ điều gì xảy ra sau nhiều lần retry thất bại: dead-letter, alert, lưu diagnostic context và quy trình replay.

**Tại sao hữu ích:**
Một message lỗi vĩnh viễn có thể bị retry liên tục, tiêu tốn throughput và che backlog thật. Poison-message path tách transient fault khỏi dữ liệu hoặc business state không thể xử lý tự động.

**Ví dụ:**
```text
Message: ImportCustomer
DeliveryCount tăng liên tục

Flow hợp lý:
1. transient failure -> retry có backoff
2. vượt ngưỡng -> Dead Letter Queue
3. log MessageId + CorrelationId + reason
4. alert nếu DLQ tăng
5. sửa nguyên nhân rồi replay có kiểm soát
```

**Lưu ý:**
Không replay hàng loạt DLQ ngay sau khi deploy fix mà không kiểm tra idempotency. Một số message có thể đã tạo side effect một phần ở lần xử lý trước.

### Tip 4 — Dùng browser Performance panel để phân biệt network bottleneck với main-thread bottleneck

**Mẹo:**
Khi Vue/React page “chậm”, kiểm tra cả Network waterfall và Performance trace để biết thời gian nằm ở backend/network, parse JavaScript, layout, rendering hay long task trên main thread.

**Tại sao hữu ích:**
Một page có TTFB thấp nhưng vẫn lag vì JavaScript bundle lớn hoặc component rerender quá nhiều. Ngược lại, tối ưu frontend không giúp nếu 70% latency nằm ở API chậm.

**Ví dụ:**
```text
Case A:
TTFB 1.2s, JS execution 120ms
=> ưu tiên backend/network

Case B:
TTFB 150ms, JS execution 1.8s, nhiều long task >50ms
=> điều tra bundle, rendering, synchronous work
```

**Lưu ý:**
Đừng profile chỉ trên máy developer mạnh. Throttle CPU/network và nếu có thể dùng Real User Monitoring để xem behavior trên thiết bị thật.

### Tip 5 — Khi dùng AI coding agent review PR, yêu cầu nó chứng minh claim bằng file và dòng code

**Mẹo:**
Khi giao AI review repository hoặc pull request, yêu cầu mỗi finding quan trọng phải chỉ ra file, đoạn code liên quan, failure scenario và bằng chứng test/log nếu có.

**Tại sao hữu ích:**
AI dễ đưa ra nhận xét nghe hợp lý nhưng dựa trên assumption không tồn tại trong codebase. Evidence grounding giúp phân biệt bug thật với style preference hoặc hallucinated architecture concern.

**Ví dụ:**
```text
Finding tốt:
- src/Orders/OrderService.cs:112
- cancellation token không truyền vào SaveChangesAsync
- request bị client hủy nhưng DB operation vẫn tiếp tục
- đề xuất test integration mô phỏng cancelled request

Finding yếu:
- "Có thể có race condition" nhưng không chỉ ra state nào bị race
```

**Lưu ý:**
AI review không thay thế compiler, test suite, static analysis hay reviewer hiểu domain. Đặc biệt với security, transaction và concurrency, luôn xác minh claim trên source và runtime behavior.

## 🧠 Software Design

### Design 1 — Cache invalidation bằng versioned key khi dữ liệu có nhiều projection phụ thuộc

**Khái niệm:**
Thay vì cố xóa mọi cache key phụ thuộc khi dữ liệu thay đổi, một chiến lược là gắn version vào namespace/key và tăng version khi source state đổi đáng kể.

**Vấn đề nó giải quyết:**
Một product có thể xuất hiện trong product detail, category page, search suggestion và recommendation cache. Xóa chính xác toàn bộ key phụ thuộc dễ bỏ sót và gây stale data.

**Ví dụ thực tế:**
```text
Tenant catalog version = 42

cache key:
catalog:42:category:keyboard:page:1
catalog:42:product:123

Khi publish batch catalog mới:
version -> 43
=> request mới tự dùng namespace mới
=> key version 42 hết hạn theo TTL
```

**Trade-off:**
Versioned key đơn giản hóa invalidation và tránh scan/delete hàng loạt, nhưng tạm thời giữ cache cũ tới khi TTL hết và có thể gây cold-cache spike sau version bump.

**Middle → Senior insight:**
Middle developer cần hiểu cache key phải phản ánh dependency/freshness semantics. Senior / Technical developer phải chọn giữa targeted invalidation, versioned namespace và event-driven invalidation dựa trên fan-out, stale tolerance, memory cost và peak reload traffic.

### Design 2 — Generic framework nội bộ vs business-specific implementation

**Khái niệm:**
Một abstraction dùng chung chỉ đáng tạo khi nhiều use case thật sự có invariant và lifecycle giống nhau. Nếu mỗi feature phải truyền hàng chục hook/config option, framework có thể đang che business differences thay vì tạo reuse.

**Vấn đề nó giải quyết:**
Team thường thấy hai workflow giống nhau rồi tạo “generic engine”. Sau vài tháng, mỗi business case thêm exception riêng và abstraction trở thành nơi khó hiểu nhất hệ thống.

**Ví dụ thực tế:**
```text
Ban đầu:
- Approval flow cho Expense
- Approval flow cho Leave

Sau đó:
Expense cần budget check + finance escalation
Leave cần calendar conflict + manager delegation

Nếu engine phải có 20 extension points,
hai implementation riêng với shared primitives có thể rõ hơn.
```

**Trade-off:**
Generic framework giảm duplication khi behavior thật sự ổn định, nhưng tăng indirection, testing matrix và migration cost. Business-specific code có thể duplicate một ít nhưng thường dễ đọc và thay đổi cục bộ hơn.

**Middle → Senior insight:**
Middle developer cần tránh DRY máy móc trên code trông giống nhau. Senior / Technical developer phải đánh giá rate of change, semantic similarity và cost of wrong abstraction trước khi chuẩn hóa thành framework dùng chung.

### Design 3 — SLO-based scaling: scale theo bottleneck và latency objective, không chỉ CPU

**Khái niệm:**
Horizontal scaling nên dựa trên tín hiệu phản ánh khả năng phục vụ workload như latency, queue depth, request concurrency hoặc saturation của dependency, thay vì chỉ nhìn CPU utilization.

**Vấn đề nó giải quyết:**
Một API I/O-bound có thể CPU chỉ 30% nhưng connection pool đã đầy và p99 tăng mạnh. Ngược lại, scale thêm app instance không giúp nếu bottleneck nằm ở một SQL database đang saturated.

**Ví dụ thực tế:**
```text
Symptom:
p99 API = 2.8s
CPU App Service = 35%
DB connection pool wait tăng
SQL CPU = 92%

Scale app 2 -> 6 instance:
=> nhiều connection hơn đổ xuống DB
=> tình hình có thể tệ hơn
```

Thiết kế capacity phải đi từ symptom -> evidence -> bottleneck -> scaling decision.

**Trade-off:**
SLO-based scaling giúp tránh scale sai tầng và kiểm soát cost tốt hơn, nhưng yêu cầu telemetry đủ chất lượng và hiểu dependency chain. Rule phức tạp quá cũng có thể tạo oscillation hoặc overreaction.

**Middle → Senior insight:**
Middle developer cần biết đọc CPU, memory, latency, connection pool và queue metrics cùng nhau. Senior / Technical developer phải xác định saturation signal, headroom, autoscaling policy và dependency capacity để scaling không chỉ chuyển bottleneck sang tầng khác.
