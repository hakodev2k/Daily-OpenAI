# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwaitOptions.SuppressThrowing` chỉ khi thật sự muốn quan sát task mà không propagate exception

**Mẹo:**
Trong một số infrastructure path đặc biệt, bạn có thể await một `Task` với `ConfigureAwaitOptions.SuppressThrowing` để task được quan sát mà exception không bị throw tại điểm await.

**Tại sao hữu ích:**
Phù hợp với cleanup hoặc telemetry path nơi lỗi đã được xử lý ở nơi khác và bạn chỉ cần chắc chắn task hoàn tất, tránh tạo thêm `try/catch` boilerplate.

**Ví dụ:**
```csharp
await backgroundCleanupTask.ConfigureAwait(
    ConfigureAwaitOptions.SuppressThrowing);
```

**Lưu ý:**
Không dùng để “nuốt lỗi” business logic. Nếu exception cần ảnh hưởng flow hoặc cần log/alert, hãy xử lý rõ ràng thay vì suppress.

### Tip 2 — Dùng `SET TRANSACTION ISOLATION LEVEL` có chủ đích khi điều tra blocking

**Mẹo:**
Khi query bị blocking hoặc đọc dữ liệu cạnh tranh với write, đừng mặc định tăng timeout. Kiểm tra isolation level hiện tại và chọn mức phù hợp với consistency requirement.

**Tại sao hữu ích:**
`READ COMMITTED`, snapshot-based isolation và mức cao hơn tạo behavior khác nhau về lock, stale read và phantom read. Chọn đúng isolation có thể giảm contention mà vẫn giữ invariant cần thiết.

**Ví dụ:**
SQL Server:

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

SELECT *
FROM Orders
WHERE Status = 'Pending';

COMMIT;
```

**Lưu ý:**
Snapshot isolation không miễn phí: nó dùng version store và có thể phát sinh update conflict. Phải đánh giá workload và database configuration trước khi áp dụng.

### Tip 3 — Dùng `git clean -ndx` trước khi xóa generated/untracked files

**Mẹo:**
Trước khi chạy `git clean`, luôn preview bằng `-n` để biết chính xác file nào sẽ bị xóa, đặc biệt khi muốn xóa cả ignored files.

**Tại sao hữu ích:**
Giúp dọn build artifacts, `bin/obj`, generated files hoặc cache mà không vô tình xóa file local quan trọng.

**Ví dụ:**
Preview:

```bash
git clean -ndx
```

Nếu chắc chắn:

```bash
git clean -fdx
```

**Lưu ý:**
`git clean` xóa file không được track và rất khó khôi phục. Không chạy `-fdx` khi chưa preview hoặc chưa hiểu rõ `.gitignore` của repository.

### Tip 4 — Dùng `HttpClient` handler lifetime phù hợp với DNS thay đổi

**Mẹo:**
Nếu backend gọi service có DNS thay đổi theo deployment/load balancer, cấu hình handler lifetime hoặc `PooledConnectionLifetime` thay vì giữ connection mãi.

**Tại sao hữu ích:**
Connection pool quá lâu có thể tiếp tục dùng IP cũ dù DNS đã đổi, gây lỗi sau failover hoặc rolling deployment.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient("catalog")
    .ConfigurePrimaryHttpMessageHandler(() =>
        new SocketsHttpHandler
        {
            PooledConnectionLifetime = TimeSpan.FromMinutes(5)
        });
```

**Lưu ý:**
Lifetime quá ngắn làm tăng TCP/TLS handshake và giảm connection reuse. Chọn giá trị theo TTL DNS và đặc tính hạ tầng thực tế.

### Tip 5 — Dùng deterministic seed cho test dữ liệu ngẫu nhiên

**Mẹo:**
Nếu test sinh random data, cố định seed và log seed khi fail để có thể tái hiện chính xác cùng dữ liệu.

**Tại sao hữu ích:**
Flaky test do randomness rất khó debug nếu mỗi lần chạy tạo case khác. Seed biến lỗi “ngẫu nhiên” thành lỗi reproducible.

**Ví dụ:**
```csharp
var seed = 123456;
var random = new Random(seed);

var quantity = random.Next(1, 1000);
```

Trong property-based testing, hãy log seed/counterexample khi failure xảy ra.

**Lưu ý:**
Đừng dùng seed cố định duy nhất cho mọi test mãi mãi nếu mục tiêu là khám phá nhiều input. Có thể rotate seed nhưng luôn ghi lại seed khi fail.

## 🧠 Software Design

### Design 1 — Cache Versioning để tránh invalidation phụ thuộc quá nhiều key

**Khái niệm:**
Cache Versioning gắn version vào key namespace, giúp invalidate một nhóm cache bằng cách tăng version thay vì tìm và xóa từng key riêng lẻ.

**Vấn đề nó giải quyết:**
Khi dữ liệu phụ thuộc nhiều cache entries, selective invalidation có thể phức tạp và dễ sót key cũ.

**Ví dụ thực tế:**
Thay vì key:

```text
product:123
product:124
```

dùng:

```text
catalog:v17:product:123
catalog:v17:product:124
```

Khi catalog thay đổi lớn, tăng `v17` → `v18`; key cũ tự hết hạn theo TTL.

**Trade-off:**
Đơn giản hóa invalidation và giảm coupling giữa writer với từng cache entry, nhưng tạm thời tạo duplicated cache data và cần quản lý TTL/garbage của version cũ.

**Middle → Senior insight:**
Middle developer nên hiểu invalidation không nhất thiết là `DEL` từng key. Senior developer cần cân nhắc version scope, TTL, memory amplification và khi nào versioning tốt hơn event-driven invalidation chi tiết.

### Design 2 — Single Writer Principle để giảm conflict trên state quan trọng

**Khái niệm:**
Single Writer Principle giới hạn một logical owner chịu trách nhiệm mutate một loại state, trong khi các thành phần khác gửi command hoặc đọc projection thay vì cùng ghi trực tiếp.

**Vấn đề nó giải quyết:**
Khi nhiều service/process cùng cập nhật một state machine, race condition và invariant violation tăng mạnh vì không có authority duy nhất cho transition.

**Ví dụ thực tế:**
Chỉ `OrderService` được phép đổi `OrderStatus`. Payment và Shipping không update bảng Order trực tiếp; chúng gửi event/command để Order xử lý transition hợp lệ.

**Trade-off:**
Giảm concurrency bug và làm ownership rõ, nhưng writer có thể thành bottleneck nếu thiết kế partitioning kém. Đôi khi cần shard writer theo aggregate key để scale.

**Middle → Senior insight:**
Middle developer nên nhận ra shared-write database là nguồn coupling mạnh. Senior developer phải chọn writer boundary theo invariant, throughput và partitioning strategy thay vì biến “single writer” thành một process duy nhất cho toàn hệ thống.

### Design 3 — Consumer Lag là một phần của consistency model

**Khái niệm:**
Trong event-driven system, độ trễ giữa lúc producer commit state và lúc consumer cập nhật projection/read model quyết định mức eventual consistency thực tế mà user quan sát.

**Vấn đề nó giải quyết:**
Team thường nói “eventually consistent” nhưng không định nghĩa eventual là 100 ms, 5 giây hay 10 phút. Khi lag tăng, user có thể thấy state mâu thuẫn hoặc workflow phụ bị trễ.

**Ví dụ thực tế:**
Order vừa được thanh toán nhưng dashboard billing chỉ cập nhật sau 30 giây vì consumer backlog. Nếu SLA của business yêu cầu dưới 2 giây, consumer lag phải được monitor và capacity phải được thiết kế theo đó.

**Trade-off:**
Async processing giúp decouple và scale tốt, nhưng freshness phụ thuộc queue lag, retry và consumer throughput. Tăng số consumer có thể giảm lag nhưng làm tăng downstream pressure hoặc ordering complexity.

**Middle → Senior insight:**
Middle developer nên biết đo queue depth và processing latency. Senior developer phải biến freshness thành SLO, thiết kế alert theo lag, capacity headroom, replay behavior và xác định use case nào không chấp nhận eventual consistency.
