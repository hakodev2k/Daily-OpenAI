# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Chuẩn hóa lỗi API bằng `ProblemDetails` thay vì trả JSON tùy ý

**Mẹo:**
Trong ASP.NET Core, với lỗi validation, not found, conflict hoặc business rule failure, ưu tiên trả response theo `ProblemDetails` / RFC 9457-compatible shape thay vì mỗi endpoint tự tạo một object lỗi khác nhau.

**Tại sao hữu ích:**
Client cần contract lỗi ổn định để xử lý retry, hiển thị message và phân biệt lỗi business với lỗi hệ thống. Khi mỗi controller trả một shape riêng, frontend/mobile phải viết nhiều nhánh parsing và rất dễ break khi API tiến hóa. `ProblemDetails` cũng giúp centralized exception handling map exception/domain result sang HTTP semantics rõ ràng.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();
```

Một conflict có thể trả:

```json
{
  "type": "https://example.com/problems/order-version-conflict",
  "title": "Order has been modified",
  "status": 409,
  "detail": "Reload the order before saving again."
}
```

**Lưu ý:**
Không đưa stack trace, SQL error hoặc secret vào `detail` ở production. Đồng thời đừng biến mọi domain error thành `500`; chọn status code theo HTTP semantics thực tế như `400`, `404`, `409`, `422` khi phù hợp.

### Tip 2 — Khi SQL Server deadlock, đọc deadlock graph thay vì chỉ tăng retry

**Mẹo:**
Nếu production xuất hiện deadlock, thu thập deadlock graph từ Extended Events hoặc monitoring rồi xác định resource, statement và lock order của các transaction tham gia trước khi chỉnh code.

**Tại sao hữu ích:**
Deadlock không chỉ có nghĩa “database bận”. Nó thường là vòng chờ do hai transaction giữ lock theo thứ tự khác nhau, transaction quá dài hoặc query scan nhiều row hơn dự kiến. Retry có thể giảm lỗi cho user nhưng không sửa nguyên nhân contention.

**Ví dụ:**
Giả sử transaction A:

```text
UPDATE Orders ...
UPDATE Inventory ...
```

Transaction B lại:

```text
UPDATE Inventory ...
UPDATE Orders ...
```

Hai luồng có thể khóa chéo nhau. Một fix bền vững là thống nhất lock order và rút ngắn transaction; index phù hợp cũng có thể giảm số row bị khóa.

**Lưu ý:**
Không bật `NOLOCK` hoặc hạ isolation level một cách máy móc để “hết deadlock”. Bạn có thể đổi deadlock thành dirty read hoặc inconsistency khó phát hiện hơn. Retry vẫn nên tồn tại cho lỗi transient nhưng phải có giới hạn và telemetry.

### Tip 3 — Với Azure Service Bus, tính `lock duration` theo thời gian xử lý thực tế

**Mẹo:**
Nếu consumer xử lý message lâu, theo dõi processing duration so với message lock và cấu hình auto lock renewal phù hợp. Nếu lock hết hạn trước khi `CompleteMessageAsync`, message có thể được giao lại dù business work đã chạy gần xong.

**Tại sao hữu ích:**
Azure Service Bus dùng peek-lock cho nhiều consumer scenario. Khi lock hết hạn, broker xem message chưa hoàn tất và có thể redeliver. Nếu handler tạo side effect không idempotent, duplicate delivery có thể tạo order, email hoặc payment lặp.

**Ví dụ:**
Một message xử lý file mất 4–6 phút nhưng lock ban đầu 1 phút. Consumer cần:

```text
processing p95: 5m20s
lock renewal budget: > p99 + safety margin
```

và side effect vẫn nên được bảo vệ bằng idempotency key hoặc Inbox/deduplication strategy.

**Lưu ý:**
Đừng chỉ tăng lock renewal lên hàng giờ. Processing dài bất thường có thể là dấu hiệu workflow nên được chia nhỏ hoặc chuyển sang orchestrated background process. Lock renewal không thay thế idempotency.

### Tip 4 — Chống SSRF khi backend nhận URL từ user hoặc third-party data

**Mẹo:**
Nếu application fetch URL do user, CMS editor hoặc external integration cung cấp, validate scheme/host và chặn private/internal address range thay vì gọi `HttpClient` trực tiếp với URL nhận được.

**Tại sao hữu ích:**
SSRF cho phép attacker biến server thành proxy để truy cập endpoint nội bộ như metadata service, admin API hoặc service chỉ mở trong private network. Đây là lỗi đặc biệt nguy hiểm ở cloud vì backend thường có network/identity privilege lớn hơn client.

**Ví dụ:**
Một image-import feature nhận:

```text
https://example.com/image.jpg
```

Backend nên chỉ cho phép `https`, resolve DNS an toàn, áp allowlist khi có thể và chặn IP như loopback, link-local, RFC1918/private ranges trước khi gửi request.

**Lưu ý:**
Chỉ regex hostname là chưa đủ vì DNS rebinding và redirect có thể đổi destination sau bước validation. Cần kiểm soát redirect và validate destination thực tế theo threat model.

### Tip 5 — Dùng `await using` khi resource có async cleanup thực sự

**Mẹo:**
Với type triển khai `IAsyncDisposable`, dùng `await using` để cleanup không chặn thread khi việc giải phóng cần I/O hoặc async flush.

**Tại sao hữu ích:**
Một số resource như async stream, database-related scope hoặc writer có thể cần flush/close bất đồng bộ. Gọi cleanup đồng bộ trong hot path có thể block thread hoặc bỏ qua bước hoàn tất async mà library yêu cầu.

**Ví dụ:**
```csharp
await using var stream = await blobClient.OpenWriteAsync(
    overwrite: true,
    cancellationToken: cancellationToken);

await source.CopyToAsync(stream, cancellationToken);
```

Khi scope kết thúc, `DisposeAsync` được await đúng cách.

**Lưu ý:**
Không tự động đổi mọi `using` thành `await using`. Chỉ áp dụng khi type thực sự hỗ trợ `IAsyncDisposable` và async cleanup mang lại ý nghĩa. Với resource thuần memory, async disposal chỉ làm code phức tạp hơn.

## 🧠 Software Design

### Design 1 — Modular Monolith cần ownership dữ liệu theo module, không chỉ chia folder

**Khái niệm:**
Modular Monolith giữ deployment chung nhưng chia hệ thống thành module có boundary rõ về domain, API nội bộ và dữ liệu. Một module không nên tùy ý query/update table của module khác chỉ vì cùng database.

**Vấn đề nó giải quyết:**
Nhiều codebase gọi mình là “modular” nhưng chỉ tách project/folder; business logic và database vẫn cross-reference tự do. Khi đó coupling thực tế vẫn cao và sau này gần như không thể tách capability hoặc thay đổi schema độc lập.

**Ví dụ thực tế:**
`Orders` sở hữu `Orders` và `OrderItems`; `Inventory` sở hữu stock state. Thay vì Orders trực tiếp update bảng Inventory, Orders gọi internal application contract hoặc publish domain/integration event theo consistency requirement.

**Trade-off:**
Module ownership cải thiện cohesion, testability và khả năng tiến hóa, nhưng thêm boundary code và đôi khi cần duplicate read model. Nếu hệ thống nhỏ và domain rất đơn giản, boundary quá cứng có thể tạo ceremony nhiều hơn giá trị.

**Middle → Senior insight:**
Middle developer cần tôn trọng dependency rule, không bypass module API để “query cho nhanh”. Senior / Technical developer phải quyết định boundary dựa trên domain ownership, transaction need, team ownership và khả năng tiến hóa; đồng thời biết khi nào local transaction xuyên vài table vẫn đơn giản hơn việc ép event-driven flow.

### Design 2 — Expand-and-Contract cho thay đổi API/database không downtime

**Khái niệm:**
Expand-and-Contract là chiến lược rollout thay đổi theo nhiều bước tương thích: đầu tiên mở rộng contract/schema để old và new code cùng chạy, sau đó migrate traffic/data, cuối cùng mới xóa phần cũ.

**Vấn đề nó giải quyết:**
Trong rolling deployment, nhiều version application có thể chạy đồng thời. Nếu release mới rename column, đổi field JSON hoặc xóa API ngay lập tức, instance cũ hoặc consumer chưa deploy có thể fail trong khoảng rollout.

**Ví dụ thực tế:**
Cần đổi `CustomerName` thành `DisplayName`:

1. Thêm `DisplayName` nhưng vẫn giữ `CustomerName`.
2. New code đọc field mới, có fallback field cũ.
3. Backfill dữ liệu.
4. Update producer/consumer.
5. Sau khi telemetry xác nhận field cũ không còn dùng, mới remove.

**Trade-off:**
Chiến lược này giảm downtime và breaking change, nhưng tạo giai đoạn schema/contract dư thừa, migration logic và cleanup bắt buộc. Với internal tool nhỏ deploy atomic, quy trình nhiều bước có thể không cần thiết.

**Middle → Senior insight:**
Middle developer cần viết code backward-compatible trong thời gian transition. Senior / Technical developer phải thiết kế migration sequence, compatibility window, rollback path và telemetry chứng minh safe removal thay vì chỉ tập trung vào final schema đẹp nhất.

### Design 3 — Build vs Buy phải tính cả operational ownership, không chỉ feature checklist

**Khái niệm:**
Quyết định tự xây hay dùng managed/product service cần so sánh total cost of ownership: engineering effort, reliability, compliance, scaling, observability, upgrade và khả năng thoát khỏi vendor — không chỉ license cost.

**Vấn đề nó giải quyết:**
Team thường đánh giá “build” dựa trên MVP vài tuần nhưng bỏ qua nhiều năm vận hành. Ngược lại, “buy” có thể rút ngắn time-to-market nhưng tạo vendor lock-in, giới hạn customization hoặc chi phí tăng mạnh theo scale.

**Ví dụ thực tế:**
Một e-commerce platform cần full-text search. Tự xây search engine là lựa chọn tệ; nhưng giữa managed Elasticsearch/OpenSearch-like service và một SaaS search product, team phải đánh giá relevance tuning, ingestion pipeline, SLA, data residency, cost per query và khả năng export index/configuration.

**Trade-off:**
Buy giảm thời gian xây nền tảng và chuyển một phần operational burden cho vendor; đổi lại là recurring cost, dependency và constraint theo product. Build cho control cao hơn nhưng yêu cầu đội ngũ sở hữu reliability, security, scaling và upgrades lâu dài.

**Middle → Senior insight:**
Middle developer cần hiểu integration boundary và tránh couple domain quá chặt với vendor SDK. Senior / Technical developer phải lượng hóa TCO, exit cost, strategic differentiation và operational maturity; chỉ nên build phần tạo lợi thế riêng, không tái tạo commodity infrastructure nếu không có lý do mạnh.
