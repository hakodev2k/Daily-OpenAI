# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `git worktree` khi cần làm song song nhiều branch

**Mẹo:**
Thay vì liên tục `stash`, `checkout` và rebuild khi chuyển task, dùng `git worktree` để mở nhiều working directory cùng trỏ tới một repository nhưng ở các branch khác nhau.

**Tại sao hữu ích:**
Rất tiện khi vừa sửa production bug, vừa review PR hoặc để AI coding agent làm ở branch riêng mà không phá trạng thái working tree hiện tại.

**Ví dụ:**
```bash
git worktree add ../myapp-hotfix hotfix/payment-timeout
git worktree add ../myapp-feature feature/new-report
```

Xem danh sách:

```bash
git worktree list
```

Xóa worktree khi xong:

```bash
git worktree remove ../myapp-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree. Đừng xóa folder thủ công nếu Git vẫn đang quản lý worktree; dùng `git worktree remove` hoặc `git worktree prune`.

### Tip 2 — Giới hạn concurrency thay vì `Task.WhenAll` trên hàng nghìn item

**Mẹo:**
Khi xử lý batch lớn, tránh tạo hàng nghìn network/database tasks cùng lúc. Dùng bounded concurrency như `Parallel.ForEachAsync`, `SemaphoreSlim` hoặc `Channel<T>`.

**Tại sao hữu ích:**
Giảm nguy cơ socket exhaustion, connection-pool saturation, rate-limit errors và memory spike trong background jobs.

**Ví dụ:**
```csharp
await Parallel.ForEachAsync(
    userIds,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 8,
        CancellationToken = cancellationToken
    },
    async (userId, ct) =>
    {
        await syncService.SyncUserAsync(userId, ct);
    });
```

**Lưu ý:**
`MaxDegreeOfParallelism` không có một giá trị đúng cho mọi workload. Hãy chọn theo giới hạn của downstream dependency, connection pool, CPU và rate limit thực tế.

### Tip 3 — Stream HTTP response lớn với `ResponseHeadersRead`

**Mẹo:**
Khi tải file hoặc response lớn, dùng `HttpCompletionOption.ResponseHeadersRead` để `HttpClient` trả về ngay sau khi nhận headers thay vì buffer toàn bộ body trước.

**Tại sao hữu ích:**
Giảm memory usage và latency trước khi bắt đầu xử lý dữ liệu, đặc biệt với export file, blob hoặc streaming API.

**Ví dụ:**
```csharp
using var response = await httpClient.GetAsync(
    url,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);

response.EnsureSuccessStatusCode();

await using var stream = await response.Content
    .ReadAsStreamAsync(cancellationToken);

await stream.CopyToAsync(destinationStream, cancellationToken);
```

**Lưu ý:**
Khi stream response, bạn phải dispose `HttpResponseMessage` đúng cách. Nếu giữ response/stream quá lâu, connection có thể không được trả sớm về pool.

### Tip 4 — Dùng `pg_stat_statements` để tìm SQL chậm theo tổng chi phí, không chỉ query đơn lẻ

**Mẹo:**
Trong PostgreSQL production, `pg_stat_statements` giúp xem query nào tiêu tốn nhiều tổng thời gian nhất, gọi nhiều nhất hoặc có latency trung bình cao.

**Tại sao hữu ích:**
Một query 20 ms nhưng chạy 5 triệu lần có thể gây tải lớn hơn một query 2 giây chỉ chạy vài lần. Chỉ nhìn slow-query log dễ bỏ sót loại bottleneck này.

**Ví dụ:**
```sql
SELECT
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

**Lưu ý:**
Extension cần được enable/configure phù hợp trên server. Query text cũng có thể chứa thông tin nhạy cảm tùy cách application phát sinh SQL, nên cần kiểm soát quyền truy cập monitoring data.

### Tip 5 — Redact secrets ngay tại logging boundary

**Mẹo:**
Thiết kế logging sao cho token, password, cookie, API key và PII bị loại bỏ trước khi log event được gửi tới sink, thay vì trông chờ developer nhớ không log chúng.

**Tại sao hữu ích:**
Một log line vô tình ghi `Authorization` header có thể bị replicate sang nhiều hệ thống: console, Application Insights, Elasticsearch, backup và ticket debug.

**Ví dụ:**
Thay vì log toàn bộ request headers:

```csharp
_logger.LogInformation("Headers: {@Headers}", request.Headers);
```

hãy chỉ log allow-list cần thiết:

```csharp
_logger.LogInformation(
    "Request {Method} {Path} CorrelationId={CorrelationId}",
    request.Method,
    request.Path,
    correlationId);
```

**Lưu ý:**
Mask kiểu `abcd****` vẫn có thể làm lộ dữ liệu nếu phần giữ lại mang tính nhận dạng. Với secret thực sự, ưu tiên loại bỏ hoàn toàn thay vì chỉ che một phần.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency cho dữ liệu có nhiều người cùng sửa

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng một record nhưng chỉ cho update thành công nếu version của record vẫn giống lúc client đọc nó.

**Vấn đề nó giải quyết:**
Nếu hai người cùng mở một Employee/Profile rồi cùng save, request đến sau có thể âm thầm ghi đè thay đổi của request đến trước — một lost update mà transaction thông thường không tự ngăn được.

**Ví dụ thực tế:**
Entity có `RowVersion`:

```csharp
public byte[] RowVersion { get; set; } = default!;
```

Client A đọc version `10`, Client B cũng đọc version `10`. B save trước làm version thành `11`. Khi A save với version `10`, persistence layer phát hiện conflict và yêu cầu reload/merge thay vì overwrite dữ liệu mới.

**Trade-off:**
Lợi ích là không cần giữ database lock suốt thời gian người dùng chỉnh sửa và scale tốt cho workload ít conflict. Chi phí là application phải xử lý conflict UX, retry hoặc merge; nếu contention rất cao, retry liên tục có thể trở nên đắt.

**Middle → Senior insight:**
Middle developer nên biết dùng concurrency token và xử lý conflict thay vì catch rồi retry mù quáng. Senior developer cần quyết định field nào có thể merge tự động, operation nào phải fail, khi nào dùng ETag/version ở API boundary và khi nào pessimistic locking phù hợp hơn.

### Design 2 — Dead-Letter Queue không phải nơi “ném lỗi rồi quên”

**Khái niệm:**
Dead-Letter Queue (DLQ) chứa message không thể xử lý thành công sau policy retry đã định nghĩa, giúp tách poison message khỏi luồng xử lý bình thường.

**Vấn đề nó giải quyết:**
Một message malformed hoặc vi phạm business rule có thể bị retry vô hạn, chiếm consumer capacity và làm queue backlog tăng liên tục.

**Ví dụ thực tế:**
Consumer nhận `InvoiceCreated`. Nếu RabbitMQ message thiếu `CustomerId`, retry 50 lần sẽ không giúp gì. Sau vài retry có backoff, message được chuyển sang DLQ cùng metadata như exception type, retry count và original message id để điều tra hoặc replay.

**Trade-off:**
DLQ bảo vệ throughput và cô lập poison message, nhưng tạo thêm operational workflow: alert, triage, retention, replay và tránh duplicate side effects khi đưa message trở lại queue.

**Middle → Senior insight:**
Middle developer cần phân biệt transient failure và permanent failure. Senior developer phải thiết kế retry budget, DLQ schema, alert threshold, replay tooling, idempotency và ownership rõ ràng: ai chịu trách nhiệm khi DLQ bắt đầu tăng.

### Design 3 — Feature Flag cần lifecycle, không chỉ là `if` trong code

**Khái niệm:**
Feature Flag tách thời điểm deploy code khỏi thời điểm bật behavior cho user, tenant hoặc traffic segment. Nhưng flag phải được quản lý như một phần của kiến trúc vận hành.

**Vấn đề nó giải quyết:**
Release lớn thường cần rollout dần, canary test hoặc khả năng tắt nhanh tính năng lỗi mà không redeploy toàn bộ application.

**Ví dụ thực tế:**
Backend deploy logic tính phí mới nhưng chỉ bật cho 5% tenant. Nếu metrics ổn, tăng lên 25%, 50%, rồi 100%. Nếu error rate tăng, tắt flag trong vài giây thay vì rollback deployment.

**Trade-off:**
Feature flag giảm release risk và hỗ trợ progressive delivery, nhưng mỗi flag tạo thêm execution path, test matrix và cognitive load. Flag tồn tại quá lâu trở thành technical debt và có thể gây behavior khó dự đoán.

**Middle → Senior insight:**
Middle developer nên biết kiểm thử cả trạng thái on/off và tránh rải flag logic khắp codebase. Senior developer cần thiết kế owner, expiry date, telemetry, cleanup policy và phân biệt release flag ngắn hạn với permission/configuration lâu dài.
