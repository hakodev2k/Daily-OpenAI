# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — Inject `TimeProvider` thay vì gọi `DateTime.UtcNow` trực tiếp trong business logic

**Mẹo:**
Với code có logic phụ thuộc thời gian như token expiry, retry window, scheduled action hoặc business cutoff, inject `TimeProvider` thay vì đọc `DateTime.UtcNow` rải rác trong domain/application code.

**Tại sao hữu ích:**
Thời gian là một external dependency. Gọi trực tiếp clock thật làm test phải phụ thuộc vào timing thực tế, dễ flaky và khó kiểm thử edge case như “vừa hết hạn”, “qua midnight” hoặc “sau 30 phút”. `TimeProvider` cho phép production dùng clock thật nhưng test điều khiển thời gian một cách deterministic.

**Ví dụ:**
```csharp
public sealed class TokenExpiryService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

Trong test có thể dùng fake/test `TimeProvider` để advance clock mà không cần `Task.Delay` hoặc chỉnh system time.

**Lưu ý:**
Không cần abstract thời gian ở mọi nơi. Nếu timestamp chỉ phục vụ logging/telemetry, abstraction riêng có thể là overhead. Nhưng với logic business có branch dựa trên thời gian, testability và determinism thường đáng giá.

### Tip 2 — Dùng `ResponseHeadersRead` khi gọi API trả payload lớn để tránh buffer toàn bộ response

**Mẹo:**
Khi `HttpClient` tải file, export hoặc JSON payload rất lớn mà application có thể xử lý theo stream, dùng `HttpCompletionOption.ResponseHeadersRead` để bắt đầu xử lý sau khi nhận headers thay vì chờ toàn bộ body được buffer trước.

**Tại sao hữu ích:**
Mặc định, một số flow HTTP có thể buffer response body trước khi trả control về caller. Với payload lớn, điều này làm tăng memory usage và time-to-first-processing. Streaming giúp giảm working set và cho phép pipeline xử lý dữ liệu sớm hơn.

**Ví dụ:**
```csharp
using var response = await httpClient.GetAsync(
    requestUri,
    HttpCompletionOption.ResponseHeadersRead,
    ct);

response.EnsureSuccessStatusCode();

await using var stream = await response.Content.ReadAsStreamAsync(ct);
await ProcessLargePayloadAsync(stream, ct);
```

Phù hợp với download file, media, large export hoặc parser có thể consume stream incrementally.

**Lưu ý:**
Khi streaming, connection thường bị giữ cho tới khi body được đọc xong hoặc response bị dispose. Client chậm hoặc parser chậm có thể giữ socket lâu. Cần timeout, cancellation và giới hạn payload rõ ràng; streaming không tự bảo vệ khỏi response quá lớn hoặc malicious payload.

### Tip 3 — Với MongoDB compound index, sắp field theo query pattern chứ không theo thứ tự model

**Mẹo:**
Khi thiết kế compound index cho MongoDB, bắt đầu từ access pattern. Một heuristic hữu ích là ưu tiên Equality trước, sau đó Sort và Range khi phù hợp, thay vì tạo index theo thứ tự field trong document hoặc DTO.

**Tại sao hữu ích:**
Index `{ tenantId: 1, status: 1, createdAt: -1 }` có thể phục vụ tốt query lọc chính xác `tenantId` + `status` rồi sort theo `createdAt`. Nếu đặt range field quá sớm, các field phía sau có thể không còn được dùng hiệu quả để thu hẹp scan hoặc hỗ trợ sort.

**Ví dụ:**
```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})
```

Query:
```javascript
db.orders.find({
  tenantId: "t-42",
  status: "Pending"
}).sort({ createdAt: -1 }).limit(50)
```

Kiểm tra bằng `explain("executionStats")` để xem số document/key được scan thay vì chỉ nhìn index có tồn tại hay không.

**Lưu ý:**
Equality-Sort-Range là heuristic, không phải luật tuyệt đối. Data cardinality, selectivity, sort direction, query coverage và workload write đều ảnh hưởng. Mỗi index làm tăng storage và write amplification, nên tránh tạo một index riêng cho mọi biến thể filter.

### Tip 4 — Dùng `git bisect run` để tự động tìm commit gây regression

**Mẹo:**
Nếu biết một commit cũ còn tốt và một commit mới bị lỗi, dùng `git bisect` kết hợp một test/script trả exit code pass/fail để Git tự tìm commit đầu tiên gây regression bằng binary search.

**Tại sao hữu ích:**
Với hàng trăm commit giữa hai mốc, checkout thủ công từng commit rất tốn thời gian. `git bisect` chỉ cần khoảng `log2(N)` bước; `git bisect run` còn tự động hóa toàn bộ nếu lỗi có thể tái hiện bằng test hoặc command ổn định.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

git bisect run dotnet test tests/Regression.Tests \
  --filter FullyQualifiedName~CheckoutLatencyRegression

git bisect reset
```

Script/test phải trả `0` khi good và non-zero khi bad.

**Lưu ý:**
Bisect chỉ đáng tin nếu reproduction deterministic. Flaky test, environment drift hoặc migration incompatible giữa các commit có thể dẫn Git tới commit sai. Với commit không build được, có thể cần script xử lý và trả mã skip phù hợp.

### Tip 5 — Phân biệt `Cache-Control: no-cache` và `no-store` để tránh vô tình tắt caching

**Mẹo:**
Khi thiết kế HTTP caching, nhớ rằng `no-cache` không có nghĩa “không được cache”; nó cho phép cache lưu response nhưng phải revalidate trước khi reuse. `no-store` mới yêu cầu không lưu response vào cache.

**Tại sao hữu ích:**
Nhầm hai directive này có thể làm mất toàn bộ lợi ích của conditional request. Với tài nguyên thay đổi nhưng có `ETag`, `no-cache` vẫn cho browser/CDN revalidate và nhận `304 Not Modified`, giảm bandwidth trong khi vẫn đảm bảo freshness.

**Ví dụ:**
```http
Cache-Control: no-cache
ETag: "catalog-v42"
```

Request sau:
```http
If-None-Match: "catalog-v42"
```

Nếu tài nguyên chưa đổi, server có thể trả `304` mà không gửi lại body.

**Lưu ý:**
Với dữ liệu nhạy cảm như account statement hoặc token-related response, `no-store` có thể đúng hơn. Không đặt cache policy chỉ dựa trên performance; phải xét privacy, shared cache behavior, authentication và mức freshness business thực sự cần.

## 🧠 Software Design

### Design 1 — Outbox Pattern giữ database change và event publication trong cùng một transaction boundary

**Khái niệm:**
Outbox Pattern ghi business state và một outbox record vào cùng transaction database. Một publisher riêng sau đó đọc outbox và gửi event/message ra broker. Mục tiêu không phải “gửi message exactly once”, mà là tránh khoảng trống giữa commit dữ liệu và publish integration event.

**Vấn đề nó giải quyết:**
Nếu code update `Order` thành `Paid` rồi gọi Azure Service Bus, process có thể crash sau database commit nhưng trước khi message được publish. Nếu đảo thứ tự, message có thể được gửi nhưng transaction database lại rollback. Cả hai đều tạo inconsistency giữa local state và downstream systems.

**Ví dụ thực tế:**
```text
Database transaction:
1. UPDATE Orders SET Status = 'Paid'
2. INSERT Outbox(Id, Type, Payload, CreatedAt)
3. COMMIT

Publisher:
4. đọc Outbox chưa gửi
5. publish OrderPaid
6. đánh dấu processed
```

Consumer vẫn phải idempotent vì publisher có thể gửi lại message nếu crash sau publish nhưng trước khi đánh dấu processed.

**Trade-off:**
Outbox cải thiện reliability nhưng thêm table/storage, polling hoặc CDC publisher, cleanup, monitoring và duplicate-delivery semantics. Nếu use case chỉ nằm trong một process/database và không cần external event, thêm Outbox có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu transaction local không bao phủ message broker và phải xử lý duplicate publication/consumption. Senior / Technical developer phải xác định transaction boundary, ordering requirement, publisher strategy, retention, backpressure và liệu consistency requirement có thực sự cần asynchronous integration hay không.

### Design 2 — Bulkhead Isolation ngăn một dependency hoặc workload chiếm hết tài nguyên của service

**Khái niệm:**
Bulkhead Isolation chia capacity thành các vùng độc lập để một workload lỗi/chậm không tiêu hết thread, connection, concurrency slot hoặc queue capacity của workload khác. Ý tưởng giống khoang kín trên tàu: một khoang ngập không làm cả hệ thống chìm ngay.

**Vấn đề nó giải quyết:**
Một API phục vụ cả checkout và report export. Khi report downstream chậm, hàng trăm export request có thể giữ toàn bộ outbound connection hoặc worker concurrency, khiến checkout cũng timeout dù dependency của checkout hoàn toàn khỏe mạnh.

**Ví dụ thực tế:**
```text
Checkout outbound concurrency: 80 slots
Report export concurrency:      10 slots
Background enrichment:          20 slots
```

Mỗi workload có queue/limit riêng; khi export bị nghẽn, hệ thống reject hoặc queue export thay vì làm checkout mất capacity.

**Trade-off:**
Bulkhead giảm blast radius nhưng có thể làm capacity bị “nhàn rỗi” ở partition này trong khi partition khác đang quá tải. Quá nhiều partition cũng làm configuration và monitoring phức tạp. Đôi khi autoscaling hoặc queue riêng là giải pháp rõ hơn concurrency limiter trong cùng process.

**Middle → Senior insight:**
Middle developer cần nhận ra resource pool dùng chung là một coupling runtime. Senior / Solution-oriented engineer phải phân loại workload theo criticality, SLO và resource consumption, rồi quyết định isolation ở level process, queue, connection pool, pod/deployment hay thậm chí service boundary.

### Design 3 — Optimistic Concurrency với ETag phù hợp khi nhiều client có thể sửa cùng một resource

**Khái niệm:**
ETag kết hợp `If-Match` cho phép API chỉ chấp nhận update nếu resource vẫn ở version mà client đã đọc. Đây là optimistic concurrency: không khóa resource trong suốt thời gian user chỉnh sửa, nhưng phát hiện lost update tại thời điểm ghi.

**Vấn đề nó giải quyết:**
User A và User B cùng mở hồ sơ khách hàng ở version 7. A đổi email và lưu thành version 8. B vẫn đang giữ version 7 rồi sửa địa chỉ. Nếu API update không kiểm tra version, request của B có thể ghi đè thay đổi của A mà không ai biết.

**Ví dụ thực tế:**
```http
GET /customers/42
ETag: "7"

PUT /customers/42
If-Match: "7"
```

Nếu resource hiện đã là version 8, API trả `412 Precondition Failed` thay vì silently overwrite.

**Trade-off:**
Optimistic concurrency tránh lock dài và scale tốt cho conflict rate thấp, nhưng client phải xử lý conflict UX/retry/merge. Với workload conflict rất cao hoặc invariant cần serialization chặt, pessimistic locking hoặc command-specific transaction có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần propagate version/ETag và xử lý `412` đúng semantics. Senior / Technical developer phải quyết định conflict granularity, merge strategy, version source, API contract và phân biệt retry an toàn với việc tự động overwrite một conflict business thực sự.
