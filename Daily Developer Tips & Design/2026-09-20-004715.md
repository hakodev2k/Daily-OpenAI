# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `ArrayPool<T>` chỉ đáng dùng khi allocation profile chứng minh buffer là hot path

**Mẹo:**
Với code xử lý buffer tạm có tần suất cao, cân nhắc `ArrayPool<T>.Shared` để tái sử dụng array thay vì cấp phát mới liên tục. Hãy bắt đầu từ allocation profile, không từ giả định rằng pooling luôn nhanh hơn.

**Tại sao hữu ích:**
Buffer lớn hoặc được tạo với tần suất cao có thể làm allocation rate và GC pressure tăng. Pooling giảm số allocation, nhưng đổi lại application phải quản lý lifetime và tránh giữ reference ngoài thời gian thuê buffer.

**Ví dụ:**
Một serializer nội bộ tạo `byte[]` vài chục KB hàng nghìn lần mỗi giây. Profiler cho thấy phần lớn allocation đến từ buffer này; benchmark phiên bản dùng `ArrayPool<byte>` để xác nhận throughput và GC pause có thực sự cải thiện.

**Lưu ý:**
Luôn `Return` buffer trong `finally` khi phù hợp và không đọc dữ liệu ngoài vùng đã ghi. Với dữ liệu nhạy cảm, cân nhắc clear buffer trước khi trả pool. Đừng dùng pooling cho object nhỏ, ít allocation nếu complexity lớn hơn lợi ích.

### Tip 2 — HTTP conditional request có thể giảm payload bằng `ETag` thay vì cache mù

**Mẹo:**
Với resource đọc nhiều nhưng vẫn cần kiểm tra freshness, cân nhắc trả `ETag` và xử lý `If-None-Match` để client/CDN revalidate mà không tải lại toàn bộ representation khi dữ liệu chưa đổi.

**Tại sao hữu ích:**
Conditional request vẫn kiểm tra server state nhưng có thể trả `304 Not Modified`, giảm bandwidth và serialization cost. Nó hữu ích khi TTL dài không phù hợp nhưng payload tương đối lớn hoặc client refresh thường xuyên.

**Ví dụ:**
Product detail API tạo ETag từ version ổn định của product. Client gửi lại `If-None-Match`; nếu version không đổi, API trả `304` thay vì serialize JSON đầy đủ.

**Lưu ý:**
ETag phải phản ánh representation thực tế, bao gồm variation theo language/tenant nếu có. Không tạo hash đắt hơn chính việc sinh response, và đừng nhầm conditional caching với optimistic concurrency cho write nếu semantics khác nhau.

### Tip 3 — Redis outage phải được thiết kế như capacity event của database

**Mẹo:**
Khi Redis cache unavailable, đừng mặc định cho mọi request fallback thẳng xuống database. Xác định database có chịu nổi cache-miss traffic hay cần concurrency limit, stale fallback hoặc load shedding.

**Tại sao hữu ích:**
Cache thường hấp thụ phần lớn read traffic. Nếu cache hit ratio từ 95% về 0%, source database có thể nhận tải tăng hàng chục lần; fallback tưởng là tăng availability lại gây cascading failure.

**Ví dụ:**
Product API phát hiện Redis timeout. Thay vì hàng nghìn request cùng query SQL, service giới hạn concurrent fallback, ưu tiên dữ liệu quan trọng và emit metric về cache availability, database saturation và rejected requests.

**Lưu ý:**
Không retry Redis liên tục trên request path khi cache đang lỗi vì có thể cộng thêm latency. Degradation policy phải dựa trên freshness requirement và capacity thực tế của source of truth.

### Tip 4 — Dùng `git bisect` khi regression có khoảng commit đủ lớn

**Mẹo:**
Khi biết một commit cũ là good và HEAD là bad, dùng `git bisect` để tìm commit gây regression theo binary search thay vì đọc tuần tự hàng chục commit.

**Tại sao hữu ích:**
Với khoảng 128 commits, binary search chỉ cần khoảng 7 lần phân loại good/bad nếu test đủ deterministic. Đây là cách biến điều tra history thành quá trình có bằng chứng thay vì đoán từ commit message.

**Ví dụ:**
Một API bắt đầu trả sai rounding nhưng không rõ từ release nào. Đánh dấu tag production cũ là good, HEAD là bad, rồi chạy regression test tại từng commit mà Git chọn cho đến khi xác định candidate đầu tiên.

**Lưu ý:**
`git bisect` kém hiệu quả nếu mỗi commit không build được hoặc test flaky. Có thể cần script setup/test ổn định trước; commit được tìm thấy là điểm bắt đầu root-cause analysis, không tự động chứng minh mọi dòng trong commit đều sai.

### Tip 5 — Production alert nên gắn với user impact, không chỉ exception count

**Mẹo:**
Khi thiết kế alert trong Azure Monitor/Application Insights, ưu tiên signal như error rate, latency, saturation hoặc failed business operation thay vì cảnh báo mỗi exception đơn lẻ.

**Tại sao hữu ích:**
Một exception được handle đúng có thể không ảnh hưởng user, trong khi latency tăng hoặc queue backlog có thể gây incident lớn mà exception count vẫn thấp. Alert theo impact giảm noise và giúp on-call tập trung vào degradation thực.

**Ví dụ:**
Thay vì alert khi có bất kỳ `HttpRequestException`, cảnh báo khi checkout failure rate vượt ngưỡng trong một cửa sổ đủ lớn, sau đó dùng dependency telemetry/traces để xác định downstream nào đóng góp vào failure.

**Lưu ý:**
Đừng bỏ diagnostic exceptions khỏi telemetry chỉ vì không alert trên chúng. Alerting và observability phục vụ hai mục tiêu khác nhau: phát hiện incident và điều tra nguyên nhân.

## 🧠 Software Design

### Design 1 — Backpressure là contract giữa producer và consumer

**Khái niệm:**
Backpressure giới hạn tốc độ producer tạo work khi consumer hoặc downstream không theo kịp. Thay vì để queue/memory tăng vô hạn, hệ thống biểu đạt rõ capacity và hành vi khi capacity đã đầy.

**Vấn đề nó giải quyết:**
Một API nhận work nhanh hơn worker xử lý có thể tích lũy hàng triệu items, tăng memory, queue latency và cuối cùng làm cả process hoặc dependency sụp đổ dù throughput trung bình ban đầu có vẻ ổn.

**Ví dụ thực tế:**
In-process pipeline dùng bounded `Channel<T>` với capacity xác định. Khi đầy, producer chờ, từ chối hoặc áp policy phù hợp thay vì tiếp tục enqueue vô hạn. Với broker bên ngoài, consumer concurrency/prefetch cũng phải phù hợp downstream capacity.

**Trade-off:**
Backpressure bảo vệ resource và latency nhưng buộc hệ thống quyết định điều gì xảy ra khi demand vượt capacity: wait, reject, drop hay persist. Mỗi lựa chọn có business semantics khác nhau.

**Middle → Senior insight:**
Middle developer cần hiểu bounded queue và cancellation. Senior / Technical developer phải thiết kế capacity budget, overload semantics và propagation của pressure qua nhiều service để tránh chỉ chuyển bottleneck sang layer khác.

### Design 2 — Saga choreography vs orchestration theo độ phức tạp workflow

**Khái niệm:**
Saga chia business transaction dài thành local transactions và compensating actions. Choreography để services phản ứng với events; orchestration có một coordinator quyết định bước tiếp theo và compensation.

**Vấn đề nó giải quyết:**
Checkout có Inventory, Payment và Fulfillment thuộc các boundaries khác nhau nên không thể dựa vào một ACID transaction đơn giản. Partial failure cần workflow khôi phục business state có chủ đích.

**Ví dụ thực tế:**
Sau khi reserve inventory, payment thất bại. Orchestrator có thể yêu cầu release inventory. Với choreography, PaymentFailed event kích hoạt Inventory tự compensation theo contract đã thống nhất.

**Trade-off:**
Choreography giảm central coordinator nhưng flow dễ trở nên khó nhìn khi nhiều events/services tham gia. Orchestration làm workflow và state rõ hơn nhưng tạo coordinator cần reliability, persistence và ownership rõ ràng.

**Middle → Senior insight:**
Middle developer cần hiểu local transaction, idempotency và compensation không phải database rollback. Senior / Technical developer phải chọn choreography/orchestration dựa trên workflow visibility, coupling, team ownership, failure recovery và operational debugging.

### Design 3 — Strangler Fig cho modernization thay vì big-bang rewrite

**Khái niệm:**
Strangler Fig thay thế legacy system từng capability bằng cách đưa traffic/chức năng dần sang implementation mới, giữ hệ thống cũ hoạt động trong quá trình chuyển đổi.

**Vấn đề nó giải quyết:**
Big-bang rewrite có feedback cycle dài và phải tái hiện hàng năm business behavior trước khi tạo giá trị. Với hệ thống .NET Framework/CMS cũ, migration từng slice giúp giảm scope và kiểm chứng production sớm hơn.

**Ví dụ thực tế:**
Một legacy ASP.NET application giữ phần back-office cũ, trong khi product-search endpoint được route sang ASP.NET Core service mới. Sau khi telemetry và behavior ổn định, capability tiếp theo mới được tách.

**Trade-off:**
Incremental migration giảm cutover risk nhưng tạo giai đoạn hai hệ thống cùng tồn tại, routing/data synchronization và duplicate operational concerns. Big-bang có thể đơn giản hơn cho hệ thống nhỏ, ít integration và dễ thay thế.

**Middle → Senior insight:**
Middle developer cần giữ compatibility contract và regression tests trong từng slice. Senior / Technical developer phải chọn migration seam, sequence theo risk/value, ownership dữ liệu và tiêu chí retire legacy thay vì chỉ dựng kiến trúc đích đẹp hơn.
