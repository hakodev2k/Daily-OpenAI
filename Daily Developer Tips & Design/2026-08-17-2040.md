# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Random.Shared` thay vì tạo `new Random()` lặp lại trong code concurrent

**Mẹo:**
Với các nhu cầu random không liên quan đến cryptography như jitter, sampling hoặc test data đơn giản, dùng `Random.Shared` thay vì tạo nhiều instance `Random` ngắn hạn.

**Tại sao hữu ích:**
Giảm allocation, tránh seed trùng khi tạo nhiều instance gần nhau và dùng thuận tiện trong code chạy đa luồng.

**Ví dụ:**
```csharp
var delayMs = Random.Shared.Next(100, 500);
await Task.Delay(delayMs, cancellationToken);
```

**Lưu ý:**
`Random` không phù hợp cho token, password, key hoặc giá trị security-sensitive. Trường hợp đó dùng `RandomNumberGenerator`.

### Tip 2 — Dùng SQL Server `OUTPUT` để lấy dữ liệu vừa `INSERT`/`UPDATE` mà không query lại

**Mẹo:**
Khi cần lấy `Id`, timestamp hoặc giá trị vừa thay đổi, dùng `OUTPUT INSERTED...` thay vì chạy thêm một câu `SELECT` sau `INSERT`/`UPDATE`.

**Tại sao hữu ích:**
Giảm round-trip và tránh race condition giữa thao tác ghi với câu query đọc lại.

**Ví dụ:**
```sql
UPDATE Orders
SET Status = 'Approved',
    ApprovedAt = SYSUTCDATETIME()
OUTPUT INSERTED.Id, INSERTED.ApprovedAt
WHERE Id = @Id;
```

**Lưu ý:**
`OUTPUT` có semantics riêng khi dùng với trigger và multi-row statement. Cần hiểu rõ output shape nếu một statement ảnh hưởng nhiều record.

### Tip 3 — Dùng `git diff --submodule=log` khi PR có thay đổi submodule

**Mẹo:**
Nếu repository dùng Git submodule, xem diff với `--submodule=log` để biết submodule pointer đã nhảy qua những commit nào thay vì chỉ thấy SHA cũ và mới.

**Tại sao hữu ích:**
Giúp code review nhanh nhận ra dependency nội bộ đã chứa thay đổi gì và tránh merge một submodule update “mù”.

**Ví dụ:**
```bash
git diff --submodule=log origin/main...HEAD
```

**Lưu ý:**
Command này chỉ hiển thị lịch sử commit của submodule. Reviewer vẫn cần mở repository con nếu muốn đánh giá chi tiết patch hoặc security impact.

### Tip 4 — Dùng `docker inspect` để kiểm tra config thật của container thay vì đoán từ compose file

**Mẹo:**
Khi container chạy khác dự kiến, kiểm tra state/config runtime bằng `docker inspect` thay vì chỉ đọc Dockerfile hoặc `docker-compose.yml`.

**Tại sao hữu ích:**
Bạn có thể thấy environment, mount, network, restart policy, health state, entrypoint và port mapping mà Docker thực sự áp dụng cho container hiện tại.

**Ví dụ:**
```bash
docker inspect myapp
```

Lấy nhanh health status:

```bash
docker inspect \
  --format='{{json .State.Health}}' \
  myapp
```

**Lưu ý:**
`docker inspect` có thể hiển thị environment chứa secret nếu hệ thống đang cấu hình không an toàn. Không paste output nguyên bản vào ticket/chat công khai.

### Tip 5 — Dùng `HttpResponseMessage.EnsureSuccessStatusCode()` chỉ khi mọi non-2xx đều là lỗi kỹ thuật

**Mẹo:**
`EnsureSuccessStatusCode()` rất tiện với internal call đơn giản, nhưng chỉ nên dùng khi caller thật sự không cần phân biệt `404`, `409`, `429` hoặc business-specific status.

**Tại sao hữu ích:**
Giúp tránh mất semantics HTTP do biến mọi non-2xx thành một exception generic quá sớm.

**Ví dụ:**
```csharp
using var response = await httpClient.SendAsync(
    request,
    cancellationToken);

if (response.StatusCode == HttpStatusCode.Conflict)
{
    return ConflictResult.Instance;
}

response.EnsureSuccessStatusCode();
```

**Lưu ý:**
Đừng dùng exception làm control flow cho những status business bình thường. Với API client quan trọng, map status code sang domain/result type rõ ràng hơn.

## 🧠 Software Design

### Design 1 — Tell, Don’t Ask để giữ invariant gần domain behavior

**Khái niệm:**
Thay vì lấy dữ liệu từ object ra ngoài, kiểm tra điều kiện rồi sửa lại object, hãy yêu cầu object thực hiện hành vi mà nó chịu trách nhiệm nếu invariant thuộc về chính object đó.

**Vấn đề nó giải quyết:**
Logic nghiệp vụ dễ bị phân tán khi nhiều service đều đọc state rồi tự quyết định cách mutate entity, khiến invariant bị duplicate và ngày càng khó giữ nhất quán.

**Ví dụ thực tế:**
Thay vì:

```csharp
if (order.Status == OrderStatus.Pending)
{
    order.Status = OrderStatus.Approved;
    order.ApprovedAt = now;
}
```

có thể dùng:

```csharp
order.Approve(now);
```

`Order` tự kiểm tra transition hợp lệ và cập nhật state liên quan.

**Trade-off:**
Behavior-rich domain model giữ rule gần dữ liệu và giảm duplicate logic, nhưng có thể làm entity phức tạp nếu nhét cả orchestration, I/O hoặc dependency ngoài vào domain object.

**Middle → Senior insight:**
Middle developer nên nhận ra nơi nào đang “ask rồi mutate” cùng một rule ở nhiều chỗ. Senior developer cần phân biệt domain invariant thật với orchestration/application concern để tránh vừa anemic model vừa fat entity.

### Design 2 — Monotonic Reads khi user không được phép nhìn thấy dữ liệu “quay ngược”

**Khái niệm:**
Monotonic Reads bảo đảm sau khi client đã đọc version mới hơn của một dữ liệu, các lần đọc tiếp theo không trả về version cũ hơn dù hệ thống có nhiều replica hoặc cache layer.

**Vấn đề nó giải quyết:**
Trong hệ thống eventual consistency, user có thể thấy trạng thái `Approved`, refresh lần sau lại thấy `Pending` vì request được route sang replica đang lag.

**Ví dụ thực tế:**
Response có `version=42`. Client hoặc gateway giữ version đó trong session/context; lần đọc sau nếu replica chỉ có version 40 thì route sang node mới hơn hoặc primary thay vì trả state cũ.

**Trade-off:**
Cải thiện trải nghiệm và consistency cảm nhận nhưng làm routing/version propagation phức tạp hơn và có thể giảm khả năng tận dụng replica bất kỳ.

**Middle → Senior insight:**
Middle developer nên phân biệt read-your-writes với monotonic reads. Senior developer phải xác định scope theo user/session/entity, cách propagate version và chi phí fallback khi replica không đủ mới.

### Design 3 — Circuit Breaker nên scoped theo failure domain thật, không gom mọi dependency vào một breaker

**Khái niệm:**
Circuit Breaker mở khi failure vượt ngưỡng để ngừng gọi dependency đang lỗi. Breaker scope phải bám theo endpoint, tenant, region hoặc dependency instance tùy failure thực tế xảy ra ở đâu.

**Vấn đề nó giải quyết:**
Một breaker global cho cả external API có thể vô tình chặn toàn bộ traffic chỉ vì một endpoint hoặc một region lỗi cục bộ.

**Ví dụ thực tế:**
Nếu Payment API có `authorize` và `refund` với failure profile khác nhau, có thể cần policy/breaker riêng thay vì để lỗi `refund` mở circuit khiến `authorize` cũng bị chặn.

**Trade-off:**
Breaker chi tiết giảm blast radius và phản ứng chính xác hơn, nhưng tăng số state/policy phải theo dõi. Scope quá nhỏ lại khó đủ sample để quyết định circuit state ổn định.

**Middle → Senior insight:**
Middle developer nên hiểu Circuit Breaker không chỉ là thêm một Polly policy quanh `HttpClient`. Senior developer phải chọn scope, failure threshold, sampling window, half-open behavior và fallback theo failure domain thực tế.
