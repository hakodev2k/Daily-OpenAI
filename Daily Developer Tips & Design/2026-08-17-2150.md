# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConditionalWeakTable` khi metadata không nên giữ object sống lâu hơn cần thiết

**Mẹo:**
Khi cần gắn metadata phụ vào object mà không muốn dictionary mạnh giữ object đó khỏi GC, cân nhắc `ConditionalWeakTable<TKey, TValue>`.

**Tại sao hữu ích:**
Phù hợp cho cache metadata, instrumentation hoặc adapter state đi kèm lifetime của object gốc mà không cần tự cleanup key thủ công.

**Ví dụ:**
```csharp
private static readonly ConditionalWeakTable<object, Metadata> MetadataTable = new();

public static Metadata GetMetadata(object instance)
{
    return MetadataTable.GetValue(
        instance,
        _ => new Metadata());
}
```

Khi `instance` không còn reference mạnh ở nơi khác, entry tương ứng cũng có thể được GC.

**Lưu ý:**
Không dùng `ConditionalWeakTable` như cache business thông thường hoặc nơi cần enumerate toàn bộ entry. Semantics của nó phục vụ association theo object lifetime, không phải key-value store tổng quát.

### Tip 2 — Dùng ASP.NET Core Output Cache cho response đắt nhưng có thể tái sử dụng

**Mẹo:**
Với endpoint GET có response giống nhau trong một khoảng ngắn, cân nhắc Output Cache để cache toàn bộ response thay vì mỗi request đều chạy lại DB/query/render logic.

**Tại sao hữu ích:**
Giảm CPU, database load và latency ở endpoint đọc nhiều, đặc biệt khi response có thể vary theo route/query/header rõ ràng.

**Ví dụ:**
```csharp
builder.Services.AddOutputCache();

app.UseOutputCache();

app.MapGet("/catalog/{category}", GetCatalog)
   .CacheOutput(policy => policy
       .Expire(TimeSpan.FromSeconds(30))
       .SetVaryByRouteValue("category"));
```

**Lưu ý:**
Không cache response chứa dữ liệu per-user nếu policy không vary đúng theo identity/authorization context. Cũng cần xác định invalidation strategy khi dữ liệu thay đổi trước TTL.

### Tip 3 — Dùng SQL Server `SESSION_CONTEXT` để truyền metadata kỹ thuật theo connection

**Mẹo:**
Khi cần database trigger, audit procedure hoặc diagnostic query biết request/tenant/correlation metadata, có thể đặt key-value bằng `sp_set_session_context` trên SQL Server connection.

**Tại sao hữu ích:**
Giúp correlate database activity với application request mà không phải thêm parameter vào mọi stored procedure hoặc mọi câu SQL.

**Ví dụ:**
```sql
EXEC sys.sp_set_session_context
    @key = N'CorrelationId',
    @value = @correlationId;
```

Đọc lại:

```sql
SELECT SESSION_CONTEXT(N'CorrelationId');
```

**Lưu ý:**
Connection pooling làm connection được tái sử dụng. Nếu application đặt session context, phải đảm bảo giá trị được set/reset đúng cho mỗi logical request để tránh metadata “rò” sang request kế tiếp.

### Tip 4 — Dùng `git diff --check` trước commit để bắt whitespace error gây noise

**Mẹo:**
Chạy `git diff --check` trước commit hoặc trong pre-commit/CI để phát hiện trailing whitespace và whitespace error trong patch.

**Tại sao hữu ích:**
Giảm diff noise, tránh file bị thay đổi hàng loạt chỉ vì whitespace và giữ patch dễ review hơn.

**Ví dụ:**
```bash
git diff --check
```

Kiểm tra phần đã stage:

```bash
git diff --cached --check
```

**Lưu ý:**
Whitespace policy phụ thuộc repository. Với generated file hoặc format đặc biệt, cần cấu hình `.gitattributes`/tooling phù hợp thay vì áp một rule cứng cho mọi file.

### Tip 5 — Dùng `Expect: 100-continue` có chọn lọc cho upload request lớn

**Mẹo:**
Với HTTP request có body rất lớn, `Expect: 100-continue` cho phép client chờ server chấp nhận headers trước khi gửi toàn bộ payload.

**Tại sao hữu ích:**
Nếu server sẽ reject sớm vì auth, quota hoặc validation ở header, client có thể tránh upload hàng trăm MB vô ích.

**Ví dụ:**
```http
POST /imports HTTP/1.1
Content-Length: 524288000
Expect: 100-continue
Authorization: Bearer ...
```

Server có thể trả lỗi ngay hoặc gửi `100 Continue` để client bắt đầu upload body.

**Lưu ý:**
Cơ chế này thêm một round-trip trước body và không phải proxy/server nào cũng xử lý giống nhau. Với payload nhỏ, overhead có thể lớn hơn lợi ích.

## 🧠 Software Design

### Design 1 — Consumer/Supplier relationship cần contract negotiation rõ ràng

**Khái niệm:**
Trong DDD context mapping, Consumer/Supplier mô tả quan hệ nơi upstream supplier cung cấp model/API còn downstream consumer phụ thuộc vào nó, nhưng hai bên vẫn có thể thương lượng contract thay vì downstream chỉ chấp nhận mọi quyết định.

**Vấn đề nó giải quyết:**
Nếu upstream thay đổi chỉ vì nhu cầu nội bộ mà không quan tâm downstream, integration trở nên mong manh. Ngược lại, nếu downstream ép supplier phục vụ mọi nhu cầu riêng, upstream mất quyền sở hữu domain.

**Ví dụ thực tế:**
`EmployeeService` là supplier của `Payroll`. Payroll cần `EmploymentStatus`, `EffectiveDate` và `PayrollGroup`, nhưng không nên phụ thuộc toàn bộ Employee entity. Hai team thống nhất contract nhỏ và compatibility window cho field quan trọng.

**Trade-off:**
Contract negotiation giảm accidental coupling và breaking change, nhưng cần communication, ownership và release discipline. Với dependency third-party không thể thương lượng, Anti-Corruption Layer hoặc Conformist phù hợp hơn.

**Middle → Senior insight:**
Middle developer nên nhận ra service dependency còn là quan hệ ownership giữa team/context. Senior developer phải xác định ai sở hữu contract, ai chịu migration cost và cơ chế governance tối thiểu để tránh cả hai cực đoan: supplier độc đoán hoặc consumer-driven model phình to.

### Design 2 — Work Stealing phù hợp khi task cost không đồng đều

**Khái niệm:**
Work Stealing cho phép worker rảnh lấy task từ queue/deque của worker khác thay vì mỗi worker bị cố định vào một partition workload bất kể độ nặng của task.

**Vấn đề nó giải quyết:**
Nếu task cost biến động lớn, static partitioning có thể khiến một worker bị backlog dài trong khi worker khác idle, làm throughput và tail latency kém.

**Ví dụ thực tế:**
Một image/document processing service có 8 worker. Một số file xử lý 200 ms, một số 30 giây. Thay vì chia cứng mỗi worker một shard nhỏ, worker rảnh có thể “steal” task chưa chạy từ worker đang quá tải.

**Trade-off:**
Work stealing cải thiện utilization và balance tự động, nhưng ordering/locality khó giữ hơn và coordination phức tạp hơn. Nếu workload yêu cầu strict per-key ordering, partition cố định thường an toàn hơn.

**Middle → Senior insight:**
Middle developer nên hiểu concurrency không chỉ là tăng số worker. Senior developer cần chọn scheduler theo task-cost distribution, locality, ordering constraint và overhead coordination chứ không mặc định một queue chung luôn tối ưu.

### Design 3 — Data Retention là một phần của architecture, không phải cleanup job cuối cùng

**Khái niệm:**
Data Retention xác định dữ liệu nào được giữ bao lâu, ở storage tier nào, khi nào archive/anonymize/delete và dependency nào phải cùng tuân thủ lifecycle đó.

**Vấn đề nó giải quyết:**
Nếu mọi bảng, log, event và blob chỉ “giữ mãi”, storage cost tăng, query chậm hơn và rủi ro privacy/compliance lớn dần theo thời gian.

**Ví dụ thực tế:**
Audit security log có thể giữ 365 ngày ở hot storage rồi archive thêm 2 năm. Temporary export file giữ 24 giờ. Raw request payload chứa PII chỉ giữ 7 ngày hoặc không lưu nếu không cần thiết.

**Trade-off:**
Retention rõ ràng giảm cost và exposure, nhưng deletion/anonymization xuyên database, object storage, cache, search index và backup rất khó làm đúng. Giữ quá ngắn có thể làm mất khả năng điều tra hoặc đáp ứng business requirement.

**Middle → Senior insight:**
Middle developer nên hỏi dữ liệu có lifetime gì thay vì mặc định persist vô hạn. Senior developer phải thiết kế ownership, legal/business retention, cascade deletion, backup semantics, archive tier và observability để retention trở thành capability vận hành thực sự.
