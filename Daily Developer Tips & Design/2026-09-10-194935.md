# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` khi cần bulk update mà không cần materialize entity

**Mẹo:**
Với EF Core, nếu cần cập nhật nhiều row theo cùng một rule và không cần domain behavior trên từng entity, cân nhắc `ExecuteUpdateAsync` thay vì `ToListAsync()` rồi sửa từng object.

**Tại sao hữu ích:**
Cách load entity trước sẽ tạo database round trip để đọc dữ liệu, allocation cho object, change tracking và sau đó phát nhiều update hoặc batching. `ExecuteUpdateAsync` dịch trực tiếp thành một lệnh `UPDATE`, giảm memory và round trip đáng kể.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now), ct);
```

Phù hợp với job đánh dấu hàng nghìn order hết hạn mà không cần chạy logic riêng trên từng aggregate.

**Lưu ý:**
Bulk operation này đi thẳng xuống database và không đồng bộ state của entity đang được track trong cùng `DbContext`. Nó cũng bỏ qua domain method/interceptor logic mà bạn có thể đang dựa vào, nên transaction boundary và invariant phải được xem xét rõ.

### Tip 2 — Thiết kế compound index MongoDB theo query shape, không theo danh sách field “hay dùng”

**Mẹo:**
Khi tạo compound index trong MongoDB, bắt đầu từ các query thật: field equality, sort và range nào thường đi cùng nhau; sau đó kiểm tra `explain()` thay vì ghép mọi field phổ biến vào một index lớn.

**Tại sao hữu ích:**
Thứ tự field trong compound index quyết định query nào tận dụng được index prefix và có thể tránh in-memory sort. Một index tồn tại không có nghĩa query đang sử dụng nó hiệu quả.

**Ví dụ:**
```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })

db.orders.find({
  tenantId: "t-42",
  status: "Pending"
}).sort({ createdAt: -1 }).limit(50)
```

Sau đó dùng:

```javascript
db.orders.find(...).sort(...).explain("executionStats")
```

Kiểm tra `totalKeysExamined`, `totalDocsExamined` và số document trả về để đánh giá selectivity thực tế.

**Lưu ý:**
Đừng over-index. Mỗi index làm tăng storage, memory pressure và chi phí write. Query pattern thay đổi cũng có thể khiến index cũ trở thành technical debt.

### Tip 3 — Giữ correlation xuyên `HttpClient` bằng `Activity` thay vì tự phát minh header tracing riêng

**Mẹo:**
Trong .NET service-to-service calls, ưu tiên chuẩn distributed tracing dựa trên `System.Diagnostics.Activity` và W3C Trace Context để telemetry từ inbound request sang outbound `HttpClient` có cùng trace.

**Tại sao hữu ích:**
Khi API A gọi B rồi B gọi database hoặc third-party API, một correlation ID tự chế chỉ hữu ích nếu mọi component nhớ forward đúng. Instrumentation chuẩn cho phép Application Insights/OpenTelemetry liên kết request, dependency và span theo cùng trace graph.

**Ví dụ:**
```csharp
using var activity = MyActivitySource.StartActivity("RecalculateInvoice");
activity?.SetTag("invoice.id", invoiceId);

await httpClient.PostAsJsonAsync(
    $"/billing/{invoiceId}/recalculate",
    payload,
    cancellationToken);
```

Khi điều tra latency, đi từ request chậm → dependency span → downstream request thay vì grep log thủ công giữa nhiều service.

**Lưu ý:**
Không đưa PII, token hoặc dữ liệu cardinality cực cao vào tag. Tracing cũng không thay thế metrics và structured logs; mỗi loại telemetry trả lời một nhóm câu hỏi khác nhau.

### Tip 4 — Validate dữ liệu API ở runtime dù frontend dùng TypeScript

**Mẹo:**
TypeScript chỉ kiểm tra type ở compile time. Với dữ liệu từ REST API, local storage hoặc third-party script, hãy coi payload là `unknown` cho đến khi đã validate runtime nếu correctness hoặc security phụ thuộc vào shape đó.

**Tại sao hữu ích:**
Backend có thể deploy version khác, proxy có thể trả error payload, hoặc field có thể `null` ngoài contract. Ép kiểu bằng `as Customer` chỉ làm compiler im lặng chứ không biến JSON sai thành object hợp lệ.

**Ví dụ:**
```ts
type Customer = {
  id: string
  displayName: string
}

function isCustomer(value: unknown): value is Customer {
  if (typeof value !== "object" || value === null) return false
  const x = value as Record<string, unknown>
  return typeof x.id === "string" && typeof x.displayName === "string"
}

const payload: unknown = await response.json()
if (!isCustomer(payload)) throw new Error("Invalid customer payload")
```

Trong hệ thống lớn, schema validator có thể được generate từ OpenAPI hoặc dùng thư viện validation phù hợp.

**Lưu ý:**
Không cần validate lặp lại mọi object nội bộ đã được tạo từ nguồn tin cậy. Runtime validation nên tập trung tại trust boundary để tránh duplication và overhead không cần thiết.

### Tip 5 — Khi Pod ở trạng thái `Pending`, xem scheduler events trước khi đọc application logs

**Mẹo:**
Nếu Kubernetes Pod chưa chạy và đang `Pending`, dùng `kubectl describe pod` để đọc Events trước. Application log thường chưa tồn tại vì container còn chưa được schedule hoặc start.

**Tại sao hữu ích:**
`Pending` thường là vấn đề trước runtime: thiếu CPU/memory phù hợp, node selector không match, taint/toleration, PVC chưa bind hoặc image pull prerequisite. Đi thẳng vào log application khiến việc chẩn đoán sai tầng.

**Ví dụ:**
```bash
kubectl get pod checkout-api-7f9d8c -o wide
kubectl describe pod checkout-api-7f9d8c
```

Nếu Events báo:

```text
0/6 nodes are available: 6 Insufficient memory
```

hypothesis đầu tiên nên là scheduling/resource capacity, không phải lỗi ASP.NET Core startup.

**Lưu ý:**
`describe` phản ánh event gần đây và event retention có giới hạn. Sau khi Pod đã start nhưng restart/crash, chuyển sang `kubectl logs --previous`, probe status và container exit reason để điều tra đúng lifecycle stage.

## 🧠 Software Design

### Design 1 — Outbox Pattern để giữ transaction boundary giữa database và message broker

**Khái niệm:**
Outbox Pattern ghi business state và message/event cần publish vào cùng một database transaction. Một dispatcher riêng sau đó đọc outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application vừa `SaveChanges` vừa publish message theo hai thao tác độc lập, process có thể crash giữa hai bước. Database đã commit nhưng event chưa gửi, hoặc event đã gửi nhưng transaction database lại fail, tạo inconsistency khó phục hồi.

**Ví dụ thực tế:**
```text
Transaction SQL:
1. INSERT Order
2. INSERT OutboxMessage(OrderPlaced)
3. COMMIT

Dispatcher:
4. đọc OutboxMessage chưa gửi
5. publish Azure Service Bus
6. đánh dấu processed
```

Consumer vẫn phải idempotent vì dispatcher có thể publish lại nếu crash sau bước 5 nhưng trước bước 6.

**Trade-off:**
Outbox loại bỏ khoảng trống atomicity giữa local database transaction và việc ghi nhận intent gửi message, nhưng thêm bảng outbox, dispatcher, cleanup, retry, monitoring và eventual consistency. Với ứng dụng đơn giản không có broker, đây có thể là complexity không cần thiết.

**Middle → Senior insight:**
Middle developer cần hiểu vì sao `SaveChangesAsync(); PublishAsync();` không phải distributed transaction an toàn. Senior / Technical developer phải xác định delivery guarantee, deduplication strategy, ordering requirement, outbox retention và operational recovery trước khi áp dụng pattern.

### Design 2 — Cache-aside phải thiết kế cả cache miss lẫn cache failure

**Khái niệm:**
Cache-aside để application đọc cache trước; nếu miss thì đọc source of truth, trả dữ liệu và populate cache. Thiết kế hoàn chỉnh còn phải quyết định hệ thống cư xử thế nào khi Redis chậm hoặc unavailable.

**Vấn đề nó giải quyết:**
Cache giảm latency và database load, nhưng nếu application coi Redis là dependency bắt buộc cho mọi read thì một cache outage có thể biến optimization thành single point of failure. Ngược lại, fallback toàn bộ xuống database có thể gây thundering herd và làm database sập tiếp.

**Ví dụ thực tế:**
```text
Product catalog request
-> Redis hit: trả ngay
-> Redis miss: đọc SQL, populate TTL
-> Redis timeout: fallback SQL có rate limit/bulkhead
-> database pressure cao: degrade một số dữ liệu phụ hoặc trả stale value nếu business cho phép
```

TTL, jitter và request coalescing có thể giảm việc nhiều instance cùng refresh một hot key.

**Trade-off:**
Cache-aside giữ source of truth rõ và triển khai tương đối đơn giản, nhưng chấp nhận stale data, cold-cache spike và logic invalidation. Resilience bổ sung như stale fallback hay coalescing tiếp tục tăng complexity.

**Middle → Senior insight:**
Middle developer cần implement hit/miss, TTL và invalidation đúng. Senior / Technical developer phải thiết kế behavior khi cache degraded dựa trên latency SLO, database headroom, consistency requirement và blast radius — không chỉ hỏi “Redis có nhanh không?”.

### Design 3 — API backward compatibility nên được coi là migration protocol

**Khái niệm:**
Thay đổi REST API an toàn không chỉ là giữ endpoint cũ. Đó là protocol cho phép producer và nhiều consumer nâng cấp ở thời điểm khác nhau mà vẫn hoạt động trong migration window.

**Vấn đề nó giải quyết:**
Mobile app, frontend CDN, partner integration và service nội bộ không deploy đồng thời. Rename field, đổi semantics hoặc biến optional field thành required có thể phá client vẫn đang chạy dù server mới deploy thành công.

**Ví dụ thực tế:**
```text
Hiện tại:
status: "active" | "disabled"

Cần thêm trạng thái mới:
status: "pending_review"
```

Trước khi thêm, phải biết client cũ xử lý unknown enum thế nào. Một migration an toàn có thể cần tolerant client, telemetry về version đang dùng, compatibility test và deprecation window trước khi contract cũ bị loại bỏ.

**Trade-off:**
Backward compatibility giảm release coupling và production incidents nhưng buộc server/client duy trì behavior cũ trong một thời gian, tăng test matrix và technical debt. Versioning quá sớm cho mọi thay đổi cũng có thể tạo nhiều API lineage khó vận hành.

**Middle → Senior insight:**
Middle developer cần phân biệt additive và breaking change, đồng thời giữ contract test cho consumer quan trọng. Senior / Technical developer phải thiết kế migration sequence, deprecation policy, telemetry adoption và rollback path; mục tiêu là cho hệ thống tiến hóa an toàn chứ không phải giữ mọi version mãi mãi.
