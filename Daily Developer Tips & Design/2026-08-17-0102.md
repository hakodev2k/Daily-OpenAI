# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ConfigureAwait(false)` có chọn lọc trong library code

**Mẹo:**
Trong reusable library không phụ thuộc synchronization context của caller, có thể dùng `ConfigureAwait(false)` để continuation không yêu cầu quay lại context ban đầu. Với ASP.NET Core application code hiện đại, thường không cần rải nó khắp nơi vì ASP.NET Core không có `SynchronizationContext` kiểu ASP.NET cũ.

**Tại sao hữu ích:**
Giúp phân biệt optimization/correctness concern của library với application code và tránh cargo-cult async patterns.

**Ví dụ:**
```csharp
public async Task<string> ReadAsync(CancellationToken cancellationToken)
{
    using var response = await _httpClient
        .GetAsync("data", cancellationToken)
        .ConfigureAwait(false);

    return await response.Content
        .ReadAsStringAsync(cancellationToken)
        .ConfigureAwait(false);
}
```

**Lưu ý:**
Không thêm `ConfigureAwait(false)` máy móc vào mọi ASP.NET Core method. Nếu code thực sự cần continuation trên một context cụ thể như UI thread, dùng sai có thể gây lỗi.

### Tip 2 — Tránh `SELECT *` trong production query

**Mẹo:**
Chỉ lấy những columns thực sự cần, đặc biệt với bảng rộng hoặc endpoint có traffic cao.

**Tại sao hữu ích:**
Giảm network payload, memory, I/O và có thể cho optimizer cơ hội sử dụng covering index thay vì phải đọc base table.

**Ví dụ:**
```sql
-- Không nên
SELECT *
FROM Orders
WHERE CustomerId = @CustomerId;

-- Tốt hơn
SELECT Id, Status, TotalAmount, CreatedAt
FROM Orders
WHERE CustomerId = @CustomerId;
```

Trong EF Core, projection cũng giúp đạt cùng mục tiêu:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(x.Id, x.Status, x.TotalAmount))
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Không tối ưu cực đoan các internal/admin query nhỏ chỉ vì nguyên tắc. Ưu tiên nơi data volume và request frequency thực sự đáng kể.

### Tip 3 — Dùng `curl -v` để debug HTTP trước khi đổ lỗi cho application

**Mẹo:**
Khi API hoạt động khác nhau giữa local, server hoặc proxy, dùng `curl -v` để quan sát DNS/connect/TLS/request/response headers ở mức thấp hơn application client.

**Tại sao hữu ích:**
Nhanh chóng tách lỗi application khỏi lỗi redirect, certificate, proxy, authentication header hoặc HTTP negotiation.

**Ví dụ:**
```bash
curl -v \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json" \
  https://api.example.com/orders/123
```

Nếu chỉ cần response headers:

```bash
curl -I https://api.example.com/health
```

**Lưu ý:**
`-v` có thể hiển thị sensitive headers. Không paste nguyên output chứa token, cookie hoặc credential vào ticket/log công khai.

### Tip 4 — Đặt timeout cho outbound HTTP dựa trên request budget

**Mẹo:**
Không để downstream call chờ tùy ý. Timeout nên nhỏ hơn tổng latency budget của request và phối hợp với cancellation/retry policy.

**Tại sao hữu ích:**
Một dependency chậm có thể giữ connection và resources đủ lâu để tạo cascading failure. Timeout rõ ràng giúp hệ thống fail có kiểm soát.

**Ví dụ:**
```csharp
services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri("https://inventory.internal");
    client.Timeout = TimeSpan.FromSeconds(3);
});
```

Nếu endpoint có budget 5 giây, không hợp lý khi một dependency được phép chờ 30 giây.

**Lưu ý:**
Timeout ngắn không tự động làm hệ thống resilient. Retry sai cách có thể nhân tải lên dependency đang gặp sự cố; cần cân nhắc retry count, backoff và idempotency.

### Tip 5 — Dùng `git worktree` khi phải làm nhiều branch song song

**Mẹo:**
`git worktree` cho phép checkout nhiều branch của cùng repository ở các thư mục khác nhau mà không cần clone repository nhiều lần hoặc stash liên tục.

**Tại sao hữu ích:**
Rất tiện khi đang phát triển feature nhưng cần mở ngay hotfix, review PR hoặc chạy hai phiên bản code song song.

**Ví dụ:**
```bash
git worktree add ../app-hotfix hotfix/payment-timeout
```

Sau khi hoàn tất:

```bash
git worktree remove ../app-hotfix
```

**Lưu ý:**
Một branch không thể được checkout đồng thời trong hai worktrees. Cũng cần nhớ cleanup worktree cũ để tránh thư mục và metadata dư thừa.

## 🧠 Software Design

### Design 1 — Cache-Aside và bài toán stale data

**Khái niệm:**
Cache-Aside để application đọc cache trước; khi miss thì đọc source of truth rồi đưa kết quả vào cache. Khi dữ liệu thay đổi, application thường invalidate hoặc update cache riêng biệt.

**Vấn đề nó giải quyết:**
Giảm database load và latency cho read-heavy workloads, nhưng tạo ra câu hỏi quan trọng: hệ thống chấp nhận dữ liệu cũ trong bao lâu và cache được invalidated thế nào?

**Ví dụ thực tế:**
Product catalog được đọc hàng nghìn lần nhưng giá chỉ đổi vài lần mỗi ngày. API cache `ProductDto` trong Redis 5 phút. Khi admin cập nhật sản phẩm, service xóa key tương ứng; TTL vẫn đóng vai trò safety net nếu invalidation thất bại.

**Trade-off:**
Lợi ích là throughput cao và latency thấp. Chi phí là stale data, cache stampede, invalidation complexity và thêm dependency vận hành. Với dữ liệu yêu cầu strong consistency như số dư tài khoản, cache-aside có thể không phù hợp cho quyết định giao dịch.

**Middle → Senior insight:**
Middle developer nên biết cache key, TTL và invalidation. Senior developer cần xác định freshness requirement theo business, xử lý stampede, failure mode của Redis và quyết định dữ liệu nào không nên cache dù technically có thể.

### Design 2 — API evolution: ưu tiên additive change trước versioning

**Khái niệm:**
API evolution là thay đổi contract mà không phá vỡ consumers hiện tại. Nhiều thay đổi có thể thực hiện theo hướng additive trước khi phải tạo `/v2`.

**Vấn đề nó giải quyết:**
Versioning quá sớm khiến nhiều contract phải được duy trì song song; nhưng breaking change trực tiếp có thể làm client production ngừng hoạt động.

**Ví dụ thực tế:**
Thay vì đổi field:

```json
{
  "name": "Ha"
}
```

thành một object hoàn toàn khác ngay lập tức, API có thể thêm field mới:

```json
{
  "name": "Ha",
  "displayName": "Ha Dinh"
}
```

Consumer cũ tiếp tục dùng `name`, consumer mới chuyển dần sang `displayName`. Field cũ chỉ được loại bỏ theo deprecation policy rõ ràng.

**Trade-off:**
Additive evolution giảm migration pressure nhưng contract có thể tích tụ legacy fields. Version mới tạo contract sạch hơn nhưng tăng maintenance, documentation, testing và routing complexity.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking changes. Senior developer phải đánh giá consumer ownership, release cadence, backward compatibility window và migration cost trước khi quyết định versioning thay vì chỉ thêm `/v2` theo thói quen.

### Design 3 — Outbox Pattern cho database + message broker consistency

**Khái niệm:**
Outbox Pattern lưu business change và integration event trong cùng local database transaction. Background publisher sau đó đọc outbox và gửi event tới broker.

**Vấn đề nó giải quyết:**
Nếu service update database rồi publish RabbitMQ/Azure Service Bus bằng hai operation độc lập, process có thể crash ở giữa: database đã commit nhưng event chưa được gửi, hoặc ngược lại.

**Ví dụ thực tế:**
Khi order được xác nhận, transaction ghi cả `Orders.Status = Confirmed` và một `OrderConfirmed` record vào `OutboxMessages`. Worker publish message sau commit và đánh dấu outbox record đã xử lý.

```text
Request
   |
   v
[DB Transaction]
   |-- Update Order
   |-- Insert OutboxMessage
   v
 Commit
   |
   v
Outbox Worker ---> Message Broker ---> Consumer
```

**Trade-off:**
Lợi ích là không cần distributed transaction và giảm nguy cơ mất event. Chi phí là eventual consistency, outbox storage/cleanup, publisher retry và khả năng duplicate delivery; consumer vẫn cần idempotent handling.

**Middle → Senior insight:**
Middle developer nên hiểu vì sao database transaction không bao phủ message broker. Senior developer cần thiết kế delivery semantics, deduplication, ordering, retry/backoff, poison-message handling và observability cho toàn bộ pipeline.
