# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate `Options` ngay lúc startup thay vì đợi request đầu tiên mới lỗi

**Mẹo:**
Với configuration bắt buộc cho ASP.NET Core, dùng strongly typed Options cùng validation và `ValidateOnStart()` để phát hiện endpoint, timeout, credential metadata hoặc business settings không hợp lệ trước khi instance nhận traffic.

**Tại sao hữu ích:**
Configuration lỗi nhưng chỉ được đọc ở một code path hiếm có thể khiến deployment trông healthy trong nhiều phút hoặc nhiều giờ. Fail-fast ở startup chuyển lỗi cấu hình thành deployment failure quan sát được, thay vì runtime incident phụ thuộc request nào chạm vào setting trước.

**Ví dụ:**
Payment integration yêu cầu `BaseUrl` hợp lệ và `TimeoutSeconds` trong khoảng cho phép. Instance mới validate các giá trị này khi boot; nếu environment variable bị thiếu, readiness không bao giờ chuyển sang ready và rollout dừng trước khi traffic đi vào version lỗi.

**Lưu ý:**
Không validate bằng cách gọi external dependency trong Options validator; startup validation nên kiểm tra cấu hình cục bộ và deterministic. Secrets có thể được resolve qua provider riêng, nhưng cần phân biệt lỗi configuration với transient dependency outage.

### Tip 2 — EF Core query translation phải được kiểm tra ở database provider thật

**Mẹo:**
Với LINQ phức tạp, kiểm tra SQL được generate và chạy integration test trên provider production thay vì giả định expression đúng vì unit test với collection/in-memory implementation đã pass.

**Tại sao hữu ích:**
LINQ-to-Objects và LINQ provider của database có semantics/capabilities khác nhau. Một expression có thể chạy hoàn hảo trong memory nhưng translate thành SQL đắt, không translate được, hoặc có behavior khác về collation, null, date/time và case sensitivity.

**Ví dụ:**
Search endpoint dùng nhiều predicates động và string operations. Test với PostgreSQL container xác minh generated SQL, kết quả và query count; team phát hiện một expression tạo function trên indexed column khiến index không được sử dụng dù test logic thuần C# vẫn xanh.

**Lưu ý:**
Không cần biến mọi unit test thành database test. Giữ unit tests cho business logic thuần; dùng integration tests có chọn lọc ở data-access boundary nơi translation, constraint, transaction và provider semantics thực sự quan trọng.

### Tip 3 — Elasticsearch filter và full-text query phục vụ hai mục tiêu khác nhau

**Mẹo:**
Dùng full-text query cho relevance trên text đã analyze; dùng filter context cho điều kiện exact/range như `tenantId`, `status`, category hoặc date range khi không cần scoring.

**Tại sao hữu ích:**
Đưa mọi điều kiện vào scoring query làm intent khó đọc và có thể tốn computation không cần thiết. Ngược lại, dùng exact matching cho field text đã analyze có thể trả kết quả bất ngờ vì giá trị trong index không còn giống raw input.

**Ví dụ:**
Product search dùng `multi_match` cho tên/mô tả nhưng đặt `tenantId`, `isActive` và price range trong `bool.filter`. Mapping giữ keyword subfield cho exact filtering/sorting và text field cho relevance.

**Lưu ý:**
Query tốt không cứu được mapping sai. Analyzer, tokenization và field type là quyết định index-time; thay đổi quan trọng thường cần reindex. Luôn kiểm tra mapping và `_explain`/profile khi relevance hoặc latency bất thường.

### Tip 4 — CDN cache key phải phản ánh đúng các dimensions làm response thay đổi

**Mẹo:**
Khi dùng Akamai/CDN hoặc reverse proxy cache, xác định rõ URL, query parameters, headers, locale, authentication state và content variation nào thực sự làm response khác nhau; cache key phải bao gồm đúng các dimensions đó.

**Tại sao hữu ích:**
Thiếu dimension có thể trả nội dung của context này cho context khác; thêm quá nhiều dimensions lại phá hit ratio. Đây vừa là vấn đề performance vừa có thể là security issue nếu personalized response bị cache như public content.

**Ví dụ:**
Trang catalog public thay đổi theo `locale` nhưng bỏ qua tracking parameters. Cache key giữ locale và các query filter ảnh hưởng nội dung, loại `utm_*`; response có user-specific pricing không được đưa vào shared public cache nếu chưa có isolation strategy an toàn.

**Lưu ý:**
Đừng chỉ nhìn `Cache-Control` ở application rồi giả định mọi layer xử lý giống nhau. Kiểm tra CDN rules, `Vary`, purge behavior, browser cache và authenticated responses end-to-end trước khi rollout.

### Tip 5 — AI-generated migration phải được review như code có khả năng phá dữ liệu

**Mẹo:**
Khi AI coding agent tạo EF Core/database migration, kiểm tra generated operations, SQL thực tế, lock/data-movement risk và rollback path; không chấp nhận migration chỉ vì model snapshot và build đều hợp lệ.

**Tại sao hữu ích:**
Agent có thể suy luận rename thành drop + add, tạo column non-null trên table lớn theo cách gây rewrite/lock, hoặc bỏ qua backfill cần thiết. Những lỗi này thường không xuất hiện khi compile nhưng có thể gây downtime hoặc mất dữ liệu khi deploy.

**Ví dụ:**
Agent đổi `CustomerName` thành `DisplayName` và sinh migration drop/add. Review phát hiện dữ liệu sẽ mất, nên team chuyển sang expand/backfill/contract hoặc explicit rename phù hợp với rollout topology và database engine.

**Lưu ý:**
Migration chạy được trên database nhỏ local không chứng minh an toàn ở production. Cần xem table size, lock semantics, execution duration, compatibility với old/new application versions và backup/recovery strategy.

## 🧠 Software Design

### Design 1 — BFF chỉ đáng dùng khi client có nhu cầu composition thực sự khác nhau

**Khái niệm:**
Backend for Frontend tạo backend boundary tối ưu cho một client experience như web hoặc mobile, thường chịu trách nhiệm composition, shaping và client-specific orchestration thay vì đẩy mọi khác biệt vào một API chung.

**Vấn đề nó giải quyết:**
Mobile có bandwidth/interaction flow khác web; một generic API có thể buộc client gọi nhiều endpoints, tự orchestration và biết quá nhiều service topology. BFF gom các concerns thật sự thuộc client experience về server-side boundary.

**Ví dụ thực tế:**
Mobile home screen cần profile, loyalty summary và lightweight recommendations trong một round trip, trong khi admin web cần dữ liệu quản trị hoàn toàn khác. Hai BFF có thể expose contracts phù hợp nhưng cùng gọi các domain services phía sau.

**Trade-off:**
BFF giảm client coupling và network chatter nhưng thêm deployment, duplicated composition logic và nguy cơ business rules bị phân tán. Nếu web/mobile có nhu cầu gần như giống nhau, một API đơn giản có thể tốt hơn hai backend riêng.

**Middle → Senior insight:**
Middle developer cần giữ BFF ở composition/presentation boundary và không copy domain logic tùy tiện. Senior / Technical developer phải đánh giá client divergence, ownership, latency, security và duplication cost trước khi tạo thêm service boundary.

### Design 2 — Read replica cải thiện read capacity nhưng đưa replication lag vào contract

**Khái niệm:**
Read replica tách một phần read workload khỏi primary database, nhưng dữ liệu trên replica thường được replicate asynchronous nên read-after-write consistency không mặc nhiên được bảo đảm.

**Vấn đề nó giải quyết:**
Reporting, catalog hoặc dashboard reads có thể gây pressure lớn lên primary. Replica tăng read capacity và isolation, nhưng nếu application không phân loại consistency requirement, user có thể vừa update xong rồi lập tức đọc thấy state cũ.

**Ví dụ thực tế:**
Product catalog search có thể chịu stale vài giây và đọc replica. Sau khi user đổi password hoặc submit payment state, request xác nhận đọc primary hoặc dùng consistency strategy khác vì stale read ở đây có thể gây hành vi sai nghiêm trọng.

**Trade-off:**
Replica giảm tải primary nhưng tăng topology, failover/routing complexity và consistency reasoning. Lag có thể tăng mạnh đúng lúc primary bận; “eventually consistent” phải được lượng hóa theo user/business tolerance chứ không chỉ ghi trong diagram.

**Middle → Senior insight:**
Middle developer cần biết query nào đang đi primary/replica và không giả định immediate consistency. Senior / Technical developer phải phân loại read paths, đo lag, thiết kế read-your-writes khi cần và quyết định liệu thêm replica có xử lý bottleneck thật hay chỉ che query/index kém.

### Design 3 — Dependency Inversion nên bảo vệ policy khỏi volatility, không tạo interface cho mọi class

**Khái niệm:**
Dependency Inversion hướng business policy phụ thuộc vào abstraction ổn định thay vì chi tiết volatile như payment SDK, storage hoặc transport. Mục tiêu là kiểm soát coupling và direction of change, không phải đạt tỷ lệ interface/class 1:1.

**Vấn đề nó giải quyết:**
Nếu domain/application logic gọi trực tiếp vendor SDK ở khắp nơi, thay provider, test failure paths hoặc đổi integration contract sẽ lan thay đổi qua nhiều modules. Một boundary có ý nghĩa gom volatility vào adapter.

**Ví dụ thực tế:**
Checkout application phụ thuộc vào `IPaymentGateway` thể hiện operations mà business cần; adapter Stripe/vendor cụ thể mapping SDK errors sang application semantics. Ngược lại, một pure calculation service nội bộ không cần interface chỉ để “theo SOLID”.

**Trade-off:**
Abstraction đúng giúp testability và thay đổi integration; abstraction sớm hoặc quá generic tạo indirection, nhiều files và contract không phản ánh domain. Interface cũng không tự động tạo loose coupling nếu nó chỉ mirror nguyên vendor API.

**Middle → Senior insight:**
Middle developer cần đặt dependency direction đúng và viết abstraction theo consumer need. Senior / Technical developer phải nhận diện volatility thực, chọn seam có giá trị và biết khi nào concrete dependency đơn giản hơn, tránh biến architectural principle thành ceremony.
