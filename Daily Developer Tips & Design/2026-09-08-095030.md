# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ArrayPool<T>` khi buffer lớn được tạo lặp lại trong hot path

**Mẹo:**
Nếu application liên tục cấp phát buffer lớn ngắn hạn để encode, parse hoặc xử lý stream, cân nhắc thuê buffer từ `ArrayPool<T>` thay vì `new` array ở mỗi lần gọi.

**Tại sao hữu ích:**
Buffer lớn tạo allocation pressure và có thể đẩy object vào Large Object Heap. Trong workload throughput cao, việc thuê lại array giúp giảm allocation và GC frequency, đặc biệt ở code xử lý payload lớn hoặc serialization pipeline.

**Ví dụ:**
```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);

try
{
    var read = await stream.ReadAsync(buffer, cancellationToken);
    Process(buffer.AsSpan(0, read));
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

**Lưu ý:**
Array thuê có thể lớn hơn kích thước yêu cầu và chứa dữ liệu cũ. Không đọc ngoài phạm vi hợp lệ; với dữ liệu nhạy cảm, cân nhắc `clearArray: true`. Đừng dùng pooling nếu profiling chưa cho thấy allocation là bottleneck.

### Tip 2 — Khi Redis cache stampede xảy ra, bảo vệ “miss path” chứ không chỉ tăng TTL

**Mẹo:**
Nếu một key hết hạn và hàng trăm request cùng miss rồi cùng truy vấn database, thêm cơ chế single-flight/local lock/distributed coordination phù hợp để chỉ một request rebuild cache trong một thời điểm.

**Tại sao hữu ích:**
Cache stampede biến một cache miss bình thường thành burst traffic xuống database hoặc external API. Tăng TTL chỉ trì hoãn thời điểm burst, không loại bỏ cơ chế gây ra nó.

**Ví dụ:**
Flow đơn giản:
```text
cache hit -> return
cache miss -> acquire per-key gate
           -> re-check cache
           -> load source
           -> set cache
           -> release gate
```

Với nhiều application instance, có thể cần distributed strategy; với instance-local duplicate request, local keyed lock đôi khi đã đủ.

**Lưu ý:**
Distributed lock thêm failure mode riêng: timeout, lock expiry, owner crash. Không biến mọi cache miss thành distributed coordination. Hãy chọn mức bảo vệ theo traffic và giá trị của nguồn dữ liệu.

### Tip 3 — Dùng Playwright trace để debug flaky E2E test thay vì chỉ rerun đến khi pass

**Mẹo:**
Khi E2E test fail ngẫu nhiên, bật Playwright tracing cho lần retry hoặc failure để xem DOM snapshot, network, action timeline và screenshot tại đúng thời điểm lỗi.

**Tại sao hữu ích:**
Flaky test thường liên quan race condition, selector không ổn định, API chậm hoặc state leak giữa test. Chỉ rerun có thể che symptom mà không cho evidence về nguyên nhân.

**Ví dụ:**
```ts
use: {
  trace: 'on-first-retry'
}
```

Sau khi test fail, trace có thể cho thấy button đã render nhưng overlay vẫn che, request `/api/orders` trả muộn hoặc test click trước khi state ổn định.

**Lưu ý:**
Không sửa flaky test bằng `waitForTimeout(3000)` theo phản xạ. Fixed sleep làm suite chậm và vẫn không deterministic. Ưu tiên wait theo observable condition, locator hoặc network/state signal rõ ràng.

### Tip 4 — Với Optimizely CMS, đừng để rendering logic gọi dữ liệu ngoài lặp lại cho từng block

**Mẹo:**
Nếu một page chứa nhiều block cùng cần product, pricing hoặc profile data từ external API, gom request ở service/query layer có cache hoặc batching thay vì mỗi block tự gọi dependency riêng.

**Tại sao hữu ích:**
Một page 20 block có thể vô tình tạo 20 outbound call, làm latency tăng tuyến tính và dễ gây rate-limit. CMS rendering thường che N+1 integration problem vì từng component nhìn riêng lẻ có vẻ hợp lý.

**Ví dụ:**
Thay vì:
```text
Block A -> Product API
Block B -> Product API
Block C -> Product API
```

có thể preload/batch:
```text
Page request -> collect product IDs
             -> one batch query/cache lookup
             -> render blocks from prepared model
```

**Lưu ý:**
Đừng cache mọi external response vô thời hạn. Content freshness, personalization và editorial preview có thể cần bypass hoặc cache key khác. Cần xác định scope rõ: request cache, distributed cache hay source cache.

### Tip 5 — Khi Lighthouse báo LCP chậm, xác định resource gây LCP trước khi tối ưu chung chung

**Mẹo:**
Dùng Chrome DevTools/Lighthouse để xác định chính xác element nào là Largest Contentful Paint và request chain của nó trước khi nén toàn bộ bundle hoặc thêm CDN theo cảm tính.

**Tại sao hữu ích:**
LCP có thể chậm vì hero image quá lớn, preload sai, server response chậm hoặc JavaScript chặn render. Mỗi nguyên nhân cần giải pháp khác nhau; cùng một score không nói trực tiếp bottleneck nằm ở frontend hay backend.

**Ví dụ:**
Nếu LCP element là hero image:
```text
TTFB: 180 ms
image discovered: +900 ms
image download: 1.8 s
render delay: 200 ms
```

có thể ưu tiên preload đúng asset, responsive image, kích thước phù hợp và tránh lazy-load cho image above-the-fold.

**Lưu ý:**
Không tối ưu chỉ theo Lighthouse lab score. So sánh với real-user Core Web Vitals nếu có, vì network/device thực tế và cache state khác lab environment.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service: chọn theo execution model, không theo độ “cloud-native”

**Khái niệm:**
Azure Functions phù hợp cho event-driven workload có execution rời rạc, scale theo trigger và ít state local. Worker Service phù hợp hơn khi process chạy liên tục, cần lifecycle chủ động, long-running coordination hoặc kiểm soát resource ổn định.

**Vấn đề nó giải quyết:**
Team thường chọn Functions chỉ vì serverless hoặc chọn Worker chỉ vì quen .NET. Cả hai đều có thể xử lý background job, nhưng failure model, scaling và operational behavior khác nhau.

**Ví dụ thực tế:**
Resize image sau khi blob upload có thể hợp với Azure Functions. Một consumer cần giữ local in-memory scheduler, xử lý connection lâu dài và kiểm soát concurrency chi tiết có thể phù hợp hơn với Worker Service trên App Service/Kubernetes/VM.

**Trade-off:**
Functions giảm infrastructure management và scale tốt với burst, nhưng có cold start, execution/runtime constraint và debugging distributed hơn. Worker Service cho control rõ hơn nhưng phải tự quản deployment, scaling và capacity.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và idempotency của Function/Worker handler. Senior / Technical developer phải chọn dựa trên traffic shape, execution duration, cost, failure recovery, concurrency control và operational ownership — không dựa trên nhãn serverless.

### Design 2 — Normalization vs denormalization: tối ưu theo write invariant và read shape

**Khái niệm:**
Normalization giảm duplication và bảo vệ consistency ở write model; denormalization chủ động lưu dữ liệu lặp hoặc read model riêng để phục vụ query nhanh hơn. Đây là trade-off giữa consistency đơn giản và read efficiency.

**Vấn đề nó giải quyết:**
Một schema chuẩn hóa cao có thể yêu cầu nhiều join cho dashboard/query nóng. Ngược lại, denormalize quá sớm tạo nhiều bản sao dữ liệu cần đồng bộ và làm update logic khó hơn.

**Ví dụ thực tế:**
Order nên lưu `ProductNameAtPurchase` như snapshot dù Product hiện tại có thể đổi tên. Đây là denormalization có business meaning, không chỉ performance optimization. Còn profile customer hiện tại có thể vẫn nên tham chiếu source-of-truth thay vì copy vào mọi table.

**Trade-off:**
Normalization giảm update anomaly và giữ invariant tập trung nhưng có thể tăng join/query cost. Denormalization tăng read performance và autonomy của read model nhưng đổi lại synchronization, storage và stale-data risk.

**Middle → Senior insight:**
Middle developer cần hiểu dependency dữ liệu và tránh copy field tùy tiện. Senior / Technical developer phải phân biệt snapshot business hợp lệ, cache/read model và duplicate source-of-truth; đồng thời xác định cơ chế đồng bộ và consistency tolerance rõ ràng.

### Design 3 — Transaction boundary nên bám theo business invariant, không theo số lượng repository/service call

**Khái niệm:**
Một transaction nên bao trùm các thay đổi cần cùng thành công hoặc cùng thất bại để giữ business invariant. Boundary không nên được xác định máy móc theo từng repository method hay từng application service.

**Vấn đề nó giải quyết:**
Nếu mỗi repository tự `SaveChanges`, workflow tạo Order rồi trừ Inventory có thể commit một nửa khi bước sau lỗi. Ngược lại, transaction quá rộng bao gồm external HTTP call sẽ giữ lock lâu và tăng contention.

**Ví dụ thực tế:**
Trong cùng database:
```text
Create Order
Reserve local Inventory row
Insert OutboxMessage
COMMIT
```

Sau commit, payment hoặc external integration chạy ngoài transaction và dùng retry/idempotency/compensation phù hợp.

**Trade-off:**
Transaction boundary đúng giúp invariant rõ và rollback đơn giản, nhưng transaction càng rộng càng tăng lock duration và coupling. Tách boundary giảm contention nhưng có thể chuyển consistency problem sang eventual consistency và workflow recovery.

**Middle → Senior insight:**
Middle developer cần biết operation nào phải atomic và tránh `SaveChanges` rải rác. Senior / Technical developer phải xác định invariant thật, điểm commit hợp lý, external side effect nào phải tách ra và khi nào cần Outbox/Saga thay vì kéo transaction dài hơn.
