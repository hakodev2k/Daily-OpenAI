# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Chẩn đoán ThreadPool starvation bằng evidence thay vì chỉ tăng thread

**Mẹo:**
Khi ASP.NET Core latency tăng mạnh nhưng CPU chưa cao, kiểm tra ThreadPool queue length, request duration, blocking call và số thread trước khi chỉnh cấu hình ThreadPool.

**Tại sao hữu ích:**
ThreadPool starvation thường xảy ra khi worker thread bị giữ bởi synchronous I/O, `.Result`, `.Wait()` hoặc lock kéo dài. Khi request mới phải chờ thread rảnh, latency tăng dù CPU vẫn còn dư.

**Ví dụ:**
Một endpoint gọi:
```csharp
var response = httpClient.GetAsync(url).Result;
```

Dưới load cao, nhiều request cùng block worker thread. Thay bằng async end-to-end:
```csharp
var response = await httpClient.GetAsync(url, cancellationToken);
```

Khi điều tra production, đối chiếu latency spike với ThreadPool queue và blocking stack trace trước khi kết luận database hay network là nguyên nhân.

**Lưu ý:**
Không mặc định tăng minimum threads để “fix” starvation. Cách đó có thể che symptom, tăng context switching và làm dependency downstream chịu burst lớn hơn. Ưu tiên loại bỏ blocking root cause.

### Tip 2 — Dùng `INCLUDE` trong SQL Server khi query cần covering index nhưng không nên mở rộng key

**Mẹo:**
Khi query filter/sort bằng một số cột nhưng select thêm nhiều cột khác, cân nhắc đặt cột chỉ phục vụ projection vào `INCLUDE` thay vì đưa tất cả vào index key.

**Tại sao hữu ích:**
Một covering index có thể tránh key lookup, nhưng key quá rộng làm index lớn, tốn memory và tăng write cost. `INCLUDE` cho phép chứa dữ liệu cần trả về mà không ảnh hưởng key order và key width theo cùng cách.

**Ví dụ:**
Query:
```sql
SELECT OrderId, CreatedAt, Total, CustomerName
FROM Orders
WHERE TenantId = @TenantId
ORDER BY CreatedAt DESC;
```

Một index có thể là:
```sql
CREATE INDEX IX_Orders_TenantId_CreatedAt
ON Orders (TenantId, CreatedAt DESC)
INCLUDE (OrderId, Total, CustomerName);
```

**Lưu ý:**
Covering index không phải càng nhiều cột càng tốt. Mỗi cột `INCLUDE` làm index lớn hơn và tăng I/O/write amplification. Xem actual execution plan và workload trước khi thêm.

### Tip 3 — Với cookie authentication, hiểu CSRF trước khi chỉ tập trung vào CORS

**Mẹo:**
Nếu browser tự động gửi authentication cookie, bảo vệ state-changing request bằng anti-forgery strategy phù hợp thay vì giả định CORS đã ngăn được CSRF.

**Tại sao hữu ích:**
CORS kiểm soát khả năng JavaScript từ origin khác đọc/gọi resource theo browser policy, nhưng cookie có thể vẫn được gửi tự động trong một số cross-site request. CSRF khai thác chính cơ chế browser gửi credential này.

**Ví dụ:**
Với form hoặc endpoint dùng cookie auth, anti-forgery token hoặc double-submit-style mechanism giúp server xác nhận request thực sự phát sinh từ application hợp lệ, không chỉ dựa trên cookie.

**Lưu ý:**
Không áp anti-forgery token máy móc cho API dùng bearer token trong `Authorization` header vì threat model khác. Cần phân biệt cookie-based auth, SameSite behavior, CORS và CSRF thay vì coi chúng là một cơ chế.

### Tip 4 — Trong Optimizely CMS, tránh gọi service/database lặp lại trong property rendering nóng

**Mẹo:**
Với component hoặc block render trên nhiều trang, tránh đặt query nặng, external call hoặc lookup lặp lại trong getter/property renderer nếu dữ liệu có thể được batch, cache hoặc chuẩn bị ở application layer.

**Tại sao hữu ích:**
CMS page thường gồm nhiều block. Một lookup tưởng nhỏ nhưng chạy cho từng block có thể tạo N+1 ở tầng CMS/service và làm TTFB tăng mạnh khi trang có nhiều component.

**Ví dụ:**
Nếu 20 product blocks mỗi block gọi product API riêng, tổng page render có thể tạo 20 outbound request. Thay vào đó, collect product IDs rồi batch fetch một lần hoặc dùng request-scoped cache cho cùng key.

**Lưu ý:**
Không cache vô thời hạn content có editorial freshness requirement. Cần hiểu dependency invalidation, personalization và preview mode trước khi thêm cache để tránh editor thấy dữ liệu stale.

### Tip 5 — Khi production lỗi sau deploy, dùng log correlation để phân biệt regression với dependency incident

**Mẹo:**
Khi error rate tăng ngay sau deployment, so sánh request telemetry theo version/build, correlation ID và dependency failure thay vì mặc định rollback ngay hoặc mặc định đổ lỗi cho external service.

**Tại sao hữu ích:**
Hai sự kiện có thể trùng thời điểm nhưng không có quan hệ nhân quả. Version tag và distributed trace giúp xác định lỗi chỉ xảy ra trên instance mới, ở tất cả version, hay bắt đầu từ một dependency cụ thể.

**Ví dụ:**
Nếu `5xx` tăng nhưng trace cho thấy cả old và new version đều timeout ở cùng payment API, khả năng cao là dependency incident. Nếu chỉ build mới có `NullReferenceException` trước outbound call, đó là regression nội bộ.

**Lưu ý:**
Không chờ tới incident mới nghĩ về telemetry schema. Build/version, environment, correlation ID và dependency metadata nên được thiết kế trước để khi sự cố xảy ra có evidence đủ dùng.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service

**Khái niệm:**
Azure Functions phù hợp với event-driven execution có trigger rõ, scale theo workload và operational model serverless. Worker Service phù hợp hơn khi process cần chạy liên tục, giữ state/lifecycle dài hoặc kiểm soát execution host sâu hơn.

**Vấn đề nó giải quyết:**
Team thường chọn Functions cho mọi background task vì triển khai nhanh, nhưng workload chạy lâu, polling liên tục hoặc cần custom concurrency có thể không khớp serverless execution model.

**Ví dụ thực tế:**
Một blob upload cần resize image độc lập theo event phù hợp với Azure Function. Một service luôn mở connection tới external feed, duy trì in-memory state và xử lý stream liên tục có thể hợp với Worker Service hơn.

**Trade-off:**
Functions giảm infrastructure management và scale linh hoạt, nhưng có cold start, execution/runtime constraint và behavior retry cần hiểu rõ. Worker Service cho control tốt hơn nhưng bạn phải sở hữu scaling, hosting, deployment và health monitoring nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, cancellation và idempotency của từng model. Senior / Technical developer phải chọn dựa trên workload shape, latency requirement, execution duration, cost model, operational ownership và failure recovery thay vì theo xu hướng serverless.

### Design 2 — Normalization vs Denormalization theo read/write pressure

**Khái niệm:**
Normalization giảm duplication và giữ invariant dữ liệu rõ ràng; denormalization chủ động lặp dữ liệu để giảm join hoặc phục vụ read model nhanh hơn. Đây là trade-off theo workload, không phải lựa chọn đúng/sai tuyệt đối.

**Vấn đề nó giải quyết:**
Một schema chuẩn hóa cao có thể rất tốt cho transactional consistency nhưng gây query phức tạp cho dashboard hoặc search screen. Ngược lại, denormalize quá sớm tạo nhiều nơi phải cập nhật cùng một fact.

**Ví dụ thực tế:**
Order transaction giữ `CustomerId` tham chiếu Customer. Read model cho customer-service dashboard có thể copy `CustomerDisplayName` vào projection để tránh join nhiều nguồn trong mỗi request, miễn là chấp nhận eventual update khi tên khách hàng đổi.

**Trade-off:**
Normalization giảm inconsistency nhưng có thể tăng join cost và coupling query. Denormalization tối ưu read nhưng tăng storage, synchronization logic và risk stale data.

**Middle → Senior insight:**
Middle developer cần hiểu source of truth và không duplicate field tùy tiện. Senior / Technical developer phải quyết định nơi denormalize dựa trên query frequency, consistency SLA, update frequency, data ownership và cost đồng bộ.

### Design 3 — Contract Testing cho integration boundary thay vì mock mọi thứ

**Khái niệm:**
Contract Testing xác minh producer và consumer đồng thuận về API/message contract mà không cần chạy toàn bộ hệ thống end-to-end cho mọi thay đổi.

**Vấn đề nó giải quyết:**
Unit test với mock thường chỉ chứng minh code tương tác với mock mà chính team định nghĩa. Nếu provider đổi field, status code hoặc message schema, cả hai phía vẫn có thể pass unit test nhưng integration thật bị break.

**Ví dụ thực tế:**
Mobile backend kỳ vọng `GET /products/{id}` luôn trả `price.amount` và `price.currency`. Contract test có thể phát hiện provider đổi thành `unitPrice` trước khi release dù từng service test riêng vẫn xanh.

**Trade-off:**
Contract tests bắt breaking integration sớm và chạy nhẹ hơn full E2E, nhưng cần versioning, ownership và pipeline phối hợp. Chúng không thay thế integration test với database/network thật cho behavior phức tạp.

**Middle → Senior insight:**
Middle developer cần phân biệt unit mock với contract thực và giữ test theo observable interface. Senior / Technical developer phải xác định boundary nào đáng có contract test, quản lý compatibility/versioning và cân bằng contract, integration và E2E tests để tránh test suite vừa đắt vừa trùng lặp.
