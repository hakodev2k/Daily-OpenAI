# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng để `DbContext` sống qua nhiều business operations

**Mẹo:**
Giữ `DbContext` theo một unit of work ngắn và rõ ràng, thường tương ứng với một request hoặc một message-processing attempt. Với background worker, tạo scope mới cho từng work item thay vì giữ một context dùng lâu dài.

**Tại sao hữu ích:**
`DbContext` giữ change tracker, identity map và trạng thái entity. Context sống quá lâu làm tracker phình ra, tăng chi phí `DetectChanges`, giữ stale state và dễ tạo concurrency/lifetime bugs. Nó cũng không thread-safe.

**Ví dụ:**
Một `BackgroundService` đọc 10.000 messages không nên inject rồi tái sử dụng cùng `DbContext`. Mỗi message hoặc batch có transaction boundary riêng nên tạo DI scope, resolve context, xử lý rồi dispose scope.

**Lưu ý:**
Không biến việc tạo context thành cách che một transaction boundary sai. Nếu nhiều thay đổi bắt buộc atomic, chúng vẫn cần nằm trong cùng unit of work phù hợp.

### Tip 2 — Dùng `Cache-Control` theo semantics của response, không theo thói quen

**Mẹo:**
Thiết kế HTTP caching dựa trên việc response có public/private, có phụ thuộc user hay authorization và mức stale được chấp nhận. Đừng gắn một `max-age` chung cho mọi endpoint.

**Tại sao hữu ích:**
Browser/CDN cache đúng có thể giảm backend latency và traffic đáng kể, nhưng cache sai scope có thể phục vụ dữ liệu cá nhân cho người khác hoặc giữ content cũ quá lâu. Cache policy là một phần của API contract.

**Ví dụ:**
Trang product công khai có thể dùng `public, max-age` và validator như `ETag`; endpoint `/me/profile` phải được xem là user-specific và không được cache ở shared CDN chỉ vì GET được coi là cacheable về mặt HTTP.

**Lưu ý:**
`GET` không tự động đồng nghĩa “an toàn để shared-cache”. Kiểm tra `Vary`, cookies, authorization, query parameters và CDN configuration thực tế.

### Tip 3 — PostgreSQL index-only scan vẫn phụ thuộc visibility map

**Mẹo:**
Khi thiết kế covering index trong PostgreSQL, đừng giả định có đủ columns trong index là query sẽ luôn tránh heap access. Kiểm tra actual plan và heap fetches.

**Tại sao hữu ích:**
MVCC yêu cầu PostgreSQL xác định tuple có visible hay không. Index-only scan chỉ thực sự tránh đọc heap cho pages được visibility map xác nhận all-visible; workload update-heavy hoặc autovacuum không theo kịp có thể làm lợi ích thấp hơn kỳ vọng.

**Ví dụ:**
Một reporting query có index bao phủ `tenant_id`, `created_at`, `status` nhưng production vẫn có nhiều heap fetches. `EXPLAIN (ANALYZE, BUFFERS)` cùng vacuum statistics cho thấy table churn cao khiến visibility map chưa hỗ trợ index-only access như benchmark trên dữ liệu tĩnh.

**Lưu ý:**
Đừng thêm `INCLUDE` columns vô hạn để ép covering index. Index lớn làm tăng storage, cache pressure và write amplification; quyết định phải dựa trên read/write profile.

### Tip 4 — Source map production cần policy, không chỉ bật hoặc tắt

**Mẹo:**
Với Vue/React production build, quyết định source-map strategy cùng observability và security requirements: có thể tạo maps để error monitoring symbolicate stack trace nhưng không public chúng trực tiếp từ web server/CDN.

**Tại sao hữu ích:**
Không có source maps, minified stack trace làm production debugging khó. Public source maps lại có thể làm lộ source structure và implementation details. Build pipeline có thể upload artifact maps tới error-monitoring system rồi loại chúng khỏi public deployment.

**Ví dụ:**
CI build frontend tạo source maps, upload đúng artifact version tới monitoring service, sau đó deployment package chỉ chứa minified assets. Exception từ browser vẫn map được về TypeScript source tương ứng với release.

**Lưu ý:**
Source maps không phải nơi được phép chứa secrets; secrets vốn không được bundle vào frontend. Cũng cần versioning chính xác, nếu map và deployed JS lệch release thì stack trace sẽ gây hiểu nhầm.

### Tip 5 — Khi pod bị OOMKilled, xem memory limit và working set trước khi gọi đó là leak

**Mẹo:**
Trong Kubernetes, bắt đầu từ container termination reason, memory working set/RSS, configured limit và traffic pattern trước khi kết luận .NET process có memory leak.

**Tại sao hữu ích:**
OOMKilled nghĩa là container vượt giới hạn cgroup, không chứng minh managed heap tăng vô hạn. Burst allocations, native memory, large buffers, concurrency tăng hoặc limit đặt quá thấp đều có thể tạo cùng symptom.

**Ví dụ:**
API chỉ OOMKilled lúc batch export chạy. GC heap sau collection ổn định nhưng concurrent exports giữ nhiều compressed buffers và container limit là 512 MiB. Root cause là peak working set + concurrency, không phải object retention dài hạn.

**Lưu ý:**
Đừng chỉ tăng memory limit. Sau khi xác định peak source, cân nhắc streaming, bounded concurrency, allocation reduction hoặc capacity sizing; nếu heap thực sự tăng qua nhiều GC cycles thì mới đi sâu retention analysis.

## 🧠 Software Design

### Design 1 — API Composition hay materialized read model

**Khái niệm:**
Khi một màn hình cần dữ liệu từ nhiều bounded contexts, API Composition gọi các owners lúc read-time; materialized read model tổng hợp dữ liệu trước để query nhanh từ một model dành riêng cho đọc.

**Vấn đề nó giải quyết:**
UI thường cần một view không trùng với ownership của write model. Nếu frontend phải tự gọi nhiều services, latency, partial failure và coupling với backend topology tăng lên.

**Ví dụ thực tế:**
Order Details cần Ordering, Payment và Shipment. BFF có thể compose ba APIs nếu traffic thấp và freshness quan trọng; dashboard có hàng triệu reads có thể dùng projection cập nhật từ events để tránh fan-out mỗi request.

**Trade-off:**
Composition đơn giản hơn về data synchronization nhưng latency và availability phụ thuộc nhiều calls. Read model cho read performance và isolation tốt hơn nhưng thêm eventual consistency, storage, rebuild và event-processing complexity.

**Middle → Senior insight:**
Middle developer cần xử lý timeout/partial response hoặc projection update đúng. Senior / Technical developer phải chọn theo freshness, query volume, failure budget, ownership và operational cost thay vì mặc định CQRS/read model cho mọi UI.

### Design 2 — Consumer-driven compatibility cho event evolution

**Khái niệm:**
Event contract nên tiến hóa theo những gì consumers thực sự phụ thuộc, ưu tiên additive change và compatibility rules thay vì để producer tự do thay schema rồi yêu cầu mọi consumer nâng cấp đồng thời.

**Vấn đề nó giải quyết:**
Event tồn tại lâu hơn request HTTP và có thể nằm trong queue, replay hoặc được nhiều consumers dùng. Rename/remove field hoặc đổi semantics có thể phá consumer đang deploy độc lập và cả historical replay.

**Ví dụ thực tế:**
`OrderPlaced` cần thêm `salesChannel`. Producer thêm optional field với default semantics thay vì đổi tên field cũ ngay. Contract tests/schema governance xác minh các consumers hiện tại vẫn đọc được event mới trước rollout.

**Trade-off:**
Compatibility giảm coordinated deployment nhưng giữ legacy fields lâu hơn và cần schema governance. Version mới hoàn toàn có thể sạch hơn nhưng làm routing, migration, replay và dual-consumption phức tạp.

**Middle → Senior insight:**
Middle developer cần tránh breaking serialization changes và tolerant-reader assumptions nguy hiểm. Senior / Technical developer phải thiết kế versioning/deprecation policy, retention/replay strategy và xác định khi additive evolution không còn đủ.

### Design 3 — Bulkhead theo resource pool, không chỉ theo service name

**Khái niệm:**
Bulkhead Isolation giới hạn blast radius bằng cách tách hoặc giới hạn resource mà một workload có thể chiếm, ví dụ concurrency, connection pool, queue hoặc worker capacity.

**Vấn đề nó giải quyết:**
Một dependency chậm hoặc tenant nặng có thể chiếm toàn bộ threads/connections và khiến các luồng không liên quan thất bại dù bản thân chúng khỏe mạnh.

**Ví dụ thực tế:**
Report export chậm không được phép dùng hết database connections cần cho checkout. Hệ thống đặt bounded concurrency cho export và có worker/queue capacity riêng, bảo vệ critical traffic khi reporting workload tăng đột biến.

**Trade-off:**
Bulkhead tăng fault isolation nhưng làm capacity bị phân mảnh và thêm tuning/monitoring. Giới hạn quá thấp gây queueing không cần thiết; quá cao thì không còn bảo vệ resource quan trọng.

**Middle → Senior insight:**
Middle developer cần nhận biết shared-resource exhaustion và tuân thủ concurrency limits. Senior / Technical developer phải xác định resource nào thực sự cần isolation, ưu tiên workload theo business criticality và điều chỉnh limits từ telemetry thay vì chọn số tùy ý.
