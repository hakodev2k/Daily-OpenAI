# Daily Developer Tips & Design — 2026-09-16

## 🛠 Developer Tips & Tricks

### Tip 1 — Rate limiting theo đúng resource, không chỉ theo IP

**Mẹo:**
Với ASP.NET Core Rate Limiting, chọn partition key theo resource cần bảo vệ: authenticated user, tenant, API key hoặc endpoint class thay vì mặc định dùng IP cho mọi request.

**Tại sao hữu ích:**
Nhiều user có thể đi qua cùng NAT/proxy, còn attacker có thể phân tán request qua nhiều IP. Partition theo identity/business boundary giúp quota phản ánh đúng consumer và bảo vệ downstream dependency chính xác hơn.

**Ví dụ:**
```csharp
options.AddPolicy("per-user", context =>
    RateLimitPartition.GetFixedWindowLimiter(
        context.User.Identity?.Name ?? context.Connection.RemoteIpAddress?.ToString() ?? "anonymous",
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1)
        }));
```
Một API export đắt đỏ có thể cần policy riêng thấp hơn API đọc metadata.

**Lưu ý:**
Đừng coi rate limiting là authorization hoặc DDoS protection hoàn chỉnh. Khi chạy nhiều instance, limiter in-memory của từng process không tạo ra một global quota tuyệt đối.

### Tip 2 — Keyset pagination tránh chi phí OFFSET tăng dần

**Mẹo:**
Với bảng lớn và luồng “next page”, ưu tiên keyset pagination dựa trên một ordering ổn định thay vì `OFFSET ... FETCH` ngày càng lớn.

**Tại sao hữu ích:**
Database thường vẫn phải đi qua số lượng row bị offset trước khi lấy page tiếp theo. Keyset cho phép seek từ giá trị cuối của page trước và thường tận dụng index hiệu quả hơn.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp có thể bắt đầu bằng `(CreatedAt DESC, Id DESC)` tùy workload và database engine.

**Lưu ý:**
Ordering phải deterministic; chỉ dùng `CreatedAt` có thể bỏ/trùng row khi nhiều record cùng timestamp. Keyset cũng không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 500 theo số trang.

### Tip 3 — Dùng Playwright Trace cho flaky E2E thay vì chỉ chụp screenshot cuối

**Mẹo:**
Khi E2E test flaky trong CI, bật Playwright tracing cho retry/failure để giữ timeline gồm DOM snapshots, network, console và action history.

**Tại sao hữu ích:**
Screenshot cuối thường chỉ cho thấy trạng thái sau khi lỗi xảy ra. Trace giúp xác định request nào chậm, selector resolve sai, navigation nào chưa hoàn tất hoặc UI state thay đổi ở bước nào.

**Ví dụ:**
```ts
export default defineConfig({
  use: {
    trace: 'on-first-retry'
  },
  retries: 2
});
```
Khi test checkout fail trên CI nhưng pass local, trace có thể cho thấy `/api/cart` trả `409` trước khi nút Submit biến mất.

**Lưu ý:**
Đừng “fix” flaky test bằng cách tăng timeout hàng loạt. Trace có thể chứa dữ liệu nhạy cảm; kiểm soát retention và artifact access trong CI.

### Tip 4 — Phân biệt memory leak với allocation pressure bằng GC evidence

**Mẹo:**
Khi memory của .NET service tăng, đừng kết luận ngay là leak. Quan sát allocation rate, heap size sau GC, Gen 2 collections và LOH trước khi chọn hướng điều tra.

**Tại sao hữu ích:**
Allocation rate cao có thể làm GC chạy thường xuyên nhưng memory vẫn được thu hồi; leak/retention lại thể hiện object sống lâu và heap sau collection tiếp tục tăng. Hai vấn đề cần cách sửa khác nhau.

**Ví dụ:**
```bash
dotnet-counters monitor -p <PID> System.Runtime
```
Nếu Allocation Rate rất cao nhưng GC Heap Size ổn định, hãy tìm hot allocation. Nếu heap sau nhiều Gen 2 GC vẫn tăng, lấy dump và tìm retention path/root.

**Lưu ý:**
RSS/process memory không đồng nghĩa managed heap. Native allocations, buffers, mapped memory và runtime overhead cũng có thể làm process memory tăng.

### Tip 5 — Đừng log secret chỉ vì structured logging tiện

**Mẹo:**
Thiết kế logging để allowlist field an toàn; không serialize nguyên request, headers hoặc object authentication vào log production.

**Tại sao hữu ích:**
Structured logging làm dữ liệu dễ query nhưng cũng khiến token, cookie, password, PII hoặc connection string dễ bị đưa vào Application Insights/Elasticsearch và tồn tại lâu hơn request gốc.

**Ví dụ:**
```csharp
logger.LogInformation(
    "Payment request completed {PaymentId} {StatusCode} {ElapsedMs}",
    paymentId, statusCode, elapsedMs);
```
Log business identifiers cần thiết thay vì `Authorization`, full request body hoặc toàn bộ user object.

**Lưu ý:**
Masking bằng regex ở sink không phải lớp bảo vệ duy nhất; nested JSON và format mới có thể lọt qua. Tốt hơn là không tạo sensitive telemetry ngay từ nguồn.

## 🧠 Software Design

### Design 1 — CQRS chỉ khi read/write thực sự có áp lực khác nhau

**Khái niệm:**
CQRS tách read model và write model để mỗi phía tối ưu cho nhu cầu riêng. Giá trị nằm ở việc giải quyết asymmetry thực tế, không phải ở việc tạo thêm `Command`/`Query` class.

**Vấn đề nó giải quyết:**
Một hệ thống có write side cần invariant/domain logic phức tạp nhưng read side cần projection, denormalization hoặc scale khác biệt. Một model duy nhất bắt đầu làm cả hai phía khó tối ưu và khó hiểu.

**Ví dụ thực tế:**
E-commerce checkout ghi `Order` theo transaction boundary chặt, trong khi màn hình operations cần dashboard tổng hợp order, payment và shipment. Read model riêng có thể được cập nhật bất đồng bộ để query nhanh mà không làm aggregate write phình to.

**Trade-off:**
CQRS cho phép tối ưu và scale độc lập, nhưng tăng model duplication, synchronization, eventual consistency và operational complexity. CRUD application nhỏ thường không nhận đủ lợi ích để bù chi phí này.

**Middle → Senior insight:**
Middle developer cần giữ command/query responsibility rõ và hiểu consistency của read model. Senior / Technical developer phải chứng minh pressure nào đòi CQRS, quyết định mức tách phù hợp — từ logical separation trong Modular Monolith tới datastore riêng — và biết khi một model CRUD đơn giản là lựa chọn tốt hơn.

### Design 2 — Chọn Cosmos DB partition key theo access pattern và growth

**Khái niệm:**
Partition key không chỉ là field để phân nhóm document; nó quyết định cách dữ liệu và request được phân phối giữa logical/physical partitions, vì vậy là một quyết định kiến trúc khó sửa về sau.

**Vấn đề nó giải quyết:**
Một key có cardinality thấp hoặc traffic lệch có thể tạo hot partition, trong khi key không khớp query pattern làm nhiều request trở thành cross-partition query tốn RU và latency.

**Ví dụ thực tế:**
Multi-tenant SaaS lưu activity events. `TenantId` thuận tiện cho query theo tenant, nhưng một enterprise tenant tạo 60% traffic có thể trở thành hotspot. Một thiết kế như synthetic key `TenantId + bucket` có thể phân tán write, đổi lại query tenant-wide phải fan-out qua nhiều bucket.

**Trade-off:**
Key tốt cải thiện locality, throughput và cost predictability; key phân tán hơn có thể làm query/transaction phức tạp. Không có partition key tối ưu độc lập với workload.

**Middle → Senior insight:**
Middle developer cần hiểu query nào có partition key và tránh cross-partition scan vô ý. Senior / Technical developer phải dự báo data growth, tenant skew, transactional scope và RU distribution, benchmark workload đại diện rồi chọn key có đường migration chấp nhận được.

### Design 3 — Observability là contract vận hành, không phải “thêm log sau”

**Khái niệm:**
Observability design xác định trước telemetry nào cần để suy luận trạng thái hệ thống: metrics cho xu hướng/saturation, traces cho request flow và structured logs cho chi tiết sự kiện.

**Vấn đề nó giải quyết:**
Một service có thể chạy đúng trong test nhưng khi production latency tăng, team không biết thời gian nằm ở database, external API, queue hay code nội bộ. Logging ngẫu nhiên không tạo đủ evidence để chẩn đoán.

**Ví dụ thực tế:**
Checkout API phát trace xuyên qua ASP.NET Core → SQL → payment provider, metric `checkout.duration` theo percentile và error class, cùng correlation identifiers. Khi p99 tăng nhưng median ổn định, team có thể khoanh vùng dependency span thay vì đọc hàng nghìn log line.

**Trade-off:**
Telemetry tốt giảm MTTR và hỗ trợ capacity planning, nhưng có cost ingest/storage, cardinality risk, privacy risk và instrumentation maintenance. Thu thập mọi thứ không đồng nghĩa quan sát tốt hơn.

**Middle → Senior insight:**
Middle developer cần tạo structured telemetry có correlation và không làm lộ sensitive data. Senior / Technical developer phải xác định SLI/SLO, cardinality budget, sampling/retention, ownership và telemetry cần thiết cho các failure mode quan trọng thay vì tối đa hóa số lượng log.
