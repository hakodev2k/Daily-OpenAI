# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `DateOnly` / `TimeOnly` khi domain không có khái niệm timezone

**Mẹo:**
Nếu dữ liệu chỉ là ngày hoặc giờ độc lập, dùng `DateOnly` / `TimeOnly` thay vì ép mọi thứ vào `DateTime`.

**Tại sao hữu ích:**
Giảm bug do timezone conversion, `Kind`, midnight boundary và intent mơ hồ. Một ngày nghỉ `2026-08-17` không nên tự nhiên biến thành một timestamp UTC.

**Ví dụ:**
```csharp
public sealed record LeaveRequest(
    DateOnly StartDate,
    DateOnly EndDate);

var start = new DateOnly(2026, 8, 17);
```

**Lưu ý:**
Nếu dữ liệu đại diện cho một thời điểm thực trên timeline, vẫn cần `DateTimeOffset` hoặc instant type phù hợp. Đừng dùng `DateOnly` chỉ để tránh xử lý timezone đúng cách.

### Tip 2 — Propagate `HttpContext.RequestAborted` xuống I/O dài

**Mẹo:**
Trong ASP.NET Core, truyền `HttpContext.RequestAborted` hoặc cancellation token tương đương xuống database, HTTP call và stream operation khi request bị client hủy.

**Tại sao hữu ích:**
Tránh tiếp tục tiêu CPU, DB connection hoặc external quota cho request mà client đã đóng kết nối.

**Ví dụ:**
```csharp
app.MapGet("/reports/{id}", async (
    int id,
    HttpContext context,
    ReportService service) =>
{
    var report = await service.LoadAsync(
        id,
        context.RequestAborted);

    return Results.Ok(report);
});
```

**Lưu ý:**
Không propagate cancellation mù quáng qua operation đã commit một phần business state. Một số workflow cần chuyển sang background completion/recovery thay vì dừng giữa chừng.

### Tip 3 — Dùng `git log --cherry` để tìm commit tương đương giữa hai branch

**Mẹo:**
Khi release branch chứa nhiều cherry-pick với SHA khác main, dùng `--cherry` để ẩn các patch tương đương và tập trung vào thay đổi thật sự chỉ tồn tại ở một phía.

**Tại sao hữu ích:**
Giảm noise khi audit backport hoặc chuẩn bị merge release branch trở lại main.

**Ví dụ:**
```bash
git log --left-right --cherry-pick \
  --oneline main...release/1.8
```

**Lưu ý:**
Git so patch equivalence, không hiểu semantic equivalence. Hai commit viết khác nhưng behavior giống nhau vẫn có thể xuất hiện như khác biệt.

### Tip 4 — Dùng `getent hosts` khi muốn biết application Linux sẽ resolve hostname thế nào

**Mẹo:**
Nếu `dig` trả kết quả đúng nhưng application vẫn resolve khác, kiểm tra `getent hosts` vì nó đi qua Name Service Switch (`/etc/nsswitch.conf`) giống nhiều application Linux hơn.

**Tại sao hữu ích:**
Có thể phát hiện `/etc/hosts`, mDNS, LDAP/NSS hoặc resolver ordering đang override DNS mà `dig` không thể hiện.

**Ví dụ:**
```bash
getent hosts api.internal.local
```

So sánh với:

```bash
dig api.internal.local
```

**Lưu ý:**
Resolver behavior còn phụ thuộc runtime/container. Hãy chạy command trong đúng network namespace/container nơi application đang chạy.

### Tip 5 — Chống path traversal bằng canonical path, không chỉ bằng string check

**Mẹo:**
Khi user cung cấp relative path để đọc/ghi file, normalize bằng `Path.GetFullPath()` rồi xác nhận kết quả vẫn nằm dưới root được phép.

**Tại sao hữu ích:**
String check kiểu `Contains("..")` dễ bị bypass bởi separator, encoding hoặc path normalization khác nhau.

**Ví dụ:**
```csharp
var root = Path.GetFullPath(uploadRoot);
var target = Path.GetFullPath(
    Path.Combine(root, userRelativePath));

if (!target.StartsWith(
        root + Path.DirectorySeparatorChar,
        StringComparison.Ordinal))
{
    throw new UnauthorizedAccessException();
}
```

**Lưu ý:**
Cần tính đến case-sensitivity, symlink/reparse point và platform semantics. Với boundary security cao, canonical path check chỉ là một lớp phòng vệ.

## 🧠 Software Design

### Design 1 — Temporal Table khác Soft Delete vì mục tiêu là lịch sử thay đổi

**Khái niệm:**
System-versioned Temporal Table lưu lại version trước của row khi dữ liệu được update/delete, cho phép query trạng thái tại một thời điểm trong quá khứ.

**Vấn đề nó giải quyết:**
Soft Delete chỉ cho biết record hiện đang “đã xóa”, nhưng không tự trả lời entity đã có giá trị gì trước mỗi lần thay đổi.

**Ví dụ thực tế:**
Employee thay đổi Office, Title và Manager nhiều lần. Temporal history cho phép điều tra:

```text
Employee 123 lúc 2026-06-01 thuộc office nào?
```

mà không cần tự viết history insert ở mọi code path.

**Trade-off:**
Temporal history mạnh cho audit/debug và point-in-time query, nhưng tăng storage, retention management và migration complexity. Nó cũng không tự ghi actor/reason như một audit event giàu ngữ nghĩa.

**Middle → Senior insight:**
Middle developer nên phân biệt “giữ record đã xóa” với “lưu mọi version của record”. Senior developer phải chọn temporal history, business history hay audit log theo câu hỏi cần trả lời, retention và compliance requirement.

### Design 2 — Data Locality có thể quan trọng hơn normalization tuyệt đối trên hot read path

**Khái niệm:**
Data Locality đặt dữ liệu thường được đọc cùng nhau gần nhau về storage/read model để giảm join, network hop hoặc random I/O, dù điều đó có thể tạo controlled denormalization.

**Vấn đề nó giải quyết:**
Một model normalized rất đẹp có thể buộc request latency-sensitive thực hiện nhiều join/service call chỉ để dựng một màn hình hoặc response phổ biến.

**Ví dụ thực tế:**
Dashboard cần `EmployeeName`, `OfficeName`, `ProjectName` cho hàng nghìn timesheet rows. Một read model denormalized có thể lưu sẵn các display field thay vì mỗi request join qua nhiều bảng/service.

**Trade-off:**
Data locality cải thiện read performance và giảm dependency fan-out, nhưng dữ liệu duplicate cần synchronization và có thể stale. Normalize vẫn phù hợp hơn cho source-of-truth write model có invariant mạnh.

**Middle → Senior insight:**
Middle developer nên biết normalization là công cụ, không phải mục tiêu tuyệt đối. Senior developer phải cân nhắc read/write ratio, freshness SLA, update fan-out và ownership trước khi denormalize.

### Design 3 — Admission Control nên dựa trên cost của request, không chỉ số request

**Khái niệm:**
Admission Control quyết định workload nào được phép vào hệ thống khi capacity hữu hạn. Request count đơn thuần thường không phản ánh cost thật vì một request export có thể đắt hơn hàng trăm request lookup.

**Vấn đề nó giải quyết:**
Rate limit kiểu “100 request/second cho mọi endpoint” có thể vẫn làm hệ thống sập nếu vài request cực nặng chiếm toàn bộ CPU, DB connections hoặc memory.

**Ví dụ thực tế:**
API có thể tính weighted cost:

```text
GET /employee/{id}     = 1 unit
POST /reports/export   = 20 units
POST /bulk-import      = 50 units
```

Mỗi tenant/workload chỉ được dùng một budget nhất định trong cửa sổ thời gian.

**Trade-off:**
Cost-aware admission bảo vệ capacity tốt hơn và công bằng hơn giữa workload, nhưng cần telemetry, cost model và tuning. Cost estimate sai có thể throttle nhầm request rẻ hoặc cho request đắt đi qua quá nhiều.

**Middle → Senior insight:**
Middle developer nên phân biệt rate limiting với capacity protection. Senior developer phải xác định bottleneck thực, đo request cost và kết hợp quota, concurrency limit, queueing và load shedding theo SLO.
