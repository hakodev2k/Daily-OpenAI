# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống database connection pooling

**Mẹo:**
Phân biệt `AddDbContextPool` của EF Core với connection pooling của database provider. `DbContext` pooling tái sử dụng instance/context state sau khi EF reset nó; connection pooling tái sử dụng physical database connections. Chỉ bật context pooling khi profiling cho thấy context creation là chi phí đáng kể và code không giữ state theo request trong `DbContext`.

**Tại sao hữu ích:**
Nhầm hai cơ chế dễ dẫn tới tối ưu sai chỗ. Một API bị connection-pool exhaustion sẽ không được chữa bằng cách pool thêm `DbContext`; ngược lại, context pooling có thể giảm allocation/setup overhead ở hot path nhưng không làm query SQL nhanh hơn.

**Ví dụ:**
Production có timeout khi mở connection và telemetry cho thấy active connections chạm giới hạn. Việc đổi `AddDbContext` sang `AddDbContextPool` không giải quyết root cause; team phải kiểm tra transaction kéo dài, query latency, connection lifetime và pool settings của provider.

**Lưu ý:**
Không lưu tenant-specific hoặc request-specific mutable state trực tiếp trong pooled `DbContext` mà không có chiến lược reset đúng. Đo trước khi bật; với nhiều ứng dụng, database I/O lớn hơn rất nhiều so với chi phí tạo context.

### Tip 2 — `ProblemDetails` nên là contract lỗi ổn định, không phải nơi dump exception

**Mẹo:**
Chuẩn hóa API errors bằng `ProblemDetails` với `type`, `title`, `status`, business/error code và correlation identifier phù hợp; giữ stack trace, SQL, internal exception message trong telemetry thay vì response production.

**Tại sao hữu ích:**
Client cần contract có thể xử lý bằng code, còn operator cần diagnostic detail. Trộn hai nhu cầu khiến API vừa khó version vừa có nguy cơ lộ implementation, query, path hoặc dữ liệu nhạy cảm. Error code ổn định cũng giúp frontend không phải parse message text.

**Ví dụ:**
Conflict khi cập nhật order trả `409` với code `ORDER_VERSION_CONFLICT` và trace ID. Application Insights chứa exception cùng trace ID để điều tra; mobile client chỉ dựa vào status/code để quyết định reload order.

**Lưu ý:**
Đừng biến mọi exception thành `500` giống nhau hoặc expose `Exception.Message` trực tiếp. Validation, authorization, concurrency và dependency failures có semantics khác nhau; mapping phải nhất quán nhưng không che mất status phù hợp.

### Tip 3 — PostgreSQL/SQL Server deadlock cần đọc wait graph, không chỉ retry

**Mẹo:**
Retry deadlock victim có thể tăng resilience, nhưng investigation phải xác định resources và lock order tạo cycle. Thu deadlock graph/diagnostics, đối chiếu transaction boundaries, statement order và indexes trước khi sửa.

**Tại sao hữu ích:**
Deadlock không đơn giản là “database quá tải”; hai transactions có thể giữ resource mà transaction kia cần theo thứ tự ngược nhau. Retry xử lý symptom cho request hiện tại nhưng deadlock frequency cao vẫn làm tăng latency, rollback work và tải database.

**Ví dụ:**
Transaction A update `Orders` rồi `Inventory`, transaction B update `Inventory` rồi `Orders`. Deadlock graph xác nhận cycle. Chuẩn hóa access order và rút ngắn transaction giải quyết nguyên nhân; retry với bounded backoff chỉ còn là safety net cho trường hợp hiếm.

**Lưu ý:**
Không tăng isolation hoặc thêm lock hint theo cảm tính. Missing index cũng có thể mở rộng lock footprint; luôn xem execution plan và transaction duration cùng deadlock evidence.

### Tip 4 — Kubernetes `readiness` và `liveness` trả lời hai câu hỏi khác nhau

**Mẹo:**
Dùng readiness để quyết định Pod có nên nhận traffic; dùng liveness để phát hiện process bị kẹt đến mức restart là biện pháp hợp lý. Đừng copy cùng một deep dependency check cho cả hai probes.

**Tại sao hữu ích:**
Nếu liveness phụ thuộc trực tiếp vào SQL hoặc external API, một dependency outage có thể khiến toàn bộ Pods restart liên tục, biến lỗi downstream thành self-inflicted outage. Readiness có thể tạm rút instance khỏi traffic mà không phá process khỏe mạnh.

**Ví dụ:**
API mất kết nối tới dependency bắt buộc cho request path. Readiness chuyển false để load balancer ngừng gửi traffic; liveness vẫn true nếu process/event loop khỏe. Khi dependency phục hồi, Pod có thể trở lại ready mà không cần restart storm.

**Lưu ý:**
Readiness quá nhạy cũng có thể loại toàn bộ replicas cùng lúc. Thiết kế probes theo failure mode, startup behavior và khả năng degrade của service; với startup chậm, cân nhắc startup probe thay vì nới liveness vô hạn.

### Tip 5 — AI-generated migration phải được kiểm tra bằng schema diff và dữ liệu thật đại diện

**Mẹo:**
Khi dùng AI coding agent để tạo EF Core/database migration, kiểm tra generated SQL, lock/data-loss risk, backward compatibility và chạy trên dataset có kích thước/phân bố gần production trước khi chấp nhận.

**Tại sao hữu ích:**
Agent có thể tạo code compile đúng nhưng giả định rename là drop/add, backfill trong một transaction khổng lồ hoặc thêm `NOT NULL` trước khi dữ liệu cũ được xử lý. Migration failure thường xảy ra ở deployment boundary, nơi rollback khó hơn code bug thông thường.

**Ví dụ:**
Agent đổi `CustomerName` thành `DisplayName` bằng drop/add. Review schema diff phát hiện nguy cơ mất dữ liệu; team chuyển sang expand/backfill/switch/contract và đo thời gian backfill trên snapshot đại diện trước release.

**Lưu ý:**
Test migration trên empty database là chưa đủ. Luôn kiểm tra upgrade từ schema đang chạy thực tế và, khi cần, downgrade/rollback strategy; AI output là proposal cần verification chứ không phải authority.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho idempotent message consumption

**Khái niệm:**
Inbox Pattern lưu identity/trạng thái của message đã xử lý ở phía consumer, thường trong cùng transaction với business changes, để duplicate delivery không tạo duplicate side effect. Nó bổ sung cho at-least-once messaging thay vì giả định broker chỉ giao một lần.

**Vấn đề nó giải quyết:**
Consumer có thể commit database rồi crash trước khi broker nhận acknowledgement. Message được giao lại và handler chạy lần nữa; nếu operation như cấp voucher hoặc tạo invoice không idempotent, duplicate trở thành lỗi nghiệp vụ.

**Ví dụ thực tế:**
Consumer nhận `OrderPaid` có `MessageId`. Trong một local transaction, service kiểm tra/insert Inbox record và tạo fulfillment state. Delivery thứ hai thấy `MessageId` đã hoàn tất nên không tạo shipment lần nữa.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, unique constraint, cleanup/retention và quyết định xử lý message đang `Processing` hoặc failed. Nó không tự giải quyết mọi external side effect nếu side effect nằm ngoài cùng transaction boundary.

**Middle → Senior insight:**
Middle developer cần implement deduplication atomically và hiểu retry semantics. Senior / Technical developer phải xác định message identity, retention window, transaction boundary, concurrency behavior và cách phối hợp Inbox với Outbox/third-party effects để guarantee thực sự phù hợp business.

### Design 2 — Modular Monolith trước Microservices khi boundary chưa đủ trưởng thành

**Khái niệm:**
Modular Monolith giữ một deployment unit nhưng chia hệ thống thành modules có ownership, contracts và dependency rules rõ. Nó cho phép luyện service boundaries ở mức code/domain trước khi trả operational cost của distributed deployment.

**Vấn đề nó giải quyết:**
Tách microservices quá sớm khi domain boundaries còn thay đổi tạo network contracts, distributed data và deployment coordination ở những nơi vốn chỉ cần refactor local. Ngược lại, monolith không modular dễ trở thành tightly coupled codebase khó tiến hóa.

**Ví dụ thực tế:**
E-commerce tách Catalog, Ordering và Reviews thành modules trong cùng application/database deployment, cấm direct cross-module entity access và giao tiếp qua explicit application contracts. Chỉ module có scaling/ownership/release pressure rõ mới được cân nhắc extract sau.

**Trade-off:**
Modular Monolith đơn giản vận hành hơn và refactor boundary rẻ hơn, nhưng không có independent scaling/deployment thật sự và cần discipline/tooling để ngăn dependency erosion. Microservices mang isolation/independence nhưng thêm latency, observability, messaging, consistency và platform overhead.

**Middle → Senior insight:**
Middle developer cần tôn trọng module boundaries và tránh shared-domain shortcuts. Senior / Technical developer phải đánh giá coupling, team topology, scaling, data ownership và deployment pressure; extraction phải giải quyết constraint đo được, không phải chạy theo architecture trend.

### Design 3 — Optimistic concurrency là business conflict detection, không chỉ EF Core feature

**Khái niệm:**
Optimistic concurrency cho phép nhiều readers làm việc song song nhưng phát hiện khi state đã thay đổi trước lúc write, thường bằng version/token trong điều kiện update. Sau conflict, hệ thống phải quyết định reload, merge, retry hay yêu cầu user xử lý dựa trên semantics nghiệp vụ.

**Vấn đề nó giải quyết:**
Hai users đọc cùng một record rồi cùng cập nhật có thể gây lost update: người ghi sau âm thầm đè thay đổi của người trước. Transaction isolation thông thường không bảo vệ workflow kéo dài qua nhiều HTTP requests.

**Ví dụ thực tế:**
Editor A và B cùng mở product version 12. A lưu và tạo version 13. B gửi update dựa trên version 12; `UPDATE ... WHERE Id = @id AND Version = 12` ảnh hưởng 0 rows, API trả conflict thay vì ghi đè dữ liệu của A.

**Trade-off:**
Optimistic concurrency tránh giữ lock dài và phù hợp khi conflict hiếm, nhưng buộc application thiết kế conflict UX/retry semantics. Auto-retry mù quáng có thể tái áp dụng command lên state mới và vi phạm intent; pessimistic locking có thể hợp lý hơn cho một số critical, short-lived workflows.

**Middle → Senior insight:**
Middle developer cần cấu hình concurrency token và xử lý conflict đúng. Senior / Technical developer phải phân biệt technical retry với business merge, chọn conflict granularity và quyết định optimistic hay pessimistic strategy dựa trên contention, invariant và user workflow.
