# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `Task.Run` để bọc I/O async trong ASP.NET Core

**Mẹo:**
Nếu operation đã có API bất đồng bộ như `ReadAsync`, `ExecuteReaderAsync`, `SendAsync` hoặc `SaveChangesAsync`, hãy `await` trực tiếp thay vì bọc nó trong `Task.Run`.

**Tại sao hữu ích:**
`Task.Run` chỉ đẩy delegate sang ThreadPool. Với I/O async thật, thread không cần bị giữ trong thời gian chờ I/O. Bọc thêm `Task.Run` tạo scheduling overhead, làm khó cancellation/context propagation và có thể góp phần vào ThreadPool pressure dưới tải cao.

**Ví dụ:**
```csharp
// Không cần thiết
var order = await Task.Run(() => repository.LoadAsync(id, ct), ct);

// Tốt hơn
var order = await repository.LoadAsync(id, ct);
```

**Lưu ý:**
`Task.Run` vẫn có chỗ dùng cho CPU-bound work cần tách khỏi request thread, nhưng với workload CPU nặng kéo dài trong web app, thường nên cân nhắc background processing hoặc worker riêng thay vì đẩy vô hạn vào ThreadPool.

### Tip 2 — Với SQL Server, tránh predicate không SARGable nếu muốn tận dụng index seek

**Mẹo:**
Khi lọc theo cột đã index, tránh bọc cột trong function nếu có thể viết điều kiện tương đương trực tiếp trên giá trị gốc.

**Tại sao hữu ích:**
Optimizer thường tận dụng index hiệu quả hơn khi predicate có thể chuyển thành range seek trực tiếp. Nếu áp dụng function lên từng row, database có thể phải scan nhiều dữ liệu hơn vì không thể dùng cấu trúc index theo cách mong muốn.

**Ví dụ:**
```sql
-- Kém thân thiện với index
WHERE CAST(CreatedAt AS date) = @Date

-- Tốt hơn
WHERE CreatedAt >= @Date
  AND CreatedAt < DATEADD(day, 1, @Date)
```

**Lưu ý:**
Không phải mọi function đều khiến index vô dụng trong mọi engine/version. Luôn kiểm tra actual execution plan và logical reads thay vì áp dụng quy tắc này máy móc.

### Tip 3 — Khi dùng `HttpClient`, phân biệt request timeout với DNS/connection lifetime

**Mẹo:**
Trong service gọi third-party API lâu dài, dùng `IHttpClientFactory` hoặc `SocketsHttpHandler` với connection lifetime phù hợp thay vì tạo `new HttpClient()` cho mỗi request hoặc giữ một handler vĩnh viễn mà không cân nhắc DNS rotation.

**Tại sao hữu ích:**
Tạo client/handler liên tục có thể làm tăng socket churn; ngược lại connection giữ quá lâu có thể tiếp tục dùng endpoint cũ sau khi DNS thay đổi. `PooledConnectionLifetime` cho phép connection được tái tạo theo chu kỳ mà vẫn hưởng lợi từ pooling.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient("Catalog")
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)
    });
```

**Lưu ý:**
Đừng chọn 5 phút theo thói quen. Giá trị hợp lý phụ thuộc DNS TTL, load balancer, infrastructure và traffic pattern. Request timeout và connection lifetime giải quyết hai vấn đề khác nhau.

### Tip 4 — Với Git conflict lớn, xác định “ý định thay đổi” trước khi chọn `ours` hoặc `theirs`

**Mẹo:**
Khi merge conflict liên quan nhiều dòng refactor, đừng giải bằng cách chọn nguyên block `ours` hoặc `theirs` chỉ để compile. Đọc commit hoặc diff để hiểu invariant và behavior mà mỗi nhánh đang cố giữ.

**Tại sao hữu ích:**
Conflict là xung đột về text, nhưng bug sau merge thường là xung đột về semantics: cả hai nhánh đều đúng riêng lẻ nhưng khi ghép lại có thể mất validation, logging, transaction boundary hoặc error handling.

**Ví dụ:**
```bash
git log --oneline -- src/Orders/OrderService.cs
git diff HEAD...origin/main -- src/Orders/OrderService.cs
```

Sau khi resolve, chạy test ở behavior chịu ảnh hưởng thay vì chỉ build solution.

**Lưu ý:**
`git checkout --ours` / `--theirs` phù hợp cho file generated hoặc trường hợp ownership rõ, nhưng là công cụ quá thô cho business logic thay đổi song song.

### Tip 5 — Khi dùng AI coding agent, yêu cầu evidence từ repository thay vì tin giả định của agent

**Mẹo:**
Với task sửa bug hoặc refactor, yêu cầu agent chỉ ra file, symbol, call path hoặc test hiện có làm cơ sở cho thay đổi trước khi code.

**Tại sao hữu ích:**
AI có thể tạo code hợp lý về mặt cú pháp nhưng dựa trên API không tồn tại, version sai hoặc assumption không đúng với architecture thật của repository. Grounding vào source hiện tại giảm nguy cơ tạo abstraction và behavior lệch hệ thống.

**Ví dụ:**
```text
Trước khi sửa:
1. tìm entry point của request
2. trace call path tới data access
3. tìm test hiện có liên quan
4. xác nhận package/framework version
5. chỉ sau đó đề xuất patch
```

**Lưu ý:**
Source inspection vẫn không chứng minh patch đúng. Phải chạy test, static analysis hoặc reproduce scenario thật; AI-generated test cũng cần kiểm tra xem nó test behavior hay chỉ mirror implementation.

## 🧠 Software Design

### Design 1 — Repository abstraction vs dùng trực tiếp `DbContext`

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like capabilities. Một custom Repository chỉ đáng thêm khi nó tạo abstraction có ý nghĩa cho domain, ownership hoặc query policy, không phải vì mọi project “phải có Repository Pattern”.

**Vấn đề nó giải quyết:**
Nếu application layer phụ thuộc trực tiếp vào hàng chục query phức tạp hoặc data-source-specific concern, repository/query service có thể gom policy và giảm coupling. Nhưng repository generic kiểu `Add`, `GetAll`, `Update` thường chỉ bọc lại EF Core mà không tạo giá trị mới.

**Ví dụ thực tế:**
```text
Không cần thiết:
GenericRepository<T>.GetAll()
-> trả IQueryable<T>
-> caller vẫn biết toàn bộ EF behavior

Có giá trị hơn:
IOrderReadModel.GetPendingOrdersForBilling(...)
-> contract phản ánh use case rõ ràng
```

**Trade-off:**
Dùng trực tiếp `DbContext` giảm abstraction và giữ LINQ/query capability đầy đủ. Repository có thể bảo vệ boundary và tăng clarity nhưng thêm interface, mapping và nguy cơ che mất tính năng quan trọng của ORM.

**Middle → Senior insight:**
Middle developer cần biết dùng `DbContext` trực tiếp không đồng nghĩa code “thiếu architecture”. Senior / Technical developer phải đánh giá abstraction dựa trên volatility, domain boundary, test strategy và team ownership thay vì áp dụng pattern theo template.

### Design 2 — Saga chỉ phù hợp khi business workflow chấp nhận compensation thay vì ACID toàn cục

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transaction; nếu bước sau thất bại, system thực hiện compensating action thay vì rollback toàn bộ bằng distributed transaction.

**Vấn đề nó giải quyết:**
Trong workflow qua nhiều service hoặc external system, không thể giả định mọi participant cùng tham gia một ACID transaction. Ví dụ đặt hàng có thể gồm ReserveInventory, ChargePayment và CreateShipment.

**Ví dụ thực tế:**
```text
ReserveInventory -> success
ChargePayment    -> success
CreateShipment   -> fail

Compensation:
RefundPayment
ReleaseInventory
```

**Trade-off:**
Saga tăng resilience trước partial failure và tránh distributed transaction, nhưng business phải định nghĩa compensation, retry, idempotency, state tracking và handling khi compensation cũng thất bại. Không phải side effect nào cũng đảo ngược hoàn toàn.

**Middle → Senior insight:**
Middle developer cần hiểu compensation không phải database rollback. Senior / Technical developer phải thiết kế state machine, ownership của orchestration/choreography, timeout, retry, audit và manual recovery cho những trạng thái không thể tự phục hồi.

### Design 3 — Cache key design là một phần của data contract

**Khái niệm:**
Cache key không chỉ là string kỹ thuật; nó encode identity của dữ liệu, scope, version và đôi khi cả authorization context. Thiết kế key sai có thể tạo stale data hoặc data leak giữa tenant/user.

**Vấn đề nó giải quyết:**
Một key như `product-list` có thể vô tình dùng chung cho nhiều language, tenant hoặc filter khác nhau. Kết quả là response hợp lệ về kiểu dữ liệu nhưng sai ngữ cảnh.

**Ví dụ thực tế:**
```text
product-list:{tenantId}:{locale}:{categoryId}:v3
```

Version trong key có thể hỗ trợ invalidation theo schema/representation khi rollout format mới.

**Trade-off:**
Key càng chi tiết thì correctness tốt hơn nhưng cardinality tăng, hit ratio có thể giảm và invalidation phức tạp hơn. Key quá coarse tăng hit ratio nhưng dễ trả dữ liệu stale hoặc sai scope.

**Middle → Senior insight:**
Middle developer cần bảo đảm mọi input ảnh hưởng response đều được phản ánh trong cache identity khi cần. Senior / Technical developer phải cân nhắc tenancy, authorization, versioning, invalidation cost, memory footprint và observability của cache namespace.
