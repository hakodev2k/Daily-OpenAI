# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — Stream file upload thay vì buffer toàn bộ request vào memory

**Mẹo:**
Với file upload lớn trong ASP.NET Core, thiết kế endpoint để stream dữ liệu tới storage thay vì đọc toàn bộ file thành `byte[]` hoặc `MemoryStream` trước khi ghi.

**Tại sao hữu ích:**
Buffering file lớn làm memory usage tăng theo số request đồng thời, gây allocation lớn, GC pressure và thậm chí OOM. Streaming giữ memory footprint gần như cố định theo buffer size và phù hợp hơn cho workload upload đồng thời.

**Ví dụ:**
Một CMS cho phép upload video 500 MB không nên gọi `CopyToAsync()` vào `MemoryStream` rồi mới upload lên Azure Blob Storage. Thay vào đó, validate metadata cần thiết và truyền request stream trực tiếp tới storage API hỗ trợ streaming.

**Lưu ý:**
Streaming không thay thế security validation. Vẫn phải giới hạn request size, kiểm tra authorization, content type/signature khi phù hợp, chống path traversal và xử lý cancellation. Nếu cần virus scanning trước khi publish, có thể stream vào quarantine storage thay vì giữ file trong RAM.

### Tip 2 — EF Core optimistic concurrency cần xử lý conflict như business case

**Mẹo:**
Dùng concurrency token như SQL Server `rowversion` cho dữ liệu có khả năng bị nhiều user cập nhật, và xử lý `DbUpdateConcurrencyException` theo semantics của nghiệp vụ thay vì retry `SaveChangesAsync()` một cách mù quáng.

**Tại sao hữu ích:**
EF Core thêm concurrency token vào `UPDATE ... WHERE`. Nếu row đã thay đổi kể từ lúc được đọc, affected rows bằng 0 và EF Core phát hiện conflict. Điều này ngăn request cũ âm thầm ghi đè thay đổi mới hơn.

**Ví dụ:**
```csharp
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }
    [Timestamp]
    public byte[] Version { get; set; } = default!;
}
```
Nếu hai admin cùng sửa giá, request thứ hai có thể nhận conflict và yêu cầu reload/merge thay vì silently overwrite.

**Lưu ý:**
Không phải conflict nào cũng nên auto-retry. Nếu business decision phụ thuộc dữ liệu cũ, retry sau khi reload có thể áp dụng một quyết định không còn hợp lệ. Phân biệt technical transient failure với semantic concurrency conflict.

### Tip 3 — Azure Blob SAS phải có scope và lifetime nhỏ nhất cần thiết

**Mẹo:**
Khi client cần upload/download trực tiếp Azure Blob Storage, tạo SAS chỉ cho container/blob cần thiết, permission tối thiểu và expiry ngắn; ưu tiên backend dùng Managed Identity để tạo quyền truy cập thay vì lưu account key trong application configuration.

**Tại sao hữu ích:**
Direct client transfer giảm bandwidth và connection pressure trên backend. Nhưng SAS thực chất là bearer credential: ai có URL còn hiệu lực có thể thực hiện các permission được cấp.

**Ví dụ:**
Ứng dụng e-commerce tạo upload SAS cho đúng blob `product-images/{generated-id}` với quyền create/write và expiry 10 phút. Client upload trực tiếp, sau đó backend xác nhận metadata trước khi asset được publish.

**Lưu ý:**
Không phát SAS cấp quyền rộng cho cả container chỉ vì dễ triển khai. Không ghi full SAS URL vào logs/telemetry. Với workflow nhạy cảm, cần xem xét revocation strategy, content validation và trạng thái quarantine trước khi file được phục vụ công khai.

### Tip 4 — Vue watcher phải cleanup side effect để tránh stale update

**Mẹo:**
Khi `watch`/`watchEffect` khởi tạo fetch, timer hoặc subscription, đăng ký cleanup để side effect cũ bị hủy khi dependency thay đổi hoặc component bị dispose.

**Tại sao hữu ích:**
Nếu user thay đổi search term nhanh, request cũ có thể hoàn thành sau request mới và ghi đè state bằng dữ liệu stale. Cleanup biến lifecycle của side effect thành một phần rõ ràng của reactive flow.

**Ví dụ:**
```ts
watch(search, async (value, _, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())

  results.value = await searchApi(value, controller.signal)
})
```
Request của search term trước bị cancel khi term mới xuất hiện.

**Lưu ý:**
Cancellation phía browser không đảm bảo server đã rollback mọi side effect. Với command thay đổi dữ liệu, correctness vẫn cần idempotency/concurrency semantics ở backend; frontend cleanup chủ yếu kiểm soát lifecycle và stale UI state.

### Tip 5 — Contract test nên bảo vệ boundary, không duplicate toàn bộ integration test

**Mẹo:**
Với service hoặc third-party integration, tập trung contract test vào request/response schema, required fields, status semantics và compatibility assumptions mà consumer thực sự phụ thuộc.

**Tại sao hữu ích:**
Một mock có thể tiếp tục trả response cũ dù provider đã đổi contract. Contract-focused tests làm assumptions ở integration boundary trở nên executable và phát hiện breaking change sớm hơn test unit chỉ kiểm tra application logic.

**Ví dụ:**
Payment adapter phụ thuộc `transactionId`, `status` và HTTP `409` cho duplicate operation. Test contract nên xác minh các assumptions này với provider sandbox/stub được sinh từ OpenAPI phù hợp, thay vì assert hàng chục field application không sử dụng.

**Lưu ý:**
Contract test không thay thế E2E hoặc integration test thật: authentication, DNS, TLS, rate limit và provider behavior vẫn có thể thất bại. Tránh snapshot toàn response nếu điều đó biến mọi field không quan trọng thành coupling bắt buộc.

## 🧠 Software Design

### Design 1 — Direct `DbContext` vs Repository abstraction

**Khái niệm:**
EF Core `DbContext` đã cung cấp Unit of Work và repository-like access qua `DbSet<T>`. Repository riêng chỉ có giá trị khi nó tạo boundary có ý nghĩa, che giấu persistence concern cụ thể hoặc cung cấp business-oriented data access contract; nó không mặc nhiên cần thiết cho mọi project.

**Vấn đề nó giải quyết:**
Trong application đơn giản, generic `IRepository<T>` thường chỉ bọc lại `Add`, `Update`, `Find` và làm mất khả năng dùng projection/query feature của EF Core. Ngược lại, domain phức tạp có thể cần một boundary như `IOrderRepository` để bảo vệ aggregate loading và persistence rules.

**Ví dụ thực tế:**
CRUD admin module có thể inject application `DbContext` trực tiếp và project DTO bằng LINQ. Order domain có aggregate invariants lại có thể expose `GetOrderForFulfillmentAsync()` thay vì cho application layer tự ghép nhiều tables theo cách tùy ý.

**Trade-off:**
Direct `DbContext` giảm abstraction và giữ đầy đủ EF Core capability nhưng coupling application với EF Core rõ hơn. Repository có thể tăng cohesion và test seam ở boundary phù hợp, nhưng generic repository dễ tạo pass-through layer, query leakage hoặc abstraction nghèo hơn ORM.

**Middle → Senior insight:**
Middle developer cần sử dụng `DbContext` lifecycle, query và transaction đúng. Senior / Technical developer phải quyết định abstraction dựa trên domain boundary, testing strategy, persistence variability và complexity thực tế; không thêm Repository chỉ để tuân theo một template kiến trúc.

### Design 2 — Azure Functions vs Worker Service cho background processing

**Khái niệm:**
Azure Functions tối ưu cho event-driven execution với managed triggers/scaling; Worker Service phù hợp hơn khi process cần lifecycle dài, execution model chủ động, resource control hoặc hosting behavior ổn định.

**Vấn đề nó giải quyết:**
Một workload xử lý message ngắn, độc lập và bursty có thể hưởng lợi từ Functions. Một processor giữ connection lâu, chạy continuous loop, cần fine-grained concurrency hoặc xử lý task kéo dài có thể trở nên khó kiểm soát nếu ép vào serverless execution model.

**Ví dụ thực tế:**
Thumbnail generation từ Blob trigger có thể là Function. Một market-data processor giữ streaming connection liên tục, quản lý partition ownership và in-memory state có thể phù hợp hơn với Worker Service chạy trên App Service, Container Apps hoặc Kubernetes tùy hạ tầng.

**Trade-off:**
Functions giảm operational burden và scale theo event nhưng có cold start, execution/runtime constraints, retry semantics và cost profile riêng. Worker Service cho nhiều control hơn nhưng team phải sở hữu scaling, health, deployment và capacity planning nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, cancellation, retry và idempotent processing. Senior / Technical developer phải đánh giá workload shape, duration, concurrency, state, SLO, scaling curve, cost và operational ownership trước khi chọn hosting model.

### Design 3 — Synchronous integration vs asynchronous integration

**Khái niệm:**
Synchronous integration giữ caller chờ dependency hoàn thành để nhận kết quả ngay; asynchronous integration chấp nhận work rồi xử lý qua queue/event, tách availability và timing giữa producer với consumer.

**Vấn đề nó giải quyết:**
Nếu checkout gọi tuần tự inventory, email, analytics và CRM, latency và availability của request bị ràng buộc bởi mọi dependency. Nhưng chuyển tất cả sang messaging cũng không phù hợp khi user cần kết quả ngay để quyết định bước tiếp theo.

**Ví dụ thực tế:**
Payment authorization cần phản hồi đồng bộ vì checkout phải biết giao dịch được chấp nhận hay từ chối. Gửi receipt email và analytics event có thể xử lý bất đồng bộ sau khi transaction quan trọng đã hoàn tất.

**Trade-off:**
Synchronous flow dễ hiểu và có immediate consistency nhưng tạo temporal coupling và failure propagation. Asynchronous flow tăng resilience và throughput isolation nhưng thêm broker, eventual consistency, duplicate handling, observability và operational complexity.

**Middle → Senior insight:**
Middle developer cần triển khai timeout/cancellation cho synchronous call và idempotent consumer cho async flow. Senior / Technical developer phải phân loại interaction theo business response requirement, consistency boundary và failure semantics; mục tiêu không phải async hóa tối đa mà là đặt coupling đúng nơi.
