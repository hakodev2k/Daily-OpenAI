# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt CPU saturation với ThreadPool starvation trước khi scale thêm instance

**Mẹo:**
Khi ASP.NET Core latency tăng nhưng CPU chưa cao, kiểm tra ThreadPool starvation bằng `dotnet-counters`, runtime metrics và request queue thay vì mặc định cho rằng application thiếu CPU.

**Tại sao hữu ích:**
ThreadPool starvation xảy ra khi worker thread bị giữ quá lâu, thường do sync-over-async, blocking I/O hoặc lock contention. Khi đó request mới phải chờ thread dù CPU vẫn còn dư, nên scale CPU hoặc tối ưu một query nhỏ có thể không giải quyết đúng bottleneck.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 System.Runtime Microsoft.AspNetCore.Hosting
```

Nếu thấy thread count tăng dần, queue length cao và request latency xấu trong khi CPU không tương ứng, hãy kiểm tra các đoạn như `.Result`, `.Wait()`, synchronous I/O hoặc lock kéo dài.

**Lưu ý:**
ThreadPool tăng thread chậm có chủ đích để tránh oversubscription. Đừng chữa bằng `ThreadPool.SetMinThreads` ngay lập tức; thay đổi này có thể che blocking code và làm contention/GC tệ hơn.

### Tip 2 — Chuẩn hóa lỗi API bằng `ProblemDetails` thay vì tự tạo nhiều JSON shape

**Mẹo:**
Trong ASP.NET Core, dùng `ProblemDetails` cho lỗi HTTP có cấu trúc thống nhất thay vì mỗi controller trả một object lỗi khác nhau.

**Tại sao hữu ích:**
Client, frontend và observability dễ xử lý lỗi hơn khi các response có cùng contract như `type`, `title`, `status`, `detail` và `traceId`. Điều này cũng giảm logic mapping lặp lại giữa validation, authorization và unexpected exception.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();
app.UseStatusCodePages();
```

Với lỗi business cụ thể, có thể thêm extension như `errorCode` nhưng vẫn giữ base contract theo `ProblemDetails`.

**Lưu ý:**
Không đưa stack trace, connection string, SQL text hoặc dữ liệu nhạy cảm vào response production. `ProblemDetails` chuẩn hóa contract lỗi, không thay thế logging nội bộ hay classification lỗi domain.

### Tip 3 — Chống cache stampede bằng TTL jitter và request coalescing thay vì chỉ tăng TTL

**Mẹo:**
Khi nhiều request cùng đọc một Redis key sắp hết hạn, thêm TTL jitter và cơ chế chỉ cho một request refresh dữ liệu trong cùng thời điểm.

**Tại sao hữu ích:**
Nếu hàng nghìn key có cùng TTL hoặc một hot key hết hạn đúng lúc traffic cao, nhiều application instance có thể đồng thời truy vấn database hoặc upstream service. Cache miss đồng loạt biến cache thành nguồn tạo load spike thay vì giảm tải.

**Ví dụ:**
```text
Base TTL: 10 phút
Jitter: + random 0..90 giây

Khi cache miss:
- request đầu tiên refresh dữ liệu
- request còn lại chờ kết quả hoặc dùng stale value ngắn hạn
```

Trong multi-instance system, request coalescing có thể cần distributed coordination hoặc stale-while-revalidate strategy tùy mức criticality.

**Lưu ý:**
Distributed lock cho mọi cache miss có thể tạo bottleneck mới. Với dữ liệu ít quan trọng, phục vụ stale data ngắn hạn đôi khi tốt hơn giữ toàn bộ request chờ một lock trung tâm.

### Tip 4 — Chặn SSRF bằng outbound policy, không chỉ validate URL bằng regex

**Mẹo:**
Nếu backend cho phép user cung cấp URL để fetch webhook preview, image hoặc external document, kiểm soát destination ở network/application boundary thay vì chỉ kiểm tra URL format.

**Tại sao hữu ích:**
Một URL hoàn toàn hợp lệ có thể trỏ tới `localhost`, metadata endpoint, private subnet hoặc hostname resolve lại sang IP nội bộ. SSRF thường khai thác chính khả năng server có quyền truy cập mạng rộng hơn user bên ngoài.

**Ví dụ:**
```text
User URL
-> parse URI
-> allow only http/https
-> resolve host
-> reject loopback/private/link-local ranges
-> optionally enforce domain allowlist
-> send qua outbound proxy/egress policy
```

Nếu workload chỉ cần gọi một tập provider cố định, allowlist rõ ràng thường an toàn hơn cố blacklist mọi destination nguy hiểm.

**Lưu ý:**
Kiểm tra hostname một lần chưa đủ nếu DNS rebinding là rủi ro. Redirect cũng phải được validate lại ở từng hop; tuyệt đối không tự động follow redirect tới private address.

### Tip 5 — Trong Vue/React, hủy request cũ để tránh stale response ghi đè state mới

**Mẹo:**
Khi UI fetch dữ liệu theo search/filter thay đổi nhanh, dùng `AbortController` hoặc cơ chế request cancellation tương đương để hủy request trước khi gửi request mới.

**Tại sao hữu ích:**
Network response không đảm bảo trả về theo thứ tự gửi. Request cho keyword cũ có thể hoàn tất sau request mới và ghi đè state, tạo bug UI rất khó tái hiện dù backend hoàn toàn đúng.

**Ví dụ:**
```ts
let controller: AbortController | null = null

async function loadProducts(query: string) {
  controller?.abort()
  controller = new AbortController()

  const response = await fetch(`/api/products?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  })

  return response.json()
}
```

Ngoài cancellation, có thể dùng request sequence/version để bỏ qua response cũ nếu thư viện không hỗ trợ abort đầy đủ.

**Lưu ý:**
Cancellation ở browser không đảm bảo backend đã dừng xử lý. Nếu operation phía server tốn tài nguyên, cần propagate disconnect/cancellation tới ASP.NET Core, database và outbound calls khi có thể.

## 🧠 Software Design

### Design 1 — Transactional Outbox giải quyết khoảng trống giữa database commit và message publish

**Khái niệm:**
Transactional Outbox lưu business change và message cần publish trong cùng database transaction. Một dispatcher riêng sau đó đọc Outbox và gửi message tới broker.

**Vấn đề nó giải quyết:**
Nếu application cập nhật database rồi publish event trực tiếp, có hai failure window: database commit thành công nhưng broker publish thất bại, hoặc broker nhận message nhưng database rollback. Hai hệ thống không cùng transaction nên trạng thái có thể lệch nhau.

**Ví dụ thực tế:**
```text
Transaction SQL:
1. UPDATE Orders SET Status = 'Paid'
2. INSERT Outbox(Id, Type, Payload, CreatedAt)
3. COMMIT

Dispatcher:
4. đọc Outbox chưa gửi
5. publish OrderPaid
6. đánh dấu đã gửi
```

Consumer vẫn cần idempotency vì dispatcher có thể publish lại nếu crash sau bước 5 nhưng trước bước 6.

**Trade-off:**
Outbox cải thiện atomicity giữa state change và publish intent, nhưng thêm bảng, dispatcher, cleanup, monitoring, duplicate delivery và latency nhỏ trước khi event xuất hiện trên broker.

**Middle → Senior insight:**
Middle developer cần hiểu vì sao `SaveChangesAsync()` rồi `PublishAsync()` không tạo một atomic transaction xuyên hai hệ thống. Senior / Technical developer phải chọn polling, CDC hoặc broker integration, xác định ordering, retention, throughput và duplicate-handling dựa trên reliability requirement thực tế.

### Design 2 — Normalize write model, denormalize read model khi access pattern yêu cầu

**Khái niệm:**
Normalization bảo vệ consistency và giảm duplication trong transactional model; denormalization cố ý duplicate một phần dữ liệu để phục vụ read path nhanh hoặc đơn giản hơn.

**Vấn đề nó giải quyết:**
Một schema chuẩn hóa tốt có thể cần nhiều join cho dashboard, search hoặc reporting traffic lớn. Ngược lại, denormalize toàn bộ ngay từ đầu làm write path phức tạp và tăng nguy cơ dữ liệu không đồng bộ.

**Ví dụ thực tế:**
```text
Write model:
Orders
Customers
OrderItems
Products

Read model cho dashboard:
OrderSummary
- OrderId
- CustomerName
- Total
- ItemCount
- LastUpdatedAt
```

Read model có thể được cập nhật đồng bộ trong transaction hoặc bất đồng bộ bằng event tùy consistency requirement.

**Trade-off:**
Normalization giúp update/invariant rõ và giảm duplication; denormalization giảm join/query cost nhưng tăng storage, synchronization logic và eventual-consistency risk.

**Middle → Senior insight:**
Middle developer cần tránh duplicate dữ liệu vô cớ và biết dùng projection/query hợp lý trước. Senior / Technical developer phải quyết định khi nào read pressure đủ lớn để trả chi phí synchronization, chọn freshness SLA và thiết kế rebuild strategy cho denormalized model.

### Design 3 — Tách deployment khỏi release bằng Feature Flags

**Khái niệm:**
Feature Flag cho phép deploy code lên production nhưng kiểm soát riêng khi nào capability được bật cho user, tenant hoặc traffic segment.

**Vấn đề nó giải quyết:**
Nếu mỗi thay đổi chỉ có thể được bật bằng một deployment mới, release risk gắn chặt với deployment risk. Khi feature lớn cần rollout dần hoặc rollback logic nhanh, redeploy toàn application tạo blast radius không cần thiết.

**Ví dụ thực tế:**
```text
Deploy version 5.2 chứa NewCheckout

Feature flag:
- Internal users: ON
- 5% production traffic: ON
- 95% traffic: OFF

Telemetry ổn -> tăng dần 25% -> 50% -> 100%
```

Flag cũng có thể tách migration kỹ thuật thành nhiều release nhỏ, ví dụ đọc từ schema mới nhưng vẫn giữ fallback về schema cũ.

**Trade-off:**
Feature Flags giảm release risk và hỗ trợ gradual rollout, nhưng tạo nhiều execution path, tăng test matrix và dễ tích tụ dead flags. Flag dài hạn trở thành technical debt nếu không có owner và expiry policy.

**Middle → Senior insight:**
Middle developer cần viết code cho cả trạng thái ON/OFF an toàn và không để flag logic rải rác vô tổ chức. Senior / Technical developer phải thiết kế lifecycle, ownership, kill switch, telemetry, dependency giữa flags và cleanup strategy để tránh biến production thành tập hợp trạng thái không thể dự đoán.
