# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `required` member để ép object initialization đầy đủ ở compile time

**Mẹo:**
Với DTO/config/model cần một số property bắt buộc ngay khi tạo object, dùng `required` để compiler cảnh báo nếu caller quên gán.

**Tại sao hữu ích:**
Giảm bug kiểu object được tạo thành công nhưng thiếu dữ liệu quan trọng, đặc biệt ở mapping layer, test fixture và configuration object.

**Ví dụ:**
```csharp
public sealed class ExportRequest
{
    public required string Format { get; init; }
    public required string Destination { get; init; }
    public int BatchSize { get; init; } = 1000;
}

var request = new ExportRequest
{
    Format = "xlsx",
    Destination = "/tmp/report.xlsx"
};
```

**Lưu ý:**
`required` là compile-time contract, không phải runtime validation. Dữ liệu từ JSON/model binding vẫn cần validation về empty string, range hoặc business rule.

### Tip 2 — Dùng `AsEnumerable()` có chủ đích để đánh dấu ranh giới SQL → in-memory

**Mẹo:**
Nếu một phần LINQ không thể hoặc không nên translate sang SQL, dùng `AsEnumerable()` đúng chỗ để thể hiện rõ từ đâu query chuyển sang xử lý trong memory.

**Tại sao hữu ích:**
Giúp reviewer nhìn ra data boundary và tránh vô tình kéo toàn bộ bảng về application chỉ vì một helper method không translate được.

**Ví dụ:**
```csharp
var recent = dbContext.Orders
    .Where(x => x.CreatedAt >= cutoff)
    .Select(x => new { x.Id, x.Reference })
    .AsEnumerable()
    .Where(x => IsInterestingReference(x.Reference))
    .ToList();
```

**Lưu ý:**
Đặt `AsEnumerable()` quá sớm có thể làm database filter/sort mất tác dụng và gây tải dữ liệu lớn. Luôn push phần filter/projection có thể translate xuống database trước.

### Tip 3 — Dùng `git commit --fixup` + `rebase --autosquash` để giữ review history sạch

**Mẹo:**
Khi đang review branch và cần sửa một commit cũ, tạo fixup commit nhắm vào commit đó thay vì tự nhớ phải squash thủ công sau này.

**Tại sao hữu ích:**
Giữ feedback loop nhanh trong quá trình review nhưng vẫn cho phép tạo history gọn trước khi merge.

**Ví dụ:**
```bash
git commit --fixup <target-commit-sha>
git rebase -i --autosquash origin/main
```

**Lưu ý:**
Không rewrite history đã được nhiều người khác dựa vào nếu chưa thống nhất. Autosquash phù hợp nhất với feature branch cá nhân hoặc branch chưa được publish rộng.

### Tip 4 — Dùng `docker run --rm --entrypoint` để debug image mà không sửa Dockerfile

**Mẹo:**
Khi container fail ngay ở entrypoint, override entrypoint tạm thời để mở shell hoặc chạy command kiểm tra bên trong image.

**Tại sao hữu ích:**
Giúp kiểm tra file copy, environment, certificate, permission hoặc runtime dependency ngay trên image thật mà không phải tạo image debug riêng.

**Ví dụ:**
```bash
docker run --rm -it \
  --entrypoint /bin/sh \
  myapp:latest
```

Hoặc:

```bash
docker run --rm \
  --entrypoint ls \
  myapp:latest -la /app
```

**Lưu ý:**
Minimal/distroless image có thể không có shell. Khi đó dùng image inspection, debug container riêng hoặc multi-stage debug target phù hợp hơn.

### Tip 5 — Dùng `ILogger.BeginScope` để gắn context cho cả một workflow

**Mẹo:**
Khi nhiều log trong cùng request/job cần chung metadata như `OrderId`, `TenantId`, `JobId`, dùng `BeginScope` thay vì lặp field ở từng log call.

**Tại sao hữu ích:**
Giúp log correlation nhất quán và giảm nguy cơ một log line quan trọng bị thiếu context khi điều tra production.

**Ví dụ:**
```csharp
using var scope = logger.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = orderId,
    ["TenantId"] = tenantId
});

logger.LogInformation("Starting payment");
await paymentService.ProcessAsync(cancellationToken);
logger.LogInformation("Payment completed");
```

**Lưu ý:**
Scope chỉ hữu ích nếu logging provider/exporter thực sự capture scope properties. Tránh nhét object lớn hoặc PII vào scope vì nó sẽ xuất hiện trên nhiều log entry.

## 🧠 Software Design

### Design 1 — Anti-Entropy để sửa divergence không phụ thuộc read traffic

**Khái niệm:**
Anti-Entropy là cơ chế background định kỳ so sánh replica hoặc data partition rồi sửa khác biệt, thay vì chờ đến khi user đọc mới phát hiện stale data.

**Vấn đề nó giải quyết:**
Một replica ít được đọc có thể giữ dữ liệu cũ rất lâu nếu hệ thống chỉ dựa vào read repair. Background reconciliation giúp dữ liệu hội tụ ngay cả với cold data.

**Ví dụ thực tế:**
Hai region lưu customer profile. Một replication event bị mất trong network incident. Job reconciliation định kỳ so sánh version/hash theo partition và replay record bị lệch cho region còn thiếu.

**Trade-off:**
Tăng khả năng convergence và phát hiện corruption, nhưng tiêu tốn network/I/O và cần strategy để tránh scan toàn bộ dataset quá thường xuyên.

**Middle → Senior insight:**
Middle developer nên hiểu eventual consistency cần cơ chế repair chủ động. Senior developer phải chọn granularity, checksum/version strategy, scan frequency, conflict resolution và capacity budget để reconciliation không tự trở thành workload gây sự cố.

### Design 2 — Soft Delete chỉ nên dùng khi semantics phục hồi/audit thực sự cần

**Khái niệm:**
Soft Delete đánh dấu record là đã xóa thay vì physical delete, thường bằng `DeletedAt` hoặc trạng thái tương đương.

**Vấn đề nó giải quyết:**
Hữu ích khi business cần restore, audit, legal retention hoặc giữ reference lịch sử mà không muốn record biến mất vật lý ngay lập tức.

**Ví dụ thực tế:**
Employee document bị “xóa” khỏi UI nhưng cần giữ 90 ngày cho audit. Record được set `DeletedAt`, query mặc định lọc record này ra, và background retention job physical-delete sau 90 ngày.

**Trade-off:**
Khôi phục và audit dễ hơn, nhưng mọi query/index/unique constraint phải hiểu deleted state. Nếu dùng mọi nơi theo thói quen, bảng phình lớn và bug “quên filter deleted row” xuất hiện thường xuyên.

**Middle → Senior insight:**
Middle developer nên hiểu soft delete là business/data-retention decision, không phải default CRUD pattern. Senior developer phải quyết định retention, uniqueness semantics, cascade behavior, indexing và thời điểm physical cleanup rõ ràng.

### Design 3 — Failure Domain nên nhỏ hơn Deployment Boundary khi có thể

**Khái niệm:**
Failure Domain là phạm vi bị ảnh hưởng khi một dependency/component lỗi. Deployment Boundary là đơn vị deploy. Hai khái niệm không nhất thiết phải trùng nhau.

**Vấn đề nó giải quyết:**
Một modular monolith vẫn có thể để lỗi report/export làm cạn thread, connection hoặc memory khiến toàn application chết, dù business modules logically tách biệt.

**Ví dụ thực tế:**
`Reporting` và `Core API` cùng nằm trong một deployable nhưng report job có queue, concurrency limit và database pool riêng. Nếu reporting overload, request chính vẫn còn capacity để phục vụ user.

**Trade-off:**
Giảm blast radius mà chưa cần tách microservice, nhưng cần isolation về resource, timeout, queue, circuit breaker hoặc process boundary. Isolation quá mức cũng tăng config và vận hành.

**Middle → Senior insight:**
Middle developer nên nhìn failure propagation ngoài class/module boundary. Senior developer cần thiết kế blast radius theo CPU, memory, connection pool, queue và dependency graph, rồi chỉ tách deployment khi isolation trong cùng process không còn đủ.
