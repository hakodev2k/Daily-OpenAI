# Daily Developer Tips & Design — 2026-09-15

## 🛠 Developer Tips & Tricks

### Tip 1 — `IAsyncDisposable` cho resource cần cleanup bất đồng bộ

**Mẹo:**
Khi resource cần thực hiện I/O trong quá trình cleanup, dùng `IAsyncDisposable` và `await using` thay vì ép cleanup bất đồng bộ chạy synchronously trong `Dispose()`.

**Tại sao hữu ích:**
Một số resource như stream/writer hoặc wrapper quanh network/database operation có thể cần flush bất đồng bộ. Blocking bằng `.GetAwaiter().GetResult()` trong cleanup làm tăng nguy cơ ThreadPool starvation và kéo dài request latency dưới tải.

**Ví dụ:**
```csharp
await using var writer = new AsyncReportWriter(stream);
await writer.WriteAsync(report, ct);
```

Nếu `DisposeAsync()` cần flush buffer xuống storage, caller có thể chờ operation đó mà không block thread.

**Lưu ý:**
Không thêm `IAsyncDisposable` chỉ vì class có method async. Cleanup phải thực sự có asynchronous work. Nếu type implement cả `IDisposable` và `IAsyncDisposable`, cần định nghĩa rõ semantics của hai đường cleanup và tránh double-dispose resource con.

### Tip 2 — ASP.NET Core: giới hạn request body trước khi parse payload lớn

**Mẹo:**
Với endpoint nhận upload hoặc JSON lớn, đặt giới hạn kích thước phù hợp với business requirement và tránh buffer toàn bộ payload vào memory khi có thể stream.

**Tại sao hữu ích:**
Một endpoint chấp nhận body không giới hạn có thể bị dùng để tiêu thụ memory, disk hoặc connection time. Giới hạn ở web server/application boundary giúp reject request quá lớn sớm hơn thay vì để model binding hoặc parser allocate dữ liệu không cần thiết.

**Ví dụ:**
```csharp
app.MapPost("/imports", async (HttpRequest request, CancellationToken ct) =>
{
    // Parse/stream theo format thay vì ReadToEnd toàn bộ file lớn.
});
```

Với file import tối đa 25 MB, cấu hình limit tương ứng ở reverse proxy/IIS/Kestrel và endpoint thay vì mặc định cho mọi route.

**Lưu ý:**
Limit ở application không đủ nếu proxy phía trước có cấu hình khác. Đồng bộ giới hạn giữa CDN/reverse proxy/web server/application và trả lỗi `413 Payload Too Large` rõ ràng cho client.

### Tip 3 — PostgreSQL: keyset pagination ổn định hơn `OFFSET` cho danh sách sâu

**Mẹo:**
Với feed hoặc bảng dữ liệu lớn có sort ổn định, dùng keyset pagination dựa trên sort key cuối cùng của trang trước thay vì tăng `OFFSET` liên tục.

**Tại sao hữu ích:**
`OFFSET 100000` vẫn buộc database tìm rồi bỏ qua lượng lớn row trước khi trả page. Keyset pagination cho phép index seek/range scan từ vị trí đã biết và tránh nhiều anomaly khi row mới được chèn giữa các lần đọc.

**Ví dụ:**
```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@lastCreatedAt, @lastId)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Composite index phù hợp với `(created_at DESC, id DESC)` giúp query đi tiếp từ cursor hiệu quả.

**Lưu ý:**
Keyset không phù hợp khi UI bắt buộc nhảy trực tiếp tới page 437 theo số trang. Sort key phải deterministic; dùng `created_at` một mình có thể bỏ/duplicate row khi nhiều record cùng timestamp.

### Tip 4 — Structured logging: log property có schema thay vì nhúng mọi thứ vào message

**Mẹo:**
Đưa các dimension cần query như `OrderId`, `TenantId`, `Dependency`, `ElapsedMs` thành structured properties thay vì ghép vào chuỗi log tự do.

**Tại sao hữu ích:**
Application Insights/Kibana có thể filter, aggregate và correlate property có cấu trúc. Khi incident xảy ra, query `TenantId == X AND ElapsedMs > 2000` hữu ích hơn grep hàng nghìn biến thể của một message string.

**Ví dụ:**
```csharp
logger.LogWarning(
    "Payment dependency slow for order {OrderId}; elapsed {ElapsedMs} ms",
    orderId,
    elapsed.TotalMilliseconds);
```

Giữ message template ổn định để hệ thống logging nhóm event tốt hơn.

**Lưu ý:**
Không log token, password, full payment data hoặc PII chỉ vì structured property dễ query. Cardinality cực cao trên metric dimensions cũng có thể làm observability backend tốn kém; logs và metrics có mục đích khác nhau.

### Tip 5 — SonarQube warning cần triage theo risk, không sửa máy móc để đạt “zero issues”

**Mẹo:**
Dùng static analysis như một nguồn evidence cho code review: ưu tiên bug/security/reliability finding có đường gây lỗi thực tế, rồi mới xử lý maintainability smell theo context.

**Tại sao hữu ích:**
Static analyzer phát hiện pattern mà compiler không bắt được, nhưng rule không hiểu đầy đủ business context. Việc refactor hàng loạt chỉ để làm dashboard xanh có thể tạo regression và noise lớn hơn giá trị nhận được.

**Ví dụ:**
```text
Finding A: disposable resource có thể leak trong error path
Finding B: method có 16 cognitive-complexity points thay vì threshold 15
```

A có thể cần xử lý ngay; B cần xem method có thực sự khó thay đổi/test hay chỉ vượt threshold nhỏ.

**Lưu ý:**
Không suppress warning mà không ghi lý do, nhưng cũng không biến analyzer thành kiến trúc sư tự động. Baseline legacy debt và áp quality gate nghiêm hơn cho code mới thường thực tế hơn sửa toàn bộ repository một lần.

## 🧠 Software Design

### Design 1 — Transaction boundary nên đi theo business invariant

**Khái niệm:**
Transaction boundary xác định tập thay đổi phải cùng thành công hoặc cùng thất bại. Boundary tốt thường phản ánh business invariant cần atomicity, không đơn giản là “một request = một transaction” hay “một repository = một transaction”.

**Vấn đề nó giải quyết:**
Nếu tạo Order và OrderItems phải luôn tồn tại cùng nhau, commit chúng riêng lẻ có thể tạo trạng thái không hợp lệ. Ngược lại, giữ transaction mở trong lúc gọi payment provider qua HTTP kéo database lock/resource qua một network dependency không kiểm soát được.

**Ví dụ thực tế:**
```text
Local transaction:
- Create Order
- Create OrderItems
- Record PaymentRequested event/outbox
COMMIT

Sau commit:
- worker gọi payment provider
```

Atomicity local được giữ trong database; external side effect được xử lý bằng workflow có retry/idempotency riêng.

**Trade-off:**
Transaction lớn giúp invariant local đơn giản hơn nhưng tăng lock duration, contention và failure surface. Transaction nhỏ giảm coupling/resource hold nhưng có thể yêu cầu eventual consistency và recovery logic.

**Middle → Senior insight:**
Middle developer cần đặt `SaveChanges`/transaction đúng quanh một unit of work có ý nghĩa. Senior / Technical developer phải xác định invariant nào thật sự cần atomicity, đâu là integration boundary và khi nào nên chuyển từ ACID local sang workflow eventual-consistent có recovery rõ ràng.

### Design 2 — Read Model tách khỏi write model khi nhu cầu đọc khác biệt đáng kể

**Khái niệm:**
Read Model là representation được tối ưu cho query/use case đọc, có thể khác cấu trúc domain/write model. Không nhất thiết phải triển khai full CQRS hoặc database riêng mới áp dụng được ý tưởng này.

**Vấn đề nó giải quyết:**
Dashboard cần Order + Customer + payment status + aggregate theo ngày. Ép domain aggregate phục vụ mọi report thường dẫn đến `Include` graph lớn, coupling giữa UI và write model hoặc query phức tạp khó tối ưu.

**Ví dụ thực tế:**
```text
Write model:
Order aggregate + invariants

Read model:
OrderDashboardRow
- OrderId
- CustomerName
- PaymentStatus
- Total
- LastUpdatedAt
```

Read model có thể là SQL projection/view trước; chỉ denormalize sang store riêng khi workload chứng minh cần thiết.

**Trade-off:**
Tách read shape cải thiện query clarity và cho phép tối ưu độc lập, nhưng thêm model cần maintain. Nếu dùng asynchronous projection/store riêng, dữ liệu có thể stale và cần rebuild/reconciliation strategy.

**Middle → Senior insight:**
Middle developer cần biết DTO/query model không phải domain entity. Senior / Technical developer phải chọn mức tách phù hợp: projection trong cùng DB, materialized view hay read store riêng dựa trên scale, consistency và operational cost thay vì áp CQRS đầy đủ theo template.

### Design 3 — Graceful Degradation khi dependency phụ không khả dụng

**Khái niệm:**
Graceful Degradation cho phép hệ thống tiếp tục cung cấp phần giá trị cốt lõi khi dependency không thiết yếu bị lỗi, thay vì biến mọi dependency failure thành toàn bộ request thất bại.

**Vấn đề nó giải quyết:**
Product page phụ thuộc Recommendation Service để hiển thị “Sản phẩm liên quan”. Nếu service này timeout, trả `500` cho cả product page làm availability của chức năng chính phụ thuộc vào một feature phụ.

**Ví dụ thực tế:**
```text
Product DB: OK
Pricing: OK
Recommendation API: timeout

Response:
- product detail: hiển thị bình thường
- recommendation section: bỏ qua/fallback
- telemetry: ghi nhận degraded dependency
```

Điều này chỉ phù hợp khi recommendation không phải invariant của transaction.

**Trade-off:**
Degradation tăng availability và fault isolation nhưng làm hệ thống có nhiều trạng thái behavior hơn, cần observability và UX rõ. Fallback dữ liệu cũ có thể nguy hiểm với price, authorization hoặc compliance-sensitive data.

**Middle → Senior insight:**
Middle developer cần phân biệt dependency bắt buộc với optional và xử lý timeout/fallback có chủ đích. Senior / Technical developer phải định nghĩa degradation policy theo business criticality, consistency/security constraints, SLO và bảo đảm fallback không âm thầm che một outage nghiêm trọng.
