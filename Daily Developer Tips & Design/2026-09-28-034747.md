# Daily Developer Tips & Design — 2026-09-28

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong .NET

**Mẹo:**
Khi ASP.NET Core latency tăng mạnh nhưng CPU chưa cao, kiểm tra ThreadPool trước khi tăng instance. Dùng `dotnet-counters` theo dõi `dotnet.thread_pool.thread.count`, queue length và work-item throughput; tìm các đoạn sync-over-async như `.Result`, `.Wait()` hoặc blocking I/O.

**Tại sao hữu ích:**
ThreadPool starvation xảy ra khi request cần worker thread nhưng các thread hiện tại đang bị block. Runtime có thể bổ sung thread, nhưng tốc độ điều chỉnh không tức thời; queue tăng làm latency leo thang dù CPU còn dư.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id <pid> System.Runtime
```
Nếu request queue tăng, thread count liên tục tăng nhưng CPU chỉ 30–40%, hãy trace blocking call thay vì kết luận server thiếu CPU.

**Lưu ý:**
Thread count cao không tự chứng minh starvation. Correlate với CPU, queue, request latency và trace; workload CPU-bound thực sự cần cách xử lý khác.

### Tip 2 — Dùng keyset pagination cho bảng lớn thay vì OFFSET ngày càng sâu

**Mẹo:**
Với API duyệt tuần tự dữ liệu lớn, dùng stable sort key và cursor/keyset pagination thay cho `OFFSET ... FETCH` ở page sâu.

**Tại sao hữu ích:**
Database vẫn phải bỏ qua nhiều row trước khi trả page sâu bằng offset. Keyset biến vị trí hiện tại thành predicate có thể seek qua index, đồng thời giảm hiện tượng item bị trượt giữa page khi dữ liệu thay đổi.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp bắt đầu theo `CreatedAt, Id` và phải được kiểm chứng bằng execution plan.

**Lưu ý:**
Keyset không phù hợp khi UI bắt buộc nhảy trực tiếp tới “page 317”. Sort key phải deterministic; chỉ dùng `CreatedAt` khi có duplicate sẽ gây mất/lặp row.

### Tip 3 — Đừng để Kubernetes readiness probe kiểm tra mọi dependency

**Mẹo:**
Thiết kế readiness để trả lời “instance này có thể nhận traffic hữu ích không?”, không phải “toàn bộ hệ sinh thái có khỏe không?”. Tách liveness và readiness, và tránh biến dependency transient failure thành restart cascade.

**Tại sao hữu ích:**
Nếu readiness phụ thuộc một service dùng chung đang chập chờn, tất cả pods có thể đồng loạt rời load balancer. Nếu liveness cũng kiểm tra dependency đó, Kubernetes còn restart các process vốn hoàn toàn khỏe.

**Ví dụ:**
ASP.NET Core có thể map health checks theo tag: readiness kiểm tra critical local capability cần để phục vụ request; liveness chủ yếu xác nhận process còn hoạt động. Dependency telemetry/alerting xử lý các external failures riêng.

**Lưu ý:**
Không loại dependency khỏi readiness một cách máy móc. Nếu ứng dụng thực sự không thể phục vụ bất kỳ request có giá trị nào khi database mất kết nối, readiness có thể cần phản ánh điều đó.

### Tip 4 — Vue/React: hủy request cũ khi search-as-you-type để tránh stale UI

**Mẹo:**
Với autocomplete/search UI, dùng `AbortController` để cancel request trước khi gửi request mới và vẫn bảo vệ state khỏi response cũ đến muộn.

**Tại sao hữu ích:**
Network response không đảm bảo đúng thứ tự gửi. Query `"car"` có thể trả sau `"cargo"` và ghi đè kết quả mới, tạo race condition khó tái hiện trên local network nhanh.

**Ví dụ:**
```ts
controller?.abort();
controller = new AbortController();

const response = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
  signal: controller.signal
});
```
Kết hợp debounce để giảm request volume; cancellation giải quyết work không còn cần thiết, debounce giải quyết tần suất.

**Lưu ý:**
Client abort không đảm bảo server đã dừng mọi xử lý. Backend vẫn cần propagation cancellation hợp lý và không dựa vào abort để bảo đảm transactional correctness.

### Tip 5 — Dùng AI coding agent với “evidence contract” khi điều tra repository

**Mẹo:**
Khi nhờ AI sửa bug, yêu cầu agent chỉ kết luận root cause sau khi chỉ ra file/symbol, call path, test tái hiện và bằng chứng từ runtime/log; sau đó chạy test liên quan trước khi đề xuất patch.

**Tại sao hữu ích:**
AI dễ tạo lời giải hợp lý về mặt ngôn ngữ nhưng dựa trên API không tồn tại hoặc assumption sai về codebase. Evidence contract ép quá trình chuyển từ pattern matching sang repository-grounded diagnosis.

**Ví dụ:**
Thay vì “fix duplicate order bug”, giao nhiệm vụ: “trace endpoint → application handler → persistence; tìm đường tạo duplicate, thêm failing regression test, chỉ sửa sau khi test đỏ; báo file và symbol làm bằng chứng”.

**Lưu ý:**
Test xanh không chứng minh patch đúng toàn bộ. Review security, concurrency, backward compatibility và diff scope; không cho agent tự thêm abstraction chỉ để làm patch trông tổng quát hơn.

## 🧠 Software Design

### Design 1 — Optimistic concurrency thay cho khóa dài ở workflow người dùng

**Khái niệm:**
Optimistic concurrency cho phép nhiều actor đọc cùng trạng thái nhưng chỉ chấp nhận update nếu version vẫn đúng. Conflict được phát hiện lúc write thay vì giữ database lock trong suốt thời gian người dùng suy nghĩ.

**Vấn đề nó giải quyết:**
Hai nhân viên mở cùng một Order, cùng chỉnh sửa, người lưu sau vô tình ghi đè thay đổi của người trước. Giữ pessimistic lock từ lúc mở form tới lúc submit là không thực tế cho web application.

**Ví dụ thực tế:**
SQL Server `rowversion` được map thành concurrency token trong EF Core. API nhận version của resource; update với version cũ gây `DbUpdateConcurrencyException`, sau đó trả conflict để client reload/merge theo business rule.

**Trade-off:**
Optimistic concurrency tránh lock dài và scale tốt khi conflict hiếm, nhưng application phải thiết kế UX/retry/merge khi conflict xảy ra. Pessimistic locking có thể hợp với critical section ngắn, contention cao và invariant cần serialization chặt.

**Middle → Senior insight:**
Middle developer cần không nuốt `DbUpdateConcurrencyException` và phải bảo toàn concurrency token qua API contract. Senior / Technical developer cần quyết định conflict nào có thể retry tự động, conflict nào cần người dùng resolve, và khi nào contention đủ cao để optimistic strategy trở nên đắt hoặc nguy hiểm.

### Design 2 — API backward compatibility là một deployment constraint

**Khái niệm:**
API contract phải tiến hóa sao cho client cũ và server mới có thể cùng tồn tại trong khoảng rollout thực tế. Compatibility không chỉ là version number; nó gồm schema, semantics, defaults và deployment order.

**Vấn đề nó giải quyết:**
Mobile app không thể được nâng cấp đồng thời với backend; frontend/CDN cũng có thể giữ bundle cũ. Rename field hoặc thay semantics “nhỏ” có thể phá client vẫn đang chạy ngoài production.

**Ví dụ thực tế:**
Thay vì đổi `status` từ string sang object ngay lập tức, server thêm field mới, hỗ trợ contract cũ trong migration window, đo usage rồi mới deprecate. Consumer-driven contract test có thể chặn accidental breaking change trong CI.

**Trade-off:**
Compatibility giảm release coupling nhưng tạo code chuyển tiếp, contract debt và thời gian deprecation. Versioning mọi thay đổi lại tạo nhiều surface phải vận hành; additive evolution thường rẻ hơn khi semantics cho phép.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking change và test contract. Senior / Technical developer phải thiết kế migration sequence, telemetry để biết client nào còn dùng contract cũ, deprecation policy và cân bằng compatibility cost với nhu cầu làm sạch hệ thống.

### Design 3 — Bulkhead: cô lập resource để một dependency không làm chìm toàn API

**Khái niệm:**
Bulkhead giới hạn concurrency/resource theo workload hoặc dependency để failure ở một khu vực không chiếm toàn bộ thread, connection hoặc outbound capacity của process.

**Vấn đề nó giải quyết:**
Một third-party recommendation API chậm có thể khiến hàng nghìn requests cùng chờ, tiêu thụ outbound connections và memory, rồi làm cả checkout endpoint không liên quan suy giảm.

**Ví dụ thực tế:**
Giới hạn số concurrent calls tới recommendation provider, đặt timeout ngắn và fallback bỏ recommendation. Checkout/payment giữ capacity riêng thay vì cạnh tranh vô hạn với dependency không critical.

**Trade-off:**
Bulkhead cải thiện fault isolation và predictable degradation, nhưng capacity limit quá thấp gây self-throttling; chia pool quá cứng cũng có thể lãng phí resource khi workload thay đổi.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, cancellation và concurrency limit ở dependency boundary. Senior / Technical developer phải phân loại criticality, đặt capacity từ measurement/SLO, quyết định fallback semantics và theo dõi rejected/queued work để điều chỉnh thay vì chọn con số tùy ý.
