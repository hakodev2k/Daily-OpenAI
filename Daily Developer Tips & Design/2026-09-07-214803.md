# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Propagate `CancellationToken` xuyên suốt call chain thay vì chỉ nhận ở controller

**Mẹo:**
Nếu request có thể bị client hủy, timeout hoặc application shutdown, truyền `CancellationToken` từ ASP.NET Core endpoint xuống EF Core, `HttpClient`, background operation và các async API hỗ trợ cancellation thay vì dừng ở tầng controller.

**Tại sao hữu ích:**
Nếu token không được propagate, request đã mất client nhưng database query hoặc outbound HTTP vẫn tiếp tục chiếm connection, CPU và memory. Dưới tải cao, những “orphaned work” này có thể làm connection pool cạn hoặc kéo dài thời gian shutdown.

**Ví dụ:**
```csharp
app.MapGet("/orders/{id:int}", async (
    int id,
    AppDbContext db,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Nếu tầng tiếp theo gọi external API, tiếp tục truyền cùng token vào `SendAsync` hoặc typed client method.

**Lưu ý:**
Cancellation không đồng nghĩa rollback mọi side effect. Nếu operation đã commit database hoặc gọi third-party thành công trước khi token bị hủy, bạn vẫn cần transaction/idempotency strategy phù hợp. Không catch `OperationCanceledException` rồi log như lỗi hệ thống bình thường.

### Tip 2 — Dùng keyset pagination khi page sâu làm `OFFSET` ngày càng đắt

**Mẹo:**
Với bảng lớn và danh sách được duyệt tuần tự, cân nhắc keyset pagination dựa trên cột sort ổn định thay vì `OFFSET ... FETCH` cho page sâu.

**Tại sao hữu ích:**
`OFFSET` buộc database phải tìm và bỏ qua nhiều row trước khi trả page hiện tại. Khi user đi tới page 10.000, lượng work có thể tăng mạnh dù page size vẫn chỉ 50. Keyset pagination bắt đầu từ giá trị cuối của page trước nên thường giữ cost ổn định hơn.

**Ví dụ:**
Thay vì:
```sql
SELECT Id, CreatedAt, Total
FROM Orders
ORDER BY CreatedAt DESC, Id DESC
OFFSET 500000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Dùng cursor từ page trước:
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Composite index phù hợp có thể hỗ trợ tốt access path này.

**Lưu ý:**
Keyset pagination khó hỗ trợ “nhảy trực tiếp tới page 427” và cần sort key deterministic. Nếu UX thực sự cần random page navigation trên dataset nhỏ, `OFFSET` vẫn có thể là lựa chọn đơn giản hơn.

### Tip 3 — Trong Elasticsearch, dùng filter context cho điều kiện không cần relevance score

**Mẹo:**
Khi điều kiện chỉ dùng để loại trừ document — như `status`, `tenantId`, date range hoặc category — đặt chúng trong `bool.filter` thay vì `must` nếu không cần tính `_score`.

**Tại sao hữu ích:**
Query context tính relevance score; filter context chỉ quyết định match hay không và phù hợp hơn cho structured constraints. Điều này làm intent rõ ràng hơn và có thể giảm scoring work, đặc biệt khi kết hợp full-text search với nhiều business filter.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless headphones" } }
      ],
      "filter": [
        { "term": { "status": "published" } },
        { "term": { "tenantId": "t-42" } },
        { "range": { "price": { "lte": 200 } } }
      ]
    }
  }
}
```

Text search vẫn dùng scoring, còn business constraints không làm thay đổi relevance.

**Lưu ý:**
Đừng chuyển mọi clause sang filter. Nếu ranking theo độ phù hợp của text là quan trọng, `match`, `multi_match` hoặc query context vẫn cần thiết. Mapping sai kiểu field cũng có thể khiến filter không dùng được đúng cách.

### Tip 4 — Phân biệt readiness và liveness probe để tránh Kubernetes tự làm outage nặng hơn

**Mẹo:**
Dùng readiness probe để quyết định Pod có nên nhận traffic; dùng liveness probe chỉ khi process thực sự cần restart để hồi phục. Hai probe không nên mặc định kiểm tra cùng một dependency bên ngoài.

**Tại sao hữu ích:**
Nếu database tạm thời chậm mà liveness probe phụ thuộc trực tiếp vào database, Kubernetes có thể restart hàng loạt Pod đúng lúc hệ thống đang chịu sự cố dependency. Điều đó làm mất warm state, tăng reconnect burst và kéo dài outage. Readiness có thể ngừng gửi traffic mà không giết process.

**Ví dụ:**
Một ASP.NET Core service có:
```text
/health/live   -> process/runtime còn hoạt động
/health/ready  -> app đã khởi tạo và có thể phục vụ request
```

Readiness có thể kiểm tra dependency critical có chọn lọc; liveness nên rất thận trọng và thường chỉ phản ánh khả năng process tự hồi phục.

**Lưu ý:**
Không biến readiness thành một “full dependency audit” gọi 10 service mỗi vài giây. Probe quá nặng tự tạo traffic và có thể làm Pod flapping. Cần timeout ngắn, endpoint nhẹ và semantics rõ.

### Tip 5 — Khi review code do AI tạo, kiểm tra “negative space”: edge case mà diff không đề cập

**Mẹo:**
Sau khi AI coding agent tạo patch, đừng chỉ đọc code được thêm. Kiểm tra những behavior không xuất hiện trong diff: cancellation, authorization, nullability, transaction boundary, logging, failure path, concurrency và backward compatibility.

**Tại sao hữu ích:**
AI thường sinh happy-path code khá thuyết phục nhưng bỏ qua constraint ngầm trong production system. Một method có thể compile và pass unit test hiện tại nhưng vẫn phá contract, leak sensitive data hoặc gây duplicate side effect khi retry.

**Ví dụ:**
Agent thêm endpoint import customer và test case thành công. Review nên hỏi thêm:
```text
- Request 10 MB thì sao?
- Duplicate submission thì sao?
- User thiếu permission thì sao?
- Database commit thành công nhưng external call timeout thì sao?
- Client disconnect giữa chừng thì sao?
```

Sau đó bổ sung test hoặc guardrail cho những failure path thực sự quan trọng.

**Lưu ý:**
Không tạo checklist khổng lồ áp cho mọi diff. Chọn edge case theo risk profile của thay đổi. Mục tiêu là dùng AI để tăng tốc implementation nhưng vẫn giữ engineering judgment ở bước verification.

## 🧠 Software Design

### Design 1 — Timeout, Retry và Circuit Breaker phải được thiết kế như một budget thống nhất

**Khái niệm:**
Timeout giới hạn thời gian chờ một attempt; Retry cho phép thử lại lỗi transient; Circuit Breaker tạm ngừng gọi dependency đang thất bại. Ba policy này chỉ hiệu quả khi được thiết kế cùng một latency/failure budget thay vì thêm độc lập.

**Vấn đề nó giải quyết:**
Một API downstream chậm có thể làm caller giữ connection và ThreadPool lâu. Nếu mỗi request retry 5 lần với timeout 10 giây, một call tưởng có SLA 2 giây có thể giữ tài nguyên gần một phút và khuếch đại load lên dependency đang lỗi.

**Ví dụ thực tế:**
Checkout API có budget 2 giây cho Pricing service. Một policy hợp lý có thể là:
- per-attempt timeout khoảng 600 ms
- tối đa 2 retry cho lỗi transient phù hợp
- exponential backoff + jitter
- circuit breaker mở khi failure rate vượt threshold

Tổng budget phải còn chỗ cho các bước khác trong checkout flow.

**Trade-off:**
Resilience policy giúp chịu transient fault và giảm cascading failure, nhưng retry làm tăng load, circuit breaker có thể reject request dù dependency vừa hồi phục, còn timeout quá ngắn gây false failure. Policy càng phức tạp càng cần telemetry và tuning.

**Middle → Senior insight:**
Middle developer cần biết loại exception/status nào được retry và luôn đặt timeout. Senior / Technical developer phải thiết kế end-to-end latency budget, retry amplification, fallback behavior, observability và quyết định dependency nào nên fail fast thay vì “retry cho chắc”.

### Design 2 — Shared Database giữa services là coupling kiến trúc, không chỉ là lựa chọn deployment

**Khái niệm:**
Khi nhiều service cùng đọc/ghi trực tiếp một schema hoặc table, database trở thành integration contract ngầm giữa các service. Điều này có thể đơn giản ở giai đoạn đầu nhưng giảm autonomy về schema, deployment và ownership.

**Vấn đề nó giải quyết:**
Team có thể tách application thành nhiều service để scale hoặc ownership độc lập, nhưng vẫn giữ shared database vì migration sang data ownership riêng quá tốn kém. Nếu không nhận diện trade-off, hệ thống có “microservices ở code” nhưng vẫn là monolith ở data layer.

**Ví dụ thực tế:**
`OrdersService` và `BillingService` cùng update bảng `Orders`. Một schema migration đổi column name buộc hai service phải deploy phối hợp. Nếu Billing chỉ cần trạng thái order, có thể chuyển dần sang API/event/read model riêng thay vì direct table access.

**Trade-off:**
Shared database giữ transaction đơn giản, giảm duplication và đôi khi hoàn toàn hợp lý với team nhỏ. Nhưng nó tăng schema coupling, lock contention, coordinated deployment và khó xác định source of truth. Tách database tăng autonomy nhưng đổi lại eventual consistency, messaging, migration và operational cost.

**Middle → Senior insight:**
Middle developer cần tránh “query chéo cho nhanh” khi boundary đã được định nghĩa. Senior / Technical developer phải quyết định liệu autonomy có đủ giá trị để trả chi phí tách data hay không; không nên tách database chỉ để đạt hình thức microservices.

### Design 3 — Architecture Decision Record nên ghi constraint và lý do, không chỉ ghi kết luận

**Khái niệm:**
Architecture Decision Record (ADR) lưu một quyết định kỹ thuật cùng bối cảnh, lựa chọn đã cân nhắc, constraint và hậu quả. Giá trị chính không phải là “chúng ta dùng Redis”, mà là lý do Redis phù hợp trong điều kiện cụ thể tại thời điểm đó.

**Vấn đề nó giải quyết:**
Sau vài tháng, team thường nhớ quyết định nhưng quên pressure ban đầu: latency target, skill set, deadline, compliance, cost hoặc limitation của vendor. Khi context mất, người sau dễ “sửa” kiến trúc theo giả định mới hoặc giữ một lựa chọn đã hết lý do tồn tại.

**Ví dụ thực tế:**
Một ADR cho search có thể ghi:
```text
Decision: dùng Elasticsearch cho full-text search.
Context: SQL LIKE không đạt p95 < 300 ms với 8M document.
Alternatives: PostgreSQL FTS, managed search SaaS.
Constraints: cần on-prem-compatible deployment và custom analyzer.
Consequences: thêm indexing pipeline, eventual consistency và operational ownership.
```

**Trade-off:**
ADR cải thiện traceability và onboarding, nhưng nếu viết quá chi tiết hoặc bắt buộc cho mọi quyết định nhỏ sẽ thành bureaucracy. ADR cũ cũng phải được supersede thay vì coi như chân lý vĩnh viễn.

**Middle → Senior insight:**
Middle developer cần hiểu và cập nhật quyết định ảnh hưởng code mình thay đổi. Senior / Technical developer phải biết quyết định nào đủ quan trọng để ghi ADR, làm rõ constraint, alternative và reversal cost, đồng thời nhận ra khi assumption cũ đã thay đổi để mở quyết định mới.
