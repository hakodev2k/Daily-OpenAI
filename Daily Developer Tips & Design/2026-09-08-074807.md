# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh LOH pressure bằng streaming và buffer reuse thay vì materialize payload lớn

**Mẹo:**
Khi xử lý file, JSON payload hoặc byte buffer lớn trong .NET, ưu tiên streaming và buffer reuse thay vì liên tục tạo `byte[]`, `string` hoặc object graph lớn sống ngắn.

**Tại sao hữu ích:**
Object lớn có thể đi vào Large Object Heap, làm allocation cost và GC pressure tăng đáng kể. Nếu một API upload/download tạo nhiều buffer lớn đồng thời, memory có thể tăng nhanh dù mỗi request riêng lẻ vẫn chạy đúng. Streaming giữ working set nhỏ hơn và tránh tạo peak memory không cần thiết.

**Ví dụ:**
Thay vì đọc toàn bộ file vào memory:
```csharp
var bytes = await File.ReadAllBytesAsync(path, cancellationToken);
await blobClient.UploadAsync(new BinaryData(bytes), cancellationToken);
```

có thể stream trực tiếp:
```csharp
await using var stream = File.OpenRead(path);
await blobClient.UploadAsync(stream, cancellationToken);
```

Với hot path cần buffer tạm, có thể cân nhắc `ArrayPool<byte>` nếu lifecycle rõ ràng.

**Lưu ý:**
`ArrayPool<T>` không phải optimization mặc định. Buffer thuê phải được trả đúng cách và dữ liệu nhạy cảm có thể cần clear trước khi return. Luôn profile allocation trước khi thêm pooling complexity.

### Tip 2 — Dùng `ExecuteUpdateAsync` cho bulk update đơn giản thay vì load entity rồi track từng row

**Mẹo:**
Với EF Core, nếu cần update nhiều row bằng cùng một rule và không cần domain logic trên từng entity, cân nhắc `ExecuteUpdateAsync` để gửi một set-based SQL statement trực tiếp xuống database.

**Tại sao hữu ích:**
Load hàng nghìn entity rồi thay đổi property khiến EF Core phải materialize object, track state và phát nhiều work ở application layer. Set-based update giảm round trip, allocation và change-tracking overhead.

**Ví dụ:**
```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired),
        cancellationToken);
```

Database xử lý update trực tiếp mà không cần load từng `Order`.

**Lưu ý:**
`ExecuteUpdateAsync` bypass change tracker và không chạy domain method trên entity. Nếu update cần invariant, audit logic, event generation hoặc concurrency check riêng, direct bulk update có thể không phù hợp.

### Tip 3 — Với cookie authentication, đừng coi `SameSite` là lớp bảo vệ CSRF duy nhất

**Mẹo:**
Nếu application dùng cookie-based authentication cho browser, bảo vệ state-changing request bằng anti-forgery mechanism phù hợp thay vì chỉ dựa vào `SameSite` cookie.

**Tại sao hữu ích:**
Cookie được browser tự động gửi theo request, nên attacker có thể cố ép browser gửi request thay user. `SameSite` giảm nhiều CSRF scenario nhưng behavior phụ thuộc navigation context, browser và integration requirement. Anti-forgery token tạo thêm bằng chứng rằng request đến từ UI hợp lệ của application.

**Ví dụ:**
Với form hoặc endpoint browser-facing dùng cookie auth, flow nên có anti-forgery token được generate và validate ở request thay đổi dữ liệu thay vì chỉ kiểm tra user đã authenticated.

**Lưu ý:**
API dùng bearer token trong `Authorization` header không có cùng CSRF threat model vì browser không tự gắn header đó như cookie. Đừng áp anti-forgery máy móc cho mọi API; xác định credential transport trước.

### Tip 4 — Trong CMS, tránh gọi content API lặp lại trong rendering loop

**Mẹo:**
Khi render listing hoặc block tree trong Optimizely CMS hay CMS tương tự, gom content reference cần thiết và tận dụng batch loading/cache thay vì gọi content loader từng item trong vòng lặp.

**Tại sao hữu ích:**
Một page có 100 item có thể vô tình tạo 100 lần content resolution hoặc remote/content-store lookup. Dù CMS có cache nội bộ, repeated calls vẫn tạo lookup overhead và làm rendering path khó đoán hơn dưới tải lớn.

**Ví dụ:**
Thay vì:
```csharp
foreach (var item in model.Items)
{
    var content = contentLoader.Get<IContent>(item.ContentLink);
    // render
}
```

ưu tiên batch API hoặc preload tập reference khi platform hỗ trợ, rồi map kết quả theo content link.

**Lưu ý:**
Không cache mọi content object ở application layer nếu CMS đã có cache invalidation semantics riêng. Cache ngoài platform có thể tạo stale content khó xử lý khi editor publish thay đổi.

### Tip 5 — Với Playwright, ưu tiên locator theo semantics thay vì CSS selector mong manh

**Mẹo:**
Trong end-to-end test, ưu tiên locator theo role, label, accessible name hoặc test id có chủ đích thay vì selector phụ thuộc sâu vào DOM structure.

**Tại sao hữu ích:**
Selector như `.page > div:nth-child(3) > button` dễ vỡ khi UI refactor dù behavior không đổi. Semantic locator gần với cách user tương tác và thường tạo test bền hơn, đồng thời khuyến khích accessibility tốt.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved successfully')).toBeVisible();
```

Nếu component không có semantic label ổn định, dùng `data-testid` có chủ đích thay vì selector ngẫu nhiên từ DOM.

**Lưu ý:**
Đừng biến `data-testid` thành default cho mọi element. Nếu role/label phản ánh behavior thật thì đó thường là contract tốt hơn. Test cũng nên tránh phụ thuộc timing bằng `waitForTimeout` cố định khi có condition rõ để chờ.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service theo execution model và operational control

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có execution tương đối độc lập và cần platform-managed scaling. Worker Service phù hợp hơn khi process cần lifecycle dài, kiểm soát concurrency chi tiết, stateful connection hoặc execution pattern liên tục.

**Vấn đề nó giải quyết:**
Team thường chọn Functions chỉ vì workload chạy background, nhưng một job dài, throughput ổn định hoặc cần kiểm soát resource chặt có thể phù hợp hơn với Worker Service. Ngược lại, chạy Worker 24/7 cho vài event mỗi giờ có thể lãng phí vận hành.

**Ví dụ thực tế:**
Image thumbnail generation theo Blob trigger, mỗi task vài giây và độc lập, có thể hợp với Azure Functions. Một consumer xử lý high-throughput Service Bus liên tục, cần custom partitioning, warm connections và precise backpressure có thể phù hợp hơn với .NET Worker Service.

**Trade-off:**
Functions giảm infrastructure management và scale theo event nhưng thêm cold-start, execution-host và platform constraint. Worker Service cho control tốt hơn nhưng team phải sở hữu deployment, scaling, health check và capacity planning nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, cancellation và idempotency của workload. Senior / Technical developer phải đánh giá traffic shape, execution duration, scaling behavior, cost, observability và operational ownership trước khi chọn hosting model.

### Design 2 — Optimistic concurrency vs pessimistic locking theo contention thực tế

**Khái niệm:**
Optimistic concurrency cho phép nhiều transaction làm việc song song và chỉ phát hiện conflict tại thời điểm update. Pessimistic locking giữ lock sớm hơn để ngăn thay đổi cạnh tranh trước khi chúng xảy ra.

**Vấn đề nó giải quyết:**
Nếu hai user cùng chỉnh một order, update cuối cùng có thể âm thầm ghi đè update trước. Nhưng giữ lock dài trên mọi edit flow lại làm giảm throughput và tăng blocking.

**Ví dụ thực tế:**
Back-office edit order có contention thấp có thể dùng `rowversion`/concurrency token; nếu version đổi, API trả `409 Conflict` để user reload. Một workflow cấp phát inventory cực kỳ cạnh tranh có thể cần transaction/locking strategy chặt hơn tùy database và invariant.

**Trade-off:**
Optimistic concurrency giữ throughput tốt và tránh lock dài nhưng đẩy conflict handling lên application/user flow. Pessimistic locking giảm race trong critical section nhưng tăng blocking, deadlock risk và transaction duration.

**Middle → Senior insight:**
Middle developer cần implement concurrency token và xử lý conflict rõ ràng. Senior / Technical developer phải đo contention, cost của retry, business impact của conflict và transaction duration để chọn strategy thay vì mặc định một kiểu cho toàn hệ thống.

### Design 3 — Shared-schema vs database-per-tenant trong multi-tenant system

**Khái niệm:**
Shared-schema multi-tenancy lưu nhiều tenant trong cùng database/table và phân biệt bằng `TenantId`. Database-per-tenant cô lập dữ liệu vật lý hơn bằng database riêng cho mỗi tenant hoặc nhóm tenant.

**Vấn đề nó giải quyết:**
Shared schema đơn giản hóa deployment và tối ưu resource utilization nhưng tăng yêu cầu data isolation trong application. Database-per-tenant tăng isolation và tùy biến nhưng làm provisioning, migration và monitoring phức tạp hơn.

**Ví dụ thực tế:**
Một SaaS có hàng nghìn tenant nhỏ có thể dùng shared schema với index bắt đầu bằng `TenantId`, authorization filter bắt buộc và automated test chống cross-tenant access. Một số enterprise tenant có compliance hoặc workload đặc biệt có thể được tách database riêng.

**Trade-off:**
Shared schema rẻ hơn và dễ aggregate/report nhưng blast radius lớn hơn khi query/filter sai. Database-per-tenant tăng isolation, backup/restore độc lập và noisy-neighbor control nhưng làm schema migration, connection management và fleet operations khó hơn.

**Middle → Senior insight:**
Middle developer cần đảm bảo tenant context luôn đi xuyên query, cache key và authorization boundary. Senior / Technical developer phải cân nhắc compliance, tenant count, workload skew, migration automation, cost và operational tooling; hybrid model đôi khi thực tế hơn việc ép mọi tenant vào một chiến lược duy nhất.
