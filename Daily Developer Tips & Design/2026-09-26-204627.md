# Daily Developer Tips & Design — 2026-09-26

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt ThreadPool starvation với CPU saturation trong ASP.NET Core

**Mẹo:**
Khi API latency tăng mạnh nhưng CPU chưa cao, kiểm tra ThreadPool queue, số worker thread và các đoạn sync-over-async trước khi scale instance. Các lệnh như `Task.Result`, `.Wait()` hoặc blocking I/O trong request path có thể giữ worker thread trong khi công việc thực tế chỉ đang chờ.

**Tại sao hữu ích:**
ASP.NET Core dựa nhiều vào ThreadPool. Khi request giữ thread để chờ I/O, request mới phải xếp hàng; runtime có thể bổ sung thread nhưng không tức thời. Kết quả là p95/p99 tăng dù CPU vẫn còn dư.

**Ví dụ:**
```csharp
// Tránh
var response = httpClient.GetAsync(url).Result;

// Ưu tiên
var response = await httpClient.GetAsync(url, cancellationToken);
```
Nếu production chậm sau release, đối chiếu request latency, ThreadPool queue length, dependency duration và stack trace trước khi kết luận thiếu CPU.

**Lưu ý:**
Không phải mọi blocking đều sai; workload CPU-bound có thể cần chiến lược riêng. `Task.Run` quanh synchronous I/O không biến I/O đó thành scalable async và có thể làm ThreadPool pressure nặng hơn.

### Tip 2 — Dùng keyset pagination khi OFFSET trở thành chi phí tuyến tính

**Mẹo:**
Với danh sách lớn được duyệt tuần tự, cân nhắc keyset pagination dựa trên cột sort ổn định thay vì `OFFSET ... LIMIT` ở các page sâu.

**Tại sao hữu ích:**
Database vẫn phải tìm và bỏ qua nhiều row trước khi trả page sâu với offset pagination. Keyset dùng giá trị cuối của page trước làm điểm bắt đầu, cho phép index seek hiệu quả hơn và giảm hiện tượng item bị trượt giữa các page khi dữ liệu thay đổi.

**Ví dụ:**
```sql
SELECT id, created_at, total
FROM orders
WHERE tenant_id = @tenantId
  AND (created_at < @lastCreatedAt
       OR (created_at = @lastCreatedAt AND id < @lastId))
ORDER BY created_at DESC, id DESC
LIMIT 50;
```
Một index phù hợp với `tenant_id, created_at, id` cần được đánh giá theo query plan và workload thực tế.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 437. Sort key phải deterministic; nếu `created_at` không unique, thêm tie-breaker như `id`.

### Tip 3 — Dùng Managed Identity thay vì đưa Azure credential vào configuration

**Mẹo:**
Khi workload chạy trên Azure cần truy cập Key Vault, Blob Storage hoặc dịch vụ hỗ trợ Microsoft Entra authentication, ưu tiên Managed Identity và cấp đúng RBAC role thay vì lưu client secret trong `appsettings`, environment variable hoặc pipeline secret.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời phân phối/rotate secret khỏi application. Credential được platform quản lý, còn quyền truy cập được kiểm soát ở resource boundary theo least privilege.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);
```
Local development có thể dùng developer credential; workload trên Azure tự dùng identity phù hợp trong credential chain.

**Lưu ý:**
Managed Identity không tự đảm bảo least privilege. RBAC cấp quá rộng vẫn là security risk; đồng thời cần hiểu credential chain để tránh local/prod dùng identity ngoài dự kiến.

### Tip 4 — Test database constraint bằng integration test, đừng mock DbContext để chứng minh nó

**Mẹo:**
Các behavior phụ thuộc unique constraint, foreign key, transaction hoặc provider-specific SQL nên được test trên database engine đại diện thay vì chỉ mock `DbContext` hoặc dùng collection in-memory.

**Tại sao hữu ích:**
Mock có thể xác nhận method được gọi nhưng không mô phỏng optimizer, isolation, constraint hay transaction semantics. Nhiều bug data chỉ xuất hiện tại boundary thật giữa EF Core và database.

**Ví dụ:**
Một test tạo đồng thời hai user có cùng normalized email và kỳ vọng database chỉ chấp nhận một row nhờ unique index. Đây là bằng chứng mạnh hơn test rằng repository đã gọi `AnyAsync` trước `Add`.

**Lưu ý:**
Integration test cần isolation và lifecycle dữ liệu rõ. Không biến toàn bộ test suite thành E2E chậm; business rule thuần vẫn nên có unit test nhanh.

### Tip 5 — Ground AI coding agent bằng source và test thay vì mô tả kiến trúc từ trí nhớ

**Mẹo:**
Khi giao AI agent sửa code, yêu cầu nó đọc project file, package versions, contracts, tests và implementation liên quan trước khi đề xuất patch; sau đó bắt buộc build/test hoặc kiểm chứng bằng công cụ phù hợp.

**Tại sao hữu ích:**
Agent dễ suy diễn API theo version khác, tạo abstraction không tồn tại trong codebase hoặc sửa đúng “ý tưởng” nhưng sai contract hiện tại. Repository source và executable tests tạo grounding có thể kiểm chứng.

**Ví dụ:**
Thay vì “thêm retry cho payment API”, task nên yêu cầu agent xác định HTTP client registration hiện tại, timeout policy, idempotency semantics và integration tests trước; patch phải chạy test chứng minh retry không lặp payment command không an toàn.

**Lưu ý:**
Test xanh không chứng minh thiết kế đúng nếu test thiếu edge case. Với security, migration hoặc distributed side effect, human review và kiểm tra documentation/source chính thức vẫn cần thiết.

## 🧠 Software Design

### Design 1 — Retry chỉ an toàn khi operation có semantics phù hợp

**Khái niệm:**
Retry là cơ chế resilience cho transient failure, không phải default wrapper cho mọi lỗi. Quyết định retry phải dựa trên loại failure, idempotency của operation, timeout budget và khả năng downstream đã thực hiện side effect trước khi connection thất bại.

**Vấn đề nó giải quyết:**
Network và cloud dependency có lỗi tạm thời, nhưng retry mù có thể biến một lỗi nhỏ thành retry storm hoặc thực hiện business action hai lần.

**Ví dụ thực tế:**
`GET` catalog bị 503 có thể retry với exponential backoff và jitter trong latency budget. Với `POST /payments`, timeout sau khi gửi request không chứng minh payment chưa được tạo; client cần idempotency key hoặc reconciliation thay vì đơn giản gửi lại command mới.

**Trade-off:**
Retry cải thiện availability trước transient faults nhưng tăng latency, load và nguy cơ duplicate side effect. Không retry có thể fail quá sớm; retry quá nhiều có thể làm dependency đang suy yếu sập nhanh hơn.

**Middle → Senior insight:**
Middle developer cần phân loại exception/status code, dùng bounded retry và cancellation đúng. Senior / Technical developer phải thiết kế end-to-end timeout budget, idempotency contract, backoff/jitter, circuit breaking và quyết định operation nào tuyệt đối không được retry tự động.

### Design 2 — Cache là một consistency boundary, không chỉ là tối ưu tốc độ

**Khái niệm:**
Khi application phục vụ dữ liệu từ Redis hoặc CDN, hệ thống đã có thêm một representation có lifecycle riêng. TTL, invalidation và failure behavior vì thế là quyết định consistency chứ không chỉ performance tuning.

**Vấn đề nó giải quyết:**
Một API đọc product price từ cache có thể nhanh hơn database nhưng trả giá cũ sau update. Nếu team không định nghĩa mức stale chấp nhận được, cache bug trở thành business correctness bug.

**Ví dụ thực tế:**
Product description có thể cache 10 phút và chấp nhận eventual refresh. Inventory khả dụng trong checkout lại cần policy chặt hơn: cache có thể hỗ trợ display, nhưng reservation phải xác nhận ở source of truth trước khi commit order.

**Trade-off:**
Cache giảm latency và downstream load nhưng thêm invalidation, stale data, stampede và operational dependency. Bỏ cache giữ model consistency đơn giản hơn nhưng có thể không đáp ứng throughput/latency.

**Middle → Senior insight:**
Middle developer cần implement key, TTL, invalidation và fallback đúng. Senior / Technical developer phải phân loại dữ liệu theo staleness tolerance, chọn source of truth, xác định behavior khi cache unavailable và chứng minh cache thực sự cần bằng measurement.

### Design 3 — Contract testing tại integration boundary thay vì nhân đôi toàn bộ E2E

**Khái niệm:**
Contract test kiểm chứng producer và consumer đồng ý về shape và semantics quan trọng của API/event mà không cần khởi động toàn bộ distributed system cho mọi test case.

**Vấn đề nó giải quyết:**
Unit test có thể xanh ở từng service nhưng deployment vẫn phá consumer vì field, status code hoặc event semantics thay đổi. Ngược lại, chỉ dựa vào E2E lớn làm feedback chậm và khó xác định lỗi thuộc service nào.

**Ví dụ thực tế:**
Mobile backend phụ thuộc `GET /products/{id}`. Contract test khóa các field bắt buộc, nullability và status semantics; provider verification chạy trong CI của API. Một số user journey quan trọng vẫn được giữ bằng E2E để kiểm tra wiring thật.

**Trade-off:**
Contract testing phát hiện breaking integration sớm và nhanh hơn full E2E, nhưng thêm contract lifecycle, versioning và tooling. Contract quá chi tiết có thể khóa implementation thay vì behavior; contract test cũng không thay thế network, auth và deployment E2E.

**Middle → Senior insight:**
Middle developer cần viết contract quanh behavior consumer thực sự phụ thuộc và giữ integration tests cho infrastructure semantics. Senior / Technical developer phải thiết kế test pyramid theo failure risk: chọn boundary nào cần contract, journey nào xứng đáng E2E và tránh duplicate test khiến pipeline vừa chậm vừa khó bảo trì.
