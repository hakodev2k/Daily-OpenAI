# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh `Task.Run` trong ASP.NET Core request pipeline

**Mẹo:**
Không bọc I/O async bằng `Task.Run` trong controller/service chỉ để “chạy nền”. Với HTTP, database và file API đã có async API thì hãy `await` trực tiếp.

**Tại sao hữu ích:**
`Task.Run` không làm I/O nhanh hơn; nó chỉ chiếm thêm ThreadPool thread và có thể làm tăng nguy cơ thread starvation khi tải cao.

**Ví dụ:**
```csharp
// Không nên
var result = await Task.Run(() => httpClient.GetStringAsync(url));

// Nên
var result = await httpClient.GetStringAsync(url, cancellationToken);
```

**Lưu ý:**
`Task.Run` vẫn có chỗ dùng với CPU-bound work ngắn khi thật sự cần tách khỏi caller, nhưng không nên dùng để che giấu synchronous I/O trong server code.

### Tip 2 — Dùng keyset pagination thay vì `OFFSET` cho bảng lớn

**Mẹo:**
Khi paginate dữ liệu theo một thứ tự ổn định, dùng giá trị của record cuối trang trước làm cursor thay vì `OFFSET` lớn.

**Tại sao hữu ích:**
Database không phải scan rồi bỏ qua hàng chục nghìn rows ở mỗi page, nên latency ổn định hơn khi page number tăng.

**Ví dụ:**
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @LastCreatedAt)
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC
LIMIT 50;
```

**Lưu ý:**
Cursor cần dựa trên ordering deterministic. Nếu chỉ order theo field không unique như `CreatedAt`, có thể bị duplicate hoặc bỏ sót record.

### Tip 3 — Dùng `HttpCompletionOption.ResponseHeadersRead` cho response lớn

**Mẹo:**
Khi download file hoặc stream response lớn bằng `HttpClient`, dùng `ResponseHeadersRead` để bắt đầu xử lý stream ngay sau khi nhận headers.

**Tại sao hữu ích:**
Tránh buffer toàn bộ response vào memory trước khi trả control về application, giúp giảm peak memory và latency với file lớn.

**Ví dụ:**
```csharp
using var response = await httpClient.GetAsync(
    url,
    HttpCompletionOption.ResponseHeadersRead,
    cancellationToken);

response.EnsureSuccessStatusCode();
await using var stream = await response.Content.ReadAsStreamAsync(cancellationToken);
```

**Lưu ý:**
Khi dùng streaming, bạn phải dispose response/stream đúng cách và tự chịu trách nhiệm timeout/cancellation trong quá trình đọc nội dung.

### Tip 4 — Dùng `redis-cli --latency` khi nghi Redis chậm

**Mẹo:**
Khi cache operation đột nhiên chậm, dùng `redis-cli` để tách vấn đề network/server latency khỏi code application.

**Tại sao hữu ích:**
Giúp nhanh chóng xác định vấn đề nằm ở Redis server, network hay chính application client/pool configuration.

**Ví dụ:**
```bash
redis-cli -h redis.example.internal --latency
```

Hoặc xem command chậm:

```bash
redis-cli SLOWLOG GET 20
```

**Lưu ý:**
Không dùng `KEYS *` để debug trên production dataset lớn; command này có thể block Redis event loop đáng kể.

### Tip 5 — Dùng `git range-diff` khi review branch đã rebase

**Mẹo:**
Sau khi một PR branch được rebase hoặc force-push, dùng `git range-diff` để so sánh “chuỗi commit cũ” với “chuỗi commit mới” thay vì đọc lại toàn bộ diff.

**Tại sao hữu ích:**
Reviewer dễ thấy commit nào thay đổi nội dung sau rebase và commit nào chỉ đổi SHA do history rewrite.

**Ví dụ:**
```bash
git range-diff origin/main..old-branch origin/main..new-branch
```

**Lưu ý:**
`range-diff` không thay thế final code diff. Nó hữu ích nhất để review evolution của patch series sau rebase hoặc amend.

## 🧠 Software Design

### Design 1 — Strangler Fig Pattern cho việc thay thế legacy system

**Khái niệm:**
Strangler Fig Pattern thay thế hệ thống cũ từng phần bằng cách chuyển từng use case hoặc route sang implementation mới, thay vì rewrite toàn bộ rồi cut-over một lần.

**Vấn đề nó giải quyết:**
Big-bang rewrite thường kéo dài, khó kiểm chứng và dễ thất bại vì business vẫn tiếp tục thay đổi trong thời gian rewrite.

**Ví dụ thực tế:**
Một monolith cũ xử lý Customer, Orders và Billing. Team đặt gateway phía trước, chuyển endpoint Customer sang service/module mới trước, trong khi Orders và Billing vẫn chạy trên legacy. Sau mỗi giai đoạn, traffic được migrate dần.

**Trade-off:**
Ưu điểm là giảm migration risk và cho phép deliver incremental value. Chi phí là tồn tại song song hai implementation, routing phức tạp hơn và có nguy cơ duplicate business rule trong giai đoạn chuyển tiếp.

**Middle → Senior insight:**
Middle developer cần hiểu migration có thể incremental, không nhất thiết rewrite toàn bộ. Senior developer phải chọn seam phù hợp để cắt hệ thống, xác định source of truth, data synchronization strategy và điều kiện retire từng phần legacy.

### Design 2 — Timeout budget thay vì mỗi layer tự đặt timeout

**Khái niệm:**
Timeout budget là tổng thời gian tối đa của một request được phân bổ có chủ đích cho từng downstream call thay vì mỗi layer đặt một timeout độc lập và cộng dồn không kiểm soát.

**Vấn đề nó giải quyết:**
Nếu API gateway timeout 5 giây nhưng service A gọi service B với timeout 10 giây và B gọi database thêm 30 giây, hệ thống tiếp tục xử lý dù client đã bỏ cuộc, gây resource waste và retry amplification.

**Ví dụ thực tế:**
Request có SLA 2 giây. Application dành 1.2 giây cho external API, 500 ms cho database và giữ phần còn lại cho serialization, network overhead và fallback. `CancellationToken` từ caller được truyền xuyên suốt.

**Trade-off:**
Giúp latency predictable và giảm zombie work, nhưng timeout quá aggressive có thể biến spike tạm thời thành error rate cao. Cần dữ liệu latency percentile để đặt budget hợp lý.

**Middle → Senior insight:**
Middle developer cần truyền cancellation và không đặt timeout tùy tiện. Senior developer phải xây timeout hierarchy theo end-to-end SLA, kết hợp retry budget và tránh để retry khiến tổng thời gian vượt deadline của request.

### Design 3 — Consumer-driven contract testing cho integration giữa service

**Khái niệm:**
Consumer-driven contract testing cho phép consumer mô tả phần contract nó phụ thuộc, rồi provider chạy verification để đảm bảo thay đổi mới không phá các consumer hiện tại.

**Vấn đề nó giải quyết:**
Integration test end-to-end thường chậm và brittle, còn unit test riêng từng service không phát hiện breaking change ở HTTP/message contract.

**Ví dụ thực tế:**
Order Service phụ thuộc Payment API trả `paymentId`, `status` và `processedAt`. Contract test của Order chỉ yêu cầu các field thực sự dùng. Khi Payment team đổi schema hoặc semantics, CI provider phát hiện incompatibility trước deployment.

**Trade-off:**
Giảm regression integration và feedback nhanh hơn full E2E test, nhưng thêm contract lifecycle, tooling và governance. Nó cũng không chứng minh toàn bộ system behavior như network policy, authentication hoặc production routing.

**Middle → Senior insight:**
Middle developer cần phân biệt compile-time compatibility với behavioral compatibility. Senior developer phải quyết định contract nào đáng formalize, quản lý version/evolution của contract và cân bằng contract tests với integration/E2E tests để tránh trùng lặp test suite.
