# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsSplitQuery()` khi nhiều collection `Include` gây cartesian explosion

**Mẹo:**
Trong EF Core, nếu một query `Include` nhiều collection cùng lúc và SQL trả số row phình lên bất thường, cân nhắc `AsSplitQuery()` sau khi đo execution plan, row count và round trip thực tế.

**Tại sao hữu ích:**
Một single query join nhiều collection có thể nhân bản dữ liệu cha theo tích số phần tử con. Ví dụ một `Order` có 20 `Lines` và 10 `AuditEntries` có thể tạo khoảng 200 row trung gian cho cùng một order, tăng network payload, materialization cost và memory usage.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.AuditEntries)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

EF Core sẽ tách collection loading thành nhiều SQL query thay vì một join lớn.

**Lưu ý:**
Split query tăng số round trip và dữ liệu giữa các query có thể thay đổi nếu concurrent writes xảy ra. Với projection đơn giản hoặc dataset nhỏ, `Select` đúng shape thường tốt hơn cả `Include` lẫn split query.

### Tip 2 — Chống Redis cache stampede bằng single-flight và TTL có jitter

**Mẹo:**
Khi nhiều request cùng đọc một key hết hạn, đừng để tất cả cùng truy vấn database rồi cùng rebuild cache. Dùng cơ chế single-flight/short lease cho việc refresh và thêm jitter vào TTL để nhiều key không hết hạn cùng thời điểm.

**Tại sao hữu ích:**
Cache hit ratio cao có thể sụp đột ngột nếu hàng nghìn request cùng miss một hot key. Database hoặc external API lúc đó nhận burst lớn hơn bình thường và có thể trở thành bottleneck, khiến cache miss kéo dài hơn nữa.

**Ví dụ:**
```text
TTL cơ bản: 10 phút
Jitter:      + 0..60 giây

Key hết hạn
-> một request giành quyền refresh
-> request khác dùng stale value ngắn hạn hoặc chờ có giới hạn
-> cache được cập nhật một lần
```

**Lưu ý:**
Distributed lock không nên giữ lâu hơn thời gian refresh cần thiết và phải có expiry. Với dữ liệu yêu cầu freshness tuyệt đối, stale-while-revalidate có thể không phù hợp; cần xác định consistency requirement trước.

### Tip 3 — Phân biệt Kubernetes `readiness` và `liveness` để tránh restart loop

**Mẹo:**
Dùng `readinessProbe` để quyết định Pod có nhận traffic hay không; dùng `livenessProbe` chỉ để phát hiện process thực sự bị kẹt và cần restart.

**Tại sao hữu ích:**
Nếu dependency tạm thời như database chậm được đưa vào liveness check, Kubernetes có thể restart Pod liên tục đúng lúc dependency đang lỗi. Điều này làm mất warm state, tăng startup load và biến incident dependency thành restart storm.

**Ví dụ:**
```text
/readiness
- app đã startup
- critical initialization hoàn tất
- có thể phục vụ request

/liveness
- process/event loop còn hoạt động
- không kiểm tra mọi downstream dependency
```

**Lưu ý:**
Probe quá nhạy cũng gây false positive. Cần cấu hình `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds` và failure threshold dựa trên startup/runtime behavior thực tế, không copy cấu hình mẫu máy móc.

### Tip 4 — Chặn SSRF khi backend nhận URL từ user

**Mẹo:**
Nếu ASP.NET Core service tải image, webhook target hoặc document từ URL do user cung cấp, coi URL đó là untrusted input. Ưu tiên allowlist host/scheme và kết hợp network egress policy thay vì chỉ kiểm tra chuỗi URL.

**Tại sao hữu ích:**
SSRF có thể khiến server truy cập endpoint nội bộ, cloud metadata service hoặc service chỉ mở trong private network. Một URL nhìn hợp lệ ban đầu còn có thể redirect hoặc resolve DNS tới địa chỉ không mong muốn.

**Ví dụ:**
```text
Cho phép:
https://cdn.partner.example/...

Từ chối:
file://...
http://127.0.0.1/...
http://169.254.169.254/...
private/internal hosts không thuộc allowlist
```

Sau redirect cũng phải áp dụng lại policy tương ứng.

**Lưu ý:**
Regex URL đơn giản không đủ để chống DNS rebinding, redirect hoặc các dạng IP encoding. Với use case bắt buộc gọi arbitrary URL, cần defense-in-depth ở DNS/network/egress layer và timeout/response-size limit.

### Tip 5 — Buộc AI coding agent kiểm chứng API và version từ repository trước khi sửa code

**Mẹo:**
Khi dùng AI coding agent, yêu cầu nó đọc `.csproj`, lock file, source hiện tại và documentation/version phù hợp trước khi đề xuất API hoặc package change; sau đó phải build/test để xác nhận.

**Tại sao hữu ích:**
Agent có thể nhớ đúng tên một API nhưng sai version, namespace hoặc behavioral assumption. Lỗi kiểu này đặc biệt dễ xảy ra khi codebase dùng legacy .NET/package version khác với kiến thức phổ biến hiện tại.

**Ví dụ:**
```text
1. Inspect TargetFramework + PackageReference
2. Locate current usage in repository
3. Propose minimal change
4. dotnet build
5. run relevant tests
6. inspect diff for unrelated abstractions
```

**Lưu ý:**
Test pass không chứng minh design đúng hoặc security đúng. Với migration, auth, SQL hay concurrency, vẫn cần review assumptions, failure modes và production compatibility thay vì giao toàn bộ judgment cho agent.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service

**Khái niệm:**
Azure Functions phù hợp với event-driven workload có execution tương đối độc lập và muốn platform quản lý scaling/execution model. Worker Service phù hợp hơn khi cần process sống lâu, control loop rõ, connection/state lifecycle ổn định hoặc hosting behavior tùy chỉnh sâu.

**Vấn đề nó giải quyết:**
Một team có background processing thường dễ chọn Functions chỉ vì serverless, hoặc chọn Worker chỉ vì quen .NET. Quyết định đúng phụ thuộc workload shape, latency, execution duration, scaling và operational ownership.

**Ví dụ thực tế:**
```text
Blob uploaded -> resize image nhanh, độc lập
=> Azure Function hợp lý

Consumer giữ nhiều connection, batch liên tục,
custom concurrency + graceful shutdown phức tạp
=> Worker Service có thể phù hợp hơn
```

**Trade-off:**
Functions giảm infrastructure management và scale theo trigger tốt, nhưng có execution/runtime constraints, cold-start/cost model và ít control hơn. Worker Service cho control rõ hơn nhưng team phải chịu trách nhiệm hosting, scaling, deployment và health management nhiều hơn.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry, idempotency và graceful cancellation của execution model đang dùng. Senior / Technical developer phải chọn dựa trên workload duration, throughput curve, scaling latency, operational cost và failure recovery thay vì coi serverless luôn tốt hơn.

### Design 2 — CQRS chỉ đáng dùng khi read/write model thực sự có pressure khác nhau

**Khái niệm:**
CQRS tách model/flow xử lý command khỏi model tối ưu cho query. Điều này có thể chỉ là separation trong cùng application/database; không bắt buộc phải đi kèm microservices, message broker hay Event Sourcing.

**Vấn đề nó giải quyết:**
Một domain phức tạp có write side cần bảo vệ invariant, trong khi read side cần projection phẳng, search/filter hoặc scale pattern khác. Dùng một model duy nhất đôi khi làm cả hai phía trở nên khó tối ưu.

**Ví dụ thực tế:**
```text
Write:
PlaceOrder command
-> validate inventory/payment rules
-> persist aggregate

Read:
OrderHistoryView
-> projection tối ưu cho UI
-> không cần hydrate toàn bộ aggregate
```

**Trade-off:**
CQRS giúp model rõ theo intent và tối ưu read/write độc lập, nhưng thêm duplicate model, mapping, synchronization và có thể tạo eventual consistency nếu read model tách riêng. Với CRUD thông thường, chi phí này thường không đáng.

**Middle → Senior insight:**
Middle developer cần phân biệt command với query và không mutate state trong read path. Senior / Technical developer phải chứng minh complexity/performance pressure đủ lớn để tách model, rồi quyết định mức tách tối thiểu cần thiết thay vì triển khai full distributed CQRS theo template.

### Design 3 — SQL vs Document Database: chọn theo invariant và access pattern

**Khái niệm:**
Relational database mạnh khi dữ liệu có quan hệ, constraint và transaction xuyên nhiều entity cần được bảo vệ nhất quán. Document database mạnh khi aggregate có boundary tự nhiên, thường được đọc/ghi cùng nhau và cần scale/distribution theo partition key rõ ràng.

**Vấn đề nó giải quyết:**
Chọn database chỉ theo nhãn “structured” hay “unstructured” dễ dẫn tới model sai. Một JSON document vẫn có thể cần relational invariant; ngược lại, dữ liệu có schema rõ vẫn có thể phù hợp document model nếu access pattern xoay quanh aggregate độc lập.

**Ví dụ thực tế:**
```text
Finance ledger:
- constraint chặt
- transaction/consistency quan trọng
=> SQL thường phù hợp

Product catalog snapshot:
- product + attributes thường đọc cùng nhau
- schema thay đổi theo category
- partition theo product/tenant rõ
=> document database có thể phù hợp
```

**Trade-off:**
SQL cho constraint, join và transaction mạnh nhưng horizontal distribution có thể phức tạp hơn. Document database giảm impedance cho aggregate và scale theo partition tốt, nhưng denormalization, cross-document transaction/query và hot partition có thể trở thành chi phí lớn.

**Middle → Senior insight:**
Middle developer cần model theo query/update pattern thay vì map object một cách máy móc. Senior / Technical developer phải đánh giá invariant, transaction boundary, partition strategy, expected query evolution, operational skill và migration cost trước khi chọn persistence technology.
