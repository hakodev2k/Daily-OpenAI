# Daily Developer Tips & Design — 2026-09-24

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống database connection pooling

**Mẹo:** Dùng `AddDbContextPool` khi profiling cho thấy chi phí khởi tạo `DbContext` đáng kể, nhưng nhớ rằng database connection pooling là cơ chế riêng của ADO.NET provider.

**Tại sao hữu ích:** Nếu API chờ `SqlConnection.OpenAsync`, tăng context pool không sửa connection exhaustion. Hãy điều tra query duration, transaction lifetime và connection leaks.

**Ví dụ:** `builder.Services.AddDbContextPool<AppDbContext>(o => o.UseSqlServer(connectionString));`

**Lưu ý:** Pooled context được tái sử dụng; tránh giữ mutable per-request state trong context và đừng bật pooling nếu chưa đo bottleneck.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` trên dataset lớn

**Mẹo:** Với feed lớn có sort key ổn định, dùng cursor/keyset pagination thay vì page sâu bằng `OFFSET`.

**Tại sao hữu ích:** `OFFSET` phải bỏ qua ngày càng nhiều rows và dữ liệu thay đổi giữa hai request có thể tạo duplicate hoặc missing item. Keyset tiếp tục từ key cuối cùng đã thấy.

**Ví dụ:** `WHERE CreatedAt < @lastCreatedAt ORDER BY CreatedAt DESC` kết hợp index phù hợp cho phép database seek gần cursor.

**Lưu ý:** Sort phải deterministic; thêm `Id` làm tie-breaker khi timestamp có thể trùng. Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page tùy ý.

### Tip 3 — Kubernetes readiness và liveness phải biểu diễn hai failure semantics khác nhau

**Mẹo:** Readiness quyết định pod có nhận traffic; liveness chỉ nên xác định process có cần restart để phục hồi hay không.

**Tại sao hữu ích:** Nếu liveness phụ thuộc trực tiếp vào SQL Server hoặc external API, dependency outage có thể khiến toàn bộ pods restart đồng loạt dù restart không sửa được dependency.

**Ví dụ:** `/health/live` kiểm tra process-critical state; `/health/ready` phản ánh khả năng phục vụ request và được gắn vào readiness probe.

**Lưu ý:** Readiness quá nhạy cũng có thể loại toàn bộ replicas. Health endpoint cần timeout ngắn và không nên trở thành integration test của mọi dependency.

### Tip 4 — Vue `computed` nên chứa derived state, không chứa side effect

**Mẹo:** Dùng `computed` cho giá trị suy ra từ reactive state; dùng `watch` hoặc event handler cho side effect như gọi API hay ghi storage.

**Tại sao hữu ích:** `computed` được cache và reevaluate theo dependency graph. Side effect bên trong làm behavior khó dự đoán, khó test và có thể tạo request lặp.

**Ví dụ:** `const total = computed(() => cart.value.reduce((s, x) => s + x.price * x.qty, 0));` còn tải shipping methods khi country đổi thuộc `watch`.

**Lưu ý:** `watch` gọi API cũng cần xử lý cancellation hoặc stale response khi dependency đổi nhanh.

### Tip 5 — Dùng `git bisect` để thu hẹp regression theo binary search

**Mẹo:** Khi biết một commit cũ hoạt động và HEAD bị lỗi, dùng `git bisect` thay vì đọc tuần tự lịch sử commit.

**Tại sao hữu ích:** Với 128 commits nghi vấn, binary search chỉ cần khoảng 7 lần phân loại good/bad nếu revision có thể test được.

**Ví dụ:** Chạy `git bisect start`, đánh dấu `bad HEAD`, `good <known-good-ref>`, rồi dùng `git bisect run ./verify-regression.sh` nếu có test deterministic.

**Lưu ý:** Flaky test hoặc commits không build được có thể làm kết quả sai; script phải thực sự tái hiện regression.

## 🧠 Software Design

### Design 1 — Optimistic concurrency vs pessimistic locking

**Khái niệm:** Optimistic concurrency phát hiện conflict khi ghi bằng version/token; pessimistic locking giữ lock sớm để ngăn conflict trong critical section.

**Vấn đề nó giải quyết:** Hai actor cùng sửa một aggregate có thể gây lost update nếu lần ghi sau âm thầm ghi đè state trước đó.

**Ví dụ thực tế:** EF Core dùng `rowversion` và ném `DbUpdateConcurrencyException` khi version cũ không còn khớp. Với critical allocation ngắn nhưng contention cao, explicit locking có thể phù hợp hơn.

**Trade-off:** Optimistic giữ lock ngắn nhưng cần retry/merge; pessimistic giảm conflict-at-commit nhưng tăng blocking và deadlock risk.

**Middle → Senior insight:** Middle developer cần xử lý lost update đúng. Senior / Technical developer phải chọn strategy từ contention rate, transaction duration, business merge semantics và cost của retry.

### Design 2 — Saga orchestration vs choreography

**Khái niệm:** Saga chia distributed business transaction thành local transactions và compensation. Orchestration có coordinator; choreography để services phản ứng qua events.

**Vấn đề nó giải quyết:** Order workflow xuyên Inventory, Payment và Shipping không thể dựa vào một ACID transaction duy nhất; partial failure cần recovery semantics rõ ràng.

**Ví dụ thực tế:** Orchestrator gửi `ReserveInventory`, rồi `AuthorizePayment`; payment fail thì gửi `ReleaseInventory`. Choreography thay coordinator bằng chuỗi domain/integration events.

**Trade-off:** Orchestration dễ quan sát workflow nhưng coordinator có thể thành coupling hub. Choreography phân tán ownership nhưng workflow dài dễ trở nên implicit và khó trace.

**Middle → Senior insight:** Middle developer cần hiểu compensation không phải database rollback và handlers phải idempotent. Senior / Technical developer phải chọn dựa trên workflow complexity, ownership, observability và failure recovery.

### Design 3 — API backward compatibility là contract, không chỉ là URL version

**Khái niệm:** Consumer cũ phải tiếp tục hoạt động khi provider tiến hóa. `/v1` hay `/v2` chỉ là versioning mechanism; compatibility thật nằm ở schema, HTTP semantics và behavior.

**Vấn đề nó giải quyết:** Đổi một response field từ string thành object có thể làm mobile app cũ crash dù endpoint URL không đổi.

**Ví dụ thực tế:** Giữ `customerName`, thêm `customer`, đánh dấu deprecation và đo usage trước khi removal; contract tests giúp phát hiện breaking changes trong CI.

**Trade-off:** Compatibility kéo dài tăng maintenance cost; version mới tạo boundary rõ nhưng buộc vận hành nhiều contracts và migration consumers.

**Middle → Senior insight:** Middle developer cần nhận diện breaking changes. Senior / Technical developer phải định nghĩa compatibility policy, consumer inventory, telemetry, deprecation window và migration strategy.
