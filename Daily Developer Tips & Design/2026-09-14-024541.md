# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` khi producer nhanh hơn consumer và cần backpressure rõ ràng

**Mẹo:**
Khi một background pipeline có producer tạo work nhanh hơn consumer xử lý, cân nhắc `System.Threading.Channels` với bounded capacity thay vì dùng `ConcurrentQueue<T>` rồi để queue tăng vô hạn.

**Tại sao hữu ích:**
Một queue không giới hạn có thể che mất bottleneck cho tới khi memory tăng mạnh. Bounded `Channel<T>` tạo backpressure: khi buffer đầy, producer phải chờ, drop hoặc áp policy đã chọn. Điều này làm capacity của pipeline trở nên có chủ đích thay vì phụ thuộc vào lượng RAM còn lại.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, ct);

await foreach (var item in channel.Reader.ReadAllAsync(ct))
{
    await ProcessAsync(item, ct);
}
```

Nếu consumer chậm kéo dài, `WriteAsync` sẽ chờ khi buffer đạt 500 item thay vì tiếp tục tích work vô hạn.

**Lưu ý:**
Backpressure không tự sửa bottleneck. Nếu throughput consumer thấp hơn input trung bình trong thời gian dài, hệ thống vẫn cần giảm input, scale consumer hoặc thay đổi workload. Chọn `DropOldest`, `DropNewest` hay `Wait` phải dựa trên business semantics; với payment/job quan trọng, drop thường không chấp nhận được.

### Tip 2 — Stream response lớn bằng `IAsyncEnumerable<T>` thay vì materialize toàn bộ danh sách

**Mẹo:**
Với API trả tập dữ liệu lớn và client có thể xử lý dần, cân nhắc streaming thay vì `ToListAsync()` toàn bộ trước khi serialize. Trong ASP.NET Core, `IAsyncEnumerable<T>` có thể giúp giảm peak memory và time-to-first-byte.

**Tại sao hữu ích:**
Materialize 100.000 row trước khi gửi khiến application giữ toàn bộ object graph trong memory và client chỉ nhận dữ liệu sau khi query hoàn tất. Streaming cho phép đọc/serialize từng phần, giảm memory footprint và bắt đầu truyền dữ liệu sớm hơn.

**Ví dụ:**
```csharp
app.MapGet("/api/audit/export", (AuditDbContext db, CancellationToken ct) =>
{
    return db.AuditEntries
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new AuditRow(x.Id, x.Action, x.CreatedAt))
        .AsAsyncEnumerable();
});
```

Với export thực tế, CSV/NDJSON thường phù hợp với streaming hơn một JSON array rất lớn.

**Lưu ý:**
Streaming giữ database connection/request sống lâu hơn. Nếu client đọc chậm, server có thể giữ resource trong thời gian dài. Không dùng streaming để né pagination cho các API interactive thông thường; hãy chọn theo UX, transaction consistency và resource lifetime.

### Tip 3 — Trong Elasticsearch, đưa điều kiện không cần relevance vào `filter` context

**Mẹo:**
Khi query vừa có full-text search vừa có điều kiện chính xác như `status`, `tenantId`, khoảng ngày hoặc category, đặt các điều kiện không ảnh hưởng score vào `bool.filter` thay vì `must` nếu bạn không cần tính relevance cho chúng.

**Tại sao hữu ích:**
`filter` context trả lời câu hỏi “document có match hay không” mà không tính `_score`. Điều này phù hợp với exact constraint và có thể cho phép Elasticsearch tối ưu/cache tốt hơn so với biến mọi điều kiện thành scoring query.

**Ví dụ:**
```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "wireless headphones" } }
      ],
      "filter": [
        { "term": { "tenantId": "t-42" } },
        { "term": { "status": "published" } },
        { "range": { "price": { "lte": 200 } } }
      ]
    }
  }
}
```

Full-text `match` vẫn quyết định relevance; các ràng buộc tenant/status/price chỉ lọc tập kết quả.

**Lưu ý:**
Đừng đổi mọi query sang `filter`: nếu ranking theo text relevance là yêu cầu business, phần text vẫn cần scoring query phù hợp. Ngoài ra hiệu năng search còn phụ thuộc mapping, shard count, cardinality và query shape; không kết luận chỉ dựa trên một DSL rewrite.

### Tip 4 — Dùng Managed Identity để ứng dụng Azure lấy secret thay vì lưu credential trong config

**Mẹo:**
Với App Service, Function hoặc workload Azure hỗ trợ Managed Identity, ưu tiên cấp identity cho workload rồi authorize identity đó vào Key Vault/Storage/Service Bus thay vì lưu client secret hoặc connection credential dài hạn trong `appsettings` hay pipeline variable.

**Tại sao hữu ích:**
Credential tĩnh tạo thêm lifecycle: tạo, phân phối, rotate, revoke và tránh leak. Managed Identity chuyển việc xác thực sang identity do Azure quản lý, giúp application không cần giữ secret tương ứng trong source/config và giảm rủi ro credential bị copy giữa môi trường.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Local development có thể dùng developer credential; production App Service dùng Managed Identity nhưng code authentication path vẫn thống nhất qua `DefaultAzureCredential`.

**Lưu ý:**
Managed Identity không tự tạo authorization đúng. Vẫn cần least privilege, phân biệt identity theo workload và audit role assignment. Không cấp quyền rộng ở subscription/resource group chỉ để “cho chạy được”. Với Key Vault, secret vẫn cần rotation nếu bản thân third-party credential bên trong là secret tĩnh.

### Tip 5 — Dùng `git bisect` khi regression có nhiều commit nghi ngờ

**Mẹo:**
Khi production regression xuất hiện nhưng không rõ commit nào gây ra và khoảng nghi ngờ có hàng chục/hàng trăm commit, dùng `git bisect` để tìm commit đầu tiên lỗi theo binary search thay vì checkout tuần tự từng commit.

**Tại sao hữu ích:**
Nếu có 128 commit giữa bản tốt và bản lỗi, kiểm tra tuyến tính có thể cần tới 128 lần. `git bisect` thường giảm xuống khoảng 7 lần kiểm tra nếu mỗi lần bạn xác định được trạng thái good/bad rõ ràng.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.8.4

# build/test commit Git chọn
# rồi đánh dấu:
git bisect good
# hoặc
git bisect bad

# kết thúc
git bisect reset
```

Nếu có một test tự động tái hiện regression, có thể dùng `git bisect run <script>` để tự động hóa toàn bộ quá trình.

**Lưu ý:**
`git bisect` chỉ hữu ích khi tiêu chí good/bad deterministic. Nếu build cũ không còn chạy được, migration môi trường thay đổi hoặc bug flaky, kết quả có thể nhiễu. Khi đó cần script setup/reproduction ổn định trước.

## 🧠 Software Design

### Design 1 — Inbox Pattern cho consumer cần chống xử lý trùng message

**Khái niệm:**
Inbox Pattern ghi nhận message đã xử lý bằng một identifier bền vững ở phía consumer. Trước hoặc trong cùng transaction với business change, consumer kiểm tra/ghi `MessageId` để lần delivery tiếp theo có thể nhận biết đây là duplicate.

**Vấn đề nó giải quyết:**
Message broker thường cung cấp at-least-once delivery trong nhiều failure scenario. Consumer có thể xử lý thành công rồi crash trước khi acknowledge, khiến cùng message được redeliver. Nếu handler không idempotent, một `PaymentCaptured` có thể cộng tiền, gửi email hoặc tạo record hai lần.

**Ví dụ thực tế:**
```text
Transaction phía consumer:
1. kiểm tra InboxMessages(MessageId)
2. nếu đã tồn tại -> bỏ qua business side effect
3. nếu chưa có -> update business data
4. INSERT InboxMessages(MessageId, ProcessedAt)
5. COMMIT
6. acknowledge message
```

Unique constraint trên `MessageId` giúp hai consumer cạnh tranh không cùng ghi nhận một message như mới.

**Trade-off:**
Inbox tăng reliability nhưng thêm storage, cleanup và transaction logic. Nó cũng không thay thế idempotent business design cho mọi trường hợp: side effect ngoài database như email hoặc external API vẫn cần boundary/strategy riêng.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery là bình thường và handler không được giả định exactly-once. Senior / Technical developer phải thiết kế deduplication key, transaction boundary, retention, external side effects và quan hệ giữa broker semantics với business idempotency.

### Design 2 — API backward compatibility quan trọng hơn version number đơn thuần

**Khái niệm:**
API evolution nên bắt đầu từ compatibility contract: thay đổi nào client cũ vẫn hiểu được, thay đổi nào phá parsing/behavior và thời gian hỗ trợ bao lâu. Gắn `/v2` không tự động làm migration an toàn nếu contract vận hành không được quản lý.

**Vấn đề nó giải quyết:**
Mobile app, CMS frontend hoặc third-party client có thể không deploy cùng lúc với backend. Nếu backend đổi enum, rename field hoặc thay semantics ngay lập tức, client cũ có thể lỗi dù server đã “có version mới”.

**Ví dụ thực tế:**
```text
Tương đối an toàn:
- thêm optional response field
- thêm endpoint mới
- thêm optional request parameter với default cũ

Có nguy cơ breaking:
- rename/remove field
- đổi field từ nullable -> required
- đổi enum semantics
- đổi status code mà client đang phụ thuộc
```

Có thể giữ contract cũ trong một transition window và theo dõi usage trước khi retire.

**Trade-off:**
Backward compatibility giảm rủi ro client break nhưng tăng chi phí duy trì code path cũ và hạn chế freedom refactor contract. Versioning quá sớm cho mọi thay đổi cũng tạo nhiều API surface khó vận hành.

**Middle → Senior insight:**
Middle developer cần nhận ra breaking change ở schema và behavior, không chỉ compile-time change. Senior / Technical developer phải quyết định compatibility window, deprecation policy, telemetry usage và migration path theo loại client, release cadence và business cost.

### Design 3 — Read Replica cải thiện read scale nhưng đưa consistency lag vào kiến trúc

**Khái niệm:**
Read Replica tách một phần traffic đọc khỏi primary database bằng cách replicate dữ liệu sang node đọc. Nó hữu ích khi read workload lớn, nhưng replication thường không đảm bảo dữ liệu xuất hiện tức thì trên replica sau mỗi write.

**Vấn đề nó giải quyết:**
Một hệ thống e-commerce có primary SQL đang chịu cả transaction write và hàng nghìn query reporting/catalog. Chuyển các read chịu stale ngắn sang replica có thể giảm load primary mà không cần thay toàn bộ data model.

**Ví dụ thực tế:**
```text
Primary:
- checkout
- payment state
- inventory reservation

Read Replica:
- dashboard
- historical reports
- product analytics
```

Nếu user vừa cập nhật profile rồi request tiếp theo đọc từ replica đang lag 2 giây, họ có thể thấy dữ liệu cũ dù write đã commit thành công.

**Trade-off:**
Read Replica tăng read capacity và fault isolation nhưng thêm replication lag, routing complexity, monitoring và failover concerns. Với workflow yêu cầu read-your-own-write hoặc invariant mạnh, đọc primary có thể vẫn cần thiết.

**Middle → Senior insight:**
Middle developer cần biết query nào được phép stale và không assume mọi database endpoint có cùng consistency. Senior / Solution-oriented engineer phải phân loại workload theo consistency requirement, định nghĩa fallback khi replica lag và chứng minh rằng tăng read capacity đáng với operational complexity thay vì tối ưu primary/index trước.
