# Câu 1 — EF Core Tracking và truy vấn phát sinh ngoài dự kiến trong hệ thống báo cáo

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** EF Core internals, query execution, performance diagnosis, production debugging

## Bối cảnh

Một ASP.NET Core Web API phục vụ dashboard quản trị. Endpoint lấy danh sách Order cùng Customer và một số thống kê. Sau khi tăng dữ liệu lên vài triệu bản ghi, API bắt đầu chậm và memory tăng cao.

Một developer đã tối ưu bằng cách thêm một số Include và chuyển một số logic xử lý sang LINQ trong service.

Thông tin chưa rõ: số lượng dữ liệu thực tế, index database, query plan, tracking requirement.

## Câu hỏi chính

Hãy giải thích EF Core thực hiện truy vấn như thế nào trong trường hợp này. Điều gì xảy ra bên trong khi dùng tracking, Include và LINQ deferred execution? Vì sao có thể xuất hiện vấn đề performance? Bạn sẽ kiểm chứng giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint cần update entity sau khi đọc hay chỉ đọc dữ liệu?
- Số lượng bản ghi trung bình và lớn nhất là bao nhiêu?
- Query đang được translate xuống SQL hay có phần chạy trong memory?
- Database provider là SQL Server hay PostgreSQL?

## Gợi ý tư duy

- Gợi ý 1: Phân biệt object loading, query execution và change tracking.
- Gợi ý 2: Kiểm tra SQL generated, execution plan và memory allocation.
- Gợi ý 3: Read-only workload thường cần tối ưu projection, AsNoTracking và query shape.

## Cấu trúc trả lời đề xuất

1. Làm rõ workload
2. Giải thích cơ chế EF Core
3. Xác định bottleneck
4. Đưa ra phương án tối ưu
5. Đánh giá trade-off
6. Đề xuất monitoring và test

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu tracking tạo ChangeTracker entry.
- Hiểu LINQ chưa chạy ngay cho tới khi enumerate.
- Biết kiểm tra SQL thực tế.

### Điểm cộng
- Nhắc tới projection DTO.
- Phân tích N+1 query.
- Đề cập index và execution plan.

### Nâng cao
- So sánh split query và single query.
- Phân tích concurrency và cache.

## Hướng giải quyết tham khảo

Giả định đây là dashboard chỉ đọc. Giải pháp phù hợp là projection trực tiếp sang DTO, dùng AsNoTracking, kiểm tra SQL generated và tối ưu index dựa trên execution plan. Không nên chỉ thêm Include vì có thể tạo join lớn và duplicate dữ liệu.

Cần bổ sung integration test với dữ liệu gần production, đo latency, database CPU, logical reads và memory.

## Mẫu trả lời trong phỏng vấn

"Em sẽ không bắt đầu bằng việc thêm Include. Trước tiên em cần xác định endpoint đang cần dữ liệu gì và query thực tế EF sinh ra. Nếu đây là read-only scenario, em ưu tiên projection và AsNoTracking để giảm overhead. Sau đó em kiểm tra execution plan, index và đo bằng metrics thay vì đoán."

## Câu hỏi đào sâu

- Khi nào Include vẫn là lựa chọn phù hợp?
- Split query giải quyết vấn đề gì?
- Làm sao xử lý khi dashboard cần dữ liệu realtime?

## Lỗi trả lời thường gặp

- Chỉ nói thêm index.
- Không phân biệt SQL execution và LINQ execution.
- Không đề cập đo lường.

## Thang điểm 0–10

- Requirement clarification: /10
- Technical correctness: /10
- Depth: /10
- Trade-off analysis: /10
- Production readiness: /10
- Communication: /10

# Câu 2 — Thiết kế hệ thống Background Job xử lý tài liệu với Azure và Hangfire

**Loại câu hỏi:** System design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Architecture, reliability, background processing, Azure design

## Bối cảnh

Một hệ thống cho phép người dùng upload tài liệu. Sau upload cần xử lý OCR, validate dữ liệu, lưu kết quả và gửi notification. Hiện tại một API request chạy toàn bộ pipeline khiến timeout khi file lớn.

Traffic chưa xác định rõ, có thể tăng từ vài trăm lên vài chục nghìn file mỗi ngày.

## Câu hỏi chính

Bạn sẽ thiết kế lại hệ thống xử lý background như thế nào? Hãy trình bày kiến trúc, data flow, retry, idempotency, monitoring và recovery.

## Câu hỏi làm rõ nên cân nhắc

- File size và SLA xử lý?
- Có yêu cầu thứ tự xử lý không?
- Nếu worker chết giữa chừng thì sao?
- Có cần audit history không?

## Gợi ý tư duy

- Tách synchronous upload khỏi asynchronous processing.
- Thiết kế trạng thái job rõ ràng.
- Retry phải đi cùng idempotency.

## Hướng giải quyết tham khảo

MVP có thể dùng modular monolith với Hangfire/Azure Functions worker. Lưu job state trong database, dùng storage cho file, tạo processing pipeline rõ ràng. Mỗi bước cần idempotent và có logging/tracing.

Không mặc định cần microservices nếu scale chưa yêu cầu.

# Câu 3 — AI Code Review Agent cho repository .NET

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** AI agents, context engineering, evaluation, security

## Bối cảnh

Team muốn xây dựng AI agent hỗ trợ review Pull Request cho dự án .NET. Agent có thể đọc code, chạy tool phân tích và đưa ra comment.

Yêu cầu: giảm bug, không expose source code ra ngoài trái phép, tránh comment sai gây mất niềm tin.

## Câu hỏi chính

Bạn sẽ thiết kế agent này như thế nào? Context nào được đưa vào model? Tool permission ra sao? Làm thế nào đánh giá chất lượng output?

## Hướng giải quyết tham khảo

Không nên gửi toàn bộ repository cho model. Cần context selection, rule files, coding standards, deterministic tools như compiler, analyzer, tests. Output phải được validate trước khi tạo review comment.

Cần đo false positive, false negative, latency, cost và audit log.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Hiểu runtime behavior trước khi tối ưu.
- Thiết kế background processing với retry và idempotency.
- AI system cần validation và evaluation, không chỉ gọi LLM.

## Mẫu tư duy cần nhớ

- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Treat observability as part of architecture.
- Validate AI output deterministically.
