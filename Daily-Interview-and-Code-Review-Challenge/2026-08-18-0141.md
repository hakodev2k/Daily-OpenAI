# Câu 1 — EF Core query execution và memory pressure trong hệ thống báo cáo

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** EF Core internals, LINQ execution, performance diagnosis

## Bối cảnh

Một ASP.NET Core Web API cung cấp dashboard cho quản trị viên. Sau 1 năm dữ liệu tăng lên vài triệu Order, endpoint báo cáo chậm dần. CPU application tăng, memory thường xuyên cao, nhưng database chưa có dấu hiệu quá tải.

Developer đã thêm `Include()` để lấy đủ navigation data và chuyển một số xử lý sang LINQ trong service.

## Câu hỏi chính

Giải thích bên trong EF Core xử lý query, tracking, deferred execution và materialization như thế nào. Vì sao cách triển khai hiện tại có thể tạo vấn đề production? Bạn sẽ xác minh giả thuyết bằng dữ liệu nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint này chỉ đọc hay cần update entity?
- Số lượng bản ghi trả về thực tế là bao nhiêu?
- Query đang được translate hoàn toàn xuống SQL hay có xử lý trong memory?
- Có cần tất cả navigation property hay chỉ một phần dữ liệu?

## Gợi ý tư duy

- Gợi ý 1: Phân biệt thời điểm tạo query, execute query và materialize object.
- Gợi ý 2: Kiểm tra SQL generated, execution plan, allocations và tracking behavior.
- Gợi ý 3: Tối ưu query shape trước khi tối ưu code syntax.

## Cấu trúc trả lời đề xuất

1. Clarify workload
2. Giải thích runtime behavior
3. Xác định bottleneck
4. Đề xuất nhiều phương án
5. So sánh trade-off
6. Chọn giải pháp
7. Nêu cách test và monitor

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu ChangeTracker tạo overhead.
- Hiểu LINQ deferred execution.
- Biết kiểm tra SQL thực tế thay vì đoán.

### Điểm cộng
- Nhắc tới projection DTO, `AsNoTracking`, N+1 query.
- Phân tích execution plan và index.

### Nâng cao
- So sánh split query và single query.
- Đề cập cache hoặc read model khi phù hợp.

## Hướng giải quyết tham khảo

Với dashboard read-only, ưu tiên projection trực tiếp sang DTO, `AsNoTracking`, giới hạn dữ liệu trả về và đo bằng telemetry. Không nên chỉ thêm `Include()` vì có thể tạo join lớn, duplicate dữ liệu và tăng memory.

Cần kiểm tra SQL generated, database statistics, logical reads, latency và load test với dữ liệu gần production.

## Mẫu trả lời trong phỏng vấn

"Em sẽ không bắt đầu bằng việc thêm Include. Trước tiên em xác định endpoint cần dữ liệu gì, query EF sinh ra SQL nào và workload đọc hay ghi. Nếu đây là read-only, em ưu tiên projection và AsNoTracking, sau đó đo execution plan và metrics để quyết định tối ưu tiếp."

## Câu hỏi đào sâu

- Khi nào Include vẫn là lựa chọn tốt?
- Khi nào nên dùng raw SQL?
- Nếu dashboard cần realtime thì kiến trúc có thay đổi không?

## Lỗi trả lời thường gặp

- Chỉ nói thêm index.
- Không phân biệt LINQ execution và SQL execution.
- Không đề cập measurement.

## Thang điểm 0–10

- Requirement clarification: /10
- Technical correctness: /10
- Depth: /10
- Trade-off analysis: /10
- Production readiness: /10
- Communication: /10

# Câu 2 — Thiết kế hệ thống xử lý background job với Hangfire và Azure

**Loại câu hỏi:** System design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Architecture, reliability, distributed processing

## Bối cảnh

Một hệ thống cho phép upload tài liệu. Sau upload cần OCR, validate dữ liệu, lưu kết quả và gửi notification. Hiện tại API xử lý toàn bộ trong request nên timeout khi file lớn.

Traffic hiện tại vài trăm file/ngày nhưng business dự kiến tăng mạnh.

## Câu hỏi chính

Bạn thiết kế lại hệ thống xử lý background như thế nào? Trình bày flow, storage, job state, retry, idempotency, monitoring và recovery.

## Câu hỏi làm rõ nên cân nhắc

- SLA xử lý tài liệu là bao lâu?
- Có yêu cầu thứ tự xử lý không?
- Nếu worker crash giữa chừng thì sao?
- Có cần audit history không?

## Gợi ý tư duy

- Tách upload flow và processing flow.
- Retry phải đi cùng idempotency.
- Observability là một phần của design.

## Hướng giải quyết tham khảo

MVP có thể dùng modular monolith với Hangfire hoặc Azure Functions. File lưu ở object storage, database lưu trạng thái processing. Mỗi bước cần khả năng chạy lại an toàn.

Không tự động chuyển microservices nếu chưa có yêu cầu scale hoặc ownership rõ ràng.

# Câu 3 — AI Engineering: Xây dựng AI Agent hỗ trợ Code Review

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Context engineering, agent design, evaluation

## Bối cảnh

Team muốn xây AI agent hỗ trợ review Pull Request cho dự án .NET. Agent có thể đọc diff, tra coding rules, gọi analyzer và đề xuất comment.

Yêu cầu: giảm bug nhưng không tạo quá nhiều false positive, không làm lộ source code và phải kiểm soát quyền truy cập.

## Câu hỏi chính

Bạn thiết kế agent này như thế nào? Context nào gửi cho model? Tool nào được phép sử dụng? Làm sao đánh giá chất lượng?

## Gợi ý tư duy

- Không gửi toàn bộ repository nếu không cần.
- Deterministic tools nên xử lý phần có thể kiểm chứng.
- Agent output cần validation trước khi hành động.

## Hướng giải quyết tham khảo

Thiết kế workflow gồm context selection, repository rules, analyzers, tests, LLM reasoning và human approval. Dùng structured output, audit log và evaluation dataset để đo false positive, false negative, cost và latency.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Hiểu cơ chế runtime trước khi tối ưu.
- Thiết kế background system cần retry, idempotency và recovery.
- AI production cần context control, validation và evaluation.

## Mẫu tư duy cần nhớ

- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Treat observability as part of architecture.
- Validate AI output deterministically.
