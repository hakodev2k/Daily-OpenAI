# Câu 1 — EF Core Query Execution và vấn đề hiệu năng trong API báo cáo

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** EF Core internals, query optimization, performance diagnosis

## Bối cảnh

Một hệ thống ASP.NET Core Web API sử dụng EF Core và PostgreSQL. Endpoint `/api/timesheets/report` phục vụ màn hình quản lý.

Sau khi dữ liệu tăng từ vài trăm nghìn lên vài triệu bản ghi:

- API từ 500ms tăng lên 8-15 giây.
- CPU application tăng cao.
- Database CPU không tăng tương ứng.
- Một số developer thêm `ToListAsync()` sớm để "fix" lỗi timeout.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong EF Core khi xây dựng và thực thi query. Vì sao việc materialize dữ liệu quá sớm có thể gây vấn đề? Bạn sẽ kiểm chứng giả thuyết như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Số lượng record trả về thực tế là bao nhiêu?
- Query có dùng projection hay load toàn bộ entity?
- Có sử dụng tracking không?
- Execution plan của database như thế nào?

## Gợi ý tư duy

- Gợi ý 1: Phân biệt việc xây dựng expression tree và thời điểm query thực sự chạy.
- Gợi ý 2: Xem xét tracking, projection và lượng dữ liệu di chuyển.
- Gợi ý 3: Tối ưu bắt đầu từ đo lường query SQL thực tế.

## Hướng giải quyết tham khảo

EF Core sử dụng LINQ expression để tạo query model, sau đó translate sang SQL khi query được execute. Các thao tác như `Where`, `Select` được compose trước khi gửi xuống database.

Giải pháp thường gồm:

- Projection sang DTO thay vì load entity đầy đủ.
- Dùng `AsNoTracking()` cho read-only.
- Kiểm tra SQL generated và execution plan.
- Pagination thay vì trả toàn bộ dữ liệu.
- Đo bằng logging, tracing và database metrics.

Không nên tối ưu bằng cách chỉ thêm cache hoặc tăng timeout khi chưa biết bottleneck.

## Mẫu trả lời trong phỏng vấn

"Em sẽ không bắt đầu bằng việc sửa code ngay. Đầu tiên em xác định query thực tế, số lượng dữ liệu và execution plan. Trong EF Core, LINQ chưa chạy ngay mà chỉ tạo query expression. Khi materialize như ToListAsync thì SQL mới được gửi xuống database. Nếu materialize quá sớm, application có thể kéo nhiều dữ liệu lên memory, gây CPU và GC pressure. Em sẽ dùng projection, AsNoTracking, pagination và kiểm chứng bằng metrics trước khi chọn giải pháp."

# Câu 2 — Thiết kế hệ thống QA Automation Platform cho ETM

**Loại câu hỏi:** System Design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Architecture, scalability, testing strategy, automation design

## Bối cảnh

Một team muốn xây dựng nền tảng QA Automation cho hệ thống ETM gồm Timesheet, Leave, Approval.

Yêu cầu:

- Chạy hàng trăm test case mỗi ngày.
- Có video, screenshot, log khi fail.
- Có thể chạy lại test thất bại.
- Hỗ trợ nhiều environment.
- Developer có thể xem kết quả trong dashboard.

## Câu hỏi chính

Hãy thiết kế hệ thống này. Bạn chọn kiến trúc, database model, execution flow, retry strategy và observability như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Test chạy đồng thời tối đa bao nhiêu?
- Có yêu cầu approval trước khi chạy production test không?
- Artifact lưu bao lâu?
- Có cần tích hợp CI/CD không?

## Gợi ý tư duy

- Gợi ý 1: Bắt đầu từ lifecycle của một test run.
- Gợi ý 2: Tách orchestration, execution và storage.
- Gợi ý 3: Thiết kế retry phải đi cùng idempotency.

## Hướng giải quyết tham khảo

MVP nên bắt đầu bằng modular monolith:

- API quản lý test suite.
- Background worker nhận execution job.
- Playwright runner thực thi test.
- Database lưu test run, case result.
- Blob storage lưu video/screenshot.
- Dashboard đọc trạng thái.

Cần quan tâm:

- Retry không tạo duplicate result.
- Environment isolation.
- Secret management.
- Logging structured.
- Metrics về pass rate, duration, flaky test.

## Mẫu trả lời trong phỏng vấn

"Em sẽ bắt đầu bằng việc xác định lifecycle của một test execution. Với MVP em không chọn microservices ngay mà xây modular monolith gồm API, scheduler và worker. Điểm quan trọng không chỉ là chạy test mà là quản lý artifact, retry, trace và khả năng phân tích flaky test."

# Câu 3 — Xây dựng AI Code Review Agent trong workflow .NET

**Loại câu hỏi:** AI Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** AI architecture, evaluation, security, context engineering

## Bối cảnh

Một team muốn dùng AI agent để hỗ trợ review Pull Request cho dự án .NET.

Agent có thể đọc code, issue, architecture document và đưa ra review comment.

## Câu hỏi chính

Bạn thiết kế agent này như thế nào để tạo giá trị thực tế mà không phụ thuộc mù quáng vào LLM?

## Câu hỏi làm rõ nên cân nhắc

- Code repository có dữ liệu nhạy cảm không?
- Ai phê duyệt comment của AI?
- Quality metric là gì?
- Agent được quyền truy cập những tool nào?

## Gợi ý tư duy

- Gợi ý 1: AI không nên thay thế deterministic checks.
- Gợi ý 2: Context và permission quan trọng hơn prompt dài.
- Gợi ý 3: Cần evaluation loop trước khi mở rộng.

## Hướng giải quyết tham khảo

Thiết kế nên gồm:

- Context retrieval từ repository, coding rules, architecture docs.
- Tool permission giới hạn.
- Structured output cho review findings.
- Rule-based validation cho security/performance checks.
- Human approval trước merge.
- Evaluation bằng historical PR data.

Theo dõi:

- False positive.
- False negative.
- Token cost.
- Latency.
- Developer acceptance rate.

## Mẫu trả lời trong phỏng vấn

"Em không xem LLM là reviewer cuối cùng. Em dùng AI để tăng tốc phân tích, nhưng các quyết định quan trọng vẫn cần validation. Em sẽ thiết kế context pipeline, tool permission, structured output và evaluation dataset trước khi đưa vào production."
