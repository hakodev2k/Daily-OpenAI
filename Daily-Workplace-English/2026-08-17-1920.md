# Daily Workplace English — Ngày 27

- **Ngày:** 17/08/2026 (UTC+7)
- **Tình huống công việc:** Thông báo một breaking change trong API contract cho frontend team trước khi triển khai
- **Kỹ năng giao tiếp chính:** Mô tả thay đổi API rõ ràng, giải thích impact, đưa migration path và xác nhận thời điểm chuyển đổi
- **Thời gian học:** 20–25 phút
- **Độ khó:** Lower-intermediate

## 1. Tình huống hôm nay

Bạn đang thay đổi một ASP.NET Core API được frontend sử dụng. Hiện endpoint trả về field `employeeStatus`, nhưng backend cần đổi sang cấu trúc mới gồm `statusCode` và `statusLabel` để hỗ trợ thêm nhiều trạng thái trong tương lai.

Những người liên quan gồm bạn và frontend developer. Nếu backend deploy thay đổi ngay mà frontend chưa cập nhật, màn hình hiện tại có thể không đọc được response đúng cách.

Bạn cần thông báo:

- Field nào sẽ thay đổi.
- Vì sao thay đổi này là cần thiết.
- Frontend bị ảnh hưởng như thế nào.
- Có khoảng thời gian chuyển đổi hay backward compatibility hay không.
- Team cần phối hợp deploy theo thứ tự nào.

Rủi ro giao tiếp là chỉ nói về code mà không nói về impact. Một câu như:

> “We changed the response model.”

không đủ để frontend biết họ phải làm gì.

Cấu trúc nên dùng:

**Change → Reason → Impact → Migration path → Timing → Confirmation**

## 2. Bạn cần nói gì?

Trong tình huống này, mục tiêu giao tiếp là:

- Nói rõ đây là một thay đổi có thể ảnh hưởng consumer của API.
- Chỉ ra field cũ và field mới bằng tên cụ thể.
- Giải thích ngắn gọn lý do thay đổi, không sa đà vào implementation detail.
- Cho frontend biết cần cập nhật gì.
- Đưa ra phương án giảm rủi ro, ví dụ giữ field cũ trong một release.
- Xác nhận timeline trước khi backend loại bỏ field cũ.

Điểm quan trọng: khi nói về breaking change, hãy tránh câu mơ hồ như “There are some API updates.” Người nghe cần biết **cái gì thay đổi và khi nào nó bắt đầu ảnh hưởng họ**.

## 3. Đoạn hội thoại hoặc mẫu trình bày

**You:** “I want to flag an upcoming change to the employee API response.”  
*Tôi muốn báo trước một thay đổi sắp tới trong response của employee API.*

**Frontend Developer:** “What’s changing?”  
*Phần nào sẽ thay đổi vậy?*

**You:** “The current `employeeStatus` field will be replaced by `statusCode` and `statusLabel`.”  
*Field `employeeStatus` hiện tại sẽ được thay bằng `statusCode` và `statusLabel`.*

**You:** “We need the new structure because the API will support more status values, and the frontend should not depend on display text as the identifier.”  
*Chúng ta cần cấu trúc mới vì API sẽ hỗ trợ nhiều trạng thái hơn, và frontend không nên dùng text hiển thị làm identifier.*

**Frontend Developer:** “Will the old field disappear as soon as the backend is deployed?”  
*Field cũ có biến mất ngay khi backend được deploy không?*

**You:** “Not immediately. I suggest we keep `employeeStatus` for one release so you can migrate without breaking the current UI.”  
*Không ngay lập tức. Tôi đề xuất giữ `employeeStatus` thêm một release để phía bạn có thể chuyển đổi mà không làm hỏng UI hiện tại.*

**You:** “Once the frontend has switched to the new fields, we can remove the old one in the following release.”  
*Khi frontend đã chuyển sang các field mới, chúng ta có thể bỏ field cũ ở release tiếp theo.*

**You:** “Could you confirm whether that migration window works for your team?”  
*Bạn có thể xác nhận khoảng thời gian chuyển đổi đó có phù hợp với team của bạn không?*

## 4. Các cụm từ quan trọng

### 1. “I want to flag an upcoming change to…”

- **Nghĩa:** Tôi muốn báo trước một thay đổi sắp tới đối với…
- **Khi dùng:** Khi cần chủ động cảnh báo một thay đổi có thể ảnh hưởng team khác.
- **Ví dụ thêm:** “I want to flag an upcoming change to the authentication flow.”

### 2. “The current … will be replaced by …”

- **Nghĩa:** … hiện tại sẽ được thay bằng …
- **Khi dùng:** Khi mô tả rõ một field, component hoặc behavior sắp được thay thế.
- **Ví dụ thêm:** “The current polling job will be replaced by an event-driven process.”

### 3. “We need the new structure because…”

- **Nghĩa:** Chúng ta cần cấu trúc mới vì…
- **Khi dùng:** Khi muốn giải thích lý do thay đổi theo cách ngắn gọn và có logic.
- **Ví dụ thêm:** “We need the new structure because the current model cannot represent multiple permissions.”

### 4. “I suggest we keep … for one release.”

- **Nghĩa:** Tôi đề xuất giữ … trong thêm một release.
- **Khi dùng:** Khi đề xuất một migration window hoặc backward-compatible period.
- **Ví dụ thêm:** “I suggest we keep the old endpoint for one release.”

### 5. “so you can migrate without breaking…”

- **Nghĩa:** để phía bạn có thể chuyển đổi mà không làm hỏng…
- **Khi dùng:** Khi giải thích lợi ích thực tế của phương án chuyển đổi dần.
- **Ví dụ thêm:** “We can support both formats temporarily so clients can migrate without breaking existing integrations.”

### 6. “Once … has switched to …, we can…”

- **Nghĩa:** Khi … đã chuyển sang …, chúng ta có thể…
- **Khi dùng:** Khi một bước phụ thuộc vào việc team khác hoàn thành migration trước.
- **Ví dụ thêm:** “Once QA has verified the new behavior, we can enable the feature flag.”

### 7. “Could you confirm whether … works for your team?”

- **Nghĩa:** Bạn có thể xác nhận liệu … có phù hợp với team bạn không?
- **Khi dùng:** Khi cần chốt alignment thay vì tự giả định timeline phù hợp.
- **Ví dụ thêm:** “Could you confirm whether Thursday works for your team?”

## 5. Từ vựng trong tình huống

### 1. `breaking change` — noun phrase

- **IPA:** /ˈbreɪkɪŋ tʃeɪndʒ/
- **Nghĩa:** thay đổi làm consumer hiện tại có thể không còn hoạt động nếu không cập nhật.
- **Ví dụ:** “This would be a breaking change if we removed the field immediately.”
- **Collocation:** `introduce a breaking change`, `avoid a breaking change`

### 2. `API contract` — noun phrase

- **IPA:** /ˌeɪ piː ˈaɪ ˈkɒntrækt/
- **Nghĩa:** giao kèo về request, response, field, status code và behavior mà API cung cấp cho consumer.
- **Ví dụ:** “We need to update the API contract before frontend integration.”
- **Collocation:** `change the API contract`, `API contract validation`

### 3. `migration` — noun

- **IPA:** /maɪˈɡreɪʃən/
- **Nghĩa:** quá trình chuyển từ cách cũ sang cách mới.
- **Ví dụ:** “We should give the frontend team enough time for the migration.”
- **Collocation:** `migration plan`, `migration window`

### 4. `backward compatibility` — noun phrase

- **IPA:** /ˈbækwəd kəmˌpætəˈbɪləti/
- **Nghĩa:** khả năng hệ thống mới vẫn hỗ trợ consumer đang dùng behavior cũ.
- **Ví dụ:** “Keeping the old field temporarily gives us backward compatibility.”
- **Collocation:** `maintain backward compatibility`

### 5. `consumer` — noun

- **IPA:** /kənˈsjuːmə(r)/
- **Nghĩa:** hệ thống hoặc ứng dụng sử dụng API.
- **Ví dụ:** “We should notify all API consumers before removing the field.”
- **Collocation:** `API consumer`, `external consumer`

### 6. `deprecate` — verb

- **IPA:** /ˈdeprəkeɪt/
- **Nghĩa:** đánh dấu một API hoặc field là sắp không còn được hỗ trợ và nên ngừng sử dụng.
- **Ví dụ:** “We can deprecate the old field before removing it.”
- **Collocation:** `deprecate an endpoint`, `deprecated field`

## 6. Mẫu câu hoặc ngữ pháp cần nhớ

### Passive voice với thay đổi hệ thống: “will be + past participle”

Cấu trúc:

**Subject + will be + past participle**

Ví dụ trong bài:

- “The current `employeeStatus` field **will be replaced** by `statusCode` and `statusLabel`.”

Dùng passive voice khi điều quan trọng là **thành phần nào sẽ bị thay đổi**, không phải ai là người thực hiện thay đổi.

Ví dụ khác:

- “The old endpoint **will be removed** in the next release.”
- “The validation rule **will be updated** before deployment.”
- “The new fields **will be documented** in the API specification.”

### Khi nên dùng

Trong software communication, passive voice rất tự nhiên khi nói về:

- deployment
- configuration
- API changes
- database changes
- fixes
- releases

### Lỗi thường gặp

Sai:

> “The old field will removed next week.”

Đúng:

> “The old field **will be removed** next week.”

Sau `will` trong passive voice phải có `be`.

## 7. Cách nói tự nhiên hơn

### Chưa tự nhiên hoặc quá trực tiếp

“We change the API. Frontend must change too.”

### Tự nhiên và chuyên nghiệp hơn

“We’re updating the API contract, and the frontend will need to migrate to the new fields.”

### Giải thích

Câu tốt hơn nói rõ đây là API contract change và dùng `will need to` thay vì `must`, nên vẫn trực tiếp nhưng hợp tác hơn.

### Chưa tự nhiên hoặc quá trực tiếp

“Your UI will break if you don’t fix it.”

### Tự nhiên và chuyên nghiệp hơn

“If the old field is removed before the frontend is updated, the current UI may stop working correctly.”

### Giải thích

Câu mới mô tả điều kiện và consequence của hệ thống, không đổ lỗi cho người nghe. `may` cũng phù hợp khi bạn đang nói về risk thay vì khẳng định tuyệt đối.

### Chưa tự nhiên hoặc quá trực tiếp

“Tell me when you finish.”

### Tự nhiên và chuyên nghiệp hơn

“Could you let me know once the frontend has switched to the new fields?”

### Giải thích

Câu này nêu rõ điều kiện hoàn thành cần được thông báo. Trong tình huống phối hợp cross-team, cách nói này rõ hơn và chuyên nghiệp hơn. Tuy nhiên, trong incident khẩn cấp, câu trực tiếp hơn có thể phù hợp nếu cần hành động ngay.

## 8. Phát âm và luyện nói

### “I want to flag an upcoming change.”

- **Trọng âm:** `FLAG`, `UPcoming`, `CHANGE`
- **Connected speech:** `want to` thường được nói nhanh, âm `/t/` không cần bật quá mạnh.
- **Gợi ý cho người Việt:** Không đọc từng từ tách rời; giữ nhịp ở các từ mang thông tin chính.
- **Ngắt:** “I want to flag / an upcoming change.”
- **Nhấn:** `flag`, `change`

### “The current field will be replaced by…”

- **Trọng âm:** `CURRENT`, `FIELD`, `REPLACED`
- **Connected speech:** `will be` thường nhẹ hơn từ `replaced`.
- **Gợi ý:** Đừng nhấn đều tất cả các từ.
- **Ngắt:** “The current field / will be replaced by…”
- **Nhấn:** `field`, `replaced`

### “Could you confirm whether that works for your team?”

- **Trọng âm:** `CONFIRM`, `WORKS`, `TEAM`
- **Connected speech:** `Could you` thường nối tự nhiên, không cần đọc tách mạnh `could` và `you`.
- **Gợi ý:** Cuối câu nên giữ giọng lịch sự, không cần lên quá cao như một câu hỏi Yes/No đơn giản.
- **Ngắt:** “Could you confirm / whether that works for your team?”
- **Nhấn:** `confirm`, `works`, `team`

### Shadowing script

“I want to flag an upcoming change to the employee API response.”  
“The current field will be replaced by two new fields.”  
“I suggest we keep the old field for one release so the frontend can migrate safely.”  
“Could you confirm whether that migration window works for your team?”

Luyện theo thứ tự:

1. Đọc chậm từng câu.
2. Nghe lại bằng Text-to-Speech nếu có.
3. Lặp từng câu một, bắt chước nhịp và trọng âm.
4. Ghi âm giọng của bạn.
5. Nói lại toàn bộ đoạn mà không nhìn văn bản.

## 10. Bài tập thực hành chủ động

### Nhiệm vụ

Viết một message 6–8 câu cho frontend developer để thông báo một API contract change.

### Scenario

Backend sẽ đổi field `isActive: true/false` thành `status: "Active" | "Inactive" | "Pending"` vì hệ thống sắp hỗ trợ thêm trạng thái `Pending`.

### Bắt buộc phải có

- Field cũ là gì.
- Field mới là gì.
- Lý do thay đổi.
- Impact nếu frontend chưa update.
- Một migration window hoặc compatibility plan.
- Một câu xác nhận timeline với frontend.

### Cấu trúc gợi ý

**Flag the change → Describe old/new contract → Explain reason → Explain impact → Suggest migration plan → Ask for confirmation**

### Cụm từ có thể dùng

- “I want to flag an upcoming change to…”
- “The current … will be replaced by …”
- “We need the new structure because…”
- “I suggest we keep … for one release.”
- “Once the frontend has switched to…”
- “Could you confirm whether … works for your team?”

### Tiêu chí hoàn thành

Message của bạn đạt yêu cầu nếu người đọc có thể trả lời ba câu hỏi:

1. What is changing?
2. What do I need to do?
3. When do I need to do it?

Cả hai đều tập trung vào dependency thay vì ra lệnh trực tiếp.

### Bài 4

**Đáp án: 2 → 3 → 4 → 1**

Bạn nên nói rõ thay đổi trước, giải thích lý do, đưa migration plan, rồi mới xác nhận timeline.

**Đáp án: B. `will be removed`**

Đây là passive voice. Endpoint là đối tượng bị remove.

Một đáp án phù hợp:

> “I suggest we keep the old field for one release so the frontend can migrate without breaking the current UI.”

- “…so existing clients have time to migrate.”
- “…so we can avoid a breaking change during the transition.”

## 12. Mẫu trả lời tham khảo

“I want to flag an upcoming change to the employee API response. The current `isActive` field **will be replaced by** a new `status` field with `Active`, `Inactive`, and `Pending` values. We need the new structure because the system will support more than two states. If we remove `isActive` immediately, the current frontend integration may stop working correctly. **I suggest we keep** `isActive` for one release while the frontend migrates. **Once the frontend has switched to** `status`, we can remove the old field. **Could you confirm whether that migration window works for your team?**”

## 13. Thử nói lại theo cách của bạn

Hãy chọn một API, database field hoặc integration thật trong công việc hiện tại và nói lại theo template sau:

- **Context:** What API or integration are we discussing?
- **What happened:** What contract or field is changing?
- **My current understanding:** Why is the change needed?
- **Missing information:** Which consumer or timeline still needs confirmation?
- **My proposed action:** What migration or compatibility plan do I suggest?
- **Expected next update:** When should the teams confirm or complete the migration?

Bạn không cần dùng câu phức tạp. Mục tiêu là giúp team khác hiểu rõ **change, impact và next step**.

## 14. Tóm tắt cần ghi nhớ

### 3 câu nên nhớ

1. “I want to flag an upcoming change to the API response.”
2. “The current field will be replaced by two new fields.”

### Lỗi cần tránh

- Chỉ nói “The API changed” mà không nói field nào thay đổi.

- Đổ trách nhiệm cho consumer bằng câu như “Your UI will break” thay vì mô tả dependency một cách trung lập.

### Thử thách hôm nay

**Change → Reason → Impact → Migration plan → Confirmation**
