# Daily Workplace English — Ngày 34

- **Ngày:** 17/08/2026 (UTC+7)
- **Tình huống công việc:** Làm rõ edge cases trước khi implement một thay đổi trong API
- **Kỹ năng giao tiếp chính:** Hỏi về các trường hợp biên một cách có cấu trúc để tránh implement sai requirement
- **Thời gian học:** 20–25 phút
- **Độ khó:** Lower-intermediate

## 1. Tình huống hôm nay

Bạn đang chuẩn bị implement một thay đổi cho ASP.NET Core API. Requirement nói rằng user có thể cập nhật trạng thái của một record từ `Active` sang `Inactive`. Happy path khá rõ, nhưng một số edge case chưa được mô tả: chuyện gì xảy ra nếu record đã là `Inactive`, nếu request được gửi hai lần, hoặc nếu record không còn tồn tại.

Những người liên quan gồm bạn, Product Owner và QA engineer. Bạn cần hỏi để làm rõ behavior trước khi code và trước khi QA viết test case.

Rủi ro giao tiếp là hỏi quá chung chung như “What about edge cases?” khiến người khác khó trả lời, hoặc tự giả định behavior rồi implement luôn. Cách tốt hơn là nêu từng scenario cụ thể, đưa ra cách hiểu hiện tại của bạn và yêu cầu xác nhận.

## 2. Bạn cần nói gì?

Mục tiêu giao tiếp hôm nay:

- Xác nhận happy path mà bạn đã hiểu.
- Nêu rõ từng edge case chưa được định nghĩa.
- Đưa ra proposed behavior khi hợp lý.
- Hỏi Product Owner xác nhận thay vì tự quyết định.
- Giúp QA có expected result rõ ràng để viết test.

Cấu trúc nên dùng:

**Current understanding → Edge case → Proposed behavior → Confirmation**

## 3. Đoạn hội thoại hoặc mẫu trình bày

**Developer:** “I understand that an active record can be changed to inactive.”  
*Mình hiểu rằng một record đang active có thể được chuyển sang inactive.*

**Developer:** “I’d like to clarify a few edge cases before I start the implementation.”  
*Mình muốn làm rõ một vài trường hợp biên trước khi bắt đầu implement.*

**Developer:** “If the record is already inactive, should we return `200 OK` and keep the current state?”  
*Nếu record đã inactive rồi, chúng ta có nên trả `200 OK` và giữ nguyên trạng thái hiện tại không?*

**Product Owner:** “Yes, that sounds right.”  
*Đúng, như vậy hợp lý.*

**Developer:** “What should happen if the same request is sent twice?”  
*Nếu cùng một request được gửi hai lần thì behavior mong muốn là gì?*

**Product Owner:** “The second request should not create any additional side effect.”  
*Request thứ hai không nên tạo thêm side effect nào.*

**Developer:** “Got it. And if the record no longer exists, should the API return `404 Not Found`?”  
*Hiểu rồi. Còn nếu record không còn tồn tại thì API nên trả `404 Not Found`, đúng không?*

**Product Owner:** “Yes.”  
*Đúng.*

**Developer:** “Thanks. I’ll document these cases in the API notes so QA can use the same expected behavior.”  
*Cảm ơn. Mình sẽ ghi lại các trường hợp này trong API notes để QA dùng cùng một expected behavior.*

## 4. Các cụm từ quan trọng

### 1. “I’d like to clarify…”
- **Nghĩa:** Tôi muốn làm rõ…
- **Khi dùng:** Khi requirement còn thiếu hoặc có thể hiểu theo nhiều cách.
- **Ví dụ:** “I’d like to clarify how retries should be handled.”

### 2. “What should happen if…?”
- **Nghĩa:** Điều gì nên xảy ra nếu…?
- **Khi dùng:** Hỏi expected behavior cho một scenario cụ thể.
- **Ví dụ:** “What should happen if the external service is unavailable?”

### 3. “If …, should we …?”
- **Nghĩa:** Nếu … thì chúng ta có nên … không?
- **Khi dùng:** Khi bạn muốn đưa ra một proposed behavior để người khác xác nhận.
- **Ví dụ:** “If the token has expired, should we return `401 Unauthorized`?”

### 4. “My current understanding is…”
- **Nghĩa:** Cách hiểu hiện tại của tôi là…
- **Khi dùng:** Khi bạn muốn nói rõ assumption trước khi hỏi.
- **Ví dụ:** “My current understanding is that the API should remain backward compatible.”

### 5. “Does that match the expected behavior?”
- **Nghĩa:** Điều đó có đúng với behavior mong muốn không?
- **Khi dùng:** Cuối phần giải thích để xác nhận alignment.
- **Ví dụ:** “We’ll retry three times and then move the message to the dead-letter queue. Does that match the expected behavior?”

### 6. “I’ll document these cases…”
- **Nghĩa:** Tôi sẽ ghi lại các trường hợp này…
- **Khi dùng:** Khi muốn chốt action để tránh hiểu sai sau cuộc trao đổi.
- **Ví dụ:** “I’ll document these cases in the ticket after the meeting.”

## 5. Từ vựng trong tình huống

### 1. edge case — noun
- **IPA:** /ˈedʒ keɪs/
- **Nghĩa:** trường hợp biên, ít phổ biến nhưng cần xử lý đúng
- **Ví dụ:** “We should clarify the edge cases before implementation.”
- **Collocation:** handle an edge case, test an edge case

### 2. side effect — noun
- **IPA:** /ˈsaɪd ɪˌfekt/
- **Nghĩa:** tác động phụ do một thao tác gây ra
- **Ví dụ:** “The repeated request should not create another side effect.”
- **Collocation:** unwanted side effect, avoid side effects

### 3. idempotent — adjective
- **IPA:** /ˌaɪdəmˈpoʊtənt/
- **Nghĩa:** gọi nhiều lần vẫn cho cùng trạng thái cuối cùng mà không tạo tác động lặp ngoài ý muốn
- **Ví dụ:** “This update operation should be idempotent.”
- **Collocation:** idempotent operation, idempotent endpoint

### 4. expected behavior — noun phrase
- **IPA:** /ɪkˈspektɪd bɪˈheɪvjər/
- **Nghĩa:** hành vi mong đợi
- **Ví dụ:** “QA needs the expected behavior for duplicate requests.”
- **Collocation:** define expected behavior, confirm expected behavior

### 5. assumption — noun
- **IPA:** /əˈsʌmpʃən/
- **Nghĩa:** giả định
- **Ví dụ:** “I want to confirm this assumption before coding.”
- **Collocation:** make an assumption, validate an assumption

## 6. Mẫu câu hoặc ngữ pháp cần nhớ

### Conditional question: “If + present simple, should + subject + base verb?”

**Cấu trúc:**

`If + present simple, should + subject + base verb?`

Ví dụ:

- “If the record is already inactive, should we return `200 OK`?”
- “If the user does not exist, should we return `404 Not Found`?”

**Ý nghĩa:** Dùng để hỏi behavior mong muốn cho một điều kiện cụ thể.

**Khi dùng:** Rất hữu ích khi clarify requirements, đặc biệt với API behavior, validation, retry, permissions hoặc error handling.

**Lỗi thường gặp:**

Không dùng `will` trong mệnh đề `if` cho dạng câu hỏi này.

Sai: “If the record will be inactive, should we return `200`?”  
Đúng: “If the record is inactive, should we return `200`?”

## 7. Cách nói tự nhiên hơn

### Chưa tự nhiên hoặc quá trực tiếp

“What about edge cases?”

### Tự nhiên và chuyên nghiệp hơn

“I’d like to clarify a few edge cases before I start the implementation.”

### Giải thích

Câu thứ hai cho người nghe context rõ hơn: bạn cần clarify trước khi code, chứ không chỉ hỏi một câu quá rộng.

### Chưa tự nhiên hoặc quá trực tiếp

“If duplicate request, return what?”

### Tự nhiên và chuyên nghiệp hơn

“What should happen if the same request is sent twice?”

### Giải thích

Tiếng Việt thường lược bỏ chủ ngữ và trợ động từ, nhưng trong tiếng Anh câu hoàn chỉnh sẽ tự nhiên và chuyên nghiệp hơn.

### Chưa tự nhiên hoặc quá trực tiếp

“I think return 404 is correct.”

### Tự nhiên và chuyên nghiệp hơn

“My current assumption is that we should return `404 Not Found`. Does that match the expected behavior?”

### Giải thích

Cách thứ hai tách rõ đây là assumption cần xác nhận, thay vì biến suy đoán kỹ thuật của bạn thành requirement chính thức.

## 8. Phát âm và luyện nói

### “I’d like to clarify…”
- Nhấn: **LIKE**, **CLARIFY**
- `I’d like to` thường nối âm khá nhanh.
- Có thể ngắt nhẹ sau `clarify` nếu câu tiếp theo dài.
- Gợi ý gần đúng cho người Việt: tập nói liền cụm `I'd-like-to`, không tách từng từ quá mạnh.

### “What should happen if…?”
- Nhấn: **WHAT**, **HAPPEN**
- `should` thường nhẹ hơn từ nội dung chính.
- Có thể ngắt nhẹ sau phần điều kiện dài.

### “Does that match the expected behavior?”
- Nhấn: **MATCH**, **EXPECTED BEHAVIOR**
- `Does that` có thể nối khá nhanh trong speech tự nhiên.
- Giữ giọng lên nhẹ ở cuối vì đây là câu hỏi xác nhận.

### Shadowing script

“I’d like to clarify a few edge cases before I start the implementation.”  
“If the record is already inactive, should we keep the current state?”  
“What should happen if the same request is sent twice?”  
“Does that match the expected behavior?”

Luyện theo 5 bước:

1. Đọc chậm từng câu.
2. Nghe bằng Text-to-Speech nếu có.
3. Lặp lại từng câu một.
4. Ghi âm giọng của bạn.
5. Nói lại toàn bộ đoạn mà không nhìn văn bản.

## 10. Bài tập thực hành chủ động

### Scenario

Bạn đang implement một endpoint mới để deactivate user account. Requirement hiện chỉ nói: “Admins can deactivate an active user.”

### Nhiệm vụ

Viết hoặc nói một đoạn 5–7 câu để hỏi Product Owner về ba edge cases:

- User đã inactive.
- User không tồn tại.
- Cùng request được gửi hai lần.

### Cấu trúc gợi ý

1. Nói cách hiểu hiện tại.
2. Nêu edge case thứ nhất.
3. Đề xuất behavior.
4. Nêu edge case thứ hai.
5. Nêu edge case thứ ba.
6. Xin xác nhận.

### Useful phrases

- “My current understanding is…”
- “I’d like to clarify…”
- “What should happen if…?”
- “If …, should we …?”
- “Does that match the expected behavior?”

### Tiêu chí hoàn thành

- Có ít nhất 5 câu tiếng Anh.
- Có đủ ba edge cases.
- Có ít nhất hai câu hỏi conditional.
- Có câu xác nhận cuối cùng.

## 12. Mẫu trả lời tham khảo

“My current understanding is that admins can deactivate an active user. **I’d like to clarify a few edge cases before I start the implementation.** If the user is already inactive, **should we return `200 OK` and keep the current state?** If the user does not exist, should we return `404 Not Found`? Also, what should happen if the same request is sent twice? My assumption is that the operation should be idempotent and should not create any additional side effect. **Does that match the expected behavior?**”

Các mẫu nên tái sử dụng:

- **I’d like to clarify…**
- **If …, should we …?**
- **My assumption is that…**
- **Does that match the expected behavior?**
