### dotnetpower/fdai — `Semantic query planner cannot ground enumerated property values`

**Issue link:** https://github.com/dotnetpower/fdai/issues/161  
**Labels:** `bug`, `needs-triage`  
**Issue status:** Open, chưa assign, 0 comment tại thời điểm kiểm tra  
**Difficulty:** Intermediate–Advanced  
**Estimated effort:** One day / Several days  
**Potential contribution value:** High

**Confirmed facts:**

- Planner hiện nhận property names, types và access scope nhưng không nhận allowed/enumerated values.
- Với truy vấn theo category như `database`, planner tạo predicate `type == database`, trong khi dữ liệu thực dùng các id như `sql-database`, `postgresql-server`, `mysql-server`, `nosql-database`, `redis-enterprise`.
- Vocabulary đã tồn tại trong `rule-catalog/vocabulary/resource-types.yaml` và `inventory-query-language.yaml`, nhưng chưa được đưa vào planner.
- Issue chỉ ra hai vị trí liên quan trực tiếp: `query_manifest.py::_descriptor` và `PropertyDecl` trong ontology contracts.
- Issue yêu cầu ungrounded value phải dẫn tới clarification/unsupported disposition thay vì trả `0 of 0 rows` như thể truy vấn hợp lệ.
- Chưa tìm thấy open PR liên quan trực tiếp đến #161 tại thời điểm kiểm tra.

**Analysis:** đây là một lỗi điển hình của semantic query planning: schema biết “field nào tồn tại” nhưng model không có đủ ontology để map từ ngôn ngữ người dùng sang canonical value. Đây là vấn đề rất gần với RAG, agent planning, MCP tool schema và natural-language-to-query systems.

**Opportunity:** ngay cả khi chưa code, việc thiết kế một “value grounding contract” nhỏ cho issue này là bài tập tốt về boundary giữa ontology metadata, planner prompt/context và deterministic resolver.

**Risk or uncertainty:** issue đang có label `needs-triage`, chưa có maintainer response và còn ít nhất ba hướng thiết kế được nêu trong issue. Không nên bắt đầu refactor lớn trước khi maintainer xác nhận preferred approach.

### Suggested contribution plan

1. Reproduce query `database + name contains fdai` và xác nhận planner thực sự emit canonicality sai.
2. Đọc `query_manifest.py`, `PropertyDecl` và hai vocabulary YAML để hiểu contract hiện tại.
3. Comment hỏi maintainer muốn ưu tiên `allowed-values facet` trong manifest hay một deterministic resolution step riêng.
4. Nếu được xác nhận, implement smallest path chỉ cho enumerated values, không mở rộng toàn bộ ontology model.
5. Add focused tests cho category → concrete ids và unknown category → clarification.
6. Chuẩn bị PR ghi rõ tác động tới manifest digest và backward compatibility.

**Sample comment:**

Before implementing, would you prefer the vocabulary to be projected into the query manifest as an explicit allowed-value facet, or kept behind a separate deterministic value-resolution step? I can start with a focused test covering `database -> concrete resource type ids` and the ungrounded-value clarification path.
