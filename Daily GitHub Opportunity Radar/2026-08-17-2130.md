## 5. Tool I Can Apply Today

**Tool:** GitHub Actions deployment concurrency + runtime deployment verification pattern  
**Problem it solves:** tránh workflow báo trạng thái “ổn” trong khi production chưa chạy build mới hoặc deploy bị cancel/skip  
**Relevant workflow:** GitHub Actions CI/CD, Docker deployment, Azure/self-hosted deployment  
**Adoption difficulty:** Easy  
**Production readiness:** Production-ready pattern; cách triển khai cụ thể tùy project

**Confirmed facts:** Muhabbet #573/#574 cho thấy `cancel-in-progress` có thể tạo deployment race và workflow conclusion không đủ để xác nhận deployment thực tế.

**Analysis:** với các project .NET/Docker/GitHub Actions, nên tách hai khái niệm: “workflow completed” và “target environment runs expected revision”.

**Integration approach:**
- deploy artifact/image được gắn commit SHA;
- app expose build SHA/version qua endpoint hoặc health metadata;
- job cuối gọi target environment và so sánh revision với `${{ github.sha }}`;
- nếu dùng Docker/self-hosted runner, có thể kiểm tra image digest/container metadata;
- production deploy concurrency thường nên queue nếu từng deploy có side effect và không an toàn khi bị kill giữa chừng.

**Required permissions/data access:** read deployment target hoặc endpoint version; không cần quyền rộng hơn deploy workflow hiện có nếu version endpoint public/internal-read-only.

**Privacy/security concerns:** không expose secret/config trong `/version`; chỉ trả commit/build identifier cần thiết.

**Maintenance burden:** thấp nếu build metadata được chuẩn hóa ngay từ pipeline.

**Smallest proof of concept:** thêm `APP_COMMIT_SHA` vào Docker image/.NET configuration, expose `/version`, rồi thêm post-deploy check rằng response bằng SHA đang deploy.
