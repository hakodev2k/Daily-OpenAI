- Issue đã thử `context.SetOfflineAsync(true)` và `context.RouteAsync(...AbortAsync())`; service-worker fetch vẫn đi tới server.
- Hướng được đề xuất là tạo local forwarding proxy rồi stop proxy để cắt network thật ở browser context.
- Acceptance criterion rất cụ thể: bỏ được hai `Skip` và giữ negative control xác nhận network thực sự unavailable.

**Analysis:**
- Đây là contribution tốt hơn một docs-only issue vì buộc phải hiểu boundary giữa Playwright routing, browser networking và service worker target.
- Kỹ năng học được có thể áp dụng trực tiếp cho E2E/offline tests, proxy-based fault injection và flaky-test diagnosis.

**Relevant files / technologies:**
- `ServiceWorkerBehaviourTests`
- Microsoft.Playwright for .NET
- BrowserContext proxy configuration
- Minimal TCP/HTTP forwarding proxy fixture
- Service Worker cache/offline behavior

**Questions nên hỏi maintainer:**
- Có chấp nhận embedded lightweight proxy fixture trong test project hay muốn test infrastructure riêng?
- Proxy chỉ cần HTTP hay phải hỗ trợ HTTPS CONNECT?
- Test có cần chạy cross-browser hay Chromium-only là đủ cho first PR?

**Risk contribution may not be accepted:** Low–Medium. Scope đã rõ nhưng proxy implementation có thể bị maintainer yêu cầu đổi nếu quá phức tạp.

### Suggested contribution plan

1. Chạy hai skipped tests và xác nhận negative control hiện tại không cắt được network của worker.
2. Đọc fixture setup và cách test server được khởi động.
3. Comment trên issue với thiết kế minimal proxy + stop/start lifecycle.
4. Implement proxy nhỏ nhất có thể, không đưa thêm dependency nếu chưa cần.
5. Bật lại hai tests và thêm cleanup để không rò socket/process giữa test runs.
6. Chạy test lặp nhiều lần rồi mở PR với giải thích vì sao page routing không đủ.

**Sample comment:**

> Hi, I’d like to take this issue. I plan to reproduce the two skipped tests first, then add a minimal local forwarding proxy to the test fixture so the proxy can be stopped to make the network unavailable to both the page and service worker. I’ll keep the existing negative control and avoid production-code changes. Is Chromium-only coverage acceptable for the first PR, or do you want the fixture validated across all Playwright browsers?
