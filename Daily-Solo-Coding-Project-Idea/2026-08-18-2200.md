# Ý tưởng hôm nay: Local Knowledge Sync Agent

## 1. Tóm tắt ý tưởng
Một công cụ self-hosted giúp developer đồng bộ tài liệu kỹ thuật cá nhân (README, Markdown, PDF, source notes, API docs) thành một kho kiến thức có tìm kiếm thông minh và hỗ trợ hỏi đáp theo ngữ cảnh. Dự án Medium, MVP khoảng 3-4 tuần.

## 2. Bài toán thực tế
Developer thường lưu kiến thức ở nhiều nơi: repository, OneNote, Notion, file Markdown, tài liệu nội bộ. Khi dự án lớn dần, việc nhớ tài liệu nào nằm ở đâu và tìm lại quyết định kỹ thuật cũ trở nên tốn thời gian.

Giả định MVP tập trung vào developer cá nhân hoặc team nhỏ, không thay thế hoàn toàn hệ thống quản lý tài liệu doanh nghiệp.

## 3. Người dùng mục tiêu
.NET developer, technical lead hoặc solo builder có nhiều repository và tài liệu kỹ thuật cá nhân.

Pain point chính: mất thời gian tìm lại thông tin đã từng đọc hoặc tự viết.

## 4. Giải pháp đề xuất
Người dùng kết nối thư mục chứa tài liệu → hệ thống scan file → trích xuất nội dung → lập chỉ mục → cho phép tìm kiếm và hỏi đáp.

Ví dụ: Developer hỏi "Project A đang xử lý retry RabbitMQ như thế nào?". Hệ thống tìm trong tài liệu và trả lời kèm nguồn file liên quan.

Điểm khác biệt: ưu tiên self-hosted, dữ liệu thuộc quyền kiểm soát của developer, không phụ thuộc vào cloud knowledge platform.

## 5. Tại sao ý tưởng này đáng làm
Có giá trị ngay cả khi chỉ dùng cá nhân. Dự án giúp học document indexing, search, embedding, background processing và AI integration.

Lý do không nên làm: thị trường có nhiều công cụ knowledge management. Giá trị phải nằm ở workflow cho developer và khả năng chạy local.

## 6. Phạm vi MVP

### Must have
- Import Markdown, TXT, PDF
- Theo dõi thư mục tài liệu
- Full-text search
- Lưu metadata tài liệu
- CLI hoặc web UI đơn giản

### Should have
- Vector search
- Git repository integration
- Auto re-index khi file thay đổi
- Export knowledge snapshot

### Later
- Multi-user
- Agent workflow
- IDE extension
- Team permission

## 7. Luồng hoạt động
File mới xuất hiện → worker phát hiện thay đổi → validate định dạng → extract text → lưu database → tạo index → người dùng tìm kiếm hoặc hỏi → trả kết quả.

Failure case:
- File lỗi format → đánh dấu failed.
- AI không khả dụng → fallback sang keyword search.

## 8. Kiến trúc đề xuất
Modular monolith:

- Web API quản lý tài liệu và search.
- Worker xử lý indexing nền.
- Database lưu metadata.
- File storage giữ tài liệu gốc.
- Search engine phục vụ truy vấn.

Không cần microservice hoặc Kubernetes cho MVP.

## 9. Công nghệ đề xuất

- .NET 8/9 + ASP.NET Core: phù hợp backend và background worker.
- EF Core + PostgreSQL: lưu metadata và trạng thái xử lý.
- PostgreSQL Full Text Search trước, có thể thêm vector extension sau.
- Vue hoặc Blazor cho UI.
- Docker để chạy self-hosted.
- GitHub Actions để build/test.

Đơn giản hơn: SQLite + console app cho phiên bản cá nhân.

## 11. API và tích hợp

- File system watcher: theo dõi tài liệu local.
- Git repository: lấy README và source documentation.
- PDF parser library: đọc tài liệu.
- AI API tùy chọn: tạo embedding hoặc trả lời.

Privacy: tài liệu nhạy cảm nên hỗ trợ local model hoặc tắt AI.

## 12. AI có thực sự cần thiết không?
AI hữu ích nhưng optional.

Nhiệm vụ:
- Tạo embedding cho semantic search.
- Tổng hợp câu trả lời từ nhiều tài liệu.

Validation:
- Luôn hiển thị nguồn tham chiếu.
- Không cho phép AI tự tạo thông tin ngoài context.

Fallback: keyword search truyền thống.

## 13. Kế hoạch triển khai

### Phase 0 — Validation
Mục tiêu: xác nhận bản thân có nhu cầu.

Tạo tool scan một repository cá nhân và tìm kiếm tài liệu.

### Phase 1 — Core MVP
Xây parser, database, search API, UI cơ bản.

Hoàn thành khi tìm được tài liệu theo keyword.

### Phase 2 — Reliability
Thêm retry, logging, test, xử lý file lỗi.

### Phase 3 — Useful expansion
Thêm semantic search và Git integration.

### Phase 4 — Production readiness
Docker image, backup, monitoring, documentation.

## 14. Các bài toán kỹ thuật đáng học

- Document indexing: học pipeline xử lý dữ liệu.
- Incremental sync: học đồng bộ dữ liệu thay đổi.
- Search ranking: cải thiện trải nghiệm tìm kiếm.
- AI context retrieval: học RAG thực tế.
- Background processing: học workflow dài hạn.

## 15. Rủi ro và cách xử lý

- Scope quá lớn → chỉ hỗ trợ vài định dạng đầu tiên.
- Chi phí AI → dùng embedding local hoặc giới hạn.
- Privacy → ưu tiên self-hosted.
- Search không chính xác → cho phép xem nguồn gốc.

## 16. Kiểm thử

Năm scenario quan trọng:

1. Import file Markdown thành công.
2. File thay đổi được cập nhật index.
3. File lỗi không làm worker dừng.
4. Search trả đúng tài liệu liên quan.
5. AI không trả thông tin ngoài context.

## 17. Cách đo dự án có hữu ích hay không

- Thời gian tìm tài liệu giảm.
- Số lần sử dụng mỗi tuần.
- Tỷ lệ tìm thấy câu trả lời trong lần đầu.
- Thời gian indexing.
- Tỷ lệ lỗi xử lý tài liệu.

## 20. Việc cần làm ngay hôm nay

Trong 60-120 phút:

1. Tạo solution:

```
dotnet new webapi -n KnowledgeSync.Api
```

2. Tạo module:

- DocumentScanner
- DocumentRepository
- SearchService

3. Đọc một thư mục Markdown mẫu.

4. Lưu metadata vào SQLite/PostgreSQL.

5. Tạo API:

```
GET /documents/search?q=retry
```

Kết quả mong đợi: gọi API trả về danh sách file chứa nội dung tìm kiếm.

Dừng khi vertical slice đầu tiên hoạt động end-to-end.
