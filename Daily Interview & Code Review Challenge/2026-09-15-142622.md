# Code Review Challenge 1 — Optimistic concurrency bị biến thành lost update bởi retry mù

**Chủ đề:** C#/.NET, EF Core, optimistic concurrency, transactions, HTTP API, correctness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API quản lý approval request. Nhiều người có thể mở cùng một request; approver thay đổi `Status`, còn owner có thể sửa `Title` và `Description`. Entity đã có SQL Server `rowversion` để phát hiện concurrent update.

Sau khi team thêm retry để “giảm lỗi concurrency”, production gần như không còn trả conflict nhưng support phát hiện thỉnh thoảng thay đổi của người dùng khác bị mất. Requirement chưa nói rằng last-write-wins là chấp nhận được.

## Đoạn code cần review

```csharp
public sealed record UpdateApprovalRequest(
    string Title,
    string Description,
    string Status);

[HttpPut("approval-requests/{id:guid}")]
public async Task<IActionResult> Update(
    Guid id,
    UpdateApprovalRequest request,
    CancellationToken cancellationToken)
{
    for (var attempt = 0; attempt < 3; attempt++)
    {
        var entity = await _db.ApprovalRequests
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (entity is null)
            return NotFound();

        entity.Title = request.Title;
        entity.Description = request.Description;
        entity.Status = request.Status;

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
            return Ok(entity);
        }
        catch (DbUpdateConcurrencyException)
        {
            foreach (var entry in _db.ChangeTracker.Entries())
            {
                await entry.ReloadAsync(cancellationToken);
            }
        }
    }

    return StatusCode(StatusCodes.Status500InternalServerError);
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong concurrency handling.
2. Giải thích vì sao retry hiện tại có thể ghi đè thay đổi hợp lệ của user khác.
3. Phân tích API contract còn thiếu để client có thể tham gia optimistic concurrency.
4. Ưu tiên findings theo severity và business impact.
5. Đề xuất corrected design mà không mặc định dùng pessimistic locking.
6. Nêu tests cho concurrent edits, conflict resolution và cancellation.
7. Nêu telemetry giúp phân biệt expected conflict với infrastructure/database failure.

## Câu hỏi gợi mở

1. Sau `ReloadAsync`, giá trị nào trở thành current/original values trong tracked entity?
2. Request có mang version mà user thực sự đã đọc không?
3. Nếu approver đổi `Status` giữa lúc owner đọc và save, API nên merge, reject hay overwrite?
4. Retry có còn an toàn nếu operation mang business intent thay vì chỉ là transient infrastructure operation?
5. HTTP response nào giúp client hiểu đây là concurrency conflict thay vì server failure?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **retry thay đổi semantics của optimistic concurrency**.

### Gợi ý 2

Concurrency token chỉ hữu ích nếu update được so với version mà caller đã quan sát và conflict được xử lý theo business rule rõ ràng.

## Kết quả code review tham khảo

### Critical — Client không gửi concurrency version đã đọc

**Vấn đề:** Update request không chứa `rowversion`/ETag hoặc concurrency precondition tương đương.

**Tại sao xảy ra:** Server query lại entity ngay trước mỗi save, nên concurrency check chỉ bảo vệ khoảng thời gian rất ngắn giữa query và save, không bảo vệ user editing session.

**Ảnh hưởng production:** Một user có thể ghi đè dữ liệu được người khác thay đổi sau thời điểm họ mở màn hình mà API không nhận biết business-level stale edit.

**Cách sửa:** Trả version cho client khi đọc và yêu cầu version đó khi update, ví dụ ETag/`If-Match` hoặc DTO field phù hợp. Gắn version client gửi vào concurrency original value trước `SaveChangesAsync`.

### Critical — Retry mù sau conflict có thể biến conflict thành lost update

**Vấn đề:** Handler reload database state rồi tiếp tục vòng lặp và áp lại toàn bộ payload.

**Tại sao xảy ra:** Retry không giải quyết business conflict; nó chỉ lấy version mới rồi thử ghi cùng intent lên state mới mà không hỏi liệu merge có hợp lệ.

**Ảnh hưởng production:** Thay đổi của concurrent user có thể bị overwrite và conflict biến mất khỏi quan sát của caller.

**Cách sửa:** Với semantic conflict, trả conflict/precondition failure kèm current version/data cần thiết hoặc thực hiện merge chỉ theo explicit domain rule. Không retry mù.

### High — Whole-resource PUT cho phép owner vô tình ghi đè field thuộc workflow

**Vấn đề:** DTO cho phép caller cập nhật cả `Status`, `Title`, `Description` mà không thể hiện ownership/authorization từng transition.

**Tại sao xảy ra:** API contract trộn content editing và approval state transition.

**Ảnh hưởng production:** Ngoài concurrency, caller có thể thay đổi workflow state ngoài intent/permission nếu authorization chỉ ở endpoint level.

**Cách sửa:** Tách command/endpoint theo business intent hoặc validate policy/allowed transition rõ ràng. Chỉ update fields operation sở hữu.

### High — Reload toàn bộ ChangeTracker là phạm vi quá rộng

**Vấn đề:** Catch block reload mọi tracked entry.

**Tại sao xảy ra:** Handler giả định context chỉ chứa một entity và mọi entry đều thuộc conflict.

**Ảnh hưởng production:** Nếu action/interceptor/domain logic track thêm entity, state có thể bị thay đổi ngoài ý muốn và tạo extra database round trips.

**Cách sửa:** Xử lý chính xác entries trong `DbUpdateConcurrencyException.Entries` và theo conflict policy của từng entity.

### High — Conflict bị trả thành HTTP 500 sau ba lần

**Vấn đề:** Expected concurrency conflict cuối cùng trở thành generic server error.

**Tại sao xảy ra:** Infrastructure retry model được áp cho business concurrency.

**Ảnh hưởng production:** Client không biết cần refresh/reconcile; monitoring ghi nhận false server-failure signal.

**Cách sửa:** Dùng API semantics rõ, ví dụ `412 Precondition Failed` khi dùng `If-Match`, hoặc `409 Conflict` khi contract phù hợp, cùng machine-readable `ProblemDetails`.

### Medium — Không phân biệt transient database failure với concurrency conflict

**Vấn đề:** Retry loop chỉ bắt concurrency nhưng naming/behavior dễ dẫn tới suy nghĩ mọi retry đều giống nhau.

**Tại sao xảy ra:** Optimistic conflict là concurrent business state, không phải mặc định là transient connectivity issue.

**Ảnh hưởng production:** Retry policy khó reasoning và có thể mở rộng sai sang side effects khác.

**Cách sửa:** Tách retry cho transient infrastructure failures khỏi conflict resolution. Mỗi loại có policy và telemetry riêng.

### Medium — Response trả tracked entity trực tiếp

**Vấn đề:** `Ok(entity)` coupling persistence model với API contract và version exposure có thể không nhất quán.

**Tại sao xảy ra:** Không có explicit response DTO/ETag policy.

**Ảnh hưởng production:** Contract khó evolve và client có thể không nhận concurrency token theo format ổn định.

**Cách sửa:** Map sang response DTO và trả version/ETag rõ ràng.

### Low — Không có structured conflict telemetry

**Vấn đề:** Conflict bị catch nhưng không có metric/log có kiểm soát.

**Tại sao xảy ra:** Handler coi conflict chỉ là exception cần retry.

**Ảnh hưởng production:** Không biết conflict rate theo endpoint/entity/version và không phát hiện UX/workflow contention.

**Cách sửa:** Metric conflict count/rate, structured identifiers không nhạy cảm và trace correlation; không log toàn bộ payload.

## Phiên bản đề xuất

Ví dụ dưới đây dùng version trong DTO; với HTTP API có thể chuyển cùng semantics sang ETag/`If-Match`:

```csharp
public sealed record UpdateApprovalContentRequest(
    string Title,
    string Description,
    byte[] Version);

[HttpPut("approval-requests/{id:guid}/content")]
public async Task<IActionResult> UpdateContent(
    Guid id,
    UpdateApprovalContentRequest request,
    CancellationToken cancellationToken)
{
    var entity = await _db.ApprovalRequests
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (entity is null)
        return NotFound();

    _db.Entry(entity)
        .Property(x => x.Version)
        .OriginalValue = request.Version;

    entity.Title = request.Title;
    entity.Description = request.Description;

    try
    {
        await _db.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateConcurrencyException)
    {
        var current = await _db.ApprovalRequests
            .AsNoTracking()
            .Where(x => x.Id == id)
            .Select(x => new
            {
                x.Id,
                x.Title,
                x.Description,
                x.Status,
                x.Version
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (current is null)
            return NotFound();

        return Conflict(new ProblemDetails
        {
            Title = "Approval request was modified by another user",
            Detail = "Refresh or reconcile your changes before retrying.",
            Status = StatusCodes.Status409Conflict
        });
    }

    return Ok(new
    {
        entity.Id,
        entity.Title,
        entity.Description,
        entity.Status,
        entity.Version
    });
}
```

Nếu contract dùng ETag, server có thể trả ETag từ version khi GET và yêu cầu `If-Match` khi update; khi precondition không còn đúng, `412` là lựa chọn tự nhiên. Exact mapping cần nhất quán với API conventions của hệ thống.

## Giải thích thiết kế sau khi sửa

Concurrency version đại diện state mà caller đã quan sát. Database concurrency predicate so sánh version đó với current row; nếu khác, server không tự quyết định rằng payload cũ được phép overwrite state mới.

Tách content edit khỏi status transition làm business intent rõ hơn và giảm vùng conflict. Nếu domain cho phép merge field-level, merge phải là explicit rule: ví dụ content fields và workflow state độc lập có thể được xử lý bằng command riêng, không phải generic retry.

Không mặc định dùng lock dài qua user editing session. Optimistic concurrency phù hợp khi conflict tương đối hiếm và UX có thể refresh/reconcile.

## Trade-offs

- Client phải lưu/gửi version và xử lý conflict UX.
- Tách command tăng số endpoint/type nhưng làm ownership rõ hơn.
- Field-level merge giảm false conflict nhưng tăng domain complexity.
- Pessimistic locking có thể giảm conflict trong một số workflow ngắn nhưng tăng blocking/deadlock/operational cost và không phù hợp với user think-time dài.

## Cách kiểm thử

1. **Concurrency integration test:** hai clients đọc cùng version; client A save trước, client B phải nhận conflict/precondition failure.
2. **Workflow test:** owner content update không được thay đổi `Status` nếu operation không sở hữu field đó.
3. **Delete race test:** entity bị xóa sau khi client đọc; response phải theo contract rõ thay vì 500.
4. **Cancellation test:** request bị abort trong database operation; cancellation được propagate và không bị biến thành conflict.
5. **Telemetry test:** expected conflict tăng metric riêng nhưng không làm tăng generic 5xx alert.

## Quan sát trong production

Theo dõi concurrency conflict rate theo endpoint/entity type, 409/412 rate, request latency và database dependency duration. Structured logs nên có trace ID, entity ID và operation name nhưng tránh raw sensitive payload. Nếu conflict tăng sau UI/process change, correlation với user workflow có thể cho thấy command boundary quá rộng thay vì database có lỗi.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào field-level merge an toàn hơn reject toàn bộ update?
2. Nếu approval transition có external side effect, bạn xử lý concurrency và retry khác thế nào?
3. Bạn chọn ETag/`If-Match` hay version field trong JSON dựa trên tiêu chí nào?

# Code Review Challenge 2 — Playwright suite “ổn” nhờ retry nhưng thực tế các parallel workers đang dùng chung dữ liệu

**Chủ đề:** Playwright, TypeScript, E2E testing, parallelism, test isolation, CI/CD, flaky tests, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một portal nội bộ có Playwright E2E suite chạy trong CI. Để giảm thời gian pipeline, team bật parallel workers. Sau đó test bắt đầu flaky nên cấu hình thêm retries. Pipeline thường xanh sau retry nhưng tổng thời gian dao động mạnh và thỉnh thoảng production bug lọt qua vì team không còn tin failure đầu tiên.

Các tests dùng chung một account và cùng một approval request seed. Backend test environment là shared environment cho nhiều CI jobs. Team muốn giữ E2E suite có signal cao, không đơn giản tăng retry hoặc chạy serial toàn bộ.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const approvalId = 'seed-approval-001';

async function login(page) {
  await page.goto('/login');
  await page.getByLabel('Email').fill('qa-user@example.test');
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
}

test.describe('approval workflow', () => {
  test.beforeEach(async ({ page, request }) => {
    await request.post(`/test-api/approvals/${approvalId}/reset`);
    await login(page);
  });

  test('approves request', async ({ page }) => {
    await page.goto(`/approvals/${approvalId}`);
    await page.getByRole('button', { name: 'Approve' }).click();
    await page.waitForTimeout(1000);
    await expect(page.getByText('Approved')).toBeVisible();
  });

  test('rejects request', async ({ page }) => {
    await page.goto(`/approvals/${approvalId}`);
    await page.getByRole('button', { name: 'Reject' }).click();
    await page.waitForTimeout(1000);
    await expect(page.getByText('Rejected')).toBeVisible();
  });
});
```

CI config hiện chạy 6 workers và `retries: 2`. Hai pipeline của các pull requests khác nhau có thể chạy cùng lúc trên cùng test environment.

## Nhiệm vụ của ứng viên

1. Xác định nguyên nhân flaky liên quan test data và parallel execution.
2. Review synchronization/wait strategy và assertion quality.
3. Giải thích vì sao retry có thể che correctness problem của test suite.
4. Ưu tiên findings theo impact lên CI signal.
5. Đề xuất design giữ parallelism nhưng cô lập test state.
6. Nêu cách kiểm thử chính test infrastructure và failure diagnostics.
7. Đề xuất artifacts/telemetry giúp phân biệt product failure với test-environment collision.

## Câu hỏi gợi mở

1. Hai workers chạy `beforeEach` trên cùng `approvalId` có thể interleave như thế nào?
2. Điều gì xảy ra nếu một PR pipeline reset data trong lúc pipeline khác đang assert?
3. `waitForTimeout(1000)` đang chờ condition nào?
4. Retry pass lần hai chứng minh product đúng hay chỉ chứng minh race không xảy ra lần hai?
5. Test data ownership nên gắn với test, worker hay toàn environment?

### Gợi ý 2

Giữ parallelism bằng cách tạo namespace/data riêng cho mỗi test execution và chờ observable condition thay vì sleep cố định.

## Kết quả code review tham khảo

### High — Tất cả tests và CI jobs mutate cùng một approval

**Vấn đề:** `approvalId` là global seed cố định.

**Tại sao xảy ra:** Parallel workers và concurrent pipelines đều reset/update cùng resource.

**Ảnh hưởng production:** Test pass/fail phụ thuộc scheduling; một test có thể reset state sau khi test khác vừa approve/reject.

**Cách sửa:** Provision resource unique theo test/run/worker, ví dụ run ID + worker index + generated entity ID. Cleanup theo ownership thay vì global reset.

### High — Shared account có thể mang mutable session/domain state

**Vấn đề:** Mọi worker dùng cùng identity.

**Tại sao xảy ra:** Nếu account có server-side session, preferences, throttling hoặc ownership-specific state, tests ảnh hưởng nhau dù approval IDs đã tách.

**Ảnh hưởng production:** Flakiness khó chẩn đoán và false failures dưới parallel load.

**Cách sửa:** Xác định account state semantics. Nếu identity state mutable, provision users per worker/run; nếu identity thực sự stateless cho scenario, có thể reuse nhưng phải chứng minh bằng contract.

### High — Fixed sleep không đồng bộ với application condition

**Vấn đề:** `waitForTimeout(1000)` giả định UI/backend hoàn tất trong một giây.

**Tại sao xảy ra:** Time delay không quan sát network/state transition thực tế.

**Ảnh hưởng production:** CI chậm thì false failure; local nhanh thì test pass; sleep dài hơn chỉ làm suite chậm và vẫn không deterministic.

**Cách sửa:** Chờ user-visible state hoặc response/event cụ thể bằng Playwright auto-wait/assertions. Nếu backend processing async, poll API/UI condition với bounded timeout phù hợp.

### High — Retry che flaky infrastructure/test design

**Vấn đề:** `retries: 2` biến first-attempt failure thành green pipeline mà không phân loại nguyên nhân.

**Tại sao xảy ra:** Retry được dùng như correctness mechanism thay vì diagnostic/resilience policy.

**Ảnh hưởng production:** Team mất niềm tin vào failures, regression thật có thể bị intermittent pass che khuất.

**Cách sửa:** Sửa isolation/waits trước. Retry có thể giữ ở mức có chủ đích cho known external flakiness, nhưng phải report flaky tests riêng và không coi retry-pass là tín hiệu tương đương first-pass.

### Medium — Reset API result không được kiểm tra

**Vấn đề:** `request.post(...)` không assert status/result.

**Tại sao xảy ra:** Setup failure vẫn cho test tiếp tục.

**Ảnh hưởng production:** Failure biểu hiện ở UI assertion thay vì setup, làm RCA sai hướng.

**Cách sửa:** Assert setup/provision response và fail fast với diagnostic context.

### Medium — Login lặp qua UI làm tăng noise cho tests không kiểm tra login

**Vấn đề:** Mọi test thực hiện full UI login.

**Tại sao xảy ra:** Authentication setup và approval behavior bị coupling.

**Ảnh hưởng production:** Suite chậm, auth transient failure làm hàng loạt unrelated tests fail.

**Cách sửa:** Với tests không nhằm kiểm tra login, cân nhắc authenticated storage state/fixture được tạo an toàn theo test strategy. Giữ một nhóm tests riêng kiểm tra login UI thực sự.

### Medium — Không capture execution namespace trong diagnostics

**Vấn đề:** Khi failure xảy ra, artifacts không cho biết resource thuộc run/worker nào.

**Tại sao xảy ra:** Test data không có ownership identity.

**Ảnh hưởng production:** Trace/video/network logs khó correlate với backend logs và concurrent CI job.

**Cách sửa:** Gắn `runId`, worker/test ID vào created data và headers/log context khi test API hỗ trợ.

## Phiên bản đề xuất

Ví dụ fixture đơn giản tạo approval riêng cho từng test:

```ts
import { test, expect } from '@playwright/test';

async function createApproval(request, testInfo) {
  const key = `${process.env.CI_RUN_ID ?? 'local'}-${testInfo.workerIndex}-${Date.now()}`;
  const response = await request.post('/test-api/approvals', {
    data: { externalKey: key, title: `E2E ${key}` }
  });

  expect(response.ok()).toBeTruthy();
  const body = await response.json();
  return body.id as string;
}

async function login(page) {
  await page.goto('/login');
  await page.getByLabel('Email').fill('qa-user@example.test');
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page).toHaveURL(/\/home|\/approvals/);
}

test.describe('approval workflow', () => {
  test.beforeEach(async ({ page }) => {
    await login(page);
  });

  test('approves request', async ({ page, request }, testInfo) => {
    const approvalId = await createApproval(request, testInfo);

    await page.goto(`/approvals/${approvalId}`);
    await page.getByRole('button', { name: 'Approve' }).click();

    await expect(page.getByText('Approved')).toBeVisible();
  });

  test('rejects request', async ({ page, request }, testInfo) => {
    const approvalId = await createApproval(request, testInfo);

    await page.goto(`/approvals/${approvalId}`);
    await page.getByRole('button', { name: 'Reject' }).click();

    await expect(page.getByText('Rejected')).toBeVisible();
  });
});
```

`Date.now()` chỉ minh họa uniqueness; production test harness nên dùng run-scoped unique identifier đủ mạnh và deterministic ownership metadata. Nếu tests cần cleanup, cleanup chỉ xóa resources thuộc run đó, không reset global environment.

## Giải thích thiết kế sau khi sửa

Mỗi test sở hữu mutable resource riêng nên workers có thể chạy song song mà không tranh chấp domain state. Assertions chờ observable UI state thay vì arbitrary delay, tận dụng Playwright waiting semantics.

Setup API được assert để failure nằm đúng layer. Login có thể tiếp tục qua UI nếu authentication là một phần scenario; nếu không, fixture/storage state giúp giảm noise nhưng phải tránh share mutable session state không an toàn.

Retry không bị cấm tuyệt đối, nhưng retry phải là telemetry signal: test pass sau retry nên được đánh dấu flaky và theo dõi, không coi như first-pass success.

## Trade-offs

- Per-test provisioning tăng số records và cần cleanup/lifecycle policy.
- Unique users per worker tăng setup cost nếu identity provisioning đắt.
- Shared environment rẻ hơn isolated environment per PR nhưng luôn cần namespace/ownership discipline.
- Chạy serial có thể giảm race nhưng kéo dài pipeline và che thiết kế test data kém; chỉ dùng khi scenario thật sự serial theo business semantics.

## Cách kiểm thử

1. **Parallel stress:** chạy suite nhiều lần với 6+ workers; không được có cross-test state collision.
2. **Concurrent pipeline test:** hai runs dùng cùng environment nhưng khác run IDs; resources không ảnh hưởng nhau.
3. **Slow backend test:** inject latency lớn hơn 1 giây; assertion condition-based vẫn pass trong timeout hợp lý.
4. **Setup failure test:** provisioning API trả 500; test fail ngay tại setup với diagnostic rõ.
5. **Flake reporting test:** cố tình tạo intermittent failure trong staging harness; CI phải phân biệt first-pass, retry-pass và hard failure.

## Quan sát trong production

Lưu Playwright trace, screenshot/video khi failure theo policy, network errors và test duration. CI dashboard nên theo dõi first-attempt pass rate, retry-pass rate, top flaky tests, duration p95 và failure category.

Backend test environment logs nên nhận run/test correlation ID nếu có thể, để một failed E2E trace map được tới API request và database entity thuộc đúng run. Alert/quality gate nên quan tâm flake rate tăng, không chỉ final green/red pipeline.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận chạy một test suite serial thay vì đầu tư isolation?
2. Bạn quản lý test data cleanup thế nào để cleanup job không xóa dữ liệu của run đang hoạt động?
3. Retry ở E2E layer có trường hợp hợp lý nào, và bạn ngăn nó che regression bằng cách nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Optimistic concurrency không phải cơ chế để tự động retry cho tới khi ghi thành công. Nó là cơ chế phát hiện state đã thay đổi để application/client áp dụng business conflict policy có chủ đích. Stable concurrency version và database enforcement phải gắn với state caller thực sự đã quan sát.

E2E parallelism chỉ đáng tin khi mutable test state có ownership rõ. Retry và fixed sleep có thể làm pipeline nhìn xanh hơn nhưng giảm signal nếu root cause là race trong test infrastructure.

## Mẫu tư duy cần nhớ

- Phân biệt **transient retry** với **business concurrency conflict**.
- Enforce concurrency/invariant ở authority và giữ business intent rõ trong API contract.
- Với parallel tests, mỗi execution phải sở hữu mutable state riêng hoặc chứng minh state thật sự immutable.
- Chờ **observable condition**, không chờ một khoảng thời gian đoán trước.
- Theo dõi first-pass và retry-pass riêng; green sau retry vẫn là reliability signal cần điều tra.
