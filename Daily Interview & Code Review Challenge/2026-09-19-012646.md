# Code Review Challenge 1 — Service Bus consumer xử lý đơn hàng trùng khi retry

**Chủ đề:** C#/.NET, Azure Service Bus, idempotency, EF Core, distributed failure  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một ASP.NET Core worker nhận `OrderPaid` từ Azure Service Bus. Mỗi message phải cập nhật trạng thái order trong SQL Server, tạo shipment và gọi một third-party fulfillment API. Hệ thống chạy 4 instances để scale-out. Broker có thể redeliver message khi processing thất bại hoặc message lock không còn hợp lệ.

Production thỉnh thoảng tạo hai shipment cho cùng một order. Log cho thấy cùng `OrderId` có thể được xử lý trên hai instance ở các thời điểm gần nhau. Team đã thêm retry cho HTTP call nhưng chưa có cơ chế idempotency rõ ràng. Fulfillment API hỗ trợ một `Idempotency-Key` header nhưng code hiện chưa sử dụng.

## Đoạn code cần review

```csharp
public sealed class OrderPaidHandler
{
    private readonly AppDbContext _db;
    private readonly HttpClient _http;
    private readonly ILogger<OrderPaidHandler> _logger;

    public OrderPaidHandler(
        AppDbContext db,
        HttpClient http,
        ILogger<OrderPaidHandler> logger)
    {
        _db = db;
        _http = http;
        _logger = logger;
    }

    public async Task HandleAsync(OrderPaid message)
    {
        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId);

        if (order.Status == "Shipped")
            return;

        order.Status = "ProcessingShipment";
        await _db.SaveChangesAsync();

        var request = new HttpRequestMessage(
            HttpMethod.Post,
            "/api/shipments");

        request.Content = JsonContent.Create(new
        {
            order.Id,
            order.CustomerId,
            order.ShippingAddress
        });

        HttpResponseMessage response = null!;

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                response = await _http.SendAsync(request);
                if (response.IsSuccessStatusCode)
                    break;
            }
            catch (HttpRequestException ex)
            {
                _logger.LogWarning(ex,
                    "Fulfillment failed for order {OrderId}", order.Id);
            }

            await Task.Delay(TimeSpan.FromSeconds(1));
        }

        response.EnsureSuccessStatusCode();

        var shipment = await response.Content
            .ReadFromJsonAsync<ShipmentResponse>();

        order.Status = "Shipped";
        order.ShipmentId = shipment!.Id;

        await _db.SaveChangesAsync();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong điều kiện redelivery/concurrency.
2. Xác định các rủi ro reliability, HTTP retry và resource handling.
3. Giải thích production impact và failure windows.
4. Ưu tiên các vấn đề theo severity.
5. Đề xuất implementation/design sửa lại.
6. Giải thích cách test duplicate delivery, timeout và crash.
7. Đề xuất telemetry đủ để chứng minh consumer đang hoạt động idempotently.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu process crash sau khi fulfillment đã tạo shipment nhưng trước `SaveChangesAsync()` cuối?
2. `if (order.Status == "Shipped")` có ngăn được hai instances cùng xử lý không?
3. Retry một `POST` có an toàn khi client không biết server đã xử lý request hay chưa?
4. Có vấn đề gì khi reuse cùng `HttpRequestMessage` qua nhiều lần `SendAsync`?
5. Transaction SQL có thể bao phủ an toàn một HTTP call tới hệ thống bên ngoài không?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **at-least-once delivery + side effect không idempotent + concurrency**.

### Gợi ý 2

Hãy tìm các failure window giữa SQL commit, HTTP side effect và message settlement; sau đó xem mỗi operation có identity/idempotency boundary riêng hay chưa.

## Kết quả code review tham khảo

### Critical — External side effect không idempotent

**Vấn đề:** Mỗi retry/redelivery có thể gửi một `POST /api/shipments` mới mà không có stable idempotency key.  
**Tại sao xảy ra:** Distributed call có trạng thái “unknown outcome”: client có thể timeout sau khi server đã tạo shipment. Broker cũng có thể redeliver message.  
**Ảnh hưởng production:** Một order có thể tạo nhiều shipment hoặc phát sinh charge/operation lặp.  
**Cách sửa:** Tạo stable operation key, ví dụ dựa trên event/message identity hoặc `OrderId + operation type`, lưu state idempotency bền vững và gửi cùng key qua `Idempotency-Key` nếu fulfillment contract bảo đảm semantics đó.

### High — Check-then-act không bảo vệ concurrency

**Vấn đề:** Hai instances có thể cùng đọc `Status != Shipped`, rồi cùng chuyển sang `ProcessingShipment`.  
**Tại sao xảy ra:** Read/check/update không có atomic concurrency guard.  
**Ảnh hưởng production:** Duplicate external calls và race trên shipment state.  
**Cách sửa:** Dùng unique constraint/idempotency record hoặc optimistic concurrency/conditional update để chỉ một logical operation claim được work. Thiết kế phải vẫn chịu được worker crash sau khi claim.

### High — Crash window giữa HTTP success và SQL commit

**Vấn đề:** Fulfillment có thể tạo shipment thành công nhưng worker chết trước khi lưu `ShipmentId`.  
**Tại sao xảy ra:** SQL và external API không cùng transaction boundary.  
**Ảnh hưởng production:** Redelivery không biết side effect đã xảy ra và có thể tạo shipment thứ hai.  
**Cách sửa:** Không cố giữ distributed transaction quanh HTTP. Dùng idempotent external operation + durable workflow state. Khi retry, query/retry bằng cùng operation key theo contract của provider.

### High — Retry semantics của HTTP request không an toàn

**Vấn đề:** Code retry mọi non-success response và network failure gần như giống nhau.  
**Tại sao xảy ra:** Không phân biệt transient failure, permanent 4xx, timeout/unknown outcome và server overload.  
**Ảnh hưởng production:** Tăng tải dependency, kéo dài lock/message processing và lặp side effect.  
**Cách sửa:** Chỉ retry lỗi transient theo policy có bounded attempts, backoff/jitter và deadline; non-transient response phải đi failure path phù hợp. Retry `POST` chỉ khi operation idempotent theo contract.

### High — Reuse `HttpRequestMessage`

**Vấn đề:** Cùng một `HttpRequestMessage` được gửi lại trong loop.  
**Tại sao xảy ra:** Request message là một send operation object; retry nên tạo request mới cho từng attempt và tái tạo content/headers cần thiết.  
**Ảnh hưởng production:** Retry có thể thất bại hoặc có behavior không đáng tin cậy tùy request/content lifecycle.  
**Cách sửa:** Tạo request mới mỗi attempt từ immutable command payload và stable idempotency key.

### Medium — Không truyền `CancellationToken`

**Vấn đề:** EF Core, HTTP và delay không nhận cancellation.  
**Tại sao xảy ra:** Handler không expose token của message processor/host shutdown.  
**Ảnh hưởng production:** Shutdown kéo dài, work tiếp tục khi message processing đã bị hủy và tăng xác suất redelivery.  
**Cách sửa:** Propagate token qua database, HTTP, delay và các operations có hỗ trợ.

### Medium — `HttpResponseMessage` lifecycle không được quản lý

**Vấn đề:** Responses của failed attempts không được dispose rõ ràng.  
**Tại sao xảy ra:** Loop ghi đè biến `response`.  
**Ảnh hưởng production:** Dưới load có thể giữ resources lâu hơn cần thiết và làm HTTP behavior khó quan sát.  
**Cách sửa:** Dispose từng response sau khi đọc/đánh giá; giữ response thành công trong scope rõ ràng.

### Medium — Workflow state thiếu failure model

**Vấn đề:** Order có thể nằm ở `ProcessingShipment` sau permanent failure/crash nhưng code không thể hiện retry ownership, retry count hay terminal failure.  
**Tại sao xảy ra:** Business state và processing state bị trộn mà không có workflow semantics.  
**Ảnh hưởng production:** Orders bị kẹt, support khó phân biệt đang chạy với đã thất bại.  
**Cách sửa:** Model processing state/attempt/error rõ ràng hoặc dùng durable operation/outbox/work item phù hợp.

## Phiên bản đề xuất

```csharp
public sealed class OrderPaidHandler
{
    private readonly AppDbContext _db;
    private readonly HttpClient _http;
    private readonly ILogger<OrderPaidHandler> _logger;

    public OrderPaidHandler(
        AppDbContext db,
        HttpClient http,
        ILogger<OrderPaidHandler> logger)
    {
        _db = db;
        _http = http;
        _logger = logger;
    }

    public async Task HandleAsync(OrderPaid message, CancellationToken ct)
    {
        var operationId = $"shipment:{message.OrderId}";

        var operation = await _db.ShipmentOperations
            .SingleOrDefaultAsync(x => x.OperationId == operationId, ct);

        if (operation?.Status == "Completed")
            return;

        if (operation is null)
        {
            operation = new ShipmentOperation
            {
                OperationId = operationId,
                OrderId = message.OrderId,
                Status = "Pending"
            };

            _db.ShipmentOperations.Add(operation);

            try
            {
                await _db.SaveChangesAsync(ct);
            }
            catch (DbUpdateException)
            {
                _db.ChangeTracker.Clear();
                operation = await _db.ShipmentOperations
                    .SingleAsync(x => x.OperationId == operationId, ct);

                if (operation.Status == "Completed")
                    return;
            }
        }

        var order = await _db.Orders
            .AsNoTracking()
            .SingleAsync(x => x.Id == message.OrderId, ct);

        using var request = new HttpRequestMessage(HttpMethod.Post, "/api/shipments")
        {
            Content = JsonContent.Create(new
            {
                order.Id,
                order.CustomerId,
                order.ShippingAddress
            })
        };

        request.Headers.TryAddWithoutValidation("Idempotency-Key", operationId);

        using var response = await _http.SendAsync(request, ct);
        response.EnsureSuccessStatusCode();

        var shipment = await response.Content
            .ReadFromJsonAsync<ShipmentResponse>(cancellationToken: ct)
            ?? throw new InvalidOperationException("Missing shipment response.");

        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        var trackedOrder = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId, ct);

        operation = await _db.ShipmentOperations
            .SingleAsync(x => x.OperationId == operationId, ct);

        trackedOrder.Status = "Shipped";
        trackedOrder.ShipmentId = shipment.Id;
        operation.Status = "Completed";
        operation.ExternalId = shipment.Id;

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);

        _logger.LogInformation(
            "Shipment operation {OperationId} completed with {ShipmentId}",
            operationId,
            shipment.Id);
    }
}
```

Implementation trên minh họa boundary, không phải universal solution. `ShipmentOperations.OperationId` phải có unique constraint. Contract của fulfillment phải được xác minh để chắc chắn cùng `Idempotency-Key` thực sự trả về/cố định cùng logical operation. Nếu cần retry HTTP, tạo request mới mỗi attempt và dùng cùng operation key. Nếu provider không hỗ trợ idempotency, cần thiết kế reconciliation/deduplication khác; SQL transaction không thể biến external API thành atomic resource.

## Giải thích thiết kế sau khi sửa

Điểm cốt lõi là chuyển từ “message chỉ chạy một lần” sang “message có thể chạy nhiều lần nhưng logical operation chỉ tạo một kết quả”. Durable operation record cung cấp identity và audit state; unique constraint biến deduplication thành invariant ở database thay vì check trong memory.

External call vẫn nằm ngoài SQL transaction. Correctness phụ thuộc vào idempotency contract hoặc reconciliation protocol với provider. Transaction cuối chỉ đảm bảo local order state và operation state commit cùng nhau.

## Trade-offs

Idempotency table tăng schema/state-management complexity và cần cleanup/retention policy. Nếu fulfillment idempotency key có retention window, workflow phải phù hợp với window đó. Một stricter claim/lease mechanism có thể giảm concurrent duplicate calls nhưng làm recovery sau crash phức tạp hơn. Không nên dùng distributed lock như cách duy nhất để bảo đảm business idempotency.

## Cách kiểm thử

1. **Concurrency test:** gửi cùng event đồng thời cho nhiều handler instances; xác minh chỉ có một logical shipment.
2. **Failure-path test:** fulfillment tạo shipment rồi client nhận timeout; redelivery phải reuse cùng idempotency key.
3. **Crash/recovery integration test:** mô phỏng crash sau HTTP success nhưng trước local commit, sau đó replay event.
4. **Database test:** hai instances cùng insert `ShipmentOperation`; unique constraint phải bảo vệ invariant.
5. **Cancellation test:** shutdown/cancel phải dừng HTTP/EF/delay đúng cách mà không đánh dấu operation hoàn tất sai.

## Quan sát trong production

Log structured fields gồm `MessageId`, `OrderId`, `OperationId`, `DeliveryCount`, instance và external shipment ID. Theo dõi duplicate-delivery count, fulfillment latency/error/timeout, operation states bị pending quá lâu, Service Bus active/dead-letter counts và handler duration. Correlate message trace với dependency telemetry trong Application Insights. Alert khi pending operation age vượt SLO hoặc duplicate external IDs được phát hiện.

## Câu hỏi phỏng vấn mở rộng

1. Outbox Pattern giúp phần nào trong workflow này và không giải quyết phần nào?
2. Nếu fulfillment provider không hỗ trợ idempotency key, bạn thiết kế reconciliation thế nào?
3. Vì sao distributed lock không nên là correctness boundary duy nhất cho duplicate delivery?

# Code Review Challenge 2 — Vue search component trả kết quả cũ đè kết quả mới

**Chủ đề:** Vue.js, TypeScript, async race condition, API integration, browser security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 6–8

## Bối cảnh

Một enterprise product-search page dùng Vue 3 + TypeScript gọi ASP.NET Core API. Khi user gõ nhanh, UI đôi khi hiển thị kết quả cho keyword cũ dù ô search đã chứa keyword mới. QA cũng thấy nhiều request giống nhau khi component remount. API có thể trả lỗi 429/500 và response có field `highlightHtml` do backend search service tạo để highlight keyword.

Product muốn giữ cảm giác search gần real-time. Không có requirement phải gửi request cho từng keystroke. Backend đã có authentication cookie và API cùng origin.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { onMounted, ref, watch } from 'vue'

interface SearchItem {
  id: string
  title: string
  highlightHtml: string
}

const query = ref('')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')

async function search() {
  loading.value = true
  error.value = ''

  const response = await fetch(`/api/search?q=${query.value}`)
  const data = await response.json()

  items.value = data.items
  loading.value = false
}

watch(query, async () => {
  try {
    await search()
  } catch (e: any) {
    error.value = e.message
    loading.value = false
  }
})

onMounted(() => {
  search()
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in items" :key="item.id">
        <a :href="`/products/${item.id}`" v-html="item.highlightHtml"></a>
      </li>
    </ul>
  </section>
</template>
```

## Kết quả code review tham khảo

### Critical — `v-html` có thể tạo XSS nếu HTML không được bảo đảm an toàn

**Vấn đề:** Component render `highlightHtml` trực tiếp vào DOM.  
**Tại sao xảy ra:** `v-html` coi string là HTML; nếu backend/search index chứa hoặc phản chiếu nội dung attacker-controlled mà không có trusted sanitization contract, scriptable markup có thể đi vào DOM.  
**Ảnh hưởng production:** Stored/reflected XSS tùy nguồn dữ liệu và sanitization pipeline.  
**Cách sửa:** Ưu tiên trả structured highlight segments/text và render bằng text binding. Nếu business bắt buộc HTML, sanitization phải là explicit, tested trust boundary bằng allowlist phù hợp; không dựa vào frontend escaping sau khi đã dùng raw HTML.

### High — Request cũ có thể ghi đè kết quả mới

**Vấn đề:** Mọi `search()` đều ghi `items` khi hoàn thành, không kiểm tra request nào còn current.  
**Tại sao xảy ra:** Network responses không bảo đảm hoàn thành theo thứ tự request.  
**Ảnh hưởng production:** User thấy kết quả không tương ứng với query hiện tại.  
**Cách sửa:** Cancel request trước bằng `AbortController` và/hoặc dùng request sequence token để chỉ latest request được commit state.

### High — HTTP error không được xử lý đúng

**Vấn đề:** Code gọi `response.json()` mà không kiểm tra `response.ok`.  
**Tại sao xảy ra:** `fetch` thường resolve với HTTP error response; nó không tự throw chỉ vì status là 4xx/5xx.  
**Ảnh hưởng production:** Error payload có thể bị xử lý như success, gây exception mơ hồ hoặc state sai.  
**Cách sửa:** Kiểm tra status/`response.ok`, xử lý 429 và server errors theo UX policy, parse error contract có kiểm soát.

### Medium — Không debounce input

**Vấn đề:** Mỗi thay đổi `query` tạo request.  
**Tại sao xảy ra:** Watcher chạy theo từng update mà không có delay/coalescing.  
**Ảnh hưởng production:** Request amplification, backend load tăng và nhiều race hơn khi user gõ nhanh.  
**Cách sửa:** Debounce khoảng thời gian phù hợp với UX đã đo; không hard-code “chuẩn” nếu chưa có requirement/performance evidence.

### Medium — Query parameter không được encode đúng

**Vấn đề:** `query.value` được nối trực tiếp vào URL.  
**Tại sao xảy ra:** Ký tự đặc biệt có semantics trong URL query.  
**Ảnh hưởng production:** Keyword bị parse sai, thêm parameter ngoài ý muốn hoặc search behavior không nhất quán.  
**Cách sửa:** Dùng `URLSearchParams`.

### Medium — `loading` có race

**Vấn đề:** Request cũ có thể set `loading = false` trong khi request mới vẫn chạy.  
**Tại sao xảy ra:** Shared boolean được nhiều async operations mutate.  
**Ảnh hưởng production:** Loading indicator sai và làm debugging khó hơn.  
**Cách sửa:** Chỉ latest request được update loading/error hoặc model request state theo request identity.

### Low — Initial empty search có thể không cần thiết

**Vấn đề:** `onMounted(search)` gọi API với empty query dù requirement chưa nói empty search có ý nghĩa.  
**Tại sao xảy ra:** Component luôn fetch khi mount.  
**Ảnh hưởng production:** Request thừa, đặc biệt khi route/component remount.  
**Cách sửa:** Xác định semantics cho empty query; chỉ fetch nếu cần. Nếu cần initial list, model nó như use case rõ ràng thay vì vô tình reuse search.

## Phiên bản đề xuất

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue'

interface SearchItem {
  id: string
  title: string
  highlightParts: Array<{ text: string; highlighted: boolean }>
}

const query = ref('')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')

let controller: AbortController | null = null
let debounceTimer: ReturnType<typeof setTimeout> | null = null
let requestVersion = 0

async function search(term: string) {
  const version = ++requestVersion
  controller?.abort()
  controller = new AbortController()

  loading.value = true
  error.value = ''

  try {
    const params = new URLSearchParams({ q: term })
    const response = await fetch(`/api/search?${params}`, {
      signal: controller.signal
    })

    if (!response.ok) {
      throw new Error(`Search failed with status ${response.status}`)
    }

    const data = await response.json()

    if (version === requestVersion) {
      items.value = data.items
    }
  } catch (e) {
    if (e instanceof DOMException && e.name === 'AbortError')
      return

    if (version === requestVersion) {
      error.value = e instanceof Error ? e.message : 'Search failed'
    }
  } finally {
    if (version === requestVersion) {
      loading.value = false
    }
  }
}

watch(query, (value) => {
  if (debounceTimer)
    clearTimeout(debounceTimer)

  const term = value.trim()

  if (!term) {
    controller?.abort()
    requestVersion++
    items.value = []
    error.value = ''
    loading.value = false
    return
  }

  debounceTimer = setTimeout(() => {
    void search(term)
  }, 250)
})

onBeforeUnmount(() => {
  controller?.abort()
  if (debounceTimer)
    clearTimeout(debounceTimer)
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in items" :key="item.id">
        <a :href="`/products/${encodeURIComponent(item.id)}`">
          <template v-for="(part, index) in item.highlightParts" :key="index">
            <mark v-if="part.highlighted">{{ part.text }}</mark>
            <template v-else>{{ part.text }}</template>
          </template>
        </a>
      </li>
    </ul>
  </section>
</template>
```

`250 ms` ở đây chỉ là scenario choice để minh họa debounce, không phải universal optimum. Giá trị thực tế nên dựa trên UX requirement và telemetry. Contract `highlightParts` cũng yêu cầu backend thay đổi; nếu không thể đổi contract, cần một sanitization strategy được security-review và test rõ ràng.

## Giải thích thiết kế sau khi sửa

`AbortController` giảm work không còn cần thiết, nhưng sequence/version check vẫn hữu ích vì correctness không nên phụ thuộc hoàn toàn vào việc cancellation luôn đến dependency đúng lúc. Chỉ request mới nhất được commit `items`, `error` và `loading`.

Structured highlight data loại bỏ nhu cầu đưa raw HTML từ search/backend vào DOM. `URLSearchParams` làm query serialization rõ ràng. Empty-query behavior được định nghĩa thay vì tự động gọi API khi mount.

## Trade-offs

Debounce tăng một lượng latency có chủ đích trước khi request bắt đầu; giá trị quá lớn làm UX chậm, quá nhỏ giảm ít traffic. Cancellation không đồng nghĩa backend chắc chắn ngừng toàn bộ work nếu request đã tới server; backend vẫn cần cancellation propagation/rate limiting phù hợp. Structured highlights tăng API contract complexity nhưng tạo trust boundary an toàn và dễ test hơn raw HTML.

## Cách kiểm thử

1. **Playwright E2E:** gõ `car`, rồi nhanh chóng `cargo`; delay response `car` lâu hơn và xác minh UI cuối chỉ hiển thị `cargo`.
2. **API/error UI test:** mock 429/500 và xác minh không render payload như success, loading kết thúc đúng.
3. **Security test:** đưa malicious markup vào highlight source; xác minh nó được render như text, không thành executable HTML.
4. **Browser/network test:** gõ nhanh 10 ký tự và xác minh debounce/cancellation giới hạn số request theo expected behavior.
5. **Lifecycle test:** unmount component khi request đang chạy; xác minh không commit stale state sau teardown.

## Quan sát trong production

Theo dõi search request count per interaction/session, cancellation rate, HTTP status distribution, p50/p95 latency và backend dependency latency. Client telemetry nên ghi query length/bucket thay vì raw query nếu raw search text có thể chứa dữ liệu nhạy cảm. Theo dõi frontend error rate, 429 rate và stale-result bugs qua correlation/request IDs khi phù hợp. Browser network waterfall hữu ích để xác minh request amplification và out-of-order completion trong incident.

## Câu hỏi phỏng vấn mở rộng

1. `AbortController` có đủ để bảo đảm stale response không update state không? Vì sao vẫn có thể dùng request version?
2. Nếu product bắt buộc backend trả `highlightHtml`, bạn sẽ đặt và kiểm thử sanitization trust boundary ở đâu?
3. Khi nào debounce search phía client là chưa đủ và backend cần rate limiting/load shedding?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào cùng một nguyên tắc ở hai tầng khác nhau: asynchronous/distributed operations không bảo đảm “đến một lần” hoặc “hoàn thành đúng thứ tự”. Ở backend, Azure Service Bus redelivery và HTTP unknown outcome buộc side effect phải có idempotency boundary bền vững. Ở frontend, network completion order buộc UI chỉ cho request hiện hành commit state. Security boundary cũng phải rõ: raw HTML từ search data không nên được tin cậy ngầm.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng với idempotency; đừng giả định exactly-once processing.
- Xác định failure window giữa các transaction/resource boundaries.
- Async completion order không phải request order; state update cần identity/version.
- External input/HTML phải có explicit trust boundary.
- Test failure path và concurrency thay vì chỉ happy path.
