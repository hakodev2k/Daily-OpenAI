# Code Review Challenge 1 — Service Bus consumer xác nhận message trước khi lưu kết quả

**Chủ đề:** C#/.NET 8, Azure Service Bus, idempotency, transaction boundary  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7

## Bối cảnh

Một hệ thống đặt hàng nhận `OrderPaid` qua Azure Service Bus queue. Mỗi message có `EventId`, `OrderId` và `Amount`. Consumer phải tạo đúng một bản ghi thanh toán trong PostgreSQL và cập nhật trạng thái đơn hàng. Hệ thống chạy ba instance trên Azure App Service; đôi khi DB timeout, process bị restart, message được redeliver. Vài đơn hàng được đánh dấu Paid nhưng không có payment; một số khác có payment trùng. Giả định message có thể được giao lại, `EventId` ổn định qua retries và DB là nguồn sự thật.

## Đoạn code cần review

```csharp
public sealed record OrderPaid(Guid EventId, Guid OrderId, decimal Amount);

public sealed class PaymentConsumer : BackgroundService
{
    private readonly ServiceBusClient _bus;
    private readonly IServiceProvider _services;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(ServiceBusClient bus, IServiceProvider services,
        ILogger<PaymentConsumer> logger)
    {
        _bus = bus;
        _services = services;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var processor = _bus.CreateProcessor("order-paid", new ServiceBusProcessorOptions
        {
            AutoCompleteMessages = true,
            MaxConcurrentCalls = 16
        });

        processor.ProcessMessageAsync += async args =>
        {
            var evt = args.Message.Body.ToObjectFromJson<OrderPaid>();
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var exists = await db.Payments.AnyAsync(
                x => x.EventId == evt.EventId);
            if (exists) return;

            db.Payments.Add(new Payment
            {
                EventId = evt.EventId,
                OrderId = evt.OrderId,
                Amount = evt.Amount
            });

            var order = await db.Orders.FindAsync(evt.OrderId);
            if (order != null) order.Status = "Paid";

            await db.SaveChangesAsync();
            _logger.LogInformation("Processed {EventId}", evt.EventId);
        };

        processor.ProcessErrorAsync += args =>
        {
            _logger.LogError(args.Exception, "Service Bus failure");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Không có idempotency được enforce ở DB

**Vấn đề:** `AnyAsync` rồi insert là check-then-act không atomic.  
**Tại sao xảy ra:** Hai instance cùng thấy `false` trước khi insert.  
**Ảnh hưởng production:** Duplicate payment hoặc conflict không được phân loại.  
**Cách sửa:** Unique index trên `Payments.EventId` (hoặc inbox table), bắt unique violation cụ thể và coi duplicate đã xử lý là thành công sau khi kiểm tra dữ liệu tương ứng.

### [High] — AutoComplete che khuất settlement policy

**Vấn đề:** `AutoCompleteMessages=true`; code không kiểm soát explicit complete/abandon/dead-letter.  
**Tại sao xảy ra:** Handler hoàn thành bình thường được SDK tự complete; exception có thể dẫn tới redelivery theo processor behavior.  
**Ảnh hưởng production:** Missing order vẫn bị complete vì handler không throw; lỗi vĩnh viễn lặp đến DLQ mà không có phân loại.  
**Cách sửa:** Tắt auto-complete, complete sau commit; phân loại transient/permanent, dùng DLQ cho dữ liệu không hợp lệ theo policy.

### [High] — Không xử lý missing order

**Vấn đề:** Vẫn insert payment khi `order == null`.  
**Tại sao xảy ra:** Thiếu kiểm tra invariant và dependency ordering.  
**Ảnh hưởng production:** Payment orphan, reconciliation sai.  
**Cách sửa:** Xác định contract: event có thể đến trước Order hay không. Nếu có, retry có giới hạn hoặc pending workflow; nếu không, DLQ và alert.

### [High] — Shutdown không dispose/stop processor có kiểm soát

**Vấn đề:** Processor tạo trong `ExecuteAsync` nhưng không `await using` hoặc `StopProcessingAsync` ở finally.  
**Tại sao xảy ra:** Delay bị cancel và method kết thúc mà không quản lý lifetime.  
**Ảnh hưởng production:** In-flight handler bị cắt ngang, settlement không hoàn tất, khó drain.  
**Cách sửa:** `await using`, finally stop processor với shutdown budget phù hợp.

### [Medium] — Thiếu cancellation propagation

**Vấn đề:** EF calls và `SaveChangesAsync` không nhận `args.CancellationToken`.  
**Tại sao xảy ra:** Handler bỏ qua cancellation khi message lock bị mất hoặc shutdown.  
**Ảnh hưởng production:** Tiếp tục tốn DB resources, tăng khả năng xử lý sau khi lock hết hạn.  
**Cách sửa:** Truyền token và thiết kế idempotency để chịu được cancellation ở bất kỳ điểm nào.

### [Medium] — Chưa validate payload và domain transition

**Vấn đề:** Không kiểm tra `Amount`, `OrderId`, schema version hay trạng thái trước đó.  
**Tại sao xảy ra:** Tin message là hợp lệ và status transition luôn an toàn.  
**Ảnh hưởng production:** Đơn bị Paid sai hoặc dữ liệu âm; event cũ ghi đè trạng thái mới.  
**Cách sửa:** Validate schema và domain invariants; kiểm tra trạng thái/phiên bản đơn hàng trong transaction.

### [Medium] — Thiếu observability theo delivery

**Vấn đề:** Chỉ log EventId thành công và lỗi chung.  
**Tại sao xảy ra:** Không log DeliveryCount, MessageId, correlation, settlement outcome.  
**Ảnh hưởng production:** Không phân biệt duplicate, retry, poison message hay DB contention.  
**Cách sửa:** Structured logs, metrics latency/duplicate/abandon/DLQ và trace correlation; không log payload nhạy cảm.

## Phiên bản đề xuất

Thiết lập DB trước (migrations và kiểm tra duplicate cũ trước khi thêm constraint):

CREATE UNIQUE INDEX ux_payments_event_id ON payments(event_id);

Ví dụ handler chính (minh họa; mapping entity, policy DLQ và exception provider-specific cần hoàn thiện theo ứng dụng):

```csharp
var processor = client.CreateProcessor("order-paid",
    new ServiceBusProcessorOptions
    {
        AutoCompleteMessages = false,
        MaxConcurrentCalls = 8,
        MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(5)
    });

processor.ProcessMessageAsync += async args =>
{
    var ct = args.CancellationToken;
    OrderPaid? evt;
    try
    {
        evt = args.Message.Body.ToObjectFromJson<OrderPaid>();
        if (evt is null || evt.EventId == Guid.Empty ||
            evt.OrderId == Guid.Empty || evt.Amount <= 0)
            throw new JsonException("Invalid event");
    }
    catch (JsonException)
    {
        await args.DeadLetterMessageAsync(
            args.Message, "InvalidPayload", cancellationToken: ct);
        return;
    }

    await using var scope = services.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

    try
    {
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        var existing = await db.Payments
            .AnyAsync(x => x.EventId == evt.EventId, ct);
        if (!existing)
        {
            var order = await db.Orders
                .SingleOrDefaultAsync(x => x.Id == evt.OrderId, ct);
            if (order is null)
                throw new MissingOrderException(evt.OrderId);

            // Validate domain state and payment amount here.
            db.Payments.Add(new Payment {
                EventId = evt.EventId, OrderId = evt.OrderId,
                Amount = evt.Amount
            });
            order.Status = "Paid";
            await db.SaveChangesAsync(ct);
        }

        await tx.CommitAsync(ct);
        await args.CompleteMessageAsync(args.Message, ct);
    }
    catch (DbUpdateException ex) when (IsUniqueEventIdViolation(ex))
    {
        // Provider-specific predicate must verify the exact constraint.
        // Transaction has rolled back/disposed before rechecking on fresh context.
        throw; // Outer policy should recheck committed event then complete.
    }
    catch (MissingOrderException)
    {
        // Policy: retry if upstream ordering is eventually consistent;
        // otherwise DLQ with explicit reason and alert.
        throw;
    }
};
```

**Quan trọng:** Đoạn minh họa trên chưa phải implementation hoàn chỉnh để copy production. Cần xử lý unique-conflict bằng fresh DbContext sau rollback, xác nhận bản ghi trùng thực sự cùng `EventId` và payload, rồi complete; nếu khác payload thì alert/DLQ. Đặt try/finally quanh `StartProcessingAsync`, gọi `StopProcessingAsync` và `DisposeAsync`. Cấu hình `ProcessErrorAsync`, retry budget và lock renewal. DB commit và broker complete không thể là một transaction nguyên tử; unique constraint giúp redelivery an toàn.

## Giải thích thiết kế sau khi sửa

Transaction giữ payment và order transition nhất quán trong một database. Unique constraint là chốt idempotency cuối cùng khi race xảy ra. Broker settlement chỉ sau commit. Với event có khả năng đến sai thứ tự, cần inbox/pending state hoặc retry có giới hạn thay vì coi missing order luôn là permanent error.

## Trade-offs

Unique index tăng chi phí ghi và cần migration dọn dữ liệu; transaction kéo dài có thể gây contention; concurrency thấp hơn giảm throughput đỉnh nhưng bảo vệ DB. Inbox table hữu ích khi nhiều event type và side effects, nhưng phức tạp hơn một unique index. Exactly-once effect ở DB không đồng nghĩa exactly-once delivery.

## Cách kiểm thử

1. **Concurrency test:** 100 message cùng `EventId` qua nhiều consumer, đúng một payment.
2. **Failure-path test:** DB commit xong nhưng complete thất bại; redelivery không ghi thêm.
3. **Integration test:** Missing order theo cả hai contract (event đến sớm và dữ liệu không hợp lệ).
4. **Shutdown test:** Cancel lúc SaveChanges; restart và reconcile không mất payment.
5. **Load test:** 16+ concurrent handlers, đo connection pool, p95 và lock expiration.

## Quan sát trong production

Log `EventId`, `MessageId`, `DeliveryCount`, `OrderId` (theo chính sách PII), DB transaction outcome và settlement outcome. Theo dõi Service Bus active/DLQ message count, lock-lost exceptions, duplicate rate, DB unique violations, consumer latency và backlog age. Dùng Application Insights dependency traces nối Service Bus processing với PostgreSQL.

# Code Review Challenge 2 — CMS preview bị cache công khai ở CDN

CDN được cấu hình cache GET dựa trên URL, không phân biệt cookie nếu không được chỉ dẫn. Đội vận hành cần giữ tốc độ cho public pages, nhưng tuyệt đối không phát tán draft. Giả định `IContentStore` hỗ trợ truy vấn published hoặc draft và `IsEditor` chỉ kiểm tra editor đã xác thực.

## Đoạn code cần review

```csharp
[ApiController]
[Route("content")]
public sealed class ContentController : ControllerBase
{
    private readonly IContentStore _store;
    private readonly IMemoryCache _cache;

    public ContentController(IContentStore store, IMemoryCache cache)
    {
        _store = store;
        _cache = cache;
    }

    [HttpGet("{slug}")]
    public async Task<IActionResult> Get(
        string slug, string? locale, bool preview = false)
    {
        var cacheKey = $"page:{slug}";
        var page = await _cache.GetOrCreateAsync(cacheKey, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(20);
            return await _store.LoadAsync(slug, locale ?? "en",
                includeDraft: preview);
        });

        if (page is null) return NotFound();

        Response.Headers.CacheControl = "public,max-age=600,s-maxage=3600";
        Response.Headers.ETag = $"\"{page.Version}\"";

        if (preview && !User.IsEditor())
            return Forbid();

        return Ok(new
        {
            page.Title,
            page.HtmlBody,
            page.CanonicalUrl,
            page.Version
        });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Preview authorization quá muộn

**Vấn đề:** Draft có thể được load và đưa vào shared memory cache trước khi `Forbid`.  
**Tại sao xảy ra:** Authorization check sau cache retrieval.  
**Ảnh hưởng production:** Draft có thể rò sang public response qua cùng cache key.  
**Cách sửa:** Authorization trước mọi draft access; tách preview endpoint và bypass mọi shared cache.

### [Critical] — Public cache key không phân biệt draft/published và locale

**Vấn đề:** `page:{slug}` dùng chung cho mọi locale và preview mode.  
**Tại sao xảy ra:** Cache identity thiếu các chiều quyết định nội dung.  
**Ảnh hưởng production:** Public nhận draft hoặc ngôn ngữ sai ngay cả khi request public hợp lệ.  
**Cách sửa:** Public-only key chứa normalized locale, slug, tenant/site và version nếu phù hợp; preview không dùng cache này.

### [High] — Public cache headers áp dụng cho preview

**Vấn đề:** `public,max-age=600,s-maxage=3600` cho response chứa draft.  
**Tại sao xảy ra:** Không phân biệt cache policy theo sensitivity.  
**Ảnh hưởng production:** Shared proxy/CDN có thể lưu nội dung unpublished.  
**Cách sửa:** Preview dùng `Cache-Control: private, no-store` (ưu tiên `no-store`), CDN bypass preview routes và auth cookies.

### [High] — Invalidation thiếu sau publish/unpublish

**Vấn đề:** TTL cố định không phản ánh content update.  
**Tại sao xảy ra:** Không có purge/versioned URL/short TTL policy.  
**Ảnh hưởng production:** Trang bị stale hoặc vẫn hiển thị sau unpublish.  
**Cách sửa:** Event-driven purge theo content identity, origin invalidation, bounded stale strategy cho public và fallback khi purge fail.

### [Medium] — ETag không phản ánh representation đầy đủ

**Vấn đề:** `page.Version` có thể trùng giữa locale hoặc site, và không tính serialized representation.  
**Tại sao xảy ra:** Dùng version CMS thay vì identity của response representation.  
**Ảnh hưởng production:** Conditional requests hoặc intermediary cache có thể tái sử dụng bản không phù hợp.  
**Cách sửa:** ETag dựa trên site/locale/published version hoặc response hash; kiểm thử 304 theo biến thể.

### [Medium] — Không kiểm soát SEO preview

**Vấn đề:** Preview URL và canonical URL có thể xuất hiện với crawler.  
**Tại sao xảy ra:** Không có `X-Robots-Tag: noindex, nofollow` và canonical policy cho preview.  
**Ảnh hưởng production:** Search index chứa draft URL hoặc duplicate content.  
**Cách sửa:** Preview auth-only, noindex, không đưa vào sitemap; public canonical phải đúng locale.

### [Medium] — HTML body và rendering trust boundary chưa rõ

**Vấn đề:** `HtmlBody` trả nguyên từ CMS; client có thể inject vào DOM.  
**Tại sao xảy ra:** Chưa xác định HTML sanitization/CSP và editor trust model.  
**Ảnh hưởng production:** Stored XSS nếu CMS content hoặc embedded third-party HTML không được kiểm soát.  
**Cách sửa:** Allowlist/sanitize theo pipeline CMS và render context; CSP phù hợp, test malicious content.

## Phiên bản đề xuất

```csharp
[ApiController]
[Route("content")]
public sealed class ContentController : ControllerBase
{
    private readonly IContentStore _store;
    private readonly IMemoryCache _cache;

    public ContentController(IContentStore store, IMemoryCache cache)
    {
        _store = store;
        _cache = cache;
    }

    [HttpGet("{slug}")]
    public async Task<IActionResult> Public(
        string slug, [FromQuery] string locale = "en",
        CancellationToken ct = default)
    {
        locale = NormalizeSupportedLocale(locale);
        slug = NormalizeSlug(slug);
        var key = $"published:site-main:{locale}:{slug}";

        var page = await _cache.GetOrCreateAsync(key, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            return await _store.LoadPublishedAsync(slug, locale, ct);
        });

        if (page is null) return NotFound();

        Response.Headers.CacheControl = "public,max-age=60,s-maxage=300";
        Response.Headers.ETag = MakeRepresentationEtag(page, locale);
        return Ok(ToSafePublicDto(page));
    }

    [HttpGet("preview/{slug}")]
    [Authorize(Policy = "CmsEditor")]
    public async Task<IActionResult> Preview(
        string slug, [FromQuery] string locale = "en",
        CancellationToken ct = default)
    {
        Response.Headers.CacheControl = "private,no-store";
        Response.Headers["X-Robots-Tag"] = "noindex, nofollow";

        var page = await _store.LoadDraftAsync(
            NormalizeSlug(slug), NormalizeSupportedLocale(locale), ct);
        return page is null ? NotFound() : Ok(ToSafePreviewDto(page));
    }
}
```

`NormalizeSupportedLocale`, `NormalizeSlug`, `MakeRepresentationEtag` và DTO mapping là application-specific functions cần implement và test. `IContentStore` phải thực sự enforce published-only semantics; `[Authorize]` phải được cấu hình đúng middleware/policy. CDN rule phải bypass `/content/preview/*` và không cache response có authentication; không dựa riêng vào header nếu CDN đang override origin headers. Đảm bảo không cache personalized content ở public endpoint.

## Giải thích thiết kế sau khi sửa

Tách route preview làm rõ trust boundary. Public route không bao giờ có đường code load draft. Cache identity phản ánh locale và site; cache policy có thể audit độc lập. Purge/invalidation phải xử lý cả origin cache trên nhiều instance và CDN; `IMemoryCache` chỉ local, không tự đồng bộ.

## Trade-offs

Bỏ cache preview tăng origin traffic nhưng editor traffic thường thấp. TTL public ngắn tăng cache misses; purge giúp TTL dài hơn nhưng tăng operational complexity và yêu cầu retry/monitoring. Cache key nhiều chiều tăng cardinality; cân nhắc quota và eviction. Không nên đưa Redis vào chỉ để giải quyết một bug key nếu CDN + bounded local cache đã đủ.

## Cách kiểm thử

1. **Security integration:** Anonymous gọi preview nhận 401/403; không có draft trong public response sau đó.
2. **Cross-variant:** Cùng slug với hai locale và draft/published trả đúng representation qua nhiều instance.
3. **CDN E2E:** Request preview có cookie không được cache; inspect `Age`, `Cache-Control` và cache-status.
4. **Publish/unpublish:** Trigger purge, kiểm tra origin và CDN không phục vụ bản cũ quá freshness SLA.
5. **Security/E2E:** CMS HTML chứa script/unsafe URL, xác minh sanitization/CSP và noindex preview.

## Quan sát trong production

Theo dõi CDN cache hit/miss và cache status theo route class (không log auth cookie), response `Age`, cache purge failures, origin cache hit ratio, preview authorization denials, content version/locale mismatch, published-to-visible lag và crawler access to preview routes. Alert ngay khi public response mang draft version marker; không ghi raw unpublished content vào logs.

## Câu hỏi phỏng vấn mở rộng

1. Khi CDN purge API outage, bạn chọn stale window và fallback thế nào?
2. Multi-tenant CMS với cùng slug và locale cần thêm gì vào cache key và authorization?
3. Nếu site dùng React SSR, đâu là ranh giới giữa CDN cache và per-user hydration data?
