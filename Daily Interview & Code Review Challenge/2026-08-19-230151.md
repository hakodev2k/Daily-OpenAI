# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng và ghi đè trạng thái

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, transaction handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để xử lý cấu hình offboarding. Job tìm các cấu hình đến hạn, gọi dịch vụ ngoài để cập nhật mailbox rồi đánh dấu bản ghi đã hoàn tất. Ứng dụng chạy 3 instance phía sau load balancer; Hangfire có nhiều worker. Bình thường khoảng vài trăm cấu hình/ngày, nhưng cuối tháng có thể tăng mạnh.

Production thỉnh thoảng ghi nhận cùng một mailbox được gọi cập nhật hai lần, một số bản ghi đã xử lý bên ngoài nhưng vẫn còn `Pending`, và khi dịch vụ ngoài chậm thì số job retry tăng mạnh. Yêu cầu nghiệp vụ là thao tác phải an toàn khi retry; không được giả định external API hỗ trợ distributed transaction với database.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IExchangeService exchange,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task RunAsync()
    {
        var now = DateTime.UtcNow;

        var configs = await _db.OffboardingConfigs
            .Where(x => x.Status == "Pending" && x.EndTime <= now)
            .ToListAsync();

        foreach (var config in configs)
        {
            try
            {
                await _exchange.ResetMailboxAsync(config.UserEmail);

                config.Status = "Completed";
                config.CompletedAt = DateTime.UtcNow;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Reset mailbox completed for {Email}",
                    config.UserEmail);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Reset mailbox failed for {Email}",
                    config.UserEmail);
                throw;
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không có cơ chế atomic claim bản ghi

- **Problem:** Nhiều worker có thể cùng query một config `Pending`.
- **Why it happens:** Query và chuyển trạng thái không phải một atomic operation có concurrency guard.
- **Production impact:** External API có thể nhận thao tác trùng; trạng thái và audit có thể sai.
- **Severity:** Critical.
- **Recommended fix:** Claim item atomically trước khi thực hiện side effect, ví dụ conditional update `Pending -> Processing` với concurrency token/affected-row check; thiết kế theo khả năng của SQL Server/PostgreSQL.

### 2. External side effect và database commit tạo dual-write failure window

- **Problem:** `ResetMailboxAsync` có thể thành công nhưng `SaveChangesAsync` thất bại.
- **Why it happens:** Hai hệ thống không nằm trong cùng transaction.
- **Production impact:** Retry gọi external operation lần nữa trong khi DB vẫn cho rằng item chưa hoàn tất.
- **Severity:** Critical.
- **Recommended fix:** External operation phải idempotent nếu có thể; dùng operation/idempotency key nếu provider hỗ trợ. Nếu không, kiểm tra trạng thái đích trước khi mutate và có reconciliation state rõ ràng.

### 3. Retry ở mức toàn batch

- **Problem:** Exception ở item thứ N làm Hangfire retry toàn `RunAsync`.
- **Why it happens:** Method throw sau lỗi của một item.
- **Production impact:** Các item trước đó được scan lại, tăng tải và mở rộng duplicate window.
- **Severity:** High.
- **Recommended fix:** Enqueue job theo từng item hoặc dispatcher chỉ claim/enqueue item; retry độc lập từng operation.

### 4. Không có idempotency contract

- **Problem:** Code giả định gọi `ResetMailboxAsync` nhiều lần là an toàn.
- **Why it happens:** Không định nghĩa desired state hoặc operation identity.
- **Production impact:** Side effect lặp lại có thể gây lỗi hoặc thay đổi ngoài ý muốn.
- **Severity:** High.
- **Recommended fix:** Thiết kế operation theo desired state, operation ID và/hoặc kiểm tra trạng thái hiện tại trước mutation.

### 5. Không truyền cancellation token

- **Problem:** Query, save và external call không nhận cancellation.
- **Why it happens:** `RunAsync` không expose token phù hợp cho shutdown/cancellation.
- **Production impact:** Deployment/shutdown có thể kéo dài; request ngoài tiếp tục dù worker cần dừng.
- **Severity:** Medium.
- **Recommended fix:** Tích hợp cancellation abstraction phù hợp với job runtime và truyền xuống I/O APIs.

### 6. Load toàn bộ batch vào memory

- **Problem:** `ToListAsync()` lấy toàn bộ item đến hạn.
- **Why it happens:** Không giới hạn batch/pagination.
- **Production impact:** Memory, tracking overhead và thời gian giữ `DbContext` tăng khi backlog lớn.
- **Severity:** Medium.
- **Recommended fix:** Claim theo batch nhỏ, có index hỗ trợ `(Status, EndTime)` và lặp có giới hạn.

### 7. Một DbContext tracking nhiều entity trong job dài

- **Problem:** Context sống xuyên suốt toàn batch.
- **Why it happens:** Mỗi entity vẫn được tracking sau `SaveChangesAsync`.
- **Production impact:** Change tracker tăng dần, khó recovery sau lỗi và làm job dài khó kiểm soát.
- **Severity:** Medium.
- **Recommended fix:** Job per-item với scope riêng hoặc context ngắn hạn theo batch/item.

### 8. State model quá nghèo

- **Problem:** Chỉ có `Pending/Completed`.
- **Why it happens:** Không biểu diễn claim, retry, uncertain outcome hoặc terminal failure.
- **Production impact:** Khó reconciliation và vận hành khi external outcome không xác định.
- **Severity:** Medium.
- **Recommended fix:** Dùng state rõ ràng như `Pending`, `Processing`, `Completed`, `RetryableFailure`, `NeedsReconciliation`; lưu attempt, operation ID và timestamps.

### 9. Logging thiếu correlation và operation identity

- **Problem:** Log chủ yếu dựa trên email.
- **Why it happens:** Không có config ID, operation ID, attempt hoặc duration.
- **Production impact:** Khó chứng minh duplicate và lần theo retry.
- **Severity:** Low.
- **Recommended fix:** Structured log với config ID, operation ID, job ID/attempt, duration và external result category; tránh log dữ liệu nhạy cảm không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa separation giữa dispatcher và item processor. `TryClaimAsync` phải được hiện thực bằng conditional update atomic tại database; không phải read-then-write thông thường.

```csharp
public sealed class OffboardingDispatcher
{
    private readonly IOffboardingStore _store;
    private readonly IBackgroundJobClient _jobs;

    public OffboardingDispatcher(
        IOffboardingStore store,
        IBackgroundJobClient jobs)
    {
        _store = store;
        _jobs = jobs;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        var ids = await _store.FindDueIdsAsync(
            DateTimeOffset.UtcNow,
            take: 100,
            cancellationToken);

        foreach (var id in ids)
            _jobs.Enqueue<OffboardingItemJob>(x => x.RunAsync(id, CancellationToken.None));
    }
}

public sealed class OffboardingItemJob
{
    private readonly IOffboardingStore _store;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingItemJob> _logger;

    public OffboardingItemJob(
        IOffboardingStore store,
        IExchangeService exchange,
        ILogger<OffboardingItemJob> logger)
    {
        _store = store;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task RunAsync(long configId, CancellationToken cancellationToken)
    {
        var operationId = Guid.NewGuid().ToString("N");
        var item = await _store.TryClaimAsync(
            configId,
            operationId,
            cancellationToken);

        if (item is null)
            return;

        try
        {
            await _exchange.EnsureMailboxResetAsync(
                item.UserEmail,
                operationId,
                cancellationToken);

            await _store.MarkCompletedAsync(
                configId,
                operationId,
                DateTimeOffset.UtcNow,
                cancellationToken);

            _logger.LogInformation(
                "Offboarding operation {OperationId} completed for config {ConfigId}",
                operationId,
                configId);
        }
        catch (Exception ex)
        {
            await _store.MarkForRetryOrReconciliationAsync(
                configId,
                operationId,
                cancellationToken);

            _logger.LogError(
                ex,
                "Offboarding operation {OperationId} failed for config {ConfigId}",
                operationId,
                configId);

            throw;
        }
    }
}
```

Điểm quan trọng: implementation thực tế phải định nghĩa semantics khi process chết sau external success nhưng trước `MarkCompletedAsync`. Nếu external system không hỗ trợ idempotency key, `EnsureMailboxResetAsync` cần kiểm tra desired state hoặc workflow phải đưa item vào reconciliation thay vì mù quáng replay side effect.

## Trade-offs

Tách job per-item tăng số Hangfire records và scheduling overhead nhưng isolation, retry và observability tốt hơn. Atomic claim làm database logic phức tạp hơn và khác nhau giữa SQL Server/PostgreSQL, nhưng loại bỏ phần lớn race condition ở application layer. Distributed lock có thể giảm concurrency nhưng không tự giải quyết dual-write failure và không nên được xem là thay thế cho idempotency. Nếu external operation thực sự idempotent theo desired state, thiết kế có thể đơn giản hơn đáng kể.

## Cách kiểm thử

1. **Concurrency integration test:** cho 20 worker đồng thời claim cùng `configId`; xác nhận chỉ một worker nhận quyền xử lý.
2. **Failure-path test:** external call thành công nhưng DB completion giả lập fail; retry không tạo side effect nguy hiểm và item cuối cùng được reconcile.
3. **Retry test:** external API timeout ở attempt đầu, thành công ở attempt sau; trạng thái và attempt count đúng.
4. **Load test:** backlog hàng chục nghìn item; xác nhận batch size, memory, DB query latency và worker throughput ổn định.
5. **Crash test:** kill process tại các boundary trước/sau external call và trước/sau DB update; xác nhận workflow hội tụ về desired state.

## Quan sát trong production

Theo dõi số item theo từng state, tuổi của item `Pending/Processing`, retry count, reconciliation backlog, external-call latency/error rate, job duration và throughput. Trace nên liên kết `configId`, operation ID, Hangfire job và external request. Alert khi `Processing` quá lâu, retry spike hoặc backlog tăng liên tục. Database nên theo dõi query plan/index usage và contention trên thao tác claim.

## Câu hỏi phỏng vấn mở rộng

2. Distributed lock có giải quyết được lỗi “external success, DB failure” không? Vì sao?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log có lỗ hổng authorization và SQL injection

**Chủ đề:** Authentication/authorization, SQL correctness, input validation, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cung cấp màn hình audit log cho portal nội bộ. Người dùng đã đăng nhập bằng bearer token. Mỗi tenant có dữ liệu audit riêng; chỉ user có quyền audit trong tenant hiện tại mới được xem. Endpoint cho phép tìm theo text và khoảng ngày.

Sau một đợt penetration test, security team nghi ngờ endpoint có thể đọc dữ liệu tenant khác và có khả năng injection. Production cũng ghi nhận một số search request làm SQL Server CPU tăng cao. Audit payload đôi khi chứa email, IDs và metadata nghiệp vụ.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        string tenantId,
        string? q,
        DateTime? from,
        DateTime? to)
    {
        var sql = $@"
            SELECT Id, TenantId, UserEmail, Action, Payload, CreatedAt
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'";

        if (!string.IsNullOrWhiteSpace(q))
            sql += $" AND (Action LIKE '%{q}%' OR Payload LIKE '%{q}%')";

        if (from.HasValue)
            sql += $" AND CreatedAt >= '{from.Value:yyyy-MM-dd HH:mm:ss}'";

        if (to.HasValue)
            sql += $" AND CreatedAt <= '{to.Value:yyyy-MM-dd HH:mm:ss}'";

        sql += " ORDER BY CreatedAt DESC";

        _logger.LogInformation("Audit search SQL: {Sql}", sql);

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization

- **Problem:** `tenantId` do client tự truyền và code không kiểm tra membership/permission.
- **Why it happens:** `[Authorize]` chỉ yêu cầu principal đã được authenticate theo policy mặc định; nó không tự chứng minh quyền truy cập tenant cụ thể.
- **Production impact:** User hợp lệ có thể thử tenant ID khác và đọc audit data không thuộc phạm vi của mình.
- **Severity:** Critical.
- **Recommended fix:** Resolve tenant từ trusted claim/context hoặc thực hiện resource-based/policy authorization đối với tenant; query luôn scope bằng tenant đã được server xác thực.

### 2. SQL injection qua `tenantId` và `q`

- **Problem:** User input được interpolate trực tiếp vào SQL.
- **Why it happens:** `FromSqlRaw` nhận SQL đã được ghép chuỗi.
- **Production impact:** Có thể thay đổi predicate/query semantics, đọc trái phép dữ liệu hoặc gây tác động khác tùy quyền DB account.
- **Severity:** Critical.
- **Recommended fix:** Dùng LINQ parameterized query hoặc API SQL parameterization phù hợp; không concatenate user-controlled input.

### 3. Không giới hạn số kết quả

- **Problem:** Query trả toàn bộ rows matching.
- **Why it happens:** Không pagination/take cap.
- **Production impact:** Memory pressure, response lớn, DB load cao và dễ bị abuse.
- **Severity:** High.
- **Recommended fix:** Cursor/keyset pagination hoặc bounded page size; giới hạn cứng hợp lý.

### 4. Search `%q%` trên `Payload` có thể rất đắt

- **Problem:** Leading wildcard search trên text/payload lớn thường không tận dụng B-tree index thông thường cho prefix seek.
- **Why it happens:** Search arbitrary substring trên nhiều cột.
- **Production impact:** Scan nhiều dữ liệu, CPU/I/O tăng theo tenant history.
- **Severity:** High.
- **Recommended fix:** Xác định requirement tìm kiếm; index các field có cấu trúc, dùng search technology/full-text phù hợp khi thật sự cần free-text, giới hạn date range và page size.

### 5. Trả entity/payload đầy đủ không theo least privilege

- **Problem:** Endpoint trả `UserEmail`, `Payload` và toàn entity cho mọi caller có route access.
- **Why it happens:** Không projection/field-level access policy.
- **Production impact:** Lộ PII/metadata nhiều hơn nhu cầu UI.
- **Severity:** High.
- **Recommended fix:** DTO projection chỉ gồm fields cần thiết; mask/redact payload và áp dụng quyền chi tiết nếu cần.

### 6. Log raw SQL chứa input và dữ liệu tìm kiếm

- **Problem:** Log statement chứa tenant ID và query text do user nhập.
- **Why it happens:** Ghi toàn bộ interpolated SQL.
- **Production impact:** Sensitive search terms bị lưu trong logging backend; newline/control input còn có thể làm log khó phân tích.
- **Severity:** Medium.
- **Recommended fix:** Log structured metadata như tenant scope ID đã chuẩn hóa, page size, duration, result count; không log raw query payload nếu không cần.

### 7. Không validate khoảng thời gian

- **Problem:** `from > to`, khoảng thời gian quá rộng hoặc semantics timezone không rõ.
- **Why it happens:** Không có validation/business constraint.
- **Production impact:** Query sai kỳ vọng hoặc scan lượng dữ liệu rất lớn.
- **Severity:** Medium.
- **Recommended fix:** Chuẩn hóa UTC/`DateTimeOffset`, validate range và áp dụng maximum window nếu phù hợp nghiệp vụ.

### 8. Không truyền request cancellation

- **Problem:** Query tiếp tục khi client disconnect/cancel.
- **Why it happens:** Không nhận `CancellationToken` từ action.
- **Production impact:** DB vẫn tốn tài nguyên cho request không còn người nhận.
- **Severity:** Low/Medium.
- **Recommended fix:** Nhận `CancellationToken` và truyền vào EF Core async operation.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IAuthorizationService _authorization;

    public AuditController(
        AppDbContext db,
        IAuthorizationService authorization)
    {
        _db = db;
        _authorization = authorization;
    }

    [HttpGet]
    public async Task<ActionResult<AuditPage>> Search(
        Guid tenantId,
        [FromQuery] string? q,
        [FromQuery] DateTimeOffset? from,
        [FromQuery] DateTimeOffset? to,
        [FromQuery] int take = 50,
        [FromQuery] DateTimeOffset? before = null,
        CancellationToken cancellationToken = default)
    {
        var auth = await _authorization.AuthorizeAsync(
            User,
            tenantId,
            "CanReadTenantAudit");

        if (!auth.Succeeded)
            return Forbid();

        if (from.HasValue && to.HasValue && from > to)
            return BadRequest("'from' must be earlier than or equal to 'to'.");

        take = Math.Clamp(take, 1, 100);
        q = string.IsNullOrWhiteSpace(q) ? null : q.Trim();

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value);

        if (before.HasValue)
            query = query.Where(x => x.CreatedAt < before.Value);

        if (q is not null)
            query = query.Where(x => x.Action.Contains(q));

        var items = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(take + 1)
            .Select(x => new AuditItemDto(
                x.Id,
                x.Action,
                x.CreatedAt))
            .ToListAsync(cancellationToken);

        var hasMore = items.Count > take;
        if (hasMore)
            items.RemoveAt(items.Count - 1);

        return Ok(new AuditPage(items, hasMore));
    }
}

public sealed record AuditItemDto(
    long Id,
    string Action,
    DateTimeOffset CreatedAt);

public sealed record AuditPage(
    IReadOnlyList<AuditItemDto> Items,
    bool HasMore);
```

Đây là reference direction, không phải universal solution. Nếu UI thật sự phải tìm arbitrary text trong payload, nên thiết kế search riêng thay vì giả định `Contains` trên một cột nhỏ giải quyết được yêu cầu. Authorization policy cũng phải xác minh tenant membership/role từ nguồn đáng tin cậy; việc đặt `tenantId` vào route chỉ cải thiện resource modeling chứ tự nó không tạo authorization.

## Trade-offs

LINQ giúp parameterization và composability nhưng không tự đảm bảo query nhanh; execution plan vẫn phải được đo. Keyset pagination hiệu quả và ổn định hơn offset ở dataset lớn nhưng API phức tạp hơn, đặc biệt khi sort key không unique; nên dùng composite cursor như `(CreatedAt, Id)` nếu cần pagination chính xác. Full-text/search engine tăng khả năng tìm kiếm nhưng thêm hạ tầng, consistency và chi phí vận hành. Projection giảm exposure nhưng có thể cần endpoint chi tiết riêng khi người có quyền cần xem payload đầy đủ.

## Cách kiểm thử

1. **Authorization test:** user tenant A gọi route tenant B phải bị từ chối dù token hợp lệ.
2. **Injection test:** truyền payload chứa quote, SQL metacharacters và wildcard; query không thay đổi semantics ngoài search value.
3. **Data exposure test:** response list không chứa `UserEmail`/`Payload`; endpoint chi tiết nếu có phải kiểm tra quyền riêng.
4. **Performance test:** tenant có hàng triệu audit rows; đo query plan, logical reads, latency với date filter và pagination.
5. **Cancellation/failure test:** client cancel trong lúc DB query; request dừng hợp lý và không ghi log lỗi giả tạo.

## Quan sát trong production

Ghi structured log cho authorization failure, tenant scope đã chuẩn hóa, query duration, result count và page size nhưng tránh raw search text/sensitive payload. Theo dõi p50/p95/p99 latency, DB duration, timeout/cancellation rate, denied-access count và rows scanned/logical reads nếu telemetry cho phép. Alert khi latency hoặc DB CPU tăng bất thường; review execution plan/index cho `(TenantId, CreatedAt, Id)` theo pattern query thực tế.

## Câu hỏi phỏng vấn mở rộng

1. Nếu tenant ID đã có trong JWT claim, bạn có còn cần resource authorization không? Trường hợp nào có và không?
2. Vì sao parameterization sửa SQL injection nhưng không sửa được broken authorization?
3. Nếu business bắt buộc search substring trong JSON payload trên hàng trăm triệu records, bạn sẽ thay đổi data model/search architecture thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào một nguyên tắc quan trọng của distributed workflow: database commit và external side effect tạo ra failure window mà transaction cục bộ không thể loại bỏ. Retry chỉ an toàn khi operation có idempotency/reconciliation semantics, và concurrency phải được kiểm soát ở nơi có atomicity thực sự.

Challenge 2 nhấn mạnh rằng authentication, authorization và SQL parameterization giải quyết ba lớp vấn đề khác nhau. Một endpoint có token hợp lệ vẫn có thể bị broken object/tenant authorization; parameterized query chống injection nhưng không sửa quyền truy cập hoặc query plan kém. Pagination, projection và observability là một phần của security/performance design chứ không chỉ là tối ưu phụ.

## Mẫu tư duy cần nhớ

- Xem mọi background job có retry như một state machine có thể bị dừng ở bất kỳ boundary nào.
- Thiết kế retry cùng idempotency và reconciliation; đừng coi distributed lock là lời giải cho dual-write failure.
- Authentication trả lời “ai”, authorization trả lời “được làm gì trên resource nào”.
- Parameterize input, nhưng đồng thời kiểm tra trust boundary, scope dữ liệu và cost của query.
- Treat observability as part of the design: operation identity, state transition, latency và failure category phải truy vết được.
