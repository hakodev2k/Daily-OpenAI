# Câu 1 — Search UI hiển thị kết quả cũ: Promise, event loop và race condition đang xảy ra thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** JavaScript/TypeScript, Vue.js/React.js, Promise, event loop, Fetch API, `AbortController`, async race condition, state management, frontend/backend integration

## Bối cảnh

Một product-search page được xây bằng Vue.js hoặc React.js. Khi user gõ vào search box, frontend gọi API:

```text
GET /api/products/search?q={keyword}
```

Để giảm request, UI có debounce 250 ms. Logic hiện tại về ý tưởng gần giống:

```ts
async function search(keyword: string) {
  loading.value = true;

  try {
    const response = await fetch(`/api/products/search?q=${encodeURIComponent(keyword)}`);
    const data = await response.json();
    products.value = data.items;
  } finally {
    loading.value = false;
  }
}
```

Production symptoms:

- user gõ nhanh `car` rồi tiếp tục thành `car seat`;
- network tab cho thấy request `car seat` đôi lúc trả về trước request `car`;
- UI sau đó lại hiển thị kết quả của `car`;
- bug khó tái hiện local khi network nhanh;
- developer đề xuất tăng debounce lên 1 giây;
- developer khác đề xuất dùng `setTimeout` trước khi gán state để “đợi request mới nhất chạy xong”;
- một developer nói Promise chạy theo thứ tự tạo request nên response cũ không thể overwrite response mới;
- page còn có loading indicator và error message dùng chung state.

Chưa biết chắc:

- backend có cache theo query hay không;
- component có unmount/remount khi route đổi hay không;
- request cũ có cần bị cancel thật sự hay chỉ cần bỏ kết quả stale;
- search API có side effect hay hoàn toàn read-only;
- framework-specific lifecycle/state library hiện đang dùng cách nào.

## Câu hỏi chính

Hãy giải thích ở mức event loop/Promise completion vì sao request được gửi trước vẫn có thể hoàn thành sau và overwrite state của request mới hơn, sau đó thiết kế một solution chống stale response phù hợp cho Vue.js/React.js mà không phụ thuộc vào timing may mắn.

## Câu hỏi làm rõ nên cân nhắc

1. API search có hoàn toàn read-only và idempotent không?
2. Khi keyword đổi, requirement là cancel network request cũ hay chỉ bảo đảm kết quả cũ không được commit vào UI state?
3. Có nhiều component cùng dùng search state hay state chỉ local trong page?
4. Loading indicator phải phản ánh request mới nhất hay tổng số request đang in-flight?
5. Khi component unmount hoặc route đổi, pending fetch hiện được cleanup như thế nào?

## Gợi ý tư duy

### Gợi ý 1

Thứ tự gọi `fetch()` không tạo ra thứ tự hoàn thành của network I/O.

### Gợi ý 2

`await` chỉ tiếp tục function khi Promise tương ứng settle; hai async executions độc lập có thể resume theo thứ tự khác nhau.

### Gợi ý 3

Một solution chắc chắn thường cần identity/version của request mới nhất và/hoặc cancellation bằng `AbortController`.

## Cấu trúc trả lời đề xuất

1. Mô tả hai request A và B theo timeline.
2. Giải thích Promise/microtask continuation ở mức đủ dùng.
3. Chỉ ra assumption sai về request order.
4. Phân biệt debounce với race-condition control.
5. Chọn strategy: latest-request token/version, `AbortController`, hoặc kết hợp.
6. Thiết kế loading/error state đúng với request mới nhất.
7. Xử lý component cleanup.
8. Đánh giá backend cancellation có thật sự tiết kiệm work hay không.
9. Viết test tái hiện response reordering.
10. Đề xuất browser/network telemetry phù hợp.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu request A gửi trước không đảm bảo response A về trước B.
- Hiểu mỗi async call có Promise/continuation độc lập; continuation chạy khi operation của chính nó hoàn tất.
- Nhận ra debounce chỉ giảm tần suất request, không bảo đảm ordering của response.
- Không dùng arbitrary `setTimeout` để sửa race.
- Có cơ chế latest-request-wins hoặc request version/token.
- Biết `AbortController` có thể abort `fetch` và response-body consumption khi phù hợp.
- Không để request cũ reset `loading=false` hoặc overwrite error state của request mới.
- Có cleanup khi component unmount/navigation.

### Điểm cộng

- Phân biệt cancellation của client với guarantee rằng server đã dừng processing; backend phải propagate cancellation phù hợp và operation có thể đã hoàn thành.
- Dùng immutable request context gồm keyword/requestId thay vì dựa vào mutable global variable không rõ ownership.
- Thiết kế query library/state layer để deduplicate/cache khi project đã dùng công cụ phù hợp, nhưng không thêm dependency chỉ để che một race đơn giản.
- Xử lý `AbortError` riêng để không hiển thị lỗi cho cancellation chủ động.

### Senior+

- Mô hình hóa state thành `idle/loading/success/error` gắn với request version thay vì nhiều booleans rời rạc.
- Viết deterministic test bằng deferred promises hoặc mocked fetch để chủ động trả B trước A.
- Phân biệt UI consistency với backend business consistency: với read-only search, latest-result-wins thường phù hợp; với mutation thì cần idempotency/concurrency semantics khác.
- Đề xuất telemetry đo canceled requests, stale-result drops, request latency và search conversion mà không log dữ liệu nhạy cảm không cần thiết.

## Hướng giải quyết tham khảo

Tôi sẽ mô tả bằng timeline.

Giả sử user gõ `car`, frontend gửi request A. Sau đó user gõ `car seat`, frontend gửi request B. A bắt đầu trước nhưng backend/cache/network path của A có thể chậm hơn B. Vì vậy B có thể resolve trước:

```text
T0: send A("car")
T1: send B("car seat")
T2: B response arrives
T3: B continuation updates state -> "car seat" results
T4: A response arrives
T5: A continuation updates state -> stale "car" results
```

JavaScript không “xếp hàng network response theo thứ tự request”. `fetch()` trả Promise ngay. Khi từng network operation hoàn thành, Promise tương ứng settle và continuation sau `await` được scheduling theo event-loop/microtask semantics. Điều quan trọng là hai async executions độc lập không có ordering relationship chỉ vì A được gọi trước B.

Debounce 250 ms giúp giảm số request khi user đang gõ nhưng không loại bỏ trường hợp hai request cùng in-flight. Tăng debounce lên 1 giây chỉ làm UX chậm hơn và race vẫn tồn tại khi request overlap.

Một cách đơn giản là request version:

```ts
let latestRequestId = 0;

async function search(keyword: string) {
  const requestId = ++latestRequestId;

  loading.value = true;
  error.value = null;

  try {
    const response = await fetch(
      `/api/products/search?q=${encodeURIComponent(keyword)}`
    );

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const data = await response.json();

    if (requestId !== latestRequestId) {
      return;
    }

    products.value = data.items;
  } catch (err) {
    if (requestId !== latestRequestId) {
      return;
    }

    error.value = err instanceof Error ? err.message : "Search failed";
  } finally {
    if (requestId === latestRequestId) {
      loading.value = false;
    }
  }
}
```

Đây là latest-request-wins ở state boundary. Request cũ vẫn có thể dùng bandwidth/backend resources, nhưng kết quả stale không được commit.

Nếu muốn cancel request cũ, dùng `AbortController`:

```ts
let currentController: AbortController | null = null;
let latestRequestId = 0;

async function search(keyword: string) {
  const requestId = ++latestRequestId;

  currentController?.abort();
  const controller = new AbortController();
  currentController = controller;

  loading.value = true;
  error.value = null;

  try {
    const response = await fetch(
      `/api/products/search?q=${encodeURIComponent(keyword)}`,
      { signal: controller.signal }
    );

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const data = await response.json();

    if (requestId === latestRequestId) {
      products.value = data.items;
    }
  } catch (err) {
    if (controller.signal.aborted) {
      return;
    }

    if (requestId === latestRequestId) {
      error.value = err instanceof Error ? err.message : "Search failed";
    }
  } finally {
    if (requestId === latestRequestId) {
      loading.value = false;
    }
  }
}
```

Tôi vẫn giữ request version kể cả khi abort, vì cancellation không nên là dependency duy nhất cho state correctness. Một request có thể đã hoàn thành sát thời điểm abort; version check làm commit rule explicit.

Trong React, pattern tương tự có thể nằm trong `useEffect` cleanup; trong Vue có thể đặt ở watcher/lifecycle cleanup. Exact API phụ thuộc version/framework setup hiện tại, nhưng nguyên tắc là lifecycle phải cancel hoặc invalidate work cũ khi dependency/component không còn current.

Với loading state, request A không được phép set `loading=false` trong khi B còn chạy. Vì vậy `finally` cũng phải kiểm tra request identity. Tương tự error của A không được overwrite success/error của B.

Backend side: aborting browser fetch có thể truyền cancellation xuống ASP.NET Core nếu connection/request cancellation được framework propagate và code backend truyền `HttpContext.RequestAborted`/`CancellationToken` tới downstream operations. Nhưng client abort không phải guarantee rằng DB/external work chưa commit. Với read-only search đây chủ yếu là resource optimization. Với mutation, không được dùng browser abort như transaction rollback semantics.

Test tốt nhất là deterministic response reordering. Mock fetch để A chờ, B resolve trước, assert UI hiển thị B, sau đó resolve A và assert UI vẫn giữ B. Thêm test abort/unmount, loading state và error của stale request.

MDN hiện mô tả `AbortController.abort()` có thể abort fetch request, response body consumption và streams. Exact browser support cần kiểm tra nếu application hỗ trợ browser rất cũ, nhưng đây là Web API đã phổ biến rộng.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không coi thứ tự gọi `fetch` là thứ tự response. Hai async call độc lập; A có thể gửi trước nhưng B resolve trước. Khi B update state xong, continuation của A có thể chạy sau và overwrite UI bằng dữ liệu cũ. Debounce chỉ giảm request count chứ không sửa ordering.

Em dùng latest-request-wins: mỗi search có `requestId`, chỉ request có id mới nhất mới được phép commit `products/loading/error`. Đồng thời em abort request cũ bằng `AbortController` để giảm work không cần thiết, nhưng vẫn giữ version check vì state correctness không nên phụ thuộc hoàn toàn vào cancellation timing.

Khi component unmount em cleanup pending request. Em test bằng mocked fetch cho B trả trước A để race tái hiện deterministic. Nếu backend hỗ trợ cancellation, em propagate token, nhưng với mutation em không bao giờ coi client abort là rollback.”

## Câu hỏi đào sâu

1. Nếu search request A đã vào database trước khi browser abort, backend có chắc chắn dừng query ngay không? Bạn sẽ thiết kế cancellation thế nào?
2. Nếu Product muốn cache query results ở frontend để back-navigation nhanh, request-version logic và cache key nên thay đổi ra sao?
3. Một teammate đề xuất chỉ dùng `AbortController` và bỏ request version vì “abort là đủ”; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Cho rằng Promise luôn resolve theo thứ tự được tạo.
- Tăng debounce hoặc thêm `setTimeout` để che race.
- Chỉ bảo vệ `products` nhưng để stale request overwrite `loading/error`.
- Hiển thị cancellation chủ động như application error.
- Dùng client-side abort như guarantee backend mutation chưa xảy ra.

## Thang điểm 0–10

- **0–2:** Chỉ tăng debounce hoặc nói “JavaScript single-thread nên không có race”.
- **3–4:** Nhận ra response reordering nhưng fix phụ thuộc timing.
- **5–6:** Có latest-request-wins/cancellation và hiểu Promise execution cơ bản.
- **7–8:** Xử lý đầy đủ state, lifecycle, deterministic tests và backend cancellation.
- **9–10:** Phân biệt state consistency/cancellation/business side effects, thiết kế state machine và telemetry rõ ràng.

# Câu 2 — Release “thành công” trong TeamCity/Octopus nhưng API 500 vì database migration và version compatibility

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** CI/CD, TeamCity, Octopus Deploy, ASP.NET Core, SQL Server, database migration, backward compatibility, deployment safety, rollback, observability, incident response

## Bối cảnh

Một enterprise portal chạy 6 ASP.NET Core instances sau load balancer. CI build bằng TeamCity và deploy bằng Octopus Deploy.

Release mới gồm:

- code version `v42`;
- EF Core migration đổi schema `Orders`;
- một column cũ `LegacyStatus` được thay bằng `StatusCode`;
- code `v42` chỉ đọc `StatusCode`;
- migration script add `StatusCode`, backfill từ `LegacyStatus`, rồi drop `LegacyStatus` trong cùng deployment;
- deployment rolling từng instance để tránh downtime;
- pipeline báo xanh và package deployment thành công.

Ngay sau release:

- 500 tăng theo từng đợt trong khoảng 10 phút;
- một số request thành công, một số fail;
- log ở vài instances báo missing column `LegacyStatus`;
- log ở vài instances khác báo missing column `StatusCode` trong thời gian đầu;
- rollback application package về `v41` không phục hồi hoàn toàn service;
- DBA cho biết migration đã chạy một lần và drop column cũ;
- developer đề xuất từ giờ luôn chạy migration trước code deployment;
- người khác đề xuất luôn deploy code trước migration;
- release còn có một background job đang chạy trong lúc schema thay đổi.

Chưa biết chắc:

- exact ordering giữa migration và từng instance rollout;
- old/new instances coexist trong bao lâu;
- background job version nào đang chạy ở từng thời điểm;
- migration có transaction toàn bộ hay từng bước;
- backfill duration và lock impact;
- rollback script có tồn tại/đã test hay không;
- health check có kiểm tra functional DB compatibility hay chỉ process health.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào, dùng evidence gì để dựng timeline, và redesign release/migration strategy như thế nào để old và new application versions có thể coexist an toàn trong rolling deployment mà không phụ thuộc vào “migration luôn trước” hoặc “code luôn trước”.

## Câu hỏi làm rõ nên cân nhắc

1. Load balancer có thực sự route tới cả `v41` và `v42` trong deployment window không?
2. Migration được thực thi bởi pipeline, application startup hay một job riêng?
3. Có release nào khác/background worker dùng cùng schema nhưng deploy độc lập không?
4. Drop `LegacyStatus` có thật sự bắt buộc trong cùng release hay có thể trì hoãn?
5. Có restore/rollback plan cho destructive migration và đã rehearsal trên production-like data chưa?

## Gợi ý tư duy

### Gợi ý 1

Rolling deployment tạo một khoảng thời gian nhiều application versions cùng tồn tại. Database contract phải phục vụ được cả hai nếu chúng dùng chung schema.

### Gợi ý 2

Rollback binary không thể tự undo một destructive schema change đã commit.

### Gợi ý 3

Hãy nghĩ theo expand → migrate/backfill → switch → contract, không theo một lệnh migration lớn duy nhất.

## Cấu trúc trả lời đề xuất

1. Đánh giá business impact và quyết định pause/rollback/forward-fix.
2. Dựng timeline từ deployment, instance version, DB schema và background jobs.
3. Xác định schema-version incompatibility cụ thể.
4. Stabilize bằng version còn tương thích với schema hiện tại.
5. Phân tích rollback feasibility sau destructive migration.
6. Thiết kế expand-contract migration.
7. Tách deploy code/schema/backfill thành phases có health gate.
8. Thiết kế compatibility cho background jobs.
9. Test rolling deployment với mixed versions.
10. Thêm telemetry và release guardrails.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra pipeline success không đồng nghĩa production compatibility.
- Dựng timeline theo instance version + schema version + migration step.
- Không có universal rule “DB trước” hoặc “code trước”; phụ thuộc compatibility contract.
- Destructive schema changes không nên đi cùng lúc nếu old version vẫn cần field cũ.
- Dùng backward-compatible expand-contract strategy.
- Binary rollback cần schema vẫn tương thích hoặc có forward-fix/restore plan.
- Background jobs cũng là application consumers của schema và phải tính vào compatibility matrix.
- Có deployment validation dưới mixed-version state.

### Điểm cộng

- Dùng feature flag/read-switch để chuyển dần từ old column sang new column.
- Backfill ngoài critical migration transaction nếu data volume lớn, với resumability/metrics.
- Dùng dual-write tạm thời khi requirement cho phép, nhưng có plan remove rõ ràng.
- Có schema compatibility checks trong CI/CD hoặc integration test.
- Tách destructive cleanup thành release sau khi telemetry chứng minh không còn reader cũ.

### Senior+

- Thiết kế migration như state machine có preconditions/postconditions và idempotent/re-runnable steps.
- Có expand-contract cho cả application + worker + reporting consumers.
- Định nghĩa release gate theo schema compatibility, error rate, mixed-version traffic và backfill completeness.
- Phân tích lock/log growth/transaction duration của backfill thay vì chỉ correctness.

## Hướng giải quyết tham khảo

Trong incident hiện tại, tôi không chạy thêm migration ngay. Tôi ưu tiên xác định schema thực tế và versions đang phục vụ traffic.

Tôi thu thập:

- deployment start/end từng instance;
- application version tag trong logs/telemetry;
- DB migration history và exact timestamps;
- schema state tại từng mốc;
- 500 rate theo instance/version;
- exception types;
- background job version;
- load balancer target health;
- backfill/drop duration.

Triệu chứng `v41` thiếu `LegacyStatus` sau rollback cho thấy schema đã đi qua destructive point và binary rollback không còn tương thích. Nếu `v42` trước migration lại thiếu `StatusCode`, mixed deployment tạo một cửa sổ mà cả hai version đều có lúc không tương thích.

Một strategy an toàn hơn là expand-contract qua nhiều release.

### Release A — Expand

DB thêm field mới nhưng chưa xóa field cũ:

```sql
ALTER TABLE Orders ADD StatusCode int NULL;
```

Application version trung gian vẫn đọc old field nhưng có thể bắt đầu dual-write old/new hoặc write new theo logic tương thích. Exact design tùy business semantics.

Điều quan trọng là schema sau expand vẫn chạy được với `v41` và version mới.

### Phase B — Backfill

Backfill `StatusCode` từ `LegacyStatus` theo batches có metrics/checkpoint thay vì một transaction khổng lồ nếu table lớn.

Cần kiểm tra:

- rows remaining;
- data mapping errors;
- lock duration;
- transaction log growth;
- replication/backup impact nếu có;
- rollback/resume behavior.

Backfill script nên idempotent hoặc ít nhất safely resumable.

### Release C — Switch reads

Deploy version mới có khả năng đọc `StatusCode`, nhưng trong rollout vẫn phải chịu mixed versions. Có thể dùng feature flag/read switch sau khi tất cả instances đã deploy và backfill complete.

Nếu cần dual-write trong transition, phải tránh divergence và có reconciliation. Nếu logic domain phức tạp, đôi khi tốt hơn write vào canonical field mới rồi giữ compatibility projection/triggers/application layer có kiểm soát; không áp một recipe cố định.

### Release D — Contract

Chỉ drop `LegacyStatus` khi đã chứng minh:

- không còn old application instances;
- background jobs/reporting/scripts không đọc field cũ;
- telemetry không thấy access cũ;
- rollback window cho old binaries đã đóng theo release policy;
- backup/restore plan sẵn sàng.

Destructive cleanup có thể là release riêng vài ngày/tuần sau.

`migration first` hay `code first` chỉ là shorthand. Câu hỏi đúng là: ở mỗi intermediate state, versions nào đang chạy và schema có tương thích với tất cả chúng không?

Rollback cũng phải được thiết kế trước. Với additive changes, rollback binary thường dễ hơn vì old schema contract còn tồn tại. Với destructive change, rollback có thể yêu cầu restore data hoặc forward-fix, nên cần approval và rehearsal. Không nên quảng cáo “one-click rollback” nếu database state không reversible.

Background jobs rất quan trọng. Nếu job `v41` chạy trong 20 phút trong khi web `v42` đã deploy, drop field có thể làm job fail hoặc partial process. Job phải tham gia deployment choreography hoặc dùng compatibility contract giống web app.

CI/CD nên có:

- immutable artifact/version metadata;
- migration package versioned cùng release;
- pre-deploy schema compatibility check;
- migration preconditions;
- mixed-version integration test;
- health/synthetic test sau mỗi rollout wave;
- error-rate gate;
- manual approval cho destructive migration;
- backup/restore verification theo risk.

Test production-like quan trọng nhất không chỉ là `v42` + schema mới. Phải test matrix:

```text
v41 + expanded schema
v42 + expanded schema
v41 worker + expanded schema
v42 worker + expanded schema
mixed v41/v42 behind load balancer
```

Sau khi contract step mới test state final không còn field cũ.

Observability nên tag request/job logs với application version, deployment ID và database schema/migration version để incident timeline không phải đoán.

## Mẫu trả lời trong phỏng vấn

“Em sẽ pause rollout, xác định schema state hiện tại và map 500 theo application version. Rollback package không đủ nếu migration đã drop column mà `v41` cần, nên trước hết phải chọn forward-fix hoặc restore dựa trên state thực tế.

Long-term em không dùng rule cứng DB trước hay code trước. Với rolling deployment, old/new versions coexist nên DB phải backward-compatible. Em dùng expand-contract: release đầu add `StatusCode` nhưng giữ `LegacyStatus`; backfill theo batch; deploy code mới có thể coexist; switch read sau khi data complete; chỉ drop old column ở release sau khi không còn consumer cũ và rollback window đóng.

Background jobs cũng phải nằm trong compatibility matrix. Pipeline cần test mixed versions, schema preconditions, error-rate health gate và approval cho destructive migrations. Em tag telemetry theo app version + migration version để dựng timeline nhanh khi incident xảy ra.”

## Câu hỏi đào sâu

1. Nếu table có 500 triệu rows và backfill mất nhiều giờ, bạn tổ chức backfill và read-switch thế nào để không lock hệ thống?
2. Nếu business bắt buộc rollback application trong 30 phút sau release, bạn sẽ trì hoãn contract/drop field bao lâu và quản lý technical debt đó ra sao?
3. Một DBA đề xuất wrap add + backfill + drop trong một transaction duy nhất để “atomic”; bạn phản biện thế nào với table lớn và rolling deployment?

## Lỗi trả lời thường gặp

- Chỉ nói “migration phải chạy trước code”.
- Cho rằng rollback package sẽ undo database change.
- Drop old column trong cùng release khi old instances vẫn chạy.
- Quên background jobs/reporting/scripts là schema consumers.
- Không test mixed-version state.

## Thang điểm 0–10

- **0–2:** Chỉ redeploy/restart mà không hiểu compatibility problem.
- **3–4:** Biết migration ordering nhưng dùng rule cứng.
- **5–6:** Có expand-contract và rollback reasoning cơ bản.
- **7–8:** Có phased backfill, mixed-version tests, worker compatibility và release gates.
- **9–10:** Thiết kế migration/release như state machine có measurable preconditions, reversible boundaries và operational evidence.

# Câu 3 — Thiết kế Notification Platform: synchronous REST hay Azure Service Bus, SQL hay event-driven?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Service Bus, SQL Server, distributed systems, Outbox Pattern, idempotency, retries, notification design, observability, security, architecture trade-offs

## Bối cảnh

Một SaaS personal-productivity platform cần Notification capability dùng chung cho nhiều modules như Tasks, Projects, Calendar, Documents và Security.

Yêu cầu ban đầu:

- notification có thể gửi qua In-app, Email và Browser Push;
- security-critical notification cần cố gắng gửi đủ cả 3 channels;
- user có Notification Center để mark read/unread, delete và mở resource liên quan;
- một business action như `TaskDueSoon` có thể tạo notification cho một user;
- tương lai traffic có thể tăng đáng kể nhưng hiện tại team nhỏ;
- ASP.NET Core backend chạy nhiều instances;
- SQL Server là transactional database hiện tại;
- Azure Service Bus có sẵn trong Azure subscription nhưng chưa bắt buộc phải dùng;
- email/browser-push providers là external dependencies có thể timeout hoặc rate-limit;
- user có thể disable một số loại non-critical notifications, nhưng security notification có policy riêng;
- Product muốn business transaction không bị fail chỉ vì email provider đang down.

Ba proposal đang tranh luận:

### Proposal A — Synchronous

Mỗi module gọi `NotificationService.SendAsync()` trong request và service gọi thẳng Email/Push providers trước khi trả response.

### Proposal B — Service Bus cho mọi thứ

Mỗi action publish event lên Azure Service Bus; nhiều microservices riêng xử lý từng channel.

### Proposal C — SQL notification record + background delivery

Business transaction ghi notification/outbox state trong SQL; worker đọc và gửi channels asynchronously; chỉ dùng Service Bus nếu scale/decoupling thực sự cần.

Chưa biết chắc:

- throughput peak thực tế;
- latency requirement của từng notification class;
- email/push provider SLA/rate limits;
- requirement ordering giữa notifications;
- retention/audit requirement;
- có cần cross-region hay không;
- team có đủ operational capacity cho nhiều microservices hay không.

## Câu hỏi chính

Hãy thiết kế Notification Platform phù hợp cho giai đoạn hiện tại nhưng có đường mở rộng rõ ràng. Giải thích khi nào bạn chọn synchronous call, SQL-backed background processing, Azure Service Bus hoặc tách service; đồng thời định nghĩa transaction boundary, idempotency, retry, failure handling, user preferences, observability và security.

## Câu hỏi làm rõ nên cân nhắc

1. Security notification cần “accepted for delivery”, “delivered to provider” hay “user actually received/read” trong SLA?
2. Business action có được commit nếu tạo notification record thất bại không?
3. Một logical notification gửi 3 channels có cần all-or-nothing không, hay mỗi channel có trạng thái độc lập?
4. Peak notifications/second hiện tại và projected 12–18 tháng là bao nhiêu?
5. User preference được snapshot tại thời điểm event hay evaluate tại delivery time?

## Gợi ý tư duy

### Gợi ý 1

Tách “business transaction succeeded” khỏi “external provider delivered notification”.

### Gợi ý 2

Retry external delivery tạo nguy cơ duplicate; mỗi channel cần idempotency/deduplication strategy riêng.

### Gợi ý 3

Service Bus và microservices có thể hữu ích, nhưng nếu current scale/team chưa cần thì SQL outbox + worker có thể đơn giản hơn và vẫn đúng.

## Cấu trúc trả lời đề xuất

1. Phân loại notification classes và SLA.
2. Xác định source-of-truth và data model.
3. Định nghĩa transaction boundary với business modules.
4. Chọn delivery architecture theo current scale.
5. Thiết kế worker/queue/idempotency.
6. Tách channel state và retry policy.
7. Xử lý provider outage/rate limits.
8. Thiết kế preferences/security policies.
9. Thiết kế observability/audit/recovery.
10. Nêu trigger rõ khi nào cần Service Bus/service extraction.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không để email/push external call nằm trong critical business transaction nếu Product không yêu cầu synchronous delivery.
- Có durable notification record/tracking state.
- Có transaction-safe way để tránh business commit nhưng notification intent bị mất khi notification bắt buộc.
- Retry bounded, có backoff và phân loại transient/permanent failures.
- Delivery phải idempotent/deduplicated ở logical notification/channel level.
- Mỗi channel có trạng thái riêng thay vì coi 3-channel send là một boolean.
- User preferences không được phép disable security notification nếu policy không cho phép.
- Có audit/telemetry nhưng không log secret/token/sensitive payload tùy tiện.
- Không mặc định tách nhiều microservices nếu team/scale chưa justify.

### Điểm cộng

- Dùng Outbox Pattern khi notification intent phát sinh cùng SQL transaction với business change.
- Dùng unique key như `(NotificationId, Channel)` để chặn duplicate local delivery attempts.
- Có DLQ/failure table/manual retry tooling cho permanent hoặc exhausted failures.
- Có per-provider circuit breaker/rate-limit awareness và queue/backlog isolation.
- Notification Center đọc từ durable store độc lập với external delivery success.

### Senior+

- Phân biệt notification event/intention với delivery attempts và provider receipts.
- Thiết kế at-least-once pipeline nhưng exactly-once business effect không được assume.
- Nếu dùng Service Bus, hiểu Peek Lock có thể redeliver; duplicate detection phía send không thay idempotent consumer.
- Đưa ra criteria cụ thể để chuyển từ SQL worker sang Service Bus: throughput, independent scaling, backlog isolation, cross-service producers, operational need.
- Có SLO theo class như enqueue latency, delivery latency, failure rate, queue age, nhưng không tự bịa số khi Product chưa cung cấp.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng classification, vì không phải mọi notification có cùng semantics.

Ví dụ conceptual:

- `SecurityCritical`: password/security/support/emergency events;
- `Transactional`: task reminder, document shared, billing-like event;
- `Informational`: product tips/general updates.

Mỗi class có policy về channels, preference override, retry và retention.

Tôi tách data model thành ít nhất:

```text
Notification
- Id
- UserId
- Type
- ResourceType
- ResourceId
- CreatedAt
- ReadAt
- DeletedAt
- PolicyClass

NotificationDelivery
- NotificationId
- Channel
- Status
- AttemptCount
- NextAttemptAt
- ProviderReference
- LastErrorCode
- DeliveredAt
```

Notification Center đọc `Notification`; delivery state của Email/Push/In-app là concerns riêng.

### Transaction boundary

Nếu một Task transaction commit và requirement nói reminder intent không được mất, tôi không làm:

```text
UPDATE Task
COMMIT
call Notification API
```

vì process có thể crash giữa commit và external call.

Nếu Task và notification/outbox dùng cùng SQL database/boundary, solution đơn giản là ghi business change + notification intent/outbox record trong cùng DB transaction:

```text
BEGIN TRANSACTION
  update Task
  insert Notification
  insert OutboxMessage/DeliveryWork
COMMIT
```

Worker sau đó xử lý delivery asynchronously. Đây tránh dual-write gap trong cùng database boundary.

Nếu modules sau này tách database/service, transaction boundary thay đổi; lúc đó mỗi producer có local outbox rồi publish integration event.

### Current-stage architecture

Với team nhỏ và throughput chưa chứng minh cao, tôi có thể bắt đầu bằng SQL-backed worker trong cùng deployable application hoặc worker process riêng:

```text
Business transaction
      ↓
Notification + Outbox rows
      ↓
Background worker claims batches
      ↓
Email / Browser Push / In-app delivery
```

Ưu điểm:

- ít infrastructure hơn;
- transaction consistency đơn giản;
- dễ query Notification Center/audit;
- deployment/observability footprint nhỏ.

Trade-off:

- polling/claiming logic cần đúng;
- SQL có thêm queue-like workload;
- scale rất lớn hoặc nhiều producers độc lập có thể cần broker.

Worker phải claim rows concurrency-safe. Có thể dùng database locking/lease/status transition pattern phù hợp SQL Server, nhưng exact SQL cần benchmark và tránh hot polling. Không giữ một transaction mở trong lúc gọi external provider.

Flow tốt hơn:

1. transaction ngắn claim một batch và mark ownership/processing lease;
2. commit;
3. gọi provider ngoài transaction;
4. persist result;
5. retry/recover nếu worker crash.

Vì crash có thể xảy ra sau provider accepted nhưng trước local DB update, delivery phải idempotent nếu provider hỗ trợ idempotency key. Nếu provider không hỗ trợ, local dedupe chỉ giảm duplicate attempts chứ không loại bỏ ambiguous external outcome; có thể cần provider reference/reconciliation.

### Khi dùng Azure Service Bus

Service Bus có giá trị khi:

- nhiều independent producers cần publish notification events;
- worker/channel cần independent scaling;
- backlog isolation quan trọng;
- spike smoothing cần broker;
- team đã có operational maturity cho queue/DLQ/monitoring;
- notification trở thành shared platform boundary thực sự.

Khi đó architecture có thể là:

```text
Producer local transaction
  ↓
Outbox
  ↓
Publisher
  ↓
Service Bus
  ↓
Notification consumer
  ↓
Notification store + channel work
```

Hoặc notification platform nhận event rồi fan-out channel work. Nhưng tôi không nhất thiết tạo 3 microservices chỉ vì có 3 channels. Có thể một service/module với separate handlers/queues nếu scale tương tự.

Microsoft Learn hiện mô tả Peek Lock là at-least-once: nếu consumer không settle trước lock expiry/crash/network failure, message có thể được redeliver. Vì vậy consumer phải idempotent. Duplicate detection ở sender-side giúp duplicate sends trong detection window nhưng không thay idempotency ở receiver.

### Retry/failure

Mỗi delivery channel có retry policy riêng:

- timeout/429/transient 5xx: bounded exponential backoff theo provider guidance;
- invalid email/device token: permanent failure hoặc disable endpoint sau policy;
- authentication/config failure: không retry loop nhanh; alert operationally;
- exhausted attempts: failed/dead-letter state + manual/automatic recovery policy.

Security-critical notification có thể yêu cầu stronger escalation khi một channel fail, nhưng “all 3 providers must succeed atomically” thường không thực tế vì external systems không nằm trong distributed transaction. Tôi lưu status từng channel và có policy/alert nếu chưa đạt delivery objective.

### In-app

In-app notification thường được tạo durable ngay khi transaction commit, nên Notification Center có thể hiển thị dù email provider down. Browser Push/Email là delivery projections của cùng logical notification.

### Preferences

Preference evaluation cần defined semantics. Với non-critical type, worker kiểm tra preference snapshot/current policy tùy requirement. Với security-critical type, server-side policy override; không tin client flag để bỏ mandatory notification.

### Security

- không nhét secrets vào notification payload;
- provider credentials ở Key Vault/Managed Identity where supported;
- validate resource authorization khi user click notification;
- notification chứa resource ID không có nghĩa user còn quyền xem resource;
- không log full sensitive content/token;
- audit preference change và security delivery events khi required.

### Observability

Theo dõi:

- notification intents created/sec;
- oldest pending age;
- attempts/success/failure theo channel/provider;
- delivery latency p50/p95/p99;
- retry count;
- permanent failure rate;
- worker lease/recovery count;
- Service Bus queue depth/DLQ nếu dùng;
- provider latency/429/5xx;
- correlation từ business event → notification → channel delivery.

### Testing

- transaction rollback không tạo orphan notification;
- crash sau claim trước provider call;
- crash sau provider success trước DB update;
- duplicate outbox/message delivery;
- provider timeout/429/5xx;
- invalid device token/email;
- preference change race;
- multiple app instances processing same work;
- Service Bus redelivery nếu architecture có broker;
- security-critical policy cannot be disabled by normal preference.

Tôi sẽ bắt đầu modular/SQL-backed nếu current requirements đủ, rồi extract broker/service khi metrics cho thấy queue throughput, producer count, independent scaling hoặc isolation justify complexity. Architecture tốt không phải architecture có nhiều distributed components nhất; là architecture đáp ứng delivery semantics với chi phí vận hành hợp lý.

## Mẫu trả lời trong phỏng vấn

“Em tách business commit khỏi external delivery. Notification Center cần durable record, còn Email/Browser Push là delivery attempts có status riêng. Nếu Task update và notification intent phải cùng thành công, em ghi business change + notification/outbox trong cùng SQL transaction, rồi worker xử lý asynchronously.

Với current team nhỏ và throughput chưa rõ, em chưa tách ngay thành nhiều microservices. SQL-backed worker hoặc một notification module/worker có thể đủ, miễn claim work concurrency-safe, transaction ngắn và retry/idempotency đúng. Nếu sau này nhiều producers, backlog lớn hoặc channels cần scale/isolate độc lập, em đưa Service Bus vào.

Nếu dùng Service Bus, em vẫn coi delivery là at-least-once và consumer phải idempotent; duplicate detection phía sender không thay điều đó. Mỗi `(NotificationId, Channel)` có trạng thái/attempt riêng. External timeout cần bounded retry và nếu provider có idempotency key thì dùng stable key.

Security notifications có policy server-side, không bị preference thường tắt. Em monitor oldest pending age, delivery latency, retry/failure và provider health; click notification vẫn phải authorize resource tại thời điểm truy cập.”

## Câu hỏi đào sâu

1. Nếu email provider nhận request thành công nhưng client timeout trước khi nhận response, bạn làm gì để tránh gửi duplicate email khi retry?
2. Nếu SQL notification worker xử lý 500 notifications/second ổn định nhưng một campaign tạo spike 1 triệu notifications, tiêu chí nào khiến bạn thêm Service Bus?
3. Một architect nói “mỗi channel phải là một microservice để đúng microservice architecture”; bạn phản biện dựa trên ownership, scale và failure isolation thế nào?

## Lỗi trả lời thường gặp

- Gửi email/push synchronously trong business transaction theo mặc định.
- Cho rằng Service Bus tạo exactly-once delivery tự động.
- Retry external sends vô hạn.
- Dùng một boolean `Sent=true` cho cả 3 channels.
- Tách microservices trước khi có scale/ownership requirement rõ.

## Thang điểm 0–10

- **0–2:** Chỉ chọn Service Bus hoặc Redis/queue theo buzzword.
- **3–4:** Có async worker nhưng thiếu transaction/idempotency/failure model.
- **5–6:** Có durable notification, outbox, channel state, retries và observability.
- **7–8:** Có transition criteria SQL→broker, failure recovery, security policy và multi-instance concurrency.
- **9–10:** Thiết kế rõ delivery semantics, business consistency, operational cost và nêu điều kiện làm architecture thay đổi.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Async request order không phải response order:** Promise/fetch completions có thể đảo thứ tự; UI phải có explicit latest-result policy.
- **Debounce không phải concurrency control:** giảm request count không loại bỏ stale-response race.
- **Rolling deployment là mixed-version system:** database schema phải tương thích với các application/worker versions đang coexist.
- **Database migration an toàn thường là expand → backfill → switch → contract:** destructive cleanup nên tách khỏi thời điểm old consumers còn sống.
- **Notification delivery là distributed side effect:** business commit, notification intent và provider delivery là các boundaries khác nhau.
- **At-least-once cần idempotency:** queue/broker giúp durability và decoupling nhưng không tự động loại bỏ duplicate business effects.

## Mẫu tư duy cần nhớ

1. **Make ordering rules explicit instead of relying on timing.**
2. **Design intermediate deployment states, not only final state.**
3. **Preserve rollback compatibility before destructive cleanup.**
4. **Separate durable intent from external side effects.**
5. **Add distributed infrastructure only when scale, ownership or failure isolation pays for it.**
