# Câu 1 — ASP.NET Core Response Compression: vì sao Brotli làm tăng CPU nhưng p95 không cải thiện?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core middleware, HTTP content negotiation, CPU profiling, CDN

## Bối cảnh

API .NET 8 trả JSON 1.5 MB, được bật Brotli/Gzip trên Azure App Service sau Akamai. Bandwidth giảm 60% nhưng CPU tăng và p95 từ 180 ms lên 340 ms. Một số request trả Content-Encoding: br, một số không. Chưa rõ payload có chứa dữ liệu nhạy cảm, cache key và Accept-Encoding ra sao.

## Câu hỏi chính

Giải thích cơ chế negotiation, compression và buffering/streaming; tìm bằng chứng vì sao p95 tăng, xác định trường hợp nên nén tại origin, CDN hoặc không nén.

## Câu hỏi làm rõ nên cân nhắc

1. Payload nào đã được nén sẵn và loại content nào chiếm traffic?
2. Response có chứa secrets hoặc nội dung nhạy cảm trong cùng compression context không?
3. CPU, network egress, p95/p99 phân bố theo payload size và Accept-Encoding?
4. Akamai có nén ở edge và có tách cache variants theo encoding không?

## Gợi ý tư duy

### Gợi ý 1

Băng thông giảm không đồng nghĩa end-to-end latency giảm.

### Gợi ý 2

Đo CPU time compression, payload size, transfer time và queueing.

### Gợi ý 3

Kiểm tra middleware order, MIME types, Vary: Accept-Encoding và trường hợp streaming.

## Cấu trúc trả lời đề xuất

1. Làm rõ yêu cầu và giả định chưa biết.
2. Phân tích cơ chế, boundary và tác động production.
3. Thu thập bằng chứng để phân biệt các giả thuyết/phương án.
4. Đề xuất giải pháp có điều kiện, nêu trade-offs và failure paths.
5. Thiết kế kiểm thử, telemetry, rollout và rollback phù hợp.

## Ý chính của câu trả lời tốt

### Bắt buộc

Hiểu Accept-Encoding/Content-Encoding và Vary; phân biệt CPU-bound compression với network-bound transfer; đo latency theo phase.

### Điểm cộng

Thử compression level, response size threshold và edge compression; kiểm tra cache variants và nội dung nhạy cảm.

### Senior+

Làm controlled experiment theo payload distribution và capacity, cân nhắc compression side-channel trong ngữ cảnh thích hợp.

## Hướng giải quyết tham khảo

Browser gửi Accept-Encoding để khai báo các encoding chấp nhận. Server/CDN chọn representation nén tương ứng và trả Content-Encoding; shared cache cần phân biệt variants, thường qua Vary: Accept-Encoding hoặc CDN cache-key policy. Nén tiêu tốn CPU; khi network nhanh hoặc CPU saturation, tổng thời gian tăng dù bytes giảm. Một số response không nén do MIME, size, streaming, request header hoặc policy CDN. Không nén file đã compressed như JPEG/ZIP; đánh giá streaming và buffering trên endpoint lớn. Điều tra bằng trace request duration, CPU profiler, bytes in/out, CDN cache hit và edge/origin transfer. Chạy A/B compression level theo payload buckets, quan sát p50/p95/p99, CPU và cost; tránh kết luận từ bandwidth đơn lẻ. Với dữ liệu nhạy cảm trộn cùng attacker-controlled input, xem xét compression side-channel; không bật response compression cho các endpoint rủi ro chỉ vì hiệu năng. Nếu edge đã nén hiệu quả và origin CPU hạn chế, chuyển compression về CDN có thể hợp lý, nhưng phải kiểm chứng cache semantics và khả năng CDN.

**Kiểm thử có giá trị:** Thiết kế một integration test cho hành vi chính, một failure-path test, một load/concurrency hoặc release validation test, và một regression test cho tình huống gây lỗi. Xác minh qua traces, structured logs không chứa secrets, metrics theo phiên bản release và cảnh báo gắn với tác động người dùng. Các số liệu trong bối cảnh là giả định; phải kiểm chứng trên môi trường thực tế trước khi quyết định.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không coi bandwidth giảm là thành công nếu p95 tăng. Em tách latency thành serialization, compression CPU, queueing và transfer, rồi đối chiếu theo payload size và encoding. Accept-Encoding là negotiation, Content-Encoding là encoding thực tế; Vary/cache key cần bảo đảm các variant đúng. Em sẽ profile CPU và so sánh A/B các mức compression hoặc edge compression. Nếu bottleneck ở CPU, giảm mức nén hoặc chỉ nén payload lớn; nếu ở network, nén vẫn có lợi. Đồng thời kiểm tra các response chứa dữ liệu nhạy cảm và không nén dữ liệu đã compressed. Quyết định cuối dựa trên p95, capacity và chi phí chứ không chỉ tỷ lệ nén.”

## Câu hỏi đào sâu

1. Nếu CDN trả cached Brotli cho client không hỗ trợ br, bạn điều tra cache key thế nào?
2. Nếu CPU tăng nhưng p95 cải thiện ở mạng di động, bạn chọn policy nào?
3. Nếu JSON chứa token nhạy cảm cạnh input do attacker kiểm soát, bạn đánh giá rủi ro gì?

## Lỗi trả lời thường gặp

- Bật Brotli maximum cho mọi endpoint.
- Đồng nhất bytes transferred với latency.
- Không kiểm tra Vary/cache variants.
- Bỏ qua CPU saturation và dữ liệu nhạy cảm.

## Thang điểm 0–10

- **0–2:** Không nắm cơ chế hoặc bỏ qua impact.
- **3–4:** Có một giải pháp nhưng thiếu bằng chứng và điều kiện.
- **5–6:** Phân tích hợp lý, còn thiếu failure paths hoặc trade-offs.
- **7–8:** Có nhiều giả thuyết/phương án, test, monitoring và rollout.
- **9–10:** Quyết định có điều kiện, evidence-driven, an toàn production và giao tiếp rõ.
- **Rubric:** requirement clarification 1; technical correctness 2; depth 2; debugging/reasoning 2; trade-offs 1; production readiness 1; communication 1.

# Câu 2 — Elasticsearch reindex sau release làm search mất kết quả từng đợt

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Elasticsearch aliases, indexing, search consistency, observability

## Bối cảnh

Website catalog có 4 triệu sản phẩm; SQL Server là source of truth, Elasticsearch là read model. Sau release thay analyzer, tìm kiếm mất 10–20% sản phẩm trong 40 phút. API vẫn trả 200, indexing worker báo thành công; Kibana cho thấy search p95 tăng và số document trong index mới thấp hơn cũ. Có nhiều worker instances và một batch import đang chạy.

## Câu hỏi chính

Điều phối incident, xác định nguyên nhân với bằng chứng, khôi phục search và thiết kế reindex/cutover an toàn khi mapping/analyzer thay đổi.

## Câu hỏi làm rõ nên cân nhắc

1. Alias hiện trỏ tới index nào và thay đổi lúc nào?
2. Có dual indexing, event backlog hoặc document versioning không?
3. Reindex có snapshot/high-water mark và kiểm tra completeness trước swap không?
4. Có thể rollback alias mà không làm mất updates mới không?

## Gợi ý tư duy

### Gợi ý 1

200 không chứng minh search correctness.

### Gợi ý 2

Phân biệt ingestion success với index refresh/visibility và completeness.

### Gợi ý 3

Xem alias cutover, concurrent writes, mapping, analyzer và reconciliation.

## Cấu trúc trả lời đề xuất

1. Làm rõ yêu cầu và giả định chưa biết.
2. Phân tích cơ chế, boundary và tác động production.
3. Thu thập bằng chứng để phân biệt các giả thuyết/phương án.
4. Đề xuất giải pháp có điều kiện, nêu trade-offs và failure paths.
5. Thiết kế kiểm thử, telemetry, rollout và rollback phù hợp.

## Ý chính của câu trả lời tốt

### Bắt buộc

Stabilize impact, kiểm tra alias, index counts và query samples; không kết luận một root cause khi chưa đo.

### Điểm cộng

Dùng versioned index, atomic alias switch, catch-up delta và parity validation.

### Senior+

Thiết kế rollback khi new writes phát sinh, reconciliation, freshness SLO và release gates.

## Hướng giải quyết tham khảo

Trước tiên xác nhận phạm vi bằng query samples, search success rate, conversion, index document count và alias state. Nếu index cũ còn đầy đủ, cân nhắc rollback alias để giảm tác động; cần đánh giá updates phát sinh sau cutover và replay chúng, tránh mất dữ liệu mới. Các giả thuyết gồm alias swap trước khi backfill hoàn tất, worker bỏ sót records do pagination/checkpoint, analyzer làm tokenization khác, refresh chưa phản ánh writes, hoặc pipeline retry làm mất updates. Đối chiếu SQL product IDs với index IDs theo partition và sample queries; kiểm tra failed bulk items (HTTP batch success không có nghĩa từng item thành công), worker checkpoints, queue lag, mapping/analyzer và query DSL. Quy trình an toàn: tạo index version mới, backfill theo snapshot/high-water mark, ghi delta qua durable event/outbox hoặc change capture, validate counts và representative queries, catch up delta, atomic alias swap, tiếp tục quan sát và giữ index cũ đủ lâu để rollback. Nếu business yêu cầu near-real-time, định nghĩa freshness SLA và alert backlog. Test bulk partial failures, worker crash/restart, concurrent updates, alias cutover và analyzer regression. Telemetry gồm per-item indexing failures, backlog age, index count parity, p95 search, zero-result rate và product search availability. Không coi index document count bằng nhau là đủ vì mappings/query behavior cũng phải kiểm tra.

**Kiểm thử có giá trị:** Thiết kế một integration test cho hành vi chính, một failure-path test, một load/concurrency hoặc release validation test, và một regression test cho tình huống gây lỗi. Xác minh qua traces, structured logs không chứa secrets, metrics theo phiên bản release và cảnh báo gắn với tác động người dùng. Các số liệu trong bối cảnh là giả định; phải kiểm chứng trên môi trường thực tế trước khi quyết định.

## Mẫu trả lời trong phỏng vấn

“Em sẽ coi đây là incident correctness dù HTTP vẫn 200. Đầu tiên em đo số sản phẩm bị mất và khả năng rollback alias về index cũ, đồng thời đánh giá delta updates để không mất dữ liệu. Sau đó em so sánh alias state, document IDs với SQL, bulk item errors, worker checkpoint và analyzer/query behavior. Em không giả định chỉ do refresh; việc index mới thiếu document gợi ý backfill hoặc cutover chưa hoàn tất. Về dài hạn em dùng versioned index, backfill theo snapshot, catch-up delta, validation trước atomic alias swap và giữ rollback window. Alert cần đo zero-result rate, index parity và backlog age chứ không chỉ API 5xx.”

## Câu hỏi đào sâu

1. Nếu index cũ không có 20 phút cập nhật mới, rollback có an toàn không?
2. Nếu counts bằng nhau nhưng search vẫn mất kết quả, bạn kiểm tra gì?
3. Nếu bulk API trả HTTP 200 nhưng có item errors, worker phải xử lý thế nào?

## Lỗi trả lời thường gặp

- Chỉ restart Elasticsearch.
- Coi HTTP 200 là search thành công.
- Swap alias trước validation.
- Bỏ qua updates xảy ra trong reindex.

- **3–4:** Có một giải pháp nhưng thiếu bằng chứng và điều kiện.
- **5–6:** Phân tích hợp lý, còn thiếu failure paths hoặc trade-offs.
- **7–8:** Có nhiều giả thuyết/phương án, test, monitoring và rollout.

# Câu 3 — Thiết kế migration pipeline TeamCity → Jenkins/Octopus Deploy cho ứng dụng IIS mà không gián đoạn release

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** CI/CD, IIS, Windows Server, release safety, artifact provenance

## Bối cảnh

Doanh nghiệp có ASP.NET MVC .NET Framework 4.5 trên IIS và ASP.NET Core 8 API trên Azure App Service. TeamCity build, Octopus Deploy release, Azure Repos lưu source. Do license/cost, công ty cân nhắc Jenkins cho CI; vẫn phải deploy được hotfix trong 15 phút, audit mỗi artifact, rollback an toàn và không lưu secrets trong pipeline. 8 services, 3 environments, schema SQL Server dùng chung ở giai đoạn chuyển tiếp.

## Câu hỏi chính

## Câu hỏi làm rõ nên cân nhắc

1. Pain point thực tế là license, reliability hay deployment lead time?
2. Hiện artifacts có immutable/versioned và promoted qua environments không?
3. Có database migrations backward compatible và rollback scripts không?
4. Hotfix approval, segregation of duties và audit requirements cụ thể là gì?

## Gợi ý tư duy

### Gợi ý 1

Không nhầm CI engine với deployment orchestration.

### Gợi ý 2

### Senior+

## Hướng giải quyết tham khảo

Nếu chọn Jenkins, chạy shadow CI cho một service, so sánh tests, build output, SBOM/dependency scanning và artifact checksum với TeamCity. Dùng build-once/promote-same-artifact qua dev/staging/prod, có provenance, signed hoặc integrity-checked artifacts và approval gates. Octopus có thể tiếp tục làm deployment orchestration cho IIS/App Service nếu release lifecycle và variable scoping đã tốt; không cần thay tất cả tools cùng lúc. Secrets nằm trong credential store/Key Vault, agents least privilege, không in secrets vào logs, phân quyền deploy theo environment. IIS rollout cần health checks, app pool startup validation, backup cấu hình và rollback binary; App Service dùng deployment slots khi phù hợp. SQL shared schema phải theo expand/contract để code cũ và mới cùng chạy; rollback binary không cứu được destructive migration. CI/CD contract tests, integration tests, Playwright smoke tests và deployment smoke checks là gates; hotfix có expedited approval nhưng vẫn audit. Migrate service-by-service, giữ TeamCity fallback trong transition, rehearsal rollback, metrics deployment failure, lead time, MTTR và change failure rate. Nếu yêu cầu chỉ là giảm cost, so sánh TCO Jenkins agents/plugins/security patching với license TeamCity và chi phí support Octopus; tránh migration chỉ vì công cụ mới.
