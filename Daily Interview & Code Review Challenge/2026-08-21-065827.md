# Code Review Challenge 1 — Consumer xử lý thanh toán bị chạy trùng khi RabbitMQ redelivery

**Chủ đề:** Idempotency, concurrency, EF Core transaction, message processing  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7 vấn đề

## Bối cảnh

Một service .NET nhận message `PaymentCaptured` từ RabbitMQ để đánh dấu invoice đã thanh toán và enqueue Hangfire job gửi email. Hệ thống chạy 4 instance, mỗi instance có nhiều consumer. Khi broker redeliver message sau timeout/network failure, production thỉnh thoảng ghi nhận email gửi hai lần, `PaidAt` bị cập nhật lại và một số message được retry liên tục. Yêu cầu nghiệp vụ là một payment event chỉ tạo ra một business effect, nhưng broker vẫn được phép redeliver.

## Đoạn code cần review

```csharp
public sealed class PaymentCapturedConsumer
{
    private readonly BillingDbContext _db;
    private readonly IBackgroundJobClient _jobs;
    private readonly ILogger<PaymentCapturedConsumer> _logger;

    public PaymentCapturedConsumer(
        BillingDbContext db,
        IBackgroundJobClient jobs,
        ILogger<PaymentCapturedConsumer> logger)
    {
        _db = db;
        _jobs = jobs;
        _logger = logger;
    }

    public async Task HandleAsync(PaymentCaptured message)
    {
        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId);

        if (alreadyProcessed)
            return;

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId);

        invoice.Status = InvoiceStatus.Paid;
        invoice.PaidAt = DateTime.UtcNow;

        _jobs.Enqueue<InvoiceEmailJob>(x =>
            x.SendPaidEmail(message.InvoiceId));

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Processed payment {MessageId} for invoice {InvoiceId}",
            message.MessageId,
            message.InvoiceId);
    }
}
```

2. Tìm rủi ro concurrency, reliability và performance.
3. Giải thích tác động production.
4. Ưu tiên vấn đề theo mức độ nghiêm trọng.
5. Đề xuất implementation đã sửa.

## Câu hỏi gợi mở

- Hai consumer có thể cùng đọc `alreadyProcessed == false` không?
- Việc enqueue Hangfire job và commit database có cùng atomic boundary không?
- Điều gì xảy ra nếu process crash sau enqueue nhưng trước `SaveChangesAsync`?
- Unique constraint có vai trò gì nếu application đã kiểm tra bằng `AnyAsync`?
- Nếu handler bị cancel giữa chừng, trạng thái nào có thể còn lại?

## Gợi ý

### Gợi ý 1

### Gợi ý 2

Có hai hệ thống durable độc lập: database và Hangfire storage. Hãy tìm failure window giữa chúng.

## Kết quả code review tham khảo

### 1. Check-then-act không đảm bảo idempotency

- **Problem:** `AnyAsync` rồi mới insert `ProcessedMessage`.
- **Why:** Hai consumer đồng thời có thể cùng quan sát “chưa tồn tại”.
- **Production impact:** Cả hai cùng cập nhật invoice và enqueue email.
- **Severity:** Critical.
- **Recommended fix:** Enforce unique constraint/index trên `MessageId`; coi database là authority và xử lý unique-key conflict đúng cách.

### 2. Database commit và Hangfire enqueue không atomic

- **Problem:** Job được enqueue trước khi `SaveChangesAsync` commit.
- **Why:** Hai durable stores không nằm trong cùng transaction boundary một cách mặc định.
- **Production impact:** Crash sau enqueue nhưng trước commit có thể tạo email dù payment chưa được commit; redelivery có thể enqueue lần nữa.
- **Severity:** Critical.
- **Recommended fix:** Dùng transactional outbox: commit invoice, processed-message và outbox record trong cùng DB transaction; dispatcher riêng enqueue/send từ outbox theo cơ chế idempotent.

### 3. Side effect downstream chưa có idempotency key

- **Problem:** Email job chỉ nhận `InvoiceId`.
- **Why:** Retry của outbox/Hangfire vẫn có thể thực thi job nhiều lần.
- **Production impact:** Duplicate email dù consumer chính đã an toàn hơn.
- **Severity:** High.
- **Recommended fix:** Truyền stable event/outbox ID và deduplicate tại consumer/job hoặc thiết kế operation downstream idempotent.

### 4. Không kiểm tra state transition của invoice

- **Problem:** Luôn ghi `Paid` và reset `PaidAt`.
- **Why:** Event duplicate hoặc out-of-order có thể ghi đè state hợp lệ.
- **Production impact:** Audit timestamp sai; có thể phá workflow nếu invoice đã refund/cancel tùy business rule.
- **Severity:** High.
- **Recommended fix:** Validate transition theo business invariant; chỉ chuyển state hợp lệ và giữ timestamp gốc khi duplicate.

### 5. Thiếu transaction rõ ràng cho business invariant nhiều record

- **Problem:** Invoice update và processed marker phụ thuộc cùng một invariant nhưng intent chưa được biểu diễn rõ.
- **Why:** `SaveChanges` thường transaction hóa một lần save, nhưng thiết kế cần bảo đảm toàn bộ database mutation liên quan nằm trong cùng atomic commit, đặc biệt khi logic mở rộng.
- **Production impact:** Future refactor dễ tạo partial state.
- **Severity:** Medium.
- **Recommended fix:** Giữ mutations trong một unit-of-work/transaction boundary rõ ràng; outbox cùng transaction.

### 6. Không truyền `CancellationToken`

- **Problem:** EF calls không nhận cancellation token.
- **Why:** Shutdown/cancel không được propagate xuống database operations.
- **Production impact:** Slow shutdown, wasted DB work, khó kiểm soát failure path.
- **Severity:** Medium.
- **Recommended fix:** Nhận token từ consumer framework và truyền vào EF APIs.

### 7. Observability thiếu attempt/delivery context

- **Problem:** Log chỉ ghi message và invoice IDs.
- **Why:** Không phân biệt first delivery, duplicate, conflict, retry hay outbox dispatch.
- **Production impact:** Khó chứng minh nguyên nhân duplicate và đo effectiveness của idempotency.
- **Severity:** Medium.
- **Recommended fix:** Structured logs/metrics cho message ID, delivery attempt, duplicate count, unique conflicts, processing latency và outbox lag.

## Phiên bản code đề xuất

```csharp
public sealed class PaymentCapturedConsumer
{
    private readonly BillingDbContext _db;
    private readonly ILogger<PaymentCapturedConsumer> _logger;

    public PaymentCapturedConsumer(
        BillingDbContext db,
        ILogger<PaymentCapturedConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        PaymentCaptured message,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId, cancellationToken);

        var duplicate = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId, cancellationToken);

        if (duplicate)
        {
            await tx.RollbackAsync(cancellationToken);
            return;
        }

        if (invoice.Status != InvoiceStatus.Paid)
        {
            invoice.Status = InvoiceStatus.Paid;
            invoice.PaidAt ??= DateTime.UtcNow;
        }

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "InvoicePaidEmail",
            AggregateId = message.InvoiceId.ToString(),
            IdempotencyKey = message.MessageId,
            CreatedAt = DateTime.UtcNow
        });

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsUniqueMessageIdViolation(ex))
        {
            await tx.RollbackAsync(cancellationToken);
            _logger.LogInformation(
                "Duplicate payment message ignored: {MessageId}",
                message.MessageId);
            return;
        }
    }

    private static bool IsUniqueMessageIdViolation(DbUpdateException ex)
    {
        // Implement provider-specific detection for SQL Server/PostgreSQL.
        return ex.InnerException is not null;
    }
}
```

Database phải có unique constraint/index trên `ProcessedMessages.MessageId`. Hàm nhận diện unique violation ở ví dụ trên chỉ là placeholder: production code phải kiểm tra error code cụ thể của provider, không được coi mọi `DbUpdateException` là duplicate. Outbox dispatcher xử lý riêng và phải retry an toàn.

## Trade-offs

Transactional outbox tăng schema, worker, cleanup và operational complexity nhưng loại bỏ critical dual-write window. Nếu side effect nằm cùng database thì transaction đơn giản có thể đủ. Nếu throughput rất cao, có thể tối ưu dedup bằng insert-first thay vì `AnyAsync`, nhưng unique constraint vẫn là invariant cuối cùng. Exactly-once delivery end-to-end thường không nên giả định; mục tiêu thực tế là at-least-once transport cộng idempotent effects.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 20 handler đồng thời với cùng `MessageId`; chỉ một processed record và một outbox record được commit.
2. **Failure-path test:** crash/fault sau DB commit nhưng trước dispatch; outbox vẫn được dispatch sau restart.
3. **Retry test:** dispatcher xử lý cùng outbox message nhiều lần; email sink deduplicate bằng stable key.
4. **State-transition test:** duplicate/out-of-order event không reset `PaidAt` hoặc phá trạng thái terminal khác.
5. **Database test:** xác minh unique constraint hoạt động trên cả provider production đang dùng.

## Quan sát trong production

Theo dõi `message_processing_duration`, duplicate/unique-conflict count, redelivery count, outbox pending count và oldest-outbox age. Correlate trace theo `MessageId`, `InvoiceId`, `OutboxId`; alert khi outbox lag tăng, retry storm xuất hiện hoặc duplicate rate tăng bất thường. Log không nên chứa dữ liệu thanh toán nhạy cảm ngoài identifier cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Tại sao unique constraint vẫn cần dù code đã query duplicate trước?
2. Nếu Hangfire và application DB dùng cùng SQL Server, bạn có chọn distributed transaction thay cho outbox không? Vì sao?
3. Làm thế nào xử lý event cùng invoice nhưng khác `MessageId` đến sai thứ tự?

# Code Review Challenge 2 — API tìm kiếm audit log vừa chậm vừa có nguy cơ lộ dữ liệu

**Chủ đề:** Authorization, SQL/EF Core query execution, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép nhân viên hỗ trợ tìm audit logs theo tenant. Sau khi dữ liệu tăng lên hàng triệu rows, endpoint có latency cao và memory spike. Security review cũng phát hiện khả năng người dùng support của tenant A truy cập log tenant B nếu biết `tenantId`. Một số log chứa email, access-token fragments và request payload.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        Guid tenantId,
        string? text,
        DateTime? from,
        DateTime? to)
    {
        _logger.LogInformation(
            "Audit search tenant={TenantId}, text={Text}", tenantId, text);

        var rows = await _db.AuditLogs
            .Where(x => x.TenantId == tenantId)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(text))
        {
            rows = rows
                .Where(x => x.RequestBody.Contains(text) ||
                            x.UserEmail.Contains(text))
                .ToList();
        }

        if (from.HasValue)
            rows = rows.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            rows = rows.Where(x => x.CreatedAt <= to.Value).ToList();

        return Ok(rows.OrderByDescending(x => x.CreatedAt));
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization

- **Problem:** Caller tự cung cấp `tenantId`; code chỉ yêu cầu authenticated user.
- **Why:** Không có policy/claim/resource authorization chứng minh caller thuộc hoặc được phép xem tenant đó.
- **Production impact:** Cross-tenant data exposure.
- **Severity:** Critical.
- **Recommended fix:** Resolve allowed tenant từ trusted identity/authorization layer hoặc authorize requested tenant bằng policy/resource-based authorization; deny by default.

### 2. Trả nguyên audit entity có thể lộ dữ liệu nhạy cảm

- **Problem:** `return Ok(rows...)` serialize toàn entity.
- **Why:** Audit record có thể chứa request body, token fragments hoặc internal fields.
- **Production impact:** Credential/PII leakage và tăng blast radius của endpoint.
- **Severity:** Critical.
- **Recommended fix:** Projection sang DTO allowlist; redact/mask sensitive fields; tuyệt đối không lưu secret/token raw nếu không cần.

### 3. Materialize toàn bộ tenant trước khi filter

- **Problem:** `ToListAsync` chạy ngay sau tenant predicate.
- **Why:** Các filter sau chạy bằng LINQ-to-Objects trong process.
- **Production impact:** DB/network payload lớn, allocation/GC pressure, latency và OOM risk.
- **Severity:** High.
- **Recommended fix:** Giữ `IQueryable`, compose predicates trước materialization.

### 4. Không pagination/limit

- **Problem:** Endpoint có thể trả toàn bộ matching rows.
- **Why:** Không có page size/cursor.
- **Production impact:** Memory spike, huge responses, abuse/DoS amplification.
- **Severity:** High.
- **Recommended fix:** Bounded page size; ưu tiên keyset pagination cho deep/high-volume traversal.

### 5. Search trên payload có thể rất đắt

- **Problem:** `Contains` trên trường text lớn có thể dẫn tới scan tùy DB/index/query shape.
- **Why:** Arbitrary substring search thường khó tận dụng B-tree index thông thường.
- **Production impact:** CPU/I/O database tăng mạnh.
- **Severity:** High.
- **Recommended fix:** Xác định search requirement; index các trường exact/prefix phù hợp hoặc dùng database full-text/search engine nếu thực sự cần arbitrary text search.

### 6. Log raw search term có thể ghi PII/secrets

- **Problem:** `text` do user nhập được ghi trực tiếp.
- **Why:** Người dùng có thể search email/token/payload fragment.
- **Production impact:** Sensitive data lan sang logging platform và retention khác.
- **Severity:** High.
- **Recommended fix:** Không log raw search text; log metadata như query-present, normalized length hoặc hash khi có justification.

### 7. Thiếu cancellation propagation

- **Problem:** Action và EF query không nhận request cancellation token.
- **Why:** Client disconnect không hủy DB work sớm.
- **Production impact:** Wasted capacity khi query đắt hoặc request timeout.
- **Severity:** Medium.
- **Recommended fix:** Nhận `CancellationToken` và truyền vào async DB call.

### 8. Date-range semantics và indexing chưa rõ

- **Problem:** `to <= value` dễ gây ambiguity với local time/end-of-day; index strategy chưa thể hiện.
- **Why:** Timestamp contract không rõ timezone/inclusive boundary.
- **Production impact:** Missing/extra records và query plan kém.
- **Severity:** Medium.
- **Recommended fix:** Chuẩn hóa UTC, dùng explicit half-open range `[from, to)` khi phù hợp; index theo access pattern, ví dụ `(TenantId, CreatedAt, Id)` sau khi đo execution plan.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
[Authorize(Policy = "AuditReader")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantAccessService _tenantAccess;

    public AuditController(
        AppDbContext db,
        ITenantAccessService tenantAccess)
    {
        _db = db;
        _tenantAccess = tenantAccess;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        Guid tenantId,
        string? text,
        DateTimeOffset? from,
        DateTimeOffset? to,
        int pageSize = 50,
        DateTimeOffset? before = null,
        CancellationToken cancellationToken = default)
    {
        if (!await _tenantAccess.CanReadAuditAsync(
                User, tenantId, cancellationToken))
            return Forbid();

        pageSize = Math.Clamp(pageSize, 1, 100);

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value.UtcDateTime);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt < to.Value.UtcDateTime);

        if (before.HasValue)
            query = query.Where(x => x.CreatedAt < before.Value.UtcDateTime);

        if (!string.IsNullOrWhiteSpace(text))
        {
            var normalized = text.Trim();
            query = query.Where(x => x.UserEmail.Contains(normalized));
        }

        var result = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Select(x => new AuditLogDto(
                x.Id,
                x.CreatedAt,
                x.Action,
                MaskEmail(x.UserEmail)))
            .Take(pageSize)
            .ToListAsync(cancellationToken);

        return Ok(result);
    }

    private static string MaskEmail(string email)
    {
        var at = email.IndexOf('@');
        return at <= 1 ? "***" : $"{email[0]}***{email[at..]}";
    }
}
```

Trong production, projection cần chỉ dùng các expression mà EF provider translate được. Nếu helper như `MaskEmail` không translate được, hãy project dữ liệu tối thiểu cần thiết rồi mask sau materialization, hoặc dùng expression/server-side function phù hợp. Với keyset pagination ổn định khi nhiều rows có cùng `CreatedAt`, cursor nên bao gồm cả `(CreatedAt, Id)`, không chỉ timestamp như snippet rút gọn. Arbitrary full-text search trên `RequestBody` nên tách thành capability có thiết kế/index và authorization riêng thay vì scan payload mặc định.

## Trade-offs

Keyset pagination nhanh và ổn định hơn offset ở deep pages nhưng API cursor phức tạp hơn. Projection/redaction giảm exposure nhưng support staff có thể cần detail endpoint riêng với quyền cao hơn và audit access chặt chẽ. Full-text search tăng khả năng tìm kiếm nhưng thêm index/storage/operational cost; nếu nhu cầu chỉ là email/action/time thì query relational có index phù hợp đơn giản hơn.

## Cách kiểm thử

1. **Security integration test:** user tenant A request tenant B phải nhận 403 và không query/return dữ liệu tenant B.
2. **Data-exposure test:** response không chứa request body, token fragment hoặc field ngoài DTO allowlist.
3. **Database/performance test:** seed hàng triệu rows; xác minh generated SQL có predicates, `ORDER BY`, `LIMIT/TOP` và kiểm tra execution plan/index usage.
4. **Pagination correctness test:** nhiều rows cùng timestamp không bị duplicate/missing khi chuyển cursor.
5. **Cancellation/load test:** cancel request hoặc disconnect client; xác minh request capacity phục hồi và không tạo memory spike bất thường.

## Quan sát trong production

Theo dõi endpoint latency p50/p95/p99, rows scanned/returned nếu DB telemetry hỗ trợ, query duration, timeout/cancellation count, response size và authorization-denied count. Trace request qua ASP.NET Core → EF/database. Alert trên latency/error-rate tăng và anomalous cross-tenant authorization failures. Không ghi raw search terms, request bodies hoặc credentials vào telemetry.

1. Vì sao `AsNoTracking` hữu ích ở endpoint read-only nhưng không giải quyết vấn đề materialization quá sớm?
2. Khi nào bạn chọn PostgreSQL full-text search hoặc một search engine thay vì `LIKE`/`Contains`?
3. Nếu support admin cần xem raw payload để điều tra incident, bạn thiết kế quyền, redaction và audit-access như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào ranh giới atomicity: broker redelivery là bình thường, vì vậy idempotency phải được enforce bằng invariant durable và side effect cần xử lý dual-write failure. Unique constraint cộng transactional outbox là hai cơ chế khác nhau nhưng bổ trợ nhau.

Challenge 2 tập trung vào hai ranh giới thường bị bỏ sót: authentication không thay thế tenant/resource authorization, và `ToListAsync` là điểm chuyển query từ database sang application memory.
