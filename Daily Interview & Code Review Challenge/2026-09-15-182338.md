# Code Review Challenge 1 — File download API làm cạn memory và giữ connection khi client hủy request

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, streaming, CancellationToken, resource disposal, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một document service chạy ASP.NET Core trên Azure App Service. File được lưu trong Azure Blob Storage; kích thước phổ biến 5–30 MB nhưng có thể đạt 700 MB. API hiện proxy file qua backend vì authorization phải được kiểm tra trước khi download.

Production chạy 6 instances. Khi khoảng 80–120 users đồng thời tải file lớn, memory mỗi instance tăng mạnh, GC hoạt động nhiều, request latency tăng và đôi khi instance restart. Application Insights còn cho thấy một số Blob dependency tiếp tục chạy sau khi browser đã hủy download.

Team chưa quyết định có nên chuyển sang direct Blob download bằng SAS. Yêu cầu hiện tại chỉ là review implementation và giữ authorization đúng.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpGet("{id:guid}/download")]
    public async Task<IActionResult> Download(Guid id)
    {
        var document = await _db.Documents
            .SingleOrDefaultAsync(x => x.Id == id);

        if (document is null)
            return NotFound();

        var blob = _container.GetBlobClient(document.BlobName);
        var response = await blob.DownloadStreamingAsync();

        using var memory = new MemoryStream();
        await response.Value.Content.CopyToAsync(memory);

        var bytes = memory.ToArray();

        _logger.LogInformation(
            "Downloaded document {DocumentId}, bytes={Bytes}",
            id,
            bytes.Length);

        return File(bytes, document.ContentType, document.FileName);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, memory/resource lifetime và cancellation.
2. Giải thích behavior dưới concurrent large-file downloads và production impact.
3. Review authorization boundary còn thiếu trong snippet.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design tốt hơn, bao gồm lựa chọn proxy streaming và điều kiện để cân nhắc direct Blob access.
6. Nêu testing cho large files, client disconnect, Blob failure và authorization.
7. Đề xuất telemetry để xác minh memory/GC/network bottleneck.

## Câu hỏi gợi mở

1. Một file 700 MB tồn tại bao nhiêu bản sao trong managed memory ở flow hiện tại?
2. Request cancellation có được truyền tới EF Core, Azure Blob SDK và response streaming không?
3. `DownloadStreamingAsync` trả về resource nào cần được dispose?
4. Việc biết `DocumentId` có đủ để được phép download file không?
5. Nếu chuyển sang SAS, authorization và thời hạn truy cập nên nằm ở đâu?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **buffering toàn bộ payload + request cancellation/resource lifetime**.

### Gợi ý 2

Phân biệt metadata authorization với data transfer. Backend có thể authorize mà không nhất thiết phải giữ toàn bộ file trong RAM.

## Kết quả code review tham khảo

### Critical — Toàn bộ Blob được buffer vào managed memory

**Vấn đề:** Code copy toàn bộ Blob vào `MemoryStream`, sau đó `ToArray()` tạo thêm một byte array chứa toàn bộ file.

**Tại sao xảy ra:** Implementation biến streaming source thành full-buffered response. Với file lớn, memory footprint của mỗi concurrent request có thể rất lớn và còn có allocation/copy bổ sung.

**Ảnh hưởng production:** Memory pressure, large allocations, GC overhead, possible OOM/restart và latency tăng mạnh khi nhiều download đồng thời.

**Cách sửa:** Stream content trực tiếp tới HTTP response hoặc trả stream/file result phù hợp, không materialize toàn bộ file trong memory.

### Critical — Không thấy authorization theo document/resource

**Vấn đề:** Endpoint chỉ lookup theo `id`; snippet không kiểm tra caller có quyền truy cập document hay không.

**Tại sao xảy ra:** Authentication ở pipeline, nếu có, không tự động cung cấp resource-level authorization.

**Ảnh hưởng production:** IDOR/broken authorization có thể cho phép user tải tài liệu của tenant/user khác.

**Cách sửa:** Enforce resource authorization trước khi truy cập Blob. Query nên scope theo tenant/ownership hoặc dùng policy/authorization service phù hợp domain; không tin `id` từ route như proof of access.

### High — Cancellation không được propagate

**Vấn đề:** Action không nhận `CancellationToken`; EF query, Blob download và copy không dùng `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Khi client disconnect, server-side I/O có thể tiếp tục cho đến khi operation tự kết thúc/fail.

**Ảnh hưởng production:** Lãng phí Blob bandwidth, sockets, DB/worker resources và làm incident nặng hơn dưới churn/load.

**Cách sửa:** Nhận `CancellationToken`, truyền xuyên suốt các cancellable operations và bảo đảm streaming path phản ứng đúng với request abort.

### High — Blob streaming response không được dispose rõ ràng

**Vấn đề:** `DownloadStreamingAsync` trả response chứa stream/resource nhưng code không quản lý lifetime của response/stream một cách rõ ràng.

**Tại sao xảy ra:** Resource được mở từ dependency và ownership không được thể hiện trong action.

**Ảnh hưởng production:** Connection/resource có thể được giữ lâu hơn cần thiết, đặc biệt khi exception/cancellation xảy ra.

**Cách sửa:** Dùng `await using`/`using` theo type/SDK contract và bảo đảm stream sống đủ lâu cho HTTP response nhưng được dispose sau transfer. Nếu framework sở hữu stream khi trả `File(stream, ...)`, thiết kế lifetime theo contract đó.

### High — Metadata query load entity nhiều hơn cần thiết và không truyền cancellation

**Vấn đề:** Read-only download lookup materialize entity tracking mặc định và không cancel theo request.

**Tại sao xảy ra:** Query dùng `SingleOrDefaultAsync` trực tiếp trên DbSet.

**Ảnh hưởng production:** Không phải bottleneck chính như buffering, nhưng tăng tracking/allocation và giữ work khi request đã abort.

**Cách sửa:** Project đúng fields cần thiết, dùng `AsNoTracking` nếu phù hợp và truyền cancellation token.

### Medium — Không xử lý Blob-not-found/race giữa metadata và object storage

**Vấn đề:** DB record có thể tồn tại nhưng Blob đã bị xóa/move hoặc storage tạm lỗi.

**Tại sao xảy ra:** SQL metadata và Blob Storage không có atomic consistency boundary.

**Ảnh hưởng production:** Unhandled dependency exception/500 và khó phân biệt data inconsistency với transient outage.

**Cách sửa:** Phân loại Blob 404, timeout/transient errors và cancellation; log/metric riêng và trả response phù hợp contract. Reconcile orphan metadata/blob theo background process nếu domain cần.

### Medium — Content metadata được tin mà không có validation policy

**Vấn đề:** `ContentType`/`FileName` lấy từ database và đưa vào response.

**Tại sao xảy ra:** Metadata có thể bắt nguồn từ upload/user-controlled source.

**Ảnh hưởng production:** Tùy client/browser behavior, filename/content type không được kiểm soát có thể gây unsafe rendering hoặc response-header issues.

**Cách sửa:** Validate/sanitize metadata tại upload boundary, dùng safe download disposition và không cho phép active content được inline nếu policy yêu cầu attachment.

### Low — Logging chỉ ghi success và byte count

**Vấn đề:** Không có duration, Blob dependency outcome, cancellation reason hay tenant/correlation context.

**Tại sao xảy ra:** Telemetry tập trung vào happy path.

**Ảnh hưởng production:** Khó chứng minh bottleneck và phân biệt client abort với storage/server failure.

**Cách sửa:** Structured telemetry cho document ID, size, duration, outcome, cancellation, Blob latency và correlation; tránh log sensitive filenames nếu không cần.

## Phiên bản đề xuất

Một phương án giữ backend proxy nhưng stream trực tiếp:

```csharp
[HttpGet("{id:guid}/download")]
public async Task<IActionResult> Download(
    Guid id,
    CancellationToken cancellationToken)
{
    var document = await _db.Documents
        .AsNoTracking()
        .Where(x => x.Id == id && x.TenantId == CurrentTenantId)
        .Select(x => new
        {
            x.BlobName,
            x.ContentType,
            x.FileName
        })
        .SingleOrDefaultAsync(cancellationToken);

    if (document is null)
        return NotFound();

    var authorizationResult = await _authorizationService
        .AuthorizeAsync(User, id, "DownloadDocument");

    if (!authorizationResult.Succeeded)
        return Forbid();

    var blob = _container.GetBlobClient(document.BlobName);

    try
    {
        var download = await blob.DownloadStreamingAsync(
            cancellationToken: cancellationToken);

        return File(
            download.Value.Content,
            document.ContentType,
            document.FileName,
            enableRangeProcessing: true);
    }
    catch (RequestFailedException ex) when (ex.Status == StatusCodes.Status404NotFound)
    {
        _logger.LogWarning(
            "Blob missing for document {DocumentId}", id);
        return NotFound();
    }
}
```

Đây là skeleton: production code phải xác minh ownership/disposal semantics của stream với framework/SDK version đang dùng, authorization model thật và policy cho range requests/content disposition.

Một alternative là backend authorize request rồi phát hành short-lived, least-privilege SAS cho đúng Blob. Cách đó giảm bandwidth/connection load trên API nhưng thay đổi threat model: URL trở thành bearer capability trong thời hạn hiệu lực. Chỉ chọn khi requirement cho phép và phải kiểm soát TTL, scope, HTTPS, logging/redaction và revocation strategy phù hợp.

## Giải thích thiết kế sau khi sửa

Streaming giữ memory gần với buffer size thay vì file size, nên concurrent large downloads scale tốt hơn về managed memory. Cancellation token nối lifecycle của browser request với database/storage operations.

Authorization được thực hiện ở resource boundary trước khi dữ liệu được phát. Tenant-scoped query còn giảm khả năng cross-tenant lookup, nhưng không thay thế policy nếu quyền truy cập phức tạp hơn ownership đơn giản.

Direct SAS không mặc định tốt hơn. Nó giảm API data-plane cost nhưng thêm capability-URL semantics và có thể khó revoke tức thời. Proxy streaming vẫn hợp lý khi cần kiểm soát/audit chặt hoặc storage không được expose trực tiếp.

## Trade-offs

- Proxy streaming vẫn tiêu tốn outbound bandwidth và connection duration trên application instances.
- Direct SAS giảm backend load nhưng URL có thể bị chia sẻ trong TTL window.
- Range processing cải thiện resume/media-style access nhưng cần xác minh storage/framework behavior và authorization semantics.
- Aggressive cancellation tiết kiệm resource nhưng cần phân biệt client abort bình thường với dependency failure trong telemetry.

## Cách kiểm thử

1. **Load test:** nhiều concurrent downloads 500–700 MB; đo working set, allocation/GC, p95/p99 và throughput.
2. **Cancellation test:** browser/client abort giữa transfer; xác minh Blob operation/response kết thúc và resource được release.
3. **Authorization integration test:** user/tenant khác không thể tải document dù biết GUID.
4. **Failure-path test:** DB metadata tồn tại nhưng Blob missing hoặc Blob Storage timeout; response/telemetry phải đúng contract.
5. **Range/download test:** kiểm tra filename, content type, partial request và file integrity nếu range processing được hỗ trợ.

## Quan sát trong production

Theo dõi request duration/size, concurrent downloads, process working set, allocation rate, GC pause, instance restarts, 5xx và client-aborted requests. Correlate Application Insights request telemetry với Azure Blob dependency duration/failure/cancellation.

Dashboard nên tách small/large file cohorts để tránh average che mất tail latency. Alert khi memory hoặc restart tăng cùng download concurrency, và theo dõi p95/p99 thay vì chỉ average.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn SAS direct download thay vì proxy streaming?
2. Nếu business yêu cầu revoke quyền truy cập gần như ngay lập tức sau khi SAS đã phát hành, thiết kế sẽ thay đổi thế nào?
3. Bạn sẽ chứng minh memory pressure đến từ buffering chứ không phải EF Core hay một memory leak khác bằng evidence nào?

# Code Review Challenge 2 — SQL pagination chậm dần và trả duplicate/missing rows khi dữ liệu thay đổi

**Chủ đề:** SQL Server, PostgreSQL concepts, pagination, composite indexes, execution plan, concurrency correctness, API performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một admin portal hiển thị audit events. Bảng có khoảng 180 triệu rows và tăng 8–12 triệu rows mỗi tháng. API cho phép lọc theo `TenantId`, khoảng thời gian và phân trang theo newest-first.

Ở page đầu, query thường dưới 100 ms. Khi user nhảy tới page 2.000–5.000, latency có thể lên nhiều giây và CPU/reads trên database tăng mạnh. QA còn thấy đôi lúc cùng một event xuất hiện ở hai pages hoặc một event biến mất khỏi sequence khi có records mới được insert trong lúc user đang paging.

Schema/query hiện tại:

## Đoạn code cần review

```sql
CREATE TABLE AuditEvents
(
    Id           BIGINT IDENTITY PRIMARY KEY,
    TenantId     UNIQUEIDENTIFIER NOT NULL,
    CreatedAtUtc DATETIME2 NOT NULL,
    EventType    NVARCHAR(100) NOT NULL,
    ActorId      UNIQUEIDENTIFIER NULL,
    PayloadJson  NVARCHAR(MAX) NULL
);

CREATE INDEX IX_AuditEvents_CreatedAtUtc
    ON AuditEvents (CreatedAtUtc DESC);

DECLARE @TenantId UNIQUEIDENTIFIER = @p0;
DECLARE @FromUtc DATETIME2 = @p1;
DECLARE @ToUtc DATETIME2 = @p2;
DECLARE @Page INT = @p3;
DECLARE @PageSize INT = @p4;

SELECT
    Id,
    TenantId,
    CreatedAtUtc,
    EventType,
    ActorId,
    PayloadJson
FROM AuditEvents
WHERE TenantId = @TenantId
  AND CreatedAtUtc >= @FromUtc
  AND CreatedAtUtc < @ToUtc
ORDER BY CreatedAtUtc DESC
OFFSET (@Page - 1) * @PageSize ROWS
FETCH NEXT @PageSize ROWS ONLY;
```

Product nói users chủ yếu bấm Next/Previous; requirement “jump tới page 5000” chưa được xác nhận là bắt buộc. API hiện trả page number chứ chưa có cursor.

## Nhiệm vụ của ứng viên

1. Xác định performance và correctness issues của query/index/pagination.
2. Giải thích vì sao deep pages chậm dù chỉ trả 50 rows.
3. Phân tích duplicate/missing rows khi concurrent inserts xảy ra.
4. Đề xuất index dựa trên actual predicate/order, không chỉ nói “thêm index”.
5. Đề xuất pagination contract phù hợp requirement và nêu trade-offs.
6. Nêu testing với large dataset, ties và concurrent inserts.
7. Nêu evidence cần lấy từ execution plan/database metrics trước khi tối ưu.

## Câu hỏi gợi mở

1. Index hiện tại bắt đầu bằng column nào, trong khi predicate quan trọng nhất bắt đầu bằng gì?
2. `ORDER BY CreatedAtUtc` có deterministic khi nhiều rows cùng timestamp không?
3. Database phải làm gì với hàng trăm nghìn rows trước offset trước khi trả page sâu?
4. Nếu page 1 được đọc rồi có 100 records mới insert trước khi page 2 được đọc, offset có còn trỏ cùng logical boundary không?
5. Product thực sự cần random page access hay chỉ sequential navigation?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **deep OFFSET cost + unstable ordering/boundary dưới concurrent writes**.

### Gợi ý 2

Hãy thiết kế index và cursor cùng một ordering tuple, ví dụ timestamp cộng unique tiebreaker, thay vì xem chúng là hai vấn đề độc lập.

## Kết quả code review tham khảo

### High — Deep OFFSET buộc database bỏ qua lượng lớn rows

**Vấn đề:** `OFFSET` tăng tuyến tính theo page number trước khi lấy page nhỏ tiếp theo.

**Tại sao xảy ra:** Engine vẫn phải locate/process ordered rows trước boundary; việc chỉ return 50 rows không có nghĩa chỉ 50 rows được xử lý.

**Ảnh hưởng production:** Logical reads, CPU và latency tăng ở deep pages; concurrent deep queries có thể ảnh hưởng workload khác.

**Cách sửa:** Nếu UX chủ yếu Next/Previous, cân nhắc keyset/cursor pagination để seek từ last seen ordering key thay vì skip toàn bộ prefix.

### High — Index không align tốt với tenant-scoped access pattern

**Vấn đề:** Index chỉ bắt đầu bằng `CreatedAtUtc`, trong khi query luôn filter một `TenantId` cụ thể rồi order theo time.

**Tại sao xảy ra:** Engine có thể phải đọc/filter nhiều entries của tenants khác tùy distribution/selectivity/plan.

**Ảnh hưởng production:** Excessive reads và CPU trên bảng rất lớn.

**Cách sửa:** Candidate index cần bắt đầu từ equality predicate và tiếp tục theo ordering/range, ví dụ `(TenantId, CreatedAtUtc DESC, Id DESC)`; INCLUDE columns phải cân nhắc kích thước/write cost, đặc biệt không mặc định include `PayloadJson` lớn.

### High — Ordering không deterministic khi timestamp trùng nhau

**Vấn đề:** `ORDER BY CreatedAtUtc DESC` không định nghĩa thứ tự giữa rows có cùng timestamp.

**Tại sao xảy ra:** `CreatedAtUtc` không unique.

**Ảnh hưởng production:** Rows có thể đổi relative order giữa executions/pages, tạo duplicate/missing behavior ngay cả ngoài concurrent inserts.

**Cách sửa:** Dùng stable unique tiebreaker, ví dụ `ORDER BY CreatedAtUtc DESC, Id DESC`, và cursor/index dùng cùng tuple.

### High — Offset pagination không ổn định trước concurrent inserts

**Vấn đề:** Page boundary được tính bằng vị trí tương đối tại thời điểm từng query, không phải logical anchor.

**Tại sao xảy ra:** Khi rows mới được insert trước current offset, vị trí của rows cũ dịch chuyển.

**Ảnh hưởng production:** User có thể thấy duplicate hoặc skip events giữa các page requests.

**Cách sửa:** Keyset cursor giữ boundary `(CreatedAtUtc, Id)` của row cuối page trước. Query page sau lấy rows strictly older hơn tuple đó.

### Medium — Fetch `PayloadJson` lớn cho list view có thể tạo I/O/network cost không cần thiết

**Vấn đề:** Query luôn trả `NVARCHAR(MAX)` dù portal list có thể không hiển thị payload đầy đủ.

**Tại sao xảy ra:** Read model chưa tách list summary và detail.

**Ảnh hưởng production:** Tăng page reads, data transfer, serialization và API memory/latency.

**Cách sửa:** Xác minh UI requirement; nếu list chỉ cần metadata, bỏ payload khỏi list query và tải detail theo nhu cầu.

### Medium — Page arithmetic và input bounds chưa được bảo vệ ở contract

**Vấn đề:** `@Page`, `@PageSize` có thể invalid/huge; arithmetic cũng không nên được coi là unconstrained user input.

**Tại sao xảy ra:** SQL snippet không thể hiện API validation.

**Ảnh hưởng production:** Expensive requests hoặc unexpected behavior có thể bị tạo cố ý/vô ý.

**Cách sửa:** Validate page/cursor contract và giới hạn page size. Với cursor, validate opaque token/version/tenant binding nếu token được client gửi lại.

### Medium — Index design cần kiểm tra write amplification và plan thực tế

**Vấn đề:** “Thêm covering index” có thể trở thành phản xạ nhưng audit table có write volume cao và payload lớn.

**Tại sao xảy ra:** Mỗi index tăng storage/write maintenance; include quá nhiều columns làm index nặng.

**Ảnh hưởng production:** Insert throughput/storage có thể xấu đi dù read query nhanh hơn.

**Cách sửa:** Dùng actual execution plan, logical reads, row counts và workload để chọn narrow index; benchmark read/write trade-off.

## Phiên bản đề xuất

Nếu product xác nhận sequential navigation là chính, một design có thể là:

```sql
CREATE INDEX IX_AuditEvents_Tenant_Created_Id
ON AuditEvents
(
    TenantId,
    CreatedAtUtc DESC,
    Id DESC
)
INCLUDE
(
    EventType,
    ActorId
);
```

Page đầu:

```sql
SELECT TOP (@PageSize)
    Id,
    TenantId,
    CreatedAtUtc,
    EventType,
    ActorId
FROM AuditEvents
WHERE TenantId = @TenantId
  AND CreatedAtUtc >= @FromUtc
  AND CreatedAtUtc < @ToUtc
ORDER BY CreatedAtUtc DESC, Id DESC;
```

Page tiếp theo dùng cursor của row cuối page trước:

```sql
SELECT TOP (@PageSize)
    Id,
    TenantId,
    CreatedAtUtc,
    EventType,
    ActorId
FROM AuditEvents
WHERE TenantId = @TenantId
  AND CreatedAtUtc >= @FromUtc
  AND CreatedAtUtc < @ToUtc
  AND
  (
      CreatedAtUtc < @LastCreatedAtUtc
      OR (CreatedAtUtc = @LastCreatedAtUtc AND Id < @LastId)
  )
ORDER BY CreatedAtUtc DESC, Id DESC;
```

API có thể trả opaque cursor chứa/version hóa boundary cần thiết thay vì expose raw implementation details. Nếu requirement bắt buộc random access tới arbitrary page, OFFSET có thể vẫn cần cho use case đó hoặc cần một strategy khác; không nên loại bỏ feature trước khi clarify requirement.

## Giải thích thiết kế sau khi sửa

Equality key `TenantId` đứng đầu index phù hợp tenant-scoped query; tiếp theo là ordering tuple để engine seek/range scan theo đúng thứ tự. `Id` tạo deterministic order cho timestamp ties.

Keyset pagination làm cost page kế tiếp phụ thuộc chủ yếu vào page size và selectivity quanh cursor thay vì số rows phải skip. Cursor còn ổn định hơn trước inserts mới ở đầu timeline vì boundary dựa trên giá trị của row đã thấy, không dựa trên ordinal position.

Không include `PayloadJson` mặc định vì đây có thể là large value và list UI chưa chắc cần. Đây là requirement/read-model decision, không chỉ index tuning.

## Trade-offs

- Keyset pagination không hỗ trợ jump tới arbitrary page number tự nhiên như OFFSET.
- Cursor contract phức tạp hơn và cần versioning/validation.
- Composite index tăng storage và write amplification.
- `Previous` navigation cần cursor strategy phù hợp hoặc reverse ordering logic.
- Nếu tenant cực lớn/hot hoặc retention/query pattern khác, partitioning/archival có thể cần đánh giá sau khi evidence chỉ ra bottleneck; không nên nhảy thẳng tới partitioning.

## Cách kiểm thử

1. **Database performance test:** seed production-like cardinality/distribution; so sánh logical reads, CPU và duration giữa shallow/deep OFFSET và keyset.
2. **Tie test:** nhiều rows cùng `CreatedAtUtc`; xác minh deterministic order nhờ `Id`.
3. **Concurrency test:** insert records mới giữa page requests; keyset không duplicate/skip rows thuộc snapshot-like traversal semantics đã định nghĩa.
4. **API integration test:** invalid/expired/tampered cursor và page-size limits được xử lý đúng.
5. **Load test:** nhiều tenants paging đồng thời; theo dõi database waits, CPU, reads và API p95/p99.

## Quan sát trong production

Thu thập actual execution plan, logical reads, rows read vs rows returned, query duration, CPU, waits và index usage. Ở API layer theo dõi page/cursor depth, response size, p95/p99 và timeout rate.

Correlate slow requests với database dependency telemetry trong Application Insights. Sau index rollout, so sánh reads/CPU/latency và đồng thời theo dõi insert cost/index size để xác nhận optimization không chuyển bottleneck sang write path.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc jump trực tiếp tới page 5.000, bạn sẽ giữ/thiết kế feature đó như thế nào?
2. Nếu `CreatedAtUtc` có thể được sửa sau insert, cursor semantics có vấn đề gì và bạn sẽ chọn ordering key nào?
3. Khi nào bạn cân nhắc partitioning/archival thay vì tiếp tục tối ưu index trên một bảng audit rất lớn?

## Kiến thức trọng tâm

Challenge 1 tập trung vào data-plane behavior của large-file API: streaming khác buffering ở memory complexity, request cancellation phải propagate xuyên dependency chain, resource-level authorization không thể được thay bằng việc biết một GUID, và Blob/SQL là các failure boundary riêng.

## Mẫu tư duy cần nhớ

- **Stream large payloads; đừng materialize nếu không cần.**
- Propagate cancellation qua toàn bộ I/O chain và quan sát client-abort riêng với server failure.
- Authorization phải được enforce tại resource boundary, không chỉ authentication ở request pipeline.
- Thiết kế index theo **equality predicates → range/order → projection**, rồi xác minh bằng execution plan và logical reads.
- Pagination contract là product + consistency decision; không chỉ là cú pháp SQL.
