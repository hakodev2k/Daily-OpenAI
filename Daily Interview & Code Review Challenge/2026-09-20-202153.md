# Câu 1 — DI lifetime trong ASP.NET Core: vì sao một `Scoped` service bị giữ sống lâu hơn request?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, dependency injection, DI lifetimes, `DbContext`, scopes, `BackgroundService`, resource lifetime, debugging

## Bối cảnh

Một ASP.NET Core API trên .NET 8 xử lý đơn hàng bằng EF Core. `OrderDbContext` và `OrderRepository` được đăng ký `Scoped`. Team vừa thêm một service tổng hợp metrics và một `BackgroundService` để định kỳ flush dữ liệu. Sau release, production xuất hiện các triệu chứng không ổn định: memory tăng dần, đôi lúc có lỗi liên quan tới disposed `DbContext`, và ở một nhánh code khác có hiện tượng nhiều tác vụ dùng cùng một `DbContext` ngoài ý muốn.

Một developer cho rằng: “`Scoped` nghĩa là object luôn chỉ sống đúng một HTTP request nên DI container chắc chắn sẽ tự xử lý.” Một developer khác đề xuất đổi repository thành `Singleton` để giảm allocations.

Bạn chưa biết service nào đang inject service nào, scope được tạo ở đâu, có service nào resolve dependency từ root provider hay không, và background loop có chạy song song nhiều iteration hay không.

## Câu hỏi chính

Hãy giải thích `Transient`, `Scoped`, `Singleton` thực sự được quản lý theo scope như thế nào trong ASP.NET Core; vì sao `Scoped` không đồng nghĩa tuyệt đối với “một HTTP request”; captive dependency hoặc resolve từ sai scope có thể gây hành vi gì; và bạn sẽ điều tra, sửa, kiểm thử vấn đề này như thế nào nếu `DbContext` phải được dùng cả trong request lẫn background processing?

## Câu hỏi làm rõ nên cân nhắc

1. Dependency graph thực tế giữa `Singleton`, hosted service, repository và `DbContext` là gì?
2. Background worker đang inject trực tiếp scoped service hay tạo scope bằng `IServiceScopeFactory` cho từng unit of work?
3. Có code nào giữ `IServiceProvider`, repository hoặc `DbContext` trong static field/cache/callback lâu dài không?
4. Mỗi background iteration có thể chạy song song hay overlap không, và transaction boundary mong muốn là gì?
5. Scope validation có được bật trong môi trường development/test và lỗi xuất hiện ở startup hay runtime?

## Gợi ý tư duy

### Gợi ý 1

Lifetime gắn với **DI scope**, không gắn về mặt khái niệm với HTTP request. HTTP request chỉ là một nơi ASP.NET Core tạo scope tự nhiên.

### Gợi ý 2

Một long-lived component không nên giữ một dependency có lifetime ngắn hơn qua nhiều units of work.

### Gợi ý 3

Với background processing, hãy xác định rõ scope boundary và concurrency boundary trước khi sửa registration.

## Cấu trúc trả lời đề xuất

1. Vẽ dependency graph và lifetime của từng component.
2. Giải thích root provider, child/request scope và disposal.
3. Xác định captive dependency hoặc service locator misuse.
4. Kiểm tra concurrency quanh `DbContext`.
5. Thu evidence từ logs, exception stack, traces và runtime diagnostics.
6. Chọn scope boundary cho HTTP request và background unit of work.
7. Sửa dependency construction thay vì đổi lifetime tùy tiện.
8. Test disposal, concurrency và multi-iteration behavior.
9. Theo dõi lỗi, memory và background processing sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Scoped` nghĩa là một instance trên mỗi DI scope, không phải định nghĩa cứng “mỗi HTTP request”.
- HTTP request thường có request scope; background service không tự có request scope tương đương.
- Không inject trực tiếp scoped `DbContext`/repository vào singleton/hosted service để giữ nó suốt lifetime ứng dụng.
- Không đổi repository/`DbContext` thành `Singleton` để giảm allocations.
- `DbContext` không được thiết kế để dùng concurrent operations trên cùng instance.
- Với background work, tạo scope có chủ đích cho mỗi unit of work hoặc dùng factory phù hợp với design.

### Điểm cộng

- Phân biệt scope lifetime với object reachability do application giữ reference.
- Nhắc tới disposal của scoped disposables khi scope kết thúc.
- Dùng scope validation để phát hiện một số lifetime mismatch sớm.
- Không biến `IServiceProvider.GetService` thành service-locator pattern lan rộng trong business code.

### Senior+

- Thiết kế transaction/unit-of-work boundary độc lập với DI registration.
- Nếu worker xử lý song song, mỗi concurrent unit cần dependency scope/context riêng.
- Xem lifetime bug là correctness/reliability problem trước khi coi là allocation optimization.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng việc đổi registration. Trước tiên tôi vẽ dependency graph. Trong ASP.NET Core, request thường tạo một scope nên scoped service được reuse trong request đó và disposed khi scope kết thúc. Nhưng `Scoped` về bản chất là “một instance trong một scope”. Nếu code tự tạo scope thì lifetime theo scope đó; nếu một long-lived object giữ reference tới scoped object sai cách thì object có thể sống lâu hơn intent của request.

Một `BackgroundService` được host như long-lived service. Nếu nó cần `OrderRepository`/`OrderDbContext`, boundary hợp lý thường là tạo một scope cho từng logical unit/iteration bằng `IServiceScopeFactory`, resolve scoped dependencies trong scope, hoàn thành operation rồi dispose scope. Nếu nhiều messages/jobs được xử lý song song thì không share cùng `DbContext`; mỗi unit có scope/context riêng. Một alternative là `IDbContextFactory<TContext>` khi pattern đó phù hợp, nhưng factory không thay thế việc xác định transaction boundary.

Tôi cũng kiểm tra captive dependencies: singleton phụ thuộc trực tiếp hoặc gián tiếp vào scoped service, object bị cache/static capture, callback sống lâu giữ reference, hoặc code resolve từ provider không đúng boundary. Nếu có disposed-context exception, stack trace và ownership/disposal path rất quan trọng. Nếu có concurrent-operation exception hoặc data behavior bất thường, tôi correlate với worker overlap và context identity.

Đổi repository hoặc `DbContext` thành singleton là hướng sai vì nó kéo state/change tracker và connection-related behavior qua nhiều operations, đồng thời tạo thread-safety/correctness risk. Giảm allocation không phải lý do hợp lệ để phá lifetime semantics.

Testing nên có integration test chạy nhiều request độc lập, worker nhiều iterations và concurrency test nếu worker parallel. Tôi muốn assert mỗi unit có context riêng, resource được dispose đúng lúc, không dùng context sau scope, và graceful shutdown không để work dùng dependency đã dispose. Production telemetry nên ghi operation/job correlation, exception type, worker concurrency, processing duration và memory trend.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không hiểu `Scoped` là keyword đồng nghĩa với HTTP request. Nó là một instance trong một DI scope; HTTP request chỉ là scope mà framework tạo sẵn. Hosted service lại sống lâu, nên nếu singleton/worker giữ scoped repository hoặc `DbContext`, lifetime boundary có thể sai.

Em sẽ vẽ dependency graph, kiểm tra scope validation, stack trace và chỗ resolve dependency. Với background processing, em tạo scope theo từng logical unit of work, resolve `DbContext` trong scope đó và dispose sau khi xong. Nếu xử lý parallel, mỗi unit có context riêng vì `DbContext` không nên được share cho concurrent operations.

Em sẽ không đổi `DbContext` thành singleton để giảm allocations. Sau khi sửa, em test nhiều worker iterations, concurrency, cancellation/shutdown và theo dõi disposed/concurrency exceptions cùng memory trend để xác nhận root cause đã được xử lý.”

## Câu hỏi đào sâu

1. Nếu một background job cần thực hiện ba repository operations trong cùng transaction, bạn đặt scope và transaction boundary ở đâu?
2. Nếu team đề xuất `IDbContextFactory` cho mọi nơi, kể cả request CRUD đơn giản, bạn đồng ý hay phản biện thế nào?
3. Nếu scope đã đúng nhưng memory vẫn tăng, bằng chứng nào khiến bạn chuyển hướng khỏi DI lifetime sang retention/cache/GC investigation?

## Lỗi trả lời thường gặp

- Đồng nhất `Scoped` với HTTP request trong mọi context.
- Đổi `DbContext` thành singleton để “reuse connection”.
- Tạo một scope duy nhất cho toàn bộ lifetime của `BackgroundService`.
- Share một context giữa các jobs chạy song song.
- Chỉ sửa registration mà không xác định ownership và transaction boundary.

## Thang điểm 0–10

- **0–2:** Chỉ thuộc định nghĩa ba lifetime, không giải thích scope behavior.
- **3–4:** Nhận ra singleton/scoped mismatch nhưng chưa xử lý background/concurrency đúng.
- **5–6:** Hiểu scope boundary, disposal và `DbContext` lifetime; đề xuất sửa hợp lý.
- **7–8:** Có dependency graph, diagnostics, concurrency/test/telemetry đầy đủ.
- **9–10:** Kết nối DI lifetime với transaction ownership, background unit of work, shutdown và production correctness một cách có điều kiện.

# Câu 2 — Azure Service Bus backlog tăng nhanh: consumer “khỏe” nhưng message bị xử lý lặp và vào DLQ

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, distributed systems, retries, idempotency, message lock, DLQ, observability, SQL, production incident response

## Bối cảnh

Một order integration service nhận messages từ Azure Service Bus queue và đồng bộ order sang hệ thống fulfillment bên thứ ba. Bình thường queue gần như rỗng. Sau khi fulfillment API chậm bất thường trong khoảng một giờ, queue depth tăng nhanh. Khi dependency phục hồi, consumer scale-out mạnh nhưng team thấy một số order được gửi sang fulfillment hai lần, một số messages xuất hiện lại sau khi đã “xử lý gần xong”, và DLQ bắt đầu tăng.

Application Insights cho thấy request tới fulfillment có cả timeout lẫn response thành công. Database nội bộ có bảng `IntegrationLog`, nhưng team chưa chắc việc ghi log diễn ra trước hay sau external call. Consumer có retry policy ở HTTP client và Service Bus cũng có redelivery behavior. Một engineer muốn tăng concurrency thật cao để “drain queue càng nhanh càng tốt”; engineer khác muốn xóa toàn bộ DLQ rồi requeue.

Bạn chưa biết lock duration/renewal behavior, handler execution time, settlement mode, max delivery count, idempotency contract của fulfillment API, hay ordering requirement.

## Câu hỏi chính

Bạn sẽ xử lý incident theo thứ tự nào để giảm business impact nhưng không tạo thêm duplicate side effects? Hãy mô tả evidence cần thu để phân biệt slow dependency, lock loss, retry amplification, poison messages và capacity bottleneck; cách thiết kế idempotency/settlement/retry; cách xử lý backlog và DLQ an toàn; và cách ngăn sự cố tương tự tái diễn.

## Câu hỏi làm rõ nên cân nhắc

1. Duplicate fulfillment có gây charge/shipment thực hay downstream có idempotency key?
2. Handler duration so với message lock và lock renewal configuration thế nào?
3. Message được `Complete` ở thời điểm nào; exception/timeout sau external side effect được xử lý ra sao?
4. HTTP retry policy retry những failure nào, tối đa bao nhiêu lần và có jitter/backoff không?
5. DLQ reasons/delivery count/message classes có tập trung vào một lỗi schema/business cụ thể hay phân bố rộng?

## Gợi ý tư duy

### Gợi ý 1

At-least-once delivery nghĩa là duplicate delivery phải được xem là tình huống bình thường cần thiết kế, không phải sự kiện “không thể xảy ra”.

### Gợi ý 2

Timeout không chứng minh downstream chưa thực hiện side effect.

### Gợi ý 3

Drain backlog nhanh hơn chỉ có ích nếu downstream và idempotency boundary chịu được concurrency đó.

## Cấu trúc trả lời đề xuất

1. Định lượng user/business impact và loại side effect bị duplicate.
2. Giới hạn blast radius bằng concurrency/rate phù hợp downstream.
3. Dựng timeline queue → handler → external call → persistence → settlement.
4. Thu queue metrics, delivery count, DLQ reason, traces và dependency telemetry.
5. Lập competing hypotheses và prediction cho từng giả thuyết.
6. Xác định idempotency boundary và ambiguous timeout behavior.
7. Sửa retry/settlement/lock handling.
8. Replay DLQ có kiểm soát.
9. Load/failure test với slow/timeout dependency.
10. Alert trên queue age/depth, DLQ, duplicate và dependency health.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định queue bảo đảm exactly-once side effects.
- Không tăng concurrency vô hạn khi downstream đang/đã bị quá tải.
- Phân biệt delivery retry với HTTP retry và nhận ra retry multiplication.
- Timeout sau external call là trạng thái ambiguous; cần idempotency/reconciliation.
- Không bulk requeue DLQ trước khi phân loại nguyên nhân.
- Settlement chỉ nên xảy ra khi business processing đạt trạng thái được định nghĩa là thành công.

### Điểm cộng

- Dùng stable business idempotency key nếu downstream hỗ trợ.
- Nếu downstream không hỗ trợ idempotency, thiết kế local inbox/state machine/reconciliation tùy semantics thay vì hứa exactly-once.
- Theo dõi message age, active count, dead-letter count, delivery count distribution và processing latency.
- Tách transient failure khỏi permanent validation/schema failure.

### Senior+

- Giải thích “DB record rồi external call” và “external call rồi DB record” đều có failure window nếu không có distributed transaction chung.
- Dùng state machine/outbox-inbox/reconciliation để quản lý uncertainty thay vì che giấu bằng retry.
- Capacity recovery dựa trên downstream rate limit, safe concurrency và backlog age SLO.

## Hướng giải quyết tham khảo

Đầu tiên tôi đánh giá duplicate side effect có gây shipment/charge thật không và tạm giới hạn consumer concurrency ở mức downstream chịu được. Khi dependency vừa phục hồi, scale-out cực mạnh cộng với HTTP retries có thể tạo retry storm và làm dependency suy yếu lần nữa. Tôi không xóa/requeue DLQ hàng loạt vì có thể replay poison message hoặc duplicate side effects.

Tôi dựng trace cho từng `MessageId`/business `OrderId`: dequeue time, delivery count, handler start/end, external request attempt, response/timeout, local state update và settlement. Tôi xem queue depth/oldest age, DLQ reason, lock-related exceptions, dependency p95/p99 và tỷ lệ timeout. Nếu handler kéo dài gần/vượt lock boundary, lock loss/redelivery là một hypothesis; nếu delivery count thấp nhưng mỗi delivery tạo nhiều HTTP attempts, retry amplification là hypothesis khác.

Về correctness, Service Bus delivery phải được coi là có thể lặp. Consumer cần idempotent behavior theo business operation. Nếu fulfillment API hỗ trợ idempotency key, dùng stable key gắn với operation/order version thay vì sinh key mới mỗi retry. Nếu external request timeout, không được suy ra request thất bại: downstream có thể đã commit rồi response bị mất. Khi đó cần query/reconcile trạng thái hoặc dùng downstream idempotency contract.

Local `IntegrationLog` chỉ hữu ích nếu semantics rõ. Nếu ghi “processed” trước external call thì crash có thể bỏ sót side effect; nếu gọi external trước rồi mới ghi thì crash ở giữa có thể dẫn tới duplicate khi redelivery. Không có local transaction nào tự làm atomic được SQL + arbitrary external HTTP. Tôi sẽ thiết kế explicit processing states và reconciliation, hoặc inbox/outbox ở boundary phù hợp. Mục tiêu là deterministic recovery, không tuyên bố exactly-once nếu hệ thống không cung cấp nó.

Retry phải phân loại lỗi: transient 429/5xx/network theo contract có bounded exponential backoff + jitter; validation/business permanent failure không retry vô hạn. Message settlement, lock renewal và max delivery count phải phù hợp handler duration. DLQ được triage theo reason/schema/version; chỉ replay sau khi fix và với rate limit, audit và duplicate protection.

Testing gồm duplicate delivery, timeout sau downstream commit, lock expiration, dependency 429/5xx, consumer crash ở từng failure window và replay DLQ. Monitoring gồm oldest message age, active/dead-letter count, delivery count, processing success/failure, external attempt rate, idempotency conflicts và downstream latency/error rate.

## Mẫu trả lời trong phỏng vấn

“Em ưu tiên ngăn duplicate side effect trước khi drain queue. Service Bus có thể redeliver nên consumer phải chịu được duplicate; đồng thời HTTP retry bên trong một delivery có thể nhân số calls lên. Em sẽ giới hạn concurrency theo capacity của fulfillment, dựng trace theo `MessageId` và `OrderId`, rồi correlate delivery count, lock errors, handler duration, HTTP attempts, timeout và settlement.

Điểm quan trọng là timeout không có nghĩa downstream chưa xử lý. Nếu fulfillment hỗ trợ idempotency key, em dùng stable business key cho mọi retry. Nếu không, em cần state/reconciliation rõ ràng vì SQL log và external HTTP không thể atomic chỉ bằng local transaction.

DLQ em phân loại theo reason trước, không requeue hàng loạt. Sau fix, replay có rate limit và duplicate protection. Em test duplicate delivery, timeout-after-commit, lock loss và crash windows; production alert theo oldest-message age, DLQ growth, delivery count và dependency health.”

## Câu hỏi đào sâu

1. Nếu fulfillment API không có endpoint tra cứu trạng thái và cũng không hỗ trợ idempotency key, bạn giảm duplicate risk bằng cách nào và giới hạn nào vẫn còn?
2. Bạn vừa đề xuất giảm concurrency; nếu backlog age đang vi phạm SLA nghiêm trọng, bạn quyết định safe drain rate dựa trên dữ liệu nào?
3. Nếu business yêu cầu strict ordering theo từng customer nhưng vẫn muốn parallelism cao giữa customers, bạn đánh giá thiết kế nào?

## Lỗi trả lời thường gặp

- Tin rằng queue bảo đảm side effect exactly-once.
- Retry mọi exception ở cả HTTP và message layer mà không tính tổng attempts.
- Tăng consumer concurrency tối đa ngay sau dependency outage.
- Requeue toàn bộ DLQ mà không triage.
- Xem timeout là bằng chứng downstream chưa commit.

## Thang điểm 0–10

- **0–2:** Chỉ nói “retry/requeue/scale consumer”.
- **3–4:** Biết duplicate delivery nhưng thiếu failure-window reasoning.
- **5–6:** Có idempotency, settlement, DLQ triage và observability hợp lý.
- **7–8:** Phân tích được retry amplification, ambiguous timeout, lock và recovery capacity.
- **9–10:** Thiết kế deterministic recovery/reconciliation, giải thích giới hạn exactly-once và cân bằng correctness với backlog SLO.

# Câu 3 — Modernize portal .NET Framework + jQuery: rewrite toàn bộ hay strangler migration?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** .NET modernization, architecture, ASP.NET Core, React/Vue, IIS, Azure App Service, migration strategy, CI/CD, testing, observability, rollout/rollback

## Bối cảnh

Một enterprise management portal đã hoạt động nhiều năm. Backend chính là .NET Framework 4.5 chạy IIS/Windows Server, frontend gồm server-rendered MVC views và nhiều jQuery modules. Hệ thống dùng SQL Server chung, tích hợp authentication doanh nghiệp và vài third-party APIs. Release hiện tại cần maintenance window và rollback chủ yếu dựa vào redeploy artifact cũ.

Business muốn tăng tốc feature delivery, giảm rủi ro security/unsupported dependencies và dần chuyển sang modern .NET. Team có kinh nghiệm ASP.NET Core, .NET 8, Vue.js/React.js, Azure App Service và CI/CD, nhưng chỉ có một nhóm nhỏ; portal vẫn phải hoạt động trong quá trình migration. Product đề nghị “rewrite toàn bộ trong 6 tháng cho sạch”, trong khi operations muốn giữ hệ thống cũ càng lâu càng tốt vì sợ migration.

Traffic ở mức enterprise vừa phải, không có bằng chứng cần microservices hoặc Kubernetes. Database chứa nhiều stored procedures và schema được dùng bởi các module legacy. Một số workflow quan trọng nhưng test automation hiện chưa đầy đủ.

## Câu hỏi chính

Bạn sẽ xây dựng chiến lược modernization như thế nào? Hãy so sánh rewrite toàn bộ với incremental/strangler migration; xác định boundaries, data ownership, authentication, frontend transition, hosting/deployment, compatibility, testing, observability và rollback; đồng thời giải thích tiêu chí nào khiến bạn chọn kiến trúc đơn giản hoặc phức tạp hơn trong từng giai đoạn.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào thay đổi thường xuyên, có business value cao và ít coupling nhất?
2. Những dependencies nào chặn modern .NET và có source/replacement path hay không?
3. Authentication/session hiện tại hoạt động thế nào giữa MVC legacy và ứng dụng mới?
4. Stored procedures/schema nào được nhiều modules cùng ghi, và transaction boundaries hiện nằm ở đâu?
5. Business chấp nhận bao nhiêu downtime, dual-run period và migration risk cho từng release?

## Gợi ý tư duy

### Gợi ý 1

Modernization là bài toán quản trị risk và boundaries, không phải chỉ đổi target framework.

### Gợi ý 2

Tìm seam cho phép thay đổi từng phần nhưng tránh tạo hai hệ thống cùng sở hữu một business invariant mà không có contract.

### Gợi ý 3

Một kiến trúc mới tốt phải cải thiện deployability/testability mà không bắt team vận hành distributed complexity chưa cần thiết.

## Cấu trúc trả lời đề xuất

1. Inventory application, dependencies và operational constraints.
2. Phân loại modules theo value, coupling, risk và change frequency.
3. Xác định target architecture tối thiểu cần thiết.
4. Chọn migration seams/boundaries.
5. Thiết kế auth/session và routing coexistence.
6. Xác định data ownership và schema migration strategy.
7. Thiết kế frontend migration theo vertical slices.
8. Xây test safety net và observability trước khi cutover.
9. Rollout/canary/rollback theo từng slice.
10. Định nghĩa exit criteria để retire legacy components.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite-from-scratch là lựa chọn tốt nhất.
- Không mặc định microservices/Kubernetes chỉ vì đang modernization.
- Có inventory dependency/compatibility và migration risk trước khi chọn target.
- Có chiến lược coexistence giữa legacy và modern app.
- Xử lý data ownership/shared database có chủ đích.
- Testing và rollback là phần của architecture, không để cuối dự án.

### Điểm cộng

- Chọn vertical slice có value cao nhưng boundary đủ rõ để pilot.
- Có characterization/integration/E2E tests quanh critical legacy behavior trước khi thay thế.
- Dùng reverse proxy/routing hoặc boundary tương đương để chuyển traffic từng phần nếu phù hợp hạ tầng.
- Tách frontend modernization khỏi backend rewrite khi điều đó giảm coupling/risk.

### Senior+

- Dùng migration fitness criteria: deployment frequency, lead time, error rate, rollback time, unsupported dependency count.
- Có anti-corruption boundary khi legacy data/API model không phù hợp target domain.
- Tránh shared-write ownership kéo dài; nếu phải dùng shared DB tạm thời thì đặt constraints và exit plan rõ.
- Target có thể là modular monolith trên App Service trước; chỉ tách service khi có boundary/scale/ownership evidence.

## Hướng giải quyết tham khảo

Tôi sẽ không nhận yêu cầu “rewrite 6 tháng” hoặc “giữ nguyên mọi thứ” như hai lựa chọn duy nhất. Trước hết cần inventory: framework/dependency compatibility, modules, deployment coupling, authentication/session, shared database writes, stored procedures, external integrations, incident history và test coverage. Sau đó chấm modules theo business value, change frequency, coupling và migration risk để tìm một pilot slice.

Nếu scale và team size chưa tạo nhu cầu distributed architecture, target ban đầu có thể là một ASP.NET Core modular application trên .NET 8 hoặc version được tổ chức hỗ trợ, deploy lên App Service/IIS/container tùy constraints. Tôi không đưa Kubernetes/microservices vào chỉ để gọi là modern. Mục tiêu đầu tiên là supported runtime, repeatable deployment, observability, automated tests và module boundaries tốt hơn.

Strangler migration phù hợp nếu có thể tạo routing/boundary rõ: một feature/route được chuyển sang modern app trong khi phần còn lại vẫn chạy legacy. Tuy nhiên coexistence cần giải quyết auth/session. Tôi ưu tiên identity/token contract chung hoặc gateway/reverse-proxy pattern phù hợp thay vì copy security state tùy tiện. Nếu legacy authentication không tương thích, đó có thể là một workstream nền tảng trước pilot.

Data là phần khó. Shared SQL có thể được giữ tạm thời để giảm migration blast radius, nhưng không nên để cả legacy và modern modules cùng tự do mutate cùng aggregate mãi mãi. Với mỗi slice, xác định owner của writes và contract cho reads/integration. Stored procedures được characterization-test trước khi thay. Nếu schema change phải backward compatible trong giai đoạn coexistence, dùng expand/migrate/contract thay vì breaking migration một lần.

Frontend cũng không nhất thiết rewrite toàn bộ cùng lúc. Có thể thay từng page/workflow bằng Vue/React khi backend contract ổn, giữ shell/navigation chung trong giai đoạn chuyển tiếp. Tôi tránh tạo hai frontend frameworks trong cùng page nếu không có isolation rõ vì sẽ tăng bundle, state và maintenance complexity.

Trước cutover, bổ sung safety net: API/database integration tests cho invariants, Playwright E2E cho critical workflows, contract tests cho external dependencies và production telemetry baseline. CI/CD phải tạo immutable/repeatable artifact, environment config tách khỏi artifact, migration ordering rõ và rollback path đã rehearsal. Với data migration không rollback đơn giản, rollback application phải tương thích schema đã expand.

Tôi rollout từng slice nhỏ, có health checks, logs/traces/metrics, error/latency comparison và business KPI. Chỉ retire legacy code khi traffic đã chuyển, dữ liệu/operations ổn định và rollback window đóng có chủ đích. Rewrite toàn bộ chỉ trở nên hấp dẫn hơn nếu hệ thống đủ nhỏ, coupling không thể tách hợp lý, behavior có test/spec tốt và chi phí dual-run vượt chi phí replacement; ngay cả khi đó vẫn cần staged validation chứ không big-bang vì “code cũ xấu”.

## Mẫu trả lời trong phỏng vấn

“Em sẽ coi đây là migration-risk problem chứ không phải framework-upgrade đơn thuần. Em inventory dependencies, auth, shared DB/stored procedures, critical workflows và deployment trước, rồi chọn một vertical slice có value cao nhưng boundary đủ rõ để pilot.

Với team nhỏ và scale hiện tại, em chưa thấy lý do mặc định chọn microservices hay Kubernetes. Target đầu có thể là modular ASP.NET Core app trên modern .NET với CI/CD, tests và observability tốt. Legacy và modern app coexist qua routing boundary; auth phải có contract chung. Shared DB có thể tồn tại tạm thời nhưng mỗi business area cần write ownership và exit plan, tránh dual-write tùy tiện.

Em xây characterization/integration tests và Playwright cho workflow quan trọng trước cutover, dùng backward-compatible schema changes, rollout từng slice và đo error/latency/business behavior. Rewrite toàn bộ chỉ chọn nếu analysis chứng minh incremental seams quá đắt hoặc không khả thi; không chọn chỉ vì muốn codebase ‘sạch’.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên bạn chọn phụ thuộc trực tiếp vào 40 stored procedures dùng chung với legacy, bạn tiếp tục strangler hay đổi slice? Tiêu chí quyết định là gì?
2. Bạn đề xuất modular monolith, nhưng CTO muốn microservices để các team “deploy độc lập”; bằng chứng nào khiến bạn thay đổi recommendation?
3. Nếu schema migration mới đã ghi dữ liệu theo format mà binary cũ không đọc được, rollback strategy phải thay đổi thế nào?

## Lỗi trả lời thường gặp

- Chọn big-bang rewrite vì “legacy khó maintain” mà không lượng hóa migration risk.
- Chọn microservices/Kubernetes như biểu tượng modernization.
- Bỏ qua authentication/session coexistence.
- Cho cả legacy và modern app cùng ghi shared data không có ownership/contract.
- Đợi đến cuối migration mới bổ sung automated tests và observability.

## Thang điểm 0–10

- **0–2:** Chỉ nói upgrade framework/rewrite code.
- **3–4:** Có incremental migration nhưng thiếu data/auth/rollback reasoning.
- **5–6:** Có boundaries, coexistence, testing và deployment plan hợp lý.
- **7–8:** Quản trị tốt data ownership, compatibility, rollout và complexity cost.
- **9–10:** Có decision criteria rõ cho rewrite vs strangler, target architecture theo evidence, measurable migration outcomes và credible exit/rollback strategy.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- DI lifetime được xác định bởi scope boundary; HTTP request chỉ là một loại scope phổ biến. Background processing cần ownership và scope riêng cho từng unit of work.
- Distributed message processing phải giả định duplicate delivery và ambiguous failure. Retry, idempotency, settlement và reconciliation phải được thiết kế cùng nhau.
- Modernization hiệu quả là quản trị risk theo boundaries và incremental evidence; “modern” không đồng nghĩa với kiến trúc phân tán phức tạp.
- Testing, observability và rollback là thuộc tính của thiết kế production, không phải bước bổ sung sau implementation.

## Mẫu tư duy cần nhớ

- Vẽ lifetime/ownership boundary trước khi sửa DI registration.
- Stabilize trước, rồi dùng evidence để phân biệt các failure hypotheses.
- Thiết kế retry cùng idempotency và failure recovery.
- Chọn complexity theo requirement và operational evidence, không theo xu hướng.
- Migration từng phần cần explicit compatibility, ownership và exit criteria.
