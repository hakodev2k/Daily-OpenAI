# Câu 1 — DI lifetime trong ASP.NET Core: vì sao `Scoped` service bị giữ lâu hơn một request?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, dependency injection, service lifetime, `DbContext`, `BackgroundService`, disposal, concurrency, production diagnostics

## Bối cảnh

Một ASP.NET Core application trên .NET 8 xử lý HTTP requests bằng EF Core. `OrderDbContext` và `OrderService` được đăng ký `Scoped`. Team vừa thêm một `BackgroundService` để định kỳ xử lý orders quá hạn. Developer inject `OrderService` trực tiếp vào constructor của worker vì cho rằng DI container sẽ “tạo scope tự động giống controller”.

Ở một nhánh khác, một singleton cache service giữ reference tới một object được resolve từ request scope thông qua factory code tự viết. Sau deployment, background processing đôi lúc đọc state cũ, có lỗi liên quan đến concurrent EF operations, và memory tăng dần trong load test. HTTP request path riêng lẻ vẫn hoạt động bình thường.

Bạn chưa biết registration đầy đủ, cách worker resolve dependencies, object graph thực tế hay disposal timeline.

## Câu hỏi chính

Hãy giải thích cách root provider, request scope và các lifetime `Transient` / `Scoped` / `Singleton` thực sự hoạt động; vì sao lifetime mismatch có thể dẫn đến captive dependency, shared `DbContext`, stale state hoặc disposal sai; cách bạn chứng minh object đang sống ở scope nào; và cách thiết kế đúng cho cả HTTP request lẫn `BackgroundService`.

## Câu hỏi làm rõ nên cân nhắc

1. `OrderService`, `OrderDbContext` và các dependencies của chúng được đăng ký chính xác bằng lifetime nào?
2. Worker được đăng ký bằng `AddHostedService` hay được tạo theo cơ chế khác, và constructor hiện nhận những gì?
3. Có bật scope validation ở môi trường development/test không, và startup có báo captive dependency không?
4. Background iteration có thể chạy song song hay overlap không; một `DbContext` có bị dùng đồng thời không?
5. Singleton cache đang giữ dữ liệu immutable/value data hay giữ trực tiếp scoped service/entity/context?

## Gợi ý tư duy

### Gợi ý 1

Lifetime của object không được quyết định bởi class gọi nó là controller hay worker; nó phụ thuộc vào provider/scope dùng để resolve object graph.

### Gợi ý 2

Hosted service về bản chất có lifetime dài. Hãy xem điều gì xảy ra nếu một dependency gắn với unit-of-work ngắn lại bị capture vào object sống suốt process.

### Gợi ý 3

Tách câu hỏi “object được tạo ở đâu?” khỏi “object được dispose khi nào?” và “object có thread-safe không?”.

## Cấu trúc trả lời đề xuất

1. Xác nhận registrations và resolution path.
2. Vẽ root provider và các child/request scopes.
3. Giải thích lifetime/disposal theo từng scope.
4. Xác định captive dependencies và shared mutable state.
5. Correlate instance identity với request/worker iteration.
6. Sửa worker bằng explicit scope phù hợp.
7. Loại bỏ scoped object khỏi singleton state.
8. Test concurrency và disposal.
9. Theo dõi EF errors, memory và worker telemetry sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Scoped` không có nghĩa “tự động mỗi request” trong mọi execution context; HTTP request tạo scope, còn background work phải có scope phù hợp.
- Hosted service thông thường là long-lived; không nên capture request-scoped `DbContext`/service vào lifetime dài.
- `DbContext` không được thiết kế để dùng concurrent operations trên cùng instance.
- Scope phải được dispose để dispose các scoped/transient disposable objects mà container theo dõi trong scope đó.
- Singleton không nên giữ reference trực tiếp tới scoped service/entity graph có lifecycle không phù hợp.
- Cần kiểm chứng registrations, instance identity, stack/telemetry và resolution path thay vì chỉ đổi lifetime thành `Transient`.

### Điểm cộng

- Dùng `IServiceScopeFactory`/scope creation trong từng logical background unit-of-work.
- Phân biệt service lifetime với thread safety; `Singleton` không tự động thread-safe.
- Nhận ra đổi `DbContext` thành transient không tự sửa transaction/unit-of-work semantics.
- Bật scope validation trong môi trường phù hợp để bắt một số lifetime mismatch sớm.

### Senior+

- Xác định boundary của scope theo message/job/iteration thay vì theo timer process lifetime.
- Nếu xử lý song song, mỗi unit-of-work có scope/`DbContext` riêng và concurrency được giới hạn có chủ đích.
- Cache chỉ giữ data representation phù hợp, không giữ infrastructure object hoặc tracked entity graph vô hạn.

## Hướng giải quyết tham khảo

Trong ASP.NET Core, container có root service provider. Mỗi HTTP request thường được framework tạo một scope và các service `Scoped` resolve trong cùng request scope sẽ dùng chung instance cho scope đó. Điều quan trọng là `Scoped` không có semantic “request” tuyệt đối; nó có semantic “một instance trong một DI scope”. Một background worker không tự nhiên có request scope.

`IHostedService`/`BackgroundService` được host quản lý như long-lived service. Nếu một scoped dependency bị capture vào object sống từ root provider, lifetime thực tế có thể bị kéo dài hoặc scope validation có thể phát hiện cấu hình không hợp lệ, tùy cách registration/resolution được thực hiện. Với `DbContext`, điều này đặc biệt nguy hiểm: context giữ change tracker/unit-of-work state và không phù hợp để nhiều operation concurrent dùng chung một instance.

Tôi sẽ lấy registration graph thực tế trước. Trong diagnostics/test có thể log một instance identifier cho scope/service/context cùng operation ID để chứng minh các iteration có đang dùng cùng object hay không. Tôi cũng kiểm tra exception stack, EF Core diagnostics và memory profile để phân biệt captive object graph với cache tăng hợp lệ hoặc nguyên nhân khác.

Worker nên inject dependency có lifetime an toàn như `IServiceScopeFactory`, rồi tạo scope cho mỗi logical batch/message/iteration; resolve `OrderService` bên trong scope và dispose scope sau khi work hoàn tất. Nếu chạy nhiều items song song, không chia sẻ cùng scoped service/context giữa tasks; mỗi unit-of-work cần scope riêng hoặc thiết kế rõ ràng tương đương. Đồng thời phải propagate cancellation từ `stoppingToken` và tránh overlap không kiểm soát.

Singleton cache không nên giữ `DbContext`, repository scoped hoặc tracked entity graph. Nếu cache cần dữ liệu, lưu immutable/value representation với invalidation/size policy rõ ràng. Việc đổi tất cả sang `Transient` chỉ che triệu chứng: một transient resolved từ root có thể vẫn có disposal/lifetime implications, và transaction boundary vẫn sai.

Testing nên gồm scope identity test, worker nhiều iterations, concurrent processing, cancellation/shutdown và memory soak test. Production telemetry nên có worker iteration duration, active concurrency, failures, EF Core exceptions và correlation giữa job ID với dependency calls.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không hiểu `Scoped` là ‘mỗi request’ một cách tuyệt đối; chính xác hơn là một instance trên mỗi DI scope. HTTP pipeline tạo request scope, nhưng `BackgroundService` là long-lived và không tự có request scope cho từng iteration. Nếu worker hoặc singleton capture `OrderService`/`DbContext`, object có thể sống quá boundary mong muốn và một context có thể bị dùng qua nhiều operations hoặc concurrent tasks.

Em sẽ kiểm tra registrations và resolution graph trước, bật scope validation ở môi trường phù hợp, đồng thời log instance IDs theo request/job để chứng minh lifetime thực tế. Với worker, em tạo scope cho từng logical unit-of-work bằng `IServiceScopeFactory`, resolve scoped services trong đó rồi dispose scope. Nếu parallel processing thì mỗi work item có context riêng và concurrency limit rõ ràng.

Em cũng bỏ việc singleton giữ scoped infrastructure object; cache chỉ nên giữ data có lifecycle/invalidation được định nghĩa. Sau đó em test concurrent iterations, cancellation và soak memory thay vì chỉ thấy request đơn lẻ chạy được rồi kết luận fix đúng.”

## Câu hỏi đào sâu

1. Nếu mỗi message tạo một scope mới làm tăng overhead, bạn có gộp 100 messages vào một scope không? Điều gì quyết định boundary?
2. Nếu service không giữ state, tại sao đăng ký nó `Singleton` vẫn có thể sai khi dependency bên dưới là scoped?
3. Bạn vừa đề xuất mỗi parallel work item có scope riêng; transaction cần atomic trên cả batch thì thiết kế thay đổi thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất `Scoped` với HTTP request trong mọi context.
- Sửa bằng cách đổi `DbContext` sang `Singleton` hoặc `Transient` mà không xét unit-of-work.
- Cho rằng singleton mặc định thread-safe.
- Tạo scope nhưng giữ resolved service ra ngoài lifetime của scope.
- Chỉ test một worker iteration, không test overlap/concurrency/disposal.

## Thang điểm 0–10

- **0–2:** Chỉ thuộc định nghĩa ba lifetime, không giải thích scope graph hay failure.
- **3–4:** Nhận ra hosted service cần scope nhưng thiếu disposal/concurrency reasoning.
- **5–6:** Giải thích đúng request scope, captive dependency và `DbContext` lifecycle.
- **7–8:** Có verification, scope boundary, concurrency testing và production telemetry.
- **9–10:** Reasoning rõ về object graph, disposal, unit-of-work, parallelism và cost của các lifetime alternatives.

# Câu 2 — Kubernetes rollout “xanh” nhưng người dùng nhận 503 và request đang chạy bị cắt

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, readiness/liveness, graceful shutdown, rolling deployment, resource limits, observability, incident response

## Bối cảnh

Một ASP.NET Core API được containerize và chạy trên Kubernetes. Deployment có 6 replicas. Release pipeline báo rollout thành công, nhưng trong khoảng 2–4 phút khi deploy, tỷ lệ `503` tăng và một số request upload dài bị cắt giữa chừng. Sau rollout, hệ thống trở lại bình thường.

Manifest hiện có readiness và liveness probes cùng gọi `/health`, `terminationGracePeriodSeconds` đã được cấu hình nhưng team chưa xác nhận application có phản ứng đúng với `SIGTERM`. Deployment dùng rolling update, nhưng chưa rõ `maxUnavailable`, `maxSurge`, startup duration hay thời điểm Pod được đưa vào Service endpoints. Một số Pod có CPU gần limit lúc warm-up.

Một engineer muốn tăng liveness timeout; engineer khác muốn thêm replicas cố định. Business yêu cầu zero/minimal disruption vì API phục vụ transaction quan trọng.

## Câu hỏi chính

Bạn sẽ xử lý incident theo thứ tự nào để xác định 503 đến từ đâu, kiểm tra readiness/liveness và Pod lifecycle, chứng minh hoặc bác bỏ capacity loss, startup failure và shutdown không graceful; sau đó bạn sẽ sửa rollout/application behavior và thiết kế validation/monitoring như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. `503` được trả từ ingress/load balancer/service mesh hay application, và request có tới Pod không?
2. Readiness/liveness `/health` đang kiểm tra những dependencies nào, latency và failure thresholds ra sao?
3. Pod cũ nhận `SIGTERM` rồi mất bao lâu để ngừng nhận traffic và hoàn tất in-flight requests?
4. RollingUpdate strategy (`maxUnavailable`, `maxSurge`) và replica availability thực tế trong incident là gì?
5. CPU throttling, startup time, image pull, migrations hoặc cache warm-up có làm Pod mới ready chậm không?

## Gợi ý tư duy

### Gợi ý 1

“Rollout succeeded” chỉ chứng minh controller đạt trạng thái mong muốn cuối cùng; nó không chứng minh từng giây trong rollout không có user impact.

### Gợi ý 2

Readiness trả lời “có nên nhận traffic?”, liveness trả lời “process có cần restart?”; dùng cùng một check sâu cho cả hai có thể tạo failure amplification.

### Gợi ý 3

Quan sát timeline của endpoint membership, Pod state, probe results, termination và request traces trên cùng một trục thời gian.

## Cấu trúc trả lời đề xuất

1. Đánh giá impact và phạm vi endpoint bị lỗi.
2. Stabilize bằng rollback/pause rollout nếu regression đang tiếp diễn.
3. Dựng timeline deployment–Pod–traffic.
4. Xác định layer phát 503.
5. Correlate readiness, liveness, restarts và endpoints.
6. Kiểm tra capacity/CPU throttling và startup.
7. Kiểm tra SIGTERM/graceful shutdown/in-flight requests.
8. Sửa probes, rollout strategy và app shutdown theo evidence.
9. Chạy deployment test dưới representative load.
10. Alert trên availability trong rollout, không chỉ rollout status.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Ưu tiên giảm impact/rollback nếu release đang gây lỗi.
- Không mặc định tăng probe timeout trước khi biết layer phát 503.
- Phân biệt readiness và liveness về mục đích.
- Kiểm tra Service endpoints/Pod readiness và available capacity trong rollout.
- Kiểm tra application graceful shutdown khi nhận termination signal và request duration thực tế.
- Có deployment/load/failure validation và monitoring theo request success rate.

### Điểm cộng

- Liveness không nên phụ thuộc mù quáng vào transient external dependency nếu việc restart process không giải quyết dependency outage.
- Readiness có thể cần phản ánh khả năng phục vụ traffic nhưng phải tránh flapping.
- CPU limit/throttling trong warm-up có thể kéo dài readiness và làm giảm effective capacity.
- Xem xét `preStop`/termination behavior khi thực sự cần, nhưng không coi sleep cố định là universal fix.

### Senior+

- Tính capacity với `maxUnavailable`/`maxSurge`, warm-up và peak traffic thay vì chỉ tăng replicas cảm tính.
- Định nghĩa drain behavior cho long-running requests; nếu request có thể dài hơn grace period, cần contract/architecture phù hợp thay vì chỉ tăng timeout vô hạn.
- Tách startup/readiness/liveness concerns và kiểm thử rollout như một production behavior.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định 503 được sinh ở layer nào. Nếu ingress trả 503 vì không có healthy backend, hướng điều tra khác với application chủ động trả 503. Tôi sẽ correlate ingress metrics/logs, request traces, Kubernetes events, Pod readiness transitions, endpoint membership, restart count và deployment timeline.

Nếu release đang gây user impact, ưu tiên pause/rollback phiên bản mới nếu rollback an toàn. Sau đó dựng timeline: Pod mới start lúc nào, probe pass lúc nào, Pod cũ chuyển terminating lúc nào, endpoint bị remove lúc nào, request failures nằm ở khoảng nào. Điều này giúp phân biệt capacity gap với application regression.

Readiness và liveness không nên được hiểu giống nhau. Readiness quyết định Pod có phù hợp nhận traffic; liveness là tín hiệu process bị kẹt đến mức restart có ích. Nếu cả hai gọi một health check sâu phụ thuộc SQL/external API, một dependency outage có thể đồng thời loại Pod khỏi traffic và restart hàng loạt, làm incident nặng hơn. Tôi sẽ thiết kế check dựa trên failure semantics thật, không chỉ tách URL cho đẹp.

Với termination, cần xác nhận ASP.NET Core host nhận signal, ngừng nhận work mới theo hosting/network behavior và có đủ thời gian hoàn thành in-flight work trong grace period. Request upload rất dài cần được đánh giá riêng: nếu duration vượt drain budget, có thể cần resumable/direct-to-storage/background workflow tùy requirement; không nên kỳ vọng rolling deployment giữ connection vô hạn.

Rolling strategy phải giữ đủ capacity trong lúc Pod mới warm up. Tôi sẽ kiểm tra `maxUnavailable`, `maxSurge`, CPU requests/limits và throttling. Nếu Pod mới mất 60 giây mới ready nhưng Pod cũ bị giảm quá nhanh, availability có thể tụt dù cuối cùng rollout thành công. Fix có thể là probe/startup tuning, resource sizing, rollout strategy, application startup optimization hoặc nhiều yếu tố kết hợp—chỉ sau evidence.

Validation gồm deploy dưới load, long-running request during rollout, dependency degradation, slow startup và termination test. Alert nên theo 5xx/success rate, ready replicas, restart count, rollout duration, CPU throttling và request cancellation; pipeline success không phải availability SLO.

## Mẫu trả lời trong phỏng vấn

“Em sẽ chưa tăng timeout hay replicas ngay. Trước tiên em xác định 503 đến từ ingress hay app, rồi đặt deployment timeline cạnh Pod readiness, endpoints, restarts và request traces. Nếu release đang tiếp tục gây impact, em pause hoặc rollback trước khi deep-dive.

Em tách readiness khỏi liveness theo semantics: readiness quyết định nhận traffic, liveness chỉ nên restart khi process thực sự không recover được. Em cũng kiểm tra rolling strategy và capacity trong warm-up, đặc biệt CPU throttling và thời gian Pod mới ready.

Với request bị cắt, em test termination path: Pod nhận SIGTERM lúc nào, endpoint removal/drain diễn ra ra sao, app shutdown bao lâu và request duration có vượt grace period không. Fix có thể nằm ở probes, resources, rollout strategy hoặc graceful shutdown; em chỉ chọn sau khi timeline chứng minh. Sau đó em chạy deployment test dưới load và alert theo user-facing 5xx trong rollout, không chỉ theo trạng thái Deployment.”

## Câu hỏi đào sâu

1. Nếu database outage làm readiness của toàn bộ Pods fail cùng lúc, bạn muốn hệ thống phản ứng thế nào và vì sao?
2. Bạn đề xuất tăng `terminationGracePeriodSeconds`; nếu có upload kéo dài 30 phút thì có tiếp tục tăng lên 30 phút không?
3. Nếu `maxUnavailable=0` nhưng vẫn có 503 trong rollout, những giả thuyết nào còn lại?

## Lỗi trả lời thường gặp

- Đồng nhất readiness và liveness.
- Chỉ tăng replica count mà không đo capacity/timeline.
- Thấy rollout thành công rồi loại trừ deployment lifecycle.
- Dùng sleep/preStop như fix mặc định mà không kiểm chứng drain behavior.
- Không test deployment dưới traffic và long-running requests.

## Thang điểm 0–10

- **0–2:** Chỉ chỉnh probe timeout/restart Pod.
- **3–4:** Biết readiness/liveness nhưng thiếu incident timeline và stabilization.
- **5–6:** Điều tra đúng layer, capacity, probes và shutdown.
- **7–8:** Có evidence-driven remediation, rollout/load testing và observability.
- **9–10:** Kết nối Kubernetes lifecycle, application semantics, capacity engineering và long-request architecture thành một kế hoạch có điều kiện rõ ràng.

# Câu 3 — Modernize portal .NET Framework trên IIS: migrate từng bước hay rewrite lên .NET 10?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** .NET modernization, architecture, IIS, ASP.NET Core, Azure App Service, compatibility, data boundaries, deployment, testing, migration strategy, technical decision-making

## Bối cảnh

Một enterprise management portal khoảng 8 năm tuổi chạy ASP.NET MVC trên .NET Framework 4.5 và IIS/Windows Server. Hệ thống có khoảng 30 modules, dùng SQL Server chung, một số stored procedures, Windows-specific libraries, jQuery frontend, scheduled jobs trong application process và tích hợp 6 third-party systems.

Business muốn giảm deployment risk, cải thiện security/supportability và cho phép team phát triển feature mới nhanh hơn. Có đề xuất rewrite toàn bộ lên .NET 10 + React + Kubernetes. Đề xuất khác là nâng từng phần sang ASP.NET Core/.NET hiện đại, giữ database và một phần UI trong giai đoạn chuyển tiếp. Downtime cho phép rất hạn chế; release vẫn phải tiếp tục trong 12 tháng migration.

Team có 6 developers và QA automation hiện chưa cover đầy đủ critical workflows. Không có requirement bắt buộc Kubernetes hoặc Microservices. Một vài third-party SDK cũ chưa rõ compatibility với modern .NET.

## Câu hỏi chính

Bạn sẽ xây dựng modernization strategy như thế nào: thu thập evidence gì trước, chia migration boundaries ra sao, lựa chọn target runtime/hosting/frontend thế nào, xử lý dependencies và shared database ra sao, đảm bảo releases song song/rollback thế nào, và tiêu chí nào khiến bạn chọn incremental migration thay vì rewrite hoặc ngược lại?

## Câu hỏi làm rõ nên cân nhắc

1. Modules nào tạo business value/thay đổi thường xuyên nhất, và modules nào ổn định nhưng phụ thuộc sâu vào .NET Framework/Windows?
2. Test coverage hiện tại của critical user journeys, integration contracts và database behavior đến đâu?
3. Có hard dependency nào vào `System.Web`, Windows Authentication, COM, GAC/native libraries hoặc vendor SDK chỉ hỗ trợ .NET Framework không?
4. Deployment/hosting mục tiêu có constraint về Windows/Linux, Azure App Service, on-prem networking hoặc compliance không?
5. Shared SQL schema có ownership rõ theo module không, và cross-module transactions/stored procedures đang chặt đến mức nào?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng target architecture. Bắt đầu bằng inventory, dependency graph, business risk và characterization tests.

### Gợi ý 2

Modernization có nhiều dimensions: runtime, hosting, application boundaries, frontend, data và deployment. Không nhất thiết đổi tất cả trong cùng một bước.

### Gợi ý 3

Mỗi migration slice cần coexistence, observability và rollback path; “compile thành công” chưa phải migration thành công.

## Cấu trúc trả lời đề xuất

1. Xác định business goals và success metrics.
2. Inventory code/dependencies/runtime/hosting/data integrations.
3. Baseline production behavior và critical journeys.
4. Phân loại modules theo value, coupling và migration risk.
5. Chọn target runtime/hosting dựa trên constraints.
6. Thiết kế coexistence boundary và routing.
7. Migrate một vertical slice nhỏ nhưng có giá trị.
8. Xử lý database/contracts và deployment compatibility.
9. Mở rộng theo evidence, không theo big-bang plan.
10. Định nghĩa rollback, telemetry và exit criteria cho legacy.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite, Microservices hoặc Kubernetes là modernization tốt hơn.
- Inventory dependencies và compatibility trước khi cam kết target.
- Có characterization/integration/E2E tests cho behavior quan trọng trước và trong migration.
- Chia migration thành vertical slices/coexistence boundaries có thể release độc lập khi khả thi.
- Shared database cần ownership/transaction analysis; không tách database chỉ để “trông giống microservices”.
- Có rollout, rollback và observability cho từng slice.

### Điểm cộng

- Tách runtime modernization khỏi frontend rewrite để giảm simultaneous change nếu không có business reason phải làm cùng lúc.
- Đánh giá Azure App Service trước Kubernetes nếu operational requirements không đòi orchestration complexity.
- Dùng contract tests cho third-party integrations và anti-corruption/adapters ở boundary phù hợp.
- Chọn supported modern .NET target theo compatibility/lifecycle requirements tại thời điểm implementation, không hard-code vì “mới nhất luôn tốt nhất”.

### Senior+

- Có dependency heat map và migration sequencing theo coupling/value/risk.
- Dùng strangler-style routing/coexistence khi phù hợp nhưng không biến pattern thành mục tiêu.
- Định nghĩa data ownership dần dần trước khi cân nhắc service extraction.
- Có measurable exit criteria: legacy traffic/modules giảm, deployment lead time, change failure rate, vulnerability/support posture, performance và defect rate.

## Hướng giải quyết tham khảo

Tôi sẽ không phê duyệt “.NET 10 + React + Kubernetes rewrite” chỉ vì đó là stack mới. Trước hết cần xác định modernization đang tối ưu điều gì: security/supportability, deployment frequency, maintainability, cloud hosting hay scalability. Sau đó inventory application: projects, NuGet/vendor dependencies, `System.Web` usage, authentication, Windows-only APIs, scheduled jobs, filesystem assumptions, stored procedures, shared transactions và integration contracts.

Bước tiếp theo là tạo safety net. Với legacy system thiếu tests, tôi ưu tiên characterization tests quanh critical business behavior, API/integration tests và Playwright E2E cho journeys có rủi ro cao. Mục tiêu không phải đạt 100% coverage mà là phát hiện behavior regression khi thay runtime/boundary.

Tôi sẽ phân loại modules theo business change frequency, coupling và compatibility. Một module có boundary tương đối rõ, giá trị cao và ít Windows-only dependency là candidate tốt cho first vertical slice. Có thể đưa endpoint mới sang ASP.NET Core/modern .NET và route traffic theo path/feature, trong khi legacy vẫn phục vụ phần còn lại. Cách coexist cụ thể phụ thuộc network/auth/session constraints; không giả định reverse proxy là miễn phí về complexity.

Database chung chưa cần bị tách ngay. Tôi sẽ map ownership và cross-module transactions trước. Trong giai đoạn đầu, modernized slice có thể dùng cùng SQL Server nếu điều đó giữ consistency và giảm migration risk, nhưng cần tránh để schema coupling tiếp tục tăng. Khi ownership rõ và business cần independent scaling/deployment, mới đánh giá data separation/messaging.

Frontend cũng không nhất thiết rewrite đồng thời. Nếu jQuery UI gây velocity/maintainability issue, có thể migrate theo page/feature sang React hoặc Vue; nếu không, ưu tiên backend/runtime trước để giảm số biến thay đổi. Tương tự, hosting nên dựa trên operational need: App Service có thể đủ đơn giản và phù hợp; Kubernetes chỉ đáng chọn nếu requirements về orchestration, portability, scale hoặc platform strategy bù được operational cost.

Scheduled jobs trong web process cần được inventory vì hosting/recycle semantics có thể gây duplicate/missed execution. Tùy workload, có thể chuyển sang Worker Service, Functions hoặc scheduler phù hợp, nhưng phải thiết kế idempotency/locking/observability trước.

Mỗi slice cần compatibility contract, deployment order, feature flag/routing strategy nếu phù hợp, telemetry so sánh legacy/new path và rollback. Tôi sẽ không remove legacy implementation cho đến khi production evidence đủ. Rewrite toàn bộ chỉ trở nên hấp dẫn hơn nếu code/data boundaries quá khó untangle, business semantics đã thay đổi lớn, coexistence cost vượt migration cost, và organization có đủ test/parallel-delivery capacity—nhưng vẫn phải chứng minh bằng analysis thay vì cảm giác “code cũ xấu”.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách mục tiêu modernization khỏi việc chọn stack. Trước tiên em inventory dependencies, Windows-specific APIs, `System.Web`, authentication, jobs, shared SQL transactions và third-party SDKs; đồng thời baseline critical business journeys bằng characterization/integration/Playwright tests. Với 30 modules và vẫn phải release feature trong 12 tháng, em thiên về incremental migration trừ khi dependency analysis chứng minh coexistence gần như không khả thi.

Em chọn một vertical slice có business value nhưng coupling thấp, đưa nó sang supported modern .NET và host theo requirement thực tế. Em không mặc định Kubernetes; nếu App Service đáp ứng availability/scale/operations thì complexity thấp hơn. Database có thể tạm dùng chung, nhưng em làm rõ ownership và ngăn coupling mới thay vì tách DB ngay.

Em cũng không bắt buộc rewrite frontend cùng lúc. Runtime, hosting và UI có thể được migrate theo các nhịp khác nhau để giảm blast radius. Mỗi slice phải có contract tests, telemetry, routing/rollback và production comparison. Chỉ khi evidence cho thấy legacy boundaries không thể tách hợp lý hoặc business semantics cần xây lại lớn thì em mới nghiêng mạnh hơn về rewrite.”

## Câu hỏi đào sâu

1. Bạn đề xuất giữ shared SQL Server giai đoạn đầu; làm sao ngăn module mới tiếp tục phụ thuộc trực tiếp vào bảng của module legacy khác?
2. Nếu vendor SDK quan trọng chỉ chạy .NET Framework nhưng module đó cần feature mới ngay, bạn sẽ tạo boundary tạm thời thế nào và chấp nhận trade-off gì?
3. Ban lãnh đạo yêu cầu Kubernetes vì “đó là chuẩn tương lai”; bạn sẽ đưa ra evidence/decision criteria nào thay vì tranh luận theo sở thích công nghệ?

## Lỗi trả lời thường gặp

- Chọn rewrite vì code cũ khó đọc mà không định lượng migration risk.
- Đổi runtime, frontend, database architecture và hosting cùng lúc không có lý do.
- Chọn Microservices/Kubernetes như mục tiêu thay vì công cụ.
- Không tạo regression safety net trước khi thay behavior.
- Không có coexistence/rollback nên mỗi migration slice trở thành big-bang nhỏ.

## Thang điểm 0–10

- **0–2:** Chỉ chọn stack mới và đề xuất rewrite.
- **3–4:** Có migration phases nhưng thiếu dependency/data/testing/rollback analysis.
- **5–6:** Có inventory, incremental slices, compatibility và safety net hợp lý.
- **7–8:** Cân bằng runtime/hosting/data/frontend, có production coexistence và measurable criteria.
- **9–10:** Đưa ra strategy dựa trên business value, coupling, operational cost, data ownership, evidence và khả năng đảo ngược quyết định.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- DI lifetime phải được hiểu theo **scope/object graph/disposal boundary**, không chỉ theo nhãn `Scoped` / `Singleton` / `Transient`.
- Production rollout trên Kubernetes là một **traffic + capacity + process lifecycle problem**, không chỉ là trạng thái cuối cùng của Deployment.
- Modernization tốt giảm rủi ro và tăng khả năng thay đổi; không đồng nghĩa phải rewrite hoặc chọn kiến trúc phức tạp nhất.
- Với mọi production symptom, cần nối telemetry thành timeline để phân biệt correlation với root cause.
- Testing phải nhắm vào failure modes: concurrency, deployment transition, compatibility và rollback—not chỉ happy path.

## Mẫu tư duy cần nhớ

- **Clarify lifecycle before changing lifetime.**
- **Stabilize before deep investigation.**
- **Observe before guessing.**
- **Separate modernization dimensions to reduce blast radius.**
- **Prefer reversible architecture decisions when evidence is incomplete.**
