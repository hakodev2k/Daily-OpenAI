# Câu 1 — Cosmos DB RU tăng mạnh dù traffic gần như không đổi: partition key và query fan-out đang làm gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, logical partition, query routing, RU consumption, indexing, data modeling, observability

## Bối cảnh

Một ASP.NET Core API phục vụ hệ thống event-management lưu `Registration` documents trong Cosmos DB. Container được tạo từ giai đoạn đầu với partition key `/tenantId`. Mỗi tenant có từ vài trăm đến vài triệu registrations.

Một endpoint mới cho operations team cho phép tìm registrations theo `email`, `status` và khoảng thời gian nhưng request không luôn có `tenantId`. Sau rollout:

- request volume chỉ tăng khoảng 8%;
- p95 của endpoint tăng từ dưới 300 ms lên hơn 2 giây ở một số thời điểm;
- tổng RU consumption tăng gần 3 lần;
- một số tenant lớn bị throttling nhiều hơn;
- CPU của ASP.NET Core application bình thường;
- developer đề xuất “tăng RU/s vì Cosmos DB là NoSQL nên query nào cũng scale ngang được”.

Team chưa kiểm tra query metrics, partition distribution hoặc execution diagnostics.

## Câu hỏi chính

Hãy giải thích partition key ảnh hưởng thế nào tới query routing, fan-out và RU cost trong scenario này. Vì sao traffic gần như không đổi nhưng RU và latency vẫn có thể tăng mạnh? Bạn sẽ xác minh hypothesis bằng evidence nào và quyết định giữa sửa query/API contract, index, data model, partition strategy hoặc tăng throughput như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Operations search có bắt buộc cross-tenant hay có thể yêu cầu tenant scope trong phần lớn use case?
2. Distribution của registrations theo `tenantId` có skew lớn đến mức nào và tenant lớn nhất chiếm bao nhiêu workload?
3. Query diagnostics cho biết request chạm bao nhiêu partitions và RU charge phân bố thế nào?
4. Composite/filter requirements thực tế là gì, và indexing policy hiện tại có hỗ trợ query shape này không?
5. Freshness requirement của operations search có cho phép một read model/search index riêng hay phải đọc trực tiếp source container?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng throughput. Trước tiên xác định request có partition key hay phải tìm trên nhiều partitions.

### Gợi ý 2

Partition key vừa là data-distribution decision vừa là query-routing contract. Một access pattern mới có thể làm assumption ban đầu không còn phù hợp.

### Gợi ý 3

Tách ba vấn đề: routing/fan-out, indexing/query shape và hot/skewed workload. Mỗi vấn đề cần evidence và cách sửa khác nhau.

## Cấu trúc trả lời đề xuất

1. Làm rõ access patterns và cross-tenant requirement.
2. Giải thích logical partition và routing theo partition key.
3. Thu request charge, query diagnostics và partition-level distribution.
4. So sánh query có `tenantId` với query cross-partition trên representative data.
5. Kiểm tra indexing policy/query shape.
6. Xác định hot partition/skew nếu có.
7. Chọn giải pháp ít complexity nhất đáp ứng requirement.
8. Load-test với tenant size distribution thực tế.
9. Monitor RU/request, throttling, p95/p99 và partition hot spots.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Partition key quyết định cách dữ liệu được phân vùng và cho phép request được route hiệu quả khi key được biết.
- Query không có partition key có thể phải fan-out trên nhiều partitions; cost phụ thuộc dữ liệu/query/indexing và phải đo bằng request charge/diagnostics.
- “NoSQL scale ngang” không có nghĩa mọi access pattern có cost tương đương.
- Tăng throughput có thể giảm throttling nhưng không tự sửa query shape hoặc data model kém phù hợp.
- Cần phân biệt cross-partition cost với hot/skewed partition.

### Điểm cộng

- Đề xuất thay API contract để tenant-scoped search là default nếu business cho phép.
- Nếu cross-tenant search là use case quan trọng và độc lập, cân nhắc read model/search store được thiết kế cho access pattern đó thay vì phá source model ngay.
- Kiểm tra indexing metrics/policy trước khi thêm index một cách máy móc.
- Dùng representative tenant cardinality trong performance tests.

### Senior+

- Nhận ra partition-key migration là thay đổi data architecture lớn; không chọn chỉ để chữa một endpoint mới.
- Phân tích consistency/freshness nếu tạo secondary read model hoặc Elasticsearch-based operational search.
- Xác định SLO và cost budget theo RU/request thay vì chỉ theo tổng RU/s.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu từ access pattern. Nếu endpoint thường có thể biết `tenantId`, tôi ưu tiên tenant-scoped query vì partition key cho phép Cosmos DB route request hẹp hơn. Nếu endpoint thực sự phải search toàn hệ thống, tôi coi đó là một access pattern khác cần được đo và có thể cần read model riêng.

Tôi thu diagnostics của cả query tốt và query chậm: request charge, latency, throttling và số partition/range được chạm. Sau đó kiểm tra indexing policy và query shape cho `email`, `status`, thời gian. Tôi không mặc định thêm composite index; phải xem query cụ thể và metrics.

Nếu RU tăng chủ yếu vì cross-partition fan-out, tăng RU/s chỉ là capacity mitigation. Có thể hữu ích để stabilize incident, nhưng long-term tôi sẽ sửa API contract hoặc thiết kế read path phù hợp. Nếu operations cần global search với nhiều filter và chấp nhận eventual consistency, một search/read model riêng có thể hợp lý; nhưng nó thêm synchronization, failure recovery và observability nên chỉ chọn khi requirement chứng minh giá trị.

Nếu throttling tập trung ở tenant lớn, tôi kiểm tra distribution/hot partition thay vì kết luận fan-out là toàn bộ root cause. Thay partition key là migration lớn, cần đánh giá toàn bộ read/write patterns, data movement, coexistence và rollback.

Tôi sẽ load-test bằng dữ liệu có tenant-size skew giống production và theo dõi RU/request, p95/p99, throttled requests và partition-level hot spots. Recommendation cuối cùng phụ thuộc requirement cross-tenant, freshness và cost target.

## Mẫu trả lời trong phỏng vấn

“Traffic tăng ít nhưng RU có thể tăng mạnh nếu query mới thay đổi access pattern. Với `/tenantId`, request biết tenant có thể được route hẹp; search không có tenant có thể fan-out và cost tăng theo query/data/indexing. Tôi sẽ chứng minh bằng request charge và query diagnostics chứ không suy ra từ tổng RU.

Tôi cũng tách fan-out khỏi hot partition. Nếu tenant lớn bị throttling riêng, distribution có thể là vấn đề khác. Tăng RU/s có thể dùng để stabilize nhưng không phải default root-cause fix.

Nếu business cho phép, tôi làm tenant-scoped search thành contract chính. Nếu global operations search là requirement quan trọng, tôi đánh giá read model/search store riêng và chấp nhận cost eventual consistency/synchronization. Tôi chỉ đổi partition strategy sau khi inventory toàn bộ access patterns vì đó là migration data architecture, không phải query tweak.”

## Câu hỏi đào sâu

1. Nếu global search phải strong-consistent với write path, recommendation về secondary read model thay đổi thế nào?
2. Nếu query đã có `tenantId` nhưng một tenant cực lớn vẫn throttling, bạn điều tra tiếp gì?
3. Tôi đề xuất đổi partition key ngay sang `/email`; bạn cần chứng minh những rủi ro nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- Coi tăng RU/s là fix duy nhất.
- Nói cross-partition query luôn xấu mà không xét business requirement và đo cost.
- Đổi partition key theo một endpoint mà không inventory toàn workload.
- Không phân biệt fan-out với hot partition.
- Thêm index không dựa trên query diagnostics.

## Thang điểm 0–10

- **0–2:** Chỉ nói scale RU hoặc thêm index.
- **3–4:** Biết partition key nhưng không giải thích routing/cost hoặc evidence.
- **5–6:** Có fan-out reasoning, diagnostics và API/data-model options.
- **7–8:** Phân biệt hot partition, indexing, read model và migration trade-offs.
- **9–10:** Kết nối access pattern → partition architecture → measurable RU economics → consistency/cost/operational trade-offs rõ ràng.

# Câu 2 — Service Bus backlog tăng nhưng scale consumer không cứu được: lock expiry, retry hay downstream saturation?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, at-least-once delivery, message lock, retries, idempotency, downstream failure, SQL Server, observability, incident response

## Bối cảnh

Một order-integration service nhận messages từ Azure Service Bus queue và ghi trạng thái vào SQL Server trước khi gọi third-party fulfillment API. Bình thường queue depth gần 0. Sau một release buổi chiều:

- active message count tăng liên tục;
- consumer instances được scale từ 4 lên 12 nhưng throughput chỉ tăng nhẹ;
- third-party API p95 tăng từ khoảng 400 ms lên 6–10 giây và thỉnh thoảng timeout;
- duplicate business operations bắt đầu xuất hiện ở fulfillment provider;
- một số messages được xử lý lại;
- SQL CPU tăng nhưng chưa đạt saturation;
- DLQ tăng chậm;
- team chưa biết lock duration, retry policy, handler concurrency và idempotency implementation hiện tại có tương thích workload mới không.

Operations muốn tăng concurrency mạnh để “drain queue càng nhanh càng tốt”.

## Câu hỏi chính

Bạn sẽ xử lý incident theo trình tự nào từ impact → stabilization → evidence → competing hypotheses → root cause → remediation? Hãy giải thích vì sao scale/concurrency có thể làm tình hình xấu hơn khi downstream chậm, cách message lock/retry/duplicate delivery liên quan tới symptom, và thiết kế idempotency/telemetry nào cần có.

## Câu hỏi làm rõ nên cân nhắc

1. Business side effect nào ở fulfillment provider có thể lặp lại và provider có hỗ trợ idempotency key không?
2. Handler mất bao lâu ở p50/p95/p99 so với lock/renewal behavior hiện tại?
3. Message được complete ở thời điểm nào so với SQL commit và external API call?
4. Retry xảy ra ở Service Bus processor, HTTP client, application logic hay cả ba tầng?
5. Queue depth tăng vì incoming rate vượt processing capacity hay vì redelivery/retry đang khuếch đại workload?

## Gợi ý tư duy

### Gợi ý 1

Backlog là symptom của capacity mismatch, nhưng capacity bottleneck có thể nằm ở downstream chứ không phải số consumer.

### Gợi ý 2

At-least-once delivery nghĩa là duplicate processing phải được xem là normal failure mode cần thiết kế, không phải sự kiện “không thể xảy ra”.

### Gợi ý 3

Correlate message delivery count, processing duration, lock/renewal, HTTP dependency latency và business idempotency key. Scale chỉ sau khi biết saturation point.

## Cấu trúc trả lời đề xuất

1. Định lượng impact: backlog age, order delay, duplicate fulfillment.
2. Giảm blast radius của duplicate side effects.
3. Giới hạn concurrency/retry để bảo vệ downstream nếu cần.
4. Thu queue, processor, dependency và database telemetry.
5. Lập hypotheses: downstream saturation, lock expiry, retry amplification, SQL contention, release regression.
6. Xác minh processing timeline của representative messages.
7. Sửa idempotency và retry/timeout/concurrency policy.
8. Drain backlog có kiểm soát.
9. Test failure paths và duplicate delivery.
10. Alert theo queue age, delivery count, dependency latency và duplicate rate.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Scale consumer không tạo thêm capacity cho dependency đang saturated; có thể tăng pressure và timeout.
- Service Bus processing phải chịu được duplicate delivery; handler cần idempotency ở business side effects.
- Retry ở nhiều tầng có thể nhân request volume và kéo dài backlog.
- Message lock/processing duration cần được quan sát; không được giả định message chỉ được xử lý một lần.
- Stabilization ưu tiên ngăn duplicate fulfillment và bảo vệ downstream trước khi tối đa throughput.

### Điểm cộng

- Dùng stable business operation/idempotency key với provider nếu API hỗ trợ; nếu không, thiết kế deduplication/inbox state ở boundary phù hợp.
- Không giữ database transaction mở xuyên external network call.
- Phân biệt transient retry với poison/permanent failure và DLQ handling.
- Theo dõi oldest-message age thay vì chỉ queue count.
- Có bounded concurrency/bulkhead và backoff có jitter cho downstream.

### Senior+

- Phân tích transaction boundary giữa SQL state và external side effect; nhận ra không thể có atomic transaction đơn giản xuyên Service Bus + SQL + third-party API.
- Đề xuất state machine/outbox-style workflow khi reliability requirement đủ cao, nhưng không thêm distributed architecture nếu business flow đơn giản hơn có thể xử lý bằng idempotent state transition.
- Thiết kế replay/recovery procedure có audit để drain backlog sau incident.

## Hướng giải quyết tham khảo

Tôi ưu tiên business impact: duplicate fulfillment nghiêm trọng hơn việc queue chậm vài phút. Nếu provider đang degraded, tăng concurrency từ 12 lên cao hơn có thể làm timeout nhiều hơn. Tôi sẽ tạm giới hạn concurrency ở mức downstream chịu được, giảm retry amplification và nếu cần pause một phần processing để ngăn side effect lặp.

Evidence cần correlate theo message ID/business order ID: delivery count, dequeue/receive time, handler duration, lock/renewal events, SQL operation, HTTP request, timeout và settlement. Tôi cũng kiểm tra release diff vì incident bắt đầu sau deployment nhưng không giả định release là root cause duy nhất.

Idempotency phải gắn với business operation. Nếu fulfillment provider hỗ trợ idempotency key, tôi gửi key ổn định theo operation. Ở phía consumer, tôi lưu trạng thái xử lý/deduplication sao cho redelivery không tạo side effect lần hai. Cần thiết kế race khi hai deliveries cùng đến; chỉ `SELECT` rồi `INSERT` không atomic có thể vẫn duplicate.

Retry phải có ownership. Tôi inventory retry ở Service Bus processor, HTTP policy và application. Với downstream timeout, retry có exponential backoff/jitter và giới hạn; permanent failures đi đường khác/DLQ. Tôi không giữ SQL transaction mở trong lúc chờ HTTP nhiều giây.

Sau stabilization, tôi drain backlog theo bounded rate, theo dõi oldest-message age, completion rate, delivery count, provider p95/error rate, SQL waits và DLQ. Tests phải bao gồm duplicate delivery đồng thời, timeout sau khi provider đã nhận request nhưng client chưa nhận response, process crash trước settlement và provider outage kéo dài.

## Mẫu trả lời trong phỏng vấn

“Tôi không tăng concurrency ngay vì bottleneck hiện có dấu hiệu nằm ở fulfillment API. Mục tiêu đầu tiên là ngăn duplicate business side effects và tránh retry storm. Tôi sẽ correlate từng order với Service Bus delivery count, handler duration, lock behavior, SQL state và HTTP dependency trace.

Vì delivery là at-least-once, consumer phải idempotent. Tôi dùng stable business key và provider idempotency key nếu có; phía mình cũng cần atomic state/deduplication để hai deliveries concurrent không cùng tạo fulfillment. Tôi inventory retry ở mọi tầng vì ba retry policies chồng nhau có thể khuếch đại traffic.

Tôi sẽ đặt bounded concurrency theo downstream capacity, timeout/backoff hợp lý, không giữ DB transaction xuyên network call, rồi drain backlog có kiểm soát. Recovery được chứng minh bằng queue age giảm, duplicate rate về 0 và dependency latency ổn định, không chỉ bằng active message count.”

## Câu hỏi đào sâu

1. Nếu provider xử lý request thành công nhưng client timeout trước khi nhận response và provider không hỗ trợ idempotency key, bạn thiết kế reconciliation thế nào?
2. Nếu lock renewal hoạt động tốt nhưng messages vẫn redeliver, những failure path nào khác bạn kiểm tra?
3. Tôi muốn `MaxConcurrentCalls` thật lớn vì SQL còn dư CPU; bạn phản biện bằng metric nào?

## Lỗi trả lời thường gặp

- Scale consumer theo queue depth mà bỏ qua downstream capacity.
- Tin rằng message ID tự động ngăn mọi duplicate business side effect.
- Retry vô hạn hoặc retry đồng thời ở nhiều tầng.
- Giữ transaction SQL mở trong external API call dài.
- Chỉ monitor queue count, không monitor queue age/delivery count/dependency saturation.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất scale hoặc retry.
- **3–4:** Nhận ra duplicate nhưng thiếu transaction/idempotency reasoning.
- **5–6:** Có stabilization, evidence, bounded concurrency và retry policy.
- **7–8:** Có atomic idempotency, lock/delivery analysis, failure-path tests và telemetry.
- **9–10:** Xử lý được distributed side-effect ambiguity, recovery/reconciliation và capacity trade-offs ở mức production.

# Câu 3 — Thiết kế document/file service: backend proxy toàn bộ file hay direct upload vào Blob Storage?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS, security, large-file upload, metadata, asynchronous processing, SQL, Service Bus/Functions alternatives, reliability, observability

## Bối cảnh

Một internal employee platform cần module quản lý tài liệu. Người dùng upload PDF/image, xem metadata, download và một số file cần virus scanning + thumbnail generation. Dự kiến ban đầu 2.000 active users/ngày nhưng file có thể từ vài KB đến 1 GB. Hệ thống ASP.NET Core hiện chạy Azure App Service và dùng SQL Server.

Product yêu cầu:

- file không được public;
- authorization theo employee/project;
- upload lớn không làm web API mất ổn định;
- có audit ai upload/download;
- scanning có thể mất vài phút;
- người dùng không được download file chưa scan xong;
- phải có retry/recovery nếu scanning service lỗi;
- team đang cân nhắc backend proxy mọi byte, direct browser upload bằng SAS, hoặc đưa cả workflow vào một microservice mới.

Chưa có requirement về independent team ownership hoặc scale buộc phải tách microservice.

## Câu hỏi chính

Bạn sẽ thiết kế document/file service này thế nào? Hãy làm rõ API, metadata/data model, upload/download authorization, Blob Storage access, SAS/Managed Identity, scanning workflow, consistency/state transitions, retry/idempotency, observability, deployment và failure recovery. So sánh backend proxy với direct upload và giải thích khi nào bạn giữ module trong Modular Monolith/App Service, khi nào mới tách service riêng.

## Câu hỏi làm rõ nên cân nhắc

1. File 1 GB có phổ biến hay chỉ là upper bound, và client/network có cần resumable upload không?
2. Virus scanning service là synchronous API, queue-based service hay sản phẩm bên ngoài có callback?
3. Audit download cần ghi mọi byte-range/request hay chỉ successful authorized access event?
4. File retention, legal deletion và versioning requirements là gì?
5. Authorization có thể thay đổi sau upload và download URL được phép sống bao lâu?

## Gợi ý tư duy

### Gợi ý 1

Tách control plane khỏi data plane: API có thể quyết định quyền và lifecycle mà không nhất thiết proxy mọi byte.

### Gợi ý 2

Direct upload giảm tải application nhưng chuyển một phần security/reliability responsibility sang token scope, expiry, blob naming và post-upload verification.

### Gợi ý 3

Model file lifecycle như state machine: initiated → uploaded → scanning → available/rejected/failed. Retry phải đi cùng idempotency và authorization phải được kiểm tra ở đúng boundary.

## Cấu trúc trả lời đề xuất

1. Chốt file size/distribution, security và freshness requirements.
2. Thiết kế metadata record và lifecycle states.
3. Chọn upload path theo file size/load.
4. Thiết kế private Blob container và identity/access model.
5. Xác thực completion trước khi enqueue scanning.
6. Thiết kế asynchronous scanning + retry/idempotency.
7. Chặn download cho state chưa `Available`.
8. Thiết kế audit, logs, metrics và traces.
9. Xử lý orphan blobs, failed scans và deletion.
10. Chọn module boundary/deployment complexity theo requirement thực tế.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Blob container private; application identity dùng least privilege.
- Authorization business không được thay thế chỉ bằng việc biết blob URL.
- Với large files, direct upload có thể tránh application memory/bandwidth bottleneck; backend proxy vẫn có trường hợp phù hợp nếu kiểm soát/transform streaming bắt buộc.
- SAS nếu dùng phải scope hẹp, expiry ngắn và được cấp sau authorization; không hard-code storage keys.
- Upload completion không đồng nghĩa file an toàn để download; cần explicit lifecycle state.
- Scanning workflow phải chịu retry/duplicate execution và có failure recovery.

### Điểm cộng

- API tạo upload session/metadata trước, cấp target blob path không đoán được hoặc không phụ thuộc user input trực tiếp.
- Sau upload, backend xác minh blob metadata/size/type theo policy trước khi chuyển state và phát work.
- Dùng Managed Identity cho server-side Blob access; user-facing SAS chỉ cấp permission tối thiểu cần thiết.
- Download có thể cấp short-lived read SAS sau authorization thay vì proxy byte nếu audit/security requirement cho phép.
- Có cleanup job cho abandoned upload/orphan blob và retention policy.

### Senior+

- Xử lý race giữa authorization change và pre-signed/SAS URL còn hiệu lực; expiry là security/freshness trade-off.
- Thiết kế state transition atomic/idempotent và reconciliation cho trường hợp blob upload xong nhưng event/queue publish thất bại.
- Cân nhắc Outbox Pattern nếu metadata transaction và scanning dispatch cần reliability đủ cao.
- Không tách microservice nếu module boundary/ownership/scale chưa trả được complexity cost.

## Hướng giải quyết tham khảo

Tôi sẽ tách metadata/control khỏi file bytes. SQL giữ `DocumentId`, owner/project, blob identifier, size, content type, checksum nếu cần, lifecycle state, audit metadata và timestamps. Blob Storage giữ binary trong private container.

Với file lớn, tôi nghiêng về direct upload: client gọi API để tạo upload session; API authorize user, tạo metadata ở trạng thái `Initiated`, rồi cấp SAS write-only có scope đúng blob và expiry ngắn. Backend không đưa account key cho client. Server-side operations dùng Managed Identity. Sau khi client báo completion hoặc hệ thống nhận signal phù hợp, backend xác minh blob tồn tại và policy metadata trước khi chuyển sang `Uploaded/Scanning`.

Scanning chạy asynchronous. Có thể dùng Service Bus + Worker/Function tùy workload, execution model và operational preference; tôi không chọn Functions chỉ vì có file. Message chứa `DocumentId`, consumer đọc metadata/blob bằng identity, scan rồi thực hiện idempotent state transition. Retry transient failures với backoff; permanent/repeated failures chuyển `Failed`/DLQ để operator xử lý. Nếu publish message có thể mất sau SQL commit, Outbox là lựa chọn khi reliability requirement biện minh complexity.

Download API luôn kiểm tra current authorization và state `Available`. Sau đó hoặc stream qua backend, hoặc cấp short-lived read SAS. Direct download giảm App Service bandwidth nhưng SAS còn hiệu lực một khoảng thời gian dù quyền user vừa bị revoke, nên expiry phải theo security requirement. Nếu audit yêu cầu server chứng kiến từng download hoặc cần transform/redact content, proxy streaming có thể hợp lý hơn.

Tôi không load file 1 GB vào memory. Nếu proxy, dùng streaming và cancellation. Upload validation không chỉ tin filename/content type do client gửi. Scanning result, checksum và policy quyết định availability.

Observability gồm upload success/failure, orphan count, scanning queue age, scan duration/error, state-transition failures, Blob dependency latency, authorized/denied download, DLQ và correlation theo `DocumentId`. Reconciliation job tìm documents mắc ở state quá lâu và blobs không có metadata tương ứng.

Tôi sẽ giữ module trong existing application nếu boundaries và scale vẫn phù hợp. Có thể tách worker process mà chưa cần tách toàn bộ business service. Chỉ tách microservice khi deployment/ownership/scale/isolation requirement thực sự xuất hiện.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách control plane khỏi file data. SQL giữ metadata, ownership và lifecycle; Blob Storage private giữ binary. Với file tới 1 GB, tôi ưu tiên direct upload để App Service không proxy toàn bộ bandwidth: API authorize trước rồi cấp SAS write-only, scope đúng blob và expiry ngắn; server dùng Managed Identity.

File upload xong chưa được download ngay. Tôi model state `Initiated → Uploaded → Scanning → Available/Rejected/Failed`. Scanning chạy async và idempotent, có retry/DLQ/reconciliation. Download API luôn kiểm tra current business authorization và `Available`, sau đó có thể cấp read SAS ngắn hoặc proxy stream tùy audit/security requirement.

Tôi đặc biệt xử lý failure giữa metadata commit và dispatch scanning; nếu requirement đủ cao, Outbox có thể đáng dùng. Tôi cũng cleanup orphan uploads và monitor queue age/state stuck.

Tôi chưa tách microservice chỉ vì đây là file module. Có thể giữ control API trong Modular Monolith và tách worker execution trước. Chỉ tách service khi ownership, independent deployment hoặc scaling/isolation thực sự mang lại lợi ích.”

## Câu hỏi đào sâu

1. Nếu security yêu cầu revoke download access gần như tức thời, read SAS strategy của bạn thay đổi thế nào?
2. Nếu scanning provider không idempotent và có phí cao cho mỗi scan, bạn chống duplicate work ra sao?
3. Tôi muốn proxy mọi upload/download để “an toàn hơn”; bạn cần đo và phân tích những trade-off nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- Cho client storage key hoặc SAS quá rộng/quá lâu.
- Coi upload thành công là file đã an toàn để download.
- Load file lớn hoàn toàn vào ASP.NET Core memory.
- Không xử lý orphan blob hoặc message dispatch failure.
- Tách microservice/Kubernetes mà không có requirement tương ứng.

## Thang điểm 0–10

- **0–2:** Chỉ nói lưu file vào Blob Storage.
- **3–4:** Có SAS/async scan nhưng thiếu lifecycle/security/failure reasoning.
- **5–6:** Có private storage, state machine, authorization, retry và observability.
- **7–8:** Có idempotency, reconciliation, Outbox trade-off, large-file/data-plane reasoning.
- **9–10:** Thiết kế cân bằng security, reliability, cost, revocation semantics và operational complexity với conditional decisions rõ ràng.

## Kiến thức trọng tâm

- Cosmos DB partition key là quyết định đồng thời về distribution và query routing; access pattern mới có thể làm RU tăng dù traffic gần như không đổi.

- File architecture nên phân biệt control plane với data plane; private Blob Storage + scoped access + explicit lifecycle giúp large-file workflow an toàn và vận hành được.

3. **Design retry together with idempotency and reconciliation.**

5. **Chỉ trả complexity cost khi requirement chứng minh lợi ích.**
