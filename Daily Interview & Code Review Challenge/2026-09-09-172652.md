# Code Review Challenge 1 — Azure Service Bus consumer hoàn thành message quá sớm, tạo duplicate side effect và mất khả năng recovery khi lock hết hạn

**Chủ đề:** C#, .NET 8, Azure Service Bus, idempotency, retries, message settlement, lock renewal, EF Core, distributed systems, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một hệ thống order fulfillment chạy trên .NET 8 nhận message từ Azure Service Bus queue. Mỗi message yêu cầu:

- tạo shipment trong SQL Server;
- gọi một third-party carrier API để tạo vận đơn;
- lưu tracking number;
- gửi email xác nhận sau khi hoàn tất.

Application chạy nhiều instances để scale-out. Queue dùng PeekLock. Carrier API đôi khi mất 30–90 giây và thỉnh thoảng timeout dù request thực tế đã được xử lý thành công phía carrier.

Production xuất hiện các triệu chứng:

- một số order có hai tracking numbers khác nhau;
- cùng một message đôi khi được xử lý lại sau vài phút;
- logs ghi “completed successfully” nhưng database chưa có shipment;
- một số message đi vào DLQ sau nhiều delivery attempts;
- khi application restart, có order bị gửi email hai lần;
- team muốn tăng lock duration tối đa và retry carrier API nhiều lần để “chắc chắn thành công”.

## Đoạn code cần review

```csharp
public sealed class ShipmentMessageHandler
{
    private readonly AppDbContext _db;
    private readonly ICarrierClient _carrier;
    private readonly IEmailSender _email;
    private readonly ILogger<ShipmentMessageHandler> _logger;

    public ShipmentMessageHandler(
        AppDbContext db,
        ICarrierClient carrier,
        IEmailSender email,
        ILogger<ShipmentMessageHandler> logger)
    {
        _db = db;
        _carrier = carrier;
        _email = email;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var message = args.Message;
        var command = JsonSerializer.Deserialize<CreateShipmentCommand>(
            message.Body)!;

        await args.CompleteMessageAsync(message, cancellationToken);

        var exists = await _db.Shipments.AnyAsync(
            x => x.OrderId == command.OrderId,
            cancellationToken);

        if (exists)
        {
            _logger.LogInformation(
                "Shipment already exists for order {OrderId}",
                command.OrderId);
            return;
        }

        var carrierResult = await _carrier.CreateShipmentAsync(
            command.OrderId,
            command.Address,
            cancellationToken);

        var shipment = new Shipment
        {
            Id = Guid.NewGuid(),
            OrderId = command.OrderId,
            TrackingNumber = carrierResult.TrackingNumber,
            CreatedAtUtc = DateTime.UtcNow
        };

        _db.Shipments.Add(shipment);
        await _db.SaveChangesAsync(cancellationToken);

        await _email.SendShipmentCreatedAsync(
            command.OrderId,
            carrierResult.TrackingNumber,
            cancellationToken);

        _logger.LogInformation(
            "Shipment processed. MessageId={MessageId}, OrderId={OrderId}",
            message.MessageId,
            command.OrderId);
    }
}
```

## Kết quả code review tham khảo

### Critical — Message bị complete trước khi business processing thành công

**Vấn đề:** `CompleteMessageAsync` được gọi ngay sau deserialize, trước carrier call, SQL write và email.

**Tại sao xảy ra:** Handler coi việc nhận được message là tương đương với việc xử lý thành công.

**Ảnh hưởng production:** Nếu process crash, carrier fail, SQL fail hoặc application restart sau khi message đã được complete, broker đã coi message là xử lý xong và không redeliver. Business work có thể mất vĩnh viễn dù logs/queue không còn message để retry.

**Cách sửa:** Với PeekLock, chỉ complete sau khi phần business processing được coi là thành công theo contract. Nếu processing thất bại transient, không complete; tùy framework/handler strategy có thể abandon hoặc để exception khiến message được redeliver. Permanent invalid message nên dead-letter có reason rõ.

### Critical — External carrier call không idempotent theo logical operation

**Vấn đề:** `CreateShipmentAsync` không truyền stable idempotency/reference key cho carrier.

**Tại sao xảy ra:** Message delivery identity, order identity và external-operation identity chưa được thiết kế cùng nhau.

**Ảnh hưởng production:** Nếu carrier tạo shipment nhưng response timeout hoặc client mất kết nối, retry cùng request có thể tạo tracking number thứ hai cho cùng order.

**Cách sửa:** Nếu provider hỗ trợ idempotency, gửi stable key như `OrderId` hoặc `ShipmentOperationId`. Nếu provider không hỗ trợ, cần reconciliation bằng provider reference/query trước khi retry blind. Trạng thái “timeout” phải được model là outcome unknown, không mặc định là failure.

### Critical — `AnyAsync` + insert không ngăn duplicate dưới concurrency

**Vấn đề:** Hai instances có thể cùng query `exists == false` rồi cùng gọi carrier và cùng insert.

**Tại sao xảy ra:** Đây là check-then-act race giữa hai độc lập message deliveries/consumers.

**Ảnh hưởng production:** Double external side effect và duplicate shipment rows/tracking numbers.

**Cách sửa:** Database phải enforce invariant, ví dụ unique constraint/index trên `OrderId` nếu business chỉ cho một shipment logical cho mỗi order. Application pre-check chỉ để tối ưu UX/work, không phải authority cuối cùng. Nếu cần reservation state, dùng atomic insert/conditional update để một consumer giành quyền xử lý.

### High — Message delivery có thể lặp lại dù lock được renew lâu

**Vấn đề:** Team giả định lock dài đồng nghĩa exactly-once.

**Tại sao xảy ra:** PeekLock giữ message tạm thời cho một receiver nhưng settlement vẫn có thể thất bại, connection có thể mất, process có thể restart, lock có thể hết hạn, hoặc successful settlement acknowledgment có thể không đến client.

**Ảnh hưởng production:** Cùng message có thể xuất hiện lại và side effects phải chịu được duplicate delivery.

**Cách sửa:** Thiết kế consumer theo at-least-once delivery semantics: idempotent processing, persisted operation state và duplicate detection ở business boundary. Lock renewal chỉ giúp giữ ownership trong một processing window dài hơn, không thay thế idempotency.

### High — Không có persisted processing state cho workflow nhiều bước

**Vấn đề:** Code chỉ lưu final `Shipment` sau carrier success. Không có record cho trạng thái `Pending`, `CarrierRequestSent`, `CarrierOutcomeUnknown`, `Confirmed`, `EmailPending`, `Completed`.

**Tại sao xảy ra:** Workflow được viết như một transaction tuần tự trong memory trong khi thực tế có nhiều distributed side effects.

**Ảnh hưởng production:** Sau crash hoặc timeout, hệ thống không biết bước nào đã xảy ra và có xu hướng retry toàn bộ workflow.

**Cách sửa:** Persist một shipment operation/state machine. Trước external call, tạo operation record với stable operation ID. Sau carrier response, update trạng thái. Với outcome unknown, reconciliation worker/query provider xác minh trước retry. State transition nên atomic/conditional để nhiều consumer không cùng tiến hành một operation.

### High — Email là side effect thứ hai và cũng không idempotent

**Vấn đề:** Email được gửi sau DB commit nhưng trước message settlement; crash sau email có thể khiến message redeliver và email gửi lại.

**Tại sao xảy ra:** Email side effect không có delivery marker/outbox semantics.

**Ảnh hưởng production:** User nhận email trùng, hoặc nếu chuyển email trước DB commit thì có thể nhận email cho shipment chưa tồn tại.

**Cách sửa:** Dùng Outbox Pattern hoặc persisted notification state. Commit shipment + outbox event trong cùng SQL transaction; worker riêng gửi email và đánh dấu sent/idempotency key. Redelivery của Service Bus message thấy shipment operation đã hoàn tất thì chỉ complete, không lặp side effects.

### High — Carrier timeout bị coi là lỗi thông thường thay vì ambiguous outcome

**Vấn đề:** Nếu HTTP call timeout sau khi carrier đã xử lý request, caller không biết side effect đã xảy ra chưa.

**Tại sao xảy ra:** Network timeout bị đồng nhất với provider business failure.

**Ảnh hưởng production:** Retry blind tạo duplicate shipment; không retry lại có thể bỏ sót shipment đã hoặc chưa được tạo.

**Cách sửa:** Phân loại `definitive failure`, `definitive success`, `unknown outcome`. Với unknown outcome, query carrier theo stable reference/idempotency key trước khi thực hiện lại. Nếu provider không cung cấp khả năng reconciliation, business phải chấp nhận một compensation/manual-review path rõ ràng.

### High — Concurrency 32 có thể khuếch đại pressure lên carrier và database

**Vấn đề:** `MaxConcurrentCalls = 32` được đặt mà không dựa trên downstream capacity hoặc lock/latency profile.

**Tại sao xảy ra:** Concurrency được xem là throughput knob độc lập.

**Ảnh hưởng production:** Carrier chậm có thể làm 32 calls giữ connection cùng lúc trên mỗi instance; scale-out nhân concurrency tổng. SQL connections, outbound sockets và rate limit của carrier có thể bị pressure, gây timeout nhiều hơn và tạo feedback loop.

**Cách sửa:** Chọn concurrency dựa trên evidence: carrier rate limits, latency, DB pool, process memory, queue depth và SLO. Có thể dùng bounded concurrency/rate limiter. Scale policy nên dựa trên queue backlog + processing latency chứ không chỉ tăng `MaxConcurrentCalls`.

### Medium — Deserialize không có validation/failure classification

**Vấn đề:** `Deserialize(... )!` giả định payload hợp lệ và đầy đủ.

**Tại sao xảy ra:** Handler chỉ tập trung happy path.

**Ảnh hưởng production:** Poison message có thể retry nhiều lần rồi vào DLQ mà không có reason hữu ích; malformed address/order fields có thể đi sâu tới carrier.

**Cách sửa:** Validate schema/business fields ngay đầu handler. Invalid non-retriable input nên dead-letter với bounded reason/metadata; không log raw PII nếu payload chứa dữ liệu nhạy cảm.

### Medium — Cancellation cần được hiểu đúng ở side-effect boundary

**Vấn đề:** Token được propagate nhưng cancellation giữa external side effect và local persistence không tự rollback carrier operation.

**Tại sao xảy ra:** Cancellation được hiểu như transactional rollback.

**Ảnh hưởng production:** Host shutdown/client cancellation có thể dừng local code sau khi carrier đã thực hiện side effect, tạo ambiguous state.

**Cách sửa:** Propagate cancellation cho I/O phù hợp, nhưng sau khi bắt đầu non-transactional external side effect, recovery phải dựa trên idempotency/reconciliation, không dựa vào cancellation semantics.

### Medium — Telemetry thiếu delivery attempt và operation state

**Vấn đề:** Log chỉ có `MessageId` và `OrderId` khi success; thiếu `DeliveryCount`, operation ID, carrier request ID, lock-loss/settlement outcome và state transition.

**Tại sao xảy ra:** Observability được thêm ở cuối thay vì thiết kế cùng workflow.

**Ảnh hưởng production:** Khó phân biệt duplicate delivery, duplicate business operation, timeout unknown và settlement failure.

**Cách sửa:** Structured logs/traces cần có `MessageId`, `OrderId`, `ShipmentOperationId`, `DeliveryCount`, carrier correlation/reference, processing duration, settlement result và final state. Alert trên DLQ growth, duplicate constraint violations và ambiguous carrier outcomes.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa một flow an toàn hơn: persist operation trước, dùng unique business key, gọi carrier với stable operation reference, commit business state + outbox trong SQL transaction, rồi mới complete message.

```csharp
public sealed class ShipmentMessageHandler
{
    private readonly AppDbContext _db;
    private readonly ICarrierClient _carrier;
    private readonly ILogger<ShipmentMessageHandler> _logger;

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken ct)
    {
        var message = args.Message;
        var command = JsonSerializer.Deserialize<CreateShipmentCommand>(
            message.Body)
            ?? throw new InvalidOperationException("Invalid message body.");

        var operation = await _db.ShipmentOperations
            .SingleOrDefaultAsync(
                x => x.OrderId == command.OrderId,
                ct);

        if (operation?.Status == ShipmentOperationStatus.Completed)
        {
            await args.CompleteMessageAsync(message, ct);
            return;
        }

        if (operation is null)
        {
            operation = new ShipmentOperation
            {
                Id = Guid.NewGuid(),
                OrderId = command.OrderId,
                Status = ShipmentOperationStatus.PendingCarrier,
                CreatedAtUtc = DateTime.UtcNow
            };

            _db.ShipmentOperations.Add(operation);

            try
            {
                await _db.SaveChangesAsync(ct);
            }
            catch (DbUpdateException ex) when (IsUniqueOrderViolation(ex))
            {
                operation = await _db.ShipmentOperations
                    .SingleAsync(x => x.OrderId == command.OrderId, ct);
            }
        }

        CarrierShipmentResult carrierResult;

        try
        {
            carrierResult = await _carrier.CreateShipmentAsync(
                operation.Id.ToString("N"),
                command.OrderId,
                command.Address,
                ct);
        }
        catch (CarrierOutcomeUnknownException)
        {
            operation.Status = ShipmentOperationStatus.CarrierOutcomeUnknown;
            await _db.SaveChangesAsync(CancellationToken.None);
            throw;
        }

        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        operation.TrackingNumber = carrierResult.TrackingNumber;
        operation.Status = ShipmentOperationStatus.Completed;
        operation.CompletedAtUtc = DateTime.UtcNow;

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "ShipmentCreated",
            Payload = JsonSerializer.Serialize(new
            {
                command.OrderId,
                carrierResult.TrackingNumber
            }),
            CreatedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);

        await args.CompleteMessageAsync(message, ct);

        _logger.LogInformation(
            "Shipment completed. MessageId={MessageId}, OrderId={OrderId}, OperationId={OperationId}, DeliveryCount={DeliveryCount}",
            message.MessageId,
            command.OrderId,
            operation.Id,
            message.DeliveryCount);
    }
}
```

Database cần unique constraint/index cho `ShipmentOperations.OrderId` nếu invariant là một logical shipment operation cho mỗi order. Nếu carrier có idempotency key native, `operation.Id` nên được dùng làm stable key. Nếu carrier chỉ có query-by-reference, reconciliation job cần xử lý trạng thái `CarrierOutcomeUnknown` trước khi retry create.

Email được gửi bởi Outbox dispatcher riêng. Dispatcher cũng cần idempotent send semantics hoặc persisted `SentAt`/delivery key phù hợp để retry an toàn.

## Giải thích thiết kế sau khi sửa

Thiết kế mới không cố tạo distributed ACID transaction giữa Service Bus, SQL Server, carrier API và email. Thay vào đó nó dùng **persisted state + idempotency + reconciliation + controlled settlement**.

Message chỉ được complete sau khi core business state đã được commit. Nếu message redeliver sau commit nhưng trước settlement acknowledgment, handler nhìn thấy operation đã `Completed` và complete lại mà không gọi carrier/email lần nữa.

Carrier operation có stable identity. Timeout được xem là ambiguous outcome; hệ thống query/reconcile thay vì blindly retry.

Email được tách qua outbox vì shipment commit và email send không thể atomic trong một local SQL transaction. Outbox cho phép commit business state và intent-to-notify cùng lúc rồi retry notification độc lập.

## Trade-offs

- **Persisted state machine:** thêm bảng/trạng thái và code reconciliation, nhưng đổi lại có recovery path rõ ràng sau crash/timeout.
- **Outbox:** tăng write volume và cần dispatcher/cleanup, nhưng giảm duplicate/lost notification.
- **Unique constraint:** tạo authority mạnh ở database; caller phải handle conflict thay vì coi duplicate là impossible.
- **Lock renewal:** hữu ích cho processing dài thật sự nhưng không nên được dùng để che workflow quá dài hoặc thiếu idempotency.
- **Lower concurrency:** có thể giảm peak throughput nhưng thường tăng stability nếu carrier/DB đang là bottleneck thực tế.

## Cách kiểm thử

1. **Concurrency test:** gửi cùng logical order nhiều lần đồng thời trên nhiều consumer instances; phải chỉ có một shipment operation và tối đa một carrier side effect theo idempotency key.
2. **Failure-path test:** carrier trả success nhưng simulated process crash trước DB commit; reconciliation phải xác định outcome mà không tạo shipment thứ hai.
3. **Settlement test:** DB commit xong nhưng `CompleteMessageAsync` fail/lock lost; redelivery phải complete mà không lặp carrier/email.
4. **DLQ test:** malformed message phải được dead-letter với reason rõ; transient carrier failure không bị dead-letter ngay.
5. **Load test:** đo queue depth, processing latency, carrier concurrency, DB pool usage và duplicate rate khi scale nhiều instances.

## Quan sát trong production

- Metric queue active count, dead-letter count, delivery count distribution và message processing latency.
- Structured trace xuyên `MessageId` → `ShipmentOperationId` → SQL → carrier request/reference → outbox notification.
- Alert khi `DeliveryCount` tăng bất thường, DLQ tăng, unique constraint conflict tăng hoặc `CarrierOutcomeUnknown` tồn tại quá lâu.
- Metric `carrier_request_duration`, timeout rate, reconciliation success rate và duplicate response rate từ provider.
- Dashboard cho end-to-end order-to-shipment latency, p95/p99 processing và settlement failures.

## Câu hỏi phỏng vấn mở rộng

1. Nếu carrier không hỗ trợ idempotency key và cũng không có API query theo reference, bạn thiết kế business recovery như thế nào?
2. Khi nào bạn dùng Service Bus duplicate detection và vì sao nó vẫn không thay thế application-level idempotency?
3. Nếu processing hợp lệ mất 20 phút, bạn giữ message lock lâu hay chuyển thành workflow chia nhỏ nhiều messages/state transitions?

# Code Review Challenge 2 — Kubernetes probes cùng gọi database làm rolling deployment tự tạo restart storm khi SQL chậm

## Kết quả code review tham khảo

### Critical — Liveness probe phụ thuộc SQL/Redis/external API

**Vấn đề:** `/health` kiểm tra mọi dependency rồi được dùng làm liveness probe.

**Tại sao xảy ra:** Team dùng một health endpoint duy nhất cho mọi mục đích.

**Ảnh hưởng production:** Khi SQL hoặc external API chậm, liveness fail trên nhiều Pods và kubelet restart containers dù process ASP.NET Core vẫn hoàn toàn có khả năng phục hồi khi dependency trở lại. Restart storm làm mất connection pools/warm state, tăng startup load và có thể khuếch đại outage.

**Cách sửa:** Liveness chỉ nên phản ánh process có còn khả năng tiến triển hay không, thường là lightweight self-check không phụ thuộc remote services. Dependency health phù hợp hơn với readiness hoặc observability, tùy dependency có bắt buộc để serve traffic hay không.

### Critical — Readiness và liveness dùng cùng threshold rất nhạy

**Vấn đề:** Cả hai probe chạy mỗi 5 giây, timeout 1 giây, failure threshold 2. Một dependency latency spike ngắn có thể khiến Pod vừa bị remove khỏi traffic vừa nhanh chóng bị restart.

**Tại sao xảy ra:** Không có separation giữa transient dependency degradation và process failure.

**Ảnh hưởng production:** Nhiều Pods đồng loạt restart, traffic dồn lên số Pods còn lại, khiến chúng overload và readiness cũng bắt đầu fail — cascading failure.

**Cách sửa:** Readiness có thể phản ứng với dependency cần thiết cho request serving; liveness phải độc lập. Threshold/timeout cần dựa trên measured startup/request/dependency behavior, không chọn chỉ vì muốn “phát hiện nhanh”.

### High — `maxUnavailable: 4` + `maxSurge: 0` giảm capacity đáng kể trong rollout

**Vấn đề:** Với 12 replicas, rollout cho phép tối đa bốn replicas unavailable mà không tạo Pod bổ sung vượt desired count.

**Tại sao xảy ra:** Strategy tối ưu resource usage nhưng chưa đối chiếu với headroom thực tế.

**Ảnh hưởng production:** Nếu cluster thường chạy gần capacity, rollout có thể giảm serving capacity khoảng một phần ba trước khi tính thêm readiness failures do dependency issue.

**Cách sửa:** Chọn `maxUnavailable`/`maxSurge` theo capacity headroom, startup time và failure tolerance. Với stateless API critical, thường nên giữ `maxUnavailable` thấp và cho phép một lượng surge nếu cluster capacity cho phép. Không có một con số đúng cho mọi hệ thống; phải validate bằng load test.

### High — Startup probe budget có thể không phù hợp startup thực tế

**Vấn đề:** Startup probe cũng gọi deep `/health`; app có thể bị coi là chưa startup chỉ vì external config API hoặc SQL đang tạm chậm.

**Tại sao xảy ra:** Startup readiness của process bị gắn với toàn bộ runtime dependency graph.

**Ảnh hưởng production:** New Pods không bao giờ qua startup probe hoặc bị restart trong rollout khi dependency tạm degraded.

**Cách sửa:** Startup probe nên kiểm tra application đã khởi tạo đủ để tiến vào normal lifecycle chưa. Nếu startup thực sự cần config remote bắt buộc, budget phải phản ánh observed startup worst case và failure semantics rõ; không mặc định dùng toàn bộ downstream dependencies.

### High — Termination grace quá ngắn so với request duration

**Vấn đề:** `preStop` sleep 3 giây và toàn bộ `terminationGracePeriodSeconds` chỉ 5 giây.

**Tại sao xảy ra:** Team không đối chiếu grace period với request p95/p99 và app shutdown behavior.

**Ảnh hưởng production:** Pod có thể bị force-kill khi request đang chạy, tạo connection reset/partial work. Long-running writes hoặc outbound calls có thể bị cắt giữa chừng.

**Cách sửa:** Xác định shutdown sequence: endpoint removal/readiness transition, load balancer propagation, ASP.NET Core graceful shutdown và maximum request budget. Grace period nên đủ cho controlled drain theo SLO. Long-running jobs không nên phụ thuộc request drain vô hạn; cần cancellation/idempotency.

### High — Probe fan-out có thể tự tạo load lên dependencies

**Vấn đề:** 12 Pods gọi SQL, Redis và external config API mỗi 5 giây cho nhiều loại probe; trong startup/rollout còn có thêm probe overlap.

**Tại sao xảy ra:** Health check được xem là free.

**Ảnh hưởng production:** Khi dependency đang yếu, probe traffic thêm connection/query/network load đúng lúc hệ thống cần giảm áp lực nhất.

**Cách sửa:** Liveness không fan-out remote. Readiness dependency checks phải lightweight, có timeout hợp lý và cân nhắc cached/aggregated health state khi cần. Deep diagnostics có thể chạy ở monitoring layer thay vì per-Pod probe với tần suất cao.

### High — Resource requests/limits có thể quá thấp và tạo throttling/OOM risk

**Vấn đề:** CPU request 100m/limit 250m và memory 128/256Mi được cấu hình nhưng không có evidence workload profile.

**Tại sao xảy ra:** Resource values thường được copy từ template.

**Ảnh hưởng production:** CPU throttling làm request/probe timeout tăng; memory limit thấp có thể gây OOMKill. Cả hai có thể bị hiểu nhầm thành application health issue.

**Cách sửa:** Chọn requests/limits từ production/load-test measurements: steady CPU, startup CPU, memory working set, GC behavior và burst profile. Theo dõi throttling và OOM. Không bỏ limits vô điều kiện; điều chỉnh dựa trên evidence.

### Medium — Readiness dependency set chưa phân loại bắt buộc và optional

**Vấn đề:** SQL, Redis và config API đều được coi như nhau.

**Tại sao xảy ra:** Health design không gắn với request capability.

**Ảnh hưởng production:** Nếu Redis chỉ là cache và application có fallback về SQL, Redis outage vẫn có thể remove toàn bộ Pods khỏi service dù API có thể phục vụ chậm hơn.

**Cách sửa:** Phân loại dependency theo contract. SQL có thể là mandatory cho orders API; Redis có thể optional nếu fallback tồn tại; config API có thể chỉ cần lúc startup nếu config đã cache. Readiness phải phản ánh khả năng phục vụ meaningful traffic, không phải “mọi dependency đều xanh”.

### Medium — Giảm `periodSeconds` xuống 2 giây có thể làm hệ thống kém ổn định hơn

**Vấn đề:** Team muốn probe nhanh hơn mà không phân tích false positive/load.

**Tại sao xảy ra:** Detection speed được tối ưu độc lập với recovery behavior.

**Ảnh hưởng production:** Tăng probe traffic, phản ứng quá nhạy với transient latency và tăng restart/removal churn.

**Cách sửa:** Chọn probe cadence và thresholds dựa trên detection-time objective, dependency latency distribution, failure duration và cost của false positive. Faster không luôn tốt hơn.

### Medium — Không thấy deployment safety gates dựa trên readiness/metrics

**Vấn đề:** YAML không cho thấy rollout observation, SLO gate hoặc rollback trigger.

**Tại sao xảy ra:** Deployment được coi là “apply manifest rồi chờ Kubernetes”.

**Ảnh hưởng production:** Regression có thể lan qua nhiều replicas trước khi team nhận ra.

**Cách sửa:** CI/CD nên theo dõi rollout status, readiness, 5xx, p95/p99, restart count và key business metrics; abort/rollback theo policy nếu vượt ngưỡng. Tùy platform có thể dùng progressive delivery, nhưng không cần thêm complexity nếu rolling update + metrics gate đã đủ.

## Phiên bản đề xuất

Ví dụ dưới đây tách probe semantics. Đây là điểm khởi đầu; timeout/threshold/resource values cuối cùng phải được hiệu chỉnh bằng load/production evidence.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 12
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 2
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: orders-api
          image: registry.example.com/orders-api:2026.09.09
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 5"]
```

ASP.NET Core có thể tag health checks theo mục đích:

```csharp
builder.Services
    .AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddSqlServer(connectionString, tags: ["ready"])
    .AddRedis(redisConnectionString, tags: ["optional"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

app.MapGet("/health/startup", () => Results.Ok());
```

Nếu Redis thật sự optional vì application có fallback, không nên để Redis failure tự động làm readiness fail. Nếu config service chỉ cần lúc startup và config đã được cache local/in-memory, runtime readiness cũng không nên gọi nó mỗi vài giây.

Resource values trong YAML minh họa không phải universal recommendation. Team phải thay bằng numbers lấy từ load test và telemetry thật.

## Giải thích thiết kế sau khi sửa

Liveness trả lời: process có còn hoạt động đủ để tiếp tục hay cần restart? Vì remote dependency outage không được chữa bằng restart process, liveness không gọi SQL/Redis/external API.

Readiness trả lời: Pod hiện có nên nhận traffic không? Nó có thể kiểm tra dependency bắt buộc để phục vụ request, nhưng chỉ những dependency thật sự required. Optional dependencies nên có fallback/degraded mode thay vì remove toàn Pod nếu business vẫn phục vụ được.

Startup probe cho phép ứng dụng có thời gian khởi tạo trước khi liveness/readiness có hiệu lực. Nó không nên biến transient runtime dependency issue thành startup crash loop trừ khi dependency đó thực sự là requirement bắt buộc để process khởi động.

Rolling update giữ capacity tốt hơn với `maxUnavailable` thấp và một ít surge, nhưng cấu hình thật phải tính cluster headroom. Graceful shutdown đủ dài để traffic drain và ASP.NET Core hoàn tất requests trong budget hợp lý.

## Trade-offs

- **Readiness check ít dependency hơn:** giảm false negative nhưng có thể cho traffic vào Pod đang degraded; cần fallback/error contract rõ.
- **Liveness lightweight:** tránh restart storm nhưng không phát hiện mọi loại dependency-related failure; đó là nhiệm vụ của metrics/readiness/alerts.
- **Longer termination grace:** rollout scale-down chậm hơn nhưng giảm request reset và partial work.
- **Higher resource requests:** giảm scheduling density/có thể tăng cost nhưng tạo capacity predictable hơn.
- **Lower `maxUnavailable`:** rollout chậm hơn một chút nhưng bảo toàn serving capacity tốt hơn.

## Cách kiểm thử

1. **Failure injection:** làm SQL timeout 40 giây; Pods phải có thể thành NotReady nếu SQL là mandatory nhưng không bị liveness restart chỉ vì SQL outage.
2. **Rolling deployment load test:** giữ steady production-like traffic trong rollout; theo dõi 5xx, p95/p99, ready replicas và restart count.
3. **Graceful shutdown test:** tạo requests dài 10–15 giây rồi terminate Pod; xác minh request drain/cancellation behavior và không có unexpected connection reset.
4. **Resource test:** chạy load tới peak, đo CPU throttling, memory working set, GC và OOM behavior để hiệu chỉnh requests/limits.
5. **Optional dependency test:** tắt Redis; nếu contract cho fallback, API vẫn Ready và metrics phản ánh degraded cache mode.

## Quan sát trong production

- Kubernetes metrics: ready replicas, restart count, probe failures, rollout duration, OOMKilled, CPU throttling.
- Application Insights: request rate, 5xx, p95/p99, SQL dependency duration/failure, Redis dependency failures.
- Alert khi readiness loss đồng loạt nhiều Pods, restart burst hoặc ready capacity dưới safe threshold.
- Correlate deployment revision/image digest với latency/error changes.
- Theo dõi connection churn tới SQL/Redis trong rollout/outage để phát hiện probe/restart amplification.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL outage kéo dài 10 phút và API không thể phục vụ bất kỳ request hữu ích nào, readiness nên làm gì và autoscaling có giúp không?
2. Nếu application có deadlock nội bộ nhưng `/health/live` chỉ trả 200 từ một trivial endpoint, bạn thiết kế liveness signal tốt hơn thế nào mà không kéo remote dependencies vào?
3. Khi nào progressive delivery/canary đáng để thêm vào thay vì chỉ dùng rolling update + metrics gate?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Service Bus PeekLock cung cấp lock + explicit settlement nhưng consumer vẫn phải thiết kế cho duplicate delivery và idempotency.
- External side effects cần stable operation identity, reconciliation và persisted state; timeout không đồng nghĩa “chắc chắn chưa thực hiện”.
- Outbox giúp tách local database commit khỏi notification side effect mà vẫn giữ retry/recovery rõ ràng.
- Kubernetes liveness, readiness và startup probes phục vụ ba mục đích khác nhau; trộn dependency health vào liveness có thể tạo cascading restart storm.
- Rolling deployment safety phụ thuộc capacity headroom, graceful shutdown, resource sizing và telemetry chứ không chỉ manifest syntactically valid.

## Mẫu tư duy cần nhớ

1. **Design retry together with idempotency.**
2. **Treat timeout as potentially ambiguous when an external side effect may already have happened.**
3. **Do not use restart as a cure for remote dependency failure unless restart can actually fix the fault.**
4. **Separate health semantics: alive, ready, started.**
5. **Measure rollout capacity and failure behavior before tuning thresholds aggressively.**
