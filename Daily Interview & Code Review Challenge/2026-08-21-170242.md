# Code Review Challenge 1 — Job offboarding chạy lại và tạo side effect trùng lặp

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling, external API failure  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một Hangfire job xử lý offboarding nhân viên. Job cập nhật trạng thái trong SQL Server rồi gọi Microsoft Graph và Exchange Online để vô hiệu hóa tài khoản, chuyển mailbox và cấu hình forwarding. Hangfire có thể retry khi job throw exception; đồng thời một thao tác thủ công của admin cũng có thể enqueue cùng employee.

Production thỉnh thoảng xuất hiện hai job xử lý cùng một employee. Có trường hợp Graph đã disable user nhưng database vẫn ghi `Pending`; một số thao tác Exchange được gọi nhiều lần và lịch sử audit có bản ghi trùng. Không được giả định rằng mọi external operation đều transactional hoặc có cùng semantics khi gọi lại.

## Đoạn code cần review

```csharp
public sealed class EmployeeOffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IGraphClient _graph;
    private readonly IExchangeService _exchange;
    private readonly ILogger<EmployeeOffboardingJob> _logger;

    public EmployeeOffboardingJob(
        AppDbContext db,
        IGraphClient graph,
        IExchangeService exchange,
        ILogger<EmployeeOffboardingJob> logger)
    {
        _db = db;
        _graph = graph;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 3)]
    public async Task RunAsync(Guid employeeId)
    {
        var employee = await _db.Employees
            .SingleAsync(x => x.Id == employeeId);

        if (employee.OffboardingStatus == "Completed")
            return;

        employee.OffboardingStatus = "Processing";
        employee.OffboardingStartedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        await _graph.DisableUserAsync(employee.AzureAdObjectId);
        await _exchange.ConvertToSharedMailboxAsync(employee.Email);
        await _exchange.SetForwardingAsync(employee.Email, employee.ManagerEmail);

        _db.OffboardingHistories.Add(new OffboardingHistory
        {
            EmployeeId = employee.Id,
            Action = "OffboardingCompleted",
            CreatedAt = DateTime.UtcNow
        });

        employee.OffboardingStatus = "Completed";
        employee.OffboardingCompletedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Offboarding completed for {EmployeeId} {Email}",
            employee.Id,
            employee.Email);
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không atomic

- **Problem:** Hai worker có thể cùng đọc trạng thái khác `Completed` và cùng bắt đầu xử lý.
- **Why it happens:** Query và cập nhật `Processing` là các thao tác tách rời, không có compare-and-set hoặc concurrency token.
- **Production impact:** External side effects bị thực thi trùng.
- **Severity:** Critical
- **Recommended fix:** Claim work atomically bằng conditional update/concurrency token hoặc một cơ chế distributed ownership phù hợp. Database vẫn phải bảo vệ invariant ngay cả khi có distributed lock.

### 2. `Processing` không chứng minh worker hiện tại sở hữu job

- **Problem:** Code chỉ bỏ qua `Completed`; worker thứ hai vẫn xử lý record đang `Processing`.
- **Why it happens:** Không có operation ID, lease/version hoặc state transition được enforce atomically.
- **Production impact:** Duplicate processing dưới concurrency.
- **Severity:** Critical
- **Recommended fix:** Lưu `OperationId`, state/version và chỉ claim từ trạng thái hợp lệ bằng conditional update.

### 3. Retry toàn method có thể lặp external side effects

- **Problem:** Nếu step sau thất bại, Hangfire retry từ đầu.
- **Why it happens:** Không persist trạng thái từng step và không có idempotency contract rõ ràng với dependency.
- **Production impact:** Duplicate permission/mailbox/forwarding operations, lỗi khó phân biệt giữa retry an toàn và state conflict.
- **Severity:** Critical
- **Recommended fix:** Thiết kế workflow theo step, persist completion/result của từng step và chỉ retry step chưa hoàn thành. Dùng idempotency key khi external API hỗ trợ; nếu không, read-before-write hoặc operation semantics phù hợp.

### 4. Dual-write inconsistency giữa database và external systems

- **Problem:** Graph có thể thành công nhưng database hoặc Exchange thất bại.
- **Why it happens:** SQL transaction không bao phủ external APIs.
- **Production impact:** DB nói `Pending/Processing` trong khi tài khoản thực tế đã bị disable.
- **Severity:** High
- **Recommended fix:** Dùng durable workflow/state machine, persist step result và reconciliation. Không tuyên bố atomicity xuyên SQL + Graph + Exchange.

### 5. Không có trạng thái failure/recovery đủ chi tiết

- **Problem:** Không lưu step nào thất bại, attempt, last error hoặc next retry.
- **Why it happens:** Model chỉ có trạng thái tổng quát.
- **Production impact:** Khó support và khó resume chính xác.
- **Severity:** High
- **Recommended fix:** Persist per-step status, attempt count, timestamps và sanitized error metadata.

### 6. Audit record không có uniqueness/idempotency key

- **Problem:** Retry/concurrent execution có thể thêm nhiều history tương đương.
- **Why it happens:** Không có operation key hoặc unique constraint.
- **Production impact:** Audit không đáng tin cậy.
- **Severity:** High
- **Recommended fix:** Gắn history với `OperationId` + step/action và enforce unique constraint phù hợp.

### 7. Không truyền cancellation token

- **Problem:** DB và external calls không nhận cancellation token.
- **Why it happens:** Method không expose token.
- **Production impact:** Shutdown/cancellation có thể kéo dài và làm recovery khó đoán.
- **Severity:** Medium
- **Recommended fix:** Nếu execution framework/integration hỗ trợ cancellation, propagate token qua I/O boundaries và đảm bảo cancellation không phá invariant.

### 8. Logging thiếu correlation và step information

- **Problem:** Chỉ log completion.
- **Why it happens:** Không có operation ID và structured step events.
- **Production impact:** Khó reconstruct workflow khi retry hoặc partial failure.
- **Severity:** Medium
- **Recommended fix:** Log operation ID, employee ID, step, attempt, duration, outcome; không log token/secret và hạn chế PII không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng thiết kế; conditional claim cần được triển khai phù hợp provider/database thực tế.

```csharp
public sealed class EmployeeOffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IGraphClient _graph;
    private readonly IExchangeService _exchange;
    private readonly ILogger<EmployeeOffboardingJob> _logger;

    public EmployeeOffboardingJob(
        AppDbContext db,
        IGraphClient graph,
        IExchangeService exchange,
        ILogger<EmployeeOffboardingJob> logger)
    {
        _db = db;
        _graph = graph;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 3)]
    public async Task RunAsync(Guid employeeId, CancellationToken ct)
    {
        var operationId = Guid.NewGuid();

        var claimed = await _db.Employees
            .Where(x => x.Id == employeeId && x.OffboardingStatus == "Pending")
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.OffboardingStatus, "Processing")
                .SetProperty(x => x.OffboardingOperationId, operationId)
                .SetProperty(x => x.OffboardingStartedAt, DateTime.UtcNow), ct);

        if (claimed == 0)
        {
            var status = await _db.Employees
                .Where(x => x.Id == employeeId)
                .Select(x => x.OffboardingStatus)
                .SingleOrDefaultAsync(ct);

            _logger.LogInformation(
                "Offboarding not claimed. EmployeeId={EmployeeId}, Status={Status}",
                employeeId, status);
            return;
        }

        try
        {
            var employee = await _db.Employees
                .SingleAsync(x => x.Id == employeeId &&
                                  x.OffboardingOperationId == operationId, ct);

            await RunStepAsync(employee, "DisableUser",
                () => _graph.DisableUserAsync(employee.AzureAdObjectId, ct), ct);

            await RunStepAsync(employee, "ConvertMailbox",
                () => _exchange.ConvertToSharedMailboxAsync(employee.Email, ct), ct);

            await RunStepAsync(employee, "SetForwarding",
                () => _exchange.SetForwardingAsync(
                    employee.Email, employee.ManagerEmail, ct), ct);

            employee.OffboardingStatus = "Completed";
            employee.OffboardingCompletedAt = DateTime.UtcNow;
            await _db.SaveChangesAsync(ct);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Offboarding failed. EmployeeId={EmployeeId}, OperationId={OperationId}",
                employeeId, operationId);
            throw;
        }
    }

    private async Task RunStepAsync(
        Employee employee,
        string step,
        Func<Task> action,
        CancellationToken ct)
    {
        var alreadyDone = await _db.OffboardingSteps
            .AnyAsync(x => x.EmployeeId == employee.Id &&
                           x.OperationId == employee.OffboardingOperationId &&
                           x.Step == step &&
                           x.Status == "Completed", ct);

        if (alreadyDone)
            return;

        await action();

        _db.OffboardingSteps.Add(new OffboardingStep
        {
            EmployeeId = employee.Id,
            OperationId = employee.OffboardingOperationId!.Value,
            Step = step,
            Status = "Completed",
            CompletedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(ct);
    }
}
```

Lưu ý: ví dụ này cải thiện claim và resumability nhưng vẫn tồn tại một cửa sổ failure giữa `action()` thành công và việc persist step. Với side effect không hỗ trợ idempotency key, production-grade design cần reconciliation/read-back hoặc semantics riêng của từng external operation. Unique constraint trên `(EmployeeId, OperationId, Step)` vẫn cần thiết.

## Trade-offs

Persist từng step tăng số database writes và complexity nhưng đổi lại có khả năng resume, audit và reconciliation. Distributed lock có thể giảm duplicate execution nhưng không nên là lớp bảo vệ duy nhất vì lock có thể hết hạn hoặc process chết. Một durable workflow engine có thể phù hợp khi số step, timeout và compensation tăng mạnh; với workflow nhỏ, state machine trong modular monolith thường đơn giản hơn.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời nhiều invocation cùng employee và xác nhận chỉ một execution claim thành công.
2. **Failure-path integration test:** Graph thành công, Exchange throw; retry phải không lặp step đã xác nhận hoàn tất hoặc phải reconcile đúng.
3. **Database test:** unique constraint ngăn duplicate step/audit record.
4. **Recovery test:** worker chết giữa các step; invocation sau resume từ state đã persist.
5. **Cancellation test:** cancel trong external call và xác nhận state không bị đánh dấu `Completed` sai.

## Quan sát trong production

- Structured logs: `OperationId`, `EmployeeId`, `Step`, `Attempt`, `Outcome`, `DurationMs`.
- Metrics: số offboarding pending/processing/failed, retry count, step latency, age của record ở `Processing`.
- Distributed traces qua DB và external calls khi integration hỗ trợ.
- Alert khi record `Processing` vượt ngưỡng hoặc failure rate tăng.
- Reconciliation report so sánh trạng thái DB với external systems cho workflow bị lỗi lâu.

# Code Review Challenge 2 — Endpoint tìm outlet vô tình kéo toàn bộ dữ liệu về memory

**Chủ đề:** EF Core query execution, SQL performance, input validation, cancellation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API trả outlet trong map viewport. Bảng `Outlets` có hàng triệu record. Sau khi thêm filter theo tên và bounding box, QA thấy request có lúc mất vài giây và memory của container tăng mạnh khi nhiều user pan/zoom bản đồ cùng lúc. Endpoint chỉ cần tối đa 200 outlet để render.

Database có latitude/longitude và một spatial point column ở một số environment, nhưng code hiện tại chưa tận dụng nhất quán. Yêu cầu ordering chính xác chưa được PO chốt.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/outlets")]
public sealed class OutletsController : ControllerBase
{
    private readonly AppDbContext _db;

    public OutletsController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        double bottomLeftLat,
        double bottomLeftLng,
        double topRightLat,
        double topRightLng,
        string? keyword)
    {
        var outlets = await _db.Outlets
            .Include(x => x.Region)
            .Include(x => x.Questionnaires)
            .ToListAsync();

        var result = outlets
            .Where(x => x.Latitude >= bottomLeftLat &&
                        x.Latitude <= topRightLat &&
                        x.Longitude >= bottomLeftLng &&
                        x.Longitude <= topRightLng)
            .Where(x => string.IsNullOrWhiteSpace(keyword) ||
                        x.Name.ToLower().Contains(keyword.ToLower()))
            .OrderBy(x => x.Name)
            .Select(x => new
            {
                x.Id,
                x.Name,
                x.Latitude,
                x.Longitude,
                Region = x.Region.Name,
                QuestionnaireCount = x.Questionnaires.Count
            })
            .Take(200)
            .ToList();

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ bảng trước khi filter

- **Problem:** `ToListAsync()` chạy trước bounding box, keyword và `Take`.
- **Why it happens:** Sau materialization, các operator tiếp theo chạy bằng LINQ-to-Objects.
- **Production impact:** Full/large read, allocation lớn, latency và DB/network load tăng theo kích thước bảng.
- **Severity:** Critical
- **Recommended fix:** Giữ query dưới dạng `IQueryable` cho đến projection + limit cuối cùng.

### 2. Eager-load collections không cần thiết

- **Problem:** `Include(Questionnaires)` tải entity collection chỉ để đếm.
- **Why it happens:** Projection được thực hiện sau materialization.
- **Production impact:** Tăng dữ liệu truyền, tracking và memory; collection include có thể làm result set phình mạnh tùy query shape.
- **Severity:** High
- **Recommended fix:** Project trực tiếp `QuestionnaireCount = x.Questionnaires.Count()` để provider translate thành SQL phù hợp; không `Include` khi chỉ projection.

### 3. Bounding box không được database xử lý

- **Problem:** Lat/lng filter chạy trong memory.
- **Why it happens:** Query đã materialize.
- **Production impact:** Không thể hưởng lợi từ database filtering/index strategy.
- **Severity:** High
- **Recommended fix:** Đẩy predicate xuống DB. Nếu spatial `Point` + spatial index đã được chuẩn hóa, benchmark query spatial như `Intersects` với polygon so với scalar predicates trên workload thật.

### 4. Keyword normalization gây allocation và không thể tận dụng database collation/index hiện tại

- **Problem:** `ToLower()` chạy cho mỗi entity trong memory; semantics case-insensitive phụ thuộc yêu cầu/collation.
- **Why it happens:** Filtering sau materialization và normalize bằng string allocation.
- **Production impact:** CPU/allocation tăng, behavior tìm kiếm có thể khác DB.
- **Severity:** Medium
- **Recommended fix:** Xác định semantics search trước. Dùng database collation/operator/index phù hợp provider; parameterize input và benchmark execution plan thay vì mặc định lowercase cả hai phía.

### 5. Không validate tọa độ và viewport

- **Problem:** Không kiểm tra latitude/longitude range, thứ tự corners hoặc trường hợp crossing antimeridian.
- **Why it happens:** Endpoint tin input.
- **Production impact:** Kết quả sai hoặc query cực rộng ngoài dự kiến.
- **Severity:** Medium
- **Recommended fix:** Validate ranges và business semantics; xử lý antimeridian nếu product support khu vực đó.

### 6. Không propagate request cancellation

- **Problem:** Không nhận `CancellationToken`.
- **Why it happens:** DB operation không gắn với request abort.
- **Production impact:** User pan map liên tục có thể bỏ request cũ nhưng server vẫn tiếp tục xử lý.
- **Severity:** Medium
- **Recommended fix:** Nhận `CancellationToken` và truyền vào EF Core async terminal operation.

### 7. Tracking không cần thiết cho read-only endpoint

- **Problem:** Query entity mặc định có tracking trước khi materialization.
- **Why it happens:** Không projection server-side/`AsNoTracking`.
- **Production impact:** Thêm memory/CPU không cần thiết.
- **Severity:** Medium
- **Recommended fix:** Projection trực tiếp thường tránh nhu cầu tracking entity; có thể dùng `AsNoTracking` rõ ràng cho read-only query.

### 8. Ordering requirement chưa rõ nhưng đang sort trước limit

- **Problem:** `OrderBy(Name)` có thể buộc DB sort tập match lớn sau khi fix query.
- **Why it happens:** Requirement chưa được xác nhận.
- **Production impact:** Có thể trở thành bottleneck với viewport rộng.
- **Severity:** Low
- **Recommended fix:** Clarify deterministic ordering/pagination requirement và thiết kế index/query tương ứng.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/outlets")]
public sealed class OutletsController : ControllerBase
{
    private readonly AppDbContext _db;

    public OutletsController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        double bottomLeftLat,
        double bottomLeftLng,
        double topRightLat,
        double topRightLng,
        string? keyword,
        CancellationToken ct)
    {
        if (bottomLeftLat is < -90 or > 90 ||
            topRightLat is < -90 or > 90 ||
            bottomLeftLng is < -180 or > 180 ||
            topRightLng is < -180 or > 180 ||
            bottomLeftLat > topRightLat)
        {
            return BadRequest("Invalid viewport.");
        }

        var query = _db.Outlets
            .AsNoTracking()
            .Where(x => x.Latitude >= bottomLeftLat &&
                        x.Latitude <= topRightLat &&
                        x.Longitude >= bottomLeftLng &&
                        x.Longitude <= topRightLng);

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            var term = keyword.Trim();
            query = query.Where(x => x.Name.Contains(term));
        }

        var result = await query
            .OrderBy(x => x.Name)
            .Select(x => new OutletSearchDto(
                x.Id,
                x.Name,
                x.Latitude,
                x.Longitude,
                x.Region.Name,
                x.Questionnaires.Count()))
            .Take(200)
            .ToListAsync(ct);

        return Ok(result);
    }
}

public sealed record OutletSearchDto(
    Guid Id,
    string Name,
    double Latitude,
    double Longitude,
    string Region,
    int QuestionnaireCount);
```

Đây là baseline an toàn hơn, không phải tuyên bố rằng scalar lat/lng là phương án nhanh nhất. Nếu schema đã có spatial point với SRID phù hợp và workload là viewport search, nên tạo polygon và để database thực hiện spatial predicate, sau đó kiểm tra actual execution plan và benchmark với spatial index. Search case-insensitive cũng cần chọn implementation theo SQL Server/PostgreSQL, collation và yêu cầu sản phẩm thay vì áp một công thức chung.

## Trade-offs

Projection server-side giảm memory và network nhưng query count/navigation có thể tạo SQL phức tạp hơn; cần kiểm tra generated SQL. Spatial index có thể cải thiện viewport query nhưng thêm storage/write cost và yêu cầu dữ liệu geometry/geography nhất quán. Scalar bounding-box predicates vẫn có thể hợp lý cho dataset nhỏ hoặc schema chưa sẵn sàng. `OrderBy` cho output ổn định nhưng có cost; nếu UI không cần thứ tự theo tên, một strategy khác có thể tốt hơn.

## Cách kiểm thử

1. **Integration test:** xác nhận generated query chỉ trả tối đa 200 rows và filter chạy tại DB.
2. **Load test:** mô phỏng nhiều user pan/zoom, đo p50/p95/p99 latency, DB CPU, allocations và memory.
3. **Database test:** so sánh actual execution plan/logical reads giữa scalar bounding box và spatial predicate trên dữ liệu gần production.
4. **Correctness test:** viewport biên, invalid coordinates, empty keyword, Unicode/case behavior và antimeridian nếu được support.
5. **Cancellation test:** abort request trong lúc DB query đang chạy và xác nhận cancellation được propagate.

## Quan sát trong production

- Trace duration của endpoint và database span.
- Metrics: request latency percentiles, rows returned, timeout/cancellation rate, DB CPU/logical reads nếu observability stack hỗ trợ.
- Log viewport dimensions thay vì dump dữ liệu nhạy cảm; log query category và result count.
- Theo dõi container working set/GC allocation rate trước và sau thay đổi.
- Dùng EF Core query logging có kiểm soát trong môi trường phù hợp; tránh bật sensitive-data logging tùy tiện ở production.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao spatial predicate có thể nhanh hơn scalar lat/lng comparison ngay cả trước khi xét spatial index trong một số workload, và bạn sẽ chứng minh thay vì đoán như thế nào?
2. Nếu `QuestionnaireCount` trở thành bottleneck, bạn cân nhắc những phương án nào và trade-off consistency ra sao?
3. Nếu map cần hàng nghìn điểm ở zoom-out, bạn có tiếp tục tăng `Take` hay thay đổi API/data representation?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào ranh giới transaction giữa database và external systems: retry không tự tạo idempotency, còn trạng thái `Processing` không tự tạo mutual exclusion. Workflow có side effect cần atomic claim, durable step state, uniqueness, reconciliation và observability.

Challenge 2 tập trung vào EF Core query boundary: một `ToListAsync()` đặt sai vị trí có thể biến query database thành xử lý toàn bộ dataset trong application memory. Tối ưu đúng bắt đầu từ query shape, generated SQL, execution plan và benchmark thay vì chỉ thêm index.

## Mẫu tư duy cần nhớ

- Retry luôn phải được thiết kế cùng idempotency.
- Database state transition nên enforce invariant atomically.
- Không giả định transaction local có thể rollback external side effects.
- Giữ `IQueryable` đến khi filter, projection và limit đã được biểu diễn cho database.
- Measure generated SQL, execution plan và production metrics trước khi kết luận performance.
