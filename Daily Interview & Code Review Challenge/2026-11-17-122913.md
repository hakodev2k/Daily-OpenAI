## Đoạn code cần review

```csharp
[ApiController]
[Route("api/cases")]
public sealed class AttachmentsController : ControllerBase
{
    private readonly IWebHostEnvironment _env;
    private readonly AppDbContext _db;
    private readonly ILogger<AttachmentsController> _log;

    public AttachmentsController(IWebHostEnvironment env,
        AppDbContext db, ILogger<AttachmentsController> log)
        => (_env, _db, _log) = (env, db, log);

    [HttpPost("{caseId:int}/attachments")]
    public async Task<IActionResult> Upload(
        int caseId, IFormFile file, string? folder)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Empty file");

        var caseRecord = await _db.Cases.FindAsync(caseId);
        if (caseRecord == null) return NotFound();

        var root = Path.Combine(_env.WebRootPath, "uploads");
        var directory = Path.Combine(root, folder ?? caseId.ToString());
        Directory.CreateDirectory(directory);

        var path = Path.Combine(directory, file.FileName);
        await using (var output = System.IO.File.Create(path))
            await file.CopyToAsync(output);

        var attachment = new Attachment
        {
            CaseId = caseId,
            OriginalName = file.FileName,
            PhysicalPath = path,
            UploadedBy = User.Identity?.Name ?? "anonymous",
            CreatedUtc = DateTime.UtcNow
        };
        _db.Attachments.Add(attachment);
        await _db.SaveChangesAsync();

        _log.LogInformation("Uploaded {Path} for {CaseId}", path, caseId);
        return Ok(new { attachment.Id, attachment.OriginalName });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Thiếu resource-based authorization

**Vấn đề:** Endpoint chỉ kiểm tra hồ sơ tồn tại.
**Tại sao xảy ra:** `FindAsync` không xác minh tenant, owner hoặc quyền edit.
**Ảnh hưởng production:** Người có phiên đăng nhập (hoặc anonymous nếu endpoint chưa được bảo vệ ở nơi khác) có thể gắn tài liệu vào hồ sơ không thuộc quyền.
**Cách sửa:** Bắt buộc authentication và kiểm tra policy/ACL của chính hồ sơ trước khi ghi; query phải áp dụng tenant boundary.

### [Critical] — Input quyết định đường dẫn lưu trữ

**Vấn đề:** `folder` và `file.FileName` được đưa trực tiếp vào đường dẫn.
**Tại sao xảy ra:** Dữ liệu do client cung cấp không phải storage key đáng tin cậy; tên tuyệt đối hoặc thành phần traversal có thể thay đổi đường dẫn theo nền tảng và cách chuẩn hóa.
**Ảnh hưởng production:** Ghi file ngoài vùng dự kiến hoặc ghi đè dữ liệu nếu không có kiểm soát.
**Cách sửa:** Không nhận storage folder từ client; sinh tên ngẫu nhiên server-side, giữ original name chỉ để hiển thị, cố định root.

### [High] — File có thể được public ngoài ý muốn

**Vấn đề:** Lưu trong `WebRootPath`.
**Tại sao xảy ra:** Static-file middleware/IIS có thể phục vụ nội dung trong web root tùy cấu hình.
**Ảnh hưởng production:** File nhạy cảm có thể được tải trực tiếp, bỏ qua authorization ở API.
**Cách sửa:** Lưu ngoài web root, download qua endpoint kiểm tra quyền; kiểm tra IIS virtual directories và ACL thực tế.

### [High] — Ghi đè và race condition

**Vấn đề:** `File.Create` truncate file đã tồn tại.
**Tại sao xảy ra:** Storage key phụ thuộc tên người dùng nhập.
**Ảnh hưởng production:** Mất dữ liệu và metadata trỏ tới nội dung không đúng.
**Cách sửa:** Random opaque key, `FileMode.CreateNew`, retry collision có giới hạn.

### [High] — Không giới hạn kích thước và loại file

**Vấn đề:** Chỉ kiểm tra độ dài lớn hơn 0.
**Tại sao xảy ra:** Không có upload quota, validation nội dung, chính sách extension/MIME, scanning theo threat model.
**Ảnh hưởng production:** Disk exhaustion, lưu nội dung độc hại, tăng tải bất thường.
**Cách sửa:** Giới hạn request/form và kiểm tra size thực tế, allowlist định dạng, kiểm tra signature nếu phù hợp, malware scanning/quarantine theo yêu cầu.

### [High] — File và database không atomic

**Vấn đề:** File được ghi trước khi metadata commit.
**Tại sao xảy ra:** Filesystem không tham gia transaction EF Core.
**Ảnh hưởng production:** Orphan file, file chưa hoàn tất, sai trạng thái khi tiến trình bị kill.
**Cách sửa:** Ghi vào staging, hoàn tất/flush, chuyển vào final, ghi metadata với trạng thái; có cleanup/reconciliation định kỳ. Không tuyên bố đây là distributed transaction.

### [Medium] — Không truyền cancellation và không xử lý lỗi disk

**Vấn đề:** I/O và EF Core không nhận `RequestAborted`, không có cleanup có điều kiện.
**Tại sao xảy ra:** Request cancellation và failure path chưa được thiết kế.
**Ảnh hưởng production:** I/O lãng phí sau disconnect, file rác khi hết dung lượng.
**Cách sửa:** Truyền token, cleanup file do request sở hữu; phân biệt lỗi transient và lỗi validation.

### [Medium] — Audit identity và log path chưa đủ an toàn

**Vấn đề:** Fallback `anonymous`, ghi full physical path nhưng thiếu audit decision và request correlation.
**Tại sao xảy ra:** Identity được lấy từ display name thay vì stable subject identifier.
**Ảnh hưởng production:** Khó điều tra và lộ cấu trúc filesystem trong log.
**Cách sửa:** Dùng immutable user ID/tenant ID, log attachment ID, result, duration, size; tránh sensitive paths.

## Phiên bản đề xuất

Đoạn sau minh họa đường đi chính. Giả định `ICaseAccess` đã triển khai tenant-aware authorization, `IUploadPolicy` kiểm tra size/format và `IFileStore` được cấu hình root ngoài web root với ACL giới hạn. Quy trình phục hồi orphan file vẫn cần job reconciliation.

```csharp
[Authorize]
[ApiController]
[Route("api/cases")]
public sealed class AttachmentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ICaseAccess _access;
    private readonly IUploadPolicy _policy;
    private readonly IFileStore _files;

    public AttachmentsController(
        AppDbContext db, ICaseAccess access,
        IUploadPolicy policy, IFileStore files)
        => (_db, _access, _policy, _files) =
            (db, access, policy, files);

    [HttpPost("{caseId:int}/attachments")]
    [RequestSizeLimit(32_000_000)]
    public async Task<IActionResult> Upload(
        int caseId, IFormFile file, CancellationToken ct)
    {
        if (!await _access.CanEditAsync(User, caseId, ct))
            return Forbid();

        if (file is null || !_policy.IsAllowed(file))
            return BadRequest("Invalid attachment");

        var key = Guid.NewGuid().ToString("N");
        var original = Path.GetFileName(file.FileName);
        var stored = false;
        try
        {
            await using (var input = file.OpenReadStream())
                await _files.SaveNewAsync(key, input, ct);
            stored = true;

            var entity = new Attachment
            {
                CaseId = caseId,
                StorageKey = key,
                OriginalName = original,
                UploadedBy = User.FindFirst("sub")?.Value
                    ?? throw new InvalidOperationException("Missing subject"),
                CreatedUtc = DateTime.UtcNow
            };
            _db.Attachments.Add(entity);
            await _db.SaveChangesAsync(ct);
            return Created($"/api/attachments/{entity.Id}",
                new { entity.Id, entity.OriginalName });
        }
        catch
        {
            if (stored)
                await _files.TryDeleteAsync(key, CancellationToken.None);
            throw;
        }
    }
}
```

`IFileStore.SaveNewAsync` phải enforce root cố định, exclusive creation, streaming, quota và hoàn tất file an toàn trước khi trả về. `TryDeleteAsync` phải không xóa file không thuộc request; failure của cleanup cần telemetry. Cần xử lý thêm trường hợp process crash giữa lưu file và commit DB bằng reconciliation. Với yêu cầu chống malware, chỉ publish file sau khi scanning pass.

## Giải thích thiết kế sau khi sửa

Quyền truy cập được xác thực trước side effect. Storage key tách khỏi tên gốc, giảm collision và traversal. Filesystem là dependency riêng để test failure injection. Dữ liệu download phải đi qua kiểm tra quyền tương đương. Với shared drive, cần xác nhận atomic rename có được bảo đảm trên cùng volume/share hay không.

## Trade-offs

Lưu trên shared drive giữ compatibility với legacy và chi phí migration thấp, nhưng phải tự vận hành quota, ACL, backup, orphan cleanup và HA. Azure Blob Storage là lựa chọn khi có bằng chứng về scaling/availability; không tự động giải quyết authorization hoặc malware scanning. Staging/reconciliation tăng độ phức tạp nhưng làm failure có thể phục hồi.

## Cách kiểm thử

1. **Security integration:** user tenant A upload vào case tenant B phải bị từ chối; không có file nào được tạo.
2. **Path test:** tên chứa traversal, absolute path, Unicode và ký tự đặc biệt không ảnh hưởng storage key.
3. **Concurrency:** 40 upload cùng original filename không ghi đè và trả về 40 storage keys riêng.
4. **Failure-path:** giả lập disk full, DB timeout, process crash; kiểm tra cleanup/reconciliation.
5. **Deployment validation:** xác minh IIS static-file mapping, NTFS ACL và giới hạn request thực tế.

## Quan sát trong production

Structured logs: `attachmentId`, `caseId`, tenant ID, upload outcome, correlation ID (không ghi nội dung file). Metrics: upload latency p95, bytes, rejected count, orphan count, disk free space, failures theo loại. Alert khi disk free dưới ngưỡng vận hành hoặc orphan backlog tăng. Theo dõi IIS request failures và Application Insights dependencies.

## Câu hỏi phỏng vấn mở rộng

1. Làm sao migration dữ liệu cũ sang Blob Storage mà không downtime và không phá download URL?
2. Khi shared drive tạm mất kết nối, API nên retry hay fail fast, và tại sao?
3. Nếu legal yêu cầu immutable retention, bạn sẽ thay đổi storage contract thế nào?

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Order = { id: number; customer: string; status: string }
type SearchResult = { items: Order[]; total: number }

const search = ref('')
const status = ref('all')
const page = ref(1)
const rows = ref<Order[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')

async function loadOrders() {
  loading.value = true
  error.value = ''
  const url = '/api/orders?search=' + search.value
    + '&status=' + status.value + '&page=' + page.value
  try {
    const response = await fetch(url)
    const result = await response.json() as SearchResult
    rows.value = result.items
    total.value = result.total
  } catch (e) {
    error.value = 'Cannot load orders'
  } finally {
    loading.value = false
  }
}

watch([search, status, page], loadOrders)
onMounted(loadOrders)

function changeStatus(next: string) {
  status.value = next
  page.value = 1
}
</script>

<template>
  <input v-model="search" placeholder="Customer" />
  <select :value="status" @change="changeStatus(($event.target as HTMLSelectElement).value)">
    <option value="all">All</option>
    <option value="pending">Pending</option>
    <option value="paid">Paid</option>
  </select>
  <p v-if="loading">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <table>
    <tr v-for="order in rows" :key="order.id">
      <td>{{ order.customer }}</td><td>{{ order.status }}</td>
    </tr>
  </table>
  <button @click="page++">Next</button>
  <p>Total: {{ total }}</p>
</template>
```

## Kết quả code review tham khảo

### [High] — Stale response ghi đè kết quả mới

**Vấn đề:** Mọi response đều cập nhật `rows`/`total`.
**Tại sao xảy ra:** Request chạy đồng thời và hoàn tất không theo thứ tự gửi.
**Ảnh hưởng production:** Người dùng xem hoặc thao tác trên đơn hàng không phù hợp filter đang hiển thị.
**Cách sửa:** Abort request trước và dùng request sequence guard trước mọi state write.

### [High] — Không xử lý HTTP error status

**Vấn đề:** JSON từ HTTP 4xx/5xx vẫn được coi là `SearchResult`.
**Tại sao xảy ra:** `fetch` chỉ reject cho lỗi network/abort, không tự reject cho status lỗi.
**Ảnh hưởng production:** Bảng rỗng/undefined, lỗi runtime hoặc dữ liệu sai mà không báo lỗi.
**Cách sửa:** Kiểm tra `response.ok`, validate response shape ở trust boundary nếu cần.

### [Medium] — Query string không encode

**Vấn đề:** Nối raw user input vào URL.
**Tại sao xảy ra:** `&` hoặc `#` làm thay đổi cấu trúc query.
**Ảnh hưởng production:** Filter sai, kết quả bất ngờ.
**Cách sửa:** `URLSearchParams`.

### [Medium] — Loading state không đại diện request mới nhất

**Vấn đề:** Request cũ kết thúc và đặt `loading=false` khi request mới vẫn chạy.
**Tại sao xảy ra:** `finally` không xác minh request identity.
**Ảnh hưởng production:** Spinner tắt sớm, người dùng hiểu nhầm dữ liệu đã cập nhật.
**Cách sửa:** Sequence guard trong `finally`.

### [Medium] — Quá nhiều request khi nhập

**Vấn đề:** Watch chạy mỗi thay đổi text.
**Tại sao xảy ra:** Không debounce hoặc phân biệt committed search.
**Ảnh hưởng production:** Tăng request load và cạnh tranh connection; trên mobile UX kém.
**Cách sửa:** Debounce search, không debounce status/page, hủy pending debounce khi unmount.

### [Medium] — Pagination không reset đúng khi đổi search

**Vấn đề:** Chỉ reset page khi đổi status.
**Tại sao xảy ra:** Search và pagination là state độc lập.
**Ảnh hưởng production:** Tìm kiếm mới bắt đầu ở page cũ, bảng trống dù có kết quả.
**Cách sửa:** Reset page trước khi thực hiện search mới; validate page và disable Next theo `total`.

### [Medium] — Dữ liệu cũ và error state có thể cùng xuất hiện

**Vấn đề:** Error không làm rõ bảng hiện tại thuộc filter nào.
**Tại sao xảy ra:** State chưa mô hình hóa loading/error/success theo query.
**Ảnh hưởng production:** Dữ liệu cũ bị hiểu là kết quả mới.
**Cách sửa:** Clear hoặc gắn nhãn stale state, giữ last-successful data chỉ khi UX chủ đích.

## Phiên bản đề xuất

Dùng `watch` với cleanup để hủy request khi dependency đổi, sequence guard và debounce riêng cho text. `pageSize=20` là giả định minh họa; cần khớp API contract. Code dưới đây chủ động clear rows khi query mới bắt đầu.

```vue
<script setup lang="ts">
import { ref, watch, onUnmounted } from 'vue'

type Order = { id: number; customer: string; status: string }
type Result = { items: Order[]; total: number }

const input = ref('')
const committedSearch = ref('')
const status = ref('all')
const page = ref(1)
const rows = ref<Order[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
let timer: ReturnType<typeof setTimeout> | undefined
let generation = 0

watch(input, value => {
  clearTimeout(timer)
  page.value = 1
  timer = setTimeout(() => { committedSearch.value = value }, 300)
})
watch(status, () => { page.value = 1 })

watch([committedSearch, status, page], async (
  [query, state, currentPage], _old, onCleanup
) => {
  const id = ++generation
  const controller = new AbortController()
  onCleanup(() => controller.abort())
  loading.value = true
  error.value = ''
  rows.value = []
  total.value = 0

  const params = new URLSearchParams({
    search: query, status: state, page: String(currentPage)
  })
  try {
    const response = await fetch('/api/orders?' + params, {
      signal: controller.signal
    })
    if (!response.ok) throw new Error('HTTP ' + response.status)
    const result = await response.json() as Result
    if (id !== generation) return
    if (!Array.isArray(result.items) || !Number.isFinite(result.total))
      throw new Error('Invalid response')
    rows.value = result.items
    total.value = result.total
  } catch (e) {
    if (id !== generation || controller.signal.aborted) return
    error.value = 'Cannot load orders'
  } finally {
    if (id === generation) loading.value = false
  }
}, { immediate: true })

onUnmounted(() => { clearTimeout(timer); generation++ })
</script>

<template>
  <input v-model="input" placeholder="Customer" />
  <select v-model="status">
    <option value="all">All</option>
    <option value="pending">Pending</option>
    <option value="paid">Paid</option>
  </select>
  <p v-if="loading">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <table>
    <tr v-for="order in rows" :key="order.id">
      <td>{{ order.customer }}</td>
      <td>{{ order.status }}</td>
    </tr>
  </table>
  <button :disabled="loading || page <= 1" @click="page--">Previous</button>
  <button :disabled="loading || page * 20 >= total" @click="page++">Next</button>
  <p>Total: {{ total }}</p>
</template>
```

Trong ứng dụng thực, nếu input thay đổi trong khi debounce chưa hoàn tất, phải quyết định UX: giữ kết quả của committed query với nhãn rõ ràng, hoặc invalidation ngay khi input đổi. Để bảo đảm tuyệt đối "filter hiện tại" theo input, có thể xóa rows và abort active request ngay ở watcher của `input`, hoặc disable thao tác trên bảng trong thời gian debounce. `AbortController` không đảm bảo server đã ngừng xử lý; API cần hỗ trợ cancellation và server-side limits.

## Giải thích thiết kế sau khi sửa

Sequence guard bảo vệ state ngay cả khi cancellation không ngăn được response. Query params được encode đúng. HTTP status được kiểm tra tường minh. `watch` cleanup xử lý request superseded; `immediate` thay thế `onMounted` để tránh gọi hai lần. Reset pagination phù hợp query mới.

## Trade-offs

Debounce giảm request nhưng thêm độ trễ 300 ms. Clear bảng tránh stale interpretation nhưng gây flicker; giữ stale-while-revalidate có thể tốt hơn nếu label rõ và disable action. Dùng TanStack Query/Vue Query có lợi khi cache/invalidation phức tạp, nhưng chưa cần cho màn hình đơn giản. Server vẫn cần enforce authorization và bounded pagination.

## Cách kiểm thử

1. **Playwright E2E:** route mock response A chậm hơn B; bảng cuối phải thuộc B.
2. **API failure:** HTTP 500 với JSON ProblemDetails phải hiển thị error, không render như dữ liệu.
3. **Encoding:** search `A&B #1` và Unicode được gửi chính xác.
4. **Pagination:** đổi search/status từ page 5 về page 1; Next disabled khi hết dữ liệu.
5. **Failure-path:** unmount khi request đang chạy, abort, kiểm tra không cập nhật state cũ.

## Quan sát trong production

Browser Performance/Network: request count trên mỗi lần nhập, aborted count, latency, HTTP 4xx/5xx, stale-response-suppressed count (không ghi PII từ search). Backend Application Insights: request p95/p99, dependency duration, status, correlation ID. Alert khi error rate tăng; đối chiếu frontend request burst với server load trước khi chọn caching.

## Câu hỏi phỏng vấn mở rộng

1. Khi API có cursor pagination thay vì page number, state management cần đổi thế nào?
2. Nếu người dùng chọn một order rồi filter đổi trong lúc đang mở detail, bạn bảo vệ action correctness ra sao?
3. Khi nào nên cache search result tại browser, và cache key/invalidation sẽ được thiết kế thế nào?

Resource authorization phải đi trước filesystem side effects; tên file do client cung cấp không phải storage identifier; file và database cần reconciliation thay vì giả định atomicity.
