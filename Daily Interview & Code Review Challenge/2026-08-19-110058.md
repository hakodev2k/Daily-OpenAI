# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core transaction  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để xử lý cấu hình offboarding mailbox. Job quét các cấu hình đã hết hạn, gọi Exchange/Microsoft 365 integration để reset forwarding rồi cập nhật database. Hệ thống chạy nhiều application instances và đôi khi job bị retry sau lỗi mạng. Production ghi nhận một số mailbox bị gọi reset nhiều lần, trạng thái DB không khớp với hệ thống ngoài, và thời gian job tăng mạnh khi số record hết hạn lớn.

## Đoạn code cần review

```csharp
public class OffboardingCleanupJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingCleanupJob> _logger;

    public OffboardingCleanupJob(
        AppDbContext db,
        IExchangeService exchange,
        ILogger<OffboardingCleanupJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task Run()
    {
        var expired = await _db.MailConfigs
            .Where(x => x.EndTime < DateTime.UtcNow && !x.IsReset)
            .ToListAsync();

        foreach (var config in expired)
        {
            try
            {
                await _exchange.ResetForwardingAsync(config.UserEmail);

                config.IsReset = true;
                config.ResetAt = DateTime.UtcNow;

                await _db.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed to reset mailbox {Email} config {@Config}",
                    config.UserEmail,
                    config);
            }
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Tìm rủi ro concurrency, retry và performance.
3. Giải thích impact khi chạy nhiều worker/instance.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation an toàn hơn.
6. Nêu cách test concurrency và failure recovery.
7. Đề xuất logs, traces và metrics cần theo dõi.

## Câu hỏi gợi mở

- Hai worker có thể cùng đọc một record `IsReset = false` không?
- Nếu external call thành công nhưng `SaveChangesAsync` thất bại thì chuyện gì xảy ra khi retry?
- Việc bắt exception rồi tiếp tục ảnh hưởng thế nào tới retry semantics của Hangfire?
- Có nên load toàn bộ record hết hạn trong một lần không?
- Log hiện tại có nguy cơ chứa dữ liệu không cần thiết không?

## Gợi ý

### Gợi ý 1

Hãy phân biệt **exactly-once execution** với **idempotent effect**; background job retry không tự biến external side effect thành exactly-once.

### Gợi ý 2

Hãy xem xét claim/lease hoặc optimistic concurrency ở database, idempotency ở integration boundary, batching, cancellation và cách biểu diễn trạng thái `Pending/InProgress/Completed/Failed`.

## Kết quả code review tham khảo

### 1. Race condition khi nhiều worker cùng chọn record

- **Problem:** query rồi xử lý là read-modify-write không atomic.
- **Why:** nhiều worker có thể cùng thấy `IsReset = false`.
- **Impact:** external side effect bị thực hiện nhiều lần.
- **Severity:** Critical.
- **Fix:** claim work atomically bằng trạng thái/lease hoặc concurrency token; external operation vẫn phải idempotent nếu có thể.

### 2. Dual-write inconsistency giữa Exchange và database

- **Problem:** external call và DB update không nằm trong một atomic transaction chung.
- **Why:** Exchange có thể thành công nhưng DB save thất bại.
- **Impact:** retry gọi external operation lần nữa.
- **Severity:** Critical.
- **Fix:** thiết kế operation idempotent, lưu operation/idempotency key, reconciliation; không giả định distributed transaction.

### 3. Nuốt exception làm mất retry cấp job

- **Problem:** mọi exception đều bị catch và không throw lại.
- **Why:** Hangfire có thể coi invocation hoàn tất dù một số item thất bại.
- **Impact:** record lỗi có thể nằm lại vô thời hạn nếu không có lần quét tiếp theo phù hợp.
- **Severity:** High.
- **Fix:** lưu trạng thái failure/retry có chủ đích hoặc chia thành per-item jobs; phân loại transient/permanent errors.

### 4. Không có explicit processing state/lease

- **Problem:** chỉ có boolean `IsReset`.
- **Impact:** khó phân biệt chưa chạy, đang chạy, lỗi, cần retry và worker chết giữa chừng.
- **Severity:** High.
- **Fix:** state machine + `LeaseUntil`, `AttemptCount`, `LastErrorCode`, `CompletedAt`.

### 5. Load toàn bộ expired records

- **Problem:** `ToListAsync()` không batch/limit.
- **Impact:** memory pressure, tracking overhead, job kéo dài.
- **Severity:** Medium.
- **Fix:** claim theo batch nhỏ, ví dụ 50–200 tùy workload, đo rồi điều chỉnh.

### 6. Không truyền CancellationToken

- **Problem:** query và external call không thể dừng cooperative khi shutdown.
- **Impact:** deployment/shutdown kéo dài hoặc operation tiếp tục ngoài mong muốn.
- **Severity:** Medium.
- **Fix:** truyền cancellation token xuyên suốt nếu integration hỗ trợ.

### 7. SaveChanges mỗi item

- **Problem:** tăng round trips DB.
- **Impact:** throughput thấp khi volume lớn.
- **Severity:** Medium.
- **Fix:** cân bằng batching với durability; nếu mỗi item là một state transition độc lập thì per-item save có thể chấp nhận được nhưng cần đo.

### 8. Structured logging có thể log quá nhiều entity data

- **Problem:** `{@Config}` serialize object rộng.
- **Impact:** PII leakage, log volume cao.
- **Severity:** Medium.
- **Fix:** log identifiers/status/error category cần thiết, mask dữ liệu nhạy cảm.

## Phiên bản code đề xuất

```csharp
public sealed class OffboardingCleanupJob
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<OffboardingCleanupJob> _logger;

    public OffboardingCleanupJob(
        IServiceScopeFactory scopeFactory,
        ILogger<OffboardingCleanupJob> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<IOffboardingResetProcessor>();

            var claimed = await processor.ClaimBatchAsync(100, ct);
            if (claimed.Count == 0)
                return;

            foreach (var item in claimed)
            {
                ct.ThrowIfCancellationRequested();

                try
                {
                    await processor.ResetMailboxIdempotentlyAsync(
                        item.Id,
                        item.OperationId,
                        ct);

                    await processor.MarkCompletedAsync(item.Id, ct);
                }
                catch (OperationCanceledException) when (ct.IsCancellationRequested)
                {
                    throw;
                }
                catch (Exception ex)
                {
                    await processor.MarkFailedAsync(item.Id, ex, ct);
                    _logger.LogError(ex,
                        "Offboarding reset failed. ConfigId={ConfigId} OperationId={OperationId}",
                        item.Id,
                        item.OperationId);
                }
            }
        }
    }
}
```

`ClaimBatchAsync` cần thực hiện claim có concurrency control ở database; implementation cụ thể phụ thuộc SQL Server/PostgreSQL. `ResetMailboxIdempotentlyAsync` không nên hứa exactly-once nếu API ngoài không hỗ trợ idempotency; khi đó cần read-before-write/reconciliation phù hợp với semantics của operation.

## Trade-offs

Claim/lease làm model phức tạp hơn boolean nhưng cung cấp recovery tốt khi worker chết. Per-item job trong Hangfire có thể tận dụng retry/visibility tốt hơn nhưng tạo nhiều jobs. Distributed lock có thể giảm concurrent execution nhưng không giải quyết dual-write failure và không thay thế idempotency.

## Cách kiểm thử

1. Chạy đồng thời 10 workers claim cùng 100 records; mỗi record chỉ được một worker claim tại một thời điểm.
2. External reset thành công nhưng DB completion fail; retry không tạo side effect sai.
3. Worker chết sau khi claim; record được reclaim sau lease expiry.
4. External API trả transient timeout rồi phục hồi; retry/backoff đúng và không retry permanent error vô hạn.
5. Load test hàng chục nghìn expired records để kiểm tra memory, DB round trips và throughput.

## Quan sát trong production

Theo dõi `claimed/completed/failed/retried`, processing latency, lease expirations, attempt count, external API latency/error rate, backlog age, DB query duration và số operation cần reconciliation. Trace nên liên kết `ConfigId`, `OperationId`, job invocation và external request nhưng tránh PII không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Distributed lock có đủ để bảo đảm không duplicate side effect không? Vì sao?
2. Nếu Exchange API không có idempotency key, bạn thiết kế reconciliation thế nào?
3. Khi nào bạn tách mỗi mailbox thành một Hangfire job riêng?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log có authorization và SQL injection risk

**Chủ đề:** Authorization, SQL correctness/security, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Portal nội bộ cung cấp endpoint tìm audit log theo tenant. Người dùng đã đăng nhập bằng JWT. Endpoint được dùng bởi support và tenant admin. Sau một security review, team phát hiện khả năng người dùng tenant A xem dữ liệu tenant B và database CPU tăng khi search chuỗi dài. Requirements về role cụ thể chưa được mô tả đầy đủ.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        string tenantId,
        string? text,
        int page = 1)
    {
        var sql = $@"
            SELECT * FROM AuditLogs
            WHERE TenantId = '{tenantId}'
              AND Message LIKE '%{text}%'
            ORDER BY CreatedAt DESC";

        _logger.LogInformation("Audit query: {Sql}", sql);

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .Skip((page - 1) * 100)
            .Take(100)
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/security/performance issues.
2. Giải thích production impact.
3. Ưu tiên severity.
4. Đề xuất authorization model và query an toàn.
5. Nêu test strategy.
6. Đề xuất logs/metrics/traces phù hợp.

## Câu hỏi gợi mở

- `[Authorize]` chứng minh được điều gì và chưa chứng minh được điều gì?
- `tenantId` lấy từ query string có đáng tin không?
- User-controlled strings đi vào `FromSqlRaw` như thế nào?
- `SELECT *` và trả entity trực tiếp có ảnh hưởng gì?
- Search `%text%` có đặc tính performance nào cần đo?

### Gợi ý 1

Authentication không đồng nghĩa với tenant authorization; hãy xác định nguồn tenant identity đáng tin cậy.

### Gợi ý 2

Xem xét parameterized/LINQ query, policy-based authorization, projection DTO, input bounds và index/search strategy.

## Kết quả code review tham khảo

### 1. SQL injection

- **Problem:** `tenantId` và `text` được interpolate trực tiếp vào SQL.
- **Why:** `FromSqlRaw` nhận chuỗi SQL đã được ghép từ input.
- **Impact:** query manipulation/data exposure hoặc phá hoại tùy quyền DB account.
- **Severity:** Critical.
- **Fix:** dùng LINQ hoặc parameterization; không concatenate untrusted input.

### 2. Broken tenant-level authorization

- **Problem:** caller tự truyền `tenantId`; `[Authorize]` chỉ yêu cầu authenticated principal theo cấu hình, không tự kiểm tra caller được phép truy cập tenant đó.
- **Impact:** cross-tenant data exposure.
- **Severity:** Critical.
- **Fix:** derive tenant từ trusted claim/server-side membership hoặc authorize requested tenant bằng policy/resource authorization.

### 3. Log raw SQL chứa user input

- **Problem:** log toàn bộ SQL.
- **Impact:** sensitive search terms, tenant identifiers và malicious payload vào logs; log forging/volume concerns tùy sink.
- **Severity:** High.
- **Fix:** structured metadata tối thiểu; không log raw query text/input nếu không cần.

### 4. Trả entity trực tiếp

- **Problem:** `SELECT *` + serialize entity.
- **Impact:** accidental sensitive-field exposure và coupling API với persistence model.
- **Severity:** High.
- **Fix:** projection DTO với allow-list fields.

### 5. Không validate page/text bounds

- **Problem:** page <= 0 hoặc text rất dài.
- **Impact:** invalid offset, expensive queries, abuse.
- **Severity:** Medium.
- **Fix:** validate page, page size cố định/capped, giới hạn search length.

### 6. Contains search có thể scan lớn

- **Problem:** `%term%` thường không tận dụng B-tree index theo cách prefix lookup thông thường.
- **Impact:** CPU/I/O tăng khi audit table lớn.
- **Severity:** Medium.
- **Fix:** đo execution plan; cân nhắc search-specific indexing/full-text/search engine nếu requirement và scale cần.

### 7. Offset pagination suy giảm ở page sâu

- **Problem:** `Skip` lớn làm database phải xử lý nhiều rows trước khi trả page.
- **Impact:** latency tăng theo page depth.
- **Severity:** Medium.
- **Fix:** keyset/cursor pagination bằng `(CreatedAt, Id)` nếu UX phù hợp.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "AuditReader")]
[HttpGet]
public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
    [FromQuery] string? text,
    [FromQuery] DateTimeOffset? before,
    CancellationToken ct)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    if (text is { Length: > 200 })
        return BadRequest("Search text is too long.");

    var query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(text))
        query = query.Where(x => x.Message.Contains(text));

    if (before.HasValue)
        query = query.Where(x => x.CreatedAt < before.Value);

    var rows = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Select(x => new AuditLogDto(
            x.Id,
            x.CreatedAt,
            x.EventType,
            x.Message))
        .Take(100)
        .ToListAsync(ct);

    return Ok(rows);
}
```

Đây là hướng tham khảo: claim name, policy và tenant-membership model phải khớp identity architecture thực tế. `Contains` an toàn hơn raw interpolation về injection nhưng không tự giải quyết search performance; cần benchmark và execution plan trên database thật.

## Trade-offs

Tenant từ token đơn giản nếu mỗi principal chỉ thuộc một tenant và token claims đáng tin/cập nhật phù hợp. Nếu support user có thể truy cập nhiều tenant, resource-based authorization hoặc server-side membership lookup rõ ràng hơn. Keyset pagination hiệu quả cho feed tuần tự nhưng khó hỗ trợ nhảy trực tiếp tới page N. Full-text/search service tăng vận hành và consistency complexity, chỉ nên thêm khi workload chứng minh cần thiết.

## Cách kiểm thử

1. Security integration test: tenant A yêu cầu tenant B phải bị từ chối và không leak row.
2. Injection payload trong `text`/tenant input không thay đổi query semantics.
3. Role không có `AuditReader` nhận 403.
4. Kiểm tra DTO không serialize sensitive columns.
5. Load test search trên dataset production-like; inspect execution plan, p95/p99 latency và DB CPU.

## Quan sát trong production

Log actor ID pseudonymous/appropriate identifier, authorized tenant, request correlation, result count, duration và denial reason category; không log raw sensitive search text. Theo dõi 401/403, query latency, DB CPU/I/O, slow-query count, page/cursor usage và security anomaly theo tenant.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support engineer được phép chọn tenant bất kỳ trong một tập tenant, bạn implement authorization thế nào?
2. Global query filter của EF Core có đủ để thay thế authorization không?
3. Khi nào bạn chuyển audit search sang full-text hoặc một search service riêng?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Background processing đáng tin cậy cần thiết kế concurrency, retry và idempotency cùng nhau; distributed lock không tự giải quyết external side-effect consistency. Với multi-tenant API, authentication chỉ xác nhận principal; authorization phải kiểm tra quyền trên resource/tenant cụ thể. SQL parameterization, projection DTO và observability tối thiểu dữ liệu là các boundary controls quan trọng.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency và reconciliation.
- Không biến read-then-write thành giả định atomic.
- Authentication ≠ authorization; luôn kiểm tra resource boundary.
- Parameterize mọi untrusted input và giảm dữ liệu trả về theo allow-list.
- Measure query plans/latency trước khi chọn optimization hoặc search architecture.
