# Câu 1 — Vì sao deep pagination bằng `OFFSET` ngày càng chậm dù đã có index?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** SQL Server, PostgreSQL, indexes, execution plan, pagination, API design, query performance, consistency

## Bối cảnh

Một REST API phục vụ danh sách order cho enterprise portal. Backend là ASP.NET Core + EF Core, database chính là SQL Server; một deployment khác của cùng sản phẩm đang đánh giá PostgreSQL.

Endpoint hiện tại hỗ trợ:

- sort theo `CreatedAt DESC`;
- filter theo `CustomerId`, `Status`, khoảng thời gian;
- pagination bằng `pageNumber` và `pageSize`;
- `pageSize` mặc định 50;
- UI đôi khi cho phép user nhảy trực tiếp tới page 500–1000.

EF Core query cuối cùng tương đương:

```sql
SELECT ...
FROM Orders
WHERE CustomerId = @customerId
ORDER BY CreatedAt DESC
OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY;
```

Production symptoms:

- page 1 khoảng vài chục ms;
- page 20 vẫn chấp nhận được;
- page 500 có thể mất vài giây;
- CPU database tăng trong giờ cao điểm;
- execution plan vẫn cho thấy có dùng index;
- team đã tạo index trên `CreatedAt` nhưng deep pages vẫn chậm;
- một developer đề xuất “thêm Redis để cache page 500”;
- một developer khác đề xuất tăng `pageSize` để giảm số lần user phải chuyển trang.

Chưa biết chắc:

- index hiện tại là đơn cột hay composite;
- filter cardinality thực tế;
- có duplicate `CreatedAt` hay không;
- user có thật sự cần random access tới page 1000 hay chỉ cần “load more”;
- dữ liệu có thay đổi liên tục trong lúc user đang paging hay không;
- API contract có cho phép đổi từ page-number sang cursor/keyset pagination hay không.

## Câu hỏi chính

Hãy giải thích vì sao `OFFSET` có thể ngày càng đắt khi đi sâu vào tập dữ liệu ngay cả khi database dùng index, điều gì xảy ra trong query execution, và bạn sẽ thiết kế lại pagination/query/index như thế nào để cải thiện latency mà vẫn giữ correctness và UX phù hợp.

## Câu hỏi làm rõ nên cân nhắc

1. User có thật sự cần nhảy tới page bất kỳ hay chỉ cần đi tiếp/lùi tuần tự?
2. Sort order có duy nhất không, hay nhiều records có cùng `CreatedAt`?
3. Filter phổ biến nhất là gì và selectivity của `CustomerId`, `Status`, date range ra sao?
4. Có requirement giữ snapshot ổn định trong suốt phiên paging hay chấp nhận dữ liệu mới chen vào giữa các request?
5. Response có cần total count chính xác ở mọi request hay có thể tách/approximate/lazy-load?

## Gợi ý tư duy

### Gợi ý 1

Index giúp tìm và đọc theo thứ tự, nhưng `OFFSET N` vẫn yêu cầu database xử lý/bỏ qua một lượng rows trước khi trả page hiện tại.

### Gợi ý 2

Pagination correctness phụ thuộc sort order ổn định. `ORDER BY CreatedAt` đơn thuần có thể không đủ nếu timestamp trùng nhau.

### Gợi ý 3

Nếu UX không cần random page jump, keyset/cursor pagination thường thay đổi bản chất bài toán từ “bỏ qua N rows” thành “tiếp tục từ key cuối cùng đã thấy”.

## Cấu trúc trả lời đề xuất

1. Làm rõ UX và consistency requirement.
2. Mô tả query execution của `OFFSET` ở page nông và page sâu.
3. Đọc execution plan + logical reads + duration theo nhiều `skip` values.
4. Kiểm tra index key order và filter selectivity.
5. Kiểm tra sort uniqueness/stability.
6. So sánh page-number với keyset/cursor.
7. Thiết kế API cursor contract.
8. Xử lý total count riêng.
9. Test correctness khi có inserts/updates đồng thời.
10. Theo dõi p95/p99 và database workload sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu rằng dùng index không có nghĩa query cost không tăng theo `OFFSET`.
- Đo logical reads, duration và execution plan thay vì chỉ nhìn “index seek/scan”.
- Không mặc định “thêm index” là đủ; phải khớp filter + order pattern.
- Nhận ra sort cần deterministic, thường cần tie-breaker như `(CreatedAt, Id)`.
- Biết keyset/cursor pagination phù hợp khi user đi tuần tự.
- Nêu trade-off: keyset không hỗ trợ random page jump tự nhiên như page-number.
- Không dùng Redis như fix mặc định khi root cause nằm ở access pattern/query shape.

### Điểm cộng

- Đề xuất composite index theo dominant query pattern, ví dụ cân nhắc `CustomerId`, `CreatedAt`, `Id`, nhưng chỉ sau khi xem execution plan/cardinality.
- Tách total count khỏi data page nếu `COUNT(*)` trở thành bottleneck riêng.
- Giải thích inserts giữa hai requests có thể làm page-number bị duplicate/missing rows.
- Đề xuất opaque cursor thay vì expose raw SQL-specific implementation details.

### Senior+

- Thiết kế cursor versioning/signing hoặc validation để tránh client chỉnh sửa cursor tùy ý.
- Phân tích direction both ways: next/previous với descending sort.
- Nêu cách keyset điều kiện lexicographic hoạt động với tie-breaker.
- Đặt measurable SLO cho p95/p99 theo representative dataset thay vì benchmark bằng vài nghìn rows local.

## Hướng giải quyết tham khảo

Tôi sẽ không kết luận “index không hoạt động” chỉ vì page 500 chậm. Với `OFFSET`, database vẫn phải xác định thứ tự và đi qua các rows trước điểm bắt đầu. Nếu `skip = 25,000`, engine phải đọc/xử lý đủ để bỏ qua 25,000 rows rồi mới trả 50 rows tiếp theo. Index có thể giúp tránh sort đắt và giúp access theo order, nhưng chi phí bỏ qua vẫn tăng theo vị trí sâu.

Tôi sẽ lấy execution plan thực tế và đo tối thiểu:

- elapsed time;
- CPU time;
- logical reads;
- rows read vs rows returned;
- operator nào tăng cost;
- memory grant/sort nếu có;
- ảnh hưởng của từng filter phổ biến.

Sau đó benchmark cùng query ở `OFFSET 0`, 1,000, 10,000, 50,000... trên dataset production-like. Nếu logical reads tăng gần tuyến tính theo offset, đó là evidence rõ.

Index phải khớp access pattern. Ví dụ nếu query gần như luôn `WHERE CustomerId = ? ORDER BY CreatedAt DESC, Id DESC`, một index bắt đầu bằng `CustomerId` rồi tới sort keys có thể phù hợp hơn index chỉ có `CreatedAt`. Nhưng tôi không tự áp một index recipe cố định vì selectivity, included columns, write overhead và query mix có thể khác. Tôi cần actual plan và workload.

Về correctness, `CreatedAt` có thể trùng nhau. Nếu chỉ order theo timestamp, database không đảm bảo thứ tự ổn định giữa rows đồng hạng. Tôi sẽ dùng deterministic order, ví dụ:

```sql
ORDER BY CreatedAt DESC, Id DESC
```

Nếu business/UI chỉ cần next/previous hoặc infinite scrolling, tôi ưu tiên keyset pagination. Client gửi cursor đại diện cho row cuối page trước, ví dụ `(CreatedAt, Id)`. Query page tiếp theo sẽ dạng logic:

```sql
WHERE CustomerId = @customerId
  AND (
       CreatedAt < @lastCreatedAt
       OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
      )
ORDER BY CreatedAt DESC, Id DESC
FETCH FIRST @take ROWS ONLY;
```

Cú pháp cụ thể khác giữa SQL Server/PostgreSQL, nhưng principle là tiếp tục từ key boundary thay vì skip N rows. Với index phù hợp, engine có thể seek gần vị trí cần đọc và chỉ lấy page tiếp theo.

API không nhất thiết expose raw timestamp/id. Tôi có thể trả opaque cursor:

```json
{
  "items": [...],
  "nextCursor": "...",
  "hasMore": true
}
```

Cursor encode các sort keys cần thiết và có thể ký/validate nếu client không được phép sửa. Nếu filters/sort thay đổi, cursor cũ phải bị reject hoặc versioned để tránh semantics sai.

Trade-off chính: keyset pagination không dễ nhảy trực tiếp tới page 731. Nếu user thật sự cần random page jump, page-number có thể vẫn cần cho một số view, nhưng tôi sẽ xác minh use case. Nhiều UI hiển thị page numbers theo thói quen nhưng user thực tế chỉ dùng first/next/search/filter.

Nếu random access là requirement thật, có thể giữ page-number cho shallow pages, giới hạn maximum deep page, hoặc xây specialized reporting/export path thay vì bắt interactive API scan sâu. Quyết định này là product/API decision chứ không chỉ SQL tuning.

Tôi cũng tách câu chuyện `COUNT(*)`. Một endpoint có thể tối ưu page data nhưng vẫn chậm vì mỗi request chạy count lớn để tính total pages. Có thể cache/compute count riêng, chỉ tính khi cần, hoặc cung cấp `hasMore` thay vì exact total nếu UX cho phép. Nhưng phải thỏa requirement, không silently đổi contract.

Về consistency: với page-number, inserts mới ở đầu danh sách có thể đẩy rows sang page khác, khiến user thấy duplicate/missing rows giữa request 1 và 2. Keyset ổn định hơn cho forward traversal theo boundary đã thấy, nhưng vẫn không tạo snapshot isolation tự động. Nếu business cần snapshot cố định, cần thêm snapshot/version/time boundary hoặc transaction/session strategy phù hợp, với cost riêng.

Testing tôi muốn có:

- duplicate `CreatedAt`;
- rows insert giữa page 1 và page 2;
- filter cardinality thấp/cao;
- deep paging dataset lớn;
- next/previous direction;
- cursor bị sửa hoặc dùng với filter khác;
- query plan regression sau schema/index change.

Production telemetry: p50/p95/p99 theo endpoint, page depth hoặc cursor mode, DB dependency duration, logical reads/query-store data nếu có, timeouts, rows returned, total-count duration và index usage/write overhead.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhìn thấy `Index Seek` rồi kết luận query đã tối ưu. Với `OFFSET`, database vẫn phải đi qua và bỏ N rows trước khi trả page hiện tại, nên page càng sâu thì logical reads và CPU thường càng tăng. Em sẽ đo execution plan thực tế, logical reads và duration theo nhiều offset để chứng minh.

Nếu access pattern chủ yếu là `CustomerId + CreatedAt DESC`, em kiểm tra composite index khớp filter/order, nhưng em cũng làm sort deterministic bằng `CreatedAt, Id`. Nếu UX chỉ cần next/previous, em đổi sang keyset pagination: cursor chứa key cuối page trước và query `WHERE key < lastKey` thay vì `OFFSET N`.

Trade-off là keyset không nhảy trực tiếp tới page tùy ý, nên em cần Product xác nhận random page jump có thật sự cần. Em cũng tách exact total count nếu nó là bottleneck riêng, rồi load test dataset production-like và theo dõi p95/p99, logical reads và database CPU trước/sau.”

## Câu hỏi đào sâu

1. Nếu Product bắt buộc user phải nhảy trực tiếp tới page 800, bạn giữ UX đó thế nào mà vẫn kiểm soát database cost?
2. Nếu `CreatedAt` có thể được chỉnh sửa sau khi order tạo, cursor dựa trên `(CreatedAt, Id)` có rủi ro gì?
3. Nếu execution plan cho page sâu vẫn dùng index seek nhưng logical reads rất cao, bạn giải thích thế nào với reviewer nói rằng “seek nghĩa là O(1)”?

## Lỗi trả lời thường gặp

- Chỉ nói “thêm index” mà không xem rows read/logical reads.
- Cho rằng index seek luôn đồng nghĩa query rẻ.
- Đổi sang keyset nhưng không có deterministic tie-breaker.
- Dùng Redis để cache hàng nghìn page không ổn định mà không xử lý root cause.
- Bỏ exact total count hoặc random paging mà không xác minh requirement.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất thêm index/cache mà không hiểu `OFFSET` cost.
- **3–4:** Nhận ra deep pagination nhưng thiếu execution-plan evidence và correctness.
- **5–6:** Có index reasoning, deterministic order và keyset design cơ bản.
- **7–8:** Có cursor contract, concurrency/data-change reasoning, count strategy và monitoring.
- **9–10:** Cân bằng UX/API/DB cost, chứng minh bằng workload evidence, xử lý snapshot semantics và nêu rõ điều kiện recommendation thay đổi.

# Câu 2 — Kubernetes rolling deployment gây 503 dù Pod vẫn “Running”

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, readiness/liveness, graceful shutdown, rolling deployment, health checks, observability, deployment safety

## Bối cảnh

Một ASP.NET Core .NET 8 API được containerize và chạy trên Kubernetes. Service nhận traffic từ ingress tới một Deployment có 8 replicas.

Sau một release, deployment pipeline báo thành công nhưng trong khoảng 2–4 phút user thấy spike HTTP 503 và một số request bị reset.

Quan sát ban đầu:

- Pods mới chuyển sang trạng thái `Running` khá nhanh;
- một số Pods cũ bị terminate trong lúc vẫn còn request dài 20–40 giây;
- readiness và liveness đang trỏ cùng endpoint `/health`;
- `/health` chỉ trả 200 nếu cả database và một third-party API đều reachable;
- khi third-party API chậm vài giây, một số Pods bị restart;
- application startup cần warm cache khoảng 15–25 giây;
- container có `terminationGracePeriodSeconds: 30`;
- `preStop` chưa được cấu hình;
- pipeline không có synthetic traffic validation sau rollout;
- team đề xuất tăng replicas từ 8 lên 20 để “che” lỗi deploy.

Chưa biết chắc:

- `maxUnavailable`/`maxSurge` hiện tại;
- probe initial delays/periods/failure thresholds;
- endpoint `/health` có phân biệt startup/readiness/liveness hay không;
- ingress/service endpoint propagation nhanh đến đâu trong cluster hiện tại;
- application có xử lý `SIGTERM` và stop accepting new work đúng cách không;
- long-running requests có thể được retry an toàn hay không;
- Pod resources có bị CPU/memory throttling trong warm-up hay không.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào, dùng evidence gì để phân biệt probe misconfiguration, insufficient rollout capacity và graceful-shutdown failure, sau đó thiết kế lại probes + lifecycle + rollout validation như thế nào để giảm 503 mà không chỉ tăng số replicas?

## Câu hỏi làm rõ nên cân nhắc

1. `kubectl describe pod`/events cho thấy Pods restart vì liveness failure, OOM, crash hay nguyên nhân khác?
2. Readiness failure có xảy ra trước 503 spike không, và số ready endpoints của Service giảm xuống bao nhiêu trong rollout?
3. Long-running requests là idempotent/read-only hay có side effects khiến retry nguy hiểm?
4. Application warm-up cần dependency nào, và readiness có chỉ bật sau khi application thật sự có thể phục vụ traffic không?
5. Current rolling strategy cho phép bao nhiêu Pods unavailable đồng thời và capacity còn lại có chịu peak load không?

## Gợi ý tư duy

### Gợi ý 1

`Running` chỉ nói container/process đang chạy; nó không đồng nghĩa application đã `Ready` để nhận traffic.

### Gợi ý 2

Liveness không nên biến một dependency outage tạm thời thành restart storm nếu process bản thân vẫn có thể recover.

### Gợi ý 3

Rollout an toàn cần lifecycle hai chiều: startup phải chờ thật sự ready; shutdown phải ngừng nhận traffic rồi mới kết thúc in-flight work trong giới hạn hợp lý.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact và tạm dừng/rollback rollout nếu cần.
2. Dựng timeline Deployment → Pod lifecycle → Service endpoints → 503.
3. Kiểm tra Pod events/restarts/probe failures/resources.
4. Phân biệt startup, readiness và liveness semantics.
5. Kiểm tra rollout capacity (`maxUnavailable`, `maxSurge`).
6. Kiểm tra SIGTERM/graceful shutdown/in-flight request behavior.
7. Redesign health endpoints và thresholds.
8. Thêm deployment validation/canary/synthetic checks.
9. Failure-injection test dependency outage và slow requests.
10. Theo dõi rollout SLO + automatic abort criteria.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi `Pod Running` là bằng chứng application ready.
- Tách startup/readiness/liveness theo mục đích.
- Không để liveness phụ thuộc trực tiếp vào third-party transient availability nếu process vẫn healthy.
- Readiness dùng để quyết định instance có thể nhận traffic hay không.
- Có graceful shutdown: ngừng nhận traffic, xử lý in-flight trong grace window, propagate cancellation.
- Kiểm tra rollout capacity trước khi tăng replicas mù quáng.
- Có rollback/pause strategy khi 5xx tăng trong deployment.
- Quan sát Pod events, restart reason, endpoint count, ingress/service metrics.

### Điểm cộng

- Dùng ASP.NET Core health checks với tags/endpoints khác nhau cho liveness/readiness.
- Đề xuất startup probe khi app có warm-up dài để tránh liveness giết container trong startup.
- Đánh giá `terminationGracePeriodSeconds` dựa trên actual request duration, không chọn số ngẫu nhiên.
- Dùng `preStop`/readiness transition khi cần để tạo thời gian drain, nhưng xác minh behavior của ingress/service trong environment thật.
- Bounded timeout cho third-party dependency thay vì health endpoint treo lâu.

### Senior+

- Thiết kế deployment health gate dựa trên error rate, ready replicas, latency và restart count.
- Phân biệt request draining với background jobs/queue consumers khi Pod shutdown.
- Đề xuất PodDisruptionBudget chỉ khi availability objective và disruption model justify, không coi nó là fix cho mọi rollout.
- Nêu interaction giữa autoscaling, warm-up và rolling deployment capacity.

## Hướng giải quyết tham khảo

Trong incident, nếu 503 tăng rõ theo rollout và ảnh hưởng user, tôi ưu tiên pause/rollback release trước khi “tune probes live”. Sau đó dựng timeline cụ thể:

- Deployment bắt đầu lúc nào;
- replica set cũ/mới có bao nhiêu Pods;
- mỗi Pod lúc nào start, Ready, NotReady, terminate;
- probe failures;
- container restart reason;
- Service endpoint count theo thời gian;
- ingress 5xx/latency;
- request termination/reset logs.

Điểm đầu tiên: Kubernetes Pod `Running` không đồng nghĩa ready. Một Pod có thể process đang chạy nhưng readiness chưa pass. Traffic routing thông thường dựa vào ready endpoints, nên tôi cần nhìn readiness state chứ không chỉ `kubectl get pods` status column.

Tôi sẽ tách health semantics:

### Startup

Nếu app cần 15–25 giây warm cache/start dependencies, startup probe có thể bảo vệ giai đoạn này để liveness không restart process quá sớm. Startup chỉ nên pass khi initialization cần thiết hoàn tất.

### Readiness

Readiness trả fail khi instance tạm thời không nên nhận traffic. Ví dụ app chưa warm xong, local critical resource chưa sẵn sàng, hoặc đang draining. Dependency check cần cẩn thận: nếu third-party outage khiến mọi Pod cùng NotReady, Service có thể mất toàn bộ endpoints. Nếu application có thể phục vụ degraded responses hoặc requests không phụ thuộc third-party, readiness không nên vô điều kiện fail vì dependency đó. Phải theo actual capability.

### Liveness

Liveness trả lời câu hỏi process có bị kẹt/không thể tự phục hồi hay không. Tôi không dùng một third-party API reachability làm liveness condition mặc định. Nếu provider down 30 giây mà Pods đều bị liveness restart, hệ thống biến một dependency incident thành restart storm và mất local warm state.

Với ASP.NET Core, có thể đăng ký health checks theo tags rồi map endpoint riêng, ví dụ conceptual:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<SelfHealthCheck>("self", tags: new[] { "live" })
    .AddCheck<DatabaseHealthCheck>("db", tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Đây là pattern minh họa; exact dependency checks và thresholds phải dựa trên service behavior. Không nên ping external dependency quá nặng ở tần suất probe cao.

Rolling strategy cũng cần inspect. Nếu `maxUnavailable` cho phép mất nhiều capacity trong lúc Pods mới warm chậm, remaining replicas có thể overload. Tôi sẽ đo per-pod utilization trong rollout, request concurrency và ready replica count. `maxSurge` có thể cho thêm temporary capacity, nhưng resource quota/cluster capacity phải đủ. Không tăng replicas vĩnh viễn nếu vấn đề là lifecycle bug.

Shutdown path quan trọng không kém startup. Khi Pod nhận SIGTERM, application nên bắt đầu shutdown gracefully, ngừng nhận new work theo lifecycle Kubernetes/hosting, cho in-flight request hoàn tất trong grace window nếu hợp lý, và propagate cancellation tới downstream I/O. Nếu request dài 40 giây mà grace period chỉ 30 giây, một số request có thể bị cắt. Nhưng tôi không đơn giản tăng grace lên 10 phút; cần xem request SLA và liệu request có thể checkpoint/retry/idempotent hay nên chuyển long work ra background processing.

`preStop` có thể hữu ích trong một số ingress/service environments để tạo drain delay trước process termination, nhưng không phải universal magic sleep. Tôi sẽ xác minh endpoint removal/traffic behavior trong cluster thật, tránh thêm sleep lớn mà không evidence.

Nếu long-running request có side effect, retry ở client/ingress có thể tạo duplicate. Vì vậy graceful shutdown và idempotency phải được xem cùng nhau.

Testing trước production:

- rollout dưới representative load;
- warm-up chậm 30–60 giây;
- third-party timeout/outage;
- DB transient failure;
- Pod terminate giữa request 40 giây;
- liveness failure thật (process deadlock/unresponsive simulation phù hợp);
- readiness flap;
- insufficient cluster capacity cho `maxSurge`.

Deployment pipeline nên có health gate:

- desired vs ready replicas;
- restart count không tăng bất thường;
- 5xx/error-rate threshold;
- p95/p99 latency;
- synthetic critical request;
- minimum observation window;
- automatic pause/rollback theo policy.

Observability gồm Kubernetes events, container termination reason, probe results, ready endpoint count, ingress status codes, ASP.NET Core request telemetry, dependency telemetry, process startup duration và shutdown duration.

## Mẫu trả lời trong phỏng vấn

“Em sẽ pause/rollback nếu 503 gắn với rollout, rồi dựng timeline Pod lifecycle, readiness, restart reason, Service endpoints và ingress 5xx. `Running` không đồng nghĩa `Ready`.

Em tách health thành startup/readiness/liveness. Startup bảo vệ warm-up; readiness chỉ bật khi instance thực sự nhận traffic được; liveness chỉ nên fail khi process không thể tự recover. Em không đưa third-party transient reachability vào liveness mặc định vì có thể tạo restart storm.

Tiếp theo em kiểm tra `maxUnavailable/maxSurge` và remaining capacity trong rollout. Shutdown phải xử lý SIGTERM, drain traffic và cho in-flight requests kết thúc trong grace period hợp lý; request dài hơn grace cần redesign hoặc idempotent retry, không chỉ tăng timeout vô hạn.

Cuối cùng em load-test rolling deployment, inject dependency failure và thêm deployment gate theo ready replicas, restart count, 5xx, p95/p99 và synthetic request thay vì coi pipeline success là production success.”

## Câu hỏi đào sâu

1. Nếu third-party API là bắt buộc cho 90% endpoints nhưng không cần cho `/health` và một số read-only endpoints, readiness nên phản ánh dependency đó thế nào?
2. Một teammate đề xuất liveness gọi cả database, Redis và 5 external APIs để “chắc chắn Pod khỏe”; bạn phản biện thế nào?
3. Nếu request longest p99 là 90 giây nhưng business chấp nhận async processing, bạn sẽ thay đổi shutdown/architecture strategy ra sao?

## Lỗi trả lời thường gặp

- Chỉ nhìn `Pod Running` và bỏ qua readiness/endpoints.
- Dùng cùng một endpoint/check cho startup, readiness và liveness.
- Restart Pod khi external dependency tạm thời down.
- Chỉ tăng replica count mà không fix rollout/lifecycle.
- Tăng grace period rất lớn mà không xem request semantics/idempotency.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng replicas hoặc restart cluster.
- **3–4:** Biết probes nhưng không phân biệt semantics hoặc thiếu evidence plan.
- **5–6:** Có startup/readiness/liveness, rollout capacity và graceful shutdown cơ bản.
- **7–8:** Có lifecycle timeline, failure injection, deployment health gate và request-idempotency reasoning.
- **9–10:** Thiết kế rollout dựa trên measurable capacity/SLO, phân biệt dependency degradation, background work, drain behavior và nêu rõ điều kiện thay đổi cấu hình.

# Câu 3 — Thiết kế dịch vụ upload tài liệu lớn: backend proxy, Azure Blob Storage, SAS hay Managed Identity?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS, security, asynchronous processing, Azure Functions/Worker Service, API design, observability, failure recovery

## Bối cảnh

Một internal document platform cần hỗ trợ upload tài liệu phục vụ approval workflow.

Yêu cầu ban đầu:

- web frontend bằng React hoặc Vue.js;
- backend ASP.NET Core;
- file phổ biến 5–30 MB, nhưng có thể tới 1–2 GB;
- mỗi ngày vài chục nghìn uploads;
- sau upload cần antivirus/malware scan, metadata extraction và optional OCR;
- user phải thấy progress/status;
- file private, không public;
- một số tài liệu chứa dữ liệu nhạy cảm;
- production chạy trên Azure;
- team đã có kinh nghiệm Azure Blob Storage, Azure Functions, Managed Identity, Service Bus và App Service.

Hai proposal:

### Proposal A

Browser upload toàn bộ file qua ASP.NET Core API; API giữ stream và proxy trực tiếp lên Blob Storage. Sau đó API gọi scanner synchronously rồi trả 200.

### Proposal B

Backend cấp một SAS URL để browser upload trực tiếp vào Blob Storage. Blob event/queue kích hoạt asynchronous processing. Frontend poll trạng thái qua API.

Concerns hiện tại:

- security team lo SAS bị leak;
- developer lo direct upload làm backend “mất quyền kiểm soát”; 
- Product muốn retry upload lớn mà không bắt user upload lại từ đầu nếu network chập chờn;
- scan có thể mất vài phút với file lớn;
- một số processing step có thể fail tạm thời;
- cần audit ai upload file nào;
- cần ngăn file chưa scan bị download/consume như file hợp lệ;
- chưa rõ Azure Functions có phù hợp với mọi loại processing lâu hay Worker Service tốt hơn.

Chưa biết chắc:

- browser/client library có dùng block/blob chunk upload/resume strategy không;
- scanning engine nằm ở đâu và latency/resource profile thế nào;
- OCR có CPU-heavy hay external API;
- retention/lifecycle policy;
- compliance requirement cho encryption/key management;
- recovery time objective khi processing backlog lớn;
- download flow có cần temporary URL hay luôn proxy qua backend.

## Câu hỏi chính

Hãy thiết kế architecture end-to-end cho upload 1–2 GB an toàn và có khả năng recover, giải thích khi nào chọn direct-to-Blob với SAS thay vì backend proxy, Managed Identity được dùng ở boundary nào, cách bảo đảm file chưa scan không bị trusted, và cách bạn chọn Azure Functions vs Worker Service cho processing pipeline.

## Câu hỏi làm rõ nên cân nhắc

1. Security requirement có cấm client nhận delegated storage token hoàn toàn không, hay chấp nhận SAS scope hẹp/TTL ngắn?
2. Upload có cần resume theo chunks sau browser/network interruption không?
3. Scan/OCR execution time và resource usage distribution ra sao?
4. File có thể được download ngay sau upload hay chỉ sau trạng thái `Clean/Approved`?
5. Có requirement giữ audit immutable, retention/legal hold hoặc customer-managed encryption key không?

## Gợi ý tư duy

### Gợi ý 1

Tách data plane khỏi control plane: backend có thể kiểm soát authorization/audit/state mà không cần proxy toàn bộ bytes.

### Gợi ý 2

File upload hoàn thành không đồng nghĩa file đã trusted. Cần quarantine/state transition trước khi cho downstream sử dụng.

### Gợi ý 3

SAS và Managed Identity giải quyết các trust boundaries khác nhau: client delegation khác service-to-service identity.

## Cấu trúc trả lời đề xuất

1. Clarify security/compliance/size/UX requirements.
2. Xác định trust boundaries và data ownership.
3. So sánh backend proxy với direct upload.
4. Thiết kế upload session + scoped delegation.
5. Thiết kế quarantine blob/container + metadata state.
6. Thiết kế asynchronous processing pipeline.
7. Quyết định Functions vs Worker Service theo workload.
8. Thiết kế idempotency/retry/DLQ/reconciliation.
9. Thiết kế download authorization sau scan.
10. Test large-file/network/security/failure paths và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giữ 1–2 GB trong process memory.
- Phân biệt backend control plane với blob data plane.
- SAS phải scope tối thiểu, TTL ngắn và resource/action cụ thể nếu dùng.
- Managed Identity dùng cho trusted Azure service/backend access khi phù hợp, không “đưa Managed Identity token cho browser”.
- File mới upload vào quarantine/untrusted state.
- Chỉ chuyển trạng thái/cho phép download sau scan policy pass.
- Processing phải asynchronous nếu scan/OCR lâu.
- Retry phải idempotent/bounded; poison work có DLQ hoặc terminal failure state.
- Audit user identity, upload session, blob identity/hash/status transitions.

### Điểm cộng

- Dùng block/blob chunk upload để resume/retry phần thất bại thay vì gửi lại cả file.
- Backend cấp upload session ID và pre-authorize size/content policy trước SAS.
- Validate content using more than extension/MIME supplied by browser.
- Tách original immutable blob khỏi derived artifacts/metadata.
- Dùng hash/checksum khi phù hợp để detect corruption/dedup/integrity, nhưng không coi hash là malware scan.

### Senior+

- Thiết kế state machine rõ: `Created -> Uploading -> Uploaded -> Scanning -> Clean/Infected/Failed -> Available`.
- Bảo đảm event duplicate không scan/process sai bằng idempotency key/version.
- Tách compute class: lightweight event orchestration vs CPU/long-running scanner worker.
- Có backpressure, concurrency control và queue age SLO.
- Thiết kế secure download path: authorized API cấp short-lived read delegation hoặc proxy khi compliance yêu cầu.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng trust model. Backend phải kiểm soát “ai được phép upload cái gì”, nhưng điều đó không bắt buộc mọi byte đi qua ASP.NET Core process. Với file 1–2 GB và throughput lớn, backend proxy sẽ tiêu thụ connection duration, bandwidth, worker resources và tạo thêm hop. Streaming đúng cách có thể tránh memory blow-up, nhưng backend vẫn trở thành data-plane bottleneck và coupling point.

Nếu security policy cho phép delegated upload, tôi thiên về direct-to-Blob cho large files:

1. Client gọi `POST /upload-sessions` với metadata dự kiến: filename, size, content type, workflow context.
2. Backend authenticate + authorize user và validate quota/policy.
3. Backend tạo `UploadSession` trong DB với trạng thái `Created` và server-generated blob path/id.
4. Backend tạo delegation rất hẹp cho đúng blob/container path, chỉ permissions cần thiết, TTL ngắn.
5. Browser upload trực tiếp Blob Storage bằng chunk/block upload.
6. Client/backend finalize session hoặc processing pipeline xác nhận blob tồn tại/metadata expected.
7. Blob vẫn ở quarantine/untrusted namespace.
8. Event/queue kích hoạt scan/metadata/OCR pipeline.
9. Chỉ khi scan pass và required processing hoàn tất, record chuyển `Available`.

SAS leak concern là hợp lệ. Mitigation không phải “SAS luôn an toàn” mà là least privilege:

- write-only nếu use case cho phép;
- scope đúng resource/path;
- expiry ngắn;
- HTTPS only;
- không log token/query string;
- không cho list container;
- server-generated blob name;
- optional user delegation SAS khi architecture phù hợp;
- revoke/rotate strategy phụ thuộc loại SAS/account policy.

Exact SAS mechanism phải tuân theo Azure Storage security policy của organization. Nếu delegated client access bị policy cấm, backend proxy hoặc dedicated upload gateway có thể cần thiết. Nhưng proxy vẫn phải stream bytes, set request limits/timeouts phù hợp và tránh buffering toàn file.

Managed Identity dùng ở trusted service boundaries: ASP.NET Core App Service/Worker/Function truy cập Blob Storage, Service Bus, Key Vault... mà không hard-code account keys/secrets. Browser không nhận Managed Identity credential của backend.

### Quarantine

Tôi không cho newly uploaded blob xuất hiện ngay trong normal download path. Metadata DB là source of truth cho state:

```text
Created
  -> Uploading
  -> Uploaded
  -> Scanning
  -> Clean -> Available
           -> ProcessingDerivedData -> Available
  -> Infected
  -> Failed
```

Tên states cụ thể có thể khác, nhưng principle là untrusted until verified. Download API chỉ trả file nếu user authorized và state thỏa policy.

Scan nên kiểm tra nội dung thực tế theo scanning engine, không chỉ extension hoặc client-provided MIME. File infected bị isolate/delete theo retention/security policy; không tự ý xóa nếu compliance yêu cầu giữ evidence.

### Async processing

Scan/OCR vài phút không nên giữ HTTP upload request. Sau upload complete, enqueue work với `UploadSessionId/BlobId`, processor xử lý independent.

Delivery có thể duplicate, nên mỗi stage cần idempotent transition. Ví dụ transaction chỉ cho scanner claim từ `Uploaded -> Scanning`; retry cùng file không tạo derived artifacts trùng vô hạn. Nếu external scanner timeout có ambiguous outcome, stage phải reconcile theo contract.

Failures:

- transient storage/network: bounded retry + backoff;
- malformed/unsupported file: terminal failure, không retry vô hạn;
- malware detected: terminal security state;
- processing poison: DLQ + alert + operator tooling;
- worker crash: message redeliver và state machine recover;
- queue backlog: autoscale/concurrency theo downstream capacity.

### Azure Functions vs Worker Service

Tôi không chọn bằng slogan.

Azure Functions phù hợp khi workload event-driven, execution model/runtime constraints phù hợp, có scale-to-demand value và processing step stateless/bounded. Nhưng nếu scanner cần heavy native dependencies, long CPU-intensive processing, predictable process lifetime, custom concurrency hoặc sustained workload, Worker Service/container có thể đơn giản/kiểm soát tốt hơn.

Tôi có thể dùng Functions làm orchestrating/lightweight trigger rồi queue work cho dedicated Worker pool, nhưng chỉ nếu separation tạo giá trị. Không cần nhiều services chỉ để trông “cloud-native”.

### Upload resume

Với 1–2 GB, chunk/block upload giúp retry block thất bại thay vì upload lại toàn file. Session state lưu expected blob identity/size và finalize chỉ khi upload hoàn tất. Client progress dựa trên bytes uploaded, còn business status sau upload dựa trên processing state.

### Download

Option 1: authorized API cấp short-lived read SAS sau khi kiểm tra user + document state. Tốt cho large-file bandwidth.

Option 2: backend proxy download nếu compliance/audit/content transformation yêu cầu mọi byte qua app.

Option 3: edge/private delivery service nếu scale cần, nhưng security policy quyết định.

Không bao giờ cấp read URL cho `Scanning/Infected/Failed` file.

### Security

- authentication/authorization ở upload-session API;
- authorization lại ở download, không tin blob URL cũ;
- limit size/type/count;
- generate server-side blob names;
- normalize/sanitize filename metadata;
- không dùng filename làm filesystem path;
- encrypt in transit/at rest theo platform/policy;
- secrets ở Key Vault nếu có secret không thay thế được bằng Managed Identity;
- audit actor, timestamps, state transitions, scanner result reference;
- không log SAS token.

### Observability

Dashboard cần:

- upload success/failure và duration theo size bucket;
- average retry/chunk retry;
- processing queue depth + oldest age;
- scan duration/error/infected count;
- OCR duration/error;
- state stuck duration;
- DLQ count;
- Blob dependency latency/error;
- worker CPU/memory/concurrency;
- end-to-end time từ upload session tạo đến `Available`.

Alerts cho queue age, stuck `Scanning`, DLQ growth, unusual infected-rate spike, authorization failures và repeated SAS issuance failures.

### Testing

- 1 MB, 100 MB, 2 GB file;
- network interruption giữa upload rồi resume;
- expired SAS giữa upload;
- upload vượt size policy;
- forged MIME/extension;
- malicious sample trong safe controlled security testing environment;
- duplicate processing message;
- worker crash giữa scan và DB update;
- scanner timeout/429/5xx;
- unauthorized download trước và sau scan;
- high concurrency/backlog recovery.

Architecture final có thể là:

```text
Browser
  -> ASP.NET Core Control API
      -> DB (UploadSession/Document state)
      -> issues scoped upload delegation

Browser
  -> Azure Blob Storage (quarantine data plane)

Blob/Event or API Finalize
  -> Queue / Service Bus
      -> Scanner Worker / Function
      -> Metadata/OCR Worker
      -> DB state transition

Browser
  -> Status API
  -> Authorized download only when Available
```

Nếu security policy không cho direct client-to-storage, tôi giữ same control/state/processing architecture nhưng thay upload leg bằng streaming proxy. Phần còn lại không cần thay đổi toàn bộ.

## Mẫu trả lời trong phỏng vấn

“Em tách control plane khỏi data plane. Backend vẫn authenticate, authorize, audit và tạo upload session, nhưng với file 1–2 GB em ưu tiên direct-to-Blob nếu security policy cho phép, vì proxy toàn bộ bytes qua ASP.NET Core tạo thêm bandwidth/connection bottleneck.

Backend chỉ cấp SAS scope rất hẹp, TTL ngắn, đúng blob và permission cần thiết; browser không nhận Managed Identity credential. Managed Identity dùng giữa App Service/Function/Worker với Blob, Service Bus hoặc Key Vault.

File upload xong vẫn là untrusted. Em giữ nó trong quarantine và state machine `Uploaded -> Scanning -> Clean/Infected/Failed -> Available`; download chỉ được phép ở trạng thái hợp lệ. Scan/OCR chạy async qua queue, có idempotent processing, bounded retries, DLQ và status API cho frontend.

Functions hay Worker Service phụ thuộc execution profile: event-driven/bounded workload có thể hợp Functions; heavy native/long-running/predictable compute có thể hợp Worker. Em sẽ test network resume, expired SAS, duplicate event, worker crash, malicious file và unauthorized download, rồi monitor queue age, scan latency, DLQ và end-to-end time-to-available.”

## Câu hỏi đào sâu

1. Nếu security team cấm SAS hoàn toàn nhưng vẫn yêu cầu 2 GB upload và resume, bạn thiết kế proxy/gateway thế nào để không làm ASP.NET Core memory/connection collapse?
2. Nếu scanner trả timeout nhưng thực tế đã scan xong và lưu result ở external system, retry strategy của bạn thay đổi thế nào?
3. Nếu Product muốn file vừa upload có thể preview ngay trước khi scan hoàn tất, bạn phản biện requirement và đưa ra lựa chọn nào?

## Lỗi trả lời thường gặp

- Cho rằng direct upload đồng nghĩa backend mất authorization/control.
- Đưa account key hoặc long-lived SAS cho browser.
- Cho file upload xong là trusted ngay.
- Chạy scan/OCR synchronous trong request 1–2 GB.
- Retry processing vô hạn hoặc không có DLQ/state reconciliation.

## Thang điểm 0–10

- **0–2:** Chỉ nói “dùng Blob Storage” mà không có security/state/failure model.
- **3–4:** Có direct upload nhưng SAS quá rộng hoặc thiếu quarantine/async processing.
- **5–6:** Có scoped delegation, Managed Identity service-side, state machine và async pipeline.
- **7–8:** Có resumable upload, idempotency, DLQ, secure download, Functions-vs-Worker trade-off và observability.
- **9–10:** Thiết kế rõ trust boundaries, recoverable state transitions, compliance-aware alternatives, capacity/backpressure và nêu được khi nào proxy là lựa chọn đúng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Deep pagination là access-pattern problem:** index có thể giúp order/filter nhưng `OFFSET` sâu vẫn làm database xử lý nhiều rows trước khi trả kết quả; keyset pagination thay đổi boundary truy cập.
- **Pagination correctness cần deterministic order:** dùng tie-breaker và xem xét dữ liệu thay đổi giữa các request.
- **Kubernetes `Running` không đồng nghĩa `Ready`:** startup, readiness và liveness có mục tiêu khác nhau và phải phản ánh application capability.
- **Deployment safety cần cả startup lẫn shutdown lifecycle:** warm-up, readiness, request draining, graceful termination và rollout capacity phải được đo cùng nhau.
- **Large-file architecture nên tách control plane khỏi data plane:** backend vẫn quản lý authorization/audit/state trong khi direct Blob upload có thể loại bỏ unnecessary byte proxy.
- **Uploaded không có nghĩa trusted:** quarantine + malware scan + explicit state transition là security boundary.

## Mẫu tư duy cần nhớ

1. **Đo rows read/actual work, không chỉ nhìn tên operator trong execution plan.**
2. **Phân biệt process alive, service ready và dependency healthy.**

4. **Tách control plane và data plane khi payload lớn nhưng vẫn giữ authorization boundary.**
5. **Một asynchronous pipeline phải thiết kế retry cùng idempotency, terminal failure và observability.**
