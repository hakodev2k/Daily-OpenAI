# Code Review Challenge 1 — Đồng bộ Elasticsearch index từ PostgreSQL bị mất bản cập nhật

**Chủ đề:** .NET 8, EF Core, PostgreSQL, Elasticsearch, background processing, eventual consistency

## Bối cảnh

Một hệ thống quản lý sản phẩm sử dụng PostgreSQL làm source of truth, Elasticsearch phục vụ tìm kiếm. Sau mỗi lần cập nhật giá/tên, API gọi indexing service. Có 8 API instances; trong giờ cao điểm khoảng 200 updates/giây, Elasticsearch đôi lúc trả HTTP 429 hoặc timeout. Người dùng thấy sản phẩm đã đổi tên trong trang chi tiết nhưng tìm kiếm vẫn hiển thị tên cũ, đôi khi bản cập nhật cũ ghi đè bản mới. Yêu cầu nghiệp vụ chấp nhận search trễ tối đa khoảng 60 giây trong điều kiện bình thường; cần làm rõ SLA khi search cluster outage kéo dài. Không được chuyển source of truth sang Elasticsearch.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/products")]
public sealed class ProductsController(
    CatalogDbContext db,
    IProductSearchIndexer indexer,
    ILogger<ProductsController> logger) : ControllerBase
{
    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id, UpdateProductRequest request, CancellationToken ct)
    {
        var product = await db.Products.FindAsync(new object[] { id }, ct);
        if (product is null) return NotFound();

        product.Name = request.Name;
        product.Price = request.Price;
        await db.SaveChangesAsync(ct);

        _ = Task.Run(async () =>
        {
            try
            {
                await indexer.UpsertAsync(new SearchProduct(
                    product.Id, product.Name, product.Price));
            }
            catch (Exception ex)
            {
                logger.LogWarning(ex, "Index failed for {ProductId}", id);
            }
        });

        return Ok(new { product.Id, product.Name, product.Price });
    }
}

public sealed class SearchRebuildWorker(
    IServiceScopeFactory scopeFactory,
    IProductSearchIndexer indexer) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
            var changed = await db.Products
                .Where(p => p.UpdatedAt > DateTime.UtcNow.AddMinutes(-2))
                .Take(500).ToListAsync(stoppingToken);

            foreach (var product in changed)
                await indexer.UpsertAsync(new SearchProduct(
                    product.Id, product.Name, product.Price));

            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Không có durable handoff giữa database commit và indexing

**Vấn đề:** API commit rồi fire-and-forget Task trong process.  
**Tại sao xảy ra:** Task không được await hoặc lưu vào durable queue; process restart, recycle hoặc deployment có thể mất nó.  
**Ảnh hưởng production:** Search mất bản cập nhật vĩnh viễn nếu cơ chế bù không bắt được.  
**Cách sửa:** Transactional Outbox: ghi product và event trong cùng PostgreSQL transaction; worker đọc outbox, chỉ mark processed sau khi indexing thành công.

### [High] — Index có thể bị ghi lùi phiên bản

**Vấn đề:** Hai updates cùng product được gửi không theo thứ tự.  
**Tại sao xảy ra:** Task scheduling, network latency, retry và nhiều instances đảo thứ tự hoàn tất.  
**Ảnh hưởng production:** Search trả dữ liệu cũ dù bản mới đã commit.  
**Cách sửa:** Gắn monotonic version từ database, dùng external versioning phù hợp hoặc compare-and-apply có kiểm soát ở search adapter. Không lấy timestamp client làm thứ tự đáng tin.

### [High] — Worker bỏ sót thay đổi khi backlog lớn

**Vấn đề:** Cửa sổ thời gian trượt kết hợp `Take(500)` không có thứ tự và checkpoint.  
**Tại sao xảy ra:** Tốc độ cập nhật vượt tốc độ scan, downtime dài hơn cửa sổ, pagination thiếu.  
**Ảnh hưởng production:** Documents không bao giờ được đồng bộ.  
**Cách sửa:** Đọc outbox theo stable key và trạng thái; xử lý theo batch với checkpoint bền vững; có reconciliation job định kỳ.

### [High] — Không có retry policy và dead-letter handling

**Vấn đề:** Exception từ indexer làm worker thoát; Task API chỉ log rồi bỏ qua.  
**Tại sao xảy ra:** Chưa phân biệt 429, transient 5xx, permanent mapping errors.  
**Ảnh hưởng production:** Backlog hoặc dữ liệu sai kéo dài không được phát hiện.  
**Cách sửa:** Bounded exponential backoff + jitter, retry count, poison-event isolation, alert và operator replay.

### [High] — Multiple instances xử lý trùng hoặc tranh chấp

**Vấn đề:** Mỗi API instance chạy worker quét cùng tập dữ liệu.  
**Tại sao xảy ra:** Không có claim/lease giữa workers.  
**Ảnh hưởng production:** Tăng load Elasticsearch, duplicate requests, race với versions.  
**Cách sửa:** Claim rows bằng PostgreSQL `FOR UPDATE SKIP LOCKED` trong transaction ngắn, hoặc một consumer group có coordination; chấp nhận duplicate và thiết kế idempotency.

### [Medium] — Captured tracked entity không ổn định

**Vấn đề:** Closure giữ `product` là tracked EF entity sau request.  
**Tại sao xảy ra:** Scope/DbContext đã có thể bị dispose; object mutable và không phải snapshot công việc.  
**Ảnh hưởng production:** Dữ liệu indexing không rõ phiên bản, khó test.  
**Cách sửa:** Persist immutable event payload/version; không truyền entity tracked qua background boundary.

### [Medium] — API thiếu optimistic concurrency

**Vấn đề:** Concurrent PUT có thể lost update trong PostgreSQL.  
**Tại sao xảy ra:** Không có concurrency token/expected version; last writer wins mặc định có thể trái business requirement.  
**Ảnh hưởng production:** Thay đổi người dùng bị ghi đè âm thầm.  
**Cách sửa:** Dùng explicit version và conditional update, trả 409 khi stale nếu nghiệp vụ yêu cầu; tách biệt vấn đề database concurrency với search ordering.

### [Medium] — Không có visibility về lag và backlog

**Vấn đề:** Log warning đơn lẻ không thể chứng minh consistency SLA.  
**Tại sao xảy ra:** Thiếu outbox age, success/failure counters, document version drift.  
**Ảnh hưởng production:** Khách hàng phát hiện lỗi trước hệ thống giám sát.  
**Cách sửa:** Metrics backlog, oldest pending age, retry rate, indexing latency và reconciliation mismatch.

## Phiên bản đề xuất

Ví dụ dưới đây thể hiện **transactional boundary** và thuật toán worker; `ClaimBatchAsync`, `MarkDoneAsync`, `RescheduleAsync` là abstractions cần hiện thực bằng SQL có transaction/lease và test concurrency. Adapter Elasticsearch phải bảo đảm document không bị downgrade theo `Version`.

```csharp
public sealed record ProductChanged(
    Guid EventId, Guid ProductId, long Version,
    string Name, decimal Price);

public async Task<IResult> UpdateProduct(
    Guid id, UpdateProductRequest input,
    CatalogDbContext db, CancellationToken ct)
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    var product = await db.Products.SingleOrDefaultAsync(p => p.Id == id, ct);
    if (product is null) return Results.NotFound();

    product.Name = input.Name;
    product.Price = input.Price;
    product.Version++; // Requires concurrency-safe DB update/check.
    product.UpdatedAt = DateTimeOffset.UtcNow;

    db.Outbox.Add(new OutboxMessage
    {
        Id = Guid.NewGuid(),
        AggregateId = id,
        AggregateVersion = product.Version,
        Payload = JsonSerializer.Serialize(new ProductChanged(
            Guid.NewGuid(), id, product.Version, product.Name, product.Price)),
        CreatedAt = DateTimeOffset.UtcNow
    });
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return Results.Accepted($"/api/products/{id}");
}

public sealed class IndexOutboxWorker(
    IServiceScopeFactory scopes,
    ILogger<IndexOutboxWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = scopes.CreateAsyncScope();
            var store = scope.ServiceProvider.GetRequiredService<IOutboxStore>();
            var indexer = scope.ServiceProvider.GetRequiredService<IVersionedIndexer>();
            var batch = await store.ClaimBatchAsync(100, ct);
            foreach (var item in batch)
            {
                try
                {
                    var change = JsonSerializer.Deserialize<ProductChanged>(
                        item.Payload)!;
                    await indexer.UpsertIfNewerAsync(change, ct);
                    await store.MarkDoneAsync(item.Id, ct);
                }
                catch (Exception ex) when (!ct.IsCancellationRequested)
                {
                    log.LogWarning(ex, "Index retry for {OutboxId}", item.Id);
                    await store.RescheduleAsync(item.Id, ct);
                }
            }
            if (batch.Count == 0)
                await Task.Delay(TimeSpan.FromSeconds(2), ct);
        }
    }
}
```

**Implementation contract:** `Version++` chỉ đúng nếu database bảo vệ concurrent writers bằng optimistic concurrency token hoặc atomic update; không được dùng nguyên ví dụ để mặc định an toàn. `ClaimBatchAsync` phải claim atomically, có lease expiry/recovery sau crash, retry scheduling và poison handling. `UpsertIfNewerAsync` phải kiểm tra version atomically ở search side; chỉ mark done sau acknowledged write. Cần bổ sung delete/tombstone events và xử lý schema evolution nếu có xóa sản phẩm.

## Giải thích thiết kế sau khi sửa

Product và outbox cùng commit nên không có khoảng trống mất event sau database commit. Delivery vẫn có thể duplicate khi worker crash giữa indexing và mark done, vì vậy indexer phải idempotent. Version bảo vệ ordering; claim/lease bảo vệ multi-instance throughput; reconciliation xử lý sai lệch lâu dài.

## Trade-offs

Outbox thêm bảng, storage, cleanup, retry operations và độ trễ eventual consistency. Nếu throughput thấp và SLA đơn giản, một worker + outbox trong Modular Monolith đủ tốt, chưa cần Service Bus hoặc Microservices. Nếu yêu cầu strong consistency giữa detail và search, cần làm rõ trải nghiệm sản phẩm thay vì hứa atomic transaction xuyên PostgreSQL/Elasticsearch.

## Cách kiểm thử

1. **Integration test:** Kill process ngay sau DB commit, restart worker và xác minh event vẫn được index.
2. **Concurrency test:** Gửi hai versions đảo thứ tự; search cuối cùng giữ version cao nhất.
3. **Failure-path test:** Elasticsearch trả 429/timeout, xác minh retry, backoff, backlog và không mất event.
4. **Load test:** Tạo hơn 500 changes/phút, đo lag p95 và eventual convergence.
5. **Database test:** Chạy nhiều workers cùng claim, xác minh không có event bị bỏ và lease recovery sau crash.

## Quan sát trong production

Dashboard: outbox pending count, oldest pending age, indexing throughput, retry/poison counts, Elasticsearch 429/5xx, per-product version mismatch sampled. Structured logs chứa `EventId`, `ProductId`, `Version`, `TraceId` (không log dữ liệu nhạy cảm). Alert khi oldest pending vượt SLA hoặc reconciliation mismatch tăng; trace nối HTTP update, DB commit và indexing attempt qua correlation metadata.

1. Khi đổi Elasticsearch mapping cần reindex toàn bộ, bạn tổ chức dual-index/alias cutover thế nào?
2. Nếu outbox tăng đến hàng chục triệu rows, partitioning, retention và cleanup nên thiết kế ra sao?
3. Làm thế nào để xử lý delete event đến trước update event cũ?

<script setup lang="ts">
import { ref, watch, onMounted } from 'vue';

type Order = { id: string; customer: string; note: string };
const query = ref('');
const page = ref(1);
const orders = ref<Order[]>([]);
const selected = ref<Order | null>(null);
const loading = ref(false);
const error = ref('');
const token = localStorage.getItem('access_token') ?? '';

async function load() {
  loading.value = true;
  error.value = '';
  const url = `/api/orders?q=${query.value}&page=${page.value}`;
  try {
    const response = await fetch(url, {
      headers: { Authorization: `Bearer ${token}` }
    });
    const data = await response.json();
    orders.value = data.items;
    window.dispatchEvent(new CustomEvent('analytics', {
      detail: { url, token, count: orders.value.length }
    }));
  } catch (e) {
    error.value = String(e);
  }
  loading.value = false;
}

watch([query, page], load);
onMounted(load);

async function openOrder(order: Order) {
  selected.value = order;
  const response = await fetch(`/api/orders/${order.id}`, {
    headers: { Authorization: `Bearer ${token}` }
  });
  selected.value = await response.json();
}
</script>

<template>
  <input v-model="query" placeholder="Search orders" />
  <button @click="page++">Next</button>
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <div v-for="order in orders" :key="order.id">
    <button @click="openOrder(order)">{{ order.customer }}</button>
  </div>
  <section v-if="selected" v-html="selected.note"></section>
</template>

## Kết quả code review tham khảo

### [Critical] — Token bị phát tán qua browser analytics event

**Vấn đề:** `CustomEvent.detail` chứa bearer token.  
**Tại sao xảy ra:** Bất kỳ listener script nào trong cùng document có thể nhận event.  
**Ảnh hưởng production:** Credential exposure và khả năng impersonation nếu token còn hiệu lực.  
**Cách sửa:** Không bao giờ gửi token vào analytics/logs; chỉ gửi metadata allowlisted, kiểm soát third-party scripts và CSP.

### [High] — `v-html` với untrusted note tạo XSS risk

**Vấn đề:** HTML từ API được đưa thẳng vào DOM.  
**Tại sao xảy ra:** `v-html` không escape nội dung như Vue text interpolation.  
**Ảnh hưởng production:** Script execution tùy payload/browser context, session compromise và data theft.  
**Cách sửa:** Render `{{ selected.note }}` nếu chỉ cần text; nếu rich text là requirement, sanitize với policy được review ở boundary phù hợp và dùng defense in depth.

### [High] — Search results bị stale overwrite

**Vấn đề:** Mọi response đều ghi `orders.value` bất kể query hiện tại.  
**Tại sao xảy ra:** Network completion order khác request start order.  
**Ảnh hưởng production:** UI hiển thị sai kết quả, có thể dẫn đến thao tác trên đơn không mong muốn.  
**Cách sửa:** Abort previous request và dùng monotonically increasing request ID để bỏ response cũ.

### [High] — Detail panel có race riêng

**Vấn đề:** `openOrder` không kiểm tra selection hiện tại sau await.  
**Tại sao xảy ra:** Hai detail requests hoàn thành đảo thứ tự.  
**Ảnh hưởng production:** Ghi chú của đơn A xuất hiện khi người dùng vừa chọn B.  
**Cách sửa:** Abort/detail sequence guard độc lập với search.

### [High] — Không kiểm tra HTTP status

**Vấn đề:** `fetch` resolve cả 401/500; `response.json()` có thể trả error object thay vì `items`.  
**Tại sao xảy ra:** Chỉ network errors mới reject theo mặc định.  
**Ảnh hưởng production:** UI sai trạng thái, che mất lỗi authentication và backend outage.  
**Cách sửa:** Kiểm tra `response.ok`, phân nhánh 401, xử lý error payload có cấu trúc.

### [Medium] — Token snapshot trong localStorage

**Vấn đề:** Token đọc một lần, không refresh; localStorage có thể bị script đọc khi XSS.  
**Tại sao xảy ra:** Không có session abstraction hoặc lifecycle management.  
**Ảnh hưởng production:** 401 kéo dài sau refresh, credential theft khi có XSS.  
**Cách sửa:** Dùng auth client đã kiểm soát và short-lived credentials; đánh giá BFF/HttpOnly cookie với CSRF protection tùy kiến trúc. Không khẳng định cookie tự động giải quyết mọi rủi ro.

### [Medium] — Request amplification và query encoding

**Vấn đề:** Mỗi keystroke tạo request, query nối string không encode.  
**Tại sao xảy ra:** Watch không debounce, không `URLSearchParams`.  
**Ảnh hưởng production:** Tăng API load, query có `&` hoặc ký tự đặc biệt bị parse sai.  
**Cách sửa:** Debounce có giới hạn, URLSearchParams, reset page khi query thay đổi.

### [Medium] — Loading/error state không nhất quán

**Vấn đề:** Request cũ có thể set loading=false trong khi request mới đang chạy; detail errors không xử lý.  
**Tại sao xảy ra:** Shared state không gắn với request identity; thiếu finally/guard.  
**Ảnh hưởng production:** Spinner sai, lỗi im lặng, UX khó chẩn đoán.  
**Cách sửa:** Per-request sequence, finally chỉ update khi còn active, detail error state riêng.

## Phiên bản đề xuất

Ví dụ giả định API trả `{ items: Order[] }`; `auth.getAccessToken()` là abstraction lấy token hiện hành, phải được hiện thực và bảo vệ theo security architecture. Code xử lý search và detail độc lập.

const orders = ref<Order[]>([]);

const error = ref('');
const detailError = ref('');
let searchController: AbortController | undefined;
let detailController: AbortController | undefined;
let searchSeq = 0;
let detailSeq = 0;
let debounce: ReturnType<typeof setTimeout> | undefined;

watch(query, () => { page.value = 1; });
watch([query, page], () => {
  clearTimeout(debounce);
  searchController?.abort();
  ++searchSeq; // Invalidate old results immediately.
  loading.value = true;
  debounce = setTimeout(() => void load(), 250);
}, { immediate: true });

async function load() {
  const seq = ++searchSeq;
  const controller = new AbortController();
  searchController = controller;
  loading.value = true;
  error.value = '';
  try {
    const params = new URLSearchParams({
      q: query.value, page: String(page.value)
    });
    const accessToken = await auth.getAccessToken();
    if (controller.signal.aborted || seq !== searchSeq) return;
    const response = await fetch(`/api/orders?${params}`, {
      signal: controller.signal,
      headers: { Authorization: `Bearer ${accessToken}` }
    });
    if (response.status === 401) throw new Error('SESSION_EXPIRED');
    if (!response.ok) throw new Error(`HTTP_${response.status}`);
    const data: { items: Order[] } = await response.json();
    if (seq === searchSeq) orders.value = data.items;
  } catch (e) {
    if (seq === searchSeq && !controller.signal.aborted)
      error.value = e instanceof Error ? e.message : 'REQUEST_FAILED';
  } finally {
    if (seq === searchSeq) loading.value = false;
  }
}

async function openOrder(order: Order) {
  detailController?.abort();
  const seq = ++detailSeq;
  const controller = new AbortController();
  detailController = controller;
  selected.value = null;
  detailError.value = '';
  try {
    const token = await auth.getAccessToken();
    if (seq !== detailSeq) return;
    const response = await fetch(
      `/api/orders/${encodeURIComponent(order.id)}`, {
        signal: controller.signal,
        headers: { Authorization: `Bearer ${token}` }
      });
    if (!response.ok) throw new Error(`HTTP_${response.status}`);
    const data: Order = await response.json();
    if (seq === detailSeq) selected.value = data;
  } catch (e) {
    if (seq === detailSeq && !controller.signal.aborted)
      detailError.value = 'Không tải được chi tiết đơn hàng';
  }
}

onBeforeUnmount(() => {
  clearTimeout(debounce);
  searchController?.abort();
  detailController?.abort();
  ++searchSeq;
  ++detailSeq;
});
</script>

<template>
  <input v-model="query" placeholder="Search orders" />
  <button @click="page++">Next</button>
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <div v-for="order in orders" :key="order.id">
    <button @click="openOrder(order)">{{ order.customer }}</button>
  </div>
  <p v-if="detailError">{{ detailError }}</p>
  <section v-if="selected">{{ selected.note }}</section>
</template>

**Implementation note:** Production code nên bổ sung response schema validation, page bounds, session-expired redirect/refresh policy, accessible loading states và analytics abstraction có allowlist. Không được gửi PII, query nhạy cảm hoặc tokens vào telemetry. Nếu dùng cookie authentication, cấu hình CSRF và CORS theo deployment topology.

## Giải thích thiết kế sau khi sửa

`AbortController` giảm công việc không cần thiết, nhưng sequence guard mới là điều kiện correctness khi cancellation không kịp ngăn response. Search và detail dùng hai independent sequences. `URLSearchParams` đảm bảo encoding. Vue text interpolation escape nội dung thay vì inject HTML. Authentication lifecycle được tách khỏi component.

## Trade-offs

Debounce 250 ms giảm request nhưng tăng độ trễ cảm nhận; điều chỉnh bằng đo lường thực tế. Cancellation không bảo đảm backend ngừng xử lý, nên server vẫn cần rate limiting và cancellation propagation. BFF với HttpOnly cookie giảm JS token exposure nhưng thêm backend state/CSRF considerations. Rich-text sanitization phức tạp hơn text rendering và chỉ nên dùng khi thật sự cần.

## Cách kiểm thử

1. **Playwright E2E:** Mock hai search responses hoàn thành đảo thứ tự; xác minh chỉ kết quả mới hiển thị.
2. **Concurrency/UI test:** Click A rồi B nhanh, delay response A; detail cuối cùng phải là B.
3. **Security test:** Note chứa HTML/script payload hiển thị như text; không có executable DOM injection.
4. **API failure test:** 401, 500, invalid JSON và network abort; kiểm tra UI state/không có unhandled rejection.
5. **Load/network test:** Gõ nhanh 20 ký tự, đo số request và latency; xác minh URL encoding cho `&`, Unicode.

## Quan sát trong production

Theo dõi frontend request latency p50/p95, HTTP status distribution, canceled/stale response counts, search errors và server correlation ID. Browser RUM không chứa token, order note hoặc query nhạy cảm. Kết hợp Application Insights backend dependency telemetry để phân biệt API chậm với network/client races. Alert khi 401/5xx tăng bất thường, kiểm tra CSP reports cho dấu hiệu injection.

## Câu hỏi phỏng vấn mở rộng

1. Nếu frontend chuyển sang React, bạn sẽ dùng `useEffect` cleanup và query cache library thế nào để bảo vệ ordering?
2. Nếu API dùng cookie authentication, CSRF và SameSite cần đánh giá ra sao?
3. Khi người dùng mở nhiều tabs, auth refresh race và logout propagation cần xử lý thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- PostgreSQL commit và Elasticsearch indexing không nằm trong cùng atomic transaction: durable outbox, retry, idempotency và version ordering là những cơ chế riêng biệt.
- Vue asynchronous UI phải chống stale responses, kể cả khi đã abort request.
- Browser trust boundary: bearer tokens không được đưa vào analytics events; untrusted HTML không được render trực tiếp.
- Production reliability cần đo lag, backlog, errors và xác minh behavior dưới failure injection.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và transaction boundary trước khi thiết kế async side effects.
2. Thiết kế retry cùng idempotency, ordering và poison handling.
3. Phân biệt cancellation để tiết kiệm tài nguyên với sequence validation để bảo đảm correctness.
4. Kiểm tra mọi boundary nơi dữ liệu hoặc credentials rời khỏi trust domain.
5. Dùng telemetry và failure-path tests để chứng minh giải pháp, không chỉ đọc code.
