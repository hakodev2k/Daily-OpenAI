# Code Review Challenge 1 — Regex validation biến một endpoint nhẹ thành CPU DoS dưới tải

**Chủ đề:** Input validation, performance, error handling, resource exhaustion, logging và observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép người dùng lưu một “matching rule” dạng regex để lọc tên file log. Team muốn kiểm tra nhanh rule trước khi lưu nên endpoint sẽ chạy regex với một sample string do client gửi.

Traffic bình thường thấp, nhưng sau khi feature được public cho nhiều tenant, production ghi nhận:

- CPU của API đôi lúc tăng gần 100% dù request rate không cao,
- một số request giữ thread/CPU rất lâu,
- autoscaling tăng instance nhưng không giải quyết triệt để,
- p99 latency tăng mạnh trong khi database gần như không tải,
- log chứa toàn bộ regex pattern và sample input dài hàng trăm KB,
- cùng một pattern gây chậm có thể được gửi lặp lại nhiều lần.

Business vẫn cần cho phép regex tương đối linh hoạt, nhưng endpoint không được để một input xấu làm ảnh hưởng cả process.

## Đoạn code cần review

```csharp
public sealed record ValidateRuleRequest(
    string Pattern,
    string Sample);

[ApiController]
[Route("api/rules")]
public sealed class RulesController : ControllerBase
{
    private readonly ILogger<RulesController> _logger;

    public RulesController(ILogger<RulesController> logger)
    {
        _logger = logger;
    }

    [Authorize]
    [HttpPost("validate")]
    public IActionResult Validate(ValidateRuleRequest request)
    {
        _logger.LogInformation(
            "Validating regex {Pattern} against {Sample}",
            request.Pattern,
            request.Sample);

        try
        {
            var regex = new Regex(
                request.Pattern,
                RegexOptions.IgnoreCase | RegexOptions.Compiled);

            var matched = regex.IsMatch(request.Sample);

            return Ok(new
            {
                valid = true,
                matched
            });
        }
        catch (ArgumentException ex)
        {
            _logger.LogWarning(ex, "Invalid regex {Pattern}", request.Pattern);
            return BadRequest(new { valid = false });
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không đặt timeout cho regex do người dùng cung cấp

**Problem:** Regex chạy không có execution timeout.  
**Why it happens:** Constructor không truyền `matchTimeout`.  
**Production impact:** Pattern pathological có thể chiếm CPU rất lâu, làm request treo và ảnh hưởng request khác trong cùng process.  
**Severity:** Critical  
**Recommended fix:** Dùng timeout hữu hạn khi tạo regex và xử lý `RegexMatchTimeoutException` như validation failure hoặc request bị giới hạn.

### 2. Không giới hạn kích thước `Pattern` và `Sample`

**Problem:** Client có thể gửi input rất lớn.  
**Why it happens:** Không có validation length/size tại API boundary.  
**Production impact:** Tăng allocation, GC pressure và thời gian xử lý; kết hợp regex xấu có thể khuếch đại CPU cost.  
**Severity:** High  
**Recommended fix:** Đặt max length hợp lý cho pattern/sample và request body; reject sớm bằng `400` hoặc `413` theo thiết kế API.

### 3. Dùng `RegexOptions.Compiled` cho pattern ad-hoc

**Problem:** Mỗi request tạo một compiled regex mới.  
**Why it happens:** Team coi compiled luôn nhanh hơn mà không xét chi phí compile và reuse.  
**Production impact:** Pattern thay đổi liên tục có thể làm tăng CPU/memory mà không có lợi ích reuse tương xứng.  
**Severity:** High  
**Recommended fix:** Không bật `Compiled` mặc định cho pattern one-shot. Chỉ cache/reuse pattern đã được duyệt nếu workload thực sự hưởng lợi và cache có giới hạn.

### 4. Không có chống abuse ở endpoint tốn CPU

**Problem:** Caller có thể gửi lặp lại pattern tốn tài nguyên.  
**Why it happens:** Endpoint chỉ dựa vào authentication, không có quota/rate/admission control.  
**Production impact:** Một tenant hoặc client lỗi có thể làm giảm chất lượng dịch vụ cho toàn hệ thống.  
**Severity:** High  
**Recommended fix:** Áp dụng rate limiting/quota theo tenant hoặc user, giới hạn concurrency cho operation CPU-bound nếu phù hợp.

### 5. Log raw `Pattern` và toàn bộ `Sample`

**Problem:** Log có thể chứa dữ liệu nhạy cảm và payload rất lớn.  
**Why it happens:** Structured logging được dùng nhưng không có redaction/length limit.  
**Production impact:** Tăng chi phí log, có thể làm lộ dữ liệu và gây thêm allocation/I/O.  
**Severity:** High  
**Recommended fix:** Log hash/id, độ dài, tenant, outcome và elapsed time; truncate hoặc không log raw input.

### 6. Chỉ bắt `ArgumentException`

**Problem:** Timeout runtime không được phân biệt với invalid syntax.  
**Why it happens:** Error handling chỉ nghĩ đến compile/parse failure.  
**Production impact:** Khi thêm timeout mà không xử lý riêng, telemetry/response semantics khó phân tích.  
**Severity:** Medium  
**Recommended fix:** Xử lý riêng `RegexMatchTimeoutException`, log outcome có cấu trúc và trả response rõ ràng.

### 7. Không quan sát duration và timeout rate

**Problem:** Endpoint không có metric đủ để xác định pattern nào/caller nào làm hệ thống nóng CPU.  
**Why it happens:** Chỉ log raw request.  
**Production impact:** Điều tra incident chậm, khó xác định abuse hay regression.  
**Severity:** Medium  
**Recommended fix:** Ghi metric duration, timeout count, rejected-by-size, requests per tenant và CPU saturation ở cấp process.

## Phiên bản code đề xuất

```csharp
public sealed record ValidateRuleRequest(
    string Pattern,
    string Sample);

[ApiController]
[Route("api/rules")]
public sealed class RulesController : ControllerBase
{
    private static readonly TimeSpan MatchTimeout =
        TimeSpan.FromMilliseconds(200);

    private readonly ILogger<RulesController> _logger;

    public RulesController(ILogger<RulesController> logger)
    {
        _logger = logger;
    }

    [Authorize]
    [HttpPost("validate")]
    public IActionResult Validate(ValidateRuleRequest request)
    {
        if (string.IsNullOrWhiteSpace(request.Pattern) ||
            request.Pattern.Length > 2_000 ||
            request.Sample.Length > 50_000)
        {
            return BadRequest(new
            {
                valid = false,
                code = "input_too_large_or_empty"
            });
        }

        var started = Stopwatch.GetTimestamp();

        try
        {
            var regex = new Regex(
                request.Pattern,
                RegexOptions.IgnoreCase,
                MatchTimeout);

            var matched = regex.IsMatch(request.Sample);

            _logger.LogInformation(
                "Regex validation succeeded. PatternLength={PatternLength}, SampleLength={SampleLength}, ElapsedMs={ElapsedMs}",
                request.Pattern.Length,
                request.Sample.Length,
                Stopwatch.GetElapsedTime(started).TotalMilliseconds);

            return Ok(new { valid = true, matched });
        }
        catch (RegexMatchTimeoutException)
        {
            _logger.LogWarning(
                "Regex validation timed out. PatternLength={PatternLength}, SampleLength={SampleLength}",
                request.Pattern.Length,
                request.Sample.Length);

            return BadRequest(new
            {
                valid = false,
                code = "regex_timeout"
            });
        }
        catch (ArgumentException)
        {
            return BadRequest(new
            {
                valid = false,
                code = "invalid_regex"
            });
        }
    }
}
```

## Trade-offs

- Timeout quá ngắn có thể reject regex hợp lệ nhưng phức tạp; timeout phải dựa trên SLO và benchmark thực tế.
- Giới hạn pattern/sample giảm tính linh hoạt nhưng tạo security boundary rõ ràng.
- Nếu business cần chạy rule trên dữ liệu lớn, nên chuyển validation/execution sang worker bị cô lập tài nguyên thay vì cho chạy trực tiếp trong request path.
- Caching regex có thể giúp nếu pattern được reuse nhiều, nhưng cần bounded cache để tránh memory growth.

## Cách kiểm thử

1. **Unit test:** Pattern syntax sai, pattern rỗng, pattern/sample vượt limit.
2. **Failure-path test:** Regex gây timeout phải kết thúc trong giới hạn và trả lỗi kiểm soát.
3. **Load test:** Nhiều request đồng thời với input hợp lệ và input xấu; theo dõi CPU, latency, allocation.
4. **Abuse test:** Một tenant gửi lặp pattern tốn CPU; xác minh rate/quota policy hoạt động.
5. **Observability test:** Không log raw sample/secret; metric timeout và reject count phải tăng đúng.

## Quan sát trong production

- Metric: request duration, regex timeout count, rejected-by-size count, validation requests/tenant.
- Process metric: CPU saturation, GC pause/allocation rate, thread pool queue length nếu có liên quan.
- Trace: span cho endpoint với outcome và input-size bucket, không gắn raw input.
- Alert khi regex timeout rate hoặc CPU p95 tăng bất thường.
- Structured log chỉ giữ tenant/user/correlation id và thông tin kích thước/outcome cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn sẽ cho phép user-defined regex chạy trực tiếp trong API, và khi nào nên đưa sang isolated worker?
2. Nếu phải cache compiled regex, bạn thiết kế bounded cache và eviction thế nào?
3. Bạn sẽ benchmark và chọn timeout bao nhiêu mà không biến con số đó thành “magic number”?

# Code Review Challenge 2 — `Task.WhenAll` trên cùng một `DbContext` làm truy vấn song song thất bại ngẫu nhiên

**Chủ đề:** EF Core query execution, async/await, resource lifetime, cancellation, performance và observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một endpoint dashboard cần trả 4 khối dữ liệu độc lập: số nhân viên active, số ticket mở, 10 background job gần nhất và 20 audit event gần nhất. Team thấy các query “độc lập” nên dùng `Task.WhenAll` để giảm latency.

Endpoint dùng một `AppDbContext` scoped theo request. Production ghi nhận:

- thỉnh thoảng xuất hiện exception liên quan nhiều operation cùng chạy trên context,
- lỗi tăng rõ khi traffic cao,
- retry request thường thành công,
- database không có deadlock tương ứng,
- team định sửa bằng cách tăng connection pool và `Max Pool Size`,
- khi client cancel request, một số query vẫn tiếp tục vì không phải query nào cũng dùng token.

Business ưu tiên correctness và latency ổn định hơn là tối ưu vài chục millisecond bằng mọi giá.

## Đoạn code cần review

```csharp
public sealed class DashboardService
{
    private readonly AppDbContext _db;

    public DashboardService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<DashboardDto> GetAsync(
        Guid tenantId,
        CancellationToken cancellationToken)
    {
        var activeEmployeesTask = _db.Employees
            .Where(x => x.TenantId == tenantId && x.IsActive)
            .CountAsync(cancellationToken);

        var openTicketsTask = _db.Tickets
            .Where(x => x.TenantId == tenantId && x.Status == TicketStatus.Open)
            .CountAsync();

        var recentJobsTask = _db.BackgroundJobs
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .Take(10)
            .ToListAsync(cancellationToken);

        var auditEventsTask = _db.AuditEvents
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .Take(20)
            .ToListAsync();

        await Task.WhenAll(
            activeEmployeesTask,
            openTicketsTask,
            recentJobsTask,
            auditEventsTask);

        return new DashboardDto(
            await activeEmployeesTask,
            await openTicketsTask,
            await recentJobsTask,
            await auditEventsTask);
    }
}
```

2. Xác định các rủi ro concurrency, cancellation và database pressure.

## Kết quả code review tham khảo

### 1. Chạy nhiều EF Core operation đồng thời trên cùng một `DbContext`

**Problem:** Bốn async query bắt đầu trước khi operation trước hoàn tất.  
**Why it happens:** `Task.WhenAll` được áp dụng lên query dùng chung một scoped context.  
**Production impact:** Có thể phát sinh runtime exception hoặc behavior không được hỗ trợ; request fail không ổn định dưới tải.  
**Severity:** Critical  
**Recommended fix:** Không chạy concurrent operation trên cùng context. Chạy tuần tự hoặc dùng context độc lập cho từng operation nếu thật sự cần parallelism.

### 2. Nhầm connection pool với `DbContext` concurrency

**Problem:** Team dự định tăng pool để chữa lỗi concurrency trên context.  
**Why it happens:** Hai khái niệm resource bị đánh đồng.  
**Production impact:** Không sửa root cause và còn có thể tăng áp lực database nếu mở rộng concurrency.  
**Severity:** High  
**Recommended fix:** Sửa lifecycle/concurrency ở application layer trước; chỉ tune pool dựa trên đo lường connection contention thực tế.

### 3. Hai query không nhận `CancellationToken`

**Problem:** `CountAsync()` và `ToListAsync()` ở hai nhánh bỏ token.  
**Why it happens:** Inconsistent cancellation propagation.  
**Production impact:** Client đã cancel nhưng database/query vẫn tiếp tục, lãng phí connection/CPU và làm shutdown khó hơn.  
**Severity:** High  
**Recommended fix:** Propagate cùng token tới toàn bộ I/O phù hợp.

### 4. Parallel query có thể làm tăng database pressure mà latency không cải thiện tương xứng

**Problem:** Mỗi request có thể tiêu thụ nhiều query/connection cùng lúc nếu tách context để chạy parallel.  
**Why it happens:** Tối ưu local latency nhưng bỏ qua system-wide concurrency.  
**Production impact:** Dưới load cao, pool exhaustion hoặc DB CPU tăng khiến p95/p99 xấu hơn.  
**Severity:** High  
**Recommended fix:** Benchmark tuần tự trước; nếu parallel, giới hạn concurrency và đánh giá total QPS/connection budget.

### 5. Materialize entity đầy đủ cho dashboard read-only

**Problem:** `BackgroundJobs` và `AuditEvents` load entity tracking mặc định dù chỉ để hiển thị.  
**Why it happens:** Query chưa tối ưu cho read-only projection.  
**Production impact:** Allocation và change-tracking overhead không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Dùng `AsNoTracking()` và projection sang DTO cần thiết.

### 6. Await lại từng task sau `WhenAll` làm code khó đọc hơn cần thiết

**Problem:** Sau `WhenAll`, code tiếp tục `await` từng task.  
**Why it happens:** Pattern cơ học.  
**Production impact:** Không phải bug lớn nhưng làm intent kém rõ ràng.  
**Severity:** Low  
**Recommended fix:** Với bản tuần tự, await trực tiếp; với task độc lập hợp lệ, đọc `.Result` sau `WhenAll` hoặc giữ await nhưng tổ chức code rõ hơn.

### 7. Thiếu observability theo query group

**Problem:** Không biết query nào chậm/lỗi khi dashboard fail.  
**Why it happens:** Không có span/metric riêng theo logical query.  
**Production impact:** Khó phân biệt lỗi context concurrency, connection wait hay một SQL cụ thể chậm.  
**Severity:** Medium  
**Recommended fix:** Trace query groups, theo dõi DB duration, connection wait, pool saturation và endpoint p95/p99.

## Phiên bản code đề xuất

```csharp
public sealed class DashboardService
{
    private readonly AppDbContext _db;

    public DashboardService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<DashboardDto> GetAsync(
        Guid tenantId,
        CancellationToken cancellationToken)
    {
        var activeEmployees = await _db.Employees
            .Where(x => x.TenantId == tenantId && x.IsActive)
            .CountAsync(cancellationToken);

        var openTickets = await _db.Tickets
            .Where(x => x.TenantId == tenantId &&
                        x.Status == TicketStatus.Open)
            .CountAsync(cancellationToken);

        var recentJobs = await _db.BackgroundJobs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .Take(10)
            .Select(x => new BackgroundJobDto(
                x.Id,
                x.Status,
                x.CreatedAt))
            .ToListAsync(cancellationToken);

        var auditEvents = await _db.AuditEvents
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .Take(20)
            .Select(x => new AuditEventDto(
                x.Id,
                x.Action,
                x.CreatedAt))
            .ToListAsync(cancellationToken);

        return new DashboardDto(
            activeEmployees,
            openTickets,
            recentJobs,
            auditEvents);
    }
}
```

> Nếu profiling cho thấy bốn query tuần tự không đạt SLO, có thể dùng `IDbContextFactory<AppDbContext>` để tạo context độc lập cho từng nhánh. Tuy nhiên đó là quyết định tối ưu có chi phí: mỗi request có thể dùng nhiều connection đồng thời, vì vậy phải load test và đặt concurrency budget ở cấp hệ thống.

## Trade-offs

- Chạy tuần tự đơn giản, đúng lifecycle và thường ổn định hơn dưới load.
- Chạy song song với context riêng có thể giảm latency ở traffic thấp nhưng tăng tổng connection concurrency.
- Gộp dashboard thành một query lớn không mặc định tốt hơn; có thể tạo SQL phức tạp hoặc khó tối ưu.
- Có thể cache một số aggregate nếu freshness cho phép, nhưng phải xác định rõ TTL và consistency requirement.

## Cách kiểm thử

1. **Integration test:** Gọi endpoint nhiều lần đồng thời và xác minh không còn lỗi concurrent operation trên context.
2. **Cancellation test:** Cancel request giữa chừng; query đang chạy phải nhận cancellation phù hợp.
3. **Load test:** So sánh tuần tự và parallel-with-separate-context về p50/p95/p99, DB CPU và connection usage.
4. **Correctness test:** Tenant A không được nhìn thấy aggregate/list của tenant B.
5. **Performance test:** Verify projection/read-only query không materialize field/graph không cần thiết.

## Quan sát trong production

- Endpoint metrics: p50/p95/p99 latency, error rate, cancellation count.
- Database: query duration, active connections, connection wait/pool saturation, CPU và slow-query statistics.
- Trace: span riêng cho từng logical query hoặc DB command.
- Alert khi connection wait, timeout hoặc endpoint error rate tăng sau release.
- Log nên ghi tenant/correlation id và logical operation, không log raw entity data nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu tuần tự không đạt SLO, bạn sẽ chứng minh parallel query đáng giá bằng dữ liệu nào?
2. Bạn thiết kế `IDbContextFactory` và concurrency limit thế nào để tránh một request chiếm quá nhiều connection?
3. Trong dashboard này, aggregate nào có thể cache mà vẫn giữ business correctness?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Input do người dùng điều khiển có thể biến một operation tưởng nhẹ thành resource-exhaustion problem.
- Timeout, input limits và admission control là một phần của API correctness đối với workload tốn CPU.
- `DbContext` là unit-of-work có lifecycle rõ ràng; async không đồng nghĩa với việc có thể chạy nhiều operation đồng thời trên cùng instance.
- Tối ưu latency cục bộ cần được đánh giá cùng connection budget, database pressure và p95/p99 toàn hệ thống.
- Cancellation và observability phải được thiết kế xuyên suốt chứ không thêm sau cùng.

## Mẫu tư duy cần nhớ

- Clarify resource boundary before parallelizing.
- Bound user-controlled work by time, size and concurrency.
- Measure system-wide impact, not only single-request latency.
- Propagate cancellation through every I/O path.
- Treat observability as part of the design.
