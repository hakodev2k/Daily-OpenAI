# Code Review Challenge 1 — Azure Service Bus consumer xử lý payment event: tại sao cùng một business event vẫn có thể tạo side effect hai lần?

**Chủ đề:** Azure Service Bus, C#/.NET, idempotency, message settlement, retry, database transaction, Outbox/Inbox concepts, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một order platform nhận `PaymentCaptured` event qua Azure Service Bus queue. Consumer chạy trên ASP.NET Core Worker Service trong Azure App Service và có thể scale ra nhiều instances.

Mục tiêu nghiệp vụ:

- mỗi payment event phải cập nhật order đúng một lần theo business semantics;
- sau khi cập nhật thành công, hệ thống gửi email xác nhận cho khách hàng;
- message lỗi tạm thời nên retry;
- poison message cần đi vào DLQ;
- restart, network failure hoặc message redelivery không được tạo duplicate business effect;
- throughput giờ cao điểm khoảng vài chục message/giây;
- database là SQL Server;
- email provider là external dependency và đôi khi timeout 10–20 giây.

Production gần đây xuất hiện một số order có hai email xác nhận dù database chỉ có một trạng thái `Paid`. Team thấy một số message có `DeliveryCount > 1`, nhưng chưa xác định duplicate đến từ producer, Service Bus redelivery, lost settlement hay consumer concurrency.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<PaymentConsumer> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        try
        {
            var message = JsonSerializer.Deserialize<PaymentCaptured>(
                args.Message.Body.ToString());

            if (message is null)
            {
                await args.DeadLetterMessageAsync(args.Message);
                return;
            }

            var alreadyProcessed = await _db.ProcessedMessages
                .AnyAsync(x => x.MessageId == args.Message.MessageId);

            if (alreadyProcessed)
            {
                await args.CompleteMessageAsync(args.Message);
                return;
            }

            var order = await _db.Orders
                .SingleAsync(x => x.Id == message.OrderId);

            order.Status = OrderStatus.Paid;
            order.PaidAtUtc = DateTime.UtcNow;

            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = args.Message.MessageId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync();

            await _emailSender.SendPaymentConfirmationAsync(
                order.CustomerEmail,
                order.Id,
                CancellationToken.None);

            await args.CompleteMessageAsync(args.Message);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Payment event failed. Body={Body}",
                args.Message.Body.ToString());

            if (args.Message.DeliveryCount >= 3)
            {
                await args.DeadLetterMessageAsync(args.Message);
            }
            else
            {
                await args.AbandonMessageAsync(args.Message);
            }
        }
    }
}
```

## Kết quả code review tham khảo

### Critical — Database commit và email side effect không có durable coordination

**Vấn đề:**  
Database được commit trước khi gửi email, còn message chỉ được complete sau email.

**Tại sao xảy ra:**  
Nếu `SaveChangesAsync()` thành công, email gửi thành công, nhưng process crash hoặc `CompleteMessageAsync()` không tới Service Bus, message có thể được giao lại. Consumer lần sau thấy `ProcessedMessages` tồn tại và complete ngay, nhưng duplicate email đã xảy ra ở lần trước nếu failure xảy ra sau email nhưng trước settlement.

Một failure window khác là email provider nhận request và gửi email nhưng client timeout trước khi nhận response. Consumer không biết side effect đã xảy ra hay chưa.

**Ảnh hưởng production:**  
Duplicate email, khó xác định trạng thái thật của external side effect, support ticket và mất niềm tin người dùng.

**Cách sửa:**  
Không gọi email trực tiếp trong critical consume transaction. Commit business state + một durable Outbox record trong cùng SQL transaction. Một publisher/worker riêng đọc Outbox và gửi email với idempotency key nếu provider hỗ trợ, hoặc quản lý trạng thái delivery/retry rõ ràng.

---

### High — Check-then-insert `ProcessedMessages` có race condition

**Vấn đề:**  
`AnyAsync` và `Insert` là hai thao tác riêng.

**Tại sao xảy ra:**  
Hai consumers có thể cùng đọc `false`, cùng update business state và cùng insert `ProcessedMessages` nếu database không có unique constraint trên `MessageId`.

**Ảnh hưởng production:**  
Duplicate processing hoặc lỗi dữ liệu dưới concurrency. Nếu schema có unique constraint nhưng code không xử lý conflict có chủ đích, một consumer có thể fail sau khi đã làm work khác trong transaction scope không rõ ràng.

**Cách sửa:**  
Dùng **database-enforced uniqueness** cho idempotency key, ví dụ unique index trên `ProcessedMessages.MessageId` hoặc business event id. Insert inbox marker và business changes trong cùng transaction. Conflict vì duplicate phải được xử lý như expected duplicate, không phải generic infrastructure failure.

---

### High — Chưa chứng minh `MessageId` là business-stable idempotency key

**Vấn đề:**  
Code giả định `args.Message.MessageId` đại diện duy nhất cho business event.

**Tại sao xảy ra:**  
Producer có thể retry bằng một `MessageId` mới cho cùng payment nếu không có contract ổn định. Service Bus duplicate detection cũng dựa trên application-controlled `MessageId` trong configured time window, nên không giúp nếu producer phát id mới cho cùng business event.

**Ảnh hưởng production:**  
Hai logically identical `PaymentCaptured` events có thể vượt qua inbox check.

**Cách sửa:**  
Thiết kế idempotency key từ business event identity, ví dụ `PaymentId`/`EventId` immutable do producer phát và giữ nguyên khi retry. Có thể dùng chính key này làm `MessageId`, nhưng contract phải explicit.

---

### High — Không dùng cancellation token của message handler

**Vấn đề:**  
EF Core calls và email call không dùng cancellation token từ processing context; email còn dùng `CancellationToken.None`.

**Tại sao xảy ra:**  
Khi host shutdown, processor stop hoặc operation bị hủy, work vẫn tiếp tục lâu hơn cần thiết.

**Ảnh hưởng production:**  
Shutdown chậm, tăng khả năng lock expiry/redelivery, giữ DB connection và external call không cần thiết.

**Cách sửa:**  
Propagate `args.CancellationToken` vào EF Core và downstream calls, đồng thời thiết kế graceful shutdown. Cancellation không được coi là đảm bảo rollback external side effect đã được provider nhận.

---

### High — Generic catch + manual retry/DLQ policy có thể trộn transient và permanent failures

**Vấn đề:**  
Mọi exception được xử lý giống nhau và DLQ dựa chỉ trên `DeliveryCount >= 3`.

**Tại sao xảy ra:**  
Validation error, missing order, SQL timeout, serialization incompatibility và transient network failure có recovery semantics khác nhau.

**Ảnh hưởng production:**  
Poison message có thể retry vô ích; transient dependency outage có thể đưa message vào DLQ quá sớm; support mất failure reason có cấu trúc.

**Cách sửa:**  
Phân loại lỗi: invalid contract/permanent business violation → dead-letter với reason + safe metadata; transient infrastructure → để retry theo processor/entity policy; expected duplicate → complete. Chọn threshold theo SLA và failure model, không hard-code một con số không có căn cứ.

---

### Medium — Có nguy cơ dùng `DbContext` sai lifetime khi processor chạy concurrent callbacks

**Vấn đề:**  
Snippet inject trực tiếp `AppDbContext` vào consumer nhưng không cho thấy consumer lifetime và processor concurrency model.

**Tại sao xảy ra:**  
Nếu `PaymentConsumer` là singleton hoặc cùng instance xử lý nhiều callbacks song song, một scoped/non-thread-safe `DbContext` có thể bị dùng concurrent.

**Ảnh hưởng production:**  
`InvalidOperationException`, mixed tracking state hoặc undefined application behavior.

**Cách sửa:**  
Xác minh registration. Với singleton processor/worker, tạo DI scope per message hoặc dùng `IDbContextFactory<AppDbContext>` để mỗi concurrent message có context riêng.

---

### Medium — Logging raw message body có thể lộ dữ liệu nhạy cảm

**Vấn đề:**  
Catch block log toàn bộ body.

**Tại sao xảy ra:**  
Payment event có thể chứa customer identifiers, email hoặc fields nhạy cảm.

**Ảnh hưởng production:**  
Data leakage vào Application Insights/Kibana, retention/compliance risk.

**Cách sửa:**  
Log structured metadata an toàn: `MessageId`, `EventId`, `OrderId` đã policy-approved, `DeliveryCount`, correlation ID, exception category. Không log raw payload mặc định.

---

### Medium — Thời điểm cập nhật `PaidAtUtc` không phản ánh domain event time

**Vấn đề:**  
Code dùng `DateTime.UtcNow` khi consumer xử lý message.

**Tại sao xảy ra:**  
Queue delay/retry có thể khiến processing time khác payment capture time.

**Ảnh hưởng production:**  
Audit/reporting sai semantics nếu field này được hiểu là thời điểm payment thực sự captured.

**Cách sửa:**  
Nếu event có authoritative `CapturedAtUtc`, persist value đó; giữ `ProcessedAtUtc` riêng cho operational timing.

## Phiên bản đề xuất

Một cách thiết kế an toàn hơn là dùng Inbox + Outbox trong cùng database transaction. Ví dụ rút gọn:

```csharp
public sealed class PaymentConsumer
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<PaymentConsumer> logger)
    {
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var ct = args.CancellationToken;
        var envelope = JsonSerializer.Deserialize<PaymentCaptured>(
            args.Message.Body.ToString());

        if (envelope is null || envelope.EventId == Guid.Empty)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                deadLetterReason: "InvalidContract",
                cancellationToken: ct);
            return;
        }

        await using var db = await _dbFactory.CreateDbContextAsync(ct);
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        var duplicate = await db.ProcessedMessages
            .AnyAsync(x => x.EventId == envelope.EventId, ct);

        if (!duplicate)
        {
            var order = await db.Orders
                .SingleOrDefaultAsync(x => x.Id == envelope.OrderId, ct);

            if (order is null)
            {
                await tx.RollbackAsync(ct);
                await args.DeadLetterMessageAsync(
                    args.Message,
                    deadLetterReason: "OrderNotFound",
                    cancellationToken: ct);
                return;
            }

            order.Status = OrderStatus.Paid;
            order.PaidAtUtc = envelope.CapturedAtUtc;

            db.ProcessedMessages.Add(new ProcessedMessage
            {
                EventId = envelope.EventId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            db.OutboxMessages.Add(OutboxMessage.PaymentConfirmation(
                envelope.EventId,
                order.Id,
                order.CustomerEmail));

            try
            {
                await db.SaveChangesAsync(ct);
                await tx.CommitAsync(ct);
            }
            catch (DbUpdateException ex) when (IsDuplicateEvent(ex))
            {
                await tx.RollbackAsync(ct);
                _logger.LogInformation(
                    "Duplicate payment event ignored. EventId={EventId}",
                    envelope.EventId);
            }
        }
        else
        {
            await tx.RollbackAsync(ct);
        }

        await args.CompleteMessageAsync(args.Message, ct);
    }
}
```

Database phải enforce uniqueness, ví dụ:

```sql
CREATE UNIQUE INDEX UX_ProcessedMessages_EventId
ON ProcessedMessages(EventId);
```

Sau đó một Outbox dispatcher độc lập gửi email:

```text
Outbox Pending
  -> send with stable idempotency key when provider supports it
  -> mark Sent only after confirmed success
  -> retry transient failures with bounded backoff
  -> alert / quarantine persistent failures
```

Nếu provider không hỗ trợ idempotency, exactly-once external side effect vẫn không thể được “tạo ra” chỉ bằng SQL transaction + Service Bus settlement. Khi đó phải xác định acceptable semantics, provider reconciliation capability và cách deduplicate ở downstream nếu có thể.

Microsoft Learn mô tả rằng message có thể được redeliver khi lock bị mất, consumer restart trước settlement hoặc settlement thành công phía service nhưng acknowledgement về client bị gián đoạn. Vì vậy consumer phải được thiết kế để có thể reprocess an toàn, không chỉ dựa vào assumption “mỗi message chỉ tới một lần”.

Tài liệu tham khảo:

- Microsoft Learn — Azure Service Bus duplicate detection: `https://learn.microsoft.com/azure/service-bus-messaging/duplicate-detection`
- Microsoft Learn — Prevent message loss and duplicate processing in Azure Service Bus: `https://learn.microsoft.com/azure/service-bus-messaging/service-bus-message-loss-and-duplicates`

## Giải thích thiết kế sau khi sửa

Database transaction chịu trách nhiệm cho **business state + durable intent to send email**. Service Bus settlement chỉ xảy ra sau khi durable state được commit.

Khi message quay lại:

- unique business event id bảo vệ database;
- Inbox marker cho phép nhận diện duplicate;
- Outbox bảo đảm email intent không biến mất giữa DB commit và external call;
- Outbox dispatcher retry độc lập, không kéo dài message lock chỉ vì email provider chậm.

Điểm quan trọng là không claim “exactly once” cho toàn distributed workflow. Có nhiều independent durability boundaries: Service Bus, SQL Server và email provider. Design tốt hướng tới **effectively-once business outcome** bằng idempotency + durable state + reconciliation.

## Trade-offs

Inbox/Outbox tăng thêm bảng, cleanup policy, dispatcher, monitoring và operational complexity. Với hệ thống nhỏ, có thể dùng một transactional job table thay vì framework/pattern phức tạp, miễn cùng nguyên tắc durable handoff được giữ.

Unique idempotency records cũng cần retention policy. Nếu xóa quá sớm, một message rất cũ được replay có thể vượt qua dedupe. Nếu giữ vô hạn, bảng tăng kích thước. Retention phải theo replay window, audit requirement và business semantics.

Nếu email provider hỗ trợ stable idempotency key, reliability tốt hơn. Nếu không, vẫn còn ambiguous outcome khi timeout sau khi provider đã nhận request; cần reconciliation hoặc chấp nhận bounded duplicate risk theo requirement.

## Cách kiểm thử

1. **Concurrency test:** giao cùng `EventId` đồng thời cho nhiều handler instances; chỉ một business transition + một Outbox intent được commit.
2. **Failure-path test:** crash sau SQL commit nhưng trước `CompleteMessageAsync`; redelivery không tạo thêm payment transition hoặc thêm Outbox record.
3. **External dependency test:** email provider nhận request rồi timeout response; xác minh retry/idempotency/reconciliation behavior theo contract.
4. **Lock/redelivery test:** cố ý làm processing vượt lock hoặc simulate settlement failure; duplicate delivery vẫn an toàn.
5. **Security/observability test:** exception path không log raw payload/PII và vẫn có đủ correlation metadata.

## Quan sát trong production

Nên có structured logs/metrics/traces cho:

- `message_id`, `event_id`, `delivery_count`;
- queue/subscription name;
- duplicate-inbox count;
- message processing duration;
- Service Bus lock-lost / settlement failures;
- DB transaction duration và duplicate-key conflicts;
- Outbox pending age, retry count, success/failure rate;
- email provider latency/result category;
- DLQ count + dead-letter reason;
- correlation từ producer event → consumer trace → order update → Outbox delivery.

Alert nên tập trung vào **oldest Outbox age**, DLQ growth và repeated lock/settlement failures thay vì chỉ CPU/memory.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Azure Service Bus duplicate detection đã bật, vì sao bạn vẫn giữ consumer idempotency?
2. Nếu email provider không hỗ trợ idempotency key, bạn sẽ thiết kế reconciliation/UX thế nào để giảm duplicate side effect?
3. Khi nào bạn sẽ chọn đơn giản hóa bằng synchronous processing thay vì Outbox, và requirement nào khiến trade-off đó chấp nhận được?

# Code Review Challenge 2 — Đồng bộ SQL Server sang Elasticsearch: polling job chạy “ổn” nhưng âm thầm bỏ sót document và gây indexing pressure

**Chủ đề:** Elasticsearch, SQL Server, EF Core, C#/.NET, incremental indexing, checkpoint, Bulk API, eventual consistency, failure recovery, search observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một e-commerce search service dùng SQL Server làm source of truth và Elasticsearch làm search index. Một `BackgroundService` poll product changes mỗi 10 giây.

Mục tiêu:

- search có thể eventual consistent trong khoảng dưới vài phút;
- không được âm thầm bỏ sót product update;
- reprocessing cùng product phải an toàn;
- production có thể có burst hàng chục nghìn product updates trong vài phút;
- product có thể bị soft-delete;
- search cluster thỉnh thoảng trả partial failures hoặc timeout;
- job có thể restart bất kỳ lúc nào;
- application chạy nhiều instances trong tương lai, dù hiện tại mới có một instance.

Sau một campaign import, team phát hiện một số products trong SQL đã cập nhật nhưng Elasticsearch vẫn hiển thị dữ liệu cũ. Restart indexer đôi khi “tự hết” với một số record, nhưng không phải tất cả. CPU SQL bình thường; Elasticsearch indexing latency tăng rõ trong burst.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductIndexer : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly IProductSearchClient _search;
    private readonly ILogger<ProductIndexer> _logger;
    private DateTime _lastSyncUtc = DateTime.UtcNow.AddMinutes(-5);

    public ProductIndexer(
        IServiceScopeFactory scopeFactory,
        IProductSearchClient search,
        ILogger<ProductIndexer> logger)
    {
        _scopeFactory = scopeFactory;
        _search = search;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                using var scope = _scopeFactory.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

                var batch = await db.Products
                    .AsNoTracking()
                    .Where(x => x.UpdatedAtUtc > _lastSyncUtc)
                    .OrderBy(x => x.UpdatedAtUtc)
                    .Take(500)
                    .ToListAsync(stoppingToken);

                foreach (var product in batch)
                {
                    await _search.IndexAsync(
                        indexName: "products",
                        id: product.Id.ToString(),
                        document: ProductDocument.From(product),
                        refresh: true,
                        cancellationToken: stoppingToken);
                }

                _lastSyncUtc = DateTime.UtcNow;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Product indexing cycle failed");
            }

            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review code và:

1. tìm các bug có thể làm **miss updates** dù job không crash;
2. đánh giá cursor/checkpoint semantics khi nhiều rows có cùng `UpdatedAtUtc`;
3. chỉ ra performance issues khi burst lớn;
4. đánh giá failure handling khi một số index operations thành công, số khác thất bại;
5. xử lý soft-delete và restart;
6. đề xuất design có thể scale lên nhiều application instances mà không duplicate uncontrolled work;
7. giải thích cách test correctness và đo search freshness trong production.

## Câu hỏi gợi mở

1. Nếu có 5.000 rows cùng `UpdatedAtUtc` nhưng query chỉ `Take(500)`, điều gì xảy ra khi `_lastSyncUtc` bị nhảy tới `DateTime.UtcNow`?
2. Nếu process restart, checkpoint hiện nằm ở đâu?
3. `refresh: true` cho từng document có ảnh hưởng gì tới indexing throughput và có thực sự cần cho SLA vài phút không?
4. Nếu product bị soft-delete, `Where(x => x.UpdatedAtUtc > ...)` + `IndexAsync` hiện tại có làm document biến mất khỏi search không?
5. Nếu document thứ 120 fail nhưng 121–500 thành công, checkpoint nên được advance tới đâu?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **checkpoint không đại diện cho durable, contiguous progress**. Hãy tìm mọi chỗ cursor có thể vượt qua một record chưa được index thành công.

### Gợi ý 2

Elasticsearch search visibility và indexing acknowledgement là hai khái niệm khác nhau. Đừng dùng forced refresh trên từng item để che một ingestion design không có checkpoint/retry semantics.

## Kết quả code review tham khảo

### Critical — `_lastSyncUtc = DateTime.UtcNow` có thể nhảy qua các rows chưa đọc

**Vấn đề:**  
Cursor được advance tới wall-clock time sau khi chỉ đọc tối đa 500 rows.

**Tại sao xảy ra:**  
Nếu có hơn 500 rows thỏa điều kiện, các rows còn lại có thể có `UpdatedAtUtc` nhỏ hơn thời điểm `DateTime.UtcNow` mới. Cycle sau query `UpdatedAtUtc > _lastSyncUtc` và bỏ qua chúng vĩnh viễn.

**Ảnh hưởng production:**  
Silent data loss trong search index; application không có exception nên rất khó phát hiện.

**Cách sửa:**  
Checkpoint phải advance tới **last successfully processed source position**, không phải current wall clock. Dùng stable ordered cursor như `(UpdatedAtUtc, Id)` hoặc tốt hơn một monotonic change/version sequence nếu source cung cấp.

---

### High — Cursor chỉ dùng timestamp không đủ total ordering

**Vấn đề:**  
Query order chỉ theo `UpdatedAtUtc`, filter dùng `>`.

**Tại sao xảy ra:**  
Nhiều rows có thể cùng timestamp resolution. Nếu page boundary cắt giữa nhóm cùng timestamp, cycle sau với `>` sẽ bỏ qua các rows còn lại có timestamp bằng checkpoint.

**Ảnh hưởng production:**  
Missed documents phụ thuộc timing/data distribution, thường chỉ xuất hiện ở burst import.

**Cách sửa:**  
Dùng deterministic keyset ordering:

```text
ORDER BY UpdatedAtUtc, Id
WHERE UpdatedAtUtc > @lastTime
   OR (UpdatedAtUtc = @lastTime AND Id > @lastId)
```

Persist cả hai values sau durable success.

---

### High — Checkpoint chỉ nằm trong memory

**Vấn đề:**  
`_lastSyncUtc` bị reset khi process restart.

**Tại sao xảy ra:**  
Indexer không có durable checkpoint store.

**Ảnh hưởng production:**  
Có thể reindex một khoảng dữ liệu cũ hoặc, tùy default/window, không replay đủ để sửa các missed updates trước đó. Restart behavior không deterministic.

**Cách sửa:**  
Persist checkpoint trong SQL/table operational state hoặc một durable coordinator. Reprocessing cần idempotent vì crash có thể xảy ra sau indexing nhưng trước checkpoint commit.

---

### High — Per-document `refresh: true` tạo indexing pressure không cần thiết

**Vấn đề:**  
Mỗi document yêu cầu refresh visibility ngay sau indexing.

**Tại sao xảy ra:**  
Elasticsearch vốn có near-real-time search visibility; forced refresh thường tốn tài nguyên và có thể làm throughput indexing giảm mạnh khi gọi liên tục.

**Ảnh hưởng production:**  
Indexing latency tăng, nhiều refresh operations, cluster pressure trong burst import.

**Cách sửa:**  
Không force refresh từng item trừ khi business thực sự cần immediate read-after-write search visibility. Với SLA vài phút, dùng normal refresh behavior và batch/Bulk API; nếu workflow đặc biệt cần wait-for visibility, áp dụng có chủ đích ở boundary phù hợp.

---

### High — Không có batch/Bulk API và không kiểm tra partial failure semantics

**Vấn đề:**  
Code gửi từng document tuần tự.

**Tại sao xảy ra:**  
Network overhead lớn. Khi chuyển sang Bulk, mỗi item vẫn có thể success/fail độc lập nên implementation phải inspect item results, không chỉ HTTP-level success.

**Ảnh hưởng production:**  
Throughput thấp, backlog tăng và retry khó tối ưu.

**Cách sửa:**  
Batch source rows rồi dùng Bulk API qua wrapper có result per item. Chỉ advance durable checkpoint qua contiguous range đã được xử lý an toàn; failures phải retry/quarantine theo policy.

---

### High — Soft-delete không được đồng bộ thành delete/tombstone trong search

**Vấn đề:**  
Flow chỉ index current `ProductDocument`.

**Tại sao xảy ra:**  
Nếu SQL soft-delete row nhưng search document vẫn tồn tại, search tiếp tục trả product không còn active.

**Ảnh hưởng production:**  
User thấy sản phẩm không được phép bán/hiển thị.

**Cách sửa:**  
Change feed phải mang operation type hoặc row có `IsDeleted`. Indexer gửi delete operation cho search document tương ứng. Nếu hard-delete source rows, cần CDC/outbox/change table/tombstone để deletion event không biến mất cùng row.

---

### Medium — Generic catch có thể tạo hot retry loop theo cycle mà không phân loại lỗi

**Vấn đề:**  
Mọi exception chỉ log rồi sleep 10 giây.

**Tại sao xảy ra:**  
Mapping error/permanent bad document và transient cluster timeout cần treatment khác nhau.

**Ảnh hưởng production:**  
Một poison record có thể chặn progress hoặc bị retry vô hạn; outage làm logs noisy mà không có backoff.

**Cách sửa:**  
Phân loại transient/permanent failures, bounded exponential backoff, retry budget và quarantine/dead-letter equivalent cho bad documents.

---

### Medium — Multi-instance execution chưa có coordination model

**Vấn đề:**  
Mỗi application instance sẽ chạy cùng poller và checkpoint riêng.

**Tại sao xảy ra:**  
Scale-out tạo duplicate reads/index operations và race ở checkpoint nếu sau này checkpoint được shared nhưng không có ownership/concurrency control.

**Ảnh hưởng production:**  
Waste, higher Elasticsearch load, non-deterministic progress.

**Cách sửa:**  
Chọn explicit model: single active indexer via lease/leader, partitioned work, queue-based change events hoặc database job claiming. Không cần distributed lock nếu architecture có một dedicated worker deployment với replicas=1 và HA requirement cho phép, nhưng failover semantics phải rõ.

---

### Medium — Không có freshness SLO/lag telemetry

**Vấn đề:**  
Log chỉ báo cycle exception.

**Tại sao xảy ra:**  
Indexer có thể “healthy” về process nhưng search dữ liệu stale hàng giờ.

**Ảnh hưởng production:**  
Silent degradation không được phát hiện.

**Cách sửa:**  
Theo dõi source-to-index lag, checkpoint age, batch backlog, indexed/deleted/failed docs, bulk latency và sampled source-vs-index consistency checks.

## Phiên bản đề xuất

Một implementation an toàn hơn nên dùng durable stable cursor và bulk writer abstraction. Ví dụ rút gọn:

```csharp
public sealed record SearchCheckpoint(DateTime UpdatedAtUtc, long ProductId);

public sealed class ProductIndexer : BackgroundService
{
    private const int BatchSize = 500;
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IProductSearchBulkWriter _search;
    private readonly ICheckpointStore _checkpoints;
    private readonly ILogger<ProductIndexer> _logger;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var checkpoint = await _checkpoints.LoadAsync(
                "products",
                stoppingToken);

            await using var db = await _dbFactory.CreateDbContextAsync(stoppingToken);

            var batch = await db.Products
                .AsNoTracking()
                .Where(x =>
                    x.UpdatedAtUtc > checkpoint.UpdatedAtUtc ||
                    (x.UpdatedAtUtc == checkpoint.UpdatedAtUtc &&
                     x.Id > checkpoint.ProductId))
                .OrderBy(x => x.UpdatedAtUtc)
                .ThenBy(x => x.Id)
                .Take(BatchSize)
                .Select(x => new ProductChange(
                    x.Id,
                    x.UpdatedAtUtc,
                    x.IsDeleted,
                    x.Name,
                    x.Description,
                    x.Price))
                .ToListAsync(stoppingToken);

            if (batch.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
                continue;
            }

            var operations = batch.Select(change =>
                change.IsDeleted
                    ? SearchOperation.Delete(change.Id.ToString())
                    : SearchOperation.Index(
                        change.Id.ToString(),
                        ProductDocument.From(change)))
                .ToArray();

            var result = await _search.BulkAsync(
                "products",
                operations,
                stoppingToken);

            if (!result.AllSucceeded)
            {
                foreach (var failure in result.Failures)
                {
                    _logger.LogWarning(
                        "Search indexing item failed. ProductId={ProductId} Category={Category}",
                        failure.Id,
                        failure.Category);
                }

                await DelayWithBackoffAsync(stoppingToken);
                continue;
            }

            var last = batch[^1];

            await _checkpoints.SaveAsync(
                "products",
                new SearchCheckpoint(last.UpdatedAtUtc, last.Id),
                stoppingToken);
        }
    }
}
```

Implementation này vẫn là **at-least-once indexing**: crash có thể xảy ra sau Bulk success nhưng trước checkpoint save. Điều đó chấp nhận được nếu `Index`/`Delete` dùng stable document id và reapplying cùng source state là idempotent theo search projection contract.

Tuy nhiên timestamp + id chỉ an toàn khi `UpdatedAtUtc` thực sự được cập nhật atomically cho mọi source change và rows không thể bị hard-delete mà không có tombstone. Với hệ thống quan trọng hơn, một durable change table/outbox/CDC sequence thường rõ semantics hơn:

```text
Product transaction
  -> update Products
  -> append ProductSearchChange(sequence, productId, operation)

Indexer
  -> read sequence > checkpoint
  -> bulk index/delete
  -> persist checkpoint
```

`sequence` cung cấp monotonic ordering rõ hơn timestamp. Việc có cần CDC, Outbox hay một queue riêng phải dựa trên throughput, ownership và operational cost; không tự động thêm messaging nếu simple change table đáp ứng requirement.

Elastic documentation mô tả Bulk API cho phép nhiều index/delete/update operations trong một request để giảm overhead, và bulk response phải được kiểm tra vì từng item có thể fail riêng. Search visibility cũng chịu refresh semantics; không nên force refresh cho mọi write khi requirement không cần immediate visibility.

Tài liệu tham khảo:

- Elastic — Bulk API: `https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-bulk`
- Elastic — Near real-time search / refresh concepts: `https://www.elastic.co/guide/en/elasticsearch/reference/current/near-real-time.html`

## Giải thích thiết kế sau khi sửa

Có ba invariants chính:

1. **Stable total order:** mọi source change có vị trí deterministic.
2. **Durable checkpoint:** restart không làm mất knowledge về contiguous progress.
3. **Idempotent replay:** indexer được phép xử lý lại một range nếu crash xảy ra ở boundary bất định.

Bulk improves throughput, nhưng correctness không đến từ Bulk. Correctness đến từ source ordering + durable checkpoint + item-level failure handling + replay-safe operations.

Search là derived projection, nên source of truth vẫn là SQL Server. Nếu index corrupt hoặc checkpoint history không đáng tin, hệ thống nên có khả năng rebuild index từ source hoặc reprocess change log vào một new index rồi alias-switch sau validation, thay vì patch thủ công từng document.

## Trade-offs

Timestamp + ID keyset là giải pháp đơn giản, ít infrastructure nhưng phụ thuộc chất lượng `UpdatedAtUtc` và delete semantics.

Change table/Outbox tạo correctness rõ hơn nhưng tăng write amplification, storage và cleanup. CDC có thể giảm application coupling nhưng thêm operational expertise và retention concerns.

Single active indexer dễ reasoning nhưng giới hạn throughput/HA. Partitioned consumers scale tốt hơn nhưng cần partition key, checkpoint per partition và replay model phức tạp hơn.

Forced refresh có thể làm data visible sớm hơn nhưng đánh đổi indexing throughput. Với requirement “dưới vài phút”, thường nên đo default refresh + end-to-end lag trước khi dùng aggressive refresh controls.

## Cách kiểm thử

1. **Pagination correctness test:** tạo >500 rows có cùng `UpdatedAtUtc`; tất cả phải được index qua nhiều batches, không duplicate/miss ngoài replay cho phép.
2. **Crash-recovery test:** simulate crash sau Bulk success nhưng trước checkpoint save; restart replays batch an toàn và cuối cùng converges đúng.
3. **Partial failure test:** một vài Bulk items fail; checkpoint không được vượt qua unhandled failures và retry/quarantine behavior đúng.
4. **Delete test:** soft-delete/hard-delete-with-tombstone phải remove document khỏi search.
5. **Load test:** burst hàng chục nghìn updates; đo source-to-index lag, bulk throughput, cluster indexing latency và SQL query cost.

## Quan sát trong production

Nên có metrics/traces cho:

- durable checkpoint position + age;
- newest source change timestamp/sequence;
- **source-to-index lag** p50/p95/max;
- rows fetched per batch;
- bulk request duration/size;
- item success/failure/retry count;
- delete operation count;
- Elasticsearch rejected/indexing pressure signals phù hợp cluster;
- worker restart count;
- active indexer owner/lease nếu có coordination;
- sampled consistency check giữa SQL source và search document version.

Một dashboard chỉ hiện “background job running” là chưa đủ. Metric quan trọng là **projection có đang hội tụ về source of truth trong freshness SLO hay không**.

## Câu hỏi phỏng vấn mở rộng

1. Nếu requirement đổi từ “search stale vài phút được” thành “user update product xong phải search thấy ngay”, bạn thay consistency contract và architecture thế nào?
2. Nếu phải chạy 8 indexer instances, bạn partition/claim work ra sao để vẫn giữ deterministic checkpoint và replay semantics?
3. Khi nào bạn chọn rebuild toàn index + alias switch thay vì cố sửa incremental pipeline hiện tại?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Service Bus consumer phải được thiết kế cho **redelivery**. Settlement failure, lock loss, restart hoặc ambiguous network outcome có thể khiến cùng message được xử lý lại.
- Consumer idempotency không chỉ là `SELECT rồi INSERT`; uniqueness cần được enforce ở durable store và gắn với stable business event identity.
- External side effect như email không thể được atomically commit cùng SQL + Service Bus. Inbox/Outbox giúp tạo durable coordination và giảm failure window.
- Elasticsearch là derived projection; incremental sync chỉ an toàn khi có stable source ordering, durable checkpoint, idempotent replay và explicit delete semantics.
- Cursor không được nhảy theo wall clock. Nó phải đại diện cho **contiguous progress đã xử lý thành công**.
- Performance optimization như Bulk API hoặc refresh tuning chỉ nên thực hiện sau khi correctness semantics rõ ràng và được đo bằng backlog/freshness metrics.

## Mẫu tư duy cần nhớ

- **Cắt workflow tại từng failure boundary:** hỏi điều gì đã durable nếu process chết ngay tại đó.
- **Idempotency phải được enforce, không chỉ được kiểm tra.**
- **Checkpoint chỉ được advance qua work đã hoàn tất an toàn.**
- **Derived data phải có replay/rebuild path.**
- **Đo end-to-end freshness/lag thay vì chỉ đo worker “còn sống”.**
