# Câu 1 — Vì sao pagination bằng `OFFSET` càng xuống sâu càng chậm và có thể trả duplicate/missing rows khi dữ liệu đang thay đổi?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** SQL Server/PostgreSQL, execution plan, indexing, ordering, `OFFSET/FETCH` / `LIMIT/OFFSET`, keyset pagination, concurrency, consistency, API pagination, performance diagnostics

## Bối cảnh

Một ASP.NET Core .NET 8 API phục vụ màn hình audit log có khoảng 120 triệu rows. Endpoint hiện hỗ trợ sort mới nhất trước và pagination theo page number:

```sql
SELECT Id, TenantId, CreatedAtUtc, EventType, Summary
FROM AuditLogs
WHERE TenantId = @tenantId
ORDER BY CreatedAtUtc DESC
OFFSET @offset ROWS
FETCH NEXT @pageSize ROWS ONLY;
```

Index hiện tại:

```sql
CREATE INDEX IX_AuditLogs_TenantId_CreatedAtUtc
ON AuditLogs(TenantId, CreatedAtUtc DESC);
```

API dùng `pageSize = 50`. Page 1 trả trong khoảng vài chục ms, nhưng page 2.000 thường mất vài giây. Khi traffic cao và audit events liên tục được insert, frontend đôi lúc thấy cùng một row xuất hiện ở hai page liên tiếp hoặc một số row bị “nhảy qua”.

Một teammate đề xuất:

1. tăng database CPU;
2. thêm Redis cache cho từng page;
3. tăng index coverage bằng cách include mọi column;
4. giữ nguyên page-number API vì frontend đang dùng nó.

Bạn chưa có execution plan thực tế của query chậm và chưa biết user có thật sự cần truy cập page 2.000 bằng số trang hay chỉ cần “Next/Previous”.

## Câu hỏi chính

Hãy giải thích cơ chế bên trong khiến deep pagination bằng `OFFSET` thường tốn chi phí tăng dần, vì sao concurrent inserts có thể làm pagination theo page number bị duplicate/missing rows, và bạn sẽ xác minh điều đó như thế nào trước khi đổi thiết kế. Sau đó đề xuất API/query strategy tốt hơn, nhưng phải nói rõ khi nào `OFFSET` vẫn là lựa chọn hợp lý.

## Câu hỏi làm rõ nên cân nhắc

1. User có thật sự cần nhảy trực tiếp tới page bất kỳ hay chủ yếu browse tuần tự?
2. Ordering hiện tại có deterministic không nếu nhiều rows có cùng `CreatedAtUtc`?
3. Query plan của page sâu đọc/skip bao nhiêu rows và có sort/spill/lookup nào đáng kể không?
4. Audit log có yêu cầu snapshot-consistent pagination hay chấp nhận dữ liệu mới xuất hiện giữa các requests?
5. Có filter bổ sung theo `EventType`, date range hoặc full-text khiến index strategy thay đổi không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng “thêm index”. Hãy hình dung database phải làm gì để trả 50 rows sau khi bỏ qua 99.950 rows.

### Gợi ý 2

Pagination correctness phụ thuộc không chỉ query cost mà còn vào **stable total ordering** và việc dataset có thay đổi giữa hai requests hay không.

### Gợi ý 3

Nếu user chỉ cần Next/Previous, hãy nghĩ tới việc mang sort key của row cuối cùng từ page trước sang request tiếp theo.

## Cấu trúc trả lời đề xuất

1. Làm rõ UX và consistency requirement.
2. Mô tả internal work của deep `OFFSET`.
3. Kiểm tra deterministic ordering.
4. Phân tích concurrent insert/delete/update giữa page requests.
5. Thu execution plan + logical reads + latency theo offset depth.
6. So sánh `OFFSET` với keyset/seek pagination.
7. Thiết kế cursor/API contract.
8. Xem xét index phù hợp với filter + sort.
9. Test correctness/performance dưới concurrent writes.
10. Theo dõi p95/p99, reads và query-plan regressions.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu rằng deep `OFFSET` không làm database “nhảy miễn phí” tới row thứ N; engine vẫn phải tìm/sắp xếp/duyệt đủ rows để bỏ qua phần trước tùy plan.
- Nhận ra `(TenantId, CreatedAtUtc)` chưa tạo total ordering nếu `CreatedAtUtc` trùng nhau.
- Giải thích concurrent inserts có thể làm vị trí tương đối của rows thay đổi giữa page 1 và page 2.
- Đề xuất deterministic tie-breaker như `(CreatedAtUtc DESC, Id DESC)` nếu semantics phù hợp.
- Đề xuất keyset pagination cho browse tuần tự khi scale lớn.
- Yêu cầu execution plan/reads/evidence trước khi “thêm Redis” hay “include mọi cột”.

### Điểm cộng

- Phân biệt index phục vụ filtering/sorting với covering index và chi phí write/storage của INCLUDE quá rộng.
- Nêu rằng keyset pagination đổi UX/API semantics: khó nhảy tới page 2.000 trực tiếp.
- Thiết kế opaque cursor thay vì expose raw database details khi phù hợp.
- Nếu cần snapshot consistency mạnh, thảo luận transaction/snapshot/version token thay vì giả định keyset tự giải quyết mọi concurrent update.

### Senior+

- Nêu rằng cursor nên chứa toàn bộ sort tuple cần cho total ordering, ví dụ `(CreatedAtUtc, Id)`.
- Phân tích trường hợp row update làm sort key thay đổi giữa requests.
- Tách interactive browsing khỏi “export toàn bộ” hoặc reporting workload; không ép một pagination API phục vụ cả hai.
- Đề xuất benchmark ở các depth khác nhau và quan sát logical reads/CPU/temp spill thay vì chỉ đo elapsed time.

## Hướng giải quyết tham khảo

Với `OFFSET 99950 FETCH NEXT 50`, database không thể đơn giản lấy trực tiếp row thứ 99.951 như truy cập phần tử array. Tùy execution plan, engine vẫn phải scan/seek một range đủ lớn, duy trì ordering và bỏ qua phần trước khi trả 50 rows cuối. Vì vậy chi phí thường tăng theo depth dù index hỗ trợ order.

Tôi sẽ chưa kết luận index hiện tại “sai”. Trước hết tôi lấy actual execution plan và đo:

- elapsed time;
- CPU time;
- logical reads;
- rows read vs rows returned;
- sort/spill;
- key lookup;
- index seek/scan shape;
- parameter distribution theo tenant.

Một vấn đề correctness khác là ordering hiện chỉ theo `CreatedAtUtc`. Nếu hai events có cùng timestamp, database không bắt buộc giữ thứ tự ổn định giữa chúng. Tôi sẽ dùng total order, ví dụ:

```sql
ORDER BY CreatedAtUtc DESC, Id DESC
```

và index tương ứng nếu query profile chứng minh cần:

```sql
CREATE INDEX IX_AuditLogs_Tenant_Created_Id
ON AuditLogs(TenantId, CreatedAtUtc DESC, Id DESC);
```

Với page-number pagination, giả sử request page 1 lấy rows theo vị trí 1–50. Trước khi client gọi page 2, có 20 rows mới được insert ở đầu danh sách. `OFFSET 50` của request sau bây giờ tính trên dataset mới, nên một phần rows page 1 cũ có thể lại rơi vào page 2. Delete/update sort key cũng có thể tạo missing rows.

Nếu UX chủ yếu là Next/Previous, tôi ưu tiên keyset pagination. Page đầu:

```sql
SELECT TOP (@pageSize)
    Id, TenantId, CreatedAtUtc, EventType, Summary
FROM AuditLogs
WHERE TenantId = @tenantId
ORDER BY CreatedAtUtc DESC, Id DESC;
```

Page sau dùng last seen tuple:

```sql
SELECT TOP (@pageSize)
    Id, TenantId, CreatedAtUtc, EventType, Summary
FROM AuditLogs
WHERE TenantId = @tenantId
  AND (
        CreatedAtUtc < @lastCreatedAtUtc
        OR (CreatedAtUtc = @lastCreatedAtUtc AND Id < @lastId)
      )
ORDER BY CreatedAtUtc DESC, Id DESC;
```

Với PostgreSQL có thể dùng row-value comparison nếu schema/type phù hợp, nhưng nguyên lý vẫn là seek theo cursor thay vì skip N rows.

Tôi sẽ expose opaque cursor như:

```text
GET /api/audit-logs?limit=50&after=eyJjcmVhdGVkQXQiOi...}
```

Cursor encode/sign các sort values cần thiết; không cần chứa toàn bộ state của database.

`OFFSET` vẫn hợp lý nếu:

- dataset nhỏ;
- depth bị giới hạn;
- user thật sự cần numbered pages;
- performance đã được đo và đạt SLO;
- consistency semantics chấp nhận được.

Tôi không thêm Redis chỉ để che deep pagination cost. Cache page-number trong dataset biến động còn làm invalidation/consistency phức tạp hơn. Tôi cũng không INCLUDE mọi column mặc định vì covering index lớn làm tăng storage, cache footprint và write cost.

Nếu business yêu cầu user có thể “nhảy page 2.000” chính xác trên một snapshot, cần làm rõ đó là interactive browsing hay reporting. Có thể một export/report pipeline hoặc snapshot-based query phù hợp hơn keyset API.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ kiểm tra hai vấn đề riêng: performance và pagination correctness. Với deep OFFSET, database vẫn phải xử lý đủ rows để bỏ qua phần trước, nên page càng sâu logical reads/CPU thường càng tăng. Tôi sẽ xác minh bằng actual execution plan, rows read, logical reads và latency theo depth thay vì chỉ nói thêm index.

Ordering hiện tại cũng chưa deterministic nếu nhiều rows có cùng CreatedAtUtc; tôi sẽ thêm tie-breaker như Id. Dù vậy page-number vẫn có thể duplicate/miss nếu có insert/delete giữa hai requests vì vị trí rows thay đổi.

Nếu UX chủ yếu Next/Previous, tôi sẽ chuyển sang keyset pagination với cursor chứa `(CreatedAtUtc, Id)`, query bằng điều kiện seek và index cùng thứ tự. Trade-off là khó nhảy trực tiếp tới page N. Nếu business thực sự cần numbered pages và dataset/depth nhỏ, OFFSET vẫn có thể đủ tốt. Tôi sẽ không thêm Redis hay covering index cực lớn trước khi có execution-plan evidence và freshness requirement rõ.”

## Câu hỏi đào sâu

1. Nếu user sort theo `Price ASC` và nhiều rows có cùng price, cursor phải chứa gì để pagination ổn định?
2. Nếu requirement bắt buộc nhảy trực tiếp tới page 500, bạn giữ `OFFSET`, precompute anchors hay thiết kế workload khác? Vì sao?
3. Bạn đang khuyến nghị keyset; trong trường hợp nào giải pháp này lại làm UX hoặc implementation tệ hơn `OFFSET`?

## Lỗi trả lời thường gặp

- Chỉ nói “thêm index” mà không xem execution plan.
- Cho rằng keyset pagination tự động tạo snapshot consistency.
- Không thêm deterministic tie-breaker.
- Đề xuất Redis cache page-number mà không bàn invalidation.
- Không hỏi user có thật sự cần random page access hay không.

## Thang điểm 0–10

- **0–2:** Chỉ tăng CPU/index/cache.
- **3–4:** Biết OFFSET chậm nhưng không giải thích cơ chế/correctness.
- **5–6:** Có execution-plan reasoning, stable ordering và keyset pagination.
- **7–8:** Có cursor/API design, index trade-offs, concurrency tests và conditional reasoning.
- **9–10:** Phân biệt interactive browse/reporting/snapshot requirements, đo rows-read/reads/CPU, thiết kế semantics rõ cho concurrent mutation.

# Câu 2 — Sau campaign launch, Akamai trả HTML cũ cho một số users dù origin đã deploy đúng version

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** CDN, Akamai, HTTP caching, `Cache-Control`, cache key, purge/invalidation, ASP.NET Core, deployment, SEO, observability, incident response, failure isolation

## Bối cảnh

Một marketing website ASP.NET Core chạy trên Azure App Service và dùng Akamai CDN phía trước. Site có khoảng vài triệu page views/ngày. Phần lớn HTML anonymous có thể cache ở edge; logged-in pages không được public-cache.

08:00 team deploy campaign mới. Origin health checks pass và khi gọi thẳng origin, HTML mới xuất hiện đúng. Tuy nhiên từ 08:10:

- một số users thấy banner/canonical metadata cũ;
- user khác ở region khác thấy nội dung mới;
- hard refresh không luôn sửa được;
- frontend JS bundle mới đã được deploy với hashed filename;
- HTML response qua CDN đôi lúc có `Age` lớn;
- một số URL có query string tracking như `?utm_source=...`;
- team vừa thay rule tạo `Cache-Control` cho HTML nhưng chưa chắc mọi route đều giống nhau;
- purge request đã được gửi cho một số campaign URLs, nhưng không rõ có cover tất cả cache-key variants không;
- App Service CPU/latency bình thường;
- team đề xuất tắt toàn bộ CDN cache ngay lập tức.

Business impact cao vì campaign copy và canonical metadata phải đồng nhất. Bạn chưa có bằng chứng một Akamai POP cụ thể bị lỗi và chưa biết cache key hiện có vary theo host/query/header nào.

## Câu hỏi chính

Hãy xử lý incident này theo flow **impact → stabilize → evidence → competing hypotheses → verification → remediation → prevention**. Bạn phải phân biệt stale edge object, browser cache, origin response, cache-key fragmentation, purge coverage và application bug. Đề xuất mitigation nhanh nhưng không được mặc định tắt toàn bộ CDN cache nếu chưa cần.

## Câu hỏi làm rõ nên cân nhắc

1. HTML anonymous hiện trả `Cache-Control`, `Surrogate-Control` hoặc equivalent CDN policy nào, TTL bao lâu?
2. Cache key có include full query string, whitelist query params, host, cookies hoặc selected headers không?
3. Stale response xuất hiện ở cùng URL qua nhiều regions hay chỉ một số POP/paths?
4. Purge dùng URL purge hay cache-tag/key invalidation, và deployment có biết chính xác object variants cần invalidation không?
5. Logged-in traffic có bypass/shared-cache rules đúng không, hay cookie/header handling có nguy cơ cache personalized content?

## Gợi ý tư duy

### Gợi ý 1

Trước khi sửa, chứng minh response stale đến từ **browser**, **edge**, hay **origin** bằng headers, request path và direct-origin comparison.

### Gợi ý 2

Một “URL” ở business layer có thể tương ứng nhiều cache objects nếu cache key vary theo query/host/header.

### Gợi ý 3

Purge chỉ hiệu quả nếu bạn invalidate đúng object namespace. Thiết kế cache tốt phải khiến invalidation có thể dự đoán được.

## Cấu trúc trả lời đề xuất

1. Xác định affected pages/regions/users và business risk.
2. Stabilize campaign correctness với targeted bypass/purge nếu cần.
3. So sánh origin vs CDN response.
4. Thu cache headers/key dimensions/POS evidence.
5. Xây competing hypotheses.
6. Verify purge coverage và rule changes.
7. Sửa cache policy/key/invalidation.
8. Kiểm tra personalized/private routes.
9. Test deployment + purge end-to-end.
10. Thêm synthetic probes/alerts cho content freshness.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận “Akamai lỗi” chỉ vì origin đúng.
- Dùng evidence như `Age`, cache status headers, response version marker, origin direct response.
- Kiểm tra cache key/query-string variants.
- Kiểm tra purge có cover đúng variants/object namespace không.
- Phân biệt browser cache với CDN edge cache.
- Có mitigation targeted trước khi tắt toàn bộ CDN.
- Kiểm tra private/personalized content không bị public cache.

### Điểm cộng

- Gắn deployment/content version header an toàn để so edge/origin.
- Chuẩn hóa tracking query params không ảnh hưởng representation để giảm cache fragmentation nếu CDN policy hỗ trợ và requirement cho phép.
- Dùng immutable hashed assets với TTL dài, trong khi HTML có policy khác.
- Thiết kế purge theo content dependency/tag thay vì duy trì danh sách URL thủ công nếu platform/process hỗ trợ.

### Senior+

- Phân biệt freshness SLO của HTML campaign với static assets.
- Xem stale-if-error/stale-while-revalidate như intentional policy cần hiểu, không mặc định coi mọi stale response là bug.
- Có rollback strategy cho CDN rule changes độc lập với application deploy.
- Thiết kế synthetic fetch từ nhiều regions/POP và compare version markers sau release.
- Đánh giá cache poisoning/data leakage risk khi thay đổi key/cookie/header policy.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng business impact: URL nào sai, tỷ lệ traffic, regions, campaign/legal/SEO severity. Nếu metadata hoặc copy sai gây rủi ro cao, tôi có thể targeted-bypass cache cho affected route hoặc purge đúng namespace trước khi hoàn tất RCA. Tắt toàn bộ CDN toàn site là blast radius lớn vì origin có thể không đủ capacity.

Tiếp theo tôi chứng minh từng layer:

```text
Browser
→ Akamai edge
→ origin App Service
→ application/rendering source
```

Với cùng URL tôi thu:

- response body/version marker;
- `Age`;
- `Cache-Control` và CDN-specific cache status headers đang được cấu hình expose;
- `Date`, `ETag` nếu có;
- request host/query/cookies/headers ảnh hưởng key;
- direct-origin response qua đường kiểm soát an toàn.

Competing hypotheses:

1. **Old edge object:** TTL chưa hết hoặc purge miss object.
2. **Cache-key fragmentation:** `?utm_source=x`, host alias hoặc header tạo object khác mà purge chỉ cover canonical URL.
3. **Rule regression:** HTML mới nhận TTL/policy ngoài dự kiến.
4. **Browser cache:** edge đã mới nhưng browser giữ response cũ.
5. **Origin split/version drift:** một số origin instances vẫn chạy release cũ dù kiểm tra một instance thấy đúng.
6. **Application rendering/data source:** origin bản thân trả variant cũ ở một path/locale.
7. **Intentional stale serving:** CDN policy cho phép serve stale trong một failure/revalidation condition.

Tôi sẽ so cùng request qua nhiều regions và direct origin. Nếu stale CDN response có `Age` cao, version cũ và origin trả version mới, edge caching hypothesis mạnh. Sau đó inspect cache key: query tracking có được ignore/normalize hay mỗi query tạo object riêng? Nếu purge chỉ URL canonical nhưng cache key chứa query, variants có thể còn sống.

Mitigation ưu tiên theo blast radius:

- purge/tag invalidation cho affected content;
- temporary cache bypass/TTL reduction chỉ route campaign;
- rollback CDN rule change nếu regression rõ;
- origin traffic protection nếu phải bypass nhiều hơn dự kiến.

Tôi không dùng một policy cho mọi resource. Static assets hashed như:

```text
/app.8f3c1a.js
```

có thể immutable + TTL dài. HTML thường cần freshness/purge semantics khác. Personalized responses cần `private`/`no-store` hoặc bypass shared cache theo design; không được vô tình public-cache theo cookie/header thiếu trong key.

Về prevention:

- deployment tạo release/content version marker;
- automated post-deploy synthetic fetch qua CDN ở nhiều locations;
- verify `Age`/cache status/version;
- invalidate bằng predictable tags/keys nếu workflow hỗ trợ;
- test query-param normalization;
- config-as-code/review cho CDN rules;
- alert nếu edge content version không khớp expected version quá freshness SLO.

Nếu origin đã đúng nhưng CDN vẫn serve stale, tôi vẫn không mặc định “purge mọi thứ”. Tôi cần biết object key và invalidation semantics để tránh incident lặp lại.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách browser, CDN và origin trước. Với cùng URL tôi so version marker, Age, Cache-Control/cache-status headers và direct-origin response. Vì chỉ một số regions/users stale, tôi sẽ kiểm tra cache-key variants theo query/host/header và purge coverage; UTM query có thể làm một business URL thành nhiều edge objects tùy rule.

Nếu impact cao, mitigation nhanh là targeted purge hoặc temporary bypass riêng campaign route, không tắt CDN toàn site vì có thể dồn traffic về origin. Sau đó tôi kiểm tra rule change gần release, TTL, stale policy, query normalization và origin version drift.

Dài hạn tôi tách policy HTML với immutable hashed assets, đảm bảo personalized pages không shared-cache, dùng predictable invalidation/tagging nếu có, và thêm synthetic probes nhiều regions sau deploy. Tôi cần evidence chứng minh edge stale trước khi gọi đây là Akamai outage.”

## Câu hỏi đào sâu

1. Nếu bỏ UTM params khỏi cache key, rủi ro correctness/security nào bạn phải kiểm tra trước?
2. Nếu origin không chịu được full traffic khi bypass CDN, bạn stabilize incident thế nào?
3. Bạn đề xuất purge theo cache tag; khi nào URL purge đơn giản lại tốt hơn và ít complexity hơn?

## Lỗi trả lời thường gặp

- Tắt toàn bộ CDN ngay mà không đánh giá origin capacity.
- Chỉ purge một URL mà không hiểu cache-key variants.
- Không phân biệt browser cache với edge cache.
- Dùng TTL dài cho HTML vì static assets cũng TTL dài.
- Không kiểm tra personalized routes/public-cache risk.

## Thang điểm 0–10

- **0–2:** Chỉ purge/tắt CDN/restart origin.
- **3–4:** Biết xem cache headers nhưng không có hypothesis structure.
- **5–6:** Phân biệt edge/browser/origin, kiểm tra key và purge coverage.
- **7–8:** Có targeted mitigation, rule rollback, synthetic checks và security review.
- **9–10:** Thiết kế freshness SLO, predictable invalidation, capacity-aware mitigation, region/version observability và cache-policy governance.

# Câu 3 — Hệ thống approval workflow nên bắt đầu bằng Modular Monolith hay tách Microservices ngay từ Release 1?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** architecture boundaries, Modular Monolith, Microservices, DDD concepts, transaction boundaries, REST APIs, asynchronous processing, SQL Server, reliability, observability, deployment, cost of complexity

## Bối cảnh

Một công ty muốn xây approval platform nội bộ cho khoảng 8.000 employees. Release 1 gồm:

- leave requests;
- expense approvals;
- document approval;
- multi-step approver chains;
- reminder/escalation jobs;
- audit history;
- email/in-app notifications;
- role/policy-based permissions;
- REST API cho web frontend;
- dự kiến khoảng vài chục requests/second ở peak, không phải hàng chục nghìn;
- một engineering team 7 người;
- yêu cầu ship Release 1 trong 5 tháng;
- hiện chưa có platform team riêng cho Kubernetes/service mesh/distributed tracing;
- business nói có thể sau này tích hợp HR, Finance ERP và mobile app.

Hai proposals:

**Proposal A — Microservices ngay:**

- Request Service;
- Approval Service;
- Notification Service;
- Audit Service;
- Identity Integration Service;
- mỗi service database riêng;
- giao tiếp qua REST + messaging.

Lý do: “sau này scale dễ hơn” và “microservices là kiến trúc enterprise”.

**Proposal B — Modular Monolith:**

- một deployable ASP.NET Core;
- modules có boundaries rõ;
- một SQL Server instance, nhưng ownership/schema/table boundaries được kiểm soát;
- background processing/notification abstractions nằm sau interfaces;
- chỉ tách service khi có evidence về scale, ownership hoặc release independence.

Chưa có bằng chứng module nào cần scale độc lập. Tuy nhiên audit history và notifications có failure/retention characteristics khác transactional approval path.

## Câu hỏi chính

Bạn sẽ chọn architecture khởi đầu nào và vì sao? Hãy làm rõ requirements, module boundaries, transaction ownership, sync/async interaction, database design, audit, notification failure handling, security, observability, deployment và migration path nếu sau này cần tách services. Phải so sánh nhiều phương án hợp lý và tính **cost of complexity**.

## Câu hỏi làm rõ nên cân nhắc

1. Các approval modules có cần transaction atomic xuyên domain nào, ví dụ request state + audit record?
2. Notification failure có được phép làm approval transaction fail không?
3. Team có nhu cầu deploy/scale độc lập thật sự giữa modules hay chỉ là giả định tương lai?
4. Integrations HR/ERP có synchronous SLO nào hay chấp nhận async/eventual consistency?
5. Audit history có compliance/immutability/retention requirement nào vượt khả năng schema thông thường không?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn architecture từ số lượng danh từ trong domain. Hãy chọn từ **boundaries, ownership, failure modes và operational capability**.

### Gợi ý 2

Một deployable không đồng nghĩa code phải coupling chặt. Modular Monolith vẫn có thể enforce module boundaries nghiêm túc.

### Gợi ý 3

Tìm những interaction nào cần transaction mạnh và interaction nào nên tách bằng asynchronous handoff.

## Cấu trúc trả lời đề xuất

1. Làm rõ scale/SLO/team/deadline.
2. Xác định domain/module boundaries.
3. Xác định transactional invariants.
4. Tách core approval path và side effects.
5. So sánh Modular Monolith/Microservices.
6. Chọn data ownership strategy.
7. Thiết kế notifications/audit/integrations.
8. Thiết kế security/observability/deployment.
9. Nêu extraction seams nếu tương lai tách service.
10. Đặt measurable triggers để revisit architecture.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chọn Microservices chỉ vì “enterprise/scalable”.
- Cân nhắc team size 7 người và deadline 5 tháng.
- Định nghĩa module boundaries/ownership dù dùng monolith.
- Tách notification failure khỏi core approval transaction nếu business semantics cho phép.
- Audit record quan trọng phải gắn với state transition theo transaction semantics phù hợp.
- Có migration/extraction path nếu sau này cần service độc lập.
- Có observability ngay cả khi chỉ một deployable.

### Điểm cộng

- Một SQL Server instance không đồng nghĩa modules được phép join/write tùy tiện qua nhau.
- Dùng internal contracts/application events để giảm coupling giữa modules.
- Nếu notification cần reliable async handoff, có thể dùng transactional outbox trong cùng database trước khi cân nhắc external broker.
- External integrations được bao quanh bởi adapter/anti-corruption boundary.
- Kiểm thử architecture boundaries bằng project references/module tests/static analysis.

### Senior+

- Đặt explicit extraction triggers: independent scale, separate team ownership, release cadence conflict, fault isolation requirement hoặc regulatory boundary.
- Nhận ra premature database-per-service tạo distributed consistency/migration/reporting complexity.
- Phân biệt domain event nội bộ với integration event bên ngoài.
- Nêu cách giữ schemas/contracts backward-compatible để extraction từng module không thành rewrite lần hai.
- Không mặc định cần Kubernetes; deployment platform nên theo operational needs.

## Hướng giải quyết tham khảo

Với dữ liệu hiện có, tôi nghiêng về **Modular Monolith** cho Release 1 vì peak chỉ vài chục requests/second, team 7 người, deadline 5 tháng và chưa có nhu cầu scale/deploy ownership độc lập rõ. Đây không phải vì microservices “xấu”, mà vì distributed-system tax hiện chưa được business justification.

Tôi sẽ chia logical modules như:

```text
Requests
Approvals
Audit
Notifications
Identity/Policy Integration
External Integrations
```

Nhưng boundaries phải enforce:

- module sở hữu table/schema/repository của mình;
- module khác không write trực tiếp;
- giao tiếp qua application contracts hoặc domain/application events;
- dependency direction rõ;
- tránh shared “God services” và shared mutable domain models.

Core state transition ví dụ:

```text
Pending → Approved
```

có thể cần transaction cùng audit entry nếu audit là invariant: không được có approval state thay đổi mà thiếu audit record. Trong cùng database, transaction local đơn giản và đáng tin cậy hơn distributed transaction.

Notification lại thường là side effect không nên làm approval fail nếu email provider down. Một flow hợp lý:

```text
SQL transaction:
  update Approval
  insert AuditEntry
  insert OutboxMessage(NotificationRequested)
commit

background dispatcher:
  read outbox
  send notification
  retry/idempotency
  mark delivered/failed
```

Outbox không bắt buộc nếu business cho phép notification best-effort, nhưng nếu requirement nói notification phải không mất thì nó là lựa chọn hợp lý mà chưa cần tách thành microservice.

Audit module có thể cần append-oriented design/retention/index strategy riêng, nhưng vẫn có thể cùng SQL Server trong R1. Nếu compliance yêu cầu immutable/WORM storage hoặc retention đặc biệt, recommendation có thể thay đổi.

External HR/ERP integrations được đặt sau adapters. Nếu ERP chậm, core approval path không nên bị kéo dài nếu requirement cho phép async synchronization. Nếu một decision bắt buộc real-time validation từ HR, đó lại là hard dependency cần timeout/degraded behavior riêng.

Tôi sẽ instrument:

- request/approval latency;
- transition failures;
- outbox backlog;
- notification delivery latency/failure;
- audit write failures;
- integration dependency p95/p99;
- correlation ID xuyên modules.

Deployment ban đầu có thể là một ASP.NET Core app + background worker trong cùng solution/deployable hoặc tách worker process nếu operationally có lợi. Tôi không mặc định Kubernetes nếu App Service/VM/container hosting đơn giản hơn đã đáp ứng SLO.

Khi nào tách service?

- Notifications cần scale/rate-limit/failure isolation rất khác;
- một module có team ownership riêng;
- release cadence xung đột;
- một integration gây blast radius cần cô lập;
- regulatory/data-boundary requirement;
- measured load yêu cầu independent scaling.

Nếu boundaries đã đúng từ đầu, extraction là chuyển internal contract thành network/integration contract dần dần, không phải rewrite toàn hệ thống.

Microservices ngay từ R1 vẫn có thể hợp lý nếu organization đã có platform mature, teams sở hữu services độc lập, hoặc requirements thật sự cần isolation/scale riêng. Nhưng scenario hiện chưa cho evidence đó.

## Mẫu trả lời trong phỏng vấn

“Với team 7 người, deadline 5 tháng và chỉ vài chục requests/second, tôi sẽ bắt đầu bằng Modular Monolith nhưng enforce module boundaries nghiêm túc. Lý do là hiện chưa có requirement scale/deploy độc lập để bù distributed-system cost như network failure, tracing, schema evolution và eventual consistency.

Tôi sẽ giữ approval transition + audit invariant trong local SQL transaction nếu audit bắt buộc. Notification thì tách khỏi transaction qua outbox/background dispatcher nếu requirement cần reliable delivery, vì email failure không nên rollback approval.

Modules không được write trực tiếp table của nhau; giao tiếp qua contracts/events để tạo extraction seams. Tôi sẽ instrument backlog, dependency latency, failure rates ngay từ đầu.

Tôi chỉ tách service khi có evidence: independent scaling, separate team ownership, fault-isolation requirement, release cadence conflict hoặc regulatory boundary. Nếu sau này notifications thực sự cần scale độc lập, boundary đã rõ sẽ giúp extract mà không rewrite core. Nếu organization đã có platform microservices mature hoặc có hard isolation requirement ngay từ đầu thì recommendation có thể đổi.”

## Câu hỏi đào sâu

1. Nếu Audit phải tuyệt đối không mất nhưng write audit làm approval latency tăng mạnh, bạn thiết kế thế nào?
2. Nếu bạn dùng một SQL database cho Modular Monolith, làm sao ngăn developer tạo cross-module joins/coupling ngày càng nặng?
3. Bạn đang chọn monolith; nếu Notification outage làm process memory/threads tăng và ảnh hưởng Approval API, recommendation của bạn thay đổi ra sao?

## Lỗi trả lời thường gặp

- Chọn Microservices vì “scale” dù chưa có scale requirement.
- Gọi Modular Monolith nhưng modules vẫn dùng chung repository/entities tùy tiện.
- Gửi email đồng bộ trong approval transaction.
- Không có extraction triggers/measurable revisit conditions.
- Mặc định Kubernetes/message broker/CQRS dù chưa cần.

## Thang điểm 0–10

- **0–2:** Chọn architecture theo trend.
- **3–4:** Nêu pros/cons chung nhưng không có transaction/failure reasoning.
- **5–6:** Có module boundaries, local transaction, async notification và observability.
- **7–8:** Có outbox khi justified, extraction seams, integration boundaries và deployment trade-offs.
- **9–10:** Đặt evidence-based extraction triggers, phân biệt invariants/side effects, tính organizational/operational cost và giữ migration reversible.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Deep `OFFSET` pagination có cả vấn đề performance lẫn correctness khi dataset thay đổi.
- Stable pagination cần deterministic total ordering; keyset pagination phù hợp khi browse tuần tự ở scale lớn.
- CDN incident phải được phân tách browser → edge → origin bằng evidence thay vì purge/tắt cache theo phản xạ.
- Cache key và invalidation semantics quyết định khả năng xử lý stale content.
- Modular Monolith có thể là lựa chọn production-grade khi boundaries rõ và distributed-system complexity chưa được justification.
- Core transactional invariants và asynchronous side effects nên được thiết kế theo failure semantics khác nhau.

## Mẫu tư duy cần nhớ

- Measure before optimizing.
- Separate correctness problems from performance problems.
- Localize failure by layer before choosing remediation.
- Choose architecture from requirements and operational capability, not trends.
- Keep future extraction reversible by enforcing ownership boundaries today.
