# Code Review Challenge 1 — Giới hạn concurrency gọi API ngoài bằng `SemaphoreSlim` nhưng vẫn vượt rate limit và treo request

**Chủ đề:** Concurrency, async/await, cancellation, HTTP client usage, failure handling, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core service đồng bộ trạng thái lịch họp sang một external calendar provider. Provider giới hạn số request đồng thời và trả `429` khi tải tăng cao. Team thêm `SemaphoreSlim` để giới hạn tối đa 10 request đồng thời.

API chạy trên 6 instance sau load balancer. Bình thường có 20–40 request/giây, nhưng vào đầu giờ làm việc có burst 300–500 request/giây. Production ghi nhận:

- external provider vẫn thường xuyên trả `429`,
- một số request chờ rất lâu dù downstream đã phục hồi,
- số permit khả dụng đôi lúc giảm dần theo thời gian,
- client đã ngắt kết nối nhưng server vẫn tiếp tục chờ hoặc gọi downstream,
- khi provider timeout, throughput của toàn service giảm mạnh,
- mỗi instance log “max concurrency = 10” nhưng tổng số request đồng thời từ hệ thống vẫn cao hơn nhiều.

Business yêu cầu API không được tạo overload cho downstream, cần có backpressure rõ ràng, timeout/cancellation hợp lý và không được làm request treo vô hạn.

## Đoạn code cần review

```csharp
public sealed class CalendarSyncService
{
    private static readonly SemaphoreSlim Gate = new(10, 10);

    private readonly HttpClient _httpClient;
    private readonly ILogger<CalendarSyncService> _logger;

    public CalendarSyncService(
        HttpClient httpClient,
        ILogger<CalendarSyncService> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task SyncAsync(
        Guid eventId,
        CalendarUpdate update,
        CancellationToken cancellationToken)
    {
        await Gate.WaitAsync();

        var response = await _httpClient.PostAsJsonAsync(
            $"/api/events/{eventId}/sync",
            update);

        if ((int)response.StatusCode == 429)
        {
            await Task.Delay(TimeSpan.FromSeconds(2));

            response = await _httpClient.PostAsJsonAsync(
                $"/api/events/{eventId}/sync",
                update);
        }

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogError(
                "Calendar sync failed for {EventId}. Status={Status}",
                eventId,
                response.StatusCode);

            throw new InvalidOperationException("Calendar sync failed");
        }

        Gate.Release();
    }
}
```

## Kết quả code review tham khảo

### 1. Permit bị leak khi exception xảy ra

**Problem:** `Gate.Release()` chỉ chạy ở happy path cuối method.  
**Why it happens:** Không có `try/finally` bao quanh vùng đã acquire semaphore.  
**Production impact:** Mỗi exception có thể làm mất một permit. Sau đủ số lỗi, mọi request mới có thể chờ vô hạn dù downstream đã khỏe lại.  
**Severity:** Critical  
**Recommended fix:** Sau khi acquire thành công, luôn release trong `finally`.

### 2. Chờ semaphore không hỗ trợ request cancellation

**Problem:** `Gate.WaitAsync()` không nhận `cancellationToken`.  
**Why it happens:** Overload không có token được dùng.  
**Production impact:** Client disconnect hoặc request timeout nhưng work vẫn nằm trong queue chờ permit.  
**Severity:** High  
**Recommended fix:** Dùng `await Gate.WaitAsync(cancellationToken)` hoặc một bounded work queue có cancellation rõ ràng.

### 3. HTTP calls không truyền `CancellationToken`

**Problem:** Cả hai lần `PostAsJsonAsync` đều không nhận token.  
**Why it happens:** Request lifecycle không được propagate tới downstream I/O.  
**Production impact:** Request bị huỷ nhưng downstream call vẫn chạy, tiêu tốn socket và concurrency slot.  
**Severity:** High  
**Recommended fix:** Truyền `cancellationToken` cho HTTP call; cân nhắc linked timeout token nếu cần giới hạn ngắn hơn request tổng.

### 4. Giới hạn concurrency chỉ có hiệu lực trong từng process

**Problem:** `static SemaphoreSlim` không tạo giới hạn toàn cluster.  
**Why it happens:** Mỗi instance có process memory riêng.  
**Production impact:** 6 instance x 10 permit có thể tạo tối đa khoảng 60 request đồng thời, chưa kể retry, nên downstream vẫn bị overload.  
**Severity:** High  
**Recommended fix:** Làm rõ yêu cầu. Nếu provider cần global rate/concurrency limit, dùng coordination tập trung hoặc queue/worker model có số consumer được kiểm soát. Nếu local limit đủ, sizing phải tính theo số instance.

### 5. Retry cố định cho `429` dễ tạo synchronized retry wave

**Problem:** Mọi request chờ đúng 2 giây rồi retry.  
**Why it happens:** Không có jitter/backoff và không đọc tín hiệu retry của downstream.  
**Production impact:** Hàng trăm request có thể retry cùng lúc, tạo burst mới và tiếp tục nhận `429`.  
**Severity:** High  
**Recommended fix:** Dùng retry policy có giới hạn, exponential backoff + jitter, tôn trọng `Retry-After` nếu provider hỗ trợ, và đặt retry budget.

### 6. Retry side effect nhưng không làm rõ idempotency

**Problem:** `POST` được gọi lại sau `429`/failure mà không có idempotency semantics.  
**Why it happens:** Retry được thêm ở transport layer nhưng không xem xét business side effect.  
**Production impact:** Nếu downstream đã xử lý request đầu nhưng response bị mất, lần retry có thể áp dụng thay đổi hai lần tùy API semantics.  
**Severity:** High  
**Recommended fix:** Dùng idempotency key/operation id nếu downstream hỗ trợ, hoặc thiết kế endpoint/state update có semantics retry-safe.

### 7. `HttpResponseMessage` không được dispose rõ ràng

**Problem:** Response object không được dispose, và response đầu tiên bị ghi đè khi retry.  
**Why it happens:** Lifetime của response bị bỏ qua.  
**Production impact:** Có thể giữ resource/network response lâu hơn cần thiết, đặc biệt dưới tải cao.  
**Severity:** Medium  
**Recommended fix:** Dùng `using`/`using var` cho từng response hoặc wrapper method xử lý response đầy đủ.

### 8. Không có timeout/policy phân biệt lỗi transient và permanent

**Problem:** Mọi lỗi non-2xx đều dẫn đến cùng một exception generic.  
**Why it happens:** Failure policy chưa phân loại status code hoặc exception.  
**Production impact:** Có thể retry sai loại lỗi, khó điều tra, và giữ concurrency slot lâu khi downstream treo.  
**Severity:** Medium  
**Recommended fix:** Xác định timeout hợp lý, phân loại `429`, 5xx, network timeout và 4xx permanent; retry chỉ khi phù hợp.

### 9. Backpressure chưa rõ ràng

**Problem:** Tất cả request đều có thể xếp hàng chờ semaphore.  
**Why it happens:** Không giới hạn queue length hoặc wait duration.  
**Production impact:** Khi burst traffic lớn, latency tăng không giới hạn và memory/request backlog tăng.  
**Severity:** Medium  
**Recommended fix:** Dùng bounded queue hoặc reject/return trạng thái phù hợp khi capacity đã đầy; đặt SLA cho thời gian chờ.

### 10. Observability thiếu thông tin về queue/concurrency/downstream

**Problem:** Chỉ log lỗi cuối cùng.  
**Why it happens:** Không đo thời gian chờ semaphore, active permits, retry count hay downstream latency.  
**Production impact:** Khó xác định bottleneck nằm ở local queue hay provider.  
**Severity:** Medium  
**Recommended fix:** Thêm metrics cho active requests, queue wait, retries, `429`, dependency latency, timeout và cancellation.

## Phiên bản code đề xuất

```csharp
public sealed class CalendarSyncService
{
    private static readonly SemaphoreSlim Gate = new(10, 10);

    private readonly HttpClient _httpClient;
    private readonly ILogger<CalendarSyncService> _logger;

    public CalendarSyncService(
        HttpClient httpClient,
        ILogger<CalendarSyncService> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task SyncAsync(
        Guid eventId,
        CalendarUpdate update,
        CancellationToken cancellationToken)
    {
        var acquired = false;

        try
        {
            await Gate.WaitAsync(cancellationToken);
            acquired = true;

            const int maxAttempts = 3;

            for (var attempt = 1; attempt <= maxAttempts; attempt++)
            {
                using var response = await _httpClient.PostAsJsonAsync(
                    $"/api/events/{eventId}/sync",
                    update,
                    cancellationToken);

                if (response.IsSuccessStatusCode)
                    return;

                if ((int)response.StatusCode != 429 &&
                    (int)response.StatusCode < 500)
                {
                    throw new InvalidOperationException(
                        $"Calendar sync failed with status {(int)response.StatusCode}.");
                }

                if (attempt == maxAttempts)
                {
                    throw new InvalidOperationException(
                        $"Calendar sync failed after {maxAttempts} attempts.");
                }

                var delay = TimeSpan.FromMilliseconds(
                    250 * Math.Pow(2, attempt - 1) +
                    Random.Shared.Next(50, 250));

                await Task.Delay(delay, cancellationToken);
            }
        }
        finally
        {
            if (acquired)
                Gate.Release();
        }
    }
}
```

Đây chỉ là bản sửa tối thiểu ở application layer. Nếu provider yêu cầu rate limit toàn cluster hoặc traffic burst lớn, kiến trúc queue + bounded consumers thường dễ kiểm soát hơn so với để request HTTP trực tiếp xếp hàng sau semaphore trên từng instance.

## Trade-offs

- Local semaphore đơn giản, latency thấp nhưng không kiểm soát cluster-wide concurrency.
- Distributed limiter/central queue kiểm soát tốt hơn nhưng thêm dependency và complexity.
- Retry giúp chịu lỗi transient nhưng làm tăng load downstream nếu không có budget/backoff.
- Fail-fast khi queue đầy bảo vệ hệ thống nhưng caller phải biết retry ở cấp workflow.
- Giảm concurrency bảo vệ downstream nhưng có thể tăng latency tổng.

## Cách kiểm thử

1. **Concurrency test:** bắn 200 request đồng thời trên một instance, xác nhận active downstream calls không vượt local limit.
2. **Multi-instance test:** chạy 3–6 instance và chứng minh local semaphore không phải global limiter.
3. **Failure-path test:** cho HTTP call ném exception liên tục; xác nhận permit không bị leak và service hồi phục sau lỗi.
4. **Cancellation test:** huỷ request khi đang chờ semaphore và khi đang gọi downstream; xác nhận work dừng đúng chỗ.
5. **Load/retry test:** giả lập `429`/5xx theo burst, đo retry wave, queue wait và throughput.

## Quan sát trong production

Nên theo dõi:

- active downstream requests
- semaphore queue wait duration
- request queue depth nếu có bounded queue
- dependency latency p50/p95/p99
- `429`, 5xx, timeout, cancellation counts
- retry attempts per operation
- success rate sau retry
- số request chờ vượt SLA
- correlation id / event id / dependency attempt trong trace

# Code Review Challenge 2 — Permission cache làm người dùng vẫn truy cập được sau khi quyền đã bị thu hồi

## Bối cảnh

Một ASP.NET Core API dùng database làm nguồn sự thật cho quyền truy cập theo tenant. Để giảm query DB, team cache danh sách permission của mỗi user trong `IMemoryCache` trong 30 phút.

Hệ thống chạy trên 5 instance. Admin có thể thu hồi role của user bất kỳ lúc nào. Production ghi nhận:

- sau khi admin revoke quyền, user đôi khi vẫn truy cập endpoint nhạy cảm thêm 10–30 phút,
- behavior không nhất quán: request này bị `403`, request khác lại thành công,
- khi deploy/restart, vấn đề tạm biến mất,
- một số user chuyển tenant nhưng vẫn thấy permission cũ trong một khoảng thời gian,
- cache hit rate cao nên team cho rằng cơ chế đang “hoạt động tốt”.

Business yêu cầu revoke quyền nhạy cảm phải có hiệu lực trong vòng dưới một phút. Quyền phải luôn được đánh giá theo đúng tenant hiện tại.

## Đoạn code cần review

```csharp
public sealed class PermissionService
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;

    public PermissionService(
        IMemoryCache cache,
        AppDbContext db)
    {
        _cache = cache;
        _db = db;
    }

    public async Task<bool> HasPermissionAsync(
        Guid userId,
        Guid tenantId,
        string permission,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"permissions:{userId}";

        if (!_cache.TryGetValue(
                cacheKey,
                out HashSet<string>? permissions))
        {
            permissions = await _db.UserRoles
                .Where(x => x.UserId == userId)
                .SelectMany(x => x.Role.Permissions)
                .Select(x => x.Name)
                .ToHashSetAsync(cancellationToken);

            _cache.Set(
                cacheKey,
                permissions,
                TimeSpan.FromMinutes(30));
        }

        return permissions.Contains(permission);
    }
}
```

## Kết quả code review tham khảo

### 1. Cache key không chứa `tenantId`

**Problem:** Permission của user được cache chỉ theo `userId`.  
**Why it happens:** Tenant boundary bị bỏ khỏi identity của cache entry.  
**Production impact:** Permission của tenant A có thể được tái sử dụng khi cùng user truy cập tenant B. Đây là lỗi authorization nghiêm trọng.  
**Severity:** Critical  
**Recommended fix:** Cache key phải chứa tenant, ví dụ `permissions:{tenantId}:{userId}`; tốt hơn nữa là model authorization luôn truyền tenant context bắt buộc.

### 2. Database query cũng không filter theo tenant

**Problem:** Query lấy mọi role của user mà không lọc `tenantId`.  
**Why it happens:** Service nhận tenant nhưng không enforce boundary ở persistence layer.  
**Production impact:** User có thể được cấp quyền dựa trên role thuộc tenant khác ngay cả khi cache tắt.  
**Severity:** Critical  
**Recommended fix:** Query bắt buộc filter theo cả `UserId` và `TenantId`; tenant isolation nên được bảo vệ ở nhiều lớp nếu hệ thống multi-tenant nhạy cảm.

### 3. TTL 30 phút vi phạm yêu cầu revoke dưới một phút

**Problem:** Cache có thể stale tối đa 30 phút.  
**Why it happens:** TTL được chọn theo performance thay vì security SLA.  
**Production impact:** Quyền đã revoke vẫn tiếp tục có hiệu lực lâu hơn business cho phép.  
**Severity:** High  
**Recommended fix:** Dùng TTL phù hợp SLA hoặc event/version-based invalidation; với permission nhạy cảm có thể bypass cache hoặc yêu cầu freshness cao hơn.

### 4. `IMemoryCache` tạo state riêng trên từng instance

**Problem:** Mỗi instance có cache riêng.  
**Why it happens:** In-memory cache không đồng bộ giữa process.  
**Production impact:** User có thể nhận `403` trên instance đã refresh và `200` trên instance còn stale.  
**Severity:** High  
**Recommended fix:** Dùng distributed cache có version/invalidation hoặc broadcast invalidation tới mọi instance; không phụ thuộc cache local độc lập cho security state có SLA chặt.

### 5. Không có invalidation khi role/permission thay đổi

**Problem:** Cache chỉ hết hạn theo thời gian.  
**Why it happens:** Write path và cache lifecycle không liên kết.  
**Production impact:** Revoke, role update hoặc tenant membership change không phản ánh sớm.  
**Severity:** High  
**Recommended fix:** Khi thay đổi authorization state, tăng permission version hoặc phát invalidation event; read path kiểm tra version/freshness.

### 6. Permission cache mutable có thể bị sửa ngoài ý muốn

**Problem:** Cache lưu `HashSet<string>` mutable.  
**Why it happens:** Object cached được trả và dùng trực tiếp.  
**Production impact:** Nếu code khác giữ reference và sửa set, authorization behavior có thể thay đổi ngoài dự kiến trong cùng process.  
**Severity:** Medium  
**Recommended fix:** Cache immutable/read-only representation hoặc không expose mutable object ra ngoài service.

### 7. Không có protection chống cache stampede sau invalidation

**Problem:** Khi nhiều request miss cùng lúc, tất cả có thể query DB.  
**Why it happens:** Không có per-key single-flight hoặc jitter.  
**Production impact:** Sau deploy/invalidation lớn, DB load tăng đột biến.  
**Severity:** Medium  
**Recommended fix:** Với traffic cao, dùng per-key coalescing/single-flight hoặc distributed cache phù hợp. Tuy nhiên không đánh đổi correctness để tối ưu performance.

### 8. Không log decision context phục vụ audit

**Problem:** Service không có telemetry về source/version/freshness của permission decision.  
**Why it happens:** Authorization được xem như helper đơn giản.  
**Production impact:** Khi có incident khó chứng minh quyết định dựa trên tenant nào, cache age bao nhiêu và policy version nào.  
**Severity:** Medium  
**Recommended fix:** Trace/log structured các metadata an toàn như tenant id, user id, permission, decision source/cache age/version; tránh log token/secret.

### 9. Cache hit rate cao là metric chưa đủ

**Problem:** Team dùng cache hit rate như chỉ báo success chính.  
**Why it happens:** Performance metric bị nhầm với correctness metric.  
**Production impact:** Cache có thể “rất hiệu quả” trong việc trả dữ liệu sai/stale.  
**Severity:** Low  
**Recommended fix:** Theo dõi stale decision rate, invalidation latency, authorization-deny/allow anomalies và revoke propagation time.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng cache theo tenant-user với TTL ngắn hơn. Trong production có SLA revoke dưới một phút trên nhiều instance, nên nên bổ sung distributed invalidation/versioning thay vì chỉ dựa vào TTL.

```csharp
public sealed class PermissionService
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;

    public PermissionService(
        IMemoryCache cache,
        AppDbContext db)
    {
        _cache = cache;
        _db = db;
    }

    public async Task<bool> HasPermissionAsync(
        Guid userId,
        Guid tenantId,
        string permission,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"permissions:{tenantId}:{userId}";

        if (!_cache.TryGetValue(
                cacheKey,
                out IReadOnlySet<string>? permissions))
        {
            var loaded = await _db.UserRoles
                .AsNoTracking()
                .Where(x =>
                    x.UserId == userId &&
                    x.TenantId == tenantId)
                .SelectMany(x => x.Role.Permissions)
                .Select(x => x.Name)
                .Distinct()
                .ToListAsync(cancellationToken);

            permissions = loaded.ToHashSet(StringComparer.Ordinal);

            _cache.Set(
                cacheKey,
                permissions,
                TimeSpan.FromSeconds(30));
        }

        return permissions.Contains(permission);
    }
}
```

Một thiết kế mạnh hơn cho nhiều instance:

- lưu `PermissionVersion` theo `(TenantId, UserId)` hoặc membership/role version,
- khi role thay đổi: tăng version và phát invalidation event,
- distributed cache key chứa version,
- local cache chỉ là lớp tối ưu ngắn hạn,
- endpoint nhạy cảm có thể yêu cầu revalidation trực tiếp khi policy cần freshness gần real-time.

## Trade-offs

- TTL ngắn tăng freshness nhưng tăng DB/cache load.
- Distributed cache giảm inconsistency giữa instance nhưng vẫn cần invalidation semantics.
- Event-driven invalidation nhanh nhưng phức tạp hơn và phải xử lý event loss/delay.
- Version-based authorization dễ audit hơn nhưng tăng model/state cần quản lý.
- Với endpoint cực nhạy cảm, query source of truth mỗi request có thể đáng giá hơn performance cache.

## Cách kiểm thử

1. **Tenant isolation test:** cùng user có role khác nhau ở hai tenant, xác nhận không reuse permission chéo tenant.
2. **Revoke test:** cache permission, revoke role, xác nhận access bị chặn trong SLA yêu cầu.
3. **Multi-instance test:** warm cache khác nhau trên nhiều instance, thực hiện revoke và kiểm tra propagation.
4. **Cache failure test:** distributed/local cache unavailable, xác nhận fallback không fail-open ngoài ý muốn.
5. **Load test:** invalidation hàng loạt, đo DB load và stampede behavior.

## Quan sát trong production

Nên theo dõi:

- authorization decision allow/deny theo endpoint/permission
- permission cache hit/miss
- cache entry age khi decision xảy ra
- revoke-to-enforcement latency
- invalidation event delay/failure
- permission version mismatch
- cross-tenant anomaly detection
- DB query latency cho authorization reads
- trace correlation giữa admin role change và request authorization sau đó

## Câu hỏi phỏng vấn mở rộng

1. Nếu revoke phải có hiệu lực gần như ngay lập tức, bạn chọn version check hay pub/sub invalidation? Vì sao?
2. Nếu distributed cache bị outage, authorization service nên fail-open hay fail-closed cho endpoint nhạy cảm?
3. Bạn đặt boundary tenant ở controller, service, query filter hay database layer như thế nào để defense-in-depth?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Concurrency limit cục bộ không đồng nghĩa với global rate limit trong hệ thống nhiều instance.
- Acquire/release resource phải có cấu trúc đảm bảo cleanup ngay cả khi exception/cancellation xảy ra.
- Retry phải đi cùng backoff, jitter, timeout và idempotency semantics.
- Security cache cần được thiết kế theo freshness SLA, tenant isolation và invalidation, không chỉ hit rate.
- Authorization state là correctness/security state; stale cache có thể trở thành lỗ hổng chứ không chỉ là vấn đề performance.

## Mẫu tư duy cần nhớ

- Phân biệt local concurrency, global rate limit và queue backpressure.
- Mọi retry đều phải hỏi: thao tác này có retry-safe không?
- Mọi cache key phải chứa đầy đủ identity của dữ liệu được cache.
- Security freshness phải được thiết kế theo SLA revoke cụ thể.
- Observability phải đo correctness/freshness, không chỉ throughput và hit rate.
