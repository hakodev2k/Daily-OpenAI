# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy lặp và ghi trạng thái sai

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để xử lý cấu hình email khi nhân viên nghỉ việc. Job đọc các cấu hình đến hạn, gọi dịch vụ Exchange Online để gỡ forwarding/delegation, sau đó đánh dấu cấu hình đã xử lý.

Ứng dụng chạy **3 instance** phía sau load balancer. Mỗi instance đều có Hangfire Server. Trong giờ cao điểm, Exchange Online đôi khi timeout hoặc trả lỗi tạm thời. Gần đây production xuất hiện các triệu chứng:

- một mailbox bị gọi reset nhiều lần gần như cùng thời điểm;
- có cấu hình trong DB được đánh dấu `Completed` dù thao tác Exchange thất bại;
- một số lần retry tạo nhiều history record giống nhau;
- thời gian chạy job tăng mạnh khi có nhiều mailbox;
- khi deploy/restart, một số thao tác bên ngoài đã thành công nhưng DB vẫn ở trạng thái cũ.

Business yêu cầu không được bỏ sót mailbox, nhưng việc gọi thao tác bên ngoài nhiều lần cũng phải được kiểm soát. Chưa có cam kết rằng mọi lệnh Exchange đều có tính idempotent.

## Đoạn code cần review

```csharp
public sealed class ResetExpiredMailJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeOnlineService _exchange;
    private readonly ILogger<ResetExpiredMailJob> _logger;

    public ResetExpiredMailJob(
        AppDbContext db,
        IExchangeOnlineService exchange,
        ILogger<ResetExpiredMailJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ExecuteAsync()
    {
        var configs = await _db.EmployeeOffboardingMailConfigs
            .Where(x => !x.IsDeleted &&
                        x.Status != "Completed" &&
                        x.EndTime <= DateTime.UtcNow)
            .ToListAsync();

        await Task.WhenAll(configs.Select(ProcessAsync));
    }

    private async Task ProcessAsync(EmployeeOffboardingMailConfig config)
    {
        try
        {
            if (config.EmailAction == "Forward")
            {
                await _exchange.RemoveMailboxForwardingAsync(config.UserEmail);
            }
            else if (config.EmailAction == "Delegate")
            {
                await _exchange.RemoveMailboxDelegationAsync(config.UserEmail);
            }

            config.Status = "Completed";
            config.CompletedAt = DateTime.UtcNow;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Failed to reset mailbox {Email} with config {@Config}",
                config.UserEmail,
                config);

            _db.EmployeeOffboardingMailConfigHistories.Add(
                new EmployeeOffboardingMailConfigHistory
                {
                    EmployeeOffboardingMailConfigId = config.Id,
                    FailedCount = 1,
                    HistoryNote = ex.ToString()
                });
        }
        finally
        {
            await _db.SaveChangesAsync();
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Dùng cùng một `DbContext` trong nhiều operation song song

- **Problem:** `Task.WhenAll(configs.Select(ProcessAsync))` khiến nhiều `ProcessAsync` cùng dùng `_db`.
- **Why it happens:** `DbContext` không được thiết kế để chạy nhiều operation song song trên cùng instance.
- **Production impact:** exception kiểu “A second operation was started...”, state tracking khó dự đoán và batch thất bại dưới tải.
- **Severity:** **Critical**
- **Recommended fix:** xử lý tuần tự trong một scope, hoặc tạo DI scope/`IDbContextFactory` riêng cho mỗi worker; nếu cần parallelism phải giới hạn concurrency và mỗi operation dùng context riêng.

### 2. Không có cơ chế claim/lock atomic cho configuration

- **Problem:** nhiều Hangfire worker/server có thể cùng đọc một row `Status != Completed`.
- **Why it happens:** query chỉ đọc rồi mới xử lý; không có atomic state transition hoặc database concurrency guard.
- **Production impact:** cùng mailbox bị gọi external action nhiều lần, race khi cập nhật status và duplicate history.
- **Severity:** **Critical**
- **Recommended fix:** claim work atomically, ví dụ chuyển `Pending/Retryable -> Processing` bằng conditional update và chỉ worker update thành công mới được xử lý. Có thể dùng optimistic concurrency token hoặc provider-specific locking khi thực sự cần.

### 3. Khoảng trống consistency giữa Exchange và DB

- **Problem:** Exchange có thể thành công nhưng process chết trước khi DB ghi `Completed`.
- **Why it happens:** database transaction không thể bao phủ side effect trên remote Exchange Online.
- **Production impact:** lần chạy sau thực hiện lại side effect; nếu operation không idempotent có thể gây lỗi hoặc thay đổi ngoài ý muốn.
- **Severity:** **Critical**
- **Recommended fix:** thiết kế operation có idempotency/reconciliation. Trước hoặc sau retry có thể đọc trạng thái remote để xác định desired state đã đạt chưa. Lưu attempt/state machine bền vững và coi retry là at-least-once.

### 4. Exception bị nuốt nên Hangfire có thể xem job là thành công

- **Problem:** `catch` ghi history nhưng không throw lại.
- **Why it happens:** exception không thoát khỏi `ExecuteAsync`.
- **Production impact:** `[AutomaticRetry]` không được kích hoạt cho lỗi đã bị nuốt; mailbox có thể nằm chờ đến scheduler tiếp theo thay vì retry như kỳ vọng.
- **Severity:** **High**
- **Recommended fix:** chọn rõ retry model. Nếu retry ở cấp item, persist `RetryableFailed`, `NextAttemptAt`, attempt count rồi enqueue item job. Nếu dựa vào Hangfire retry, phải để exception propagate và bảo đảm job idempotent.

### 5. `SaveChangesAsync` trong `finally`

- **Problem:** mọi đường đi đều save cùng một context, kể cả khi lỗi vừa xảy ra.
- **Why it happens:** persistence và external operation bị trộn trong `finally`.
- **Production impact:** khó reasoning về transaction boundary; một `SaveChanges` có thể ghi state của entity khác đang được context track, đặc biệt khi code chạy song song.
- **Severity:** **High**
- **Recommended fix:** mỗi item có unit of work rõ ràng; save transition cụ thể ở từng bước, không dùng shared context/finally cho batch parallel.

### 6. Không giới hạn concurrency với Exchange Online

- **Problem:** số external calls tăng theo toàn bộ số config đến hạn.
- **Why it happens:** `Task.WhenAll` fan-out không bounded.
- **Production impact:** throttling, timeout, socket/resource pressure và cascading retries.
- **Severity:** **High**
- **Recommended fix:** bounded concurrency (`Parallel.ForEachAsync` với giới hạn phù hợp, channel/worker pool hoặc Hangfire queues). Backoff dựa trên loại lỗi và chính sách API.

### 7. History không biểu diễn đúng số lần thất bại

- **Problem:** mỗi record luôn `FailedCount = 1`.
- **Why it happens:** không có attempt model rõ ràng.
- **Production impact:** telemetry sai, khó xác định mailbox poison/retry nhiều lần.
- **Severity:** **Medium**
- **Recommended fix:** lưu từng `AttemptNumber` hoặc atomic increment trên aggregate; thêm error category, timestamp, correlation ID.

### 8. Logging có nguy cơ lộ dữ liệu không cần thiết

- **Problem:** structured logging toàn bộ `config` và `ex.ToString()` vào DB.
- **Why it happens:** object có thể chứa target email, auto-reply content hoặc dữ liệu cá nhân.
- **Production impact:** tăng phạm vi dữ liệu nhạy cảm trong log/history và chi phí lưu trữ.
- **Severity:** **Medium**
- **Recommended fix:** allow-list field cần thiết; không serialize toàn entity; chuẩn hóa error code/message và retention.

### 9. Không truyền cancellation token

- **Problem:** query, external call và save không nhận cancellation.
- **Why it happens:** method không expose token.
- **Production impact:** shutdown/deploy có thể kéo dài; operation tiếp tục khi worker đang dừng.
- **Severity:** **Medium**
- **Recommended fix:** nhận cancellation token khi execution model hỗ trợ, truyền xuống EF/external dependency và thiết kế recovery cho cancellation giữa các bước.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa **item-level processing + atomic claim + context riêng**. Chi tiết conditional update có thể thay đổi theo database/provider.

```csharp
public sealed class ResetExpiredMailJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IExchangeOnlineService _exchange;
    private readonly ILogger<ResetExpiredMailJob> _logger;

    public ResetExpiredMailJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IExchangeOnlineService exchange,
        ILogger<ResetExpiredMailJob> logger)
    {
        _dbFactory = dbFactory;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 0)]
    public async Task ProcessAsync(long configId, CancellationToken ct)
    {
        var attemptId = Guid.NewGuid();

        await using var claimDb = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await claimDb.EmployeeOffboardingMailConfigs
            .Where(x => x.Id == configId &&
                        (x.Status == "Pending" || x.Status == "RetryableFailed") &&
                        x.EndTime <= DateTime.UtcNow)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.LastAttemptId, attemptId)
                .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

        if (claimed == 0)
            return;

        try
        {
            await using var readDb = await _dbFactory.CreateDbContextAsync(ct);
            var config = await readDb.EmployeeOffboardingMailConfigs
                .AsNoTracking()
                .SingleAsync(x => x.Id == configId, ct);

            switch (config.EmailAction)
            {
                case "Forward":
                    await _exchange.EnsureMailboxForwardingRemovedAsync(
                        config.UserEmail, ct);
                    break;
                case "Delegate":
                    await _exchange.EnsureMailboxDelegationRemovedAsync(
                        config.UserEmail, ct);
                    break;
                default:
                    throw new InvalidOperationException(
                        $"Unsupported action: {config.EmailAction}");
            }

            await using var completeDb = await _dbFactory.CreateDbContextAsync(ct);
            await completeDb.EmployeeOffboardingMailConfigs
                .Where(x => x.Id == configId &&
                            x.Status == "Processing" &&
                            x.LastAttemptId == attemptId)
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, "Completed")
                    .SetProperty(x => x.CompletedAt, DateTime.UtcNow), ct);
        }
        catch (Exception ex) when (!ct.IsCancellationRequested)
        {
            await using var failureDb = await _dbFactory.CreateDbContextAsync(ct);

            await failureDb.EmployeeOffboardingMailConfigs
                .Where(x => x.Id == configId && x.LastAttemptId == attemptId)
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, "RetryableFailed")
                    .SetProperty(x => x.LastErrorCode, ex.GetType().Name), ct);

            _logger.LogError(ex,
                "Mailbox reset attempt {AttemptId} failed for config {ConfigId}",
                attemptId, configId);

            throw;
        }
    }
}
```

Trong production, `EnsureMailbox...RemovedAsync` phải thực sự kiểm tra/đưa remote resource về **desired state**, thay vì chỉ đổi tên method. Với lỗi permanent, state nên là `FailedPermanent` thay vì retry vô hạn. Scheduler/dispatcher nên enqueue từng `configId`, giới hạn concurrency và có stale-processing recovery nếu worker chết sau khi claim.

## Trade-offs

Atomic claim và state machine làm code phức tạp hơn nhưng đổi lại có semantics rõ khi chạy nhiều worker. Database lock dài xuyên qua network call có vẻ đơn giản nhưng thường không nên dùng vì giữ lock trong lúc remote latency không kiểm soát được. Distributed lock có thể giảm duplicate execution nhưng không loại bỏ failure window “remote succeeded, local commit failed”; vì vậy idempotency/reconciliation vẫn cần thiết.

Nếu số lượng mailbox rất nhỏ và job chạy một node duy nhất, xử lý tuần tự có thể đủ. Khi scale nhiều worker hoặc external operation quan trọng, item-level durable state là lựa chọn bền vững hơn.

## Cách kiểm thử

1. **Concurrency test:** 20 worker đồng thời cố claim cùng `configId`; chỉ một worker được phép thực hiện external action.
2. **Failure-path test:** Exchange trả timeout trước khi biết kết quả; retry/reconciliation không tạo trạng thái sai.
3. **Crash-window integration test:** giả lập remote success rồi process chết trước local completion; lần sau phải xác nhận desired remote state và hoàn tất an toàn.
4. **Load test:** hàng nghìn config đến hạn; xác minh bounded concurrency, DB pool và external throttling không bị bão hòa.
5. **Permanent failure test:** mailbox không tồn tại/permission bị từ chối; job chuyển sang trạng thái phù hợp và không retry vô hạn.

## Quan sát trong production

- **Logs:** `ConfigId`, `AttemptId`, action, transition cũ/mới, sanitized error category, duration; không log toàn entity.
- **Metrics:** pending count, processing count, retryable/permanent failures, completion rate, retry count, Exchange latency/throttling rate.
- **Traces:** span DB claim → remote operation → DB completion với correlation ID.
- **Alerts:** backlog age vượt ngưỡng, failure ratio tăng, stale `Processing`, throttling/timeout tăng bất thường.
- **Database observations:** số row ở từng state, oldest pending age, duplicate attempt anomaly và contention quanh claim query.

# Code Review Challenge 2 — API tìm kiếm nhân viên: authorization bị bỏ qua và query có thể kéo cả bảng vào memory

## Bối cảnh

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeesController> _logger;

    public EmployeesController(
        AppDbContext db,
        ILogger<EmployeesController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        string? search,
        string? officeCode,
        bool includeInactive = false)
    {
        _logger.LogInformation(
            "Employee search: {Search}, office={Office}, user={User}",
            search,
            officeCode,
            User.Claims.ToDictionary(x => x.Type, x => x.Value));

        var employees = await _db.Employees
            .Include(x => x.Department)
            .Include(x => x.Office)
            .ToListAsync();

        if (!includeInactive)
            employees = employees.Where(x => x.IsActive).ToList();

        if (!string.IsNullOrWhiteSpace(officeCode))
            employees = employees
                .Where(x => x.Office.Code == officeCode)
                .ToList();

        if (!string.IsNullOrWhiteSpace(search))
        {
            var term = search.Trim().ToLower();
            employees = employees.Where(x =>
                    x.FullName.ToLower().Contains(term) ||
                    x.Email.ToLower().Contains(term) ||
                    x.Mobile.Contains(term))
                .ToList();
        }

        return Ok(employees.Select(x => new
        {
            x.Id,
            x.FullName,
            x.Email,
            x.Mobile,
            Department = x.Department.Name,
            Office = x.Office.Code,
            x.HomeAddress,
            x.PersonalEmail,
            x.Salary
        }));
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object-level authorization

- **Problem:** endpoint chỉ yêu cầu authenticated user; không enforce role hoặc employee scope.
- **Why it happens:** `[Authorize]` không tự áp business authorization như department/office ownership.
- **Production impact:** manager có thể đọc employee ngoài phạm vi được phép; đây là data exposure nghiêm trọng.
- **Severity:** **Critical**
- **Recommended fix:** policy/authorization service xác định scope từ trusted server-side claims/data; filter query bằng allowed employee/department/office trước khi execute.

### 2. Trả dữ liệu nhạy cảm vượt quá nhu cầu search

- **Problem:** response gồm `HomeAddress`, `PersonalEmail`, `Salary`, mobile… dù màn hình search có thể chỉ cần identity/display fields.
- **Why it happens:** DTO không được thiết kế theo least-data principle.
- **Production impact:** tăng blast radius khi authorization bug, browser compromise hoặc log/network leakage.
- **Severity:** **Critical**
- **Recommended fix:** projection sang DTO tối thiểu; endpoint chi tiết riêng với authorization mạnh hơn cho field nhạy cảm.

### 3. Materialize toàn bộ bảng trước khi filter

- **Problem:** `ToListAsync()` chạy trước mọi filter.
- **Why it happens:** các `Where` sau đó là LINQ-to-Objects.
- **Production impact:** tải toàn bộ employee + related entities vào application memory, tăng DB traffic, GC pressure, latency và nguy cơ OOM.
- **Severity:** **High**
- **Recommended fix:** giữ `IQueryable`, áp authorization + business filters + search + pagination trước khi `ToListAsync`.

### 4. Không giới hạn result set/pagination

- **Problem:** request rỗng có thể trả gần toàn bộ employee được query.
- **Why it happens:** không có `Take`, page size hay cursor.
- **Production impact:** response rất lớn, memory/network pressure và endpoint dễ bị abuse.
- **Severity:** **High**
- **Recommended fix:** page size có upper bound; có thể yêu cầu minimum search length tùy UX; deterministic ordering.

### 5. Log toàn bộ claims và raw search term

- **Problem:** log dictionary toàn bộ claims và input có thể chứa PII.
- **Why it happens:** logging phục vụ debug nhưng không có allow-list/redaction.
- **Production impact:** token-related identity/authorization data và PII lan sang logging platform, tăng privacy/security exposure.
- **Severity:** **High**
- **Recommended fix:** chỉ log stable user identifier nếu cần, authorization scope summary, search length/hash nếu có lý do; không log toàn claims/raw PII.

### 6. `includeInactive` do client tự chọn mà không kiểm tra quyền

- **Problem:** mọi authenticated user đều có thể yêu cầu inactive employees.
- **Why it happens:** business capability được biểu diễn bằng query parameter nhưng không có authorization.
- **Production impact:** lộ dữ liệu nhân viên cũ cho role không phù hợp.
- **Severity:** **High**
- **Recommended fix:** kiểm tra policy/capability trước khi cho phép `includeInactive=true`.

### 7. Search expression hiện tại khó tối ưu ở quy mô lớn

- **Problem:** `ToLower().Contains()` trên nhiều field không phải chiến lược search tốt ở dataset lớn; mobile cũng được scan bằng contains.
- **Why it happens:** substring search tùy ý thường khó tận dụng B-tree index thông thường.
- **Production impact:** CPU/I/O database tăng khi chuyển filter xuống SQL nhưng dữ liệu tiếp tục lớn.
- **Severity:** **Medium**
- **Recommended fix:** thiết kế search semantics trước: prefix/exact search cho email/mobile nếu phù hợp; index theo access pattern; full-text/trigram/search engine chỉ khi requirement thực sự cần substring/fuzzy search. Kiểm tra execution plan trên provider thực tế.

### 8. Tracking không cần thiết cho read-only endpoint

- **Problem:** entity query mặc định có thể được change tracker theo dõi.
- **Why it happens:** không dùng projection/`AsNoTracking`.
- **Production impact:** allocation và tracking overhead không cần thiết.
- **Severity:** **Medium**
- **Recommended fix:** projection trực tiếp sang DTO thường loại bỏ nhu cầu tracking entity; nếu query entity read-only thì dùng `AsNoTracking`.

## Phiên bản code đề xuất

```csharp
public sealed record EmployeeSearchItem(
    long Id,
    string FullName,
    string WorkEmail,
    string Department,
    string OfficeCode);

[HttpGet("search")]
[Authorize(Policy = "EmployeeSearch")]
public async Task<ActionResult<IReadOnlyList<EmployeeSearchItem>>> Search(
    string? search,
    string? officeCode,
    bool includeInactive = false,
    int pageSize = 25,
    CancellationToken ct = default)
{
    pageSize = Math.Clamp(pageSize, 1, 100);
    var term = search?.Trim();

    if (term is { Length: < 2 })
        return BadRequest("Search term must contain at least 2 characters.");

    var scope = await _employeeAuthorization.GetReadableScopeAsync(User, ct);

    if (includeInactive && !scope.CanReadInactiveEmployees)
        return Forbid();

    var query = _db.Employees
        .AsNoTracking()
        .Where(x => scope.AllowedDepartmentIds.Contains(x.DepartmentId));

    if (!includeInactive)
        query = query.Where(x => x.IsActive);

    if (!string.IsNullOrWhiteSpace(officeCode))
    {
        if (!scope.AllowedOfficeCodes.Contains(officeCode))
            return Forbid();

        query = query.Where(x => x.Office.Code == officeCode);
    }

    if (!string.IsNullOrWhiteSpace(term))
    {
        query = query.Where(x =>
            x.FullName.Contains(term) ||
            x.Email.Contains(term) ||
            x.Mobile.StartsWith(term));
    }

    var result = await query
        .OrderBy(x => x.FullName)
        .ThenBy(x => x.Id)
        .Take(pageSize)
        .Select(x => new EmployeeSearchItem(
            x.Id,
            x.FullName,
            x.Email,
            x.Department.Name,
            x.Office.Code))
        .ToListAsync(ct);

    _logger.LogInformation(
        "Employee search completed for user {UserId}; ResultCount={ResultCount}; PageSize={PageSize}",
        scope.UserId,
        result.Count,
        pageSize);

    return Ok(result);
}
```

Đây là **recommended approach**, không phải một search implementation tối ưu cho mọi database. Case sensitivity và khả năng dùng index của `Contains`/`StartsWith` phụ thuộc provider, collation và query plan. Với PostgreSQL có thể cân nhắc provider-specific operators/indexes khi requirement đã rõ; với SQL Server cần kiểm tra collation và execution plan. Không nên chọn full-text hoặc search engine chỉ vì “có search”.

Một điểm quan trọng khác: nếu `AllowedDepartmentIds` rất lớn, việc đưa danh sách trực tiếp vào query không nhất thiết là thiết kế tốt nhất. Khi đó authorization scope nên được biểu diễn bằng quan hệ/query server-side thích hợp.

## Trade-offs

Projection DTO giảm dữ liệu và allocation nhưng cần thêm DTO/versioning. Minimum search length giảm load nhưng có thể ảnh hưởng UX đối với tên ngắn; đây là business decision. Offset pagination đơn giản nhưng cursor/keyset pagination phù hợp hơn khi tập dữ liệu lớn và người dùng duyệt sâu.

Authorization bằng policy cộng query scope tạo thêm code nhưng giữ security boundary phía server. Không nên tin `officeCode` client gửi để quyết định quyền; nó chỉ là filter sau khi quyền đã được xác định.

## Cách kiểm thử

1. **Authorization integration test:** manager department A tìm employee department B bằng ID/name/email phải không nhận được dữ liệu ngoài scope.
2. **Sensitive-data test:** response search không bao giờ chứa salary, home address hoặc personal email, kể cả HR search endpoint nếu contract không yêu cầu.
3. **Database query test:** xác minh filter/projection/pagination được translate server-side; kiểm tra generated SQL và execution plan với dataset representative.
4. **Load test:** search đồng thời trên dataset lớn, đo p95/p99 latency, allocations, DB CPU/reads và connection pool.
5. **Abuse/input test:** empty term, term 1 ký tự, page size cực lớn, office ngoài scope, `includeInactive=true` với role không đủ quyền.

## Quan sát trong production

- **Logs:** user ID đã chuẩn hóa, policy result, result count, duration; tránh raw search term và toàn bộ claims.
- **Metrics:** request count, p50/p95/p99 latency, authorization denials, result-size distribution, DB query duration/timeouts.
- **Traces:** HTTP span → authorization lookup → EF Core/database span.
- **Alerts:** p95 tăng đột biến, DB timeout, denial anomaly hoặc request volume bất thường từ một principal.
- **Database observations:** logical reads/execution plan, index usage, slow-query samples và row estimates thực tế so với estimate.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào một nguyên tắc quan trọng của distributed side effects: **retry và concurrency phải được thiết kế cùng idempotency, durable state và recovery**. Database transaction không thể tự bảo đảm consistency với Exchange Online. Shared `DbContext` cũng không được dùng cho nhiều operation song song.

Challenge 2 nhấn mạnh rằng **authentication không đồng nghĩa authorization**. Query security scope phải được áp phía server trước khi lấy dữ liệu, còn EF Core query phải giữ ở dạng `IQueryable` cho đến khi filter, projection và pagination hoàn tất. Data minimization là một phần của security design, không chỉ là tối ưu response.

## Mẫu tư duy cần nhớ

1. **Xác định transaction boundary trước khi thêm retry.** External side effect và DB thường tạo dual-write problem.
2. **Thiết kế retries cùng idempotency/reconciliation.** At-least-once execution phải được coi là tình huống bình thường.
3. **Authorize dữ liệu, không chỉ authorize endpoint.** Xác định row scope và field scope từ nguồn trusted phía server.
4. **Giữ query ở database càng lâu càng tốt.** Filter → project → paginate → materialize.
5. **Treat observability as part of the design.** Log đủ để điều tra nhưng không biến logging system thành kho PII/secrets thứ hai.
