# Code Review Challenge 1 — Product search mất đồng bộ vì cập nhật Elasticsearch trong cùng request

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, Elasticsearch, eventual consistency, partial failure, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một e-commerce platform lưu product master data trong SQL Server và dùng Elasticsearch cho full-text search. Admin cập nhật product qua ASP.NET Core API. Business chấp nhận search có thể trễ vài giây so với database, nhưng không chấp nhận product bị mất khỏi search vĩnh viễn hoặc API báo lỗi dù database thực tế đã commit thành công.

API chạy nhiều instances trên Azure App Service. Elasticsearch đôi khi có transient network failure hoặc cluster degradation. Production gần đây xuất hiện hai triệu chứng: một số product hiển thị dữ liệu cũ trong search hàng giờ, và một số request trả `500` khiến admin retry nhưng database đã chứa thay đổi từ request đầu tiên.

Team muốn giữ SQL Server là source of truth. Không có requirement bắt buộc distributed transaction giữa SQL Server và Elasticsearch.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/products")]
public sealed class ProductsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IElasticClient _elastic;
    private readonly ILogger<ProductsController> _logger;

    public ProductsController(
        AppDbContext db,
        IElasticClient elastic,
        ILogger<ProductsController> logger)
    {
        _db = db;
        _elastic = elastic;
        _logger = logger;
    }

    [HttpPut("{id:long}")]
    public async Task<IActionResult> Update(
        long id,
        UpdateProductRequest request,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (product is null)
            return NotFound();

        product.Name = request.Name;
        product.Description = request.Description;
        product.Price = request.Price;
        product.UpdatedUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        var document = new ProductSearchDocument
        {
            Id = product.Id,
            Name = product.Name,
            Description = product.Description,
            Price = product.Price,
            UpdatedUtc = product.UpdatedUtc
        };

        var response = await _elastic.IndexDocumentAsync(
            document,
            cancellationToken);

        if (!response.IsValid)
        {
            _logger.LogError(
                "Failed to index product {ProductId}: {Reason}",
                product.Id,
                response.ServerError?.Error?.Reason);

            return StatusCode(500, "Search update failed");
        }

        return Ok(product);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và consistency problems giữa SQL Server và Elasticsearch.
2. Phân tích các failure window khi SQL commit thành công nhưng indexing thất bại hoặc request bị cancel.
3. Xác định vì sao retry HTTP request không tự sửa được consistency một cách đáng tin cậy.
4. Ưu tiên findings theo severity và production impact.
5. Đề xuất corrected implementation/design giữ SQL Server là source of truth.
6. Giải thích cách test transient Elasticsearch failure, process crash và repeated delivery.
7. Đề xuất telemetry/reconciliation để chứng minh search index cuối cùng hội tụ về source of truth.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu `SaveChangesAsync` commit thành công nhưng `IndexDocumentAsync` timeout?
2. Client nhận `500` có thể kết luận database chưa thay đổi không?
3. Nếu process chết ngay sau SQL commit thì operation nào sẽ chịu trách nhiệm index product về sau?
4. Có cần distributed transaction giữa SQL Server và Elasticsearch để đáp ứng requirement hiện tại không?
5. Nếu cùng một product được update liên tiếp rất nhanh, làm sao tránh event cũ ghi đè document mới hơn?

## Gợi ý

### Gợi ý 1

Primary risk là **dual write không atomic** giữa source of truth và search projection.

### Gợi ý 2

Hãy nghĩ đến durable intent trong cùng transaction với SQL change, asynchronous projection, idempotency/version ordering và reconciliation thay vì cố biến Elasticsearch thành một phần của transaction request.

## Kết quả code review tham khảo

### Critical — SQL và Elasticsearch bị dual-write mà không có durable recovery path

**Vấn đề:** Database commit trước, Elasticsearch update sau. Nếu bước thứ hai thất bại, không có durable record nào bảo đảm indexing sẽ được thử lại.

**Tại sao xảy ra:** Hai hệ thống có transaction boundary độc lập. Request handler đang giả định sequential calls tạo ra một operation thống nhất.

**Ảnh hưởng production:** SQL chứa product mới nhưng search có thể giữ document cũ vô thời hạn. Restart application không tự biết product nào cần reindex.

**Cách sửa:** Ghi product change và một Outbox record trong cùng SQL transaction. Background publisher/projector đọc Outbox và cập nhật Elasticsearch. Chỉ đánh dấu Outbox processed sau khi indexing thành công theo protocol rõ ràng. Duplicate processing phải an toàn.

### High — API trả `500` sau khi database đã commit

**Vấn đề:** Client nhận failure dù primary business write đã thành công.

**Tại sao xảy ra:** Search projection failure được dùng làm kết quả của primary write sau transaction boundary.

**Ảnh hưởng production:** Admin retry có thể tạo repeated work, audit confusion hoặc conflict với subsequent edits. API contract không phản ánh state thực tế.

**Cách sửa:** Nếu requirement chấp nhận eventual consistency, primary API nên trả success khi authoritative SQL update thành công và durable indexing intent đã được commit. Search propagation được theo dõi riêng. Nếu business thực sự yêu cầu search synchronous, contract và failure semantics phải được thiết kế khác và requirement đó cần được xác nhận.

### High — Không có ordering/version protection cho rapid updates

**Vấn đề:** Hai updates cho cùng product có thể được index out of order khi asynchronous retry/concurrency được thêm vào.

**Tại sao xảy ra:** Document chỉ mang timestamp ứng dụng nhưng code không enforce monotonic version khi ghi projection.

**Ảnh hưởng production:** Event cũ có thể overwrite dữ liệu mới, khiến index hội tụ về sai state dù mọi event cuối cùng đều được xử lý.

**Cách sửa:** Mang một source version đáng tin cậy trong Outbox/document, ví dụ database-generated version hoặc monotonic product version. Projector phải bỏ qua stale version hoặc dùng Elasticsearch concurrency/version semantics phù hợp sau khi xác minh API/client version đang dùng. Một lựa chọn đơn giản khác là event chỉ mang `ProductId`, projector luôn reread current SQL state trước khi index; trade-off là thêm database read nhưng giảm nguy cơ stale payload.

### High — Cancellation có thể tạo ambiguous outcome

**Vấn đề:** Client disconnect/cancellation có thể xảy ra sau database commit nhưng trước hoặc trong Elasticsearch call.

**Tại sao xảy ra:** Cancellation của HTTP request bị dùng xuyên qua cả primary write và secondary side effect nhưng không có durable state machine.

**Ảnh hưởng production:** Caller không biết operation đã commit tới đâu; projection có thể bị bỏ dở.

**Cách sửa:** Durable Outbox làm recovery độc lập với lifetime của HTTP request. Sau khi transaction commit, eventual projection không nên phụ thuộc vào request còn sống.

### Medium — Không có retry/backoff policy ở projection boundary

**Vấn đề:** Một transient Elasticsearch/network failure trở thành permanent inconsistency trong flow hiện tại.

**Tại sao xảy ra:** Không có durable retry worker, attempt count, backoff hoặc dead-letter/manual reconciliation state.

**Ảnh hưởng production:** Short outage tạo long-lived stale search data.

**Cách sửa:** Projector retry transient failures với bounded exponential backoff/jitter phù hợp; permanent mapping/data failures cần terminal handling và alert thay vì retry vô hạn.

### Medium — Response trả EF entity trực tiếp

**Vấn đề:** API trả persistence entity sau update.

**Tại sao xảy ra:** Persistence model và HTTP contract bị coupling.

**Ảnh hưởng production:** Có thể vô tình expose fields/navigation hoặc làm contract thay đổi theo entity refactor.

**Cách sửa:** Trả response DTO chỉ chứa fields được contract cho phép, bao gồm version nếu client cần optimistic concurrency.

### Medium — Validation/business invariants không thể hiện ở boundary

**Vấn đề:** Snippet không cho thấy validation của price/name hoặc authorization cho product administration.

**Tại sao xảy ra:** Controller tập trung vào persistence/indexing nhưng trust request trực tiếp.

**Ảnh hưởng production:** Invalid product state hoặc unauthorized modification có thể đi vào source of truth nếu các concern này thực sự chưa được enforce ở nơi khác.

**Cách sửa:** Xác minh authorization policy và validation/domain invariants trước mutation. Không được kết luận chúng chắc chắn thiếu nếu chúng đã được enforce bằng filter/pipeline ngoài snippet; đây là điểm cần kiểm tra trong repository.

### Medium — Logging chưa đủ để điều tra projection lag

**Vấn đề:** Chỉ log lỗi synchronous indexing; không có event identity, attempt, source version, projection latency.

**Tại sao xảy ra:** Projection chưa được mô hình hóa như một asynchronous subsystem.

**Ảnh hưởng production:** Khó phân biệt backlog, poison event, stale ordering và Elasticsearch outage.

**Cách sửa:** Structured telemetry theo `OutboxId`, `ProductId`, source version, attempt, age, result và dependency duration; không log product content nhạy cảm nếu không cần.

### Low — Không có reconciliation path

**Vấn đề:** Ngay cả Outbox system cũng có thể có bug/operator mistake khiến projection drift.

**Tại sao xảy ra:** Chỉ dựa vào online delivery path.

**Ảnh hưởng production:** Silent drift có thể tồn tại lâu.

**Cách sửa:** Có periodic reconciliation hoặc controlled reindex strategy từ SQL source of truth; đo mismatch thay vì giả định projection luôn đúng.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa transactional Outbox ở application boundary. Chi tiết worker và Elasticsearch client API cần khớp version package thực tế của repository.

```csharp
[HttpPut("{id:long}")]
[Authorize(Policy = "ProductAdmin")]
public async Task<IActionResult> Update(
    long id,
    UpdateProductRequest request,
    CancellationToken cancellationToken)
{
    var product = await _db.Products
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (product is null)
        return NotFound();

    product.Update(
        request.Name,
        request.Description,
        request.Price,
        DateTime.UtcNow);

    var outbox = new OutboxMessage
    {
        Id = Guid.NewGuid(),
        Type = "ProductSearchProjectionRequested",
        AggregateId = product.Id.ToString(),
        OccurredUtc = DateTime.UtcNow,
        Payload = JsonSerializer.Serialize(new
        {
            ProductId = product.Id
        })
    };

    _db.OutboxMessages.Add(outbox);

    await _db.SaveChangesAsync(cancellationToken);

    return Ok(new ProductResponse(
        product.Id,
        product.Name,
        product.Description,
        product.Price,
        product.UpdatedUtc));
}
```

Projector có thể reread authoritative state trước khi index:

```csharp
public async Task ProjectAsync(
    OutboxMessage message,
    CancellationToken cancellationToken)
{
    var productId = ReadProductId(message.Payload);

    var product = await _db.Products
        .AsNoTracking()
        .Where(x => x.Id == productId)
        .Select(x => new ProductSearchDocument
        {
            Id = x.Id,
            Name = x.Name,
            Description = x.Description,
            Price = x.Price,
            UpdatedUtc = x.UpdatedUtc
        })
        .SingleOrDefaultAsync(cancellationToken);

    if (product is null)
    {
        await DeleteProjectionIfPresentAsync(productId, cancellationToken);
    }
    else
    {
        await IndexProjectionAsync(product, cancellationToken);
    }

    await MarkProcessedAsync(message.Id, cancellationToken);
}
```

`MarkProcessedAsync` và worker claiming phải được thiết kế để duplicate execution không phá correctness. Nếu process chết sau Elasticsearch success nhưng trước Outbox acknowledgement, message sẽ được xử lý lại; do đó index operation cần idempotent theo document identity/current source state. Với throughput cao, có thể tối ưu batching/coalescing sau khi đo backlog và database load.

## Giải thích thiết kế sau khi sửa

SQL update và durable intent nằm trong cùng local transaction, nên không có khoảng trống “database đã đổi nhưng không ai biết cần update search”. Elasticsearch trở thành projection eventual-consistent có thể rebuild từ source of truth. API không giả vờ có atomic transaction xuyên SQL và Elasticsearch.

Reread current state là một cách đơn giản để tránh stale payload overwrite: dù Outbox event cũ được xử lý muộn, projector lấy state mới nhất. Nếu cần preserve từng historical transition hoặc throughput không cho phép reread, cần explicit source version và ordering strategy.

## Trade-offs

Outbox thêm table, worker, cleanup, retry và monitoring. Search không cập nhật tức thời; UI cần chấp nhận propagation delay theo SLO. Reread SQL tăng query load. Dùng Azure Service Bus giữa Outbox publisher và projector có thể hữu ích khi cần decoupling/scale, nhưng không loại bỏ nhu cầu idempotency và không cần thiết nếu một SQL-backed projector đơn giản đã đáp ứng tải.

## Cách kiểm thử

1. **Integration test:** SQL product update và Outbox insert phải cùng commit hoặc cùng rollback.
2. **Failure-path test:** Elasticsearch unavailable sau commit; API authoritative write vẫn đúng và Outbox còn pending để retry.
3. **Crash test:** giả lập process chết sau successful indexing nhưng trước acknowledgement; retry không tạo sai projection.
4. **Ordering/concurrency test:** update cùng product nhiều lần và xử lý Outbox đảo thứ tự; final search document phải phản ánh current authoritative state.
5. **Reconciliation test:** cố tình làm index lệch SQL rồi chạy reconciliation/reindex; drift phải được phát hiện và sửa theo policy.

## Quan sát trong production

Theo dõi Outbox pending count, oldest message age, attempts, permanent failures, projection latency và Elasticsearch dependency latency/error rate. Dashboard cần phân biệt write API health với search projection health. Alert theo oldest unprocessed age/SLO thay vì chỉ exception count. Có thể sampling kiểm tra SQL-vs-index version/mismatch để phát hiện silent drift. Correlation giữa `ProductId`, `OutboxId` và trace giúp đi từ admin request tới projection attempt mà không cần log toàn bộ document.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn payload snapshot thay vì chỉ lưu `ProductId` rồi reread SQL trong projector?
2. Nếu Elasticsearch phải phản ánh thay đổi trong dưới 500 ms ở p99, kiến trúc và SLO monitoring cần thay đổi thế nào?
3. Outbox có bảo đảm exactly-once indexing không? Nếu không, business guarantee thực tế nên được định nghĩa ra sao?

# Code Review Challenge 2 — Release pipeline chạy database migration sau khi traffic đã vào version mới

**Chủ đề:** CI/CD, TeamCity, Octopus Deploy, ASP.NET Core, SQL migration, artifact consistency, rollback, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core application được build bằng TeamCity và deploy tới IIS/Windows Server qua Octopus Deploy. Production có hai web nodes sau load balancer. Team muốn zero/minimal-downtime deployment và có thể rollback application nhanh nếu release lỗi.

Sau một release gần đây, node đầu tiên nhận traffic với code mới trước khi schema migration hoàn tất. Một request ghi dữ liệu theo schema mới và fail. Team rerun deployment; migration script chạy lại một phần, trong khi node thứ hai vẫn chạy code cũ. Ngoài ra pipeline build package riêng cho từng environment để thay `appsettings`, nên artifact được test ở staging không hoàn toàn giống bytes deploy lên production.

Đoạn PowerShell dưới đây đại diện cho logic deployment hiện tại được Octopus step gọi trên mỗi target web node.

## Đoạn code cần review

```powershell
param(
    [string]$Environment,
    [string]$PackagePath,
    [string]$SitePath,
    [string]$ConnectionString
)

Write-Host "Deploying $PackagePath to $Environment"
Write-Host "Database: $ConnectionString"

Import-Module WebAdministration

Stop-WebAppPool -Name "CatalogAppPool"

Remove-Item "$SitePath\*" -Recurse -Force
Expand-Archive -Path $PackagePath -DestinationPath $SitePath -Force

Start-WebAppPool -Name "CatalogAppPool"

Invoke-Sqlcmd `
    -ConnectionString $ConnectionString `
    -InputFile "$SitePath\db\migration.sql"

$config = Get-Content "$SitePath\appsettings.json" -Raw
$config = $config.Replace("__ENVIRONMENT__", $Environment)
Set-Content "$SitePath\appsettings.json" $config

Invoke-WebRequest `
    -Uri "http://localhost/health" `
    -UseBasicParsing

Write-Host "Deployment completed"
```

## Nhiệm vụ của ứng viên

1. Xác định release-safety, security và correctness problems trong deployment flow.
2. Phân tích migration ordering khi nhiều web nodes và mixed application versions cùng tồn tại.
3. Xác định vấn đề artifact immutability/configuration và rollback semantics.
4. Ưu tiên findings theo production impact.
5. Đề xuất corrected deployment sequence phù hợp IIS + TeamCity + Octopus Deploy mà không mặc định phải chuyển sang Kubernetes.
6. Giải thích cách test migration compatibility, rollback và partial deployment failure.
7. Đề xuất telemetry/release evidence để biết chính xác version nào đang phục vụ traffic.

## Câu hỏi gợi mở

1. Vì sao `Start-WebAppPool` trước migration có thể làm code mới nhận request trên schema cũ?
2. Nếu step này chạy trên hai targets, migration sẽ được thực thi bao nhiêu lần và có an toàn không?
3. Connection string xuất hiện trong `Write-Host` có thể đi đâu sau deployment?
4. Nếu production package được rebuild hoặc mutate khác staging package, bạn còn biết mình đang promote artifact nào không?
5. Một rollback application binary có luôn an toàn sau database migration không?

## Gợi ý

### Gợi ý 1

Primary risk là **release không có compatibility contract giữa application version, database schema và traffic switching**.

### Gợi ý 2

Hãy tách build artifact, environment configuration, database migration và traffic/readiness thành các bước có ownership rõ ràng. Migration cần được chạy một lần theo release strategy và thiết kế backward-compatible nếu old/new versions cùng tồn tại.

## Kết quả code review tham khảo

### Critical — Application mới được start trước database migration

**Vấn đề:** App Pool được start trước `Invoke-Sqlcmd`.

**Tại sao xảy ra:** Deployment coi file copy/start và schema migration là các bước độc lập nhưng không kiểm soát traffic compatibility.

**Ảnh hưởng production:** Code mới có thể query/write schema chưa tồn tại, tạo 5xx hoặc partial business writes.

**Cách sửa:** Xác định migration strategy trước rollout. Với rolling/minimal downtime, ưu tiên expand-and-contract: deploy schema thay đổi backward-compatible trước hoặc như một release step chạy một lần, sau đó rollout application, rồi cleanup destructive schema ở release sau khi old code không còn chạy. Không start node vào traffic trước khi preconditions và health/readiness đạt yêu cầu.

### Critical — Migration chạy trên mỗi deployment target

**Vấn đề:** Script target-scoped chạy `migration.sql` trên từng web node.

**Tại sao xảy ra:** Database migration ownership bị gắn vào node deployment thay vì release-level step.

**Ảnh hưởng production:** Hai nodes có thể chạy cùng migration concurrently hoặc rerun partial script; lock/contention hoặc duplicate DDL/data changes có thể xảy ra.

**Cách sửa:** Chạy migration như một release-level/run-once step với explicit locking/version history và migration tooling/script có repeatability semantics phù hợp. Không dựa vào “chắc Octopus sẽ chạy tuần tự” nếu process không enforce điều đó.

### Critical — Secret bị ghi vào deployment log

**Vấn đề:** `Write-Host "Database: $ConnectionString"` xuất connection string.

**Tại sao xảy ra:** Diagnostic logging không phân biệt secret và ordinary configuration.

**Ảnh hưởng production:** Credential có thể tồn tại trong Octopus task logs, export hoặc support artifacts và được đọc bởi người có log access.

**Cách sửa:** Dùng sensitive variables/secret store của deployment platform và tuyệt đối không log raw secret. Rotate credential nếu đã bị exposed; audit access theo policy.

### High — Artifact bị mutate/rebuild theo environment

**Vấn đề:** Pipeline thay `appsettings.json` trong deployed package path; bối cảnh còn cho biết package được build riêng cho từng environment.

**Tại sao xảy ra:** Build và deployment configuration bị trộn.

**Ảnh hưởng production:** Staging và production không chạy cùng immutable artifact; khó trace, reproduce và rollback.

**Cách sửa:** Build once trong TeamCity, version/hash artifact, promote cùng package qua environments. Inject environment-specific config ở deployment/runtime boundary bằng Octopus variables, environment variables hoặc protected configuration mechanism mà không rebuild application binaries.

### High — Destructive file replacement tạo downtime và partial-state risk

**Vấn đề:** Stop App Pool, xóa toàn bộ site rồi extract trực tiếp vào live path.

**Tại sao xảy ra:** Deployment không có staged directory/atomic switch hoặc multi-node traffic-drain strategy.

**Ảnh hưởng production:** Extract failure có thể để site thiếu files; node unavailable lâu hơn cần thiết. Nếu load balancer vẫn route vào node, user nhận lỗi.

**Cách sửa:** Drain node khỏi load balancer, deploy vào versioned/staging path hoặc sử dụng deployment mechanism phù hợp với IIS, validate package/config, switch/start, health-check rồi đưa node trở lại traffic. Roll từng node nếu compatibility cho phép.

### High — Rollback binary không được thiết kế cùng database compatibility

**Vấn đề:** Pipeline ngầm giả định có thể restore app version cũ sau bất kỳ migration nào.

**Tại sao xảy ra:** Database migration thường là persistent state transition, không tự rollback cùng binary.

**Ảnh hưởng production:** Rollback code cũ có thể fail trên schema mới hoặc đọc dữ liệu theo assumptions cũ.

**Cách sửa:** Thiết kế backward-compatible schema changes, xác định rollback/roll-forward policy và test old-version/new-schema compatibility khi rollback binary là requirement. Destructive rename/drop nên tách sang contract phase sau khi rollback window đóng.

### Medium — Health check chỉ kiểm tra localhost và không chứng minh node sẵn sàng qua real routing path

**Vấn đề:** `Invoke-WebRequest http://localhost/health` chỉ chứng minh một endpoint local trả success tại một thời điểm.

**Tại sao xảy ra:** Readiness được giản lược thành process endpoint check.

**Ảnh hưởng production:** Binding, reverse proxy/load balancer, environment config hoặc critical dependency có thể vẫn lỗi khi traffic thật vào.

**Cách sửa:** Có deployment validation phù hợp: local application health để xác minh process, sau đó smoke test qua routing path hoặc synthetic check trước/after traffic enable. Health contract không nên thực hiện destructive/expensive work.

### Medium — Không có explicit failure handling/rollback cho từng step

**Vấn đề:** Script không thể hiện `$ErrorActionPreference = 'Stop'`, try/finally, node traffic state hoặc recovery khi extract/migration/config/health thất bại.

**Tại sao xảy ra:** Happy path được coi là deployment protocol hoàn chỉnh.

**Ảnh hưởng production:** Node có thể bị để ở trạng thái stopped, partially deployed hoặc được đưa vào traffic sai lúc tùy orchestration bên ngoài.

**Cách sửa:** Fail fast, model deployment state, chỉ enable traffic sau validation; recovery phải biết version/site path trước đó. Database failure cần runbook riêng, không blind rerun.

### Medium — Configuration được mutate sau application start

**Vấn đề:** `appsettings.json` được thay placeholder sau khi App Pool đã start.

**Tại sao xảy ra:** Configuration injection nằm sai thứ tự.

**Ảnh hưởng production:** Process có thể load config cũ/placeholder khi startup; file change có thể trigger reload behavior không được kiểm soát.

**Cách sửa:** Resolve/validate configuration trước startup hoặc cung cấp config qua environment/runtime mechanism. Secret/config validation phải là precondition của start.

### Low — Không ghi release identity vào telemetry

**Vấn đề:** Script không cho thấy version/hash được expose cho logs/health/telemetry.

**Tại sao xảy ra:** Deployment success chỉ là một log string.

**Ảnh hưởng production:** Khi hai nodes chạy khác version, incident response khó correlation lỗi với release.

**Cách sửa:** Stamp immutable build/release identity vào application metadata và structured telemetry; dashboard theo node/version.

## Phiên bản đề xuất

Một flow an toàn hơn nên được orchestrate ở release level thay vì nhồi toàn bộ logic vào per-node script:

```text
TeamCity
  1. Restore/build/test/static analysis.
  2. Produce ONE immutable application artifact.
  3. Produce/version database migration artifact.
  4. Publish hashes + build/version metadata.

Octopus release
  1. Resolve protected environment configuration/secrets.
  2. Pre-deployment compatibility checks.
  3. Run database EXPAND migration ONCE for the release.
  4. For each web node:
       a. Drain node from load balancer.
       b. Deploy immutable package to staged/versioned location.
       c. Inject/resolve environment configuration before start.
       d. Start application.
       e. Run local health/readiness validation.
       f. Run smoke test through intended routing path.
       g. Re-enable node traffic.
       h. Observe error/latency signals before next node.
  5. Verify all nodes report expected release identity.
  6. Run post-deployment smoke/E2E checks.
  7. CONTRACT/destructive DB changes only in a later safe release.
```

Per-node PowerShell nên chỉ làm nhiệm vụ node-local và fail fast, ví dụ:

```powershell
param(
    [string]$PackagePath,
    [string]$VersionedSitePath,
    [string]$AppPoolName
)

$ErrorActionPreference = 'Stop'

Import-Module WebAdministration

if (-not (Test-Path $PackagePath)) {
    throw "Deployment package not found"
}

New-Item -ItemType Directory `
    -Path $VersionedSitePath `
    -Force | Out-Null

Expand-Archive `
    -Path $PackagePath `
    -DestinationPath $VersionedSitePath `
    -Force

# Environment configuration is resolved securely before process startup.
# Load-balancer drain/enable is controlled by the release orchestration.

Restart-WebAppPool -Name $AppPoolName

$response = Invoke-WebRequest `
    -Uri "http://localhost/health/ready" `
    -UseBasicParsing `
    -TimeoutSec 10

if ($response.StatusCode -ne 200) {
    throw "Node did not become ready"
}
```

Cách switch IIS physical path/versioned directory phụ thuộc hosting setup thực tế và cần được test; reference này không giả định một lệnh switch cụ thể luôn phù hợp. Quan trọng là package được staged/validated trước khi node quay lại traffic và migration không còn chạy per node.

## Giải thích thiết kế sau khi sửa

Build pipeline tạo artifact một lần; deployment pipeline chỉ cấu hình/promote artifact đó. Database migration là release concern riêng và phải có compatibility strategy. Rolling node deployment chỉ an toàn nếu schema hỗ trợ đồng thời old/new application versions trong rollout window.

Expand-and-contract tránh yêu cầu distributed transaction giữa deployment nodes. Ví dụ thêm nullable column/index theo cách tương thích trước, deploy code bắt đầu sử dụng schema mới, backfill nếu cần, rồi chỉ drop old schema sau khi không còn consumer cũ và rollback window đã đóng.

## Trade-offs

Build-once/promote cần quản lý configuration tốt hơn thay vì bake config vào package. Expand-and-contract làm migration kéo dài qua nhiều release và có temporary schema duplication. Draining/rolling nodes cần load-balancer automation và capacity headroom. Một maintenance window đơn giản có thể hợp lý hơn nếu business cho phép downtime ngắn; zero downtime không nên được chọn chỉ vì nghe “hiện đại”.

## Cách kiểm thử

1. **Migration compatibility test:** chạy old app trên expanded schema và new app trên cùng schema; cả hai phải hoạt động trong mixed-version window nếu rollout yêu cầu.
2. **Partial deployment test:** fail deployment ở node thứ hai; node thứ nhất/new version và node còn lại/old version phải vẫn có defined behavior và release có safe stop/rollback path.
3. **Rollback validation:** deploy schema + new binary rồi rollback binary; xác minh old version vẫn chạy trên migrated schema trong supported rollback window.
4. **Artifact integrity test:** so sánh artifact hash được promote qua test/staging/production; environment change không được rebuild binary.
5. **Post-deployment E2E/smoke test:** kiểm tra critical user path qua load balancer sau rollout, đồng thời theo dõi 5xx và latency regression.

## Quan sát trong production

Mỗi node cần expose/log build version, commit/release ID và startup timestamp. Application Insights/Azure Monitor hoặc hệ thống telemetry hiện có cần dashboard request rate, 5xx, p95/p99 latency và dependency failures theo release version/node. Deployment logs phải ghi migration version, artifact hash, node drain/enable state và health result nhưng không chứa secrets. Alert trong rollout nên so sánh error/latency với baseline và cho phép pause release trước node tiếp theo.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào maintenance window + stop-all-nodes là lựa chọn tốt hơn rolling deployment phức tạp?
2. Bạn xử lý migration `NOT NULL` trên bảng rất lớn thế nào nếu old application vẫn đang ghi dữ liệu trong rollout window?
3. Nếu release đã chạy irreversible data transformation rồi phát hiện application regression, bạn chọn rollback hay roll-forward dựa trên tiêu chí nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Một write đi qua hai data stores không tự trở thành atomic chỉ vì code gọi chúng liên tiếp. Khi SQL Server là source of truth và Elasticsearch là search projection, cần durable propagation, idempotency, ordering strategy và reconciliation thay vì trả `500` sau một secondary write failure rồi hy vọng client retry sẽ sửa mọi thứ.

Deployment cũng là một distributed state transition: application version, database schema, configuration và traffic có thể ở các trạng thái khác nhau trong cùng một release. Release an toàn cần compatibility contract và observability, không chỉ một script copy file rồi chạy migration.

## Mẫu tư duy cần nhớ

* Với **dual write**, luôn hỏi failure xảy ra giữa hai commits thì ai sẽ recover.
* Với eventual consistency, thiết kế **durable intent + idempotent projection + reconciliation**.
* **Build once, promote the same artifact**; environment configuration không nên biến production thành một build khác staging.
* Database migration phải được thiết kế cùng **mixed-version window, rollback và traffic switching**.
* Đừng coi “deployment completed” là bằng chứng; cần release identity, health, metrics và user-path verification.
