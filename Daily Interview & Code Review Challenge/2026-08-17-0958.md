# Code Review Challenge 1 — API xuất dữ liệu cho phép vượt quyền và làm lộ thông tin nhạy cảm

**Chủ đề:** Authentication, authorization, input validation, sensitive-data exposure, logging  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép nhân viên tải báo cáo hồ sơ người dùng theo phòng ban. Frontend chỉ hiển thị chức năng này cho role `Manager`, nhưng backend cũng được gọi trực tiếp từ mobile app và các client nội bộ. Mỗi manager chỉ được xem phòng ban mình quản lý; `Admin` được xem mọi phòng ban.

Sau một đợt pentest, đội security báo rằng có khả năng một tài khoản hợp lệ truy cập dữ liệu ngoài phạm vi được phép. Production cũng đang ghi log request để hỗ trợ điều tra sự cố. Báo cáo có email, số điện thoại và một trường nội bộ `IdentityNumber`. Hệ thống dùng JWT authentication; chi tiết claim mapping chưa được cung cấp.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(AppDbContext db, ILogger<ReportsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("employees")]
    public async Task<IActionResult> ExportEmployees(
        [FromQuery] int departmentId,
        [FromQuery] string? search,
        CancellationToken cancellationToken)
    {
        var userId = User.FindFirst("sub")?.Value;

        _logger.LogInformation(
            "Export requested by {UserId}, department={DepartmentId}, search={Search}, token={Token}",
            userId,
            departmentId,
            search,
            Request.Headers.Authorization.ToString());

        var query = _db.Employees
            .Where(x => x.DepartmentId == departmentId);

        if (!string.IsNullOrWhiteSpace(search))
        {
            query = query.Where(x =>
                x.Email.Contains(search) ||
                x.FullName.Contains(search) ||
                x.IdentityNumber.Contains(search));
        }

        var employees = await query
            .OrderBy(x => x.FullName)
            .Select(x => new
            {
                x.Id,
                x.FullName,
                x.Email,
                x.PhoneNumber,
                x.IdentityNumber,
                x.Salary,
                x.DepartmentId
            })
            .ToListAsync(cancellationToken);

        return Ok(new
        {
            RequestedBy = userId,
            Search = search,
            Data = employees
        });
    }
}
```

4. Ưu tiên vấn đề theo mức độ nghiêm trọng.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách test authorization boundary và failure path.
7. Đề xuất logs, traces và metrics phục vụ audit mà không làm lộ secret/PII.

## Kết quả code review tham khảo

### 1. Endpoint không khai báo yêu cầu authentication/authorization

**Problem:** Action không có `[Authorize]` hoặc policy tương đương ở controller/route configuration.  
**Why it happens:** Code đang ngầm dựa vào UI hoặc một cấu hình bên ngoài chưa được thể hiện. Nếu không có fallback policy toàn cục, anonymous request có thể đi vào action.  
**Production impact:** Có thể dẫn tới truy cập dữ liệu nhân viên không cần đăng nhập.  
**Severity:** Critical  
**Recommended fix:** Bảo vệ endpoint bằng `[Authorize(Policy = "EmployeeReport.Read")]` hoặc policy phù hợp; đồng thời test cấu hình thực tế, không chỉ nhìn attribute.

### 2. Broken object/resource-level authorization qua `departmentId`

**Problem:** Caller tự truyền `departmentId`, backend không kiểm tra caller có quyền với department đó hay không.  
**Why it happens:** Authentication chỉ xác nhận danh tính; nó không chứng minh user được phép truy cập resource cụ thể.  
**Production impact:** Một manager hợp lệ có thể thay query string để đọc phòng ban khác.  
**Severity:** Critical  
**Recommended fix:** Resolve phạm vi được phép từ trusted server-side data/claims và áp dụng resource-based authorization hoặc filter bắt buộc trước khi query.

### 3. Ghi nguyên Authorization header vào log

**Problem:** Access token được ghi vào application log.  
**Why it happens:** Logging request context quá mức. Bearer token là credential.  
**Production impact:** Người có quyền đọc log có thể chiếm token còn hiệu lực; log aggregator, backup và support tooling làm tăng blast radius.  
**Severity:** Critical  
**Recommended fix:** Không log token, API key, cookie hay credential. Chỉ log correlation ID, subject/user identifier đã phù hợp chính sách và authorization decision metadata cần thiết.

### 4. Overexposure dữ liệu nhạy cảm

**Problem:** Response trả `IdentityNumber`, `Salary`, phone và các trường không được chứng minh là cần cho use case.  
**Why it happens:** DTO được thiết kế theo entity thay vì principle of least data.  
**Production impact:** Tăng hậu quả nếu endpoint bị abuse, token bị compromise hoặc response bị lưu/cache sai.  
**Severity:** High  
**Recommended fix:** Tạo explicit export DTO theo business requirement; chỉ trả field thực sự cần. Tách quyền xem compensation/identity nếu business yêu cầu.

### 5. Search cho phép dò dữ liệu nhạy cảm qua `IdentityNumber`

**Problem:** Người dùng có thể tìm theo identity number dù chức năng báo cáo có thể không cần capability này.  
**Why it happens:** Search surface được mở rộng theo field có sẵn thay vì theo requirement.  
**Production impact:** Hỗ trợ enumeration/dò PII và làm tăng sensitivity của endpoint.  
**Severity:** High  
**Recommended fix:** Chỉ cho phép search trên field được phê duyệt; cân nhắc exact/prefix semantics và authorization riêng nếu cần tìm bằng identifier nhạy cảm.

### 6. Không có giới hạn số bản ghi/pagination hoặc cơ chế export bất đồng bộ

**Problem:** `ToListAsync` tải toàn bộ kết quả phù hợp vào memory.  
**Why it happens:** Endpoint export được triển khai như endpoint query thông thường.  
**Production impact:** Department lớn hoặc request lặp lại có thể gây memory pressure, query dài và tăng latency/DB load.  
**Severity:** High  
**Recommended fix:** Đặt giới hạn, pagination/streaming phù hợp hoặc chuyển export lớn sang background workflow với quota và authorization được giữ nguyên.

### 7. Không validate `departmentId` và `search`

**Problem:** Không kiểm tra department hợp lệ, độ dài search, format hoặc minimum search length.  
**Why it happens:** Model binding không đồng nghĩa business validation.  
**Production impact:** Query tốn kém, hành vi khó dự đoán và tăng abuse surface.  
**Severity:** Medium  
**Recommended fix:** Validate input bằng request model; đặt giới hạn độ dài và business constraints.

### 8. Search bằng `Contains` trên nhiều cột có thể gây query đắt

**Problem:** Substring search trên nhiều field, đặc biệt field nhạy cảm, có thể khó tận dụng index thông thường tùy provider/collation/query plan.  
**Why it happens:** Search semantics được chọn vì tiện code hơn là dựa trên access pattern.  
**Production impact:** Scan lớn và latency tăng khi dữ liệu phát triển.  
**Severity:** Medium  
**Recommended fix:** Xác định search semantics thực tế, kiểm tra SQL/query plan, dùng index phù hợp hoặc search solution khác nếu yêu cầu full-text/sub-string ở scale lớn.

### 9. Echo lại search input trong response không cần thiết

**Problem:** Response trả lại nguyên `search`.  
**Why it happens:** Diagnostic metadata được trộn vào contract.  
**Production impact:** Có thể làm PII/user-controlled content lan sang client logs hoặc downstream storage; lợi ích thấp.  
**Severity:** Low  
**Recommended fix:** Bỏ nếu client không cần; nếu cần thì định nghĩa rõ contract và giới hạn input.

## Phiên bản code đề xuất

```csharp
public sealed record EmployeeReportRequest(
    int DepartmentId,
    string? Search,
    int Page = 1,
    int PageSize = 100);

public sealed record EmployeeReportRow(
    Guid Id,
    string FullName,
    string Email);

[ApiController]
[Route("api/reports")]
[Authorize(Policy = "EmployeeReport.Read")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IAuthorizationService _authorization;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        AppDbContext db,
        IAuthorizationService authorization,
        ILogger<ReportsController> logger)
    {
        _db = db;
        _authorization = authorization;
        _logger = logger;
    }

    [HttpGet("employees")]
    public async Task<ActionResult<IReadOnlyList<EmployeeReportRow>>> ExportEmployees(
        [FromQuery] EmployeeReportRequest request,
        CancellationToken cancellationToken)
    {
        if (request.DepartmentId <= 0 ||
            request.Page <= 0 ||
            request.PageSize is < 1 or > 200 ||
            request.Search?.Length > 100)
        {
            return ValidationProblem();
        }

        var authorization = await _authorization.AuthorizeAsync(
            User,
            request.DepartmentId,
            "DepartmentEmployeeReport.Read");

        if (!authorization.Succeeded)
            return Forbid();

        var search = request.Search?.Trim();

        var query = _db.Employees
            .AsNoTracking()
            .Where(x => x.DepartmentId == request.DepartmentId);

        if (!string.IsNullOrWhiteSpace(search))
        {
            query = query.Where(x =>
                x.Email.Contains(search) ||
                x.FullName.Contains(search));
        }

        var rows = await query
            .OrderBy(x => x.FullName)
            .ThenBy(x => x.Id)
            .Skip((request.Page - 1) * request.PageSize)
            .Take(request.PageSize)
            .Select(x => new EmployeeReportRow(x.Id, x.FullName, x.Email))
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Employee report exported by {UserId} for department {DepartmentId}; rows={RowCount}",
            User.FindFirst("sub")?.Value,
            request.DepartmentId,
            rows.Count);

        return Ok(rows);
    }
}
```

Policy/resource handler phải resolve quyền từ nguồn trusted, ví dụ mapping manager-to-department trong database hoặc claims đã được thiết kế và quản trị đúng. Không nên đơn giản kiểm tra `departmentId` bằng một claim do code chưa xác minh semantics.

## Trade-offs

Resource-based authorization thêm một lookup hoặc logic policy nhưng đổi lại boundary được enforce ở server. Nếu quyền department ổn định và claims được phát hành đáng tin cậy, có thể đưa scope vào token để giảm DB lookup; đổi lại quyền bị revoke có thể không phản ánh ngay cho tới khi token hết hạn hoặc được xử lý bằng cơ chế khác.

Pagination phù hợp cho browsing; export thật sự hàng trăm nghìn dòng có thể nên chuyển sang job tạo file có expiry, quota và access control. Khi đó phải re-check authorization tại thời điểm tạo/download và tránh đưa PII vào URL hoặc log.

## Cách kiểm thử

1. **Security integration test:** anonymous request phải 401; authenticated nhưng không có policy phải 403.
2. **Authorization boundary test:** manager của department A thử gọi `departmentId=B` phải bị từ chối; Admin theo đúng policy mới được phép.
3. **Sensitive-data test:** response không chứa `IdentityNumber`, salary hoặc token; log sink cũng không chứa Authorization header.
4. **Load/database test:** department lớn + search phổ biến; kiểm tra SQL, query plan, latency, allocation và giới hạn page size.
5. **Token-compromise scenario:** xác minh quyền của token chỉ cho phép scope tối thiểu và audit trail đủ để điều tra access bất thường.

## Quan sát trong production

- Log authorization outcome, subject ID phù hợp chính sách, department, correlation/trace ID và row count; không log token/PII search term nếu không thật sự cần.
- Metric: số request 401/403, export/request rate theo user, row count distribution, latency p95/p99 và DB query duration.
- Trace từ HTTP request tới EF Core/database span để tìm query chậm.
- Alert khi một principal truy cập nhiều department bất thường, export rate tăng đột biến hoặc số lượng 403 tăng mạnh.
- Database observation: execution plan, logical reads, index usage và lock/wait nếu query trở nên nặng.

# Code Review Challenge 2 — EF Core dashboard tưởng là “một query” nhưng kéo cả bảng vào memory

**Chủ đề:** EF Core query execution, LINQ deferred execution, SQL performance, cancellation  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một endpoint dashboard trả danh sách khách hàng có đơn hàng gần đây cùng tổng doanh thu. Database có vài triệu `Orders` và hàng trăm nghìn `Customers`. Sau khi release tính năng lọc theo `keyword`, API tăng từ dưới một giây lên nhiều giây ở giờ cao điểm, memory của pod tăng mạnh và database CPU cũng cao.

Đội phát triển nói rằng “EF Core sẽ tự chuyển LINQ thành SQL nên đoạn này chỉ chạy trên database”. Endpoint được gọi khoảng vài chục request/giây trong giờ cao điểm. SQL Server/PostgreSQL đều là deployment target của sản phẩm, nên không nên dựa vào hành vi provider-specific mà chưa đo đạc.

## Đoạn code cần review

```csharp
public sealed class DashboardService
{
    private readonly AppDbContext _db;

    public DashboardService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<IReadOnlyList<CustomerSummary>> GetCustomersAsync(
        string? keyword,
        DateTime fromUtc,
        int limit,
        CancellationToken cancellationToken)
    {
        var customers = await _db.Customers
            .Include(x => x.Orders)
            .ToListAsync(cancellationToken);

        var filtered = customers
            .Where(c => string.IsNullOrWhiteSpace(keyword) ||
                        c.Name.Contains(keyword, StringComparison.OrdinalIgnoreCase))
            .Where(c => c.Orders.Any(o => o.CreatedAt >= fromUtc))
            .Select(c => new CustomerSummary
            {
                CustomerId = c.Id,
                Name = c.Name,
                OrderCount = c.Orders.Count(o => o.CreatedAt >= fromUtc),
                Revenue = c.Orders
                    .Where(o => o.CreatedAt >= fromUtc)
                    .Sum(o => o.TotalAmount)
            })
            .OrderByDescending(x => x.Revenue)
            .Take(limit)
            .ToList();

        await Task.Delay(10);

        return filtered;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và query-execution problems.
2. Phân tích memory, database và concurrency/load impact.
3. Giải thích chính xác phần nào chạy ở database, phần nào chạy trong process.
4. Ưu tiên các vấn đề gây incident.
5. Đề xuất query/contract tốt hơn nhưng vẫn portable hợp lý giữa SQL Server và PostgreSQL.
6. Giải thích cách kiểm tra SQL thực tế và query plan.
7. Đề xuất tests, metrics và traces chứng minh fix có hiệu quả.

## Câu hỏi gợi mở

- `ToListAsync` thay đổi kiểu và nơi thực thi của pipeline như thế nào?
- `Include` có cần thiết khi kết quả cuối chỉ là projection aggregate không?
- `Take(limit)` đang được áp dụng trước hay sau khi dữ liệu về application?
- Cancellation token có đi xuyên suốt toàn bộ operation không?
- `limit` và `fromUtc` cần validation gì?

## Gợi ý

### Gợi ý 1

Hãy xác định **materialization boundary**. LINQ không phải lúc nào cũng là LINQ-to-database.

### Gợi ý 2

Nếu giữ pipeline dưới dạng `IQueryable` cho đến projection/order/take/materialization, database có cơ hội filter và aggregate trước khi truyền dữ liệu qua network.

## Kết quả code review tham khảo

### 1. Materialize toàn bộ Customers + Orders trước khi filter

**Problem:** `Include(...).ToListAsync()` tải toàn bộ tập customer cùng orders trước mọi filter business.  
**Why it happens:** `ToListAsync` là materialization boundary. Sau đó `customers` là collection trong memory, nên các LINQ operator tiếp theo là LINQ-to-Objects.  
**Production impact:** Memory pressure lớn, network payload DB→app lớn, query chậm và có thể dẫn tới GC pressure/OOM dưới tải.  
**Severity:** Critical  
**Recommended fix:** Giữ `IQueryable` đến cuối; filter, aggregate, order và `Take` ở database rồi mới materialize.

### 2. `Include` tải entity graph không cần thiết

**Problem:** Toàn bộ `Orders` được materialize dù output chỉ cần count và sum.  
**Why it happens:** `Include` dành cho loading related entities; aggregate projection có thể được translate thành SQL mà không cần hydrate collection.  
**Production impact:** Tăng allocation, tracking overhead và dữ liệu truyền.  
**Severity:** High  
**Recommended fix:** Bỏ `Include`; dùng projection trực tiếp từ navigation/query.

### 3. Tracking không cần thiết cho read-only dashboard

**Problem:** Query entity đang được tracking mặc định nếu context chưa cấu hình khác.  
**Why it happens:** Query entity thông thường dùng tracking behavior mặc định.  
**Production impact:** Change tracker giữ state cho lượng entity rất lớn, tăng memory/CPU.  
**Severity:** High  
**Recommended fix:** Với read-only entity query, dùng `AsNoTracking`; projection scalar/DTO đã giảm đáng kể nhu cầu tracking nhưng vẫn nên thiết kế rõ intent.

### 4. `Take(limit)` xảy ra trong memory

**Problem:** Giới hạn kết quả chỉ được áp dụng sau khi toàn bộ dữ liệu đã tải và aggregate trong process.  
**Why it happens:** Pipeline đã chuyển sang LINQ-to-Objects sau `ToListAsync`.  
**Production impact:** `limit=20` không cứu được DB/network/memory cost của hàng triệu rows.  
**Severity:** High  
**Recommended fix:** Áp dụng `OrderBy...Take(...)` trên `IQueryable` trước `ToListAsync`.

### 5. Keyword filtering trong process và semantics không portable sang SQL như đang viết

**Problem:** `Contains(keyword, StringComparison.OrdinalIgnoreCase)` hiện chạy trong memory vì materialization sớm. Nếu chỉ xóa `ToListAsync` rồi giữ nguyên expression, không nên giả định mọi provider sẽ translate overload này theo semantics mong muốn.  
**Why it happens:** .NET string semantics và database collation/case-sensitivity/provider translation không giống nhau một cách mặc định.  
**Production impact:** Hoặc client-side work như code hiện tại, hoặc translation/semantics khác kỳ vọng khi refactor thiếu kiểm chứng.  
**Severity:** High  
**Recommended fix:** Định nghĩa yêu cầu case sensitivity rõ ràng, dùng expression/provider strategy đã được kiểm chứng cho SQL Server/PostgreSQL, và integration-test cả hai provider nếu portability là requirement.

### 6. Không validate `limit`

**Problem:** Caller có thể truyền limit rất lớn, 0 hoặc âm.  
**Why it happens:** Service tin input.  
**Production impact:** Query/resource abuse hoặc contract không nhất quán.  
**Severity:** Medium  
**Recommended fix:** Clamp/validate, ví dụ 1–100 tùy requirement.

### 7. `fromUtc` không được validate/normalize theo contract

**Problem:** Tên biến nói UTC nhưng code không chứng minh `DateTime.Kind`, range hay business retention window.  
**Why it happens:** Temporal contract chưa rõ.  
**Production impact:** Query phạm vi quá rộng hoặc kết quả sai theo timezone convention.  
**Severity:** Medium  
**Recommended fix:** Dùng UTC convention rõ ràng; cân nhắc `DateTimeOffset`; validate range tối đa theo business requirement.

### 8. `Task.Delay(10)` không có mục đích và không nhận cancellation token

**Problem:** Artificial delay thêm latency; nếu request bị cancel thì delay vẫn chạy hết.  
**Why it happens:** Có thể là workaround/test code sót lại.  
**Production impact:** Lãng phí latency và giữ request operation lâu hơn cần thiết.  
**Severity:** Low  
**Recommended fix:** Xóa. Nếu delay thật sự có ý nghĩa thì truyền cancellation token.

## Phiên bản code đề xuất

```csharp
public sealed class DashboardService
{
    private readonly AppDbContext _db;

    public DashboardService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<IReadOnlyList<CustomerSummary>> GetCustomersAsync(
        string? keyword,
        DateTime fromUtc,
        int limit,
        CancellationToken cancellationToken)
    {
        if (limit is < 1 or > 100)
            throw new ArgumentOutOfRangeException(nameof(limit));

        if (fromUtc.Kind != DateTimeKind.Utc)
            throw new ArgumentException("fromUtc must be UTC", nameof(fromUtc));

        var query = _db.Customers
            .AsNoTracking()
            .Where(c => c.Orders.Any(o => o.CreatedAt >= fromUtc));

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            var normalizedKeyword = keyword.Trim();

            // Case-sensitivity semantics phải được định nghĩa và kiểm thử
            // theo database provider/collation thực tế.
            query = query.Where(c => c.Name.Contains(normalizedKeyword));
        }

        return await query
            .Select(c => new CustomerSummary
            {
                CustomerId = c.Id,
                Name = c.Name,
                OrderCount = c.Orders.Count(o => o.CreatedAt >= fromUtc),
                Revenue = c.Orders
                    .Where(o => o.CreatedAt >= fromUtc)
                    .Sum(o => (decimal?)o.TotalAmount) ?? 0m
            })
            .OrderByDescending(x => x.Revenue)
            .ThenBy(x => x.CustomerId)
            .Take(limit)
            .ToListAsync(cancellationToken);
    }
}
```

Đây là hướng thiết kế, không phải lời khẳng định rằng một SQL shape duy nhất tối ưu cho mọi provider/data distribution. Cần xem SQL được sinh ra và execution plan trên database thật. Với dataset lớn, có thể cân nhắc query bắt đầu từ `Orders`, aggregate theo `CustomerId`, sau đó join `Customers`; lựa chọn phụ thuộc cardinality, indexes và optimizer.

## Trade-offs

Một query aggregate lớn chạy hoàn toàn ở database giảm network và application memory nhưng có thể tăng CPU tại DB nếu access pattern/index không phù hợp. Nếu dashboard được gọi liên tục trên cùng cửa sổ dữ liệu, pre-aggregation/materialized summary/cache có thể tốt hơn, đổi lại có freshness và invalidation complexity.

Case-insensitive search là điểm portability quan trọng: SQL Server collation và PostgreSQL behavior có thể khác. Nếu sản phẩm thực sự hỗ trợ cả hai, abstraction không nên che mất semantic difference; integration test theo provider và cấu hình collation/index tương ứng.

## Cách kiểm thử

1. **Integration test:** seed customer/order ở trước và sau `fromUtc`; xác minh count/revenue chính xác, kể cả customer không có order trong window.
2. **SQL inspection test:** dùng EF Core logging/`ToQueryString()` trong môi trường phù hợp để xác nhận filter, aggregate, order và limit nằm trong SQL trước materialization.
3. **Load test:** so sánh p95/p99, allocations, process memory, DB CPU và rows transferred trước/sau với dataset production-like.
4. **Provider test:** chạy semantic tests cho keyword/case sensitivity trên SQL Server và PostgreSQL deployment configuration thực tế.
5. **Cancellation test:** cancel request khi DB query đang chạy; xác minh cancellation được propagate và request không tiếp tục xử lý vô ích.

## Quan sát trong production

- Metric: endpoint duration p50/p95/p99, request rate, error/cancellation rate và result count.
- Runtime: GC collections, allocation rate, heap size, working set và thread-pool signals để xác nhận memory symptom giảm.
- DB: query duration, CPU, logical reads/buffer activity, rows examined/returned, execution plan và index usage.
- Distributed trace: HTTP span → EF Core/database span, gắn operation name nhưng không đưa raw keyword nhạy cảm vào telemetry.
- Alert khi p95 vượt SLO, DB duration tăng mạnh hoặc memory/GC regress sau deployment.

## Câu hỏi phỏng vấn mở rộng

1. Nếu query SQL mới vẫn mất 5 giây dù chỉ trả 20 rows, bạn điều tra tiếp theo thứ tự nào?
2. Nếu dashboard chấp nhận dữ liệu trễ 1 phút, bạn có dùng Redis/cache hoặc bảng summary không? Cache key và invalidation sẽ thiết kế thế nào?
3. Nếu product owner yêu cầu contains-search case-insensitive giống hệt trên SQL Server và PostgreSQL, bạn làm thế nào để vừa đúng semantics vừa giữ indexability?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge hôm nay tập trung vào hai boundary mà Senior Backend Developer phải nhìn thấy rõ. Thứ nhất, authenticated không có nghĩa authorized: quyền phải được enforce ở server và thường phải xét cả resource/scope cụ thể; credential và PII không được lan vào log/response chỉ vì code làm được. Thứ hai, với EF Core cần xác định chính xác materialization boundary: trước `ToListAsync` thường là query expression có thể được provider translate, còn sau khi đã materialize collection thì các filter/aggregate tiếp theo chạy trong application memory.

## Mẫu tư duy cần nhớ

- Authentication trả lời “ai”, authorization trả lời “được làm gì trên resource nào”.
- Enforce security ở server; UI hiding không phải security boundary.
- Giảm dữ liệu càng sớm càng tốt: filter/project/aggregate/limit trước materialization.
- Không đoán SQL từ LINQ; xem generated SQL, execution plan và production telemetry.
- Treat observability as part of design, nhưng telemetry cũng phải tuân thủ least-privilege và data minimization.
