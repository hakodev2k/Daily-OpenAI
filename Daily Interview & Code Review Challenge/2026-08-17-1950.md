# Code Review Challenge 1 — EF Core `Include` nhiều collection làm query phình dữ liệu và timeout dưới tải

**Chủ đề:** EF Core query execution, tracking, SQL performance, memory/allocation, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API trả chi tiết project cho màn hình quản trị timesheet. Mỗi project có khoảng 100–300 nhân viên, 20–80 work item và hàng nghìn timesheet entry trong kỳ hiện tại.

API chạy trên 4 instance. Bình thường endpoint dưới đây mất 300–500 ms, nhưng cuối tháng có lúc tăng lên 8–15 giây. SQL Server ghi nhận lượng row trả về rất lớn, network giữa app và database tăng mạnh, memory process tăng, GC nhiều hơn và một số request timeout.

Team cho rằng “chỉ là một query nên chắc chắn nhanh hơn nhiều query”. Business chỉ cần một DTO tổng hợp để hiển thị project, thành viên, work item và 30 ngày timesheet gần nhất; không cần tracking để update trong request này.

## Đoạn code cần review

```csharp
public sealed class ProjectQueryService
{
    private readonly AppDbContext _db;

    public ProjectQueryService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<ProjectDetailsDto> GetAsync(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var project = await _db.Projects
            .Include(x => x.Members)
                .ThenInclude(x => x.Employee)
            .Include(x => x.WorkItems)
            .Include(x => x.TimesheetEntries)
                .ThenInclude(x => x.Employee)
            .SingleAsync(
                x => x.Id == projectId,
                cancellationToken);

        return new ProjectDetailsDto
        {
            Id = project.Id,
            Name = project.Name,
            Members = project.Members
                .Select(x => new MemberDto(
                    x.EmployeeId,
                    x.Employee.DisplayName))
                .ToList(),
            WorkItems = project.WorkItems
                .Select(x => new WorkItemDto(x.Id, x.Name))
                .ToList(),
            Timesheets = project.TimesheetEntries
                .Where(x => x.Date >= DateTime.UtcNow.Date.AddDays(-30))
                .OrderByDescending(x => x.Date)
                .Select(x => new TimesheetDto(
                    x.Id,
                    x.Employee.DisplayName,
                    x.Date,
                    x.Hours))
                .ToList()
        };
    }
}
```

## Kết quả code review tham khảo

### 1. Filter timesheet được áp dụng sau khi collection đã load toàn bộ

**Problem:** `Where(x => x.Date >= ...)` chạy trên collection đã materialize trong memory.  
**Why it happens:** `Include(x => x.TimesheetEntries)` tải navigation trước khi DTO mapping diễn ra.  
**Production impact:** Hàng nghìn hoặc hàng chục nghìn entry cũ vẫn được query, truyền qua network và materialize dù không dùng.  
**Severity:** High  
**Recommended fix:** Projection trực tiếp từ query và đưa điều kiện ngày vào SQL; hoặc dùng filtered include nếu thực sự cần entity graph.

### 2. Nhiều collection `Include` trong cùng query có thể tạo cartesian explosion

**Problem:** `Members`, `WorkItems` và `TimesheetEntries` đều là collection navigation.  
**Why it happens:** Join nhiều one-to-many collection có thể làm dữ liệu cha/con bị lặp nhiều lần trong result set.  
**Production impact:** SQL trả lượng row lớn hơn rất nhiều số entity logic, tăng DB CPU, I/O, network, materialization cost và latency.  
**Severity:** High  
**Recommended fix:** Ưu tiên projection theo DTO; nếu vẫn cần include nhiều collection, đánh giá `AsSplitQuery()` và đo thực tế.

### 3. Query read-only vẫn bật tracking mặc định

**Problem:** Entity graph được Change Tracker theo dõi dù request chỉ đọc.  
**Why it happens:** Không dùng `AsNoTracking()` hoặc projection DTO hoàn toàn.  
**Production impact:** Tăng memory, CPU và chi phí identity resolution/change tracking.  
**Severity:** High  
**Recommended fix:** Dùng `AsNoTracking()` cho read-only query, hoặc projection để tránh materialize entity không cần thiết.

### 4. Load entity graph trước rồi mới map DTO

**Problem:** Query lấy nhiều cột/navigation hơn output thực tế cần.  
**Why it happens:** Mapping diễn ra sau `SingleAsync`.  
**Production impact:** Tăng payload SQL, allocations và coupling giữa API shape với persistence model.  
**Severity:** High  
**Recommended fix:** `Select` trực tiếp thành DTO/query model với đúng field cần trả.

### 5. `DateTime.UtcNow.Date.AddDays(-30)` nằm trong phase mapping hiện tại

**Problem:** Mốc thời gian không được capture một lần trước query.  
**Why it happens:** Expression nằm trong thao tác LINQ-to-Objects sau materialization.  
**Production impact:** Ít nghiêm trọng về correctness, nhưng làm query khó kiểm soát/test và có thể tạo khác biệt nhỏ nếu logic phức tạp hơn.  
**Severity:** Medium  
**Recommended fix:** Tính `cutoff` một lần trước query bằng clock abstraction nếu cần test deterministic.

### 6. Không có giới hạn dữ liệu timesheet trả về ngoài 30 ngày

**Problem:** 30 ngày vẫn có thể chứa lượng entry rất lớn.  
**Why it happens:** API chưa xác định pagination/aggregation cho collection lớn.  
**Production impact:** Response lớn, serialization tốn CPU/memory, client render chậm.  
**Severity:** Medium  
**Recommended fix:** Làm rõ UI thực sự cần full list, aggregate hay pagination/cursor.

### 7. Không có query tagging/correlation cho truy vấn nóng

**Problem:** Khi endpoint chậm, khó nối request với SQL cụ thể.  
**Why it happens:** Thiếu tracing/query diagnostics phù hợp.  
**Production impact:** Điều tra production mất thời gian và dễ tối ưu sai query.  
**Severity:** Medium  
**Recommended fix:** Dùng tracing, request correlation và query tags khi phù hợp; quan sát duration, rows, reads và execution plan.

### 8. Giả định “một query luôn tốt hơn nhiều query” là sai về mặt thiết kế

**Problem:** Tối ưu theo round-trip count thay vì tổng cost.  
**Why it happens:** Không đo result cardinality, network payload và materialization.  
**Production impact:** Có thể khiến một query join khổng lồ đắt hơn vài query nhỏ có shape rõ ràng.  
**Severity:** Medium  
**Recommended fix:** So sánh bằng benchmark/load test và execution statistics, không chọn theo trực giác.

## Phiên bản code đề xuất

```csharp
public sealed class ProjectQueryService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public ProjectQueryService(
        AppDbContext db,
        TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task<ProjectDetailsDto> GetAsync(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var cutoff = _timeProvider
            .GetUtcNow()
            .UtcDateTime
            .Date
            .AddDays(-30);

        var project = await _db.Projects
            .AsNoTracking()
            .Where(x => x.Id == projectId)
            .Select(x => new ProjectDetailsDto
            {
                Id = x.Id,
                Name = x.Name,
                Members = x.Members
                    .OrderBy(m => m.Employee.DisplayName)
                    .Select(m => new MemberDto(
                        m.EmployeeId,
                        m.Employee.DisplayName))
                    .ToList(),
                WorkItems = x.WorkItems
                    .OrderBy(w => w.Name)
                    .Select(w => new WorkItemDto(w.Id, w.Name))
                    .ToList(),
                Timesheets = x.TimesheetEntries
                    .Where(t => t.Date >= cutoff)
                    .OrderByDescending(t => t.Date)
                    .ThenBy(t => t.Id)
                    .Select(t => new TimesheetDto(
                        t.Id,
                        t.Employee.DisplayName,
                        t.Date,
                        t.Hours))
                    .ToList()
            })
            .SingleAsync(cancellationToken);

        return project;
    }
}
```

Nếu generated SQL vẫn tạo join quá lớn cho provider/version/query shape thực tế, một lựa chọn rõ ràng hơn là tách thành 3–4 projection query nhỏ theo `projectId`, chạy tuần tự hoặc với các `DbContext` độc lập khi thật sự cần concurrency. Không nên chạy nhiều query song song trên cùng một `DbContext`.

## Trade-offs

Projection giảm dữ liệu thừa và tracking cost nhưng DTO query có thể phức tạp hơn. `AsSplitQuery()` giảm cartesian explosion nhưng tăng số round trip và cần cân nhắc consistency giữa các query nếu dữ liệu thay đổi giữa lúc đọc. Tách nhiều query thủ công cho phép kiểm soát shape tốt nhất nhưng tăng code và số lần truy cập DB. Với màn hình read-only, ưu tiên projection và đo bằng execution plan/telemetry trước khi quyết định.

## Bối cảnh

Một middleware được thêm để đo latency API. Team muốn biết endpoint nào chậm và user nào gặp lỗi nên gắn `UserId`, raw path, query string, status code và exception message vào metric labels.

Sau vài tuần, observability backend tăng chi phí mạnh. Metric ingestion bắt đầu bị throttle, dashboard chậm, exporter queue tăng và application process có thêm allocation/CPU trong giờ cao điểm. Một số query string chứa email, search keyword và token tạm thời. Team vẫn cần metrics hữu ích cho SLO và troubleshooting nhưng không được biến metrics thành nơi chứa dữ liệu có cardinality gần như vô hạn.

## Đoạn code cần review

```csharp
public sealed class ApiMetricsMiddleware
{
    private static readonly Meter Meter = new("Company.Api");
    private static readonly Histogram<double> Duration =
        Meter.CreateHistogram<double>("http.server.duration.ms");

    private readonly RequestDelegate _next;
    private readonly ILogger<ApiMetricsMiddleware> _logger;

    public ApiMetricsMiddleware(
        RequestDelegate next,
        ILogger<ApiMetricsMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? error = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            error = ex;
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started).TotalMilliseconds;
            var userId = context.User.FindFirst("sub")?.Value ?? "anonymous";
            var url = context.Request.Path + context.Request.QueryString;

            Duration.Record(
                elapsed,
                new KeyValuePair<string, object?>("user.id", userId),
                new KeyValuePair<string, object?>("url", url),
                new KeyValuePair<string, object?>("status", context.Response.StatusCode),
                new KeyValuePair<string, object?>("error", error?.Message ?? "none"));

            _logger.LogInformation(
                "Request {Url} by {UserId} finished in {Elapsed} ms with {Status}. Error={Error}",
                url,
                userId,
                elapsed,
                context.Response.StatusCode,
                error?.ToString());
        }
    }
}
```

## Kết quả code review tham khảo

### 1. `user.id` tạo high-cardinality metric dimension

**Problem:** Mỗi user có thể tạo một time series riêng.  
**Why it happens:** Metric label đang chứa định danh gần như unbounded.  
**Production impact:** Series count tăng theo số user, làm ingestion/storage/query tốn tài nguyên và có thể bị throttle.  
**Severity:** High  
**Recommended fix:** Không gắn `UserId` vào metric dimension dùng cho aggregate monitoring; giữ user identity trong trace/log khi thật sự cần và theo policy privacy.

### 2. Raw URL + query string tạo cardinality rất cao

**Problem:** `url` chứa path value và query parameter khác nhau theo request.  
**Why it happens:** Không chuẩn hóa theo route template.  
**Production impact:** Mỗi resource id/search query có thể sinh series mới.  
**Severity:** High  
**Recommended fix:** Dùng route/endpoint name hoặc route pattern có cardinality thấp; không đưa raw query string vào metric.

### 3. Query string có thể chứa dữ liệu nhạy cảm

**Problem:** Email, keyword, temporary token có thể xuất hiện cả metric và log.  
**Why it happens:** Telemetry ghi nguyên request target.  
**Production impact:** Tăng nguy cơ lộ PII/secret và mở rộng phạm vi dữ liệu cần bảo vệ.  
**Severity:** High  
**Recommended fix:** Không log query string mặc định; allowlist field an toàn hoặc redact/hash theo policy rõ ràng.

### 4. Exception message dùng làm metric label

**Problem:** `error?.Message` có cardinality không giới hạn và có thể chứa dữ liệu động.  
**Why it happens:** Metric bị dùng như log event.  
**Production impact:** Series explosion và có thể lộ dữ liệu từ exception text.  
**Severity:** High  
**Recommended fix:** Dùng error class/category ổn định, ví dụ exception type đã normalize hoặc outcome code; chi tiết exception để trong trace/log.

### 5. Log `error?.ToString()` cho mọi request lỗi có thể rất đắt và lộ dữ liệu

**Problem:** Full stack trace được serialize trong request middleware mà không có policy/sampling.  
**Why it happens:** Logging design chưa tách operational signal khỏi diagnostic detail.  
**Production impact:** Allocation, I/O và log volume tăng; exception data có thể chứa sensitive context.  
**Severity:** Medium  
**Recommended fix:** Dùng exception logging có cấu trúc tại error boundary phù hợp, sampling/rate control nếu cần, và redaction policy.

### 6. `status` nên là dimension ổn định nhưng tên/value nên chuẩn hóa

**Problem:** Dùng raw integer vẫn bounded nhưng cần convention nhất quán để query/dashboard dễ bảo trì.  
**Why it happens:** Instrumentation ad-hoc.  
**Production impact:** Không nghiêm trọng về cardinality nhưng dễ phân mảnh schema observability.  
**Severity:** Low  
**Recommended fix:** Chuẩn hóa theo semantic convention/team schema hiện tại, ví dụ status code hoặc status class.

### 7. Không có route-level outcome dimensions đủ hữu ích

**Problem:** Sau khi bỏ high-cardinality labels, metric hiện tại thiếu method/route/outcome ổn định để phân tích SLO.  
**Why it happens:** Thiết kế tập trung vào dữ liệu từng request.  
**Production impact:** Khó phát hiện endpoint cụ thể có p95/p99 hoặc error rate tăng.  
**Severity:** Medium  
**Recommended fix:** Ghi method, normalized route/endpoint name, status/outcome và duration; giữ tập dimensions nhỏ, bounded.

### 8. Telemetry overhead không được đo hoặc giới hạn

**Problem:** Không có quan sát exporter queue/drop/throttle hay cardinality budget.  
**Why it happens:** Observability được coi là “miễn phí”.  
**Production impact:** Hệ thống giám sát có thể tự gây CPU/allocation/network pressure cho application.  
**Severity:** Medium  
**Recommended fix:** Theo dõi exporter failures/drops/queue, series count, ingestion rate và chi phí; đặt telemetry budget.

## Phiên bản code đề xuất

```csharp
public sealed class ApiMetricsMiddleware
{
    private static readonly Meter Meter = new("Company.Api");
    private static readonly Histogram<double> Duration =
        Meter.CreateHistogram<double>("http.server.duration.ms");

    private readonly RequestDelegate _next;
    private readonly ILogger<ApiMetricsMiddleware> _logger;

    public ApiMetricsMiddleware(
        RequestDelegate next,
        ILogger<ApiMetricsMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? error = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            error = ex;
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started).TotalMilliseconds;
            var endpoint = context.GetEndpoint();
            var routeName = endpoint?.DisplayName ?? "unmatched";
            var method = context.Request.Method;
            var statusCode = context.Response.StatusCode;
            var outcome = error is null ? "success" : "error";
            var errorType = error?.GetType().Name ?? "none";

            Duration.Record(
                elapsed,
                new KeyValuePair<string, object?>("http.method", method),
                new KeyValuePair<string, object?>("http.route", routeName),
                new KeyValuePair<string, object?>("http.status_code", statusCode),
                new KeyValuePair<string, object?>("outcome", outcome),
                new KeyValuePair<string, object?>("error.type", errorType));

            if (error is not null)
            {
                _logger.LogError(
                    error,
                    "Request failed. Method={Method} Route={Route} Status={Status} TraceId={TraceId}",
                    method,
                    routeName,
                    statusCode,
                    context.TraceIdentifier);
            }
        }
    }
}
```

Trong production, nên ưu tiên instrumentation HTTP chuẩn từ framework/OpenTelemetry stack hiện có thay vì tự tạo toàn bộ schema nếu hệ thống đã có. Điểm chính của challenge là kiểm soát cardinality và tách đúng vai trò metric/trace/log.

## Trade-offs

Bỏ `UserId` và raw URL khỏi metrics làm giảm khả năng drill-down trực tiếp từ chart theo từng user, nhưng đổi lại metric ổn định, rẻ và có thể aggregate đúng. Khi cần điều tra từng request, dùng trace id để đi từ metric exemplar/trace sang log. Ghi exception type thay vì message giảm chi tiết nhưng giữ cardinality bounded. Nếu một business dimension như tenant tier thực sự hữu ích, chỉ thêm khi số giá trị nhỏ và được kiểm soát.

## Cách kiểm thử

1. Load test với hàng chục nghìn user/path/query khác nhau; so sánh số distinct metric series trước/sau.
2. Kiểm tra telemetry không chứa query token, email hoặc raw user id ngoài policy cho phép.
3. Đo CPU, allocations và exporter queue/drop rate dưới tải.
4. Integration test route matched/unmatched, 2xx/4xx/5xx và exception path.
5. Kiểm tra dashboard vẫn trả lời được câu hỏi SLO: endpoint nào chậm, error rate nào tăng, từ thời điểm nào.

## Quan sát trong production

Theo dõi metric-series cardinality, ingestion volume, exporter queue/drop/error, telemetry CPU/network overhead, application p95/p99 latency và log volume. Alert khi exporter drop/throttle tăng hoặc cardinality vượt budget. Dùng trace sampling có chủ đích cho request lỗi/chậm và đảm bảo redaction policy được áp dụng nhất quán.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ chọn dimensions nào cho một HTTP latency histogram production-grade?
2. Khi nào tenant id có thể chấp nhận được trong metric label, và khi nào tuyệt đối không nên dùng?
3. Nếu team vẫn cần tìm tất cả request của một user cụ thể, bạn sẽ thiết kế observability flow thế nào mà không đưa user id vào metric?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Một query EF Core duy nhất không đồng nghĩa với chi phí thấp; query shape, join cardinality, tracking, network payload và materialization mới là thứ cần đo.
- Filter và projection nên được đẩy xuống database càng sớm càng tốt cho read-heavy endpoint.
- Metrics phải có dimensions bounded; dữ liệu định danh và chi tiết động thuộc về trace/log phù hợp hơn.
- Observability cũng tiêu tốn CPU, memory, network và tiền; telemetry cần được thiết kế với budget và failure mode như một subsystem thật sự.

## Mẫu tư duy cần nhớ

- Measure query shape, không chỉ đếm số query.
- Push filtering/projection tới nơi dữ liệu được xử lý hiệu quả nhất.
- Low-cardinality cho metrics, request-level detail cho traces/logs.
- Treat telemetry overhead as production load.
- Tối ưu dựa trên execution evidence, không dựa trên trực giác.
