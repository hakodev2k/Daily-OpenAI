# Code Review Challenge 1 — Export ZIP chạy ổn với 20 files nhưng làm API tăng memory và đôi lúc tạo ZIP lỗi khi tải lớn

**Chủ đề:** C#/.NET, ASP.NET Core, async I/O, concurrency, streaming, memory, reliability, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một enterprise document portal có endpoint cho phép người dùng export toàn bộ files trong một folder thành một file ZIP.

Hệ thống chạy ASP.NET Core trên nhiều application instances. Metadata của files được đọc từ database; nội dung file được lấy qua một storage abstraction trỏ tới Azure Blob Storage.

Thông thường folder có 10–50 files, nhưng một số folder lớn có:

- 500–1.500 files;
- tổng dung lượng 1–4 GB;
- từng file có thể từ vài KB đến vài trăm MB;
- nhiều users có thể export cùng lúc vào cuối tháng.

Production bắt đầu xuất hiện các symptom:

- process memory tăng nhanh khi có nhiều export đồng thời;
- GC time tăng và request p99 của toàn service xấu đi, không chỉ riêng endpoint export;
- thỉnh thoảng client tải được ZIP nhưng giải nén báo archive corrupted;
- một export thất bại ở file thứ 200 khiến user phải chạy lại toàn bộ;
- storage dependency latency vẫn bình thường;
- CPU không phải bottleneck chính;
- team đề xuất tăng memory limit của container và tăng parallelism để export nhanh hơn.

Code hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/folders")]
public sealed class FolderExportController : ControllerBase
{
    private readonly IFolderRepository _folders;
    private readonly IFileStorage _storage;
    private readonly ILogger<FolderExportController> _logger;

    public FolderExportController(
        IFolderRepository folders,
        IFileStorage storage,
        ILogger<FolderExportController> logger)
    {
        _folders = folders;
        _storage = storage;
        _logger = logger;
    }

    [HttpGet("{folderId:guid}/export")]
    public async Task<IActionResult> Export(
        Guid folderId,
        CancellationToken cancellationToken)
    {
        var files = await _folders.GetFilesAsync(folderId, cancellationToken);

        using var output = new MemoryStream();
        using var archive = new ZipArchive(output, ZipArchiveMode.Create, leaveOpen: true);

        var tasks = files.Select(async file =>
        {
            var entry = archive.CreateEntry(file.FileName, CompressionLevel.Fastest);

            await using var input = await _storage.OpenReadAsync(
                file.StorageKey,
                cancellationToken);

            await using var entryStream = entry.Open();
            await input.CopyToAsync(entryStream, cancellationToken);

            _logger.LogInformation(
                "Added {FileName} to export {FolderId}",
                file.FileName,
                folderId);
        });

        await Task.WhenAll(tasks);

        archive.Dispose();

        return File(
            output.ToArray(),
            "application/zip",
            $"folder-{folderId}.zip");
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code này như một pull request chuẩn bị deploy production.

Bạn cần:

1. xác định các vấn đề correctness;
2. xác định các rủi ro performance/reliability dưới concurrency và load;
3. giải thích vì sao code có thể chạy tốt với folder nhỏ nhưng sụp khi nhiều export lớn chạy đồng thời;
4. ưu tiên finding theo severity;
5. đề xuất implementation/design tốt hơn;
6. nêu chiến lược testing;
7. nêu telemetry cần có để chứng minh fix hiệu quả trong production.

## Câu hỏi gợi mở

1. `ZipArchive` và các entry streams có được thiết kế để nhiều tasks ghi đồng thời vào cùng một archive hay không?
2. Một export 2 GB thực tế tạo ra bao nhiêu bản sao dữ liệu trong memory với `MemoryStream` + `ToArray()`?
3. `Task.WhenAll(files.Select(...))` tạo bao nhiêu concurrent storage reads nếu folder có 1.500 files?
4. Khi client disconnect ở giữa quá trình export, application có dừng toàn bộ work đủ sớm không?
5. Nếu streaming trực tiếp ra response và file thứ 200 thất bại, API còn có thể đổi response sang `ProblemDetails` như một request chưa gửi body hay không?

## Gợi ý

### Gợi ý 1

Rủi ro chính không nằm ở `CompressionLevel.Fastest`. Hãy nhìn vào **shared mutable archive + unbounded concurrency + full buffering**.

### Gợi ý 2

Hãy phân biệt hai bài toán: export nhỏ có thể stream trực tiếp trong request; export rất lớn có thể phù hợp hơn với một background job tạo artifact tạm thời rồi cho client download sau.

## Kết quả code review tham khảo

### Critical — Nhiều tasks cùng ghi vào một `ZipArchive`

**Vấn đề:**  
Mọi task gọi `archive.CreateEntry(...)` rồi mở entry stream và ghi đồng thời vào cùng một archive instance.

**Tại sao xảy ra:**  
`ZipArchive` là mutable container có cấu trúc central directory và state nội bộ. Code đang giả định việc tạo/ghi nhiều entries song song vào cùng archive là an toàn mà không có synchronization guarantee.

**Ảnh hưởng production:**  
Có thể tạo archive lỗi/corrupted, exception nondeterministic hoặc output không hợp lệ. Đây là lỗi correctness vì kết quả phụ thuộc timing và thường chỉ xuất hiện khi folder đủ lớn hoặc storage latency tạo interleaving khác nhau.

**Cách sửa:**  
Không ghi song song vào cùng `ZipArchive`. Cách đơn giản và an toàn là tạo từng entry và stream từng source file tuần tự vào archive. Nếu cần parallelism, chỉ parallelize các bước độc lập có bounded buffering rõ ràng; phần ghi archive vẫn phải được serialize.

---

### High — Toàn bộ ZIP được giữ trong `MemoryStream`

**Vấn đề:**  
Endpoint tạo toàn bộ archive trong memory trước khi gửi byte đầu tiên cho client.

**Tại sao xảy ra:**  
`MemoryStream` phải giữ toàn bộ compressed output. Khi archive lớn, backing buffer tăng theo kích thước ZIP.

**Ảnh hưởng production:**  
Một vài export lớn đồng thời có thể chiếm hàng GB memory, tạo allocation/GC pressure, container OOM hoặc làm latency của request khác tăng dù CPU/storage vẫn bình thường.

**Cách sửa:**  
Với export có kích thước phù hợp cho synchronous HTTP flow, stream ZIP trực tiếp ra `Response.Body` thay vì materialize toàn bộ archive trong memory. Với export rất lớn, cân nhắc asynchronous export job tạo file tạm ở Blob Storage rồi trả download URL khi hoàn tất.

---

### High — `output.ToArray()` tạo thêm một bản sao lớn của toàn bộ archive

**Vấn đề:**  
Sau khi đã có ZIP trong `MemoryStream`, `ToArray()` tạo một `byte[]` khác chứa toàn bộ dữ liệu.

**Tại sao xảy ra:**  
`File(byte[], ...)` yêu cầu mảng bytes, nên code copy toàn bộ buffer thêm một lần.

**Ảnh hưởng production:**  
Peak memory có thể cao đáng kể hơn kích thước archive thực tế. Với object lớn, áp lực lên GC/LOH tăng mạnh và nhiều concurrent exports khuếch đại vấn đề.

**Cách sửa:**  
Không chuyển archive thành `byte[]`. Stream output hoặc dùng pre-generated artifact trong storage.

---

### High — Unbounded fan-out tới storage dependency

**Vấn đề:**  
`files.Select(async ...)` tạo work cho tất cả files và `Task.WhenAll` cho phép hàng trăm hoặc hàng nghìn reads tồn tại đồng thời.

**Tại sao xảy ra:**  
Không có concurrency limit hoặc backpressure.

**Ảnh hưởng production:**  
Có thể làm tăng open connections/streams, socket usage, memory buffers, storage throttling và tail latency. Một export lớn có thể cạnh tranh tài nguyên với requests của users khác.

**Cách sửa:**  
Trong design streaming sequential ZIP, storage read tự nhiên bị bounded ở khoảng một file tại một thời điểm. Nếu có bước cần concurrency, dùng bounded concurrency theo measurement thay vì fan-out theo số files.

---

### High — Không có size/count guardrail cho synchronous export

**Vấn đề:**  
Endpoint xử lý 20 MB và 4 GB theo cùng một execution model.

**Tại sao xảy ra:**  
Không có giới hạn về số files, total expected bytes, thời gian chạy hoặc policy chuyển sang asynchronous export.

**Ảnh hưởng production:**  
Một request cực lớn có thể giữ connection và resources rất lâu, dễ bị client/network timeout, restart hoặc deployment interruption.

**Cách sửa:**  
Định nghĩa rõ threshold. Ví dụ: export nhỏ/trung bình có thể stream trực tiếp; export vượt file-count/size/time budget chuyển sang background job có progress/status và artifact TTL. Threshold phải dựa trên load test và SLO, không hard-code tùy ý mà không đo.

---

### Medium — Cancellation chưa chắc phản ánh đầy đủ client disconnect

**Vấn đề:**  
Method nhận `CancellationToken`, nhưng cần xác minh token đó có gắn với request abort semantics trong toàn call chain và storage abstraction có thực sự observe cancellation hay không.

**Tại sao xảy ra:**  
Một abstraction có thể nhận token nhưng dependency bên dưới bỏ qua nó. Ngoài ra, khi stream response, `HttpContext.RequestAborted` là signal quan trọng cần được propagate.

**Ảnh hưởng production:**  
Client đã đóng browser nhưng server vẫn tiếp tục đọc hàng GB từ storage và nén archive vô ích.

**Cách sửa:**  
Propagate request-abort cancellation xuyên suốt repository/storage/copy operations và kiểm thử thực tế bằng client disconnect. Với background export, cancellation semantics phải tách khỏi HTTP request lifecycle.

---

### Medium — Tên file từ dữ liệu được đưa trực tiếp vào ZIP entry

**Vấn đề:**  
`file.FileName` đi thẳng vào `CreateEntry`.

**Tại sao xảy ra:**  
Tên file có thể chứa path separators hoặc sequences như `../` nếu source metadata không được normalize theo policy.

**Ảnh hưởng production:**  
Archive có thể chứa entry names nguy hiểm cho consumer không xử lý extraction an toàn. Đây không nhất thiết khai thác trực tiếp server đang tạo ZIP, nhưng là output-security concern đáng xử lý ở boundary.

**Cách sửa:**  
Normalize/sanitize entry names về tên tương đối an toàn theo business rule, loại bỏ directory traversal semantics và xử lý duplicate names deterministically.

---

### Medium — Failure giữa stream không có recovery contract rõ ràng

**Vấn đề:**  
Nếu một source file fail, toàn request throw. Với full-buffer design hiện tại client chưa nhận response; với streaming design tương lai, response có thể đã bắt đầu.

**Tại sao xảy ra:**  
HTTP streaming không cho phép “quay lại” và thay body đã gửi bằng một JSON error response.

**Ảnh hưởng production:**  
Client có thể nhận archive bị cắt giữa chừng mà không hiểu file nào fail. Retry toàn bộ gây tốn băng thông/storage reads.

**Cách sửa:**  
Định nghĩa failure contract. Với synchronous streaming, abort response và có telemetry rõ. Với exports lớn/critical, background artifact generation cho phép chỉ publish artifact khi ZIP hoàn tất và checksum/validation thành công.

---

### Low — Per-file Information log tạo volume lớn và có thể lộ tên tài liệu

**Vấn đề:**  
Mỗi file ghi một `Information` log chứa `FileName`.

**Tại sao xảy ra:**  
Một export 1.500 files tạo 1.500 log events; concurrent exports nhân volume lên nhanh.

**Ảnh hưởng production:**  
Logging cost/volume tăng, signal-to-noise giảm và tên tài liệu có thể thuộc dữ liệu nhạy cảm tùy domain.

**Cách sửa:**  
Log aggregate ở export level: file count, total bytes, elapsed time, result, failure count. Per-file diagnostic chỉ bật có kiểm soát và theo policy dữ liệu.

## Phiên bản đề xuất

Một phiên bản đơn giản hơn cho export vừa phải là stream archive trực tiếp và ghi entries tuần tự:

```csharp
[ApiController]
[Route("api/folders")]
public sealed class FolderExportController : ControllerBase
{
    private readonly IFolderRepository _folders;
    private readonly IFileStorage _storage;
    private readonly ILogger<FolderExportController> _logger;

    public FolderExportController(
        IFolderRepository folders,
        IFileStorage storage,
        ILogger<FolderExportController> logger)
    {
        _folders = folders;
        _storage = storage;
        _logger = logger;
    }

    [HttpGet("{folderId:guid}/export")]
    public async Task Export(Guid folderId)
    {
        var ct = HttpContext.RequestAborted;
        var files = await _folders.GetFilesAsync(folderId, ct);

        ValidateExportBudget(files);

        Response.StatusCode = StatusCodes.Status200OK;
        Response.ContentType = "application/zip";
        Response.Headers.ContentDisposition =
            $"attachment; filename=\"folder-{folderId}.zip\"";

        var startedAt = Stopwatch.GetTimestamp();
        long sourceBytes = 0;
        var completedFiles = 0;

        try
        {
            using var archive = new ZipArchive(
                Response.Body,
                ZipArchiveMode.Create,
                leaveOpen: true);

            foreach (var file in files)
            {
                ct.ThrowIfCancellationRequested();

                var safeName = NormalizeZipEntryName(file.FileName);
                var entry = archive.CreateEntry(
                    safeName,
                    CompressionLevel.Fastest);

                await using var input = await _storage.OpenReadAsync(
                    file.StorageKey,
                    ct);

                await using var entryStream = entry.Open();
                await input.CopyToAsync(entryStream, ct);

                sourceBytes += file.SizeBytes;
                completedFiles++;
            }
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            _logger.LogWarning(
                "Folder export aborted. Folder={FolderId} CompletedFiles={CompletedFiles}",
                folderId,
                completedFiles);
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(startedAt);

            _logger.LogInformation(
                "Folder export finished. Folder={FolderId} Files={CompletedFiles}/{TotalFiles} " +
                "SourceBytes={SourceBytes} ElapsedMs={ElapsedMs}",
                folderId,
                completedFiles,
                files.Count,
                sourceBytes,
                elapsed.TotalMilliseconds);
        }
    }

    private static void ValidateExportBudget(IReadOnlyList<FileDescriptor> files)
    {
        // Thresholds should come from measured operational limits.
        // Large exports should be redirected to an asynchronous export workflow.
    }

    private static string NormalizeZipEntryName(string fileName)
    {
        var name = Path.GetFileName(fileName);
        return string.IsNullOrWhiteSpace(name) ? "file" : name;
    }
}
```

Nếu export vài GB là use case bình thường, design tốt hơn có thể là:

```text
POST /exports
        |
        v
Create export job
        |
        v
Background worker builds ZIP -> temporary Blob Storage
        |
        v
Validate artifact / checksum / metadata
        |
        v
GET /exports/{id} -> status + authorized download
```

HTTP request ban đầu khi đó ngắn, retry/recovery dễ kiểm soát hơn và client không cần giữ connection hàng chục phút.

## Giải thích thiết kế sau khi sửa

Điểm quan trọng nhất là bỏ ba nguồn amplification cùng lúc:

1. không concurrent-write vào shared `ZipArchive`;
2. không tạo unbounded parallel storage reads;
3. không materialize toàn bộ ZIP thành memory rồi copy lần nữa.

Streaming tuần tự có vẻ “ít parallel” hơn nhưng workload này thường bị giới hạn bởi storage/network/compression và cần bảo vệ toàn service, không phải tối đa throughput của một request duy nhất.

Nếu measurement cho thấy đọc storage tuần tự không đủ nhanh, không nên quay lại `Task.WhenAll` hàng nghìn files. Có thể thiết kế bounded prefetch nhỏ, nhưng phải giữ memory budget rõ và serialize archive writes. Complexity chỉ đáng thêm khi benchmark chứng minh bottleneck.

Streaming trực tiếp có một trade-off quan trọng: sau khi response bắt đầu, server không thể đổi thành clean `ProblemDetails` nếu file thứ N lỗi. Vì vậy large/long-running exports thường phù hợp hơn với artifact-generation workflow: chỉ đánh dấu job completed và cho download sau khi toàn ZIP hợp lệ.

Background export cũng cần production concerns riêng: idempotent job execution, concurrency quota per user/tenant, artifact TTL, cancellation, cleanup, authorization khi download, storage cost và progress telemetry.

## Trade-offs

- Streaming trực tiếp giảm memory rất mạnh và đơn giản, nhưng request sống lâu và mid-stream failure khó biểu diễn đẹp cho client.
- Background artifact generation tăng reliability/retryability cho file lớn, nhưng thêm queue/job state/storage lifecycle và UX polling/notification.
- Ghi ZIP tuần tự tránh corruption, nhưng một request đơn lẻ có thể chậm hơn so với aggressive parallel reads. Phải tối ưu theo system throughput và SLO, không chỉ stopwatch của một request.
- Compression cao hơn có thể giảm bandwidth nhưng tăng CPU; `Fastest` hay mức khác phải benchmark theo file types thực tế.
- Entry-name sanitization tăng safety nhưng cần rule xử lý duplicate filenames để không gây nhầm lẫn cho user.

## Cách kiểm thử

1. **Concurrency/load test:** chạy nhiều exports 500–1.500 files đồng thời, đo peak working set, allocation/GC, request p95/p99 và impact lên endpoint không liên quan.
2. **Archive correctness test:** tạo nhiều files với sizes/names khác nhau, export lặp lại dưới load và giải nén/verify checksum từng entry.
3. **Client-disconnect test:** hủy HTTP request giữa file lớn, xác minh storage reads/copy dừng sớm và resources được dispose.
4. **Failure-path test:** inject storage error ở file thứ N; xác minh synchronous stream bị abort có telemetry đúng, còn background mode không publish artifact incomplete.
5. **Security/input test:** filenames chứa `../`, path separators, Unicode edge cases và duplicate names phải tạo archive theo policy an toàn/deterministic.

## Quan sát trong production

Theo dõi ít nhất:

- active export count;
- export duration p50/p95/p99;
- source bytes và output bytes;
- files/export distribution;
- process working set, allocation rate, Gen 2/LOH/GC pause signals;
- request-abort count;
- storage dependency latency/error/throttling;
- export failure stage/file index;
- HTTP response aborted rate;
- nếu dùng background jobs: queue depth, job age, retries, completion/failure rate, artifact generation duration và cleanup failures.

Dashboard nên correlate concurrent exports với memory/GC và latency của toàn service để chứng minh export không còn gây noisy-neighbor effect.

## Câu hỏi phỏng vấn mở rộng

1. Nếu requirement bắt buộc một export 10 GB hoàn tất trong dưới 3 phút, bạn sẽ benchmark và thay đổi architecture nào trước khi tăng parallelism?
2. Nếu background worker có thể chạy lại cùng export job sau process restart, bạn sẽ thiết kế idempotency và artifact publication thế nào?
3. Khi nào bạn chấp nhận buffer toàn bộ response trong memory thay vì streaming?

# Code Review Challenge 2 — CMS preview component biến content hợp lệ thành stored XSS và làm access token trở thành mục tiêu

**Chủ đề:** React, TypeScript, ASP.NET Core integration, frontend security, XSS, token handling, redirect safety, defense in depth  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một marketing platform có React frontend và ASP.NET Core backend. Editors dùng CMS để nhập rich-text cho campaign pages.

Frontend có route preview dành cho authenticated employees. Backend trả về một HTML fragment đã được lưu trong CMS để editor xem trước trước khi publish.

Ứng dụng hiện lưu access token trong `localStorage` để gọi API. Team cho rằng route preview chỉ dùng nội bộ nên có thể render CMS HTML trực tiếp.

Gần đây security test cho thấy:

- editor account bị compromise có thể lưu một payload HTML/JavaScript vào content;
- khi một employee khác mở preview, script có thể chạy trong origin của application;
- application còn đọc `returnUrl` từ query string để điều hướng người dùng sau khi đóng preview;
- Content Security Policy hiện khá permissive vì legacy scripts;
- team đề xuất chỉ “escape `<script>` tag” ở frontend.

Code hiện tại:

## Đoạn code cần review

```tsx
import { useEffect, useState } from 'react';

interface PreviewResponse {
  title: string;
  html: string;
}

export function CampaignPreview({ campaignId }: { campaignId: string }) {
  const [preview, setPreview] = useState<PreviewResponse | null>(null);
  const [error, setError] = useState<string | null>(null);

  const params = new URLSearchParams(window.location.search);
  const returnUrl = params.get('returnUrl') ?? '/campaigns';
  const token = localStorage.getItem('access_token');

  useEffect(() => {
    fetch(`/api/campaigns/${campaignId}/preview`, {
      headers: {
        Authorization: `Bearer ${token}`
      }
    })
      .then(response => {
        if (!response.ok) {
          throw new Error(`Preview failed: ${response.status}`);
        }

        return response.json() as Promise<PreviewResponse>;
      })
      .then(setPreview)
      .catch(err => setError(String(err)));
  }, [campaignId, token]);

  if (error) {
    return <div>Could not load preview: {error}</div>;
  }

  if (!preview) {
    return <div>Loading...</div>;
  }

  return (
    <main>
      <h1>{preview.title}</h1>

      <section
        className="campaign-preview"
        dangerouslySetInnerHTML={{ __html: preview.html }}
      />

      <button onClick={() => { window.location.href = returnUrl; }}>
        Close preview
      </button>
    </main>
  );
}
```

## Nhiệm vụ của ứng viên

Hãy review component này trong bối cảnh production security.

Bạn cần:

1. xác định correctness/security problems;
2. giải thích trust boundary giữa CMS content, backend và browser;
3. giải thích vì sao stored XSS có thể biến token storage thành vấn đề lớn hơn;
4. đánh giá `returnUrl` handling;
5. ưu tiên các finding theo severity;
6. đề xuất implementation/design an toàn hơn;
7. nêu cách test và production telemetry phù hợp mà không log sensitive data.

## Câu hỏi gợi mở

1. “Editor đã authenticated” có đồng nghĩa HTML do editor nhập là trusted executable code không?
2. React mặc định escape text ở đâu, và `dangerouslySetInnerHTML` thay đổi boundary đó thế nào?
3. Nếu JavaScript chạy được trong cùng origin, dữ liệu nào trong `localStorage` trở thành accessible?
4. `returnUrl` có thể chứa scheme/host nào và browser sẽ xử lý `window.location.href` ra sao?
5. Sanitization nên gắn với business policy nào thay vì chỉ xóa chuỗi `<script>`?

## Gợi ý

### Gợi ý 1

Primary risk là **stored XSS tại rich-content trust boundary**. Hãy xem token/redirect/CSP là những lớp làm tăng hoặc giảm blast radius.

### Gợi ý 2

Sanitization đúng không phải regex tìm `<script>`. Hãy nghĩ theo **allowlist of permitted HTML semantics** và defense in depth.

## Kết quả code review tham khảo

### Critical — Render CMS HTML trực tiếp bằng `dangerouslySetInnerHTML` tạo stored-XSS boundary

**Vấn đề:**  
`preview.html` được đưa trực tiếp vào DOM như trusted HTML.

**Tại sao xảy ra:**  
React escape string khi render như text, nhưng `dangerouslySetInnerHTML` chủ động bypass lớp escaping đó. CMS rich text là dữ liệu do con người và integrations tạo ra; nó không tự động trở thành trusted code chỉ vì source là CMS.

**Ảnh hưởng production:**  
Nếu attacker có thể lưu payload qua compromised editor account, vulnerable integration hoặc validation bypass, JavaScript/HTML nguy hiểm có thể thực thi trong application origin khi employee mở preview. Từ đó attacker có thể gọi APIs dưới session context, đọc browser-accessible secrets/data, thay đổi UI hoặc exfiltrate information.

**Cách sửa:**  
Xác định explicit rich-text policy và sanitize bằng một proven HTML sanitizer/allowlist ở trust boundary phù hợp. Ưu tiên sanitize/normalize trước khi content được coi là publishable/renderable, có thể kết hợp server-side enforcement. Frontend vẫn phải treat returned HTML as untrusted unless contract bảo đảm đã sanitized theo versioned policy.

---

### High — Access token trong `localStorage` làm XSS blast radius lớn hơn

**Vấn đề:**  
Bearer token được lưu trong `localStorage` và đọc bởi JavaScript.

**Tại sao xảy ra:**  
Bất kỳ script nào chạy trong cùng origin có quyền truy cập `localStorage` theo browser security model.

**Ảnh hưởng production:**  
Stored XSS không chỉ thực hiện actions trong page mà còn có thể đọc/exfiltrate bearer token nếu token nằm ở browser-readable storage, mở rộng impact tùy token scope/lifetime.

**Cách sửa:**  
Đánh giá authentication architecture. Nếu phù hợp, dùng server-managed session/BFF hoặc secure `HttpOnly` cookie để token không trực tiếp accessible với JavaScript, đồng thời thiết kế CSRF protection phù hợp cho cookie-based auth. Nếu SPA bắt buộc dùng browser-held access token, giảm lifetime/scope và vẫn phải xử lý XSS như critical risk; token storage choice không thay thế sanitization.

---

### High — `returnUrl` chưa được validate trước navigation

**Vấn đề:**  
Giá trị query string được gán trực tiếp vào `window.location.href`.

**Tại sao xảy ra:**  
Client coi navigation target do caller cung cấp là trusted.

**Ảnh hưởng production:**  
Có thể tạo open-redirect behavior tới external origin hoặc scheme không mong muốn tùy browser/input handling. Điều này hữu ích cho phishing flows và có thể kết hợp với các vulnerability khác.

**Cách sửa:**  
Chỉ cho phép internal relative paths theo explicit rule, hoặc map một enum/known destination thay vì raw URL. Parse target và reject absolute/external/non-HTTP-safe schemes. Validation tương tự cũng phải có ở server nếu server dùng redirect parameter.

---

### High — “Xóa `<script>` tag” không phải sanitization đầy đủ

**Vấn đề:**  
Đề xuất của team tập trung vào một element cụ thể.

**Tại sao xảy ra:**  
HTML execution surface không chỉ nằm ở `<script>`. Event handlers, dangerous URL schemes, SVG/MathML behavior, malformed markup và browser parsing edge cases có thể vượt qua regex/string replacement đơn giản.

**Ảnh hưởng production:**  
Patch dễ tạo cảm giác đã fix nhưng vẫn exploitable.

**Cách sửa:**  
Dùng sanitizer được thiết kế cho HTML parsing và một allowlist cụ thể cho product: ví dụ cho phép `p`, `strong`, `em`, heading, list, safe links/images theo policy; loại bỏ event handlers, executable/unsafe URL schemes và unsupported elements/attributes.

---

### Medium — CSP permissive làm mất một lớp defense in depth

**Vấn đề:**  
Scenario cho biết CSP hiện cho phép legacy scripts khá rộng.

**Tại sao xảy ra:**  
Khi policy cho phép inline/eval/unrestricted script sources, browser có ít cơ hội chặn payload ngay cả khi sanitization có bug.

**Ảnh hưởng production:**  
XSS exploitability/blast radius có thể cao hơn. Tuy nhiên CSP không phải primary fix vì policy mạnh vẫn không nên được dùng thay thế output handling/sanitization.

**Cách sửa:**  
Lập kế hoạch siết CSP theo measurement: loại bỏ inline script dependencies dần, dùng nonce/hash khi phù hợp, hạn chế script sources và bật CSP reporting trước khi enforce thay đổi lớn.

---

### Medium — Không có explicit cancellation/lifecycle handling cho request preview

**Vấn đề:**  
Fetch không dùng `AbortController` khi component unmount hoặc `campaignId` đổi.

**Tại sao xảy ra:**  
Request cũ vẫn có thể hoàn thành sau khi component lifecycle đã thay đổi.

**Ảnh hưởng production:**  
Có thể tạo unnecessary network work hoặc stale UI edge case. Đây không phải security root cause chính và severity thấp hơn XSS/token issues.

**Cách sửa:**  
Abort request trong cleanup hoặc dùng data-fetching layer có cancellation/deduplication semantics. Không biến race này thành primary issue của security review.

---

### Medium — Error text hiển thị raw `Error` string không có user-safe contract

**Vấn đề:**  
UI hiển thị `String(err)` trực tiếp.

**Tại sao xảy ra:**  
Technical failure detail và user-facing error path bị trộn.

**Ảnh hưởng production:**  
Hiện tại message chủ yếu chứa status, nhưng pattern này dễ phát triển thành hiển thị backend/network details không phù hợp. React sẽ escape text nên đây không phải XSS tương đương với `dangerouslySetInnerHTML`.

**Cách sửa:**  
Hiển thị generic user message; gửi diagnostic detail vào structured telemetry phù hợp, không đưa tokens/content nhạy cảm vào logs.

---

### Medium — Authorization không thể được chứng minh từ frontend component

**Vấn đề:**  
Component có bearer token nhưng snippet không cho thấy backend kiểm tra employee có quyền preview `campaignId` cụ thể hay không.

**Tại sao xảy ra:**  
Frontend routing/UI visibility không phải security boundary.

**Ảnh hưởng production:**  
Nếu API chỉ kiểm tra “authenticated” mà không kiểm tra resource-level permission, attacker có thể enumerate campaign IDs. Tuy nhiên đây là điều **cần xác minh**, không được kết luận backend chắc chắn thiếu authorization từ snippet frontend.

**Cách sửa:**  
Review backend policy/resource authorization và test trực tiếp API với user roles khác nhau. Server phải enforce permission độc lập với UI.

---

### Low — Token string có thể trở thành `Bearer null`

**Vấn đề:**  
Nếu `localStorage` không có token, header vẫn được gửi là `Authorization: Bearer null`.

**Tại sao xảy ra:**  
Authentication state không được model rõ.

**Ảnh hưởng production:**  
Tạo unnecessary 401s, telemetry nhiễu và UX không rõ. Không phải vulnerability chính.

**Cách sửa:**  
Authentication layer phải quyết định trạng thái signed-in trước khi gọi API; không build raw authorization header trong individual component.

## Phiên bản đề xuất

Một hướng tốt hơn là component không tự xử lý raw bearer token và chỉ render HTML đã qua một explicit sanitization contract.

Ví dụ dưới đây giả định application có một API client/auth layer và backend trả `sanitizedHtml` theo policy đã định nghĩa:

```tsx
import { useEffect, useMemo, useState } from 'react';
import { api } from './apiClient';

interface PreviewResponse {
  title: string;
  sanitizedHtml: string;
}

function getSafeReturnPath(search: string): string {
  const value = new URLSearchParams(search).get('returnUrl');

  if (!value || !value.startsWith('/') || value.startsWith('//')) {
    return '/campaigns';
  }

  return value;
}

export function CampaignPreview({ campaignId }: { campaignId: string }) {
  const [preview, setPreview] = useState<PreviewResponse | null>(null);
  const [failed, setFailed] = useState(false);

  const returnPath = useMemo(
    () => getSafeReturnPath(window.location.search),
    []
  );

  useEffect(() => {
    const controller = new AbortController();

    setPreview(null);
    setFailed(false);

    api.getPreview(campaignId, { signal: controller.signal })
      .then(setPreview)
      .catch(error => {
        if (error.name !== 'AbortError') {
          setFailed(true);
        }
      });

    return () => controller.abort();
  }, [campaignId]);

  if (failed) {
    return <div>Không thể tải preview.</div>;
  }

  if (!preview) {
    return <div>Loading...</div>;
  }

  return (
    <main>
      <h1>{preview.title}</h1>

      <section
        className="campaign-preview"
        dangerouslySetInnerHTML={{ __html: preview.sanitizedHtml }}
      />

      <button onClick={() => window.location.assign(returnPath)}>
        Close preview
      </button>
    </main>
  );
}
```

Phần quan trọng nằm ở contract phía server/content pipeline, ví dụ về mặt design:

```text
CMS rich text input
      |
      v
Parse + sanitize against versioned allowlist
      |
      +--> reject/strip disallowed elements/attributes/URL schemes
      |
      v
Store or produce sanitized renderable representation
      |
      v
Authorized Preview API
      |
      v
Frontend renders only sanitized contract
```

Sanitization implementation cụ thể nên dùng một mature HTML parser/sanitizer phù hợp stack; không tự viết regex sanitizer.

## Giải thích thiết kế sau khi sửa

Điểm cốt lõi là định nghĩa trust boundary rõ:

- CMS editor là authenticated actor nhưng content họ nhập vẫn là untrusted input đối với browser execution context.
- Backend/API chịu trách nhiệm authorization và nên enforce content-safety contract trước khi data trở thành renderable HTML.
- Frontend không tự lấy token từ `localStorage` trong từng component. Authentication concern nên được centralize để refresh/error/session behavior nhất quán.
- `dangerouslySetInnerHTML` có thể vẫn tồn tại nếu rich-text requirement bắt buộc, nhưng chỉ sau explicit sanitization contract. Xóa API này khỏi component mà sau đó tự parse HTML bằng cách không an toàn không giải quyết root cause.

Về token storage, không có một câu trả lời tuyệt đối cho mọi SPA. Nếu architecture cho phép BFF/server session với secure `HttpOnly` cookie, XSS không thể đơn giản đọc bearer token từ `localStorage`; đổi lại cookie-based auth cần CSRF strategy và backend/session complexity. Nếu phải dùng SPA token model, primary defense vẫn là ngăn script injection và giới hạn token scope/lifetime.

Về redirect, `startsWith('/') && !startsWith('//')` là baseline minh họa cho internal-relative paths; production utility cần test encoding/normalization edge cases và có thể an toàn hơn nếu chỉ cho phép một set route names thay vì raw paths.

CSP là defense in depth. Team nên đo CSP violations/report-only, loại bỏ legacy inline dependencies rồi mới enforce stricter policy để tránh break production. CSP không thay thế sanitizer.

## Trade-offs

- Server-side sanitization tạo một policy trung tâm và dễ audit, nhưng cần xử lý legacy content khi policy version thay đổi.
- Sanitization lúc write giúp dữ liệu render nhanh/consistent nhưng có thể mất original input; nhiều hệ thống lưu cả source và sanitized projection với quyền truy cập khác nhau.
- Sanitization lúc read linh hoạt hơn khi policy đổi nhưng tăng runtime cost và có nguy cơ các consumer khác quên sanitize.
- BFF/HttpOnly-session model giảm exposure của bearer token với JavaScript nhưng thêm server/session/CSRF concerns.
- CSP nghiêm ngặt tăng defense nhưng legacy scripts có thể cần migration dần để tránh outage.

## Cách kiểm thử

1. **Security test — malicious rich text:** thử event handlers, dangerous URL schemes, SVG/HTML edge cases và xác minh output sau sanitization chỉ còn allowlisted semantics.
2. **Authorization integration test:** user không có quyền preview campaign phải bị từ chối ở API dù gọi trực tiếp không qua UI.
3. **Redirect test:** external absolute URLs, protocol-relative URLs, encoded inputs và safe internal paths phải cho kết quả đúng policy.
4. **Browser E2E test:** preview hợp lệ vẫn render rich formatting sau sanitization; malicious payload không execute và không tạo network call bất hợp lệ.
5. **CSP rollout test:** chạy report-only trước, theo dõi violations của legitimate application rồi siết policy mà không phá critical flow.

## Quan sát trong production

Theo dõi phù hợp gồm:

- preview API 401/403 rate;
- sanitization reject/strip counters theo rule category, không log raw malicious content nếu có thể chứa secrets/PII;
- CSP violation reports sau khi đã có endpoint/process xử lý an toàn;
- suspicious redirect validation failures;
- frontend error rate cho preview flow;
- authentication/session failures;
- security audit events cho content edit/publish/preview access nếu domain yêu cầu.

Không log access token, raw authorization header hoặc toàn bộ malicious HTML payload vào general application logs.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product bắt buộc cho editors nhúng một số trusted third-party widgets/scripts, bạn sẽ thiết kế policy và isolation thế nào thay vì mở toàn bộ HTML/JavaScript?
2. Nếu chuyển từ SPA bearer token sang BFF + `HttpOnly` cookie, những threat/control nào mới cần xem xét, đặc biệt là CSRF?
3. Nếu có nhiều consumer khác ngoài React frontend đọc cùng CMS rich text, bạn sẽ đặt sanitization ở đâu để tránh mỗi consumer tự triển khai một policy khác nhau?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async I/O không đồng nghĩa càng nhiều `Task` chạy song song càng tốt; shared mutable resources và dependency fan-out cần bounded concurrency/backpressure.
- Full buffering có thể biến một endpoint I/O-heavy thành nguồn memory/GC pressure ảnh hưởng toàn service; streaming phải được cân nhắc cùng failure semantics.
- Với long-running file generation, synchronous HTTP streaming và asynchronous artifact generation là hai design khác nhau, mỗi design có failure/retry/UX trade-off riêng.
- Rich text từ CMS vẫn là untrusted input đối với browser execution context; authentication của editor không làm HTML trở thành trusted code.
- XSS, browser-readable token storage, permissive CSP và unsafe redirects có thể kết hợp thành blast radius lớn hơn từng issue riêng lẻ.
- Security boundary phải được enforce ở server/content pipeline; frontend UI không phải authorization boundary.

## Mẫu tư duy cần nhớ

1. **Tìm resource amplification dưới load: concurrency × memory × dependency fan-out.**
2. **Thiết kế streaming cùng failure behavior, không chỉ cùng throughput.**
3. **Phân biệt authenticated actor với trusted executable content.**
4. **Đặt sanitization/authorization tại trust boundary, không vá từng component.**
5. **Đánh giá vulnerability theo chain và blast radius, không chỉ từng finding riêng lẻ.**
