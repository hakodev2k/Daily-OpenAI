# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi dưới tải

**Loại câu hỏi:** Internal mechanism trong tình huống production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, Change Tracker, query execution, performance diagnosis, observability

## Bối cảnh

Một ASP.NET Core API đọc danh sách nhân viên và trạng thái mailbox từ PostgreSQL. Sau một đợt refactor, endpoint vẫn trả dữ liệu đúng nhưng p95 tăng mạnh khi traffic cao. APM cho thấy số SQL command/request tăng, allocation tăng và DbContext giữ nhiều entity hơn trước. Đoạn application service xây dựng một `IQueryable<Employee>`, truyền qua vài helper để bổ sung filter, sau đó có nhiều bước gọi `CountAsync`, `ToListAsync` và truy cập navigation properties. Team cho rằng “LINQ query đã được tạo một lần nên database chỉ chạy một lần”.

Chưa rõ endpoint có bật lazy loading hay không, query có `Include`, projection hay `AsNoTracking`, và cùng một `DbContext` có xử lý bao nhiêu entity.

## Câu hỏi chính

Bạn sẽ giải thích cơ chế thực thi bên trong của `IQueryable`/EF Core như thế nào, tại sao endpoint có thể phát sinh nhiều SQL command và tăng memory dù chỉ “xây query một lần”, misconception nào đang tồn tại, rủi ro production là gì, và bạn sẽ chứng minh giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Query được enumerate bao nhiêu lần và ở những vị trí nào?
- Endpoint có lazy-loading proxies hoặc explicit loading không?
- Đây là read-only API hay entity sau đó còn được cập nhật?
- Số record và navigation cardinality trung bình/p95 là bao nhiêu?
- SQL command count, query duration và allocation thay đổi thế nào trước/sau refactor?

## Gợi ý tư duy

**Gợi ý 1:** Phân biệt việc xây expression tree với thời điểm query thực sự được thực thi.

**Gợi ý 2:** Xem xét deferred execution, nhiều terminal operation, Change Tracker, navigation loading và projection.

**Gợi ý 3:** Đừng tối ưu bằng cảm giác; đo SQL thực tế, số lần execute, rows returned, tracking overhead và query plan trước khi thay đổi thiết kế.

## Cấu trúc trả lời đề xuất

1. Xác nhận read/write semantics và cách query được consume.
2. Giải thích expression tree và deferred execution.
3. Liệt kê các điểm có thể tạo SQL riêng biệt.
4. Phân tích tracking, materialization và navigation loading.
5. Đề xuất projection/no-tracking/loading strategy phù hợp.
6. So sánh round-trip, payload, consistency và maintainability.
7. Đo trước/sau bằng logs, tracing và database metrics.
8. Kiểm thử correctness lẫn performance regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` mô tả query; việc tạo query không đồng nghĩa đã lấy dữ liệu.
- Các terminal operation như `CountAsync` và `ToListAsync` có thể tạo các database round-trip riêng.
- Enumerate lại query có thể thực thi lại query.
- Tracking có chi phí khi materialize entity; read-only query thường nên cân nhắc `AsNoTracking` hoặc projection.
- Navigation loading strategy có thể gây N+1 nếu thiết kế không phù hợp.

### Điểm cộng

- Dùng `Select` DTO để giảm columns/entities materialized.
- Phân biệt eager, explicit và lazy loading thay vì mặc định cho rằng `Include` luôn tốt.
- Quan sát generated SQL qua logging/APM và dùng `ToQueryString()` khi phân tích query shape.
- Kiểm tra query plan/index và rows scanned thay vì chỉ nhìn thời gian phía .NET.

### Nâng cao

- Nhận ra một query “ít round-trip hơn” chưa chắc tốt hơn nếu tạo Cartesian explosion hoặc payload rất lớn.
- Nêu consistency implication khi `Count` và `ToList` là hai query độc lập trong môi trường concurrent writes.
- Đặt performance budget và regression test cho query count/latency.

## Hướng giải quyết tham khảo

**Giả định:** endpoint chỉ đọc dữ liệu và không cần update các entity đã load.

`IQueryable` giữ expression tree cho đến khi một operation cần kết quả. Vì vậy `CountAsync()` và `ToListAsync()` trên cùng query thường là hai lần thực thi database riêng. Nếu query được enumerate thêm ở helper hoặc navigation được load riêng, command count tiếp tục tăng. Khi entity được materialize dưới tracking query, EF Core đưa chúng vào Change Tracker; điều này hữu ích cho update nhưng có overhead không cần thiết với nhiều read-only endpoint.

Tôi sẽ bắt đầu bằng SQL command logging/tracing theo request, so sánh command count và duration với phiên bản trước. Sau đó kiểm tra generated SQL, số rows, execution plan và navigation loading. Với endpoint read-only, tôi ưu tiên projection trực tiếp sang DTO và chỉ chọn columns cần thiết; cân nhắc `AsNoTracking`. Nếu cần total count cho pagination, chấp nhận hai query khi business cần exact total, hoặc thay đổi API contract nếu count quá đắt và UX không thực sự cần nó.

Không nên chữa N+1 bằng cách thêm `Include` vô điều kiện. Với quan hệ cardinality lớn, một join lớn có thể tăng duplication/payload; có thể cần projection hoặc split strategy sau khi đo. Nếu dữ liệu thay đổi giữa count và list là vấn đề nghiệp vụ, phải xác định consistency requirement và transaction/isolation phù hợp thay vì giả định hai kết quả luôn là snapshot duy nhất.

Test gồm integration test kiểm tra dữ liệu, performance test với dataset thực tế, command-count instrumentation và load test. Production theo dõi SQL duration, command count/request, rows returned, allocation/GC và endpoint p95/p99.

Khuyến nghị thay đổi nếu endpoint cần entity tracking để update trong cùng unit of work, hoặc consistency requirement bắt buộc một chiến lược transaction khác.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ xác nhận endpoint có thực sự read-only và query được enumerate ở đâu. Việc tạo `IQueryable` chỉ xây expression tree; nó chưa đồng nghĩa database đã chạy. Nếu code gọi `CountAsync` rồi `ToListAsync`, đó có thể là hai SQL command riêng, và enumerate lại sẽ chạy lại. Nếu lazy loading tồn tại thì navigation access còn có thể tạo N+1. Với tracking query, các entity materialized còn được giữ trong Change Tracker, nên dataset lớn sẽ tăng allocation và memory.

Tôi sẽ không sửa ngay bằng `Include` hay cache. Tôi sẽ bật SQL command telemetry theo request, xem generated SQL, rows returned và execution plan. Nếu đây là read-only endpoint, hướng mặc định của tôi là project trực tiếp sang DTO và cân nhắc `AsNoTracking`, đồng thời chỉ load navigation thực sự cần. Với pagination, tôi sẽ xác nhận business có cần exact total hay không vì count là một query riêng và có chi phí. Sau thay đổi tôi so sánh p95, command count/request, DB duration và allocation. Trade-off chính là giảm tracking/round-trip nhưng vẫn phải giữ correctness và tránh biến một N+1 thành một query join quá lớn.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTracking` không phải lựa chọn phù hợp?
2. Nếu `Include` loại bỏ N+1 nhưng query mới trả lượng dữ liệu lớn hơn rất nhiều, bạn xử lý thế nào?
3. Nếu product yêu cầu `totalCount` và page data phải nhất quán tuyệt đối trước concurrent writes, thiết kế của bạn thay đổi ra sao?

## Lỗi trả lời thường gặp

- Nói “LINQ luôn chạy in-memory” hoặc “IQueryable chỉ chạy một lần”.
- Mặc định mọi vấn đề đều giải quyết bằng `AsNoTracking` mà không xác nhận semantics.
- Chỉ nhìn code C# mà không kiểm tra SQL/query plan.
- Thêm `Include` hàng loạt mà bỏ qua cardinality và payload.
- Không đề xuất telemetry để xác nhận nguyên nhân.

## Thang điểm 0–10

- Requirement clarification: **1.5 điểm**
- Technical correctness: **2.5 điểm**
- Depth: **2 điểm**
- Trade-off analysis: **1.5 điểm**
- Production readiness: **1.5 điểm**
- Communication: **1 điểm**

# Câu 2 — Incident: Hangfire job gửi thông báo trùng sau deployment

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Incident response, Hangfire/background jobs, idempotency, database concurrency, reliability, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire để xử lý notification sau khi thay đổi lịch sự kiện. Sau deployment, một số người dùng nhận 2–3 email giống nhau. Dashboard cho thấy một số job được thực thi lại sau lỗi transient từ provider; đồng thời hệ thống đang chạy nhiều application instances. Database ghi nhận notification rows được tạo gần nhau cho cùng event/user. Không có bằng chứng chắc chắn rằng nguyên nhân duy nhất là retry.

Business yêu cầu giảm duplicate ngay vì email liên quan tới lịch họp quan trọng, nhưng không được làm mất notification hợp lệ. Provider bên ngoài có thể timeout sau khi đã nhận request.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ mitigation đến root cause và thiết kế phòng ngừa dài hạn như thế nào, đặc biệt khi không thể giả định job chỉ chạy đúng một lần hoặc timeout đồng nghĩa request chưa được provider xử lý?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate được định nghĩa theo event/user/version hay chỉ theo nội dung email?
- Job được enqueue ở đâu và transaction tạo business change có liên hệ gì với enqueue?
- Provider có hỗ trợ idempotency key hoặc message identifier không?
- Retry policy hiện tại và failure distribution là gì?
- Có nhiều producer hoặc scheduler cùng enqueue một logical notification không?

## Gợi ý tư duy

**Gợi ý 1:** Tách “job chạy nhiều lần” khỏi “business side effect xảy ra nhiều lần”.

**Gợi ý 2:** Điều tra cả producer, storage, retry, multi-instance concurrency và external provider ambiguity.

**Gợi ý 3:** Thiết kế một business idempotency boundary có persistent state; nếu cần đồng bộ DB change với việc phát work, cân nhắc transactional outbox.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius và business impact.
2. Giảm duplicate mà không dừng toàn bộ notification nếu có thể.
3. Thu thập correlation evidence xuyên suốt enqueue → job → provider.
4. Lập nhiều giả thuyết và kiểm chứng.
5. Xác định idempotency semantics.
6. Thiết kế short-term guard.
7. Thiết kế durable workflow/outbox nếu cần.
8. Test retry/concurrency/failure ambiguity.
9. Thiết lập SLO, metrics và alert.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định exactly-once execution.
- Immediate mitigation có kiểm soát, ví dụ giảm retry hoặc tạm gate loại notification bị ảnh hưởng sau khi đánh giá rủi ro.
- Correlation ID/business key xuyên producer, Hangfire job và provider.
- Persistent idempotency/deduplication dựa trên business semantics, không chỉ in-memory lock.
- Xử lý trường hợp timeout sau khi side effect đã xảy ra.

### Điểm cộng

- Unique constraint/index trên business idempotency key để database là guard cuối cùng.
- Outbox để tránh dual-write giữa business transaction và enqueue/publish.
- State machine như Pending/Sending/Sent/Failed/Unknown cùng attempt metadata.
- Reconciliation cho trạng thái “unknown”.

### Nâng cao

- Phân biệt deduplication ở producer, consumer/job và provider.
- Thiết kế retry theo loại lỗi, exponential backoff/jitter và poison handling.
- Không giữ DB transaction mở trong lúc gọi external provider.
- Định nghĩa metric duplicate rate theo logical notification ID.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định blast radius: loại notification nào, tenant/user nào, từ deployment nào, duplicate rate và liệu có notification bị mất. Mitigation có thể là giảm hoặc tạm dừng retry cho flow bị ảnh hưởng, hoặc bật dedupe guard trước provider; không nên tắt toàn bộ hệ thống nếu chưa cần thiết.

Tôi tạo một logical notification key, ví dụ `(EventId, RecipientId, EventVersion, NotificationType)`, rồi trace từ transaction tạo thay đổi, điểm enqueue, Hangfire job ID, attempt number đến provider request ID. Tôi kiểm tra nhiều giả thuyết: producer enqueue nhiều lần, recurring scheduler overlap, retry sau exception, multi-instance race, transaction rollback/enqueue mismatch, hoặc provider nhận request nhưng response bị timeout.

Fix bền vững là business operation phải idempotent. Lưu notification/outbox record có unique constraint trên logical key. Job nhận ID của record thay vì toàn bộ side effect intent. Nó đọc state và thực hiện state transition có concurrency control. Nếu provider hỗ trợ idempotency key, truyền logical ID đó. Nếu provider không hỗ trợ và timeout xảy ra sau send, local system không thể luôn biết chắc side effect đã xảy ra; cần trạng thái `Unknown`, provider lookup/webhook nếu có, hoặc reconciliation/business policy trước khi resend.

Nếu business data update và notification scheduling phải atomic, dùng transactional outbox: ghi business change + outbox trong cùng DB transaction; dispatcher publish/enqueue sau commit và đánh dấu processed idempotently. Đây không tạo “exactly once” toàn hệ thống, nhưng làm retry an toàn hơn.

Test bằng parallel execution cùng logical key, crash sau provider call nhưng trước local commit, provider 5xx, timeout, process restart và duplicate enqueue. Theo dõi duplicate logical notifications, retry count, age của pending/unknown records, provider latency/error và outbox backlog.

## Mẫu trả lời trong phỏng vấn

“Trước tiên tôi sẽ coi đây là incident về side-effect duplication chứ không chỉ là Hangfire retry. Tôi xác định blast radius và nếu duplicate đang tăng nhanh thì áp dụng guard hoặc giảm retry cho flow bị ảnh hưởng. Sau đó tôi trace cùng một logical notification từ producer tới Hangfire attempt và provider bằng business correlation key.

Tôi sẽ kiểm tra ít nhất bốn hướng: enqueue trùng, multi-instance race, retry sau lỗi, và timeout sau khi provider thực tế đã nhận email. Về thiết kế, tôi không dựa vào giả định job chỉ chạy một lần. Tôi tạo persistent notification/outbox record với unique key như event + recipient + version + type. Job xử lý record đó idempotently; nếu provider hỗ trợ idempotency key thì dùng cùng logical ID. Nếu business update và scheduling phải atomic, tôi dùng transactional outbox.

Trường hợp khó nhất là provider timeout sau khi side effect đã xảy ra. Nếu provider không hỗ trợ idempotency hoặc lookup, tôi sẽ biểu diễn trạng thái unknown và có reconciliation/policy thay vì resend mù. Cuối cùng tôi test parallel execution, retry, crash boundary và theo dõi duplicate rate, attempts, outbox backlog và unknown-state age. Mục tiêu là at-least-once processing nhưng business side effect an toàn khi bị lặp.”

## Câu hỏi đào sâu

1. Vì sao distributed lock một mình chưa đủ để đảm bảo không gửi email trùng?
2. Nếu provider không hỗ trợ idempotency key hoặc query trạng thái request, bạn chọn resend hay không resend thế nào?
3. Transactional outbox giải quyết vấn đề gì và không giải quyết vấn đề gì?

## Lỗi trả lời thường gặp

- Tắt toàn bộ retry và coi incident đã được giải quyết.
- Tin rằng Hangfire/distributed lock mang lại exactly-once side effect.
- Dùng Redis/in-memory flag mà không có durable business constraint.
- Giữ database transaction mở qua network call dài.
- Không xử lý ambiguous timeout.

## Thang điểm 0–10

- Requirement clarification: **1.5 điểm**
- Technical correctness: **2 điểm**
- Depth: **2 điểm**
- Trade-off analysis: **1.5 điểm**
- Production readiness: **2 điểm**
- Communication: **1 điểm**

# Câu 3 — Thiết kế AI code-review agent có quyền đọc repository và tạo đề xuất sửa code

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** AI agents, context engineering, tool permissions, deterministic validation, security, evaluation, auditability

## Bối cảnh

Team muốn xây một AI code-review agent cho repository .NET. Agent nhận pull request, đọc diff và các file liên quan, phát hiện correctness/security/performance issues, có thể chạy test hoặc static analysis trong môi trường cô lập, rồi tạo review suggestion. Giai đoạn sau có thể cho phép agent tạo commit sửa lỗi.

Repository có source code nội bộ, CI secrets không được lộ cho model, và PR có thể đến từ contributor bên ngoài. Nội dung source/comment/README là untrusted input. Team muốn giảm review time nhưng không chấp nhận agent tự ý merge hoặc thực thi lệnh tùy ý trên infrastructure production.

## Câu hỏi chính

Bạn sẽ thiết kế agent này thế nào để AI chỉ xử lý phần cần reasoning, phần nào phải deterministic, context/tool permissions được giới hạn ra sao, output được kiểm chứng thế nào, hallucination và prompt injection được phát hiện/giảm thiểu ra sao, chất lượng được đo thế nào, và fallback/audit flow là gì?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được tạo branch/commit? Có bao giờ được merge không?
- Repository size, ngôn ngữ và loại issue ưu tiên là gì?
- Latency/cost budget cho mỗi PR là bao nhiêu?
- Test/static-analysis environment có network access hay secrets không?
- False positive và false negative nào gây thiệt hại lớn hơn cho team?

## Gợi ý tư duy

**Gợi ý 1:** Tách reasoning khỏi authority; model không nên tự quyết định quyền mà nó được cấp.

**Gợi ý 2:** Xây context có provenance, typed tool interface, least privilege, sandbox và deterministic validation.

**Gợi ý 3:** Đánh giá bằng dataset PR/issues có ground truth, đo precision/usefulness/cost/latency và giữ human approval ở high-impact action.

## Cấu trúc trả lời đề xuất

1. Xác nhận mục tiêu và action boundary.
2. Threat-model input, tools, secrets và side effects.
3. Chia deterministic pipeline và LLM reasoning.
4. Thiết kế context retrieval/provenance.
5. Thiết kế tool schema và permission policy.
6. Validate structured output và evidence.
7. Chạy verification tools trong sandbox.
8. Human approval cho write/high-impact actions.
9. Offline + online evaluation.
10. Audit, fallback và incident handling.

## Ý chính của câu trả lời tốt

### Bắt buộc

- LLM không nhận raw production credentials/secrets.
- Source/PR text được coi là untrusted data, không phải instruction có authority.
- Tool permissions do host/policy layer kiểm soát, không phải prompt tự kiểm soát.
- Structured output phải được schema-validate và finding phải gắn với evidence/file/line khi có thể.
- Static analysis/tests/build là deterministic verification layer.
- Human approval trước commit/merge hoặc hành động có side effect đáng kể.

### Điểm cộng

- Read-only GitHub token hoặc scoped app permission cho review phase.
- Sandbox ephemeral, giới hạn filesystem/network/process/time/resources.
- Context budget ưu tiên diff, call sites, tests và project metadata thay vì dump toàn repo.
- Provenance cho mỗi context chunk và tool result.
- Confidence không được dùng như bằng chứng duy nhất.

### Nâng cao

- Threat model indirect prompt injection từ code/comments/docs/tool output.
- Policy enforcement ngoài model cho command allowlist, path scope và network egress.
- Evaluation dataset gồm known bugs, clean PRs và adversarial PRs.
- Canary rollout/shadow mode trước khi agent được phép post review tự động.

## Hướng giải quyết tham khảo

**Giả định:** MVP chỉ đọc PR và tạo draft review; không merge và không có production access.

AI phù hợp cho reasoning qua diff, tìm interaction khó nhận biết và giải thích trade-off. Các phần có thể xác định bằng compiler, formatter, analyzers, tests, secret scanning, dependency/security scanning và policy checks nên vẫn deterministic.

Pipeline có thể gồm: ingest PR metadata/diff → deterministic prechecks → context builder chọn file/call site/test liên quan → LLM tạo structured findings → verifier kiểm tra schema/evidence → sandbox chạy targeted build/tests/analyzers khi được phép → ranking/dedup → human reviewer duyệt hoặc agent đăng comment theo policy.

Context không nên là toàn repo. Mỗi chunk có source/path/commit SHA; secret files bị loại/redact theo policy. Nội dung code, comments và docs đều là dữ liệu không đáng tin cậy; instruction hierarchy và tool authorization nằm ở host. Tool interface là typed operations như `read_file(path, ref)`, `search_code(query)`, `run_test(target)` với path/command/network restrictions; không cấp generic shell nếu không cần.

Nếu sau này agent tạo patch, nó chỉ ghi vào workspace/branch cô lập. Patch phải build/test/analyze lại và cần human approval trước merge. Agent không tự tăng quyền. Audit log lưu model/config version, context references, tool calls, validation results, findings và approval decision nhưng phải tránh log secrets.

Hallucination được giảm bằng yêu cầu evidence, kiểm tra file/line tồn tại, deterministic tool verification và cho phép `insufficient_evidence`. Prompt injection được giảm bằng least privilege, data/instruction separation, sandbox và policy enforcement; không có biện pháp prompt-only nào đủ làm security boundary.

Evaluation dùng corpus PR đã review: precision của actionable findings, false-positive rate, recall trên known defects khi có ground truth, reviewer acceptance rate, time saved, latency và cost. Thêm adversarial tests chứa instruction độc hại trong comments/docs. Rollout từ offline → shadow → draft comments → limited auto-comment; write actions vẫn approval-gated.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ bắt đầu bằng action boundary: MVP chỉ đọc PR và tạo draft finding, không merge và không có production secrets. LLM chỉ dùng cho phần cần reasoning; compiler, analyzers, tests, schema validation và policy checks vẫn deterministic.

Tôi coi toàn bộ PR, source, comment và README là untrusted input vì chúng có thể chứa indirect prompt injection. Agent host mới là nơi quyết định quyền. Tool sẽ là typed operations với least privilege, ví dụ read file theo commit SHA, search code và chạy targeted test trong ephemeral sandbox; không cấp generic shell hoặc network nếu không cần. Context builder chỉ lấy diff, call sites, tests và metadata liên quan, kèm provenance.

Model trả structured findings gồm file, line, category, reasoning và evidence. Host validate schema, xác minh location, chạy analyzer/test khi có thể và cho phép model nói insufficient evidence. Nếu sau này agent tạo patch, patch chỉ nằm trên isolated branch, phải build/test lại và cần human approval trước merge.

Tôi đo chất lượng bằng known-bug/clean/adversarial PR dataset: precision, false positives, recall khi có ground truth, reviewer acceptance, latency và cost. Rollout theo shadow mode trước. Trade-off là context/tool verification tăng latency và cost, nhưng đổi lại giảm hallucination và blast radius; với code review có quyền truy cập repository, tôi ưu tiên bounded authority và auditability hơn autonomous execution.”

## Câu hỏi đào sâu

1. Nếu agent cần chạy `dotnet test` nhưng test project có thể chứa code độc hại từ PR, sandbox cần bảo vệ những gì?
2. Vì sao system prompt “hãy bỏ qua prompt injection” không đủ làm security control?
3. Team muốn agent tự commit để tiết kiệm thời gian; bạn sẽ đặt approval boundary ở đâu và vì sao?

## Lỗi trả lời thường gặp

- Cấp shell/GitHub write token rộng ngay từ MVP.
- Dump toàn repository vào context mà không xét relevance, privacy hoặc cost.
- Dùng confidence score của model như validation duy nhất.
- Cho rằng prompt instruction có thể thay thế sandbox/authorization.
- Chỉ đo số comment agent tạo thay vì usefulness và false positives.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hôm nay tập trung vào ba năng lực Senior/Architect khác nhau: hiểu chính xác deferred execution và tracking của EF Core; thiết kế background processing an toàn khi retry/concurrency khiến execution có thể lặp; và xây AI agent theo nguyên tắc reasoning không đồng nghĩa với authority. Điểm chung là không dựa vào assumption “chạy một lần”, “query một lần” hay “model sẽ tuân thủ prompt”, mà phải có cơ chế xác minh và boundary rõ ràng.

## Mẫu tư duy cần nhớ

- Phân biệt **description/execution**: query được xây không có nghĩa query đã chạy.
- Thiết kế **retry cùng idempotency**, không giả định exactly-once side effect.
- Khi incident xảy ra: **stabilize → collect evidence → test hypotheses → prevent recurrence**.
- Với AI agent: **reasoning capability ≠ permission**; authority phải được policy layer giới hạn.
- **Observability và deterministic verification là một phần của thiết kế**, không phải việc bổ sung sau cùng.
