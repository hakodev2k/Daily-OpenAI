# Code Review Challenge 1 — Race condition khi xử lý trạng thái đơn hàng bằng EF Core

**Chủ đề:** Concurrency, EF Core transaction, consistency
**Độ khó:** Senior
**Thời gian review đề xuất:** 35 phút
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một API xử lý thanh toán cho hệ thống thương mại điện tử. Khi payment provider gửi callback, backend cập nhật Order từ Pending sang Paid và tạo transaction record. Hệ thống chạy nhiều instance trên Azure App Service.

Triệu chứng production:
- Một số order bị tạo transaction duplicate.
- Có trường hợp inventory bị trừ hai lần.
- Không tái hiện được ở local.
- Log hiện tại chỉ ghi request id.

## Đoạn code cần review

```csharp
public async Task ConfirmPaymentAsync(Guid orderId, CancellationToken ct)
{
    var order = await _db.Orders
        .FirstAsync(x => x.Id == orderId, ct);

    if (order.Status == OrderStatus.Paid)
        return;

    order.Status = OrderStatus.Paid;

    await _db.PaymentTransactions.AddAsync(new PaymentTransaction
    {
        OrderId = orderId,
        CreatedAt = DateTime.UtcNow
    }, ct);

    await _inventoryService.ReserveAsync(order.ProductId, ct);
    await _db.SaveChangesAsync(ct);
}
```

## Nhiệm vụ của ứng viên

1. Xác định vấn đề correctness, concurrency và reliability.
2. Giải thích production impact.
3. Đề xuất thiết kế sửa lỗi.
4. Mô tả cách test và monitor.

## Câu hỏi gợi mở

- Điều gì xảy ra khi hai callback chạy cùng lúc?
- Transaction database bao phủ những thao tác nào?
- Operation này có idempotent không?

## Gợi ý

### Gợi ý 1
Tập trung vào race condition và atomic operation.

### Gợi ý 2
Xem xét optimistic concurrency, transaction boundary và idempotency key.

## Kết quả code review tham khảo

- Không có concurrency control. Severity: Critical. Hai request có thể cùng đọc Pending và cùng xử lý.
- Inventory update nằm ngoài transaction. Severity: High. Có thể xảy ra trạng thái không nhất quán.
- Không có idempotency handling. Severity: High.
- SaveChanges đặt sau external call. Severity: Medium.
- Logging thiếu business context. Severity: Medium.

## Phiên bản code đề xuất

Áp dụng idempotency key từ payment provider, transaction database cho state transition, optimistic concurrency token trên Order, và tách external side effect thành workflow có retry.

## Cách kiểm thử

- Hai callback đồng thời cho cùng order.
- Payment retry nhiều lần.
- Inventory service timeout.
- Database deadlock simulation.

## Quan sát production

- Log order id, payment id, correlation id.
- Metric duplicate callback.
- Trace transaction flow.

# Code Review Challenge 2 — BackgroundService xử lý queue gây memory leak và mất cancellation

**Chủ đề:** async/await, resource lifetime, background processing
**Độ khó:** Senior
**Thời gian review đề xuất:** 30 phút
**Số vấn đề cần tìm:** Khoảng 7 vấn đề

## Bối cảnh

Một worker ASP.NET Core đọc message RabbitMQ để xử lý gửi email. Khi traffic tăng, memory tăng dần và deployment shutdown kéo dài.

## Đoạn code cần review

```csharp
public class EmailWorker : BackgroundService
{
    private readonly IServiceProvider _provider;
    private readonly RabbitClient _client;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            var message = await _client.ReceiveAsync();

            using var scope = _provider.CreateScope();
            var sender = scope.ServiceProvider.GetRequiredService<IEmailSender>();

            _ = Task.Run(async () =>
            {
                await sender.SendAsync(message);
                await _client.AckAsync(message.Id);
            });
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Tìm lỗi về async, cancellation, resource lifetime và reliability.
2. Đánh giá khi chạy dưới load.
3. Đề xuất implementation tốt hơn.

## Câu hỏi gợi mở

- Có giới hạn số lượng task đang chạy không?
- Cancellation token được sử dụng ở đâu?
- Scope còn tồn tại khi background task chạy không?

## Gợi ý

### Gợi ý 1
Xem xét fire-and-forget trong worker.

### Gợi ý 2
Cần có bounded queue, controlled concurrency và graceful shutdown.

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

- Vòng lặp vô hạn bỏ qua cancellation. Severity: High.
- Fire-and-forget task không được quản lý. Severity: Critical.
- Scope dependency có thể bị dispose trước khi task hoàn thành. Severity: High.
- Không giới hạn concurrency gây memory pressure. Severity: High.
- Không xử lý exception trong task. Severity: Medium.

## Phiên bản code đề xuất

Dùng Channel<T> bounded, worker pool có giới hạn concurrency, truyền CancellationToken xuyên suốt, await tất cả processing task khi shutdown.

## Cách kiểm thử

- Shutdown khi đang xử lý message.
- RabbitMQ timeout.
- Email provider lỗi liên tục.
- Load test nhiều message đồng thời.

## Tổng kết hôm nay

## Kiến thức trọng tâm

- Concurrency cần được thiết kế, không chỉ xử lý bằng lock.
- External side effect cần idempotency.
- Background processing cần kiểm soát lifecycle và cancellation.
- Observability là một phần của production design.

## Mẫu tư duy cần nhớ

- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Stabilize before investigating.
- Treat observability as part of the design.
