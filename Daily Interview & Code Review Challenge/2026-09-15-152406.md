# Code Review Challenge 1 — ASP.NET Core proxy download giữ connection và buffer file lớn vào memory

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, streaming, CancellationToken, resource disposal, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một document API chạy trên Azure App Service cho phép người dùng tải file private từ Azure Blob Storage thông qua backend vì authorization được kiểm tra ở API. File thường 5–30 MB nhưng có thể tới 800 MB. Production chạy nhiều instances và giờ cao điểm có hàng trăm download đồng thời.

Sau khi traffic tăng, memory của process tăng nhanh, GC hoạt động nhiều hơn, request p99 tăng và đôi lúc instance restart. Application Insights cho thấy Blob dependency latency không tăng tương ứng. Team nghi ngờ implementation download nhưng chưa có profiling đủ để kết luận.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _logger = logger;
    }

    [HttpGet("{id:guid}/download")]
    public async Task<IActionResult> Download(
        Guid id,
        CancellationToken cancellationToken)
    {
        var document = await LoadDocumentAsync(id, cancellationToken);
        if (document is null)
            return NotFound();

        if (!UserCanRead(document))
            return Forbid();

        var blob = _container.GetBlobClient(document.BlobName);
        var response = await blob.DownloadStreamingAsync();

        using var memory = new MemoryStream();
        await response.Value.Content.CopyToAsync(memory);

        var bytes = memory.ToArray();

        _logger.LogInformation(
            "Downloaded {DocumentId} {FileName} size={Size}",
            id,
            document.FileName,
            bytes.Length);

        return File(
            bytes,
            document.ContentType,
            document.FileName);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/resource-lifetime problems.
2. Phân tích allocation/memory behavior khi nhiều file lớn được tải đồng thời.
3. Xác định cancellation propagation còn thiếu và ảnh hưởng khi client disconnect.
4. Ưu tiên findings theo production impact.
5. Đề xuất corrected design phù hợp private-file authorization mà không mặc định backend phải buffer toàn bộ file.
6. Nêu tests cho large file, concurrent downloads, cancellation và Blob failure.
7. Nêu telemetry/profiling cần dùng để chứng minh bottleneck.

## Câu hỏi gợi mở

1. Một file 800 MB tồn tại bao nhiêu bản copy trong managed memory ở happy path này?
2. Điều gì xảy ra với Blob stream khi client HTTP đã disconnect nhưng backend vẫn đang copy?
3. `DownloadStreamingAsync()` và `CopyToAsync()` đang nhận cancellation token ở đâu?
4. Backend có thực sự cần sở hữu toàn bộ byte array trước khi bắt đầu gửi response không?
5. Nếu chuyển sang direct Blob download bằng SAS, authorization và credential exposure cần thay đổi thế nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **buffering một payload lớn thành nhiều managed allocations** thay vì giữ pipeline dạng streaming.

### Gợi ý 2

Theo dõi ownership của từng resource và cancellation từ HTTP request xuống Blob operation; sau đó cân nhắc backend streaming so với short-lived SAS dựa trên security requirement.

## Kết quả code review tham khảo

### Critical — Toàn bộ file được buffer vào managed memory trước khi gửi

**Vấn đề:** Blob content được copy vào `MemoryStream`, sau đó `ToArray()` tạo thêm một byte array chứa toàn bộ file.

**Tại sao xảy ra:** Implementation biến một I/O streaming workload thành full-buffer workload. `MemoryStream` tăng capacity khi cần và `ToArray()` tạo bản sao độc lập.

**Ảnh hưởng production:** Với file hàng trăm MB và nhiều downloads đồng thời, working set/allocation pressure tăng mạnh, GC tốn thời gian và process có thể gặp memory pressure hoặc bị restart. Exact allocation phải được đo thay vì suy ra chỉ từ file size.

**Cách sửa:** Stream Blob content trực tiếp tới HTTP response hoặc trả stream-based `FileResult`; không materialize toàn bộ payload thành `byte[]` nếu không có requirement cần full buffering.

### High — Blob response/stream không được dispose rõ ràng

**Vấn đề:** `response.Value.Content` sở hữu network-backed stream nhưng code không thể hiện disposal lifetime.

**Tại sao xảy ra:** Resource lifetime bị che bởi response wrapper và action trả `byte[]` sau khi copy xong.

**Ảnh hưởng production:** Connection/resource release có thể bị trì hoãn, đặc biệt khi exception/cancellation xảy ra.

**Cách sửa:** Dùng `await using`/`using` theo type contract phù hợp và đảm bảo stream được dispose sau khi ASP.NET Core hoàn tất việc gửi, không dispose trước khi framework đọc xong.

### High — Cancellation không được propagate xuống Blob download/copy

**Vấn đề:** Action nhận `CancellationToken` nhưng Blob call và `CopyToAsync` không dùng token.

**Tại sao xảy ra:** Cancellation chain bị đứt sau metadata lookup.

**Ảnh hưởng production:** Client disconnect có thể vẫn khiến backend tải hàng trăm MB từ Blob và allocate memory vô ích, giữ bandwidth/connection/CPU lâu hơn.

**Cách sửa:** Truyền request cancellation vào Blob operation và stream copy API phù hợp. Với direct response streaming, gắn lifetime với `HttpContext.RequestAborted`/action token.

### High — Time-to-first-byte bị trì hoãn tới khi tải xong toàn bộ Blob

**Vấn đề:** Client không nhận file cho tới khi backend đã đọc hết Blob và tạo byte array.

**Tại sao xảy ra:** Full buffering tạo serialization point trước response body.

**Ảnh hưởng production:** Perceived latency và request duration tăng; backend giữ resources lâu hơn.

**Cách sửa:** Streaming response cho phép bắt đầu gửi sớm hơn khi headers/authorization đã xác định.

### Medium — Không có explicit handling cho Blob-not-found/race sau metadata authorization

**Vấn đề:** Database metadata có thể tồn tại nhưng Blob đã bị xóa/move hoặc storage tạm lỗi.

**Tại sao xảy ra:** Hai stores không có atomic consistency boundary.

**Ảnh hưởng production:** Storage exception có thể thành generic 500 và khó phân biệt permanent missing object với transient dependency failure.

**Cách sửa:** Phân loại storage failure; map missing Blob theo API contract, retry chỉ transient operation khi safe, và ghi dependency telemetry.

### Medium — Content metadata cần được coi là untrusted domain data

**Vấn đề:** `ContentType`/`FileName` đến từ metadata và được đưa vào HTTP response.

**Tại sao xảy ra:** Metadata có thể sai hoặc được tạo từ upload flow trước đó.

**Ảnh hưởng production:** Incorrect MIME/disposition behavior; tùy endpoint/browser context có thể tăng security risk.

**Cách sửa:** Validate/sanitize filename, dùng safe content-disposition behavior và policy MIME rõ. Download endpoint private thường nên ưu tiên attachment semantics khi phù hợp.

### Medium — Không có admission control hoặc capacity policy cho large downloads

**Vấn đề:** Hàng trăm large transfers có thể đồng thời chiếm outbound bandwidth và request slots/resources.

**Tại sao xảy ra:** Streaming giảm memory nhưng không loại bỏ bandwidth/concurrency cost.

**Ảnh hưởng production:** Instance saturation vẫn có thể xảy ra dưới traffic burst.

**Cách sửa:** Đo concurrency/bandwidth trước; nếu cần, dùng rate limiting/admission policy hoặc chuyển data plane sang Blob/CDN bằng scoped SAS trong khi backend giữ authorization control plane.

### Low — Logging filename có thể tạo cardinality/privacy concern

**Vấn đề:** Mỗi download log `FileName` và document ID ở Information level.

**Tại sao xảy ra:** Logging chưa có explicit privacy/cardinality policy.

**Ảnh hưởng production:** Log volume/cost tăng và filename có thể chứa business-sensitive text.

**Cách sửa:** Log structured identifiers tối thiểu cần thiết; review classification và sampling/metrics strategy.

## Phiên bản đề xuất

Một phương án giữ authorization tại API nhưng stream Blob qua backend:

```csharp
[HttpGet("{id:guid}/download")]
public async Task<IActionResult> Download(
    Guid id,
    CancellationToken cancellationToken)
{
    var document = await LoadDocumentAsync(id, cancellationToken);
    if (document is null)
        return NotFound();

    if (!UserCanRead(document))
        return Forbid();

    var blob = _container.GetBlobClient(document.BlobName);

    try
    {
        var download = await blob.DownloadStreamingAsync(
            cancellationToken: cancellationToken);

        var stream = download.Value.Content;

        return File(
            stream,
            document.ContentType,
            fileDownloadName: SanitizeFileName(document.FileName),
            enableRangeProcessing: true);
    }
    catch (RequestFailedException ex) when (ex.Status == StatusCodes.Status404NotFound)
    {
        return NotFound();
    }
}
```

Production implementation phải xác minh ownership/disposal behavior của stream với framework/version đang dùng và test cancellation thực tế. Nếu cần kiểm soát disposal chính xác hơn, có thể stream thủ công vào `Response.Body` trong action/service với `await using` và `CopyToAsync(..., cancellationToken)`.

Một alternative khác là backend authorize request rồi phát short-lived read-only SAS cho đúng Blob. Khi đó bytes đi trực tiếp Blob → client, giảm data-plane load trên API. SAS phải có thời hạn ngắn, scope tối thiểu, HTTPS và audit phù hợp; nếu policy không cho client thấy storage URL thì backend streaming vẫn hợp lý.

## Giải thích thiết kế sau khi sửa

Streaming giữ memory gần với buffer-size thay vì file-size và cho phép backpressure từ client/network tác động tự nhiên hơn. Cancellation phải đi xuyên từ request đến storage để client disconnect không tiếp tục tiêu tốn tài nguyên không cần thiết.

Direct SAS có thể giảm đáng kể API bandwidth/capacity requirement, nhưng đổi security boundary: backend quyết định quyền truy cập tại thời điểm cấp token, còn Blob phục vụ dữ liệu sau đó. Requirement về revocation, URL exposure và audit sẽ quyết định lựa chọn.

Không mặc định thêm Redis, queue hay Kubernetes; đây chủ yếu là data-transfer/resource-lifetime problem.

## Trade-offs

- Backend streaming giữ authorization/data path tập trung nhưng API vẫn chịu bandwidth và concurrent connection cost.
- SAS offload giảm API load nhưng thêm token-lifetime/revocation/security considerations.
- Range processing hữu ích cho resume/media-like access nhưng cần xác minh storage/framework behavior và authorization semantics.
- Admission control bảo vệ capacity nhưng có thể từ chối/queue user requests trong peak traffic.

## Cách kiểm thử

1. **Large-file integration test:** tải file lớn và xác nhận hash/length đúng trong khi memory không tăng tuyến tính bằng nhiều lần file size.
2. **Concurrency/load test:** nhiều downloads song song; đo working set, allocation rate, GC pause, request p95/p99 và outbound throughput.
3. **Cancellation test:** client abort giữa download; xác nhận storage transfer/request kết thúc sớm và resource được release.
4. **Dependency failure test:** Blob trả not-found/transient error; API mapping/retry behavior đúng contract.
5. **Security test:** unauthorized caller không nhận stream/SAS; filename/content-disposition được xử lý an toàn.

## Quan sát trong production

Theo dõi request concurrency, response size, p95/p99 duration, process working set, allocation rate, GC pause/collections và App Service restarts. Correlate với Application Insights Blob dependency duration/failure và HTTP client-abort/cancellation counts.

Nếu Blob dependency latency ổn nhưng process memory tăng cùng số concurrent downloads, heap/allocation profiling có thể chứng minh full buffering là bottleneck. Sau fix, kỳ vọng memory không còn tỷ lệ trực tiếp với tổng kích thước các file đang transfer, nhưng outbound bandwidth vẫn phải được theo dõi riêng.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào direct SAS tốt hơn backend streaming, và requirement nào khiến bạn từ chối SAS?
2. Nếu client rất chậm, streaming ảnh hưởng connection lifetime/capacity ra sao và bạn bảo vệ service thế nào?
3. Bạn sẽ chứng minh bằng metric/profile nào rằng memory pressure đến từ download buffering chứ không phải EF Core/cache hoặc leak khác?

# Code Review Challenge 2 — React auth state lưu access token trong localStorage và render HTML từ profile API

**Chủ đề:** React.js, TypeScript, authentication, XSS, token handling, API integration, frontend security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một React SPA gọi ASP.NET Core API dùng bearer access token. Team muốn giữ login qua refresh nên lưu access token vào `localStorage`. Profile API trả `displayName` và `bioHtml`; `bioHtml` ban đầu được tạo bởi internal editor nhưng sau một integration mới có thể chứa nội dung nhập từ hệ thống bên ngoài.

Security review phát hiện nếu attacker tìm được một XSS vector trong SPA thì token có thể bị đọc. Team cũng thấy component đôi khi update state sau khi user logout/navigation. Requirement chưa xác định SPA bắt buộc phải giữ bearer token trong browser storage hay có thể chuyển sang BFF/cookie architecture.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type Profile = {
  displayName: string;
  bioHtml: string;
};

export function ProfilePage() {
  const [profile, setProfile] = useState<Profile | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const token = localStorage.getItem("access_token");

    fetch("/api/profile", {
      headers: {
        Authorization: `Bearer ${token}`
      }
    })
      .then(async response => {
        if (!response.ok) {
          throw new Error(await response.text());
        }

        return response.json() as Promise<Profile>;
      })
      .then(data => setProfile(data))
      .catch(err => setError(String(err)));
  }, []);

  if (error) {
    return <div className="error">{error}</div>;
  }

  if (!profile) {
    return <div>Loading...</div>;
  }

  return (
    <main>
      <h1>{profile.displayName}</h1>
      <section
        dangerouslySetInnerHTML={{ __html: profile.bioHtml }}
      />
    </main>
  );
}
```

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — `bioHtml` được đưa trực tiếp vào `dangerouslySetInnerHTML`

**Vấn đề:** API-provided HTML được render như active markup mà không thấy sanitization contract.

**Tại sao xảy ra:** `dangerouslySetInnerHTML` bypass React text escaping. Khi source trở thành external/untrusted, malicious markup có thể đi vào DOM nếu không được sanitize đúng ngữ cảnh.

**Ảnh hưởng production:** XSS có thể thực thi trong origin của SPA, thao tác UI/API theo quyền user và đọc JavaScript-accessible secrets.

**Cách sửa:** Tốt nhất đổi contract thành structured/plain content và render bằng React escaping. Nếu business bắt buộc rich HTML, sanitize bằng một well-maintained sanitizer với explicit allowlist và test bypass cases; xác định rõ sanitize ở ingestion/server/render boundary, không dựa vào “internal source”.

### Critical — Bearer access token nằm trong `localStorage`

**Vấn đề:** Token có thể được JavaScript cùng origin đọc.

**Tại sao xảy ra:** `localStorage` được thiết kế cho script-accessible persistent storage.

**Ảnh hưởng production:** Khi XSS xảy ra, attacker có thể exfiltrate bearer token và sử dụng nó ngoài browser cho tới khi token hết hạn/revoked theo khả năng hệ thống.

**Cách sửa:** Trước mắt loại XSS và giảm token lifetime/scope theo identity design. Ở mức architecture, đánh giá BFF/server session hoặc secure `HttpOnly` cookie nếu phù hợp. Không tuyên bố cookie là universal fix: cần `Secure`, `SameSite`, CSRF protections và session lifecycle đúng.

### High — Authorization header được tạo ngay cả khi token null

**Vấn đề:** Code có thể gửi `Authorization: Bearer null`.

**Tại sao xảy ra:** Không có authenticated-state guard trước request.

**Ảnh hưởng production:** Request lỗi không cần thiết, telemetry nhiễu và UI state khó reasoning sau logout/token expiry.

**Cách sửa:** Auth layer nên quyết định request có credential hay redirect/refresh/re-auth theo contract; component không tự ghép token string từ storage.

### High — Request không được cancel khi component unmount hoặc auth state thay đổi

**Vấn đề:** Fetch tiếp tục và callbacks có thể chạy sau navigation/logout.

**Tại sao xảy ra:** Effect không có cleanup/`AbortController` và dependency không phản ánh auth session.

**Ảnh hưởng production:** Wasted network work, stale profile state và race với logout/session change.

**Cách sửa:** Dùng `AbortController` trong effect hoặc data-fetching abstraction có lifecycle cancellation; reset profile/error khi auth identity thay đổi.

### Medium — Raw response body bị biến thành UI error

**Vấn đề:** `response.text()` từ API được đưa vào `Error` rồi render cho user.

**Tại sao xảy ra:** UI không có stable error contract.

**Ảnh hưởng production:** Internal details có thể lộ; UX phụ thuộc backend payload. React sẽ escape string nên đoạn hiện tại không tự tạo HTML injection qua `{error}`, nhưng disclosure vẫn là concern.

**Cách sửa:** API dùng stable ProblemDetails/error code; UI map sang user-safe message và correlation ID.

### Medium — Component tự sở hữu authentication transport concern

**Vấn đề:** Feature component đọc token storage và xây Authorization header.

**Tại sao xảy ra:** Authentication/session ownership không được centralize.

**Ảnh hưởng production:** Token refresh/logout/error behavior dễ khác nhau giữa pages và khó test/security-review.

**Cách sửa:** Dùng authenticated API client/session abstraction; component chỉ yêu cầu profile data.

### Medium — Không có explicit response schema validation

**Vấn đề:** Type assertion `as Promise<Profile>` chỉ ảnh hưởng TypeScript compile-time, không validate JSON runtime.

**Tại sao xảy ra:** External API data được tin theo static type.

**Ảnh hưởng production:** Malformed/unexpected payload có thể gây UI behavior khó đoán; với HTML field, trust assumption càng nguy hiểm.

**Cách sửa:** Validate API contract ở boundary khi risk/complexity biện minh; quan trọng hơn, loại active HTML contract nếu không cần.

## Phiên bản đề xuất

Phương án đơn giản nhất là API trả plain text/structured content thay vì HTML và component dùng authenticated client. Ví dụ:

```tsx
import { useEffect, useState } from "react";

type Profile = {
  displayName: string;
  bio: string;
};

type Props = {
  api: {
    getProfile(signal: AbortSignal): Promise<Profile>;
  };
};

export function ProfilePage({ api }: Props) {
  const [profile, setProfile] = useState<Profile | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();

    setProfile(null);
    setError(null);

    api.getProfile(controller.signal)
      .then(data => {
        if (!controller.signal.aborted) {
          setProfile(data);
        }
      })
      .catch(error => {
        if (controller.signal.aborted) return;
        setError("Không thể tải profile. Vui lòng thử lại.");
      });

    return () => controller.abort();
  }, [api]);

  if (error) return <div className="error">{error}</div>;
  if (!profile) return <div>Loading...</div>;

  return (
    <main>
      <h1>{profile.displayName}</h1>
      <p>{profile.bio}</p>
    </main>
  );
}
```

Authenticated client có thể dùng in-memory access token + refresh/session flow hoặc BFF/cookie tùy architecture. Nếu dùng cookie session, browser gửi cookie tự động; server phải có CSRF strategy phù hợp cho state-changing requests. Nếu SPA vẫn cần bearer token, tránh persistent JavaScript-readable storage khi threat model cho phép và giữ token lifetime/scope tối thiểu.

Nếu rich text là requirement bắt buộc, sanitized HTML phải có explicit security boundary và test suite riêng; không thay `dangerouslySetInnerHTML` bằng một wrapper rồi coi vấn đề đã biến mất.

## Giải thích thiết kế sau khi sửa

React text rendering escape content mặc định, vì vậy đổi `bioHtml` thành `bio` loại bỏ một active-code boundary lớn. Authentication transport được đưa khỏi feature component để token refresh/logout/session policy có một owner duy nhất.

AbortController giải quyết lifecycle waste/race của request, nhưng cancellation không phải security control cho XSS. Hai vấn đề cần được xử lý độc lập: content trust và credential storage.

BFF/HttpOnly cookie có thể làm access token không còn đọc được từ browser JavaScript, giảm một hậu quả của XSS là token exfiltration. Tuy nhiên XSS vẫn có thể hành động như user trong browser, và cookie-based auth phải xử lý CSRF. Vì vậy architecture change không thay thế việc loại/sanitize XSS source.

## Trade-offs

- Plain text mất rich-format capability; structured rich text có thể là middle ground nhưng tăng renderer complexity.
- Sanitizer cho phép rich HTML nhưng cần maintenance và security regression tests.
- In-memory token giảm persistence nhưng refresh/navigation/session UX phức tạp hơn.
- BFF giảm token exposure ở SPA nhưng thêm server/session infrastructure và CSRF considerations.
- Central API client tăng abstraction nhưng giảm duplicated auth logic và làm telemetry/testing nhất quán hơn.

## Cách kiểm thử

1. **Security test:** profile chứa script/event-handler/unsafe URL payload; không có executable content chạy trong browser.
2. **E2E auth test:** logout trong lúc profile request đang pending; response cũ không restore authenticated UI/state.
3. **Integration test:** expired/401 response được auth layer xử lý theo contract, không gửi `Bearer null`.
4. **Contract test:** malformed profile response không được tin chỉ vì TypeScript type assertion.
5. **CSP/security regression test:** nếu hệ thống dùng CSP, xác minh policy hỗ trợ defense-in-depth nhưng không dùng CSP thay sanitization.

## Quan sát trong production

Không log access token, Authorization header hoặc raw `bio`. Theo dõi 401/403 rate, profile API latency/failure, auth refresh/session failures và frontend error events với correlation ID. CSP violation reports có thể là defense-in-depth signal nếu CSP được triển khai, nhưng phải xử lý privacy/noise.

Browser telemetry nên cho biết request aborted do navigation/logout, API error category và release version. Backend traces nên correlate profile request với authenticated subject identifier theo privacy policy, không ghi credential.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc rich HTML từ CMS, bạn đặt sanitization boundary ở ingestion, API hay browser và vì sao?
2. BFF + HttpOnly cookie giảm rủi ro nào và tạo thêm rủi ro/complexity nào so với SPA bearer token?
3. Nếu CSP đã rất chặt, bạn có bỏ sanitization cho `dangerouslySetInnerHTML` không? Vì sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào data-plane resource behavior: payload lớn nên được streaming thay vì materialize thành nhiều managed buffers, cancellation phải xuyên suốt dependency chain, và direct Blob access bằng scoped SAS là một architectural alternative cần đánh giá theo security requirement.

Challenge 2 tập trung vào browser trust boundary: React escaping chỉ bảo vệ khi dữ liệu được render như text; active HTML cần explicit sanitization. JavaScript-readable bearer credential làm hậu quả của XSS nghiêm trọng hơn, nhưng đổi sang cookie/BFF cũng không xóa XSS và cần xử lý CSRF/session semantics.

## Mẫu tư duy cần nhớ

- Với payload lớn, theo dõi **bytes đi qua đâu, được copy bao nhiêu lần và ai sở hữu lifetime**.
- Propagate cancellation qua toàn bộ I/O chain; client đã bỏ request thì backend không nên tiếp tục công việc đắt đỏ nếu có thể dừng an toàn.
- Xác định **trust boundary** trước khi render dữ liệu thành active HTML.
- Không xem credential storage là vấn đề tách rời XSS; threat model phải xét chuỗi khai thác hoàn chỉnh.
- Đo bằng telemetry/profile trước khi tối ưu hoặc thay architecture.
