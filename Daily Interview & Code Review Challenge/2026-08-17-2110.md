# Code Review Challenge 1 — ADO.NET streaming reader giữ connection quá lâu và rò tài nguyên khi client ngắt giữa chừng

**Chủ đề:** Resource lifetime và disposal, async/await và cancellation, database access, performance, error handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API export dữ liệu audit dưới dạng NDJSON để tránh giữ toàn bộ kết quả trong memory. Endpoint có thể stream từ vài nghìn tới vài triệu record.

Production ghi nhận:

- khi nhiều user export đồng thời, connection pool của database cạn dần,
- một số request đã bị client cancel nhưng query vẫn tiếp tục chạy,
- p99 latency của các API khác tăng dù CPU application không cao,
- thỉnh thoảng xuất hiện timeout khi mở connection mới,
- log chỉ ghi `Export failed` nhưng không biết request đã đọc được bao nhiêu row,
- restart process thì tình trạng tạm thời hết.

Business cho phép user cancel export bất kỳ lúc nào. Export không được làm các API transactional thiếu database connection.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditExportController : ControllerBase
{
    private readonly string _connectionString;
    private readonly ILogger<AuditExportController> _logger;

    public AuditExportController(
        IConfiguration configuration,
        ILogger<AuditExportController> logger)
    {
        _connectionString = configuration.GetConnectionString("AppDb")!;
        _logger = logger;
    }

    [Authorize]
    [HttpGet("export")]
    public async Task Export(DateTime from, DateTime to)
    {
        Response.ContentType = "application/x-ndjson";

        var connection = new SqlConnection(_connectionString);
        await connection.OpenAsync();

        var command = connection.CreateCommand();
        command.CommandText = """
            SELECT Id, UserId, Action, CreatedAt
            FROM AuditLogs
            WHERE CreatedAt >= @from AND CreatedAt < @to
            ORDER BY CreatedAt, Id
            """;
        command.Parameters.AddWithValue("@from", from);
        command.Parameters.AddWithValue("@to", to);

        var reader = await command.ExecuteReaderAsync();
        var count = 0;

        try
        {
            while (await reader.ReadAsync())
            {
                var item = new
                {
                    Id = reader.GetGuid(0),
                    UserId = reader.GetGuid(1),
                    Action = reader.GetString(2),
                    CreatedAt = reader.GetDateTime(3)
                };

                await JsonSerializer.SerializeAsync(
                    Response.Body,
                    item);

                await Response.Body.WriteAsync("\n"u8.ToArray());
                count++;
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Export failed after {Count} rows", count);
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không dispose `SqlConnection`, `SqlCommand` và `SqlDataReader`

**Problem:** Ba resource quan trọng được tạo nhưng không nằm trong `using`/`await using`.  
**Why it happens:** Endpoint dựa vào GC thay vì deterministic disposal.  
**Production impact:** Connection có thể không được trả về pool kịp thời, đặc biệt khi exception xảy ra; nhiều export đồng thời có thể làm pool cạn.  
**Severity:** Critical  
**Recommended fix:** Dùng `await using` cho connection/reader và `using` hoặc `await using` phù hợp cho command.

### 2. Không truyền request cancellation token

**Problem:** `OpenAsync`, `ExecuteReaderAsync`, `ReadAsync`, serialize và write không nhận `HttpContext.RequestAborted`.  
**Why it happens:** Cancellation không được propagate qua call chain.  
**Production impact:** Client disconnect nhưng database query và loop vẫn tiếp tục, giữ connection và tiêu tốn I/O vô ích.  
**Severity:** Critical  
**Recommended fix:** Truyền `RequestAborted` vào mọi API async hỗ trợ cancellation và xử lý `OperationCanceledException` như một đường thoát bình thường.

### 3. Catch mọi exception rồi nuốt lỗi

**Problem:** Endpoint log lỗi nhưng không rethrow hoặc set status khi response chưa bắt đầu.  
**Why it happens:** Error handling bị dùng như cơ chế “không làm request fail”.  
**Production impact:** Monitoring có thể ghi request như success; client nhận stream bị cắt mà không có signal rõ ràng.  
**Severity:** High  
**Recommended fix:** Chỉ xử lý cancellation riêng; các lỗi khác nên propagate tới middleware nếu response chưa start. Nếu response đã start, log outcome là aborted/failed và đóng stream.

### 4. Giữ database connection suốt toàn bộ thời gian client đọc

**Problem:** Tốc độ database bị gắn chặt với tốc độ network/client.  
**Why it happens:** Reader được stream trực tiếp ra response mà không có chunk boundary hay concurrency control.  
**Production impact:** Client chậm có thể giữ connection hàng phút, làm giảm pool capacity cho request khác.  
**Severity:** High  
**Recommended fix:** Giới hạn số export đồng thời; cân nhắc đọc theo page/chunk rồi giải phóng connection giữa các chunk nếu consistency requirement cho phép; với export rất lớn có thể tạo background export file.

### 5. Không có command timeout hoặc execution policy phù hợp

**Problem:** Query dài có thể chiếm resource quá lâu tùy cấu hình mặc định.  
**Why it happens:** Endpoint không định nghĩa timeout theo SLA export.  
**Production impact:** Slow query làm connection bị giữ lâu, tăng pool pressure.  
**Severity:** High  
**Recommended fix:** Đặt timeout có chủ đích và monitor timeout rate; timeout không thay thế query/index optimization.

### 6. `AddWithValue` có thể tạo parameter type không tối ưu

**Problem:** Kiểu parameter được suy luận thay vì chỉ định rõ.  
**Why it happens:** API tiện dụng được dùng ở query quan trọng.  
**Production impact:** Tùy schema/provider có thể ảnh hưởng plan reuse hoặc implicit conversion.  
**Severity:** Medium  
**Recommended fix:** Khai báo `SqlParameter` với kiểu dữ liệu phù hợp schema.

### 7. Serialize từng object với nhiều call nhỏ vào response

**Problem:** Mỗi row có một lần serialize và một lần write newline riêng.  
**Why it happens:** Không có buffering/chunking hợp lý.  
**Production impact:** Tăng syscall/flush pressure và overhead dưới hàng triệu row.  
**Severity:** Medium  
**Recommended fix:** Dùng buffer hợp lý, tránh flush mỗi row và benchmark với dữ liệu thật.

### 8. Không giới hạn date range hoặc số export đồng thời

**Problem:** Caller có thể yêu cầu khoảng thời gian cực lớn và chạy nhiều export cùng lúc.  
**Why it happens:** API chỉ nhận `from/to` mà không có admission control.  
**Production impact:** Một số user có thể chiếm phần lớn connection pool và I/O database.  
**Severity:** High  
**Recommended fix:** Validate range, quota/concurrency theo user/tenant và chuyển export cực lớn sang job bất đồng bộ.

### 9. Observability chưa đủ để phân biệt slow DB, slow client và cancellation

**Problem:** Chỉ log số row tại exception.  
**Why it happens:** Không instrument theo từng phase.  
**Production impact:** Khó xác định pool exhaustion do query, network hay user abort.  
**Severity:** Medium  
**Recommended fix:** Track duration DB open/query/read/write, rows exported, cancellations, active exports và pool-related errors.

## Phiên bản code đề xuất

```csharp
[Authorize]
[HttpGet("export")]
public async Task Export(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    if (to <= from || to - from > TimeSpan.FromDays(31))
    {
        Response.StatusCode = StatusCodes.Status400BadRequest;
        return;
    }

    Response.ContentType = "application/x-ndjson";

    await using var connection = new SqlConnection(_connectionString);
    await connection.OpenAsync(cancellationToken);

    await using var command = connection.CreateCommand();
    command.CommandText = """
        SELECT Id, UserId, Action, CreatedAt
        FROM AuditLogs
        WHERE CreatedAt >= @from AND CreatedAt < @to
        ORDER BY CreatedAt, Id
        """;
    command.CommandTimeout = 60;
    command.Parameters.Add(new SqlParameter("@from", SqlDbType.DateTime2) { Value = from });
    command.Parameters.Add(new SqlParameter("@to", SqlDbType.DateTime2) { Value = to });

    await using var reader = await command.ExecuteReaderAsync(
        CommandBehavior.SequentialAccess,
        cancellationToken);

    var count = 0;

    try
    {
        while (await reader.ReadAsync(cancellationToken))
        {
            var item = new
            {
                Id = reader.GetGuid(0),
                UserId = reader.GetGuid(1),
                Action = reader.GetString(2),
                CreatedAt = reader.GetDateTime(3)
            };

            await JsonSerializer.SerializeAsync(
                Response.Body,
                item,
                cancellationToken: cancellationToken);

            await Response.Body.WriteAsync("\n"u8, cancellationToken);
            count++;
        }

        _logger.LogInformation(
            "Audit export completed with {Count} rows",
            count);
    }
    catch (OperationCanceledException)
        when (cancellationToken.IsCancellationRequested)
    {
        _logger.LogInformation(
            "Audit export cancelled after {Count} rows",
            count);
        throw;
    }
}
```

> Giả định export tối đa 31 ngày là một policy ví dụ. Giá trị thực tế phải dựa trên dữ liệu, SLA và nhu cầu business. Với export rất lớn hoặc client chậm, background export sang object storage thường phù hợp hơn việc giữ connection HTTP + database trong thời gian dài.

## Trade-offs

- Streaming trực tiếp giảm memory và thời gian chờ trước byte đầu tiên, nhưng giữ database connection lâu hơn.
- Chunked pagination giải phóng connection giữa các batch nhưng phải quyết định consistency semantics nếu dữ liệu thay đổi trong lúc export.
- Background export tăng kiến trúc và storage cost nhưng cô lập workload tốt hơn, dễ retry và kiểm soát concurrency.
- Command timeout giúp giới hạn failure duration nhưng không phải giải pháp cho query/index kém.

## Cách kiểm thử

1. **Cancellation integration test:** Client đọc vài trăm row rồi ngắt kết nối; verify query dừng và connection được trả về pool.
2. **Failure-path test:** Ép `Response.Body` ném lỗi hoặc database timeout; verify resource được dispose.
3. **Load test:** Chạy nhiều export song song cùng traffic API bình thường; theo dõi pool wait và p99 latency.
4. **Range validation test:** Request khoảng thời gian vượt policy phải bị từ chối trước khi mở connection.
5. **Large dataset test:** Export hàng triệu row và đo allocation, throughput, duration giữ connection.

## Quan sát trong production

- Metric: active exports, rows exported, export duration, cancellations, failures, database connection-open latency.
- Trace: span riêng cho open connection, execute query và stream response.
- Log structured: export id, actor/tenant, range, row count, outcome; không log raw audit content.
- Alert khi active exports hoặc connection-open latency tăng vượt baseline.
- Theo dõi database wait statistics, pool timeout và long-running query.

# Code Review Challenge 2 — Cancellation bị biến thành lỗi 500 và retry middleware vô tình retry cả request không an toàn

## Bối cảnh

Một ASP.NET Core API có custom middleware để “tăng độ ổn định”: mọi exception sẽ được retry tối đa 3 lần rồi trả lỗi chuẩn hóa.

Sau khi deploy, production ghi nhận:

- client bấm Cancel nhưng server vẫn tiếp tục chạy thêm vài giây,
- một số POST tạo order bị tạo trùng record,
- dashboard lỗi 500 tăng mạnh khi mobile network chập chờn,
- log có ba stack trace giống nhau cho cùng một request,
- downstream timeout gây request giữ resource lâu hơn dự kiến,
- team khó phân biệt client-cancel, timeout và lỗi thật.

Business yêu cầu request bị client hủy phải dừng sớm. Retry chỉ được dùng khi operation thật sự an toàn để retry.

## Đoạn code cần review

```csharp
public sealed class RetryAndErrorMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RetryAndErrorMiddleware> _logger;

    public RetryAndErrorMiddleware(
        RequestDelegate next,
        ILogger<RetryAndErrorMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                await _next(context);
                return;
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Request failed on attempt {Attempt}",
                    attempt);

                if (attempt < 3)
                {
                    await Task.Delay(500);
                    continue;
                }

                context.Response.StatusCode = 500;
                await context.Response.WriteAsJsonAsync(new
                {
                    error = "unexpected_error",
                    detail = ex.Message
                });
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Retry toàn bộ request pipeline có thể lặp side effect

**Problem:** `_next(context)` được gọi lại cho cùng POST/PUT khi exception xảy ra.  
**Why it happens:** Middleware không biết operation trước đó đã commit database hoặc gọi downstream thành công một phần hay chưa.  
**Production impact:** Tạo duplicate order, duplicate message hoặc external side effect.  
**Severity:** Critical  
**Recommended fix:** Không retry toàn pipeline. Retry phải đặt quanh dependency operation cụ thể và chỉ khi idempotency/failure semantics cho phép.

### 2. Cancellation bị bắt như exception thông thường

**Problem:** `OperationCanceledException`/`TaskCanceledException` đi vào catch chung.  
**Why it happens:** Middleware không phân biệt request cancellation với lỗi ứng dụng.  
**Production impact:** Client đã rời đi nhưng server vẫn retry, giữ thread/resource và tăng 500 giả.  
**Severity:** High  
**Recommended fix:** Khi `context.RequestAborted.IsCancellationRequested`, propagate cancellation và không retry/log như application error.

### 3. Delay giữa retry không nhận cancellation token

**Problem:** `Task.Delay(500)` luôn chờ đủ thời gian.  
**Why it happens:** Không truyền `RequestAborted`.  
**Production impact:** Tăng latency và giữ request sống sau khi client disconnect.  
**Severity:** High  
**Recommended fix:** Nếu retry ở layer phù hợp, delay phải nhận cancellation token.

### 4. Có thể retry sau khi response đã bắt đầu

**Problem:** Middleware không kiểm tra `context.Response.HasStarted`.  
**Why it happens:** Giả định exception luôn xảy ra trước khi response được ghi.  
**Production impact:** Response có thể bị corrupt hoặc ném thêm exception khi attempt sau cố ghi lại headers/body.  
**Severity:** High  
**Recommended fix:** Error middleware phải kiểm tra `HasStarted`; nếu đã start thì log và rethrow/abort connection theo framework behavior.

### 5. Trả `ex.Message` trực tiếp cho client

**Problem:** Nội dung exception nội bộ bị expose.  
**Why it happens:** Dùng exception message làm API detail.  
**Production impact:** Có thể lộ schema, host, SQL, file path hoặc thông tin downstream.  
**Severity:** High  
**Recommended fix:** Trả error code/message an toàn; chi tiết giữ trong server logs có access control.

### 6. Retry mọi exception không phân loại transient/permanent

**Problem:** Validation bug, authorization bug, programming error đều bị retry.  
**Why it happens:** `catch (Exception)` không có policy.  
**Production impact:** Tăng tải đúng lúc hệ thống đang lỗi và che nguyên nhân thật.  
**Severity:** High  
**Recommended fix:** Retry chỉ lỗi transient đã xác định ở dependency boundary, với giới hạn, backoff và jitter phù hợp.

### 7. Log cùng exception ở mỗi attempt gây noise

**Problem:** Mỗi failure được log `Error` riêng.  
**Why it happens:** Retry policy và final error logging không tách biệt.  
**Production impact:** Log volume tăng, alert bị nhiễu, khó thấy final outcome.  
**Severity:** Medium  
**Recommended fix:** Attempt log ở mức phù hợp/metric; final failure log một lần với attempt count và dependency context.

### 8. Không kiểm tra response state trước khi viết JSON lỗi

**Problem:** Middleware luôn set status và ghi body sau attempt cuối.  
**Why it happens:** Không xét trường hợp headers/body đã gửi.  
**Production impact:** Client nhận response không hợp lệ hoặc exception thứ cấp.  
**Severity:** High  
**Recommended fix:** Chỉ ghi standardized error khi response chưa start.

## Phiên bản code đề xuất

```csharp
public sealed class ErrorHandlingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ErrorHandlingMiddleware> _logger;

    public ErrorHandlingMiddleware(
        RequestDelegate next,
        ILogger<ErrorHandlingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (OperationCanceledException)
            when (context.RequestAborted.IsCancellationRequested)
        {
            _logger.LogInformation(
                "Request cancelled by client. TraceId={TraceId}",
                context.TraceIdentifier);
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Unhandled request error. TraceId={TraceId}",
                context.TraceIdentifier);

            if (context.Response.HasStarted)
                throw;

            context.Response.StatusCode =
                StatusCodes.Status500InternalServerError;

            await context.Response.WriteAsJsonAsync(
                new
                {
                    error = "unexpected_error",
                    traceId = context.TraceIdentifier
                },
                context.RequestAborted);
        }
    }
}
```

Retry cho external dependency nên đặt ở typed client/application layer, ví dụ quanh một GET idempotent hoặc command có idempotency key rõ ràng, thay vì replay cả request pipeline.

## Trade-offs

- Không retry toàn pipeline giảm nguy cơ duplicate nhưng yêu cầu từng dependency tự có resilience policy phù hợp.
- Retry transient call có thể tăng success rate nhưng cũng tăng latency và downstream load; cần timeout, backoff, jitter và stop condition.
- Idempotency key giúp retry command an toàn hơn nhưng cần persistence/uniqueness semantics và lifecycle rõ ràng.
- Với response đã bắt đầu, không thể luôn trả JSON lỗi đẹp; integrity và connection behavior quan trọng hơn cosmetic error payload.

## Cách kiểm thử

1. **Cancellation test:** Hủy request khi business handler đang chờ; verify không có attempt thứ hai và không tăng metric 500.
2. **Duplicate-side-effect test:** POST tạo order rồi ném lỗi sau commit; verify middleware không replay operation.
3. **Partial-response test:** Handler ghi một phần body rồi ném; middleware không cố ghi JSON lỗi mới.
4. **Transient dependency test:** Retry chỉ xảy ra ở client layer cho failure được phân loại và dừng khi cancellation xảy ra.
5. **Sensitive-data test:** Exception chứa SQL/path/token giả; response client không được chứa nội dung đó.

## Quan sát trong production

- Metric: request cancelled, unhandled exception, dependency retry count, retry exhausted, duplicate/idempotency conflict.
- Trace: mỗi outbound retry là event/span attribute, không tạo ba request trace giả.
- Log final error một lần với trace id; attempt logs dùng level phù hợp.
- Alert tách riêng cancellation rate khỏi 5xx rate.
- Theo dõi latency do retry để phát hiện retry amplification.

## Câu hỏi phỏng vấn mở rộng

1. Bạn quyết định lỗi nào là transient để retry dựa trên signal nào?
2. Nếu POST thanh toán cần retry, bạn thiết kế idempotency key và transaction boundary thế nào?
3. Circuit breaker có giải quyết cùng vấn đề với retry không, và khi nào nên dùng cả hai?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Streaming không đồng nghĩa với resource usage thấp: nếu stream trực tiếp từ database, connection có thể bị giữ suốt thời gian client đọc.
- Disposable resource phải có deterministic lifetime, đặc biệt trên failure/cancellation path.
- Cancellation token cần được propagate xuyên suốt call chain; client abort không nên bị xem như lỗi 500 thông thường.
- Retry phải đặt đúng boundary và đi cùng idempotency; replay toàn bộ HTTP pipeline là một thiết kế nguy hiểm.
- Observability cần phân biệt database wait, client cancellation, retry và lỗi thật thay vì gom tất cả thành một metric 500.

## Mẫu tư duy cần nhớ

1. Review resource lifetime trên cả success, failure và cancellation path.
2. Propagate cancellation tới mọi I/O operation có hỗ trợ.
3. Retry chỉ tại boundary biết rõ operation có an toàn để retry hay không.
4. Thiết kế idempotency trước khi thêm retry cho command có side effect.
5. Tách client cancellation khỏi application failure trong logs và metrics.
