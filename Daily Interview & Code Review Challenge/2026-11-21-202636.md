## Kết quả code review tham khảo

### Critical — Stop App Pool trước khi drain traffic

**Vấn đề:** Node có thể còn nhận request khi process bị dừng.  
**Tại sao xảy ra:** Không có bước đưa node ra khỏi load balancer và đợi in-flight requests.  
**Ảnh hưởng production:** 502/503, timeout, transaction dang dở.  
**Cách sửa:** Drain node; đợi active requests về ngưỡng chấp nhận được; deploy lần lượt từng node; xác nhận còn capacity.

### Critical — Release có thể được báo thành công dù health fail

**Vấn đề:** Catch chỉ warning, không fail deployment.  
**Tại sao xảy ra:** Script bỏ qua exit status.  
**Ảnh hưởng production:** Load balancer đưa node hỏng vào phục vụ.  
**Cách sửa:** Throw khi readiness fail, chặn rollout, rollback node và xác minh lại.

### High — Xóa thư mục live trước khi artifact sẵn sàng

**Vấn đề:** Deployment không atomic, có khoảng trống filesystem và không có version trước để rollback.  
**Tại sao xảy ra:** Remove-Item và Expand-Archive thực hiện trực tiếp trên live path.  
**Ảnh hưởng production:** Thiếu DLL/config, startup fail, mixed binaries khi file lock.  
**Cách sửa:** Validate artifact, extract vào versioned staging directory, switch physical path/binding theo cơ chế được thử nghiệm; giữ version trước.

### High — Secret lộ trong log và trên disk

**Vấn đề:** Connection string được in ra log; ghi trực tiếp vào JSON deploy.  
**Tại sao xảy ra:** Logging dữ liệu nhạy cảm và configuration mutation.  
**Ảnh hưởng production:** Rò rỉ credential qua TeamCity/Octopus log, backup và artifact.  
**Cách sửa:** Octopus sensitive variables/secret store; inject qua protected environment configuration; không log secret; hạn chế ACL.

### High — Health check có thể sai process hoặc sai binding

**Vấn đề:** localhost:5000 không nhất thiết là IIS site; kiểm tra status mà không validate readiness/version.  
**Tại sao xảy ra:** IIS in-process hosting không yêu cầu site listen port 5000.  
**Ảnh hưởng production:** False positive hoặc false negative.  
**Cách sửa:** Probe đúng binding qua host header/HTTPS và readiness endpoint, xác minh expected release ID.

### High — Không có schema compatibility gate

**Vấn đề:** Database migration có thể phá version cũ trong rolling deployment.  
**Tại sao xảy ra:** Release script không xét expand/contract, migration ordering.  
**Ảnh hưởng production:** Lỗi truy vấn hoặc deserialize trên một nửa cluster.  
**Cách sửa:** Expand schema tương thích trước, rollout application, contract sau khi version cũ rút hết; rollback application không phụ thuộc schema rollback nguy hiểm.

### Medium — ErrorActionPreference Continue

**Vấn đề:** Cmdlet lỗi non-terminating vẫn cho script chạy tiếp.  
**Tại sao xảy ra:** Thiết lập Continue và thiếu kiểm tra đầu ra.  
**Ảnh hưởng production:** Artifact deploy một phần, báo trạng thái không chính xác.  
**Cách sửa:** Stop, try/finally, kiểm tra explicit status và exit nonzero.

### Medium — JSON serialization và configuration drift

**Vấn đề:** ConvertTo-Json mặc định có depth giới hạn; viết file không kiểm soát encoding, cấu trúc có thể bị biến đổi.  
**Tại sao xảy ra:** Re-serialize config production trong release.  
**Ảnh hưởng production:** Config lồng nhau bị thay đổi hoặc mất dữ liệu.  
**Cách sửa:** Externalize environment-specific config, validate startup options và artifact immutability.

## Phiên bản đề xuất

Đây là **orchestration sketch** cho Octopus Deploy, không phải script copy-paste hoàn chỉnh: các lệnh drain/enable phụ thuộc API của load balancer hiện có. IIS physical-path switching phải được thử trên môi trường staging; health URL là binding đã cấu hình.

```powershell
param(
  [Parameter(Mandatory=$true)][string]$PackagePath,
  [Parameter(Mandatory=$true)][string]$ReleaseId,
  [Parameter(Mandatory=$true)][string]$Node,
  [Parameter(Mandatory=$true)][string]$SiteName,
  [Parameter(Mandatory=$true)][string]$HealthUrl
)
$ErrorActionPreference = "Stop"
Import-Module WebAdministration

$root = "C:\deploy\orders"
$staged = Join-Path $root $ReleaseId
$site = "IIS:\Sites\$SiteName"
$previous = (Get-ItemProperty $site).physicalPath
$switched = $false

function Assert-Ready {
  $response = Invoke-RestMethod -Uri $HealthUrl -TimeoutSec 10
  if ($response.status -ne "ready" -or
      $response.release -ne $ReleaseId) {
    throw "Readiness or release mismatch"
  }
}

try {
  if (Test-Path $staged) { throw "Release directory exists" }
  New-Item -ItemType Directory -Path $staged | Out-Null
  Expand-Archive -Path $PackagePath -DestinationPath $staged
  if (-not (Test-Path (Join-Path $staged "web.config"))) {
    throw "Invalid IIS artifact"
  }

  # Implement through the existing load balancer management API.
  Invoke-DrainNode -Node $Node
  Wait-ForDrainedNode -Node $Node -TimeoutSeconds 120

  Set-ItemProperty $site -Name physicalPath -Value $staged
  $switched = $true
  Restart-WebAppPool -Name "OrdersApi"
  Assert-Ready

  Invoke-EnableNode -Node $Node
}
catch {
  if ($switched) {
    Set-ItemProperty $site -Name physicalPath -Value $previous
    Restart-WebAppPool -Name "OrdersApi"
  }
  # Keep the node drained unless previous version passes its own readiness.
  throw
}
```

Các hàm `Invoke-DrainNode`, `Wait-ForDrainedNode` và `Invoke-EnableNode` là **integration points cần triển khai**, không phải PowerShell built-ins. Trong thực tế, phải validate previous version readiness trước khi re-enable sau rollback; xử lý recycle semantics, warm-up, ACL, package signature/checksum, disk capacity và cleanup riêng. Release orchestrator chỉ chuyển sang node tiếp theo sau khi node hiện tại healthy và metrics ổn định.

## Giải thích thiết kế sau khi sửa

Immutable versioned directories giúp rollback application không phụ thuộc vào thao tác giải nén. Drain trước khi thay physical path giảm lỗi in-flight. Readiness kiểm tra version thực tế, không chỉ process sống. Fail-fast giữ lỗi hiển thị rõ trong Octopus. Configuration được quản lý tách biệt với artifact và không xuất hiện trong log.

## Trade-offs

Rolling deployment lâu hơn và cần headroom để một node gánh traffic. Versioned directories tốn disk. Readiness kiểm tra dependency quá sâu có thể làm toàn cluster bị rút khỏi traffic khi dependency chung hỏng; cần phân biệt liveness/readiness. Nếu không có load balancer drain API, cần phương án bảo trì có kiểm soát thay vì giả định zero downtime.

## Cách kiểm thử

1. **Deployment validation:** deploy artifact hỏng và xác nhận không có node tiếp theo bị cập nhật.
2. **Load test:** duy trì request dài trong khi drain, đo tỷ lệ 5xx và latency.
3. **Compatibility test:** chạy v1/v2 đồng thời với schema expand, kiểm tra cả đọc/ghi.
4. **Failure-path test:** readiness fail sau switch; rollback binary và xác minh node vẫn drained khi rollback fail.
5. **Security test:** scan Octopus logs, disk ACL và environment để xác nhận không lộ connection string.

## Quan sát trong production

Application Insights: request 5xx, p95/p99, dependency failures theo `releaseId` và `node`. IIS logs và Windows Event Viewer: startup errors, recycle, 502.5. Octopus: deployment stage, drain duration, rollback status. Alert khi node chưa healthy sau timeout hoặc capacity cluster thấp; correlate request với deployment window.

<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Order = {
  id: string
  customerName: string
  total: number
}

const props = defineProps<{
  tenantId: string
  accessToken: string
}>()

const search = ref('')
const orders = ref<Order[]>([])
const loading = ref(false)
const error = ref('')
const page = ref(1)

async function loadOrders() {
  loading.value = true
  error.value = ''

  const url = '/api/orders?tenantId=' + props.tenantId +
    '&q=' + search.value + '&page=' + page.value

  try {
    const response = await fetch(url, {
      headers: { Authorization: 'Bearer ' + props.accessToken }
    })
    const data = await response.json()
    orders.value = data.items
  } catch (e) {
    error.value = String(e)
  } finally {
    loading.value = false
  }
}

watch(search, loadOrders)
watch(page, loadOrders)
watch(() => props.tenantId, loadOrders)
onMounted(loadOrders)
</script>

<template>
  <input v-model="search" placeholder="Search orders" />
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <table>
    <tr v-for="order in orders" :key="order.id">
      <td>{{ order.customerName }}</td>
      <td>{{ order.total }}</td>
    </tr>
  </table>
  <button @click="page++">Next</button>
</template>

## Kết quả code review tham khảo

### High — Out-of-order response ghi đè state

**Vấn đề:** Request cũ có thể hoàn tất sau request mới.  
**Tại sao xảy ra:** Không có AbortController hay sequence guard.  
**Ảnh hưởng production:** Người dùng xem kết quả sai tenant/search; quyết định nghiệp vụ sai.  
**Cách sửa:** Abort request trước và chỉ commit response của request mới nhất.

### High — Stale tenant data vẫn hiển thị

**Vấn đề:** `orders` không clear khi đổi tenant.  
**Tại sao xảy ra:** UI giữ state cũ trong lúc chờ request.  
**Ảnh hưởng production:** Hiển thị thông tin tenant trước trong session UI, đặc biệt nghiêm trọng trên thiết bị dùng chung.  
**Cách sửa:** Clear ngay khi context đổi, reset page và invalidate requests; backend vẫn phải enforce authorization.

### High — HTTP 401/500 bị xử lý như success

**Vấn đề:** `fetch` resolve với HTTP error; `response.json()` có thể trả ProblemDetails.  
**Tại sao xảy ra:** Không kiểm tra `response.ok`.  
**Ảnh hưởng production:** Empty/undefined list, lỗi UI khó chẩn đoán; auth expiry không được xử lý.  
**Cách sửa:** Phân loại 401/403/429/5xx; refresh/auth redirect theo chính sách của app; không retry 401 vô hạn.

### Medium — URL query không encode

**Vấn đề:** Search chứa `&`, `#`, `?` làm sai query.  
**Tại sao xảy ra:** String concatenation.  
**Ảnh hưởng production:** Kết quả sai, request khó debug.  
**Cách sửa:** URLSearchParams.

### Medium — Loading state không gắn request identity

**Vấn đề:** Request cũ có thể set loading false khi request mới còn chạy.  
**Tại sao xảy ra:** Finally chạy không điều kiện.  
**Ảnh hưởng production:** Loading indicator sai, thao tác lặp.  
**Cách sửa:** Chỉ cập nhật loading nếu sequence hiện hành.

### Medium — Request storm và page không reset

**Vấn đề:** Mỗi keystroke gọi API, chuyển filter giữ page cũ.  
**Tại sao xảy ra:** Watch trực tiếp không debounce; filter không reset pagination.  
**Ảnh hưởng production:** Tải API tăng, trang trống giả.  
**Cách sửa:** Debounce search, reset page khi search/tenant đổi; cancel in-flight.

### Medium — Không validate response contract

**Vấn đề:** Gán `data.items` trực tiếp.  
**Tại sao xảy ra:** TypeScript type không validate JSON runtime.  
**Ảnh hưởng production:** Render lỗi khi API trả shape bất thường.  
**Cách sửa:** Validate response shape (schema validator hoặc explicit checks).

### Low — Pagination không có termination và accessible state

**Vấn đề:** Next luôn enabled, không có total/hasMore, không có thông báo lỗi có thể truy cập.  
**Tại sao xảy ra:** API contract/UX thiếu pagination metadata.  
**Ảnh hưởng production:** Request dư thừa, trải nghiệm khó sử dụng.  
**Cách sửa:** Trả `hasMore` hoặc cursor; disable Next khi không còn dữ liệu.

## Phiên bản đề xuất

```vue
<script setup lang="ts">
import { ref, watch, onUnmounted } from 'vue'

type Order = { id: string; customerName: string; total: number }
const props = defineProps<{ tenantId: string; accessToken: string }>()
const search = ref('')
const page = ref(1)
const orders = ref<Order[]>([])
const hasMore = ref(false)
const loading = ref(false)
const error = ref('')
let controller: AbortController | undefined
let sequence = 0
let debounce: ReturnType<typeof setTimeout> | undefined

async function load() {
  controller?.abort()
  const current = ++sequence
  const request = new AbortController()
  controller = request
  loading.value = true
  error.value = ''
  orders.value = []
  hasMore.value = false

  const params = new URLSearchParams({
    q: search.value, page: String(page.value)
  })
  try {
    const response = await fetch('/api/orders?' + params, {
      headers: { Authorization: 'Bearer ' + props.accessToken },
      signal: request.signal
    })
    if (!response.ok) {
      if (response.status === 401) throw new Error('Session expired')
      throw new Error('Orders API failed: ' + response.status)
    }
    const data: unknown = await response.json()
    if (!data || typeof data !== 'object' ||
        !('items' in data) || !Array.isArray(data.items) ||
        !('hasMore' in data) || typeof data.hasMore !== 'boolean') {
      throw new Error('Unexpected API response')
    }
    if (current === sequence) {
      orders.value = data.items as Order[]
      hasMore.value = data.hasMore
    }
  } catch (e) {
    if (current === sequence && !request.signal.aborted)
      error.value = e instanceof Error ? e.message : 'Unknown error'
  } finally {
    if (current === sequence) loading.value = false
  }
}

watch(() => [props.tenantId, props.accessToken], () => {
  page.value = 1
  void load()
}, { immediate: true })

watch(search, () => {
  if (debounce) clearTimeout(debounce)
  controller?.abort()
  ++sequence
  orders.value = []
  loading.value = false
  page.value = 1
  debounce = setTimeout(() => { void load() }, 250)
})

watch(page, () => { void load() })

onUnmounted(() => {
  if (debounce) clearTimeout(debounce)
  controller?.abort()
  ++sequence
})
</script>

<template>
  <input v-model="search" aria-label="Search orders" />
  <p v-if="loading" role="status">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <table>
    <tr v-for="order in orders" :key="order.id">
      <td>{{ order.customerName }}</td>
      <td>{{ order.total }}</td>
    </tr>
  </table>
  <button :disabled="loading || !hasMore" @click="page++">Next</button>
</template>
```

Trong production nên gom filters thành một watcher hoặc composable để tránh request thừa khi `page` reset đồng thời với tenant/search. Mẫu trên minh họa cancellation + sequence guard, nhưng **chưa validate từng phần tử Order**; cần runtime schema validation ở boundary nếu API không được kiểm soát chặt. Tenant context nên được backend xác định từ authorized identity; nếu backend hỗ trợ multi-tenant switching, phải xác thực quyền trên từng tenant và truyền tenant context qua contract được thiết kế rõ ràng.

## Giải thích thiết kế sau khi sửa

Sequence guard bảo vệ state ngay cả khi cancellation đến quá muộn; AbortController giảm công việc không cần thiết nhưng không đảm bảo server đã dừng xử lý. Clear list ngăn stale display. HTTP status check phân biệt lỗi transport và business/auth errors. Debounce giảm request storm; URLSearchParams đảm bảo encoding.

## Trade-offs

Clear list tạo loading flicker; có thể giữ stale-while-revalidate trong cùng tenant nhưng tuyệt đối không dùng lại dữ liệu khác tenant. Debounce tăng độ trễ cảm nhận khoảng 250ms. Abort không thay thế backend timeout, authorization và rate limiting. Request identity guard tăng logic state; dùng Vue Query/TanStack Query có thể đơn giản hóa ở ứng dụng lớn nhưng cần key chứa đầy đủ auth/tenant/filter context và cấu hình cache isolation.

## Cách kiểm thử

1. **Concurrency test:** dùng deferred responses trả B trước A, đảm bảo A không ghi đè B.
2. **Security/integration test:** đổi tenant giữa request, xác nhận không render dữ liệu cũ và backend từ chối tenant không được phép.
3. **Failure-path test:** 401, 429, 500, invalid JSON, network abort; không có unhandled rejection.
4. **Playwright E2E:** nhập nhanh chuỗi chứa `&`, đổi page và tenant; kiểm tra query và state.
5. **Load test:** so sánh request rate trước/sau debounce; xác nhận server-side pagination.

## Quan sát trong production

Browser RUM: API duration, aborted requests, HTTP error rate, request sequence mismatch (aggregate count, không log access token hay PII). Application Insights: route latency, 401/403/429, per-tenant authorized request counts (tenant identifier đã pseudonymize), request correlation ID. Theo dõi p95/p99 và API load sau rollout, alert khi auth failures tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cần cache kết quả tìm kiếm theo tenant, cache key và invalidation sẽ thiết kế thế nào?
2. Nếu token refresh diễn ra trong lúc có ba request đang chờ, tránh refresh storm bằng cách nào?
3. Nếu API chuyển sang cursor pagination, UI phải thay đổi state và test ra sao?

IIS deployment an toàn đòi hỏi traffic draining, immutable artifact, readiness đúng binding, release gate và database backward compatibility. ## Mẫu tư duy cần nhớ

1. **Stabilize before rollout:** giữ capacity và rollback path trước khi thay live process.

3. **Concurrency changes correctness:** response cuối cùng không nhất thiết là response mới nhất.
4. **Separate security boundaries:** UI state isolation hỗ trợ UX; authorization thuộc backend.
5. **Test failure paths:** deploy fail, 401, network latency và out-of-order responses là test bắt buộc.
