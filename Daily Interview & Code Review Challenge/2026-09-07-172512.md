# Code Review Challenge 1 — Typed `HttpClient` bị giữ trong `BackgroundService`, DNS đổi nhưng worker vẫn gọi endpoint cũ

**Chủ đề:** C#/.NET, `IHttpClientFactory`, typed client lifetime, DNS changes, async/concurrency, retry, timeout, cancellation, third-party API integration, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một e-commerce integration service chạy .NET 8 trên Azure App Service Linux. Service có một `BackgroundService` đồng bộ giá từ một third-party Product API mỗi 2 phút.

Hệ thống hiện có:

- 6.000–15.000 SKUs cần refresh mỗi run;
- Product API dùng DNS-based blue/green cutover khi deploy;
- API giới hạn throughput theo client và có thể trả `429` hoặc `503`;
- một request bình thường mất 50–300 ms nhưng khi dependency degraded có thể kéo dài nhiều giây;
- App Service có thể restart hoặc scale-out;
- team đã chuyển từ `new HttpClient()` sang `IHttpClientFactory` vì từng gặp socket exhaustion;
- một typed client `ProductApiClient` được inject vào `BackgroundService`;
- production gần đây có incident sau khi Product API đổi DNS: worker tiếp tục gọi IP cũ lâu hơn mong đợi;
- trong giờ cao điểm, số request outbound tăng đột biến, connection usage tăng mạnh và một số run kéo dài chồng lên run tiếp theo;
- logs chứa cả bearer token trong debug message của request;
- team đề xuất chỉ tăng `SetHandlerLifetime` lên 30 phút để “giảm connection churn”.

Implementation hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductApiClient
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<ProductApiClient> _logger;

    public ProductApiClient(
        HttpClient httpClient,
        ILogger<ProductApiClient> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<ProductPrice?> GetPriceAsync(
        string sku,
        string accessToken)
    {
        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                using var request = new HttpRequestMessage(
                    HttpMethod.Get,
                    $"api/prices/{sku}");

                request.Headers.Authorization =
                    new AuthenticationHeaderValue("Bearer", accessToken);

                _logger.LogDebug(
                    "Calling {Url} with token {Token}",
                    request.RequestUri,
                    accessToken);

                var response = await _httpClient.SendAsync(request);

                if (response.StatusCode == HttpStatusCode.NotFound)
                {
                    return null;
                }

                response.EnsureSuccessStatusCode();

                return await response.Content
                    .ReadFromJsonAsync<ProductPrice>();
            }
            catch (Exception ex)
            {
                _logger.LogWarning(
                    ex,
                    "Product API attempt {Attempt} failed for {Sku}",
                    attempt,
                    sku);

                await Task.Delay(500);
            }
        }

        throw new InvalidOperationException(
            $"Could not load price for {sku}");
    }
}

public sealed class PriceRefreshWorker : BackgroundService
{
    private readonly ProductApiClient _client;
    private readonly IProductRepository _products;
    private readonly ITokenProvider _tokenProvider;

    public PriceRefreshWorker(
        ProductApiClient client,
        IProductRepository products,
        ITokenProvider tokenProvider)
    {
        _client = client;
        _products = products;
        _tokenProvider = tokenProvider;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var token = await _tokenProvider.GetTokenAsync();
            var skus = await _products.GetActiveSkusAsync();

            var tasks = skus.Select(async sku =>
            {
                var price = await _client.GetPriceAsync(sku, token);
                await _products.UpdatePriceAsync(sku, price);
            });

            await Task.WhenAll(tasks);

            await Task.Delay(TimeSpan.FromMinutes(2));
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định lifetime problem giữa typed client và `BackgroundService`.
2. Giải thích tại sao dùng `IHttpClientFactory` vẫn có thể không phản ứng đúng với DNS changes.
3. Phân tích `Task.WhenAll` trên hàng nghìn SKUs và downstream capacity.
4. Đánh giá retry hiện tại theo HTTP semantics.
5. Đánh giá timeout và `CancellationToken` handling.
6. Phân tích overlapping runs và shutdown behavior.
7. Tìm security issue trong logging.
8. Đề xuất implementation/lifetime strategy tốt hơn.
9. Giải thích khi nào dùng typed client ngắn hạn, named client, hoặc long-lived `HttpClient` với `PooledConnectionLifetime`.
10. Giải thích testing và production telemetry để chứng minh DNS, retry và connection behavior.

## Câu hỏi gợi mở

1. Typed client được đăng ký transient nhưng điều gì xảy ra khi nó được constructor-inject vào một singleton `BackgroundService` sống suốt process lifetime?
2. `IHttpClientFactory` có thể rotate handler nếu `HttpClient` đã bị giữ sống lâu hơn `HandlerLifetime` không?
3. Với 15.000 SKUs, `Task.WhenAll` tạo ra bao nhiêu outbound operations cùng lúc nếu không có concurrency limit?
4. Có nên retry mọi `4xx`, `429`, timeout và exception với cùng một delay 500 ms không?
5. Nếu host nhận shutdown signal, đoạn code hiện tại dừng ở đâu và operation nào vẫn tiếp tục?

## Kết quả code review tham khảo

### Critical — Typed client bị captive trong singleton `BackgroundService`

**Vấn đề:**  
`ProductApiClient` được tạo như typed client từ `IHttpClientFactory` nhưng bị constructor-inject vào `PriceRefreshWorker`. Hosted services được đăng ký như singleton, vì vậy typed client instance có thể bị giữ suốt lifetime của worker.

**Tại sao xảy ra:**  
`IHttpClientFactory` chỉ có thể tạo client mới với handler mới khi application thực sự request client mới. Một factory-created `HttpClient` bị giữ lâu có thể tiếp tục dùng handler/connection pool cũ thay vì tham gia handler rotation như thiết kế mong muốn.

**Ảnh hưởng production:**  
Nếu Product API thay đổi DNS/IP, worker có thể tiếp tục dùng connection pool gắn với endpoint cũ lâu hơn `HandlerLifetime` mà team tưởng rằng đã cấu hình. Blue/green cutover có thể gây timeout, 5xx hoặc traffic đi sai backend.

**Cách sửa:**  
Không giữ typed client lâu trong singleton. Một lựa chọn là inject `IHttpClientFactory` và gọi `CreateClient` tại thời điểm cần, hoặc tạo scope mỗi run rồi resolve typed client mới. Nếu cố ý dùng long-lived `HttpClient`, cấu hình `SocketsHttpHandler.PooledConnectionLifetime` phù hợp để connection được tái tạo và DNS được resolve lại theo policy.

### High — `Task.WhenAll` tạo unbounded fan-out tới Product API

**Vấn đề:**  
Code tạo một task cho mọi SKU rồi chạy cùng lúc.

**Tại sao xảy ra:**  
Không có concurrency bound, rate limiter hoặc backpressure.

**Ảnh hưởng production:**  
Với hàng nghìn SKUs, application có thể tạo burst rất lớn về outbound requests, sockets/connections, token usage và database writes. Dependency có thể trả `429`, latency tăng, retry storm xuất hiện và chính worker tự khuếch đại incident.

**Cách sửa:**  
Dùng bounded concurrency, ví dụ `Parallel.ForEachAsync` với `MaxDegreeOfParallelism`, `SemaphoreSlim`, channel/worker-pool hoặc rate limiter. Concurrency phải dựa trên Product API limit, outbound connection telemetry, database write capacity và target refresh SLO.

---

### High — Retry mọi exception/response theo một policy cố định

**Vấn đề:**  
Mọi exception đi vào cùng một retry loop 3 lần với delay 500 ms.

**Tại sao xảy ra:**  
Code không phân biệt failure semantics.

**Ảnh hưởng production:**  
Retry có thể vô ích hoặc gây hại đối với permanent failures như nhiều `4xx`; retry đồng bộ hàng nghìn requests sau `429/503` có thể tạo retry storm. Nếu server gửi `Retry-After`, code cũng bỏ qua tín hiệu này.

**Cách sửa:**  
Phân loại failure. Ví dụ:

- không retry validation/authentication failures nếu không có evidence token refresh sẽ sửa được;
- retry bounded cho transient network errors, selected 5xx và throttling;
- tôn trọng `Retry-After` khi phù hợp;
- dùng exponential backoff + jitter;
- giới hạn tổng retry time bằng timeout/deadline;
- đo retry attempts và final outcome.

Không mặc định “3 lần” là đúng cho mọi dependency.

---

### High — Không có `CancellationToken` xuyên suốt I/O path

**Vấn đề:**  
`GetTokenAsync`, repository calls, `SendAsync`, deserialization, `UpdatePriceAsync` và `Task.Delay` không nhận `stoppingToken`.

**Tại sao xảy ra:**  
Worker kiểm tra cancellation chỉ ở đầu loop nhưng không propagate vào operations bên trong.

**Ảnh hưởng production:**  
Deployment/shutdown có thể chờ lâu hoặc terminate process giữa batch. Requests đã không còn cần thiết vẫn tiếp tục giữ resource và gọi downstream.

**Cách sửa:**  
Propagate cancellation token tới mọi async API có hỗ trợ. Với retry delay, truyền token. Đồng thời xác định graceful-shutdown semantics: work nào phải hoàn thành, work nào có thể bỏ và run sau sẽ recover thế nào.

---

### High — Không có timeout/deadline rõ ràng cho dependency

**Vấn đề:**  
Code không thể hiện timeout budget phù hợp với refresh workflow.

**Tại sao xảy ra:**  
Dependency request được để mặc cho default/configuration implicit behavior.

**Ảnh hưởng production:**  
Khi Product API treo/chậm, hàng nghìn requests có thể giữ resources lâu và đẩy run vượt quá 2 phút, gây backlog hoặc overlap nếu scheduling sau này bị tách khỏi awaited loop.

**Cách sửa:**  
Đặt request timeout/deadline phù hợp với business SLO và retry budget. Timeout phải được xem cùng retry: tổng thời gian tối đa của một SKU phải bounded.

---

### High — Sensitive bearer token bị ghi vào log

**Vấn đề:**  
`accessToken` được log trực tiếp.

**Tại sao xảy ra:**  
Debug telemetry ghi cả credential thay vì metadata an toàn.

**Ảnh hưởng production:**  
Bearer token có thể bị lộ qua Application Insights/Kibana/log export và được dùng để truy cập Product API trong thời gian token còn hiệu lực.

**Cách sửa:**  
Không log token, authorization header hoặc secret. Log endpoint name, status, duration, retry attempt, correlation ID và safe subject/client metadata nếu cần.

---

### High — `HttpResponseMessage` không được dispose rõ ràng

**Vấn đề:**  
`response` không nằm trong `using`/`await using` scope.

**Tại sao xảy ra:**  
Code return sau deserialize nhưng không thể hiện deterministic response disposal.

**Ảnh hưởng production:**  
Tùy content consumption và handler behavior, việc giữ response lâu hơn cần thiết có thể làm resource/connection reuse kém rõ ràng và khó reasoning dưới load.

**Cách sửa:**  
Dùng `using var response = await _httpClient.SendAsync(...)`. Khi xử lý payload lớn, cân nhắc `ResponseHeadersRead` và stream thay vì buffer mặc định nếu requirement cần.

### Medium — SKU được nối trực tiếp vào relative URI

**Vấn đề:**  
`sku` được đưa thẳng vào path.

**Tại sao xảy ra:**  
Code giả định SKU luôn là path-safe string.

**Ảnh hưởng production:**  
SKU chứa `/`, `?`, `#` hoặc ký tự đặc biệt có thể tạo URI không đúng semantics.

**Cách sửa:**  
Encode path segment hoặc dùng URI construction abstraction phù hợp. Đồng thời validate SKU theo domain invariant nếu format đã được định nghĩa.

### Medium — Scheduling semantics chưa rõ và dễ drift

**Vấn đề:**  
Worker “mỗi 2 phút” thực tế chờ toàn bộ run xong rồi mới delay 2 phút.

**Tại sao xảy ra:**  
Không phân biệt fixed-delay với fixed-rate schedule.

**Ảnh hưởng production:**  
Nếu một run mất 8 phút, run tiếp theo bắt đầu khoảng 10 phút sau run trước, không phải cứ 2 phút. Có thể đúng hoặc sai tùy requirement.

**Cách sửa:**  
Làm rõ business requirement. Nếu chỉ cần continuous refresh, fixed-delay có thể hợp lý. Nếu cần wall-clock schedule, phải thiết kế overlap/skip/catch-up semantics và idempotency rõ ràng.

---

### Medium — Một token dùng cho toàn batch mà không xác định expiry behavior

**Vấn đề:**  
Token được lấy một lần trước batch lớn.

**Tại sao xảy ra:**  
Code giả định token còn hợp lệ đủ lâu cho mọi request.

**Ảnh hưởng production:**  
Nếu batch kéo dài vượt token lifetime, phần cuối có thể nhận auth failure và retry vô ích với cùng token.

**Cách sửa:**  
`ITokenProvider` nên quản lý cache/refresh theo expiry và caller không nên tự giữ credential lâu hơn cần thiết. Nếu nhận `401`, chỉ retry sau token refresh nếu contract xác nhận đây là recoverable case.

### Medium — Telemetry không cho phép chứng minh DNS/connection/retry hypothesis

**Vấn đề:**  
Log chỉ có attempt và SKU; không có dependency duration, status distribution, retry reason, endpoint instance/correlation hoặc run metrics.

**Tại sao xảy ra:**  
Observability không được thiết kế cùng integration.

**Ảnh hưởng production:**  
Khó trả lời: failure có phải DNS stale, throttling, token issue, Product API latency hay local connection pressure.

**Cách sửa:**  
Theo dõi dependency telemetry, status codes, latency, retries, active requests, run duration, processed SKU count, timeout/cancel count và DNS/network diagnostics phù hợp.

## Phiên bản đề xuất

Ví dụ dưới đây dùng named client được lấy đúng thời điểm, bounded concurrency và cancellation. Retry policy có thể được cấu hình qua resilience handler phù hợp với dependency contract thay vì viết ad-hoc trong business code.

```csharp
public sealed class ProductPriceService
{
    private readonly IHttpClientFactory _httpClientFactory;
    private readonly ITokenProvider _tokenProvider;

    public ProductPriceService(
        IHttpClientFactory httpClientFactory,
        ITokenProvider tokenProvider)
    {
        _httpClientFactory = httpClientFactory;
        _tokenProvider = tokenProvider;
    }

    public async Task<ProductPrice?> GetPriceAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        var client = _httpClientFactory.CreateClient("ProductApi");
        var token = await _tokenProvider.GetTokenAsync(cancellationToken);
        var encodedSku = Uri.EscapeDataString(sku);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"api/prices/{encodedSku}");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        using var response = await client.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }

        response.EnsureSuccessStatusCode();

        return await response.Content
            .ReadFromJsonAsync<ProductPrice>(
                cancellationToken: cancellationToken);
    }
}
```

Worker:

```csharp
public sealed class PriceRefreshWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<PriceRefreshWorker> _logger;
    private readonly int _maxConcurrency = 16;

    public PriceRefreshWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<PriceRefreshWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(2));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await using var scope = _scopeFactory.CreateAsyncScope();

            var products = scope.ServiceProvider
                .GetRequiredService<IProductRepository>();

            var prices = scope.ServiceProvider
                .GetRequiredService<ProductPriceService>();

            var skus = await products.GetActiveSkusAsync(stoppingToken);

            await Parallel.ForEachAsync(
                skus,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = _maxConcurrency,
                    CancellationToken = stoppingToken
                },
                async (sku, ct) =>
                {
                    var price = await prices.GetPriceAsync(sku, ct);
                    await products.UpdatePriceAsync(sku, price, ct);
                });
        }
    }
}
```

## Giải thích thiết kế sau khi sửa

### 1. Client lifetime và handler rotation trở nên intentional

Factory-created client được lấy tại thời điểm sử dụng thay vì bị giữ trong singleton. Điều này cho phép handler lifecycle thực sự có cơ hội rotate.

### 2. Concurrency được bounded

Dependency không bị nhận burst 15.000 requests một lúc. Concurrency limit cần tune bằng đo đạc, không copy con số `16` một cách máy móc.

### 3. Retry được tách khỏi business loop

Resilience policy nên hiểu HTTP status, timeout budget và dependency contract. Business code chỉ xử lý outcome có ý nghĩa.

### 4. Cancellation đi xuyên qua toàn pipeline

Shutdown có thể dừng request, delay và database operation có kiểm soát.

### 5. Secret không còn là telemetry

Bearer token không được log; observability tập trung vào behavior thay vì credential.

## Trade-offs

- Factory-created clients ngắn hạn tạo thêm object wrapper nhưng handler/connection pool vẫn được factory quản lý.
- Long-lived `HttpClient` với `PooledConnectionLifetime` đơn giản về ownership nhưng cần cấu hình connection lifetime đúng.
- Concurrency quá thấp làm refresh chậm; quá cao gây throttling và connection pressure.
- Retry tăng khả năng recover transient failure nhưng cũng tăng latency và load; mỗi dependency cần retry budget riêng.
- `PeriodicTimer` không tự giải quyết requirement fixed-rate/catch-up; scheduling semantics vẫn phải được xác định.

## Cách kiểm thử

1. **DNS cutover integration test:** đổi upstream endpoint/DNS trong môi trường test và xác minh client mới eventually dùng connection tới backend mới theo lifetime policy.
2. **Load test:** 10.000+ SKUs với bounded concurrency; đo outbound active requests, p95/p99, socket/connection usage và Product API throttle rate.
3. **Failure-path test:** inject `429`, `503`, timeout và `401`; verify chỉ failure phù hợp mới retry và tổng retry time bị bounded.
4. **Shutdown test:** cancel host giữa batch; outbound requests/database operations phải dừng theo policy và không log normal cancellation như incident.
5. **Security test:** kiểm tra logs/Application Insights không chứa access token hoặc authorization header.

## Quan sát trong production

Theo dõi:

- Product API dependency request count, p50/p95/p99;
- status-code distribution (`2xx`, `4xx`, `429`, `5xx`);
- retry attempts theo reason;
- timeout/cancellation count;
- active/concurrent outbound requests;
- connection establishment errors và network failures;
- refresh run duration, processed SKU count, failed SKU count;
- token refresh/auth failure rate;
- App Service instance ID và deployment version;
- correlation/trace ID giữa refresh item và downstream request;
- alerts khi dependency error rate, queue/backlog hoặc run duration vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn long-lived `HttpClient` + `PooledConnectionLifetime` thay vì `IHttpClientFactory`?
2. Nếu Product API limit 100 requests/second nhưng latency dao động mạnh, bạn thiết kế concurrency/rate limiting thế nào?
3. Nếu một run chưa xong khi lịch tiếp theo đến, bạn sẽ skip, overlap hay coalesce run? Điều gì quyết định lựa chọn?

# Code Review Challenge 2 — Playwright suite “xanh” nhờ retry nhưng thực tế phụ thuộc thứ tự test và shared account

## Bối cảnh

Một React storefront + ASP.NET Core backend có Playwright E2E suite chạy trên CI trước production deploy.

Suite hiện có khoảng 350 tests. Team chạy 8 workers để giảm thời gian CI.

Production pipeline gần đây có các dấu hiệu:

- cùng một commit có thể fail ở run đầu nhưng pass khi rerun;
- tỷ lệ test pass sau retry cao nên dashboard vẫn gần 100%;
- nhiều tests dùng chung account `e2e-admin@example.test`;
- test tạo product với cùng tên `E2E Product`;
- một số tests chỉ pass nếu file trước đó đã chạy và tạo data;
- CI chạy parallel nhưng local chạy gần như tuần tự;
- tests dùng nhiều `waitForTimeout(2000)`;
- khi fail trên CI, screenshot thường chỉ cho thấy màn hình cuối cùng, không rõ network/action trước đó;
- cleanup đôi khi xóa data mà test khác đang dùng;
- team đề xuất tăng retry từ 2 lên 5 để “hết flaky”.

## Nhiệm vụ của ứng viên

1. Xác định test-isolation problems.
2. Phân tích behavior khi Playwright chạy tests parallel.
3. Đánh giá shared `storageState`/shared account.
4. Tìm ordering dependency giữa tests.
5. Đánh giá global mutable variable `productId`.
6. Phân tích fixed sleeps và web-first waiting.
7. Đánh giá cleanup strategy và shared test data.
8. Phân tích việc retries đang che giấu flaky behavior.
9. Đề xuất deterministic test-data strategy.
10. Giải thích CI artifacts/trace/metrics để debug flakiness.

## Câu hỏi gợi mở

1. Playwright có bảo đảm test `edit product created above` chạy sau test `create product` không?
2. Nếu hai workers cùng tạo `E2E Product`, selector `.first()` sẽ chọn record nào?
3. Shared authenticated state có đồng nghĩa với shared browser context giữa các tests không, và shared backend account state vẫn có thể xung đột thế nào?
4. `waitForTimeout(2000)` đang chờ condition nào?
5. Nếu test chỉ pass sau retry, đó là reliability hay symptom của nondeterminism?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **backend test data/shared identity không được isolate trong khi test runner được chạy parallel**.

### Gợi ý 2

Phân biệt:

- browser-context isolation do Playwright cung cấp;
- shared server-side state mà browser isolation không thể tự giải quyết;
- synchronization dựa trên condition so với sleep dựa trên thời gian đoán.

## Kết quả code review tham khảo

### Critical — Test phụ thuộc thứ tự chạy qua global `productId`

**Vấn đề:**  
Test thứ hai phụ thuộc test đầu tiên gán `productId`.

**Tại sao xảy ra:**  
Các tests được viết như một workflow tuần tự nhưng không khai báo/setup lifecycle phù hợp. Playwright thiết kế test isolation để mỗi test có thể chạy độc lập; parallel execution/sharding/retry có thể làm thứ tự hoặc worker khác với assumption hiện tại.

**Ảnh hưởng production:**  
CI flaky, test thứ hai có thể dùng `undefined`/empty ID, retry có thể chạy trong state khác và sharding có thể phá suite hoàn toàn.

**Cách sửa:**  
Mỗi test phải tự tạo precondition của mình hoặc dùng fixture/setup rõ ràng. Nếu business scenario thực sự cần multi-step E2E workflow, giữ các bước trong một test hoặc dùng serial mode có chủ đích cho rất ít scenario phù hợp; không mặc định biến toàn suite thành serial.

---

### Critical — Shared backend account + shared test data gây cross-test interference

**Vấn đề:**  
Tất cả workers dùng cùng authenticated account và cùng product name.

**Tại sao xảy ra:**  
Browser contexts có thể isolated về cookies/localStorage, nhưng server-side state vẫn dùng cùng user/tenant/data namespace.

**Ảnh hưởng production:**  
Một test có thể thấy, sửa hoặc xóa data của test khác. Failure rate tăng khi worker count tăng, còn local serial run vẫn có vẻ ổn.

**Cách sửa:**  
Tạo unique test namespace theo worker/test ID, ví dụ product name chứa run ID + worker index + random suffix. Nếu business rules yêu cầu account-level state độc lập, provision account/tenant riêng theo worker hoặc fixture scope phù hợp.

---

### High — Cleanup theo tên có thể xóa data của test khác

**Vấn đề:**  
`DELETE /by-name/E2E Product` có phạm vi cleanup quá rộng.

**Tại sao xảy ra:**  
Test artifact không có unique ownership identity.

**Ảnh hưởng production:**  
Worker A cleanup có thể xóa record worker B vừa tạo, gây failures ngẫu nhiên ở test đang chạy.

**Cách sửa:**  
Cleanup theo exact resource ID đã tạo bởi test/fixture hoặc test run namespace. Cleanup phải idempotent và chỉ sở hữu data của chính test.

---

### High — `.first()` biến duplicate test data thành nondeterministic selector

**Vấn đề:**  
Selector không chứng minh row đúng; nó chỉ lấy row đầu tiên matching name.

**Tại sao xảy ra:**  
Data không unique và test dùng `.first()` để né strictness thay vì giải quyết ambiguity.

**Ảnh hưởng production:**  
Test có thể pass khi edit sai product, tạo false positive nguy hiểm hơn một failure rõ ràng.

**Cách sửa:**  
Dùng unique data + locator thể hiện stable user-facing identity. Nếu có API trả created ID, dùng ID đó làm exact target; không dùng `.first()` để che duplicate selector.

---

### High — Fixed `waitForTimeout` tạo flaky test và lãng phí CI time

**Vấn đề:**  
Test ngủ 2 giây sau save.

**Tại sao xảy ra:**  
Sleep không gắn với condition thực sự cần đạt. Backend có thể hoàn thành sau 2,1 giây hoặc 100 ms.

**Ảnh hưởng production:**  
Suite vừa chậm vừa flaky. Khi CI load cao, 2 giây không đủ; khi hệ thống nhanh, test vẫn phí 2 giây.

**Cách sửa:**  
Dựa vào Playwright auto-waiting/web-first assertions hoặc chờ observable state: response phù hợp, success UI, URL transition, row xuất hiện hoặc API state. Tránh arbitrary timeout trừ khi chính thời gian là behavior đang test.

---

### High — Retry đang che giấu nondeterminism

**Vấn đề:**  
CI pass sau retry nhưng team coi đó là suite healthy.

**Tại sao xảy ra:**  
Retry được dùng như correction mechanism thay vì diagnostic signal.

**Ảnh hưởng production:**  
Regression thật có thể bị mask, CI time tăng và confidence giảm. Flaky rate không được nhìn thấy trong release decision.

**Cách sửa:**  
Giữ retry nhỏ nếu cần để thu thập diagnostic artifacts, nhưng theo dõi `flaky` separately. Test chỉ pass sau retry phải được coi là reliability defect cần triage. Không tăng retry lên 5 để “làm xanh”.

---

### High — Shared `storageState` có thể tạo coupling tới account/session state

**Vấn đề:**  
Mọi worker dùng cùng account state file.

**Tại sao xảy ra:**  
Mặc dù mỗi test nhận browser context riêng, các contexts đều đại diện cùng backend identity. Nếu tests thay đổi server-side state của account hoặc auth session bị revoke/rotated, failures có thể lan rộng.

**Ảnh hưởng production:**  
Tests liên quan profile, cart, permissions, preferences hoặc account-scoped limits có thể interfere nhau.

**Cách sửa:**  
Nếu tests chỉ cần read-only identity và backend state không mutate, shared auth state có thể đủ. Nếu tests mutate account-scoped state, dùng per-worker/per-test accounts hoặc isolated tenant/data strategy. Không over-engineer nếu workload không cần.

---

### Medium — Setup qua UI cho mọi test có thể làm suite chậm và tăng failure surface

**Vấn đề:**  
Nếu mọi precondition đều phải click UI để tạo data, suite lớn sẽ tốn nhiều thời gian và phụ thuộc thêm UI paths không liên quan mục tiêu test.

**Tại sao xảy ra:**  
Test setup và behavior-under-test chưa được tách.

**Ảnh hưởng production:**  
350 tests có thể bị chậm đáng kể và nhiều failure thực chất đến từ setup.

**Cách sửa:**  
Dùng API/fixture để seed deterministic preconditions khi mục tiêu test không phải creation UI. Chỉ dùng UI để tạo data khi chính creation flow là behavior cần verify.

---

### Medium — Không capture trace/network evidence đủ tốt cho CI failure

**Vấn đề:**  
Config chỉ giữ screenshot khi fail.

**Tại sao xảy ra:**  
Screenshot chỉ mô tả cuối state, không mô tả sequence action/network/DOM snapshots dẫn tới failure.

**Ảnh hưởng production:**  
Flaky failure khó RCA, đặc biệt khi chỉ xảy ra trên CI.

**Cách sửa:**  
Bật trace theo policy phù hợp, ví dụ `on-first-retry` hoặc `retain-on-failure`, kèm HTML report/artifacts. Trace là diagnostic tool; bật `on` cho mọi test có thể tăng artifact/performance cost không cần thiết.

---

### Medium — Local và CI có concurrency model khác nhau quá nhiều

**Vấn đề:**  
Local luôn `workers: 1`, CI là 8.

**Tại sao xảy ra:**  
Developer ít khi reproduce parallelism-related failure trước khi push.

**Ảnh hưởng production:**  
Concurrency bug chỉ xuất hiện muộn trên CI.

**Cách sửa:**  
Giữ default local experience nhanh nhưng có command/profile cho parallel run tương tự CI, đặc biệt trong pre-merge validation hoặc khi debug flaky tests.

## Phiên bản đề xuất

Ví dụ dưới đây dùng fixture tạo product riêng cho mỗi test qua API, cleanup theo exact ID và trace trên first retry.

```ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  workers: process.env.CI ? 8 : undefined,
  retries: process.env.CI ? 1 : 0,
  use: {
    baseURL: process.env.BASE_URL,
    storageState: 'playwright/.auth/admin.json',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure'
  }
});
```

Fixture minh họa:

```ts
import { test as base, expect } from '@playwright/test';
import crypto from 'node:crypto';

type Fixtures = {
  product: { id: string; name: string };
};

export const test = base.extend<Fixtures>({
  product: async ({ request }, use, testInfo) => {
    const name = [
      'E2E',
      testInfo.parallelIndex,
      crypto.randomUUID()
    ].join('-');

    const create = await request.post('/api/test/products', {
      data: { name }
    });

    expect(create.ok()).toBeTruthy();

    const product = await create.json() as {
      id: string;
      name: string;
    };

    try {
      await use(product);
    } finally {
      await request.delete(`/api/test/products/${product.id}`);
    }
  }
});
```

Test độc lập:

```ts

```

Creation UI được test riêng:

Trong hệ thống thật, test-only API phải được bảo vệ và không deploy/enable không kiểm soát ở production. Một alternative là seed trực tiếp database trong ephemeral test environment nếu architecture và ownership cho phép.

## Giải thích thiết kế sau khi sửa

### 1. Mỗi test sở hữu precondition riêng

Không test nào cần test khác chạy trước.

### 2. Backend state cũng được isolate

Browser context isolation không được nhầm với server-side data isolation. Unique resource IDs/namespaces loại bỏ cross-worker collision.

### 3. Cleanup có ownership rõ

Fixture xóa đúng ID mà nó đã tạo, không xóa theo tên chung.

### 4. Waiting dựa trên observable condition

Không đoán 2 giây. Playwright chờ locator/assertion state cần thiết.

### 5. Retry trở thành diagnostic aid

Trace ở first retry giúp RCA; retry không được dùng để biến flaky test thành pass-rate đẹp.

## Trade-offs

- Per-test data creation tăng API/database traffic trong test environment.
- Per-worker accounts/tenants tăng provisioning complexity và cleanup burden.
- API-based setup nhanh hơn UI nhưng không kiểm thử creation UI; vì vậy creation UI cần test riêng.
- `fullyParallel` giúp expose isolation bugs và giảm runtime nhưng đòi hỏi backend test data thật sự parallel-safe.
- Trace artifacts tăng CI storage; cần retention phù hợp.

## Cách kiểm thử

1. **Parallel stability test:** chạy suite hoặc critical subset nhiều lần với 8–16 workers; flaky rate phải gần zero và không có cross-test cleanup failures.
2. **Order-independence test:** shuffle/shard tests; mọi test phải pass độc lập.
3. **Retry audit:** thống kê tests chỉ pass sau retry; không cho phép tỷ lệ flaky tăng mà release vẫn được coi như hoàn toàn healthy.
4. **Cleanup test:** kill CI job giữa run rồi chạy reconciliation để tìm orphan test data; cleanup không được đụng production/non-test namespace.
5. **Trace validation:** cố ý inject một failure và xác minh CI artifact đủ để thấy action timeline, DOM snapshot và network evidence cần thiết.

## Quan sát trong production

Đây là test/CI workload, vì vậy telemetry trọng tâm nằm ở pipeline và test environment:

- first-run pass rate;
- flaky rate / pass-after-retry rate;
- failure rate theo test file/browser/worker;
- median/p95 test duration;
- retry count;
- trace/screenshot/video artifact availability;
- API 4xx/5xx trong E2E environment;
- duplicate test-data creation conflicts;
- cleanup failures và orphan data count;
- test environment CPU/database saturation;
- CI shard/worker distribution;
- commit/build SHA gắn với report.

Nếu E2E tests gọi production-like backend observability stack, dùng correlation ID để nối Playwright test với ASP.NET Core request/Application Insights trace khi điều tra failure.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào `test.describe.configure({ mode: 'serial' })` là lựa chọn hợp lý thay vì sửa test để độc lập?
2. Bạn sẽ thiết kế authentication fixture thế nào nếu mỗi worker cần account riêng nhưng login UI rất chậm?
3. Nếu retry giảm false-negative release block nhưng có nguy cơ che regression, bạn sẽ dùng retry metric trong quality gate thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IHttpClientFactory` không tự sửa mọi lifetime problem; factory-created client bị captive trong singleton vẫn có thể làm handler/DNS behavior lệch kỳ vọng.
- Outbound integration cần bounded concurrency, timeout budget, cancellation và retry policy hiểu failure semantics.
- Retry không phải default fix cho mọi HTTP failure; retry sai có thể tạo load amplification.
- Playwright browser contexts cung cấp test isolation ở browser state, nhưng không tự isolate shared backend account/data.
- E2E tests phải độc lập về order và ownership của test data nếu muốn chạy parallel/sharding đáng tin cậy.
- Fixed sleep và high retry count thường che nondeterminism thay vì sửa root cause.
- Observability của integration và test pipeline phải đủ để chứng minh hypothesis, không chỉ cho biết “failed”.

## Mẫu tư duy cần nhớ

1. **Lifetime phải được phân tích theo object thật sự bị giữ, không chỉ theo DI registration label.**
2. **Bound concurrency theo capacity của dependency, không theo số lượng work cần làm.**
3. **Retry chỉ sau khi phân loại transient vs permanent failure và đặt deadline.**
4. **Isolation phải bao phủ cả client state và server-side state.**
5. **Một test chỉ pass sau retry vẫn là một reliability signal cần điều tra.**
