# Câu 1 — JWT hợp lệ nhưng user vẫn truy cập sai dữ liệu: Authentication, Authorization và claims thực sự được áp dụng ở đâu?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Authentication, Authorization, JWT, claims, policy-based authorization, multi-tenant security, middleware pipeline, API design, observability

## Bối cảnh

Một ASP.NET Core API trên .NET 8 phục vụ một enterprise management platform. User đăng nhập qua Microsoft Entra ID / Azure AD B2C và frontend gửi Bearer token tới API.

API có endpoint:

```csharp
[Authorize]
[HttpGet("projects/{projectId:guid}")]
public async Task<ActionResult<ProjectDto>> GetProject(
    Guid projectId,
    CancellationToken cancellationToken)
{
    var project = await _dbContext.Projects
        .AsNoTracking()
        .Where(x => x.Id == projectId)
        .Select(x => new ProjectDto(
            x.Id,
            x.TenantId,
            x.Name,
            x.Status))
        .SingleOrDefaultAsync(cancellationToken);

    return project is null ? NotFound() : Ok(project);
}
```

Production phát hiện một security incident: user thuộc Tenant A có thể lấy dữ liệu của một project thuộc Tenant B nếu biết `projectId` hợp lệ.

Một developer nói:

> “Endpoint đã có `[Authorize]`, token cũng đã được Microsoft validate nên authorization không thể sai.”

Một developer khác đề xuất thêm claim `tenant_id` vào JWT rồi coi như vấn đề được giải quyết.

Một developer thứ ba muốn để frontend ẩn các project không thuộc tenant hiện tại và không thay backend.

Chưa biết chắc:

- token hiện có những claims nào;
- API đang validate issuer/audience/signature/configuration như thế nào;
- `TenantId` trong database được gắn với user/account theo rule nào;
- có super-admin/support flow cross-tenant hợp lệ hay không;
- authorization hiện được kiểm tra ở controller, application layer hay data-access layer;
- có endpoint khác dùng cùng `projectId` pattern hay không;
- có query filter hoặc policy/authorization handler dùng chung hay không.

## Câu hỏi chính

Hãy giải thích request đi qua Authentication và Authorization trong ASP.NET Core như thế nào, vì sao một JWT hợp lệ và `[Authorize]` vẫn chưa bảo vệ được resource-level access, và bạn sẽ thiết kế authorization boundary để ngăn cross-tenant data access mà vẫn hỗ trợ các trường hợp đặc biệt như support/admin một cách kiểm soát được.

## Câu hỏi làm rõ nên cân nhắc

1. `tenant_id` là claim do identity provider phát hành đáng tin cậy, claim do application tự bổ sung, hay giá trị client có thể gửi?
2. Một user có thể thuộc nhiều tenants hay chỉ đúng một tenant trong lifetime của session/token?
3. Super-admin/support có được phép cross-tenant không, và nếu có thì yêu cầu consent/audit nào?
4. Có background jobs/service-to-service calls cần truy cập tenant data ngoài request user context không?
5. Data model hiện có foreign key/constraint nào giúp bảo đảm project luôn thuộc một tenant hợp lệ không?

## Gợi ý tư duy

### Gợi ý 1

Authentication trả lời “request này đại diện cho identity nào”; nó không tự trả lời “identity đó có được phép đọc resource cụ thể này không”.

### Gợi ý 2

`[Authorize]` mặc định có thể chỉ yêu cầu authenticated principal. Resource ownership vẫn cần một authorization decision gắn với dữ liệu cụ thể.

### Gợi ý 3

Một claim hữu ích chỉ khi nguồn claim đáng tin cậy và backend dùng nó để enforce policy/query boundary; frontend filtering không phải security control.

## Cấu trúc trả lời đề xuất

1. Tách Authentication khỏi Authorization.
2. Giải thích principal/claims được tạo sau token validation.
3. Xác định security invariant của multi-tenant resource access.
4. Phân tích vì sao query hiện tại vi phạm invariant.
5. Chọn nơi enforce tenant/resource authorization.
6. Thiết kế exception path cho support/admin.
7. Xử lý service-to-service/background access.
8. Test negative/cross-tenant paths.
9. Thiết kế logging/audit không lộ dữ liệu nhạy cảm.
10. Xác minh toàn bộ endpoint tương tự, không chỉ endpoint phát hiện incident.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Phân biệt rõ Authentication và Authorization.
- Nhận ra `[Authorize]` không tự kiểm tra `Project.TenantId` so với tenant/user hiện tại.
- Không tin `tenantId` lấy từ query/header/body do client tự gửi nếu không validate với trusted identity/context.
- Backend phải enforce resource ownership hoặc policy tương đương.
- Tránh query resource chỉ bằng globally unique `projectId` khi security boundary cần thêm tenant/user scope.
- Có explicit rule cho privileged access thay vì bypass tùy ý.
- Có negative tests chứng minh Tenant A không đọc/sửa/xóa resource Tenant B.
- Có audit cho cross-tenant privileged access.

### Điểm cộng

- Dùng policy/resource-based authorization khi permission phụ thuộc resource state/ownership.
- Đưa tenant scope vào query để tránh load dữ liệu ngoài boundary rồi mới filter.
- Centralize current-tenant context từ authenticated principal thay vì copy logic ở từng controller.
- Xem xét global query filter như defense-in-depth nhưng không coi nó là giải pháp duy nhất nếu có admin/background cases phức tạp.
- Có strategy cho stale role/permission claims khi quyền thay đổi trong lúc token còn hiệu lực.

### Senior+

- Thiết kế authorization theo capability/permission thay vì hard-code role string khắp nơi.
- Tách normal user path khỏi support elevation path, yêu cầu reason/consent/audit/expiry khi business cần.
- Phân tích confused-deputy risk trong service-to-service calls.
- Thiết kế database/query APIs làm “secure by construction”, ví dụ repository/query service bắt buộc tenant scope ở normal path.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng invariant: với normal user request, một user chỉ được đọc project mà user có quyền trong tenant hợp lệ. `projectId` không tự tạo authorization boundary.

Ở ASP.NET Core, authentication middleware/handler validate credential/token theo cấu hình và tạo `ClaimsPrincipal` cho request khi thành công. Sau đó authorization đánh giá policy/requirements đối với principal và endpoint/resource. Một token hợp lệ chứng minh identity theo trust configuration; nó không chứng minh identity có quyền với mọi project trong database.

Endpoint hiện tại có `[Authorize]`, nhưng query chỉ dùng:

```csharp
x.Id == projectId
```

Nếu project IDs có thể bị lộ qua URL, logs, browser history, email hoặc enumeration từ endpoint khác, user authenticated bất kỳ có thể đọc resource nếu backend không thêm ownership check. Đây là broken object-level/resource authorization.

Nếu normal security model là một active tenant trong token/context, query nên được scoped theo trusted tenant context, ví dụ conceptually:

```csharp
var tenantId = _currentTenant.RequireTenantId();

var project = await _dbContext.Projects
    .AsNoTracking()
    .Where(x => x.Id == projectId && x.TenantId == tenantId)
    .Select(...)
    .SingleOrDefaultAsync(cancellationToken);
```

Điểm quan trọng là `_currentTenant` phải được xây từ trusted authenticated context, không phải header client tự đặt mà không verify. Nếu user có thể thuộc nhiều tenants, selected tenant có thể tới từ route/header nhưng backend phải chứng minh membership trước khi dùng nó.

Nếu authorization phụ thuộc nhiều hơn tenant equality, ví dụ project private, role theo project, delegated access hoặc support permission, tôi dùng policy/resource-based authorization. Có thể load minimal resource metadata hoặc permission record rồi gọi `IAuthorizationService` với requirement phù hợp. Tôi tránh đưa business authorization logic rải rác vào `if (User.IsInRole(...))` ở hàng chục controllers.

Tôi cũng không chỉ “thêm `tenant_id` claim”. Claim chỉ là input cho authorization decision. Cần xác minh:

- ai phát hành claim;
- claim có nằm trong issuer/audience/token flow đúng không;
- application có map đúng claim type không;
- quyền có thể stale bao lâu;
- multi-tenant user semantics là gì.

Frontend ẩn project chỉ cải thiện UX. Security boundary luôn ở server vì client hoàn toàn có thể gọi API trực tiếp.

Với privileged support/admin, tôi không cho bypass bằng `if (IsAdmin) return true` chung. Tôi tách policy rõ, ví dụ `CrossTenantSupportAccess`, yêu cầu permission mạnh hơn, reason/consent/ticket nếu business yêu cầu, expiry ngắn và audit đầy đủ: actor, target tenant, resource, action, reason, timestamp, outcome. Cross-tenant path nên hiếm và observable.

Với background jobs/service-to-service, tôi không giả vờ chúng là end-user. Chúng cần service identity riêng, least privilege và explicit tenant scope lấy từ work item/message đã được validate. Nếu job chạy tất cả tenants, loop vẫn phải xác định tenant boundary cho từng unit of work và tránh accidental cross-tenant writes.

Defense-in-depth có thể gồm:

- application query scope;
- authorization policies;
- database constraints;
- tenant-aware unique keys/indexes;
- query filters nơi phù hợp;
- tests toàn bộ CRUD paths;
- security review cho endpoints dùng IDs trực tiếp.

Tôi sẽ grep/search toàn repository cho `FindAsync(id)`, `SingleAsync(x => x.Id == id)`, raw SQL theo ID và tương tự, vì security bug dạng này hiếm khi chỉ tồn tại ở một endpoint.

Testing cần ít nhất:

- Tenant A đọc project A → allowed;
- Tenant A đọc project B → denied/not found theo API disclosure policy;
- Tenant A update/delete project B → denied;
- user mất membership → behavior sau token refresh/revocation theo design;
- support flow hợp lệ → allowed + audit;
- support không có elevation/consent → denied.

Production telemetry nên log authorization outcome theo safe identifiers/correlation ID, không log raw JWT/token. Alert các cross-tenant privileged operations bất thường và các authorization-denied spikes nếu có.

## Mẫu trả lời trong phỏng vấn

“Em tách authentication và authorization. Token hợp lệ chỉ chứng minh request có một trusted identity theo issuer/audience/signature config; `[Authorize]` mặc định không tự biết project nào thuộc tenant nào. Endpoint hiện query chỉ theo `projectId`, nên đây là resource-level authorization gap.

Em lấy tenant/user context từ authenticated principal hoặc membership đã được backend xác minh, rồi scope query theo `projectId + tenantId` hoặc dùng resource-based policy nếu permission phức tạp. Em không tin tenant ID client tự gửi và frontend filtering không được tính là security control.

Với support/admin cross-tenant, em tạo policy riêng, least privilege, expiry/consent/reason theo requirement và audit đầy đủ thay vì bypass toàn bộ. Sau khi fix, em rà toàn repository các endpoint truy cập resource bằng ID và thêm negative tests cho read/update/delete giữa hai tenants.”

## Câu hỏi đào sâu

1. Nếu một user có thể thuộc 20 tenants và chọn tenant hiện tại bằng header `X-Tenant-Id`, bạn làm gì để header đó an toàn?
2. Nếu permission thay đổi nhưng JWT còn hiệu lực thêm 45 phút, bạn xử lý stale authorization như thế nào tùy mức rủi ro?
3. Một teammate đề xuất dùng EF Core global query filter cho tenant và bỏ toàn bộ resource-based authorization; bạn phản biện trong trường hợp nào?

## Lỗi trả lời thường gặp

- Đồng nhất “token hợp lệ” với “được phép truy cập mọi resource”.
- Tin `tenantId` client gửi mà không verify membership.
- Chỉ ẩn dữ liệu ở frontend.
- Fix riêng endpoint GET nhưng quên update/delete/download/export.
- Cho admin bypass toàn bộ mà không có audit/elevation boundary.

## Thang điểm 0–10

- **0–2:** Chỉ nói thêm `[Authorize]` hoặc validate JWT.
- **3–4:** Nhận ra tenant check nhưng thiếu trusted-context và negative testing.
- **5–6:** Có scoped query/policy, trusted claim context và audit cơ bản.
- **7–8:** Có resource authorization, privileged path, service identity, defense-in-depth và repository-wide review.
- **9–10:** Thiết kế authorization model rõ theo invariants/capabilities, xử lý multi-tenant/stale permission/service access và chứng minh bằng tests + telemetry.

# Câu 2 — Vue search page trả kết quả sai và backend bị request storm khi network chậm

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Vue.js, TypeScript, JavaScript async behavior, browser networking, REST API integration, cancellation, race conditions, performance, observability, full-stack troubleshooting

## Bối cảnh

Một Vue.js admin portal có màn hình tìm product. Khi user gõ từ khóa, thay đổi category hoặc sort order, frontend gọi API:

`GET /api/products/search?q=...&category=...&sort=...`

Đoạn code rút gọn:

```ts
const query = ref('')
const category = ref<string | null>(null)
const sort = ref('relevance')
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

watch([query, category, sort], async () => {
  loading.value = true
  error.value = null

  try {
    const response = await fetch(
      `/api/products/search?q=${encodeURIComponent(query.value)}` +
      `&category=${encodeURIComponent(category.value ?? '')}` +
      `&sort=${encodeURIComponent(sort.value)}`
    )

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    products.value = await response.json()
  } catch (e) {
    error.value = 'Search failed'
  } finally {
    loading.value = false
  }
})
```

Production symptoms:

- user gõ nhanh `iphone`, nhưng UI đôi lúc cuối cùng hiển thị kết quả của `iph`;
- khi network chậm, DevTools cho thấy nhiều requests cùng in-flight;
- backend p95/p99 tăng mạnh vào giờ cao điểm;
- SQL query count và outbound search dependency calls tăng theo số keystrokes;
- user đổi filter trong khi request cũ đang chạy thì loading indicator nhấp nháy;
- một số request trả 499/aborted ở reverse proxy, nhưng nhiều request cũ vẫn tiếp tục chạy tới database;
- developer đề xuất debounce 500 ms là đủ;
- developer khác đề xuất cache mọi search response 10 phút trên backend;
- QA nói lỗi khó tái hiện vì local network quá nhanh.

Chưa biết chắc:

- watcher có `immediate` hay được trigger thêm từ lifecycle code khác;
- API có propagate `RequestAborted`/`CancellationToken` xuống EF Core/external calls hay không;
- search endpoint có caching/CDN hay không;
- result freshness requirement;
- request nào thực sự expensive;
- có pagination hay request size limit không;
- search dependency có rate limit hay bulk behavior nào không.

## Câu hỏi chính

Bạn sẽ điều tra incident này như thế nào từ browser đến backend, xác định race condition nào làm stale response ghi đè state mới, và redesign frontend/backend ra sao để giảm request storm mà không che lỗi bằng cache hoặc debounce một cách máy móc?

## Câu hỏi làm rõ nên cân nhắc

1. Search được trigger chỉ bởi watcher này hay còn submit button/lifecycle/store watcher khác?
2. User expectation là search-as-you-type gần realtime hay chỉ cần sau khi ngừng gõ một khoảng ngắn?
3. Backend query có phụ thuộc user/tenant/permission khiến response cache key phải khác nhau không?
4. Khi browser abort request, ASP.NET Core endpoint hiện có nhận và propagate cancellation không?
5. Có correlation ID/request ID nối browser timing với Application Insights/SQL dependency telemetry không?

## Gợi ý tư duy

### Gợi ý 1

Promise hoàn thành theo thời điểm network/dependency kết thúc, không theo thứ tự request được bắt đầu.

### Gợi ý 2

Debounce giảm số request được khởi tạo nhưng không tự bảo đảm response cũ không ghi đè response mới.

### Gợi ý 3

Cancellation phải đi end-to-end; browser abort mà server vẫn query database thì bạn mới chỉ giải quyết nửa pipeline.

## Cấu trúc trả lời đề xuất

1. Reproduce dưới throttled network và rapid interaction.
2. Vẽ timeline request A/B/C từ browser đến backend.
3. Xác định stale-response race và loading-state race.
4. Đo request amplification theo user action.
5. Thêm frontend debounce/dedup/cancellation phù hợp.
6. Bảo vệ state bằng request identity/latest-request semantics.
7. Propagate server cancellation tới DB/dependencies.
8. Đánh giá caching theo correctness/freshness/security.
9. Load test và failure test.
10. Thêm browser + backend telemetry để chứng minh fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra request cũ có thể hoàn thành sau request mới và ghi đè `products`.
- Không cho rằng `await` đảm bảo watcher invocations chạy tuần tự.
- Dùng cancellation (`AbortController`) và/hoặc latest-request token/version để stale response không commit state.
- Debounce search input khi UX cho phép nhưng không coi debounce là race-condition fix duy nhất.
- Loading state phải gắn với active/latest request, không để request cũ set `loading=false` cho request mới.
- Backend nhận `CancellationToken` từ HTTP request và propagate vào EF Core/outbound I/O khi phù hợp.
- Đo backend request rate, query duration, cancellation rate và p95/p99.
- Cache chỉ dùng nếu key/freshness/security semantics đúng.

### Điểm cộng

- Dùng Vue watcher cleanup để abort previous request khi dependency thay đổi.
- Tách text debounce khỏi category/sort changes nếu UX cần phản hồi ngay cho filter.
- Dedupe identical requests và normalize search parameters.
- Có minimum query length hoặc explicit submit cho expensive search nếu product requirement cho phép.
- Server-side rate limit/load shedding khi abuse hoặc accidental storms có thể gây saturation.

### Senior+

- Thiết kế end-to-end latency/cancellation budget.
- Phân biệt browser cancellation với business operation đã có side effect; search GET là read-only nên cancellation dễ áp dụng hơn mutation.
- Tách UI state thành `latestRequestId`, results, error và loading để out-of-order completion không phá state.
- Dùng trace/correlation để chứng minh canceled browser requests có giảm SQL/dependency work thực tế.

## Hướng giải quyết tham khảo

Triệu chứng “gõ `iphone` nhưng cuối cùng thấy `iph`” là dấu hiệu điển hình của out-of-order completion.

Giả sử:

- request A cho `iph` bắt đầu lúc 10:00:00 và mất 900 ms;
- request B cho `ipho` bắt đầu sau đó và mất 200 ms;
- request C cho `iphone` mất 250 ms.

B/C có thể hoàn thành trước A. Mỗi watcher invocation độc lập; `await fetch()` chỉ pause invocation hiện tại, không serialize các invocation khác. Khi A cuối cùng hoàn thành, code hiện tại vẫn thực hiện:

```ts
products.value = await response.json()
```

nên stale result có thể ghi đè latest result.

Tôi sẽ reproduce bằng Chrome/Playwright network throttling hoặc proxy delay, gõ nhanh và lưu network waterfall. Mỗi request thêm request ID và query snapshot để correlation với backend telemetry.

Frontend fix có hai lớp.

Thứ nhất, giảm request không cần thiết bằng debounce nếu UX cho phép. Ví dụ text input có thể debounce 200–400 ms tùy UX evidence, trong khi category/sort có thể trigger ngay. Con số không nên lấy từ thói quen; test perceived latency và request reduction.

Thứ hai, cancel previous request và bảo vệ latest state. Conceptually:

```ts
let currentController: AbortController | null = null
let requestVersion = 0

watch([query, category, sort], async () => {
  const version = ++requestVersion

  currentController?.abort()
  const controller = new AbortController()
  currentController = controller

  loading.value = true
  error.value = null

  const q = query.value
  const c = category.value
  const s = sort.value

  try {
    const response = await fetch(buildUrl(q, c, s), {
      signal: controller.signal
    })

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    const data = await response.json()

    if (version === requestVersion) {
      products.value = data
    }
  } catch (e) {
    if (controller.signal.aborted) {
      return
    }

    if (version === requestVersion) {
      error.value = 'Search failed'
    }
  } finally {
    if (version === requestVersion) {
      loading.value = false
    }
  }
})
```

Trong Vue, tôi cũng có thể dùng watcher cleanup API phù hợp với version đang dùng để abort request cũ khi watcher reruns/unmounts. Tôi sẽ xác minh API cụ thể theo Vue version của project trước khi code.

`AbortController` giúp browser hủy fetch, nhưng backend cần hợp tác. ASP.NET Core endpoint nên nhận `CancellationToken`/`HttpContext.RequestAborted` và truyền xuống EF Core async methods, HttpClient/dependency calls, search client v.v. Nếu backend catch `OperationCanceledException` rồi tiếp tục work hoặc không truyền token xuống, DB vẫn chịu tải dù browser đã rời đi.

Ví dụ endpoint:

```csharp
[HttpGet("search")]
public async Task<ActionResult<SearchResponse>> Search(
    [FromQuery] SearchRequest request,
    CancellationToken cancellationToken)
{
    var result = await _searchService.SearchAsync(request, cancellationToken);
    return Ok(result);
}
```

Service/repository tiếp tục propagate token vào `ToListAsync(cancellationToken)` và outbound calls.

Tôi không cache mọi response 10 phút mặc định. Search có thể phụ thuộc tenant, permission, locale, price/availability, index freshness và sort. Cache key sai có thể thành data leak. TTL 10 phút có thể vi phạm freshness. Nếu evidence cho thấy repeated identical queries đủ nhiều, cache có thể hữu ích, nhưng cần key dimensions, TTL/invalidation và stale behavior rõ.

Backend cũng cần tối ưu query độc lập với frontend: pagination, indexes/search-engine query, response size, timeout và optional rate limiting. Frontend fix không cứu một query intrinsically đắt.

Testing:

- rapid typing với network delay random để force out-of-order responses;
- category/sort thay đổi liên tiếp;
- unmount/navigate away khi request in-flight;
- request bị abort trước/giữa DB query;
- backend timeout/dependency 500;
- 50–100 concurrent users search-as-you-type;
- Playwright test assert latest query luôn quyết định visible result.

Telemetry cần nối browser event/request ID tới backend trace; theo dõi requests/user action, canceled requests, SQL dependency duration, p95/p99, search dependency rate, active requests và response payload size. Fix chỉ được coi là thành công khi không chỉ UI đúng mà backend work amplification thực sự giảm.

## Mẫu trả lời trong phỏng vấn

“Em sẽ reproduce bằng network throttling vì đây có vẻ là out-of-order response race. Mỗi watcher invocation chạy độc lập; request `iph` có thể hoàn thành sau `iphone` và ghi đè state mới. `await` không serialize các watcher runs.

Em dùng debounce để giảm request theo UX, nhưng thêm `AbortController` để cancel previous fetch và request version để chỉ latest request được commit `products/error/loading`. Sau đó em propagate cancellation từ ASP.NET Core xuống EF Core và outbound calls; nếu browser abort mà SQL vẫn chạy thì backend load chưa được xử lý.

Em không cache 10 phút mặc định vì search có tenant/permission/freshness semantics. Em đo request count trên mỗi user action, cancellation, SQL/dependency duration và p95/p99, rồi chạy Playwright với delayed/out-of-order responses để chứng minh latest state luôn đúng.”

## Câu hỏi đào sâu

1. Nếu backend response rất nhanh nhưng frontend vẫn đôi lúc gọi duplicate identical requests, bạn sẽ tìm những trigger nào trong Vue lifecycle/store/watchers?
2. Nếu search result chứa price thay đổi thường xuyên, bạn đánh giá client cache/backend cache như thế nào?
3. Một teammate muốn bỏ cancellation và chỉ dùng `requestVersion` vì UI đã đúng; bạn phản biện gì về system capacity?

## Lỗi trả lời thường gặp

- Chỉ thêm debounce và coi race đã hết.
- Không bảo vệ `loading`/`error` khỏi stale request completion.
- Abort browser request nhưng không propagate cancellation ở server.
- Cache search response mà bỏ qua tenant/permission/freshness key.
- Test chỉ trên localhost/network nhanh.

## Thang điểm 0–10

- **0–2:** Chỉ tăng debounce hoặc retry.
- **3–4:** Nhận ra async race nhưng fix chỉ ở UI.
- **5–6:** Có abort/latest-request semantics và server cancellation cơ bản.
- **7–8:** Có end-to-end telemetry, load testing, cache correctness và Vue lifecycle handling tốt.
- **9–10:** Chứng minh full-stack amplification bằng evidence, thiết kế latency/cancellation budget và cân bằng UX, capacity, freshness, security.

# Câu 3 — Thiết kế upload file lớn: backend proxy hay direct-to-Blob, quét malware và xử lý bất đồng bộ thế nào?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, SAS, Managed Identity, ASP.NET Core, Azure Service Bus, Azure Functions/Worker Service, security, distributed systems, file processing, observability, failure recovery

## Bối cảnh

Một document-management platform cho phép user upload PDF, Office documents và ảnh.

Hiện tại frontend gửi file qua ASP.NET Core API:

`Browser -> API -> Azure Blob Storage`

API nhận toàn bộ upload, kiểm tra metadata rồi stream vào Blob Storage. Hệ thống sắp mở cho enterprise customers và requirement thay đổi:

- file phổ biến 10–100 MB;
- file lớn có thể tới nhiều GB;
- nhiều uploads đồng thời;
- sau upload phải quét malware;
- extract metadata/text preview;
- lưu document record trong SQL Server;
- chỉ file đã scan an toàn mới được download/share;
- cần progress/status cho frontend;
- production chạy nhiều App Service instances;
- secrets phải lưu an toàn;
- user chỉ được upload vào phạm vi account/tenant của mình;
- upload lỗi giữa chừng phải retry được;
- external processing có thể mất vài phút.

Team đang tranh luận:

1. giữ backend proxy vì “server kiểm soát được mọi byte”;
2. cho browser upload trực tiếp vào Blob bằng SAS để giảm load API;
3. đưa toàn bộ xử lý vào Azure Functions;
4. dùng BackgroundService trong web app để khỏi thêm service;
5. một architect muốn dùng Kubernetes vì có nhiều bước processing.

Chưa biết chắc:

- maximum file size business thật sự cần;
- client có cần resumable/chunked upload không;
- malware scanning technology/service cụ thể;
- processing CPU/memory profile;
- retention/lifecycle policy;
- download authorization model;
- availability/SLA;
- team đã vận hành Service Bus/Functions/Kubernetes ở mức nào.

## Câu hỏi chính

Hãy thiết kế end-to-end upload/processing architecture cho hệ thống này và giải thích khi nào bạn chọn backend proxy hay direct-to-Blob, cách cấp quyền upload/download an toàn, cách chuyển file qua trạng thái quarantine → scanned → processed, xử lý retry/duplicate/failure ra sao, và tiêu chí chọn Functions, Worker Service hay kiến trúc đơn giản hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Có requirement phải inspect file content trước khi bytes đi vào storage không, hay quarantine storage được chấp nhận?
2. Maximum file size, average upload duration và expected concurrent uploads là bao nhiêu?
3. User có cần resume upload khi network bị ngắt không?
4. Malware scan/extraction là CPU-heavy, external API hay managed service; timeout và retry characteristics thế nào?
5. File sau khi an toàn có được public/CDN access hay mọi download vẫn cần authorization per user/tenant?

## Gợi ý tư duy

### Gợi ý 1

Direct upload không đồng nghĩa mất kiểm soát nếu backend chỉ phát credential ngắn hạn, scoped chính xác tới resource/permission cần thiết.

### Gợi ý 2

“Blob uploaded” không nên đồng nghĩa “document usable”. Hãy thiết kế explicit state machine và quarantine boundary.

### Gợi ý 3

Retry ở pipeline bất đồng bộ phải đi cùng idempotency; event duplicate hoặc worker crash sau side effect không được tạo hai document/processings trái ngược nhau.

## Cấu trúc trả lời đề xuất

1. Clarify security, file size, resumability, SLA và processing profile.
2. Xác định trust boundaries và document lifecycle states.
3. So sánh backend proxy với direct-to-Blob.
4. Thiết kế delegated upload permission.
5. Thiết kế metadata/document record và finalize handshake.
6. Trigger asynchronous processing an toàn.
7. Thiết kế idempotency/retry/DLQ/reconciliation.
8. Chọn Functions vs Worker Service theo workload.
9. Thiết kế download authorization và safe release.
10. Thiết kế observability, lifecycle cleanup, testing và deployment.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cho client biết storage account key.
- Nếu direct upload, SAS phải short-lived, least privilege, scoped resource; ưu tiên user delegation SAS khi architecture phù hợp.
- Upload vào quarantine/private area trước khi scan.
- File chưa scan không được coi là safe/downloadable.
- Có document processing state machine trong durable store.
- Validate file name/type/size nhưng không tin MIME extension alone là security validation.
- Processing async phải idempotent và chịu duplicate/retry/crash.
- Không chạy long/unbounded processing trong request path.
- Có cleanup cho abandoned uploads và failed/quarantined files.
- Download phải re-authorize user/resource, không chỉ biết blob URL.

### Điểm cộng

- Backend tạo upload session/document ID trước rồi phát SAS chỉ cho blob path cụ thể.
- Blob name dùng generated opaque ID, không dùng raw user filename làm authority/path logic.
- Metadata chứa expected size/checksum/content type nhưng server verify sau upload.
- Dùng Service Bus/event workflow để decouple scan/extract/preview khi reliability cần.
- Có status API/push notification cho client.
- Managed Identity cho server/worker truy cập Blob/Service Bus/Key Vault thay vì connection strings nơi platform hỗ trợ.

### Senior+

- Thiết kế state transitions bằng optimistic concurrency/version để duplicate processors không advance state sai.
- Có reconciliation job tìm `Uploading` quá lâu, blob có nhưng DB chưa finalized, DB finalized nhưng event chưa publish.
- Phân biệt upload idempotency với processing idempotency và download authorization.
- Đưa ra criteria rõ để chọn Functions vs Worker Service vs Kubernetes thay vì theo xu hướng.
- Thiết kế staged containers/prefixes và permissions để scanner có read quarantine, processor có scoped access, public delivery không bao giờ thấy quarantine.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng trust boundary và lifecycle, không bắt đầu từ Azure service list.

Một document có thể có states như:

`Created -> Uploading -> Uploaded -> Scanning -> Safe -> Processing -> Ready`

và failure states như:

`UploadExpired`, `Rejected`, `ScanFailed`, `Malicious`, `ProcessingFailed`.

Tên states cụ thể tùy business, nhưng nguyên tắc là `Uploaded` không đồng nghĩa `Ready`.

### Backend proxy vs direct-to-Blob

Backend proxy có ưu điểm:

- server kiểm soát request flow tập trung;
- dễ enforce một số validation/policies trước storage;
- client implementation đơn giản hơn.

Nhưng với file hàng trăm MB tới nhiều GB và concurrency cao, API instances trở thành data plane: network bandwidth, connection lifetime, memory/buffer risk, request timeout và scale cost đều tăng. API đang nhận bytes chỉ để chuyển tiếp sang storage.

Direct-to-Blob thường phù hợp hơn nếu business chấp nhận file đi vào private quarantine trước scan. Flow:

1. Client gọi `POST /documents/upload-sessions`.
2. Backend authenticate + authorize tenant/user + validate requested metadata/limits.
3. Backend tạo `DocumentId`/upload record trạng thái `Uploading`.
4. Backend cấp short-lived SAS chỉ cho blob path cụ thể và permission cần thiết.
5. Browser upload trực tiếp tới Blob.
6. Client gọi finalize hoặc backend nhận storage event/verify blob existence.
7. Backend verify size/checksum/metadata theo capability.
8. Document chuyển `Uploaded` và enqueue scan workflow.

Microsoft hiện khuyến nghị khi cần SAS cho Blob Storage nên ưu tiên user delegation SAS được ký dựa trên Microsoft Entra credentials thay vì SAS ký bằng storage account key khi có thể. SAS phải được bảo vệ như credential: giới hạn resource, permissions và expiry. Managed Identity/RBAC có thể được dùng cho backend để xin user delegation key hoặc truy cập storage mà không giữ account key trong code/config.

Tôi không cấp SAS container-wide với write/read/delete dài hạn cho browser. Chỉ write/create vào một blob path cụ thể, expiry ngắn, HTTPS-only theo policy phù hợp. Nếu client cần resumable/chunked upload, dùng Blob block upload/client SDK capability phù hợp và upload session ownership trong backend.

### Quarantine và scan

Blob mới đi vào private quarantine container/prefix. User không có download SAS cho quarantine. Scanner có least-privilege access để đọc file; kết quả scan được persist vào document state.

File extension/MIME header chỉ là metadata, không phải bằng chứng file an toàn. Tôi validate:

- maximum size;
- allowed business types;
- magic/content signatures khi scanner/parser hỗ trợ;
- malformed archives/zip-bomb protections nếu format liên quan;
- path/name normalization cho display;
- parser sandbox/resource limits tùy threat model.

Nếu malicious → state `Malicious/Rejected`, deny download, retain/delete theo security/audit policy. Nếu scanner unavailable → không fail-open; giữ quarantine và retry/alert theo policy.

### Async processing

Sau `Uploaded`, tôi phát work tới Service Bus hoặc durable queue tương đương. Consumer scan cần idempotent theo `DocumentId + processingVersion`. Duplicate message không được scan rồi tạo duplicate DB rows hoặc chuyển state ngược.

Tôi tránh dual-write kiểu:

1. update DB `Uploaded`;
2. publish message;

nếu crash giữa hai bước có thể mất processing. Có thể dùng Outbox Pattern hoặc reconciliation scanner tùy complexity/volume. Nếu hệ thống đã dùng Service Bus và reliability quan trọng, outbox là lựa chọn đáng cân nhắc.

Processor workflow có thể là:

- Scan worker: `Uploaded -> Scanning -> Safe/Malicious`;
- Extraction worker: `Safe -> Processing -> Ready/ProcessingFailed`;
- Preview generation có thể tách nếu resource profile khác.

Không nhất thiết một message cho mọi tiny step; granularity phải cân bằng operability và complexity.

### Functions vs Worker Service

Azure Functions phù hợp khi workload event-driven, execution model/limits phù hợp và team muốn managed scaling. Nhưng tôi không chọn Functions chỉ vì có queue trigger. Với processing dài, CPU/memory-heavy, native binaries hoặc cần kiểm soát process/runtime nhiều hơn, Worker Service/container có thể rõ ràng hơn.

`BackgroundService` chạy bên trong web app có thể đủ cho workload nhỏ/best-effort, nhưng với production document pipeline tôi lo deployment/restart của web, horizontal scaling, resource contention giữa HTTP và processing, duplicate execution và independent scaling. Tách worker deployable thường cho boundary vận hành tốt hơn.

Kubernetes chỉ hợp lý nếu organization đã có platform và workload cần orchestration/container capabilities cụ thể. “Có nhiều bước” không tự tạo requirement cho Kubernetes.

### Download

Khi document `Ready`, download request vẫn đi qua backend authorization:

1. authenticate user;
2. verify tenant/resource permission;
3. verify document state safe/ready;
4. trả file qua backend hoặc phát read-only short-lived SAS/redirect tùy performance/security requirement.

Nếu dùng SAS download, thời hạn ngắn và scoped đúng blob. Không lưu permanent public URL cho private documents.

### Failure/recovery

Các failure quan trọng:

- client upload nửa chừng → session timeout + cleanup uncommitted/orphan data;
- blob upload xong nhưng finalize call mất → reconciliation/event detection;
- DB updated nhưng enqueue fail → outbox/reconciliation;
- scanner timeout → bounded retry, không release file;
- worker crash sau scan trước DB update → idempotent reprocessing/requery scan result nếu có;
- duplicate message → state/version check;
- preview parser crash trên malicious/malformed file → sandbox/resource limit + failure isolation;
- Blob unavailable → retry/backoff theo SDK/service guidance, không infinite retry.

Document row nên có status, version, blob identity, tenant, uploader, size/hash khi available, timestamps, failure code, processing attempt info. State transition dùng concurrency check để hai workers không ghi đè nhau.

### Observability

Tôi muốn dashboard:

- upload sessions created/completed/expired;
- bytes uploaded và duration;
- failed/direct upload error rate;
- scan queue depth/age;
- scan duration/success/malicious/failure;
- processing queue depth;
- end-to-end `Created -> Ready` p50/p95/p99;
- retries/DLQ;
- orphan blob/document counts;
- authorization denied download attempts;
- worker CPU/memory nếu extraction nặng.

Mọi stage dùng `DocumentId`/correlation ID xuyên suốt, nhưng không log SAS tokens hay raw sensitive content.

Testing gồm:

- unauthorized tenant xin SAS cho document khác;
- expired/over-permissioned SAS validation;
- oversized/malformed/malicious file;
- interrupted/resumed upload;
- duplicate finalize;
- duplicate Service Bus message;
- scanner timeout/down;
- worker crash giữa state transitions;
- concurrent processors;
- download trước scan phải bị deny;
- load test nhiều multi-GB uploads mà API data-plane không bị saturation.

## Mẫu trả lời trong phỏng vấn

“Với file lớn và concurrency cao, em ưu tiên API là control plane chứ không phải data plane nếu security model cho phép. Backend tạo upload session/document ID, authorize tenant rồi phát short-lived least-privilege SAS cho đúng blob quarantine; browser upload thẳng Blob. Em không cấp account key và ưu tiên user delegation SAS/Managed Identity theo Azure security guidance khi phù hợp.

Upload xong chưa được download. Document đi qua durable states `Uploaded -> Scanning -> Safe -> Processing -> Ready`; scanner/worker xử lý async qua queue, idempotent theo DocumentId/version và file fail scan không được fail-open. Em có outbox hoặc reconciliation để xử lý gap DB-message và orphan upload.

Functions hay Worker Service phụ thuộc execution profile; Kubernetes chỉ khi có requirement/platform maturity thật. Download luôn re-authorize resource rồi mới trả short-lived read access. Em theo dõi queue age, scan duration, retries, orphan files và end-to-end time-to-ready.”

## Câu hỏi đào sâu

1. Nếu browser upload 8 GB thành công nhưng mất mạng trước khi gọi finalize, hệ thống của bạn phát hiện và recover thế nào mà không tạo orphan vĩnh viễn?
2. Nếu malware scanner mất 30 phút outage, bạn ưu tiên availability hay security ra sao và user experience nên thế nào?
3. Một architect muốn cho Blob container public-read sau khi scan để giảm backend load; bạn phản biện thế nào nếu documents có tenant-level authorization?

## Lỗi trả lời thường gặp

- Đưa storage account key xuống client.
- Cấp SAS container-wide/quyền rộng/thời hạn dài không cần thiết.
- Cho download ngay khi blob upload xong trước scan.
- Dùng queue retry nhưng consumer không idempotent.
- Chọn Functions/Kubernetes theo tên công nghệ thay vì execution/operational requirements.

## Thang điểm 0–10

- **0–2:** Chỉ nói “upload Blob rồi scan”.
- **3–4:** Có SAS và async worker nhưng thiếu quarantine/idempotency/failure recovery.
- **5–6:** Có secure delegated upload, lifecycle states, queue processing, authorization và monitoring.
- **7–8:** Có outbox/reconciliation, state concurrency, resumability, least-privilege identities và workload-based compute choice.
- **9–10:** Thiết kế đầy đủ trust boundaries, failure semantics, operability, cleanup, security posture và giải thích rõ điều kiện đổi recommendation.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Authentication không thay thế resource authorization:** JWT hợp lệ chỉ xác định trusted identity; backend vẫn phải enforce tenant/resource ownership và permission.
- **Security boundary phải nằm ở server:** frontend filtering và client-supplied tenant identifiers không thể thay authorization policy/query scoping.
- **Async UI có thể race dù từng function dùng `await`:** nhiều watcher invocations chạy độc lập và response cũ có thể hoàn thành sau response mới.
- **Cancellation cần đi end-to-end:** browser abort chỉ có giá trị capacity khi server propagate cancellation tới database/dependencies.
- **Large-file architecture nên tách control plane khỏi data plane khi phù hợp:** short-lived scoped SAS cho direct upload có thể giảm API load mà vẫn giữ authorization.
- **Uploaded không đồng nghĩa trusted:** quarantine, malware scanning, durable state machine và idempotent processing phải được thiết kế trước khi file được release.

## Mẫu tư duy cần nhớ

1. **Authenticate identity, then authorize the specific resource.**
2. **Latest user intent must win over out-of-order async completion.**
3. **Cancellation only helps capacity when every relevant layer cooperates.**
4. **Treat uploaded content as untrusted until verification completes.**
5. **Design retry together with idempotency, durable state and reconciliation.**
