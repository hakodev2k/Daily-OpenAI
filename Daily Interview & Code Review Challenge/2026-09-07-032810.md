# Code Review Challenge 1 — CMS page cache làm lộ nội dung cá nhân hóa và giữ stale content sau publish

**Chủ đề:** C#/.NET, ASP.NET Core, Optimizely CMS architecture, CDN/Akamai caching, cache invalidation, multi-instance consistency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một marketing website dùng ASP.NET Core và Optimizely CMS. Website chạy trên nhiều App Service instance phía sau CDN. Một số trang có nội dung hoàn toàn public, nhưng một số block có thể thay đổi theo:

- culture;
- campaign query string;
- user đăng nhập hay anonymous;
- customer segment được backend xác định;
- preview/edit mode của editor.

Traffic read lớn hơn write rất nhiều. Editor kỳ vọng nội dung publish mới xuất hiện trong vài phút. Production gần đây có các hiện tượng:

- editor publish rồi nhưng một số user vẫn thấy nội dung cũ khá lâu;
- cùng một URL nhưng user khác nhau đôi khi thấy CTA không đúng segment;
- sau khi scale out, một instance trả nội dung mới còn instance khác trả nội dung cũ;
- memory tăng dần trong nhiều ngày;
- support ghi nhận một trang personalized đôi khi bị edge cache và phục vụ lại cho anonymous user.

Team bổ sung một service cache HTML như sau. Các abstraction `ICmsPageRenderer` và `IEdgePurgeClient` là service nội bộ của hệ thống; bài toán không yêu cầu nhớ API riêng của một CMS vendor.

## Đoạn code cần review

```csharp
public sealed class CmsPageService
{
    private static readonly ConcurrentDictionary<string, string> HtmlCache = new();

    private readonly ICmsPageRenderer _renderer;
    private readonly IEdgePurgeClient _edgePurge;
    private readonly ILogger<CmsPageService> _logger;

    public CmsPageService(
        ICmsPageRenderer renderer,
        IEdgePurgeClient edgePurge,
        ILogger<CmsPageService> logger)
    {
        _renderer = renderer;
        _edgePurge = edgePurge;
        _logger = logger;
    }

    public async Task<string> RenderAsync(
        string path,
        string culture,
        ClaimsPrincipal user,
        string? campaign,
        CancellationToken cancellationToken)
    {
        if (HtmlCache.TryGetValue(path, out var cached))
            return cached;

        var segment = user.FindFirst("segment")?.Value ?? "anonymous";

        var html = await _renderer.RenderAsync(
            path,
            culture,
            segment,
            campaign,
            cancellationToken);

        HtmlCache[path] = html;
        return html;
    }

    public void ConfigureResponse(HttpResponse response)
    {
        response.Headers.CacheControl = "public,max-age=3600";
    }

    public async Task OnContentPublishedAsync(
        string publishedPath,
        CancellationToken cancellationToken)
    {
        HtmlCache.TryRemove(publishedPath, out _);

        _ = _edgePurge.PurgeAsync(
            publishedPath,
            CancellationToken.None);

        _logger.LogInformation(
            "Published content invalidated for {Path}",
            publishedPath);

        await Task.CompletedTask;
    }
}
```

Bạn cần:

1. xác định các lỗi correctness và data-isolation;
2. đánh giá cache key;
3. đánh giá local cache trong môi trường nhiều instance;

Không mặc định rằng mọi trang đều cacheable giống nhau. Không mặc định rằng purge edge luôn thành công.

## Câu hỏi gợi mở

1. `path` có đủ để đại diện cho tất cả biến thể của một page response không?
2. Nếu response chứa CTA theo segment nhưng header là `public`, CDN có thể làm gì với response đó?
3. `static ConcurrentDictionary` hoạt động như thế nào khi application chạy trên 6 instance?
4. Điều gì xảy ra nếu purge CDN fail hoặc process restart ngay sau publish?
5. Cache hiện tại có eviction policy, TTL hoặc size bound không?

Hãy phân biệt rõ bốn lớp có thể cache độc lập:

- CMS/content cache;
- application cache;
- browser cache;
- edge/CDN cache.

Invalidating một lớp không đồng nghĩa các lớp còn lại đã coherent.

## Kết quả code review tham khảo

### Critical — Personalized HTML bị đánh dấu `public` và có thể được shared cache lưu lại

**Vấn đề:**  
`ConfigureResponse` luôn phát `Cache-Control: public,max-age=3600` kể cả khi HTML được render theo `segment`, authentication state hoặc campaign.

**Tại sao xảy ra:**  
HTTP caching policy không phản ánh response variance. Một shared cache như CDN có thể coi response là dùng chung nếu hệ thống không partition cache đúng hoặc không bypass cache cho personalized content.

**Ảnh hưởng production:**  
Một response được render cho segment A có thể bị phục vụ cho segment B hoặc anonymous user. Với nội dung có thông tin cá nhân hay offer riêng, đây có thể là data exposure chứ không chỉ là stale-content bug.

**Cách sửa:**  
Phân loại page thành public-cacheable và private/non-cacheable. Với personalized response, ưu tiên `private`, `no-store` hoặc bypass edge cache tùy requirement. Chỉ cho phép CDN cache response khi output thực sự invariant theo user và cache key của edge đã cover mọi dimension cần thiết.

---

### Critical — Application cache key bỏ qua culture, segment và campaign

**Vấn đề:**  
Cache chỉ key theo `path`.

**Tại sao xảy ra:**  
Output thực tế phụ thuộc ít nhất vào `culture`, `segment` và `campaign`.

**Ảnh hưởng production:**  
Request đầu tiên điền cache sẽ quyết định HTML mà các request sau cùng path nhận được. User tiếng Việt có thể nhận nội dung English; segment anonymous có thể nhận CTA của logged-in segment; campaign A có thể nhận content của campaign B.

**Cách sửa:**  
Hoặc không cache personalized HTML, hoặc xây cache key canonical chứa đúng các dimensions thực sự làm thay đổi response. Không thêm dimension một cách máy móc nếu cardinality quá lớn; trước tiên xác định cacheability contract.

---

### High — Local static cache không coherent giữa nhiều application instance

**Vấn đề:**  
`ConcurrentDictionary` chỉ tồn tại trong process hiện tại.

**Tại sao xảy ra:**  
Scale-out tạo nhiều process với memory độc lập.

**Ảnh hưởng production:**  
Publish event được xử lý ở instance A chỉ xóa cache của A. Instance B/C có thể tiếp tục phục vụ HTML cũ. User thấy response thay đổi theo load balancer routing.

**Cách sửa:**  
Nếu cần application-level shared cache, dùng distributed strategy có invalidation semantics rõ ràng; hoặc giữ local cache nhưng broadcast invalidation đến mọi node. Với CMS, có thể tận dụng platform-level content invalidation thay vì tự cache nguyên rendered HTML nếu chưa chứng minh benefit.

---

### High — Cache không có TTL, eviction hay size bound

**Vấn đề:**  
`ConcurrentDictionary` tăng theo số path từng được request và chỉ giảm khi đúng path được publish.

**Tại sao xảy ra:**  
Không có expiration hoặc memory pressure policy.

**Ảnh hưởng production:**  
Long-running instance có thể giữ hàng nghìn hoặc hàng triệu HTML string, tăng Gen 2 pressure và working set. Path có query/route variants càng làm cardinality tăng.

**Cách sửa:**  
Dùng cache abstraction hỗ trợ expiration, size limit và eviction. Nếu cached object lớn, đo memory cost trước khi quyết định cache rendered HTML.

---

### High — Publish invalidation không cover mọi cache variant

**Vấn đề:**  
`TryRemove(publishedPath)` chỉ xóa một key theo path.

**Tại sao xảy ra:**  
Nếu implementation đúng hơn sau này key theo culture/segment/campaign, một publish có thể tạo nhiều derived variants. Ngoài ra một content block thay đổi có thể ảnh hưởng nhiều page khác nhau.

**Ảnh hưởng production:**  
Một số variant hoặc dependent page tiếp tục stale dù editor đã publish nội dung mới.

**Cách sửa:**  
Mô hình invalidation theo content dependency hoặc surrogate/cache tags. Khi một content item thay đổi, invalidate các derived artifacts liên quan thay vì chỉ exact URL string.

---

### High — Fire-and-forget CDN purge làm mất failure semantics

**Vấn đề:**  
`_edgePurge.PurgeAsync(...)` bị gọi rồi bỏ Task; method dùng `CancellationToken.None` và không await kết quả.

**Tại sao xảy ra:**  
Publish handler không sở hữu lifecycle của operation purge.

**Ảnh hưởng production:**  
Purge có thể fail silently. Process recycle có thể hủy execution giữa chừng. Log vẫn ghi “invalidated” dù edge chưa được purge.

**Cách sửa:**  
Nếu purge là requirement đồng bộ, await và handle failure. Nếu purge cần decouple, enqueue durable work với retry/backoff, idempotency và monitoring. Không dùng fire-and-forget Task trong request/event flow cho side effect quan trọng.

---

### Medium — Không phân biệt preview/edit mode với public delivery

**Vấn đề:**  
Service signature và cache policy không thể hiện preview/edit mode.

**Tại sao xảy ra:**  
CMS delivery semantics bị giản lược thành path → HTML.

**Ảnh hưởng production:**  
Nếu cùng flow được tái sử dụng cho editor preview, unpublished hoặc preview-specific response có thể bị cache sai scope.

**Cách sửa:**  
Preview/edit mode phải bypass public caches và có authorization riêng. Cacheability là một phần của content-delivery contract.

---

### Medium — Không có cache stampede protection

**Vấn đề:**  
Khi cache miss, nhiều request cùng path có thể đồng thời gọi renderer.

**Tại sao xảy ra:**  
`TryGetValue` rồi render rồi set không serialize work cho cùng cache key.

**Ảnh hưởng production:**  
Ngay sau invalidation hoặc cold start, traffic cao có thể tạo spike rendering/CMS/backend dependency load.

**Cách sửa:**  
Chỉ thêm single-flight/per-key coordination nếu metrics cho thấy miss burst gây vấn đề. Không nên mặc định distributed lock cho mọi page; complexity phải được biện minh bằng evidence.

---

### Medium — Logging tuyên bố success quá sớm và thiếu telemetry phân lớp cache

**Vấn đề:**  
Log “invalidated” được ghi mà không biết edge purge có thành công hay không; cũng không có cache hit/miss theo layer.

**Tại sao xảy ra:**  
Observability không mô hình hóa lifecycle invalidation.

**Ảnh hưởng production:**  
Incident stale content khó xác định đang nằm ở CMS, app cache, browser hay CDN.

**Cách sửa:**  
Log publish/content ID, affected routes/cache tags, purge request ID/status; đo app-cache hit ratio, edge cache status và stale-content age.

## Phiên bản đề xuất

Ví dụ dưới đây cố ý giữ solution đơn giản:

- chỉ cache page được xác định là fully public;
- cache local qua `IMemoryCache` với TTL/size policy;
- key cover culture và campaign cho public content;
- personalized page bypass shared/public cache;
- publish đưa purge vào durable queue thay vì fire-and-forget.

```csharp
public sealed class CmsPageService
{
    private readonly IMemoryCache _cache;
    private readonly ICmsPageRenderer _renderer;
    private readonly ICacheInvalidationQueue _invalidationQueue;

    public CmsPageService(
        IMemoryCache cache,
        ICmsPageRenderer renderer,
        ICacheInvalidationQueue invalidationQueue)
    {
        _cache = cache;
        _renderer = renderer;
        _invalidationQueue = invalidationQueue;
    }

    public async Task<PageResult> RenderAsync(
        PageRequest request,
        CancellationToken cancellationToken)
    {
        if (request.IsPreview || request.IsPersonalized)
        {
            var privateHtml = await _renderer.RenderAsync(
                request.Path,
                request.Culture,
                request.Segment,
                request.Campaign,
                cancellationToken);

            return new PageResult(
                privateHtml,
                CacheControl: "private,no-store");
        }

        var key = $"page:{request.Culture}:{request.Path}:{request.Campaign ?? "-"}";

        var html = await _cache.GetOrCreateAsync(key, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            entry.Size = 1;

            return await _renderer.RenderAsync(
                request.Path,
                request.Culture,
                "public",
                request.Campaign,
                cancellationToken);
        });

        return new PageResult(
            html!,
            CacheControl: "public,max-age=60,s-maxage=300");
    }

    public Task OnContentPublishedAsync(
        ContentPublishedEvent published,
        CancellationToken cancellationToken)
    {
        return _invalidationQueue.EnqueueAsync(
            new CacheInvalidationCommand(
                published.ContentId,
                published.AffectedRoutes,
                published.CacheTags),
            cancellationToken);
    }
}
```

Ở hệ thống thực, nếu CDN hỗ trợ cache tags/surrogate keys hoặc purge-by-tag, chúng có thể giảm việc phải biết mọi URL phụ thuộc. Nếu không có khả năng đó, cần maintain dependency mapping hoặc chấp nhận TTL ngắn hơn với trade-off rõ ràng.

## Giải thích thiết kế sau khi sửa

### 1. Cacheability trở thành explicit policy

Không hỏi “có cache trang này không?” theo kiểu binary. Cần biết response có invariant theo user hay không, có preview không, culture/campaign nào làm thay đổi output và layer nào được phép cache.

### 2. Personalized response không đi vào shared public cache

Đây là default an toàn hơn. Chỉ khi có thiết kế edge segmentation rõ ràng và business value đủ lớn mới cân nhắc shared caching cho personalized variants.

### 3. Invalidation là workflow có trạng thái

CDN purge là remote side effect có thể fail. Durable queue giúp retry, audit và quan sát backlog thay vì đánh mất Task.

### 4. Không mặc định distributed cache

Nếu local memory cache + short TTL + CDN đã đủ, thêm Redis chỉ làm hệ thống phức tạp hơn. Distributed cache chỉ hợp lý khi cần coherence/hit ratio/value đủ lớn và đã đo được bottleneck.

## Trade-offs

- Bypass cache cho personalized page tăng origin load; có thể bù bằng caching ở data/component level thay vì toàn HTML.
- Short TTL giảm stale window nhưng tăng render/origin traffic.
- Durable invalidation queue tăng operational complexity nhưng đổi lại có retry, audit và failure visibility.
- Cache tag/dependency mapping chính xác hơn exact-path purge nhưng cần maintain relationship giữa content và rendered pages.
- `IMemoryCache` vẫn per-process; nếu consistency requirement chặt hơn TTL cho phép, cần cơ chế invalidation cross-node hoặc shared cache.

## Cách kiểm thử

1. **Security/integration test:** hai user khác segment request cùng URL; không được nhận HTML của nhau và personalized response không được đánh dấu public-cacheable.
2. **Culture/cache-key test:** cùng path với `vi-VN` và `en-US` phải trả đúng variant.
3. **Multi-instance test:** publish content trong environment có nhiều instance rồi xác minh mọi node/edge hết stale theo SLA.
4. **Failure-path test:** làm CDN purge fail; command phải retry hoặc chuyển trạng thái có thể alert, không được silently mất.
5. **Load test:** tạo cold-cache burst sau publish và đo renderer load, app cache hit ratio, memory và origin latency.

## Quan sát trong production

Theo dõi:

- cache hit/miss ratio của application;
- memory size/entry count hoặc eviction count của local cache;
- CDN cache status/hit ratio;
- age của cached response;
- publish-to-visible latency;
- invalidation queue depth/retry/failure;
- purge request duration và failure rate;
- request latency origin vs edge;
- số response personalized vô tình có public cache policy;
- correlation giữa content publish event, affected route và purge operation.

## Câu hỏi phỏng vấn mở rộng

1. Nếu 95% traffic là anonymous và 5% personalized, bạn sẽ chọn cache ở page level hay component/data level như thế nào?
2. Nếu Akamai purge API tạm unavailable 20 phút, hệ thống nên degrade ra sao để giảm stale-content risk mà không gây origin overload?
3. Nếu một shared content block xuất hiện trên 5.000 pages, exact-URL invalidation còn phù hợp không? Bạn sẽ thay đổi dependency model thế nào?

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface Product {
  id: string
  name: string
  descriptionHtml: string
}

const query = ref('')
const category = ref('all')
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')
let timer: number | undefined

async function search() {
  loading.value = true
  error.value = ''

  try {
    const token = localStorage.getItem('access_token')
    const url = `/api/products/search?q=${query.value}&category=${category.value}`

    const response = await fetch(url, {
      headers: {
        Authorization: `Bearer ${token}`
      }
    })

    const data = await response.json()
    products.value = data.items
  } catch (e) {
    error.value = String(e)
  } finally {
    loading.value = false
  }
}

watch([query, category], () => {
  window.clearTimeout(timer)
  timer = window.setTimeout(() => {
    search()
  }, 200)
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <select v-model="category">
      <option value="all">All</option>
      <option value="cars">Cars</option>
      <option value="parts">Parts</option>
    </select>

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <article v-for="product in products" :key="product.id">
      <h3>{{ product.name }}</h3>
      <div v-html="product.descriptionHtml"></div>
    </article>
  </section>
</template>
```

Escaping mặc định của template bị bypass khi render raw HTML.

**Ảnh hưởng production:**  
Nếu upstream content chứa malicious markup/script-capable payload phù hợp với browser context, UI có thể trở thành XSS vector. Trong admin portal, impact có thể nghiêm trọng vì user thường có quyền cao hơn anonymous visitor.

**Cách sửa:**  
Tốt nhất render plain text nếu business không cần HTML. Nếu thực sự phải render rich HTML, sanitize bằng một allowlist-based sanitizer ở trust boundary phù hợp và xác định source ownership rõ ràng. Không coi “data đến từ backend của mình” là đủ để trust nếu backend lại nhận content từ CMS/third party.

---

### High — Response race làm request cũ overwrite kết quả mới

**Vấn đề:**  
Mọi invocation `search()` đều có quyền set `products.value` khi hoàn tất.

**Tại sao xảy ra:**  
Network completion order không đảm bảo giống request start order.

**Ảnh hưởng production:**  
User gõ `car`, UI có thể cuối cùng hiển thị result của `ca` nếu request cũ hoàn tất muộn hơn.

**Cách sửa:**  
Abort request trước khi tạo request mới và/hoặc dùng request sequence ID; chỉ latest active request được commit state.

---

### High — Loading/error state cũng bị race

**Vấn đề:**  
Request cũ có thể chạy `finally` sau request mới và set `loading=false`; request cũ fail có thể overwrite `error` sau khi request mới thành công.

**Tại sao xảy ra:**  
UI state không gắn với ownership của current request.

**Ảnh hưởng production:**  
Spinner biến mất trong khi current request vẫn chạy hoặc stale error xuất hiện sau successful result.

**Cách sửa:**  
Chỉ latest request được phép thay đổi `products`, `error`, `loading` trong completion path.

---

### High — Không cancel obsolete requests

**Vấn đề:**  
Debounce chỉ giảm request trước khi timer fire; nó không cancel request đã được gửi.

**Tại sao xảy ra:**  
Không dùng `AbortController`.

**Ảnh hưởng production:**  
Typing nhanh vẫn để nhiều request in-flight nếu user pause >200 ms hoặc backend chậm. Backend tiếp tục tốn CPU/DB/network cho kết quả UI không còn cần.

**Cách sửa:**  
Abort request cũ khi search criteria thay đổi. Backend ASP.NET Core nên propagate cancellation đến database/external calls khi phù hợp.

---

### High — HTTP 4xx/5xx không được xử lý đúng

**Vấn đề:**  
Code gọi `response.json()` mà không kiểm tra `response.ok`.

**Tại sao xảy ra:**  
`fetch` resolve Promise khi nhận HTTP response; 4xx/5xx không tự động trở thành exception chỉ vì status code.

**Ảnh hưởng production:**  
500 response có error body khác shape có thể gây secondary exception hoặc bị coi như thành công không rõ ràng. Observability và UX đều kém.

**Cách sửa:**  
Kiểm tra `response.ok`, map status code có chủ đích và chỉ parse success schema khi hợp lệ.

---

### Medium — Query string được concat thủ công

**Vấn đề:**  
`query` và `category` được ghép trực tiếp vào URL.

**Tại sao xảy ra:**  
Không URL-encode input.

**Ảnh hưởng production:**  
Các ký tự đặc biệt có thể thay đổi semantics của query string hoặc làm request sai.

**Cách sửa:**  
Dùng `URLSearchParams`.

---

### Medium — Empty/very-short query vẫn có thể bắn request

**Vấn đề:**  
Watcher không có minimum criteria hoặc reset behavior.

**Tại sao xảy ra:**  
Mọi thay đổi đều schedule search.

**Ảnh hưởng production:**  
Request không cần thiết, đặc biệt khi user xóa text hoặc category change với empty query.

**Cách sửa:**  
Xác định product requirement: minimum length, empty-state hay default list. Cancel active request và clear state khi criteria không đủ.

---

### Medium — Token lấy từ `localStorage` làm tăng impact của XSS

**Vấn đề:**  
Bearer token có thể đọc được bởi JavaScript chạy trong origin.

**Tại sao xảy ra:**  
Storage model đặt credential trong JS-accessible storage.

**Ảnh hưởng production:**  
Nếu XSS xảy ra, attacker có thể đọc token tùy kiến trúc authentication. Risk này đặc biệt đáng chú ý vì component hiện còn dùng raw HTML.

**Cách sửa:**  
Authentication architecture cần được review toàn hệ thống. Nếu dùng BFF/session cookie pattern, HttpOnly cookie có thể giảm token exposure cho JS; nếu SPA bắt buộc giữ bearer token phía client, cần giảm XSS surface, CSP phù hợp và tránh persist token lâu hơn cần thiết. Không có một storage strategy đúng cho mọi hệ thống.

---

### Medium — Error message raw không phù hợp cho UI

**Vấn đề:**  
`String(e)` được show trực tiếp.

**Tại sao xảy ra:**  
Technical exception và user-facing error bị trộn.

**Ảnh hưởng production:**  
UX khó hiểu và có thể vô tình lộ detail không cần thiết nếu error object chứa thông tin nhạy cảm.

**Cách sửa:**  
Map sang stable user message; gửi technical details vào telemetry, không render raw exception.

## Phiên bản đề xuất

Ví dụ sau dùng cả `AbortController` và request ID. Request ID vẫn hữu ích để bảo vệ state trong trường hợp cancellation race hoặc implementation thay đổi.

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

interface Product {
  id: string
  name: string
  description: string
}

const query = ref('')
const category = ref('all')
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')

let timer: number | undefined
let controller: AbortController | undefined
let requestId = 0

async function search() {
  const normalized = query.value.trim()

  controller?.abort()

  if (normalized.length < 2) {
    products.value = []
    loading.value = false
    error.value = ''
    return
  }

  const currentId = ++requestId
  controller = new AbortController()

  const params = new URLSearchParams({
    q: normalized,
    category: category.value
  })

  loading.value = true
  error.value = ''

  try {
    const response = await fetch(`/api/products/search?${params}`, {
      signal: controller.signal,
      credentials: 'same-origin'
    })

    if (!response.ok) {
      throw new Error(`Search failed with status ${response.status}`)
    }

    const data = await response.json() as { items: Product[] }

    if (currentId === requestId) {
      products.value = data.items
    }
  } catch (e) {
    if (e instanceof DOMException && e.name === 'AbortError')
      return

    if (currentId === requestId) {
      error.value = 'Không thể tải kết quả tìm kiếm.'
    }
  } finally {
    if (currentId === requestId) {
      loading.value = false
    }
  }
}

watch([query, category], () => {
  window.clearTimeout(timer)
  timer = window.setTimeout(search, 250)
})

onBeforeUnmount(() => {
  window.clearTimeout(timer)
  controller?.abort()
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <select v-model="category">
      <option value="all">All</option>
      <option value="cars">Cars</option>
      <option value="parts">Parts</option>
    </select>

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <article v-for="product in products" :key="product.id">
      <h3>{{ product.name }}</h3>
      <p>{{ product.description }}</p>
    </article>
  </section>
</template>
```

Ví dụ dùng `credentials: 'same-origin'` để minh họa trường hợp hệ thống đã chọn cookie/BFF authentication. Nếu architecture thực tế dùng OAuth/OIDC SPA bearer token, authentication portion phải được thay bằng cơ chế phù hợp; không nên copy đoạn này rồi coi đó là migration strategy hoàn chỉnh.

## Giải thích thiết kế sau khi sửa

### 1. Latest request sở hữu UI state

Request ID làm rõ invariant: chỉ request mới nhất mới được commit `products`, `error` và `loading`.

### 2. Cancellation giảm wasted work

`AbortController` dừng obsolete client request. Nếu backend propagate `RequestAborted`/`CancellationToken` xuống database hoặc external dependency, wasted server work cũng giảm.

### 3. URL construction an toàn hơn

`URLSearchParams` đảm bảo query values được encode đúng semantics.

### 4. Raw HTML bị loại khỏi view

Nếu rich HTML không phải requirement bắt buộc, render plain text là cách đơn giản và giảm risk nhất. Nếu phải support rich text, sanitizer cần nằm trong design chứ không phải một comment “data trusted”.

### 5. Error handling theo protocol

HTTP status và network exception là hai loại failure khác nhau. Client nên phân biệt đủ để telemetry và UX có ý nghĩa.

## Trade-offs

- Abort/cancel thêm code state-management; với form rất đơn giản và backend cực nhanh có thể chưa cần, nhưng scenario này đã có race production nên complexity là justified.
- Debounce 250 ms là UX/performance choice, không phải universal constant; phải đo request rate và perceived latency.
- Minimum query length giảm load nhưng có thể mâu thuẫn product requirement nếu single-character search hợp lệ.
- BFF/cookie authentication giảm JS token exposure nhưng tăng backend/session/CSRF considerations; không phải auto-win cho mọi SPA.
- Sanitizing rich HTML giữ được formatting nhưng tạo dependency security-critical; plain text an toàn và đơn giản hơn nếu business chấp nhận.

## Cách kiểm thử

1. **Race test:** mock `ca` response chậm 900 ms và `car` response nhanh 100 ms; UI cuối cùng phải hiển thị `car`.
2. **Cancellation test:** gõ liên tiếp nhiều query; request cũ phải abort và không thay đổi UI state.
3. **Failure-path test:** response 500/429/network error phải hiển thị stable error message và spinner phải kết thúc đúng.
4. **Security test:** product description chứa HTML/script-like payload; UI không được execute/render raw content ngoài policy.
5. **E2E/Playwright test:** typing nhanh, đổi category giữa request, navigate/unmount component và quay lại; không có stale result hoặc console error bất thường.

## Quan sát trong production

Theo dõi:

- frontend search request count per user action;
- aborted request count;
- request duration p50/p95/p99;
- HTTP 4xx/5xx/429;
- browser network waterfall;
- stale-result/race symptom thông qua request ID trong debug telemetry nếu cần;
- backend cancellation rate;
- SQL/dependency duration của search API;
- search request volume theo query length;
- frontend error rate;
- CSP/XSS violation report nếu hệ thống sử dụng CSP reporting.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend search sử dụng Elasticsearch và query cũ đã đến cluster trước khi browser abort, cancellation phía client còn giúp được gì và giới hạn của nó là gì?
2. Nếu muốn prefetch hoặc cache query result ở frontend, bạn sẽ thiết kế cache key và stale policy thế nào để không tái tạo stale-state bug?
3. Khi nào bạn chọn server-driven sanitization thay vì client-side sanitization cho CMS/product rich text?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache correctness bắt đầu từ việc xác định **response identity** và **cacheability**, không phải từ việc chọn Redis hay `ConcurrentDictionary`.
- Một CMS page có thể bị cache ở nhiều layer độc lập; invalidating local memory không đồng nghĩa browser hoặc CDN đã fresh.
- Personalized content và shared public cache là tổ hợp rủi ro cao nếu cache key/policy không được thiết kế rõ.
- Remote purge là distributed side effect: có thể fail, cần retry/audit/observability nếu stale-content SLA quan trọng.
- Debounce không giải quyết request race sau khi request đã được gửi.
- Frontend async state cần ownership: chỉ latest relevant request được commit UI state.
- `fetch` HTTP error handling, request cancellation và XSS boundary đều là trách nhiệm end-to-end của full-stack engineering.

## Mẫu tư duy cần nhớ

1. **Define cache identity before implementing cache.**
2. **Never share personalized output unless the sharing boundary is explicit and safe.**
3. **Treat invalidation as a failure-prone workflow, not a local dictionary operation.**
4. **Latest request owns state; obsolete work should be cancelled or ignored.**
5. **Prefer simpler safe rendering over raw HTML unless rich content is truly required.**
