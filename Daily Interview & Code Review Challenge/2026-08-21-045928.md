# Code Review Challenge 1 — Hangfire phát hành vé bị xử lý trùng dưới tải cao

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để phát hành vé sau khi thanh toán thành công. Mỗi job đọc booking từ SQL Server, gọi dịch vụ cấp vé bên ngoài, cập nhật trạng thái và gửi push notification. Bình thường hệ thống chạy ổn, nhưng khi traffic tăng hoặc worker restart, đôi lúc một booking nhận hai vé hoặc hai notification. Một số job bị retry sau timeout mặc dù phía dịch vụ cấp vé có thể đã xử lý request. Nhiều Hangfire worker và nhiều application instance có thể chạy đồng thời.

## Đoạn code cần review

```csharp
public sealed class TicketIssueJob
{
    private readonly AppDbContext _db;
    private readonly ITicketProvider _ticketProvider;
    private readonly IPushNotificationService _push;
    private readonly ILogger<TicketIssueJob> _logger;

    public TicketIssueJob(
        AppDbContext db,
        ITicketProvider ticketProvider,
        IPushNotificationService push,
        ILogger<TicketIssueJob> logger)
    {
        _db = db;
        _ticketProvider = ticketProvider;
        _push = push;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task Execute(Guid bookingId)
    {
        var booking = await _db.Bookings
            .FirstOrDefaultAsync(x => x.Id == bookingId);

        if (booking == null || booking.Status == BookingStatus.Issued)
            return;

        booking.Status = BookingStatus.Processing;
        await _db.SaveChangesAsync();

        var ticket = await _ticketProvider.IssueAsync(new IssueTicketRequest
        {
            BookingId = booking.Id,
            UserId = booking.UserId,
            EventId = booking.EventId
        });

        booking.TicketNumber = ticket.Number;
        booking.Status = BookingStatus.Issued;
        booking.IssuedAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        await _push.SendAsync(
            booking.UserId,
            $"Your ticket {ticket.Number} is ready");

        _logger.LogInformation(
            "Ticket issued for booking {BookingId}: {TicketNumber}",
            booking.Id,
            ticket.Number);
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không atomic — **Critical**

**Problem:** Nhiều worker có thể cùng đọc trạng thái chưa `Issued`, sau đó đều chuyển sang `Processing` và gọi provider.  
**Why:** Query và update không tạo một atomic claim có điều kiện.  
**Impact:** Duplicate ticket và side effect bên ngoài.  
**Fix:** Claim booking bằng conditional update/optimistic concurrency, ví dụ update chỉ khi status còn `Pending`; chỉ worker có affected rows = 1 được tiếp tục.

### 2. External call không có idempotency key — **Critical**

**Problem:** Provider có thể xử lý thành công nhưng client timeout; Hangfire retry và phát hành vé lần nữa.  
**Why:** Timeout không chứng minh operation thất bại.  
**Impact:** Duplicate ticket, chi phí và dữ liệu khó reconcile.  
**Fix:** Nếu provider hỗ trợ, gửi stable idempotency key dựa trên booking/operation ID; nếu không, cần lookup/reconciliation protocol trước retry.

### 3. `Processing` có thể bị kẹt — **High**

**Problem:** Worker crash sau khi đổi trạng thái khiến booking nằm `Processing`.  
**Impact:** Booking không hoàn tất nếu logic retry/claim không hỗ trợ lease hoặc recovery.  
**Fix:** Dùng processing lease với timestamp/owner hoặc state machine có recovery policy.

### 4. Database state và external side effect không atomic — **High**

**Problem:** Không thể dùng một local SQL transaction để atomically commit cả DB và ticket provider.  
**Impact:** Có các trạng thái provider đã cấp vé nhưng DB chưa ghi nhận.  
**Fix:** Thiết kế workflow idempotent và reconciliation; lưu operation ID/provider reference để resume an toàn.

### 5. Notification có thể gửi trùng hoặc bị mất — **High**

**Problem:** Crash sau `SendAsync` nhưng trước khi job kết thúc có thể gửi lại; crash trước send sau DB commit có thể cần retry riêng.  
**Fix:** Ghi notification intent vào outbox trong cùng transaction với state transition; dispatcher gửi và retry độc lập với deduplication key.

### 6. Không truyền cancellation token — **Medium**

**Problem:** DB/external calls không nhận cancellation.  
**Impact:** Shutdown hoặc cancellation khó kiểm soát, request có thể tiếp tục lâu hơn cần thiết.  
**Fix:** Khi execution environment hỗ trợ cancellation, propagate token tới I/O APIs.

### 7. Observability thiếu operation/correlation data — **Medium**

**Problem:** Chỉ log thành công cuối workflow.  
**Impact:** Khó phân biệt retry, provider timeout, claim conflict và reconciliation.  
**Fix:** Structured logs/traces chứa bookingId, jobId, attempt, operationId, provider result và state transition; không log secret/PII không cần thiết.

### 8. `DateTime.UtcNow` khó test và không thống nhất clock abstraction — **Low**

**Fix:** Inject `TimeProvider` để test deterministic và chuẩn hóa time handling.

## Phiên bản code đề xuất

```csharp
public sealed class TicketIssueJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ITicketProvider _provider;
    private readonly TimeProvider _clock;

    public TicketIssueJob(
        IDbContextFactory<AppDbContext> dbFactory,
        ITicketProvider provider,
        TimeProvider clock)
    {
        _dbFactory = dbFactory;
        _provider = provider;
        _clock = clock;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task Execute(Guid bookingId, CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);
        var operationId = $"issue-ticket:{bookingId:N}";

        var claimed = await db.Bookings
            .Where(x => x.Id == bookingId && x.Status == BookingStatus.Pending)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, BookingStatus.Processing)
                .SetProperty(x => x.ProcessingStartedAtUtc,
                    _clock.GetUtcNow().UtcDateTime), ct);

        if (claimed == 0)
        {
            var current = await db.Bookings
                .AsNoTracking()
                .SingleOrDefaultAsync(x => x.Id == bookingId, ct);

            if (current?.Status == BookingStatus.Issued)
                return;

            throw new InvalidOperationException(
                $"Booking {bookingId} could not be claimed safely.");
        }

        var booking = await db.Bookings.SingleAsync(x => x.Id == bookingId, ct);

        var ticket = await _provider.IssueAsync(
            new IssueTicketRequest
            {
                BookingId = booking.Id,
                UserId = booking.UserId,
                EventId = booking.EventId,
                IdempotencyKey = operationId
            }, ct);

        await using var tx = await db.Database.BeginTransactionAsync(ct);

        booking.TicketNumber = ticket.Number;
        booking.ProviderOperationId = ticket.OperationId;
        booking.Status = BookingStatus.Issued;
        booking.IssuedAtUtc = _clock.GetUtcNow().UtcDateTime;

        db.NotificationOutbox.Add(new NotificationOutbox
        {
            Id = Guid.NewGuid(),
            DeduplicationKey = $"ticket-issued:{bookingId:N}",
            UserId = booking.UserId,
            Message = $"Your ticket {ticket.Number} is ready"
        });

        await db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

Implementation trên minh họa hướng thiết kế, không biến external provider và SQL thành một distributed transaction. Nếu claim dùng lease, retry phải có logic reclaim lease hết hạn và reconciliation với provider trước khi gọi lại.

## Trade-offs

Conditional update đơn giản và hiệu quả cho một state transition, nhưng workflow dài cần state machine/lease rõ ràng. Outbox tăng thêm table, dispatcher và cleanup nhưng giảm coupling giữa transaction nghiệp vụ và notification. Idempotency key là lựa chọn tốt nhất khi provider hỗ trợ; nếu provider không hỗ trợ, reconciliation phức tạp hơn và có thể cần business-level uniqueness.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 execution cùng booking; chỉ một execution được claim và provider chỉ tạo một logical ticket.
2. **Failure-path:** provider xử lý thành công nhưng client nhận timeout; retry dùng cùng idempotency key và không tạo ticket thứ hai.
3. **Crash recovery:** giả lập crash sau claim; lease/recovery đưa booking trở lại trạng thái có thể xử lý an toàn.
4. **Outbox integration:** commit booking và outbox cùng transaction; dispatcher retry notification không tạo duplicate logical event.
5. **Load test:** nhiều booking song song, đo claim conflicts, throughput, DB waits và provider latency.

## Quan sát trong production

Theo dõi số job retry, claim conflict, booking ở `Processing` quá SLA, provider timeout/error, idempotency replay, outbox backlog/age và duplicate reconciliation. Trace nên nối Hangfire execution → SQL state transition → provider call → outbox dispatch bằng correlation/operation ID.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không hỗ trợ idempotency key hoặc lookup theo booking ID, bạn thiết kế recovery thế nào?
2. Có nên dùng distributed lock thay conditional update không? Khi nào lock đáng dùng?
3. Nếu notification phải gửi qua RabbitMQ thay vì local dispatcher, bạn đảm bảo DB commit và publish như thế nào?

# Code Review Challenge 2 — API tìm kiếm outlet vừa chậm vừa có lỗ hổng authorization

**Chủ đề:** EF Core query execution, SQL performance, authorization, input boundaries  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** Khoảng 7–8 vấn đề

## Bối cảnh

Một API ASP.NET Core trả về outlet nằm trong viewport bản đồ. Dữ liệu có hàng triệu outlet thuộc nhiều tenant/OpCo. Sau một thay đổi gần đây, QA thấy request có thể mất vài giây khi zoom rộng và memory của application tăng mạnh. Endpoint dùng JWT authentication. Product yêu cầu user chỉ được nhìn outlet thuộc các OpCo mà họ có quyền truy cập.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/outlets")]
public sealed class OutletController : ControllerBase
{
    private readonly AppDbContext _db;

    public OutletController(AppDbContext db) => _db = db;

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        double minLat,
        double minLng,
        double maxLat,
        double maxLng,
        string? opcoCode,
        string? keyword)
    {
        var outlets = await _db.Outlets
            .Include(x => x.Address)
            .Include(x => x.Contacts)
            .Where(x => x.IsActive)
            .ToListAsync();

        var result = outlets
            .Where(x => x.Latitude >= minLat && x.Latitude <= maxLat)
            .Where(x => x.Longitude >= minLng && x.Longitude <= maxLng)
            .Where(x => string.IsNullOrEmpty(opcoCode) || x.OpCoCode == opcoCode)
            .Where(x => string.IsNullOrEmpty(keyword) ||
                        x.Name.Contains(keyword, StringComparison.OrdinalIgnoreCase))
            .OrderBy(x => x.Name)
            .Select(x => new
            {
                x.Id,
                x.Name,
                x.OpCoCode,
                x.Latitude,
                x.Longitude,
                Address = x.Address!.FullAddress,
                Contacts = x.Contacts.Select(c => new { c.Name, c.Email })
            })
            .ToList();

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Thiếu resource/tenant authorization — **Critical**

**Problem:** `[Authorize]` chỉ yêu cầu authenticated principal; code không giới hạn outlet theo OpCo được phép truy cập. User có thể bỏ `opcoCode` hoặc truyền code khác.  
**Impact:** Cross-tenant/cross-OpCo data exposure.  
**Fix:** Resolve allowed OpCo scope từ trusted claims/policy/data store và đưa predicate đó vào server-side query. Không dùng query parameter do client cung cấp làm bằng chứng authorization.

### 2. `ToListAsync()` materialize toàn bộ active outlets trước filter — **High**

**Problem:** Bounding box, OpCo và keyword chạy trong memory.  
**Impact:** DB/network payload lớn, memory allocation, GC pressure và latency tăng theo toàn bộ dataset.  
**Fix:** Giữ pipeline là `IQueryable`, filter/project trước materialization.

### 3. Eager-load collections không cần thiết — **High**

**Problem:** `Include(Address)` và `Include(Contacts)` trước khi lọc có thể làm query/data materialization nặng hơn đáng kể.  
**Fix:** Projection trực tiếp DTO sau filters; chỉ lấy columns/navigation cần thiết. Đánh giá split query nếu shape thực sự cần nhiều collection, nhưng không dùng nó để che giấu việc filter sai vị trí.

### 4. Không giới hạn kích thước viewport/result — **High**

**Problem:** Client có thể request phạm vi rất lớn và nhận lượng dữ liệu không giới hạn.  
**Impact:** Expensive query, response lớn, dễ tạo resource exhaustion.  
**Fix:** Validate coordinate/order/range, giới hạn viewport hoặc result count/paging phù hợp UX.

### 5. Predicate lat/lng cần chiến lược index/query phù hợp — **Medium**

**Problem:** Sau khi đưa filter xuống DB, hiệu năng còn phụ thuộc data distribution và index. Với geo search thường xuyên, spatial point + spatial predicate/index có thể phù hợp hơn hai range predicates.  
**Fix:** Đo execution plan và logical reads; dùng spatial strategy nếu workload chứng minh lợi ích. Không khẳng định index nào nhanh hơn nếu chưa benchmark trên dữ liệu thực.

### 6. Keyword search semantics/performance chưa rõ — **Medium**

**Problem:** In-memory `StringComparison` không thể giữ nguyên khi chuyển trực tiếp sang provider SQL. Search `%keyword%` cũng có thể không tận dụng B-tree index thông thường hiệu quả.  
**Fix:** Xác định yêu cầu case/accent/collation; chọn DB-supported predicate/search mechanism và benchmark. Với search nâng cao có thể cân nhắc full-text/search service nếu justified.

### 7. Projection trả contact email cần kiểm tra business permission — **Medium**

**Problem:** Authentication không mặc nhiên cho phép xem contact PII.  
**Fix:** Xác nhận policy/need-to-know và chỉ project field được phép.

### 8. Không propagate cancellation token — **Low/Medium**

**Fix:** Nhận `CancellationToken` từ action và truyền tới EF Core async operation.

## Phiên bản code đề xuất

```csharp
[Authorize]
[HttpGet("search")]
public async Task<ActionResult<IReadOnlyList<OutletDto>>> Search(
    [FromQuery] OutletSearchRequest request,
    CancellationToken ct)
{
    if (request.MinLat is < -90 or > 90 ||
        request.MaxLat is < -90 or > 90 ||
        request.MinLng is < -180 or > 180 ||
        request.MaxLng is < -180 or > 180 ||
        request.MinLat > request.MaxLat ||
        request.MinLng > request.MaxLng)
    {
        return BadRequest("Invalid bounding box.");
    }

    var allowedOpCos = await GetAllowedOpCosAsync(User, ct);
    if (allowedOpCos.Count == 0)
        return Ok(Array.Empty<OutletDto>());

    if (!string.IsNullOrWhiteSpace(request.OpCoCode) &&
        !allowedOpCos.Contains(request.OpCoCode))
    {
        return Forbid();
    }

    IQueryable<Outlet> query = _db.Outlets
        .AsNoTracking()
        .Where(x => x.IsActive)
        .Where(x => allowedOpCos.Contains(x.OpCoCode))
        .Where(x => x.Latitude >= request.MinLat && x.Latitude <= request.MaxLat)
        .Where(x => x.Longitude >= request.MinLng && x.Longitude <= request.MaxLng);

    if (!string.IsNullOrWhiteSpace(request.OpCoCode))
        query = query.Where(x => x.OpCoCode == request.OpCoCode);

    if (!string.IsNullOrWhiteSpace(request.Keyword))
    {
        var keyword = request.Keyword.Trim();
        query = query.Where(x => x.Name.Contains(keyword));
    }

    var result = await query
        .OrderBy(x => x.Name)
        .Take(500)
        .Select(x => new OutletDto(
            x.Id,
            x.Name,
            x.OpCoCode,
            x.Latitude,
            x.Longitude,
            x.Address != null ? x.Address.FullAddress : null))
        .ToListAsync(ct);

    return Ok(result);
}
```

Đây là baseline an toàn hơn, không phải tuyên bố rằng hai range predicates là geo design tối ưu. Với workload map thực tế, có thể lưu point/spatial column và dùng spatial predicate/index, nhưng quyết định phải dựa trên execution plan và benchmark. `Take(500)` cũng chỉ là ví dụ policy; giới hạn thực tế phải xuất phát từ UX và SLO.

## Trade-offs

Projection giảm tracking/materialization nhưng nếu client cần contacts thì có thể cần projection shape khác hoặc endpoint chi tiết. Spatial index tăng complexity của schema/migration nhưng phù hợp hơn khi geo filtering là workload cốt lõi. Pagination truyền thống không phải lúc nào cũng hợp map viewport; giới hạn số marker, clustering hoặc server aggregation có thể tốt hơn khi zoom rộng.

## Cách kiểm thử

1. **Authorization integration:** user OpCo A không thể lấy outlet OpCo B kể cả truyền `opcoCode=B` hoặc bỏ filter.
2. **SQL integration:** xác nhận generated SQL chứa bounding box và allowed OpCo predicates trước materialization.
3. **Load test:** benchmark viewport nhỏ/lớn trên dataset production-like; đo p95/p99, DB CPU, logical reads và allocation.
4. **Boundary tests:** invalid latitude/longitude, inverted bounds, empty permission scope và oversized viewport.
5. **Data exposure test:** response không chứa contact/PII ngoài policy cho phép.

## Quan sát trong production

Theo dõi endpoint p50/p95/p99 latency, rows returned, response bytes, EF/SQL duration, DB logical reads/CPU, timeout rate, GC/allocation và số request bị reject do invalid/oversized viewport. Trace nên chứa query shape/tenant scope metadata an toàn, không ghi raw token hoặc PII.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao đưa predicate xuống SQL có thể cải thiện lớn ngay cả trước khi thêm index?
2. Khi nào bạn chuyển từ lat/lng range predicate sang spatial `STIntersects`/`STWithin` và bạn benchmark thế nào?
3. Nếu một user có quyền trên hàng nghìn OpCo, `Contains` tạo `IN (...)` lớn; bạn thay đổi authorization filtering ra sao?
