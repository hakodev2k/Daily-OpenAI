# Câu 1 — Scoped service bị giữ trong Singleton: vì sao lỗi chỉ xuất hiện khi production có concurrency?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, dependency injection, service lifetimes, DbContext, concurrency, object lifetime, BackgroundService, disposal, production debugging

## Bối cảnh

Một ASP.NET Core API trên .NET 8 có service sau:

```csharp
public sealed class ReportCache
{
    private readonly AppDbContext _dbContext;

    public ReportCache(AppDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public async Task<IReadOnlyList<ReportDto>> LoadAsync(
        CancellationToken cancellationToken)
    {
        return await _dbContext.Reports
            .AsNoTracking()
            .Select(x => new ReportDto(x.Id, x.Name))
            .ToListAsync(cancellationToken);
    }
}
```

Đăng ký DI hiện tại:

```csharp
services.AddDbContext<AppDbContext>(...);
services.AddSingleton<ReportCache>();
```

Ngoài ra một `BackgroundService` cũng inject `ReportCache` để refresh cache mỗi 5 phút.

Trong development single-user, hệ thống chạy ổn. Ở production:

- thỉnh thoảng có lỗi kiểu `A second operation was started on this context instance before a previous operation completed`;
- một số request fail sau deployment hoặc recycle;
- đôi khi xuất hiện `ObjectDisposedException` liên quan đến dependency bị dispose;
- cùng lúc đó CPU và SQL Server đều bình thường;
- team đề xuất bật retry cho mọi lỗi EF Core;
- một developer cho rằng DI container sẽ tự tạo `DbContext` mới cho mỗi method call vì `DbContext` đã đăng ký scoped;
- một developer khác muốn đổi `DbContext` thành singleton để “lifetime khớp với ReportCache”.

Chưa biết chắc:

- `ValidateScopes` có được bật trong environment production không;
- `ReportCache` còn giữ dependency scoped nào khác hay không;
- BackgroundService có chạy song song với request path không;
- `LoadAsync` có thể bị gọi đồng thời trên cùng singleton instance không;
- có code giữ `IServiceProvider` và resolve service thủ công hay không;
- cache có thực sự cần singleton state hay chỉ cần shared external cache.

## Câu hỏi chính

Hãy giải thích ASP.NET Core DI lifetime thực sự hoạt động thế nào trong trường hợp singleton phụ thuộc vào scoped `DbContext`, vì sao lỗi có thể chỉ bộc lộ dưới concurrency hoặc sau lifecycle events, và bạn sẽ sửa thiết kế cho cả request path lẫn BackgroundService như thế nào mà không biến `DbContext` thành singleton.

## Câu hỏi làm rõ nên cân nhắc

1. `ReportCache` có cần giữ state trong process hay chỉ là một service truy cập dữ liệu?
2. Background refresh có thể chạy đồng thời với request đang đọc cùng singleton không?
3. `DbContext` được resolve từ root provider hay request scope?
4. Production có bật scope validation không, và startup có warning/error nào liên quan captive dependency không?
5. Nếu cache cần dùng chung nhiều instances, in-memory singleton có còn đúng requirement không?

## Gợi ý tư duy

### Gợi ý 1

Lifetime của dependency không tự động “thu nhỏ lại” chỉ vì type đó được đăng ký scoped.

### Gợi ý 2

Một singleton sống lâu có thể giữ một dependency ngắn hạn lâu hơn intended lifetime của nó; đây là captive dependency.

### Gợi ý 3

BackgroundService không có request scope tự nhiên. Nếu cần scoped service, phải tạo scope rõ ràng cho từng unit of work.

## Cấu trúc trả lời đề xuất

1. Xác định lifetime graph và resolution path.
2. Giải thích root scope, request scope và captive dependency.
3. Giải thích DbContext thread-safety/concurrency implications.
4. Phân biệt lifetime bug với transient database failure.
5. Kiểm tra scope validation/logs/runtime stack trace.
6. Thiết kế request service theo scoped lifetime.
7. Thiết kế BackgroundService tạo scope per iteration.
8. Tách cache state khỏi data-access dependency nếu cần.
9. Kiểm thử concurrency/disposal/lifecycle.
10. Theo dõi lỗi sau deployment.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `AddDbContext` mặc định tạo `DbContext` theo scoped lifetime trong ASP.NET Core.
- Nếu singleton resolve một scoped dependency từ root scope, scoped dependency có thể bị giữ như captive dependency trong lifetime dài hơn intended.
- DI container không tự tạo `DbContext` mới cho mỗi method call của singleton.
- `DbContext` không được thiết kế để dùng đồng thời từ nhiều threads/operations.
- Không sửa bằng cách đổi `DbContext` thành singleton.
- Request-oriented service dùng `DbContext` thường nên scoped hoặc transient với dependency graph hợp lý.
- `BackgroundService` cần tạo scope bằng `IServiceScopeFactory` cho mỗi iteration/unit of work khi dùng scoped dependencies.
- Retry không sửa lifetime/thread-safety bug.

### Điểm cộng

- Bật scope validation để phát hiện captive dependency sớm trong development/test.
- Tách singleton cache coordinator khỏi scoped repository/query service.
- Nếu cần tạo context ngoài request scope, cân nhắc `IDbContextFactory<TContext>` khi phù hợp.
- Nhận ra singleton state trong multi-instance deployment không phải shared state toàn hệ thống.
- Nếu cache shared giữa instances, đánh giá Redis/distributed cache thay vì chỉ singleton memory.

### Senior+

- Phân tích root provider resolution và disposal semantics thay vì chỉ lặp lại “scoped per request”.
- Thiết kế object graph để dependency lifetime không dài hơn owner một cách sai ngữ nghĩa.
- Phân biệt concurrency protection ở cache state với lifetime của data-access objects.
- Đưa ra test tái hiện concurrent calls và background/request overlap.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu từ dependency graph. `ReportCache` được đăng ký singleton nên container tạo một instance sống gần như suốt process lifetime. Nếu singleton đó được tạo từ root provider và constructor cần `AppDbContext`, container không tự resolve một context mới cho từng method call. Nó resolve dependency tại thời điểm tạo singleton; context đó bị giữ lâu bất thường.

Đây là captive dependency: object lifetime dài đang giữ object có intended lifetime ngắn hơn. Với `DbContext`, hậu quả còn nghiêm trọng vì context giữ change-tracking/internal state và không hỗ trợ nhiều operations song song trên cùng instance. Nếu request và BackgroundService hoặc hai requests gọi `LoadAsync` cùng lúc, cùng context có thể bị dùng concurrent và sinh lỗi `A second operation was started...`.

`ObjectDisposedException` cũng có thể xuất hiện tùy cách object graph được resolve/dispose hoặc nếu code giữ một scoped service vượt quá scope của nó. Tôi sẽ xác minh bằng startup validation, DI registration audit, stack traces và test concurrency thay vì gắn nhãn đây là transient SQL failure.

Sửa thiết kế phụ thuộc intent.

Nếu `ReportCache` thực chất là data-access/query service, tôi đổi nó thành scoped và để mỗi request dùng scoped `DbContext` riêng.

Nếu thật sự có singleton coordinator giữ cache state, tôi không inject `DbContext` trực tiếp. Tôi inject abstraction/factory phù hợp, hoặc mỗi lần refresh tạo scope:

```csharp
public sealed class ReportRefreshWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public ReportRefreshWorker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var loader = scope.ServiceProvider.GetRequiredService<ReportLoader>();
            await loader.RefreshAsync(stoppingToken);

            await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
        }
    }
}
```

`ReportLoader` có thể scoped và nhận `AppDbContext` scoped. Scope kết thúc sau iteration và context được dispose đúng boundary.

Một lựa chọn khác là `IDbContextFactory<AppDbContext>` cho work không gắn trực tiếp request scope. Khi đó mỗi operation chủ động tạo context riêng và dispose rõ ràng. Tôi vẫn không chia sẻ một context giữa concurrent operations.

Nếu cache phải dùng chung giữa nhiều application instances, singleton memory không đủ. Khi đó tôi đánh giá distributed cache hoặc một data source khác, nhưng không tự động thêm Redis nếu consistency/availability requirement chưa cần.

Testing gồm: concurrent requests gọi cùng functionality, background refresh trùng thời điểm với requests, app recycle, cancellation và deployment restart. Tôi muốn scope validation bật trong non-production pipeline để lỗi lifetime bị phát hiện trước khi deploy.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xem đây là lifetime/concurrency bug trước, không phải lỗi SQL transient. `ReportCache` là singleton nên dependency constructor của nó không được resolve lại mỗi lần method chạy. Nếu nó giữ một scoped `DbContext`, context đó trở thành captive dependency và có thể bị dùng bởi nhiều calls cùng lúc, trong khi `DbContext` không thread-safe cho concurrent operations.

Em sẽ không đổi `DbContext` thành singleton. Với request service, em giữ service scoped. Với `BackgroundService`, em tạo scope cho từng iteration bằng `IServiceScopeFactory`, resolve scoped loader/context trong scope đó rồi dispose. Nếu use case cần tạo context ngoài request scope, em cân nhắc `IDbContextFactory`.

Em cũng bật scope validation, viết concurrency test và kiểm tra liệu cache state có cần shared giữa nhiều instances không. Retry không giải quyết bug lifetime này.”

## Câu hỏi đào sâu

1. Nếu singleton chỉ inject `IDbContextFactory<AppDbContext>` thay vì `AppDbContext`, điều gì vẫn có thể sai nếu code cache context được factory tạo ra vào field?
2. Một teammate muốn đặt `lock` quanh toàn bộ `LoadAsync` để tránh concurrent EF calls; bạn phản biện thế nào?
3. Nếu hệ thống chạy 10 instances và cache phải nhất quán trong 30 giây, bạn có tiếp tục dùng singleton in-memory không?

## Lỗi trả lời thường gặp

- Nghĩ scoped dependency tự động tạo mới cho mỗi method call.
- Đổi `DbContext` thành singleton.
- Dùng retry để che lifetime bug.
- Chỉ thêm `lock` mà không sửa object lifetime.
- Quên rằng BackgroundService cần scope riêng khi dùng scoped services.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất retry hoặc singleton DbContext.
- **3–4:** Biết lifetime mismatch nhưng chưa giải thích resolution/concurrency.
- **5–6:** Giải thích captive dependency, DbContext thread-safety và scope-per-work.
- **7–8:** Có factory option, multi-instance cache reasoning, validation và concurrency testing.
- **9–10:** Kết nối lifetime graph, disposal, concurrency và deployment topology thành design có điều kiện rõ.

# Câu 2 — Redis chậm 2 phút làm API chậm hơn cả khi không có cache: bạn xử lý incident thế nào?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Redis, cache-aside, dependency degradation, timeout, fallback, cache stampede, SQL Server, observability, incident response, distributed systems

## Bối cảnh

Một ASP.NET Core e-commerce API dùng Redis cache cho product-detail data. SQL Server vẫn là source of truth.

Normal flow:

1. đọc Redis theo key `product:{id}`;
2. miss thì query SQL;
3. serialize result và `SET` Redis TTL 10 phút;
4. trả response.

Một incident xảy ra khi Redis latency tăng mạnh trong khoảng 2 phút:

- product-detail p99 tăng từ dưới 300 ms lên 8–15 giây;
- SQL CPU sau đó tăng mạnh;
- Redis timeout count tăng;
- nhiều requests cùng miss hoặc timeout trên cùng hot products;
- sau khi Redis hồi phục, SQL vẫn load cao thêm vài phút;
- application error rate cuối cùng không quá cao vì nhiều requests retry/fallback thành công;
- team đề xuất tăng Redis timeout từ 1 giây lên 10 giây;
- một developer muốn fallback SQL cho mọi Redis error;
- một developer khác muốn xóa toàn bộ cache để “reset trạng thái”.

Chưa biết chắc:

- client retry policy và connection configuration hiện tại;
- cache read/write timeout;
- hot-key distribution;
- SQL capacity nếu toàn bộ traffic bypass cache;
- TTL có jitter hay mọi key cùng expire gần nhau;
- cache miss và cache timeout có được phân biệt trong telemetry không;
- circuit breaker/bulkhead có hay không;
- stale cache có được phép dùng khi Redis đang degrade hay không.

## Câu hỏi chính

Bạn sẽ stabilize incident theo thứ tự nào, phân biệt Redis degradation, cache stampede và SQL overload thứ cấp ra sao, rồi redesign cache/fallback behavior như thế nào để một cache outage không biến thành cascading failure ở source database?

## Câu hỏi làm rõ nên cân nhắc

1. Business chấp nhận product detail stale trong bao lâu khi dependency/cache gặp sự cố?
2. SQL có chịu được 100% read traffic trong vài phút không?
3. Redis timeout khác cache miss đang được ghi nhận thế nào?
4. Các hot products chiếm bao nhiêu phần trăm traffic và TTL distribution ra sao?
5. Client có retry Redis command tự động khiến một request chờ nhiều lần trước khi fallback không?

## Gợi ý tư duy

### Gợi ý 1

Cache không phải lúc nào cũng giúp availability; nếu application chờ cache quá lâu, cache có thể trở thành latency dependency.

### Gợi ý 2

Fallback toàn bộ sang SQL có thể biến cache outage thành database outage.

### Gợi ý 3

Stampede thường cần admission/coalescing/jitter chứ không chỉ TTL dài hơn.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và request budget.
2. Giảm latency amplification từ Redis.
3. Bảo vệ SQL khỏi fallback burst.
4. Correlate Redis timeout, miss, SQL load và hot keys.
5. Kiểm tra retry/timeout/circuit behavior.
6. Thiết kế fallback policy theo dữ liệu/SLO.
7. Thiết kế anti-stampede.
8. Test outage/degraded mode.
9. Khôi phục cache có kiểm soát.
10. Monitor dependency health và cache effectiveness.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Cache miss và cache failure là hai trạng thái khác nhau.
- Tăng Redis timeout quá dài có thể làm user request chờ cache lâu hơn cả query source.
- Fallback toàn bộ sang SQL không an toàn nếu SQL không có capacity cho uncached traffic.
- Cần bounded timeout phù hợp request latency budget.
- Có cơ chế chống stampede/coalescing/single-flight hoặc distributed coordination khi hot key miss đồng thời.
- TTL jitter giúp tránh synchronized expiration.
- Retry phải bounded và tính vào end-to-end deadline.
- Phải đo Redis latency/timeouts, hit rate, miss rate, SQL load và fallback rate.
- Recovery phải tránh warm-up burst làm SQL/Redis quá tải lần nữa.

### Điểm cộng

- Dùng stale-while-revalidate hoặc stale fallback nếu business chấp nhận dữ liệu cũ ngắn hạn.
- Circuit breaker có thể tạm bypass Redis sau threshold thay vì mọi request tiếp tục timeout.
- Bulkhead/rate limit fallback để SQL không nhận vô hạn uncached traffic.
- Negative caching cho “not found” nếu use case phù hợp.
- Hot-key monitoring và prewarming có chọn lọc.

### Senior+

- Thiết kế cache as optimization layer với explicit failure budget, không phải implicit hard dependency.
- Phân tích feedback loop: Redis slow → timeout/retry → fallback SQL → SQL slow → request lifetime dài → concurrency tăng → hệ thống suy giảm thêm.
- Có degraded-mode policy theo business criticality.
- Định nghĩa recovery ramp thay vì mở traffic/cache refresh toàn bộ ngay lập tức.

## Hướng giải quyết tham khảo

Tôi sẽ ổn định incident bằng cách giảm amplification trước. Nếu Redis đang mất 8–10 giây mới timeout, tăng timeout lên 10 giây thường làm p99 tệ hơn. Cache lookup phải có budget ngắn hơn đáng kể so với toàn request và so với source-query path.

Tôi cần phân biệt ba signal: cache miss bình thường, cache timeout/error và SQL source latency. Nếu Redis timeout tăng trước, sau đó fallback/miss tăng và SQL CPU mới tăng, đó là evidence của cascading failure.

Tôi không fallback tất cả requests sang SQL một cách không giới hạn. Nếu SQL chỉ được sizing cho 20–30% uncached load, cache outage có thể kéo SQL xuống. Tôi có thể giới hạn fallback concurrency, shed non-critical traffic, dùng stale data nếu business cho phép, hoặc circuit-break Redis reads ngắn hạn để tránh mỗi request mất timeout budget.

Với hot keys, khi cache hết hạn hoặc bị unavailable, hàng trăm requests có thể cùng query SQL và cùng rebuild một key. Tôi dùng request coalescing/single-flight ở process hoặc coordination phù hợp, cộng TTL jitter để expiry không đồng bộ. Nếu deployment chạy nhiều instances, per-process single-flight vẫn chưa loại bỏ toàn bộ cross-instance stampede nên cần cân nhắc distributed strategy hoặc source-side protection.

Nếu product data có thể stale 30–60 giây, stale-while-revalidate là lựa chọn mạnh: serve snapshot cũ trong degradation window và cho một background refresh có kiểm soát. Nhưng nếu field như price/legal state phải current, tôi tách semantics thay vì dùng stale policy mù quáng.

Tôi cũng kiểm tra client retries. Hai retries Redis cộng một fallback SQL và HTTP retry downstream có thể biến một request thành nhiều dependency attempts. Tổng retry budget phải bounded theo request deadline.

Sau khi Redis hồi phục, tôi không xóa toàn bộ cache. Việc flush có thể biến mọi key thành miss cùng lúc và làm SQL nổ tải. Recovery nên giữ cache còn tốt, refresh dần hot keys và ramp traffic.

Testing phải gồm Redis latency injection, hard outage, synchronized TTL expiry, hot-key burst, SQL degraded mode và recovery. Metrics cần Redis p95/p99, timeout/error rate, hit/miss, fallback rate, stale-served count, SQL QPS/CPU, coalesced refresh count và request p99.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không tăng Redis timeout như phản xạ đầu tiên. Cache là optimization layer nên lookup phải có budget ngắn; nếu Redis chậm hơn source query mà request vẫn chờ, cache trở thành latency dependency.

Em sẽ correlate Redis timeout với fallback/miss và SQL load để xác nhận feedback loop. Trong incident, em giảm retry/timeout amplification, bảo vệ SQL bằng fallback concurrency limit hoặc degraded mode, và nếu business cho phép thì serve stale data ngắn hạn.

Để tránh stampede, em dùng single-flight/coalescing cho hot key, TTL jitter và có strategy phù hợp multi-instance. Khi Redis hồi phục em không flush toàn cache vì sẽ tạo miss storm. Em ramp recovery và monitor hit rate, fallback, SQL QPS, Redis timeout và p99.”

## Câu hỏi đào sâu

1. Nếu price phải tuyệt đối current nhưng product description có thể stale 5 phút, bạn tách cache model và fallback policy thế nào?
2. Một teammate muốn Redis outage thì bypass cache 100% sang SQL vì “SQL là source of truth”; bạn phản biện ra sao?
3. Nếu single-flight trong mỗi instance vẫn gây 20 concurrent refreshes vì có 20 pods, bạn giải quyết thế nào mà không tạo distributed lock quá nặng?

## Lỗi trả lời thường gặp

- Tăng timeout để “cho Redis thêm thời gian”.
- Fallback vô hạn sang SQL.
- Flush toàn bộ cache sau incident.
- Không phân biệt timeout với miss.
- Chỉ thêm TTL mà không xử lý stampede/retry/capacity.

## Thang điểm 0–10

- **0–2:** Chỉ tăng timeout hoặc flush cache.
- **3–4:** Biết fallback nhưng chưa bảo vệ SQL.
- **5–6:** Có bounded timeout, stampede control, TTL jitter và monitoring.
- **7–8:** Có stale/degraded mode, circuit/bulkhead, recovery ramp và failure tests.
- **9–10:** Phân tích được cascading loop, business freshness semantics và capacity boundaries end-to-end.

# Câu 3 — Modular Monolith hay Microservices cho nền tảng approval + notification đang tăng module?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** architecture, Modular Monolith, Microservices, DDD, service boundaries, SQL Server, Azure Service Bus, deployment, observability, reliability, team topology, trade-offs

## Bối cảnh

Một enterprise platform hiện có các module:

- Employee Directory;
- Leave/Approval;
- Timesheet;
- Notification;
- Document Management;
- Reporting.

Backend là một ASP.NET Core solution dùng SQL Server. Team khoảng 8–12 engineers, release 1–2 lần/tuần. Hệ thống hiện chưa gặp throughput bottleneck nghiêm trọng nhưng codebase bắt đầu có vấn đề:

- module gọi trực tiếp repository/entity của nhau;
- database tables dùng chung foreign keys chằng chịt;
- một thay đổi ở Approval dễ ảnh hưởng Reporting hoặc Notification;
- test suite chậm;
- deployment toàn hệ thống dù chỉ đổi một module;
- Product dự kiến thêm nhiều modules trong 2–3 năm tới;
- một số integrations cần asynchronous processing;
- một architect đề xuất “chuyển hết sang microservices ngay để scale tương lai”.

Constraints:

- team chưa có platform/SRE team riêng;
- production support do chính developers đảm nhận;
- dữ liệu HR có authorization/security sensitivity cao;
- một số workflows cần transaction nhất quán trong cùng module;
- reporting cần dữ liệu từ nhiều domain;
- business không yêu cầu mỗi module deploy độc lập ngay hôm nay;
- downtime lớn để rewrite không được chấp nhận.

Chưa biết chắc:

- team ownership theo domain có ổn định không;
- module nào có workload/availability/SLA khác biệt thật sự;
- shared database coupling ở mức nào;
- deployment pipeline hiện chậm vì architecture hay vì test/build tooling;
- cross-module transaction requirements;
- roadmap có external clients cần module APIs độc lập hay không.

## Câu hỏi chính

Hãy quyết định modernization architecture cho 2–3 năm tới giữa giữ layered monolith, chuyển sang Modular Monolith, hoặc tách Microservices. Đề xuất boundaries, data ownership, communication patterns, deployment strategy, reporting integration, security, observability và migration path; giải thích rõ điều kiện nào khiến bạn trì hoãn hoặc chấp nhận microservices.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào có business ownership và lifecycle độc lập thật sự?
2. Có use case nào cần scale/deploy/availability độc lập ngay hiện tại không?
3. Cross-module writes có cần ACID transaction hay có thể eventual-consistent?
4. Reporting cần near-real-time hay batch/eventual-consistent là đủ?
5. Team có đủ operational maturity cho distributed tracing, service ownership, incident handling và versioned contracts không?

## Gợi ý tư duy

### Gợi ý 1

Kiến trúc không nên được chọn theo số lượng module mà theo boundaries, ownership, coupling và operational requirements.

### Gợi ý 2

Modular Monolith có thể tạo boundary mạnh mà vẫn giữ deployment/runtime đơn giản.

### Gợi ý 3

Microservices chuyển complexity từ codebase sang network, data consistency, deployment và operations; hãy chỉ trả chi phí đó khi có requirement tương xứng.

## Cấu trúc trả lời đề xuất

1. Làm rõ business domains, team ownership và SLO.
2. Đánh giá current coupling bằng code/data/deployment dependencies.
3. Xác định bounded contexts/module boundaries.
4. Quy định data ownership và cross-module access.
5. Chọn sync/async communication theo use case.
6. Thiết kế reporting/read models.
7. Thiết kế auth/security boundaries.
8. Chọn deployment/runtime architecture.
9. Đề xuất incremental migration/strangler path.
10. Định nghĩa exit criteria để tách module thành service sau này.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định microservices là đích đến vì hệ thống sẽ có nhiều modules.
- Bắt đầu từ domain/module boundaries và data ownership.
- Ngăn module truy cập trực tiếp tables/entities nội bộ của module khác.
- Modular Monolith là lựa chọn hợp lý khi cần boundary nhưng chưa cần distributed deployment.
- Microservices chỉ có lợi khi independent deployment/scaling/ownership/availability hoặc organizational boundary đủ mạnh.
- Cross-service transaction trở nên khó hơn; cần eventual consistency/outbox/saga khi tách boundaries.
- Reporting xuyên domain không nên phá data ownership bằng shared-table queries tùy tiện nếu muốn modularity bền vững.
- Security/authorization phải là explicit contract ở boundaries.
- Migration nên incremental, không rewrite toàn hệ thống.

### Điểm cộng

- Module có schema/database ownership rõ dù ban đầu vẫn cùng SQL Server instance.
- Internal contracts/API/events thay cho repository/entity sharing.
- Outbox cho integration events khi cần reliable async communication.
- Reporting có projection/read model riêng được cập nhật qua events hoặc ETL phù hợp freshness requirement.
- Contract tests và architecture tests ngăn dependency ngược boundary.

### Senior+

- Đưa ra criteria để extract một module: change velocity cao, ownership riêng, SLA khác, scale profile khác, external integration boundary rõ, deployment independence mang giá trị đo được.
- Thừa nhận microservices làm tăng observability, CI/CD, secret/config, network failure, versioning và incident complexity.
- Dùng “modular first, extract when justified” để giảm optionality cost nhưng không khóa đường phát triển.
- Phân tích team topology: service boundary không bền nếu ownership tổ chức không tương ứng.

## Hướng giải quyết tham khảo

Với dữ kiện hiện tại, tôi thiên về Modular Monolith trước, không phải vì microservices xấu mà vì requirement chưa trả đủ operational cost.

Vấn đề hiện tại chủ yếu là coupling: module gọi repository/entity của nhau, shared database không có ownership và mọi thay đổi lan rộng. Những vấn đề này không tự biến mất khi deploy thành nhiều services; nếu boundaries chưa rõ, ta chỉ tạo distributed monolith.

Tôi sẽ xác định module/bounded context rõ: Approval sở hữu request/state transitions; Timesheet sở hữu timesheet data; Document sở hữu metadata/file lifecycle; Notification sở hữu delivery preferences/status; Reporting không sở hữu transactional state của các module khác.

Ở code level, mỗi module có application/domain/infrastructure boundary riêng và expose contract rõ. Module khác không query trực tiếp DbSet/table nội bộ. Ban đầu có thể vẫn cùng SQL Server instance để giảm ops complexity, nhưng schema/table ownership phải rõ và migration riêng theo module. Nếu muốn extract sau này, việc không chia sẻ trực tiếp tables là điều kiện quan trọng.

Communication trong cùng process có thể synchronous qua module interface khi operation cần immediate result. Những side effects không cần transaction đồng bộ như Notification có thể dùng integration event. Tôi không dùng in-process event rồi gọi đó là microservices; điều quan trọng là semantic boundary.

Nếu Approval commit transaction và cần phát notification event reliably, outbox là lựa chọn phù hợp để commit business state + outbox record cùng transaction, sau đó publisher gửi Azure Service Bus. Notification consumer idempotent. Nhưng tôi chỉ thêm messaging nơi asynchronous decoupling có giá trị, không biến mọi method call thành event.

Reporting cần được thiết kế theo freshness. Nếu daily/near-real-time vài giây-phút là đủ, tôi tạo reporting projection/warehouse/read model từ events hoặc ETL. Nếu một report cần strongly current transactional view, có thể có query API hoặc sanctioned read model; tôi không để reporting trở thành lý do mọi module chia sẻ schema tùy tiện.

Security: authentication có thể centralized ở platform boundary, nhưng authorization rule phải gần domain ownership. Approval module quyết định ai có thể approve; Document module quyết định access file. Không chỉ dựa vào frontend hide/show.

Deployment ban đầu vẫn một deployable artifact nếu điều đó giúp vận hành đơn giản. Tôi cải thiện CI để test module affected + integration contract hợp lý thay vì dùng microservices chỉ để có deploy nhỏ hơn.

Sau đó tôi định nghĩa extraction criteria. Ví dụ Notification có throughput profile khác, cần scale consumer độc lập, có team ownership riêng và release cadence khác; đó là candidate đầu tiên để tách service. Khi extract, contract đã tồn tại, data ownership rõ, integration event đã stable nên migration ít rủi ro hơn.

Nếu trong 12 tháng Product yêu cầu external client truy cập Document API với SLA và scaling riêng, hoặc một module có deployment cadence 20 lần/tuần trong khi core chỉ 1 lần/tuần, recommendation có thể chuyển sang service extraction sớm hơn.

Testing gồm architecture dependency tests, module integration tests, contract tests, migration tests và end-to-end critical workflows. Observability dùng correlation across module/event boundaries để khi tách service sau này không bắt đầu từ zero.

## Mẫu trả lời trong phỏng vấn

“Với dữ kiện này em sẽ ưu tiên Modular Monolith trước, vì pain hiện tại là boundary/data coupling chứ chưa phải independent scaling hay deployment. Nếu tách microservices ngay khi domain boundaries còn mơ hồ, rất dễ tạo distributed monolith.

Em sẽ xác định ownership cho Approval, Timesheet, Document, Notification, Reporting; cấm module đọc repository/table nội bộ của nhau; expose contracts rõ và có thể dùng schema ownership ngay cả khi cùng SQL Server. Side effects bất đồng bộ như notification có thể đi qua outbox + Service Bus khi reliability yêu cầu.

Reporting sẽ dùng projection/read model theo freshness SLO thay vì query chéo mọi schema. Sau đó em đặt exit criteria để extract service: scale profile khác, SLA khác, team ownership riêng, external contract hoặc deployment independence có giá trị thật. Như vậy ta giữ runtime đơn giản hiện tại nhưng vẫn tạo đường tách service sau này mà không rewrite.”

## Câu hỏi đào sâu

1. Nếu Notification cần scale gấp 20 lần Approval và release độc lập hàng ngày, bạn tách nó như thế nào mà không phá transaction của Approval?
2. CTO yêu cầu mỗi module một microservice vì “đó là best practice enterprise”; bạn dùng tiêu chí và evidence gì để phản biện?
3. Nếu Reporting bắt buộc phải xem dữ liệu Approval + Timesheet gần như realtime dưới 2 giây, bạn thiết kế projection/consistency thế nào?

## Lỗi trả lời thường gặp

- Chọn microservices vì số module tăng.
- Modular Monolith nhưng vẫn cho mọi module query chung tables/repositories.
- Dùng events cho mọi interaction dù cần immediate consistency.
- Không tính operational cost của distributed system.
- Không có extraction criteria hoặc migration path.

## Thang điểm 0–10

- **0–2:** Chọn architecture theo trend.
- **3–4:** Nhắc được modularity nhưng boundary/data ownership mơ hồ.
- **5–6:** Có module boundaries, communication/data ownership và migration path hợp lý.
- **7–8:** Có reporting, outbox, security, extraction criteria và operational trade-offs.
- **9–10:** Kết nối domain, team topology, consistency, deployment và evolution strategy thành architecture có điều kiện rõ ràng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- DI lifetime là object-lifetime contract, không chỉ là cấu hình container. Singleton giữ scoped dependency là một dạng captive dependency có thể gây concurrency/disposal bugs.
- `DbContext` không nên được chia sẻ giữa concurrent operations; BackgroundService cần tạo scope rõ ràng cho scoped work.
- Redis là optimization layer nhưng vẫn có thể trở thành latency/cascading-failure dependency nếu timeout, retry và fallback không được thiết kế theo capacity.
- Cache outage phải được thiết kế cùng anti-stampede, stale/degraded mode, SQL protection và controlled recovery.
- Modular Monolith có thể giải quyết coupling/data ownership trước khi hệ thống thực sự cần operational complexity của microservices.
- Microservices chỉ đáng giá khi independent ownership, deployment, scale, availability hoặc external boundaries trả được chi phí distributed systems.

## Mẫu tư duy cần nhớ

1. **Trace object/data ownership trước khi sửa symptom.**
2. **Measure dependency failure amplification, không chỉ final error rate.**
3. **Design fallback theo capacity của source system.**
4. **Boundary trước, distribution sau.**
5. **Chỉ trả complexity cost khi requirement thực sự cần nó.**
