# Code Review Challenge 1 — Cổng CRM bị nghẽn khi đối tác giới hạn request

**Chủ đề:** C#/.NET 8, HttpClient, resilience, concurrency, cancellation  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 6

## Bối cảnh

Một API CRM tổng hợp trạng thái hợp đồng từ đối tác. Mỗi request nhận tối đa 100 mã hợp đồng; hệ thống chạy ba instance trên App Service. Đối tác giới hạn tổng lưu lượng theo tài khoản, đôi lúc trả 429 hoặc phản hồi chậm. Sau chiến dịch marketing, p95 tăng từ 600 ms lên 18 giây (số liệu giả định), số kết nối outbound tăng và khách hàng hủy request nhiều hơn. Yêu cầu không được báo hợp đồng không tồn tại chỉ vì đối tác tạm thời lỗi. Chưa xác định SLA cho kết quả từng phần và quota chính xác.

## Đoạn code cần review

```csharp
public sealed class ContractGateway
{
    private readonly ILogger<ContractGateway> _logger;
    public ContractGateway(ILogger<ContractGateway> logger)
        => _logger = logger;

    public async Task<Dictionary<string, string?>> LoadAsync(
        IReadOnlyList<string> ids, CancellationToken ct)
    {
        var tasks = ids.Select(async id =>
        {
            for (var attempt = 0; attempt < 4; attempt++)
            {
                try
                {
                    using var client = new HttpClient();
                    client.Timeout = TimeSpan.FromSeconds(20);
                    using var response = await client.GetAsync(
                        "https://partner.example/contracts/" +
                        Uri.EscapeDataString(id));
                    if (response.IsSuccessStatusCode)
                        return (id, Value: (string?)await
                            response.Content.ReadAsStringAsync());
                    if (response.StatusCode == HttpStatusCode.NotFound)
                        return (id, Value: (string?)null);
                }
                catch (Exception ex)
                {
                    _logger.LogWarning(ex, "Partner request failed");
                }
                await Task.Delay(100);
            }
            return (id, Value: (string?)null);
        });
        var results = await Task.WhenAll(tasks);
        return results.ToDictionary(x => x.id, x => x.Value);
    }
}
```

## Kết quả code review tham khảo

### High — Kết quả nghiệp vụ sai

**Vấn đề:** null đại diện cho cả 404 và lỗi sau retry.

**Tại sao xảy ra:** hợp đồng trả về không biểu diễn trạng thái dependency.

**Ảnh hưởng production:** CRM có thể hiển thị hợp đồng không tồn tại dù chỉ bị timeout.

**Cách sửa:** dùng kết quả có trạng thái Found, NotFound, Unavailable; chỉ coi 404 là NotFound nếu hợp đồng API đối tác xác nhận.

### High — Fan-out và retry khuếch đại tải

**Vấn đề:** Task.WhenAll khởi động toàn bộ tác vụ; retry cả lỗi không transient.

**Tại sao xảy ra:** không có giới hạn dùng chung, không phân loại HTTP status, delay cố định.

**Ảnh hưởng production:** tối đa 400 lần gọi cho 100 mã, chưa tính các request đồng thời. Retry đồng pha làm 429 nghiêm trọng hơn.

**Cách sửa:** giới hạn concurrency dùng chung theo process, budget toàn request, phân loại lỗi; nếu retry cần tôn trọng Retry-After và jitter, quota toàn cụm phải được xử lý riêng.

### High — Cancellation không được truyền

**Vấn đề:** ct không được dùng trong I/O hay delay.

**Tại sao xảy ra:** timeout từng attempt không thay thế deadline của request.

**Ảnh hưởng production:** công việc vô ích tiếp tục giữ tài nguyên sau khi caller rời đi.

**Cách sửa:** truyền token xuyên suốt, không nuốt OperationCanceledException do caller hủy.

### High — Tạo HttpClient cho từng attempt

**Vấn đề:** mỗi lần tạo client mặc định sở hữu handler riêng.

**Tại sao xảy ra:** dispose liên tục phá khả năng tái sử dụng connection pool giữa các lần gọi.

**Ảnh hưởng production:** tăng connection churn, có thể cạn tài nguyên socket/SNAT; cần đo trước khi kết luận.

**Cách sửa:** IHttpClientFactory với named client hoặc client dài hạn có cấu hình connection lifetime phù hợp.

### Medium — Mã trùng gây exception

**Vấn đề:** ToDictionary ném exception khi ids trùng.

**Tại sao xảy ra:** input không được chuẩn hóa theo quy tắc định danh.

**Ảnh hưởng production:** toàn bộ batch thất bại dù đối tác trả thành công.

**Cách sửa:** xác định comparer theo contract, deduplicate và giới hạn batch ở server.

### Medium — Thiếu phân loại telemetry và giới hạn payload

**Vấn đề:** log exception chung, đọc toàn bộ response không có giới hạn nghiệp vụ.

**Tại sao xảy ra:** không có metric theo outcome và contract kích thước.

**Ảnh hưởng production:** khó phân biệt throttling, timeout và lỗi xác thực; payload lớn tăng memory pressure.

**Cách sửa:** metric theo nhóm status, giới hạn response, không log body chứa thông tin hợp đồng.

## Phiên bản đề xuất

Giả định caller đã được kiểm tra quyền trên từng mã, đối tác quy định 404 là không tồn tại và payload nhỏ tối đa 64 KiB. Chọn không retry tại gateway trong giai đoạn ổn định; caller nhận kết quả từng phần nếu nghiệp vụ chấp thuận. Đăng ký gateway singleton để limiter dùng chung toàn process.

```csharp
public enum LookupState { Found, NotFound, Unavailable }
public sealed record Lookup(LookupState State, string? Body = null);

public sealed class ContractGateway(IHttpClientFactory factory)
{
    private readonly SemaphoreSlim _slots = new(8, 8);

    public async Task<Dictionary<string, Lookup>> LoadAsync(
        IReadOnlyList<string> ids, CancellationToken ct)
    {
        if (ids.Count > 100)
            throw new ArgumentException("Batch too large");
        using var budget = CancellationTokenSource
            .CreateLinkedTokenSource(ct);
        budget.CancelAfter(TimeSpan.FromSeconds(3));
        using var client = factory.CreateClient("partner");

        async Task<Lookup> Fetch(string id)
        {
            try
            {
                await _slots.WaitAsync(budget.Token);
                try
                {
                    using var response = await client.GetAsync(
                        "contracts/" + Uri.EscapeDataString(id),
                        budget.Token);
                    if (response.StatusCode == HttpStatusCode.NotFound)
                        return new(LookupState.NotFound);
                    if (!response.IsSuccessStatusCode)
                        return new(LookupState.Unavailable);
                    return new(LookupState.Found,
                        await response.Content.ReadAsStringAsync(budget.Token));
                }
                finally { _slots.Release(); }
            }
            catch (OperationCanceledException) when (!ct.IsCancellationRequested)
            {
                return new(LookupState.Unavailable);
            }
            catch (HttpRequestException)
            {
                return new(LookupState.Unavailable);
            }
        }

        var keys = ids.Distinct(StringComparer.Ordinal).ToArray();
        var values = await Task.WhenAll(keys.Select(Fetch));
        return keys.Zip(values).ToDictionary(x => x.First, x => x.Second);
    }
}

// Program.cs
builder.Services.AddHttpClient("partner", client =>
{
    client.BaseAddress = new Uri("https://partner.example/");
    client.MaxResponseContentBufferSize = 64 * 1024;
    client.Timeout = TimeSpan.FromSeconds(2);
});
builder.Services.AddSingleton<ContractGateway>();
```

## Giải thích thiết kế sau khi sửa

GetAsync mặc định buffer response; MaxResponseContentBufferSize giới hạn phần buffer đó. Với payload lớn cần streaming và giới hạn số byte khi đọc. Deadline 3 giây bao gồm thời gian chờ semaphore; timeout 2 giây là giới hạn riêng cho HTTP. Các giá trị chỉ là giả định cần load test. Caller cancellation vẫn propagate. Tám slot mỗi process không phải tám slot toàn cụm; cũng không phải rate limit theo giây. Cần thêm admission control tại API để tránh hàng chờ không giới hạn và đo quota trước khi chọn rate limiter toàn cụm. Phân loại 401/403 thành cảnh báo cấu hình riêng ở telemetry, không retry. Nếu cần retry GET, chỉ retry lỗi transient trong budget còn lại, tôn trọng Retry-After; không tự động áp dụng cho POST. Nếu đối tác hỗ trợ batch API, đánh giá giảm fan-out trước khi thêm infrastructure.

## Trade-offs

Kết quả từng phần giảm latency nhưng caller phải xử lý trạng thái Unavailable. Limiter giảm áp lực đối tác nhưng có thể làm request hết budget khi chờ. Không retry giảm amplification nhưng tăng lỗi nhìn thấy khi sự cố rất ngắn. Distributed limiter chỉ đáng dùng nếu quota chung và số instance biến động khiến phân bổ tĩnh không đủ.

## Cách kiểm thử

1. Integration test: 404, 429, 401 và 500 không bị đồng nhất thành NotFound.
2. Concurrency test: nhiều batch đồng thời, tối đa tám HTTP call đang hoạt động mỗi process.
3. Failure-path test: caller hủy trong lúc chờ slot và trong lúc đọc response; không rò slot.
4. Load test: partner chậm, đo p95/p99, hàng chờ, tỷ lệ Unavailable và socket.
5. Boundary test: mã trùng, batch vượt giới hạn và response vượt 64 KiB.

## Quan sát trong production

Application Insights dependency traces theo status và duration; metric in-flight, limiter wait, deadline exceeded, caller cancellation, batch size và tỷ lệ kết quả từng phần. Theo dõi connection churn, SNAT và CPU để phân biệt nghẽn mạng với CPU. Alert khi 429 hoặc Unavailable vượt baseline; không dùng contract ID làm metric label.

## Câu hỏi phỏng vấn mở rộng

2. Nếu business không chấp nhận partial result, API nên phản hồi và retry thế nào?
3. Khi nào batch endpoint hoặc cache hợp lý hơn distributed rate limiter?

# Code Review Challenge 2 — Release SQL Server không tương thích với rollback

## Bối cảnh

Sau thử nghiệm staging, có lúc ghi dữ liệu thất bại và database bị blocking. Chưa biết maintenance window, tốc độ ghi và khả năng rollback dữ liệu.

## Kết quả code review tham khảo

### Critical — Phá compatibility của binary đang chạy

**Vấn đề:** xóa EmployeeCode trước khi tất cả node cũ ngừng phục vụ.

**Tại sao xảy ra:** database migration và app rollout không có cùng transaction boundary.

### High — Transaction backfill quá lớn

**Vấn đề:** update 12 triệu dòng trong một transaction cùng DDL.

**Ảnh hưởng production:** blocking, timeout, log growth và rollback lâu.

**Cách sửa:** batch nhỏ, commit từng batch, theo dõi log và blocking; DDL riêng với lock timeout và cửa sổ phù hợp.

### High — Không có chiến lược đồng bộ trong giai đoạn chuyển tiếp

**Cách sửa:** triển khai bản bridge đọc cột cũ và ghi cả hai cột trong cùng transaction; chỉ chuyển read sau khi không còn writer cũ và reconciliation thành công.

### High — Rollback không bao gồm database state

**Vấn đề:** rollback chỉ đổi binary.

**Tại sao xảy ra:** pipeline coi schema change là một phần có thể đảo ngược của artifact.

**Ảnh hưởng production:** mất khả năng khôi phục nhanh khi smoke test lỗi.

## Phiên bản đề xuất

Giả định đây là đổi tên logic, hai giá trị phải giống nhau, AttendanceId là khóa chính bigint. Các script dưới đây là từng release gate độc lập, không chạy liên tiếp trong một deployment. Migration runner ghi ledger và chỉ cho một tiến trình chạy; schema precondition phải được xác minh.

```sql
-- Release A: expand
SET LOCK_TIMEOUT 5000;
IF COL_LENGTH('dbo.Attendance', 'StaffCode') IS NULL
    ALTER TABLE dbo.Attendance ADD StaffCode nvarchar(50) NULL;
```

Deploy bridge: tất cả insert/update ghi cả EmployeeCode và StaffCode trong cùng transaction; vẫn đọc EmployeeCode. Chờ toàn bộ node và background writer cũ dừng. Sau đó chạy từng batch dưới đây bằng runner, commit mỗi lần, tăng dần @LastId theo tập khóa đã xử lý; bắt đầu từ giá trị nhỏ hơn khóa nhỏ nhất, giả định ID dương. Nếu timeout thì retry batch chưa commit có giới hạn. Lưu checkpoint sau commit; replay batch an toàn.

```sql
-- Một batch; @LastId do runner truyền vào
SET XACT_ABORT ON;
SET LOCK_TIMEOUT 5000;
BEGIN TRANSACTION;
DECLARE @Keys TABLE (Id bigint PRIMARY KEY);
INSERT @Keys(Id)
SELECT TOP (1000) AttendanceId
FROM dbo.Attendance
WHERE AttendanceId > @LastId
ORDER BY AttendanceId;

UPDATE a
SET StaffCode = a.EmployeeCode
FROM dbo.Attendance a
JOIN @Keys k ON k.Id = a.AttendanceId
WHERE a.StaffCode IS NULL OR a.StaffCode <> a.EmployeeCode;

COMMIT TRANSACTION;
SELECT MAX(Id) AS NextCheckpoint, COUNT(*) AS BatchCount
FROM @Keys;
```

Sau backfill, kiểm tra null/mismatch trên toàn bộ dữ liệu; thực hiện dưới điều kiện writer bridge đã được xác nhận. So sánh theo collation phù hợp với contract mã nhân viên. Nếu cần index, kiểm tra execution plan và khả năng online index operation theo edition/version thực tế trước khi chọn phương án. Deploy bản B đọc StaffCode nhưng vẫn dual-write. Rollback về bridge vẫn an toàn.

```sql
-- Release C: chỉ sau khi hết rollback window
-- và không còn binary nào cần EmployeeCode.
SET LOCK_TIMEOUT 5000;
ALTER TABLE dbo.Attendance
    ALTER COLUMN StaffCode nvarchar(50) NOT NULL;
```

Trước khi deploy bản chỉ ghi StaffCode, cần cho phép EmployeeCode NULL hoặc bỏ yêu cầu ghi cột cũ bằng một migration riêng; xác nhận mọi reader dùng StaffCode. Khi tất cả writer mới ổn định và hết cửa sổ rollback về bản dual-write, mới DROP EmployeeCode trong release riêng. Kiểm tra dependency (view, procedure, report, ETL) trước khi drop. Nếu không thể bảo đảm các gate, giữ cột cũ hoặc dùng maintenance window có kế hoạch rõ ràng.

## Giải thích thiết kế sau khi sửa

Expand giữ compatibility; bridge xác lập invariant cho dữ liệu mới; backfill xử lý dữ liệu lịch sử; contract chỉ diễn ra khi không còn consumer cũ. Batch quét theo khóa thay vì OFFSET, giới hạn lượng công việc mỗi transaction. DDL vẫn có thể blocking dù bảng đã backfill; lock timeout không đảm bảo DDL nhanh, chỉ giới hạn chờ lock. Nếu rollback về writer chỉ ghi cột cũ sau backfill thì phải quay lại gate reconciliation trước khi chuyển read lần nữa. TeamCity build artifact một lần; Octopus promote cùng artifact và cấu hình môi trường riêng. Không tự chạy migration trên mỗi IIS node.

## Trade-offs

Dual-write tăng write cost và kéo dài thời gian tồn tại schema kép. Batch nhỏ giảm lock duration nhưng tăng số round trip và tổng thời gian migration. Maintenance window có thể đơn giản hơn nếu downtime được chấp thuận. Nếu chỉ đổi tên hiển thị, mapping ở application có thể tránh migration vật lý hoàn toàn.

## Cách kiểm thử

1. Integration test với binary cũ và bridge chạy đồng thời trên schema expand.
2. Database test: backfill đồng thời với bridge insert/update, kiểm tra invariant và replay checkpoint.
3. Deployment validation: dừng pipeline sau từng gate, rollback về phiên bản tương thích.
4. Load test với dữ liệu đại diện, đo blocking, transaction log và latency.
5. Failure-path test: runner bị kill sau commit nhưng trước lưu checkpoint; chạy lại không làm sai dữ liệu.

## Quan sát trong production

Theo dõi SQL Server blocking sessions, deadlocks, log usage, batch duration, rows processed, mismatch count, API error rate theo app version và p95. Correlate Octopus release ID với Application Insights deployment markers. Dừng backfill khi blocking hoặc log vượt ngưỡng đã thống nhất với DBA; chỉ tiếp tục sau khi xác minh recovery. Không log mã nhân viên thô nếu không cần.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- HTTP resilience cần deadline, cancellation, connection reuse, phân loại outcome và kiểm soát tải theo đúng phạm vi quota.
- Database transaction không đảm bảo atomicity cho deployment nhiều phiên bản; compatibility phải được thiết kế và kiểm chứng qua từng release gate.

## Mẫu tư duy cần nhớ

- Phân biệt lỗi dependency với kết quả nghiệp vụ.
- Giới hạn retry cùng với concurrency và deadline.
- Đo trước khi tối ưu; kiểm tra phạm vi của mỗi limiter.
- Thiết kế rollback trước khi thay đổi schema.
- Kiểm thử failure path và trạng thái chuyển tiếp, không chỉ happy path.
