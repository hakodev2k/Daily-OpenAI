# Code Review Challenge 1 — Refresh token rotation bị race condition và cho phép replay ngoài ý muốn

**Chủ đề:** Authentication & authorization, concurrency/race condition, transaction handling, sensitive-data exposure, error handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API sử dụng access token ngắn hạn và refresh token lưu trong database. Mobile app đôi lúc gửi hai request refresh gần như đồng thời do retry ở network layer. API chạy trên 4 instance sau load balancer.

Production ghi nhận một số session tạo ra nhiều access token hợp lệ từ cùng một refresh token. Team cũng phát hiện refresh token xuất hiện trong application log khi điều tra lỗi. Khi người dùng đổi mật khẩu hoặc admin revoke session, một số refresh token cũ vẫn có thể được dùng trong một khoảng thời gian không mong muốn.

Business yêu cầu:

- mỗi refresh token chỉ được consume theo rule rõ ràng,
- retry hợp lệ từ client không được làm session hỏng ngẫu nhiên,
- replay đáng ngờ phải được phát hiện,
- revoke phải có semantics xác định,
- token nhạy cảm không được xuất hiện trong log.

## Đoạn code cần review

```csharp
public sealed class TokenService
{
    private readonly AppDbContext _db;
    private readonly IJwtIssuer _jwtIssuer;
    private readonly ILogger<TokenService> _logger;

    public TokenService(
        AppDbContext db,
        IJwtIssuer jwtIssuer,
        ILogger<TokenService> logger)
    {
        _db = db;
        _jwtIssuer = jwtIssuer;
        _logger = logger;
    }

    public async Task<TokenResponse> RefreshAsync(
        string refreshToken,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Refreshing token {RefreshToken}",
            refreshToken);

        var session = await _db.RefreshSessions
            .SingleOrDefaultAsync(
                x => x.RefreshToken == refreshToken,
                cancellationToken);

        if (session == null || session.ExpiresAt <= DateTime.UtcNow)
        {
            throw new UnauthorizedAccessException();
        }

        var accessToken = _jwtIssuer.CreateAccessToken(session.UserId);
        var newRefreshToken = Convert.ToBase64String(
            RandomNumberGenerator.GetBytes(64));

        session.RefreshToken = newRefreshToken;
        session.ExpiresAt = DateTime.UtcNow.AddDays(30);
        session.LastUsedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        return new TokenResponse(
            accessToken,
            newRefreshToken,
            session.ExpiresAt);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và security trong flow refresh token.
2. Xác định race condition khi nhiều request dùng cùng một token gần như đồng thời.
3. Giải thích production impact và khả năng replay.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation có rotation/revocation semantics rõ ràng hơn.
6. Giải thích cách test concurrency, retry và revoke.
7. Đề xuất logs, traces và metrics cần có ở production mà không làm lộ secret.

## Câu hỏi gợi mở

1. Hai request trên hai instance có thể cùng đọc cùng một `RefreshSession` hợp lệ không?
2. Điều gì đảm bảo chỉ một request được phép consume refresh token cũ?
3. Có nên lưu refresh token nguyên bản trong database và log hay không?

## Kết quả code review tham khảo

### 1. Refresh token bị ghi nguyên bản vào log

**Problem:** Code log trực tiếp `refreshToken` ở `Information` level.  
**Why it happens:** Credential được xem như diagnostic value bình thường.  
**Production impact:** Người có quyền đọc log hoặc hệ thống downstream của logging có thể sử dụng token còn hiệu lực để chiếm session.  
**Severity:** Critical  
**Recommended fix:** Không log token nguyên bản. Chỉ log identifier không thể dùng để authenticate, ví dụ session id, token fingerprint/hash prefix an toàn hoặc correlation id theo policy.

### 2. Check-then-update không atomic nên cùng một token có thể được consume nhiều lần

**Problem:** Hai request đồng thời có thể cùng đọc `session` khi token cũ vẫn hợp lệ, sau đó cả hai cùng phát hành access token mới.  
**Why it happens:** Validation và rotation không có concurrency guard ở database.  
**Production impact:** Một refresh credential duy nhất có thể sinh nhiều access token; replay detection trở nên mơ hồ và session state cuối cùng phụ thuộc request nào save sau.  
**Severity:** Critical  
**Recommended fix:** Dùng optimistic concurrency token/version, conditional update hoặc transaction/locking strategy phù hợp để chỉ một state transition từ `Active` sang `Consumed/Replaced` thành công.

### 3. Refresh token được lưu nguyên bản trong database

**Problem:** Database chứa credential có thể dùng trực tiếp để authenticate.  
**Why it happens:** Query lookup dựa trên plaintext token.  
**Production impact:** Nếu database hoặc backup bị đọc trái phép, attacker có thể dùng token còn hiệu lực.  
**Severity:** High  
**Recommended fix:** Sinh token ngẫu nhiên đủ entropy, trả nguyên bản chỉ cho client, nhưng lưu hash phù hợp trong DB; lookup bằng hash của token do client gửi.

### 4. Không có trạng thái revoke rõ ràng

**Problem:** Chỉ kiểm tra `session == null` và `ExpiresAt`.  
**Why it happens:** Session model không biểu diễn revoke/consumed/compromised state.  
**Production impact:** Đổi mật khẩu, admin revoke hoặc logout-all không có enforcement rõ ràng trong flow này.  
**Severity:** High  
**Recommended fix:** Có `RevokedAt`, `ConsumedAt`, `ReplacedBySessionId`, `TokenFamilyId` hoặc session version tùy thiết kế; validation phải kiểm tra trạng thái.

### 5. Không có replay detection/token-family policy

**Problem:** Khi token cũ bị dùng lại, code chỉ có thể thấy token không tồn tại sau rotation hoặc session state cuối cùng, nhưng không có policy xử lý reuse.  
**Why it happens:** Rotation chỉ overwrite token hiện tại.  
**Production impact:** Không phân biệt được retry hợp lệ, stale client và credential theft; khó revoke cả token family khi có dấu hiệu compromise.  
**Severity:** High  
**Recommended fix:** Thiết kế token family và lưu lịch sử tối thiểu cần thiết để nhận biết token đã consumed. Khi phát hiện reuse, áp policy như revoke family/session và yêu cầu login lại nếu risk model yêu cầu.

### 6. Expiry bị kéo dài 30 ngày ở mọi refresh mà chưa nêu rõ business rule

**Problem:** Mỗi lần refresh lại đặt `ExpiresAt = now + 30 days`.  
**Why it happens:** Sliding expiration được áp ngầm.  
**Production impact:** Session có thể tồn tại vô thời hạn nếu người dùng hoạt động liên tục, trái với absolute session lifetime mà security policy có thể yêu cầu.  
**Severity:** Medium  
**Recommended fix:** Tách `AbsoluteExpiresAt` và `IdleExpiresAt` nếu cần; làm rõ rolling/sliding semantics với security requirement.

### 7. Dùng nhiều lần `DateTime.UtcNow` khiến state khó nhất quán/test

**Problem:** Các timestamp được lấy ở nhiều thời điểm trong cùng operation.  
**Why it happens:** Time source không được đóng gói.  
**Production impact:** Khó deterministic test và có thể tạo boundary behavior khó giải thích gần expiry.  
**Severity:** Low  
**Recommended fix:** Lấy `now` một lần qua `TimeProvider` hoặc clock abstraction.

### 8. Không có observability cho refresh outcome và concurrency conflict

**Problem:** Chỉ có log chứa secret, không có metric có ích về success/failure/replay/conflict.  
**Why it happens:** Logging tập trung vào input thay vì lifecycle event.  
**Production impact:** Khó phát hiện credential abuse hoặc bug retry từ client.  
**Severity:** Medium  
**Recommended fix:** Log structured `SessionId`, `UserId` nội bộ, outcome, reason, IP/device metadata theo privacy policy; metric cho refresh success, invalid, expired, revoked, reuse detected, concurrency conflict.

### 9. Không nói rõ semantics nếu response đầu tiên thành công nhưng client không nhận được

**Problem:** Client có thể retry token cũ sau khi server đã rotate thành công.  
**Why it happens:** Network failure path chưa được thiết kế.  
**Production impact:** User có thể bị logout oan hoặc retry bị xem là attack.  
**Severity:** Medium  
**Recommended fix:** Chọn policy rõ ràng: strict single-use, short grace window có ràng buộc, hoặc idempotency mechanism dựa trên client request id/device session. Mỗi lựa chọn có trade-off security khác nhau.

## Phiên bản code đề xuất

Ví dụ dưới đây minh hoạ optimistic concurrency và token hash. Chi tiết cryptographic storage, token-family policy và grace window phải phù hợp threat model thực tế.

```csharp
public sealed class TokenService
{
    private readonly AppDbContext _db;
    private readonly IJwtIssuer _jwtIssuer;
    private readonly TimeProvider _timeProvider;

    public TokenService(
        AppDbContext db,
        IJwtIssuer jwtIssuer,
        TimeProvider timeProvider)
    {
        _db = db;
        _jwtIssuer = jwtIssuer;
        _timeProvider = timeProvider;
    }

    public async Task<TokenResponse> RefreshAsync(
        string refreshToken,
        CancellationToken cancellationToken)
    {
        var now = _timeProvider.GetUtcNow();
        var tokenHash = HashToken(refreshToken);

        var session = await _db.RefreshSessions
            .SingleOrDefaultAsync(
                x => x.TokenHash == tokenHash,
                cancellationToken)
            ?? throw new UnauthorizedAccessException();

        if (session.RevokedAt != null ||
            session.ConsumedAt != null ||
            session.ExpiresAt <= now)
        {
            throw new UnauthorizedAccessException();
        }

        var nextToken = Convert.ToBase64String(
            RandomNumberGenerator.GetBytes(64));
        var nextHash = HashToken(nextToken);

        session.ConsumedAt = now;
        session.ReplacedByTokenHash = nextHash;

        var nextSession = new RefreshSession
        {
            Id = Guid.NewGuid(),
            UserId = session.UserId,
            TokenFamilyId = session.TokenFamilyId,
            TokenHash = nextHash,
            CreatedAt = now,
            ExpiresAt = Min(
                now.AddDays(30),
                session.AbsoluteExpiresAt),
            AbsoluteExpiresAt = session.AbsoluteExpiresAt
        };

        _db.RefreshSessions.Add(nextSession);

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException)
        {
            throw new UnauthorizedAccessException();
        }

        var accessToken = _jwtIssuer.CreateAccessToken(session.UserId);

        return new TokenResponse(
            accessToken,
            nextToken,
            nextSession.ExpiresAt.UtcDateTime);
    }

    private static string HashToken(string token)
    {
        var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(token));
        return Convert.ToHexString(bytes);
    }

    private static DateTimeOffset Min(
        DateTimeOffset left,
        DateTimeOffset right) => left <= right ? left : right;
}
```

`RefreshSession` cần được cấu hình concurrency token phù hợp hoặc thao tác consume phải dùng một conditional update bảo đảm chỉ một request thắng. Hash minh hoạ ở trên không thay thế threat-model review; hệ thống thực tế cần policy đầy đủ cho token generation, storage, rotation, reuse detection và revoke.

## Trade-offs

- Strict single-use đơn giản và an toàn hơn nhưng có thể làm client retry sau network loss bị logout.
- Grace window cải thiện UX nhưng tăng replay window; phải ràng buộc chặt theo session/device/request semantics.
- Lưu token history hỗ trợ replay detection nhưng tăng dữ liệu và yêu cầu retention policy.
- Revoke cả family khi reuse là phòng thủ mạnh nhưng có thể ảnh hưởng user nếu duplicate request hợp lệ bị hiểu nhầm.
- Database locking mạnh có thể serialize refresh nhưng tăng contention; optimistic concurrency thường phù hợp hơn nếu conflict rate thấp.

## Cách kiểm thử

1. **Concurrency test:** gửi 20 request đồng thời với cùng refresh token; xác nhận chỉ state transition hợp lệ theo policy được chấp nhận.
2. **Replay test:** dùng lại token đã consumed; xác nhận replay được phát hiện và xử lý đúng token-family policy.
3. **Revocation test:** revoke session rồi refresh; phải bị từ chối ngay.
4. **Network retry scenario:** mô phỏng server commit nhưng client mất response, sau đó retry token cũ; xác nhận behavior đúng theo policy đã chọn.
5. **Sensitive-data test:** kiểm tra log/traces không chứa refresh token nguyên bản.

## Quan sát trong production

Nên theo dõi:

- refresh success/failure theo reason,
- concurrency conflict count,
- token reuse/replay detected count,
- revoked-session attempts,
- refresh latency,
- unusual refresh frequency theo session/device,
- correlation id và session id không chứa secret,
- alert khi reuse rate tăng bất thường.

# Code Review Challenge 2 — Playwright test suite bị flaky vì dùng chung BrowserContext và Page khi chạy song song

**Chủ đề:** Concurrency and race conditions, resource lifetime/disposal, async/await, test isolation, logging & observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Team có một bộ Playwright for .NET chạy trong CI để regression test portal nội bộ. Để giảm thời gian chạy, pipeline bật parallel execution cho nhiều test class.

Một helper được đăng ký singleton để tránh mở browser nhiều lần. Helper giữ một `IBrowserContext` và một `IPage` dùng chung cho toàn bộ test.

Sau khi parallelism tăng, CI bắt đầu flaky:

- test A đôi lúc bị chuyển sang URL của test B,
- cookie/session của user admin xuất hiện trong test user thường,
- screenshot khi fail không đúng test,
- thỉnh thoảng lỗi `Target page, context or browser has been closed`,
- chạy test riêng lẻ thường pass nhưng chạy full suite thì fail ngẫu nhiên.

Team muốn giữ browser startup cost thấp nhưng cần isolation đáng tin cậy giữa test.

## Đoạn code cần review

```csharp
public sealed class SharedBrowserFixture : IAsyncDisposable
{
    private readonly IPlaywright _playwright;
    private readonly IBrowser _browser;
    private IBrowserContext? _context;
    private IPage? _page;

    public SharedBrowserFixture()
    {
        _playwright = Playwright.CreateAsync().GetAwaiter().GetResult();
        _browser = _playwright.Chromium
            .LaunchAsync(new BrowserTypeLaunchOptions
            {
                Headless = true
            })
            .GetAwaiter()
            .GetResult();
    }

    public async Task<IPage> GetPageAsync(string userName, string password)
    {
        _context ??= await _browser.NewContextAsync();
        _page ??= await _context.NewPageAsync();

        await _page.GotoAsync("https://portal.example.test/login");
        await _page.FillAsync("#username", userName);
        await _page.FillAsync("#password", password);
        await _page.ClickAsync("button[type=submit]");

        return _page;
    }

    public async Task CaptureFailureAsync(string testName)
    {
        if (_page != null)
        {
            await _page.ScreenshotAsync(new PageScreenshotOptions
            {
                Path = $"artifacts/{testName}.png",
                FullPage = true
            });
        }
    }

    public async ValueTask DisposeAsync()
    {
        if (_context != null)
        {
            await _context.CloseAsync();
        }

        await _browser.CloseAsync();
        _playwright.Dispose();
    }
}
```

4. Ưu tiên vấn đề nào cần sửa trước.

## Kết quả code review tham khảo

### 1. Một `IPage` mutable được dùng chung cho mọi test

**Problem:** `_page` là field chung và `GetPageAsync` luôn trả lại cùng page.  
**Why it happens:** Fixture tối ưu browser startup bằng cách reuse cả stateful page.  
**Production impact:** Test đồng thời navigate/fill/click trên cùng page, khiến thao tác interleave và assert sai ngữ cảnh.  
**Severity:** Critical  
**Recommended fix:** Không share `IPage` giữa test chạy song song. Tạo page riêng theo test scope.

### 2. Một `IBrowserContext` dùng chung làm rò rỉ session state giữa test

**Problem:** Cookie, local storage và browser state trong context được chia sẻ.  
**Why it happens:** `_context` singleton-like lifetime.  
**Production impact:** Test user thường có thể kế thừa authentication state của admin test, tạo false positive/false negative nghiêm trọng.  
**Severity:** Critical  
**Recommended fix:** Tạo context riêng cho mỗi test hoặc mỗi isolated scenario. Browser có thể share nếu test framework/lifecycle được thiết kế đúng.

### 3. Lazy initialization bằng `??=` không bảo đảm test isolation dưới concurrency

**Problem:** Nhiều caller đồng thời truy cập `_context`/`_page` mà không có ownership rõ ràng.  
**Why it happens:** Shared mutable fields bị dùng như cache.  
**Production impact:** Race trong khởi tạo/sử dụng, orphan resource và hành vi không xác định theo timing.  
**Severity:** High  
**Recommended fix:** Bỏ shared context/page. Factory method tạo một `TestBrowserSession` mới cho mỗi test.

### 4. Synchronous-over-async trong constructor

**Problem:** `GetAwaiter().GetResult()` được dùng để tạo Playwright/browser.  
**Why it happens:** Async initialization bị ép vào constructor sync.  
**Production impact:** Test startup khó quản lý timeout/cancellation và có thể gây blocking không cần thiết; lifecycle cũng khó báo lỗi chuẩn.  
**Severity:** Medium  
**Recommended fix:** Dùng async fixture initialization theo test framework hoặc factory `CreateAsync`.

### 5. Failure screenshot có thể chụp nhầm page

**Problem:** `CaptureFailureAsync` dùng global `_page`.  
**Why it happens:** Artifact capture không gắn với test-owned page.  
**Production impact:** Screenshot misleading, làm triage flaky test khó hơn.  
**Severity:** High  
**Recommended fix:** Test session tự capture screenshot/trace với test id riêng.

### 6. Teardown global có thể đóng resource mà test khác còn đang dùng

**Problem:** `DisposeAsync` đóng shared context/browser mà không thể hiện ownership hay active-test coordination.  
**Why it happens:** Singleton fixture và parallel test lifecycle không được đồng bộ.  
**Production impact:** Test khác nhận lỗi page/context/browser closed.  
**Severity:** High  
**Recommended fix:** Browser lifetime thuộc assembly/worker fixture; context/page lifetime thuộc test. Chỉ đóng browser sau khi toàn bộ dependent tests hoàn tất theo lifecycle của framework.

### 7. Login lặp lại bằng credential trực tiếp trong helper nhưng không có timeout/diagnostic strategy

**Problem:** Flow login nằm trong generic page factory và fail chỉ thể hiện như automation error.  
**Why it happens:** Setup và test action trộn với nhau.  
**Production impact:** Khó phân biệt auth failure, selector change, navigation timeout và CI slowness.  
**Severity:** Medium  
**Recommended fix:** Tách authentication helper, capture trace/screenshot/log theo setup step, và dùng storage state khi phù hợp với isolation/security policy.

### 8. Artifact path có thể conflict khi test name trùng hoặc retry

**Problem:** File path chỉ dựa trên `testName`.  
**Why it happens:** Không có run id/attempt id.  
**Production impact:** Retry hoặc parallel test có thể overwrite artifact, làm mất evidence.  
**Severity:** Low  
**Recommended fix:** Dùng run id, test id, browser/project, attempt number và timestamp an toàn trong artifact path.

## Phiên bản code đề xuất

Ví dụ dưới đây reuse `IBrowser` nhưng mỗi test nhận context/page riêng và tự dispose.

```csharp
public sealed class BrowserHost : IAsyncDisposable
{
    private readonly IPlaywright _playwright;
    private readonly IBrowser _browser;

    private BrowserHost(
        IPlaywright playwright,
        IBrowser browser)
    {
        _playwright = playwright;
        _browser = browser;
    }

    public static async Task<BrowserHost> CreateAsync()
    {
        var playwright = await Playwright.CreateAsync();
        var browser = await playwright.Chromium.LaunchAsync(
            new BrowserTypeLaunchOptions
            {
                Headless = true
            });

        return new BrowserHost(playwright, browser);
    }

    public async Task<TestBrowserSession> CreateSessionAsync(
        string testId)
    {
        var context = await _browser.NewContextAsync();
        var page = await context.NewPageAsync();

        return new TestBrowserSession(testId, context, page);
    }

    public async ValueTask DisposeAsync()
    {
        await _browser.CloseAsync();
        _playwright.Dispose();
    }
}

public sealed class TestBrowserSession : IAsyncDisposable
{
    private readonly string _testId;
    private readonly IBrowserContext _context;

    public TestBrowserSession(
        string testId,
        IBrowserContext context,
        IPage page)
    {
        _testId = testId;
        _context = context;
        Page = page;
    }

    public IPage Page { get; }

    public async Task LoginAsync(
        string userName,
        string password)
    {
        await Page.GotoAsync("https://portal.example.test/login");
        await Page.FillAsync("#username", userName);
        await Page.FillAsync("#password", password);
        await Page.ClickAsync("button[type=submit]");
    }

    public async Task CaptureFailureAsync(int attempt)
    {
        var path = $"artifacts/{_testId}-attempt-{attempt}.png";

        await Page.ScreenshotAsync(new PageScreenshotOptions
        {
            Path = path,
            FullPage = true
        });
    }

    public async ValueTask DisposeAsync()
    {
        await _context.CloseAsync();
    }
}
```

Browser-host lifetime phải được test framework quản lý ở scope phù hợp, còn `TestBrowserSession` thuộc từng test. Nếu cần login nhanh hơn, có thể chuẩn bị storage state riêng cho từng role/user nhưng vẫn phải tránh chia sẻ mutable authenticated context giữa tests chạy song song.

## Trade-offs

- Context-per-test tăng setup cost nhưng cho isolation tốt hơn nhiều so với shared context.
- Browser-per-test isolation mạnh hơn nữa nhưng thường tốn startup cost lớn hơn.
- Storage state giúp giảm login time nhưng có thể che giấu bug login nếu tất cả test đều bỏ qua UI auth flow.
- Parallelism cao rút ngắn wall-clock time nhưng có thể overload test environment; cần benchmark và giới hạn worker phù hợp.
- Reuse một account cho nhiều test song song có thể vẫn gây conflict ở server-side data dù browser isolation đúng; test data strategy phải được thiết kế riêng.

## Cách kiểm thử

1. **Parallel isolation test:** chạy 20 test đồng thời với nhiều user/role; xác nhận cookie/session không cross-contaminate.
2. **Navigation race test:** mỗi test navigate tới URL khác; xác nhận page state hoàn toàn độc lập.
3. **Failure artifact test:** cố tình fail nhiều test đồng thời và xác nhận screenshot/trace map đúng test id/attempt.
4. **Lifecycle test:** kết thúc một test session trong khi test khác còn chạy; test kia không bị ảnh hưởng.
5. **Load/CI test:** tăng parallelism dần và theo dõi test duration, CPU/memory của runner, browser crash rate và target-environment saturation.

## Quan sát trong production

Với test infrastructure/CI, nên thu thập:

- test id, suite, attempt, worker id,
- browser/context creation duration,
- test duration và timeout reason,
- trace/screenshot/video khi fail theo policy,
- count của browser/context/page closed errors,
- retry rate và flaky-pass-after-retry rate,
- CPU/memory của runner,
- số concurrent contexts/pages,
- target environment latency/error rate trong thời gian test.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn browser-per-worker thay vì browser-per-suite?
2. Nếu storage state được reuse cho nhiều test, bạn bảo vệ test isolation và secret management thế nào?
3. Nếu flaky test giảm khi tắt parallelism, bạn sẽ chứng minh nguyên nhân là shared browser state thay vì target environment quá tải ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Credential rotation phải được thiết kế như state machine có invariant ở database; check-then-update đơn thuần không đủ dưới concurrency.
- Sensitive credential không nên xuất hiện trong log và nên giảm blast radius nếu storage bị compromise.
- Retry semantics phải được thiết kế cùng với replay detection thay vì giả định network luôn trả response đúng một lần.
- Trong test automation, reusable resource và mutable state phải có lifetime khác nhau: browser có thể share, nhưng context/page cần isolation rõ ràng khi chạy song song.
- Flaky test thường là tín hiệu của race condition, shared state, resource ownership hoặc môi trường bị saturation chứ không chỉ là “test không ổn định”.

## Mẫu tư duy cần nhớ

- **Model credential lifecycle explicitly:** Active → Consumed/Replaced/Revoked thay vì chỉ kiểm tra expiry.
- **Put invariants where concurrency happens:** nếu nhiều instance cùng xử lý, invariant phải được database hoặc coordination mechanism enforce.
- **Design retries together with idempotency/replay semantics.**
- **Share expensive immutable infrastructure, isolate mutable state.**
- **Treat observability as part of the design:** log outcome/correlation, không log secret.
