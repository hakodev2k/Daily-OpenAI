# Code Review Challenge 1 — Hangfire gửi thông báo bị trùng khi retry

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để gửi thông báo khi lịch sự kiện thay đổi. API cập nhật database rồi enqueue một job. Job đọc event, gọi dịch vụ notification bên ngoài và cuối cùng đánh dấu `NotificationSent = true`.

Production đôi lúc xuất hiện hai notification giống nhau. Hiện tượng thường xảy ra khi external API chậm, worker restart hoặc Hangfire retry job. Hệ thống có nhiều Hangfire workers và có thể xử lý nhiều job song song. Business yêu cầu một thay đổi của event chỉ được gửi một lần tới mỗi người nhận.

## Đoạn code cần review

```csharp
public sealed class EventNotificationJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<EventNotificationJob> _logger;

    public EventNotificationJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<EventNotificationJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task SendAsync(Guid eventId)
    {
        var evt = await _db.Events
            .Include(x => x.Attendees)
            .FirstOrDefaultAsync(x => x.Id == eventId);

        if (evt == null || evt.NotificationSent)
            return;

        foreach (var attendee in evt.Attendees)
        {
            var response = await _httpClient.PostAsJsonAsync(
                "/api/notifications",
                new
                {
                    EventId = evt.Id,
                    attendee.Email,
                    evt.Title,
                    evt.StartTime,
                    evt.EndTime
                });

            response.EnsureSuccessStatusCode();
        }

        evt.NotificationSent = true;
        evt.NotificationSentAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Notification sent for event {EventId} to {Count} attendees",
            eventId,
            evt.Attendees.Count);
    }
}
```

## Câu hỏi gợi mở

- Hai workers có thể cùng đọc `NotificationSent == false` không?
- Điều gì xảy ra nếu gửi thành công cho 8/10 attendees rồi request thứ 9 timeout?

## Kết quả code review tham khảo

### 1. Check-then-act không atomic

**Problem:** `NotificationSent` được đọc trước rồi cập nhật sau toàn bộ quá trình gửi.  
**Why:** Hai workers có thể cùng đọc `false` trước khi bất kỳ worker nào commit.  
**Production impact:** Gửi notification trùng.  
**Severity:** Critical  
**Recommended fix:** Không dùng boolean check như distributed lock. Thiết kế durable delivery record có unique key và state transition có concurrency control.

### 2. External side effect và database commit không atomic

**Problem:** HTTP request thành công nhưng process có thể chết trước `SaveChangesAsync`.  
**Why:** Database transaction không thể rollback side effect đã xảy ra ở external service.  
**Production impact:** Retry gửi lại notification.  
**Severity:** Critical  
**Recommended fix:** Dùng idempotency key mà downstream hỗ trợ, hoặc outbox/delivery ledger kết hợp unique delivery identity và retry an toàn.

### 3. Partial success làm retry gửi lại người đã nhận

**Problem:** Nếu attendee thứ 9 lỗi, 8 attendee trước đã nhận nhưng event vẫn chưa được đánh dấu hoàn tất.  
**Why:** Trạng thái chỉ tồn tại ở cấp event.  
**Production impact:** Retry gửi lại cho 8 người đầu.  
**Severity:** High  
**Recommended fix:** Theo dõi delivery riêng cho từng recipient và event version; chỉ retry delivery chưa thành công.

### 4. `NotificationSent` không mô hình hóa version của event

**Problem:** Sau lần gửi đầu, một thay đổi thời gian tiếp theo có thể cần notification mới nhưng boolean vẫn `true`.  
**Why:** State không gắn với version/change identity.  
**Production impact:** Có thể bỏ sót notification hợp lệ hoặc phải reset boolean bằng logic dễ race.  
**Severity:** High  
**Recommended fix:** Tạo `EventChangeId`/version và delivery key `(EventId, Version, RecipientId)`.

### 5. Không truyền cancellation token

**Problem:** EF Core và HTTP calls không nhận cancellation token.  
**Why:** Job shutdown/cancellation khó propagate xuống I/O.  
**Production impact:** Shutdown lâu hơn và request không còn cần thiết vẫn tiếp tục.  
**Severity:** Medium  
**Recommended fix:** Truyền token phù hợp nếu execution framework/application cung cấp cancellation semantics.

### 6. Gửi tuần tự có latency tuyến tính

**Problem:** Mỗi attendee chờ request trước hoàn thành.  
**Why:** `foreach` + `await` tuần tự.  
**Production impact:** Job kéo dài khi attendee nhiều; tăng xác suất timeout/retry.  
**Severity:** Medium  
**Recommended fix:** Ưu tiên queue/delivery-per-recipient; nếu cần parallelism thì bounded concurrency thay vì `Task.WhenAll` không giới hạn.

### 7. `EnsureSuccessStatusCode` không phân biệt transient/permanent failure

**Problem:** Mọi non-success đều thành exception.  
**Why:** Không phân loại 4xx, 429, 5xx, timeout.  
**Production impact:** Retry vô ích với permanent failure hoặc retry quá mạnh khi downstream throttling.  
**Severity:** Medium  
**Recommended fix:** Có retry policy rõ ràng, exponential backoff/jitter, tôn trọng tín hiệu throttling khi có, và dead-letter/manual review cho lỗi vĩnh viễn.

### 8. Logging chỉ có success tổng thể

**Problem:** Không có delivery identity, attempt hoặc trạng thái từng recipient.  
**Why:** Log chỉ được ghi cuối happy path.  
**Production impact:** Khó phân biệt retry, duplicate và partial delivery.  
**Severity:** Medium  
**Recommended fix:** Structured logs/metrics theo delivery ID, event version, attempt, downstream status và duration; tránh log dữ liệu nhạy cảm không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định mỗi lần thay đổi event tạo một `EventNotificationDelivery` riêng cho từng recipient và database có unique constraint trên `(EventId, EventVersion, AttendeeId)`. Downstream nhận `Idempotency-Key` và bảo đảm cùng key không tạo side effect lần hai.

```csharp
public sealed class EventNotificationJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<EventNotificationJob> _logger;

    public EventNotificationJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<EventNotificationJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task SendDeliveryAsync(Guid deliveryId, CancellationToken ct)
    {
        var delivery = await _db.EventNotificationDeliveries
            .SingleOrDefaultAsync(x => x.Id == deliveryId, ct);

        if (delivery is null || delivery.Status == DeliveryStatus.Succeeded)
            return;

        var idempotencyKey = delivery.Id.ToString("N");

        using var request = new HttpRequestMessage(
            HttpMethod.Post,
            "/api/notifications")
        {
            Content = JsonContent.Create(new
            {
                delivery.EventId,
                delivery.EventVersion,
                delivery.Recipient,
                delivery.Title,
                delivery.StartTime,
                delivery.EndTime
            })
        };

        request.Headers.TryAddWithoutValidation("Idempotency-Key", idempotencyKey);

        var startedAt = Stopwatch.GetTimestamp();

        try
        {
            using var response = await _httpClient.SendAsync(request, ct);

            if (!response.IsSuccessStatusCode)
            {
                throw new HttpRequestException(
                    $"Notification provider returned {(int)response.StatusCode}",
                    null,
                    response.StatusCode);
            }

            delivery.Status = DeliveryStatus.Succeeded;
            delivery.SentAt = DateTimeOffset.UtcNow;
            delivery.LastError = null;
            await _db.SaveChangesAsync(ct);

            _logger.LogInformation(
                "Notification delivery {DeliveryId} succeeded for event {EventId} version {Version}",
                delivery.Id,
                delivery.EventId,
                delivery.EventVersion);
        }
        catch (Exception ex) when (ex is not OperationCanceledException)
        {
            delivery.AttemptCount++;
            delivery.LastAttemptAt = DateTimeOffset.UtcNow;
            delivery.LastError = ex.GetType().Name;
            await _db.SaveChangesAsync(CancellationToken.None);

            _logger.LogWarning(
                ex,
                "Notification delivery {DeliveryId} failed after {ElapsedMs} ms",
                delivery.Id,
                Stopwatch.GetElapsedTime(startedAt).TotalMilliseconds);

            throw;
        }
    }
}
```

Điểm quan trọng: code trên chỉ thật sự chống duplicate external side effect nếu downstream thực thi idempotency theo key, hoặc ta có một cơ chế delivery khác cung cấp guarantee tương đương. Việc ghi `Succeeded` sau HTTP success vẫn có crash window; idempotency key làm retry qua cửa sổ đó an toàn.

## Trade-offs

Delivery ledger tăng số row và complexity nhưng cho phép retry từng recipient, audit và phân tích failure rõ ràng. Outbox giải quyết đáng tin cậy việc chuyển database state thành message nhưng bản thân outbox không tự biến một HTTP consumer không-idempotent thành exactly-once. Nếu downstream không hỗ trợ idempotency, cần thay đổi protocol, sở hữu consumer, hoặc chấp nhận/định nghĩa cơ chế deduplication ở một boundary khác.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời nhiều execution cho cùng `deliveryId`; downstream fake phải quan sát tối đa một business side effect cho cùng idempotency key.
2. **Crash-window test:** downstream trả success nhưng giả lập lỗi trước DB commit; retry phải không tạo notification thứ hai.
3. **Partial failure:** 10 recipient, một recipient lỗi; chỉ delivery lỗi được retry.
4. **Transient failure:** 429/5xx/timeout được retry theo policy; permanent 4xx không bị retry vô hạn.
5. **Event version:** cùng attendee nhưng event version mới phải tạo delivery mới, trong khi retry cùng version không tạo duplicate.

## Quan sát trong production

Theo dõi `delivery_attempt_total`, `delivery_success_total`, `delivery_failure_total`, retry count, age của pending deliveries, downstream latency/error rate và số lần downstream báo idempotency replay nếu có. Trace nên nối Hangfire execution → delivery → HTTP dependency bằng correlation/delivery ID. Alert khi backlog hoặc oldest pending age vượt SLO, thay vì chỉ alert theo exception count.

## Câu hỏi phỏng vấn mở rộng

1. Outbox pattern giải quyết phần nào của bài toán và phần nào nó không giải quyết?
2. Nếu notification provider không hỗ trợ idempotency key, bạn thay đổi architecture như thế nào?
3. Unique constraint trong database có đủ để bảo đảm exactly-once external side effect không? Vì sao?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log vừa chậm vừa lộ dữ liệu

## Bối cảnh

Một API nội bộ cho phép người dùng portal tìm audit logs. Mỗi user thuộc một tenant/OpCo. Admin tenant được xem log trong tenant của mình; user thường chỉ được xem activity của chính họ.

Sau khi số lượng audit log tăng lên vài triệu row, endpoint bắt đầu tiêu thụ nhiều memory và latency tăng mạnh. Security review đồng thời phát hiện có trường hợp user nhìn thấy log không thuộc phạm vi được phép. Query text và metadata đôi khi chứa email, identifier và nội dung lỗi từ downstream.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? text,
        string? tenantId,
        DateTime? from,
        DateTime? to,
        int page = 1,
        int pageSize = 100)
    {
        var logs = await _db.AuditLogs
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(tenantId))
            logs = logs.Where(x => x.TenantId == tenantId).ToList();

        if (!string.IsNullOrWhiteSpace(text))
            logs = logs.Where(x =>
                x.Message.Contains(text, StringComparison.OrdinalIgnoreCase) ||
                x.UserEmail.Contains(text, StringComparison.OrdinalIgnoreCase))
                .ToList();

        if (from.HasValue)
            logs = logs.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            logs = logs.Where(x => x.CreatedAt <= to.Value).ToList();

        var result = logs
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.UserEmail,
                x.Message,
                x.Metadata,
                x.CreatedAt
            });

        _logger.LogInformation(
            "Audit search text={Text}, tenant={TenantId}, count={Count}",
            text,
            tenantId,
            logs.Count);

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant authorization / IDOR-style data exposure

**Problem:** Client tự truyền `tenantId`, và khi bỏ trống thì không có tenant filter.  
**Why:** Authorization scope dựa trên dữ liệu không đáng tin cậy từ request.  
**Production impact:** User có thể đọc audit logs của tenant khác.  
**Severity:** Critical  
**Recommended fix:** Lấy tenant/user scope từ authenticated principal/server-side authorization context; policy authorization quyết định phạm vi truy cập.

### 2. Không enforce quyền admin so với user thường

**Problem:** Endpoint không giới hạn user thường về activity của chính họ.  
**Why:** Chỉ có optional tenant filter, không có authorization rule theo role/claim.  
**Production impact:** Horizontal privilege escalation trong cùng tenant.  
**Severity:** Critical  
**Recommended fix:** Áp dụng policy và build mandatory predicate: tenant admin → tenant scope; regular user → tenant + own subject/user ID.

### 3. Materialize toàn bộ bảng trước khi filter

**Problem:** `ToListAsync()` chạy trước mọi filter/pagination.  
**Why:** Sau đó toàn bộ LINQ là LINQ-to-Objects.  
**Production impact:** Đọc hàng triệu row, memory pressure, GC, DB/network load và latency cao.  
**Severity:** High  
**Recommended fix:** Xây dựng `IQueryable`, filter trước, projection/pagination rồi mới materialize.

### 4. Pagination không được validate

**Problem:** `page <= 0`, `pageSize <= 0` hoặc page size cực lớn đều không bị chặn.  
**Why:** Không có request validation.  
**Production impact:** Error/behavior bất ngờ hoặc response cực lớn gây resource exhaustion.  
**Severity:** High  
**Recommended fix:** Validate và cap page size; cân nhắc cursor/keyset pagination khi offset sâu trở thành bottleneck.

### 5. Response trả dữ liệu nhạy cảm quá mức

**Problem:** Trả nguyên `UserEmail`, `Message`, `Metadata`.  
**Why:** DTO phản ánh storage model thay vì least-data contract.  
**Production impact:** PII, downstream errors, token/identifier vô tình bị lộ.  
**Severity:** High  
**Recommended fix:** Projection sang DTO tối thiểu; redact/sanitize metadata; quyền chi tiết tách riêng nếu cần.

### 6. Search text được ghi thẳng vào application log

**Problem:** User-controlled search string được log.  
**Why:** Structured logging vẫn lưu raw value nếu không sanitize.  
**Production impact:** PII/secrets có thể được nhân bản sang logging platform; tăng rủi ro log injection/forensic noise tùy sink.  
**Severity:** Medium  
**Recommended fix:** Không log raw search text; log normalized metadata như query-present, length, filter types và correlation ID.

### 7. Date range không giới hạn

**Problem:** Có thể query phạm vi rất rộng.  
**Why:** Không có validation/range policy.  
**Production impact:** Expensive query và abuse.  
**Severity:** Medium  
**Recommended fix:** Đặt max range phù hợp business hoặc dùng privileged export workflow cho range lớn.

### 8. Search strategy có thể không scale

**Problem:** `Contains` trên các trường text lớn có thể không tận dụng index thông thường hiệu quả tùy database/collation/query shape.  
**Why:** Substring search có đặc tính khác equality/prefix lookup.  
**Production impact:** Scan lớn khi dữ liệu tăng.  
**Severity:** Medium  
**Recommended fix:** Đo execution plan; xác định semantics search; dùng index phù hợp, full-text/search service nếu yêu cầu thật sự cần substring/fuzzy search ở quy mô lớn.

## Phiên bản code đề xuất

Ví dụ giả định authentication middleware đã tạo `TenantId`, `sub` và role claims. Authorization policy bảo đảm caller được phép dùng audit search. Cách map claim thực tế phải theo identity model của hệ thống.

```csharp
[Authorize(Policy = "Audit.Read")]
[HttpGet("search")]
public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
    [FromQuery] AuditSearchRequest request,
    CancellationToken ct)
{
    if (request.Page < 1 || request.PageSize is < 1 or > 200)
        return ValidationProblem("Invalid pagination parameters.");

    if (request.From.HasValue && request.To.HasValue && request.From > request.To)
        return ValidationProblem("Invalid date range.");

    var tenantId = User.FindFirst("tenant_id")?.Value;
    var subjectId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

    if (string.IsNullOrWhiteSpace(tenantId) || string.IsNullOrWhiteSpace(subjectId))
        return Forbid();

    var isTenantAdmin = User.IsInRole("TenantAdmin");

    IQueryable<AuditLog> query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!isTenantAdmin)
        query = query.Where(x => x.SubjectId == subjectId);

    if (request.From.HasValue)
        query = query.Where(x => x.CreatedAt >= request.From.Value);

    if (request.To.HasValue)
        query = query.Where(x => x.CreatedAt <= request.To.Value);

    if (!string.IsNullOrWhiteSpace(request.Text))
    {
        var term = request.Text.Trim();
        query = query.Where(x =>
            x.Message.Contains(term) || x.UserEmail.Contains(term));
    }

    var rows = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Skip((request.Page - 1) * request.PageSize)
        .Take(request.PageSize)
        .Select(x => new AuditLogDto(
            x.Id,
            x.Action,
            x.CreatedAt,
            x.UserDisplayName))
        .ToListAsync(ct);

    _logger.LogInformation(
        "Audit search completed for tenant {TenantId}; admin={IsAdmin}; hasText={HasText}; pageSize={PageSize}; returned={Count}",
        tenantId,
        isTenantAdmin,
        !string.IsNullOrWhiteSpace(request.Text),
        request.PageSize,
        rows.Count);

    return Ok(rows);
}

public sealed record AuditSearchRequest(
    string? Text,
    DateTimeOffset? From,
    DateTimeOffset? To,
    int Page = 1,
    int PageSize = 50);

public sealed record AuditLogDto(
    Guid Id,
    string Action,
    DateTimeOffset CreatedAt,
    string? UserDisplayName);
```

`Contains` ở ví dụ trên chỉ minh họa giữ filtering ở database; production cần kiểm tra SQL được provider sinh ra, collation/case-sensitivity và execution plan thay vì giả định substring search sẽ scale.

## Trade-offs

Offset pagination đơn giản và phù hợp UI nhỏ, nhưng page sâu ngày càng đắt và dữ liệu thay đổi giữa các request có thể làm item dịch chuyển. Keyset pagination theo `(CreatedAt, Id)` tốt hơn cho feed lớn nhưng khó hỗ trợ nhảy trực tiếp tới page N. Full-text/search engine cải thiện search phức tạp nhưng tăng infrastructure và consistency considerations; chỉ nên thêm sau khi requirement và measurement chứng minh cần thiết.

## Cách kiểm thử

1. **Authorization integration test:** tenant A không bao giờ đọc được row tenant B dù tự sửa query parameters.
2. **Role test:** regular user chỉ thấy own activity; tenant admin thấy toàn tenant theo policy.
3. **Database/query test:** kiểm tra generated SQL hoặc command instrumentation để bảo đảm WHERE/LIMIT/OFFSET được thực thi ở DB và projection không tải `Metadata` không cần thiết.
4. **Load test:** vài triệu rows, đo p95/p99 latency, rows read và database CPU cho common filters; kiểm tra deep pagination riêng.
5. **Sensitive-data test:** response và logs không chứa raw metadata/search text hoặc fields không thuộc contract.

## Quan sát trong production

Theo dõi request latency p50/p95/p99, DB command duration, timeout/error rate, returned-row count, page-size distribution và slow-query plans. Security telemetry nên ghi actor ID, tenant scope, authorization result và correlation ID nhưng tránh raw search term/PII không cần thiết. Alert khi audit-search error/timeout tăng hoặc query duration vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển từ offset pagination sang keyset pagination?
2. Nếu requirement bắt buộc search substring không phân biệt hoa thường trên hàng chục triệu logs, bạn đánh giá SQL index, full-text và external search như thế nào?
3. Global query filter cho tenant có đủ thay thế authorization policy không? Vì sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 nhấn mạnh rằng retry và distributed side effects phải được thiết kế cùng idempotency. Một database flag không biến HTTP side effect thành exactly-once, và crash window giữa external success với DB commit là failure mode cần thiết kế chủ động.

Challenge 2 nhấn mạnh thứ tự ưu tiên trong backend review: authorization boundary trước, sau đó mới correctness và performance. Query phải giữ ở `IQueryable` cho đến khi filtering/projection/pagination hoàn tất; đồng thời API contract và logging phải tuân theo nguyên tắc least privilege/least data.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng idempotency; đừng thêm retry độc lập với side-effect semantics.
- Authorization scope phải đến từ trusted identity/context, không từ client-supplied identifiers.
- Đẩy filtering, projection và pagination xuống database trước khi materialize.
- Thiết kế failure path trước khi tin happy path: partial success và crash-after-side-effect là case bình thường của distributed systems.
- Observability là một phần của design, nhưng telemetry cũng phải tuân thủ data minimization.
