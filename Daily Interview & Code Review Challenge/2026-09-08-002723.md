# Câu 1 — Vì sao Elasticsearch có thể trả kết quả “cũ” dù dữ liệu nguồn đã cập nhật thành công?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, eventual consistency, indexing pipeline, search architecture, debugging, observability, API design

## Bối cảnh

Một e-commerce platform có SQL Server làm source of truth cho product catalog và Elasticsearch phục vụ product search.

Flow hiện tại:

- Product Admin API cập nhật giá, title, availability trong SQL Server.
- Sau khi transaction SQL thành công, application gửi một message để đồng bộ document sang Elasticsearch.
- Search API chỉ đọc Elasticsearch để giữ latency thấp.
- Production chạy nhiều application instances.
- Người dùng đôi khi vừa cập nhật product trong admin portal nhưng search page vẫn thấy dữ liệu cũ trong vài giây, đôi lúc lâu hơn.
- Monitoring cho thấy SQL update đã thành công.
- Không phải mọi trường hợp đều có Elasticsearch error.
- Một developer đề xuất gọi Elasticsearch refresh ngay sau mỗi lần index để “đảm bảo dữ liệu mới xuất hiện ngay”.
- Một developer khác đề xuất bỏ Elasticsearch và cho search endpoint query trực tiếp SQL Server.

Chưa biết chắc:

- message có bị duplicate hoặc delay hay không;
- consumer có bảo toàn ordering theo product hay không;
- indexing request đã được Elasticsearch acknowledge ở thời điểm người dùng search hay chưa;
- business thực sự cần strong consistency hay chấp nhận độ trễ ngắn;
- có nhiều update liên tiếp cho cùng product hay không.

## Câu hỏi chính

Hãy giải thích cơ chế nào có thể khiến search trả dữ liệu cũ mặc dù SQL update đã commit, cách bạn chứng minh nguyên nhân trong production, và bạn sẽ thiết kế consistency contract giữa SQL Server, message processing và Elasticsearch như thế nào thay vì chỉ “ép refresh”.

## Câu hỏi làm rõ nên cân nhắc

1. Business chấp nhận search lag tối đa bao lâu sau khi product được cập nhật?
2. Search result có bắt buộc phản ánh ngay price/availability mới hay một số field có requirement consistency khác nhau?
3. Message có chứa toàn bộ product snapshot, chỉ product ID, hay event delta/version?
4. Với nhiều update liên tiếp cho cùng product, hệ thống hiện có sequence/version để ngăn event cũ ghi đè event mới không?
5. Dashboard hiện có timestamp/correlation ID xuyên suốt SQL commit → publish → consume → index → searchable hay chưa?

## Gợi ý tư duy

### Gợi ý 1

Tách “database đã commit” khỏi “search projection đã được cập nhật” và khỏi “document mới đã searchable”. Đây là các mốc khác nhau.

### Gợi ý 2

Hãy kiểm tra cả pipeline trước Elasticsearch: publish failure, backlog, retry, duplicate, ordering, consumer crash và stale event.

### Gợi ý 3

Một giải pháp tốt cần định nghĩa business consistency contract, versioning/idempotency và observability end-to-end; refresh chỉ là một phần của search-engine visibility behavior.

## Cấu trúc trả lời đề xuất

1. Làm rõ consistency requirement theo từng field/use case.
2. Mô tả các stage từ SQL commit đến search visibility.
3. Liệt kê các giả thuyết cạnh tranh.
4. Xác định telemetry/evidence để phân biệt từng giả thuyết.
5. Phân tích ordering, duplicate và stale-write risk.
6. Đề xuất consistency contract và projection design.
7. Đánh giá refresh-on-every-write, direct SQL query và các lựa chọn khác.
8. Đề xuất test failure/reordering/backlog.
9. Đề xuất monitoring/SLO.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra SQL Server và Elasticsearch là hai data stores khác nhau; commit ở SQL không đồng nghĩa search projection đã được cập nhật.
- Phân biệt message publication/consumption/indexing/search visibility.
- Không giả định một root cause duy nhất.
- Xem xét duplicate, out-of-order event và stale overwrite.
- Đề xuất idempotency/versioning cho search projection.
- Không dùng manual refresh sau mọi write như default answer.
- Có cách đo end-to-end propagation lag.

### Điểm cộng

- Đề xuất Outbox Pattern hoặc cơ chế tương đương để thu hẹp khoảng trống giữa database commit và event publication.
- Phân loại field theo consistency sensitivity; ví dụ price/availability có thể cần treatment khác content marketing.
- Đề xuất read-your-writes UX cho admin thay vì biến toàn bộ search system thành strongly consistent.
- Nêu phương án rebuild/replay index an toàn.

### Senior+

- Thiết kế version monotonic per product hoặc source version và chỉ apply event không cũ hơn projection hiện tại.
- Phân tích trade-off giữa search freshness, throughput, indexing pressure và failure recovery.
- Định nghĩa measurable SLO như “99% catalog updates searchable trong X giây”, với X phải xuất phát từ business requirement chứ không tự bịa.

## Hướng giải quyết tham khảo

Trước hết, tôi sẽ không kết luận “Elasticsearch chậm refresh” chỉ vì SQL đã commit nhưng search còn cũ. Pipeline có nhiều boundary.

Một update hợp lý có thể đi qua các mốc:

1. transaction SQL commit;
2. event/message được persist/publish;
3. broker nhận message;
4. consumer nhận message;
5. consumer đọc hoặc dựng document;
6. indexing request tới Elasticsearch thành công;
7. document trở nên visible với search;
8. client/CDN/frontend nhận kết quả mới.

Dữ liệu cũ có thể xuất phát ở bất kỳ boundary nào. Ví dụ:

- SQL commit thành công nhưng process chết trước khi publish message;
- message backlog làm consumer xử lý chậm;
- retry khiến message tới muộn;
- hai update A rồi B cho cùng product nhưng consumer xử lý B trước A và A ghi đè về dữ liệu cũ;
- consumer index thành công nhưng search visibility chưa đạt thời điểm mà request sau đó nhìn thấy thay đổi;
- application/search layer còn cache cũ;
- client gọi vào một query/index alias khác với nơi consumer vừa ghi.

Vì vậy tôi cần correlation xuyên suốt. Với mỗi product update, tôi muốn có ít nhất `productId`, source version hoặc updated timestamp đáng tin cậy, event ID, publish timestamp, consume timestamp, indexing result, dependency duration và thời điểm projection được quan sát là mới. Không cần log toàn document nếu có PII hoặc payload lớn.

Nếu hiện tại application update SQL rồi publish message ngoài transaction, có dual-write gap. Một failure giữa hai hành động có thể làm SQL mới nhưng không có event. Tôi sẽ cân nhắc transactional outbox: product update và outbox record được commit cùng database transaction; publisher riêng đọc outbox và gửi message. Đây không làm end-to-end operation thành exactly-once, nhưng giúp tránh mất event do khoảng trống commit/publish. Consumer vẫn cần idempotent vì message có thể được giao lại.

Với nhiều updates cùng product, event cần identity và ordering/version semantics. Ví dụ source lưu `Version = 42`; projection hiện ở 42 thì event version 41 tới muộn phải bị bỏ qua, còn duplicate 42 không được tạo side effect sai. Chỉ dựa vào event arrival time thường không đủ nếu clocks hoặc retries làm thứ tự không đáng tin cậy.

Về Elasticsearch refresh: tôi không chọn refresh trên mọi write như fix mặc định. Việc buộc visibility đồng bộ cho từng update có thể làm giảm throughput và tăng indexing overhead. Nếu business chỉ yêu cầu near-real-time search, giải pháp tốt hơn thường là định nghĩa bounded freshness SLO và đo lag. Nếu một flow cụ thể thật sự cần read-your-writes, có thể thiết kế riêng: admin confirmation page đọc source-of-truth hoặc trả lại DTO vừa cập nhật thay vì phụ thuộc search projection ngay lập tức.

Tôi cũng không bỏ Elasticsearch chỉ vì có eventual consistency. SQL Server có thể phù hợp nếu requirement search đơn giản và scale nhỏ, nhưng quyết định phải dựa trên query capabilities, relevance, full-text behavior, scale và operational cost. Nếu product search cần Elasticsearch, ta nên làm consistency contract rõ ràng thay vì biến search engine thành database giao dịch.

Testing cần gồm:

- duplicate event;
- out-of-order event;
- consumer crash sau index nhưng trước message acknowledgement;
- broker delay/backlog;
- Elasticsearch transient failure;
- rebuild index rồi alias switch;
- burst updates cùng product;
- load test đo propagation lag.

Monitoring nên có backlog, consumer error/retry rate, indexing latency/error, end-to-end projection lag, stale-event discard count và freshness SLO. Khi incident xảy ra, trace một `productId` cụ thể từ write tới search sẽ cho bằng chứng thay vì đoán.

Nếu business nói price/availability phải tuyệt đối current ở checkout, tôi sẽ không dùng search index làm authority cho checkout validation. Search có thể hiển thị candidate information, còn thao tác tạo order cần validate lại bằng transactional source phù hợp trước khi commit.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách ba sự kiện: SQL đã commit, search projection đã được index, và document đã visible cho search. SQL thành công chỉ chứng minh bước đầu tiên. Tôi sẽ trace một product bằng event ID/source version để xem delay nằm ở publish, broker backlog, consumer, Elasticsearch indexing hay cache phía sau. Tôi cũng kiểm tra duplicate và đặc biệt out-of-order event vì một event cũ tới muộn có thể ghi đè dữ liệu mới.

Nếu đang dual-write SQL rồi publish message, tôi cân nhắc outbox để tránh mất event giữa hai bước. Consumer phải idempotent và nên dùng source version để reject stale updates. Tôi không ép refresh sau mọi write theo mặc định vì đổi freshness lấy indexing cost/throughput; trước hết cần business xác nhận freshness SLO. Với admin flow cần read-your-writes, tôi có thể đọc source-of-truth hoặc trả dữ liệu vừa update thay vì buộc toàn bộ search path strongly consistent. Tôi sẽ đo end-to-end propagation lag và test duplicate, reordering, backlog, consumer crash và Elasticsearch failure.”

## Câu hỏi đào sâu

1. Nếu consumer đã index Elasticsearch thành công nhưng crash trước khi acknowledge message, thiết kế của bạn xử lý delivery lặp lại ra sao?
2. Nếu Product yêu cầu price trên search phải cập nhật trong dưới một ngưỡng rất nhỏ nhưng description có thể trễ lâu hơn, bạn có thay đổi kiến trúc không?
3. Nếu dùng source version để bỏ stale event, bạn xử lý rebuild toàn index và alias switch như thế nào để không làm version logic sai?

## Lỗi trả lời thường gặp

- Kết luận ngay “Elasticsearch eventual consistency” mà không kiểm tra message pipeline.
- Cho rằng message broker đảm bảo exactly-once nên consumer không cần idempotency.
- Gọi refresh sau mọi index mà không đánh giá throughput/freshness requirement.
- Không xem xét event cũ ghi đè event mới.
- Không có metric end-to-end nên incident vẫn phải grep log thủ công.

## Thang điểm 0–10

- **0–2:** Chỉ nói “thêm refresh” hoặc “thêm retry”, không hiểu pipeline consistency.
- **3–4:** Nhận ra eventual consistency nhưng thiếu evidence, ordering và failure analysis.
- **5–6:** Phân tích được publish/consume/index/visibility, có monitoring và idempotency cơ bản.
- **7–8:** Có versioning, outbox/recovery strategy, trade-off freshness/throughput và testing thực tế.
- **9–10:** Định nghĩa consistency contract theo business use case, failure semantics rõ, measurable SLO, rebuild/replay strategy và communication súc tích.

# Câu 2 — IIS application pool liên tục recycle làm API có 5xx, login thất thường và background job chạy lại

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET Core hosting, process lifecycle, memory, deployment, background processing, observability, incident response

## Bối cảnh

Một enterprise internal portal đã được nâng cấp từ .NET Framework lên ASP.NET Core .NET 8 nhưng vẫn host trên Windows Server/IIS do hạ tầng doanh nghiệp hiện tại.

Sau một release gần đây, production xuất hiện theo từng đợt:

- một phần request trả 502/503;
- user đang đăng nhập đôi khi bị redirect/login lại;
- warm request sau một khoảng yên tĩnh chậm hơn rõ rệt;
- một scheduled reconciliation job đôi khi chạy lại sau khi application khởi động;
- memory của worker process tăng dần trong vài giờ;
- support nói “restart IIS thì hết một lúc”;
- log application có nhiều startup messages nhưng chưa có correlation với IIS/process events;
- server có nhiều application cùng chạy;
- deployment pipeline hiện copy file trực tiếp vào website directory;
- team chưa chắc recycle đến từ memory limit, scheduled recycle, config change, file change, crash hay host health policy;
- một developer đề xuất tăng memory limit và auto-restart thường xuyên hơn.

Business impact là người dùng nội bộ không hoàn thành approval workflow ổn định trong giờ cao điểm. Không có bằng chứng hiện tại rằng database hoặc downstream API là root cause.

## Câu hỏi chính

Bạn là người trực incident. Hãy trình bày cách ổn định hệ thống, thu thập bằng chứng để phân biệt các nguyên nhân làm worker process/application restart, tìm root cause, và ngăn việc process lifecycle gây mất availability hoặc duplicate background work.

## Câu hỏi làm rõ nên cân nhắc

1. 502/503 xảy ra đồng thời trên tất cả servers hay chỉ một node/process cụ thể?
2. Có process ID/start time/recycle reason nào được capture trong application logs, Windows Event Logs hoặc IIS telemetry không?
3. Session/authentication state hiện lưu ở memory của process hay dùng external/shared state?
4. Scheduled reconciliation job có distributed coordination/idempotency không, hay cứ startup là chạy?
5. Deployment copy file có làm application restart giữa lúc traffic đang phục vụ và có health/drain strategy hay không?

## Gợi ý tư duy

### Gợi ý 1

“Restart IIS thấy đỡ” là symptom, không phải root cause. Trước hết cần biết chính xác process nào chết/recycle và tại sao.

### Gợi ý 2

Phân biệt application restart hợp lệ với crash, memory pressure, configuration/file change, deployment và infrastructure policy.

### Gợi ý 3

Ngay cả khi không thể loại bỏ restart, application vẫn phải chịu được restart: session strategy, graceful shutdown, idempotent background work, health checks và safe deployment.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và blast radius.
2. Stabilize traffic mà không phá bằng chứng.
3. Correlate 5xx với worker process lifetime/recycle events.
4. Xây nhiều giả thuyết và bằng chứng cần kiểm tra cho từng giả thuyết.
5. Điều tra memory, crash dump/event log, deployment/configuration và health state.
6. Xác minh root cause trước khi đổi limit.
7. Tách remediation cho availability và background correctness.
8. Thiết kế deployment/rollback an toàn.
9. Test restart/recycle/failure path.
10. Thiết lập monitoring/prevention.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Ưu tiên giảm impact trước nhưng không “restart loop” vô điều kiện.
- Correlate request failures với process ID/start time/IIS-Windows events.
- Không giả định memory leak chỉ vì memory tăng.
- Kiểm tra deployment/file/config changes và process crash/recycle reasons.
- Nhận ra in-process state/background work dễ bị ảnh hưởng bởi restart.
- Scheduled/background operation phải idempotent hoặc có coordination phù hợp.
- Có rollback/canary/drain/health strategy phù hợp môi trường.

### Điểm cộng

- Thu dump/metrics khi memory vượt threshold có ý nghĩa trước khi restart thủ công.
- Phân tích GC heap vs native memory vs connection/resource leak.
- Tách authentication cookie/token validity khỏi server-side session state.
- Đưa process identity/start timestamp vào structured logs/traces.

### Senior+

- Định nghĩa failure injection test bằng deliberate recycle/process termination.
- Thiết kế background job để retry sau crash không tạo duplicate side effect.
- Có release strategy tránh copy-in-place gây window không nhất quán.
- Đưa root-cause evidence vào post-incident action thay vì chỉnh infrastructure limit theo cảm tính.

## Hướng giải quyết tham khảo

Tôi sẽ xử lý incident theo hai track: availability trước, diagnosis song song.

Về stabilization, nếu chỉ một node lỗi và hệ thống có nhiều node, tôi ưu tiên drain/remove node đó khỏi traffic thay vì recycle toàn bộ farm. Nếu toàn bộ nodes cùng lỗi sau release, rollback release là lựa chọn mạnh nếu có bằng chứng temporal correlation và rollback an toàn. Tôi tránh cứ restart IIS định kỳ vì hành động đó xóa trạng thái quan sát được và có thể che leak/crash pattern.

Sau đó tôi muốn xây timeline chung gồm:

- request 5xx rate;
- server/node;
- worker process ID;
- process start timestamp;
- memory/CPU/thread count;
- application startup/shutdown log;
- IIS/Windows process or recycle events;
- deployment timestamps;
- configuration/file changes;
- background job executions.

Mục tiêu là chứng minh 5xx có trùng với process restart/recycle không. Nếu có, tiếp tục xác định trigger. Tôi không gọi mọi restart là “IIS recycle do memory”. Có thể là deployment chạm file/config, application crash, external process termination, configured recycle policy, health/failure condition hoặc host action. Root cause phải dựa trên event/log/configuration evidence.

Nếu working set tăng dần, tôi tách các khả năng:

- managed heap tăng do object retention;
- LOH pressure;
- native/unmanaged allocation;
- streams/handles/sockets không dispose;
- unbounded caches;
- queue/background buffer tăng;
- traffic pattern hợp lệ khiến process giữ memory nhưng GC vẫn quản lý bình thường.

Tôi muốn thu runtime counters, heap/dump khi phù hợp và so sánh snapshots trước/sau tăng trưởng. Nếu chỉ tăng memory limit mà leak thật sự tồn tại, ta chỉ kéo dài thời gian tới failure.

Login issue cũng cần tách. Nếu authentication hoàn toàn token/cookie stateless và key material ổn định, process restart không nhất thiết buộc user login lại. Nhưng nếu session/auth state nằm in-memory, key/config thay đổi, hoặc application startup làm invalid state thì restart có thể biểu hiện thành login issue. Tôi sẽ trace authentication failure cụ thể thay vì suy ra.

Scheduled reconciliation job là correctness risk riêng. Nếu “on startup” luôn trigger và deployment/recycle làm nhiều process khởi động, job có thể chạy lại. Nếu có nhiều servers, mỗi process thậm chí có thể chạy cùng lúc. Tôi sẽ thiết kế job theo logical work identity và idempotency; nếu yêu cầu single active executor thì dùng một coordination mechanism phù hợp hoặc đưa scheduling sang một worker/job platform có semantics rõ hơn. Nhưng ngay cả có lock, side effects quan trọng vẫn nên idempotent vì process có thể chết sau side effect nhưng trước khi ghi trạng thái hoàn tất.

Deployment copy file trực tiếp vào live directory cũng cần review. Tôi muốn artifact immutable/consistent, có health validation, traffic drain hoặc slot/node rotation tùy hạ tầng, và rollback rõ ràng. Mục tiêu là tránh serving traffic trong trạng thái binaries/config đang được thay từng phần.

Long-term prevention:

- structured log thêm host/node/process ID/start time/version;
- dashboard restart/recycle/crash rate;
- alerts cho 5xx + restart correlation;
- memory trend và resource counters;
- health/readiness endpoint phản ánh dependency/startup cần thiết nhưng không tự gây restart storm;
- graceful shutdown cho request/background processing;
- deployment runbook;
- restart/recycle chaos test;
- job idempotency tests.

Nếu root cause cuối cùng thật sự là memory leak trong một release, short-term có thể rollback và process recycle chỉ là mitigation có kiểm soát trong lúc fix. Long-term phải sửa retention/resource lifecycle, không coi recycle là architecture mechanism.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng tăng memory limit hay restart IIS. Tôi muốn correlate 502/503 với node, worker PID, process start time, Windows/IIS events và deployment timestamp để biết process thực sự recycle/crash vì gì. Nếu một node đang gây impact, tôi drain node đó; nếu release mới gây lỗi toàn hệ thống và rollback an toàn, tôi ưu tiên rollback.

Memory tăng chưa đủ để kết luận managed memory leak. Tôi sẽ lấy runtime counters/dump khi phù hợp và tách managed heap, native resource, unbounded cache, handles/sockets và workload pattern. Đồng thời kiểm tra deployment copy-in-place hoặc configuration/file change có kích hoạt restart không.

Tôi cũng coi background job là correctness issue: restart là bình thường trong production, nên job phải retry-safe/idempotent và nếu cần single executor thì có coordination rõ ràng. Session/auth cũng không nên phụ thuộc vô tình vào process memory. Sau incident tôi sẽ thêm process lifecycle telemetry, safe deployment, restart testing và alert correlation để lần sau biết chính xác nguyên nhân thay vì dùng restart như fix.”

## Câu hỏi đào sâu

1. Nếu memory dump cho thấy managed heap ổn nhưng process working set vẫn tăng, bạn sẽ điều tra hướng nào tiếp theo?
2. Nếu business không cho phép chuyển scheduled job sang dịch vụ riêng, bạn làm gì để job chạy an toàn khi IIS recycle hoặc có nhiều web nodes?
3. Nếu tăng memory limit thực sự giảm incident trong ngắn hạn, tại sao bạn vẫn có thể phản đối coi đó là fix chính thức?

## Lỗi trả lời thường gặp

- Gọi mọi restart là IIS recycle do memory mà không xem event evidence.
- Restart toàn bộ servers ngay lập tức rồi mất dữ liệu phục vụ diagnosis.
- Cho rằng background job “chỉ chạy một lần” vì code chỉ đăng ký một HostedService.
- Chỉ nhìn managed GC mà bỏ native resources/handles/sockets.
- Không xem deployment mechanism như một nguồn gây application restart/regression.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/tăng memory limit.
- **3–4:** Biết xem logs/memory nhưng không có incident structure hoặc competing hypotheses.
- **5–6:** Correlate process lifecycle, biết rollback/stabilize, nhận ra job/session risk.
- **7–8:** Điều tra có bằng chứng, phân tích managed/native resources, safe deployment và idempotency.
- **9–10:** Kết nối availability, lifecycle correctness, release engineering, observability và failure testing thành chiến lược production hoàn chỉnh.

# Câu 3 — Thiết kế CMS-backed marketing platform: Optimizely CMS, Akamai, product data và chiến lược modernization

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, content modeling, ASP.NET Core, Akamai/CDN, API integration, caching, security, SEO, deployment, observability, architecture trade-offs

## Bối cảnh

Một doanh nghiệp có nhiều marketing websites cho các thị trường khác nhau. Team muốn chuẩn hóa nền tảng mới dựa trên ASP.NET Core và Optimizely CMS.

Yêu cầu sơ bộ:

- editors quản lý landing pages, campaign pages và reusable content blocks;
- website hiển thị product information lấy từ một product platform bên ngoài;
- review/rating đến từ third-party API;
- một số pages có traffic spike lớn khi chạy campaign;
- Akamai được dùng làm CDN/edge cache;
- SEO, accessibility và Core Web performance là yêu cầu quan trọng;
- publishing content phải xuất hiện nhanh nhưng không nhất thiết mọi request đều bypass cache;
- product price/availability thay đổi thường xuyên hơn editorial content;
- website có nhiều locale;
- cần preview/draft cho editors;
- third-party dependencies đôi khi chậm hoặc unavailable;
- team đang tranh luận giữa:
  1. để CMS page/block code gọi trực tiếp mọi external API khi render;
  2. tạo một integration/application layer riêng;
  3. tách thành nhiều microservices ngay từ đầu;
- hệ thống cũ dùng jQuery và server-rendered pages; một số interactive areas dự kiến migrate dần sang React/Vue.

Chưa có con số chắc chắn về peak RPS, số editors, số products mỗi page hoặc freshness SLA cho từng loại dữ liệu.

## Câu hỏi chính

Hãy đề xuất kiến trúc cho nền tảng này. Bạn cần giải thích content model, CMS/runtime boundaries, external integration strategy, caching/CDN behavior, freshness, failure handling, frontend modernization, security, SEO/accessibility, deployment và observability. Đồng thời nêu rõ vì sao bạn chọn mức độ kiến trúc đó thay vì mặc định microservices hoặc mặc định “mọi thứ nằm trong CMS”.

## Câu hỏi làm rõ nên cân nhắc

1. Editorial content, price, availability và review có freshness/SLA khác nhau như thế nào?
2. Editors cần preview external product data thật hay chấp nhận mocked/snapshot data khi dependency down?
3. Campaign traffic peak, geographic distribution và cacheability của từng page/component là gì?
4. Product platform có rate limit, bulk API, webhook/event feed hay contract nào hỗ trợ synchronization không?
5. Các thị trường dùng cùng page structure/content blocks hay có nhiều variation/local compliance requirements?

## Gợi ý tư duy

### Gợi ý 1

Tách content ownership khỏi product/transactional ownership. CMS không nên trở thành source of truth cho dữ liệu mà hệ thống khác sở hữu.

### Gợi ý 2

Cache strategy phải theo data class. Editorial content, price, availability và review không nhất thiết dùng cùng TTL/invalidation policy.

### Gợi ý 3

Thiết kế failure behavior trước: external API chậm, CDN stale content, publish invalidation thất bại, partial page data thiếu, và deployment rollback.

## Cấu trúc trả lời đề xuất

1. Làm rõ business, scale, freshness và editorial workflow.
2. Xác định bounded ownership của CMS và external systems.
3. Thiết kế content types/blocks và reference model.
4. Thiết kế integration layer/read models.
5. Phân lớp cache: request/application/distributed/CDN khi thực sự cần.
6. Định nghĩa invalidation/freshness theo data category.
7. Thiết kế dependency failure/fallback.
8. Thiết kế frontend modernization và rendering strategy.
9. Security, SEO, accessibility và data governance.
10. Deployment, observability, test và recovery.
11. So sánh modular architecture với microservices.

## Ý chính của câu trả lời tốt

### Bắt buộc

- CMS sở hữu editorial structure/content; external product platform vẫn là authority cho product data.
- Không gọi N external APIs tùy tiện trong page rendering path.
- Có timeout, cancellation, fallback và rate-limit awareness cho external integrations.
- Cache strategy theo freshness requirement, không một TTL cho mọi thứ.
- Akamai invalidation/purge phải có strategy chứ không “cache forever”.
- Preview/editorial workflow được thiết kế riêng khỏi public delivery.
- Không mặc định microservices nếu scale/team boundaries chưa chứng minh nhu cầu.
- Có SEO, accessibility, performance và observability trong kiến trúc ngay từ đầu.

### Điểm cộng

- Dùng stable product identifiers trong CMS thay vì copy toàn bộ product data vào content blocks.
- Có bulk/prefetch/read-model strategy để tránh waterfall/N+1 API calls khi page chứa nhiều products.
- Stale-while-error hoặc last-known-good cho loại dữ liệu phù hợp, nhưng không dùng stale data cho thao tác cần transactional correctness.
- Phân biệt cache key theo locale, content version, personalization/authentication khi có.

### Senior+

- Nêu contract cho publish → edge invalidation và behavior nếu purge thất bại.
- Thiết kế observability theo page render decomposition: CMS lookup, product integration, review API, cache status, CDN.
- Đưa ra migration incrementally từ server-rendered/jQuery sang islands/components React/Vue mà không rewrite toàn bộ.
- Có tiêu chí cụ thể khi nào mới tách integration thành service độc lập.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu từ ownership. Optimizely CMS nên sở hữu editorial content: page hierarchy, localized copy, campaign composition, SEO metadata, reusable blocks và references tới business entities. Product platform vẫn là source of truth cho product fields như identifier, price và availability nếu đó là nơi business quản lý chúng.

Trong CMS, tôi ưu tiên content model theo intent của editor thay vì map 1:1 UI implementation. Ví dụ `CampaignPage`, `HeroBlock`, `ProductCollectionBlock`, `RichText/ContentBlock`, `CTA`, `SEO metadata`. `ProductCollectionBlock` nên lưu product IDs hoặc query/reference criteria ổn định, không duplicate toàn bộ product object. Như vậy editor compose page nhưng lifecycle product data không bị trộn vào CMS publish lifecycle.

Tôi không để từng block tự gọi external APIs theo cách ad-hoc. Với một page có 20 products, cách đó dễ thành N+1 outbound calls, tăng latency và làm page availability phụ thuộc trực tiếp nhiều downstreams. Tôi tạo integration/application boundary: một typed client/gateway cho product platform, một client cho reviews, contract DTO rõ ràng, timeout/cancellation, resilience policy có điều kiện và telemetry. Nếu provider có bulk API, tôi ưu tiên batch theo page needs. Nếu traffic/freshness phù hợp, có thể xây read model/cache được cập nhật asynchronously thay vì gọi dependency trên mọi page request.

Cache cần chia lớp và chia data category.

- Editorial HTML/content thường cache được lâu hơn, invalidation gắn với publish.
- Product descriptive fields có thể TTL khác.
- Price/availability thường freshness nhạy hơn.
- Reviews có thể chấp nhận stale lâu hơn tùy business.

Akamai là edge layer tốt cho campaign traffic nếu response cacheable. Nhưng cache key phải phản ánh locale và những dimensions thực sự ảnh hưởng representation. Nếu có personalized/authenticated content, không được vô tình cache response riêng tư thành public response.

Khi editor publish, tôi muốn một invalidation contract: xác định URL/surrogate grouping cần purge hoặc revalidate. Nếu purge thất bại, hệ thống phải retry và quan sát được; không nên trả `publish succeeded` nhưng hoàn toàn không biết edge đang stale bao lâu. Tuy nhiên cách cụ thể phụ thuộc Akamai configuration/API contract hiện tại; tôi sẽ xác minh implementation trước khi chọn kỹ thuật purge.

Với price/availability, nếu public product cards chấp nhận trễ vài chục giây thì cache có thể giúp bảo vệ backend. Nhưng nếu user bắt đầu transaction như add-to-cart/checkout, transactional service phải revalidate dữ liệu quan trọng; CDN/search/CMS không nên là authority cho business commit.

Failure handling phải được xác định trước:

- product API timeout: dùng last-known-good nếu business cho phép, hoặc render component degraded thay vì làm cả page 500;
- review API down: có thể ẩn rating hoặc dùng cached rating;
- CMS unavailable: edge cache có thể tiếp tục phục vụ cacheable pages trong một số tình huống, nhưng phải hiểu expiration behavior;
- purge thất bại: retry + alert + manual recovery path;
- malformed external payload: validate contract, log safe metadata, không để một product làm crash toàn page.

Frontend modernization không nhất thiết rewrite. Tôi giữ server rendering cho content/SEO-critical shell nếu nó phù hợp, sau đó migrate interactive zones từ jQuery thành React/Vue components theo từng area. API contracts của interactive components phải độc lập khỏi internal CMS model. Điều này giảm coupling và cho phép incremental migration.

SEO/performance/accessibility:

- semantic HTML và metadata từ content model;
- canonical/hreflang/localization strategy theo requirement;
- image sizing/optimization và lazy loading hợp lý;
- tránh render-blocking JavaScript không cần thiết;
- accessibility semantics/focus/keyboard testing;
- Lighthouse chỉ là một signal, phải kết hợp real-user/performance telemetry khi có;
- Playwright E2E cho critical journeys và visual/content contract ở mức phù hợp.

Security:

- secrets của external APIs không nằm trong CMS content;
- dùng secure configuration/Key Vault và Managed Identity nơi contract hỗ trợ;
- encode/sanitize output đúng context;
- authorization cho editorial/admin operations;
- không log tokens/PII;
- validate external URLs/files/content theo threat model.

Về kiến trúc, tôi sẽ bắt đầu với modular boundaries trong một deployable application nếu team/scale chưa cần independent deployment. Có modules như CMS presentation, Product Integration, Reviews Integration, Cache/Delivery. Chỉ tách service khi có lý do rõ: ownership/team độc lập, scale khác biệt lớn, reliability isolation, reuse cross-channels hoặc deployment cadence riêng. Microservices ngay từ đầu sẽ thêm network failure, observability, deployment và data-consistency cost mà chưa chắc tạo giá trị.

Observability nên cho phép nhìn một page request và biết:

- edge cache hit/miss nếu telemetry có sẵn;
- origin render duration;
- CMS content lookup duration;
- product/review dependency latency/error;
- cache hit ratio/freshness;
- timeout/fallback count;
- publish-to-edge-freshness lag;
- response status và page/version correlation.

Testing gồm unit cho mapping/policy, integration cho CMS/integration contracts, contract tests với third-party mocks/sandbox khi có, cache invalidation tests, load test campaign path, dependency failure injection, accessibility checks và Playwright E2E cho publish/render/critical interaction. Deployment cần versioned artifact, configuration validation, health checks, staged rollout và rollback.

Nếu sau khi đo traffic thấy origin gần như không tải vì Akamai hit ratio cao và integration data được cập nhật asynchronously, một modular monolith có thể là đủ. Nếu product aggregation trở thành shared platform phục vụ nhiều web/mobile channels với scale và ownership riêng, lúc đó tách nó thành service có thể có lý do mạnh hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi tách ownership trước: Optimizely CMS quản lý editorial composition và localized content; product platform vẫn là source of truth cho price/availability. Trong CMS, block chỉ giữ stable product references, không copy toàn bộ product data.

Tôi không cho từng block gọi external API tùy tiện. Tôi tạo integration layer với typed clients, timeout/cancellation, bulk fetching hoặc read model/cache để tránh N+1. Cache cũng theo loại dữ liệu: editorial content có thể edge-cache dài hơn và purge khi publish, còn price/availability có freshness policy ngắn hơn và phải revalidate ở transactional boundary.

Akamai cần cache-key/invalidation rõ và purge failure phải observable/retryable. External dependency down không nhất thiết làm cả page 500; với data phù hợp có thể dùng last-known-good hoặc degraded component. Tôi giữ server-rendered SEO-critical shell và migrate jQuery sang React/Vue theo từng interactive area thay vì rewrite.

Tôi chưa chọn microservices ngay vì chưa có bằng chứng về independent scale/ownership/deployment. Tôi bắt đầu modular, đo traffic/failure, rồi tách khi boundary tạo giá trị rõ. Cuối cùng tôi theo dõi publish-to-edge freshness, dependency latency, cache hit, origin render và test load, failure, accessibility, SEO-critical rendering và rollback.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu editor bấm Publish và nội dung mới phải xuất hiện toàn cầu rất nhanh, nhưng Akamai purge đôi khi thất bại, bạn thiết kế user feedback và recovery như thế nào?
2. Nếu một page có 100 product cards và product platform chỉ cho 20 requests/second, kiến trúc của bạn thay đổi ra sao?
3. Một Tech Lead phản biện rằng microservices sẽ “future-proof” hệ thống và cho scale độc lập; bạn sẽ dùng tiêu chí nào để chứng minh nên hoặc chưa nên tách?

## Lỗi trả lời thường gặp

- Nhét toàn bộ product data vào CMS để “editor dễ quản lý”, làm sai ownership và freshness.
- Mỗi content block tự gọi API dẫn tới waterfall/N+1 và dependency amplification.
- Dùng một TTL/cache policy cho mọi dữ liệu.
- Nói “dùng CDN là nhanh” nhưng không giải thích invalidation, cache key và private/personalized content.
- Chọn microservices hoặc SPA rewrite vì xu hướng thay vì requirement.

## Thang điểm 0–10

- **0–2:** Chỉ liệt kê CMS + CDN + Redis/microservices mà không có ownership/failure model.
- **3–4:** Có content model và cache nhưng integration/freshness/failure còn mơ hồ.
- **5–6:** Kiến trúc hợp lý, có modular boundary, CDN/integration, SEO/security/testing.
- **7–8:** Phân loại freshness, purge recovery, N+1 prevention, incremental frontend modernization và observability tốt.
- **9–10:** Thiết kế cân bằng business/editor workflow, reliability, performance, consistency và operational cost; nêu rõ điều kiện khiến recommendation thay đổi.
