# Code Review Challenge 1 — Upload file lớn qua ASP.NET Core làm memory tăng vọt và bỏ qua security boundary của Blob Storage

**Chủ đề:** C#/.NET 8, ASP.NET Core, file upload, streaming, Azure Blob Storage, Managed Identity, SAS, validation, memory pressure, cancellation, security, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một ASP.NET Core API chạy trên Azure App Service cung cấp chức năng upload tài liệu cho internal document portal. File cuối cùng được lưu vào Azure Blob Storage.

Business requirements:

- user chỉ được upload file vào container tương ứng với tenant của mình;
- file tối đa 500 MB;
- chấp nhận PDF, DOCX, XLSX và ảnh;
- không được tin hoàn toàn vào `Content-Type` hoặc extension do client gửi;
- upload phải hỗ trợ cancellation khi client disconnect;
- API không được buffer toàn bộ file lớn trong memory;
- Blob Storage account không public;
- production sử dụng Managed Identity;
- một số flow tương lai có thể cho browser upload trực tiếp bằng short-lived SAS, nhưng hiện tại endpoint backend vẫn là flow chính;
- upload thất bại giữa chừng không được để database record ở trạng thái "Completed";
- logs không được ghi raw file content hoặc secret/SAS token.

Production hiện có các triệu chứng:

- memory của App Service tăng mạnh khi vài user upload file 200–500 MB cùng lúc;
- có lúc worker process restart do memory pressure;
- request bị client cancel nhưng backend vẫn tiếp tục đọc/upload file;
- một file `.exe` đổi tên thành `.pdf` đã lọt qua validation extension;
- developer đang dùng Storage Account connection string trong configuration;
- code tạo blob name trực tiếp từ `FileName` client gửi;
- database đôi khi ghi `Uploaded` dù Blob upload thực tế fail ở cuối request;
- team muốn "fix nhanh" bằng cách tăng App Service memory tier mà chưa phân tích data path.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [Authorize]
    [HttpPost("upload")]
    [RequestSizeLimit(600_000_000)]
    public async Task<IActionResult> Upload(
        [FromForm] IFormFile file,
        [FromForm] string tenantId)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        var extension = Path.GetExtension(file.FileName);
        var allowed = new[] { ".pdf", ".docx", ".xlsx", ".jpg", ".png" };

        if (!allowed.Contains(extension, StringComparer.OrdinalIgnoreCase))
            return BadRequest("Unsupported file type");

        await using var input = file.OpenReadStream();

        using var memory = new MemoryStream();
        await input.CopyToAsync(memory);

        var blobName = $"{tenantId}/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);

        var document = new Document
        {
            Id = Guid.NewGuid(),
            TenantId = tenantId,
            OriginalFileName = file.FileName,
            BlobName = blobName,
            Status = "Uploaded",
            CreatedAt = DateTimeOffset.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync();

        memory.Position = 0;
        await blob.UploadAsync(memory, overwrite: true);

        _logger.LogInformation(
            "Uploaded {FileName} for tenant {TenantId} to {BlobUri}",
            file.FileName,
            tenantId,
            blob.Uri);

        return Ok(new
        {
            document.Id,
            document.Status,
            blob.Uri
        });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, security, memory, tenant isolation, storage identity và failure handling.
2. Giải thích vì sao `IFormFile` + `MemoryStream` hiện tại có thể gây memory pressure rất lớn khi upload concurrent file lớn.
3. Chỉ ra vì sao extension check không đủ để xác minh loại file.
4. Phân tích rủi ro của việc lấy `tenantId` trực tiếp từ form data.
5. Review cách tạo `blobName` từ `file.FileName` và các vấn đề collision/path/logging liên quan.
6. Đánh giá việc ghi database `Status = "Uploaded"` trước khi Blob upload thực sự thành công.
7. Đề xuất state machine đơn giản cho upload để xử lý partial failure.
8. Đề xuất cách dùng Managed Identity thay connection string khi App Service truy cập Blob Storage.
9. Đề xuất streaming flow không buffer toàn file và có cancellation propagation.
10. Nêu cách kiểm thử load, failure path, malicious file metadata và tenant isolation.
11. Nêu telemetry để phân biệt bottleneck ở request body, application memory, outbound Blob upload và storage dependency.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### Critical — Buffer toàn bộ file vào `MemoryStream`

**Vấn đề:** File được copy hoàn toàn từ `IFormFile` stream sang `MemoryStream` trước khi upload Blob.

**Tại sao xảy ra:** Code biến một workload có thể stream thành workload giữ một bản sao đầy đủ trong managed memory.

**Ảnh hưởng production:** Với file hàng trăm MB và nhiều request concurrent, memory tăng cực nhanh, GC pressure lớn, process có thể restart hoặc request khác bị ảnh hưởng. Tăng App Service tier chỉ che symptom nếu data path vẫn nhân memory theo concurrency.

**Cách sửa:** Stream trực tiếp từ request/file stream sang Blob Storage khi flow backend proxy là requirement. Không copy toàn file sang `MemoryStream`. Với upload rất lớn hoặc cần scale tốt hơn, cân nhắc direct-to-Blob bằng short-lived scoped SAS sau khi authorization phù hợp.

### Critical — `tenantId` do client gửi được dùng làm security boundary

**Vấn đề:** Blob path và database record lấy tenant từ `[FromForm] string tenantId`.

**Tại sao xảy ra:** Client-controlled input được coi là trusted tenant context.

**Ảnh hưởng production:** User tenant A có thể thử upload vào namespace tenant B nếu backend không có check khác.

**Cách sửa:** Derive tenant từ authenticated principal/application identity mapping. Nếu privileged support/system flow cần target tenant khác, dùng explicit authorization policy và audit riêng.

### Critical — Database ghi `Uploaded` trước khi storage operation hoàn tất

**Vấn đề:** Metadata được persist ở trạng thái success trước khi `blob.UploadAsync` chạy.

**Tại sao xảy ra:** Local transaction boundary không bao phủ external storage dependency nhưng state model lại giả định atomicity.

**Ảnh hưởng production:** Blob upload fail thì database vẫn nói tài liệu đã upload. UI/search/downstream có thể tham chiếu blob không tồn tại.

**Cách sửa:** Dùng state transitions như `PendingUpload → Uploaded` hoặc `Failed`. Tạo metadata pending trước nếu cần audit/id; chỉ chuyển `Uploaded` sau khi Blob upload success. Nếu DB update cuối fail sau Blob success, cần reconciliation/cleanup strategy thay vì giả định distributed transaction.

### High — Validation chỉ dựa trên extension client-controlled

**Vấn đề:** `Path.GetExtension(file.FileName)` không chứng minh nội dung thật của file.

**Tại sao xảy ra:** Filename metadata do client kiểm soát.

**Ảnh hưởng production:** File executable hoặc payload không mong muốn có thể đổi extension để vượt check. Nếu file sau này được serve/download/scan/parse, risk tăng.

**Cách sửa:** Kết hợp allow-list extension, content-type sanity check, magic-signature/file-format validation khi phù hợp, malware scanning theo risk model và không thực thi uploaded content. Không có một check metadata đơn lẻ nào đủ cho untrusted file.

### High — Không propagate cancellation

**Vấn đề:** Method không nhận `CancellationToken`; `CopyToAsync` và `UploadAsync` không dùng `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Request lifecycle bị tách khỏi I/O lifecycle.

**Ảnh hưởng production:** Client disconnect nhưng backend vẫn tiêu bandwidth, memory, CPU và storage requests cho work không còn hữu ích.

**Cách sửa:** Nhận `CancellationToken` action parameter hoặc dùng `RequestAborted`, truyền xuyên suốt database/storage operations. Cancellation không thay thế cleanup/reconciliation vì process có thể chết đột ngột.

### High — Storage credential dùng connection string thay vì Managed Identity

**Vấn đề:** Application giữ account credential/connection string trong configuration dù production đã có Managed Identity.

**Tại sao xảy ra:** Authentication model cũ được giữ nguyên khi migrate lên Azure.

**Ảnh hưởng production:** Secret rotation/handling phức tạp hơn, blast radius lớn nếu config leak, khó áp dụng least privilege.

**Cách sửa:** Dùng `DefaultAzureCredential`/Managed Identity với Blob service endpoint và cấp RBAC tối thiểu phù hợp, ví dụ quyền data-plane cần thiết trên đúng account/container.

### High — Blob name lấy trực tiếp từ raw filename

**Vấn đề:** `file.FileName` được dùng làm storage key và log value.

**Tại sao xảy ra:** Client filename bị trộn với internal storage identity.

**Ảnh hưởng production:** Collision/overwrite, tên khó kiểm soát, encoding/path semantics phức tạp, có thể leak PII trong object name/logs. `overwrite: true` làm collision nguy hiểm hơn.

**Cách sửa:** Sinh internal blob id độc lập, ví dụ `{tenant}/{documentId}` hoặc random GUID; lưu original filename chỉ như metadata đã sanitize/normalize cho display.

### High — `overwrite: true` có thể phá correctness khi blob name collision

**Vấn đề:** Hai upload cùng `tenantId/fileName` có thể overwrite nhau.

**Tại sao xảy ra:** Business identity của document bị gắn vào mutable filename.

**Ảnh hưởng production:** User upload file mới có thể vô tình thay nội dung của record cũ hoặc race với request khác.

**Cách sửa:** Dùng immutable blob key theo document id/version; chỉ overwrite khi business semantics yêu cầu explicit replace và có concurrency/version check.

### Medium — `RequestSizeLimit` không đủ để bảo vệ memory/concurrency

**Vấn đề:** Limit 600 MB chỉ chặn request vượt ngưỡng, không giới hạn tổng memory hoặc số upload đồng thời.

**Tại sao xảy ra:** Per-request size control bị nhầm với capacity control.

**Ảnh hưởng production:** Nhiều request hợp lệ dưới limit vẫn có thể làm process quá tải.

**Cách sửa:** Streaming + concurrency/load protection + App Service/request-server limits phù hợp. Đo throughput trước khi chọn limit/parallelism.

### Medium — Response trả `blob.Uri` dù storage private

**Vấn đề:** URI được expose như thể client có thể dùng trực tiếp.

**Tại sao xảy ra:** Resource address và access authorization bị trộn lẫn.

**Ảnh hưởng production:** Có thể gây hiểu nhầm API contract; team sau này dễ bật public access hoặc phát SAS quá rộng để "cho link chạy".

**Cách sửa:** Trả document id/business endpoint. Khi cần download, backend authorize rồi stream/proxy hoặc issue short-lived scoped SAS theo threat model.

### Medium — Logging raw filename/URI chưa có privacy model rõ ràng

**Vấn đề:** Filename có thể chứa PII/business-sensitive data.

**Tại sao xảy ra:** Diagnostic log dùng trực tiếp user-controlled metadata.

**Ảnh hưởng production:** Sensitive identifiers bị copy vào log retention system.

**Cách sửa:** Log document id, tenant id, content length, normalized extension/type, operation id, storage status; chỉ log filename khi policy cho phép và đã sanitize.

### Medium — Không có cleanup/reconciliation cho orphan Blob hoặc orphan metadata

**Vấn đề:** DB và Blob Storage là hai systems với independent failure.

**Tại sao xảy ra:** Code không model partial success.

**Ảnh hưởng production:** Có thể có row không có blob hoặc blob không có row.

**Cách sửa:** Thiết kế reconciliation job/cleanup TTL hoặc deterministic state machine. Đừng cố mô phỏng distributed transaction nếu complexity không đáng.

## Phiên bản đề xuất

Một hướng đơn giản cho backend-proxy upload là giữ metadata state rõ ràng, derive tenant từ identity và stream thẳng sang Blob.

```csharp
public sealed class DocumentUploadService
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ICurrentUser _currentUser;

    public DocumentUploadService(
        BlobContainerClient container,
        AppDbContext db,
        ICurrentUser currentUser)
    {
        _container = container;
        _db = db;
        _currentUser = currentUser;
    }

    public async Task<Guid> UploadAsync(
        IFormFile file,
        CancellationToken cancellationToken)
    {
        if (file.Length <= 0 || file.Length > 500_000_000)
            throw new ValidationException("Invalid file size.");

        var documentId = Guid.NewGuid();
        var tenantId = _currentUser.TenantId;
        var extension = Path.GetExtension(file.FileName).ToLowerInvariant();

        ValidateAllowedExtension(extension);

        var blobName = $"{tenantId}/{documentId:N}";

        var entity = new Document
        {
            Id = documentId,
            TenantId = tenantId,
            OriginalFileName = Path.GetFileName(file.FileName),
            BlobName = blobName,
            Status = DocumentStatus.PendingUpload,
            CreatedAt = DateTimeOffset.UtcNow
        };

        _db.Documents.Add(entity);
        await _db.SaveChangesAsync(cancellationToken);

        try
        {
            await using var stream = file.OpenReadStream();

            await ValidateFileSignatureAsync(
                stream,
                extension,
                cancellationToken);

            stream.Position = 0;

            var blob = _container.GetBlobClient(blobName);

            await blob.UploadAsync(
                stream,
                overwrite: false,
                cancellationToken);

            entity.Status = DocumentStatus.Uploaded;
            entity.UploadedAt = DateTimeOffset.UtcNow;
            entity.SizeBytes = file.Length;

            await _db.SaveChangesAsync(cancellationToken);

            return documentId;
        }
        catch
        {
            entity.Status = DocumentStatus.Failed;

            try
            {
                await _db.SaveChangesAsync(CancellationToken.None);
            }
            catch
            {
                // production code: emit telemetry for reconciliation
            }

            throw;
        }
    }
}
```

Đây là một design direction, không phải API contract duy nhất. Nếu file upload rất lớn hoặc traffic cao, browser-to-Blob upload bằng short-lived SAS có thể loại backend khỏi data path. Khi đó backend vẫn phải authorize tenant, tạo scoped upload intent, giới hạn blob path/permissions/expiry, validate completion và không log SAS token.

`ValidateFileSignatureAsync` cần implement theo từng format thực tế. Một số format như DOCX/XLSX là ZIP-based nên validation không chỉ là vài bytes đầu. Nếu threat model yêu cầu malware scanning, cần asynchronous scanning/quarantine state thay vì coi extension/signature check là antivirus.

## Giải thích thiết kế sau khi sửa

Internal `documentId` là storage identity; client filename chỉ là metadata. Tenant đến từ trusted identity context.

Metadata được tạo ở trạng thái `PendingUpload`, sau đó chỉ chuyển `Uploaded` khi storage operation thành công. Điều này thừa nhận DB và Blob Storage không có transaction chung.

Data path không còn copy toàn file vào `MemoryStream`. Cancellation đi cùng request để dừng I/O khi client không còn chờ.

Managed Identity giảm secret management và cho phép least-privilege RBAC thay vì account-level connection string.

## Trade-offs

Backend streaming đơn giản cho authorization và scanning flow nhưng App Service vẫn chịu bandwidth/connection duration. Direct-to-Blob SAS giảm backend load nhưng làm flow nhiều bước hơn và cần completion validation.

Signature validation sâu có CPU/I/O cost. Malware scanning thường cần quarantine + asynchronous workflow. Mức bảo vệ phải dựa trên threat model và cách file được sử dụng sau upload.

State machine `Pending/Uploaded/Failed` thêm logic và reconciliation, nhưng đổi lại correctness khi external storage fail rõ ràng hơn.

Nếu business muốn replace file hiện có, immutable blob key có thể tạo nhiều versions và tăng storage; lifecycle policy/cleanup có thể xử lý.

## Cách kiểm thử

1. **Load test:** 20–50 concurrent uploads với file representative 100–500 MB; theo dõi working set, GC, request latency và storage throughput.
2. **Cancellation test:** client disconnect giữa upload; xác minh request/storage work dừng hợp lý và metadata không thành `Uploaded`.
3. **Security test:** user tenant A thử gửi `tenantId` giả hoặc filename crafted; xác minh storage path luôn dùng tenant từ identity và internal blob id.
4. **File-validation test:** đổi extension của executable/invalid payload thành `.pdf`; xác minh bị reject/quarantine theo policy.
5. **Failure-path integration test:** mô phỏng Blob upload fail sau khi metadata đã tạo; xác minh state là `Failed/Pending`, không phải `Uploaded`.

## Quan sát trong production

Theo dõi:

- upload size distribution;
- concurrent active uploads;
- request duration p50/p95/p99;
- process memory/working set;
- GC collections/allocations nếu có telemetry phù hợp;
- request aborted/cancelled count;
- Blob dependency latency/error/status;
- bytes uploaded/sec;
- `PendingUpload` age và count;
- failed upload count theo reason;
- orphan/reconciliation count;
- auth failures/cross-tenant attempts;
- correlation từ request → document id → blob operation → metadata transition.

Alert khi memory tăng theo upload concurrency bất thường, `PendingUpload` tồn tại quá lâu, Blob error rate tăng hoặc process restart trùng với upload bursts.

## Câu hỏi phỏng vấn mở rộng

1. Nếu browser upload trực tiếp bằng SAS, bạn thiết kế upload intent và completion validation thế nào để user không thể ghi blob ngoài tenant path?
2. Nếu malware scanning mất 1–2 phút, bạn thay đổi document state machine và download authorization thế nào?
3. Khi nào backend proxy upload vẫn tốt hơn direct-to-Blob dù tốn App Service bandwidth?

# Code Review Challenge 2 — Kubernetes deployment "healthy" nhưng rollout vẫn nhận traffic quá sớm và gây 5xx

**Chủ đề:** Kubernetes, Deployment, readiness/liveness probes, rolling update, resource requests/limits, graceful termination, ASP.NET Core health checks, configuration, release safety, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API trước đây chạy trên Azure App Service, nay một team đang đánh giá Kubernetes cho một environment mới. API phụ thuộc SQL Server và một external pricing API.

Mỗi pod mất khoảng 20–40 giây để warm application caches và hoàn tất startup initialization. Khi shutdown, pod cần tối đa khoảng 15 giây để ngừng nhận request mới và hoàn tất in-flight requests quan trọng.

Sau một release, production-like environment gặp các triệu chứng:

- rollout có nhiều `502/503` trong 30–60 giây đầu;
- Kubernetes báo pod `Running` rất sớm nhưng API chưa thật sự sẵn sàng;
- khi SQL có transient latency, nhiều pods restart liên tục;
- pod bị OOMKilled ở giờ cao điểm dù node còn memory;
- deployment đôi lúc terminate old pod trước khi new pod thực sự phục vụ ổn định;
- `/health` hiện kiểm tra cả SQL và external pricing API;
- liveness/readiness dùng cùng endpoint;
- container shutdown đôi lúc bị kill trước khi request hoàn tất;
- config chứa một API key plaintext trong Deployment manifest;
- team đề xuất tăng `initialDelaySeconds` thật lớn cho cả readiness và liveness để "ổn định".

## Đoạn configuration cần review

```yaml
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 1
            failureThreshold: 2
```

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc SQL và external pricing API

**Vấn đề:** `/health` kiểm tra dependencies và được dùng cho liveness.

**Tại sao xảy ra:** Team dùng một endpoint cho hai semantics khác nhau.

**Ảnh hưởng production:** Khi SQL/external API degrade nhưng process vẫn hoạt động đúng, liveness fail làm Kubernetes restart pods. Nhiều pods restart đồng thời có thể làm outage nặng hơn và tạo cold-start/reconnect storm.

**Cách sửa:** Liveness chỉ nên trả lời process có bị stuck/broken cần restart hay không. Dependency reachability thường phù hợp hơn với readiness hoặc telemetry, tùy contract. Tách endpoint/tags như `/health/live` và `/health/ready`.

### Critical — Readiness bắt đầu quá sớm so với startup thực tế

**Vấn đề:** Application cần 20–40 giây warm-up nhưng readiness bắt đầu sau 2 giây.

**Tại sao xảy ra:** Probe config không phản ánh startup behavior.

**Ảnh hưởng production:** Nếu endpoint trả success trước khi critical initialization hoàn tất, Service có thể route traffic quá sớm; nếu endpoint fail liên tục, rollout chậm/unstable tùy thresholds.

**Cách sửa:** Readiness phải gắn với actual ability to serve requests. Có thể dùng startup probe hoặc readiness state tied to initialization. Không chỉ tăng một delay magic number mà không model startup state.

### High — Không có startup probe cho application khởi động chậm

**Vấn đề:** Liveness bắt đầu kiểm tra rất sớm trong khi startup có thể 40 giây.

**Tại sao xảy ra:** Startup và steady-state health bị coi là cùng một phase.

**Ảnh hưởng production:** Container khỏe nhưng đang khởi động có thể bị liveness kill/restart trước khi hoàn tất, tạo crash loop giả.

**Cách sửa:** Dùng `startupProbe` khi startup thực tế có thể dài/biến động. Sau khi startup probe thành công, liveness/readiness mới đảm nhiệm steady-state semantics.

### High — `terminationGracePeriodSeconds` ngắn hơn shutdown budget cần thiết

**Vấn đề:** Pod chỉ có 5 giây trong khi application cần tới 15 giây để drain in-flight requests.

**Tại sao xảy ra:** Kubernetes termination budget không khớp application behavior.

**Ảnh hưởng production:** Process có thể bị kill giữa request/transaction, gây 5xx hoặc partial work.

**Cách sửa:** Chọn grace period dựa trên measured shutdown/drain time. Application phải handle SIGTERM, ngừng nhận work mới, propagate cancellation và hoàn tất bounded in-flight work.

### High — Rolling update có thể giảm capacity trong lúc pod mới warm-up

**Vấn đề:** `maxSurge: 0` không tạo thêm pod tạm; `maxUnavailable: 1` cho phép mất một replica trong rollout.

**Tại sao xảy ra:** Strategy ưu tiên không vượt replica count hơn availability headroom.

**Ảnh hưởng production:** Với 3 replicas, capacity có thể giảm còn 2 trong khi new pod cần lâu mới ready; nếu traffic cao hoặc một pod khác degrade, error rate tăng.

**Cách sửa:** Đánh giá SLO/capacity và cân nhắc `maxSurge > 0`, `maxUnavailable: 0` hoặc giá trị phù hợp. Không có một cấu hình đúng cho mọi workload; phải dựa trên headroom và rollout requirements.

### High — Plaintext secret trong Deployment manifest

**Vấn đề:** `Pricing__ApiKey` được hard-code trực tiếp.

**Tại sao xảy ra:** Config và secret bị trộn.

**Ảnh hưởng production:** Secret xuất hiện trong repository/manifests/audit output và có thể bị đọc bởi người có quyền xem workload spec.

**Cách sửa:** Dùng Kubernetes Secret/secret provider phù hợp hoặc workload identity + external secret store nếu platform có. Áp dụng least privilege và rotation. Không log secret.

### High — `image: ...:latest` làm release không immutable

**Vấn đề:** Tag mutable không xác định chính xác artifact của release.

**Tại sao xảy ra:** Deployment reference không gắn với version/digest cố định.

**Ảnh hưởng production:** Rollback/redeploy không chắc chạy cùng binary đã test; debugging diff giữa pods khó hơn.

**Cách sửa:** Dùng immutable version tag và tốt hơn là image digest trong release metadata. Record commit/build/image digest để audit.

### High — Memory limit có thể gây OOMKilled

**Vấn đề:** Limit 256Mi có thể thấp hơn peak working set thực tế.

**Tại sao xảy ra:** Resource config không dựa trên profiling/load evidence.

**Ảnh hưởng production:** Container vượt memory limit có thể bị OOMKilled dù node còn tổng memory. Repeated restart làm latency/error tệ hơn.

**Cách sửa:** Đo working set/GC/allocation dưới representative load; đặt requests/limits có headroom phù hợp. Không "fix" bằng unlimited memory mà thiếu capacity model.

### Medium — Không có resource requests

**Vấn đề:** Chỉ đặt limits.

**Tại sao xảy ra:** Scheduler capacity reservation không được model rõ.

**Ảnh hưởng production:** Placement/QoS có thể không phản ánh nhu cầu steady-state, dễ contention khi node nhiều workloads.

**Cách sửa:** Set CPU/memory requests dựa trên typical measured usage và limits dựa trên safe upper bound. Theo dõi throttling/OOM.

### Medium — Timeout 1 giây có thể quá aggressive cho readiness dependency checks

**Vấn đề:** Readiness gọi dependency-sensitive health check với timeout rất thấp.

**Tại sao xảy ra:** Probe timeout được chọn mà chưa dựa trên normal health-check latency.

**Ảnh hưởng production:** Transient latency có thể làm pod bị remove khỏi Service dù application vẫn có thể phục vụ degraded traffic.

**Cách sửa:** Health check nên lightweight; readiness dependencies phải được chọn kỹ. Thresholds/timeouts cần dựa trên SLO và measured latency, tránh probe trở thành load amplifier.

### Medium — Health check external API có thể tự tạo dependency load

**Vấn đề:** Mỗi pod gọi pricing API định kỳ chỉ để probe.

**Tại sao xảy ra:** Readiness check được implement như synthetic business call quá thường xuyên.

**Ảnh hưởng production:** N pods × probe frequency có thể tăng dependency traffic và fail đồng thời khi provider chậm.

**Cách sửa:** Chỉ check dependency nếu readiness thật sự phải phụ thuộc nó; dùng lightweight/cached health state khi phù hợp. Có thể giữ pod ready và xử lý degraded dependency bằng application resilience nếu business cho phép.

### Medium — Không có explicit pre-stop/drain coordination

**Vấn đề:** Config chỉ dựa vào termination grace period.

**Tại sao xảy ra:** Traffic removal và application drain chưa được thiết kế cùng nhau.

**Ảnh hưởng production:** Một số requests có thể vẫn đến trong transition window tùy routing/endpoint propagation.

**Cách sửa:** Đảm bảo readiness chuyển false khi shutdown bắt đầu, application host nhận termination signal, Service ngừng route new traffic, và grace period đủ cho in-flight work. `preStop` có thể hữu ích trong một số setup nhưng không phải magic sleep bắt buộc.

## Phiên bản đề xuất

Một hướng cấu hình minh họa:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pricing-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: pricing-api
  template:
    metadata:
      labels:
        app: pricing-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: pricing-api
          image: registry.example.com/pricing-api@sha256:RELEASE_DIGEST
          ports:
            - containerPort: 8080
          env:
            - name: Pricing__ApiKey
              valueFrom:
                secretKeyRef:
                  name: pricing-api-secrets
                  key: pricing-api-key
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: pricing-api-secrets
                  key: main-db
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
```

ASP.NET Core có thể phân loại checks bằng tags:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: new[] { "live" })
    .AddSqlServer(connectionString, tags: new[] { "ready" })
    .AddCheck<PricingApiReadinessCheck>("pricing-api", tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Tuy nhiên không nên mặc định rằng external pricing API phải nằm trong readiness. Nếu application có thể vẫn phục vụ cached/degraded response khi pricing provider down, readiness có thể chỉ cần local critical dependencies; external provider health nên đi vào telemetry/circuit-breaker behavior thay vì remove toàn bộ pod khỏi traffic.

Resource values ở trên chỉ là minh họa. Production phải lấy từ measurements, không copy con số.

## Giải thích thiết kế sau khi sửa

`startupProbe` bảo vệ application khỏi bị liveness kill trong startup window. `readinessProbe` quyết định traffic eligibility. `livenessProbe` chỉ dùng cho trạng thái process cần restart.

Rolling strategy giữ old capacity cho tới khi new pod ready hơn, đổi lại có thời điểm chạy thêm pod (`maxSurge`). Đây là availability vs capacity/cost trade-off.

Immutable digest giúp release/rollback reproducible. Secret được tách khỏi manifest plaintext.

Shutdown budget được tăng để phù hợp application drain requirement, nhưng application vẫn phải implement graceful shutdown đúng; tăng grace period một mình không đủ.

## Trade-offs

`maxUnavailable: 0` + surge cần thêm temporary capacity. Nếu cluster không đủ resource, rollout có thể pending. Team phải reserve headroom hoặc chọn strategy khác.

Dependency-aware readiness giúp tránh gửi request vào pod không thể phục vụ critical path, nhưng nếu check dependency quá nhạy có thể làm toàn bộ fleet unready cùng lúc. Cần phân biệt application readiness với global dependency outage.

Memory limits cao hơn giảm OOM risk nhưng nếu đặt quá rộng có thể làm node overcommit/capacity planning kém. Requests/limits phải dựa trên load profile.

Kubernetes thêm operational complexity. Nếu workload không cần orchestration features này, App Service vẫn có thể là lựa chọn đơn giản hơn. Không nên coi Kubernetes là nâng cấp mặc định.

## Cách kiểm thử

1. **Deployment validation:** rollout dưới representative traffic; xác minh không có 5xx tăng khi pod mới startup 40 giây.
2. **Dependency failure test:** làm pricing API hoặc SQL chậm/fail; xác minh liveness không restart process chỉ vì external dependency outage.
3. **Graceful shutdown test:** terminate pod trong khi có long-running requests; xác minh readiness loại pod khỏi traffic và in-flight work hoàn tất trong budget.
4. **Resource/load test:** tăng load tới peak dự kiến; quan sát memory working set, CPU throttling và OOM behavior trước khi chốt requests/limits.
5. **Rollback test:** deploy image digest A → B → rollback A; xác minh chính xác artifact/digest và config version được khôi phục.

## Quan sát trong production

Theo dõi:

- pod ready count/desired replicas;
- rollout duration;
- readiness/liveness/startup probe failures theo reason;
- pod restart count và restart reason;
- OOMKilled events;
- CPU throttling, memory working set;
- request p50/p95/p99 và 5xx rate trong rollout;
- termination duration/in-flight request count;
- dependency latency/error rate SQL/pricing API;
- image digest đang chạy trên từng pod;
- config/secret version metadata không chứa secret value;
- correlation giữa deployment revision và error spikes.

Alert khi available replicas giảm dưới SLO, restart tăng, probe failure đồng loạt hoặc rollout làm 5xx vượt threshold.

2. Nếu cluster không đủ capacity cho `maxSurge: 1`, bạn cân bằng availability và rollout speed thế nào?
3. So với Azure App Service deployment slots, Kubernetes rollout mang lại lợi ích gì và complexity nào tăng đáng kể cho team application developer?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Streaming chỉ hiệu quả khi toàn bộ data path không buffer lại payload lớn trong memory.
- Tenant/security context phải đến từ trusted server-side identity, không từ form/query data do client tự khai báo.
- Khi database và external storage không có transaction chung, cần state machine + reconciliation thay vì giả định atomicity.
- Managed Identity giúp giảm secret handling và hỗ trợ least privilege cho Azure resources.
- Kubernetes `Running`, readiness, liveness và startup là các semantics khác nhau.
- Dependency outage không đồng nghĩa process cần restart; probe thiết kế sai có thể biến một partial failure thành restart storm.
- Rollout safety cần kết hợp readiness, capacity headroom, immutable artifact và graceful termination.

## Mẫu tư duy cần nhớ

- **Stream end-to-end; đừng chỉ nhìn tên API có chữ stream.**
- **Security boundary phải dùng server-owned identity context.**
- **Model partial failure giữa các systems thay vì giả lập distributed atomicity.**
- **Readiness quyết định traffic; liveness quyết định restart.**
- **Release artifact phải immutable và rollback phải reproducible.**
