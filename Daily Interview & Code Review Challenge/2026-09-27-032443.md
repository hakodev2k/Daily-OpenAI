# Code Review Challenge 1 — BackgroundService xử lý job trùng khi scale-out

**Chủ đề:** C#/.NET, BackgroundService, concurrency, horizontal scaling, SQL Server, idempotency  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Một hệ thống enterprise chạy ASP.NET Core trên Azure App Service. Một `BackgroundService` quét bảng `ExportJobs` mỗi 5 giây để lấy các job `Pending`, tạo file báo cáo và upload lên Azure Blob Storage. Hệ thống trước đây chạy 1 instance; gần đây scale lên 4 instances. Sau đó người dùng đôi lúc nhận nhiều file cho cùng một job, một số job bị ghi `Completed` dù upload lỗi, và khi deployment/restart xảy ra có job mất nhiều phút mới được xử lý lại.

Mỗi job có `Id`, `Status`, `CreatedAt`. Chưa có yêu cầu business rõ ràng về exactly-once; điều cần đảm bảo là không gây side effect trùng và job cuối cùng phải được xử lý thành công hoặc có trạng thái lỗi có thể điều tra.

## Đoạn code cần review

```csharp
public sealed class ExportWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly ILogger<ExportWorker> _logger;

    public ExportWorker(IServiceProvider services, ILogger<ExportWorker> logger)
    {
        _services = services;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var blob = scope.ServiceProvider.GetRequiredService<IBlobStorage>();

            var jobs = await db.ExportJobs
                .Where(x => x.Status == "Pending")
                .OrderBy(x => x.CreatedAt)
                .Take(20)
                .ToListAsync();

            foreach (var job in jobs)
            {
                try
                {
                    job.Status = "Processing";
                    await db.SaveChangesAsync();

                    var bytes = await BuildReportAsync(job.Id);
                    await blob.UploadAsync($"exports/{job.Id}.csv", bytes);

                    job.Status = "Completed";
                    job.CompletedAt = DateTime.UtcNow;
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex, "Export failed");
                    job.Status = "Pending";
                }

                await db.SaveChangesAsync();
            }

            await Task.Delay(TimeSpan.FromSeconds(5));
        }
    }

    private static async Task<byte[]> BuildReportAsync(Guid jobId)
    {
        await Task.Delay(100);
        return Encoding.UTF8.GetBytes($"report:{jobId}");
    }
}
```

## Kết quả code review tham khảo

### Critical — Claim job không atomic giữa nhiều instance

**Vấn đề:** Các instance đều có thể query cùng các hàng `Pending` trước khi bất kỳ instance nào commit `Processing`.  
**Tại sao xảy ra:** Query và update là hai bước riêng; tracking của EF Core chỉ bảo vệ state trong một `DbContext`, không tạo distributed lock.  
**Ảnh hưởng production:** Cùng job được xử lý nhiều lần và tạo side effect trùng.  
**Cách sửa:** Claim bằng thao tác có concurrency control tại database: conditional update `WHERE Status='Pending'`, optimistic concurrency token, hoặc database-specific locking/queue semantics. Chỉ worker claim thành công mới xử lý.

### High — Side effect upload và trạng thái database không atomic

**Vấn đề:** Process có thể upload thành công rồi crash trước khi ghi `Completed`.  
**Tại sao xảy ra:** Blob Storage và SQL không chung local transaction.  
**Ảnh hưởng production:** Retry có thể upload lại hoặc gửi downstream effect lần nữa.  
**Cách sửa:** Thiết kế operation idempotent. Với blob có key deterministic theo job ID, overwrite có kiểm soát có thể an toàn nếu nội dung deterministic; với side effect không idempotent cần idempotency key/outbox/inbox hoặc workflow phù hợp.

### High — Không hỗ trợ graceful shutdown/cancellation

**Vấn đề:** `while(true)`, EF query, `SaveChangesAsync`, report generation, upload và `Task.Delay` đều không nhận `stoppingToken`.  
**Tại sao xảy ra:** Cancellation không được propagate.  
**Ảnh hưởng production:** Deployment kéo dài, process bị hard-kill giữa job và recovery khó dự đoán.  
**Cách sửa:** Dùng `while (!stoppingToken.IsCancellationRequested)` và truyền token xuyên suốt.

### High — Job lỗi có thể retry vô hạn

**Vấn đề:** Catch đặt lại `Pending` ngay, không có attempt count/backoff/dead-letter state.  
**Tại sao xảy ra:** Không có retry policy hữu hạn.  
**Ảnh hưởng production:** Poison job chiếm capacity, tăng log/storage/dependency load.  
**Cách sửa:** Lưu `AttemptCount`, `NextAttemptAt`, `LastErrorCode`; exponential backoff có jitter và chuyển `Failed` sau ngưỡng phù hợp.

### Medium — Recovery cho job Processing bị bỏ dở chưa tồn tại

**Vấn đề:** Nếu worker chết sau claim, job có thể nằm `Processing` vĩnh viễn.  
**Tại sao xảy ra:** Không có lease/visibility timeout.  
**Ảnh hưởng production:** Job bị kẹt.  
**Cách sửa:** Lưu `LeaseUntil` và `WorkerId`; cho phép reclaim lease hết hạn, hoặc dùng queue có lock/visibility semantics.

### Medium — Batch được xử lý tuần tự

**Vấn đề:** 20 job xử lý serial.  
**Tại sao xảy ra:** `foreach` await từng job.  
**Ảnh hưởng production:** Throughput thấp khi report/upload là I/O-bound.  
**Cách sửa:** Chỉ tăng concurrency sau khi claim đúng; dùng bounded concurrency và quan sát DB/Blob limits.

### Medium — Log thiếu context

**Vấn đề:** Log không có `JobId`, attempt, worker/instance hoặc phase.  
**Tại sao xảy ra:** Message quá chung.  
**Ảnh hưởng production:** Khó correlate duplicate/retry/crash.  
**Cách sửa:** Structured logging với `JobId`, `Attempt`, `InstanceId`, duration và outcome.

### Low — Magic strings cho trạng thái

**Vấn đề:** `"Pending"`, `"Processing"`, `"Completed"` phân tán.  
**Tại sao xảy ra:** Domain state không được model rõ.  
**Ảnh hưởng production:** Dễ typo và transition sai khi code lớn lên.  
**Cách sửa:** Enum/value constants và validate state transition.

## Phiên bản đề xuất

Ví dụ dưới đây dùng optimistic claim bằng conditional update. Cú pháp cụ thể cần điều chỉnh theo database/schema và phải có recovery lease.

```csharp
public sealed class ExportWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<ExportWorker> _logger;

    public ExportWorker(IServiceScopeFactory scopeFactory, ILogger<ExportWorker> logger)
        => (_scopeFactory, _logger) = (scopeFactory, logger);

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            var processed = await TryProcessOneAsync(ct);
            if (!processed)
                await Task.Delay(TimeSpan.FromSeconds(5), ct);
        }
    }

    private async Task<bool> TryProcessOneAsync(CancellationToken ct)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var blob = scope.ServiceProvider.GetRequiredService<IBlobStorage>();

        var now = DateTime.UtcNow;
        var id = await db.ExportJobs
            .Where(x => x.Status == "Pending" && x.NextAttemptAt <= now)
            .OrderBy(x => x.CreatedAt)
            .Select(x => (Guid?)x.Id)
            .FirstOrDefaultAsync(ct);

        if (id is null) return false;

        var leaseUntil = now.AddMinutes(5);
        var claimed = await db.ExportJobs
            .Where(x => x.Id == id && x.Status == "Pending")
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.LeaseUntil, leaseUntil), ct);

        if (claimed != 1) return true;

        try
        {
            var bytes = await BuildReportAsync(id.Value, ct);
            await blob.UploadAsync($"exports/{id}.csv", bytes, ct);

            await db.ExportJobs.Where(x => x.Id == id)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "Completed")
                    .SetProperty(x => x.CompletedAt, DateTime.UtcNow)
                    .SetProperty(x => x.LeaseUntil, (DateTime?)null), ct);
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Export {JobId} failed", id);
            await RecordRetryOrFailureAsync(db, id.Value, CancellationToken.None);
        }

        return true;
    }

    private static async Task<byte[]> BuildReportAsync(Guid id, CancellationToken ct)
    {
        await Task.Delay(100, ct);
        return Encoding.UTF8.GetBytes($"report:{id}");
    }
}
```

Phần production cần thêm reclaim `Processing` khi `LeaseUntil` hết hạn và `RecordRetryOrFailureAsync` phải atomically tăng attempt/đặt `NextAttemptAt` hoặc `Failed`. Nếu side effect không idempotent, chỉ lease là chưa đủ.

## Giải thích thiết kế sau khi sửa

Conditional update biến claim thành cuộc đua mà chỉ một worker thắng. Lease xử lý crash recovery. Cancellation hỗ trợ shutdown. Retry state ngăn poison job quay vòng vô hạn. Blob key deterministic giảm duplicate artifact, nhưng không được suy diễn rằng mọi side effect đều idempotent.

Nếu workload trở thành queue-oriented rõ rệt, Azure Service Bus có thể là lựa chọn tốt hơn polling table vì có competing consumers, lock/retry/DLQ; tuy nhiên chuyển sang messaging có operational complexity và vẫn không loại bỏ yêu cầu idempotent consumer.

## Trade-offs

Database claim giữ kiến trúc đơn giản và phù hợp workload vừa phải nhưng tăng polling/locking pressure. Lease cần tuning và clock semantics. Service Bus giảm polling và hỗ trợ failure workflow tốt hơn nhưng thêm dependency, eventual processing và vận hành queue. Bounded parallelism tăng throughput nhưng tăng pressure lên DB/Blob.

## Cách kiểm thử

1. **Concurrency test:** chạy 10 worker đồng thời với cùng 100 job, xác minh mỗi job chỉ được claim bởi một worker.
2. **Failure-path test:** kill worker sau upload nhưng trước completion; xác minh retry không tạo side effect sai.
3. **Integration test:** lease hết hạn được reclaim; lease còn hạn không bị worker khác lấy.
4. **Load test:** đo throughput, DB waits, connection pool và Blob latency khi tăng worker count.
5. **Shutdown test:** gửi cancellation trong lúc idle và trong lúc processing, xác minh shutdown có kiểm soát.

## Quan sát trong production

Structured logs theo `JobId`/attempt/instance; metrics pending count, processing count, retry count, failed count, oldest-job age, processing duration; Application Insights dependency telemetry cho SQL/Blob; alert khi oldest pending age hoặc failed rate vượt baseline. Theo dõi SQL blocking/waits và App Service restart/instance count để correlate incident.

## Câu hỏi phỏng vấn mở rộng

1. Nếu upload Blob không thể overwrite và downstream gửi email ngay sau upload, bạn thiết kế idempotency thế nào?
2. Khi nào bạn giữ database polling thay vì chuyển sang Azure Service Bus?
3. Lease 5 phút có thể gây lỗi gì nếu một report hợp lệ mất 20 phút?

## Kết quả code review tham khảo

### Critical — Render HTML không có bằng chứng sanitization

**Vấn đề:** `highlightHtml` được đưa thẳng vào `dangerouslySetInnerHTML`.  
**Tại sao xảy ra:** Client tin HTML từ API/search index. Nếu dữ liệu hoặc highlight chứa payload độc hại, browser có thể interpret markup nguy hiểm.  
**Ảnh hưởng production:** Stored/reflected XSS tùy nguồn dữ liệu và backend behavior.  
**Cách sửa:** Tốt nhất API trả structured highlight segments thay vì arbitrary HTML. Nếu bắt buộc dùng HTML, sanitize bằng cơ chế/library được duy trì và policy rõ ràng ở trust boundary; không tự viết sanitizer bằng regex.

### High — Request race ghi stale result

**Vấn đề:** Request cũ có thể hoàn thành sau request mới và overwrite `items`.  
**Tại sao xảy ra:** Mỗi thay đổi query tạo async request độc lập, không cancellation/sequence guard.  
**Ảnh hưởng production:** UI hiển thị kết quả không khớp input.  
**Cách sửa:** Abort request trước trong cleanup và chỉ cập nhật state cho request hiện hành.

### High — Một request cho mỗi keystroke

**Vấn đề:** Không debounce.  
**Tại sao xảy ra:** Effect chạy ngay mỗi lần `query` đổi.  
**Ảnh hưởng production:** Request amplification, search backend load và cost tăng.  
**Cách sửa:** Debounce input/query ở mức UX phù hợp; vẫn giữ cancellation vì debounce không loại bỏ race hoàn toàn.

### Medium — Query không URL-encode

**Vấn đề:** Nối chuỗi trực tiếp vào query string.  
**Tại sao xảy ra:** Không dùng `URLSearchParams`.  
**Ảnh hưởng production:** Ký tự `&`, `+`, Unicode hoặc ký tự đặc biệt làm request sai nghĩa.  
**Cách sửa:** Dùng `URLSearchParams`.

### Medium — Không kiểm tra HTTP status/schema

**Vấn đề:** `r.json()` chạy cả khi status không thành công; response shape được tin tuyệt đối.  
**Tại sao xảy ra:** Thiếu response contract/error handling.  
**Ảnh hưởng production:** Error khó hiểu, UI có thể crash hoặc hiển thị state sai.  
**Cách sửa:** Check `response.ok`, validate contract ở boundary khi rủi ro đáng kể.

### Medium — Error/loading có thể bị request cũ thay đổi

**Vấn đề:** Request cũ có thể set `loading=false` hoặc error sau khi request mới bắt đầu.  
**Tại sao xảy ra:** Shared state không gắn với active request.  
**Ảnh hưởng production:** Loading indicator sai và lỗi cũ xuất hiện trên query mới.  
**Cách sửa:** Abort/identity guard; reset error khi request mới bắt đầu.

### Low — Query rỗng không reset toàn bộ state

**Vấn đề:** Clear input chỉ set items, không reset loading/error.  
**Tại sao xảy ra:** Early return thiếu state transition.  
**Ảnh hưởng production:** UI có thể giữ error/loading không còn liên quan.  
**Cách sửa:** Reset state phù hợp khi query trống.

## Phiên bản đề xuất

Ví dụ ưu tiên API trả highlight dưới dạng text/segments. Ở đây render `highlightText` như text, tránh HTML trust boundary.

```tsx
type SearchItem = {
  id: string;
  title: string;
  highlightText: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [debouncedQuery, setDebouncedQuery] = useState("");
  const [items, setItems] = useState<SearchItem[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const timer = window.setTimeout(() => setDebouncedQuery(query.trim()), 250);
    return () => window.clearTimeout(timer);
  }, [query]);

  useEffect(() => {
    if (!debouncedQuery) {
      setItems([]);
      setLoading(false);
      setError(null);
      return;
    }

    const controller = new AbortController();

    async function search() {
      setLoading(true);
      setError(null);

      try {
        const qs = new URLSearchParams({ q: debouncedQuery });
        const response = await fetch(`/api/search?${qs}`, {
          signal: controller.signal
        });

        if (!response.ok)
          throw new Error(`Search failed: HTTP ${response.status}`);

        const data = await response.json() as { items: SearchItem[] };

        if (!controller.signal.aborted)
          setItems(data.items);
      } catch (e) {
        if (e instanceof DOMException && e.name === "AbortError") return;
        if (!controller.signal.aborted)
          setError(e instanceof Error ? e.message : "Search failed");
      } finally {
        if (!controller.signal.aborted)
          setLoading(false);
      }
    }

    void search();
    return () => controller.abort();
  }, [debouncedQuery]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      {loading && <span>Loading...</span>}
      {error && <div role="alert">{error}</div>}
      <ul>
        {items.map(item => (
          <li key={item.id}>
            <a href={`/products/${encodeURIComponent(item.id)}`}>
              {item.title}
            </a>
            <div>{item.highlightText}</div>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Nếu requirement bắt buộc highlight từng token bằng markup, contract nên trả segments như `[{ text, highlighted }]` để React render element an toàn thay vì truyền raw HTML. Nếu backend đã sanitize HTML theo allowlist được kiểm chứng, frontend vẫn cần document rõ trust boundary và test security.

## Giải thích thiết kế sau khi sửa

Debounce giảm request amplification; `AbortController` ngăn response cũ cập nhật UI và giải phóng request không còn cần thiết khi browser/server hỗ trợ cancellation chain. `URLSearchParams` xử lý encoding. UI chỉ render text do React escape mặc định. Không cần thêm global state manager vì state này local với component.

Ở backend ASP.NET Core, `HttpContext.RequestAborted` nên được propagate xuống search client nếu việc hủy request có giá trị; cancellation không thay thế timeout và resilience policy.

## Trade-offs

Debounce thêm một ít perceived latency và giá trị 250 ms cần đo thay vì coi là chân lý. Cancellation phía browser không đảm bảo mọi downstream work lập tức dừng. Structured highlight segments làm API contract phức tạp hơn nhưng giảm đáng kể XSS risk và làm trust boundary rõ hơn. Runtime schema validation tăng safety nhưng thêm code/dependency.

## Cách kiểm thử

1. **Component test:** mô phỏng response cho query cũ về sau query mới; xác minh UI chỉ hiển thị query mới.
2. **Security test:** dữ liệu highlight chứa markup/script/event handler; xác minh không execute và được render an toàn.
3. **Network test:** gõ nhanh 10 ký tự; xác minh debounce/cancellation giới hạn số request.
4. **E2E Playwright:** search với Unicode, `&`, `+`, khoảng trắng; xác minh URL và kết quả đúng.
5. **Failure-path test:** API trả 500, timeout hoặc malformed response; xác minh error/loading state nhất quán.

## Quan sát trong production

Frontend telemetry: search request count per session, abort rate, error rate, latency và query-to-result duration. Application Insights: request/dependency duration, failure rate, cancellation/499-equivalent nếu hạ tầng ghi nhận, p95/p99 Search API. Browser/network traces dùng khi điều tra race. Security monitoring cần CSP/reporting phù hợp như defense-in-depth, nhưng CSP không thay thế output handling đúng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào hai dạng race khác nhau: distributed concurrency giữa nhiều .NET process và async request race trong browser. Điểm chung là không được suy diễn “đã set state” thành “đã có exclusivity”. Với background processing, retry phải đi cùng idempotency, lease/recovery và observability. Với frontend, request lifecycle phải gắn với state lifecycle; dữ liệu HTML từ API vẫn là untrusted input nếu trust boundary chưa được chứng minh.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; đừng coi exactly-once là mặc định.
- State transition chỉ an toàn khi cơ chế concurrency tương ứng thực sự atomic.
- Treat external systems và process lifetime as failure-prone.
- Với async UI, chỉ request hiện hành mới được quyền cập nhật state.
- Xác định trust boundary trước khi render hoặc execute dữ liệu từ bên ngoài.
