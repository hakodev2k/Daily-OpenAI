# Code Review Challenge 1 — Cosmos DB query vẫn chạy nhưng RU tăng mạnh, deep pagination chậm và một tenant tạo hot partition

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Cosmos DB, partition key, RU consumption, continuation token, pagination, hot partition, retry/backoff, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal audit platform lưu audit events trong Azure Cosmos DB. Mỗi event thuộc một tenant. Container hiện có partition key `/tenantId`.

Endpoint `GET /api/audit-events` dùng để hiển thị lịch sử theo tenant. UI hiện gửi `page` và `pageSize`. Một số tenant chỉ có vài nghìn events, nhưng một tenant enterprise tạo hàng chục triệu events mỗi tháng.

Production có các triệu chứng:

- page đầu thường nhanh, nhưng page vài trăm hoặc vài nghìn chậm rõ rệt;
- RU consumption tăng mạnh khi nhiều user mở audit history;
- xuất hiện nhiều `429` trong giờ cao điểm;
- một tenant enterprise chiếm phần lớn throughput của container;
- team tăng `MaxItemCount` lên 1000 vì nghĩ ít round-trip hơn sẽ luôn rẻ hơn;
- code retry ngay lập tức khi gặp `429`;
- API materialize rất nhiều items rồi mới `Skip/Take` trong memory;
- logs không ghi request charge, continuation token usage, partition key hay retry count;
- một developer đề xuất tăng RU autoscale và giữ nguyên query;
- một developer khác đề xuất chuyển toàn bộ audit data sang SQL Server vì cho rằng Cosmos DB “không hợp query”.

Business requirements:

- user chỉ được đọc audit events của tenant hiện tại;
- sort mới nhất trước;
- UI không bắt buộc nhảy trực tiếp tới page 5000 nếu continuation-based navigation hợp lý hơn;
- query cần predictable hơn về latency và cost;
- không được biến retry thành retry storm;
- hệ thống phải quan sát được RU, throttling và tenant nào gây tải;
- không cần đổi database nếu vấn đề chủ yếu là access pattern và partition/query design.

## Đoạn code cần review

```csharp
public sealed class AuditEventService
{
    private readonly Container _container;
    private readonly ILogger<AuditEventService> _logger;

    public AuditEventService(
        CosmosClient cosmosClient,
        ILogger<AuditEventService> logger)
    {
        _container = cosmosClient
            .GetDatabase("audit")
            .GetContainer("events");
        _logger = logger;
    }

    public async Task<IReadOnlyList<AuditEventDto>> SearchAsync(
        string tenantId,
        int page,
        int pageSize,
        DateTimeOffset? from,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.createdAt >= @from " +
            "ORDER BY c.createdAt DESC")
            .WithParameter(
                "@from",
                from ?? DateTimeOffset.MinValue);

        var iterator = _container.GetItemQueryIterator<AuditEvent>(
            query,
            requestOptions: new QueryRequestOptions
            {
                MaxItemCount = 1000
            });

        var all = new List<AuditEvent>();

        while (iterator.HasMoreResults)
        {
            try
            {
                var response = await iterator.ReadNextAsync(cancellationToken);
                all.AddRange(response.Resource);
            }
            catch (CosmosException ex)
                when ((int)ex.StatusCode == 429)
            {
                _logger.LogWarning("Cosmos throttled. Retrying immediately.");
                continue;
            }
        }

        return all
            .Where(x => x.TenantId == tenantId)
            .Skip(page * pageSize)
            .Take(pageSize)
            .Select(x => new AuditEventDto(
                x.Id,
                x.CreatedAt,
                x.Action,
                x.SubjectId))
            .ToList();
    }
}
```

## Nhiệm vụ của ứng viên

7. Đề xuất pagination bằng continuation token thay vì page number khi phù hợp.

## Kết quả code review tham khảo

### Critical — Tenant filter chỉ chạy sau khi đã đọc dữ liệu từ Cosmos DB

**Vấn đề:** Query không có `tenantId` predicate và không truyền `PartitionKey`; code lọc `TenantId` sau khi materialize toàn bộ results.

**Tại sao xảy ra:** Security/data-boundary logic bị đặt sai tầng. Database đọc dữ liệu vượt quá tenant cần thiết rồi application mới loại bỏ.

**Ảnh hưởng production:** RU cao, latency cao, memory tăng và blast radius lớn hơn nếu sau này code vô tình trả dữ liệu trước khi filter.

**Cách sửa:** Dùng authenticated tenant context và target đúng logical partition bằng `QueryRequestOptions.PartitionKey = new PartitionKey(tenantId)`. Query chỉ nên đọc partition tương ứng. Có thể thêm `tenantId` predicate để contract rõ ràng, nhưng security authority phải đến từ server-owned context chứ không từ client input không tin cậy.

### Critical — Toàn bộ result set được đọc trước khi pagination

**Vấn đề:** `while (iterator.HasMoreResults)` đọc hết dữ liệu phù hợp `from`, sau đó mới `Skip/Take`.

**Tại sao xảy ra:** Page-number abstraction được áp dụng như với in-memory collection thay vì distributed query iterator.

**Ảnh hưởng production:** Page size 50 không giới hạn RU/memory thực tế. Một request có thể đọc hàng trăm nghìn hoặc hàng triệu events chỉ để trả 50 items.

**Cách sửa:** Đọc đúng số page cần thiết từ iterator và trả continuation token cho client. Không scan toàn bộ result set chỉ để tính offset sâu.

### High — Deep offset pagination không phù hợp với access pattern lớn

**Vấn đề:** `page * pageSize` tạo kỳ vọng random access tới deep pages trong khi backend thực tế phải traverse data.

**Tại sao xảy ra:** UI page-number model bị coi như storage primitive.

**Ảnh hưởng production:** Cost tăng theo depth; latency và RU khó predictable.

**Cách sửa:** Dùng continuation-based pagination cho audit feed. Nếu business bắt buộc random jump theo thời gian, xem xét query theo time range/bookmark thay vì numeric offset.

### High — Retry `429` bằng tight loop

**Vấn đề:** Khi gặp throttling, code `continue` ngay lập tức.

**Tại sao xảy ra:** Retry không có delay/budget và bỏ qua server throttling guidance.

**Ảnh hưởng production:** Tạo retry storm, tăng pressure lên cùng partition/container, kéo dài request và làm saturation nặng hơn.

**Cách sửa:** Dựa vào retry behavior của SDK/configuration phù hợp và giới hạn retry budget. Nếu tự xử lý, respect retry delay từ response, có backoff/jitter phù hợp và cancellation. Không retry vô hạn trong request path.

### High — Hot tenant có thể làm partition strategy trở thành bottleneck

**Vấn đề:** `/tenantId` gom toàn bộ một tenant vào cùng logical partition.

**Tại sao xảy ra:** Partition key tối ưu tenant-local reads nhưng distribution phụ thuộc tenant cardinality và skew.

**Ảnh hưởng production:** Tenant enterprise có thể tập trung traffic/storage vào một logical partition, dẫn đến throttling dù tổng container throughput còn khả năng ở các partition khác.

**Cách sửa:** Đầu tiên đo distribution và workload. Nếu skew thực sự là root cause, cân nhắc data model/partition strategy mới như synthetic key có time bucket hoặc dimension khác phù hợp access pattern. Đây là migration/data-model decision, không phải code tweak đơn giản.

### High — Không ghi nhận request charge nên team tối ưu mù

**Vấn đề:** Code không log/metric `RequestCharge` cho từng page/query.

**Tại sao xảy ra:** Observability chỉ nhìn HTTP latency mà không nhìn cost model của database.

**Ảnh hưởng production:** Có thể tăng throughput để che query inefficiency hoặc kết luận sai rằng Cosmos DB không phù hợp.

**Cách sửa:** Ghi metric RU/request, RU/item, latency, throttled request count, retry count, tenant dimension đã được kiểm soát cardinality và continuation usage.

### Medium — `MaxItemCount = 1000` bị dùng như optimization mặc định

**Vấn đề:** Page size phía Cosmos được tăng mạnh mà không có evidence.

**Tại sao xảy ra:** Round-trip count bị coi là metric duy nhất.

**Ảnh hưởng production:** Response page lớn hơn làm tăng latency từng call, memory burst và amount of work trước khi cancellation có hiệu lực; RU tổng thể không tự nhiên giảm chỉ vì client page lớn hơn.

**Cách sửa:** Tune dựa trên measured RU, response size, latency và UI page size. Có thể để SDK/default behavior hoặc chọn page size nhỏ hơn phù hợp request contract.

### Medium — `SELECT *` lấy dữ liệu nhiều hơn cần thiết

**Vấn đề:** Endpoint chỉ cần vài field nhưng query load toàn document.

**Tại sao xảy ra:** DTO projection bị thực hiện sau khi dữ liệu đã rời database.

**Ảnh hưởng production:** Tăng payload, serialization và network cost; RU có thể cao hơn tùy document/query shape.

**Cách sửa:** Project chỉ fields cần thiết trong query nếu model/query path ổn định và đo được lợi ích.

### Medium — Không validate pagination input

**Vấn đề:** `page`, `pageSize` có thể âm hoặc rất lớn.

**Tại sao xảy ra:** Request boundary thiếu validation.

**Ảnh hưởng production:** Unexpected behavior, memory/cost amplification và API contract khó kiểm soát.

**Cách sửa:** Với continuation pagination, giới hạn `pageSize`; validate token và input. Nếu vẫn giữ page-number compatibility, đặt giới hạn rõ ràng.

### Medium — Tenant identity chưa được model hóa như trusted server context

**Vấn đề:** Method nhận `tenantId` như một string parameter bình thường; chưa rõ nguồn từ authenticated principal hay client.

**Tại sao xảy ra:** Security context và application input trộn lẫn.

**Ảnh hưởng production:** Dễ dẫn tới cross-tenant query nếu caller truyền tenant tùy ý.

**Cách sửa:** Dùng `ICurrentTenant`/server-owned context được derive từ validated identity; service không nhận arbitrary tenant id từ request khi không cần.

## Phiên bản đề xuất

Một hướng phù hợp với feed-style UI là continuation-based pagination trong đúng tenant partition:

```csharp
public sealed record AuditPage(
    IReadOnlyList<AuditEventDto> Items,
    string? ContinuationToken,
    double RequestCharge);

public sealed class AuditEventService
{
    private readonly Container _container;
    private readonly ICurrentTenant _currentTenant;
    private readonly ILogger<AuditEventService> _logger;

    public AuditEventService(
        Container container,
        ICurrentTenant currentTenant,
        ILogger<AuditEventService> logger)
    {
        _container = container;
        _currentTenant = currentTenant;
        _logger = logger;
    }

    public async Task<AuditPage> SearchAsync(
        int pageSize,
        DateTimeOffset? from,
        string? continuationToken,
        CancellationToken cancellationToken)
    {
        pageSize = Math.Clamp(pageSize, 1, 100);
        var tenantId = _currentTenant.Id;

        var query = new QueryDefinition(
            "SELECT c.id, c.createdAt, c.action, c.subjectId " +
            "FROM c " +
            "WHERE c.tenantId = @tenantId AND c.createdAt >= @from " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@tenantId", tenantId)
            .WithParameter("@from", from ?? DateTimeOffset.MinValue);

        using var iterator = _container.GetItemQueryIterator<AuditEventDto>(
            query,
            continuationToken,
            new QueryRequestOptions
            {
                PartitionKey = new PartitionKey(tenantId),
                MaxItemCount = pageSize
            });

        if (!iterator.HasMoreResults)
            return new AuditPage([], null, 0);

        var response = await iterator.ReadNextAsync(cancellationToken);

        _logger.LogInformation(
            "Audit query tenant {TenantId} returned {Count} items with {RequestCharge} RU",
            tenantId,
            response.Count,
            response.RequestCharge);

        return new AuditPage(
            response.Resource.ToList(),
            response.ContinuationToken,
            response.RequestCharge);
    }
}
```

Đoạn trên minh họa một page đọc trong đúng tenant partition. Retry/throttling policy nên được cấu hình có budget và theo SDK/runtime behavior thực tế; không nên thêm vòng retry vô hạn quanh iterator.

Nếu tenant enterprise vẫn bị throttling dù query đã partition-targeted và RU/request hợp lý, bước tiếp theo là phân tích distribution: storage size, request volume, write/read hotspots theo tenant và time. Nếu `/tenantId` tạo skew không chấp nhận được, có thể cần migration sang partition strategy mới. Ví dụ synthetic key theo tenant + time bucket có thể phân tán write/read, nhưng đổi lại query lịch sử tenant sẽ phải đọc nhiều buckets. Đây là trade-off cần benchmark trên access pattern thật.

## Giải thích thiết kế sau khi sửa

Query chỉ nhắm một logical partition nên loại bỏ cross-partition fan-out không cần thiết. Tenant scope đến từ trusted context thay vì input tùy ý.

Continuation token biến pagination thành traversal state do database cung cấp. API không cần đọc mọi item trước vị trí offset. Điều này phù hợp audit feed, nơi user thường đi tuần tự qua các trang.

`MaxItemCount` được align với UI page size thay vì dùng một giá trị lớn theo cảm tính. Đây không phải quy tắc tuyệt đối; production có thể tune sau khi đo latency và RU.

Request charge được đưa vào telemetry để team biết optimization có giảm cost thật hay chỉ thay đổi timing.

## Trade-offs

Continuation token làm UX “jump tới page 5000” khó hơn. Nếu business thực sự cần random navigation, cần một navigation model khác như time-range bookmarks hoặc index riêng, chứ không nên giả lập random access bằng scan đắt đỏ.

Partition key `/tenantId` rất tự nhiên cho tenant isolation và tenant-local queries, nhưng workload skew có thể tạo hot partition. Synthetic partitioning giúp distribution tốt hơn nhưng tăng query complexity và migration cost.

Tăng provisioned/autoscale throughput có thể là đúng nếu query đã hiệu quả và tải business thực sự tăng. Nhưng throughput không nên che access pattern tệ.

Chuyển sang SQL Server chỉ hợp lý nếu workload/query/transaction requirements tổng thể phù hợp hơn; không nên đổi database chỉ vì một implementation đang đọc sai partition và pagination.

## Cách kiểm thử

1. **Integration test:** tenant A và B có dữ liệu xen kẽ; query của A chỉ trả A và request được target bằng đúng partition key.
2. **Pagination test:** tạo nhiều pages, traverse bằng continuation token; xác minh không duplicate/missing item theo ordering contract trong dataset ổn định.
3. **Load test:** chạy nhiều tenants đồng thời, bao gồm một tenant lớn; đo RU/request, p95/p99, `429` và memory trước/sau fix.
4. **Throttle/failure-path test:** mô phỏng throttling; xác minh request không tight-loop, respect cancellation và retry budget.
5. **Hot-partition experiment:** replay representative workload theo tenant distribution để xác định skew có đến từ partition model hay query inefficiency.

## Quan sát trong production

Theo dõi:

- RU/request và RU/item;
- query latency p50/p95/p99;
- `429` count/rate;
- retry count và retry delay;
- request volume theo tenant bucket đã kiểm soát metric cardinality;
- continuation-token pagination usage;
- response item count;
- document payload size;
- top tenants theo RU consumption;
- storage/request distribution theo partition-related telemetry khả dụng;
- ASP.NET Core cancellation rate và request duration.

Alert khi một tenant chiếm tỷ trọng RU bất thường, `429` tăng kéo dài, RU/request tăng sau release hoặc continuation-based query latency vượt SLO.

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky trên CI vì shared test data, hard wait và race với network

**Chủ đề:** Playwright, TypeScript, E2E testing, test isolation, parallel execution, deterministic waiting, shared state, CI/CD, flaky tests, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một back-office React application có Playwright E2E suite chạy trong CI. Local developer thường chạy 1 worker; CI chạy nhiều workers song song để giảm thời gian pipeline.

Các tests cùng dùng một account `qa-admin@example.test` và một order seed cố định `ORDER-1001`.

Production code không có lỗi rõ ràng, nhưng CI có các triệu chứng:

- cùng commit chạy lại có lúc pass, có lúc fail;
- test edit order đôi lúc thấy dữ liệu do test khác vừa thay đổi;
- test delete order làm test view order fail ngẫu nhiên;
- suite dùng `waitForTimeout` để “đợi API xong”;
- đôi lúc click xong rồi mới đăng ký `waitForResponse`, nên response đã đi qua trước khi waiter bắt đầu;
- `retries: 3` làm pipeline xanh nhưng trace cho thấy test đã fail 1–2 lần trước đó;
- screenshots có nhiều lỗi “element detached” hoặc text chưa kịp cập nhật;
- cleanup không chạy nếu test fail giữa chừng;
- team đề xuất tăng toàn bộ timeout lên 60 giây và giảm workers về 1.

Business requirements:

- suite phải phát hiện regression thật, không che flaky bằng retry;
- tests có thể chạy parallel khi dữ liệu độc lập;
- test data phải deterministic và cleanup an toàn;
- E2E chỉ nên kiểm tra flows cần browser; setup data có thể dùng API nếu giúp ổn định;
- CI cần artifact đủ để điều tra failure;
- không cần cố chạy parallel mọi test nếu một nhóm thực sự không thể isolate.

```ts
  await page.goto(`/orders/${orderNo}`)
  await page.getByRole('button', { name: 'Delete' }).click()
  await page.waitForTimeout(1000)
  await expect(page.getByText('Order deleted')).toBeVisible()
})

test('view order', async ({ page }) => {
  await page.goto(`/orders/${orderNo}`)
  await expect(page.getByText(orderNo)).toBeVisible()
})
```

## Nhiệm vụ của ứng viên

1. Xác định các nguyên nhân flaky test do shared state, parallel workers, timing và waiter ordering.
2. Giải thích vì sao `ORDER-1001` dùng chung khiến tests không độc lập.
3. Chỉ ra race condition khi `waitForResponse` được đăng ký sau `click` + hard wait.
4. Phân tích vì sao `waitForTimeout` không chứng minh application đã đạt trạng thái mong muốn.
5. Đánh giá `retries: 3`: khi nào hữu ích cho diagnostics và khi nào đang che test defect.
6. Đề xuất data setup per-test bằng API hoặc fixture với unique identifiers.
7. Đề xuất cách đăng ký network waiter trước action gây request.
8. Nêu khi nào giảm parallelism cho một describe block là hợp lý thay vì tắt parallel toàn suite.
9. Đề xuất cleanup/idempotent teardown sao cho test fail giữa chừng vẫn không phá run sau.
10. Nêu CI artifacts/telemetry cần giữ để root-cause flaky test nhanh hơn.

## Câu hỏi gợi mở

1. Ba tests trên có thể chạy đồng thời mà không thay đổi state của nhau không?
2. Nếu PUT response hoàn tất trong 100 ms nhưng code đợi 1500 ms rồi mới gọi `waitForResponse`, waiter có còn nhìn thấy response cũ không?
3. Timeout dài hơn làm race condition biến mất hay chỉ làm failure mất nhiều thời gian hơn?

5. Setup qua UI có thật sự cần thiết nếu mục tiêu test chỉ là flow edit/delete/view sau khi order đã tồn tại?

## Kết quả code review tham khảo

### Critical — Các tests dùng chung mutable order

**Vấn đề:** Cả ba tests đọc/sửa/xóa `ORDER-1001`.

**Tại sao xảy ra:** Test data được coi như global fixture bất biến trong khi tests thực hiện mutation.

**Ảnh hưởng production/CI:** Khi chạy parallel, outcome phụ thuộc execution order. Delete có thể phá view/edit; edit có thể thay assertion state của test khác.

**Cách sửa:** Mỗi test tạo order riêng với unique id/order number. Dùng API fixture hoặc test-support endpoint phù hợp để setup nhanh, rồi cleanup chính resource test đó.

### High — `waitForResponse` được đăng ký quá muộn

**Vấn đề:** Code click Save, đợi 1.5 giây, rồi mới bắt đầu chờ PUT response.

**Tại sao xảy ra:** Event waiter được tạo sau action có thể đã phát event.

**Ảnh hưởng production/CI:** Test timeout dù request thực tế đã thành công. Fast environment có thể fail nhiều hơn slow environment.

**Cách sửa:** Tạo waiter trước hoặc dùng `Promise.all` để action và waiter được phối hợp:

```ts
const [response] = await Promise.all([
  page.waitForResponse(r =>
    r.url().includes('/api/orders/') &&
    r.request().method() === 'PUT'),
  page.getByRole('button', { name: 'Save' }).click()
])
```

### High — `waitForTimeout` tạo test timing-based thay vì state-based

**Vấn đề:** Test giả định 1–1.5 giây là đủ để UI/backend hoàn tất.

**Tại sao xảy ra:** Fixed delay thay cho observable condition.

**Ảnh hưởng production/CI:** CI load khác local; delay có thể quá ngắn khi chậm hoặc lãng phí khi nhanh.

**Cách sửa:** Chờ response cụ thể, UI state, URL, toast, network contract hoặc assertion auto-wait của Playwright.

### High — Retry đang che flaky failure

**Vấn đề:** `retries: 3` có thể làm run cuối xanh dù test không deterministic.

**Tại sao xảy ra:** Retry bị dùng như reliability mechanism thay vì diagnostic safety net.

**Ảnh hưởng production/CI:** Regression confidence giảm; pipeline tốn thời gian; team quen bỏ qua flaky test.

**Cách sửa:** Theo dõi retry rate như failure signal. Giữ retry thấp nếu cần capture trace on retry, nhưng flaky tests phải được triage/fix. Không xem “pass after retry” tương đương clean pass.

### High — Shared authentication state có thể kéo theo shared server-side state

**Vấn đề:** Tất cả workers dùng cùng authenticated account.

**Tại sao xảy ra:** Shared `storageState` tiện lợi nhưng application có thể có user-scoped mutable preferences/session side effects.

**Ảnh hưởng production/CI:** Nếu tests thay đổi user settings, drafts, locks hoặc current tenant, workers ảnh hưởng nhau.

**Cách sửa:** Nếu auth chỉ là stateless identity và app không có mutable user state, shared auth có thể chấp nhận. Nếu có stateful behavior, tạo account/identity pool hoặc isolate relevant tests. Cần dựa trên actual application semantics.

### Medium — Không có deterministic setup contract

**Vấn đề:** Tests giả định `ORDER-1001` tồn tại với đúng initial state.

**Tại sao xảy ra:** Environment seed bị dùng như implicit precondition.

**Ảnh hưởng production/CI:** Run trước, manual tester hoặc environment reset có thể làm test fail.

**Cách sửa:** Setup resource trong test/fixture bằng API hoặc database test fixture có contract rõ ràng. Test phải biết chính xác initial state nó tạo.

### Medium — Cleanup không được đảm bảo

**Vấn đề:** Nếu test fail trước cleanup thủ công, resource có thể còn lại hoặc bị xóa nửa chừng.

**Tại sao xảy ra:** Lifecycle data không gắn với fixture/test teardown.

**Ảnh hưởng production/CI:** Data leak giữa runs và tăng flakiness theo thời gian.

**Cách sửa:** Dùng fixture/`afterEach` cleanup idempotent, hoặc unique test namespace có batch cleanup. Cleanup failure cần được log riêng nhưng không che original test failure.

### Medium — `fullyParallel: true` áp dụng rộng hơn khả năng isolation thực tế

**Vấn đề:** Toàn bộ suite bị ép parallel mà không phân loại tests có shared constraints.

**Tại sao xảy ra:** Pipeline time được tối ưu trước test architecture.

**Ảnh hưởng production/CI:** Tests vốn không isolate sẽ race.

**Cách sửa:** Giữ parallel cho tests độc lập. Với nhóm thật sự cần serialized resource, dùng `test.describe.configure({ mode: 'serial' })` hoặc worker-scoped fixture, nhưng phải coi serialization là exception có lý do rõ ràng.

### Medium — Artifacts chưa đủ để điều tra flaky

**Vấn đề:** Chỉ screenshot khi fail.

**Tại sao xảy ra:** Failure investigation thiếu network/action timeline.

**Ảnh hưởng production/CI:** Khó biết request nào fail, waiter nào miss hoặc state nào bị test khác mutate.

**Cách sửa:** Bật trace phù hợp như `on-first-retry` hoặc theo policy CI, giữ video/network/log khi cần, attach test data id và API correlation id.

### Low — Selector/assertion chưa gắn đủ chặt với resource state

**Vấn đề:** `getByText('Approved')` hoặc `Order deleted` có thể match text không phải nguồn state chính nếu UI phức tạp.

**Tại sao xảy ra:** Assertion quá generic.

**Ảnh hưởng production/CI:** False positive hoặc ambiguous failure.

**Cách sửa:** Ưu tiên role/label/test id hợp lý và assertion tại component/resource context cụ thể. Không lạm dụng `data-testid` nếu accessible selector đã đủ ổn định.

## Phiên bản đề xuất

Ví dụ dưới đây dùng API setup per-test và waiter đăng ký trước action. Endpoint/fixture names chỉ là minh họa cho test architecture.

```ts
import { test, expect, APIRequestContext } from '@playwright/test'

async function createOrder(request: APIRequestContext) {
  const orderNo = `E2E-${crypto.randomUUID()}`

  const response = await request.post('/api/test-support/orders', {
    data: {
      orderNo,
      status: 'Pending'
    }
  })

  expect(response.ok()).toBeTruthy()
  return orderNo
}

async function deleteOrder(
  request: APIRequestContext,
  orderNo: string
) {
  await request.delete(`/api/test-support/orders/${orderNo}`)
}

test('edit order status', async ({ page, request }) => {
  const orderNo = await createOrder(request)

  try {
    await page.goto(`/orders/${orderNo}`)

    await page.getByRole('button', { name: 'Edit' }).click()
    await page.getByLabel('Status').selectOption('Approved')

    const [response] = await Promise.all([
      page.waitForResponse(r =>
        r.url().includes('/api/orders/') &&
        r.request().method() === 'PUT'),
      page.getByRole('button', { name: 'Save' }).click()
    ])

    expect(response.ok()).toBeTruthy()

    await expect(
      page.getByRole('status')
    ).toContainText('Saved')

    await expect(
      page.getByTestId('order-status')
    ).toHaveText('Approved')
  } finally {
    await deleteOrder(request, orderNo)
  }
})
```

Một config cân bằng hơn:

```ts
export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  workers: process.env.CI ? 6 : undefined,
  retries: process.env.CI ? 1 : 0,
  use: {
    baseURL: process.env.BASE_URL,
    storageState: 'playwright/.auth/qa-admin.json',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure'
  }
})
```

`workers: 6` và retry count ở đây chỉ là minh họa, không phải con số mặc định đúng cho mọi CI. Concurrency phải dựa trên environment capacity và test isolation. Nếu shared auth account có mutable user-scoped state, cần thay đổi fixture/auth strategy thay vì chỉ tune workers.

## Giải thích thiết kế sau khi sửa

Mỗi test sở hữu resource riêng nên execution order không còn ảnh hưởng state. Unique id cũng giúp trace logs/backend correlation dễ hơn.

Setup qua API tránh tốn browser steps không thuộc behavior đang test. E2E vẫn kiểm tra UI edit flow, nhưng fixture creation được làm deterministic và nhanh hơn.

`Promise.all` đăng ký response waiter trước khi action phát request. Playwright assertions auto-wait trên UI state thay vì ngủ theo thời gian cố định.

Retry được giảm xuống mức phục vụ diagnostics chứ không che flakiness. Trace on first retry cung cấp timeline để điều tra.

## Trade-offs

Test-support API làm setup nhanh nhưng cần giới hạn chỉ trong test environment và không được mở ra production một cách thiếu kiểm soát. Alternative là fixture trực tiếp DB hoặc reusable backend client tùy architecture.

Per-test data creation tăng số API/database operations. Tuy nhiên đây thường là chi phí đáng đổi lấy isolation. Có thể dùng worker-scoped immutable seed cho dữ liệu thật sự read-only.

Parallelism cao làm suite nhanh hơn nhưng có thể overload shared staging environment. Nếu backend capacity nhỏ, giảm workers có thể cần thiết sau khi tests đã isolate; đó là capacity decision, không phải cách chữa race condition.

Serialized describe block có thể hợp lý cho flow dùng shared external sandbox không thể clone. Nhưng serialization làm test suite chậm và che dependency coupling, nên phải dùng có chủ đích.

## Cách kiểm thử

1. **Repeatability test:** chạy cùng suite 20–50 lần với cùng commit; theo dõi flaky/retry rate thay vì chỉ final pass rate.
2. **Parallel stress test:** tăng workers trong giới hạn environment; xác minh tests vẫn pass vì data isolation, không phải vì timing may mắn.
3. **Network-race test:** delay PUT response có chủ đích, rồi cho response nhanh/chậm khác nhau; xác minh waiter và UI assertions vẫn deterministic.
4. **Failure cleanup test:** cố tình làm assertion fail giữa test; xác minh cleanup vẫn xóa đúng resource và run sau không bị ảnh hưởng.
5. **CI artifact validation:** gây một failure có kiểm soát; xác minh trace/screenshot/correlation metadata đủ để xác định action, request và resource liên quan.

## Quan sát trong production/CI

Theo dõi:

- test pass rate lần đầu;
- pass-after-retry rate;
- flaky tests theo thời gian;
- duration p50/p95 theo test;
- worker count và total suite duration;
- API error/latency trong thời gian E2E run;
- số test resources được tạo/cleanup;
- cleanup failures;
- test data id/order number gắn với trace;
- screenshots/traces cho first failure hoặc first retry;
- backend correlation id nếu test chạm API quan trọng.

Một pipeline “xanh sau retry” nhưng retry rate tăng là tín hiệu chất lượng xấu, không nên coi là success hoàn toàn.

2. Nếu staging environment dùng chung với manual QA và không thể reset database mỗi run, bạn thiết kế namespace/test data ownership thế nào?
3. Bạn sẽ dùng Playwright E2E, API integration test và unit test theo tỷ lệ/risk nào để tránh biến browser suite thành nơi kiểm tra mọi logic?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với Cosmos DB, partition targeting và access pattern quyết định lớn tới RU/latency; tăng throughput không thay thế query design đúng.
- Continuation token phù hợp hơn offset/deep pagination cho feed lớn và distributed query traversal.
- `429` cần retry có budget/backoff phù hợp; tight retry loop làm saturation nặng hơn.
- Partition key tốt phải cân bằng query locality và data/traffic distribution; tenant skew có thể biến key tự nhiên thành hotspot.
- E2E test phải sở hữu state riêng nếu muốn chạy parallel đáng tin cậy.
- Fixed sleep không chứng minh application đạt trạng thái mong muốn; chờ observable condition mới tạo test deterministic.
- Retry trong CI nên hỗ trợ diagnostics, không được dùng để hợp thức hóa flaky tests.

## Mẫu tư duy cần nhớ

- **Target the partition before tuning throughput.**
- **Traverse large datasets bằng continuation/state, không scan rồi Skip trong memory.**
- **Throttle là feedback của hệ thống; retry phải có budget và delay.**
- **Parallel tests chỉ an toàn khi test data và mutable state được isolate.**
- **Wait for state, not time.**
