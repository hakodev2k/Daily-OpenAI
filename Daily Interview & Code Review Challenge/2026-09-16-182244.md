# Câu 1 — `IQueryable` trông như collection nhưng query thực sự chạy khi nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Entity Framework Core, LINQ, `IQueryable`, expression trees, deferred execution, query translation, `DbContext`, SQL round trips, performance

## Bối cảnh

Một ASP.NET Core API dùng EF Core để trả danh sách đơn hàng. Team vừa refactor repository thành:

```csharp
public IQueryable<Order> GetActiveOrders()
{
    return _db.Orders.Where(x => x.Status == OrderStatus.Active);
}
```

Service tiếp tục compose query theo filter từ request, rồi controller gọi `CountAsync()` để tạo metadata và `ToListAsync()` để lấy page. Ở một chỗ khác, developer enumerate cùng một `IQueryable` hai lần trong hai helper methods. Một reviewer nói rằng `GetActiveOrders()` đã “load active orders từ database” khi method return. Reviewer khác cho rằng vì LINQ là lazy nên mọi operation đều chỉ chạy một lần ở cuối request.

Production cho thấy một endpoint có nhiều SQL commands hơn team dự kiến, nhưng chưa có trace/query-count evidence đủ rõ.

## Câu hỏi chính

Hãy giải thích internal/practical behavior của `IQueryable`, expression tree, deferred execution và EF Core query translation trong scenario này. Query thực sự được gửi xuống database khi nào, vì sao cùng một query shape có thể tạo nhiều round trips, assumptions nào của hai reviewer là sai, và bạn sẽ xác minh behavior thực tế như thế nào trước khi tối ưu?

## Câu hỏi làm rõ nên cân nhắc

1. `CountAsync()` và `ToListAsync()` có cùng filter/pagination projection hay không?
2. Có helper nào gọi `AsEnumerable()`, `ToList()`, `First()`, `Any()` hoặc enumerate navigation collections không?
3. `DbContext` lifetime có còn hợp lệ tại thời điểm query được enumerate không?
4. Endpoint cần exact total count hay UX có thể dùng một pagination contract khác?
5. SQL command count và payload size thực tế ở p95 traffic là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

`IQueryable` thường đại diện cho một query description có thể tiếp tục compose; nó không đồng nghĩa kết quả đã materialize.

### Gợi ý 2

Hãy tìm các terminal/materialization operations và mỗi lần enumeration thay vì chỉ nhìn nơi query được khai báo.

### Gợi ý 3

Phân biệt “một expression tree được compose” với “một SQL command được execute”. Hai terminal operations có thể cần hai database operations khác nhau.

## Cấu trúc trả lời đề xuất

1. Làm rõ query pipeline và `DbContext` lifetime.
2. Giải thích expression-tree composition.
3. Xác định execution/materialization boundaries.
4. Liệt kê các vị trí có thể gây multiple enumeration/round trips.
5. Kiểm tra SQL/logging/tracing thực tế.
6. Đánh giá requirement của count + page.
7. Tối ưu projection/query shape hoặc contract khi evidence hỗ trợ.
8. Test query count và correctness.
9. Theo dõi database dependency count/duration trong production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Returning `IQueryable` không tự đồng nghĩa query đã được execute/materialize.
- EF Core provider nhận expression tree và dịch phần có thể dịch thành database query khi execution xảy ra.
- `CountAsync()` và `ToListAsync()` là hai operations riêng; không được giả định một lần execute tự cung cấp cả count và page result.
- Enumerating cùng một non-materialized query nhiều lần có thể tạo nhiều database executions.
- Query composition phải xảy ra khi `DbContext` còn sống; deferred execution có lifetime implications.
- Phải đo SQL command count, generated SQL và timings trước khi kết luận optimization.

### Điểm cộng

- Dùng projection chỉ lấy columns cần thiết thay vì materialize full entities cho read API.
- Phân biệt `IQueryable<T>` với `IEnumerable<T>` và cảnh giác khi crossing boundary làm phần còn lại chạy client-side/in-memory.
- Xem total-count requirement như product/API decision, không mặc định mọi pagination cần exact count.
- Dùng integration test/command interception hoặc telemetry phù hợp để assert query count ở critical path.

### Senior+

- Nhận ra việc expose `IQueryable` xuyên architecture boundary tạo coupling với persistence/query provider; có thể chấp nhận hoặc không tùy design, nhưng phải đánh giá ownership và testability thay vì áp dụng rule tuyệt đối.
- Không cố gộp count + page thành một query phức tạp nếu complexity/cost không được chứng minh là tốt hơn.
- Đánh giá query shape, round trips, consistency giữa count và page, và isolation requirement cùng nhau.

## Hướng giải quyết tham khảo

Tôi sẽ xem `GetActiveOrders()` là bước tạo query description, chưa phải bằng chứng database đã được gọi. Các `Where`, `OrderBy`, `Select`, `Skip`, `Take` tiếp theo có thể tiếp tục tạo expression tree. Khi code gọi một terminal async operation như `CountAsync()` hoặc `ToListAsync()`, provider mới cần thực thi database operation tương ứng.

Vì vậy endpoint gọi `CountAsync()` rồi `ToListAsync()` thường phải được xem là hai database operations độc lập. Nếu cùng một `IQueryable` bị enumerate ở hai helper khác nhau, nó cũng có thể execute lại. Tôi sẽ không dựa vào nhận định “LINQ lazy nên chỉ chạy một lần”; lazy chỉ trì hoãn execution, không memoize result.

Tôi xác minh bằng EF Core command logging/Application Insights dependency telemetry hoặc interceptor trong integration test để đếm commands và xem generated SQL. Tôi cũng tìm các materialization boundaries như `ToList`, `First`, `Any`, `AsEnumerable` và navigation access.

Sau đó mới tối ưu theo requirement. Với read endpoint, projection DTO trước materialization thường giảm data transfer/tracking cost. Nếu exact total count đắt và UI không thực sự cần, pagination contract có thể thay đổi. Nếu count bắt buộc, hai operations có thể hoàn toàn hợp lý; cần đo latency/DB load trước khi tạo một query phức tạp chỉ để giảm round trip.

Tôi cũng kiểm tra consistency requirement: count và page là hai statements nên dữ liệu có thể thay đổi giữa chúng tùy isolation/concurrency. Nếu business cần snapshot semantics thì đó là requirement riêng, không nên vô tình giải quyết bằng một optimization trick.

## Mẫu trả lời trong phỏng vấn

“Em coi `IQueryable` là query description chứ không phải collection đã load. EF Core compose expression tree qua các LINQ operators, và execution xảy ra khi gặp terminal operation như `CountAsync` hoặc `ToListAsync`. Vì vậy gọi cả hai thường là hai database operations; enumerate lại query cũng có thể execute lại. Deferred execution không có nghĩa result được cache.

Em sẽ chứng minh bằng command logging/tracing và integration test đếm SQL commands, đồng thời xem generated SQL và nơi code chuyển sang `IEnumerable` hoặc materialize. Sau đó mới quyết định: projection DTO, bỏ tracking nếu phù hợp, thay pagination contract nếu exact count không cần, hoặc giữ hai queries nếu cost chấp nhận được.

Em cũng để ý `DbContext` lifetime và consistency giữa count/page. Em không tối ưu chỉ dựa trên số round trips nếu query phức tạp hơn lại làm database tệ hơn.”

## Câu hỏi đào sâu

1. Nếu repository return `IQueryable` làm application layer phụ thuộc EF Core semantics, bạn giữ design này hay thay bằng query-specific abstraction?
2. Nếu product bắt buộc exact count nhưng bảng có hàng trăm triệu rows, bạn sẽ điều tra và thiết kế pagination như thế nào?
3. Tôi muốn materialize ngay trong repository để “chắc chắn chỉ query một lần”; trade-off của quyết định đó là gì?

## Lỗi trả lời thường gặp

- Nói `IQueryable` đã chứa dữ liệu từ database.
- Nghĩ deferred execution đồng nghĩa automatic memoization.
- Tối ưu bằng `ToList()` sớm mà không xét memory/data transfer.
- Không kiểm tra generated SQL/query count.
- Bỏ qua `DbContext` lifetime và consistency giữa nhiều executions.

## Thang điểm 0–10

- **0–2:** Chỉ nói LINQ là lazy.
- **3–4:** Biết terminal operation nhưng không phân tích multiple execution.
- **5–6:** Giải thích expression/query execution đúng và có verification.
- **7–8:** Có projection, API requirement, lifetime, consistency và telemetry reasoning.
- **9–10:** Phân tích query provider, architecture boundary, database cost và product semantics như một quyết định thống nhất.

# Câu 2 — Service Bus backlog tăng nhưng consumer CPU thấp: lock, retry hay downstream đang nghẽn?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, .NET worker, at-least-once delivery, message locks, retries, idempotency, DLQ, dependency degradation, observability, production incident reasoning

## Bối cảnh

Một .NET worker xử lý order events từ Azure Service Bus. Bình thường backlog gần 0. Sau khi một external fulfillment API bắt đầu chậm, queue depth tăng liên tục trong 45 phút. Consumer CPU chỉ 25–35%, nhưng logs có một số message xuất hiện nhiều lần. Một số order downstream bị tạo duplicate shipment request.

Worker hiện xử lý mỗi message bằng cách đọc order từ SQL Server, gọi fulfillment API, ghi trạng thái rồi complete message. Team có retry ở HTTP client và cũng dùng retry/redelivery behavior của messaging. Chưa rõ fulfillment API có idempotency key hay không, message processing duration có vượt lock window hay không, và telemetry chưa tách attempt đầu với redelivery.

Một developer đề xuất tăng concurrency tối đa để drain queue. Developer khác muốn tăng retry count của HTTP call.

## Câu hỏi chính

Bạn sẽ xử lý incident theo impact → stabilization → evidence → competing hypotheses → root cause → remediation như thế nào? Hãy phân tích backlog, dependency latency, message lock/redelivery, layered retries và idempotency; giải thích khi nào tăng concurrency giúp, khi nào nó có thể làm downstream hoặc duplicate side effects tệ hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Fulfillment API latency/error distribution và rate limit hiện tại thế nào?
2. Message processing duration so với lock/renewal behavior thực tế ra sao?
3. Duplicate message có cùng message/business ID hay là upstream publish duplicate?
4. HTTP retry policy retry lỗi nào, bao nhiêu lần, backoff ra sao; Service Bus delivery count thay đổi thế nào?
5. Fulfillment API hỗ trợ idempotency key hoặc query/reconciliation theo order ID không?

## Gợi ý tư duy

### Gợi ý 1

Queue backlog có thể là symptom của downstream throughput thấp hơn arrival rate; CPU consumer thấp không có nghĩa consumer còn safe capacity.

### Gợi ý 2

Retry ở nhiều layer nhân số attempts. Nếu side effect không idempotent, một timeout không cho biết remote operation đã thất bại hay đã thành công nhưng response bị mất.

### Gợi ý 3

Theo dõi message identity, delivery count, processing duration, lock/settlement và downstream request identity trong cùng trace để phân biệt redelivery với duplicate publish.

## Cấu trúc trả lời đề xuất

1. Định lượng business impact: backlog age, duplicate shipments, affected orders.
2. Stabilize duplicate side effects và bảo vệ fulfillment dependency.
3. Thu queue metrics, delivery count, lock/processing timings và dependency traces.
4. Lập hypotheses: slow dependency, lock expiry, layered retry amplification, poison subset, upstream duplicate.
5. Xác minh từng hypothesis bằng message/business IDs.
6. Thiết kế idempotent processing/side-effect contract.
7. Tune concurrency/retry dựa trên downstream capacity.
8. Thiết kế DLQ/reconciliation cho ambiguous outcomes.
9. Failure/load test.
10. Alert theo queue age/depth, redelivery, DLQ và dependency saturation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- CPU thấp không chứng minh có thể tăng concurrency an toàn; consumer có thể đang chờ network.
- At-least-once style processing yêu cầu consumer chịu được duplicate delivery; không được giả định một message chỉ xuất hiện một lần.
- Timeout của external API tạo ambiguous outcome: remote side effect có thể đã xảy ra.
- Retry ở HTTP + messaging layer cần được thiết kế tổng thể để tránh retry amplification.
- Message completion phải xảy ra theo failure semantics rõ ràng; không complete trước khi required processing state được đảm bảo.
- Cần theo dõi DLQ, delivery count, queue age/depth và dependency latency/error.

### Điểm cộng

- Dùng stable business idempotency key khi fulfillment API hỗ trợ.
- Nếu API không hỗ trợ idempotency, thiết kế local inbox/state/reconciliation phù hợp thay vì tin rằng retry là an toàn.
- Tách transient failure khỏi permanent/poison message và có DLQ handling/runbook.
- Concurrency được bound theo downstream capacity/rate limit và database capacity.
- Dùng jittered/exponential backoff phù hợp thay vì synchronized aggressive retry.

### Senior+

- Nhận ra “exactly once” end-to-end thường không đạt được chỉ bằng queue setting khi có external side effect; cần business-level idempotency/reconciliation.
- Thiết kế state machine cho `Pending → FulfillmentRequested → Confirmed/Unknown/Failed` nếu remote outcome có thể ambiguous.
- Phân biệt drain backlog nhanh với bảo vệ hệ thống; recovery throughput phải tránh tạo retry storm lần hai.

## Hướng giải quyết tham khảo

Tôi sẽ ưu tiên ngăn duplicate shipment trước khi cố drain queue. Nếu fulfillment đang degrade, tăng concurrency có thể gửi nhiều request hơn vào dependency đang nghẽn và làm timeout/retry tăng. Tôi cần biết arrival rate, queue age, active messages, delivery count, processing duration, lock behavior và fulfillment p95/p99/error/rate-limit.

Tôi correlate một `orderId`/message ID xuyên consumer, SQL state và HTTP request. Nếu cùng message được redeliver sau processing dài hoặc settlement failure, đó là một branch. Nếu upstream publish nhiều message khác nhau cho cùng business event, đó là branch khác. Nếu HTTP timeout xảy ra sau remote side effect, retry có thể tạo duplicate shipment nếu remote API không idempotent.

Thiết kế tốt nhất phụ thuộc fulfillment contract. Nếu API hỗ trợ idempotency key, tôi gửi stable key theo business operation và persist processing state. Nếu không, tôi cần local deduplication/inbox và reconciliation; local dedupe một mình vẫn không giải quyết hoàn toàn ambiguous remote outcome, nên có thể cần query remote state hoặc manual/automated reconciliation.

Tôi xem retry budget end-to-end: HTTP retries phải giới hạn và chỉ cho lỗi phù hợp; message redelivery là một layer retry khác. Permanent failures nên đi DLQ theo policy thay vì retry vô hạn. Concurrency chỉ tăng sau khi chứng minh downstream còn capacity và database/worker không bị saturation.

Testing gồm duplicate-delivery test, timeout-after-remote-success simulation, lock/long-processing test, downstream 429/5xx failure injection và load recovery từ backlog. Production alerts gồm oldest-message age, active/dead-letter count, delivery count distribution, processing duration, settlement failures, fulfillment latency/error và duplicate-business-operation metric.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không tăng concurrency ngay vì CPU thấp có thể chỉ nghĩa worker đang chờ fulfillment API. Việc quan trọng nhất là duplicate shipment: timeout không chứng minh remote call thất bại, và Service Bus có thể redeliver, nên consumer phải có business-level idempotency.

Em sẽ correlate message ID/order ID, delivery count, processing duration, lock/settlement và HTTP attempts. Đồng thời em tính retry budget của cả HTTP layer lẫn message redelivery để tránh amplification. Nếu fulfillment hỗ trợ idempotency key, em dùng stable key; nếu không, cần dedupe + state/reconciliation cho outcome không xác định.

Sau khi biết downstream capacity em mới tune concurrency. Em monitor queue age/depth, DLQ, redelivery, dependency p99 và duplicate operations. Mục tiêu không chỉ drain backlog mà drain an toàn, không tạo incident thứ hai.”

## Câu hỏi đào sâu

1. Nếu fulfillment API không có endpoint tra cứu trạng thái và không hỗ trợ idempotency key, bạn giảm duplicate risk thế nào?
2. Nếu backlog đã tương đương 6 giờ traffic, bạn lập recovery plan/concurrency ramp như thế nào?
3. Tôi muốn complete message trước HTTP call rồi retry fulfillment bằng application code để tránh redelivery; bạn phản biện failure mode nào?

## Lỗi trả lời thường gặp

- Tăng concurrency chỉ vì CPU thấp.
- Tăng mọi retry count khi dependency đang degrade.
- Nghĩ duplicate detection ở queue tự giải quyết duplicate side effect end-to-end.
- Không phân biệt timeout với confirmed remote failure.
- Không có DLQ/reconciliation strategy.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng consumer hoặc retry.
- **3–4:** Biết redelivery/idempotency nhưng thiếu incident evidence.
- **5–6:** Có lock, retries, downstream capacity, DLQ và observability.
- **7–8:** Có ambiguous-outcome handling, business idempotency và recovery testing.
- **9–10:** Thiết kế được end-to-end failure semantics và backlog recovery có kiểm soát, cân bằng throughput với duplicate risk.

# Câu 3 — Nền tảng upload tài liệu: proxy qua API hay upload trực tiếp Azure Blob Storage?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS concepts, file streaming, security, asynchronous processing, SQL metadata, reliability, observability, system design

## Bối cảnh

Một internal employee platform cần tính năng upload tài liệu cho khoảng 30.000 nhân viên. File phổ biến 1–20 MB nhưng đôi lúc có file vài trăm MB. Yêu cầu sơ bộ:

- user phải authenticated và chỉ được upload vào hồ sơ họ có quyền sửa;
- metadata tài liệu nằm trong SQL Server;
- binary lưu ở Azure Blob Storage;
- sau upload cần virus/malware scanning và trích xuất metadata trước khi file được phép download;
- UI React cần hiển thị progress và retry hợp lý;
- hệ thống ASP.NET Core hiện chạy Azure App Service nhiều instances;
- team đang tranh luận giữa upload toàn bộ file qua API server và cấp quyền upload trực tiếp tới Blob Storage;
- chưa có con số chính xác về peak concurrent uploads, compliance retention hay requirement resumable upload.

Một architect đề xuất mọi file đi qua API vì “security tốt hơn”. Một developer đề xuất client được quyền ghi trực tiếp toàn container để giảm tải backend.

## Câu hỏi chính

Bạn sẽ thiết kế upload workflow và boundaries như thế nào? Hãy so sánh backend-proxy upload với direct-to-Blob upload, thiết kế authorization, scoped upload permission, metadata/state machine, scanning/quarantine, retry/idempotency, download authorization, cleanup, observability và failure recovery. Giải pháp phải giải thích điều kiện nào khiến bạn chọn hoặc thay đổi từng approach.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrency, file-size distribution và upload bandwidth kỳ vọng là bao nhiêu?
2. File types, malware/compliance requirements và retention/legal-hold rules là gì?
3. Browser có cần resumable/chunked upload và retry sau network interruption không?
4. Download có cần backend authorization mỗi lần hay có thể cấp short-lived scoped access sau authorization?
5. Khi metadata record được tạo nhưng upload không hoàn tất, business muốn giữ trạng thái bao lâu trước cleanup?

## Gợi ý tư duy

### Gợi ý 1

Đừng đồng nhất “đi qua backend” với “an toàn”. Security đến từ authorization, scope, identity, validation và lifecycle controls.

### Gợi ý 2

Upload binary và commit business metadata không nhất thiết là một atomic transaction. Hãy thiết kế explicit states và recovery cho partial failure.

### Gợi ý 3

Direct upload có thể giảm bandwidth/memory pressure ở App Service, nhưng permission phải cực kỳ scoped và file chưa scan không được tự động trở thành downloadable business asset.

## Cấu trúc trả lời đề xuất

1. Làm rõ scale, security/compliance và UX requirements.
2. Xác định resource ownership và authorization model.
3. So sánh proxy vs direct upload theo size/concurrency/control/cost complexity.
4. Thiết kế upload session + blob naming + scoped permission.
5. Thiết kế metadata/state machine và idempotency.
6. Quarantine → scan → promote/mark-ready workflow.
7. Thiết kế download authorization.
8. Xử lý abandoned upload, retry và cleanup.
9. Testing/security/failure injection.
10. Observability, deployment và operational runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cấp broad container write permission cho browser.
- Authorization phải kiểm tra business ownership trước khi cấp khả năng upload/download.
- Direct upload permission nếu dùng phải short-lived/scoped theo resource/operation phù hợp với storage security model đang chọn.
- Unscanned file phải ở trạng thái quarantine/not-ready và không được public/download như file hợp lệ.
- Metadata + blob lifecycle cần explicit state vì SQL và Blob Storage không phải một local atomic transaction.
- File size/concurrency quyết định mạnh tới proxy-vs-direct trade-off.
- Secrets/credentials dài hạn không được gửi xuống client.

### Điểm cộng

- Backend dùng Managed Identity cho server-to-storage access thay vì lưu storage secret khi environment hỗ trợ.
- Blob key không dựa trực tiếp vào user filename; original filename là metadata đã sanitize/encode phù hợp khi hiển thị.
- State machine ví dụ `PendingUpload → Uploaded → Scanning → Ready/Rejected`, kèm expiry cho abandoned sessions.
- Event/background processing cho scan có idempotency và retry; duplicate event không được promote file hai lần theo cách gây sai state.
- Download path kiểm tra `Ready` và authorization trước khi stream hoặc cấp short-lived scoped read access.

### Senior+

- Phân tích TOCTOU/lifecycle risk giữa upload completion, scan result và download availability.
- Thiết kế checksum/content-length/content-type validation nhưng không tin client-provided MIME type như security boundary.
- Có cleanup/reconciliation job cho orphan blob và orphan metadata.
- Chọn proxy cho file nhỏ/low scale hoặc khi inspection/control bắt buộc inline; chọn direct upload khi bandwidth/large-file/concurrency benefit đủ lớn, nhưng không biến nó thành rule tuyệt đối.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng scale và compliance. Với file vài trăm MB và nhiều concurrent uploads, proxy toàn bộ binary qua App Service có thể nhân bandwidth, connection duration và resource pressure. Direct-to-Blob có thể phù hợp hơn, nhưng browser không bao giờ được broad credential cho container.

Một workflow khả thi là client gọi API `POST /document-uploads`. Backend authenticate user, authorize hồ sơ, tạo metadata `PendingUpload`, sinh blob key server-controlled và cấp một upload capability ngắn hạn chỉ cho blob/operation cần thiết theo cơ chế Azure Storage phù hợp đã được security review. Client upload trực tiếp và báo completion, hoặc backend nhận storage event/verify blob existence trước khi chuyển state.

File mới nằm trong quarantine namespace/container hoặc ít nhất state không cho download. Background scanner xử lý blob, validate các metadata cần thiết và chuyển record sang `Ready` hoặc `Rejected`. Scanner phải idempotent vì event/retry có thể lặp. Nếu scan service lỗi, file giữ trạng thái không-ready và retry theo policy; không fail-open.

Download API authorize user trên metadata và chỉ cho file `Ready`. Tùy requirement, backend có thể stream file hoặc cấp short-lived scoped read access. Nếu compliance yêu cầu mọi byte đi qua inspection/audit gateway, proxy có thể hợp lý hơn dù cost cao hơn. Tôi không mặc định direct upload là tốt nhất.

SQL record và blob không atomic nên cần reconciliation. Pending session có expiry; cleanup tìm abandoned metadata/blob. Nếu client upload xong nhưng callback mất, backend/storage event hoặc reconciliation có thể phát hiện blob và tiếp tục workflow. Nếu metadata bị xóa nhưng blob còn, lifecycle cleanup xử lý theo retention policy.

Security tests gồm unauthorized upload/download, capability scope/expiry, filename/content-type attacks, oversized file và malware/quarantine path. Reliability tests gồm interrupted upload, duplicate completion/event, scan timeout, SQL failure sau upload và cleanup. Observability gồm upload session ID/correlation ID, bytes/duration/failure, pending age, scan latency/result, orphan counts và download authorization failures.

## Mẫu trả lời trong phỏng vấn

“Em không coi proxy qua API tự động an toàn hơn. Với file lớn và concurrency đáng kể, em nghiêng về direct-to-Blob để tránh App Service làm data plane, nhưng backend vẫn là control plane: authenticate, authorize business resource, tạo upload session và cấp quyền ngắn hạn cực kỳ scoped cho đúng blob/operation. Client không bao giờ có container credential rộng.

Em tách lifecycle thành `PendingUpload`, `Uploaded`, `Scanning`, `Ready/Rejected`. File chưa scan không được download. Scanner chạy idempotent và failure phải fail-closed. Download vẫn qua authorization, sau đó backend có thể stream hoặc cấp scoped read access tùy compliance.

Vì SQL và Blob không atomic, em thiết kế expiry/reconciliation cho orphan metadata/blob và duplicate events. Nếu scale thấp hoặc policy bắt buộc inline inspection, proxy upload có thể đơn giản và đúng hơn. Em sẽ chọn dựa trên file size, concurrency, compliance và operational complexity, không theo một pattern cố định.”

## Câu hỏi đào sâu

1. Nếu security team cấm mọi client-side storage access, bạn thiết kế proxy upload thế nào để file 500 MB không gây memory pressure và timeout?
2. Nếu scan service down 6 giờ nhưng business yêu cầu upload vẫn hoạt động, workflow và UX của bạn xử lý thế nào?
3. Tôi muốn dùng một SAS/container permission dùng chung trong 24 giờ để giảm số lần gọi backend; bạn phản biện rủi ro và cost nào?

## Lỗi trả lời thường gặp

- Cấp storage key/container write permission cho browser.
- Cho download ngay sau upload trước scan.
- Cố tạo “distributed transaction” giả giữa SQL và Blob mà không có recovery state.
- Tin filename/MIME type từ client như security validation.
- Chọn direct upload hoặc proxy như rule tuyệt đối mà không hỏi scale/compliance.

## Thang điểm 0–10

- **0–2:** Chỉ mô tả endpoint upload cơ bản.
- **3–4:** Có Blob Storage và authorization nhưng thiếu partial-failure lifecycle.
- **5–6:** Có scoped access, quarantine, state machine, scanning và recovery.
- **7–8:** Có idempotency, reconciliation, download security, failure tests và observability.
- **9–10:** Cân bằng data-plane/control-plane, security, large-file UX, distributed consistency và operational complexity với điều kiện quyết định rõ ràng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` là query composition abstraction; deferred execution trì hoãn nhưng không memoize database result, nên terminal operations và multiple enumeration phải được quan sát như execution boundaries.
- Message processing với external side effects phải thiết kế retry cùng idempotency và ambiguous-outcome recovery; backlog không được chữa bằng concurrency một cách máy móc.
- File upload architecture cần tách authorization/control plane khỏi binary data plane, đồng thời thiết kế quarantine, lifecycle state và reconciliation cho partial failure.
- Senior-level optimization bắt đầu từ requirement và telemetry, không từ một pattern hoặc infrastructure knob.

## Mẫu tư duy cần nhớ

1. **Tìm execution boundary trước khi tối ưu abstraction.**
2. **Thiết kế retry cùng idempotency và recovery cho outcome không xác định.**
3. **CPU thấp không đồng nghĩa hệ thống còn capacity ở dependency khác.**
4. **Tách control plane khỏi data plane khi scale/resource profile chứng minh lợi ích.**
5. **Khi hai storage systems không atomic, dùng explicit state + reconciliation thay vì giả định consistency.**
