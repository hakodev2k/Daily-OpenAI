# Câu 1 — API vẫn `async` nhưng p99 tăng mạnh vì allocation lớn và GC pause

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, GC, LOH, allocation, ASP.NET Core, async I/O, response streaming, performance measurement, production diagnostics

## Bối cảnh

Một ASP.NET Core API trên .NET 8 cung cấp endpoint tạo file JSON/CSV theo yêu cầu. Mỗi response thường 5–20 MB. Endpoint hiện được viết hoàn toàn bằng `async/await`, không có `Task.Wait()` hay `.Result`.

Trong traffic bình thường hệ thống ổn định. Khi khoảng 100–150 requests cùng lúc:

- CPU chỉ khoảng 55–65%;
- request throughput không tăng tương ứng khi scale traffic;
- p50 vẫn khoảng 500 ms nhưng p99 nhảy lên 8–12 giây;
- memory working set tăng theo từng đợt traffic rồi giảm chậm;
- Application Insights cho thấy SQL dependency không chậm đáng kể;
- team quan sát nhiều Gen 2 collections trong `dotnet-counters`;
- một developer đề xuất “đổi thêm code sang async” vì nghĩ GC pause liên quan đến thread bị block.

Đoạn code rút gọn:

```csharp
[HttpGet("reports/{id:guid}")]
public async Task<IActionResult> Download(Guid id, CancellationToken ct)
{
    var rows = await _db.ReportRows
        .AsNoTracking()
        .Where(x => x.ReportId == id)
        .OrderBy(x => x.Sequence)
        .ToListAsync(ct);

    var json = JsonSerializer.Serialize(rows);
    var utf8 = Encoding.UTF8.GetBytes(json);

    await using var compressed = new MemoryStream();
    await using (var gzip = new GZipStream(
        compressed,
        CompressionLevel.Fastest,
        leaveOpen: true))
    {
        await gzip.WriteAsync(utf8, ct);
    }

    var result = compressed.ToArray();
    return File(result, "application/gzip", $"{id}.json.gz");
}
```

Giả sử business thực sự cần tải file lớn, và chưa có bằng chứng SQL là bottleneck chính.

## Câu hỏi chính

Hãy giải thích điều gì có thể đang xảy ra bên trong .NET runtime khi endpoint này chịu concurrency cao, vì sao code “đã async” vẫn có thể tạo p99 latency lớn, những giả định nào của team có thể sai, và bạn sẽ chứng minh hoặc bác bỏ giả thuyết GC/allocation bằng production evidence như thế nào trước khi sửa.

## Câu hỏi làm rõ nên cân nhắc

1. Distribution thực tế của số rows và kích thước response là bao nhiêu ở p50/p95/p99?
2. `dotnet-counters`/trace cho thấy allocation rate, heap size, LOH size, Gen 2 collection count và GC pause duration như thế nào trong incident?
3. Endpoint có thể stream dữ liệu dần ra response hay business bắt buộc phải có toàn bộ payload đã compress trước khi gửi?
4. Có reverse proxy/CDN nào buffer response, giới hạn size hoặc tự compression thêm không?
5. SQL query trả dữ liệu trong bao lâu và bao nhiêu bytes được materialize trước serialization?

## Gợi ý tư duy

### Gợi ý 1

`async/await` chủ yếu giúp không giữ thread trong lúc chờ I/O. Nó không tự làm giảm kích thước object graph, số byte được allocate hay chi phí GC.

### Gợi ý 2

Hãy đếm các representation cùng tồn tại trong memory: entity/list, UTF-16 `string`, UTF-8 `byte[]`, `MemoryStream` buffer và `ToArray()` result. Với payload lớn, một request có thể tạo nhiều large objects.

### Gợi ý 3

Kết nối runtime mechanism với số đo: allocation rate → LOH/Gen 2 pressure → GC pause/heap expansion → tail latency. Sau đó so sánh với một implementation streaming bằng load test thay vì chỉ suy luận từ code.

## Cấu trúc trả lời đề xuất

1. Làm rõ response-size/concurrency distribution.
2. Mô tả lifetime và allocation của từng buffer trong code.
3. Giải thích GC generations, large-object behavior và tại sao tail latency có thể tăng.
4. Tách CPU saturation, ThreadPool starvation, SQL latency và GC pressure thành các giả thuyết cạnh tranh.
5. Chỉ ra telemetry cần thu để phân biệt các giả thuyết.
6. Đề xuất thay đổi theo thứ tự ít rủi ro nhất.
7. Nêu cách load test, đo trước/sau và rollback nếu kết quả không cải thiện.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra `async` không đồng nghĩa với low allocation hoặc low memory pressure.
- Nhận ra endpoint materialize nhiều bản sao lớn của cùng payload.
- Giải thích large allocations có xu hướng làm tăng Gen 2/LOH pressure và tail latency.
- Không kết luận GC là root cause chỉ từ một counter; phải correlate với pause duration, allocation rate và request latency.
- Đề xuất streaming/projection/batching khi phù hợp thay vì chỉ “tăng RAM”.
- Đề cập cancellation và bounded response/workload.

### Điểm cộng

- Phân biệt working set, managed heap, LOH và object lifetime.
- Nhận ra `MemoryStream.ToArray()` tạo thêm một copy.
- Đề xuất `JsonSerializer.SerializeAsync`/streaming writer hoặc pipeline theo batch nếu contract cho phép.
- Đề xuất projection chỉ các fields cần thiết thay vì materialize full entities.
- Biết kiểm tra ThreadPool counters để tránh nhầm GC với starvation.

### Senior+

- Liên hệ p99 với stop-the-world phases/heap pressure mà không tuyệt đối hóa mọi GC implementation detail.
- Đề xuất measurement bằng `dotnet-counters`, `dotnet-trace`/EventPipe, allocation profiling và representative load test.
- Cân nhắc backpressure/admission limits cho expensive exports thay vì cho concurrency tăng vô hạn.
- Cân nhắc chuyển very-large report sang asynchronous export + Blob nếu synchronous HTTP download không còn phù hợp UX/SLO, nhưng chỉ khi requirement biện minh.

## Hướng giải quyết tham khảo

Điểm đầu tiên cần sửa trong mental model là: `async/await` giải quyết **waiting efficiency**, không giải quyết **memory efficiency**. Trong đoạn code hiện tại, một request lớn có thể giữ đồng thời nhiều representation của dữ liệu.

`ToListAsync()` materialize toàn bộ rows và object graph. `JsonSerializer.Serialize(rows)` tạo một `string`; vì .NET `string` dùng UTF-16, 10 MB UTF-8 payload có thể cần lượng memory đáng kể hơn ở representation này tùy content. `Encoding.UTF8.GetBytes(json)` tạo một `byte[]` mới. `MemoryStream` giữ buffer cho compressed bytes. Sau đó `ToArray()` lại copy toàn bộ compressed buffer sang một array mới để `File()` trả response. Những object/buffer đủ lớn tạo pressure lên managed heap, nhiều object có thể đi vào LOH và sống đủ lâu để kéo theo Gen 2 collection.

Không nên nói đơn giản rằng “object > một con số cố định nên chắc chắn LOH và Gen 2 luôn pause X ms”; runtime implementation và workload cần được đo. Nhưng pattern này rất đáng nghi vì concurrency nhân allocation per request lên nhanh. 100 requests, mỗi request giữ vài chục MB transient data, có thể tạo allocation rate cực lớn dù CPU chưa 100%.

Gen 2/LOH pressure có thể làm heap mở rộng và GC thực hiện expensive collections. Điều đó thường ảnh hưởng tail latency mạnh hơn median: phần lớn requests chạy nhanh, một số requests trùng vào GC pressure hoặc resource contention nên p99 tăng đột biến. CPU 60% không bác bỏ GC/memory bottleneck.

Tuy nhiên, một Senior không nên nhảy từ “Gen 2 tăng” tới “GC là root cause”. Tôi sẽ thu đồng thời:

- request duration p50/p95/p99 theo endpoint và response-size bucket;
- allocation rate (`alloc-rate`), GC heap size, LOH size, Gen 0/1/2 counts, `% time in GC`/pause signals phù hợp runtime;
- working set và container memory;
- ThreadPool thread count/queue length/completed work item rate;
- SQL dependency duration/query rows;
- CPU và exception rate.

Nếu incident cần sâu hơn, dùng EventPipe/`dotnet-trace` hoặc profiler để xem allocation hotspots và GC pauses correlate với traffic. Kết quả tốt nhất là reproduce dưới representative load: cùng dataset size, same concurrency, same container limits.

Nếu measurement xác nhận allocation amplification, hướng sửa đầu tiên là giảm số lần materialize/copy. Ví dụ projection thẳng DTO cần export, serialize trực tiếp vào output stream hoặc `GZipStream` gắn với `Response.Body`, thay vì tạo `string`, `byte[]`, `MemoryStream`, rồi `ToArray()`. Nếu dataset rất lớn, đọc/serialize theo streaming hoặc batch thay vì `ToListAsync()` toàn bộ.

Một sketch đơn giản:

```csharp
[HttpGet("reports/{id:guid}")]
public async Task Download(Guid id, CancellationToken ct)
{
    Response.ContentType = "application/gzip";
    Response.Headers.ContentDisposition =
        $"attachment; filename=\"{id}.json.gz\"";

    await using var gzip = new GZipStream(
        Response.Body,
        CompressionLevel.Fastest,
        leaveOpen: true);

    var query = _db.ReportRows
        .AsNoTracking()
        .Where(x => x.ReportId == id)
        .OrderBy(x => x.Sequence)
        .Select(x => new ReportRowDto(x.Sequence, x.Code, x.Value));

    await JsonSerializer.SerializeAsync(
        gzip,
        query.AsAsyncEnumerable(),
        cancellationToken: ct);
}
```

Đây chỉ là direction; cần xác minh provider/EF streaming semantics, error behavior sau khi response đã bắt đầu, reverse-proxy buffering và serializer format mong muốn. Nếu partial-response failure không chấp nhận được, có thể generation ra durable object trước rồi download sau — nhưng đó là product/architecture decision, không phải reflex optimization.

Tôi cũng sẽ đặt maximum report size/date range hoặc concurrency limit nếu một request có cost rất lớn. Sau sửa, chạy load test A/B và so sánh allocation/request, heap size, GC pause, p99, throughput và DB load. Nếu p99 vẫn cao nhưng GC signals giảm, tiếp tục điều tra ThreadPool, proxy buffering, network throughput hoặc serialization CPU thay vì tuyên bố thành công.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không kết luận rằng async đang có vấn đề. `async/await` giúp giải phóng thread khi chờ I/O, nhưng code này vẫn materialize và copy payload nhiều lần. Một request giữ list entities, sau đó một JSON string, một UTF-8 byte array, buffer của `MemoryStream`, rồi `ToArray()` lại copy compressed payload. Khi mỗi response 5–20 MB và concurrency lên hơn 100, allocation rate có thể tăng rất lớn và tạo LOH/Gen 2 pressure. Điều đó phù hợp với symptom p50 khá ổn nhưng p99 nhảy mạnh, dù CPU chưa 100%.

Nhưng tôi chưa gọi GC là root cause chỉ từ việc Gen 2 count tăng. Tôi muốn correlate request latency với allocation rate, managed heap/LOH size, GC pause, working set và đồng thời xem ThreadPool queue, CPU và SQL dependency. Nếu cần tôi dùng `dotnet-trace` hoặc profiler trong môi trường reproduce để xác định allocation hotspot.

Nếu giả thuyết đúng, tôi sẽ giảm materialization: projection đúng fields cần thiết, tránh serialize thành string rồi convert byte array, tránh `MemoryStream.ToArray()`, và nếu HTTP contract cho phép thì serialize trực tiếp qua `GZipStream` vào response. Với report rất lớn tôi sẽ cân nhắc batch/stream dữ liệu và giới hạn concurrency hoặc chuyển sang asynchronous export, nhưng chỉ nếu product requirement cho phép.

Sau đó tôi load test cùng dataset/concurrency và so sánh allocation/request, GC pause, p99 và throughput. Mục tiêu không phải ‘ít GC bằng mọi giá’, mà là chứng minh tail latency và memory behavior được cải thiện mà không làm hỏng correctness hoặc error semantics.”

## Câu hỏi đào sâu

1. Nếu streaming làm allocation giảm rõ rệt nhưng response đã bắt đầu rồi mới phát sinh SQL exception, bạn sẽ thiết kế error semantics và client behavior thế nào?
2. Nếu profiler cho thấy GC pause thấp nhưng ThreadPool queue tăng mạnh, giả thuyết tiếp theo của bạn là gì và bạn sẽ kiểm tra ra sao?
3. Tôi phản đối streaming vì muốn retry toàn bộ response dễ dàng và biết `Content-Length` trước; bạn sẽ bảo vệ hay thay đổi đề xuất như thế nào?

## Lỗi trả lời thường gặp

- Nói “đã async thì không thể có performance problem”.
- Thấy Gen 2 tăng rồi kết luận ngay GC là root cause mà không correlate telemetry.
- Chỉ đề xuất tăng memory/CPU hoặc gọi `GC.Collect()`.
- Tối ưu serializer chi tiết trước khi đo allocation và payload distribution.
- Bỏ qua cancellation, response-size limits và production load behavior.

## Thang điểm 0–10

- **0–2:** Chỉ nói chung chung về async/GC, không giải thích allocation chain hoặc cách đo.
- **3–4:** Nhận ra nhiều buffer/copies nhưng thiếu runtime mechanism hoặc production verification.
- **5–6:** Giải thích hợp lý GC/LOH pressure, có telemetry cơ bản và đề xuất streaming/projection.
- **7–8:** Phân biệt các competing hypotheses, biết đo allocation/GC/ThreadPool và thiết kế load test trước–sau.
- **9–10:** Kết nối chính xác mechanism → evidence → mitigation → trade-offs; cân nhắc error semantics, admission control, deployment verification và biết khi nào nên đổi interaction model sang asynchronous export.

# Câu 2 — Editor đã publish nhưng người dùng vẫn thấy content cũ, purge lại làm origin quá tải

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai/CDN, HTTP caching, cache invalidation, ASP.NET Core, observability, incident response, performance, SEO/web delivery

## Bối cảnh

Một marketing website dùng Optimizely CMS và ASP.NET Core. Public traffic đi qua Akamai CDN. Site có khoảng 3 triệu page views/ngày, phần lớn anonymous traffic. Các campaign pages cần cập nhật trong vòng 2 phút sau khi editor publish.

Kiến trúc đơn giản:

`Browser → Akamai → ASP.NET Core/Optimizely → content database`

Có thêm application-level cache cho một số content fragments. Team đã cấu hình `Cache-Control` khác nhau cho static assets và HTML pages, nhưng policy thay đổi qua nhiều release.

Sáng thứ Hai, editor publish thay đổi legal text trên khoảng 200 campaign pages. Incident xuất hiện:

- một số users thấy content mới ngay;
- một số users ở region khác vẫn thấy content cũ hơn 30 phút;
- hard refresh đôi lúc vẫn thấy cũ;
- support purge toàn bộ site trên CDN và content dần đúng trở lại;
- ngay sau global purge, origin request rate tăng khoảng 8 lần, p95 từ 350 ms lên 4.5 giây và một số requests trả 503;
- Optimizely editors vẫn thấy preview đúng trong CMS;
- team tranh luận ba root cause: Akamai stale cache, Optimizely object cache, hoặc browser cache;
- logs hiện tại không ghi rõ cache status, content version hoặc publish event correlation.

Không có bằng chứng chắc chắn root cause duy nhất tại thời điểm bạn vào incident.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào để vừa giảm user/business impact, vừa tìm đúng cache layer đang phục vụ stale content, tránh “purge everything” gây thundering herd lên origin, rồi thiết kế cơ chế publish/invalidation và observability nào để giảm khả năng tái diễn?

## Câu hỏi làm rõ nên cân nhắc

1. HTML response hiện có `Cache-Control`, `Surrogate-Control`, `ETag`, `Vary`, cookies hoặc cache-key rules nào ở Akamai?
2. Stale content có correlate theo URL, region/POP, authentication/cookie state hay một content type cụ thể không?
3. Optimizely publish event hiện có trigger invalidation/purge nào, và purge là theo URL/tag/content dependency hay global?
4. Origin/app cache dùng key gì và invalidation khi publish có chạy trên mọi application instance không?
5. Akamai response headers/logs có cho biết cache hit/miss, age, cache key hoặc revalidation result cho các request stale không?

## Gợi ý tư duy

### Gợi ý 1

Đừng coi “cache” là một layer. Hãy vẽ từng cache boundary và tìm evidence cho **response nào được tạo ở đâu, lúc nào, từ content version nào**.

### Gợi ý 2

Global purge là một remediation rất mạnh nhưng có thể biến cache incident thành origin-capacity incident. Hãy nghĩ đến targeted invalidation, stale-while-revalidate/collapse behavior và rate/capacity protection.

### Gợi ý 3

Một publish pipeline tốt cần mapping từ content thay đổi → affected URLs/cache tags → invalidation signal → verification. Không nhất thiết mọi publish đều phải purge toàn bộ HTML.

## Cấu trúc trả lời đề xuất

1. Xác định business impact và phạm vi stale content.
2. Stabilize bằng biện pháp có blast radius nhỏ nhất.
3. Thu evidence ở browser/CDN/origin/CMS layers.
4. Xây 3–5 hypotheses cạnh tranh và cách falsify từng hypothesis.
5. Tìm root cause/failure window cụ thể.
6. Sửa ngắn hạn và verify theo region/URL/content version.
7. Thiết kế invalidation/publish flow dài hạn.
8. Bổ sung load protection, tests, dashboards và alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu từ impact/stabilization, không nhảy thẳng vào config change.
- Phân biệt browser cache, CDN edge cache, application cache và CMS content state.
- Dùng response headers/CDN diagnostics/origin logs để xác định layer stale.
- Tránh global purge mặc định; ưu tiên targeted invalidation nếu có thể.
- Nhận ra purge lớn có thể tạo cache miss storm lên origin.
- Thiết kế verification sau invalidation, không chỉ “API purge trả 200”.

### Điểm cộng

- Đề cập cache-key correctness (`Vary`, query string, cookies, host/language/market dimensions).
- Đề cập TTL/revalidation và stale policies một cách có điều kiện.
- Đề xuất cache tags/surrogate keys hoặc mapping content → affected URLs nếu platform hỗ trợ.
- Có origin rate limiting/capacity/autoscale/warmup strategy phù hợp.
- Correlate publish event ID/content version với purge request và observed edge version.

### Senior+

- Nhận ra invalidation là distributed-system workflow có partial failure và cần retry/idempotency/audit.
- Thiết kế canary verification nhiều POP/regions thay vì chỉ kiểm tra từ office network.
- Cân nhắc SEO impact của stale legal/canonical/meta content và crawler caching khi relevant.
- Phân biệt static immutable assets (versioned long TTL) với mutable HTML/content APIs.

## Hướng giải quyết tham khảo

Tôi sẽ xử lý đây như một incident phân tán qua nhiều cache layers, không giả định Akamai hay Optimizely là thủ phạm từ đầu.

**1. Impact và stabilization.** Đầu tiên xác định affected campaign/regions và mức độ business/legal impact. Nếu legal text sai là critical, mục tiêu là phục vụ đúng content nhanh nhưng không làm origin sập. Thay vì global purge ngay, tôi sẽ ưu tiên purge/invalidate tập URL bị ảnh hưởng hoặc cache tag/content group nếu Akamai configuration hỗ trợ. Nếu origin đã bị overload sau purge, có thể tạm giảm phạm vi invalidation, tăng capacity trong safe limits, bật/cấu hình request collapsing hoặc stale policy phù hợp với risk, và bảo vệ non-critical traffic. Với legal content, không nên tiếp tục serve stale chỉ để giữ availability nếu compliance requirement cấm điều đó; decision phải explicit.

**2. Thu evidence theo layer.** Với một URL stale và một URL correct, lấy response từ nhiều regions/POPs. Tôi muốn biết `Age`, cache-hit/miss diagnostic headers, `Cache-Control`, `ETag`/`Last-Modified`, `Vary`, cookies, query strings và cache key dimensions. Nếu một edge trả response có `Age` 1800 và origin không hề nhận request, đó là bằng chứng mạnh ở CDN layer. Nếu edge miss nhưng origin vẫn trả old content, đi xuống app/CMS cache.

Tại origin, log cần content ID/version/published timestamp, hostname/instance và application-cache hit/miss. Nếu origin instance A trả version mới còn B trả cũ, app cache invalidation có thể chỉ chạy local. Nếu tất cả origin instances trả mới nhưng một số POP vẫn trả cũ, tập trung Akamai purge propagation/cache-key mismatch. Nếu browser trả cũ nhưng `curl`/clean client qua cùng edge trả mới, browser cache/service worker có thể là layer cần xem.

**3. Hypotheses cạnh tranh.** Ví dụ:

- H1: purge không bao phủ mọi cache key/URL variant (language/query/host/cookie).
- H2: Akamai TTL hoặc stale policy giữ object cũ vì invalidation signal không tới một số POP.
- H3: Optimizely/application cache invalidation chỉ xảy ra ở một instance hoặc key dependency sai.
- H4: browser cache/service worker giữ HTML quá lâu.
- H5: publish tạo content mới trong CMS nhưng delivery path đọc một published version khác do routing/language/market rule.

Mỗi hypothesis phải có evidence để falsify, không chỉ “thử clear cache xem sao”.

**4. Root-cause remediation.** Giả sử evidence cho thấy publish pipeline chỉ purge canonical URL nhưng Akamai cache key có language/market variants, fix phải nằm ở mapping content → variants. Nếu app cache mới là root cause, sửa invalidation propagation/distributed cache key semantics. Nếu browser headers sai, giảm/mô hình hóa TTL của mutable HTML và dùng revalidation. Không nên giữ một kết luận chung “CDN cache lỗi”.

**5. Long-term design.** Tôi sẽ phân loại asset:

- fingerprinted static assets: long TTL + immutable;
- mutable HTML/content: TTL ngắn hơn hoặc revalidation, tùy freshness SLO;
- content fragment/API: cache policy theo volatility và personalization.

Publish event tạo một stable event/correlation ID. Một invalidation component map content ID sang affected URLs/tags rồi gửi purge idempotently, ghi trạng thái `Requested/Succeeded/Failed`, retry transient failures và verify representative URLs. Nếu 200 pages thay đổi, batching/tag invalidation tốt hơn 200×N calls hoặc global purge.

Origin phải chịu được realistic miss burst. Load test cold-cache scenario, theo dõi cache hit ratio, origin RPS, p95/p99, 5xx, CPU, CMS/database dependency latency. Có thể dùng warmup có kiểm soát cho critical URLs sau purge, nhưng không nên prefetch toàn site mù quáng.

**6. Observability.** Tôi muốn dashboard có publish count, invalidation latency p95, purge failure/retry, cache hit ratio theo region, origin request amplification, stale-verification failures và content-version mismatch. Logs/traces mang `ContentId`, version, publish correlation ID và cache layer result nhưng tránh high-cardinality metrics không kiểm soát. Alert không chỉ khi origin 5xx; alert khi freshness SLO >2 phút bị vi phạm.

**7. Testing.** Integration test publish → invalidate → fetch representative variants; config test cho cache keys/headers; load test cold-cache/global-miss scenario; failure-path test giả lập purge API timeout/partial failure; E2E test nhiều locale/anonymous-auth variants. Rollout cache-policy changes nhỏ và quan sát trước khi mở rộng.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng global purge vì chính symptom cho thấy purge toàn site làm origin bị cache-miss storm. Đầu tiên tôi xác định blast radius và nếu legal text là critical thì targeted invalidate các URLs hoặc cache tags bị ảnh hưởng, đồng thời theo dõi origin capacity.

Sau đó tôi lấy cùng URL từ nhiều POP và so sánh cache diagnostics như hit/miss, `Age`, `Cache-Control`, `Vary`, cache key, rồi correlate với origin logs. Nếu edge trả object cũ mà origin không nhận request thì nghiêng về CDN. Nếu edge miss nhưng origin trả cũ, tôi kiểm tra Optimizely/application cache theo instance và content version. Nếu clean client đúng nhưng browser cũ thì mới tập trung browser/service worker. Tôi muốn ít nhất vài hypotheses cạnh tranh chứ không gọi mọi thứ là ‘cache issue’.

Sau khi xác định root cause, tôi sửa đúng layer. Dài hạn, publish event nên map content sang affected URLs/tags, gửi invalidation idempotently, retry failure và có verification sau purge. Static fingerprinted assets có thể long TTL; mutable HTML phải có freshness policy phù hợp. Tôi cũng load test cold-cache burst để chắc origin chịu được một đợt miss hợp lý.

Telemetry cần nối publish ID/content version với invalidation latency, edge cache status, origin traffic và freshness verification. Mục tiêu là biết content mới thực sự tới user trong SLO 2 phút, chứ không chỉ biết purge API đã trả success.”

## Câu hỏi đào sâu

1. Nếu Akamai không hỗ trợ cache tags theo cách hệ thống hiện tại dùng, bạn sẽ thiết kế targeted invalidation thế nào mà không phải purge toàn site?
2. Nếu origin chỉ chịu được 2× traffic bình thường nhưng một legal update bắt buộc invalidate hàng nghìn URLs ngay lập tức, bạn ưu tiên consistency và availability ra sao?
3. Tôi cho rằng TTL 30 giây cho mọi HTML sẽ loại bỏ nhu cầu invalidation; bạn đồng ý hay phản đối, và dựa trên dữ liệu nào?

## Lỗi trả lời thường gặp

- Quy mọi stale content cho CDN mà không kiểm tra origin/app/browser layers.
- “Purge all” như default fix mà không tính origin amplification.
- Chỉ nói giảm TTL mà không xem cache keys, invalidation propagation và freshness SLO.
- Không có verification sau publish/purge.
- Không đưa observability/content version vào thiết kế.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất clear cache/restart app.
- **3–4:** Biết có nhiều cache layers nhưng investigation thiếu evidence hoặc hypotheses.
- **5–6:** Có incident flow hợp lý, targeted purge và cache-header/CDN diagnostics.
- **7–8:** Thiết kế được publish→invalidation→verification, cold-cache protection và observability đầy đủ.
- **9–10:** Xử lý tốt trade-off freshness/availability/origin capacity, partial failure của invalidation workflow, multi-region verification và long-term cache architecture mà không over-engineer.

# Câu 3 — Modernize hệ thống .NET Framework 4.5 mà không biến migration thành một rewrite nhiều năm

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework 4.5 → .NET 8, IIS/Windows Server, ASP.NET MVC, legacy frontend, SQL Server, deployment, compatibility, incremental migration, testing, observability, architecture trade-offs

## Bối cảnh

Một internal enterprise portal đã chạy hơn 8 năm:

- ASP.NET MVC trên .NET Framework 4.5;
- host trên IIS/Windows Server;
- SQL Server dùng chung một database lớn;
- khoảng 35 modules: employee profile, approvals, timesheet, document metadata, admin, reporting;
- server-rendered views pha nhiều jQuery và một phần AngularJS cũ;
- authentication hiện tích hợp enterprise identity theo cơ chế legacy;
- có 6 third-party libraries cũ, trong đó một số chỉ support .NET Framework;
- deployment bằng TeamCity + Octopus Deploy;
- test automation ít, chủ yếu manual regression;
- release hiện tại mỗi 2 tuần, downtime khoảng 10 phút;
- production incidents thường khó chẩn đoán vì logging không đồng nhất.

Business muốn trong 12–18 tháng:

- support .NET 8+ cho phần lớn active development;
- giảm deployment risk;
- cải thiện observability và automated testing;
- tiếp tục ship features trong quá trình migration;
- không chấp nhận freeze product một năm để rewrite;
- chưa có requirement scale độc lập từng module;
- team khoảng 8 developers, mạnh .NET/SQL nhưng DevOps platform capacity có hạn.

Có ba đề xuất trong team:

1. **Big-bang rewrite** toàn bộ thành React + .NET 8 microservices trên Kubernetes.
2. **In-place upgrade** toàn solution từ .NET Framework 4.5 lên .NET 8 trong một branch lớn rồi cutover.
3. **Incremental modernization**: giữ hệ thống cũ chạy, thiết lập boundary/routing để migrate từng vertical/module sang .NET 8 theo thời gian.

Bạn chưa biết phương án 3 chắc chắn là tốt nhất; cần đánh giá dựa trên constraint thực tế.

## Câu hỏi chính

Bạn sẽ phân tích và đề xuất modernization strategy như thế nào? Hãy nêu các thông tin cần làm rõ, cách chia migration thành các bước có thể ship được, cách xử lý shared database, authentication, third-party dependencies, frontend legacy, CI/CD, rollback và observability; đồng thời giải thích khi nào bạn **không** chọn incremental migration hoặc khi nào kiến trúc phức tạp hơn như microservices/Kubernetes thực sự đáng giá.

## Câu hỏi làm rõ nên cân nhắc

1. Những modules nào thay đổi thường xuyên, tạo nhiều incidents hoặc mang business value cao nhất?
2. Dependency graph giữa modules/database tables hiện chặt đến mức nào, có shared session/static state/in-process integration nào không?
3. Sáu libraries chỉ support .NET Framework đang phục vụ capability gì, có replacement/source access/vendor roadmap không?
4. Identity/session hiện được triển khai ra sao và có thể dùng token/cookie sharing hoặc một transition boundary an toàn không?
5. Deployment/hosting target bắt buộc là Windows/IIS hay organization đã chuẩn hóa App Service/Linux/container ở mức nào?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu từ target architecture. Bắt đầu từ **dependency inventory, business risk, deployability và migration seams**.

### Gợi ý 2

Một migration tốt tạo ra intermediate states có thể chạy production, đo được và rollback được. “Cuối cùng đẹp” nhưng 12 tháng không ship được là một failure mode.

### Gợi ý 3

Shared database không bắt buộc phải được tách ngay. Có thể trước hết tách ownership/code boundary, rồi chỉ tách storage khi có lợi ích rõ và invariant cho phép.

## Cấu trúc trả lời đề xuất

1. Làm rõ business/SLO/operational constraints.
2. Inventory code/dependencies/data/integration/deployment.
3. Định nghĩa modernization goals và success metrics.
4. So sánh big bang, in-place và incremental theo risk/cost/time-to-value.
5. Chọn pilot slice và migration seam.
6. Thiết kế compatibility cho identity/data/routing/contracts.
7. Xây testing + observability + CI/CD foundation.
8. Lập rollout/rollback theo từng slice.
9. Định nghĩa tiêu chí khi cần thay đổi strategy hoặc thêm architecture complexity.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite/microservices/Kubernetes là modernization.
- Có dependency inventory và prioritization trước migration.
- Có cách tiếp tục release features trong quá trình chuyển đổi.
- Có explicit compatibility/rollback strategy.
- Xử lý shared DB pragmatically, không bắt buộc database-per-service ngay.
- Đưa automated tests và observability vào migration foundation.
- Nhận diện third-party dependencies/identity là blockers cần spike sớm.

### Điểm cộng

- Đề xuất pilot module low-coupling nhưng đủ representative.
- Có routing seam/reverse proxy hoặc module boundary rõ để legacy và new app coexist.
- Dùng expand/contract cho schema khi old/new versions cùng chạy.
- Đề xuất characterization/integration/E2E tests trước khi refactor code khó hiểu.
- Giữ TeamCity/Octopus nếu vẫn đáp ứng needs thay vì đổi CI/CD tool cùng lúc không cần thiết.

### Senior+

- Thiết kế strangler/incremental migration mà không tạo “distributed monolith”.
- Biết khi nào dùng shared DB transitional ownership và cách ngăn new code tiếp tục tăng coupling.
- Có decision criteria cho App Service/IIS/container/Kubernetes dựa trên operational requirements.
- Có measurable exit criteria cho mỗi migration wave và plan retire legacy code.
- Phân biệt technical modernization với frontend rewrite; không buộc React migration nếu jQuery/AngularJS area ổn định và ít value.

## Hướng giải quyết tham khảo

Tôi sẽ không chọn phương án dựa trên “modern stack” trước. Với constraint 8 developers, phải tiếp tục ship features, ít automated tests và chưa có requirement independent scaling, big-bang React + microservices + Kubernetes tạo quá nhiều simultaneous change: runtime, architecture, UI, deployment platform, data boundaries và operations. Nó có thể đúng trong một số tổ chức, nhưng ở đây risk rất cao mà business driver chưa chứng minh complexity đó.

In-place upgrade toàn solution trên một branch lớn cũng có rủi ro: .NET Framework 4.5 → .NET 8 không phải một target-framework edit đơn giản. ASP.NET hosting model, libraries, authentication, configuration, APIs và legacy packages có incompatibilities. Long-lived branch tạo merge drift và cutover blast radius lớn.

Tôi có xu hướng **incremental modernization**, nhưng trước khi commit strategy tôi làm discovery 2–4 tuần với output cụ thể:

- dependency graph theo module/project/package;
- inventory third-party libraries và replacement options;
- database table/stored procedure ownership và cross-module writes;
- authentication/session dependencies;
- IIS-specific behavior, filesystem, scheduled jobs, COM/native dependencies nếu có;
- production traffic/error/hotspot map;
- release/incidents theo module;
- test coverage ở business-critical flows.

### Chọn migration seam

Tôi chọn pilot có business value nhưng coupling vừa phải, ví dụ một approval/reporting module không phụ thuộc sâu vào in-process session. Mục tiêu pilot là chứng minh coexistence, CI/CD, observability và rollback — không phải chứng minh “microservice architecture”.

Có thể đặt reverse proxy/routing boundary: một số routes vẫn tới legacy IIS app, routes migrated tới .NET 8 app. Nếu organization thuận tiện Windows/IIS trước, .NET 8 app có thể host IIS ban đầu; chuyển Linux/App Service/container là decision riêng. Giảm số dimensions thay đổi cùng lúc thường giảm migration risk.

### Shared database

Tôi không tách database ngay chỉ vì code được tách. Trong transition, new app có thể dùng cùng SQL Server nhưng cần explicit ownership: module mới chỉ được đọc/write tables/contracts thuộc slice; cross-module access phải qua documented APIs/application layer khi feasible. Schema change dùng expand/contract để old và new code coexist: add new nullable column/table first, deploy code compatible, backfill, switch reads/writes, rồi remove old schema ở release sau.

Nếu sau này independent deployment bị shared-schema lockstep cản trở hoặc scale/security/ownership requirement mạnh, lúc đó mới xem database separation/eventing. Không nên tạo distributed transaction problem trước khi business cần.

### Identity

Identity là spike sớm. Tôi cần biết cookie format, session, claims và enterprise provider. Có thể dùng shared authentication boundary/token exchange hoặc một gateway/BFF transition tùy stack. Goal là user không phải login lại giữa legacy/new routes và authorization semantics không lệch. Không copy blindly legacy claims trust sang app mới; test resource-level authorization.

### Third-party dependencies

Với six Framework-only libraries, phân loại:

1. replace bằng supported package;
2. upgrade vendor version;
3. isolate capability sau một adapter/process/API tạm thời;
4. nếu không thể thay và business-critical, module đó ở legacy lâu hơn.

Một blocker package không nên giữ toàn bộ system hostage nếu boundary cho phép isolate.

### Frontend

Tôi không rewrite toàn bộ jQuery/AngularJS sang React chỉ để đồng bộ “modernization”. Với pages đang ổn định, có thể giữ UI và đổi backend trước. Với module mới hoặc area có UX/maintainability pain rõ, Vue/React có thể dùng dần. Frontend migration cần own value, tests và browser telemetry.

### Testing và observability foundation

Trước khi migrate risky flow, tạo characterization tests ở boundaries: integration tests cho SQL/API, contract tests giữa legacy/new, Playwright E2E cho top business journeys. Không cần đạt 90% unit coverage rồi mới bắt đầu.

Chuẩn hóa structured logs, correlation ID, request/dependency telemetry trong cả legacy/new nếu có thể. Dashboard theo route/version giúp so sánh error rate/p95 giữa old/new path. Đây là safety net cho incremental cutover.

### CI/CD

TeamCity + Octopus không cần bị thay chỉ vì runtime đổi nếu chúng vẫn build/deploy/release tốt. Tôi thêm pipeline cho .NET 8 app, automated tests, artifact versioning, environment config/secrets, health verification và rollback. Tool migration chỉ làm khi có operational/business benefit riêng.

### Rollout

Mỗi slice:

1. migrate behind route/feature flag nếu phù hợp;
2. deploy new app dark/no traffic;
3. smoke/integration verify;
4. shift small internal/canary traffic;
5. compare logs/errors/latency/business outcomes;
6. increase traffic;
7. rollback routing nếu regression;
8. khi stable mới retire legacy route/code.

Success metrics có thể gồm % routes/modules trên .NET 8, deployment failure rate, lead time, incident rate, p95, automated critical-flow coverage và number of Framework-only blockers.

### Khi không chọn incremental

Tôi có thể chọn in-place hơn nếu codebase thực tế là một ứng dụng nhỏ, dependencies đã support modern .NET, automated tests tốt và upgrade tooling cho thấy phần lớn compatible — lúc đó coexistence layer có thể phức tạp hơn cần thiết.

Big-bang rewrite chỉ hợp lý nếu current system gần như không thể sửa, requirements sắp thay hoàn toàn, business chấp nhận parallel product investment và có migration/cutover budget lớn. Nhưng rewrite vẫn phải giải quyết data migration, behavior parity và rollout risk.

Microservices/Kubernetes chỉ đáng giá khi có drivers như independent team ownership/deploy cadence, isolation, distinct scaling/reliability needs hoặc organizational platform maturity. Với 8 developers và chưa có independent-scale requirement, modular monolith hoặc vài deployable apps thường có cost thấp hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi không coi modernization là đồng nghĩa với rewrite sang microservices/Kubernetes. Với system này, rủi ro lớn nhất là thay runtime, architecture, frontend, deployment platform và database boundary cùng lúc trong khi test automation còn yếu và team chỉ 8 người.

Tôi sẽ bắt đầu bằng dependency inventory: modules, Framework-only packages, shared DB writes, identity/session, IIS-specific dependencies và production hotspots. Sau đó chọn một pilot module coupling vừa phải để chứng minh coexistence. Khả năng cao tôi dùng incremental route-by-route/module-by-module migration sang .NET 8, có reverse-proxy/routing seam để legacy và new app cùng chạy.

Tôi không tách SQL Server ngay. Trong transition có thể dùng shared DB nhưng phải đặt ownership boundary và dùng expand/contract schema để old/new versions tương thích. Identity và six legacy libraries là spikes sớm vì có thể quyết định migration order. Frontend cũng không bắt buộc rewrite toàn bộ; area ổn định có thể để nguyên, area có business value mới migrate Vue/React khi đáng giá.

Trước cutover tôi thêm characterization/integration tests, Playwright cho critical journeys, structured logs và telemetry theo route/version. TeamCity/Octopus vẫn dùng nếu đáp ứng nhu cầu; đổi CI/CD tool không phải mục tiêu tự thân.

Mỗi slice deploy nhỏ, canary/verify rồi tăng traffic; rollback bằng routing về legacy. Tôi chỉ chọn microservices/Kubernetes nếu sau này có requirement independent scaling, isolation hoặc ownership đủ mạnh để trả chi phí vận hành. Modernization thành công với tôi là giảm risk và tăng delivery capability qua từng wave, không phải đạt một architecture diagram đẹp.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên cần ghi vào 12 tables đang được 5 legacy modules cùng sửa trực tiếp, bạn sẽ tạo migration seam thế nào mà không giả vờ boundary đã tồn tại?
2. Tôi phản đối shared database vì cho rằng “đã tách app thì phải database-per-service”; bạn sẽ bảo vệ hoặc điều chỉnh approach dựa trên tiêu chí nào?
3. Nếu một Framework-only library business-critical không có replacement trong 18 tháng tới, strategy tổng thể của bạn thay đổi ra sao?

## Lỗi trả lời thường gặp

- Chọn microservices/Kubernetes vì “hiện đại hơn” mà không có driver.
- Đề xuất rewrite toàn bộ frontend/backend cùng lúc và bỏ qua rollout risk.
- Cố tách database ngay trước khi hiểu invariants/ownership.
- Chỉ nói về code migration mà không xử lý identity, third-party packages, CI/CD, testing và rollback.
- Xây architecture đích rất đẹp nhưng không có intermediate production states có thể ship.

## Thang điểm 0–10

- **0–2:** Chỉ chọn một stack/architecture mới, gần như không bàn migration risk.
- **3–4:** Có incremental idea nhưng thiếu dependency discovery, data/auth compatibility hoặc rollback.
- **5–6:** Có strategy khả thi, pilot, testing/observability và shared-DB transition hợp lý.
- **7–8:** So sánh tốt các options, thiết kế coexistence/expand-contract/canary và decision criteria cho complexity.
- **9–10:** Thể hiện strong architecture judgment: tối ưu time-to-value và reversibility, xử lý blockers/organizational capacity, biết khi nào đơn giản hơn tốt hơn và khi nào requirements thực sự biện minh cho microservices/Kubernetes/database separation.
