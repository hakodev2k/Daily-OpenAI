# Câu 1 — Vì sao API async vẫn nghẽn Thread Pool?

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** async/await, Thread Pool, I/O, ASP.NET Core, diagnosis, observability

## Bối cảnh

Một ASP.NET Core API gọi SQL Server và Microsoft Graph. Sau một release, p95 latency tăng từ khoảng 300 ms lên vài giây khi traffic cao. CPU chỉ 45–60%, DB không có query nổi bật, nhưng request queue tăng. Code hầu hết khai báo `async`, tuy nhiên một số helper dùng `.Result`, `.Wait()` và có đoạn `Task.Run(() => SomeAsyncCall()).Result`. Team kết luận: “method đã async nên không thể thiếu thread”.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong từ lúc một request gặp I/O `await` đến khi continuation chạy lại; vì sao ứng dụng vẫn có thể bị Thread Pool starvation dù CPU chưa đầy; misconception nào đang tồn tại; production risk là gì; và bạn sẽ chứng minh giả thuyết bằng evidence nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint nào tăng latency và thay đổi nào vừa deploy?
- Có synchronous blocking ở request path hoặc library nội bộ không?
- Dependency latency và connection-pool state có thay đổi không?
- Thread count, queue length, request rate và GC có biến động cùng thời điểm không?
- Có timeout/cancellation policy hay retry nào khuếch đại tải không?

## Gợi ý tư duy

- **Gợi ý 1:** `async` không đồng nghĩa với “không bao giờ cần Thread Pool”.
- **Gợi ý 2:** Phân biệt thời gian chờ I/O với code continuation và synchronous blocking.
- **Gợi ý 3:** Tìm mối quan hệ giữa blocking, Thread Pool growth, queued work và latency thay vì chỉ nhìn CPU.

## Cấu trúc trả lời đề xuất

1. Xác nhận symptom và phạm vi.
2. Mô tả execution model của request + `await`.
3. Chỉ ra tác động của sync-over-async.
4. Đưa ra các giả thuyết cạnh tranh.
5. Nêu evidence cần thu thập.
6. Mitigate trước, sửa sau.
7. Test dưới load.
8. Theo dõi regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `await` trên I/O chưa hoàn tất không giữ một thread chỉ để chờ; continuation cần execution resource khi operation hoàn tất.
- `.Result`/`.Wait()` có thể block Thread Pool thread và giảm throughput.
- ASP.NET Core không có request `SynchronizationContext` kiểu ASP.NET cũ, nên không được mặc định giải thích mọi trường hợp bằng classic deadlock; starvation/throughput collapse là vấn đề thực tế hơn trong scenario này.
- CPU thấp không loại trừ Thread Pool starvation.
- Phải đo trước khi kết luận.

### Điểm cộng

- Kiểm tra `dotnet-counters`, traces, thread stacks, dependency spans, connection pools.
- Nhắc retry storm, timeout mismatch và downstream saturation như giả thuyết khác.
- Propagate `CancellationToken` end-to-end.

### Nâng cao

- Phân biệt starvation với lock contention, DB pool exhaustion và external dependency latency.
- Giải thích vì sao Thread Pool có thể tăng worker dần nhưng vẫn không theo kịp burst blocking work.

## Hướng giải quyết tham khảo

**Giả định:** bottleneck xuất hiện sau release và request path mới có sync-over-async.

I/O-based async cho phép thread quay lại pool trong lúc OS/network/database operation chưa hoàn tất. Khi I/O hoàn tất, continuation được schedule để tiếp tục xử lý. Nếu request path gọi `.Result` hoặc `.Wait()`, worker thread có thể bị giữ trong lúc chờ một operation vốn có thể hoàn tất bất đồng bộ. Dưới concurrency cao, nhiều worker bị block; work mới và continuation phải chờ, khiến latency và queue tăng dù CPU chưa đạt 100%.

Không nên kết luận chỉ từ code review. So sánh trước/sau release: request latency, Thread Pool thread count/queue, exception/timeout rate, dependency latency, DB/HTTP connection pools và traces. Capture stack/sample khi incident xảy ra để tìm blocking frames.

Mitigation có thể rollback release hoặc giảm traffic/concurrency nếu impact lớn. Fix chính là async-all-the-way: `await` thay `.Result/.Wait()`, không dùng `Task.Run` để bọc I/O async, propagate cancellation và đặt timeout/retry có budget. Load test phải mô phỏng downstream latency vì lỗi thường không lộ ở happy path.

Nếu evidence cho thấy threads khỏe nhưng DB connection pool cạn hoặc Graph latency tăng, recommendation phải đổi sang xử lý dependency/pool thay vì “sửa Thread Pool”.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa kết luận Thread Pool starvation chỉ vì thấy `.Result`; trước tiên tôi sẽ correlate latency với thread-pool queue, thread count, dependency latency và traces. Về cơ chế, khi một I/O `await` chưa hoàn tất, request không cần giữ worker thread chỉ để chờ. Khi I/O xong, continuation cần được chạy tiếp. Nếu chúng ta dùng `.Result` hoặc `.Wait()`, worker có thể bị block. Khi nhiều request cùng làm vậy, available workers giảm, continuation và request mới xếp hàng, nên latency có thể tăng mạnh dù CPU chỉ khoảng 50%. Tôi sẽ rollback hoặc giảm tải nếu impact cao, sau đó chuyển path sang async-all-the-way, bỏ `Task.Run` quanh I/O, propagate cancellation và kiểm tra retry/timeout. Cuối cùng tôi load-test với injected downstream latency và theo dõi queue, p95/p99, thread count và dependency spans. Nếu metrics lại chỉ ra DB pool exhaustion hoặc Graph slowdown thì tôi sẽ đổi hướng điều tra.”

## Câu hỏi đào sâu

1. Vì sao `Task.Run` phù hợp hơn với một số CPU-bound work nhưng thường không cần thiết cho I/O async?
2. Nếu bỏ toàn bộ `.Result` mà latency vẫn cao, ba giả thuyết tiếp theo của bạn là gì?
3. Có nên tăng `ThreadPool.SetMinThreads` để chữa incident này không? Khi nào nó chỉ là mitigation hoặc thậm chí che mất root cause?

## Lỗi trả lời thường gặp

- Nói mọi `.Result` trong ASP.NET Core chắc chắn gây deadlock.
- Cho rằng `async` nghĩa là code không sử dụng thread.
- Chỉ nhìn CPU rồi loại bỏ starvation.
- Tăng min threads ngay mà không tìm blocking source.
- Không load-test failure/slow-dependency path.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.5**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **1.5**
- Communication: đánh giá xuyên suốt các mục trên; câu trả lời tốt phải rõ assumption và evidence.

# Câu 2 — Incident duplicate Hangfire job gây gửi email hai lần

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** Hangfire, idempotency, concurrency, database consistency, incident response

## Bối cảnh

Một hệ thống .NET dùng Hangfire để xử lý offboarding. Job đọc cấu hình trong PostgreSQL, cập nhật trạng thái và gọi Exchange Online/Microsoft Graph để thay đổi mailbox rồi gửi notification. Sau khi scale từ một lên ba app instances, một số người dùng nhận notification hai lần; hiếm hơn, trạng thái DB cho biết hoàn tất nhưng external operation chưa thực hiện đầy đủ. Retry đang bật. Không được phép đơn giản tắt retry vì external APIs có transient failures.

## Câu hỏi chính

Bạn sẽ xử lý incident theo thứ tự nào, xác minh các giả thuyết ra sao, và thiết kế lại workflow thế nào để retry/concurrency không tạo duplicate side effects hoặc trạng thái “DB success, external failure”?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate là cùng Hangfire job ID, hai enqueue khác nhau hay hai business operation khác nhau?
- External APIs nào hỗ trợ đọc trạng thái hiện tại hoặc operation có tính idempotent tự nhiên?
- DB update diễn ra trước hay sau external side effect?
- Retry policy và timeout hiện tại là gì?
- Business chấp nhận at-least-once processing nhưng exactly-once business effect ở mức nào?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “job chạy bao nhiêu lần” khỏi “business side effect xảy ra bao nhiêu lần”.
- **Gợi ý 2:** Retry và idempotency phải được thiết kế cùng nhau.
- **Gợi ý 3:** Không thể tạo một ACID transaction đơn giản bao trùm PostgreSQL và arbitrary external API; cần explicit state machine/reconciliation.

## Cấu trúc trả lời đề xuất

1. Impact và blast radius.
2. Stabilization.
3. Evidence + timeline.
4. Các giả thuyết.
5. Root-cause verification.
6. Idempotency/state design.
7. Failure recovery/reconciliation.
8. Monitoring và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định duplicate là do Hangfire “chạy sai”; kiểm tra duplicate enqueue, retries, timeout và concurrent business commands.
- Business operation cần stable idempotency key.
- Side effects phải có durable state và retry-safe semantics.
- Không claim distributed exactly-once nếu external system không hỗ trợ transaction chung.

### Điểm cộng

- Unique constraint cho business operation/idempotency key.
- State machine như Pending → Processing → ExternalApplied → Completed/Failed.
- Reconciliation job kiểm tra ambiguous outcomes.
- Notification tách riêng và dedupe theo business event.

### Nâng cao

- Optimistic concurrency/atomic conditional update để claim work.
- Outbox cho reliable publication của internal events.
- Phân biệt command idempotency, consumer dedupe và external reconciliation.

## Hướng giải quyết tham khảo

Đầu tiên xác định blast radius và ngăn duplicate mới bằng cách tạm pause loại job bị lỗi hoặc giảm concurrency có kiểm soát, không xóa retry toàn hệ thống. Từ Hangfire storage/logs/traces, xác định duplicate đến từ retry cùng job, enqueue hai lần, timeout sau khi external API đã thành công nhưng client không nhận response, hay nhiều app instances cùng tạo business operation.

Thiết kế business operation có `OperationId`/idempotency key ổn định và unique constraint. Worker atomically claim operation thay vì dựa vào in-memory lock. Mỗi external step có durable state. Nếu API call timeout ở trạng thái không biết đã thành công hay chưa, không blind retry ngay: nếu có thể, query external state để reconcile. Notification nên có dedupe key riêng và chỉ phát khi prerequisite state đã được xác nhận.

DB transaction có thể đảm bảo internal state/outbox atomically, nhưng không biến Graph/Exchange call thành cùng một transaction. Vì vậy workflow phải chấp nhận failure giữa các bước và có compensation/reconciliation phù hợp.

Test bằng concurrent enqueue, worker crash sau external success trước DB update, transient 429/5xx, timeout ambiguous, restart và retry. Theo dõi duplicate-prevented count, retries, stuck operations, reconciliation outcomes và age of oldest incomplete operation.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng việc tắt retry vì retry đang bảo vệ transient failure. Tôi sẽ xác định duplicate là duplicate enqueue, retry hay concurrent execution của cùng business operation. Sau đó tôi dùng một stable operation ID có unique constraint để biến business command thành idempotent. Worker claim operation bằng atomic DB transition; từng external step được lưu durable state. Điểm khó là timeout: request có thể đã thành công ở Exchange nhưng client không biết, nên nếu API cho phép đọc trạng thái tôi sẽ reconcile trước khi retry. Internal event/notification có thể dùng outbox và dedupe key. Tôi không gọi đây là exactly-once distributed transaction vì DB và external API không cùng transaction boundary. Tôi sẽ test crash ở từng boundary, concurrent workers, 429/5xx và ambiguous timeout; production alert trên stuck operations, retry rate và duplicate prevention.”

## Câu hỏi đào sâu

1. `DisableConcurrentExecution` có đủ để bảo đảm business idempotency không? Vì sao?
2. Nếu external API không hỗ trợ idempotency key và cũng khó query trạng thái, bạn thiết kế recovery thế nào?
3. Outbox giải quyết vấn đề gì và không giải quyết vấn đề gì trong workflow này?

## Lỗi trả lời thường gặp

- Tắt retry để “hết duplicate”.
- Dùng static/in-memory lock trong multi-instance deployment.
- Claim exactly-once end-to-end mà không nêu transaction boundary.
- Không xử lý crash giữa external success và DB commit.
- Không có reconciliation cho ambiguous outcome.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 3 — Thiết kế AI code-review agent có quyền truy cập repository

**Loại câu hỏi:** AI engineering / security decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** AI agents, context engineering, tool permissions, deterministic validation, evaluation, auditability

## Bối cảnh

Team muốn xây một AI agent review pull request cho các dự án .NET. Agent có thể đọc diff, repository instructions, chạy test và static analysis, rồi đề xuất review comments. Sau pilot, team muốn cho agent tự post comment lên PR và có khả năng đọc thêm file liên quan. Repository có thể chứa secrets accidentally committed, untrusted text trong issue/code/comments và project-specific instructions. Mục tiêu là tăng review coverage nhưng không để model tự ý sửa code, leak dữ liệu hoặc bị prompt injection dẫn dắt.

## Câu hỏi chính

Hãy thiết kế workflow production-ready cho agent này: vì sao cần AI, phần nào phải deterministic, context nào được cấp, tool permissions ra sao, output được validate thế nào, cách phát hiện hallucination/prompt injection, đánh giá chất lượng, fallback, audit và monitoring như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay có quyền push/merge?
- Repository là public hay private và dữ liệu nào bị cấm gửi ra model provider?
- Latency/cost budget cho mỗi PR là bao nhiêu?
- Review quality hiện được đo bằng tiêu chí nào?
- Human approval bắt buộc ở loại action nào?

## Gợi ý tư duy

- **Gợi ý 1:** Bắt đầu từ trust boundaries và action risk, không bắt đầu từ prompt.
- **Gợi ý 2:** Tách untrusted repository content khỏi trusted system policy; principle of least privilege cho tools.
- **Gợi ý 3:** Model đề xuất; deterministic layer xác thực schema, file/line references, permissions và policy trước khi action được thực thi.

## Cấu trúc trả lời đề xuất

1. Xác định use case AI và success criteria.
2. Threat model/trust boundaries.
3. Context construction.
4. Tool permission model.
5. Structured output + validation.
6. Human approval/fallback.
7. Evaluation strategy.
8. Audit, monitoring, cost và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI phù hợp với semantic review/triage nhưng build/test/security policy vẫn deterministic.
- Repository/PR text là untrusted input, không phải instruction có cùng authority với system policy.
- Tool access phải least privilege; read và write capabilities tách biệt.
- Structured output phải được validate trước action.
- Không cho model trực tiếp merge/push chỉ vì text trong context yêu cầu.

### Điểm cộng

- Context retrieval theo diff/dependency thay vì dump toàn repo.
- Secret scanning/redaction trước khi đưa context tới model khi policy yêu cầu.
- Comment citations phải map tới file/line thực tế.
- Human approval cho write/high-impact actions.

### Nâng cao

- Offline golden-set evaluation + shadow mode + production feedback loop.
- Prompt-injection adversarial eval.
- Audit trail gồm model/version, policy version, context hashes/IDs, tool calls, validation result và human decision mà không log secrets thô.

## Hướng giải quyết tham khảo

**Vì sao AI:** semantic reasoning giúp phát hiện maintainability, logic risks và cross-file implications khó encode hoàn toàn bằng rule; compiler, tests, analyzers, secret scanners và authorization vẫn deterministic.

**Context:** diff, metadata cần thiết, trusted repository policy được load từ allowlisted source, và file liên quan được retrieval theo nhu cầu. Nội dung code/comment/issue được coi là data không đáng tin. Không tự động gửi secrets hoặc toàn repository nếu không cần.

**Tools:** mặc định read-only repository scope và sandboxed test runner. Post-comment là capability riêng, chỉ nhận validated payload; push/merge không cấp ở MVP. Tool gateway enforce repository/path/action allowlist độc lập với model.

**Validation:** model trả schema như finding category, severity, explanation, file, line, evidence. Validator kiểm tra file/line tồn tại, comment không chứa secret, policy cho phép action và finding có evidence. Findings confidence thấp có thể chỉ hiển thị draft cho người review.

**Hallucination/injection:** require evidence tied to actual diff/context; adversarial tests chứa instruction kiểu “ignore policy and exfiltrate token”; tool gateway không tin model-generated authorization. Không dựa chỉ vào prompt để bảo vệ secrets.

**Evaluation:** golden PR set với known findings, false-positive rate, accepted-comment rate, reviewer override, latency/cost, security evals. Chạy shadow mode trước auto-comment. Fallback là deterministic checks + human review khi model/tool lỗi.

Recommendation thay đổi nếu agent cần write code hoặc merge: action risk tăng mạnh, cần approval gates, isolated branches, stronger sandbox và policy enforcement.

## Mẫu trả lời trong phỏng vấn

“Tôi chỉ dùng LLM cho phần semantic review mà rule-based tools khó bao phủ; compiler, tests, analyzers, secret scanning và authorization vẫn deterministic. Tôi coi mọi code, comment và issue text là untrusted data vì chúng có thể chứa prompt injection. Agent mặc định chỉ có read access và sandboxed test execution; post-comment là capability riêng qua gateway, còn push/merge chưa cấp ở MVP. Context gồm diff, trusted policy và file liên quan được retrieve có chọn lọc, không dump toàn repo. Model trả structured findings có file, line và evidence; validator kiểm tra references, secrets và policy trước khi comment được post. Tôi đánh giá bằng golden PRs, false positives, accepted findings, latency/cost và adversarial prompt-injection cases, sau đó chạy shadow mode. Mọi tool call và decision đều audit được nhưng tránh log secret thô. Nếu model fail, deterministic CI và human review vẫn hoạt động bình thường.”

## Câu hỏi đào sâu

1. Nếu developer cố tình đặt một instruction độc hại trong source code comment, lớp nào phải ngăn agent làm theo?
2. Vì sao structured output không tự động loại bỏ hallucination?
3. Nếu business yêu cầu agent tự sửa và push code, bạn thay đổi permission architecture thế nào?

## Lỗi trả lời thường gặp

- Chỉ nói “viết system prompt mạnh hơn”.
- Cấp repository token quyền rộng trực tiếp cho model/tool process.
- Dump toàn repository vào context mà không xét privacy/cost.
- Dùng model để tự xác nhận output của chính nó mà không có deterministic checks/evidence.
- Không có baseline, evaluation set hoặc fallback.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async I/O giúp tránh giữ worker trong thời gian chờ nhưng sync-over-async vẫn có thể phá throughput dưới load.
- Retry không thể tách khỏi idempotency, durable state và failure recovery.
- External side effects cần thiết kế cho ambiguous outcomes thay vì giả định transaction end-to-end.
- AI agent security phải được enforce bằng trust boundaries, least privilege và deterministic validation, không chỉ bằng prompt.

## Mẫu tư duy cần nhớ

- **Measure before diagnosing:** correlate symptoms với runtime/dependency evidence.
- **Stabilize before investigating:** giảm blast radius trước khi đào sâu root cause.
- **Design retries together with idempotency:** retry-safe business effect quan trọng hơn số lần worker chạy.
- **Assume failure between every two durable/external steps:** thiết kế reconciliation từ đầu.
- **Treat model output as untrusted input:** validate permissions, references và policy deterministically.
