# Câu 1 — SQL pagination chậm dù đã có index

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** SQL Server, PostgreSQL, EF Core, execution plans, pagination.

## Bối cảnh

API .NET 8 liệt kê lịch sử phê duyệt trên bảng 45 triệu bản ghi. Page 1 mất 70 ms, page 8000 mất 9 giây. Có index `CreatedAt`; dữ liệu liên tục được thêm và sửa trạng thái. API hiện chạy:

```csharp
var items = await db.ApprovalEvents.AsNoTracking()
    .Where(x => x.Status == status)
    .OrderByDescending(x => x.CreatedAt)
    .Skip((page - 1) * 50).Take(50)
    .Select(x => new ApprovalDto(x.Id, x.CreatedAt, x.OwnerId))
    .ToListAsync(ct);
```

Business không muốn người dùng thấy bản ghi trùng hoặc thiếu khi cuộn. Chưa rõ có yêu cầu nhảy tới trang bất kỳ.

## Câu hỏi chính

Giải thích cơ chế thực thi, vì sao index chưa chắc giúp phân trang sâu, và thiết kế phương án vừa nhanh vừa có consistency contract rõ ràng.

## Câu hỏi làm rõ nên cân nhắc

1. UX cần nhảy trang bất kỳ hay chỉ load more?
2. Có yêu cầu snapshot cố định hay live feed?
3. `CreatedAt` có trùng và có thể thay đổi không?
4. Composite index, execution plan, distribution của `Status` ra sao?
5. DB engine, query p95 và write volume thực tế thế nào?

## Gợi ý tư duy

### Gợi ý 1
Số dòng trả về khác số dòng database phải xử lý.

### Gợi ý 2
Xem thứ tự sort có deterministic và index có phù hợp filter không.

### Gợi ý 3
Cân nhắc cursor theo cặp `CreatedAt, Id`, và thay đổi dữ liệu giữa các request.

## Cấu trúc trả lời đề xuất

Clarify UX → giải thích OFFSET → actual execution plan → index strategy → keyset/snapshot alternatives → concurrency tests → production telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `Skip` trang sâu vẫn đòi hỏi bỏ qua nhiều dòng.
- Index đơn `CreatedAt` không đảm bảo tối ưu filter `Status`, sort và projection.
- Timestamp trùng khiến order không ổn định; thêm `Id` làm tie-breaker.
- Không khẳng định nguyên nhân nếu chưa xem actual execution plan.

### Điểm cộng
- Index `(Status, CreatedAt DESC, Id DESC)` và covering projection khi được plan chứng minh.
- Keyset pagination và opaque cursor có filter binding.
- Giới hạn page size, đánh giá write amplification.

### Senior+
- Phân biệt keyset live feed với snapshot consistency.
- Đọc logical reads, sort spill, statistics, parameter sensitivity, waits.
- Đề xuất snapshot/materialized result nếu business cần tập dữ liệu bất biến.

## Hướng giải quyết tham khảo

Với `OFFSET 399950`, database thường vẫn phải duyệt/xử lý lượng lớn hàng đủ điều kiện trước khi trả 50 hàng. Index `CreatedAt` có thể phải scan nhiều hàng không đúng `Status`, thực hiện lookup hoặc sort. Kiểm tra actual execution plan, logical reads và duration theo page depth: SQL Server dùng actual plan và `SET STATISTICS IO, TIME ON`; PostgreSQL dùng `EXPLAIN (ANALYZE, BUFFERS)` trên môi trường phù hợp. Không thêm index chỉ theo trực giác.

Nếu chủ yếu cuộn tuần tự, dùng keyset với sort `CreatedAt DESC, Id DESC`. Ví dụ SQL Server:

```sql
SELECT TOP (@take) Id, CreatedAt, OwnerId
FROM dbo.ApprovalEvents
WHERE Status = @status
  AND (CreatedAt < @cursorTime
       OR (CreatedAt = @cursorTime AND Id < @cursorId))
ORDER BY CreatedAt DESC, Id DESC;
```

Trang đầu bỏ cursor predicate. Đánh giá index `(Status, CreatedAt DESC, Id DESC) INCLUDE (OwnerId)` dựa trên reads, plan và write cost. Cursor nên mang filter, sort keys và được bảo vệ khỏi sửa đổi tùy ý. Keyset giảm vấn đề chèn mới ở đầu danh sách nhưng không tự bảo đảm snapshot khi `Status` thay đổi. Nếu cần snapshot chính xác, thiết kế snapshot kết quả hoặc cutoff kết hợp điều kiện dữ liệu phù hợp; không giữ transaction mở qua nhiều HTTP request. Nếu bắt buộc nhảy trang tùy ý, offset vẫn là một lựa chọn có chi phí rõ ràng.

Kiểm thử timestamp trùng, insert/update giữa các trang, tải đồng thời và so sánh p95/logical reads. Theo dõi query duration, page depth, lock waits, sort spill và timeout, không log dữ liệu nhạy cảm.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác nhận người dùng cần nhảy trang hay chỉ cuộn, và ‘không bỏ sót’ có nghĩa snapshot hay live feed. OFFSET sâu không trở thành O(1) chỉ vì có index. Tôi đọc actual plan và logical reads để xem scan, sort và lookup; đồng thời thêm Id làm tie-breaker cho CreatedAt. Nếu chỉ cuộn, tôi ưu tiên keyset cursor, cân nhắc composite index theo Status và thứ tự sort. Tuy nhiên status update giữa các request vẫn có thể thay đổi tập kết quả, nên nếu cần snapshot thật sự phải thiết kế riêng. Tôi chứng minh bằng concurrency test và p95 thay vì chỉ nhìn một lần chạy.”

## Câu hỏi đào sâu

1. Nếu UX phải nhảy thẳng đến trang 500 thì sao?
2. Nếu `Status` thay đổi giữa hai request, keyset có bảo đảm không bỏ sót không?
3. Nếu composite index không cải thiện p95, bạn điều tra gì tiếp?

## Lỗi trả lời thường gặp

- Coi index là bảo đảm độ phức tạp O(1).
- Chỉ sort timestamp không unique.
- Nhầm keyset với snapshot.
- Không đo execution plan hoặc write cost.

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ requirement | 1.5 |
| Cơ chế SQL đúng | 2 |
| Evidence/debugging | 2 |
| Giải pháp pagination/index | 2 |
| Trade-offs, tests, observability | 1.5 |
| Communication | 1 |
| **Tổng** | **10** |

# Câu 2 — IIS App Pool recycle và lỗi đăng nhập sau release

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC, .NET Framework 4.5, Octopus Deploy, observability, security.

## Bối cảnh

Cổng nhân sự dùng ASP.NET MVC/.NET Framework 4.5 chạy trên hai Windows Server sau load balancer. Sau release bằng Octopus Deploy, 7% request login trả 500 hoặc redirect lại trang login. Một node có App Pool recycle thường xuyên; memory tăng. Release thay đổi `web.config` và thêm thư viện xử lý ảnh. Hai node có cấu hình chưa hoàn toàn giống nhau. Không được dừng toàn bộ hệ thống trong giờ cao điểm. Chưa có root cause được xác nhận.

## Câu hỏi chính

Bạn xử lý incident từ phút đầu đến root cause và rollout an toàn như thế nào, với nhiều giả thuyết có thể đồng thời đúng?

## Câu hỏi làm rõ nên cân nhắc

1. Lỗi phân bố theo node, version, thời gian và user cohort thế nào?
2. Session mode và Forms Authentication `machineKey` giữa các node có đồng nhất?
3. App Pool recycle do schedule, memory, crash hay config change?
4. Có thể drain từng node và rollback artifact/config độc lập không?
5. Có IIS logs, Event Viewer, FREB, dump, Application Insights không?

## Gợi ý tư duy

### Gợi ý 1
Giảm blast radius trước khi debug sâu.

### Gợi ý 2
Tách authentication ticket khỏi server session và process lifecycle.

### Gợi ý 3
Đối chiếu recycle reasons, machineKey, InProc session, package native dependency và deployment diff.

## Cấu trúc trả lời đề xuất

Impact → stabilization → evidence → competing hypotheses → experiments → remediation → verification → prevention.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Đo 500/login failure theo node/version, drain node lỗi hoặc rollback an toàn.
- Kiểm tra IIS/WAS/Event Viewer và deployment diff.
- Không kết luận memory leak chỉ vì private bytes tăng.
- Không ghi cookie, token, credential vào logs.

### Điểm cộng
- Phân biệt InProc session mất khi recycle và Forms Authentication ticket không giải mã được nếu machineKey khác nhau.
- Kiểm tra process bitness, native handles, package compatibility.
- Canary release từng node, health probes và smoke test login xuyên node.

### Senior+
- Điều tra đồng thời nhiều root causes.
- Thiết kế rollback có kiểm tra ticket/session backward compatibility.
- Lập kế hoạch incremental modernization sau incident, không rewrite trong hotfix.

## Hướng giải quyết tham khảo

**Impact và stabilize:** lập incident channel, phân đoạn lỗi theo node, version, thời gian; đánh giá capacity node khỏe. Drain node lỗi hoặc rollback release/config có kiểm soát nếu đủ capacity, không recycle cả cụm. Xác minh login, session continuity và error rate ngay sau mitigation.

**Evidence:** IIS status/substatus, request correlation ID, Event Viewer (WAS/.NET Runtime), recycle reason, memory/private bytes/handles, deployment logs, cấu hình App Pool, `machineKey`, session state, `web.config` và package versions. Dùng FREB/crash dump có kiểm soát quyền truy cập; tránh lộ PII/secrets.

**Giả thuyết:** (A) machineKey khác khiến Forms Authentication ticket không đọc được khi chuyển node; (B) InProc session mất sau recycle; (C) package xử lý ảnh làm leak unmanaged resources hoặc crash; (D) config/deployment gây AppDomain restart; (E) load balancer health probe hoặc capacity. Kiểm tra từng giả thuyết bằng log auth, node affinity, recycle events, memory/handle trend, dump và timeline. Có thể có cả A và B, không ép một nguyên nhân.

**Remediation:** đồng bộ khóa bảo vệ ticket bằng cơ chế quản lý secrets an toàn; cân nhắc shared session state nếu cần survive recycle; sửa resource leak nếu profiler xác nhận; chuẩn hóa node config qua deployment pipeline. Rollout canary, drain, smoke test và rollback gate. Sau incident, inventory dependencies để chuyển dần khỏi runtime cũ, dùng characterization tests và incremental migration.

**Testing:** login/logout xuyên hai node; recycle có chủ đích trên staging; soak/load test image processing; failover và rollback; xác minh session/auth khi đổi version. **Observability:** 500 theo node/version, recycle counts, auth failure reason (không chứa ticket), process handles/private bytes, p95, deployment annotations và alert threshold.

## Mẫu trả lời trong phỏng vấn

“Tôi không vội quy lỗi cho package ảnh. Tôi sẽ xác định blast radius theo node và release, rồi drain node lỗi hoặc rollback nếu capacity cho phép. Tôi đối chiếu IIS/WAS events, machineKey, session mode và thay đổi web.config. Forms Authentication ticket không đọc được giữa hai node khác với InProc session mất sau recycle; chúng có thể cùng xảy ra. Memory tăng chỉ là tín hiệu, tôi cần dump hoặc profiler trước khi gọi là leak. Sau mitigation, tôi canary từng node, test login qua failover và giám sát error rate/recycle. Modernization sẽ là kế hoạch riêng sau khi production ổn định.”

## Câu hỏi đào sâu

1. Nếu rollback xong vẫn có 500, bước tiếp theo là gì?
2. Sticky session có giải quyết triệt để lỗi authentication không?
3. Phân biệt memory leak với memory tăng do cache/GC bằng cách nào?

## Lỗi trả lời thường gặp

- Recycle toàn bộ App Pool khiến session mất hàng loạt.
- Coi sticky session là giải pháp đủ.
- Nhầm authentication ticket với session state.
- Ghi raw cookie/token để debug.
- Rewrite hệ thống khi incident chưa ổn định.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact/stabilization | 2 |
| Evidence collection | 2 |
| Competing hypotheses | 2 |
| Fix/rollback | 1.5 |
| Tests, security, telemetry | 1.5 |
| Incident communication | 1 |
| **Tổng** | **10** |

# Câu 3 — Thiết kế upload tài liệu an toàn cho approval platform đa tổ chức

**Loại câu hỏi:** Architecture / system design / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, PostgreSQL, Managed Identity, background processing, authorization.

## Bối cảnh

Approval platform đa tổ chức nhận 200.000 PDF/ảnh mỗi ngày, phần lớn 1–10 MB, một số 500 MB. File phải scan trước khi download; user chỉ đọc tài liệu thuộc tổ chức và hồ sơ có quyền. Retention 3 năm, audit download bắt buộc. Team 5 backend developers đang dùng ASP.NET Core + PostgreSQL + Azure App Service, chưa có message broker. Cần kiểm soát chi phí và phục hồi lỗi; SLA scan và yêu cầu revoke URL chưa rõ.

## Câu hỏi chính

Thiết kế upload → quarantine → scan → authorize → download, lựa chọn proxy/direct Blob và đồng bộ/bất đồng bộ, trình bày failure recovery, security, data model, observability, rollout và trade-offs.

## Câu hỏi làm rõ nên cân nhắc

1. SLA scan, chính sách malware/retention/legal hold?
2. Mobile cần resumable upload và mạng không ổn định không?
3. Revoke quyền download cần hiệu lực ngay hay chấp nhận vài phút?
4. Tenant isolation và quyền theo record/role thay đổi thế nào?
5. Có yêu cầu chống duplicate, versioning, data residency không?

## Gợi ý tư duy

### Gợi ý 1
Upload hoàn tất không đồng nghĩa file được phép phục vụ.

### Gợi ý 2
Metadata ownership, Blob permission và authorization phải tách biệt.

### Gợi ý 3
Xem dual-write, idempotent scan, orphan cleanup và giới hạn SAS.

## Cấu trúc trả lời đề xuất

Threat model/SLA → API/data model → state machine → upload strategy → async scan/recovery → download authorization → tests/telemetry/deployment.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Metadata `TenantId, DocumentId, RecordId, BlobKey, Status, Version, CreatedAt`.
- `PendingUpload → Quarantined → Scanning → Ready/Rejected`; chỉ Ready được download.
- Authorization server-side theo user, tenant và record.
- Private Blob container, không dựa vào GUID bí mật.
- Failure handling cho DB/Blob/worker.

### Điểm cộng
- User delegation SAS scope hẹp, expiry ngắn; checksum, MIME sniffing, quotas.
- Scan idempotent, retries, poison queue, orphan reconciliation.
- Phân biệt audit cấp URL và audit bytes thực tải.

### Senior+
- Trade-off revoke quyền với SAS đã phát.
- Outbox hoặc DB work table với atomic lease trước khi cần Service Bus.
- Lifecycle/retention, least privilege, encryption, egress cost, incident recovery.

## Hướng giải quyết tham khảo

**API và state:** `POST /documents/uploads` xác thực quyền gắn file vào record, tạo upload intent; `POST /documents/{id}/complete` xác minh Blob size/checksum và đưa vào Quarantined; `GET /documents/{id}` trả metadata sau authorize; `POST /documents/{id}/download` kiểm tra lại quyền và trạng thái Ready. DB là source of truth cho ownership và trạng thái; Blob name random, private và không được coi là quyền truy cập.

**Upload:** file lớn/mobile phù hợp direct upload tới private Azure Blob với user delegation SAS chỉ có quyền ghi đúng object và TTL ngắn. SAS không tự thực thi business file-size/type policy; backend kiểm tra sau upload, enforce quota và cleanup orphan. Proxy upload có lợi khi phải kiểm tra inline hoặc kiểm soát toàn bộ bytes, nhưng tăng bandwidth, memory/connection pressure và cost. Dùng Managed Identity và least privilege thay vì chia sẻ account key rộng.

**Scan:** worker nhận job bền vững, scan theo `DocumentId + BlobVersion` idempotently, giới hạn concurrency, timeout, retry/backoff, dead-letter/manual review. DB work table có lease atomic và reconciliation có thể đủ với team nhỏ; nếu cần isolation/scale, Service Bus kết hợp Outbox để tránh commit DB thành công nhưng mất message. Không dựa vào exactly-once. `Rejected` và `Scanning` không thể download; kiểm tra magic bytes và content handling, không chỉ MIME do client khai.

**Download:** luôn authorize theo tenant/record tại thời điểm request. Proxy streaming dễ enforce revoke và audit chi tiết nhưng tốn resources; short-lived read SAS giảm tải nhưng URL đã cấp có cửa sổ hiệu lực, audit cấp URL không chứng minh user tải đủ bytes. Chọn theo yêu cầu revoke và threat model. Cân nhắc `Content-Disposition`, type restrictions, retention, backup/restore, lifecycle và storage/egress cost.

**Failure recovery:** reconciler tìm upload chưa complete, orphan Blob, scan stuck, version mismatch và retries quá giới hạn; mọi state transition có concurrency guard. Test cross-tenant IDOR, upload 500 MB ngắt mạng, duplicate completion, scan failure, worker crash, authorization revoked và rollback. Telemetry: scan queue age/p95, stuck count, rejected count, orphan count, download denied, egress cost, correlation IDs và audit.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác nhận SLA scan và yêu cầu revoke trước. Metadata và quyền ở PostgreSQL; Blob private giữ bytes. Upload xong chỉ vào quarantine, scan thành công mới Ready. Với file lớn/mobile tôi chọn direct upload qua SAS hẹp và ngắn hạn, backend xác minh bytes và quota sau complete. Scan chạy idempotent, có retry, poison handling và reconciliation; có thể bắt đầu bằng DB work table rồi thêm Service Bus nếu cần scale. Download luôn kiểm tra tenant và record. Nếu revoke tức thì, proxy có lợi hơn; nếu chấp nhận URL sống ngắn, SAS giảm tải. Tôi test cross-tenant, network failure, duplicate job và đo queue age, scan latency, access denied.”

## Câu hỏi đào sâu

1. Nếu phải revoke download tức thì, tại sao short-lived SAS chưa đủ?
2. DB commit xong nhưng scan job không xuất hiện: bạn phục hồi thế nào?
3. Nếu chi phí egress tăng, lựa chọn nào vẫn giữ được security boundary?

## Lỗi trả lời thường gặp

- Public Blob hoặc GUID thay cho authorization.
- Cho download trước khi scan.
- Tin file type và size do client tự khai.
- Thêm message broker nhưng bỏ qua dual-write.
- Mặc định Kubernetes/microservices dù chưa có nhu cầu.
