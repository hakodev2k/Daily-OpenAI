# Câu 1 — Vì sao Cosmos DB query vẫn “đúng” nhưng RU và latency tăng mạnh khi container lớn dần?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, logical/physical partition, RU, query routing, hot partition, cross-partition query, indexing, observability

## Bối cảnh

Một SaaS multi-tenant dùng Azure Cosmos DB for NoSQL để lưu activity records. Container hiện có khoảng 300 triệu documents và tiếp tục tăng.

Partition key hiện tại là:

```text
/id
```

Document mẫu:

```json
{
  "id": "activity-01JXYZ...",
  "tenantId": "tenant-42",
  "customerId": "customer-817",
  "type": "OrderUpdated",
  "occurredAtUtc": "2026-09-10T00:10:00Z",
  "payload": { }
}
```

API phổ biến nhất là:

```sql
SELECT TOP 50 *
FROM c
WHERE c.tenantId = @tenantId
  AND c.customerId = @customerId
ORDER BY c.occurredAtUtc DESC
```

Khi hệ thống còn nhỏ, query này chạy nhanh và RU tương đối thấp. Sau khi data và throughput tăng, production xuất hiện:

- cùng query shape nhưng RU tăng đáng kể;
- p95/p99 tăng khi container lớn hơn;
- một số tenant lớn có nhiều traffic hơn tenant khác;
- tăng provisioned RU/s giúp một phần nhưng chi phí tăng nhanh;
- team nói “Cosmos DB có index nên query phải O(log n), partition key chỉ ảnh hưởng write distribution”; 
- một đề xuất khác là tăng throughput tiếp vì “cross-partition query đã được SDK parallelize nên không có vấn đề”.

Bạn chưa được cung cấp exact number of physical partitions, RU breakdown hay query metrics.

## Câu hỏi chính

Hãy giải thích cơ chế bên trong khiến query vẫn trả kết quả đúng nhưng có thể tốn RU và latency hơn khi container scale-out. Phân tích vai trò của logical partition, physical partition, partition-key routing, cross-partition fan-out và hot partition. Sau đó trình bày cách bạn sẽ xác minh nguyên nhân và quyết định giữa giữ `/id`, đổi partition strategy, dùng hierarchical partition key, tạo read projection hay chấp nhận cross-partition query.

## Câu hỏi làm rõ nên cân nhắc

1. Read traffic chủ yếu query theo `tenantId`, `customerId`, hay point-read theo `id`?
2. Một tenant hoặc một customer lớn nhất có bao nhiêu data và bao nhiêu RU/s so với median?
3. Query metrics hiện cho thấy bao nhiêu partitions được chạm tới và RU charge phân phối ra sao?
4. Requirement consistency, transaction boundary và retention theo tenant/customer là gì?
5. Có workload nào cần lookup trực tiếp theo `id` mà không biết tenant/customer không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu từ “index có hay không”. Hãy hỏi trước: query engine có thể route request đến một logical partition cụ thể hay phải tìm trên nhiều physical partitions?

### Gợi ý 2

Partition key quyết định cả data placement lẫn khả năng route query. Một index tốt không loại bỏ chi phí fan-out nếu partition key không khớp access pattern.

### Gợi ý 3

Tăng RU/s có thể che triệu chứng nhưng không sửa query shape hoặc skew. Hãy dùng telemetry để phân biệt cross-partition fan-out với hot-partition pressure.

## Cấu trúc trả lời đề xuất

1. Làm rõ dominant access patterns và scale distribution.
2. Giải thích logical partition vs physical partition.
3. Giải thích routing của in-partition query vs cross-partition query.
4. Phân tích `/id` trong workload hiện tại.
5. Tách hai hypothesis: fan-out cost và hot partition/skew.
6. Nêu telemetry/query metrics cần thu.
7. So sánh các partition-key alternatives.
8. Đề xuất migration/read-projection strategy nếu cần.
9. Nêu test/load plan và điều kiện thay đổi recommendation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu rằng `/id` phân phối write rất tốt khi `id` có high cardinality, nhưng query theo `tenantId/customerId` không có equality filter trên partition key nên trở thành cross-partition query.
- Hiểu cross-partition query phải fan out tới các physical partitions liên quan, chạy query trên các partition-local indexes rồi merge kết quả.
- Không nói “có index nên partition key không quan trọng”.
- Không mặc định tăng RU/s là fix tốt nhất.
- Yêu cầu query metrics, RU charge, physical-partition count, throttling/429 và workload skew trước khi redesign.
- Phân biệt fan-out query cost với hot partition do uneven request/data distribution.

### Điểm cộng

- Nhận ra point read hiệu quả yêu cầu biết `id` và partition key value; `/id` thuận lợi cho point-read khi `id` là partition key nhưng gây bất lợi cho tenant/customer queries.
- Đề xuất candidate key như `tenantId`, `customerId`, synthetic key hoặc hierarchical partition key dựa trên access patterns thay vì theo intuition.
- Đề cập migration của partition key là data migration/new container problem chứ không phải in-place column update.
- Đề xuất read projection/container thứ hai nếu có hai query patterns độc lập và cost justified.

### Senior+

- Phân tích skew: partition key có high cardinality chưa đủ, request/storage phải phân phối đủ đều.
- Dùng conditional reasoning: nếu tenant lớn có thể vượt logical-partition limits hoặc cực hot, single `tenantId` key có thể không phù hợp.
- Cân nhắc hierarchical partition keys khi workload route theo prefix và cần scale vượt một logical partition đơn.
- So sánh extra projection/store cost với cross-partition RU cost bằng benchmark thực tế.
- Nêu migration với dual-read/shadow-read, checkpointed backfill, cutover và rollback.

## Hướng giải quyết tham khảo

Cosmos DB không có một global B-tree duy nhất cho toàn container theo cách team đang hình dung. Data được tổ chức thành logical partitions theo partition-key value, còn Azure quản lý placement các logical partitions lên physical partitions.

Với partition key `/id`, mỗi activity ID có thể trở thành một logical partition riêng. Điều này phân phối writes tốt vì `id` có cardinality cao và giúp point operations theo đúng `id` rất hiệu quả. Nhưng query hiện tại filter theo `tenantId` và `customerId`, không filter equality trên `/id`. Vì vậy Cosmos DB không thể route query tới một logical partition cụ thể chỉ từ predicate này.

Khi query không có partition-key equality phù hợp, nó trở thành cross-partition query. Query engine/SDK có thể parallelize, nhưng vẫn phải chạy query trên các physical partitions cần thiết rồi aggregate/merge result. Khi container còn nhỏ và chỉ có ít physical partitions, overhead này có thể không đáng kể. Khi data/throughput tăng và số physical partitions tăng, fan-out cost có thể tăng theo số partitions bị chạm tới. Parallelism giảm wall-clock latency trong một số trường hợp, nhưng không làm RU cost biến mất.

Do đó assumption “đã có index nên partition key không quan trọng” là sai. Index giúp tìm dữ liệu trong từng partition hiệu quả hơn, nhưng routing và fan-out vẫn chịu ảnh hưởng của partition key.

Tôi sẽ thu evidence trước:

- request charge theo query;
- query metrics và diagnostics;
- số physical partitions hiện tại;
- 429/throttling rate;
- RU consumption theo partition-key range;
- p50/p95/p99 theo tenant/customer;
- item count/data size theo tenant/customer;
- distribution của write/read traffic;
- latency dependency từ Application Insights hoặc Azure Monitor.

Sau đó tôi tách hai vấn đề:

**1. Cross-partition fan-out:** nếu mỗi query chạm rất nhiều partitions và RU tăng theo container scale, key không align access pattern là candidate chính.

**2. Hot partition/skew:** nếu một số logical partition/range nhận phần lớn traffic, có thể bị throttling dù tổng container RU vẫn còn. Khi đó chỉ đổi sang `tenantId` mà một tenant chiếm phần lớn traffic có thể tạo hot logical partition mới.

Một candidate đơn giản là partition theo `tenantId` nếu hầu hết requests luôn biết tenant và tenant size/traffic không quá skew. Tuy nhiên nếu một tenant rất lớn hoặc throughput của tenant đó có thể vượt giới hạn logical partition, `tenantId` đơn có thể không scale tốt.

Nếu dominant query luôn biết `tenantId` và `customerId`, có thể cân nhắc synthetic partition key hoặc hierarchical partition key, ví dụ hierarchy `tenantId/customerId`, sau khi xác minh query-routing semantics và data distribution phù hợp. Hierarchical partition keys có thể cho phép query theo prefix hiệu quả hơn và phân phối một tenant lớn qua nhiều subpartitions, nhưng complexity phải được justify bởi workload.

Nếu hệ thống có hai access patterns khó tối ưu bằng một key — ví dụ write/point read theo `id` và feed read theo tenant/customer — một read projection/container thứ hai có thể hợp lý. Source container giữ write model, projection được build asynchronously và partition theo read pattern. Nhưng lúc đó phải chấp nhận eventual consistency, replay/reconciliation, extra RU/storage và operational complexity.

Tôi sẽ không migrate partition key chỉ dựa trên một query chậm. Tôi sẽ benchmark candidate models bằng data distribution gần production: hot tenant, median tenant, deep history, peak concurrency. Nếu current `/id` vẫn đạt SLO với acceptable RU cost, giữ nó có thể là lựa chọn đơn giản hơn.

Tài liệu chính thức để xác minh behavior:

- Microsoft Learn — Partitioning and horizontal scaling in Azure Cosmos DB: https://learn.microsoft.com/azure/cosmos-db/partitioning
- Microsoft Learn — Query an Azure Cosmos DB container: https://learn.microsoft.com/azure/cosmos-db/how-to-query-container

## Mẫu trả lời trong phỏng vấn

“Query đúng không có nghĩa là query rẻ. Với `/id` là partition key, query theo tenant/customer không có equality predicate trên partition key nên Cosmos DB phải fan out qua các physical partitions cần thiết, query index cục bộ rồi merge kết quả. Khi container còn ít partitions, overhead nhỏ; khi scale-out, RU và p99 có thể tăng. SDK parallelization chỉ giảm một phần latency, không loại bỏ RU fan-out. Tôi sẽ đo request charge, query diagnostics, 429, partition-level RU và skew trước. Nếu dominant read luôn theo tenant/customer, tôi sẽ benchmark `tenantId`, synthetic hoặc hierarchical key. Nhưng nếu một tenant cực lớn thì `tenantId` đơn có thể tạo hot partition. Nếu hai access patterns xung đột, read projection có thể hợp lý, nhưng phải tính eventual consistency và operational cost. Tôi chỉ migrate khi evidence cho thấy current key không còn đáp ứng SLO/cost.”

## Câu hỏi đào sâu

1. Nếu 95% reads là point-read theo `id`, còn 5% là expensive feed query theo tenant/customer, bạn có đổi partition key chính không?
2. Nếu một tenant tạo 40% tổng traffic, vì sao `tenantId` có thể vẫn là lựa chọn kém dù query routing đẹp hơn?
3. Nếu projection container bị lag 2 phút trong incident, bạn quyết định fail, serve stale hay fallback source container dựa trên requirement nào?

## Lỗi trả lời thường gặp

- Nói “Cosmos DB tự scale nên partition key không quan trọng”.
- Chỉ đề xuất tăng RU/s mà không xem query diagnostics.
- Chọn `tenantId` chỉ vì multi-tenant mà không kiểm tra skew/size.
- Nói cross-partition query luôn xấu hoặc luôn phải tránh; small-container workload có thể vẫn hoàn toàn chấp nhận được.
- Đề xuất thêm container/projection mà không nói consistency, replay và operational cost.

## Thang điểm 0–10

- **0–2:** Chỉ nói thêm index hoặc tăng RU.
- **3–4:** Biết partition key ảnh hưởng query nhưng không giải thích routing/fan-out.
- **5–6:** Giải thích đúng logical/physical partition, cross-partition query và evidence cần đo.
- **7–8:** Có skew analysis, candidate key trade-offs, migration/test plan.
- **9–10:** Lập luận conditional, cân nhắc hierarchical/projection architecture, consistency và cost of complexity bằng telemetry thực tế.

# Câu 2 — IIS application pool liên tục recycle rồi website trả 503 sau deployment

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET, application pool, 503, recycling, Rapid-Fail Protection, deployment troubleshooting, observability, incident response

## Bối cảnh

Một enterprise portal legacy chạy ASP.NET MVC trên .NET Framework 4.5, host trên IIS/Windows Server. Hệ thống có 4 web servers sau load balancer.

Một release nhỏ được deploy lúc 21:00 bằng Octopus Deploy. Khoảng 10 phút sau:

- một số users nhận 503, sau đó tỷ lệ tăng;
- load balancer dần loại một số nodes vì health check fail;
- trên một server, Application Pool chuyển sang `Stopped`;
- restart App Pool giúp website lên lại trong vài phút rồi lỗi tái diễn;
- Windows Event Logs có nhiều entries gần thời điểm worker process restart;
- working set tăng sau mỗi lần traffic lên nhưng chưa có dump;
- team nói “IIS tự recycle định kỳ, cứ tăng private memory limit hoặc tắt Rapid-Fail Protection là được”;
- một người khác nghi ngờ deployment thiếu file/config và muốn rollback ngay;
- database latency vẫn bình thường;
- chỉ production gặp, staging với traffic thấp không tái hiện.

Bạn chưa biết nguyên nhân là crash, memory-triggered recycle, startup failure, queue exhaustion, bad deployment artifact hay application bug dưới load.

## Câu hỏi chính

Hãy xử lý incident theo production reasoning: xác định impact, stabilize, thu evidence, xây competing hypotheses, khoanh vùng vì sao worker process/app pool recycle hoặc stop, quyết định rollback hay tiếp tục điều tra, rồi đề xuất remediation và prevention. Không được giả định sẵn một root cause.

## Câu hỏi làm rõ nên cân nhắc

1. Event Viewer/WAS/Application logs ghi recycle reason, process crash hay Rapid-Fail Protection event nào?
2. 503 được phát từ HTTP.sys do queue/app pool unavailable hay từ application code/proxy layer?
3. Application Pool recycling settings có memory threshold, schedule, request-count hoặc idle timeout nào?
4. Release có thay đổi native dependency, appSettings/connection strings, startup code, static files hay assembly binding không?
5. Lỗi có xảy ra đồng đều trên cả 4 nodes hay chỉ node nhận artifact/config khác?

## Gợi ý tư duy

### Gợi ý 1

`App Pool stopped` là symptom quan trọng nhưng chưa phải root cause. Hãy tìm reason code/event trước khi thay cấu hình.

### Gợi ý 2

Phân biệt **normal recycle**, **worker-process crash**, **startup failure**, **Rapid-Fail Protection**, **memory-triggered recycle**, và **HTTP.sys queue rejection**.

### Gợi ý 3

Staging traffic thấp không tái hiện có thể là clue cho load-dependent bug, nhưng artifact/config drift vẫn phải được kiểm tra.

## Cấu trúc trả lời đề xuất

1. Xác định user impact và affected nodes.
2. Stabilize bằng traffic draining/rollback/scoped restart phù hợp.
3. Preserve evidence trước khi restart hàng loạt.
4. Phân loại 503 source và app-pool state.
5. Thu Event Logs, IIS logs, HTTPERR, recycle reasons, crash dumps/perf counters.
6. So sánh artifact/config giữa healthy và unhealthy nodes.
7. Xây và loại trừ competing hypotheses.
8. Chọn short-term remediation.
9. Thiết kế long-term prevention, tests và monitoring.
10. Xác minh recovery dưới production-like load.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tắt Rapid-Fail Protection ngay như “fix”.
- Không tăng memory limit trước khi biết recycle reason.
- Phân biệt recycle bình thường với crash/rapid fail.
- Thu Windows Event Logs/WAS, IIS logs, HTTPERR và app logs trước khi mất evidence.
- Xác minh deployment artifact/config consistency giữa nodes.
- Có rollback criteria rõ dựa trên impact/risk, không cố debug production vô thời hạn.

### Điểm cộng

- Draining một node khỏi load balancer để điều tra trong khi giữ capacity trên nodes còn lại.
- Capture crash dump hoặc memory dump nếu process crash/memory growth tái hiện.
- Theo dõi private bytes, working set, handle count, thread count, request queue, error rate và recycle count.
- Nhận ra memory-based recycle có thể che leak thay vì sửa leak.
- Kiểm tra scheduled recycle/idle timeout nhưng không nhầm chúng với repeated crash.

### Senior+

- Dùng symptom → evidence → hypothesis → verification thay vì “restart until green”.
- Tách mitigation khỏi root-cause fix.
- Thiết kế canary/rolling deployment cho IIS farm để giảm blast radius.
- Có artifact hashing/config drift detection và automated smoke/health verification sau deploy.
- Xây load test đủ để tái hiện failure path trước release lại.

## Hướng giải quyết tham khảo

**1. Impact và stabilization**

Tôi sẽ xác định ngay số nodes affected, 503 rate, request volume và business flows bị ảnh hưởng. Nếu một node đang crash/recycle liên tục, drain node đó khỏi load balancer thay vì restart tất cả nodes cùng lúc.

Nếu failure bắt đầu ngay sau release và impact đang tăng, rollback là mitigation hợp lệ dù chưa có root cause đầy đủ, đặc biệt khi previous artifact/config known-good và rollback risk thấp. Tuy nhiên trước rollback/restart, nên capture đủ logs và trạng thái để không xóa evidence.

**2. Phân loại 503**

503 trong IIS có nhiều nguồn. Tôi cần biết response/log evidence:

- app pool unavailable/stopped;
- HTTP.sys queue full;
- startup failure;
- Rapid-Fail Protection sau nhiều worker-process crashes;
- upstream/load balancer health failure;
- application tự trả 503.

HTTPERR logs, IIS logs và Windows Event Viewer giúp tách các case này.

**3. Kiểm tra recycle/worker process evidence**

IIS application pool có thể recycle theo schedule, elapsed time, request count, virtual/private memory thresholds hoặc admin action. Normal recycle không tự động đồng nghĩa incident. Tôi sẽ kiểm tra configured recycling settings và event logging reason.

Nếu Event Log cho thấy repeated worker-process crashes rồi Application Pool bị stop, Rapid-Fail Protection có thể là cơ chế bảo vệ sau crash chứ không phải nguyên nhân ban đầu. Tắt nó có thể khiến crash loop tiếp tục và làm server churn mạnh hơn.

Microsoft IIS documentation cho phép cấu hình recycling conditions và logging recycle reason. Rapid-Fail Protection có thể stop application pool khi worker process failures vượt threshold trong window cấu hình; khi pool unavailable IIS có thể trả 503.

Tài liệu tham khảo:

- Microsoft Learn — Application Pool recycling settings: https://learn.microsoft.com/iis/configuration/system.applicationhost/applicationpools/add/recycling/
- Microsoft Learn — Application pool failure/Rapid-Fail Protection settings: https://learn.microsoft.com/iis/wmi-provider/applicationpoolfailuresettings-class

**4. Competing hypotheses**

Tôi sẽ giữ ít nhất các hypothesis sau:

- release tạo unhandled process crash/native crash;
- startup/config binding failure chỉ production mới có;
- memory leak hoặc allocation pattern dưới load chạm recycle limit;
- app-pool recycle setting quá aggressive;
- file/assembly version mismatch giữa nodes;
- Octopus step partial failure dẫn đến artifact drift;
- HTTP.sys queue exhaustion do worker process chậm/hung;
- external dependency hoặc thread starvation làm health check fail, dù DB normal.

**5. Evidence**

Tôi sẽ thu:

- Windows Application/System logs, đặc biệt WAS/IIS-related events;
- IIS access logs + status/substatus;
- `HTTPERR` logs;
- deployment logs/artifact version;
- hash/version của deployed binaries/config trên từng node;
- app logs/correlation IDs;
- private bytes, working set, GC if managed, handle/thread count;
- request queue length;
- worker process uptime/recycle count;
- crash dumps hoặc DebugDiag/ProcDump-style capture khi crash phù hợp với operational policy.

Nếu only production traffic trigger, một node drained có thể được dùng để reproduce có kiểm soát bằng synthetic load, miễn không gây ảnh hưởng người dùng.

**6. Remediation theo evidence**

Nếu bad artifact/config: rollback/correct deployment, verify all nodes converge cùng version.

Nếu crash bug: fix code/native dependency, add dump capture và regression test.

Nếu memory leak: sửa retention/resource lifecycle; memory recycle threshold có thể là temporary safety valve nhưng không phải permanent fix.

Nếu queue exhaustion: tìm why request processing chậm/hung trước khi chỉ tăng queue length.

Nếu health check quá nhạy: điều chỉnh health semantics nhưng không dùng health check để che crash.

**7. Prevention**

- deploy từng node/canary trước;
- health/smoke test sau deploy;
- immutable artifact version + hash verification;
- config drift detection;
- alert recycle rate, app-pool stop, 503, worker crash, queue depth;
- production-like load test cho flows có risk;
- runbook capture evidence trước restart.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tắt Rapid-Fail Protection hay tăng memory limit trước khi biết vì sao pool stop. Đầu tiên tôi xác định affected nodes và drain node đang fail để giữ capacity. Vì incident bắt đầu sau deployment, rollback là mitigation hợp lệ nếu impact tăng, nhưng tôi sẽ capture Event Viewer, WAS/IIS events, IIS + HTTPERR logs và deployment artifact/version trước. Tôi cần phân biệt normal recycle, crash loop, startup failure, memory-triggered recycle và HTTP.sys queue full. Nếu repeated worker crashes kích hoạt Rapid-Fail Protection thì protection chỉ là hậu quả, không phải root cause. Tôi cũng so hash/config giữa healthy và failed nodes. Sau đó fix theo evidence: bad artifact thì rollback/correct deploy; leak thì sửa retention chứ không dùng recycle làm permanent fix; queue full thì điều tra latency/threading. Dài hạn tôi thêm canary rollout, immutable artifact verification, recycle/crash alerts và load test tái hiện production.”

## Câu hỏi đào sâu

1. Nếu rollback về version cũ nhưng app pool vẫn stop, giả thuyết nào tăng xác suất và bạn kiểm tra tiếp gì?
2. Nếu memory threshold recycle làm incident biến mất, tại sao bạn vẫn không coi đó là root-cause fix?
3. Nếu chỉ một trong bốn servers gặp lỗi nhưng artifact hash giống nhau, bạn sẽ so sánh những machine-level differences nào?

## Lỗi trả lời thường gặp

- Tắt Rapid-Fail Protection ngay để “website không stop”.
- Tăng private-memory limit mà không thu memory evidence.
- Restart toàn farm trước khi preserve logs/dumps.
- Kết luận bad deployment chỉ vì incident xảy ra sau deployment.
- Chỉ nhìn application logs mà bỏ qua WAS/IIS/HTTPERR evidence.

## Thang điểm 0–10

- **0–2:** Chỉ restart App Pool hoặc server.
- **3–4:** Biết xem Event Viewer nhưng thiếu hypothesis/mitigation structure.
- **5–6:** Phân biệt recycle/crash/503 sources và có rollback + evidence plan.
- **7–8:** Có node draining, dump/perf telemetry, artifact comparison và prevention.
- **9–10:** Điều tra có hệ thống, bảo toàn evidence, giảm blast radius, đưa ra conditional remediation và deployment/runbook improvements production-ready.

# Câu 3 — Modernize hệ thống .NET Framework 4.5: rewrite toàn bộ hay migrate từng phần?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** .NET Framework modernization, ASP.NET Core, incremental migration, architecture boundaries, compatibility, rollout, testing, CI/CD, observability, technical decision-making

## Bối cảnh

Một internal enterprise portal đã tồn tại gần 10 năm:

- ASP.NET MVC trên .NET Framework 4.5;
- một số Web API controllers;
- Entity Framework 6 + SQL Server;
- jQuery và một AngularJS module cũ;
- IIS/Windows Server;
- Windows Authentication ở một số flows;
- khoảng 80 projects trong solution;
- nhiều shared libraries phụ thuộc `System.Web`;
- vài third-party packages đã cũ;
- business vẫn release feature mới hàng tháng;
- có khoảng 150 critical screens/API flows;
- automated tests coverage còn thấp;
- downtime cho big-bang cutover chỉ được phép tối đa khoảng 30 phút.

Management muốn “lên .NET 8 hoặc mới hơn càng sớm càng tốt”.

Hai proposal xuất hiện:

**Proposal A — Rewrite:** tạo solution ASP.NET Core mới, React frontend mới, migrate toàn bộ trong 12–18 tháng rồi cutover một lần.

**Proposal B — Incremental:** tạo application ASP.NET Core side-by-side, route một số endpoints/features sang app mới, giữ phần chưa migrate chạy trên .NET Framework, rồi thay dần theo vertical slices.

Một số developers cho rằng incremental sẽ “rất bẩn vì phải chạy hai systems”; nhóm khác nói rewrite sẽ “sạch hơn và nhanh hơn vì không mang technical debt cũ”.

Chưa có compatibility inventory đầy đủ, chưa đo test coverage theo business criticality và chưa xác định module nào đang thay đổi nhiều nhất.

## Câu hỏi chính

Bạn sẽ quyết định rewrite, incremental migration hay hybrid strategy như thế nào? Hãy đưa ra assumptions, discovery plan, target boundaries, compatibility analysis, data/session/auth strategy, rollout, testing, CI/CD, observability, rollback và tiêu chí để biết migration đã hoàn tất. Không mặc định “modern hơn” đồng nghĩa “rewrite tốt hơn”.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào có business change rate cao, module nào gần như stable?
2. Những dependencies nào khóa hệ thống vào `System.Web`, Windows-only APIs hoặc third-party unsupported packages?
3. Authentication/session state hiện được chia sẻ như thế nào và có thể tách boundary không?
4. Database schema có thể dùng chung trong giai đoạn chuyển tiếp hay có module cần schema ownership riêng?
5. Organization có đủ automated regression tests và release capacity để chịu một big-bang cutover không?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn strategy trước compatibility inventory và risk map. “Rewrite sạch” không xóa business-rule uncertainty.

### Gợi ý 2

Migration boundary tốt thường theo business capability/vertical slice, không chỉ theo project/folder.

### Gợi ý 3

Một migration strategy tốt phải có rollback được ở từng bước, không chỉ có target architecture đẹp.

## Cấu trúc trả lời đề xuất

1. Clarify business deadline, support risk, downtime và release cadence.
2. Inventory dependencies/compatibility/runtime assumptions.
3. Map modules theo value, change rate, coupling và testability.
4. So sánh rewrite vs incremental bằng risk/cost.
5. Chọn target architecture tối thiểu đủ dùng.
6. Thiết kế side-by-side routing/auth/session/data strategy.
7. Lập migration slices và dependency order.
8. Thiết kế test pyramid/regression safety net.
9. Thiết kế CI/CD, canary, observability và rollback.
10. Định nghĩa completion/decommission criteria.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chọn rewrite chỉ vì code cũ xấu.
- Bắt đầu bằng dependency/compatibility inventory.
- Nhận ra automated-test gap làm big-bang rewrite rủi ro hơn.
- Thiết kế migration theo business slice và rollback capability.
- Xử lý auth/session/data/shared library boundaries trong giai đoạn coexistence.
- Có plan xác minh parity bằng production telemetry, không chỉ compile/test pass.

### Điểm cộng

- Dùng strangler/side-by-side routing pattern khi phù hợp.
- Tách libraries ít phụ thuộc framework trước để giảm coupling.
- Dùng contract/API boundary thay vì cho app mới reference trực tiếp toàn bộ legacy internals.
- Prioritize high-change/high-value modules hoặc modules có dependency dễ tách trước, không nhất thiết “dễ nhất” hay “khó nhất”.
- Có feature flags/shadow traffic/dual-run nơi phù hợp.

### Senior+

- Đề xuất measurable exit criteria cho từng slice: parity, error rate, latency, support incidents, fallback rate.
- Quản lý schema evolution theo expand/contract để old/new versions coexist.
- Có strategy cho shared authentication mà không tạo permanent coupling.
- Tính cost của vận hành hai runtimes trong transition nhưng so với risk reduction của big-bang.
- Chỉ dùng automated upgrade tooling như accelerator, không coi tool là migration strategy.

## Hướng giải quyết tham khảo

Tôi sẽ không phê duyệt rewrite hoặc incremental ngay khi chưa có inventory. Bước đầu là discovery có thời hạn rõ:

**1. Compatibility inventory**

- target framework của từng project;
- package dependencies và supported versions;
- `System.Web` usage;
- Windows-only APIs;
- EF6 patterns/migrations;
- authentication/session dependencies;
- file system/registry/COM/native dependencies;
- background jobs/scheduled tasks;
- integration endpoints;
- deployment assumptions trên IIS.

.NET Upgrade Assistant có thể hỗ trợ phân tích và một số upgrade paths. Microsoft hiện hỗ trợ cả in-place, side-by-side và side-by-side incremental options tùy project type; với complicated ASP.NET applications, side-by-side incremental là một lựa chọn được hỗ trợ để chuyển từng phần dần sang ASP.NET Core. Tool vẫn không tự giải quyết business logic, unsupported dependencies hay architecture boundaries.

Tài liệu tham khảo:

- Microsoft Learn — .NET Upgrade Assistant overview: https://learn.microsoft.com/dotnet/core/porting/upgrade-assistant-overview

**2. Risk map**

Tôi sẽ classify module theo:

- business criticality;
- change frequency;
- coupling;
- test coverage;
- dependency compatibility;
- production incident history;
- user volume.

Rewrite có lợi nếu product scope thay đổi rất mạnh, legacy architecture không còn phản ánh domain, team có đủ test/specification và có khả năng chịu parallel delivery dài hạn. Nhưng 12–18 tháng rewrite thường có hidden risk: business vẫn thay đổi, old system tiếp tục nhận features, requirements drift và parity khó chứng minh.

Incremental có overhead vận hành hai stacks, routing/auth/data coexistence và temporary complexity. Nhưng nó giảm cutover risk, cho phép release value sớm và rollback từng slice.

Với constraints hiện tại — nhiều critical flows, test coverage thấp, business vẫn release hàng tháng và downtime rất thấp — recommendation ban đầu của tôi nghiêng về **incremental/hybrid modernization**, không phải vì incremental luôn tốt hơn mà vì blast radius của big-bang rewrite đang quá lớn.

**3. Boundary strategy**

Tôi sẽ tránh migrate theo “project 1, project 2”. Thay vào đó chọn vertical slice có boundary rõ, ví dụ `Document Management`, `Reporting`, `Notifications` hoặc một subset API + UI.

Có thể đặt ASP.NET Core app phía trước hoặc dùng reverse proxy/routing để request cho migrated routes đi app mới, route còn lại về legacy. Boundary cụ thể phụ thuộc hosting/network/security architecture.

**4. Shared authentication/session**

Nếu old app dùng server-side session và Windows Authentication, cần thiết kế carefully. Mục tiêu là không để app mới phụ thuộc sâu vào legacy session object. Có thể cần standardized identity claims/token/session bridge trong transition, nhưng phải xác minh security constraints.

**5. Data strategy**

Ban đầu có thể dùng cùng SQL database nếu transaction boundary và deployment safety yêu cầu, nhưng phải kiểm soát schema ownership. Migrations nên backward-compatible theo expand/contract: thêm schema mới trước, deploy versions coexist, chuyển reads/writes, rồi mới remove old columns/constraints sau khi legacy slice decommission.

Không nên để old/new apps cùng update cùng business invariant theo hai implementations khác nhau mà không có ownership rõ.

**6. Shared libraries**

Các domain/application libraries ít phụ thuộc `System.Web` có thể được extract/retarget trước. Nhưng không biến migration thành một “big shared library rewrite”. Framework-specific code nên bị cô lập sau interfaces/contracts khi có giá trị.

**7. Testing safety net**

Vì test coverage thấp, trước migration cần build tests theo risk:

- characterization tests cho legacy behavior;
- API contract tests;
- integration tests database/auth;
- Playwright E2E cho critical user journeys;
- performance baseline;
- security regression tests;
- migration compatibility tests old/new coexistence.

Không cần đạt 100% coverage. Cần đủ confidence cho critical flows.

**8. Delivery**

Mỗi migrated slice có:

1. feature flag/routing control;
2. health + telemetry;
3. canary rollout;
4. parity checks;
5. rollback route về legacy nếu safe;
6. defined decommission point.

Nếu slice mới có error rate/latency/support regression vượt threshold, rollback routing nhanh hơn là rollback toàn platform.

**9. Completion criteria**

Migration không hoàn tất khi “solution mới compile”. Hoàn tất khi:

- traffic critical đã chuyển;
- legacy routes không còn usage;
- old scheduled jobs/services disabled;
- data ownership moved;
- monitoring stable qua agreed window;
- rollback dependency on legacy removed;
- old IIS/.NET Framework runtime có thể decommission an toàn.

**Khi nào tôi đổi sang rewrite?**

Nếu inventory cho thấy phần lớn business logic phải thay đổi hoàn toàn, legacy contracts không còn giá trị, test/specification coverage đủ mạnh, organization chấp nhận parallel feature freeze hoặc synchronized product roadmap, và incremental bridge cost lớn hơn rewrite risk, rewrite có thể hợp lý. Nhưng recommendation phải dựa trên evidence thay vì preference kiến trúc.

## Mẫu trả lời trong phỏng vấn

“Với 80 projects, test coverage thấp, business vẫn release hàng tháng và downtime chỉ 30 phút, tôi sẽ không chọn big-bang rewrite chỉ vì code cũ khó chịu. Đầu tiên tôi inventory `System.Web`, packages, Windows-only dependencies, auth/session, EF6 và deployment assumptions. Sau đó map modules theo business criticality, coupling và change rate. Recommendation ban đầu là incremental/hybrid: dựng ASP.NET Core side-by-side, route vertical slices sang app mới và giữ rollback về legacy. Tôi sẽ migrate theo capability chứ không theo folder. Database schema dùng expand/contract để old/new coexist; auth/session phải có boundary rõ, không share legacy state vô hạn. Tôi thêm characterization/API/E2E tests cho critical flows trước mỗi slice, rollout canary, đo error/latency/parity và chỉ decommission legacy khi traffic + data ownership đã chuyển. Upgrade Assistant là accelerator, không phải strategy. Nếu inventory chứng minh bridge cost quá lớn và business có thể chịu full rewrite risk thì tôi mới đổi recommendation.”

## Câu hỏi đào sâu

1. Nếu app mới và legacy cùng cần update một transaction-sensitive workflow trong 6 tháng transition, bạn tránh split-brain business logic như thế nào?
2. Nếu management yêu cầu “không được chạy hai applications quá 3 tháng”, điều đó thay đổi slice sizing và strategy của bạn ra sao?
3. Nếu Upgrade Assistant convert được 70% code nhưng 30% còn lại là `System.Web`, authentication và unsupported packages, bạn đánh giá 70% đó như thế nào để tránh false confidence?

## Lỗi trả lời thường gặp

- “Rewrite cho sạch” mà không tính business-rule parity và product drift.
- “Dùng Upgrade Assistant là xong migration”.
- Migrate theo project/folder mà không có business ownership boundary.
- Cho old/new apps cùng mutate schema/business rules mà không có coexistence plan.
- Không có rollback per slice.
- Chờ migration xong mới bổ sung observability/testing.

## Thang điểm 0–10

- **0–2:** Chọn rewrite/incremental theo preference cá nhân.
- **3–4:** Có compatibility analysis nhưng thiếu rollout/data/auth strategy.
- **5–6:** Có risk-based incremental plan, tests, routing và rollback.
- **7–8:** Có vertical slices, schema coexistence, telemetry/exit criteria và cost trade-offs.
- **9–10:** Recommendation conditional, cân bằng delivery risk với technical debt, quản lý coexistence production-ready và biết chính xác điều kiện khiến strategy phải đổi.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Trong Cosmos DB, partition key ảnh hưởng routing, RU và scale behavior; index không loại bỏ cross-partition fan-out.
- Production troubleshooting trên IIS phải phân biệt normal recycle, crash, Rapid-Fail Protection, queue exhaustion và deployment/config drift bằng evidence.
- Rapid-Fail Protection hoặc memory-based recycle có thể là protection/symptom chứ không phải root cause.
- Modernization strategy phải bắt đầu từ compatibility + business-risk inventory, không từ sở thích rewrite hay architecture trend.
- Incremental migration chỉ có giá trị khi mỗi slice có boundary, observability, test safety net và rollback rõ ràng.

## Mẫu tư duy cần nhớ

- **Route before optimize:** hiểu request/data được route tới đâu trước khi thêm throughput/index.
- **Stabilize, preserve evidence, then diagnose:** đừng restart đến mức mất root-cause evidence.
- **Symptom ≠ root cause:** recycle, 503 hoặc protection trigger chỉ là điểm bắt đầu điều tra.
- **Migrate by business boundary, not folder structure.**
- **Prefer reversible change:** mỗi bước modernization cần có cách rollback hoặc traffic fallback rõ ràng.
