# Câu 1 — Cosmos DB tăng RU dù số document trả về không đổi

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18–22 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, query fan-out, indexing, RU reasoning, observability

## Bối cảnh

Một ASP.NET Core API đọc lịch sử hoạt động từ Cosmos DB. Mỗi request thường trả 20–30 documents. Sau khi bổ sung filter theo `status` và sort theo thời gian, response payload gần như không đổi nhưng RU/request tăng mạnh và p95 tăng. Team kết luận rằng “RU chủ yếu phụ thuộc số documents trả về” và đề xuất tăng provisioned throughput.

Container có partition key, nhưng endpoint hiện không phải lúc nào cũng truyền partition-key value. Chưa có bằng chứng rằng throughput tổng thể là bottleneck.

## Câu hỏi chính

Hãy giải thích vì sao hai queries trả cùng số documents vẫn có thể có request charge và latency rất khác nhau; partition routing, scanned/indexed work và query shape tham gia thế nào; giả định nào của team chưa đúng; và bạn sẽ xác minh bằng evidence gì trước khi tăng capacity?

## Câu hỏi làm rõ nên cân nhắc

1. Partition key hiện tại là gì và có xuất hiện trong filter của endpoint không?
2. Cardinality và phân bố dữ liệu giữa logical partitions ra sao?
3. Query metrics/request charge thay đổi thế nào trước và sau release?
4. Indexing policy có hỗ trợ filter/sort hiện tại không?
5. Traffic/query distribution có đổi cùng thời điểm không?

## Gợi ý tư duy

### Gợi ý 1

Tách “số kết quả trả về” khỏi “khối lượng work cần thực hiện để tìm ra kết quả”.

### Gợi ý 2

Một query được route tới một partition khác đáng kể so với query phải tìm trên nhiều partitions.

### Gợi ý 3

Đừng kết luận từ RU tổng; so sánh request charge, query metrics và query shape trên cùng data distribution.

## Cấu trúc trả lời đề xuất

1. Làm rõ partition key và query semantics.
2. Giải thích routing và cross-partition work.
3. Phân tích filter/sort/indexing.
4. So sánh request charge và latency theo query class.
5. Xác định competing hypotheses.
6. Thử query/index/data-model changes có kiểm soát.
7. Chỉ scale throughput nếu evidence cho thấy capacity thực sự thiếu.
8. Regression/load test và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- RU phản ánh resource work, không chỉ số documents trả về.
- Query có partition-key equality phù hợp có thể được route hẹp hơn cross-partition query.
- Filter/sort/indexing và lượng dữ liệu phải xét có thể làm cost thay đổi.
- Cần đo request charge/query metrics thay vì đoán.
- Tăng throughput không sửa một query shape/data model kém hiệu quả.

### Điểm cộng

- Phân biệt hot partition với cross-partition fan-out.
- Xem pagination/continuation behavior và result cardinality.
- Đề xuất workload-specific partition-key review thay vì đổi key chỉ vì một endpoint.

### Senior+

- Nhận ra partition-key redesign là migration/data-model decision có cost lớn.
- Đặt query efficiency trong context consistency, scale và access patterns tổng thể.
- Nêu điều kiện khiến denormalization/materialized read model đáng cân nhắc.

## Hướng giải quyết tham khảo

Hai queries có cùng output count không nhất thiết làm cùng lượng work. Nếu query không cung cấp partition-key value phù hợp, Cosmos DB có thể phải thực hiện work trên nhiều physical/logical partition routes thay vì target hẹp. Filter mới hoặc sort mới cũng có thể làm lượng index/data work tăng tùy indexing policy và query shape.

Tôi sẽ không mặc định nguyên nhân là thiếu RU capacity. Trước hết so sánh request charge và query metrics của query cũ/mới trên cùng dataset, correlate theo endpoint/filter và kiểm tra partition-key routing. Sau đó xem indexing policy có phù hợp với filter/sort, số partitions được chạm tới, dữ liệu được xét so với số kết quả trả về, và latency distribution.

Nếu endpoint có natural partition key nhưng code bỏ không truyền, sửa routing có thể giảm work đáng kể. Nếu access pattern thực sự cần query toàn tenant/container, cần đánh giá data model: có thể query đó là legitimate cross-partition workload và capacity phải đáp ứng, hoặc có thể cần read model/denormalization nếu business value và scale biện minh complexity. Không đổi partition key tùy tiện vì ảnh hưởng toàn container và migration.

Tôi sẽ load test với distribution production, theo dõi request charge, throttling, p95/p99 và partition-level behavior. Chỉ tăng throughput khi evidence cho thấy workload hợp lý nhưng capacity không đủ.

## Mẫu trả lời trong phỏng vấn

“Điểm đầu tiên tôi sửa assumption là RU không chỉ phụ thuộc số documents trả về. Hai query cùng trả 20 rows nhưng một query target đúng partition còn query kia fan-out hoặc phải làm nhiều index/data work thì cost có thể khác nhiều.

Tôi sẽ lấy request charge và query metrics của query cũ/mới, kiểm tra partition key có nằm trong predicate không, query chạm bao nhiêu partitions và indexing policy có hỗ trợ filter/sort mới không. Tôi cũng kiểm tra traffic distribution để phân biệt query regression với capacity issue.

Nếu natural partition key có sẵn mà endpoint không truyền, tôi ưu tiên sửa query/routing. Nếu business requirement thật sự là cross-partition search, tôi đánh giá liệu cost đó có chấp nhận được hay cần read model khác. Tôi không đổi partition key hoặc tăng RU trước khi có evidence vì hai giải pháp đều có cost và có thể che nguyên nhân. Sau thay đổi tôi load test và theo dõi RU/request, throttling và p95/p99.”

## Câu hỏi đào sâu

1. Hot partition và cross-partition query khác nhau thế nào về symptom và remediation?
2. Nếu query bắt buộc cross-partition nhưng traffic thấp, bạn có tạo read model riêng không?
3. Nếu tăng throughput làm hết 429 nhưng RU/request vẫn cao bất thường, bạn coi incident đã giải quyết chưa?

## Lỗi trả lời thường gặp

- Đồng nhất RU với số rows trả về.
- Đổi partition key ngay mà không phân tích access patterns toàn hệ thống.
- Chỉ tăng throughput.
- Chỉ nhìn average latency, bỏ request charge và partition behavior.

## Thang điểm 0–10

- **0–2:** Chỉ biết “Cosmos DB tính RU”.
- **3–4:** Nhắc partition/index nhưng không liên kết với query work.
- **5–6:** Giải thích đúng routing, query shape và measurement.
- **7–8:** Có data-model trade-off, testing và production evidence.
- **9–10:** Reasoning conditional, cân bằng cost, migration complexity và scale rất rõ.

# Câu 2 — Akamai vẫn phục vụ trang cũ sau CMS publish

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Akamai/CDN, Optimizely CMS, HTTP caching, cache invalidation, observability, incident response

## Bối cảnh

Một marketing website dùng Optimizely CMS phía origin và Akamai phía trước. Sau một campaign publish, một nhóm người dùng vẫn thấy hero banner và canonical metadata cũ trong 25–40 phút, trong khi editor preview và request trực tiếp tới origin đã thấy content mới. Một số URL cập nhật gần như ngay lập tức.

Team nghi CDN và muốn purge toàn bộ site sau mỗi publish. Không rõ response headers hiện tại, cache key có vary theo query/cookie hay không, hoặc publish workflow có phát purge/invalidation event hay không. Website có traffic cao; purge toàn site có thể tạo tải lớn lên origin.

## Câu hỏi chính

Bạn sẽ stabilize và điều tra incident này thế nào theo chuỗi impact → evidence → hypotheses → verification → remediation, đồng thời thiết kế cache invalidation an toàn hơn mà không mặc định “purge everything” là giải pháp?

## Câu hỏi làm rõ nên cân nhắc

1. URL nào bị stale, URL nào không, và chúng khác nhau về cache policy/cache key thế nào?
2. `Cache-Control`, `Age`, CDN cache status và surrogate/invalidation metadata thực tế là gì?
3. Publish là atomic cho page + referenced blocks/assets hay có nhiều bước?
4. Purge hiện tại target URL nào và có retry/telemetry không?
5. SEO metadata và HTML có cùng cache object/lifetime không?

## Gợi ý tư duy

### Gợi ý 1

Origin đúng không chứng minh edge đúng; cần quan sát response ở từng layer.

### Gợi ý 2

Phân biệt TTL expiry, cache-key mismatch, failed invalidation và multi-object content dependency.

### Gợi ý 3

Purge toàn site có thể chuyển stale-content incident thành origin-overload incident.

## Cấu trúc trả lời đề xuất

1. Xác định business/SEO impact và affected URL set.
2. Stabilize bằng targeted invalidation nếu xác định được scope.
3. Capture headers từ affected edge responses và origin.
4. Xây timeline publish/invalidation/cache behavior.
5. Form competing hypotheses.
6. Verify cache key, TTL, purge delivery và referenced content dependencies.
7. Fix invalidation contract.
8. Test publish-to-edge propagation.
9. Monitor freshness và purge failures.
10. Review fallback khi CDN/invalidation dependency lỗi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- So sánh edge response với origin bằng headers/evidence.
- Kiểm tra `Cache-Control`, `Age`, cache status/key behavior và invalidation logs.
- Không purge toàn site mặc định.
- Xem content dependencies: page, block, metadata, assets có thể invalidate khác nhau.
- Có targeted remediation và verification từ nhiều edge locations nếu cần.

### Điểm cộng

- Xem cookie/query-string variance và personalized content risk.
- Đề xuất publish event → deterministic affected-URL set → purge → retry/alert.
- Có stale-while-revalidate/TTL trade-off khi phù hợp requirement.

### Senior+

- Thiết kế cache strategy theo content class thay vì một TTL cho mọi thứ.
- Xem origin protection khi purge lớn: shielding/rate/gradual invalidation theo capability hiện có.
- Đưa SEO correctness vào acceptance tests cho canonical/redirect/status metadata.

## Hướng giải quyết tham khảo

Đầu tiên xác định scope và mức độ: campaign URL, regions, anonymous/authenticated, HTML hay assets. Nếu impact cao và biết affected URLs, targeted invalidation là stabilization hợp lý hơn purge toàn site. Sau đó capture edge headers và origin headers cho cùng URL để chứng minh object nào stale và cache semantics hiện tại.

Các hypotheses gồm TTL đơn giản chưa hết; purge không được gửi hoặc thất bại; purge gửi sai URL/cache key; query/cookie tạo variants; page phụ thuộc content block nhưng publish event chỉ invalidate page hoặc ngược lại; nhiều edge objects có policy khác nhau.

Tôi sẽ correlate CMS publish timestamp với invalidation request/result và edge `Age`/cache status. Nếu invalidation workflow không durable/retryable, cần làm rõ delivery guarantee và observability. Thiết kế tốt hơn là từ publish event xác định tập affected URLs/objects theo content dependency, gửi targeted invalidation, ghi operation ID/result, retry bounded và alert khi propagation vượt SLO.

Không nên đặt mọi content `no-store` chỉ để tránh invalidation; điều đó bỏ lợi ích CDN. Cũng không purge toàn site thường xuyên vì miss storm có thể tăng origin load. Cache policy nên theo content class: HTML campaign-sensitive có TTL/invalidation khác static versioned assets.

Testing gồm publish page, shared block được dùng trên nhiều pages, canonical metadata, redirect và failed purge simulation. Production dashboard nên có purge success/failure, propagation latency, origin traffic/cache hit ratio và freshness probes cho critical pages.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ chứng minh stale nằm ở layer nào trước. Tôi lấy cùng URL từ edge và origin, xem `Cache-Control`, `Age`, cache status và cache-key variance, rồi correlate với CMS publish và purge logs. Origin đã mới chỉ cho biết CMS publish thành công, chưa cho biết edge object đã invalidated.

Tôi giữ nhiều hypotheses: TTL chưa hết, purge fail, purge sai variant, hoặc shared block/page dependency không được map đúng. Nếu campaign đang ảnh hưởng user, tôi targeted purge các URLs đã xác định thay vì purge toàn site để tránh origin spike.

Long-term tôi muốn publish workflow tạo deterministic affected-object set, purge có operation tracking/retry/alert và freshness SLO. Static versioned assets có thể cache dài, còn HTML nhạy với publish dùng policy khác. Tôi sẽ test cả shared blocks và SEO metadata vì một publish có thể ảnh hưởng nhiều URLs. Sau fix tôi theo dõi cache hit ratio, origin load, purge propagation latency và synthetic freshness probes.”

## Câu hỏi đào sâu

1. Nếu một shared Optimizely block xuất hiện trên 2.000 pages, targeted invalidation còn đơn giản không?
2. Bạn chọn TTL ngắn thay cho purge event-driven trong trường hợp nào?
3. Nếu purge toàn site khắc phục stale ngay, tại sao đó vẫn có thể là design kém?

## Lỗi trả lời thường gặp

- Purge toàn site ngay như permanent solution.
- Chỉ kiểm tra CMS publish log.
- Không xem cache variants/query/cookies.
- Bỏ qua origin load sau mass invalidation.
- Không test SEO metadata và shared content dependencies.

## Thang điểm 0–10

- **0–2:** Chỉ nói clear cache.
- **3–4:** Biết TTL/purge nhưng thiếu evidence-driven incident flow.
- **5–6:** Có headers, cache key, targeted purge và monitoring.
- **7–8:** Có dependency-aware invalidation, failure handling và tests.
- **9–10:** Cân bằng freshness, origin protection, SEO và operational complexity ở mức architecture.

# Câu 3 — Thiết kế file-processing platform: Blob Storage + Functions hay App Service worker?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, Azure Functions, BackgroundService, Service Bus, security, idempotency, failure recovery, architecture trade-offs

## Bối cảnh

Một enterprise portal cho phép người dùng upload CSV/JSON files để import dữ liệu. File từ vài MB đến vài trăm MB. Sau upload, hệ thống validate, parse, ghi dữ liệu vào SQL Server và tạo report lỗi. Business muốn upload không giữ HTTP request mở trong suốt quá trình xử lý; người dùng cần xem trạng thái và tải error report.

Team đang cân nhắc: backend proxy toàn bộ upload rồi `BackgroundService` xử lý; browser upload trực tiếp Blob Storage bằng scoped access rồi Azure Functions xử lý; hoặc Blob + Service Bus + worker. Chưa rõ peak concurrency, processing duration hay requirement ordering. Security yêu cầu user không được ghi vào arbitrary blob path và processor dùng least privilege.

## Câu hỏi chính

Bạn sẽ làm rõ requirements và chọn kiến trúc nào cho file-processing workflow này? Hãy trình bày API/data model, upload boundary, asynchronous processing, idempotency, security, failure recovery, observability, deployment và các điều kiện khiến bạn đổi lựa chọn.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent uploads, file-size distribution và processing time là bao nhiêu?
2. Một file có cần atomic import hay chấp nhận partial success?
3. Có ordering/deduplication requirement theo tenant/import type không?
4. Error report chứa dữ liệu nhạy cảm và retention policy thế nào?
5. Retry một file sau partial DB write phải có semantics gì?

## Gợi ý tư duy

### Gợi ý 1

Tách upload transport khỏi processing lifecycle.

### Gợi ý 2

Blob chỉ giải quyết durable object storage; workflow vẫn cần ownership, state và retry semantics.

### Gợi ý 3

Functions, worker hay messaging là quyết định dựa trên duration/load/failure model, không phải hierarchy “modern hơn”.

## Cấu trúc trả lời đề xuất

1. Clarify scale, duration, consistency và security.
2. Define import job state machine.
3. Chọn upload path và authorization.
4. Chọn processing trigger/queue ownership.
5. Thiết kế idempotency và transaction boundaries.
6. Failure/retry/DLQ/reconciliation.
7. Status/report APIs.
8. Observability và audit.
9. Deployment/scaling.
10. Test và nêu conditions đổi architecture.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giữ HTTP request cho long-running import.
- Blob Storage là durable file boundary hợp lý; direct upload có thể giảm backend bandwidth nếu access được scope chặt.
- Có durable import-job state (`Uploaded/Queued/Processing/Completed/Failed` hoặc tương đương).
- Retry phải đi cùng idempotency/partial-write strategy.
- Processor dùng Managed Identity/least privilege khi phù hợp; upload token/SAS phải scope/time-bound theo requirement.
- Không mặc định cần Service Bus nếu trigger đơn giản đủ đáp ứng failure model.

### Điểm cộng

- Quarantine/validation cho file trước business import.
- Checksum/business import ID để deduplicate khi phù hợp.
- Streaming/chunk processing thay vì load file lớn toàn bộ vào memory.
- Error report retention/access control rõ ràng.

### Senior+

- So sánh Blob-triggered Function với queue-mediated processing về backpressure, retry visibility, poison work và operational control.
- Xem transaction chunking/checkpoint nếu import lớn.
- Có tenant isolation, quota và abuse protection.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng scale/duration/consistency. Với file lớn và processing lâu, HTTP request chỉ nên tạo import session/job rồi upload độc lập. Một hướng hợp lý là API tạo `ImportJob` và cấp quyền upload giới hạn cho đúng blob/object; client upload trực tiếp Blob Storage nếu security model cho phép. Processor truy cập Blob bằng service identity/Managed Identity với least privilege.

Sau upload, cần durable state. Nếu workload vừa phải và Blob-triggered Functions đáp ứng duration/retry/operational needs, đó có thể là lựa chọn đơn giản. Nếu cần backpressure rõ, controlled concurrency, DLQ, retries và tách upload events khỏi processing, Blob event/producer có thể enqueue Service Bus message và consumers xử lý. Nếu processing dài, cần custom lifecycle hoặc dependency/tooling phù hợp worker, `BackgroundService`/worker service cũng defensible. Không chọn messaging chỉ vì pattern phổ biến.

Idempotency là trọng tâm. Mỗi import có stable ID; database writes phải biết retry semantics. Với atomic import nhỏ có thể transaction; với file lớn có thể chunk/checkpoint và staging tables, sau đó commit/promote theo business requirement. Retry sau partial write không được duplicate rows. File parsing nên streaming nếu kích thước khiến full-memory load không an toàn.

Security: upload credential chỉ cho operation/path cần thiết, TTL ngắn theo workflow, validate content/type/size, không tin filename làm storage path, report lỗi có authorization/retention. Processor không dùng account key hard-coded.

Observability gồm queue/job age, processing duration, rows processed/rejected, retry/DLQ, blob read failures, SQL dependency latency và correlation theo ImportJobId. API cho user xem status và lấy report qua authorized path.

Nếu workload rất thấp, backend-proxied upload có thể vẫn đủ và đơn giản hơn. Nếu file size/bandwidth cao, direct-to-Blob có lợi hơn. Nếu processing requirements vượt Function model hoặc cần kiểm soát concurrency/lifecycle sâu, worker là lựa chọn tốt hơn. Recommendation phải đổi theo evidence.

## Mẫu trả lời trong phỏng vấn

“Tôi tách upload khỏi processing. API tạo `ImportJob`, sau đó nếu file lớn và traffic đáng kể tôi ưu tiên direct upload vào Blob bằng quyền scope đúng object và thời gian ngắn. Processor dùng Managed Identity thay vì shared secret.

Sau upload, tôi cần durable job state và stable ImportJobId. Tôi chưa mặc định Service Bus: nếu Blob-triggered Function đủ cho duration/retry và operations thì đơn giản hơn. Nếu cần backpressure, DLQ và controlled concurrency rõ, tôi thêm Service Bus. Nếu processing dài hoặc cần lifecycle đặc thù, worker service có thể phù hợp hơn.

Retry phải idempotent. Với file lớn tôi cân nhắc staging/chunk checkpoint thay vì một transaction khổng lồ; partial retry không được insert duplicate. Parsing nên streaming. Error report cũng là protected artifact có retention.

Tôi theo dõi job age, processing latency, retry/DLQ, row counts và SQL dependencies. Nếu volume thấp, proxy upload qua backend vẫn có thể là lựa chọn hợp lý; tôi chỉ thêm infrastructure khi scale và failure model thực sự cần.”

## Câu hỏi đào sâu

1. Nếu mỗi file mất 45 phút để xử lý, yếu tố nào khiến bạn nghiêng khỏi một Function implementation cụ thể?
2. Nếu business yêu cầu toàn bộ file import atomic nhưng file có hàng triệu rows, bạn đánh đổi thế nào?
3. Service Bus thêm giá trị gì nếu Blob event đã có thể kích hoạt processing, và khi nào giá trị đó không đáng complexity?

## Lỗi trả lời thường gặp

- Upload file lớn qua API rồi xử lý ngay trong request.
- Chọn Functions hoặc Service Bus vì “serverless/event-driven là tốt hơn”.
- Retry mà không có idempotency/partial-write design.
- Dùng storage account key trong config.
- Load toàn bộ file lớn vào memory mà không xét size distribution.

## Thang điểm 0–10

- **0–2:** Chỉ liệt kê Azure services.
- **3–4:** Có async processing nhưng thiếu state/failure/security.
- **5–6:** Thiết kế hợp lý với Blob, job state, retry và access control.
- **7–8:** Có conditional technology choice, backpressure, staging và observability.
- **9–10:** Cân bằng simplicity, consistency, security, scale và operational failure modes ở mức architect.

## Kiến thức trọng tâm

Cosmos DB query cost phải được hiểu từ partition routing và lượng work thực tế thay vì số documents trả về. - Chọn infrastructure theo failure model và operational need, không theo độ “hiện đại”.
- Tách transport, durable state và processing ownership thành các quyết định riêng.
