# Code Review Challenge 1 — File upload API đọc toàn bộ file vào memory và tin metadata từ client

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, file streaming, security, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một document service cho phép users upload tài liệu lên Azure Blob Storage thông qua ASP.NET Core API. API chạy nhiều instances trên Azure App Service Linux. Production thường nhận file 5–30 MB, nhưng một số workflow hợp lệ có thể upload file lớn hơn đáng kể. Business yêu cầu tenant isolation, không overwrite nhầm tài liệu, và request bị client hủy không nên tiếp tục tiêu tốn tài nguyên vô hạn.

Sau khi traffic tăng, team thấy memory tăng theo số upload đồng thời, GC pause tăng và một vài instance restart. Security review cũng phát hiện client có thể tự gửi `containerName`, `blobName` và `contentType`. Team đang cân nhắc tăng App Service memory như remediation chính.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/files")]
[Authorize]
public sealed class FilesController : ControllerBase
{
    private readonly BlobServiceClient _blobServiceClient;
    private readonly ILogger<FilesController> _logger;

    public FilesController(
        BlobServiceClient blobServiceClient,
        ILogger<FilesController> logger)
    {
        _blobServiceClient = blobServiceClient;
        _logger = logger;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(
        IFormFile file,
        [FromForm] string containerName,
        [FromForm] string blobName,
        [FromForm] string contentType)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        using var memory = new MemoryStream();
        await file.CopyToAsync(memory);
        var bytes = memory.ToArray();

        var container = _blobServiceClient.GetBlobContainerClient(containerName);
        await container.CreateIfNotExistsAsync();

        var blob = container.GetBlobClient(blobName);

        await blob.UploadAsync(
            new BinaryData(bytes),
            overwrite: true);

        await blob.SetHttpHeadersAsync(new BlobHttpHeaders
        {
            ContentType = contentType
        });

        _logger.LogInformation(
            "Uploaded {FileName} to {Container}/{BlobName}, size={Size}",
            file.FileName,
            containerName,
            blobName,
            bytes.Length);

        return Ok(new
        {
            container = containerName,
            blob = blobName
        });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems.
2. Xác định performance, security và reliability concerns.
3. Giải thích impact khi nhiều uploads lớn chạy đồng thời.
4. Ưu tiên tenant isolation, memory amplification và overwrite risk trước style issues.
5. Đề xuất corrected implementation/design phù hợp với App Service và Blob Storage.
6. Giải thích testing cho large file, cancellation, authorization và duplicate blob names.
7. Nêu telemetry production cần có để chứng minh remediation hiệu quả.

## Câu hỏi gợi mở

1. Một file 100 MB có thể tồn tại bao nhiêu bản copy trong managed memory ở implementation này?
2. Client có nên quyết định physical container/blob namespace không?
3. `overwrite: true` có semantics gì khi hai requests cùng chọn một blob name?
4. `Content-Type` từ multipart request có phải trust boundary an toàn không?
5. Request cancellation hiện được propagate tới Blob Storage operations ở đâu?

### Gợi ý 1

### Gợi ý 2

Hãy phân biệt logical document identity do application kiểm soát với physical blob path; upload stream nên được xử lý theo bounded-resource semantics và cancellation.

## Kết quả code review tham khảo

### Critical — Client kiểm soát storage namespace mà không có tenant authorization boundary

**Vấn đề:** `containerName` và `blobName` được nhận trực tiếp từ request rồi dùng làm physical storage destination.  
**Tại sao xảy ra:** authentication được coi như authorization cho mọi namespace.  
**Ảnh hưởng production:** tùy storage/account layout, user có thể ghi vào namespace không thuộc tenant của mình hoặc cố tình đụng tên tài liệu khác.  
**Cách sửa:** application phải derive tenant/document identity từ trusted authenticated context và server-side metadata. Physical container/blob path phải được tạo bởi server theo policy; cross-tenant access phải explicit và auditable.

### High — Toàn bộ file được nhân bản trong managed memory

**Vấn đề:** `IFormFile` được copy vào `MemoryStream`, sau đó `ToArray()` tạo thêm byte array, rồi `BinaryData` giữ payload cho upload.  
**Tại sao xảy ra:** implementation buffer toàn bộ content thay vì stream. Ngoài ra multipart handling có buffering behavior riêng tùy hosting/configuration cần đo thực tế.  
**Ảnh hưởng production:** concurrent large uploads tạo memory pressure, LOH allocations/GC pressure và process restart/OOM risk.  
**Cách sửa:** stream từ `OpenReadStream()` tới Blob client, đặt explicit request/file size policy và benchmark memory dưới concurrency. Với very-large-file requirements, cân nhắc direct-to-Blob upload bằng short-lived scoped SAS nếu threat model và architecture phù hợp.

### High — `overwrite: true` làm mất dữ liệu khi identity collision hoặc concurrent upload

**Vấn đề:** blob cùng tên bị replace mà không có business concurrency semantics.  
**Tại sao xảy ra:** storage path vừa là client input vừa được coi như unique business identity.  
**Ảnh hưởng production:** upload A có thể bị upload B ghi đè; retry cũng có thể thay content ngoài ý muốn.  
**Cách sửa:** tạo immutable/server-generated blob key hoặc dùng conditional write/versioning strategy phù hợp business requirement. Mapping document ID → blob key nên được persist với concurrency control nếu cần.

### High — Không propagate request cancellation

**Vấn đề:** copy, container operation, upload và header update không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** async được dùng nhưng cancellation boundary bị bỏ qua.  
**Ảnh hưởng production:** client disconnect có thể để server tiếp tục đọc/upload large payload, giữ memory/network resources trong deployment hoặc traffic spike.  
**Cách sửa:** propagate cancellation token qua cancellable operations và xử lý cancellation như expected request lifecycle.

### High — Không có explicit upload size/content policy

**Vấn đề:** chỉ reject zero-length file.  
**Tại sao xảy ra:** endpoint không enforce business maximum hoặc content constraints.  
**Ảnh hưởng production:** resource-exhaustion risk và storage abuse; infrastructure limits có thể fail request ở tầng khác với UX/telemetry kém.  
**Cách sửa:** xác định maximum theo business workflow, enforce ở request pipeline/application boundary và có exception path riêng nếu workflow thực sự cần file rất lớn.

### Medium — Tin `contentType` từ client

**Vấn đề:** client quyết định metadata được phục vụ lại sau này.  
**Tại sao xảy ra:** MIME type được coi là verified content classification.  
**Ảnh hưởng production:** nếu blob sau đó được render/download trong web origin, content sniffing hoặc unsafe content handling có thể tạo security issue tùy delivery design.  
**Cách sửa:** validate allowed types dựa trên business policy; khi cần, inspect file signature bằng bounded prefix thay vì tin extension/MIME. Serve downloads với safe headers và domain/origin strategy phù hợp.

### Medium — Upload và SetHttpHeaders là hai operations tách rời

**Vấn đề:** content upload có thể thành công nhưng header update fail.  
**Tại sao xảy ra:** metadata được set trong request thứ hai.  
**Ảnh hưởng production:** partial success và retry ambiguity.  
**Cách sửa:** truyền HTTP headers/options cùng upload operation nếu SDK API đang dùng hỗ trợ; nếu không, model partial state và retry có kiểm soát. Không giả định hai remote calls là atomic.

### Medium — `CreateIfNotExistsAsync` trên request path che ownership/configuration problem

**Vấn đề:** endpoint tự tạo container từ user input.  
**Tại sao xảy ra:** provisioning và request handling bị trộn.  
**Ảnh hưởng production:** namespace sprawl và permission requirements rộng hơn cần thiết.  
**Cách sửa:** provision known containers bằng deployment/bootstrap process hoặc server-side tenant policy; dùng Managed Identity/least privilege cho storage access.

### Medium — Logging chưa đủ correlation và có thể chứa user-controlled text

**Vấn đề:** log file/path values nhưng thiếu tenant/document/request identity; user-controlled strings có thể tạo noisy/high-cardinality logs.  
**Tại sao xảy ra:** log phục vụ debug đơn lẻ thay vì operational model.  
**Ảnh hưởng production:** khó trace partial uploads và memory incidents.  
**Cách sửa:** structured log trusted document ID, tenant ID phù hợp privacy policy, upload outcome, bytes, duration và storage dependency correlation; tránh secrets/SAS URLs.

## Phiên bản đề xuất

Ví dụ dưới đây giả định application đã resolve `tenantId` từ trusted authorization context và tạo `documentId` server-side. Maximum size chỉ là application policy placeholder; giá trị thật phải đến từ requirement và hosting constraints.

```csharp
[HttpPost("upload")]
public async Task<IActionResult> Upload(
    IFormFile file,
    CancellationToken cancellationToken)
{
    if (file is null || file.Length <= 0)
        return BadRequest("Empty file");

    var tenantId = GetAuthorizedTenantId(User);
    var documentId = Guid.NewGuid();

    ValidateFilePolicy(file);

    var container = _blobServiceClient
        .GetBlobContainerClient("documents");

    var blobName = $"{tenantId:N}/{documentId:N}";
    var blob = container.GetBlobClient(blobName);

    await using var source = file.OpenReadStream();

    var options = new BlobUploadOptions
    {
        HttpHeaders = new BlobHttpHeaders
        {
            ContentType = GetValidatedContentType(file)
        },
        Conditions = new BlobRequestConditions
        {
            IfNoneMatch = ETag.All
        },
        Metadata = new Dictionary<string, string>
        {
            ["documentId"] = documentId.ToString("N")
        }
    };

    try
    {
        await blob.UploadAsync(source, options, cancellationToken);
    }
    catch (RequestFailedException ex) when (ex.Status == StatusCodes.Status412PreconditionFailed)
    {
        return Conflict();
    }

    _logger.LogInformation(
        "Uploaded document {DocumentId} for tenant {TenantId}, size={Size}",
        documentId,
        tenantId,
        file.Length);

    return Created($"api/files/{documentId}", new { documentId });
}
```

`GetAuthorizedTenantId`, `ValidateFilePolicy` và `GetValidatedContentType` đại diện cho application-specific authorization/security policy, không phải framework APIs có sẵn. Nếu container chưa tồn tại, provisioning nên được thực hiện ngoài hot request path hoặc bằng trusted bootstrap logic.

## Giải thích thiết kế sau khi sửa

Server kiểm soát namespace và dùng immutable document identity. Upload đi trực tiếp từ source stream tới Blob client thay vì materialize toàn payload thành byte array. Conditional create ngăn accidental overwrite của generated key. Cancellation được propagate.

Nếu requirement là upload hàng GB hoặc user ở xa application region, backend-proxy design có thể không tối ưu. Khi đó có thể cấp short-lived, least-privilege SAS chỉ cho một blob key cụ thể rồi để browser upload trực tiếp; backend vẫn chịu trách nhiệm authorization, metadata record và completion validation. Không nên chuyển sang direct upload chỉ vì “Blob hỗ trợ SAS” nếu threat model, CORS, malware scanning hoặc audit workflow chưa được thiết kế.

## Trade-offs

Streaming giảm managed-memory amplification nhưng request vẫn giữ connection/server resources trong thời gian upload. Direct-to-Blob giảm backend bandwidth nhưng tăng complexity về SAS lifecycle, completion verification và client retry. Immutable blob names tránh overwrite nhưng cần lifecycle/cleanup cho abandoned uploads. File signature validation tăng CPU/I/O và chỉ nên đọc bounded prefix thay vì buffer toàn file.

## Cách kiểm thử

1. **Load test:** nhiều uploads lớn đồng thời; theo dõi working set, allocations/GC, request p95/p99 và storage dependency latency.
2. **Security/integration test:** authenticated tenant A không thể chọn hoặc overwrite path của tenant B.
3. **Cancellation test:** abort request giữa upload; verify server releases work trong bounded time và telemetry phân biệt cancellation với failure.
4. **Concurrency test:** hai attempts cho cùng logical document/key không silently overwrite khi policy yêu cầu create-only.
5. **Failure-path test:** Blob Storage timeout/5xx; verify partial state, retry behavior và response contract không báo success sai.

## Quan sát trong production

Theo dõi concurrent uploads, bytes in-flight, request duration, process working set, allocation/GC counters, 4xx/5xx, cancellations, Blob dependency duration/failures và storage throttling signals. Correlate request ID → tenant/document ID → Blob dependency trong Application Insights. Alert dựa trên memory pressure/restart và upload failure rate, không chỉ CPU.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn direct browser-to-Blob bằng SAS thay vì backend streaming?
2. Nếu cần antivirus/malware scanning trước khi file được phép download, bạn thay đổi lifecycle và storage layout thế nào?
3. Nếu business yêu cầu replace document nhưng vẫn audit được mọi version, bạn thiết kế identity/concurrency thế nào?

# Code Review Challenge 2 — Kubernetes deployment chứa secret trong manifest và liveness probe tự tạo restart loop

**Chủ đề:** Kubernetes, ASP.NET Core health checks, Secrets/configuration, resource limits, graceful rollout, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core internal portal vừa được chuyển từ IIS/Windows Server sang container và Kubernetes. Deployment chạy 6 replicas. App cần khoảng 25–45 giây để warm caches và kết nối dependencies sau cold start. Endpoint `/health` hiện kiểm tra SQL Server, Redis và một third-party API.

Sau release, một số pods liên tục restart khi Redis hoặc third-party API chập chờn, rollout có lúc không đạt đủ capacity. Security team phát hiện database password nằm trong repository manifest. Team đề xuất tăng `failureThreshold` của liveness probe và commit một password mới sau mỗi rotation.

## Kết quả code review tham khảo

### Critical — Production credential được hard-code trong repository manifest

**Vấn đề:** SQL username/password nằm trong source-controlled YAML.  
**Tại sao xảy ra:** deployment configuration được dùng như secret store.  
**Ảnh hưởng production:** credential có thể tồn tại trong Git history, clones, CI logs hoặc review artifacts; rotation bằng commit mới không xóa exposure cũ.  
**Cách sửa:** rotate credential ngay theo incident procedure và chuyển secret sang approved secret-management mechanism. Với Azure-hosted workload, đánh giá Managed Identity/Key Vault integration nếu architecture hỗ trợ; nếu dùng Kubernetes Secret, hiểu rằng Secret object không tự động là external secret vault và vẫn cần RBAC/encryption/rotation policy.

### High — Liveness phụ thuộc downstream dependencies

**Vấn đề:** cùng `/health` kiểm tra SQL, Redis, third-party API cho liveness.  
**Tại sao xảy ra:** service readiness/dependency health bị đồng nhất với process recoverability.  
**Ảnh hưởng production:** dependency outage khiến healthy process bị restart, làm mất capacity và có thể tạo retry/reconnect storm.  
**Cách sửa:** liveness chỉ phản ánh trạng thái mà restart process có khả năng chữa được; readiness có thể phản ánh khả năng phục vụ request nhưng dependency checks phải chọn lọc để tránh loại toàn fleet vì shared dependency outage.

### High — Startup window không phù hợp warmup

**Vấn đề:** liveness bắt đầu sau 5 giây trong khi startup hợp lệ có thể mất 25–45 giây.  
**Tại sao xảy ra:** không có startup probe hoặc startup budget phù hợp.  
**Ảnh hưởng production:** pod có thể bị restart trước khi hoàn tất startup, tạo CrashLoop-like cycle dù application không crash.  
**Cách sửa:** dùng `startupProbe` với budget dựa trên measured worst-case startup; liveness/readiness chỉ có hiệu lực phù hợp sau startup semantics.

### High — Image dùng mutable `latest` tag

**Vấn đề:** manifest không pin immutable artifact identity.  
**Tại sao xảy ra:** tag mutable được coi như version.  
**Ảnh hưởng production:** replicas/redeploy có thể chạy image khác nhau tùy pull/cache policy; rollback và audit khó tái lập.  
**Cách sửa:** deploy immutable version tag và tốt hơn là digest trong pipeline; promote cùng artifact qua environments.

### High — Resource budget có nguy cơ không phản ánh runtime thực tế

**Vấn đề:** memory request và limit đều 128Mi, CPU limit 100m nhưng không có evidence đây là measured working set/CPU requirement.  
**Tại sao xảy ra:** resource values có vẻ được chọn tĩnh.  
**Ảnh hưởng production:** memory limit thấp có thể gây OOM kill; CPU limit thấp có thể tạo throttling/latency và kéo dài startup.  
**Cách sửa:** profile/load-test container, quan sát working set/GC/CPU throttling rồi đặt requests/limits theo capacity/SLO; không xóa limits hoặc tăng tùy ý mà không đo.

### Medium — Readiness dùng cùng dependency aggregate mà không có degradation semantics

**Vấn đề:** shared dependency failure có thể làm tất cả replicas unready cùng lúc.  
**Tại sao xảy ra:** readiness được thiết kế như “mọi dependency đều xanh”.  
**Ảnh hưởng production:** service mất toàn bộ endpoints dù một số request paths có thể vẫn phục vụ được hoặc graceful degradation khả thi.  
**Cách sửa:** thiết kế readiness theo khả năng phục vụ core traffic và dependency criticality; non-critical dependency nên có degradation/fallback/telemetry thay vì luôn remove pod.

### Medium — RollingUpdate không nêu capacity constraints

**Vấn đề:** không explicit `maxUnavailable`/`maxSurge` theo SLO và startup behavior.  
**Tại sao xảy ra:** default rollout behavior được chấp nhận mà chưa capacity-model.  
**Ảnh hưởng production:** với slow startup hoặc probe instability, rollout có thể giảm effective capacity.  
**Cách sửa:** chọn rollout parameters dựa trên headroom và SLO; validate bằng deployment test. `maxUnavailable: 0` không tự đảm bảo zero errors nếu readiness/draining sai.

### Medium — Không thể hiện graceful termination/draining design

**Vấn đề:** manifest không cho thấy termination budget phù hợp long-running requests/background work.  
**Tại sao xảy ra:** deployment tập trung startup mà bỏ shutdown lifecycle.  
**Ảnh hưởng production:** rolling update có thể reset in-flight requests nếu process bị terminate trước khi drain.  
**Cách sửa:** đo request/shutdown duration, cấu hình `terminationGracePeriodSeconds` phù hợp và application graceful shutdown; kiểm tra ingress/service endpoint propagation.

### Low — Configuration ownership chưa tách secret và non-secret

**Vấn đề:** connection/config values nằm trực tiếp trong Deployment.  
**Tại sao xảy ra:** config lifecycle chưa được model.  
**Ảnh hưởng production:** environment promotion/rotation khó audit và dễ drift.  
**Cách sửa:** non-secret config có thể đi qua ConfigMap hoặc deployment configuration system; secrets qua dedicated secret path. Tránh abstraction chỉ để “đúng mẫu” nếu pipeline hiện tại đã cung cấp equivalent controls.

## Phiên bản đề xuất

Manifest dưới đây minh họa lifecycle/resource structure; secret integration cụ thể phụ thuộc cluster/platform. `employee-portal-config` và `employee-portal-secrets` phải được provision bởi deployment/secret-management workflow, không chứa plaintext secret trong repository.

```yaml

    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 2
  selector:
    matchLabels:
      app: employee-portal
  template:
    metadata:
      labels:
        app: employee-portal
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example/employee-portal@sha256:<immutable-digest>
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: employee-portal-config
            - secretRef:
                name: employee-portal-secrets
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
          resources:
            requests:
              cpu: "<measured-request>"
              memory: "<measured-request>"
            limits:
              cpu: "<measured-limit>"
              memory: "<measured-limit>"
```

Các placeholder resource values phải được thay bằng values từ load/profile data. `secretRef` chỉ minh họa injection boundary; production secret architecture phải đáp ứng encryption, RBAC, rotation và platform requirements. Nếu Azure Managed Identity loại bỏ được SQL password, đó thường là hướng đáng đánh giá hơn việc luân chuyển static password, nhưng phải xác minh driver/database/authentication support của deployment hiện tại.

## Giải thích thiết kế sau khi sửa

Startup probe dành riêng budget cho cold start. Liveness không dùng shared dependency outage như lý do restart process. Readiness phản ánh traffic admission và phải được implement theo critical request capability thay vì một aggregate “mọi thứ phải online”. Artifact được pin immutable để rollout/rollback reproducible.

Resource settings không thể suy ra từ snippet nên phiên bản đề xuất cố ý không bịa số production. Team phải đo CPU throttling, memory working set, GC và startup under load trước khi chốt values.

## Trade-offs

`maxUnavailable: 0` cần cluster capacity cho surge pods và không chữa readiness/draining bug. Startup budget quá dài làm detection của truly stuck startup chậm hơn; quá ngắn tạo restart loop. Readiness dependency checks quá strict có thể tạo fleet-wide outage, nhưng quá loose có thể route request vào pod không thể phục vụ core operation. External secret integration tăng operational components nhưng giảm secret exposure và hỗ trợ rotation tốt hơn.

## Cách kiểm thử

1. **Deployment validation:** deploy immutable image revision và verify mọi pod chạy đúng digest, rollout giữ required ready capacity.
2. **Failure-path test:** làm Redis/third-party dependency unavailable; liveness phải tiếp tục healthy nếu process vẫn recoverable, readiness/degradation behavior phải đúng design.
3. **Startup test:** cold start ở realistic load phải hoàn tất trong startup probe budget mà không restart loop.
4. **Resource/load test:** theo dõi CPU throttling, working set, OOM kills, GC và p95/p99 để tune requests/limits.
5. **Security validation:** repository/CI artifacts không chứa production credential; rotated old credential không còn usable và workload lấy secret/identity qua approved path.

## Quan sát trong production

Theo dõi pod restarts theo reason, readiness transitions, startup duration, deployment revision/digest, OOMKilled events, CPU throttling, memory working set, request p95/p99, 5xx và dependency health. Correlate Kubernetes lifecycle events với Application Insights traces. Alert khi rollout-correlated error rate tăng hoặc ready replica count xuống dưới capacity threshold.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL Server là dependency bắt buộc cho mọi endpoint, readiness nên phản ứng thế nào khi SQL outage kéo dài?
2. Kubernetes Secret có giải quyết toàn bộ secret-management problem không? Còn những controls nào cần có?
3. Với một internal portal chỉ có 6 replicas và operational team nhỏ, khi nào quay lại Azure App Service có thể là quyết định đơn giản và hợp lý hơn Kubernetes?

Challenge hôm nay tập trung vào hai boundary dễ bị bỏ qua khi hệ thống chuyển từ development sang production: resource/trust boundary của file upload và lifecycle/security boundary của container deployment.
