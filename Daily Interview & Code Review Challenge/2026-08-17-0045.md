# Code Review Challenge 1 — Race condition khi cập nhật approval và gửi notification

**Chủ đề:** Concurrency, EF Core transaction handling, idempotency, background jobs  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API xử lý việc manager approve timesheet. Khi approve thành công, hệ thống cập nhật trạng thái trong SQL Server và enqueue Hangfire job để gửi notification.

Production có thể có nhiều request đồng thời do user double-click, retry từ frontend hoặc hai manager thao tác gần nhau. Team báo cáo thỉnh thoảng cùng một timesheet bị approve hai lần, notification được gửi trùng, và đôi lúc audit log không khớp trạng thái cuối cùng.

Yêu cầu quan trọng:

- Một timesheet chỉ được chuyển từ `Submitted` sang `Approved` một lần.
- Không được mất notification sau khi transaction DB commit.
- Retry phải an toàn.
- API cần hỗ trợ cancellation.

## Đoạn code cần review

```csharp
public sealed class TimesheetApprovalService
{
    private readonly AppDbContext _db;
    private readonly IBackgroundJobClient _jobs;
    private readonly ILogger<TimesheetApprovalService> _logger;

    public TimesheetApprovalService(
        AppDbContext db,
        IBackgroundJobClient jobs,
        ILogger<TimesheetApprovalService> logger)
    {
        _db = db;
        _jobs = jobs;
        _logger = logger;
    }

    public async Task ApproveAsync(
        int timesheetId,
        int approverId,
        CancellationToken cancellationToken)
    {
        var timesheet = await _db.Timesheets
            .FirstOrDefaultAsync(x => x.Id == timesheetId);

        if (timesheet == null)
            throw new InvalidOperationException("Timesheet not found");

        if (timesheet.Status == "Approved")
            return;

        timesheet.Status = "Approved";
        timesheet.ApprovedBy = approverId;
        timesheet.ApprovedAt = DateTime.UtcNow;

        _db.ApprovalHistories.Add(new ApprovalHistory
        {
            TimesheetId = timesheetId,
            ApproverId = approverId,
            Action = "Approved",
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _jobs.Enqueue<NotificationJob>(x =>
            x.SendTimesheetApprovedEmail(timesheetId));

        _logger.LogInformation(
            "Timesheet {TimesheetId} approved by {ApproverId}",
            timesheetId,
            approverId);
    }
}
```

## Gợi ý

### Gợi ý 1

Hãy tách ba bài toán: concurrent state transition, atomicity giữa DB và queue, và idempotency của side effect.

Một check `if (Status == "Approved")` trong application code không đủ để bảo vệ trước concurrent writers. Hãy nghĩ tới optimistic concurrency/conditional update và outbox.

## Kết quả code review tham khảo

### 1. Race condition khi hai request cùng approve

- **Problem:** Hai request có thể cùng đọc `Submitted`, cùng chuyển sang `Approved` và cùng tạo history.
- **Why it happens:** Check trạng thái và update không phải một atomic state transition.
- **Production impact:** Duplicate history, sai `ApprovedBy`, notification trùng, audit không đáng tin cậy.
- **Severity:** Critical
- **Recommended fix:** Dùng optimistic concurrency token (`rowversion`) hoặc conditional update `WHERE Id = @id AND Status = 'Submitted'`; chỉ request update thành công mới tiếp tục.

### 2. Dual-write giữa SQL và Hangfire không atomic

- **Problem:** DB commit thành công nhưng enqueue có thể fail hoặc process có thể crash trước khi enqueue.
- **Why it happens:** Hai hệ thống persistence độc lập không nằm trong cùng transaction guarantee.
- **Production impact:** Timesheet đã approved nhưng notification không bao giờ được gửi.
- **Severity:** Critical
- **Recommended fix:** Dùng transactional outbox: ghi business state và outbox message trong cùng DB transaction; worker riêng publish/enqueue sau.

### 3. Notification job không có idempotency contract rõ ràng

- **Problem:** Hangfire hoặc application retry có thể chạy job nhiều lần.
- **Why it happens:** Background processing thường cần chịu at-least-once execution.
- **Production impact:** Duplicate email hoặc side effects khác.
- **Severity:** High
- **Recommended fix:** Dùng operation/message ID ổn định; consumer kiểm tra/persist processed state hoặc thiết kế side effect idempotent khi có thể.

### 4. Cancellation token không được truyền cho EF Core

- **Problem:** `FirstOrDefaultAsync` và `SaveChangesAsync` bỏ qua token.
- **Why it happens:** Overload không có `cancellationToken` được dùng.
- **Production impact:** Request đã bị client cancel nhưng DB work vẫn tiếp tục, tăng resource usage và tạo behavior khó hiểu.
- **Severity:** Medium
- **Recommended fix:** Truyền token cho tất cả async DB operations phù hợp.

### 5. `InvalidOperationException` không biểu đạt domain/not-found rõ ràng

- **Problem:** Generic exception có thể bị map thành HTTP 500.
- **Why it happens:** Không có domain/application error contract.
- **Production impact:** Sai status code, log noise, client retry không cần thiết.
- **Severity:** Medium
- **Recommended fix:** Dùng typed result/domain exception và map thành 404/409 phù hợp.

### 6. String status dễ tạo invalid state

- **Problem:** Trạng thái được so sánh bằng string literal.
- **Why it happens:** Không có enum/value object/state transition abstraction.
- **Production impact:** Typo, inconsistent casing, transition không hợp lệ khó phát hiện.
- **Severity:** Medium
- **Recommended fix:** Dùng enum/value object hoặc domain method kiểm soát transition.

### 7. Audit time được lấy nhiều lần

- **Problem:** `ApprovedAt` và history `CreatedAt` có thể khác nhau không cần thiết.
- **Why it happens:** Gọi `DateTime.UtcNow` nhiều lần.
- **Production impact:** Nhỏ nhưng làm timeline/audit kém nhất quán.
- **Severity:** Low
- **Recommended fix:** Capture một `now` duy nhất qua `TimeProvider` để test dễ hơn.

### 8. Logging thiếu correlation/operation identity

- **Problem:** Chỉ log `TimesheetId` và `ApproverId`.
- **Why it happens:** Không có business operation ID hoặc trace context được dùng trong log message.
- **Production impact:** Khó phân biệt retry, duplicate request và background attempt.
- **Severity:** Medium
- **Recommended fix:** Log operation ID, trace ID, old/new status, affected rows và outbox message ID.

## Phiên bản code đề xuất

```csharp
public sealed class TimesheetApprovalService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public TimesheetApprovalService(
        AppDbContext db,
        TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task ApproveAsync(
        int timesheetId,
        int approverId,
        CancellationToken cancellationToken)
    {
        var now = _timeProvider.GetUtcNow().UtcDateTime;
        var operationId = Guid.NewGuid();

        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var affected = await _db.Timesheets
            .Where(x =>
                x.Id == timesheetId &&
                x.Status == TimesheetStatus.Submitted)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, TimesheetStatus.Approved)
                .SetProperty(x => x.ApprovedBy, approverId)
                .SetProperty(x => x.ApprovedAt, now),
                cancellationToken);

        if (affected == 0)
        {
            var exists = await _db.Timesheets
                .AsNoTracking()
                .AnyAsync(x => x.Id == timesheetId, cancellationToken);

            if (!exists)
                throw new TimesheetNotFoundException(timesheetId);

            throw new InvalidTimesheetStateException(timesheetId);
        }

        _db.ApprovalHistories.Add(new ApprovalHistory
        {
            TimesheetId = timesheetId,
            ApproverId = approverId,
            Action = "Approved",
            CreatedAt = now,
            OperationId = operationId
        });

        _db.OutboxMessages.Add(OutboxMessage.Create(
            operationId,
            "TimesheetApproved",
            new { TimesheetId = timesheetId }));

        await _db.SaveChangesAsync(cancellationToken);
        await transaction.CommitAsync(cancellationToken);
    }
}
```

Outbox publisher chịu trách nhiệm gửi message ra background processor. Consumer notification phải xử lý duplicate theo `OperationId`.

## Trade-offs

- `ExecuteUpdateAsync` tạo atomic conditional transition rõ ràng, nhưng bypass Change Tracker; nếu aggregate logic phức tạp thì optimistic concurrency trên entity có thể phù hợp hơn.
- Outbox tăng thêm bảng, worker và cleanup logic nhưng loại bỏ failure window giữa DB commit và enqueue.
- Distributed lock có thể giảm contention nhưng không thay thế idempotency hoặc transactional outbox.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 requests approve cùng timesheet; chỉ một request được phép thành công.
2. **Failure-path test:** giả lập crash ngay sau DB commit; outbox vẫn còn và notification cuối cùng được publish.
3. **Duplicate-delivery test:** gửi cùng outbox message nhiều lần; consumer chỉ gây side effect một lần.
4. **Cancellation test:** cancel request khi DB operation đang chạy; kiểm tra token được propagate đúng.
5. **State-transition test:** approve timesheet đang `Draft`, `Rejected` hoặc đã `Approved`; không được tạo history/outbox sai.

## Quan sát trong production

- Log `OperationId`, `TimesheetId`, `TraceId`, affected rows và outbox ID.
- Metric: approval conflicts, duplicate suppressions, outbox backlog, outbox oldest age, notification retries.
- Trace: API request → DB transaction → outbox publish → notification job.
- Alert khi outbox backlog hoặc oldest message age vượt ngưỡng vận hành.
- Theo dõi deadlocks/concurrency exceptions trong database.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào optimistic concurrency với `rowversion` tốt hơn conditional `ExecuteUpdateAsync`?
2. Transactional outbox xử lý được gì mà distributed lock không xử lý được?
3. Nếu email provider không hỗ trợ idempotency key thì bạn giảm duplicate side effect bằng cách nào?

# Code Review Challenge 2 — Authorization bypass và dữ liệu nhạy cảm trong endpoint tìm kiếm nhân viên

**Chủ đề:** Authentication/authorization, input validation, sensitive-data exposure, SQL/EF Core performance, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal ASP.NET Core API cho phép HR và manager tìm kiếm nhân viên. Endpoint được thêm nhanh để phục vụ dashboard mới.

Business rules:

- HR có thể xem nhân viên toàn công ty.
- Manager chỉ được xem nhân viên thuộc team mình quản lý.
- Không được trả `PersonalEmail`, `NationalId` hoặc salary cho manager.
- Search có thể nhận từ khóa user nhập trực tiếp.
- API có khoảng vài trăm nghìn employee records.

Production security review phát hiện một số manager có thể lấy thông tin ngoài team bằng cách thay query string.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeeController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeeController> _logger;

    public EmployeeController(
        AppDbContext db,
        ILogger<EmployeeController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? keyword,
        int? managerId,
        bool includeSensitive = false)
    {
        _logger.LogInformation(
            "Employee search keyword={Keyword} managerId={ManagerId}",
            keyword,
            managerId);

        var query = _db.Employees
            .Include(x => x.Manager)
            .Include(x => x.Office)
            .AsQueryable();

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            query = query.Where(x =>
                x.FullName.Contains(keyword) ||
                x.Email.Contains(keyword));
        }

        if (managerId.HasValue)
        {
            query = query.Where(x => x.ManagerId == managerId.Value);
        }

        var employees = await query
            .OrderBy(x => x.FullName)
            .Take(500)
            .ToListAsync();

        return Ok(employees.Select(x => new
        {
            x.Id,
            x.FullName,
            x.Email,
            x.PersonalEmail,
            x.NationalId,
            x.Salary,
            Manager = x.Manager?.FullName,
            Office = x.Office?.Name,
            Sensitive = includeSensitive
        }));
    }
}
```

## Kết quả code review tham khảo

### 1. Không có explicit authentication/authorization requirement

- **Problem:** Endpoint không có `[Authorize]` hoặc policy requirement thể hiện trong đoạn code.
- **Why it happens:** Có thể team dựa vào assumption rằng internal API đã được bảo vệ ở nơi khác.
- **Production impact:** Nếu route có thể truy cập ngoài expected boundary, toàn bộ employee data có thể bị lộ.
- **Severity:** Critical
- **Recommended fix:** Enforce authentication và authorization policy tại endpoint/controller hoặc global policy; defense in depth.

### 2. Caller kiểm soát `managerId`

- **Problem:** Manager có thể thay `managerId` thành manager khác hoặc bỏ filter.
- **Why it happens:** Authorization scope được lấy từ query string thay vì identity/server-side relationship.
- **Production impact:** Horizontal authorization bypass, xem dữ liệu ngoài team.
- **Severity:** Critical
- **Recommended fix:** Xác định caller identity từ authenticated principal; server tự derive team scope. Chỉ HR policy mới được phép query rộng hơn.

### 3. `includeSensitive` hoàn toàn do caller điều khiển

- **Problem:** Boolean query parameter không phải authorization control.
- **Why it happens:** Presentation preference bị nhầm với permission decision.
- **Production impact:** Manager có thể yêu cầu dữ liệu nhạy cảm.
- **Severity:** Critical
- **Recommended fix:** Quyết định projection dựa trên policy/role/claim được server xác minh, không dựa trên query parameter.

### 4. Response luôn chứa dữ liệu nhạy cảm

- **Problem:** `PersonalEmail`, `NationalId`, `Salary` luôn được serialize; field `Sensitive` chỉ echo flag.
- **Why it happens:** Không có separate DTO/projection theo permission.
- **Production impact:** PII và compensation data bị lộ.
- **Severity:** Critical
- **Recommended fix:** Projection tối thiểu; tách DTO cho HR và manager hoặc build projection theo authorized capability.

### 5. Materialize entity graph rồi mới project

- **Problem:** `Include` + `ToListAsync` load full entities trước khi mapping anonymous object.
- **Why it happens:** Projection được thực hiện sau materialization.
- **Production impact:** Đọc nhiều columns hơn cần thiết, tracking/memory overhead, tăng latency.
- **Severity:** High
- **Recommended fix:** `AsNoTracking()` và project sang DTO trước `ToListAsync`; bỏ `Include` nếu projection có thể translate navigation fields.

### 6. Không propagate cancellation token

- **Problem:** DB query tiếp tục khi request đã bị abort.
- **Why it happens:** Method không nhận `CancellationToken`.
- **Production impact:** Resource waste dưới load hoặc slow queries.
- **Severity:** Medium
- **Recommended fix:** Nhận token từ action parameter và truyền vào `ToListAsync`.

### 7. Search không có input constraints rõ ràng

- **Problem:** Keyword có thể quá dài hoặc wildcard/search pattern gây query tốn kém tùy provider/collation.
- **Why it happens:** Không validate length/shape và không thiết kế search strategy theo volume.
- **Production impact:** Slow query, high DB CPU/IO, abuse.
- **Severity:** Medium
- **Recommended fix:** Giới hạn keyword length, normalize input, cân nhắc index/search strategy thích hợp theo DB và use case.

### 8. `Take(500)` nhưng không có pagination contract

- **Problem:** Client không biết có thêm dữ liệu hay không và result có thể bị truncate âm thầm.
- **Why it happens:** Hard cap thay cho pagination.
- **Production impact:** UX sai, query vẫn lớn, khó scale.
- **Severity:** Medium
- **Recommended fix:** Cursor/page-based pagination với maximum page size.

### 9. Logging raw keyword có thể ghi PII

- **Problem:** Search term có thể là email, tên hoặc dữ liệu nhạy cảm và bị lưu trong logs.
- **Why it happens:** Structured logging nhưng không phân loại dữ liệu.
- **Production impact:** PII leakage sang log store, tăng compliance/security risk.
- **Severity:** High
- **Recommended fix:** Không log raw keyword nếu không cần; log metadata như length, normalized search type hoặc hash khi phù hợp.

### 10. Authorization và data filtering không được test như business invariant

- **Problem:** Code không cho thấy boundary được đóng gói thành policy/query specification.
- **Why it happens:** Security logic dễ bị phân tán trong controller.
- **Production impact:** Regression khi endpoint mới tái sử dụng query khác.
- **Severity:** Medium
- **Recommended fix:** Centralize authorization policy/data-scope service và có integration tests theo role.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/employees")]
[Authorize]
public sealed class EmployeeController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IAuthorizationService _authorization;
    private readonly ICurrentUser _currentUser;

    public EmployeeController(
        AppDbContext db,
        IAuthorizationService authorization,
        ICurrentUser currentUser)
    {
        _db = db;
        _authorization = authorization;
        _currentUser = currentUser;
    }

    [HttpGet("search")]
    public async Task<ActionResult<EmployeeSearchResponse>> Search(
        [FromQuery] string? keyword,
        [FromQuery] int pageSize = 50,
        CancellationToken cancellationToken = default)
    {
        pageSize = Math.Clamp(pageSize, 1, 100);
        keyword = keyword?.Trim();

        if (keyword is { Length: > 100 })
            return BadRequest("Keyword is too long.");

        var canViewAll = (await _authorization.AuthorizeAsync(
            User,
            "Employee.ViewAll")).Succeeded;

        var canViewSensitive = (await _authorization.AuthorizeAsync(
            User,
            "Employee.ViewSensitive")).Succeeded;

        IQueryable<Employee> query = _db.Employees.AsNoTracking();

        if (!canViewAll)
        {
            var managerEmployeeId = _currentUser.EmployeeId;
            query = query.Where(x => x.ManagerId == managerEmployeeId);
        }

        if (!string.IsNullOrEmpty(keyword))
        {
            query = query.Where(x =>
                x.FullName.Contains(keyword) ||
                x.Email.Contains(keyword));
        }

        if (canViewSensitive)
        {
            var rows = await query
                .OrderBy(x => x.FullName)
                .Take(pageSize + 1)
                .Select(x => new EmployeeSearchItem(
                    x.Id,
                    x.FullName,
                    x.Email,
                    x.Manager != null ? x.Manager.FullName : null,
                    x.Office != null ? x.Office.Name : null,
                    x.PersonalEmail,
                    x.NationalId,
                    x.Salary))
                .ToListAsync(cancellationToken);

            return Ok(EmployeeSearchResponse.From(rows, pageSize));
        }

        var safeRows = await query
            .OrderBy(x => x.FullName)
            .Take(pageSize + 1)
            .Select(x => new EmployeeSearchItem(
                x.Id,
                x.FullName,
                x.Email,
                x.Manager != null ? x.Manager.FullName : null,
                x.Office != null ? x.Office.Name : null,
                null,
                null,
                null))
            .ToListAsync(cancellationToken);

        return Ok(EmployeeSearchResponse.From(safeRows, pageSize));
    }
}
```

Trong hệ thống thực tế, policy names, claim model và mapping giữa user identity với employee/manager relationship phải phản ánh domain hiện có. Ví dụ trên chỉ minh họa nguyên tắc server-side authorization scope và minimal projection.

## Trade-offs

- Tách projection theo permission tạo thêm code nhưng giúp review/security rõ ràng và giảm nguy cơ serialize nhầm field.
- Role-based policy đơn giản nhưng permission-based authorization linh hoạt hơn khi quyền thay đổi theo tenant/domain.
- `Contains` có thể đủ với dataset nhỏ và index/collation phù hợp; với search lớn có thể cần giải pháp khác, nhưng phải đo query plan và use case trước khi chọn full-text/search engine.

## Cách kiểm thử

1. **Authorization integration test:** manager A không thể xem employee thuộc manager B dù thay query parameters.
2. **Sensitive-data test:** manager response tuyệt đối không chứa `PersonalEmail`, `NationalId`, `Salary`.
3. **HR test:** user có policy phù hợp có thể search toàn công ty và xem field được cho phép.
4. **Performance/database test:** xác minh generated SQL chỉ select columns cần thiết và query có pagination giới hạn.
5. **Security/logging test:** keyword chứa email/NationalId không xuất hiện raw trong application logs.

## Quan sát trong production

- Log caller ID, policy outcome, result count, duration và page size; tránh raw PII.
- Metric: authorization denials, search latency P95/P99, DB query duration, result count distribution.
- Trace endpoint tới database query để phân biệt application latency và DB latency.
- Alert khi authorization-denied rate tăng bất thường hoặc endpoint xuất hiện spike traffic.
- Theo dõi slow-query plan và index usage ở SQL Server/PostgreSQL theo môi trường thực tế.

## Câu hỏi phỏng vấn mở rộng

1. Khác biệt giữa kiểm tra role ở controller và data-scope authorization ở query layer là gì?
2. Làm sao tránh việc một endpoint mới vô tình bỏ qua cùng authorization rule này?
3. Nếu HR chỉ được xem salary của một số legal entities chứ không phải toàn công ty, bạn thiết kế policy và query scope thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Check-then-update trong application code không bảo đảm correctness dưới concurrency; state transition quan trọng nên được enforce atomically.
- Background jobs nên được thiết kế với giả định có thể chạy lại; retry phải đi cùng idempotency.
- Database commit và queue enqueue là dual-write problem; transactional outbox là một pattern quan trọng khi không được mất event/job.
- Authorization scope phải được derive từ authenticated identity và server-side policy, không từ query parameter do caller kiểm soát.
- Sensitive fields nên được loại bỏ từ query/projection ngay từ đầu, không chỉ ẩn ở UI.
- Logging và observability cũng có data-classification risk; structured logging không tự động đồng nghĩa với safe logging.

## Mẫu tư duy cần nhớ

1. **Clarify before reviewing** — xác định business invariant và failure guarantee trước khi chấm code.
2. **Assume concurrency exists** — mọi check/update quan trọng cần được xem dưới góc nhìn nhiều request cùng lúc.
3. **Design retries together with idempotency** — đừng tắt retry chỉ để tránh duplicate.
4. **Authorize the data, not just the endpoint** — endpoint authenticated chưa có nghĩa mọi row đều được phép đọc.
5. **Treat observability as part of security** — logs, traces và metrics không được vô tình chứa secrets/PII.
