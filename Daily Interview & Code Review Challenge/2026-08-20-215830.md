# Câu 1 — EF Core tracking, identity resolution và truy vấn đọc bị chậm dưới tải

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, change tracking, SQL, profiling, performance

## Bối cảnh

Một ASP.NET Core API dùng EF Core để trả danh sách 5.000 nhân viên cùng phòng ban. Sau một thay đổi refactor, p95 tăng từ khoảng 180 ms lên hơn 1,5 giây và memory allocation/request tăng mạnh. Code mới gọi `Include`, sau đó map entity sang DTO. Endpoint chỉ đọc dữ liệu. Một developer đề xuất thêm `AsNoTracking()` và nói rằng “EF sẽ không tạo object nữa nên chắc chắn nhanh hơn”. Một developer khác cho rằng `AsNoTrackingWithIdentityResolution()` luôn tốt hơn.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong EF Core khi materialize kết quả ở các chế độ tracking, `AsNoTracking()` và `AsNoTrackingWithIdentityResolution()`; vì sao latency/memory có thể thay đổi; các nhận định trên sai ở đâu; rủi ro production là gì và bạn sẽ xác minh bằng bằng chứng nào trước khi sửa?

## Câu hỏi làm rõ nên cân nhắc

- Query thực tế select những cột nào và generated SQL ra sao?
- Quan hệ có làm nhân bản row do JOIN hay không?
- Endpoint có cần update entity sau khi đọc không?
- 5.000 bản ghi là yêu cầu thật hay thiếu pagination?
- Bottleneck nằm ở DB, network, materialization hay serialization?

## Gợi ý tư duy

- **Gợi ý 1:** Tách chi phí database khỏi chi phí phía .NET.
- **Gợi ý 2:** Xem xét ChangeTracker, identity resolution, số object được materialize và projection.
- **Gợi ý 3:** Với read-only API, hãy so sánh entity graph với server-side projection trực tiếp sang DTO thay vì chỉ đổi tracking mode.

## Cấu trúc trả lời đề xuất

1. Làm rõ query và SLA.
2. Giải thích pipeline query/materialization.
3. Phân biệt ba tracking mode.
4. Xác định giả thuyết bằng measurement.
5. Đề xuất projection/pagination/tracking phù hợp.
6. Kiểm thử SQL, allocation, latency và correctness.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Tracking query đưa entity vào ChangeTracker và thực hiện identity resolution.
- `AsNoTracking()` bỏ tracking overhead nhưng vẫn materialize object cần cho kết quả; không có nghĩa là “không tạo object”.
- `AsNoTrackingWithIdentityResolution()` dùng identity resolution riêng cho query nhưng không track entity vào context sau khi query hoàn tất; nó có overhead riêng.
- Phải kiểm tra generated SQL, query plan, số row, allocation và serialization.

### Điểm cộng

- Projection `Select` sang DTO thường tránh tải cột/entity graph không cần thiết.
- Pagination hoặc giới hạn result set có thể quan trọng hơn tracking mode.
- JOIN với collection có thể làm tăng dữ liệu truyền; cân nhắc query shape/split query khi có bằng chứng phù hợp.

### Nâng cao

- Benchmark phải giữ cùng dữ liệu và warm-up; phân biệt DB time, materialization và response serialization.
- Identity resolution có thể giảm duplicate entity instances nhưng không mặc định thắng về performance.

## Hướng giải quyết tham khảo

**Giả định:** endpoint hoàn toàn read-only và client không thực sự cần toàn bộ entity graph.

Trước tiên lấy generated SQL (`ToQueryString` trong môi trường phù hợp), DB execution plan, row count, OpenTelemetry trace và allocation profile. Nếu SQL nhanh nhưng application time cao, kiểm tra materialization/serialization. Nếu endpoint chỉ cần DTO, ưu tiên `Select` các field cần thiết và `AsNoTracking()` khi query vẫn materialize entity. Không coi tracking mode là thuốc chữa mọi vấn đề.

Nếu JOIN làm lặp dữ liệu lớn, thử query shape khác hoặc split query rồi benchmark. Nếu client không cần 5.000 records, pagination/cursor là thay đổi kiến trúc hiệu quả hơn. Cần load test trên dữ liệu gần production và kiểm tra p50/p95/p99, allocated bytes, DB duration và response size.

Điều kiện làm thay đổi quyết định: nếu cùng DbContext cần update các entity vừa query thì tracking có thể hợp lý; nếu graph có nhiều reference lặp lại, identity resolution có thể đáng benchmark.

## Mẫu trả lời trong phỏng vấn

“Em sẽ chưa đổi sang `AsNoTracking` ngay mà tách bottleneck trước. Tracking query vừa materialize entity vừa đưa chúng vào ChangeTracker và thực hiện identity resolution. `AsNoTracking` loại phần tracking đó nhưng vẫn phải tạo object cho kết quả, nên nhận định rằng nó không tạo object là sai. `AsNoTrackingWithIdentityResolution` lại có một tracker tạm phục vụ identity resolution, vì vậy không thể nói luôn nhanh hơn. Với endpoint read-only, em sẽ xem generated SQL, execution plan, số row, response size và trace để biết thời gian nằm ở DB hay .NET. Nếu API chỉ cần vài field, em ưu tiên projection trực tiếp sang DTO và pagination. Sau đó benchmark các phương án với cùng dataset, theo dõi p95, allocation và DB duration. Nếu endpoint sau đó cần update entity trong cùng unit of work thì em sẽ xem lại lựa chọn tracking.”

## Câu hỏi đào sâu

1. Vì sao `Include` collection có thể làm response/query data phình lớn?
2. Khi nào split query có thể tốt hơn và nó đánh đổi điều gì?
3. Nếu projection đã tạo DTO trực tiếp, thêm `AsNoTracking()` có còn là tối ưu quan trọng không?

## Lỗi trả lời thường gặp

- Khẳng định `AsNoTracking()` luôn nhanh hơn mà không đo.
- Nhầm no-tracking với không materialize object.
- Chỉ tối ưu EF mà bỏ qua SQL plan và response size.
- Không hỏi tại sao endpoint trả 5.000 records.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.5
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 1.5
- Communication: 1.0

# Câu 2 — Incident: Hangfire job gửi email bị thực thi trùng sau timeout

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** Hangfire, idempotency, distributed systems, SQL, incident response, observability

## Bối cảnh

Một job gửi email lịch họp qua Microsoft Graph. Sau khi Graph có latency cao trong khoảng 20 phút, một số người dùng nhận 2–3 email giống nhau. Dashboard cho thấy job có retry. Database có trạng thái `Pending/Sent`, nhưng worker đọc `Pending`, gọi external API rồi mới cập nhật `Sent`. Không có bằng chứng rằng Graph luôn trả response thành công trước khi email được gửi. Hệ thống chạy nhiều Hangfire workers trên hai instances.

## Câu hỏi chính

Bạn sẽ xử lý incident và thiết kế lại flow như thế nào để giảm duplicate mà không làm mất email, trong điều kiện external API có thể timeout sau khi side effect đã xảy ra?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate được định nghĩa theo business key nào?
- Graph request nào đang được dùng và có cơ chế idempotency phía provider hay không?
- Retry policy hiện tại gồm automatic retry và HTTP retry thế nào?
- Có nhiều job cùng business entity được enqueue đồng thời không?
- Business chấp nhận at-least-once hay yêu cầu trải nghiệm gần exactly-once?

## Gợi ý tư duy

- **Gợi ý 1:** Timeout không chứng minh operation thất bại.
- **Gợi ý 2:** Phân biệt job delivery semantics với business idempotency.
- **Gợi ý 3:** Dùng durable state/business key, atomic claim/outbox khi phù hợp và reconciliation cho trạng thái không chắc chắn.

## Cấu trúc trả lời đề xuất

1. Xác định impact và ngăn blast radius.
2. Thu thập correlation/job/request evidence.
3. Lập nhiều giả thuyết.
4. Xác định ambiguity window quanh external side effect.
5. Thiết kế idempotency/state machine.
6. Retry có phân loại lỗi.
7. Reconciliation và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định retry framework đảm bảo exactly-once.
- Timeout sau request có thể là ambiguous outcome.
- Business operation cần idempotency key/state riêng và concurrency control.
- Immediate mitigation phải tránh tiếp tục spam nhưng không xóa dữ liệu điều tra.

### Điểm cộng

- Unique constraint theo business operation để chặn enqueue/processing trùng logic.
- Trạng thái như Pending/Processing/Sent/Unknown/Failed với timestamps và attempt metadata.
- Retry chỉ lỗi transient; exponential backoff/jitter và giới hạn attempt.

### Nâng cao

- Outbox giải quyết atomicity giữa thay đổi DB và việc phát work, nhưng không tự biến external side effect thành exactly-once.
- Reconciliation/lookup provider state nếu API hỗ trợ; nếu không, business phải chọn trade-off duplicate vs loss cho ambiguous outcome.

## Hướng giải quyết tham khảo

Đầu tiên đánh giá số người bị ảnh hưởng, tạm giảm/disable retry cho loại lỗi gây spam nếu cần và giữ job/request logs. Correlate Hangfire job id, business message id và Graph request metadata. Kiểm tra xem duplicate do cùng job retry, enqueue trùng, worker concurrency hay HTTP retry.

Thiết kế business key duy nhất cho một email logic, unique constraint trong DB và atomic claim để chỉ một worker sở hữu attempt tại một thời điểm. Lưu attempt trước external call. Sau thành công cập nhật `Sent`; với timeout sau khi request đã đi, không vội coi là `Failed` mà chuyển `Unknown` nếu không thể chứng minh outcome. Reconciliation quyết định retry dựa trên khả năng kiểm tra provider hoặc policy business.

Outbox có thể đảm bảo DB state và enqueue work không bị lệch, nhưng external API vẫn là boundary không thể transaction chung. Theo dõi duplicate-prevented count, unknown outcomes, retry count, Graph latency/error rate và age của pending jobs.

## Mẫu trả lời trong phỏng vấn

“Em xem đây là bài toán at-least-once cộng với ambiguous external side effect. Việc job retry sau timeout không có nghĩa email trước chưa được gửi. Trong incident em sẽ xác định blast radius, correlate job id với business message id và external request, sau đó hạn chế retry gây spam nhưng vẫn giữ evidence. Về thiết kế, em tạo business idempotency key có unique constraint, claim operation atomically và lưu từng attempt. Sau external success mới đánh `Sent`; nếu timeout sau khi request đã gửi thì em coi outcome là `Unknown`, không tự động retry mù. Nếu provider cho phép query/reconcile thì kiểm tra trước khi retry; nếu không thì phải thống nhất trade-off với business. Outbox giúp tránh lệch DB với enqueue nhưng không giải quyết exactly-once ở external boundary. Em sẽ test concurrent workers, timeout trước/sau side effect và theo dõi retry, unknown state, duplicate-prevention và latency.”

## Câu hỏi đào sâu

1. `DisableConcurrentExecution` có đủ để giải quyết duplicate business operation không?
2. Outbox giải quyết phần nào và không giải quyết phần nào?
3. Nếu provider không có idempotency key hoặc API kiểm tra trạng thái, bạn chọn retry hay không retry khi timeout?

## Lỗi trả lời thường gặp

- Tin rằng Hangfire retry đảm bảo exactly-once.
- Chỉ thêm distributed lock rồi coi vấn đề đã xong.
- Retry mọi exception giống nhau.
- Không thiết kế trạng thái `Unknown` cho ambiguous outcome.
- Không có correlation và metrics.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 2.0
- Production readiness: 1.5
- Communication: 1.0

# Câu 3 — Thiết kế AI code-review agent có quyền đọc repository và tạo PR comment

**Loại câu hỏi:** AI engineering / system decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** AI agents, tool permissions, context engineering, secure design, evaluation, deterministic validation

## Bối cảnh

Team muốn một agent review pull request C#/.NET. Agent được phép đọc diff, một phần repository, coding rules và issue liên quan; sau đó đề xuất review comments. Product owner muốn agent tự post comment để tiết kiệm thời gian. Repository có secrets trong CI configuration, generated files, security-sensitive code và có thể chứa text cố tình hướng dẫn model bỏ qua policy. Team chưa có benchmark chất lượng.

## Câu hỏi chính

Hãy thiết kế MVP an toàn và đo được chất lượng cho agent này: AI thực sự cần làm phần nào, phần nào deterministic, context được xây thế nào, tool permission ra sao, output được validate/audit thế nào và khi nào mới cho phép agent tự post comment?

## Câu hỏi làm rõ nên cân nhắc

- Mục tiêu chính là correctness, security, style hay maintainability?
- False positive và false negative bên nào đắt hơn?
- Repository/private code có policy dữ liệu nào?
- Agent chỉ comment hay có thể sửa code/chạy command?
- Ai chịu trách nhiệm khi recommendation sai?

## Gợi ý tư duy

- **Gợi ý 1:** Tách reasoning không chắc chắn khỏi enforcement có thể kiểm chứng.
- **Gợi ý 2:** Principle of least privilege và coi repository content là untrusted input đối với agent.
- **Gợi ý 3:** Bắt đầu read-only + draft review, structured output, deterministic gates và evaluation set trước khi tăng autonomy.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu và risk budget.
2. Chia deterministic vs probabilistic tasks.
3. Thiết kế context boundary.
4. Thiết kế tools/permissions.
5. Structured output + validation.
6. Human approval/fallback.
7. Offline/online evaluation.
8. Audit, monitoring và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cấp write permission ngay từ MVP.
- Repository/issue/PR text là dữ liệu, không phải trusted instruction.
- Context phải tối thiểu, có provenance và giới hạn scope.
- Output phải theo schema và được validate trước action.
- Chất lượng phải có evaluation dataset/metrics thay vì cảm giác.

### Điểm cộng

- Static analyzers/tests/formatters giữ vai trò deterministic.
- Agent chỉ tập trung semantic review khó encode bằng rule.
- Human approval cho high-impact action; audit mọi tool call và nguồn context.

### Nâng cao

- Eval theo precision/recall hoặc acceptance rate phân loại severity, false-positive rate và regression suite.
- Canary rollout, shadow mode, confidence không được coi là bằng chứng duy nhất.
- Tool authorization được enforce ngoài prompt.

## Hướng giải quyết tham khảo

**MVP:** webhook/worker nhận PR metadata, deterministic service xác định changed files và chạy compiler/tests/static analyzers. Context builder chỉ lấy diff, coding rules được quản trị, symbol/dependency context cần thiết và issue metadata đã sanitize/label provenance. Model không được đọc secrets hay toàn repo mặc định.

Agent có read-only tools; không shell/write repo. Model trả structured findings gồm file, line/range, category, severity, reasoning ngắn và evidence. Validator kiểm tra file/line tồn tại, finding có evidence trong diff/context, deduplicate và chặn comment dựa trên instruction xuất hiện trong repository. Ban đầu output chỉ thành draft cho người review duyệt.

Tạo golden set từ PR lịch sử được senior engineer gắn nhãn; đo precision, useful-finding acceptance, false-positive rate, latency/cost và security red-team cases như indirect prompt injection. Chỉ tăng quyền post comment khi quality threshold ổn định, có rollback/kill switch và policy giới hạn loại comment. Quyền write phải nằm ở service/action layer, không phải model tự quyết.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng agent có quyền write. AI hữu ích ở semantic review, còn compiler, tests, analyzers, schema validation và permission enforcement nên deterministic. Context builder chỉ đưa diff, rules được tin cậy và code context cần thiết, đồng thời gắn provenance; nội dung repo hay issue được coi là untrusted data vì có thể chứa prompt injection. Model trả structured findings, sau đó validator kiểm tra file/line/evidence và policy. MVP chạy shadow hoặc draft mode để human approve. Em xây golden dataset từ PR thật và đo useful acceptance, false-positive, severity accuracy, latency và cost, cộng security eval. Chỉ khi metrics ổn định mới cho phép auto-post một subset low-risk, với least privilege, audit log và kill switch. Nếu model hoặc tool lỗi thì fallback là không post, không làm thay đổi repository.”

## Câu hỏi đào sâu

1. Prompt injection trong comment/code có thể vượt qua prompt instruction bằng cách nào và bạn enforce boundary ở đâu?
2. Nếu agent đạt acceptance rate cao nhưng bỏ sót security bug nghiêm trọng thì metric hiện tại có đủ không?
3. Tại sao structured output vẫn chưa đủ để bảo đảm action an toàn?

## Lỗi trả lời thường gặp

- “Dùng LLM review PR” mà không chia deterministic/AI responsibility.
- Dùng prompt như lớp authorization duy nhất.
- Cho agent toàn quyền repo/shell ngay từ đầu.
- Không có evaluation dataset.
- Dùng confidence tự báo của model làm quality gate duy nhất.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.0
- Communication: 1.0
