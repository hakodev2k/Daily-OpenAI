# Code Review Challenge 1 — Hangfire job gửi thông báo bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để gửi email nhắc lịch cho người dùng. Nhiều Hangfire worker chạy trên nhiều instance để tăng throughput. Gần đây production ghi nhận một số người dùng nhận 2–3 email giống nhau, đặc biệt khi SMTP chậm hoặc worker restart. Database là SQL Server. Business yêu cầu mỗi reminder chỉ được gửi một lần về mặt nghiệp vụ, nhưng job vẫn phải retry khi lỗi tạm thời.

## Đoạn code cần review

```csharp
public sealed class ReminderJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<ReminderJob> _logger;

    public ReminderJob(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<ReminderJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    public async Task SendAsync(Guid reminderId)
    {
        var reminder = await _db.Reminders
            .Include(x => x.User)
            .FirstOrDefaultAsync(x => x.Id == reminderId);

        if (reminder == null || reminder.IsSent)
            return;

        await _emailSender.SendAsync(
            reminder.User.Email,
            reminder.Subject,
            reminder.Body);

        reminder.IsSent = true;
        reminder.SentAtUtc = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Reminder {ReminderId} sent to {Email}",
            reminder.Id,
            reminder.User.Email);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Tìm rủi ro concurrency, retry và failure recovery.
3. Giải thích tác động production.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử.
7. Đề xuất logs, traces và metrics phù hợp.

## Câu hỏi gợi mở

- Hai worker có thể cùng đọc `IsSent = false` không?
- Điều gì xảy ra nếu email đã gửi thành công nhưng process chết trước `SaveChangesAsync()`?
- Transaction database có thể làm cho việc gửi email và cập nhật database trở thành một atomic operation không?
- Retry của Hangfire thay đổi yêu cầu idempotency như thế nào?
- Có nên coi `IsSent` là cơ chế chống duplicate đủ mạnh không?

## Gợi ý

### Gợi ý 1

Hãy tách “side effect bên ngoài database” khỏi “trạng thái đã xử lý trong database”, rồi xem từng failure window.

### Gợi ý 2

Một transaction SQL không thể rollback email đã được SMTP/provider chấp nhận. Hãy nghĩ đến unique constraint, trạng thái xử lý, outbox và idempotency key.

## Kết quả code review tham khảo

### 1. Check-then-act không atomic

**Problem:** Hai worker có thể cùng đọc reminder với `IsSent = false` rồi cùng gửi email.  
**Why:** Query và update là hai bước độc lập, không có concurrency control đủ mạnh.  
**Production impact:** Duplicate email dưới tải hoặc khi cùng job được enqueue nhiều lần.  
**Severity:** Critical  
**Recommended fix:** Thiết kế idempotent ở database bằng unique key/trạng thái claim atomic hoặc transactional outbox; không dựa vào boolean check đơn thuần.

### 2. Failure window sau khi gửi email

**Problem:** Email có thể đã được provider nhận nhưng database chưa ghi `IsSent = true`.  
**Why:** External side effect và database commit không cùng một transaction phân tán.  
**Production impact:** Worker crash/timeout sau send khiến Hangfire retry và gửi lại.  
**Severity:** Critical  
**Recommended fix:** Dùng transactional outbox để transaction nghiệp vụ chỉ ghi intent; dispatcher xử lý outbox với idempotency key nếu provider hỗ trợ. Nếu provider không hỗ trợ deduplication, phải chấp nhận/định nghĩa semantics at-least-once và giảm duplicate bằng claim + durable delivery state.

### 3. Không có idempotency key ở delivery boundary

**Problem:** Mỗi retry nhìn như một lần gửi mới đối với email provider.  
**Why:** Không có stable delivery identifier như `reminderId`.  
**Production impact:** Duplicate side effect khó phát hiện và reconcile.  
**Severity:** High  
**Recommended fix:** Truyền stable idempotency key cho provider nếu API hỗ trợ; lưu provider message ID và attempt history.

### 4. Không truyền cancellation token

**Problem:** Query và send không nhận cancellation token.  
**Why:** Job không hợp tác tốt với shutdown/cancellation.  
**Production impact:** Shutdown kéo dài, request ngoại vi tiếp tục khi worker đang dừng, failure window khó kiểm soát hơn.  
**Severity:** Medium  
**Recommended fix:** Truyền token xuyên suốt các API hỗ trợ cancellation; với Hangfire cần thiết kế phù hợp với cancellation mechanism của job runtime.

### 5. Không phân loại lỗi transient và permanent

**Problem:** Mọi exception đều được xử lý giống nhau bởi retry mặc định bên ngoài đoạn code.  
**Why:** Không phân biệt timeout/429/5xx với invalid recipient hoặc dữ liệu sai.  
**Production impact:** Retry vô ích, tăng tải và kéo dài incident.  
**Severity:** Medium  
**Recommended fix:** Xác định retry policy có bounded backoff, dead-letter/failed state và quy tắc lỗi permanent.

### 6. Logging chứa email người dùng

**Problem:** Log trực tiếp địa chỉ email.  
**Why:** PII được đưa vào log aggregation không cần thiết.  
**Production impact:** Tăng phạm vi dữ liệu nhạy cảm và rủi ro compliance/access.  
**Severity:** Medium  
**Recommended fix:** Log `ReminderId`, `UserId`, provider message ID; mask/hash email nếu thực sự cần.

### 7. Không có attempt/audit state

**Problem:** Chỉ có `IsSent` và `SentAtUtc`.  
**Why:** Không ghi nhận attempt, lỗi cuối, trạng thái processing hoặc provider ID.  
**Production impact:** Khó điều tra duplicate, stuck job và retry storm.  
**Severity:** Medium  
**Recommended fix:** Lưu delivery/outbox record với status, attempt count, timestamps và correlation/provider ID.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng transactional outbox cho phần tạo intent. Dispatcher là component riêng; unique constraint trên `OutboxMessages.DeduplicationKey` là lớp bảo vệ bắt buộc ở database.

```csharp
public sealed class ReminderService
{
    private readonly AppDbContext _db;

    public ReminderService(AppDbContext db) => _db = db;

    public async Task QueueReminderAsync(
        Guid reminderId,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var reminder = await _db.Reminders
            .SingleOrDefaultAsync(x => x.Id == reminderId, cancellationToken);

        if (reminder is null)
            return;

        var key = $"reminder:{reminderId}";

        var exists = await _db.OutboxMessages
            .AnyAsync(x => x.DeduplicationKey == key, cancellationToken);

        if (!exists)
        {
            _db.OutboxMessages.Add(new OutboxMessage
            {
                Id = Guid.NewGuid(),
                Type = "ReminderEmail",
                AggregateId = reminderId,
                DeduplicationKey = key,
                CreatedAtUtc = DateTime.UtcNow,
                Status = OutboxStatus.Pending
            });
        }

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }
}

public sealed class ReminderOutboxDispatcher
{
    private readonly IEmailSender _emailSender;
    private readonly AppDbContext _db;

    public ReminderOutboxDispatcher(IEmailSender emailSender, AppDbContext db)
    {
        _emailSender = emailSender;
        _db = db;
    }

    public async Task DispatchAsync(Guid outboxId, CancellationToken ct)
    {
        var message = await _db.OutboxMessages
            .SingleAsync(x => x.Id == outboxId, ct);

        if (message.Status == OutboxStatus.Sent)
            return;

        var reminder = await _db.Reminders
            .Include(x => x.User)
            .SingleAsync(x => x.Id == message.AggregateId, ct);

        var result = await _emailSender.SendAsync(
            reminder.User.Email,
            reminder.Subject,
            reminder.Body,
            idempotencyKey: message.DeduplicationKey,
            cancellationToken: ct);

        message.Status = OutboxStatus.Sent;
        message.ProcessedAtUtc = DateTime.UtcNow;
        message.ProviderMessageId = result.MessageId;
        await _db.SaveChangesAsync(ct);
    }
}
```

Database phải có unique constraint/index cho `DeduplicationKey`; việc `AnyAsync()` chỉ là optimization/readability, không phải correctness boundary. Dispatcher thực tế cũng cần cơ chế claim cạnh tranh an toàn giữa nhiều worker. Nếu provider không hỗ trợ idempotency key, outbox vẫn giải quyết atomicity của việc tạo intent nhưng không thể tự bảo đảm exactly-once cho external side effect trong mọi failure window.

## Trade-offs

Outbox thêm table, dispatcher, cleanup và observability nhưng tạo ranh giới retry rõ ràng. Distributed lock có thể giảm concurrent execution nhưng không giải quyết crash sau khi external side effect đã thành công. Database transaction với lock mạnh có thể serialize worker nhưng vẫn không biến SMTP thành transactional resource. Nếu duplicate email có tác động thấp, một thiết kế at-least-once có dedupe best-effort có thể hợp lý hơn một hệ thống phức tạp.

## Cách kiểm thử

1. **Concurrency test:** enqueue cùng `reminderId` đồng thời trên nhiều worker; chỉ một outbox intent hợp lệ được tạo.
2. **Crash test:** giả lập provider trả success rồi process chết trước database update; xác minh retry semantics và provider idempotency.
3. **Transient failure:** provider trả timeout/429 rồi thành công; xác minh bounded retry và không tạo intent mới.
4. **Permanent failure:** invalid recipient; xác minh chuyển failed/dead-letter thay vì retry vô hạn.
5. **Database test:** xác minh unique constraint chống duplicate ngay cả khi hai transaction cùng vượt qua `AnyAsync()`.

## Quan sát trong production

Theo dõi `outbox_pending_count`, tuổi của message cũ nhất, attempts/message, send success/failure rate, retry count, duplicate-key conflict và provider latency. Trace nên liên kết `ReminderId`, `OutboxId`, Hangfire job ID và provider message ID. Alert khi backlog/oldest-message age vượt SLO hoặc retry rate tăng bất thường. Không log nội dung email hay PII không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `DisableConcurrentExecution` hoặc distributed lock chưa đủ để bảo đảm exactly-once delivery?
2. Nếu email provider không hỗ trợ idempotency key, bạn định nghĩa delivery guarantee thế nào?
3. Bạn sẽ claim một batch outbox records an toàn giữa 10 worker như thế nào trên SQL Server hoặc PostgreSQL?

# Code Review Challenge 2 — Endpoint tìm kiếm outlet kéo toàn bộ dữ liệu về memory

**Chủ đề:** EF Core query execution, SQL performance, cancellation, API correctness  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 7–8 vấn đề

## Bối cảnh

Một API ASP.NET Core tìm outlet theo viewport bản đồ và từ khóa. Bảng `Outlets` có hàng triệu dòng. Production ghi nhận latency tăng mạnh khi zoom-out, memory spike trên app instance và đôi lúc container restart. Endpoint phục vụ mobile map nên người dùng thường pan/zoom liên tục và request cũ nhanh chóng trở nên vô ích.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/outlets")]
public sealed class OutletsController : ControllerBase
{
    private readonly AppDbContext _db;

    public OutletsController(AppDbContext db) => _db = db;

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        double minLat,
        double minLng,
        double maxLat,
        double maxLng,
        string? keyword)
    {
        var outlets = await _db.Outlets
            .Include(x => x.Category)
            .ToListAsync();

        var result = outlets
            .Where(x => x.Latitude >= minLat && x.Latitude <= maxLat)
            .Where(x => x.Longitude >= minLng && x.Longitude <= maxLng)
            .Where(x => string.IsNullOrWhiteSpace(keyword) ||
                        x.Name.ToLower().Contains(keyword.ToLower()))
            .OrderBy(x => x.Name)
            .Select(x => new
            {
                x.Id,
                x.Name,
                x.Latitude,
                x.Longitude,
                Category = x.Category.Name
            })
            .Take(500)
            .ToList();

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ bảng trước khi filter

**Problem:** `ToListAsync()` chạy trước mọi predicate.  
**Why:** Từ đó trở đi LINQ xử lý trên collection trong memory.  
**Production impact:** Đọc hàng triệu row, network/database I/O lớn, memory allocation cao và latency tăng mạnh.  
**Severity:** Critical  
**Recommended fix:** Giữ query ở dạng `IQueryable`, thêm predicates/projection/limit trước `ToListAsync()`.

### 2. `Take(500)` không giới hạn dữ liệu lấy từ database

**Problem:** Limit được áp dụng sau khi toàn bộ bảng đã materialize.  
**Why:** SQL query ban đầu không chứa limit tương ứng.  
**Production impact:** API trả ít row nhưng vẫn trả giá của full-table transfer.  
**Severity:** High  
**Recommended fix:** Đặt `Take` trước terminal async execution.

### 3. `Include(Category)` tải entity graph không cần thiết

**Problem:** Tracking query tải Outlet và Category entity trong khi response chỉ cần vài cột.  
**Why:** Projection được thực hiện sau materialization.  
**Production impact:** Tăng dữ liệu truyền, tracking overhead và allocation.  
**Severity:** High  
**Recommended fix:** Projection trực tiếp trong query; read-only query có thể dùng `AsNoTracking()` khi phù hợp.

### 4. Search bằng `ToLower().Contains()` trên dữ liệu đã materialize

**Problem:** Tạo string/CPU work cho từng row và semantics case-sensitivity phụ thuộc cách xử lý.  
**Why:** Search không được database tối ưu hóa.  
**Production impact:** CPU và GC tăng khi dataset lớn.  
**Severity:** High  
**Recommended fix:** Để database xử lý search theo collation/operator phù hợp; tránh giả định một cách viết portable sẽ có cùng semantics và index behavior trên SQL Server/PostgreSQL. Với search lớn/phức tạp, cân nhắc search-specific index/engine sau khi đo.

### 5. Không validate bounding box

**Problem:** Không kiểm tra latitude/longitude hợp lệ hoặc `min <= max`.  
**Why:** Input được dùng trực tiếp như business criteria.  
**Production impact:** Kết quả sai, query cực rộng hoặc behavior khó đoán; antimeridian cũng cần quy ước rõ nếu hệ thống hỗ trợ toàn cầu.  
**Severity:** Medium  
**Recommended fix:** Validate ranges, ordering, maximum viewport/zoom policy và semantics địa lý.

### 6. Không truyền request cancellation

**Problem:** `ToListAsync()` không nhận `HttpContext.RequestAborted`.  
**Why:** Server không chủ động ngừng query khi client bỏ request.  
**Production impact:** Pan/zoom nhanh tạo nhiều công việc vô ích ở app/database.  
**Severity:** Medium  
**Recommended fix:** Truyền `RequestAborted` tới EF Core async operation và downstream calls.

### 7. Không có pagination/stable continuation contract

**Problem:** Hard limit 500 có thể cắt kết quả mà client không biết còn dữ liệu.  
**Why:** API contract không biểu diễn truncation/pagination.  
**Production impact:** UX không đầy đủ và khó mở rộng.  
**Severity:** Medium  
**Recommended fix:** Với map, cân nhắc viewport + max result contract, clustering hoặc continuation phù hợp; nếu paging thì dùng deterministic ordering và cursor/keyset khi hợp lý.

## Phiên bản code đề xuất

```csharp
[HttpGet("search")]
public async Task<IActionResult> Search(
    double minLat,
    double minLng,
    double maxLat,
    double maxLng,
    string? keyword,
    CancellationToken cancellationToken)
{
    if (minLat is < -90 or > 90 || maxLat is < -90 or > 90 ||
        minLng is < -180 or > 180 || maxLng is < -180 or > 180 ||
        minLat > maxLat || minLng > maxLng)
    {
        return BadRequest("Invalid bounding box.");
    }

    var query = _db.Outlets
        .AsNoTracking()
        .Where(x => x.Latitude >= minLat && x.Latitude <= maxLat)
        .Where(x => x.Longitude >= minLng && x.Longitude <= maxLng);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x => x.Name.Contains(term));
    }

    var result = await query
        .OrderBy(x => x.Name)
        .ThenBy(x => x.Id)
        .Select(x => new
        {
            x.Id,
            x.Name,
            x.Latitude,
            x.Longitude,
            Category = x.Category.Name
        })
        .Take(500)
        .ToListAsync(cancellationToken);

    return Ok(result);
}
```

Đây là baseline sửa lỗi lớn nhất: execution ở database, projection nhỏ và cancellation. `Contains` chỉ là ví dụ chức năng; case-insensitive behavior và khả năng dùng index phải được thiết kế theo database/collation thực tế. Với workload map lớn, cần benchmark execution plan và cân nhắc spatial column/index hoặc chiến lược index phù hợp thay vì mặc định rằng compound B-tree hay spatial index luôn thắng.

## Trade-offs

Query lat/lng range đơn giản dễ hiểu và có thể đủ nhanh ở viewport nhỏ. Spatial type/index có thể phù hợp hơn cho bài toán địa lý nhưng tăng complexity và cần đúng query shape để optimizer tận dụng. `AsNoTracking()` giảm tracking overhead cho read-only query nhưng không nên dùng máy móc nếu caller cần update entity. Hard cap bảo vệ hệ thống nhưng API phải nói rõ truncation hoặc dùng clustering/pagination.

## Cách kiểm thử

1. **Integration test:** xác minh SQL chỉ lấy projection cần thiết và giới hạn kết quả, không materialize toàn bảng.
2. **Load test:** viewport nhỏ, vừa và rất lớn trên dataset gần production; đo p50/p95/p99, DB CPU, logical reads và app allocations.
3. **Cancellation test:** hủy request khi query đang chạy và xác minh work được cancel ở mức hỗ trợ của provider.
4. **Correctness test:** invalid coordinates, boundary values, keyword rỗng, case-sensitivity theo contract và dữ liệu ở mép bounding box.
5. **Database test:** so sánh execution plan/logical reads trước và sau index/spatial strategy bằng cùng dataset và parameter distribution.

## Quan sát trong production

Theo dõi request latency theo viewport size, result count, cancellation rate, EF/DB command duration, timeout rate, DB CPU/logical reads, app memory/GC và container restarts. Trace cần tách thời gian HTTP → application → database. Slow-query diagnostics nên lưu query shape và parameter dimensions ở mức không làm lộ dữ liệu nhạy cảm.
