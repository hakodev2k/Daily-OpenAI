# Code Review Challenge 1 — Consumer RabbitMQ xử lý thanh toán bị trùng dưới tải

**Chủ đề:** Concurrency, idempotency, EF Core transaction, messaging  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một worker .NET nhận sự kiện `PaymentCaptured` từ RabbitMQ để đánh dấu invoice đã thanh toán và gửi email. RabbitMQ có thể redeliver khi connection bị mất hoặc consumer chết trước ACK. Hệ thống chạy 4 replicas; production thỉnh thoảng ghi nhận email gửi hai lần và một số invoice có `PaidAt` bị ghi lại. Không được giả định broker cung cấp exactly-once delivery.

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly BillingDbContext _db;
    private readonly IEmailSender _email;

    public PaymentConsumer(BillingDbContext db, IEmailSender email)
    {
        _db = db;
        _email = email;
    }

    public async Task HandleAsync(PaymentCaptured message)
    {
        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId);

        if (alreadyProcessed)
            return;

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId);

        invoice.Status = InvoiceStatus.Paid;
        invoice.PaidAt = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        await _email.SendReceiptAsync(invoice.CustomerEmail, invoice.Id);

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();
    }
}
```

2. Tìm rủi ro concurrency/retry/idempotency.
3. Giải thích impact production.
4. Ưu tiên vấn đề.
5. Đề xuất implementation an toàn hơn.
6. Nêu cách test failure windows và concurrency.
7. Đề xuất logs, traces, metrics.

## Câu hỏi gợi mở

- DB commit và external side effect có cùng atomic boundary không?
- Unique constraint có vai trò gì ngoài application-level check?
- Cancellation/ACK nên gắn với thời điểm nào?

## Kết quả code review tham khảo

### 1. Check-then-act không chống được concurrent duplicate
**Problem:** `AnyAsync` rồi mới insert dedupe record.  
**Why:** hai consumer có thể cùng đọc “chưa tồn tại”.  
**Impact:** cùng update invoice và gửi email.  
**Severity:** Critical.  
**Fix:** unique constraint/index trên `ProcessedMessages.MessageId` và thiết kế transaction/idempotent state transition để DB là arbiter.

### 2. Email được gửi trước khi dedupe marker được commit
**Problem:** crash sau `SendReceiptAsync` nhưng trước `SaveChangesAsync` cuối.  
**Why:** side effect ngoài DB không atomic với transaction DB.  
**Impact:** redelivery gửi email lần nữa.  
**Severity:** Critical.  
**Fix:** transactional outbox: commit invoice state + inbox/dedupe + outbox event trong cùng DB transaction; dispatcher riêng gửi email và retry idempotently nếu provider hỗ trợ idempotency key.

### 3. Invoice update và processed marker nằm ở hai commit
**Problem:** trạng thái business có thể commit nhưng marker chưa commit.  
**Impact:** retry re-executes operation.  
**Severity:** High.  
**Fix:** một transaction cho các thay đổi DB liên quan.

### 4. Không bảo vệ state transition của invoice
**Problem:** event duplicate/out-of-order có thể ghi lại `PaidAt`.  
**Impact:** mất timestamp nghiệp vụ gốc, audit sai.  
**Severity:** High.  
**Fix:** chỉ transition từ trạng thái hợp lệ; dùng conditional update/concurrency token nếu có competing transitions.

### 5. Dedupe chỉ dựa vào code, thiếu DB invariant
**Problem:** ngay cả khi transaction được thêm, isolation mặc định không tự biến check-then-insert thành uniqueness guarantee.  
**Severity:** High.  
**Fix:** unique index là invariant cuối cùng; xử lý duplicate-key như already processed.

### 6. Không truyền `CancellationToken`
**Problem:** shutdown/cancellation không đi xuyên qua EF/email calls.  
**Impact:** shutdown kéo dài, trạng thái xử lý khó đoán.  
**Severity:** Medium.  
**Fix:** nhận token và truyền xuống các API hỗ trợ.

### 7. `DateTime.UtcNow` được lấy nhiều lần
**Problem:** timestamp business và processed không nhất quán hoàn toàn.  
**Severity:** Low.  
**Fix:** capture `now` một lần hoặc dùng timestamp từ event nếu semantics yêu cầu thời điểm payment thực tế.

## Phiên bản code đề xuất

```csharp
public sealed class PaymentConsumer
{
    private readonly BillingDbContext _db;

    public PaymentConsumer(BillingDbContext db) => _db = db;

    public async Task HandleAsync(PaymentCaptured message, CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        if (await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId, ct))
            return;

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId, ct);

        if (invoice.Status != InvoiceStatus.Paid)
        {
            invoice.Status = InvoiceStatus.Paid;
            invoice.PaidAt = message.CapturedAtUtc;

            _db.OutboxMessages.Add(OutboxMessage.Create(
                "SendPaymentReceipt",
                new { invoice.Id, invoice.CustomerEmail },
                idempotencyKey: message.MessageId));
        }

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

Database phải có unique index cho `ProcessedMessages.MessageId`. Outbox dispatcher chịu trách nhiệm gửi email sau commit và đánh dấu outbox item đã xử lý; nó vẫn phải giả định retry có thể xảy ra.

## Trade-offs

Outbox tăng schema, worker và operational complexity nhưng loại bỏ failure window nguy hiểm giữa DB commit và publish/send. Nếu side effect vốn idempotent và business chấp nhận duplicate, thiết kế đơn giản hơn có thể đủ. Với throughput rất cao, có thể dùng atomic insert/conditional update thay vì transaction dài, nhưng DB invariant vẫn cần giữ.

## Cách kiểm thử

1. Chạy 20 handler đồng thời với cùng `MessageId`; chỉ một business transition/outbox item hợp lệ.
2. Inject crash sau DB commit nhưng trước broker ACK; redelivery không tạo email intent thứ hai.
3. Inject failure ở outbox email sender rồi retry; không mất receipt.
4. Gửi duplicate event sau invoice đã Paid; `PaidAt` không bị thay đổi.
5. Test graceful shutdown/cancellation giữa các bước.

## Quan sát trong production

Log `MessageId`, `InvoiceId`, delivery attempt và outcome nhưng không log dữ liệu nhạy cảm. Metric nên có duplicate-detected count, outbox backlog/age, consumer failure/retry rate và processing latency. Trace nên nối broker consume → DB transaction → outbox dispatch → email provider; alert khi outbox oldest age hoặc retry rate vượt ngưỡng.

## Câu hỏi phỏng vấn mở rộng

1. Unique constraint có đủ để bảo đảm email exactly once không? Vì sao?
2. Nếu email provider không hỗ trợ idempotency key, bạn định nghĩa guarantee nào cho hệ thống?
3. Khi nào bạn chọn inbox/outbox thay vì distributed transaction?

# Code Review Challenge 2 — API tìm kiếm audit log vừa chậm vừa có nguy cơ lộ dữ liệu

**Chủ đề:** Authorization, EF Core query execution, sensitive-data exposure, performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một ASP.NET Core API cho quản trị viên tìm audit log theo tenant. Endpoint chạy trên multi-tenant SaaS, bảng `AuditLogs` có hàng chục triệu rows. Sau một release, latency và memory tăng mạnh khi query khoảng thời gian dài. Security review đồng thời nghi ngờ người dùng thuộc tenant A có thể đọc log tenant B nếu biết `tenantId`. Payload log đôi khi chứa access token hoặc request body.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        Guid tenantId,
        DateTime? from,
        DateTime? to,
        string? contains)
    {
        var logs = await _db.AuditLogs
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        var result = logs
            .Where(x => x.TenantId == tenantId)
            .Where(x => !from.HasValue || x.CreatedAt >= from.Value)
            .Where(x => !to.HasValue || x.CreatedAt <= to.Value)
            .Where(x => string.IsNullOrEmpty(contains) ||
                        x.RequestBody.Contains(contains))
            .Take(5000)
            .ToList();

        _logger.LogInformation(
            "Audit search tenant={TenantId} contains={Contains} result={@Result}",
            tenantId, contains, result);

        return Ok(result);
    }
}
```

3. Ưu tiên lỗ hổng và bottleneck.
4. Đề xuất query/API contract an toàn hơn.
5. Nêu cách test authorization và SQL generation.
6. Đề xuất index/pagination có căn cứ.
7. Nêu logs, traces, metrics phù hợp.

## Câu hỏi gợi mở

- `[Authorize]` có chứng minh caller được phép truy cập `tenantId` không?
- `ToListAsync()` nằm trước hay sau filtering và điều đó thay đổi execution ở đâu?
- API có nên trả entity audit đầy đủ không?
- Offset hay keyset pagination phù hợp hơn khi dữ liệu lớn và liên tục được ghi?
- Log application hiện tại có thể trở thành data-exfiltration channel không?

### Gợi ý 1

Tách ba lớp vấn đề: tenant authorization, query boundary và data exposure.

### Gợi ý 2

Trước `ToListAsync` là `IQueryable`; sau đó các `Where` chạy trên object trong memory. Hãy đưa tenant/time filtering, projection và limit xuống database.

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization
**Problem:** endpoint chỉ yêu cầu authenticated user, nhưng tin `tenantId` từ request.  
**Impact:** caller có thể truy cập tenant khác nếu không có lớp authorization khác.  
**Severity:** Critical.  
**Fix:** derive tenant từ trusted claims/context hoặc policy/resource-based authorization kiểm tra membership/permission trước query.

### 2. Toàn bộ bảng được materialize trước filter
**Problem:** `ToListAsync()` chạy SQL trước mọi `Where`.  
**Impact:** massive DB I/O, network transfer, allocation/GC, latency và có thể OOM.  
**Severity:** Critical.  
**Fix:** giữ `IQueryable` tới cuối, filter/order/project/page rồi mới materialize.

### 3. Trả trực tiếp audit entity có thể lộ secret/PII
**Problem:** response có thể chứa `RequestBody` hoặc field nhạy cảm.  
**Severity:** High.  
**Fix:** projection sang DTO allowlist; redact/mask dữ liệu nhạy cảm tại ingestion và/hoặc presentation.

### 4. Structured logging toàn bộ `result`
**Problem:** serialize audit records vào application logs.  
**Impact:** nhân bản secret/PII sang log store, tăng chi phí và blast radius.  
**Severity:** High.  
**Fix:** chỉ log metadata như tenant-safe identifier, filters đã sanitize, count, duration, correlation ID.

### 5. Không giới hạn time range/input search
**Problem:** caller có thể yêu cầu range rất lớn và expensive text search.  
**Severity:** High.  
**Fix:** validate range, page size, search length; cân nhắc dedicated search capability nếu substring search là requirement quan trọng.

### 6. `Take(5000)` sau materialization không giảm DB workload
**Problem:** limit chỉ áp dụng in-memory.  
**Severity:** High.  
**Fix:** limit/pagination trong SQL.

### 7. Read-only query vẫn tracking entities
**Problem:** EF change tracker giữ objects không cần thiết.  
**Severity:** Medium.  
**Fix:** `AsNoTracking()` và projection.

### 8. Pagination/order chưa deterministic
**Problem:** chỉ sort `CreatedAt`; rows cùng timestamp có thể làm pagination không ổn định.  
**Severity:** Medium.  
**Fix:** composite ordering `(CreatedAt DESC, Id DESC)` và keyset cursor tương ứng.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "AuditReader")]
[HttpGet]
public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
    DateTime fromUtc,
    DateTime toUtc,
    DateTime? beforeCreatedAt,
    long? beforeId,
    int pageSize = 100,
    CancellationToken ct = default)
{
    var tenantId = User.GetRequiredTenantId();

    if (toUtc <= fromUtc || toUtc - fromUtc > TimeSpan.FromDays(31))
        return BadRequest("Invalid time range.");

    pageSize = Math.Clamp(pageSize, 1, 200);

    var query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId &&
                    x.CreatedAt >= fromUtc &&
                    x.CreatedAt < toUtc);

    if (beforeCreatedAt.HasValue && beforeId.HasValue)
    {
        query = query.Where(x =>
            x.CreatedAt < beforeCreatedAt.Value ||
            (x.CreatedAt == beforeCreatedAt.Value && x.Id < beforeId.Value));
    }

    var result = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Select(x => new AuditLogDto(
            x.Id,
            x.CreatedAt,
            x.Action,
            x.ActorId,
            x.StatusCode))
        .Take(pageSize)
        .ToListAsync(ct);

    _logger.LogInformation(
        "Audit search tenant={TenantId} count={Count}",
        tenantId, result.Count);

    return Ok(result);
}
```

Khuyến nghị index cần được xác nhận bằng execution plan và workload thực tế; một candidate hợp lý là composite index bắt đầu bằng `TenantId`, tiếp theo các cột phục vụ range/order như `CreatedAt` và tie-breaker `Id`. Không nên khẳng định một index là tối ưu nếu chưa đo.

## Trade-offs

Keyset pagination nhanh và ổn định hơn offset ở deep pages nhưng không thuận tiện cho “nhảy tới page 237”. Projection giảm payload nhưng nếu UI thực sự cần xem body, nên có endpoint detail riêng với authorization mạnh hơn và redaction. Substring search `%term%` trên dữ liệu lớn thường không hưởng lợi từ B-tree index thông thường; tùy requirement có thể cần full-text/search engine hoặc thay đổi searchable fields.

## Cách kiểm thử

1. Security integration test: user tenant A yêu cầu tenant B và không nhận được dữ liệu B.
2. SQL/EF integration test xác nhận filter, projection và `Take` được thực thi server-side.
3. Load test trên dataset gần production; đo p95/p99, rows read và allocations.
4. Test keyset pagination với nhiều records có cùng `CreatedAt`, không duplicate/missing giữa pages.
5. Test response/logging với payload chứa token giả; secret không xuất hiện trong response DTO hoặc application logs.

## Quan sát trong production

Theo dõi endpoint latency p50/p95/p99, rows returned, DB duration, timeout/error rate và page-size/range distribution. Dùng distributed tracing cho HTTP → EF/SQL. Quan sát execution plans/query store hoặc công cụ tương đương của database, logical reads và index usage. Alert trên latency/error spike thay vì log raw audit content.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `AsNoTracking()` không giải quyết vấn đề lớn nhất của code ban đầu?
2. Nếu product bắt buộc tìm substring trong request body trên hàng trăm triệu records, bạn thiết kế search thế nào?
3. Nếu tenant ID trong token có thể thay đổi theo “admin acting on behalf”, authorization model nên thay đổi ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào hai boundary thường gây incident ở backend: **delivery boundary** giữa message broker–database–external side effect và **trust/query boundary** giữa authenticated identity–tenant authorization–database execution. At-least-once delivery phải được thiết kế cùng idempotency; application-level existence check không thay thế database invariant. Với EF Core, vị trí materialization quyết định phần nào chạy ở database và phần nào chạy trong memory. Multi-tenant security phải authorize resource/tenant chứ không chỉ authenticate caller.

- Tìm failure window trước khi thêm retry.
- Thiết kế retries cùng idempotency và database invariants.
