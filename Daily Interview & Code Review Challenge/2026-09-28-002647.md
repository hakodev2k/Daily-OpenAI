# Câu 1 — `IQueryable` trông vô hại nhưng làm API tìm kiếm chậm và sai kỳ vọng

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ translation, `IQueryable`, deferred execution, SQL Server, query plan, pagination, observability

## Bối cảnh

Một ASP.NET Core .NET 8 API phục vụ màn hình quản lý sản phẩm. SQL Server chứa khoảng 8 triệu sản phẩm. Endpoint hỗ trợ lọc theo tenant, trạng thái, từ khóa và sắp xếp. Team đã tách query building vào repository để “tái sử dụng”.

Ở production, request không có từ khóa thường khoảng 120 ms, nhưng một số request có từ khóa mất 4–12 giây và SQL CPU tăng mạnh. Developer thấy code chỉ có một `ToListAsync` nên kết luận “chắc chắn chỉ có một query, EF Core không phải vấn đề”. Một người khác đề xuất thêm Redis trước khi xem SQL.

Đoạn rút gọn:

```csharp
public IQueryable<Product> GetProducts(Guid tenantId)
{
    return _db.Products
        .Where(x => x.TenantId == tenantId && x.IsActive);
}

public async Task<IReadOnlyList<ProductDto>> SearchAsync(
    Guid tenantId,
    string? keyword,
    int page,
    CancellationToken ct)
{
    var query = _repository.GetProducts(tenantId);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        query = query.Where(x =>
            x.Name.ToLower().Contains(keyword.ToLower()) ||
            x.Description.ToLower().Contains(keyword.ToLower()));
    }

    return await query
        .OrderBy(x => x.Name)
        .Skip((page - 1) * 50)
        .Take(50)
        .Select(x => new ProductDto(x.Id, x.Name, x.Price))
        .ToListAsync(ct);
}
```

Chưa rõ collation, index hiện có, distribution của `TenantId`, selectivity của `IsActive`, execution plan, parameter values gây chậm, hay requirement tìm kiếm là substring thật sự hay chỉ prefix/full-text.

## Câu hỏi chính

Hãy giải thích từ lúc `GetProducts` trả về `IQueryable<Product>` đến lúc `ToListAsync` chạy thì EF Core thực sự làm gì; vì sao “chỉ một SQL query” không đồng nghĩa query hiệu quả; những assumption nào trong đoạn code cần kiểm chứng; và bạn sẽ dùng evidence nào để quyết định sửa LINQ, index, search strategy hay pagination thay vì thêm cache theo phản xạ?

## Câu hỏi làm rõ nên cân nhắc

1. Business cần case-insensitive substring search, prefix search hay full-text semantics?
2. SQL Server database/column đang dùng collation nào, và có cần gọi `ToLower()` để đạt requirement không?
3. Execution plan của request chậm cho thấy seek, scan, sort, memory grant và row estimates như thế nào?
4. Có composite index nào bắt đầu bằng `TenantId` và phù hợp với filter/order thực tế không?
5. Người dùng có thể đi đến page rất sâu hay UI chỉ tải vài page đầu?

## Gợi ý tư duy

### Gợi ý 1

`IQueryable` là expression tree được compose; query chưa chạy tại thời điểm repository trả về nó.

### Gợi ý 2

Hãy tách ba câu hỏi: SQL nào được generate, database phải làm bao nhiêu work để thực thi SQL đó, và requirement search/pagination thực sự cần semantics nào.

### Gợi ý 3

Các function áp lên indexed column, wildcard semantics và deep offset pagination có thể làm cost tăng dù application chỉ thực hiện một round trip.

## Cấu trúc trả lời đề xuất

1. Xác nhận search và pagination requirements.
2. Giải thích deferred execution và LINQ translation.
3. Xem generated SQL và query parameters.
4. Thu thập execution plan, logical reads, duration và row estimates.
5. Phân tích predicate, collation, index và sort.
6. So sánh substring search, prefix search và full-text/search engine.
7. Đánh giá offset so với keyset pagination.
8. Sửa dựa trên evidence.
9. Integration/load test với dữ liệu có distribution gần production.
10. Theo dõi latency và SQL telemetry sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` giữ expression tree; các `Where`, `OrderBy`, `Skip`, `Take`, `Select` được compose cho tới terminal operation như `ToListAsync`.
- Một round trip vẫn có thể cực đắt nếu SQL phải scan/sort nhiều dữ liệu.
- Không được khẳng định `ToLower()` là nguyên nhân duy nhất nếu chưa biết collation và generated SQL.
- Cần xem SQL + actual execution plan/query telemetry thay vì suy đoán từ LINQ.
- `Contains` thường thể hiện substring semantics; index B-tree thông thường không tự giải quyết mọi substring search.
- `Skip` ở page sâu vẫn có thể khiến database xử lý/bỏ qua nhiều row trước khi trả page.
- Cache không sửa một access pattern hoặc query plan sai và còn tạo invalidation complexity.

### Điểm cộng

- Projection trước materialization giúp chỉ lấy cột cần thiết.
- Đề xuất index phải dựa vào filter/order/selectivity và write cost, không chỉ “index Name”.
- Nếu requirement là prefix, thiết kế predicate/search khác substring có thể mở lựa chọn tối ưu hơn.
- Nếu requirement là linguistic/full-text search, đánh giá SQL Server Full-Text Search hoặc Elasticsearch dựa trên nhu cầu thay vì ép relational index làm search engine.
- Keyset pagination phù hợp khi UX không yêu cầu nhảy tùy ý tới page N và có deterministic sort key.

### Senior+

- Phân biệt application-level LINQ composition với database optimizer behavior.
- Xem parameter sensitivity/data skew nếu cùng SQL shape nhưng latency khác mạnh theo tenant/keyword.
- Thiết kế benchmark với cardinality và distribution thực tế, không chỉ vài nghìn rows local.
- Xác định SLO và dùng p95/p99, logical reads, CPU, query duration để chứng minh improvement.

## Hướng giải quyết tham khảo

`GetProducts` chưa lấy product từ database. EF Core trả về một `IQueryable<Product>` gắn với provider và expression tree. Các operator sau đó tiếp tục mở rộng tree. Khi `ToListAsync(ct)` được gọi, EF Core mới translate phần hỗ trợ được sang SQL, gửi command tới SQL Server và materialize projection thành `ProductDto`. Vì vậy “chỉ có một query” chỉ nói về round trip trong path này; nó không nói database đọc bao nhiêu pages, sort bao nhiêu rows hay dùng index hiệu quả hay không.

Tôi sẽ lấy generated SQL bằng logging/`ToQueryString()` trong môi trường phù hợp, sau đó capture actual execution plan hoặc Query Store telemetry cho các parameter gây chậm. Tôi muốn biết operator nào chiếm cost, logical reads, scan/seek, sort, spills, row estimates và actual rows. Tôi cũng kiểm tra collation trước khi kết luận về `ToLower()`: nếu column đã dùng case-insensitive collation thì lowercasing có thể vừa dư thừa vừa làm predicate khó tận dụng access path mong muốn; nhưng recommendation phải dựa trên schema thực tế.

Nếu business thật sự cần `%keyword%` trên hàng triệu records, một index B-tree đơn giản trên `Name` không phải câu trả lời tổng quát. Tôi sẽ xác minh liệu prefix search đủ dùng, hay cần SQL Server Full-Text Search/Elasticsearch vì semantics tìm kiếm phức tạp hơn. Nếu Elasticsearch được chọn thì phải chấp nhận synchronization và eventual consistency, không coi nó là drop-in optimization.

Với pagination, `Skip`/`Take` có thể ổn ở page nông. Nếu người dùng scroll sâu và sort key ổn định, keyset pagination theo `Name, Id` có thể giảm work, nhưng đổi API semantics nên chỉ làm nếu UX cho phép. Index cũng cần thiết kế quanh tenant/filter/order dựa trên selectivity và execution plan; thêm index có write/storage cost.

Tôi chỉ cân nhắc Redis nếu evidence cho thấy cùng query/result được đọc lặp lại đủ nhiều, freshness requirement cho phép và team có invalidation strategy. Trước hết phải sửa query/access pattern. Sau rollout tôi theo dõi SQL duration, logical reads/CPU, API p95/p99, timeout rate và query-plan regression.

## Mẫu trả lời trong phỏng vấn

“Ở đây `IQueryable` chưa execute trong repository. Nó giữ expression tree và các `Where`, `OrderBy`, `Skip`, `Take`, `Select` tiếp tục được compose; `ToListAsync` mới trigger translation và execution. Nhưng một query vẫn có thể scan hàng triệu rows rồi sort nên ‘một query’ không chứng minh hiệu quả. Tôi sẽ xác nhận search semantics và collation, lấy generated SQL cùng actual execution plan, logical reads và parameters của request chậm. Nếu requirement là substring trên 8 triệu rows thì tôi không mặc định thêm index Name; tôi sẽ so sánh prefix/full-text/Elasticsearch theo semantics. Deep offset cũng cần xem lại, có thể dùng keyset nếu UX cho phép. Redis chỉ đến sau khi evidence chứng minh caching phù hợp, vì cache không sửa query plan và thêm invalidation complexity. Tôi sẽ load test với distribution gần production và theo dõi p95/p99 cùng SQL CPU/reads sau rollout.”

## Câu hỏi đào sâu

1. Nếu actual execution plan cho thấy index seek nhưng request vẫn chậm 8 giây, bạn sẽ điều tra gì tiếp?
2. Nếu Product Owner bắt buộc substring search và kết quả phải phản ánh update gần như ngay lập tức, bạn chọn SQL Full-Text Search hay Elasticsearch dựa trên tiêu chí nào?
3. Team muốn cache mọi kết quả search 10 phút để tránh sửa query trong sprint này; bạn phản biện và giảm rủi ro thế nào?

## Lỗi trả lời thường gặp

- Cho rằng một `ToListAsync` đồng nghĩa performance tốt.
- Đề xuất index mà không xem execution plan/selectivity.
- Khẳng định `ToLower()` luôn sai mà không kiểm tra collation.
- Đưa Redis vào trước khi xác định bottleneck.
- Đổi sang Elasticsearch nhưng bỏ qua synchronization và consistency.

## Thang điểm 0–10

- **0–2:** Chỉ nói “thêm index/cache”, không giải thích `IQueryable`.
- **3–4:** Hiểu deferred execution nhưng thiếu database evidence.
- **5–6:** Phân tích được SQL/index/search/pagination và đề xuất investigation hợp lý.
- **7–8:** Có production evidence, trade-offs và testing/monitoring rõ ràng.
- **9–10:** Kết nối EF translation, optimizer, search semantics, data distribution và API design thành quyết định có điều kiện.

# Câu 2 — Optimizely publish thành công nhưng khách hàng vẫn thấy nội dung cũ

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, ASP.NET Core, Akamai/CDN, caching, Azure App Service, distributed production troubleshooting, observability

## Bối cảnh

Một marketing website dùng Optimizely CMS và ASP.NET Core, chạy 4 instances trên Azure App Service sau Akamai. Editor publish một campaign page lúc 09:00. Backoffice hiển thị version mới ngay, nhưng khoảng 30% người dùng vẫn thấy headline cũ trong 20–40 phút. Refresh nhiều lần đôi khi đổi qua lại giữa cũ và mới.

Sau 45 phút hiện tượng tự hết. Không có spike rõ ràng về HTTP 5xx. Team có ba giả thuyết ban đầu:

- “Optimizely publish lỗi.”
- “Akamai cache quá lâu.”
- “Một App Service instance chưa nhận invalidation.”

Ứng dụng còn có một custom in-memory cache cho view model campaign. Chưa rõ cache key/TTL, event invalidation, CDN cache key, `Cache-Control`, purge flow, instance affinity, origin response theo từng instance, hay editor đang xem qua cùng public CDN path hay backoffice preview path.

## Câu hỏi chính

Bạn đang on-call. Hãy trình bày cách xử lý incident theo thứ tự impact → stabilize → evidence → hypotheses → verification → remediation; làm sao phân biệt CMS content version, application cache, multi-instance invalidation, CDN cache và browser cache; và bạn sẽ sửa hệ thống thế nào để lần publish sau không phụ thuộc vào “chờ cache tự hết”?

## Câu hỏi làm rõ nên cân nhắc

1. Response của user cũ/mới có `Age`, `Cache-Control`, CDN cache status, ETag hoặc header nhận diện origin/version nào?
2. Request bypass CDN trực tiếp tới origin và từng instance có trả cùng content version không?
3. Custom in-memory cache được invalidated bằng event nào, hay chỉ dựa vào TTL cục bộ?
4. Akamai cache key có bao gồm hostname/path/query/cookie nào làm cùng page tồn tại nhiều variants không?
5. Business chấp nhận stale content bao lâu sau publish và có yêu cầu purge/invalidation tự động không?

## Gợi ý tư duy

### Gợi ý 1

Đừng purge mọi thứ trước khi lưu evidence tối thiểu. Cùng một URL có nhiều cache layers và mỗi layer có thể có lifecycle khác nhau.

### Gợi ý 2

Việc refresh trả cũ/mới luân phiên là tín hiệu hữu ích: hãy tìm layer nào có nhiều nodes/instances với state không đồng nhất.

### Gợi ý 3

Thiết kế publish correctness cần cache policy và invalidation contract rõ ràng; TTL chỉ là safety net, không phải luôn là cơ chế consistency chính.

## Cấu trúc trả lời đề xuất

1. Xác định scope và business impact.
2. Chọn biện pháp stabilize có blast radius thấp.
3. Capture headers/content version/correlation data trước khi purge.
4. Bypass từng cache layer để khoanh vùng.
5. Kiểm tra origin consistency giữa App Service instances.
6. Kiểm tra custom cache invalidation.
7. Kiểm tra CDN key, TTL và purge behavior.
8. Sửa root cause và định nghĩa freshness contract.
9. Test publish/invalidation trên multi-instance + CDN.
10. Thêm telemetry và runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nhảy từ symptom tới kết luận “CDN lỗi”.
- So sánh response qua public CDN với origin/bypass path và, nếu khả thi, giữa các instances.
- Kiểm tra headers/cache metadata để biết response đến từ cache layer nào.
- Local in-memory cache trên 4 instances là bốn state độc lập nếu không có invalidation coordination phù hợp.
- CDN có thể giữ nhiều variants nếu cache key khác nhau; purge sai key/scope có thể để lại stale variants.
- Cần xác minh content version tại CMS/origin trước khi đổ lỗi cho publish.
- Remediation phải gắn với freshness requirement và có telemetry xác nhận invalidation.

### Điểm cộng

- Dùng content/version identifier an toàn trong response/log để correlate mà không lộ dữ liệu nhạy cảm.
- Phân biệt browser cache, CDN edge cache, application cache và CMS-level caching.
- Purge targeted URL/key trước khi purge toàn site để giảm origin surge.
- Đánh giá stale-while-revalidate/stale-if-error chỉ nếu phù hợp business semantics.
- Có synthetic post-publish validation từ nhiều locations/path.

### Senior+

- Thiết kế invalidation idempotent và observable.
- Nếu custom cache không tạo đủ value, cân nhắc bỏ nó thay vì thêm distributed cache theo phản xạ.
- Nếu cần distributed coordination, chọn mechanism dựa trên correctness/failure behavior, không chỉ “dùng Redis”.
- Runbook có rollback/purge/bypass và giới hạn blast radius.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng scope: URL nào, region nào, tỷ lệ stale, campaign có deadline hay compliance impact không. Nếu impact cao, tôi có thể giảm TTL hoặc targeted purge URL bị ảnh hưởng, nhưng trước đó capture vài response cũ/mới gồm timestamp, content version, `Age`, `Cache-Control`, ETag/CDN cache status và correlation ID để không xóa hết evidence.

Tiếp theo tôi chia đường đi thành CMS → application/origin → CDN → browser. Tôi xác minh version đã publish trong Optimizely và gọi origin theo cách vận hành cho phép để xem origin có version mới không. Nếu các origin responses luân phiên cũ/mới, tôi tập trung vào multi-instance application state hoặc CMS synchronization. Custom `IMemoryCache` đáng nghi vì mỗi process có cache riêng; nếu publish chỉ evict cache trong instance xử lý event, các instance khác có thể giữ view model cũ tới TTL.

Nếu origin luôn mới nhưng public endpoint đôi lúc cũ, tôi xem Akamai cache status, cache key và variants. Có thể purge chỉ một representation trong khi cookie/query/host tạo variants khác. Tôi cũng phân biệt browser cache bằng request sạch hoặc controlled client; không kết luận từ refresh của một browser.

Fix phụ thuộc freshness requirement. Với campaign cần cập nhật nhanh, publish flow nên tạo invalidation signal đáng tin cậy cho application cache và targeted CDN purge, có retry/idempotency và telemetry. TTL vẫn là fallback. Nếu custom view-model cache không chứng minh được lợi ích, bỏ layer đó có thể an toàn hơn xây distributed invalidation phức tạp. Nếu giữ, cache key phải chứa đúng content identity/language/version dimensions và invalidation phải hoạt động trên mọi instance.

Tôi sẽ có integration/E2E test publish content, gọi nhiều origin instances/public CDN path, xác nhận version convergence trong SLO; test purge failure và retry. Dashboard theo dõi publish timestamp → first fresh origin → edge convergence, purge failures, cache hit/miss và content-version mismatch.

## Mẫu trả lời trong phỏng vấn

“Refresh lúc cũ lúc mới khiến tôi nghĩ tới state không đồng nhất giữa nodes, nhưng tôi chưa kết luận CDN hay App Service. Tôi sẽ xác định impact, capture response headers/version từ cả stale và fresh response, rồi đi từng layer: xác minh Optimizely version đã publish; bypass CDN để kiểm tra origin; nếu có thể so sánh các App Service instances; sau đó kiểm tra custom in-memory cache invalidation. Nếu origin luôn mới thì mới tập trung Akamai cache key, variants, TTL và purge. Với incident gấp tôi ưu tiên targeted purge thay vì purge toàn site để tránh origin surge. Fix lâu dài phải dựa trên freshness SLO: publish phải phát invalidation observable/idempotent cho các cache layer cần thiết, TTL chỉ là fallback. Nếu custom cache không mang lại lợi ích đo được, tôi sẽ cân nhắc bỏ nó. Sau đó test multi-instance + CDN và theo dõi thời gian convergence sau mỗi publish.”

## Câu hỏi đào sâu

1. Nếu bypass CDN vẫn trả lúc cũ lúc mới nhưng tất cả App Service instances đọc cùng một Optimizely database, bạn sẽ kiểm tra những cơ chế nào tiếp theo?
2. Nếu business yêu cầu publish toàn cầu dưới 5 giây nhưng CDN purge đôi khi mất lâu hơn, bạn sẽ thách thức hoặc thiết kế requirement ra sao?
3. Một developer đề xuất chuyển toàn bộ custom cache sang Redis để “hết stale”; vì sao điều đó chưa đủ chứng minh root cause và có thể tạo failure mode mới?

## Lỗi trả lời thường gặp

- Purge toàn CDN ngay rồi mất evidence và tạo origin spike.
- Đồng nhất CMS cache với CDN cache.
- Quên rằng `IMemoryCache` là process-local trong scale-out.
- Chỉ tăng/giảm TTL mà không thiết kế invalidation.
- Không định nghĩa freshness SLO hay telemetry để xác minh fix.

## Thang điểm 0–10

- **0–2:** Chọn ngẫu nhiên một cache layer và restart/purge.
- **3–4:** Biết có nhiều cache layers nhưng investigation thiếu thứ tự/evidence.
- **5–6:** Khoanh vùng được CMS/origin/CDN/browser và có remediation hợp lý.
- **7–8:** Có stabilization, blast-radius control, multi-instance reasoning, testing và observability.
- **9–10:** Thiết kế được freshness contract/invalidation architecture có failure handling và đo được convergence.

# Câu 3 — Có nên đưa API hiện tại từ Azure App Service lên Kubernetes?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Kubernetes, Azure App Service, architecture trade-offs, CI/CD, operations, scalability, reliability, cost of complexity, modernization

## Bối cảnh

Một enterprise management platform gồm:

- ASP.NET Core .NET 8 API;
- React frontend;
- SQL Server;
- Redis;
- Azure Blob Storage;
- một số background jobs;
- khoảng 25 deployments/tháng.

API hiện chạy trên Azure App Service on Linux với 3–8 instances theo tải. p95 bình thường 220 ms, availability đáp ứng SLO hiện tại. Team 8 developers có CI/CD ổn định và Application Insights. Không có platform/SRE team chuyên trách.

Công ty sắp thêm 3 backend services trong 12 tháng. Một architect đề xuất chuyển toàn bộ backend sang Kubernetes ngay vì “sắp thành microservices, Kubernetes scale tốt hơn và là chuẩn enterprise”. Một tech lead muốn ở lại App Service vì chưa có production problem nào Kubernetes giải quyết rõ ràng.

Có thêm yêu cầu mới: một workload xử lý batch cần CPU cao trong khoảng 15 phút vài lần mỗi ngày; một service khác có thể cần custom sidecar/proxy trong tương lai. Chưa có cost model, compliance constraint, network topology target, RTO/RPO thay đổi, hay bằng chứng App Service đang giới hạn workload.

## Câu hỏi chính

Nếu bạn phải đưa ra architecture decision cho 12–18 tháng tới, bạn sẽ quyết định giữ App Service, chuyển toàn bộ sang Kubernetes, hay áp dụng mô hình hỗn hợp như thế nào? Hãy nêu criteria, evidence cần thu thập, migration/rollback strategy, operational ownership và điều kiện cụ thể nào sẽ khiến bạn thay đổi quyết định.

## Câu hỏi làm rõ nên cân nhắc

1. Ba service mới có thực sự cần independent scaling/deployment/isolation hay chỉ là logical modules?
2. Batch workload có thể tách thành worker/job trên compute phù hợp mà không kéo toàn bộ API sang Kubernetes không?
3. Sidecar/proxy là requirement đã xác nhận hay mới là khả năng tương lai?
4. Team có ai chịu trách nhiệm cluster lifecycle, upgrades, ingress, policies, observability, capacity và incident response?
5. Có networking, compliance, portability hoặc workload constraints nào App Service không đáp ứng được không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu từ sản phẩm. Bắt đầu từ workload, constraints, SLO và ownership.

### Gợi ý 2

Kubernetes giải quyết một tập vấn đề orchestration, nhưng cũng biến nhiều platform concerns thành trách nhiệm của team.

### Gợi ý 3

Architecture decision không nhất thiết nhị phân; workload đặc biệt có thể dùng compute khác trong khi API ổn định tiếp tục ở managed PaaS.

## Cấu trúc trả lời đề xuất

1. Làm rõ business/technical drivers.
2. Baseline trạng thái hiện tại bằng SLO, deployment và cost.
3. Phân loại workload theo scaling/runtime/isolation needs.
4. Xác định App Service constraints thực tế.
5. Xác định Kubernetes capabilities thực sự cần.
6. So sánh operational burden và team readiness.
7. Chọn kiến trúc tối thiểu đáp ứng requirement.
8. Đề xuất proof-of-concept cho uncertainty lớn.
9. Lập migration, rollback và observability plan.
10. Định nghĩa trigger để revisit ADR.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi số lượng services là lý do tự động dùng Kubernetes.
- App Service đang đáp ứng SLO là evidence quan trọng; migration phải có driver rõ.
- Kubernetes mang lại deployment/orchestration primitives nhưng tăng operational surface: cluster/node/runtime upgrades, probes, resources, ingress/networking, policies, troubleshooting.
- Batch CPU workload nên được đánh giá riêng thay vì ép architecture toàn hệ thống thay đổi.
- Sidecar requirement tương lai cần xác minh trước khi dùng làm justification hiện tại.
- Cần migration/rollback theo workload, không big-bang.
- Quyết định phải có ownership, skill/cost model và observability.

### Điểm cộng

- Có thể giữ API trên App Service và thử workload đặc thù trên nền tảng phù hợp; Kubernetes chỉ là một lựa chọn.
- Nếu chọn Kubernetes, application developer phải hiểu readiness/liveness, requests/limits, graceful shutdown, rolling deployment và configuration/secrets.
- Phân biệt horizontal application scaling với operational scalability của platform/team.
- Dùng ADR với measurable triggers: deployment constraints, required runtime primitives, cost, SLO, isolation, networking.
- Không tự động chuyển monolith thành microservices chỉ vì đổi hosting.

### Senior+

- Tính migration cost, dual-running, failure domains, on-call burden và opportunity cost.
- Đề xuất pilot một non-critical workload để đo deploy lead time, incident burden, resource utilization và platform toil.
- Xem xét organizational boundary: nếu sau này có platform team, economics của Kubernetes có thể thay đổi.
- Đặt exit criteria cho pilot và rollback path trước khi bắt đầu.

## Hướng giải quyết tham khảo

Với dữ liệu hiện tại, tôi chưa thấy lý do để chuyển toàn bộ backend khỏi App Service. API đang đáp ứng SLO, autoscale hoạt động, deployment pipeline ổn và team không có platform/SRE ownership. “Sắp có nhiều service” và “enterprise standard” không đủ là technical driver.

Tôi sẽ baseline chi phí, p95/p99, availability, deploy frequency/failure rate, scaling behavior và các constraint hiện tại. Sau đó phân loại ba service mới. Nếu chúng chỉ cần independent deployment và App Service đáp ứng runtime/networking, có thể deploy riêng mà không cần cluster. Batch CPU 15 phút vài lần/ngày là workload khác; tôi sẽ đánh giá worker/job compute riêng dựa trên scheduling, startup, retry, cost và operational needs. Không cần đổi hosting của API chỉ để giải quyết batch.

Kubernetes trở nên hợp lý hơn nếu nhiều workload thực sự cần orchestration primitives như custom scheduling, sidecars đã xác nhận, fine-grained resource controls, standardized container platform ở quy mô đủ lớn, networking/policy requirements hoặc portability mà App Service không đáp ứng; đồng thời tổ chức phải sở hữu platform lifecycle. Nhưng nếu dùng Kubernetes, team phải vận hành readiness/liveness, requests/limits, rollout, secrets/config, ingress, upgrades và troubleshooting; “managed Kubernetes” không xóa các trách nhiệm application/platform đó.

Tôi sẽ ghi ADR: giữ App Service cho workload đang ổn, tách workload mới theo requirement, và nếu uncertainty về Kubernetes đáng kể thì pilot một service không critical. Pilot đo lead time, deployment failure, resource utilization, incident/toil và cost. Migration nếu có sẽ từng service, với routing/cutover quan sát được và rollback về hosting cũ. Tôi revisit khi xuất hiện constraint đo được hoặc organization có platform capability mới.

## Mẫu trả lời trong phỏng vấn

“Với evidence hiện tại tôi không chuyển toàn bộ sang Kubernetes. App Service đang đạt SLO, autoscale được và team không có platform ownership; số service tăng không tự động biến Kubernetes thành lựa chọn đúng. Tôi sẽ baseline cost/SLO/deployment, rồi phân loại từng workload. Batch CPU nên được giải riêng bằng compute phù hợp; sidecar chỉ là driver khi requirement được xác nhận. Kubernetes đáng cân nhắc nếu chúng ta thật sự cần orchestration primitives, resource/isolation/networking controls hoặc standardized platform ở quy mô đủ lớn và có người sở hữu vận hành. Tôi sẽ giữ API ổn định trên App Service, pilot một workload ít critical nếu cần học Kubernetes, đặt exit criteria và đo toil/cost/reliability. Nếu pilot chứng minh value, migration từng service với rollback; nếu không, không trả complexity tax chỉ để theo xu hướng.”

## Câu hỏi đào sâu

1. Nếu CTO yêu cầu “Kubernetes trong 6 tháng” vì chiến lược chuẩn hóa toàn công ty, bạn sẽ biến mandate đó thành kế hoạch kỹ thuật an toàn như thế nào?
2. Nếu pilot Kubernetes giảm infrastructure cost 25% nhưng số incident vận hành tăng gấp đôi, bạn đánh giá trade-off ra sao?
3. Nếu ba service mới cần transaction consistency chặt với cùng SQL database, điều đó ảnh hưởng thế nào tới quyết định service boundary và deployment platform?

## Lỗi trả lời thường gặp

- Đồng nhất microservices với Kubernetes.
- Chọn Kubernetes chỉ vì “scale tốt hơn” mà không nêu bottleneck hiện tại.
- Bỏ qua platform ownership và on-call burden.
- Big-bang migration không có rollback.
- Dùng một workload đặc biệt để biện minh đổi platform cho mọi workload.

## Thang điểm 0–10

- **0–2:** Chọn platform theo xu hướng hoặc preference.
- **3–4:** Nêu được pros/cons nhưng không gắn với workload/SLO.
- **5–6:** Có criteria, workload segmentation và migration reasoning.
- **7–8:** Có operational ownership, pilot, metrics, rollback và ADR triggers.
- **9–10:** Cân bằng technical capability, organizational economics, failure domains và opportunity cost; recommendation thay đổi rõ ràng theo evidence.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` và deferred execution chỉ giải thích thời điểm query được compose/execute; performance vẫn phải được chứng minh bằng generated SQL, execution plan và telemetry.
- Production caching là chuỗi nhiều layers. CMS, application cache, CDN và browser có failure/invalidation semantics khác nhau; stale content cần được khoanh vùng bằng evidence.
- Architecture decision phải xuất phát từ workload, constraints, SLO và ownership. Kubernetes là công cụ orchestration, không phải bước tiến bắt buộc khi số service tăng.
- Cache, search engine hay platform migration đều tạo complexity mới; chỉ thêm chúng khi evidence cho thấy chúng giải quyết vấn đề đáng trả chi phí.

## Mẫu tư duy cần nhớ

- Clarify semantics before optimizing.
- Measure before optimizing.
- Isolate one failure layer at a time.
- Treat cache invalidation as a consistency contract, not only a TTL.
- Choose the simplest platform that satisfies measured requirements.
