# Câu 1 — Vì sao bộ nhớ tăng sau khi export Excel dù không có memory leak?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** .NET 8, Garbage Collector, LOH, allocation, streaming, IDisposable, ASP.NET Core.

## Bối cảnh

Một ASP.NET Core API xuất báo cáo doanh thu. Mỗi request tạo nhiều mảng byte và MemoryStream, cuối cùng trả file 80–200 MB. Sau một đợt 30 người dùng export đồng thời, working set tăng từ 600 MB lên 4 GB; request bình thường vẫn hoạt động, nhưng container đôi khi bị OOM kill. Developer kết luận GC bị lỗi vì sau khi request hoàn thành RSS không trở lại 600 MB. Chưa có allocation profile, dump, GC counters hoặc bằng chứng object còn được tham chiếu.

## Câu hỏi chính

Giải thích vòng đời object, GC generations, LOH, managed heap và RSS trong tình huống này. Làm thế nào phân biệt allocation pressure, retained memory, fragmentation, native memory và leak, rồi giảm rủi ro mà không kết luận vội?

## Câu hỏi làm rõ nên cân nhắc

1. File được tạo toàn bộ trong RAM hay stream từng phần? Thư viện export có giữ workbook/caches không?
2. Memory metric là managed heap, private bytes, RSS hay container working set?
3. Memory tăng theo số request đang chạy hay không giảm qua nhiều chu kỳ tải/nghỉ?
4. Giới hạn RAM container, concurrency, file size và timeout là bao nhiêu?
5. Có static cache, event subscriptions, pooled buffers hoặc unmanaged allocations không?

## Gợi ý tư duy

### Gợi ý 1
RSS không đồng nghĩa số byte object còn sống.

### Gợi ý 2
Hãy tách allocated bytes, live heap, GC committed memory và native memory; xem mảng lớn đi vào vùng nào.

### Gợi ý 3
Đo heap sau full GC ở môi trường kiểm thử, tìm retention roots, rồi giới hạn peak concurrent bytes trước khi tinh chỉnh GC.

## Cấu trúc trả lời đề xuất

1. Xác định metric và thời điểm đo.
2. Giải thích allocation, LOH, generations và GC.
3. Đưa ít nhất ba giả thuyết cạnh tranh.
4. Thu thập counters, traces, dumps phù hợp.
5. Đề xuất giảm peak allocation và concurrency; đánh giá trade-offs.
6. Kiểm thử tải và đặt ngưỡng cảnh báo.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Mảng lớn (thông thường từ khoảng 85 KB) được phân bổ trên LOH; tạo nhiều bản sao file gây allocation pressure.
- GC thu hồi object không còn reachable nhưng không cam kết trả ngay toàn bộ committed memory cho OS.
- Phân biệt live managed objects, GC reserved/committed memory, native memory và RSS; không suy ra leak từ RSS.
- Có thể phải giảm concurrency, tránh buffer toàn bộ file, hoặc stream từ nguồn.

### Điểm cộng
- Xác định retention roots bằng dump; kiểm tra pinned buffers và thư viện native.
- Dùng dotnet-counters, dotnet-gcdump/dotnet-dump ở môi trường có quyền và dữ liệu an toàn; đối chiếu container metrics.
- Cân nhắc backpressure, 429/503 với Retry-After, bounded queue, cleanup khi client disconnect.

### Senior+
- Tính peak memory budget: nếu mỗi export giữ 2–3 bản sao 150 MB thì 10 export có thể cần nhiều GB, chưa tính overhead.
- Không bật LOH compaction hoặc GC.Collect tùy tiện; chỉ tối ưu dựa trên bằng chứng và kiểm thử latency.

## Hướng giải quyết tham khảo

**Giả định:** mỗi request hiện tạo một workbook, chuyển thành byte array rồi copy vào MemoryStream trước khi gửi response. Nếu thư viện chỉ hỗ trợ in-memory workbook, streaming response không loại bỏ toàn bộ peak RAM; cần đo chính xác.

**Cơ chế:** Allocation tạo object trên managed heap; object lớn thường vào LOH. GC xét reachability và generations; một object không còn được tham chiếu có thể vẫn chiếm không gian heap cho đến collection. Sau collection, runtime có thể giữ lại committed pages để phục vụ allocation tiếp theo. Working set/RSS còn chịu ảnh hưởng native heap, runtime, file mappings và hệ điều hành. Vì vậy cần xem đường cong live heap và allocation rate thay vì RSS đơn lẻ.

**Điều tra:** ghi timestamp của từng export, kích thước file, số request đồng thời, bytes allocated, GC heap size, Gen2/LOH size, GC pause time, process RSS và container OOM events. So sánh trước tải, lúc peak, sau nghỉ và sau GC tự nhiên; chỉ dùng forced full GC trong bài test có kiểm soát. Nếu live heap sau nghỉ tăng đều, phân tích retention roots trong dump. Nếu live heap ổn nhưng RSS cao, xem committed heap, pools và native allocations. Nếu OOM trùng số export đồng thời, peak memory là giả thuyết ưu tiên.

**Khắc phục:** dùng writer hỗ trợ forward-only streaming nếu khả thi, tránh ToArray/copy thừa; trả FileStreamResult hoặc ghi vào Response.Body với CancellationToken, bảo đảm dispose stream và temp files. Với format buộc materialize, tạo file tạm trên storage có quota và lifecycle cleanup; không giả định disk vô hạn. Giới hạn số export đồng thời theo memory budget; chuyển báo cáo lớn sang background job có trạng thái và download URL nếu latency chấp nhận. Áp dụng auth, giới hạn dữ liệu theo tenant và timeout; không ghi dữ liệu nhạy cảm vào logs.

**Trade-offs:** streaming giảm peak RAM nhưng làm request dài hơn và tăng rủi ro khi client ngắt; background export tăng độ phức tạp trạng thái, lưu trữ và dọn dẹp; file tạm cần encryption/permissions và quota. Kiểm thử 1, 5, 20 export đồng thời, file lớn nhất, cancellation, disk-full và load kéo dài. Alert trên memory headroom, OOM count, export concurrency, p95 duration và failure rate.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không gọi đây là memory leak chỉ vì RSS không giảm. Tôi cần tách lượng object còn sống khỏi memory runtime đã commit và native allocations. Với export 200 MB, nhiều lần copy byte array và 30 request song song có thể tạo peak nhiều GB, nhất là trên LOH. Tôi sẽ đo allocation rate, GC heap, LOH, RSS và số export đang chạy; nếu live heap tiếp tục tăng sau giai đoạn nghỉ mới đi tìm retention roots. Ngắn hạn tôi giới hạn concurrency theo RAM budget, sau đó loại bỏ buffer/copy thừa hoặc chuyển báo cáo lớn sang job và lưu file tạm có cleanup. Tôi sẽ load-test cùng giới hạn container thật, theo dõi OOM, GC pause và p95 để chứng minh thay đổi.”

## Câu hỏi đào sâu

1. Khi live heap giảm nhưng RSS không giảm, cần thêm bằng chứng nào trước khi thay đổi GC settings?
2. Nếu thư viện Excel bắt buộc giữ toàn bộ workbook trong RAM, bạn thiết kế export service thế nào?
3. Streaming có thể gây vấn đề gì khi client hủy request sau khi đã gửi response headers?

## Lỗi trả lời thường gặp

- Đồng nhất RSS với live managed heap.
- Gọi GC.Collect trên mọi request để “chữa” OOM.
- Dùng MemoryStream rồi ToArray và gọi đó là streaming.
- Bỏ qua concurrency budget và native allocations.
- Không kiểm thử cancellation và cleanup.

## Thang điểm 0–10

- 0–2: Làm rõ metric, quy mô và giả định.
- 0–2: Giải thích chính xác GC/LOH/RSS.
- 0–2: Có giả thuyết và phương pháp đo để phân biệt.
- 0–2: Đề xuất giảm peak memory và failure handling.
- 0–1: Trade-offs, test và observability.
- 0–1: Trình bày mạch lạc, ưu tiên đúng.

# Câu 2 — Cosmos DB tăng RU và trả 429 sau chiến dịch bán hàng

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, RU, 429, .NET SDK, observability, incident response.

## Bối cảnh

API ASP.NET Core phục vụ giỏ hàng trên Cosmos DB. Trong 15 phút flash sale, p99 của GET cart tăng từ 180 ms lên 8 giây, 429 xuất hiện, người dùng có lúc thấy giỏ hàng cập nhật chậm. Dashboard cho thấy tổng RU/s chưa đạt mức provisioned của container, nhưng một nhóm request liên quan một merchant lớn bị ảnh hưởng mạnh. SDK có retry mặc định theo chính sách cấu hình; ứng dụng còn có retry ở tầng API. Chưa biết partition key, request diagnostics, physical partition distribution, consistency level và truy vấn thực tế.

## Câu hỏi chính

Bạn sẽ điều hành incident, xác minh nguyên nhân, phục hồi dịch vụ và quyết định thay đổi data model/partitioning thế nào để không gây mất hoặc nhân đôi cập nhật giỏ hàng?

## Câu hỏi làm rõ nên cân nhắc

1. Partition key là merchantId, customerId hay một khóa khác? Access pattern đọc/ghi chủ đạo?
2. 429 tập trung vào logical/physical partition nào, hay toàn container?
3. Các request là point reads hay cross-partition queries; RU charge và query metrics ra sao?
4. Có bao nhiêu tầng retry, backoff và timeout budget?
5. Giỏ hàng yêu cầu consistency, concurrency control và độ bền ghi như thế nào?

## Gợi ý tư duy

### Gợi ý 1
Tổng throughput còn dư không bảo đảm mọi partition đều có đủ tài nguyên.

### Gợi ý 2
Đối chiếu partition key, hot keys, diagnostics, 429 và retry amplification.

### Gợi ý 3
Phân biệt mitigation nhanh với partition-key migration dài hạn; đừng đổi khóa mà chưa kiểm tra atomicity và routing.

## Cấu trúc trả lời đề xuất

1. Xác định phạm vi ảnh hưởng và thao tác ghi có rủi ro.
2. Ổn định traffic, timeout và retry.
3. Thu thập RU, 429, partition diagnostics, dependency latency.
4. Đưa giả thuyết cạnh tranh và cách bác bỏ.
5. Đề xuất mitigation, root-cause remediation và migration.
6. Kiểm thử, rollout, rollback và cảnh báo.

## Ý chính của câu trả lời tốt

### Bắt buộc
- 429 là tín hiệu throttling; phân biệt throttling có retry thành công với request thất bại.
- Hot partition có thể xảy ra dù tổng RU/s chưa sử dụng hết.
- Phải phân tích partition key theo access pattern và dữ liệu thực, không chọn theo cardinality đơn thuần.
- Retry cần giới hạn theo end-to-end deadline; tránh retry chồng nhiều tầng.
- Kiểm soát concurrent cart updates bằng ETag/optimistic concurrency hoặc semantics phù hợp.

### Điểm cộng
- Xem SDK diagnostics, normalized RU consumption, partition-key ranges, request charge, latency theo operation.
- So sánh point read bằng id + partition key với query cross-partition.
- Đề xuất adaptive throttling và load shedding có ưu tiên thao tác checkout.

### Senior+
- Lập migration strategy dual-read/dual-write có idempotency, reconciliation, canary và rollback.
- Phân biệt transactional batch trong cùng logical partition với giao dịch xuyên partition; không hứa atomicity toàn cục.

## Hướng giải quyết tham khảo

**Impact → stabilize:** xác định tỷ lệ add-to-cart thất bại, merchant/region bị ảnh hưởng, số cart updates không xác nhận; thông báo tình trạng cho nhóm vận hành. Hạn chế request không thiết yếu, đặt concurrency cap cho hot endpoints, tránh retry vô hạn; cân nhắc tăng throughput tạm thời nếu đo cho thấy giúp được partition nóng và nằm trong ngân sách. Không xóa hoặc replay writes khi chưa biết trạng thái commit.

**Evidence:** phân tách 429 theo operation, logical partition key, physical partition, request charge, retry count và client-side latency. Kiểm tra query plans và partition distribution. So sánh CPU/API threads, connection pool, downstream latency để loại trừ bottleneck khác. SDK diagnostics có thể chỉ ra request charge, timing và retry; cần đối chiếu telemetry dịch vụ, không suy diễn từ tổng RU.

**Hypotheses:** (a) merchantId gom lượng ghi flash sale vào một logical partition; (b) truy vấn cross-partition tăng RU; (c) retry tầng API cộng SDK khuếch đại tải; (d) item growth hoặc indexing policy làm RU/write tăng; (e) client timeout thấp hơn tổng retry budget. Xác minh từng giả thuyết bằng metric theo key, operation và deployment timeline.

**Fix:** nếu cart thuộc một customer, cân nhắc partition key gắn với customer/cart và point read; nhưng chỉ quyết định sau khi đánh giá access pattern, tenant isolation, hot customers và giới hạn partition. Dùng idempotency key cho write retries, optimistic concurrency bằng ETag và xử lý 412 theo conflict policy. Với tăng trưởng dữ liệu cần đổi partition key, xây container mới, backfill, đồng bộ delta, reconcile, chuyển reads/writes có kiểm soát; Cosmos DB không cho đổi partition key của container hiện hữu như một update metadata đơn giản. Tránh dual-write không có kế hoạch khôi phục khi một phía thất bại. Đảm bảo log không chứa cart PII.

**Verification:** fault injection 429, burst traffic, concurrent updates, client timeout sau server commit, cross-partition query benchmark, backfill consistency và rollback rehearsal. Alert theo 429 rate, retry amplification, RU per request, hot partition saturation, p99 và lost-update conflicts.

## Mẫu trả lời trong phỏng vấn

“Tôi ưu tiên bảo vệ tính đúng đắn của giỏ hàng rồi mới tối ưu latency. Tổng RU còn dư không loại trừ hot partition, nên tôi sẽ xem 429 và RU theo partition key, operation, request diagnostics và số retry thực tế. Tôi sẽ giảm retry amplification, giới hạn concurrency và giữ checkout trong latency budget. Có ít nhất ba khả năng: khóa partition gom traffic vào merchant lớn, truy vấn tốn RU hoặc retry chồng tầng. Nếu chứng minh partition key sai access pattern, tôi đề xuất container mới và migration có backfill, reconciliation, canary, rollback; không sửa khóa trực tiếp hoặc dual-write mù. Concurrent updates cần ETag hoặc cơ chế xung đột được định nghĩa. Tôi kiểm chứng bằng load test và telemetry trước khi rollout rộng.”

## Câu hỏi đào sâu

1. Nếu 429 tăng nhưng request cuối cùng vẫn thành công, bạn đánh giá SLO và cost thế nào?
2. Nếu giỏ hàng cần query theo merchant và customer, bạn chọn partition key và secondary read model ra sao?
3. Tại sao tăng tổng RU/s chưa chắc giải quyết hot logical partition?

## Lỗi trả lời thường gặp

- Cho rằng RU tổng chưa đầy thì Cosmos DB không thể throttling.
- Retry ngay lập tức ở cả SDK, API và frontend.
- Đề xuất đổi partition key trực tiếp không cần migration.
- Bỏ qua idempotency, ETag và kết quả write không chắc chắn sau timeout.
- Kết luận nguyên nhân khi chưa có partition-level evidence.

## Thang điểm 0–10

- 0–2: Impact, stabilization và communication.
- 0–2: Thu thập đúng RU/429/partition evidence, nhiều giả thuyết.
- 0–2: Phân tích partitioning, query cost và retries.
- 0–2: Correctness, idempotency, migration/rollback.
- 0–1: Test, alerts và trade-offs.
- 0–1: Trình bày có ưu tiên, phân biệt giả định và bằng chứng.

# Câu 3 — Hiện đại hóa cổng quản lý nhân sự .NET Framework mà không dừng nghiệp vụ

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** .NET Framework 4.5, IIS, ASP.NET Core, Vue.js, SQL Server, auth, CI/CD, incremental modernization.

## Bối cảnh

Cổng quản lý nhân sự chạy ASP.NET MVC trên .NET Framework 4.5, IIS/Windows Server, jQuery và SQL Server. Hệ thống có 70.000 nhân viên, các module chấm công, phê duyệt nghỉ phép, báo cáo và tích hợp payroll qua batch file. Product yêu cầu thêm Vue.js self-service trong sáu tháng; downtime cho phép rất ít. Một số thư viện bên thứ ba chưa hỗ trợ modern .NET; nhóm chỉ có 6 developers và 2 QA. Có đề xuất rewrite Microservices + Kubernetes; phương án khác giữ monolith và thêm API. Chưa rõ dependency inventory, identity model, database coupling hay release constraints.

## Câu hỏi chính

Bạn sẽ lựa chọn kiến trúc đích và lộ trình migration nào để đưa tính năng mới lên production an toàn, bảo đảm quyền truy cập và consistency của approval workflow, đồng thời kiểm soát chi phí vận hành?

## Câu hỏi làm rõ nên cân nhắc

1. Những module nào có tần suất thay đổi cao, phụ thuộc thư viện cũ hoặc shared session?
2. SSO, authentication cookie, roles/claims và tenant boundaries hiện hoạt động ra sao?
3. SQL schema và stored procedures có bị nhiều module ghi trực tiếp không?
4. SLA, rollback window, release pipeline và test coverage hiện tại?
5. Cần đồng bộ UI/URL, SEO nội bộ, audit trail, file batch payroll và accessibility mức nào?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt mục tiêu business với việc thay toàn bộ technology stack.

### Gợi ý 2
Tìm seam ở routing, API và ownership dữ liệu trước khi cắt module.

### Gợi ý 3
Xây compatibility contract, auth boundary, strangler migration và rollback theo từng vertical slice.

## Cấu trúc trả lời đề xuất

1. Inventory dependencies, critical paths và business constraints.
2. So sánh ba lựa chọn: giữ legacy + API, incremental strangler, rewrite.
3. Chọn boundaries, ownership, auth và data migration.
4. Thiết kế API, frontend integration và release topology.
5. Lập phases, quality gates, rollback, monitoring.
6. Nêu điều kiện khiến quyết định thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không chọn Microservices/Kubernetes chỉ vì hiện đại.
- Có chiến lược incremental migration và dependency compatibility.
- Xác định ownership của approval transactions, audit và payroll export.
- Không chia sẻ cookie/session hoặc DB writes xuyên ứng dụng tùy tiện.
- Có feature flags, contract tests, canary và rollback.

### Điểm cộng
- Bảo đảm authorization ở API, không chỉ ẩn nút Vue.
- Thiết kế BFF/reverse proxy nếu cần cùng origin và routing nhất quán.
- Chọn transactional outbox khi cần phát event đáng tin cậy sau commit; không áp dụng khi không có nhu cầu.
- Đánh giá khả năng nâng cấp legacy lên phiên bản .NET Framework được hỗ trợ trong giai đoạn chuyển tiếp.

### Senior+
- Định nghĩa measurable exit criteria theo module, ownership map và migration risk register.
- Tách database bằng schema/contracts trước khi tách deployment nếu coupling lớn; tránh distributed transaction không cần thiết.

## Hướng giải quyết tham khảo

**Lựa chọn:** với 6 developers và dependency legacy, mặc định ưu tiên strangler theo vertical slices, giữ IIS app cho nghiệp vụ ổn định, thêm ASP.NET Core API/module cho self-service mới, Vue.js làm frontend. Có thể deploy API lên IIS hoặc Azure App Service tùy network, identity và vận hành; không cần Kubernetes. Nếu coupling quá cao, bắt đầu bằng modularization trong monolith và anti-corruption layer thay vì phân tách vật lý sớm.

**Phases:** (0) inventory .NET assemblies, authentication/session, DB schema, stored procedures, batch integrations, telemetry, security vulnerabilities và test coverage. (1) Thiết lập build reproducibility, staging gần production, smoke/E2E Playwright cho approval, backup/restore rehearsal và baseline latency. (2) Tạo route boundary/reverse proxy, SSO chuẩn hóa; API xác thực token/cookie theo trust boundary, CSRF protection cho cookie-based mutations, policy authorization và audit. (3) Di chuyển một read-only vertical slice sang Vue + API, dùng contract tests và feature flag. (4) Di chuyển workflow ghi với single writer ownership, DB constraints và optimistic concurrency; các side effects như payroll file phải idempotent và có reconciliation. (5) Tắt dần legacy routes sau khi đo error rate và business parity.

**Data ownership:** trong giai đoạn đầu có thể dùng cùng SQL Server nhưng module mới không được viết trực tiếp vào bảng thuộc module legacy nếu chưa có contract. Dùng API facade hoặc stored procedure có versioning; ưu tiên transaction local cho approval + audit, Outbox chỉ khi cần integration asynchronous. Tránh hai hệ thống cùng ghi một workflow không có cơ chế conflict.

**Deployment:** versioned APIs, expand/contract schema migrations, compatibility window cho UI cũ và mới, canary theo nhóm nhân viên, feature flags và rollback ứng dụng. Rollback schema không phải lúc nào an toàn sau khi có dữ liệu mới; thiết kế forward-compatible migrations. Nếu dùng cùng origin, reverse proxy cần xử lý forwarded headers và cookie settings an toàn. Bảo vệ secrets qua managed identity/secret store phù hợp.

**Trade-offs:** strangler kéo dài thời gian chạy hai stack và tăng observability/routing complexity, nhưng giảm blast radius; rewrite có thể đơn giản hơn về code cuối cùng nhưng rủi ro tiến độ, parity và cutover cao; modular monolith giảm chi phí vận hành nhưng yêu cầu kỷ luật boundaries. Nếu thư viện legacy không thể cô lập hoặc yêu cầu bảo mật không thể đáp ứng, có thể ưu tiên thay module đó sớm hơn.

**Testing & observability:** golden-path approvals, concurrency approvals, payroll reconciliation, auth negative tests, E2E Vue/legacy navigation, load test, release smoke và rollback drill. Dashboard correlation ID xuyên proxy/API, approval success/error, audit completeness, batch reconciliation, p95 và deployment regressions.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- GC live heap và process RSS là hai phép đo khác nhau; peak allocation cần được quản trị theo concurrency.
- Cosmos DB throttling phải phân tích ở mức partition, operation và retry budget, không chỉ tổng RU.
- Modernization thành công dựa vào dependency boundaries, data ownership, backward compatibility và release safety hơn là số lượng services.

## Mẫu tư duy cần nhớ

1. **Measure before optimize:** xác định metric và bằng chứng có thể bác bỏ giả thuyết.
2. **Stabilize before deep investigation:** bảo vệ correctness và SLO trước khi thay kiến trúc.
3. **Design retries with idempotency:** timeout không chứng minh write chưa commit.
4. **Migrate by reversible slices:** rollout/rollback cần được thiết kế trước cutover.
5. **Pay for complexity only when justified:** kiến trúc đơn giản có thể là lựa chọn Senior+.
