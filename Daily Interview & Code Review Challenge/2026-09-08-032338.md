# Câu 1 — Vì sao inject `DbContext` vào singleton có thể chạy “được” nhưng vẫn sai về lifetime và concurrency?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core Dependency Injection, service lifetime, EF Core, `DbContext`, scope, disposal, concurrency, background services, runtime behavior

## Bối cảnh

Một ASP.NET Core .NET 8 application có các đăng ký DI gần như sau:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<OrderCacheWarmup>();
builder.Services.AddHostedService<CacheWarmupWorker>();
```

`OrderCacheWarmup` được viết như sau:

```csharp
public sealed class OrderCacheWarmup
{
    private readonly AppDbContext _dbContext;

    public OrderCacheWarmup(AppDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public async Task<IReadOnlyList<OrderSummary>> LoadAsync(
        CancellationToken cancellationToken)
    {
        return await _dbContext.Orders
            .AsNoTracking()
            .OrderByDescending(x => x.CreatedAt)
            .Take(100)
            .Select(x => new OrderSummary(x.Id, x.Status, x.CreatedAt))
            .ToListAsync(cancellationToken);
    }
}
```

Developer local không thấy lỗi rõ ràng vì application khởi động được trong một số environment/configuration. Sau khi deploy production và worker bắt đầu chạy song song với web traffic, team thấy các symptom khó tái hiện:

- thỉnh thoảng có exception liên quan concurrent operation trên `DbContext`;
- một số query dùng data/tracking state khó giải thích;
- worker sống suốt process lifetime;
- application scale lên nhiều instances;
- team đề xuất đổi `AddDbContext` sang `AddSingleton<AppDbContext>()` để “lifetime khớp nhau”;
- một developer khác đề xuất inject root `IServiceProvider` rồi gọi `GetRequiredService<AppDbContext>()` mỗi khi cần.

Chưa biết chắc:

- worker có chạy các operation song song không;
- scope validation có bật ở tất cả environments không;
- có operation nào giữ entity tracked lâu không;
- singleton có được gọi từ nhiều thread đồng thời không;
- warmup thực sự cần một DbContext dài hạn hay chỉ cần một unit-of-work ngắn cho mỗi lần chạy.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra ở DI container khi một singleton phụ thuộc vào scoped service như `AppDbContext`, vì sao lifetime mismatch này nguy hiểm dù code có thể compile hoặc thậm chí chạy trong một số trường hợp, và bạn sẽ thiết kế lại worker/singleton như thế nào để mỗi operation có scope, disposal và concurrency boundary đúng.

## Câu hỏi làm rõ nên cân nhắc

1. `OrderCacheWarmup.LoadAsync` có thể bị gọi đồng thời từ nhiều nơi hoặc nhiều vòng worker không?
2. Có lý do business nào yêu cầu giữ cùng một `DbContext` qua nhiều iteration không?
3. Worker cần transaction xuyên nhiều lần chạy hay mỗi execution độc lập?
4. App hiện có `ValidateScopes`/scope validation trong production không?
5. Query chỉ read-only hay sau này warmup có thể ghi/cache metadata vào database?

## Gợi ý tư duy

### Gợi ý 1

Hãy phân biệt lifetime của singleton, lifetime của request scope và lifetime phù hợp của một EF Core unit-of-work.

### Gợi ý 2

`DbContext` không nên trở thành shared mutable state giữa các operation concurrent chỉ vì DI container có thể trả cùng một instance.

### Gợi ý 3

Trong singleton/hosted service, hãy nghĩ tới explicit scope cho từng logical operation thay vì kéo scoped dependency lên singleton lifetime.

## Cấu trúc trả lời đề xuất

1. Xác định lifetime graph hiện tại.
2. Giải thích captive dependency là gì.
3. Giải thích `AddDbContext` mặc định và unit-of-work lifetime.
4. Phân tích disposal/tracking/concurrency risk.
5. Phản biện `AddSingleton<AppDbContext>()`.
6. Phản biện resolve scoped service từ root provider.
7. Đề xuất `IServiceScopeFactory` hoặc factory phù hợp.
8. Xác định boundary cho mỗi worker iteration.
9. Thêm cancellation, error handling và observability.
10. Kiểm thử concurrency/lifecycle.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết `AddDbContext` đăng ký `DbContext` với scoped lifetime theo mặc định.
- Nhận ra singleton giữ scoped dependency là captive dependency/lifetime mismatch.
- Không đổi `DbContext` thành singleton.
- Không dùng một `DbContext` đồng thời cho nhiều operations.
- Tạo explicit scope cho từng unit-of-work từ singleton/hosted service khi cần scoped dependencies.
- Dispose scope sau mỗi operation.
- Propagate `CancellationToken`.
- Không giữ tracked entities/context qua nhiều worker iterations nếu không có lý do rất đặc biệt.

### Điểm cộng

- Dùng `IDbContextFactory<TContext>` khi pattern tạo context theo operation phù hợp hơn explicit scope.
- Phân biệt `IServiceScopeFactory.CreateScope()` với resolve từ root provider.
- Giải thích vì sao scope validation có thể phát hiện lỗi sớm ở development nhưng không nên dựa vào việc “production chưa nổ”.
- Thiết kế worker không overlap iteration nếu workload không thread-safe.

### Senior+

- Tách rõ application scope, DI scope và database transaction boundary.
- Nêu rằng một scoped service không nhất thiết bằng “one request only”; background flow có thể tự tạo scope.
- Đề xuất metrics cho worker duration/failure/overlap và query duration.
- Nếu warm cache chạy nhiều App Service instances, nhận ra DI scope không giải quyết duplicate execution giữa instances; cần idempotency/coordination riêng nếu business yêu cầu single execution.

## Hướng giải quyết tham khảo

Vấn đề cốt lõi không phải compiler hay EF Core query syntax mà là lifetime graph.

`AddDbContext<AppDbContext>()` đăng ký `AppDbContext` là scoped theo mặc định. Trong HTTP request, ASP.NET Core tạo request scope và dispose scoped services khi request kết thúc. Singleton thì tồn tại gần như suốt application process lifetime.

Nếu singleton giữ một scoped `AppDbContext`, scoped dependency bị kéo dài theo lifetime của singleton. Điều này phá assumption của `DbContext`: một context thường đại diện một unit-of-work tương đối ngắn, giữ change tracker/state và không được thiết kế cho concurrent operations từ nhiều threads.

Một context sống quá lâu có thể gây:

- tracking state tích tụ nếu query/update có tracking;
- stale entity state hoặc confusing state transitions;
- database connection/resource lifecycle khó kiểm soát;
- multiple operations cùng dùng một instance;
- `InvalidOperationException` khi concurrent EF operations xảy ra;
- memory growth nếu tracked graph lớn dần.

Đổi `AppDbContext` sang singleton là sai hướng. Nó làm lifetime mismatch “biến mất” về mặt DI graph nhưng làm vấn đề concurrency/state nghiêm trọng hơn.

Resolve scoped dependency trực tiếp từ root `IServiceProvider` cũng không phải cách đúng. Root provider không tạo logical scope mới cho operation. Cách phù hợp là tạo scope rõ ràng:

```csharp
public sealed class CacheWarmupWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<CacheWarmupWorker> _logger;

    public CacheWarmupWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<CacheWarmupWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await using var scope = _scopeFactory.CreateAsyncScope();
                var warmup = scope.ServiceProvider
                    .GetRequiredService<IOrderCacheWarmup>();

                await warmup.LoadAsync(stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Order cache warmup failed");
            }

            await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
        }
    }
}
```

Và registration:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

builder.Services.AddScoped<IOrderCacheWarmup, OrderCacheWarmup>();
builder.Services.AddHostedService<CacheWarmupWorker>();
```

Ở đây mỗi iteration có scope riêng, nên `DbContext` được tạo/dispose theo logical operation. Nếu operation gồm nhiều scoped services, chúng cùng chia sẻ một scope phù hợp.

Một alternative khác là `IDbContextFactory<AppDbContext>` nếu class cần tự tạo context cho mỗi operation và không cần resolve cả graph scoped phức tạp. Ví dụ:

```csharp
public sealed class OrderCacheWarmup
{
    private readonly IDbContextFactory<AppDbContext> _contextFactory;

    public OrderCacheWarmup(IDbContextFactory<AppDbContext> contextFactory)
    {
        _contextFactory = contextFactory;
    }

    public async Task<IReadOnlyList<OrderSummary>> LoadAsync(
        CancellationToken cancellationToken)
    {
        await using var db = await _contextFactory
            .CreateDbContextAsync(cancellationToken);

        return await db.Orders
            .AsNoTracking()
            .OrderByDescending(x => x.CreatedAt)
            .Take(100)
            .Select(x => new OrderSummary(x.Id, x.Status, x.CreatedAt))
            .ToListAsync(cancellationToken);
    }
}
```

Lựa chọn giữa scope factory và DbContext factory phụ thuộc vào dependency graph. Nếu operation cần repository/service scoped khác cùng transaction/context boundary, explicit scope thường tự nhiên hơn. Nếu chỉ cần DbContext độc lập theo operation, factory có thể đơn giản hơn.

Concurrency cũng cần explicit. Nếu worker loop có thể overlap vì timer/event hoặc gọi `Task.WhenAll`, mỗi concurrent operation phải có context riêng. Nếu business không cần overlap, tốt hơn chặn overlap thay vì vô tình chạy hai lần.

Quan trọng: scope chỉ giải quyết lifetime trong một process. Nếu App Service scale ra 5 instances thì có 5 hosted services. Nếu warmup phải chỉ chạy một lần toàn hệ thống, cần distributed coordination, queue-based competing consumer, scheduler hoặc idempotent design; DI scope không giải quyết distributed duplication.

Testing nên gồm:

- scope validation trong test/development startup;
- multiple concurrent worker operations;
- cancellation khi host shutdown;
- exception giữa query;
- context disposal verification gián tiếp qua integration test;
- scale-out scenario nếu operation có side effect.

Production telemetry:

- worker iteration duration;
- overlap/concurrency count;
- EF Core query dependency duration;
- worker failures/retries;
- context-related concurrency exceptions;
- instance identifier để phát hiện duplicate execution giữa replicas.

Tài liệu Microsoft Learn về DI service lifetimes hiện xác nhận `AddDbContext` mặc định là scoped và scoped service phải được dùng trong scope; singleton cần tạo explicit scope khi sử dụng scoped dependency.

## Mẫu trả lời trong phỏng vấn

“Ở đây `DbContext` là scoped còn `OrderCacheWarmup` là singleton, nên singleton đang capture một dependency có lifetime ngắn hơn. Nếu context bị giữ suốt process lifetime, tracking state và resource lifetime bị kéo dài, và nguy hiểm nhất là nhiều operation có thể dùng cùng một `DbContext` concurrent dù `DbContext` không thread-safe.

Em không sửa bằng cách biến `DbContext` thành singleton. Với hosted service, em tạo scope cho từng logical iteration bằng `IServiceScopeFactory`, resolve scoped service bên trong rồi dispose scope sau khi xử lý. Nếu class chỉ cần context độc lập theo operation thì `IDbContextFactory` cũng là option phù hợp.

Em cũng tách vấn đề process-local với scale-out: tạo scope đúng không ngăn 5 App Service instances cùng chạy warmup. Nếu operation chỉ được chạy một lần toàn hệ thống thì phải thêm idempotency hoặc distributed coordination riêng. Em sẽ test concurrent execution, cancellation và theo dõi iteration duration/error/overlap.”

## Câu hỏi đào sâu

1. Nếu một background operation cần transaction qua 3 scoped services, bạn chọn `IServiceScopeFactory` hay `IDbContextFactory` và vì sao?
2. Nếu đổi worker sang `Task.WhenAll` để xử lý 20 tenants song song, bạn quản lý scope/DbContext như thế nào?
3. Nếu team nói “production chưa thấy lỗi nên lifetime này có thể chấp nhận”, bạn sẽ chứng minh rủi ro bằng test hoặc runtime evidence nào?

## Lỗi trả lời thường gặp

- Đổi `DbContext` thành singleton để lifetime “match”.
- Inject root `IServiceProvider` rồi resolve scoped service không tạo scope.
- Cho rằng scoped service chỉ tồn tại được trong HTTP request.
- Dùng cùng một `DbContext` cho nhiều task concurrent.
- Quên rằng scale-out tạo nhiều worker instances độc lập.

## Thang điểm 0–10

- **0–2:** Chỉ nói “DI lifetime sai” nhưng không giải thích hậu quả.
- **3–4:** Biết scoped/singleton nhưng đề xuất fix không an toàn.
- **5–6:** Tạo scope đúng và hiểu `DbContext` unit-of-work/concurrency.
- **7–8:** So sánh scope factory/DbContext factory, có cancellation/testing/observability.
- **9–10:** Phân biệt process scope với distributed execution, thiết kế concurrency và transaction boundaries rõ ràng.

# Câu 2 — Cosmos DB liên tục trả 429 dù tổng RU/s vẫn còn dư

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, RU/s, hot partition, throttling, data modeling, query patterns, observability, incident response

## Bối cảnh

Một event-management platform lưu attendee activity trong Azure Cosmos DB for NoSQL.

Container hiện dùng partition key:

```text
/eventId
```

Mỗi document gần giống:

```json
{
  "id": "activity-id",
  "eventId": "EVENT-2026-001",
  "attendeeId": "USER-123",
  "type": "check-in",
  "createdAt": "2026-09-08T03:00:00Z",
  "payload": {}
}
```

Trong phần lớn thời gian hệ thống chạy ổn. Tuy nhiên khi có một sự kiện lớn với hàng trăm nghìn attendees, production xuất hiện:

- request latency tăng;
- nhiều operation nhận HTTP 429;
- retry latency tăng;
- tổng RU/s dashboard chưa luôn chạm max toàn container;
- các event nhỏ gần như không bị ảnh hưởng;
- scale-up RU/s toàn container giúp một phần nhưng chi phí tăng mạnh;
- developer đề xuất tăng retry count thật cao;
- một developer khác đề xuất đổi partition key ngay sang `/attendeeId`;
- query phổ biến gồm:
  - ghi activity theo event;
  - lấy activity của một attendee trong event;
  - thống kê gần-real-time theo event;
  - đọc recent activities của event.

Chưa biết chắc:

- RU consumption phân bổ theo physical partition thế nào;
- một event lớn chiếm bao nhiêu % traffic;
- read/query có cross-partition không;
- consistency level nào đang dùng;
- document size/index policy hiện tại;
- write burst pattern theo check-in gate;
- có thể thay data model/API contract mà không migration big-bang hay không.

## Câu hỏi chính

Bạn sẽ xử lý incident 429 này theo thứ tự nào, chứng minh có phải hot partition hay không, và nếu partition key `/eventId` thực sự tạo hotspot thì bạn sẽ redesign partition strategy/data access như thế nào mà không chỉ tăng RU/s hoặc retry vô hạn?

## Câu hỏi làm rõ nên cân nhắc

1. `Normalized RU Consumption` theo partition key range cho thấy distribution ra sao?
2. 429 tập trung vào writes, point reads hay queries nào?
3. Một event lớn có throughput profile bao nhiêu so với các event còn lại?
4. Query nào bắt buộc cần lấy toàn bộ activity theo `eventId`, và latency/SLA của query đó là gì?
5. Có thể introduce synthetic/sharded partition key trong phiên bản mới mà vẫn giữ old data đọc được không?

## Gợi ý tư duy

### Gợi ý 1

Tổng RU/s còn dư không chứng minh mọi physical partition còn capacity.

### Gợi ý 2

Partition key là quyết định data distribution và access pattern; đổi key phải đánh giá cả write distribution lẫn query fan-out.

### Gợi ý 3

Retry có thể che transient throttling nhưng không sửa structural hotspot nếu cùng logical key nhận phần lớn traffic.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact.
2. Thu thập 429 rate, latency, retry count và RU metrics.
3. Kiểm tra normalized RU theo partition/key range.
4. Phân loại hot logical key vs uneven query load.
5. Đánh giá partition-key/data-model hiện tại.
6. Stabilize incident ngắn hạn.
7. Thiết kế partition strategy mới theo access patterns.
8. Giải quyết query fan-out/aggregation/read model.
9. Lập migration/backward-compatibility plan.
10. Load test và đặt SLO/alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận chỉ từ tổng RU/s.
- Dùng normalized RU metrics để kiểm tra hot partition/key range.
- Hiểu một logical partition key nóng có thể bị throttled dù capacity ở partition khác còn dư.
- Retry phải bounded và tôn trọng retry-after/SDK behavior; không retry vô hạn.
- Không đổi `/eventId` sang `/attendeeId` mà chưa đánh giá access patterns.
- Partition-key redesign phải cân bằng distribution và query locality.
- Có migration strategy thay vì destructive switch ngay production.
- Đo lại 429, latency, RU/request và fan-out sau thay đổi.

### Điểm cộng

- Cân nhắc synthetic key như `eventId + bucket` khi workload chủ yếu bị hot theo event.
- Phân biệt write model với read/aggregation model.
- Có asynchronous aggregation/read model cho dashboard thay vì cross-partition scan liên tục.
- Kiểm tra indexing policy/document size nếu RU/request cao bất thường.
- Capacity-limit writes theo gate/burst khi business cho phép.

### Senior+

- Thiết kế bucket/shard strategy dựa trên cardinality và throughput thực tế, không random number tùy ý.
- Có deterministic mapping để point-read vẫn biết partition key.
- Thiết kế fan-out query có bounded cost hoặc secondary projection.
- Lập phased migration dual-read/dual-write/backfill với rollback.
- Xử lý event “siêu lớn” như một workload class riêng thay vì tối ưu toàn container cho worst case nếu economics không hợp lý.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng incident evidence. HTTP 429 trong Cosmos DB không tự động có nghĩa toàn container thiếu RU/s. Tôi cần xem:

- 429 rate;
- request latency;
- retry count;
- RU charge theo operation;
- normalized RU consumption theo partition key range;
- top logical partition keys nếu telemetry có thể suy ra an toàn;
- query type và request volume.

Microsoft Learn hiện mô tả một hot partition có thể xảy ra khi một hoặc vài logical partition keys tiêu thụ phần lớn RU/s của physical partition tương ứng, trong khi RU/s ở physical partitions khác vẫn chưa dùng hết. `Normalized RU Consumption` là metric quan trọng để xác minh pattern này.

Nếu một event lớn có `eventId = EVENT-2026-001` và mọi activity đều dùng cùng partition key đó, toàn bộ write/read cho event này tập trung vào cùng logical partition. Dù các event nhỏ được phân tán tốt, event lớn vẫn có thể tạo hotspot.

Ngắn hạn tôi sẽ:

1. giảm amplification từ retry nếu hiện đang retry quá nhiều;
2. kiểm tra SDK retry policy và request diagnostics;
3. scale throughput tạm thời nếu business impact cần mitigation nhanh;
4. giảm các expensive aggregation queries trong peak nếu có thể;
5. giới hạn non-critical polling/dashboard refresh;
6. ưu tiên correctness và ingestion trước report không critical.

Nhưng scale RU/s không phải long-term fix nếu một single logical partition key vẫn là bottleneck structural.

Partition redesign phải bắt đầu từ access patterns. Chỉ đổi sang `/attendeeId` có thể phân tán writes tốt hơn, nhưng query “recent activity của event” hoặc aggregate theo event có thể biến thành cross-partition query đắt và khó kiểm soát.

Một option là synthetic partition key theo event + bucket, ví dụ conceptual:

```text
partitionKey = eventId + ":" + bucket
```

`bucket` có thể dựa trên hash của attendee hoặc một deterministic shard function. Ví dụ:

```text
EVENT-2026-001:07
```

Điều này phân tán một event lớn qua nhiều logical partitions. Nhưng đổi lại:

- query toàn event cần fan-out qua buckets;
- point read cần biết bucket;
- transaction scope bị giới hạn trong một logical partition;
- bucket count cần capacity reasoning;
- distribution function phải ổn định.

Nếu access “attendee trong event” là phổ biến, client/server có thể tính bucket từ `attendeeId` deterministic để point query tới đúng partition. Ví dụ hash(`attendeeId`) mod N. Nhưng N không nên thay đổi tùy tiện vì mapping cũ sẽ hỏng; có thể cần versioned partition scheme.

Với aggregate/report theo event, tôi không muốn mỗi dashboard request scan tất cả raw activities liên tục. Tôi cân nhắc projection:

- raw activity container được partition để ingest scale tốt;
- asynchronous processor cập nhật per-event counters/time-bucket summaries;
- dashboard đọc summary documents tối ưu cho read pattern.

Đây là denormalization có chủ đích. Nó thêm eventual consistency và processing complexity, nên cần xác nhận dashboard có chấp nhận lag ngắn hay không.

Migration không nên big-bang. Một plan khả thi:

1. tạo new container với partition strategy mới;
2. version data-access abstraction;
3. dual-write hoặc outbox/change-feed-based replication trong transition nếu phù hợp;
4. backfill historical data;
5. validate counts/hashes/sample queries;
6. switch reads theo feature flag/event cohort;
7. monitor 429/RU/latency;
8. rollback read path nếu regression;
9. stop old writes sau khi ổn định;
10. decommission old container theo retention policy.

Nếu dual-write trực tiếp từ request path, phải xử lý partial failure; dùng event/outbox/change feed có thể giảm coupling nhưng thêm lag. Cần chọn theo consistency requirement.

Tôi cũng kiểm tra:

- document size vì RU write/read tăng theo payload/indexing work;
- indexing policy có index mọi field không cần thiết hay không;
- query có dùng partition key filter không;
- aggregation có thể precompute không;
- hot key có thật là `/eventId` hay query pattern khác đang tạo hotspot;
- autoscale/manual throughput economics.

Testing cần production-like skew, không chỉ uniform synthetic traffic. Nếu 90% requests dồn vào một event lớn, load test phải mô phỏng đúng skew đó.

Metrics sau redesign:

- 429 %;
- normalized RU distribution;
- RU/request;
- p50/p95/p99;
- ingest throughput;
- cross-partition query count/cost;
- aggregation freshness lag;
- cost per million activities hoặc business unit phù hợp.

Tài liệu Microsoft Learn tham khảo:

- `https://learn.microsoft.com/en-us/azure/cosmos-db/monitor-normalized-request-units`
- `https://learn.microsoft.com/en-us/azure/cosmos-db/troubleshoot-request-rate-too-large`

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhìn total RU rồi kết luận Cosmos còn dư capacity. Em kiểm tra 429 theo operation và `Normalized RU Consumption` theo partition key range để xem một partition có chạm 100% trong khi partition khác thấp không. Với `/eventId`, một event cực lớn có thể trở thành một hot logical key dù toàn container còn RU.

Ngắn hạn em giảm retry amplification, kiểm tra SDK diagnostics và có thể tăng throughput tạm để ổn định. Long-term em thiết kế partition key theo access pattern. Nếu cần phân tán một event, em cân nhắc synthetic key `eventId + bucket` với deterministic bucket từ attendee. Trade-off là query toàn event phải fan-out, nên dashboard aggregate có thể cần read model/projection riêng.

Em không đổi thẳng sang `/attendeeId` vì có thể làm query theo event rất đắt. Migration sẽ dùng new container, backfill + dual-read/dual-write hoặc event replication theo requirement, rồi rollout từng bước và đo 429, RU/request, p95/p99 và aggregation lag.”

## Câu hỏi đào sâu

1. Nếu một event có 10 triệu attendees còn 99% event khác rất nhỏ, bạn chọn fixed bucket count cho mọi event hay adaptive strategy? Trade-off là gì?
2. Nếu Product yêu cầu dashboard count phải strong-consistent ngay sau mỗi check-in, projection async còn phù hợp không?
3. Nếu sau khi sharding theo `eventId + bucket`, write 429 giảm nhưng query RU tăng gấp nhiều lần, bạn tối ưu bước tiếp theo thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng RU/s mà không xác minh partition distribution.
- Retry 429 vô hạn.
- Đổi partition key chỉ dựa trên write path mà bỏ qua read/query patterns.
- Chọn bucket count tùy ý không benchmark.
- Migration container mới mà không có compatibility/reconciliation plan.

## Thang điểm 0–10

- **0–2:** Chỉ nói “tăng RU” hoặc “thêm retry”.
- **3–4:** Biết hot partition nhưng chưa liên hệ data model/access pattern.
- **5–6:** Có metric, partition redesign và bounded retry hợp lý.
- **7–8:** Có sharding/read-model/migration strategy và load test với skew.
- **9–10:** Cân bằng throughput, query locality, consistency, migration risk và cost bằng evidence.

# Câu 3 — React/Vue SPA gọi ASP.NET Core API: lưu token ở đâu và có nên dùng BFF?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** React.js, Vue.js, ASP.NET Core, authentication, authorization, OAuth/OIDC concepts, Microsoft Entra ID / Azure AD B2C concepts, XSS, CSRF, CORS, BFF, API architecture, operational trade-offs

## Bối cảnh

Một enterprise portal đang được modernization từ ASP.NET MVC + jQuery sang frontend hiện đại.

Team đang cân nhắc React.js hoặc Vue.js cho UI và ASP.NET Core .NET 8 cho backend APIs.

Requirements hiện có:

- người dùng đăng nhập qua enterprise identity provider;
- một số deployment dùng Microsoft Entra ID concepts, một số customer-facing scenario đang đánh giá Azure AD B2C/identity solution phù hợp;
- UI gọi nhiều backend endpoints;
- có role/permission theo user;
- application chứa dữ liệu nội bộ nhạy cảm;
- cần support multiple tabs và session expiration hợp lý;
- frontend được host tách origin trong một số environment;
- team muốn tránh refresh token hoặc long-lived credential bị lộ qua JavaScript;
- một architect đề xuất SPA nhận access token và lưu `localStorage` vì “đơn giản”;
- một architect khác đề xuất BFF để browser chỉ giữ secure cookie;
- team security lo XSS, còn backend team lo CSRF/CORS và thêm operational hop nếu dùng BFF.

Chưa biết chắc:

- identity provider/product version cụ thể và flow hỗ trợ hiện tại;
- frontend/backend có thể cùng site/domain hay bắt buộc cross-site;
- APIs chỉ phục vụ browser portal hay còn mobile/third-party clients;
- user session duration requirement;
- có downstream APIs cần delegated user token hay không;
- compliance có yêu cầu session revocation/audit đặc biệt không.

## Câu hỏi chính

Hãy thiết kế authentication/session architecture cho React/Vue + ASP.NET Core trong bối cảnh này. So sánh SPA trực tiếp giữ access token với BFF/cookie-based session, giải thích XSS/CSRF/CORS trade-offs, authorization boundary ở đâu, và nêu điều kiện khiến bạn chọn hoặc không chọn BFF.

## Câu hỏi làm rõ nên cân nhắc

1. Frontend và BFF/API có thể được phục vụ cùng site không?
2. Browser app có cần gọi trực tiếp third-party APIs hay chỉ backend của mình?
3. Có mobile/native client dùng cùng API không?
4. Backend có cần delegated token để gọi downstream service thay mặt user không?
5. Security/compliance yêu cầu logout/revocation/session inactivity như thế nào?

## Gợi ý tư duy

### Gợi ý 1

“Token lưu ở đâu” chỉ là một phần; hãy xác định trust boundary giữa browser JavaScript, backend session và APIs.

### Gợi ý 2

Cookie giúp tránh JavaScript đọc token nếu dùng `HttpOnly`, nhưng cookie tự động được browser gửi nên CSRF trở thành concern cần thiết kế.

### Gợi ý 3

BFF giảm token exposure trong browser nhưng thêm server state/traffic/complexity. Không phải mọi SPA đều bắt buộc dùng BFF.

## Cấu trúc trả lời đề xuất

1. Clarify client types, origins, identity provider và downstream needs.
2. Xác định threat model: XSS, token theft, CSRF, CORS mistakes.
3. Mô tả option SPA + token.
4. Mô tả option BFF + secure session cookie.
5. Xác định authorization boundary ở API.
6. Thiết kế session/token refresh/logout.
7. Thiết kế CSRF/CORS/cookie attributes.
8. Tách browser API khỏi mobile/public API nếu cần.
9. Operational considerations: scaling, cache/session store, observability.
10. Test security và failure scenarios.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tin frontend authorization làm security boundary.
- Backend/API phải enforce authorization dựa trên authenticated principal/claims/policies phù hợp.
- Nhận ra XSS có thể đánh cắp token accessible bởi JavaScript và cũng có thể thực hiện actions trong active session.
- `HttpOnly` cookie giảm khả năng JavaScript đọc session token nhưng không tự giải quyết CSRF.
- Cookie auth cần `Secure`, `HttpOnly`, `SameSite` strategy phù hợp và CSRF protection cho state-changing requests.
- CORS không phải authentication/authorization mechanism.
- Không mặc định `localStorage` là nơi “an toàn” cho long-lived credential.
- BFF là trade-off, không slogan.

### Điểm cộng

- Dùng Authorization Code + PKCE concepts cho public SPA khi direct OAuth/OIDC flow là requirement và provider hỗ trợ.
- Nếu dùng BFF, browser chỉ giữ opaque/session cookie; BFF giữ/đổi tokens server-side theo provider contract.
- Tách API phục vụ SPA/BFF khỏi API cho mobile/third-party nếu auth model khác nhau.
- Dùng policy-based authorization trong ASP.NET Core cho permission/claims logic phức tạp.
- Xử lý logout, session expiration và token refresh failure rõ ràng.

### Senior+

- Phân biệt token theft với session riding: `HttpOnly` giảm credential exfiltration nhưng XSS vẫn rất nghiêm trọng.
- Thiết kế anti-CSRF token/double-submit hoặc framework-supported antiforgery pattern theo architecture thực tế.
- Đánh giá same-site vs cross-site deployment ảnh hưởng cookie/SameSite/CORS.
- Có session-store/scaling strategy nếu BFF cần server-side state.
- Có threat model cho downstream delegated tokens và least privilege/scopes.

## Hướng giải quyết tham khảo

Tôi bắt đầu từ trust boundary. Browser JavaScript là môi trường phải giả định có thể bị ảnh hưởng bởi XSS nếu application hoặc dependency có lỗ hổng. Vì vậy tôi không muốn long-lived high-value credentials accessible trực tiếp từ JavaScript nếu có architecture đơn giản hơn để tránh.

Có hai broad options.

### Option A — SPA trực tiếp dùng OAuth/OIDC access token

SPA thực hiện flow phù hợp cho public client, thường theo Authorization Code + PKCE nếu identity provider hỗ trợ. Browser nhận access token và gọi API bằng `Authorization: Bearer`.

Ưu điểm:

- architecture ít server hop hơn;
- API có thể độc lập và phục vụ nhiều client;
- dễ scale stateless ở backend nếu token self-contained/validation strategy phù hợp.

Rủi ro/trade-off:

- token tồn tại trong browser context;
- nếu lưu persistent storage như `localStorage`, XSS có thể đọc/exfiltrate token;
- refresh token handling trong browser cần tuân thủ provider guidance;
- token lifecycle/logout/revocation có thể phức tạp;
- frontend phải xử lý token acquisition/renewal.

Nếu chọn direct SPA, tôi ưu tiên provider SDK/pattern chính thức, short-lived access token và tránh tự xây token storage/refresh protocol. Exact behavior phải dựa trên identity provider hiện tại, không dùng assumption từ provider khác.

### Option B — BFF + cookie-based browser session

Browser chỉ giao tiếp với BFF thuộc trust boundary của application. BFF thực hiện OIDC interaction, giữ token server-side hoặc dùng secure session abstraction. Browser nhận cookie như:

- `HttpOnly`;
- `Secure`;
- `SameSite` phù hợp deployment;
- expiration/sliding policy rõ.

Browser không cần đọc access token bằng JavaScript. BFF gọi internal/downstream APIs thay cho browser.

Ưu điểm:

- giảm token exposure trực tiếp trong JavaScript;
- centralized session/token handling;
- backend có thể quản lý downstream token exchange/refresh;
- đơn giản hóa frontend auth logic.

Trade-off:

- thêm hop và backend traffic;
- cần scale/session strategy;
- nếu server-side session state, cần distributed session store hoặc sticky/session design phù hợp;
- CSRF trở thành concern vì cookie được browser gửi tự động;
- BFF có thể trở thành bottleneck nếu proxy mọi payload lớn không cần thiết;
- APIs cho mobile/third-party vẫn cần auth model riêng.

### XSS

BFF không “giải quyết XSS”. `HttpOnly` giúp JavaScript không đọc cookie value, nên giảm token theft/exfiltration. Nhưng malicious script chạy trong origin vẫn có thể gọi application endpoints như user nếu không bị các control khác chặn. Vì vậy vẫn cần:

- output encoding đúng context;
- tránh unsafe HTML injection;
- sanitize untrusted rich content phù hợp;
- Content Security Policy nếu architecture hỗ trợ;
- dependency hygiene;
- React/Vue safe rendering defaults không bị bypass bằng raw HTML tùy tiện.

### CSRF

Cookie tự động attach vào requests nên state-changing endpoints phải chống CSRF. Strategy phụ thuộc same-site/cross-site deployment. Có thể dùng framework-supported antiforgery token, custom request header với token binding phù hợp, origin/same-site controls và cookie attributes. Tôi không coi `SameSite` một mình là universal solution nếu deployment/use cases phức tạp.

### CORS

CORS chỉ là browser policy về cross-origin requests. Nó không xác thực user và không thay authorization. Tôi cấu hình exact allowed origins/methods/headers/credentials theo environment; không dùng permissive `*` với credentialed browser flows.

### Authorization

Frontend có thể hide button để UX tốt, nhưng API vẫn phải authorize mọi sensitive action.

Trong ASP.NET Core, tôi dùng policy-based authorization cho permission/claims logic, ví dụ conceptual:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanApproveOrder", policy =>
        policy.RequireClaim("permission", "order.approve"));
});
```

Sau đó endpoint enforce policy server-side. Claims/scopes phải đến từ trust chain hợp lệ; không tin field do frontend tự gửi.

### Chọn BFF khi nào?

Tôi nghiêng BFF nếu:

- application browser chứa dữ liệu nhạy cảm;
- team muốn giảm token exposure trong JS;
- browser chủ yếu gọi backend của chính mình;
- có downstream delegated-token logic;
- frontend/backend có thể đặt cùng site hoặc cookie topology quản lý được;
- team chấp nhận vận hành BFF/session layer.

Tôi có thể không chọn BFF nếu:

- API chủ yếu là public/multi-client platform;
- SPA direct-to-API là core architecture;
- identity provider hỗ trợ SPA flow tốt và security team chấp nhận token model;
- extra proxy hop tạo cost lớn;
- browser cần direct access tới APIs không thể đi qua BFF hợp lý.

Có thể hybrid: BFF cho browser portal, còn mobile/public clients gọi API với bearer tokens. API authentication schemes/boundaries phải thiết kế rõ để không vô tình mở browser-only endpoints cho client không phù hợp.

### Session/logout

Tôi xác định:

- idle timeout;
- absolute lifetime;
- refresh behavior;
- logout local + identity-provider logout semantics;
- revoked/disabled user behavior;
- multi-tab consistency;
- downstream token expiry;
- failure khi identity provider unavailable.

Không tự hứa “logout revoke mọi JWT ngay” nếu provider/token model không bảo đảm điều đó; cần xác minh contract thực tế.

### Observability

Không log raw access token/cookie. Theo dõi:

- login success/failure;
- callback errors;
- token refresh/exchange failures;
- unauthorized/forbidden counts;
- session expiration;
- downstream 401/403;
- auth dependency latency;
- suspicious repeated failures;
- correlation ID cho auth flow nhưng tránh PII/secrets.

### Testing

- expired session/access token;
- revoked/disabled user theo provider capability;
- user thiếu permission;
- CSRF attempt;
- untrusted origin CORS request;
- XSS regression ở rich content;
- multi-tab logout;
- identity provider temporary outage;
- downstream token expiry;
- horizontal scale với BFF session state.

Final recommendation chỉ có thể chốt sau khi biết identity provider, origin topology và client types. Nếu đây là browser-only enterprise portal với sensitive data và backend-owned APIs, BFF thường là candidate mạnh vì giảm token exposure trong browser. Nhưng tôi vẫn phải thiết kế CSRF, XSS, session scaling và operational cost đầy đủ.

## Mẫu trả lời trong phỏng vấn

“Em bắt đầu từ trust boundary chứ không từ `localStorage` hay cookie. Frontend không bao giờ là authorization boundary; ASP.NET Core API vẫn enforce claims/policies server-side.

Nếu SPA giữ bearer token trực tiếp, architecture đơn giản hơn cho multi-client API nhưng token nằm trong browser context; persistent storage như `localStorage` làm XSS token-exfiltration risk lớn hơn. Nếu application là browser portal nhạy cảm và chủ yếu gọi backend của mình, em nghiêng BFF: browser giữ `HttpOnly`, `Secure` cookie còn access/refresh token ở server side.

BFF giảm việc JavaScript đọc token nhưng không loại bỏ XSS, và cookie flow phải chống CSRF. CORS cũng không phải auth. Em sẽ chọn `SameSite`, antiforgery strategy và allowed origins dựa trên same-site/cross-site topology thực tế.

Nếu mobile/third-party clients cũng dùng API, em không ép chúng qua BFF; có thể browser dùng BFF còn API vẫn hỗ trợ bearer auth riêng. Quyết định cuối phụ thuộc identity provider, downstream delegation, session requirements và operational cost.”

## Câu hỏi đào sâu

1. Nếu frontend và BFF buộc nằm ở hai site khác nhau do organizational hosting, cookie/SameSite/CSRF strategy của bạn thay đổi thế nào?
2. Nếu mobile app và SPA cùng dùng một API, bạn có dùng chung authentication scheme/endpoints hay tách boundary ra sao?
3. Một security reviewer nói “BFF dùng `HttpOnly` cookie nên XSS không còn nguy hiểm”; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Cho rằng lưu access token ở `localStorage` là mặc định an toàn.
- Cho rằng `HttpOnly` cookie loại bỏ XSS.
- Dùng CORS như authorization mechanism.
- Chỉ hide UI button thay vì authorize server-side.
- Chọn BFF nhưng không thiết kế CSRF/session scaling/logout.

## Thang điểm 0–10

- **0–2:** Chỉ nói “JWT + localStorage” hoặc “cookie an toàn hơn” mà không có threat model.
- **3–4:** Biết XSS/CSRF nhưng authorization/session boundaries còn mơ hồ.
- **5–6:** So sánh SPA token với BFF hợp lý, API authorization đúng và có security controls cơ bản.
- **7–8:** Có same-site/cross-site reasoning, multi-client architecture, session lifecycle và operational trade-offs.
- **9–10:** Thiết kế dựa trên threat model/provider constraints, nêu rõ giới hạn từng control và điều kiện làm recommendation thay đổi.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **DI lifetime phải khớp với logical unit-of-work:** singleton không nên capture scoped `DbContext`; background operations cần explicit scope hoặc context factory phù hợp.
- **`DbContext` không phải shared concurrent state:** mỗi concurrent unit-of-work cần context riêng và disposal boundary rõ.
- **Cosmos DB 429 có thể đến từ hot partition dù tổng RU/s còn dư:** phải nhìn normalized RU distribution và workload skew, không chỉ total throughput.
- **Partition key là quyết định access-pattern architecture:** cải thiện write distribution có thể làm query fan-out đắt hơn, nên cần read-model/migration trade-off.
- **Authentication architecture phải dựa trên trust boundary:** BFF giảm token exposure trong browser nhưng thêm CSRF/session/operational complexity.
- **Frontend không phải authorization boundary:** sensitive permissions phải enforce ở ASP.NET Core API/BFF/server-side policy.

## Mẫu tư duy cần nhớ

1. **Match lifetime to the unit-of-work, not to convenience.**
2. **Measure per-partition pressure before buying more total capacity.**
3. **Design partition keys from real read + write patterns together.**
4. **Threat-model browser credentials before choosing token storage.**
5. **Security controls move risk; they rarely eliminate all risk.**
