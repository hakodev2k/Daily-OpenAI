# Code Review Challenge 1 — Consumer Service Bus xác nhận đơn hàng nhưng phát sinh tác vụ trùng

**Chủ đề:** C#/.NET, Azure Service Bus, idempotency, transaction boundaries  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một hệ thống e-commerce nhận event OrderPaid từ Azure Service Bus queue. Mỗi event phải chuyển đơn hàng từ Pending sang Paid, lưu bản ghi audit và yêu cầu fulfillment đúng một lần về mặt hiệu ứng nghiệp vụ. ASP.NET Core Worker chạy 4 replicas; SQL Server lưu đơn hàng, một HTTP API bên thứ ba tạo fulfillment. Khi đối tác trả 503, số lượng fulfillment đôi lúc tăng gấp đôi; queue có message bị redeliver. Một số log báo xử lý thành công nhưng audit thiếu. Không rõ đối tác có hỗ trợ idempotency key hay không.

## Đoạn code cần review

~~~csharp
public sealed record OrderPaid(Guid OrderId, string PaymentId);

public sealed class OrderPaidWorker : BackgroundService
{
    private readonly ServiceBusClient _bus;
    private readonly IServiceScopeFactory _scopes;
    private readonly IHttpClientFactory _http;
    private readonly ILogger<OrderPaidWorker> _log;

    public OrderPaidWorker(ServiceBusClient bus, IServiceScopeFactory scopes,
        IHttpClientFactory http, ILogger<OrderPaidWorker> log)
        => (_bus, _scopes, _http, _log) = (bus, scopes, http, log);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await using var processor = _bus.CreateProcessor("order-paid",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = false,
                MaxConcurrentCalls = 16
            });

        processor.ProcessMessageAsync += async args =>
        {
            var evt = JsonSerializer.Deserialize<OrderPaid>(
                args.Message.Body.ToString())!;

            using var scope = _scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<OrdersDbContext>();
            var order = await db.Orders.FindAsync(evt.OrderId);
            if (order == null) return;

            order.Status = "Paid";
            await db.SaveChangesAsync();

            var client = _http.CreateClient("fulfillment");
            var response = await client.PostAsJsonAsync("/shipments",
                new { evt.OrderId, evt.PaymentId });
            if (!response.IsSuccessStatusCode)
                _log.LogWarning("Fulfillment failed {OrderId}", evt.OrderId);

            db.OrderAudits.Add(new OrderAudit
            {
                OrderId = evt.OrderId, Action = "Paid"
            });
            await db.SaveChangesAsync();

            await args.CompleteMessageAsync(args.Message);
        };

        processor.ProcessErrorAsync += args =>
        {
            _log.LogError(args.Exception, "Bus processor error");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
~~~

## Kết quả code review tham khảo

### [Critical] — Thiếu idempotency ở ranh giới nghiệp vụ

**Vấn đề:** Mọi lần redelivery đều có thể gọi /shipments.  
**Tại sao xảy ra:** CompleteMessageAsync không atomic với SQL/HTTP; 4 replicas có thể xử lý cùng business event qua các bản sao message hoặc retry.  
**Ảnh hưởng production:** Tạo nhiều shipment, phí vận chuyển và sai tồn kho.  
**Cách sửa:** Unique key cho PaymentId hoặc event identity theo domain; Inbox/Outbox có constraint; gửi idempotency key ổn định cho đối tác nếu được hỗ trợ. Nếu không, phải reconciliation trước khi retry side effect.

### [Critical] — Đánh dấu thành công dù HTTP thất bại

**Vấn đề:** HTTP non-2xx chỉ được log rồi message vẫn Complete.  
**Tại sao xảy ra:** Không có trạng thái pending fulfillment hay retry riêng.  
**Ảnh hưởng production:** Đơn Paid nhưng không có shipment; công việc có thể mất vĩnh viễn.  
**Cách sửa:** Ghi durable fulfillment intent vào Outbox trong cùng SQL transaction; worker khác gửi và retry có kiểm soát.

### [High] — Trạng thái, audit và intent không cùng transaction

**Vấn đề:** Hai SaveChangesAsync tách rời, không có durable intent.  
**Tại sao xảy ra:** Crash giữa các bước để lại partial state.  
**Ảnh hưởng production:** Audit thiếu; không biết có cần gọi lại đối tác.  
**Cách sửa:** Cùng một SQL transaction cho order state, audit và outbox record.

### [High] — Message không tồn tại đơn hàng không được settlement

**Vấn đề:** return khi order null, không Complete/DeadLetter.  
**Tại sao xảy ra:** Handler thoát mà không settle.  
**Ảnh hưởng production:** Redelivery liên tục đến khi vượt delivery count; DLQ không có thông tin phân loại.  
**Cách sửa:** Xác định eventual arrival hay invalid event; retry có giới hạn hoặc DeadLetter kèm reason.

### [High] — Không truyền cancellation và thiếu lock-duration strategy

**Vấn đề:** SQL, HTTP và settlement không gắn cancellation phù hợp; xử lý có thể vượt message lock.  
**Tại sao xảy ra:** Thiếu CancellationToken; không đặt MaxAutoLockRenewalDuration phù hợp với workload.  
**Ảnh hưởng production:** Duplicate khi lock mất; shutdown kéo dài.  
**Cách sửa:** Dùng args.CancellationToken, timeout cho HTTP, auto-renew bounded; công việc dài tách sang outbox worker.

### [Medium] — Deserialize và exception handling chưa phân loại

**Vấn đề:** Payload null/invalid có thể ném exception; không có đường xử lý poison rõ ràng.  
**Tại sao xảy ra:** Null-forgiving operator che giấu validation.  
**Ảnh hưởng production:** Retry vô ích, DLQ khó điều tra.  
**Cách sửa:** Validate schema/version và required fields; DeadLetter invalid payload, retry lỗi transient.

### [Medium] — Trạng thái đơn hàng bị ghi đè không kiểm tra transition

**Vấn đề:** Đơn Cancelled/Refunded có thể chuyển ngược thành Paid.  
**Tại sao xảy ra:** Không có state machine, concurrency token hoặc conditional update.  
**Ảnh hưởng production:** Vi phạm business invariant.  
**Cách sửa:** Kiểm tra transition hợp lệ, concurrency control và kiểm tra PaymentId thuộc đơn hàng.

### [Medium] — Thiếu correlation và bảo vệ dữ liệu

**Vấn đề:** Log không gắn MessageId, DeliveryCount, trace ID, outcome; outbound payload có thể chứa dữ liệu nhạy cảm trong tương lai.  
**Tại sao xảy ra:** Logging chưa thiết kế theo lifecycle.  
**Ảnh hưởng production:** Khó truy dấu, tăng thời gian MTTR.  
**Cách sửa:** Structured logs với identifiers không nhạy cảm, trace propagation, metrics và alerts.

## Phiên bản đề xuất

Giải pháp sau tách **ingestion** và **fulfillment delivery**. Giả định PaymentId duy nhất cho một successful payment và có unique constraint trên InboxEvents(EventKey), OutboxMessages(EventKey); order transition được kiểm tra. Pseudocode C# minh họa phần quan trọng, cần bổ sung mapping/DI và migration tương ứng.

~~~csharp
public async Task HandleAsync(ProcessMessageEventArgs args)
{
    OrderPaid? evt;
    try
    {
        evt = args.Message.Body.ToObjectFromJson<OrderPaid>();
        if (evt is null || evt.OrderId == Guid.Empty ||
            string.IsNullOrWhiteSpace(evt.PaymentId))
            throw new JsonException("Invalid OrderPaid");
    }
    catch (JsonException)
    {
        await args.DeadLetterMessageAsync(args.Message,
            "InvalidPayload", cancellationToken: args.CancellationToken);
        return;
    }

    await using var scope = scopes.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<OrdersDbContext>();
    var ct = args.CancellationToken;
    var eventKey = $"payment:{evt.PaymentId}";

    await using var tx = await db.Database.BeginTransactionAsync(ct);
    try
    {
        if (!await db.InboxEvents.AnyAsync(x => x.EventKey == eventKey, ct))
        {
            var order = await db.Orders.SingleOrDefaultAsync(
                x => x.Id == evt.OrderId, ct);
            if (order is null)
                throw new InvalidOperationException("Order missing: retry policy required");
            if (order.Status != "Pending" && order.Status != "Paid")
                throw new InvalidOperationException("Invalid order transition");
            if (order.Status == "Pending")
                order.Status = "Paid";

            db.OrderAudits.Add(new OrderAudit
                { OrderId = evt.OrderId, Action = "PaymentAccepted" });
            db.OutboxMessages.Add(new OutboxMessage
                { EventKey = eventKey, OrderId = evt.OrderId,
                  Type = "CreateShipment", Status = "Pending" });
            db.InboxEvents.Add(new InboxEvent { EventKey = eventKey });
            await db.SaveChangesAsync(ct);
        }
        await tx.CommitAsync(ct);
    }
    catch (DbUpdateException ex) when (IsUniqueEventConflict(ex))
    {
        await tx.RollbackAsync(ct);
        // A concurrent consumer committed this same event.
        // Verify persisted inbox/outbox before acknowledging.
        if (!await db.InboxEvents.AsNoTracking()
            .AnyAsync(x => x.EventKey == eventKey, ct))
            throw;
    }

    await args.CompleteMessageAsync(args.Message, ct);
}
~~~

Outbox dispatcher (thiết kế, không phải full implementation): claim các pending records bằng atomic update/lease có expiry; gửi POST với header Idempotency-Key = EventKey và timeout; ghi outcome vào SQL; retry với exponential backoff + jitter; quarantine lỗi permanent; reconcile các kết quả ambiguous. Nếu đối tác **không** hỗ trợ idempotency/reconciliation, không thể cam kết exactly-once external effect chỉ bằng local SQL. Cần thay đổi contract hoặc chấp nhận và quản lý rủi ro duplicate. Trong ví dụ, IsUniqueEventConflict phải nhận diện đúng SQL Server error code/constraint; cần reload DbContext sau conflict. Các lỗi nghiệp vụ không retry vô hạn: phân loại và đưa DLQ sau số lần phù hợp.

## Giải thích thiết kế sau khi sửa

Inbox ngăn xử lý lại event đã commit; unique constraint là tuyến phòng thủ cuối cùng khi nhiều consumer đua nhau. SQL transaction đảm bảo audit và fulfillment intent xuất hiện cùng thay đổi trạng thái. Outbox dispatcher chịu trách nhiệm HTTP và có retry riêng, tránh giữ Service Bus lock trong lúc chờ đối tác. Message settlement chỉ diễn ra sau khi durable state đã commit. Đây là **effectively-once business processing trong database**, không phải exactly-once HTTP delivery.

## Trade-offs

Outbox tăng bảng, cleanup, worker và latency. Idempotency key phải có retention đủ dài so với cửa sổ retry; TTL quá ngắn có thể cho phép duplicate muộn. Transaction isolation/unique constraints có chi phí contention. Nếu fulfillment API chỉ cho tạo shipment mà không có lookup theo business key, ambiguous timeout vẫn là vấn đề vận hành. Đừng thêm distributed lock khi unique constraint và transactional claim đã đủ.

## Cách kiểm thử

1. **Concurrency integration:** gửi 100 bản sao cùng PaymentId qua nhiều worker; chỉ một Inbox và Outbox intent.
2. **Failure injection:** crash sau SQL commit trước Complete; redelivery không tạo intent thứ hai.
3. **HTTP failure-path:** timeout sau khi đối tác đã xử lý; retry với cùng idempotency key không tạo shipment thứ hai (nếu contract hỗ trợ).
4. **Poison message:** JSON invalid vào DLQ; missing order xử lý theo policy có giới hạn.
5. **Transition test:** Cancelled/Refunded không bị chuyển Paid; rollback giữ audit/outbox nhất quán.

## Quan sát trong production

Application Insights traces nối MessageId, EventKey, OrderId, dependency HTTP và SQL; log outcome không chứa token/payment secrets. Theo dõi Service Bus ActiveMessages, DeadLetterMessageCount, DeliveryCount, lock lost, consumer error rate; Outbox pending age, retry count, reconciliation queue; số shipment/order và số transition conflict. Alert khi pending age vượt SLO hoặc duplicate business key xuất hiện; dashboard đối chiếu Paid-without-shipment.

2. Khi đối tác không hỗ trợ idempotency và response timeout, cách quyết định retry thế nào?
3. Nếu throughput tăng 20 lần, bạn scale outbox dispatcher mà không double-claim ra sao?

## Kết quả code review tham khảo

### [Critical] — Credential được hardcode trong Deployment

**Vấn đề:** SQL username/password xuất hiện trong manifest.  
**Tại sao xảy ra:** Connection string trực tiếp trong env value.  
**Ảnh hưởng production:** Lộ credential qua repository, deployment logs hoặc người có quyền đọc workload spec.  
**Cách sửa:** Rotate credential đã lộ; dùng Kubernetes Secret/secret provider hoặc workload identity phù hợp. Secret không tự bảo đảm an toàn nếu RBAC/encryption yếu.

### [High] — Liveness và readiness dùng chung dependency-sensitive endpoint

**Vấn đề:** /health có thể thất bại khi SQL down, khiến Kubernetes restart process vẫn khỏe.  
**Tại sao xảy ra:** Không phân biệt liveness với readiness.  
**Ảnh hưởng production:** Restart storm trong dependency outage, tăng cold start và giảm khả năng phục hồi.  
**Cách sửa:** /health/live chỉ xác minh process không bị deadlock; /health/ready kiểm tra khả năng phục vụ theo chính sách đã xác định. Không đưa external dependency vào liveness trừ khi có lý do đặc biệt.

### [High] — Không có startupProbe cho warm up dài

**Vấn đề:** Liveness bắt đầu quá sớm; 2 lần fail cách 5 giây có thể restart Pod trước khi warm up xong.  
**Tại sao xảy ra:** initialDelaySeconds=3 không phù hợp startup 25–45 giây.  
**Ảnh hưởng production:** CrashLoopBackOff, rollout stalled.  
**Cách sửa:** startupProbe đủ budget (ví dụ 60–90 giây tùy p99 startup đo được); readiness chỉ true sau warm up.

### [High] — RollingUpdate cho phép giảm capacity quá sâu

**Vấn đề:** maxUnavailable=2 với 3 replicas, maxSurge=0.  
**Tại sao xảy ra:** Deployment có thể giảm số Pod available xuống 1 trong rollout.  
**Ảnh hưởng production:** Capacity collapse, p95 tăng, 503 khi còn ít endpoints.  
**Cách sửa:** maxUnavailable=0, maxSurge=1 nếu cluster có headroom; cân nhắc PodDisruptionBudget cho voluntary disruptions (PDB không thay thế rolling update settings).

### [High] — terminationGracePeriodSeconds quá ngắn

**Vấn đề:** 5 giây không đủ cho request dài hoặc drain.  
**Tại sao xảy ra:** SIGTERM không có đủ thời gian hoàn thành in-flight requests.  
**Ảnh hưởng production:** Request bị reset, partial operations.  
**Cách sửa:** Đo request duration, đặt graceful shutdown timeout và termination grace phù hợp; kiểm tra app ngừng nhận traffic khi shutdown, cân nhắc preStop nếu thực sự cần.

### [Medium] — Image latest không bảo đảm release reproducibility

**Vấn đề:** Cùng manifest có thể pull image khác nhau.  
**Tại sao xảy ra:** Mutable tag.  
**Ảnh hưởng production:** Khó rollback, audit, điều tra version mismatch.  
**Cách sửa:** Pin digest hoặc immutable release tag; pipeline xác nhận artifact provenance.

### [Medium] — Requests/limits thiếu bằng chứng sizing

**Vấn đề:** CPU 100m và RAM 128Mi có thể throttle/OOM khi CMS warm up.  
**Tại sao xảy ra:** Cấu hình không dựa trên load/GC/working set.  
**Ảnh hưởng production:** OOMKilled, latency spikes, false probe failures.  
**Cách sửa:** Dựa vào metrics thực tế để điều chỉnh requests/limits; không mặc định tăng vô hạn.

### [Medium] — Readiness không có chính sách degraded mode

**Vấn đề:** Chưa rõ SQL outage có nên rút toàn bộ endpoints khỏi Service hay trả 503 có kiểm soát.  
**Tại sao xảy ra:** /health duy nhất không thể hiện capability.  
**Ảnh hưởng production:** Tất cả Pod NotReady làm Service không có endpoints, trong khi một số public cached content có thể vẫn phục vụ được.  
**Cách sửa:** Định nghĩa readiness theo yêu cầu traffic; kiểm tra dependency có timeout ngắn và tránh probe gây quá tải DB.

  selector:
    matchLabels:
      app: cms-api
  template:
    metadata:
      labels:
        app: cms-api
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: api
          image: registry.example.com/cms-api@sha256:REPLACE_WITH_VALID_DIGEST
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_URLS
              value: "http://+:8080"
            - name: ConnectionStrings__CmsDb
              valueFrom:
                secretKeyRef:
                  name: cms-db-connection
                  key: connectionString
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080

            timeoutSeconds: 2

          resources:

              cpu: 250m
              memory: 256Mi

Các số resources và probe budgets là **giá trị minh họa**, phải đo lại. Định nghĩa /health/startup chỉ true sau startup cần thiết; /health/live không query SQL; /health/ready phản ánh có thể nhận request. App cần cấu hình HostOptions.ShutdownTimeout và HTTP request cancellation tương thích với grace period. Service hiện tại có thể giữ nguyên nếu selector/ports phù hợp. Bổ sung topologySpreadConstraints, PodDisruptionBudget và autoscaling chỉ khi hạ tầng/traffic chứng minh cần.

## Giải thích thiết kế sau khi sửa

startupProbe ngăn liveness đánh giá process trước khi khởi động xong; readiness điều khiển việc đưa Pod vào Service endpoints; liveness chỉ khởi động lại process khi process không thể tự hồi phục. maxUnavailable=0 giữ số available replicas trong rollout nếu có đủ capacity cho surge. Immutable digest làm release và rollback có thể kiểm chứng. Secret tham chiếu không để credential lộ trong YAML (nhưng phải quản lý quyền đọc Secret).

## Trade-offs

Surge=1 cần tài nguyên cluster dư; nếu không có headroom, rollout có thể pending. Startup budget quá dài làm phát hiện lỗi khởi động chậm; quá ngắn gây restart loop. Readiness phụ thuộc SQL có thể tạo no-endpoints khi SQL outage; lựa chọn tùy endpoint và degraded mode. Grace period dài giữ Pod terminating lâu hơn, cần điều chỉnh theo SLO. Không nên chuyển sang Kubernetes chỉ để sửa một lỗi deployment nếu App Service đã đáp ứng yêu cầu vận hành.

## Cách kiểm thử

1. **Deployment validation:** staging rollout với startup 45 giây; không có 503 và không restart trước startup budget.
2. **Failure injection:** ngắt SQL 60 giây; kiểm tra liveness không restart, readiness/degraded response đúng contract.
3. **Load test:** rolling update dưới peak traffic; đo p95/p99, error rate và available endpoints.
4. **Graceful shutdown:** gửi request dài, terminate Pod, kiểm tra in-flight requests và thời gian drain.
5. **Security/deployment:** quét manifest không chứa credential; verify immutable image digest, rollback về artifact trước.

## Quan sát trong production

Kubernetes events, Pod restart count, reason OOMKilled, readiness/liveness probe failures, deployment unavailable replicas, endpoint count và rollout duration. Azure Monitor/Application Insights theo dõi request 503, p95/p99, SQL dependency failures, CPU throttling, working set/GC và cancellation. Correlate deployment revision/digest với lỗi; alert khi available replicas dưới mức an toàn, rollout timeout hoặc 5xx vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL down nhưng trang public có thể phục vụ cache, readiness nên kiểm tra điều gì?
2. Cluster không đủ tài nguyên cho maxSurge=1: bạn đổi chiến lược rollout hay capacity plan?
3. Nếu readiness pass nhưng request thực tế vẫn 503, bạn phân biệt lỗi ingress, Service endpoints và application thế nào?

## Kiến thức trọng tâm

Message settlement không atomic với SQL transaction hay HTTP side effect; cần idempotency, durable intent và reconciliation cho ambiguous outcomes.
