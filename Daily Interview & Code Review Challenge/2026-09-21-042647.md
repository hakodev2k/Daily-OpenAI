# Code Review Challenge 1 — Authorization theo claims nhưng endpoint đang tin dữ liệu từ client

**Chủ đề:** C#/.NET, ASP.NET Core, Microsoft Entra ID/JWT, policy-based authorization, EF Core, IDOR, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề quan trọng

## Bối cảnh

Một internal employee platform dùng Microsoft Entra ID để đăng nhập. API cho phép manager xem và phê duyệt timesheet của nhân viên. Frontend gửi `managerId` và `employeeId` cùng request. Team cho rằng dữ liệu này an toàn vì UI chỉ hiển thị nhân viên thuộc manager hiện tại.

Sau một security review, QA phát hiện có thể sửa request bằng browser dev tools. Chưa có bằng chứng rằng dữ liệu đã bị truy cập trái phép trong production. Hãy review implementation hiện tại mà không giả định frontend là security boundary.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/timesheets")]
public sealed class TimesheetsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<TimesheetsController> _logger;

    public TimesheetsController(AppDbContext db, ILogger<TimesheetsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{id:guid}")]
    public async Task<ActionResult<TimesheetDto>> Get(
        Guid id,
        [FromQuery] Guid managerId,
        CancellationToken cancellationToken)
    {
        var timesheet = await _db.Timesheets
            .AsNoTracking()
            .Where(x => x.Id == id)
            .Select(x => new TimesheetDto(
                x.Id, x.EmployeeId, x.Employee.Email,
                x.WeekStart, x.TotalHours, x.Status))
            .SingleOrDefaultAsync(cancellationToken);

        if (timesheet is null)
            return NotFound();

        _logger.LogInformation(
            "Manager {ManagerId} viewed employee {EmployeeId}",
            managerId, timesheet.EmployeeId);

        return Ok(timesheet);
    }

    [HttpPost("{id:guid}/approve")]
    public async Task<IActionResult> Approve(
        Guid id,
        [FromBody] ApproveTimesheetRequest request,
        CancellationToken cancellationToken)
    {
        var timesheet = await _db.Timesheets
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (timesheet is null)
            return NotFound();

        if (timesheet.EmployeeId != request.EmployeeId)
            return BadRequest();

        timesheet.Status = "Approved";
        timesheet.ApprovedByManagerId = request.ManagerId;
        timesheet.ApprovedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);
        return NoContent();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness và authorization, đặc biệt các trust boundary sai.
2. Phân tích production impact nếu attacker hoặc user hợp lệ sửa `id`, `employeeId`, `managerId`.
3. Ưu tiên finding theo severity thay vì chỉ nêu code style.
4. Đề xuất authorization design dựa trên authenticated principal và business relationship thực tế.
5. Nêu test cần có cho horizontal/vertical authorization.
6. Nêu telemetry/audit cần thiết nhưng không log dữ liệu nhạy cảm quá mức.
7. Giải thích trade-off giữa query-scoped authorization và policy/resource-based authorization.

## Câu hỏi gợi mở

1. `[Authorize]` đảm bảo điều gì và không đảm bảo điều gì trong endpoint này?
2. `managerId` lấy từ query/body có phải bằng chứng identity không?
3. Nếu manager chỉ được xem nhân viên thuộc team tại thời điểm request, relationship nên được kiểm tra ở đâu?
4. Nếu admin có quyền override, bạn sẽ biểu diễn rule đó thế nào để tránh `if` rải rác?
5. Audit log nào giúp điều tra incident nhưng không biến log thành nguồn PII không cần thiết?

## Kết quả code review tham khảo

### Critical — GET endpoint không kiểm tra quyền trên timesheet

**Vấn đề:** Bất kỳ authenticated user nào biết/đoán được `id` đều có thể lấy timesheet; `managerId` chỉ được log.  
**Tại sao xảy ra:** Code nhầm authentication với resource authorization và tin rằng UI giới hạn navigation.  
**Ảnh hưởng production:** Horizontal privilege escalation/IDOR, lộ dữ liệu nhân viên.  
**Cách sửa:** Derive caller identity từ authenticated principal; authorize resource dựa trên relationship/role/policy thực tế trước khi trả dữ liệu.

### Critical — Approve tin `request.ManagerId`

**Vấn đề:** Caller tự khai manager identity rồi server ghi vào audit/business state.  
**Tại sao xảy ra:** Trust boundary đặt ở request payload thay vì token/principal và server-side authorization.  
**Ảnh hưởng production:** User hợp lệ có thể giả danh approver nếu không có control khác.  
**Cách sửa:** Lấy stable subject/object identifier từ claims đã được validate; map tới internal identity nếu cần và kiểm tra quyền approve trên resource.

### High — `EmployeeId` equality không chứng minh quyền approve

**Vấn đề:** Kiểm tra timesheet thuộc employee client gửi chỉ chứng minh hai input khớp nhau.  
**Tại sao xảy ra:** Business authorization relation manager→employee không được kiểm tra.  
**Ảnh hưởng production:** Unauthorized approval.  
**Cách sửa:** Query/authorization handler phải xác minh caller quản lý employee hoặc có explicit privileged role/policy.

### High — Business transition không được bảo vệ

**Vấn đề:** Code chuyển mọi trạng thái sang `Approved` mà không kiểm tra trạng thái hiện tại/rule như submitted, already approved, locked period.  
**Tại sao xảy ra:** Endpoint coi authorization và state transition là assignment đơn giản.  
**Ảnh hưởng production:** Invalid workflow và audit inconsistency.  
**Cách sửa:** Enforce state-machine/business invariant và concurrency semantics phù hợp.

### Medium — Audit event dùng identity không đáng tin

**Vấn đề:** Log `managerId` do client cung cấp có thể tạo audit trail sai.  
**Tại sao xảy ra:** Telemetry không phân biệt caller identity đã xác thực và business identifiers từ request.  
**Ảnh hưởng production:** Incident investigation sai lệch.  
**Cách sửa:** Log safe authenticated subject/internal actor ID, resource ID, decision/result và correlation ID; tránh token/claims nhạy cảm.

### Medium — Authorization logic có nguy cơ bị copy/paste giữa endpoints

**Vấn đề:** Khi rule phức tạp, inline checks dễ drift.  
**Tại sao xảy ra:** Không có reusable policy/resource authorization boundary.  
**Ảnh hưởng production:** Endpoint mới dễ quên kiểm tra.  
**Cách sửa:** Cân nhắc policy/resource-based authorization hoặc domain/application authorization service; giữ query filtering gần data layer khi phù hợp.

## Phiên bản đề xuất

Một skeleton an toàn hơn là lấy actor từ principal và authorize resource server-side:

```csharp
[HttpPost("{id:guid}/approve")]
public async Task<IActionResult> Approve(Guid id, CancellationToken ct)
{
    var subject = User.FindFirst("oid")?.Value
        ?? User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

    if (string.IsNullOrWhiteSpace(subject))
        return Forbid();

    var actor = await _db.Users
        .SingleOrDefaultAsync(x => x.ExternalSubject == subject, ct);

    if (actor is null)
        return Forbid();

    var timesheet = await _db.Timesheets
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    if (timesheet is null)
        return NotFound();

    var canApprove = actor.IsTimesheetAdmin ||
        await _db.ManagerAssignments.AnyAsync(
            x => x.ManagerId == actor.Id &&
                 x.EmployeeId == timesheet.EmployeeId &&
                 x.IsActive,
            ct);

    if (!canApprove)
        return Forbid();

    if (timesheet.Status != "Submitted")
        return Conflict();

    timesheet.Status = "Approved";
    timesheet.ApprovedByManagerId = actor.Id;
    timesheet.ApprovedAt = DateTime.UtcNow;

    await _db.SaveChangesAsync(ct);
    return NoContent();
}
```

Tên claim cụ thể phụ thuộc token configuration/identity contract; không được copy `oid` máy móc nếu hệ thống dùng identifier khác. Với rule lớn hơn, resource-based authorization handler/application service thường giúp tập trung policy. Query-scoped filtering có thể giảm khả năng tải resource trái phép, nhưng phải giữ semantics `404`/`403`, audit và maintainability nhất quán.

## Giải thích thiết kế sau khi sửa

Security boundary nằm ở server. Token đã validate cung cấp identity/claims; business authorization xác minh actor-resource relationship bằng dữ liệu authoritative. Client không gửi `managerId` để tự chứng minh quyền. Business state transition cũng được validate riêng vì một caller có quyền không đồng nghĩa mọi transition đều hợp lệ.

## Trade-offs

- Inline query authorization đơn giản và hiệu quả cho rule nhỏ nhưng dễ lặp/drift.
- Resource-based policy tập trung rule tốt hơn nhưng thêm abstraction và cần tránh handler làm quá nhiều database work không kiểm soát.
- Trả `404` có thể giảm resource enumeration trong một số threat model; `403` rõ semantics hơn. Chọn nhất quán theo API/security requirements.
- Claims có thể chứa role/permission, nhưng dynamic manager assignment thường cần server-side authoritative data hoặc strategy cache có invalidation rõ ràng.

## Cách kiểm thử

1. Integration test user A không thể GET/approve timesheet của employee ngoài scope.
2. Test sửa `managerId`/`employeeId` không thay đổi authorization decision.
3. Test manager hợp lệ, admin override và user không có role.
4. Test workflow transition: Draft/Submitted/Approved/locked period.
5. Test concurrent approval nếu business yêu cầu chống double transition, với concurrency token/transaction strategy phù hợp.

## Quan sát trong production

Audit authorization decision theo actor ID an toàn, resource ID, policy/result, correlation ID và endpoint; không log raw JWT. Alert trên spike 403/404 bất thường, repeated access nhiều resource IDs và approval failures. Correlate với Entra sign-in/security telemetry khi điều tra nhưng không kết luận malicious chỉ từ một signal.

## Câu hỏi phỏng vấn mở rộng

1. Nếu manager assignment thay đổi trong ngày nhưng role claim chỉ refresh khi token được cấp lại, bạn sẽ đặt dữ liệu authorization nào trong token và dữ liệu nào server-side?
2. Bạn sẽ phản biện đề xuất “chỉ dùng GUID khó đoán nên không cần resource authorization” thế nào?
3. Nếu authorization query trở thành bottleneck, bạn tối ưu/caching ra sao mà vẫn giữ revocation semantics?

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky khi CI chạy song song

**Chủ đề:** Playwright, E2E testing, CI/CD, test isolation, shared state, parallel workers, test data, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 7–10 vấn đề quan trọng

## Bối cảnh

Một e-commerce team có Playwright suite chạy ổn trên laptop nhưng CI thường fail ngẫu nhiên khi bật 6 workers. Team đang cân nhắc thêm retry toàn bộ test để “ổn định pipeline”. Failure phổ biến: test checkout đôi lúc thấy cart trống, test profile đôi lúc login thành user khác, và một số assertions timeout sau deploy.

Pipeline dùng cùng staging environment cho nhiều tests. Review test/config dưới đây và tập trung vào nguyên nhân hệ thống, không chỉ tăng timeout.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const sharedEmail = 'e2e-user@example.test';
let orderId: string | undefined;

test.beforeAll(async ({ request }) => {
  await request.post('/test/reset-user', {
    data: { email: sharedEmail }
  });
});

test('checkout', async ({ page }) => {
  await page.goto('/login');
  await page.fill('#email', sharedEmail);
  await page.fill('#password', 'Password123!');
  await page.click('button[type=submit]');

  await page.goto('/products/sku-123');
  await page.click('text=Add to cart');
  await page.waitForTimeout(2000);
  await page.goto('/cart');

  await expect(page.locator('.cart-item')).toHaveCount(1);
  await page.click('text=Checkout');
  await page.waitForTimeout(3000);

  orderId = await page.locator('[data-order-id]').getAttribute('data-order-id') ?? undefined;
  expect(orderId).toBeTruthy();
});

test('profile shows latest order', async ({ page }) => {
  await page.goto(`/profile?email=${encodeURIComponent(sharedEmail)}`);
  await page.waitForTimeout(1000);

  await expect(page.locator(`text=${orderId}`)).toBeVisible();
});

test.afterAll(async ({ request }) => {
  await request.delete(`/test/orders/${orderId}`);
  await request.post('/test/reset-user', { data: { email: sharedEmail } });
});
```

## Nhiệm vụ của ứng viên

1. Tìm race conditions, hidden ordering assumptions và shared-state problems.
2. Giải thích vì sao tăng retries/timeouts có thể che lỗi thay vì sửa suite.
3. Đề xuất test-data/isolation strategy phù hợp khi chạy nhiều workers và nhiều CI runs.
4. Đề xuất cách đồng bộ theo observable state thay vì sleep cố định.
5. Xác định security risk của test credentials/test-only endpoints.
6. Thiết kế diagnostics để một failure trên CI có đủ evidence điều tra.
7. Nêu trade-offs giữa E2E coverage và API/integration tests.

## Câu hỏi gợi mở

1. Hai tests có thực sự độc lập không, và Playwright có đảm bảo thứ tự bạn đang ngầm dựa vào không?
2. Điều gì xảy ra khi hai workers hoặc hai pipeline runs cùng reset `sharedEmail`?
3. `waitForTimeout` chứng minh điều kiện business nào đã hoàn thành?
4. `orderId` global có lifetime/visibility semantics nào khiến suite khó tin cậy?

## Kết quả code review tham khảo

### High — Tests phụ thuộc thứ tự thông qua global `orderId`

**Vấn đề:** `profile shows latest order` cần output từ `checkout`.  
**Tại sao xảy ra:** Suite dùng test case như workflow steps nhưng vẫn khai báo thành independent tests.  
**Ảnh hưởng production:** Parallelism/retry/sharding làm test fail nondeterministically; failure đầu gây cascade.  
**Cách sửa:** Mỗi test tự tạo prerequisite qua fixture/API hoặc gộp thành một scenario nếu dependency thực sự là một E2E journey không thể tách.

### High — Shared user gây cross-worker/cross-run interference

**Vấn đề:** Mọi test/run dùng cùng email và reset cùng state.  
**Tại sao xảy ra:** Test data không có ownership namespace.  
**Ảnh hưởng production:** Cart/order/session bị test khác thay đổi, tạo false failures hoặc false passes.  
**Cách sửa:** Tạo unique user/data per worker/test/run, ví dụ run ID + worker index; cleanup theo owned resources.

### High — Reset endpoint có thể là security boundary nguy hiểm

**Vấn đề:** Endpoint có khả năng mutate/reset account.  
**Tại sao xảy ra:** Test convenience được đưa vào deployed environment mà chưa nêu access control.  
**Ảnh hưởng production:** Nếu exposed sai environment/permission, endpoint có thể trở thành privileged backdoor.  
**Cách sửa:** Tách test fixture mechanism, restrict bằng environment/network/identity/authorization; đảm bảo không deploy hoặc không accessible ở production theo architecture.

### Medium — Fixed sleeps tạo timing race

**Vấn đề:** 2s/3s/1s không chứng minh cart/order/profile đã đạt trạng thái cần thiết.  
**Tại sao xảy ra:** Đồng bộ theo thời gian thay vì observable condition.  
**Ảnh hưởng production:** CI chậm thì fail; local nhanh thì lãng phí thời gian.  
**Cách sửa:** Chờ UI locator state, response có nghĩa, URL/state transition hoặc poll backend condition có bounded timeout.

### Medium — Cleanup dựa vào state có thể chưa tồn tại

**Vấn đề:** `afterAll` delete với `orderId` undefined hoặc order thuộc execution khác.  
**Tại sao xảy ra:** Cleanup không idempotent và ownership yếu.  
**Ảnh hưởng production:** Test data leak/corruption và failure thứ cấp che root cause.  
**Cách sửa:** Fixture lưu resources đã tạo, cleanup idempotent trong `finally`/fixture teardown, scope đúng test/worker.

### Medium — Credential hard-code trong source

**Vấn đề:** Password nằm trong test code.  
**Tại sao xảy ra:** Secret/test credential management chưa tách khỏi repository.  
**Ảnh hưởng production:** Credential reuse/leak và khó rotation.  
**Cách sửa:** Provision ephemeral credentials hoặc secret injection phù hợp CI; không log secret.

### Medium — Locator phụ thuộc text/DOM implementation

**Vấn đề:** `text=Add to cart`, CSS classes và interpolated text dễ ambiguous/brittle.  
**Tại sao xảy ra:** Test selector không dựa trên accessible semantics/stable test contract.  
**Ảnh hưởng production:** UI refactor nhỏ gây noise.  
**Cách sửa:** Ưu tiên role/label và stable `data-testid` khi cần; assert business state thay vì DOM incidental detail.

## Phiên bản đề xuất

Ví dụ dùng fixture/API để tạo user/order riêng cho từng test:

```ts
import { test, expect } from '@playwright/test';

function uniqueEmail(testId: string) {
  return `e2e-${process.env.CI_RUN_ID ?? 'local'}-${testId}@example.test`;
}

test('checkout creates an order', async ({ page, request }, testInfo) => {
  const email = uniqueEmail(`${testInfo.workerIndex}-${testInfo.testId}`);

  const setup = await request.post('/test-fixtures/users', {
    data: { email }
  });
  expect(setup.ok()).toBeTruthy();

  try {
    await page.goto('/login');
    await page.getByLabel('Email').fill(email);
    await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
    await page.getByRole('button', { name: 'Sign in' }).click();

    await page.goto('/products/sku-123');
    await page.getByRole('button', { name: 'Add to cart' }).click();
    await expect(page.getByTestId('cart-count')).toHaveText('1');

    await page.goto('/cart');
    await page.getByRole('button', { name: 'Checkout' }).click();

    await expect(page).toHaveURL(/\/orders\//);
    await expect(page.getByTestId('order-status')).toBeVisible();
  } finally {
    await request.delete(`/test-fixtures/users/${encodeURIComponent(email)}`);
  }
});
```

Tên endpoint chỉ là scenario design; trong hệ thống thật phải dùng fixture mechanism được bảo vệ và không expose sai environment. `E2E_PASSWORD` cũng không nên là shared permanent credential nếu có thể provision identity riêng.

## Giải thích thiết kế sau khi sửa

Mỗi test sở hữu prerequisite và cleanup của nó, không dựa vào test trước. Parallel worker chỉ an toàn khi data isolation cũng parallel-safe. Đồng bộ dựa trên state observable giúp test vừa nhanh vừa deterministic hơn. Retry chỉ nên dùng có chủ đích cho infrastructure/transient behavior đã hiểu; retry không thay thế root-cause analysis.

## Trade-offs

- Unique data tăng setup/cleanup cost nhưng đổi lại isolation và khả năng chạy parallel.
- UI E2E cho confidence cao ở critical journey nhưng chậm/brittle hơn integration/API tests; không nên dùng UI để test mọi permutation.
- API fixture nhanh nhưng có thể bypass production UI path; vì vậy dùng để arrange state, còn assertion quan trọng vẫn đi qua boundary cần kiểm chứng.
- Trace/video/screenshot tăng storage/time nhưng rất hữu ích khi chỉ bật on-first-retry/failure theo policy phù hợp.

## Cách kiểm thử

1. Chạy cùng suite với 1, 2, 6+ workers và lặp nhiều lần để tìm shared-state race.
2. Chạy hai CI jobs đồng thời với namespace khác nhau.
3. Inject latency vào checkout/order propagation để xác nhận test chờ condition chứ không dựa sleep.
4. Force test failure giữa setup và assertion để xác minh cleanup idempotent.
5. Security test/deployment check bảo đảm fixture/reset endpoints không accessible ngoài intended test environment.

## Quan sát trong production

Ở CI lưu Playwright trace, screenshot, video/network evidence theo failure policy; log run ID, worker ID, test ID và fixture IDs nhưng không log password/token. Dashboard flake rate theo test, retry pass rate, duration percentile và environment health. Phân biệt product defect, test defect và environment defect thay vì coi mọi retry-pass là thành công.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận retry một E2E test, và metric nào cho thấy retry đang che flakiness?
2. Nếu checkout phụ thuộc eventual consistency của downstream service, bạn sẽ assert thế nào mà không tạo timeout rất dài?
3. Bạn sẽ chia test pyramid giữa unit, integration/API và Playwright cho flow checkout như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authorization phải dựa trên authenticated identity và server-side resource/business rules, không dựa vào identifiers do client tự khai.
- E2E parallelism chỉ đáng tin khi test data, mutable state và cleanup có ownership/isolation rõ ràng.
- Security, correctness và observability phải được thiết kế cùng implementation thay vì thêm sau khi incident xảy ra.

## Mẫu tư duy cần nhớ

- Xác định trust boundary trước khi đọc từng dòng code.
- Với authorization: **identity → resource → policy/business relationship → decision → audit**.
- Với flaky test: **shared state → ordering → timing → environment → evidence** trước khi tăng retry.
- Chờ observable condition thay vì sleep cố định.
- Test theo risk và failure mode; không dùng E2E cho mọi trường hợp chỉ vì nó gần production hơn.
