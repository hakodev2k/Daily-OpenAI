# Code Review Challenge 1 — Hangfire xử lý offboarding bị chạy trùng và cập nhật sai trạng thái

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, transaction handling, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core/.NET service dùng Hangfire để xử lý các cấu hình offboarding đã hết hạn. Job chạy trên nhiều application instance. Mỗi bản ghi có thể yêu cầu gọi một external mail service để bỏ forwarding rồi cập nhật database. Gần đây production ghi nhận một số mailbox bị gọi reset nhiều lần, một số record được đánh dấu `Completed` dù external call thất bại, và thỉnh thoảng hai worker cùng xử lý một cấu hình.

Hệ thống cần chịu được retry của Hangfire và việc process bị restart giữa chừng. External mail operation tương đối đắt và không nên gọi lặp không cần thiết.

## Đoạn code cần review

```csharp
public sealed class OffboardingResetJob
{
    private readonly AppDbContext _db;
    private readonly IMailAdminClient _mailClient;
    private readonly ILogger<OffboardingResetJob> _logger;

    public OffboardingResetJob(
        AppDbContext db,
        IMailAdminClient mailClient,
        ILogger<OffboardingResetJob> logger)
    {
        _db = db;
        _mailClient = mailClient;
        _logger = logger;
    }

    public async Task RunAsync()
    {
        var expired = await _db.OffboardingMailConfigs
            .Where(x => x.EndTime <= DateTime.UtcNow && x.Status != "Completed")
            .ToListAsync();

        foreach (var item in expired)
        {
            try
            {
                item.Status = "Processing";
                await _db.SaveChangesAsync();

                await _mailClient.RemoveForwardingAsync(item.UserEmail);

                item.Status = "Completed";
                item.CompletedAt = DateTime.UtcNow;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed to reset offboarding for {Email}", item.UserEmail);

                item.Status = "Failed";
            }
            finally
            {
                await _db.SaveChangesAsync();
            }
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Xác định rủi ro concurrency, retry và performance.
3. Giải thích tác động production của từng vấn đề quan trọng.
4. Ưu tiên vấn đề cần sửa trước.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách test retry, crash và concurrent workers.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai Hangfire worker có thể đọc cùng một record trước khi worker nào `SaveChangesAsync()` không?
- `Status = "Processing"` có thực sự tạo ra quyền sở hữu độc quyền đối với record không?
- Điều gì xảy ra nếu external call thành công nhưng process chết trước khi lưu `Completed`?
- Retry của job có thể gọi external side effect lần thứ hai không?
- Có nên giữ database transaction mở trong lúc gọi external service không?

## Gợi ý

### Gợi ý 1

### Gợi ý 2

Tập trung vào atomic claim, optimistic/pessimistic concurrency, idempotency key và trạng thái trung gian khi crash xảy ra giữa external call và database commit.

## Kết quả code review tham khảo

### 1. Không có atomic claim — nhiều worker có thể xử lý cùng record

**Problem:** Query lấy mọi record chưa `Completed`, sau đó mới đổi trạng thái từng record.  
**Why:** Hai worker có thể cùng đọc record khi nó vẫn ở trạng thái cũ. Không có concurrency token, conditional update hoặc lock để xác lập ownership.  
**Production impact:** External reset có thể chạy nhiều lần; trạng thái cuối có thể bị worker khác ghi đè.  
**Severity:** Critical.  
**Recommended fix:** Claim record bằng một thao tác atomic, ví dụ conditional `UPDATE ... WHERE Status = Pending` và chỉ worker update thành công mới được xử lý; hoặc dùng cơ chế concurrency phù hợp của database.

### 2. Workflow không idempotent

**Problem:** Retry gọi lại `RemoveForwardingAsync` mà không có operation/idempotency key.  
**Why:** Hangfire và distributed job systems nói chung phải được thiết kế với khả năng thực thi lại khi failure xảy ra.  
**Production impact:** Side effect bị lặp, quota/API cost tăng hoặc trạng thái external không dự đoán được.  
**Severity:** Critical.  
**Recommended fix:** Làm external operation idempotent nếu API cho phép; lưu stable operation ID và kiểm tra trạng thái trước khi retry.

### 3. Crash window giữa external success và database commit

**Problem:** Mail operation có thể thành công nhưng process chết trước khi `Completed` được lưu.  
**Why:** Database và external system không nằm trong cùng atomic transaction.  
**Production impact:** Retry nhìn record như chưa hoàn thành và gọi side effect lại.  
**Severity:** High.  
**Recommended fix:** Thiết kế state machine có `Processing`, operation ID, attempt metadata và reconciliation; không giả định distributed atomicity.

### 4. `Processing` vẫn được query lại

**Problem:** Predicate chỉ loại `Completed`; record `Processing` và `Failed` đều được chọn ở lần chạy tiếp theo.  
**Why:** Không có định nghĩa rõ trạng thái eligible, lease hoặc retry schedule.  
**Production impact:** Worker khác có thể lấy record đang chạy; failed item có thể retry liên tục.  
**Severity:** High.  
**Recommended fix:** Query trạng thái cụ thể (`Pending`, retryable `Failed`) và dùng lease/claim timestamp nếu cần recovery worker bị chết.

### 5. Không có cancellation/timeout policy rõ ràng

**Problem:** Database và external calls không nhận cancellation token.  
**Why:** Shutdown/deployment không thể cooperatively cancel work; external dependency có thể treo lâu.  
**Production impact:** Shutdown kéo dài, worker slot bị chiếm, recovery khó dự đoán.  
**Severity:** Medium.  
**Recommended fix:** Propagate cancellation; external client cần timeout/retry policy phù hợp và phân biệt transient/permanent failures.

### 6. Một lần query có thể tải quá nhiều record

**Problem:** `ToListAsync()` lấy toàn bộ expired records.  
**Why:** Không có batch size hoặc pagination.  
**Production impact:** Memory tăng, DbContext tracking lớn, job kéo dài.  
**Severity:** Medium.  
**Recommended fix:** Claim và xử lý theo batch nhỏ.

### 7. DbContext tracking tích tụ trong job dài

**Problem:** Tất cả entity nằm trong một DbContext xuyên suốt job.  
**Why:** EF Core change tracker giữ references tới tracked entities.  
**Production impact:** Memory/SaveChanges overhead tăng theo batch lớn.  
**Severity:** Medium.  
**Recommended fix:** Scope DbContext theo batch/item hoặc detach/clear phù hợp.

### 8. Catch mọi exception và biến thành `Failed`

**Problem:** Không phân biệt transient, permanent, cancellation hay programming errors.  
**Why:** Broad catch che mất semantics retry.  
**Production impact:** Có thể vô hiệu hóa retry đúng chỗ hoặc retry sai lỗi không thể phục hồi.  
**Severity:** Medium.  
**Recommended fix:** Phân loại failure; lưu `AttemptCount`, `LastErrorCode`, `NextRetryAt`; rethrow khi muốn Hangfire retry theo policy.

### 9. `finally` luôn ghi database

**Problem:** `SaveChangesAsync` trong `finally` có thể phát sinh exception mới và che exception ban đầu.  
**Why:** Cleanup block chứa operation có thể fail.  
**Production impact:** Diagnostic khó, trạng thái không chắc chắn.  
**Severity:** Medium.  
**Recommended fix:** Persist transition có chủ đích ở từng nhánh; log failure khi persistence thất bại.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa pattern atomic claim ở application level. Chi tiết SQL/EF cần điều chỉnh theo SQL Server hoặc PostgreSQL và schema thực tế.

```csharp
public sealed class OffboardingResetJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IMailAdminClient _mailClient;
    private readonly ILogger<OffboardingResetJob> _logger;

    public OffboardingResetJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IMailAdminClient mailClient,
        ILogger<OffboardingResetJob> logger)
    {
        _dbFactory = dbFactory;
        _mailClient = mailClient;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var db = await _dbFactory.CreateDbContextAsync(ct);

            var candidateIds = await db.OffboardingMailConfigs
                .AsNoTracking()
                .Where(x => x.EndTime <= DateTime.UtcNow && x.Status == "Pending")
                .OrderBy(x => x.EndTime)
                .Select(x => x.Id)
                .Take(50)
                .ToListAsync(ct);

            if (candidateIds.Count == 0)
                return;

            foreach (var id in candidateIds)
            {
                ct.ThrowIfCancellationRequested();
                await ProcessOneAsync(id, ct);
            }
        }
    }

    private async Task ProcessOneAsync(Guid id, CancellationToken ct)
    {
        var operationId = $"offboarding-reset:{id}";

        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.OffboardingMailConfigs
            .Where(x => x.Id == id && x.Status == "Pending")
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.OperationId, operationId)
                .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

        if (claimed != 1)
            return;

        try
        {
            await _mailClient.RemoveForwardingAsync(operationId, ct);

            await db.OffboardingMailConfigs
                .Where(x => x.Id == id &&
                            x.Status == "Processing" &&
                            x.OperationId == operationId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "Completed")
                    .SetProperty(x => x.CompletedAt, DateTime.UtcNow), ct);
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Offboarding reset failed. ConfigId={ConfigId} OperationId={OperationId}",
                id, operationId);

            await db.OffboardingMailConfigs
                .Where(x => x.Id == id && x.OperationId == operationId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "Failed")
                    .SetProperty(x => x.LastError, ex.GetType().Name), ct);

            throw;
        }
    }
}
```

Điểm quan trọng: `ExecuteUpdateAsync` conditional claim làm việc claim atomically ở database. Tuy nhiên đoạn mẫu vẫn cần chiến lược recovery cho record mắc kẹt ở `Processing`, và external client phải hỗ trợ idempotency hoặc workflow phải có bước reconciliation. Không nên giữ database transaction mở trong suốt network call chỉ để cố tạo “atomicity” giả giữa database và external service.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi số lượng worker vừa phải. Lease (`ClaimedUntil`) tốt hơn nếu worker có thể chết sau claim vì record có thể được reclaim sau timeout. Database locking mạnh hơn có thể giảm duplicate processing nhưng tăng contention và cần hiểu behavior riêng của SQL Server/PostgreSQL. Outbox/inbox hữu ích nếu workflow chuyển sang message-driven, nhưng thêm schema và operational complexity. Distributed lock chỉ nên dùng khi thật sự cần; nó không tự giải quyết crash window giữa external side effect và database commit.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 worker đồng thời với cùng một pending ID; xác nhận chỉ một worker claim thành công.
2. **Crash/failure-path:** giả lập external call thành công rồi process dừng trước DB completion; xác nhận reconciliation/idempotency xử lý an toàn.
3. **Retry test:** external client timeout lần đầu, thành công lần hai; xác nhận không tạo side effect trùng.
4. **Load test:** hàng chục nghìn expired records; đo memory, DB query time, worker throughput và lock contention.
5. **Cancellation test:** cancel trong lúc job đang chạy; xác nhận shutdown có kiểm soát và trạng thái có thể recover.

## Quan sát trong production

Theo dõi `offboarding_job_claim_total`, success/failure/retry count, processing duration, records mắc kẹt ở `Processing`, duplicate-operation detections và external latency/error rate. Log theo `ConfigId` + `OperationId`, không dùng email làm primary correlation field nếu không cần vì đây là dữ liệu nhạy cảm. Trace DB claim → external call → status transition. Alert khi số `Processing` quá lease threshold hoặc retry tăng bất thường.

# Code Review Challenge 2 — Endpoint tìm kiếm audit log có nguy cơ SQL injection và lộ dữ liệu nhạy cảm

**Chủ đề:** Input validation, SQL injection, authorization, sensitive-data exposure, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một internal admin API cho phép support team tìm audit log theo tenant, email và text. API dùng ASP.NET Core với SQL Server. Sau khi mở quyền cho nhiều support users hơn, security review phát hiện endpoint có thể trả log của tenant khác và request có query lạ làm database CPU tăng mạnh.

Audit log có thể chứa email, IP address, error detail và metadata nghiệp vụ. Endpoint phải hỗ trợ tìm kiếm nhưng không được tin client-supplied tenant identity.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly IConfiguration _configuration;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        IConfiguration configuration,
        ILogger<AuditController> logger)
    {
        _configuration = configuration;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        string tenantId,
        string? email,
        string? text,
        int take = 1000)
    {
        var connectionString = _configuration.GetConnectionString("MainDb");
        await using var connection = new SqlConnection(connectionString);
        await connection.OpenAsync();

        var sql = $@"
            SELECT TOP ({take}) Id, TenantId, UserEmail, IpAddress,
                   Action, Detail, CreatedAt
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'";

        if (!string.IsNullOrWhiteSpace(email))
            sql += $" AND UserEmail LIKE '%{email}%'";

        if (!string.IsNullOrWhiteSpace(text))
            sql += $" AND Detail LIKE '%{text}%'";

        sql += " ORDER BY CreatedAt DESC";

        _logger.LogInformation("Audit search SQL: {Sql}", sql);

        await using var command = new SqlCommand(sql, connection);
        await using var reader = await command.ExecuteReaderAsync();

        var result = new List<object>();
        while (await reader.ReadAsync())
        {
            result.Add(new
            {
                Id = reader.GetGuid(0),
                TenantId = reader.GetString(1),
                UserEmail = reader.GetString(2),
                IpAddress = reader.GetString(3),
                Action = reader.GetString(4),
                Detail = reader.GetString(5),
                CreatedAt = reader.GetDateTime(6)
            });
        }

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. SQL injection qua `tenantId`, `email`, `text` và `take`

**Problem:** Request data được nội suy trực tiếp vào SQL.  
**Why:** String interpolation thay đổi SQL text thay vì truyền values dưới dạng parameters.  
**Production impact:** Có thể đọc/sửa dữ liệu trái phép tùy quyền DB principal; ít nhất có thể phá query hoặc gây resource abuse.  
**Severity:** Critical.  
**Recommended fix:** Parameterized query; `take` phải validate/clamp và không lấy trực tiếp từ SQL fragment.

### 2. Broken tenant authorization

**Problem:** Caller tự truyền `tenantId`; `[Authorize]` chỉ yêu cầu authenticated principal theo policy mặc định, không chứng minh quyền đối với tenant đó.  
**Why:** Resource/tenant authorization chưa được thực hiện.  
**Production impact:** Cross-tenant data exposure.  
**Severity:** Critical.  
**Recommended fix:** Derive tenant scope từ trusted claims/server-side membership và enforce authorization policy/resource check.

### 3. Endpoint trả quá nhiều dữ liệu nhạy cảm

**Problem:** Response luôn gồm email, IP và raw `Detail`.  
**Why:** Không áp dụng data minimization/redaction theo role/use case.  
**Production impact:** Privacy/security blast radius tăng nếu account support bị compromise.  
**Severity:** High.  
**Recommended fix:** Chỉ trả fields cần thiết; redact/mask sensitive detail; phân quyền riêng cho raw audit detail.

### 4. Log raw SQL chứa dữ liệu người dùng

**Problem:** SQL sau interpolation được ghi ở Information level.  
**Why:** Query chứa tenant ID, email và search text.  
**Production impact:** Sensitive data bị copy sang logging platform và retention khác database.  
**Severity:** High.  
**Recommended fix:** Structured logging với metadata an toàn như caller ID, tenant scope ID nếu policy cho phép, result count, duration; không log raw search text/SQL chứa PII.

### 5. Không giới hạn `take`

**Problem:** Client có thể yêu cầu giá trị rất lớn hoặc không hợp lệ.  
**Why:** Không có server-side paging contract.  
**Production impact:** DB/memory/network pressure và abuse dễ dàng.  
**Severity:** High.  
**Recommended fix:** Clamp page size, ví dụ 1–200; ưu tiên cursor/keyset pagination cho audit stream lớn.

### 6. Contains search `%term%` có thể rất đắt

**Problem:** Leading wildcard thường khiến B-tree index thông thường không hỗ trợ seek theo prefix như truy vấn `term%`.  
**Why:** Search requirement và index strategy không khớp.  
**Production impact:** Scan lớn, CPU/I/O tăng khi audit table phát triển.  
**Severity:** Medium.  
**Recommended fix:** Làm rõ search semantics; dùng exact/prefix search khi đủ; cân nhắc full-text/search engine nếu business thật sự cần substring/full-text.

### 7. Không truyền cancellation token

**Problem:** Open/execute/read không dùng `HttpContext.RequestAborted`.  
**Why:** Query tiếp tục chạy sau khi client disconnect nếu provider/runtime chưa tự hủy.  
**Production impact:** Lãng phí DB connection và compute.  
**Severity:** Medium.  
**Recommended fix:** Propagate request cancellation.

### 8. Không có query timeout/pagination strategy rõ ràng

**Problem:** Endpoint có thể giữ connection lâu với expensive query.  
**Why:** Không có explicit operational bound ngoài default behavior.  
**Production impact:** Connection pool pressure và cascading latency.  
**Severity:** Medium.  
**Recommended fix:** Bounded query, page size, suitable command timeout, index/search design và monitoring.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly SqlConnectionFactory _connections;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        SqlConnectionFactory connections,
        ITenantAccessService tenantAccess,
        ILogger<AuditController> logger)
    {
        _connections = connections;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize(Policy = "AuditReader")]
    public async Task<IActionResult> Search(
        [FromQuery] string? emailPrefix,
        [FromQuery] DateTime? before,
        [FromQuery] int take = 100,
        CancellationToken ct = default)
    {
        var tenantId = await _tenantAccess.GetAuthorizedTenantAsync(User, ct);
        if (tenantId is null)
            return Forbid();

        take = Math.Clamp(take, 1, 200);
        before ??= DateTime.UtcNow;

        const string sql = """
            SELECT TOP (@Take)
                   Id, Action, CreatedAt, UserEmail
            FROM AuditLogs
            WHERE TenantId = @TenantId
              AND CreatedAt < @Before
              AND (@EmailPrefix IS NULL OR UserEmail LIKE @EmailPrefix + '%')
            ORDER BY CreatedAt DESC, Id DESC;
            """;

        await using var connection = await _connections.OpenAsync(ct);
        await using var command = new SqlCommand(sql, connection)
        {
            CommandTimeout = 10
        };

        command.Parameters.Add("@Take", SqlDbType.Int).Value = take;
        command.Parameters.Add("@TenantId", SqlDbType.NVarChar, 64).Value = tenantId;
        command.Parameters.Add("@Before", SqlDbType.DateTime2).Value = before.Value;
        command.Parameters.Add("@EmailPrefix", SqlDbType.NVarChar, 256).Value =
            string.IsNullOrWhiteSpace(emailPrefix)
                ? DBNull.Value
                : emailPrefix.Trim();

        var started = Stopwatch.GetTimestamp();
        var result = new List<AuditListItem>(take);

        await using var reader = await command.ExecuteReaderAsync(ct);
        while (await reader.ReadAsync(ct))
        {
            result.Add(new AuditListItem(
                reader.GetGuid(0),
                reader.GetString(1),
                reader.GetDateTime(2),
                MaskEmail(reader.GetString(3))));
        }

        _logger.LogInformation(
            "Audit search completed. ResultCount={ResultCount} ElapsedMs={ElapsedMs}",
            result.Count,
            Stopwatch.GetElapsedTime(started).TotalMilliseconds);

        return Ok(result);
    }

    private static string MaskEmail(string email)
    {
        var at = email.IndexOf('@');
        return at <= 1 ? "***" : $"{email[0]}***{email[at..]}";
    }

    public sealed record AuditListItem(
        Guid Id,
        string Action,
        DateTime CreatedAt,
        string UserEmail);
}
```

Đây là một reference direction, không phải schema bắt buộc. Nếu một support user được phép truy cập nhiều tenant, `ITenantAccessService` nên xác minh requested tenant nằm trong server-side authorized tenant set thay vì chỉ lấy một tenant. Nếu raw detail là nghiệp vụ bắt buộc, nên có endpoint/quyền riêng và audit việc truy cập dữ liệu nhạy cảm.

## Trade-offs

Parameterized SQL giải quyết injection nhưng không tự giải quyết authorization hay expensive query. Prefix search dễ index hơn substring search nhưng thay đổi UX. Full-text/search service mạnh hơn cho text search lớn nhưng tăng cost, data synchronization và privacy surface. Masking mặc định giảm exposure nhưng support có thể cần workflow “reveal” được phân quyền/audit riêng. Keyset pagination ổn định hơn offset trên bảng audit lớn nhưng API contract phức tạp hơn.

## Cách kiểm thử

1. **Security test:** gửi payload chứa quote/comment/operator trong mọi query parameter; xác nhận không thay đổi SQL semantics.
2. **Authorization test:** user tenant A yêu cầu tenant B; phải bị từ chối và không trả bất kỳ record B nào.
3. **Data exposure test:** role AuditReader thông thường không nhận raw IP/detail; role đặc quyền chỉ nhận khi policy cho phép.
4. **Load/database test:** table lớn với realistic distribution; kiểm tra execution plan, reads, latency và connection-pool behavior.
5. **Cancellation/failure test:** client disconnect hoặc DB timeout; request dừng hợp lý và log không chứa email/search text raw.

## Quan sát trong production

Theo dõi request latency p50/p95/p99, DB command duration, timeout count, rows returned, rejected authorization count, connection-pool pressure và slow-query telemetry. Audit quyền truy cập dữ liệu nhạy cảm theo actor/resource/action. Không log access token, raw SQL chứa user input, raw audit detail hoặc full email nếu không có yêu cầu nghiệp vụ rõ ràng.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product bắt buộc hỗ trợ substring search trên hàng trăm triệu audit rows, bạn thiết kế search/index thế nào?
2. Parameterization có ngăn được mọi loại injection hoặc abuse không? Những lớp bảo vệ nào vẫn cần?
3. Nếu một support engineer được cấp quyền tạm thời truy cập tenant khác trong 30 phút, bạn thiết kế authorization và audit trail ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào distributed job correctness: một database status flag không tự tạo mutual exclusion; retry phải được thiết kế cùng idempotency; external side effect và database commit tạo ra crash window cần reconciliation/state machine thay vì cố che bằng transaction dài.

Challenge 2 tập trung vào security boundary: authentication không đồng nghĩa authorization; tenant scope phải đến từ nguồn đáng tin cậy; parameterization, least privilege, data minimization và bounded queries phải được thiết kế cùng nhau.

## Mẫu tư duy cần nhớ

- Xác định **ownership/atomicity boundary** trước khi xử lý concurrency.
- Thiết kế **retry cùng idempotency và recovery**, không thêm retry độc lập.
- Xem mọi client input là **untrusted**, kể cả tenant ID và page size.
- Tách **authentication → authorization → data minimization** thành ba câu hỏi riêng.
- Treat observability as part of the design nhưng **không biến logs thành nơi rò rỉ PII/secrets**.
