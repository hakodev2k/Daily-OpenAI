# Câu 1 — File import 80 MB làm memory tăng gấp nhiều lần: .NET GC và LOH đang làm gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** C#, .NET runtime, GC, LOH, allocation, ASP.NET Core, streaming, memory profiling, performance

## Bối cảnh

Một ASP.NET Core API trên .NET 8 nhận file CSV để import dữ liệu. Flow hiện tại:

- request body được copy vào một `MemoryStream`;
- sau đó gọi `ToArray()`;
- parser tạo `List<RowDto>` cho toàn bộ file;
- một phần dữ liệu được serialize lại thành JSON để audit;
- dữ liệu được ghi SQL Server theo batch;
- request chỉ trả về khi toàn bộ import hoàn tất.

File thông thường chỉ 2–5 MB, nhưng có lúc 30–80 MB. Khi nhiều user import đồng thời:

- working set tăng nhanh;
- Gen 2 GC tăng;
- p95/p99 tăng mạnh dù CPU chưa luôn đạt 100%;
- một số instance restart vì memory pressure;
- developer thấy `GC.Collect()` làm memory giảm trong local test và đề xuất gọi sau mỗi import;
- một developer khác cho rằng chỉ cần đổi `List<RowDto>` thành `IEnumerable<RowDto>`.

Chưa biết chắc:

- dữ liệu bị copy/materialize bao nhiêu lần;
- parser tạo bao nhiêu strings/objects;
- bao nhiêu import chạy đồng thời;
- transaction/database batch giữ object sống bao lâu;
- audit requirement có thực sự cần giữ toàn bộ payload;
- business có chấp nhận asynchronous import hay không.

## Câu hỏi chính

Hãy giải thích vì sao file 50–80 MB có thể tạo managed-memory footprint lớn hơn nhiều kích thước file, Large Object Heap và Gen 2 GC liên quan thế nào, vì sao `GC.Collect()` không phải root-cause fix, và bạn sẽ dùng evidence để redesign endpoint giảm peak memory mà vẫn giữ correctness.

## Câu hỏi làm rõ nên cân nhắc

1. File format có thể parse tuần tự hay business rule cần nhìn toàn bộ file cùng lúc?
2. Số import đồng thời tối đa trên một instance là bao nhiêu?
3. Audit cần raw file, normalized rows hay chỉ metadata/hash?
4. Import có bắt buộc atomic all-or-nothing không?
5. Hiện đã có allocation profile, heap/LOH size, GC pause và memory-per-request metrics chưa?

## Gợi ý tư duy

### Gợi ý 1

Đừng chỉ nhìn file size; hãy liệt kê mọi representation của cùng dữ liệu cùng tồn tại trong memory.

### Gợi ý 2

Large arrays/strings có lifetime và collection behavior khác object nhỏ; workload allocation lớn có thể đẩy pressure lên Gen 2/LOH.

### Gợi ý 3

Giải pháp thường nằm ở giảm dữ liệu sống đồng thời: streaming, bounded batching, backpressure và tránh duplicate buffers.

## Cấu trúc trả lời đề xuất

1. Clarify file size, concurrency, atomicity và SLA.
2. Vẽ allocation/lifetime path của một request.
3. Giải thích heap generations, LOH và collection pressure.
4. Xác định duplicate materialization.
5. Thu profiler/runtime metrics.
6. Thiết kế streaming/bounded batches.
7. Thiết kế concurrency limit/backpressure.
8. Xử lý cancellation và transaction boundary.
9. So sánh synchronous và asynchronous import.
10. Load-test và theo dõi sau release.

## Ý chính của câu trả lời tốt

### Bắt buộc

- File size không bằng heap footprint; có thể đồng thời tồn tại request buffer, `MemoryStream`, `byte[]`, decoded strings, DTOs, audit JSON và DB objects.
- Large allocations có thể tạo LOH pressure và kéo theo Gen 2 collections.
- Không mặc định gọi `GC.Collect()` trong normal request path.
- Phải đo allocation rate, heap/LOH, GC pause, working set và concurrent imports.
- `IEnumerable<T>` không tự động đồng nghĩa lazy/streaming nếu producer đã materialize.
- Khi business cho phép, dùng streaming + bounded batch để giảm live set.
- Cần admission/concurrency control cho workload memory-heavy.
- Cancellation phải propagate qua stream/database work.

### Điểm cộng

- Phân biệt managed heap với process working set.
- Dùng staging table + final promote nếu cần all-or-nothing mà không muốn giữ toàn bộ file trong memory.
- Stream file trực tiếp lên Azure Blob Storage rồi xử lý background khi synchronous HTTP không cần thiết.
- Chỉ dùng `ArrayPool<T>`/buffer reuse nếu profiling chứng minh lợi ích và code vẫn an toàn.
- Đo memory-per-MB và p95/p99 dưới load thay vì benchmark một request.

### Senior+

- Thiết kế bounded pipeline đọc → parse → validate → write với số record/buffer tối đa in-flight.
- Định nghĩa failure semantics cho malformed row, DB timeout, duplicate upload, cancellation và partial completion.
- Phân biệt tactical scale-up với structural allocation fix.
- Chọn batch size bằng throughput + memory evidence, không bằng cảm tính.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng allocation graph. Một file 50 MB có thể tồn tại đồng thời dưới nhiều dạng: request/body buffer, `MemoryStream`, kết quả `ToArray()`, decoded text, parser tokens, DTOs, strings trên từng field, collections, audit JSON và database parameters/entities. Vì vậy peak heap có thể lớn hơn input nhiều lần.

Trong .NET, large objects được quản lý trên LOH và được thu gom cùng full/Gen 2 collections. Workload liên tục tạo large arrays/strings ngắn hạn có thể tăng full-collection pressure và tail latency. Tôi không kết luận từ working set một mình; tôi cần runtime metrics và profiler cho workload thật.

Evidence tôi muốn gồm allocation rate, managed heap size, LOH size, Gen 0/1/2 collection count, GC pause, working set, request size, concurrent imports, parse time, DB time và audit serialization time. Tôi có thể dùng `dotnet-counters`, `dotnet-trace`, `dotnet-gcdump`, profiler hoặc Azure diagnostics phù hợp.

Nếu format cho phép streaming, tôi bỏ flow “copy toàn bộ → `ToArray()` → parse toàn bộ → `List`”. Thay vào đó đọc tuần tự, parse record, validate và ghi theo bounded batch. Bản chất quan trọng không phải tên interface mà là không materialize toàn bộ dataset.

Nếu import cần atomic all-or-nothing, tôi không nhất thiết giữ toàn bộ DTO trong memory. Có thể stream vào staging table, validate ở staging, sau đó dùng một transaction ngắn để promote dữ liệu hợp lệ. Nếu business chấp nhận asynchronous processing, API có thể stream file lên Blob Storage, tạo job record và worker xử lý sau. Cách đó giảm HTTP timeout coupling nhưng thêm job state, retry/idempotency và operational complexity.

Tôi cũng đặt max file size và max concurrent large imports. Scale-out không tự giải quyết nếu mỗi instance vẫn cho phép quá nhiều memory-heavy requests cùng lúc.

`GC.Collect()` sau mỗi import thường chỉ ép runtime thu gom ở thời điểm do application chọn, có thể làm pause/throughput xấu hơn. Tôi chỉ xem xét forced collection trong lifecycle rất đặc biệt có bằng chứng, không dùng như policy của endpoint.

Testing phải chạy nhiều file sizes và concurrency levels, có malformed file, cancellation, DB timeout và large burst. Success được chứng minh bằng peak heap thấp hơn, ít Gen 2/GC pause hơn và p95/p99 ổn định hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không coi file 50 MB tương đương 50 MB memory. Flow hiện tại có thể giữ nhiều bản sao cùng lúc: `MemoryStream`, `byte[]`, strings/DTOs, audit JSON và DB objects. Large allocations còn tạo LOH/Gen 2 pressure nên tail latency có thể tăng dù CPU chưa max.

Em sẽ profile allocation, heap/LOH, GC pause, working set và concurrent imports trước. Nếu format cho phép, em chuyển sang streaming + bounded batches, thêm concurrency limit và propagate cancellation. Nếu cần all-or-nothing, em cân nhắc staging table thay vì giữ cả file trong RAM; nếu import dài, có thể stream lên Blob rồi xử lý background.

Em không dùng `GC.Collect()` như fix mặc định, và `IEnumerable<T>` cũng không chứng minh dữ liệu được stream. Sau thay đổi em load-test theo file size/concurrency thật và so peak heap, Gen 2, throughput, p95/p99 trước-sau.”

## Câu hỏi đào sâu

1. Nếu business yêu cầu file 2 GB phải all-or-nothing, bạn giữ atomicity mà không giữ 2 GB dữ liệu trong memory thế nào?
2. Nếu streaming giảm memory nhưng DB throughput giảm vì batch quá nhỏ, bạn chọn batch size theo evidence nào?
3. Một teammate muốn dùng `ArrayPool<byte>` ở mọi nơi; khi nào bạn phản đối?

## Lỗi trả lời thường gặp

- Gọi mọi memory pressure là “memory leak”.
- Dùng `GC.Collect()` sau mỗi request.
- Cho rằng `IEnumerable<T>` tự động streaming.
- Tăng RAM nhưng không đo allocation amplification.
- Không giới hạn concurrency của workload memory-heavy.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng RAM hoặc gọi GC thủ công.
- **3–4:** Nhận ra allocation lớn nhưng không có evidence plan.
- **5–6:** Hiểu materialization, LOH/GC pressure, streaming và batching.
- **7–8:** Có bounded pipeline, concurrency control, transaction strategy và load testing.
- **9–10:** Phân tích được lifetime, atomicity, failure semantics và chứng minh recommendation bằng runtime evidence.

# Câu 2 — Azure Function xử lý cùng một job nhiều lần sau scale/restart và downstream bị retry storm

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure Functions, retries, idempotency, background processing, scale-out, external APIs, SQL Server, observability, incident response

## Bối cảnh

Một Azure Function xử lý job đồng bộ dữ liệu giá sản phẩm từ một queue-triggered workflow. Mỗi message chứa `ProductId` và `SyncVersion`. Function:

- đọc product từ SQL Server;
- gọi external pricing provider;
- cập nhật giá đã normalize vào database;
- ghi audit log.

Sau một đợt traffic tăng và một deployment:

- một số `ProductId` được xử lý nhiều lần gần nhau;
- external provider bắt đầu trả 429;
- queue backlog tăng;
- Application Insights có nhiều retry/exception records;
- một số executions bị host restart hoặc timeout;
- team tăng retry count để “đảm bảo không mất job”;
- có nhiều Function instances cùng scale-out;
- audit table ghi nhiều bản ghi cho cùng product/version;
- một developer đề xuất dùng distributed lock toàn hệ thống;
- một developer khác cho rằng queue trigger phải bảo đảm mỗi message chỉ chạy một lần.

Chưa biết chắc:

- trigger/retry configuration hiện tại;
- message delivery count;
- retry đang xảy ra ở trigger layer, HTTP layer hay cả hai;
- provider có idempotency key/rate-limit headers hay không;
- database update có unique constraint theo product/version không;
- host timeout và execution duration distribution;
- poison/dead-letter handling hiện tại;
- deployment/restart xảy ra ở thời điểm nào trong execution.

## Câu hỏi chính

Bạn sẽ stabilize incident và chứng minh duplicate/retry xuất phát từ đâu như thế nào? Sau đó hãy thiết kế processing flow để scale-out, retry, host restart hoặc duplicate delivery không tạo duplicate business side effects và không biến downstream degradation thành retry storm.

## Câu hỏi làm rõ nên cân nhắc

1. Trigger dùng queue/service nào và delivery/retry semantics cụ thể hiện tại ra sao?
2. Một duplicate execution có cùng message ID/delivery count hay là producer đã phát hai messages?
3. Provider có hỗ trợ idempotency key hoặc lookup theo `ProductId + SyncVersion` không?
4. Tổng worst-case attempts là bao nhiêu khi cộng trigger retry và HTTP retry?
5. Business cho phép cùng product/version được xử lý lại nếu kết quả cuối cùng giống nhau hay audit phải exactly-one logical operation?

## Gợi ý tư duy

### Gợi ý 1

Scale-out làm nhiều executions song song; correctness không nên dựa vào giả định một process hoặc một lần delivery.

### Gợi ý 2

Retry ở nhiều layer có thể nhân số attempts. 429 là signal cần backoff/rate-limit awareness, không phải lý do retry mạnh hơn.

### Gợi ý 3

Hãy thiết kế operation idempotency trước khi nghĩ đến distributed lock toàn cục.

## Cấu trúc trả lời đề xuất

1. Đánh giá business impact và stop amplification.
2. Correlate message/execution/provider attempts.
3. Phân biệt producer duplicate, redelivery, retry và restart.
4. Xác định failure windows.
5. Thiết kế idempotency/state transitions.
6. Rationalize retry ownership.
7. Điều chỉnh concurrency/rate limit/backpressure.
8. Thiết kế poison/dead-letter/reconciliation.
9. Failure-test restart/duplicate/429.
10. Monitor recovery và regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định queue-triggered Function chạy exactly once.
- Duplicate delivery/retry/restart phải được coi là failure mode bình thường.
- Correlation phải có message ID, `ProductId`, `SyncVersion`, execution/attempt và downstream request ID.
- Retry cần bounded; tránh retry chồng nhiều tầng.
- 429 cần backoff và tôn trọng provider capacity/rate-limit contract.
- Consumer phải idempotent theo business operation.
- Không dùng global distributed lock mặc định vì có thể tạo bottleneck/single contention point.
- Poison/permanent failures cần dead-letter/recovery path.
- Scale-out/concurrency phải phù hợp downstream capacity.

### Điểm cộng

- Dùng unique constraint/idempotency record theo `ProductId + SyncVersion`.
- Nếu provider hỗ trợ idempotency key, dùng stable key cho mọi attempt cùng logical operation.
- Nếu external result không chắc chắn sau timeout, có reconciliation/query-before-retry strategy.
- Tách transient lỗi khỏi validation/business lỗi.
- Có metric retry amplification factor và queue-age SLO.

### Senior+

- Phân tích crash window giữa external side effect và local commit.
- Thiết kế state machine như Pending → Processing → ExternalConfirmed → Completed, kèm recovery cho trạng thái ambiguous.
- Nếu producer ghi SQL rồi enqueue rời rạc, cân nhắc Outbox/CDC phù hợp để tránh dual-write gap.
- Đưa ra concurrency/rate budget thay vì tăng instance/threads theo cảm tính.

## Hướng giải quyết tham khảo

Tôi sẽ stabilize bằng cách giảm amplification trước. Nếu provider đang trả 429, tăng retry count và concurrency có thể làm outage dài hơn. Tôi cần xem queue age, execution rate, delivery count, HTTP attempts và provider throttling cùng timeline.

Tôi chọn vài `ProductId + SyncVersion` bị duplicate và dựng chuỗi: enqueue → execution start → provider call → DB update → audit → completion. Tôi phân biệt bốn nguồn: producer phát duplicate, broker redelivery, Function retry sau exception và HTTP retry bên trong một execution.

Một Function/queue trigger không nên được thiết kế với assumption “mỗi message đúng một lần”. Nếu process crash sau provider call nhưng trước local commit/ack, logical operation có thể chạy lại. Do đó idempotency phải nằm ở business boundary.

Local DB có thể có idempotency record hoặc unique constraint trên `ProductId + SyncVersion`. Một attempt nhận thấy trạng thái Completed thì có thể no-op/return kết quả cũ. Nhưng local uniqueness một mình chưa làm external call atomic. Nếu provider hỗ trợ idempotency key, mọi attempt của cùng logical operation phải dùng cùng stable key. Nếu provider không hỗ trợ và timeout khiến outcome không chắc chắn, cần query/reconciliation trước khi create/update lại.

Tôi rationalize retry ownership: một bounded retry policy cho transient HTTP failures với exponential backoff/jitter khi phù hợp; trigger retry phải tính tổng duration/attempts. Không retry validation failure. Với 429, tôn trọng `Retry-After` hoặc provider contract nếu có và giới hạn concurrent calls.

Distributed lock toàn hệ thống thường quá rộng. Nếu thật sự cần serialize theo product, có thể dùng per-key coordination hoặc optimistic concurrency, nhưng lựa chọn phải dựa trên invariant và load. Idempotency vẫn cần vì lock không ngăn crash/retry sau khi lock release.

Poison message phải đi dead-letter hoặc recovery store sau ngưỡng rõ, có alert/runbook/replay có kiểm soát. Replay chỉ sau khi root cause/idempotency đủ an toàn.

Testing cần ép host restart sau provider success, duplicate message song song, 429 burst, timeout-unknown-outcome, DB deadlock/transient failure và poison data. Metrics gồm queue age/depth, delivery count, retries theo layer, 429 rate, external latency, duplicate/no-op count, dead-letter count và end-to-end sync lag.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xử lý đây là correctness + retry-amplification incident. Trước hết em giảm concurrency/retry nếu provider đang 429, rồi correlate MessageId, ProductId, SyncVersion, Function execution và HTTP attempt để biết duplicate đến từ producer, redelivery hay retry layer nào.

Em không giả định queue trigger exactly-once. Consumer phải idempotent theo business operation, ví dụ unique key ProductId + SyncVersion. Nếu provider hỗ trợ idempotency key, em dùng stable key cho mọi attempt. Nếu timeout làm outcome không chắc chắn, em reconcile trước khi retry side effect.

Retry phải bounded và có một ownership rõ để tránh trigger retry nhân với HTTP retry. 429 phải backoff/rate-limit-aware. Poison work đi dead-letter, scale-out/concurrency phải theo downstream capacity. Sau đó em failure-test restart sau side effect, duplicate delivery, 429 burst và timeout ambiguous; monitor queue age, attempts, throttling, duplicate/no-op và DLQ.”

## Câu hỏi đào sâu

1. Nếu Function crash ngay sau provider đã cập nhật giá nhưng trước DB commit, bạn recover thế nào khi provider không hỗ trợ idempotency key?
2. Một teammate muốn một Redis distributed lock cho toàn bộ pricing sync để chắc chắn không duplicate; bạn phản biện thế nào?
3. Nếu backlog rất lớn sau khi provider hồi phục, bạn drain backlog mà không tạo burst overload mới ra sao?

## Lỗi trả lời thường gặp

- Giả định Azure Function/queue trigger exactly-once.
- Tăng retry count khi downstream đang 429.
- Không tính retry multiplication giữa trigger và HTTP layer.
- Dùng global distributed lock thay cho idempotency.
- Không xử lý timeout có outcome không chắc chắn.

## Thang điểm 0–10

- **0–2:** Chỉ tăng retries hoặc lock.
- **3–4:** Nhận ra duplicate delivery nhưng thiếu idempotency/failure-window reasoning.
- **5–6:** Có bounded retry, idempotency, DLQ và evidence plan.
- **7–8:** Có rate-aware recovery, ambiguous-outcome handling, concurrency budget và failure injection.
- **9–10:** Thiết kế được protocol recoverable qua scale/restart/retry với observability và trade-offs rõ.

# Câu 3 — Modernize ASP.NET MVC + jQuery sang Vue/React mà không phá SEO, CMS workflow và release safety

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** frontend modernization, Vue.js, React.js, ASP.NET Core, CMS integration, SEO, accessibility, Akamai/CDN, APIs, deployment, architecture trade-offs

## Bối cảnh

Một marketing/e-commerce website lâu năm dùng ASP.NET MVC server-rendered views và jQuery. CMS quản lý landing pages, campaign content và SEO metadata. Akamai CDN cache public pages.

Team muốn modernize vì:

- jQuery code khó maintain;
- interactive components ngày càng phức tạp;
- frontend tests ít;
- build/release frontend gắn chặt backend;
- Product muốn trải nghiệm tương tác tốt hơn.

Hai proposal:

1. rewrite toàn bộ thành SPA React và dùng CMS chỉ như headless content API;
2. giữ server-rendered site và migrate từng interactive area sang Vue.js hoặc React.js.

Constraints:

- organic search rất quan trọng;
- Core Web Vitals/Lighthouse đang được theo dõi;
- editor cần preview/publish workflow ổn định;
- canonical URLs, metadata, structured data và redirects không được regression;
- authenticated/personalized areas không được cache public;
- release vẫn phải diễn ra trong khi migration kéo dài;
- team backend có kinh nghiệm Vue/React nhưng không phải dedicated frontend platform team;
- một số legacy browser integration và third-party scripts vẫn tồn tại.

Chưa biết chắc:

- page nào thực sự cần client-side interactivity cao;
- SSR/SSG/headless capability của CMS stack hiện tại;
- traffic split theo page type;
- current JavaScript bundle cost;
- CDN cache hit ratio;
- editor preview có phụ thuộc server rendering không;
- team có nhu cầu deploy frontend độc lập thật hay chỉ muốn code boundary sạch hơn.

## Câu hỏi chính

Hãy đề xuất modernization strategy theo từng giai đoạn. So sánh full SPA/headless rewrite với incremental islands/components, giải thích cách giữ CMS editorial workflow, SEO/crawlability, accessibility, performance, CDN caching, API/security boundaries, testing và rollback. Nêu tiêu chí khiến bạn chọn Vue, React hoặc chưa cần framework cho một phần trang.

## Câu hỏi làm rõ nên cân nhắc

1. Những page/component nào có interaction/state complexity đủ lớn để framework tạo giá trị?
2. Business có yêu cầu deploy frontend/backend độc lập hay chỉ muốn giảm coupling trong codebase?
3. CMS preview/personalization/localization hiện hoạt động thế nào?
4. Search bots và social crawlers cần server-rendered metadata/content tới mức nào?
5. Existing CDN/cache key có dimensions locale, authentication, personalization hoặc campaign variants không?

## Gợi ý tư duy

### Gợi ý 1

“Modern frontend” không đồng nghĩa toàn bộ website phải trở thành SPA.

### Gợi ý 2

SEO, editor preview và CDN behavior là architecture constraints, không phải checklist xử lý sau migration.

### Gợi ý 3

Hãy tối ưu migration risk: chọn component/page có boundary rõ, đo bundle/performance và giữ rollback path.

## Cấu trúc trả lời đề xuất

1. Inventory page types, interactions, SEO/editor requirements.
2. Baseline performance/JS/test coverage.
3. Xác định rendering strategy theo page type.
4. Định nghĩa frontend/backend API boundaries.
5. Chọn incremental migration sequence.
6. Thiết kế CMS preview/content contracts.
7. Thiết kế CDN/cache/security semantics.
8. Thiết kế testing/observability.
9. Rollout/canary/rollback.
10. Đặt criteria cho full headless hoặc independent frontend deployment sau này.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định full SPA rewrite.
- Server rendering có thể tiếp tục cho content/SEO-critical pages.
- Chỉ dùng Vue/React ở interactive zones khi complexity justify.
- CMS vẫn sở hữu editorial content/model/workflow; frontend framework không nên làm editor mất preview/publish semantics.
- API contract phải tách khỏi internal CMS model và có authorization phù hợp.
- Canonical, metadata, structured data, redirects và crawlability phải regression-test.
- CDN cache key/invalidation phải phân biệt public với authenticated/personalized content.
- Migration phải incremental và rollbackable.
- Performance phải đo bằng bundle/runtime/network/Core Web Vitals, không chỉ Lighthouse score local.
- Accessibility cần kiểm thử keyboard/focus/semantics.

### Điểm cộng

- Dùng islands/progressive enhancement cho component tương tác cao, tránh hydrate toàn page nếu không cần.
- Tách shared frontend design/components mà không buộc tách deployment ngay.
- Playwright E2E cho critical journeys, visual/SEO assertions ở mức phù hợp.
- Feature flag/canary theo component hoặc route để rollback.
- Phân tích third-party scripts vì chúng có thể chiếm phần lớn performance budget.

### Senior+

- Đưa ra tiêu chí khi nào headless/SPA thật sự đáng giá: multi-channel reuse, independent team ownership, rendering infrastructure mature, preview solved, API contracts stable.
- Thiết kế cache strategy theo locale/personalization/content version.
- Có performance budget và telemetry real-user thay vì chỉ synthetic.
- Có strangler strategy cho routes/components và migration governance tránh hai frontend stacks tồn tại vô hạn.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng inventory, không bằng framework. Phân loại pages: content-heavy/SEO-critical, commerce/listing, authenticated application, và các widgets có interaction phức tạp. Với mỗi nhóm, tôi đo current bundle size, JavaScript execution, Core Web Vitals/RUM nếu có, CDN hit ratio, editor workflow và regression risk.

Nếu phần lớn public marketing pages là server-rendered content với một vài widgets, full SPA thường thêm JavaScript/hydration cost và làm SEO/preview/deployment phức tạp mà chưa chắc tạo giá trị. Tôi sẽ giữ server-rendered shell và migrate từng interactive region sang Vue hoặc React. Một component như product filter, booking widget hoặc account panel có thể được mount vào server-rendered markup; static content vẫn render từ server.

CMS giữ ownership của editorial structure, localization, metadata và publish workflow. Tôi không expose raw internal CMS model trực tiếp cho frontend. Nếu component cần data động, backend cung cấp stable API/DTO contract. Preview mode cần route/cache behavior riêng để editor thấy draft content mà không leak draft ra public cache.

Vue vs React không nên chọn theo popularity. Nếu team đã có reusable Vue components và skills mạnh, Vue có thể giảm adoption cost; nếu ecosystem/product requirements hoặc existing React components mạnh hơn, React có thể hợp lý. Với component rất nhỏ, plain TypeScript/progressive enhancement có thể rẻ hơn cả hai. Tôi đặt một default framework để tránh fragmentation, nhưng cho phép exception có lý do.

CDN caching phải được review cùng rendering. Public server-rendered pages có thể cache edge theo URL/locale/content variant phù hợp. Authenticated/personalized responses không được vô tình cache public. Publish cần invalidation/purge strategy và observable failure behavior.

SEO regression suite nên kiểm tra status codes, redirects, canonical, title/meta, structured data, robots/crawlability và server-rendered content quan trọng. Tôi không dựa vào client JavaScript để “hy vọng bot render được” nếu organic search là business-critical constraint.

Performance budget nên gồm JS transferred, main-thread work, LCP/INP/CLS và third-party impact. Framework migration chỉ được coi là thành công nếu user metrics không xấu đi. Third-party marketing tags thường phải được quản lý riêng vì rewrite app nhưng giữ script bloat vẫn không cải thiện trải nghiệm.

Testing gồm unit/component tests cho logic, integration/API tests và Playwright E2E cho critical journeys/editor-preview paths. Accessibility checks có automated scan cộng manual keyboard/focus review cho interaction phức tạp.

Rollout theo strangler: chọn một route/component có boundary rõ, feature flag/canary, compare errors/performance/SEO, rồi mở rộng. Legacy jQuery chỉ được giảm dần theo roadmap; cần rule không thêm jQuery mới trừ emergency exception để tránh migration kéo dài vô hạn.

Tôi chỉ chuyển full headless/SPA khi business/organization chứng minh lợi ích: nhiều channels cần reuse content/API, frontend team có ownership độc lập, preview/editor tooling được giải quyết, SSR/edge rendering có operational maturity và independent deployment tạo giá trị thật. Nếu không, hybrid/server-first architecture có thể đơn giản và an toàn hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không rewrite thành SPA chỉ vì muốn bỏ jQuery. Trước hết em phân loại page theo SEO/content/interactivity, đo current bundle, Core Web Vitals và editor workflow. Với public content pages, em giữ server-rendered shell và migrate từng interactive area sang một framework mặc định — Vue hoặc React theo team capability — còn component đơn giản có thể chỉ cần TypeScript.

CMS tiếp tục sở hữu editorial content, preview, localization và metadata. Interactive components dùng stable APIs thay vì phụ thuộc internal CMS model. Em review CDN cache key/invalidation để public và personalized content không trộn nhau, đồng thời regression-test canonical, redirects, structured data và crawlability.

Migration đi theo strangler/component/route, có feature flag và rollback. Em dùng Playwright cho critical flows, accessibility tests và real-user performance metrics. Chỉ khi có nhu cầu multi-channel, independent frontend ownership/deployment và SSR/headless maturity rõ thì em mới cân nhắc full headless/SPA.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu mọi campaign page có preview draft realtime nhưng CDN cache public rất mạnh, bạn tách preview/public delivery thế nào?
2. CTO nói “React SPA sẽ tốt cho SEO vì Google render JavaScript được”; bạn phản biện bằng engineering risk và evidence gì?
3. Nếu sau 6 tháng hệ thống tồn tại cả jQuery, Vue và React, bạn đặt governance nào để tránh modernization biến thành permanent fragmentation?

## Lỗi trả lời thường gặp

- Full SPA rewrite chỉ vì “frontend hiện đại”.
- Chọn framework theo trend thay vì team/product constraints.
- Chỉ test UI behavior mà bỏ canonical/redirect/structured-data regression.
- Không phân biệt public CDN caching với authenticated/personalized responses.
- Không có deprecation/governance plan cho jQuery nên migration kéo dài vô hạn.

## Thang điểm 0–10

- **0–2:** Chỉ chọn framework và rewrite.
- **3–4:** Có incremental migration nhưng thiếu SEO/CMS/CDN/testing reasoning.
- **5–6:** Có rendering strategy, API boundary, SEO/performance/accessibility và rollout.
- **7–8:** Có preview/cache semantics, performance budget, Playwright, strangler và framework governance.
- **9–10:** Cân bằng editorial workflow, SEO, operability, team capability và cost of complexity; nêu rõ điều kiện khiến full headless/SPA trở nên hợp lý.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Memory performance phải được phân tích theo **allocation + lifetime + concurrency**, không theo kích thước input đơn lẻ.
- LOH/Gen 2 pressure thường là hệ quả của large live sets và repeated materialization; forced GC không thay thế thiết kế dữ liệu/streaming tốt.
- Azure Functions/queue processing phải giả định duplicate delivery, retry và host restart; correctness cần business idempotency và bounded retries.
- Retry và scale-out có thể tạo feedback loop khi downstream bị throttling; backpressure/rate-awareness là một phần của reliability.
- Frontend modernization là bài toán rendering, CMS workflow, SEO, performance, CDN, testing và team ownership — không chỉ là lựa chọn Vue hay React.

## Mẫu tư duy cần nhớ

1. **Measure before optimizing:** chứng minh allocation, retry amplification hoặc frontend cost trước khi sửa.
2. **Design retry together with idempotency:** duplicate delivery không được biến thành duplicate business effect.
3. **Treat restarts and scale-out as normal failure modes.**
4. **Modernize incrementally with rollbackable boundaries.**
5. **Choose framework/architecture complexity only when requirements trả được chi phí.**
