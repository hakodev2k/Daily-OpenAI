# Câu 1 — Tối ưu parser bằng `Span<T>` nhưng lại muốn giữ dữ liệu sau khi method kết thúc: runtime đang bảo vệ bạn khỏi điều gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, .NET 8, `Span<T>`, `ReadOnlySpan<T>`, `Memory<T>`, stack/heap lifetime, slicing, allocations, async boundaries, API design, performance measurement

## Bối cảnh

Một ASP.NET Core API nhận payload dạng text lớn từ một external integration. Team đang tối ưu parser vì profiling cho thấy nhiều allocation nhỏ khi dùng `Substring`.

Một developer refactor code theo hướng:

```csharp
public static ReadOnlySpan<char> ExtractAccountCode(string input)
{
    var span = input.AsSpan();
    var separator = span.IndexOf('|');

    if (separator < 0)
        return ReadOnlySpan<char>.Empty;

    return span[..separator];
}
```

Đoạn này được dùng ngay trong cùng call stack thì ổn. Sau đó team muốn mở rộng parser để:

- giữ các slices lại trong một object rồi xử lý ở bước sau;
- truyền một slice qua `await` tới một asynchronous validation step;
- parse dữ liệu từ pooled buffer thay vì từ `string`;
- giảm allocation nhưng không làm API trở nên khó dùng hoặc dễ tạo lifetime bug;
- một developer đề xuất “cứ đổi mọi `string` thành `Span<char>` là nhanh hơn”;
- một developer khác muốn trả `ReadOnlyMemory<char>` từ public API nhưng chưa hiểu ownership/lifetime của backing storage.

Chưa có benchmark chứng minh parsing hiện tại thực sự là bottleneck lớn nhất của request.

## Câu hỏi chính

Hãy giải thích `Span<T>`/`ReadOnlySpan<T>` đại diện cho dữ liệu như thế nào, vì sao chúng có các lifetime restriction đặc biệt, vì sao không thể được dùng tự do qua `await` hoặc lưu trong object thông thường như một heap field, và khi nào `Memory<T>`/`ReadOnlyMemory<T>` phù hợp hơn. Sau đó đề xuất một design thực tế cho parser có ít allocation nhưng vẫn an toàn về ownership/lifetime, đồng thời giải thích bạn sẽ đo xem tối ưu này có đáng làm hay không.

## Câu hỏi làm rõ nên cân nhắc

1. Input backing storage là immutable `string`, managed array, pooled array hay unmanaged buffer?
2. Parsed fields cần sống trong bao lâu: chỉ trong synchronous parse step, trong toàn request hay được queue sang background processing?
3. Validation asynchronous có thực sự cần giữ slice hay có thể parse thành domain value nhỏ trước `await`?
4. Buffer pool có ownership contract rõ về thời điểm trả buffer hay không?
5. Profiling hiện tại cho thấy allocation/GC chiếm bao nhiêu phần trăm request latency và throughput?

## Gợi ý tư duy

### Gợi ý 1

Đừng coi `Span<T>` như “array nhanh hơn”. Hãy reasoning về một **view trên vùng nhớ** và lifetime của vùng nhớ đó.

### Gợi ý 2

Một abstraction có thể giảm allocation nhờ không copy dữ liệu, nhưng điều đó đồng nghĩa caller phải tôn trọng ownership và lifetime chặt chẽ hơn.

### Gợi ý 3

Tách hot synchronous parsing path khỏi data representation cần sống lâu hoặc đi qua asynchronous boundary.

## Cấu trúc trả lời đề xuất

1. Xác định backing storage và required lifetime.
2. Giải thích slicing/view semantics.
3. Giải thích restriction của stack-only/byref-like data.
4. Phân biệt `Span<T>` và `Memory<T>`.
5. Xác định chỗ nên parse/copy thành stable domain value.
6. Thiết kế ownership nếu dùng pooled buffer.
7. So sánh allocation saving với complexity cost.
8. Benchmark/measure.
9. Test lifetime, correctness và failure paths.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Span<T>`/`ReadOnlySpan<T>` là view lên một contiguous region of memory; slicing thường tạo view khác thay vì copy nội dung.
- `Span<T>` là `ref struct`, có lifetime restrictions nhằm ngăn reference tới memory sống ngắn bị escape sang nơi sống lâu hơn.
- Không nên thiết kế như thể `Span<T>` có thể được giữ trong ordinary heap object hoặc sống tự do xuyên asynchronous suspension.
- `Memory<T>`/`ReadOnlyMemory<T>` là heap-storable representation phù hợp hơn khi view cần sống qua async boundaries hoặc được giữ trong object, nhưng backing storage vẫn phải có ownership/lifetime hợp lệ.
- Nếu dùng pooled array, việc trả buffer về pool trong khi `Memory<T>` vẫn còn được sử dụng là correctness bug dù code compile.
- `Span<T>` không tự làm mọi code nhanh hơn; hiệu quả đến từ access pattern và việc tránh allocation/copy khi hot path thực sự bị allocation-bound.
- Cần measure trước khi biến public API thành low-level memory-oriented API.

### Điểm cộng

- Với input là `string`, `ReadOnlySpan<char>` rất phù hợp cho synchronous parse/split/compare mà không tạo substring tạm.
- Nếu kết quả thực sự cần lưu lâu, parse thành typed immutable values như `AccountCode`, `Guid`, `int`, enum hoặc tạo `string` copy có chủ đích ở boundary cần ownership độc lập.
- Nếu async validation chỉ cần account code nhỏ, có thể materialize code trước `await` thay vì cố kéo span xuyên boundary.
- Nếu buffer được pooled, define owner rõ: owner giữ buffer cho tới khi mọi consumer hoàn tất, rồi mới return buffer.
- BenchmarkDotNet hoặc representative load/profile nên so allocation, throughput và p95 thay vì chỉ microbenchmark một operation không phản ánh request path.

### Senior+

- Nhận ra zero-copy design có thể tăng coupling giữa parser và storage lifetime; đôi khi một allocation nhỏ ở stable boundary là trade-off tốt hơn.
- Không expose pooled backing memory cho component có lifetime không kiểm soát nếu ownership contract không thể enforce.
- Phân biệt “copy avoidance” với “data ownership”; borrowed view không trở thành owner chỉ vì được bọc bằng `Memory<T>`.
- Đề xuất API cấp cao trước, dùng span overload nội bộ/hot path khi cần, tránh để optimization detail lan khắp domain layer.

## Hướng giải quyết tham khảo

`ReadOnlySpan<char>` từ `string.AsSpan()` không tạo một substring mới. Nó tạo một view vào vùng ký tự của string. Khi slice:

```csharp
var accountCode = input.AsSpan()[..separator];
```

`accountCode` mô tả một range trên backing data, không phải một string độc lập mới.

Điểm quan trọng là `Span<T>` là byref-like `ref struct`. Runtime/language áp đặt restrictions để một reference tới memory ngắn hạn không escape tới heap hoặc sống lâu hơn memory mà nó trỏ tới. Đây là lý do developer không nên coi nó như ordinary DTO field.

Một design thực tế:

```csharp
public readonly record struct ParsedHeader(
    string AccountCode,
    int Version);

public static bool TryParseHeader(
    ReadOnlySpan<char> input,
    out ParsedHeader header)
{
    header = default;

    var first = input.IndexOf('|');
    if (first <= 0)
        return false;

    var rest = input[(first + 1)..];
    var second = rest.IndexOf('|');
    if (second <= 0)
        return false;

    var accountCodeSpan = input[..first];
    var versionSpan = rest[..second];

    if (!int.TryParse(versionSpan, out var version))
        return false;

    // Deliberate materialization because the result outlives the parse stack.
    var accountCode = accountCodeSpan.ToString();

    header = new ParsedHeader(accountCode, version);
    return true;
}
```

Ở đây span vẫn có lợi vì intermediate scanning/parsing không cần tạo nhiều substring. Nhưng output tạo một stable owned value tại boundary cần sống lâu.

Nếu input là pooled byte buffer và asynchronous code cần giữ memory:

```csharp
public sealed class BufferLease : IDisposable
{
    private byte[]? _buffer;

    public BufferLease(byte[] buffer)
    {
        _buffer = buffer;
    }

    public Memory<byte> Memory =>
        _buffer ?? throw new ObjectDisposedException(nameof(BufferLease));

    public void Dispose()
    {
        var buffer = Interlocked.Exchange(ref _buffer, null);
        if (buffer is not null)
            ArrayPool<byte>.Shared.Return(buffer);
    }
}
```

Ý tưởng ở đây không phải đây là abstraction duy nhất đúng, mà ownership phải explicit: consumer không được dùng `Memory<byte>` sau khi lease trả buffer về pool.

Nếu async validation chỉ cần một account code nhỏ:

```csharp
var accountCode = accountCodeSpan.ToString();
await validator.ValidateAsync(accountCode, cancellationToken);
```

Một allocation có chủ đích ở boundary có thể an toàn và đơn giản hơn nhiều so với cố giữ borrowed memory xuyên nhiều layers.

Tôi chỉ giữ optimization nếu profiling/benchmark cho thấy nó có ý nghĩa. Đo trước và sau:

- allocations/request;
- Gen 0/Gen 1 pressure;
- CPU time trong parser;
- throughput;
- p95/p99 của endpoint dưới representative payload;
- complexity/regression risk.

Nếu parser chỉ chiếm 1% latency còn external API chiếm 80%, span-heavy refactor rộng có thể không đáng chi phí maintainability.

## Mẫu trả lời trong phỏng vấn

“Em xem `Span<T>` là một borrowed view lên memory chứ không phải collection bình thường. Slicing span thường không copy, nên nó hữu ích cho parser hot path. Nhưng `Span<T>` là `ref struct`, bị giới hạn lifetime để reference tới stack hoặc short-lived memory không escape lên heap hay sống qua async suspension một cách unsafe.

Nếu dữ liệu chỉ được parse synchronous, em dùng `ReadOnlySpan<char>` rất thoải mái. Nếu kết quả phải sống qua `await` hoặc được lưu trong object, em chuyển sang stable owned value hoặc `ReadOnlyMemory<T>` khi backing storage có lifetime phù hợp. Với pooled buffer, Memory không giải quyết ownership: em vẫn phải giữ lease tới khi consumer dùng xong rồi mới return buffer.

Em cũng không đổi toàn codebase sang Span chỉ vì nghe là nhanh. Em profile trước, đo allocation và CPU của parser, rồi tối ưu hot path. Ở boundary cần maintainability, em sẵn sàng trả giá một allocation nhỏ để có ownership rõ ràng.”

## Câu hỏi đào sâu

1. Nếu bạn trả `ReadOnlyMemory<byte>` trỏ vào một pooled array rồi array được return ngay sau method, vì sao code vẫn có thể compile nhưng design vẫn sai?
2. Nếu parser sử dụng `Span<T>` giúp allocation giảm 40% nhưng endpoint latency gần như không đổi, bạn giữ refactor hay revert? Cần thêm evidence gì?
3. Một teammate đề xuất expose `Span<T>` xuyên toàn domain layer để tối đa performance. Bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Nói `Span<T>` luôn nằm trên stack và bỏ qua khái niệm backing storage/view.
- Cho rằng `Memory<T>` tự sở hữu backing data.
- Cố giữ borrowed memory sau khi pooled buffer đã được trả.
- Dùng Span ở mọi nơi mà không đo bottleneck.
- Chỉ nói “không dùng được với async” nhưng không giải thích lifetime/escape reason.

## Thang điểm 0–10

- **0–2:** chỉ biết Span nhanh hơn string/array.
- **3–4:** biết span tránh allocation nhưng chưa reasoning về lifetime.
- **5–6:** giải thích đúng view, ref-struct restrictions và Memory use case.
- **7–8:** có ownership design cho async/pooled buffers, stable boundary và measurement strategy.
- **9–10:** cân bằng zero-copy với maintainability, hiểu escape/lifetime sâu và đưa recommendation conditional theo profiling + ownership semantics.

# Câu 2 — Cosmos DB tổng RU chưa dùng hết nhưng vẫn 429: incident nằm ở throughput tổng hay hot partition?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, logical/physical partitions, RU/s, 429 throttling, hot partition, query patterns, .NET SDK retries, observability, data modeling, incident response, scalability

## Bối cảnh

Một multi-tenant event-management API dùng Azure Cosmos DB for NoSQL để lưu user activity stream.

Container hiện partition theo:

```text
/tenantId
```

Production có vài nghìn tenants, nhưng một enterprise tenant mới tạo traffic lớn hơn phần còn lại rất nhiều. Sau onboarding tenant này:

- API p95 tăng từ khoảng 250 ms lên 2–6 giây trong giờ cao điểm;
- Application Insights cho thấy dependency duration tới Cosmos DB tăng;
- Azure metrics có HTTP 429;
- tổng consumed RU/s của container nhìn chung chưa chạm max configured throughput;
- một vài partition-key-range metrics lên gần 100% normalized RU consumption trong khi nhiều ranges còn thấp;
- .NET SDK đang retry một số 429 nên application logs không phải request nào cũng surface exception;
- team đề xuất tăng toàn bộ RU/s gấp 5 lần;
- team khác đề xuất đổi partition key ngay sang `/eventId`;
- API thường query recent events theo tenant + time range;
- một số request cần lookup một event theo ID;
- chưa biết event volume tối đa trên một tenant, retention, growth forecast, exact RU charge của từng query hoặc normalized consumption theo logical key.

Không được giả định trước rằng chỉ có một root cause hoặc rằng repartition luôn là fix đầu tiên.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident theo flow **impact → stabilize → evidence → hypotheses → verification → remediation → prevention**. Giải thích vì sao một container có thể còn RU/s tổng thể nhưng một subset request vẫn bị 429, cách partition key ảnh hưởng tới request distribution và query cost, vì sao tăng total RU/s hoặc đổi sang `/eventId` chưa chắc đúng, và cách bạn thiết kế lại partitioning/data model nếu tenant skew là structural.

## Câu hỏi làm rõ nên cân nhắc

1. 429 tập trung trên tenant nào, partition key range nào và operation nào: point read, query hay write?
2. SDK retry policy đang che bao nhiêu throttling và end-to-end latency sau retry là bao nhiêu?
3. Enterprise tenant có event rate/storage growth dự kiến tới mức nào so với các tenant khác?
4. Query quan trọng nhất có luôn tenantId hay có nhiều cross-tenant/global queries?
5. Có thể thay đổi logical partition strategy mà vẫn giữ common query single-partition, ví dụ composite/synthetic key theo tenant + bucket không?

## Gợi ý tư duy

### Gợi ý 1

Đừng chỉ nhìn aggregate RU. Hãy nhìn **distribution** của workload theo partition key ranges và logical keys.

### Gợi ý 2

Partition key vừa ảnh hưởng scalability vừa ảnh hưởng query locality. Một key phân tán writes rất đều nhưng phá query pattern chính vẫn có thể là design tệ.

### Gợi ý 3

SDK retry có thể biến visible error thành latency. “Không thấy exception” không đồng nghĩa không có throttling.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và tenant blast radius.
2. Stabilize traffic/retry pressure.
3. Thu normalized RU, 429, RU charge, latency theo operation/key.
4. Form competing hypotheses.
5. Xác minh hot partition vs expensive query vs client/network issue.
6. Tune ngắn hạn theo evidence.
7. Đánh giá structural partition-key problem.
8. Thiết kế migration/repartition strategy.
9. Test realistic skew/load.
10. Monitor và capacity-plan.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Aggregate consumed RU/s thấp không loại trừ throttling tại một hot partition key range.
- Nếu một hoặc vài logical partition keys nhận traffic disproportionate, underlying physical partition/range có thể saturate trong khi throughput ở ranges khác chưa dùng hết.
- HTTP 429 là rate limiting signal; SDK retry có thể absorb một phần nhưng làm latency tăng.
- Cần xem normalized RU consumption theo partition/range, request charge, operation type và tenant/key distribution.
- Tăng total RU/s có thể giảm pressure trong một số trường hợp nhưng không chữa một hot logical key có skew structural vô hạn.
- Đổi partition key sang `/eventId` có thể phân tán tốt nhưng làm common query “recent events by tenant” trở thành cross-partition query, tăng RU/latency/complexity.
- Partition-key selection phải dựa trên cardinality, distribution và query access patterns.
- Repartitioning là data migration/architecture change, cần rollout strategy chứ không phải config flip đơn giản.

### Điểm cộng

- Giảm concurrency hoặc rate-limit noisy tenant tạm thời nếu business cho phép để bảo vệ các tenants còn lại.
- Tách retry telemetry ra khỏi user-visible failures; theo dõi throttled requests kể cả khi SDK retry thành công.
- Xem RU charge theo query để tránh đổ mọi lỗi cho partitioning nếu một query/indexing pattern quá đắt.
- Cân nhắc synthetic partition key như tenant + time/hash bucket nếu một tenant đơn lẻ vượt capacity của một logical partition, nhưng chỉ khi query fan-out vẫn có thể bounded.
- Dùng point reads khi có partition key + ID ở paths phù hợp.
- Kiểm tra indexing policy nếu writes/query RU bất thường.

### Senior+

- Nhận ra hot tenant isolation có thể là product architecture concern: dedicated container/account/tier cho extreme tenants đôi khi đơn giản hơn schema phức tạp cho tất cả tenants.
- Thiết kế bucket count từ measured peak volume và query fan-out trade-off, không hard-code ngẫu nhiên.
- Đưa tenant-level quotas/admission control vào design để một tenant không phá shared SLO.
- Có migration dual-write/backfill/cutover hoặc offline strategy tùy consistency requirement.
- Capacity planning dựa trên p95/p99 RU, skew và growth thay vì average RU.

## Hướng giải quyết tham khảo

### 1. Stabilize

Đầu tiên xác định blast radius. Nếu một enterprise tenant tạo workload vượt xa baseline và đang làm shared SLO xấu đi, có thể áp dụng tenant-level throttling/admission control tạm thời hoặc giảm một số non-critical operations, nếu contract cho phép.

Không tăng retry không giới hạn. Retry khi throttled có thể hữu ích nhưng nếu arrival rate liên tục lớn hơn capacity, retry chỉ thêm queueing và latency.

### 2. Evidence

Tôi cần ít nhất:

- 429 count/rate;
- normalized RU consumption theo partition key range;
- RU charge theo operation/query;
- p50/p95/p99 Cosmos dependency duration;
- tenantId hoặc hashed tenant identifier trong structured telemetry;
- request volume theo tenant;
- query shape;
- item size;
- storage distribution;
- SDK diagnostics cho sample slow requests.

Microsoft Learn mô tả trường hợp normalized RU consumption đạt 100% trên một partition key range có thể gây 429 trong khi các ranges khác vẫn thấp; điều này là dấu hiệu điển hình cần kiểm tra khi nghi hot partition.

### 3. Competing hypotheses

**Hypothesis A — hot tenant / hot partition.**  
Một tenant chiếm phần lớn requests nên logical partition `/tenantId` trở thành hot.

**Hypothesis B — expensive query/index behavior.**  
Query recent events có filter/sort shape gây RU cao hơn dự kiến hoặc indexing không phù hợp.

**Hypothesis C — retry amplification.**  
SDK/application retry làm latency và request pressure tăng thêm.

**Hypothesis D — unrelated client/network saturation.**  
Connection/network/client resource issues cũng có thể tạo latency; cần SDK diagnostics thay vì nhìn 429 một chiều.

### 4. Vì sao tăng RU không phải luôn đủ

Nếu physical partition đang thiếu throughput nhưng workload vẫn phân tán tương đối tốt, tăng throughput có thể đúng.

Nếu một logical key duy nhất luôn cực nóng, chỉ scale tổng throughput có thể rất tốn và vẫn có giới hạn practical. Cần cân nhắc key strategy hoặc tenant isolation.

### 5. Vì sao `/eventId` có thể sai

Query chính hiện là:

```text
tenant + recent time range
```

Nếu partition bằng eventId, mỗi event phân bố rất đều nhưng query theo tenant có thể phải fan out trên nhiều partitions. Ta đổi write distribution lấy read/query inefficiency. Đây không phải free win.

### 6. Candidate redesign

Nếu data cho thấy một tenant có thể quá lớn, synthetic key có thể là:

```text
tenantId + yyyyMM
```

hoặc tenant + bounded hash/time bucket tùy workload.

Ví dụ:

```text
contoso|202609
contoso|202610
```

Recent-history query 30 ngày có thể fan out một số bucket nhỏ đã biết thay vì toàn container. Nhưng time bucket có thể vẫn hot trong tháng hiện tại nếu write rate quá lớn; khi đó tenant + hash bucket có distribution tốt hơn nhưng query phải fan out N buckets. Chọn N theo measured workload.

Một alternative khác: giữ shared container cho normal tenants, đưa extreme enterprise tenant sang dedicated container/throughput tier nếu isolation/value justify complexity. Đây có thể đơn giản hơn synthetic partitioning toàn hệ thống.

### 7. Migration

Nếu đổi key cần container mới. Một safe plan có thể gồm:

1. tạo new container + indexing policy;
2. backfill historical data;
3. dual-write có idempotency/version guard nếu consistency requirement cho phép;
4. verify counts/query results/RU/latency;
5. cut read traffic theo cohort;
6. monitor;
7. stop old writes;
8. decommission sau retention/rollback window.

Exact approach phụ thuộc whether event writes can tolerate eventual consistency trong migration.

### 8. Testing/monitoring

Load test phải mô phỏng skew thật: một tenant chiếm phần lớn traffic, không chỉ uniform random tenants.

Dashboard:

- normalized RU by range;
- 429 rate;
- retries;
- RU per operation;
- tenant-level request rate;
- dependency p95/p99;
- cross-partition query rate;
- storage growth;
- alert khi một range sustained near saturation.

Tài liệu Microsoft Learn hiện hành về normalized RU consumption nêu rõ hot partition có thể xuất hiện khi một vài logical partition keys tiêu thụ phần lớn throughput, và 429 có thể xảy ra dù aggregate utilization nhìn còn thấp. citeturn489019search0turn489019search2

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhìn total RU rồi kết luận Cosmos còn dư capacity. Với partitioned workload, một tenant hot có thể saturate partition key range của nó trong khi ranges khác còn nhàn. 429 cũng có thể bị SDK retry nên user thấy latency tăng thay vì exception rõ.

Em sẽ correlate 429, normalized RU theo range, request charge, tenant volume và query shape. Nếu chỉ một tenant gây hot key, tăng total RU có thể là mitigation ngắn hạn nhưng chưa chắc chữa structural skew. Em cũng không đổi sang eventId ngay vì query chính là recent events theo tenant; eventId sẽ phân tán write tốt nhưng có thể biến query thành cross-partition fan-out.

Nếu tenant skew là dài hạn, em đánh giá synthetic tenant+bucket key hoặc isolate extreme tenant sang dedicated container. Em test bằng skewed load, không dùng uniform test data. Nếu repartition, em dùng container mới, backfill, dual-write/cutover có validation và rollback. Cuối cùng em monitor normalized RU, 429, retry, RU/query và tenant-level traffic để phát hiện hot key trước khi SLO bị ảnh hưởng.”

## Câu hỏi đào sâu

1. Nếu autoscale container vẫn có 429 nhưng total throughput chưa đạt configured maximum, evidence nào giúp bạn chứng minh hot partition thay vì “autoscale không hoạt động”?
2. Nếu tenant+month key vẫn hot vì một tenant ghi 50.000 events/giây, bạn thay partitioning thế nào mà không biến mọi read thành unbounded fan-out?
3. Một teammate muốn bật retry nhiều hơn để user không thấy 429. Bạn challenge recommendation đó thế nào?

## Lỗi trả lời thường gặp

- Chỉ nhìn aggregate RU/s.
- Tăng RU không giới hạn mà không kiểm tra skew.
- Chọn `/eventId` chỉ vì cardinality cao.
- Không tính cross-partition query cost.
- Load test với traffic phân bố đều nên không tái hiện hot tenant.

## Thang điểm 0–10

- **0–2:** chỉ tăng RU hoặc đổi partition key theo cảm tính.
- **3–4:** biết hot partition nhưng chưa có evidence/query trade-off.
- **5–6:** hiểu 429, normalized RU, partition distribution và query locality.
- **7–8:** có tenant isolation/synthetic key, migration và realistic load-test strategy.
- **9–10:** cân bằng multi-tenant economics, SLO isolation, partition math, retry amplification và evolutionary migration dựa trên measured skew.

# Câu 3 — Modernize ứng dụng .NET Framework 4.5 đang chạy IIS: rewrite toàn bộ hay strangler/incremental migration?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET Framework 4.5, ASP.NET MVC/Web API, .NET 8, ASP.NET Core, IIS, Windows Server, Azure App Service, legacy modernization, backward compatibility, migration strategy, CI/CD, testing, observability, rollout, architecture trade-offs

## Bối cảnh

Một enterprise operations portal được xây nhiều năm trước trên:

- .NET Framework 4.5;
- ASP.NET MVC + ASP.NET Web API;
- IIS trên Windows Server;
- SQL Server;
- jQuery ở nhiều màn hình, một số Angular legacy modules;
- Windows Authentication ở một phần internal site;
- scheduled jobs chạy trong cùng web application;
- shared class libraries phụ thuộc System.Web và một số third-party packages cũ;
- deployment qua Jenkins + Octopus Deploy;
- production có nhiều business workflows quan trọng nhưng automated integration/E2E coverage còn thấp.

Business muốn chuyển dần sang modern .NET và Azure. Họ cân nhắc .NET 8/ASP.NET Core trên Azure App Service. Đồng thời:

- hệ thống vẫn phải release feature trong 12 tháng migration;
- không chấp nhận downtime dài;
- một số third-party components chưa rõ compatibility;
- database hiện dùng chung bởi nhiều modules;
- team 6 developers;
- Product đề xuất “rewrite sạch trong 6 tháng rồi switch một lần”;
- Architect khác đề xuất tách ngay thành microservices + Kubernetes trong khi migrate;
- chưa có dependency inventory đầy đủ, production traffic profile, test baseline hoặc module coupling map.

## Câu hỏi chính

Hãy đề xuất modernization strategy cho hệ thống này từ .NET Framework 4.5 sang modern .NET. So sánh big-bang rewrite với incremental/strangler migration; xác định module boundaries, compatibility seams, authentication, database, scheduled jobs, frontend, deployment và observability. Đồng thời giải thích khi nào Azure App Service đủ tốt và khi nào mới có lý do thực sự để chọn Kubernetes hoặc microservices.

## Câu hỏi làm rõ nên cân nhắc

1. Những modules nào thay đổi thường xuyên, business-critical hoặc có coupling thấp đủ để migrate trước?
2. Third-party packages/components nào block modern .NET và có source/replacement option không?
3. Windows Authentication có bắt buộc giữ nguyên hay identity strategy có thể thay đổi?
4. Có requirement tách database ownership theo module hay shared SQL được chấp nhận trong giai đoạn transition?
5. Release frequency, rollback tolerance, availability target và current production incident rate là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

Modernization trước hết là **risk-management problem**, không phải framework-upgrade exercise.

### Gợi ý 2

Hãy tìm seams nơi old và new system có thể coexist. Nếu mọi thứ phải chuyển cùng lúc, rollback và learning cost tăng rất mạnh.

### Gợi ý 3

Đừng gắn “modern .NET” mặc định với “microservices + Kubernetes”. Runtime modernization và distributed architecture là hai quyết định khác nhau.

## Cấu trúc trả lời đề xuất

1. Inventory dependencies và business criticality.
2. Baseline behavior bằng tests/telemetry.
3. Chọn migration units/seams.
4. Quyết định hosting/auth/configuration compatibility.
5. Thiết kế old/new coexistence.
6. Xử lý shared database và transaction boundaries.
7. Tách scheduled/background work.
8. Lập rollout/rollback strategy.
9. Modernize frontend theo value/risk.
10. CI/CD và observability.
11. So sánh App Service vs Kubernetes.
12. Định nghĩa exit criteria và decommission legacy.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không thể estimate/commit rewrite an toàn trước dependency inventory, coupling map và behavioral baseline.
- Big-bang rewrite có risk cao khi automated tests thấp và business vẫn cần feature releases song song.
- Incremental migration cho phép old/new coexist, giảm blast radius và tạo feedback sớm.
- Cần xác định seams bằng business capability/module/API boundary, không chỉ chia theo technical layer.
- Shared database trong transition có thể chấp nhận được nhưng schema ownership/mixed-version compatibility phải rõ.
- Scheduled jobs không nên vô thức giữ trong web process nếu hosting/lifecycle mới làm duplicate execution hoặc unreliable execution khi scale-out.
- Authentication/authorization migration phải được design rõ; không coi Windows Authentication → cloud identity là package replacement đơn giản.
- App Service có thể đủ cho nhiều ASP.NET Core workloads; Kubernetes chỉ đáng chọn khi orchestration/operational requirements justify complexity.
- Modernization phải có rollback, telemetry, parity validation và incremental decommission plan.

### Điểm cộng

- Xây dependency inventory: System.Web usage, unsupported APIs, package compatibility, config, filesystem assumptions, Windows-only APIs, COM/native dependencies.
- Dùng characterization tests/API contract tests quanh legacy behavior trước khi refactor.
- Chọn low-coupled/high-value module làm first vertical slice, không migrate shared utility library trước chỉ vì dễ compile.
- Có reverse proxy/routing strategy cho old/new endpoints nếu cần strangler pattern.
- Tách background jobs sang Worker Service/Azure Functions chỉ khi execution semantics phù hợp; thiết kế idempotency/single-execution khi scale.
- Giữ database migrations backward compatible trong mixed-version window.
- Frontend modernization có thể gradual: giữ jQuery/Angular legacy nơi ổn, dùng Vue/React cho new surfaces thay vì rewrite UI đồng loạt.

### Senior+

- Phân biệt source compatibility, runtime behavior compatibility, data compatibility và operational compatibility.
- Có architecture decision records cho exceptions/temporary bridges để migration không biến thành permanent hybrid chaos.
- Đề xuất feature flags/canary/cohort routing và parity telemetry để compare old/new behavior.
- Tách modernization platform work khỏi domain feature delivery bằng roadmap có explicit capacity budget.
- Có decommission criteria: traffic zero, no callers, data ownership transferred, rollback window expired, operational runbooks updated.

## Hướng giải quyết tham khảo

### 1. Discovery trước migration

Tôi bắt đầu bằng inventory thay vì tạo solution .NET 8 rồi port file-by-file.

Lập map:

```text
Module
- business criticality
- change frequency
- dependencies
- System.Web coupling
- Windows-only dependencies
- database tables owned/used
- external integrations
- authentication mode
- scheduled/background work
- automated test coverage
- production traffic/error profile
```

Dùng tooling hỗ trợ analysis/Upgrade Assistant khi phù hợp, nhưng output của tool không thay thế architecture judgement. Microsoft Learn hiện có guidance về .NET Upgrade Assistant và incremental modernization cho ASP.NET Framework applications. citeturn489019search5

### 2. Baseline behavior

Legacy system ít tests nên trước refactor cần characterization/contract coverage ở boundaries quan trọng:

- API request/response;
- authentication/authorization cases;
- database effects;
- critical workflow;
- scheduled job behavior;
- integration contracts.

Dùng production telemetry để biết endpoints thực sự được dùng; không port dead code chỉ vì nó tồn tại trong repository.

### 3. Chọn first slice

Không chọn module chỉ vì “code ít nhất”. Chọn vertical slice có:

- business value rõ;
- coupling vừa phải;
- measurable behavior;
- rollback/routing seam tốt;
- ít unsupported dependencies.

Ví dụ migrate một read-heavy reporting module trước:

```text
Client
  ↓
Reverse proxy / routing
  ├── /legacy/*  → IIS .NET Framework
  └── /reports/* → ASP.NET Core .NET 8
```

Old và new cùng chạy. Traffic migration theo endpoint/cohort giúp rollback bằng routing thay vì redeploy toàn hệ thống.

### 4. Shared database

Không bắt buộc tách DB ngay để được gọi là modernization.

Trong transition, cả old/new có thể dùng SQL Server nhưng cần rules:

- module/table ownership documented;
- destructive schema changes không chạy khi old code còn phụ thuộc;
- expand/contract cho incompatible migrations;
- query/transaction behavior được test dưới mixed versions;
- tránh để new app trực tiếp phụ thuộc mọi legacy table nếu muốn boundary tiến hóa.

Nếu business capability sau này thật sự cần independent ownership, có thể tách data theo evidence. Đừng thêm distributed transaction problem vào migration chỉ vì muốn microservices.

### 5. Authentication

Windows Authentication là architecture constraint cần discovery. Nếu internal environment vẫn yêu cầu Integrated Windows Auth, có thể giữ một legacy/auth edge trong giai đoạn transition. Nếu chuyển sang Microsoft Entra ID, phải map:

- identity;
- roles/claims;
- service accounts;
- authorization policies;
- logout/session semantics;
- automation callers;
- support/admin flows.

Đây là migration riêng có security test plan, không phải “đổi middleware”.

### 6. Scheduled jobs

Legacy jobs nằm trong IIS web app có thể dựa vào single-process assumption. Khi ASP.NET Core app scale nhiều instances, mỗi instance có thể khởi động hosted service tương tự và tạo duplicate execution.

Cần classify jobs:

- simple in-process maintenance;
- durable scheduled business operation;
- long-running worker;
- retryable queue consumer.

Sau đó chọn Worker Service, Azure Functions, queue/messaging hoặc external scheduler khi semantics justify. Với business jobs, idempotency/locking/leader/singleton strategy phải explicit.

### 7. Frontend

Không rewrite jQuery chỉ vì nó cũ. Nếu page ổn định, giữ nó trong legacy slice cho tới khi business/module được migrate.

New modules có thể dùng Vue.js/React.js với API contract mới. Nếu incremental page composition quá phức tạp, route-level migration thường đơn giản hơn microfrontend architecture.

### 8. Hosting

Azure App Service phù hợp khi application là standard stateless web/API workload cần scale-out, managed hosting, deployment slots và không có orchestration requirement đặc biệt.

Kubernetes chỉ cân nhắc nếu có requirements như:

- nhiều independently deployed services;
- custom networking/sidecars/workload orchestration;
- container scheduling/resource controls ở mức cần thiết;
- team có operational capability;
- platform standard đã tồn tại và cost hợp lý.

“Muốn modern” hoặc “có nhiều users” không phải reason đủ.

### 9. CI/CD

Pipeline nên build artifact một lần rồi promote immutable artifact qua environments. Migration stages có gates:

1. deploy new slice disabled;
2. health/readiness validation;
3. synthetic tests;
4. route small cohort;
5. compare error/latency/business outputs;
6. expand traffic;
7. rollback routing nếu regress;
8. decommission legacy endpoint sau window.

### 10. Observability

Old và new phải có correlation để compare:

- request count/error/latency;
- auth failures;
- SQL dependencies;
- external dependencies;
- background job outcomes;
- instance/restart/deployment version;
- business KPI parity.

Nếu new service nhanh hơn nhưng tạo sai data, modernization vẫn thất bại.

### 11. Roadmap ví dụ

**Phase 0 — Discovery/Baseline**  
Inventory, tests, telemetry, dependency map.

**Phase 1 — Foundation**  
.NET 8 host, CI/CD, logging/tracing, auth bridge, routing seam.

**Phase 2 — First vertical slice**  
Migrate low-coupled capability, canary traffic.

**Phase 3 — Repeated extraction**  
Migrate capabilities theo priority, giữ mixed-version DB compatibility.

**Phase 4 — Background/auth modernization**  
Tách jobs và identity khi prerequisites rõ.

**Phase 5 — Legacy retirement**  
Remove dead routes, packages, Windows/IIS dependencies khi traffic/callers về zero.

Big-bang rewrite chỉ có thể hợp lý nếu system nhỏ, behavior hiểu rất rõ, feature freeze khả thi, tests mạnh, migration window chấp nhận được và rollback đơn giản. Scenario hiện tại không cung cấp evidence đó.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không commit rewrite sáu tháng trước khi inventory dependency và baseline behavior. Với .NET Framework 4.5, System.Web, Windows Auth, scheduled jobs và test coverage thấp, big-bang làm tăng risk vì team vừa phải reproduce behavior vừa tiếp tục feature delivery.

Em ưu tiên incremental modernization. Đầu tiên map module/dependency/database/auth/jobs, thêm characterization tests và production telemetry. Sau đó chọn một vertical slice ít coupling, chạy ASP.NET Core .NET 8 song song với legacy và route traffic theo endpoint/cohort để rollback nhanh.

Shared SQL có thể giữ trong transition nếu schema changes backward-compatible và ownership rõ; em không tách database/microservices chỉ để trông hiện đại. Scheduled jobs được classify và đưa sang Worker/Functions chỉ khi execution semantics phù hợp, có idempotency khi scale.

Về hosting, App Service là default candidate cho web/API nếu requirements bình thường. Kubernetes chỉ khi orchestration/independent-service requirements thực sự justify operational cost. Mỗi slice có canary, contract tests, telemetry parity và decommission criteria. Mục tiêu là giảm legacy risk dần chứ không tạo một distributed-system migration song song với framework migration.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên cần một third-party library chỉ chạy trên .NET Framework, bạn tạo seam/bridge thế nào thay vì block toàn roadmap?
2. Nếu CTO yêu cầu microservices vì “sau này team sẽ tăng từ 6 lên 30 người”, bạn cần thêm evidence nào trước khi chấp nhận service split?
3. Nếu old và new application cùng ghi một bảng SQL trong 9 tháng transition, bạn kiểm soát schema evolution và transaction behavior thế nào?

## Lỗi trả lời thường gặp

- Rewrite toàn bộ chỉ vì legacy code “xấu”.
- Port project theo technical layer thay vì business capability.
- Chọn Kubernetes/microservices cùng lúc với runtime migration mà không phân tích operational cost.
- Bỏ qua auth, scheduled jobs và deployment semantics.
- Không có behavioral baseline nên không biết new system có thực sự parity.

## Thang điểm 0–10

- **0–2:** chỉ nói dùng Upgrade Assistant hoặc rewrite sang .NET 8.
- **3–4:** có incremental idea nhưng thiếu coexistence/rollback/data strategy.
- **5–6:** có dependency inventory, vertical slices, mixed-version DB, tests và rollout.
- **7–8:** xử lý auth/jobs/CI-CD/telemetry, App Service vs Kubernetes trade-offs rõ.
- **9–10:** modernization roadmap dựa trên business risk, evolutionary boundaries, decommission criteria, organizational capacity và conditional decisions thay vì technology fashion.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Span<T>` giúp tạo borrowed views và tránh copy/allocation ở hot paths, nhưng lifetime/ownership phải được hiểu rõ trước khi đưa qua async hoặc pooled memory.
- `Memory<T>` giải quyết khả năng lưu/đi qua async tốt hơn `Span<T>`, nhưng không tự trở thành owner của backing storage.
- Cosmos DB phải được quan sát theo distribution của RU và partition keys, không chỉ aggregate throughput.
- Partition-key design là trade-off giữa distribution, storage growth và query locality.
- Modernization .NET là bài toán quản trị rủi ro, compatibility và rollout; không đồng nghĩa rewrite, microservices hoặc Kubernetes.
- Architecture tốt giữ được rollback path và cho phép old/new coexist trong giai đoạn chuyển đổi.

## Mẫu tư duy cần nhớ

- **Reason about lifetime and ownership before optimizing memory.**
- **Measure distribution, not only aggregates.**
- **Design partitioning from access patterns and skew.**
- **Migrate through reversible seams instead of betting everything on one cutover.**
- **Do not add distributed-system complexity unless requirements pay for it.**
