# Code Review Challenge 1 — Cosmos DB query “chạy đúng” nhưng RU tăng mạnh khi dữ liệu và số partition lớn dần

**Chủ đề:** C#/.NET 8, Azure Cosmos DB for NoSQL, partition key, cross-partition query, RU consumption, pagination, tenant isolation, query diagnostics  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một internal order-management API chạy ASP.NET Core .NET 8 và lưu order summary trong Azure Cosmos DB for NoSQL. Container `orders` dùng partition key `/tenantId`. Mỗi tenant có từ vài nghìn tới vài triệu orders.

Endpoint bên dưới trả các order gần đây theo `status`. Trong giai đoạn đầu hệ thống chỉ có vài tenant nên latency và RU khá thấp. Sau khi onboarding thêm nhiều tenant và dữ liệu tăng mạnh, team quan sát:

- p95 latency của endpoint tăng đáng kể;
- RU tiêu thụ cho cùng một request tăng theo thời gian dù mỗi user chỉ xem dữ liệu của một tenant;
- một số request đọc nhiều pages từ Cosmos DB rồi cuối cùng chỉ trả vài chục records;
- autoscale throughput thường xuyên chạm ngưỡng trong giờ cao điểm;
- request vẫn trả dữ liệu đúng tenant vì code lọc `TenantId` sau khi đọc về;
- team đang đề xuất tăng throughput nhưng chưa chứng minh bottleneck nằm ở capacity hay query shape.

Business yêu cầu tenant isolation, page size tối đa 100, và UI cần continuation-based “Load more”; không yêu cầu biết tổng số records chính xác trước khi render page đầu.

## Đoạn code cần review

```csharp
public sealed class OrderSearchService
{
    private readonly Container _container;

    public OrderSearchService(Container container)
    {
        _container = container;
    }

    public async Task<IReadOnlyList<OrderSummary>> SearchAsync(
        string tenantId,
        string status,
        DateTimeOffset from,
        int take,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.status = @status " +
            "AND c.createdAt >= @from " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@status", status)
            .WithParameter("@from", from);

        using var iterator = _container.GetItemQueryIterator<OrderSummary>(
            query,
            requestOptions: new QueryRequestOptions
            {
                MaxItemCount = 500
            });

        var results = new List<OrderSummary>();

        while (iterator.HasMoreResults)
        {
            var response = await iterator.ReadNextAsync(cancellationToken);

            results.AddRange(
                response.Resource.Where(x => x.TenantId == tenantId));

            if (results.Count >= take)
            {
                break;
            }
        }

        return results
            .Take(take)
            .ToArray();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, performance và scalability trong query path.
2. Giải thích vì sao query có thể trả đúng dữ liệu nhưng vẫn tiêu tốn RU không cần thiết.
3. Phân tích vai trò của partition key trong routing và vì sao lọc tenant trong memory là quá muộn.
4. Review cách dùng `MaxItemCount`, `take` và pagination hiện tại.
5. Đề xuất implementation phù hợp với continuation-based paging.
6. Nêu evidence cần thu thập trước khi quyết định tăng throughput hoặc đổi data model.
7. Đề xuất tests và production telemetry cho query cost, latency và tenant isolation.

## Câu hỏi gợi mở

1. Container partition theo `/tenantId`, nhưng request hiện cho Cosmos DB biết `tenantId` ở bước nào?
2. Việc mỗi item cuối cùng được filter đúng tenant có đồng nghĩa query chỉ đọc partition của tenant đó không?
3. `MaxItemCount = 500` có phải giới hạn tổng số items mà toàn bộ request sẽ đọc không?
4. Nếu UI chỉ cần một page và continuation token, vì sao service lại loop qua nhiều feed pages trong cùng request?
5. Nếu một tenant riêng lẻ cực lớn, chỉ thêm `PartitionKey` đã giải quyết mọi vấn đề query/index chưa?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **query routing**. Hãy phân biệt “lọc dữ liệu sau khi client đã nhận” với “định tuyến query tới đúng logical partition ngay từ đầu”.

### Gợi ý 2

Sau khi query được scope đúng partition, tiếp tục review pagination contract, index/query shape và telemetry dựa trên RU thay vì giả định throughput cao hơn là lời giải đầu tiên.

## Kết quả code review tham khảo

### Critical — Query không được scope theo tenant/partition key

**Vấn đề:** SQL query không có predicate `tenantId`, và `QueryRequestOptions` cũng không chỉ định `PartitionKey`.

**Tại sao xảy ra:** Container partition theo `/tenantId`, nhưng Cosmos DB không nhận được thông tin cần thiết để target logical partition tương ứng với request. Query theo `status` và `createdAt` có thể trở thành cross-partition query, rồi client mới lọc tenant sau khi đã nhận kết quả.

**Ảnh hưởng production:** Query phải fan out qua nhiều partitions hơn cần thiết. Khi container và số physical partitions tăng, latency và RU có thể tăng dù business request chỉ cần dữ liệu của một tenant. Đây cũng là một thiết kế dễ che giấu lỗi tenant isolation nếu sau này một code path quên filter in-memory.

**Cách sửa:** Tenant phải là một phần của query contract. Thêm `c.tenantId = @tenantId` và scope request tới `new PartitionKey(tenantId)` khi đó là partition key đầy đủ của container. Defense in depth ở cả query predicate và request routing làm intent rõ hơn.

### High — Tenant isolation đang phụ thuộc vào post-filter trong application memory

**Vấn đề:** Correctness hiện tại dựa vào `response.Resource.Where(x => x.TenantId == tenantId)`.

**Tại sao xảy ra:** Data boundary được áp dụng sau khi dữ liệu đã rời database service và đi vào process.

**Ảnh hưởng production:** Một refactor nhỏ, một endpoint tái sử dụng iterator khác, logging/debug dump hoặc mapping sai có thể làm lộ cross-tenant data. Ngoài security risk, application còn deserialize và giữ objects không liên quan tới request.

**Cách sửa:** Enforce tenant boundary tại datastore query. Có thể giữ thêm guard/assertion ở application layer nếu cần, nhưng không coi client-side filter là security boundary chính.

### High — Method đọc nhiều Cosmos pages để tự tạo một page ứng dụng

**Vấn đề:** Loop tiếp tục gọi `ReadNextAsync` cho tới khi đã thu đủ `take` items của tenant, trong khi mỗi Cosmos page có thể chứa chủ yếu items của tenants khác.

**Tại sao xảy ra:** Query scope sai khiến service phải bù lại bằng client-side scanning.

**Ảnh hưởng production:** Một UI request có thể tạo nhiều backend round trips, RU và latency khó dự đoán. Under load, pattern này khuếch đại throughput pressure.

**Cách sửa:** Sau khi target đúng partition, để một request ứng dụng đọc một feed page hợp lý và trả continuation token cho UI. Không loop vô hạn để “lấp đầy” page trừ khi contract thực sự yêu cầu và có budget rõ ràng.

### High — `MaxItemCount = 500` không enforce business page size tối đa 100

**Vấn đề:** `take` không được validate, còn SDK page request đặt `MaxItemCount` cố định 500.

**Tại sao xảy ra:** Hai khái niệm bị trộn: số items service muốn trả cho UI và page size mà SDK yêu cầu từ Cosmos DB.

**Ảnh hưởng production:** Một request có thể đọc/deserialise nhiều dữ liệu hơn cần thiết. Nếu caller truyền `take` lớn bất thường, service không enforce constraint business.

**Cách sửa:** Validate `pageSize` trong range rõ ràng, ví dụ 1–100 theo requirement. Dùng page size đó làm input cho request options như một hint/bound hợp lý, đồng thời thiết kế API trả continuation token thay vì đọc toàn bộ kết quả.

### High — Không expose continuation token nên pagination không ổn định về cost

**Vấn đề:** Service trả mỗi danh sách items, bỏ continuation token từ feed response.

**Tại sao xảy ra:** Pagination được implement như “đọc cho đủ N items” thay vì giữ vị trí của query engine.

**Ảnh hưởng production:** UI không thể tiếp tục từ vị trí server đã đọc. Team có thể bị thúc đẩy sang offset-style paging hoặc chạy lại query từ đầu, làm RU/latency tăng và behavior khó dự đoán khi dữ liệu thay đổi.

**Cách sửa:** Contract trả `{ Items, ContinuationToken }`. Caller gửi token ở lần “Load more” tiếp theo. Token nên được coi là opaque; không parse hay tự chế format.

### Medium — Không validate `take`, `status` và temporal range

**Vấn đề:** Method chấp nhận `take`, `status`, `from` trực tiếp.

**Tại sao xảy ra:** Query service thiếu resource-budget validation.

**Ảnh hưởng production:** Caller có thể tạo query quá rộng hoặc page size ngoài expectation. Dù đã scope partition, một tenant lớn vẫn có thể phát sinh query tốn RU nếu time range rất rộng và query/index shape không phù hợp.

**Cách sửa:** Validate page size, status domain và range theo business semantics. Nếu UI chỉ cần recent orders, đặt explicit maximum look-back khi product requirement cho phép.

### Medium — Projection `SELECT *` đọc nhiều fields hơn màn hình cần

**Vấn đề:** Query lấy toàn bộ document dù `OrderSummary` có thể chỉ cần một subset.

**Tại sao xảy ra:** Query shape chưa được thiết kế từ response contract.

**Ảnh hưởng production:** Tăng payload, deserialization và network cost. RU impact phải đo thực tế, nhưng projection hẹp thường làm contract rõ hơn và tránh mang field nhạy cảm/không dùng vào process.

**Cách sửa:** Project đúng fields UI cần, ví dụ id, status, createdAt, amount, display fields. Không tối ưu mù quáng; xác minh bằng diagnostics/RU trước và sau.

### Medium — Không thu thập request charge/diagnostics ở query boundary

**Vấn đề:** Code bỏ qua metadata từ feed response.

**Tại sao xảy ra:** Observability chỉ nhìn HTTP latency nên không phân biệt network, fan-out, throttling hay query shape.

**Ảnh hưởng production:** Team dễ phản ứng bằng cách tăng throughput thay vì sửa query routing. Khi incident xảy ra, thiếu evidence để so sánh RU/page, partitions và throttling.

**Cách sửa:** Ghi metrics cho request charge, page latency, item count, status code/substatus khi phù hợp, retry/throttle signals và correlation. Không log continuation token hoặc business payload nhạy cảm nếu không cần.

## Phiên bản đề xuất

Một contract phù hợp hơn với UI “Load more” có thể là:

```csharp
public sealed record OrderPage(
    IReadOnlyList<OrderSummary> Items,
    string? ContinuationToken);

public sealed class OrderSearchService
{
    private readonly Container _container;
    private readonly ILogger<OrderSearchService> _logger;

    public OrderSearchService(
        Container container,
        ILogger<OrderSearchService> logger)
    {
        _container = container;
        _logger = logger;
    }

    public async Task<OrderPage> SearchAsync(
        string tenantId,
        string status,
        DateTimeOffset from,
        int pageSize,
        string? continuationToken,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(tenantId))
            throw new ArgumentException("Tenant is required.", nameof(tenantId));

        if (pageSize is < 1 or > 100)
            throw new ArgumentOutOfRangeException(nameof(pageSize));

        var query = new QueryDefinition(
            "SELECT c.id, c.tenantId, c.status, c.createdAt, c.total " +
            "FROM c " +
            "WHERE c.tenantId = @tenantId " +
            "AND c.status = @status " +
            "AND c.createdAt >= @from " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@tenantId", tenantId)
            .WithParameter("@status", status)
            .WithParameter("@from", from);

        using var iterator = _container.GetItemQueryIterator<OrderSummary>(
            query,
            continuationToken,
            new QueryRequestOptions
            {
                PartitionKey = new PartitionKey(tenantId),
                MaxItemCount = pageSize
            });

        if (!iterator.HasMoreResults)
            return new OrderPage(Array.Empty<OrderSummary>(), null);

        var response = await iterator.ReadNextAsync(cancellationToken);

        _logger.LogInformation(
            "Cosmos order query completed for tenant {TenantId}; " +
            "items={ItemCount}; requestCharge={RequestCharge}",
            tenantId,
            response.Count,
            response.RequestCharge);

        return new OrderPage(
            response.Resource.ToArray(),
            response.ContinuationToken);
    }
}
```

Phần logging trên chỉ minh họa loại telemetry hữu ích. Trong production có thể metric hóa `RequestCharge` thay vì log mỗi request để tránh log volume cao. Tenant ID cũng cần xử lý theo policy dữ liệu của hệ thống; nếu là identifier nhạy cảm thì hash/tokenize hoặc dùng dimension an toàn.

Theo tài liệu Azure Cosmos DB hiện hành, query có equality filter trên partition key có thể được route hiệu quả tới partition tương ứng, còn query không có partition-key filter có thể phải chạy cross-partition. Vì vậy việc đưa tenant vào query/routing là thay đổi về query topology, không chỉ là micro-optimization.

Nếu sau khi target đúng partition mà RU vẫn cao, bước tiếp theo là xem indexing policy, cardinality, sort/filter combination, document size, query metrics và access pattern. Không tự động đổi partition key hoặc thêm cache trước khi có evidence.

## Giải thích thiết kế sau khi sửa

Thiết kế mới đưa tenant boundary xuống nơi dữ liệu được truy vấn. Query engine không cần quét dữ liệu của tenants khác chỉ để application loại bỏ sau đó.

Pagination contract cũng thay đổi từ “server cố đọc đến đủ N items” thành “đọc một page và trả continuation token”. Điều này làm work per request bounded hơn và phù hợp UI Load more.

`MaxItemCount` không nên được hiểu như cam kết tuyệt đối rằng service luôn nhận đúng từng đó items; pagination phải dựa trên iterator/continuation semantics. Application contract chỉ cần bảo đảm không trả quá page size đã chốt và xử lý page rỗng/nhỏ đúng cách.

Nếu một tenant trở thành hotspot hoặc có volume khác biệt lớn, đó là một vấn đề khác với cross-tenant fan-out. Khi đó cần xem phân bố RU/storage, access pattern và khả năng hierarchical partition key hoặc data-model change; không nên đổi key chỉ dựa trên cảm giác.

## Trade-offs

Scope query theo partition key cải thiện routing nhưng đồng nghĩa API phải luôn có tenant identity đáng tin cậy. Tenant ID không nên lấy từ request body/query string mà không gắn với authenticated context nếu điều đó cho phép user chọn tenant tùy ý.

Continuation-token pagination đơn giản và hiệu quả cho “Load more”, nhưng token là state opaque gắn với query progression. Nếu product cần random page number kiểu “jump to page 37”, requirement phải được phân tích lại thay vì giả vờ continuation token là offset.

Projection hẹp làm payload nhỏ và contract rõ, nhưng thêm maintenance khi UI cần fields mới. Chỉ nên tối ưu các fields có ý nghĩa thay vì tạo hàng chục DTO/query variants không cần thiết.

Tăng provisioned/autoscale throughput vẫn có thể đúng khi workload thực sự cần, nhưng chỉ sau khi query routing và data model đã hợp lý. Capacity không nên che một fan-out pattern do bug.

## Cách kiểm thử

1. **Integration test tenant isolation:** seed nhiều tenants có cùng `status`/time range; gọi service cho tenant A và xác minh chỉ nhận A, kể cả khi dữ liệu B nhiều hơn rất nhiều.
2. **Query-cost regression test:** so sánh request charge/query diagnostics của query cũ và query đã scope partition trên dataset representative; đặt threshold regression hợp lý theo môi trường test.
3. **Pagination test:** đọc nhiều pages qua continuation token; xác minh không duplicate/missing trong điều kiện data set cố định và mỗi response không vượt page-size contract.
4. **Load test:** chạy concurrent searches trên nhiều tenants và quan sát p95/p99, RU consumption, throttling/retry và CPU/memory phía API.
5. **Validation/failure-path test:** page size ngoài 1–100, tenant rỗng, cancellation giữa `ReadNextAsync` và dependency throttling phải cho behavior rõ ràng, không biến thành generic success rỗng.

## Quan sát trong production

Theo dõi tối thiểu:

# Code Review Challenge 2 — Playwright suite chỉ flaky trên CI khi chạy parallel

**Chủ đề:** Playwright, TypeScript, test isolation, parallel execution, shared backend state, auto-waiting, resilient locators, CI diagnostics  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một team dùng Playwright để chạy E2E tests cho order-management portal. Local developer thường chạy một test file với một worker nên suite ổn định. Trên CI, test project bật `fullyParallel: true` và chia suite thành nhiều shards để giảm runtime.

Sau khi parallelize, pipeline bắt đầu flaky:

- test “cancel order” và “ship order” thỉnh thoảng fail lẫn nhau;
- retry thường pass nên team đang cân nhắc tăng `retries` lên 3;
- screenshot lúc fail cho thấy trạng thái order đôi khi đã bị test khác thay đổi;
- một số failure chỉ xảy ra trên CI chậm hơn local;
- test dùng cùng một test user và một shared order tạo trong `beforeAll`;
- selectors phụ thuộc CSS classes từ UI implementation.

Business muốn CI signal đáng tin cậy hơn là chỉ giảm thời gian chạy. Team có API test fixture để tạo/xóa order data nhưng chưa dùng nhất quán.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const userEmail = 'e2e-user@company.test';
let orderId: string;

test.describe.configure({ mode: 'parallel' });

test.beforeAll(async ({ request }) => {
  const response = await request.post('/test-api/orders', {
    data: {
      customerEmail: userEmail,
      status: 'Pending'
    }
  });

  const body = await response.json();
  orderId = body.id;
});

test('user can cancel an order', async ({ page }) => {
  await page.goto(`/orders/${orderId}`);
  await page.locator('.actions .cancel-button').click();
  await page.waitForTimeout(2000);

  const status = await page.locator('.order-status').textContent();
  expect(status).toContain('Cancelled');
});

test('warehouse can ship an order', async ({ page }) => {
  await page.goto(`/orders/${orderId}`);
  await page.locator('.actions .ship-button').click();
  await page.waitForTimeout(2000);

  const toast = await page.locator('.toast.success').textContent();
  expect(toast).toContain('Order shipped');

  await page.reload();
  expect(await page.locator('.order-status').textContent())
    .toContain('Shipped');
});

test.afterAll(async ({ request }) => {
  await request.delete(`/test-api/orders/${orderId}`);
});
```

## Nhiệm vụ của ứng viên

1. Xác định các nguồn flakiness và correctness problem trong test design.
2. Phân biệt browser-context isolation của Playwright với shared backend state của application.
3. Giải thích vì sao suite có thể ổn khi chạy một worker nhưng fail khi parallel/sharding.
4. Review waits, assertions và locators hiện tại.
5. Đề xuất test-data strategy để mỗi test có thể chạy độc lập và retry an toàn.
6. Đánh giá việc tăng `retries` có giải quyết root cause hay chỉ che lỗi.
7. Đề xuất CI telemetry/artifacts giúp phân biệt product bug, test bug và environment issue.

## Câu hỏi gợi mở

1. Hai tests có BrowserContext riêng thì có đồng nghĩa chúng không thể race trên cùng một database row không?
2. Điều gì xảy ra nếu “ship” chạy trước “cancel”, hoặc nếu retry chỉ một test sau khi order đã bị thay đổi?
3. `waitForTimeout(2000)` đang chờ một condition cụ thể hay chỉ hy vọng UI kịp cập nhật?
4. `textContent()` + synchronous `expect` khác gì một web-first assertion của Playwright?
5. Nếu CI chạy nhiều shards trên nhiều machines, global variable trong process có bảo vệ được shared backend data không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **test isolation chỉ tồn tại ở browser nhưng không tồn tại ở backend data**. Parallel execution làm dependency giữa tests lộ ra.

### Gợi ý 2

Sau khi tách data ownership, hãy bỏ fixed sleeps và implementation-detail selectors; để test chờ user-visible state bằng locators/assertions có auto-wait semantics.

## Kết quả code review tham khảo

### Critical — Hai tests song song mutate cùng một order

**Vấn đề:** `beforeAll` tạo một `orderId`, rồi cả “cancel” và “ship” dùng cùng record trong `mode: 'parallel'`.

**Tại sao xảy ra:** BrowserContexts của Playwright cô lập cookies/local storage/page state, nhưng order nằm trong backend database chung. Hai workers/processes có thể thao tác cùng entity gần như đồng thời.

**Ảnh hưởng production/CI:** Kết quả phụ thuộc scheduling: cancel có thể làm ship không hợp lệ, ship có thể làm cancel không hợp lệ. Failure là nondeterministic và retry có thể pass chỉ vì thứ tự chạy khác.

**Cách sửa:** Mỗi test tự sở hữu backend data riêng. Tạo order trong per-test fixture hoặc trong test setup với unique identifier gắn với `testInfo`. Không dùng shared mutable business entity cho independent parallel tests.

### High — `beforeAll`/`afterAll` không tạo lifecycle an toàn cho parallel independent tests

**Vấn đề:** Setup/cleanup được thiết kế quanh một shared resource.

**Tại sao xảy ra:** Test suite giả định group có lifecycle tuần tự, nhưng đã opt-in parallel mode và CI còn có thể shard test execution.

**Ảnh hưởng production/CI:** Cleanup có thể làm test khác mất data nếu architecture fixture thay đổi; retry behavior khó hiểu; failure trong setup/cleanup có thể cascade sang cả group.

**Cách sửa:** Dùng fixture per test tạo entity duy nhất và cleanup entity của chính test đó. Cleanup nên idempotent, best-effort nhưng vẫn report rõ nếu môi trường test bị rò rỉ data.

### High — `waitForTimeout(2000)` tạo timing assumption

**Vấn đề:** Test ngủ đúng 2 giây thay vì chờ condition business/UI.

**Tại sao xảy ra:** Fixed delay không biết request đã hoàn tất, UI đã rerender hay CI đang chậm hơn bình thường.

**Ảnh hưởng production/CI:** 2 giây có thể dư trên local nhưng thiếu trên CI; tăng sleep làm suite chậm nhưng vẫn flaky khi tail latency vượt timeout tùy ý.

**Cách sửa:** Chờ thông qua user-visible state với Playwright locators/web-first assertions; nếu cần sync với network, chờ response/event có contract rõ ràng thay vì sleep.

### High — Assertions đọc snapshot rồi assert ngoài retry loop của Playwright

**Vấn đề:** Code lấy `textContent()` một lần rồi dùng `expect(status).toContain(...)`.

**Tại sao xảy ra:** Giá trị string là snapshot tại một thời điểm; assertion không tự re-query DOM cho tới khi UI đạt trạng thái mong muốn.

**Ảnh hưởng production/CI:** Test fail trong race nhỏ giữa API response, state update và rendering dù UI cuối cùng đúng.

**Cách sửa:** Dùng web-first assertions như `await expect(locator).toContainText('Cancelled')` hoặc `toHaveText` khi contract exact. Locator được re-evaluate theo retry semantics trong timeout.

### High — Retry có thể chạy trên backend state đã bị test attempt trước mutate

**Vấn đề:** Team dự định tăng retries nhưng test data không reset độc lập giữa attempts theo business state cần thiết.

**Tại sao xảy ra:** First attempt có thể ship/cancel thành công rồi fail ở assertion. Retry sau đó không còn bắt đầu từ `Pending` sạch.

**Ảnh hưởng production/CI:** Retry che root cause, tạo false pass hoặc failure khác với attempt đầu. CI signal mất giá trị.

**Cách sửa:** Mỗi test attempt cần deterministic precondition. Tạo fresh data per test/attempt bằng fixture phù hợp hoặc reset qua supported test API. Retry là resilience cho transient environment/browser issues, không phải dependency manager cho shared state.

### Medium — CSS selectors gắn chặt vào implementation detail

**Vấn đề:** `.actions .cancel-button`, `.toast.success`, `.order-status` phụ thuộc class structure.

**Tại sao xảy ra:** Test chọn element dựa trên styling/DOM internals thay vì user-facing semantics hoặc explicit test contract.

**Ảnh hưởng production/CI:** Refactor CSS/layout có thể phá E2E dù behavior không đổi; failure noise tăng.

**Cách sửa:** Ưu tiên `getByRole`, accessible name, label, text hoặc stable test id khi không có semantic locator phù hợp. Đây cũng hỗ trợ accessibility-oriented contract tốt hơn.

### Medium — Setup API không check response success trước khi parse

**Vấn đề:** `request.post` được parse trực tiếp mà không assert status/success.

**Tại sao xảy ra:** Fixture giả định test API luôn hoạt động.

**Ảnh hưởng production/CI:** Nếu setup trả 500/401/429, test có thể fail sau đó với `orderId` undefined hoặc lỗi UI gây nhiễu root cause.

**Cách sửa:** Validate setup response ngay tại boundary và fail với message chứa safe diagnostic metadata. Tương tự cho cleanup nếu cleanup correctness quan trọng.

### Medium — Shared static user có thể là một backend bottleneck/race khác

**Vấn đề:** Mọi test dùng cùng `e2e-user@company.test`.

**Tại sao xảy ra:** Browser auth có thể isolated nhưng server-side cart/session/preferences/rate limits hoặc ownership data vẫn gắn với cùng account.

**Ảnh hưởng production/CI:** Parallel tests ở files/shards khác có thể ảnh hưởng lẫn nhau qua account-scoped state, tạo flakes ngoài hai tests đang review.

**Cách sửa:** Xác định state nào account-scoped. Nếu có mutable shared state, provision pool accounts per worker hoặc tạo identity/data namespace riêng cho test. Không nhân bản accounts vô hạn nếu hệ thống có cách fixture isolation đơn giản hơn.

### Medium — Thiếu diagnostic artifacts có correlation tới test data

**Vấn đề:** Khi test fail, team có screenshot nhưng không có stable correlation giữa test, order và backend request.

**Tại sao xảy ra:** Test data không mang unique test identity và pipeline chưa coi traces/network/server logs là một phần của debugging strategy.

**Ảnh hưởng production/CI:** Khó biết đây là product race, backend error, environment slowdown hay test-design race.

**Cách sửa:** Gắn test-run/test ID vào data/headers khi phù hợp; retain Playwright trace, screenshot/video theo policy, browser console/network errors và correlate với backend structured logs.

## Phiên bản đề xuất

Một hướng đơn giản là để mỗi test tự tạo order riêng thông qua helper/fixture và dùng user-facing locators:

```ts
import { test, expect, APIRequestContext } from '@playwright/test';

async function createOrder(
  request: APIRequestContext,
  testKey: string
): Promise<string> {
  const response = await request.post('/test-api/orders', {
    data: {
      customerEmail: `e2e-${testKey}@company.test`,
      status: 'Pending'
    }
  });

  expect(response.ok()).toBeTruthy();

  const body = await response.json();
  return body.id;
}

async function deleteOrder(
  request: APIRequestContext,
  orderId: string
): Promise<void> {
  await request.delete(`/test-api/orders/${orderId}`);
}

test('user can cancel an order', async ({ page, request }, testInfo) => {
  const orderId = await createOrder(request, testInfo.testId);

  try {
    await page.goto(`/orders/${orderId}`);

    await page.getByRole('button', { name: 'Cancel order' }).click();

    await expect(page.getByTestId('order-status'))
      .toHaveText('Cancelled');
  } finally {
    await deleteOrder(request, orderId);
  }
});

test('warehouse can ship an order', async ({ page, request }, testInfo) => {
  const orderId = await createOrder(request, testInfo.testId);

  try {
    await page.goto(`/orders/${orderId}`);

    await page.getByRole('button', { name: 'Ship order' }).click();

    await expect(page.getByRole('status'))
      .toContainText('Order shipped');

    await page.reload();

    await expect(page.getByTestId('order-status'))
      .toHaveText('Shipped');
  } finally {
    await deleteOrder(request, orderId);
  }
});
```

Trong code thực tế, `testInfo.testId` có thể chứa ký tự/độ dài không phù hợp để đưa thẳng vào email. Helper nên normalize/hash thành một test key hợp lệ. Ví dụ trên tập trung vào ownership concept chứ không định nghĩa email-format utility.

Tốt hơn nữa, project có thể tạo custom fixture `order` thực hiện setup/teardown per test và trả về `orderId`. Như vậy tests chỉ mô tả behavior, còn data isolation policy nằm trong một chỗ reusable.

Theo Playwright documentation hiện hành, tests dùng BrowserContexts cô lập browser state, nhưng parallel tests vẫn phải tự tránh shared state ở backend. Playwright locators và web-first assertions có auto-wait/retry behavior phù hợp hơn fixed sleeps cho UI state.

## Giải thích thiết kế sau khi sửa

Mỗi test giờ có precondition độc lập: một order `Pending` chỉ test đó sở hữu. Hai tests có thể chạy cùng lúc, đổi thứ tự, chạy trên shards khác hoặc retry mà không mutate cùng entity.

Fixed timeout bị loại bỏ. Test chờ trạng thái mà user quan sát được. Điều này không làm test “chậm hơn”; assertion có thể pass ngay khi condition đúng và chỉ chờ tới timeout khi thật sự cần.

Semantic locator giảm coupling với CSS. `getByTestId` vẫn là explicit testing contract và phù hợp khi element không có role/name tự nhiên; không cần ép mọi locator thành accessibility query nếu semantics không phù hợp.

Retry vẫn có thể giữ ở mức pipeline policy hợp lý cho transient browser/environment behavior, nhưng test phải pass ổn định khi chạy lặp lại không retry. Retry count cao không được coi là fix cho shared-state race.

## Trade-offs

Per-test data creation tăng số API/database operations và có thể làm suite chậm hơn. Đổi lại, tests parallelize an toàn và debugging đáng tin cậy hơn. Có thể tối ưu bằng lightweight test-data API hoặc fixtures, nhưng không quay lại shared mutable record.

Unique user per test có thể đắt nếu account provisioning phức tạp. Nếu user identity không chứa mutable shared state, có thể dùng một account nhưng tách order data; nếu account có server-side state, dùng worker-scoped account pool hoặc test namespace. Quyết định dựa trên actual isolation boundary.

E2E không nên test mọi permutation. Logic business chi tiết vẫn nên được cover ở unit/integration/API tests nhanh hơn; Playwright tập trung vào critical user journeys và frontend/backend integration.

Trace/video retention giúp debug nhưng tốn storage và có thể chứa dữ liệu nhạy cảm. Chỉ retain theo failure/retry policy và scrub/protect artifacts phù hợp.

## Cách kiểm thử

1. **Parallel stress test:** chạy hai tests lặp lại nhiều lần với nhiều workers và `fullyParallel`; không được có cross-test state conflict.
2. **Sharding validation:** chạy suite trên nhiều shards/machines dùng chung backend test environment; xác minh generated test data không collide.
3. **Slow-response test:** inject network/backend delay lớn hơn 2 giây; web-first assertions vẫn pass khi UI cuối cùng đúng mà không cần fixed sleep.
4. **Retry-state test:** cố tình fail assertion sau mutation ở attempt đầu; retry phải bắt đầu với entity độc lập phù hợp, không reuse corrupted business state.
5. **Selector resilience test:** thay đổi CSS class/layout không đổi accessible role/test contract; critical E2E không fail chỉ vì styling refactor.

## Quan sát trong production

Với CI/test environment, thu thập:

- Playwright trace cho failed/retried tests;
- screenshot/video theo retention policy;
- browser console errors;
- failed network requests/status codes;
- test ID, worker/shard ID và owned data ID;
- backend correlation ID để nối browser action tới ASP.NET Core/Application Insights logs;
- duration theo test và action;
- retry rate và flaky-test rate theo thời gian;
- setup/cleanup API failure rate;
- environment health signals như CPU, DB saturation hoặc dependency latency khi suite chạy.

Một dashboard tốt cần phân biệt ít nhất ba nhóm: product regression, test isolation/timing defect và test-environment instability. Nếu một test chỉ pass sau retry thường xuyên, đó vẫn là signal cần điều tra chứ không phải success hoàn toàn.

## Câu hỏi phỏng vấn mở rộng

1. Nếu tạo data per test làm CI chậm 40%, bạn sẽ tối ưu fixture architecture như thế nào mà vẫn giữ isolation?
2. Khi nào bạn chờ một network response cụ thể, và khi nào chỉ nên assert user-visible state thay vì coupling test vào implementation request?
3. Nếu một external sandbox chỉ cấp đúng một shared account không hỗ trợ concurrent mutation, bạn sẽ thiết kế test scheduling/isolation ra sao thay vì tắt parallel cho toàn bộ suite?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với Cosmos DB, query trả đúng kết quả chưa đủ; cần xem query được route tới đâu và RU được tiêu ở tầng nào. Partition key phải phản ánh access pattern thực tế.
- Lọc tenant trong application sau khi datastore đã trả dữ liệu không thay thế tenant-scoped query và có thể tạo cả security lẫn scalability risk.
- Continuation-based pagination giúp bound work tốt hơn việc loop nhiều backend pages để tự dựng một page UI.
- Playwright BrowserContext cô lập browser state, không tự cô lập database rows, external services hay account-scoped backend state.
- Parallel tests chỉ đáng tin cậy khi test data ownership độc lập; fixed sleep và retry cao không sửa được shared-state race.

## Mẫu tư duy cần nhớ

- Đưa filtering/routing tới đúng data boundary thay vì sửa hậu quả ở memory.
- Đo query cost trước khi mua thêm capacity.
- Thiết kế pagination để bound work của mỗi request.
- Test isolation phải bao phủ cả browser và backend state.
- Chờ một condition có ý nghĩa thay vì chờ một khoảng thời gian tùy ý.
