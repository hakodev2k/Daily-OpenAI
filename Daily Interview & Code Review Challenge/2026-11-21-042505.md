# Code Review Challenge 1 — Azure Service Bus xử lý hoàn tiền bị trùng

**Chủ đề:** .NET 8, Azure Service Bus, idempotency, transaction boundary, retries  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một nền tảng bán vé nhận sự kiện `RefundRequested` từ Azure Service Bus queue. Một ứng dụng .NET 8 chạy trên nhiều Azure App Service instances, mỗi instance có một worker. Worker ghi hoàn tiền vào PostgreSQL rồi gọi payment provider. Provider hỗ trợ `Idempotency-Key`, nhưng tài liệu nội bộ chưa xác nhận thời gian lưu key. Mỗi yêu cầu có `RefundId` ổn định và `OrderId`. Queue dùng PeekLock và có thể redeliver. Khi provider timeout, đội vận hành đôi lúc thấy hai khoản hoàn tiền hoặc trạng thái DB không khớp.

## Đoạn code cần review

```csharp
public sealed record RefundRequested(
    Guid RefundId, Guid OrderId, decimal Amount, string Currency);

public sealed class RefundWorker(
    ServiceBusClient bus,
    IServiceScopeFactory scopeFactory,
    HttpClient http,
    ILogger<RefundWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var processor = bus.CreateProcessor("refunds", new ServiceBusProcessorOptions
        {
            AutoCompleteMessages = false,
            MaxConcurrentCalls = 16
        });

        processor.ProcessMessageAsync += async args =>
        {
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var request = args.Message.Body.ToObjectFromJson<RefundRequested>();

            var existing = await db.Refunds
                .FirstOrDefaultAsync(x => x.RefundId == request.RefundId);

            if (existing is null)
            {
                db.Refunds.Add(new Refund
                {
                    RefundId = request.RefundId,
                    OrderId = request.OrderId,
                    Amount = request.Amount,
                    Status = "Pending"
                });
                await db.SaveChangesAsync();
            }

            var response = await http.PostAsJsonAsync("/refunds", new
            {
                request.OrderId,
                request.Amount,
                request.Currency
            });

            response.EnsureSuccessStatusCode();
            var row = await db.Refunds.SingleAsync(
                x => x.RefundId == request.RefundId);
            row.Status = "Completed";
            await db.SaveChangesAsync();
            await args.CompleteMessageAsync(args.Message);

            logger.LogInformation("Refund completed {RefundId}", request.RefundId);
        };

        processor.ProcessErrorAsync += args =>
        {
            logger.LogError(args.Exception, "Refund processor failed");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Gọi payment provider lại khi đã xử lý

**Vấn đề:** Dù `existing` tồn tại, code vẫn gọi `POST /refunds`.  
**Tại sao xảy ra:** Nhánh kiểm tra DB chỉ ngăn insert, không ngăn side effect. Message redelivery là hành vi cần dự liệu trong at-least-once processing.  
**Ảnh hưởng production:** Hoàn tiền trùng nếu provider không tự deduplicate.  
**Cách sửa:** Persist business idempotency key, kiểm tra trạng thái, truyền `Idempotency-Key` cố định đến provider và reconcile kết quả không xác định.

### [Critical] — HTTP timeout có thể tạo trạng thái không xác định

**Vấn đề:** Provider có thể đã hoàn tiền nhưng response bị mất.  
**Tại sao xảy ra:** HTTP timeout không rollback side effect bên ngoài.  
**Ảnh hưởng production:** Retry tạo khoản hoàn thứ hai hoặc operator xử lý thủ công sai.  
**Cách sửa:** Dùng provider idempotency key và lookup/reconciliation API (nếu hỗ trợ); không suy ra thất bại từ timeout. Nếu provider không bảo đảm idempotency, cần quy trình xác minh trước khi retry.

### [High] — Race condition khi insert

**Vấn đề:** Hai callbacks có thể cùng thấy không có row rồi cùng insert.  
**Tại sao xảy ra:** Read-then-insert không atomic.  
**Ảnh hưởng production:** Unique violation hoặc duplicate rows nếu thiếu constraint.  
**Cách sửa:** Unique index trên `RefundId`, xử lý unique conflict; claim state qua atomic conditional update/lease có thời hạn.

### [High] — Thiếu quản lý trạng thái và lease cho xử lý song song

**Vấn đề:** `Pending` không cho biết ai đang sở hữu xử lý, có được phép retry hay không.  
**Tại sao xảy ra:** Không có `Processing`, `AttemptId`, `LeaseUntil`, `Unknown` và state transition có điều kiện.  
**Ảnh hưởng production:** Nhiều worker đồng thời thực hiện cùng refund.  
**Cách sửa:** Durable state machine và atomic claim; stale lease chỉ được phục hồi qua reconciliation an toàn.

### [High] — Message lock và shutdown không được xử lý có chủ đích

**Vấn đề:** Không cấu hình thời gian auto-renew phù hợp; processor không được stop/dispose trong `finally`.  
**Tại sao xảy ra:** Callback có thể chạy lâu hơn lock, hoặc host shutdown giữa operation.  
**Ảnh hưởng production:** Redelivery trong lúc request cũ vẫn chạy; mất kiểm soát drain.  
**Cách sửa:** `await using` processor, `StopProcessingAsync` khi shutdown, bounded provider timeout, lock renewal phù hợp, idempotency độc lập với lock.

### [Medium] — Không truyền CancellationToken và không phân loại lỗi

**Vấn đề:** DB/HTTP/settlement bỏ qua cancellation, mọi exception được xử lý ngầm bởi processor.  
**Tại sao xảy ra:** Thiếu `args.CancellationToken` và policy cho transient/permanent failures.  
**Ảnh hưởng production:** Shutdown kéo dài, retries vô ích, DLQ thiếu thông tin.  
**Cách sửa:** Truyền token; validation lỗi vĩnh viễn thì dead-letter; transient thì abandon/retry theo bounded policy; lưu diagnostics không chứa dữ liệu nhạy cảm.

### [Medium] — Không kiểm tra business invariants

**Vấn đề:** Không kiểm tra amount/currency, order ownership và số tiền hoàn tối đa.  
**Tại sao xảy ra:** Tin message payload mà không kiểm tra against authoritative order data.  
**Ảnh hưởng production:** Hoàn tiền sai hoặc vượt giới hạn.  
**Cách sửa:** Validate domain invariants trong transaction và giới hạn quyền queue producer.

### [Medium] — Thiếu trace liên kết các bước

**Vấn đề:** Chỉ log thành công và exception chung.  
**Tại sao xảy ra:** Không có structured correlation theo `RefundId`, `MessageId`, `DeliveryCount`, provider request ID.  
**Ảnh hưởng production:** Khó điều tra double refund và reconciliation.  
**Cách sửa:** Metrics state transition, provider latency, unknown outcomes, retries, DLQ; distributed tracing và alert.

## Phiên bản đề xuất

Thiết kế dưới đây là **khung triển khai**: cần thêm migration, DI, timeout policy, adapter theo contract provider và reconciliation scheduler. Không xem nó là giao dịch distributed atomic.

```csharp
public sealed class RefundHandler(
    IDbContextFactory<AppDbContext> dbFactory,
    IPaymentGateway gateway,
    ILogger<RefundHandler> log)
{
    public async Task HandleAsync(RefundRequested message, CancellationToken ct)
    {
        if (message.Amount <= 0 || string.IsNullOrWhiteSpace(message.Currency))
            throw new InvalidRefundMessageException();

        await using var db = await dbFactory.CreateDbContextAsync(ct);

        // Implement ClaimAsync using a DB transaction, UNIQUE(RefundId),
        // conditional state transition and an expiring processing lease.
        var claim = await db.RefundClaims.ClaimAsync(
            message.RefundId, message.OrderId,
            message.Amount, message.Currency, ct);

        if (claim.State == ClaimState.Completed) return;
        if (claim.State == ClaimState.Busy)
            throw new RetryLaterException();

        // Persist the same key across attempts and worker restarts.
        var key = claim.ProviderIdempotencyKey;
        GatewayRefundResult result;
        try
        {
            result = await gateway.RefundAsync(
                message.OrderId, message.Amount, message.Currency, key, ct);
        }
        catch (GatewayOutcomeUnknownException)
        {
            await db.RefundClaims.MarkUnknownAsync(
                message.RefundId, claim.AttemptId, CancellationToken.None);
            throw new RetryLaterException("Reconcile before another payment attempt");
        }

        if (result.IsConfirmed)
        {
            await db.RefundClaims.CompleteIfOwnedAsync(
                message.RefundId, claim.AttemptId,
                result.ProviderReference, ct);
        }
        else
        {
            await db.RefundClaims.RecordFailureAsync(
                message.RefundId, claim.AttemptId, result.Code, ct);
            throw new RetryLaterException();
        }

        log.LogInformation("Refund confirmed {RefundId}", message.RefundId);
    }
}
```

Settlement ở adapter Service Bus: `Complete` **chỉ sau** khi handler xác nhận Completed hoặc đã thấy Completed; `RetryLater` dùng policy có backoff/delayed redelivery, không hot-loop; malformed message được `DeadLetter` với reason an toàn. `Unknown` không được tự động gửi lại request với key mới. `ClaimAsync` phải xác minh order, amount, currency và unique constraint, tránh race giữa workers. Nếu provider không hỗ trợ idempotency key đủ lâu, reconciliation phải xác nhận outcome trước khi retry.

## Giải thích thiết kế sau khi sửa

Database chịu trách nhiệm durable workflow state, không cố giả vờ transaction bao phủ provider. Atomic claim tránh hai active owners, nhưng lease expiry **không bảo đảm** request cũ đã dừng; provider idempotency vẫn bắt buộc. `AttemptId` bảo vệ stale worker khỏi ghi đè state mới. Settlement và database update vẫn có crash window, được hấp thụ bằng idempotency.

## Trade-offs

Thêm state machine, unique constraints, reconciliation và provider lookup làm tăng complexity/latency. Đổi lại giảm rủi ro hoàn tiền trùng. Có thể dùng Service Bus sessions để tuần tự hóa theo business key nếu thiết kế queue phù hợp, nhưng sessions không thay thế durable idempotency. Không nên áp dụng distributed lock đơn thuần như bằng chứng exactly-once.

## Cách kiểm thử

1. **Concurrency integration:** 100 deliveries cùng `RefundId` trên nhiều worker, provider ghi nhận tối đa một logical refund.
2. **Failure-path:** Provider hoàn tiền thành công nhưng HTTP timeout; recovery tra cứu outcome, không tạo refund mới.
3. **Crash test:** Kill worker sau provider success trước DB commit và trước message completion.
4. **Database test:** Unique constraint, stale lease, concurrent claim, attempt fencing và invariant tổng tiền hoàn.
5. **Retry/DLQ:** malformed payload, transient 429/503, expired lock, shutdown; xác nhận policy không hot-loop.

## Quan sát trong production

Application Insights trace `RefundId`/message ID/provider reference (không log credentials hay dữ liệu thanh toán nhạy cảm). Dashboard: duplicate claims, Unknown age, pending backlog, Service Bus delivery count, DLQ count, provider 429/5xx, p95 request duration, reconciliation success. Alert khi Unknown quá SLA hoặc một order có nhiều confirmed refunds vượt giới hạn.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không có idempotency API và không hỗ trợ lookup, bạn thay đổi SLA/operational control ra sao?
2. Nếu lease hết hạn khi provider request vẫn chạy, cách nào ngăn owner mới gây side effect?
3. Khi nào dùng Outbox Pattern, và nó giải quyết phần nào so với provider idempotency?

## Kết quả code review tham khảo

### [Critical] — Secret nằm trực tiếp trong manifest

**Vấn đề:** `Search__ApiKey` là plaintext.  
**Tại sao xảy ra:** Manifest có thể được commit, xuất qua CI logs hoặc đọc bởi người có quyền xem workload.  
**Ảnh hưởng production:** Credential exposure và unauthorized API usage.  
**Cách sửa:** Dùng external secret integration/secret manager hoặc Kubernetes Secret với RBAC, encryption at rest và rotation; ưu tiên workload identity nếu provider hỗ trợ.

### [High] — Liveness phụ thuộc external services

**Vấn đề:** Search/CMS/SQL timeout làm liveness fail.  
**Tại sao xảy ra:** Endpoint tổng hợp dùng chung cho readiness và liveness.  
**Ảnh hưởng production:** Restart storm, giảm availability dù app có thể phục vụ cached content.  
**Cách sửa:** `/health/live` chỉ kiểm tra khả năng sống của process; readiness đánh giá các điều kiện thực sự cần để phục vụ traffic, không buộc optional search thành điều kiện toàn hệ thống.

### [High] — Rollout làm giảm capacity quá mức

**Vấn đề:** `maxSurge: 0`, `maxUnavailable: 1` với hai replicas cho phép chỉ một replica sẵn sàng trong rollout.  
**Tại sao xảy ra:** Không tạo Pod mới trước khi loại Pod cũ.  
**Ảnh hưởng production:** Capacity hụt, 503 dưới load.  
**Cách sửa:** `maxSurge: 1`, `maxUnavailable: 0`, bảo đảm node capacity và readiness chính xác; kiểm tra PodDisruptionBudget nếu phù hợp.

### [High] — Mutable image tag

**Vấn đề:** `:latest` không pin artifact.  
**Tại sao xảy ra:** Tag có thể trỏ sang image khác giữa các deploy; rollback không reproducible.  
**Ảnh hưởng production:** Mixed versions, khó audit/rollback.  
**Cách sửa:** Pin digest `@sha256:...` từ CI, promote cùng artifact qua environments.

### [Medium] — Probe timing quá gắt và thiếu startup protection

**Vấn đề:** Timeout 1 giây và initial delay ngắn có thể fail trong warm-up, GC hoặc CPU throttling.  
**Tại sao xảy ra:** Không có `startupProbe`, thresholds chưa dựa trên measurements.  
**Ảnh hưởng production:** Pod bị restart trước khi warm-up xong.  
**Cách sửa:** Startup probe, thresholds theo cold-start distribution; readiness phản ánh app initialization.

### [Medium] — Không khai báo resource requests

**Vấn đề:** Chỉ có limits.  
**Tại sao xảy ra:** Scheduler không có requested capacity chính xác, dễ tranh chấp CPU/memory.  
**Ảnh hưởng production:** CPU throttling, OOMKill, rollout pending.  
**Cách sửa:** Đặt requests dựa trên p95 CPU/memory profile, limits theo policy cluster; kiểm tra OOM/throttling trước khi tăng.

### [Medium] — Không mô tả graceful termination

**Vấn đề:** Không có `terminationGracePeriodSeconds` và ứng dụng chưa chứng minh drain request.  
**Tại sao xảy ra:** Pod termination có race với endpoint propagation và request in-flight.  
**Ảnh hưởng production:** Request bị ngắt khi rolling update.  
**Cách sửa:** App xử lý SIGTERM, stop accepting new work, hoàn thành in-flight trong bounded grace period; kiểm tra ingress/Service propagation, cân nhắc preStop delay nếu được đo lường cần thiết.

### [Medium] — Thiếu deployment signals

**Vấn đề:** Không có `minReadySeconds`, rollout monitoring hay dependency-degraded metrics.  
**Tại sao xảy ra:** Một Pod thoáng Ready có thể được coi là rollout thành công.  
**Ảnh hưởng production:** Regression lọt qua release gate.  
**Cách sửa:** `minReadySeconds`, `progressDeadlineSeconds`, canary/synthetic checks và rollback criteria.

```yaml
      targetPort: 8080
```

Ví dụ `/health/live` chỉ trả healthy nếu process có khả năng xử lý request; `/health/ready` kiểm tra startup completed và những dependency **bắt buộc** để phục vụ core pages. Search outage có thể trả degraded metric và fallback UI thay vì 503 readiness, **nếu** cached page vẫn đáp ứng requirement. `replicas: 3` chỉ là giả định capacity, cần load test để chốt.

## Giải thích thiết kế sau khi sửa

Readiness thất bại khiến Pod không được chọn làm endpoint mới của Service, không nhất thiết restart process. Liveness thất bại có thể dẫn đến container restart. Startup probe bảo vệ warm-up khỏi liveness/readiness evaluation đến khi startup thành công. `maxUnavailable: 0` bảo toàn số Pod available theo rollout semantics, nhưng không bảo đảm zero downtime nếu toàn cluster thiếu capacity hoặc ứng dụng không graceful. Kubernetes Secret không tự động giải quyết mọi rủi ro: phải cấu hình RBAC, encryption, rotation và giới hạn quyền đọc.

## Trade-offs

Surge và replicas tăng chi phí compute. Startup thresholds quá rộng có thể che giấu deadlock; readiness quá nghiêm ngặt gây outage toàn cluster, quá lỏng gây lỗi cho người dùng. App Service có thể đơn giản hơn Kubernetes nếu không cần orchestration-specific features; quyết định dựa trên yêu cầu networking, release, operations và total cost, không dựa vào sở thích công nghệ.

## Cách kiểm thử

1. **Failure injection:** Search API timeout 30 giây; cached CMS pages vẫn phục vụ, không restart storm.
2. **Deployment validation:** Rolling update dưới load, đo 5xx, p95 và số available endpoints.
3. **Startup test:** Cold start dài hơn 30 giây; startup probe tránh kill sớm nhưng phát hiện process thật sự không khởi động.
4. **Security test:** Manifest, CI logs và runtime permissions không lộ secret; rotation được kiểm chứng.
5. **Graceful shutdown:** SIGTERM trong request dài; xác minh drain và không mất request vượt SLA.

## Quan sát trong production

Azure Monitor/Application Insights: request 5xx, p95/p99, search dependency timeout, cache fallback rate. Kubernetes: ready replicas, restart count, probe failures, OOMKilled, CPU throttling, rollout progress, pending pods. Alert khi available replicas thấp hơn mục tiêu, 5xx vượt SLO hoặc dependency degraded kéo dài; liên kết deployment revision/digest với incident timeline.

## Câu hỏi phỏng vấn mở rộng

# Tổng kết hôm nay

## Kiến thức trọng tâm

- At-least-once delivery đòi hỏi business idempotency; message settlement không thể atomic cùng payment provider.
- Durable state, conditional claim, provider idempotency và reconciliation xử lý crash windows.
- Kubernetes liveness khác readiness; external dependency degradation không mặc định đồng nghĩa process failure.
- Rollout availability phụ thuộc cả surge capacity, graceful termination, immutable artifacts và observability.

## Mẫu tư duy cần nhớ

3. Đo availability và capacity khi rolling update, không chỉ kiểm tra YAML hợp lệ.
4. Tách process health khỏi dependency degradation và user-visible functionality.
5. Kiểm thử crash window, dependency outage và recovery path trước khi release.
