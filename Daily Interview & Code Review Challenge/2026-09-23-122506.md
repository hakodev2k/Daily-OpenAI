# Code Review Challenge 1 — Cosmos DB query chạy ổn ở staging nhưng tăng RU và latency khi production scale

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Cosmos DB, partition key, query cost, pagination, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một ASP.NET Core API phục vụ màn hình lịch sử activity của khách hàng. Dữ liệu được lưu trong Azure Cosmos DB container `activities`. Production có hàng chục triệu documents, nhiều tenants và traffic tăng mạnh vào giờ cao điểm. Container hiện partition theo `/tenantId`.

Support ghi nhận endpoint đôi lúc mất 4–8 giây, RU consumption tăng đột biến và có `429` khi một tenant lớn mở màn hình lịch sử. Staging chỉ có vài nghìn documents nên không tái hiện được. Product yêu cầu phân trang 50 items/lần và sort mới nhất trước.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/activities")]
public sealed class ActivitiesController : ControllerBase
{
    private readonly Container _container;

    public ActivitiesController(Container container)
    {
        _container = container;
    }

    [HttpGet]
    public async Task<IActionResult> Get(
        string tenantId,
        string customerId,
        int page = 1,
        int pageSize = 50)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.customerId = @customerId " +
            "ORDER BY c.createdAtUtc DESC")
            .WithParameter("@customerId", customerId);

        var iterator = _container.GetItemQueryIterator<ActivityDocument>(
            query,
            requestOptions: new QueryRequestOptions
            {
                MaxItemCount = page * pageSize
            });

        var all = new List<ActivityDocument>();

        while (iterator.HasMoreResults)
        {
            var response = await iterator.ReadNextAsync();
            all.AddRange(response);
        }

        var result = all
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .ToList();

        return Ok(result);
    }
}
```

Document mẫu:

```json
{
  "id": "01J...",
  "tenantId": "tenant-42",
  "customerId": "customer-9182",
  "createdAtUtc": "2026-09-23T04:10:00Z",
  "type": "OrderViewed",
  "payload": { }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong filtering/pagination.
2. Xác định nguyên nhân có thể làm RU/latency tăng theo data volume.
3. Phân tích partition-key behavior thay vì chỉ nói “Cosmos DB chậm”.
4. Nêu production impact và ưu tiên severity.
5. Đề xuất query/API contract tốt hơn.
6. Giải thích testing strategy với production-like cardinality.
7. Nêu telemetry cần thu thập để chứng minh giả thuyết.

## Câu hỏi gợi mở

1. Query có cung cấp partition key cho Cosmos DB không?
2. `tenantId` được nhận từ request nhưng đang được dùng ở đâu?
3. `MaxItemCount` có tương đương SQL `LIMIT/OFFSET` không?
4. Vì sao đọc hết iterator rồi `Skip` trong memory làm cost tăng theo dữ liệu?
5. Continuation token phù hợp với Cosmos DB hơn page-number pagination ở điểm nào?

## Gợi ý

### Gợi ý 1

Tập trung vào query routing, số partition bị quét và lượng dữ liệu thực sự được đọc trước khi response được tạo.

### Gợi ý 2

Cosmos DB pagination có continuation token. Hãy xem API contract hiện tại đang ép backend mô phỏng offset pagination như thế nào.

## Kết quả code review tham khảo

### Critical — Tenant boundary không được enforce trong query

**Vấn đề:** `tenantId` được nhận nhưng query chỉ filter `customerId`.  
**Tại sao xảy ra:** Application bỏ qua partition/authorization boundary trong data access.  
**Ảnh hưởng production:** Nếu `customerId` không globally unique hoặc authorization chỉ dựa vào input này, dữ liệu tenant khác có thể bị trả về. Đây vừa là correctness vừa là security issue.  
**Cách sửa:** Tenant identity phải lấy từ trusted authorization context khi phù hợp, query phải scope theo tenant và request phải truyền đúng `PartitionKey`.

### High — Query không scope vào logical partition

**Vấn đề:** `QueryRequestOptions` không có `PartitionKey`.  
**Tại sao xảy ra:** Container partition theo `/tenantId` nhưng query không cung cấp tenant partition.  
**Ảnh hưởng production:** Query có thể trở thành cross-partition query, tăng RU và latency theo số partition/data distribution.  
**Cách sửa:** Khi requirement luôn query trong một tenant, truyền `new PartitionKey(tenantId)` và giữ filter tenant rõ ràng trong query để code dễ audit.

### High — Đọc toàn bộ result set rồi mới phân trang trong memory

**Vấn đề:** Loop đọc đến khi iterator hết.  
**Tại sao xảy ra:** Code hiểu iterator như một cách lấy “page hiện tại”, nhưng thực tế nó tiếp tục đọc các result pages.  
**Ảnh hưởng production:** RU, network bytes, allocations và latency tăng theo tổng số activity của customer.  
**Cách sửa:** API dùng continuation token và chỉ đọc lượng cần cho response hiện tại; không materialize toàn bộ lịch sử.

### High — `MaxItemCount` bị hiểu như total limit

**Vấn đề:** `MaxItemCount = page * pageSize` không giới hạn tổng query result.  
**Tại sao xảy ra:** Đây là request option cho kích thước page trả về từ query iterator, không phải SQL-style total `LIMIT`.  
**Ảnh hưởng production:** Developer tưởng query đã bounded trong khi loop vẫn đọc tiếp.  
**Cách sửa:** Dùng continuation token và dừng sau response page phù hợp; thiết kế contract theo cursor.

### Medium — Page-number pagination không phù hợp với access pattern hiện tại

**Vấn đề:** `Skip` được thực hiện sau khi tải dữ liệu.  
**Tại sao xảy ra:** API contract yêu cầu random page number nhưng storage API tự nhiên hỗ trợ continuation token.  
**Ảnh hưởng production:** Deep pages ngày càng đắt và khó giữ consistency khi dữ liệu mới được insert.  
**Cách sửa:** Trả opaque continuation token cho client; nếu business bắt buộc random access cần đánh giá read model/index khác thay vì giả lập bằng full scan.

### Medium — Không validate page/pageSize

**Vấn đề:** Giá trị âm, zero hoặc rất lớn chưa bị chặn.  
**Tại sao xảy ra:** Thiếu input constraints.  
**Ảnh hưởng production:** Có thể tạo request tốn tài nguyên hoặc kết quả khó đoán.  
**Cách sửa:** Giới hạn page size theo API policy; với cursor API có thể bỏ `page` hoàn toàn.

### Medium — Không propagate request cancellation

**Vấn đề:** `ReadNextAsync()` không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Cancellation token không đi qua I/O chain.  
**Ảnh hưởng production:** Client rời đi nhưng backend vẫn tiếp tục tiêu RU/network.  
**Cách sửa:** Nhận `CancellationToken` trong action và truyền xuống SDK.

### Medium — Không quan sát request charge và throttling

**Vấn đề:** Code bỏ qua diagnostics/request charge của Cosmos response.  
**Tại sao xảy ra:** Endpoint chỉ quan tâm documents.  
**Ảnh hưởng production:** Khó phân biệt query fan-out, hot partition, throttling và network latency.  
**Cách sửa:** Ghi metrics cho RU/request, latency, 429/retry, continuation behavior và diagnostics phù hợp; không log payload nhạy cảm.

### Low — `SELECT *` tăng payload khi UI chỉ cần summary

**Vấn đề:** Toàn bộ document/payload được tải.  
**Tại sao xảy ra:** Không projection theo read use case.  
**Ảnh hưởng production:** Network/serialization và có thể RU cao hơn mức cần thiết tùy document/index/query.  
**Cách sửa:** Projection các field UI thực sự cần và đo lại RU/latency.

## Phiên bản đề xuất

```csharp
public sealed record ActivityPage(
    IReadOnlyList<ActivitySummary> Items,
    string? ContinuationToken);

[HttpGet]
public async Task<ActionResult<ActivityPage>> Get(
    string customerId,
    string? continuationToken,
    int pageSize = 50,
    CancellationToken cancellationToken = default)
{
    if (pageSize is < 1 or > 100)
        return BadRequest("pageSize must be between 1 and 100.");

    var tenantId = GetAuthorizedTenantId(User);

    var query = new QueryDefinition("""
        SELECT c.id, c.customerId, c.createdAtUtc, c.type
        FROM c
        WHERE c.tenantId = @tenantId
          AND c.customerId = @customerId
        ORDER BY c.createdAtUtc DESC
        """)
        .WithParameter("@tenantId", tenantId)
        .WithParameter("@customerId", customerId);

    using var iterator = _container.GetItemQueryIterator<ActivitySummary>(
        query,
        continuationToken,
        new QueryRequestOptions
        {
            PartitionKey = new PartitionKey(tenantId),
            MaxItemCount = pageSize
        });

    if (!iterator.HasMoreResults)
        return Ok(new ActivityPage([], null));

    var response = await iterator.ReadNextAsync(cancellationToken);

    RecordCosmosMetrics(response.RequestCharge, response.Diagnostics);

    return Ok(new ActivityPage(
        response.Resource.ToList(),
        response.ContinuationToken));
}
```

Nếu một logical tenant trở nên quá lớn/hot, không nên tự động đổi partition key chỉ từ triệu chứng này. Cần đo traffic distribution, RU theo partition, item growth và access patterns trước; thay partition strategy là data-model/migration decision có chi phí lớn.

## Giải thích thiết kế sau khi sửa

Query được route vào tenant partition và tenant identity đến từ authorization context. API chuyển từ page number sang cursor/continuation token để không phải đọc toàn bộ dữ liệu trước page hiện tại. Projection giảm payload. Cancellation và RU telemetry trở thành một phần của design.

## Trade-offs

Continuation token hiệu quả nhưng client không thể nhảy tùy ý tới page 500. Token cũng nên được coi là opaque. Partition theo tenant rất phù hợp khi access pattern tenant-scoped và distribution đủ tốt, nhưng tenant cực lớn có thể trở thành hot partition; khi đó cần dữ liệu thực tế trước khi chọn hierarchical/alternative partitioning hoặc read model khác.

## Cách kiểm thử

1. Integration test với nhiều tenants và trùng `customerId`, xác minh không cross-tenant data leak.
2. Seed production-like volume, so sánh RU/latency giữa cross-partition/full-materialization và partition-scoped cursor query.
3. Test nhiều continuation pages trong khi có inserts mới; document rõ consistency kỳ vọng của UI.
4. Failure-path test tạo throttling/429 hợp lý và xác minh retry/telemetry, không tạo retry storm ở application layer.
5. Test client cancellation giữa query và xác minh operation dừng sớm.

## Quan sát trong production

Theo dõi RU/request, normalized RU consumption, 429 count, retry delay, p50/p95/p99, diagnostics, response item count, continuation-page count, partition-level traffic khi có thể, request cancellation và Application Insights dependency telemetry. Correlate theo tenant identifier đã được xử lý an toàn, không log payload.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một tenant chiếm 70% traffic nhưng chỉ 10% data, bạn cần đo gì trước khi thay partition strategy?
2. Khi nào SQL Server với composite index/keyset pagination có thể đơn giản hơn Cosmos DB cho use case này?
3. Nếu Product bắt buộc “jump to arbitrary page”, bạn sẽ thay đổi read model/API thế nào?

# Code Review Challenge 2 — React lưu access token sai chỗ và tạo XSS thành account takeover

**Chủ đề:** React, TypeScript, ASP.NET Core API integration, XSS, token handling, authorization, frontend security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một React admin portal gọi ASP.NET Core API. Sau login, frontend nhận access token và lưu để dùng cho các request tiếp theo. Portal cũng hiển thị “announcement HTML” do admin nhập từ CMS. Security team báo rằng một tài khoản CMS bị compromise có thể chỉnh announcement.

API vẫn phải enforce authorization server-side. Frontend không được coi việc ẩn button là security boundary. Requirement chưa xác định bắt buộc phải dùng cookie hay bearer token; ứng viên cần phân tích threat model và auth architecture trước khi chọn.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

export function AdminDashboard() {
  const [announcement, setAnnouncement] = useState("");
  const [users, setUsers] = useState<User[]>([]);

  useEffect(() => {
    const token = localStorage.getItem("access_token");

    fetch("/api/admin/dashboard", {
      headers: {
        Authorization: `Bearer ${token}`
      }
    })
      .then(r => r.json())
      .then(data => {
        setAnnouncement(data.announcementHtml);
        setUsers(data.users);
      });
  }, []);

  async function deleteUser(id: string) {
    const token = localStorage.getItem("access_token");

    await fetch(`/api/admin/users/${id}`, {
      method: "DELETE",
      headers: {
        Authorization: `Bearer ${token}`
      }
    });

    setUsers(users.filter(x => x.id !== id));
  }

  return (
    <main>
      <section
        dangerouslySetInnerHTML={{ __html: announcement }}
      />

      {users.map(user => (
        <div key={user.id}>
          <span>{user.email}</span>
          <button onClick={() => deleteUser(user.id)}>
            Delete
          </button>
        </div>
      ))}
    </main>
  );
}
```

1. Xác định security/correctness/reliability issues.
2. Mô tả exploit chain khả thi thay vì chỉ liệt kê “XSS”.
3. Phân biệt authentication token storage với authorization enforcement.
4. Ưu tiên findings theo production impact.
5. Đề xuất frontend + backend design đã sửa.
6. Nêu security/E2E tests.
7. Nêu telemetry giúp phát hiện abuse mà không log secrets.

## Câu hỏi gợi mở

1. Nếu announcement chứa script-capable payload, token trong `localStorage` có thể bị ảnh hưởng thế nào?
2. React escape text mặc định, nhưng `dangerouslySetInnerHTML` thay đổi điều gì?
3. Nếu button bị ẩn với non-admin thì API có an toàn hơn không?

## Kết quả code review tham khảo

### Critical — Untrusted HTML được render trực tiếp vào privileged admin origin

**Vấn đề:** `announcementHtml` đi vào `dangerouslySetInnerHTML` mà không có bằng chứng đã sanitize bằng policy phù hợp.  
**Tại sao xảy ra:** CMS content được coi là trusted chỉ vì người nhập là admin.  
**Ảnh hưởng production:** Nếu attacker kiểm soát CMS content và tạo được active content trong browser context, họ có thể thực hiện actions với quyền của admin; với bearer token đọc được từ JavaScript, impact có thể mở rộng thành credential theft.  
**Cách sửa:** Tránh raw HTML nếu không cần; nếu business cần rich HTML, sanitize bằng allowlist được duy trì ở trust boundary phù hợp, áp dụng CSP như defense-in-depth và test payload thực tế.

### High — Bearer token trong `localStorage` làm tăng impact của XSS

**Vấn đề:** JavaScript cùng origin có thể đọc token.  
**Tại sao xảy ra:** Token được persist trong browser storage có JS access.  
**Ảnh hưởng production:** XSS có thể exfiltrate reusable credential, tùy token audience/scope/lifetime.  
**Cách sửa:** Chọn auth architecture theo threat model. Với same-origin web app, cân nhắc BFF hoặc secure `HttpOnly`, `Secure`, appropriate `SameSite` cookie; nếu dùng cookie phải thiết kế CSRF protection phù hợp. Nếu bearer token trong browser là bắt buộc, giảm lifetime/scope và ưu tiên loại bỏ XSS source; không coi storage change là fix duy nhất.

### High — Client UI không phải authorization boundary

**Vấn đề:** Code không cho thấy guarantee rằng DELETE API enforce admin policy/resource authorization.  
**Tại sao xảy ra:** Frontend có thể tạo cảm giác “chỉ admin thấy button”.  
**Ảnh hưởng production:** Attacker có thể gọi API trực tiếp nếu backend authorization thiếu/sai.  
**Cách sửa:** ASP.NET Core endpoint phải dùng policy/claims/resource authorization server-side; frontend visibility chỉ là UX.

### Medium — Không kiểm tra HTTP status trước khi parse/update state

**Vấn đề:** Dashboard luôn gọi `r.json()` và delete luôn remove user khỏi UI.  
**Tại sao xảy ra:** Network/API failure path bị bỏ qua.  
**Ảnh hưởng production:** UI báo trạng thái sai khi 401/403/500/network timeout.  
**Cách sửa:** Centralize API client, kiểm tra status, mapping ProblemDetails/error và chỉ mutate local state sau success.

### Medium — Không có cancellation cho request khi component unmount

**Vấn đề:** Fetch tiếp tục dù component lifecycle đã kết thúc.  
**Tại sao xảy ra:** Không dùng `AbortController`.  
**Ảnh hưởng production:** Waste network và có thể tạo stale state behavior trong flow phức tạp hơn.  
**Cách sửa:** Abort request trong effect cleanup.

### Medium — Stale closure khi update users

**Vấn đề:** `setUsers(users.filter(...))` dùng snapshot `users` tại render tạo handler.  
**Tại sao xảy ra:** Concurrent UI updates có thể làm state mới hơn bị ghi đè.  
**Ảnh hưởng production:** Danh sách UI có thể mất update khi nhiều operations gần nhau.  
**Cách sửa:** Functional update: `setUsers(current => current.filter(...))`.

### Medium — Auth failure handling không được centralize

**Vấn đề:** Mỗi function tự lấy token và tự gọi fetch.  
**Tại sao xảy ra:** Thiếu API/auth boundary.  
**Ảnh hưởng production:** Inconsistent 401/403 behavior, token refresh logic dễ race và khó audit.  
**Cách sửa:** Dùng typed API client/auth layer với một policy rõ cho credentials, refresh và error mapping.

### Low — Thiếu security telemetry cho privileged operation

**Vấn đề:** Frontend/backend flow không thể hiện audit trail.  
**Tại sao xảy ra:** Chỉ tập trung UI behavior.  
**Ảnh hưởng production:** Khó điều tra mass deletion/authorization failures.  
**Cách sửa:** Backend audit event cho privileged action với actor/resource/result/correlation ID; tuyệt đối không log access token.

## Phiên bản đề xuất

Ví dụ dưới đây giả định team chọn same-origin session/BFF-style cookie sau khi đánh giá architecture; cookie được server phát với flags phù hợp và server có CSRF strategy tương ứng. Nếu hệ thống buộc phải dùng SPA bearer token flow thì credential handling sẽ khác, nhưng XSS sanitization và server-side authorization vẫn bắt buộc.

```tsx
import { useEffect, useState } from "react";

export function AdminDashboard() {
  const [announcementText, setAnnouncementText] = useState("");
  const [users, setUsers] = useState<User[]>([]);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();

    async function load() {
      try {
        const response = await fetch("/api/admin/dashboard", {
          credentials: "same-origin",
          signal: controller.signal
        });

        if (!response.ok)
          throw new Error(`Dashboard failed: ${response.status}`);

        const data: DashboardResponse = await response.json();
        setAnnouncementText(data.announcementText);
        setUsers(data.users);
      } catch (e) {
        if (!controller.signal.aborted)
          setError("Unable to load dashboard.");
      }
    }

    void load();
    return () => controller.abort();
  }, []);

  async function deleteUser(id: string) {
    const response = await fetch(`/api/admin/users/${encodeURIComponent(id)}`, {
      method: "DELETE",
      credentials: "same-origin",
      headers: {
        "X-CSRF-Token": getCsrfToken()
      }
    });

    if (!response.ok) {
      setError("Delete failed.");
      return;
    }

    setUsers(current => current.filter(x => x.id !== id));
  }

  return (
    <main>
      {error && <p role="alert">{error}</p>}
      <section>{announcementText}</section>

      {users.map(user => (
        <div key={user.id}>
          <span>{user.email}</span>
          <button onClick={() => void deleteUser(user.id)}>
            Delete
          </button>
        </div>
      ))}
    </main>
  );
}
```

ASP.NET Core vẫn phải enforce authorization, ví dụ policy ở endpoint/controller và resource-level checks nếu operation phụ thuộc tenant/resource. CSRF token trong snippet chỉ minh họa rằng cookie-based auth cần CSRF design; implementation cụ thể phụ thuộc framework/auth architecture và không nên tự chế crypto/token protocol.

## Giải thích thiết kế sau khi sửa

Rich HTML được loại bỏ khỏi ví dụ vì requirement chưa chứng minh cần thiết. Nếu cần rich content, phải có explicit sanitization policy. Credential architecture được đưa về một boundary thay vì đọc `localStorage` ở mọi component. Backend giữ quyền quyết định authorization. UI chỉ phản ánh kết quả server.

## Trade-offs

`HttpOnly` cookie giảm khả năng JavaScript đọc credential nhưng không loại bỏ XSS: malicious script vẫn có thể thực hiện same-origin actions trong browser session. Cookie auth cũng yêu cầu CSRF reasoning. BFF tăng server-side complexity nhưng có thể giảm token exposure trong browser. Bearer token SPA có thể hợp lý trong một số architecture; khi đó token lifetime/scope, XSS prevention và refresh design cần được đánh giá riêng.

## Cách kiểm thử

1. Security test CMS content chứa representative XSS payloads; xác minh output không tạo executable DOM.
2. API authorization integration test gọi DELETE với user không có admin policy, bất kể frontend button visibility.
3. Nếu dùng cookie auth, CSRF integration test request thiếu/sai anti-forgery signal phải bị reject theo policy.
4. Playwright E2E cho 401/403/500/network failure; UI không xóa user giả khi backend fail.
5. Test rapid concurrent deletes/state updates để xác minh functional state update không làm mất thay đổi.

## Quan sát trong production

Theo dõi 401/403 rate, privileged DELETE audit events, unusual delete volume, CSP violation reports nếu triển khai CSP reporting, frontend error rate và API correlation IDs. Không log bearer token, cookie, authorization header hoặc CMS content nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao chuyển token từ `localStorage` sang `HttpOnly` cookie không tự động “fix XSS”?
2. Nếu portal và API khác origin, bạn sẽ đánh giá CORS, cookie/SameSite và CSRF thế nào?
3. Nếu business bắt buộc rich HTML từ CMS, bạn đặt sanitization ở CMS, API hay browser — và vì sao có thể cần nhiều lớp?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB query cần được thiết kế theo partition/access pattern; staging data nhỏ có thể che cross-partition scan và pagination cost.
- Continuation token phù hợp hơn việc materialize toàn bộ dữ liệu rồi mô phỏng offset pagination.
- Multi-tenant boundary phải được enforce bằng trusted identity và data-access scope, không chỉ nhận `tenantId` từ query string.
- Browser security cần reasoning theo chuỗi trust boundary; XSS, credential storage, CSRF và server-side authorization liên quan nhưng không thay thế nhau.
- Frontend visibility không bao giờ thay thế backend authorization.

## Mẫu tư duy cần nhớ

- Đo RU/latency/partition behavior trước khi đổi data model.
- Đưa authorization boundary xuống nơi dữ liệu và side effect thực sự được bảo vệ.
- Không materialize dữ liệu lớn chỉ để phân trang ở application memory.
- Xem untrusted content và browser credential như các trust boundaries riêng.
- Security fix phải xét exploit chain và failure mode, không chỉ đổi một API.
