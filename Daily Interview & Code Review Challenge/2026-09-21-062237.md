# Code Review Challenge 1 — `IAsyncDisposable` bị bỏ qua khi export stream thất bại giữa chừng

**Chủ đề:** C#/.NET, ASP.NET Core, `IAsyncDisposable`, async resource lifetime, cancellation, streaming, connection pool, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core API export báo cáo lớn từ PostgreSQL. Repository mở một database reader và trả về wrapper triển khai `IAsyncDisposable`; controller stream từng row thành CSV. Ở local file nhỏ chạy ổn. Production đôi lúc client đóng tab giữa lúc download, reverse proxy timeout, hoặc serialization ném exception do dữ liệu lỗi. Sau các đợt export lớn, pool bắt đầu thiếu connection và request khác chậm theo.

Team nghi ngờ “PostgreSQL pool quá nhỏ” và muốn tăng pool size. Chưa có bằng chứng leak nằm ở database driver, application resource ownership hay downstream network. Hãy review code trước khi thay đổi capacity.

## Đoạn code cần review

```csharp
public sealed class ExportSession : IAsyncDisposable
{
    public NpgsqlConnection Connection { get; }
    public NpgsqlDataReader Reader { get; }

    public ExportSession(NpgsqlConnection connection, NpgsqlDataReader reader)
    {
        Connection = connection;
        Reader = reader;
    }

    public async ValueTask DisposeAsync()
    {
        await Reader.DisposeAsync();
        await Connection.DisposeAsync();
    }
}

public sealed class ReportRepository
{
    private readonly string _connectionString;

    public ReportRepository(IConfiguration configuration)
        => _connectionString = configuration.GetConnectionString("Reports")!;

    public async Task<ExportSession> OpenExportAsync(DateTime from, DateTime to)
    {
        var connection = new NpgsqlConnection(_connectionString);
        await connection.OpenAsync();

        var command = connection.CreateCommand();
        command.CommandText = """
            SELECT id, created_at, customer_email, amount
            FROM report_rows
            WHERE created_at >= @from AND created_at < @to
            ORDER BY created_at, id
            """;
        command.Parameters.AddWithValue("from", from);
        command.Parameters.AddWithValue("to", to);

        var reader = await command.ExecuteReaderAsync();
        return new ExportSession(connection, reader);
    }
}

[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly ReportRepository _repository;

    public ReportsController(ReportRepository repository)
        => _repository = repository;

    [HttpGet("export")]
    public async Task Export(DateTime from, DateTime to)
    {
        var session = await _repository.OpenExportAsync(from, to);

        Response.ContentType = "text/csv";
        await Response.WriteAsync("id,createdAt,email,amount\n");

        while (await session.Reader.ReadAsync())
        {
            var line = $"{session.Reader.GetGuid(0)},{session.Reader.GetDateTime(1):O}," +
                       $"{session.Reader.GetString(2)},{session.Reader.GetDecimal(3)}\n";

            await Response.WriteAsync(line);
        }

        await session.DisposeAsync();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness/resource ownership trong success path và failure path.
2. Phân tích ảnh hưởng performance/reliability khi client disconnect, query lỗi hoặc response write lỗi.
3. Ưu tiên finding theo production impact thay vì style.
4. Đề xuất ownership boundary và corrected design.
5. Giải thích cancellation nên đi từ HTTP request tới database/network như thế nào.
6. Đề xuất tests cho success, cancellation và injected failure.
7. Đề xuất telemetry để chứng minh connection exhaustion có hoặc không liên quan resource leak.

## Câu hỏi gợi mở

1. Điều gì xảy ra với `session.DisposeAsync()` nếu `ReadAsync()` hoặc `Response.WriteAsync()` ném exception?
2. Nếu `OpenAsync()` thành công nhưng `ExecuteReaderAsync()` thất bại thì connection thuộc về ai?
3. `await using` giải quyết phần nào, và phần nào vẫn cần repository tự cleanup?
4. `HttpContext.RequestAborted` nên được truyền tới những operation nào?
5. Tăng pool size có chữa root cause nếu connection không được trả về pool đúng lúc không?

## Gợi ý

### Gợi ý 1

Resource cleanup phải đúng cho mọi exit path, không chỉ dòng cuối của happy path.

### Gợi ý 2

Hãy tách hai ownership transition: trước khi `ExportSession` được tạo thành công và sau khi caller nhận ownership của session.

## Kết quả code review tham khảo

### Critical — Session không được dispose khi streaming thất bại

**Vấn đề:** `DisposeAsync()` chỉ chạy ở cuối happy path.  
**Tại sao xảy ra:** exception/cancellation từ reader hoặc response bỏ qua dòng cleanup.  
**Ảnh hưởng production:** reader/connection sống lâu hơn dự kiến; dưới nhiều export bị abort có thể tạo pool pressure và cascading latency.  
**Cách sửa:** caller dùng `await using` hoặc `try/finally` để ownership được giải phóng trên mọi exit path.

### High — Repository leak connection nếu tạo session thất bại giữa chừng

**Vấn đề:** connection được mở trước `ExecuteReaderAsync()`, nhưng nếu execute thất bại thì chưa có `ExportSession` để caller dispose.  
**Tại sao xảy ra:** ownership được chuyển quá muộn nhưng failure cleanup không tồn tại.  
**Ảnh hưởng production:** transient SQL/query errors có thể giữ resource không cần thiết.  
**Cách sửa:** repository dùng `try/catch`; dispose command/connection nếu chưa chuyển ownership thành công.

### High — Không propagate request cancellation

**Vấn đề:** database open/query/read và response writes không nhận `RequestAborted`.  
**Tại sao xảy ra:** API signatures không nhận `CancellationToken`.  
**Ảnh hưởng production:** client đã rời đi nhưng server/database vẫn có thể tiếp tục expensive work.  
**Cách sửa:** truyền cancellation token xuyên suốt các async operations có hỗ trợ cancellation.

### High — `DbCommand` ownership không rõ và không được dispose

**Vấn đề:** command được tạo local nhưng không được session sở hữu/dispose.  
**Tại sao xảy ra:** wrapper chỉ chứa connection và reader.  
**Ảnh hưởng production:** resource lifetime mơ hồ, dễ tạo leak/regression khi implementation thay đổi.  
**Cách sửa:** ownership graph phải rõ; session có thể sở hữu command hoặc repository thiết kế abstraction streaming mà cleanup toàn bộ graph trong một scope.

### Medium — CSV escaping không đúng

**Vấn đề:** email hoặc field chứa comma, quote hoặc newline làm hỏng CSV.  
**Tại sao xảy ra:** nối string trực tiếp.  
**Ảnh hưởng production:** file sai cấu trúc/data integrity ở consumer.  
**Cách sửa:** dùng CSV escaping đúng chuẩn hoặc library phù hợp.

### Medium — Không validate export range/cost

**Vấn đề:** caller có thể yêu cầu khoảng thời gian cực lớn.  
**Tại sao xảy ra:** endpoint không có guardrail.  
**Ảnh hưởng production:** long-running query giữ connection lâu và tăng contention.  
**Cách sửa:** xác định product limits, async export workflow nếu workload vượt interactive HTTP budget.

### Medium — Chưa có evidence để kết luận pool size là nguyên nhân

**Vấn đề:** proposal tăng pool dựa trên symptom.  
**Tại sao xảy ra:** thiếu correlation giữa active exports, connection acquisition wait và aborted requests.  
**Ảnh hưởng production:** tăng capacity có thể chỉ trì hoãn exhaustion.  
**Cách sửa:** đo pool wait/query duration/export concurrency/request cancellation trước khi tuning.

## Phiên bản đề xuất

```csharp
public async Task<ExportSession> OpenExportAsync(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    var connection = new NpgsqlConnection(_connectionString);
    NpgsqlCommand? command = null;

    try
    {
        await connection.OpenAsync(cancellationToken);
        command = connection.CreateCommand();
        command.CommandText = """
            SELECT id, created_at, customer_email, amount
            FROM report_rows
            WHERE created_at >= @from AND created_at < @to
            ORDER BY created_at, id
            """;
        command.Parameters.AddWithValue("from", from);
        command.Parameters.AddWithValue("to", to);

        var reader = await command.ExecuteReaderAsync(cancellationToken);
        return new ExportSession(connection, command, reader);
    }
    catch
    {
        if (command is not null)
            await command.DisposeAsync();
        await connection.DisposeAsync();
        throw;
    }
}

public sealed class ExportSession : IAsyncDisposable
{
    public NpgsqlDataReader Reader { get; }
    private readonly NpgsqlCommand _command;
    private readonly NpgsqlConnection _connection;

    public ExportSession(
        NpgsqlConnection connection,
        NpgsqlCommand command,
        NpgsqlDataReader reader)
    {
        _connection = connection;
        _command = command;
        Reader = reader;
    }

    public async ValueTask DisposeAsync()
    {
        await Reader.DisposeAsync();
        await _command.DisposeAsync();
        await _connection.DisposeAsync();
    }
}

[HttpGet("export")]
public async Task Export(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    await using var session =
        await _repository.OpenExportAsync(from, to, cancellationToken);

    Response.ContentType = "text/csv";
    await Response.WriteAsync("id,createdAt,email,amount\n", cancellationToken);

    while (await session.Reader.ReadAsync(cancellationToken))
    {
        var line = CsvFormatter.Format(
            session.Reader.GetGuid(0),
            session.Reader.GetDateTime(1),
            session.Reader.GetString(2),
            session.Reader.GetDecimal(3));

        await Response.WriteAsync(line, cancellationToken);
    }
}
```

## Giải thích thiết kế sau khi sửa

Caller nhận ownership chỉ sau khi session hoàn chỉnh được tạo; từ thời điểm đó `await using` bảo đảm async cleanup khi success, exception hoặc cancellation. Trước ownership transition, repository chịu trách nhiệm cleanup partial construction. Cancellation đi theo request boundary để abandoned HTTP work không tiếp tục vô ích. Với export rất lớn, cần cân nhắc chuyển sang background export + Blob Storage thay vì giữ HTTP/database connection dài, nhưng chỉ khi requirement và workload chứng minh interactive streaming không phù hợp.

## Trade-offs

- Streaming giảm memory so với materialize toàn bộ, nhưng giữ database connection trong suốt download.
- Background export tăng operational complexity nhưng tách thời gian query khỏi client connection.
- `await using` làm ownership rõ hơn nhưng không thay thế cleanup cho partial construction trong factory/repository.
- Tăng pool size có thể hữu ích cho legitimate concurrency sau khi đo đạc, nhưng không phải remediation cho leak.

## Cách kiểm thử

1. Integration test success path và xác minh connection có thể được tái sử dụng sau export.
2. Test client cancellation giữa stream; xác minh query/read dừng và resource được dispose.
3. Inject exception ở `ExecuteReaderAsync()` để kiểm tra partial construction cleanup.
4. Inject response-write failure sau nhiều rows và kiểm tra session disposal.
5. Load test nhiều export đồng thời, theo dõi connection acquisition latency/pool pressure thay vì chỉ request throughput.

## Quan sát trong production

Theo dõi active export count, export duration, aborted request count, database dependency duration, connection acquisition wait, query cancellation, exception type và p95/p99 của endpoint khác dùng cùng database. Correlate bằng trace/correlation ID. Không log email/raw exported data nếu không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Nếu `DisposeAsync()` của reader cũng ném exception trong lúc đang xử lý exception gốc, bạn muốn logging/error semantics thế nào?
2. Khi nào bạn chuyển export sang background job + Blob thay vì tiếp tục HTTP streaming?
3. Nếu pool không leak nhưng vẫn thường xuyên full, evidence nào giúp bạn phân biệt legitimate concurrency với slow query?

# Code Review Challenge 2 — Jenkins pipeline publish artifact không bất biến và deploy nhầm binary

**Chủ đề:** CI/CD, Jenkins, artifact provenance, immutable artifacts, secrets, deployment promotion, rollback, SonarQube  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một team build ASP.NET Core application bằng Jenkins. Dev, staging và production là ba jobs riêng. Mỗi environment checkout branch rồi tự `dotnet publish`; production đôi lúc chạy vài giờ sau staging. Gần đây production nhận binary khác staging dù release ticket ghi cùng commit. Một hotfix khác rollback thất bại vì package cũ không còn xác định được chính xác.

Team muốn thêm nhiều approval thủ công. Hãy review pipeline theo hướng release safety và provenance, không tập trung vào việc nhớ Jenkins UI.

## Đoạn code cần review

```groovy
pipeline {
  agent any

  environment {
    CONFIGURATION = 'Release'
    FEED_TOKEN = credentials('nuget-feed-token')
  }

  stages {
    stage('Checkout') {
      steps {
        git branch: params.BRANCH,
            url: 'https://github.com/example/commerce-api.git'
      }
    }

    stage('Restore') {
      steps {
        sh 'dotnet restore --source https://api.nuget.org/v3/index.json --source https://packages.example.local/nuget/v3/index.json'
      }
    }

    stage('Build') {
      steps {
        sh 'dotnet publish src/Commerce.Api/Commerce.Api.csproj -c Release -o publish'
      }
    }

    stage('Quality') {
      steps {
        sh 'dotnet test --no-restore'
        sh 'sonar-scanner'
      }
    }

    stage('Package') {
      steps {
        sh 'tar -czf commerce-api-latest.tar.gz publish/'
        archiveArtifacts artifacts: 'commerce-api-latest.tar.gz'
      }
    }

    stage('Deploy') {
      steps {
        sh "./deploy.sh ${params.ENVIRONMENT} commerce-api-latest.tar.gz"
      }
    }
  }
}
```

## Nhiệm vụ của ứng viên

1. Tìm các rủi ro correctness, supply-chain/release safety, reproducibility và rollback.
2. Giải thích tại sao cùng `BRANCH` không chứng minh staging và production chạy cùng artifact.
3. Ưu tiên các vấn đề có thể gây deploy sai binary hoặc không audit được release.
4. Đề xuất build-once/promote-many flow phù hợp mà không phụ thuộc Jenkins UI cụ thể.
5. Nêu cách quản lý secrets/config mà không bake environment-specific secret vào artifact.
6. Đề xuất tests/gates theo risk.
7. Đề xuất metadata/telemetry để production có thể trả lời “đang chạy artifact nào?”.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu branch có commit mới giữa staging build và production build?
2. `commerce-api-latest.tar.gz` có đủ để làm release identity không?
3. Restore hôm nay và restore vài giờ sau có chắc lấy cùng dependency graph không?
4. Approval thủ công có giải quyết artifact drift không?
5. Rollback cần những thông tin nào ngoài “deploy branch release/x”?

### Gợi ý 1

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Mỗi environment rebuild từ mutable branch

**Vấn đề:** staging và production có thể checkout các commits khác nhau.  
**Tại sao xảy ra:** branch là mutable pointer; pipeline không pin release bằng commit SHA/artifact digest.  
**Ảnh hưởng production:** artifact production chưa từng là artifact được staging xác nhận.  
**Cách sửa:** build một lần từ immutable commit, publish artifact có version/digest rồi promote cùng artifact qua environments.

### Critical — Artifact dùng tên `latest`, không có provenance mạnh

**Vấn đề:** package name không thể hiện commit/build/digest.  
**Tại sao xảy ra:** release identity bị thay bằng convenience filename.  
**Ảnh hưởng production:** audit/rollback dễ chọn nhầm binary.  
**Cách sửa:** artifact repository/version immutable; lưu commit SHA, build ID, dependency metadata và cryptographic digest phù hợp.

### High — Dependency restore có thể drift

**Vấn đề:** pipeline restore lại theo thời điểm build; nếu dependency versions không được lock đủ chặt, graph có thể thay đổi.  
**Tại sao xảy ra:** rebuild nhiều lần và thiếu reproducibility controls.  
**Ảnh hưởng production:** cùng source commit có thể không đảm bảo cùng dependency content.  
**Cách sửa:** lock dependency versions phù hợp, lưu restore/build metadata và không rebuild khi promote.

### High — Test command không bảo đảm test đúng artifact sẽ deploy

**Vấn đề:** pipeline test source/build context nhưng release process không tạo immutable relation test-result → artifact → deploy.  
**Tại sao xảy ra:** package/deploy identity yếu.  
**Ảnh hưởng production:** khó chứng minh binary production đã qua gates nào.  
**Cách sửa:** gates gắn với build artifact ID; promotion chỉ nhận artifact đã đạt policy.

### High — Rollback không có immutable target

**Vấn đề:** package cũ không có durable version identity.  
**Tại sao xảy ra:** `latest` và rebuild-oriented process.  
**Ảnh hưởng production:** rollback chậm hoặc deploy nhầm.  
**Cách sửa:** retention policy cho immutable release artifacts và manifest đủ để chọn đúng version.

### Medium — Secret scope rộng hơn cần thiết

**Vấn đề:** feed credential được đưa vào pipeline-level environment.  
**Tại sao xảy ra:** secret scope không giới hạn theo stage/operation cần dùng.  
**Ảnh hưởng production:** tăng blast radius nếu command/plugin/logging ngoài ý muốn truy cập environment.  
**Cách sửa:** bind secret ở scope nhỏ nhất, không echo, không bake vào artifact; dùng workload identity/token ngắn hạn nếu platform hỗ trợ và phù hợp.

### Medium — Quality gates chưa thể hiện fail policy

**Vấn đề:** `sonar-scanner` chạy nhưng snippet không chứng minh pipeline chờ/đánh giá quality gate.  
**Tại sao xảy ra:** tool invocation bị nhầm với release policy.  
**Ảnh hưởng production:** scan tồn tại nhưng release vẫn có thể đi tiếp khi policy không đạt.  
**Cách sửa:** định nghĩa explicit gate dựa trên risk và kết quả scan/test.

### Medium — Thiếu deployment manifest/runtime version endpoint

**Vấn đề:** sau deploy khó trả lời process nào đang chạy commit/artifact nào.  
**Tại sao xảy ra:** build metadata không đi cùng release.  
**Ảnh hưởng production:** incident triage và rollback chậm.  
**Cách sửa:** embed non-secret build metadata hoặc expose version endpoint/telemetry tags gồm commit, artifact version/digest, build ID.

## Phiên bản đề xuất

Flow đề xuất ở mức nguyên tắc:

```text
commit SHA
  ↓
restore + build + unit/integration tests + static analysis
  ↓
immutable artifact
  - artifact version
  - commit SHA
  - build ID
  - digest
  - dependency/build metadata
  ↓
deploy artifact X to staging
  ↓
smoke/E2E/Playwright + approval policy
  ↓
promote SAME artifact X to production
  ↓
verify health + telemetry + release marker
```

Ví dụ package identity:

```groovy
stage('Package') {
  steps {
    script {
      env.RELEASE_ID = "${env.GIT_COMMIT}-${env.BUILD_NUMBER}"
    }
    sh 'tar -czf commerce-api-${RELEASE_ID}.tar.gz publish/'
    sh 'sha256sum commerce-api-${RELEASE_ID}.tar.gz > commerce-api-${RELEASE_ID}.sha256'
    archiveArtifacts artifacts: 'commerce-api-*.tar.gz,commerce-api-*.sha256', fingerprint: true
  }
}
```

Trong hệ thống thực, artifact nên được publish tới artifact registry/repository có retention và immutability phù hợp; production deployment nhận `RELEASE_ID`/digest đã được staging xác nhận thay vì checkout branch và build lại. Environment configuration/secrets được inject lúc deploy/runtime theo security model, không thay đổi binary.

## Giải thích thiết kế sau khi sửa

Build-once/promote-many làm release artifact trở thành đơn vị kiểm thử và audit. Commit SHA chỉ định source, còn digest xác định artifact bytes. Approval có giá trị hơn khi approval gắn với immutable release candidate. Rollback chọn artifact đã biết và đã lưu, không tạo một build mới từ source cũ trong lúc incident.

## Trade-offs

- Immutable artifact repository cần retention/storage/governance nhưng giảm release ambiguity.
- Reproducible build controls vẫn có giá trị dù promote cùng artifact, đặc biệt cho supply-chain verification và disaster recovery.
- Nhiều gates tăng confidence nhưng cũng tăng lead time; chọn gate theo risk thay vì thêm approval vô hạn.
- Runtime config giúp một artifact đi nhiều environments nhưng phải có schema validation và secret management tốt.

## Cách kiểm thử

1. Pipeline test chứng minh staging và production promotion dùng cùng digest.
2. Test branch thay đổi sau staging không làm production artifact thay đổi.
3. Rollback drill tới artifact trước đó và xác minh health/version metadata.
4. Secret-scanning/log test bảo đảm credential không nằm trong artifact/logs.
5. Playwright/smoke tests chạy trên deployed staging artifact trước promotion; production có post-deploy smoke/health verification phù hợp.

## Quan sát trong production

Gắn release marker vào Application Insights/monitoring và structured logs: `release_id`, commit SHA, build ID, artifact digest, deployment time, environment. Dashboard incident phải correlate error rate/p95 với release marker. Version endpoint nếu có không được lộ secrets/internal data không cần thiết.

1. Nếu cần hotfix khẩn cấp, bạn giữ build-once/promote-many nhưng rút ngắn lead time thế nào mà không mất provenance?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async resource ownership phải đúng cả happy path, cancellation và partial-construction failure.
- `IAsyncDisposable`/`await using` là lifecycle mechanism; thiết kế vẫn phải xác định rõ ai sở hữu resource ở từng thời điểm.
- CI/CD release safety dựa trên immutable artifact và provenance, không dựa vào mutable branch hoặc filename `latest`.
- Production troubleshooting cần evidence để phân biệt leak với legitimate capacity pressure.

## Mẫu tư duy cần nhớ

1. Vẽ ownership graph và kiểm tra mọi exit path trước khi tăng resource limits.
2. Propagate cancellation qua toàn bộ I/O boundary có liên quan.
3. Với release: **build once → verify → promote same artifact → observe → rollback known artifact**.
4. Phân biệt source identity (commit SHA) với artifact identity (version/digest).
5. Mọi remediation phải có test và telemetry chứng minh giả thuyết.
