# Câu 1 — Cosmos DB query fan-out và RU spike

**Loại câu hỏi:** Internal mechanism  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Cosmos DB, .NET SDK, partitioning, security

## Bối cảnh

Audit API ASP.NET Core 8 lưu document theo /tenantId nhưng query 50 events gần nhất chỉ lọc userId và createdAt. Production nhiều tenant, RU và p95 tăng, 429 xuất hiện; dev ít dữ liệu không tái hiện. Chưa biết indexing policy, tenant context và hot partitions.

## Câu hỏi chính

Giải thích query routing, RU, 429, những giả định sai và quy trình đo trước khi sửa.

## Câu hỏi làm rõ nên cân nhắc

1. API có tenant scope được ủy quyền không?
2. RU/query, retries và số partitions là bao nhiêu?
3. Indexing policy và query plan ra sao?
4. Tenant skew, SLO và retention thế nào?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt routing với indexing.

### Gợi ý 2

Đọc diagnostics, RequestCharge, continuation token.

### Gợi ý 3

Thiếu partition key có thể fan-out; 429 không chứng minh nguyên nhân duy nhất.

## Cấu trúc trả lời đề xuất

1. Xác định security scope
2. Giải thích partition routing
3. Đo diagnostics
4. Thử query/index
5. Đánh giá migration và rollback

## Ý chính của câu trả lời tốt

### Bắt buộc

Giải thích logical partition, cross-partition query, throttling, authorization và RU.

### Điểm cộng

Đánh giá index policy, continuation tokens và phân phối tải.

### Senior+

Thiết kế migration sang container khác hoặc read model nếu access patterns xung đột, với consistency và backfill.

## Hướng giải quyết tham khảo

Cosmos DB định tuyến theo partition key. Với /tenantId, query không giới hạn tenant có thể fan-out qua nhiều partitions; TOP 50 không bảo đảm RU thấp. 429 là throttling, có thể do hot partition, throughput hoặc query cost; SDK retry làm latency tăng. Trước tiên xác minh tenant từ authorization context, không tin tenantId client; nếu nghiệp vụ tenant-scoped, thêm equality filter tenantId và PartitionKey trong QueryRequestOptions, kiểm tra hai giá trị nhất quán. Thu thập RequestCharge, query metrics, diagnostics, retry delay, 429 rate, p95/p99 và phân phối theo tenant; không log payload nhạy cảm. Kiểm tra indexing policy, query shape, projection và ORDER BY. Dùng continuation token thay offset pagination sâu; lưu ý dữ liệu mới xen vào giữa các trang. Tăng RU chỉ khi workload đã được tối ưu và capacity thực sự thiếu. Redis không mặc định giải quyết vấn đề và có rủi ro invalidation. Đổi partition key đòi hỏi container mới, backfill, kiểm tra dữ liệu, cutover và rollback; cần đo cardinality, hot keys và consistency trước khi chọn. Test tenant isolation, high-load tenant, cross-tenant authorized use case và throttling.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ chưa tăng RU hay thêm Redis. Vì container partition theo tenantId nhưng query chỉ filter userId, tôi nghi fan-out; tuy nhiên phải đo RU, diagnostics và 429 theo tenant để phân biệt index, hot partition và capacity. Tôi xác minh tenant authorization, thử query có tenantId và PartitionKey option, so sánh cùng workload, rồi mới cân nhắc indexing hay throughput. Đổi partition key là data migration có rollback và consistency risk, không phải chỉnh cấu hình. Tôi chứng minh hiệu quả bằng RU/query, p95 và throttling.

## Câu hỏi đào sâu

1. Nếu user thuộc 20 tenant, query và authorization sẽ thay đổi ra sao?
2. Nếu tenant lớn vẫn hot dù đã partition filter đúng thì chọn giải pháp nào?
3. Nếu RU giảm nhưng p99 không giảm, kiểm tra SDK retry và network thế nào?

## Lỗi trả lời thường gặp

- Cho rằng TOP 50 luôn rẻ.
- Tin tenantId do frontend gửi.
- Kết luận 429 chỉ do thiếu RU.
- Đổi partition key không có migration.

## Thang điểm 0–10

Clarification/security 2; mechanism 2.5; evidence 2; trade-offs 2; test/communication 1.5.

# Câu 2 — IIS recycle và HTTP 503 sau khi phát hành

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET Core, Octopus Deploy

## Bối cảnh

ASP.NET Core 8 chạy sau IIS trên hai Windows Server qua load balancer, có native DLL xử lý báo cáo. Sau TeamCity/Octopus release, 503 xuất hiện ngắt quãng và worker restart. Chưa rõ hosting model, bitness, app pool identity, health checks hay schema migration. Business cần ổn định dịch vụ ngay.

## Câu hỏi chính

Dẫn dắt 30 phút đầu của incident và thiết kế prevention, không giả định trước root cause.

## Câu hỏi làm rõ nên cân nhắc

1. 503 do IIS hay load balancer, có substatus không?
2. Một hay cả hai node bị ảnh hưởng?
3. Release thay đổi runtime, DLL, ACL hoặc config nào?
4. Rollback binary có tương thích DB không?
5. Health probe và process exit code là gì?

## Gợi ý tư duy

### Gợi ý 1

Stabilize trước debug sâu.

### Gợi ý 2

Đối chiếu node, IIS logs, Event Viewer và release artifact.

### Gợi ý 3

Phân biệt process crash, rapid-fail, recycle, startup và upstream health.

## Cấu trúc trả lời đề xuất

1. Đo impact
2. Drain/rollback an toàn
3. Giữ evidence
4. Đặt competing hypotheses
5. Verify fix từng node
6. Prevention và postmortem

## Ý chính của câu trả lời tốt

### Bắt buộc

Nêu rollback criteria, phân biệt nguồn 503, kiểm tra process lifetime và node-specific evidence.

### Điểm cộng

IIS substatus, Event Viewer, ANCM diagnostics, dumps an toàn, artifact checksum.

### Senior+

Rolling deploy, backward-compatible migrations, readiness gates, rollback rehearsal.

## Hướng giải quyết tham khảo

Đầu tiên ghi nhận 5xx, p95, chức năng ảnh hưởng, node nào lỗi và business impact. Drain node lỗi nếu node còn lại đủ capacity; rollback artifact/config khi đã kiểm tra DB compatibility. Giữ evidence trước khi restart. Thu IIS logs/status/substatus, Windows Event Viewer, ASP.NET Core Module events, process exit, app logs, uptime, memory, handles, CPU, load balancer probe và release timeline. So sánh node A/B về hosting model, app pool bitness/identity, ACL, installed runtime, native DLL architecture, environment variables và checksums. Giữ nhiều giả thuyết: native DLL sai bitness; startup exception; rapid-fail/recycle; memory/handle exhaustion; unhealthy probe; SQL connection pool issues. Với từng giả thuyết, chỉ ra evidence xác nhận/phủ định. Nếu chứng minh native DLL mismatch, build/publish đúng architecture và smoke-test route báo cáo. Nếu memory issue, lấy counters/dump theo chính sách dữ liệu rồi profiling. Rollout từng node, quan sát trước khi tiếp tục. Prevention gồm immutable artifacts, config validation, release annotation, expand-contract migrations, health/readiness probes, deployment gates, rollback drill và alert process restarts/503 theo node. Không kết luận 503 đồng nghĩa memory leak.

## Mẫu trả lời trong phỏng vấn

> Tôi xác định nguồn 503 và blast radius trước. Nếu một node khỏe, tôi drain node lỗi; rollback chỉ khi binary cũ còn tương thích database. Tôi giữ logs trước khi recycle, đối chiếu IIS substatus, Event Viewer, process exit và sự khác biệt native DLL, app pool và runtime giữa hai node. Tôi không đoán root cause từ một status code. Sau khi xác minh, tôi sửa, deploy từng node và theo dõi 5xx, restarts và latency. Dài hạn tôi thêm artifact checks, smoke tests, readiness, rollback gates và release monitoring.

## Câu hỏi đào sâu

1. Nếu rollback binary không tương thích schema mới thì sao?
2. Nếu process không crash nhưng vẫn 503 thì điều tra thế nào?
3. Nếu lỗi chỉ xuất hiện sau 8 giờ tải, thu chứng cứ gì?

## Lỗi trả lời thường gặp

- Restart app pool mà không giữ evidence.
- Quy 503 thành thiếu RAM.
- Rollback bỏ qua schema compatibility.
- Health check phụ thuộc mọi downstream.
- Không định nghĩa success criteria.

## Thang điểm 0–10

Impact/stabilization 2; evidence 2; hypotheses 2; remediation/rollback 2; prevention/communication 2.

# Câu 3 — Modernize Optimizely CMS mà không mất SEO và editorial preview

**Loại câu hỏi:** Architecture decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Vue.js, Akamai, SEO, architecture

## Bối cảnh

Marketing website dùng Optimizely CMS page types/content blocks, server-rendered templates và jQuery; cần Vue.js tương tác và content API cho mobile. 300.000 page views/ngày giả định; organic search quan trọng, Akamai cache public pages, editor cần preview. Team 5 engineers, deadline 4 tháng; phải giữ URLs, metadata và rollback.

## Câu hỏi chính

So sánh server-rendered + Vue islands, hybrid headless và SPA/SSR; chọn rollout bảo vệ SEO, cache và editor workflow.

## Câu hỏi làm rõ nên cân nhắc

1. Trang nào thực sự cần interactivity?
2. Editor preview, scheduling, personalization cần gì?
3. Mobile cần content reuse ở mức nào?
4. Akamai cache key/purge hiện ra sao?
5. Team có thể vận hành SSR service riêng không?

## Gợi ý tư duy

### Gợi ý 1

Tách nhu cầu tương tác khỏi nhu cầu headless.

### Gợi ý 2

Xem crawlability, preview bypass và CDN cache boundary.

### Gợi ý 3

Migration theo route; operational cost là một tiêu chí.

## Cấu trúc trả lời đề xuất

1. Baseline requirements
2. So sánh rendering options
3. Định nghĩa content/API ownership
4. Cache/security/SEO
5. Incremental rollout
6. Measure và rollback

## Ý chính của câu trả lời tốt

### Bắt buộc

Không mặc định SPA/headless; bảo vệ HTML crawlable, canonical, preview và public/private cache.

### Điểm cộng

Playwright metadata snapshots, Core Web Vitals, consent, redirects, purge events.

### Senior+

Chi phí SSR, eventual consistency, content model migration, feature-flag routing và failure recovery.

## Hướng giải quyết tham khảo

Với team nhỏ, deadline ngắn và SEO/preview quan trọng, lựa chọn mặc định có cơ sở là giữ server-rendered pages, thêm Vue islands cho tương tác cần thiết và cung cấp public content API có scope rõ cho mobile. Nếu nhu cầu omnichannel lớn và team vận hành được frontend SSR, cân nhắc headless SSR theo route; không chọn client-only SPA toàn site theo trend. CMS sở hữu content model, publish state và editorial workflow; rendering layer sở hữu HTML, canonical, metadata, structured data và consent. Preview cần auth, Cache-Control: no-store và không đi shared CDN cache; public API chỉ trả content được publish. Thiết kế Akamai cache keys, TTL, purge khi publish/unpublish, origin fallback, tránh cache personalized responses chung. Giữ URL, redirects, sitemap, robots, canonical và structured data. Lấy baseline LCP/INP/CLS, TTFB, crawl errors, cache hit ratio, publish-to-live delay. Pilot một content type với feature flag, Playwright E2E kiểm tra metadata, preview, publish, accessibility; canary theo route và rollback renderer không phải rollback schema. Nếu đổi content model, dùng expand-contract, mapping và kiểm tra dữ liệu. Trade-offs: hybrid ít rủi ro nhưng coupling CMS templates; headless SSR tăng autonomy và reuse nhưng thêm network hop, deployment, preview/caching complexity; SPA có thể tăng SEO/rendering risk. Quyết định phải dựa trên requirement và số đo.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ không rewrite toàn site ngay. Với SEO và editor preview quan trọng, tôi đo baseline rồi ưu tiên Vue islands trên server-rendered pages, giữ URL và HTML hiện tại. Tôi mở content API có kiểm soát cho mobile, tách preview khỏi Akamai shared cache và thiết kế purge khi publish. Tôi pilot một content type, dùng Playwright kiểm tra canonical, metadata, preview, publish và Core Web Vitals, rồi rollout bằng feature flag. Nếu omnichannel lớn và team đủ năng lực SSR, tôi cân nhắc headless theo route. Tôi đánh đổi frontend autonomy với chi phí vận hành và rủi ro SEO.

## Câu hỏi đào sâu

1. Nếu Product bắt buộc SPA toàn site thì điều kiện chấp nhận nào?
2. Nếu Akamai cache unpublished content, xử lý incident ra sao?
3. Nếu headless frontend cập nhật chậm 10 phút, thiết kế consistency và telemetry thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất Vue với SPA.
- Bỏ qua preview cache boundary.
- Chỉ đo Lighthouse lab.
- Không có rollback.
- Chọn headless không tính operational cost.

## Thang điểm 0–10

Requirements 1.5; architecture trade-offs 2.5; SEO/cache/security 2.5; rollout/testing 2; observability 1.5.
