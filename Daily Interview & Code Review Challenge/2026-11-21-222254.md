# Code Review Challenge 1 — Approval workflow bị duyệt hai lần khi nhiều instance xử lý đồng thời

**Chủ đề:** ASP.NET Core, EF Core, SQL Server, optimistic concurrency, transactional outbox  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một cổng quản lý nội bộ chạy ASP.NET Core/.NET 8 trên ba Azure App Service instances. Người quản lý phê duyệt yêu cầu hoàn tiền; một yêu cầu chỉ được phê duyệt một lần, người phê duyệt phải thuộc nhóm được cấp quyền theo tenant, và notification được gửi sau khi trạng thái đã lưu. Trong giờ cao điểm, người dùng nhấn hai lần hoặc gateway retry khi mất kết nối. Một số yêu cầu ghi nhận hai lần vào bảng audit và gửi nhiều notification. Nhóm chưa xác nhận có database constraint, cơ chế retry, hoặc service nhận notification có hỗ trợ idempotency hay không.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/approvals")]
public sealed class ApprovalsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly HttpClient _http;
    private readonly ILogger<ApprovalsController> _logger;

    public ApprovalsController(
        AppDbContext db,
        IHttpClientFactory factory,
        ILogger<ApprovalsController> logger)
    {
        _db = db;
        _http = factory.CreateClient("notifications");
        _logger = logger;
    }

    [HttpPost("{id:guid}/approve")]
    [Authorize]
    public async Task<IActionResult> Approve(Guid id)
    {
        var tenantId = User.FindFirst("tenant_id")?.Value;
        var approverId = User.FindFirst("sub")?.Value;
        var request = await _db.ApprovalRequests
            .FirstOrDefaultAsync(x => x.Id == id);

        if (request is null)
            return NotFound();

        if (request.Status == "Approved")
            return Ok(new { request.Id, request.Status });

        request.Status = "Approved";
        request.ApprovedBy = approverId;
        request.ApprovedAt = DateTime.UtcNow;

        _db.ApprovalAudits.Add(new ApprovalAudit
        {
            RequestId = id,
            ActorId = approverId,
            Action = "Approved",
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        var response = await _http.PostAsJsonAsync(
            "/api/notifications",
            new { request.Id, request.TenantId, request.ApprovedBy });

        if (!response.IsSuccessStatusCode)
            _logger.LogWarning("Notification failed: {Body}",
                await response.Content.ReadAsStringAsync());

        return Ok(new { request.Id, request.Status, tenantId });
    }
}
```

## Kết quả code review tham khảo

### Critical — Thiếu authorization theo tenant và quyền duyệt

**Vấn đề:** Chỉ xác thực danh tính, truy vấn bằng `Id` mà không lọc tenant hoặc kiểm tra quyền trên request.

**Tại sao xảy ra:** `[Authorize]` không tự thực hiện resource-based authorization; claim `tenant_id` được đọc nhưng không dùng.

**Ảnh hưởng production:** Người đăng nhập có thể duyệt yêu cầu thuộc tenant khác nếu biết ID; tác động tài chính và audit.

**Cách sửa:** Xác thực tenant claim từ trusted issuer; áp policy/authorization handler kiểm tra actor, role và đối tượng; query tenant-scoped và trả 404/403 theo chính sách chống enumeration.

### Critical — Race condition cho phép hai approval cùng thành công

**Vấn đề:** Check `Status` rồi `SaveChangesAsync` không phải atomic compare-and-set.

**Tại sao xảy ra:** Hai DbContext ở hai instance có thể cùng đọc Pending, cùng update và cùng insert audit. Transaction mặc định của một SaveChanges không khóa điều kiện đã đọc ở transaction khác.

**Ảnh hưởng production:** Hai audit, hai notification, dữ liệu actor cuối cùng ghi đè actor đầu.

**Cách sửa:** Conditional `UPDATE ... WHERE Status = Pending` và kiểm tra affected rows; hoặc optimistic concurrency token với xử lý conflict. Đặt audit và outbox trong cùng transaction, bảo vệ uniqueness bằng constraint thích hợp.

### High — Notification sau commit không có durable recovery

**Vấn đề:** HTTP call chạy sau commit; lỗi mạng không được retry có kiểm soát, và response không thành công vẫn trả success.

**Tại sao xảy ra:** Database transaction không bao gồm external HTTP call; process crash giữa commit và call làm mất notification.

**Ảnh hưởng production:** Người nhận không được thông báo, khó đối soát.

**Cách sửa:** Transactional outbox trong database, worker publish/retry với backoff, dead-letter/escalation, và idempotent consumer theo event ID.

### High — Thiếu business idempotency cho retry

**Vấn đề:** Không có idempotency key hoặc command identity; retry không có cách phân biệt cùng một ý định và một approval khác.

**Tại sao xảy ra:** HTTP retry có thể diễn ra sau khi client mất response.

**Ảnh hưởng production:** Response và audit không nhất quán; các side effect ngoài DB có thể lặp.

**Cách sửa:** Định nghĩa semantic idempotency theo `RequestId` + transition hoặc command key; unique index cho approval transition/outbox event; lưu kết quả command nếu API contract yêu cầu replay response.

### High — Không xác thực trạng thái chuyển và actor

**Vấn đề:** Mọi trạng thái không phải Approved đều được chuyển thành Approved; `approverId` có thể null.

**Tại sao xảy ra:** Không có state machine và claim validation.

**Ảnh hưởng production:** Yêu cầu Rejected/Cancelled có thể bị duyệt trái quy trình, audit thiếu actor.

**Cách sửa:** Chỉ cho phép Pending → Approved khi actor đủ điều kiện; xác thực identifier và business invariants.

### Medium — Không truyền CancellationToken vào database và HTTP

**Vấn đề:** Không hỗ trợ request cancellation và timeout budget rõ ràng.

**Tại sao xảy ra:** API gọi async overload không có token.

**Ảnh hưởng production:** Request bị ngắt vẫn tiêu tốn tài nguyên; HTTP dependency chậm kéo dài latency.

**Cách sửa:** Truyền token cho phần xử lý request; với outbox worker dùng shutdown token, per-attempt timeout và retry policy riêng.

### Medium — Log response của dependency có thể chứa dữ liệu nhạy cảm

**Vấn đề:** Log toàn bộ response body.

**Tại sao xảy ra:** Chưa xác định hợp đồng logging và phân loại dữ liệu.

**Ảnh hưởng production:** PII/token có thể xuất hiện trong centralized logs.

**Cách sửa:** Log status code, dependency name, event ID, correlation ID và lỗi đã sanitize.

### Medium — API response không thể hiện conflict rõ ràng

**Vấn đề:** Request đến sau trả `200 OK` cho mọi Approved dù người khác đã duyệt; có thể phù hợp với idempotent read nhưng che giấu conflict nghiệp vụ.

**Tại sao xảy ra:** Không xác định contract giữa duplicate cùng command và competing command.

**Ảnh hưởng production:** Client hiểu sai actor/ownership của quyết định.

**Cách sửa:** Xác định contract: replay cùng command trả kết quả đã lưu; competing approval trả 409 hoặc trạng thái hiện tại có metadata tùy yêu cầu.

## Phiên bản đề xuất

Ví dụ dưới đây dùng SQL Server và EF Core, giả định bảng `ApprovalRequests` có `TenantId`, `Status`, `ApprovedBy`, `ApprovedAt`; `ApprovalAudits` và `OutboxMessages` được map cùng DbContext. Authorization policy `CanApprove` phải được triển khai với logic nghiệp vụ thực tế. `ExecuteSqlInterpolatedAsync` thực hiện conditional update và tham gia transaction hiện tại của DbContext.

```csharp
[HttpPost("{id:guid}/approve")]
[Authorize]
public async Task<IActionResult> Approve(
    Guid id, CancellationToken ct)
{
    var tenant = User.FindFirst("tenant_id")?.Value;
    var actor = User.FindFirst("sub")?.Value;
    if (string.IsNullOrWhiteSpace(tenant) ||
        string.IsNullOrWhiteSpace(actor))
        return Forbid();

    var target = await _db.ApprovalRequests
        .AsNoTracking()
        .SingleOrDefaultAsync(
            x => x.Id == id && x.TenantId == tenant, ct);
    if (target is null) return NotFound();

    var decision = await _authorization.AuthorizeAsync(
        User, target, "CanApprove");
    if (!decision.Succeeded) return Forbid();

    await using var tx = await _db.Database.BeginTransactionAsync(ct);
    var now = DateTime.UtcNow;
    var affected = await _db.Database.ExecuteSqlInterpolatedAsync(
        $@"UPDATE ApprovalRequests
           SET Status = {'Approved'},
               ApprovedBy = {actor}, ApprovedAt = {now}
           WHERE Id = {id} AND TenantId = {tenant}
             AND Status = {'Pending'}", ct);

    if (affected != 1)
    {
        await tx.RollbackAsync(ct);
        return Conflict(new ProblemDetails
        {
            Title = "Approval state changed",
            Status = StatusCodes.Status409Conflict
        });
    }

    _db.ApprovalAudits.Add(new ApprovalAudit
    {
        RequestId = id, ActorId = actor,
        Action = "Approved", CreatedAt = now
    });
    _db.OutboxMessages.Add(new OutboxMessage
    {
        Id = Guid.NewGuid(),
        Type = "ApprovalCompleted",
        AggregateId = id.ToString(),
        Payload = JsonSerializer.Serialize(
            new { RequestId = id, TenantId = tenant, ActorId = actor }),
        CreatedAt = now
    });
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return Ok(new { Id = id, Status = "Approved" });
}
```

**Điều kiện triển khai:** Inject `IAuthorizationService` và cấu hình policy; kiểm tra mapping/table names và schema thực tế. SQL trên dành cho SQL Server; PostgreSQL cần cú pháp/quoting tương ứng. Outbox worker phải claim rows an toàn giữa instances, xử lý retry và dedupe theo `OutboxMessage.Id`. Nếu cần trả lại chính xác kết quả cho duplicate cùng command, bổ sung command idempotency store và replay logic; đoạn code mẫu hiện trả 409 cho mọi transition đã hoàn thành.

## Giải thích thiết kế sau khi sửa

Conditional update là điểm tuyến tính hóa: tối đa một request đổi Pending thành Approved. Audit và outbox cùng commit nên không có trường hợp trạng thái đã đổi nhưng thiếu bản ghi event cần publish. Resource authorization được kiểm tra trước mutation; điều kiện tenant cũng được giữ trong câu UPDATE để phòng sai sót. Consumer cần idempotency vì worker có thể gửi lại sau timeout/ack loss. Với yêu cầu tài chính, database constraint và business invariant phải là tuyến phòng vệ cuối cùng, không dựa vào distributed lock.

## Trade-offs

Conditional SQL rõ ràng nhưng giảm tính portable và bỏ qua EF change tracker; cần kiểm tra concurrency token, triggers và affected-row semantics. Optimistic concurrency token portable hơn ở tầng EF nhưng vẫn cần transaction và xử lý conflict. Outbox tăng storage, worker và độ trễ notification; đổi lại có durable recovery. Không thể tuyên bố exactly-once delivery chỉ vì có outbox. Nếu notification chỉ mang tính best-effort, có thể chấp nhận thiết kế đơn giản hơn sau khi Product xác nhận.

## Cách kiểm thử

1. **Concurrency integration test:** 50 requests đồng thời trên nhiều service instances cùng duyệt một ID; assert đúng một transition, một audit và một outbox event.
2. **Security test:** actor tenant A thử duyệt ID của tenant B và actor thiếu quyền; không có DB mutation.
3. **Failure-path test:** crash sau DB commit trước publish; worker khởi động lại và phát event.
4. **Retry/idempotency test:** consumer nhận cùng event ID hai lần; chỉ một business side effect.
5. **State-transition test:** Pending, Approved, Rejected, Cancelled và malformed claims; kiểm tra status code theo contract.

## Quan sát trong production

Ghi structured logs với `requestId`, `tenantId` đã kiểm soát truy cập, `commandId`, `eventId`, `traceId`; không log payload nhạy cảm. Dashboard: approval conflict rate, duplicate-command rate, outbox oldest age, pending count, publish attempts, dead-letter count, notification success rate, p95 DB latency. Application Insights dependency traces giúp phân biệt SQL contention và downstream timeout. Alert khi outbox age vượt SLO hoặc có cross-tenant authorization anomaly.

# Code Review Challenge 2 — React product search hiển thị dữ liệu cũ và làm quá tải API

## Bối cảnh

Một trang e-commerce dùng React/TypeScript gọi ASP.NET Core search API. Người dùng gõ nhanh, đổi category và chuyển trang; mỗi truy vấn có thể mất 100–1.500 ms. QA báo kết quả không khớp từ khóa hiện tại, UI thỉnh thoảng render mô tả HTML không an toàn, API nhận nhiều requests và pagination nhảy sai. Backend áp rate limit và có endpoint `GET /api/products?q=&category=&page=`; chưa rõ response có cache headers hay không.

## Đoạn code cần review

```tsx
type Product = {
  id: string;
  name: string;
  descriptionHtml: string;
  price: number;
};

type SearchResponse = {
  items: Product[];
  total: number;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [items, setItems] = useState<Product[]>([]);
  const [total, setTotal] = useState(0);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  useEffect(() => {
    setLoading(true);
    fetch(
      "/api/products?q=" + query +
      "&category=" + category + "&page=" + page
    )
      .then(response => response.json())
      .then((data: SearchResponse) => {
        setItems(data.items);
        setTotal(data.total);
        setLoading(false);
      })
      .catch(err => {
        setError(String(err));
        setLoading(false);
      });
  }, [query, category, page]);

  return (
    <section>
      <input value={query}
        onChange={e => { setQuery(e.target.value); setPage(1); }} />
      <select value={category}
        onChange={e => { setCategory(e.target.value); setPage(1); }}>
        <option value="all">All</option>
        <option value="sale">Sale</option>
      </select>
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>{items.map(p => (
        <li key={p.id}>
          <strong>{p.name}</strong>
          <div dangerouslySetInnerHTML={{ __html: p.descriptionHtml }} />
          <span>{p.price}</span>
        </li>
      ))}</ul>
      <button onClick={() => setPage(page + 1)}
        disabled={page * 20 >= total}>Next</button>
    </section>
  );
}
```

## Kết quả code review tham khảo

### Critical — XSS qua dangerouslySetInnerHTML

**Vấn đề:** Render HTML từ API trực tiếp vào DOM.

**Tại sao xảy ra:** React escaping không áp dụng cho `dangerouslySetInnerHTML`; nội dung CMS hoặc third-party product feed có thể bị chỉnh sửa.

**Ảnh hưởng production:** Script/event handlers độc hại, session compromise tùy cấu hình và khả năng lạm dụng browser.

**Cách sửa:** Ưu tiên plain text rendering; nếu HTML là requirement, sanitize bằng thư viện được duy trì với allowlist, CSP và server-side validation; không dùng regex tự viết để sanitize HTML.

### High — Stale response ghi đè search mới

**Vấn đề:** Request chậm của query cũ có thể hoàn thành sau query mới.

**Tại sao xảy ra:** Mỗi effect tạo promise độc lập và không cleanup/cancel.

**Ảnh hưởng production:** Hiển thị sai kết quả, giá và category; user có thể thao tác với sản phẩm không mong muốn.

**Cách sửa:** AbortController khi dependencies thay đổi, cộng với guard chỉ cho phép effect còn active cập nhật state.

### High — Không kiểm tra HTTP status

**Vấn đề:** `fetch` không reject chỉ vì HTTP 4xx/5xx.

**Tại sao xảy ra:** Code parse JSON và cast thành `SearchResponse` không xác thực shape.

**Ảnh hưởng production:** UI rỗng/sai dữ liệu hoặc crash khi backend trả ProblemDetails.

**Cách sửa:** Kiểm tra `response.ok`, validate response schema tại boundary, xử lý 429/503 bằng UI thông báo và retry có kiểm soát.

### High — Mỗi phím gõ phát request, không giới hạn churn

**Vấn đề:** Effect chạy theo từng ký tự và mỗi lần thay đổi bộ lọc.

**Tại sao xảy ra:** Không debounce hoặc query threshold.

**Ảnh hưởng production:** Tăng API load, rate-limit, connection churn, giảm trải nghiệm.

**Cách sửa:** Debounce 250–400 ms theo UX đo được; cancellation và server-side rate limit/pagination vẫn cần thiết.

### Medium — Query string không encode

**Vấn đề:** Ghép trực tiếp input với URL.

**Tại sao xảy ra:** Không dùng `URLSearchParams`.

**Ảnh hưởng production:** `&`, `#`, `+` thay đổi ý nghĩa query; kết quả tìm kiếm sai.

**Cách sửa:** Tạo query string bằng `URLSearchParams`, validate category/page trên server.

### Medium — Error/loading state không nhất quán

**Vấn đề:** Error cũ không được reset; request cũ có thể tắt loading khi request mới đang chạy.

**Tại sao xảy ra:** Không có ownership của request đối với state.

**Ảnh hưởng production:** UI vừa báo lỗi vừa hiển thị kết quả, loading sai.

**Cách sửa:** Reset error ở đầu request mới; chỉ active effect được set state; có empty/error states rõ ràng.

### Medium — Pagination thiếu ràng buộc và stale closure

**Vấn đề:** Không có Previous, không chặn page dưới 1; `setPage(page + 1)` có thể dùng giá trị stale khi nhiều clicks; total có thể thuộc query cũ.

**Tại sao xảy ra:** Pagination không gắn với result identity.

**Ảnh hưởng production:** Nhảy trang và nút Next sai trạng thái.

**Cách sửa:** Functional update, reset page khi filter đổi, disable trong loading, ràng buộc page hợp lệ theo total mới.

## Phiên bản đề xuất

Giả định API trả JSON `{items,total}`, description được hiển thị dạng plain text và server sử dụng page size 20. Đây là phiên bản không dùng thư viện ngoài; production nên bổ sung runtime schema validation và accessible labels theo design system.

```tsx
type Product = {
  id: string; name: string; descriptionHtml: string; price: number;
};
type SearchResponse = { items: Product[]; total: number };

function useDebounced<T>(value: T, delay: number): T {
  const [result, setResult] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setResult(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return result;
}

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [items, setItems] = useState<Product[]>([]);
  const [total, setTotal] = useState(0);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");
  const debouncedQuery = useDebounced(query, 300);

  useEffect(() => {
    const controller = new AbortController();
    let active = true;
    const params = new URLSearchParams({
      q: debouncedQuery, category, page: String(page)
    });
    setLoading(true);
    setError("");
    setItems([]);
    setTotal(0);

    async function load() {
      try {
        const response = await fetch(
          `/api/products?${params}`, { signal: controller.signal }
        );
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const data: unknown = await response.json();
        if (!isSearchResponse(data)) throw new Error("Invalid API response");
        if (active) {
          setItems(data.items);
          setTotal(data.total);
        }
      } catch (e) {
        if (active && !controller.signal.aborted)
          setError(e instanceof Error ? e.message : "Search failed");
      } finally {
        if (active) setLoading(false);
      }
    }
    void load();
    return () => { active = false; controller.abort(); };
  }, [debouncedQuery, category, page]);

  const filterPending = query !== debouncedQuery;
  const busy = loading || filterPending;
  return <section>
    <label>Search <input value={query}
      onChange={e => { setQuery(e.target.value); setPage(1); }} /></label>
    <label>Category <select value={category}
      onChange={e => { setCategory(e.target.value); setPage(1); }}>
      <option value="all">All</option><option value="sale">Sale</option>
    </select></label>
    {busy && <p role="status">Loading...</p>}
    {error && !busy && <p role="alert">{error}</p>}
    {!busy && !error && <ul>{items.map(p =>
      <li key={p.id}><strong>{p.name}</strong>
        <p>{p.descriptionHtml}</p><span>{p.price}</span></li>
    )}</ul>}
    <button disabled={busy || page <= 1}
      onClick={() => setPage(p => Math.max(1, p - 1))}>Previous</button>
    <button disabled={busy || page * 20 >= total}
      onClick={() => setPage(p => p + 1)}>Next</button>
  </section>;
}

function isSearchResponse(x: unknown): x is SearchResponse {
  if (typeof x !== "object" || x === null) return false;
  const v = x as Record<string, unknown>;
  return Array.isArray(v.items) &&
    v.items.every(p => typeof p === "object" && p !== null &&
      typeof p.id === "string" && typeof p.name === "string" &&
      typeof p.descriptionHtml === "string" &&
      typeof p.price === "number") &&
    typeof v.total === "number" &&
    Number.isSafeInteger(v.total) && v.total >= 0;
}
```

**Lưu ý về tính đúng đắn:** Khi query đang debounce, component ẩn kết quả cũ bằng `filterPending`; tuy nhiên effect của query cũ vẫn có thể hoàn tất trong khoảng debounce và cập nhật state tạm thời. Guard hiển thị ngăn kết quả cũ xuất hiện trong thời gian đó; nếu yêu cầu không cập nhật state cũ dưới bất kỳ hình thức nào, dùng request generation gắn trực tiếp với raw query hoặc tách debounced input và committed search parameters thành một state object duy nhất. Validation ví dụ kiểm tra các field dùng trong UI, chưa thay thế schema validation đầy đủ (giới hạn kích thước, pagination contract và numeric domain).

## Giải thích thiết kế sau khi sửa

Effect cleanup loại bỏ ownership của request cũ; AbortController tiết kiệm network work khi browser/server hỗ trợ cancellation nhưng không được coi là bảo đảm server đã dừng xử lý. `active` guard đảm bảo promise cũ không thay đổi state sau cleanup. Plain text rendering dùng React escaping. Debounce giảm request rate; URLSearchParams bảo toàn semantics của input. Backend vẫn phải validate query và authorize dữ liệu; client validation không phải security boundary.

## Trade-offs

Debounce tăng độ trễ cảm nhận khi gõ; cần đo p95 và user behavior trước khi chọn delay. Clearing items giảm nguy cơ stale display nhưng gây layout shift; có thể giữ dữ liệu cũ kèm trạng thái rõ ràng nếu UX cho phép. TanStack Query hoặc SWR hỗ trợ caching/deduplication nhưng thêm dependency và yêu cầu thiết kế query key chuẩn. Với dữ liệu sản phẩm biến động nhanh, caching phải gắn TTL/invalidation và không giả định giá hiển thị là giá checkout cuối cùng.

## Cách kiểm thử

1. **Race test:** Mock request A chậm, B nhanh; gõ liên tục và xác minh UI chỉ hiển thị B.
2. **Security test:** API trả HTML chứa event handler/script; xác minh nó hiển thị dạng text, không thực thi.
3. **Failure-path test:** Mock HTTP 429, 500, malformed JSON, offline và abort; xác minh error/loading nhất quán.
4. **E2E Playwright:** Nhập query chứa `&`, `#`, `+`; đổi category/page nhanh; kiểm tra URL và kết quả.
5. **Load test:** So sánh requests per search session, p95 API latency và rate-limit rate trước/sau debounce.

## Quan sát trong production

Đo frontend search-to-result latency, request count per session, aborted requests, HTTP 429/5xx, stale-result incidents theo synthetic tests, và browser error rate. Backend Application Insights dùng `traceId`, normalized query length, category, page, dependency duration, request status; tránh log raw search nếu có PII. Kết hợp network waterfall với server p95/p99 để phân biệt UI race và backend bottleneck. Alert khi 429/5xx tăng hoặc API latency vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu sản phẩm có rich HTML do CMS biên tập, bạn thiết kế sanitization, CSP và trust boundary ra sao?
2. Nếu search API trả cursor thay vì page number, state và cache key thay đổi thế nào?
3. Khi nào dùng React Query/SWR thay vì tự quản lý effect, và những vấn đề nào thư viện vẫn không giải quyết hộ?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Một state transition quan trọng phải được bảo vệ bằng invariant ở database, không chỉ bằng `if` trong request handler. Transactional outbox giải quyết khoảng trống giữa database commit và external side effect nhưng không loại bỏ duplicate delivery; consumer phải idempotent. Trong React, kết quả bất đồng bộ phải gắn với query identity; cancellation, response validation và DOM escaping xử lý các lớp rủi ro khác nhau.

## Mẫu tư duy cần nhớ

1. **Xác minh trust boundary trước khi thay đổi dữ liệu:** authentication không thay thế resource authorization.
2. **Thiết kế retry cùng idempotency:** timeout không chứng minh operation thất bại.
3. **Bảo vệ invariant tại nguồn dữ liệu:** nhiều instances không chia sẻ memory lock.
4. **Chỉ request hiện hành được cập nhật UI:** đo race bằng response đảo thứ tự.
5. **Test failure path và quan sát production:** chứng minh bằng concurrency tests, telemetry và SLO, không chỉ happy path.
