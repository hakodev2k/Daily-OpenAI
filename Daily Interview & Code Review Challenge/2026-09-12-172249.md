# Câu 1 — MongoDB đã có index nhưng query vẫn chậm: vì sao `COLLSCAN` biến mất mà p99 gần như không cải thiện?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** MongoDB, query planner, compound index, ESR guideline, selectivity, covered query, sorting, pagination, working set, C# MongoDB Driver, production diagnostics

## Bối cảnh

Một ASP.NET Core API dùng MongoDB để lưu audit events. Collection `audit_events` có khoảng 180 triệu documents và tăng thêm 8–12 triệu documents mỗi tháng.

Document rút gọn:

```json
{
  "_id": "...",
  "tenantId": 42,
  "userId": 9851,
  "eventType": "DocumentViewed",
  "createdAt": "2026-09-12T08:14:00Z",
  "resourceId": "DOC-123",
  "metadata": {
    "ip": "...",
    "userAgent": "...",
    "description": "..."
  }
}
```

API phổ biến nhất:

```csharp
public async Task<IReadOnlyList<AuditEvent>> SearchAsync(
    int tenantId,
    string? eventType,
    DateTime from,
    DateTime to,
    int page,
    int pageSize,
    CancellationToken ct)
{
    var filter = Builders<AuditEvent>.Filter.Eq(x => x.TenantId, tenantId) &
                 Builders<AuditEvent>.Filter.Gte(x => x.CreatedAt, from) &
                 Builders<AuditEvent>.Filter.Lt(x => x.CreatedAt, to);

    if (!string.IsNullOrWhiteSpace(eventType))
    {
        filter &= Builders<AuditEvent>.Filter.Eq(x => x.EventType, eventType);
    }

    return await _collection
        .Find(filter)
        .SortByDescending(x => x.CreatedAt)
        .Skip(page * pageSize)
        .Limit(pageSize)
        .ToListAsync(ct);
}
```

Ban đầu collection chỉ có index mặc định `_id`. Production p95 của endpoint lên 4–7 giây. Team tạo index:

```javascript
db.audit_events.createIndex({ createdAt: -1, tenantId: 1, eventType: 1 })
```

Sau rollout, `explain()` không còn `COLLSCAN`; query chuyển sang `IXSCAN`. Nhưng với tenant lớn và khoảng thời gian 30 ngày, p99 vẫn 3–6 giây. Một số dashboard cho thấy:

- `keysExamined` có lúc hàng triệu dù chỉ trả 50 documents;
- `docsExamined` thấp hơn trước nhưng vẫn cao hơn `nReturned` rất nhiều;
- CPU MongoDB tăng trong giờ cao điểm;
- query trang 1 khá nhanh nhưng trang 2,000 rất chậm;
- khi filter `eventType` cụ thể thì có tenant nhanh, có tenant gần như không đổi;
- working set lớn hơn RAM và disk read tăng theo traffic;
- developer kết luận “đã dùng index nên query side hết việc để tối ưu, giờ chỉ còn tăng hardware”.

## Câu hỏi chính

Hãy giải thích tại sao “query dùng `IXSCAN`” chưa đủ để kết luận index tốt, compound-index field order ảnh hưởng thế nào đến equality/range/sort, vì sao `Skip()` càng sâu càng đắt, cách đọc các số liệu như `keysExamined`, `docsExamined`, `nReturned`, và bạn sẽ thiết kế index/query/pagination nào cho workload này mà không tạo một index riêng cho mọi tổ hợp filter.

## Câu hỏi làm rõ nên cân nhắc

1. Distribution tenant size ra sao? Một vài tenant cực lớn hay tương đối đều?
2. `eventType` có bao nhiêu distinct values và selectivity thực tế theo từng tenant?
3. Endpoint có thật sự cần random access tới page 2,000 hay chỉ next/previous/infinite scroll?
4. Response cần toàn bộ `metadata` hay chỉ một projection nhỏ cho list screen?
5. Write throughput và storage budget cho secondary indexes là bao nhiêu?
6. Query pattern nào chiếm phần lớn traffic: tenant + time, tenant + eventType + time, hay user/resource lookup?

## Gợi ý tư duy

### Gợi ý 1

Một index có thể được chọn bởi planner nhưng vẫn scan một range rất lớn. `IXSCAN` chỉ nói access path có dùng index, không nói số work đã đủ nhỏ.

### Gợi ý 2

Với query có equality trên `tenantId`, optional equality trên `eventType`, range trên `createdAt` và sort theo `createdAt`, hãy suy nghĩ theo nguyên tắc Equality → Sort → Range, nhưng luôn kiểm chứng bằng workload/explain thay vì học thuộc thứ tự.

### Gợi ý 3

`Skip(100000)` không cho database “nhảy miễn phí” tới item thứ 100001. Những entries trước offset vẫn phải được đi qua theo access path.

## Cấu trúc trả lời đề xuất

1. Xác định dominant query shapes và data distribution.
2. Đọc `explain("executionStats")` thay vì chỉ nhìn `winningPlan`.
3. Phân tích index hiện tại theo prefix và query predicates.
4. Đề xuất một số compound indexes có chủ đích cho query shapes chính.
5. Thay offset pagination bằng seek/keyset pagination khi UX cho phép.
6. Giảm document fetch bằng projection/covered-query opportunities.
7. Đo write amplification, index size, cache pressure và query latency trước–sau.
8. Rollout index an toàn và theo dõi production regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi `IXSCAN` là bằng chứng index đã tối ưu.
- Nhìn tỷ lệ `keysExamined/nReturned` và `docsExamined/nReturned`.
- Nhận ra index `{ createdAt, tenantId, eventType }` có leading field là range/time, nên với workload tenant-specific có thể scan rất nhiều timestamps của tenants khác trước khi filter.
- Đề xuất đưa equality fields có giá trị lọc cao/phù hợp query shape trước `createdAt`, ví dụ `{ tenantId: 1, createdAt: -1 }` cho query phổ biến không có `eventType`.
- Với shape tenant + eventType + time, cân nhắc `{ tenantId: 1, eventType: 1, createdAt: -1 }`.
- Nhận ra deep `Skip()` gây cost tuyến tính theo offset và nên dùng cursor/keyset khi requirements cho phép.
- Có production verification bằng `explain`, profiler/query telemetry và latency distribution.

### Điểm cộng

- Phân biệt index selectivity với field cardinality chung; selectivity phải xét theo query/data distribution.
- Cân nhắc projection để giảm fetch/network/memory; không trả `metadata` nếu list screen không cần.
- Nhận ra thêm index làm tăng write cost, storage, cache footprint và maintenance.
- Dùng stable tie-breaker như `_id` cùng `createdAt` cho cursor pagination để tránh duplicate/missing rows khi timestamps bằng nhau.
- Đề cập partial index chỉ khi query/data semantics thực sự phù hợp.

### Senior+

- Không áp dụng ESR như luật bất biến; biết trade-off giữa sort coverage và range selectivity rồi verify bằng execution stats.
- Phân tích skew: một index tốt cho tenant nhỏ chưa chắc đủ cho tenant chiếm 20% collection.
- Cân nhắc archive/partitioning/sharding chỉ khi retention/scale evidence yêu cầu, không dùng như first fix.
- Thiết kế benchmark với hot-cache/cold-cache representative workload và concurrent writes.
- Có rollout plan để build index mà không tạo incident về CPU/disk/storage.

## Hướng giải quyết tham khảo

Đầu tiên tôi sẽ sửa mental model của team: **`IXSCAN` không đồng nghĩa với efficient scan**. Query planner có thể chọn index vì nó tốt hơn collection scan, nhưng vẫn phải đi qua hàng triệu index entries để tìm 50 results.

Index hiện tại bắt đầu bằng `createdAt`:

```javascript
{ createdAt: -1, tenantId: 1, eventType: 1 }
```

Trong workload này, request luôn có `tenantId`, còn `createdAt` là range. Khi leading field là thời gian, database có thể phải scan một vùng thời gian chứa events của rất nhiều tenants rồi mới dùng phần sau của key để lọc. Nếu một tháng có hàng chục triệu events, việc “có index” vẫn có thể là một scan rất rộng.

Tôi sẽ lấy những query shapes chiếm phần lớn traffic và chạy `explain("executionStats")`. Ví dụ shape phổ biến nhất là:

```text
tenantId = X
createdAt >= from && createdAt < to
sort createdAt desc
limit 50
```

Một candidate index tự nhiên là:

```javascript
{ tenantId: 1, createdAt: -1 }
```

Vì equality trên tenant thu hẹp search space trước, sau đó index order trên `createdAt` có thể phục vụ time range và descending sort. Với shape có `eventType` equality thường xuyên:

```javascript
{ tenantId: 1, eventType: 1, createdAt: -1 }
```

có thể tốt hơn. Nhưng tôi không tự động giữ cả hai nếu traffic không biện minh; cần xem query frequency, index size và write cost.

Điều tôi muốn thấy sau thay đổi là `keysExamined` và `docsExamined` gần `nReturned` hơn cho representative queries. Không nhất thiết tỷ lệ luôn 1:1, nhưng từ hàng triệu keys để lấy 50 rows là tín hiệu rõ ràng access path còn kém.

Vấn đề thứ hai độc lập với index field order là offset pagination:

```csharp
.Skip(page * pageSize)
```

Page 2,000 với page size 50 nghĩa là hệ thống phải đi qua khoảng 100,000 ordered entries trước khi trả batch tiếp theo. Index giúp traversal hiệu quả hơn collection scan nhưng không biến deep offset thành O(1).

Nếu product chỉ cần next/previous, tôi đổi sang cursor pagination dựa trên sort key ổn định, ví dụ `(createdAt, _id)`:

```text
WHERE tenantId = X
AND (
    createdAt < lastCreatedAt
    OR (createdAt = lastCreatedAt AND _id < lastId)
)
ORDER BY createdAt DESC, _id DESC
LIMIT 50
```

Tương ứng index có thể cần:

```javascript
{ tenantId: 1, createdAt: -1, _id: -1 }
```

Nếu có `eventType`, query shape/index được điều chỉnh tương ứng. `_id` làm tie-breaker để hai records có cùng timestamp không gây duplicate/missing khi lật trang.

Tôi cũng kiểm tra projection. List view có thể chỉ cần `eventType`, `createdAt`, `resourceId`, `userId`; nếu lấy cả `metadata.description` lớn cho mọi row, document fetch/network/deserialization vẫn tốn chi phí dù index scan tốt. Projection có thể giảm bytes và memory. Covered query chỉ đáng theo đuổi nếu fields/index size trade-off hợp lý; không nhồi mọi field vào index chỉ để đạt covered query.

Về production rollout, tôi sẽ:

1. chụp baseline p50/p95/p99, `keysExamined`, `docsExamined`, CPU, disk reads và query shape frequency;
2. build candidate index trong staging với production-like cardinality;
3. benchmark hot/cold working-set conditions;
4. rollout index vào production trong window có headroom, theo dõi index-build resource impact;
5. deploy query/cursor change behind flag nếu cần;
6. so sánh query latency và write overhead;
7. chỉ drop index cũ sau observation period và xác nhận không có query shape khác phụ thuộc vào nó.

Nếu sau khi access path/pagination đã tốt nhưng working set vẫn vượt RAM và retention 7 năm khiến dataset tiếp tục tăng, lúc đó mới bàn archive old data, tiering hoặc sharding. Hardware có thể là một phần solution, nhưng không nên mua hardware để che một query đang scan hàng triệu keys cho 50 rows.

## Mẫu trả lời trong phỏng vấn

“Điểm đầu tiên tôi phản biện là `IXSCAN` không chứng minh query đã efficient. Tôi sẽ nhìn `executionStats`: nếu `keysExamined` hàng triệu mà `nReturned` chỉ 50 thì index vẫn buộc database làm rất nhiều work.

Index hiện tại bắt đầu bằng `createdAt`, trong khi query luôn equality theo `tenantId`. Với range 30 ngày, nó có thể scan events của rất nhiều tenants trong time window rồi mới lọc tenant. Tôi sẽ benchmark `{ tenantId: 1, createdAt: -1 }` cho shape chính; nếu `eventType` là equality phổ biến thì benchmark thêm `{ tenantId: 1, eventType: 1, createdAt: -1 }`. Tôi không tạo index cho mọi combination vì mỗi index tăng write/storage/cache cost.

Deep pagination cũng là vấn đề riêng. `Skip(100000)` vẫn phải traverse 100,000 entries. Nếu UX chỉ cần next/previous, tôi dùng cursor trên `(createdAt, _id)` và stable sort để page cost không tăng theo offset.

Sau đó tôi dùng projection nhỏ hơn và đo lại p95/p99, keys/docs examined, disk reads, CPU và write latency. Nếu workload sau tối ưu vẫn vượt memory/storage capacity thì mới đánh giá archive/sharding/hardware. Tôi muốn evidence cho từng bước, không dùng ‘đã có index’ như điểm kết thúc investigation.”

## Câu hỏi đào sâu

1. Nếu 95% requests không filter `eventType`, nhưng 5% requests có `eventType` là admin export rất nặng, bạn có giữ index thứ hai không?
2. Nếu product bắt buộc jump trực tiếp tới page 2,000, bạn sẽ giữ offset pagination hay thay đổi contract/storage model thế nào?
3. Nếu thêm compound index làm read p99 giảm 80% nhưng write latency tăng 25%, bạn cần dữ liệu nào để quyết định giữ hay bỏ?

## Lỗi trả lời thường gặp

- Chỉ nói “tạo index” mà không đọc execution stats.
- Học thuộc ESR rồi áp dụng mà không xét data distribution/query frequency.
- Tạo một index cho mọi filter combination.
- Bỏ qua deep `Skip()` và chỉ tối ưu compound index.
- Đề xuất sharding ngay trước khi sửa query/index cơ bản.
- Không đo write amplification và index footprint.

## Thang điểm 0–10

- **0–2:** Chỉ biết `COLLSCAN` xấu, `IXSCAN` tốt.
- **3–4:** Nhận ra field order quan trọng nhưng chưa giải thích scan/selectivity/pagination.
- **5–6:** Đề xuất compound index hợp lý, đọc execution stats và thay deep offset bằng cursor.
- **7–8:** Cân bằng query shapes, projection, index cost, skew và production rollout.
- **9–10:** Kết nối planner/access path → data distribution → pagination → working set → evidence; biết khi nào mới cần archive/sharding/hardware.

# Câu 2 — Cùng một commit nhưng production chạy DLL khác staging: pipeline “rebuild per environment” đã phá rollback thế nào?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Git, TeamCity, Octopus Deploy, .NET build/publish, artifact immutability, CI/CD, versioning, configuration management, rollback, supply-chain integrity, observability

## Bối cảnh

Một team .NET deploy ASP.NET Core application qua TeamCity và Octopus Deploy.

Flow hiện tại:

1. merge PR vào `main`;
2. TeamCity build và deploy staging;
3. QA approve;
4. production deployment kích hoạt một TeamCity build mới từ `main`;
5. build production chạy `dotnet restore`, `dotnet publish`, tạo ZIP mới rồi push package lên Octopus;
6. Octopus deploy package mới vào production.

Team cố giữ cùng một semantic version `4.18.0` cho staging và production vì cho rằng “đó vẫn là cùng release”.

Một incident xảy ra:

- staging đã test package lúc 10:00 và pass;
- 10:20 có một PR khác merge vào `main` để chuẩn bị release kế tiếp;
- 10:40 production approval được nhấn;
- production build checkout `main` mới nhất, build lại package nhưng vẫn gắn version `4.18.0`;
- production xuất hiện behavior chưa từng thấy ở staging;
- team thử rollback về `4.17.3`, nhưng package feed có hai artifacts mang metadata/version gây khó xác định cái nào thực sự từng chạy;
- một NuGet dependency dùng floating version đã resolve patch khác so với build staging;
- config transform cũng được TeamCity áp khác nhau giữa staging/prod;
- Git SHA không được expose trong application telemetry;
- câu hỏi “production đang chạy source nào và dependency graph nào?” mất gần 40 phút mới trả lời được.

Một developer đề xuất fix bằng cách “tag Git tại thời điểm deploy production rồi rebuild từ tag”. Một người khác nói “Octopus đã là deployment tool nên artifact immutability không quan trọng”.

## Câu hỏi chính

Bạn sẽ xử lý incident và redesign pipeline thế nào để một release candidate đã test là **đúng cùng binary/artifact** được promote qua environments, rollback deterministic, configuration vẫn environment-specific mà không rebuild code, và operators có thể xác định ngay Git commit/package/dependency version đang chạy?

## Câu hỏi làm rõ nên cân nhắc

1. TeamCity hiện tạo package version bằng cách nào và artifact repository có cho overwrite cùng version không?
2. `dotnet restore` có dùng lock file/central package management hay floating/transitive versions không?
3. Config nào đang compile/build-time và config nào thực sự runtime environment-specific?
4. Octopus release snapshot có pin exact package versions/variables không?
5. Production nodes có thể chạy nhiều package versions trong rolling deployment không?
6. Secrets được inject ở deploy/runtime hay nhúng vào artifact?

## Gợi ý tư duy

### Gợi ý 1

Một release tốt nên trả lời: **build once, identify once, promote many**. Environment promotion không nên thay đổi bytes của application artifact.

### Gợi ý 2

Git tag giúp định danh source, nhưng nếu mỗi environment vẫn restore/build lại thì toolchain/dependency/feed state có thể làm binary khác dù source commit giống nhau.

### Gợi ý 3

Immutable application artifact không có nghĩa mọi config phải giống nhau. Phân biệt artifact identity với environment/runtime configuration và secrets.

## Cấu trúc trả lời đề xuất

1. Stabilize incident và xác định exact bytes/version đang chạy.
2. Reconstruct provenance: commit, build ID, package hash, dependency lock, config snapshot.
3. Loại bỏ artifact overwrite/rebuild-per-environment.
4. Thiết kế build-once/promotion flow.
5. Tách application artifact khỏi environment config/secrets.
6. Thiết kế deterministic rollback.
7. Expose deployment provenance trong telemetry/health/info endpoint.
8. Bổ sung pipeline policies/tests/audit.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra rebuild production từ moving `main` là correctness failure của release process.
- Cùng semantic version không bảo đảm cùng binary nếu build lại.
- Đề xuất build một immutable artifact từ một exact commit rồi promote artifact đó staging → production.
- Package/version không được overwrite; mỗi artifact phải có unique immutable identity.
- Rollback phải chọn một previously deployed known-good artifact, không rebuild source cũ.
- Environment config/secrets được inject mà không thay application binary.
- Expose Git SHA/build/package version trong telemetry.

### Điểm cộng

- Pin SDK/toolchain và dependency resolution; dùng lock files khi phù hợp.
- Lưu artifact checksum/SBOM/provenance metadata.
- Octopus release should pin package version và variable snapshot theo release.
- Phân biệt deployment rollback với database rollback; schema changes cần expand/contract compatibility.
- Có policy ngăn package feed overwrite.

### Senior+

- Nhận ra tag-then-rebuild vẫn không bảo đảm byte-for-byte identity nếu build environment/dependencies khác.
- Cân nhắc reproducible builds nhưng không dùng reproducibility thay cho promotion artifact.
- Thiết kế promotion approvals dựa trên artifact digest/build ID thay vì branch state.
- Có artifact retention đủ để rollback và incident forensics.
- Đưa provenance vào logs/traces để phân biệt mixed-version nodes trong rolling rollout.

## Hướng giải quyết tham khảo

Trong incident, ưu tiên đầu tiên là ngừng deploy thêm và xác định chính xác production đang chạy gì. Tôi sẽ lấy package/deployment metadata từ Octopus, file version/assembly informational version nếu có, package hash và TeamCity build ID. Nếu application chưa expose Git SHA thì có thể phải truy ngược package manifest/build logs. Đồng thời so staging package hash với production package hash. Nếu khác, đó là bằng chứng trực tiếp rằng “release 4.18.0” thực tế không phải cùng artifact.

Root cause process-level là production **rebuild** thay vì **promote**. Staging đã test binary A, còn production build từ một moving branch tạo binary B. Kể cả checkout cùng Git SHA, dependency feed hoặc SDK/toolchain khác vẫn có thể tạo output khác. Vì vậy Git tag chỉ giải quyết source identity, không thay thế artifact identity.

Pipeline tôi muốn:

```text
PR merge
  ↓
TeamCity build exact commit once
  ↓
restore/test/publish/package
  ↓
immutable package: OrdersApi.4.18.0+build.731.zip
Git SHA: abc123...
Package SHA256: ...
  ↓
Octopus release references exact package version
  ↓
Deploy Dev/Staging
  ↓
QA approval
  ↓
Promote SAME Octopus release/package to Production
```

Không có `dotnet publish` mới ở bước production. Production approval chỉ thay đổi **where the existing artifact is deployed**, không thay đổi source/dependencies/binary.

Package repository phải reject overwrite cùng immutable version. Nếu organization muốn semantic release `4.18.0`, internal build metadata/build number vẫn phải tạo identity duy nhất. Điều quan trọng là deployment record pin exact artifact/digest.

Dependencies cũng cần determinism hợp lý. Floating versions trong release builds làm provenance yếu. Tôi sẽ xem `packages.lock.json`, Central Package Management, exact package versions và pinned .NET SDK qua `global.json` khi phù hợp. CI logs/SBOM lưu resolved dependency graph. Không cần tuyên bố mọi build byte-for-byte reproducible ngay lập tức; build-once already loại bỏ class lỗi chính.

Configuration cần tách khỏi binary. Ví dụ artifact chứa application code và baseline non-secret defaults. Octopus/environment injects connection strings, endpoints, feature flags hoặc secret references qua environment variables/config files/runtime provider. Nhưng config snapshot/version phải audit được để trả lời “binary giống nhau nhưng environment behavior khác vì config nào”. Secret value không nên log ra telemetry.

Rollback là chọn exact previous release/artifact đã chạy tốt, ví dụ package hash của `4.17.3-build.702`, rồi redeploy. Không checkout old tag và build lại. Tuy nhiên database migration cần plan riêng: nếu release mới đã thực hiện destructive schema change thì binary rollback có thể không còn compatible. Vì vậy schema changes nên expand/contract để old/new app coexist trong rollback window.

Tôi sẽ embed provenance lúc build:

```xml
<PropertyGroup>
  <ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>
  <InformationalVersion>$(Version)+$(GitCommit)</InformationalVersion>
</PropertyGroup>
```

và expose safe metadata trong health/info/telemetry:

```json
{
  "version": "4.18.0",
  "buildId": "731",
  "gitSha": "abc123def...",
  "artifactDigest": "sha256:..."
}
```

Logs/traces có deployment version dimension. Với rolling deploy, dashboard có thể so p95/error rate giữa old/new versions.

Guardrails:

- build step outputs one package once;
- production deployment job không có compile/restore permissions/path;
- immutable package feed;
- exact package pinned in Octopus release;
- deployment approval page hiển thị Git SHA + package digest;
- artifact retention covers rollback policy;
- automated smoke checks after deployment;
- audit records who promoted what artifact where and when.

## Mẫu trả lời trong phỏng vấn

“Root cause lớn nhất không phải Git tag; đó là team test artifact A ở staging nhưng production lại build artifact B từ một moving branch và thậm chí resolve dependencies lại. Cùng version string `4.18.0` không làm hai ZIP giống nhau.

Tôi chuyển pipeline sang build once, promote many. TeamCity checkout exact commit, restore/test/publish một lần, tạo immutable package có unique build identity, Git SHA và digest. Octopus release pin đúng package đó. QA approve release thì production deploy cùng package bytes, không chạy `dotnet publish` lần nữa.

Git tag vẫn hữu ích để identify source nhưng tôi không dùng tag-then-rebuild như promotion. Dependency versions và SDK cũng phải pin đủ để provenance rõ; package feed cấm overwrite.

Config/secrets vẫn environment-specific, nhưng inject tại deploy/runtime và được version/audit riêng; không rebuild binary để đổi connection string. Rollback deploy lại exact known-good artifact trước đó, còn DB schema dùng expand/contract để binary rollback còn khả thi.

Cuối cùng application expose version/build/Git SHA/artifact digest trong telemetry. Khi incident xảy ra, tôi muốn mất vài giây chứ không phải 40 phút để biết từng node đang chạy release nào.”

## Câu hỏi đào sâu

1. Nếu cùng artifact nhưng production vẫn behavior khác staging, bạn sẽ kiểm tra config, data, infrastructure và feature flags theo thứ tự nào?
2. Nếu security patch của NuGet dependency xuất hiện sau staging approval nhưng trước production, bạn promote artifact đã test hay rebuild? Quy trình release mới nên thế nào?
3. Nếu rollback binary cũ nhưng database đã migrate schema không backward-compatible, bạn xử lý ra sao và phòng ngừa từ trước thế nào?

## Lỗi trả lời thường gặp

- Cho rằng Git tag là đủ để bảo đảm binary giống nhau.
- Rebuild lại source cũ khi rollback.
- Cho phép overwrite package version trong artifact feed.
- Nhúng production config/secrets vào build artifact để “giữ mọi thứ cố định”.
- Không expose provenance trong telemetry.
- Bỏ qua database compatibility trong rollback.

## Thang điểm 0–10

- **0–2:** Chỉ nói tag branch hoặc thêm manual approval.
- **3–4:** Nhận ra phải pin commit nhưng vẫn rebuild từng environment.
- **5–6:** Build-once/promote-many, immutable package và deterministic rollback.
- **7–8:** Thêm dependency/toolchain pinning, config separation, provenance telemetry và DB compatibility.
- **9–10:** Thiết kế được release provenance end-to-end, artifact digest/audit/retention, mixed-version observability và policy guardrails chống tái diễn.

# Câu 3 — REST API có 12 consumers: versioning thế nào để đổi contract mà không biến mỗi thay đổi thành `/v2`, `/v3`, `/v4`?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** REST API design, backward compatibility, contract evolution, ASP.NET Core, OpenAPI, consumer-driven testing, deprecation, database migration, rollout strategy, observability, architecture trade-offs

## Bối cảnh

Một Employee Platform expose REST API dùng bởi:

- web app nội bộ;
- mobile app có user đôi khi không update trong 6 tháng;
- 4 internal services;
- Power BI/data integration scripts;
- 3 external partner integrations;
- một automation platform do operations team quản lý.

Endpoint hiện tại:

```http
GET /api/employees/{id}
```

Response:

```json
{
  "id": 123,
  "fullName": "Nguyen Van A",
  "department": "Engineering",
  "managerId": 50,
  "status": "Active"
}
```

Business muốn thay đổi dần:

1. `fullName` được tách thành structured name để hỗ trợ localization;
2. `department` từ string chuyển thành object có `id`, `code`, `displayName`;
3. thêm trạng thái mới `OnLeave` và `Suspended`;
4. một field nhạy cảm mới chỉ được trả cho caller có permission;
5. trong 12 tháng tới sẽ bỏ `managerId` cũ để hỗ trợ multiple reporting lines;
6. database schema cũng phải đổi theo.

Một team đề xuất tạo `/api/v2/employees/{id}` ngay và copy controller/service models, sau đó mọi breaking change tiếp theo lại tạo version mới. Team khác muốn giữ `/api/employees/{id}` mãi mãi và “consumer phải tolerant với JSON thay đổi”.

External partners yêu cầu ít nhất 6 tháng notice trước breaking change. Mobile app không thể force upgrade ngay lập tức. Internal services có thể deploy nhanh hơn nhưng ownership nằm ở nhiều teams.

## Câu hỏi chính

Bạn sẽ thiết kế strategy cho API contract evolution/versioning/deprecation thế nào để hỗ trợ thay đổi business trên, giữ backward compatibility có chủ đích, không clone toàn bộ codebase theo version, và có bằng chứng rằng một field/version cũ thực sự không còn consumer trước khi remove?

## Câu hỏi làm rõ nên cân nhắc

1. Consumers nào do team kiểm soát và consumers nào có release cadence độc lập?
2. Có API gateway/client identity để đo usage theo consumer/version/field route không?
3. Mobile app versions cũ nhất còn active là gì và retention distribution thế nào?
4. Contract hiện được publish qua OpenAPI/SDK hay consumers tự hand-code?
5. External partner agreements quy định deprecation/SLA ra sao?
6. Có requirement legal/security nào buộc field phải biến mất ngay thay vì giữ compatibility window?

## Gợi ý tư duy

### Gợi ý 1

Không phải mọi schema change đều là breaking change. Thêm optional field thường khác hoàn toàn với đổi type hoặc remove/rename field.

### Gợi ý 2

Versioning là consumer-coordination strategy, không chỉ là URL naming convention.

### Gợi ý 3

Hãy tách **domain model evolution** khỏi **wire contract evolution**. Internal model/database có thể tiến lên trước trong khi adapter vẫn emit legacy shape trong compatibility window.

## Cấu trúc trả lời đề xuất

1. Inventory consumers và compatibility requirements.
2. Classify từng requested change: additive, behavioral hay breaking.
3. Định nghĩa API compatibility policy.
4. Thiết kế contract adapters để tránh clone business logic theo version.
5. Thiết kế rollout/deprecation timeline.
6. Đồng bộ database migration bằng expand/contract.
7. Thêm contract tests/OpenAPI diff/consumer verification.
8. Đo version/consumer usage trước removal.
9. Định nghĩa khi nào version mới thực sự cần thiết.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tạo major API version cho mọi additive change.
- Nhận ra đổi `department` string → object và `managerId` single → reporting-lines collection là breaking changes nếu thay tại cùng field.
- Có compatibility window, deprecation notice và usage telemetry.
- Tách public DTO/wire contract khỏi domain/database model.
- Reuse core business logic và dùng representation/version adapters thay vì copy controller/service stack.
- Có expand/contract database migration để old/new contracts coexist.
- Có contract/OpenAPI tests trong CI.

### Điểm cộng

- Giữ legacy field song song với new field trong migration window, ví dụ add `name`, `departmentInfo`, `reportingLines` trước khi remove old fields.
- Enum evolution được xử lý cẩn thận vì clients có thể deserialize closed enum và crash với value mới.
- Security-sensitive field có authorization ở server, không chỉ “consumer tự bỏ qua”.
- Deprecation headers/docs/changelog được xem như communication channel, nhưng không thay usage telemetry.
- API gateway/client ID giúp biết consumer nào còn gọi legacy version.

### Senior+

- Phân biệt representation versioning với domain service versioning.
- Biết rằng tolerant reader không cứu được client dùng generated enum/switch exhaustive/type assumptions.
- Có automated compatibility checks giữa OpenAPI current/proposed.
- Thiết kế sunset dựa trên measured traffic + contractual obligations, không dựa trên “đã gửi email 6 tháng trước”.
- Có strategy cho emergency security removal khác normal deprecation.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng compatibility policy, không bắt đầu bằng `/v2`. Mỗi thay đổi được classify.

### 1. Structured name

Thay trực tiếp:

```json
"fullName": "Nguyen Van A"
```

thành:

```json
"fullName": {
  "given": "Van A",
  "family": "Nguyen"
}
```

là breaking vì type đổi từ string sang object. Nhưng ta có thể làm additive trước:

```json
{
  "fullName": "Nguyen Van A",
  "name": {
    "given": "Van A",
    "family": "Nguyen",
    "display": "Nguyen Van A"
  }
}
```

Consumers migrate sang `name`; `fullName` được deprecate rồi remove ở một major compatibility boundary sau.

### 2. Department

Tương tự, không đổi type của `department` in-place nếu clients cũ expect string. Thêm:

```json
"departmentInfo": {
  "id": 7,
  "code": "ENG",
  "displayName": "Engineering"
}
```

Giữ `department` trong compatibility window.

### 3. Enum status

Thêm `OnLeave`/`Suspended` trông additive nhưng có thể breaking về behavior. Client C# generated từ OpenAPI có enum đóng hoặc code `switch` không có default có thể fail. Vì vậy compatibility checklist phải xem consumer behavior, không chỉ JSON schema. Có thể document unknown-value handling, update SDKs trước và theo dõi client versions.

### 4. Sensitive field

Field nhạy cảm chỉ xuất hiện khi server authorization cho phép. Không để client truyền `includeSensitive=true` rồi tin vào flag. Permission evaluation nằm ở application/resource authorization. Cache/CDN layer nếu có phải tránh cache response privileged rồi serve cho unprivileged caller.

### 5. Reporting lines

Add new collection first:

```json
"reportingLines": [
  { "managerId": 50, "type": "Primary" }
]
```

và giữ `managerId` mapped từ primary manager cho legacy clients. Khi all required consumers migrate, remove `managerId` trong next breaking version/sunset.

### Khi nào tạo `/v2`?

Nếu compatibility shape trở nên quá mâu thuẫn, semantics thay đổi sâu hoặc cần remove/change existing fields, major version là hợp lý. Nhưng tôi không clone entire application. Core domain/application service trả một canonical internal model; presentation layer maps sang `EmployeeV1Response` hoặc `EmployeeV2Response`.

Conceptually:

```csharp
public sealed record EmployeeView(
    int Id,
    PersonName Name,
    DepartmentView Department,
    IReadOnlyList<ReportingLine> ReportingLines,
    EmployeeStatus Status);

public interface IEmployeeQueryService
{
    Task<EmployeeView?> GetAsync(int id, ClaimsPrincipal user, CancellationToken ct);
}
```

Then adapters:

```csharp
EmployeeV1Response MapV1(EmployeeView employee) => ...;
EmployeeV2Response MapV2(EmployeeView employee) => ...;
```

Business rules/data access không bị copy per version. Nếu behavior thực sự khác theo contract, difference phải explicit và testable.

### Database migration

Wire compatibility phải đi cùng schema compatibility. Nếu `DepartmentName` string đang nằm trong Employee table và muốn normalize sang `DepartmentId`, tôi làm expand/contract:

1. add new table/column;
2. deploy code có thể đọc old + new theo transition plan;
3. backfill;
4. switch writes/reads;
5. keep old column while old app/API versions may require it;
6. remove old schema only after rollback/compatibility window closed.

Không deploy destructive rename cùng release với application expecting new schema nếu old version còn traffic.

### Deprecation lifecycle

Tôi định nghĩa policy, ví dụ:

- additive compatible changes: normal release;
- breaking contract: new major representation/version hoặc explicit migration bridge;
- external partners: minimum 6-month deprecation notice;
- sunset date chỉ được finalize khi contractual conditions + usage evidence cho phép;
- security emergency có exception process riêng.

Docs/OpenAPI đánh dấu deprecated fields. Nếu phù hợp, response có `Deprecation`/`Sunset` headers theo supported standards/gateway capabilities. Nhưng communication không đủ — phải đo usage.

Tôi muốn client identity (`client_id`, API key identity, mTLS principal hoặc gateway consumer) và metrics theo API version/route. Không log sensitive payload. Dashboard trả lời:

- request count V1/V2 theo consumer;
- last-seen timestamp của legacy consumers;
- error rate sau migration;
- active mobile app versions;
- partner adoption status.

Nếu không có field-level usage, ít nhất endpoint/version usage + owner mapping giúp coordinate. Với field removal quan trọng, có thể instrument server-side legacy-field adapter usage nếu architecture cho phép.

### CI protection

OpenAPI spec là versioned artifact. CI chạy breaking-change diff giữa proposed và released contract. Integration/contract tests assert legacy DTO shape. Consumer-driven contract tests hữu ích cho critical internal consumers nhưng không thay producer compatibility policy.

Test matrix bao gồm old mobile/client SDK against new server. Với enum, test unknown/new value behavior. Với permissions, test response shape/cache behavior cho privileged/unprivileged callers.

## Mẫu trả lời trong phỏng vấn

“Tôi không tạo `/v2` cho mọi thay đổi và cũng không dựa vào câu ‘JSON clients phải tolerant’. Tôi classify change. Thêm field mới thường compatible; đổi type của `fullName` hay `department` là breaking; thêm enum value có thể behavior-breaking với generated clients.

Tôi sẽ giữ domain model mới độc lập với wire contract. Ví dụ thêm `name`, `departmentInfo`, `reportingLines` song song với legacy fields. Consumers migrate dần. Nếu sau compatibility window cần remove/change old fields, khi đó V2 có lý, nhưng V1/V2 chỉ là adapters trên cùng application service chứ không copy toàn bộ controller/business/data stack.

Database cũng migrate expand/contract để old/new contracts cùng hoạt động và rollback được. Với external partners tôi giữ minimum notice 6 tháng, nhưng không remove chỉ vì deadline đã qua: gateway telemetry phải cho biết consumer nào còn gọi legacy version. Mobile app version distribution cũng phải được theo dõi.

CI chạy OpenAPI breaking-change checks và old-client contract tests. Sensitive fields được authorize server-side. Với status enum, tôi test client behavior với unknown values vì schema additive chưa chắc runtime-compatible.

Mục tiêu là version khi semantics thực sự cần boundary mới, còn additive evolution thì giữ contract stable. Versioning ở đây là coordination + evidence problem, không chỉ chọn URL format.”

## Câu hỏi đào sâu

1. Nếu external partner duy nhất còn dùng V1 không chịu migrate sau 9 tháng nhưng mang lại 20% doanh thu, bạn xử lý sunset thế nào?
2. Nếu security review yêu cầu xóa một field nhạy cảm ngay trong 48 giờ, compatibility/deprecation policy có còn áp dụng không?
3. Bạn chọn URL versioning, header versioning hay media-type versioning cho hệ thống này? Điều gì khiến lựa chọn đó quan trọng hoặc không quan trọng bằng lifecycle policy?

## Lỗi trả lời thường gặp

- Tạo `/v2` ngay cho mọi field mới.
- Copy toàn bộ service/repository code theo mỗi API version.
- Cho rằng thêm enum value luôn backward-compatible.
- Chỉ gửi deprecation email nhưng không đo actual usage.
- Thay database schema destructively trước khi old clients/version hết traffic.
- Dùng “tolerant reader” như lý do để đổi type/semantics tùy ý.
- Không phân biệt normal deprecation với emergency security removal.

## Thang điểm 0–10

- **0–2:** Versioning chỉ được hiểu là thêm `/v2` vào URL.
- **3–4:** Biết additive vs breaking nhưng thiếu migration/deprecation evidence.
- **5–6:** Có DTO adapters, compatibility window, expand/contract DB và usage telemetry.
- **7–8:** Xử lý tốt enum/mobile/external partner/security nuances, contract tests và rollout.
- **9–10:** Thiết kế contract-evolution lifecycle end-to-end, giảm version sprawl, giữ reversibility và coordination dựa trên measured consumer adoption.
