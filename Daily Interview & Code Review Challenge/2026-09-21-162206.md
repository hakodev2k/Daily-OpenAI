# Code Review Challenge 1 — EF Core lost update trong approval workflow

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, SQL Server, optimistic concurrency, authorization, transaction boundary  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một enterprise portal có workflow duyệt expense request. Một request ở trạng thái `Pending` có thể được manager `Approve` hoặc `Reject`. UI tải request, cho manager xem dữ liệu rồi gửi quyết định. Hệ thống chạy nhiều Azure App Service instances và dùng SQL Server.

Production ghi nhận một số request có audit log `Rejected` nhưng trạng thái cuối cùng lại là `Approved`. Team nghi ngờ database bị lỗi vì mỗi API call đều gọi `SaveChangesAsync()` thành công. Có trường hợp hai manager thao tác gần như đồng thời trên cùng request. Requirement nghiệp vụ là quyết định đầu tiên thành công phải thắng; quyết định sau phải nhận conflict và không được ghi audit như thể nó đã thành công.

## Đoạn code cần review

```csharp
public sealed class ExpenseRequest
{
    public Guid Id { get; set; }
    public string Status { get; set; } = "Pending";
    public string? DecisionBy { get; set; }
    public DateTimeOffset? DecisionAt { get; set; }
}

public sealed class ApprovalService
{
    private readonly AppDbContext _db;
    private readonly ILogger<ApprovalService> _logger;

    public ApprovalService(AppDbContext db, ILogger<ApprovalService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task DecideAsync(
        Guid requestId,
        bool approve,
        string managerId,
        CancellationToken cancellationToken)
    {
        var request = await _db.ExpenseRequests
            .SingleAsync(x => x.Id == requestId, cancellationToken);

        if (request.Status != "Pending")
            throw new InvalidOperationException("Request already decided");

        request.Status = approve ? "Approved" : "Rejected";
        request.DecisionBy = managerId;
        request.DecisionAt = DateTimeOffset.UtcNow;

        _db.ApprovalAudits.Add(new ApprovalAudit
        {
            RequestId = requestId,
            Decision = request.Status,
            ManagerId = managerId,
            CreatedAt = DateTimeOffset.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Request {RequestId} changed to {Status} by {ManagerId}",
            requestId, request.Status, managerId);
    }
}
```

2. Xác định reliability/security/maintainability concerns liên quan.
3. Giải thích production impact và failure timeline.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design bảo đảm “first successful decision wins”.
6. Giải thích cách kiểm thử race condition.

## Câu hỏi gợi mở

3. Audit row và state transition cần có transaction boundary ra sao?
4. Authorization của `managerId` nên được tin từ đâu?

## Kết quả code review tham khảo

### Critical — Lost update cho phép quyết định sau ghi đè quyết định trước

**Vấn đề:** Entity không có concurrency token và update không có điều kiện bảo vệ trạng thái ban đầu. Hai request có thể cùng đọc `Pending`, sau đó cả hai `SaveChangesAsync()` thành công; update commit sau ghi đè `Status`, `DecisionBy`, `DecisionAt`.

**Tại sao xảy ra:** Check `request.Status != "Pending"` chỉ kiểm tra snapshot đã đọc trong từng `DbContext`. Nó không phải atomic compare-and-set ở database.

**Ảnh hưởng production:** Business invariant “first successful decision wins” bị phá vỡ; trạng thái cuối cùng có thể trái với quyết định đã được người dùng thấy là thành công.

**Cách sửa:** Dùng optimistic concurrency token như SQL Server `rowversion`, hoặc atomic conditional update `WHERE Id = @id AND Status = 'Pending'` và yêu cầu affected rows bằng 1. Nếu affected rows bằng 0, trả conflict.

### High — Audit có thể ghi lịch sử của một quyết định đã bị ghi đè

**Vấn đề:** Mỗi transaction có thể insert audit row của chính nó trong khi state cuối cùng chỉ phản ánh transaction commit sau.

**Tại sao xảy ra:** Audit mô tả “decision succeeded”, nhưng không có concurrency precondition khiến decision thứ hai thất bại.

**Ảnh hưởng production:** Audit trail trở nên khó diễn giải hoặc sai semantic, đặc biệt với compliance và incident investigation.

**Cách sửa:** Chỉ tạo audit cho state transition thực sự thắng concurrency check; state transition và audit phải commit atomically trong cùng local database transaction/unit of work.

### High — `managerId` là input có thể bị spoof nếu lấy trực tiếp từ request

**Vấn đề:** Service nhận `managerId` như dữ liệu gọi vào mà snippet không chứng minh identity này đến từ authenticated principal hoặc authorization policy.

**Tại sao xảy ra:** Business identity và caller-supplied data bị trộn lẫn.

**Ảnh hưởng production:** Nếu controller truyền giá trị do client kiểm soát, audit attribution và authorization có thể sai.

**Cách sửa:** Lấy actor identity từ authenticated claims/context ở trusted boundary và kiểm tra policy/ownership phù hợp. Không dùng client-supplied manager ID làm nguồn sự thật.

### High — Business conflict bị biểu diễn bằng `InvalidOperationException`

**Vấn đề:** “Already decided” là expected domain conflict, không phải unexpected server failure.

**Tại sao xảy ra:** Exception generic không biểu diễn API semantics.

**Ảnh hưởng production:** Có thể bị map thành `500`, gây retry sai và telemetry nhiễu.

**Cách sửa:** Trả domain result/typed exception được map sang `409 Conflict` (hoặc contract tương đương) và không retry tự động như transient infrastructure failure.

### Medium — String status cho phép invalid state và typo

**Vấn đề:** `Status` là mutable string.

**Tại sao xảy ra:** Domain state không được biểu diễn bằng type/constraint đủ chặt.

**Ảnh hưởng production:** Có thể tạo trạng thái không hợp lệ từ code/migration/manual operation.

**Cách sửa:** Dùng enum/value object phù hợp và database constraint nếu có giá trị hữu hạn; vẫn phải xử lý compatibility khi schema hiện tại lưu string.

### Medium — Hai timestamp được lấy riêng

**Vấn đề:** `DecisionAt` và audit `CreatedAt` gọi `UtcNow` hai lần.

**Tại sao xảy ra:** Không có một logical decision timestamp dùng chung.

**Ảnh hưởng production:** Thường nhỏ nhưng gây khó khi reconstruct event timeline chính xác.

**Cách sửa:** Capture một `now` và dùng cho cả state transition lẫn audit; có thể inject `TimeProvider` để test deterministic.

### Medium — Logging cần phân biệt conflict với successful transition

**Vấn đề:** Log success chỉ có sau save, nhưng không có structured telemetry riêng cho concurrency conflict.

**Tại sao xảy ra:** Workflow chưa coi conflict là expected observable outcome.

**Ảnh hưởng production:** Khó đo contention và phát hiện UI/client đang tạo duplicate decisions.

**Cách sửa:** Ghi metric/log structured cho `approval_conflict`, actor, request ID và outcome; không log dữ liệu nhạy cảm không cần thiết.

## Phiên bản đề xuất

Một cách dùng SQL Server `rowversion` với EF Core:

```csharp
public sealed class ExpenseRequest
{
    public Guid Id { get; set; }
    public ExpenseStatus Status { get; set; } = ExpenseStatus.Pending;
    public string? DecisionBy { get; set; }
    public DateTimeOffset? DecisionAt { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = Array.Empty<byte>();
}

public sealed record DecisionResult(bool Succeeded, bool Conflict);

public async Task<DecisionResult> DecideAsync(
    Guid requestId,
    bool approve,
    string authenticatedManagerId,
    CancellationToken cancellationToken)
{
    var request = await _db.ExpenseRequests
        .SingleOrDefaultAsync(x => x.Id == requestId, cancellationToken);

    if (request is null)
        throw new KeyNotFoundException();

    if (request.Status != ExpenseStatus.Pending)
        return new(false, true);

    var now = _timeProvider.GetUtcNow();
    request.Status = approve ? ExpenseStatus.Approved : ExpenseStatus.Rejected;
    request.DecisionBy = authenticatedManagerId;
    request.DecisionAt = now;

    _db.ApprovalAudits.Add(new ApprovalAudit
    {
        RequestId = requestId,
        Decision = request.Status.ToString(),
        ManagerId = authenticatedManagerId,
        CreatedAt = now
    });

    try
    {
        await _db.SaveChangesAsync(cancellationToken);
        return new(true, false);
    }
    catch (DbUpdateConcurrencyException)
    {
        _db.ChangeTracker.Clear();
        return new(false, true);
    }
}
```

Model configuration có thể dùng:

```csharp
modelBuilder.Entity<ExpenseRequest>()
    .Property(x => x.Version)
    .IsRowVersion();
```

Nếu chỉ cần atomic state transition đơn giản, một conditional `UPDATE ... WHERE Status = 'Pending'` hoặc `ExecuteUpdateAsync` với kiểm tra affected rows có thể rõ hơn. Khi audit phải được ghi cùng transition, cần giữ cả hai thay đổi trong một local transaction và chỉ insert audit khi transition thắng.

## Giải thích thiết kế sau khi sửa

`rowversion` khiến EF Core đưa concurrency token vào điều kiện `UPDATE`. Hai request cùng đọc một version; transaction đầu cập nhật row làm version đổi. Transaction thứ hai không còn match version cũ và EF Core báo concurrency conflict thay vì silently overwrite.

Đây là optimistic concurrency: phù hợp khi conflict hiếm và tránh giữ lock dài trong thời gian người dùng suy nghĩ. Không nên giữ database transaction từ lúc UI load đến lúc manager click quyết định.

Nếu workflow chỉ cần chuyển `Pending → Approved/Rejected`, conditional update có lợi thế là business precondition xuất hiện trực tiếp ở database statement. Chọn phương án dựa trên complexity của aggregate, audit requirement và khả năng maintain của team.

## Trade-offs

- `rowversion` gắn implementation vào SQL Server; nếu cần PostgreSQL hoặc portability, chọn concurrency token/version strategy phù hợp provider.
- Optimistic concurrency yêu cầu client/API có UX rõ cho conflict thay vì tự retry decision.
- Conditional update đơn giản và hiệu quả nhưng có thể khó hơn nếu state transition cập nhật nhiều aggregate/side effects.
- Pessimistic locking có thể phù hợp trong một số critical section ngắn, nhưng lock lâu làm tăng blocking và không phù hợp với user think-time.

## Cách kiểm thử

1. **Concurrency integration test:** dùng hai `DbContext` độc lập đọc cùng row `Pending`, cho cả hai quyết định rồi điều phối save gần đồng thời; chỉ một decision được success.
2. **Database test:** xác nhận concurrency token thực sự nằm trong generated `UPDATE` và conflict được map thành `409`.
3. **Audit consistency test:** sau race chỉ có audit đại diện cho transition thắng theo contract.
4. **Security/API test:** client không thể giả `managerId`; identity phải đến từ authenticated principal và authorization policy.
5. **Failure-path test:** database failure không được để API/log tuyên bố success khi transaction chưa commit.

## Quan sát trong production

Theo dõi `approval_success_total`, `approval_conflict_total`, conflict rate theo endpoint/version, SQL deadlocks/blocking, request latency, `DbUpdateConcurrencyException`, và correlation giữa request ID, actor identity, decision outcome. Application Insights trace nên cho phép phân biệt expected business conflict với database/transient error. Alert nếu conflict rate tăng đột biến vì có thể là UI duplicate submission hoặc automation bug.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product yêu cầu manager có thể đổi quyết định trong 30 giây, concurrency model và audit model thay đổi thế nào?
2. Khi chuyển từ SQL Server sang PostgreSQL, bạn sẽ thay `rowversion` bằng chiến lược nào và cần test lại assumption gì?
3. Vì sao tự động retry `DbUpdateConcurrencyException` rồi ghi đè state mới nhất có thể phá business invariant?

# Code Review Challenge 2 — React search hiển thị kết quả cũ vì async race và cache key sai

**Chủ đề:** React, TypeScript, REST API integration, async race condition, request cancellation, browser state, cache correctness, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–10 vấn đề quan trọng

## Bối cảnh

Một product-search page dùng React + TypeScript gọi ASP.NET Core API. Khi user gõ từ khóa hoặc đổi market, UI fetch danh sách sản phẩm. Team thêm một module-level cache để giảm request.

Production ghi nhận user gõ nhanh `lap` → `laptop` đôi khi thấy kết quả của `lap` xuất hiện sau cùng. Khi chuyển market từ `US` sang `VN`, đôi lúc UI vẫn hiển thị giá/kết quả của market trước. Browser Network cho thấy nhiều request đồng thời; backend không báo lỗi.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type Product = {
  id: string;
  name: string;
  price: number;
};

const cache = new Map<string, Product[]>();

export function ProductSearch({ market }: { market: string }) {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (!query.trim()) {
      setProducts([]);
      return;
    }

    const key = query.trim().toLowerCase();
    const cached = cache.get(key);
    if (cached) {
      setProducts(cached);
      return;
    }

    setLoading(true);
    setError(null);

    fetch(`/api/products?q=${encodeURIComponent(query)}&market=${market}`)
      .then(r => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json() as Promise<Product[]>;
      })
      .then(data => {
        cache.set(key, data);
        setProducts(data);
      })
      .catch(err => setError(String(err)))
      .finally(() => setLoading(false));
  }, [query, market]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>
        {products.map(p => (
          <li key={p.id}>{p.name} — {p.price}</li>
        ))}
      </ul>
    </section>
  );
}
```

5. Đề xuất implementation/design sửa đúng, không chỉ “debounce mọi thứ”.

## Kết quả code review tham khảo

### High — Response cũ có thể ghi đè kết quả của query mới

**Vấn đề:** Mỗi effect tạo request mới nhưng không cancel hoặc invalidate request trước.

**Tại sao xảy ra:** Network completion order không bảo đảm giống request-start order. Request `lap` có thể chậm hơn `laptop` và gọi `setProducts` sau cùng.

**Ảnh hưởng production:** UI hiển thị kết quả không tương ứng input hiện tại; với dữ liệu thương mại, user có thể thấy sản phẩm/giá không đúng context.

**Cách sửa:** Dùng `AbortController` trong effect cleanup và/hoặc generation/request identity để chỉ request hiện tại được commit state. Cancellation là tối ưu tài nguyên; stale-result guard mới là invariant cần bảo vệ nếu transport cancellation không tuyệt đối.

### High — Cache key bỏ qua `market`

**Vấn đề:** Cache chỉ dùng normalized query.

**Tại sao xảy ra:** Response phụ thuộc cả `query` và `market` nhưng key không phản ánh market.

**Ảnh hưởng production:** Search cùng keyword ở `VN` có thể nhận cached data từ `US`, gây sai catalog/price/availability.

**Cách sửa:** Cache key phải gồm stable dimensions của response, ví dụ `${market}:${normalizedQuery}`; nếu response còn phụ thuộc currency, locale, auth segment hoặc filter khác thì key policy phải phản ánh chúng hoặc không dùng shared module cache kiểu này.

### High — Module-level cache không có freshness/invalidation policy

**Vấn đề:** Cache tồn tại suốt lifetime của JavaScript module và không có TTL/version/invalidation.

**Tại sao xảy ra:** `Map` chỉ lưu dữ liệu, không có semantics về freshness.

**Ảnh hưởng production:** Product/price thay đổi nhưng tab có thể tiếp tục phục vụ dữ liệu cũ vô thời hạn.

**Cách sửa:** Chốt freshness requirement; dùng HTTP caching/server contract hoặc client data-fetching layer có stale time/invalidation rõ. Nếu giữ custom cache, lưu timestamp/version và eviction policy.

### Medium — Request cũ có thể tắt `loading` của request mới

**Vấn đề:** Mọi request đều gọi `setLoading(false)` trong `finally`.

**Tại sao xảy ra:** State boolean không gắn với request identity.

**Ảnh hưởng production:** Spinner biến mất trong khi request mới vẫn đang chạy; UX và telemetry client-side sai.

**Cách sửa:** Chỉ current request được thay đổi loading/error state, hoặc derive pending state từ request identity/count phù hợp.

### Medium — Error cũ có thể xuất hiện cho query mới

**Vấn đề:** `catch` của stale request luôn gọi `setError`.

**Tại sao xảy ra:** Không có stale guard; abort cũng có thể bị hiển thị như lỗi nếu không phân loại `AbortError`.

**Ảnh hưởng production:** User thấy lỗi không thuộc thao tác hiện tại.

**Cách sửa:** Bỏ qua expected abort và chỉ current request được commit error.

### Medium — Empty query không reset đầy đủ request state

**Vấn đề:** Khi query rỗng chỉ clear products; request cũ vẫn có thể hoàn thành sau đó và repopulate list.

**Tại sao xảy ra:** Không cancel request trước và không reset loading/error theo logical state transition.

**Ảnh hưởng production:** User xóa input nhưng kết quả cũ quay lại.

**Cách sửa:** Cleanup/cancel request khi dependency đổi; empty-query branch reset state cần thiết.

### Medium — Không có debounce/admission strategy cho type-ahead

**Vấn đề:** Mỗi keystroke có thể tạo request.

**Tại sao xảy ra:** Effect chạy ngay khi `query` thay đổi.

**Ảnh hưởng production:** Tăng request volume, backend work và network contention; đặc biệt rõ ở latency cao.

**Cách sửa:** Sau khi sửa correctness, cân nhắc debounce ngắn dựa trên UX/latency requirement. Debounce không thay thế cancellation/stale-result protection.

## Phiên bản đề xuất

```tsx
import { useEffect, useRef, useState } from "react";

type Product = {
  id: string;
  name: string;
  price: number;
};

type CacheEntry = {
  data: Product[];
  expiresAt: number;
};

const cache = new Map<string, CacheEntry>();
const CACHE_TTL_MS = 30_000;

export function ProductSearch({ market }: { market: string }) {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const generation = useRef(0);

  useEffect(() => {
    const currentGeneration = ++generation.current;
    const normalized = query.trim().toLowerCase();
    const controller = new AbortController();

    if (!normalized) {
      setProducts([]);
      setLoading(false);
      setError(null);
      return () => controller.abort();
    }

    const key = `${market}:${normalized}`;
    const cached = cache.get(key);

    if (cached && cached.expiresAt > Date.now()) {
      setProducts(cached.data);
      setLoading(false);
      setError(null);
      return () => controller.abort();
    }

    setLoading(true);
    setError(null);

    void (async () => {
      try {
        const response = await fetch(
          `/api/products?q=${encodeURIComponent(normalized)}&market=${encodeURIComponent(market)}`,
          { signal: controller.signal }
        );

        if (!response.ok)
          throw new Error(`HTTP ${response.status}`);

        const data = (await response.json()) as Product[];

        if (generation.current !== currentGeneration)
          return;

        cache.set(key, {
          data,
          expiresAt: Date.now() + CACHE_TTL_MS
        });
        setProducts(data);
      } catch (err) {
        if (controller.signal.aborted)
          return;

        if (generation.current === currentGeneration)
          setError(String(err));
      } finally {
        if (generation.current === currentGeneration)
          setLoading(false);
      }
    })();

    return () => controller.abort();
  }, [query, market]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>
        {products.map(p => (
          <li key={p.id}>{p.name} — {p.price}</li>
        ))}
      </ul>
    </section>
  );
}
```

TTL `30_000` ở đây chỉ là scenario choice để minh họa; production phải chọn freshness policy từ business requirement và server cache semantics, không copy con số này máy móc.

## Giải thích thiết kế sau khi sửa

Effect cleanup abort request cũ khi query/market đổi hoặc component unmount. `generation` bổ sung correctness guard: chỉ generation mới nhất được commit products/error/loading. Điều này làm correctness không phụ thuộc hoàn toàn vào việc underlying transport có dừng ngay lập tức hay không.

Cache key gồm market và normalized query, nhưng đây mới chỉ đúng nếu hai dimension đó thực sự quyết định toàn bộ response. Nếu API response phụ thuộc user segment, locale, currency, filters hoặc authorization, phải đưa các dimension phù hợp vào cache design hoặc bỏ custom cache.

Custom `Map` vẫn có hạn chế về eviction/memory và invalidation. Trong production, nên ưu tiên tận dụng HTTP cache semantics hoặc một data-fetching abstraction đã có trong codebase nếu nó giải quyết request deduplication, stale time và invalidation rõ ràng. Không thêm library chỉ để che một bug lifecycle đơn giản.

## Trade-offs

- Abort request giảm wasted client/network work nhưng server có thể đã bắt đầu xử lý; backend vẫn cần capacity controls riêng.
- Debounce giảm request volume nhưng tăng một chút perceived latency và không tự giải quyết stale response.
- Client cache cải thiện responsiveness nhưng làm freshness/invalidation phức tạp hơn; với search thay đổi nhanh, no-cache hoặc short-lived cache có thể đơn giản hơn.
- Cache key càng nhiều dimensions càng đúng hơn nhưng cardinality/memory cũng tăng.

## Cách kiểm thử

1. **Deterministic component test:** mock hai fetch promises; resolve `laptop` trước rồi `lap` sau và xác nhận UI vẫn hiển thị `laptop`.
2. **Market correctness test:** cùng query ở `US` rồi `VN`; dữ liệu cache không được cross-market.
3. **Cancellation test:** đổi query/unmount và xác nhận stale request không commit products/error/loading.
4. **E2E Playwright test:** route API với artificial latency khác nhau, gõ nhanh nhiều ký tự và xác nhận final UI khớp input hiện tại.
5. **Freshness test:** advance fake clock qua TTL hoặc trigger invalidation contract và xác nhận dữ liệu được refetch.

## Quan sát trong production

Theo dõi frontend request count/search interaction, aborted request count, latency, HTTP error rate, cache hit/miss nếu custom cache đáng để instrument, và correlation ID với ASP.NET Core API. Browser telemetry nên ghi query length/market ở mức không gây lộ dữ liệu nhạy cảm; tránh log raw search text nếu nó có thể chứa PII. Backend theo dõi request rate, cancellation, p95/p99 latency và dependency/database load để biết debounce/cancellation có thực sự giảm work hay chỉ giảm UI updates.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend trả `ETag`/`Cache-Control`, bạn sẽ thay custom `Map` bằng browser/HTTP caching như thế nào?
2. Nếu search API hỗ trợ cursor pagination, request identity và cache key cần thêm những dimension nào?
3. `AbortController` có bảo đảm backend dừng mọi database work ngay khi browser abort không? Bạn sẽ thiết kế cancellation end-to-end ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Check state trong application memory không đủ để bảo vệ business invariant dưới concurrency; precondition quan trọng phải được enforce ở database boundary bằng concurrency token hoặc atomic conditional update.
- Audit trail chỉ đáng tin khi semantic “success” của audit và state transition dùng cùng transaction/concurrency outcome.
- Async UI phải kiểm soát quyền commit state của request; request bắt đầu sau không nhất thiết hoàn thành sau.
- Cache key phải đại diện cho mọi dimension làm thay đổi response và cache phải có freshness/invalidation policy.
- Cancellation, debounce và caching giải quyết các vấn đề khác nhau; không dùng một kỹ thuật như lời giải thay thế cho correctness.

## Mẫu tư duy cần nhớ

- Biến business invariant thành atomic precondition tại nơi dữ liệu được commit.
- Khi có concurrency, dựng timeline của hai actor thay vì chỉ đọc code theo một luồng.
- Với async UI, hỏi “response nào còn quyền cập nhật state?”
- Thiết kế cache key từ response dimensions, rồi mới quyết định TTL/invalidation.
- Test failure/race path bằng orchestration deterministic thay vì hy vọng race xuất hiện ngẫu nhiên.
