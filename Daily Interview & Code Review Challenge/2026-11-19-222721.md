## Bối cảnh

Giờ cao điểm phát sinh 300 product updates/giây. Product có Id, UpdatedAt, Version, IsPublished, Name, Price. Search cần phản ánh thay đổi trong 60 giây. Sau scale-out, một số giá cũ và sản phẩm unpublished vẫn xuất hiện. Không thể dừng website để reindex. Giả định search client có IndexAsync/DeleteAsync trả response chứa IsValidResponse.

## Đoạn code cần review

```csharp
public sealed class ProductIndexer : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ElasticsearchClient _client;
    private DateTime _cursor = DateTime.UtcNow.AddMinutes(-5);

    public ProductIndexer(IServiceScopeFactory scopeFactory,
        ElasticsearchClient client)
    {
        _scopeFactory = scopeFactory;
        _client = client;
    }

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = _scopeFactory.CreateScope();
            var db = scope.ServiceProvider
                .GetRequiredService<CatalogDbContext>();

            var upper = DateTime.UtcNow;
            var products = await db.Products
                .Where(p => p.UpdatedAt > _cursor
                    && p.UpdatedAt <= upper)
                .OrderBy(p => p.UpdatedAt)
                .Take(500)
                .ToListAsync(ct);

            foreach (var p in products)
            {
                if (p.IsPublished)
                    await _client.IndexAsync(
                        new ProductDocument(p.Id, p.Name, p.Price),
                        x => x.Index("products").Id(p.Id), ct);
                else
                    await _client.DeleteAsync<ProductDocument>(
                        p.Id, x => x.Index("products"), ct);
            }

            _cursor = upper;
            await Task.Delay(TimeSpan.FromSeconds(15), ct);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Cursor bỏ qua rows chưa xử lý

**Vấn đề:** Chỉ đọc 500 rows rồi gán cursor bằng upper timestamp.  
**Tại sao xảy ra:** Checkpoint không gắn với dữ liệu đã hoàn thành.  
**Ảnh hưởng production:** Các rows từ 501 trở đi trong khoảng thời gian bị bỏ qua vĩnh viễn.  
**Cách sửa:** Dùng durable outbox cursor hoặc phân trang theo (UpdatedAt, Id) và chỉ advance sau successful delivery; cần giải quyết commit trễ.

### [Critical] — Không kiểm tra response và thứ tự version

**Vấn đề:** Không kiểm tra IsValidResponse, không có version guard.  
**Tại sao xảy ra:** Một HTTP response lỗi có thể không throw; retry/instance khác có thể gửi update cũ sau update mới.  
**Ảnh hưởng production:** Giá cũ, sai publish state, delete bị đảo ngược.  
**Cách sửa:** Kiểm tra item-level success; dùng per-product monotonic version, idempotent update và delete/tombstone strategy phù hợp Elasticsearch version đang dùng.

### [High] — Cursor chỉ nằm trong RAM

**Vấn đề:** Restart khởi tạo lại cursor bằng now minus 5 minutes.  
**Tại sao xảy ra:** Không có persistent checkpoint.  
**Ảnh hưởng production:** Mất thay đổi khi app dừng quá 5 phút.  
**Cách sửa:** Durable outbox với claim/retry status hoặc persisted checkpoint an toàn.

### [High] — Duplicate processing khi scale-out

**Vấn đề:** Mỗi instance chạy cùng job với cursor riêng.  
**Tại sao xảy ra:** BackgroundService không có distributed coordination.  
**Ảnh hưởng production:** Tăng tải và tạo race/out-of-order writes.  
**Cách sửa:** Atomic claim/lease trong PostgreSQL hoặc single consumer coordinator; vẫn cần idempotency.

### [High] — Timestamp polling không phải change log

**Vấn đề:** Hard-delete không được thấy; timestamp có thể trùng, thay đổi không update timestamp, hoặc transaction commit trễ.  
**Tại sao xảy ra:** Scan theo thời gian không atomic với transaction cập nhật.  
**Ảnh hưởng production:** Search diverges dù job báo thành công.  
**Cách sửa:** Transactional Outbox ghi event cùng transaction với Product; hoặc CDC đã kiểm chứng.

### [Medium] — Tracking, ordering và query plan

**Vấn đề:** Query đọc tracked entities, order chỉ theo timestamp và có thể thiếu index.  
**Tại sao xảy ra:** EF Core tracking mặc định; timestamp không unique.  
**Ảnh hưởng production:** Memory và SQL latency tăng; pagination dễ mất/trùng rows.  
**Cách sửa:** AsNoTracking, projection, composite index, stable ordering với Id.

### [Medium] — Sequential requests và thiếu retry policy

**Vấn đề:** Một network round trip mỗi product; exception thoát ExecuteAsync.  
**Tại sao xảy ra:** Không bulk, không bounded retries hoặc poison handling.  
**Ảnh hưởng production:** Lag tăng; transient outage có thể ngừng worker.  
**Cách sửa:** Bulk bounded batches, exponential backoff/jitter, dead-letter/quarantine, cancellation và graceful shutdown.

### [Low] — Thiếu telemetry thành công thực tế

**Vấn đề:** Không ghi success, failure, retry, lag, queue depth.  
**Tại sao xảy ra:** Không có delivery-level observability.  
**Ảnh hưởng production:** Khó phát hiện silent data loss.  
**Cách sửa:** Structured logs, event correlation, alerts và reconciliation samples.

## Phiên bản đề xuất

Code minh họa dùng interfaces **do ứng dụng tự triển khai**, không phải APIs có sẵn. Repository implementation phải claim atomically (ví dụ PostgreSQL SKIP LOCKED với lease), lưu trạng thái bền vững, retry khi lease hết hạn. Product transaction phải ghi outbox event atomically; search writer phải áp dụng monotonic version/tombstone semantics.

```csharp
public sealed record SearchEvent(
    long EventId, Guid ProductId, long Version,
    bool IsPublished, ProductDocument? Document);

public interface IEventStore
{
    Task<IReadOnlyList<SearchEvent>> ClaimAsync(
        int count, TimeSpan lease, CancellationToken ct);
    Task CompleteAsync(long eventId, CancellationToken ct);
    Task RetryAsync(long eventId, string reason,
        CancellationToken ct);
}
public interface IVersionedSearchWriter
{
    Task ApplyIfNewerAsync(SearchEvent item, CancellationToken ct);
}

public sealed class SearchSyncWorker : BackgroundService
{
    private readonly IEventStore _store;
    private readonly IVersionedSearchWriter _search;
    private readonly ILogger<SearchSyncWorker> _log;

    public SearchSyncWorker(IEventStore store,
        IVersionedSearchWriter search,
        ILogger<SearchSyncWorker> log)
        => (_store, _search, _log) = (store, search, log);

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            try
            {
                var batch = await _store.ClaimAsync(
                    100, TimeSpan.FromMinutes(2), ct);
                foreach (var item in batch)
                {
                    ct.ThrowIfCancellationRequested();
                    try
                    {
                        await _search.ApplyIfNewerAsync(item, ct);
                        await _store.CompleteAsync(item.EventId, ct);
                    }
                    catch (OperationCanceledException)
                        when (ct.IsCancellationRequested) { throw; }
                    catch (Exception ex)
                    {
                        _log.LogWarning(ex,
                            "Search event {Id} failed", item.EventId);
                        await _store.RetryAsync(
                            item.EventId, ex.GetType().Name, ct);
                    }
                }
                if (batch.Count == 0)
                    await Task.Delay(TimeSpan.FromSeconds(2), ct);
            }
            catch (OperationCanceledException)
                when (ct.IsCancellationRequested) { break; }
            catch (Exception ex)
            {
                _log.LogError(ex, "Outbox polling failed");
                await Task.Delay(TimeSpan.FromSeconds(5), ct);
            }
        }
    }
}
```

Implementation contract: claim không cho hai workers sở hữu cùng lease; worker phải renew lease nếu batch vượt thời hạn; RetryAsync áp dụng retry budget, delay, quarantine; CompleteAsync chỉ sau khi search xác nhận. Search writer xử lý index và delete với version guard; cần kiểm tra chính xác external versioning và tombstone behavior trên phiên bản Elasticsearch đang triển khai. Nếu outbox event bị replay, kết quả cuối vẫn đúng. Reindex dùng snapshot + replay từ offset an toàn vào index mới, kiểm tra đối chiếu rồi chuyển alias; tránh race ở giai đoạn cutover.

## Giải thích thiết kế sau khi sửa

PostgreSQL là source of truth; outbox đóng khoảng hở giữa DB commit và phát event. At-least-once delivery dễ vận hành hơn cố bảo đảm exactly-once xuyên PostgreSQL/Elasticsearch; version guard giúp duplicate và out-of-order không làm hỏng projection. Không cần thêm Service Bus nếu DB outbox throughput đáp ứng.

## Trade-offs

Outbox thêm storage, write amplification và cleanup. Lease cần tuning/renewal. Bulk indexing nhanh hơn nhưng partial failure phức tạp hơn. Version guard và reindex cutover tăng complexity. Với traffic thấp, timestamp scan có durable cursor, reconciliation và giới hạn rủi ro có thể là lựa chọn chấp nhận được, nhưng không có guarantee như transactional outbox.

## Cách kiểm thử

1. **Integration:** 1.000 updates cùng cửa sổ, không mất rows.
2. **Concurrency:** Ba workers claim cùng lúc và replay idempotent.
3. **Failure-path:** Timeout sau khi search đã apply; retry không rollback version.
4. **Ordering:** Update version 12 đến trước version 11, delete version 13 vẫn thắng.
5. **Recovery:** Kill worker giữa batch, lease expiry và reindex reconciliation.

## Quan sát trong production

Application Insights: pending event count, oldest event age, retry/DLQ count, item-level success/failure, Elasticsearch rejected writes, index latency p95, PostgreSQL lock waits, execution plan, trace theo EventId. Alert khi lag >60 giây liên tục và khi reconciliation mismatch tăng. Không log payload chứa PII.

2. Khi reindex 2 triệu products, làm sao replay thay đổi phát sinh trong lúc build index?
3. Nếu hard-delete product, làm sao ngăn old event resurrect document?

```typescript
type Principal = { sub: string; tenantId: string; roles: string[] };
type Context = { auth: Principal; log: (msg: string) => void };
type RequestDoc = {
  id: string; tenantId: string; status: string;
  createdAt: string; requesterEmail: string; description: string;
};

export function handlers(container: any) {
  async function list(req: Request, ctx: Context): Promise<Response> {
    const url = new URL(req.url);
    const tenant = url.searchParams.get("tenantId")
      || ctx.auth.tenantId;
    const status = url.searchParams.get("status") || "Pending";
    const size = Number(url.searchParams.get("limit") || 1000);
    const sql = "SELECT * FROM c WHERE c.tenantId = '" +
      tenant + "' AND c.status = '" + status +
      "' ORDER BY c.createdAt DESC";
    const { resources } = await container.items
      .query<RequestDoc>({ query: sql }, { maxItemCount: size })
      .fetchAll();

    ctx.log("Fetched " + resources.length + " requests");
    return Response.json(resources);
  }

  async function approve(req: Request, ctx: Context): Promise<Response> {
    const body = await req.json() as {
      id: string; tenantId: string
    };
    const { resource } = await container
      .item(body.id, body.tenantId).read<RequestDoc>();
    if (!resource)
      return new Response(null, { status: 404 });

    resource.status = "Approved";
    await container.item(resource.id, resource.tenantId)
      .replace(resource);
    return Response.json({ id: resource.id, status: resource.status });
  }

  return { list, approve };
}
```

## Phiên bản đề xuất

Code sau dùng Cosmos adapter **do ứng dụng định nghĩa**, không phải API SDK có sẵn. Adapter chịu trách nhiệm parameterized query, partition-scoped fetchNext, ETag IfMatch, request charge và error mapping. Middleware phải verify token signature, issuer, audience trước khi xây Principal.

```typescript
type Principal = {
  sub: string; tenantId: string; roles: string[];
};
type Summary = { id: string; status: string; createdAt: string };
type RecordDoc = Summary & {
  tenantId: string; _etag: string;
};
type Page = { items: Summary[]; next?: string; ru: number };

interface RequestStore {
  page(input: {
    tenantId: string;
    status: "Pending" | "Approved";
    limit: number;
    cursor?: string;
  }): Promise<Page>;
  get(id: string, tenantId: string): Promise<RecordDoc | null>;
  replaceIfMatch(
    record: RecordDoc, etag: string
  ): Promise<"ok" | "conflict">;
}

export function safeHandlers(store: RequestStore) {
  async function list(req: Request, auth: Principal): Promise<Response> {
    const url = new URL(req.url);
    const status = url.searchParams.get("status") ?? "Pending";
    if (status !== "Pending" && status !== "Approved")
      return Response.json({ error: "Invalid status" }, { status: 400 });
    const limit = Number(url.searchParams.get("limit") ?? 25);
    if (!Number.isInteger(limit) || limit < 1 || limit > 100)
      return Response.json({ error: "Invalid limit" }, { status: 400 });

    const page = await store.page({
      tenantId: auth.tenantId,
      status,
      limit,
      cursor: url.searchParams.get("cursor") ?? undefined
    });
    return Response.json({
      items: page.items, nextCursor: page.next
    });
  }

  async function approve(req: Request, auth: Principal): Promise<Response> {
    if (!auth.roles.includes("RequestApprover"))
      return new Response(null, { status: 403 });
    const body = await req.json() as { id?: unknown };
    if (typeof body.id !== "string" || !body.id.trim())
      return Response.json({ error: "Invalid id" }, { status: 400 });

    const record = await store.get(body.id, auth.tenantId);
    if (!record) return new Response(null, { status: 404 });
    if (record.status !== "Pending")
      return new Response(null, { status: 409 });

    const result = await store.replaceIfMatch(
      { ...record, status: "Approved" }, record._etag);
    if (result === "conflict")
      return new Response(null, { status: 409 });
    return Response.json({ id: record.id, status: "Approved" });
  }
  return { list, approve };
}
```

Adapter phải bind parameters thay vì string interpolation, truyền tenant partition key, dùng continuation token không thể tráo giữa tenants/filters (ký hoặc lưu server-side), ETag conditional write và giới hạn dữ liệu projection. Nếu workflow có audit, cần ghi actor/time trong cùng transaction boundary khi khả thi. Với multi-tenant users, xác minh membership cho tenant được chọn thay vì tin claim không được đối chiếu.
