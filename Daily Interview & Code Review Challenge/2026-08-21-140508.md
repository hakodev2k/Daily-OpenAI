# Code Review Challenge 1 — Hangfire job gửi notification bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 7 vấn đề

## Bối cảnh

Một Hangfire job gửi reminder trước giờ bắt đầu event. Hệ thống chạy nhiều worker để tăng throughput. Production thỉnh thoảng ghi nhận một user nhận cùng notification 2–3 lần, đặc biệt sau khi worker restart hoặc external push provider timeout. Database là SQL Server qua EF Core. Yêu cầu nghiệp vụ là mỗi reminder logic chỉ được gửi một lần cho mỗi booking, nhưng retry khi lỗi tạm thời vẫn phải an toàn.

## Đoạn code cần review

```csharp
public sealed class EventReminderJob
{
    private readonly AppDbContext _db;
    private readonly IPushNotificationService _push;
    private readonly ILogger<EventReminderJob> _logger;

    public EventReminderJob(
        AppDbContext db,
        IPushNotificationService push,
        ILogger<EventReminderJob> logger)
    {
        _db = db;
        _push = push;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid bookingId)
    {
        var booking = await _db.UserEventBookings
            .Include(x => x.User)
            .FirstOrDefaultAsync(x => x.Id == bookingId);

        if (booking == null || booking.IsReminderSent)
            return;

        try
        {
            await _push.SendAsync(
                booking.User.DeviceToken,
                "Upcoming event",
                $"Your event starts at {booking.StartTimeUtc}");

            booking.IsReminderSent = true;
            booking.ReminderSentAtUtc = DateTime.UtcNow;

            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Failed to send reminder for booking {BookingId} to {DeviceToken}",
                booking.Id,
                booking.User.DeviceToken);

            throw;
        }
    }
}
```

- Transaction database có thể làm cho external HTTP call trở thành exactly-once không?
- Device token có nên xuất hiện trong application log không?

### Gợi ý 2

## Kết quả code review tham khảo

### 1. Check-then-act race condition

- **Problem:** Nhiều worker có thể cùng đọc `IsReminderSent == false` rồi cùng gửi.
- **Why:** Read và update không tạo một atomic claim cho booking.
- **Production impact:** Duplicate notification dưới concurrency.
- **Severity:** Critical
- **Recommended fix:** Claim công việc atomically bằng conditional update/state transition hoặc thiết kế outbox với unique business key.

### 2. Không thể bảo đảm exactly-once giữa database và push provider

- **Problem:** Provider có thể nhận notification nhưng process crash trước `SaveChangesAsync`.
- **Why:** External side effect và database transaction là hai resource độc lập.
- **Production impact:** Hangfire retry và gửi lại notification.
- **Severity:** Critical
- **Recommended fix:** Dùng provider idempotency key nếu được hỗ trợ; nếu không, thiết kế delivery semantics rõ ràng và durable outbox/deduplication.

### 3. State chỉ được ghi sau external call

- **Problem:** Không có durable record thể hiện attempt đang được xử lý.
- **Why:** Toàn bộ trạng thái trước send chỉ tồn tại trong worker.
- **Production impact:** Crash/restart làm mất trạng thái attempt.
- **Severity:** High
- **Recommended fix:** Persist notification/outbox record trước khi dispatch; có trạng thái Pending/Processing/Sent/Failed và business key duy nhất.

### 4. Không có unique invariant ở database

- **Problem:** Application logic là hàng rào duy nhất chống duplicate.
- **Why:** Không có unique key như `(BookingId, NotificationType)`.
- **Production impact:** Bug hoặc concurrent path khác có thể tạo nhiều delivery record.
- **Severity:** High
- **Recommended fix:** Enforce invariant bằng unique constraint/index.

### 5. Catch mọi exception rồi retry không phân loại lỗi

- **Problem:** Permanent failure và transient failure đều bị xử lý giống nhau.
- **Why:** `catch (Exception)` chỉ log rồi throw.
- **Production impact:** Retry vô ích, tăng tải provider và noise.
- **Severity:** Medium
- **Recommended fix:** Phân loại transient/permanent failure, giới hạn retry và có dead-letter/manual recovery path.

### 6. Sensitive device token được log trực tiếp

- **Problem:** Device token bị ghi vào log.
- **Why:** Structured logging chứa raw token.
- **Production impact:** Tăng phạm vi dữ liệu nhạy cảm trong observability systems.
- **Severity:** Medium
- **Recommended fix:** Không log token hoặc chỉ log masked/hash identifier phù hợp.

### 7. Không truyền cancellation token

- **Problem:** EF query, push request và SaveChanges không nhận cancellation.
- **Why:** Method không nhận `CancellationToken`.
- **Production impact:** Shutdown/deployment có thể kéo dài; request đang hủy vẫn tiếp tục sử dụng resource.
- **Severity:** Low
- **Recommended fix:** Propagate cancellation khi execution model cho phép và thiết kế retry an toàn.

## Phiên bản code đề xuất

Một hướng thực tế là tách “schedule reminder” khỏi “send reminder” bằng durable outbox. Unique constraint trên `(BookingId, Type)` bảo vệ invariant.

```csharp
public sealed class EventReminderJob
{
    private readonly AppDbContext _db;

    public EventReminderJob(AppDbContext db) => _db = db;

    public async Task ExecuteAsync(Guid bookingId, CancellationToken ct)
    {
        var exists = await _db.UserEventBookings
            .AsNoTracking()
            .AnyAsync(x => x.Id == bookingId, ct);

        if (!exists)
            return;

        _db.NotificationOutbox.Add(new NotificationOutbox
        {
            Id = Guid.NewGuid(),
            BookingId = bookingId,
            Type = "EventReminder",
            Status = OutboxStatus.Pending,
            CreatedAtUtc = DateTime.UtcNow
        });

        try
        {
            await _db.SaveChangesAsync(ct);
        }
        catch (DbUpdateException ex) when (IsUniqueConstraintViolation(ex))
        {
            return;
        }
    }

    private static bool IsUniqueConstraintViolation(DbUpdateException ex)
    {
        // Provider-specific inspection should be implemented here.
        return false;
    }
}

public sealed class NotificationDispatcher
{
    private readonly AppDbContext _db;
    private readonly IPushNotificationService _push;

    public NotificationDispatcher(AppDbContext db, IPushNotificationService push)
    {
        _db = db;
        _push = push;
    }

    public async Task DispatchAsync(Guid outboxId, CancellationToken ct)
    {
        var item = await _db.NotificationOutbox
            .SingleAsync(x => x.Id == outboxId, ct);

        if (item.Status == OutboxStatus.Sent)
            return;

        var idempotencyKey = $"event-reminder:{item.BookingId}";

        await _push.SendAsync(item.BookingId, idempotencyKey, ct);

        item.Status = OutboxStatus.Sent;
        item.SentAtUtc = DateTime.UtcNow;
        await _db.SaveChangesAsync(ct);
    }
}
```

**Giả định:** `IPushNotificationService`/provider có cơ chế nhận idempotency key. Nếu provider không hỗ trợ deduplication, outbox vẫn giảm đáng kể duplicate nhưng không thể tự biến external side effect thành exactly-once tuyệt đối.

## Trade-offs

Outbox thêm bảng, dispatcher và cleanup/monitoring nhưng đổi lại có durable state, khả năng recovery và audit tốt hơn. Atomic conditional update đơn giản hơn nếu chỉ cần ngăn hai worker gửi đồng thời, nhưng vẫn không giải quyết hoàn toàn trường hợp provider đã nhận request rồi worker crash trước khi database ghi `Sent`. Distributed lock có thể giảm concurrency nhưng không thay thế idempotency.

## Cách kiểm thử

1. **Concurrency test:** chạy nhiều execution cùng `bookingId`; chỉ một outbox business key được tạo.
2. **Failure-path test:** provider thành công rồi mô phỏng crash trước DB update; retry phải tuân theo idempotency contract.
3. **Database integration test:** xác nhận unique constraint thực sự chặn duplicate.
4. **Retry test:** transient timeout được retry; permanent failure không retry vô hạn.
5. **Security test:** xác nhận logs không chứa raw device token.

## Quan sát trong production

Theo dõi `notification_attempt_total`, `notification_duplicate_suppressed_total`, retry count, outbox age, Pending/Failed backlog và provider latency/error rate. Trace nên liên kết booking ID, outbox ID, Hangfire job ID và external request correlation ID, nhưng không chứa device token. Alert khi oldest pending age hoặc failure ratio vượt ngưỡng vận hành đã định.

## Câu hỏi phỏng vấn mở rộng

1. Nếu push provider không hỗ trợ idempotency key, bạn sẽ định nghĩa delivery guarantee thế nào?
2. Tại sao distributed lock không giải quyết được crash sau external side effect?
3. Nếu throughput tăng lên hàng triệu notification/ngày, bạn thay đổi dispatcher và data retention ra sao?

# Code Review Challenge 2 — API tìm outlet: authorization và query performance

**Chủ đề:** Authorization, EF Core query execution, input validation, pagination, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ màn hình bản đồ outlet. Người dùng thuộc một tenant chỉ được xem outlet của tenant đó. QA thấy request với viewport lớn đôi khi mất nhiều giây và memory của container tăng mạnh. Security review cũng nghi ngờ endpoint có thể trả dữ liệu của tenant khác. Dataset đã lên đến hàng triệu outlet.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/outlets")]
public sealed class OutletController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<OutletController> _logger;

    public OutletController(AppDbContext db, ILogger<OutletController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string tenantId,
        double minLat,
        double minLng,
        double maxLat,
        double maxLng,
        string? keyword)
    {
        var outlets = await _db.Outlets
            .Include(x => x.Manager)
            .Include(x => x.Visits)
            .ToListAsync();

        var result = outlets
            .Where(x => x.TenantId == tenantId)
            .Where(x => x.Latitude >= minLat && x.Latitude <= maxLat)
            .Where(x => x.Longitude >= minLng && x.Longitude <= maxLng)
            .Where(x => string.IsNullOrEmpty(keyword) ||
                        x.Name.ToLower().Contains(keyword.ToLower()))
            .OrderBy(x => x.Name)
            .Select(x => new
            {
                x.Id,
                x.Name,
                x.Latitude,
                x.Longitude,
                ManagerEmail = x.Manager.Email,
                VisitCount = x.Visits.Count
            })
            .ToList();

        _logger.LogInformation(
            "Outlet search tenant={TenantId}, keyword={Keyword}, results={Count}",
            tenantId, keyword, result.Count);

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant isolation / IDOR-style authorization risk

- **Problem:** Client tự truyền `tenantId` và server dùng trực tiếp để quyết định dữ liệu được xem.
- **Why:** Không có kiểm tra tenant từ authenticated identity hoặc authorization policy.
- **Production impact:** User có thể thử tenant ID khác để đọc dữ liệu trái phép.
- **Severity:** Critical
- **Recommended fix:** Resolve tenant từ trusted claims/server-side membership và enforce authorization trước query.

### 2. Load toàn bộ bảng và navigation trước khi filter

- **Problem:** `ToListAsync()` chạy trước tất cả `Where`.
- **Why:** Sau materialization, filter chạy trong process thay vì database.
- **Production impact:** Memory/CPU/network/database load tăng theo toàn bộ dataset; latency rất cao.
- **Severity:** Critical
- **Recommended fix:** Giữ query là `IQueryable` đến projection/materialization cuối cùng.

### 3. `Include(Visits)` gây tải dữ liệu không cần thiết

- **Problem:** Toàn bộ visits được load chỉ để lấy `Count`.
- **Why:** Navigation được materialize trước projection.
- **Production impact:** Data amplification lớn và allocation cao.
- **Severity:** High
- **Recommended fix:** Projection trực tiếp `VisitCount = x.Visits.Count()` để database aggregate.

### 4. Không giới hạn result set

- **Problem:** Viewport lớn có thể trả lượng record rất lớn.
- **Why:** Không pagination, cap hoặc clustering contract.
- **Production impact:** Response lớn, timeout và memory pressure ở API/client.
- **Severity:** High
- **Recommended fix:** Validate viewport, áp dụng bounded page/result limit hoặc map clustering tùy UX.

### 5. Không validate coordinate ranges/order

- **Problem:** API chấp nhận latitude/longitude ngoài range hoặc min > max.
- **Why:** Không có request validation.
- **Production impact:** Query sai, expensive requests hoặc behavior khó dự đoán.
- **Severity:** Medium
- **Recommended fix:** Validate latitude [-90,90], longitude [-180,180], ordering và xử lý rõ trường hợp crossing antimeridian nếu sản phẩm hỗ trợ.

### 6. String normalization chạy trong memory và allocation không cần thiết

- **Problem:** `ToLower()` được gọi trên nhiều record/string.
- **Why:** Filtering diễn ra sau `ToListAsync`.
- **Production impact:** CPU/allocation tăng; semantics case sensitivity không rõ.
- **Severity:** Medium
- **Recommended fix:** Để database xử lý search với collation/operator phù hợp DB và requirement; cân nhắc search index nếu use case lớn.

### 7. Trả `ManagerEmail` mà chưa chứng minh business requirement

- **Problem:** Endpoint map có thể expose PII không cần thiết.
- **Why:** Projection trả email manager mặc định.
- **Production impact:** Tăng data exposure và privacy risk.
- **Severity:** Medium
- **Recommended fix:** Data minimization; chỉ trả field thật sự cần và authorization riêng nếu cần email.

### 8. Log raw keyword có thể chứa dữ liệu không mong muốn

- **Problem:** User-controlled search text đi vào logs.
- **Why:** Structured log lưu raw input.
- **Production impact:** Log pollution và có thể lưu dữ liệu nhạy cảm người dùng nhập.
- **Severity:** Low
- **Recommended fix:** Log metadata cần thiết; truncate/sanitize hoặc tránh raw search terms tùy policy.

## Phiên bản code đề xuất

```csharp
public sealed record OutletSearchRequest(
    double MinLat,
    double MinLng,
    double MaxLat,
    double MaxLng,
    string? Keyword,
    int Limit = 200);

[Authorize]
[HttpGet("search")]
public async Task<IActionResult> Search(
    [FromQuery] OutletSearchRequest request,
    CancellationToken ct)
{
    if (request.MinLat < -90 || request.MaxLat > 90 ||
        request.MinLng < -180 || request.MaxLng > 180 ||
        request.MinLat > request.MaxLat ||
        request.MinLng > request.MaxLng)
    {
        return BadRequest("Invalid bounding box.");
    }

    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    var limit = Math.Clamp(request.Limit, 1, 500);

    IQueryable<Outlet> query = _db.Outlets
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId)
        .Where(x => x.Latitude >= request.MinLat && x.Latitude <= request.MaxLat)
        .Where(x => x.Longitude >= request.MinLng && x.Longitude <= request.MaxLng);

    if (!string.IsNullOrWhiteSpace(request.Keyword))
    {
        var keyword = request.Keyword.Trim();
        query = query.Where(x => x.Name.Contains(keyword));
    }

    var result = await query
        .OrderBy(x => x.Name)
        .ThenBy(x => x.Id)
        .Take(limit)
        .Select(x => new
        {
            x.Id,
            x.Name,
            x.Latitude,
            x.Longitude,
            VisitCount = x.Visits.Count()
        })
        .ToListAsync(ct);

    _logger.LogInformation(
        "Outlet search completed for tenant {TenantId}; count={Count}; limit={Limit}",
        tenantId, result.Count, limit);

    return Ok(result);
}
```

**Lưu ý:** `Contains` có semantics/performance phụ thuộc database provider, collation và index strategy. Với PostgreSQL có thể cân nhắc provider-specific operator/index; với SQL Server cần xem collation và execution plan. Với map search lớn, spatial type + spatial index hoặc một chiến lược bounding-box/index phù hợp có thể tốt hơn scalar latitude/longitude, nhưng phải benchmark trên dữ liệu và query shape thực tế thay vì mặc định kết luận.

## Trade-offs

`AsNoTracking` phù hợp read-only query và giảm tracking overhead, nhưng không dùng nếu entity cần được sửa trong cùng unit of work. Hard cap bảo vệ hệ thống nhưng UX có thể cần clustering hoặc pagination. Projection làm SQL phức tạp hơn một chút nhưng tránh materialize navigation. Spatial index đáng cân nhắc khi workload thực sự là geographic search; migration phức tạp hơn scalar columns và cần benchmark execution plan trên từng database engine.

## Cách kiểm thử

1. **Authorization test:** user tenant A cố truy vấn dữ liệu tenant B nhưng không thể thay đổi tenant scope bằng input.
2. **Integration test:** kiểm tra generated SQL/filter được thực thi server-side và không load toàn bộ bảng.
3. **Load test:** viewport lớn và concurrent users vẫn giữ latency/memory trong SLO đã định.
4. **Boundary test:** invalid lat/lng, reversed bounds và result limit.
5. **Data exposure test:** response không chứa manager email hoặc field không được phép.

## Quan sát trong production

Theo dõi endpoint p50/p95/p99 latency, rows returned, DB duration, query timeout, allocation/GC, response size và rejected invalid requests. Dùng distributed trace từ HTTP request tới EF Core/database span. Với slow query, xem actual execution plan/query statistics và index usage thay vì chỉ dựa vào application timing. Alert theo SLO/error ratio thay vì một threshold latency đơn lẻ.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry và concurrency khiến “check rồi làm” không đủ để bảo vệ side effect; idempotency phải là một phần của business design.
- Database transaction không thể tự làm external HTTP side effect trở thành exactly-once.
- `ToListAsync()` là materialization boundary quan trọng trong EF Core; filter/projection nên được đẩy xuống database khi phù hợp.
- Multi-tenant authorization phải dựa trên trusted identity/membership, không tin tenant identifier do client tự khai báo.
- Performance optimization cần dựa trên generated SQL, execution plan, metrics và benchmark workload thực tế.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency.
- Enforce business invariant ở lớp bền vững nhất có thể, thường gồm database constraint.
- Giữ query server-side cho đến khi thực sự cần materialize.
- Authorize từ trusted context trước khi query dữ liệu.
- Measure before optimizing; observability là một phần của design.
