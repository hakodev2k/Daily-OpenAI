# Câu 1 — `await foreach` đã có `CancellationToken`, nhưng API vẫn không dừng khi client disconnect: cancellation của `IAsyncEnumerable<T>` thực sự chảy qua đâu?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** C#/.NET 8, `IAsyncEnumerable<T>`, async iterators, cancellation propagation, compiler-generated state machine, ASP.NET Core, EF Core streaming, resource lifetime, production diagnostics

## Bối cảnh

Một ASP.NET Core API stream hàng trăm nghìn audit records cho internal analytics tool. Team chuyển từ `ToListAsync()` sang `IAsyncEnumerable<T>` để giảm memory usage:

```csharp
[HttpGet("api/audit/export")]
public async Task Export(CancellationToken ct)
{
    Response.ContentType = "application/x-ndjson";

    await foreach (var row in _service.StreamAuditRowsAsync(
        User.GetTenantId(),
        DateTimeOffset.UtcNow.AddDays(-30)))
    {
        await JsonSerializer.SerializeAsync(Response.Body, row, cancellationToken: ct);
        await Response.Body.WriteAsync("\n"u8.ToArray(), ct);
    }
}

public sealed class AuditService
{
    private readonly AppDbContext _db;

    public AuditService(AppDbContext db) => _db = db;

    public async IAsyncEnumerable<AuditRowDto> StreamAuditRowsAsync(
        int tenantId,
        DateTimeOffset from)
    {
        await foreach (var row in _db.AuditRows
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.CreatedAt >= from)
            .OrderBy(x => x.Id)
            .Select(x => new AuditRowDto(x.Id, x.CreatedAt, x.Action))
            .AsAsyncEnumerable())
        {
            yield return row;
        }
    }
}
```

Production có các triệu chứng:

- user đóng tab sau vài giây nhưng SQL query vẫn tiếp tục chạy khá lâu;
- connection pool có lúc gần cạn khi nhiều export bị abandon;
- request telemetry đã kết thúc hoặc báo client disconnect, nhưng SQL dependency vẫn xuất hiện sau đó;
- developer A nói controller đã có `CancellationToken ct` nên cancellation chắc chắn tự chảy xuống iterator;
- developer B thêm `.WithCancellation(ct)` ở `await foreach` trong controller nhưng vẫn muốn hiểu nó thực sự thay đổi điều gì;
- developer C đề xuất thêm một parameter `CancellationToken` vào iterator nhưng không biết có cần `[EnumeratorCancellation]` không;
- team cũng chưa rõ cancellation khi enumerate khác gì cancellation của method call bình thường.

## Câu hỏi chính

Hãy giải thích cơ chế cancellation của `IAsyncEnumerable<T>`/async iterator trong C#: token nằm ở thời điểm tạo enumerable hay thời điểm tạo enumerator, `.WithCancellation(ct)` làm gì, `[EnumeratorCancellation]` có vai trò gì, vì sao đoạn code trên có thể tiếp tục đọc SQL sau khi client disconnect, và bạn sẽ sửa cũng như kiểm chứng behavior đó trong production như thế nào.

## Câu hỏi làm rõ nên cân nhắc

1. `CancellationToken ct` của controller có phải `HttpContext.RequestAborted` trong hosting path hiện tại không?
2. EF Core provider/SQL client version hiện tại có honor cancellation cho async query ở mức nào và query có phần nào khó interrupt không?
3. Export có đi qua proxy nào buffer response, khiến application nhận disconnect chậm hơn không?
4. Một request export giữ `DbContext`/connection trong bao lâu và concurrent export limit hiện là bao nhiêu?
5. Business muốn cancellation là best-effort hay bắt buộc phải giải phóng database resources trong một SLO cụ thể?

## Gợi ý tư duy

### Gợi ý 1

`IAsyncEnumerable<T>` tách **tạo sequence** khỏi **enumerate sequence**. Cancellation dành cho async iteration được truyền vào `GetAsyncEnumerator(CancellationToken)`.

### Gợi ý 2

`.WithCancellation(ct)` không magically sửa mọi iterator. Nó truyền token ở enumeration boundary; iterator phải được viết theo cách nhận/merge token đó và downstream operation cũng phải honor token.

### Gợi ý 3

Với async iterator có parameter `CancellationToken`, `[EnumeratorCancellation]` cho compiler biết parameter nào phải nhận token từ `GetAsyncEnumerator`. Sau đó chính code bên trong iterator vẫn phải truyền token xuống EF/HTTP/file APIs.

## Cấu trúc trả lời đề xuất

1. Giải thích model `IAsyncEnumerable<T>` → `GetAsyncEnumerator(token)` → `MoveNextAsync()`.
2. Phân tích token trong controller hiện tại có và chưa đi tới đâu.
3. Giải thích `.WithCancellation` và `[EnumeratorCancellation]`.
4. Chỉ ra resource lifetime của EF query/DbContext/DB connection khi stream.
5. Đề xuất implementation đúng.
6. Phân biệt cancellation request, timeout và host shutdown.
7. Nêu tests/telemetry để chứng minh connection được release sớm.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết `IAsyncEnumerable<T>` chỉ thực sự thực thi khi enumerate.
- Biết cancellation token cho enumeration đi qua `GetAsyncEnumerator(CancellationToken)`.
- Không giả định controller token tự động chảy qua mọi async iterator.
- Hiểu `.WithCancellation(ct)` truyền token vào enumeration.
- Hiểu `[EnumeratorCancellation]` dùng để bind/merge token của caller vào parameter cancellation của async iterator.
- Truyền token tiếp xuống EF Core async enumeration/downstream I/O.
- Dispose enumerator/resource đúng cách khi loop kết thúc/cancel.

### Điểm cộng

- Phân biệt method parameter token với enumerator token.
- Nêu rằng cancellation là cooperative, không phải forced thread abort.
- Theo dõi active exports, cancelled exports, duration sau disconnect và DB connection usage.
- Có concurrency/admission control vì streaming lâu vẫn giữ expensive resources dù memory thấp.

### Senior+

- Giải thích compiler warning khi async iterator có `CancellationToken` nhưng thiếu `[EnumeratorCancellation]` trong tình huống phù hợp.
- Biết không nên chỉ fix controller mà bỏ qua provider semantics/proxy disconnect detection.
- Thiết kế integration test disconnect thật sự thay vì chỉ unit test token đã cancel.
- Nhận ra streaming giảm allocation nhưng có thể tăng thời gian giữ connection, nên cần trade-off batching/keyset paging nếu export kéo dài.

## Hướng giải quyết tham khảo

Mental model quan trọng là một async iterator không chạy toàn bộ tại lúc gọi method. Lời gọi `StreamAuditRowsAsync(...)` tạo ra một object thực hiện `IAsyncEnumerable<AuditRowDto>`. Khi `await foreach` bắt đầu, compiler lấy async enumerator và gọi `MoveNextAsync()` nhiều lần. Cancellation cho cơ chế enumerate được truyền vào `GetAsyncEnumerator(CancellationToken)`.

Trong controller hiện tại, `ct` chỉ được truyền vào `SerializeAsync` và `WriteAsync`. Nó chưa xuất hiện ở `StreamAuditRowsAsync(...)`, và loop cũng không dùng `.WithCancellation(ct)`. Vì vậy response write có thể bị cancel sau disconnect, nhưng iterator đang đọc database không có token tương ứng để yêu cầu dừng query.

Một implementation rõ ràng hơn:

```csharp
public async IAsyncEnumerable<AuditRowDto> StreamAuditRowsAsync(
    int tenantId,
    DateTimeOffset from,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var row in _db.AuditRows
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId && x.CreatedAt >= from)
        .OrderBy(x => x.Id)
        .Select(x => new AuditRowDto(x.Id, x.CreatedAt, x.Action))
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        ct.ThrowIfCancellationRequested();
        yield return row;
    }
}
```

Controller có thể gọi:

```csharp
await foreach (var row in _service
    .StreamAuditRowsAsync(tenantId, from, ct)
    .WithCancellation(ct))
{
    await JsonSerializer.SerializeAsync(Response.Body, row, cancellationToken: ct);
    await Response.Body.WriteAsync("\n"u8.ToArray(), ct);
}
```

Không nhất thiết phải truyền cùng token bằng cả argument lẫn `.WithCancellation` nếu contract đã được thiết kế rõ; điều quan trọng là hiểu token nào là token tạo iterator và token nào đến từ enumeration. `[EnumeratorCancellation]` cho compiler biết parameter cần nhận token của `GetAsyncEnumerator` và xử lý kết hợp với token đã truyền khi tạo enumerable theo semantics của async iterator. Nếu không có annotation đúng, caller dùng `.WithCancellation(ct)` có thể không ảnh hưởng parameter mà developer tưởng đang dùng.

Sau đó token phải tiếp tục chảy tới downstream operation. EF Core async enumeration cuối cùng dựa trên database provider/ADO.NET support. Cancellation trong .NET là cooperative: request cancel không có nghĩa SQL Server lập tức dừng trong zero milliseconds. Vì vậy cần đo thời gian từ `RequestAborted` đến query/connection release thay vì chỉ kiểm tra code có token.

Một vấn đề khác là resource lifetime. Streaming tránh `ToListAsync()` và giảm peak memory, nhưng một export 5 phút có thể giữ DbContext, data reader và database connection lâu hơn. Nếu có 100 exports đồng thời, connection pool vẫn có thể cạn dù allocation rất thấp. Có thể cần giới hạn concurrent exports, chunk bằng keyset paging, hoặc chuyển very-large export thành background generation nếu business workflow phù hợp.

Tôi sẽ kiểm chứng bằng integration test chạy API qua real HTTP server, bắt đầu đọc một phần response rồi đóng client socket/cancel request. Sau đó xác minh application ghi nhận cancellation, database command bị cancel/complete sớm, active connection trở về baseline và không còn dependency chạy nhiều chục giây sau request. Production dashboard nên có active exports, cancellation count, p95 time-to-stop after abort, export duration, DB command duration và connection-pool saturation.

## Mẫu trả lời trong phỏng vấn

“Điểm tôi kiểm tra đầu tiên là token của controller hiện chỉ dùng khi serialize/write response, chưa chắc đã đi vào async iterator. `IAsyncEnumerable<T>` khác một async method trả `Task<T>` ở chỗ execution diễn ra từng bước qua async enumerator. Token của enumeration được đưa vào `GetAsyncEnumerator`.

Tôi sẽ làm iterator nhận `CancellationToken` có `[EnumeratorCancellation]`, và truyền token đó xuống EF enumeration. Ở caller, `.WithCancellation(ct)` thể hiện rõ token dùng cho enumeration. Annotation giúp compiler nối token của enumerator với parameter cancellation của iterator đúng semantics.

Nhưng tôi không dừng ở việc code compile. Cancellation là cooperative, provider và SQL operation phải honor nó. Tôi sẽ integration-test bằng cách thật sự disconnect client giữa stream, rồi đo thời gian tới khi DB command và connection được release.

Ngoài ra streaming đổi trade-off: memory tốt hơn nhưng connection có thể bị giữ lâu hơn. Vì vậy nếu export rất dài tôi vẫn cần concurrency limit hoặc chunking; nếu requirement cho phép thì large export có thể chuyển thành durable offline job. Mục tiêu là request abort làm work vô ích dừng sớm và không làm cạn database pool.”

## Câu hỏi đào sâu

1. Nếu `.WithCancellation(ct)` đã được dùng ở controller nhưng iterator bên trong lại gọi một API không nhận token, behavior thực tế sẽ như thế nào?
2. Nếu streaming giữ SQL connection 3 phút còn keyset paging mở connection nhiều lần nhưng mỗi lần ngắn, bạn chọn phương án nào và dựa trên metric nào?
3. Nếu reverse proxy chỉ phát hiện client disconnect chậm 30 giây, bạn bổ sung timeout/budget ở application layer ra sao?

## Lỗi trả lời thường gặp

- Nói “có `CancellationToken` trong controller là tự động propagate”.
- Xem cancellation như `Thread.Abort` tức thời.
- Thêm `.WithCancellation(ct)` nhưng không kiểm tra iterator/downstream có sử dụng token.
- Tối ưu streaming nhưng bỏ qua thời gian giữ DB connection.
- Chỉ unit test `OperationCanceledException` mà không test disconnect/resource cleanup thật.

## Thang điểm 0–10

- **0–2:** Biết cancellation chung chung nhưng không hiểu async enumeration boundary.
- **3–4:** Biết `.WithCancellation` nhưng giải thích mơ hồ `[EnumeratorCancellation]` và propagation.
- **5–6:** Giải thích đúng enumerator token, sửa iterator hợp lý và nhắc cooperative cancellation.
- **7–8:** Kết nối runtime mechanism với EF/resource lifetime, integration test và production telemetry.
- **9–10:** Phân tích đầy đủ token semantics, provider/proxy behavior, connection-pool trade-off, concurrency control và chọn streaming/chunking/offline export dựa trên evidence.

# Câu 2 — Sau khi backend đổi IP, một số pods .NET vẫn gọi endpoint cũ; tăng retry lại làm SNAT/connection pressure nặng hơn

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** `HttpClient`, `IHttpClientFactory`, `SocketsHttpHandler`, DNS, connection pooling, TCP, SNAT/ephemeral ports, retries, resilience, ASP.NET Core, production diagnostics

## Bối cảnh

Một ASP.NET Core service `EmployeeApi` gọi internal `BenefitsApi` qua hostname:

`https://benefits.internal.company`

Hệ thống chạy nhiều instances trong cloud. `BenefitsApi` vừa blue/green deploy: DNS được chuyển từ IP cũ sang IP mới với TTL ngắn.

Khoảng 10 phút sau cutover:

- khoảng 70% requests hoạt động bình thường;
- một số `EmployeeApi` instances vẫn có timeout/502 khi gọi backend cũ;
- restart instance bị lỗi thường làm request hoạt động lại;
- DNS lookup từ shell trong container trả IP mới;
- team dùng `IHttpClientFactory` nhưng một typed client có custom handler;
- sau khi tăng retry từ 2 lên 6, error rate đôi lúc giảm ngắn hạn nhưng outbound connection count và latency tăng mạnh;
- một môi trường khác từng gặp `SocketException`/outbound port exhaustion khi traffic spike;
- dashboard hiện chỉ có tổng dependency duration/error, chưa có remote endpoint IP, connection reuse hay retry-attempt dimension.

Cấu hình rút gọn:

```csharp
builder.Services.AddHttpClient<IBenefitsClient, BenefitsClient>(client =>
{
    client.BaseAddress = new Uri("https://benefits.internal.company");
    client.Timeout = TimeSpan.FromSeconds(10);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    MaxConnectionsPerServer = 200,
    ConnectTimeout = TimeSpan.FromSeconds(3),
    PooledConnectionIdleTimeout = TimeSpan.FromMinutes(15)
});
```

Developer A nói: “DNS TTL là 30 giây, nên .NET chắc chắn đổi IP sau 30 giây.”  
Developer B đề xuất tạo `new HttpClient()` cho mỗi request để ép DNS lookup mới.  
Developer C muốn retry mọi `5xx`, `timeout`, `TaskCanceledException` sáu lần ngay lập tức.

## Câu hỏi chính

Bạn sẽ điều tra incident này như thế nào, giải thích mối quan hệ giữa DNS TTL, DNS resolution và connection pooling của `SocketsHttpHandler`, vì sao process có thể tiếp tục dùng connection tới IP cũ dù shell resolve hostname mới, khi nào `PooledConnectionLifetime` hữu ích, và vì sao cách “new HttpClient per request” hoặc retry quá nhiều có thể biến lỗi backend thành connection/SNAT incident lớn hơn?

## Câu hỏi làm rõ nên cân nhắc

1. Connection hiện tại tới IP cũ còn healthy ở TCP/TLS level hay chỉ application phía cũ không phục vụ đúng nữa?
2. DNS record TTL, load balancer drain window và blue/green overlap được cấu hình thế nào?
3. Custom handler này có làm thay đổi handler lifetime mặc định mà team nghĩ `IHttpClientFactory` đang quản lý không?
4. Outbound network có NAT gateway/SNAT quota nào, và số source ports/connections đang ở trạng thái nào?
5. Requests nào idempotent và thực sự an toàn để retry?

## Gợi ý tư duy

### Gợi ý 1

DNS TTL không có nghĩa một TCP connection đang mở bị đóng đúng lúc TTL hết hạn. HTTP client có thể reuse pooled connection mà không cần resolve DNS lại.

### Gợi ý 2

Hai lifetime khác nhau cần phân biệt: lifetime của `HttpClient` abstraction và lifetime của underlying connections/handler.

### Gợi ý 3

Retry là load multiplier. Khi downstream đang chậm, nhiều retry đồng bộ có thể tăng concurrent sockets, queueing, SNAT usage và làm recovery khó hơn.

## Cấu trúc trả lời đề xuất

1. Stabilize incident và giới hạn retry amplification.
2. So sánh failing vs healthy instance ở DNS, remote IP, connection pool và request path.
3. Giải thích `HttpClient`/handler/connection pooling semantics.
4. Xác định DNS cutover contract và desired connection lifetime.
5. Sửa resilience policy có budget/jitter/idempotency.
6. Kiểm tra NAT/SNAT/ephemeral-port behavior.
7. Load/failure test và thêm observability.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không đồng nhất DNS TTL với pooled-connection lifetime.
- Không tạo/dispose `HttpClient` mỗi request để “fix DNS”.
- Hiểu `SocketsHttpHandler` pool connections theo endpoint.
- Biết `PooledConnectionLifetime` có thể buộc connection được refresh định kỳ để re-resolve DNS cho connection mới.
- Biết retry phải bounded và chỉ cho operation an toàn/idempotent.
- Nhận ra retry làm tăng load và có thể làm cạn outbound connection/SNAT capacity.

### Điểm cộng

- Phân biệt `PooledConnectionIdleTimeout` và `PooledConnectionLifetime`.
- Kiểm tra remote IP bằng network/dependency telemetry thay vì chỉ `nslookup`.
- Có exponential backoff + jitter, overall timeout budget và circuit-breaking/load-shedding khi phù hợp.
- Phối hợp DNS TTL với backend drain duration để connection cũ không bị cắt quá sớm.
- Không retry blindly non-idempotent POST.

### Senior+

- Nhận ra custom `ConfigurePrimaryHttpMessageHandler` cần được hiểu cùng handler rotation/lifetime của factory, không dựa vào assumption mặc định.
- Phân biệt stale DNS connection với SNAT exhaustion, ThreadPool starvation và downstream saturation bằng evidence.
- Thiết kế deployment contract: endpoint discovery + connection lifetime + graceful drain phải khớp nhau.
- Có retry budget ở service level thay vì từng layer cùng retry gây retry storm.

## Hướng giải quyết tham khảo

Tôi sẽ không restart tất cả instances ngay vì restart xóa evidence. Trước hết giảm retry amplification nếu đang gây pressure, rồi lấy một failing instance và một healthy instance để so sánh.

`nslookup`/DNS lookup trong shell chỉ chứng minh resolver hiện trả IP mới. Nó không chứng minh `HttpClient` sẽ thực hiện lookup cho request tiếp theo. `SocketsHttpHandler` reuse HTTP connections. Nếu một pooled connection tới IP cũ vẫn mở, request tiếp theo có thể đi trên connection đó mà không cần DNS resolution mới. Vì vậy DNS TTL 30 giây không tự đóng TCP connection sau 30 giây.

Trong config hiện tại có `PooledConnectionIdleTimeout`, nghĩa connection không được dùng trong một khoảng idle đủ lâu có thể bị loại khỏi pool. Nó không đặt maximum age tuyệt đối cho connection đang được dùng thường xuyên. Một busy connection/pool có thể sống qua nhiều DNS TTL. `PooledConnectionLifetime` đặt tuổi tối đa cho pooled connection; sau khi hết lifetime, connection không được tái sử dụng cho request mới và connection mới sẽ dẫn tới resolution/connect mới.

Ví dụ, nếu deployment/DNS model yêu cầu clients refresh backend trong vài phút:

```csharp
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    MaxConnectionsPerServer = 200,
    ConnectTimeout = TimeSpan.FromSeconds(3),
    PooledConnectionIdleTimeout = TimeSpan.FromMinutes(2),
    PooledConnectionLifetime = TimeSpan.FromMinutes(2)
});
```

Con số 2 phút không phải magic best practice. Nó phải phù hợp với DNS/load-balancer/drain contract và connection churn acceptable. Lifetime quá ngắn có thể làm tăng TCP/TLS handshakes và outbound port churn; quá dài có thể bám endpoint cũ lâu hơn desired.

Tạo `new HttpClient()` mỗi request là một phản xạ nguy hiểm. Vấn đề lịch sử phổ biến là tạo/dispose clients/handlers liên tục làm mất connection reuse và tăng số sockets/TIME_WAIT, có thể dẫn tới ephemeral/SNAT port pressure. `IHttpClientFactory` hoặc long-lived client với handler policy đúng tồn tại để quản lý reuse/lifetime có chủ đích.

Retry cũng không phải miễn phí. Nếu một request timeout sau 10 giây rồi retry sáu lần, logical request có thể giữ resources rất lâu. Nếu 500 incoming requests cùng làm vậy, downstream nhận nhiều lần traffic mong muốn. Với backend đang degraded, retry storm làm connection count, queue length, latency và NAT usage tăng.

Tôi sẽ xác định operations nào idempotent, đặt small retry count với exponential backoff + jitter, và một overall deadline/budget. Không nên mỗi layer — client SDK, service, gateway — cùng retry 3–6 lần. Có thể dùng circuit breaker hoặc concurrency limit/load shedding nếu downstream failure kéo dài, nhưng policy phải dựa trên failure mode thật.

Điều tra cần telemetry tới remote endpoint IP nếu stack/platform cho phép, DNS/connect timing, HTTP status/exception taxonomy, attempt number, total logical-request duration, active/established outbound connections, NAT/SNAT port metrics, connection pool queueing và backend health. Nếu failing pods đều tiếp tục kết nối IP cũ, evidence rất khác với trường hợp tất cả pods dùng IP mới nhưng NAT gateway hết port.

Ở deployment layer, blue/green phải có drain contract. Nếu DNS chuyển lúc 10:00 nhưng old backend bị kill lúc 10:00:30, trong khi clients được phép giữ pooled connections vài phút, stale connections sẽ fail. Hoặc backend cũ nên tiếp tục drain đủ lâu, hoặc client connection lifetime/discovery mechanism phải refresh nhanh hơn. Đây là distributed deployment contract, không chỉ là `HttpClient` config.

## Mẫu trả lời trong phỏng vấn

“DNS TTL 30 giây không có nghĩa request .NET sẽ resolve DNS lại sau đúng 30 giây. Nếu `SocketsHttpHandler` đang reuse một pooled connection tới IP cũ, request không cần DNS lookup mới. Vì thế shell resolve IP mới nhưng process vẫn gọi endpoint cũ là hoàn toàn có thể.

Tôi sẽ so sánh failing và healthy pods theo remote IP, connection age/count, error taxonomy và NAT metrics trước. Nếu evidence đúng là pooled connection bám old backend, tôi cân nhắc `PooledConnectionLifetime` phù hợp với blue/green drain window, thay vì tạo `HttpClient` mỗi request.

Tôi cũng sẽ rollback retry từ 6 về một policy có budget. Retry là load multiplier; timeout + sáu retries ở concurrency cao có thể biến một dependency incident thành socket/SNAT exhaustion. Chỉ retry operation idempotent, dùng backoff+jitter và overall deadline.

Cuối cùng tôi sửa deployment contract: DNS cutover, old-backend drain duration và client connection lifetime phải tương thích. Sau đó failure-test bằng cách đổi backend IP dưới load và chứng minh clients chuyển endpoint trong SLO mà connection/SNAT metrics vẫn ổn.”

## Câu hỏi đào sâu

1. Nếu `PooledConnectionLifetime` giảm stale routing nhưng TLS handshake CPU tăng đáng kể, bạn chọn lifetime thế nào?
2. Nếu POST tạo benefit enrollment không có idempotency key, bạn xử lý timeout/retry ra sao để không tạo duplicate side effects?
3. Nếu remote IP đã là IP mới ở mọi failing pod nhưng timeout vẫn tăng cùng NAT port usage, investigation tiếp theo của bạn là gì?

## Lỗi trả lời thường gặp

- Tin rằng DNS TTL tự động kill pooled TCP connection.
- Tạo `new HttpClient()` cho từng request.
- Retry mọi lỗi với số lần lớn và không có backoff/jitter/deadline.
- Restart pods trước khi thu evidence rồi tuyên bố “DNS cache”.
- Chỉ xem HTTP error rate, bỏ qua outbound connection/NAT metrics.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart hoặc flush DNS.
- **3–4:** Biết `HttpClient` nên reuse nhưng không giải thích connection pool/DNS relationship.
- **5–6:** Hiểu `PooledConnectionLifetime`, retry amplification và có investigation hợp lý.
- **7–8:** Kết nối DNS, connection pool, SNAT, deployment drain, idempotency và telemetry.
- **9–10:** Thiết kế được end-to-end discovery/resilience contract, phân biệt competing failure modes bằng evidence và cân bằng stale routing với handshake/port churn/load protection.

# Câu 3 — Từ `IsAdmin` và role strings đến authorization có thể audit: thiết kế quyền cho employee platform mà không tạo role explosion

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core Authorization, RBAC, permission-based authorization, resource-based authorization, ABAC concepts, multi-tenant security, least privilege, auditability, caching, revocation, API design, testing

## Bối cảnh

Một employee platform .NET 8 có các modules:

- Employee Profile;
- Leave/Timesheet;
- Documents;
- Finance reimbursement;
- Admin configuration;
- Support tooling.

Hệ thống hiện có khoảng 8 roles lưu trong identity claims: `Employee`, `Manager`, `HR`, `Finance`, `Support`, `Admin`, ... Code bắt đầu xuất hiện nhiều checks như:

```csharp
if (User.IsInRole("Admin") || User.IsInRole("HR"))
{
    // allow
}
```

và:

```csharp
[Authorize(Roles = "Manager,HR,Admin")]
public async Task<IActionResult> GetEmployeeSalary(int employeeId) { ... }
```

Business đang mở rộng:

- Manager chỉ được xem nhân viên trong reporting line của mình;
- HR ở Việt Nam không mặc định được xem payroll của tenant/country khác;
- Finance được approve reimbursement tới một limit nhất định;
- Support có thể xem một số metadata nhưng không được xem sensitive document content;
- temporary delegates có quyền approve trong một date range;
- privileged actions phải audit được “ai, quyền nào, resource nào, vì sao được phép”;
- quyền bị revoke cần có hiệu lực trong vài phút, không phải chờ JWT 8 giờ hết hạn;
- hệ thống multi-tenant và có API + background processes;
- team muốn tránh một authorization microservice nếu chưa thực sự cần.

Một đề xuất là tạo thêm roles như `VN_HR`, `SG_HR`, `Finance_10M`, `Finance_50M`, `Manager_Department_A`, ...  
Một đề xuất khác là đưa toàn bộ permissions/employee IDs vào JWT claims.  
Đề xuất thứ ba là xây một central permission database và mỗi request query database trực tiếp.

## Câu hỏi chính

Bạn sẽ thiết kế authorization model và implementation trong ASP.NET Core như thế nào để hỗ trợ role/permission/resource constraints, tenant boundaries, delegation, audit và revocation mà không tạo role explosion hoặc database lookup không kiểm soát trên mọi request? Hãy nêu rõ authentication khác authorization ra sao, đâu là stable claims nên có trong token, đâu là runtime/resource data nên được đánh giá ở server, caching/revocation semantics, và cách rollout từ code `IsInRole()` hiện tại.

## Câu hỏi làm rõ nên cân nhắc

1. Identity provider hiện phát access token/cookie gì, TTL bao lâu và có hỗ trợ claims transformation/introspection không?
2. Reporting line, country, tenant membership và approval limits thay đổi với tần suất nào?
3. Permission check có cần consistent ngay lập tức sau revoke hay SLO vài phút là đủ?
4. Background jobs hành động nhân danh user hay dùng service identity/system permission riêng?
5. Audit requirement cần lưu decision input đầy đủ đến mức nào và retention/privacy ra sao?

## Gợi ý tư duy

### Gợi ý 1

Role thường mô tả nhóm năng lực tương đối coarse-grained. “Manager của employee X trong tenant Y tại thời điểm T” là quan hệ với resource/context, không nên nhân thành vô số role strings.

### Gợi ý 2

Token nên chứa identity/stable context phù hợp với lifetime của token. Dữ liệu thay đổi thường xuyên hoặc cardinality lớn không phù hợp để đóng băng hàng nghìn values trong JWT dài nhiều giờ.

### Gợi ý 3

ASP.NET Core policy/requirement/handler và resource-based authorization cho phép tách rule khỏi controller. Nhưng centralization code không tự động giải quyết caching, audit, revocation và multi-tenant data boundaries.

## Cấu trúc trả lời đề xuất

1. Xác định authorization vocabulary: subject, action, resource, tenant, context.
2. Phân loại coarse roles, permissions và resource attributes.
3. Thiết kế ASP.NET Core policies/handlers.
4. Chọn stable token claims vs server-side dynamic data.
5. Thiết kế permission store/cache/revocation.
6. Xử lý delegation/background identities/audit.
7. Rollout từ legacy role checks.
8. Test negative paths và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Phân biệt authentication và authorization.
- Không encode mọi business rule thành role strings.
- Có tenant/resource-level authorization, không chỉ endpoint-level role check.
- Không tin client-supplied `tenantId`/`employeeId` là proof of access.
- Dùng policy/requirement/handler hoặc tương đương để centralize rule.
- Có strategy cho revocation nhanh hơn token expiry.
- Có audit cho privileged decisions.

### Điểm cộng

- Token chứa stable subject/tenant memberships hoặc coarse roles phù hợp, dynamic relationships được resolve server-side.
- Permission cache có explicit TTL/version/invalidation semantics.
- Delegation được model thành grant có `validFrom/validTo`, scope/action/resource constraints.
- Background service dùng service identity hoặc persisted actor context rõ ràng thay vì replay raw user JWT lâu dài.
- Deny-by-default và negative authorization tests.

### Senior+

- Phân biệt RBAC, permission-based và attribute/resource-based checks mà không biến hệ thống thành một generic policy engine quá sớm.
- Có permission/version stamp hoặc security-stamp-like mechanism để invalidate cache/session/token-derived authorization nhanh.
- Audit decision theo policy/action/resource/subject và relevant grant/version, tránh log sensitive payload không cần thiết.
- Thiết kế rollout dual-evaluation/shadow logging để tìm behavior drift trước khi xóa legacy checks.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng vocabulary thay vì framework API. Một authorization decision có ít nhất:

- **subject**: user/service identity;
- **action**: `EmployeeProfile.Read`, `Reimbursement.Approve`, `Document.Metadata.Read`;
- **resource**: employee, reimbursement, document, tenant;
- **context/attributes**: reporting relationship, country, amount, delegation window, sensitivity.

Authentication trả lời “caller là ai?”. Authorization trả lời “caller này có được thực hiện action này trên resource này trong context hiện tại không?”. JWT hợp lệ không đồng nghĩa user được đọc employee được chỉ định trong route.

Tôi vẫn có thể giữ coarse roles như `Employee`, `HR`, `Finance`, `Support`, nhưng roles chỉ là một input. Thay vì controller chứa:

```csharp
User.IsInRole("Admin") || User.IsInRole("HR")
```

định nghĩa permissions/policies:

```csharp
public static class Permissions
{
    public const string EmployeeSensitiveRead = "employee.sensitive.read";
    public const string ReimbursementApprove = "reimbursement.approve";
}
```

Một policy có requirement và handler:

```csharp
public sealed record EmployeeAccessRequirement(string Permission)
    : IAuthorizationRequirement;

public sealed class EmployeeAccessHandler
    : AuthorizationHandler<EmployeeAccessRequirement, Employee>
{
    private readonly IAuthorizationData _data;

    public EmployeeAccessHandler(IAuthorizationData data) => _data = data;

    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        EmployeeAccessRequirement requirement,
        Employee employee)
    {
        var subjectId = context.User.GetSubjectId();
        var tenantId = context.User.GetTenantId();

        if (employee.TenantId != tenantId)
            return;

        if (await _data.HasPermissionAsync(subjectId, tenantId, requirement.Permission) &&
            await _data.CanAccessEmployeeAsync(subjectId, employee.Id))
        {
            context.Succeed(requirement);
        }
    }
}
```

Đây chỉ là sketch; thực tế nên tránh hai database round trips riêng nếu có thể evaluate bằng một query/cache snapshot hợp lý.

### Role explosion

`VN_HR`, `SG_HR`, `Manager_Department_A`, `Finance_50M` trộn identity grouping với business attributes. Khi country × department × amount × tenant × delegation kết hợp, số role tăng theo tích Descartes và rất khó audit/revoke.

Thay vào đó:

- role/permission: caller có capability loại gì;
- resource/attributes: capability đó áp dụng ở tenant/country/reporting line nào;
- grant: exception/delegation scoped theo thời gian/resource.

Ví dụ `Finance` + permission `reimbursement.approve` có `maxApprovalAmount=50_000_000` trong authorization data, hoặc một grant record scoped tenant/currency. Handler so amount của reimbursement với grant. Không cần tạo role mới cho mỗi threshold.

### Token claims

Tôi tránh nhét hàng nghìn employee IDs hoặc mọi dynamic permission vào JWT 8 giờ. Token tốt cho `sub`, issuer/audience, authentication strength, perhaps stable tenant context/coarse roles — các values phù hợp với token lifetime.

Reporting line, temporary delegation, approval limit và revoked permission có thể thay đổi nhanh. Nếu đóng băng tất cả vào self-contained token dài 8 giờ, revoke không có hiệu lực cho tới expiry trừ khi thêm server-side check anyway.

Có vài lựa chọn:

1. giảm token/session lifetime;
2. permission version/security stamp lưu server-side và cache;
3. server-side authorization snapshot/cache theo subject+tenant với TTL vài phút và invalidation khi grant thay đổi;
4. với ultra-sensitive action, bypass stale cache hoặc dùng stricter fresh check.

Nếu requirement nói revoke trong 5 phút, cache TTL 2–3 phút có thể đủ nếu invalidation đáng tin; hoặc event/version bump cho immediate-ish invalidation. Design phải ghi rõ worst-case staleness, không nói “Redis cache nên chắc nhanh”.

### Permission store và cache

Không query 8 tables cho mọi request một cách mù quáng. Có thể có normalized grants trong SQL và build authorization snapshot theo `(subjectId, tenantId, version)`. Cache snapshot ngắn hạn trong distributed cache/local cache tùy topology. Khi admin thay đổi quyền, transaction cập nhật grant + tăng `AuthorizationVersion`. Cache key mang version hoặc invalidation event làm old snapshot không còn được dùng.

Quan trọng là correctness khi cache lỗi: privileged action thường nên fail closed nếu không thể xác minh permission; nhưng một số low-risk reads có thể có degraded policy khác nếu business chấp nhận. Decision phải explicit.

### Resource-based authorization

Endpoint như `/employees/{id}/salary` phải load tối thiểu resource/metadata cần thiết rồi gọi `IAuthorizationService.AuthorizeAsync(User, employee, policy)`. Việc route có `employeeId` không chứng minh caller có access. Multi-tenant filter cũng nên có defense in depth ở query/data layer; authorization không thay thế tenant-scoped data access.

### Delegation

Temporary manager delegate nên là data:

```text
GrantId
SubjectId
TenantId
Permission
ResourceScope
ValidFrom
ValidTo
GrantedBy
Reason
RevokedAt
Version
```

Handler kiểm tra thời gian hiện tại và scope. Không cấp permanent role rồi mong ai đó nhớ xóa sau kỳ nghỉ.

### Background processes

Không lưu raw user JWT rồi dùng lại nhiều giờ. Job persist actor identity + authorized request facts nếu job thực thi “on behalf of”, hoặc dùng service identity với service permission rõ. Với sensitive action, cần quyết định authorization được snapshot tại submit time hay re-evaluate tại execution time. Ví dụ payroll approval có thể cần re-check để revoke có hiệu lực trước execution.

### Audit

Audit privileged decision nên có subject, tenant, action/policy, resource ID/type, result, relevant grant/version, timestamp, correlation ID và actor/service context. Tránh log salary/document content chỉ để “audit”. Audit log cần tamper/retention/access controls phù hợp.

### Rollout

Không thay toàn bộ authorization trong một release. Tôi inventory `IsInRole`/role attributes, mapping từng behavior sang permission/resource rule. Với critical endpoints có thể chạy legacy check và new policy ở shadow mode: legacy vẫn quyết định, policy mới log `would_allow/would_deny`. So mismatch, sửa model/test rồi chuyển enforcement từng module. Cuối cùng xóa duplicated checks để tránh hai nguồn truth.

Tests phải ưu tiên negative paths: manager A không xem employee ngoài reporting line; HR VN không xem SG payroll; expired delegate bị deny; tenant mismatch luôn deny; cache chứa old grant sau revoke không vượt staleness SLO; support metadata permission không mở document body. Authorization bugs thường nằm ở “what must be denied”, không phải happy path.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không giải bài toán này bằng việc thêm hàng trăm role strings. Role là coarse grouping, còn ‘manager có được xem employee X ở tenant Y hay không’ là resource relationship.

Tôi sẽ định nghĩa permissions/actions và dùng ASP.NET Core policies + resource-based handlers. Token giữ stable identity context như `sub`, tenant context và có thể coarse roles. Reporting line, approval limit, delegation và sensitive resource attributes được resolve server-side vì chúng thay đổi nhanh và có cardinality lớn.

Để tránh database query nặng trên mọi request, tôi dùng authorization snapshot/cache theo user+tenant với explicit version/TTL. Khi permission thay đổi, version bump/invalidation làm cache cũ hết hiệu lực trong SLO revoke. Với privileged action tôi fail closed nếu không xác minh được quyền.

Temporary delegation là grant có time window và scope, không phải role permanent. Background jobs dùng service identity hoặc persisted actor context, và tôi quyết định rõ quyền được snapshot lúc submit hay re-check lúc execute.

Rollout sẽ inventory legacy `IsInRole`, map sang policies, shadow-evaluate để tìm mismatch, rồi enforce từng module. Tôi đặc biệt viết negative tests cho tenant boundary, reporting line, expired delegation và support/sensitive-data separation. Audit ghi subject, action, resource, policy/grant version và decision — không log sensitive payload không cần thiết.”

## Câu hỏi đào sâu

1. Nếu requirement đổi thành revoke phải có hiệu lực dưới 10 giây, cache/token design của bạn thay đổi thế nào?
2. Một approval job được submit lúc user còn quyền nhưng chạy 20 phút sau khi user bị revoke; bạn chọn snapshot hay re-evaluate authorization và vì sao?
3. Khi nào bạn sẽ tách authorization thành service/policy engine riêng thay vì giữ trong modular monolith?

## Lỗi trả lời thường gặp

- Nhầm authentication với authorization.
- Biến mọi combination thành role mới.
- Nhét toàn bộ dynamic permissions/resource IDs vào JWT dài hạn.
- Chỉ kiểm tra role ở endpoint, không kiểm tra resource/tenant.
- Dùng cache nhưng không định nghĩa staleness/revocation semantics.
- Chỉ test allow cases, không test deny/bypass paths.
- Xây authorization microservice ngay dù team/scale chưa cần operational complexity đó.

## Thang điểm 0–10

- **0–2:** Chỉ nói dùng roles/JWT, không xử lý resource/tenant/revoke.
- **3–4:** Có permissions nhưng vẫn chủ yếu endpoint-level và thiếu dynamic context.
- **5–6:** Có policy/resource-based authorization, cache/revocation và audit cơ bản.
- **7–8:** Thiết kế tốt role+permission+attributes/grants, background/delegation, rollout và negative testing.
- **9–10:** Thể hiện strong security/architecture judgment: least privilege, explicit staleness/failure semantics, auditable decisions, migration path thực tế và chỉ thêm central policy-service complexity khi requirement biện minh.
