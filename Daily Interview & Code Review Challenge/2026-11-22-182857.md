# Câu 1 — EF Core compiled query, DbContext pooling và dữ liệu sai tenant

**Loại câu hỏi:** Internal mechanism  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18 phút  
**Kỹ năng được đánh giá:** EF Core, DbContext pooling, query filters, multi-tenancy

## Bối cảnh

Một ASP.NET Core API phục vụ 80 tenant trên .NET 8, PostgreSQL và EF Core. Đội phát triển bật AddDbContextPool và dùng global query filter cho TenantId. Sau tối ưu throughput, QA phát hiện hiếm khi một request đọc được đơn hàng của tenant khác. Không có bằng chứng token JWT bị giả mạo. Mỗi request được xác thực, tenant lấy từ claim; API chạy 6 replicas.

## Câu hỏi chính

Giải thích vòng đời DbContext, state được tái sử dụng, cách EF Core dịch và cache query; lập kế hoạch xác định và loại bỏ nguy cơ cross-tenant data leakage mà không đoán nguyên nhân.

## Câu hỏi làm rõ nên cân nhắc

1. TenantId nằm trong field mutable của DbContext hay service scoped?
2. Có dùng IgnoreQueryFilters, FromSqlRaw, compiled query hoặc DbContextFactory?
3. DbContext có được inject vào singleton/background job?
4. Có log tenant, context instance, request ID và SQL parameters mà không lộ PII?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt pooling DbContext với pooling database connection.

### Gợi ý 2

Xem state do ứng dụng đặt trên instance được tái sử dụng.

### Gợi ý 3

Đối chiếu claim tenant, tenant trên context, query filter và SQL thực tế theo request.

## Cấu trúc trả lời đề xuất

1. Vẽ lifecycle request → tenant resolution → context acquisition → query → return-to-pool.
2. Đối chiếu invariant tenant isolation ở mọi tầng.
3. Reproduce và cô lập từng giả thuyết.
4. Sửa state management, kiểm thử và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

Nêu DbContext không thread-safe; pooled context được tái sử dụng nên mutable application state phải được thiết lập lại an toàn; query filter không thay thế authorization; phải chứng minh bằng trace/SQL.

### Điểm cộng

Phân biệt model caching với parameterized query, nguy cơ bypass filter ở raw SQL và IgnoreQueryFilters.

### Senior+

Thiết kế defense-in-depth bằng PostgreSQL Row Level Security nếu phù hợp, kiểm soát session context khi pooling và audit.

## Hướng giải quyết tham khảo

**Giả định:** tenant claim được xác minh từ JWT và mỗi request chỉ thuộc một tenant. EF Core DbContext pooling tái sử dụng instance; OnConfiguring không chạy lại cho từng lần lấy từ pool. Nếu TenantId là mutable property đặt không đầy đủ hoặc đặt sai thời điểm, query filter có thể lấy tenant cũ. Đây là **giả thuyết**, không phải kết luận nếu chưa thấy code.

**Điều tra:** dùng request correlation ID, hashed tenant ID, context ID và SQL parameter để xác định request A nhận tenant B ở tầng nào. Kiểm tra middleware order, scoped tenant accessor, code đặt TenantId, factory, DbContext lifetime, compiled queries, IgnoreQueryFilters và raw SQL. Reproduce bằng test concurrent requests xen kẽ nhiều tenant với pool nhỏ. Đừng log JWT hoặc dữ liệu đơn hàng.

**Sửa:** ưu tiên DbContext scoped không pooling trong lúc containment nếu pooling nghi vấn; triển khai scoped factory đặt tenant từ principal đã xác thực mỗi lần context được cấp phát, đảm bảo không cho phép tenant trống và không cho phép caller override tenant. Query filter phải tham chiếu đúng instance tenant parameter, không capture một tenant cố định khi model được cache. Kiểm tra SaveChanges cũng enforce tenant cho insert/update; mọi endpoint vẫn cần resource-level authorization. Nếu dùng RLS, cấu hình session tenant theo transaction và reset session state đúng khi trả connection về pool.

**Kiểm chứng:** integration test isolation 80 tenant, concurrency stress, kiểm thử pooled context reuse và negative authorization; monitor tỷ lệ cross-tenant invariant violation (mục tiêu 0), latency p95 và pool pressure. Triển khai canary, rollback ngay nếu có violation. Nếu chứng cứ chỉ ra claim mapping sai, sửa identity pipeline thay vì quy lỗi cho pooling.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ xử lý đây là security incident, giới hạn truy cập endpoint bị ảnh hưởng và kiểm tra audit trước. DbContext pooling tái sử dụng instance, nên một property TenantId do ứng dụng đặt có thể bị giữ lại nếu reset không đúng. Tôi không khẳng định đó là root cause trước khi đối chiếu request claim, context tenant và SQL parameter. Tôi sẽ tái hiện bằng test nhiều tenant chạy song song, tạm tắt pooling nếu cần, sau đó dùng scoped factory và kiểm soát tenant ở cả read/write path. Global query filter là guardrail chứ không thay thế authorization. Tôi sẽ rollout canary với invariant telemetry, và cân nhắc RLS nếu mức độ bảo vệ dữ liệu yêu cầu.

## Câu hỏi đào sâu

1. Nếu bỏ pooling làm p95 tăng 15%, bạn đánh đổi thế nào?
2. Compiled query có tự gây rò tenant không, và bạn xác minh ra sao?
3. Nếu có background job không có HTTP principal, tenant context được thiết kế thế nào?

## Lỗi trả lời thường gặp

1. Quy ngay lỗi cho EF Core mà không có bằng chứng.
2. Cho phép tenant lấy từ query string tùy ý.
3. Giả định global query filter thay thế authorization.
4. Log token hoặc dữ liệu nhạy cảm để debug.

## Thang điểm 0–10

Clarification 1; correctness 2; runtime depth 2; investigation 2; trade-off 1; production 1; communication 1. Chấm theo bằng chứng trong câu trả lời, không chấm theo số lượng buzzwords.

# Câu 2 — Kubernetes rollout: readiness xanh nhưng khách hàng gặp 502 và mất session

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 22 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Kubernetes, probes, ingress, authentication, deployment

## Bối cảnh

Một portal ASP.NET Core chạy trên Kubernetes với 12 pods, ingress controller và external identity provider. Sau rolling deployment, p99 tăng từ 450 ms lên 8 s, 502 xuất hiện trong 3 phút và một số người dùng phải đăng nhập lại. Readiness probe `/health` vẫn trả 200. Logs ứng dụng không ghi nhận mọi request 502. Phiên bản trước không có lỗi.

## Câu hỏi chính

Bạn là incident lead: hãy ổn định dịch vụ, phân biệt nguyên nhân 502 và session loss, thu thập chứng cứ, sửa và ngăn tái diễn thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Ingress và service mesh có timeout/connection draining gì?
2. Pod terminationGracePeriodSeconds, preStop và shutdown timeout là bao nhiêu?
3. Authentication dùng cookie với Data Protection keys ở đâu?
4. Health endpoint kiểm tra gì, rollout maxUnavailable/maxSurge thế nào?
5. 502 do ingress hay upstream, có phân bố theo pod/version?

## Gợi ý tư duy

### Gợi ý 1

Không phải mọi 502 đều đi vào ASP.NET Core.

### Gợi ý 2

Xem sự khác nhau giữa readiness, liveness và graceful termination.

### Gợi ý 3

Cookie authentication và Data Protection key ring có liên quan tới mất session.

## Cấu trúc trả lời đề xuất

1. Định lượng ảnh hưởng và dừng rollout.
2. Đối chiếu ingress metrics, endpoint lifecycle, pod events và app traces.
3. Tách giả thuyết routing/termination khỏi key persistence.
4. Thực hiện fix, canary, fault injection và postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc

Tạm dừng rollout/rollback theo bằng chứng; kiểm tra ingress upstream failures và pod termination; kiểm tra Data Protection key persistence.

### Điểm cộng

Đối chiếu endpoint propagation delay, keep-alive, startup warmup, readiness thật và HPA.

### Senior+

Thiết kế release gate theo SLO, chaos test termination và zero-downtime migration key ring.

## Hướng giải quyết tham khảo

**Impact và stabilize:** xác định error budget, affected routes và tỷ lệ login failures; pause rollout, rollback nếu canary vượt ngưỡng, giữ capacity. Không restart hàng loạt khi chưa thu thập pod/ingress events.

**Các giả thuyết cạnh tranh:** (1) ingress còn gửi request tới pod đang terminate; (2) app chưa warmup nhưng readiness quá nông; (3) upstream timeout hoặc connection reset; (4) Data Protection keys không được share/persist khiến cookie không giải mã được giữa pods hoặc sau restart; (5) thay đổi cookie domain/issuer. Các hiện tượng có thể có **hai root causes độc lập**.

**Evidence:** ingress access log status, upstream_status, upstream_response_time; Kubernetes endpoints/EndpointSlices, pod deletion timestamps, readiness transitions, SIGTERM events; Application Insights trace và dependency latency; auth failure reason đã sanitize. 502 không xuất hiện trong app logs có thể phát sinh trước khi request đến app.

**Fix:** readiness phản ánh khả năng nhận traffic, startup probe nếu cần; graceful shutdown ngừng nhận request mới và chờ inflight theo budget; cấu hình drain/termination phù hợp với ingress và thời gian xử lý thực tế. Lưu ASP.NET Core Data Protection key ring vào kho dùng chung, bảo vệ keys và ổn định application name. Không xoá key cũ tùy tiện. Chỉ cấu hình sticky session nếu có lý do rõ; nó không thay thế key persistence.

**Validate:** canary 1→10→100%, load test trong rolling update, test cookie qua pods/restarts, fault injection kill pod, cảnh báo 502/p99/login failures. Nếu nguyên nhân là identity provider outage, phương án điều tra và giảm thiểu khác.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ dừng rollout và so sánh error rate theo pod version. Vì 502 không luôn vào application logs, tôi bắt đầu từ ingress upstream status, pod termination events và EndpointSlices. Readiness 200 không chứng minh request đang xử lý được drain đúng. Mất session là nhánh điều tra riêng: ASP.NET Core cookie phụ thuộc Data Protection key ring, nên cần xác minh keys được chia sẻ và giữ ổn định khi pod thay đổi. Tôi sẽ không áp dụng sticky session để che lỗi. Sau khi sửa sẽ thử rolling update dưới tải, verify cookie cross-pod, canary theo SLO và có rollback tự động.

## Câu hỏi đào sâu

1. Nếu readiness đã kiểm tra DB, tại sao vẫn 502?
2. Khi nào preStop sleep giúp, khi nào chỉ che lỗi?
3. Bạn bảo đảm key rotation không logout hàng loạt thế nào?

## Lỗi trả lời thường gặp

1. Chỉ xem app logs rồi kết luận không có lỗi.
2. Dùng liveness probe để kiểm tra dependency chập chờn và gây restart storm.
3. Cho rằng 502 và logout nhất thiết cùng nguyên nhân.
4. Tăng timeout vô hạn thay cho đo latency và drain.

## Thang điểm 0–10

Impact/stabilization 2; evidence 2; hypotheses 2; correctness 1; remediation 1; testing/monitoring 1; communication 1. Chấm theo bằng chứng trong câu trả lời, không chấm theo số lượng buzzwords.

# Câu 3 — Thiết kế product-search API giữa PostgreSQL, Elasticsearch và Optimizely CMS

**Loại câu hỏi:** Architecture decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** System design, Elasticsearch, CMS, CQRS trade-offs, reliability

## Bối cảnh

Một website thương mại có 2 triệu SKU, nội dung marketing được biên tập trong Optimizely CMS, giá và tồn kho nằm trong PostgreSQL, tìm kiếm full-text/filter chạy Elasticsearch. Product updates 300/s trong giờ cao điểm. Yêu cầu tìm kiếm nhanh, giá không được hiển thị sai khi checkout, nội dung CMS có lịch publish. Ngân sách vận hành hạn chế, đội 6 backend engineers.

## Câu hỏi chính

Đề xuất ranh giới dữ liệu, luồng indexing, API search và checkout, consistency contract, failure modes và chiến lược triển khai; giải thích vì sao không nhất thiết cần microservices.

## Câu hỏi làm rõ nên cân nhắc

1. Search freshness SLA bao nhiêu giây và stale stock được chấp nhận tới đâu?
2. Checkout có yêu cầu reservation/oversell prevention không?
3. Có multi-region, multi-currency, tenant hay compliance đặc biệt?
4. Optimizely là source of truth cho thuộc tính nào, có version publish không?
5. Đỉnh QPS, facet cardinality và latency budget là gì?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt search projection với transactional source of truth.

### Gợi ý 2

Thiết kế update path có thể replay và đo lag.

### Gợi ý 3

Checkout phải xác nhận dữ liệu authoritative, không tin index.

## Cấu trúc trả lời đề xuất

1. Chốt SLO và ownership.
2. Phác data model/API và write-to-index pipeline.
3. Chọn consistency per operation.
4. Thiết kế degradation/recovery và operational cost.
5. Đề xuất test, observability, rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

PostgreSQL authoritative cho price/stock; Elasticsearch là read model eventual consistent; CMS ownership rõ; checkout revalidate.

### Điểm cộng

Transactional outbox, versioned indexing, DLQ/replay, idempotency, facets/pagination và SEO canonical.

### Senior+

Đánh giá modular monolith vs services theo team size, index rebuild alias swap, consistency contract và incident recovery.

## Hướng giải quyết tham khảo

**Giả định:** giá và tồn kho cần chính xác tại checkout, còn search freshness có thể trễ vài giây; cần xác nhận SLA thực tế. PostgreSQL giữ ProductId, Price, Currency, StockVersion và inventory ledger/constraints; Optimizely giữ content blocks, editorial status, publication windows; Elasticsearch lưu projection đã publish cho search, filters và ranking.

**Luồng:** product update commit DB cùng outbox event trong một transaction. Worker đọc outbox, merge với published CMS content theo version, index idempotently theo product ID và monotonic version; retry/backoff, poison queue, replay, full reindex và alias swap. CMS publish/unpublish tạo sự kiện riêng; phải xử lý thứ tự cập nhật và xóa tài liệu không còn publish. Không mặc định Elasticsearch hỗ trợ transaction cùng PostgreSQL.

**API:** GET /products/search?query=&cursor=&filters= trả danh sách, facets, freshness metadata nếu cần; GET /products/{id} lấy detail và có thể refresh price/availability. Checkout dùng transaction/concurrency control với DB authoritative để validate giá, stock và reservation; xử lý idempotency key và payment callback duplicates. Tránh tin giá được gửi từ client hay search index.

**Failure:** Elasticsearch outage → degraded browse từ cached curated content hoặc trả 503 có thông báo phù hợp, không chạy full-table wildcard SQL bất ngờ. CMS outage → phục vụ published snapshot nếu policy cho phép; checkout vẫn hoạt động độc lập. Outbox lag → metric lag/age, alert, replay; không bỏ event âm thầm.

**Architecture:** modular monolith với search indexing worker riêng có thể đủ cho 6 người; microservices chỉ khi ownership, deploy independence hoặc scale thực sự biện minh. Security: admin publish permission, API rate limits, secrets/Managed Identity khi có thể. Tests: event reorder/duplicates, index rebuild, stale-price checkout, search outage, CMS unpublish, load p95. Monitor search p95/p99, indexing lag, DLQ, checkout price conflicts và conversion. Nếu search freshness phải gần strong consistency, xem lại UX/architecture thay vì hứa Elasticsearch tức thời.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ tách rõ transactional truth và search projection. PostgreSQL quyết định giá và tồn kho khi checkout; Optimizely sở hữu nội dung đã publish; Elasticsearch phục vụ full-text và facets nhưng có độ trễ. Tôi cần xác nhận freshness SLA trước khi chọn pipeline. Tôi nghiêng về modular monolith cùng outbox và worker indexing vì team nhỏ, dễ vận hành hơn microservices. Worker phải idempotent, replay được và đo indexing lag. Khi search lỗi, website giảm cấp có kiểm soát; checkout không phụ thuộc vào search index. Tôi sẽ kiểm thử duplicate/out-of-order events, reindex, publish/unpublish và stale price, rồi canary rollout.

## Câu hỏi đào sâu

1. Nếu product update tăng lên 10.000/s, bạn thay đổi thành phần nào trước?
2. Nếu business yêu cầu search phản ánh stock trong 100 ms, bạn thương lượng hoặc thiết kế lại thế nào?
3. Làm sao rollback index mapping mới mà không mất cập nhật?

## Lỗi trả lời thường gặp

1. Cho Elasticsearch làm nguồn giá authoritative.
2. Dual-write DB và index không có recovery.
3. Đề xuất microservices vì quy mô SKU lớn mà không đo bottleneck.
4. Không xử lý unpublish và out-of-order events.

## Thang điểm 0–10

Requirements 1; boundaries/consistency 2; technical depth 2; failure design 2; trade-offs 1; testing/observability 1; communication 1. Chấm theo bằng chứng trong câu trả lời, không chấm theo số lượng buzzwords.
