# Code Review Challenge 1 — BackgroundService xử lý song song nhưng dùng sai lifetime

**Chủ đề:** Background jobs, DI lifetime, concurrency, cancellation, resource lifetime  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core nhận các yêu cầu đồng bộ nhân viên từ Azure AD/Microsoft Graph rồi lưu vào SQL Server. Team viết một `BackgroundService` để đọc queue nội bộ và xử lý song song nhằm tăng throughput.

Service chạy trên 3 application instances. Mỗi instance có thể nhận hàng nghìn item trong giờ cao điểm.

Production gần đây xuất hiện các triệu chứng:

- Thỉnh thoảng có lỗi `A second operation was started on this context instance before a previous operation completed`.
- Một số record bị ghi đè hoặc trạng thái không nhất quán.
- Khi deploy, container mất nhiều thời gian để shutdown.
- Có lúc memory và số lượng active tasks tăng nhanh khi queue dồn nhiều item.
- Một số lỗi từ worker không xuất hiện rõ trong log.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class EmployeeSyncWorker : BackgroundService
{
    private readonly AppDbContext _dbContext;
    private readonly IEmployeeDirectoryClient _directoryClient;
    private readonly IEmployeeSyncQueue _queue;
    private readonly ILogger<EmployeeSyncWorker> _logger;

    public EmployeeSyncWorker(
        AppDbContext dbContext,
        IEmployeeDirectoryClient directoryClient,
        IEmployeeSyncQueue queue,
        ILogger<EmployeeSyncWorker> logger)
    {
        _dbContext = dbContext;
        _directoryClient = directoryClient;
        _queue = queue;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var items = await _queue.DequeueBatchAsync(100);

            if (items.Count == 0)
            {
                await Task.Delay(1000);
                continue;
            }

            foreach (var item in items)
            {
                _ = Task.Run(async () =>
                {
                    var profile = await _directoryClient.GetEmployeeAsync(item.Email);

                    var employee = await _dbContext.Employees
                        .SingleOrDefaultAsync(x => x.Email == item.Email);

                    if (employee == null)
                    {
                        employee = new Employee
                        {
                            Email = item.Email,
                            CreatedAt = DateTime.UtcNow
                        };

                        _dbContext.Employees.Add(employee);
                    }

                    employee.DisplayName = profile.DisplayName;
                    employee.Department = profile.Department;
                    employee.LastSyncedAt = DateTime.UtcNow;

                    await _dbContext.SaveChangesAsync();

                    await _queue.MarkCompletedAsync(item.Id);
                });
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Inject `DbContext` trực tiếp vào `BackgroundService`

- **Problem:** Worker giữ một `AppDbContext` lâu dài.
- **Why it happens:** `BackgroundService` được đăng ký như hosted service và sống cùng host, trong khi `DbContext` thường được dùng theo scope/unit-of-work ngắn.
- **Production impact:** Context tích lũy tracking state, lifetime quá dài, tăng memory và tạo nền tảng cho các lỗi concurrency.
- **Severity:** Critical
- **Recommended fix:** Inject `IServiceScopeFactory` hoặc `IDbContextFactory<AppDbContext>` rồi tạo context riêng cho mỗi operation/batch.

### 2. Nhiều task sử dụng cùng một `DbContext`

- **Problem:** Mỗi `Task.Run` truy cập cùng `_dbContext`.
- **Why it happens:** `DbContext` không được thiết kế để thực hiện nhiều operation song song trên cùng instance.
- **Production impact:** Exception kiểu “second operation started”, state corruption trong change tracker, update không xác định.
- **Severity:** Critical
- **Recommended fix:** Mỗi work item dùng context riêng hoặc mỗi bounded worker giữ scope/context riêng theo unit of work.

### 3. Fire-and-forget `Task.Run` làm mất ownership của task

- **Problem:** `_ = Task.Run(...)` tạo task nhưng không await hoặc track.
- **Why it happens:** Main loop tiếp tục ngay sau khi schedule task.
- **Production impact:** Exception có thể bị bỏ sót, shutdown không đợi task, queue item có thể đang xử lý dở khi process bị terminate.
- **Severity:** High
- **Recommended fix:** Dùng bounded worker pool, `Parallel.ForEachAsync`, `Channel<T>` hoặc explicit task collection có ownership rõ ràng.

### 4. Không giới hạn concurrency

- **Problem:** Mỗi batch 100 item đều tạo 100 task và vòng lặp có thể tiếp tục tạo thêm task khi batch tiếp theo đến.
- **Why it happens:** Không có semaphore, channel capacity hoặc max degree of parallelism.
- **Production impact:** Memory tăng, connection pool bị pressure, SQL connection saturation, downstream Graph bị throttling, latency tăng dây chuyền.
- **Severity:** High
- **Recommended fix:** Giới hạn concurrency dựa trên dependency capacity và đo tải thực tế.

### 5. Không truyền `CancellationToken`

- **Problem:** `DequeueBatchAsync`, `Task.Delay`, Graph call, EF query, `SaveChangesAsync` và `MarkCompletedAsync` đều bỏ qua `stoppingToken`.
- **Why it happens:** Cancellation không được propagate qua call chain.
- **Production impact:** Shutdown chậm, operation tiếp tục sau khi host yêu cầu dừng, deploy có thể kill process giữa transaction/business operation.
- **Severity:** High
- **Recommended fix:** Propagate `stoppingToken` đến mọi API hỗ trợ cancellation; phân biệt cancellation với application failure.

### 6. Race condition khi hai item cùng update một employee

- **Problem:** Hai task có thể cùng đọc cùng record và cùng ghi.
- **Why it happens:** Không có deduplication, serialization theo employee key hoặc concurrency control.
- **Production impact:** Lost update, trạng thái cuối phụ thuộc timing.
- **Severity:** High
- **Recommended fix:** Xác định business guarantee. Có thể dùng idempotency key, unique work key, optimistic concurrency token hoặc partition processing theo employee.

### 7. Queue completion không atomic với database side effect

- **Problem:** `SaveChangesAsync` thành công nhưng `MarkCompletedAsync` thất bại thì item có thể được xử lý lại.
- **Why it happens:** Hai side effects nằm ở hai hệ thống khác nhau.
- **Production impact:** Duplicate processing, duplicate external calls hoặc update lặp lại.
- **Severity:** High
- **Recommended fix:** Thiết kế idempotent handler; nếu queue nằm trong DB có thể dùng transaction phù hợp, nếu khác hệ thống cần operation state/idempotency/reconciliation.

### 8. Không có exception handling theo work item

- **Problem:** Worker task không có `try/catch` có cấu trúc.
- **Why it happens:** Fire-and-forget task chạy độc lập.
- **Production impact:** Khó biết item nào fail, retry policy không rõ, có thể tạo poison items.
- **Severity:** Medium
- **Recommended fix:** Catch ở boundary của từng work item, log correlation IDs, phân loại transient/permanent failure và quyết định retry/dead-letter.

### 9. `Task.Run` không cần thiết cho async I/O

- **Problem:** Bọc async I/O trong `Task.Run`.
- **Why it happens:** Nhầm rằng cần thêm thread để “chạy song song”.
- **Production impact:** Tăng scheduling overhead và làm ownership/cancellation khó hơn.
- **Severity:** Medium
- **Recommended fix:** Gọi async method trực tiếp trong bounded concurrency primitive.

### 10. Polling delay không cancelable

- **Problem:** `Task.Delay(1000)` không nhận token.
- **Why it happens:** Bỏ qua cancellation.
- **Production impact:** Shutdown bị trì hoãn không cần thiết.
- **Severity:** Low
- **Recommended fix:** `Task.Delay(TimeSpan.FromSeconds(1), stoppingToken)`.

## Phiên bản code đề xuất

Một implementation đơn giản hơn là dùng `Parallel.ForEachAsync` với concurrency có giới hạn và tạo scope riêng cho từng item:

```csharp
public sealed class EmployeeSyncWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly IEmployeeSyncQueue _queue;
    private readonly ILogger<EmployeeSyncWorker> _logger;

    private const int MaxConcurrency = 8;

    public EmployeeSyncWorker(
        IServiceScopeFactory scopeFactory,
        IEmployeeSyncQueue queue,
        ILogger<EmployeeSyncWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _queue = queue;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var items = await _queue.DequeueBatchAsync(100, stoppingToken);

            if (items.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
                continue;
            }

            await Parallel.ForEachAsync(
                items,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = MaxConcurrency,
                    CancellationToken = stoppingToken
                },
                ProcessItemAsync);
        }
    }

    private async ValueTask ProcessItemAsync(
        EmployeeSyncItem item,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();

        var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var directoryClient = scope.ServiceProvider
            .GetRequiredService<IEmployeeDirectoryClient>();

        try
        {
            var profile = await directoryClient.GetEmployeeAsync(
                item.Email,
                cancellationToken);

            var employee = await dbContext.Employees
                .SingleOrDefaultAsync(
                    x => x.Email == item.Email,
                    cancellationToken);

            if (employee is null)
            {
                employee = new Employee
                {
                    Email = item.Email,
                    CreatedAt = DateTime.UtcNow
                };

                dbContext.Employees.Add(employee);
            }

            employee.DisplayName = profile.DisplayName;
            employee.Department = profile.Department;
            employee.LastSyncedAt = DateTime.UtcNow;

            await dbContext.SaveChangesAsync(cancellationToken);

            await _queue.MarkCompletedAsync(
                item.Id,
                cancellationToken);
        }
        catch (OperationCanceledException)
            when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Employee sync failed. ItemId={ItemId}, Email={Email}",
                item.Id,
                item.Email);

            await _queue.MarkFailedAsync(
                item.Id,
                ex.GetType().Name,
                cancellationToken);
        }
    }
}
```

Implementation trên xử lý phần lớn vấn đề về lifetime và task ownership, nhưng **chưa tự động giải quyết idempotency hoặc race condition theo employee**. Nếu queue có thể chứa nhiều item cho cùng employee, cần bổ sung business-level concurrency strategy.

Ví dụ:

- Deduplicate theo `(EmployeeId, Version)`.
- Serialize các item có cùng partition key.
- Dùng optimistic concurrency token.
- Lưu operation state/idempotency key.

## Trade-offs

- `Parallel.ForEachAsync` đơn giản và phù hợp khi batch đã có sẵn trong memory.
- `Channel<T>` tốt hơn nếu muốn pipeline dài hạn, backpressure rõ ràng và worker pool cố định.
- Concurrency thấp bảo vệ DB/downstream nhưng giảm throughput.
- Concurrency cao tăng throughput chỉ đến khi dependency bắt đầu saturation/throttling.
- Scope/context per item tạo thêm overhead nhỏ nhưng đổi lại isolation và correctness tốt hơn.
- Nếu mỗi item rất nhỏ, xử lý theo batch transaction có thể hiệu quả hơn, nhưng failure isolation sẽ khác.

## Cách kiểm thử

1. **Concurrency test:** enqueue 1.000 items và xác minh active workers không vượt `MaxConcurrency`.
2. **Same-employee race test:** enqueue nhiều update cho cùng employee, xác minh strategy concurrency không làm mất dữ liệu.
3. **Cancellation test:** shutdown host khi đang xử lý batch, xác minh worker dừng có kiểm soát và item chưa hoàn tất có thể retry.
4. **Failure-path test:** Graph timeout/SQL transient failure, xác minh retry/failure state đúng và không mất item.
5. **Load test:** theo dõi throughput, DB connections, Graph throttling, memory và queue lag khi tăng tải.

# Code Review Challenge 2 — Search API có pagination nhưng vẫn kéo dữ liệu khổng lồ về memory

## Bối cảnh

Một ASP.NET Core endpoint cho phép HR tìm employee theo office, status, tên và khoảng ngày tạo.

Database có khoảng 3 triệu employee/history-related rows. Endpoint được gọi thường xuyên bởi admin portal.

- Memory của application tăng mạnh khi user search rộng.
- SQL CPU tăng trong giờ cao điểm.
- Pagination đôi khi trả duplicate hoặc thiếu record khi có employee mới được thêm trong lúc user chuyển page.

Code hiện tại:

## Đoạn code cần review

```csharp
public async Task<EmployeeSearchResponse> SearchAsync(
    EmployeeSearchRequest request,
    CancellationToken cancellationToken)
{
    var employees = await _dbContext.Employees
        .Include(x => x.Office)
        .Include(x => x.Status)
        .Include(x => x.Manager)
        .Where(x => !x.IsDeleted)
        .ToListAsync(cancellationToken);

    if (!string.IsNullOrWhiteSpace(request.Keyword))
    {
        employees = employees
            .Where(x =>
                x.FullName.Contains(request.Keyword,
                    StringComparison.OrdinalIgnoreCase) ||
                x.Email.Contains(request.Keyword,
                    StringComparison.OrdinalIgnoreCase))
            .ToList();
    }

    if (request.OfficeIds?.Count > 0)
        employees = employees
            .Where(x => request.OfficeIds.Contains(x.OfficeId))
            .ToList();

    if (request.StatusIds?.Count > 0)
        employees = employees
            .Where(x => request.StatusIds.Contains(x.StatusId))
            .ToList();

    if (request.CreatedFrom.HasValue)
        employees = employees
            .Where(x => x.CreatedAt >= request.CreatedFrom.Value)
            .ToList();

    if (request.CreatedTo.HasValue)
        employees = employees
            .Where(x => x.CreatedAt <= request.CreatedTo.Value)
            .ToList();

    var total = employees.Count;

    var page = employees
        .OrderByDescending(x => x.CreatedAt)
        .Skip((request.Page - 1) * request.PageSize)
        .Take(request.PageSize)
        .Select(x => new EmployeeSearchItem
        {
            Id = x.Id,
            FullName = x.FullName,
            Email = x.Email,
            OfficeName = x.Office.Name,
            StatusName = x.Status.Name,
            ManagerName = x.Manager == null ? null : x.Manager.FullName
        })
        .ToList();

    return new EmployeeSearchResponse
    {
        Total = total,
        Items = page
    };
}
```

## Kết quả code review tham khảo

### 1. `ToListAsync` quá sớm

- **Problem:** Toàn bộ employee chưa bị xóa cùng navigation được tải về trước khi filter.
- **Why it happens:** `ToListAsync` materialize `IQueryable` thành list.
- **Production impact:** Full/large table read, network I/O lớn, application memory cao, GC pressure.
- **Severity:** Critical
- **Recommended fix:** Giữ query ở dạng `IQueryable` đến sau filter/sort/pagination/projection.

### 2. Filter chạy trong memory

- **Problem:** Keyword, office, status và date filters chạy bằng LINQ-to-Objects.
- **Why it happens:** Query đã trở thành `List<Employee>`.
- **Production impact:** Database không thể dùng index hiệu quả cho các filter đó; application phải scan tập dữ liệu lớn.
- **Severity:** Critical
- **Recommended fix:** Build predicates trên `IQueryable` trước materialization.

### 3. `Include` nhiều navigation không cần thiết

- **Problem:** `Office`, `Status`, `Manager` được `Include` trước khi cuối cùng chỉ lấy vài field.
- **Why it happens:** Query entity graph theo thói quen.
- **Production impact:** Nhiều columns/object allocations/tracking hơn cần thiết.
- **Severity:** High
- **Recommended fix:** Projection trực tiếp sang DTO; EF Core có thể tạo join/subquery cần thiết từ projection.

### 4. Tracking không cần thiết cho read-only search

- **Problem:** Entity query mặc định có thể tracking.
- **Why it happens:** Không dùng no-tracking/projection-only strategy.
- **Production impact:** Change Tracker giữ nhiều entity, tăng memory và CPU.
- **Severity:** High
- **Recommended fix:** Projection trực tiếp; có thể thêm `AsNoTracking()` cho read-only query entity nếu cần.

### 5. Pagination order không deterministic hoàn toàn

- **Problem:** Chỉ sort theo `CreatedAt`.
- **Why it happens:** Nhiều employee có thể có cùng timestamp.
- **Production impact:** Duplicate/missing rows giữa pages ngay cả khi dataset không thay đổi.
- **Severity:** High
- **Recommended fix:** Thêm tie-breaker unique, ví dụ `ThenByDescending(x => x.Id)`.

### 6. Offset pagination dễ bị drift khi dữ liệu thay đổi

- **Problem:** `Skip/Take` dựa trên vị trí hiện tại của dataset.
- **Why it happens:** Record mới có thể chèn vào trước page tiếp theo.
- **Production impact:** User có thể thấy duplicate hoặc miss record khi duyệt nhiều page.
- **Severity:** Medium
- **Recommended fix:** Nếu cần consistency cao khi browse, cân nhắc keyset/cursor pagination hoặc snapshot semantics.

### 7. `Skip` lớn có thể ngày càng đắt

- **Problem:** Deep page yêu cầu database bỏ qua nhiều rows.
- **Why it happens:** Offset pagination.
- **Production impact:** Query latency tăng theo page depth tùy execution plan/index/data distribution.
- **Severity:** Medium
- **Recommended fix:** Keyset pagination cho use case browse tuần tự; giữ offset nếu admin cần nhảy trực tiếp page và volume hợp lý.

### 8. Keyword search bằng `%term%` có thể khó tận dụng B-tree index

- **Problem:** Nếu triển khai bằng `Contains`, SQL thường phải xử lý substring matching.
- **Why it happens:** Search requirement không phân biệt prefix/full-text/substring.
- **Production impact:** Scan lớn khi dataset tăng.
- **Severity:** Medium
- **Recommended fix:** Làm rõ search semantics; cân nhắc prefix search, normalized search columns, full-text search hoặc search engine nếu requirement cần fuzzy/substring quy mô lớn.

### 9. Không validate page/page size

- **Problem:** `Page <= 0` hoặc `PageSize` cực lớn có thể tạo behavior xấu.
- **Why it happens:** Thiếu request validation.
- **Production impact:** Error hoặc query/payload quá lớn.
- **Severity:** Medium
- **Recommended fix:** Enforce `Page >= 1`, `1 <= PageSize <= max`.

## Phiên bản code đề xuất

Một phiên bản offset-pagination hợp lý hơn:

```csharp
public async Task<EmployeeSearchResponse> SearchAsync(
    EmployeeSearchRequest request,
    CancellationToken cancellationToken)
{
    if (request.Page < 1)
        throw new ArgumentOutOfRangeException(nameof(request.Page));

    if (request.PageSize is < 1 or > 200)
        throw new ArgumentOutOfRangeException(nameof(request.PageSize));

    IQueryable<Employee> query = _dbContext.Employees
        .AsNoTracking()
        .Where(x => !x.IsDeleted);

    if (!string.IsNullOrWhiteSpace(request.Keyword))
    {
        var keyword = request.Keyword.Trim();

        query = query.Where(x =>
            x.FullName.Contains(keyword) ||
            x.Email.Contains(keyword));
    }

    if (request.OfficeIds?.Count > 0)
    {
        query = query.Where(x =>
            request.OfficeIds.Contains(x.OfficeId));
    }

    if (request.StatusIds?.Count > 0)
    {
        query = query.Where(x =>
            request.StatusIds.Contains(x.StatusId));
    }

    if (request.CreatedFrom.HasValue)
    {
        query = query.Where(x =>
            x.CreatedAt >= request.CreatedFrom.Value);
    }

    if (request.CreatedTo.HasValue)
    {
        query = query.Where(x =>
            x.CreatedAt <= request.CreatedTo.Value);
    }

    var total = await query.CountAsync(cancellationToken);

    var items = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Skip((request.Page - 1) * request.PageSize)
        .Take(request.PageSize)
        .Select(x => new EmployeeSearchItem
        {
            Id = x.Id,
            FullName = x.FullName,
            Email = x.Email,
            OfficeName = x.Office.Name,
            StatusName = x.Status.Name,
            ManagerName = x.Manager == null
                ? null
                : x.Manager.FullName
        })
        .ToListAsync(cancellationToken);

    return new EmployeeSearchResponse
    {
        Total = total,
        Items = items
    };
}
```

### Lưu ý về keyword search

Đoạn:

```csharp
x.FullName.Contains(keyword)
```

chưa chắc là solution performance tối ưu. Cần dựa vào:

- database provider;
- collation/case sensitivity;
- search semantics;
- data distribution;
- execution plan;
- loại index hiện có.

Nếu business chỉ cần prefix search, có thể thiết kế query/index khác. Nếu cần full-text/fuzzy search trên hàng triệu rows, nên đánh giá full-text search hoặc search infrastructure chuyên biệt.

## Keyset pagination tham khảo

Nếu UI chủ yếu “Next/Previous” và không cần nhảy trực tiếp đến page 5000, keyset pagination có thể ổn định và hiệu quả hơn.

Ví dụ cursor gồm `(CreatedAt, Id)`:

```csharp
query = query
    .Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id < cursor.Id))
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(pageSize);
```

Điều này tránh `Skip` sâu và giảm pagination drift khi có record mới nằm trước cursor.

## Trade-offs

### Offset pagination

**Ưu điểm:**

- Dễ implement.
- Dễ hiển thị page number.
- Cho phép nhảy trực tiếp đến page N.

**Nhược điểm:**

- Deep page có thể chậm.
- Dễ drift khi dataset thay đổi.

### Keyset pagination

**Ưu điểm:**

- Ổn định hơn cho sequential browsing.
- Performance tốt hơn ở page sâu khi index phù hợp.

**Nhược điểm:**

- Khó nhảy trực tiếp đến page bất kỳ.
- Cursor contract phức tạp hơn.

### `CountAsync`

Total count có thể đắt với filter phức tạp trên bảng lớn. Nếu UI không thực sự cần exact total, có thể cân nhắc:

- trả `hasMore`;
- lazy count;
- approximate count tùy business requirement.

Không nên bỏ total chỉ vì performance mà chưa hỏi product requirement.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Hosted service sống lâu; scoped dependencies phải được tạo trong scope phù hợp thay vì giữ lâu dài.
- `DbContext` không phải concurrent unit-of-work dùng chung cho nhiều task.
- Async I/O không cần `Task.Run` chỉ để tạo concurrency.
- Concurrency phải **bounded** và có backpressure/ownership rõ ràng.
- Cancellation cần được propagate xuyên suốt workflow.
- Retry và duplicate execution phải được thiết kế cùng idempotency/business state.
- Trong EF Core, gọi `ToListAsync` quá sớm biến database query thành in-memory processing.
- Filter, projection, sort và pagination nên được push xuống database khi có thể.
- Pagination cần deterministic ordering; offset và keyset có trade-offs khác nhau.
- Performance tuning phải dựa trên generated SQL, execution plan, metrics và workload thật.

## Mẫu tư duy cần nhớ

1. **Define ownership before adding concurrency** — ai tạo task thì phải biết ai await, cancel và observe lỗi của task đó.
2. **Scope state to the unit of work** — `DbContext`, transaction và operation state không nên sống lâu hơn cần thiết.
3. **Bound concurrency before scaling throughput** — throughput không tăng vô hạn theo số task.
4. **Keep queries composable until the database has done its work** — tránh materialize sớm.
5. **Make ordering deterministic before paginating** — pagination correctness bắt đầu từ stable sort key.
