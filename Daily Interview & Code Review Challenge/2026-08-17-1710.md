# Code Review Challenge 1 — Background dispatcher bị mất kiểm soát dưới tải cao

**Chủ đề:** Background jobs, concurrency, async/await, cancellation, resource lifetime, memory/allocation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút

## Bối cảnh

Một hệ thống ASP.NET Core nhận request tạo thông báo từ nhiều module. Để giảm latency của request, team đưa notification vào một `Channel<NotificationCommand>` rồi dùng `BackgroundService` xử lý bất đồng bộ.

Traffic bình thường khoảng 50–100 notification/giây, nhưng khi có chiến dịch hoặc batch import có thể tăng lên 1.500–2.500 notification/giây trong vài phút. Mỗi notification cần:

- Đọc thông tin người nhận từ SQL Server qua EF Core.
- Gọi một provider HTTP để gửi email/push.
- Ghi trạng thái gửi vào database.

Production gần đây xuất hiện các triệu chứng:

- Memory tăng nhanh trong giờ peak.
- Số task đang chạy tăng rất lớn.
- Shutdown deployment đôi khi mất hơn 30 giây nhưng vẫn còn notification chưa hoàn tất.
- Log có `InvalidOperationException` liên quan đến EF Core khi nhiều thao tác chạy đồng thời.
- Khi provider chậm hoặc timeout, API vẫn tiếp tục nhận request bình thường nhưng backlog tăng không giới hạn.
- Một số notification thất bại nhưng không có retry record rõ ràng.

Team đăng ký `NotificationDispatcher` là hosted service, `AppDbContext` là scoped, và muốn giữ kiến trúc đơn giản, chưa muốn đưa RabbitMQ vào nếu chưa thực sự cần.

## Đoạn code cần review

```csharp
public sealed record NotificationCommand(
    Guid NotificationId,
    Guid UserId,
    string Message);

public sealed class NotificationQueue
{
    public Channel<NotificationCommand> Channel { get; } =
        System.Threading.Channels.Channel.CreateUnbounded<NotificationCommand>();

    public ValueTask EnqueueAsync(NotificationCommand command)
        => Channel.Writer.WriteAsync(command);
}

public sealed class NotificationDispatcher : BackgroundService
{
    private readonly NotificationQueue _queue;
    private readonly AppDbContext _dbContext;
    private readonly IHttpClientFactory _httpClientFactory;
    private readonly ILogger<NotificationDispatcher> _logger;

    public NotificationDispatcher(
        NotificationQueue queue,
        AppDbContext dbContext,
        IHttpClientFactory httpClientFactory,
        ILogger<NotificationDispatcher> logger)
    {
        _queue = queue;
        _dbContext = dbContext;
        _httpClientFactory = httpClientFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var command in _queue.Channel.Reader.ReadAllAsync())
        {
            _ = ProcessAsync(command);
        }
    }

    private async Task ProcessAsync(NotificationCommand command)
    {
        try
        {
            var user = await _dbContext.Users
                .SingleAsync(x => x.Id == command.UserId);

            var client = _httpClientFactory.CreateClient("notification-provider");

            var response = await client.PostAsJsonAsync(
                "/send",
                new { user.Email, command.Message });

            if (response.IsSuccessStatusCode)
            {
                var notification = await _dbContext.Notifications
                    .SingleAsync(x => x.Id == command.NotificationId);

                notification.Status = "Sent";
                notification.SentAtUtc = DateTime.UtcNow;
                await _dbContext.SaveChangesAsync();
            }
            else
            {
                _logger.LogError(
                    "Provider failed for notification {NotificationId}: {StatusCode}",
                    command.NotificationId,
                    response.StatusCode);
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Failed to process notification {NotificationId}",
                command.NotificationId);
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Chia sẻ một `AppDbContext` cho nhiều task đồng thời

**Problem:** `NotificationDispatcher` giữ `_dbContext` làm field và dùng nó từ nhiều `ProcessAsync` chạy song song.

**Why it happens:** Hosted service có lifetime dài, trong khi `DbContext` được thiết kế theo unit-of-work ngắn và không thread-safe cho concurrent operations. Việc fire-and-forget hàng loạt task khiến cùng một instance có thể bị sử dụng đồng thời.

**Production impact:** Có thể phát sinh exception kiểu “A second operation was started on this context instance before a previous operation completed”, state tracking bị khó kiểm soát và dữ liệu cập nhật có thể trở nên không đáng tin cậy.

**Severity:** Critical

**Recommended fix:** Không inject trực tiếp scoped `AppDbContext` vào hosted service. Inject `IServiceScopeFactory` hoặc `IDbContextFactory<AppDbContext>`, rồi tạo scope/context riêng cho từng message hoặc từng worker iteration.

### 2. Fire-and-forget `_ = ProcessAsync(command)` tạo concurrency không giới hạn

**Problem:** Consumer loop dequeue càng nhanh càng tốt rồi spawn task không await.

**Why it happens:** `ReadAllAsync()` đọc item nhanh hơn tốc độ xử lý downstream, và mỗi item tạo một task mới ngay lập tức.

**Production impact:** Khi traffic tăng hoặc provider chậm, hàng nghìn task cùng tồn tại, tăng memory, socket pressure, DB connection pressure, ThreadPool continuation work và làm hệ thống dễ rơi vào cascading failure.

**Severity:** Critical

**Recommended fix:** Dùng số lượng worker cố định hoặc `SemaphoreSlim` để giới hạn concurrency. Ví dụ 8–32 worker tùy benchmark và dependency capacity, không chọn con số theo cảm tính.

### 3. `Channel.CreateUnbounded` không có backpressure

**Problem:** Queue trong memory có thể tăng không giới hạn khi producer nhanh hơn consumer.

**Why it happens:** Unbounded channel chấp nhận tiếp item mà không buộc producer chậm lại.

**Production impact:** Backlog vài trăm nghìn item có thể tiêu tốn memory lớn. Nếu process restart, toàn bộ queue in-memory bị mất. API có vẻ “healthy” trong khi hệ thống đã không còn theo kịp throughput thực tế.

**Severity:** High

**Recommended fix:** Dùng bounded channel với capacity xác định và `BoundedChannelFullMode.Wait` nếu chấp nhận áp backpressure. Nếu business không thể block producer hoặc yêu cầu durability, đây là tín hiệu cần chuyển sang persistent queue/broker.

### 4. Không truyền `stoppingToken` vào `ReadAllAsync`

**Problem:** Loop không truyền cancellation token.

**Why it happens:** `ReadAllAsync()` được gọi không tham số.

**Production impact:** Shutdown behavior kém rõ ràng; service có thể tiếp tục chờ queue hoặc xử lý không đúng lifecycle mong muốn.

**Severity:** High

**Recommended fix:** Dùng `ReadAllAsync(stoppingToken)` hoặc worker loop gọi `WaitToReadAsync(stoppingToken)`.

### 5. Cancellation không được propagate vào EF Core và HTTP call

**Problem:** `SingleAsync`, `PostAsJsonAsync`, `SaveChangesAsync` đều không nhận `CancellationToken`.

**Why it happens:** `ProcessAsync` không có token parameter.

**Production impact:** Khi app shutdown hoặc operation đã không còn cần thiết, query/HTTP/database write vẫn tiếp tục chạy, kéo dài graceful shutdown và tiêu tốn connection/resource.

**Severity:** High

**Recommended fix:** `ProcessAsync(command, cancellationToken)` và truyền token xuyên suốt I/O calls.

### 6. Fire-and-forget task không được host theo dõi khi shutdown

**Problem:** `ExecuteAsync` có thể kết thúc nhưng các `ProcessAsync` đã spawn vẫn đang chạy.

**Why it happens:** Task bị bỏ reference và không được await/join.

**Production impact:** Deployment có thể terminate process trước khi task hoàn tất, gây notification ở trạng thái mơ hồ hoặc side effect đã xảy ra nhưng DB chưa cập nhật.

**Severity:** High

**Recommended fix:** Worker loop phải await từng process trong số worker giới hạn, hoặc quản lý tập task đang chạy và chờ drain có timeout rõ ràng khi shutdown.

### 7. Failure chỉ log, không có retry policy hoặc failure state bền vững

**Problem:** Provider trả non-success hoặc exception chỉ được log rồi item biến mất khỏi queue.

**Why it happens:** In-memory queue không có retry/dead-letter semantics mặc định, code cũng không persist attempt state.

**Production impact:** Notification transient failure có thể mất vĩnh viễn. Không thể phân biệt retryable và permanent failure, không có dashboard backlog hoặc attempt count đáng tin cậy.

**Severity:** High

**Recommended fix:** Persist trạng thái `Pending/Processing/Sent/Failed`, `AttemptCount`, `NextAttemptAtUtc`, `LastErrorCode`; retry có giới hạn với backoff và phân loại lỗi. Với side effect bên ngoài, cân nhắc idempotency key nếu provider hỗ trợ hoặc dedup logic nội bộ.

### 8. Response object không được dispose rõ ràng

**Problem:** `HttpResponseMessage` được giữ đến cuối method và không `Dispose()` rõ ràng.

**Why it happens:** Code chỉ kiểm tra `IsSuccessStatusCode`.

**Production impact:** Tùy handler/content, resource của response có thể được giữ lâu hơn cần thiết, đặc biệt ở throughput cao.

**Severity:** Medium

**Recommended fix:** `using var response = await client.PostAsJsonAsync(...)` và chỉ đọc phần content thực sự cần.

### 9. `SingleAsync` làm toàn bộ pipeline fail nếu dữ liệu không tồn tại

**Problem:** User hoặc notification bị xóa/missing dẫn tới exception.

**Why it happens:** Code giả định record luôn tồn tại.

**Production impact:** Một dữ liệu business bất thường bị ghi chung như system failure, khó phân loại và có thể retry vô ích.

**Severity:** Medium

**Recommended fix:** Dùng `SingleOrDefaultAsync`, phân biệt `NotFound/PermanentFailure`, ghi status phù hợp và không retry vô hạn.

### 10. Observability chưa phản ánh queue health

**Problem:** Chỉ log lỗi theo notification, không đo backlog, processing duration, worker saturation hoặc success rate.

**Why it happens:** Observability được thêm ở exception path thay vì thiết kế cùng pipeline.

**Production impact:** Hệ thống có thể backlog nghiêm trọng nhưng API vẫn 200 và dashboard không cảnh báo sớm.

**Severity:** Medium

**Recommended fix:** Theo dõi queue depth, enqueue rate, dequeue rate, active workers, processing latency, success/failure/retry rate, provider latency/status codes và age của item cũ nhất.

## Phiên bản code đề xuất

Ví dụ dưới đây giữ queue in-memory nhưng thêm bounded channel, bounded worker concurrency, scope riêng cho từng item, cancellation và trạng thái failure rõ hơn. Đây là một hướng triển khai, không phải cấu hình tối ưu cho mọi hệ thống.

```csharp
public sealed class NotificationQueue
{
    private readonly Channel<NotificationCommand> _channel;

    public NotificationQueue()
    {
        _channel = Channel.CreateBounded<NotificationCommand>(
            new BoundedChannelOptions(5_000)
            {
                SingleWriter = false,
                SingleReader = false,
                FullMode = BoundedChannelFullMode.Wait
            });
    }

    public ValueTask EnqueueAsync(
        NotificationCommand command,
        CancellationToken cancellationToken)
        => _channel.Writer.WriteAsync(command, cancellationToken);

    public IAsyncEnumerable<NotificationCommand> ReadAllAsync(
        CancellationToken cancellationToken)
        => _channel.Reader.ReadAllAsync(cancellationToken);
}

public sealed class NotificationDispatcher : BackgroundService
{
    private const int WorkerCount = 16;

    private readonly NotificationQueue _queue;
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<NotificationDispatcher> _logger;

    public NotificationDispatcher(
        NotificationQueue queue,
        IServiceScopeFactory scopeFactory,
        ILogger<NotificationDispatcher> logger)
    {
        _queue = queue;
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var workers = Enumerable.Range(0, WorkerCount)
            .Select(_ => RunWorkerAsync(stoppingToken));

        return Task.WhenAll(workers);
    }

    private async Task RunWorkerAsync(CancellationToken stoppingToken)
    {
        await foreach (var command in _queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                await ProcessAsync(command, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                throw;
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Unhandled notification processing failure. NotificationId={NotificationId}",
                    command.NotificationId);
            }
        }
    }

    private async Task ProcessAsync(
        NotificationCommand command,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var clientFactory = scope.ServiceProvider.GetRequiredService<IHttpClientFactory>();

        var user = await db.Users
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == command.UserId,
                cancellationToken);

        var notification = await db.Notifications
            .SingleOrDefaultAsync(
                x => x.Id == command.NotificationId,
                cancellationToken);

        if (user is null || notification is null)
        {
            _logger.LogWarning(
                "Notification skipped because data is missing. NotificationId={NotificationId}, UserId={UserId}",
                command.NotificationId,
                command.UserId);
            return;
        }

        if (notification.Status == "Sent")
            return;

        var client = clientFactory.CreateClient("notification-provider");

        using var response = await client.PostAsJsonAsync(
            "/send",
            new
            {
                notificationId = command.NotificationId,
                user.Email,
                command.Message
            },
            cancellationToken);

        if (response.IsSuccessStatusCode)
        {
            notification.Status = "Sent";
            notification.SentAtUtc = DateTime.UtcNow;
            notification.LastError = null;
        }
        else
        {
            notification.Status = "Failed";
            notification.AttemptCount += 1;
            notification.LastError = $"HTTP {(int)response.StatusCode}";
        }

        await db.SaveChangesAsync(cancellationToken);
    }
}
```

## Trade-offs

- **Bounded in-memory queue** đơn giản, latency thấp và phù hợp nếu mất một số pending work khi process crash là chấp nhận được hoặc source có thể replay. Đổi lại, nó không durability.
- **Backpressure** bảo vệ process nhưng có thể làm request producer chậm hoặc timeout. Cần quyết định business behavior khi queue full.
- **Fixed worker count** dễ kiểm soát nhưng phải benchmark theo DB/provider capacity. Tăng worker không đồng nghĩa throughput tăng mãi.
- Nếu notification **không được phép mất**, hoặc cần retry/dedup/dead-letter bền vững, persistent broker hoặc database-backed work queue sẽ phù hợp hơn.
- Nếu side effect bên ngoài có thể thành công nhưng process chết trước khi DB commit, cần idempotency/dedup strategy thay vì giả định exactly-once.

## Cách kiểm thử

1. **Load test/backpressure:** bơm traffic cao hơn throughput consumer trong vài phút; xác nhận memory không tăng vô hạn và producer chịu backpressure theo thiết kế.
2. **Concurrency test:** chạy nhiều worker đồng thời và xác nhận không còn lỗi shared `DbContext`, không cập nhật chéo state.
3. **Shutdown test:** bắt đầu nhiều notification với provider cố tình chậm, gửi shutdown signal và xác nhận graceful cancellation/drain behavior đúng policy.
4. **Failure-path test:** provider trả 429/500/timeout; xác nhận status, attempt count, retry classification và logs/metrics chính xác.
5. **Crash/restart test:** kill process khi backlog còn lớn để chứng minh rõ giới hạn của in-memory queue; dùng kết quả này để quyết định có cần durable broker hay không.

# Code Review Challenge 2 — Bulk status update gây partial data và lock amplification

**Chủ đề:** EF Core transaction handling, SQL performance, correctness, concurrency, error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một API nội bộ cho phép admin đóng hàng loạt `Timesheet` đã quá hạn. Mỗi request có thể chứa từ vài chục đến 5.000 `timesheetIds`. Business rule:

- Chỉ timesheet đang ở trạng thái `Submitted` mới được chuyển sang `Closed`.
- Nếu một timesheet không tồn tại hoặc đã bị user chỉnh sửa sang trạng thái khác, API phải báo rõ số item thành công/thất bại.
- Không được để trạng thái database rơi vào tình huống khó giải thích nếu request bị hủy giữa chừng.
- Một scheduled job khác cũng có thể cập nhật cùng bảng trong thời điểm đó.

Production cho thấy batch lớn mất vài phút, database có lock wait cao và thỉnh thoảng API trả 500 sau khi đã cập nhật được một phần dữ liệu. Khi client retry cùng payload, một số record bị update nhiều lần về mặt audit timestamp.

## Đoạn code cần review

```csharp
public sealed class TimesheetService
{
    private readonly AppDbContext _dbContext;
    private readonly ILogger<TimesheetService> _logger;

    public TimesheetService(
        AppDbContext dbContext,
        ILogger<TimesheetService> logger)
    {
        _dbContext = dbContext;
        _logger = logger;
    }

    public async Task<int> CloseTimesheetsAsync(
        IReadOnlyCollection<Guid> timesheetIds,
        Guid adminUserId,
        CancellationToken cancellationToken)
    {
        var closedCount = 0;

        foreach (var id in timesheetIds)
        {
            var timesheet = await _dbContext.Timesheets
                .SingleOrDefaultAsync(x => x.Id == id);

            if (timesheet is null)
                continue;

            if (timesheet.Status != "Submitted")
                continue;

            timesheet.Status = "Closed";
            timesheet.ClosedAtUtc = DateTime.UtcNow;
            timesheet.ClosedByUserId = adminUserId;

            await _dbContext.SaveChangesAsync();
            closedCount++;

            _logger.LogInformation(
                "Closed timesheet {TimesheetId} by {AdminUserId}",
                id,
                adminUserId);
        }

        return closedCount;
    }
}
```

## Kết quả code review tham khảo

### 1. `SaveChangesAsync` trong mỗi vòng lặp gây partial commit không kiểm soát

**Problem:** Mỗi timesheet được commit riêng.

**Why it happens:** Không có explicit transaction bao phủ batch, và mỗi `SaveChangesAsync` tạo transaction riêng cho lần save đó khi cần.

**Production impact:** Nếu request lỗi/cancel ở item thứ 2.000, 1.999 item trước có thể đã commit. Client chỉ nhận 500 và không biết chính xác trạng thái batch nếu API không trả result chi tiết.

**Severity:** Critical

**Recommended fix:** Trước tiên xác định business semantics. Nếu cần all-or-nothing, dùng transaction cho toàn batch. Nếu cho phép partial success, phải thiết kế result per item rõ ràng và xử lý chunk/commit boundary có chủ đích, không để partial commit xảy ra ngẫu nhiên.

### 2. N+1 query và N lần save round-trip

**Problem:** Mỗi ID thực hiện query riêng và có thể thêm một `SaveChanges` riêng.

**Why it happens:** Batch được xử lý như nhiều request đơn lẻ.

**Production impact:** Với 5.000 IDs có thể tạo hàng nghìn round-trip, latency tăng mạnh, tăng load SQL Server/PostgreSQL và chiếm connection lâu hơn.

**Severity:** High

**Recommended fix:** Query theo batch bằng `Contains`/join với collection phù hợp, chunk nếu danh sách rất lớn hoặc provider/database có giới hạn thực tế. Sau đó save theo batch/chunk thay vì từng row.

### 3. Cancellation token không được truyền vào query và save

**Problem:** Method nhận `cancellationToken` nhưng không dùng.

**Why it happens:** Async calls dùng overload không token.

**Production impact:** Client đã hủy request nhưng server vẫn tiếp tục chạy nhiều query/update, làm lãng phí database resource và khiến partial result khó hiểu hơn.

**Severity:** High

**Recommended fix:** Truyền token vào `SingleOrDefaultAsync`, `SaveChangesAsync` và các operation khác. Đồng thời transaction semantics phải giải thích rõ khi cancellation xảy ra.

### 4. Race condition giữa read-check-write

**Problem:** Code đọc `Status == Submitted`, sau đó mutate entity và save nhưng không có concurrency guard business-specific.

**Why it happens:** Có khoảng thời gian giữa query và update; process khác có thể thay đổi row.

**Production impact:** Có thể overwrite thay đổi mới hơn hoặc đóng record mà business không còn cho phép đóng tại thời điểm write.

**Severity:** High

**Recommended fix:** Dùng optimistic concurrency token (`rowversion`/version column) hoặc conditional update `WHERE Id = ... AND Status = 'Submitted'`. Nếu affected rows = 0, classify item là conflict/not-updated thay vì giả định success.

### 5. API chỉ trả `closedCount`, không trả nguyên nhân thất bại

**Problem:** Missing record và wrong status đều silently skipped.

**Why it happens:** Service coi mọi non-success như không đáng báo.

**Production impact:** Admin không biết item nào thất bại vì missing, conflict hay trạng thái không hợp lệ; retry khó làm đúng.

**Severity:** High

**Recommended fix:** Trả structured result gồm `ClosedIds`, `NotFoundIds`, `InvalidStatusIds`, `ConflictIds` hoặc aggregate counts kèm correlation/batch id nếu payload quá lớn.

### 6. Timestamp `DateTime.UtcNow` gọi per item và retry làm audit thay đổi

**Problem:** Mỗi row có timestamp khác nhau và retry có thể ghi lại `ClosedAtUtc` nếu logic không đủ idempotent.

**Why it happens:** Không xác định rõ idempotency semantics cho operation “close”.

**Production impact:** Audit trail khó hiểu; cùng một batch retry có thể làm timestamp bị thay đổi nếu trạng thái/rules cho phép update lại.

**Severity:** Medium

**Recommended fix:** Capture `now` một lần cho batch hoặc chunk. Chỉ update record đang `Submitted`; record đã `Closed` không nên mutate lại nếu request được retry.

### 7. Tracking nhiều entity có thể làm tăng memory và change-detection cost

**Problem:** Nếu sửa theo hướng load toàn bộ 5.000 entity tracked rồi save một lần, vẫn cần cân nhắc memory/change tracker cost.

**Why it happens:** EF Core tracking giữ state của entity trong context.

**Production impact:** Batch rất lớn làm context nặng, đặc biệt nếu entity graph lớn hoặc context đã track nhiều thứ khác.

**Severity:** Medium

**Recommended fix:** Projection chỉ field cần thiết, chunk batch, context lifetime ngắn; nếu phù hợp version/provider, có thể dùng set-based update/SQL có điều kiện thay vì materialize entity. Không giả định một API cụ thể nếu chưa xác nhận version EF Core đang dùng.

### 8. Logging mỗi item ở Information có thể tạo log volume lớn

**Problem:** Batch 5.000 item tạo 5.000 info logs.

**Why it happens:** Log được thiết kế theo row thay vì theo batch.

**Production impact:** Tăng chi phí log, khó tìm signal quan trọng, có thể ảnh hưởng throughput nếu sink chậm.

**Severity:** Medium

**Recommended fix:** Log summary theo batch và chỉ log per-item khi cần debug/audit chuyên biệt. Audit business quan trọng nên có storage/schema phù hợp thay vì dựa hoàn toàn vào application log.

## Phiên bản code đề xuất

Ví dụ dưới đây chọn **partial-success có kiểm soát**, vì requirement yêu cầu báo rõ thành công/thất bại từng nhóm. Batch được chunk để giảm round-trip và tránh context quá lớn. Concurrency được kiểm tra lại thông qua version token giả định `RowVersion` trên entity. Nếu hệ thống chưa có concurrency token, có thể thay bằng conditional set-based update phù hợp database/provider.

```csharp
public sealed record CloseTimesheetsResult(
    IReadOnlyList<Guid> ClosedIds,
    IReadOnlyList<Guid> NotFoundIds,
    IReadOnlyList<Guid> InvalidStatusIds,
    IReadOnlyList<Guid> ConflictIds);

public sealed class TimesheetService
{
    private const int ChunkSize = 500;

    private readonly IDbContextFactory<AppDbContext> _dbContextFactory;
    private readonly ILogger<TimesheetService> _logger;

    public TimesheetService(
        IDbContextFactory<AppDbContext> dbContextFactory,
        ILogger<TimesheetService> logger)
    {
        _dbContextFactory = dbContextFactory;
        _logger = logger;
    }

    public async Task<CloseTimesheetsResult> CloseTimesheetsAsync(
        IReadOnlyCollection<Guid> timesheetIds,
        Guid adminUserId,
        CancellationToken cancellationToken)
    {
        var requestedIds = timesheetIds.Distinct().ToArray();
        var closed = new List<Guid>();
        var notFound = new List<Guid>();
        var invalidStatus = new List<Guid>();
        var conflicts = new List<Guid>();
        var now = DateTime.UtcNow;

        foreach (var chunk in requestedIds.Chunk(ChunkSize))
        {
            cancellationToken.ThrowIfCancellationRequested();

            await using var db = await _dbContextFactory
                .CreateDbContextAsync(cancellationToken);

            var entities = await db.Timesheets
                .Where(x => chunk.Contains(x.Id))
                .ToListAsync(cancellationToken);

            var byId = entities.ToDictionary(x => x.Id);

            foreach (var id in chunk)
            {
                if (!byId.TryGetValue(id, out var entity))
                {
                    notFound.Add(id);
                    continue;
                }

                if (entity.Status != "Submitted")
                {
                    invalidStatus.Add(id);
                    continue;
                }

                entity.Status = "Closed";
                entity.ClosedAtUtc = now;
                entity.ClosedByUserId = adminUserId;
            }

            try
            {
                await db.SaveChangesAsync(cancellationToken);

                closed.AddRange(
                    entities
                        .Where(x => x.Status == "Closed" && x.ClosedAtUtc == now)
                        .Select(x => x.Id));
            }
            catch (DbUpdateConcurrencyException ex)
            {
                foreach (var entry in ex.Entries)
                {
                    if (entry.Entity is Timesheet timesheet)
                        conflicts.Add(timesheet.Id);
                }

                _logger.LogWarning(
                    ex,
                    "Concurrency conflict while closing timesheets. ConflictCount={ConflictCount}",
                    conflicts.Count);
            }
        }

        _logger.LogInformation(
            "Close timesheets completed. Requested={Requested}, Closed={Closed}, NotFound={NotFound}, InvalidStatus={InvalidStatus}, Conflicts={Conflicts}, AdminUserId={AdminUserId}",
            requestedIds.Length,
            closed.Count,
            notFound.Count,
            invalidStatus.Count,
            conflicts.Count,
            adminUserId);

        return new CloseTimesheetsResult(
            closed,
            notFound,
            invalidStatus,
            conflicts);
    }
}
```

Lưu ý: implementation trên minh họa trade-off và giả định entity có concurrency token được cấu hình đúng. Trong hệ thống production, cách xử lý `DbUpdateConcurrencyException` cần cẩn thận hơn: một exception trên chunk có thể khiến ta phải reload/reevaluate từng entry hoặc retry chunk theo policy thay vì coi những entity còn lại chắc chắn đã commit.

Một hướng mạnh hơn cho batch lớn là dùng **conditional set-based update** theo chunk, ví dụ update chỉ row có `Status = Submitted`, sau đó đọc/đối chiếu affected rows để phân loại. Cách này giảm tracking và round-trip, nhưng implementation phụ thuộc EF Core version/provider và yêu cầu audit/result chi tiết đến đâu.

## Trade-offs

- **Một transaction cho toàn bộ 5.000 rows:** dễ đạt all-or-nothing nhưng giữ lock lâu hơn, rollback lớn hơn và tăng contention. Phù hợp nếu business bắt buộc atomic toàn batch.
- **Transaction theo chunk:** giảm blast radius và lock duration, nhưng tạo partial success có chủ đích. API phải trả result rõ ràng và client phải hiểu semantics.
- **Set-based update:** hiệu quả hơn nhiều khi chỉ cần cập nhật điều kiện đơn giản, nhưng khó trả lý do per-row nếu không thiết kế thêm bước classify.
- **Optimistic concurrency:** tránh lock dài nhưng client/service phải xử lý conflict như một outcome bình thường.
- **Pessimistic locking:** có thể phù hợp cho một số invariant nghiêm ngặt nhưng tăng contention/deadlock risk; không nên chọn mặc định.

## Cách kiểm thử

1. **Database integration test:** 5.000 IDs gồm valid, missing, wrong-status; xác nhận counts và danh sách outcome đúng.
2. **Concurrency test:** scheduled job đổi status của một subset ngay giữa batch; xác nhận conflict được phát hiện, không silently overwrite.
3. **Cancellation test:** cancel giữa các chunk; xác nhận chunk đã commit được báo/trace rõ, chunk chưa xử lý không bị mutate.
4. **Load/locking test:** chạy nhiều batch song song với scheduled job; đo lock wait, deadlock, transaction duration và DB CPU.
5. **Retry/idempotency test:** gửi lại cùng payload sau khi một số item đã `Closed`; xác nhận audit timestamp không bị ghi lại ngoài ý muốn và outcome dễ hiểu.

## Quan sát trong production

Nên theo dõi:

- Batch size và processing duration.
- Rows requested/closed/not-found/invalid/conflict.
- DB round-trip count nếu tracing cho phép.
- SQL duration, lock waits, deadlocks và blocked sessions.
- `DbUpdateConcurrencyException` rate.
- Cancellation rate.
- Số batch vượt SLA.
- Structured log theo `BatchId`, `AdminUserId`, outcome counts; không log danh sách hàng nghìn IDs ở Information nếu không cần.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Hosted service cần quản lý concurrency, DI scope, cancellation và shutdown semantics một cách có chủ đích.
- Queue in-memory không chỉ là cấu trúc dữ liệu; bounded/unbounded quyết định backpressure và failure behavior của cả hệ thống.
- `DbContext` không nên bị chia sẻ cho nhiều concurrent operation.
- Batch update cần xác định rõ atomicity, partial-success semantics và concurrency strategy trước khi tối ưu query.
- Giảm round-trip SQL là quan trọng, nhưng correctness và observability phải được giữ nguyên hoặc tốt hơn sau tối ưu.

## Mẫu tư duy cần nhớ

- **Bound concurrency before increasing throughput.**
- **Design backpressure before peak traffic arrives.**
- **Define transaction semantics before moving `SaveChanges`.**
- **Treat cancellation as part of correctness, not only performance.**
- **Measure queue age, lock waits and conflicts—not only request latency.**
