# Code Review Challenge 1 — Optimizely CMS cache trả nội dung sai giữa các market và làm origin quá tải sau publish

**Chủ đề:** C#/.NET, ASP.NET Core, Optimizely CMS, caching, Akamai/CDN, content delivery, concurrency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một marketing website dùng Optimizely CMS trên ASP.NET Core. Website phục vụ nhiều market và language, ví dụ `vi-VN`, `en-US`, `en-GB`. Nội dung product landing page được editor publish thường xuyên. Một số block có nội dung khác nhau theo market và language.

Ứng dụng chạy nhiều instances phía sau Akamai. Team muốn giảm tải CMS nên thêm `IMemoryCache` vào service render page. Production xuất hiện hai triệu chứng: đôi lúc user ở market UK thấy nội dung/CTA của US; sau một đợt publish lớn, origin CPU tăng mạnh và nhiều request đồng thời cùng truy vấn CMS. Editor cũng phản ánh nội dung vừa publish có lúc phải chờ đến 15 phút mới xuất hiện.

Akamai đang cache HTML theo URL. URL hiện tại không phải lúc nào cũng chứa market; market có thể được xác định từ cookie/header sau khi request vào application. Không có cơ chế invalidation cache ứng dụng gắn với content publish event.

## Đoạn code cần review

```csharp
public sealed class LandingPageService
{
    private readonly IContentLoader _contentLoader;
    private readonly IMemoryCache _cache;
    private readonly ILogger<LandingPageService> _logger;

    public LandingPageService(
        IContentLoader contentLoader,
        IMemoryCache cache,
        ILogger<LandingPageService> logger)
    {
        _contentLoader = contentLoader;
        _cache = cache;
        _logger = logger;
    }

    public async Task<LandingPageViewModel> GetAsync(
        ContentReference pageReference,
        string market,
        CultureInfo culture,
        CancellationToken cancellationToken)
    {
        var key = $"landing:{pageReference.ID}";

        if (_cache.TryGetValue(key, out LandingPageViewModel? cached))
            return cached!;

        var page = _contentLoader.Get<LandingPage>(pageReference, culture);

        var blocks = new List<LandingBlockViewModel>();

        foreach (var blockReference in page.MainContentArea.FilteredItems)
        {
            var block = _contentLoader.Get<IContent>(
                blockReference.ContentLink,
                culture);

            blocks.Add(MapBlock(block, market));
        }

        var model = new LandingPageViewModel
        {
            Title = page.Title,
            Market = market,
            Culture = culture.Name,
            Blocks = blocks
        };

        _cache.Set(
            key,
            model,
            TimeSpan.FromMinutes(15));

        _logger.LogInformation(
            "Rendered landing page {PageId} for {Market} {Culture}",
            pageReference.ID,
            market,
            culture.Name);

        await Task.CompletedTask;
        return model;
    }
}
```

## Kết quả code review tham khảo

### Critical — Cache key bỏ qua market và culture

**Vấn đề:** `landing:{pageReference.ID}` dùng chung cho mọi market/language dù output phụ thuộc cả `market` và `culture`.  
**Tại sao xảy ra:** Cache identity không phản ánh toàn bộ input tạo ra `LandingPageViewModel`. Request đầu tiên populate cache sẽ quyết định nội dung mà request sau nhận.  
**Ảnh hưởng production:** User có thể nhận sai language, CTA, nội dung hoặc commercial messaging của market khác. Đây là correctness boundary, không chỉ là stale cache.  
**Cách sửa:** Cache key phải chứa normalized content identity + market + culture + các dimension khác thực sự ảnh hưởng output. Nếu personalization phức tạp hơn, cần cân nhắc không cache full rendered model ở tầng này.

### Critical — CDN cache public HTML nhưng market phụ thuộc cookie/header không nằm trong edge cache identity

**Vấn đề:** Response được đánh dấu `public,max-age=900` trong khi HTML thay đổi theo cookie/header.  
**Tại sao xảy ra:** Akamai có thể coi cùng URL là cùng object nếu cache configuration không vary/partition theo dimension tương ứng.  
**Ảnh hưởng production:** Một response dành cho một market có thể được edge phục vụ cho market khác trước cả khi request vào application.  
**Cách sửa:** Thiết kế canonical URL/cache key để market/language là deterministic ở edge, ví dụ route/host rõ ràng; hoặc cấu hình edge variation có kiểm soát. Nếu response thực sự personalized, không đánh dấu public cache một cách rộng rãi. Không thêm `Vary` tùy tiện với high-cardinality headers mà chưa đánh giá cache efficiency.

### High — Không invalidation khi content được publish

**Vấn đề:** Content mới phải chờ TTL hết hạn.  
**Tại sao xảy ra:** Cache lifecycle độc lập với CMS content lifecycle.  
**Ảnh hưởng production:** Editor publish thành công nhưng user vẫn thấy nội dung cũ tới 15 phút; rollback/hotfix content cũng bị trì hoãn.  
**Cách sửa:** Gắn invalidation với content publish/change events hoặc dependency/version token phù hợp với CMS architecture. Purge edge cache theo đúng URL/surrogate key khi cần. TTL chỉ là safety bound, không nên là cơ chế freshness duy nhất nếu requirement yêu cầu publish gần real-time.

### High — Cache stampede sau expiry/restart/purge

**Vấn đề:** Nhiều request miss cùng key đều render cùng page đồng thời.  
**Tại sao xảy ra:** `TryGetValue` rồi compute rồi `Set` không có single-flight/per-key coordination.  
**Ảnh hưởng production:** Sau deploy/purge/popular-page expiry, origin CPU và CMS reads tăng đột biến; chính cache lại tạo synchronized load spike.  
**Cách sửa:** Dùng per-key single-flight/async lazy strategy phù hợp, hoặc cache abstraction hỗ trợ stampede protection. Lock phải scoped theo key và không biến thành global serialization. Với multi-instance, local single-flight chỉ bảo vệ từng instance; cần đánh giá edge cache/distributed strategy nếu herd xuyên nhiều instances là vấn đề thực tế.

### High — Content reads đồng bộ nằm trên request path

**Vấn đề:** Method được khai báo `async` nhưng content loading thực tế là synchronous; `Task.CompletedTask` không biến I/O/work thành async.  
**Tại sao xảy ra:** Async signature tạo cảm giác request path non-blocking nhưng không thay đổi behavior của API đồng bộ được gọi bên trong.  
**Ảnh hưởng production:** Nếu content resolution hoặc downstream work block đáng kể, concurrency cao có thể tăng request threads/latency. Tuy nhiên không được tự động bọc bằng `Task.Run` trong web request để “fix async”.  
**Cách sửa:** Dùng API phù hợp với CMS/runtime nếu có và cần; nếu API là sync/in-memory optimized thì giữ semantics rõ ràng và đo trước. Không giả lập async bằng `Task.CompletedTask`.

### Medium — CancellationToken không kiểm soát content-loading work

**Vấn đề:** Token được truyền vào service nhưng không được sử dụng trong các content reads.  
**Tại sao xảy ra:** API đang gọi không nhận token.  
**Ảnh hưởng production:** Client abort không nhất thiết dừng phần render đang chạy; dưới load có thể tiếp tục tiêu tốn tài nguyên.  
**Cách sửa:** Propagate cancellation tới các operation hỗ trợ nó; kiểm tra token ở boundary hợp lý cho CPU/loop work nếu có lợi. Không tuyên bố cancellation guarantee cho API đồng bộ không hỗ trợ cancellation.

### Medium — Cache size/lifetime không có policy rõ

**Vấn đề:** Cache entry không có size policy và cardinality sẽ tăng khi thêm market/culture dimension.  
**Tại sao xảy ra:** Thiết kế cache chỉ nghĩ theo TTL.  
**Ảnh hưởng production:** Nhiều page × market × language có thể làm memory tăng và eviction khó dự đoán.  
**Cách sửa:** Đo working set/cache cardinality, đặt size/eviction policy phù hợp hoặc dùng cache abstraction có quota. Không chuyển ngay sang Redis nếu chưa có evidence rằng cross-instance cache mang lại lợi ích lớn hơn complexity.

### Medium — `Accept-Language` được dùng trực tiếp như một culture name

**Vấn đề:** HTTP `Accept-Language` có thể chứa danh sách và quality values, không nhất thiết là một giá trị culture đơn.  
**Tại sao xảy ra:** Header parsing bị giản lược.  
**Ảnh hưởng production:** Request hợp lệ có thể lỗi hoặc chọn culture sai.  
**Cách sửa:** Dùng ASP.NET Core localization/request-culture infrastructure hoặc parser/policy rõ ràng, allow-list các culture được hỗ trợ và fallback deterministic.

### Medium — Logging không cho biết cache behavior

**Vấn đề:** Chỉ log khi render, không có metric cache hit/miss, render duration, invalidation/purge outcome.  
**Tại sao xảy ra:** Observability không được thiết kế cùng caching.  
**Ảnh hưởng production:** Khó chứng minh origin spike do stampede, cache-key mismatch hay CDN miss.  
**Cách sửa:** Metric theo cache layer: hit ratio, miss, render latency, invalidation count/failure, edge cache status, origin request rate. Tránh high-cardinality dimensions không kiểm soát.

### Low — N+1-style content loading cần được đo và tối ưu theo CMS API

**Vấn đề:** Mỗi content-area item được load riêng trong loop.  
**Tại sao xảy ra:** Code map từng reference độc lập.  
**Ảnh hưởng production:** Với page nhiều block, có thể tăng lookup overhead tùy content-loader/cache behavior.  
**Cách sửa:** Nếu profiling chứng minh đây là bottleneck, dùng batch-loading API/pattern phù hợp với Optimizely version và content semantics. Không tối ưu mù vì CMS có caching nội bộ.

## Phiên bản đề xuất

```csharp
public sealed class LandingPageService
{
    private readonly IContentLoader _contentLoader;
    private readonly IMemoryCache _cache;
    private readonly KeyedSemaphore _singleFlight;

    public LandingPageService(
        IContentLoader contentLoader,
        IMemoryCache cache,
        KeyedSemaphore singleFlight)
    {
        _contentLoader = contentLoader;
        _cache = cache;
        _singleFlight = singleFlight;
    }

    public async Task<LandingPageViewModel> GetAsync(
        ContentReference pageReference,
        string market,
        CultureInfo culture,
        CancellationToken cancellationToken)
    {
        var normalizedMarket = NormalizeMarket(market);
        var normalizedCulture = NormalizeSupportedCulture(culture);
        var key = $"landing:{pageReference.ID}:{normalizedMarket}:{normalizedCulture.Name}";

        if (_cache.TryGetValue(key, out LandingPageViewModel? cached))
            return cached!;

        await using var lease = await _singleFlight.AcquireAsync(
            key, cancellationToken);

        if (_cache.TryGetValue(key, out cached))
            return cached!;

        cancellationToken.ThrowIfCancellationRequested();

        var page = _contentLoader.Get<LandingPage>(
            pageReference,
            normalizedCulture);

        var blocks = page.MainContentArea.FilteredItems
            .Select(item => _contentLoader.Get<IContent>(
                item.ContentLink,
                normalizedCulture))
            .Select(block => MapBlock(block, normalizedMarket))
            .ToArray();

        var model = new LandingPageViewModel
        {
            Title = page.Title,
            Market = normalizedMarket,
            Culture = normalizedCulture.Name,
            Blocks = blocks
        };

        _cache.Set(key, model, new MemoryCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(15),
            Size = EstimateCacheUnits(model)
        });

        return model;
    }
}
```

Phần trên minh họa cache identity và per-key single-flight; `KeyedSemaphore`, `NormalizeMarket`, `NormalizeSupportedCulture` và `EstimateCacheUnits` là application abstractions cần implement/test, không phải Optimizely APIs.

Publish pipeline cần invalidate các application cache keys liên quan đến content đã thay đổi và purge đúng edge objects. Nếu page composition phụ thuộc nested blocks, dependency tracking phải bao gồm block/content dependencies thay vì chỉ page ID. Edge strategy nên ưu tiên URL/host có market/language rõ ràng nếu business routing cho phép, vì nó giúp cache identity deterministic hơn cookie-based variation.

## Giải thích thiết kế sau khi sửa

Cache key phải đại diện cho output identity. Single-flight giảm duplicate render trong một instance, nhưng không được hiểu là distributed lock. Freshness được nối với content lifecycle thay vì chỉ dựa TTL. CDN và application cache phải chia sẻ cùng semantics về variation; nếu edge không biết market dimension thì application cache đúng vẫn không cứu được response đã bị cache sai ở edge.

## Trade-offs

Thêm market/culture vào key tăng cardinality và giảm hit ratio. Publish-driven invalidation tăng coupling với CMS event lifecycle và cần xử lý nested content dependencies. Purge CDN quá rộng có thể gây origin spike; purge quá hẹp có thể để stale content. Distributed cache có thể tăng consistency giữa instances nhưng thêm network dependency, serialization và failure mode; chỉ dùng khi evidence/requirements biện minh.

## Cách kiểm thử

1. **Integration test:** cùng page ID nhưng khác market/culture phải trả đúng model và không dùng nhầm cache entry.
2. **Concurrency/load test:** hàng trăm request cùng miss một popular page; đo số lần render/content load thực tế và origin latency.
3. **Publish invalidation test:** publish/update nested block rồi xác minh application cache và edge purge workflow làm nội dung mới xuất hiện theo freshness SLO.
4. **E2E/CDN test:** cùng URL với các market/language combinations; kiểm tra Akamai cache key/status và không cross-market leakage.
5. **Failure-path test:** purge/invalidation thất bại hoặc một instance restart; hệ thống vẫn phục vụ đúng và telemetry chỉ rõ stale-risk window.

## Quan sát trong production

Theo dõi cache hit/miss theo layer, render duration, CMS content-load count, application memory/GC, origin request rate, Akamai cache hit ratio/cache status, invalidation/purge success/failure, publish-to-visible latency và p95/p99 page latency. Correlate content ID/version với deployment/trace nhưng tránh labels có cardinality không kiểm soát.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một block được dùng trên 500 pages, bạn thiết kế dependency invalidation thế nào để không purge toàn site?
2. Khi nào Redis/distributed cache thực sự tốt hơn per-instance memory cache trong kiến trúc này?
3. Nếu business bắt buộc market selection bằng cookie trên cùng URL, bạn sẽ thiết kế CDN caching ra sao để vừa đúng vừa giữ hit ratio hợp lý?

# Code Review Challenge 2 — CI/CD chạy database migration trước deployment làm release không thể rollback an toàn

## Bối cảnh

Một ASP.NET Core e-commerce API được build bằng TeamCity và release qua Octopus Deploy tới 6 application instances. Database SQL Server dùng chung cho tất cả instances. Team muốn tự động hóa EF Core migration và thêm script PowerShell dưới đây vào release process.

Release gần đây thêm cột `DisplayName` thay cho `Name`. Migration rename/drop schema được chạy trước khi application instances được rolling update. Trong khoảng vài phút, old version và new version cùng tồn tại. Một instance mới fail health check nên Octopus rollback application package về version cũ, nhưng database vẫn ở schema mới. Sau đó một phần request trả 500.

Pipeline hiện tại cho phép nhiều production releases được bấm gần nhau nếu hai hotfix cùng cần triển khai.

## Kết quả code review tham khảo

### Critical — Secret production bị hard-code và in ra log

**Vấn đề:** Connection string chứa privileged credential trong script và được `Write-Host`.  
**Tại sao xảy ra:** Secret management bị trộn với release definition.  
**Ảnh hưởng production:** Credential có thể rò qua source control, build/release logs hoặc operator access; dùng `sa` làm blast radius rất lớn.  
**Cách sửa:** Lấy secret từ protected Octopus variable/secret store hoặc identity mechanism phù hợp; không log secret; dùng least-privileged migration identity tách khỏi runtime identity nếu operational model cho phép.

### Critical — Destructive schema change chạy trước rolling deployment

**Vấn đề:** Rename `Name` và drop `LegacyCategoryCode` trước khi old instances ngừng dùng schema cũ.  
**Tại sao xảy ra:** Database là shared mutable state nhưng migration không backward-compatible với old binary.  
**Ảnh hưởng production:** Trong mixed-version window, old instances có thể lỗi query/runtime; rollback binary về old version vẫn lỗi vì schema đã contract.  
**Cách sửa:** Dùng expand/contract. Release A thêm `DisplayName` nullable/compatible nhưng giữ `Name`; deploy code có thể đọc/write theo transition strategy; backfill/verify; release sau chuyển hoàn toàn; chỉ drop/rename legacy sau khi không còn binary phụ thuộc và rollback window đã đóng.

### High — Application rollback không rollback được database semantics

**Vấn đề:** Pipeline giả định package rollback đủ để phục hồi release.  
**Tại sao xảy ra:** Schema/data migrations có thể destructive hoặc data-transforming, và `Down()` không đảm bảo đảo ngược dữ liệu đã mất.  
**Ảnh hưởng production:** Rollback tạo binary/schema mismatch hoặc mất dữ liệu.  
**Cách sửa:** Thiết kế migration forward-compatible và ưu tiên roll-forward. Xác định trước rollback matrix: version N/N+1 của app tương thích với schema nào; backup/restore là disaster-recovery mechanism chứ không phải default per-release rollback.

### High — Không serialize migration execution giữa concurrent releases

**Vấn đề:** Hai production releases có thể chạy migration gần nhau trên cùng DB.  
**Tại sao xảy ra:** Không có environment-level deployment lock/single migration owner.  
**Ảnh hưởng production:** Race giữa schema versions, migration history conflicts, blocking hoặc một release deploy binary không khớp schema cuối cùng.  
**Cách sửa:** Serialize production database migration stage theo environment/database. Một release phải sở hữu migration transition; release orchestration phải ngăn overlapping incompatible deployments.

### High — Retry migration vô điều kiện và không kiểm tra lần retry

**Vấn đề:** Bất kỳ failure nào cũng retry sau 5 giây, rồi pipeline tiếp tục mà không kiểm tra exit code lần hai.  
**Tại sao xảy ra:** Không phân loại transient/non-transient failure và không fail closed.  
**Ảnh hưởng production:** Migration lỗi do SQL/schema/code vẫn có thể dẫn đến deploy application mới trên schema cũ/partial state.  
**Cách sửa:** Migration failure phải dừng release trừ khi retry policy chỉ áp dụng lỗi transient đã xác định; mọi attempt phải kiểm tra kết quả. Ghi telemetry sanitized và yêu cầu intervention khi state không rõ.

### High — Runtime `dotnet ef database update` phụ thuộc source/tooling thay vì migration artifact được kiểm soát

**Vấn đề:** Production release chạy EF CLI từ project/startup project.  
**Tại sao xảy ra:** Migration execution phụ thuộc tool/version/source layout của deployment agent.  
**Ảnh hưởng production:** Khó audit chính xác SQL sẽ chạy, tool mismatch và artifact drift giữa build/release.  
**Cách sửa:** Build immutable migration artifact ở CI, ví dụ reviewed SQL script/idempotent script hoặc migration bundle phù hợp với EF Core version/process của team; promote cùng release metadata và kiểm tra checksum/version. Lựa chọn artifact cụ thể cần theo version/support policy hiện hành.

### Medium — Không có health gate giữa từng deployment batch

**Vấn đề:** Script restart tuần tự nhưng không chờ readiness/health và smoke test trước target tiếp theo.  
**Tại sao xảy ra:** `Restart-Service` được coi như deployment success.  
**Ảnh hưởng production:** Broken version có thể lan qua toàn bộ fleet trước khi phát hiện.  
**Cách sửa:** Rolling/canary batches với health gate, API smoke test và error-rate/latency check; dừng rollout khi threshold vi phạm.

### Medium — Artifact identity không immutable trong script

**Vấn đề:** `Commerce.Api.zip` không thể hiện version/hash.  
**Tại sao xảy ra:** Pipeline dựa vào tên chung thay vì release artifact identity.  
**Ảnh hưởng production:** Audit/rollback khó; có nguy cơ deploy artifact khác với artifact đã test nếu package resolution không chặt.  
**Cách sửa:** Promote immutable versioned artifact/checksum từ CI tới environments; Octopus release phải tham chiếu version cụ thể.

### Medium — Không có pre-deployment compatibility check

**Vấn đề:** Pipeline không xác minh DB version, pending migrations, expected app version hoặc concurrent deployment state.  
**Tại sao xảy ra:** Release coi database luôn ở expected baseline.  
**Ảnh hưởng production:** Hotfix/out-of-order release có thể áp migration trên baseline không mong đợi.  
**Cách sửa:** Validate expected schema/migration history, release lock và compatibility contract trước mutation.

### Medium — Destructive migration không có data-safety gate

**Vấn đề:** Drop column được thực hiện cùng release mà không chứng minh không còn reader/writer và dữ liệu không còn cần.  
**Tại sao xảy ra:** Contract phase bị gộp vào expand phase.  
**Ảnh hưởng production:** Mất rollback capability và có thể mất dữ liệu cần cho legacy consumers/reporting.  
**Cách sửa:** Tách destructive change thành release sau; verify usage telemetry, retention/backup requirement và sign-off phù hợp trước contract.

## Phiên bản đề xuất

Pipeline nên tách thành các stage có gate rõ ràng thay vì một script làm tất cả:

```text
CI
  1. Build + test application artifact: Commerce.Api.<version>.zip
  2. Build reviewed migration artifact for schema transition
  3. Integration test old/new app compatibility against transition schema
  4. Publish immutable artifacts + checksums

Production release (serialized per database)
  1. Acquire environment/database deployment lock
  2. Verify expected current schema/app baseline
  3. Apply EXPAND migration with least-privileged migration identity
  4. Verify migration result and schema invariants
  5. Deploy one canary/new instance
  6. Health + smoke + telemetry gate
  7. Roll remaining instances in controlled batches
  8. Verify old/new compatibility during mixed-version window
  9. Release deployment lock

Later release after rollback window
  1. Verify no old binary/readers depend on legacy columns
  2. Complete backfill/data verification
  3. Apply CONTRACT migration
  4. Observe and retain recovery plan
```

Một expand migration cho rename có thể bắt đầu bằng việc thêm cột mới thay vì rename ngay:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>(
        name: "DisplayName",
        table: "Products",
        type: "nvarchar(300)",
        nullable: true);
}
```

Sau đó cần transition strategy cụ thể. Ví dụ backfill `DisplayName` từ `Name`, deploy application version có thể tương thích với cả schema cũ/mới theo contract đã chọn, rồi chuyển reads/writes. Cách dual-write hay DB-side synchronization chỉ nên dùng khi cần và phải có owner/exit plan; không mặc định tạo trigger chỉ để tránh thiết kế rollout. Khi mọi consumer đã bỏ `Name` và `LegacyCategoryCode`, contract migration mới drop chúng.

Pseudo-PowerShell cho migration gate:

```powershell
$connectionString = Get-ProtectedVariable "CommerceMigrationConnection"
$bundle = Get-ReleaseArtifact "Commerce.Migrations.$ReleaseVersion"

Assert-NoConcurrentDatabaseDeployment -Database "Commerce"
Assert-ExpectedSchemaVersion -Database "Commerce" -Expected $ExpectedSchema

& $bundle --connection $connectionString
if ($LASTEXITCODE -ne 0) {
    throw "Database migration failed; deployment stopped."
}

Assert-SchemaInvariants -Database "Commerce"
```

Các helper ở trên là pipeline abstractions minh họa, không phải built-in TeamCity/Octopus commands. Implementation thực tế phải dùng deployment coordination và secret-management capability mà organization đang vận hành.

## Giải thích thiết kế sau khi sửa

Database migration được xem như một compatibility transition, không phải bước setup trước khi copy binary. Expand/contract giữ old và new versions hoạt động trong rolling window và làm application rollback khả thi hơn. Migration được serialize vì database là shared resource. Artifact migration được build/test/audit trước thay vì để production agent tự suy ra từ source tại thời điểm deploy.

## Trade-offs

Expand/contract cần nhiều release hơn, có temporary duplicate columns và logic transition. Backfill bảng lớn có thể tốn thời gian, log/lock/IO và cần batching/throttling. Serializing migration giảm parallelism release nhưng loại bỏ class race condition nguy hiểm. Canary/health gates làm deployment lâu hơn nhưng giảm blast radius. Một số emergency change có thể cần quy trình khác, nhưng vẫn phải xác định compatibility và recovery trước khi mutate shared state.

## Cách kiểm thử

1. **Database integration test:** chạy expand migration trên production-like schema/data, xác minh data preservation và migration duration/locking.
2. **Mixed-version compatibility test:** old app và new app cùng chạy trên transition schema; cả hai xử lý read/write path quan trọng thành công.
3. **Rollback test:** deploy new binary rồi rollback về old binary mà không rollback DB; xác minh old binary vẫn hoạt động trong supported window.
4. **Deployment validation:** inject health-check failure ở canary; pipeline phải dừng trước khi rollout toàn fleet và không chạy contract migration.
5. **Concurrency test:** trigger hai release attempts vào cùng database; chỉ một migration owner được phép tiến hành.

## Quan sát trong production

Theo dõi deployment/version per instance, health/readiness, HTTP 5xx, p95/p99, SQL migration duration, blocking/deadlocks, transaction-log growth, schema version, failed migration step, connection failures và error signature liên quan missing column. Application Insights nên cho phép correlate error rate với application version/release ID. Release logs phải chứa artifact version/checksum và migration version nhưng tuyệt đối không chứa connection secret.

## Câu hỏi phỏng vấn mở rộng

1. Với bảng hàng trăm triệu rows, bạn backfill `DisplayName` thế nào để tránh transaction/log/locking quá lớn?
2. Khi nào bạn chấp nhận migration không backward-compatible, và deployment topology nào phải thay đổi để làm điều đó an toàn?
3. Nếu hotfix N+2 cần deploy khi release N+1 đang ở giữa expand/contract, bạn quản lý schema compatibility và release ordering thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache correctness phụ thuộc vào việc cache key biểu diễn đầy đủ mọi dimension làm thay đổi output; TTL không thay thế invalidation.
- CDN cache và application cache phải thống nhất về market/language/personalization semantics, nếu không có thể phục vụ nội dung sai trước khi request tới application.
- Cache stampede là failure mode dưới concurrency; cần đo và kiểm soát herd ở đúng layer thay vì chỉ tăng TTL.
- Database migration trong rolling deployment là bài toán backward compatibility của shared state, không chỉ là chạy `dotnet ef database update` thành công.
- Application rollback không tự động đảo ngược destructive schema/data changes; expand/contract và immutable migration artifacts giúp giảm blast radius.

## Mẫu tư duy cần nhớ

- Cache identity phải phản ánh output identity.
- Thiết kế freshness cùng invalidation, không chỉ cùng TTL.
- Shared database schema phải tương thích với mọi binary cùng tồn tại trong rollout window.
- Tách expand, deploy/backfill và contract khi thay đổi schema có thể phá backward compatibility.
- Test failure path và rollback trước khi production buộc bạn phải dùng chúng.
