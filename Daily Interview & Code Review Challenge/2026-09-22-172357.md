# Câu 1 — Cosmos DB vẫn nhanh với point read nhưng API query theo customer lại tăng RU đột biến

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, logical partition, query routing, RU consumption, data modeling, ASP.NET Core, observability

## Bối cảnh

Một ASP.NET Core backend lưu `OrderSummary` trong Azure Cosmos DB. Container được tạo từ giai đoạn MVP với partition key `/tenantId` vì mỗi tenant được xem là boundary tự nhiên.

Document rút gọn:

```json
{
  "id": "order-8472",
  "tenantId": "tenant-a",
  "customerId": "customer-912",
  "status": "Paid",
  "createdAtUtc": "2026-09-22T08:30:00Z",
  "total": 125.40
}
```

Endpoint mới cần lấy 20 orders gần nhất của một customer:

```csharp
var query = new QueryDefinition(
    "SELECT TOP 20 * FROM c " +
    "WHERE c.customerId = @customerId " +
    "ORDER BY c.createdAtUtc DESC")
    .WithParameter("@customerId", customerId);

using var iterator = container.GetItemQueryIterator<OrderSummary>(query);
```

Ở tenant nhỏ endpoint ổn. Sau khi onboard một enterprise tenant có hàng triệu orders, RU consumption và p95 tăng mạnh. Point read ở các endpoint biết cả `id` và `tenantId` vẫn nhanh. Team kết luận Cosmos DB “không scale” và đề xuất tăng throughput; một developer khác đề xuất thêm index cho `customerId` như cách thường làm với SQL.

Chưa biết endpoint có luôn biết `tenantId`, distribution của customer trong từng tenant, indexing policy hiện tại, query metrics, số physical partitions hay freshness/consistency requirement.

## Câu hỏi chính

Hãy giải thích cơ chế routing/partitioning nào có thể khiến point read vẫn hiệu quả nhưng query theo `customerId` trở nên đắt, assumption nào từ SQL indexing không thể áp dụng máy móc, và bạn sẽ dùng evidence nào để quyết định giữa sửa query, thay đổi data model/partition strategy, tạo read projection hay chỉ tăng throughput?

## Câu hỏi làm rõ nên cân nhắc

1. Request có biết `tenantId` cùng với `customerId` không, hay `customerId` được coi là globally unique?
2. Một tenant lớn có bao nhiêu customers và distribution orders/customer có skew mạnh không?
3. Query diagnostics cho thấy request charge, partitions contacted và retrieved/output document counts thế nào?
4. Endpoint cần strong freshness với write model hay chấp nhận eventual consistency cho một read projection?
5. Các access patterns quan trọng khác đang phụ thuộc `/tenantId` như thế nào?

## Gợi ý tư duy

### Gợi ý 1

Partition key không chỉ là một “index column”. Nó quyết định locality và khả năng route request tới phạm vi dữ liệu hẹp hơn.

### Gợi ý 2

Nếu application biết partition key nhưng query không cung cấp nó, hãy hỏi Cosmos DB phải tìm dữ liệu ở đâu.

### Gợi ý 3

Một partition strategy tốt phải được đánh giá theo **toàn bộ access patterns + cardinality + skew + growth**, không chỉ endpoint đang chậm.

## Cấu trúc trả lời đề xuất

1. Clarify access pattern và key availability.
2. Giải thích partition routing và point-read behavior.
3. Phân tích query hiện tại và indexing assumption.
4. Thu thập RU/query diagnostics thay vì đoán.
5. Thử tối ưu query trong partition nếu có thể.
6. So sánh remodeling/read projection với repartitioning.
7. Đánh giá consistency, migration và operational cost.
8. Load-test với data distribution gần production.
9. Theo dõi RU, latency và hot-partition signals sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Point read hiệu quả khi application có `id` và partition key; điều đó không chứng minh arbitrary query cũng có cùng cost profile.
- Nếu query không được giới hạn bằng partition key phù hợp, hệ thống có thể phải thực hiện cross-partition query thay vì route tới một logical partition cụ thể.
- Secondary indexing không thay thế vai trò của partition key; “thêm index” theo tư duy relational không tự biến một access pattern cross-partition thành point/single-partition operation.
- Nếu request biết `tenantId`, query phải được đánh giá với partition key scope thay vì bỏ thông tin routing có sẵn.
- Phải đo request charge, query metrics/diagnostics, partitions fan-out, latency và data distribution trước khi tăng throughput hoặc redesign.
- Thay partition key là quyết định data-model/migration lớn; không nên đề xuất chỉ từ một endpoint.

### Điểm cộng

- `/tenantId` có thể tạo hot/large logical partition risk nếu một tenant chiếm workload rất lớn; cần kiểm tra giới hạn và distribution hiện tại thay vì mặc định tenant là key tốt mãi mãi.
- Composite/hierarchical partitioning hoặc read projection có thể là phương án để đánh giá nếu access patterns và phiên bản/capabilities thực tế phù hợp; phải xác minh tài liệu hiện hành trước khi chọn.
- Projection theo customer có thể tối ưu read nhưng thêm write amplification, synchronization, replay/rebuild và consistency trade-offs.
- `TOP 20 ORDER BY` vẫn cần xem indexing policy/query plan và số dữ liệu phải scan/retrieve; không suy luận chỉ từ số output rows.
- Throughput increase có thể giảm throttling nhưng không chữa query shape/data-locality kém và làm chi phí tăng.

### Senior+

- Phân biệt logical partition design, physical distribution và request routing thay vì nói chung chung “partition nhiều hơn”.
- Đánh giá hot tenant/hot customer, growth horizon và multi-tenant isolation.
- Nếu tạo projection, thiết kế idempotent update, lag metric, rebuild path và source-of-truth rõ ràng.
- Có migration strategy và dual-read/dual-write validation nếu partition model phải thay đổi.

## Hướng giải quyết tham khảo

Tôi chưa kết luận Cosmos DB không scale. Hai workload đang khác nhau. Point read biết `id` và `/tenantId` có đủ thông tin để route trực tiếp tới partition chứa item. Query chỉ filter `customerId` nhưng không đưa partition-key boundary vào access pattern có thể phải fan-out rộng hơn, vì `customerId` không phải partition key hiện tại.

Việc đầu tiên là xác minh request có biết `tenantId`. Nếu có, tôi sẽ truyền partition-key scope phù hợp cho query và đo lại. Tôi cũng xem Cosmos diagnostics/query metrics: request charge, latency, throttling, partitions contacted, retrieved versus returned documents và indexing behavior. Đồng thời kiểm tra data distribution: tenant lớn nhất chiếm bao nhiêu storage/RU, customer nào hot, và `/tenantId` có tạo skew không.

Tôi không nói “thêm index `customerId`” như trong SQL rồi coi vấn đề đã giải quyết. Cosmos indexing và partition routing giải quyết các vấn đề khác nhau. Index có thể hỗ trợ query evaluation, nhưng locality/routing vẫn phụ thuộc partition model và query scope.

Nếu phần lớn requests luôn có tenant + customer, giữ `/tenantId` có thể vẫn hợp lý nếu tenant distribution an toàn; query cần được scoped đúng và indexing policy cần hỗ trợ sort/filter. Nếu enterprise tenants khiến partition/workload skew trở thành structural problem, tôi mới đánh giá partition strategy khác dựa trên toàn bộ access patterns.

Nếu endpoint customer-history cực kỳ quan trọng nhưng write model hiện tại tối ưu cho các access pattern khác, một read projection theo `(tenant, customer)` có thể hợp lý. Đổi lại, hệ thống có thêm write amplification, eventual consistency, retry/replay và rebuild complexity. Projection phải có source of truth rõ, idempotent updates và lag monitoring.

Tăng provisioned throughput chỉ hợp lý nếu diagnostics cho thấy workload/query shape đã hợp lý nhưng capacity thật sự thiếu. Nếu một query fan-out tốn RU không cần thiết, tăng throughput chỉ mua thêm capacity cho inefficiency.

Tôi sẽ test với distribution gần production: small tenant, enterprise tenant, hot customer, concurrent reads/writes và throttling scenarios. Theo dõi RU/request, p95/p99, 429/throttling, partition-level hot spots nếu telemetry hỗ trợ, và projection lag nếu dùng projection.

## Mẫu trả lời trong phỏng vấn

“Point read nhanh không mâu thuẫn với query này chậm. Khi biết `id` và partition key, Cosmos có thể route trực tiếp. Nhưng query chỉ theo `customerId` trong khi container partition theo `tenantId`; nếu không scope bằng partition key, nó có thể trở thành cross-partition query.

Tôi sẽ hỏi request có biết tenant không, rồi xem diagnostics: RU/request, partitions contacted, retrieved/output count, throttling và distribution của tenant/customer. Tôi không mặc định thêm secondary index sẽ chữa locality vì index và partition routing là hai vấn đề khác nhau.

Nếu query có thể chạy trong tenant partition với indexing phù hợp, tôi sửa access pattern trước. Nếu một tenant quá lớn/hot hoặc customer-history là access pattern chủ đạo, tôi đánh giá partition model hoặc read projection. Projection đổi lại bằng consistency và operational complexity. Tôi chỉ tăng throughput khi evidence cho thấy query/data model đã hợp lý mà capacity vẫn thiếu.”

## Câu hỏi đào sâu

1. Nếu request không biết `tenantId` và chỉ có globally unique `customerId`, bạn thay API/data model hay thêm lookup/projection như thế nào?
2. Nếu `/tenantId` tối ưu 90% workload nhưng một enterprise tenant tạo phần lớn RU, bạn có đổi partition key cho toàn hệ thống không?
3. Nếu business yêu cầu customer history phản ánh order mới trong dưới một giây, recommendation dùng eventual-consistent projection thay đổi ra sao?

## Lỗi trả lời thường gặp

- Coi partition key chỉ như một SQL index.
- Tăng RU ngay mà không xem request charge/query diagnostics.
- Đổi partition key chỉ để tối ưu một endpoint mà không inventory access patterns khác.
- Đề xuất projection nhưng không nói source of truth, lag, replay và failure handling.
- Nhìn `TOP 20` rồi kết luận query chắc chắn rẻ.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng throughput hoặc thêm index.
- **3–4:** Biết cross-partition query nhưng chưa có evidence/data-model reasoning.
- **5–6:** Hiểu routing, đo RU/diagnostics và sửa query scope hợp lý.
- **7–8:** Phân tích skew, projection, migration, consistency và testing.
- **9–10:** Thiết kế theo access-pattern portfolio, growth/hot-partition risk và operational trade-offs thay vì tối ưu cục bộ.

# Câu 2 — Elasticsearch search trả dữ liệu cũ sau reindex, nhưng SQL và indexing job đều “thành công”

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, eventual consistency, indexing pipeline, SQL source of truth, retries, alias/cutover, observability, incident investigation

## Bối cảnh

Một automotive marketplace lưu authoritative listing data trong SQL Server và dùng Elasticsearch cho full-text search. Sau deployment thay đổi search mapping/analyzer, team chạy một reindex job để xây search index mới rồi chuyển traffic sang index mới.

Khoảng 45 phút sau cutover, support báo một số listings đã đổi giá hoặc chuyển `Inactive` trong SQL nhưng search vẫn hiển thị giá cũ và thậm chí dẫn người dùng tới listing không còn active. API đọc trực tiếp theo listing ID trả dữ liệu đúng từ SQL.

Thông tin ban đầu:

- bulk reindex báo completed;
- incremental indexing worker vẫn đang chạy;
- không có Elasticsearch cluster outage rõ ràng;
- một số messages trong indexing pipeline đã retry;
- deployment có thay đổi document mapping và tên index;
- search latency vẫn bình thường.

Team đề xuất chạy lại full reindex ngay. Chưa biết cutover timeline chính xác, source offset/checkpoint, alias behavior, writes phát sinh trong lúc reindex, retry ordering, document versioning/idempotency hay index lag.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo trình tự nào để giảm user impact và chứng minh dữ liệu cũ xuất phát từ reindex race, incremental pipeline, retry/out-of-order update, alias/cutover hay query/index mapping? Hãy thiết kế cách reindex/cutover an toàn hơn để search là eventual-consistent projection nhưng không âm thầm mất updates xảy ra trong lúc rebuild.

## Câu hỏi làm rõ nên cân nhắc

1. SQL có timestamp/version/change sequence đáng tin cậy để xác định mọi mutation trong reindex window không?
2. Incremental worker đang ghi vào index cũ, index mới hay cả hai trong giai đoạn rebuild?
3. Alias/search target được switch lúc nào so với snapshot/reindex start và incremental checkpoint?
4. Retry có thể làm event cũ ghi đè document mới hơn không?
5. Business chấp nhận search lag bao lâu và `Inactive` listing có severity cao hơn stale price không?

## Gợi ý tư duy

### Gợi ý 1

“Full reindex completed” chỉ chứng minh một batch hoàn tất; nó không chứng minh mọi update xảy ra **trong lúc batch chạy** đã có mặt trong target index.

### Gợi ý 2

Hãy dựng timeline giữa snapshot/baseline, live changes, retries và alias switch. Đây là bài toán projection consistency, không chỉ Elasticsearch availability.

### Gợi ý 3

Một retry thành công vẫn có thể sai nếu event cũ được áp dụng sau event mới mà consumer không có version/order guard.

## Cấu trúc trả lời đề xuất

1. Đánh giá business impact và loại stale data nguy hiểm nhất.
2. Stabilize search hoặc filter/verify critical states nếu cần.
3. Dựng timeline SQL mutation → event/checkpoint → indexing → alias cutover.
4. Lấy mẫu stale documents và trace từng listing end-to-end.
5. So sánh competing hypotheses bằng evidence.
6. Remediate dữ liệu hiện tại có kiểm soát.
7. Thiết kế rebuild + change capture/catch-up boundary.
8. Thêm idempotency/version ordering.
9. Test race/failure/cutover.
10. Monitor lag, mismatch và retry/DLQ signals.

## Ý chính của câu trả lời tốt

### Bắt buộc

- SQL là source of truth; Elasticsearch là projection nên stale search phải được điều tra như projection synchronization failure.
- Không chạy full reindex lần nữa trước khi hiểu race; nếu pipeline/cutover sai, rerun có thể tái tạo cùng lỗi.
- Cần trace một số stale listing bằng authoritative version/timestamp, indexing events, retries và target index.
- Reindex phải xử lý writes xảy ra trong rebuild window bằng snapshot/change sequence, dual-write/change capture/catch-up hoặc cơ chế tương đương có correctness rõ ràng.
- Alias/cutover chỉ nên xảy ra khi target index đã baseline + catch-up tới một known checkpoint và validation đạt yêu cầu.
- Retry/out-of-order events cần idempotency/version guard để event cũ không ghi đè state mới.
- Search latency bình thường không chứng minh search data đúng.

### Điểm cộng

- Stabilization có thể ưu tiên loại `Inactive` khỏi result bằng verification/filter strategy tạm thời nếu cost và business impact cho phép; không mặc định gọi SQL cho mọi result lâu dài.
- So sánh sample/hash/count theo partition/time range hoặc business invariants trước cutover.
- Giữ old index trong rollback window thay vì xóa ngay sau alias switch.
- Có dead-letter/replay strategy và replay không được phá ordering/version semantics.
- Mapping/analyzer change cần functional relevance tests ngoài data completeness.

### Senior+

- Thiết kế explicit high-water mark/checkpoint để chứng minh target index đã catch up.
- Tách delivery semantics khỏi business correctness: at-least-once + idempotent/version-aware consumer có thể tốt hơn cố đạt exactly-once giả tạo.
- Thiết kế blue/green index lifecycle: build → catch up → validate → switch → observe → retire.
- Có automated stale/invariant detection cho high-risk fields như availability/status.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng impact: stale `Inactive` listing có thể gây user-facing correctness nghiêm trọng hơn stale price, nên nếu cần tôi tạm giảm exposure của search feature, filter một nhóm rủi ro hoặc verify critical status trước khi render/click-through. Cách stabilize phụ thuộc traffic và SQL capacity; không biến mitigation tạm thành một N+1 dependency mới không kiểm soát.

Sau đó tôi chọn một vài listing sai và dựng timeline:

1. SQL version/timestamp hiện tại và lịch sử mutation nếu có.
2. Event/change record được tạo lúc nào.
3. Consumer nhận attempt nào, retry nào, target index nào.
4. Document version trong old/new index.
5. Alias switch timestamp.
6. Checkpoint/high-water mark trước và sau cutover.

Các hypothesis:

- **Reindex race:** baseline đọc state cũ; live update xảy ra trong lúc rebuild nhưng không được replay vào target.
- **Wrong target:** incremental worker vẫn ghi old index sau khi new index được build.
- **Out-of-order retry:** event cũ retry muộn và overwrite document mới.
- **Alias/cutover:** alias trỏ nhầm/multiple indices hoặc switch trước khi target catch up.
- **Mapping/query behavior:** data có trong document nhưng field/mapping/filter mới khiến result semantics sai.

Tôi không rerun full reindex trước khi biết pipeline semantics. Một design an toàn hơn là lấy một known baseline/change checkpoint, build index mới, đồng thời đảm bảo mọi change sau checkpoint được lưu/replay. Sau baseline, consumer catch up target tới high-water mark; validate document counts/business invariants/sample versions; rồi atomically switch search target/alias. Sau switch tiếp tục observe và giữ old index một khoảng rollback phù hợp.

Consumer update nên idempotent và version-aware. Nếu event mang monotonically increasing source version/change sequence, target không được chấp nhận event cũ ghi đè version mới. Cơ chế cụ thể phải phù hợp pipeline và Elasticsearch version đang dùng; không giả định API/version semantics chưa được xác minh.

Tests quan trọng gồm mutation trong khi full reindex đang đọc, event duplicate, retry cũ đến sau event mới, worker restart mất checkpoint, alias switch giữa tải, target indexing failure và rollback. Với mapping mới còn cần relevance/regression tests.

Production telemetry cần có source-to-index lag, oldest unindexed change age, success/retry/failure/DLQ counts, per-target-index writes, checkpoint/high-water mark, alias target, reindex progress và sample/invariant mismatch. Alert dựa trên freshness/correctness chứ không chỉ cluster health và query latency.

## Mẫu trả lời trong phỏng vấn

“Tôi coi Elasticsearch là projection, nên SQL đúng nhưng search sai là synchronization incident. Tôi chưa chạy full reindex lại. Tôi lấy vài listing stale và trace SQL version, event, retry, target index, document version và alias switch để dựng timeline.

Tôi kiểm tra bốn nhóm chính: baseline reindex bỏ lỡ live writes, incremental worker ghi nhầm old index, retry cũ overwrite update mới, hoặc alias switch trước khi target catch up. Search latency bình thường không loại trừ các lỗi này.

Về thiết kế, tôi muốn blue/green index: chốt baseline/checkpoint, build target, replay/catch up mọi change sau checkpoint, validate tới known high-water mark rồi mới switch alias. Consumer phải idempotent và version-aware để event cũ không overwrite state mới. Sau cutover giữ old index cho rollback window và monitor source-to-index lag, retries, checkpoint và mismatch invariants.”

## Câu hỏi đào sâu

1. Nếu source không có monotonically increasing version/change sequence đáng tin cậy, bạn tạo correctness boundary cho rebuild như thế nào?
2. Nếu product yêu cầu search update dưới 2 giây nhưng full rebuild mất 3 giờ, blue/green flow của bạn duy trì freshness ra sao trong 3 giờ đó?
3. Nếu retry cũ đến sau cutover nhưng event đó vẫn hợp lệ cho một field độc lập, document-level version guard có quá thô không?

## Lỗi trả lời thường gặp

- Rerun full reindex mà không tìm race window.
- Coi cluster green/query nhanh là bằng chứng dữ liệu đúng.
- Switch alias ngay khi baseline bulk job kết thúc.
- Có retry nhưng không có ordering/version/idempotency semantics.
- Xóa old index ngay sau cutover, mất rollback/evidence.

## Thang điểm 0–10

- **0–2:** Chỉ restart worker hoặc rerun reindex.
- **3–4:** Biết eventual consistency nhưng không dựng timeline/checkpoint.
- **5–6:** Trace source→event→index, tìm race và thiết kế catch-up trước cutover.
- **7–8:** Có version-aware idempotency, blue/green validation, rollback và observability.
- **9–10:** Xử lý correctness dưới concurrent writes/retries có formal checkpoint boundary và cân bằng freshness, rollback, operational cost.

# Câu 3 — Modernize .NET Framework 4.5 + IIS lên .NET 8 mà không biến migration thành rewrite nhiều năm

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework 4.5, ASP.NET Core/.NET 8, IIS, Azure App Service, SQL Server, legacy dependencies, CI/CD, TeamCity, Octopus Deploy, rollout, rollback, architecture trade-offs

## Bối cảnh

Một internal approval platform đã chạy hơn 8 năm trên .NET Framework 4.5, ASP.NET MVC, IIS và Windows Server. Database là SQL Server dùng chung cho nhiều modules. Deployment hiện build bằng TeamCity và release qua Octopus Deploy tới 6 IIS nodes.

Ứng dụng có khoảng 40 modules nhưng chỉ 6 modules thay đổi thường xuyên. Một số dependencies cũ phụ thuộc Windows-specific APIs; có scheduled jobs chạy trong web application; authentication tích hợp với enterprise identity; frontend có jQuery và một số Angular legacy screens.

Business muốn:

- giảm rủi ro từ runtime/dependencies cũ;
- chuyển phần active development sang modern .NET;
- cải thiện deployment safety và observability;
- không dừng feature delivery trong 12 tháng;
- không chấp nhận big-bang data migration;
- rollback release quan trọng trong vài phút.

Có hai đề xuất:

1. Rewrite toàn bộ thành microservices trên Kubernetes trước khi thêm feature mới.
2. Giữ nguyên monolith thêm vài năm rồi nâng tất cả trong một cuối tuần.

Team có kinh nghiệm ASP.NET Core và Azure App Service nhưng vận hành Kubernetes còn hạn chế. Chưa inventory đầy đủ package compatibility, Windows-only APIs, session/state assumptions, database coupling hay module boundaries.

## Câu hỏi chính

Hãy đề xuất modernization strategy có thể triển khai dần từ .NET Framework 4.5/IIS sang modern .NET, giải thích cách bạn inventory dependencies, chọn migration seams, xử lý shared database/background jobs/authentication, tổ chức CI/CD và rollback. Khi nào bạn giữ IIS/Windows, khi nào chuyển App Service/Linux, và evidence nào mới đủ để biện minh cho microservices/Kubernetes?

## Câu hỏi làm rõ nên cân nhắc

1. Modules nào tạo phần lớn change rate, incidents và business value; coupling giữa chúng qua code/database ra sao?
2. Windows-only dependencies cụ thể là gì và có replacement/cross-platform path không?
3. Authentication/session/file-system/local-machine state hiện phụ thuộc IIS/Windows ở mức nào?
4. Database schema ownership có thể tách dần hay stored procedures/tables đang bị nhiều modules ghi chéo?
5. RTO/rollback requirement có bao gồm schema changes và background jobs hay chỉ web binary?

## Gợi ý tư duy

### Gợi ý 1

Modernization không đồng nghĩa microservices. Trước hết tạo inventory và xác định **migration seams** có thể release độc lập.

### Gợi ý 2

Binary rollback nhanh chỉ có ý nghĩa nếu database/schema và side effects vẫn backward-compatible.

### Gợi ý 3

Tách background jobs khỏi web process có thể là một modernization step độc lập có giá trị, nhưng cần idempotency/ownership/deployment semantics rõ ràng.

## Cấu trúc trả lời đề xuất

1. Baseline/inventory runtime, packages, APIs, modules và production behavior.
2. Phân loại blockers và migration candidates theo value/risk/coupling.
3. Chọn target architecture tối thiểu và migration seams.
4. Thiết kế coexistence/routing giữa legacy và modern components.
5. Xử lý data ownership/schema compatibility.
6. Tách/hiện đại hóa background processing và authentication có kiểm soát.
7. Thiết kế CI/CD, artifact, config/secrets và observability.
8. Thiết kế rollout/rollback từng increment.
9. Test compatibility/E2E/performance/failure paths.
10. Định nghĩa evidence-based triggers cho App Service/Linux, services hoặc Kubernetes.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chọn rewrite big-bang hoặc microservices/Kubernetes chỉ vì hệ thống cũ.
- Bắt đầu bằng inventory thực tế: target frameworks, NuGet/packages, Windows APIs, auth/session, filesystem, background jobs, database coupling, external integrations, deployment assumptions và tests.
- Ưu tiên modules có change rate/value cao và boundary tương đối rõ; migration theo vertical slice/seam thay vì chuyển folder/layer hàng loạt.
- Coexistence giữa legacy và modern app cần routing/auth/data compatibility rõ ràng.
- Shared database có thể là transitional constraint; không giả vờ đã có service autonomy khi nhiều modules vẫn cùng ghi tables.
- Schema migration phải backward-compatible qua rollout/rollback window khi cần; binary rollback không đủ nếu schema destructive.
- Scheduled jobs trong web process phải được inventory vì scale/recycle có thể gây duplicate/missed execution; modernization cần explicit ownership/idempotency.
- CI/CD phải build immutable artifacts, tách environment configuration/secrets và có health/smoke/rollback gates.

### Điểm cộng

- Dùng strangler-style migration ở routing/application boundary khi phù hợp, nhưng không biến pattern name thành mục tiêu.
- Có characterization/integration tests quanh legacy behavior trước khi refactor risky modules.
- Có contract tests cho boundary giữa old/new và Playwright E2E cho critical user journeys.
- Có expand/contract database migration, dual-read/write chỉ khi thật sự cần và có reconciliation plan.
- Có thể target modern .NET trên Windows trước để giảm một dimension rủi ro, rồi mới đánh giá Linux nếu Windows dependencies đã loại bỏ.
- App Service có thể đủ nếu workload/deployment model đơn giản; Kubernetes chỉ hợp lý khi orchestration requirements/organizational maturity biện minh complexity.

### Senior+

- Xây dependency/ownership map và sequence migration để giảm coupling dần thay vì chỉ đổi runtime.
- Tách runtime modernization khỏi architecture modernization: không bắt buộc làm đồng thời.
- Thiết kế telemetry so sánh legacy/modern path và progressive rollout/canary.
- Có decommission criteria rõ để legacy code không sống vô thời hạn sau khi traffic đã chuyển.

## Hướng giải quyết tham khảo

Tôi chia chương trình thành các increments có rollback được thay vì một “migration project” duy nhất.

### 1. Baseline trước khi đổi kiến trúc

Tạo inventory tự động + manual cho project graph, target frameworks, NuGet dependencies, unsupported/deprecated libraries, Windows-specific APIs, authentication/session, local filesystem, registry/COM nếu có, scheduled jobs, external integrations, SQL access/stored procedures và runtime configuration. Kết hợp production telemetry để biết module nào thực sự được dùng, latency/error hotspots và change frequency.

Tôi cũng dựng critical-path test baseline: integration tests cho APIs/data behavior và Playwright E2E cho các approval journeys quan trọng. Với legacy code khó unit test, characterization tests có giá trị hơn việc cố đạt coverage percentage tùy ý.

### 2. Chọn migration seams

Xếp modules theo business value × change rate × technical risk × coupling. Sáu modules active có thể là candidates, nhưng chỉ chọn module có boundary đủ rõ. Tôi không tách module chỉ vì folder tên đẹp nếu nó vẫn transactionally ghi chéo nhiều tables với module khác.

Một vertical slice có thể được implement bằng ASP.NET Core/.NET 8 và route một nhóm endpoints/URLs sang modern app, trong khi legacy app tiếp tục phục vụ phần còn lại. Authentication identity/claims contract phải thống nhất; không tự tạo hai security models không tương thích.

### 3. Data strategy

Ban đầu shared SQL database có thể được chấp nhận như transitional architecture để giảm migration dimensions. Nhưng tôi ghi rõ table/schema ownership và ngăn coupling mới. Với mỗi module tách dần, mục tiêu là làm ownership rõ hơn.

Schema changes dùng expand/contract khi rollout có old/new binaries cùng tồn tại: thêm schema backward-compatible trước, deploy code chuyển dần, backfill/reconcile, rồi chỉ remove old schema sau khi rollback window kết thúc. Destructive migration không đi cùng release nếu nó làm mất khả năng rollback mà business yêu cầu.

### 4. Background jobs

Inventory job nào đang dựa vào IIS/App Pool lifetime. Job critical nên có explicit host/scheduler/worker ownership thay vì “web app đang chạy thì job chạy”. Nếu chuyển sang Worker Service, Azure Functions hoặc cơ chế khác, lựa chọn dựa trên execution model; mọi job phải có idempotency, retry policy, observability và multi-instance semantics. Không chuyển công nghệ trước khi hiểu duplicate/missed-run behavior.

### 5. Hosting

Tôi tách quyết định runtime khỏi OS/container. Một module có thể lên .NET 8 nhưng vẫn chạy Windows nếu còn Windows dependency; đó vẫn là tiến bộ vì giảm runtime legacy risk. Khi module không còn OS-specific dependency và load/ops model phù hợp, App Service on Linux có thể là target đơn giản hơn Kubernetes.

Kubernetes chỉ được cân nhắc khi có evidence: nhiều independently deployed/scaled workloads, scheduling/network/resource requirements, platform standardization hoặc team ownership model cần orchestration đó và organization có khả năng vận hành. “Future-proof” không phải evidence.

### 6. CI/CD

TeamCity có thể tiếp tục build nếu đang ổn; Octopus có thể tiếp tục release trong transition. Tôi không đổi toàn bộ toolchain cùng lúc chỉ để gọi là modernization. Pipeline phải tạo immutable/versioned artifacts, chạy tests/static analysis, scan dependencies, deploy environment config/secrets đúng cách, chạy DB migration có gate, health/smoke checks và progressive rollout.

Khi new app lên App Service, có thể dùng deployment strategy phù hợp platform như slot/canary nếu được xác minh và đáp ứng topology. Quan trọng là artifact promotion và rollback semantics, không phải UI của tool.

### 7. Rollout và rollback

Mỗi migrated slice có feature/routing control để chuyển traffic dần khi hợp lý. Quan sát error rate, p95/p99, dependency behavior và business outcome giữa legacy/modern path. Rollback application chỉ được coi là khả thi nếu schema/data contract còn compatible. Với side effects, cần reconciliation chứ không chỉ redeploy binary.

### 8. Decommission

Mỗi slice có exit criteria: traffic chuyển hoàn toàn, parity tests pass, observability ổn định, rollback window hết, old code/job/config không còn dependency. Sau đó xóa/decommission legacy path. Nếu không có bước này, strangler migration dễ biến thành hai hệ thống phải duy trì mãi.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chọn rewrite microservices/Kubernetes và cũng không đợi một cuối tuần để nâng tất cả. Tôi bắt đầu bằng inventory package/API/Windows dependencies, auth/session, jobs, DB coupling và production usage, rồi chọn vertical slices có value cao nhưng boundary đủ rõ.

Tôi tách runtime modernization khỏi architecture modernization. Một module có thể lên .NET 8 trên Windows trước; khi bỏ được OS-specific dependency mới cân nhắc Linux/App Service. Legacy và modern app có thể coexist qua routing seam, dùng cùng identity contract và transitional shared database nếu cần, nhưng tôi phải làm rõ schema ownership và ngăn coupling mới.

Database changes dùng expand/contract để old/new binaries cùng chạy và rollback được. Background jobs phải tách khỏi giả định IIS process lifetime, có idempotency và observability. TeamCity/Octopus không cần thay ngay nếu pipeline vẫn tạo immutable artifact và có test/health/rollback gates.

Tôi chỉ chọn Kubernetes khi independent scaling/deployment hoặc orchestration requirements thực tế biện minh operational cost. Mỗi slice có telemetry, progressive rollout và decommission criteria để migration thực sự tiến tới kết thúc.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên có boundary nghiệp vụ rõ nhưng transaction hiện cập nhật tables của ba modules khác trong cùng SQL transaction, bạn còn tách nó trước không?
2. Nếu CTO yêu cầu Linux-only trong 6 tháng nhưng một dependency COM critical chưa có replacement, bạn sequence modernization thế nào?
3. Nếu rollback phải dưới 5 phút nhưng release cần data backfill 200 triệu rows, bạn thiết kế migration/release boundary ra sao?

## Lỗi trả lời thường gặp

- Đồng nhất modernization với rewrite hoặc microservices.
- Đổi runtime, hosting, CI/CD, database và frontend cùng lúc làm blast radius quá lớn.
- Nói “strangler pattern” nhưng không xác định routing/data/auth seam cụ thể.
- Hứa rollback nhanh nhưng dùng destructive schema migration trong cùng release.
- Chuyển scheduled jobs khỏi IIS mà không thiết kế duplicate execution/idempotency.

## Thang điểm 0–10

- **0–2:** Chọn big-bang rewrite/nâng cấp cuối tuần mà không có risk model.
- **3–4:** Có incremental migration nhưng data/auth/jobs/rollback còn mơ hồ.
- **5–6:** Có inventory, vertical slices, coexistence và backward-compatible release strategy.
- **7–8:** Có testing, progressive rollout, observability, decommission và hosting trade-offs.
- **9–10:** Tách runtime/architecture/hosting modernization thành các decisions độc lập, giảm coupling theo sequence và dùng evidence để biện minh complexity.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB partition key quyết định data locality/routing; secondary indexing không thay thế partition strategy.
- Point-read performance không đại diện cho cross-partition query cost; cần đo RU/query diagnostics theo access pattern và distribution thực tế.
- Elasticsearch trong search architecture nên được coi là projection khi SQL là source of truth; reindex phải có baseline, catch-up, validation và cutover boundary rõ ràng.
- Retry không đảm bảo correctness nếu update có thể đến out-of-order; projection consumer cần idempotency/version semantics phù hợp.
- .NET modernization có thể tiến dần mà không đồng nghĩa rewrite, microservices hay Kubernetes; runtime, architecture, hosting và deployment tooling là các decision dimensions riêng.
- Rollback application chỉ thực sự an toàn khi database/data contracts và side effects cũng được thiết kế cho rollback/coexistence.

## Mẫu tư duy cần nhớ

- **Design partitioning from access patterns, cardinality and skew—not from entity names.**
- **A projection needs a source of truth, checkpoint, replay and lag visibility.**
- **A successful retry is not necessarily a correct update.**
- **Modernize one risk dimension at a time when possible.**
- **Rollback requirements must shape schema and release design before deployment.**
