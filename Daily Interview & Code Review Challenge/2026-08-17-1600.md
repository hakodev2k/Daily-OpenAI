# Code Review Challenge 1 — Race condition trong cập nhật tồn kho

**Chủ đề:** Concurrency, EF Core transaction, optimistic concurrency
**Độ khó:** Senior+
**Thời gian review đề xuất:** 35 phút
**Số vấn đề cần tìm:** Khoảng 7 vấn đề

## Bối cảnh

Một API bán hàng ASP.NET Core xử lý hàng nghìn đơn mỗi phút. Khi nhiều khách cùng mua sản phẩm cuối cùng, hệ thống đôi lúc tạo đơn vượt quá tồn kho.

## Đoạn code cần review

```csharp
public async Task<bool> ReserveStock(Guid productId, int quantity)
{
    var product = await _db.Products
        .FirstAsync(x => x.Id == productId);

    if (product.Stock < quantity)
        return false;

    product.Stock -= quantity;
    await _db.SaveChangesAsync();

    return true;
}
```

## Nhiệm vụ của ứng viên

1. Tìm lỗi correctness và concurrency.
2. Giải thích tại sao lỗi chỉ xuất hiện khi tải cao.
3. Đề xuất giải pháp an toàn.
4. Nêu cách test race condition.
5. Đề xuất metrics cần theo dõi.

## Câu hỏi gợi mở

- Hai request đọc cùng một stock value sẽ xảy ra điều gì?
- Transaction isolation có đủ giải quyết không?
- Có cần optimistic concurrency không?

## Gợi ý

### Gợi ý 1

Kiểm tra khoảng thời gian giữa read và write.

### Gợi ý 2

Cần atomic update hoặc concurrency token.

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

---

## Kết quả code review tham khảo

- Read-modify-write không atomic.
- Có race condition khi nhiều request cập nhật cùng record.
- Thiếu concurrency handling.
- Không có audit hoặc correlation id.

Severity cao nhất: Critical.

## Phiên bản code đề xuất

Dùng optimistic concurrency với RowVersion hoặc câu lệnh update có điều kiện:

```sql
UPDATE Products
SET Stock = Stock - @quantity
WHERE Id = @id AND Stock >= @quantity
```

Sau đó kiểm tra affected rows.

## Cách kiểm thử

- Chạy 100 request đồng thời mua cùng sản phẩm.
- Kiểm tra invariant stock không âm.
- Test transaction rollback.

## Quan sát production

- Failed reservation count.
- Concurrency conflict count.
- Order consistency metrics.

# Code Review Challenge 2 — HttpClient tạo lỗi socket exhaustion

**Chủ đề:** HTTP client lifetime, resource management, resilience
**Độ khó:** Senior
**Thời gian review đề xuất:** 30 phút
**Số vấn đề cần tìm:** Khoảng 6 vấn đề

## Bối cảnh

Một service gọi Microsoft Graph để đồng bộ dữ liệu người dùng. Sau vài giờ chạy, API bắt đầu timeout.

## Đoạn code cần review

```csharp
public async Task<UserDto?> GetUser(string id)
{
    using var client = new HttpClient();

    var response = await client.GetAsync($"https://api.example.com/users/{id}");

    if (!response.IsSuccessStatusCode)
        return null;

    var json = await response.Content.ReadAsStringAsync();
    return JsonSerializer.Deserialize<UserDto>(json);
}
```

## Nhiệm vụ của ứng viên

1. Review resource lifetime.
2. Phân tích production impact.
3. Đề xuất thiết kế thay thế.
4. Nêu cách kiểm thử lỗi timeout.

## Câu hỏi gợi mở

- HttpClient nên được tạo khi nào?
- Có cần retry không?
- Timeout và cancellation xử lý ra sao?

## Gợi ý

### Gợi ý 1

Xem xét connection pooling.

### Gợi ý 2

Cần quản lý lifetime và resilience policy.

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

---

## Kết quả code review tham khảo

- Tạo HttpClient liên tục gây áp lực connection lifecycle.
- Thiếu timeout rõ ràng.
- Không truyền CancellationToken.
- Không có retry policy phù hợp.
- Thiếu logging lỗi dependency.

Severity cao nhất: High.

## Phiên bản code đề xuất

Sử dụng IHttpClientFactory, typed client, timeout policy và structured logging.

## Cách kiểm thử

- Dependency timeout.
- API trả 500 liên tục.
- Load test nhiều request.

## Quan sát production

- HTTP latency.
- Failure rate.
- Dependency availability.
- Retry count.
