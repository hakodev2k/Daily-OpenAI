# Code Review Challenge 1 — Product search càng nhiều dữ liệu càng chậm, kết quả exact filter lại “mất tích” khó hiểu

**Chủ đề:** C#/.NET 8, ASP.NET Core, Elasticsearch, text vs keyword, query design, deep pagination, source projection, cancellation, search observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một e-commerce integration layer chạy ASP.NET Core .NET 8. SQL Server là source of truth cho product data, còn Elasticsearch phục vụ màn hình product search của back-office.

Index `products-v3` có các field chính:

- `name`: `text`, có sub-field `name.keyword`;
- `description`: `text`;
- `brand`: `keyword`;
- `categoryId`: `keyword`;
- `status`: `keyword`;
- `updatedAt`: `date`.

UI hỗ trợ:

- search theo tên/mô tả;
- filter brand/category/status;
- sort newest;
- page size tối đa 50;
- user có thể đi qua nhiều pages nhưng product không yêu cầu exact total count cho mọi request.

Khi index còn nhỏ, endpoint hoạt động chấp nhận được. Sau khi index tăng lên vài triệu documents, production xuất hiện các triệu chứng:

- search một cụm phổ biến có p95 tăng mạnh ở page sâu;
- query kiểu `shoe` đôi lúc không match như user kỳ vọng khi code chuyển sang `term` để “nhanh hơn”;
- filter brand hoạt động không ổn định vì code đôi lúc dùng `match` trên field `keyword`;
- request với page lớn gây CPU tăng trên search cluster;
- API trả một document khá lớn trong khi UI chỉ render khoảng 8 fields;
- user đóng tab nhưng một số search request vẫn tiếp tục chạy;
- team đề xuất tăng số node Elasticsearch nhưng chưa có evidence query shape hiện tại hợp lý.

Service hiện tại dùng một abstraction nội bộ `ISearchGateway` để tránh phụ thuộc trực tiếp API surface của một client library cụ thể.

## Đoạn code cần review

```csharp
public sealed class ProductSearchService
{
    private readonly ISearchGateway _search;

    public ProductSearchService(ISearchGateway search)
    {
        _search = search;
    }

    public async Task<ProductSearchResponse> SearchAsync(
        ProductSearchRequest request,
        CancellationToken cancellationToken)
    {
        var size = request.PageSize ?? 100;
        var from = (request.Page - 1) * size;

        var query = new SearchQuery
        {
            Index = "products-v3",
            From = from,
            Size = size,
            TrackTotalHits = true,
            SourceIncludes = null,
            Must = new List<SearchClause>()
        };

        if (!string.IsNullOrWhiteSpace(request.Text))
        {
            query.Must.Add(SearchClause.Term(
                "name",
                request.Text));

            query.Must.Add(SearchClause.Wildcard(
                "description",
                $"*{request.Text}*"));
        }

        if (!string.IsNullOrWhiteSpace(request.Brand))
        {
            query.Must.Add(SearchClause.Match(
                "brand",
                request.Brand));
        }

        if (!string.IsNullOrWhiteSpace(request.CategoryId))
        {
            query.Must.Add(SearchClause.Match(
                "categoryId",
                request.CategoryId));
        }

        if (!string.IsNullOrWhiteSpace(request.Status))
        {
            query.Must.Add(SearchClause.Match(
                "status",
                request.Status));
        }

        query.Sort = new[]
        {
            SortField.Descending("updatedAt")
        };

        var result = await _search.SearchAsync(
            query,
            CancellationToken.None);

        return new ProductSearchResponse(
            result.Documents,
            result.TotalHits,
            request.Page,
            size);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và relevance trong cách dùng `term`, `match`, `wildcard`, `text` và `keyword`.
2. Xác định các vấn đề performance/scalability khi index lớn và user đi page sâu.
3. Giải thích production impact của `TrackTotalHits`, `_source` đầy đủ và page size không được bound.
4. Review cancellation propagation.
5. Phân biệt full-text scoring với exact filtering và đề xuất query structure rõ ràng hơn.
6. Đề xuất pagination strategy phù hợp nếu product cần browse sâu.
7. Nêu cách kiểm thử và telemetry để chứng minh query design mới tốt hơn thay vì chỉ tăng cluster capacity.

## Câu hỏi gợi mở

1. `term` query trên một analyzed `text` field có cùng semantics với search text mà user nhập không?
2. Những điều kiện `brand`, `categoryId`, `status` có cần ảnh hưởng `_score`, hay chúng chỉ là exact filters?
3. Chi phí của `from = 100000` khác gì `from = 0` khi search engine phải tìm top results?
4. UI có thật sự cần exact total hit count trong mọi request không?
5. Nếu user đóng browser request, token cancellation hiện đang dừng operation ở layer nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **query semantics không khớp mapping** và **pagination cost tăng theo độ sâu**. Hãy tách full-text search khỏi exact filters trước khi nghĩ tới scale cluster.

### Gợi ý 2

Xem query như một execution contract: analyzed text cần full-text semantics; exact dimensions cần filter semantics; pagination, projection và cancellation đều ảnh hưởng resource budget của một request.

## Kết quả code review tham khảo

### High — Dùng `term` trên field `name` kiểu `text` làm semantics sai

**Vấn đề:** Code dùng `Term("name", request.Text)` trên field được mapping là `text`.

**Tại sao xảy ra:** `text` được analyzer xử lý thành tokens tại indexing/search time. `term` query mang semantics exact term và không phải lựa chọn mặc định cho natural-language full-text input.

**Ảnh hưởng production:** User nhập một cụm hợp lý nhưng không nhận kết quả như mong đợi, đặc biệt khi casing, tokenization hoặc analyzer biến input/indexed value thành các terms khác với literal request.

**Cách sửa:** Dùng full-text query phù hợp như `match`/`multi_match` cho `name` và `description` theo abstraction của gateway. Nếu business thật sự cần exact product name, dùng `name.keyword` hoặc một dedicated normalized keyword field với semantics được xác định rõ.

### High — Leading wildcard trên `description` là query shape đắt và relevance kém

**Vấn đề:** `*{request.Text}*` yêu cầu substring-like matching trên một field text.

**Tại sao xảy ra:** Leading wildcard không tận dụng inverted index theo cách hiệu quả như normal term-based full-text query và có thể mở rộng matching rất rộng.

**Ảnh hưởng production:** CPU/search latency tăng khi vocabulary/index lớn. Query còn bỏ qua language analysis/relevance mà field `description` vốn được thiết kế để hỗ trợ.

**Cách sửa:** Với natural-language description search, dùng full-text query. Nếu product requirement là substring/autocomplete, thiết kế mapping/index strategy tương ứng, ví dụ n-gram/search-as-you-type style field khi thực sự cần, thay vì biến mọi full-text request thành wildcard scan.

### High — Exact dimensions đang bị đưa vào scoring `Must` thay vì filter context

**Vấn đề:** `brand`, `categoryId`, `status` là `keyword` nhưng code dùng `Match` và đặt tất cả vào `Must`.

**Tại sao xảy ra:** Query builder không phân biệt “điều kiện ảnh hưởng relevance” với “điều kiện boolean/exact để loại document”.

**Ảnh hưởng production:** Semantics khó hiểu, scoring có thể bị tác động không cần thiết và query intent khó tối ưu/maintain. Một developer khác có thể tiếp tục trộn analyzed search với exact filters.

**Cách sửa:** Dùng exact `term`-style filter trên `keyword` fields và đặt chúng trong filter context. Chỉ full-text clause tham gia scoring khi ranking thực sự cần `_score`.

### High — Deep pagination bằng `from/size` làm cost tăng khi page sâu

**Vấn đề:** `from = (Page - 1) * size` cho phép offset tăng không giới hạn.

**Tại sao xảy ra:** Search engine vẫn phải xác định và giữ top results tới `from + size` trước khi bỏ các hits đầu. Offset càng sâu, resource cost càng tăng.

**Ảnh hưởng production:** Một số ít request page sâu có thể làm CPU/memory pressure tăng đáng kể và ảnh hưởng latency của traffic bình thường.

**Cách sửa:** Bound độ sâu cho normal offset paging. Nếu product cần browse sâu, dùng cursor/search-after style pagination với deterministic sort, ví dụ `updatedAt` cộng một unique tie-breaker như product ID. Cursor phải được coi là opaque ở API boundary.

### High — Page size không được validate theo business limit

**Vấn đề:** Default là 100 dù requirement tối đa 50, và caller có thể gửi giá trị lớn hơn.

**Tại sao xảy ra:** API không enforce resource budget.

**Ảnh hưởng production:** Payload, deserialization, search work và network cost tăng; request ác ý hoặc client bug có thể tạo load không cần thiết.

**Cách sửa:** Validate page size trong range rõ ràng, ví dụ 1–50 theo requirement. Trả validation error cho input ngoài range thay vì silently chấp nhận.

### Medium — `TrackTotalHits = true` có thể tính exact total khi UI không cần

**Vấn đề:** Mọi query đều yêu cầu total hit count đầy đủ dù requirement nói không cần exact count cho mọi request.

**Tại sao xảy ra:** Response contract được thiết kế quanh pagination truyền thống hơn là user need.

**Ảnh hưởng production:** Thêm work không có giá trị ở các broad query. Mức ảnh hưởng phải đo theo query/index thực tế, không nên giả định đây là bottleneck duy nhất.

**Cách sửa:** Chỉ yêu cầu exact total ở use case thực sự cần. Với browse/load-more, có thể trả `hasMore`/cursor hoặc bounded/approximate count tùy product contract.

### Medium — Lấy toàn bộ `_source` dù UI chỉ dùng ít fields

**Vấn đề:** `SourceIncludes = null` khiến gateway trả full document theo contract hiện tại.

**Tại sao xảy ra:** Search query không được project theo read model của màn hình.

**Ảnh hưởng production:** Tăng response bytes, JSON parsing, allocations và network transfer. Nếu document chứa internal fields, blast radius cũng lớn hơn nếu API mapping sai.

**Cách sửa:** Chỉ include các fields cần cho `ProductSearchItem`, ví dụ `id`, `name`, `brand`, `categoryId`, `status`, `price`, `thumbnailUrl`, `updatedAt`.

### Medium — Cancellation bị cắt ở search boundary

**Vấn đề:** Method nhận `cancellationToken` nhưng gọi gateway bằng `CancellationToken.None`.

**Tại sao xảy ra:** HTTP cancellation không propagate xuống dependency call.

**Ảnh hưởng production:** Client disconnect/timeout vẫn có thể để search request tiêu tốn cluster/app resources tới khi hoàn thành hoặc timeout khác xảy ra.

**Cách sửa:** Truyền `cancellationToken` xuống gateway và xác minh implementation/client thực tế honor cancellation phù hợp. Cancellation là cooperative; cần đo request-stop latency thay vì chỉ kiểm tra signature.

### Medium — Sort chỉ bằng `updatedAt` chưa đủ ổn định cho cursor pagination

**Vấn đề:** Nhiều products có thể có cùng `updatedAt`.

**Tại sao xảy ra:** Cursor/search-after cần deterministic total ordering để tránh skip/duplicate khi sort values trùng nhau.

**Ảnh hưởng production:** Khi chuyển sang cursor pagination, user có thể thấy duplicate hoặc miss items giữa pages.

**Cách sửa:** Dùng thêm stable unique tie-breaker, ví dụ `(updatedAt DESC, id ASC)`. Với dữ liệu thay đổi trong lúc paging, phải nêu rõ consistency expectation và chấp nhận/giảm thiểu drift theo product requirement.

### Medium — Thiếu query-level telemetry để phân biệt query design với capacity issue

**Vấn đề:** Service không ghi nhận query category, latency, page depth, result count hay dependency diagnostics.

**Tại sao xảy ra:** Team chỉ nhìn cluster CPU và API latency tổng thể.

**Ảnh hưởng production:** Dễ scale hardware trước khi biết wildcard/deep pagination/broad query nào đang gây load.

**Cách sửa:** Thu thập structured metrics/traces cho search duration, query type, page/cursor usage, requested size, result count, timeout/cancel/error, dependency latency và cluster-side slow query evidence khi có. Không log raw search text nếu có risk chứa dữ liệu nhạy cảm; có thể log length/category/hash theo policy.

## Phiên bản đề xuất

Abstraction dưới đây minh họa intent, không phụ thuộc một Elasticsearch client library cụ thể:

```csharp
public sealed class ProductSearchService
{
    private readonly ISearchGateway _search;

    public ProductSearchService(ISearchGateway search)
    {
        _search = search;
    }

    public async Task<ProductSearchResponse> SearchAsync(
        ProductSearchRequest request,
        CancellationToken cancellationToken)
    {
        var size = request.PageSize ?? 25;

        if (size is < 1 or > 50)
            throw new ArgumentOutOfRangeException(nameof(request.PageSize));

        if (request.Text?.Length > 200)
            throw new ArgumentException("Search text is too long.");

        var query = new SearchQuery
        {
            Index = "products-v3",
            Size = size,
            TrackTotalHits = request.RequireExactTotal,
            SourceIncludes = new[]
            {
                "id",
                "name",
                "brand",
                "categoryId",
                "status",
                "price",
                "thumbnailUrl",
                "updatedAt"
            },
            Must = new List<SearchClause>(),
            Filter = new List<SearchClause>(),
            SearchAfter = request.Cursor,
            Sort = new[]
            {
                SortField.Descending("updatedAt"),
                SortField.Ascending("id")
            }
        };

        if (!string.IsNullOrWhiteSpace(request.Text))
        {
            query.Must.Add(SearchClause.MultiMatch(
                new[] { "name^3", "description" },
                request.Text));
        }

        if (!string.IsNullOrWhiteSpace(request.Brand))
            query.Filter.Add(SearchClause.Term("brand", request.Brand));

        if (!string.IsNullOrWhiteSpace(request.CategoryId))
            query.Filter.Add(SearchClause.Term("categoryId", request.CategoryId));

        if (!string.IsNullOrWhiteSpace(request.Status))
            query.Filter.Add(SearchClause.Term("status", request.Status));

        var result = await _search.SearchAsync(query, cancellationToken);

        return new ProductSearchResponse(
            result.Documents,
            result.TotalHits,
            result.NextCursor,
            size);
    }
}
```

`MultiMatch`, `Term`, `SearchAfter` ở đây là concepts của abstraction nội bộ, không phải yêu cầu phải dùng một API signature cụ thể của bất kỳ .NET Elasticsearch client version nào.

Mapping/index design phải đi cùng query contract. `name`/`description` dùng analyzed full-text semantics; exact filter fields dùng `keyword`. Nếu cần autocomplete/substring, thêm dedicated field/mapping phù hợp thay vì làm wildcard trên field chung.

Cursor không nên cho phép client tự sửa sort values tùy ý. API có thể encode/sign cursor hoặc giữ nó opaque theo implementation. Nếu product chỉ cho xem 20 pages đầu, offset paging có thể vẫn đủ đơn giản; không cần search-after chỉ vì nó “advanced” hơn.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách hai loại intent:

- **relevance query**: tên/mô tả, nơi analyzer và scoring có ý nghĩa;
- **exact filters**: brand/category/status, nơi document hoặc được chọn hoặc bị loại.

Điều này làm query dễ reasoning hơn và tránh dùng query type theo thói quen.

Pagination chuyển sang cursor chỉ khi browse sâu là requirement thật. Nếu UI chỉ có vài pages, bounded `from/size` đơn giản hơn có thể là lựa chọn hợp lý. Senior-level decision ở đây là đặt budget rõ ràng và đo query cost, không phải mặc định chọn cơ chế phức tạp nhất.

Không nên tăng cluster size trước khi sửa một query shape rõ ràng không phù hợp. Sau khi query hợp lý, capacity scaling vẫn có thể cần nếu traffic/index growth chứng minh throughput thực sự là bottleneck.

## Trade-offs

Cursor/search-after làm API contract phức tạp hơn và không thuận tiện cho “nhảy trực tiếp tới page 200”. Nếu product bắt buộc random access page sâu, cần thảo luận lại UX/cost thay vì giấu complexity ở backend.

Source filtering giảm payload nhưng tạo coupling rõ hơn giữa API read model và index fields. Đây thường là coupling có chủ đích, nhưng mapping rollout phải được kiểm thử.

Exact total counts hữu ích cho một số back-office workflows. Không nên loại bỏ chúng hoàn toàn; có thể chỉ tính khi user/filter cụ thể yêu cầu.

Autocomplete/n-gram tăng index size và indexing cost. Chỉ thêm khi user experience cần và benchmark chứng minh giá trị.

## Cách kiểm thử

1. **Integration test query semantics:** index fixtures có tokenization/casing khác nhau; xác minh full-text search và exact brand/category/status filters trả đúng tập kết quả.
2. **Pagination test:** nhiều documents cùng `updatedAt`; đi qua nhiều cursors và xác minh không duplicate/miss trong snapshot test scenario.
3. **Load test:** so sánh representative broad query, filtered query và deep browse; đo p50/p95/p99, cluster CPU và dependency latency trước/sau thay đổi.
4. **Cancellation test:** bắt đầu một search đủ lâu rồi cancel HTTP request; xác minh gateway nhận token và dependency operation dừng trong behavior/SLO chấp nhận được.
5. **Contract/security test:** page size > 50, query quá dài và invalid cursor phải fail có kiểm soát; response chỉ chứa fields cho phép.

# Code Review Challenge 2 — Hai stored procedures thỉnh thoảng deadlock; team “fix” bằng NOLOCK và retry vô hạn

**Chủ đề:** SQL Server, transactions, locking, deadlocks, lock ordering, indexes, retry policy, correctness, production diagnostics  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một booking platform lưu reservation và inventory trong SQL Server. Hai use cases chạy đồng thời với volume cao:

1. `ConfirmReservation` xác nhận reservation và trừ một inventory unit.
2. `CancelReservation` hủy reservation và cộng inventory unit trở lại.

Production thỉnh thoảng xuất hiện SQL deadlock. Team thấy SQL Server chọn một transaction làm deadlock victim nên thêm retry trong application. Một developer còn thêm `WITH (NOLOCK)` vào các câu `SELECT` vì cho rằng “NOLOCK sẽ tránh deadlock”.

Các triệu chứng:

- deadlock tăng rõ trong giờ cao điểm;
- một số request retry nhiều lần và latency p99 rất cao;
- log chỉ ghi `SqlException` mà không lưu operation/reservation/product context;
- occasional support ticket cho thấy inventory hiển thị giá trị khó giải thích sau chuỗi confirm/cancel cạnh tranh;
- database có index trên primary key, nhưng chưa ai kiểm tra execution plan/deadlock graph gần đây.

Stored procedures hiện tại:

## Đoạn code cần review

```sql
CREATE PROCEDURE dbo.ConfirmReservation
    @ReservationId bigint,
    @ProductId bigint
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRANSACTION;

    SELECT Status
    FROM dbo.Reservations WITH (NOLOCK)
    WHERE Id = @ReservationId;

    UPDATE dbo.Reservations
    SET Status = 'Confirmed',
        UpdatedAt = SYSUTCDATETIME()
    WHERE Id = @ReservationId;

    WAITFOR DELAY '00:00:00.100';

    UPDATE dbo.Inventory
    SET AvailableQuantity = AvailableQuantity - 1
    WHERE ProductId = @ProductId;

    COMMIT TRANSACTION;
END;
GO

CREATE PROCEDURE dbo.CancelReservation
    @ReservationId bigint,
    @ProductId bigint
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRANSACTION;

    SELECT AvailableQuantity
    FROM dbo.Inventory WITH (NOLOCK)
    WHERE ProductId = @ProductId;

    UPDATE dbo.Inventory
    SET AvailableQuantity = AvailableQuantity + 1
    WHERE ProductId = @ProductId;

    WAITFOR DELAY '00:00:00.100';

    UPDATE dbo.Reservations
    SET Status = 'Cancelled',
        UpdatedAt = SYSUTCDATETIME()
    WHERE Id = @ReservationId;

    COMMIT TRANSACTION;
END;
GO
```


## Nhiệm vụ của ứng viên

1. Xác định các nguồn gây deadlock và lock contention trong hai procedures.
2. Giải thích vì sao `NOLOCK` không phải fix đúng cho transaction correctness/deadlock ở đây.
3. Review transaction boundary, lock ordering và artificial delay.
4. Xác định các invariant business đang thiếu, ví dụ state transition và inventory không âm.
5. Review retry policy ở application và phân biệt transient retry với che giấu root cause.
6. Đề xuất implementation/design cải thiện mà không mặc định tăng isolation hoặc thêm distributed lock.
7. Nêu tests và telemetry cần có để chứng minh fix dưới concurrency thực tế.

## Câu hỏi gợi mở

1. `ConfirmReservation` và `CancelReservation` đang acquire/update hai resources theo cùng thứ tự hay ngược nhau?
2. `NOLOCK` trên một `SELECT` có làm các `UPDATE` phía sau ngừng lấy locks không?
3. Điều gì xảy ra nếu hai request cùng confirm một reservation đang `Pending`?
4. Retry vô hạn có behavior gì khi contention kéo dài hoặc code luôn tạo cùng deadlock pattern?
5. Bạn cần xem deadlock graph/execution plan/index usage nào trước khi kết luận root cause duy nhất là thứ tự statements?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **inconsistent lock acquisition order trong transaction**, nhưng đừng dừng ở đó: transaction hiện còn thiếu các business preconditions cần được enforce atomically.

### Gợi ý 2

Deadlock retry là một resilience technique, không phải bằng chứng design đã đúng. Hãy giảm lock duration, giữ lock order nhất quán, kiểm tra indexes và làm retry bounded với jitter/backoff hợp lý.

## Kết quả code review tham khảo

### Critical — Hai procedures cập nhật cùng resources theo thứ tự ngược nhau

**Vấn đề:** `ConfirmReservation` update `Reservations` rồi `Inventory`; `CancelReservation` update `Inventory` rồi `Reservations`.

**Tại sao xảy ra:** Hai concurrent transactions có thể mỗi bên giữ lock trên resource thứ nhất và chờ resource thứ hai đang bị transaction kia giữ, tạo cycle trong wait-for graph.

**Ảnh hưởng production:** SQL Server phải chọn deadlock victim và rollback một transaction. Retry storm có thể tăng latency và load, đặc biệt khi traffic cao.

**Cách sửa:** Chọn một lock/update ordering nhất quán cho mọi code path chạm cùng aggregate resources, ví dụ luôn xử lý reservation trước rồi inventory, hoặc ngược lại dựa trên data model. Xác minh bằng deadlock graph thay vì chỉ suy luận từ source.

### Critical — Business state transition không được enforce trong `UPDATE`

**Vấn đề:** Confirm luôn set `Confirmed`; cancel luôn set `Cancelled` bất kể current status.

**Tại sao xảy ra:** Procedure đọc trạng thái bằng `NOLOCK` nhưng kết quả read không tham gia atomic predicate của write.

**Ảnh hưởng production:** Hai concurrent commands có thể overwrite trạng thái nhau. Inventory có thể bị trừ/cộng nhiều lần dù transition business chỉ nên xảy ra một lần.

**Cách sửa:** Enforce transition trong write predicate, ví dụ `UPDATE ... WHERE Id=@ReservationId AND Status='Pending'` cho confirm, và kiểm tra `@@ROWCOUNT`. Cancel phải xác định rõ allowed source states theo business. Chỉ thay inventory khi state transition thật sự thành công.

### Critical — Không enforce inventory invariant khi decrement

**Vấn đề:** `AvailableQuantity = AvailableQuantity - 1` không có guard `AvailableQuantity > 0`.

**Tại sao xảy ra:** Availability được đọc/assume ngoài atomic mutation.

**Ảnh hưởng production:** Concurrent confirms có thể đưa inventory âm hoặc tạo oversell semantics tùy schema/workflow.

**Cách sửa:** Dùng atomic conditional update, ví dụ `UPDATE ... SET AvailableQuantity = AvailableQuantity - 1 WHERE ProductId=@ProductId AND AvailableQuantity > 0`, kiểm tra row count và rollback/return domain conflict khi không còn stock. Có thể bổ sung database constraint `CHECK (AvailableQuantity >= 0)` như defense in depth nếu domain cho phép.

### High — `NOLOCK` không giải quyết write-write deadlock và cho phép inconsistent reads

**Vấn đề:** Team dùng `WITH (NOLOCK)` như deadlock fix.

**Tại sao xảy ra:** Hint này ảnh hưởng read locking/isolation behavior của câu select nhưng các `UPDATE` vẫn cần write locks. Nó còn cho phép dirty/non-repeatable/phantom-style observations theo semantics tương ứng.

**Ảnh hưởng production:** Logic có thể ra quyết định dựa trên dữ liệu chưa commit hoặc không nhất quán, trong khi deadlock giữa write paths vẫn tồn tại.

**Cách sửa:** Bỏ `NOLOCK` khỏi business-decision reads. Tốt hơn nữa, loại bỏ read-then-write không cần thiết bằng conditional atomic updates. Nếu muốn thay đổi isolation strategy như read committed snapshot, đánh giá ở database/workload level; không coi đó là patch tự động cho mọi deadlock.

### High — Artificial delay kéo dài thời gian giữ locks

**Vấn đề:** `WAITFOR DELAY` nằm bên trong transaction.

**Tại sao xảy ra:** Transaction giữ locks trong khi cố tình không làm useful work.

**Ảnh hưởng production:** Tăng contention window, deadlock probability và latency. Trong thực tế, tương đương có thể đến từ external call, slow query hoặc CPU work đặt trong transaction.

**Cách sửa:** Bỏ delay. Giữ transaction càng ngắn càng tốt và không gọi network/external dependency trong transaction database nếu không có lý do đặc biệt.

### High — Retry vô hạn có thể biến deadlock thành latency/load storm

**Vấn đề:** `while (true)` retry mọi deadlock không có max attempts, deadline hay jitter.

**Tại sao xảy ra:** Deadlock được coi là transient vô hạn mà không xét request budget/root cause.

**Ảnh hưởng production:** Một request có thể giữ thread/task lifecycle rất lâu, tạo thêm DB traffic và khiến p99 tăng mạnh. Khi nhiều instances retry đồng nhịp, contention có thể tệ hơn.

**Cách sửa:** Retry có giới hạn, respect cancellation/deadline và dùng backoff/jitter phù hợp. Retry chỉ sau khi transaction đã rollback sạch. Ghi metric số retry. Nếu vượt budget, fail rõ ràng để upstream có thể xử lý thay vì vô hạn.

### High — Không xác minh affected rows nên business failure có thể bị coi là success

**Vấn đề:** Procedures không kiểm tra update có chạm đúng row hay không.

**Tại sao xảy ra:** Missing reservation/product hoặc transition conflict không được phân biệt với success.

**Ảnh hưởng production:** API có thể báo thành công dù không đổi state, hoặc inventory update fail nhưng reservation đã đổi nếu error handling không rollback đúng.

**Cách sửa:** Kiểm tra `@@ROWCOUNT` sau critical conditional writes. Dùng `SET XACT_ABORT ON` và `TRY/CATCH` để rollback transaction khi error xảy ra; trả domain-specific outcome phù hợp cho application.

### High — Error handling transaction chưa an toàn

**Vấn đề:** Procedure không có `TRY/CATCH`, `XACT_ABORT`, rollback path explicit.

**Tại sao xảy ra:** Code giả định mọi statement sau `BEGIN TRANSACTION` hoặc commit hoặc engine tự xử lý theo cách application mong muốn.

**Ảnh hưởng production:** Một số lỗi có thể để transaction state khó quản lý ở connection/session, làm connection pooling và subsequent commands gặp behavior khó đoán nếu caller không xử lý chuẩn.

**Cách sửa:** Dùng `SET XACT_ABORT ON`; bọc transaction trong `TRY/CATCH`; rollback nếu `XACT_STATE() <> 0`; `THROW` lại lỗi. Application phải tạo command/transaction boundary sạch cho mỗi attempt.

### Medium — Có thể thiếu index phù hợp cho access path thực tế

**Vấn đề:** Chỉ biết có primary key index; chưa xác minh `Inventory(ProductId)` hay các access predicates đều seek đúng.

**Tại sao xảy ra:** Lock contention/deadlock phụ thuộc cả statement order lẫn số rows/pages mà query phải touch.

**Ảnh hưởng production:** Scan hoặc lookup tốn thời gian có thể mở rộng lock duration/scope, làm contention nặng hơn.

**Cách sửa:** Xem actual execution plan, indexes và deadlock graph. Bảo đảm predicates business quan trọng có access path phù hợp. Không thêm index theo phỏng đoán; index thêm cũng tăng write cost.

### Medium — Logging thiếu context để điều tra deadlock pattern

**Vấn đề:** App chỉ log exception chung.

**Tại sao xảy ra:** Không capture operation name, retry count, request correlation hoặc identifiers an toàn.

**Ảnh hưởng production:** Khó nhóm deadlocks theo procedure/product hot spot hay release, và khó biết retry có đang cứu request hay chỉ kéo dài incident.

**Cách sửa:** Structured log/metrics cho operation, retry attempt, elapsed budget, deadlock count, timeout, product/reservation identifiers khi policy cho phép; ở SQL Server thu deadlock graph bằng cơ chế diagnostics phù hợp và correlate theo thời gian/request.

## Phiên bản đề xuất

Một hướng đơn giản là giữ thứ tự update nhất quán, enforce state/inventory preconditions atomically và làm transaction ngắn. Ví dụ dưới đây giả định business rule: chỉ `Pending` mới được confirm; chỉ `Confirmed` mới được cancel và cancel trả lại đúng một inventory unit.

```sql
CREATE PROCEDURE dbo.ConfirmReservation
    @ReservationId bigint,
    @ProductId bigint
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- Thứ tự nhất quán: Reservation -> Inventory.
        UPDATE dbo.Reservations
        SET Status = 'Confirmed',
            UpdatedAt = SYSUTCDATETIME()
        WHERE Id = @ReservationId
          AND ProductId = @ProductId
          AND Status = 'Pending';

        IF @@ROWCOUNT <> 1
            THROW 51001, 'Reservation is not in a confirmable state.', 1;

        UPDATE dbo.Inventory
        SET AvailableQuantity = AvailableQuantity - 1
        WHERE ProductId = @ProductId
          AND AvailableQuantity > 0;

        IF @@ROWCOUNT <> 1
            THROW 51002, 'Inventory is unavailable.', 1;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;
GO

CREATE PROCEDURE dbo.CancelReservation
    @ReservationId bigint,
    @ProductId bigint
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- Giữ cùng thứ tự Reservation -> Inventory.
        UPDATE dbo.Reservations
        SET Status = 'Cancelled',
            UpdatedAt = SYSUTCDATETIME()
        WHERE Id = @ReservationId
          AND ProductId = @ProductId
          AND Status = 'Confirmed';

        IF @@ROWCOUNT <> 1
            THROW 51003, 'Reservation is not in a cancellable state.', 1;

        UPDATE dbo.Inventory
        SET AvailableQuantity = AvailableQuantity + 1
        WHERE ProductId = @ProductId;

        IF @@ROWCOUNT <> 1
            THROW 51004, 'Inventory row was not found.', 1;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;
GO
```

Nếu nhiều reservations/products được update trong một transaction, còn phải định nghĩa ordering giữa nhiều IDs, ví dụ sort keys trước khi acquire locks, nếu không vẫn có thể tạo cycle khác.

Application retry có thể bounded:

```csharp
const int maxAttempts = 3;

for (var attempt = 1; attempt <= maxAttempts; attempt++)
{
    try
    {
        await command.ExecuteNonQueryAsync(cancellationToken);
        return;
    }
    catch (SqlException ex) when (ex.Number == 1205 && attempt < maxAttempts)
    {
        var delay = TimeSpan.FromMilliseconds(
            40 * attempt + Random.Shared.Next(0, 40));

        await Task.Delay(delay, cancellationToken);
    }
}
```

Trong production code, mỗi retry attempt phải dùng command/transaction state hợp lệ sau rollback; nếu data access abstraction recreate command/connection per attempt thì contract cần rõ ràng. Retry budget phải nằm trong request timeout/SLO chung.

Có thể dùng optimistic concurrency, application lock hoặc isolation khác cho một số workflow, nhưng không nên thêm chúng trước khi các invariants đơn giản và lock order hiện tại đã đúng. Distributed lock càng không phải lựa chọn đầu tiên cho hai rows nằm trong cùng SQL Server transaction boundary.

## Giải thích thiết kế sau khi sửa

Fix quan trọng nhất không phải “bắt deadlock tốt hơn” mà là giảm xác suất tạo cycle và bảo vệ business invariant ngay trong write path.

Conditional update biến validation và mutation thành một atomic statement đối với state cần kiểm tra. Nó loại bỏ nhu cầu `SELECT ... NOLOCK` rồi hy vọng dữ liệu vẫn đúng tới lúc update.

Consistent lock ordering làm các transactions cạnh tranh có xu hướng chờ theo cùng một hướng thay vì tạo cycle. Tuy nhiên deadlock vẫn có thể đến từ plan/index/foreign key/trigger hoặc code path khác. Vì vậy deadlock graph là evidence bắt buộc trước khi tuyên bố đã tìm đủ root cause.

Retry bounded vẫn hữu ích vì deadlock có thể xảy ra ngay cả trong hệ thống được thiết kế tốt. Nhưng retry phải là safety net, không phải cơ chế che một pattern có thể tái tạo liên tục.

## Trade-offs

Giữ transaction ngắn và conditional update làm code chặt chẽ hơn nhưng yêu cầu business rules về state transition được định nghĩa rõ. Nếu Product cho phép cancel từ nhiều trạng thái, predicate phải phản ánh đúng domain chứ không copy ví dụ máy móc.

Database constraint cho `AvailableQuantity >= 0` tăng defense in depth nhưng có thể không phù hợp nếu domain cho phép temporary negative allocation/backorder. Quyết định phải dựa trên domain invariant thực.

Retry ít lần có thể làm một số request fail sớm hơn thay vì “cố đến cùng”, nhưng nó bảo vệ request budget và database khỏi retry amplification. Upstream/UI cần contract rõ cho transient failure.

Changing isolation level có thể cải thiện một số read/write contention nhưng ảnh hưởng semantics và tempdb/version-store/resource usage tùy lựa chọn. Không nên bật chỉ để tránh phân tích deadlock hiện tại.

## Cách kiểm thử

1. **Concurrency integration test:** chạy confirm/cancel đồng thời trên cùng reservation/product hàng nghìn lần trong test environment; xác minh không có impossible state và inventory delta đúng theo successful transitions.
2. **Deadlock regression test:** orchestrate hai sessions theo access pattern cũ để chứng minh deadlock có thể xảy ra, sau đó chạy implementation mới và so sánh deadlock rate.
3. **Invariant test:** concurrent double-confirm chỉ có một transition success; inventory giảm đúng một đơn vị và không âm nếu đó là domain invariant.
4. **Failure-path test:** inject SQL error giữa hai updates; xác minh transaction rollback cả reservation và inventory.
5. **Load test:** representative hot-product traffic; đo throughput, p95/p99, lock waits, deadlock count và retry count trước/sau fix.

## Quan sát trong production

Theo dõi:

- deadlock count/rate và deadlock graphs;
- lock wait time và top wait categories liên quan;
- retry attempts per request và retry-exhausted count;
- stored procedure duration p50/p95/p99;
- SQL timeout/error rate;
- hot `ProductId`/operation patterns theo logging policy;
- execution plans và regressions cho hai procedures;
- rows affected/domain conflict rate;
- API p95/p99 và request cancellation;
- inventory invariant violations/audit reconciliation nếu domain cần.

Khi incident xảy ra, dùng chuỗi: **symptom → deadlock graph/waits → competing hypotheses → reproduce → change → load/concurrency verification**, thay vì thêm `NOLOCK` hoặc tăng retry count theo cảm tính.

1. Nếu deadlock graph cho thấy một trigger hoặc foreign-key lookup chứ không phải hai statements chính tạo cycle, bạn sẽ thay đổi investigation/fix như thế nào?
2. Khi nào `READ_COMMITTED_SNAPSHOT` có thể giúp workload và những trade-offs nào cần đánh giá trước khi bật?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Elasticsearch query semantics phải khớp mapping: analyzed `text` phục vụ full-text search, còn `keyword` phù hợp với exact filtering/sorting/aggregation semantics.
- Deep offset pagination, broad wildcard-like query, full `_source` và exact total hits có thể tạo resource cost đáng kể; phải đo query shape trước khi scale cluster.
- Cursor/search-after chỉ đáng dùng khi browse sâu là requirement thật; sort cần deterministic tie-breaker.
- SQL deadlock không được sửa đúng bằng `NOLOCK`. Write paths cần transaction ngắn, lock ordering nhất quán, access paths phù hợp và business invariants được enforce atomically.
- Retry cho deadlock nên bounded và observable. Retry là resilience layer, không phải thay thế root-cause analysis.

## Mẫu tư duy cần nhớ

- Match data/query semantics trước khi tối ưu infrastructure.
- Measure query cost before scaling capacity.
- Enforce business preconditions trong cùng atomic write khi có thể.
- Giữ lock ordering nhất quán và transaction càng ngắn càng tốt.
- Dùng retry như safety net có budget, không dùng để che một lỗi lặp lại có hệ thống.
