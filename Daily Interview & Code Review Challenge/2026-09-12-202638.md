# Câu 1 — Transaction nhìn “đúng logic” nhưng production vẫn deadlock: SQL Server đang khóa gì, theo thứ tự nào và vì sao retry không phải toàn bộ câu trả lời?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** SQL Server, transactions, locking, deadlocks, isolation levels, execution plans, indexes, EF Core, retry, idempotency, production diagnostics

## Bối cảnh

Một approval system dùng ASP.NET Core + EF Core + SQL Server. Khi manager approve một request, hệ thống cập nhật trạng thái request và ghi audit record.

Code rút gọn:

```csharp
public async Task ApproveAsync(
    long requestId,
    int approverId,
    CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var request = await _db.ApprovalRequests
        .SingleAsync(x => x.Id == requestId, ct);

    if (request.Status != ApprovalStatus.Pending)
        throw new InvalidOperationException("Request is not pending.");

    var pendingCount = await _db.ApprovalRequests
        .Where(x => x.EmployeeId == request.EmployeeId &&
                    x.Status == ApprovalStatus.Pending)
        .CountAsync(ct);

    request.Status = ApprovalStatus.Approved;
    request.ApprovedBy = approverId;
    request.ApprovedAt = DateTimeOffset.UtcNow;

    _db.ApprovalAudits.Add(new ApprovalAudit
    {
        RequestId = requestId,
        ApproverId = approverId,
        PendingCountAtApproval = pendingCount,
        CreatedAt = DateTimeOffset.UtcNow
    });

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Ở production:

- traffic bình thường gần như không có lỗi;
- trong kỳ chốt timesheet, nhiều managers approve đồng thời cho cùng một employee/team;
- SQL Server bắt đầu xuất hiện deadlock victim errors;
- Application Insights cho thấy một số request retry ở tầng HTTP và cuối cùng thành công;
- DBA nói execution plan của `CountAsync` đôi lúc scan nhiều rows hơn dự kiến;
- team đề xuất ba hướng:
  1. đổi isolation level sang `READ UNCOMMITTED` để giảm lock;
  2. bọc toàn bộ method trong retry 5 lần;
  3. thêm `lock` trong C# quanh `ApproveAsync`.

Hệ thống chạy nhiều application instances.

## Câu hỏi chính

Hãy giải thích cơ chế deadlock có thể hình thành trong scenario này, cách SQL Server phát hiện và chọn deadlock victim, tại sao cùng một đoạn code application vẫn có thể lock resources theo thứ tự khác nhau tùy execution plan/data access, và bạn sẽ điều tra rồi sửa theo hướng nào trước khi thêm retry. Đồng thời hãy phân tích vì sao `READ UNCOMMITTED`, C# `lock`, hoặc retry mù có thể che symptom nhưng không giải quyết đúng root cause.

## Câu hỏi làm rõ nên cân nhắc

1. Deadlock graph cho thấy những statements, indexes, lock modes và resource types nào tham gia?
2. Có index phù hợp cho `(EmployeeId, Status)` và request lookup hay không, statistics có stale không?
3. Có transaction khác cập nhật cùng `ApprovalRequests`/audit tables theo thứ tự ngược lại không?
4. HTTP caller có thể gửi duplicate approve request, và operation có idempotency/concurrency semantics nào?
5. Database đang dùng `READ COMMITTED`, `READ_COMMITTED_SNAPSHOT`, hay isolation configuration khác?

## Gợi ý tư duy

### Gợi ý 1

Deadlock không đơn giản là “query chậm”. Nó cần một cycle chờ tài nguyên. Hãy tìm **resource order** giữa các transactions.

### Gợi ý 2

Execution plan và index quyết định phạm vi rows/pages/keys mà query đụng tới. Một `CountAsync` tưởng là read-only vẫn có thể tham gia locking chain dưới isolation phù hợp.

### Gợi ý 3

Retry nên là lớp resilience cuối cùng cho transient deadlock victim, nhưng thiết kế tốt vẫn phải giảm xác suất tạo cycle và bảo đảm operation retry an toàn.

## Cấu trúc trả lời đề xuất

1. Xác nhận deadlock thay vì đoán từ timeout.
2. Đọc deadlock graph và xác định cycle/resource order.
3. Phân tích execution plans/indexes và transaction scope.
4. Phân biệt blocking dài với deadlock.
5. Sửa lock footprint/order trước.
6. Đánh giá isolation/concurrency semantics.
7. Thêm bounded retry nếu operation idempotent hoặc được bảo vệ phù hợp.
8. Kiểm thử concurrent approval.
9. Theo dõi deadlock rate, lock waits và query behavior sau sửa.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết deadlock cần vòng chờ giữa ít nhất hai transactions.
- Không coi mọi blocking là deadlock.
- Yêu cầu deadlock graph/Extended Events hoặc evidence tương đương.
- Nhận ra query/index plan ảnh hưởng lock footprint và lock order.
- Không đề xuất `READ UNCOMMITTED` cho workflow cần correctness mà không phân tích dirty reads.
- Nhận ra C# `lock` chỉ đồng bộ trong process và vô dụng giữa nhiều instances nếu dùng như distributed fix.
- Retry deadlock phải bounded và operation phải retry-safe.

### Điểm cộng

- Xem lại transaction scope để giảm thời gian giữ lock.
- Đề xuất composite/covering index khi execution-plan evidence hỗ trợ.
- Cân nhắc optimistic concurrency (`rowversion`) cho trạng thái request.
- Phân tích `READ_COMMITTED_SNAPSHOT` như một option để giảm reader/writer blocking nhưng không coi nó là thuốc chữa mọi deadlock.
- Phân biệt deadlock do reader/writer với writer/writer.

### Senior+

- Liên hệ deadlock victim selection với deadlock priority/cost nhưng không dựa vào nó như fix chính.
- Biết deadlock graph có thể chỉ ra key/page/object locks và statements thực tế.
- Thiết kế state transition `Pending → Approved` thành atomic conditional update khi phù hợp.
- Nhận ra retry ở HTTP layer có thể duplicate side effects nếu audit/event/notification không idempotent.
- Có chiến lược observability và load/concurrency test tái hiện production pattern.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng việc đổi isolation hoặc thêm retry. Trước hết cần xác nhận đây thực sự là SQL Server deadlock và thu **deadlock graph**. Graph cho biết hai hay nhiều sessions đang giữ resource gì, chờ resource gì, statement nào chạy, index nào liên quan và transaction nào bị chọn làm victim.

Một cycle điển hình có thể là:

- Transaction A đọc/update request row X rồi chạy aggregate theo `EmployeeId/Status`, giữ hoặc chờ locks trên index range/pages.
- Transaction B đang xử lý request Y cùng employee, đi qua aggregate/index theo một access path rồi update row Y hoặc đụng resource theo thứ tự khác.
- Nếu mỗi transaction giữ resource mà transaction kia cần, cycle hình thành.

Không nên khẳng định đúng cycle này nếu chưa có graph. Nhưng đây là loại hypothesis cần verify.

`CountAsync` không phải “miễn lock” chỉ vì là read. Dưới `READ COMMITTED`, SQL Server vẫn dùng shared locks trong quá trình đọc theo semantics của engine/configuration. Nếu thiếu index `(EmployeeId, Status)` phù hợp, query có thể scan nhiều keys/pages hơn, tăng lock footprint và thời gian giao cắt với concurrent writers.

Tôi sẽ xem execution plan thực tế của query và index usage. Nếu evidence cho thấy scan lớn, index phù hợp có thể giảm số rows/pages touched và transaction duration. Ví dụ một index trên:

```sql
CREATE INDEX IX_ApprovalRequests_EmployeeId_Status
ON ApprovalRequests(EmployeeId, Status);
```

có thể hữu ích nếu query pattern/distribution phù hợp, nhưng phải validate bằng execution plan, cardinality và write overhead thay vì thêm index theo thói quen.

Tiếp theo tôi xem transaction scope. Nếu `pendingCount` không cần transactionally consistent với exact approval state, có thể tính ngoài transaction hoặc redesign. Nếu nó phải phản ánh một invariant tại thời điểm approval, cần giữ semantics rõ và có thể dùng cách khác thay vì một aggregate rộng trong cùng transaction.

Một hướng mạnh hơn là biến state transition thành atomic conditional update:

```sql
UPDATE ApprovalRequests
SET Status = @Approved,
    ApprovedBy = @ApproverId,
    ApprovedAt = @Now
WHERE Id = @RequestId
  AND Status = @Pending;
```

Sau đó kiểm tra affected rows. Cách này giảm read-before-write race và làm concurrency semantics rõ hơn. Nếu dùng EF Core, có thể implement bằng tracked entity + `rowversion` hoặc `ExecuteUpdateAsync`/raw SQL tùy version/requirements, nhưng phải giữ audit/transaction correctness.

`READ UNCOMMITTED` là lựa chọn nguy hiểm cho business workflow nếu `pendingCount` hoặc status logic không được phép thấy uncommitted data. Nó có thể giảm một số reader locks nhưng đổi correctness semantics. Tôi chỉ dùng nếu business thật sự chấp nhận dirty/non-repeatable behavior, điều thường không phù hợp approval state.

`lock` trong C# chỉ serialize threads trong **một process** với cùng lock object. Hệ thống nhiều instances nên instance A và B vẫn chạy đồng thời. Distributed lock cũng không nên được thêm ngay nếu database đã là nơi sở hữu invariant; database concurrency control thường là boundary phù hợp hơn.

Retry vẫn hữu ích vì deadlock có thể xảy ra hiếm ngay cả khi thiết kế tốt. Nhưng retry phải:

- chỉ áp dụng cho deadlock/transient cases phù hợp;
- bounded;
- có backoff/jitter nếu cần;
- bắt đầu lại toàn transaction từ đầu;
- bảo đảm audit/notifications/external side effects không bị duplicate.

Nếu HTTP retry hiện tại gửi lại toàn request, tôi đặc biệt kiểm tra idempotency. Nếu lần đầu commit database nhưng response mất trên network rồi client retry, logic `Status != Pending` có thể trả lỗi dù operation thực tế đã thành công. API contract cần định nghĩa duplicate approve behavior rõ hơn.

`READ_COMMITTED_SNAPSHOT` có thể giảm reader/writer blocking bằng row versioning, nhưng không loại bỏ writer/writer conflicts và không được bật như một patch thiếu phân tích. Nó có storage/behavior implications và cần test toàn workload.

Cuối cùng tôi chạy concurrency test với nhiều approvals cho cùng employee/team, cùng dataset/index distribution giống production. Đo deadlock count, lock waits, transaction duration, query reads, p95/p99 và correctness của audit rows. Sau release, theo dõi deadlocks qua Extended Events/SQL telemetry và correlate với endpoint/version.

## Mẫu trả lời trong phỏng vấn

“Trước tiên tôi cần deadlock graph vì deadlock là một cycle chờ tài nguyên, không phải cứ query chậm là deadlock. Tôi muốn biết statement nào giữ lock nào, đang chờ key/page/index nào và thứ tự access resources giữa các transactions.

Trong code này, `CountAsync` nằm trong transaction và có thể mở rộng lock footprint, đặc biệt nếu thiếu index `(EmployeeId, Status)` hoặc execution plan scan nhiều rows. Hai approvals cùng employee có thể đụng cùng index/resources trong thứ tự khác nhau với update path và tạo cycle. Tôi sẽ kiểm tra actual execution plan, index, statistics và transaction scope trước.

Tôi không chọn `READ UNCOMMITTED` vì approval workflow thường không chấp nhận dirty reads. C# `lock` cũng không giải quyết multi-instance. Retry có thể thêm cho deadlock victim, nhưng phải bounded và retry-safe; nếu audit hay external side effect bị duplicate thì retry mù còn tạo bug mới.

Tôi cũng cân nhắc làm state transition atomic, ví dụ update `WHERE Id = ... AND Status = Pending`, hoặc optimistic concurrency với `rowversion`, rồi giữ transaction ngắn. Nếu aggregate không cần cùng consistency boundary, có thể tách nó khỏi critical transaction. Sau đó tôi concurrency-test scenario production và theo dõi deadlock graph/rate, lock waits, logical reads và latency để verify fix.”

## Câu hỏi đào sâu

1. Nếu deadlock graph cho thấy hoàn toàn writer/writer trên hai indexes chứ không liên quan `CountAsync`, bạn thay đổi investigation và fix ra sao?
2. Tôi đề xuất bật `READ_COMMITTED_SNAPSHOT` toàn database ngay vì nó thường giảm blocking; bạn đồng ý hay phản đối, và cần kiểm tra gì trước?
3. Nếu API phải vừa update request vừa publish event sang Azure Service Bus, retry transaction cần kết hợp với Outbox/idempotency như thế nào?

## Lỗi trả lời thường gặp

- Gọi blocking dài là deadlock mà không yêu cầu deadlock graph.
- Đề xuất `NOLOCK`/`READ UNCOMMITTED` như performance fix mặc định.
- Dùng C# `lock` trong hệ thống multi-instance như distributed concurrency control.
- Chỉ tăng retry count mà không sửa lock order/footprint.
- Thêm index nhưng không xem execution plan và write cost.

## Thang điểm 0–10

- **0–2:** Chỉ nói “deadlock do nhiều request cùng lúc”, không giải thích cycle hoặc evidence.
- **3–4:** Biết lock/deadlock cơ bản nhưng fix chủ yếu là retry/index chung chung.
- **5–6:** Có deadlock graph, execution plan, transaction-scope reasoning và loại bỏ được các fix sai.
- **7–8:** Kết nối lock footprint/order với indexes, atomic state transition, retry safety và concurrency testing.
- **9–10:** Phân tích có điều kiện, tách correctness khỏi performance, thiết kế retry/idempotency/observability đầy đủ và biết khi nào isolation-level change thực sự hợp lý.

# Câu 2 — Slot swap báo thành công nhưng production 500/401 theo từng instance: deployment artifact, slot settings hay identity/configuration đang sai?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure App Service, deployment slots, ASP.NET Core, Managed Identity, Key Vault, configuration, health checks, release safety, Application Insights, incident investigation

## Bối cảnh

Một ASP.NET Core API chạy trên Azure App Service Linux với 6 instances. Team dùng deployment slot `staging` và swap sang `production` để giảm downtime.

Application dùng:

- SQL Server connection string từ App Service configuration;
- một external CRM API secret từ Azure Key Vault;
- Managed Identity để đọc Key Vault;
- Application Insights;
- health endpoint `/health/ready` kiểm tra SQL và một critical CRM dependency.

Release flow:

1. deploy artifact mới vào `staging`;
2. chạy smoke test trực tiếp staging URL;
3. swap `staging → production`;
4. theo dõi dashboard vài phút.

Incident sau release:

- Azure Portal báo swap thành công;
- khoảng 60% requests production trả `200`;
- khoảng 25% trả `500` khi gọi CRM;
- khoảng 15% authenticated requests trả `401` trong 5–10 phút đầu;
- restart production App Service làm tình hình tạm ổn hơn;
- staging trước swap đã pass smoke test;
- logs cho thấy một số instances resolve được Key Vault secret, một số log `403` khi truy cập Key Vault;
- deployment pipeline không ghi lại artifact digest/version theo instance;
- một engineer đề xuất swap ngược ngay;
- engineer khác muốn restart tất cả instances và chờ cache/config “ổn định”.

Bạn vào incident khi business traffic đang bị ảnh hưởng nhưng chưa biết root cause duy nhất.

## Câu hỏi chính

Bạn sẽ điều hành incident theo thứ tự nào để giảm impact nhưng vẫn giữ đủ evidence, phân biệt artifact problem với slot-specific configuration/identity/key rotation/warmup problems, và quyết định khi nào rollback/swap back là an toàn? Sau đó hãy đề xuất release design giúp slot swap deterministic hơn, đặc biệt với slot settings, Managed Identity, Key Vault references/secrets, authentication configuration và health verification.

## Câu hỏi làm rõ nên cân nhắc

1. Những App Settings/connection strings nào được đánh dấu deployment-slot settings và expected values của staging/production là gì?
2. Managed Identity là system-assigned hay user-assigned, và identity nào có Key Vault permissions ở từng slot?
3. `401` đến từ token validation, issuer/audience config, Data Protection/cookie state hay upstream authentication layer?
4. Các failed requests correlate với instance ID, deployment version hoặc cold-start window nào?
5. Swap có warmup/health-gating nào, và smoke test staging có dùng đúng production-like identity/configuration path không?

## Gợi ý tư duy

### Gợi ý 1

“Swap succeeded” chỉ nói platform operation hoàn thành. Nó không chứng minh mọi instance đang chạy cùng artifact/config và mọi dependency credential đều đúng.

### Gợi ý 2

Deployment slot có hai dimensions dễ bị trộn: **content/artifact** và **configuration that sticks or swaps**. Identity/Key Vault permissions có thể tạo behavior khác staging dù code giống hệt.

### Gợi ý 3

Rollback chỉ an toàn nếu database/schema/external side effects vẫn backward compatible. Đừng swap back theo phản xạ nếu release đã thực hiện irreversible migration.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius/SLO/security impact.
2. Giữ evidence theo instance/version/configuration state.
3. Stabilize bằng traffic/rollback decision có điều kiện.
4. Phân loại `500` CRM và `401` thành failure reasons riêng.
5. So sánh staging/production slot settings, identities và artifact identity.
6. Xác minh dependency access từ từng instance/slot.
7. Sửa root cause và verify production cohort.
8. Cải thiện pipeline, warmup, health gates, rollback compatibility.
9. Bổ sung telemetry/alerts theo release version và instance.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không dùng portal “swap success” như bằng chứng application healthy.
- Correlate failures theo instance/version.
- Kiểm tra slot-specific configuration và Managed Identity permissions.
- Tách `401` và `500` thành hypotheses riêng.
- Không restart toàn fleet trước khi thu evidence tối thiểu nếu hệ thống chưa hoàn toàn down.
- Rollback phải xét database/schema compatibility.
- Artifact/version phải immutable và observable.

### Điểm cộng

- Biết staging smoke test có thể không đại diện production slot settings/identity.
- Có production pre/post-swap validation.
- Có health/warmup strategy nhưng không cho dependency transient issue biến thành restart storm.
- Đề xuất user-assigned Managed Identity khi cần identity ổn định giữa slots, nếu platform/organization phù hợp.
- Đề cập Key Vault access policy/RBAC và secret reference/version lifecycle.

### Senior+

- Xem deployment như state transition nhiều thành phần: artifact, config, identity, schema, secrets, warmup, traffic.
- Có automated configuration-diff/allow-list check trước swap.
- Thiết kế expand/contract migration để swap back được.
- Phân biệt secret retrieval failure với application-level secret cache behavior.
- Dùng release markers/Application Insights deployment annotations/version dimensions để RCA nhanh.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng impact: tỷ lệ `5xx/401`, endpoints nào bị ảnh hưởng, authentication có security risk hay chỉ availability failure, và error budget/SLO đang burn thế nào. Vì 60% requests vẫn thành công, symptom phụ thuộc instance là hypothesis mạnh; tôi muốn giữ một phần evidence trước khi restart toàn bộ.

Tôi sẽ correlate request telemetry với:

- instance ID;
- application version/build SHA;
- slot;
- exception type;
- Key Vault dependency result;
- auth failure category;
- correlation ID.

Nếu failed CRM calls tập trung ở 2/6 instances và logs ở đó có Key Vault `403`, tôi kiểm tra identity thực tế của those workers/slot và Key Vault RBAC. Staging smoke test có thể pass vì staging slot dùng identity/config khác. Điều đó chứng minh “code mới tốt ở staging” chưa đủ.

Tôi sẽ inventory các settings và phân loại:

- settings phải **stick to slot**: production connection strings, environment-specific endpoints, possibly auth callback/issuer configuration depending design;
- settings có thể swap cùng application;
- secrets nên referenced/managed qua Key Vault/identity, không copy plaintext trong pipeline.

Không nên nói chung chung “mọi setting production đều sticky”; cần dựa vào desired deployment semantics.

Managed Identity cũng cần xác minh chính xác. Nếu dùng system-assigned identity, staging và production slots có thể có identity lifecycle/permissions khác nhau tùy App Service configuration. Nếu business cần cùng principal across slots cho một resource, user-assigned identity có thể là lựa chọn hợp lý, nhưng phải cân nhắc least privilege và blast radius. Không nên chuyển identity model chỉ để né việc cấu hình RBAC đúng.

Với `401`, tôi không giả định Key Vault là cùng root cause. Tôi phân loại authentication failure: token signature, issuer/audience, clock, Data Protection/cookie key, B2C/Entra config, middleware config. Nếu API bearer-token only thì Data Protection có thể không liên quan; nếu cookie-based auth có cross-instance keys thì lại là hypothesis khác. Failure reason phải đến từ telemetry, không từ tỷ lệ.

Về rollback: swap back có thể là stabilization tốt nếu:

- previous artifact/config state đã known-good;
- database migration backward compatible;
- external schema/event changes không irreversible;
- rollback không táiintroduce security issue.

Nếu release đã drop/rename DB column mà old app cần, swap back có thể làm outage nặng hơn. Vì vậy pipeline dài hạn phải dùng expand/contract migration.

Nếu chưa rollback, có thể drain/remove unhealthy instances hoặc fix RBAC/config rồi recycle targeted instances, tùy App Service capabilities và urgency. Tôi tránh restart toàn fleet trước evidence vì nó có thể xóa symptom/caches mà không biết root cause.

Dài hạn, release flow nên có:

1. immutable artifact version/build SHA;
2. staging deploy;
3. configuration validation/diff against expected slot contract;
4. identity/Key Vault permission check;
5. migration step theo expand/contract nếu cần;
6. warmup và functional smoke tests dùng dependency path thực;
7. swap;
8. post-swap health verification trên production hostname;
9. monitor error rate/latency/auth/dependencies theo version;
10. automated pause/rollback threshold nếu compatibility cho phép.

Application nên expose version endpoint/telemetry field, ví dụ build SHA, nhưng không lộ secret/config. Application Insights deployment marker giúp correlate incident với rollout.

Health endpoint cũng cần semantics đúng. `readiness` có thể check critical SQL/CRM nếu API không phục vụ hữu ích khi dependency down. Liveness không nên restart process chỉ vì CRM transiently fail. Trên App Service, health check configuration/instance removal behavior cần được xác minh theo platform docs/version hiện hành trước rollout; không assume Kubernetes semantics.

Testing gồm staging identity failure, expired/rotated secret, wrong slot setting, swap-back rehearsal và auth config mismatch. Một release process chưa từng test rollback thì rollback plan chỉ là tài liệu.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không coi ‘slot swap succeeded’ là release succeeded. Symptom 60% success và errors theo subset instances làm tôi ưu tiên correlate request với instance ID, build SHA, Key Vault dependency và auth failure reason trước khi restart toàn fleet.

Với CRM 500 và Key Vault 403, tôi so sánh identity/RBAC giữa staging và production slots và inventory các settings nào sticky. Staging smoke test có thể pass với identity khác nên không chứng minh production path đúng. `401` tôi điều tra riêng: issuer/audience/signature/config hoặc cookie/Data Protection tùy auth model, không gộp mọi lỗi về Key Vault.

Rollback bằng swap back chỉ thực hiện nếu previous version còn tương thích với database và external changes. Nếu migration destructive thì rollback có thể nguy hiểm hơn. Dài hạn tôi dùng immutable artifact version, expand/contract schema, automated slot-config/identity validation, warmup, post-swap tests trên production hostname và telemetry theo version/instance.

Tôi cũng muốn health semantics đúng và release dashboard có error rate, auth failures, dependency 403/5xx, instance distribution. Mục tiêu là một swap deterministic: biết artifact nào, config nào, identity nào đang chạy và có thể chứng minh production healthy sau swap.”

## Câu hỏi đào sâu

1. Nếu staging và production bắt buộc dùng hai Managed Identities khác nhau vì least privilege, bạn thiết kế pre-swap validation thế nào để vẫn phát hiện RBAC drift?
2. Tôi muốn tự động swap back ngay khi 5xx >5% trong 2 phút; bạn đồng ý hay cần thêm guardrails nào?
3. Nếu release có database expand migration đã chạy nhưng code mới fail, rollback application version cần những compatibility guarantees gì?

## Lỗi trả lời thường gặp

- Restart tất cả instances ngay và làm mất evidence.
- Cho rằng staging pass thì production config/identity chắc chắn giống.
- Gộp mọi `401/500` vào một root cause.
- Swap back mà không kiểm tra schema compatibility.
- Không version artifact/telemetry nên không biết instance nào đang chạy binary nào.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/swap back.
- **3–4:** Có kiểm tra settings/logs nhưng thiếu instance/version correlation hoặc rollback safety.
- **5–6:** Incident flow hợp lý, biết slot settings/identity/Key Vault và phân tách auth failure.
- **7–8:** Có deterministic release design, immutable artifact, compatibility strategy, post-swap verification và telemetry.
- **9–10:** Xử lý tốt partial rollout/state drift, security/identity, rollback constraints, configuration contracts và automated release gates mà không over-engineer.

# Câu 3 — Xây search cho product catalog: SQL Server vẫn là source of truth, Elasticsearch nhanh hơn nhưng chấp nhận stale đến đâu và sync bằng cách nào?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, ASP.NET Core, search architecture, eventual consistency, indexing, Outbox Pattern, retries, observability, caching, API design, failure recovery

## Bối cảnh

Một e-commerce platform có khoảng 3 triệu products. Product master data được lưu trong SQL Server và cập nhật bởi admin/CMS workflows.

Business cần search mới với:

- full-text search theo product name/description;
- filters theo category, brand, price range, availability;
- autocomplete;
- sort theo relevance/price/newest;
- p95 search < 300 ms ở khoảng 500 search requests/second;
- product update thường phải xuất hiện trong search trong vòng 1–2 phút;
- price/availability thay đổi thường xuyên hơn descriptive content;
- SQL Server vẫn là source of truth cho order/checkout correctness;
- nếu search platform lỗi, website nên degrade hợp lý thay vì toàn bộ storefront down.

Team đang cân nhắc:

1. query trực tiếp SQL Server với full-text/indexes và không dùng Elasticsearch;
2. index toàn bộ product document vào Elasticsearch và coi đó là read model cho search;
3. mỗi lần product update thì application vừa commit SQL vừa gọi Elasticsearch synchronously;
4. dùng asynchronous indexing pipeline, nhưng team lo eventual consistency và duplicate events.

Không có requirement cho microservices; backend hiện là modular ASP.NET Core application.

## Câu hỏi chính

Hãy thiết kế search architecture phù hợp cho constraints trên. Bạn cần giải thích khi nào SQL-only vẫn đủ, nếu chọn Elasticsearch thì document/index design và synchronization boundary như thế nào, làm sao xử lý duplicate/missed/out-of-order updates, reindexing, mapping changes, partial failure, fallback, price/availability freshness, security, observability và rollout. Hãy nêu trade-off để chứng minh bạn không chọn Elasticsearch chỉ vì “search chuyên dụng thì phải dùng Elasticsearch”.

## Câu hỏi làm rõ nên cân nhắc

1. Search quality requirements thực sự cần analyzers, typo tolerance, relevance tuning, autocomplete phức tạp đến mức nào?
2. Price/availability freshness có cùng SLO 1–2 phút hay checkout chỉ cần verify lại từ SQL/source-of-truth?
3. Product update rate peak là bao nhiêu và một update có thể thay đổi bao nhiêu searchable fields?
4. Multi-language, market-specific catalog hoặc tenant separation có cần nằm trong index strategy không?
5. Khi Elasticsearch unavailable, business muốn hide search, dùng degraded SQL fallback, hay serve cached/popular results?

## Gợi ý tư duy

### Gợi ý 1

Tách **transactional truth** khỏi **search read model**. Search index có thể stale trong bounded window nếu checkout vẫn verify authoritative data.

### Gợi ý 2

Dual-write SQL + Elasticsearch synchronously tạo partial-failure problem. Hãy nghĩ đến durable change capture/outbox và idempotent indexing.

### Gợi ý 3

Reindex không chỉ là bulk copy. Mapping/analyzer changes cần versioned index, backfill, verification và alias/cutover strategy để rollback được.

## Cấu trúc trả lời đề xuất

1. Làm rõ search relevance/freshness/failure SLO.
2. So sánh SQL-only và Elasticsearch bằng workload evidence.
3. Định nghĩa source of truth và search document model.
4. Thiết kế change propagation và idempotency/order handling.
5. Xử lý price/availability freshness riêng nếu cần.
6. Thiết kế reindex/mapping evolution.
7. Thiết kế API/fallback/security.
8. Kiểm thử load, consistency lag và failure paths.
9. Rollout từng bước và theo dõi search quality/latency/index lag.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định Elasticsearch là bắt buộc nếu SQL đáp ứng quality/scale.
- Nếu dùng Elasticsearch, giữ SQL/source system là authoritative cho transactional correctness.
- Tránh synchronous dual-write như một consistency guarantee.
- Có durable sync mechanism, retry và idempotent indexing.
- Nhận ra duplicate delivery và out-of-order updates.
- Có strategy cho reindex/mapping changes.
- Có fallback/degradation plan khi search unavailable.

### Điểm cộng

- Version mỗi product update để ignore stale/out-of-order index events.
- Dùng Outbox Pattern hoặc CDC-like mechanism phù hợp để tránh mất update sau SQL commit.
- Versioned indices + alias swap cho zero/low-downtime reindex.
- Tách frequently changing availability/price nếu update pressure lớn, nhưng chỉ khi measurement cần.
- Theo dõi indexing lag, failed documents, query latency và zero-result rate.

### Senior+

- Phân biệt data freshness SLO theo field thay vì một global consistency claim.
- Biết search relevance là product capability cần measurement/A-B evaluation, không chỉ latency.
- Thiết kế backfill/reconciliation để phát hiện missed events dù pipeline “reliable”.
- Cân nhắc document denormalization và update amplification.
- Không tạo microservice/event platform mới nếu modular monolith + outbox worker đủ đáp ứng.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng câu hỏi: **SQL Server hiện có thật sự không đáp ứng search requirements không?** Nếu search chủ yếu exact/prefix filters, catalog nhỏ hơn hoặc traffic thấp, SQL full-text/composite indexes có thể đơn giản và đủ tốt. Với 3 triệu products, 500 RPS, relevance/autocomplete/filtering phong phú, Elasticsearch có khả năng hợp lý hơn — nhưng tôi vẫn benchmark representative queries trước khi commit platform complexity.

Nếu chọn Elasticsearch, tôi xác định rõ:

- SQL Server/product domain store là source of truth;
- Elasticsearch là derived read model cho discovery/search;
- checkout/cart phải revalidate authoritative price/availability theo business rules.

### Document model

Tôi thường index một denormalized product search document chứa fields cần cho search/filter/sort, ví dụ:

```json
{
  "productId": "P123",
  "name": "...",
  "description": "...",
  "brandId": "B10",
  "categoryIds": ["C1", "C7"],
  "price": 129.99,
  "availability": "InStock",
  "updatedVersion": 1842,
  "updatedAt": "2026-09-12T13:00:00Z"
}
```

Text fields và exact-filter fields cần mapping khác nhau (`text` vs keyword-like exact fields), analyzers phải thiết kế theo language/search behavior. Không nên dùng dynamic mapping vô kiểm soát cho business-critical schema.

### Synchronization

Tôi tránh flow:

`SaveChanges(SQL) → gọi Elasticsearch → nếu fail thì...?`

vì SQL commit có thể thành công nhưng Elasticsearch call fail, hoặc Elasticsearch success rồi transaction SQL rollback. Không có distributed atomicity tự nhiên.

Một thiết kế thực tế trong modular monolith là Outbox:

1. transaction SQL cập nhật product;
2. cùng transaction ghi `ProductSearchChanged` outbox row với `ProductId` và version;
3. background publisher/indexer đọc outbox;
4. dựng document từ authoritative state hoặc payload đủ dữ liệu;
5. upsert Elasticsearch;
6. mark event processed.

Delivery có thể at-least-once nên index operation phải idempotent. Versioning giúp xử lý out-of-order:

- event version 1842 applied;
- sau đó duplicate 1842 → no harmful change;
- event 1841 tới muộn → ignore vì older version.

Cơ chế version cụ thể phụ thuộc Elasticsearch API/version hiện hành, nên implementation cần đối chiếu official docs; về design, requirement là monotonic version/check tại consumer.

Tôi cũng không tin chỉ outbox là đủ cho mọi failure. Có periodic reconciliation:

- compare source updated versions/timestamps với indexed state;
- requeue missing/stale products;
- dashboard count/index lag.

### Price và availability

Nếu price/availability update rất thường xuyên, đưa mọi thay đổi vào full product document có thể tạo update amplification. Có vài options:

1. vẫn update document nếu rate thực tế manageable;
2. index availability coarse-grained cho discovery nhưng verify exact stock ở product/cart/checkout;
3. tách search/filter concern khỏi real-time inventory service nếu business thật sự cần near-real-time stock.

Tôi không tách thành service/index riêng trước khi có update-rate evidence. Freshness SLO có thể khác nhau: description 2 phút, price 30 giây, inventory cuối cùng phải authoritative tại checkout.

### Reindex và mapping changes

Mapping/analyzer changes thường cần reindex. Tôi dùng versioned indices:

- `products-v17` current;
- create `products-v18` với mapping mới;
- bulk backfill từ SQL/source;
- consume/repair delta trong lúc backfill;
- validate document count/sample queries/index lag;
- atomically switch read alias `products-current` sang v18;
- giữ v17 ngắn hạn cho rollback;
- retire sau verification.

Cần chú ý write path trong transition: hoặc writes đi qua alias/version strategy rõ hoặc pipeline dual-index trong controlled period. Không nên đổi alias khi new index còn thiếu delta.

### Search API

ASP.NET Core search endpoint nhận validated query/filter/page/sort. Tôi đặt limits để tránh expensive unbounded queries, deep pagination hoặc user-controlled query DSL injection. Client không được gửi raw Elasticsearch JSON trực tiếp nếu không có controlled abstraction.

Pagination có thể dùng từ/size cho shallow pages; deep navigation cần search-after/cursor-like design phù hợp. Exact choice phụ thuộc UX.

### Failure/degradation

Nếu Elasticsearch down:

- không để checkout/order down theo;
- search endpoint có thể trả controlled `503`/degraded response;
- optionally fallback SQL cho limited exact search nếu đã load-tested và business coi đó hữu ích;
- không tự động dồn toàn bộ 500 RPS sang SQL nếu SQL không chịu được.

Fallback cũng là production load path, phải được test.

### Observability

Tôi theo dõi:

- search p50/p95/p99;
- error rate/timeouts;
- index queue/outbox backlog;
- oldest unindexed event age;
- indexing failure/retry rate;
- source-version vs index-version lag samples;
- query zero-result rate;
- top slow query patterns;
- Elasticsearch CPU/heap/search/indexing pressure theo platform metrics;
- business search-to-product-click/conversion nếu relevant.

Application Insights trace nên correlate search API với Elasticsearch dependency nhưng tránh metric labels cardinality cao theo raw query.

### Testing và rollout

- unit test query mapping/business filters;
- integration test SQL commit → outbox → index → searchable;
- duplicate/out-of-order event test;
- failure injection khi Elasticsearch unavailable;
- load test 500+ RPS representative queries;
- reindex/cutover rehearsal;
- shadow traffic: chạy Elasticsearch search song song với current path, không trả kết quả cho user, so latency/result quality;
- canary rollout một phần traffic rồi tăng dần.

Elasticsearch chỉ đáng giá nếu search quality/performance/operational value bù cho sync/index/reindex complexity. Nếu SQL-only benchmark đáp ứng SLO và relevance requirements thấp, tôi ưu tiên SQL để giữ system đơn giản hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chọn Elasticsearch chỉ từ con số 3 triệu products. Tôi làm rõ relevance/autocomplete requirements và benchmark SQL full-text/indexes trước. Nếu quality và 500 RPS thực sự phù hợp Elasticsearch hơn, tôi giữ SQL là source of truth và coi Elasticsearch là derived search read model.

Tôi tránh synchronous dual-write SQL + Elasticsearch vì có partial failure. Trong modular monolith, tôi có thể ghi product change và outbox row cùng SQL transaction, sau đó background indexer xử lý at-least-once. Event/document có product version để duplicate không hại và event cũ tới muộn bị ignore. Tôi còn có reconciliation để bắt missed/stale documents.

Mapping/analyzer changes dùng versioned index và alias swap: backfill index mới, catch up delta, verify rồi cut over, giữ old index ngắn hạn để rollback. Price/availability có freshness SLO riêng; checkout luôn revalidate authoritative data nên search có thể stale bounded mà không làm sai transaction.

Nếu Elasticsearch down, tôi không để storefront core transaction down theo. Fallback SQL chỉ dùng nếu đã load-test vì chuyển 500 RPS sang SQL có thể biến search outage thành database outage. Tôi monitor search p95/p99, index lag, outbox backlog, failed docs, zero-result rate và source/index version drift. Nếu SQL đáp ứng đủ requirement với complexity thấp hơn, tôi chọn SQL-only.”

## Câu hỏi đào sâu

1. Nếu product update rate tăng 50× vì inventory thay đổi liên tục, bạn sẽ thay đổi document/indexing design thế nào?
2. Tôi muốn synchronous dual-write vì business yêu cầu “search phải thấy update ngay lập tức”; bạn sẽ challenge requirement hoặc thiết kế strong-consistency path ra sao?
3. Nếu alias swap sang index mới xong mới phát hiện analyzer mới làm relevance tệ hơn nhưng data đã tiếp tục update, rollback index cần strategy gì?

## Lỗi trả lời thường gặp

- Chọn Elasticsearch theo buzzword mà không benchmark SQL/search requirement.
- Synchronous dual-write và coi try/catch/retry là consistency solution.
- Không xử lý duplicate/out-of-order/missed updates.
- Không có reindex/mapping migration plan.
- Fallback toàn traffic sang SQL mà chưa đo capacity.

## Thang điểm 0–10

- **0–2:** Chỉ mô tả Elasticsearch là nhanh và dùng nó thay SQL.
- **3–4:** Có source-of-truth và async sync nhưng thiếu failure/idempotency/reindex.
- **5–6:** Có Outbox/idempotency, document model, fallback và telemetry cơ bản.
- **7–8:** Xử lý version/order/reconciliation/reindex alias, field-specific freshness và rollout.
- **9–10:** So sánh SQL-only vs Elasticsearch có căn cứ, thiết kế bounded eventual consistency rõ ràng, failure recovery đầy đủ và biết tránh complexity không được requirement biện minh.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- SQL Server deadlock phải được phân tích từ lock cycle và deadlock graph; retry không thay thế việc sửa lock footprint, access order và transaction design.
- Azure App Service slot deployment là bài toán phối hợp artifact, slot configuration, identity, secrets, schema compatibility, warmup và traffic; “swap success” không đồng nghĩa application healthy.
- Elasticsearch phù hợp khi search quality/scale biện minh cho derived read model; đồng bộ với SQL cần failure-aware design, idempotency, versioning và reindex strategy.
- Với mọi hệ thống phân tán, partial failure và rollback phải được thiết kế trước production incident.

## Mẫu tư duy cần nhớ

- **Observe before guessing:** lấy deadlock graph, instance/version telemetry hoặc index lag trước khi chọn fix.
- **Fix the consistency boundary, not only the symptom:** transaction/state transition, slot configuration contract và source-of-truth phải rõ ràng.
- **Retry requires idempotency:** retry database, deployment operation hay indexing đều có thể tạo duplicate side effects nếu không thiết kế trước.
- **Prefer reversible changes:** expand/contract migration, immutable artifacts, versioned search indices và alias/canary rollout giúp rollback an toàn.
- **Complexity must earn its cost:** không dùng distributed lock, Kubernetes, microservices hay Elasticsearch nếu simpler design đáp ứng requirement.
