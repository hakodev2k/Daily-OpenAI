# Câu 1 — Bật `AddDbContextPool` để tăng throughput nhưng tenant A thỉnh thoảng đọc dữ liệu tenant B

**Loại câu hỏi:** Internal Mechanism + Security + Production Debugging  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** C#, EF Core, `DbContext` pooling, dependency injection lifetimes, multi-tenancy, global query filters, state management, data isolation, production diagnostics

## Bối cảnh

Một ASP.NET Core SaaS application dùng SQL Server và EF Core. Mỗi HTTP request xác định `TenantId` từ JWT rồi truyền vào custom `AppDbContext`.

Ban đầu DI configuration là:

```csharp
services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString);
});
```

Sau khi load test cho thấy allocation/initialization overhead của `DbContext` tương đối cao, team đổi sang pooling:

```csharp
services.AddDbContextPool<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString);
});
```

`AppDbContext` hiện tại:

```csharp
public sealed class AppDbContext : DbContext
{
    public Guid TenantId { get; set; }

    public DbSet<Order> Orders => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();

    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options)
    {
    }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == TenantId);

        modelBuilder.Entity<Customer>()
            .HasQueryFilter(x => x.TenantId == TenantId);
    }
}
```

Middleware/service đầu request gán tenant:

```csharp
public sealed class TenantDbContextInitializer
{
    private readonly AppDbContext _db;
    private readonly ITenantAccessor _tenantAccessor;

    public TenantDbContextInitializer(
        AppDbContext db,
        ITenantAccessor tenantAccessor)
    {
        _db = db;
        _tenantAccessor = tenantAccessor;
    }

    public void Initialize()
    {
        _db.TenantId = _tenantAccessor.CurrentTenantId;
    }
}
```

Sau rollout, security telemetry ghi nhận vài request rất hiếm có query parameterized bằng tenant không đúng với request hiện tại. Incident chỉ xuất hiện dưới concurrency cao và gần như không tái hiện ở local development.

Một số chi tiết:

- `TenantId` là mutable property trên `DbContext`;
- pooled contexts được reuse giữa nhiều request khác nhau theo thời gian;
- một số endpoint gọi `Initialize()`, một số endpoint mới resolve repository trực tiếp và quên gọi;
- một background worker cũng resolve `AppDbContext` từ scope riêng;
- team tin rằng “scoped service luôn là object mới cho mỗi request”;
- một developer đề xuất reset `TenantId = Guid.Empty` trong controller `finally`;
- người khác muốn bỏ global query filter và yêu cầu developer luôn viết `.Where(x => x.TenantId == tenantId)` thủ công;
- production database hiện không có Row-Level Security.

## Câu hỏi chính

Hãy giải thích `DbContext` pooling thay đổi lifecycle thực tế của context như thế nào so với `AddDbContext`, vì sao mutable request-specific state trên pooled context có thể trở thành cross-request/cross-tenant risk, và thiết kế lại tenant-aware data access sao cho tenant state luôn được thiết lập đúng khi context được thuê từ pool và không phụ thuộc vào từng controller nhớ gọi `Initialize()`.

Ngoài fix trước mắt, hãy chỉ ra defense-in-depth nào nên có để một sai sót ở application layer không dễ biến thành cross-tenant data leak.

## Câu hỏi làm rõ nên cân nhắc

1. `ITenantAccessor` được đăng ký lifetime gì và có phụ thuộc `HttpContext` không?
2. Context có được tạo trực tiếp qua `IDbContextFactory<T>` ở nơi nào ngoài HTTP request không?
3. Có endpoint admin/support nào hợp pháp cần truy cập nhiều tenant không?
4. Global query filter hiện có được bypass bằng `IgnoreQueryFilters()` ở nơi nào không?
5. Tenant identity trong database có composite key/foreign-key constraints hay chỉ là một column convention?

## Gợi ý tư duy

### Gợi ý 1

`AddDbContextPool` vẫn cấp context theo scoped semantics cho consumer, nhưng instance vật lý có thể được trả về pool và tái sử dụng cho scope khác.

### Gợi ý 2

EF Core có thể reset state nội bộ mà framework biết, nhưng không thể tự hiểu mọi mutable field/property custom của application mang nghĩa gì.

### Gợi ý 3

Một security invariant quan trọng không nên phụ thuộc vào việc “mọi developer nhớ gọi method X trước query đầu tiên”.

## Cấu trúc trả lời đề xuất

1. So sánh lifecycle `AddDbContext` với pooled `DbContext`.
2. Vẽ request A → trả context vào pool → request B thuê lại cùng instance.
3. Phân tích custom mutable state và global query filter.
4. Xác định failure paths khi initializer bị bỏ qua.
5. Đề xuất factory/wrapper bảo đảm tenant initialization tại context acquisition boundary.
6. Tách context tenant-scoped khỏi context admin/system nếu cần.
7. Thiết kế repository/query-filter invariant.
8. Bổ sung database-level constraints/RLS nếu phù hợp.
9. Thiết kế concurrency/security tests.
10. Đề xuất telemetry để phát hiện mismatch tenant sớm.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `AddDbContextPool` tái sử dụng instance `DbContext`; scoped consumer không đồng nghĩa mỗi scope luôn nhận một object vật lý chưa từng dùng trước đó.
- Mutable application state như `TenantId` phải được reset/initialize đúng cho mỗi lần context được thuê; không được giả định EF Core tự hiểu và reset property custom.
- Nếu request B quên initialize, một giá trị tenant cũ có thể tiếp tục ảnh hưởng query filter và gây data-isolation failure.
- Việc reset ở controller `finally` không đủ tin cậy vì context có thể được dùng ở background service, exception path, endpoint khác hoặc code path không đi qua controller đó.
- Tenant initialization phải nằm ở một boundary bắt buộc, ví dụ scoped factory/wrapper tạo/thuê context rồi gán tenant trước khi trả cho consumer.
- `DbContext` không thread-safe; pooled reuse là tuần tự qua scopes, không có nghĩa cùng instance được dùng concurrent một cách hợp lệ.
- Bỏ global filter và dựa hoàn toàn vào developer viết `.Where` thủ công thường làm invariant yếu hơn, không mạnh hơn.

### Điểm cộng

- Dùng `AddPooledDbContextFactory<AppDbContext>` kết hợp một scoped tenant-aware factory để lấy pooled context và gán tenant mỗi lần.
- Với factory-owned context, ownership/disposal phải rõ để context được trả về pool đúng lúc.
- Tách `TenantAppDbContext` và `AdminAppDbContext` hoặc explicit bypass path thay vì lan truyền `IgnoreQueryFilters()` tùy tiện.
- Global filter nên dựa trên state đã được set một cách bắt buộc ở acquisition boundary.
- Add assertions/guard: nếu tenant chưa được initialize, query tenant-scoped phải fail closed thay vì dùng `Guid.Empty` như một trạng thái mơ hồ.

### Senior+

- Nhận ra model configuration và per-instance state là hai lớp khác nhau: model thường được cache, nhưng filter expression có thể tham chiếu context instance state tại query execution.
- Nếu tenancy là security boundary quan trọng, cân nhắc SQL Server Row-Level Security hoặc database-per-tenant/schema-per-tenant tùy threat model và operational cost.
- Composite unique/index/foreign-key design nên include `TenantId` ở những invariant cần chống cross-tenant reference.
- Có telemetry ghi `requestTenantId`, `dbContextTenantId`, operation name và correlation id nhưng không log sensitive data.
- Test bằng context pool size nhỏ để ép reuse thường xuyên và phát hiện bug deterministic hơn.

## Hướng giải quyết tham khảo

Với `AddDbContext`, một scoped `AppDbContext` thông thường được tạo cho scope và dispose cuối scope. Với `AddDbContextPool`, consumer vẫn thấy dependency theo scope, nhưng `Dispose` chủ yếu trả instance về pool để lần sau có thể được dùng lại. Đây là optimization lifecycle quan trọng: object identity có thể sống qua nhiều HTTP requests theo thời gian.

EF Core reset nhiều state framework-owned khi context quay về pool, nhưng property application-defined như:

```csharp
public Guid TenantId { get; set; }
```

không tự có semantic “reset thành tenant của request tiếp theo”. Nếu request A đặt `TenantId = tenantA`, context quay về pool, rồi request B lấy đúng instance đó nhưng code path B quên gọi `Initialize()`, filter có thể tiếp tục dùng tenant A. Đây là loại bug hiếm ở traffic thấp nhưng xuất hiện dưới reuse/concurrency cao.

Tôi không sửa bằng `finally { db.TenantId = Guid.Empty; }` trong controller, vì invariant vẫn phụ thuộc từng caller. Tôi đưa tenant binding vào nơi context được cấp phát.

Một pattern phù hợp là pooled factory + scoped tenant-aware wrapper:

```csharp
services.AddPooledDbContextFactory<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString);
});

services.AddScoped<TenantDbContextFactory>();
```

```csharp
public sealed class TenantDbContextFactory
{
    private readonly IDbContextFactory<AppDbContext> _factory;
    private readonly ITenantAccessor _tenant;

    public TenantDbContextFactory(
        IDbContextFactory<AppDbContext> factory,
        ITenantAccessor tenant)
    {
        _factory = factory;
        _tenant = tenant;
    }

    public async Task<AppDbContext> CreateAsync(
        CancellationToken cancellationToken = default)
    {
        var tenantId = _tenant.CurrentTenantId;

        if (tenantId == Guid.Empty)
            throw new InvalidOperationException("Tenant is not initialized.");

        var db = await _factory.CreateDbContextAsync(cancellationToken);
        db.TenantId = tenantId;
        return db;
    }
}
```

Repository không được resolve raw pooled factory trực tiếp nếu nó xử lý tenant data; nó chỉ nhận tenant-aware factory. Context được dispose sau operation/unit-of-work để trả về pool.

Nếu application cần admin operation xuyên tenant, tôi không dùng một boolean kiểu `BypassTenantFilter = true` dễ rò state trên cùng pooled context. Tôi ưu tiên separate explicit path/context/repository có authorization mạnh và audit riêng.

Tôi cũng muốn fail closed. Nếu `TenantId` chưa được gán, query không được âm thầm chạy như system tenant. Có thể thêm guard ở abstraction data layer, command interceptor phù hợp hoặc invariant kiểm tra trước unit of work.

Defense-in-depth tùy hệ thống. Với SaaS có impact cao, SQL Server Row-Level Security có thể đảm bảo session/context tenant không được đọc row khác ngay cả khi query thiếu predicate, nhưng RLS cũng có complexity về session context, connection pooling, migrations và admin paths nên phải thiết kế kỹ. Ít nhất, schema nên tránh cross-tenant references bằng composite constraints nơi phù hợp.

Testing nên cố tình ép pool reuse:

1. Pool size rất nhỏ, ví dụ 1–2.
2. Request tenant A query dữ liệu.
3. Dispose scope/context.
4. Request tenant B qua mọi endpoint/repository path.
5. Assert query chỉ thấy B.
6. Chạy xen kẽ A/B hàng nghìn lần parallel.
7. Test background worker không có HTTP tenant và phải truyền tenant explicit.
8. Test admin path không thể vô tình dùng tenant context thông thường.

Telemetry nên có một invariant check ở query/unit-of-work boundary so sánh authenticated tenant với context tenant khi có request context. Nếu mismatch, fail closed và alert security thay vì tiếp tục query.

## Mẫu trả lời trong phỏng vấn

“`AddDbContextPool` vẫn cho tôi scoped usage, nhưng instance vật lý có thể được reuse giữa các scope. EF reset state mà framework quản lý, không biết custom `TenantId` của tôi phải trở thành gì. Vì vậy nếu tenant A trả context về pool và tenant B thuê lại mà code B quên initialize, global query filter có thể dùng tenant cũ.

Tôi không đặt trách nhiệm reset ở controller. Tôi centralize context acquisition bằng một tenant-aware scoped factory bọc pooled `IDbContextFactory`. Factory lấy current tenant, validate khác empty, tạo context rồi set `TenantId` trước khi trả ra. Tenant repositories chỉ được dùng factory này. Admin cross-tenant flow dùng abstraction riêng.

Tôi vẫn giữ global query filter như một guardrail, cộng thêm database constraints/RLS nếu threat model cần. Tôi ép pool reuse trong integration tests và fail closed nếu request tenant khác context tenant. Mục tiêu là biến tenant isolation thành invariant của architecture, không phải coding convention.”

## Câu hỏi đào sâu

1. Nếu `ITenantAccessor` dựa vào `HttpContext`, background worker nên lấy tenant ở đâu?
2. Nếu dùng SQL Server Row-Level Security cùng connection pooling, tenant session context phải được set/reset ở boundary nào?
3. Bạn sẽ thiết kế admin/reporting query xuyên tenant thế nào để không tạo một `IgnoreQueryFilters()` escape hatch lan khắp codebase?

## Lỗi trả lời thường gặp

- Nghĩ scoped DI luôn tạo object vật lý hoàn toàn mới khi pooling bật.
- Chỉ thêm `TenantId = Guid.Empty` cuối controller.
- Bỏ global filter và giao toàn bộ trách nhiệm cho từng query.
- Dùng một mutable `BypassTenantFilter` flag trên pooled context.
- Không test pool reuse hoặc background worker paths.
- Coi cross-tenant result là data bug thay vì security incident.

## Thang điểm 0–10

- **0–2:** Không hiểu pooling thay đổi instance lifecycle.
- **3–4:** Nhận ra stale state nhưng chỉ reset thủ công ở caller.
- **5–6:** Có tenant-aware factory, fail-closed initialization và global filter invariant.
- **7–8:** Có admin separation, forced-reuse tests, telemetry và database guardrails.
- **9–10:** Reasoning đầy đủ về EF model/context state, pooling ownership, multi-layer tenant isolation và operational security controls.

# Câu 2 — Rate limiter dựa trên `RemoteIpAddress` bị bypass sau khi deploy qua reverse proxy

**Loại câu hỏi:** Security + ASP.NET Core Infrastructure + Production Debugging  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, reverse proxy, `ForwardedHeadersMiddleware`, rate limiting, IP spoofing, trusted proxies, network topology, authentication defense-in-depth, observability

## Bối cảnh

Một public ASP.NET Core authentication API có endpoint:

```http
POST /api/auth/password-reset
```

Để giảm abuse, team rate-limit theo client IP:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter
        .Create<HttpContext, string>(context =>
        {
            var ip = context.Connection.RemoteIpAddress?.ToString()
                     ?? "unknown";

            return RateLimitPartition.GetFixedWindowLimiter(
                partitionKey: ip,
                factory: _ => new FixedWindowRateLimiterOptions
                {
                    PermitLimit = 20,
                    Window = TimeSpan.FromMinutes(1),
                    QueueLimit = 0
                });
        });
});
```

Ứng dụng trước đây expose trực tiếp qua Kestrel. Sau migration, traffic đi qua:

```text
Internet
  → CDN/WAF
  → Azure Application Gateway / reverse proxy
  → App Service / ASP.NET Core
```

Team thêm:

```csharp
app.UseForwardedHeaders(new ForwardedHeadersOptions
{
    ForwardedHeaders = ForwardedHeaders.XForwardedFor |
                       ForwardedHeaders.XForwardedProto
});
```

Sau migration có hai symptom trái ngược:

1. Ở một environment, mọi user đều bị gom vào cùng một rate-limit bucket vì `RemoteIpAddress` luôn là proxy IP.
2. Ở environment khác, attacker có thể thay `X-Forwarded-For` và nhận bucket mới gần như vô hạn.

Log sample:

```text
RemoteIpAddress=10.20.4.12
X-Forwarded-For=203.0.113.10, 10.10.1.5
```

Một security test gửi trực tiếp tới origin từ network nội bộ:

```http
X-Forwarded-For: 198.51.100.77
```

và application log lại `RemoteIpAddress=198.51.100.77` sau middleware.

Một developer đề xuất luôn lấy “IP đầu tiên” trong `X-Forwarded-For`. Người khác muốn trust header từ mọi source vì CDN “đã sanitize rồi”. Product cho rằng endpoint password reset không cần thêm controls vì rate limiter đã chặn brute-force.

## Câu hỏi chính

Hãy giải thích trust model của forwarded headers: tại sao `X-Forwarded-For` là dữ liệu attacker-controlled nếu origin không xác minh proxy chain; vì sao lấy IP đầu tiên bằng string parsing không đủ an toàn; và cách cấu hình ASP.NET Core + infrastructure để chỉ tin forwarded headers từ known proxies/networks đúng topology.

Sau đó thiết kế rate-limit key và abuse controls phù hợp cho password reset mà không biến IP thành authentication boundary duy nhất.

## Câu hỏi làm rõ nên cân nhắc

1. Origin có thể được truy cập trực tiếp từ Internet hay chỉ từ proxy subnet/private network?
2. Có bao nhiêu proxy hops thực tế và CDN/Application Gateway sửa/append `X-Forwarded-For` theo contract nào?
3. IP ranges của trusted proxies có ổn định hay được publish động?
4. IPv4/IPv6/NAT/mobile carrier ảnh hưởng fairness của IP limiting ra sao?
5. Password reset endpoint có rate limit theo account/email/device/session nào khác không?

## Gợi ý tư duy

### Gợi ý 1

Forwarded headers chỉ đáng tin nếu request đến từ một hop mà application/infrastructure đã xác định là trusted.

### Gợi ý 2

`X-Forwarded-For` là một chain, không phải một giá trị “client IP” thần kỳ.

### Gợi ý 3

IP rate limiting là abuse signal. Nó không nên là cơ chế duy nhất bảo vệ account-sensitive workflow.

## Cấu trúc trả lời đề xuất

1. Vẽ network/proxy topology thật.
2. Xác định ai có thể kết nối trực tiếp origin.
3. Giải thích semantics của `RemoteIpAddress` trước/sau forwarded middleware.
4. Xác định trusted proxy/network configuration.
5. Xác định `ForwardLimit`/proxy hop expectation.
6. Tránh manual parsing header tùy tiện.
7. Thiết kế rate-limit partitions nhiều chiều.
8. Xử lý NAT/shared IP và IPv6.
9. Thiết kế logging/alerts không tạo PII exposure quá mức.
10. Pen-test spoofed chain và topology changes.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Raw `X-Forwarded-For` không phải trusted input nếu client có thể gửi trực tiếp hoặc proxy không overwrite/sanitize đúng.
- `ForwardedHeadersMiddleware` phải chạy sớm, trước middleware cần scheme/client IP như rate limiting/auth redirect logic.
- Cần cấu hình `KnownProxies`/`KnownNetworks` hoặc equivalent trust boundary thay vì trust mọi sender.
- Origin nên được network-restrict để chỉ trusted reverse proxy/CDN path có thể truy cập khi architecture cho phép.
- Proxy chain phải được hiểu rõ; `ForwardLimit`/hop handling phải phù hợp topology.
- Không parse “IP đầu tiên” một cách ad-hoc vì attacker có thể prepend values và semantics khác nhau giữa proxies.
- Password-reset abuse protection nên partition thêm theo account/email hash hoặc normalized subject, kết hợp IP/device/risk signals và generic responses chống account enumeration.

### Điểm cộng

- Biết forwarded middleware xử lý chain từ trusted proxy side, không đơn giản chọn left-most string.
- Có test cho direct-origin request với spoofed `X-Forwarded-For` phải không được tin.
- Normalize IP representation; cân nhắc IPv6 prefix aggregation thay vì mỗi temporary IPv6 address là bucket riêng nếu threat model yêu cầu.
- Shared NAT có thể làm false positive nếu chỉ limit theo IP; account + IP layered limits hợp lý hơn.
- CDN/WAF rate limiting có thể là lớp ngoài, application rate limiting vẫn là defense-in-depth.

### Senior+

- Infrastructure rule nên chặn bypass origin; nếu attacker có thể đi vòng CDN/WAF thì application headers chỉ là một phần của vấn đề.
- Khi proxy IP ranges thay đổi động, cấu hình trust phải có operational update process, không mở `KnownNetworks` quá rộng cho tiện.
- Nếu multiple trusted hops, cần document contract: hop nào append/overwrite header nào, và application kỳ vọng bao nhiêu entries.
- Security logs nên lưu derived client-IP decision + proxy chain metadata cần thiết, có retention/privacy policy; không log toàn bộ auth payload.
- Abuse controls gồm cooldown, per-account limit, proof-of-work/CAPTCHA/risk challenge khi cần, token entropy/expiry, single-use reset token và detection of distributed low-and-slow attacks.

## Hướng giải quyết tham khảo

Trước forwarded middleware, `context.Connection.RemoteIpAddress` thường là network peer trực tiếp — trong topology mới đó là Application Gateway/reverse proxy. Nếu application không xử lý forwarded headers, mọi request có thể bị rate-limit theo cùng proxy IP.

Nhưng fix không phải đọc `X-Forwarded-For` trực tiếp. Header này do client có thể tự gửi. Nó chỉ trở thành meaningful khi trusted proxy nhận request, sanitize/append chain theo contract và origin chỉ chấp nhận interpretation từ trusted peer.

ASP.NET Core configuration cần encode trust boundary. Ví dụ minh họa:

```csharp
var forwarded = new ForwardedHeadersOptions
{
    ForwardedHeaders = ForwardedHeaders.XForwardedFor |
                       ForwardedHeaders.XForwardedProto,
    ForwardLimit = 1
};

forwarded.KnownNetworks.Add(
    new IPNetwork(
        IPAddress.Parse("10.20.4.0"),
        prefixLength: 24));

app.UseForwardedHeaders(forwarded);
```

Con số/hạ tầng thực tế phải theo topology; nếu có nhiều trusted hops thì `ForwardLimit` và networks thay đổi tương ứng. Quan trọng hơn, origin network rule nên chỉ cho proxy subnet/service path truy cập nếu có thể. Khi đó một client Internet không thể bypass WAF rồi tự gửi trusted-looking header vào origin.

Middleware order:

```text
ForwardedHeaders
→ HTTPS/scheme-sensitive middleware
→ authentication/authorization as needed
→ rate limiter/endpoints
```

Rate limiter lúc đó dùng `RemoteIpAddress` đã được middleware chuẩn hóa từ trusted chain, không tự split header string.

Tuy nhiên password reset không thể phụ thuộc chỉ vào IP. Một attacker có botnet/proxies có thể đổi IP; ngược lại hàng nghìn legitimate users có thể chung corporate/mobile NAT. Tôi sẽ có nhiều budget:

```text
per normalized account/email hash
per trusted-derived client IP
per broader network/device/risk signal
global anomaly budget
```

Response nên generic kiểu “Nếu account tồn tại, hướng dẫn đã được gửi” để giảm enumeration. Reset token phải high entropy, short-lived, single-use và invalidated theo policy phù hợp.

Testing phải gồm:

1. Direct trusted proxy request với valid chain.
2. Direct origin request từ untrusted source + fake XFF.
3. Client-supplied XFF qua proxy xem proxy sanitize/append thế nào.
4. Multiple hops đúng/sai thứ tự.
5. IPv6 and mapped IPv4 forms.
6. Shared NAT load.
7. Distributed attack nhiều IP vào cùng account.
8. Origin-bypass network penetration test.

Nếu security test hiện có thể truy cập origin từ network không đáng tin và middleware chấp nhận fake header, tôi coi đây là trust-boundary misconfiguration, không chỉ rate-limit bug.

## Mẫu trả lời trong phỏng vấn

“`X-Forwarded-For` chỉ đáng tin khi tôi tin network peer đã tạo/sanitize chain. Nếu origin nhận trực tiếp request từ attacker rồi trust XFF, attacker tự chọn identity của rate-limit bucket. Ngược lại nếu tôi không xử lý forwarded headers, `RemoteIpAddress` chỉ là proxy IP và mọi user bị gom chung.

Tôi khóa origin để chỉ trusted proxy path truy cập, cấu hình `KnownProxies`/`KnownNetworks` và `ForwardLimit` đúng topology, chạy `UseForwardedHeaders` trước rate limiter, rồi dùng `RemoteIpAddress` đã được framework derive. Tôi không tự lấy left-most XFF.

Với password reset, IP chỉ là một signal. Tôi layer per-account/email-hash limit, per-IP limit, generic anti-enumeration response và secure single-use reset token. Tôi test cả spoofed XFF, direct-origin bypass, shared NAT và distributed attack.”

## Câu hỏi đào sâu

1. Nếu CDN IP ranges thay đổi hàng tuần, bạn cập nhật trusted proxy configuration an toàn thế nào mà không redeploy thủ công liên tục?
2. Nếu Application Gateway append chứ không overwrite `X-Forwarded-For`, bạn xác định client hop nào trong chain ra sao?
3. Làm sao rate-limit IPv6 mà không cho attacker đổi privacy address liên tục nhưng cũng không block cả ISP range quá rộng?

## Lỗi trả lời thường gặp

- Luôn lấy phần tử đầu tiên của `X-Forwarded-For`.
- Trust forwarded headers từ mọi source.
- Chỉ sửa application mà để origin public bypass CDN/WAF.
- Dùng IP làm identity/security boundary duy nhất.
- Không xét NAT, IPv6 hoặc nhiều proxy hops.
- Đặt forwarded middleware sau rate limiter rồi thắc mắc vì sao limiter vẫn thấy proxy IP.

## Thang điểm 0–10

- **0–2:** Chỉ biết đọc `X-Forwarded-For`.
- **3–4:** Biết có proxy nhưng không có trust-boundary model.
- **5–6:** Cấu hình known proxies/networks, middleware order và layered rate limit đúng.
- **7–8:** Có origin restriction, chain semantics, NAT/IPv6 handling và security tests.
- **9–10:** Thiết kế đầy đủ network trust, application identity derivation, abuse economics và operational maintenance của proxy topology.

# Câu 3 — GitHub Actions `pull_request_target` làm untrusted PR code chạy với write token và repository secrets

**Loại câu hỏi:** Security + Git + CI/CD Architecture  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** Git, GitHub Actions, CI/CD, supply-chain security, pull requests, permissions, secrets, OIDC, least privilege, branch protection, artifact trust

## Bối cảnh

Một repository public/private-with-external-contributors muốn CI comment test result vào pull request. Team đổi workflow từ `pull_request` sang `pull_request_target` để workflow có quyền ghi comment và truy cập một vài secrets.

Workflow hiện tại:

```yaml
name: PR Validation

on:
  pull_request_target:
    types: [opened, synchronize, reopened]

permissions:
  contents: write
  pull-requests: write
  id-token: write

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}

      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'

      - run: dotnet test

      - name: Publish report
        run: ./scripts/publish-test-report.sh
        env:
          REPORT_API_TOKEN: ${{ secrets.REPORT_API_TOKEN }}
```

Một external contributor mở PR thay đổi:

```text
scripts/publish-test-report.sh
Directory.Build.targets
build scripts
```

Security review phát hiện workflow chạy code từ PR head trong context có elevated repository permissions/secrets. Chưa có bằng chứng token đã bị exfiltrate, nhưng repository chứa package publishing workflow và Azure deployment federation ở các workflow khác.

Một developer nói workflow YAML nằm ở default branch nên attacker không thể sửa workflow, vì vậy an toàn. Người khác đề xuất chỉ block thay đổi file `scripts/*`. Một người khác muốn chuyển tất cả CI sang self-hosted runner trong corporate network “để bảo mật hơn”.

## Câu hỏi chính

Hãy phân tích threat model của `pull_request_target` khi workflow checkout và execute untrusted PR head. Giải thích vì sao attacker không cần sửa workflow YAML để thực thi code trong privileged job; xác định blast radius của `GITHUB_TOKEN`, repository secrets và OIDC `id-token`; rồi thiết kế lại CI thành các trust zones sao cho untrusted PR code có thể build/test nhưng không có quyền ghi repo, secrets hoặc cloud credentials.

Hãy đề xuất cả remediation ngay lập tức, hardening lâu dài và cách audit xem incident có thể đã bị khai thác chưa.

## Câu hỏi làm rõ nên cân nhắc

1. Repository là public hay private, và ai có thể mở PR từ fork/branch?
2. `REPORT_API_TOKEN` có scope gì và có rotation/audit log không?
3. GitHub `GITHUB_TOKEN` default permissions của organization/repository hiện là gì?
4. Azure/cloud OIDC federated credential giới hạn subject/environment/ref ra sao?
5. Self-hosted runners có persistent disk/network access nào khiến untrusted code nguy hiểm hơn không?

## Gợi ý tư duy

### Gợi ý 1

`pull_request_target` chạy workflow trong security context của base repository. Nếu sau đó bạn checkout PR head rồi `run` build/test scripts, bạn đã đưa untrusted code vào privileged context.

### Gợi ý 2

Attacker không cần sửa `.github/workflows/*.yml`. Build systems có nhiều execution hooks: MSBuild targets, package scripts, test code, generated tools, shell scripts.

### Gợi ý 3

Tách “compute on untrusted input” khỏi “privileged action” bằng workflow/event boundaries và minimal data artifacts.

## Cấu trúc trả lời đề xuất

1. Xác định trust level của event `pull_request_target`.
2. Liệt kê tất cả code execution surfaces từ PR head.
3. Xác định token/secrets/cloud permissions trong job.
4. Contain/disable workflow và rotate credentials cần thiết.
5. Thiết kế unprivileged PR validation workflow.
6. Thiết kế privileged reporting/comment workflow riêng.
7. Xác định artifact/result trust boundary.
8. Harden permissions/actions/OIDC/environments.
9. Audit logs và compromise indicators.
10. Đánh giá self-hosted runner isolation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `pull_request_target` là event đặc biệt có privileged base-repo context; checkout PR head rồi execute nó là một dangerous trust inversion.
- Attacker không cần thay workflow YAML: `dotnet test`, MSBuild, test binaries, scripts, package hooks và build tooling đều có thể thực thi code do PR kiểm soát.
- `GITHUB_TOKEN` permissions phải theo least privilege; `contents: write` thường không cần cho job chỉ test/comment.
- Repository/action secrets không được expose cho untrusted code.
- `id-token: write` cho phép job xin OIDC token; mức độ nguy hiểm phụ thuộc cloud-side federated credential/role policy, vì vậy phải audit cả GitHub lẫn cloud trust policy.
- Untrusted PR validation nên dùng `pull_request` với read-only/minimal token, không có secrets/cloud credentials.
- Privileged comment/report step cần tách khỏi execution của PR code, chỉ consume bounded/sanitized result từ trusted mechanism.
- Immediate response gồm disable vulnerable path, rotate potentially exposed static secrets, review token/cloud audit logs và scope blast radius.

### Điểm cộng

- Pin third-party actions theo immutable commit SHA cho high-trust workflows hoặc có dependency governance tương đương.
- Set repository/org default `GITHUB_TOKEN` permissions read-only và elevate per-job khi thật sự cần.
- Use environments với protection rules cho deployment, không cấp cloud role chỉ vì workflow có `id-token: write`.
- OIDC federation bind chặt `repository`, `ref`/environment, workflow identity/subject conditions theo provider khả năng hỗ trợ.
- Untrusted workflow không chạy trên long-lived self-hosted runner có network reach/secrets trừ khi sandbox/ephemeral isolation được thiết kế riêng.

### Senior+

- Nhận ra artifact từ untrusted workflow cũng là untrusted input; privileged workflow không được `source`, execute hoặc deserialize nguy hiểm artifact đó.
- Nếu dùng `workflow_run`/separate privileged job để comment, chỉ truyền data format tối thiểu như test counts/status, validate size/schema và không execute artifact content.
- Cache poisoning là trust-boundary concern: không để untrusted PR ghi cache mà privileged release workflow sau đó blindly reuse như trusted executable dependency.
- Branch protection/rulesets không thay thế workflow least privilege nhưng giúp ngăn direct write/merge.
- Incident audit phải xem workflow run logs, secret access/rotation, repository writes/releases/packages, OIDC token issuance/cloud sign-ins và downstream API usage.

## Hướng giải quyết tham khảo

Vấn đề không phải workflow YAML có bị sửa hay không. Dòng:

```yaml
- uses: actions/checkout@v4
  with:
    ref: ${{ github.event.pull_request.head.sha }}
```

đã đưa toàn bộ source từ PR head vào workspace của privileged job. Sau đó:

```yaml
- run: dotnet test
```

có thể execute attacker-controlled code thông qua test assembly, MSBuild target, source generator, custom tool, package restore hooks hoặc scripts. `publish-test-report.sh` càng rõ ràng hơn vì file đó trực tiếp nằm trong PR.

Với `pull_request_target`, context có thể có quyền/secrets mà normal fork PR không có. Vì vậy đây là RCE trong CI trust zone có credentials.

### Immediate containment

Tôi sẽ:

1. Disable/patch workflow để không checkout/execute PR head trong `pull_request_target`.
2. Rotate `REPORT_API_TOKEN` nếu nó có thể đã được exposed.
3. Review repository Actions logs và API audit logs từ thời điểm workflow vulnerable.
4. Review commits/tags/releases/packages/issues/comments mà compromised `GITHUB_TOKEN` scope có thể tạo.
5. Audit cloud OIDC federation và cloud sign-in/audit logs nếu job có `id-token: write`.
6. Revoke/rotate downstream credentials theo blast radius, không rotate mù mọi secret nếu evidence/scope không yêu cầu nhưng ưu tiên high-impact static tokens.

### Trust-zone redesign

Workflow 1 — untrusted PR validation:

```yaml
on: pull_request

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      - run: dotnet test
```

Không secrets, không `id-token: write`, không repo-write permission. Với fork PR, đây mới là nơi chạy arbitrary contributor code.

Nếu cần comment result bằng quyền cao hơn, tôi tách một privileged workflow chỉ đọc metadata/results tối thiểu. Ví dụ một `workflow_run` job có `pull-requests: write`, nhưng **không checkout PR head và không execute artifacts/scripts từ PR**. Nó lấy result qua GitHub API hoặc một data artifact được schema-validate, size-limit và xử lý như untrusted data.

Ví dụ privileged step chỉ xây comment từ primitive fields:

```json
{
  "passed": 120,
  "failed": 2,
  "durationSeconds": 83
}
```

không download shell script hoặc binary rồi execute.

`GITHUB_TOKEN` default nên read-only; job nào cần comment chỉ nhận `pull-requests: write`, không `contents: write`. OIDC chỉ bật ở deploy job và cloud trust policy phải restrict branch/environment/workflow phù hợp. Một PR job không có lý do lấy cloud token.

Tôi không chuyển untrusted code sang shared self-hosted runner trong corporate network như một “security fix”. Điều đó có thể làm blast radius lớn hơn: attacker code có thể scan internal network, đọc leftover workspace/credentials hoặc persist nếu runner không ephemeral. Nếu business bắt buộc self-hosted, cần ephemeral runners, network isolation, clean image, no ambient credentials và disposable lifecycle.

### Audit

Tôi correlation các workflow runs từ external/untrusted PRs với:

```text
repository audit log
GitHub Actions run logs
unexpected git refs/tags/releases
package publication history
secret/token rotation timestamps
REPORT API access logs
cloud OIDC token/sign-in/audit logs
Azure resource changes
```

Không chỉ tìm explicit `curl secrets`; attacker có thể dùng DNS, package publish, artifacts hoặc cloud role để exfiltrate/establish persistence.

## Mẫu trả lời trong phỏng vấn

“`pull_request_target` không nguy hiểm chỉ vì event name; nguy hiểm ở đây là privileged base-repo context rồi checkout và execute PR head. Attacker không cần sửa workflow YAML — `dotnet test` đã có thể chạy test code/MSBuild targets của họ. Job còn có `contents: write`, secrets và `id-token: write`, nên blast radius gồm repository, downstream token và có thể cloud role tùy OIDC trust policy.

Tôi tách hai trust zones. Untrusted PR chạy bằng `pull_request`, `contents: read`, không secrets/OIDC. Một privileged workflow riêng chỉ comment kết quả, không checkout hoặc execute PR code; nó consume bounded validated data. Tôi giảm token permissions per job, restrict cloud federation bằng environment/ref/workflow conditions và tránh persistent self-hosted runners cho untrusted code.

Ngay lúc incident, tôi disable path, rotate potentially exposed static token, audit repo writes/packages/releases và cloud OIDC/sign-in logs. Artifact/cache từ untrusted job cũng phải được coi là untrusted input.”

## Câu hỏi đào sâu

1. Nếu privileged workflow dùng `workflow_run` để tải test artifact do untrusted workflow tạo, những artifact types nào vẫn nguy hiểm?
2. `id-token: write` không tự động cho quyền Azure; cloud-side federated credential quyết định blast radius thế nào?
3. Khi nào self-hosted runner có thể an toàn cho untrusted PR, và isolation controls tối thiểu là gì?

## Lỗi trả lời thường gặp

- Nghĩ workflow YAML ở default branch nên PR code không thể chiếm job.
- Chỉ block thay đổi `scripts/*` nhưng quên test code/MSBuild/package hooks.
- Giữ `contents: write` vì “có thể cần sau”.
- Cho secrets vào untrusted job rồi cố mask log output.
- Chuyển sang persistent self-hosted runner nội bộ mà không sandbox/network-isolate.
- Dùng privileged workflow để execute artifact tạo từ untrusted PR.

## Thang điểm 0–10

- **0–2:** Không nhận ra untrusted-code execution trong privileged context.
- **3–4:** Biết `pull_request_target` risky nhưng remediation chỉ là path filter/manual review.
- **5–6:** Tách untrusted `pull_request` workflow, least privilege và remove secrets/OIDC.
- **7–8:** Có privileged reporting boundary, artifact trust model, incident audit và runner isolation.
- **9–10:** Reasoning đầy đủ về CI supply-chain trust zones, token/OIDC blast radius, cache/artifact poisoning và operational incident response.
