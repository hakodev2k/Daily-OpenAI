# Code Review Challenge 1 — `Update(entity)` từ DTO làm overposting và ghi đè dữ liệu mà người dùng không được phép sửa

**Chủ đề:** EF Core tracking/update semantics, authentication & authorization, input validation, concurrency, sensitive-data protection  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép manager chỉnh sửa thông tin hồ sơ nhân viên trong tenant hiện tại. Business rule:

- Manager được sửa `DisplayName`, `PhoneNumber`, `JobTitle`.
- Chỉ HR Admin mới được sửa `Salary`, `IsActive`, `ManagerId`.
- `TenantId`, `CreatedAt`, `SecurityStamp` và `LastModifiedBy` không bao giờ được lấy trực tiếp từ client.
- Hai manager có thể cùng mở cùng một hồ sơ rồi lưu sau vài phút.

Production gần đây ghi nhận:

- một số field nhạy cảm thay đổi dù UI không có control tương ứng,
- có record bị ghi đè bằng dữ liệu cũ khi hai người cùng sửa,
- audit khó xác định chính xác field nào thay đổi,
- security review phát hiện client có thể gửi thêm property ngoài những field UI hiển thị,
- một số request cập nhật được employee thuộc tenant khác nếu biết `employeeId`.

Team đang dùng EF Core và muốn giữ endpoint đơn giản.

## Đoạn code cần review

```csharp
public sealed record UpdateEmployeeRequest(
    Guid Id,
    Guid TenantId,
    string DisplayName,
    string? PhoneNumber,
    string JobTitle,
    decimal Salary,
    bool IsActive,
    Guid? ManagerId,
    string SecurityStamp,
    DateTime CreatedAt);

[ApiController]
[Route("api/employees")]
public sealed class EmployeesController : ControllerBase
{
    private readonly AppDbContext _db;

    public EmployeesController(AppDbContext db)
    {
        _db = db;
    }

    [Authorize]
    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id,
        UpdateEmployeeRequest request,
        CancellationToken cancellationToken)
    {
        if (id != request.Id)
            return BadRequest();

        var employee = new Employee
        {
            Id = request.Id,
            TenantId = request.TenantId,
            DisplayName = request.DisplayName,
            PhoneNumber = request.PhoneNumber,
            JobTitle = request.JobTitle,
            Salary = request.Salary,
            IsActive = request.IsActive,
            ManagerId = request.ManagerId,
            SecurityStamp = request.SecurityStamp,
            CreatedAt = request.CreatedAt,
            UpdatedAt = DateTime.UtcNow
        };

        _db.Employees.Update(employee);
        await _db.SaveChangesAsync(cancellationToken);

        return NoContent();
    }
}
```

## Kết quả code review tham khảo

### 1. Không có resource-level authorization theo tenant

**Problem:** Endpoint chỉ dùng `[Authorize]`; `employeeId` và `TenantId` từ client không được ràng buộc với tenant của caller.  
**Why it happens:** Authentication được dùng thay cho authorization trên resource.  
**Production impact:** Caller hợp lệ có thể sửa employee ngoài tenant nếu đoán/biết id.  
**Severity:** Critical  
**Recommended fix:** Xác định `tenantId` từ identity đáng tin cậy và query entity bằng cả `Id` + `TenantId`; áp dụng policy/resource authorization trước khi update.

### 2. Overposting các field mà caller không được phép sửa

**Problem:** Request chứa `Salary`, `IsActive`, `ManagerId`, `SecurityStamp`, `CreatedAt`, `TenantId`.  
**Why it happens:** API contract mirror gần như toàn bộ entity.  
**Production impact:** Client có thể thay đổi dữ liệu nhạy cảm hoặc invariant nội bộ dù UI không expose field đó.  
**Severity:** Critical  
**Recommended fix:** Dùng command/request tối thiểu chỉ gồm field role đó được phép sửa; endpoint đặc quyền nên tách riêng hoặc kiểm tra policy theo action.

### 3. `_db.Employees.Update(employee)` đánh dấu graph/entity detached là modified quá rộng

**Problem:** Entity mới được dựng từ request rồi `Update()`.  
**Why it happens:** EF Core không biết giá trị nào thực sự thay đổi nên thường coi các scalar property của entity là modified.  
**Production impact:** Ghi đè field server-controlled hoặc dữ liệu mới hơn trong DB bằng dữ liệu cũ/client-supplied.  
**Severity:** High  
**Recommended fix:** Load entity hiện tại rồi gán explicit field cần thay đổi, hoặc attach và mark từng property có chủ đích khi thực sự cần detached update.

### 4. Có lost update khi hai người chỉnh sửa đồng thời

**Problem:** Không có concurrency token/version check.  
**Why it happens:** Request sau có thể ghi đè thay đổi của request trước mà không biết.  
**Production impact:** Dữ liệu hợp lệ bị mất im lặng; người dùng thấy “save thành công” nhưng thay đổi của người khác biến mất.  
**Severity:** High  
**Recommended fix:** Dùng optimistic concurrency token như row version/version column và trả `409 Conflict`/`412 Precondition Failed` khi version cũ.

### 5. Tin `TenantId` từ request

**Problem:** `TenantId` server boundary lại do client gửi.  
**Why it happens:** Request model chứa field thuộc security context.  
**Production impact:** Có thể đổi ownership của entity hoặc phá tenant isolation nếu DB không có guard khác.  
**Severity:** High  
**Recommended fix:** Tenant phải lấy từ authenticated context, không map từ body.

### 6. Tin `SecurityStamp` và `CreatedAt` từ request

**Problem:** Server-controlled metadata bị client ghi lại.  
**Why it happens:** Entity và API DTO không được phân tách.  
**Production impact:** Audit/security metadata sai lệch, có thể ảnh hưởng logic downstream.  
**Severity:** High  
**Recommended fix:** Không expose các field này trong update request; giữ nguyên giá trị server-side.

### 7. Không xác thực business rule cho `ManagerId`

**Problem:** Dù caller có quyền, code không kiểm tra manager có thuộc cùng tenant, có tồn tại hay có tạo cycle quản lý không.  
**Why it happens:** Gán FK trực tiếp từ input.  
**Production impact:** Dữ liệu tổ chức không nhất quán hoặc cross-tenant reference.  
**Severity:** Medium  
**Recommended fix:** Validate referenced resource và business invariant trước khi commit.

### 8. Audit không thể hiện before/after và actor

**Problem:** Code chỉ update DB, không ghi actor hoặc changed fields.  
**Why it happens:** Audit bị xem là logging phụ thay vì requirement dữ liệu.  
**Production impact:** Khó điều tra ai thay đổi field nhạy cảm và thay đổi từ giá trị nào sang giá trị nào.  
**Severity:** Medium  
**Recommended fix:** Ghi structured audit với entity id, actor id, tenant, changed fields, old/new value phù hợp policy và correlation id.

### 9. Validation request chưa đủ

**Problem:** Không thấy giới hạn độ dài, format, empty value hoặc normalization cho các field editable.  
**Why it happens:** Chỉ dựa vào model binding.  
**Production impact:** Dữ liệu bẩn, lỗi DB hoặc downstream UI.  
**Severity:** Medium  
**Recommended fix:** Áp dụng validation rõ ràng tại boundary và business layer.

## Phiên bản code đề xuất

```csharp
public sealed record UpdateEmployeeProfileRequest(
    string DisplayName,
    string? PhoneNumber,
    string JobTitle,
    long Version);

[ApiController]
[Route("api/employees")]
public sealed class EmployeesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;
    private readonly IAuthorizationService _authorization;

    public EmployeesController(
        AppDbContext db,
        ITenantContext tenantContext,
        IAuthorizationService authorization)
    {
        _db = db;
        _tenantContext = tenantContext;
        _authorization = authorization;
    }

    [Authorize]
    [HttpPut("{id:guid}/profile")]
    public async Task<IActionResult> UpdateProfile(
        Guid id,
        UpdateEmployeeProfileRequest request,
        CancellationToken cancellationToken)
    {
        var tenantId = _tenantContext.TenantId;

        var employee = await _db.Employees
            .SingleOrDefaultAsync(
                x => x.Id == id && x.TenantId == tenantId,
                cancellationToken);

        if (employee is null)
            return NotFound();

        var authResult = await _authorization.AuthorizeAsync(
            User,
            employee,
            "CanEditEmployeeProfile");

        if (!authResult.Succeeded)
            return Forbid();

        _db.Entry(employee)
            .Property(x => x.Version)
            .OriginalValue = request.Version;

        employee.DisplayName = request.DisplayName.Trim();
        employee.PhoneNumber = request.PhoneNumber?.Trim();
        employee.JobTitle = request.JobTitle.Trim();
        employee.UpdatedAt = DateTime.UtcNow;
        employee.LastModifiedBy = User.FindFirst("sub")?.Value;

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException)
        {
            return Conflict(new
            {
                code = "employee_version_conflict",
                message = "Employee was changed by another user. Reload and retry."
            });
        }

        return NoContent();
    }
}
```

> Giả định `Version` được cấu hình làm concurrency token. Kiểu và cách sinh version có thể khác giữa SQL Server/PostgreSQL; nguyên tắc cần giữ là request phải mang version đã đọc và update phải fail khi version không còn khớp.

## Trade-offs

- Load entity trước tạo thêm read round-trip so với detached update, nhưng đổi lại có authorization, validation và field-level control rõ ràng hơn.
- Optimistic concurrency phù hợp khi conflict tương đối hiếm. Nếu cùng một record bị tranh chấp liên tục, có thể cần workflow/locking khác.
- Tách endpoint theo quyền (`profile`, `employment-status`, `compensation`) làm API nhiều hơn nhưng giảm đáng kể attack surface và giúp audit rõ ràng.
- Nếu dùng HTTP conditional request với ETag có thể biểu đạt concurrency tốt ở REST layer, nhưng team phải thống nhất cách version mapping và client handling.

## Cách kiểm thử

1. **Security test:** Manager cố gửi `Salary`, `TenantId`, `IsActive` hoặc sửa employee tenant khác; request phải bị từ chối hoặc field bị bỏ qua theo contract.
2. **Concurrency integration test:** Hai client đọc cùng version, client A save trước, client B save sau; B phải nhận conflict thay vì overwrite.
3. **Authorization test:** Manager, HR Admin và user thường được kiểm tra đúng quyền trên cùng resource.
4. **Database test:** Verify chỉ field được phép thay đổi; `CreatedAt`, `TenantId`, `SecurityStamp` giữ nguyên.
5. **Audit test:** Mỗi update thành công phải có actor, tenant, correlation id và changed fields hợp lệ.

## Quan sát trong production

- Log structured: `EmployeeId`, `TenantId`, actor id, operation, outcome, conflict flag; không log dữ liệu nhạy cảm không cần thiết.
- Metric: update success/failure, authorization denied, concurrency conflict rate.
- Trace: span cho DB query + save, gắn operation name ổn định và correlation id.
- Alert nếu cross-tenant authorization denial tăng bất thường hoặc conflict rate tăng sau release.
- Audit store nên có retention và access control riêng nếu chứa dữ liệu nhạy cảm.

# Code Review Challenge 2 — `System.Threading.Timer` với callback `async void` làm job chạy chồng và exception khó kiểm soát

**Chủ đề:** Background jobs, async/await, concurrency, resource lifetime, cancellation, error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–9 vấn đề

## Bối cảnh

Một service .NET chạy trong container cần đồng bộ trạng thái license từ Microsoft Graph mỗi 30 giây. Team không dùng Hangfire vì cho rằng đây chỉ là periodic polling đơn giản.

Bình thường một lần sync mất 5–10 giây. Nhưng khi Graph chậm hoặc database bị lock, một lần chạy có thể kéo dài 40–90 giây.

Production ghi nhận:

- cùng một license đôi lúc được cập nhật nhiều lần gần như đồng thời,
- log của hai lần sync overlap nhau,
- số lượng outbound request tăng mạnh khi Graph chậm,
- shutdown/deploy đôi lúc mất vài chục giây nhưng không biết job đã dừng hẳn chưa,
- exception thỉnh thoảng xuất hiện ở process level mà không nằm trong log của job,
- callback vẫn có thể bắt đầu trong lúc application đang shutdown.

Business chấp nhận chậm vài phút nhưng không muốn nhiều lần sync chạy chồng nhau. Khi shutdown cần dừng nhận vòng mới và cho vòng đang chạy kết thúc trong giới hạn hợp lý.

## Đoạn code cần review

```csharp
public sealed class LicenseSyncHostedService : IHostedService, IDisposable
{
    private readonly IServiceProvider _serviceProvider;
    private readonly ILogger<LicenseSyncHostedService> _logger;
    private Timer? _timer;

    public LicenseSyncHostedService(
        IServiceProvider serviceProvider,
        ILogger<LicenseSyncHostedService> logger)
    {
        _serviceProvider = serviceProvider;
        _logger = logger;
    }

    public Task StartAsync(CancellationToken cancellationToken)
    {
        _timer = new Timer(
            async _ => await SyncAsync(),
            null,
            TimeSpan.Zero,
            TimeSpan.FromSeconds(30));

        return Task.CompletedTask;
    }

    private async Task SyncAsync()
    {
        using var scope = _serviceProvider.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var graph = scope.ServiceProvider.GetRequiredService<IGraphLicenseClient>();

        _logger.LogInformation("License sync started");

        var users = await db.Users
            .Where(x => x.IsActive)
            .ToListAsync();

        foreach (var user in users)
        {
            var license = await graph.GetLicenseAsync(
                user.ExternalId,
                CancellationToken.None);

            user.LicenseStatus = license.Status;
        }

        await db.SaveChangesAsync();

        _logger.LogInformation("License sync completed");
    }

    public Task StopAsync(CancellationToken cancellationToken)
    {
        _timer?.Change(Timeout.Infinite, 0);
        return Task.CompletedTask;
    }

    public void Dispose()
    {
        _timer?.Dispose();
    }
}
```

3. Giải thích production impact khi downstream chậm, shutdown hoặc callback lỗi.
4. Ưu tiên các vấn đề cần sửa trước.

## Câu hỏi gợi mở

1. `Timer` có chờ callback trước hoàn thành rồi mới tick lần tiếp theo không?
2. Lambda `async _ => ...` đang được chuyển thành kiểu delegate nào?
3. `StopAsync` hiện tại có đợi một lần sync đang chạy hoàn thành không?

## Gợi ý

### Gợi ý 1

Phân biệt **lịch phát tick** với **vòng xử lý tuần tự**. Một timer định kỳ không tự bảo đảm “chạy lần sau sau khi lần trước hoàn thành”.

### Gợi ý 2

Một hướng đơn giản và rõ hơn là `BackgroundService` + `PeriodicTimer`, `await` từng vòng, truyền `stoppingToken`, tạo scope cho từng iteration và kiểm soát failure ở ranh giới vòng lặp.

## Kết quả code review tham khảo

### 1. Các lần sync có thể chạy chồng nhau

**Problem:** Timer phát callback mỗi 30 giây bất kể lần trước đã xong hay chưa.  
**Why it happens:** Scheduling của timer độc lập với thời gian xử lý callback.  
**Production impact:** Nhiều vòng cùng query DB và gọi Graph, tăng tải và có thể ghi đè trạng thái nhau.  
**Severity:** Critical  
**Recommended fix:** Dùng vòng lặp tuần tự trong `BackgroundService`/`PeriodicTimer`, hoặc cơ chế single-flight rõ ràng nếu vẫn giữ timer.

### 2. Callback async trở thành `async void`

**Problem:** Delegate của `Timer` không trả `Task`; lambda async vì vậy không được caller await.  
**Why it happens:** API callback đồng bộ được dùng cho công việc async.  
**Production impact:** Exception khó được quản lý theo lifecycle, `StopAsync` không biết callback đã hoàn thành hay chưa.  
**Severity:** Critical  
**Recommended fix:** Dùng API/lifecycle hỗ trợ `Task` end-to-end, điển hình là `BackgroundService.ExecuteAsync`.

### 3. Không truyền cancellation vào EF Core và Graph call

**Problem:** Query, outbound call và `SaveChangesAsync` không nhận token shutdown.  
**Why it happens:** `CancellationToken.None` hoặc overload không token được dùng.  
**Production impact:** Deploy/shutdown kéo dài, outbound call tiếp tục dù host đã yêu cầu dừng.  
**Severity:** High  
**Recommended fix:** Propagate `stoppingToken` hoặc linked token với timeout hợp lý cho toàn pipeline.

### 4. `StopAsync` chỉ ngừng tick mới nhưng không chờ callback đang chạy

**Problem:** `Change(Timeout.Infinite, 0)` không đồng nghĩa current async work đã hoàn tất.  
**Why it happens:** Hosted service không giữ `Task` của iteration.  
**Production impact:** Process có thể thoát khi work còn dang dở hoặc shutdown state không xác định.  
**Severity:** High  
**Recommended fix:** Dùng hosted background loop mà host có thể await; nếu custom lifecycle thì phải track running task và phối hợp stop rõ ràng.

### 5. Không có timeout riêng cho downstream operation

**Problem:** Một Graph call chậm có thể giữ vòng sync rất lâu.  
**Why it happens:** Chỉ dựa vào behavior mặc định của client/dependency.  
**Production impact:** Iteration kéo dài, backlog freshness tăng; với code hiện tại còn làm nhiều timer callback overlap hơn.  
**Severity:** High  
**Recommended fix:** Có timeout budget phù hợp, phân biệt timeout/cancellation/transient failure và quyết định retry có kiểm soát.

### 6. Một exception có thể làm mất toàn bộ vòng sync

**Problem:** Không có failure isolation hoặc catch ở iteration boundary.  
**Why it happens:** Một user hoặc một dependency failure phá toàn callback.  
**Production impact:** Các user còn lại không được sync; log có thể thiếu context nếu exception thoát khỏi async callback.  
**Severity:** High  
**Recommended fix:** Catch ở vòng iteration để log/metric; cân nhắc per-user isolation tùy business nhưng không nuốt lỗi im lặng.

### 7. Load toàn bộ active users vào memory mỗi vòng

**Problem:** `ToListAsync()` lấy tất cả active users.  
**Why it happens:** Không có batching/paging.  
**Production impact:** Khi số user lớn, memory và thời gian vòng sync tăng; dễ vượt interval và tăng áp lực downstream.  
**Severity:** Medium  
**Recommended fix:** Batch/paging theo keyset hoặc workload partition; giới hạn concurrency nếu cần nhưng không share `DbContext` giữa task song song.

### 8. Không có checkpoint hoặc quan sát progress

**Problem:** Chỉ log start/completed.  
**Why it happens:** Worker không expose processed count, duration, failure count, freshness.  
**Production impact:** Khó biết job đứng ở đâu, chậm vì DB hay Graph, hoặc bao nhiêu user chưa đồng bộ.  
**Severity:** Medium  
**Recommended fix:** Structured logs/metrics theo iteration, batch, downstream latency và last-success timestamp.

### 9. Clock-based interval semantics chưa rõ

**Problem:** Business nói “mỗi 30 giây” nhưng không xác định là fixed-rate hay 30 giây sau khi lần trước xong.  
**Why it happens:** Requirement scheduling chưa được làm rõ.  
**Production impact:** Thiết kế sai kỳ vọng freshness hoặc tải hệ thống.  
**Severity:** Medium  
**Recommended fix:** Làm rõ SLA; với yêu cầu không overlap, thường ưu tiên delay sau completion hoặc single-flight scheduler.

## Phiên bản code đề xuất

```csharp
public sealed class LicenseSyncWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<LicenseSyncWorker> _logger;

    public LicenseSyncWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<LicenseSyncWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));

        await RunIterationAsync(stoppingToken);

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await RunIterationAsync(stoppingToken);
        }
    }

    private async Task RunIterationAsync(
        CancellationToken stoppingToken)
    {
        var startedAt = Stopwatch.GetTimestamp();
        var processed = 0;
        var failed = 0;

        try
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var graph = scope.ServiceProvider.GetRequiredService<IGraphLicenseClient>();

            var lastId = Guid.Empty;

            while (!stoppingToken.IsCancellationRequested)
            {
                var users = await db.Users
                    .Where(x => x.IsActive && x.Id.CompareTo(lastId) > 0)
                    .OrderBy(x => x.Id)
                    .Take(200)
                    .ToListAsync(stoppingToken);

                if (users.Count == 0)
                    break;

                foreach (var user in users)
                {
                    try
                    {
                        using var timeout = CancellationTokenSource
                            .CreateLinkedTokenSource(stoppingToken);
                        timeout.CancelAfter(TimeSpan.FromSeconds(10));

                        var license = await graph.GetLicenseAsync(
                            user.ExternalId,
                            timeout.Token);

                        user.LicenseStatus = license.Status;
                        processed++;
                    }
                    catch (OperationCanceledException)
                        when (!stoppingToken.IsCancellationRequested)
                    {
                        failed++;
                        _logger.LogWarning(
                            "License sync timed out for user {UserId}",
                            user.Id);
                    }
                }

                await db.SaveChangesAsync(stoppingToken);
                db.ChangeTracker.Clear();
                lastId = users[^1].Id;
            }

            _logger.LogInformation(
                "License sync completed. Processed={Processed}, Failed={Failed}, DurationMs={DurationMs}",
                processed,
                failed,
                Stopwatch.GetElapsedTime(startedAt).TotalMilliseconds);
        }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested)
        {
            _logger.LogInformation("License sync stopping due to host shutdown");
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "License sync iteration failed. Processed={Processed}, Failed={Failed}",
                processed,
                failed);
        }
    }
}
```

> Đoạn keyset bằng `Guid.CompareTo` chỉ mang tính minh họa cho ý tưởng batching. Trong production nên chọn khóa sắp xếp ổn định và query shape mà provider/database của hệ thống translate hiệu quả; có thể dùng khóa tăng dần hoặc cặp `(CreatedAt, Id)` tùy schema.

## Trade-offs

- `PeriodicTimer` + tuần tự rất dễ hiểu và tự tránh overlap trong một process, nhưng không tự giải quyết “single global execution” nếu cùng service chạy nhiều replica.
- Nếu chỉ một replica được phép chạy job, có thể dùng Hangfire/storage-backed scheduler, leader election hoặc coordination phù hợp. Tuy nhiên correctness vẫn không nên chỉ dựa vào distributed lock.
- Per-user timeout/failure isolation tăng resilience nhưng có thể khiến một số user stale lâu hơn; cần retry/backoff và metric freshness.
- Batch nhỏ giảm memory và transaction size nhưng tăng số round-trip DB.
- Nếu Graph hỗ trợ batch API phù hợp business, có thể giảm outbound round-trip đáng kể, nhưng cần đánh giá limit và failure semantics cụ thể trước khi áp dụng.

## Cách kiểm thử

1. **Overlap test:** Cho một iteration chạy 60 giây với interval 30 giây; xác nhận chỉ có một iteration active trong một process.
2. **Shutdown test:** Trigger cancellation khi đang query DB và khi đang gọi Graph; worker phải ngừng có kiểm soát và không bắt đầu iteration mới.
3. **Failure-path test:** Một user timeout/throw exception; xác nhận policy mong muốn: isolate user hoặc fail batch, log/metric đầy đủ.
4. **Load test:** Hàng chục nghìn user; theo dõi memory, batch duration, Graph concurrency và total sync freshness.
5. **Multi-instance test:** Chạy nhiều replica để xác nhận requirement thực sự cần mỗi-instance polling hay single global worker; nếu single global thì verify cơ chế coordination riêng.

## Quan sát trong production

- Metrics: iteration duration, processed count, failed count, downstream latency, timeout count, last successful sync timestamp, freshness lag.
- Logs: iteration id, batch number, processed/failed count, user id khi lỗi; tránh log token hoặc dữ liệu Graph nhạy cảm.
- Traces: span cho DB batch query, Graph request và save operation.
- Alert khi không có successful iteration trong một khoảng vượt SLA hoặc timeout rate tăng đột biến.
- Dashboard nên phân biệt “worker đang chạy”, “worker healthy” và “data còn fresh”.

## Câu hỏi phỏng vấn mở rộng

1. Nếu service chạy 8 replicas nhưng chỉ muốn một global sync job, bạn chọn Hangfire, database lease hay distributed lock theo tiêu chí nào?
2. Nếu cần tăng tốc bằng `Task.WhenAll`, làm sao giới hạn concurrency mà không dùng chung một `DbContext` giữa các task?
3. Nếu shutdown grace period chỉ có 20 giây nhưng một batch có thể mất 60 giây, bạn thiết kế checkpoint/recovery thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- API update model không nên mirror toàn bộ entity; field-level authorization là một phần của security boundary.
- `DbSet.Update()` trên detached entity có thể tạo update quá rộng và dễ dẫn tới overposting/lost update nếu dùng thiếu kiểm soát.
- Multi-tenant authorization phải dựa vào identity/server context, không dựa vào `TenantId` do client gửi.
- Optimistic concurrency giúp phát hiện stale write thay vì âm thầm cho last-write-wins.
- Timer callback định kỳ không mặc định chờ async work hoàn thành; background processing cần lifecycle, cancellation và failure boundary rõ ràng.
- Cancellation, timeout, batching và observability phải được thiết kế cùng với worker, không thêm sau khi production có sự cố.

## Mẫu tư duy cần nhớ

- **Authenticate ≠ authorize resource:** user hợp lệ chưa có nghĩa là được sửa resource đó.
- **Accept only what may change:** thiết kế request theo capability, không theo shape của entity.
- **Detect stale writes explicitly:** concurrency conflict tốt hơn lost update im lặng.
- **Schedule sequential work as a loop, not overlapping callbacks.**
- **Cancellation và observability là một phần của correctness trong background processing.**
