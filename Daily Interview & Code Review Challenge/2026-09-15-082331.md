# Code Review Challenge 1 — BackgroundService gửi reminder trùng sau khi scale-out và shutdown làm mất trạng thái

**Chủ đề:** C#/.NET, BackgroundService, EF Core, concurrency, multi-instance scheduling, idempotency, graceful shutdown, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40–50 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core employee platform có `BackgroundService` quét SQL Server mỗi phút để gửi reminder cho các approval sắp quá hạn. Khi hệ thống chỉ chạy một instance, chức năng hoạt động ổn. Sau khi production scale từ 1 lên 4 instances, users bắt đầu nhận 2–4 email giống nhau.

Operations cũng ghi nhận rằng khi deploy rolling update, đôi lúc một reminder đã gửi nhưng record trong database vẫn còn `Pending`; vòng chạy sau gửi lại. Product yêu cầu không được bỏ sót reminder, nhưng duplicate email cũng phải được giảm xuống mức có thể kiểm soát.

Code hiện tại:

```csharp
public sealed class ReminderWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<ReminderWorker> _logger;

    public ReminderWorker(
        IServiceProvider services,
        IEmailSender emailSender,
        ILogger<ReminderWorker> logger)
    {
        _services = services;
        _emailSender = emailSender;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var reminders = await db.Reminders
                .Where(x => x.Status == "Pending" && x.DueAt <= DateTime.UtcNow)
                .OrderBy(x => x.DueAt)
                .Take(100)
                .ToListAsync();

            foreach (var reminder in reminders)
            {
                try
                {
                    await _emailSender.SendAsync(
                        reminder.Email,
                        reminder.Subject,
                        reminder.Body);

                    reminder.Status = "Sent";
                    reminder.SentAt = DateTime.UtcNow;
                    await db.SaveChangesAsync();
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex,
                        "Failed reminder {ReminderId} for {Email}",
                        reminder.Id,
                        reminder.Email);
                }
            }

            await Task.Delay(TimeSpan.FromMinutes(1));
        }
    }
}
```

`IEmailSender.SendAsync` gọi một third-party email API. API đó có thể timeout sau khi provider đã nhận request, nên caller không phải lúc nào cũng biết email đã được gửi hay chưa. `ReminderWorker` chạy bên trong từng web instance.

## Nhiệm vụ của ứng viên

Review change này như production code. Xác định các vấn đề về multi-instance concurrency, duplicate execution, partial failure, cancellation, retry, data consistency, DI lifetime và observability. Ưu tiên findings theo severity; đề xuất corrected implementation/design; giải thích semantics thực tế có thể đạt được; nêu testing và production telemetry.

## Câu hỏi gợi mở

1. Bốn instances chạy cùng query `Pending` có thể đọc cùng một row trước khi bất kỳ instance nào commit không?
2. Nếu provider đã nhận email nhưng HTTP response bị timeout, application có biết chắc email chưa được gửi không?
3. `Status = Sent` sau external side effect có tạo một transaction atomically bao phủ email provider và SQL Server không?
4. Shutdown token có được truyền xuống query, email call và delay không?
5. Nếu một batch có 100 reminders và item đầu tiên treo lâu, các item còn lại chịu ảnh hưởng gì?

## Gợi ý

### Gợi ý 1

Rủi ro chính không nằm ở `while` loop; nó nằm ở assumption rằng **một process là scheduler duy nhất** và rằng database + external email provider có thể được cập nhật atomically.

### Gợi ý 2

Hãy phân biệt **claim work**, **perform side effect**, **record outcome** và **retry/recovery**. Thiết kế phải chịu được process crash ở giữa bất kỳ hai bước nào.

## Kết quả code review tham khảo

### Critical — Nhiều instances có thể cùng xử lý một reminder

**Vấn đề:** Mỗi web instance chạy một `ReminderWorker` và cùng query các rows `Pending`. Query + send + update không có cơ chế claim/coordination.

**Tại sao xảy ra:** Hai hoặc nhiều workers có thể đọc cùng row trước khi worker đầu tiên đổi trạng thái và commit.

**Ảnh hưởng production:** Một reminder có thể tạo nhiều email, đặc biệt khi scale-out hoặc khi batch processing chậm.

**Cách sửa:** Thiết kế một cơ chế claim work atomically ở database hoặc chuyển scheduling/delivery sang queue có competing consumers. Nếu dùng SQL, claim phải là atomic state transition phù hợp với database semantics; không chỉ `SELECT` rồi đổi property trong memory.

### Critical — External side effect và database update có partial-failure window

**Vấn đề:** Email được gửi trước, `Sent` được lưu sau. Không có distributed transaction giữa SQL Server và third-party provider.

**Tại sao xảy ra:** Process có thể crash hoặc DB commit có thể fail sau khi provider đã chấp nhận email.

**Ảnh hưởng production:** Row vẫn `Pending` và lần sau email được gửi lại.

**Cách sửa:** Chấp nhận rằng exactly-once end-to-end thường không thể được bảo đảm chỉ bằng transaction local. Dùng idempotency key nếu provider hỗ trợ; nếu không, thiết kế durable delivery state, retry policy và duplicate-risk contract rõ ràng. Có thể dùng transactional Outbox để tách domain transaction khỏi delivery worker.

### High — Timeout có trạng thái kết quả không xác định

**Vấn đề:** HTTP timeout không chứng minh provider chưa nhận email.

**Tại sao xảy ra:** Request có thể được xử lý phía provider nhưng response bị mất/chậm.

**Ảnh hưởng production:** Blind retry có thể gửi duplicate.

**Cách sửa:** Gửi stable idempotency/deduplication key theo reminder/delivery attempt nếu provider hỗ trợ. Nếu provider có status lookup, reconcile ambiguous attempts. Nếu không có capability này, document at-least-once/possible-duplicate semantics và giảm duplicate bằng durable attempt state.

### High — CancellationToken không được propagate

**Vấn đề:** `ToListAsync`, `SendAsync` và `Task.Delay` đều bỏ qua `stoppingToken`.

**Tại sao xảy ra:** Worker chỉ kiểm tra token ở đầu vòng lặp.

**Ảnh hưởng production:** Rolling shutdown có thể kéo dài, host bị terminate giữa side effect và persistence, làm tăng ambiguous outcomes.

**Cách sửa:** Truyền cancellation tới database, provider call và delay. Tuy nhiên sau khi external side effect đã có thể commit, cancellation phải được xử lý cẩn thận để vẫn record/reconcile outcome thay vì đơn giản abandon state.

### High — Không có durable claim/lease và recovery cho work đang xử lý

**Vấn đề:** Model chỉ có `Pending`/`Sent`, không biểu diễn ownership/attempt/in-progress state.

**Tại sao xảy ra:** Worker không thể phân biệt item chưa từng chạy với item đang được instance khác xử lý hoặc item bị crash giữa chừng.

**Ảnh hưởng production:** Duplicate processing hoặc stuck records khi bổ sung ad-hoc state sau này.

**Cách sửa:** Dùng state machine như `Pending → Processing → Sent/Retry/Failed`, kèm claim token/lease expiry/attempt count khi thiết kế SQL worker; hoặc để queue broker đảm nhiệm competing-consumer delivery và giữ idempotency ở consumer.

### Medium — Batch xử lý tuần tự làm một dependency chậm chặn toàn batch

**Vấn đề:** 100 emails được gửi tuần tự.

**Tại sao xảy ra:** `foreach` await từng call.

**Ảnh hưởng production:** Provider latency tăng làm backlog tăng mạnh; reminder trễ dù CPU thấp.

**Cách sửa:** Nếu provider và business cho phép, dùng bounded concurrency, không phải unbounded `Task.WhenAll`. Capacity phải dựa trên provider rate limit, DB throughput và desired recovery behavior.

### Medium — Poll interval không cancellation-aware và tạo drift

**Vấn đề:** `Task.Delay(TimeSpan.FromMinutes(1))` không nhận token; mỗi vòng đợi một phút sau khi batch hoàn tất.

**Tại sao xảy ra:** Polling cadence phụ thuộc duration của batch.

**Ảnh hưởng production:** Shutdown chậm và cadence drift khi processing lâu.

**Cách sửa:** Dùng `PeriodicTimer` hoặc delay với token tùy semantics mong muốn; quan trọng hơn là đo queue/backlog age thay vì giả định mỗi phút luôn đủ.

### Medium — Logging PII không được cân nhắc

**Vấn đề:** Raw email address được log trong error message.

**Tại sao xảy ra:** Logging ưu tiên debug convenience hơn data-minimization.

**Ảnh hưởng production:** PII xuất hiện trong centralized logs và retention systems.

**Cách sửa:** Log reminder ID, delivery attempt ID và provider correlation ID; chỉ log recipient theo policy đã được phê duyệt hoặc mask/hash khi thực sự cần.

### Medium — Không có retry taxonomy và poison-work handling

**Vấn đề:** Mọi exception chỉ được log; item vẫn `Pending` và sẽ thử lại vô hạn mỗi vòng.

**Tại sao xảy ra:** Không phân biệt transient failure với permanent failure như invalid recipient/template.

**Ảnh hưởng production:** Poison item tạo log noise, provider traffic và backlog starvation.

**Cách sửa:** Track attempts, next-attempt time, exponential backoff/jitter, permanent-failure state và alert/manual recovery path.

## Phiên bản đề xuất

Một hướng phù hợp là tách việc tạo delivery record khỏi việc gửi. Domain transaction ghi reminder/outbox; worker claim một số delivery records atomically và xử lý với bounded concurrency. Pseudocode C# ở worker:

```csharp
public sealed class ReminderDeliveryWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<ReminderDeliveryWorker> _logger;

    public ReminderDeliveryWorker(
        IServiceScopeFactory scopeFactory,
        IEmailSender emailSender,
        ILogger<ReminderDeliveryWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _emailSender = emailSender;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(15));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            IReadOnlyList<ClaimedDelivery> batch;

            await using (var scope = _scopeFactory.CreateAsyncScope())
            {
                var store = scope.ServiceProvider
                    .GetRequiredService<IReminderDeliveryStore>();

                batch = await store.ClaimDueAsync(
                    maxCount: 50,
                    leaseDuration: TimeSpan.FromMinutes(2),
                    stoppingToken);
            }

            await Parallel.ForEachAsync(
                batch,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = 8,
                    CancellationToken = stoppingToken
                },
                async (delivery, ct) =>
                {
                    var idempotencyKey = $"reminder:{delivery.Id}";

                    try
                    {
                        var result = await _emailSender.SendAsync(
                            delivery.Email,
                            delivery.Subject,
                            delivery.Body,
                            idempotencyKey,
                            ct);

                        await RecordSentAsync(
                            delivery.Id,
                            delivery.ClaimToken,
                            result.ProviderMessageId,
                            CancellationToken.None);
                    }
                    catch (OperationCanceledException) when (ct.IsCancellationRequested)
                    {
                        await MarkForReconciliationAsync(
                            delivery.Id,
                            delivery.ClaimToken,
                            CancellationToken.None);
                    }
                    catch (Exception ex)
                    {
                        _logger.LogWarning(ex,
                            "Reminder delivery {DeliveryId} failed",
                            delivery.Id);

                        await RecordFailureAsync(
                            delivery.Id,
                            delivery.ClaimToken,
                            CancellationToken.None);
                    }
                });
        }
    }
}
```

`ClaimDueAsync` phải thực hiện claim bằng database operation có concurrency semantics rõ ràng; implementation cụ thể phụ thuộc SQL schema/isolation strategy. `CancellationToken.None` trong các đoạn persistence sau side-effect chỉ minh họa ý rằng khi outcome đã trở nên ambiguous, shutdown cancellation không nên khiến worker bỏ luôn việc ghi recovery state; production code vẫn cần timeout riêng để host không treo vô hạn.

Nếu business đã dùng Azure Service Bus, một lựa chọn khác là transactional Outbox → publisher → Service Bus → idempotent email consumer. Broker giải quyết competing consumers và redelivery, nhưng **không tự tạo exactly-once email delivery**; consumer vẫn phải xử lý duplicate/ambiguous provider outcome.

## Giải thích thiết kế sau khi sửa

Claim work giải quyết race giữa nhiều instances. Stable delivery ID tạo identity cho retry/idempotency. Bounded concurrency tăng throughput mà không flood provider. Attempt state/backoff cho phép phân biệt transient và poison failures. Outbox phù hợp nếu reminder creation phải atomically dẫn tới một durable delivery intent; queue chỉ nên được thêm nếu operational complexity được justify bởi reliability/throughput requirements.

## Trade-offs

SQL polling + atomic claim giữ architecture đơn giản nhưng cần thiết kế locking/indexes/lease recovery cẩn thận và có thể tạo database load. Service Bus tách producer/consumer tốt hơn, có retry/DLQ/competing consumers nhưng thêm broker, monitoring và eventual-consistency concerns. Provider idempotency là giải pháp mạnh cho duplicate side effect nhưng phụ thuộc capability của external API; nếu không có, business phải chấp nhận một mức duplicate risk hoặc thêm reconciliation.

## Cách kiểm thử

1. **Concurrency integration test:** chạy nhiều worker instances cùng claim một tập rows và xác minh mỗi row chỉ có một active owner tại một thời điểm.
2. **Failure-path test:** provider nhận request nhưng client timeout; kiểm tra state chuyển sang reconciliation/retry theo policy thay vì blind success/failure.
3. **Crash test:** terminate worker sau provider call nhưng trước DB persistence; restart và xác minh recovery behavior.
4. **Load test:** tạo backlog lớn, đo throughput, oldest-pending age và provider rate-limit behavior với bounded concurrency.
5. **Graceful-shutdown test:** gửi cancellation giữa batch và xác minh không tạo stuck lease vĩnh viễn, không mất durable work.

## Quan sát trong production

Theo dõi pending/processing/retry/failed counts, oldest pending age, claim conflicts, attempts per delivery, duplicate/idempotency responses từ provider, provider latency/error/timeout rate, processing throughput, lease expirations, reconciliation count và worker shutdown duration. Structured logs nên có `DeliveryId`, `Attempt`, `ClaimToken`/worker instance identifier và provider correlation ID; alert theo backlog age và permanent-failure rate thay vì chỉ exception count.

## Câu hỏi phỏng vấn mở rộng

1. Nếu email provider không hỗ trợ idempotency key hoặc status lookup, bạn sẽ định nghĩa delivery guarantee với Product như thế nào?
2. Khi nào SQL atomic-claim worker đủ tốt và khi nào Azure Service Bus đáng với complexity bổ sung?
3. Nếu một worker giữ lease 2 phút nhưng provider call có thể mất 3 phút, failure mode nào xuất hiện và bạn sửa lease strategy ra sao?

# Code Review Challenge 2 — Vue search page hiển thị kết quả cũ sau kết quả mới và gửi request trùng khi user gõ nhanh

**Chủ đề:** Vue.js, TypeScript, async race conditions, request cancellation, stale state, API integration, browser performance, error handling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một enterprise product catalog có Vue 3 search page. User nhập từ khóa, đổi category và phân trang. Backend API trả kết quả trong khoảng 100 ms–3 giây tùy query. Production telemetry cho thấy khi users gõ nhanh, request count tăng mạnh; đôi lúc UI hiển thị kết quả của query cũ sau khi query mới đã hoàn thành. QA cũng thấy loading spinner nhấp nháy và error banner của request cũ có thể xuất hiện dù request mới đã thành công.

Component hiện tại:

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

interface Product {
  id: string
  name: string
}

const query = ref('')
const category = ref('all')
const page = ref(1)
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')

async function loadProducts() {
  loading.value = true
  error.value = ''

  try {
    const url = `/api/products?q=${query.value}&category=${category.value}&page=${page.value}`
    const response = await fetch(url)
    const data = await response.json()

    products.value = data.items
  } catch (e) {
    error.value = 'Unable to load products'
  } finally {
    loading.value = false
  }
}

watch(query, () => {
  page.value = 1
  loadProducts()
})

watch(category, () => {
  page.value = 1
  loadProducts()
})

watch(page, () => {
  loadProducts()
})

onMounted(() => {
  loadProducts()
})
</script>
```

Backend có rate limiting nhẹ nhưng không muốn dùng nó để che lỗi client. Product muốn search cảm giác responsive, không gửi request cho mọi keystroke nếu không cần, và chỉ state của request hiện hành được phép cập nhật UI.

## Nhiệm vụ của ứng viên

Review component theo góc nhìn full-stack production. Xác định race conditions, duplicate requests, stale state, URL construction, HTTP/error handling và UX/performance concerns. Ưu tiên findings; đề xuất corrected implementation; giải thích request cancellation/latest-result semantics; nêu tests và browser/API telemetry cần quan sát.

## Câu hỏi gợi mở

1. Nếu request cho `a` mất 2 giây nhưng request cho `abc` mất 200 ms, request nào ghi `products` cuối cùng?
2. Khi `query` watcher đặt `page = 1`, `page` watcher có thể tạo thêm request không?
3. `fetch` có throw khi server trả HTTP 500 không?
4. Query string có an toàn nếu keyword chứa `&`, `#`, Unicode hoặc dấu cách không?
5. Một request cũ bị cancel có nên bật error banner hoặc tắt loading của request mới không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **out-of-order completion**: thứ tự response hoàn thành không được đảm bảo giống thứ tự request bắt đầu.

### Gợi ý 2

Hãy thiết kế một nguồn trigger thống nhất, debounce input và bảo đảm chỉ request mới nhất có quyền commit state. Cancellation giúp tiết kiệm work nhưng state correctness không nên dựa vào assumption rằng cancellation luôn thắng race.

## Dừng lại và tự review

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

### High — Response cũ có thể overwrite kết quả mới

**Vấn đề:** Mọi invocation của `loadProducts` đều có quyền ghi `products` khi hoàn tất.

**Tại sao xảy ra:** Network completion order không được đảm bảo. Request A bắt đầu trước có thể hoàn tất sau request B.

**Ảnh hưởng production:** UI hiển thị kết quả không tương ứng với query/category/page hiện tại.

**Cách sửa:** Dùng latest-request identity/version và chỉ commit state nếu response thuộc request hiện hành. `AbortController` nên cancel request cũ để giảm waste, nhưng sequence check vẫn là guard correctness hữu ích cho races quanh completion.

### High — Watchers có thể tạo duplicate requests

**Vấn đề:** Khi `query` hoặc `category` đổi, code đặt `page = 1` rồi gọi `loadProducts`; nếu page trước đó khác 1, watcher của `page` cũng gọi `loadProducts`.

**Tại sao xảy ra:** Ba watchers độc lập cùng trigger side effect trên state liên quan.

**Ảnh hưởng production:** Request amplification, backend load, spinner flicker và race probability tăng.

**Cách sửa:** Gom search parameters vào một coordinated watch/effect hoặc tách việc normalize state khỏi một trigger duy nhất cho fetch.

### High — Không debounce text input

**Vấn đề:** Mỗi thay đổi `query` tạo HTTP request.

**Tại sao xảy ra:** Watcher chạy theo mỗi reactive change.

**Ảnh hưởng production:** User gõ nhanh tạo nhiều request không còn giá trị, tăng backend load và browser work.

**Cách sửa:** Debounce text query theo UX requirement; category/page có thể trigger ngay. Debounce duration cần đo và tune, không hard-code theo cảm tính rồi coi là universal.

### Medium — HTTP error không được kiểm tra

**Vấn đề:** `fetch` resolve bình thường với nhiều HTTP error statuses; code gọi `response.json()` và có thể xử lý error payload như success data.

**Tại sao xảy ra:** Chỉ network-level failure thường đi vào `catch` trực tiếp.

**Ảnh hưởng production:** Error state sai, runtime exception khi payload shape khác, hoặc UI bị clear không rõ lý do.

**Cách sửa:** Kiểm tra `response.ok`, map expected API errors và xử lý malformed/unexpected payload phù hợp.

### Medium — Query string được nối thủ công

**Vấn đề:** `query.value` và `category.value` được interpolate trực tiếp vào URL.

**Tại sao xảy ra:** Không encode parameter values.

**Ảnh hưởng production:** Keywords chứa `&`, `=`, `#`, spaces hoặc Unicode có thể làm request semantics sai.

**Cách sửa:** Dùng `URLSearchParams` hoặc API client có parameter encoding rõ ràng.

### Medium — `loading` và `error` cũng bị stale request ghi đè

**Vấn đề:** Request cũ có thể chạy `finally` sau request mới và đặt `loading = false`; lỗi của request cũ cũng có thể hiện banner.

**Tại sao xảy ra:** Không có ownership/version check cho auxiliary state.

**Ảnh hưởng production:** Spinner không phản ánh request hiện hành và error UI gây hiểu nhầm.

**Cách sửa:** Chỉ request hiện hành được commit `products`, `error`, `loading`; abort error của superseded request không phải user-facing failure.

### Medium — Không validate response shape

**Vấn đề:** TypeScript interface không validate JSON runtime.

**Tại sao xảy ra:** `await response.json()` trả dữ liệu runtime không tự tuân theo `Product[]`.

**Ảnh hưởng production:** Backend contract regression có thể gây UI exception hoặc silent bad state.

**Cách sửa:** Ít nhất validate required shape ở API boundary hoặc dùng generated/validated client contract phù hợp với project complexity.

### Low — Không có explicit minimum-query/empty-query behavior

**Vấn đề:** Empty query vẫn fetch ngay theo cùng semantics.

**Tại sao xảy ra:** Product behavior chưa được encode.

**Ảnh hưởng production:** Có thể tạo expensive broad query hoặc UX không mong muốn.

**Cách sửa:** Làm rõ requirement: empty query có nghĩa browse-all, không fetch, hay default recommendations; implement explicit behavior.

## Phiên bản đề xuất

Một implementation có thể gom fetch semantics và bảo vệ latest request như sau:

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

interface Product {
  id: string
  name: string
}

const query = ref('')
const category = ref('all')
const page = ref(1)
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')

let activeController: AbortController | null = null
let requestVersion = 0
let debounceHandle: number | undefined

async function executeSearch() {
  const version = ++requestVersion

  activeController?.abort()
  const controller = new AbortController()
  activeController = controller

  loading.value = true
  error.value = ''

  const params = new URLSearchParams({
    q: query.value.trim(),
    category: category.value,
    page: String(page.value)
  })

  try {
    const response = await fetch(`/api/products?${params}`, {
      signal: controller.signal
    })

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    const data = await response.json()

    if (version !== requestVersion) return
    products.value = Array.isArray(data.items) ? data.items : []
  } catch (e) {
    if (version !== requestVersion) return
    if (e instanceof DOMException && e.name === 'AbortError') return

    error.value = 'Unable to load products'
  } finally {
    if (version === requestVersion) {
      loading.value = false
    }
  }
}

function scheduleTextSearch() {
  window.clearTimeout(debounceHandle)
  debounceHandle = window.setTimeout(executeSearch, 300)
}

watch(query, () => {
  if (page.value !== 1) {
    page.value = 1
    return
  }

  scheduleTextSearch()
})

watch(category, () => {
  window.clearTimeout(debounceHandle)

  if (page.value !== 1) {
    page.value = 1
    return
  }

  void executeSearch()
})

watch(page, () => {
  window.clearTimeout(debounceHandle)
  void executeSearch()
}, { immediate: true })

onBeforeUnmount(() => {
  window.clearTimeout(debounceHandle)
  activeController?.abort()
})
</script>
```

Đây là một baseline dễ review, không phải pattern duy nhất. Trong codebase lớn, search state có thể được gom vào composable/store hoặc một query library để chuẩn hóa cancellation, cache và deduplication. Không nên thêm library chỉ để tránh hiểu race semantics cơ bản.

Một điểm cần kiểm tra thêm: khi query đổi lúc `page != 1`, code trên reset page và để page watcher trigger search ngay, nghĩa là debounce không còn áp dụng cho trường hợp đó. Nếu Product yêu cầu **mọi text input đều debounce**, nên refactor thành một computed search criteria + một debounced query value hoặc một scheduler thống nhất thay vì giữ ba watchers. Đây là ví dụ về việc review cả corrected code thay vì coi sample fix là tuyệt đối.

## Giải thích thiết kế sau khi sửa

`AbortController` giảm network/browser work của request đã obsolete. `requestVersion` xác định request nào được phép commit state, nên correctness không phụ thuộc hoàn toàn vào timing của abort. `URLSearchParams` bảo đảm encoding. `response.ok` phân biệt HTTP failures. Cleanup khi unmount tránh để component cũ tiếp tục cập nhật state.

Ở production code, tôi ưu tiên một state machine/search composable rõ ràng hơn nếu filters tăng nhiều. Mục tiêu là có **một nơi sở hữu request lifecycle**, thay vì nhiều watchers cạnh tranh cập nhật UI.

## Trade-offs

Debounce giảm request volume nhưng thêm latency cảm nhận; duration cần cân bằng UX và backend cost. Cancellation không bảo đảm backend dừng work nếu request đã được server nhận hoặc server không propagate cancellation, vì vậy backend vẫn cần capacity/rate controls riêng. Client-side cache có thể cải thiện back-navigation nhưng tạo invalidation/staleness concerns. Query library giảm boilerplate nhưng thêm dependency và learning/upgrade cost.

## Cách kiểm thử

1. **Unit/component test:** giả lập request `a` chậm hơn `abc`; xác minh response cũ không overwrite kết quả mới.
2. **Fake-timer test:** gõ nhiều ký tự trong debounce window và xác minh chỉ request mong đợi được gửi.
3. **HTTP error test:** trả 500/429 và payload không đúng shape; xác minh error/loading state chính xác.
4. **Playwright E2E:** gõ nhanh, đổi category/page liên tục trên network throttling; xác minh UI cuối cùng khớp URL/search criteria hiện tại.
5. **Unmount/cancellation test:** rời page trong khi request đang chạy và xác minh không có stale update/unhandled rejection.

## Quan sát trong production

Theo dõi API requests per search session, aborted request count phía browser nếu instrument được, p50/p95/p99 search latency, HTTP 4xx/5xx/429, backend cancellation rate, request volume theo query endpoint và browser error telemetry. Với distributed tracing/correlation phù hợp, có thể phân biệt latency thật của backend với client-side stale-response symptom. Network waterfall trong browser là evidence quan trọng khi điều tra duplicate requests.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend đã nhận request trước khi browser abort, cancellation ở frontend có thực sự giảm database work không? Cần điều kiện gì ở ASP.NET Core call chain?
2. Khi nào client-side caching search results có lợi và cache key/invalidation nên được thiết kế thế nào?
3. Bạn có chọn một query library thay cho custom composable không, và tiêu chí nào justify dependency đó?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Background job chạy trong mỗi application instance sẽ tự nhiên nhân số scheduler khi hệ thống scale-out; singleton-process assumption không còn đúng.
- External side effect và local database transaction tạo partial-failure window; retry phải được thiết kế cùng idempotency/reconciliation.
- Claiming work, processing work và recording outcome là ba bước khác nhau cần failure semantics rõ ràng.
- Async UI có thể sai dù từng request riêng lẻ đều thành công; out-of-order completion là correctness problem.
- Cancellation giúp giảm waste nhưng latest-result ownership mới là guard quan trọng cho stale state.
- Multiple reactive watchers có thể tạo request amplification khi chúng thay đổi lẫn nhau.

## Mẫu tư duy cần nhớ

1. **Khi scale-out, kiểm tra mọi assumption về “chỉ chạy một lần”.**
2. **Thiết kế retry cùng idempotency và ambiguous outcome.**
3. **Tách claim → side effect → persistence để phân tích failure window.**
4. **Trong async UI, chỉ request hiện hành được quyền commit state.**
5. **Đo request amplification và failure path, không chỉ happy-path latency.**
