# Câu 1 — EF Core Tracking và Query Execution trong API tải cao

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 15 phút
**Kỹ năng được đánh giá:** EF Core internals, performance diagnosis, database reasoning

## Bối cảnh
Một ASP.NET Core API lấy danh sách đơn hàng cho portal nội bộ. Sau khi dữ liệu tăng từ vài trăm nghìn lên vài triệu bản ghi, API bắt đầu tăng memory usage và latency dù SQL Server không bị CPU cao.

Một developer nhận xét: "Query đã dùng async và LINQ nên EF Core sẽ tối ưu rồi."

## Câu hỏi chính
Giải thích bên trong EF Core xử lý query như thế nào, tracking ảnh hưởng ra sao, vì sao có thể xảy ra vấn đề memory và bạn sẽ xác minh nguyên nhân bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc
- Query có dùng projection hay trả về entity đầy đủ?
- Có cần update entity sau khi đọc không?
- Số lượng record thực tế và pagination như thế nào?
- Có đang dùng Include nhiều navigation không?

## Gợi ý tư duy
- Async không đồng nghĩa query tối ưu.
- Tracking tạo thêm state management.
- Cần phân biệt database bottleneck và application memory bottleneck.

## Cấu trúc trả lời đề xuất
1. Làm rõ query flow.
2. Giải thích EF Core runtime behavior.
3. Đo lường bottleneck.
4. Đưa ra giải pháp và trade-off.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu Change Tracker.
- Biết AsNoTracking phù hợp cho read-only.
- Biết projection giảm dữ liệu tải về.

### Điểm cộng
- Đề cập query plan, index và pagination.
- Dùng profiling.

### Nâng cao
- Phân tích compiled query và caching strategy.

## Hướng giải quyết tham khảo
Với read-only API nên dùng projection DTO, AsNoTracking, pagination ổn định và kiểm tra SQL generated. Không tối ưu bằng cách bỏ tracking mọi nơi nếu workflow cần update entity.

## Mẫu trả lời trong phỏng vấn
"Em sẽ không kết luận EF Core chậm ngay. Em kiểm tra generated SQL, execution plan, lượng dữ liệu materialize và memory allocation. Tracking là một tính năng hữu ích nhưng có cost, nên read scenario và write scenario cần thiết kế khác nhau."

## Câu hỏi đào sâu
- Khi nào không nên dùng AsNoTracking?
- Include nhiều tầng ảnh hưởng thế nào?
- Làm sao xử lý pagination với dữ liệu thay đổi liên tục?

## Lỗi trả lời thường gặp
- Chỉ thêm index database.
- Không phân biệt SQL và EF Core.
- Không đo trước khi sửa.

# Câu 2 — Thiết kế Event Notification Platform với Background Jobs

**Loại câu hỏi:** System design
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 25 phút
**Kỹ năng được đánh giá:** Architecture, reliability, background processing

## Bối cảnh
Một hệ thống quản lý sự kiện cần gửi email, Microsoft Graph calendar invitation và notification realtime cho hàng nghìn người dùng. Một số notification quan trọng không được phép mất.

Team đang cân nhắc xử lý trực tiếp trong API hoặc đưa vào Hangfire/RabbitMQ.

## Câu hỏi chính
Thiết kế hệ thống notification này như thế nào để đảm bảo reliability, idempotency, monitoring và khả năng mở rộng?

## Câu hỏi làm rõ nên cân nhắc
- Notification có yêu cầu gửi đúng một lần không?
- Có giới hạn rate limit từ external provider không?
- Người dùng có thể retry request không?
- Cần audit lịch sử gửi không?

## Gợi ý tư duy
- Retry phải đi cùng idempotency.
- External dependency luôn có failure.
- Background processing cần observability.

## Cấu trúc trả lời đề xuất
1. Functional requirements.
2. Component design.
3. Data flow.
4. Failure handling.
5. Monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Queue/background worker.
- Idempotency key.
- Retry policy.
- Logging.

### Điểm cộng
- Dead letter queue.
- Rate limiting.
- Audit table.

### Nâng cao
- Multi-tenant isolation.
- Delivery analytics.

## Hướng giải quyết tham khảo
MVP có thể dùng modular monolith + Hangfire + database queue. Khi scale lớn mới tách message broker. Mỗi notification cần trạng thái, retry count, correlation id và cơ chế tránh gửi trùng.

## Mẫu trả lời trong phỏng vấn
"Em sẽ tránh gửi notification trong HTTP request vì latency và failure coupling. Em lưu command, xử lý async và thiết kế idempotent để retry không tạo duplicate side effect."

## Câu hỏi đào sâu
- Nếu worker crash giữa lúc gửi email thì sao?
- Khi nào cần RabbitMQ?
- Làm sao kiểm chứng notification đã tới người dùng?

## Lỗi trả lời thường gặp
- Dùng microservice ngay từ đầu.
- Không nói về duplicate message.
- Không có monitoring.

## Thang điểm 0–10

- Technical correctness:
- Depth:

- Production readiness:

# Câu 3 — AI Agent hỗ trợ Code Review cho .NET Repository

**Loại câu hỏi:** AI engineering
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** AI workflow, security, evaluation

## Bối cảnh
Team muốn tạo AI agent đọc pull request, phân tích C# code, kiểm tra security issue và đề xuất review comment.

Agent có thể dùng repository context, documentation và tool gọi CI pipeline.

## Câu hỏi chính
Thiết kế AI code review agent như thế nào để hữu ích nhưng tránh hallucination, lộ source code hoặc đưa recommendation sai?

## Câu hỏi làm rõ nên cân nhắc
- Repository có chứa dữ liệu nhạy cảm không?
- Agent có quyền sửa code không?
- Review comment được tự động merge không?

## Gợi ý tư duy
- AI không thay thế compiler/test.
- Context cần kiểm soát.
- Output cần validation.

## Cấu trúc trả lời đề xuất
1. Xác định nhiệm vụ AI.
2. Thiết kế context pipeline.
3. Permission model.
4. Evaluation.
5. Monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Human approval.
- Structured output.
- Audit logs.

### Điểm cộng
- Prompt/version tracking.
- Golden dataset.

### Nâng cao
- Feedback loop đánh giá chất lượng.

## Hướng giải quyết tham khảo
LLM nên phân tích và đề xuất, nhưng build/test/security scanner vẫn deterministic. Context chỉ cung cấp phần cần thiết. Mọi recommendation quan trọng cần confidence và verification.

## Mẫu trả lời trong phỏng vấn
"Em không giao quyền quyết định production cho agent. Em thiết kế agent như một reviewer hỗ trợ, có giới hạn quyền, có evaluation dataset và bắt buộc kiểm chứng bằng tool khác."

## Câu hỏi đào sâu
- Đánh giá agent tốt hơn bằng metric nào?
- Khi nào không nên dùng agent?
- Làm sao giảm cost và latency?

## Lỗi trả lời thường gặp
- Chỉ nói dùng GPT.
- Không đề cập permission.
- Không có evaluation.

## Thang điểm 0–10
- Requirement clarification:
- Technical correctness:
- Depth:
- Trade-off analysis:
- Production readiness:
- Communication:
