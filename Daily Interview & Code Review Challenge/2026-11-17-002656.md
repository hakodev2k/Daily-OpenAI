# Code Review Challenge 1 — Import hàng loạt trên IIS: kết quả đúng trong test, mất dữ liệu khi App Pool recycle

**Chủ đề:** ASP.NET Core, BackgroundService, IIS, SQL Server, reliability, idempotency, deployment  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút

## Bối cảnh

Một hệ thống quản lý kho đang được chuyển dần từ ASP.NET MVC trên .NET Framework sang ASP.NET Core 8, vẫn chạy IIS trên Windows Server. API nhận file CSV từ nhân viên, lưu metadata vào SQL Server và trả HTTP 202 để UI Vue.js theo dõi tiến độ. Một file có thể chứa 200.000 dòng. Hai web nodes chạy sau load balancer; mỗi node có thể recycle App Pool khi deploy hoặc do cấu hình vận hành. Product yêu cầu không import trùng khi người dùng nhấn Submit hai lần và không mất job đã được xác nhận nhận xử lý.

Triệu chứng: có job mãi ở trạng thái Pending, có lúc số lượng bản ghi tăng gấp đôi; sau deploy một số job không tiếp tục. Team chưa có queue bên ngoài và chỉ có một tuần để hotfix. Giả định SQL Server là durable store; cấu hình hiện tại không có distributed transaction.

~~~csharp
public sealed record ImportRequest(string FilePath, string RequestedBy);

public sealed class ImportQueue
{
    public ConcurrentQueue<Guid> Jobs { get; } = new();
}

[ApiController]
[Route("api/imports")]
public sealed class ImportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ImportQueue _queue;

    public ImportsController(AppDbContext db, ImportQueue queue)
    {
        _db = db;
        _queue = queue;
    }

    [HttpPost]
    public async Task<IActionResult> Submit(
        ImportRequest request, CancellationToken ct)
    {
        var job = new ImportJob
        {
            Id = Guid.NewGuid(),
            FilePath = request.FilePath,
            RequestedBy = request.RequestedBy,
            Status = "Pending"
        };
        _db.ImportJobs.Add(job);
        await _db.SaveChangesAsync(ct);
        _queue.Jobs.Enqueue(job.Id);
        return Accepted(new { job.Id });
    }
}

public sealed class ImportWorker : BackgroundService
{
    private readonly ImportQueue _queue;
    private readonly IServiceScopeFactory _scopes;

    public ImportWorker(ImportQueue queue, IServiceScopeFactory scopes)
    {
        _queue = queue;
        _scopes = scopes;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            if (!_queue.Jobs.TryDequeue(out var id))
            {
                await Task.Delay(500, stoppingToken);
                continue;
            }

            using var scope = _scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var job = await db.ImportJobs.FindAsync(new object[] { id }, stoppingToken);
            if (job is null) continue;

            job.Status = "Running";
            await db.SaveChangesAsync(stoppingToken);

            foreach (var row in File.ReadLines(job.FilePath))
            {
                db.Inventory.Add(new InventoryRow
                {
                    Sku = row.Split(',')[0],
                    Quantity = int.Parse(row.Split(',')[1])
                });
                await db.SaveChangesAsync(stoppingToken);
            }

            job.Status = "Completed";
            await db.SaveChangesAsync(stoppingToken);
        }
    }
}
~~~

Giả định ImportQueue được đăng ký Singleton, ImportWorker là HostedService, DbContext là Scoped. Code được rút gọn nhưng luồng thực thi là thật.

## Kết quả code review tham khảo

### [Critical] — SQL commit và in-memory enqueue không atomic

**Vấn đề:** Job được lưu Pending nhưng chỉ được worker nhìn thấy qua ConcurrentQueue trong một process.  
**Tại sao xảy ra:** Hai thao tác không có transaction chung; queue không persistent, không chia sẻ giữa IIS nodes.  
**Ảnh hưởng production:** Lost wake-up sau crash/recycle; job tồn tại nhưng không bao giờ chạy.  
**Cách sửa:** Dùng bảng job làm source of truth; worker poll và claim job từ SQL, hoặc transactional outbox + durable broker. HTTP 202 chỉ sau khi job và thông tin file durable.

### [Critical] — FilePath do client chỉ định

**Vấn đề:** Client quyết định server đọc file nào.  
**Tại sao xảy ra:** Không có server-owned storage key, authorization và path validation.  
**Ảnh hưởng production:** Đọc file ngoài phạm vi import, lộ dữ liệu, lạm dụng quyền của IIS identity.  
**Cách sửa:** Upload vào vùng lưu trữ do server quản lý, dùng opaque file ID gắn với tenant/user, validate size/type và quyền; tuyệt đối không nhận arbitrary local path.

### [High] — Không có idempotency hoặc unique business key

**Vấn đề:** Mỗi Submit tạo GUID mới; retry tạo job mới.  
**Tại sao xảy ra:** Không có idempotency key và ràng buộc unique ở database.  
**Ảnh hưởng production:** Import trùng, dữ liệu kho tăng sai.  
**Cách sửa:** Unique (TenantId, IdempotencyKey), kiểm tra hash/payload tương ứng; xử lý row bằng khóa nghiệp vụ và chính sách upsert rõ ràng.

### [High] — Worker không có atomic claim/lease

**Vấn đề:** Nếu chuyển sang polling ngây thơ, hai nodes có thể cùng chạy job.  
**Tại sao xảy ra:** SELECT Pending rồi UPDATE Running tách rời, thiếu lock/conditional update.  
**Ảnh hưởng production:** Duplicate writes và tranh chấp.  
**Cách sửa:** Atomic UPDATE ... OUTPUT với UPDLOCK, READPAST và điều kiện lease phù hợp; lease token/fencing token để từ chối worker cũ. READPAST và isolation cần được xác minh trên cấu hình SQL Server thực tế.

### [High] — Partial writes và retry không có checkpoint

**Vấn đề:** SaveChanges mỗi dòng rồi mới set Completed.  
**Tại sao xảy ra:** Không có transaction theo batch, checkpoint, hoặc idempotent row write.  
**Ảnh hưởng production:** Worker chết giữa chừng để lại hàng chục nghìn dòng; chạy lại sẽ nhân đôi.  
**Cách sửa:** Stage rows theo JobId + RowNumber có unique index; validate trước khi merge; commit theo batch và checkpoint trong cùng transaction, hoặc thiết kế một transaction cho dataset phù hợp kích thước.

### [High] — Exception kết thúc BackgroundService

**Vấn đề:** File missing, parse error hoặc SQL transient exception thoát khỏi ExecuteAsync.  
**Tại sao xảy ra:** Không có per-job error boundary, retry classification hay dead-letter/Failed state.  
**Ảnh hưởng production:** Worker dừng, job mắc Running và queue không tiến.  
**Cách sửa:** Catch per job (không nuốt cancellation), cập nhật Attempts/NextAttemptAt/ErrorCode, exponential backoff có giới hạn; sau quá số lần retry chuyển Failed để điều tra.

### [Medium] — Ghi database từng dòng và ChangeTracker tăng

**Vấn đề:** 200.000 lần SaveChanges, nhiều round trip và tracked entities.  
**Tại sao xảy ra:** Không batch/clear tracking.  
**Ảnh hưởng production:** Latency, memory và SQL transaction log tăng.  
**Cách sửa:** Streaming parse, bounded batch, bulk insert vào staging (khi phù hợp), đo thời gian và lock trước khi tối ưu.

### [Medium] — CSV parsing không hợp lệ với dữ liệu thực

**Vấn đề:** Split(',') và int.Parse không xử lý quoted commas, header, culture, dòng lỗi.  
**Tại sao xảy ra:** Parser giả định định dạng đơn giản.  
**Ảnh hưởng production:** Sai SKU, abort toàn job, dữ liệu không nhất quán.  
**Cách sửa:** CSV parser chuẩn, schema validation, reject/report từng dòng theo business policy, giới hạn kích thước.

### [Medium] — Identity và quyền import không được xác thực

**Vấn đề:** RequestedBy lấy từ request body, không ràng buộc user/tenant.  
**Tại sao xảy ra:** Tin vào dữ liệu do client tự khai.  
**Ảnh hưởng production:** Spoof audit, cross-tenant access.  
**Cách sửa:** Lấy subject/tenant từ authenticated claims đã được validate; authorize quyền import và truy cập job status.

### [Medium] — Shutdown và lifecycle chưa có chính sách

**Vấn đề:** CancellationToken chỉ được truyền vào một số thao tác; File.ReadLines là synchronous; không có checkpoint/lease renewal.  
**Tại sao xảy ra:** Thiết kế giả định process sống mãi.  
**Ảnh hưởng production:** Recycle ngắt job và trạng thái Running không phục hồi.  
**Cách sửa:** Bounded work, cancellation giữa batches, renew lease, reclaim lease hết hạn, cấu hình IIS shutdown và kiểm thử recycle.

## Phiên bản đề xuất

Thiết kế hotfix dưới đây là **skeleton** cho một SQL-backed job processor, không phải copy-paste production. Nó thể hiện các bất biến quan trọng; các repository methods cần hiện thực bằng SQL transaction và constraints.

~~~csharp
public sealed record SubmitImportCommand(
    Guid UploadId, string IdempotencyKey);

[HttpPost]
public async Task<IActionResult> Submit(
    SubmitImportCommand command, CancellationToken ct)
{
    var actor = _currentUser.RequireAuthenticated();
    _authorization.EnsureCanImport(actor);
    var upload = await _uploads.RequireOwnedCompletedUploadAsync(
        actor.TenantId, actor.UserId, command.UploadId, ct);

    // Transaction + unique (TenantId, IdempotencyKey).
    // Same key + different payload => Conflict.
    var result = await _jobs.CreateOrGetAsync(
        actor.TenantId, actor.UserId, command.IdempotencyKey,
        upload.Id, ct);

    return AcceptedAtAction(nameof(GetStatus), new { id = result.Id },
        new { result.Id, result.Status });
}

public sealed class SqlImportWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public SqlImportWorker(IServiceScopeFactory scopeFactory)
        => _scopeFactory = scopeFactory;

    protected override async Task ExecuteAsync(CancellationToken stop)
    {
        while (!stop.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<IImportProcessor>();

            var claim = await processor.TryClaimDueJobAsync(stop);
            if (claim is null)
            {
                await Task.Delay(TimeSpan.FromSeconds(2), stop);
                continue;
            }

            try
            {
                await processor.ProcessBatchesAsync(claim, stop);
                await processor.MarkCompletedIfLeaseOwnedAsync(claim, stop);
            }
            catch (OperationCanceledException) when (stop.IsCancellationRequested)
            {
                // Lease expires and another worker can safely resume.
                throw;
            }
            catch (Exception ex)
            {
                await processor.RecordFailureAndScheduleRetryAsync(
                    claim, ex, stop);
            }
        }
    }
}
~~~

**SQL contract tối thiểu:** bảng ImportJobs có TenantId, IdempotencyKey, PayloadHash, Status, Attempts, LeaseOwner, LeaseToken, LeaseUntil, NextAttemptAt, LastError, Checkpoint, CreatedAt; unique (TenantId, IdempotencyKey). Claim job trong một transaction bằng atomic update có OUTPUT; chỉ worker giữ đúng lease token được commit checkpoint/completion. Staging có unique (JobId, RowNumber) hoặc business key phù hợp; mỗi batch ghi dữ liệu và checkpoint atomically. Cần phân biệt lease hết hạn với worker thực sự đã dừng: token/fencing và idempotent writes bảo vệ khỏi late worker.

**Giới hạn quan trọng:** Nếu chỉ dùng SQL queue, phải có cơ chế polling, retry, cleanup và giám sát. Nếu traffic lớn hoặc nhiều consumers, cân nhắc Azure Service Bus + Outbox, nhưng broker vẫn không thay thế idempotency của consumer.

## Giải thích thiết kế sau khi sửa

Nguồn chân lý là SQL, không phải memory queue. Endpoint xác nhận job sau khi dữ liệu đầu vào và record đã durable. Worker có quyền xử lý tạm thời thông qua lease; mỗi batch có checkpoint nhất quán với dữ liệu ghi. IIS có thể recycle mà không làm mất job; worker khác reclaim và resume. API status đọc từ SQL, không phụ thuộc node nào nhận request.

## Trade-offs

- SQL polling dễ triển khai với hạ tầng hiện tại nhưng thêm tải lên SQL và đòi hỏi index/lease management.
- Transaction toàn bộ file cho atomic visibility có thể tăng lock và log; staging + publish/merge có kiểm soát thường phù hợp hơn cho file lớn.
- Idempotency key giải quyết duplicate submission; unique row/business key giải quyết duplicate execution — hai tầng khác nhau.
- Broker giảm polling nhưng tăng vận hành, permissions, delivery semantics và chi phí; không tự tạo exactly-once effects.

## Cách kiểm thử

1. **Concurrency/integration:** 20 Submit cùng idempotency key trên hai nodes; chỉ một logical job, cùng key khác payload trả conflict.
2. **Failure injection:** Kill worker sau commit batch 3; lease expiry, resume và final inventory không duplicate.
3. **Security:** UploadId của tenant khác hoặc arbitrary file path bị từ chối; audit identity lấy từ claims.
4. **Load/database:** 200.000 rows với dữ liệu thực, đo batch throughput, transaction log, SQL waits và memory.
5. **Deployment validation:** Recycle IIS App Pool trong lúc Running; job cuối cùng Completed hoặc Failed có lý do, không Pending vô hạn.

## Quan sát trong production

Structured logs: JobId, TenantId (không log dữ liệu nhạy cảm), LeaseToken hash/short identifier, Attempt, BatchNumber, RowsCommitted, ErrorCode, TraceId. Metrics: Pending age p95, Running duration, failed/retried jobs, expired leases, duplicate-key conflicts, rows/sec, SQL dependency latency và connection pool saturation. Alert khi oldest Pending vượt SLO, lease expiry tăng, hoặc worker heartbeat mất. Traces nối HTTP Submit → SQL Create → Worker Claim → Batch Commit. Dashboard trong Application Insights/Azure Monitor hoặc Kibana; đối chiếu job records và staging counts.

## Đoạn code cần review

~~~typescript
import { ref, watch, onMounted } from "vue";

type Product = { id: string; name: string; price: number };
type SearchResult = { items: Product[]; total: number };

export function useCatalogSearch() {
  const query = ref("");
  const category = ref("all");
  const page = ref(1);
  const products = ref<Product[]>([]);
  const total = ref(0);
  const loading = ref(false);
  const error = ref("");
  const cache = new Map<string, SearchResult>();

  async function search() {
    const key = query.value + ":" + category.value + ":" + page.value;
    const cached = cache.get(key);
    if (cached) {
      products.value = cached.items;
      total.value = cached.total;
      return;
    }

    loading.value = true;
    error.value = "";
    try {
      const response = await fetch(
        "/api/catalog/search?q=" + query.value +
        "&category=" + category.value + "&page=" + page.value,
        { credentials: "include" }
      );
      const result = (await response.json()) as SearchResult;
      cache.set(key, result);
      products.value = result.items;
      total.value = result.total;
    } catch (e) {
      error.value = String(e);
    } finally {
      loading.value = false;
    }
  }

  watch([query, category, page], search);
  onMounted(search);

  function reset() {
    query.value = "";
    category.value = "all";
    page.value = 1;
  }

  return { query, category, page, products, total, loading, error, reset };
}
~~~

## Kết quả code review tham khảo

### [High] — Race condition ghi đè kết quả mới

**Vấn đề:** Response của request cũ có thể ghi vào products sau response mới.  
**Tại sao xảy ra:** Watcher gọi search mà không cancel/guard request identity.  
**Ảnh hưởng production:** UI hiển thị sai query/category/page, dẫn đến quyết định mua hàng sai.  
**Cách sửa:** Abort previous request và dùng monotonically increasing sequence; chỉ request hiện hành được commit state.

### [High] — Cache không phân vùng theo auth context

**Vấn đề:** Cache key chỉ gồm query/category/page, không chứa identity hoặc permission version.  
**Tại sao xảy ra:** Cache sống trong composable instance, không có invalidation khi account/tenant đổi.  
**Ảnh hưởng production:** UI có thể hiển thị stale B2B products của account trước. Đây là lỗi hiển thị nhạy cảm; nếu API cũng thiếu authorization thì mức độ nghiêm trọng tăng thành server-side data exposure.  
**Cách sửa:** Clear cache và state khi auth context thay đổi; hoặc key theo tenant/account + authorization version. Bảo đảm API luôn enforce quyền và HTTP response private/no-store phù hợp.

### [High] — HTTP errors bị coi là dữ liệu thành công

**Vấn đề:** fetch không reject với 401/403/500; code parse JSON rồi cast trực tiếp.  
**Tại sao xảy ra:** Không kiểm tra response.ok và schema runtime.  
**Ảnh hưởng production:** UI sai, lỗi im lặng, dữ liệu cache hỏng.  
**Cách sửa:** Check status; xử lý 401/403 theo auth flow; validate response schema trước khi cache.

### [Medium] — Không encode query parameters

**Vấn đề:** Ghép URL bằng string; ký tự &, #, dấu + hoặc Unicode có thể làm sai query.  
**Tại sao xảy ra:** Không dùng URLSearchParams.  
**Ảnh hưởng production:** Kết quả sai hoặc filter bị thay đổi ngoài ý muốn.  
**Cách sửa:** Dùng URLSearchParams và canonical key từ normalized inputs.

### [Medium] — Cache hit không vô hiệu hóa request đang chạy

**Vấn đề:** Khi cache hit, hàm return sớm nhưng request cũ vẫn có thể ghi state.  
**Tại sao xảy ra:** Không có một cơ chế request lifecycle chung.  
**Ảnh hưởng production:** UI nhảy lại kết quả cũ sau khi đã hiển thị cached result.  
**Cách sửa:** Tăng sequence và abort trước cả nhánh cache hit.

### [Medium] — Loading/error không gắn với request hiện hành

**Vấn đề:** finally của request cũ đặt loading=false khi request mới chưa xong; error cũ có thể ghi đè.  
**Tại sao xảy ra:** Shared state không kiểm tra sequence.  
**Ảnh hưởng production:** Spinner biến mất sớm, thông báo lỗi sai.  
**Cách sửa:** Guard mọi mutation theo request identity; clear error ngay khi bắt đầu lượt tìm kiếm mới.

### [Medium] — Request storm và pagination không nhất quán

**Vấn đề:** Watch lập tức gửi request cho từng ký tự; đổi category không reset page.  
**Tại sao xảy ra:** Không debounce input, không chuẩn hóa transition của filter/page.  
**Ảnh hưởng production:** Tăng tải API, trang rỗng bất ngờ.  
**Cách sửa:** Debounce query 200–350ms theo UX đo được, reset page khi filter đổi; tránh multiple requests không cần thiết.

### [Medium] — Không cleanup khi component unmount

**Vấn đề:** Request có thể tiếp tục sau khi component không còn dùng.  
**Tại sao xảy ra:** Không abort trong onScopeDispose.  
**Ảnh hưởng production:** Waste network, stale writes và khó debug.  
**Cách sửa:** Abort và invalidate sequence khi scope dispose.

### [Low] — Cache không có TTL, capacity hay invalidation

**Vấn đề:** Map giữ kết quả vô thời hạn trong vòng đời composable.  
**Tại sao xảy ra:** Không định nghĩa freshness/capacity.  
**Ảnh hưởng production:** Giá/tồn kho cũ và memory tăng theo số search.  
**Cách sửa:** Bounded TTL cache hoặc bỏ client cache nếu chưa có business freshness contract.

## Phiên bản đề xuất

~~~typescript
import {
  ref, watch, onScopeDispose, type Ref
} from "vue";

type Product = { id: string; name: string; price: number };
type SearchResult = { items: Product[]; total: number };
type CacheEntry = { value: SearchResult; expiresAt: number };

export function useCatalogSearch(authScope: Ref<string>) {
  const query = ref("");
  const category = ref("all");
  const page = ref(1);
  const products = ref<Product[]>([]);
  const total = ref(0);
  const loading = ref(false);
  const error = ref("");
  const cache = new Map<string, CacheEntry>();
  let sequence = 0;
  let controller: AbortController | undefined;

  async function search() {
    const mine = ++sequence;
    controller?.abort();
    controller = new AbortController();
    loading.value = true;
    error.value = "";

    const params = new URLSearchParams({
      q: query.value.trim(), category: category.value,
      page: String(page.value)
    });
    const key = JSON.stringify([authScope.value, params.toString()]);
    const hit = cache.get(key);
    if (hit && hit.expiresAt > Date.now()) {
      products.value = hit.value.items;
      total.value = hit.value.total;
      loading.value = false;
      return;
    }

    try {
      const response = await fetch("/api/catalog/search?" + params, {
        credentials: "include",
        cache: "no-store",
        signal: controller.signal
      });
      if (!response.ok) throw new Error("HTTP " + response.status);
      const body: unknown = await response.json();
      if (!isSearchResult(body)) throw new Error("Invalid response");
      if (mine !== sequence) return;
      cache.set(key, { value: body, expiresAt: Date.now() + 15_000 });
      if (cache.size > 100) cache.delete(cache.keys().next().value!);
      products.value = body.items;
      total.value = body.total;
    } catch (e) {
      if (mine !== sequence) return;
      if (e instanceof DOMException && e.name === "AbortError") return;
      error.value = e instanceof Error ? e.message : "Search failed";
    } finally {
      if (mine === sequence) loading.value = false;
    }
  }

  // Runtime shape validation: replace with shared schema if available.
  function isSearchResult(v: unknown): v is SearchResult {
    if (typeof v !== "object" || v === null) return false;
    const x = v as Record<string, unknown>;
    return Number.isSafeInteger(x.total) &&
      (x.total as number) >= 0 &&
      Array.isArray(x.items) &&
      x.items.every((p: unknown) => {
        if (typeof p !== "object" || p === null) return false;
        const y = p as Record<string, unknown>;
        return typeof y.id === "string" &&
          typeof y.name === "string" &&
          typeof y.price === "number" &&
          Number.isFinite(y.price);
      });
  }

  let timer: ReturnType<typeof setTimeout> | undefined;
  watch([query, category], () => { page.value = 1; });
  watch([query, category, page], () => {
    clearTimeout(timer);
    // Invalidate old results immediately, not only after debounce.
    ++sequence;
    controller?.abort();
    loading.value = true;
    timer = setTimeout(() => { void search(); }, 250);
  }, { immediate: true });

  watch(authScope, () => {
    ++sequence;
    controller?.abort();
    cache.clear();
    products.value = [];
    total.value = 0;
    error.value = "";
    clearTimeout(timer);
    timer = setTimeout(() => { void search(); }, 0);
  });

  onScopeDispose(() => {
    ++sequence;
    controller?.abort();
    clearTimeout(timer);
  });

  return { query, category, page, products, total, loading, error };
}
~~~

**Giả định bắt buộc:** authScope là giá trị do auth layer cung cấp, thay đổi khi login/logout, tenant hoặc permission context thay đổi; không dùng email hay token raw làm cache key. Khi logout, auth layer phải clear state đồng bộ trước khi account khác dùng UI. Server vẫn bắt buộc kiểm tra quyền trên từng request; client cache không phải security boundary. Với dữ liệu nhạy cảm, có thể bỏ cache hoàn toàn thay vì giữ TTL 15 giây. Nếu authScope thay đổi đúng lúc request cũ hoàn thành, sequence guard loại bỏ response cũ. Production cần đảm bảo watchers không gửi trùng request khi query/category và page đổi cùng tick; có thể tách normalized search state để kiểm soát chặt hơn.

## Giải thích thiết kế sau khi sửa

Sequence guard quyết định quyền ghi state, kể cả khi AbortController không thể ngăn một response đã hoàn tất. Cancellation giảm tải mạng và công việc server khi có hỗ trợ, không phải correctness guarantee. Runtime validation tránh đưa JSON không đúng contract vào UI. URLSearchParams giữ ngữ nghĩa query. Cache key phụ thuộc auth context, có TTL/capacity và clear khi identity đổi; API authorization vẫn là tầng bảo vệ chính.

## Trade-offs

- Debounce giảm request nhưng tăng thời gian phản hồi; nên đo UX, không cố định mọi màn hình.
- Bỏ cache đơn giản và an toàn hơn cho giá/tồn kho nhạy cảm; cache có lợi khi traffic và freshness contract chứng minh được.
- Client-side cancellation không bảo đảm backend ngừng xử lý; API cần timeout, cancellation propagation và rate limits.
- Thư viện query management có thể giảm code thủ công, nhưng thêm dependency và yêu cầu cấu hình cache scope đúng.
- Server-rendered catalog cho SEO là quyết định độc lập; không nên dùng client search state làm giải pháp SEO duy nhất.

## Cách kiểm thử

1. **Race test:** Mock response A 800ms, B 50ms; nhập A rồi B, UI cuối cùng chỉ hiển thị B, kể cả A hoàn thành muộn.
2. **Auth/E2E:** Login account B2B A, tìm sản phẩm riêng, logout và login B; không còn kết quả A, API từ chối truy cập dữ liệu A.
3. **Failure-path:** HTTP 403/500, malformed JSON, network offline; không cache lỗi, hiển thị error đúng lượt request.
4. **Pagination:** Đang page 5, đổi category; request cuối dùng page 1 và không có stale update.
5. **Load/browser:** Gõ 20 ký tự nhanh, kiểm tra số request, aborts, UI latency và memory sau nhiều searches.

## Quan sát trong production

Browser telemetry: search sequence, query length (không log nội dung nhạy cảm), category, page, request duration, status code, aborted count, stale-response-dropped count, cache hit ratio và auth-scope-change events không chứa identity raw. API: trace correlation, 401/403 rates, p95/p99 latency, query execution time và request volume. Network waterfall và Playwright traces giúp tái hiện race; cảnh báo khi search errors hoặc stale results tăng sau deploy. Không ghi full search query nếu có thể chứa dữ liệu cá nhân.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Durability khác concurrency safety:** ConcurrentQueue thread-safe trong một process nhưng không durable và không cross-instance; durable job record cần atomic claim, lease, retry và idempotent effects.
- **IIS lifecycle là failure mode thực:** recycle/deploy có thể cắt ngang worker; thiết kế phải resume được, không dựa vào process tồn tại vĩnh viễn.
- **Client async correctness:** response hoàn thành không theo thứ tự; chỉ request còn hiệu lực được ghi state.
- **Authorization không phải cache key:** browser cache cần lifecycle theo identity/tenant/permission; API phải tự enforce authorization.

## Mẫu tư duy cần nhớ

1. Tách **durable state** khỏi in-memory notification.
2. Thiết kế **retry + idempotency + lease ownership** như một hợp đồng thống nhất.
3. Kiểm thử **crash giữa transaction** thay vì chỉ happy path.
4. Với async UI, kiểm tra **ai được quyền commit state**, không chỉ ai được gửi request.
5. Chọn giải pháp đơn giản nhất thỏa invariants và có telemetry chứng minh.
