# Câu 1 — CPU chưa đầy nhưng API vẫn treo hàng loạt: .NET ThreadPool starvation và sync-over-async đang xảy ra thế nào?

**Loại câu hỏi:** Internal Mechanism + Production Debugging  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** C#, async/await, .NET ThreadPool, ASP.NET Core, task scheduling, blocking, performance diagnostics, observability, incident response

## Bối cảnh

Một ASP.NET Core API chạy .NET 8 trên Linux containers. Service nhận khoảng 250 requests/second và gọi hai downstream HTTP APIs.

Sau một thay đổi nhỏ ở lớp orchestration, production bắt đầu có symptom:

- p50 vẫn khoảng 80–120 ms;
- p99 tăng lên 15–30 giây khi traffic cao;
- CPU chỉ 35–55%, không chạm container limit;
- memory ổn định, không có GC pause bất thường;
- database latency bình thường;
- downstream APIs trả lời trong 100–300 ms;
- Kestrel connection count tăng mạnh;
- restart pod làm latency giảm ngay, nhưng vài phút sau symptom quay lại khi tải tăng.

Code mới có đoạn:

```csharp
public sealed class CheckoutSummaryService
{
    private readonly PricingClient _pricing;
    private readonly InventoryClient _inventory;

    public async Task<CheckoutSummary> BuildAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        var priceTask = _pricing.GetAsync(sku, cancellationToken);
        var inventoryTask = _inventory.GetAsync(sku, cancellationToken);

        var price = priceTask.Result;
        var inventory = inventoryTask.GetAwaiter().GetResult();

        return new CheckoutSummary(price, inventory);
    }
}
```

Ở một nơi khác, developer cố “fix” bằng cách bọc blocking work vào `Task.Run`:

```csharp
var result = await Task.Run(() =>
{
    return _legacyClient.LoadAsync(id, cancellationToken).Result;
}, cancellationToken);
```

Dashboard có thêm vài metric:

```text
process_cpu_percent                 = 47%
dotnet_thread_pool_thread_count     = tăng đều từ ~20 lên >300
dotnet_thread_pool_queue_length     = tăng mạnh khi incident xảy ra
request_duration_p99                = 24s
outbound_http_duration_p99          = 280ms
```

Một developer cho rằng đây không thể là ThreadPool starvation vì CPU chưa đạt 100%. Người khác muốn tăng minimum worker threads lên 500 để xử lý nhanh hơn.

## Câu hỏi chính

Hãy giải thích cơ chế khiến `.Result`/`.GetAwaiter().GetResult()` trên asynchronous I/O có thể gây ThreadPool starvation trong ASP.NET Core ngay cả khi CPU chưa cao. Phân biệt starvation với deadlock kiểu cổ điển do `SynchronizationContext`, giải thích vì sao `Task.Run(... .Result)` không sửa root cause, rồi đưa ra quy trình chẩn đoán và remediation production-safe.

## Câu hỏi làm rõ nên cân nhắc

1. Blocking call nằm trên request path nào và có bao nhiêu concurrent requests đi qua path đó?
2. Có synchronous locks, `SemaphoreSlim.Wait()`, synchronous logging hoặc sync-over-async ở dependency khác không?
3. ThreadPool queue length, thread count và completed work item rate thay đổi thế nào theo thời gian?
4. Downstream latency có spike thật hay chỉ application không có worker thread để tiếp tục continuation?
5. Có CPU quota/throttling ở container/cgroup khiến runtime thấy processor availability khác host không?

## Gợi ý tư duy

### Gợi ý 1

Async I/O không cần giữ một worker thread trong thời gian chờ network. Nhưng `.Result` biến chờ bất đồng bộ thành chờ blocking và giữ worker thread bị chiếm.

### Gợi ý 2

Continuation của những operation đã hoàn tất vẫn cần execution capacity. Nếu quá nhiều worker đang đứng chờ chính các tasks đó, queue có thể tăng dù CPU rảnh.

### Gợi ý 3

ThreadPool có cơ chế inject thêm threads nhưng tăng dần và có chi phí; “thêm thật nhiều threads” có thể chỉ che symptom, tăng context switching và memory.

## Cấu trúc trả lời đề xuất

1. Mô tả request execution và async I/O bình thường.
2. Chỉ ra chỗ synchronous blocking làm mất lợi ích async.
3. Giải thích worker starvation và queue buildup.
4. Phân biệt starvation với `SynchronizationContext` deadlock.
5. Giải thích vì sao CPU thấp không loại trừ starvation.
6. Dùng runtime counters/traces/dumps để chứng minh hypothesis.
7. Sửa code thành async-all-the-way.
8. Xử lý legacy synchronous boundary nếu bắt buộc.
9. Đánh giá min threads như tactical mitigation, không phải durable fix.
10. Thêm load/regression test và alerting.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `.Result` và `.GetAwaiter().GetResult()` block current worker thread cho tới khi task hoàn thành.
- Với I/O-bound async code, worker thread đáng lẽ được trả về pool trong lúc socket I/O đang chờ.
- Khi nhiều requests đồng thời block workers, continuations/work items khác phải xếp hàng; ThreadPool tăng thread count nhưng không nhất thiết đủ nhanh để giữ latency ổn định.
- CPU có thể thấp vì threads đang **blocked/waiting**, không phải executing CPU work.
- ASP.NET Core không có request `SynchronizationContext` kiểu ASP.NET cũ, nên pattern này thường biểu hiện starvation/throughput collapse hơn là deadlock kinh điển “continuation phải quay về đúng context đang bị block”.
- `Task.Run(() => asyncCall.Result)` vẫn tiêu tốn một ThreadPool worker để block và còn thêm scheduling overhead.
- Permanent fix là propagate async: `await` xuyên suốt call chain.

### Điểm cộng

- Theo dõi `dotnet.thread_pool.queue.length`, thread count, work item count, request concurrency và outbound dependency duration cùng timeline.
- Dùng `dotnet-counters`, `dotnet-trace`, `dotnet-stack`/dump hoặc equivalent production tooling để xem nhiều threads đứng tại `Task.InternalWaitCore`, `ManualResetEventSlim`, lock/wait paths.
- Phân biệt starvation với downstream slowness: downstream span có thể hoàn thành nhanh nhưng request continuation bị schedule trễ.
- Cancellation cần propagate; timeout không nên dùng để che scheduler starvation.
- Nếu thật sự có blocking synchronous library không thể thay, isolate concurrency bằng bounded queue/dedicated worker strategy thay vì phát tán `Task.Run` khắp request path.

### Senior+

- Hiểu hill-climbing/thread injection của ThreadPool là adaptive, không phải instant unlimited capacity; workload blocking đột biến có thể tạo positive feedback loop về latency.
- Nhận ra tăng `ThreadPool.SetMinThreads` đôi khi là emergency mitigation hoặc startup tuning, nhưng cần evidence, benchmark và rollback vì có thể tăng memory/context switching/downstream pressure.
- Cân nhắc admission control/backpressure để tránh hàng nghìn requests cùng giữ resources khi service đã saturated.
- Tách “task đã hoàn tất I/O” với “continuation đã có cơ hội chạy”.
- Correlate runtime scheduler evidence với distributed traces để chứng minh thời gian mất ở application scheduling chứ không ở network/database.

## Hướng giải quyết tham khảo

Code đúng trước hết phải giữ asynchronous flow xuyên suốt:

```csharp
public async Task<CheckoutSummary> BuildAsync(
    string sku,
    CancellationToken cancellationToken)
{
    var priceTask = _pricing.GetAsync(sku, cancellationToken);
    var inventoryTask = _inventory.GetAsync(sku, cancellationToken);

    await Task.WhenAll(priceTask, inventoryTask);

    return new CheckoutSummary(
        await priceTask,
        await inventoryTask);
}
```

Hoặc sau `Task.WhenAll`, nếu types phù hợp, lấy results mà không thêm blocking. Điểm quan trọng không nằm ở syntax cụ thể mà ở việc không chặn worker thread trong lúc chờ I/O.

Trong ASP.NET Core, request code thường chạy trên ThreadPool. Một outbound HTTP request bắt đầu, socket I/O được đăng ký với OS và method `await` có thể trả worker thread lại pool. Khi I/O hoàn tất, continuation được queue để một worker thực hiện tiếp.

Nếu thay `await` bằng `.Result`, worker hiện tại đứng chờ. Với vài request điều này có vẻ vẫn ổn. Với hàng trăm concurrent requests, nhiều workers cùng đứng chờ. ThreadPool queue dài ra vì work mới và continuations không có worker sẵn. Runtime bắt đầu inject thêm threads nhưng quá trình này có giới hạn/thích nghi; trong lúc đó request latency tăng mạnh.

CPU chỉ 47% không phản bác hypothesis. Blocked thread gần như không dùng CPU. Đây chính là lý do starvation có thể gây latency cực cao trong khi CPU không saturated.

Tôi sẽ lấy evidence theo timeline:

```text
- ASP.NET Core request rate / current requests / p95-p99
- ThreadPool thread count
- ThreadPool queue length
- completed work-item rate
- process CPU + container CPU throttling
- outbound HTTP span duration
- exception/timeout/cancellation rate
```

Sau đó dùng trace hoặc dump trong incident window. Nếu hàng trăm managed threads có stack liên quan `.Result`, `GetResult`, waits hoặc synchronous locks, đó là bằng chứng mạnh hơn việc suy đoán từ latency.

`Task.Run(() => LoadAsync().Result)` không giúp. Nó chuyển blocking từ request worker hiện tại sang một ThreadPool work item khác, nhưng vẫn cần worker để đứng chờ. Nếu caller cũng await `Task.Run`, bạn thêm hop mà không làm operation trở thành non-blocking.

Nếu `_legacyClient` chỉ có synchronous API thật sự và không thể thay ngay, tôi xem nó như scarce blocking resource. Có thể đặt bounded concurrency bằng `SemaphoreSlim.WaitAsync`, Channel/queue + fixed workers hoặc tách workload sang process/service khác tùy SLO. Mục tiêu là không cho traffic request tạo unbounded blocking concurrency.

Tăng min threads có thể làm incident giảm tạm thời nếu runtime inject threads quá chậm so với workload, nhưng tôi chỉ dùng khi có benchmark/evidence. Nó không thay thế việc loại bỏ sync-over-async và có thể làm downstream bị flood mạnh hơn.

Regression test phải chạy đủ concurrency để tái hiện queue buildup, không chỉ benchmark một request. Acceptance criteria nên gồm p99, ThreadPool queue, thread count ổn định và dependency latency trong các mức tải gần production.

## Mẫu trả lời trong phỏng vấn

“`.Result` biến I/O bất đồng bộ thành synchronous wait và giữ ThreadPool worker. Khi nhiều requests cùng làm vậy, workers bị block, trong khi continuations của các HTTP calls hoàn tất vẫn phải chờ worker để chạy. Queue tăng và ThreadPool phải inject thêm threads, nên latency có thể lên hàng chục giây dù CPU chỉ 40–50% vì phần lớn threads đang chờ chứ không tính toán.

ASP.NET Core không có request SynchronizationContext giống ASP.NET classic, nên tôi không gọi đây mặc định là context deadlock; symptom phù hợp hơn với ThreadPool starvation. Tôi chứng minh bằng ThreadPool queue/thread counters, traces/dumps và distributed spans. Fix chính là async-all-the-way. `Task.Run(() => asyncCall.Result)` chỉ dời blocking sang worker khác.

Tăng minimum threads có thể là mitigation ngắn hạn nếu được benchmark, nhưng permanent fix là loại blocking trên hot request path và đặt bounded concurrency cho dependency synchronous không thể thay.”

## Câu hỏi đào sâu

1. Tại sao một downstream span có duration 200 ms nhưng parent request có thể đứng thêm 10 giây trước khi tiếp tục?
2. Khi nào `Task.Run` là hợp lý trong ASP.NET Core, và tại sao CPU-bound work khác bản chất I/O-bound async work?
3. Nếu một vendor SDK chỉ cung cấp synchronous API mất 2 giây/call, bạn sẽ bảo vệ service khỏi ThreadPool/resource collapse thế nào?

## Lỗi trả lời thường gặp

- Nói CPU chưa 100% nên không thể starvation.
- Gọi mọi `.Result` trong ASP.NET Core là `SynchronizationContext` deadlock mà không hiểu hosting model.
- Thêm `Task.Run` quanh async I/O như một universal fix.
- Tăng max/min threads cực lớn rồi coi incident đã xử lý.
- Chỉ nhìn HTTP dependency latency mà không xem scheduler queue và stacks.
- Chuyển toàn bộ call chain sang async nhưng bỏ cancellation/timeout/backpressure.

## Thang điểm 0–10

- **0–2:** Chỉ nói “không nên dùng `.Result`”.
- **3–4:** Biết blocking workers nhưng không giải thích queue/CPU symptom.
- **5–6:** Giải thích đúng starvation, async-all-the-way và có runtime metrics cơ bản.
- **7–8:** Phân biệt deadlock/starvation, có traces/dumps, bounded concurrency và mitigation trade-offs.
- **9–10:** Reasoning đầy đủ từ scheduler internals đến incident evidence, capacity/backpressure và production validation.

# Câu 2 — Azure Service Bus xử lý cùng một payment event hai lần dù message đã `Complete`: at-least-once delivery, lock loss và idempotency

**Loại câu hỏi:** Distributed Systems + Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, messaging semantics, idempotency, transactions, EF Core/SQL Server, retries, message locks, outbox/inbox, observability, failure recovery

## Bối cảnh

Một payment service publish event:

```json
{
  "eventId": "evt-84721",
  "orderId": "ORD-99314",
  "type": "PaymentCaptured",
  "amount": 149.90
}
```

Một fulfillment worker đọc từ Azure Service Bus queue và tạo shipment record trong SQL Server:

```csharp
processor.ProcessMessageAsync += async args =>
{
    var evt = args.Message.Body.ToObjectFromJson<PaymentCaptured>();

    _db.Shipments.Add(new Shipment
    {
        OrderId = evt.OrderId,
        Amount = evt.Amount,
        CreatedAt = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(args.CancellationToken);

    await args.CompleteMessageAsync(args.Message);
};
```

Configuration rút gọn:

```csharp
new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 32,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(5)
};
```

Production incident cho thấy một số orders có hai shipment records giống nhau. Log của một event:

```text
12:01:10 worker-A receive evt-84721 deliveryCount=1
12:01:11 worker-A INSERT shipment succeeded
12:01:14 worker-A CompleteMessageAsync timeout
12:01:42 worker-B receive evt-84721 deliveryCount=2
12:01:43 worker-B INSERT shipment succeeded
12:01:44 worker-B complete succeeded
```

Một incident khác có processing mất hơn 5 phút do gọi warehouse API chậm; worker log `MessageLockLostException`, sau đó message được deliver lại.

Team đề xuất ba cách:

1. tăng `MaxAutoLockRenewalDuration` lên 30 phút;
2. bật Service Bus duplicate detection rồi coi như xong;
3. trước khi insert, chạy `SELECT` xem `OrderId` đã tồn tại chưa.

Business yêu cầu không tạo shipment trùng và không được bỏ mất payment event.

## Câu hỏi chính

Hãy giải thích vì sao một consumer có thể commit database thành công nhưng message vẫn được redeliver, và tại sao `Complete` không tạo atomic transaction với SQL Server write trong thiết kế trên. Thiết kế consumer idempotent chịu được crash, timeout, lock loss và concurrent duplicate delivery; phân tích vai trò của Service Bus duplicate detection, unique constraint/inbox table, retry, dead-lettering và observability.

## Câu hỏi làm rõ nên cân nhắc

1. `eventId` có globally unique và stable qua publisher retry không?
2. Một order có thể hợp lệ tạo nhiều shipments hay business key thực sự là `eventId`, `orderId + type`, hay key khác?
3. Processing logic có external side effect như warehouse booking/email ngoài SQL transaction không?
4. Queue lock duration, retry policy, max delivery count và DLQ process hiện cấu hình thế nào?
5. Publisher có transactional outbox hay có khả năng publish mất/trùng event quanh database commit không?

## Gợi ý tư duy

### Gợi ý 1

Có hai durable systems độc lập: SQL Server và Service Bus. Giữa `COMMIT SQL` và `Complete message` luôn có một failure window nếu không có transaction protocol phù hợp.

### Gợi ý 2

At-least-once delivery nghĩa là consumer phải coi duplicate là trạng thái bình thường có thể xảy ra, không phải bug hiếm chỉ cần retry tuning.

### Gợi ý 3

“Check rồi insert” không an toàn nếu hai workers cùng check trước khi một bên commit. Idempotency cần một atomic guard ở durable store.

## Cấu trúc trả lời đề xuất

1. Mô tả lock/settlement và at-least-once semantics.
2. Xác định failure window SQL commit → Service Bus complete.
3. Chỉ ra lock expiry/connection loss cũng tạo redelivery.
4. Chọn idempotency key theo domain.
5. Enforce bằng unique constraint hoặc inbox record trong cùng DB transaction.
6. Xử lý external side effects bằng state machine/outbox nếu cần.
7. Phân tích duplicate detection phía broker.
8. Thiết kế retry/DLQ và poison-message handling.
9. Thêm telemetry theo message ID/event ID/delivery count.
10. Test crash/replay/concurrency có chủ đích.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Message lock không phải ownership vĩnh viễn; nếu lock hết hạn hoặc settlement không được broker xác nhận, message có thể được deliver lại.
- SQL commit và `CompleteMessageAsync` là hai operations độc lập trong code trên; thành công của một bên không guarantee bên kia.
- Consumer phải idempotent vì duplicate delivery là expected behavior trong at-least-once messaging.
- `SELECT-if-not-exists` riêng lẻ có race condition dưới concurrent consumers.
- Dùng database unique constraint hoặc inbox/idempotency table với unique event ID để duplicate attempts hội tụ về một durable result.
- Idempotency record và business mutation nên commit trong cùng SQL transaction.
- Retry không được tạo thêm side effects ngoài kiểm soát.

### Điểm cộng

- Phân biệt Service Bus `MessageId` với domain `eventId`; chọn key phải stable qua producer retries.
- Service Bus duplicate detection chủ yếu xử lý duplicate **send** theo message identity trong configured history window; nó không thay thế consumer idempotency cho redelivery sau processing/settlement failure.
- Unique constraint là last-line concurrency guard ngay cả khi application đã check trước.
- `MessageLockLostException` sau khi business transaction đã commit không nên khiến handler “undo” commit một cách ngây thơ; redelivery phải trở nên no-op/idempotent.
- DLQ cần operational ownership, reason metadata, replay tooling và idempotency vẫn phải giữ khi replay.

### Senior+

- Nếu processing bao gồm external warehouse call, cần phân biệt idempotency của local DB với idempotency của external API; có thể cần provider idempotency key, local state machine và/or transactional outbox.
- Publisher reliability cũng cần xem: transactional outbox giải quyết database state committed nhưng event chưa publish hoặc publish retry.
- Không kéo lock renewal vô hạn cho work dài; xem xét chia nhỏ workflow hoặc persist state rồi xử lý tiếp theo asynchronous steps.
- Có unique business invariant ở database thay vì chỉ application-level mutex; nhiều instances/restarts vẫn an toàn.
- Chaos test có intentional crash ngay sau SQL commit và trước settlement để chứng minh design.

## Hướng giải quyết tham khảo

Incident log là failure window điển hình:

```text
SQL commit succeeded
        ↓
process/network/broker settlement failed
        ↓
Service Bus chưa có durable acknowledgement rằng message đã complete
        ↓
lock expires / delivery resumes
        ↓
message được deliver lại
```

Không thể dựa vào việc handler “đã chạy gần xong” để đảm bảo exactly-once side effect. Tôi thiết kế business operation idempotent.

Ví dụ tạo inbox table:

```sql
CREATE TABLE dbo.ProcessedMessages
(
    ConsumerName nvarchar(100) NOT NULL,
    EventId      nvarchar(100) NOT NULL,
    ProcessedAt  datetime2      NOT NULL,
    CONSTRAINT PK_ProcessedMessages
        PRIMARY KEY (ConsumerName, EventId)
);
```

Trong một SQL transaction:

```text
BEGIN TRANSACTION
  INSERT ProcessedMessages(ConsumerName, EventId, ...)
  INSERT/UPDATE Shipment business state
COMMIT
```

Nếu duplicate worker cùng xử lý `evt-84721`, chỉ một transaction có thể insert unique inbox key. Transaction còn lại nhận duplicate-key result và có thể coi message đã được xử lý, sau đó settle message mà không tạo shipment mới.

Tùy domain, có thể unique trực tiếp trên shipment business key:

```sql
CREATE UNIQUE INDEX UX_Shipment_PaymentEventId
ON dbo.Shipments(PaymentEventId);
```

Tôi thường muốn lưu `PaymentEventId` trên entity hoặc inbox để audit rõ nguồn side effect. Nếu một order có thể tạo nhiều shipment hợp lệ, unique `OrderId` đơn thuần sẽ sai domain; key phải phản ánh invariant thật.

Pseudo-code:

```csharp
try
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    _db.ProcessedMessages.Add(new ProcessedMessage
    {
        ConsumerName = "Fulfillment.PaymentCaptured",
        EventId = evt.EventId,
        ProcessedAt = DateTime.UtcNow
    });

    _db.Shipments.Add(new Shipment
    {
        PaymentEventId = evt.EventId,
        OrderId = evt.OrderId,
        Amount = evt.Amount
    });

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
catch (DbUpdateException ex) when (IsUniqueViolation(ex))
{
    // Durable evidence says this event was already committed.
}

await args.CompleteMessageAsync(args.Message);
```

Thực tế cần cẩn thận phân biệt unique violation đúng constraint/idempotency key với lỗi database khác; không swallow mọi `DbUpdateException`.

Service Bus duplicate detection vẫn có giá trị ở producer side nếu publisher vô tình gửi lại cùng `MessageId` trong detection window. Nhưng redelivery của một received message do settlement failure là vấn đề consumer semantics; broker duplicate detection không thay cho idempotent handler.

Việc tăng lock renewal lên 30 phút có thể giảm lock expiration cho processing dài, nhưng không loại failure window sau SQL commit. Nếu handler thường mất >5 phút vì warehouse API, tôi xem lại architecture: persist local work/state nhanh, complete message khi durable state đã được ghi, rồi cho worker khác thực hiện long-running external step; hoặc đảm bảo external call có idempotency key và workflow state có thể resume.

Nếu warehouse API tạo booking, thứ tự side effects rất quan trọng. Local inbox + shipment insert không tự bảo vệ external booking khỏi duplicate call. Tôi sẽ dùng stable idempotency key khi provider hỗ trợ hoặc state machine/outbox để retry action một cách xác định.

Observability tối thiểu:

```text
EventId
ServiceBus MessageId
DeliveryCount
consumer instance
receive timestamp
lock expiry / lock-lost count
business transaction outcome
idempotency-hit count
settlement outcome
DLQ reason
```

Chaos test cần kill process ngay sau SQL commit nhưng trước `CompleteMessageAsync`, ép lock expire, inject settlement timeout và deliver cùng event concurrently. Nếu mỗi test cuối cùng chỉ có đúng một domain side effect, design mới đáng tin.

## Mẫu trả lời trong phỏng vấn

“SQL commit và Service Bus `Complete` không atomic trong code này. Nếu DB commit xong nhưng process chết hoặc settlement timeout, broker vẫn có quyền redeliver message. Vì vậy at-least-once consumer phải idempotent.

Tôi dùng một stable domain `eventId` và enforce uniqueness trong SQL bằng inbox table hoặc unique key. Idempotency record và shipment mutation commit cùng transaction. Khi duplicate delivery tới đồng thời, database constraint quyết định một winner; lần còn lại trở thành no-op rồi complete message.

Broker duplicate detection hữu ích cho duplicate sends nhưng không thay consumer idempotency. Lock renewal chỉ giảm một loại redelivery, không xóa failure window. Với external warehouse side effect, tôi còn cần provider idempotency key hoặc durable workflow/outbox state. Tôi test bằng cách crash ngay sau SQL commit trước message settlement.”

## Câu hỏi đào sâu

1. Nếu publisher database commit thành công nhưng process chết trước khi gửi event, consumer idempotency có giải quyết được không? Bạn cần pattern nào ở producer?
2. Nếu warehouse provider không hỗ trợ idempotency key nhưng booking không được tạo trùng, bạn thiết kế recovery thế nào?
3. Khi replay DLQ sau ba ngày, làm sao đảm bảo idempotency record chưa bị purge quá sớm?

## Lỗi trả lời thường gặp

- Cho rằng `CompleteMessageAsync` làm SQL transaction trở thành exactly-once.
- Chỉ tăng lock duration/renewal rồi tuyên bố hết duplicate.
- Dùng `SELECT` trước `INSERT` nhưng không có unique constraint.
- Dựa hoàn toàn vào Service Bus duplicate detection.
- Swallow mọi database exception và coi đó là duplicate.
- Có idempotency cho SQL nhưng quên external side effects.
- Replay DLQ mà không giữ idempotency/audit state tương thích.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất retry hoặc tăng lock.
- **3–4:** Biết duplicate delivery nhưng idempotency còn application-level, có race.
- **5–6:** Có durable unique key/inbox và transaction với business mutation.
- **7–8:** Phân biệt broker duplicate detection, lock semantics, publisher outbox, DLQ và external side effects.
- **9–10:** Thiết kế được end-to-end failure model, resumable workflow và chaos validation cho at-least-once system.

# Câu 3 — User đăng nhập thành công nhưng thỉnh thoảng bị logout sau scale-out: ASP.NET Core Data Protection key ring đang bị chia cắt

**Loại câu hỏi:** Security + Architecture + Production Debugging  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core Authentication, Data Protection, cookies, key management, scale-out, Azure App Service/containers, key rotation, security, deployment, observability

## Bối cảnh

Một ASP.NET Core web application dùng cookie authentication:

```csharp
builder.Services
    .AddAuthentication("Cookies")
    .AddCookie("Cookies", options =>
    {
        options.Cookie.Name = ".Company.Portal.Auth";
        options.ExpireTimeSpan = TimeSpan.FromHours(8);
        options.SlidingExpiration = true;
    });
```

Ứng dụng trước đây chạy một instance nên ổn định. Sau khi scale lên 6 containers phía sau load balancer, user bắt đầu báo:

- login thành công;
- vài request sau bị redirect về `/login`;
- symptom không xảy ra với mọi request;
- bật sticky session làm symptom gần như biến mất;
- restart/rolling deployment làm số lượng logout tăng tạm thời;
- không thấy session record nào bị xóa trong database;
- JWT access token của một API khác vẫn hợp lệ;
- application logs ở một số instances có warning liên quan key storage/ephemeral key repository;
- containers dùng ephemeral filesystem.

Startup code không cấu hình Data Protection ngoài defaults.

Team đưa ra các proposal:

1. bật sticky session vĩnh viễn;
2. lưu authentication cookie plaintext vì HTTPS đã mã hóa transport;
3. copy một encryption key cố định vào environment variable của mọi container;
4. persist Data Protection keys vào shared durable storage và bảo vệ key ring bằng platform key-management mechanism.

Ngoài ra, blue/green deployment có lúc chạy đồng thời `v1` và `v2`. Security team yêu cầu key rotation định kỳ và không muốn application source chứa master key.

## Câu hỏi chính

Hãy giải thích ASP.NET Core cookie authentication phụ thuộc vào Data Protection thế nào, tại sao các instances có key rings khác nhau tạo symptom “login lúc được lúc mất”, và vì sao sticky session chỉ che vấn đề. Thiết kế key management production-safe cho scale-out và rolling deployment, bao gồm persistence, at-rest protection, application discriminator/purpose isolation, rotation/revocation trade-offs và deployment/incident runbook.

## Câu hỏi làm rõ nên cân nhắc

1. App chạy trên Azure App Service, Kubernetes, VM hay platform nào và storage nào thực sự durable/shared?
2. `SetApplicationName` hoặc equivalent application isolation có được cấu hình nhất quán giữa slots/versions không?
3. Nhiều applications khác có dùng cùng cookie name/domain hoặc cần intentional cookie sharing không?
4. Key ring hiện được persist ở đâu, container restart có làm mất keys không?
5. Requirement khi compromise key là revoke ngay mọi cookies hay giữ availability trong một migration window?

## Gợi ý tư duy

### Gợi ý 1

Authentication cookie không chỉ là một opaque ID. ASP.NET Core dùng Data Protection để protect/unprotect authentication ticket.

### Gợi ý 2

Instance A có thể phát cookie bằng key mà instance B chưa từng thấy. B không unprotect được ticket và coi request như unauthenticated.

### Gợi ý 3

Shared key ring cần vừa durable/available, vừa được bảo vệ như security-sensitive material; “share được” không đồng nghĩa “để plaintext ở mọi nơi”.

## Cấu trúc trả lời đề xuất

1. Mô tả authentication ticket và protect/unprotect flow.
2. Liên hệ load balancing với per-instance key rings.
3. Giải thích restart/deployment symptom.
4. Bác bỏ sticky session như correctness fix.
5. Chọn shared durable key repository.
6. Bảo vệ keys at rest bằng platform key-management/key wrapping phù hợp.
7. Cấu hình application isolation nhất quán.
8. Thiết kế rotation, retention, revocation và rollback compatibility.
9. Thêm telemetry/health checks nhưng không log secret key material.
10. Xây runbook cho key loss/compromise/deployment.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Cookie authentication ticket được protected bằng ASP.NET Core Data Protection; instance phải có compatible key ring/purpose/application identity để unprotect cookie.
- Mỗi ephemeral container tự tạo keys có thể khiến cookie tạo bởi A không đọc được ở B.
- Restart có thể làm mất local ephemeral keys, khiến cả chính instance đó không đọc được cookies cũ.
- Sticky session giảm cross-instance routing nên che symptom nhưng không giải quyết failover/restart/rolling deployment.
- Production scale-out cần persist Data Protection keys vào shared durable repository phù hợp platform.
- Key ring cần được bảo vệ at rest; không hard-code master secret trong source.
- Không xóa/revoke old key ngay chỉ vì rotation bình thường; cookies đã phát bằng old key cần đọc được trong compatibility period.

### Điểm cộng

- Cấu hình cùng application name/discriminator khi các replicas của **cùng app** phải chia sẻ protected payloads; tách discriminator giữa apps không liên quan.
- Nếu intentionally share auth cookie giữa applications, cookie scheme/name/domain, authentication configuration và Data Protection purpose/application identity phải tương thích có chủ đích.
- Hiểu key generation/activation/expiration khác với key revocation.
- Rolling/blue-green versions phải có access tới compatible ring trong overlap window nếu cookies cần sống qua deployment.
- Key storage ACL/IAM phải theo least privilege; deployment pipeline không cần đọc plaintext keys nếu platform wrapping giải quyết được.

### Senior+

- Phân tích availability dependency của key repository: runtime thường dùng cached ring, nhưng bootstrap/rotation/failure modes vẫn cần runbook.
- Key compromise có thể buộc revoke và invalidate sessions; security response khác rotation bình thường.
- Dùng external protector như Key Vault/KMS certificate/key để wrap Data Protection keys nhưng vẫn hiểu rotation của wrapping key và retention requirements.
- Không log key XML/material; chỉ log key IDs/activation/expiration metadata nếu cần diagnostics.
- Test rollback từ `v2` về `v1` trong khi cookies được issue trong overlap window để đảm bảo crypto/application compatibility.

## Hướng giải quyết tham khảo

Cookie handler serialize authentication ticket rồi Data Protection protect payload trước khi gửi về browser. Khi request quay lại, server phải unprotect ticket bằng key/purpose tương thích. HTTPS chỉ bảo vệ transport; browser vẫn giữ cookie và server vẫn cần integrity/confidentiality protection cho ticket. Vì vậy proposal “plaintext vì có TLS” là sai threat model.

Trong single-instance deployment, default local key behavior có thể vô tình đủ dùng. Scale-out làm assumption lộ ra. Nếu A và B có key rings khác nhau:

```text
Login → instance A
A protects cookie bằng key KA

Next request → instance B
B chỉ biết KB
B không unprotect được cookie KA
→ authentication thất bại / redirect login
```

Sticky session giữ user trên A nên symptom giảm. Nhưng nếu A restart, failover hoặc autoscale route đổi instance, lỗi quay lại. Nó là routing workaround, không phải cryptographic correctness.

Tôi cấu hình mọi replicas cùng application dùng chung durable ring. Ví dụ ý tưởng trên Azure có thể là shared Blob Storage cho key repository và Key Vault key để protect keys at rest; trên Kubernetes có thể là một durable secure storage phù hợp platform cùng KMS/secret-management controls. Exact API phụ thuộc hosting environment, nhưng invariant là:

```text
shared + durable key repository
consistent application identity
least-privilege access
keys encrypted/wrapped at rest
old keys retained đủ lâu để unprotect active cookies
```

Một configuration conceptual:

```csharp
builder.Services
    .AddDataProtection()
    .SetApplicationName("Company.Portal")
    // .PersistKeysTo... shared durable repository
    // .ProtectKeysWith... platform-managed key/certificate
    ;
```

Tôi không nhét một static raw encryption key vào environment variable rồi tự viết crypto. Data Protection đã quản lý key lifecycle/purpose derivation; platform key management nên dùng để protect key ring, không thay thế tùy tiện bằng custom crypto.

Rotation bình thường nghĩa là key mới được tạo/activate để protect payload mới, trong khi old non-revoked keys vẫn tồn tại để unprotect cookies cũ. Nếu xóa old key ngay, active sessions được issue bằng key đó sẽ invalid. Vì vậy retention phải dài đủ cho cookie lifetime/deployment overlap theo policy.

Revocation là quyết định security khác. Nếu key bị compromise, team có thể chấp nhận invalidate sessions và buộc login lại. Runbook phải mô tả:

```text
1. xác định key IDs/time window bị ảnh hưởng;
2. revoke/rotate wrapping/data-protection keys theo incident policy;
3. đánh giá toàn bộ protected payloads bị ảnh hưởng;
4. force re-authentication nếu cần;
5. kiểm tra all replicas nhận ring mới;
6. monitor unprotect failures sau remediation.
```

Observability không được log secrets. Tôi muốn biết instance/version, authentication failure category, key-ring load/generation warnings, key identifier metadata và deployment timeline. Một sudden spike `unprotect failed` chỉ trên subset instances là tín hiệu mạnh về configuration/key-ring divergence.

Blue/green deployment cần được test với traffic qua cả v1/v2: login ở v1 rồi request v2, login ở v2 rồi request v1, restart từng node, rotate key trong overlap window. Nếu một version đổi application discriminator/cookie scheme vô tình, shared storage alone vẫn không đảm bảo interoperability.

## Mẫu trả lời trong phỏng vấn

“ASP.NET Core cookie chứa protected authentication ticket. Instance phát cookie và instance đọc cookie phải có Data Protection key ring/purpose/application identity tương thích. Nếu mỗi ephemeral container tự giữ ring riêng, A issue cookie bằng key A nhưng B không decrypt/validate được nên user bị coi là anonymous. Sticky session chỉ giảm xác suất chuyển node; restart/failover vẫn phá session.

Tôi persist key ring vào shared durable storage, bảo vệ ring at rest bằng platform KMS/Key Vault/certificate mechanism và cấu hình application name nhất quán cho replicas cùng app. Rotation tạo key mới nhưng giữ old keys đủ lâu để đọc active cookies; revocation chỉ dùng theo incident/security policy vì có thể invalidate sessions.

Tôi test cross-instance và blue/green interoperability, monitor Data Protection warnings/unprotect failures, và có runbook riêng cho key loss với key compromise.”

## Câu hỏi đào sâu

1. Nếu hai independent applications cố ý muốn share cùng SSO cookie, ngoài shared key ring còn phải thống nhất những yếu tố nào?
2. Nếu Key Vault/KMS tạm unavailable sau khi application đã chạy, service có nhất thiết logout toàn bộ user ngay không? Bạn cần kiểm tra/cân nhắc runtime caching và bootstrap behavior gì?
3. Khi phát hiện một Data Protection key có thể đã bị exfiltrate, vì sao “rotation bình thường” chưa chắc đủ?

## Lỗi trả lời thường gặp

- Cho rằng authentication cookie chỉ là random session ID nên key ring không liên quan.
- Bật sticky session rồi coi là permanent fix.
- Lưu cookie plaintext vì traffic đã qua HTTPS.
- Hard-code một symmetric key và bỏ qua Data Protection lifecycle/purpose isolation.
- Xóa old keys ngay khi rotate làm invalid hàng loạt active cookies.
- Cho mọi applications dùng cùng application name/key ring mà không có intentional trust boundary.
- Debug bằng cách log raw keys hoặc decrypted authentication tickets.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất sticky session/restart.
- **3–4:** Biết phải share key nhưng chưa hiểu cookie/Data Protection lifecycle.
- **5–6:** Có durable shared ring, application identity và at-rest protection.
- **7–8:** Có rotation/retention/revocation distinction, blue-green compatibility và observability.
- **9–10:** Thiết kế đầy đủ crypto trust boundary, compromise runbook, key-management availability và cross-version validation.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async I/O chỉ scale tốt khi call chain không biến lại thành synchronous blocking; ThreadPool starvation có thể xảy ra dù CPU còn rất nhiều headroom.
- Trong ASP.NET Core hiện đại, cần phân biệt sync-over-async starvation với `SynchronizationContext` deadlock của hosting model cũ.
- Azure Service Bus cung cấp delivery semantics mà consumer phải chịu được duplicate; SQL commit và message settlement không mặc nhiên atomic.
- Idempotency đáng tin cần durable atomic guard như unique constraint/inbox, không phải chỉ `SELECT` trước `INSERT`.
- Broker duplicate detection, lock renewal và retry là controls hữu ích nhưng không thay consumer idempotency.
- ASP.NET Core authentication cookies phụ thuộc Data Protection key ring; scale-out cần shared durable keys và consistent application identity.
- Key rotation bình thường khác key revocation sau compromise; retention quyết định khả năng đọc protected payloads đã phát trước đó.

## Mẫu tư duy cần nhớ

- **CPU thấp không chứng minh scheduler/thread capacity khỏe; xem queue, waits và execution stacks.**
- **Async phải đi xuyên suốt hot path; đừng dời blocking sang `Task.Run` rồi gọi đó là non-blocking.**
- **Trong distributed systems, luôn tìm failure window giữa hai durable commits/acknowledgements.**
- **Exactly-once business effect thường đạt bằng idempotency/invariants, không bằng kỳ vọng transport chỉ deliver một lần.**
- **Security state dùng chung giữa replicas phải có trust boundary và lifecycle rõ, không dựa vào sticky routing.**
- **Rotation, retention, revocation và rollback compatibility là bốn quyết định khác nhau.**
