# Code Review Challenge 1 — MongoDB approval workflow bị mất update và tạo duplicate audit event khi nhiều reviewer thao tác đồng thời

**Chủ đề:** C#/.NET 8, MongoDB, optimistic concurrency, atomic update, schema design, idempotency, unique index, retry, multi-document consistency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal approval platform dùng MongoDB. Mỗi approval request là một document trong collection `approvalRequests`; audit event được lưu ở collection `approvalEvents`.

Business rule:

- request bắt đầu ở `Pending`;
- reviewer có thể `Approve` hoặc `Reject`;
- chỉ transition đầu tiên từ `Pending` sang trạng thái cuối cùng được chấp nhận;
- hai reviewer thao tác gần như đồng thời không được ghi đè kết quả của nhau;
- mobile/web client có thể retry cùng một action khi timeout;
- cùng một logical action không được tạo duplicate audit event;
- application chạy trên nhiều instances;
- audit trail phải đủ tin cậy để điều tra ai đã quyết định trạng thái cuối cùng.

Production có các triệu chứng:

- đôi lúc một request được reviewer A approve nhưng vài milliseconds sau lại thành rejected bởi reviewer B;
- một số request có hai audit events trái ngược nhau;
- khi client retry sau timeout, collection `approvalEvents` có duplicate entries;
- log chỉ ghi `requestId`, không có `actionId` hoặc version;
- team đề xuất thêm `lock` static theo `requestId`;
- một developer khác đề xuất bọc toàn bộ method trong retry 3 lần nếu `UpdateOneAsync` hoặc `InsertOneAsync` throw;
- collection đã tăng nhanh vì mỗi retry có thể thêm event mới.

Document rút gọn:

```json
{
  "_id": "APR-2026-000184",
  "status": "Pending",
  "version": 7,
  "reviewedBy": null,
  "reviewedAt": null
}
```

## Đoạn code cần review

```csharp
public sealed class ApprovalService
{
    private readonly IMongoCollection<ApprovalRequest> _requests;
    private readonly IMongoCollection<ApprovalEvent> _events;
    private readonly ILogger<ApprovalService> _logger;

    public ApprovalService(
        IMongoDatabase database,
        ILogger<ApprovalService> logger)
    {
        _requests = database.GetCollection<ApprovalRequest>("approvalRequests");
        _events = database.GetCollection<ApprovalEvent>("approvalEvents");
        _logger = logger;
    }

    public async Task ApproveAsync(
        string requestId,
        string reviewerId,
        string actionId,
        CancellationToken cancellationToken)
    {
        var request = await _requests
            .Find(x => x.Id == requestId)
            .SingleOrDefaultAsync(cancellationToken);

        if (request is null)
            throw new InvalidOperationException("Request not found");

        if (request.Status != ApprovalStatus.Pending)
            throw new InvalidOperationException("Request already completed");

        request.Status = ApprovalStatus.Approved;
        request.ReviewedBy = reviewerId;
        request.ReviewedAt = DateTimeOffset.UtcNow;
        request.Version++;

        await _requests.ReplaceOneAsync(
            x => x.Id == request.Id,
            request,
            cancellationToken: cancellationToken);

        var audit = new ApprovalEvent
        {
            Id = ObjectId.GenerateNewId(),
            RequestId = request.Id,
            ActionId = actionId,
            Action = "Approved",
            ReviewerId = reviewerId,
            CreatedAt = DateTimeOffset.UtcNow
        };

        await _events.InsertOneAsync(audit, cancellationToken: cancellationToken);

        _logger.LogInformation(
            "Approval {RequestId} approved by {ReviewerId}",
            requestId,
            reviewerId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, concurrency, idempotency và consistency trong code.
2. Mô tả timeline cụ thể khi reviewer A và B cùng đọc `Pending`, sau đó ghi hai trạng thái khác nhau.
3. Giải thích vì sao `Version++` hiện tại không tạo optimistic concurrency control.
4. Đề xuất atomic update filter để chỉ transition được khi document vẫn ở state/version mong đợi.
5. Phân tích điều gì xảy ra nếu request update thành công nhưng audit insert thất bại, hoặc ngược lại trong một retry flow.
6. Giải thích vì sao `actionId` chỉ nằm trong payload event chưa đủ tạo idempotency.
7. Đánh giá `static lock` khi application chạy nhiều instances.
8. Đánh giá khi nào nên dùng single-document modeling, unique index hoặc MongoDB transaction thay vì mặc định thêm distributed transaction.
9. Đề xuất strategy xử lý timeout với unknown outcome mà không tạo duplicate decision/audit.
10. Nêu tests và telemetry cần có để chứng minh state transition đúng khi concurrency cao.

## Câu hỏi gợi mở

1. `ReplaceOneAsync(x => x.Id == request.Id, request)` có kiểm tra document vẫn còn `Pending` hoặc còn `version = 7` tại thời điểm write không?
2. Nếu hai callers cùng đọc version 7 rồi mỗi caller tự tăng local object lên 8, write thứ hai có biết write thứ nhất đã xảy ra không?
3. Một `actionId` được lưu như field bình thường có ngăn collection nhận hai documents có cùng `actionId` không?
4. Nếu request đã update nhưng process chết trước khi insert audit, retry toàn method sẽ gặp trạng thái nào?
5. Nếu state và audit thật sự phải commit cùng nhau, schema hiện tại có bắt buộc phải dùng hai collections không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **read-modify-write không có conditional predicate**. Hãy suy nghĩ theo invariant: chỉ một transition từ `Pending` được phép thắng.

### Gợi ý 2

MongoDB single-document write có atomicity ở document level; tận dụng điều đó trước khi mặc định chuyển sang transaction nhiều documents. Idempotency cũng cần được enforce bằng data constraint hoặc deterministic identity, không chỉ bằng field mang tên `ActionId`.

## Kết quả code review tham khảo

### Critical — Lost update vì replace chỉ filter theo `_id`

**Vấn đề:** Code đọc document, kiểm tra `Pending` ở application memory rồi replace bằng filter chỉ có `Id`.

**Tại sao xảy ra:** Giữa read và replace, document có thể đã được request khác cập nhật. Write thứ hai vẫn match cùng `_id` và ghi đè state mới.

**Ảnh hưởng production:** Reviewer A có thể approve, reviewer B đã đọc stale `Pending` từ trước rồi replace thành reject/approve khác. Audit trail và final state không còn phản ánh một transition duy nhất.

**Cách sửa:** Thực hiện state transition bằng conditional atomic update, ví dụ filter `Id == requestId && Status == Pending` và nếu dùng version thì thêm `Version == expectedVersion`. Kiểm tra `ModifiedCount` để biết caller có thắng transition hay không.

### Critical — `Version++` không phải optimistic concurrency nếu version không nằm trong write predicate

**Vấn đề:** Version chỉ được tăng trong local object rồi replace.

**Tại sao xảy ra:** Optimistic concurrency yêu cầu write chỉ thành công nếu version tại database vẫn bằng version caller đã đọc.

**Ảnh hưởng production:** Hai callers cùng đọc version 7, cùng ghi version 8; write sau silently overwrite write trước.

**Cách sửa:** Filter theo expected version và dùng atomic update `$set` + `$inc`. Nếu update trả `ModifiedCount == 0`, re-read state hoặc trả domain conflict thay vì retry mù.

### Critical — State update và audit insert có thể tách rời

**Vấn đề:** Hai writes nằm ở hai collections và không có atomic boundary chung.

**Tại sao xảy ra:** Application thực hiện request update trước, event insert sau. Process/network failure có thể xảy ra giữa hai bước.

**Ảnh hưởng production:** Có request ở trạng thái `Approved` nhưng không có audit event, hoặc retry có thể tạo event trùng. Với compliance/audit, đây là inconsistency nghiêm trọng.

**Cách sửa:** Trước hết đánh giá lại data model. Nếu audit event chỉ phục vụ lịch sử của một approval và kích thước bounded, có thể embed transition/audit metadata trong cùng request document để dùng single-document atomicity. Nếu audit bắt buộc ở collection riêng và hai writes phải commit cùng nhau, cân nhắc MongoDB transaction với deployment topology hỗ trợ, nhưng chấp nhận chi phí/complexity của transaction.

### Critical — `actionId` không enforce idempotency

**Vấn đề:** Mỗi retry tạo `ObjectId` mới; không có unique constraint trên logical operation.

**Tại sao xảy ra:** Field `ActionId` chỉ mang metadata, không tạo data invariant.

**Ảnh hưởng production:** Cùng client action retry có thể tạo nhiều audit documents.

**Cách sửa:** Dùng deterministic event id theo action hoặc unique compound index phù hợp, ví dụ `(RequestId, ActionId)` nếu scope uniqueness là per request. Duplicate-key outcome có thể được coi là idempotent replay sau khi xác minh event hiện có cùng semantic payload.

### High — Retry toàn method có thể làm state/audit sai hơn

**Vấn đề:** Retry policy không phân biệt concurrency conflict, duplicate key, network timeout có unknown outcome và transient infrastructure error.

**Tại sao xảy ra:** Distributed operation có thể đã commit nhưng response bị mất.

**Ảnh hưởng production:** Retry có thể tạo duplicate audit, đổi error category hoặc tăng contention.

**Cách sửa:** Thiết kế operation idempotent trước rồi mới retry. Với unknown outcome, query theo stable `actionId`/request state để reconcile. Concurrency conflict nên trả business conflict hoặc re-evaluate state, không phải mặc định retry cùng quyết định.

### High — `static lock` không bảo vệ cross-instance

**Vấn đề:** Lock in-memory chỉ tồn tại trong một process.

**Tại sao xảy ra:** Mỗi App Service/container instance có memory riêng.

**Ảnh hưởng production:** Scale-out vẫn cho phép nhiều processes update cùng document.

**Cách sửa:** Đặt concurrency invariant tại datastore bằng conditional update/version predicate. Không thêm distributed lock nếu database atomic update đã đủ.

### High — Read trước write tạo race window không cần thiết

**Vấn đề:** Application load toàn document chỉ để kiểm tra state trước transition.

**Tại sao xảy ra:** State machine được implement thành read-check-write thay vì conditional update.

**Ảnh hưởng production:** Tăng network round trip và race window.

**Cách sửa:** Dùng `FindOneAndUpdate` hoặc `UpdateOne` với filter chứa expected state/version; nếu cần trả document mới thì dùng operation phù hợp để transition và đọc result theo cùng atomic write semantics.

### Medium — Exception semantics không phân biệt domain conflict với infrastructure failure

**Vấn đề:** `InvalidOperationException` được dùng cho not found và already completed.

**Tại sao xảy ra:** Domain outcome chưa được model hóa.

**Ảnh hưởng production:** API/client/retry layer khó quyết định 404, conflict hay retryable 5xx.

**Cách sửa:** Tách `NotFound`, `AlreadyCompleted/Conflict`, duplicate-idempotent replay và transient MongoDB failures thành outcome rõ ràng.

### Medium — Audit log thiếu version/outcome correlation

**Vấn đề:** Log chỉ có request/reviewer.

**Tại sao xảy ra:** Không capture expected/current version, `actionId`, matched/modified count hoặc correlation id.

**Ảnh hưởng production:** Khó dựng lại timeline khi có race hoặc retry.

**Cách sửa:** Structured logging với `RequestId`, `ActionId`, actor, expected version, resulting version, operation outcome, correlation id; không log token hoặc sensitive payload không cần thiết.

### Medium — Schema chưa thể hiện rõ ownership của audit consistency

**Vấn đề:** Audit ở collection riêng nhưng requirement lại gần như yêu cầu audit đồng bộ tuyệt đối với state transition.

**Tại sao xảy ra:** Data model có thể được chọn theo normalized mental model từ relational database thay vì access/invariant model của MongoDB.

**Ảnh hưởng production:** Hệ thống phải gánh transaction/reconciliation complexity không cần thiết.

**Cách sửa:** Xác định lifecycle và kích thước audit history. Nếu history bounded hoặc chỉ cần transition cuối cùng, embed metadata. Nếu audit history lớn/độc lập, giữ collection riêng nhưng dùng transaction hoặc durable reconciliation pattern tùy requirement.

## Phiên bản đề xuất

Một hướng đơn giản nếu audit event vẫn cần collection riêng là: state transition phải atomic bằng conditional update; event identity phải idempotent; nếu business bắt buộc hai writes cùng commit thì đặt chúng trong transaction. Đoạn dưới tập trung vào transition + idempotency. Transaction chỉ nên bật khi requirement thực sự cần atomicity giữa hai collections.

```csharp
public async Task ApproveAsync(
    string requestId,
    string reviewerId,
    string actionId,
    CancellationToken cancellationToken)
{
    if (string.IsNullOrWhiteSpace(actionId))
        throw new ArgumentException("actionId is required", nameof(actionId));

    var now = DateTimeOffset.UtcNow;

    var filter = Builders<ApprovalRequest>.Filter.And(
        Builders<ApprovalRequest>.Filter.Eq(x => x.Id, requestId),
        Builders<ApprovalRequest>.Filter.Eq(
            x => x.Status,
            ApprovalStatus.Pending));

    var update = Builders<ApprovalRequest>.Update
        .Set(x => x.Status, ApprovalStatus.Approved)
        .Set(x => x.ReviewedBy, reviewerId)
        .Set(x => x.ReviewedAt, now)
        .Inc(x => x.Version, 1);

    var result = await _requests.UpdateOneAsync(
        filter,
        update,
        cancellationToken: cancellationToken);

    if (result.ModifiedCount == 0)
    {
        var current = await _requests
            .Find(x => x.Id == requestId)
            .Project(x => new { x.Status, x.ReviewedBy, x.Version })
            .SingleOrDefaultAsync(cancellationToken);

        if (current is null)
            throw new ApprovalNotFoundException(requestId);

        throw new ApprovalConflictException(
            requestId,
            current.Status,
            current.ReviewedBy,
            current.Version);
    }

    var audit = new ApprovalEvent
    {
        Id = $"{requestId}:{actionId}",
        RequestId = requestId,
        ActionId = actionId,
        Action = "Approved",
        ReviewerId = reviewerId,
        CreatedAt = now
    };

    try
    {
        await _events.InsertOneAsync(
            audit,
            cancellationToken: cancellationToken);
    }
    catch (MongoWriteException ex)
        when (ex.WriteError?.Category == ServerErrorCategory.DuplicateKey)
    {
        var existing = await _events
            .Find(x => x.Id == audit.Id)
            .SingleAsync(cancellationToken);

        if (existing.RequestId != requestId ||
            existing.Action != audit.Action ||
            existing.ReviewerId != reviewerId)
        {
            throw;
        }
    }

    _logger.LogInformation(
        "Approval transition committed for {RequestId}, action {ActionId}, reviewer {ReviewerId}",
        requestId,
        actionId,
        reviewerId);
}
```

Đoạn trên vẫn có cửa sổ state-update thành công nhưng event-insert chưa thành công. Nếu requirement audit yêu cầu **không bao giờ** tồn tại state final mà thiếu event, cần một trong các hướng sau:

- embed decision/audit entry vào chính `ApprovalRequest` để update một document atomically;
- dùng MongoDB transaction cho request + event nếu topology hỗ trợ và team chấp nhận operational/performance cost;
- hoặc nếu audit có thể eventual nhưng không được mất, lưu durable outbox-like marker trong cùng document rồi projector riêng ghi sang audit collection.

MongoDB bảo đảm single-document writes atomic; vì vậy effective schema design thường đơn giản hơn việc mặc định dùng multi-document transaction. Unique index hoặc deterministic `_id` nên enforce operation uniqueness ở database thay vì dựa vào pre-check ở application.

## Giải thích thiết kế sau khi sửa

Conditional update biến business invariant `Pending → Approved` thành điều kiện được kiểm tra tại thời điểm write. Hai reviewers có thể cùng gửi request nhưng chỉ operation đầu tiên còn match `Pending`.

`$inc` cập nhật version tại database thay vì copy local stale value. Nếu workflow cần expected-version từ client, có thể thêm `Version == expectedVersion` vào filter để distinguish stale edit rõ hơn.

Deterministic event identity làm retry cùng `actionId` hội tụ về cùng logical event. Một duplicate key không tự động luôn là success; code phải xác minh event cũ đúng semantic operation trước khi coi là idempotent replay.

## Trade-offs

Embed audit history vào request giúp atomicity đơn giản nhưng document có thể lớn dần nếu request có nhiều events. Nếu mỗi request chỉ có vài state transitions thì đây thường là trade-off hợp lý; nếu audit stream rất lớn, separate collection phù hợp hơn.

Transaction nhiều collections cho semantics mạnh hơn nhưng tăng complexity và runtime cost. Không nên dùng chỉ vì code hiện tại tách hai collections; trước tiên cần hỏi liệu data model có thể đặt invariant vào một document hay không.

Conditional update không cung cấp fairness giữa reviewers. Người thắng là operation commit đầu tiên. Nếu business cần priority/work ownership, phải model lease/assignment riêng.

Unique index/deterministic id cần rollout cẩn thận nếu collection đang có duplicates; phải cleanup/validate dữ liệu trước khi thêm constraint.

## Cách kiểm thử

1. **Concurrency integration test:** 100 concurrent approve/reject attempts trên cùng request `Pending`; xác minh chỉ một transition thắng và final version tăng đúng một lần.
2. **Idempotency test:** gửi cùng `actionId` nhiều lần, kể cả sau simulated timeout; xác minh chỉ một logical audit event tồn tại.
3. **Failure-path test:** inject failure giữa state update và audit write; xác minh transaction/outbox/reconciliation strategy theo design đã chọn không làm mất audit invariant.
4. **Multi-instance test:** chạy requests từ nhiều application processes; kết quả vẫn đúng mà không phụ thuộc static lock.
5. **Database constraint test:** thử insert duplicate `(RequestId, ActionId)` hoặc deterministic event `_id`; database phải reject duplicate và application map đúng outcome.

## Quan sát trong production

Theo dõi:

- approval transition attempts/success/conflict theo request;
- duplicate-idempotency hits theo `actionId`;
- state version trước/sau transition;
- số request final state nhưng thiếu audit event nếu dùng separate collections;
- MongoDB command latency/error rate;
- write conflict/transient error rate;
- retry attempts theo operation;
- correlation từ actor → `actionId` → request transition → audit event;
- growth rate của `approvalEvents` và duplicate cleanup signal.

Alert khi conflict rate tăng bất thường, phát hiện final requests thiếu audit, hoặc cùng `actionId` xuất hiện với semantic payload khác nhau.

## Câu hỏi phỏng vấn mở rộng

1. Nếu approval history có hàng nghìn comments/events trên một request, bạn còn embed tất cả vào một document không? Bạn đổi schema dựa trên access pattern nào?
2. Nếu client gửi `expectedVersion`, bạn phân biệt conflict do stale UI với conflict do request đã hoàn tất như thế nào?
3. Khi nào MongoDB transaction hợp lý hơn outbox/reconciliation, và operational cost nào bạn cần đo trước khi chọn?

# Code Review Challenge 2 — SEO redirect middleware tạo redirect loop sau CDN, làm mất query string và sinh canonical URL sai host

**Chủ đề:** ASP.NET Core, HTTP semantics, reverse proxy/CDN, forwarded headers, canonical URLs, redirects, SEO engineering, Host validation, query preservation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một marketing/e-commerce website chạy ASP.NET Core phía sau CDN/reverse proxy. Team muốn chuẩn hóa URL để tránh duplicate content:

- production canonical host là `www.example.com`;
- HTTPS là bắt buộc ở public edge;
- URL path được ưu tiên lowercase cho các content routes;
- query parameters như `?page=2`, `?utm_source=...` không được tự ý làm mất;
- canonical link phải luôn trỏ về host public hợp lệ;
- `POST`, API endpoints và callback endpoints không được bị redirect theo rule SEO dành cho page GET một cách mù quáng.

Sau release, production có các triệu chứng:

- một số request phía sau CDN bị redirect loop giữa HTTP/HTTPS;
- URL `/Products/Camera?page=2` bị redirect thành `/products/camera` và mất `page=2`;
- canonical header đôi lúc chứa hostname do client gửi lên thay vì `www.example.com`;
- health-check endpoint bị redirect và load balancer đánh dấu instance unhealthy;
- OAuth callback có query string nhưng bị canonicalization làm mất parameters;
- một số `POST` tới content endpoint nhận redirect permanent ngoài dự kiến;
- SEO crawler thấy nhiều chains gồm 2–3 redirects trước khi tới final page;
- team đề xuất “cứ redirect mọi request sang lowercase + www + HTTPS” để consistency tuyệt đối.

## Đoạn code cần review

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (context, next) =>
{
    var request = context.Request;

    if (!request.IsHttps)
    {
        var httpsUrl = $"https://{request.Host}{request.Path}";
        context.Response.Redirect(httpsUrl, permanent: true);
        return;
    }

    if (!request.Host.Host.StartsWith("www."))
    {
        var wwwUrl = $"https://www.{request.Host.Host}{request.Path}";
        context.Response.Redirect(wwwUrl, permanent: true);
        return;
    }

    var lowerPath = request.Path.Value?.ToLowerInvariant();
    if (lowerPath != request.Path.Value)
    {
        context.Response.Redirect(lowerPath!, permanent: true);
        return;
    }

    context.Response.OnStarting(() =>
    {
        var canonical =
            $"{request.Scheme}://{request.Host}{request.Path}";

        context.Response.Headers.Append(
            "Link",
            $"<{canonical}>; rel=\"canonical\"");

        return Task.CompletedTask;
    });

    await next();
});

app.MapGet("/health", () => Results.Ok("ok"));
app.MapControllers();
app.Run();
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, HTTP semantics, reverse-proxy awareness, SEO và security trong middleware.
2. Giải thích vì sao `Request.IsHttps` có thể sai phía sau TLS-terminating proxy nếu forwarded headers/trusted proxy configuration chưa được xử lý đúng.
3. Chỉ ra tất cả chỗ query string có thể bị mất.
4. Phân tích rủi ro khi xây canonical URL từ `Request.Host` do client-controlled Host header hoặc proxy configuration sai.
5. Review việc redirect mọi method, gồm `POST`, theo SEO canonicalization rule.
6. Giải thích vì sao redirect từng bước HTTPS → www → lowercase tạo redirect chain và cách giảm thành một redirect final URL.
7. Đánh giá việc lowercase toàn bộ path khi hệ thống có API/callback/static paths có semantics khác content routes.
8. Đề xuất cách exclude health checks, APIs và authentication callbacks khỏi page canonicalization khi phù hợp.
9. Đề xuất test matrix cho CDN/proxy headers, query strings, GET/HEAD/POST và malicious Host values.
10. Nêu telemetry cần có để phát hiện redirect loop, chain length và canonical mismatch trong production.

## Câu hỏi gợi mở

1. Public client dùng HTTPS nhưng CDN gọi origin bằng HTTP thì `Request.IsHttps` tại origin có nhất thiết là `true` không?
2. `$"https://{request.Host}{request.Path}"` giữ `request.QueryString` ở đâu?
3. Nếu client gửi một Host không nằm trong allowed hosts, canonical header hiện tại sẽ chứa gì?
4. Một permanent redirect từ `POST` có semantics giống page-navigation `GET` không?
5. Có cần mọi route trong application tuân theo lowercase/content canonicalization giống nhau không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là middleware đang coi **origin request representation** như public URL truth. Phía sau proxy/CDN, scheme/host cần được xác định từ trusted forwarding configuration và application canonical-host config.

### Gợi ý 2

SEO normalization nên tạo một **final target URL duy nhất** cho page requests và chỉ redirect khi thật sự cần. Query preservation, method semantics và excluded routes phải được design explicit.

## Kết quả code review tham khảo

### Critical — HTTPS redirect có thể loop phía sau TLS-terminating proxy

**Vấn đề:** Middleware dựa trực tiếp vào `Request.IsHttps` nhưng không cho thấy trusted forwarded-header processing trước đó.

**Tại sao xảy ra:** Public request có thể là HTTPS ở CDN nhưng connection CDN → origin là HTTP. Nếu application không nhận/validate forwarded scheme đúng, nó luôn nghĩ request là HTTP và redirect lại HTTPS public URL; proxy lại gọi origin HTTP và vòng lặp tiếp tục.

**Ảnh hưởng production:** Redirect loop, page unavailable, crawler/user fail và health check có thể fail.

**Cách sửa:** Cấu hình reverse proxy/CDN và ASP.NET Core forwarded headers theo trusted proxy/network model trước canonicalization. Không blindly trust arbitrary forwarding headers từ Internet. Application phải có một authoritative understanding về public scheme.

### Critical — Canonical URL dùng `Request.Host` thay vì configured canonical host

**Vấn đề:** Header `Link rel=canonical` được dựng từ request host hiện tại.

**Tại sao xảy ra:** Request metadata bị coi là canonical authority.

**Ảnh hưởng production:** Host-header injection/misconfiguration có thể làm crawler nhận canonical URL sai domain, phá SEO hoặc tạo security-related downstream issues nếu URL được reuse ở nơi khác.

**Cách sửa:** Canonical host production nên đến từ trusted application configuration, ví dụ `www.example.com`; đồng thời bật host filtering/allowed hosts phù hợp. Chỉ dùng forwarded host nếu proxy trust boundary được cấu hình rõ và vẫn validate expected hosts.

### High — Query string bị mất trên mọi redirect path

**Vấn đề:** HTTPS, www và lowercase targets chỉ nối `Request.Path`.

**Tại sao xảy ra:** `Request.QueryString` không được append vào target.

**Ảnh hưởng production:** Pagination/filter/campaign params/callback state có thể biến mất; URL khác business meaning hoặc authentication flow hỏng.

**Cách sửa:** Preserve query string theo route contract. Với tracking params, nếu product muốn bỏ khỏi canonical tag nhưng vẫn giữ trong navigation URL, đó là decision riêng; không được vô tình drop trong redirect.

### High — Redirect mọi HTTP method bằng rule dành cho page SEO

**Vấn đề:** Middleware chạy trước routing và không giới hạn GET/HEAD/content pages.

**Tại sao xảy ra:** URL normalization được áp dụng global mà không xét method/endpoint semantics.

**Ảnh hưởng production:** POST/API/callback behavior có thể thay đổi, request body/method handling phụ thuộc redirect status/client và có nguy cơ làm transaction flow lỗi.

**Cách sửa:** Chỉ canonicalize page-navigation GET/HEAD khi phù hợp. API/auth callback/webhook nên có policy riêng. Nếu cần redirect preserving method, chọn status code theo HTTP contract; không dùng một helper `permanent: true` mù quáng cho mọi request.

### High — Tạo redirect chain thay vì tính final URL một lần

**Vấn đề:** Request có cả sai scheme, host và casing sẽ bị redirect từng bước.

**Tại sao xảy ra:** Mỗi normalization rule return ngay sau khi sửa một thuộc tính.

**Ảnh hưởng production:** Tăng latency, thêm edge/origin traffic, crawler phải theo chain dài hơn, debugging phức tạp.

**Cách sửa:** Xác định final public URL từ canonical scheme + host + normalized path + query rồi thực hiện tối đa một redirect nếu current public URL khác target.

### High — Lowercase toàn bộ path có thể phá route ngoài content scope

**Vấn đề:** `ToLowerInvariant` được áp dụng global.

**Tại sao xảy ra:** Team giả định mọi path đều case-insensitive và đều có SEO semantics giống content pages.

**Ảnh hưởng production:** Callback path, signed URLs, legacy routes, static-resource keys hoặc downstream route semantics có thể thay đổi ngoài dự kiến.

**Cách sửa:** Scope normalization vào content routes đã được xác định. Nếu application routing contract thực sự case-insensitive, vẫn cần kiểm tra external integrations và generated URLs trước rollout.

### High — Health endpoint bị canonicalization tác động

**Vấn đề:** `/health` đi qua middleware trước endpoint mapping và có thể bị redirect do scheme/host/case.

**Tại sao xảy ra:** Infrastructure endpoint không được exclude.

**Ảnh hưởng production:** Load balancer/orchestrator có thể coi redirect là unhealthy tùy health-check contract.

**Cách sửa:** Map/exclude health endpoint hoặc cấu hình probe dùng URL/origin semantics đúng. Health checks nên trả trực tiếp expected status thay vì phụ thuộc SEO redirect path.

### Medium — Canonical header có thể không phản ánh final public URL

**Vấn đề:** `request.Scheme`, `request.Host` và path tại origin không nhất thiết là canonical public representation.

**Tại sao xảy ra:** Proxy rewriting và canonical-host policy chưa được tách khỏi incoming request object.

**Ảnh hưởng production:** Crawler nhận canonical inconsistent giữa pages/instances/environments.

**Cách sửa:** Centralize `CanonicalUrlBuilder` dựa trên explicit config + route-aware normalization. Test output ở production-like proxy environment.

### Medium — Permanent redirect rollout có rollback cost cao

**Vấn đề:** Code dùng permanent redirect ngay từ đầu.

**Tại sao xảy ra:** Canonicalization chưa được canary/observe trước khi cacheable behavior được phát rộng.

**Ảnh hưởng production:** Browser/CDN/crawler có thể cache redirect, làm rollback khó xác minh.

**Cách sửa:** Trong rollout, cân nhắc temporary redirect/canary trước, sau khi rule ổn định mới chuyển sang permanent status phù hợp. Exact status choice phụ thuộc method/SEO contract.

### Medium — Không có redirect-loop/normalization telemetry

**Vấn đề:** Middleware không log source/target/reason hoặc counter.

**Tại sao xảy ra:** Redirect được xem là simple plumbing.

**Ảnh hưởng production:** Team chỉ biết loop qua user reports/crawler errors.

**Cách sửa:** Structured metric/log cho redirect reason, source route category, target host/scheme, response status, repeated redirects/correlation id; tránh log sensitive query values nếu query chứa secrets/tokens.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa route-aware canonicalization. Forwarded-header trust configuration phải được thiết lập đúng cho infrastructure thực tế; không nên copy danh sách proxy/network từ ví dụ vào production mà không biết topology.

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    // Production phải cấu hình KnownProxies/KnownNetworks
    // theo CDN/reverse-proxy topology thực tế.
});

var app = builder.Build();

app.UseForwardedHeaders();

app.MapGet("/health", () => Results.Ok("ok"));

app.Use(async (context, next) =>
{
    var request = context.Request;

    var isPageMethod =
        HttpMethods.IsGet(request.Method) ||
        HttpMethods.IsHead(request.Method);

    var excluded =
        request.Path.StartsWithSegments("/api") ||
        request.Path.StartsWithSegments("/signin") ||
        request.Path.StartsWithSegments("/oauth") ||
        request.Path.StartsWithSegments("/health");

    if (!isPageMethod || excluded)
    {
        await next();
        return;
    }

    const string canonicalHost = "www.example.com";
    const string canonicalScheme = "https";

    var originalPath = request.Path.Value ?? "/";
    var canonicalPath = IsContentPath(request.Path)
        ? originalPath.ToLowerInvariant()
        : originalPath;

    var target = $"{canonicalScheme}://{canonicalHost}{canonicalPath}{request.QueryString}";

    var currentPublicUrl =
        $"{request.Scheme}://{request.Host}{request.Path}{request.QueryString}";

    if (!string.Equals(
            currentPublicUrl,
            target,
            StringComparison.Ordinal))
    {
        context.Response.StatusCode = StatusCodes.Status308PermanentRedirect;
        context.Response.Headers.Location = target;
        return;
    }

    context.Response.OnStarting(() =>
    {
        var canonicalForIndexing =
            BuildCanonicalForIndexing(
                canonicalScheme,
                canonicalHost,
                canonicalPath,
                request.Query);

        context.Response.Headers.Append(
            "Link",
            $"<{canonicalForIndexing}>; rel=\"canonical\"");

        return Task.CompletedTask;
    });

    await next();
});

app.MapControllers();
app.Run();
```

`Status308PermanentRedirect` ở đây chỉ minh họa semantics preserve method; tuy nhiên middleware đã scope vào GET/HEAD page requests nên lựa chọn final status nên được xác nhận theo SEO/product policy và rollout strategy. Trong giai đoạn canary, temporary redirect có thể an toàn hơn để rollback.

`BuildCanonicalForIndexing` không nhất thiết giữ toàn bộ query parameters. Ví dụ tracking parameters có thể bị bỏ khỏi **canonical tag** nhưng vẫn phải giữ trong navigation/redirect nếu business cần. Pagination query như `page=2` có thể là distinct indexable URL hoặc không tùy SEO requirement; phải chốt policy với product/SEO thay vì hard-code giả định.

`UseForwardedHeaders` chỉ an toàn khi trusted proxies/networks được cấu hình đúng với topology. Không nên bật trust rộng mọi forwarded header từ Internet.

## Giải thích thiết kế sau khi sửa

Canonicalization chỉ áp dụng cho page GET/HEAD. API, auth callback và health endpoint không bị kéo vào rule SEO.

Middleware xây final URL một lần nên request sai nhiều dimensions chỉ nhận một redirect. Scheme và host canonical đến từ application policy, không từ untrusted incoming Host.

Query string được preserve khi redirect. Canonical tag có thể có policy query riêng, bởi navigation correctness và search-engine canonicalization là hai concern khác nhau.

Forwarded headers được xử lý trước redirect để application hiểu public scheme từ trusted proxy chain. Đây là infrastructure/security configuration, không chỉ một SEO detail.

## Trade-offs

Hard-code một canonical host đơn giản nhưng multi-region/multi-brand/multi-domain website cần configuration theo site/tenant. Khi đó builder phải lấy canonical domain từ trusted content/site configuration, vẫn không nên lấy trực tiếp từ arbitrary Host.

Lowercase URL giúp consistency nhưng migration có thể ảnh hưởng backlinks, signed URLs hoặc legacy integrations. Nên inventory routes trước và rollout theo scope thay vì normalize toàn application trong một lần.

Permanent redirects có lợi cho canonicalization ổn định nhưng cache lâu hơn, làm rollback khó. Canary với temporary redirects rồi nâng cấp status sau khi metrics ổn định là cách giảm risk.

Forwarded-header trust config sai có thể tạo security issue hoặc redirect loop. Config phải đi cùng infrastructure-as-code/test environment giống production.

## Cách kiểm thử

1. **Proxy integration test:** public HTTPS request qua simulated trusted proxy tới HTTP origin; endpoint page phải không loop và chỉ tạo tối đa một canonical redirect.
2. **Query-preservation test:** `/Products/Camera?page=2&utm_source=test` redirect tới final URL mà không mất query; canonical tag tuân theo query-indexing policy đã chốt.
3. **Route/method matrix:** GET/HEAD content được normalize; POST/API/OAuth callback/health không bị SEO middleware redirect sai.
4. **Host-security test:** gửi unexpected/malicious Host và spoofed forwarded headers từ untrusted source; application không sinh canonical URL attacker-controlled.
5. **E2E crawler test:** crawl representative URLs và assert final status, redirect chain length, canonical header/tag, no loops, no duplicate mixed-case URLs.

## Quan sát trong production

Theo dõi:

- redirect count theo reason: scheme/host/path;
- redirect chain length từ synthetic monitoring;
- 3xx rate theo endpoint category;
- repeated redirects với cùng correlation/client;
- health-check response distribution;
- canonical host mismatch counter;
- incoming Host và forwarded-host validation failures nhưng không log sensitive query/token;
- crawler 3xx/4xx trends;
- latency edge → origin khi redirect rate tăng;
- CDN cache status cho redirect responses nếu CDN cache 3xx.

Alert khi một URL sinh nhiều redirects liên tiếp, health endpoint trả 3xx, canonical mismatch xuất hiện hoặc 3xx rate tăng mạnh sau deployment.

2. Khi nào bạn chọn `301`, `302`, `307` hoặc `308`, và method preservation/SEO/rollback ảnh hưởng quyết định ra sao?
3. Nếu Akamai/CDN cache permanent redirects rất lâu, deployment và rollback strategy cho URL normalization cần thêm safeguards nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Read-check-write trong MongoDB vẫn có thể mất update nếu write predicate không chứa expected state/version; single-document atomic update nên được tận dụng để enforce invariant tại database.
- `Version` chỉ có ý nghĩa optimistic concurrency khi expected version tham gia điều kiện write hoặc conflict detection.
- Idempotency cần stable operation identity + database-enforced uniqueness; field metadata không tự tạo constraint.
- Multi-document transaction là một lựa chọn, không phải mặc định. Schema có thể được thiết kế để invariant nằm trong một document và tận dụng atomicity đơn giản hơn.
- Ở phía sau CDN/reverse proxy, origin scheme/host không nhất thiết là public URL; canonicalization phải dựa trên trusted forwarding configuration và explicit canonical-host policy.
- SEO redirects là HTTP behavior thật: phải preserve query, tôn trọng method/route semantics, tránh chains và quan sát rollout như một production change.

## Mẫu tư duy cần nhớ

- **Đưa concurrency invariant vào write predicate, không chỉ kiểm tra trước ở application.**
- **Idempotency phải được enforce bằng identity/constraint, không bằng naming convention.**
- **Ưu tiên single-document atomicity/schema design trước khi thêm distributed transaction.**
- **Phân biệt incoming origin URL với authoritative public canonical URL.**
- **Tính final redirect một lần, preserve semantics và đo 3xx behavior sau rollout.**
