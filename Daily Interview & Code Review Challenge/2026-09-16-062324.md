# Câu 1 — EF Core `IQueryable`: vì sao một refactor nhỏ biến query nhanh thành tải dữ liệu khổng lồ?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ translation, IQueryable, deferred execution, SQL, memory, API performance

## Bối cảnh

Một ASP.NET Core API trả danh sách orders có filter theo customer, status và khoảng ngày. Trước đây repository trả `IQueryable<Order>` và service tiếp tục áp dụng `Where`, `Select`, `OrderBy`, `Take` trước `ToListAsync`. Sau một refactor, developer đổi repository thành method trả `Task<List<Order>>` vì muốn “encapsulate data access”. API vẫn trả đúng dữ liệu trong test nhỏ, nhưng production p95 tăng mạnh và memory tăng khi customer có hàng trăm nghìn orders.

Database là SQL Server. Endpoint chỉ cần 20 rows và 6 fields để render table. Chưa có execution plan hoặc query-count evidence. Team đang đề xuất thêm Redis ngay lập tức.

## Câu hỏi chính

Hãy giải thích cơ chế LINQ/EF Core nào có thể khiến refactor này chuyển work từ database sang application, cách bạn chứng minh điều đó, và bạn sẽ sửa data-access boundary thế nào mà không biến `IQueryable` thành một abstraction bị leak tùy tiện khắp hệ thống?

## Câu hỏi làm rõ nên cân nhắc

1. Repository mới gọi `ToListAsync` ở đâu so với filter/projection/pagination?
2. SQL thực tế trước và sau refactor khác nhau thế nào?
3. Endpoint dùng offset pagination hay chỉ cần first page/top N?
4. Change tracking có cần cho read path này không?
5. Data-access boundary hiện có yêu cầu reusable specification/query object hay chỉ một use case cụ thể?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt expression tree của `IQueryable` với LINQ-to-Objects sau khi query đã materialize.

### Gợi ý 2

`ToListAsync` là một execution boundary quan trọng: những operator đặt trước/sau boundary có thể chạy ở nơi khác nhau.

### Gợi ý 3

Không cần kết luận “repository xấu” hoặc “phải expose IQueryable”; hãy thiết kế query theo use case và kiểm soát execution boundary.

## Cấu trúc trả lời đề xuất

1. Làm rõ query shape trước/sau refactor.
2. Giải thích deferred execution và materialization.
3. Capture generated SQL và database telemetry.
4. Đo rows/bytes/allocation/query duration.
5. Đưa filtering/projection/pagination về trước materialization.
6. Chọn boundary: query service/specification/use-case method phù hợp.
7. Test SQL/query shape và large dataset.
8. Monitor p95/p99, rows returned và DB/application resource usage.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` có thể tích lũy expression để EF Core translate sang SQL; `List<T>` đã materialize và các LINQ operator sau đó chạy in-memory.
- Materialize quá sớm có thể kéo rất nhiều rows/columns qua network rồi filter trong process.
- Cần xem generated SQL/telemetry trước khi tối ưu.
- Projection và pagination nên diễn ra ở database khi semantics cho phép.

### Điểm cộng

- Dùng `AsNoTracking` cho read-only query khi phù hợp.
- Không expose unrestricted `IQueryable` qua mọi architectural boundary; có thể dùng use-case-specific query method/specification/query object.
- Đề cập indexes/execution plan chỉ sau khi xác nhận SQL shape.

### Senior+

- Phân biệt cost của DB scan, network transfer, materialization, tracking và serialization.
- Cân nhắc keyset pagination nếu deep paging thực sự là requirement.
- Không thêm Redis trước khi chứng minh workload có cacheable reuse và consistency contract phù hợp.

## Hướng giải quyết tham khảo

Điểm cần xác minh đầu tiên là vị trí materialization. Khi EF Core còn giữ `IQueryable`, các operator được biểu diễn thành expression tree và provider cố gắng translate phần hỗ trợ sang SQL. Khi repository gọi `ToListAsync`, query đã chạy; filter/projection sau đó là LINQ-to-Objects. Nếu repository tải toàn bộ orders của customer rồi service mới `Where/Select/Take`, application trả đúng 20 rows cuối cùng nhưng đã trả giá cho hàng trăm nghìn rows trước đó.

Tôi sẽ capture generated SQL bằng logging/diagnostics phù hợp, xem số rows database trả, duration, execution plan và Application Insights dependency telemetry. Đồng thời đo allocation/memory và response serialization để tránh quy mọi latency cho SQL.

Fix không nhất thiết là expose `IQueryable` từ infrastructure ra toàn solution. Với use case này có thể tạo query method nhận filter/paging contract và trả DTO projection trực tiếp: filter → order → select 6 fields → take/page → `ToListAsync`. Nếu nhiều use cases cần composability, specification/query object là một lựa chọn, nhưng chỉ đáng dùng khi complexity thực tế cần nó.

Read-only query có thể dùng `AsNoTracking`. Index phải dựa trên predicate/order và execution plan, không phải reflex “thêm index”. Redis chỉ hợp lý nếu measurement cho thấy repeated reads đủ lớn, freshness/invalidation rõ ràng và database/query optimization chưa đáp ứng SLO.

Testing nên seed dataset lớn, xác minh kết quả và số rows/query shape, đồng thời có performance regression test ở mức integration phù hợp. Monitoring theo dõi DB dependency duration, rows/result size, application allocations và endpoint p95/p99.

## Mẫu trả lời trong phỏng vấn

“Điểm tôi kiểm tra đầu tiên là `ToListAsync` đã bị đẩy lên sớm hay chưa. Khi còn `IQueryable`, EF Core có thể compose expression và translate filter/projection/pagination xuống SQL. Sau materialization thành `List`, các LINQ operator còn lại chạy trong memory. Vì vậy endpoint có thể chỉ trả 20 items nhưng đã tải hàng trăm nghìn rows. Tôi sẽ chứng minh bằng generated SQL, rows returned, execution plan và telemetry thay vì đoán. Tôi sửa bằng query theo use case để filter, project và page trước `ToListAsync`, dùng `AsNoTracking` nếu read-only. Tôi không nhất thiết expose `IQueryable` khắp architecture; có thể dùng query service hoặc specification nếu cần composability. Redis chưa phải bước đầu vì chưa có evidence rằng cache là bottleneck đúng.”

## Câu hỏi đào sâu

1. Nếu team cấm repository trả `IQueryable`, bạn vẫn giữ composability mà không duplicate hàng chục query methods thế nào?
2. Nếu SQL đã chỉ trả 20 rows nhưng endpoint vẫn chậm, bạn điều tra tiếp những layer nào?
3. Bạn có đồng ý thêm generic repository để “ẩn hoàn toàn EF Core” không? Khi nào điều đó có lợi hoặc gây hại?

## Lỗi trả lời thường gặp

- Nói mọi LINQ đều chạy trong database.
- Chỉ đề xuất `AsNoTracking` dù root cause là materialization sớm.
- Thêm Redis trước khi xem SQL/query volume.
- Expose `IQueryable` không giới hạn qua API/domain boundary mà không cân nhắc coupling.
- Khẳng định cần index mà chưa xem predicate/order/execution plan.

## Thang điểm 0–10

- **0–2:** Không phân biệt `IQueryable` và materialized collection.
- **3–4:** Nhận ra `ToListAsync` sớm nhưng chưa có cách chứng minh/thiết kế lại.
- **5–6:** Giải thích đúng translation boundary và đưa filtering/projection về SQL.
- **7–8:** Có telemetry, architecture boundary, tests và trade-offs.
- **9–10:** Phân tích đầy đủ DB/network/materialization/tracking/cache và chọn abstraction theo use case.

# Câu 2 — Azure App Service trả 5xx sau deployment slot swap nhưng chỉ ở một phần traffic

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure App Service, deployment slots, configuration, health checks, Managed Identity, SQL, observability, incident response

## Bối cảnh

Một ASP.NET Core application chạy Azure App Service với nhiều instances. Team deploy vào staging slot, smoke test thành công rồi swap sang production. Khoảng 5 phút sau swap, error rate tăng lên 12%; một số requests vẫn thành công. Application Insights cho thấy cả HTTP 500 và dependency failures. Release có thay đổi application code, một database migration backward-compatible theo thiết kế, và một configuration key mới dùng cho external product API.

Rollback code có thể thực hiện nhanh, nhưng database migration đã chạy. Business đang có traffic cao. Chưa rõ lỗi chỉ xảy ra trên instance cụ thể, route cụ thể hay dependency cụ thể.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào để giảm impact, thu thập evidence và phân biệt giữa configuration/slot behavior, instance health, database compatibility và external dependency regression trước khi quyết định rollback hay forward-fix?

## Câu hỏi làm rõ nên cân nhắc

1. Error distribution theo instance, operation, deployment/role version và dependency là gì?
2. Configuration key mới là slot setting hay setting được swap, và secret/identity được resolve bằng cách nào?
3. Health check hiện kiểm tra process sống hay readiness của critical dependencies?
4. Migration cụ thể có thật sự backward-compatible với version trước không?
5. Có feature flag hoặc traffic-routing mechanism để disable code path mới không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng root-cause guess; trước hết xác định blast radius và stabilization option ít rủi ro nhất.

### Gợi ý 2

Partial failure thường cho manh mối: instance, route, config, warm-up, dependency hoặc version skew.

### Gợi ý 3

Rollback chỉ an toàn nếu application version cũ vẫn tương thích database/schema/config sau migration.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và blast radius.
2. Stabilize bằng route/feature/rollback option an toàn nhất.
3. Correlate telemetry theo instance/version/operation/dependency.
4. So sánh production/staging effective configuration và identity.
5. Kiểm tra migration compatibility và DB health.
6. Form competing hypotheses và falsify từng hypothesis.
7. Chọn rollback hoặc forward-fix có explicit risk.
8. Verify recovery bằng metrics/traces/synthetic tests.
9. Thêm release guardrails và monitoring phòng tái diễn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu bằng impact/stabilization, không nhảy thẳng vào một root cause.
- Phân đoạn telemetry theo instance/operation/dependency/deployment version.
- Xác minh effective slot settings/configuration/identity thay vì giả định staging smoke test đại diện production.
- Xác minh schema backward compatibility trước rollback.
- Verify recovery sau mitigation.

### Điểm cộng

- Dùng feature flag/traffic reduction nếu chỉ code path mới lỗi.
- Kiểm tra health/readiness semantics và instance recycle/warm-up.
- Correlation giữa request telemetry và dependency telemetry.
- So sánh Key Vault/Managed Identity permissions hoặc external API credentials nếu config mới liên quan.

### Senior+

- Tách deployment artifact consistency khỏi environment configuration drift.
- Đề xuất pre-swap validation dựa trên production-like identity/config mà không lộ secrets.
- Thiết kế expand/contract migration để rollback application an toàn.
- Định nghĩa SLO/error-budget based release gate và automated rollback signal có guardrails.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng dashboard error rate, affected endpoints/users và xem lỗi có concentrated theo `cloud_RoleInstance`, operation hoặc dependency hay không. Nếu một instance lỗi rõ rệt, có thể remove/restart instance theo operational capability để giảm blast radius trong khi giữ evidence cần thiết. Nếu chỉ feature mới lỗi và có flag, disable feature thường ít rủi ro hơn full rollback.

Tiếp theo correlate traces của 500 với dependency failures. Nếu external product API failures tập trung, tôi kiểm tra effective configuration sau slot swap, slot-setting semantics, secret reference và Managed Identity/permission. Staging smoke test chỉ chứng minh staging context; nó không tự chứng minh production slot có cùng effective dependencies/identity.

Song song, xem database waits/errors, migration history và compatibility contract. Nếu migration theo expand/contract và old app vẫn chạy được, rollback code có thể an toàn. Nếu migration đã remove/rename contract mà old app cần, rollback có thể làm incident nặng hơn và forward-fix là lựa chọn hợp lý hơn.

Tôi không chọn một hypothesis chỉ vì timing trùng deployment. Các hypothesis gồm config drift, instance-specific startup/warm-up, external API auth, DB migration/performance, code regression. Mỗi hypothesis phải có evidence để xác minh/phủ định.

Sau mitigation, verify error rate, p95/p99, dependency success, instance health và synthetic business flow. Prevention gồm slot-aware config validation, startup/readiness checks, backward-compatible migrations, canary/gradual exposure nếu phù hợp, deployment annotations trong telemetry và release gate dựa trên error/dependency metrics.

## Mẫu trả lời trong phỏng vấn

“Vì chỉ khoảng 12% traffic lỗi, tôi sẽ phân đoạn ngay theo instance, operation và dependency để xác định blast radius. Mục tiêu đầu tiên là stabilize: nếu lỗi nằm ở một feature hoặc instance, tôi giảm traffic/disable feature trước khi full rollback. Sau đó tôi correlate 500 với dependency telemetry và so effective production config sau swap, đặc biệt setting mới, Key Vault/Managed Identity và slot-specific behavior. Đồng thời tôi kiểm tra migration có thật sự backward-compatible không, vì rollback code sau schema change không mặc định an toàn. Tôi giữ nhiều hypothesis song song: config drift, instance warm-up, external auth, DB regression, code bug. Sau mitigation tôi verify bằng error rate, p95/p99, dependency success và synthetic flow. Về lâu dài tôi dùng expand/contract migration, config validation, deployment markers và health/release gates để giảm khả năng lặp lại.”

## Câu hỏi đào sâu

1. Nếu chỉ một instance lỗi nhưng restart làm mất evidence, bạn cân bằng stabilization và forensics thế nào?
2. Nếu Product yêu cầu auto-rollback khi error rate >5%, bạn sẽ thêm guardrails nào để tránh rollback vào schema không tương thích?
3. Nếu staging và production dùng cùng artifact nhưng khác Managed Identity, smoke test strategy nên thay đổi ra sao?

## Lỗi trả lời thường gặp

- Rollback ngay mà không kiểm tra schema compatibility.
- Giả định slot swap đồng nghĩa mọi config/identity giống nhau.
- Chỉ xem aggregate error rate, không phân đoạn theo instance/dependency.
- Restart tất cả trước khi thu đủ evidence.
- Chỉ sửa incident mà không thêm release telemetry/guardrails.

## Thang điểm 0–10

- **0–2:** Đoán nguyên nhân và đề xuất restart/rollback không evidence.
- **3–4:** Biết xem logs nhưng chưa có incident sequence rõ.
- **5–6:** Có stabilization, telemetry correlation và config/DB checks.
- **7–8:** Quản lý rollback risk, multiple hypotheses, verification và prevention.
- **9–10:** Cân bằng blast radius, forensics, slot/identity/schema semantics và release engineering có guardrails.

# Câu 3 — Thiết kế search cho product catalog: SQL hay Elasticsearch, và source of truth nằm ở đâu?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL, e-commerce, search architecture, eventual consistency, APIs, observability, failure recovery

## Bối cảnh

Một e-commerce platform có khoảng vài triệu products. Product master data hiện nằm trong SQL Server. Business muốn search theo free text, category, brand, price range và autocomplete; tương lai có thể thêm relevance tuning. Product updates diễn ra liên tục từ back-office và third-party feed. Checkout không được dùng stale price/availability quá mức cho phép, nhưng search results có thể eventual consistent trong một khoảng ngắn.

Team chia thành hai ý kiến: một bên muốn giữ toàn bộ search bằng SQL để giảm complexity; bên kia muốn đưa Elasticsearch thành primary product database để tránh “duplicate data”. Chưa có SLO cụ thể cho search freshness, latency hoặc update throughput.

## Câu hỏi chính

Bạn sẽ làm rõ requirement và thiết kế search/data ownership thế nào? Hãy so sánh SQL-only, SQL + Elasticsearch projection/index, và Elasticsearch-as-primary; giải thích synchronization, consistency, failure behavior, reindexing, security, observability và điều kiện khiến bạn thay đổi lựa chọn.

## Câu hỏi làm rõ nên cân nhắc

1. Search latency/availability/freshness SLO thực tế là gì?
2. Những field nào quyết định checkout correctness và có cần revalidate với source of truth không?
3. Update rate/batch size và yêu cầu propagation từ product update đến search là bao nhiêu?
4. Search cần stemming, typo tolerance, language analyzers, relevance tuning hay chỉ filter/prefix đơn giản?
5. Khi search subsystem down, business muốn fail closed, degrade sang browse/basic SQL hay hiển thị cached results?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn Elasticsearch chỉ vì “search thì dùng Elasticsearch”; bắt đầu từ query capability và SLO.

### Gợi ý 2

Search index thường là một read model/projection; duplicate representation không đồng nghĩa duplicate ownership.

### Gợi ý 3

Nếu có hai stores, hãy thiết kế synchronization, replay/rebuild và stale-data boundary ngay từ đầu.

## Cấu trúc trả lời đề xuất

1. Clarify search features, scale và SLO.
2. Xác định source of truth và correctness boundary.
3. So sánh SQL-only với dedicated search index.
4. Thiết kế change propagation và idempotency.
5. Thiết kế reindex/backfill/versioned index.
6. Xử lý search outage và stale data.
7. Revalidate transactional fields tại checkout.
8. Security/filtering và multi-tenant concerns nếu có.
9. Observability cho freshness, indexing và query latency.
10. Nêu trigger để tăng/giảm complexity.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Requirement quyết định technology, không phải ngược lại.
- SQL có thể đủ cho filter/search đơn giản; Elasticsearch có lợi khi full-text/relevance/analyzer/query workload thực sự cần.
- Nếu SQL là system of record, Elasticsearch có thể là derived read model/index.
- Search result không nên là authority cuối cùng cho price/availability nếu transactional correctness yêu cầu dữ liệu mới hơn.
- Cần thiết kế sync/rebuild/failure path.

### Điểm cộng

- Outbox/change feed/event-based propagation với idempotent indexer.
- Versioned indices + alias swap cho reindex.
- Freshness lag metric và DLQ/retry cho indexing failures.
- Degraded mode khi Elasticsearch unavailable.

### Senior+

- Phân biệt write ownership, read representation và transactional invariant.
- Tránh distributed transaction giữa SQL và search index; chấp nhận eventual consistency có đo lường.
- Thiết kế authorization/filter dimensions vào index/query nếu search visibility phụ thuộc tenant/market.
- Đánh giá operational cost của cluster, mapping evolution, analyzer changes và reindex.

## Hướng giải quyết tham khảo

Tôi chưa chọn Elasticsearch trước khi có search SLO và feature set. Nếu requirement chỉ là exact filters, category, price range và prefix nhỏ ở vài triệu rows với traffic vừa phải, SQL với schema/index phù hợp có thể đủ và operationally đơn giản hơn. Nếu cần full-text quality, analyzers, relevance tuning, autocomplete phức tạp và search traffic lớn, dedicated search engine trở nên hợp lý.

Trong phương án phổ biến SQL + Elasticsearch, SQL vẫn là source of truth cho product master/transactional fields. Elasticsearch là denormalized read model tối ưu cho search. “Duplicate data” ở đây là duplicate representation, không phải hai hệ thống cùng sở hữu write authority.

Tôi propagate changes bằng durable mechanism như outbox/event/change feed phù hợp hệ thống. Indexer phải idempotent và retry được. Không cố transaction atomically giữa SQL và Elasticsearch; thay vào đó định nghĩa freshness SLO, đo indexing lag và có replay/reconciliation. Reindex nên dùng versioned index, backfill, validation rồi alias cutover để giảm downtime.

Search có thể trả product ID, display fields và indicative price; trước checkout/order commit, service authoritative phải revalidate price/availability theo business contract. Khi Elasticsearch down, degraded behavior phụ thuộc business: browse/basic fallback, cached popular results hoặc explicit unavailable search. Fallback SQL chỉ nên có nếu nó chịu được load và query semantics, tránh biến outage search thành outage database.

Elasticsearch-as-primary chỉ đáng cân nhắc nếu domain ownership/transaction requirements thực sự phù hợp; với product master có relational constraints/workflows và transactional correctness, tôi cần lý do mạnh để bỏ SQL authority. Operational complexity gồm mappings, analyzers, shard sizing, reindexing, cluster failures và security.

Telemetry gồm query p50/p95/p99, zero-result rate, error rate, indexing throughput, oldest event/indexing lag, retry/DLQ, document count/version mismatch và reconciliation failures. Recommendation thay đổi nếu search feature/SLO/traffic hoặc source-system constraints thay đổi.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng câu ‘phải dùng Elasticsearch’. Tôi hỏi search cần full-text/relevance/analyzers đến đâu, latency và freshness SLO là gì. Nếu SQL đáp ứng query đơn giản với index phù hợp, giữ một store có thể tốt hơn. Nếu search capability đủ phức tạp, tôi giữ SQL làm source of truth và xem Elasticsearch như read model. Product changes được propagate bằng durable, retryable, idempotent pipeline; tôi chấp nhận eventual consistency có đo indexing lag thay vì distributed transaction. Reindex dùng versioned index và cutover có kiểm chứng. Search result không phải authority cuối cho price/availability; checkout phải revalidate. Khi Elasticsearch down, degraded mode phải được thiết kế để không dồn query nguy hiểm sang SQL. Tôi chỉ chọn Elasticsearch-as-primary nếu ownership và transactional requirements thực sự phù hợp, không chỉ để tránh duplicate representation.”

## Câu hỏi đào sâu

1. Nếu business yêu cầu product update xuất hiện trong search dưới 2 giây, architecture và monitoring của bạn thay đổi thế nào?
2. Nếu SQL fallback làm database CPU tăng gấp ba khi Elasticsearch down, bạn có giữ fallback không?
3. Team đề xuất dual-write trực tiếp SQL + Elasticsearch trong request để giảm lag; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- “Search thì dùng Elasticsearch” mà không hỏi requirement.
- Biến Elasticsearch thành source of truth chỉ để tránh duplicate data.
- Dual-write synchronous rồi coi hai writes là atomic.
- Không có reindex/replay/reconciliation strategy.
- Dùng stale search price làm authority tại checkout.

## Thang điểm 0–10

- **0–2:** Chọn công nghệ theo tên gọi, không có consistency/failure reasoning.
- **3–4:** Biết Elasticsearch mạnh về full-text nhưng chưa thiết kế ownership/sync.
- **5–6:** Có source of truth, read model, eventual consistency và revalidation.
- **7–8:** Có durable propagation, reindex, degraded mode, telemetry và trade-offs.
- **9–10:** Điều chỉnh architecture theo SLO, operational cost, correctness boundary và failure isolation.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Ba bài hôm nay cùng kiểm tra khả năng nhận diện **execution/ownership boundary**. Với EF Core, boundary là lúc query materialize và work chuyển từ database provider sang application. Với deployment, boundary nằm giữa artifact, environment configuration, instance health và schema compatibility. Với search, boundary quan trọng nhất là write ownership/source of truth so với derived read model.

## Mẫu tư duy cần nhớ

- Xác định execution boundary trước khi tối ưu.
- Stabilize và phân đoạn evidence trước khi đoán root cause.
- Rollback chỉ an toàn khi dependency/schema contract còn tương thích.
- Phân biệt source of truth với read projection.
- Chấp nhận eventual consistency chỉ khi có freshness SLO, telemetry và recovery path.
