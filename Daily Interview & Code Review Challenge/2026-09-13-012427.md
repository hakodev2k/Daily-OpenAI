# Code Review Challenge 1 — Service Bus consumer gửi email hai lần và ghi trạng thái không nhất quán sau retry

**Chủ đề:** C#/.NET 8, Azure Service Bus, idempotency, PeekLock, message settlement, EF Core transaction boundary, external side effects, retry, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống approval chạy trên .NET 8 có worker nhận message `ApprovalCompleted` từ Azure Service Bus queue. Mỗi message yêu cầu:

- cập nhật trạng thái approval trong SQL Server;
- gửi email thông báo cho nhân viên;
- ghi audit log;
- chỉ xử lý business event một lần về mặt hiệu ứng quan sát được.

Production có nhiều worker instances để scale-out. Thỉnh thoảng support nhận ticket user nhận hai email giống nhau, trong khi một số record trong database lại chỉ có một audit entry. Có lần worker restart trong lúc đang xử lý, và có lần Service Bus báo transient network failure khi settle message.

Team đang dùng PeekLock. Họ cho rằng chỉ cần `CompleteMessageAsync` ở cuối handler là đủ để đảm bảo exactly-once. Queue đã bật retry phía SDK, nhưng consumer chưa có idempotency table riêng.

## Đoạn code cần review

```csharp
public sealed class ApprovalCompletedHandler
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<ApprovalCompletedHandler> _logger;

    public ApprovalCompletedHandler(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<ApprovalCompletedHandler> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        ServiceBusReceiver receiver,
        CancellationToken cancellationToken)
    {
        var evt = JsonSerializer.Deserialize<ApprovalCompletedEvent>(
            message.Body);

        if (evt is null)
        {
            await receiver.DeadLetterMessageAsync(
                message,
                "InvalidPayload",
                cancellationToken: cancellationToken);
            return;
        }

        var approval = await _db.Approvals
            .SingleAsync(x => x.Id == evt.ApprovalId, cancellationToken);

        approval.Status = ApprovalStatus.Completed;
        approval.CompletedAt = evt.CompletedAt;

        await _db.SaveChangesAsync(cancellationToken);

        await _emailSender.SendApprovalCompletedAsync(
            evt.EmployeeEmail,
            evt.ApprovalId,
            cancellationToken);

        _db.AuditLogs.Add(new AuditLog
        {
            ApprovalId = evt.ApprovalId,
            Event = "ApprovalCompleted",
            CreatedAt = DateTimeOffset.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        await receiver.CompleteMessageAsync(message, cancellationToken);

        _logger.LogInformation(
            "Processed approval {ApprovalId} for {Email}",
            evt.ApprovalId,
            evt.EmployeeEmail);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness và consistency trong handler.
2. Xác định rủi ro duplicate processing khi retry, lock loss hoặc worker restart.
3. Giải thích production impact của từng vấn đề và xếp thứ tự ưu tiên.
4. Đề xuất design giúp consumer idempotent mà không giả định exactly-once end-to-end.
5. Phân tích transaction boundary giữa SQL write, audit log và email side effect.
6. Nêu cách xử lý poison message, transient failure và settlement failure.
7. Đề xuất tests và telemetry đủ để chứng minh behavior dưới duplicate delivery.

## Câu hỏi gợi mở

1. Nếu email đã gửi thành công nhưng process chết trước `CompleteMessageAsync`, lần delivery tiếp theo sẽ làm gì?
2. Nếu `CompleteMessageAsync` trả lỗi do connection bị gián đoạn, bạn có chắc service chưa complete message không?
3. `SaveChangesAsync` lần thứ nhất và lần thứ hai hiện bảo đảm atomicity cho những dữ liệu nào?
4. `MessageId` và business event identity nên được dùng ở đâu trong consumer?
5. Nếu hai worker cùng xử lý cùng business event gần như đồng thời, chỉ check trạng thái `Completed` có đủ không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **at-least-once delivery gặp non-idempotent side effect**. Hãy xem handler như một distributed workflow chứ không phải một transaction duy nhất.

### Gợi ý 2

Tách câu hỏi thành ba phần: deduplicate business event, commit local state atomically và phát side effect ra ngoài một cách có thể retry an toàn.

## Kết quả code review tham khảo

### Critical — Email có thể được gửi lặp khi message được redeliver

**Vấn đề:** Handler gọi email provider trực tiếp trước khi settle message và không có idempotency guard.

**Tại sao xảy ra:** Với PeekLock, message có thể được redeliver nếu worker restart, lock bị mất hoặc settlement outcome không rõ ràng. Một lần xử lý có thể đã gửi email thành công nhưng chưa hoàn tất message theo góc nhìn của consumer.

**Ảnh hưởng production:** User nhận nhiều email, downstream provider có thể bị tính phí nhiều lần, audit và trạng thái hệ thống không phản ánh chính xác số side effects thực tế.

**Cách sửa:** Consumer phải idempotent theo `MessageId` hoặc business event ID ổn định. Không coi broker settlement là exactly-once business semantics. Với side effect bên ngoài, dùng outbox/local intent record hoặc provider idempotency key nếu provider hỗ trợ; nếu không, thiết kế sender để deduplicate bằng một notification key duy nhất.

### Critical — Local database state và external email không có cùng transaction boundary

**Vấn đề:** Database được commit trước email. Email lại diễn ra ngoài SQL transaction.

**Tại sao xảy ra:** SQL Server transaction không thể atomically bao trùm một external email API theo design thông thường.

**Ảnh hưởng production:** Có thể tồn tại trạng thái `Completed` nhưng chưa gửi email, hoặc email đã gửi nhưng audit chưa được ghi. Retry có thể làm lệch trạng thái thêm.

**Cách sửa:** Trong transaction local, commit approval state, inbox/dedup marker và outbox notification intent cùng lúc. Một dispatcher riêng gửi email từ outbox và đánh dấu sent bằng idempotent state transition. Đây là cách tách atomic local commit khỏi unreliable external side effect.

### High — Hai lần `SaveChangesAsync` tạo partial commit giữa approval và audit

**Vấn đề:** Approval được commit trước audit log.

**Tại sao xảy ra:** Hai database writes độc lập, không có transaction bao trùm business unit cần atomic.

**Ảnh hưởng production:** Crash giữa hai lần save tạo approval completed nhưng không có audit event. Retry có thể thêm duplicate audit nếu không có unique constraint.

**Cách sửa:** Nếu approval state và audit phải nhất quán, ghi cùng một transaction và một `SaveChangesAsync`, hoặc dùng explicit transaction khi flow phức tạp hơn. Thêm unique business key cho audit/event record nếu event phải xuất hiện tối đa một lần.

### High — Không có deduplication/inbox record

**Vấn đề:** Handler không ghi nhận event nào đã được xử lý.

**Tại sao xảy ra:** Code giả định một message chỉ đến một lần.

**Ảnh hưởng production:** Duplicate delivery làm toàn bộ handler chạy lại. Chỉ dựa vào `Approval.Status == Completed` không đủ nếu email, audit hoặc các side effects khác đã xảy ra một phần.

**Cách sửa:** Tạo bảng `ProcessedMessages` hoặc Inbox với unique constraint trên một stable event identity. Insert marker trong cùng transaction với local state changes. Nếu insert đụng unique key, coi event đã được xử lý local và tránh lặp side effects tương ứng.

### High — Không xử lý ambiguity của settlement failure

**Vấn đề:** Nếu `CompleteMessageAsync` thất bại do network interruption, code có thể retry business logic ở lần redelivery mà không biết server đã nhận complete hay chưa.

**Tại sao xảy ra:** Distributed acknowledgement có outcome ambiguity.

**Ảnh hưởng production:** Business logic chạy lại dù lần trước đã thành công.

**Cách sửa:** Business handler phải an toàn khi chạy lại. Settlement chỉ quyết định message lifecycle, không phải nguồn chân lý duy nhất cho exactly-once business behavior.

### High — Concurrency giữa nhiều worker có thể tạo duplicate side effect

**Vấn đề:** Không có unique event guard hoặc concurrency control ở database.

**Tại sao xảy ra:** Hai deliveries của cùng logical event có thể được xử lý gần nhau trên hai instances.

**Ảnh hưởng production:** Cả hai worker đều có thể đọc approval trước khi bên kia hoàn tất và cùng gửi email.

**Cách sửa:** Dùng database-enforced uniqueness cho event identity, không chỉ in-memory lock. In-process lock không bảo vệ multi-instance. Có thể kết hợp optimistic concurrency cho aggregate state nếu cần.

### Medium — Deserialization failure classification còn thô

**Vấn đề:** `JsonSerializer.Deserialize` có thể ném exception thay vì trả null cho nhiều malformed payloads.

**Tại sao xảy ra:** Code chỉ check `evt is null` mà không catch `JsonException` để dead-letter có chủ đích.

**Ảnh hưởng production:** Poison payload có thể bị retry vô ích tới khi vượt delivery count.

**Cách sửa:** Catch lỗi payload không retryable, ghi safe metadata, dead-letter với reason rõ ràng. Không log toàn bộ payload nếu chứa dữ liệu nhạy cảm.

### Medium — Missing business validation và event version handling

**Vấn đề:** Code tin `EmployeeEmail`, `CompletedAt`, `ApprovalId` từ payload mà không xác minh business constraints/version.

**Tại sao xảy ra:** Transport deserialization bị coi như domain validation.

**Ảnh hưởng production:** Event cũ/sai schema có thể cập nhật state không hợp lệ hoặc gửi tới sai địa chỉ.

**Cách sửa:** Validate contract version và các field bắt buộc. Khi dữ liệu người nhận là nguồn nhạy cảm, cân nhắc lấy email canonical từ database thay vì tin tuyệt đối payload.

### Medium — Observability thiếu message identity và delivery context

**Vấn đề:** Log chỉ có approval ID và email.

**Tại sao xảy ra:** Không log `MessageId`, delivery count, correlation ID, processing outcome hoặc duplicate decision.

**Ảnh hưởng production:** Khó chứng minh duplicate delivery hay phân biệt send duplicate với logging duplicate.

**Cách sửa:** Structured log/traces với `MessageId`, business event ID, approval ID, delivery count, outbox ID, dedup hit, send attempt và settlement outcome. Không log token/secret hoặc nội dung nhạy cảm không cần thiết.

## Phiên bản đề xuất

Một hướng thiết kế an toàn hơn là dùng **Inbox + local transaction + Outbox**. Handler chỉ commit state nội bộ và notification intent. Email dispatcher xử lý outbox riêng.

```csharp
public sealed class ApprovalCompletedHandler
{
    private readonly AppDbContext _db;

    public ApprovalCompletedHandler(AppDbContext db)
        => _db = db;

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        ServiceBusReceiver receiver,
        CancellationToken cancellationToken)
    {
        ApprovalCompletedEvent evt;

        try
        {
            evt = JsonSerializer.Deserialize<ApprovalCompletedEvent>(message.Body)
                ?? throw new JsonException("Payload is null.");
        }
        catch (JsonException)
        {
            await receiver.DeadLetterMessageAsync(
                message,
                "InvalidPayload",
                cancellationToken: cancellationToken);
            return;
        }

        var eventId = string.IsNullOrWhiteSpace(message.MessageId)
            ? evt.EventId
            : message.MessageId;

        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.EventId == eventId, cancellationToken);

        if (alreadyProcessed)
        {
            await transaction.RollbackAsync(cancellationToken);
            await receiver.CompleteMessageAsync(message, cancellationToken);
            return;
        }

        var approval = await _db.Approvals
            .SingleAsync(x => x.Id == evt.ApprovalId, cancellationToken);

        approval.Status = ApprovalStatus.Completed;
        approval.CompletedAt = evt.CompletedAt;

        _db.AuditLogs.Add(new AuditLog
        {
            ApprovalId = evt.ApprovalId,
            Event = "ApprovalCompleted",
            EventId = eventId,
            CreatedAt = DateTimeOffset.UtcNow
        });

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            MessageKey = $"approval-completed-email:{evt.ApprovalId}:{eventId}",
            Type = "ApprovalCompletedEmail",
            Payload = JsonSerializer.Serialize(new
            {
                evt.ApprovalId,
                evt.EmployeeEmail
            }),
            CreatedAt = DateTimeOffset.UtcNow
        });

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            EventId = eventId,
            ProcessedAt = DateTimeOffset.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
        await transaction.CommitAsync(cancellationToken);

        await receiver.CompleteMessageAsync(message, cancellationToken);
    }
}
```

Database cần unique constraint trên `ProcessedMessages.EventId`. `OutboxMessages.MessageKey` cũng nên có uniqueness phù hợp nếu một notification chỉ được tạo một lần cho cùng business event.

Email dispatcher nên xử lý một outbox row theo state machine kiểu `Pending → Sending → Sent/Failed`, với retry bounded. Nếu provider hỗ trợ idempotency key, truyền `MessageKey` sang provider. Nếu provider không hỗ trợ, hệ thống vẫn cần local dedup và phải chấp nhận/đánh giá residual ambiguity của external call timeout.

Không nên giữ SQL transaction mở trong lúc gọi email provider. Transaction chỉ bao trùm state nội bộ cần atomic. Việc gửi email là bước asynchronous có thể retry.

Theo tài liệu Azure Service Bus hiện hành, PeekLock có thể dẫn tới redelivery khi lock bị mất hoặc consumer restart; duplicate detection ở send side không thay thế idempotent receive-side processing. Vì vậy consumer phải chịu được duplicate delivery theo design.

## Giải thích thiết kế sau khi sửa

Thiết kế mới đặt database làm durable source of truth cho ba facts: event đã được consume local, approval đã chuyển state và notification cần được gửi. Ba facts này commit cùng nhau.

Nếu worker chết trước commit, message được redeliver và xử lý lại từ đầu. Nếu worker chết sau commit nhưng trước settlement, lần sau dedup marker ngăn local business mutation chạy lại. Nếu outbox dispatcher chết sau khi provider nhận email nhưng trước khi đánh dấu `Sent`, idempotency key của provider là lớp bảo vệ tốt nhất; nếu provider không hỗ trợ, cần business-aware dedup/fallback và telemetry để phát hiện ambiguity.

`CompleteMessageAsync` vẫn cần thiết, nhưng nó là broker lifecycle operation chứ không phải transaction coordinator cho SQL + email.

## Trade-offs

Inbox/Outbox thêm bảng, cleanup policy, dispatcher và observability. Đây là complexity có chi phí thật. Nó hợp lý khi side effect quan trọng, duplicate gây impact và hệ thống scale nhiều instances.

Nếu email chỉ là best-effort, business chấp nhận occasional duplicate và volume nhỏ, có thể chọn design đơn giản hơn. Tuy nhiên decision phải explicit, không nên vô tình dựa vào assumption exactly-once.

Unique constraint giúp correctness nhưng tạo write overhead và yêu cầu retention strategy cho processed IDs. Cần xác định dedup horizon dựa trên message lifetime/business replay semantics, không xóa marker quá sớm.

## Cách kiểm thử

1. **Integration test duplicate delivery:** gửi cùng `MessageId`/event ID hai lần; xác minh approval mutation, audit và outbox intent chỉ được tạo một lần.
2. **Failure-path test crash after DB commit:** mô phỏng exception trước settlement; redeliver message và xác minh không tạo duplicate local side effects.
3. **Concurrency test:** hai handler instances xử lý cùng event đồng thời; unique constraint phải ngăn double-processing.
4. **Outbox retry test:** email provider timeout sau khi request có khả năng đã được nhận; xác minh idempotency key hoặc duplicate protection hoạt động như thiết kế.
5. **Poison-message test:** malformed JSON phải đi DLQ có reason rõ ràng mà không retry vô hạn.

## Quan sát trong production

Theo dõi structured logs và metrics cho:

- `MessageId`, business event ID, correlation ID;
- delivery count và lock/settlement failures;
- inbox dedup hits;
- outbox pending count, age của oldest pending item, retry count;
- email send latency, ambiguous timeout, provider error rate;
- DLQ depth và reason distribution;
- handler duration p95/p99;
- SQL unique-constraint conflicts trên dedup key;
- trace từ Service Bus receive → SQL transaction → outbox dispatcher → email provider.

Alert khi DLQ tăng, oldest outbox age vượt SLO hoặc duplicate-related metric tăng bất thường.

### Critical — Production credential bị hard-code trong Deployment manifest

**Vấn đề:** Connection string chứa username/password plaintext trong YAML.

**Tại sao xảy ra:** Secret được coi như config bình thường và có thể xuất hiện trong Git history, CI logs hoặc manifest artifacts.

**Ảnh hưởng production:** Credential disclosure có thể dẫn tới database compromise và khó rotate an toàn.

**Cách sửa:** Dùng Kubernetes Secret hoặc tốt hơn là secret integration phù hợp với platform, ví dụ external secret store/Managed Identity khi architecture hỗ trợ. Pod chỉ nhận secret qua least-privilege mechanism. Không commit real secret vào repository.

### High — Liveness probe quá aggressive so với startup time

**Vấn đề:** App có thể cần 20–45 giây warm up nhưng liveness bắt đầu sau 5 giây và chỉ cho hai failures.

**Tại sao xảy ra:** Kubernetes có thể kết luận container unhealthy trong khi nó chỉ chưa startup xong.

**Ảnh hưởng production:** Restart loop kéo dài, rollout không ổn định, gây capacity loss.

**Cách sửa:** Thêm `startupProbe` đủ budget cho worst-case startup hợp lý. Sau khi startup probe thành công, liveness mới chịu trách nhiệm phát hiện process bị stuck. Không dùng liveness như startup gate.

### High — Readiness và liveness dùng cùng endpoint mà không phân biệt semantics

**Vấn đề:** `/health` có thể kiểm tra database/dependencies giống nhau cho cả hai probe.

**Tại sao xảy ra:** Team coi health check như một boolean duy nhất.

**Ảnh hưởng production:** Database slowdown có thể làm liveness fail và restart một process vốn vẫn sống. Nhiều pods có thể restart đồng thời, làm incident nặng hơn. Ngược lại, readiness quá đơn giản có thể cho pod nhận traffic trước khi thật sự ready.

**Cách sửa:** Tách liveness endpoint chỉ kiểm tra process-level health tối thiểu. Readiness kiểm tra khả năng serve request theo dependency policy đã chọn. Startup probe bảo vệ warm-up phase. Dependency nào được đưa vào readiness phải dựa trên behavior mong muốn khi dependency degraded.

### High — Mỗi pod tự chạy EF Core migration khi startup

**Vấn đề:** Tất cả replicas đều gọi `MigrateAsync()`.

**Tại sao xảy ra:** Migration ownership bị gắn vào application startup.

**Ảnh hưởng production:** Concurrent migration attempts, lock contention, startup delay, rollback khó, và schema change có thể phá backward compatibility với old pods đang còn chạy trong rolling deployment.

**Cách sửa:** Tách migration thành explicit deployment step/job với một owner duy nhất. Thiết kế migration backward-compatible theo expand/contract khi cần rolling rollout. Chỉ deploy app mới sau khi migration precondition phù hợp được xác minh.

### High — Rolling update làm giảm capacity mạnh

**Vấn đề:** `maxUnavailable: 50%`, `maxSurge: 0` với 4 replicas cho phép capacity giảm đáng kể trong rollout và không tạo pod mới vượt desired replicas.

**Tại sao xảy ra:** Strategy ưu tiên không tăng số pod hơn là availability.

**Ảnh hưởng production:** Nếu traffic đang gần capacity, rollout có thể gây p95/p99 tăng hoặc 5xx. Nếu pod mới warm chậm, hệ thống giữ capacity thấp lâu hơn.

**Cách sửa:** Chọn `maxUnavailable`/`maxSurge` theo traffic headroom và resource budget. Ví dụ có thể dùng `maxUnavailable: 0`, `maxSurge: 1` nếu cluster có room và availability quan trọng. Không có một cấu hình đúng cho mọi workload; phải dựa trên SLO và capacity evidence.

### High — Chỉ có resource limits, không có requests

**Vấn đề:** Container khai báo limits nhưng không khai báo CPU/memory requests.

**Tại sao xảy ra:** Resource policy chưa hoàn chỉnh.

**Ảnh hưởng production:** Scheduling và QoS behavior có thể không phản ánh nhu cầu steady-state thực. CPU limit quá thấp còn có thể làm warm-up và request processing bị throttled, khiến probe fail dây chuyền.

**Cách sửa:** Đo actual CPU/memory baseline và peak, sau đó đặt requests theo capacity cần reserve và limits theo risk policy. Theo dõi throttling/OOMKilled. Không chọn số tùy ý chỉ để “có limit”.

### Medium — `latest` tag làm artifact không immutable

**Vấn đề:** Deployment dùng `employee-api:latest`.

**Tại sao xảy ra:** Tag mutable không xác định chính xác binary nào đang chạy.

**Ảnh hưởng production:** Rollback/debug khó, cache behavior của node có thể gây confusion, audit artifact kém rõ ràng.

**Cách sửa:** Dùng version tag immutable hoặc image digest gắn với build artifact. Pipeline phải biết chính xác image nào được promote qua environments.

### Medium — Readiness có thể bật quá sớm

**Vấn đề:** readiness bắt đầu sau 1 giây và failure threshold thấp, trong khi warm-up mất hàng chục giây.

**Tại sao xảy ra:** Không có startup gate và endpoint chưa phản ánh complete initialization.

**Ảnh hưởng production:** Pod có thể nhận request trước khi cache/lookup/config initialization hoàn tất, gây latency spike hoặc lỗi.

**Cách sửa:** Startup probe trì hoãn readiness/liveness cho tới khi startup hoàn tất. Readiness endpoint chỉ trả success khi app có thể serve traffic đúng theo contract.

### Medium — Health timeout 1 giây có thể quá nhạy với dependency hiccup

**Vấn đề:** Probe timeout ngắn có thể phù hợp hoặc không, nhưng hiện không có evidence.

**Tại sao xảy ra:** Thresholds được chọn tĩnh không dựa trên actual health endpoint latency và failure semantics.

**Ảnh hưởng production:** False negative tạo traffic churn hoặc restart cascade.

**Cách sửa:** Đo probe latency và chọn timeout/threshold phù hợp. Health endpoint phải lightweight, bounded và không thực hiện expensive query.

### Medium — Không thể hiện graceful shutdown/drain behavior

**Vấn đề:** Manifest không cho thấy app có đủ thời gian hoàn tất in-flight requests/background work khi pod terminate hay không.

**Tại sao xảy ra:** Rollout được xem chủ yếu là startup concern.

**Ảnh hưởng production:** Request bị cắt giữa chừng, duplicate work hoặc partial side effect khi pod terminate.

**Cách sửa:** Xác minh ASP.NET Core shutdown behavior, termination grace period và cancellation propagation. Nếu có background consumer, stop intake trước rồi drain work trong bounded time.

## Phiên bản đề xuất

Một manifest tham khảo có thể như sau. Các giá trị resource/probe bên dưới là **scenario example**, không phải production default:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: employee-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: employee-api
  template:
    metadata:
      labels:
        app: employee-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: employee-api
          image: company.azurecr.io/employee-api:2026.09.13.1
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: employee-api-secrets
                  key: main-db
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
```

ASP.NET Core có thể map health checks theo tags:

```csharp
builder.Services
    .AddHealthChecks()
    .AddCheck<StartupHealthCheck>(
        "startup",
        tags: new[] { "startup" })
    .AddCheck<ProcessHealthCheck>(
        "live",
        tags: new[] { "live" })
    .AddCheck<DatabaseReadinessCheck>(
        "database",
        tags: new[] { "ready" });

var app = builder.Build();

app.MapHealthChecks("/health/startup", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("startup")
});

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("ready")
});

app.Run();
```

`StartupHealthCheck` chỉ nên success khi application initialization cần thiết đã hoàn tất. `ProcessHealthCheck` không nên fail chỉ vì một external dependency tạm thời chậm nếu restart process không giúp ích gì. `DatabaseReadinessCheck` phải lightweight và bounded; nếu business cho phép degraded read-only behavior, readiness policy có thể khác.

Migration nên tách khỏi app startup. Pipeline có thể chạy một migration job riêng trước rollout, verify migration thành công, sau đó rollout application artifact. Với breaking schema change cần nhiều bước, dùng expand/contract để old và new pods cùng hoạt động trong giai đoạn chuyển tiếp.

Theo Kubernetes documentation hiện hành, readiness failure loại pod khỏi Service traffic, trong khi liveness failure dẫn tới restart container; startup probe được dùng để bảo vệ các ứng dụng khởi động chậm trước khi liveness bắt đầu chi phối. RollingUpdate dùng `maxUnavailable` và `maxSurge` để kiểm soát availability/capacity trong rollout.

## Giải thích thiết kế sau khi sửa

Ba probe trả lời ba câu hỏi khác nhau:

- `startupProbe`: app đã hoàn tất giai đoạn startup cần thiết chưa;
- `livenessProbe`: process có đang ở trạng thái mà restart có khả năng giúp không;
- `readinessProbe`: pod hiện có nên nhận traffic không.

Tách semantics giúp tránh restart cascade khi dependency ngoài app bị chậm. Readiness có thể fail để traffic dừng gửi vào pod mà không cần giết process.

Resource values phải được đo. Nếu CPU limit tạo throttling đúng lúc startup, tăng probe timeout chỉ che triệu chứng. Cần xem actual CPU throttling, working set, GC và request latency trước khi chỉnh.

Rollout strategy cũng là capacity decision. Nếu `maxUnavailable: 0` nhưng cluster không còn room cho surge pod, rollout có thể stall. Vì vậy cần capacity planning chứ không copy config máy móc.

## Trade-offs

`startupProbe` làm rollout chậm hơn nếu budget quá rộng và app thực sự bị treo trong startup. Vì vậy threshold phải đủ cho normal slow startup nhưng vẫn bounded.

Readiness phụ thuộc database có thể bảo vệ user khỏi request chắc chắn fail, nhưng nếu database outage toàn vùng thì toàn bộ pods đều unready và service không có endpoint để trả degraded response. Quyết định này phải theo product behavior mong muốn.

Tăng resource requests cải thiện scheduling predictability nhưng giảm bin-packing density. Tăng limits quá cao có thể gây noisy-neighbor impact. Cần benchmark/load data.

Tách migration thành job riêng tăng pipeline complexity nhưng làm ownership, rollback và failure visibility rõ ràng hơn. Expand/contract làm migration dài hơn nhưng hỗ trợ zero/low-downtime rollout tốt hơn.

## Cách kiểm thử

1. **Deployment validation:** render/validate manifest trong CI; reject plaintext production secrets và mutable `latest` tag.
2. **Startup test:** chạy container với simulated slow startup 40–50 giây; xác minh startup probe không gây restart và pod chưa Ready trước khi initialization hoàn tất.
3. **Dependency failure test:** làm database tạm unavailable; xác minh readiness behavior đúng nhưng liveness không restart process nếu restart không giúp.
4. **Load + rolling update test:** chạy representative load, rollout version mới và quan sát p95/p99, 5xx, ready replicas, CPU throttling và rollout duration.
5. **Migration compatibility test:** kiểm tra old app + new schema và new app + transitional schema nếu dùng expand/contract; xác minh rollback path.

## Quan sát trong production

Theo dõi:

- pod restart count và reason;
- readiness/liveness/startup probe failures theo reason;
- `Ready` replicas trong rollout;
- rollout duration và unavailable replica count;
- CPU usage, CPU throttling, memory working set, OOMKilled;
- request p50/p95/p99, 5xx/502/503;
- application startup duration;
- DB connection/open latency và dependency failure rate;
- migration job status/duration;
- image digest/version đang chạy trên từng pod;
- termination duration và in-flight request failures.

Alert nên phân biệt app crash, readiness degradation và external dependency outage thay vì gom thành một “pod unhealthy”.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cluster không đủ capacity để `maxSurge: 1`, bạn điều chỉnh rollout strategy hay cluster capacity theo tiêu chí nào?
2. Nếu database down hoàn toàn nhưng API vẫn có thể serve cached read-only data, readiness check nên thiết kế ra sao?
3. Khi schema migration không backward-compatible, bạn sẽ thiết kế rollout/rollback như thế nào để tránh old pod và new schema xung đột?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Service Bus consumer phải được thiết kế cho duplicate delivery; broker settlement không tự tạo exactly-once business semantics.
- External side effect như email không nằm trong cùng local SQL transaction; Inbox/Outbox là một cách phổ biến để tách durable local commit khỏi retryable delivery.
- Idempotency phải được enforce bằng stable business/message identity và durable uniqueness, không dựa vào in-memory lock khi chạy nhiều instances.
- Kubernetes `startup`, `liveness` và `readiness` có mục đích khác nhau; dùng một endpoint/semantics cho tất cả có thể gây restart cascade hoặc nhận traffic quá sớm.
- Rolling deployment, resource requests/limits, migration ownership, secret handling và immutable artifacts đều là một phần của production correctness, không chỉ là DevOps “configuration detail”.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng với idempotency.
- Tách local atomic transaction khỏi external side effects.
- Đừng dùng restart để chữa dependency outage nếu restart không thay đổi nguyên nhân.
- Phân biệt startup, alive và ready trước khi thiết kế health checks.
- Đo capacity và resource pressure trước khi chỉnh rollout/probe thresholds.
