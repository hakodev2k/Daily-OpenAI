# Code Review Challenge 1 — Download từ Azure Blob làm cạn connection và lộ dữ liệu

**Chủ đề:** ASP.NET Core 8, Azure Blob Storage, streaming, authorization, HTTP caching  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** Khoảng 9

## Bối cảnh

Một hệ thống quản lý hồ sơ doanh nghiệp lưu file trên Azure Blob Storage. API download chạy trên Azure App Service Linux, 6 instances, xử lý file từ 10 KB đến 2 GB. Metadata trong SQL Server chứa TenantId, OwnerId, BlobName, ContentType và trạng thái đã xóa. Người dùng chỉ được tải file thuộc tenant mà họ có quyền truy cập; một số file là tài liệu nhân sự. Production ghi nhận memory spike, 502 khi nhiều lượt tải và đôi khi file tải về không đúng phiên bản sau khi thay thế. Không được thay đổi URL công khai của endpoint.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/files")]
public sealed class FilesController(
    AppDbContext db,
    BlobServiceClient blobs,
    ILogger<FilesController> logger) : ControllerBase
{
    [HttpGet("{id:guid}/download")]
    [Authorize]
    public async Task<IActionResult> Download(Guid id)
    {
        var file = await db.Files.FirstOrDefaultAsync(x => x.Id == id);
        if (file == null) return NotFound();

        var client = blobs.GetBlobContainerClient("documents")
            .GetBlobClient(file.BlobName);

        var response = await client.DownloadContentAsync();
        var bytes = response.Value.Content.ToArray();

        logger.LogInformation(
            "Downloaded {FileId} {BlobName} by {User}",
            id, file.BlobName, User.Identity?.Name);

        Response.Headers.CacheControl = "public,max-age=3600";
        Response.Headers.ETag = file.Id.ToString();
        return File(bytes, file.ContentType, file.OriginalName);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Thiếu object-level authorization

**Vấn đề:** Bất kỳ authenticated user nào biết GUID đều có thể lấy file.  
**Tại sao xảy ra:** `[Authorize]` chỉ kiểm tra principal, không kiểm tra tenant membership hay quyền đối với tài liệu.  
**Ảnh hưởng production:** Rò rỉ hồ sơ giữa tenant, có thể vi phạm yêu cầu bảo mật.  
**Cách sửa:** Lọc metadata theo quyền được xác thực từ server-side membership/authorization service, kể cả trạng thái xóa; trả 404 khi cần tránh tiết lộ tồn tại.

### [High] — Buffer toàn bộ blob vào memory

**Vấn đề:** `DownloadContentAsync` và `ToArray()` materialize file.  
**Tại sao xảy ra:** Endpoint không stream response.  
**Ảnh hưởng production:** LOH allocations, GC pressure, OOM, giảm throughput và 502.  
**Cách sửa:** `OpenReadAsync` hoặc streaming API phù hợp, truyền stream cho `FileStreamResult`, dispose theo response lifetime.

### [High] — Public caching với tài liệu riêng tư

**Vấn đề:** `public,max-age=3600` cho phép shared cache lưu response.  
**Tại sao xảy ra:** Cache policy không phân biệt private file.  
**Ảnh hưởng production:** Dữ liệu có thể tồn tại tại proxy/CDN sau khi thu hồi quyền.  
**Cách sửa:** Với dữ liệu nhạy cảm dùng `private, no-store` theo security policy; đánh giá riêng cache của public assets.

### [High] — Không propagate request cancellation

**Vấn đề:** EF/Blob calls không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Client disconnect không được truyền xuống I/O.  
**Ảnh hưởng production:** Tiếp tục tiêu thụ bandwidth, sockets và capacity vô ích.  
**Cách sửa:** Truyền cancellation token xuyên suốt, xác minh stream dispose khi response kết thúc.

### [Medium] — ETag sai semantic

**Vấn đề:** ETag là ID cố định dù blob được thay thế.  
**Tại sao xảy ra:** Không liên kết ETag với phiên bản nội dung.  
**Ảnh hưởng production:** Cache validation sai, trả dữ liệu cũ.  
**Cách sửa:** Dùng blob ETag hoặc version được pin trong metadata, đồng bộ cập nhật metadata/blob.

### [Medium] — Không xử lý race và missing blob

**Vấn đề:** Metadata có thể tồn tại nhưng blob bị xóa/thay đổi giữa hai lần đọc.  
**Tại sao xảy ra:** Không định nghĩa consistency boundary và mapping storage errors.  
**Ảnh hưởng production:** 500 ngẫu nhiên hoặc tải nhầm phiên bản.  
**Cách sửa:** Lưu blob version/ETag khi upload, dùng điều kiện đọc nếu yêu cầu consistency; map 404/412 có chủ đích.

### [Medium] — Thiếu giới hạn và kiểm soát abuse

**Vấn đề:** Không có rate/concurrency policy cho download tốn bandwidth.  
**Tại sao xảy ra:** Endpoint xử lý tất cả authenticated requests như nhau.  
**Ảnh hưởng production:** Một tenant có thể làm suy giảm service của tenant khác.  
**Cách sửa:** Đặt quota/rate limit theo tenant, cân nhắc redirect sang short-lived user-scoped SAS chỉ sau khi authorization và security review.

### [Medium] — File name và ContentType lấy từ metadata chưa được chuẩn hóa

**Vấn đề:** Tên file và MIME type có thể đến từ input upload.  
**Tại sao xảy ra:** Không kiểm tra content-disposition và content type ở boundary.  
**Ảnh hưởng production:** Nguy cơ xử lý file không an toàn ở client và sai MIME.  
**Cách sửa:** Sanitize filename, allowlist MIME theo nghiệp vụ, ưu tiên attachment và `X-Content-Type-Options: nosniff`.

### [Low] — Logging thiếu correlation và dữ liệu quá chi tiết

**Vấn đề:** Log blob path và tên người dùng, thiếu tenant/correlation metadata chuẩn.  
**Tại sao xảy ra:** Log được thiết kế như debug statement.  
**Ảnh hưởng production:** Khó điều tra và tăng rủi ro lộ thông tin qua log.  
**Cách sửa:** Structured log với file ID, tenant ID, trace ID, outcome, duration; hạn chế PII.

## Phiên bản đề xuất

Giả định `IFileAccessService` kiểm tra membership/permission từ nguồn server-side và trả metadata của file chưa xóa. `BlobVersionId` được lưu khi upload; nếu hệ thống chưa bật versioning, phải thiết kế consistency khác trước khi yêu cầu tải đúng phiên bản.

```csharp
[ApiController]
[Route("api/files")]
public sealed class FilesController(
    IFileAccessService access,
    BlobServiceClient storage,
    ILogger<FilesController> logger) : ControllerBase
{
    [Authorize]
    [HttpGet("{id:guid}/download")]
    public async Task<IActionResult> Download(
        Guid id, CancellationToken ct)
    {
        var file = await access.FindReadableAsync(User, id, ct);
        if (file is null) return NotFound();

        var blob = storage.GetBlobContainerClient("documents")
            .GetBlobClient(file.BlobName);

        if (!string.IsNullOrEmpty(file.BlobVersionId))
            blob = blob.WithVersion(file.BlobVersionId);

        try
        {
            var stream = await blob.OpenReadAsync(
                new BlobOpenReadOptions(false), ct);

            Response.Headers.CacheControl = "private, no-store";
            Response.Headers["X-Content-Type-Options"] = "nosniff";
            logger.LogInformation(
                "FileDownloadStarted FileId={FileId} TraceId={TraceId}",
                id, HttpContext.TraceIdentifier);

            return File(stream, "application/octet-stream",
                file.SafeDownloadName, enableRangeProcessing: false);
        }
        catch (RequestFailedException ex) when (ex.Status == 404)
        {
            logger.LogWarning(ex, "Blob missing for FileId={FileId}", id);
            return NotFound();
        }
    }
}
```

`IFileAccessService` phải từ chối truy cập cross-tenant và revoked membership, không dùng tenant header/query làm nguồn tin cậy. Ví dụ này là skeleton: production cần xác minh behavior của lazy blob stream khi lỗi xảy ra sau khi HTTP headers đã gửi, exception handling middleware, và dispose trong ASP.NET Core. Nếu cần range/resume cho file lớn, triển khai có kiểm thử với stream seekability và Azure SDK, không bật chỉ bằng một flag.

## Giải thích thiết kế sau khi sửa

Authorization trước khi truy cập storage giúp giảm blast radius. Stream giúp memory gần như độc lập với kích thước file, dù concurrency vẫn tiêu thụ sockets và bandwidth. Pin blob version làm rõ consistency contract; no-store bảo vệ nội dung riêng tư. Chọn server proxy khi cần audit/chặn nội dung; SAS có thể giảm tải origin nhưng tăng trách nhiệm kiểm soát lifetime và revocation.

## Trade-offs

Streaming giữ connection lâu; cần concurrency limit, timeout hợp lý và backpressure. Versioned blob tăng storage cost và yêu cầu lifecycle cleanup. `no-store` giảm hiệu quả cache và resume; file public có thể dùng policy khác. SAS giảm egress qua App Service nhưng URL bearer token có thể bị chuyển tiếp, nên phải scope và TTL tối thiểu.

## Cách kiểm thử

1. **Security integration:** user tenant A truy cập file tenant B hoặc file đã revoked, phải bị từ chối.
2. **Load:** 100–200 downloads đồng thời, theo dõi working set, allocations, p95 và 502.
3. **Failure-path:** blob bị xóa sau khi metadata tạo; kiểm tra HTTP mapping và telemetry.
4. **Consistency:** thay blob cùng logical file ID, bảo đảm tải đúng version được chỉ định.
5. **Cancellation:** client disconnect giữa stream, xác minh tài nguyên được giải phóng.

## Quan sát trong production

Application Insights: request duration, 4xx/5xx, dependency Blob latency, exceptions, trace correlation. Azure Monitor: memory working set, GC, CPU, network throughput, instance restarts. Structured audit: authorized download outcome, tenant/file ID và principal ID đã pseudonymize. Alert trên 5xx, memory và download rejection bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào nên dùng user delegation SAS thay vì proxy stream?
2. Nếu quyền truy cập bị thu hồi trong lúc download 2 GB đang diễn ra, contract nên là gì?
3. Bạn triển khai hỗ trợ HTTP Range an toàn thế nào?

## Kết quả code review tham khảo

### [Critical] — Không đảm bảo cùng artifact Staging → Production

**Vấn đề:** Hai lệnh tạo release riêng với version `latest`, không promote một release ID đã được QA xác nhận.  
**Tại sao xảy ra:** Artifact/release được resolve động ở từng stage.  
**Ảnh hưởng production:** Production có thể nhận build khác Staging.  
**Cách sửa:** Build một immutable package, tạo một release duy nhất, deploy release ID đó qua các environment.

### [High] — Checkout main phá vỡ source provenance

**Vấn đề:** Pipeline tự `git checkout main` và `pull`.  
**Tại sao xảy ra:** Jenkins SCM checkout commit trigger bị thay bằng mutable branch tip.  
**Ảnh hưởng production:** Job cho commit A thực tế build commit B, audit không đáng tin.  
**Cách sửa:** Dùng SCM checkout pinned SHA; lưu SHA trong build metadata.

### [High] — `latest` không phải immutable package version

**Vấn đề:** Mọi build tạo cùng package name/version.  
**Tại sao xảy ra:** Không dùng build number hoặc commit-derived version.  
**Ảnh hưởng production:** Collision, package ambiguity, khó rollback.  
**Cách sửa:** Unique version từ build number + short SHA, reject overwrite và kiểm tra checksum.

### [High] — Không có quality/approval gate cho Production

**Vấn đề:** Production deploy ngay sau Staging command.  
**Tại sao xảy ra:** Không chờ QA sign-off, smoke test và deployment completion status.  
**Ảnh hưởng production:** Regression chưa xác nhận được phát hành.  
**Cách sửa:** Wait for successful deployment, chạy smoke/integration checks và yêu cầu explicit approval theo policy.

### [High] — Secret có thể bị lộ qua command-line và log

**Vấn đề:** API key truyền trực tiếp trong process command; không thể hiện secret binding.  
**Tại sao xảy ra:** Thiếu Jenkins credentials binding và secret handling policy.  
**Ảnh hưởng production:** Secret exposure qua process listing hoặc build logs.  
**Cách sửa:** Credentials store, scoped service identity, masking, rotation; ưu tiên tích hợp chính thức an toàn.

### [Medium] — Thiếu concurrency coordination

**Vấn đề:** Nhiều jobs có thể cùng package/deploy.  
**Tại sao xảy ra:** Không có release serialization/lock cho Production.  
**Ảnh hưởng production:** Race, release đảo thứ tự, khó điều tra.  
**Cách sửa:** Serialize production deployments, enforce release promotion order, không khóa toàn bộ CI build.

### [Medium] — Thiếu deployment health/rollback contract

**Vấn đề:** Không kiểm tra readiness của từng IIS node hay health sau deploy.  
**Tại sao xảy ra:** Pipeline xem command exit là đủ chứng minh release thành công.  
**Ảnh hưởng production:** Partial rollout, 503, lỗi chỉ xuất hiện sau khi traffic chuyển.  
**Cách sửa:** Rolling/batched deployment, drain traffic, health checks, canary khi phù hợp, rollback về release ID đã biết.

### [Medium] — Database migration chưa được phối hợp

**Vấn đề:** Pipeline không có compatibility gate cho schema.  
**Tại sao xảy ra:** App và DB được xem là một thay đổi có thể rollback nguyên tử.  
**Ảnh hưởng production:** Binary rollback không tương thích schema mới.  
**Cách sửa:** Expand/contract migration, backward-compatible deployment, migration verification và recovery plan.

## Phiên bản đề xuất

Pseudo-Jenkinsfile sau mô tả contract; cú pháp Octopus CLI và plugin phải được xác nhận theo version thực tế trước khi triển khai. Các hàm `publishImmutablePackage`, `createOctopusRelease`, `deployAndWait`, `runSmokeTests`, `requireApproval` và `verifyReleaseHealth` là wrapper nội bộ giả định, không phải Jenkins built-in APIs.

```groovy
pipeline {
    agent { label 'windows-dotnet8' }
    options {
        timestamps()
        skipDefaultCheckout(true)
    }
    stages {
        stage('Checkout pinned commit') {
            steps {
                checkout scm
                script {
                    env.SOURCE_SHA = bat(
                        script: '@git rev-parse HEAD',
                        returnStdout: true
                    ).trim()
                    env.PACKAGE_VERSION =
                        "${env.BUILD_NUMBER}-${env.SOURCE_SHA.take(12)}"
                }
            }
        }
        stage('Build and test') {
            steps {
                bat 'dotnet restore Portal.sln --locked-mode'
                bat 'dotnet test Portal.sln -c Release --no-restore'
                bat 'dotnet publish src/Portal/Portal.csproj -c Release --no-restore -o out'
            }
        }
        stage('Package once') {
            steps {
                script {
                    publishImmutablePackage('Portal',
                        env.PACKAGE_VERSION, 'out')
                    env.RELEASE_ID = createOctopusRelease(
                        'Portal', env.PACKAGE_VERSION, env.SOURCE_SHA)
                }
            }
        }
        stage('Staging verification') {
            steps {
                script {
                    deployAndWait(env.RELEASE_ID, 'Staging')
                    runSmokeTests('Staging', env.RELEASE_ID)
                }
            }
        }
        stage('Production approval') {
            steps {
                script { requireApproval(env.RELEASE_ID) }
            }
        }
        stage('Production deployment') {
            steps {
                lock(resource: 'portal-production-deploy') {
                    script {
                        deployAndWait(env.RELEASE_ID, 'Production')
                        verifyReleaseHealth('Production', env.RELEASE_ID)
                    }
                }
            }
        }
    }
}
```

Các wrapper phải fail-closed khi Octopus deployment không thành công, kiểm tra package digest và release ID; approval gắn với release đã test, không phải một mutable branch. `lock` yêu cầu Jenkins Lockable Resources plugin hoặc cơ chế tương đương; nếu không có plugin, phải thay bằng queue/serialization khác. Restore locked-mode chỉ hoạt động khi repository có lock files hợp lệ. Trong production, bảo vệ credentials bằng Jenkins credentials store và giới hạn Octopus permissions theo environment.

## Giải thích thiết kế sau khi sửa

Commit SHA tạo provenance; unique version và digest giúp nhận diện artifact; release ID cố định cho phép promotion. Quality gate giảm khả năng đưa lỗi lên production. Serialization áp dụng riêng deployment, không chặn parallel builds. Deployment health phải xác nhận trạng thái thực của nodes và user-facing endpoints.

## Trade-offs

Approval làm chậm release nhưng phù hợp hệ thống có yêu cầu QA sign-off. Immutable packages tăng storage cần retention policy. Rollback binary nhanh nhưng không tự phục hồi dữ liệu/schema. Rolling deployment tăng complexity; với hệ thống nhỏ có thể dùng maintenance window và health validation đơn giản hơn.

## Cách kiểm thử

1. **Concurrency:** hai builds cùng lúc tạo version khác nhau và không deploy chồng Production.
2. **Provenance:** thay đổi main sau trigger; artifact vẫn tương ứng pinned SHA.
3. **Failure-path:** Staging smoke fail hoặc Octopus timeout; Production không deploy.
4. **Deployment validation:** một IIS node unhealthy; pipeline báo failed, traffic không chuyển sang node đó.
5. **Compatibility:** migrate DB bằng expand/contract, rollback binary cũ vẫn đọc/ghi hợp lệ trong compatibility window.

## Quan sát trong production

Jenkins: build ID, commit SHA, package digest, test results. Octopus: release ID, package version, deployment task status, target nodes và approvals. Application Insights: release annotations, p95, error rate, health endpoints; Windows Event Log/IIS logs: recycle, startup failures và 503. Alert khi deployment không đồng nhất giữa nodes hoặc error rate vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Làm thế nào để chống deploy nhầm artifact nếu Jenkins và Octopus lưu version khác nhau?
2. Khi migration đã chạy nhưng deployment mới fail, bạn quyết định rollback hay roll-forward dựa trên điều kiện nào?
3. Nếu Production có 4 IIS nodes, bạn thiết kế zero-downtime rollout và xác nhận health thế nào?

## Kiến thức trọng tâm

Object-level authorization không thể thay bằng authentication; streaming và cancellation quyết định khả năng chịu tải của file API. 1. Kiểm tra quyền trên từng resource, không chỉ trên endpoint.

3. Một artifact đã test phải được promote nguyên vẹn, không rebuild ngầm.
4. Xác minh trạng thái thực sau deployment, không chỉ kết quả lệnh.
5. Thiết kế rollback cùng với schema compatibility và observability.
