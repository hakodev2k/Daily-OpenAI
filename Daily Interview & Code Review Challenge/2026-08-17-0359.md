# Code Review Challenge 1 — Consumer xử lý thanh toán bị trừ tiền hai lần khi RabbitMQ redeliver

**Chủ đề:** Background jobs, idempotency, EF Core transaction, concurrency, message acknowledgement  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core worker nhận `PaymentRequested` từ RabbitMQ. Mỗi message yêu cầu ghi nhận thanh toán và gọi một payment provider bên ngoài. Hệ thống chạy 4 replica, tải bình thường khoảng 50–100 message/giây. RabbitMQ có thể redeliver message nếu consumer mất kết nối hoặc process chết trước khi acknowledgement hoàn tất.

Production thỉnh thoảng ghi nhận một `OrderId` bị charge hai lần. Log cho thấy cùng một `MessageId` đôi lúc được xử lý trên hai replica cách nhau vài giây. Business yêu cầu không được charge khách hai lần, nhưng vẫn phải retry khi provider timeout.

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly AppDbContext _db;
    private readonly IPaymentGateway _gateway;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        AppDbContext db,
        IPaymentGateway gateway,
        ILogger<PaymentConsumer> logger)
    {
        _db = db;
        _gateway = gateway;
        _logger = logger;
    }

    public async Task HandleAsync(PaymentRequested message)
    {
        var processed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId);

        if (processed)
            return;

        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId);

        if (order.PaymentStatus == PaymentStatus.Paid)
            return;

        var result = await _gateway.ChargeAsync(
            order.CustomerId,
            order.TotalAmount,
            CancellationToken.None);

        order.PaymentStatus = PaymentStatus.Paid;
        order.PaymentReference = result.Reference;

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Payment {MessageId} completed for order {@Order}",
            message.MessageId,
            order);
    }
}
```

3. Giải thích tác động production của từng vấn đề.
4. Ưu tiên vấn đề nào phải sửa trước.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử retry/redelivery/concurrency.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai consumer có thể cùng vượt qua `AnyAsync` không?
- Database transaction có thể làm cho HTTP charge và database commit trở thành một atomic operation không?
- Điều gì xảy ra nếu provider charge thành công nhưng process chết trước `SaveChangesAsync`?
- `MessageId` và `OrderId` nên có constraint nào ở database?
- Retry một HTTP payment request cần điều kiện gì để thực sự an toàn?

## Kết quả code review tham khảo

### 1. External charge không có idempotency key

- **Problem:** `ChargeAsync` không nhận một stable idempotency key.
- **Why it happens:** Redelivery hoặc retry có thể tạo một request charge mới.
- **Production impact:** Khách hàng có thể bị charge nhiều lần.
- **Severity:** Critical
- **Recommended fix:** Nếu provider hỗ trợ idempotency, gửi một key ổn định gắn với payment operation/order và persist mapping của key đó. Không giả định retry là an toàn nếu provider không có semantics tương ứng.

### 2. Check-then-act race trên `ProcessedMessages`

- **Problem:** `AnyAsync` rồi mới xử lý không khóa quyền sở hữu message.
- **Why it happens:** Hai replica có thể cùng đọc `false` trước khi một bên insert.
- **Production impact:** Cả hai cùng gọi payment provider.
- **Severity:** Critical
- **Recommended fix:** Dùng database-enforced uniqueness và cơ chế claim/state transition atomic. Unique constraint là hàng rào correctness cuối cùng, không chỉ kiểm tra ở application.

### 3. Crash window sau external side effect

- **Problem:** Provider có thể charge thành công nhưng process chết trước khi trạng thái được commit.
- **Why it happens:** External system và local DB không nằm trong cùng atomic transaction.
- **Production impact:** Redelivery thấy order chưa paid rồi charge lại.
- **Severity:** Critical
- **Recommended fix:** Thiết kế payment operation có idempotency key; khi outcome không chắc chắn, reconcile/query provider thay vì mù quáng tạo charge mới.

### 4. Không có concurrency protection trên order

- **Problem:** `PaymentStatus` chỉ được đọc rồi kiểm tra trong memory.
- **Why it happens:** Hai consumer có thể cùng load trạng thái `Pending`.
- **Production impact:** Duplicate side effect và last-write-wins ở database.
- **Severity:** High
- **Recommended fix:** Dùng atomic state transition/optimistic concurrency token hoặc một payment-operation record có unique constraint theo business invariant.

### 5. Cancellation bị bỏ qua

- **Problem:** `CancellationToken.None` được truyền xuống gateway và EF operations cũng không nhận cancellation token.
- **Why it happens:** Worker shutdown không thể cooperative-cancel I/O đang chờ.
- **Production impact:** Deploy/shutdown chậm, tăng khả năng message ownership và acknowledgement trở nên khó dự đoán.
- **Severity:** Medium
- **Recommended fix:** Propagate token của consumer. Tuy nhiên phải phân biệt cancellation trước request với trạng thái không chắc chắn sau khi request đã tới provider.

### 6. Không thể hiện chiến lược transient retry và uncertain result

- **Problem:** Timeout/network failure bị đối xử như một failure đơn giản.
- **Why it happens:** Timeout không chứng minh provider chưa thực hiện charge.
- **Production impact:** Retry có thể duplicate payment.
- **Severity:** High
- **Recommended fix:** Retry chỉ với idempotency semantics; nếu outcome ambiguous thì lookup/reconcile theo idempotency key/reference.

### 7. Logging cả entity `Order`

- **Problem:** Structured logging toàn bộ entity có thể đưa dữ liệu không cần thiết hoặc nhạy cảm vào log.
- **Why it happens:** `{@Order}` destructure object.
- **Production impact:** Tăng log volume và nguy cơ sensitive-data exposure.
- **Severity:** Medium
- **Recommended fix:** Log identifiers và trạng thái tối thiểu: `OrderId`, `MessageId`, operation/idempotency key, result category.

### 8. Dùng `DateTime.UtcNow` trực tiếp làm giảm testability

- **Problem:** Clock là dependency ẩn.
- **Why it happens:** Business timestamp lấy trực tiếp từ static clock.
- **Production impact:** Test khó kiểm soát; đây không phải lỗi correctness chính.
- **Severity:** Low
- **Recommended fix:** Với codebase cần deterministic tests, inject `TimeProvider`.

## Phiên bản code đề xuất

Giả định payment provider hỗ trợ idempotency key và `PaymentOperation.OrderId` có unique index. Claim operation phải được database bảo vệ; đoạn dưới tập trung vào flow và failure boundary, không coi local transaction là distributed transaction.

```csharp
public sealed class PaymentConsumer
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IPaymentGateway _gateway;
    private readonly ILogger<PaymentConsumer> _logger;
    private readonly TimeProvider _timeProvider;

    public PaymentConsumer(
        IDbContextFactory<AppDbContext> dbFactory,
        IPaymentGateway gateway,
        ILogger<PaymentConsumer> logger,
        TimeProvider timeProvider)
    {
        _dbFactory = dbFactory;
        _gateway = gateway;
        _logger = logger;
        _timeProvider = timeProvider;
    }

    public async Task HandleAsync(
        PaymentRequested message,
        CancellationToken cancellationToken)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

        var operation = await db.PaymentOperations
            .SingleOrDefaultAsync(
                x => x.OrderId == message.OrderId,
                cancellationToken);

        if (operation?.Status == PaymentOperationStatus.Succeeded)
            return;

        if (operation is null)
        {
            operation = new PaymentOperation
            {
                OrderId = message.OrderId,
                IdempotencyKey = $"payment:{message.OrderId}",
                Status = PaymentOperationStatus.Pending,
                CreatedAtUtc = _timeProvider.GetUtcNow()
            };

            db.PaymentOperations.Add(operation);

            try
            {
                await db.SaveChangesAsync(cancellationToken);
            }
            catch (DbUpdateException)
            {
                db.ChangeTracker.Clear();
                operation = await db.PaymentOperations.SingleAsync(
                    x => x.OrderId == message.OrderId,
                    cancellationToken);
            }
        }

        if (operation.Status == PaymentOperationStatus.Succeeded)
            return;

        var order = await db.Orders
            .AsNoTracking()
            .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

        var result = await _gateway.ChargeAsync(
            order.CustomerId,
            order.TotalAmount,
            operation.IdempotencyKey,
            cancellationToken);

        await using var tx = await db.Database.BeginTransactionAsync(cancellationToken);

        var trackedOrder = await db.Orders
            .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

        trackedOrder.PaymentStatus = PaymentStatus.Paid;
        trackedOrder.PaymentReference = result.Reference;

        operation.Status = PaymentOperationStatus.Succeeded;
        operation.ProviderReference = result.Reference;
        operation.CompletedAtUtc = _timeProvider.GetUtcNow();

        await db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Payment completed. MessageId={MessageId}, OrderId={OrderId}, IdempotencyKey={IdempotencyKey}",
            message.MessageId,
            message.OrderId,
            operation.IdempotencyKey);
    }
}
```

Trong production cần xử lý riêng trạng thái `Pending/Unknown` và reconcile nếu provider trả timeout sau khi request có thể đã được nhận. Nếu nhiều consumer có thể cùng gọi provider với cùng idempotency key, correctness còn phụ thuộc contract idempotency thực tế của provider; nếu provider không cung cấp guarantee đó, kiến trúc phải thay đổi.

## Trade-offs

Unique constraint và payment-operation record làm schema/phần xử lý phức tạp hơn nhưng biến business invariant thành thứ database có thể enforce. Lock database kéo dài qua HTTP call thường không nên dùng vì tăng contention và vẫn không giải quyết atomicity giữa hai hệ thống. Distributed lock cũng không loại bỏ crash window. Nếu provider không hỗ trợ idempotency, có thể cần workflow authorization/capture, reconciliation hoặc một integration contract khác thay vì cố “exactly once” bằng consumer code.

## Cách kiểm thử

1. **Concurrency integration test:** chạy đồng thời nhiều handler cho cùng `OrderId`; xác nhận chỉ một logical payment operation tồn tại và provider nhận cùng idempotency key.
2. **Redelivery test:** xử lý cùng `MessageId`/`OrderId` nhiều lần sau khi success; không phát sinh charge mới.
3. **Crash-window/failure-path test:** giả lập provider success nhưng DB commit fail; lần retry phải reconcile/idempotently nhận lại cùng outcome.
4. **Timeout test:** provider timeout sau khi nhận request; không được tự động tạo một payment operation mới.
5. **Database constraint test:** xác nhận unique constraint thực sự chặn hai operation cho cùng invariant.

## Quan sát trong production

- Log `MessageId`, `OrderId`, idempotency key, replica/consumer và payment operation state; không log toàn bộ customer/order.
- Metric: redelivery count, duplicate-operation conflict, provider timeout, reconciliation count, payment success/failure/unknown.
- Trace consumer → payment gateway → database với correlation ID.
- Alert khi `Unknown/Pending` tồn tại quá SLA hoặc duplicate-attempt rate tăng.
- Dashboard đối chiếu số payment operations với provider references và paid orders.

## Câu hỏi phỏng vấn mở rộng

1. Tại sao database transaction hoặc distributed lock vẫn không đủ để đảm bảo exactly-once external side effect?
2. Nếu payment provider không hỗ trợ idempotency key, bạn thay đổi workflow thế nào?
3. Outbox pattern giải quyết phần nào của bài toán này và phần nào nó **không** giải quyết?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log: SQL injection, authorization và query không thể scale

**Chủ đề:** SQL correctness/performance, authorization, input validation, sensitive-data exposure, cancellation  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép admin tìm audit log. Bảng `AuditLogs` đã vượt 80 triệu dòng. Mỗi tenant có từ vài nghìn đến hàng triệu record. Endpoint gần đây xuất hiện query chạy hàng chục giây, database CPU tăng mạnh, và security review phát hiện người dùng tenant A có thể thử truyền `tenantId` của tenant B.

Business muốn giữ khả năng lọc theo action và text, nhưng endpoint phải có giới hạn dữ liệu rõ ràng và không được lộ audit log giữa tenant.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        Guid tenantId,
        string? action,
        string? text,
        int page = 1,
        int pageSize = 5000)
    {
        var sql = $@"
            SELECT *
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'
              AND ('{action}' = '' OR Action = '{action}')
              AND ('{text}' = '' OR Message LIKE '%{text}%')
            ORDER BY CreatedAtUtc DESC";

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .ToListAsync();

        var result = rows
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.Action,
                x.Message,
                x.UserEmail,
                x.RequestBody,
                x.CreatedAtUtc
            })
            .ToList();

        _logger.LogInformation(
            "Audit search tenant={TenantId}, action={Action}, text={Text}, rows={Rows}",
            tenantId, action, text, rows.Count);

        return Ok(result);
    }
}
```

## Dừng lại và tự review

## Kết quả code review tham khảo

### 1. Tenant authorization bị giao cho input của client

- **Problem:** User chỉ cần authenticated và có thể tự truyền `tenantId`.
- **Why it happens:** `[Authorize]` xác thực/đòi authenticated principal nhưng code không enforce quyền truy cập tenant cụ thể.
- **Production impact:** Cross-tenant data exposure.
- **Severity:** Critical
- **Recommended fix:** Resolve tenant từ trusted claims/context hoặc authorize resource-specific membership/permission trước query; không coi route/query parameter là authority.

### 2. SQL injection qua `action` và `text`

- **Problem:** User input được nối trực tiếp vào raw SQL.
- **Why it happens:** String interpolation được tạo trước rồi truyền cho `FromSqlRaw`.
- **Production impact:** Có thể thay đổi semantics của query, đọc dữ liệu trái phép hoặc gây hại tùy database privileges.
- **Severity:** Critical
- **Recommended fix:** Ưu tiên LINQ parameterization hoặc parameterized raw SQL API; tuyệt đối không concatenate/interpolate untrusted values vào raw SQL string.

### 3. Fetch toàn bộ rows trước pagination

- **Problem:** `ToListAsync()` materialize tất cả kết quả trước `Skip/Take`.
- **Why it happens:** Pagination chạy trên `List<T>` trong memory.
- **Production impact:** DB I/O, network, memory allocation và latency tăng theo toàn bộ result set; có thể gây memory pressure dưới concurrent load.
- **Severity:** High
- **Recommended fix:** Giữ query là `IQueryable`, áp dụng projection và pagination trước materialization.

### 4. `SELECT *` kéo dữ liệu không cần thiết

- **Problem:** Toàn bộ entity columns được đọc dù response chỉ cần một tập field.
- **Why it happens:** Raw query materialize entity rồi mới project.
- **Production impact:** Tăng DB/network I/O, đặc biệt nếu audit rows chứa payload lớn.
- **Severity:** High
- **Recommended fix:** Project server-side đúng các field được phép trả về.

### 5. Response chứa dữ liệu nhạy cảm quá mức

- **Problem:** `UserEmail` và đặc biệt `RequestBody` được trả mặc định.
- **Why it happens:** Không có explicit data-classification/redaction policy.
- **Production impact:** PII, token hoặc business data trong request payload có thể bị expose cho người không cần biết.
- **Severity:** High
- **Recommended fix:** DTO allow-list; redact/mask sensitive fields; permission riêng nếu cần xem raw payload.

### 6. Page/pageSize không được validate

- **Problem:** `page <= 0`, `pageSize` cực lớn hoặc arithmetic bất hợp lý không được chặn.
- **Why it happens:** Client kiểm soát trực tiếp paging parameters.
- **Production impact:** Resource abuse, lỗi logic và query nặng.
- **Severity:** Medium
- **Recommended fix:** Validate `page >= 1`; giới hạn `pageSize` ở mức business cho phép. Với deep pagination lớn, cân nhắc keyset/cursor pagination.

### 7. `%text%` có thể trở thành search bottleneck

- **Problem:** Contains-style search trên bảng rất lớn có thể khó tận dụng B-tree index thông thường.
- **Why it happens:** Pattern bắt đầu bằng wildcard.
- **Production impact:** Scan nhiều dữ liệu, CPU/I/O tăng khi traffic/search volume tăng.
- **Severity:** Medium
- **Recommended fix:** Xác nhận requirement; nếu substring/full-text search là core feature, dùng search capability phù hợp với SQL Server/PostgreSQL và workload thay vì giả định một index thường sẽ giải quyết.

### 8. Offset pagination có thể đắt và không ổn định khi dữ liệu thay đổi

- **Problem:** Deep `Skip` phải bỏ qua nhiều rows và concurrent inserts có thể làm record dịch trang.
- **Why it happens:** Pagination dựa trên offset.
- **Production impact:** Latency tăng ở page sâu; duplicate/missing rows giữa các request.
- **Severity:** Medium
- **Recommended fix:** Với large ordered dataset, dùng cursor/keyset theo `(CreatedAtUtc, Id)` khi UX cho phép.

### 9. Không propagate request cancellation

- **Problem:** Query không nhận `HttpContext.RequestAborted`/action cancellation token.
- **Why it happens:** `ToListAsync()` gọi không token.
- **Production impact:** Client đã disconnect nhưng expensive query vẫn có thể tiếp tục tiêu thụ tài nguyên.
- **Severity:** Medium
- **Recommended fix:** Nhận `CancellationToken` trong action và truyền vào EF async calls.

### 10. Logging search text có thể ghi dữ liệu nhạy cảm

- **Problem:** Raw `text` được đưa vào log.
- **Why it happens:** Search term được coi là metadata vô hại.
- **Production impact:** PII/secrets có thể bị copy vào centralized logging.
- **Severity:** Medium
- **Recommended fix:** Log normalized metadata như filter-present, tenant, duration, result count; chỉ log search term khi có policy phù hợp.

## Phiên bản code đề xuất

Giả định ứng dụng có `ITenantAccessService` xác định tenant mà principal hiện tại được phép truy cập và audit message được phép trả nhưng raw request body không được trả từ endpoint search.

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private const int MaxPageSize = 100;

    private readonly AppDbContext _db;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AppDbContext db,
        ITenantAccessService tenantAccess,
        ILogger<AuditController> logger)
    {
        _db = db;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize(Policy = "AuditReader")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        Guid tenantId,
        string? action,
        string? text,
        int page = 1,
        int pageSize = 50,
        CancellationToken cancellationToken = default)
    {
        if (page < 1 || pageSize < 1 || pageSize > MaxPageSize)
            return BadRequest("Invalid paging parameters.");

        if (!await _tenantAccess.CanReadAuditAsync(
                User, tenantId, cancellationToken))
            return Forbid();

        var query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(action))
            query = query.Where(x => x.Action == action);

        if (!string.IsNullOrWhiteSpace(text))
            query = query.Where(x => x.Message.Contains(text));

        var result = await query
            .OrderByDescending(x => x.CreatedAtUtc)
            .ThenByDescending(x => x.Id)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new AuditLogDto(
                x.Id,
                x.Action,
                x.Message,
                x.CreatedAtUtc))
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Audit search completed. TenantId={TenantId}, HasAction={HasAction}, HasText={HasText}, ResultCount={ResultCount}",
            tenantId,
            !string.IsNullOrWhiteSpace(action),
            !string.IsNullOrWhiteSpace(text),
            result.Count);

        return Ok(result);
    }
}

public sealed record AuditLogDto(
    long Id,
    string Action,
    string Message,
    DateTime CreatedAtUtc);
```

Đoạn code trên dùng LINQ để EF parameterize values, nhưng `Contains` trên dataset 80 triệu dòng vẫn phải được benchmark trên database thực tế. Với search text là requirement quan trọng, cần thiết kế full-text/search index tương ứng. Với deep navigation, chuyển sang keyset pagination thay vì giữ offset vô hạn.

## Trade-offs

LINQ giúp composability và parameterization nhưng không bảo đảm query tự động nhanh; execution plan và index vẫn phải được đo. Offset pagination đơn giản cho UI có số trang, còn keyset nhanh và ổn định hơn cho feed/audit stream nhưng không hỗ trợ nhảy trực tiếp tới page N dễ dàng. Tách quyền `AuditReader` và raw-payload permission tăng authorization complexity nhưng giảm blast radius của dữ liệu nhạy cảm.

## Cách kiểm thử

1. **Security integration test:** principal của tenant A yêu cầu tenant B phải bị từ chối trước khi dữ liệu được trả.
2. **Injection test:** `action`/`text` chứa quotes và SQL-like payload vẫn chỉ được xử lý như data; kiểm tra generated SQL parameterized.
3. **Database test:** xác nhận `Take`/projection chạy server-side và không materialize toàn bộ result set.
4. **Load test:** benchmark tenant lớn, text search và concurrent requests; theo dõi p95/p99, DB CPU/I/O và allocations.
5. **Cancellation test:** abort request khi query đang chạy và xác nhận cancellation được propagate phù hợp.

## Quan sát trong production

- Metric endpoint latency p50/p95/p99, result count, cancellation, timeout và error rate.
- Database: slow-query log/query store, execution plans, rows read vs rows returned, index usage, lock/wait statistics.
- Trace HTTP request → authorization → EF/database span.
- Security audit cho denied cross-tenant attempts, nhưng không log raw search text/request body nếu không cần.
- Alert khi p95 vượt SLO hoặc database rows-read/result ratio tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Bạn thiết kế keyset pagination với `(CreatedAtUtc, Id)` như thế nào để tránh bỏ sót record có cùng timestamp?
2. SQL Server và PostgreSQL có thể cần chiến lược search/index khác nhau thế nào cho text search?
3. Nếu product bắt buộc cho phép export hàng triệu audit rows, tại sao không nên mở `pageSize` thật lớn trên endpoint này và bạn sẽ thiết kế export flow ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào ranh giới quan trọng giữa **at-least-once delivery** và **exactly-once business effect**. Idempotency phải được thiết kế xuyên qua database invariant và external provider; check-then-act trong application không đủ dưới concurrency, và local transaction không thể rollback side effect ở hệ thống khác.

Challenge 2 nhấn mạnh rằng authentication không thay thế authorization theo resource/tenant. Parameterization, server-side filtering/projection/pagination và data minimization phải được thiết kế cùng nhau; sửa SQL injection nhưng vẫn fetch hàng triệu rows thì endpoint vẫn chưa production-ready.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng idempotency và xử lý **unknown outcome**.
- Đưa invariant quan trọng xuống database bằng constraint/atomic state transition khi có thể.
- Authentication trả lời “ai”, authorization phải trả lời “được làm gì trên resource nào”.
- Filter, project và paginate trước khi materialize; đo execution plan thay vì đoán.
- Xem observability và failure recovery là một phần của design, không phải phần thêm sau.
