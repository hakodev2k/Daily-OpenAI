# Code Review Challenge 1 — Timeout bằng `Task.WhenAny` nhưng request HTTP vẫn chạy ngầm và tích tụ dưới sự cố dependency

**Chủ đề:** async/await và cancellation, HTTP client usage, resource lifetime, failure handling, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cần gọi hệ thống directory bên ngoài để lấy profile nhân viên trước khi trả dữ liệu tổng hợp cho portal nội bộ. Team muốn endpoint không chờ quá 2 giây nên tự viết timeout bằng `Task.WhenAny`.

Bình thường dependency phản hồi trong 100–300 ms. Tuy nhiên khi dependency bị chậm hoặc network có vấn đề, production ghi nhận:

- API trả `504` khá nhanh nhưng số outbound request thực tế vẫn tiếp tục tăng,
- sau vài phút, connection usage và memory tăng rõ rệt,
- dependency phục hồi nhưng API vẫn chậm thêm một thời gian,
- cùng một user retry vài lần có thể tạo nhiều request outbound đang chạy cùng lúc,
- một số `HttpResponseMessage` hoàn thành muộn nhưng không được xử lý hay dispose,
- cancellation khi client đóng trình duyệt không làm giảm đáng kể outbound traffic,
- log chỉ ghi `Directory timeout`, không biết request thật sự bị hủy hay vẫn chạy phía sau,
- p99 của các API khác cùng process cũng tăng khi sự cố kéo dài.

Business yêu cầu endpoint phải có deadline rõ ràng, không được để công việc tiếp tục vô hạn sau khi caller đã bỏ cuộc, và cần phân biệt timeout của ứng dụng với cancellation từ client.

## Đoạn code cần review

```csharp
public sealed class EmployeeDirectoryService
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<EmployeeDirectoryService> _logger;

    public EmployeeDirectoryService(
        HttpClient httpClient,
        ILogger<EmployeeDirectoryService> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<EmployeeDirectoryDto?> GetEmployeeAsync(
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"api/employees/{employeeId}");

        var sendTask = _httpClient.SendAsync(request);
        var timeoutTask = Task.Delay(TimeSpan.FromSeconds(2));

        var completed = await Task.WhenAny(sendTask, timeoutTask);

        if (completed == timeoutTask)
        {
            _logger.LogWarning(
                "Directory timeout for employee {EmployeeId}",
                employeeId);

            return null;
        }

        var response = await sendTask;

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogWarning(
                "Directory returned {StatusCode} for employee {EmployeeId}",
                response.StatusCode,
                employeeId);

            return null;
        }

        var json = await response.Content.ReadAsStringAsync();

        return JsonSerializer.Deserialize<EmployeeDirectoryDto>(json);
    }
}
```

## Kết quả code review tham khảo

### 1. `Task.WhenAny` không hủy `sendTask`

**Problem:** Khi timeout task thắng, method trả `null` nhưng outbound HTTP request vẫn có thể tiếp tục chạy.  
**Why it happens:** `Task.WhenAny` chỉ báo task nào hoàn thành trước; nó không cancel các task còn lại.  
**Production impact:** Khi dependency chậm, request ngầm tích tụ, tiếp tục giữ connection, buffer và các resource liên quan ngay cả khi caller đã nhận `504`/fallback.  
**Severity:** Critical  
**Recommended fix:** Dùng cancellation token có deadline thực sự và truyền token đó vào `SendAsync`.

### 2. Không truyền `cancellationToken` vào `SendAsync`

**Problem:** Caller cancellation không được propagate tới outbound HTTP operation.  
**Why it happens:** Code gọi `_httpClient.SendAsync(request)` mà bỏ qua token nhận từ ASP.NET Core.  
**Production impact:** User đóng browser hoặc reverse proxy hủy request nhưng process vẫn tiếp tục gọi dependency. Dưới tải, đây là wasted work và có thể khuếch đại outage.  
**Severity:** Critical  
**Recommended fix:** Tạo linked token từ caller token và timeout token, rồi truyền vào `SendAsync`.

### 3. `HttpResponseMessage` không được dispose

**Problem:** `response` không nằm trong `using`/`await using`.  
**Why it happens:** Resource lifetime của HTTP response không được quản lý rõ ràng.  
**Production impact:** Có thể giữ resource của response lâu hơn cần thiết, đặc biệt khi nhiều request thất bại hoặc trả payload lớn.  
**Severity:** High  
**Recommended fix:** `using var response = await _httpClient.SendAsync(...)` và tiêu thụ content trong scope đó.

### 4. `HttpRequestMessage` cũng không được dispose

**Problem:** Request object được tạo thủ công nhưng không dispose.  
**Why it happens:** Method không bọc `HttpRequestMessage` trong `using`.  
**Production impact:** Tăng allocation/resource retention không cần thiết trong hot path.  
**Severity:** Medium  
**Recommended fix:** `using var request = new HttpRequestMessage(...)`.

### 5. Timeout và caller cancellation bị gộp thành cùng một kết quả `null`

**Problem:** Method trả `null` cho timeout, HTTP status lỗi và có thể cả các failure khác ở caller layer.  
**Why it happens:** Contract không phân biệt failure semantics.  
**Production impact:** Caller không biết nên retry, trả 404, 503 hay coi là không có employee. Observability cũng khó phân loại.  
**Severity:** High  
**Recommended fix:** Dùng result type/exception mapping rõ ràng: not found, timeout, caller cancelled, dependency unavailable, invalid payload.

### 6. `Task.Delay` không gắn với caller cancellation

**Problem:** Delay 2 giây vẫn sống dù caller đã cancel trước đó.  
**Why it happens:** `Task.Delay(TimeSpan.FromSeconds(2))` không nhận token.  
**Production impact:** Nhỏ ở từng request nhưng tạo thêm timer/task thừa dưới tải lớn.  
**Severity:** Low  
**Recommended fix:** Tốt hơn là bỏ pattern `WhenAny` và dùng `CancellationTokenSource.CancelAfter`; nếu vẫn dùng delay thì truyền token phù hợp.

### 7. Không xử lý riêng `OperationCanceledException`

**Problem:** Khi cải tiến code để dùng cancellation, nếu không phân biệt token nào bị cancel thì timeout và caller abort có thể bị log sai như error.  
**Why it happens:** Thiếu failure classification.  
**Production impact:** Alert noise, metric timeout sai và khó xác định dependency chậm hay user rời trang.  
**Severity:** Medium  
**Recommended fix:** Kiểm tra `cancellationToken.IsCancellationRequested` và timeout token để phân loại rõ.

### 8. `ReadAsStringAsync()` materialize toàn bộ response

**Problem:** Toàn bộ body được đưa vào một string trước khi deserialize.  
**Why it happens:** Dùng API tiện lợi thay vì deserialize từ stream.  
**Production impact:** Với payload lớn hoặc nhiều request đồng thời, allocation tăng không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Dùng `ReadAsStreamAsync` + `JsonSerializer.DeserializeAsync` khi phù hợp, đồng thời giới hạn kích thước payload ở boundary.

### 9. Không có giới hạn retry/concurrency ở cấp workflow

**Problem:** Endpoint trả fallback nhanh nhưng caller hoặc upstream có thể retry ngay lập tức, trong khi request cũ chưa thực sự dừng.  
**Why it happens:** Timeout được thiết kế riêng lẻ mà không xét retry amplification và concurrency budget.  
**Production impact:** Outage của dependency có thể bị khuếch đại thành connection pressure và thread/task pressure ở service gọi nó.  
**Severity:** High  
**Recommended fix:** Thiết kế retry với backoff/jitter, concurrency limit/bulkhead phù hợp và chỉ retry lỗi transient có điều kiện.

### 10. Observability không cho biết operation có bị hủy thật hay không

**Problem:** Chỉ log `Directory timeout`.  
**Why it happens:** Không đo outbound duration, active requests, cancellation reason hay dependency status.  
**Production impact:** Team thấy API timeout nhưng không biết outbound call còn chạy bao lâu sau đó.  
**Severity:** Medium  
**Recommended fix:** Trace outbound span, metric active calls, timeout count, caller-cancel count, dependency latency/status, retry count và saturation.

## Phiên bản code đề xuất

```csharp
public enum DirectoryLookupStatus
{
    Success,
    NotFound,
    Timeout,
    Unavailable
}

public sealed record DirectoryLookupResult(
    DirectoryLookupStatus Status,
    EmployeeDirectoryDto? Employee);

public sealed class EmployeeDirectoryService
{
    private static readonly TimeSpan RequestTimeout = TimeSpan.FromSeconds(2);

    private readonly HttpClient _httpClient;
    private readonly ILogger<EmployeeDirectoryService> _logger;

    public EmployeeDirectoryService(
        HttpClient httpClient,
        ILogger<EmployeeDirectoryService> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<DirectoryLookupResult> GetEmployeeAsync(
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        using var timeoutCts = new CancellationTokenSource(RequestTimeout);
        using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
            cancellationToken,
            timeoutCts.Token);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"api/employees/{employeeId}");

        try
        {
            using var response = await _httpClient.SendAsync(
                request,
                HttpCompletionOption.ResponseHeadersRead,
                linkedCts.Token);

            if (response.StatusCode == HttpStatusCode.NotFound)
            {
                return new(
                    DirectoryLookupStatus.NotFound,
                    null);
            }

            if (!response.IsSuccessStatusCode)
            {
                _logger.LogWarning(
                    "Directory request failed with {StatusCode} for employee {EmployeeId}",
                    response.StatusCode,
                    employeeId);

                return new(
                    DirectoryLookupStatus.Unavailable,
                    null);
            }

            await using var stream = await response.Content
                .ReadAsStreamAsync(linkedCts.Token);

            var employee = await JsonSerializer.DeserializeAsync<EmployeeDirectoryDto>(
                stream,
                cancellationToken: linkedCts.Token);

            return new(
                DirectoryLookupStatus.Success,
                employee);
        }
        catch (OperationCanceledException)
            when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (OperationCanceledException)
            when (timeoutCts.IsCancellationRequested)
        {
            _logger.LogWarning(
                "Directory request timed out for employee {EmployeeId}",
                employeeId);

            return new(
                DirectoryLookupStatus.Timeout,
                null);
        }
        catch (HttpRequestException ex)
        {
            _logger.LogWarning(
                ex,
                "Directory request failed for employee {EmployeeId}",
                employeeId);

            return new(
                DirectoryLookupStatus.Unavailable,
                null);
        }
    }
}
```

> Giả định `HttpClient` được cung cấp qua DI với lifetime/configuration phù hợp. Deadline 2 giây là business/application decision, không phải một con số mặc định đúng cho mọi hệ thống.

## Trade-offs

- `CancellationTokenSource` riêng cho mỗi operation tạo thêm allocation nhỏ nhưng đổi lại deadline rõ ràng và hủy được công việc bên dưới.
- Trả result type giúp caller xử lý semantics rõ hơn, nhưng làm contract application layer phức tạp hơn so với trả `null`.
- `ResponseHeadersRead` giảm khả năng buffer toàn body sớm, nhưng caller phải quản lý response/stream lifetime cẩn thận.
- Concurrency limit/bulkhead có thể bảo vệ service khi dependency lỗi, nhưng nếu đặt quá thấp sẽ giảm throughput lúc dependency khỏe.
- Retry nên rất thận trọng với operation không idempotent; challenge này dùng GET nên retry dễ kiểm soát hơn, nhưng vẫn phải tránh retry storm.

## Cách kiểm thử

1. **Timeout test:** fake dependency giữ connection lâu hơn 2 giây; verify method trả timeout và outbound operation nhận cancellation.
2. **Caller cancellation test:** cancel request sau 100 ms; verify `OperationCanceledException` propagate thay vì bị chuyển thành timeout/fallback.
3. **Load test khi dependency chậm:** hàng trăm request đồng thời; theo dõi active outbound requests và đảm bảo chúng giảm nhanh sau deadline.
4. **Recovery test:** dependency chậm 30 giây rồi phục hồi; verify service không còn backlog request cũ kéo dài thêm nhiều phút.
5. **Failure classification test:** 404, 500, network failure và invalid JSON phải cho kết quả/log khác nhau theo contract.

## Quan sát trong production

- Metric: outbound request duration, active outbound calls, timeout count, caller-cancel count, HTTP status distribution.
- Trace: dependency span với operation name ổn định, employee id chỉ đưa vào log/tracing nếu phù hợp privacy policy.
- Alert theo tỷ lệ timeout và saturation thay vì chỉ số lượng 5xx tuyệt đối.
- Theo dõi connection-pool/handler-related symptoms gián tiếp qua latency, active requests và socket/network errors.
- Log structured phải phân biệt `timeout`, `caller_cancelled`, `dependency_5xx`, `network_error`, `deserialize_error`.

# Code Review Challenge 2 — Cleanup job load hàng triệu row vào memory rồi xóa trong một transaction khổng lồ

**Chủ đề:** EF Core query/update execution, memory và allocation, transaction handling, SQL performance, background jobs, failure recovery, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một Hangfire job chạy mỗi đêm để xóa `AuditLog` cũ hơn thời gian retention. Bảng đã tăng lên hơn 80 triệu record; một đợt cleanup có thể cần xóa từ vài trăm nghìn tới vài triệu row.

Sau một thời gian hệ thống lớn lên, production ghi nhận:

- memory của worker tăng đột biến khi job chạy,
- GC hoạt động nhiều và đôi lúc process bị restart do memory pressure,
- transaction log/database write pressure tăng mạnh,
- query/update khác bị latency cao trong thời gian cleanup,
- khi job chết giữa chừng thì đêm hôm sau lại bắt đầu lại từ đầu mà không biết đã xử lý bao nhiêu,
- một số lần cleanup giữ lock lâu và ảnh hưởng API đọc/ghi audit mới,
- log chỉ có `Deleted N rows` sau khi toàn bộ `SaveChangesAsync` hoàn tất,
- team đề xuất tăng memory limit container để “fix”.

Business chỉ yêu cầu dữ liệu cũ được dọn dần trong một khoảng thời gian hợp lý; không bắt buộc phải xóa toàn bộ trong một transaction duy nhất.

## Đoạn code cần review

```csharp
public sealed class AuditCleanupJob
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditCleanupJob> _logger;

    public AuditCleanupJob(
        AppDbContext db,
        ILogger<AuditCleanupJob> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task RunAsync(
        DateTime retentionCutoffUtc,
        CancellationToken cancellationToken)
    {
        var rows = await _db.AuditLogs
            .Where(x => x.CreatedAt < retentionCutoffUtc)
            .OrderBy(x => x.CreatedAt)
            .ToListAsync(cancellationToken);

        if (rows.Count == 0)
            return;

        _db.AuditLogs.RemoveRange(rows);

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Deleted {Count} audit rows older than {Cutoff}",
            rows.Count,
            retentionCutoffUtc);
    }
}
```

4. Ưu tiên những vấn đề cần sửa trước.

## Kết quả code review tham khảo

### 1. Materialize toàn bộ tập cần xóa vào memory

**Problem:** `ToListAsync` load tất cả row cũ hơn cutoff.  
**Why it happens:** Cleanup được viết như một CRUD operation với assumption tập dữ liệu nhỏ.  
**Production impact:** Với hàng triệu row, memory tăng mạnh, allocation lớn và GC pressure cao; có thể dẫn tới OOM/restart.  
**Severity:** Critical  
**Recommended fix:** Xử lý batch nhỏ theo khóa/order ổn định hoặc dùng set-based delete phù hợp với provider/version sau khi xác minh behavior.

### 2. Change tracker giữ toàn bộ entity tới lúc `SaveChangesAsync`

**Problem:** Tất cả entity được track rồi chuyển sang state `Deleted`.  
**Why it happens:** EF Core change tracking được dùng cho workload maintenance khối lượng lớn.  
**Production impact:** Memory và change detection overhead tăng đáng kể.  
**Severity:** High  
**Recommended fix:** Tránh materialize entity nếu không cần business logic per-row; nếu phải batch entity thì dùng context theo batch nhỏ.

### 3. Một transaction delete quá lớn

**Problem:** `SaveChangesAsync` cố xóa toàn bộ tập trong một unit of work.  
**Why it happens:** Không có batching/commit checkpoint.  
**Production impact:** Transaction kéo dài, write-ahead/transaction log tăng, lock giữ lâu và recovery khi failure tốn kém.  
**Severity:** Critical  
**Recommended fix:** Commit theo batch; chọn batch size dựa trên đo đạc production và database behavior.

### 4. Không có progress checkpoint/resume semantics

**Problem:** Job chỉ log sau khi hoàn thành toàn bộ.  
**Why it happens:** Không có batch progress/cursor.  
**Production impact:** Khi job crash hoặc bị cancel, team không biết đã xóa được bao nhiêu và thời gian còn lại bao lâu.  
**Severity:** High  
**Recommended fix:** Log/metric theo batch; thiết kế idempotent sao cho run sau tiếp tục query phần còn tồn tại.

### 5. Ordering chỉ có `CreatedAt`

**Problem:** Nếu dùng batching/cursor sau này, ordering chỉ theo timestamp chưa đủ deterministic khi nhiều row cùng thời điểm.  
**Why it happens:** Không có tie-breaker duy nhất.  
**Production impact:** Keyset/cursor không chặt có thể lặp hoặc bỏ row ở boundary.  
**Severity:** Medium  
**Recommended fix:** Order theo `(CreatedAt, Id)` hoặc khóa phù hợp khác.

### 6. Cleanup tranh chấp tài nguyên với traffic online

**Problem:** Job không có budget về batch size, pause, concurrency hay execution window.  
**Why it happens:** Maintenance job được phép sử dụng database không giới hạn.  
**Production impact:** API business bị tăng latency dù cleanup “đúng chức năng”.  
**Severity:** High  
**Recommended fix:** Throttle theo batch, đo DB pressure, chạy trong maintenance window nếu phù hợp và ưu tiên workload online.

### 7. Cancellation chỉ hữu ích ở query/SaveChanges lớn, không có checkpoint nhỏ

**Problem:** Một operation rất lớn khiến cancellation granularity kém.  
**Why it happens:** Toàn bộ cleanup là một batch duy nhất.  
**Production impact:** Hoặc job dừng trước commit và lãng phí toàn bộ read/materialization, hoặc phải chờ operation DB lớn kết thúc/abort.  
**Severity:** Medium  
**Recommended fix:** Check cancellation giữa các batch và giữ mỗi batch đủ nhỏ.

### 8. Không giới hạn số row cần xóa mỗi lần chạy

**Problem:** Backlog tăng bao nhiêu thì job cố làm bấy nhiêu trong một run.  
**Why it happens:** Không có operational guardrail.  
**Production impact:** Sau outage vài ngày, lần run kế tiếp có thể trở thành một “thundering cleanup” gây sự cố lớn hơn.  
**Severity:** High  
**Recommended fix:** Có max rows/max duration per run hoặc adaptive budget tùy yêu cầu vận hành.

### 9. Không có observability về backlog age và throughput

**Problem:** Chỉ có count sau cùng.  
**Why it happens:** Không coi retention lag là một SLO vận hành.  
**Production impact:** Không biết cleanup đang theo kịp tốc độ sinh audit hay backlog đang tăng.  
**Severity:** Medium  
**Recommended fix:** Metric backlog count/oldest retained age, rows deleted per batch, duration, cancellation, failure và DB pressure correlation.

### 10. Tăng memory limit chỉ che triệu chứng

**Problem:** Giải pháp được đề xuất là tăng RAM container mà không thay thuật toán.  
**Why it happens:** Nhầm resource shortage với root cause scalability.  
**Production impact:** Chi phí tăng nhưng sự cố sẽ quay lại khi data lớn hơn.  
**Severity:** Medium  
**Recommended fix:** Giảm working set theo thiết kế; chỉ tăng memory sau khi đã đo và vẫn cần headroom hợp lý.

## Phiên bản code đề xuất

```csharp
public sealed class AuditCleanupJob
{
    private const int BatchSize = 2_000;
    private const int MaxBatchesPerRun = 100;

    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<AuditCleanupJob> _logger;

    public AuditCleanupJob(
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<AuditCleanupJob> logger)
    {
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task RunAsync(
        DateTime retentionCutoffUtc,
        CancellationToken cancellationToken)
    {
        var totalDeleted = 0;

        for (var batchNumber = 1;
             batchNumber <= MaxBatchesPerRun;
             batchNumber++)
        {
            cancellationToken.ThrowIfCancellationRequested();

            await using var db = await _dbFactory.CreateDbContextAsync(
                cancellationToken);

            var ids = await db.AuditLogs
                .AsNoTracking()
                .Where(x => x.CreatedAt < retentionCutoffUtc)
                .OrderBy(x => x.CreatedAt)
                .ThenBy(x => x.Id)
                .Select(x => x.Id)
                .Take(BatchSize)
                .ToListAsync(cancellationToken);

            if (ids.Count == 0)
                break;

            var deleted = await db.AuditLogs
                .Where(x => ids.Contains(x.Id))
                .ExecuteDeleteAsync(cancellationToken);

            totalDeleted += deleted;

            _logger.LogInformation(
                "Audit cleanup batch {BatchNumber} deleted {DeletedCount} rows; total {TotalDeleted}; cutoff {Cutoff}",
                batchNumber,
                deleted,
                totalDeleted,
                retentionCutoffUtc);

            if (deleted == 0)
                break;
        }

        _logger.LogInformation(
            "Audit cleanup completed with {TotalDeleted} rows deleted for cutoff {Cutoff}",
            totalDeleted,
            retentionCutoffUtc);
    }
}
```

> `ExecuteDeleteAsync` chỉ nên dùng khi project đang ở EF Core version/provider hỗ trợ semantics mong muốn và khi không cần chạy domain logic/per-entity hooks ở application layer. Nếu không phù hợp, có thể delete theo batch bằng SQL/provider-specific command hoặc attach entity stub theo batch nhỏ.

## Trade-offs

- Batch nhỏ giảm lock duration và memory nhưng tăng số round-trip.
- Batch quá lớn cho throughput cao hơn nhưng tăng transaction/log pressure; không có một con số batch tối ưu cho mọi hệ thống.
- `ExecuteDeleteAsync` hiệu quả vì tránh tracking entity, nhưng bypass logic application-level thường gắn với từng entity; cần xác nhận audit cleanup không cần behavior đó.
- Giới hạn `MaxBatchesPerRun` bảo vệ database nhưng có thể làm retention lag tăng nếu tốc độ insert cao hơn tốc độ cleanup; phải monitor backlog.
- Có thể partition bảng audit theo thời gian để retention bằng partition-level maintenance nếu quy mô đủ lớn, nhưng đó là quyết định kiến trúc/database phức tạp hơn và không cần thiết cho mọi hệ thống.

## Cách kiểm thử

1. **Large-data integration test:** seed hàng trăm nghìn row cũ + mới; verify chỉ row trước cutoff bị xóa và memory không tăng theo toàn bộ dataset.
2. **Cancellation test:** cancel sau vài batch; verify batch đã commit vẫn giữ nguyên và run sau tiếp tục an toàn.
3. **Concurrent-write test:** trong lúc cleanup, liên tục insert audit mới; verify dữ liệu mới không bị xóa và API latency vẫn trong budget mong muốn.
4. **Boundary test:** nhiều row có cùng `CreatedAt` sát cutoff; verify ordering/filter không bỏ sót hoặc xóa nhầm.
5. **Failure/restart test:** giả lập crash sau batch N; chạy lại và verify cleanup tiếp tục idempotent từ phần còn lại.

## Quan sát trong production

- Metric: rows deleted/run, rows deleted/second, batch duration, cleanup failures/cancellations.
- Metric backlog: số row quá retention và tuổi của row cũ nhất còn tồn tại.
- Database observation: transaction duration, lock waits, log/write pressure, query duration và impact lên latency workload online.
- Trace mỗi batch thay vì một span khổng lồ cho toàn bộ job nếu tracing system hỗ trợ.
- Alert khi retention backlog tăng liên tục nhiều run hoặc cleanup duration vượt maintenance budget.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển từ batch delete sang table partitioning theo thời gian?
2. Nếu audit data có legal hold và một số tenant không được xóa theo retention chung, bạn thay đổi query/data model thế nào?
3. Nếu database replica phục vụ báo cáo nhưng cleanup chạy trên primary, bạn theo dõi ảnh hưởng replication lag ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Timeout ở application layer chỉ có ý nghĩa đầy đủ khi operation bên dưới nhận cancellation; ngừng `await` không đồng nghĩa với hủy công việc.
- HTTP failure handling cần quản lý vòng đời request/response, phân biệt timeout với caller cancellation và tránh retry amplification.
- Maintenance job trên bảng lớn phải có working set giới hạn, batching, checkpoint và operational budget.
- EF Core tracking phù hợp với nhiều CRUD workflow nhưng không phải lựa chọn mặc định tốt cho bulk maintenance hàng triệu row.
- Observability nên đo saturation, backlog và failure semantics thay vì chỉ log một dòng “timeout” hoặc “deleted N rows”.

## Mẫu tư duy cần nhớ

- Propagate cancellation tới dependency, không chỉ dừng chờ ở caller.
- Thiết kế timeout cùng retry, concurrency budget và failure classification.
- Giới hạn working set trước khi nghĩ tới tăng memory.
- Chia maintenance workload thành batch có thể retry/resume.
- Treat observability as part of the design.
