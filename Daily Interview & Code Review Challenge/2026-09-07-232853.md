# Code Review Challenge 1 — CRM integration retry POST làm tạo customer trùng và connection usage tăng vọt dưới load

**Chủ đề:** C#/.NET, ASP.NET Core, HttpClient, third-party API integration, retries, idempotency, timeout, cancellation, rate limiting, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 API tích hợp với external CRM để tạo customer profile sau khi user hoàn tất registration.

Flow hiện tại:

- API nhận registration request;
- application lưu user vào SQL Server;
- gọi CRM `POST /customers` để tạo profile tương ứng;
- CRM trả `201 Created` khi thành công;
- CRM đôi khi trả `429`, `500`, `502`, `503`;
- network có thể timeout ngay cả khi CRM đã nhận và commit request;
- CRM có hỗ trợ idempotency key nhưng implementation hiện tại chưa dùng;
- production chạy 6 Azure App Service instances;
- traffic peak khoảng vài trăm registration/phút;
- CRM có rate limit theo account;
- API phải giữ p95 latency hợp lý và không được tạo duplicate CRM customer;
- nếu CRM tạm thời unavailable, business chấp nhận trạng thái `PendingSync` để xử lý sau thay vì làm registration thất bại hoàn toàn.

Production gần đây ghi nhận:

- cùng một user đôi khi có 2–3 customer records trên CRM;
- outbound connection count tăng mạnh trong traffic spike;
- CRM trả nhiều `429` hơn sau khi application tự động retry;
- một số request giữ connection lâu rồi trả 500;
- client cancel registration nhưng backend vẫn tiếp tục retry CRM;
- logs chứa access token và một phần response body có email/phone;
- support không biết một CRM customer được tạo bởi registration attempt nào;
- khi CRM trả `400`, code vẫn retry ba lần;
- khi CRM trả `401`, code tiếp tục retry với cùng token;
- team đề xuất tăng số lần retry lên 10 để “tăng reliability”.

## Đoạn code cần review

```csharp
public sealed class CrmCustomerService
{
    private readonly IConfiguration _configuration;
    private readonly ILogger<CrmCustomerService> _logger;

    public CrmCustomerService(
        IConfiguration configuration,
        ILogger<CrmCustomerService> logger)
    {
        _configuration = configuration;
        _logger = logger;
    }

    public async Task<string?> CreateCustomerAsync(
        Registration registration,
        CancellationToken cancellationToken)
    {
        var baseUrl = _configuration["Crm:BaseUrl"]!;
        var accessToken = _configuration["Crm:AccessToken"]!;

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                var client = new HttpClient();
                client.BaseAddress = new Uri(baseUrl);
                client.DefaultRequestHeaders.Authorization =
                    new AuthenticationHeaderValue("Bearer", accessToken);

                var payload = JsonSerializer.Serialize(new
                {
                    registration.UserId,
                    registration.Email,
                    registration.Phone,
                    registration.FullName
                });

                var response = await client.PostAsync(
                    "/customers",
                    new StringContent(
                        payload,
                        Encoding.UTF8,
                        "application/json"),
                    CancellationToken.None);

                var body = await response.Content.ReadAsStringAsync();

                _logger.LogInformation(
                    "CRM attempt {Attempt}. Token={Token}. Status={Status}. Body={Body}",
                    attempt,
                    accessToken,
                    (int)response.StatusCode,
                    body);

                if (response.IsSuccessStatusCode)
                {
                    using var json = JsonDocument.Parse(body);
                    return json.RootElement
                        .GetProperty("customerId")
                        .GetString();
                }
            }
            catch (Exception ex)
            {
                _logger.LogWarning(
                    ex,
                    "CRM create customer failed on attempt {Attempt}",
                    attempt);
            }

            await Task.Delay(TimeSpan.FromSeconds(1));
        }

        return null;
    }
}
```

## Kết quả code review tham khảo

### Critical — Retry `POST /customers` không có idempotency key có thể tạo duplicate customer

**Vấn đề:**  
Mỗi retry gửi lại một create command mới nhưng request không có stable idempotency identifier.

**Tại sao xảy ra:**  
Network failure không nói cho caller biết chắc remote side effect có xảy ra hay chưa. CRM có thể đã commit customer rồi connection bị reset hoặc response timeout trước khi application nhận được `201`.

**Ảnh hưởng production:**  
Retry có thể tạo customer thứ hai hoặc thứ ba cho cùng registration. Duplicate này là distributed-systems correctness problem, không phải chỉ là HTTP retry configuration.

**Cách sửa:**  
Nếu CRM hỗ trợ idempotency key, tạo một stable key gắn với registration, ví dụ `registration:{RegistrationId}`, và tái sử dụng **cùng key** cho mọi retry của cùng logical operation. Persist key cùng registration để retry sau restart/deploy vẫn dùng đúng identity.

Nếu provider không hỗ trợ idempotency, cần một reconciliation strategy khác, ví dụ external reference unique theo registration rồi lookup trước/after ambiguous failure. Không được tự tuyên bố exactly-once nếu remote contract không hỗ trợ.

---

### High — Tạo `HttpClient` cho mỗi attempt làm mất lợi ích connection pooling

**Vấn đề:**  
`new HttpClient()` được tạo trong vòng retry.

**Tại sao xảy ra:**  
Mỗi client có connection management riêng nếu tự tạo với handler riêng. Dưới request rate cao, tạo và hủy nhiều clients/connections có thể gây connection churn và port/resource pressure.

**Ảnh hưởng production:**  
Outbound connections tăng, latency kết nối tăng và instance có thể gặp resource exhaustion dưới load.

**Cách sửa:**  
Dùng `IHttpClientFactory`/typed client hoặc một long-lived client được cấu hình đúng lifetime. Với application hiện tại, typed `ICrmClient` là lựa chọn dễ quản lý vì cần base address, timeout, auth và telemetry riêng cho CRM.

---

### High — Retry mọi HTTP failure cùng một cách

**Vấn đề:**  
Code retry sau bất kỳ non-success response nào.

**Tại sao xảy ra:**  
HTTP status semantics không được phân loại.

**Ảnh hưởng production:**  
`400` validation error bị gửi lại vô ích; `401` với credential invalid tiếp tục dùng cùng token; `429` bị retry đồng loạt sau 1 giây; một số `5xx` transient lại cần bounded retry/backoff.

**Cách sửa:**  
Phân loại failure:

- `400`/validation: permanent cho request hiện tại, không retry tự động;
- `401`/`403`: xử lý identity/token/configuration, không blind retry cùng credential;
- `429`: tôn trọng provider retry guidance nếu có và áp dụng bounded backoff/jitter;
- selected `5xx`, connection reset, transient timeout: có thể retry nếu operation idempotent;
- unknown/ambiguous failure: chỉ retry khi idempotency semantics đủ an toàn.

---

### High — Fixed retry delay tạo synchronized retry storm

**Vấn đề:**  
Mọi instance chờ đúng một giây rồi thử lại.

**Tại sao xảy ra:**  
Không có exponential backoff/jitter hoặc rate-limit coordination.

**Ảnh hưởng production:**  
Khi CRM degrade hoặc trả `429`, hàng trăm requests trên nhiều instances có thể retry cùng lúc, làm dependency quá tải hơn và kéo dài incident.

**Cách sửa:**  
Dùng bounded exponential backoff với jitter và tôn trọng `Retry-After` khi provider contract hỗ trợ. Đồng thời giới hạn outbound concurrency theo capacity/rate limit thay vì chỉ dựa vào số App Service instances.

---

### High — Caller cancellation bị bỏ qua trong CRM call và retry delay

**Vấn đề:**  
Method nhận `CancellationToken` nhưng dùng `CancellationToken.None`; `Task.Delay` cũng không nhận token.

**Tại sao xảy ra:**  
Request lifecycle không được propagate xuống dependency call.

**Ảnh hưởng production:**  
Client đã cancel nhưng application vẫn giữ outbound work và có thể tạo CRM side effect không còn cần thiết. Khi shutdown/deploy, work khó dừng có kiểm soát.

**Cách sửa:**  
Truyền token vào `SendAsync`/delay khi synchronous flow còn tồn tại. Tuy nhiên cancellation không giải quyết ambiguity sau khi remote side effect đã xảy ra; idempotency vẫn bắt buộc.

---

### High — Không có timeout budget phù hợp với request SLO

**Vấn đề:**  
Code dùng client mặc định mà không thiết kế timeout theo CRM dependency và end-to-end registration latency.

**Tại sao xảy ra:**  
Dependency timeout không được xem như một phần của API latency budget.

**Ảnh hưởng production:**  
Một CRM call chậm cộng nhiều retries có thể giữ request rất lâu, tăng concurrent in-flight requests và tail latency.

**Cách sửa:**  
Đặt timeout có chủ đích ở typed client/resilience layer và đảm bảo tổng retry budget nhỏ hơn business request budget. Nếu business cho phép `PendingSync`, tốt hơn là không giữ registration request chờ một dependency chậm.

---

### High — Access token bị log trực tiếp

**Vấn đề:**  
Bearer token được ghi structured log.

**Tại sao xảy ra:**  
Credential bị dùng như diagnostic field.

**Ảnh hưởng production:**  
Token có thể xuất hiện trong Application Insights/Kibana và mở rộng quyền truy cập CRM cho người có quyền đọc logs.

**Cách sửa:**  
Không log token. Dùng Managed Identity/secret store phù hợp khi integration contract cho phép; nếu vẫn dùng secret/token, quản lý qua secure configuration/Key Vault và redaction. Log token acquisition outcome chứ không log credential value.

---

### High — Response body có thể chứa PII nhưng bị log toàn bộ

**Vấn đề:**  
Response body được log cho mọi attempt.

**Tại sao xảy ra:**  
Raw remote payload bị coi là diagnostic data an toàn.

**Ảnh hưởng production:**  
Email, phone, customer fields hoặc remote error details có thể bị lưu lâu trong centralized logging.

**Cách sửa:**  
Log status, dependency duration, provider request ID, safe error code và correlation ID. Chỉ log body đã redacted khi thật sự cần và phù hợp data policy.

---

### High — Synchronous CRM call nằm trên critical registration path dù business chấp nhận `PendingSync`

**Vấn đề:**  
Registration request chờ CRM create + retries rồi mới trả response.

**Tại sao xảy ra:**  
Workflow coupling không phản ánh business requirement hiện tại.

**Ảnh hưởng production:**  
CRM outage kéo trực tiếp registration latency/error rate lên dù core user record có thể lưu thành công.

**Cách sửa:**  
Nếu requirement thực sự cho phép eventual synchronization, transaction tạo registration + durable `CrmSyncOutbox`/pending record; trả trạng thái `PendingSync`; background worker xử lý CRM với idempotency, retry và reconciliation.

---

### Medium — `HttpResponseMessage` không được dispose rõ ràng

**Vấn đề:**  
`response` không nằm trong `using`/`using var`.

**Tại sao xảy ra:**  
Resource lifetime không explicit.

**Ảnh hưởng production:**  
Response content/connection reuse có thể bị ảnh hưởng nếu response lifecycle không được hoàn tất đúng trong các code paths phức tạp hơn.

**Cách sửa:**  
Dispose response deterministically sau khi đọc dữ liệu cần thiết. Với payload lớn, cân nhắc `ResponseHeadersRead` và bounded streaming thay vì buffer toàn bộ response.

---

### Medium — Không có stable correlation giữa registration và CRM request

**Vấn đề:**  
Support không thể map CRM customer về exact registration attempt.

**Tại sao xảy ra:**  
Request không gửi/persist external correlation ID hoặc idempotency key.

**Ảnh hưởng production:**  
RCA duplicate và reconciliation tốn nhiều thời gian.

**Cách sửa:**  
Persist `RegistrationId`, `IdempotencyKey`, provider request ID, attempt count, last error category và CRM customer ID.

## Phiên bản đề xuất

Ví dụ dưới đây giả định CRM hỗ trợ header `Idempotency-Key` và application chuyển CRM synchronization ra background workflow.

Registration transaction:

```csharp
public async Task<Registration> RegisterAsync(
    RegisterRequest request,
    CancellationToken cancellationToken)
{
    await using var tx = await _db.Database.BeginTransactionAsync(
        cancellationToken);

    var registration = Registration.Create(request);

    _db.Registrations.Add(registration);
    _db.CrmSyncOutbox.Add(new CrmSyncOutbox
    {
        Id = Guid.NewGuid(),
        RegistrationId = registration.Id,
        IdempotencyKey = $"registration:{registration.Id:N}",
        Status = CrmSyncStatus.Pending,
        CreatedUtc = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(cancellationToken);
    await tx.CommitAsync(cancellationToken);

    return registration;
}
```

Typed CRM client:

```csharp
public sealed class CrmClient : ICrmClient
{
    private readonly HttpClient _httpClient;
    private readonly ICrmTokenProvider _tokenProvider;
    private readonly ILogger<CrmClient> _logger;

    public CrmClient(
        HttpClient httpClient,
        ICrmTokenProvider tokenProvider,
        ILogger<CrmClient> logger)
    {
        _httpClient = httpClient;
        _tokenProvider = tokenProvider;
        _logger = logger;
    }

    public async Task<CrmCreateResult> CreateCustomerAsync(
        Registration registration,
        string idempotencyKey,
        CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(
            HttpMethod.Post,
            "customers");

        request.Headers.Authorization =
            new AuthenticationHeaderValue(
                "Bearer",
                await _tokenProvider.GetTokenAsync(cancellationToken));

        request.Headers.TryAddWithoutValidation(
            "Idempotency-Key",
            idempotencyKey);

        request.Content = JsonContent.Create(new
        {
            registration.UserId,
            registration.Email,
            registration.Phone,
            registration.FullName
        });

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.TooManyRequests)
        {
            return CrmCreateResult.RateLimited(
                response.Headers.RetryAfter);
        }

        if (response.StatusCode is HttpStatusCode.BadRequest)
        {
            return CrmCreateResult.PermanentFailure("InvalidRequest");
        }

        if (response.StatusCode is HttpStatusCode.Unauthorized
            or HttpStatusCode.Forbidden)
        {
            return CrmCreateResult.AuthenticationFailure();
        }

        if (!response.IsSuccessStatusCode)
        {
            return CrmCreateResult.TransientOrUnknown(
                (int)response.StatusCode);
        }

        var payload = await response.Content
            .ReadFromJsonAsync<CrmCustomerResponse>(
                cancellationToken: cancellationToken);

        return payload?.CustomerId is { Length: > 0 } customerId
            ? CrmCreateResult.Success(customerId)
            : CrmCreateResult.PermanentFailure("InvalidSuccessPayload");
    }
}
```

Background worker cần:

- claim một bounded batch `Pending` records;
- giới hạn concurrency;
- reuse cùng `IdempotencyKey`;
- phân loại retryable vs permanent errors;
- dùng exponential backoff + jitter;
- honor provider retry guidance khi phù hợp;
- persist attempt count/next attempt/error category;
- mark registration `Completed` khi CRM success;
- có reconciliation path cho ambiguous outcomes.

## Giải thích thiết kế sau khi sửa

### 1. Retry được tách khỏi business identity

Một logical create operation có một stable idempotency key dù có bao nhiêu transport attempts.

### 2. Registration không còn phụ thuộc availability của CRM

Core transaction commit local durable work rồi CRM sync diễn ra độc lập nếu business cho phép eventual consistency.

### 3. HttpClient lifetime được quản lý có chủ đích

Typed client/IHttpClientFactory cung cấp connection handler reuse và một nơi tập trung cấu hình timeout, auth, telemetry và resilience.

### 4. Retry policy dựa trên failure semantics

Không retry mọi lỗi. Permanent client errors, authentication errors, rate limits và transient server/network failures cần xử lý khác nhau.

### 5. Security/observability tách khỏi raw payload

Telemetry dùng safe IDs, durations và error categories thay vì token/PII.

## Trade-offs

- Outbox/background sync tăng schema và operational complexity nhưng giảm coupling với external CRM.
- Eventual consistency nghĩa là user có thể tồn tại local trước khi CRM customer xuất hiện; UI/support phải hiểu trạng thái `PendingSync`.
- Idempotency key chỉ hữu ích nếu provider thực thi semantics phù hợp; cần xác minh contract CRM.
- Giới hạn concurrency có thể giảm peak throughput nhưng bảo vệ provider rate limit và stability.
- Retry ít hơn có thể làm một số sync hoàn tất chậm hơn nhưng tránh retry storm và duplicate side effects.

## Cách kiểm thử

1. **Ambiguous network failure test:** CRM commit create nhưng response bị drop; retry cùng idempotency key không tạo duplicate.
2. **Rate-limit integration test:** nhiều `429` liên tiếp; worker backoff đúng, không tạo retry storm và không vượt concurrency policy.
3. **Permanent error test:** `400` không retry vô hạn; record chuyển trạng thái cần manual/fix path.
4. **Authentication failure test:** `401` không blind retry với cùng invalid credential; telemetry/alert phân loại đúng.
5. **Load test:** nhiều App Service/worker instances cùng sync; đo outbound connections, CRM request rate, p95/p99, pending age và duplicate rate.

## Quan sát trong production

Theo dõi:

- CRM dependency request count, duration p50/p95/p99;
- status-code distribution;
- `429` rate và retry delay;
- retry count theo error category;
- outbound connection/socket metrics phù hợp;
- in-flight CRM request count;
- `PendingSync` count và oldest pending age;
- success/failure rate theo attempt;
- duplicate/idempotency replay count;
- provider request/correlation ID;
- authentication/token acquisition failures;
- background worker instance/deployment version;
- alert khi CRM latency/error hoặc pending backlog vượt baseline.

# Code Review Challenge 2 — Kubernetes rollout khiến .NET pods restart liên tục khi SQL chậm và release không reproducible

**Chủ đề:** Kubernetes, Deployment, readiness/liveness/startup probes, resource requests/limits, Secrets, graceful shutdown, rolling deployment, immutable artifacts, production observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 API đang được migrate từ Azure App Service sang Kubernetes như một hosting option mới.

Ứng dụng:

- có 4 replicas;
- startup thường mất 20–40 giây vì load configuration, warm local cache và initialize một số SDK clients;
- endpoint `/health` hiện check cả process, SQL Server, Redis và external pricing API;
- endpoint `/ready` chỉ check application startup state và SQL connectivity;
- request thông thường mất dưới 1 giây, nhưng một số report request có thể kéo dài 10–20 giây;
- application hỗ trợ graceful shutdown qua ASP.NET Core host;
- production image được build bởi CI và đẩy vào private registry;
- database/Redis đôi lúc có degradation ngắn 10–30 giây;
- team muốn rolling deployment không tạo noticeable downtime.

Production test cluster ghi nhận:

- khi SQL Server chậm 15 giây, nhiều pods bị restart gần như cùng lúc;
- trong deploy, một số requests nhận 502/connection reset;

## Nhiệm vụ của ứng viên

Hãy review manifest và operational design như một Senior application engineer đang chịu trách nhiệm production rollout, không phải như một Kubernetes platform specialist.

Bạn cần:

1. phân tích readiness/liveness semantics hiện tại;
2. giải thích vì sao dependency degradation có thể gây restart cascade;
3. phân tích startup behavior;
4. đánh giá `terminationGracePeriodSeconds` so với request duration/graceful shutdown;
5. đánh giá rolling deployment settings;
6. phân tích image tag `latest` và artifact reproducibility;
7. đánh giá secret/configuration handling;
8. phân tích absence của CPU/memory requests/limits;
9. đề xuất corrected Deployment configuration;
10. giải thích application health endpoints nên kiểm tra gì;
11. đề xuất deployment validation/rollback strategy;
12. giải thích telemetry cần có để phân biệt application failure và orchestration behavior.

## Câu hỏi gợi mở

1. Nếu `/health` fail chỉ vì SQL Server chậm, Kubernetes nên restart process hay tạm ngừng gửi traffic tới pod?
2. Với startup 20–40 giây nhưng liveness bắt đầu sau 5 giây, pod mới có thể trải qua lifecycle nào?
3. `pricing-api:latest` có đảm bảo rollback lấy đúng binary của release trước không?
4. `terminationGracePeriodSeconds: 5` có đủ cho request dài 10–20 giây không?
5. Nếu không có resource requests, scheduler có thông tin gì để reserve CPU/memory phù hợp cho pod?

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc SQL/Redis/external API nên dependency outage có thể restart pod khỏe mạnh

**Vấn đề:**  
`livenessProbe` gọi `/health`, trong khi `/health` check nhiều remote dependencies.

**Tại sao xảy ra:**  
Liveness đang trả lời câu hỏi “toàn bộ dependency graph có healthy không?” thay vì “process/container có bị kẹt đến mức cần restart không?”.

**Ảnh hưởng production:**  
SQL hoặc external API degradation có thể làm nhiều pods fail liveness cùng lúc. Kubelet restart các containers dù restart không sửa được dependency, khiến capacity giảm thêm và có thể tạo cascading failure.

**Cách sửa:**  
Tạo liveness endpoint chi phí thấp, chỉ fail khi application process không thể tiếp tục phục vụ hợp lý. Dependency readiness có thể nằm trong readiness endpoint nếu dependency đó thật sự bắt buộc để pod nhận traffic.

---

### Critical — Startup chậm nhưng không có `startupProbe`

**Vấn đề:**  
Liveness bắt đầu sau 5 giây trong khi startup bình thường có thể 20–40 giây.

**Tại sao xảy ra:**  
Manifest giả định application sẵn sàng rất sớm.

**Ảnh hưởng production:**  
Pod có thể bị kill/restart trước khi hoàn tất initialization và rơi vào restart loop, đặc biệt khi node/SQL/registry đang chậm.

**Cách sửa:**  
Dùng `startupProbe` với failure window đủ cho measured startup distribution. Khi startup probe tồn tại, liveness/readiness được bảo vệ khỏi chạy như bình thường trước khi startup probe thành công. Giá trị threshold phải dựa trên observed startup time, không copy từ ví dụ.

---

### High — Readiness dùng endpoint dependency-heavy giống liveness

**Vấn đề:**  
Readiness cũng gọi `/health`, bao gồm external pricing API và Redis dù requirement cho biết `/ready` đã tồn tại và semantics khác.

**Tại sao xảy ra:**  
Health endpoint không được chia theo orchestration intent.

**Ảnh hưởng production:**  
Một optional/degradable dependency có thể làm toàn bộ pods `NotReady`, loại hết traffic khỏi Service dù API vẫn có thể phục vụ một phần chức năng hoặc fallback.

**Cách sửa:**  
Dùng `/ready` và chỉ include dependencies bắt buộc để xử lý traffic. Nếu SQL là mandatory thì readiness có thể fail khi SQL unavailable; nếu Redis/pricing API có fallback, không nên mặc định làm pod NotReady. Phải quyết định dựa trên business behavior.

---

### High — `latest` + `imagePullPolicy: Always` phá artifact reproducibility

**Vấn đề:**  
Deployment reference một mutable tag.

**Tại sao xảy ra:**  
Cùng manifest có thể resolve tới image khác theo thời điểm registry tag được cập nhật.

**Ảnh hưởng production:**  
Rollback/restart có thể kéo binary khác với binary đã được test cho release đó. Incident investigation khó chứng minh exact artifact đang chạy.

**Cách sửa:**  
Deploy immutable version tag gắn build/commit hoặc tốt hơn image digest. Record image digest trong release metadata và telemetry.

---

### High — Secret nằm trực tiếp trong Deployment YAML

**Vấn đề:**  
Database password được commit như plain manifest value.

**Tại sao xảy ra:**  
Configuration và secret management không tách boundary.

**Ảnh hưởng production:**  
Credential có thể xuất hiện trong Git history, PR, CI logs hoặc bất kỳ nơi nào manifest được copy.

**Cách sửa:**  
Dùng Kubernetes Secret hoặc external secret provider/vault integration phù hợp với platform. Giới hạn RBAC và tránh log/render secret. Chỉ chuyển sang một Secret object không tự động giải quyết encryption/rotation/access control; cần thiết kế secret lifecycle đầy đủ.

---

### High — Termination grace quá ngắn so với request duration

**Vấn đề:**  
Pod chỉ có 5 giây để shutdown trong khi request hợp lệ có thể chạy 10–20 giây.

**Tại sao xảy ra:**  
Termination policy không dựa trên application behavior.

**Ảnh hưởng production:**  
Trong rollout/scale-down, in-flight requests có thể bị cắt giữa chừng và client thấy connection reset/502.

**Cách sửa:**  
Đặt grace period dựa trên measured shutdown/request duration và đảm bảo ASP.NET Core nhận termination signal để stop accepting new work rồi drain work đang chạy. Với long-running requests, cân nhắc bounded cancellation/resumable design thay vì chỉ tăng grace vô hạn.

---

### High — Không có resource requests nên scheduler không có capacity signal phù hợp

**Vấn đề:**  
Container không khai báo CPU/memory requests.

**Tại sao xảy ra:**  
Workload resource envelope chưa được model.

**Ảnh hưởng production:**  
Scheduler có thể đặt pods trên node mà không reserve capacity phản ánh nhu cầu. Dưới contention, latency trở nên khó dự đoán.

**Cách sửa:**  
Đo CPU/memory under representative load rồi đặt requests phù hợp. Limits cần được cân nhắc riêng: memory limit quá thấp có thể dẫn tới termination/OOM behavior; CPU limit quá chặt có thể tăng throttling/tail latency. Không copy arbitrary values.

---

### High — Rolling strategy chưa được đánh giá cùng readiness và capacity

**Vấn đề:**  
`maxUnavailable: 1`/`maxSurge: 1` có vẻ hợp lý nhưng không đủ đảm bảo zero noticeable downtime khi readiness sai và capacity không reserve.

**Tại sao xảy ra:**  
Rollout safety là interaction giữa strategy, probes, startup time, capacity và application compatibility.

**Ảnh hưởng production:**  
Pod cũ có thể bị giảm trước khi pod mới thực sự stable; pod mới restart do liveness; effective serving capacity giảm nhanh.

**Cách sửa:**  
Xác minh required minimum serving capacity. Với workload 4 replicas, có thể chọn `maxUnavailable: 0` nếu cluster có surge capacity và business cần tránh mất capacity, nhưng đây là trade-off chứ không phải mặc định. Quan trọng hơn là readiness chính xác, startup probe và đủ node capacity.

---

### Medium — Không có explicit rollout/availability guard như `minReadySeconds`

**Vấn đề:**  
Pod vừa Ready có thể được coi stable ngay cho rollout progression.

**Tại sao xảy ra:**  
Manifest không yêu cầu một khoảng Ready ổn định trước khi tiếp tục rollout.

**Ảnh hưởng production:**  
Một pod mới chỉ healthy trong thời gian rất ngắn rồi fail có thể vẫn làm deployment tiến quá nhanh.

**Cách sửa:**  
Cân nhắc `minReadySeconds` khi workload cần observation window ngắn trước progression. Giá trị phải dựa trên startup/regression patterns và không thay thế canary/smoke testing.

---

### Medium — Health checks chưa gắn với telemetry để giải thích restart reason

**Vấn đề:**  
Hiện không có metric/log correlation giữa probe failures, pod lifecycle và application dependency state.

**Tại sao xảy ra:**  
Observability dừng ở application logs.

**Ảnh hưởng production:**  
Support khó phân biệt crash, liveness failure, OOM, scheduling pressure, rollout termination hoặc dependency outage.

**Cách sửa:**  
Kết hợp application telemetry với Kubernetes events/container restart count/reason, probe failure logs, resource metrics, deployment revision/image digest và dependency telemetry.

Application health semantics tham khảo:

```text
/live
- process/event loop/runtime còn hoạt động
- không check remote dependency transient
- fail khi process ở trạng thái không thể tự phục hồi ngoài restart

/ready
- application initialization hoàn tất
- check dependency bắt buộc để nhận request
- không fail chỉ vì optional dependency đang degrade nếu application có fallback hợp lệ
```

Deployment flow nên gồm:

1. build immutable image once;
2. scan/test artifact;
3. deploy exact digest vào non-production/staging environment;
4. run API/smoke tests;
5. rollout production theo bounded batches;
6. observe availability/error/latency/restart signals;
7. rollback tới **exact previous digest** nếu stop/go criteria fail;
8. database/schema changes phải backward-compatible với overlap giữa old/new pods nếu release có migration.

## Giải thích thiết kế sau khi sửa

### 1. Probe semantics được tách theo mục đích

Liveness quyết định restart; readiness quyết định nhận traffic; startup probe bảo vệ slow startup khỏi premature liveness failures.

### 2. Dependency outage không mặc định biến thành process restart

Nếu SQL/Redis/external API fail, action phụ thuộc vào khả năng degrade của application. Restart chỉ hợp lý khi restart process có khả năng khắc phục trạng thái.

### 3. Release artifact immutable

Image digest làm rollback/restart reproducible và giúp telemetry map pod tới exact binary.

### 4. Resource config dựa trên measurement

Requests/limits không phải checkbox. Chúng phải dựa trên load test, actual usage và desired scheduling/runtime behavior.

### 5. Shutdown là một phần của rollout correctness

Termination grace và application cancellation/draining phải phù hợp request duration và background work.

## Trade-offs

- `maxUnavailable: 0` cần surge capacity và có thể làm rollout chậm hơn nếu cluster thiếu resource.
- Startup probe failure window quá dài có thể trì hoãn phát hiện startup thực sự bị treo; quá ngắn lại tạo restart loop.
- Readiness check dependency quá sâu có thể loại toàn bộ pods cùng lúc; quá nông có thể gửi traffic vào pod không thể xử lý request. Cần bám business semantics.
- Memory limit bảo vệ node nhưng limit thấp có thể tăng restart/OOM risk; CPU limit có thể tạo throttling. Phải test trước khi chọn.
- Longer termination grace giúp drain request nhưng làm scale-down/rollout chậm hơn.
- Kubernetes Secret chỉ là một phần của secret management; external vault/rotation có thể tăng complexity nhưng cải thiện lifecycle/security khi requirement cần.

## Cách kiểm thử

1. **Deployment validation:** deploy pod mới có startup 40 giây; startup probe phải cho phép startup bình thường và rollout không mất serving capacity vượt policy.
2. **Dependency failure test:** làm SQL chậm/unavailable ngắn; readiness/liveness behavior phải đúng semantics, không restart cascade nếu process vẫn healthy.
3. **Graceful shutdown test:** terminate pod khi đang xử lý request 15 giây; verify traffic drain/cancellation và client outcome theo policy.
4. **Resource/load test:** chạy representative load; đo CPU throttling, memory working set, GC, request p95/p99 và pod restart reason trước khi chốt requests/limits.
5. **Rollback test:** deploy release B rồi rollback; xác minh exact previous image digest, configuration và backward-compatible database behavior.

## Quan sát trong production

Theo dõi:

- Deployment desired/available/updated replicas;
- pod Ready/NotReady duration;
- restart count và container termination reason;
- liveness/readiness/startup probe failures;
- Kubernetes events theo pod/deployment;
- CPU usage/throttling và memory working set;
- request p50/p95/p99, 5xx/connection reset;
- graceful shutdown duration/in-flight requests;
- SQL/Redis/external API dependency health;
- image digest/deployment revision;
- OOM/eviction/scheduling failures nếu có;
- alert khi nhiều pods cùng NotReady/restart hoặc rollout không đạt availability target.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL Server là dependency bắt buộc và toàn cluster SQL outage, readiness nên behave thế nào để tránh tạo thêm failure?
2. Khi nào bạn không nên đặt CPU limit cho một latency-sensitive .NET API, và bạn sẽ chứng minh quyết định đó bằng metric nào?
3. Nếu requirement thực tế không cần Kubernetes features, bạn sẽ so sánh operational cost của Kubernetes với Azure App Service như thế nào trước khi tiếp tục migration?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry HTTP không thể tách khỏi idempotency khi operation tạo side effect.
- Network timeout không chứng minh remote operation chưa xảy ra.
- `HttpClient` lifetime, connection pooling, timeout và cancellation là production concerns chứ không chỉ coding style.
- External dependency failure cần phân loại trước khi retry; `400`, `401`, `429`, `5xx` và transport error không cùng semantics.
- Kubernetes liveness, readiness và startup probes trả lời ba câu hỏi khác nhau.
- Dependency outage không nên tự động gây process restart nếu restart không thể sửa dependency.
- Immutable image identity, graceful shutdown và resource sizing là một phần của release correctness.

## Mẫu tư duy cần nhớ

1. **Retry side effect chỉ khi idempotency semantics đã rõ.**
2. **Treat external systems as failure-prone, nhưng phân loại failure trước khi phản ứng.**
3. **Một health signal phải map tới một orchestration action cụ thể.**
4. **Artifact identity phải immutable nếu muốn rollback và RCA đáng tin cậy.**
5. **Tune timeout, concurrency và resources từ measurement thay vì từ default hoặc copy/paste.**
