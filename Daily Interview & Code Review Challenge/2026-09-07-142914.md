# Code Review Challenge 1 — File upload lên Azure Blob chạy được nhưng gây memory spike và làm lộ tài liệu private

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, Managed Identity, authorization, file upload security, streaming, multi-tenant isolation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một enterprise portal cho phép user upload tài liệu hợp đồng. Backend chạy ASP.NET Core .NET 8 trên Azure App Service Linux và scale-out tối đa 6 instances.

Yêu cầu nghiệp vụ:

- mỗi file thuộc về đúng một tenant;
- tài liệu là private, chỉ user có quyền trong tenant mới được tải;
- file thường 1–20 MB nhưng có thể tới khoảng 200 MB;
- user có thể upload đồng thời nhiều file;
- tên file hiển thị cần giữ lại cho UX nhưng không bắt buộc phải là storage identity;
- hệ thống cần chịu được client disconnect hoặc Blob Storage chậm;
- team muốn tránh lưu storage account key lâu dài trong application configuration;
- tương lai có thể cân nhắc browser upload trực tiếp lên Blob Storage.

Production gần đây ghi nhận:

- memory của App Service tăng mạnh khi nhiều user upload file lớn;
- một instance thỉnh thoảng restart do memory pressure;
- hai user upload cùng tên file có lúc ghi đè nhau;
- security review phát hiện container có public blob access;
- support thấy URL blob được chia sẻ ra ngoài vẫn tải được file mà không qua authorization của application;
- connection string chứa account key đang nằm trong application settings;
- client hủy upload nhưng server vẫn tiếp tục đọc hoặc gửi dữ liệu;
- log chỉ ghi original filename, không có tenant, blob ID, bytes, duration hoặc result;
- backend tin `Content-Type` do browser gửi lên.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobServiceClient _blobServiceClient;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        IConfiguration configuration,
        ILogger<DocumentsController> logger)
    {
        _blobServiceClient = new BlobServiceClient(
            configuration.GetConnectionString("Storage"));
        _logger = logger;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(long.MaxValue)]
    public async Task<IActionResult> Upload(
        [FromForm] IFormFile file,
        [FromQuery] string tenantId)
    {
        var container = _blobServiceClient
            .GetBlobContainerClient("documents");

        await container.CreateIfNotExistsAsync(
            PublicAccessType.Blob);

        var blob = container.GetBlobClient(file.FileName);

        await using var memory = new MemoryStream();
        await file.CopyToAsync(memory);
        memory.Position = 0;

        await blob.UploadAsync(
            memory,
            new BlobUploadOptions
            {
                HttpHeaders = new BlobHttpHeaders
                {
                    ContentType = file.ContentType
                }
            });

        _logger.LogInformation(
            "Uploaded file {FileName} for tenant {TenantId}",
            file.FileName,
            tenantId);

        return Ok(new
        {
            file.FileName,
            Url = blob.Uri.ToString()
        });
    }
}
```

## Kết quả code review tham khảo

### Critical — Container cho phép public blob access

**Vấn đề:**  
`CreateIfNotExistsAsync(PublicAccessType.Blob)` cấu hình anonymous read ở blob level nếu storage account cho phép public access.

**Tại sao xảy ra:**  
Storage authorization boundary bị bỏ qua ở download path. API có `[Authorize]`, nhưng browser có thể truy cập trực tiếp blob URL mà không đi qua application authorization.

**Ảnh hưởng production:**  
Tài liệu hợp đồng private có thể bị lộ nếu URL bị log, forward, lưu trong browser history hoặc chia sẻ ngoài ý muốn.

**Cách sửa:**  
Container phải private. Backend download cần kiểm tra user/tenant/resource authorization rồi stream file, hoặc cấp short-lived delegated access theo policy rõ ràng. Với SAS, giới hạn resource, permission và lifetime; không coi possession của URL là authorization vĩnh viễn.

---

### Critical — Caller tự chọn `tenantId` nhưng không có resource authorization

**Vấn đề:**  
`tenantId` đến trực tiếp từ query string và chỉ có `[Authorize]` ở endpoint.

**Tại sao xảy ra:**  
Authentication chỉ xác nhận danh tính; không chứng minh caller thuộc tenant hoặc có permission upload tài liệu cho tenant đó.

**Ảnh hưởng production:**  
User hợp lệ có thể ghi dữ liệu vào tenant khác, gây broken access control và sai ownership metadata.

**Cách sửa:**  
Resolve tenant từ trusted application context hoặc kiểm tra membership/policy trước upload. Ownership phải được persist cùng server-generated document/blob ID.

---

### High — Whole-file buffering gây memory pressure theo kích thước × concurrency

**Vấn đề:**  
Mỗi upload được copy toàn bộ vào `MemoryStream` trước khi gửi Blob Storage.

**Tại sao xảy ra:**  
Pipeline là request body → memory → Blob thay vì stream/bounded buffering.

**Ảnh hưởng production:**  
Nhiều file lớn đồng thời có thể tăng managed/unmanaged memory, allocation pressure, GC frequency và working set. App Service instance có thể recycle/OOM trước khi storage hoặc network đạt giới hạn throughput.

**Cách sửa:**  
Không materialize toàn bộ file nếu không cần. Stream file input trực tiếp vào Blob client hoặc dùng direct browser-to-Blob flow cho file lớn. Vẫn phải giới hạn request/file size và concurrency theo capacity.

---

### High — `RequestSizeLimit(long.MaxValue)` loại bỏ safety boundary

**Vấn đề:**  
Endpoint cho phép request size cực lớn mà không có business maximum thực tế.

**Tại sao xảy ra:**  
Implementation ưu tiên “không bị lỗi upload lớn” thay vì bounded resource consumption.

**Ảnh hưởng production:**  
Một số request rất lớn hoặc malicious uploads có thể tiêu thụ bandwidth, connection time và memory/resource lâu, tạo DoS amplification.

**Cách sửa:**  
Đặt giới hạn phù hợp requirement, ví dụ policy theo loại tài liệu/account tier. Reject sớm bằng 413 khi vượt giới hạn. Nếu 200 MB là max business, encode constraint tương ứng thay vì `long.MaxValue`.

---

### High — Blob name dùng trực tiếp original filename nên collision giữa users/tenants

**Vấn đề:**  
`GetBlobClient(file.FileName)` biến display filename thành global storage identity trong container.

**Tại sao xảy ra:**  
Không có server-generated unique key hoặc tenant/document namespace đáng tin cậy.

**Ảnh hưởng production:**  
Hai uploads cùng tên có thể conflict hoặc overwrite tùy upload semantics/options. Tenant isolation cũng không được phản ánh trong physical identity.

**Cách sửa:**  
Sinh `documentId`/`blobId` phía server, ví dụ `tenant/{tenantId}/{Guid}`. Giữ original filename như metadata/database field để hiển thị. Không dựa vào client filename cho uniqueness hoặc authorization.

---

### High — Storage account key nằm trong application configuration

**Vấn đề:**  
`BlobServiceClient` được tạo từ connection string chứa Shared Key.

**Tại sao xảy ra:**  
Application dùng long-lived credential thay vì workload identity.

**Ảnh hưởng production:**  
Nếu secret bị lộ qua config/log/support workflow, blast radius có thể rất lớn và rotation phức tạp.

**Cách sửa:**  
Trên Azure App Service, ưu tiên Microsoft Entra ID + Managed Identity và Azure RBAC theo least privilege. Application nên nhận `BlobServiceClient` qua DI và credential chain phù hợp môi trường. Nếu SAS là cần thiết, ưu tiên user delegation SAS khi phù hợp thay vì ký bằng account key.

---

### High — Tin `Content-Type` do client gửi lên

**Vấn đề:**  
`file.ContentType` được copy trực tiếp vào blob metadata/header.

**Tại sao xảy ra:**  
Client-controlled metadata bị coi là trustworthy classification.

**Ảnh hưởng production:**  
File có thể được phục vụ với MIME type nguy hiểm hoặc không phù hợp; nếu domain/download policy render inline, điều này có thể tạo content-sniffing/XSS-related risk tùy browser và response headers.

**Cách sửa:**  
Validate file type dựa trên business allow-list; khi cần, inspect signature/magic bytes bằng thư viện phù hợp. Với untrusted documents, ưu tiên download attachment và `X-Content-Type-Options: nosniff` ở download boundary. Không coi extension hoặc browser MIME là bằng chứng đầy đủ.

---

### High — Không truyền request cancellation vào upload pipeline

**Vấn đề:**  
`CopyToAsync` và Blob operations không dùng `HttpContext.RequestAborted`.

**Tại sao xảy ra:**  
I/O không gắn với request lifecycle.

**Ảnh hưởng production:**  
Client disconnect nhưng server vẫn có thể tiếp tục đọc/gửi dữ liệu, giữ connection và bandwidth không cần thiết.

**Cách sửa:**  
Propagate `CancellationToken`. Đồng thời xử lý partial upload semantics và cleanup/reconciliation nếu workflow có metadata record tạo trước upload.

---

### Medium — Không có state model cho upload lifecycle

**Vấn đề:**  
Không có durable record cho `Pending/Uploaded/Validated/Failed` hoặc ownership trước khi trả URL.

**Tại sao xảy ra:**  
Blob được xem là toàn bộ domain state.

**Ảnh hưởng production:**  
Khó reconciliation giữa database và storage, khó scan malware hoặc retry metadata operation sau partial failure.

**Cách sửa:**  
Nếu domain cần audit/ownership, persist document record với server-generated ID, expected tenant, filename, length, checksum/version nếu cần và trạng thái lifecycle rõ ràng.

---

### Medium — Logging chưa đủ cho production investigation

**Vấn đề:**  
Log chỉ có original filename và tenant query value.

**Tại sao xảy ra:**  
Không có document/blob ID, authenticated subject, bytes, duration, storage request correlation hoặc outcome.

**Ảnh hưởng production:**  
Khó xác định upload nào gây memory spike, blob nào bị ghi đè hoặc request nào thất bại giữa chừng.

**Cách sửa:**  
Structured telemetry với document ID, trusted tenant ID, safe user identifier, file-size bucket, duration, result, cancellation, storage dependency duration/request ID và instance identifier. Không log file contents hoặc secrets.

## Phiên bản đề xuất

Giả định ở đây:

- file tối đa 200 MB;
- upload qua backend vẫn được giữ vì application cần kiểm soát policy trực tiếp;
- container là private;
- `BlobServiceClient` được cấu hình bằng Managed Identity ngoài controller;
- metadata ownership được lưu trong database.

```csharp
[ApiController]
[Route("api/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxFileBytes = 200L * 1024 * 1024;

    private readonly BlobContainerClient _container;
    private readonly IDocumentAuthorization _authorization;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        IDocumentAuthorization authorization,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _authorization = authorization;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(MaxFileBytes)]
    public async Task<IActionResult> Upload(
        [FromForm] IFormFile file,
        CancellationToken cancellationToken)
    {
        var tenantId = await _authorization
            .GetAuthorizedTenantForUploadAsync(User, cancellationToken);

        if (file.Length is <= 0 or > MaxFileBytes)
            return BadRequest("Invalid file size.");

        var documentId = Guid.NewGuid();
        var originalName = Path.GetFileName(file.FileName);
        var blobName = $"{tenantId}/{documentId:N}";

        var document = new DocumentRecord
        {
            Id = documentId,
            TenantId = tenantId,
            OriginalFileName = originalName,
            BlobName = blobName,
            Length = file.Length,
            Status = DocumentStatus.Uploading,
            CreatedUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(cancellationToken);

        var blob = _container.GetBlobClient(blobName);
        var started = Stopwatch.GetTimestamp();

        try
        {
            await using var stream = file.OpenReadStream(MaxFileBytes);

            await blob.UploadAsync(
                stream,
                new BlobUploadOptions
                {
                    HttpHeaders = new BlobHttpHeaders
                    {
                        ContentType = "application/octet-stream"
                    },
                    Metadata = new Dictionary<string, string>
                    {
                        ["documentId"] = documentId.ToString("N")
                    },
                    Conditions = new BlobRequestConditions
                    {
                        IfNoneMatch = ETag.All
                    }
                },
                cancellationToken);

            document.Status = DocumentStatus.Uploaded;
            await _db.SaveChangesAsync(cancellationToken);

            _logger.LogInformation(
                "Document {DocumentId} uploaded for tenant {TenantId}. Bytes={Bytes} DurationMs={DurationMs}",
                documentId,
                tenantId,
                file.Length,
                Stopwatch.GetElapsedTime(started).TotalMilliseconds);

            return Ok(new
            {
                documentId,
                fileName = originalName,
                file.Length
            });
        }
        catch (OperationCanceledException)
        {
            document.Status = DocumentStatus.Cancelled;
            await _db.SaveChangesAsync(CancellationToken.None);
            throw;
        }
        catch (Exception ex)
        {
            document.Status = DocumentStatus.Failed;
            await _db.SaveChangesAsync(CancellationToken.None);

            _logger.LogError(
                ex,
                "Document {DocumentId} upload failed for tenant {TenantId}",
                documentId,
                tenantId);

            throw;
        }
    }
}
```

Container provisioning/public-access policy tốt hơn nên nằm trong infrastructure/deployment code thay vì tự thay đổi security posture ở mỗi request.

Nếu upload lớn và traffic cao, một thiết kế khác có thể là:

1. client gọi API xin upload session;
2. API authenticate + authorize tenant;
3. API tạo document ID và durable `Pending` record;
4. API cấp short-lived, write-only user delegation SAS cho đúng blob key;
5. browser upload trực tiếp lên Blob Storage;
6. client/backend finalize upload;
7. backend verify blob properties/size/checksum policy;
8. optional malware/content validation chạy trước khi document trở thành `Ready`;
9. download vẫn áp dụng resource authorization và policy riêng.

## Giải thích thiết kế sau khi sửa

### 1. Storage identity do server tạo

Original filename chỉ là display metadata. Blob key dùng `documentId`, giúp tránh collision và làm ownership rõ ràng hơn.

### 2. Private-by-default

Blob URL không tự trở thành public download endpoint. Access phải đi qua authorization boundary hoặc delegated token có scope/lifetime hẹp.

### 3. Streaming giảm peak memory

Pipeline không giữ thêm một bản full file trong `MemoryStream`. Tuy nhiên ASP.NET Core multipart handling vẫn cần được cấu hình/đo phù hợp; direct upload có thể tốt hơn khi file lớn và concurrency cao.

### 4. Managed Identity giảm secret lifecycle

Application dùng workload identity + Azure RBAC thay vì giữ long-lived account key trong config.

### 5. Upload được coi là workflow có partial failure

Database state và Blob write không phải một atomic transaction. Vì vậy cần lifecycle state, idempotency/retry semantics và reconciliation thay vì giả định mọi bước cùng thành công hoặc cùng rollback.

## Trade-offs

- Proxy upload qua backend đơn giản hóa authorization và auditing nhưng tiêu thụ App Service bandwidth/connection time.
- Direct browser-to-Blob giảm tải backend nhưng cần SAS issuance, CORS, finalize/reconciliation và threat model chặt chẽ hơn.
- Managed Identity/RBAC giảm secret risk nhưng cần provisioning quyền chính xác; permission quá rộng vẫn là security problem.
- Malware scanning/content validation tăng latency và operational complexity nhưng có thể cần thiết với untrusted documents.
- Persist upload state tăng database writes nhưng giúp recovery và audit tốt hơn.

## Cách kiểm thử

1. **Authorization integration test:** user tenant A không thể tạo/upload/download document thuộc tenant B dù sửa request parameters.
2. **Load test:** nhiều uploads lớn đồng thời; đo working set, GC, request duration, throughput và App Service restart/OOM behavior.
3. **Cancellation/failure-path test:** client disconnect hoặc inject Blob timeout giữa upload; server dừng work hợp lý và document state có thể reconcile.
4. **Security test:** container anonymous access phải bị tắt; direct blob URL không tải được nếu không có authorization phù hợp.
5. **Collision/idempotency test:** hai users upload cùng original filename đồng thời vẫn tạo hai document/blob identities độc lập.

## Quan sát trong production

Theo dõi:

- upload request count và success/failure/cancel rate;
- bytes uploaded theo distribution;
- p50/p95/p99 upload duration;
- process working set, GC heap, allocation rate;
- concurrent uploads;
- Blob Storage dependency duration/failure/throttling;
- document states `Uploading/Uploaded/Failed/Cancelled` và age của records bị kẹt;
- App Service restarts;
- authorization denials;
- storage request IDs/correlation IDs;
- blob count/orphan reconciliation metrics;
- alert khi memory, failure rate hoặc stuck-upload age vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn backend proxy upload thay vì direct browser-to-Blob?
2. Nếu cần antivirus scanning trước khi document được download, bạn sẽ đặt state machine và security boundary ở đâu?
3. Nếu user delegation SAS bị lộ trước expiry, bạn giới hạn blast radius và thiết kế revocation/recovery thế nào?

# Code Review Challenge 2 — Kubernetes health probes biến Redis outage thành restart storm

**Chủ đề:** Kubernetes, ASP.NET Core hosting, readiness/liveness/startup probes, secrets, rolling deployment, resource limits, graceful shutdown, production troubleshooting  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 API đang được thử nghiệm chuyển từ Azure App Service sang Kubernetes.

Application có:

- REST API;
- SQL Server là system of record;
- Redis chỉ dùng cache-aside và có thể fallback về SQL;
- startup bình thường mất 8–20 giây vì load configuration và warm-up;
- endpoint `/health` hiện kiểm tra process, SQL và Redis trong cùng một health check;
- graceful shutdown của application cần tối đa khoảng 20 giây để ngừng nhận request và flush telemetry;
- production chạy 4 replicas;
- deployment dùng rolling update.

Sau một incident Redis mất kết nối khoảng 3 phút:

- nhiều Pods chuyển sang restart liên tục;
- traffic còn lại dồn vào ít Pods hơn và p99 tăng mạnh;
- một số request đang xử lý bị cắt khi container restart;
- deployment mới đôi khi bị đánh giá fail dù application chỉ startup chậm;
- support thấy image `latest` ở các Pods không phải lúc nào cũng có cùng build SHA sau một đợt redeploy;
- connection string production nằm trực tiếp trong YAML được commit vào repository;
- một số Pods bị `OOMKilled` khi traffic burst.

            - name: Redis__ConnectionString

          resources:

              memory: "128Mi"
            limits:
              cpu: "250m"
              memory: "128Mi"
          readinessProbe:

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc Redis nên transient dependency outage kích hoạt container restart

**Vấn đề:**  
Liveness gọi `/health`, endpoint này fail nếu Redis fail.

**Tại sao xảy ra:**  
Một optional external dependency được dùng như bằng chứng rằng process cần bị restart.

**Ảnh hưởng production:**  
Khi Redis outage, kubelet có thể restart container dù application hoàn toàn có thể fallback SQL. Restart đồng loạt làm giảm serving capacity, làm cold start tăng và khuếch đại incident thành restart storm.

**Cách sửa:**  
Liveness endpoint nên chủ yếu chứng minh process/runtime còn hoạt động và không ở trạng thái không thể tự recover. Không đưa optional remote dependency vào liveness chỉ vì dependency đó có health check.

---

### Critical — Không có startup probe dù startup có thể lâu hơn liveness grace window

**Vấn đề:**  
Liveness bắt đầu rất sớm trong khi startup bình thường 8–20 giây.

**Tại sao xảy ra:**  
Không có startup probe bảo vệ application trong initialization phase.

**Ảnh hưởng production:**  
Pod chậm hợp lệ có thể bị kill trước khi startup xong, dẫn tới crash loop giả và rollout fail.

**Cách sửa:**  
Dùng `startupProbe` với failure window đủ lớn dựa trên measured startup distribution. Khi startup probe chưa thành công, liveness/readiness semantics không nên làm application bị restart sớm.

---

### High — Readiness và liveness dùng cùng endpoint/semantics

**Vấn đề:**  
Cả hai gọi `/health` gồm process + SQL + Redis.

**Tại sao xảy ra:**  
Health checks được thiết kế theo danh sách dependencies thay vì operational action.

**Ảnh hưởng production:**  
Một dependency failure vừa rút Pod khỏi traffic vừa restart process, dù hai action có mục tiêu khác nhau.

**Cách sửa:**  
Tách `/health/live`, `/health/ready`, `/health/startup` hoặc tag-based ASP.NET Core health checks. Readiness chỉ nên fail khi Pod hiện không thể phục vụ request theo contract. Nếu Redis có fallback, Redis fail không nhất thiết làm readiness fail; cần quyết định dựa trên capacity và business impact.

---

### High — Secret production được hard-code trong manifest/repository

**Vấn đề:**  
SQL password và Redis password xuất hiện trong YAML.

**Tại sao xảy ra:**  
Configuration và secret được trộn trực tiếp vào deployment manifest.

**Ảnh hưởng production:**  
Credentials có thể tồn tại trong Git history, pull request, CI logs hoặc artifact; rotation khó và blast radius tăng.

**Cách sửa:**  
Dùng Kubernetes Secret hoặc external secret provider phù hợp platform; tốt hơn nữa dùng workload identity/Managed Identity cho Azure services khi service hỗ trợ. RBAC và namespace access vẫn phải theo least privilege.

---

### High — Mutable `latest` tag làm release identity không reproducible

**Vấn đề:**  
Deployment tham chiếu `registry.example.com/customer-api:latest`.

**Tại sao xảy ra:**  
Tag có thể trỏ tới image khác theo thời gian.

**Ảnh hưởng production:**  
Hai rollout cùng manifest có thể chạy binary khác nhau; rollback và incident RCA khó chứng minh exact build đang chạy.

**Cách sửa:**  
Deploy immutable version tag gắn với build/commit hoặc image digest. Ghi build SHA/version vào application telemetry.

---

### High — Memory limit quá chặt nhưng không có evidence từ workload

**Vấn đề:**  
Request và limit đều 128 MiB trong khi production đã thấy `OOMKilled`.

**Tại sao xảy ra:**  
Resource values có vẻ được chọn tĩnh, không dựa trên working-set baseline, GC behavior, concurrent requests và startup peak.

**Ảnh hưởng production:**  
Container bị kill khi vượt memory cgroup limit, gây retry/restart và traffic redistribution.

**Cách sửa:**  
Profile memory dưới realistic load, xem working set/GC heap/allocations và đặt request/limit có headroom hợp lý. Không chỉ tăng limit vô hạn; trước hết tìm memory leak/allocation hotspots và concurrency behavior.

---

### High — Graceful shutdown window không được encode rõ

**Vấn đề:**  
Manifest không đặt `terminationGracePeriodSeconds` theo known application shutdown requirement.

**Tại sao xảy ra:**  
Deployment chưa kết nối Kubernetes termination lifecycle với ASP.NET Core graceful shutdown behavior.

**Ảnh hưởng production:**  
Pod có thể bị terminate trước khi request drain/telemetry flush hoàn tất nếu default hoặc platform timing không phù hợp với workload thực tế.

**Cách sửa:**  
Đặt termination grace period lớn hơn measured normal shutdown time với headroom. Application phải handle SIGTERM, ngừng nhận traffic và hoàn tất bounded in-flight work. Không dùng grace period cực dài để che work không cancel được.

---

### Medium — Rolling update cho phép giảm serving capacity trong lúc Pod mới còn warm-up

**Vấn đề:**  
`maxUnavailable: 1` có thể phù hợp hoặc không, nhưng chưa có evidence về capacity headroom và readiness correctness.

**Tại sao xảy ra:**  
Deployment strategy được chọn độc lập với SLO/traffic/capacity.

**Ảnh hưởng production:**  
Nếu mỗi Pod đã chạy gần capacity, mất một replica trong rollout có thể tăng p95/p99. Nếu readiness sai, traffic có thể vào Pod chưa sẵn sàng.

**Cách sửa:**  
Nếu capacity yêu cầu, cân nhắc `maxUnavailable: 0` và bounded surge, nhưng cần đủ cluster capacity. Quyết định dựa trên load test và operational cost, không coi một setting là universally correct.

---

### Medium — Probe thresholds quá aggressive so với transient latency

**Vấn đề:**  
`timeoutSeconds: 1`, `periodSeconds: 5`, liveness failure threshold 2 có thể biến vài giây latency thành restart.

**Tại sao xảy ra:**  
Probe timing không dựa trên measured endpoint latency hoặc failure mode.

**Ảnh hưởng production:**  
CPU pressure, GC pause hoặc transient node/network latency có thể tạo false-positive restarts.

**Cách sửa:**  
Tune timeout/period/failure threshold theo telemetry. Health endpoint phải nhẹ, bounded và không phụ thuộc vào slow deep diagnostics.

---

### Medium — Không có rollout/business validation ngoài probe

**Vấn đề:**  
Probe success bị dùng như bằng chứng release đúng về business behavior.

**Tại sao xảy ra:**  
Liveness/readiness bị trộn với deployment validation.

**Ảnh hưởng production:**  
App có thể ready nhưng authentication, critical API hoặc database workflow bị regression.

**Cách sửa:**  
Thêm post-deploy smoke tests, error-rate/latency guardrail và observation window. Probe chỉ là runtime traffic/restart signal, không thay thế release verification.

## Phiên bản đề xuất

Ví dụ minh họa dưới đây giả định:

- Redis là optional cache, không quyết định liveness;
- SQL là required để xử lý phần lớn request nên có thể tham gia readiness;
- application có endpoint riêng cho startup/live/ready;
- secret được provision bởi deployment platform;
- resource values là placeholder cần thay bằng số đã được load-test.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: customer-api
spec:
  replicas: 4
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: customer-api
  template:
    metadata:
      labels:
        app: customer-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example.com/customer-api:2026.09.07.142914
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: customer-api-secrets
                  key: main-db
            - name: Redis__ConnectionString
              valueFrom:
                secretKeyRef:
                  name: customer-api-secrets
                  key: redis
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12
          livenessProbe:
            httpGet:
              path: /health/live
              port: http
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
---
apiVersion: v1
kind: Service
metadata:
  name: customer-api
spec:
  selector:
    app: customer-api
  ports:
    - port: 80
      targetPort: http
```

ASP.NET Core health semantics nên được thiết kế theo hành động:

```text
/health/startup
  - process/config initialization đã hoàn tất chưa?

/health/live
  - process có còn responsive và có khả năng tự tiếp tục không?
  - không phụ thuộc Redis/SQL chỉ vì chúng là dependencies

/health/ready
  - Pod hiện có thể xử lý traffic theo service contract không?
  - required dependencies có thể tham gia
  - optional cache như Redis chỉ nên làm readiness fail nếu fallback không đủ để giữ service an toàn
```

Các resource values trong YAML trên chỉ là scenario example, không phải recommendation universal. Cần thay bằng dữ liệu từ profiling/load test.

## Giải thích thiết kế sau khi sửa

### 1. Probe được gắn với operational action

Liveness trả lời “restart có giúp không?”, readiness trả lời “có nên nhận traffic không?”, startup trả lời “initialization đã hoàn tất chưa?”.

### 2. Optional dependency failure không tự động trở thành process failure

Redis cache outage nên kích hoạt fallback/telemetry/capacity response trước khi biến thành restart storm.

### 3. Release identity immutable

Image version hoặc digest giúp rollback/RCA reproducible.

### 4. Secrets tách khỏi manifest source

Kubernetes Secret vẫn cần governance; với Azure-hosted workloads, workload identity/Managed Identity có thể giảm credential management khi dependency hỗ trợ.

### 5. Resources phải được đo

Requests ảnh hưởng scheduling; limits ảnh hưởng runtime throttling/OOM behavior. Không chọn số chỉ để manifest “đủ trường”.

## Trade-offs

- Startup probe quá rộng sẽ làm detect real startup failure chậm; quá hẹp sẽ tạo false restart.
- `maxUnavailable: 0` tăng rollout safety nhưng cần cluster capacity cho surge Pod.
- Memory limit cao hơn giảm OOM risk nhưng có thể che leak nếu không có profiling/alerts.
- Readiness phụ thuộc SQL sẽ rút Pod khỏi traffic khi SQL outage; nếu toàn bộ Pods cùng mất SQL, điều đó không tự tạo availability. Cần dependency incident strategy ở cấp hệ thống.
- Kubernetes tăng operational surface so với App Service; chỉ nên giữ migration nếu requirement về scheduling, platform standardization hoặc workload justify complexity.

## Cách kiểm thử

1. **Failure-path test:** làm Redis unavailable; Pods không restart chỉ vì Redis, và application fallback behavior đúng theo policy.
2. **Startup/deployment validation:** inject startup 20–40 giây; startup probe cho đủ thời gian nhưng vẫn fail bounded khi app thật sự không start.
3. **Load/resource test:** chạy realistic traffic, đo CPU, working set, GC, throttling và OOM events để tune requests/limits.
4. **Graceful-shutdown test:** terminate Pod khi có in-flight requests; xác minh readiness rút traffic và request/telemetry hoàn tất trong grace window.
5. **Rollout test:** deploy immutable image qua rolling update; xác minh không có 5xx/error-rate spike và mọi Pod báo đúng build SHA.

## Quan sát trong production

Theo dõi:

- Pod restart count và restart reason;
- `OOMKilled` events;
- readiness/liveness/startup failure counts;
- rollout duration và unavailable replica count;
- CPU throttling, CPU usage, working set và memory limit ratio;
- ASP.NET Core request p50/p95/p99, 5xx rate;
- SQL dependency latency/error;
- Redis dependency latency/error/cache hit ratio/fallback rate;
- in-flight requests lúc termination;
- application shutdown duration;
- image digest/build SHA theo Pod;
- node/Pod scheduling events;
- alert khi restart, probe failure hoặc OOM vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Khi SQL là required dependency của gần như mọi request, readiness nên xử lý SQL outage thế nào để không tạo false sense of availability?
2. Nếu application thực tế cần hơn 30 giây để shutdown trong một số batch operation, bạn sẽ sửa app hay tăng `terminationGracePeriodSeconds`, và dựa trên evidence nào?
3. Với workload này, điều gì phải đúng để Kubernetes thực sự tốt hơn Azure App Service thay vì chỉ tăng operational complexity?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication không thay thế resource authorization; tenant ownership phải được xác minh từ trusted context.
- File upload lớn nên được thiết kế như streaming workflow có bounded size, cancellation, ownership và partial-failure state.
- Azure Blob Storage private access + Managed Identity/RBAC thường tạo security posture tốt hơn public blobs + long-lived account keys.
- Display filename không nên là storage identity.
- Kubernetes probes phải phản ánh đúng operational action: startup, remove-from-traffic và restart là ba việc khác nhau.
- Optional dependency outage không nên tự động trở thành liveness failure nếu process vẫn có thể phục vụ an toàn.
- Resource requests/limits, rollout strategy và probe timing đều cần measurement thay vì copy template.

## Mẫu tư duy cần nhớ

1. **Tách authentication, authorization và resource ownership.**
2. **Bound resources before scaling concurrency.**
3. **Treat external storage and network calls as partial-failure boundaries.**
4. **Design health signals around the action they trigger.**
5. **Make deployment artifacts immutable and observable.**
