## Đoạn code cần review

```csharp
[ApiController]
[Route("api/payments")]
public sealed class PaymentWebhookController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _email;
    private readonly IRewardsClient _rewards;
    private readonly ILogger<PaymentWebhookController> _log;

    public PaymentWebhookController(AppDbContext db, IEmailSender email,
        IRewardsClient rewards, ILogger<PaymentWebhookController> log)
    {
        _db = db;
        _email = email;
        _rewards = rewards;
        _log = log;
    }

    [HttpPost("callback")]
    public async Task<IActionResult> Callback(
        [FromBody] PaymentCallback input, CancellationToken ct)
    {
        _log.LogInformation("Payment callback {Payload}",
            JsonSerializer.Serialize(input));

        var order = await _db.Orders
            .FirstOrDefaultAsync(x => x.Id == input.OrderId, ct);
        if (order is null) return NotFound();

        if (order.Status == "Paid") return Ok();

        order.Status = input.Status == "success" ? "Paid" : "Failed";
        order.PaidAmount = input.Amount;
        order.UpdatedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync(ct);

        if (order.Status == "Paid")
        {
            await _rewards.AddPointsAsync(order.CustomerId,
                order.TotalAmount, ct);
            await _email.SendReceiptAsync(order.Id, ct);
        }

        return Ok();
    }
}

public sealed record PaymentCallback(
    Guid OrderId, string EventId, string Status, decimal Amount);
```

## Kết quả code review tham khảo

### [Critical] — Không xác thực nguồn webhook

**Vấn đề:** Bất kỳ client nào có thể POST một payload tự khai báo `success`.  
**Tại sao xảy ra:** Endpoint không kiểm tra chữ ký trên raw body, timestamp/replay window hoặc nguồn sự kiện theo hợp đồng provider.  
**Ảnh hưởng production:** Đơn hàng bị đánh dấu Paid giả mạo, có thể phát sinh fulfillment và rewards.  
**Cách sửa:** Xác thực chữ ký bằng SDK/hợp đồng chính thức trên raw request body trước khi deserialize/ghi DB; giới hạn replay window và đối chiếu transaction server-side khi cần. Không coi IP allowlist là bằng chứng duy nhất.

### [Critical] — Không kiểm tra amount, currency và merchant/payment reference

**Vấn đề:** Payload có thể cập nhật Paid cho order không khớp giá trị cần thu.  
**Tại sao xảy ra:** Chỉ dùng OrderId, không đối chiếu expected amount/currency, provider transaction, merchant và trạng thái payment attempt.  
**Ảnh hưởng production:** Ghi nhận thanh toán thiếu tiền hoặc sai giao dịch.  
**Cách sửa:** So sánh theo minor units hoặc decimal đúng precision, currency, merchant, payment attempt và provider transaction; từ chối hoặc đưa vào manual reconciliation nếu không khớp.

### [High] — Race condition giữa các callback

**Vấn đề:** Hai requests có thể cùng thấy Pending và cùng chạy side effects.  
**Tại sao xảy ra:** Read-check-write không có concurrency guard; nhiều instances không chia sẻ lock bộ nhớ.  
**Ảnh hưởng production:** Double rewards, double email và trạng thái ghi đè.  
**Cách sửa:** Transaction với conditional transition, optimistic concurrency hoặc row lock phù hợp; unique constraint cho provider event/transaction; chỉ transition thắng mới tạo outbox.

### [High] — Không có idempotent inbox và kiểm soát event ordering

**Vấn đề:** EventId bị bỏ qua; một event cũ có thể đổi Paid thành Failed trong luồng có nhiều trạng thái.  
**Tại sao xảy ra:** Không có unique event key và state machine dựa trên provider semantics.  
**Ảnh hưởng production:** Trạng thái sai khi event đến trễ, retry hoặc reorder.  
**Cách sửa:** Inbox unique theo (provider, eventId); state transition hợp lệ; deduplicate theo payment transaction/business operation ngoài event ID khi cần.

### [High] — Database commit và external calls không atomic

**Vấn đề:** Sau SaveChanges, email/rewards lỗi sẽ trả 5xx; retry có thể bị short-circuit vì Paid và bỏ sót side effects.  
**Tại sao xảy ra:** Không có durable intent cho downstream operations.  
**Ảnh hưởng production:** Receipt/rewards mất vĩnh viễn hoặc bị gửi lặp.  
**Cách sửa:** Transactional outbox cùng transaction cập nhật order; worker retry với idempotency key riêng cho từng downstream operation.

### [Medium] — Cancellation của HTTP request chi phối downstream delivery

**Vấn đề:** Client ngắt kết nối có thể hủy email/rewards sau khi DB đã commit.  
**Tại sao xảy ra:** Dùng request CancellationToken cho tác vụ cần durable completion.  
**Ảnh hưởng production:** Kết quả không nhất quán và khó khôi phục.  
**Cách sửa:** Chỉ commit durable state/inbox/outbox trong request; worker độc lập xử lý delivery.

### [Medium] — Logging toàn bộ payload

**Vấn đề:** Dữ liệu giao dịch và metadata có thể bị lộ vào log.  
**Tại sao xảy ra:** Serialize nguyên payload không có redaction.  
**Ảnh hưởng production:** Rủi ro privacy/compliance, chi phí log và lộ identifiers.  
**Cách sửa:** Structured logging với event ID, order ID đã kiểm soát, outcome và correlation ID; không log chữ ký/token/PII.

### [Medium] — Không phân biệt business rejection và lỗi hạ tầng

**Vấn đề:** NotFound, provider retries và lỗi DB chưa có chính sách nhất quán.  
**Tại sao xảy ra:** Không phân loại permanent vs transient errors hoặc quan sát poison events.  
**Ảnh hưởng production:** Retry storm hoặc mất thông tin điều tra.  
**Cách sửa:** Định nghĩa HTTP acknowledgment theo hợp đồng provider, lưu audit cho event đã xác thực, retry bounded cho lỗi tạm thời và cảnh báo reconciliation.

## Phiên bản đề xuất

Pseudocode C# dưới đây minh họa các ranh giới quan trọng; `IPaymentSignatureVerifier`, `IProviderEventMapper`, `PaymentAttempt`, `WebhookInbox` và `OutboxMessage` là abstractions ứng dụng cần triển khai, không phải API có sẵn của .NET.

```csharp
[HttpPost("callback")]
public async Task<IActionResult> Callback(CancellationToken ct)
{
    using var buffer = new MemoryStream();
    await Request.Body.CopyToAsync(buffer, ct);
    var raw = buffer.ToArray();

    if (!_signatureVerifier.IsValid(raw, Request.Headers))
        return Unauthorized();

    var evt = _mapper.ParseAndValidate(raw);
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var alreadySeen = await _db.WebhookInbox.AnyAsync(
        x => x.Provider == evt.Provider && x.EventId == evt.EventId, ct);
    if (alreadySeen) return Ok();

    _db.WebhookInbox.Add(new WebhookInbox(evt.Provider, evt.EventId));
    var attempt = await _db.PaymentAttempts
        .SingleOrDefaultAsync(x => x.Provider == evt.Provider &&
            x.ProviderReference == evt.PaymentReference, ct);
    if (attempt is null)
        throw new UnmatchedPaymentEventException(evt.EventId);

    if (evt.IsSuccessful &&
        attempt.ExpectedAmount == evt.Amount &&
        attempt.Currency == evt.Currency &&
        attempt.MerchantId == evt.MerchantId)
    {
        var changed = await _db.Orders
            .Where(o => o.Id == attempt.OrderId && o.Status == "Pending")
            .ExecuteUpdateAsync(s => s
                .SetProperty(o => o.Status, "Paid")
                .SetProperty(o => o.PaidAmount, evt.Amount), ct);

        if (changed == 1)
        {
            _db.OutboxMessages.Add(OutboxMessage.ForReceipt(attempt.OrderId));
            _db.OutboxMessages.Add(OutboxMessage.ForRewards(attempt.OrderId));
        }
    }
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return Ok();
}
```

Cần thêm unique index cho `(Provider, EventId)`, unique business key cho outbox, và retry logic khi insert inbox đụng unique constraint. Production implementation cần explicit state machine cho Failed/Refunded/Chargeback, xác minh amount/currency cho mọi transition và xử lý unmatched events qua quarantine/reconciliation thay vì chỉ throw. Worker outbox phải có lease/claim, retry/backoff, dead-letter và downstream idempotency; không có exactly-once guarantee xuyên hệ thống.

## Giải thích thiết kế sau khi sửa

Database là nơi quyết định transition. Conditional update ngăn hai callback cùng thắng; inbox phân biệt event đã xử lý, outbox bảo đảm intent không biến mất khi process crash. Event ID không thay thế business-level deduplication. Chữ ký xác thực nguồn, nhưng vẫn cần validate business context và trạng thái giao dịch.

## Trade-offs

Thêm inbox/outbox làm tăng storage, worker và operational burden; đổi lại giảm mất dữ liệu khi partial failure. Nếu provider hỗ trợ truy vấn trạng thái thanh toán, reconciliation job có thể khôi phục sai lệch nhưng không thay thế xác thực callback. Row lock/serializable isolation có thể đơn giản hơn ở tải thấp, nhưng cần đo contention và deadlocks. Email có thể gửi lại; rewards phải có idempotency key bền vững ở phía nhận hoặc ledger unique constraint.

## Cách kiểm thử

1. **Security test:** Payload giả chữ ký, replay timestamp và amount/currency sai không chuyển Paid.
2. **Concurrency test:** 100 callbacks đồng thời cho cùng transaction, chỉ một transition và một cặp outbox business keys.
3. **Failure-path test:** Crash sau DB commit trước worker delivery; worker restart vẫn hoàn thành.
4. **Integration test:** Provider retry cùng event ID, event khác cùng payment reference và event đến sai thứ tự.
5. **Load test:** Đo lock contention, p95, unique-conflict rate, outbox lag và retry throughput.

## Quan sát trong production

Theo dõi Application Insights traces theo event ID/payment reference đã redacted; counters cho signature failures, mismatched amount, duplicate inbox, successful transitions, outbox pending/age, worker retries và DLQ. PostgreSQL metrics: deadlocks, lock waits, transaction duration và unique violations. Alert nếu outbox oldest age vượt SLO hoặc tỷ lệ unmatched events tăng. Đối chiếu tổng Paid với provider settlement hằng ngày.

import { ref, watch, onMounted } from 'vue'

type Product = { id: string; name: string; description: string }
const keyword = ref('')
const category = ref('all')
const page = ref(1)
const products = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')

async function load() {

  error.value = ''
  const url = '/api/search?q=' + keyword.value +

    const response = await fetch(url)

    error.value = 'Không tải được dữ liệu'

onMounted(load)

  page.value++
}

<template>

## Kết quả code review tham khảo

### [High] — Stored XSS qua v-html

**Vấn đề:** Description từ API được render như HTML không qua sanitizer.  
**Tại sao xảy ra:** `v-html` bypass escaping mặc định của Vue template interpolation.  
**Ảnh hưởng production:** Script injection nếu dữ liệu product bị kiểm soát bởi attacker hoặc nguồn upstream không tin cậy.  
**Cách sửa:** Render text bằng `{{ p.description }}`; nếu rich text bắt buộc, sanitize bằng policy allowlist ở boundary phù hợp và áp dụng CSP defense-in-depth.

### [High] — Response race ghi đè kết quả mới

**Vấn đề:** Request cũ hoàn thành muộn có thể thay products và total của filter mới.  
**Tại sao xảy ra:** Mọi request đều ghi shared state không có version check.  
**Ảnh hưởng production:** Khách thấy kết quả sai filter và ra quyết định trên dữ liệu không đúng ngữ cảnh.  
**Cách sửa:** Abort request cũ và chỉ commit kết quả nếu generation ID còn là latest; server vẫn có thể đã xử lý request bị abort.

### [Medium] — Không kiểm tra HTTP status/schema

**Vấn đề:** `fetch` không throw cho 429/503; JSON error có thể được gán vào items.  
**Tại sao xảy ra:** Không kiểm tra `response.ok` và shape dữ liệu.  
**Ảnh hưởng production:** UI trống hoặc lỗi runtime, khó phân biệt empty result với outage.  
**Cách sửa:** Check status, validate response shape, hiển thị retryable error; retry bounded với backoff và Retry-After khi hợp lý.

### [Medium] — Không reset page và không giới hạn navigation

**Vấn đề:** Đổi keyword/category giữ page cũ; nextPage có thể vượt total.  
**Tại sao xảy ra:** Page state độc lập với filter và thiếu bounds.  
**Ảnh hưởng production:** Kết quả rỗng giả, điều hướng sai.  
**Cách sửa:** Reset page=1 khi filter thay đổi; disable next khi đang loading hoặc đã đến trang cuối; thống nhất pageSize với API.

### [Medium] — Request storm khi gõ nhanh

**Vấn đề:** Mỗi keystroke tạo request mới.  
**Tại sao xảy ra:** Watch trực tiếp keyword, không debounce.  
**Ảnh hưởng production:** Tăng load API, rate limiting và chi phí.  
**Cách sửa:** Debounce keyword; cancel obsolete requests; cân nhắc minimum query length theo requirement.

### [Medium] — Loading state không đại diện request hiện tại

**Vấn đề:** Request cũ có thể đặt loading=false trong lúc request mới đang chạy.  
**Tại sao xảy ra:** Không gắn lifecycle với generation token, không có finally scoped cho latest.  
**Ảnh hưởng production:** Spinner biến mất sớm, UI bị flicker.  
**Cách sửa:** Chỉ latest request được cập nhật loading/error/products; cleanup on unmount.

### [Low] — URL state và accessibility chưa đầy đủ

**Vấn đề:** Reload/back-forward không khôi phục filter; input thiếu label, loading/error thiếu live region.  
**Tại sao xảy ra:** State chỉ ở component và markup chưa thể hiện semantics.  
**Ảnh hưởng production:** Khó chia sẻ kết quả và trải nghiệm keyboard/screen reader kém.  
**Cách sửa:** Đồng bộ state với router query (có quy tắc tránh vòng lặp), label controls, `aria-live`, disabled navigation và focus handling phù hợp.

## Phiên bản đề xuất

Ví dụ phần script và template chính; dùng debounce timer, cancellation và generation guard. Trong ứng dụng dùng Vue Router, đồng bộ `keyword/category/page` với route query ở một composable riêng; ví dụ dưới giữ scope tập trung vào request correctness.

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

type Product = { id: string; name: string; description: string }
type SearchResult = { items: Product[]; total: number }
const keyword = ref('')
const category = ref('all')
const page = ref(1)
const pageSize = 20
const products = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
let controller: AbortController | undefined
let timer: ReturnType<typeof setTimeout> | undefined
let generation = 0

function isResult(x: unknown): x is SearchResult {
  if (typeof x !== 'object' || x === null) return false
  const v = x as Record<string, unknown>
  return Array.isArray(v.items) && v.items.every(
    p => typeof p?.id === 'string' &&
         typeof p?.name === 'string' &&
         typeof p?.description === 'string'
  ) && typeof v.total === 'number' && v.total >= 0
}

async function load() {
  const id = ++generation
  controller?.abort()
  controller = new AbortController()
  const signal = controller.signal
  loading.value = true
  error.value = ''
  const query = new URLSearchParams({
    q: keyword.value, category: category.value,
    page: String(page.value), pageSize: String(pageSize)
  })
  try {
    const response = await fetch('/api/search?' + query, { signal })
    if (!response.ok) throw new Error('HTTP ' + response.status)
    const data: unknown = await response.json()
    if (!isResult(data)) throw new Error('Invalid response')
    if (id === generation) {
      products.value = data.items
      total.value = data.total
    }
  } catch (e) {
    if (id === generation && !signal.aborted)
      error.value = 'Không tải được dữ liệu. Vui lòng thử lại.'
  } finally {
    if (id === generation) loading.value = false
  }
}

watch([keyword, category], () => {
  page.value = 1
  if (timer) clearTimeout(timer)
  controller?.abort()
  ++generation
  loading.value = true
  timer = setTimeout(load, 300)
})
watch(page, () => {
  if (timer) clearTimeout(timer)
  load()
})
load()

onBeforeUnmount(() => {
  if (timer) clearTimeout(timer)
  ++generation
  controller?.abort()
})
</script>

<template>
  <label for="search">Từ khóa</label>
  <input id="search" v-model="keyword">
  <label for="category">Danh mục</label>
  <select id="category" v-model="category">
    <option value="all">Tất cả</option>
    <option value="books">Sách</option>
    <option value="devices">Thiết bị</option>
  </select>
  <p aria-live="polite" v-if="loading">Đang tải...</p>
  <p role="alert" v-if="error">{{ error }}</p>
  <article v-for="p in products" :key="p.id">
    <h3>{{ p.name }}</h3>
    <div>{{ p.description }}</div>
  </article>
  <button :disabled="loading || page * pageSize >= total"
          @click="page++">Tiếp</button>
  <span>Trang {{ page }} / {{ Math.max(1, Math.ceil(total / pageSize)) }}</span>
</template>
```

Lưu ý: Ví dụ tối giản này có thể tạo hai lần load khi filter đổi đồng thời làm `page` reset từ giá trị khác 1: watcher của page có thể chạy cùng watcher filter. Production code nên hợp nhất state thành một query model và một watcher duy nhất (hoặc router query làm source of truth), áp dụng debounce cho keyword và immediate fetch cho page/category; test để đảm bảo đúng một request hữu ích cho mỗi transition. Nếu cần retry 429, dùng bounded exponential backoff có jitter, tôn trọng Retry-After và cancellation; không tự retry vô hạn.

## Giải thích thiết kế sau khi sửa

Generation guard bảo vệ correctness ngay cả khi abort không kịp ngăn response; AbortController giảm công việc không cần thiết trên client. URLSearchParams encode input đúng. Kiểm tra status/schema ngăn lỗi backend bị hiểu là kết quả hợp lệ. Template interpolation mặc định escape nội dung text; rich HTML cần sanitizer và policy riêng.

## Trade-offs

Debounce tăng độ trễ cảm nhận khoảng 300 ms nhưng giảm request storm. Cancellation không bảo đảm backend đã ngừng xử lý, vì vậy vẫn cần server-side rate limiting, query timeout và caching nếu có số liệu hỗ trợ. Generation counter đơn giản nhưng khi dùng router, SSR hoặc shared query cache cần phân định ownership để tránh duplicate fetching. Sanitizing rich text có chi phí bảo trì policy và có thể loại bỏ một số markup hợp lệ.

## Cách kiểm thử

1. **Component test:** Mock request A chậm, B nhanh; sau B, A hoàn thành cũng không ghi đè state.
2. **Failure-path test:** 429, 503, invalid JSON và invalid schema đều hiển thị error đúng; không báo empty results.
3. **Security test:** Description chứa HTML nguy hiểm phải hiển thị như text, không thực thi.
4. **Playwright E2E:** Đổi filter từ page 8 về page 1, back/forward và reload khôi phục query khi router sync được triển khai.
5. **Load/network test:** Gõ nhanh trên slow network; đo request count, abort count và latency tới kết quả cuối.

## Quan sát trong production

Theo dõi browser RUM: search request count per interaction, debounce ratio, cancellation rate, HTTP 429/503, client-side exceptions, p95 time-to-correct-results, và route/query mismatch. Correlate request ID với ASP.NET Core Application Insights dependency traces; đo API latency, query plan và throttling trước khi đề xuất cache.

## Câu hỏi phỏng vấn mở rộng

1. Nếu dùng TanStack Query cho Vue, query key và stale data policy nên thiết kế thế nào?
2. Khi backend hỗ trợ cursor pagination thay vì page number, UI và URL state thay đổi ra sao?
3. Với search có SEO requirements, khi nào cần SSR/prerender thay vì chỉ client-side rendering?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Webhook payment phải xác thực nguồn, kiểm tra business invariants và chống duplicate ở database; side effects cần durable outbox và downstream idempotency. Vue search phải bảo vệ state khỏi stale responses, phân biệt HTTP errors, kiểm soát input và render untrusted content an toàn. Cả hai tình huống đều minh họa rằng request thành công không đồng nghĩa business workflow hoàn tất chính xác.

## Mẫu tư duy cần nhớ

1. Xác minh trust boundary trước khi tin dữ liệu bên ngoài.
2. Thiết kế retry cùng idempotency và business state transition.
3. Đặt durable intent trong cùng transaction với thay đổi dữ liệu.
4. Chỉ latest relevant response được quyền cập nhật UI state.
5. Kiểm thử concurrency, failure windows và telemetry trước khi kết luận đã sửa lỗi.
