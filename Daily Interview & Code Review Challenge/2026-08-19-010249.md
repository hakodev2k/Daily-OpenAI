# Code Review Challenge 1 — Hangfire job gửi thông báo bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để gửi thông báo nhắc lịch. API có thể được gọi lại khi client timeout. Hệ thống chạy nhiều application instance và nhiều Hangfire worker. Mỗi notification phải được gửi tối đa một lần về mặt business, nhưng production thỉnh thoảng ghi nhận cùng một người dùng nhận hai email. Một số job cũng bị retry sau lỗi tạm thời từ provider.

## Đoạn code cần review

```csharp
public sealed class NotificationService
{
    private readonly AppDbContext _db;
    private readonly IBackgroundJobClient _jobs;

    public NotificationService(AppDbContext db, IBackgroundJobClient jobs)
    {
        _db = db;
        _jobs = jobs;
    }

    public async Task<Guid> ScheduleAsync(Guid userId, string message)
    {
        var notification = new Notification
        {
            Id = Guid.NewGuid(),
            UserId = userId,
            Message = message,
            Status = "Pending",
            CreatedAt = DateTime.UtcNow
        };

        _db.Notifications.Add(notification);
        await _db.SaveChangesAsync();

        _jobs.Enqueue<NotificationJob>(x => x.SendAsync(notification.Id));
        return notification.Id;
    }
}

public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _email;

    public NotificationJob(AppDbContext db, IEmailSender email)
    {
        _db = db;
        _email = email;
    }

    public async Task SendAsync(Guid notificationId)
    {
        var notification = await _db.Notifications
            .SingleAsync(x => x.Id == notificationId);

        if (notification.Status == "Sent")
            return;

        var user = await _db.Users.SingleAsync(x => x.Id == notification.UserId);

        await _email.SendAsync(user.Email, notification.Message);

        notification.Status = "Sent";
        notification.SentAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Tìm rủi ro concurrency, retry và reliability.
3. Giải thích vì sao lỗi có thể chỉ xuất hiện dưới tải hoặc khi provider/network lỗi.
4. Ưu tiên vấn đề theo mức độ ảnh hưởng.
5. Đề xuất implementation an toàn hơn.
6. Mô tả cách kiểm thử concurrency và failure path.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai worker có thể cùng đọc `Status == "Pending"` không?
- Điều gì xảy ra nếu email provider đã nhận request nhưng process chết trước `SaveChangesAsync()`?
- Việc lưu notification và enqueue Hangfire job có phải một atomic operation không?
- Retry của job tương tác với side effect bên ngoài như thế nào?
- Idempotency nên được đảm bảo ở application memory hay durable storage?

## Gợi ý

### Gợi ý 1

Đừng coi `if (Status == "Sent")` là một lock.

### Gợi ý 2

Hãy phân tích riêng hai khoảng lỗi: **DB commit → enqueue** và **send email → DB commit**. Một transaction DB đơn thuần không thể rollback một email đã gửi ra hệ thống bên ngoài.

## Kết quả code review tham khảo

### 1. Check-then-act không chống được concurrent execution

- **Problem:** Nhiều worker có thể cùng đọc `Pending`, rồi cùng gửi email.
- **Why:** Việc đọc trạng thái và thực hiện side effect không có cơ chế mutual exclusion/atomic claim ở durable storage.
- **Production impact:** Gửi trùng notification.
- **Severity:** Critical
- **Recommended fix:** Claim công việc atomically bằng optimistic concurrency/conditional update hoặc một durable processing state; vẫn phải thiết kế idempotency cho side effect.

### 2. Crash window sau khi provider nhận email

- **Problem:** Email có thể đã được gửi nhưng DB vẫn còn `Pending`.
- **Why:** External side effect và DB transaction không cùng một atomic transaction.
- **Production impact:** Hangfire retry và gửi email lần hai.
- **Severity:** Critical
- **Recommended fix:** Nếu provider hỗ trợ idempotency key, truyền một key ổn định như `notification.Id`. Nếu không, chấp nhận semantics thực tế và thiết kế deduplication/outbox/provider reconciliation phù hợp với business.

### 3. DB commit và enqueue không atomic

- **Problem:** Process có thể chết sau `SaveChangesAsync()` nhưng trước `Enqueue()`.
- **Why:** Hai durable operations độc lập.
- **Production impact:** Notification tồn tại mãi ở `Pending` nhưng không có job xử lý.
- **Severity:** High
- **Recommended fix:** Transactional outbox: lưu Notification và OutboxMessage trong cùng DB transaction; dispatcher riêng publish/enqueue rồi đánh dấu outbox đã xử lý.

### 4. Không có explicit state transition và recovery state

- **Problem:** Chỉ có `Pending/Sent`, không biểu diễn processing attempt, lỗi cuối cùng hoặc retry metadata.
- **Why:** Model quá đơn giản cho workflow có failure/retry.
- **Production impact:** Khó điều tra stuck jobs và khó recovery có kiểm soát.
- **Severity:** High
- **Recommended fix:** Lưu attempt count, last error, processed timestamp; nếu dùng trạng thái `Processing`, phải có lease/timeout hoặc cơ chế reclaim để tránh stuck vĩnh viễn.

### 5. Không truyền CancellationToken

- **Problem:** DB và provider calls không nhận cancellation khi execution bị hủy.
- **Why:** API của method không expose cancellation token.
- **Production impact:** Shutdown/deployment có thể kéo dài hoặc để work tiếp tục ngoài lifecycle mong muốn.
- **Severity:** Medium
- **Recommended fix:** Truyền cancellation token phù hợp từ job runtime xuống các I/O API nếu integration hỗ trợ.

### 6. String status dễ tạo invalid state

- **Problem:** `"Pending"`, `"Sent"` là magic strings.
- **Why:** Không có domain constraint rõ ràng.
- **Production impact:** Typo hoặc state ngoài dự kiến gây lỗi logic.
- **Severity:** Medium
- **Recommended fix:** Enum/value object kết hợp DB constraint khi phù hợp.

### 7. Thiếu observability theo notification/attempt

- **Problem:** Không có structured logs/tracing cho enqueue, attempt, provider response và transition.
- **Why:** Workflow không ghi correlation metadata.
- **Production impact:** Khó phân biệt duplicate enqueue, retry và provider ambiguity.
- **Severity:** Medium
- **Recommended fix:** Log `NotificationId`, Hangfire job/attempt, provider message id, duration và state transition; tuyệt đối tránh log nội dung nhạy cảm không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng transactional outbox cho khoảng lỗi DB→queue và atomic claim cho worker. External email vẫn cần idempotency key ở provider nếu muốn chống duplicate tốt qua crash window.

```csharp
public async Task<Guid> ScheduleAsync(
    Guid userId,
    string message,
    CancellationToken ct)
{
    var id = Guid.NewGuid();

    _db.Notifications.Add(new Notification
    {
        Id = id,
        UserId = userId,
        Message = message,
        Status = NotificationStatus.Pending,
        CreatedAt = DateTime.UtcNow
    });

    _db.OutboxMessages.Add(new OutboxMessage
    {
        Id = Guid.NewGuid(),
        Type = "NotificationRequested",
        AggregateId = id,
        CreatedAt = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(ct);
    return id;
}

public async Task SendAsync(Guid notificationId, CancellationToken ct)
{
    var claimed = await _db.Notifications
        .Where(x => x.Id == notificationId &&
                    x.Status == NotificationStatus.Pending)
        .ExecuteUpdateAsync(s => s
            .SetProperty(x => x.Status, NotificationStatus.Processing)
            .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

    if (claimed == 0)
        return;

    try
    {
        var data = await _db.Notifications
            .Where(x => x.Id == notificationId)
            .Select(x => new
            {
                x.Message,
                Email = x.User.Email
            })
            .SingleAsync(ct);

        await _email.SendAsync(
            data.Email,
            data.Message,
            idempotencyKey: notificationId.ToString(),
            cancellationToken: ct);

        await _db.Notifications
            .Where(x => x.Id == notificationId &&
                        x.Status == NotificationStatus.Processing)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, NotificationStatus.Sent)
                .SetProperty(x => x.SentAt, DateTime.UtcNow), ct);
    }
    catch
    {
        await _db.Notifications
            .Where(x => x.Id == notificationId &&
                        x.Status == NotificationStatus.Processing)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, NotificationStatus.Pending),
                CancellationToken.None);
        throw;
    }
}
```

Điểm quan trọng: code trên minh họa hướng thiết kế, không khẳng định mọi email provider đều hỗ trợ idempotency key. Nếu provider không hỗ trợ, cần quyết định business semantics rõ ràng và có reconciliation/deduplication ở nơi kiểm soát được.

## Trade-offs

Transactional outbox thêm bảng, dispatcher và cleanup nhưng loại bỏ khoảng lỗi DB commit rồi chưa enqueue. Atomic claim giảm concurrent duplicate nhưng một `Processing` state cần recovery nếu worker chết; production thường dùng lease/version/timeout thay vì một state không hết hạn. Distributed lock có thể hữu ích trong một số trường hợp nhưng không tự giải quyết crash window sau external side effect.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời 20 executions cùng `notificationId`; xác nhận chỉ một execution claim thành công.
2. **Failure-path:** giả lập crash/lỗi sau provider call nhưng trước DB update; xác minh retry dùng cùng idempotency key.
3. **Outbox integration:** commit notification rồi dừng process trước dispatcher; sau restart outbox vẫn được xử lý.
4. **Provider timeout:** mô phỏng timeout không rõ request đã được nhận hay chưa; kiểm tra policy không tạo duplicate ngoài semantics đã chọn.
5. **Recovery:** worker chết sau khi claim; xác minh lease/recovery mechanism đưa item về trạng thái có thể xử lý lại.

## Quan sát trong production

Theo dõi structured logs theo `NotificationId`, số attempt, số notification pending/processing quá SLA, outbox lag, provider latency/error rate, tỷ lệ retry và duplicate-detection count. Trace nên nối API request → DB/outbox → Hangfire execution → provider call.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao distributed lock vẫn không đảm bảo exactly-once side effect khi process chết sau provider call?
2. Nếu email provider không hỗ trợ idempotency key, bạn sẽ định nghĩa delivery semantics và reconciliation thế nào?
3. Khi nào bạn chọn queue broker thay vì Hangfire + transactional outbox?

# Code Review Challenge 2 — API tìm kiếm audit log có nguy cơ SQL injection và rò rỉ dữ liệu

**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép admin tìm audit log. Endpoint nhận từ khóa, tên cột sort và hướng sort. Production có hàng chục triệu audit records. QA báo rằng một số query rất chậm; security review đồng thời nghi ngờ tenant isolation chưa đủ chặt. Audit detail có thể chứa dữ liệu nhạy cảm.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;

    public AuditController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        string? search,
        string sort = "CreatedAt",
        string direction = "desc")
    {
        var tenantId = Request.Headers["X-Tenant-Id"].ToString();

        var sql = $@"
            SELECT Id, TenantId, UserEmail, Action, Detail, CreatedAt
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'
              AND (UserEmail LIKE '%{search}%'
                   OR Action LIKE '%{search}%'
                   OR Detail LIKE '%{search}%')
            ORDER BY {sort} {direction}";

        var rows = await _db.Database
            .SqlQueryRaw<AuditRow>(sql)
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Tenant ID lấy từ header do client kiểm soát

- **Problem:** User đã authenticated có thể thay `X-Tenant-Id`.
- **Why:** Authentication không đồng nghĩa với authorization cho tenant được yêu cầu.
- **Production impact:** Cross-tenant data exposure.
- **Severity:** Critical
- **Recommended fix:** Resolve tenant từ trusted claims/membership server-side và enforce policy; không tin tenant identity do client tự khai nếu chưa validate quyền.

### 2. SQL injection qua tenant/search

- **Problem:** Giá trị được nội suy trực tiếp vào SQL.
- **Why:** `SqlQueryRaw` nhận chuỗi đã ghép từ untrusted input.
- **Production impact:** Đọc/sửa dữ liệu trái phép tùy quyền DB và query context.
- **Severity:** Critical
- **Recommended fix:** Parameterize values bằng LINQ hoặc parameterized SQL API.

### 3. SQL injection qua `sort` và `direction`

- **Problem:** SQL identifiers/tokens được ghép trực tiếp.
- **Why:** Parameter SQL thông thường không đại diện cho column identifier; cần allowlist mapping.
- **Production impact:** Injection hoặc query bị phá vỡ.
- **Severity:** Critical
- **Recommended fix:** Map enum/API sort key sang expression hoặc known column; direction chỉ nhận `asc/desc` đã validate.

### 4. Trả `Detail` mặc định có thể lộ dữ liệu nhạy cảm

- **Problem:** Endpoint trả nguyên audit payload.
- **Why:** Projection không áp dụng least-data principle.
- **Production impact:** PII/secrets/token-like values có thể bị expose cho role không cần xem.
- **Severity:** High
- **Recommended fix:** Redact khi ghi log, phân quyền field-level nếu cần và projection chỉ trả dữ liệu cần thiết.

### 5. Không phân trang/giới hạn kết quả

- **Problem:** `ToListAsync()` tải mọi row match.
- **Why:** Endpoint không có page size/cursor.
- **Production impact:** Memory pressure, latency cao, DB load và response khổng lồ.
- **Severity:** High
- **Recommended fix:** Bắt buộc page size giới hạn; với dataset lớn và sort ổn định, cân nhắc keyset pagination.

### 6. Leading-wildcard search trên nhiều text columns khó scale

- **Problem:** `LIKE '%term%'` thường không tận dụng B-tree index thông thường hiệu quả cho substring search.
- **Why:** Pattern bắt đầu bằng wildcard và còn search `Detail` có thể rất lớn.
- **Production impact:** Scan lớn, CPU/I/O tăng.
- **Severity:** High
- **Recommended fix:** Làm rõ search requirement; dùng exact/prefix search khi đủ, hoặc công nghệ full-text/search index phù hợp. Luôn đo execution plan thực tế.

### 7. Không có CancellationToken

- **Problem:** Client disconnect không được propagate vào DB query.
- **Why:** Action không nhận `CancellationToken`.
- **Production impact:** Expensive query có thể tiếp tục tiêu tốn tài nguyên.
- **Severity:** Medium
- **Recommended fix:** Nhận `CancellationToken` và truyền vào async DB operation.

### 8. Không validate độ dài/search shape

- **Problem:** Search input không giới hạn hợp lý.
- **Why:** Không có request model/validation.
- **Production impact:** Query đắt, abuse và khó kiểm soát SLA.
- **Severity:** Medium
- **Recommended fix:** Request DTO với max length, allowed sort fields, page size và semantic validation.

## Phiên bản code đề xuất

```csharp
public enum AuditSort
{
    CreatedAt,
    UserEmail,
    Action
}

public sealed record AuditSearchRequest(
    string? Search,
    AuditSort Sort = AuditSort.CreatedAt,
    bool Descending = true,
    int PageSize = 50,
    DateTime? Before = null);

[Authorize(Policy = "AuditReader")]
[HttpGet]
public async Task<ActionResult<IReadOnlyList<AuditListItem>>> Search(
    [FromQuery] AuditSearchRequest request,
    CancellationToken ct)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    var pageSize = Math.Clamp(request.PageSize, 1, 100);
    var search = request.Search?.Trim();

    IQueryable<AuditLog> query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrEmpty(search))
    {
        query = query.Where(x =>
            x.UserEmail.Contains(search) ||
            x.Action.Contains(search));
    }

    if (request.Before is not null)
        query = query.Where(x => x.CreatedAt < request.Before.Value);

    query = (request.Sort, request.Descending) switch
    {
        (AuditSort.UserEmail, false) => query.OrderBy(x => x.UserEmail),
        (AuditSort.UserEmail, true)  => query.OrderByDescending(x => x.UserEmail),
        (AuditSort.Action, false)    => query.OrderBy(x => x.Action),
        (AuditSort.Action, true)     => query.OrderByDescending(x => x.Action),
        (_, false) => query.OrderBy(x => x.CreatedAt).ThenBy(x => x.Id),
        _ => query.OrderByDescending(x => x.CreatedAt).ThenByDescending(x => x.Id)
    };

    var rows = await query
        .Take(pageSize)
        .Select(x => new AuditListItem(
            x.Id,
            x.UserEmail,
            x.Action,
            x.CreatedAt))
        .ToListAsync(ct);

    return Ok(rows);
}
```

Đây là hướng tham khảo. `Contains` vẫn có thể tạo query substring đắt tùy provider/database; nếu requirement thực sự cần full-text search trên hàng chục triệu records, cần benchmark và chọn search strategy phù hợp thay vì coi LINQ là giải pháp performance tự động. Tenant claim cũng chỉ đáng tin khi authentication/issuer và membership model của hệ thống bảo đảm claim đó phản ánh tenant được phép truy cập.

## Trade-offs

LINQ/expression allowlist đơn giản và an toàn hơn raw dynamic SQL cho use case này, nhưng raw SQL vẫn hợp lý khi cần query đặc thù nếu parameterization và allowlist được làm đúng. Keyset pagination nhanh và ổn định hơn deep offset pagination cho timeline lớn nhưng API phức tạp hơn. Full-text/search engine cải thiện khả năng tìm kiếm nhưng tăng operational cost và consistency concerns.

## Cách kiểm thử

1. **Security test:** user tenant A gửi header/parameter giả tenant B; không được thấy dữ liệu tenant B.
2. **Injection test:** truyền payload đặc biệt vào search/sort; query vẫn được parameterize/allowlist và không thay đổi cấu trúc SQL.
3. **Authorization test:** authenticated user thiếu `AuditReader` bị từ chối.
4. **Load/DB test:** dataset lớn, đo latency và execution plan cho các search pattern phổ biến.
5. **Data exposure test:** response list không chứa `Detail` hoặc trường nhạy cảm ngoài contract.

## Quan sát trong production

Theo dõi p50/p95/p99 latency, DB duration, rows scanned/returned, timeout/cancellation rate, page size, rejected authorization attempts và slow-query plans. Security logs nên ghi actor, tenant được resolve server-side và operation nhưng không ghi search payload/audit detail nhạy cảm một cách vô điều kiện.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một user có quyền truy cập nhiều tenant thì bạn thiết kế tenant context và authorization thế nào?
2. Khi nào keyset pagination không phù hợp với yêu cầu sort động?
3. Nếu business bắt buộc substring search trong `Detail`, bạn sẽ benchmark và lựa chọn PostgreSQL/SQL Server search capability hoặc external search index dựa trên tiêu chí nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry và concurrency biến một background job tưởng đơn giản thành bài toán idempotency và durable state.
- Transactional outbox giải quyết khoảng lỗi giữa database commit và publish/enqueue, nhưng không tự biến external side effect thành exactly-once.
