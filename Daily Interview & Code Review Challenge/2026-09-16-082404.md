# Câu 1 — Vì sao API xử lý file lớn bị memory spike dù object cuối cùng không lớn?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, memory allocation, Garbage Collector, LOH, streams, serialization, ASP.NET Core, performance profiling

## Bối cảnh

Một ASP.NET Core API nhận file JSON export từ hệ thống đối tác, kích thước thường 5–20 MB nhưng đôi lúc 80–150 MB. Implementation hiện đọc toàn bộ request thành `byte[]`, chuyển sang `string`, deserialize thành object graph rồi transform thành khoảng 10.000 records để ghi database.

Production chạy nhiều instances trên Azure App Service. Khi vài file lớn được upload gần nhau, memory của process tăng nhanh, GC activity tăng và p99 latency của các endpoint không liên quan cũng xấu đi. Sau một thời gian memory có giảm nhưng không ngay lập tức về mức cũ. Team kết luận rằng đây chắc chắn là “memory leak” và đề xuất gọi `GC.Collect()` sau mỗi import.

Chưa có allocation profile, GC counters hoặc heap dump. Chưa rõ request body có cần giữ toàn bộ trong memory để validate hay không.

## Câu hỏi chính

Hãy giải thích các cơ chế allocation/GC nào có thể tạo ra triệu chứng này dù không có memory leak thực sự, phân tích vì sao `GC.Collect()` không phải mặc định đúng, và trình bày cách bạn chứng minh root cause rồi redesign import path nếu measurement xác nhận large transient allocations là vấn đề.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent imports là bao nhiêu và có giới hạn upload/concurrency riêng cho endpoint không?
2. Allocation profile cho thấy phần lớn bytes đến từ request buffering, UTF-16 string, JSON object graph hay transform buffers?
3. Sau khi import hoàn tất, các object lớn còn reachable trong heap dump hay chỉ memory committed của runtime/process chưa giảm ngay?
4. JSON contract có cho phép streaming từng record hay validation bắt buộc cần toàn bộ document?
5. Database write hiện buffer toàn bộ records hay có thể xử lý theo bounded batches?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt **live managed objects**, managed heap segments đã commit/reserve và process working set. Memory không giảm ngay không tự động chứng minh object vẫn bị reference.

### Gợi ý 2

Theo dõi chuỗi copy: request bytes → `byte[]` → `string` → parsed object graph → transformed collections. Các allocation lớn có GC behavior khác các object nhỏ.

### Gợi ý 3

Giải pháp tốt thường giảm peak live set và concurrency pressure bằng streaming/batching/bounded work, nhưng chỉ khi input contract và validation semantics cho phép.

## Cấu trúc trả lời đề xuất

1. Xác nhận business impact và workload shape.
2. Phân biệt leak với allocation pressure/retained capacity.
3. Mô tả allocation path và GC/LOH implications.
4. Thu thập GC counters, allocation profile và heap evidence.
5. Xác định object nào thực sự sống lâu và vì sao.
6. Đánh giá streaming, batching và concurrency limiting.
7. Kiểm tra correctness/validation khi đổi processing model.
8. Load test với realistic file-size distribution.
9. Theo dõi memory, GC pause và endpoint latency sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không gọi triệu chứng là memory leak khi chưa chứng minh object không còn cần thiết vẫn bị giữ reference.
- Nhận ra multiple full-size representations của cùng payload có thể làm peak memory lớn hơn file input nhiều lần.
- Biết large objects tạo pressure lên managed heap/LOH và GC; không khẳng định một threshold/version-specific behavior nếu chưa xác minh runtime cụ thể.
- Không dùng `GC.Collect()` như một cleanup API cho application design bình thường.
- Đề xuất measurement trước optimization.

### Điểm cộng

- Dùng runtime counters/profiling để xem allocation rate, heap size, Gen 2/GC behavior, pause time và working set.
- Phân biệt object retention với heap fragmentation/capacity và OS working set.
- Đề xuất bounded concurrency để tránh nhiều imports lớn cùng nhân peak live set.
- Đánh giá streaming JSON + batched persistence thay vì chỉ “tăng memory plan”.

### Senior+

- Thảo luận failure semantics của streaming: partial processing, validation, transaction boundary, retry/idempotency.
- Nhận ra streaming có thể giảm memory nhưng tăng complexity và không phù hợp nếu business yêu cầu validate toàn document atomically trước khi commit.
- Thiết kế performance test theo distribution thực tế thay vì một file benchmark đơn lẻ.

## Hướng giải quyết tham khảo

Một file 100 MB không có nghĩa process chỉ cần thêm khoảng 100 MB. Nếu request được buffer thành `byte[]`, sau đó decode thành .NET `string`, parse thành object graph rồi tạo thêm DTO/list để persistence, nhiều representation cùng tồn tại trong một khoảng thời gian. Peak live memory vì vậy có thể cao hơn đáng kể input size. Concurrency nhân áp lực này lên nhiều lần.

GC quản lý managed objects dựa trên reachability và generation/lifetime; process memory không nhất thiết lập tức trả về OS ngay sau khi objects trở thành collectible. Vì vậy graph memory tăng rồi giảm chậm chưa đủ để kết luận leak. Cần xem heap dump/reference paths nếu nghi retention, đồng thời xem allocation profile và runtime counters để biết allocation rate, heap size, GC frequency/pause và working set.

`GC.Collect()` ép collection nhưng không loại bỏ reference đang sống và có thể gây expensive full collections/pause, làm throughput xấu hơn. Chỉ cân nhắc explicit collection trong các trường hợp đặc biệt đã đo và hiểu rõ; nó không thay cho việc giảm allocation hoặc lifetime.

Nếu profile xác nhận transient buffering là nguồn chính, redesign có thể đọc request stream, parse theo streaming model nếu JSON shape hỗ trợ, transform một bounded batch rồi persist, giải phóng batch trước khi đọc tiếp. Đồng thời giới hạn số imports lớn chạy đồng thời để peak memory có upper bound thực tế. Nếu cần atomic all-or-nothing validation, có thể stream vào temporary durable storage trước, validate/process theo phases thay vì giữ mọi thứ trong RAM.

Cần tránh silently đổi transaction semantics. Một import streaming ghi từng batch có thể để partial state khi batch sau fail. Có thể dùng staging tables/import session + finalization, hoặc transaction nếu kích thước/locking cost phù hợp. Retry phải gắn với import identity để không duplicate records.

Testing nên gồm file nhỏ, median, p95/p99 size, malformed input, concurrent large imports và dependency slowdown. Sau fix, so sánh peak working set, managed heap, allocation rate, GC pause, import duration và p95/p99 của endpoints khác.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak. Trước hết tôi muốn phân biệt object còn reachable với allocation pressure và heap/working-set behavior. Flow hiện tại có ít nhất nhiều representation của cùng payload: byte array, string, deserialized graph và transformed records. Với file lớn và nhiều imports đồng thời, peak live set có thể tăng rất mạnh và kéo theo GC pressure, ảnh hưởng cả request khác.

Tôi sẽ lấy allocation profile và GC counters trước, rồi nếu nghi retention thì heap dump để xem reference path. `GC.Collect()` không sửa được object còn reference và có thể tạo full-GC pause nên tôi không dùng nó làm mặc định.

Nếu evidence cho thấy buffering là bottleneck, tôi sẽ giảm peak live set bằng streaming/batching và giới hạn concurrency. Nhưng tôi sẽ hỏi lại atomicity requirement: nếu import phải validate toàn bộ trước khi commit thì streaming trực tiếp vào production tables có thể làm semantics xấu đi. Khi đó tôi có thể stage dữ liệu rồi finalize. Cuối cùng tôi load-test bằng nhiều file size và concurrent imports, đo allocation, GC pause, working set và p99 của toàn service để chứng minh improvement.”

## Câu hỏi đào sâu

1. Nếu heap dump cho thấy phần lớn object lớn đã collectible nhưng process working set vẫn cao, bạn điều tra tiếp thế nào?
2. Nếu Product yêu cầu toàn bộ file phải được reject mà không ghi bất kỳ business row nào khi record cuối cùng invalid, streaming design của bạn thay đổi ra sao?
3. Một teammate đề xuất tăng App Service memory gấp đôi thay vì sửa pipeline; khi nào đó là quyết định hợp lý?

## Lỗi trả lời thường gặp

- Khẳng định memory tăng là leak mà không kiểm tra reachability/reference paths.
- Cho rằng `Dispose()` hoặc `GC.Collect()` sẽ “xóa object khỏi RAM” theo cách deterministic.
- Chỉ đề xuất streaming mà bỏ qua atomicity, retry và partial-processing semantics.
- Tối ưu dựa trên file size nhưng không xét concurrent imports.
- Không đo tác động lên p95/p99 và GC pause của các endpoints khác.

## Thang điểm 0–10

- **0–2:** Chỉ nói tăng RAM hoặc gọi `GC.Collect()`.
- **3–4:** Biết GC/LOH nhưng không có evidence-driven investigation.
- **5–6:** Phân biệt leak với allocation pressure, biết profiling và đề xuất streaming/batching hợp lý.
- **7–8:** Phân tích peak live set, concurrency, GC telemetry, bounded processing và testing tốt.
- **9–10:** Thêm transaction/failure/idempotency trade-offs, conditional design và cách chứng minh improvement production-ready.

# Câu 2 — Sau release, users ở một số region vẫn thấy HTML cũ dù origin đã đúng

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Akamai/CDN, HTTP caching, Cache-Control, ASP.NET Core, Azure App Service, observability, incident response, deployment, web performance

## Bối cảnh

Một marketing website chạy ASP.NET Core trên Azure App Service và đặt Akamai phía trước. Release mới sửa một legal banner và thay metadata SEO. Deployment hoàn tất, health checks xanh và gọi trực tiếp origin cho thấy HTML mới. Tuy nhiên support nhận phản ánh rằng một số users vẫn thấy HTML cũ khoảng 20–40 phút, trong khi users khác thấy bản mới ngay.

Team có nhiều giả thuyết: browser cache, Akamai edge cache, deployment slot swap chưa đồng nhất, application in-memory cache hoặc ISP/proxy. Một developer muốn purge toàn bộ CDN sau mọi deployment. Developer khác muốn đặt `Cache-Control: no-store` cho mọi HTML để “không bao giờ stale”.

Chưa có response-header samples từ affected users, CDN cache-status evidence hoặc mapping theo region/POP. Static assets dùng fingerprinted filenames nhưng HTML route không versioned.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào để vừa giảm business impact vừa xác định layer thực sự phục vụ stale content, và sau khi có root cause bạn sẽ thiết kế cache/deployment strategy thế nào để cân bằng freshness, origin load và performance?

## Câu hỏi làm rõ nên cân nhắc

1. Legal banner có freshness/SLA bắt buộc ngay lập tức hay stale vài phút được chấp nhận?
2. Response headers ở browser bị ảnh hưởng khác gì request trực tiếp origin và request qua CDN?
3. CDN configuration có cache HTML theo URL, query, cookies, host, language/market hay các dimensions nào khác?
4. Release có thay đổi cache directives/invalidation process hay chỉ application content?
5. Có thể tái hiện stale response từ cùng POP/region và xác định object age/version không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng purge toàn bộ. Trước hết xác định **layer nào sở hữu stale object** bằng response evidence và controlled requests.

### Gợi ý 2

So sánh origin response với CDN response và browser/network trace; kiểm tra `Cache-Control`, `Age`, `ETag`/validators và CDN-specific diagnostic headers/configuration khi có quyền truy cập.

### Gợi ý 3

Deployment freshness là một contract. Fingerprinted assets, HTML TTL/revalidation và targeted invalidation có thể có policies khác nhau.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và freshness requirement.
2. Stabilize bằng targeted mitigation nếu legal content cần tức thời.
3. Thu response samples từ affected/unaffected paths/regions.
4. So sánh browser → CDN → origin.
5. Lập competing hypotheses và loại từng layer bằng evidence.
6. Xác nhận root cause trước permanent change.
7. Thiết kế cache policy theo content type/freshness contract.
8. Tích hợp invalidation/versioning vào release khi cần.
9. Test nhiều POP/browser paths.
10. Theo dõi cache hit, age, origin load và stale-version signals.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu từ impact/stabilization, không nhảy thẳng tới cấu hình.
- So sánh origin và edge response có cùng URL/context.
- Không mặc định CDN là root cause chỉ vì origin đúng.
- Không dùng `no-store` toàn bộ như universal fix.
- Không purge toàn CDN mỗi deployment nếu targeted/versioned strategy đủ.

### Điểm cộng

- Phân tích cache key/vary dimensions, TTL, revalidation và browser cache riêng với CDN cache.
- Dùng request/response version marker để biết chính xác artifact/content version đang được serve.
- Static immutable fingerprinted assets có policy khác HTML mutable.
- Xem slot swap/application cache là hypothesis riêng và chứng minh bằng direct-origin/version evidence.

### Senior+

- Định nghĩa freshness SLO theo content class: legal/security-sensitive khác marketing content bình thường.
- Thiết kế safe release với targeted purge/invalidation, short HTML TTL hoặc revalidation tùy requirement.
- Đánh giá blast radius/origin surge khi purge lớn và cache-miss storm sau invalidation.

## Hướng giải quyết tham khảo

Đầu tiên cần xác định severity. Nếu legal banner phải đúng ngay lập tức, có thể thực hiện targeted purge/invalidation cho các URLs liên quan hoặc tạm bypass cache theo change procedure đã kiểm soát, đồng thời tiếp tục điều tra. Nếu stale 20–40 phút vẫn nằm trong contract thì ưu tiên evidence trước mitigation lớn.

Thu cùng một URL từ affected browser, một controlled client qua CDN và direct origin. Ghi status, body/version marker và relevant cache headers. `Age`/validators và CDN diagnostic information có thể giúp, nhưng exact Akamai headers/tools phụ thuộc property/configuration hiện hành nên phải dùng configuration/documentation của hệ thống thay vì giả định một header cố định.

Các hypotheses cần tách riêng: browser giữ object cũ; CDN POP có object cũ do TTL/invalidation; cache key thiếu dimension; application cache ở origin; slot instances chạy artifact khác nhau; hoặc intermediary khác. Direct origin mới chỉ giảm xác suất một số origin hypotheses, không chứng minh mọi origin instance/context đều giống nhau.

Nếu root cause là edge TTL không phù hợp release freshness, permanent design nên phân loại content. Fingerprinted JS/CSS/images có thể cache lâu vì URL đổi khi content đổi. HTML mutable nên có TTL/revalidation phù hợp freshness SLO. Với thay đổi cần visible nhanh, pipeline có thể targeted invalidate URLs hoặc dùng version strategy. Không nên mặc định `no-store` vì mất CDN/browser benefits và tăng origin load/latency.

Purge toàn bộ cũng có cost: cache hit ratio tụt đồng loạt, origin nhận burst và blast radius lớn. Targeted invalidation hoặc versioned assets thường an toàn hơn. Nếu content thay đổi qua CMS ngoài deployment, invalidation strategy cũng phải bao phủ publish workflow chứ không chỉ CI/CD.

Verification cần test từ nhiều regions/POPs, browser reload semantics và authenticated/personalized variants nếu có. Telemetry nên có response version/build marker, cache hit/miss, object age nếu platform expose, origin request rate/latency và release timestamp correlation.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng purge toàn bộ hay `no-store`. Trước hết tôi xác định legal banner có yêu cầu freshness bao nhiêu; nếu impact cao tôi targeted invalidate URL bị ảnh hưởng để giảm blast radius.

Sau đó tôi lấy cùng request từ affected browser, qua CDN và direct origin, giữ nguyên host/query/cookies/language context, rồi so sánh body version và cache headers. Tôi muốn chứng minh stale object nằm ở browser, edge hay origin/application cache. Tôi cũng kiểm tra nhiều origin instances nếu slot swap có thể liên quan.

Nếu root cause là HTML edge TTL quá dài, tôi sẽ thiết kế policy theo content class: fingerprinted static assets cache dài; mutable HTML có TTL/revalidation theo freshness SLO; các legal/security changes có targeted invalidation trong release/publish flow. Tôi tránh purge toàn CDN vì nó làm cache-miss storm và tăng origin load.

Cuối cùng tôi verify nhiều POPs và theo dõi build/content version, cache hit/miss, origin traffic và stale duration. Mục tiêu không phải zero caching mà là cache behavior phù hợp freshness contract.”

## Câu hỏi đào sâu

1. Nếu stale chỉ xảy ra cho một language/market, cache-key investigation của bạn thay đổi thế nào?
2. Nếu Product yêu cầu legal changes visible toàn cầu dưới 30 giây, bạn chọn TTL ngắn hay event-driven invalidation, và failure mode của từng cách là gì?
3. Nếu purge toàn bộ chỉ mất vài giây và chưa từng gây incident, tại sao không cứ dùng cách đơn giản đó?

## Lỗi trả lời thường gặp

- Kết luận Akamai sai chỉ vì direct origin trả content mới.
- Purge mọi thứ trước khi capture evidence trong incident không khẩn cấp.
- Dùng `no-store` cho toàn site mà không đánh giá performance/origin capacity.
- Không phân biệt browser cache, edge cache và application cache.
- Không có version marker/telemetry để chứng minh response thuộc release nào.

## Thang điểm 0–10

- **0–2:** Chỉ nói clear browser cache hoặc purge CDN.
- **3–4:** Biết TTL/Cache-Control nhưng investigation tuyến tính, ít evidence.
- **5–6:** Phân lớp browser/CDN/origin và có controlled comparison.
- **7–8:** Có stabilization, competing hypotheses, cache-policy trade-offs và observability.
- **9–10:** Thiết kế freshness SLO theo content class, targeted invalidation/versioning và đánh giá cache-miss blast radius/origin capacity.

# Câu 3 — Modernize ứng dụng .NET Framework/IIS: App Service, container hay giữ Windows trước?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework, modern .NET, IIS, Windows Server, Azure App Service, Linux hosting, containers, migration strategy, CI/CD, architecture trade-offs

## Bối cảnh

Một enterprise management portal khoảng 8 năm tuổi chạy `.NET Framework 4.5` trên IIS/Windows Server. Ứng dụng gồm ASP.NET MVC, một số scheduled jobs chạy trong web process, SQL Server, file exports ghi vào local filesystem, Windows-integrated assumptions ở vài integration cũ và jQuery frontend.

Business muốn giảm operational burden và tiến tới modern .NET. Team có ba ý kiến:

1. Rewrite toàn bộ sang .NET 10 + React + microservices + Kubernetes.
2. Containerize ứng dụng hiện tại trước rồi chuyển thẳng lên Linux.
3. Giữ nguyên Windows/IIS vô thời hạn vì migration có rủi ro.

Hệ thống quan trọng nhưng traffic vừa phải. Downtime cho release bị giới hạn, song chưa có requirement bắt buộc Kubernetes/microservices. Test automation hiện mỏng. Một số third-party dependencies chưa được audit compatibility.

## Câu hỏi chính

Bạn sẽ xây migration strategy và target hosting architecture như thế nào để giảm rủi ro nhưng vẫn tạo đường đi thực tế tới modern .NET? Hãy nêu những thông tin cần xác minh, cách chia migration thành stages, tiêu chí chọn App Service/Windows/Linux/container/Kubernetes và rollback/verification strategy.

## Câu hỏi làm rõ nên cân nhắc

1. Những dependencies nào thực sự yêu cầu .NET Framework/Windows/IIS hoặc Windows authentication semantics?
2. Local filesystem chứa transient files hay business-critical durable data, và có instance affinity assumption không?
3. Scheduled jobs có idempotent không và chuyện gì xảy ra nếu web app scale thành nhiều instances?
4. Current deployment topology, RTO/RPO, rollback time và database migration process là gì?
5. Test coverage nào bảo vệ các business flows quan trọng trước framework/hosting migration?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn target platform trước khi lập **compatibility and operational dependency inventory**.

### Gợi ý 2

Tách modernization dimensions: framework/runtime, hosting OS, deployment packaging, frontend, application architecture và data migration. Không nhất thiết đổi tất cả trong một release.

### Gợi ý 3

Một migration tốt có intermediate states deployable, observable và rollback được. Kubernetes/microservices chỉ hợp lý khi requirements vận hành chứng minh complexity đó đáng giá.

## Cấu trúc trả lời đề xuất

1. Clarify business constraints/RTO/RPO/release windows.
2. Inventory dependencies và Windows/IIS coupling.
3. Establish characterization/integration/E2E tests cho critical flows.
4. Tách runtime modernization khỏi architecture rewrite.
5. Chọn smallest viable target cho từng stage.
6. Externalize filesystem/config/secrets/background jobs khi cần scale/cloud hosting.
7. Migrate incrementally và instrument mỗi stage.
8. Thiết kế DB compatibility/expand-contract khi cần.
9. Canary/slot/parallel verification và rollback.
10. Chỉ thêm containers/Kubernetes/microservices nếu operational requirement justify.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chấp nhận rewrite-from-scratch như mặc định.
- Audit package/API/Windows dependencies trước khi cam kết Linux hoặc modern .NET target.
- Tăng test safety net trước các bước migration lớn.
- Nhận ra local filesystem và in-process scheduled jobs là hosting/scale concerns.
- Có staged rollout và rollback plan.

### Điểm cộng

- Phân biệt framework migration với hosting migration để giảm simultaneous variables.
- Externalize durable files sang storage phù hợp nếu multi-instance/cloud requirement cần.
- Tách scheduled work khỏi web process hoặc thiết kế distributed coordination/idempotency nếu scale-out.
- Dùng deployment slots/canary/parallel verification khi platform và architecture cho phép.
- Database changes theo backward-compatible expand/contract khi old/new versions cần coexist.

### Senior+

- Đưa ra decision criteria thay vì một target tuyệt đối.
- Có thể chọn App Service Windows như intermediate landing zone nếu Windows dependencies còn tồn tại, rồi tiếp tục loại coupling trước Linux/container.
- Nhận ra container không tự làm .NET Framework application trở thành Linux-compatible.
- Kubernetes chỉ được chọn nếu cần orchestration capabilities đủ lớn để trả complexity/operations cost.

## Hướng giải quyết tham khảo

Bước đầu không phải chọn Kubernetes hay Linux mà là inventory. Cần xác định package compatibility, `System.Web`/ASP.NET MVC dependencies, Windows-only APIs, authentication, COM/native dependencies nếu có, filesystem assumptions, scheduled jobs, configuration/secrets, IIS modules và deployment behavior. Cũng cần baseline production telemetry và critical user journeys.

Vì test automation mỏng, trước migration nên thêm characterization/integration tests cho business rules, API/DB integration và Playwright E2E cho vài critical flows. Mục tiêu không phải 100% coverage mà là confidence cho những boundaries sẽ thay đổi.

Sau đó chia dimensions. Có thể trước tiên làm application dễ di chuyển hơn: externalize configuration/secrets, thay durable local files bằng Azure Blob Storage nếu requirement phù hợp, làm jobs idempotent/tách khỏi web lifecycle, chuẩn hóa logging/health checks. Những thay đổi này có giá trị ngay cả khi vẫn ở IIS.

Runtime migration cần đánh giá đường nâng cấp thực tế từ .NET Framework app sang modern .NET theo APIs/packages đang dùng. Không nên giả định chỉ đổi target framework là đủ. Một số modules có thể được strangled/migrated dần nếu boundaries rõ; phần còn lại tiếp tục chạy ổn định. Nếu Windows coupling còn lớn, App Service Windows hoặc Windows-based hosting có thể là intermediate target để giảm server operations trước khi ép Linux. Nếu đã loại Windows dependencies và application phù hợp, App Service on Linux có thể đơn giản hơn Kubernetes cho traffic vừa phải.

Containerization là packaging/isolation choice, không phải compatibility converter. Một .NET Framework application phụ thuộc Windows không thể chỉ đóng image rồi mặc định chạy Linux. Kubernetes cũng thêm cluster operations, networking, probes, resource management và deployment complexity; không có requirement thì App Service có thể là target hợp lý hơn.

Database migration cần backward compatibility nếu old/new versions coexist trong slot/canary. Dùng expand-contract cho schema changes phù hợp, deploy code có thể làm việc với transitional schema, quan sát rồi mới remove old columns/contracts. Rollback phải được rehearsal, đặc biệt khi database migration không trivially reversible.

Mỗi stage cần success metrics: error rate, p95/p99, critical-flow success, job correctness, resource usage và business reconciliation. Release strategy có thể dùng slots/canary/parallel path tùy platform; exact mechanism phụ thuộc target đã chọn. Chỉ chuyển sang microservices khi service boundaries, independent scaling/deployment/ownership hoặc reliability requirements đủ mạnh; nếu không, một modularized monolith trên managed hosting có thể rẻ và an toàn hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chọn rewrite hay Kubernetes trước. Tôi bắt đầu bằng dependency inventory: package/API nào khóa chúng ta vào .NET Framework, Windows, IIS, local filesystem và Windows auth; jobs đang dựa vào web-process lifecycle ra sao; database rollout và rollback hiện thế nào.

Vì test automation mỏng, tôi tạo safety net cho critical flows trước. Sau đó tôi tách modernization thành nhiều dimensions. Tôi có thể externalize config/secrets/files, làm background jobs idempotent và cải thiện observability trong khi app vẫn chạy IIS. Tiếp theo mới migrate runtime theo compatibility evidence.

Nếu Windows coupling chưa loại được, App Service Windows có thể là intermediate landing zone hợp lý để giảm server operations. Khi app đã portable, tôi đánh giá App Service Linux/container. Tôi chỉ chọn Kubernetes nếu có requirement orchestration/scaling/operational cụ thể đủ để justify cluster complexity. Container không tự biến .NET Framework thành Linux-compatible.

Mỗi stage phải deploy được, đo được và rollback được. Với DB tôi ưu tiên backward-compatible schema khi old/new versions coexist. Tôi dùng critical E2E/integration tests, health/telemetry và canary/slot strategy phù hợp. Mục tiêu là giảm số biến thay đổi mỗi lần, không biến modernization thành một big-bang rewrite.”

## Câu hỏi đào sâu

1. Nếu 20% code phụ thuộc một Windows-only document library chưa có replacement, bạn có trì hoãn toàn bộ migration không?
2. Nếu CTO yêu cầu Kubernetes vì “đó là tiêu chuẩn hiện đại”, bạn sẽ dùng tiêu chí kỹ thuật và operational nào để phản biện hoặc chấp nhận?
3. Nếu database migration của release mới không backward-compatible với version cũ, rollback strategy của bạn thay đổi thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất modernization với rewrite toàn bộ.
- Cho rằng Docker/container tự giải quyết Windows/.NET Framework compatibility.
- Chọn Kubernetes/microservices vì xu hướng thay vì requirements.
- Bỏ qua filesystem, background jobs, authentication và database compatibility.
- Migration plan không có characterization tests, telemetry hoặc rollback rehearsal.

## Thang điểm 0–10

- **0–2:** Chọn một target platform theo sở thích, không audit dependencies.
- **3–4:** Có migration steps nhưng vẫn big-bang hoặc thiếu rollback/testing.
- **5–6:** Có inventory, staged migration, test safety net và hosting trade-offs.
- **7–8:** Tách modernization dimensions, xử lý Windows coupling/jobs/filesystem/DB rollout tốt.
- **9–10:** Đưa ra conditional architecture decision, intermediate states, operational economics, backward compatibility và measurable rollback-safe delivery.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Ba bài hôm nay cùng kiểm tra khả năng phân biệt **triệu chứng** với **cơ chế thực sự**. Memory cao không tự động là leak; stale HTML không tự động là CDN bug; legacy hosting không tự động đòi rewrite hoặc Kubernetes. Senior-level reasoning cần tạo hypotheses, thu evidence, xác định boundary chịu trách nhiệm rồi mới chọn intervention có blast radius phù hợp.

Ở runtime, hãy giảm peak live set dựa trên allocation evidence. Ở web delivery, hãy thiết kế cache theo freshness contract và content class. Ở modernization, hãy giảm số biến thay đổi đồng thời, tạo intermediate states deployable/observable/rollbackable và chỉ trả complexity cost khi requirement justify.

## Mẫu tư duy cần nhớ

- Observe before guessing: triệu chứng không phải root cause.
- Measure before optimizing, đặc biệt với memory và latency.
- Tách hệ thống thành layers/boundaries rồi chứng minh layer nào gây lỗi.
- Migration tốt có intermediate states có thể deploy, verify và rollback.
- Complexity phải được trả bằng requirement cụ thể, không phải xu hướng công nghệ.
