# Code Review Challenge 1 — Bộ nhớ tăng khi đồng bộ bảng giá từ hệ thống đối tác

**Chủ đề:** C#/.NET 8, GC, ArrayPool, ownership, background processing  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 5

## Bối cảnh

Một worker nhập bảng giá từ đối tác theo từng batch. Mỗi batch gồm một stream chứa JSON UTF-8, kích thước từ 10 KB đến 2 MB. Hệ thống có 4 worker, mỗi worker nhận nhiều batch đồng thời. Sau khi thêm ArrayPool để giảm allocation, bộ nhớ vẫn tăng và đôi lúc giá sản phẩm không khớp với nội dung đầu vào. Mục tiêu là lưu bản gốc chính xác vào kho lưu trữ trước khi xác nhận batch. Giả định IArchive.WriteAsync nhận ReadOnlyMemory<byte>, chỉ cam kết không sử dụng bộ nhớ sau khi Task hoàn tất; stream thuộc quyền sở hữu của caller. Chưa biết stream có hỗ trợ seek hay không. Giới hạn nghiệp vụ là 2 MiB mỗi batch.

## Đoạn code cần review

```csharp
public sealed class PriceImporter(IArchive archive,
    ILogger<PriceImporter> logger)
{
    private static readonly ArrayPool<byte> Pool =
        ArrayPool<byte>.Shared;
    private readonly List<Task> _pending = new();

    public async Task ImportAsync(
        string batchId, Stream input, CancellationToken ct)
    {
        var buffer = Pool.Rent((int)input.Length);
        try
        {
            var count = await input.ReadAsync(
                buffer.AsMemory(), ct);
            var write = archive.WriteAsync(
                batchId, buffer.AsMemory(), CancellationToken.None);
            _pending.Add(write);
            logger.LogInformation(
                "Imported {BatchId}: {Count}", batchId, count);
        }
        finally
        {
            Pool.Return(buffer);
        }
    }

    public Task FlushAsync()
    {
        return Task.WhenAll(_pending);
    }
}
```

## Kết quả code review tham khảo

### Critical — Buffer được trả về pool trước khi ghi hoàn tất

**Vấn đề:** WriteAsync chưa được await khi finally chạy.  
**Tại sao xảy ra:** ReadOnlyMemory không tạo bản sao và không chuyển ownership. Worker khác có thể thuê lại cùng mảng.  
**Ảnh hưởng production:** Nội dung lưu trữ có thể bị thay đổi, dẫn đến giá sai hoặc lẫn dữ liệu giữa batch.  
**Cách sửa:** Await toàn bộ thao tác ghi trước khi trả buffer, xác nhận hợp đồng lifetime với archive.

### High — Ghi capacity thay vì payload

**Vấn đề:** Truyền toàn bộ mảng và chỉ đọc stream một lần.  
**Tại sao xảy ra:** Rent có thể trả mảng lớn hơn yêu cầu; ReadAsync có thể trả ít byte hơn yêu cầu mà chưa EOF.  
**Ảnh hưởng production:** JSON thiếu hoặc chứa byte dư, có thể lộ dữ liệu cũ trong pool.  
**Cách sửa:** Đọc lặp tới EOF trong giới hạn, chỉ truyền vùng đã ghi, xóa buffer khi trả nếu chứa dữ liệu nhạy cảm.

### High — Không có giới hạn kích thước và giả định stream seekable

**Vấn đề:** Dùng Length rồi cast sang int.  
**Tại sao xảy ra:** Stream mạng có thể không hỗ trợ Length; kích thước không được kiểm tra trước khi cấp phát.  
**Ảnh hưởng production:** Batch hợp lệ có thể thất bại; input lớn có thể gây áp lực bộ nhớ.  
**Cách sửa:** Đọc có giới hạn, từ chối batch vượt quota và giới hạn số batch in-flight.

### High — Báo thành công trước khi ghi bền vững

**Vấn đề:** ImportAsync trả về trước khi archive hoàn tất, bỏ cancellation.  
**Tại sao xảy ra:** Task được giữ riêng thay vì await trong luồng xử lý.  
**Ảnh hưởng production:** Caller có thể xác nhận batch đã mất; shutdown khó kiểm soát.  
**Cách sửa:** Truyền token, await ghi và chỉ xác nhận sau thành công; nếu kết quả ghi không rõ do timeout, retry theo batchId với archive idempotent.

### Medium — Danh sách Task dùng chung không an toàn

**Vấn đề:** List không thread-safe và không được dọn.  
**Tại sao xảy ra:** Nhiều caller cùng Add hoặc enumerate trong FlushAsync.  
**Ảnh hưởng production:** Race, giữ Task và exception lâu dài, lỗi khi flush.  
**Cách sửa:** Bỏ danh sách, quản lý concurrency ở worker và await từng batch.

## Phiên bản đề xuất

```csharp
public sealed class PriceImporter(IArchive archive,
    ILogger<PriceImporter> logger)
{
    private const int MaxBytes = 2 * 1024 * 1024;
    private readonly SemaphoreSlim _slots = new(4, 4);

    public async Task ImportAsync(
        string batchId, Stream input, CancellationToken ct)
    {
        await _slots.WaitAsync(ct);
        byte[]? buffer = null;
        try
        {
            buffer = ArrayPool<byte>.Shared.Rent(MaxBytes + 1);
            int used = 0;
            while (used <= MaxBytes)
            {
                int n = await input.ReadAsync(
                    buffer.AsMemory(used, MaxBytes + 1 - used), ct);
                if (n == 0) break;
                used += n;
                if (used > MaxBytes)
                    throw new InvalidDataException("Batch too large");
            }

            await archive.WriteAsync(
                batchId, buffer.AsMemory(0, used), ct);
            logger.LogInformation(
                "Archived {BatchId}: {Bytes}", batchId, used);
        }
        finally
        {
            if (buffer is not null)
                ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
            _slots.Release();
        }
    }
}
```

## Giải thích thiết kế sau khi sửa

Giả định một importer sống suốt vòng đời worker; giới hạn semaphore áp dụng cho instance đó, không phải toàn cluster. Worker cần bounded queue hoặc broker prefetch phù hợp để không tích tụ caller đang chờ. Khi shutdown, dừng nhận batch mới và chờ các thao tác đang chạy trong thời hạn cho phép. Chỉ dispose semaphore sau khi toàn bộ caller đã kết thúc nếu quản lý lifetime thủ công. Archive phải xác định rõ durable write và chính sách idempotency theo batchId; nếu cùng ID nhưng khác checksum thì từ chối thay vì ghi đè im lặng. Việc validate JSON và giá nghiệp vụ thuộc bước xử lý sau lưu bản gốc, không được suy ra từ thành công của archive.

## Trade-offs

Thuê buffer tối đa cho cả batch nhỏ làm tăng working set; pool giữ mảng để tái sử dụng nên RSS cao không tự chứng minh memory leak. Xóa toàn bộ mảng tốn CPU. Nếu phép đo cho thấy chi phí đáng kể, cân nhắc archive hỗ trợ streaming với giới hạn byte và atomic commit, hoặc buffer tăng dần. Giới hạn concurrency giảm throughput đỉnh nhưng bảo vệ memory và dependency; điều chỉnh dựa trên latency và allocation thực tế.

## Cách kiểm thử

- Unit: stream không seekable trả từng đoạn nhỏ, kiểm tra byte lưu đúng tuyệt đối.
- Boundary: batch đúng 2 MiB thành công, vượt một byte bị từ chối.
- Concurrency: archive giả lập giữ memory tới khi được giải phóng; chạy nhiều batch với payload khác nhau và so checksum.
- Failure-path: archive ném exception hoặc cancellation; không báo thành công, slot được giải phóng.
- Load: đo throughput, allocation rate, GC heap, số batch in-flight khi dependency chậm.

## Quan sát trong production

Theo dõi histogram kích thước batch, thời gian chờ slot, archive latency p95/p99, số lỗi ghi, số batch retry và checksum mismatch. Dùng Application Insights dependency traces liên kết batchId với thao tác lưu; không log payload. So sánh GC heap, LOH size, allocation rate và working set bằng runtime counters để phân biệt pool retention với leak. Nếu checksum sai, tạm dừng xác nhận batch, cô lập dữ liệu bị ảnh hưởng, xác minh bản gốc trước khi replay.

3. Làm sao phân biệt ghi thành công nhưng response bị mất với ghi thất bại?

# Code Review Challenge 2 — Akamai cache trang khuyến mãi theo thị trường

## Đoạn code cần review

```typescript
app.get("/:market/offers", async (req, res, next) => {
  try {
    const market = req.params.market;
    const preview = req.query.preview === "true";
    const member = req.cookies.memberId;
    const key = "offers";
    let html = await cache.get(key);

    if (!html) {
      const page = await cms.getOffers(market, preview);
      const prices = await pricing.getOffers(market, member);
      html = render({
        page,
        prices,
        canonical: "https://shop.example/offers"
      });
      await cache.set(key, html, 3600);
    }

    res.set("Cache-Control",
      "public, max-age=3600, s-maxage=86400");
    res.set("Content-Type", "text/html; charset=utf-8");
    res.send(html);
  } catch (error) {
    next(error);
  }
});
```

Giả định cache.set nhận TTL theo giây; render escape dữ liệu HTML đúng cách. CMS client có quyền đọc draft, còn pricing client có thể trả ưu đãi riêng theo memberId. Authentication middleware có thể đã tồn tại nhưng đoạn route không sử dụng identity đã xác thực.

## Giải thích thiết kế sau khi sửa

Đây là minh họa với các helper authentication, authorization và pricing do ứng dụng triển khai, không phải API mặc định của Express hay Optimizely. Public route phải tạo HTML giống nhau bất kể cookie; không phát Set-Cookie hoặc nhúng dữ liệu session. CDN cấu hình bypass cả cache lookup và cache storage cho preview và member API, kể cả response lỗi; middleware xác thực cũng phải đặt no-store trên lỗi. Public HTML chỉ chứa giá công khai; browser lấy giá riêng qua API sau đăng nhập. Xác minh cache key bao gồm host và path đã chuẩn hóa, thêm locale/currency nếu chúng thực sự thay đổi HTML ngoài market.

Khi publish, invalidation worker xóa origin cache rồi purge edge URL tương ứng, có retry và theo dõi kết quả. Nếu một request cũ đang render có thể ghi lại dữ liệu stale sau invalidation, dùng content revision trong origin key hoặc cơ chế kiểm tra revision trước khi ghi; edge vẫn có thể stale tới TTL nếu purge thất bại. TTL 60 giây là giả định cần Product xác nhận, không phải bảo đảm freshness tuyệt đối: hai tầng TTL có thể cộng dồn. Không cache lỗi 5xx như trang hợp lệ. Nếu cache nội bộ lỗi, chỉ fallback có giới hạn concurrency để bảo vệ CMS.

## Trade-offs

Tách API private tạo thêm request và trạng thái loading; giá riêng không xuất hiện trong HTML ban đầu, nhưng giảm nguy cơ cache leakage. TTL ngắn tăng origin traffic; purge theo publish giảm độ trễ nhưng thêm dependency vận hành. Có thể bỏ origin cache nếu edge hit ratio đủ cao và CMS chịu được miss. Không dùng Vary: Cookie như giải pháp mặc định vì tăng cardinality và phụ thuộc cấu hình edge. Với incident hiện tại, ưu tiên bypass cache và purge trước khi tối ưu hit ratio, xác định phạm vi lộ dữ liệu và phối hợp quy trình xử lý bảo mật.

## Cách kiểm thử

- Security: người dùng A/B và anonymous truy cập cùng URL qua edge, xác nhận không có giá riêng trong HTML public.
- Security: preview không đăng nhập hoặc sai market bị từ chối, response không được cache.
- Integration: publish nội dung VN không làm thay đổi SG; kiểm tra invalidation khi request cũ đang render.
- Playwright E2E: chuyển market, đăng nhập/đăng xuất và kiểm tra giá riêng biến mất, canonical đúng.
- Failure-path/load: cache outage và purge thất bại; đo origin load, freshness và hành vi khi CMS timeout.

## Quan sát trong production

Theo dõi cache hit/miss theo market và route class, Age header tại edge, origin latency, CMS dependency errors, publish-to-visible lag và purge failures. Synthetic probes kiểm tra public HTML không chứa marker private và preview luôn yêu cầu quyền. Dùng correlation ID cho publish event và invalidation job; không log token, cookie hay giá riêng gắn với identity. Theo dõi canonical và status code bằng crawler test. Cảnh báo khi private route có cache hit hoặc freshness vượt SLA; xác minh lại bằng request qua CDN thực tế trước khi mở cache sau hotfix.

## Câu hỏi phỏng vấn mở rộng

1. Nếu giá public thay đổi mỗi giây, nên cache HTML hay tách giá thành endpoint riêng?
2. Làm thế nào xử lý invalidation khi publish đồng thời nhiều revision?
3. Nếu Product yêu cầu SSR giá cá nhân, bạn sẽ thay đổi cache policy và capacity planning ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Ownership của pooled memory phải kéo dài tới khi consumer hoàn tất; capacity không đồng nghĩa payload length. Bounded concurrency và durable acknowledgment là hai yêu cầu khác nhau. Cache public chỉ an toàn khi representation không phụ thuộc identity; authorization phải được thực thi trước khi truy cập nội dung riêng, và edge policy phải phù hợp với origin.

## Mẫu tư duy cần nhớ

- Xác định ownership và lifetime trước khi tối ưu allocation.
- Đo working set cùng GC heap trước khi kết luận memory leak.
- Xác định mọi chiều biến thể trước khi thiết kế cache key.
- Thiết kế invalidation cùng failure recovery và freshness SLA.
- Kiểm thử failure path và ranh giới authorization trước rollout.
