# Code Review Challenge 1 — Tính billable amount bằng `double` và materialize quá sớm làm lệch tiền, tốn memory dưới dữ liệu lớn

**Chủ đề:** SQL correctness và performance, EF Core query execution, numeric precision, memory/allocation, business correctness, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API tạo preview invoice từ dữ liệu timesheet. Mỗi timesheet entry có `ActualHours`, `BillableHours`, `ProjectId`, `EmployeeId`, `WorkDate`. Mỗi project có một `HourlyRate` do backend quản lý.

Business rule:

- invoice chỉ tính `BillableHours`,
- `BillableHours` không được âm và không được lớn hơn `ActualHours`,
- tiền phải được tính chính xác theo currency rule,
- việc làm tròn phải theo rule của invoice, không được phụ thuộc ngẫu nhiên vào cách chia nhỏ timesheet entry,
- cùng một tập dữ liệu phải cho cùng kết quả dù chạy lại nhiều lần.

Bảng `TimesheetEntries` đã có vài triệu record. Một invoice có thể bao phủ 1–3 tháng và hàng trăm nhân viên.

Production gần đây ghi nhận:

- tổng invoice đôi lúc lệch vài cent so với báo cáo kế toán,
- khi một ngày được tách thành nhiều entry nhỏ thì tổng tiền khác so với khi gộp thành một entry,
- endpoint preview dùng rất nhiều memory ở tenant lớn,
- p99 tăng mạnh khi khoảng ngày rộng,
- một số request trả số tiền rất lớn nếu dữ liệu cũ có `BillableHours` bất thường,
- log chỉ ghi tổng amount, không ghi số entry hay số record bị loại vì validation.

## Đoạn code cần review

```csharp
public sealed class InvoicePreviewService
{
    private readonly AppDbContext _db;

    public InvoicePreviewService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<InvoicePreviewDto> BuildAsync(
        Guid projectId,
        DateTime from,
        DateTime to,
        CancellationToken cancellationToken)
    {
        var project = await _db.Projects
            .SingleAsync(x => x.Id == projectId, cancellationToken);

        var rows = await _db.TimesheetEntries
            .Where(x =>
                x.ProjectId == projectId &&
                x.WorkDate >= from &&
                x.WorkDate <= to)
            .OrderBy(x => x.WorkDate)
            .ToListAsync(cancellationToken);

        var hourlyRate = (double)project.HourlyRate;

        var items = rows
            .Where(x => x.BillableHours > 0)
            .Select(x => new InvoiceLineDto
            {
                EmployeeId = x.EmployeeId,
                WorkDate = x.WorkDate,
                Hours = (double)x.BillableHours,
                Amount = Math.Round(
                    (double)x.BillableHours * hourlyRate,
                    2)
            })
            .ToList();

        var totalHours = items.Sum(x => x.Hours);
        var totalAmount = items.Sum(x => x.Amount);

        return new InvoicePreviewDto
        {
            ProjectId = projectId,
            From = from,
            To = to,
            TotalHours = totalHours,
            TotalAmount = totalAmount,
            Lines = items
        };
    }
}
```

## Kết quả code review tham khảo

### 1. Chuyển tiền từ `decimal` sang `double`

**Problem:** `HourlyRate` và `BillableHours` bị cast sang `double` trước khi tính tiền.  
**Why it happens:** `double` là binary floating-point; nhiều giá trị thập phân không biểu diễn chính xác tuyệt đối.  
**Production impact:** Có thể phát sinh sai số nhỏ tích lũy qua nhiều line, gây lệch đối soát invoice.  
**Severity:** High  
**Recommended fix:** Giữ kiểu `decimal` cho tiền và các phép tính billing cần độ chính xác thập phân.

### 2. Làm tròn từng entry trước khi cộng có thể làm tổng phụ thuộc cách chia nhỏ entry

**Problem:** Mỗi line được `Math.Round(..., 2)` rồi mới `Sum`.  
**Why it happens:** `round(a) + round(b)` không nhất thiết bằng `round(a + b)`.  
**Production impact:** Cùng tổng giờ nhưng chia thành nhiều entry nhỏ có thể tạo tổng tiền khác.  
**Severity:** High  
**Recommended fix:** Xác định rõ business rounding policy. Nếu rule là round ở invoice total, giữ precision cao cho line calculation rồi round tại boundary đó. Nếu rule yêu cầu round từng line thì phải coi đó là rule chính thức và test theo rule kế toán.

### 3. Không enforce invariant `0 <= BillableHours <= ActualHours`

**Problem:** Code chỉ lọc `BillableHours > 0`, không kiểm tra vượt `ActualHours`.  
**Why it happens:** Preview đang tin dữ liệu persisted luôn hợp lệ.  
**Production impact:** Dữ liệu legacy hoặc bug khác có thể làm invoice bị over-billing.  
**Severity:** High  
**Recommended fix:** Enforce invariant khi ghi dữ liệu và validate lại ở luồng billing; dữ liệu vi phạm nên bị reject hoặc surfaced rõ ràng để xử lý.

### 4. Materialize toàn bộ entity trước khi projection

**Problem:** `ToListAsync()` tải toàn bộ `TimesheetEntry` matching range rồi mới lọc/projection trong memory.  
**Why it happens:** Query bị kết thúc quá sớm.  
**Production impact:** Tốn memory, network I/O và change-tracker cost không cần thiết ở invoice lớn.  
**Severity:** High  
**Recommended fix:** Project ngay trong LINQ SQL query, dùng `AsNoTracking()` cho read-only path và chỉ select field cần thiết.

### 5. Read-only query vẫn tracking entity

**Problem:** `Projects` và `TimesheetEntries` được query ở chế độ tracking mặc định.  
**Why it happens:** Không chỉ định no-tracking cho read path.  
**Production impact:** Change tracker giữ nhiều entity, làm tăng allocation/memory và chi phí tracking.  
**Severity:** Medium  
**Recommended fix:** Dùng `AsNoTracking()` hoặc projection scalar/DTO trực tiếp.

### 6. Semantics của `to` chưa rõ

**Problem:** `WorkDate <= to` có thể sai nếu caller truyền `to` là ngày ở 00:00 hoặc timestamp theo timezone khác.  
**Why it happens:** API contract chưa phân biệt date-only với instant.  
**Production impact:** Bỏ sót entry cuối ngày hoặc lệch boundary giữa client/server.  
**Severity:** Medium  
**Recommended fix:** Nếu domain là ngày công, cân nhắc `DateOnly` hoặc normalize range thành `[fromInclusive, toExclusive)` theo timezone/business rule rõ ràng.

### 7. Không kiểm tra range request

**Problem:** Caller có thể gửi khoảng thời gian cực rộng hoặc `from > to`.  
**Why it happens:** Endpoint thiếu boundary validation.  
**Production impact:** Query rất lớn, memory/latency tăng, có thể ảnh hưởng các API khác.  
**Severity:** Medium  
**Recommended fix:** Validate range, giới hạn khoảng preview hợp lý hoặc chuyển export lớn sang background flow.

### 8. Trả toàn bộ line trong response có thể quá lớn

**Problem:** Mọi matching entry được map thành `Lines`.  
**Why it happens:** Preview vừa tính tổng vừa đóng vai trò raw-detail export.  
**Production impact:** Response lớn, serialization tốn memory/CPU, client chậm và tăng latency.  
**Severity:** Medium  
**Recommended fix:** Tách summary và paged details, hoặc group theo employee/day tùy requirement.

### 9. Thiếu observability phục vụ đối soát

**Problem:** Không có count, invalid-row count, precision/rounding mode hay query duration.  
**Why it happens:** Billing observability chưa được coi là phần của correctness.  
**Production impact:** Khó giải thích vì sao invoice lệch hoặc tenant nào gây load bất thường.  
**Severity:** Medium  
**Recommended fix:** Log structured theo project, date range, row count, invalid count, duration, rounding policy/version; metric preview latency và rows processed.

## Phiên bản code đề xuất

```csharp
public sealed record InvoiceLineDto(
    Guid EmployeeId,
    DateTime WorkDate,
    decimal Hours,
    decimal UnroundedAmount,
    decimal Amount);

public sealed class InvoicePreviewService
{
    private readonly AppDbContext _db;

    public InvoicePreviewService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<InvoicePreviewDto> BuildAsync(
        Guid projectId,
        DateTime fromInclusiveUtc,
        DateTime toExclusiveUtc,
        CancellationToken cancellationToken)
    {
        if (fromInclusiveUtc >= toExclusiveUtc)
            throw new ArgumentException("Invalid invoice period.");

        var hourlyRate = await _db.Projects
            .AsNoTracking()
            .Where(x => x.Id == projectId)
            .Select(x => x.HourlyRate)
            .SingleAsync(cancellationToken);

        var rawRows = await _db.TimesheetEntries
            .AsNoTracking()
            .Where(x =>
                x.ProjectId == projectId &&
                x.WorkDate >= fromInclusiveUtc &&
                x.WorkDate < toExclusiveUtc &&
                x.BillableHours > 0)
            .Select(x => new
            {
                x.EmployeeId,
                x.WorkDate,
                x.ActualHours,
                x.BillableHours
            })
            .ToListAsync(cancellationToken);

        var invalidRows = rawRows
            .Where(x => x.BillableHours < 0 ||
                        x.BillableHours > x.ActualHours)
            .ToList();

        if (invalidRows.Count > 0)
            throw new InvalidOperationException(
                $"Invoice contains {invalidRows.Count} invalid timesheet entries.");

        var lines = rawRows
            .Select(x =>
            {
                var unrounded = x.BillableHours * hourlyRate;
                return new InvoiceLineDto(
                    x.EmployeeId,
                    x.WorkDate,
                    x.BillableHours,
                    unrounded,
                    decimal.Round(
                        unrounded,
                        2,
                        MidpointRounding.AwayFromZero));
            })
            .ToList();

        var totalHours = lines.Sum(x => x.Hours);

        var totalAmount = decimal.Round(
            lines.Sum(x => x.UnroundedAmount),
            2,
            MidpointRounding.AwayFromZero);

        return new InvoicePreviewDto
        {
            ProjectId = projectId,
            From = fromInclusiveUtc,
            To = toExclusiveUtc,
            TotalHours = totalHours,
            TotalAmount = totalAmount,
            Lines = lines
        };
    }
}
```

> Giả định ví dụ trên chọn rule “cộng amount chưa round rồi mới round tổng”. Trong hệ thống thực tế, rounding mode và rounding boundary phải được xác nhận với business/kế toán; không nên tự chọn chỉ vì code trông hợp lý.

## Trade-offs

- Giữ `decimal` tăng độ đúng cho billing nhưng có thể chậm hơn `double` trong một số workload tính toán thuần CPU; với invoice correctness thường đáng ưu tiên hơn.
- Materialize các row cần thiết vẫn có thể lớn. Nếu invoice cực lớn, nên aggregate/group ở database hoặc chuyển sang background generation thay vì trả toàn bộ detail trực tiếp.
- Reject toàn bộ invoice khi gặp dữ liệu sai là an toàn nhưng có thể làm quy trình business bị block. Một lựa chọn khác là trả validation report và không cho finalize cho đến khi dữ liệu được sửa.
- Nếu business thực sự yêu cầu round từng line vì chứng từ pháp lý, implementation phải theo rule đó thay vì round ở total.

## Cách kiểm thử

1. **Precision test:** Dùng hourly rate và hours có nhiều chữ số thập phân; verify kết quả bằng expected `decimal`, không so gần đúng kiểu floating-point.
2. **Rounding test:** So sánh một entry 1.00 giờ với nhiều entry nhỏ có cùng tổng giờ; verify đúng theo rounding policy đã chọn.
3. **Validation test:** `BillableHours < 0`, `BillableHours > ActualHours`, zero hours và dữ liệu legacy bất thường.
4. **Boundary test:** `from/to` ở đầu/cuối ngày, timezone conversion và `[from, to)` không bỏ sót record boundary.
5. **Load test:** Range lớn với hàng trăm nghìn entry; theo dõi memory, query duration, response size và database reads.

## Quan sát trong production

- Log: project id, normalized range, row count, invalid count, total hours, total amount, rounding-policy version, duration.
- Metric: invoice-preview duration, rows processed, invalid-row rate, response size, DB query duration.
- Trace: span cho project-rate lookup, timesheet query và calculation phase.
- Alert khi invalid billing data tăng hoặc p95/p99 preview latency vượt ngưỡng.
- Với billing quan trọng, nên lưu audit về input/version/rule dùng để tạo invoice nhằm tái dựng kết quả khi đối soát.

# Code Review Challenge 2 — Sửa `DefaultRequestHeaders.Authorization` trên `HttpClient` dùng chung làm token của user này lọt sang request user khác

**Chủ đề:** HTTP client usage, concurrency và race conditions, authentication/security, resource lifetime, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API gọi Microsoft Graph thay mặt người dùng bằng delegated access token. Team đã chuyển sang dùng `IHttpClientFactory` để tránh tạo `HttpClient` mới cho mỗi request.

Để “tiện”, service nhận một named `HttpClient` rồi set `DefaultRequestHeaders.Authorization` trước khi gọi Graph.

Production ghi nhận:

- lỗi chỉ xuất hiện dưới concurrent traffic,
- một số request Graph trả dữ liệu không thuộc user đang gọi API,
- audit log cho thấy `sub` của request A nhưng Graph response đôi lúc tương ứng account B,
- retry lại ngay sau đó thường thành công,
- security team nghi ngờ token bị dùng chéo giữa request,
- khi Graph chậm, một số request tiếp tục chạy dù client đã disconnect,
- log đang ghi nguyên access token để debug lỗi 401.

Service được đăng ký `Singleton` vì team nghĩ `HttpClient` nên được tái sử dụng.

## Đoạn code cần review

```csharp
public sealed class GraphCalendarService
{
    private readonly HttpClient _client;
    private readonly ILogger<GraphCalendarService> _logger;

    public GraphCalendarService(
        IHttpClientFactory factory,
        ILogger<GraphCalendarService> logger)
    {
        _client = factory.CreateClient("graph");
        _logger = logger;
    }

    public async Task<string> GetCalendarAsync(
        string accessToken,
        string userId,
        CancellationToken cancellationToken)
    {
        _client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        _logger.LogInformation(
            "Calling Graph for {UserId} with token {Token}",
            userId,
            accessToken);

        var response = await _client.GetAsync(
            $"users/{userId}/calendar/events");

        if (response.StatusCode == HttpStatusCode.Unauthorized)
        {
            await Task.Delay(1000);
            response = await _client.GetAsync(
                $"users/{userId}/calendar/events");
        }

        var body = await response.Content.ReadAsStringAsync();

        if (!response.IsSuccessStatusCode)
            throw new InvalidOperationException(body);

        return body;
    }
}
```

2. Xác định rủi ro concurrency, token leakage, sensitive-data exposure, cancellation và response disposal.
3. Giải thích production impact dưới nhiều request đồng thời.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation dùng `HttpClient` an toàn hơn cho per-request delegated token.
6. Giải thích cách test race condition, cancellation, 401/429/5xx và token isolation.
7. Đề xuất logs, traces hoặc metrics hữu ích mà không làm lộ token.

## Câu hỏi gợi mở

2. Điều gì xảy ra nếu request A set token A, request B set token B trước khi A thực sự gửi HTTP request?

## Kết quả code review tham khảo

### 1. Gắn delegated token vào `DefaultRequestHeaders` của client dùng chung

**Problem:** Authorization header được mutate trên state dùng lại giữa nhiều request.  
**Why it happens:** `DefaultRequestHeaders` thuộc `HttpClient`, không phải per-call request object. Khi service/client được dùng đồng thời, token có thể bị thay đổi giữa các call.  
**Production impact:** Request của user A có thể được gửi bằng token B — đây là security boundary violation nghiêm trọng.  
**Severity:** Critical  
**Recommended fix:** Set Authorization trên một `HttpRequestMessage` riêng cho từng outbound request hoặc dùng delegating handler có scope phù hợp và không lưu token mutable shared-state.

### 2. Log raw access token

**Problem:** Access token được ghi nguyên văn vào log.  
**Why it happens:** Debugging authentication đang làm lộ credential có thể dùng được.  
**Production impact:** Ai có quyền đọc log có thể chiếm quyền truy cập trong thời gian token còn hiệu lực; token có thể bị copy sang SIEM, backup hoặc support tooling.  
**Severity:** Critical  
**Recommended fix:** Không log token. Chỉ log metadata an toàn như token source, tenant/user subject đã xác minh, expiration bucket hoặc hash/fingerprint một chiều nếu thật sự cần correlation và được security review.

### 3. Không truyền `CancellationToken` vào HTTP call

**Problem:** `GetAsync` không nhận `cancellationToken`.  
**Why it happens:** Token chỉ tồn tại ở method signature nhưng không propagate.  
**Production impact:** Client đã disconnect nhưng outbound call vẫn chiếm socket/connection/resource cho đến khi hoàn thành hoặc timeout.  
**Severity:** High  
**Recommended fix:** Truyền cancellation vào `SendAsync`/`GetAsync` và các operation đọc content phù hợp.

### 4. Retry `401` bằng cùng token và không có refresh/reauth decision

**Problem:** Code chờ 1 giây rồi gửi lại cùng request khi 401.  
**Why it happens:** Mọi 401 bị coi là transient.  
**Production impact:** Tăng latency và load nhưng hiếm khi sửa được token hết hạn/sai audience/scope.  
**Severity:** High  
**Recommended fix:** Phân loại 401; nếu flow hỗ trợ refresh token/On-Behalf-Of thì refresh ở tầng auth có kiểm soát. Nếu không, trả auth failure để client thực hiện re-auth theo contract.

### 5. Retry không dispose response đầu tiên

**Problem:** `response` của call 401 bị ghi đè bởi response mới mà chưa dispose.  
**Why it happens:** Response object được reuse biến mà không cleanup.  
**Production impact:** Có thể trì hoãn giải phóng resource/connection liên quan response và gây pressure khi lỗi nhiều.  
**Severity:** High  
**Recommended fix:** Dispose từng `HttpResponseMessage` đúng lifecycle hoặc dùng `using`/`await using` pattern phù hợp.

### 6. `Task.Delay(1000)` không nhận cancellation

**Problem:** Delay vẫn chạy kể cả request đã bị cancel.  
**Why it happens:** Không truyền token.  
**Production impact:** Request cancellation phản hồi chậm và giữ execution sống không cần thiết.  
**Severity:** Medium  
**Recommended fix:** `Task.Delay(delay, cancellationToken)` nếu retry thực sự hợp lệ.

### 7. Đọc toàn bộ error body rồi ném raw body trong exception

**Problem:** Error body từ Graph được đưa nguyên vào exception.  
**Why it happens:** Code dùng response payload làm diagnostic message trực tiếp.  
**Production impact:** Có thể làm lộ dữ liệu nhạy cảm vào logs hoặc error pipeline; payload lớn cũng gây allocation không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Parse error code/correlation metadata cần thiết, sanitize message và giới hạn body được lưu/log.

### 8. Không phân loại 429/5xx/network failure

**Problem:** Chỉ có retry logic cho 401.  
**Why it happens:** Retry policy không dựa trên failure semantics.  
**Production impact:** Transient failure phù hợp để retry có thể fail ngay, còn auth failure lại bị retry không hợp lý.  
**Severity:** Medium  
**Recommended fix:** Có resilience policy giới hạn cho network errors, 429 và selected 5xx; tôn trọng `Retry-After` khi phù hợp, giới hạn attempt và dùng jitter/backoff theo policy của hệ thống.

### 9. `userId` được dùng trực tiếp trong URL nhưng authorization relationship chưa thể hiện

**Problem:** Method nhận cả delegated token và arbitrary `userId`; snippet không cho thấy token có quyền truy cập user đó theo business rule.  
**Why it happens:** Resource identity và caller identity được truyền rời nhau.  
**Production impact:** Nếu upstream authorization lỏng, caller có thể yêu cầu calendar của resource không được phép.  
**Severity:** Medium  
**Recommended fix:** Nếu use case là “calendar của chính tôi”, derive user identity từ validated claims/token flow thay vì nhận arbitrary userId. Nếu delegated admin/shared scenario hợp lệ, enforce explicit resource authorization.

### 10. Observability không đủ nhưng lại log bí mật

**Problem:** Log token đầy đủ nhưng thiếu Graph request id, duration, status category, retry count, cancellation outcome.  
**Why it happens:** Telemetry tập trung vào dữ liệu nhạy cảm thay vì diagnostic metadata.  
**Production impact:** Security risk cao nhưng khả năng điều tra vẫn thấp.  
**Severity:** Medium  
**Recommended fix:** Log request outcome, safe subject/tenant id, outbound duration, retry reason/count, Graph correlation headers an toàn và trace id.

## Phiên bản code đề xuất

```csharp
public sealed class GraphCalendarService
{
    private readonly HttpClient _client;
    private readonly ILogger<GraphCalendarService> _logger;

    public GraphCalendarService(
        IHttpClientFactory factory,
        ILogger<GraphCalendarService> logger)
    {
        _client = factory.CreateClient("graph");
        _logger = logger;
    }

    public async Task<string> GetCalendarAsync(
        string accessToken,
        string userId,
        CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"users/{Uri.EscapeDataString(userId)}/calendar/events");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        var started = Stopwatch.GetTimestamp();

        using var response = await _client.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        var elapsed = Stopwatch.GetElapsedTime(started);

        _logger.LogInformation(
            "Graph calendar call completed for {UserId} with status {StatusCode} in {ElapsedMs} ms",
            userId,
            (int)response.StatusCode,
            elapsed.TotalMilliseconds);

        if (response.StatusCode == HttpStatusCode.Unauthorized)
        {
            throw new UnauthorizedAccessException(
                "Graph rejected the delegated access token.");
        }

        if (!response.IsSuccessStatusCode)
        {
            var errorBody = await response.Content
                .ReadAsStringAsync(cancellationToken);

            var safeMessage = errorBody.Length <= 512
                ? errorBody
                : errorBody[..512];

            throw new HttpRequestException(
                $"Graph request failed with status {(int)response.StatusCode}: {safeMessage}",
                null,
                response.StatusCode);
        }

        return await response.Content
            .ReadAsStringAsync(cancellationToken);
    }
}
```

> Ví dụ trên cố ý không tự retry. Retry nên nằm trong resilience policy riêng, chỉ áp dụng cho lỗi phù hợp. Với 401, việc refresh/reacquire token phải phụ thuộc authentication flow thực tế; không nên mặc định retry bằng token cũ.

## Trade-offs

- Tạo `HttpRequestMessage` cho từng call có allocation nhỏ nhưng đổi lại loại bỏ mutable per-user state trên client dùng chung.
- Service singleton có thể vẫn an toàn nếu toàn bộ dependency của nó thread-safe và không giữ state per-request. Tuy nhiên token/user context không nên stored trong field singleton.
- Central delegating handler có thể giúp thống nhất auth header, nhưng handler phải lấy token theo request context an toàn và lifecycle phải được hiểu rõ; không nên biến handler thành shared mutable token cache.
- Retry policy làm tăng khả năng phục hồi nhưng cũng có thể nhân tải lên Graph. Chỉ retry failure có khả năng transient và luôn có giới hạn.

## Cách kiểm thử

1. **Concurrency isolation test:** Chạy hàng trăm request song song với token A/B và verify outbound mock server luôn nhận đúng token tương ứng user.
2. **Cancellation test:** Cancel request trong lúc outbound call đang chậm; verify `SendAsync` kết thúc bằng cancellation và không retry.
3. **Authentication test:** 401 không được retry mù bằng cùng token; verify flow trả lỗi auth hoặc reacquire token theo policy đã thiết kế.
4. **Resilience test:** 429/5xx/network failure được xử lý theo retry policy giới hạn, có backoff và cancellation.
5. **Security/log test:** Assert logs không chứa access token, Authorization header hay raw sensitive error payload.

## Quan sát trong production

- Log structured: safe user/tenant identifier, outbound status, duration, retry count/reason, cancellation status, correlation/trace id.
- Metric: Graph request latency, status-code category, 401 rate, 429 rate, retry rate, cancellation count.
- Distributed trace: span outbound HTTP với dependency name và sanitized route; không attach token.
- Alert khi 401/403 tăng sau deployment, 429 tăng đột biến hoặc p99 outbound latency vượt baseline.
- Security audit: định kỳ kiểm tra secret/token redaction ở logs, traces và exception telemetry.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn delegating handler để gắn token thay vì set header trực tiếp trên `HttpRequestMessage`?
2. Nếu Graph trả 429 cùng `Retry-After`, bạn thiết kế retry và concurrency limit thế nào để tránh retry storm?
3. Nếu nhiều downstream API dùng các token/audience khác nhau, bạn tổ chức typed/named clients và token acquisition layer ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với billing, correctness không chỉ là phép nhân đúng cú pháp: cần giữ precision phù hợp, định nghĩa rõ rounding boundary và enforce invariant dữ liệu.
- Đừng materialize entity graph hoặc danh sách lớn quá sớm nếu database có thể projection/filter trước.
- `HttpClient` có thể được tái sử dụng, nhưng credential của từng user là request-specific state và không nên nằm trong mutable shared header.
- Cancellation cần được propagate xuyên suốt outbound HTTP, delay và content read.
- Observability tốt phải giúp điều tra mà không làm lộ token, dữ liệu nhạy cảm hoặc credential.

## Mẫu tư duy cần nhớ

- Xác nhận business rule trước khi chọn kiểu dữ liệu và rounding policy.
- Giữ shared infrastructure stateless đối với dữ liệu của từng request.
- Push filter/projection xuống database trước khi materialize.
- Retry phải dựa trên failure semantics, không retry mù mọi status.
- Treat security-safe observability as part of the design.
