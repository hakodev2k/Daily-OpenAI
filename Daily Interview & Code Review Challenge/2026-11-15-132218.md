## Kết quả code review tham khảo

### [Critical] — Connection string bị ghi vào deployment log

**Vấn đề:** Script in trực tiếp secret.  
**Tại sao xảy ra:** Logging interpolates tham số nhạy cảm.  
**Ảnh hưởng production:** Người có quyền xem build/deploy logs có thể đọc credential; log retention làm tăng thời gian phơi nhiễm.  
**Cách sửa:** Không log secret; dùng secret variable masking của pipeline và identity/secret store phù hợp; rotate credential đã lộ, audit quyền truy cập.

### [High] — Không drain traffic trước khi stop App Pool

**Vấn đề:** Node vẫn nhận request khi worker process dừng.  
**Tại sao xảy ra:** Script không điều phối load balancer.  
**Ảnh hưởng production:** Request in-flight có thể thất bại; tăng 502/503.  
**Cách sửa:** Đánh dấu node unavailable trong LB, đợi connection/request drain trong deadline, sau đó deploy từng node; kiểm tra capacity node còn lại.

### [High] — In-place delete và extraction không atomic

**Vấn đề:** Production directory có thể ở trạng thái nửa cũ nửa mới.  
**Tại sao xảy ra:** Xóa trước khi xác minh archive, disk space và checksum; copy không transactional.  
**Ảnh hưởng production:** Startup lỗi, mất artifact và rollback khó.  
**Cách sửa:** Verify immutable package; extract sang release directory riêng; chuyển IIS physical path hoặc deployment pointer có kiểm soát; giữ bản trước.

### [High] — Lỗi không làm dừng pipeline đáng tin cậy

**Vấn đề:** `$ErrorActionPreference = "Continue"` và thiếu kiểm tra HTTP status/exit semantics.  
**Tại sao xảy ra:** Một số cmdlet phát non-terminating error; `Write-Host` vẫn chạy.  
**Ảnh hưởng production:** Pipeline báo thành công khi release hỏng.  
**Cách sửa:** `Stop`, `try/catch`, kiểm tra trạng thái từng bước, fail deployment khi readiness không đạt.

### [High] — Backup được tạo sau khi ghi đè

**Vấn đề:** Bản backup chứa release vừa deploy, không phải last-known-good.  
**Tại sao xảy ra:** Sai thứ tự snapshot.  
**Ảnh hưởng production:** Không thể rollback bằng artifact cũ khi gặp regression.  
**Cách sửa:** Lưu versioned release directory trước khi cutover; chỉ dọn sau retention và rollback validation.

### [High] — Health check không xác minh đúng node/site và dependency

**Vấn đề:** `http://localhost/health` có thể đi tới default site hoặc phản ánh liveness đơn thuần.  
**Tại sao xảy ra:** Không xác định host binding, port, readiness contract.  
**Ảnh hưởng production:** Đưa node lỗi vào phục vụ.  
**Cách sửa:** Gọi endpoint readiness đúng binding/host, xác minh response code và release version, sau đó smoke test từ đường đi qua LB.

### [Medium] — Ghi secret vào appsettings trên disk

**Vấn đề:** Secret tồn tại trong file artifact và có thể bị backup hoặc đọc bởi identity khác.  
**Tại sao xảy ra:** Mutation JSON tại deploy-time.  
**Ảnh hưởng production:** Credential leakage, drift giữa hai node.  
**Cách sửa:** Dùng environment-specific protected configuration/secret store, ACL tối thiểu, không đóng gói secret trong artifact.

### [Medium] — JSON serialization có thể thay đổi cấu hình

**Vấn đề:** `ConvertTo-Json` mặc định giới hạn depth; encoding/format có thể đổi.  
**Tại sao xảy ra:** Round-trip file cấu hình không có validation.  
**Ảnh hưởng production:** Mất nested settings và startup behavior bất ngờ.  
**Cách sửa:** Tránh sửa JSON trực tiếp; nếu bắt buộc, đặt depth và schema validation, so sánh output trước cutover.

### [Medium] — Không có database compatibility gate và coordinated rollback

**Vấn đề:** Release mới có thể chạy migration phá tương thích phiên bản cũ.  
**Tại sao xảy ra:** Không có expand/contract plan.  
**Ảnh hưởng production:** Rollback binary vẫn không phục hồi được service.  
**Cách sửa:** Migration additive trước, dual-compatible reads/writes, backfill, contract ở release sau; có checkpoint và rollback plan.

## Phiên bản đề xuất

Ví dụ orchestration rút gọn; `Disable-LbNode`, `Enable-LbNode`, `Wait-ForDrain` và `Assert-Readiness` là các hàm **nội bộ phải được triển khai theo load balancer thực tế**, không phải PowerShell/IIS cmdlet có sẵn.

```powershell
param(
    [Parameter(Mandatory)][string]$Package,
    [Parameter(Mandatory)][string]$Version,
    [string]$Site = "OrdersApi",
    [string]$NodeId = $env:COMPUTERNAME
)
$ErrorActionPreference = "Stop"
Import-Module WebAdministration

$root = "C:\deploy\orders"
$release = Join-Path $root "releases\$Version"
$previous = (Get-Item "IIS:\Sites\$Site").physicalPath
$switched = $false

try {
    if (Test-Path $release) { throw "Release already exists" }
    New-Item -ItemType Directory -Path $release -Force | Out-Null
    Expand-Archive -LiteralPath $Package -DestinationPath $release
    if (!(Test-Path (Join-Path $release "OrdersApi.dll"))) {
        throw "Invalid package"
    }
    # Artifact checksum/signature verified by CI/CD before this step.
    Disable-LbNode -Node $NodeId
    Wait-ForDrain -Node $NodeId -TimeoutSeconds 90
    Stop-WebAppPool -Name "OrdersApiPool"
    Set-ItemProperty "IIS:\Sites\$Site" -Name physicalPath -Value $release
    $switched = $true
    Start-WebAppPool -Name "OrdersApiPool"
    Assert-Readiness -Node $NodeId -Version $Version -TimeoutSeconds 60
    Enable-LbNode -Node $NodeId
}
catch {
    if ($switched) {
        Stop-WebAppPool -Name "OrdersApiPool"
        Set-ItemProperty "IIS:\Sites\$Site" -Name physicalPath -Value $previous
        Start-WebAppPool -Name "OrdersApiPool"
    }
    # Re-enable only after readiness of the restored version is proven.
    throw
}
```

**Điều kiện bổ sung:** Pipeline thực tế phải bảo đảm locking trên node, xử lý site/app virtual directory đúng cấu hình, package integrity, LB API errors, timeout/cancellation, cleanup và rollback database-compatible. Nếu process còn giữ file lock hoặc site path không thể chuyển an toàn, dùng cơ chế slot/site riêng với routing switch thay vì đổi physical path.

## Giải thích thiết kế sau khi sửa

Build một artifact bất biến, cấu hình qua secret store và deployment variables được bảo vệ. Deploy tuần tự từng node: preflight → drain → cutover → readiness → rejoin. Giữ release trước để rollback; không nhầm rollback application với rollback schema. Ghi deployment marker (version, commit SHA, node) vào telemetry.

## Trade-offs

Rolling deployment tăng thời gian release và yêu cầu dư capacity. Blue/green cần thêm tài nguyên nhưng giảm thời gian cutover. Database expand/contract đòi hỏi nhiều release; đổi lại rollback an toàn hơn. Không cần chuyển sang Kubernetes chỉ để giải quyết lỗi quy trình triển khai.

## Cách kiểm thử

1. **Deployment validation:** Artifact thiếu DLL hoặc checksum sai phải fail trước khi drain.
2. **Failure-path:** Giả lập extraction/startup/readiness lỗi, xác minh node không được rejoin và rollback về bản tốt.
3. **Load test:** Gửi long-running requests trong khi rolling deploy; đo error rate và in-flight completion.
4. **Security test:** Scan logs/artifacts/backups để đảm bảo secret không xuất hiện; xác minh ACL.
5. **Compatibility test:** Chạy bản cũ và mới cùng schema đã expand, kiểm tra rollback sau migration.

## Quan sát trong production

Theo dõi 502/503 theo node và release, p95/p99, active requests, IIS process restart, readiness duration, LB health, Application Insights exception/dependency traces, deployment correlation ID, DB migration version. Alert nếu một node không rejoin đúng deadline hoặc error budget bị vượt sau cutover.

## Câu hỏi phỏng vấn mở rộng

1. Nếu hai node không đủ capacity để drain một node, bạn chọn release strategy nào?
2. Nếu schema migration đã xóa column mà phiên bản cũ cần, rollback thực sự có khả thi không?
3. Bạn thiết kế automated canary gate dựa trên metric nào để tránh false positive?

# Code Review Challenge 2 — Elasticsearch search index âm thầm lệch với PostgreSQL

## Bối cảnh

Một e-commerce API lưu catalog trong PostgreSQL và dùng Elasticsearch để tìm kiếm. Mỗi lần sửa product, API cập nhật database rồi index ngay. Sau peak traffic, có sản phẩm đã cập nhật giá nhưng search hiển thị giá cũ; đôi lúc product đã xóa vẫn xuất hiện. Có 3 API instances, một số request bị client retry. Search được phép eventual consistency trong tối đa vài phút; checkout luôn phải đọc giá từ nguồn authoritative. `ISearchIndex` là abstraction nội bộ.

## Đoạn code cần review

```csharp
public sealed class CatalogService(
    CatalogDbContext db,
    ISearchIndex search,
    IMemoryCache cache,
    ILogger<CatalogService> logger)
{
    public async Task<ProductDto> UpdateAsync(
        Guid productId, UpdateProductRequest request,
        CancellationToken ct)
    {
        var product = await db.Products.FindAsync(
            new object[] { productId }, ct);
        if (product is null)
            throw new KeyNotFoundException();

        product.Name = request.Name;
        product.Price = request.Price;
        product.UpdatedAt = DateTime.UtcNow;
        await db.SaveChangesAsync(ct);

        var dto = new ProductDto(product.Id, product.Name, product.Price);
        cache.Set($"product:{productId}", dto, TimeSpan.FromHours(1));

        try
        {
            await search.UpsertAsync(product.Id.ToString(), dto,
                CancellationToken.None);
        }
        catch (Exception ex)
        {
            logger.LogWarning(ex, "Index failed for {Id}", productId);
        }
        return dto;
    }

    public async Task DeleteAsync(Guid productId, CancellationToken ct)
    {
        var product = await db.Products.FindAsync(
            new object[] { productId }, ct);
        if (product is null) return;
        db.Products.Remove(product);
        await db.SaveChangesAsync(ct);
        await search.DeleteAsync(productId.ToString(), ct);
    }

    public Task<ProductDto?> GetCachedAsync(Guid id) =>
        Task.FromResult(cache.Get<ProductDto>($"product:{id}"));
}
```

## Kết quả code review tham khảo

### [High] — Dual-write không có atomicity

**Vấn đề:** DB commit thành công nhưng search update có thể thất bại.  
**Tại sao xảy ra:** Hai hệ thống không cùng transaction; catch chỉ log.  
**Ảnh hưởng production:** Search stale vô thời hạn nếu không có replay.  
**Cách sửa:** Ghi outbox event trong cùng PostgreSQL transaction với thay đổi product; worker retry và dead-letter/alert.

### [High] — Out-of-order update ghi đè dữ liệu mới

**Vấn đề:** Hai request/worker có thể index khác thứ tự commit.  
**Tại sao xảy ra:** Không có monotonic version kiểm soát write.  
**Ảnh hưởng production:** Search hiện giá cũ dù cả hai lần index đều thành công.  
**Cách sửa:** Version tăng atomically tại DB, propagate vào event; consumer/index dùng version guard phù hợp adapter Elasticsearch, xử lý duplicate và stale event.

### [High] — Xóa không invalidate cache và thiếu durable delete

**Vấn đề:** Product bị xóa vẫn nằm trong cache; search.Delete lỗi sau commit.  
**Tại sao xảy ra:** Delete chỉ thao tác DB và gọi index trực tiếp.  
**Ảnh hưởng production:** Ghost product và hành vi không nhất quán.  
**Cách sửa:** Tombstone/delete event qua outbox, invalidate cache; có reconciliation cho missing events.

### [High] — Không có optimistic concurrency cho update

**Vấn đề:** Hai request sửa product có thể last-write-wins ngoài ý muốn.  
**Tại sao xảy ra:** Không kiểm tra row version/ETag hoặc business conflict.  
**Ảnh hưởng production:** Lost update; outbox đúng cũng chỉ phản ánh kết quả DB đã sai.  
**Cách sửa:** Concurrency token và trả 409 khi conflict nếu business yêu cầu; phân biệt chủ ý last-write-wins.

### [Medium] — CancellationToken.None làm request kéo dài

**Vấn đề:** Index call không còn chịu cancellation của request.  
**Tại sao xảy ra:** Bỏ token và thiếu bounded timeout.  
**Ảnh hưởng production:** Tăng latency, giữ resource sau client disconnect.  
**Cách sửa:** Tách index khỏi request bằng worker; worker có timeout, shutdown token và retry policy.

### [Medium] — Cache local không nhất quán giữa instances

**Vấn đề:** IMemoryCache trên ba node giữ các bản khác nhau.  
**Tại sao xảy ra:** Chỉ node xử lý update ghi cache; không invalidate node khác.  
**Ảnh hưởng production:** GET trả dữ liệu stale đến một giờ.  
**Cách sửa:** Với yêu cầu nhất quán, đọc DB hoặc dùng invalidation/versioned cache phân tán; tránh cache nếu chưa đo lợi ích.

### [Medium] — Không có reconciliation và lag SLO

**Vấn đề:** Không biết document nào lệch DB.  
**Tại sao xảy ra:** Chỉ log một warning cho lần upsert lỗi.  
**Ảnh hưởng production:** Silent data divergence kéo dài.  
**Cách sửa:** Theo dõi outbox age, failed events, index lag, periodic compare/reindex theo version.

### [Medium] — Validation thiếu invariant giá và tenant scope

**Vấn đề:** Code không thể hiện validation giá và tenant ownership.  
**Tại sao xảy ra:** Lookup bằng productId đơn thuần, request fields được gán trực tiếp.  
**Ảnh hưởng production:** Giá âm hoặc cross-tenant modification nếu authorization nằm ngoài service cũng thiếu.  
**Cách sửa:** Validate domain rules; resolve tenant từ trusted principal và enforce trong DB query/authorization boundary. Cần xác minh hệ thống có multi-tenancy trước khi kết luận đây là exploit thực tế.

### [Low] — API cache miss không có fallback

**Vấn đề:** GetCachedAsync trả null ngay khi cache miss.  
**Tại sao xảy ra:** Cache bị coi như source of truth.  
**Ảnh hưởng production:** False not-found nếu caller không fallback.  
**Cách sửa:** Cache-aside với authoritative DB lookup; đo hit ratio và latency trước khi chọn cache.

## Phiên bản đề xuất

Ví dụ C# dùng EF Core; các model `CatalogOutbox`, `Product.Version` và `TenantId` là schema **đề xuất**, cần migration/unique constraints và wiring tương ứng. Worker index không được giả định có sẵn. Mỗi DB transaction phải ghi product cùng outbox event; `SaveChangesAsync` một lần đảm bảo atomicity trong provider relational thông thường khi không có ambient transaction phức tạp.

```csharp
public sealed class CatalogService(CatalogDbContext db)
{
    public async Task<ProductDto> UpdateAsync(
        Guid tenantId, Guid id, UpdateProductRequest request,
        long expectedVersion, CancellationToken ct)
    {
        if (request.Price < 0 || string.IsNullOrWhiteSpace(request.Name))
            throw new ArgumentException("Invalid product");

        var p = await db.Products.SingleOrDefaultAsync(
            x => x.Id == id && x.TenantId == tenantId, ct)
            ?? throw new KeyNotFoundException();

        if (p.Version != expectedVersion)
            throw new DbUpdateConcurrencyException("Version conflict");

        p.Name = request.Name;
        p.Price = request.Price;
        p.Version++;
        p.UpdatedAt = DateTime.UtcNow;

        db.CatalogOutbox.Add(new CatalogOutbox
        {
            EventId = Guid.NewGuid(),
            TenantId = tenantId,
            ProductId = p.Id,
            Version = p.Version,
            Operation = "Upsert",
            Payload = JsonSerializer.Serialize(new
            {
                p.Id, p.TenantId, p.Name, p.Price, p.Version
            }),
            CreatedAt = DateTime.UtcNow
        });

        await db.SaveChangesAsync(ct);
        return new ProductDto(p.Id, p.Name, p.Price);
    }
}
```

**Điều kiện correctness quan trọng:** `Version` phải được bảo vệ bởi database concurrency token hoặc conditional SQL update; phép kiểm tra trong memory ở trên **chưa đủ** để ngăn hai transaction đồng thời. Ví dụ PostgreSQL có thể cấu hình EF concurrency token cho `Version`, kiểm tra affected rows, hoặc dùng atomic `UPDATE ... WHERE Version = expectedVersion`. Worker lấy outbox bằng lease/claim an toàn giữa nhiều instances, retry với backoff, bảo vệ thứ tự theo product, và chỉ mark processed khi index xác nhận. Khi dùng Elasticsearch external versioning, phải kiểm tra chính xác semantics của version type và delete tombstone retention; không coi versioning là thay thế cho reconciliation. Với delete, phát tombstone có version và không tái tạo document từ event cũ.

## Giải thích thiết kế sau khi sửa

PostgreSQL là nguồn authoritative cho giá và trạng thái product. Search là read model eventual-consistent; API không block chờ index. Outbox giúp không mất intent khi process crash sau DB commit. Consumer idempotent và version-aware giải quyết duplicate/out-of-order. Cache là optimization, không phải nguồn sự thật. Checkout revalidate price và availability tại DB trong transaction phù hợp.

## Trade-offs

Outbox thêm table, worker, retention và monitoring; đổi lại tránh silent loss. Index lag là trade-off chấp nhận được nếu SLO rõ ràng. Versioning cần kiểm soát concurrency thực sự ở DB và adapter search. Nếu catalog nhỏ và không cần full-text, có thể dùng PostgreSQL search trước để giảm complexity.

## Cách kiểm thử

1. **Integration test:** Inject Elasticsearch outage sau DB commit; outbox vẫn lưu và replay thành công.
2. **Concurrency test:** Hai update cùng expectedVersion; đúng một update thành công khi concurrency token được cấu hình.
3. **Ordering test:** Replay event version 12 rồi 11, document vẫn ở version 12; duplicate event không tạo side effect.
4. **Delete failure test:** Delete event bị retry và stale upsert không hồi sinh product; cache invalidated.
5. **Load/reconciliation test:** Chạy nhiều worker và hàng chục nghìn event, đo backlog age, throughput, lệch version và recovery time.

## Quan sát trong production

Dùng structured logs với event ID, product ID, tenant ID (không log thông tin nhạy cảm), version, attempt, correlation ID. Dashboard gồm outbox oldest age, queue depth, retry/dead-letter count, Elasticsearch error/429, indexing p95, version mismatch, stale search rate, DB transaction failures. Alert khi lag vượt SLO hoặc event không tiến triển; chạy reconciliation định kỳ và lưu audit trail.

## Câu hỏi phỏng vấn mở rộng

1. Nếu search cần hiển thị giá chính xác tuyệt đối, bạn đổi kiến trúc đọc như thế nào?
2. Làm sao reindex toàn bộ catalog mà không dừng tìm kiếm và không bỏ mất update trong lúc rebuild?
3. Nếu outbox worker xử lý nhiều tenant, bạn bảo đảm fairness và tránh hot tenant chiếm hết capacity ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Release safety trên IIS không chỉ là copy file: phải điều phối traffic, artifact, configuration, readiness và database compatibility. Search indexing là một distributed consistency problem: DB commit và Elasticsearch write không atomic; cần durable intent, replay, ordering, reconciliation và authoritative checkout.

## Mẫu tư duy cần nhớ

1. Stabilize traffic và giữ last-known-good trước khi cutover.
2. Secret không được xuất hiện trong log, artifact hoặc backup không được bảo vệ.
3. Thiết kế retry cùng idempotency, ordering và failure visibility.
4. Đo consistency lag, lỗi và tác động khách hàng trước khi thêm infrastructure.
5. Test rollback, duplicate, out-of-order và dependency outage thay vì chỉ happy path.
