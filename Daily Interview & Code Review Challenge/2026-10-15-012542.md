# Code Review Challenge 1 — Upload asset trên Azure Blob: memory tăng, dữ liệu bị ghi đè và retry tạo bản ghi trùng

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Blob Storage, EF Core, SQL Server, tenant authorization, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một enterprise marketing portal phục vụ nhiều tenant. API ASP.NET Core .NET 8 chạy trên ba Azure App Service instances, nhận file marketing tối đa 200 MiB, lưu private Blob và metadata trong SQL Server. File phải được scan trước khi xuất bản. Giờ cao điểm có thể đạt 300 uploads/phút; mobile client retry khi timeout.

Production xuất hiện memory spikes, hai uploads cùng filename khiến nội dung cũ biến mất, Blob không có SQL record, và nghi vấn người dùng tenant A ghi được file vào tenant B. Chưa xác định root cause duy nhất. Team muốn giữ API hiện tại nếu có thể, không chấp nhận phát hành file chưa scan.

## Đoạn code cần review

~~~csharp
[Authorize]
[ApiController]
[Route("api/tenants/{tenantId:guid}/assets")]
public sealed class AssetsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly BlobServiceClient _storage;
    private readonly ILogger<AssetsController> _logger;

    public AssetsController(
        AppDbContext db,
        BlobServiceClient storage,
        ILogger<AssetsController> logger)
    {
        _db = db;
        _storage = storage;
        _logger = logger;
    }

    [HttpPost]
    [RequestSizeLimit(209_715_200)]
    public async Task<IActionResult> Upload(Guid tenantId, IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Empty file");

        var container = _storage.GetBlobContainerClient("marketing-assets");
        var blobName = $"{tenantId}/{file.FileName}";
        var blob = container.GetBlobClient(blobName);

        await using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        await blob.UploadAsync(
            new BinaryData(buffer.ToArray()),
            overwrite: true);

        var asset = new Asset
        {
            Id = Guid.NewGuid(),
            TenantId = tenantId,
            FileName = file.FileName,
            BlobName = blobName,
            ContentType = file.ContentType,
            Status = "Ready",
            CreatedAtUtc = DateTime.UtcNow
        };

        _db.Assets.Add(asset);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Asset uploaded tenant={TenantId} file={FileName} blob={Blob}",
            tenantId, file.FileName, blobName);

        return Ok(new { asset.Id, asset.BlobName, asset.Status });
    }
}
~~~

## Kết quả code review tham khảo

### [Critical] — Thiếu tenant-level authorization

**Vấn đề:** <code>[Authorize]</code> chỉ xác nhận user đã đăng nhập, không kiểm quyền ghi vào tenant trên route.

**Tại sao xảy ra:** <code>tenantId</code> là input từ client, không phải resource permission.

**Ảnh hưởng production:** Cross-tenant write và mất data isolation.

**Cách sửa:** Dùng resource/policy-based authorization, xác minh tenant membership và quyền upload từ nguồn tin cậy trước mọi side effect; enforce tương tự ở read/publish API.

### [High] — Overwrite Blob bằng tên do client cung cấp

**Vấn đề:** Hai files cùng tên dùng chung Blob key và <code>overwrite: true</code>.

**Tại sao xảy ra:** Physical storage identity gắn với filename không unique, SQL lại tạo Asset ID mới.

**Ảnh hưởng production:** Record cũ có thể trỏ đến bytes mới; dữ liệu bị thay ngoài ý muốn.

**Cách sửa:** Server-generated immutable Blob key, filename chỉ là metadata; conditional create với <code>IfNoneMatch = ETag.All</code> khi cần chống overwrite.

### [High] — Memory amplification dưới concurrency

**Vấn đề:** Multipart <code>IFormFile</code> có thể được buffering, sau đó copy sang <code>MemoryStream</code> và <code>ToArray()</code> tạo thêm bản sao.

**Tại sao xảy ra:** Giới hạn request size không phải giới hạn memory allocation.

**Ảnh hưởng production:** LOH pressure, GC pause, OOM, process restart, p99 tăng.

**Cách sửa:** Không copy toàn bộ vào memory; dùng stream, đồng bộ multipart/request limits và concurrency. Nếu traffic/file lớn, đánh giá <code>MultipartReader</code> true streaming hoặc direct-to-Blob upload với SAS scope hẹp. <code>IFormFile.OpenReadStream()</code> một mình không loại bỏ model-binding buffering.

### [High] — Không có atomicity và recovery giữa Blob và SQL

**Vấn đề:** Upload Blob trước, ghi SQL sau; không có durable state hay compensation.

**Tại sao xảy ra:** SQL transaction không bao trùm Blob Storage; timeout có thể xảy ra sau side effect.

**Ảnh hưởng production:** Orphan Blob, mất metadata, retry tạo duplicate.

**Cách sửa:** Durable state machine <code>PendingUpload → PendingScan → Ready/Rejected</code>, reconciliation job cho stuck operations/orphans, cleanup có kiểm soát. Không giả định distributed transaction.

### [High] — Bỏ qua bước scan trước khi publish

**Vấn đề:** File được đánh dấu Ready ngay sau upload.

**Tại sao xảy ra:** Upload success bị đồng nhất với content approval.

**Ảnh hưởng production:** Untrusted file có thể được phục vụ cho người dùng.

**Cách sửa:** Quarantine/private storage, kiểm tra file signature/policy/malware theo yêu cầu, chỉ chuyển Ready sau khi scan thành công; delivery endpoint phải enforce trạng thái.

### [High] — Retry không idempotent

**Vấn đề:** Mỗi retry tạo ID mới, không có operation identity.

**Tại sao xảy ra:** Client timeout không chứng minh server chưa commit; query-then-insert đơn thuần cũng không giải quyết concurrent retries.

**Ảnh hưởng production:** Duplicate metadata, xử lý lặp và UI không nhất quán.

**Cách sửa:** Idempotency key theo tenant + unique SQL constraint + request fingerprint, xử lý unique conflict; replay trả status cũ, fingerprint khác trả 409.

### [Medium] — Thiếu validation và quota

**Vấn đề:** Chỉ check file rỗng và request limit; <code>ContentType</code> do client cung cấp.

**Tại sao xảy ra:** Không có file-type policy, signature validation, quota/rate limit.

**Ảnh hưởng production:** Abuse storage, file sai định dạng, chi phí tăng.

**Cách sửa:** Giới hạn kích thước thực, loại file, tenant quota; validate content signature và scan. Extension/MIME không đủ để bảo đảm an toàn.

### [Medium] — Không propagate cancellation

**Vấn đề:** Blob và EF calls không nhận <code>CancellationToken</code>.

**Tại sao xảy ra:** Không liên kết I/O với request lifecycle và không có recovery protocol.

**Ảnh hưởng production:** Lãng phí tài nguyên khi client disconnect; kết quả mơ hồ.

**Cách sửa:** Truyền <code>RequestAborted</code>; vẫn cần durable state vì cancellation không rollback side effect đã commit.

### [Medium] — Lộ storage internals và log input không kiểm soát

**Vấn đề:** API trả Blob key, log filename từ client.

**Tại sao xảy ra:** Public API identity trộn với physical storage identity.

**Ảnh hưởng production:** Lộ cấu trúc storage, rủi ro dữ liệu nhạy cảm trong logs.

**Cách sửa:** Trả opaque Asset ID/status, log structured OperationId và timings, giới hạn thông tin file theo policy.

### [Low] — Thiếu observability cho các bước thất bại

**Vấn đề:** Chỉ log khi thành công.

**Tại sao xảy ra:** Không có operation correlation và metrics cho workflow.

**Ảnh hưởng production:** Khó xác định lỗi Blob, SQL, scan hay retry.

**Cách sửa:** Trace từng dependency, metrics pending age, failed upload, orphan count, retry/conflict và alerts.

## Phiên bản đề xuất

Bản cải tiến sau dùng hai service nội bộ <code>ITenantAssetAuthorizer</code> và <code>IAssetWorkflow</code>; đây là abstraction do dự án implement, **không** phải Azure SDK APIs. <code>ReserveAsync</code> phải thực hiện atomic reservation với unique index <code>(TenantId, IdempotencyKey)</code>, kiểm tra fingerprint, giải quyết concurrent insert conflicts và tạo random Blob key. Ví dụ giữ <code>IFormFile</code> để hạn chế breaking change nhưng không hứa loại bỏ multipart buffering.

~~~csharp
[Authorize]
[ApiController]
[Route("api/tenants/{tenantId:guid}/assets")]
public sealed class AssetsController : ControllerBase
{
    private const long MaxBytes = 200L * 1024 * 1024;
    private readonly ITenantAssetAuthorizer _access;
    private readonly IAssetWorkflow _workflow;
    private readonly BlobContainerClient _quarantine;

    public AssetsController(
        ITenantAssetAuthorizer access,
        IAssetWorkflow workflow,
        BlobServiceClient storage)
    {
        _access = access;
        _workflow = workflow;
        _quarantine = storage.GetBlobContainerClient("asset-quarantine");
    }

    [HttpPost]
    [RequestSizeLimit(210_000_000)]
    public async Task<IActionResult> Upload(
        Guid tenantId,
        IFormFile file,
        [FromHeader(Name = "Idempotency-Key")] string key,
        CancellationToken ct)
    {
        if (!await _access.CanUploadAsync(User, tenantId, ct))
            return Forbid();

        if (file is null || file.Length <= 0 ||
            file.Length > MaxBytes || string.IsNullOrWhiteSpace(key))
            return BadRequest("Invalid upload");

        var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
        if (extension is not (".jpg" or ".png" or ".pdf"))
            return BadRequest("Unsupported file type");

        var reservation = await _workflow.ReserveAsync(
            tenantId, key, file.FileName, file.Length, ct);

        if (reservation.FingerprintConflict)
            return Conflict("Idempotency key reused for another upload");

        var asset = reservation.Asset;
        var statusUrl = $"/api/tenants/{tenantId}/assets/{asset.Id}";
        if (!reservation.IsNew)
            return Accepted(statusUrl, new { asset.Id, asset.Status });

        var blob = _quarantine.GetBlobClient(asset.BlobName);
        await using var input = file.OpenReadStream();

        await blob.UploadAsync(input, new BlobUploadOptions
        {
            Conditions = new BlobRequestConditions
            {
                IfNoneMatch = ETag.All
            },
            HttpHeaders = new BlobHttpHeaders
            {
                ContentType = "application/octet-stream"
            }
        }, ct);

        await _workflow.MarkPendingScanAsync(asset.Id, ct);
        return Accepted(statusUrl, new { asset.Id, Status = "PendingScan" });
    }
}
~~~

**Các điều kiện để code trên thực sự an toàn:** <code>ReserveAsync</code> dùng SQL transaction và unique index; fingerprint phải đủ mạnh để phân biệt request khác nội dung (cần checksum được server xác minh nếu contract yêu cầu byte-level identity). Replay <code>PendingUpload</code> trả 202 chứ không khẳng định bytes đã có; reconciler phải xử lý operation bị kẹt và retry/resume có lease. Nếu Blob upload thành công nhưng cập nhật SQL thất bại, reconciler đối chiếu record/Blob và sửa trạng thái hoặc cleanup. Scanner chỉ đọc quarantine và thực hiện conditional state transition; download chỉ phục vụ Ready với tenant authorization. Cấu hình multipart limits/reverse proxy và file signature validation phải được thực hiện ngoài đoạn code này.

## Giải thích thiết kế sau khi sửa

SQL giữ trạng thái logical operation, Blob giữ bytes; không có atomic transaction giữa hai hệ thống. Unique constraint chống concurrent duplicate trên nhiều App Service instances. Blob key server-generated tránh overwrite. <code>202 Accepted</code> phù hợp với scan bất đồng bộ; status endpoint và reconciliation là thành phần của contract. Với file nhỏ và tải thấp có thể giữ proxy API; với file lớn và concurrency cao cần đo để quyết định direct upload, không tự động tăng kiến trúc phức tạp.

## Trade-offs

- Durable state và reconciler tăng operational complexity nhưng xử lý partial failure.
- Idempotency cần key retention, fingerprint validation và unique constraint nhưng giảm duplicate side effects.
- Proxy upload dễ kiểm soát request nhưng tốn bandwidth/CPU; direct SAS giảm tải API song tăng complexity của client, completion verification và cleanup.
- Quarantine/scan tạo eventual availability nhưng bảo vệ delivery.
- Cancellation tiết kiệm tài nguyên nhưng không thay thế compensation hoặc reconciliation.

## Cách kiểm thử

1. **Security integration:** User tenant A upload/read/publish vào tenant B phải bị chặn trước side effect.
2. **Concurrency:** 20 concurrent retries cùng key qua nhiều instances chỉ tạo một logical operation; key khác nhưng filename giống không overwrite; fingerprint khác trả 409.
3. **Failure injection:** Crash sau reserve, sau Blob upload, trước SQL update; reconciliation không bao giờ publish file chưa scan.
4. **Load:** Concurrent uploads 100–200 MiB; đo working set, allocations, GC, p95/p99, disk buffering và 429/5xx.
5. **Content security:** MIME giả, file sai signature, scanner timeout/reject; delivery không cho tải asset Pending/Rejected.

## Quan sát trong production

Application Insights traces theo OperationId, Blob/SQL dependency duration, cancellation và error codes; Azure Monitor đo App Service memory, GC, restarts, HTTP 413/429/5xx và p95/p99. SQL dashboard theo PendingUpload/PendingScan age, idempotency conflicts; Blob dashboard theo orphan bytes, upload failures; alert khi scanner backlog hoặc reconciliation failures vượt SLA. Không log raw file content hoặc secrets.

## Câu hỏi phỏng vấn mở rộng

1. Nếu mobile client không thể polling status, bạn giữ contract đồng bộ đến mức nào mà vẫn tránh báo success giả?
2. Khi chuyển sang direct-to-Blob SAS, làm sao xác minh upload completion, tenant quota và ngăn client giả mạo file đã scan?
3. Scanner outage 6 giờ: chọn fail-closed hay degraded mode trong điều kiện nào?

# Code Review Challenge 2 — IIS deployment báo xanh dù schema và runtime không sẵn sàng

## Bối cảnh

Booking portal ASP.NET Core chạy trên hai IIS/Windows Server nodes phía sau load balancer, dùng chung SQL Server. TeamCity build ZIP, Octopus Deploy chạy script trên mỗi node. SLO yêu cầu giảm downtime tối đa và rollback binary nhanh. Production từng gặp 503 trong deploy, mixed versions và một lần rollback binary thất bại vì database schema không còn tương thích. Chưa biết hai nodes được triển khai song song hay tuần tự.

<code>DbMigrator.exe</code> là executable riêng của dự án, không phải một EF Core API mặc định. Script đang dùng:

## Đoạn code cần review

~~~powershell
param(
    [string]$PackageZip,
    [string]$SiteName = "BookingPortal",
    [string]$Environment = "Production",
    [string]$ConnectionString
)

$ErrorActionPreference = "Continue"
Import-Module WebAdministration

$sitePath = "C:\inetpub\wwwroot\$SiteName"
$healthUrl = "http://localhost/health"

Write-Host "Deploying $PackageZip to $Environment"
Stop-WebAppPool -Name $SiteName

Remove-Item "$sitePath\*" -Recurse -Force
Expand-Archive -Path $PackageZip -DestinationPath $sitePath -Force

$env:ASPNETCORE_ENVIRONMENT = $Environment
$env:ConnectionStrings__Main = $ConnectionString

& "C:\deploy-tools\DbMigrator.exe" --connection $ConnectionString

Start-WebAppPool -Name $SiteName
Start-Sleep -Seconds 2

$response = Invoke-WebRequest -Uri $healthUrl -UseBasicParsing
if ($response.StatusCode -ne 200) {
    Write-Host "Health check failed"
}

Write-Host "Connection used: $ConnectionString"
Write-Host "Deployment completed for $SiteName"
~~~

## Kết quả code review tham khảo

### [Critical] — Lộ database secret

**Vấn đề:** Connection string nằm trong command-line argument và bị in ra logs.

**Tại sao xảy ra:** Script không tách sensitive configuration khỏi deployment diagnostics.

**Ảnh hưởng production:** Credential compromise, truy cập DB trái phép, phải rotate và điều tra log exposure.

**Cách sửa:** Octopus sensitive variables/secret store, kênh cấu hình phù hợp với migrator không log plaintext; không truyền secret qua process arguments nếu có thể; least privilege và rotation.

### [High] — Migration không tương thích với rollback

**Vấn đề:** Migration chạy ngay trong mỗi node deploy, không có ownership/compatibility contract.

**Tại sao xảy ra:** Schema có thể bị đổi hoặc drop trong lúc old binary còn chạy; nhiều nodes có thể chạy migration lặp.

**Ảnh hưởng production:** Outage toàn hệ thống, old/new versions đều lỗi hoặc data loss.

**Cách sửa:** Expand-contract: additive schema trước, deploy code tương thích cả hai schema, backfill, contract sau khi không còn old consumers; migration một lần ở release stage có lock/ownership; test backward compatibility. Không mặc định down-migration an toàn.

### [High] — Xóa và giải nén in-place

**Vấn đề:** Xóa live directory trước khi xác nhận package hợp lệ.

**Tại sao xảy ra:** Không có immutable versioned release hoặc atomic activation.

**Ảnh hưởng production:** Site thiếu file, 503, rollback không có known-good artifact.

**Cách sửa:** Validate checksum/manifest, extract vào versioned directory, preflight, switch IIS physical path theo node; giữ previous release.

### [High] — Không fail-fast, bỏ qua exit code và health failure

**Vấn đề:** <code>$ErrorActionPreference = "Continue"</code>; native migrator exit code không được kiểm; non-200 chỉ log.

**Tại sao xảy ra:** Script coi write-host là failure handling.

**Ảnh hưởng production:** Pipeline báo success dù DB migration, deploy hoặc readiness fail.

**Cách sửa:** <code>$ErrorActionPreference = "Stop"</code>, check <code>$LASTEXITCODE</code>, throw khi failed, stop rollout và rollback có kiểm soát.

### [High] — Không có rolling deployment hoặc traffic drain

**Vấn đề:** App Pool bị stop khi node có thể vẫn nhận traffic; không có orchestration giữa hai nodes.

**Tại sao xảy ra:** Script local không phối hợp load balancer.

**Ảnh hưởng production:** 502/503, in-flight request loss, cả hai nodes unavailable nếu deploy song song.

**Cách sửa:** Drain node A, deploy/verify/rejoin, sau đó node B; xác định max unavailable và mixed-version compatibility. Với một node phải có maintenance window hoặc bổ sung capacity.

### [High] — Sai scope của environment variables

**Vấn đề:** <code>$env:</code> chỉ set trong PowerShell process.

**Tại sao xảy ra:** Không tự cấu hình IIS worker process độc lập hoặc bảo đảm giá trị còn sau restart.

**Ảnh hưởng production:** Sai environment hoặc missing DB connection.

**Cách sửa:** ASP.NET Core Module/IIS supported per-app configuration hoặc secret provider, xác minh runtime settings thực tế; không echo secret.

### [Medium] — Health check yếu và không chặn release

**Vấn đề:** <code>http://localhost/health</code> có thể sai binding; sleep cố định; failure không throw.

**Tại sao xảy ra:** Không phân biệt liveness, readiness và business smoke test.

**Ảnh hưởng production:** Rejoin node chưa sẵn sàng, lỗi chỉ phát hiện sau khi user truy cập.

**Cách sửa:** Probe đúng HTTPS host/binding, bounded retry, check readiness và business-critical flows; fail deployment nếu không đạt.

### [Medium] — Không pin artifact/release identity

**Vấn đề:** ZIP path tùy ý, không có checksum/version bảo đảm hai nodes cùng build.

**Tại sao xảy ra:** Pipeline thiếu immutable artifact contract.

**Ảnh hưởng production:** Version drift, không tái lập được incident.

**Cách sửa:** Release manifest gồm commit SHA, package checksum, version và schema compatibility, không chứa secrets.

### [Medium] — Thiếu preflight và rollback verification

**Vấn đề:** Không check disk/permissions/archive integrity; không giữ previous directory; không kiểm sau rollback.

**Tại sao xảy ra:** Chỉ thiết kế happy path.

**Ảnh hưởng production:** Deploy hỏng giữa chừng, manual recovery chậm.

**Cách sửa:** Preflight capacity, ACL, package; retain known-good release; verify readiness sau rollback.

### [Low] — Deployment observability chưa đủ

**Vấn đề:** Log không có release ID, node, duration, migration outcome và gate decision.

**Tại sao xảy ra:** Chưa coi deployment là production event.

**Ảnh hưởng production:** Khó liên hệ regression với release.

**Cách sửa:** Structured deployment events, traces và metrics theo ReleaseId/NodeId; alert 5xx, readiness và p95.

## Phiên bản đề xuất

Đây là **node activation stage**, không phải toàn bộ release pipeline. Preconditions do Octopus orchestration thực thi: verify immutable artifact/checksum; provision IIS runtime config/secrets đúng scope; chạy compatible database migration **một lần**; drain node khỏi LB; truyền đúng HTTPS health URL; triển khai tuần tự. Script giả định IIS root virtual directory tương ứng với <code>SiteName/</code>. Cần điều chỉnh cho IIS topology khác.

~~~powershell
param(
    [Parameter(Mandatory)] [string]$PackageZip,
    [Parameter(Mandatory)] [string]$SiteName,
    [Parameter(Mandatory)] [string]$AppPool,
    [Parameter(Mandatory)] [string]$ReleaseId,
    [Parameter(Mandatory)] [string]$HealthUrl
)

$ErrorActionPreference = "Stop"
Import-Module WebAdministration

$root = "C:\releases\$SiteName"
$releasePath = Join-Path $root $ReleaseId
$appcmd = Join-Path $env:windir "System32\inetsrv\appcmd.exe"

if (-not (Test-Path -PathType Leaf $PackageZip)) {
    throw "Release package missing"
}
if (Test-Path $releasePath) {
    throw "Release directory already exists"
}

New-Item -ItemType Directory -Path $releasePath -Force | Out-Null
Expand-Archive -Path $PackageZip -DestinationPath $releasePath
if (-not (Test-Path (Join-Path $releasePath "web.config"))) {
    throw "Missing IIS hosting configuration"
}

$previousPath = (& $appcmd list vdir "$SiteName/" /text:physicalPath)
if ($LASTEXITCODE -ne 0 -or [string]::IsNullOrWhiteSpace($previousPath)) {
    throw "Cannot read current IIS physical path"
}

try {
    Stop-WebAppPool -Name $AppPool
    & $appcmd set vdir "$SiteName/" "/physicalPath:$releasePath"
    if ($LASTEXITCODE -ne 0) { throw "IIS path switch failed" }

    Start-WebAppPool -Name $AppPool
    $ready = $false

    for ($attempt = 1; $attempt -le 12; $attempt++) {
        try {
            $response = Invoke-WebRequest -Uri $HealthUrl -UseBasicParsing -TimeoutSec 5
            if ($response.StatusCode -eq 200) {
                $ready = $true
                break
            }
        } catch {
            Start-Sleep -Seconds 5
        }
    }

    if (-not $ready) { throw "Readiness failed" }
    Write-Host "Activated release=$ReleaseId site=$SiteName"
}
catch {
    Stop-WebAppPool -Name $AppPool
    & $appcmd set vdir "$SiteName/" "/physicalPath:$previousPath"
    if ($LASTEXITCODE -ne 0) {
        throw "Rollback path switch failed; manual recovery required"
    }
    Start-WebAppPool -Name $AppPool
    throw
}
~~~

**Hardening cần bổ sung:** Validate <code>ReleaseId</code> theo allowlist và canonical path dưới root; dùng deployment lock tránh concurrent activation; preflight disk/ACL; verify package checksum; bounded retry cho mọi non-200 (không chỉ exceptions); verify rollback health; retention cleanup. Rollback ở đây chỉ chuyển binary/path, không rollback database. LB drain/rejoin và gate dựa trên traffic phải do pipeline điều phối. Cấu hình secrets không nằm trong script này.

**Release sequence:**

1. TeamCity build/test và phát hành immutable ZIP gắn commit SHA/checksum.
2. Octopus preflight và database expand migration một lần; test schema compatibility.
3. Drain node A, activate release, readiness + booking smoke test, quan sát 5xx/p95, rejoin.
4. Thực hiện tương tự node B; stop rollout nếu metrics vượt error budget.
5. Khi lỗi, revert node binary/path, verify readiness và dữ liệu; schema phải còn backward-compatible.
6. Contract migration chỉ sau khi không còn old readers/writers.

## Giải thích thiết kế sau khi sửa

Versioned directories giảm rủi ro deploy in-place. Rolling activation giới hạn blast radius và yêu cầu mixed-version compatibility. App Pool readiness phải được kiểm đúng host/TLS/config, không chỉ process running. Database evolution là một release lifecycle độc lập: rollback binary không thể đảo ngược mọi thay đổi dữ liệu. Không cần mặc định chuyển IIS lên Kubernetes; TeamCity + Octopus + IIS có thể đáp ứng yêu cầu nếu orchestration và verification đầy đủ.

## Trade-offs

- Rolling deployment mất thời gian hơn all-at-once nhưng giảm downtime risk.
- Versioned directories tăng disk usage và cần retention policy, đổi lại rollback nhanh.
- Expand-contract thêm release/backfill nhưng hỗ trợ old/new versions và rollback.
- Readiness quá sâu dễ phụ thuộc external systems gây cascading failures; liveness cần nhẹ hơn.
- Blue/green có thể cutover nhanh nhưng tốn capacity và vẫn cần data compatibility.
- Secrets management tăng vận hành/rotation nhưng tránh plaintext credentials trong logs.

## Cách kiểm thử

1. **Failure-path:** ZIP hỏng, thiếu web.config, disk full, path switch fail, App Pool fail; pipeline phải fail và giữ/khôi phục known-good.
2. **Database compatibility:** old/new binaries hoạt động với expanded schema, rollback binary sau migration, thử migration lock contention.
3. **Rolling/load:** request liên tục qua LB trong lúc deploy từng node; đo 502/503, p95/p99, in-flight requests và version skew.
4. **Security:** audit pipeline logs, process arguments, ACL, runtime config và secret rotation.
5. **Deployment/E2E:** health đúng HTTPS host, booking create/read/cancel smoke tests, Playwright E2E khi phù hợp, release ID đồng nhất.

## Quan sát trong production

Release events ghi ReleaseId, commit, checksum, node, stage, duration và rollback reason, không ghi secrets. IIS/Windows Server đo App Pool recycles, Event Viewer, 502/503, CPU/disk. Application Insights/Azure Monitor đo request failures, exceptions, dependency errors, p95/p99 và availability theo release/node. SQL Server theo dõi migration version, lock waits, deadlocks, connection errors. Kibana correlate logs bằng ReleaseId/NodeId/correlation ID. Stop rollout khi readiness fail, booking smoke test fail hoặc error rate vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu chỉ có một IIS node nhưng Product yêu cầu zero-downtime, bạn cần thay đổi tối thiểu những gì?
2. Migration rename cột lớn đang lock bảng 30 phút: thiết kế expand/backfill/contract như thế nào?
3. Health trả 200 nhưng booking endpoint trả 500 chỉ trên node mới: quyết định rollback dựa trên tín hiệu nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Tenant authorization là resource-level decision, không suy ra từ authentication.
- Blob và SQL không có atomic commit chung; retry cần idempotency, durable state và reconciliation.
- Multipart buffering, memory copies và concurrent large uploads có thể làm GC/OOM trở thành production incident.
- CI/CD success không đồng nghĩa production readiness; phải kiểm exit codes, IIS runtime config, LB traffic và business smoke tests.
- Binary rollback không tự rollback schema; expand-contract và mixed-version compatibility phải được thiết kế trước release.

## Mẫu tư duy cần nhớ

1. **Kiểm tra trust boundary trước khi tin input** — authenticated user chưa chắc được phép thao tác resource.
2. **Thiết kế retry cùng idempotency** — timeout không chứng minh external side effect chưa xảy ra.
3. **Measure before optimize** — đo memory, GC, p95/p99 và dependency latency trước khi đổi architecture.
4. **Rollback phải được kiểm thử** — binary, schema, config và traffic routing phải tương thích.
5. **Fail closed khi chưa chứng minh an toàn** — file chưa scan không được publish; rollout chưa ready không được tiếp tục.
