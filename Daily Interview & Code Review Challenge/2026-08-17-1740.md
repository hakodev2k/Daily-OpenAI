# Code Review Challenge 1 — Gửi 20.000 thông báo bằng `Task.WhenAll` làm downstream quá tải

**Chủ đề:** async/await, concurrency, resource lifetime, error handling, performance, cancellation  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API có chức năng gửi thông báo tới toàn bộ thành viên của một dự án. Khi project nhỏ vài chục người, endpoint hoạt động ổn. Gần đây hệ thống có các project lớn 10.000–20.000 thành viên.

Mỗi notification cần:

- đọc user preference từ database,
- gọi một HTTP provider bên ngoài,
- ghi trạng thái delivery vào database.

Sau khi một khách hàng lớn sử dụng tính năng, production xuất hiện các triệu chứng:

- outbound HTTP request tăng vọt trong vài giây,
- provider trả nhiều `429 Too Many Requests`,
- SQL connection pool bị căng,
- memory tăng mạnh,
- request mất hàng chục giây rồi timeout,
- khi client đóng trình duyệt, server vẫn tiếp tục gửi một phần notification,
- một số notification không có delivery record khi provider lỗi.

Team hiện tại muốn giữ implementation trong cùng application, chưa muốn tách microservice chỉ để giải quyết vấn đề này.

## Đoạn code cần review

```csharp
public sealed class NotificationService
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<NotificationService> _logger;

    public NotificationService(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<NotificationService> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task SendProjectAnnouncementAsync(
        Guid projectId,
        string message,
        CancellationToken cancellationToken)
    {
        var members = await _db.ProjectMembers
            .Where(x => x.ProjectId == projectId)
            .Select(x => new { x.UserId, x.Email })
            .ToListAsync(cancellationToken);

        var tasks = members.Select(async member =>
        {
            var preference = await _db.NotificationPreferences
                .FirstOrDefaultAsync(
                    x => x.UserId == member.UserId,
                    cancellationToken);

            if (preference?.EmailEnabled == false)
            {
                return;
            }

            var response = await _httpClient.PostAsJsonAsync(
                "/api/send",
                new
                {
                    to = member.Email,
                    body = message
                });

            var delivery = new NotificationDelivery
            {
                UserId = member.UserId,
                ProjectId = projectId,
                Success = response.IsSuccessStatusCode,
                StatusCode = (int)response.StatusCode,
                CreatedAt = DateTime.UtcNow
            };

            _db.NotificationDeliveries.Add(delivery);

            _logger.LogInformation(
                "Notification sent to {UserId} with status {StatusCode}",
                member.UserId,
                response.StatusCode);
        });

        await Task.WhenAll(tasks);
        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### 1. Dùng cùng một `DbContext` từ nhiều task song song

**Problem:** Tất cả task chạy trong `Task.WhenAll` đều query và mutate cùng `_db`.

**Why it happens:** `DbContext` được inject vào service rồi chia sẻ cho mọi operation trong cùng method.

**Production impact:** `DbContext` không được thiết kế để chạy nhiều operation song song trên cùng instance. Có thể gặp exception liên quan tới concurrent operation, state tracking không ổn định và request fail giữa chừng.

**Severity:** Critical

**Recommended fix:** Không dùng một `DbContext` chung trong các task song song. Hoặc chuẩn bị dữ liệu cần thiết trước khi fan-out, hoặc tạo scope/context riêng cho từng batch/worker bằng `IDbContextFactory<AppDbContext>` hoặc scope phù hợp.

### 2. Không có giới hạn concurrency

**Problem:** `members.Select(async ...)` tạo một task cho mỗi recipient rồi `Task.WhenAll` tất cả.

**Why it happens:** `Task.WhenAll` chỉ chờ nhiều task hoàn tất; nó không tự giới hạn số operation chạy đồng thời.

**Production impact:** Hàng nghìn outbound HTTP call và database operation có thể đồng thời tranh connection, socket, CPU và memory. Downstream dễ bị rate-limit hoặc quá tải.

**Severity:** Critical

**Recommended fix:** Dùng bounded concurrency, ví dụ `Parallel.ForEachAsync` với `MaxDegreeOfParallelism`, `SemaphoreSlim`, `Channel<T>` bounded hoặc queue/worker nội bộ. Giá trị concurrency cần được benchmark và điều chỉnh theo provider/database capacity.

### 3. N+1 query cho notification preference

**Problem:** Sau khi load danh sách member, code query `NotificationPreferences` một lần cho mỗi user.

**Why it happens:** Preference được lookup trong vòng fan-out thay vì preload theo batch.

**Production impact:** Với 20.000 members có thể tạo hàng chục nghìn query round-trip, tăng latency và làm SQL connection pool căng.

**Severity:** High

**Recommended fix:** Query preference theo batch hoặc join ngay từ query đầu tiên để chỉ lấy recipient đủ điều kiện.

### 4. Outbound HTTP call không truyền `CancellationToken`

**Problem:** `PostAsJsonAsync` không nhận `cancellationToken` trong code hiện tại.

**Why it happens:** Token chỉ được truyền cho EF Core operation.

**Production impact:** Khi request bị huỷ hoặc app shutdown, outbound call vẫn có thể tiếp tục tới timeout riêng của `HttpClient`.

**Severity:** High

**Recommended fix:** Truyền `cancellationToken` vào HTTP call. Với background workflow, cần phân biệt token của HTTP request với token của job/worker để tránh semantics không mong muốn.

### 5. Không có rate-limit/retry policy phù hợp cho `429` và lỗi transient

**Problem:** Mọi response được ghi thành success/failure nhưng không có backoff hoặc retry có kiểm soát.

**Why it happens:** Happy path được thiết kế như một batch I/O trực tiếp.

**Production impact:** Khi provider trả `429`, application có thể tiếp tục flood provider, làm tỷ lệ lỗi tăng và kéo dài sự cố.

**Severity:** High

**Recommended fix:** Có retry policy giới hạn với exponential backoff/jitter cho lỗi transient phù hợp, tôn trọng `Retry-After` nếu provider hỗ trợ, và giới hạn tổng retry. Không retry vô hạn hoặc retry mọi mã lỗi.

### 6. Một exception có thể làm cả `Task.WhenAll` thất bại trước khi delivery được lưu

**Problem:** Nếu bất kỳ task nào ném exception, `Task.WhenAll` fault và `SaveChangesAsync` có thể không chạy.

**Why it happens:** Delivery persistence được dồn xuống cuối và không có failure isolation theo recipient/batch.

**Production impact:** Provider có thể đã nhận một số request nhưng database không có delivery record tương ứng, gây khó retry và audit.

**Severity:** High

**Recommended fix:** Thiết kế delivery state rõ ràng như Pending/Sent/Failed, persist theo batch hoặc dùng outbox/job record trước khi thực thi side effect. Không phụ thuộc vào một `SaveChangesAsync` cuối cùng cho hàng nghìn side effects đã xảy ra.

### 7. Failure domain quá lớn

**Problem:** Một request HTTP chịu trách nhiệm orchestration cho 10.000–20.000 recipients.

**Why it happens:** Workload lớn được thực thi synchronously trong request lifecycle.

**Production impact:** Timeout, restart hoặc deploy giữa chừng làm workflow khó resume; user phải giữ request mở lâu.

**Severity:** High

**Recommended fix:** Với workload lớn, endpoint nên tạo một logical notification job rồi worker xử lý theo batch. Đây vẫn có thể nằm trong modular monolith, không bắt buộc microservice. API trả job id/trạng thái thay vì giữ request mở tới cuối.

### 8. Logging per-recipient ở `Information` tạo log volume lớn

**Problem:** Mỗi recipient tạo một log event thành công.

**Why it happens:** Diagnostic detail bị dùng như operational log mặc định.

**Production impact:** Hàng chục nghìn log/event cho một announcement làm tăng ingestion cost và gây nhiễu.

**Severity:** Medium

**Recommended fix:** Log summary theo batch/job; per-recipient chỉ log lỗi hoặc ở mức debug với sampling phù hợp.

### 9. Không dispose/consume response có chủ đích

**Problem:** `HttpResponseMessage` được giữ tới khi task kết thúc mà không `using`/dispose rõ ràng.

**Why it happens:** Response chỉ được đọc status code.

**Production impact:** Có thể giữ resource lâu hơn cần thiết; dưới concurrency lớn làm áp lực resource tăng.

**Severity:** Medium

**Recommended fix:** `using var response = await ...` hoặc thiết kế client method trả DTO/status cần thiết rồi dispose response bên trong.

### 10. Không có backpressure rõ ràng

**Problem:** Upstream có thể enqueue workload nhanh hơn downstream xử lý.

**Why it happens:** Thiếu queue capacity và admission control.

**Production impact:** Khi traffic tăng, memory/job backlog tăng không kiểm soát.

**Severity:** Medium

**Recommended fix:** Nếu dùng queue nội bộ, ưu tiên bounded channel/queue và định nghĩa hành vi khi đầy: reject, delay, hoặc persist backlog trong database.

## Phiên bản code đề xuất

Ví dụ sau giữ kiến trúc modular monolith, tạo job và xử lý theo batch với bounded concurrency. Đây là một hướng tham khảo; production có thể dùng Hangfire hoặc một worker nội bộ có persistence tuỳ yêu cầu durability.

```csharp
public sealed class NotificationBatchProcessor
{
    private const int BatchSize = 500;
    private const int MaxConcurrency = 16;

    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly INotificationProvider _provider;
    private readonly ILogger<NotificationBatchProcessor> _logger;

    public NotificationBatchProcessor(
        IDbContextFactory<AppDbContext> dbFactory,
        INotificationProvider provider,
        ILogger<NotificationBatchProcessor> logger)
    {
        _dbFactory = dbFactory;
        _provider = provider;
        _logger = logger;
    }

    public async Task ProcessAsync(
        Guid projectId,
        string message,
        CancellationToken cancellationToken)
    {
        await using var readDb =
            await _dbFactory.CreateDbContextAsync(cancellationToken);

        var recipients = await readDb.ProjectMembers
            .Where(x => x.ProjectId == projectId)
            .Join(
                readDb.NotificationPreferences,
                member => member.UserId,
                preference => preference.UserId,
                (member, preference) => new
                {
                    member.UserId,
                    member.Email,
                    preference.EmailEnabled
                })
            .Where(x => x.EmailEnabled)
            .Select(x => new Recipient(x.UserId, x.Email))
            .AsNoTracking()
            .ToListAsync(cancellationToken);

        foreach (var batch in recipients.Chunk(BatchSize))
        {
            cancellationToken.ThrowIfCancellationRequested();

            var results = new ConcurrentBag<DeliveryResult>();

            await Parallel.ForEachAsync(
                batch,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = MaxConcurrency,
                    CancellationToken = cancellationToken
                },
                async (recipient, ct) =>
                {
                    try
                    {
                        var result = await _provider.SendAsync(
                            recipient.Email,
                            message,
                            ct);

                        results.Add(new DeliveryResult(
                            recipient.UserId,
                            result.Success,
                            result.StatusCode,
                            null));
                    }
                    catch (OperationCanceledException) when (ct.IsCancellationRequested)
                    {
                        throw;
                    }
                    catch (Exception ex)
                    {
                        results.Add(new DeliveryResult(
                            recipient.UserId,
                            false,
                            null,
                            ex.GetType().Name));
                    }
                });

            await using var writeDb =
                await _dbFactory.CreateDbContextAsync(cancellationToken);

            writeDb.NotificationDeliveries.AddRange(
                results.Select(x => new NotificationDelivery
                {
                    UserId = x.UserId,
                    ProjectId = projectId,
                    Success = x.Success,
                    StatusCode = x.StatusCode,
                    ErrorCode = x.ErrorCode,
                    CreatedAt = DateTime.UtcNow
                }));

            await writeDb.SaveChangesAsync(cancellationToken);

            _logger.LogInformation(
                "Notification batch completed. ProjectId={ProjectId} BatchSize={BatchSize} Success={Success} Failed={Failed}",
                projectId,
                batch.Length,
                results.Count(x => x.Success),
                results.Count(x => !x.Success));
        }
    }

    private sealed record Recipient(Guid UserId, string Email);

    private sealed record DeliveryResult(
        Guid UserId,
        bool Success,
        int? StatusCode,
        string? ErrorCode);
}
```

`MaxConcurrency = 16` và `BatchSize = 500` chỉ là điểm khởi đầu, không phải benchmark mặc định cho mọi hệ thống. Con số thực tế phải dựa trên capacity provider, latency, connection pool và load test.

## Trade-offs

- Bounded concurrency làm throughput thấp hơn fan-out không giới hạn, nhưng đổi lại hệ thống ổn định và có backpressure.
- Xử lý theo batch tạo partial progress; nếu business yêu cầu all-or-nothing thì cần thiết kế khác, nhưng side effect tới external provider thường không thể rollback như transaction database.
- Chạy trong request đơn giản hơn nhưng không phù hợp workload dài. Background job bền vững hơn nhưng cần job state, retry và monitoring.
- `IDbContextFactory` giúp tách lifetime; một scope per batch cũng hợp lý.
- Nếu delivery phải đảm bảo mạnh hơn, outbox/job table có unique key và state machine là lựa chọn tốt hơn.

## Cách kiểm thử

1. **Load test:** 20.000 recipients, xác nhận số outbound call concurrent không vượt giới hạn cấu hình.
2. **Failure-path test:** provider trả `429` trong một khoảng thời gian, xác nhận retry/backoff không tạo retry storm.
3. **Cancellation test:** huỷ job giữa batch, xác nhận worker dừng có kiểm soát và batch đã commit không bị mất dấu.
4. **Database test:** xác nhận không có concurrent operation trên cùng `DbContext`, connection pool không bị cạn dưới load mục tiêu.
5. **Partial failure test:** một số recipient timeout, xác nhận các recipient khác vẫn được xử lý và delivery record phản ánh đúng trạng thái.

# Code Review Challenge 2 — Custom JWT authentication tin claims trước khi xác minh token

**Chủ đề:** Authentication, authorization, sensitive-data exposure, error handling, logging & observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một internal API được gọi từ web portal và một số automation client. Team muốn hỗ trợ JWT do identity provider phát hành nên đã viết custom authentication handler để đọc bearer token và tạo `ClaimsPrincipal`.

Gần đây security review phát hiện một số request với token lạ vẫn có thể truy cập endpoint cần role `Admin`. Đồng thời log production có chứa nguyên bearer token khi authentication thất bại.

Các endpoint sử dụng `[Authorize]` và một số endpoint dùng `[Authorize(Roles = "Admin")]`.

Team nói rằng token “đã được identity provider cấp” nên chỉ cần decode claims là đủ.

## Đoạn code cần review

```csharp
public sealed class CustomJwtHandler
    : AuthenticationHandler<AuthenticationSchemeOptions>
{
    private readonly ILogger<CustomJwtHandler> _logger;

    public CustomJwtHandler(
        IOptionsMonitor<AuthenticationSchemeOptions> options,
        ILoggerFactory loggerFactory,
        UrlEncoder encoder)
        : base(options, loggerFactory, encoder)
    {
        _logger = loggerFactory.CreateLogger<CustomJwtHandler>();
    }

    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        var authorization = Request.Headers.Authorization.ToString();

        if (string.IsNullOrWhiteSpace(authorization) ||
            !authorization.StartsWith("Bearer ", StringComparison.OrdinalIgnoreCase))
        {
            return Task.FromResult(AuthenticateResult.NoResult());
        }

        var token = authorization["Bearer ".Length..].Trim();

        try
        {
            var handler = new JwtSecurityTokenHandler();
            var jwt = handler.ReadJwtToken(token);

            if (jwt.ValidTo < DateTime.UtcNow)
            {
                return Task.FromResult(
                    AuthenticateResult.Fail("Token expired"));
            }

            var identity = new ClaimsIdentity(jwt.Claims, Scheme.Name);
            var principal = new ClaimsPrincipal(identity);

            _logger.LogInformation(
                "Authenticated token {Token} for subject {Subject}",
                token,
                principal.FindFirstValue("sub"));

            return Task.FromResult(
                AuthenticateResult.Success(
                    new AuthenticationTicket(principal, Scheme.Name)));
        }
        catch (Exception ex)
        {
            _logger.LogWarning(
                ex,
                "Failed to authenticate bearer token {Token}",
                token);

            return Task.FromResult(
                AuthenticateResult.Fail("Invalid token"));
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Token chỉ được parse, không được validate chữ ký

**Problem:** Code dùng `ReadJwtToken` rồi tin `jwt.Claims`.

**Why it happens:** Parse JWT chỉ đọc cấu trúc/header/payload; nó không chứng minh token được ký bởi issuer đáng tin cậy.

**Production impact:** Một attacker có thể tự tạo token chứa claims mong muốn và code vẫn tạo authenticated principal nếu token parse được và chưa hết hạn theo payload tự khai báo.

**Severity:** Critical

**Recommended fix:** Không dùng `ReadJwtToken` để authenticate. Dùng `AddJwtBearer` với authority/metadata hoặc cấu hình `TokenValidationParameters` phù hợp, để framework validate signature và các policy trước khi tạo principal.

### 2. Không validate issuer

**Problem:** Code không kiểm tra token có đến từ issuer được chấp nhận hay không.

**Why it happens:** Không có token validation pipeline.

**Production impact:** Token từ issuer khác hoặc token tự tạo có thể được chấp nhận.

**Severity:** Critical

**Recommended fix:** Validate issuer theo cấu hình identity provider. Không hard-code tùy tiện nếu hệ thống có multi-tenant/multi-issuer; cần policy rõ ràng.

### 3. Không validate audience

**Problem:** API không xác minh token được phát hành cho chính API này.

**Why it happens:** Chỉ kiểm `ValidTo`.

**Production impact:** Token hợp lệ về mặt chữ ký nhưng dành cho resource khác có thể bị dùng nhầm tại API này nếu không kiểm audience.

**Severity:** Critical

**Recommended fix:** Cấu hình valid audience(s) đúng với API/resource identifier.

### 4. Authorization có thể bị bypass qua claims giả

**Problem:** `ClaimsIdentity` được đánh dấu authenticated bằng `Scheme.Name` và chứa toàn bộ claims parse từ token chưa được verify.

**Why it happens:** Authentication và authorization trust boundary bị phá vỡ.

**Production impact:** `[Authorize]` có thể xem request là authenticated. Nếu role mapping phù hợp với claim attacker tự khai báo, `[Authorize(Roles = "Admin")]` có thể bị bypass.

**Severity:** Critical

**Recommended fix:** Chỉ tạo principal từ validated token. Role/permission claims cũng phải đến từ nguồn đã được xác minh và mapping phải được cấu hình có chủ đích.

### 5. Chỉ tự kiểm expiration là không đủ

**Problem:** Code chỉ so `ValidTo` với `UtcNow`.

**Why it happens:** Lifetime validation bị giản lược thành một field check.

**Production impact:** Bỏ qua các validation/policy khác như not-before, clock skew policy, issuer/audience/signature và key validity.

**Severity:** High

**Recommended fix:** Để token validation handler/framework xử lý lifetime theo cấu hình nhất quán.

### 6. Log nguyên bearer token

**Problem:** Token được đưa vào `Information` log khi thành công và `Warning` log khi thất bại.

**Why it happens:** Token bị coi như diagnostic string bình thường.

**Production impact:** Bearer token là credential. Nếu log bị truy cập, token chưa hết hạn có thể bị replay trong phạm vi quyền của nó.

**Severity:** High

**Recommended fix:** Không log raw token. Nếu cần correlation, log trace id, subject sau validation, issuer, token type hoặc fingerprint an toàn theo policy nội bộ; tránh tạo hash có thể gây hiểu nhầm là an toàn nếu lifecycle/policy chưa rõ.

### 7. Catch `Exception` quá rộng làm mất phân loại failure

**Problem:** Mọi exception đều được trả thành `Invalid token` và log warning như nhau.

**Why it happens:** Handler vừa parse vừa validate vừa log trong một block.

**Production impact:** Khó phân biệt malformed token, cấu hình issuer sai, key rotation issue hoặc lỗi runtime khác. Alerting khó chính xác.

**Severity:** Medium

**Recommended fix:** Dùng framework handler chuẩn; cấu hình event/log phù hợp. Nếu cần custom handling, phân loại lỗi authentication có chủ đích nhưng không tiết lộ chi tiết nhạy cảm cho client.

### 8. Tự viết authentication handler làm tăng maintenance/security burden không cần thiết

**Problem:** Team tự triển khai logic mà framework đã hỗ trợ.

**Why it happens:** Mong muốn “đơn giản hóa” bằng parse token thủ công.

**Production impact:** Dễ bỏ sót signature validation, key rollover, authority metadata, claim mapping và failure behavior.

**Severity:** Medium

**Recommended fix:** Ưu tiên `Microsoft.AspNetCore.Authentication.JwtBearer` và cấu hình chuẩn. Custom handler chỉ nên dùng khi authentication protocol thực sự khác hoặc có requirement đặc biệt đã được security review.

## Phiên bản code đề xuất

Ví dụ cấu hình chuẩn trong ASP.NET Core. Giá trị authority/audience chỉ là placeholder cấu hình, không phải giá trị mặc định thực tế.

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = builder.Configuration["Authentication:Authority"];
        options.Audience = builder.Configuration["Authentication:Audience"];

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            NameClaimType = "name",
            RoleClaimType = "roles"
        };

        options.Events = new JwtBearerEvents
        {
            OnAuthenticationFailed = context =>
            {
                var logger = context.HttpContext.RequestServices
                    .GetRequiredService<ILoggerFactory>()
                    .CreateLogger("Authentication");

                logger.LogWarning(
                    "JWT authentication failed. TraceId={TraceId} ExceptionType={ExceptionType}",
                    context.HttpContext.TraceIdentifier,
                    context.Exception.GetType().Name);

                return Task.CompletedTask;
            },
            OnTokenValidated = context =>
            {
                var logger = context.HttpContext.RequestServices
                    .GetRequiredService<ILoggerFactory>()
                    .CreateLogger("Authentication");

                logger.LogDebug(
                    "JWT validated. TraceId={TraceId} Subject={Subject}",
                    context.HttpContext.TraceIdentifier,
                    context.Principal?.FindFirstValue("sub"));

                return Task.CompletedTask;
            }
        };
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("AdminOnly", policy =>
        policy.RequireRole("Admin"));
});

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/admin/report", () => Results.Ok())
    .RequireAuthorization("AdminOnly");

app.Run();
```

Nếu identity provider dùng claim name khác cho role hoặc scope, cần cấu hình/mapping theo tài liệu của provider và contract thực tế của token. Không nên giả định mọi provider đều dùng `roles`.

## Trade-offs

- Dùng framework JWT bearer giảm custom code và security burden, nhưng cần hiểu đúng authority, audience, claims mapping và key rotation của provider.
- Role-based authorization đơn giản, nhưng với permission phức tạp có thể phù hợp hơn khi dùng policy/claim-based authorization.
- Validate token tại mỗi request có cost nhất định nhưng là phần bắt buộc của trust boundary; không được bỏ validation để “tối ưu”.
- Nếu API chấp nhận nhiều issuer, cấu hình sẽ phức tạp hơn và cần resolver/policy rõ ràng thay vì tắt issuer validation.
- Logging authentication phải đủ để điều tra incident nhưng không được biến log system thành kho credential.

## Cách kiểm thử

1. **Security test:** token tự ký chứa `roles=Admin`, xác nhận API trả `401` và không tạo principal.
2. **Audience test:** token hợp lệ nhưng dành cho resource khác, xác nhận bị reject.
3. **Issuer test:** token có signature hợp lệ từ issuer không được cho phép, xác nhận bị reject.
4. **Authorization test:** token hợp lệ nhưng không có role Admin, xác nhận endpoint Admin trả `403`.
5. **Logging test:** xác nhận raw bearer token không xuất hiện trong application log kể cả success và failure path.

## Quan sát trong production

Nên theo dõi:

- authentication success/failure count
- `401` và `403` rate tách biệt
- failure category ở mức an toàn: expired, invalid signature, invalid audience/issuer, malformed
- authority metadata/key retrieval failure
- trace id/correlation id
- subject sau khi token đã được validate
- alert khi authentication failure tăng bất thường hoặc key/metadata validation failure xuất hiện hàng loạt
- tuyệt đối không log raw access token, refresh token hoặc authorization header

## Câu hỏi phỏng vấn mở rộng

1. `401 Unauthorized` và `403 Forbidden` khác nhau thế nào trong pipeline authentication/authorization?
2. Nếu API cần chấp nhận token từ hai trusted issuers khác nhau, bạn thiết kế validation ra sao mà không tắt `ValidateIssuer`?
3. Nếu role claim trong token không đáng tin cho một hành động nhạy cảm, bạn sẽ dùng policy/permission model nào thay thế?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Task.WhenAll` không phải cơ chế giới hạn concurrency; fan-out I/O lớn cần bounded concurrency và backpressure.
- `DbContext` lifetime phải phù hợp với unit of work và không được chia sẻ cho concurrent operation.
- Side effect tới external provider cần failure isolation, retry semantics, job state và observability rõ ràng.
- Parse JWT không đồng nghĩa với validate JWT; trust chỉ được thiết lập sau signature/issuer/audience/lifetime validation.
- Authentication và authorization là hai lớp khác nhau; authorization chỉ đáng tin nếu principal được tạo từ authentication đã được xác minh.
- Secret như bearer token không bao giờ nên xuất hiện trong application log thông thường.

## Mẫu tư duy cần nhớ

1. **Bound concurrency before scaling throughput.**
2. **Never share request-scoped mutable state across parallel operations.**
3. **Design failure and retry semantics together with the happy path.**
4. **Decode is not validate; establish trust before using claims.**
5. **Treat observability as part of the security and reliability design.**
