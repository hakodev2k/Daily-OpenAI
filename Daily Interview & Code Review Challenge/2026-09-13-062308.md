# Code Review Challenge 1 — Cosmos DB activity API tăng RU đột biến và query chậm khi một tenant lớn lên

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Cosmos DB, partition key, query routing, point read, RU consumption, hot partition, pagination, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal employee platform chạy ASP.NET Core .NET 8 lưu activity feed trong Azure Cosmos DB. Container `activities` dùng partition key path `/tenantId`.

Mỗi document có dạng rút gọn:

```json
{
  "id": "act-9f0a...",
  "tenantId": "tenant-42",
  "employeeId": "emp-10482",
  "type": "TimesheetApproved",
  "createdAt": "2026-09-13T01:10:00Z",
  "payload": { }
}
```

Phần lớn tenant có vài nghìn employees, nhưng có một enterprise tenant chiếm phần lớn traffic. API hỗ trợ:

- đọc một activity theo `id`;
- lấy 100 activity gần nhất của một employee;
- ghi activity mới;
- scale nhiều application instances.

Sau vài tháng production xuất hiện các triệu chứng:

- RU consumption tăng mạnh vào giờ cao điểm;
- query activity của employee thuộc tenant lớn có latency cao hơn đáng kể;
- một số point-read endpoint trả `404` dù document tồn tại;
- có request đọc hàng nghìn records rồi mới trả 100 items;
- khi client disconnect, một số query vẫn tiếp tục consume RU;
- team đề xuất ngay việc đổi partition key sang `employeeId`, nhưng chưa đánh giá các access patterns khác hoặc migration cost.

Service hiện tại:

## Đoạn code cần review

```csharp
public sealed class ActivityService
{
    private readonly Container _container;

    public ActivityService(CosmosClient client)
    {
        _container = client.GetContainer("employee-platform", "activities");
    }

    public async Task<ActivityDocument?> GetAsync(
        string id,
        string employeeId,
        CancellationToken cancellationToken)
    {
        try
        {
            var response = await _container.ReadItemAsync<ActivityDocument>(
                id,
                new PartitionKey(employeeId),
                cancellationToken: cancellationToken);

            return response.Resource;
        }
        catch (CosmosException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
    }

    public async Task<IReadOnlyList<ActivityDocument>> GetRecentAsync(
        string employeeId,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.employeeId = @employeeId " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@employeeId", employeeId);

        using var iterator = _container.GetItemQueryIterator<ActivityDocument>(query);
        var all = new List<ActivityDocument>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(CancellationToken.None);
            all.AddRange(page.Resource);
        }

        return all.Take(100).ToArray();
    }

    public async Task AddAsync(
        ActivityDocument activity,
        CancellationToken cancellationToken)
    {
        await _container.CreateItemAsync(
            activity,
            new PartitionKey(activity.TenantId),
            cancellationToken: cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong point read và query routing.
2. Giải thích vì sao query theo `employeeId` có thể fan out rộng hơn cần thiết khi container partition theo `tenantId`.
3. Review việc đọc toàn bộ result set rồi mới `Take(100)`.
4. Phân tích nguyên nhân có thể khiến một tenant lớn trở thành điểm nóng và cách chứng minh bằng telemetry thay vì đoán.
5. Đánh giá đề xuất đổi partition key sang `employeeId`: lợi ích, chi phí và access patterns có thể bị ảnh hưởng.
6. Review cancellation propagation và resource budget của request.
7. Đề xuất corrected implementation/design, tests và production telemetry.

## Câu hỏi gợi mở

1. Với container partition theo `/tenantId`, point read cần những thông tin nào ngoài `id`?
2. Query hiện có đủ thông tin để Cosmos DB route trực tiếp đến một logical partition không?
3. `Take(100)` ở phía application có giảm lượng dữ liệu mà database đã đọc trước đó không?
4. Nếu phần lớn traffic đến từ một tenant duy nhất, partition key cardinality cao trên toàn hệ thống có tự động loại bỏ hotspot không?

## Kết quả code review tham khảo

### Critical — Point read truyền sai partition key

**Vấn đề:** Container partition theo `/tenantId`, nhưng `ReadItemAsync` truyền `employeeId` làm `PartitionKey`.

**Tại sao xảy ra:** Trong Cosmos DB, identity của một item cho point-read routing bao gồm `id` cùng partition key value tương ứng với partition key path của container. `employeeId` không thay thế được `tenantId` chỉ vì nó cũng là một field trên document.

**Ảnh hưởng production:** API có thể trả `404` cho item tồn tại vì request được route tới logical partition không chứa item đó. Đây là correctness bug, không phải eventual consistency symptom cần “retry thêm”.

**Cách sửa:** Contract của method phải nhận `tenantId` và dùng `new PartitionKey(tenantId)`. Nếu caller không biết tenant, cần xem lại API/data-access boundary thay vì biến point read thành một cross-partition lookup ngầm.

### High — Employee query không constrain partition key

**Vấn đề:** Query chỉ filter `employeeId`, trong khi partition key là `tenantId`.

**Tại sao xảy ra:** Cosmos DB không thể suy ra tenant từ `employeeId` trong query. Nếu không cung cấp `PartitionKey` trong `QueryRequestOptions` và không có predicate giúp route theo partition key, query có thể phải chạy trên nhiều partitions.

**Ảnh hưởng production:** RU và latency tăng theo lượng dữ liệu/partitions phải scan hoặc coordinate, đặc biệt khi traffic cao. Một endpoint tưởng là “lấy feed của một user” có thể tạo resource cost lớn hơn cần thiết.

**Cách sửa:** API nên nhận tenant context rõ ràng và query trong tenant partition:

```csharp
var options = new QueryRequestOptions
{
    PartitionKey = new PartitionKey(tenantId),
    MaxItemCount = 100
};
```

Query cũng nên include `tenantId` theo contract/readability nếu phù hợp, nhưng routing quan trọng là partition scope thực tế.

### High — Đọc toàn bộ result set rồi mới `Take(100)`

**Vấn đề:** Code consume mọi page từ iterator, materialize toàn bộ documents vào memory rồi mới lấy 100 items.

**Tại sao xảy ra:** Limit được thực hiện sau database/network boundary.

**Ảnh hưởng production:** RU, network bytes, allocations và request duration tăng không cần thiết. Với employee có lịch sử dài, một request nhỏ về mặt response có thể là một query rất lớn ở backend.

**Cách sửa:** Đưa limit vào query hoặc pagination contract, ví dụ `TOP 100` cho use case “100 gần nhất”, đồng thời dùng `MaxItemCount` phù hợp. Nếu UI cần paging, trả continuation token opaque thay vì đọc hết dữ liệu.

### High — Cancellation bị cắt ở query loop

**Vấn đề:** Method nhận `cancellationToken` nhưng `ReadNextAsync` dùng `CancellationToken.None`.

**Tại sao xảy ra:** Request cancellation không propagate xuống dependency operation.

**Ảnh hưởng production:** Client đã rời đi nhưng app vẫn tiếp tục đọc pages, tiêu tốn RU, network và CPU. Dưới load, work vô ích có thể làm incident nặng hơn.

**Cách sửa:** Truyền `cancellationToken` đến `ReadNextAsync`. Sau đó đo time-to-stop và RU consumed của cancelled requests thay vì chỉ kiểm tra code signature.

### High — Partition strategy có nguy cơ hotspot khi một tenant chiếm phần lớn workload

**Vấn đề:** `/tenantId` tạo locality tốt cho tenant-scoped queries, nhưng một enterprise tenant có thể chiếm tỷ lệ lớn traffic và data volume.

**Tại sao xảy ra:** Một partition key hợp lý về semantics không đảm bảo workload được phân phối đều trong mọi scale profile. Distribution phải được đánh giá bằng actual request/data distribution.

**Ảnh hưởng production:** Tenant nóng có thể gặp throttling/latency cao hơn trong khi tenants khác vẫn ổn; tổng RU provisioned cao không tự động giải quyết mọi skew ở logical partition level.

**Cách sửa:** Trước tiên thu thập RU/request charge, throttling, partition-key-level traffic và latency theo tenant. Nếu hotspot được chứng minh và vượt design envelope, cân nhắc synthetic partition key như `tenantId + bucket` hoặc một model khác phù hợp access patterns. Không đổi key chỉ vì một metric tổng tăng.

### High — Đề xuất chuyển thẳng sang `employeeId` có thể tối ưu một endpoint nhưng làm xấu use case khác

**Vấn đề:** Team muốn chọn partition key chỉ dựa trên query `employeeId`.

**Tại sao xảy ra:** Partition key là quyết định data-model cấp container, không phải index tùy endpoint. Các query tenant-wide, retention job, reporting hoặc bulk processing có thể bị phân tán mạnh hơn nếu partition theo employee.

**Ảnh hưởng production:** Một migration tốn kém có thể chuyển bottleneck từ endpoint này sang workload khác, đồng thời tăng operational complexity.

**Cách sửa:** Lập access-pattern matrix: point reads, employee feed, tenant-wide queries, writes, retention, hot-key distribution, expected size/growth. So sánh `/tenantId`, `/employeeId`, synthetic keys hoặc tách container/read model. Chỉ migrate khi evidence và scale requirement biện minh chi phí.

### Medium — `SELECT *` lấy nhiều dữ liệu hơn UI cần

**Vấn đề:** Query trả toàn bộ document, bao gồm `payload`, dù feed có thể chỉ cần id/type/time/summary.

**Tại sao xảy ra:** Data-access layer dùng document model trực tiếp làm read model.

**Ảnh hưởng production:** Tăng response bytes từ Cosmos DB, deserialization allocations và RU/network cost tùy document shape.

**Cách sửa:** Projection đúng fields cần cho feed. Nếu detail endpoint cần `payload`, giữ point read riêng.

### Medium — Không có input/resource budget rõ ràng cho query

**Vấn đề:** Method không thể hiện timeout budget, page contract hoặc giới hạn response ngoài `Take(100)` quá muộn.

**Tại sao xảy ra:** API contract được thiết kế theo “query rồi lọc” thay vì resource budget.

**Ảnh hưởng production:** Khó kiểm soát tail latency khi dependency chậm hoặc dataset lớn.

**Cách sửa:** Xác định bounded result size, continuation token, cancellation/timeout policy và telemetry cho request charge. Retry/throttling handling nên dựa trên SDK behavior và application SLO, không tạo vòng retry nóng tùy ý.

### Medium — Observability chưa gắn cost với access pattern

**Vấn đề:** Snippet không ghi nhận request charge, continuation count, tenant dimension, throttling hoặc dependency duration.

**Tại sao xảy ra:** Team chỉ thấy aggregate RU tăng nhưng không biết query shape nào gây ra.

**Ảnh hưởng production:** Dễ đưa ra quyết định partition/migration sai hoặc over-provision mà không xử lý query inefficiency.

**Cách sửa:** Ghi metrics/traces cho operation type, tenant (theo privacy policy), request charge, page count, result count, latency, cancellation và throttling. Dùng Azure Monitor/Application Insights kết hợp Cosmos DB metrics để correlate symptom với workload.

## Phiên bản đề xuất

Một implementation phù hợp với container hiện tại có thể giữ `/tenantId` nếu evidence cho thấy design vẫn đáp ứng scale, đồng thời sửa routing và query budget:

```csharp
public sealed class ActivityService
{
    private readonly Container _container;

    public ActivityService(CosmosClient client)
    {
        _container = client.GetContainer("employee-platform", "activities");
    }

    public async Task<ActivityDocument?> GetAsync(
        string tenantId,
        string id,
        CancellationToken cancellationToken)
    {
        try
        {
            var response = await _container.ReadItemAsync<ActivityDocument>(
                id,
                new PartitionKey(tenantId),
                cancellationToken: cancellationToken);

            return response.Resource;
        }
        catch (CosmosException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
    }

    public async Task<IReadOnlyList<ActivityFeedItem>> GetRecentAsync(
        string tenantId,
        string employeeId,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT TOP 100 c.id, c.type, c.createdAt " +
            "FROM c " +
            "WHERE c.tenantId = @tenantId AND c.employeeId = @employeeId " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@tenantId", tenantId)
            .WithParameter("@employeeId", employeeId);

        var options = new QueryRequestOptions
        {
            PartitionKey = new PartitionKey(tenantId),
            MaxItemCount = 100
        };

        using var iterator = _container
            .GetItemQueryIterator<ActivityFeedItem>(query, requestOptions: options);

        var result = new List<ActivityFeedItem>(100);

        while (iterator.HasMoreResults && result.Count < 100)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            result.AddRange(page.Resource);
        }

        return result.Take(100).ToArray();
    }
}
```

Nếu UI cần load-more, thay `TOP 100` bằng một paging contract dùng continuation token và bounded page size. Nếu telemetry chứng minh một tenant duy nhất vượt scale envelope của `/tenantId`, khi đó mới thiết kế repartition/synthetic key hoặc read model riêng.

## Giải thích thiết kế sau khi sửa

Fix đầu tiên không phải đổi partition key mà là làm code tôn trọng partition key hiện có. Point read nhận đúng `tenantId`; employee feed được scoped vào một tenant partition; query chỉ lấy fields và số rows cần thiết; cancellation đi xuống SDK.

Sau khi loại các inefficiency hiển nhiên, mới đánh giá skew. Nếu tenant lớn vẫn là hotspot, cần xem access pattern tổng thể. Một synthetic key có thể phân tải write/read tốt hơn nhưng làm query tenant-wide phức tạp hơn vì phải fan out qua buckets. Tách một feed-specific container cũng có thể hợp lý nếu read/write model khác biệt rõ và business chấp nhận eventual consistency giữa source và read model.

## Trade-offs

Giữ `/tenantId` đơn giản và phù hợp tenant isolation/query locality, nhưng có risk skew nếu một tenant quá lớn.

Partition theo `employeeId` phân tán employee feed tốt hơn, nhưng tenant-wide operations trở thành multi-partition và migration hiện hữu có chi phí đáng kể.

Synthetic partition key cải thiện distribution nhưng buộc application biết bucket strategy và có thể làm point lookup cần thêm metadata. Đây chỉ đáng làm khi metrics chứng minh cần thiết.

Projection nhỏ giảm cost nhưng tạo read DTO riêng thay vì reuse document model; đổi lại boundary rõ ràng hơn và giảm coupling.

## Cách kiểm thử

1. **Integration test point read:** tạo item với `tenantId = A`; đọc bằng `(id, A)` phải thành công, đọc với tenant khác không được trả item.
2. **Query-routing test:** seed nhiều tenants và xác minh employee query luôn truyền đúng partition key, trả đúng 100 items mới nhất của tenant/employee tương ứng.
3. **Load test skewed tenant:** mô phỏng một tenant chiếm phần lớn traffic; đo RU, latency p95/p99 và throttling trước/sau optimization.
4. **Cancellation test:** cancel request giữa pagination; xác minh iterator dừng sớm và không tiếp tục đọc pages không cần thiết.
5. **Projection/paging test:** kiểm tra continuation/page behavior, duplicate/missing item theo consistency contract được chọn.

## Quan sát trong production

Theo dõi:

- request charge theo operation/query category;
- p50/p95/p99 latency;
- throttled requests/429 theo tenant hoặc partition dimension phù hợp;
- số pages đọc mỗi request;
- result count và payload bytes;
- cancellation count và time-to-stop;
- Cosmos dependency duration trong Application Insights;
- top tenants theo traffic/data volume;
- request rate và RU distribution trước khi quyết định repartition.

## Câu hỏi phỏng vấn mở rộng

1. Nếu 95% query là employee-scoped nhưng reporting vẫn cần tenant-wide scan, bạn chọn partition strategy hay read model nào?
2. Khi nào bạn sẽ tạo container thứ hai phục vụ feed thay vì repartition container hiện tại?
3. Nếu hot tenant chỉ xuất hiện vài giờ mỗi ngày, bạn ưu tiên query optimization, capacity strategy hay data-model change dựa trên metric nào?

# Code Review Challenge 2 — Octopus deploy lên IIS “thành công” nhưng một số request chạy lẫn DLL cũ/mới

**Chủ đề:** TeamCity, Octopus Deploy, IIS, immutable artifacts, release safety, atomic deployment, configuration/secrets, App Pool lifecycle, rollback, health validation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core internal portal chạy trên IIS/Windows Server. TeamCity build application, tạo ZIP artifact, sau đó Octopus Deploy copy artifact lên hai IIS servers sau load balancer.

Gần đây có incident sau release:

- trong khoảng 1–2 phút, một số request trả `MissingMethodException`;
- server A chạy bình thường nhưng server B trả 500;
- refresh vài lần thì lỗi biến mất sau khi App Pool recycle;
- rollback mất nhiều thời gian vì team không chắc server đang chứa file của release nào;
- `appsettings.Production.json` được chỉnh trực tiếp trong thư mục live trên từng server;
- pipeline hiện copy file đè trực tiếp vào website đang phục vụ traffic.

Build/deploy script rút gọn như sau:

## Đoạn code cần review

```powershell
# TeamCity build step
$publish = ".\publish"
Remove-Item $publish -Recurse -Force -ErrorAction SilentlyContinue

dotnet restore .\src\EmployeePortal\EmployeePortal.csproj
dotnet publish .\src\EmployeePortal\EmployeePortal.csproj `
    -c Release `
    -o $publish

Copy-Item ".\config\appsettings.Production.json" `
    "$publish\appsettings.Production.json" -Force

Compress-Archive "$publish\*" ".\EmployeePortal.zip" -Force

# Octopus PowerShell deployment step
$sitePath = "C:\inetpub\wwwroot\EmployeePortal"
$packagePath = $OctopusParameters["Octopus.Action.Package.PackageFilePath"]

Expand-Archive $packagePath -DestinationPath $sitePath -Force

(Get-Content "$sitePath\appsettings.Production.json") `
    -replace "__DB_PASSWORD__", $OctopusParameters["DatabasePassword"] |
    Set-Content "$sitePath\appsettings.Production.json"

Import-Module WebAdministration
Restart-WebAppPool "EmployeePortal"

$response = Invoke-WebRequest "http://localhost/health"
Write-Host "Health status: $($response.StatusCode)"
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề release-safety khi expand/copy trực tiếp vào thư mục live.
2. Giải thích vì sao request có thể quan sát file set không đồng nhất trong lúc deploy.
3. Review artifact immutability và việc bake environment-specific config vào package.
4. Review secret injection và nguy cơ làm secret xuất hiện trong file/log/artifact.
5. Review App Pool restart, in-flight requests và cách drain/restore traffic an toàn hơn.
6. Đánh giá health check hiện tại có đủ để xác nhận release trên cả hai servers hay không.
7. Đề xuất deployment/rollback design tốt hơn mà không mặc định phải chuyển sang Kubernetes hoặc cloud platform khác.

## Câu hỏi gợi mở

1. `Expand-Archive -Force` có tạo ra một atomic switch từ release cũ sang release mới không?
2. Nếu một request load assembly A mới nhưng dependency B vẫn là file cũ trong vài giây, symptom nào có thể xuất hiện?
3. Artifact deploy sang test và production có còn là cùng một artifact nếu file config production được bake hoặc chỉnh thủ công theo từng server?
4. `Restart-WebAppPool` ngay sau copy xử lý thế nào với in-flight requests và traffic từ load balancer?
5. Health check `localhost` trên một node chứng minh được những gì, và không chứng minh được những gì về traffic path thực tế?

## Kết quả code review tham khảo

### Critical — Expand trực tiếp vào live directory tạo mixed-version file set

**Vấn đề:** `Expand-Archive` ghi đè nhiều files trong thư mục mà IIS đang phục vụ.

**Tại sao xảy ra:** File replacement diễn ra từng file, không phải một atomic application-version switch. Trong khoảng deployment, process hoặc request có thể quan sát tổ hợp assemblies/static files/config từ hai releases.

**Ảnh hưởng production:** `MissingMethodException`, `TypeLoadException`, inconsistent static assets hoặc behavior phụ thuộc timing. Hai servers còn có thể ở hai trạng thái khác nhau nếu một node deploy chậm/fail.

**Cách sửa:** Stage package vào một versioned directory riêng, verify đầy đủ artifact, sau đó thực hiện controlled activation. Trên IIS có thể dùng deployment strategy như app offline/drain + atomic-ish directory/symlink/junction switch phù hợp operational constraints, hoặc Web Deploy/Octopus pattern hỗ trợ thay thế an toàn. Không copy từng file vào live tree đang nhận traffic.

### High — Không có traffic drain trước App Pool restart/activation

**Vấn đề:** Script restart App Pool mà không phối hợp với load balancer hoặc connection draining.

**Tại sao xảy ra:** Deployment coi process restart là local action độc lập, trong khi node vẫn có thể nhận request.

**Ảnh hưởng production:** In-flight requests bị cắt, user thấy 5xx, background work có thể dừng giữa chừng, và hai nodes có behavior khác nhau trong rollout.

**Cách sửa:** Deploy từng node theo rolling sequence: remove/drain node khỏi traffic, chờ in-flight work trong bounded time, activate release, start/recycle app, verify health, đưa node trở lại traffic, rồi mới sang node tiếp theo.

### High — Artifact không được nhận diện/version hóa đủ rõ

**Vấn đề:** Package luôn tên `EmployeePortal.zip`; snippet không cho thấy commit SHA/build number/version được gắn vào artifact và release metadata.

**Tại sao xảy ra:** Build output được xem như file tạm thay vì immutable release artifact.

**Ảnh hưởng production:** Khó audit server đang chạy binary nào, khó rollback chính xác và dễ deploy nhầm artifact nếu pipeline/workspace reuse.

**Cách sửa:** Version artifact bằng build/release identity, lưu checksum và provenance. Octopus release phải trỏ tới một package version bất biến. Promote cùng artifact qua environments thay vì rebuild cho production.

### High — Environment-specific config bị bake/chỉnh trong application directory

**Vấn đề:** TeamCity copy `appsettings.Production.json` vào package, sau đó mỗi server còn chỉnh file live bằng deployment script/manual edits.

**Tại sao xảy ra:** Artifact và environment configuration bị trộn vào nhau.

**Ảnh hưởng production:** Server drift, khó reproduce release, rollback có thể mang config cũ/mới không rõ, cùng version package nhưng behavior khác giữa nodes.

**Cách sửa:** Giữ artifact environment-agnostic tối đa. Inject environment-specific settings tại deployment/runtime từ Octopus variables, environment variables hoặc secret/config provider có quản trị. Configuration versioning phải rõ và giống nhau giữa nodes trừ khi chủ đích khác.

### High — Secret được materialize thành plaintext file mà không có policy rõ ràng

**Vấn đề:** Script replace `__DB_PASSWORD__` trực tiếp vào `appsettings.Production.json` trên disk.

**Tại sao xảy ra:** Secret injection được làm bằng text substitution đơn giản.

**Ảnh hưởng production:** Secret có thể bị đọc bởi account không cần thiết, backup/file collection hoặc diagnostic tooling; nếu script/logging thay đổi, secret còn có risk xuất hiện trong output.

**Cách sửa:** Dùng sensitive Octopus variables và inject qua environment/runtime secret mechanism phù hợp, hạn chế ACL/least privilege. Nếu buộc phải ghi file, phải có explicit file-permission, rotation, cleanup và logging policy; không echo secret.

### High — Health validation chỉ kiểm tra localhost trên node hiện tại

**Vấn đề:** Một `Invoke-WebRequest http://localhost/health` sau restart không chứng minh external traffic path, config correctness trên cả cluster hoặc functional dependency readiness.

**Tại sao xảy ra:** “Process trả HTTP 200” bị coi là release verification đầy đủ.

**Ảnh hưởng production:** Node có thể healthy local nhưng routing/binding/TLS/config/dependency hoặc load-balancer registration vẫn lỗi. Server B có thể khác server A.

**Cách sửa:** Validate từng node trong rollout với health/readiness phù hợp, sau đó synthetic smoke test qua real entry path sau khi đưa node vào traffic. Gắn release/version vào health/info telemetry để biết node nào đang chạy build nào.

### High — Không có explicit rollback artifact/activation strategy

**Vấn đề:** Script ghi đè release cũ tại chỗ.

**Tại sao xảy ra:** Previous good release không còn nguyên vẹn dưới một versioned directory có thể activate lại nhanh.

**Ảnh hưởng production:** Rollback biến thành một deployment mới hoặc manual file recovery; MTTR tăng và dễ tạo thêm drift.

**Cách sửa:** Giữ N release directories gần nhất hoặc package versions retrievable, cùng activation metadata. Rollback phải là switch có kiểm soát về artifact đã biết tốt, đi qua cùng drain/health validation flow.

### Medium — Build dùng restore/publish nhưng chưa chứng minh dependency reproducibility

**Vấn đề:** Snippet không thể hiện lock/version policy hoặc build provenance đủ để chứng minh cùng source luôn tạo artifact tương đương.

**Tại sao xảy ra:** Pipeline tập trung vào command chạy thành công hơn là reproducibility.

**Ảnh hưởng production:** Dependency drift có thể làm build lại cùng branch nhưng binary khác, khiến incident/rollback khó điều tra.

**Cách sửa:** Pin dependency versions theo repository policy, lưu commit SHA/build number/package version, build một lần và promote artifact. Không rebuild cùng release ở mỗi environment.

### Medium — Không kiểm tra exit/error path đầy đủ trước khi activation

**Vấn đề:** Script minh họa không có fail-fast rõ ràng cho mọi command, checksum/extraction validation hoặc health retry budget.

**Tại sao xảy ra:** PowerShell step được viết tuyến tính với giả định command thất bại sẽ luôn dừng pipeline đúng cách.

**Ảnh hưởng production:** Có thể tiếp tục restart/activate sau partial extraction hoặc health validation không đủ chặt.

**Cách sửa:** Bật strict error handling (`$ErrorActionPreference = 'Stop'`), validate package, fail release nếu stage/activation/health step lỗi, và tự động rollback node về previous release khi policy cho phép.

### Medium — Restart toàn App Pool là blunt operation nếu không hiểu lifecycle

**Vấn đề:** `Restart-WebAppPool` được dùng như bước mặc định sau mọi deploy.

**Tại sao xảy ra:** Deployment không phân biệt warm-up, graceful shutdown, preload hay recycle strategy.

**Ảnh hưởng production:** Cold-start latency và request interruption có thể tăng; background tasks trong web process có thể bị cắt.

**Cách sửa:** Thiết kế lifecycle có chủ đích: drain traffic, stop/recycle với shutdown budget, warm up release, verify readiness rồi rejoin. Với critical background processing, không phụ thuộc lifecycle của IIS web process nếu workload cần durability riêng.

## Phiên bản đề xuất

Một flow triển khai đơn giản hơn nhưng an toàn hơn có thể vẫn dùng TeamCity + Octopus + IIS:

```powershell
$ErrorActionPreference = 'Stop'

$releaseId = $OctopusParameters['Octopus.Release.Number']
$packagePath = $OctopusParameters['Octopus.Action.Package.PackageFilePath']
$releasesRoot = 'C:\apps\EmployeePortal\releases'
$releasePath = Join-Path $releasesRoot $releaseId
$currentPath = 'C:\apps\EmployeePortal\current'

New-Item -ItemType Directory -Path $releasePath -Force | Out-Null
Expand-Archive $packagePath -DestinationPath $releasePath -Force

# Environment configuration should come from managed variables/runtime config.
# Do not mutate the build artifact with manually maintained server-specific files.

# At orchestration level before this point:
# 1. drain this node from load balancer
# 2. wait for in-flight requests within a bounded timeout

Import-Module WebAdministration
Stop-WebAppPool 'EmployeePortal'

if (Test-Path $currentPath) {
    Remove-Item $currentPath -Force
}

New-Item -ItemType Junction `
    -Path $currentPath `
    -Target $releasePath | Out-Null

Start-WebAppPool 'EmployeePortal'

$deadline = (Get-Date).AddSeconds(60)
do {
    try {
        $response = Invoke-WebRequest `
            'http://localhost/health/ready' `
            -TimeoutSec 5

        if ($response.StatusCode -eq 200) { break }
    }
    catch {
        Start-Sleep -Seconds 2
    }
} while ((Get-Date) -lt $deadline)

if ($response.StatusCode -ne 200) {
    throw "Release failed readiness validation"
}

# At orchestration level after this point:
# 3. return node to load balancer
# 4. run smoke test through the real external route
# 5. continue with the next node
```

Đây chỉ là một skeleton. Việc dùng junction/switch cần được validate với IIS/site layout, permissions và operational tooling thực tế. Một tổ chức có thể chọn Web Deploy hoặc Octopus IIS deployment features thay vì custom script; nguyên tắc quan trọng là versioned artifact, staged deployment, controlled activation, traffic drain, validation và fast rollback.

TeamCity nên tạo package có version rõ ràng, ví dụ gắn build number/commit SHA vào metadata. Octopus promote đúng package đó giữa environments. Secrets/config được cung cấp bởi deployment/runtime configuration chứ không sửa tay trên từng server.

## Giải thích thiết kế sau khi sửa

Release được chia thành các pha:

1. **Build once:** tạo artifact bất biến có version/provenance.
2. **Stage:** extract vào thư mục release riêng, không ảnh hưởng traffic hiện tại.
3. **Drain:** tạm ngừng đưa request mới vào node.
4. **Activate:** chuyển node sang release mới bằng mechanism có kiểm soát.
5. **Warm/verify:** đợi app ready và validate dependency/config cần thiết.
6. **Rejoin:** đưa node trở lại load balancer.
7. **Observe:** theo dõi error/latency trước khi deploy node kế tiếp.
8. **Rollback:** switch về previous known-good release nếu validation fail.

Cách này giải quyết mixed assemblies mà không cần đổi hosting platform. Kubernetes hay App Service có thể cung cấp primitives khác, nhưng không phải prerequisite để làm deployment an toàn.

## Trade-offs

Versioned release directories tốn disk và cần cleanup policy, đổi lại rollback nhanh và audit rõ.

Drain từng node làm rollout lâu hơn nhưng giảm blast radius. Với chỉ hai servers, capacity headroom phải đủ để một server tạm rời traffic; nếu không, cần điều chỉnh infrastructure hoặc maintenance strategy.

Runtime config/secrets làm pipeline/config management phức tạp hơn chút so với file sửa tay, nhưng giảm drift và tăng reproducibility.

Health checks sâu quá có thể phụ thuộc external service và gây false failure; health contract phải lightweight, bounded và phản ánh readiness cần thiết cho request path thực tế.

## Cách kiểm thử

1. **Deployment integration test:** deploy dưới representative traffic; xác minh không xuất hiện mixed-version exception và in-flight request failure nằm trong SLO.
2. **Partial-stage failure test:** làm extraction fail giữa chừng; active release phải không đổi và node không được rejoin với release lỗi.
3. **Rollback test:** sau khi readiness fail, activate previous known-good release và verify external route phục hồi.
4. **Configuration/security validation:** kiểm tra hai nodes nhận cùng non-secret config, secret không nằm trong artifact/log và file ACL/runtime injection đúng policy.
5. **Two-node rollout test:** deploy node A rồi B, verify load balancer chỉ route tới node healthy và mỗi response có release/version telemetry đúng.

## Quan sát trong production

Theo dõi:

- release ID/build SHA trên từng server;
- deploy start/end/failure và activation duration;
- App Pool recycle/restart count;
- startup/warm-up duration;
- 5xx, `MissingMethodException`, `TypeLoadException` theo release;
- request p50/p95/p99 trong rollout;
- node health/readiness và load-balancer membership;
- in-flight request count lúc drain;
- configuration version/checksum không chứa secret;
- rollback count và rollback duration.

Application Insights/Kibana logs nên có release/version dimension để correlate incident với node và artifact cụ thể.

## Câu hỏi phỏng vấn mở rộng

1. Nếu hệ thống chỉ có hai IIS servers và một server không đủ capacity gánh toàn bộ traffic, bạn thay đổi rollout strategy hay infrastructure thế nào?
2. Khi nào `app_offline.htm` là lựa chọn chấp nhận được, và khi nào rolling drain/versioned activation tốt hơn?
3. Nếu rollback binary nhưng configuration schema đã đổi, bạn thiết kế compatibility/rollback contract ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Cosmos DB partition key phải khớp access pattern thực tế; point read cần đúng partition key value của item, còn query thiếu partition scope có thể tốn nhiều RU hơn cần thiết.
- Limit ở application sau khi đã đọc hết dữ liệu không phải database-side optimization.
- Hot partition là bài toán workload distribution cần đo bằng telemetry; không nên đổi partition key chỉ vì aggregate RU tăng.
- Deployment an toàn trên IIS vẫn cần immutable/versioned artifact, staging, controlled activation, traffic draining, health validation và rollback rõ ràng.
- “Pipeline success” không đồng nghĩa “release safe”; file-copy deployment vào live directory có thể tạo mixed-version state dù mọi command đều chạy thành công.

## Mẫu tư duy cần nhớ

- Thiết kế data partition từ access patterns và distribution, không từ một query đơn lẻ.
- Đẩy resource limits xuống dependency boundary thay vì lọc muộn trong application.
- Measure skew/cost before repartitioning.
- Build once, promote the same artifact, stage before activate.
- Drain → activate → verify → observe → rollback nếu cần.
