# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để xử lý cấu hình offboarding mailbox. Khi cấu hình hết hạn, job phải gọi một external mail service để reset forwarding/delegation, sau đó đánh dấu bản ghi đã hoàn tất.

Ứng dụng chạy 3 instance. Hangfire có retry khi job thất bại. Bình thường chỉ vài trăm cấu hình hết hạn mỗi ngày, nhưng production thỉnh thoảng ghi nhận cùng một mailbox bị reset hai lần, audit history bị duplicate, và một số record vẫn ở trạng thái `Pending` dù external operation đã thành công.

Business yêu cầu không bỏ sót cấu hình, nhưng cũng không muốn một mailbox bị xử lý nhiều lần. External API không cung cấp distributed transaction với database của ứng dụng.

## Đoạn code cần review

```csharp
public sealed class ExpiredMailConfigJob
{
    private readonly AppDbContext _db;
    private readonly IMailAdminClient _mailClient;
    private readonly ILogger<ExpiredMailConfigJob> _logger;

    public ExpiredMailConfigJob(
        AppDbContext db,
        IMailAdminClient mailClient,
        ILogger<ExpiredMailConfigJob> logger)
    {
        _db = db;
        _mailClient = mailClient;
        _logger = logger;
    }

    public async Task ExecuteAsync()
    {
        var expired = await _db.MailConfigs
            .Where(x => x.Status == "Pending" && x.EndTime <= DateTime.UtcNow)
            .ToListAsync();

        foreach (var config in expired)
        {
            try
            {
                await _mailClient.ResetMailboxAsync(config.UserEmail);

                config.Status = "Completed";
                config.CompletedAt = DateTime.UtcNow;

                _db.MailConfigHistories.Add(new MailConfigHistory
                {
                    MailConfigId = config.Id,
                    Action = "ResetExpired",
                    CreatedAt = DateTime.UtcNow
                });

                await _db.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed to reset expired mail config {@Config}", config);
                throw;
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không atomic giữa nhiều worker

**Problem:** Nhiều worker có thể cùng query một record `Pending` trước khi bất kỳ worker nào commit trạng thái mới.  
**Why it happens:** `WHERE Status = Pending` chỉ là điều kiện đọc, không phải cơ chế claim độc quyền.  
**Production impact:** External reset có thể chạy nhiều lần, history duplicate hoặc side effect không mong muốn.  
**Severity:** Critical  
**Recommended fix:** Claim record bằng atomic conditional update/locking strategy phù hợp database, hoặc dùng trạng thái `Processing` kèm lease/version. Chỉ worker claim thành công mới xử lý.

### 2. Không có idempotency boundary cho external operation

**Problem:** `ResetMailboxAsync()` không gắn operation identifier hoặc business idempotency key.  
**Why it happens:** Retry có thể gửi lại cùng command sau timeout hoặc failure phía local.  
**Production impact:** Một side effect không idempotent có thể bị thực hiện nhiều lần.  
**Severity:** Critical  
**Recommended fix:** Nếu external service hỗ trợ, truyền stable operation ID như `mail-config:{Id}:reset`. Nếu không hỗ trợ, thiết kế operation theo desired state khi có thể và có reconciliation/audit để xác nhận trạng thái thực tế.

### 3. Dual-write inconsistency giữa external system và database

**Problem:** External call có thể thành công rồi database commit thất bại.  
**Why it happens:** Hai resource không nằm trong cùng transaction.  
**Production impact:** Local record vẫn `Pending`; retry gọi external operation lần nữa.  
**Severity:** High  
**Recommended fix:** Dùng explicit processing state, operation ID, retry-safe external semantics và reconciliation. Không giả định EF transaction có thể bao phủ external API.

### 4. Một lỗi làm retry lại cả batch

**Problem:** `throw` trong vòng lặp kết thúc execution.  
**Why it happens:** Một record lỗi khiến Hangfire retry invocation chứa cả batch.  
**Production impact:** Những record đã xử lý trước đó có thể được query/xử lý lại tùy trạng thái commit; throughput và blast radius kém.  
**Severity:** High  
**Recommended fix:** Tách scheduling và processing: enqueue một job theo `configId`, hoặc claim batch nhỏ rồi xử lý từng operation độc lập với retry riêng.

### 5. Không có optimistic concurrency guard

**Problem:** Update entity không kiểm tra version/status tại thời điểm commit.  
**Why it happens:** Entity được load rồi thay đổi trong memory; concurrent transition có thể xảy ra trước `SaveChangesAsync`.  
**Production impact:** Lost transition hoặc state machine không hợp lệ.  
**Severity:** High  
**Recommended fix:** Dùng concurrency token/version hoặc conditional update yêu cầu expected state/version.

### 6. Không truyền cancellation token

**Problem:** Query, external call và save không nhận cancellation token.  
**Why it happens:** Method không expose cancellation.  
**Production impact:** Shutdown/deployment khó dừng công việc sạch sẽ; operation có thể tiếp tục lâu hơn mong muốn.  
**Severity:** Medium  
**Recommended fix:** Nhận `CancellationToken` và propagate xuống I/O APIs; external operation vẫn phải idempotent vì cancellation không chứng minh remote side effect chưa xảy ra.

### 7. Load toàn bộ record hết hạn vào memory

**Problem:** `ToListAsync()` lấy toàn bộ pending records.  
**Why it happens:** Không có batching/limit.  
**Production impact:** Memory, transaction/state tracking và execution duration tăng khi backlog lớn.  
**Severity:** Medium  
**Recommended fix:** Claim batch giới hạn, ví dụ 50–200 records tùy tải, rồi lặp các batch.

### 8. Structured log có thể ghi quá nhiều dữ liệu entity

**Problem:** Log toàn bộ `{@Config}`.  
**Why it happens:** Destructuring entity trực tiếp.  
**Production impact:** Có thể lộ PII/configuration và làm log lớn.  
**Severity:** Medium  
**Recommended fix:** Log các identifier cần thiết như config ID, correlation/operation ID và mailbox đã mask/hash theo policy.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định repository cung cấp một thao tác claim atomic và external client hỗ trợ stable operation ID. Chi tiết SQL claim phụ thuộc SQL Server/PostgreSQL nên không được che giấu sau một `SELECT` thông thường.

```csharp
public sealed class ExpiredMailConfigJob
{
    private readonly IMailConfigRepository _repository;
    private readonly IMailAdminClient _mailClient;
    private readonly ILogger<ExpiredMailConfigJob> _logger;

    public ExpiredMailConfigJob(
        IMailConfigRepository repository,
        IMailAdminClient mailClient,
        ILogger<ExpiredMailConfigJob> logger)
    {
        _repository = repository;
        _mailClient = mailClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(CancellationToken cancellationToken)
    {
        while (!cancellationToken.IsCancellationRequested)
        {
            var items = await _repository.ClaimExpiredAsync(
                batchSize: 100,
                leaseDuration: TimeSpan.FromMinutes(10),
                cancellationToken);

            if (items.Count == 0)
                return;

            foreach (var item in items)
            {
                cancellationToken.ThrowIfCancellationRequested();

                var operationId = $"mail-config:{item.Id}:reset";

                try
                {
                    await _mailClient.ResetMailboxAsync(
                        item.UserEmail,
                        operationId,
                        cancellationToken);

                    await _repository.MarkCompletedAsync(
                        item.Id,
                        item.Version,
                        operationId,
                        cancellationToken);

                    _logger.LogInformation(
                        "Expired mail configuration completed. ConfigId={ConfigId} OperationId={OperationId}",
                        item.Id,
                        operationId);
                }
                catch (OperationCanceledException)
                    when (cancellationToken.IsCancellationRequested)
                {
                    throw;
                }
                catch (Exception ex)
                {
                    await _repository.RecordFailureAsync(
                        item.Id,
                        operationId,
                        ex.GetType().Name,
                        cancellationToken);

                    _logger.LogError(
                        ex,
                        "Expired mail configuration failed. ConfigId={ConfigId} OperationId={OperationId}",
                        item.Id,
                        operationId);
                }
            }
        }
    }
}
```

Repository nên đảm bảo `ClaimExpiredAsync` là atomic đối với concurrent workers và lưu `Processing`, lease expiry, attempt count/version. `MarkCompletedAsync` nên ghi state transition và history trong cùng database transaction. Nếu worker chết sau remote success nhưng trước local completion, reconciliation dùng operation ID hoặc kiểm tra desired state để kết thúc an toàn.

## Trade-offs

Claim/lease và state machine phức tạp hơn một query đơn giản nhưng giải quyết failure modes thực tế của distributed side effects. Nếu external operation thật sự idempotent theo desired state, thiết kế có thể đơn giản hơn; tuy nhiên vẫn cần xử lý duplicate history và local state. Distributed lock có thể giảm concurrent execution nhưng không tự giải quyết crash sau remote success, vì vậy không nên coi lock là thay thế cho idempotency.

## Cách kiểm thử

1. **Concurrency test:** Chạy nhiều worker cùng claim một record và xác nhận chỉ một worker nhận quyền xử lý tại một thời điểm.
2. **Failure-path integration test:** External call thành công nhưng giả lập database completion failure; retry/reconciliation không tạo side effect sai.
3. **Retry test:** Cùng operation ID chạy nhiều lần nhưng chỉ tạo một logical completion/history.
4. **Lease recovery test:** Worker chết sau claim; record được worker khác nhận lại sau lease expiry.
5. **Load test:** Tạo backlog lớn và xác nhận memory, database load, throughput và job duration nằm trong ngưỡng chấp nhận.

## Quan sát trong production

Theo dõi `pending_count`, `processing_count`, `expired_processing_lease_count`, attempts per operation, duplicate/idempotency hits, external latency/error rate và completion latency. Log `ConfigId`, `OperationId`, attempt và state transition; trace external call và database transition trong cùng correlation. Alert khi backlog/oldest pending age tăng hoặc lease hết hạn bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ implement atomic claim khác nhau thế nào trên SQL Server và PostgreSQL?
2. Nếu external API hoàn toàn không hỗ trợ idempotency key và `ResetMailbox` không phải desired-state operation, bạn giảm duplicate side effect thế nào?
3. Tại sao `[DisableConcurrentExecution]` hoặc một distributed lock vẫn chưa đủ để đảm bảo exactly-once business outcome?

# Code Review Challenge 2 — API export audit log có authorization bypass và SQL injection

**Thời gian review đề xuất:** 20–25 phút

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép tenant admin export audit events để điều tra incident. Endpoint nhận `tenantId`, khoảng thời gian và chuỗi sort từ UI. Kết quả có thể chứa email người dùng, IP và nội dung action.

Production gần đây thấy một số export có thời gian chạy rất lâu. Security review cũng đặt câu hỏi liệu tenant admin có thể truy cập dữ liệu tenant khác hay không. Endpoint đã có `[Authorize]`, nên developer ban đầu cho rằng authorization đã đủ.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly SqlConnection _connection;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        SqlConnection connection,
        ILogger<AuditController> logger)
    {
        _connection = connection;
        _logger = logger;
    }

    [HttpGet("export")]
    public async Task<IActionResult> Export(
        Guid tenantId,
        DateTime? from,
        DateTime? to,
        string sort = "CreatedAt DESC")
    {
        var sql = $@"
            SELECT Id, TenantId, UserEmail, IpAddress, Action, CreatedAt
            FROM AuditEvents
            WHERE TenantId = '{tenantId}'
              AND CreatedAt >= '{from ?? DateTime.MinValue}'
              AND CreatedAt <= '{to ?? DateTime.MaxValue}'
            ORDER BY {sort}";

        await _connection.OpenAsync();

        using var command = new SqlCommand(sql, _connection);
        using var reader = await command.ExecuteReaderAsync();

        var rows = new List<object>();
        while (await reader.ReadAsync())
        {
            rows.Add(new
            {
                Id = reader.GetGuid(0),
                TenantId = reader.GetGuid(1),
                UserEmail = reader.GetString(2),
                IpAddress = reader.GetString(3),
                Action = reader.GetString(4),
                CreatedAt = reader.GetDateTime(5)
            });
        }

        _logger.LogInformation(
            "User {User} exported audit data for tenant {TenantId}: {@Rows}",
            User.Identity!.Name, tenantId, rows);

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object-level/tenant authorization

**Problem:** Caller tự truyền `tenantId`; code không kiểm tra tenant membership/permission.  
**Why it happens:** `[Authorize]` chỉ yêu cầu authenticated principal theo policy hiện tại, không tự ràng buộc route/query resource với tenant của caller.  
**Production impact:** Một authenticated user có thể thử tenant ID khác và đọc dữ liệu không thuộc quyền của mình.  
**Severity:** Critical  
**Recommended fix:** Resolve allowed tenant từ trusted claims/membership store và enforce resource authorization trước query. Với role cross-tenant đặc biệt, dùng explicit policy và audit.

### 2. SQL injection qua `sort`

**Problem:** `ORDER BY {sort}` ghép trực tiếp user input.  
**Why it happens:** SQL identifiers/direction được tạo bằng string interpolation.  
**Production impact:** Có thể thay đổi câu SQL tùy driver/database configuration và tạo security incident nghiêm trọng.  
**Severity:** Critical  
**Recommended fix:** Map enum/known sort keys sang các SQL fragment cố định; không đưa raw client string vào SQL.

### 3. Giá trị query được xây bằng string interpolation

**Problem:** Tenant/date values được embed vào SQL text thay vì parameters.  
**Why it happens:** Interpolation tạo SQL phụ thuộc formatting và bỏ qua parameter typing.  
**Production impact:** Correctness/locale issues, khó tận dụng plan reuse và tạo thói quen injection-prone.  
**Severity:** High  
**Recommended fix:** Dùng typed `SqlParameter` cho tenant/time bounds.

### 4. Export không có giới hạn phạm vi/kích thước

**Problem:** `DateTime.MinValue` đến `DateTime.MaxValue`, không pagination/row cap/export policy.  
**Why it happens:** Missing filters mặc định thành toàn bộ lịch sử.  
**Production impact:** Query lâu, memory cao, database pressure và denial-of-service tự gây ra.  
**Severity:** High  
**Recommended fix:** Validate `from <= to`, áp maximum range, row/export size policy; với export lớn chuyển sang background export/streaming có kiểm soát.

### 5. Buffer toàn bộ kết quả vào memory

**Problem:** Tất cả rows được giữ trong `List<object>` rồi mới trả.  
**Why it happens:** Endpoint materialize full result set.  
**Production impact:** Large Object Heap/memory pressure, GC và process instability khi export lớn đồng thời.  
**Severity:** High  
**Recommended fix:** Giới hạn dataset hoặc stream file/result; export lớn nên asynchronous/background với storage và signed/authorized download flow.

### 6. Không propagate request cancellation

**Problem:** `OpenAsync`, `ExecuteReaderAsync`, `ReadAsync` không nhận `HttpContext.RequestAborted`.  
**Why it happens:** Cancellation bị bỏ qua.  
**Production impact:** Client disconnect nhưng database/query vẫn tiêu tốn tài nguyên.  
**Severity:** Medium  
**Recommended fix:** Propagate request cancellation và đặt command timeout phù hợp; cancellation không thay thế server-side query limits.

### 7. Log toàn bộ exported rows

**Problem:** `{@Rows}` đưa email, IP và action data vào application logs.  
**Why it happens:** Audit hành vi export bị nhầm với lưu bản sao dữ liệu export.  
**Production impact:** Tăng privacy/security exposure, log volume và retention footprint.  
**Severity:** High  
**Recommended fix:** Log actor ID, authorized tenant ID, time range, row count, export ID, result và correlation ID; không log payload trừ khi policy đặc biệt yêu cầu và đã redaction.

## Phiên bản code đề xuất

Ví dụ này giữ synchronous endpoint cho export nhỏ. `IAuthorizationService`/tenant membership phải thực sự kiểm tra quyền trên tenant resource; sort chỉ đi qua whitelist.

```csharp
[ApiController]
[Route("api/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly SqlConnection _connection;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        SqlConnection connection,
        ITenantAccessService tenantAccess,
        ILogger<AuditController> logger)
    {
        _connection = connection;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [HttpGet("export")]
    public async Task<IActionResult> Export(
        Guid tenantId,
        DateTimeOffset from,
        DateTimeOffset to,
        AuditSort sort = AuditSort.CreatedAtDesc,
        CancellationToken cancellationToken = default)
    {
        if (!await _tenantAccess.CanExportAuditAsync(
                User, tenantId, cancellationToken))
            return Forbid();

        if (from > to || to - from > TimeSpan.FromDays(31))
            return BadRequest("Invalid export time range.");

        var orderBy = sort switch
        {
            AuditSort.CreatedAtAsc => "CreatedAt ASC",
            AuditSort.CreatedAtDesc => "CreatedAt DESC",
            _ => "CreatedAt DESC"
        };

        var sql = $@"
            SELECT TOP (10000)
                Id, TenantId, UserEmail, IpAddress, Action, CreatedAt
            FROM AuditEvents
            WHERE TenantId = @TenantId
              AND CreatedAt >= @From
              AND CreatedAt < @To
            ORDER BY {orderBy};";

        await _connection.OpenAsync(cancellationToken);

        await using var command = new SqlCommand(sql, _connection)
        {
            CommandTimeout = 30
        };

        command.Parameters.Add("@TenantId", SqlDbType.UniqueIdentifier).Value = tenantId;
        command.Parameters.Add("@From", SqlDbType.DateTimeOffset).Value = from;
        command.Parameters.Add("@To", SqlDbType.DateTimeOffset).Value = to;

        await using var reader = await command.ExecuteReaderAsync(cancellationToken);

        var rows = new List<AuditExportRow>();
        while (await reader.ReadAsync(cancellationToken))
        {
            rows.Add(new AuditExportRow(
                reader.GetGuid(0),
                reader.GetGuid(1),
                reader.GetString(2),
                reader.GetString(3),
                reader.GetString(4),
                reader.GetDateTimeOffset(5)));
        }

        _logger.LogInformation(
            "Audit export completed. Actor={Actor} TenantId={TenantId} From={From} To={To} RowCount={RowCount}",
            User.FindFirst("sub")?.Value,
            tenantId,
            from,
            to,
            rows.Count);

        return Ok(rows);
    }
}

public enum AuditSort
{
    CreatedAtAsc,
    CreatedAtDesc
}

public sealed record AuditExportRow(
    Guid Id,
    Guid TenantId,
    string UserEmail,
    string IpAddress,
    string Action,
    DateTimeOffset CreatedAt);
```

`TOP (10000)` chỉ là ví dụ về server-side cap, không phải con số universal. Production cần chọn limit theo SLO và business requirement. Nếu audit table rất lớn, cần index phù hợp với tenant/time access pattern, ví dụ xem xét composite index bắt đầu bằng `TenantId, CreatedAt`, sau khi kiểm chứng execution plan và workload thực tế.

## Trade-offs

Synchronous export đơn giản và phù hợp dataset nhỏ nhưng giữ HTTP request/database resources trong thời gian export. Với export lớn hoặc compliance report dài hạn, background job + object storage thường dễ kiểm soát timeout và memory hơn, nhưng cần authorization khi tạo lẫn khi download, expiry, cleanup và audit. Row cap bảo vệ hệ thống nhưng phải báo rõ truncation hoặc từ chối request; không được âm thầm trả dữ liệu thiếu mà người dùng tưởng là đầy đủ.

## Cách kiểm thử

1. **Authorization integration test:** User tenant A gửi `tenantId` của tenant B phải nhận 403 và query dữ liệu không được thực hiện.
2. **Injection/security test:** Gửi malicious/invalid sort input; endpoint chỉ chấp nhận enum/whitelist và không thay đổi SQL structure.
3. **Boundary test:** `from > to`, range vượt policy, thời điểm biên và timezone được xử lý nhất quán.
4. **Load test:** Nhiều export đồng thời ở maximum allowed range; đo DB CPU/reads, API memory, GC và latency.
5. **Cancellation/failure test:** Client disconnect hoặc database timeout; query được cancel/terminate hợp lý và log không chứa exported PII.

## Quan sát trong production

Log actor subject, tenant ID, export ID, range, row count, duration và outcome. Theo dõi export request rate, authorization denials, query duration, rows scanned/returned, timeout/cancellation, DB CPU/IO và API memory. Trace authorization check và SQL call nhưng không attach raw audit rows. Alert khi export latency/error rate hoặc denied cross-tenant attempts tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc export hàng chục triệu rows, bạn thiết kế asynchronous export flow như thế nào?
2. Tenant ID trong JWT claim có đủ để authorization không, hay vẫn cần kiểm tra membership/state từ server-side source?
3. Bạn xác định composite index cho query này bằng dữ liệu nào thay vì chỉ nhìn vào câu SQL?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge cùng nhấn mạnh rằng production correctness nằm ở **boundary**. Với background jobs, boundary là giữa database state, retry và external side effect: retry không tạo exactly-once outcome, nên idempotency, atomic claim, explicit state và reconciliation phải được thiết kế cùng nhau. Với API multi-tenant, boundary là giữa authenticated identity và resource authorization: `[Authorize]` không tự chứng minh caller được phép đọc một `tenantId` cụ thể. SQL parameterization, whitelist cho dynamic identifiers, data-volume limits và privacy-aware logging đều là một phần của security design chứ không chỉ là coding style.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng với idempotency và failure recovery.
- Phân biệt authentication với resource-level authorization.
- Không cố dùng local transaction để che giấu distributed side effects.
- Parameterize values; whitelist SQL structure do client lựa chọn.
- Treat observability as part of the design nhưng không biến logs thành kho chứa sensitive payload.
