# Code Review Challenge 1 — Azure Function xử lý poison message nhưng retry đang khuếch đại sự cố

**Chủ đề:** C#/.NET, Azure Functions, retry, poison work, EF Core, external API, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–12 vấn đề quan trọng

## Bối cảnh

Một Azure Function xử lý yêu cầu đồng bộ hồ sơ khách hàng. Mỗi message chứa `CustomerId`; Function đọc SQL Server bằng EF Core, gọi CRM bên thứ ba rồi đánh dấu `SyncedAt`. Bình thường throughput ổn định. Khi CRM trả 429/503 trong khoảng 20 phút, số lần invocation tăng mạnh, SQL connections tăng, cùng `CustomerId` xuất hiện nhiều lần trong logs và một nhóm message cứ thất bại lặp lại.

Team muốn “retry mạnh hơn” bằng cách tăng số lần retry và chạy nhiều message song song. Chưa có bằng chứng rằng mọi lỗi đều transient, chưa biết trigger retry/dead-letter semantics đã cấu hình thế nào, và CRM có thể có hoặc không hỗ trợ idempotency key.

## Đoạn code cần review

```csharp
public sealed class SyncCustomerFunction
{
    private readonly AppDbContext _db;
    private readonly HttpClient _crm;
    private readonly ILogger<SyncCustomerFunction> _logger;

    public SyncCustomerFunction(
        AppDbContext db,
        HttpClient crm,
        ILogger<SyncCustomerFunction> logger)
    {
        _db = db;
        _crm = crm;
        _logger = logger;
    }

    [Function("SyncCustomer")]
    public async Task Run(
        [ServiceBusTrigger("customer-sync", Connection = "ServiceBus")]
        string body)
    {
        var message = JsonSerializer.Deserialize<SyncCustomerMessage>(body)!;

        for (var attempt = 1; attempt <= 5; attempt++)
        {
            try
            {
                var customer = await _db.Customers
                    .SingleAsync(x => x.Id == message.CustomerId);

                var response = await _crm.PostAsJsonAsync(
                    "/api/customers/sync",
                    new
                    {
                        customer.Id,
                        customer.Email,
                        customer.Name
                    });

                if (!response.IsSuccessStatusCode)
                {
                    _logger.LogWarning(
                        "CRM failed for {CustomerId}: {Body}",
                        customer.Id,
                        await response.Content.ReadAsStringAsync());

                    await Task.Delay(TimeSpan.FromSeconds(2));
                    continue;
                }

                customer.SyncedAt = DateTime.UtcNow;
                await _db.SaveChangesAsync();
                return;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Sync failed for customer {CustomerId}",
                    message.CustomerId);

                await Task.Delay(TimeSpan.FromSeconds(2));
            }
        }

        throw new InvalidOperationException(
            $"Unable to sync customer {message.CustomerId}");
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi về correctness, retry, resource lifetime, data consistency và security/observability.
2. Giải thích production impact khi CRM degraded, nhiều Function instances cùng scale và cùng logical work được nhìn thấy lại.
3. Phân loại vấn đề theo severity và ưu tiên remediation.
4. Đề xuất design sửa nhưng không giả định CRM hỗ trợ idempotency nếu chưa xác minh.
5. Nêu test cho transient failure, permanent failure, retry exhaustion, duplicate logical work và cancellation.
6. Nêu telemetry cần có để phân biệt downstream degradation, poison work và capacity issue.

## Câu hỏi gợi mở

1. Retry ở application loop tương tác thế nào với retry/redelivery của trigger?
2. Điều gì xảy ra nếu CRM đã thực hiện side effect nhưng response bị mất trước khi Function nhận được?
3. HTTP 400, 401, 429 và 503 có nên cùng một retry policy không?
4. `Task.Delay` và EF/HTTP calls hiện có phản ứng thế nào khi invocation bị hủy?
5. Bạn cần bằng chứng nào trước khi tăng concurrency?

## Kết quả code review tham khảo

### [Critical] — External side effect không có chiến lược idempotency rõ ràng

**Vấn đề:** CRM `POST` có thể thành công nhưng Function không nhận được response, sau đó retry cùng operation.

**Tại sao xảy ra:** Network failure tạo trạng thái “unknown outcome”. Retry cùng payload không đảm bảo side effect chỉ xảy ra một lần.

**Ảnh hưởng production:** Duplicate customer operation, audit sai hoặc side effect lặp tùy semantics của CRM.

**Cách sửa:** Xác minh CRM có hỗ trợ idempotency key/stable operation ID hay lookup/update semantics không. Nếu có, truyền stable key xuyên suốt retries. Nếu không, cần thiết kế reconciliation/state machine phù hợp với business semantics; không tuyên bố có thể đạt exactly-once chỉ bằng retry.

### [High] — Retry amplification giữa loop nội bộ và trigger delivery

**Vấn đề:** Code retry 5 lần rồi throw; trigger/platform có thể tiếp tục redeliver theo cấu hình thực tế.

**Tại sao xảy ra:** Hai tầng retry độc lập nhân số lần gọi CRM/SQL.

**Ảnh hưởng production:** Khi CRM degraded, request storm, queue backlog, SQL/HTTP pressure và recovery chậm hơn.

**Cách sửa:** Xác định một retry budget rõ ràng. Phân biệt retry nhanh cho transient lỗi phù hợp với redelivery/dead-letter policy của messaging layer. Đo downstream capacity trước khi tăng concurrency.

### [High] — Retry mọi lỗi theo cùng một policy

**Vấn đề:** Non-success HTTP status và mọi `Exception` gần như đều retry giống nhau.

**Tại sao xảy ra:** Không phân loại transient, throttling, authentication, validation, malformed message hay permanent business failure.

**Ảnh hưởng production:** Poison work tiêu thụ compute và dependency capacity vô ích; lỗi credential có thể tạo storm.

**Cách sửa:** Phân loại lỗi. 429 cần tôn trọng server guidance khi có; 5xx/network failures có thể retry với bounded backoff/jitter; 400-class permanent errors thường cần xử lý khác; auth failure cần alert/config remediation thay vì blind retry.

### [High] — Không propagate cancellation

**Vấn đề:** EF Core, HTTP và `Task.Delay` không nhận cancellation token.

**Tại sao xảy ra:** Invocation shutdown/cancellation không được truyền xuống dependency work.

**Ảnh hưởng production:** Work tiếp tục không cần thiết khi host muốn dừng; shutdown kéo dài và resource pressure tăng.

**Cách sửa:** Nhận cancellation token theo programming model đang dùng và truyền tới EF, HTTP và delay khi API hỗ trợ.

### [High] — `DbContext` state sống xuyên nhiều attempt

**Vấn đề:** Cùng context được dùng qua retry loop; entity/tracking state của failed attempt có thể còn trong context.

**Tại sao xảy ra:** Retry boundary không đồng nhất với unit-of-work boundary.

**Ảnh hưởng production:** State khó reasoning, đặc biệt khi lỗi DB/SaveChanges hoặc entity bị mutate qua attempts.

**Cách sửa:** Thiết kế unit of work ngắn và rõ. Tùy Functions hosting model/DI setup, tạo context phù hợp cho từng logical DB operation/attempt thay vì dựa vào một context stateful xuyên retry một cách vô thức.

### [Medium] — Fixed-delay retry gây đồng bộ retry storm

**Vấn đề:** Mọi attempt chờ đúng 2 giây.

**Tại sao xảy ra:** Không có exponential backoff/jitter hoặc downstream retry guidance.

**Ảnh hưởng production:** Nhiều instances retry gần cùng thời điểm, tạo burst khi dependency đang hồi phục.

**Cách sửa:** Dùng bounded backoff + jitter cho lỗi retryable và tôn trọng `Retry-After` khi phù hợp.

### [Medium] — Logging response body có thể làm lộ dữ liệu

**Vấn đề:** Toàn bộ CRM response body được ghi vào warning log.

**Tại sao xảy ra:** Không có data classification/redaction.

**Ảnh hưởng production:** PII/token/internal detail có thể đi vào centralized logs.

**Cách sửa:** Log status, dependency correlation ID, error category và sanitized metadata; redact/truncate body theo policy.

### [Medium] — Deserialization/validation không tạo failure classification rõ ràng

**Vấn đề:** `Deserialize(...)!` giả định payload hợp lệ.

**Tại sao xảy ra:** Null/malformed/semantically invalid message rơi vào generic failure path.

**Ảnh hưởng production:** Poison message có thể retry nhiều lần mà không có khả năng tự hồi phục.

**Cách sửa:** Validate message contract sớm; classify permanent invalid messages và route theo dead-letter/quarantine policy được hỗ trợ bởi trigger architecture.

## Phiên bản đề xuất

```csharp
public sealed class SyncCustomerFunction
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly HttpClient _crm;
    private readonly ILogger<SyncCustomerFunction> _logger;

    public SyncCustomerFunction(
        IDbContextFactory<AppDbContext> dbFactory,
        HttpClient crm,
        ILogger<SyncCustomerFunction> logger)
    {
        _dbFactory = dbFactory;
        _crm = crm;
        _logger = logger;
    }

    [Function("SyncCustomer")]
    public async Task Run(
        [ServiceBusTrigger("customer-sync", Connection = "ServiceBus")]
        string body,
        CancellationToken cancellationToken)
    {
        var message = JsonSerializer.Deserialize<SyncCustomerMessage>(body)
            ?? throw new InvalidDataException("Invalid message payload.");

        await using var db =
            await _dbFactory.CreateDbContextAsync(cancellationToken);

        var customer = await db.Customers
            .AsNoTracking()
            .SingleAsync(x => x.Id == message.CustomerId, cancellationToken);

        using var request = new HttpRequestMessage(HttpMethod.Post, "/api/customers/sync")
        {
            Content = JsonContent.Create(new
            {
                customer.Id,
                customer.Email,
                customer.Name
            })
        };

        // Chỉ thêm stable idempotency key nếu CRM contract thực sự hỗ trợ.
        request.Headers.TryAddWithoutValidation(
            "X-Operation-Id", message.OperationId);

        using var response = await _crm.SendAsync(request, cancellationToken);

        if (!response.IsSuccessStatusCode)
        {
            throw new CrmSyncException(
                response.StatusCode,
                message.CustomerId);
        }

        await using var updateDb =
            await _dbFactory.CreateDbContextAsync(cancellationToken);

        var entity = await updateDb.Customers
            .SingleAsync(x => x.Id == message.CustomerId, cancellationToken);

        entity.SyncedAt = DateTime.UtcNow;
        await updateDb.SaveChangesAsync(cancellationToken);
    }
}
```

Đây chỉ là boundary refactor, không phải retry policy hoàn chỉnh. Retry classification nên nằm ở policy/trigger architecture phù hợp và phải dựa trên verified CRM semantics. Nếu `X-Operation-Id` không được CRM hỗ trợ thì header đó không tạo idempotency; cần bỏ hoặc thay bằng cơ chế thực sự được provider hỗ trợ.

## Giải thích thiết kế sau khi sửa

Function làm một attempt rõ ràng thay vì tự lồng một retry loop mù. DB context có lifetime ngắn. Cancellation được propagate. Error type giữ HTTP status để retry/dead-letter policy phía ngoài có thể phân loại. External idempotency chỉ được coi là bảo đảm khi CRM contract xác nhận.

Nếu local state cần theo dõi workflow, có thể lưu operation state/idempotency record với unique constraint và xây reconciliation cho trạng thái “CRM outcome unknown”. Outbox/Inbox chỉ nên thêm khi failure model và business invariant biện minh cho complexity đó.

## Trade-offs

- Platform-level retry đơn giản hóa code nhưng cần hiểu trigger semantics/configuration thực tế.
- Retry nhanh cải thiện transient recovery nhưng dễ khuếch đại dependency outage.
- Idempotency store tăng DB write/storage nhưng tạo durable evidence cho duplicate logical work.
- Tăng concurrency có thể giảm backlog khi downstream khỏe; khi downstream throttling, nó có thể làm sự cố nặng hơn.

## Cách kiểm thử

1. CRM 503 rồi phục hồi: xác minh retry budget và backoff mong muốn.
2. CRM 400/401: xác minh không blind-retry như transient failure.
3. CRM thực hiện side effect rồi connection reset: xác minh idempotency/reconciliation behavior.
4. Malformed/poison message: xác minh không lặp vô hạn và có quarantine/DLQ path phù hợp.
5. Cancellation giữa HTTP/DB work: xác minh invocation dừng sạch.

## Quan sát trong production

Theo dõi invocation count theo logical `OperationId`, success/failure category, retry count, message delivery count khi có, queue age/backlog, dead-letter count/reason, CRM latency/status/429 rate, SQL dependency duration, connection pool pressure và Function instance/concurrency. Structured logs cần correlation giữa message, operation, CRM request và DB update nhưng không ghi PII/secrets không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Nếu CRM không hỗ trợ idempotency và không có read API để reconcile, bạn sẽ thay đổi business workflow thế nào?
2. Khi backlog lớn nhưng CRM đang trả 429, vì sao tăng Function concurrency có thể làm recovery time tệ hơn?
3. Bạn sẽ xác định retry budget giữa HTTP client, Function runtime và Service Bus delivery như thế nào?

# Code Review Challenge 2 — Playwright E2E pass local nhưng flaky khi chạy parallel trên CI

**Chủ đề:** Playwright, E2E testing, CI, shared test data, parallelism, test isolation, authentication, diagnostics  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–10 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core + Vue.js portal có Playwright suite chạy ổn trên laptop nhưng CI thường fail ngẫu nhiên 8–15%. Team chạy 6 workers để giảm pipeline time. Các tests dùng chung staging-like database và cùng một tài khoản `qa@example.test`. Khi fail, developer thường rerun pipeline và đa số lần thứ hai sẽ pass.

Một engineer đề xuất tăng tất cả timeout lên 60 giây. Review code dưới đây và đưa ra chiến lược làm suite deterministic hơn mà không biến toàn bộ pipeline thành serial.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const email = 'qa@example.test';
const password = process.env.E2E_PASSWORD!;

test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.fill('#email', email);
  await page.fill('#password', password);
  await page.click('button[type=submit]');
  await page.waitForTimeout(2000);

test('user can update profile', async ({ page }) => {
  await page.goto('/profile');

  await page.fill('#displayName', 'QA User');
  await page.click('#save');
  await page.waitForTimeout(3000);

  const text = await page.locator('.toast').textContent();
  expect(text).toContain('Saved');
});

test('user can disable notifications', async ({ page }) => {
  await page.goto('/settings');

  const checkbox = page.locator('#notifications');
  if (await checkbox.isChecked()) {
    await checkbox.click();
  }

  await page.click('#save-settings');
  await page.waitForTimeout(3000);

  expect(await checkbox.isChecked()).toBe(false);
});

test('profile shows latest display name', async ({ page }) => {
  await page.goto('/profile');
  expect(await page.locator('#displayName').inputValue())
    .toBe('QA User');
});
```

4. Đề xuất test-data/auth architecture cho phép parallelism có kiểm soát.

## Kết quả code review tham khảo

### [Critical] — Tests chia sẻ mutable user state giữa parallel workers

**Vấn đề:** Tất cả workers dùng `qa@example.test` và cùng sửa profile/settings.

**Tại sao xảy ra:** Test data không được isolate theo worker/test.

**Ảnh hưởng production:** Race làm assertion phụ thuộc timing; một test có thể phá precondition của test khác. CI đỏ ngẫu nhiên và có thể che regression thật.

**Cách sửa:** Provision account/data riêng theo worker/test hoặc dùng deterministic fixture tạo namespace riêng. Cleanup phải an toàn và không xóa data của worker khác.

### [High] — Test phụ thuộc thứ tự chạy

**Vấn đề:** `profile shows latest display name` kỳ vọng `QA User` nhưng chính test không tạo state đó.

**Tại sao xảy ra:** Hidden dependency vào `user can update profile`.

**Ảnh hưởng production:** Chạy riêng/reorder/shard sẽ fail hoặc cho kết quả khác nhau.

**Cách sửa:** Mỗi test tự thiết lập precondition qua fixture/API/setup helper hoặc gộp thành một test nếu thật sự đang kiểm tra một user journey duy nhất.

### [High] — Fixed sleeps thay cho condition-based synchronization

**Vấn đề:** `waitForTimeout(2000/3000)` giả định hệ thống hoàn tất trong khoảng cố định.

**Tại sao xảy ra:** CI latency biến động; sleep có thể vừa quá ngắn vừa lãng phí khi hệ thống nhanh.

**Ảnh hưởng production:** Flaky + pipeline chậm.

**Cách sửa:** Chờ URL/navigation, visible authenticated state, response phù hợp hoặc web-first assertion trên trạng thái UI cuối cùng.

### [High] — Login qua UI ở mọi test tạo coupling và chi phí không cần thiết

**Vấn đề:** Mỗi test phụ thuộc login UI/network dù mục tiêu chính không phải authentication.

**Tại sao xảy ra:** Không tái sử dụng authenticated state/fixture theo boundary phù hợp.

**Ảnh hưởng production:** Suite chậm và nhiều failure points; login outage làm nhiều tests unrelated cùng đỏ.

**Cách sửa:** Giữ một số auth E2E tests riêng; với phần còn lại dùng authenticated storage state hoặc setup API theo security model của hệ thống, đảm bảo account isolation.

### [Medium] — Assertion pattern bỏ lỡ Playwright auto-waiting

**Vấn đề:** Code lấy `textContent()`/`inputValue()` rồi assert primitive value.

**Tại sao xảy ra:** Không tận dụng web-first assertions chờ trạng thái DOM mong muốn.

**Ảnh hưởng production:** Race nhỏ giữa render/save và assertion làm test flaky.

**Cách sửa:** Dùng `await expect(locator).toHaveText(...)`, `toHaveValue(...)`, `toBeChecked()`/`not.toBeChecked()` khi phù hợp.

### [Medium] — Settings test không thiết lập precondition rõ ràng

**Vấn đề:** Test chỉ click nếu checkbox đang checked, nên path thực thi thay đổi theo state còn sót lại.

**Tại sao xảy ra:** Test vừa thích nghi với shared state vừa cố assert kết quả.

**Ảnh hưởng production:** Có thể pass mà không kiểm tra hành động disable/save thực sự.

**Cách sửa:** Fixture đặt notifications=true trước test; sau đó UI thực hiện disable và verify persisted state, có thể reload hoặc kiểm tra API/UI sau navigation.

### [Medium] — Thiếu failure artifacts và correlation

**Vấn đề:** Rerun được dùng như diagnostics.

**Tại sao xảy ra:** Không giữ trace/screenshot/video/network/server correlation đủ dùng.

**Ảnh hưởng production:** Flake bị bình thường hóa; regression thật có thể bị bỏ qua.

**Cách sửa:** Capture Playwright trace on first retry hoặc policy phù hợp, screenshot/video khi fail, test ID/correlation ID và server logs cho failed window.

## Phiên bản đề xuất

```ts
import { test, expect } from '@playwright/test';

// Giả định fixture `isolatedUser` provision một user riêng cho worker/test
// và `authenticatedPage` đã login theo cách phù hợp với hệ thống.
test('user can update profile', async ({ authenticatedPage: page, isolatedUser }) => {
  await page.goto('/profile');

  const displayName = `QA-${isolatedUser.id}`;
  await page.getByLabel('Display name').fill(displayName);

  const saveResponse = page.waitForResponse(response =>
    response.url().includes('/api/profile') &&
    response.request().method() === 'PUT'
  );

  await page.getByRole('button', { name: 'Save' }).click();

  const response = await saveResponse;
  expect(response.ok()).toBeTruthy();
  await expect(page.getByRole('status')).toContainText('Saved');

  await page.reload();
  await expect(page.getByLabel('Display name')).toHaveValue(displayName);
});

test('user can disable notifications', async ({ authenticatedPage: page, isolatedUser }) => {
  // Setup API/fixture bảo đảm notifications=true cho isolatedUser trước bước UI.
  await page.goto('/settings');

  const checkbox = page.getByLabel('Notifications');
  await expect(checkbox).toBeChecked();

  await checkbox.uncheck();
  await page.getByRole('button', { name: 'Save settings' }).click();

  await expect(page.getByRole('status')).toContainText('Saved');
  await page.reload();
  await expect(checkbox).not.toBeChecked();
});
```

Fixture implementation phải phù hợp hệ thống thực tế. Mục tiêu là ownership của test data rõ ràng, không phải copy một abstraction cụ thể.

## Giải thích thiết kế sau khi sửa

Mỗi test tạo precondition của chính nó và không dựa vào execution order. Synchronization dựa trên observable condition thay vì sleep. Authentication được tách khỏi business-flow tests để giảm thời gian và failure surface, nhưng auth vẫn có suite riêng. Data isolation cho phép giữ parallelism thay vì giải quyết flake bằng cách ép toàn bộ suite chạy serial.

Một số business rules nên được cover bằng unit/integration/API tests nhanh hơn; E2E chỉ giữ các critical user journeys cần browser integration thật.

## Trade-offs

- User-per-test isolation tăng setup cost nhưng tăng determinism và khả năng parallelize.
- User-per-worker rẻ hơn nhưng cần reset state giữa tests trong cùng worker.
- Storage state giảm login cost nhưng có lifecycle/expiration/security considerations.
- Trace/video tăng artifact size và CI cost; có thể capture theo failure/retry policy thay vì mọi test.
- Serial execution dễ giảm race tạm thời nhưng che shared-state design flaw và làm pipeline chậm.

## Cách kiểm thử

1. Chạy từng test riêng và randomize/reorder để xác minh không có hidden dependency.
2. Chạy suite với 1, 3 và 6 workers nhiều vòng để đo flake rate.
3. Inject network latency cho save API và xác minh không cần fixed sleep.
4. Chạy hai workers cố tình thao tác song song và xác minh data isolation.
5. Làm save API trả 500/timeout để xác minh UI error state và artifacts đủ chẩn đoán.

## Quan sát trong production

Trong CI, lưu test duration, retry count, flake rate theo test, worker ID, trace/screenshot/video khi fail, browser console/network errors và correlation ID nối tới ASP.NET Core logs/Application Insights của environment test. Theo dõi top flaky tests theo rolling window; retry chỉ là tín hiệu để phân loại flake, không phải cơ chế biến failure thành success rồi bỏ qua.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn user-per-worker thay vì user-per-test?
2. Nếu test chỉ fail khi 6 workers nhưng pass với 1 worker, bạn sẽ chứng minh đó là shared test state, app concurrency bug hay environment capacity issue như thế nào?
3. Những behavior nào nên chuyển từ Playwright E2E xuống integration/API tests để giảm thời gian mà không mất confidence?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry phải có budget và failure classification; nhiều tầng retry có thể khuếch đại outage.
- External side effect cần reasoning về unknown outcome và idempotency thay vì giả định exactly-once.
- Test parallel chỉ đáng tin khi test data và mutable state có ownership rõ ràng.
- Condition-based synchronization tốt hơn fixed sleep trong E2E.
- Observability phải giúp phân biệt product bug, dependency failure, poison work và test flake.

## Mẫu tư duy cần nhớ

- **Failure → classify → retry budget → idempotency → dead-letter/reconcile.**
- **Test precondition phải do chính test/fixture sở hữu.**
- **Không dùng timeout lớn để chữa race condition.**
- **Scale/concurrency chỉ tăng sau khi biết bottleneck và downstream capacity.**
- **Telemetry phải chứng minh hoặc bác bỏ hypothesis.**
