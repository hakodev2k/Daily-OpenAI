# Câu 1 — Vì sao tạo `HttpClient` mới liên tục có thể gây timeout dù downstream vẫn khỏe?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** C#, .NET, `HttpClient`, connection pooling, TCP, DNS, `IHttpClientFactory`, timeout, cancellation, resilience, observability

## Bối cảnh

Một ASP.NET Core .NET 8 API gọi sang một third-party pricing service. Code hiện tại được viết đơn giản như sau:

```csharp
public async Task<PriceResponse?> GetPriceAsync(
    string sku,
    CancellationToken cancellationToken)
{
    using var client = new HttpClient();
    client.Timeout = TimeSpan.FromSeconds(10);

    var response = await client.GetAsync(
        $"https://pricing.example.com/api/prices/{sku}",
        cancellationToken);

    response.EnsureSuccessStatusCode();

    return await response.Content.ReadFromJsonAsync<PriceResponse>(
        cancellationToken: cancellationToken);
}
```

Production chạy nhiều App Service instances. Khi traffic tăng mạnh:

- một số request outbound bị timeout;
- application log có `TaskCanceledException` và đôi lúc socket/network errors;
- CPU của application không cao;
- pricing service cho biết latency p95 của họ vẫn ổn;
- retry ở application làm tổng số outbound requests tăng mạnh hơn;
- developer đề xuất tăng `HttpClient.Timeout` lên 60 giây;
- developer khác đề xuất tạo một static `HttpClient` duy nhất và dùng mãi mãi;
- team đang dùng DNS-based endpoint phía sau load balancer và IP có thể thay đổi theo lifecycle của provider.

Chưa biết chắc:

- outbound connection count hiện tại;
- `TIME_WAIT`/socket usage trên instance;
- DNS TTL và connection lifetime;
- retry policy đang retry lỗi nào;
- timeout hiện tại bao gồm những stage nào;
- downstream có rate limit hay không;
- request có bị cancel khi upstream user disconnect không.

## Câu hỏi chính

Hãy giải thích ở mức runtime/network lifecycle vì sao việc tạo/dispose `HttpClient` cho mỗi call có thể dẫn tới connection churn, socket pressure hoặc latency bất thường dù downstream service không chậm, và bạn sẽ thiết kế lại outbound HTTP client như thế nào để cân bằng connection reuse, DNS refresh, timeout, cancellation và retry safety.

## Câu hỏi làm rõ nên cân nhắc

1. Pricing API là idempotent read-only hay có endpoint mutation dùng cùng client?
2. Có bao nhiêu outbound requests/second trên mỗi instance và concurrent requests peak bao nhiêu?
3. Provider có rate-limit, keep-alive, DNS failover hoặc IP rotation policy không?
4. Retry hiện tại retry timeout, 429, 5xx và network error giống nhau hay có phân loại?
5. `CancellationToken` từ incoming request có được propagate tới mọi downstream call không?

## Gợi ý tư duy

### Gợi ý 1

`HttpClient` chỉ là lớp API bề mặt; connection pooling thực sự nằm ở handler bên dưới. Hãy nghĩ về handler lifetime chứ không chỉ object lifetime.

### Gợi ý 2

Reuse connection quá ít gây churn, nhưng giữ connection vô hạn cũng có thể làm DNS changes không được phản ánh đủ nhanh.

### Gợi ý 3

Timeout, retry và cancellation phải được thiết kế cùng nhau. Retry một request side-effecting không idempotent có thể nguy hiểm hơn timeout ban đầu.

## Cấu trúc trả lời đề xuất

1. Xác định request type và traffic profile.
2. Giải thích `HttpClient`/handler/connection pool relationship.
3. Phân tích connection churn và socket lifecycle.
4. Phân tích DNS change với long-lived connections.
5. Đề xuất `IHttpClientFactory` hoặc long-lived client + handler policy phù hợp.
6. Thiết kế timeout theo dependency SLO và end-to-end budget.
7. Propagate `CancellationToken`.
8. Thiết kế bounded retry theo lỗi/idempotency.
9. Đề xuất telemetry để chứng minh improvement.
10. Test failure/network/DNS scenarios.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra tạo/dispose `HttpClient` liên tục có thể làm connection reuse kém và tạo connection churn.
- Hiểu connection pooling thuộc `SocketsHttpHandler`/handler layer.
- Không chỉ tăng timeout để che triệu chứng.
- Không kết luận static `HttpClient` vô hạn là luôn đúng nếu DNS endpoint có thay đổi.
- Dùng `IHttpClientFactory` hoặc quản lý handler lifetime/`PooledConnectionLifetime` phù hợp.
- Propagate cancellation từ incoming request khi downstream work không còn giá trị.
- Retry phải bounded và chỉ áp dụng lỗi phù hợp.
- Không retry mù mutation không idempotent.

### Điểm cộng

- Phân biệt connect timeout, request timeout và overall caller budget.
- Nêu nguy cơ retry amplification khi downstream đang degraded.
- Xử lý 429 theo `Retry-After` nếu provider contract hỗ trợ.
- Dùng named/typed client để cấu hình base address, headers, auth, resilience và telemetry theo dependency.
- Theo dõi connection count, outbound duration, retry count và dependency error distribution.

### Senior+

- Thiết kế per-dependency timeout budget dựa trên upstream SLA thay vì một timeout global.
- Có circuit-breaking/load-shedding khi downstream failure kéo dài, nhưng không dùng circuit breaker như “magic fix”.
- Phân biệt request cancellation do caller với dependency timeout để telemetry không gộp tất cả thành một loại lỗi.
- Nêu trade-off của connection lifetime quá ngắn: nhiều handshakes hơn; quá dài: DNS/IP freshness chậm hơn.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng việc phân biệt `HttpClient` object với connection pool. Trong modern .NET, `HttpClient` dùng một handler, thường là `SocketsHttpHandler`, để quản lý connection pool. Nếu mỗi application call tạo một `HttpClient` cùng một handler mới rồi dispose ngay, application có thể liên tục mở connection mới thay vì tái sử dụng pooled connections hiệu quả.

Ở tải cao, connection churn tạo thêm TCP/TLS handshake, ephemeral-port pressure và nhiều socket ở trạng thái lifecycle như `TIME_WAIT`. Khi đó application có thể gặp network/socket failures hoặc latency tăng dù downstream API vẫn phản hồi nhanh khi request thực sự tới được nó.

Tôi sẽ không sửa bằng cách đơn giản tăng timeout lên 60 giây. Nếu root cause là connection pressure hoặc retry amplification, timeout dài hơn chỉ giữ tài nguyên lâu hơn và làm queue/concurrency phình ra.

Một hướng chuẩn trong ASP.NET Core là dùng `IHttpClientFactory` với typed client:

```csharp
builder.Services.AddHttpClient<PricingClient>(client =>
{
    client.BaseAddress = new Uri("https://pricing.example.com/");
    client.Timeout = TimeSpan.FromSeconds(5);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5)
});
```

```csharp
public sealed class PricingClient
{
    private readonly HttpClient _httpClient;

    public PricingClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task<PriceResponse?> GetPriceAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        using var response = await _httpClient.GetAsync(
            $"api/prices/{Uri.EscapeDataString(sku)}",
            cancellationToken);

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadFromJsonAsync<PriceResponse>(
            cancellationToken: cancellationToken);
    }
}
```

Con số `5 minutes` ở ví dụ không phải recommendation cố định. Tôi sẽ dựa trên DNS/provider behavior, operational requirements và measurement. Ý chính là handler/connection reuse phải đủ lâu để giảm churn nhưng connection lifetime có thể được giới hạn để DNS/IP changes được quan sát định kỳ.

Static `HttpClient` cũng có thể là thiết kế hợp lệ nếu handler được cấu hình đúng, đặc biệt `PooledConnectionLifetime` phù hợp. Vấn đề không phải “static luôn sai” hay “factory luôn đúng”; điều cần quản lý là handler lifecycle, DNS freshness và cấu hình dependency-specific.

Timeout cần nằm trong end-to-end budget. Nếu incoming API SLO là 2 giây, một downstream timeout 10–60 giây có thể vô nghĩa. Tôi muốn biết:

- caller timeout;
- connect duration;
- downstream latency distribution;
- retry count;
- remaining request budget.

Nếu pricing call là một trong nhiều dependencies, tổng timeout của chúng không được vượt end-to-end budget theo cách uncontrolled.

Cancellation cần propagate từ `HttpContext.RequestAborted`/application token xuống HTTP call. Nếu user disconnect và kết quả không còn giá trị, nên dừng downstream work khi có thể. Tuy nhiên cancellation từ caller và timeout do dependency cần được phân biệt trong logs/metrics để investigation không nhầm.

Retry chỉ áp dụng cho transient failures phù hợp. Với GET pricing, retry có thể an toàn hơn về business semantics, nhưng vẫn cần bounded attempts + backoff/jitter và cần tránh retry storm. Với POST tạo payment/order, phải có idempotency contract trước khi retry.

Nếu downstream trả 429, cần tôn trọng provider policy, đặc biệt `Retry-After` khi có. Nếu downstream degraded kéo dài, có thể dùng circuit breaker/load shedding để bảo vệ application, nhưng chỉ sau khi xác định expected fallback behavior.

Evidence tôi muốn thu thập:

- outbound request duration p50/p95/p99;
- DNS/connect/TLS timing nếu tooling hỗ trợ;
- active connection count;
- failed connection/socket errors;
- retry attempts/request;
- `TIME_WAIT`/port pressure ở environment phù hợp;
- downstream 429/5xx;
- caller cancellation count;
- App Service SNAT/outbound networking metrics nếu topology liên quan.

Test:

- high concurrency với connection reuse;
- provider IP/DNS change;
- connection reset;
- 429 + `Retry-After`;
- slow downstream;
- caller cancellation;
- retry storm prevention.

Reference implementation phải được benchmark với production-like concurrency trước/sau. Thành công không phải “không còn exception local” mà là connection churn giảm, retry giảm và p95/p99 ổn định.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách `HttpClient` khỏi handler. Nếu mỗi call tạo/dispose client kèm handler mới, connection pool không được reuse tốt, dẫn tới nhiều TCP/TLS connections, socket/ephemeral-port pressure và latency tăng dù downstream vẫn khỏe. Em sẽ đo connection count, outbound latency, retries và network errors để chứng minh.

Em dùng typed client qua `IHttpClientFactory` hoặc long-lived `HttpClient` với `SocketsHttpHandler` được cấu hình `PooledConnectionLifetime` để vừa reuse connection vừa refresh DNS định kỳ. Timeout phải nằm trong end-to-end budget, cancellation được propagate từ request, và retry phải bounded theo loại lỗi. Với mutation, em không retry nếu chưa có idempotency contract. Em cũng theo dõi 429/5xx, retry amplification và test DNS/network failure trước khi kết luận.”

## Câu hỏi đào sâu

1. Nếu provider thay IP trong vòng vài phút nhưng DNS TTL là ngắn, static `HttpClient` không cấu hình connection lifetime có thể gặp vấn đề gì?
2. Nếu API caller timeout sau 2 giây nhưng downstream timeout đặt 10 giây, bạn thiết kế cancellation/budget thế nào?
3. Một teammate đề xuất retry 5 lần cho mọi `TaskCanceledException`; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Chỉ nói “dùng singleton HttpClient” mà không hiểu handler/DNS lifecycle.
- Tăng timeout để xử lý socket pressure.
- Retry mọi timeout không phân biệt cause/idempotency.
- Không propagate cancellation.
- Không đo connection/retry behavior trước khi tối ưu.

## Thang điểm 0–10

- **0–2:** Chỉ tăng timeout hoặc tăng App Service size.
- **3–4:** Biết reuse `HttpClient` nhưng không hiểu handler/DNS trade-off.
- **5–6:** Có factory/handler lifetime, cancellation và retry cơ bản.
- **7–8:** Có timeout budget, telemetry, DNS reasoning và failure tests.
- **9–10:** Thiết kế dependency client hoàn chỉnh với resilience, backpressure và evidence-based tuning.

# Câu 2 — Cosmos DB vẫn trả 429 dù tổng RU/s chưa dùng hết: hot partition hay vấn đề khác?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, RU/s, 429 throttling, hot partition, .NET SDK, data modeling, observability, production troubleshooting

## Bối cảnh

Một event-management platform dùng Azure Cosmos DB for NoSQL lưu attendee activity. Container có partition key hiện tại là:

```text
/eventId
```

Mỗi document đại diện một interaction của attendee trong một event.

Trong hầu hết thời gian hệ thống chạy ổn. Tuy nhiên vào thời điểm mở registration hoặc check-in cho một event lớn:

- API latency tăng;
- logs có HTTP 429 từ Cosmos DB;
- aggregate dashboard cho thấy tổng RU/s toàn container chưa đạt mức provisioned tối đa;
- event nhỏ vẫn hoạt động bình thường;
- một event lớn có lượng traffic cao hơn phần còn lại hàng chục lần;
- team tăng autoscale max RU/s nhưng 429 vẫn còn xuất hiện cho event lớn;
- developer đề xuất thêm Redis để cache;
- developer khác đề xuất retry vô hạn vì Cosmos SDK “sẽ tự retry”; 
- một architect đề xuất đổi partition key ngay trên production nhưng chưa có migration plan.

Chưa biết chắc:

- normalized RU consumption theo physical partition;
- RU charge của từng query/write;
- request distribution theo `eventId`;
- query nào cross-partition;
- SDK retry count/latency contribution;
- một logical partition có tăng rất lớn về storage hay không;
- workload là write-heavy, point-read-heavy hay query-heavy trong peak.

## Câu hỏi chính

Bạn sẽ điều tra incident theo hướng nào để phân biệt hot partition, expensive query, insufficient throughput và client-side retry amplification; sau đó bạn sẽ redesign data/partition strategy như thế nào nếu `eventId` thật sự tạo skew lớn mà vẫn bảo toàn query requirements và migration safety?

## Câu hỏi làm rõ nên cân nhắc

1. Peak workload chủ yếu là create interaction, point read hay aggregate/query theo event?
2. Request Unit charge theo operation nào đang cao nhất?
3. Normalized RU Consumption theo `PartitionKeyRangeId` có một range gần 100% trong khi range khác thấp không?
4. Business có thường query “tất cả interactions của một event” hay phần lớn query theo attendee/session/time bucket?
5. Một event lớn có thể có hàng triệu interactions hoặc vượt logical-partition storage expectations không?

## Gợi ý tư duy

### Gợi ý 1

Tổng RU/s thấp không có nghĩa mọi physical partition còn capacity như nhau.

### Gợi ý 2

Partition key là quyết định data distribution + transaction/query locality. Đổi key không chỉ là tuning index.

### Gợi ý 3

429 không luôn là “service broken”; cần xem retry, normalized RU và end-to-end latency để hiểu impact thực tế.

## Cấu trúc trả lời đề xuất

1. Xác định business/user impact và peak time window.
2. Thu thập Cosmos metrics theo partition/key range.
3. Phân tích RU charge và query patterns.
4. Phân biệt hot logical key với overall throughput shortage.
5. Kiểm tra SDK retry/429 behavior và latency.
6. Đưa ra mitigation ngắn hạn.
7. Đánh giá partition-key redesign theo access patterns.
8. Thiết kế migration/dual-write/backfill/cutover nếu cần.
9. Test load với skewed event traffic.
10. Định nghĩa production alerts và capacity guardrails.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chỉ nhìn total RU/s; phải xem Normalized RU Consumption theo partition key range.
- Hiểu hot partition có thể gây 429 trên một subset trong khi tổng throughput còn dư.
- Đo RU charge theo operation/query.
- Không retry vô hạn.
- Không thêm Redis mặc định nếu root cause là write hot partition.
- Partition-key redesign phải xuất phát từ distribution + access pattern.
- Có migration plan thay vì đổi schema tùy tiện trên production.
- Phân biệt point reads với cross-partition queries về cost.

### Điểm cộng

- Nhận ra `/eventId` cho query locality tốt theo event nhưng có thể tạo skew khi một event cực nóng.
- Đề xuất synthetic/composite key hoặc bucketing nếu query semantics cho phép, ví dụ `eventId + shard/bucket`, nhưng giải thích cost query fan-out.
- Dùng time bucket chỉ khi workload/query phù hợp, không áp dụng máy móc.
- Tách aggregate/read model nếu workload cần thống kê toàn event nhưng write path cần phân tán.
- Theo dõi request charge (`x-ms-request-charge`) và retry diagnostics từ SDK.

### Senior+

- Thiết kế migration versioned container + dual-read/dual-write hoặc backfill an toàn tùy consistency requirement.
- Đưa ra strategy cho aggregation khi dữ liệu một event bị shard.
- Phân tích trade-off giữa write distribution và transaction boundary trong một logical partition.
- Có load test skewed distribution thay vì uniform synthetic traffic.

## Hướng giải quyết tham khảo

Tôi sẽ không kết luận “thiếu RU/s” chỉ từ 429. Azure Cosmos DB phân phối throughput qua physical partitions. Nếu workload dồn vào một hoặc vài logical partition keys, physical partition tương ứng có thể đạt normalized RU consumption 100% trong khi các partition khác còn rảnh. Khi đó aggregate total RU/s nhìn vẫn chưa đầy nhưng request tới hot key có thể bị 429.

Theo Microsoft Learn hiện tại, Normalized RU Consumption theo `PartitionKeyRangeId` là metric quan trọng để phát hiện hot partition. Tôi sẽ xem đúng peak window và correlate với `eventId` lớn.

Investigation:

1. Xác định time range của incident.
2. Xem 429 count/rate và end-to-end latency.
3. Xem normalized RU by partition key range.
4. Thu RU charge của từng operation/query.
5. Phân loại point read, write, single-partition query và cross-partition query.
6. Xem SDK diagnostics/retry contribution.
7. So sánh traffic distribution theo `eventId`.

Nếu một partition range ở 100% còn các range khác thấp, và traffic tập trung vào một event, hot partition là hypothesis mạnh. Nếu tất cả ranges gần 100%, tổng throughput có thể thực sự thiếu. Nếu RU/request đột ngột tăng, query/indexing change có thể là nguyên nhân khác.

Tăng autoscale max RU có thể giúp nếu workload overall cần nhiều throughput, nhưng nếu một logical key cực nóng thì tăng tổng container throughput không phải lúc nào cũng giải quyết distribution problem hiệu quả. Một single hot logical partition vẫn bị giới hạn bởi cách dữ liệu của nó map vào partition range.

Mitigation ngắn hạn có thể gồm:

- giảm unnecessary queries;
- dùng point reads với `id + partition key` khi phù hợp;
- giảm query fan-out;
- giới hạn client concurrency nếu retry đang khuếch đại tải;
- bounded retry theo SDK guidance;
- tạm tăng capacity nếu evidence cho thấy có ích;
- cache chỉ cho read workload cacheable, không dùng để che hot writes.

Redesign cần bắt đầu từ access patterns. `/eventId` có ưu điểm: mọi interaction của event nằm cùng logical partition, query theo event dễ và transaction trong logical partition đơn giản. Nhược điểm là event lớn trở thành hot key.

Một option là shard theo event:

```text
partitionKey = eventId + ":" + shard
```

`shard` có thể derive từ attendee hash hoặc stable deterministic bucket.

Ví dụ:

```text
event-123:00
event-123:01
...
event-123:15
```

Write traffic được phân tán. Nhưng query “all interactions for event-123” giờ phải fan-out qua nhiều shards và aggregation trở nên phức tạp hơn. Đây là trade-off rõ: write scalability đổi lấy query/transaction locality.

Nếu queries chủ yếu theo event + time window, một bucket theo time có thể phù hợp, nhưng chỉ khi traffic phân bố theo thời gian và query pattern khớp. Nếu peak diễn ra trong cùng một minute/hour, time bucket thô vẫn có thể nóng.

Một thiết kế khác là raw interactions dùng sharded partition key, còn event-level aggregate được materialize vào read model riêng được cập nhật asynchronously. Khi đó hot write path phân tán, dashboard vẫn query aggregate document nhanh. Nhưng read model có eventual consistency và pipeline complexity, cần business chấp nhận.

Migration không nên “đổi partition key tại chỗ rồi hy vọng”. Tôi sẽ tạo target container với partition strategy mới, migrate/backfill data, validate counts/checksums/query semantics, rồi cutover theo plan. Tùy requirement có thể:

- dual-write tạm thời;
- change data capture/event replay nếu architecture có;
- backfill + delta sync;
- switch readers trước/writers sau hoặc ngược lại theo compatibility design.

Tôi cần định nghĩa source of truth trong migration và tránh hai containers diverge mà không detect được.

Testing phải dùng skewed distribution: một event chiếm phần lớn traffic, không phải uniform load. Measure:

- 429 rate;
- normalized RU per range;
- p95/p99;
- RU/request;
- retry count;
- write throughput;
- aggregate-query latency;
- migration correctness.

Monitoring sau fix:

- normalized RU > threshold theo partition range;
- 429 rate + latency;
- hottest partition keys;
- RU per operation;
- SDK retry duration;
- physical/logical partition growth;
- event-level traffic skew.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhìn total RU rồi kết luận còn dư capacity. Cosmos phân phối throughput theo physical partitions, nên một eventId rất nóng có thể làm partition range của nó đạt 100% normalized RU trong khi partition khác rảnh. Em sẽ correlate 429 với Normalized RU Consumption, RU charge, SDK diagnostics và traffic theo eventId để phân biệt hot partition với expensive query hoặc thiếu throughput tổng thể.

Nếu `/eventId` thật sự gây skew, em không đổi key ngay. Em xem access pattern trước. Có thể shard một event theo attendee hash hoặc bucket để phân tán writes, nhưng đổi lại query toàn event phải fan-out và transaction boundary thay đổi. Nếu dashboard cần aggregate, em có thể tạo read model riêng.

Migration sẽ dùng target container mới, backfill + delta/dual-write có kiểm soát, validation và cutover/rollback rõ. Em load test với skewed traffic và monitor normalized RU, 429, request charge, retry latency và hottest keys.”

## Câu hỏi đào sâu

1. Nếu business bắt buộc atomic transaction giữa nhiều interaction records của cùng event, sharding event thành 16 keys ảnh hưởng thiết kế thế nào?
2. Nếu SDK tự retry 429 và user không thấy lỗi nhưng p99 tăng mạnh, bạn có coi incident đã được xử lý không?
3. Nếu hot event chỉ xảy ra vài lần mỗi năm, bạn quyết định redesign partition key hay dùng operational mitigation bằng tiêu chí nào?

## Lỗi trả lời thường gặp

- Chỉ tăng RU/s mà không xem normalized RU theo partition.
- Retry vô hạn vì cho rằng 429 luôn transient.
- Thêm Redis cho write hotspot.
- Đổi partition key mà không phân tích query/transaction locality.
- Load test uniform traffic nên không tái hiện hot partition thật.

## Thang điểm 0–10

- **0–2:** Chỉ tăng RU hoặc retry.
- **3–4:** Biết hot partition nhưng không có evidence/migration plan.
- **5–6:** Có normalized RU analysis, partition trade-off và bounded retry.
- **7–8:** Có sharding/read model, skewed load test và migration strategy.
- **9–10:** Cân bằng distribution, query locality, transactions, cost, operations và rollback bằng evidence.

# Câu 3 — Thiết kế file-upload platform dùng Azure Blob Storage: backend proxy hay direct upload bằng SAS?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, ASP.NET Core, Managed Identity, SAS, security, large-file upload, async processing, observability, API design, malware scanning, reliability

## Bối cảnh

Một enterprise portal cần module upload tài liệu cho nhiều use case:

- employee upload PDF/images;
- marketing upload media files;
- data-import upload CSV/ZIP;
- file size từ vài KB tới vài GB;
- một số file cần malware scanning trước khi được người khác download;
- files có retention policy khác nhau;
- hệ thống chạy ASP.NET Core trên Azure App Service;
- authentication dùng Microsoft Entra ID concepts;
- backend có Managed Identity;
- storage target là Azure Blob Storage.

Hai design proposals đang tranh luận:

### Proposal A

Browser upload toàn bộ file qua ASP.NET Core API, backend stream tiếp sang Blob Storage.

### Proposal B

Backend cấp SAS URL ngắn hạn để browser upload trực tiếp tới Blob Storage; backend chỉ quản lý metadata/status.

Business requirements chưa đầy đủ:

- một số file có thể chứa sensitive data;
- user chỉ được upload vào folder/container thuộc tenant/project của mình;
- upload có thể bị gián đoạn;
- cần progress/resume cho file lớn nếu khả thi;
- file chưa scan không được expose cho download;
- audit cần biết ai upload, file nào, lúc nào;
- external integrations sau này có thể upload machine-to-machine;
- CDN có thể được dùng cho public media trong tương lai nhưng private documents không được public cache.

## Câu hỏi chính

Hãy thiết kế end-to-end architecture cho upload, storage, metadata, scanning, authorization và download; giải thích khi nào nên proxy upload qua backend, khi nào nên direct-to-Blob bằng SAS, cách dùng Managed Identity/SAS theo least privilege, và cách xử lý partial upload, retry, scan failure, orphan blobs và security boundaries.

## Câu hỏi làm rõ nên cân nhắc

1. File nào cần malware scanning trước khi visible và file nào có thể publish ngay?
2. Có requirement kiểm tra nội dung trong request trước khi upload hoàn tất hay chỉ metadata/size/type?
3. Tenant isolation cần ở container, path/prefix hay authorization metadata layer?
4. Download là private authenticated hay có public media/CDN use case riêng?
5. Client/browser có cần resumable/chunked upload cho multi-GB files không?

## Gợi ý tư duy

### Gợi ý 1

Đừng xem SAS như “public URL”. Hãy xem nó như delegated permission có scope, operation và expiry cụ thể.

### Gợi ý 2

Direct upload giảm backend bandwidth nhưng chuyển một phần responsibility sang storage contract và client workflow.

### Gợi ý 3

Tách `uploaded` khỏi `approved/available`. File chưa scan không nên trở thành trusted content chỉ vì upload HTTP thành công.

## Cấu trúc trả lời đề xuất

1. Làm rõ file classes, security và availability requirements.
2. Thiết kế metadata/state model.
3. So sánh proxy upload với direct upload.
4. Thiết kế auth + Managed Identity + SAS.
5. Thiết kế upload completion handshake.
6. Thiết kế scanning/quarantine pipeline.
7. Xử lý partial upload/orphan/retry/idempotency.
8. Thiết kế download authorization.
9. Thiết kế retention/lifecycle/CDN boundaries.
10. Đề xuất observability/testing/deployment.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không lưu storage account key trong application nếu Managed Identity có thể dùng.
- SAS phải ngắn hạn, least privilege và scoped đúng blob/path/action.
- File chưa scan có state quarantine/pending và không được download như trusted file.
- Direct upload không có nghĩa client được tự chọn blob path tùy ý.
- Backend vẫn sở hữu metadata/authorization/business state.
- Có upload session/idempotency để tránh duplicate/orphan data.
- Large files cần streaming/chunking thay vì buffer toàn bộ trong backend memory.
- Download private phải authorization trước khi cấp access.
- Có cleanup/lifecycle cho abandoned uploads.

### Điểm cộng

- Dùng user delegation SAS thay vì account-key-signed SAS khi architecture phù hợp và backend identity có quyền tương ứng.
- Tách quarantine container/prefix khỏi clean/available content.
- Upload completion endpoint verify blob properties/size/hash/metadata trước khi chuyển state.
- Event-driven scanning qua queue/Event Grid/worker nhưng có idempotency và retry/DLQ.
- Content type/extension chỉ là hint; không tin client-supplied metadata như security validation duy nhất.

### Senior+

- State machine rõ: `Created -> Uploading -> Uploaded -> Scanning -> Clean/Rejected -> Available/Deleted`.
- Thiết kế tenant isolation + immutable ownership metadata chống IDOR/path manipulation.
- Có integrity strategy như checksum/hash khi requirement cần.
- Tách public media delivery/CDN khỏi private-document authorization path.
- Thiết kế compensation cho blob upload thành công nhưng metadata commit thất bại và ngược lại.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng việc tách file transfer khỏi business trust state. Một blob upload thành công chỉ có nghĩa bytes đã tới storage; nó chưa có nghĩa file hợp lệ, sạch malware hay user được phép chia sẻ/download.

Tôi tạo metadata record trong database trước khi upload:

```text
FileId
TenantId
OwnerId
OriginalFileName
BlobName
ExpectedSize
ContentTypeHint
Status
CreatedAt
UploadedAt
ScanStatus
Hash (nếu dùng)
RetentionClass
```

`BlobName` do server tạo từ `FileId`/safe opaque identifier, không lấy raw client path. Authorization dựa trên metadata + authenticated user/tenant, không tin path client truyền.

### Option 1 — Backend proxy upload

Flow:

```text
Browser -> ASP.NET Core -> Blob Storage
```

Ưu điểm:

- backend kiểm soát stream trực tiếp;
- dễ enforce một số validation trong request pipeline;
- client đơn giản;
- có thể phù hợp file nhỏ hoặc network topology đặc biệt.

Nhược điểm:

- bandwidth đi qua application;
- App Service connection/request duration tăng;
- scale cost tăng với file lớn;
- backend trở thành data-plane bottleneck.

Nếu dùng proxy, tôi stream request thẳng sang Blob Storage, không `ReadAllBytes`/buffer full file trong memory. Timeout/body limits phải được thiết kế cho file-size class.

### Option 2 — Direct upload với delegated SAS

Flow:

1. Client gọi `POST /files` với metadata.
2. Backend authenticate/authorize và tạo upload session + blob name.
3. Backend dùng identity của service để cấp scoped SAS phù hợp.
4. Client upload trực tiếp Blob Storage.
5. Client gọi completion endpoint hoặc backend nhận storage event.
6. Backend verify blob properties và chuyển status `Uploaded`.
7. Trigger scanning.
8. Chỉ sau `Clean` mới chuyển `Available`.

Direct upload thường tốt hơn cho large files vì backend không phải relay bytes. Nhưng SAS phải rất hạn chế: đúng resource, đúng permissions cần thiết, expiry ngắn và ideally không cấp list/read/delete nếu chỉ cần upload.

Managed Identity dùng cho backend-to-Azure authentication. Khi cần cấp delegated access cho client, user delegation SAS là lựa chọn mạnh vì SAS được ký dựa trên Microsoft Entra credentials thay vì account key, khi service/configuration hỗ trợ. Tôi vẫn phải bảo vệ token: SAS trong URL là credential ngắn hạn và không được log tùy tiện.

Tôi không cho client tự chọn `container/path`. Backend mapping `FileId -> BlobName` và chỉ cấp SAS cho exact target resource hoặc scope nhỏ nhất có thể.

### Quarantine và scanning

File cần scan được upload vào quarantine location. Download endpoint chỉ cho access khi DB state là `Clean/Available`.

Pipeline có thể:

```text
Blob uploaded
  -> event/message
  -> scanner worker
  -> scan result
  -> metadata state update
  -> move/copy/tag file sang clean zone hoặc mark available
```

Cách move/copy cụ thể phụ thuộc Blob semantics và operational cost. Quan trọng là state transition idempotent và event có thể được xử lý lại.

Nếu scanner down:

- file giữ `PendingScan`;
- user thấy trạng thái processing;
- không publish file;
- retry bounded;
- poison/failed scans vào DLQ/manual review path;
- alert nếu backlog vượt SLO.

### Upload completion và partial failures

Các failure window cần thiết kế:

- metadata created nhưng client chưa upload;
- blob upload hoàn tất nhưng completion API fail;
- client retry upload;
- event duplicated;
- metadata update fail sau scan;
- blob tồn tại nhưng DB record bị rollback.

Tôi dùng upload session/state machine + idempotent completion. Cleanup job xóa records/blobs ở trạng thái abandoned sau retention window phù hợp.

Với multi-GB files, client có thể dùng block blob/chunked upload và resume theo SDK capability. Backend chỉ issue authorization/session, không giữ whole file. Exact client SDK strategy cần kiểm tra theo platform.

### Download

Private file:

1. client request download bằng `FileId`;
2. backend authenticate + authorize tenant/owner/role;
3. check status `Available`;
4. backend stream file hoặc issue short-lived read SAS;
5. audit access nếu required.

Short-lived read SAS giảm backend bandwidth nhưng access URL phải scope/expiry chặt. Nếu download cần policy động từng request, backend vẫn là policy decision point.

Public marketing media là use case khác. Nếu dùng CDN, chỉ clean/public-class files mới được publish; private files không share cùng public caching contract một cách mơ hồ.

### Security

- reject path traversal semantics bằng server-generated blob IDs;
- filename chỉ display metadata, không phải storage path authority;
- validate authorization ở metadata layer;
- giới hạn file size;
- không tin extension/MIME từ client;
- malware scanning khi required;
- không expose storage keys;
- sanitize logs, không log SAS;
- lifecycle delete theo retention/compliance;
- encrypt at rest/in transit theo platform defaults/policy và kiểm tra compliance requirement cụ thể.

### Observability

Metrics:

- upload started/completed/abandoned;
- upload bytes/duration;
- SAS issuance count/failures;
- completion verification failures;
- scan queue depth/age;
- scan clean/rejected/error;
- orphan cleanup count;
- download authorization failures;
- storage 4xx/5xx/dependency latency.

Trace/correlation theo `FileId`, không cần log SAS token.

### Testing

- unauthorized tenant tries another `FileId`;
- expired SAS;
- SAS cannot list/delete when only write required;
- upload interrupted giữa chừng;
- duplicate completion;
- blob exists nhưng metadata missing;
- malware-positive file;
- scanner timeout/retry/DLQ;
- multi-GB chunk upload;
- private file cannot be cached/publicly accessed;
- cleanup of abandoned sessions.

Tôi không chọn một design duy nhất cho mọi file class. File nhỏ nội bộ có thể proxy đơn giản; large media/import thường direct-to-Blob phù hợp hơn. Kiến trúc nên support policy theo file category thay vì ép mọi workload đi một path.

## Mẫu trả lời trong phỏng vấn

“Em tách transfer khỏi trust state. Backend tạo `FileId`, ownership metadata và server-controlled blob name trước. Với file lớn, em ưu tiên direct upload: backend authenticate/authorize rồi cấp SAS ngắn hạn chỉ có permission cần thiết cho đúng blob. Backend dùng Managed Identity; nếu phù hợp em ưu tiên user delegation SAS thay vì account key.

Upload xong chưa được download ngay. File đi vào quarantine, completion step verify properties rồi scanner xử lý asynchronously. Chỉ trạng thái `Clean/Available` mới được cấp read access. Private download luôn đi qua authorization decision, sau đó có thể trả short-lived read SAS.

Em thiết kế state machine/idempotent completion để xử lý upload thành công nhưng API fail, duplicate event và orphan blob. Có cleanup job, scan DLQ, metrics backlog và không log SAS. Với file nhỏ hoặc requirement cần inspect stream tại API, proxy upload vẫn có thể hợp lý, nhưng phải stream chứ không buffer whole file.”

## Câu hỏi đào sâu

1. Nếu client upload blob thành công nhưng không bao giờ gọi completion endpoint, bạn phát hiện và recover thế nào?
2. Nếu scanner cần tải file về để scan và file 20 GB, bạn thiết kế resource/cost/concurrency thế nào?
3. Một architect muốn cấp container-level SAS 24 giờ để frontend dễ upload nhiều file; bạn phản biện ra sao?

## Lỗi trả lời thường gặp

- Cấp SAS rộng, dài hạn và có nhiều quyền không cần thiết.
- Cho client tự quyết blob path/tenant prefix.
- Coi upload thành công là file đã trusted.
- Buffer file lớn qua backend memory.
- Không xử lý orphan/partial upload và duplicate events.

## Thang điểm 0–10

- **0–2:** Chỉ nói “upload lên Blob” mà không có security/state model.
- **3–4:** Có SAS/Managed Identity nhưng scope và lifecycle mơ hồ.
- **5–6:** Có direct/proxy trade-off, authorization, quarantine và cleanup.
- **7–8:** Có state machine, idempotency, large-file strategy, DLQ và telemetry.
- **9–10:** Thiết kế đầy đủ data-plane/control-plane boundaries, least privilege, failure compensation, multi-tenant isolation và operational readiness.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Outbound HTTP reliability bắt đầu từ connection lifecycle:** `HttpClient` object không phải toàn bộ câu chuyện; handler, pool, DNS và retry behavior mới quyết định production behavior.
- **Timeout không phải fix cho connection churn:** cần end-to-end budget, cancellation và bounded retry.
- **Cosmos DB phải quan sát theo partition:** tổng RU/s thấp vẫn có thể tồn tại hot partition và 429 ở một key range.
- **Partition key là architecture decision:** nó chi phối distribution, query locality, transaction scope và migration cost.
- **File upload cần tách transfer khỏi trust state:** bytes đã upload chưa đồng nghĩa file được phép sử dụng.
- **SAS là delegated credential:** phải scope nhỏ, expiry ngắn và không được coi như public URL.

## Mẫu tư duy cần nhớ

1. **Measure connection/partition behavior before increasing timeout or capacity.**
2. **Design retries together with idempotency and caller budget.**
3. **Look for skew, not only averages.**
4. **Treat data partitioning as a trade-off between distribution and locality.**
5. **Separate control-plane authorization from data-plane transfer.**
