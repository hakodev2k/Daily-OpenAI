# Code Review Challenge 1 — Elasticsearch reindex làm biến mất sản phẩm khỏi kết quả tìm kiếm

## Bối cảnh

Một e-commerce API lưu catalog chuẩn trong PostgreSQL và phục vụ tìm kiếm từ Elasticsearch. Mỗi đêm, worker tạo lại search index để áp dụng analyzer mới. Catalog có 2 triệu sản phẩm; trong lúc reindex vẫn có cập nhật giá, trạng thái bán và xóa sản phẩm. API search không được ngừng hoạt động; chấp nhận eventual consistency tối đa 60 giây đối với cập nhật thông thường. Production ghi nhận mất kết quả trong vài phút, dữ liệu giá cũ quay lại và worker đôi lúc vượt giới hạn memory. Có hai worker replicas. Giả định các abstraction bên dưới là lớp wrapper hợp lệ của ứng dụng, không phải API nguyên bản của Elasticsearch.

## Đoạn code cần review

```csharp
public sealed class CatalogReindexJob(
    CatalogDb db,
    ISearchIndex search,
    ILogger<CatalogReindexJob> logger)
{
    public async Task RunAsync(CancellationToken ct)
    {
        await search.DeleteIndexAsync("products", ct);
        await search.CreateIndexAsync("products", ct);

        var products = await db.Products
            .Include(p => p.Category)
            .Where(p => p.IsActive)
            .ToListAsync(ct);

        foreach (var product in products)
        {
            await search.IndexAsync("products", product.Id.ToString(),
                new ProductDocument(
                    product.Id,
                    product.Name,
                    product.Category.Name,
                    product.Price), ct);
        }

        await search.RefreshAsync("products", ct);
        logger.LogInformation("Reindexed {Count} products", products.Count);
    }
}

public interface ISearchIndex
{
    Task DeleteIndexAsync(string name, CancellationToken ct);
    Task CreateIndexAsync(string name, CancellationToken ct);
    Task IndexAsync(string index, string id, ProductDocument doc,
        CancellationToken ct);
    Task RefreshAsync(string index, CancellationToken ct);
}

public record ProductDocument(
    Guid Id, string Name, string Category, decimal Price);
```

## Kết quả code review tham khảo

### [Critical] — Xóa live index trước khi tạo lại

**Vấn đề:** Xóa index đang phục vụ truy vấn.  
**Tại sao xảy ra:** Không có index generation tách biệt hoặc read alias.  
**Ảnh hưởng production:** Search downtime hoặc kết quả thiếu trong toàn bộ thời gian rebuild.  
**Cách sửa:** Build `products-vN` riêng; validate rồi atomic alias swap; giữ thế hệ cũ cho rollback.

### [High] — Ghi đè dữ liệu mới bằng snapshot cũ

**Vấn đề:** Các cập nhật trong thời gian rebuild có thể mất hoặc bị đảo ngược.  
**Tại sao xảy ra:** Full scan không có checkpoint và replay các thay đổi.  
**Ảnh hưởng production:** Giá/trạng thái bán sai sau cutover.  
**Cách sửa:** Dùng transactional outbox hoặc CDC với monotonic version, ghi nhận watermark, replay và kiểm tra lag trước cutover. Không giả định chỉ scan lại là đủ.

### [High] — Không xử lý sản phẩm bị xóa hoặc ngừng bán sau snapshot

**Vấn đề:** Index mới có thể chứa sản phẩm đã bị xóa hoặc inactive.  
**Tại sao xảy ra:** Chỉ index bản ghi active tại thời điểm đọc, không replay delete/tombstone.  
**Ảnh hưởng production:** Search hiển thị hàng không bán được.  
**Cách sửa:** Sự kiện delete/inactive phải xóa document hoặc cập nhật trạng thái theo version.

### [High] — Hai replicas cùng rebuild

**Vấn đề:** Cùng xóa/tạo index vật lý và ghi chồng lẫn nhau.  
**Tại sao xảy ra:** Không có coordination/ownership cho generation.  
**Ảnh hưởng production:** Race, lỗi index not found, kết quả không xác định.  
**Cách sửa:** Lease/leader election có fencing token hoặc orchestration một job; thao tác publish kiểm tra generation và quyền sở hữu.

### [High] — Không kiểm tra lỗi indexing từng document

**Vấn đề:** Wrapper có thể che giấu partial failures nếu chuyển sang bulk; hiện tại lỗi giữa vòng lặp cũng để lại index dở dang.  
**Tại sao xảy ra:** Không có batch checkpoint, retry policy và validation.  
**Ảnh hưởng production:** Thiếu document hoặc job phải làm lại toàn bộ.  
**Cách sửa:** Bulk có bounded retries cho transient errors, xử lý per-item status, checkpoint và ngừng publish khi chưa đạt acceptance gates.

### [Medium] — Load toàn bộ catalog vào memory

**Vấn đề:** `ToListAsync` materialize hàng triệu entities và navigation.  
**Tại sao xảy ra:** EF tracking và không phân trang/projection.  
**Ảnh hưởng production:** LOH pressure, GC, OOM và DB load.  
**Cách sửa:** `AsNoTracking`, projection và keyset batches theo khóa ổn định.

### [Medium] — Index từng document tuần tự

**Vấn đề:** Mỗi sản phẩm là một network round trip.  
**Tại sao xảy ra:** Không dùng bulk API và bounded concurrency.  
**Ảnh hưởng production:** Reindex kéo dài, consistency window tăng.  
**Cách sửa:** Bulk batch có giới hạn kích thước, backpressure và theo dõi throughput.

### [Medium] — Không có validation và rollback gate

**Vấn đề:** Log thành công không chứng minh query/search quality đúng.  
**Tại sao xảy ra:** Không có schema/analyzer checks, sample queries, count reconciliation và replay lag gate.  
**Ảnh hưởng production:** Publish index thiếu hoặc mapping sai.  
**Cách sửa:** Canary queries, reconciliation theo phân đoạn, kiểm tra mapping và chỉ cutover khi đạt tiêu chí.

### [Low] — Refresh và logging chưa có chiến lược

**Vấn đề:** Refresh cuối job không thay thế việc kiểm tra visibility và không có metrics từng giai đoạn.  
**Tại sao xảy ra:** Chỉ log tổng số entity đã đọc.  
**Ảnh hưởng production:** Khó phân biệt lỗi scan, indexing, replay và cutover.  
**Cách sửa:** Instrument stage, batch, lag, rejection và generation.

## Phiên bản đề xuất

Mã sau là orchestration ở mức application; các interface phải được triển khai với atomic alias swap, version checks và durable outbox. Nó không tự nhận là một implementation hoàn chỉnh của Elasticsearch client.

```csharp
public sealed class ReindexCoordinator(
    ICatalogBatchReader catalog,
    IVersionedSearchWriter search,
    IChangeReplay replay,
    IReindexLease lease,
    IIndexValidator validator)
{
    public async Task RunAsync(CancellationToken ct)
    {
        await using var owner = await lease.AcquireAsync("catalog-reindex", ct);
        var generation = $"products-{Guid.NewGuid():N}";
        var watermark = await replay.GetCurrentWatermarkAsync(ct);
        await search.CreateGenerationAsync(generation, ct);

        Guid? after = null;
        while (true)
        {
            ct.ThrowIfCancellationRequested();
            await owner.AssertOwnershipAsync(ct);
            var batch = await catalog.ReadPageAsync(after, 1000, ct);
            if (batch.Count == 0) break;

            await search.BulkUpsertAsync(generation, batch, ct);
            after = batch[^1].Id;
        }

        var replayPosition = watermark;
        while (true)
        {
            await owner.AssertOwnershipAsync(ct);
            var result = await replay.ApplyChangesAsync(
                generation, replayPosition, ct);
            replayPosition = result.NextPosition;
            if (result.Lag <= TimeSpan.FromSeconds(10)) break;
        }

        await validator.AssertReadyAsync(generation, replayPosition, ct);
        await owner.AssertOwnershipAsync(ct);
        await search.PublishAliasAsync(
            "products-read", generation, owner.FencingToken, ct);
    }
}
```

**Điều kiện triển khai:** `ReadPageAsync` phải đọc một tập dữ liệu có snapshot/watermark nhất quán hoặc hỗ trợ replay đủ để bù mọi thay đổi; `BulkUpsertAsync` phải idempotent và áp dụng external version để tránh sự kiện cũ ghi đè; `ApplyChangesAsync` phải xử lý cả delete, có thứ tự per product và lưu vị trí bền vững. Sau cutover, live change consumer tiếp tục đồng bộ; không chỉ dừng ở một lần replay. `PublishAliasAsync` phải bảo đảm atomic alias update và từ chối stale fencing token tại coordination layer.

## Giải thích thiết kế sau khi sửa

Tách physical index khỏi read alias giúp duy trì search trong lúc rebuild. Snapshot + replay bảo vệ consistency, còn versioning chống out-of-order events. Lease với fencing giảm nguy cơ worker cũ publish sau khi mất quyền. Validation và retention của generation cũ hỗ trợ rollback. Với hệ thống nhỏ, scheduled single worker và transactional outbox đơn giản có thể đủ, không cần xây dựng một nền tảng streaming phức tạp.

## Trade-offs

Cần thêm dung lượng để tồn tại song song hai index, chi phí bulk/replay và logic vận hành generation. CDC có độ phức tạp riêng; outbox có thể phù hợp hơn nếu ứng dụng kiểm soát write path. Strong consistency tuyệt đối giữa PostgreSQL và Elasticsearch thường không thực tế nếu vẫn phục vụ async search; cần xác định SLA lag rõ ràng.

## Cách kiểm thử

1. **Integration:** Search liên tục trong lúc rebuild; không có khoảng trống do index deletion.
2. **Concurrency:** Update giá, inactive và delete khi batch đang chạy; sau replay, version mới nhất thắng.
3. **Failure-path:** Kill worker ở 30% và trước alias swap; read alias vẫn trỏ generation cũ.
4. **Load:** 2 triệu documents, giới hạn memory, throughput, DB CPU và indexing rejection.
5. **Coordination:** Hai replicas cùng khởi chạy; chỉ owner hợp lệ được publish.

## Quan sát trong production

Theo dõi `generation_id`, `reindex_stage`, scanned/indexed/rejected count, bulk latency, Elasticsearch indexing pressure, DB query time, replay lag, alias target, search p95/p99 và mismatch sampling. Alert khi lag vượt 60 giây, failed batches còn tồn đọng hoặc alias trỏ generation chưa được validate.

2. Nếu outbox retention ngắn hơn thời gian rebuild, cần xử lý ra sao?
3. Khi nào incremental indexing tốt hơn full rebuild?

## Kết quả code review tham khảo

### [High] — RollingUpdate cho phép giảm quá nhiều capacity

**Vấn đề:** `maxUnavailable: 2` với 3 replicas có thể chỉ còn một replica Ready.  
**Tại sao xảy ra:** Rollout cho phép hai Pod unavailable đồng thời.  
**Ảnh hưởng production:** Request queue, timeout, 503 khi traffic cao.  
**Cách sửa:** `maxUnavailable: 0`, `maxSurge: 1` nếu cluster có headroom; kiểm tra PDB/HPA và capacity thực tế.

### [High] — Liveness phụ thuộc SQL Server

**Vấn đề:** SQL outage có thể khiến liveness thất bại hàng loạt.  
**Tại sao xảy ra:** Dùng chung health check có dependency SQL cho readiness và liveness.  
**Ảnh hưởng production:** Restart storm, mất connection warm-up, tăng thời gian phục hồi.  
**Cách sửa:** Liveness chỉ kiểm tra process responsiveness; readiness kiểm tra dependency thực sự thiết yếu, có timeout phù hợp.

### [High] — Startup probe và startup budget không phù hợp

**Vấn đề:** Probe bắt đầu khi ứng dụng có thể chưa warm-up xong.  
**Tại sao xảy ra:** Không có startupProbe; liveness có thể kill container trước khi khởi động hoàn tất.  
**Ảnh hưởng production:** CrashLoopBackOff và rollout kéo dài.  
**Cách sửa:** Thêm startupProbe với failureThreshold × periodSeconds bao phủ startup worst-case; readiness độc lập.

### [High] — Không có shutdown/drain strategy rõ ràng

**Vấn đề:** In-flight checkout có thể bị cắt khi Pod kết thúc.  
**Tại sao xảy ra:** Không khai báo termination grace phù hợp, không kiểm chứng application shutdown và traffic drain.  
**Ảnh hưởng production:** Client retry không rõ payment đã thành công hay chưa, gây duplicate charge nếu không idempotent.  
**Cách sửa:** Configure graceful shutdown, readiness transition/drain, `terminationGracePeriodSeconds` đủ dài và payment idempotency key; test termination thực tế. Không giả định preStop sleep tự bảo đảm an toàn.

### [Medium] — Mutable image tag

**Vấn đề:** `latest` không định danh artifact duy nhất.  
**Tại sao xảy ra:** Deployment không pin digest hoặc immutable release tag.  
**Ảnh hưởng production:** Rollback không tái lập chính xác binary.  
**Cách sửa:** Pin `image@sha256:...` từ CI hoặc immutable version.

### [Medium] — Không khai báo resource requests

**Vấn đề:** Scheduler thiếu CPU/memory requests rõ ràng.  
**Tại sao xảy ra:** Chỉ khai báo limits; Kubernetes có thể default requests bằng limits khi admission không đặt giá trị khác.  
**Ảnh hưởng production:** Scheduling/capacity planning khó kiểm soát, throttling CPU có thể tăng latency.  
**Cách sửa:** Benchmark để đặt requests/limits có chủ đích, quan sát CPU throttling và OOMKilled.

### [Medium] — Không có minimum ready duration và rollout gate

**Vấn đề:** Pod vừa Ready có thể chưa ổn định nhưng rollout tiếp tục.  
**Tại sao xảy ra:** Không có `minReadySeconds` và validation theo SLO.  
**Ảnh hưởng production:** Lỗi lan ra nhiều replicas.  
**Cách sửa:** Đặt minReadySeconds phù hợp, kiểm tra rollout status và error-rate canary gate ở pipeline.

### [Medium] — Endpoint checkout chưa thể hiện cancellation/idempotency

**Vấn đề:** Không truyền request cancellation và không thể hiện idempotency contract.  
**Tại sao xảy ra:** Handler đơn giản gọi external payment provider trực tiếp.  
**Ảnh hưởng production:** Tốn tài nguyên khi client disconnect; retry sau timeout có thể charge hai lần.  
**Cách sửa:** Truyền CancellationToken với policy rõ ràng, lưu idempotency key/transaction state; không hủy tùy tiện operation đã commit tại provider.

```csharp
    CancellationToken ct) =>
    await client.ChargeAsync(request, ct));
app.Run();
```

**Lưu ý triển khai:** Image digest trong YAML là placeholder bắt buộc thay bằng digest do CI phát hành. `PaymentClient.ChargeAsync` ở ví dụ giả định hỗ trợ `CancellationToken`; hệ thống thật cần durable idempotency trước khi production. Probe `self` chỉ chứng minh health endpoint xử lý được request, không chứng minh toàn bộ process không deadlock. Nếu readiness SQL check quá tốn kém hoặc outage ngắn, cần thiết kế timeout và cache kết quả health có kiểm soát. Shutdown timeout phải kiểm tra theo phiên bản hosting/runtime và end-to-end termination behavior, không chỉ tin vào biến cấu hình.

## Giải thích thiết kế sau khi sửa

Startup probe cho ứng dụng đủ thời gian khởi động; readiness quyết định nhận traffic; liveness dành cho lỗi tiến trình có thể phục hồi bằng restart. RollingUpdate giữ đủ replicas Ready nếu cluster đủ tài nguyên. Pin digest giúp trace và rollback. Graceful shutdown phải phối hợp giữa Kubernetes, ASP.NET Core và payment provider; tránh coi HTTP timeout là bằng chứng transaction thất bại.

## Trade-offs

`maxUnavailable: 0` yêu cầu surge capacity; cluster thiếu tài nguyên có thể khiến rollout đứng chờ. Readiness phụ thuộc SQL có thể rút tất cả endpoints khỏi Service khi SQL outage; trong một số hệ thống, degraded readiness hoặc circuit breaker hợp lý hơn. Grace period dài làm release chậm và tiêu tốn tài nguyên. Requests/limits phải dựa trên load test, không sao chép máy móc số liệu ví dụ.

## Cách kiểm thử

1. **Deployment validation:** Rollout với 3 replicas và traffic liên tục; đo 5xx/p99.
2. **Failure injection:** SQL mất kết nối 30 giây; xác minh không restart storm do liveness.
3. **Startup:** Warm-up 40–55 giây; không CrashLoopBackOff.
4. **Termination:** SIGTERM khi checkout đang xử lý; xác minh drain và payment reconciliation.
5. **Rollback:** Rollback về digest cũ, kiểm tra readiness và artifact identity.

## Quan sát trong production

Theo dõi `kube_deployment_status_replicas_available`, Pod Ready transitions, restart reason, OOMKilled, CPU throttling, rollout duration, request 502/503, checkout p95/p99, in-flight requests, dependency failure và payment idempotency conflicts. Liên kết deployment revision/digest với Application Insights traces; alert khi available replicas giảm dưới ngưỡng hoặc 5xx tăng trong rollout.

## Câu hỏi phỏng vấn mở rộng

1. Nếu database outage toàn vùng, readiness có nên fail trên mọi Pod không?
2. Vì sao Pod Ready không đồng nghĩa checkout thành công?
3. Bạn thiết kế canary rollback dựa trên metric nào khi traffic ít?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Reindex an toàn cần tách build khỏi publish, replay thay đổi có version và kiểm tra dữ liệu trước cutover. Kubernetes deployment an toàn cần phân biệt startup, readiness, liveness, bảo đảm capacity và phối hợp graceful shutdown với idempotent business operations.

## Mẫu tư duy cần nhớ

1. **Không phá live path để rebuild:** chuẩn bị và xác minh thế hệ mới trước khi chuyển traffic.
2. **Snapshot không thay thế change capture:** luôn xác định dữ liệu thay đổi giữa lúc đọc và publish.
3. **Health là quyết định vận hành:** mỗi probe phải có failure semantics phù hợp.
4. **Retry phải đi cùng idempotency:** đặc biệt với payment và external side effects.
5. **Đo trước khi kết luận:** dùng trace, lag, availability và p99 để xác minh cải tiến.
