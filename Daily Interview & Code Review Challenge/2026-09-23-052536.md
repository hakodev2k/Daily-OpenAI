# Code Review Challenge 1 — API upload tài liệu tin vào tên file và `Content-Type` từ client

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, file upload security, authorization, memory, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal employee platform cho phép nhân viên upload tài liệu đính kèm vào hồ sơ. ASP.NET Core API chạy nhiều Azure App Service instances và lưu file vào Azure Blob Storage. File tối đa theo requirement business là 25 MB; người dùng chỉ được upload vào hồ sơ mà họ có quyền chỉnh sửa.

Production gần đây có request upload làm memory tăng mạnh. Security review cũng phát hiện blob URL được lưu trực tiếp và một số file có extension hợp lệ nhưng nội dung không đúng loại file. Team cho rằng `[Authorize]`, `IFormFile.ContentType` và kiểm tra extension là đủ vì endpoint chỉ dành cho user đã đăng nhập.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/employees/{employeeId:guid}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly EmployeeDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        EmployeeDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> Upload(
        Guid employeeId,
        IFormFile file,
        CancellationToken cancellationToken)
    {
        var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
        if (extension is not ".pdf" and not ".docx" and not ".png")
            return BadRequest("Unsupported file type");

        if (!file.ContentType.StartsWith("application/") &&
            !file.ContentType.StartsWith("image/"))
            return BadRequest("Unsupported content type");

        using var memory = new MemoryStream();
        await file.CopyToAsync(memory, cancellationToken);
        memory.Position = 0;

        var blobName = $"employees/{employeeId}/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);

        await blob.UploadAsync(memory, overwrite: true, cancellationToken);

        var document = new EmployeeDocument
        {
            EmployeeId = employeeId,
            FileName = file.FileName,
            ContentType = file.ContentType,
            BlobUrl = blob.Uri.ToString(),
            UploadedAtUtc = DateTime.UtcNow
        };

        _db.EmployeeDocuments.Add(document);
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Uploaded {FileName} for employee {EmployeeId} to {BlobUrl}",
            file.FileName,
            employeeId,
            blob.Uri);

        return Ok(new { document.Id, document.BlobUrl });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và security problems.
2. Xác định performance/reliability risks khi nhiều upload diễn ra đồng thời.
3. Giải thích production impact và attack/failure paths.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design an toàn hơn.
6. Nêu cách test authorization, malicious files, large uploads và Blob failure.
7. Nêu telemetry cần có trong production.

## Câu hỏi gợi mở

1. `[Authorize]` có chứng minh caller được sửa đúng `employeeId` trong route không?
2. `FileName`, extension và `ContentType` đến từ đâu, và trường nào có thể tin cậy?
3. Điều gì xảy ra với memory khi nhiều request cùng copy toàn bộ file 25 MB vào `MemoryStream`?
4. Nếu Blob upload thành công nhưng `SaveChangesAsync` thất bại thì hệ thống còn trạng thái gì?
5. Blob URL có đồng nghĩa với một authorization boundary an toàn không?

## Kết quả code review tham khảo

### Critical — Thiếu object-level authorization cho `employeeId`

**Vấn đề:** Endpoint chỉ yêu cầu caller authenticated nhưng không kiểm tra caller có quyền chỉnh sửa hồ sơ được chỉ định hay không.  
**Tại sao xảy ra:** `[Authorize]` xác thực/policy ở mức endpoint không tự suy ra ownership của route resource.  
**Ảnh hưởng production:** User hợp lệ có thể thử GUID khác và upload tài liệu vào hồ sơ không được phép nếu không có authorization ở layer khác.  
**Cách sửa:** Thực hiện resource-based/policy authorization dựa trên employee/resource và caller claims trước mọi side effect.

### High — Tin vào extension và `ContentType` do client cung cấp

**Vấn đề:** Code xem metadata từ request như bằng chứng loại file.  
**Tại sao xảy ra:** Tên file và MIME metadata có thể bị client giả mạo; extension không xác minh nội dung.  
**Ảnh hưởng production:** File ngoài allowlist có thể được lưu dưới tên/type hợp lệ, tạo rủi ro khi download/render/scan pipeline xử lý nó.  
**Cách sửa:** Treat metadata as untrusted; kiểm tra kích thước, normalize allowlist, xác minh signature/content khi phù hợp và đưa file qua malware/content scanning policy theo threat model. Không phục vụ upload như executable/active content từ trusted origin.

### High — Không enforce giới hạn 25 MB trong application flow

**Vấn đề:** Không có check `file.Length` hay request-size policy thể hiện requirement 25 MB.  
**Tại sao xảy ra:** Code giả định upstream đã giới hạn request nhưng scenario không xác nhận điều đó.  
**Ảnh hưởng production:** Oversized request có thể tiêu tốn bandwidth, temporary storage/memory và làm giảm availability.  
**Cách sửa:** Enforce giới hạn ở hosting/request layer và application validation; không chỉ dựa vào một layer.

### High — Buffer toàn bộ file vào memory trước khi upload

**Vấn đề:** Mỗi request tạo `MemoryStream` chứa toàn bộ file.  
**Tại sao xảy ra:** Upload implementation không stream từ input sang storage.  
**Ảnh hưởng production:** Nhiều file lớn đồng thời gây allocation/GC pressure và có thể dẫn tới memory exhaustion/restart.  
**Cách sửa:** Stream với bounded resource usage; cấu hình upload/request limits và concurrency/backpressure phù hợp.

### High — Blob và SQL không có atomic transaction

**Vấn đề:** Blob được tạo trước khi metadata SQL commit.  
**Tại sao xảy ra:** Hai storage systems không nằm trong cùng local transaction.  
**Ảnh hưởng production:** SQL failure để lại orphan blob; retry có thể overwrite object cũ do deterministic client filename.  
**Cách sửa:** Thiết kế explicit state/workflow: generated object ID, pending metadata, cleanup/reconciliation hoặc compensating action. Không giả vờ có distributed atomicity.

### High — Client filename được dùng làm storage identity và `overwrite: true`

**Vấn đề:** Cùng filename cho cùng employee map tới cùng blob và silently overwrite.  
**Tại sao xảy ra:** User-controlled display name bị dùng làm unique storage key.  
**Ảnh hưởng production:** Mất phiên bản/tài liệu ngoài ý muốn; concurrent upload cùng tên tạo last-writer-wins khó dự đoán.  
**Cách sửa:** Sinh server-side immutable blob key (ví dụ document ID/random identifier); giữ original sanitized display name chỉ như metadata.

### Medium — Access model của `BlobUrl` không rõ và URL được trả trực tiếp

**Vấn đề:** Code lưu/trả URI nhưng không thể hiện container private/public hay download authorization.  
**Tại sao xảy ra:** Storage location bị coi như access-control mechanism.  
**Ảnh hưởng production:** Nếu container/public policy sai, sensitive document có thể bị truy cập ngoài application authorization.  
**Cách sửa:** Giữ container private; download qua authorized backend hoặc phát short-lived scoped access khi requirement cho phép. Dùng Managed Identity/least privilege cho backend.

### Medium — Logging có thể lộ metadata nhạy cảm

**Vấn đề:** Original filename và full blob URI được log.  
**Tại sao xảy ra:** Structured log không có data-classification policy.  
**Ảnh hưởng production:** Filename có thể chứa PII; URI/path có thể tiết lộ identifiers trong centralized logs.  
**Cách sửa:** Log document ID, result, size, normalized type và correlation; hạn chế user-provided/sensitive metadata.

### Medium — Thiếu validation cho empty/malformed filename và upload semantics

**Vấn đề:** Code không xác minh file null/empty, filename normalization hay business duplicate semantics.  
**Tại sao xảy ra:** Validation chỉ tập trung extension.  
**Ảnh hưởng production:** Dữ liệu metadata kém chất lượng và behavior khó dự đoán.  
**Cách sửa:** Validate required input, length, display filename và business constraints trước storage operation.

### Low — Response `Ok` không mô tả lifecycle của document

**Vấn đề:** Nếu hệ thống thêm scanning/quarantine, response hiện tại ngầm coi upload là usable ngay.  
**Tại sao xảy ra:** Không có explicit document state.  
**Ảnh hưởng production:** Client có thể hiển thị file trước khi security processing hoàn tất.  
**Cách sửa:** Nếu scanning là asynchronous, lưu trạng thái `PendingScan` và chỉ cho download sau khi accepted.

## Phiên bản đề xuất

```csharp
[Authorize]
[ApiController]
[Route("api/employees/{employeeId:guid}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxFileSize = 25L * 1024 * 1024;
    private readonly BlobContainerClient _container;
    private readonly EmployeeDbContext _db;
    private readonly IAuthorizationService _authorization;

    public DocumentsController(
        BlobContainerClient container,
        EmployeeDbContext db,
        IAuthorizationService authorization)
    {
        _container = container;
        _db = db;
        _authorization = authorization;
    }

    [HttpPost]
    public async Task<IActionResult> Upload(
        Guid employeeId,
        IFormFile file,
        CancellationToken ct)
    {
        var employee = await _db.Employees
            .SingleOrDefaultAsync(x => x.Id == employeeId, ct);

        if (employee is null)
            return NotFound();

        var auth = await _authorization.AuthorizeAsync(
            User, employee, "EditEmployeeDocuments");
        if (!auth.Succeeded)
            return Forbid();

        if (file is null || file.Length <= 0 || file.Length > MaxFileSize)
            return BadRequest("Invalid file size");

        var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
        if (extension is not ".pdf" and not ".docx" and not ".png")
            return BadRequest("Unsupported file type");

        // Content/signature scanning policy should run here or in a
        // quarantine workflow; client ContentType is not trusted evidence.
        var document = new EmployeeDocument
        {
            Id = Guid.NewGuid(),
            EmployeeId = employeeId,
            FileName = Path.GetFileName(file.FileName),
            UploadedAtUtc = DateTime.UtcNow,
            Status = DocumentStatus.PendingScan
        };

        var blobName = $"documents/{document.Id:N}";
        var blob = _container.GetBlobClient(blobName);

        await using var input = file.OpenReadStream(MaxFileSize);
        await blob.UploadAsync(input, overwrite: false, ct);

        document.BlobName = blobName;
        _db.EmployeeDocuments.Add(document);

        try
        {
            await _db.SaveChangesAsync(ct);
        }
        catch
        {
            await blob.DeleteIfExistsAsync(cancellationToken: ct);
            throw;
        }

        return Accepted(new { document.Id, document.Status });
    }
}
```

Đây là một skeleton minh họa boundary; production implementation vẫn cần request-size configuration, content/malware scanning strategy, cleanup/reconciliation nếu compensation thất bại, và download authorization. Không nên coi delete compensation là atomic transaction.

## Giải thích thiết kế sau khi sửa

Authorization diễn ra trước side effect. Storage key do server tạo và tách khỏi original filename. Upload được stream thay vì copy toàn bộ file vào một buffer riêng. Blob không được trả như public access contract; application giữ logical document ID và authorization boundary. Nếu threat model yêu cầu scanning, document đi qua trạng thái quarantine/pending trước khi download được phép.

## Trade-offs

Streaming và private storage làm implementation/download flow phức tạp hơn. Content scanning có thể tăng latency hoặc yêu cầu asynchronous workflow. Compensation/reconciliation thêm operational work nhưng phản ánh đúng việc SQL và Blob Storage không có một transaction atomic chung. Direct-to-Blob upload bằng scoped access có thể giảm tải backend ở scale lớn, nhưng khi đó authorization, size/type validation, finalization và orphan cleanup phải được thiết kế kỹ.

## Cách kiểm thử

1. **Security/integration test:** authenticated user không có quyền với `employeeId` nhận 403 và không tạo blob.
2. **Boundary test:** file 25 MB được chấp nhận, file vượt limit bị reject ở các layer mong muốn.
3. **Security test:** file có extension/MIME giả không được coi là trusted content; scanning/quarantine flow xử lý đúng.
4. **Load test:** nhiều upload lớn đồng thời không làm memory tăng tuyến tính theo tổng kích thước file buffered trong application.
5. **Failure-path test:** Blob success + SQL failure tạo compensation/reconciliation signal; Blob failure không tạo committed document metadata sai trạng thái.

## Quan sát trong production

Theo dõi upload count/result theo status, request size distribution, request duration p95/p99, process memory/GC, rejected oversized uploads, authorization failures, Blob dependency latency/error, scanning backlog/result và orphan-cleanup failures. Correlate request ID với logical document ID; tránh log nội dung file hoặc metadata nhạy cảm không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn browser upload trực tiếp tới Blob Storage thay vì proxy file qua ASP.NET Core API?
2. Nếu malware scanning mất 30 giây, bạn thiết kế document state và download authorization như thế nào?
3. Nếu cleanup blob sau SQL failure cũng thất bại, hệ thống phát hiện và sửa orphan objects ra sao?

# Code Review Challenge 2 — Kubernetes rollout báo healthy nhưng pod nhận traffic trước khi ứng dụng sẵn sàng

**Chủ đề:** Kubernetes, ASP.NET Core, probes, resource management, rolling deployment, configuration, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API trước đây chạy Azure App Service đang được team đánh giá Kubernetes như một hosting alternative. API cần khoảng 20–40 giây lúc startup để load configuration, warm một số metadata và xác minh database connectivity. Endpoint `/health` hiện trả 200 nếu process đang chạy.

Sau rollout, production-like environment thỉnh thoảng có 502/503 trong khoảng một phút. Khi dependency SQL chậm, pods mới restart nhiều lần. Team tăng replicas lên 8 nhưng symptom vẫn còn. Manifest dưới đây deploy thành công và `kubectl get pods` thường cho thấy pods `Running`.

3. Phân tích behavior khi startup chậm hoặc SQL tạm thời unavailable.
4. Ưu tiên findings theo severity.
5. Đề xuất manifest/health-check design tốt hơn.
6. Nêu cách test rolling deployment và dependency failure.
7. Nêu telemetry cần có trong production.

## Kết quả code review tham khảo

### Critical — Production credential hard-coded trong Deployment

**Vấn đề:** SQL username/password nằm trực tiếp trong manifest.  
**Tại sao xảy ra:** Configuration và secret management không được tách.  
**Ảnh hưởng production:** Secret có thể xuất hiện trong Git, CI logs, rendered manifests và người có quyền đọc workload spec.  
**Cách sửa:** Dùng secret-management mechanism phù hợp của platform/organization; trên Azure cân nhắc workload identity/Managed Identity khi dependency hỗ trợ, hoặc external secret integration. Kubernetes Secret không nên bị hiểu là đủ an toàn nếu lifecycle/RBAC/encryption không được quản lý.

### High — Liveness bắt đầu quá sớm và dùng dependency-sensitive health semantics

**Vấn đề:** Startup 20–40 giây nhưng liveness bắt đầu sau 5 giây; cùng `/health` còn được dùng cho readiness.  
**Tại sao xảy ra:** Startup, process liveness và traffic readiness bị gộp thành một signal.  
**Ảnh hưởng production:** Slow startup/dependency có thể gây restart loop, khiến pod không bao giờ ổn định.  
**Cách sửa:** Dùng `startupProbe` để bảo vệ startup window; liveness chỉ phản ánh process không thể tự phục hồi, readiness phản ánh khả năng nhận traffic.

### High — Readiness endpoint không thể hiện application readiness thực sự

**Vấn đề:** Scenario cho biết `/health` chỉ trả 200 nếu process chạy.  
**Tại sao xảy ra:** Probe endpoint không map với dependency/warmup requirements cần để phục vụ request.  
**Ảnh hưởng production:** Pod được đưa vào Service endpoints quá sớm và user nhận 5xx.  
**Cách sửa:** Readiness check phải phản ánh minimum conditions cần để phục vụ traffic, nhưng tránh biến mọi transient downstream issue thành global outage nếu API có thể degrade gracefully.

### High — Dùng mutable image tag `latest`

**Vấn đề:** Manifest không pin artifact version/digest.  
**Tại sao xảy ra:** Deployment identity phụ thuộc tag mutable.  
**Ảnh hưởng production:** Khó biết pod nào chạy binary nào, rollback/reproduce không đáng tin và environments có thể khác artifact.  
**Cách sửa:** Deploy immutable version tag hoặc image digest do CI tạo; promotion giữ cùng artifact.

### Medium — Không khai báo resource requests

**Vấn đề:** Chỉ có limits.  
**Tại sao xảy ra:** Scheduler thiếu explicit expected resource reservation.  
**Ảnh hưởng production:** Placement/capacity planning kém predictable; CPU limit thấp cũng có thể kéo dài startup nếu application cần burst CPU.  
**Cách sửa:** Đo CPU/memory thực tế rồi cấu hình `requests`/`limits` phù hợp; không chọn số tùy ý.

### Medium — RollingUpdate safety chưa được explicit

**Vấn đề:** Manifest không thể hiện `maxUnavailable`/`maxSurge` phù hợp với availability requirement.  
**Tại sao xảy ra:** Dựa vào defaults thay vì deployment SLO/capacity analysis.  
**Ảnh hưởng production:** Khi startup chậm hoặc capacity sát ngưỡng, rollout có thể làm giảm serving capacity.  
**Cách sửa:** Chọn rolling parameters dựa trên replicas, headroom và SLO; kết hợp readiness đúng để pod cũ chỉ được thay khi pod mới thực sự ready.

### Medium — Health probe timeout/cadence không dựa trên measured behavior

**Vấn đề:** `timeoutSeconds: 1` và cadence cố định chưa có evidence.  
**Tại sao xảy ra:** Probe tuning theo guess.  
**Ảnh hưởng production:** False negatives dưới CPU/dependency jitter tạo churn.  
**Cách sửa:** Đo health endpoint latency và chọn thresholds/failureThreshold phù hợp; health endpoint phải nhẹ.

### Medium — Không thể hiện graceful shutdown/draining behavior

**Vấn đề:** Manifest/code contract không cho thấy request draining và shutdown budget.  
**Tại sao xảy ra:** Chỉ tập trung startup.  
**Ảnh hưởng production:** Rolling termination có thể cắt request đang xử lý nếu application/ingress termination semantics không phù hợp.  
**Cách sửa:** Kiểm tra ASP.NET Core graceful shutdown, termination grace period và traffic draining behavior end-to-end.

Các resource/probe values trên chỉ là scenario starting point, không phải universal production values. Chúng phải được điều chỉnh bằng startup latency, workload profile và SLO thực tế. Production secret strategy cũng cần mạnh hơn việc chỉ chuyển plaintext sang một Kubernetes Secret nếu threat model yêu cầu.

## Giải thích thiết kế sau khi sửa

`startupProbe` cho application thời gian khởi động trước khi liveness can thiệp. Readiness và liveness có semantics khác nhau: readiness điều khiển traffic eligibility, còn liveness chỉ nên restart khi process thực sự unhealthy theo cách restart có khả năng giúp. Artifact được pin bằng immutable version để rollout/rollback truy vết được. Resource requests/limits phải dựa trên measurement.

## Trade-offs

`maxUnavailable: 0` cần cluster capacity cho surge pod và có thể làm rollout chậm nếu pod mới không ready. Readiness quá phụ thuộc SQL có thể loại toàn bộ pods khi database outage, trong khi một số endpoints vẫn có thể phục vụ degraded mode; readiness design phải theo service semantics. Startup window quá rộng làm phát hiện dead startup chậm hơn. Kubernetes cũng thêm operational complexity; nếu App Service đã đáp ứng scale/deployment requirements thì Kubernetes không tự động là lựa chọn tốt hơn.

## Cách kiểm thử

1. **Deployment validation:** rollout version mới với startup cố tình 40 giây; không có user traffic tới pod trước readiness.
2. **Failure-path test:** SQL unavailable lúc startup; xác minh behavior của startup/readiness/liveness đúng với recovery design và không tạo restart storm vô ích.
3. **Load test:** đo CPU/memory/startup latency để hiệu chỉnh requests/limits và probe thresholds.
4. **Rolling deployment test:** tạo traffic liên tục trong rollout và kiểm tra 5xx, in-flight request completion, serving capacity.
5. **Rollback test:** rollback về immutable image version trước và xác minh config/schema compatibility.

## Quan sát trong production

Theo dõi pod restart count/reasons, readiness transitions, startup duration, CPU throttling, memory working set/OOM, replica availability, deployment duration, request p95/p99 và 5xx theo pod/version. Correlate application logs/traces với pod name và image version. Alert khi rollout không progress, ready replicas giảm dưới SLO hoặc restart rate tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL outage kéo dài 10 phút nhưng API có một số read-only endpoints không cần SQL, readiness nên được thiết kế thế nào?
2. Khi nào Kubernetes complexity là justified so với tiếp tục dùng Azure App Service?
3. Nếu database migration của version mới không backward-compatible, rolling deployment và rollback sẽ gặp rủi ro gì?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication không thay thế resource-level authorization; file upload phải được coi là untrusted input từ metadata tới nội dung.
- Streaming và bounded resource usage quan trọng khi xử lý file lớn/concurrent requests; buffer toàn bộ payload dễ tạo memory pressure.
- Blob Storage và SQL không tự có một atomic transaction chung; cần explicit failure state, compensation hoặc reconciliation.
- Kubernetes `Running`, readiness, liveness và startup là các khái niệm khác nhau; probe sai semantics có thể tự tạo outage.
- Deployment an toàn cần immutable artifact, secret management, measured resource configuration, rollout và rollback validation.

## Mẫu tư duy cần nhớ

- Authenticate user, rồi authorize đúng resource trước side effect.
- Treat client metadata và external input as untrusted.
- Thiết kế failure path giữa các storage/dependency boundaries, không giả định atomicity.
- Phân biệt “process sống” với “service sẵn sàng nhận traffic”.
- Đo resource/startup behavior trước khi đặt production thresholds.
