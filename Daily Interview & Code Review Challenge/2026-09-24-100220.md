# Câu 1 — API export tăng memory: leak hay allocation pressure?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, GC, LOH, ASP.NET Core, memory profiling, performance

## Bối cảnh

Một ASP.NET Core API trên .NET 8 chạy Azure App Service. Endpoint export query SQL Server rồi trả JSON. Response thông thường khoảng 200 KB, nhưng một số tenant tạo payload 20–80 MB. Khi nhiều export chạy đồng thời, working set tăng, CPU có spike và p99 của cả endpoint nhỏ cũng xấu đi. Sau request, RAM không lập tức trở về baseline; restart process làm memory giảm. Chưa có heap dump hay allocation profile.

Một developer kết luận đây chắc chắn là memory leak; người khác muốn gọi `GC.Collect()` sau mỗi export.

## Câu hỏi chính

Giải thích hiện tượng ở mức .NET runtime, phân biệt memory leak, high allocation/retention, LOH và memory runtime giữ lại; bạn sẽ thu thập evidence nào để xác minh trước khi tối ưu?

## Câu hỏi làm rõ nên cân nhắc

1. Managed heap/live object size và process working set có cùng tăng không?
2. Endpoint materialize bao nhiêu bản dữ liệu/buffer trước khi response được gửi?
3. Payload distribution và concurrency thực tế là bao nhiêu?
4. Có static cache, singleton hoặc event handler giữ reference sau request không?
5. Allocation rate, Gen2 count, GC pause và LOH size thay đổi thế nào trong incident?

## Gợi ý tư duy

### Gợi ý 1

“RAM chưa giảm” chưa đủ chứng minh leak; cần biết object còn reachable hay memory chỉ đang được runtime/process giữ để tái sử dụng.

### Gợi ý 2

Tính peak memory theo payload, temporary copies và concurrent requests; liên hệ allocation lớn với GC/LOH pressure.

### Gợi ý 3

Leak cần evidence về live objects và retention path/root qua thời gian, không chỉ một memory chart.

## Cấu trúc trả lời đề xuất

1. Làm rõ metric.
2. Nêu các giả thuyết.
3. Giải thích allocation/GC/LOH liên quan.
4. Correlate runtime metrics với request size/concurrency.
5. Reproduce.
6. Capture allocation profile và heap evidence.
7. Xác định root cause.
8. Chọn fix.
9. Load-test lại.
10. Monitor regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- GC thu hồi object không đồng nghĩa working set phải giảm ngay.
- Phải phân biệt live heap với process memory.
- Payload lớn và concurrency có thể tạo allocation pressure mà không có leak.
- Không dùng `GC.Collect()` như default fix.
- Cần profiling/heap evidence trước khi kết luận.

### Điểm cộng

- Nhận ra query materialization + DTO + serialization có thể tạo nhiều copies/buffers.
- Cân nhắc streaming, projection, concurrency limits hoặc async export artifact.
- Pooling chỉ dùng khi profiling chứng minh hotspot và ownership rõ.

### Senior+

- Tính memory amplification theo concurrent workload.
- Dùng retention path để chứng minh leak.
- Đánh giá lại synchronous giant-JSON contract thay vì chỉ micro-optimize.

## Hướng giải quyết tham khảo

Working set là metric process/OS, không phải trực tiếp “số object .NET còn sống”. Object managed chỉ collect được khi không còn reachable, nhưng sau collection runtime có thể giữ heap segments/committed memory để phục vụ allocation tiếp theo. Ngoài managed heap còn có native/runtime buffers và các thành phần khác. Vì vậy working set không giảm ngay không đủ chứng minh leak.

Với response 20–80 MB, cần kiểm tra pipeline có materialize query result, DTO graph và serialization buffer hay không. Nhiều request lớn chạy đồng thời có thể đẩy allocation rate, LOH và Gen2 pressure lên cao, kéo theo CPU/GC pause và p99 xấu cho request khác. Đây có thể là allocation/throughput problem dù object cuối cùng vẫn chết.

Tôi sẽ correlate managed heap size, allocation rate, Gen0/1/2 collections, GC pause/time-in-GC, LOH size, CPU và request concurrency. Reproduce bằng payload representative; allocation profiling tìm type tạo nhiều bytes, còn heap snapshots/dump ở nhiều thời điểm cho biết live type nào tăng và root nào giữ chúng. Nếu object graph tăng qua nhiều cycles và có root từ static/singleton/cache/event subscription thì mới có evidence mạnh cho retention leak.

Nếu root cause là peak allocation, ưu tiên sửa data flow: project field cần thiết, tránh copies, stream khi semantics/tooling cho phép, giới hạn concurrent expensive exports hoặc chuyển export lớn thành background job tạo Blob artifact. Nếu business bắt buộc synchronous JSON thì benchmark và đặt guardrail phù hợp.

Không gọi `GC.Collect()` sau mỗi request theo phản xạ vì forced collections có thể tăng pause và phá heuristic. Không áp dụng `ArrayPool<T>` đại trà: pooling tăng ownership complexity và có thể giữ buffer lớn lâu hơn.

Sau fix, chạy cùng workload và so allocation/request, heap peak, GC pause, throughput và p95/p99. Một heap đạt plateau với live objects ổn định khác căn bản với retained live objects tăng không giới hạn.

## Mẫu trả lời trong phỏng vấn

“Em chưa gọi đây là leak chỉ từ working set. Em sẽ tách process memory khỏi managed live heap. GC có thể thu hồi object nhưng runtime vẫn giữ memory để tái sử dụng. Với export 20–80 MB, em nghi high allocation trước: query materialization, DTO và serialization có thể tạo nhiều buffer, rồi concurrency khuếch đại peak memory và GC pressure.

Em sẽ correlate allocation rate, heap/LOH, Gen2 và GC pause với payload/concurrency, sau đó profile allocations và lấy heap snapshots để tìm live type và retention root. Nếu object còn bị giữ qua nhiều cycles thì xử lý leak; nếu object chết nhưng allocation quá lớn thì sửa data flow bằng projection, streaming hoặc async export và concurrency control. Em sẽ không thêm `GC.Collect()` hay pooling trước khi có evidence. Cuối cùng load-test lại và so p99, allocation/request, heap peak và time-in-GC.”

## Câu hỏi đào sâu

1. Live managed heap thấp nhưng process memory vẫn cao: bạn mở rộng investigation sang đâu?
2. Streaming giảm peak memory nhưng giữ connection lâu hơn; trade-off là gì?
3. Nếu business bắt buộc response 80 MB đồng bộ, bạn đặt guardrail nào?

## Lỗi trả lời thường gặp

- Gọi working-set growth là leak ngay.
- Nói LOH “không bao giờ collect”.
- Dùng `GC.Collect()` như fix mặc định.
- Pooling trước profiling.
- Bỏ qua concurrency và contract của export.

## Thang điểm 0–10

**0–2:** Chỉ restart/force GC.  
**3–4:** Hiểu GC cơ bản nhưng thiếu evidence.  
**5–6:** Có allocation/LOH/profiling reasoning.  
**7–8:** Có retention path, concurrency, test và telemetry.  
**9–10:** Kết nối runtime evidence với architecture/contract và trade-offs.

# Câu 2 — Search nhanh nhưng product vẫn stale 20 phút

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, eventual consistency, background processing, observability, incident response

## Bối cảnh

SQL Server là source of truth cho vài triệu products; Elasticsearch phục vụ search. Sau product update, application commit SQL rồi gửi công việc indexing sang background pipeline. Sau một release, một phần product hiển thị giá/availability cũ trong search 10–20 phút, trong khi product detail đọc SQL và đúng. Elasticsearch search p95 vẫn bình thường. Team chưa đo backlog age, indexing lag, retry/DLQ hoặc version drift.

Một engineer muốn full reindex ngay; người khác muốn chuyển search sang SQL.

## Câu hỏi chính

Bạn là on-call engineer. Hãy xử lý incident theo impact → stabilize → evidence → competing hypotheses → verification → remediation → prevention, và phân biệt lỗi producer, background pipeline, Elasticsearch indexing và read/query layer mà không giả định sẵn root cause.

## Câu hỏi làm rõ nên cân nhắc

1. Có failure window giữa SQL commit và durable publish không?
2. Product stale có pattern theo partition/category/time/worker không?
3. Backlog, oldest-message age, retries và DLQ hiện thế nào?
4. Document có source version/timestamp để so với SQL không?
5. Release đổi event schema, mapping, alias/index hay worker deployment gì?

## Gợi ý tư duy

### Gợi ý 1

Search latency khỏe không chứng minh index fresh.

### Gợi ý 2

Trace một product từ SQL commit → work item → consumer → indexed document → query.

### Gợi ý 3

Tách lost event, backlog/retry, indexing reject/out-of-order và writer/reader alias mismatch thành các giả thuyết cạnh tranh.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius/freshness SLO.
2. Stabilize theo business risk.
3. Chọn stale/fresh samples.
4. Trace từng hop.
5. So competing hypotheses.
6. Verify bằng version/timestamp/trace.
7. Repair current drift.
8. Fix root cause.
9. Failure-test.
10. Add freshness telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không dùng search latency làm freshness signal.
- Không full reindex trước khi biết blast radius.
- Trace entity end-to-end.
- Xem lost publish, backlog, retry, mapping/alias và out-of-order.
- Có recovery cho data đã stale.

### Điểm cộng

- Source version + idempotent upsert.
- Outbox nếu có SQL/publish dual-write window.
- Oldest-message age/end-to-end lag quan trọng hơn queue depth đơn lẻ.
- Reconcile subset trước full reindex.

### Senior+

- Phân biệt availability/latency SLO với freshness SLO.
- Periodic reconciliation phát hiện drift.
- Versioned index + alias cutover/rollback khi mapping migration liên quan.

## Hướng giải quyết tham khảo

Đầu tiên xác định blast radius, loại dữ liệu stale và commercial risk. Không chuyển toàn search sang SQL hoặc full reindex trước evidence vì có thể tạo incident thứ hai.

Chọn vài stale và fresh products cùng thời gian update. Với mỗi product, so SQL version/timestamp, event/work item, consumer trace/log và document version/index. Các hypothesis gồm: SQL commit nhưng publish bị mất; work tồn tại nhưng backlog/retry/poison; Elasticsearch reject/mapping error; event cũ ghi đè event mới; writer ghi index A trong khi reader query alias/index B; hoặc cache/query layer trả snapshot cũ.

Nếu queue backlog, đo arrival rate, processing rate, oldest age, retry/error class trước khi scale consumer; downstream Elasticsearch phải chịu được throughput tăng. Nếu event có thể mất giữa SQL commit và publish, transactional Outbox là một hướng để product change và outbox record commit cùng transaction. Outbox không tạo exactly-once: publisher/consumer vẫn cần idempotency và xử lý duplicate/out-of-order.

Recovery phải repair drift hiện tại. Có thể tìm products có source version mới hơn indexed version rồi replay/reconcile có kiểm soát. Full reindex chỉ khi evidence cho thấy drift rộng hoặc mapping/index migration yêu cầu; versioned index + alias giúp cutover/rollback rõ hơn.

Prevention gồm indexing success/failure, retries/DLQ, backlog age, end-to-end indexing lag, worker throughput, bulk reject/error và sampled version drift. Test crash sau DB commit, duplicate/out-of-order event, Elasticsearch timeout/429, malformed document, worker restart và alias switch.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không reindex toàn bộ ngay. Search p95 bình thường chỉ chứng minh read path nhanh. Em xác định blast radius và freshness SLO, rồi chọn stale/fresh products để trace SQL version qua event, worker và Elasticsearch document.

Em giữ nhiều giả thuyết: lost event sau SQL commit, backlog/retry, Elasticsearch reject, out-of-order update hoặc writer/reader dùng khác alias. Nếu dual-write làm mất event, em cân nhắc Outbox nhưng consumer vẫn phải idempotent. Nếu backlog là vấn đề, em đo oldest age và throughput trước khi scale.

Để sửa dữ liệu hiện tại, em reconcile/replay những product có indexed version thấp hơn source version; full reindex chỉ khi evidence yêu cầu. Sau incident em thêm indexing lag, retries/DLQ, version drift và failure-path tests.”

## Câu hỏi đào sâu

1. Queue depth thấp nhưng stale age vẫn 30 phút: hypothesis thay đổi thế nào?
2. Bạn ngăn event cũ overwrite document mới thế nào?
3. Vì sao Outbox vẫn cần idempotency/reconciliation?

## Lỗi trả lời thường gặp

- Full reindex ngay.
- Chỉ nhìn Elasticsearch cluster/search latency.
- Scale consumer không đo downstream.
- Nói Outbox = exactly-once.
- Fix future pipeline nhưng bỏ quên current drift.

## Thang điểm 0–10

**0–2:** Restart/reindex theo đoán.  
**3–4:** Có log/queue nhưng thiếu competing hypotheses.  
**5–6:** Trace end-to-end và hiểu eventual consistency.  
**7–8:** Có versioning/idempotency/reconciliation/telemetry.  
**9–10:** Incident reasoning theo risk và freshness SLO, recovery an toàn.

# Câu 3 — Modernize .NET Framework/IIS mà không biến migration thành rewrite

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** .NET modernization, IIS/Windows Server, modern .NET, Azure App Service, architecture, CI/CD, testing, rollback

## Bối cảnh

Một employee platform 8 năm tuổi chạy ASP.NET MVC trên .NET Framework 4.5 và IIS/Windows Server, gồm attendance, timesheet, approval workflow và scheduled jobs. SQL Server dùng chung; khoảng 150 nghìn dòng code. Một số internal libraries chỉ hỗ trợ .NET Framework; authentication phụ thuộc Windows-integrated behavior.

Business muốn chuyển sang supported modern .NET, cải thiện deployment và giảm production risk nhưng không chấp nhận freeze feature development một năm. Release mỗi hai tuần; test automation yếu. Team đưa ba proposal: rewrite .NET 10 + React + Kubernetes; nâng dần monolith lên modern .NET/App Service; hoặc tách microservices trong lúc migrate. Chưa có inventory rõ về coupling, Windows dependencies hay scale requirement.

## Câu hỏi chính

Bạn xây migration strategy và decision framework thế nào để modernize an toàn mà không mặc định rewrite, Microservices hoặc Kubernetes là đích đến? Hãy xét compatibility, boundaries, testing, deployment, data/schema, authentication, observability và rollback.

## Câu hỏi làm rõ nên cân nhắc

1. Dependency/API nào thật sự khóa hệ thống vào Framework/Windows/IIS?
2. Coupling code/database/jobs giữa modules ra sao?
3. Authentication target cần giữ Windows behavior hay chuyển Microsoft Entra ID?
4. Downtime/SLO/rollback requirement của critical workflows là gì?
5. Hiện có characterization/integration/E2E tests nào đủ bảo vệ behavior?

## Gợi ý tư duy

### Gợi ý 1

Inventory blockers và business outcomes trước khi chọn target architecture.

### Gợi ý 2

Tách runtime modernization khỏi architecture decomposition.

### Gợi ý 3

Ưu tiên slices có thể coexist/rollback; shared DB + weak tests có thể làm premature microservices tăng risk.

## Cấu trúc trả lời đề xuất

1. Clarify outcomes/SLO.
2. Inventory dependencies/hosting/auth/jobs.
3. Baseline behavior/tests/telemetry.
4. Classify blockers.
5. Chọn target tối thiểu đủ requirement.
6. Pilot low-risk slice.
7. Thiết kế coexistence/schema compatibility.
8. Incremental rollout.
9. Test rollback.
10. Decompose chỉ khi value/boundary rõ.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Modern .NET không đồng nghĩa Microservices/Kubernetes.
- Inventory dependency compatibility trước estimate.
- Characterization/integration tests là migration control.
- Có coexistence và rollback.
- Schema transition phải xét old/new versions.

### Điểm cộng

- Scheduled jobs được đánh giá riêng khỏi IIS lifecycle.
- App Service/Linux chỉ sau khi loại Windows blockers.
- Auth migration là workstream riêng.
- Có vertical-slice/strangler khi boundary phù hợp.

### Senior+

- Scorecard risk/value/coupling/testability.
- Tách source modernization, runtime upgrade, hosting migration, architecture redesign.
- Có exit criteria và chấp nhận dừng ở Modular Monolith nếu mục tiêu đã đạt.

## Hướng giải quyết tham khảo

Không chọn rewrite/Kubernetes trước discovery. Đầu tiên xác định outcomes: supported runtime, release safety, deployment time, incident rate, security posture và feature velocity. Inventory project types, NuGet/internal libraries, System.Web/IIS/Windows dependencies, auth, filesystem, scheduled jobs, config/secrets, SQL coupling và external integrations. Phân loại blocker thành upgrade, replace, isolate hoặc redesign.

Vì automation yếu, xây safety net quanh critical workflows bằng characterization/integration tests và một số Playwright E2E cho user journeys quan trọng; baseline production latency/error để so trước/sau.

Tách runtime modernization khỏi decomposition. Nếu monolith vẫn đáp ứng scale và ownership, modernize nó có thể tạo phần lớn value mà không thêm network/messaging/distributed operations. Chỉ extract module khi boundary và independent deployment/scaling/ownership mang value rõ.

Migration theo slices có rollback. Old/new có thể coexist qua adapter/seam; shared schema cần additive/expand-contract khi hai versions chạy đồng thời. Scheduled jobs cần xem lại lifecycle/retry/idempotency; chuyển Worker Service/Functions chỉ khi execution model phù hợp, không phải vì “modern hơn”.

Hosting là decision riêng. Azure App Service có thể đủ và giảm operational overhead. Linux chỉ khi Windows-specific dependencies đã xử lý. Kubernetes chỉ khi orchestration requirements và team capability biện minh cho complexity.

Authentication migration cần map identity/claims/authorization, security tests và rollout strategy riêng. Mỗi phase có exit criteria: functional parity, error/latency không regress ngoài threshold, rollback tested, telemetry đủ và deployment reproducible.

Nếu sau runtime/hosting modernization monolith đã giải quyết support, deployment và reliability pain, có thể dừng. Architecture tốt là architecture đạt requirement với complexity thấp hợp lý.

## Mẫu trả lời trong phỏng vấn

“Em tách bài toán thành runtime, dependencies, hosting và architecture. Upgrade Framework không có nghĩa phải rewrite hay Microservices.

Đầu tiên em inventory blockers: libraries, System.Web/IIS/Windows APIs, auth, scheduled jobs và shared SQL coupling. Vì test đang yếu, em tạo characterization/integration tests và vài Playwright E2E cho critical flows, cộng baseline telemetry.

Sau đó em pilot một slice trên modern .NET, giữ old/new coexist được và schema backward-compatible trong transition. Nếu monolith trên App Service đáp ứng SLO thì đó có thể là target đủ tốt. Em chỉ extract service khi có boundary và business/operational value rõ; Kubernetes cũng phải có requirement riêng.

Auth và scheduled jobs là workstream cần test kỹ. Mỗi phase phải rollback được và có measurable exit criteria. Nếu modernized monolith đã giải quyết pain, em sẽ không tiếp tục phân tán hệ thống chỉ vì roadmap từng ghi microservices.”

## Câu hỏi đào sâu

1. Một business-critical library chỉ chạy Framework thêm 12 tháng: làm sao không chặn toàn migration?
2. Team nói Kubernetes chắc chắn rollback tốt hơn App Service; bạn cần evidence gì?
3. Old/new cùng ghi shared SQL sáu tháng: schema evolution/ownership thiết kế thế nào?

## Lỗi trả lời thường gặp

- Rewrite vì code cũ “xấu” mà không định lượng.
- Đồng nhất modernization với microservices/Kubernetes.
- Estimate trước dependency discovery.
- Không có schema coexistence/rollback.
- Bỏ qua auth, jobs và Windows-specific behavior.

## Thang điểm 0–10

**0–2:** Tool-driven rewrite, thiếu risk analysis.  
**3–4:** Có phases nhưng thiếu compatibility/testing.  
**5–6:** Inventory và incremental strategy hợp lý.  
**7–8:** Có coexistence, auth/schema/testing/observability và conditional hosting.  
**9–10:** Cân bằng continuity, complexity và measurable exit criteria.
