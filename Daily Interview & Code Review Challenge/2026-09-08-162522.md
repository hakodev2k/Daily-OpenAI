# Câu 1 — Redis trả dữ liệu “đúng key nhưng sai version”: serialization, cache-aside và invalidation đang hỏng ở đâu?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** Redis, ASP.NET Core, serialization, cache-aside, TTL, cache key design, deployment compatibility, observability

## Bối cảnh

Một ASP.NET Core API trên .NET 8 dùng Redis theo cache-aside để đọc `ProductDetailDto`. Sau một release, DTO đổi từ:

```csharp
public sealed record ProductDetailDto(
    Guid Id,
    string Name,
    decimal Price);
```

thành:

```csharp
public sealed record ProductDetailDto(
    Guid Id,
    string Name,
    MoneyDto Price,
    IReadOnlyList<string> Badges);
```

Trong rolling deployment, old và new application instances cùng chạy vài phút. Production xuất hiện:

- một số request deserialize fail;
- một số request vẫn thành công nhưng thiếu `Badges`;
- purge Redis toàn bộ làm hệ thống ổn ngay nhưng database load tăng mạnh;
- sau vài phút lỗi xuất hiện lại lẻ tẻ;
- cache key hiện có dạng `product:{id}`;
- TTL là 30 phút;
- mỗi instance dùng cùng Redis cluster;
- một developer đề xuất bật `ReferenceHandler.IgnoreCycles`;
- một developer khác muốn bỏ TTL để giảm database traffic.

Chưa biết chắc:

- serializer settings có giống nhau giữa các versions không;
- old/new versions có cùng ghi vào cùng key không;
- cache payload có schema/version marker không;
- code xử lý deserialize failure hiện fail request hay fallback database;
- cache invalidation xảy ra khi product update như thế nào;
- release có cho phép old/new binary cùng tồn tại bao lâu.

## Câu hỏi chính

Hãy giải thích vì sao cùng một Redis key có thể chứa payload hợp lệ với version A nhưng không tương thích với version B, tại sao TTL hoặc purge không giải quyết root cause, và bạn sẽ thiết kế cache key/versioning/fallback/deployment compatibility như thế nào để rolling deployment an toàn.

## Câu hỏi làm rõ nên cân nhắc

1. Old và new application versions có cùng read/write key trong cùng thời gian không?
2. JSON contract thay đổi có backward/forward compatible không?
3. Deserialize failure hiện có metric/log riêng hay chỉ thành HTTP 500?
4. Cache invalidation dựa trên TTL hay có event/update path rõ ràng?
5. Business có chấp nhận temporary cache miss để đảm bảo correctness không?

## Gợi ý tư duy

### Gợi ý 1

Redis chỉ lưu bytes; type safety và schema compatibility nằm ở application contract.

### Gợi ý 2

Rolling deployment biến cache payload thành shared contract giữa nhiều application versions.

### Gợi ý 3

Một cache entry lỗi nên được coi là disposable derived state, không phải nguồn dữ liệu duy nhất.

## Cấu trúc trả lời đề xuất

1. Làm rõ rolling-deployment overlap và serializer contract.
2. Giải thích bytes → deserialize → object graph ở mỗi version.
3. Xác định overwrite/read race giữa versions.
4. Thu thập payload/version/evidence.
5. Thiết kế versioned key hoặc compatible envelope.
6. Thiết kế fallback khi deserialize/miss.
7. Thiết kế invalidation/TTL theo business freshness.
8. Đánh giá deploy strategy.
9. Test mixed-version rollout.
10. Monitor cache errors/hit ratio/database fallback.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Redis không biết schema C#; cùng key có thể bị các application versions hiểu khác nhau.
- Old/new instances cùng ghi một key có thể liên tục thay payload format.
- TTL chỉ giới hạn lifetime; không ngăn version A ghi payload mà version B không đọc được.
- Purge toàn cache chỉ là mitigation tạm thời nếu incompatible writers vẫn chạy.
- Cache là derived data; deserialize failure nên có safe fallback về source of truth nếu phù hợp.
- Cache key/version hoặc payload envelope phải thể hiện schema contract khi breaking change tồn tại.
- Không để cache failure biến thành system-wide outage nếu database có thể phục vụ trong giới hạn capacity.
- Cần quan sát cache hit/miss, deserialize failures, fallback rate và database load.

### Điểm cộng

- Dùng key như `product:v2:{id}` trong breaking migration rồi retire `v1` sau rollout.
- Hoặc giữ backward-compatible payload contract trong window old/new cùng tồn tại.
- Có bounded protection để fallback storm không làm database quá tải.
- Dùng jittered TTL khi nhiều keys cùng expire để giảm synchronized misses.
- Phân biệt schema versioning với business-data invalidation.

### Senior+

- Thiết kế read path có thể thử v2 → source of truth thay vì v2 → v1 mù quáng nếu semantics khác.
- Phân tích cache warmup/cutover và rollback: new binary rollback phải đọc được cache state nào.
- Định nghĩa contract test chạy old/new serializers trên cùng fixtures.
- Cân nhắc dual-read/dual-write chỉ khi migration complexity thực sự cần, không mặc định.

## Hướng giải quyết tham khảo

Redis không lưu `ProductDetailDto`; nó chỉ lưu serialized bytes. Type/schema được application hiểu ở thời điểm deserialize. Khi old và new instances cùng dùng `product:{id}`, instance cũ có thể ghi payload dạng `Price: 12.34`, instance mới lại kỳ vọng `Price: { amount, currency }`. Ngược lại instance mới có thể ghi shape mà instance cũ không hiểu. Vì vậy lỗi có thể lẻ tẻ theo instance nào vừa ghi key gần nhất.

Tôi sẽ lấy một vài cache entries lỗi và correlate với application version đã write nếu telemetry có. Tôi cũng test serializer old/new với payload của nhau để xác định backward/forward compatibility thay vì đoán.

Nếu change là breaking, phương án đơn giản và rõ thường là version key: `product:v2:{id}`. New version chỉ đọc/ghi v2; old version tiếp tục v1 trong overlap. Sau khi rollout hoàn tất và rollback window đóng, v1 tự expire hoặc được purge có kiểm soát. Nếu rollback vẫn phải hỗ trợ, tôi giữ v1 đủ lâu hoặc đảm bảo rollback binary không phụ thuộc v2.

Deserialize failure ở cache nên được xử lý như cache miss khi source of truth còn khả dụng: log structured event, xóa/ignore entry hỏng nếu an toàn, đọc database rồi repopulate đúng version. Nhưng cần rate limit/circuit/bulkhead phù hợp để Redis corruption/outage không gây database stampede.

TTL không phải schema migration mechanism. TTL phục vụ freshness/eviction policy. Tương tự, bỏ TTL làm incompatible payload sống lâu hơn và tăng stale-data risk.

Nếu muốn tránh versioned key, một lựa chọn khác là stable envelope có `schemaVersion` và backward-compatible DTO evolution, nhưng điều đó đòi hỏi contract discipline rõ. Tôi chọn phương án ít complexity nhất đáp ứng rollback/rollout requirement.

Testing cần có mixed-version integration test: old writer/new reader, new writer/old reader, Redis unavailable, corrupted payload, mass expiry và rollback. Production metrics cần cache deserialize failure, miss/fallback rate, hit ratio, Redis latency/error, database QPS và p95/p99.

## Mẫu trả lời trong phỏng vấn

“Em sẽ coi cache payload là shared contract giữa application versions. Redis chỉ giữ bytes; nếu old và new instances cùng dùng `product:{id}` nhưng DTO/serializer không tương thích thì instance nào ghi cuối có thể làm instance khác deserialize fail. Purge hoặc TTL chỉ xử lý tạm thời vì incompatible writer vẫn tồn tại.

Em sẽ verify bằng cách lấy payload thực tế và test old/new serializers. Với breaking change, em ưu tiên version key như `product:v2:{id}` hoặc duy trì backward-compatible contract trong rollout window. Cache deserialize failure được xử lý như cache miss nếu source of truth còn an toàn, nhưng phải monitor fallback để không tạo database stampede.

Em cũng test mixed-version rollout và rollback, theo dõi deserialize errors, hit ratio, Redis latency và database QPS. TTL dùng cho freshness, không dùng thay schema versioning.”

## Câu hỏi đào sâu

1. Nếu rollback từ v2 về v1 sau 20 phút, bạn bảo đảm v1 không đọc nhầm cache state do v2 để lại thế nào?
2. Một teammate đề xuất dual-write cả `v1` và `v2` trong mọi request; khi nào điều đó đáng làm và khi nào là overengineering?
3. Nếu Redis down và toàn bộ requests fallback SQL, bạn bảo vệ database khỏi thundering herd thế nào?

## Lỗi trả lời thường gặp

- Cho rằng Redis hiểu C# type/schema.
- Purge toàn cache nhưng không sửa incompatible read/write contract.
- Bỏ TTL để “ổn định cache”.
- Catch deserialize exception rồi trả null im lặng, không telemetry.
- Version key nhưng không nghĩ tới rollback window.

## Thang điểm 0–10

- **0–2:** Chỉ purge Redis hoặc đổi serializer setting.
- **3–4:** Nhận ra version mismatch nhưng thiếu rollout/fallback design.
- **5–6:** Có versioned contract, fallback, TTL/invalidation distinction và testing.
- **7–8:** Có rollback compatibility, anti-stampede và observability tốt.
- **9–10:** Kết nối serialization contract, deployment overlap, cache failure semantics và recovery thành thiết kế có điều kiện rõ.

# Câu 2 — IIS Application Pool recycle liên tục, user bị đăng xuất và request thỉnh thoảng 502

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET, ASP.NET Core hosting, App Pool recycling, process lifetime, session, health, logs, incident response

## Bối cảnh

Một enterprise portal legacy chạy trên Windows Server/IIS. Hệ thống gồm:

- một ASP.NET MVC .NET Framework module cũ;
- một ASP.NET Core module mới chạy sau IIS reverse proxy;
- authentication dùng cookie;
- một số session/cache state vẫn giữ in-process;
- deployment qua Octopus Deploy;
- traffic tăng mạnh vào giờ hành chính.

Gần đây user báo:

- thỉnh thoảng bị đăng xuất giữa phiên;
- một số request trả 502/503 theo đợt;
- background work chạy trong web process đôi lúc bị dở dang;
- Windows Event Viewer cho thấy worker process restart nhiều lần;
- IIS logs có gap ngắn quanh thời điểm incident;
- memory của process có lúc tăng nhưng chưa chắc vượt limit;
- App Pool có cấu hình periodic recycle;
- deployment cũng đôi lúc trigger restart;
- team đề xuất tắt recycle hoàn toàn.

Chưa biết chắc:

- recycle do scheduled interval, private memory limit, config change, idle timeout hay crash;
- ASP.NET Core process có out-of-process hay in-process hosting;
- cookie keys/data protection có shared/persisted đúng không;
- session state nằm ở process nào;
- background work có durable queue hay fire-and-forget trong web process;
- overlapped recycling có được bật và startup time bao lâu;
- 502 là do process unavailable, reverse-proxy timeout hay dependency khác.

## Câu hỏi chính

Bạn sẽ stabilize incident, xác định chính xác trigger nào làm App Pool/process restart và liên hệ nó với logout/502/background-work loss ra sao? Sau đó hãy thiết kế process-lifetime, session/auth state, deployment và background processing để recycle/restart trở thành failure mode có thể chịu được thay vì phải “không bao giờ restart”.

## Câu hỏi làm rõ nên cân nhắc

1. Event Viewer/IIS logs/WAS events ghi reason code gì cho từng recycle?
2. Logout là cookie mất hiệu lực hay server-side session mất state?
3. Data Protection keys có persisted/shared giữa instances/processes không?
4. Background work có thể retry/idempotent hay hiện mất hoàn toàn khi process dừng?
5. Startup/warmup time và overlapped recycle behavior hiện tại thế nào?

## Gợi ý tư duy

### Gợi ý 1

Recycle là process-lifecycle event; vấn đề là application có đang phụ thuộc quá mức vào process-local state hay không.

### Gợi ý 2

Một triệu chứng “logout” có thể đến từ session loss, cookie encryption key mismatch hoặc auth dependency — cần phân biệt bằng evidence.

### Gợi ý 3

Tắt recycle có thể che symptom nhưng làm mất guardrail hoặc không xử lý crash/deployment restart.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact.
2. Correlate recycle timestamp với 5xx/logout/background gaps.
3. Thu reason code, process exit và hosting evidence.
4. Tách hypotheses: scheduled recycle, memory, crash, config/deploy, idle timeout.
5. Stabilize bằng targeted configuration hoặc rollback nếu cần.
6. Externalize critical auth/session state.
7. Di chuyển durable background work khỏi web-process lifecycle.
8. Thiết kế warmup/health/deployment behavior.
9. Test recycle/restart chủ động.
10. Monitor process lifecycle và user impact.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định mọi recycle là memory leak.
- Phải lấy recycle reason/process exit evidence từ IIS/WAS/Event Viewer/telemetry.
- Process restart có thể làm mất in-memory session/cache/background state.
- Authentication cookie correctness không nên phụ thuộc vào ephemeral per-process key material nếu cần survive restart/multiple instances.
- Background work quan trọng không nên fire-and-forget trong web process nếu phải durable.
- Tắt recycle hoàn toàn không phải root-cause fix mặc định.
- Deployment/restart phải có warmup/health và graceful behavior phù hợp.
- Cần correlation giữa process lifecycle với HTTP 5xx và login/session telemetry.

### Điểm cộng

- Phân biệt cookie authentication ticket với server-side session state.
- Dùng persisted/shared Data Protection keys cho ASP.NET Core khi topology yêu cầu.
- Chuyển durable jobs sang queue + worker/Function/Windows Service phù hợp, có idempotency.
- Kiểm tra app pool idle timeout, rapid-fail protection, periodic restart và memory limits riêng biệt.
- Xem startup latency/reverse-proxy health khi recycle overlap không đủ.

### Senior+

- Phân tích coexistence .NET Framework + ASP.NET Core: state/key/session boundaries có thể khác nhau.
- Thiết kế chaos/recycle test trong staging để chứng minh state survival.
- Có runbook phân biệt planned recycle, deployment restart và crash.
- Cân nhắc migrate khỏi IIS chỉ khi hosting pain thực sự là bottleneck, không vì trend.

## Hướng giải quyết tham khảo

Đầu tiên tôi correlate timestamp: khi user logout/502 xảy ra có đúng lúc worker process restart không. Tôi lấy IIS/WAS/Event Viewer reason codes, process exit code, deployment timeline, memory/CPU và application logs. Nếu periodic recycle xảy ra đúng lịch nhưng logout chỉ xảy ra ở một module, đó là clue về process-local auth/session state hơn là network issue.

Tôi không tắt recycle trước khi biết nguyên nhân. Nếu restart do private-memory limit hoặc crash, tắt scheduled recycle không giải quyết. Nếu chính scheduled recycle gây capacity gap vì startup quá chậm, có thể điều chỉnh schedule/overlap/warmup như mitigation trong khi sửa design.

Logout phải tách hai lớp. Cookie có thể vẫn tồn tại ở browser nhưng server không decrypt/validate được nếu key material thay đổi. Với ASP.NET Core, Data Protection keys cần được persisted/shared phù hợp topology. Ngược lại nếu auth cookie vẫn hợp lệ nhưng app phụ thuộc session in-memory, user có thể mất workflow state mà không thật sự mất authentication.

Critical session/state nên được externalize nếu cần survive recycle/multiple instances. Nhưng không phải mọi cache phải chuyển Redis; state nào recomputable có thể đơn giản coi restart là cache miss.

Background jobs quan trọng không nên chạy fire-and-forget trong web worker nếu requirement là guaranteed completion. Tôi chuyển chúng sang durable queue + worker/Function/Service phù hợp, hoặc ít nhất durable job store, retry và idempotency. Web process có thể chết bất kỳ lúc nào do deploy, crash hoặc maintenance.

Với 502/503, tôi kiểm tra startup time, ANCM/IIS reverse-proxy logs, health endpoint và overlapped recycle. Nếu old process dừng trước khi new process sẵn sàng, user sẽ thấy capacity gap. Deployment pipeline nên warm-up/health-check và chỉ chuyển traffic khi ready nếu hosting topology cho phép.

Testing gồm forced recycle, process kill, key-store unavailable, session loss, deployment restart và long-running job đang chạy. Metrics gồm recycle count/reason, process uptime, startup duration, 5xx rate, auth-cookie validation failures, session resets và orphaned/retried jobs.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không tắt recycle trước. Em correlate IIS/WAS/Event Viewer reason code, process exit, deployment timeline và 5xx/logout để biết restart vì scheduled recycle, memory, crash hay config change.

Sau đó em xem state nào đang phụ thuộc process. Cookie auth phải survive restart bằng key persistence phù hợp; session quan trọng không nên chỉ ở memory nếu có nhiều process/recycle. Background work cần durable queue/job store thay vì fire-and-forget trong web worker.

Với 502 em kiểm tra startup/warmup và overlapped recycle để tránh capacity gap. Em sẽ test forced recycle/process kill và monitor recycle reason, startup duration, 5xx, auth failures và job recovery. Mục tiêu không phải process không bao giờ restart, mà application đúng khi restart xảy ra.”

## Câu hỏi đào sâu

1. Nếu cookie vẫn còn nhưng chỉ user ở một node bị logout sau recycle, bạn điều tra key/session topology thế nào?
2. Một teammate muốn chuyển toàn hệ thống sang Kubernetes để “không còn IIS recycle”; bạn phản biện ra sao?
3. Nếu background job đã gọi external API thành công rồi process chết trước khi ghi DB, bạn thiết kế recovery thế nào?

## Lỗi trả lời thường gặp

- Tắt recycle hoàn toàn mà không tìm reason.
- Đồng nhất logout với cookie bị xóa.
- Giữ critical background work trong web process.
- Cho rằng thêm RAM sẽ giải quyết mọi restart.
- Không test process restart như một failure mode bình thường.

## Thang điểm 0–10

- **0–2:** Chỉ tắt recycle hoặc tăng RAM.
- **3–4:** Biết cần xem Event Viewer nhưng chưa xử lý state/lifecycle design.
- **5–6:** Có reason-code investigation, auth/session externalization và durable background work.
- **7–8:** Có warmup/deployment behavior, mixed-stack reasoning và restart testing.
- **9–10:** Biến process restart thành thiết kế failure-tolerant với observability và operational runbook rõ.

# Câu 3 — Migrate .NET Framework 4.5 monolith lên .NET 8: rewrite, strangler hay incremental in-place?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET modernization, ASP.NET Framework, ASP.NET Core, architecture, migration strategy, CI/CD, testing, rollout, rollback, technical debt

## Bối cảnh

Một enterprise management platform đã tồn tại nhiều năm, hiện có:

- ASP.NET MVC trên .NET Framework 4.5;
- WCF/internal HTTP integrations;
- Entity Framework 6;
- SQL Server dùng chung;
- Windows Authentication ở một số internal flows;
- IIS/Windows Server hosting;
- nhiều Razor views + jQuery;
- scheduled jobs chạy trong web application;
- deployment bằng Jenkins + Octopus Deploy;
- test automation hạn chế.

Business muốn:

- chạy trên supported modern .NET;
- giảm rủi ro security/dependency cũ;
- hỗ trợ Linux/App Service/container options trong tương lai;
- cải thiện deployment frequency;
- vẫn phát hành feature hàng tháng;
- không chấp nhận downtime dài hoặc big-bang data migration.

Team tranh luận:

1. rewrite toàn bộ sang .NET 8 + React;
2. migrate từng project/library rồi thay web host sau;
3. xây ASP.NET Core façade mới và strangler từng capability;
4. giữ nguyên legacy thêm hai năm vì migration quá rủi ro.

Chưa biết chắc:

- third-party libraries nào chỉ hỗ trợ .NET Framework;
- WCF contracts/client dependencies thực tế;
- mức coupling giữa modules qua database/shared static state;
- Windows-specific APIs nào được dùng;
- test coverage theo critical business flows;
- traffic/usage theo module;
- authentication/SSO requirements khi old/new cùng tồn tại;
- deployment topology cho parallel legacy/modern hosting.

## Câu hỏi chính

Hãy đề xuất migration strategy có thể thực thi trong khi business vẫn phát hành feature. So sánh rewrite, incremental library/runtime migration và strangler; mô tả discovery, dependency compatibility, boundaries, data/auth integration, test strategy, rollout, observability, rollback và tiêu chí để quyết định thứ tự module.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào có business value cao nhưng coupling thấp, phù hợp pilot?
2. Third-party dependencies nào block modern .NET và có replacement/upgrade path không?
3. Old/new applications có cần share authentication/session hay chỉ SSO identity?
4. Có thể giữ chung SQL schema trong transition hay cần bounded data ownership dần?
5. Critical journeys nào phải có automated regression tests trước khi migration?

## Gợi ý tư duy

### Gợi ý 1

Migration architecture trước hết là dependency-discovery và risk-management problem.

### Gợi ý 2

Rewrite thay đổi code, framework, UI, deployment và behavior cùng lúc — đó là blast radius rất lớn.

### Gợi ý 3

Một strangler chỉ hiệu quả nếu boundary thật sự tồn tại hoặc có thể tạo ra; shared database/static state có thể làm “microservice hóa” giả tạo.

## Cấu trúc trả lời đề xuất

1. Inventory dependencies và business criticality.
2. Baseline runtime/production behavior.
3. Xây characterization/regression tests.
4. Phân loại code portable vs framework-bound.
5. Chọn migration boundary/pilot.
6. Thiết kế coexistence auth/data/routing.
7. Migrate theo vertical slice hoặc shared library có kiểm soát.
8. Thiết kế CI/CD, rollout và rollback.
9. Retire legacy dependency theo milestones.
10. Đo progress bằng risk/traffic/usage, không chỉ LOC migrated.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite-from-scratch là tốt nhất.
- Discovery phải xác định framework-specific dependencies, third-party compatibility và Windows-only assumptions.
- Cần characterization/regression tests cho critical flows trước khi thay đổi lớn.
- Migration nên incremental, có rollback và business delivery tiếp tục.
- Old/new coexistence phải xử lý routing, authentication, configuration và observability.
- Shared database có thể là transitional strategy nhưng phải quản lý schema compatibility.
- Không tách service chỉ vì muốn dùng modern .NET nếu boundary/ownership không rõ.
- Scheduled/background work trong web process cần được đánh giá lại.
- CI/CD phải build/test/deploy old và new artifacts nhất quán trong transition.

### Điểm cộng

- Migrate reusable business libraries sang target hỗ trợ modern .NET khi thực tế khả thi, nhưng không ép nếu dependency graph không cho phép.
- Dùng reverse proxy/routing hoặc façade để strangler theo route/capability.
- Chọn pilot module có value rõ, coupling thấp và observability tốt.
- Feature flags/canary giúp giảm rollback cost.
- Contract tests cho integrations/WCF replacements.

### Senior+

- Phân biệt technical target state với migration architecture; target có thể là modular monolith thay vì microservices.
- Có schema expand/contract để old/new versions coexist.
- Có identity bridge rõ: shared SSO/token claims thay vì copy process session mù quáng.
- Định nghĩa exit criteria để tránh legacy-modern hybrid tồn tại vô thời hạn.
- Ưu tiên removal of unsupported/security-critical dependencies trước cosmetic frontend rewrite nếu risk cao hơn.

## Hướng giải quyết tham khảo

Tôi sẽ không chọn rewrite hoặc strangler trước khi inventory dependency graph. Bước đầu là scan solution/packages, IIS/Windows APIs, WCF, EF6 usage, static/session state, scheduled jobs, authentication, file system và third-party libraries. Song song, map module theo business criticality, traffic, change frequency và coupling.

Tiếp theo tôi tạo safety net: characterization tests cho critical HTTP flows, database integration tests, contract tests cho external systems và một số Playwright E2E cho business journeys có giá trị cao. Mục tiêu là khóa behavior cần giữ, không cố đạt 100% coverage.

Nếu nhiều domain/business libraries ít phụ thuộc System.Web, tôi có thể tách/migrate chúng trước. Nhưng nếu code bị coupling mạnh vào HttpContext/session/EF6/static state, ép “library migration” có thể tốn nhiều refactor không tạo business progress. Khi đó vertical-slice strangler theo capability có thể tốt hơn.

Một target state hợp lý có thể là ASP.NET Core modular monolith chứ không cần microservices. Tôi chọn một module coupling thấp làm pilot, xây endpoint/UI mới trên .NET 8 và route một phần traffic qua reverse proxy/façade. Old/new cùng tồn tại trong transition.

Identity cần explicit contract. Tôi ưu tiên cùng identity provider/SSO claims thay vì share in-process session. Với database, có thể dùng chung SQL schema tạm thời nếu cần, nhưng schema changes phải backward compatible cho old/new binaries bằng expand/contract. Dần dần mới tách ownership nếu domain boundary và operational benefit đủ rõ.

WCF/internal integrations được phân loại: client-only có thể có replacement path đơn giản; contract phức tạp cần adapter/compatibility tests. Windows-specific dependencies được thay từng phần dựa trên priority nếu mục tiêu Linux hosting thực sự có business value.

Scheduled jobs trong web process nên được tách khỏi request host nếu cần durability, vì modernization là cơ hội sửa lifecycle coupling — nhưng không biến tất cả thành Azure Functions nếu Worker Service đơn giản hơn.

Release strategy phải cho phép rollback từng slice. CI build old/new separately nhưng trace cùng release version, chạy regression/contract/E2E tests theo risk, deploy canary/feature flag khi phù hợp, và giữ telemetry phân biệt legacy vs modern route để so error/latency/business outcomes.

Tôi đặt exit criteria: số critical routes đã migrate, unsupported dependencies còn lại, traffic trên legacy, production incidents do legacy, test coverage critical journeys và deadline retire old host. Nếu không có exit criteria, hybrid có thể thành permanent complexity.

Rewrite toàn bộ chỉ đáng cân nhắc nếu legacy behavior ít, product requirements thay đổi lớn và business sẵn sàng freeze/parallel-run đủ lâu. Với hệ thống đang phát hành feature hàng tháng và downtime thấp, incremental migration thường giảm blast radius hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ bắt đầu bằng inventory dependency/coupling và characterization tests chứ chưa chọn rewrite. Em map module theo business value, traffic, coupling, third-party/Windows dependencies rồi chọn pilot có boundary rõ.

Target state có thể chỉ cần ASP.NET Core modular monolith. Với capability phù hợp, em strangler từng route/vertical slice; old/new coexist bằng routing rõ, cùng SSO identity và schema changes backward-compatible. Shared DB có thể dùng tạm thời nhưng không coi đó là boundary cuối cùng.

Em ưu tiên remove unsupported/security-critical dependencies, tách durable background work khỏi web lifecycle, dùng contract/E2E tests và canary/feature flags để rollback từng slice. Em cũng đặt exit criteria để hybrid không tồn tại mãi. Rewrite toàn bộ chỉ hợp lý nếu product scope và organization chấp nhận blast radius đó.”

## Câu hỏi đào sâu

1. Nếu 70% code dùng `System.Web.HttpContext.Current`, bạn tạo seam và migration order thế nào mà không refactor toàn solution trước?
2. CTO yêu cầu microservices như target bắt buộc vì “đã modernization thì phải cloud-native”; bạn dùng tiêu chí nào để phản biện hoặc đồng ý?
3. Nếu old và new versions cùng dùng một bảng SQL nhưng migration mới cần xóa cột, bạn rollout theo expand/contract như thế nào?

## Lỗi trả lời thường gặp

- Rewrite toàn bộ chỉ vì code cũ khó chịu.
- Chọn microservices/Kubernetes như synonym của modernization.
- Không tạo regression safety net trước migration.
- Bỏ qua auth/session/schema coexistence giữa old/new.
- Không có exit criteria nên hybrid kéo dài vô hạn.

## Thang điểm 0–10

- **0–2:** Chỉ chọn framework/architecture mới.
- **3–4:** Có incremental migration nhưng thiếu dependency/test/rollback plan.
- **5–6:** Có inventory, characterization tests, coexistence và pilot strategy.
- **7–8:** Có schema/auth compatibility, strangler trade-offs, CI/CD và exit criteria.
- **9–10:** Quản lý được migration như portfolio rủi ro kỹ thuật + business continuity với target architecture đủ đơn giản.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache payload là shared application contract; rolling deployment có thể làm schema incompatibility lộ ra dù Redis vẫn hoạt động hoàn toàn bình thường.
- Process restart/recycle phải được coi là failure mode bình thường; authentication, session và background work quan trọng không nên phụ thuộc vô điều kiện vào một web process sống mãi.
- Modernization là bài toán dependency, coexistence, rollout và business continuity chứ không phải “đổi framework càng nhanh càng tốt”.
- Versioning, rollback và observability phải được thiết kế cùng deployment, không thêm vào sau.
- Derived state như cache có thể bỏ/rebuild; durable business state phải có source of truth và recovery path rõ.

## Mẫu tư duy cần nhớ

1. **Shared state là contract:** cache, database schema và auth keys đều phải tương thích trong rolling deployment.
2. **Treat restart as normal:** process có thể chết/recycle/deploy bất kỳ lúc nào; correctness không dựa vào uptime vô hạn.
3. **Migrate by risk, not by fashion:** ưu tiên dependency/security/business risk thay vì framework trend.
4. **Build a safety net before changing behavior:** characterization, contract và E2E tests theo critical journeys.
5. **Design rollback at the same time as rollout.**
