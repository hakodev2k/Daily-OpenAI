# Code Review Challenge 1 — RabbitMQ consumer: thanh toán bị xử lý hai lần dưới tải

**Chủ đề:** Concurrency, EF Core transaction, message processing, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề quan trọng

## Bối cảnh

Một service .NET nhận `PaymentConfirmed` từ RabbitMQ. Mỗi message cần đánh dấu invoice đã thanh toán, ghi payment history và gửi notification. Consumer chạy trên nhiều replicas; broker có thể redeliver message khi connection bị mất hoặc worker crash.

Traffic bình thường khoảng 20–50 messages/giây nhưng có burst vài trăm messages/giây. Production thỉnh thoảng xuất hiện hai `PaymentHistory` cho cùng một payment, duplicate notification và một số invoice có trạng thái không nhất quán sau khi pod restart.

Team tin rằng kiểm tra `invoice.Status == Paid` là đủ để chống duplicate. Database dùng EF Core + PostgreSQL. Chưa rõ publisher có message ID ổn định hay không và notification provider có hỗ trợ idempotency key hay không.

## Đoạn code cần review

```csharp
public sealed class PaymentConfirmedConsumer
{
    private readonly BillingDbContext _db;
    private readonly INotificationService _notifications;
    private readonly ILogger<PaymentConfirmedConsumer> _logger;

    public PaymentConfirmedConsumer(
        BillingDbContext db,
        INotificationService notifications,
        ILogger<PaymentConfirmedConsumer> logger)
    {
        _db = db;
        _notifications = notifications;
        _logger = logger;
    }

    public async Task HandleAsync(PaymentConfirmed message)
    {
        var invoice = await _db.Invoices
            .FirstOrDefaultAsync(x => x.Id == message.InvoiceId);

        if (invoice == null)
            return;

        if (invoice.Status == InvoiceStatus.Paid)
            return;

        invoice.Status = InvoiceStatus.Paid;
        invoice.PaidAt = DateTime.UtcNow;

        _db.PaymentHistories.Add(new PaymentHistory
        {
            InvoiceId = invoice.Id,
            PaymentId = message.PaymentId,
            Amount = message.Amount,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        await _notifications.SendPaymentReceiptAsync(
            invoice.CustomerEmail,
            invoice.Id,
            message.Amount);

        _logger.LogInformation(
            "Payment {PaymentId} processed for invoice {InvoiceId}",
            message.PaymentId,
            invoice.Id);
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act trên `invoice.Status` không chống được concurrent processing

- **Problem:** Hai workers có thể cùng đọc `Pending`, cùng vượt qua `if`, rồi cùng xử lý.
- **Why it happens:** Read và write không phải một atomic conditional transition.
- **Production impact:** duplicate history, duplicate side effects và last-writer behavior.
- **Severity:** Critical.
- **Recommended fix:** dùng business idempotency key + database uniqueness và/hoặc atomic conditional update/optimistic concurrency.

### 2. Không có persistent idempotency record hoặc unique constraint theo `PaymentId`

- **Problem:** Redelivery sau vài phút/giờ vẫn có thể tạo duplicate nếu trạng thái invoice không đủ để đại diện cho event identity.
- **Why it happens:** `InvoiceId` và `PaymentId` có semantics khác nhau; code không persist việc message/business event đã được consume.
- **Production impact:** duplicate ledger/history và khó reconcile.
- **Severity:** Critical.
- **Recommended fix:** enforce unique `PaymentId` hoặc `(Source, MessageId)` phù hợp business invariant; duplicate phải trở thành safe no-op.

### 3. Database commit và notification không atomic

- **Problem:** DB có thể commit rồi process crash trước notification, hoặc notification thành công nhưng worker mất ACK và message bị redeliver.
- **Why it happens:** external side effect không nằm trong local database transaction.
- **Production impact:** mất notification hoặc gửi nhiều lần.
- **Severity:** High.
- **Recommended fix:** transactional outbox cho notification; một dispatcher riêng gửi outbox với retry/idempotency.

### 4. Notification trực tiếp làm consumer giữ responsibility quá rộng

- **Problem:** Consumer vừa mutate domain state vừa gọi dependency chậm/fallible.
- **Why it happens:** workflow synchronous nối database với external I/O.
- **Production impact:** tăng processing latency, retry blast radius và khó phân loại failure.
- **Severity:** High.
- **Recommended fix:** commit domain state + outbox atomically; gửi notification bất đồng bộ.

### 5. Không truyền `CancellationToken`

- **Problem:** Query, save và notification không nhận cancellation của worker/shutdown.
- **Why it happens:** method signature không có token.
- **Production impact:** shutdown kéo dài, operation tiếp tục khi host đang stop, tăng ambiguity khi message bị redeliver.
- **Severity:** Medium.
- **Recommended fix:** truyền token xuyên suốt nơi API hỗ trợ và thiết kế cancellation semantics rõ ràng.

### 6. Không validate business invariant của amount/payment

- **Problem:** Code tin `message.Amount` và event mapping mà không kiểm tra invariant cần thiết.
- **Why it happens:** consumer coi broker message là authoritative tuyệt đối.
- **Production impact:** invoice có thể được đánh Paid với dữ liệu không phù hợp nếu upstream bug hoặc contract mismatch.
- **Severity:** Medium.
- **Recommended fix:** validate event version, currency/amount/business identity theo requirement trước transition.

### 7. Invoice không tồn tại bị silently ignored

- **Problem:** `invoice == null` return mà không telemetry phân biệt invalid event với eventual-consistency delay.
- **Why it happens:** missing entity bị coi như success.
- **Production impact:** message có thể mất vĩnh viễn dù invoice xuất hiện sau đó.
- **Severity:** Medium.
- **Recommended fix:** định nghĩa rõ missing invoice là permanent hay retryable; log/metric/dead-letter phù hợp.

### 8. Observability chưa đủ để điều tra delivery attempts

- **Problem:** Log chỉ có PaymentId/InvoiceId sau success.
- **Why it happens:** không capture message ID, delivery attempt, correlation ID, duplicate suppression hoặc failure phase.
- **Production impact:** khó dựng timeline khi incident xảy ra.
- **Severity:** Medium.
- **Recommended fix:** structured telemetry xuyên suốt lifecycle nhưng không log secrets/PII không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định `PaymentId` là business idempotency key ổn định và `PaymentHistory.PaymentId` có unique index. Notification được ghi vào outbox trong cùng transaction; dispatcher riêng chịu trách nhiệm gửi.

```csharp
public sealed class PaymentConfirmedConsumer
{
    private readonly BillingDbContext _db;
    private readonly ILogger<PaymentConfirmedConsumer> _logger;

    public PaymentConfirmedConsumer(
        BillingDbContext db,
        ILogger<PaymentConfirmedConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        PaymentConfirmed message,
        CancellationToken cancellationToken)
    {
        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var alreadyProcessed = await _db.PaymentHistories
            .AnyAsync(x => x.PaymentId == message.PaymentId, cancellationToken);

        if (alreadyProcessed)
        {
            _logger.LogInformation(
                "Duplicate payment suppressed. PaymentId={PaymentId}",
                message.PaymentId);
            return;
        }

        var invoice = await _db.Invoices
            .SingleOrDefaultAsync(
                x => x.Id == message.InvoiceId,
                cancellationToken)
            ?? throw new InvalidOperationException("Invoice not found.");

        ValidatePayment(invoice, message);

        invoice.Status = InvoiceStatus.Paid;
        invoice.PaidAt = message.ConfirmedAtUtc;

        _db.PaymentHistories.Add(new PaymentHistory
        {
            InvoiceId = invoice.Id,
            PaymentId = message.PaymentId,
            Amount = message.Amount,
            CreatedAt = DateTime.UtcNow
        });

        _db.OutboxMessages.Add(OutboxMessage.Create(
            type: "PaymentReceiptRequested",
            aggregateId: invoice.Id.ToString(),
            payload: new
            {
                invoice.Id,
                invoice.CustomerId,
                message.PaymentId,
                message.Amount
            }));

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
            await transaction.CommitAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsPaymentIdUniqueViolation(ex))
        {
            await transaction.RollbackAsync(CancellationToken.None);
            _logger.LogInformation(
                "Concurrent duplicate payment suppressed. PaymentId={PaymentId}",
                message.PaymentId);
        }
    }
}
```

Điểm quan trọng là `AnyAsync` chỉ là fast path; **unique constraint ở database mới là correctness backstop** khi hai workers race. Outbox dispatcher cũng cần idempotency/retry strategy riêng.

## Trade-offs

Transactional outbox thêm bảng, dispatcher và cleanup/retention logic, nhưng loại bỏ khoảng trống nguy hiểm giữa DB commit và việc enqueue/gửi notification. Distributed lock có thể giảm contention nhưng không thay thế idempotency: lock không cứu được crash sau side effect, redelivery sau khi lock release hoặc duplicate đến vào thời điểm khác.

Nếu notification provider hỗ trợ idempotency key, nên truyền stable key như `PaymentId`. Nếu không, dispatcher phải persist delivery state và chấp nhận rằng một số failure mode của external side effect không thể biến thành exactly-once tuyệt đối.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 handlers đồng thời với cùng `PaymentId`; chỉ một history/outbox record được tạo.
2. **Redelivery test:** xử lý cùng message lần hai sau khi transaction commit; lần hai phải là no-op.
3. **Crash/failure-path test:** mô phỏng crash sau DB commit; outbox dispatcher vẫn gửi notification.
4. **Database test:** verify unique constraint thực sự chặn duplicate khi hai transactions race.
5. **Dependency failure test:** notification dispatcher timeout/retry không tạo duplicate nếu provider hỗ trợ idempotency.

## Quan sát trong production

- **Logs:** MessageId, PaymentId, InvoiceId, attempt, duplicate-suppressed reason, failure phase.
- **Metrics:** processed/sec, duplicate suppressions, retry count, outbox backlog, outbox oldest age, dead-letter count.
- **Traces:** consumer span → DB transaction → outbox dispatch → notification dependency.
- **Alerts:** outbox backlog tăng liên tục, retry rate bất thường, unique-conflict spike.
- **Database:** duplicate constraint violations, transaction duration, lock waits và slow queries.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao distributed lock không đủ để đạt exactly-once business effect?
2. Bạn thiết kế outbox dispatcher thế nào nếu có nhiều replicas?
3. Nếu payment provider không cung cấp stable event ID, bạn tạo idempotency identity ở đâu và rủi ro là gì?

# Code Review Challenge 2 — API export audit log: authorization và dữ liệu nhạy cảm

## Bối cảnh

Một ASP.NET Core API cho phép admin export audit events để điều tra incident. Hệ thống là multi-tenant SaaS. User đăng nhập bằng bearer token. Endpoint nhận `tenantId`, khoảng thời gian và optional search text.

Security review phát hiện một số user support có thể export dữ liệu của tenant khác khi biết ID; log production đôi khi chứa access token và payload có email/IP address. Query cũng chậm mạnh khi search text dài hoặc date range lớn.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AuditDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AuditDbContext db,
        ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("export")]
    [Authorize]
    public async Task<IActionResult> Export(
        Guid tenantId,
        DateTime from,
        DateTime to,
        string? search)
    {
        _logger.LogInformation(
            "Audit export. Tenant={TenantId}; Auth={Auth}; Search={Search}",
            tenantId,
            Request.Headers.Authorization.ToString(),
            search);

        var query = _db.AuditEvents
            .Where(x => x.TenantId == tenantId &&
                        x.CreatedAt >= from &&
                        x.CreatedAt <= to);

        if (!string.IsNullOrWhiteSpace(search))
        {
            query = query.Where(x =>
                x.Message.Contains(search) ||
                x.UserEmail.Contains(search));
        }

        var rows = await query
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object/resource-level authorization theo `tenantId`

- **Problem:** Bất kỳ authenticated user nào có thể truyền tenant ID khác nếu không có policy/check bổ sung.
- **Why it happens:** `[Authorize]` chỉ yêu cầu identity theo cấu hình hiện tại; code không chứng minh principal được phép truy cập tenant resource này.
- **Production impact:** cross-tenant data breach.
- **Severity:** Critical.
- **Recommended fix:** derive tenant scope từ trusted claims/session hoặc resource-based authorization; không tin tenant ID chỉ vì client gửi nó.

### 2. Authorization quá rộng cho dữ liệu audit nhạy cảm

- **Problem:** Endpoint không yêu cầu permission/role chuyên biệt cho export.
- **Why it happens:** chỉ có generic authentication requirement.
- **Production impact:** user có quyền cơ bản nhưng không có audit privilege vẫn có thể lấy dữ liệu nhạy cảm.
- **Severity:** Critical.
- **Recommended fix:** policy như `Audit.Export` kết hợp tenant scope và business rules.

### 3. Log bearer token

- **Problem:** `Authorization` header được ghi trực tiếp vào log.
- **Why it happens:** debug telemetry lấy raw request credential.
- **Production impact:** credential leakage qua log aggregation, support access hoặc retention systems.
- **Severity:** Critical.
- **Recommended fix:** tuyệt đối không log bearer token; redaction ở logging pipeline là defense-in-depth.

### 4. Trả trực tiếp EF entities

- **Problem:** API serialize toàn bộ `AuditEvent` entity.
- **Why it happens:** data model và API contract bị coupling.
- **Production impact:** accidental sensitive-field exposure khi entity có thêm column; payload lớn hơn cần thiết.
- **Severity:** High.
- **Recommended fix:** projection sang explicit export DTO theo allowlist fields.

### 5. Không giới hạn date range/result size

- **Problem:** client có thể yêu cầu dataset rất lớn.
- **Why it happens:** thiếu validation/business limits.
- **Production impact:** memory pressure, long DB queries, timeout và denial-of-service amplification.
- **Severity:** High.
- **Recommended fix:** validate maximum range; pagination hoặc asynchronous export job cho dataset lớn.

### 6. Không truyền `CancellationToken`

- **Problem:** DB query tiếp tục dù request disconnect/cancel.
- **Why it happens:** action không nhận token.
- **Production impact:** lãng phí DB/application resources trong query đắt tiền.
- **Severity:** Medium.
- **Recommended fix:** nhận `CancellationToken` và truyền tới async DB operation.

### 7. Search không có giới hạn/normalization và có thể rất đắt

- **Problem:** arbitrary substring search trên `Message` và `UserEmail` có thể gây scan lớn tùy provider/index/query shape.
- **Why it happens:** generic `%term%`-style semantics khó tận dụng B-tree index thông thường cho leading-wildcard search.
- **Production impact:** latency và database CPU/I/O tăng.
- **Severity:** Medium.
- **Recommended fix:** giới hạn search length, chọn search semantics rõ; cân nhắc provider-specific full-text/trigram/index strategy khi nhu cầu thực sự cần.

### 8. Logging raw search text có thể ghi PII/untrusted content

- **Problem:** `search` được log nguyên văn.
- **Why it happens:** input của user bị coi là telemetry an toàn.
- **Production impact:** PII leakage, log pollution và tăng retention exposure.
- **Severity:** Medium.
- **Recommended fix:** log metadata như search-present/search-length hoặc hash khi thật sự cần correlation.

### 9. Không có explicit no-tracking/projection cho read-only export

- **Problem:** query materialize entity objects không cần tracking.
- **Why it happens:** default EF Core tracking query.
- **Production impact:** memory và Change Tracker overhead khi result lớn.
- **Severity:** Medium.
- **Recommended fix:** `AsNoTracking()` + projection; với export lớn dùng batching/streaming/background generation tùy format.

## Phiên bản code đề xuất

Ví dụ giả định ứng dụng có `IAuthorizationService`, tenant access requirement và policy `Audit.Export`. Giới hạn cụ thể phải dựa trên business requirement; ở đây dùng 31 ngày chỉ để minh họa.

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AuditDbContext _db;
    private readonly IAuthorizationService _authorization;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AuditDbContext db,
        IAuthorizationService authorization,
        ILogger<AuditController> logger)
    {
        _db = db;
        _authorization = authorization;
        _logger = logger;
    }

    [HttpGet("export")]
    [Authorize(Policy = "Audit.Export")]
    public async Task<ActionResult<IReadOnlyList<AuditExportRow>>> Export(
        Guid tenantId,
        DateTimeOffset from,
        DateTimeOffset to,
        string? search,
        CancellationToken cancellationToken)
    {
        if (to <= from || to - from > TimeSpan.FromDays(31))
            return BadRequest("Invalid export range.");

        if (search is { Length: > 100 })
            return BadRequest("Search text is too long.");

        var authorization = await _authorization.AuthorizeAsync(
            User,
            tenantId,
            "TenantAuditAccess");

        if (!authorization.Succeeded)
            return Forbid();

        _logger.LogInformation(
            "Audit export requested. Tenant={TenantId}; From={From}; To={To}; HasSearch={HasSearch}",
            tenantId,
            from,
            to,
            !string.IsNullOrWhiteSpace(search));

        IQueryable<AuditEvent> query = _db.AuditEvents
            .AsNoTracking()
            .Where(x =>
                x.TenantId == tenantId &&
                x.CreatedAt >= from &&
                x.CreatedAt < to);

        if (!string.IsNullOrWhiteSpace(search))
        {
            var term = search.Trim();
            query = query.Where(x =>
                x.Message.Contains(term) ||
                x.UserEmail.Contains(term));
        }

        var rows = await query
            .OrderByDescending(x => x.CreatedAt)
            .Take(10_000)
            .Select(x => new AuditExportRow(
                x.Id,
                x.CreatedAt,
                x.EventType,
                x.ActorDisplayName,
                x.Message))
            .ToListAsync(cancellationToken);

        return Ok(rows);
    }
}
```

`Take(10_000)` và 31 ngày chỉ là guardrail minh họa, không phải universal recommendation. Với export thực sự lớn, tốt hơn là tạo background export, lưu artifact có TTL và authorization rõ ràng thay vì giữ HTTP request lâu.

## Trade-offs

Resource-based authorization thêm một lookup/policy evaluation nhưng đổi lại bảo vệ tenant boundary đúng nơi. Nếu tenant ID đã được cryptographically/trusted mapped từ token và user không được chọn tenant tùy ý, API contract có thể khác; vẫn cần enforce scope server-side.

Substring search tiện cho user nhưng khó scale. PostgreSQL có thể dùng giải pháp search/index phù hợp như full-text hoặc trigram tùy semantics; SQL Server có lựa chọn khác. Không nên thêm index mù quáng trước khi xem execution plan và workload.

Async background export tăng complexity và storage lifecycle nhưng tốt hơn cho dataset lớn, cho phép progress, cancellation, retention và download authorization riêng.

## Cách kiểm thử

1. **Security integration test:** user tenant A gọi endpoint với tenant B phải nhận 403 và không có data leakage.
2. **Authorization test:** authenticated user thiếu `Audit.Export` bị từ chối dù thuộc đúng tenant.
3. **Sensitive-data test:** response DTO và logs không chứa bearer token hoặc fields ngoài allowlist.
4. **Load/database test:** maximum allowed range/search không vượt latency/resource budget; xem execution plan thực tế.
5. **Cancellation test:** client cancel request và DB command được cancel/giải phóng phù hợp.

## Quan sát trong production

- **Logs:** actor ID nội bộ, tenant ID, range duration, result count, authorization outcome; không log bearer token/raw PII không cần thiết.
- **Metrics:** export requests, denied requests, duration, rows returned, DB duration, cancellations, oversized-request rejections.
- **Traces:** authorization span → DB query → serialization/export stage.
- **Alerts:** cross-tenant authorization denials tăng bất thường, export latency/error rate spike, DB resource saturation.
- **Database:** execution plans, scanned rows, index usage, lock waits, query duration.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn dùng policy-based authorization và khi nào dùng resource-based authorization?
2. Nếu audit export có 5 triệu rows, bạn thay đổi API/workflow như thế nào?
3. Làm sao thiết kế downloadable export artifact để URL không trở thành đường vòng bypass authorization?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message broker có thể redeliver; correctness nên dựa trên **idempotent business processing**, không dựa vào giả định handler chỉ chạy một lần.
- Check-then-act trong application không đủ dưới concurrency; database unique constraint/atomic transition thường là correctness backstop quan trọng.
- Transactional outbox giải quyết khoảng trống giữa local database state và việc phát side effect/message tiếp theo, nhưng dispatcher vẫn cần retry và idempotency.
- `[Authorize]` không tự động chứng minh user được truy cập một resource/tenant cụ thể.
- Multi-tenant authorization phải được enforce server-side từ trusted identity/scope.
- Credentials như bearer token không được ghi vào application logs.
- API response nên dùng explicit DTO/projection để giảm accidental data exposure.

## Mẫu tư duy cần nhớ

1. **Design retries together with idempotency** — giả định operation có thể chạy lại.
2. **Move invariants to the strongest boundary** — dùng database uniqueness/atomicity cho invariant cần chống race.
3. **Separate authentication from authorization** — “user là ai” khác “user được làm gì trên resource nào”.
4. **Treat logs as a data store** — secrets và PII ghi vào log vẫn là data exposure.
5. **Treat observability as part of the design** — correlation, duplicate suppression và failure phase phải đo được trước incident.
