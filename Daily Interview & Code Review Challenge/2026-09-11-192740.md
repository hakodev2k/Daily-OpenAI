# Code Review Challenge 1 — Service Bus consumer báo “đã xử lý” nhưng vừa làm mất message vừa tạo shipment trùng

**Chủ đề:** C#/.NET 8, Azure Service Bus, `ServiceBusProcessor`, Peek-Lock, message settlement, idempotency, duplicate delivery, failure windows, EF Core, external API, retries, DLQ, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một e-commerce platform phát message `CreateShipment` vào Azure Service Bus sau khi order đã được thanh toán. Một .NET 8 worker nhận message, gọi API của carrier để tạo shipping label, sau đó lưu shipment vào SQL Server.

Yêu cầu:

- một order chỉ được có một shipment active cho cùng fulfillment request;
- Azure Service Bus có thể redeliver message khi consumer restart, message lock hết hạn hoặc settlement thất bại;
- carrier API đôi lúc timeout sau khi đã tạo label thành công;
- worker chạy 6 instances;
- throughput giờ cao điểm khoảng vài trăm message/phút;
- transient failure nên được retry nhưng permanent validation failure không được retry vô hạn;
- không được đánh dấu message thành công nếu business processing chưa hoàn tất;
- cancellation/shutdown phải an toàn;
- operations cần theo dõi duplicate delivery, delivery count, processing latency, failure reason và DLQ.

Sau một đợt scale-out, production xuất hiện hai symptom trái ngược:

- một số order không có shipment dù Service Bus message không còn trong queue;
- một số order có 2–3 label từ carrier nhưng database chỉ ghi một shipment;
- log cho thấy handler đã bắt exception và “để processor retry”, nhưng delivery count của một số message không tăng;
- khi carrier chậm, backlog tăng rồi xuất hiện nhiều duplicate label sau đó.

## Đoạn code cần review

```csharp
public sealed record CreateShipment(
    Guid OrderId,
    string Address,
    decimal WeightKg);

public sealed class ShipmentWorker : IAsyncDisposable
{
    private readonly ServiceBusProcessor _processor;
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly CarrierClient _carrier;
    private readonly ILogger<ShipmentWorker> _logger;

    public ShipmentWorker(
        ServiceBusClient client,
        IDbContextFactory<AppDbContext> dbFactory,
        CarrierClient carrier,
        ILogger<ShipmentWorker> logger)
    {
        _dbFactory = dbFactory;
        _carrier = carrier;
        _logger = logger;

        _processor = client.CreateProcessor(
            "create-shipment",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = true,
                MaxConcurrentCalls = 32
            });

        _processor.ProcessMessageAsync += HandleAsync;
        _processor.ProcessErrorAsync += OnErrorAsync;
    }

    public Task StartAsync(CancellationToken cancellationToken)
        => _processor.StartProcessingAsync(cancellationToken);

    private async Task HandleAsync(ProcessMessageEventArgs args)
    {
        try
        {
            var command = args.Message.Body
                .ToObjectFromJson<CreateShipment>();

            await using var db =
                await _dbFactory.CreateDbContextAsync();

            if (await db.Shipments.AnyAsync(
                x => x.OrderId == command.OrderId))
            {
                return;
            }

            var label = await _carrier.CreateLabelAsync(
                command.OrderId,
                command.Address,
                command.WeightKg);

            db.Shipments.Add(new Shipment
            {
                Id = Guid.NewGuid(),
                OrderId = command.OrderId,
                CarrierLabelId = label.Id,
                CreatedAtUtc = DateTime.UtcNow
            });

            await db.SaveChangesAsync();

            _logger.LogInformation(
                "Shipment created for order {OrderId} from message {MessageId}",
                command.OrderId,
                args.Message.MessageId);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Shipment processing failed for {MessageId}",
                args.Message.MessageId);
        }
    }

    private Task OnErrorAsync(ProcessErrorEventArgs args)
    {
        _logger.LogError(args.Exception, "Service Bus processor error");
        return Task.CompletedTask;
    }

    public async ValueTask DisposeAsync()
    {
        await _processor.DisposeAsync();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong message-processing flow.
2. Xác định reliability, concurrency, idempotency và failure-handling concerns.
3. Giải thích production impact theo từng failure window quan trọng.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa, tránh thêm distributed complexity nếu chưa cần.
6. Giải thích testing cho duplicate delivery, carrier timeout, lock loss, concurrent consumers và shutdown.
7. Đề xuất production telemetry chứng minh không mất message và không tạo shipment trùng.

## Câu hỏi gợi mở

1. Với `AutoCompleteMessages = true`, handler bắt exception rồi return bình thường sẽ khiến processor hiểu kết quả ra sao?
2. Hai deliveries của cùng order chạy đồng thời trên hai instances có thể cùng vượt qua `AnyAsync` hay không?
3. Nếu carrier đã tạo label nhưng HTTP response bị timeout, retry có biết label đã tồn tại không?
4. Database unique constraint và application-level `AnyAsync` khác nhau thế nào dưới concurrency?
5. Message settlement, database commit và external carrier side effect có thể trở thành một atomic transaction hay không?

## Gợi ý

### Gợi ý 1

Primary risk là **failure semantics không khớp với message settlement**: code bắt mọi exception nhưng không báo failure cho processor, trong khi business operation chưa chắc đã thành công.

### Gợi ý 2

Hãy vẽ các failure window theo thứ tự: receive → carrier side effect → database commit → message settlement, rồi đặt duplicate delivery hoặc timeout vào giữa từng bước.

## Kết quả code review tham khảo

### Critical — Swallow exception có thể làm message được auto-complete dù business processing thất bại

**Vấn đề:**  
`HandleAsync` bắt mọi `Exception`, log rồi return bình thường trong khi processor bật `AutoCompleteMessages = true`.

**Tại sao xảy ra:**  
Auto-complete dựa vào việc message handler hoàn tất thành công. Một exception bị nuốt không còn được runtime nhìn thấy như processing failure.

**Ảnh hưởng production:**  
Carrier hoặc SQL có thể fail nhưng message vẫn bị settlement như thành công và biến mất khỏi queue. Đây là đường trực tiếp tới symptom “không có shipment nhưng message không còn”.

**Cách sửa:**  
Không swallow lỗi transient/unexpected. Hoặc để exception thoát ra để processor áp dụng failure semantics, hoặc tắt auto-complete và explicit `CompleteMessageAsync` chỉ sau khi business processing thành công. Permanent invalid message cần được dead-letter có chủ đích thay vì chỉ log.

### Critical — External carrier side effect không idempotent trước ambiguous timeout

**Vấn đề:**  
`CreateLabelAsync` có thể tạo label thành công ở carrier nhưng caller nhận timeout trước khi biết kết quả.

**Tại sao xảy ra:**  
Một distributed call có outcome ambiguity: “request thất bại” ở client không chứng minh remote side effect chưa xảy ra.

**Ảnh hưởng production:**  
Message được redeliver/retry và worker tạo label lần hai. Database có thể chỉ lưu lần retry, trong khi carrier đã có nhiều labels và business bị tính phí hoặc phát sinh fulfillment sai.

**Cách sửa:**  
Nếu carrier hỗ trợ idempotency key, gửi một stable business key như fulfillment request ID/message business ID và query/replay theo key đó. Nếu carrier không hỗ trợ idempotency, cần thiết kế recovery/reconciliation phù hợp; không thể tạo exactly-once external side effect chỉ bằng Service Bus settlement.

### Critical — Check-then-act bằng `AnyAsync` không ngăn concurrent duplicate processing

**Vấn đề:**  
Hai consumers có thể cùng query “chưa có shipment”, cùng gọi carrier, rồi cùng cố insert.

**Tại sao xảy ra:**  
`AnyAsync` và insert là hai operations tách biệt. Application check không phải concurrency boundary.

**Ảnh hưởng production:**  
Scale-out hoặc redelivery song song có thể tạo nhiều carrier labels. Nếu database không có unique constraint thì còn có thể lưu nhiều shipment records.

**Cách sửa:**  
Đặt invariant vào database bằng unique constraint phù hợp, ví dụ unique `FulfillmentRequestId` hoặc `(OrderId, ShipmentType)` tùy domain. Nhưng unique DB constraint chỉ bảo vệ database; external carrier call vẫn cần idempotency/recovery riêng.

### High — Không có durable consumer idempotency/inbox identity rõ ràng

**Vấn đề:**  
Code chỉ deduplicate theo `OrderId`; không lưu `MessageId` hoặc stable fulfillment request ID đã xử lý.

**Tại sao xảy ra:**  
Order có thể hợp lệ có nhiều shipment theo lifecycle, còn một broker delivery có thể lặp lại. Business identity và transport identity đang bị trộn.

**Ảnh hưởng production:**  
Có thể chặn shipment hợp lệ trong tương lai hoặc vẫn không xử lý đúng duplicate của cùng operation.

**Cách sửa:**  
Xác định idempotency key ở business level. Nếu `CreateShipment` đại diện đúng một fulfillment request, message nên chứa `FulfillmentRequestId` stable. Persist key đó với unique constraint; `MessageId` hữu ích cho telemetry/dedup transport nhưng không nhất thiết là domain key duy nhất.

### High — Không propagate cancellation vào EF Core và carrier calls

**Vấn đề:**  
`CreateDbContextAsync`, `AnyAsync`, carrier request và `SaveChangesAsync` không nhận cancellation token từ message handler/shutdown.

**Tại sao xảy ra:**  
Cancellation không tự propagate qua async calls chỉ vì worker đang shutdown.

**Ảnh hưởng production:**  
Deployment có thể kéo dài; in-flight work tiếp tục sau khi processor dừng nhận message. Nếu connection/lock thay đổi trong lúc đó, settlement và business side effect càng khó reasoning.

**Cách sửa:**  
Propagate cancellation token được framework cung cấp khi phù hợp. Tuy nhiên cancellation sau external side effect vẫn là ambiguous outcome, nên idempotency vẫn bắt buộc.

### High — Concurrency 32 mỗi instance có thể khuếch đại tải carrier và database

**Vấn đề:**  
6 instances × `MaxConcurrentCalls = 32` có thể tạo concurrency lớn đối với carrier/SQL mà không thấy capacity budget nào.

**Tại sao xảy ra:**  
Processor concurrency được cấu hình độc lập với downstream rate limit, connection pool, carrier quota và processing latency.

**Ảnh hưởng production:**  
Carrier throttling/timeouts tăng, lock duration bị kéo dài, retry tăng và tạo feedback loop làm duplicate/failure nhiều hơn.

**Cách sửa:**  
Chọn concurrency dựa trên load test và downstream capacity. Theo dõi latency, throttling và DB pool. Có thể giảm concurrency hoặc thêm bounded rate limit riêng nếu carrier có quota; không copy một con số cố định giữa môi trường.

### Medium — Không phân biệt transient, permanent và poison messages

**Vấn đề:**  
Mọi exception đều có cùng behavior là log rồi return.

**Tại sao xảy ra:**  
Failure taxonomy chưa được thiết kế.

**Ảnh hưởng production:**  
Permanent validation lỗi có thể bị xử lý sai; transient dependency failure có thể bị mất; operator không có DLQ workflow rõ ràng.

**Cách sửa:**  
Validate message sớm. Dead-letter malformed/non-retriable messages với reason rõ ràng. Với transient failures, abandon/throw để retry theo policy. Monitor và vận hành DLQ như một queue cần ownership, không phải nơi “ném lỗi rồi quên”.

### Medium — Không xử lý rõ message lock/settlement failure

**Vấn đề:**  
Code không có explicit settlement, không log `DeliveryCount`, lock information hoặc outcome của settlement.

**Tại sao xảy ra:**  
Broker acknowledgment bị coi như chi tiết framework thay vì một phần correctness của at-least-once processing.

**Ảnh hưởng production:**  
Nếu processing xong nhưng settlement không tới broker, message có thể được redeliver. Không có telemetry/idempotency tốt thì operator thấy “Service Bus xử lý hai lần” nhưng không biết business operation có an toàn không.

**Cách sửa:**  
Với manual settlement, complete sau khi durable business result được xác nhận. Thiết kế consumer để redelivery an toàn ngay cả khi `CompleteMessageAsync` thất bại hoặc lock bị mất.

### Medium — Deserialization/validation chưa có boundary rõ

**Vấn đề:**  
Không kiểm tra `command` null, address/weight hoặc schema compatibility.

**Tại sao xảy ra:**  
Transport payload được đưa thẳng vào business flow.

**Ảnh hưởng production:**  
Malformed event có thể gây retry vô ích hoặc runtime failure, cuối cùng vào DLQ mà không có nguyên nhân business rõ.

**Cách sửa:**  
Validate envelope/schema và required fields trước external side effect; classify lỗi không retry được.

### Medium — Không có transaction boundary cho durable state trong SQL

**Vấn đề:**  
Nếu sau này flow thêm nhiều writes như shipment, audit, order status, idempotency marker, code hiện tại dễ tạo partial SQL state.

**Tại sao xảy ra:**  
Durable local side effects chưa được nhóm theo một local transaction/invariant.

**Ảnh hưởng production:**  
Retry có thể gặp state nửa chừng khó phân biệt.

**Cách sửa:**  
Những writes thuộc cùng SQL database và cùng business commit nên nằm trong một local transaction hoặc một `SaveChanges` transaction phù hợp. Không cố đưa Service Bus/carrier vào distributed transaction chỉ để giả lập exactly-once.

### Low — Observability thiếu các field cần cho distributed processing

**Vấn đề:**  
Logs chủ yếu có `OrderId` và `MessageId`; không thấy delivery count, fulfillment key, carrier idempotency key, duration, settlement outcome hay failure class.

**Tại sao xảy ra:**  
Telemetry chưa phản ánh message lifecycle.

**Ảnh hưởng production:**  
Khó reconstruct một message đã được nhận bao nhiêu lần, carrier call nào tương ứng, DB commit nào thắng và vì sao message vào DLQ.

**Cách sửa:**  
Structured log/trace theo `MessageId`, business operation ID, `DeliveryCount`, carrier correlation/idempotency key, processing duration, settlement outcome và error category. Tránh log address hoặc PII không cần thiết.

## Phiên bản đề xuất

Giả sử carrier hỗ trợ idempotency key và business đã có `FulfillmentRequestId` stable cho đúng một shipment operation. Database có unique index trên `Shipment.FulfillmentRequestId`.

```csharp
public sealed record CreateShipment(
    Guid FulfillmentRequestId,
    Guid OrderId,
    string Address,
    decimal WeightKg);

public sealed class ShipmentWorker
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly CarrierClient _carrier;
    private readonly ILogger<ShipmentWorker> _logger;

    public ShipmentWorker(
        IDbContextFactory<AppDbContext> dbFactory,
        CarrierClient carrier,
        ILogger<ShipmentWorker> logger)
    {
        _dbFactory = dbFactory;
        _carrier = carrier;
        _logger = logger;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var ct = args.CancellationToken;

        CreateShipment? command;
        try
        {
            command = args.Message.Body
                .ToObjectFromJson<CreateShipment>();
        }
        catch (Exception ex) when (
            ex is JsonException or NotSupportedException)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                deadLetterReason: "InvalidPayload",
                deadLetterErrorDescription: "Message schema is invalid",
                cancellationToken: ct);

            return;
        }

        if (command is null ||
            command.FulfillmentRequestId == Guid.Empty ||
            command.OrderId == Guid.Empty ||
            command.WeightKg <= 0)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                deadLetterReason: "ValidationFailed",
                deadLetterErrorDescription: "Required shipment fields are invalid",
                cancellationToken: ct);

            return;
        }

        await using var db =
            await _dbFactory.CreateDbContextAsync(ct);

        var existing = await db.Shipments
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.FulfillmentRequestId ==
                     command.FulfillmentRequestId,
                ct);

        if (existing is not null)
        {
            await args.CompleteMessageAsync(args.Message, ct);
            return;
        }

        // Carrier must treat this key idempotently.
        var carrierKey = command.FulfillmentRequestId.ToString("N");

        var label = await _carrier.CreateLabelAsync(
            command.OrderId,
            command.Address,
            command.WeightKg,
            idempotencyKey: carrierKey,
            cancellationToken: ct);

        db.Shipments.Add(new Shipment
        {
            Id = Guid.NewGuid(),
            FulfillmentRequestId = command.FulfillmentRequestId,
            OrderId = command.OrderId,
            CarrierLabelId = label.Id,
            CreatedAtUtc = DateTime.UtcNow
        });

        try
        {
            await db.SaveChangesAsync(ct);
        }
        catch (DbUpdateException)
            when (await ShipmentAlreadyExistsAsync(
                command.FulfillmentRequestId, ct))
        {
            // Another delivery committed the same business operation.
        }

        await args.CompleteMessageAsync(args.Message, ct);

        _logger.LogInformation(
            "Shipment processing completed. " +
            "MessageId={MessageId} DeliveryCount={DeliveryCount} " +
            "FulfillmentRequestId={FulfillmentRequestId}",
            args.Message.MessageId,
            args.Message.DeliveryCount,
            command.FulfillmentRequestId);
    }

    private async Task<bool> ShipmentAlreadyExistsAsync(
        Guid fulfillmentRequestId,
        CancellationToken ct)
    {
        await using var verificationDb =
            await _dbFactory.CreateDbContextAsync(ct);

        return await verificationDb.Shipments
            .AsNoTracking()
            .AnyAsync(
                x => x.FulfillmentRequestId == fulfillmentRequestId,
                ct);
    }
}
```

Đoạn code trên vẫn có một điểm phải nói rõ: unique constraint trong SQL **không** làm carrier call và SQL commit trở thành một atomic operation. Safety phụ thuộc vào carrier thực sự hỗ trợ stable idempotency key hoặc có API query/reconciliation đáng tin cậy. Nếu carrier không có cơ chế đó, design cần một state machine/reconciliation workflow phù hợp thay vì tuyên bố “exactly once”.

Ngoài ra, catch `DbUpdateException` trong production nên chỉ classify đúng unique-constraint conflict mong đợi, không swallow mọi database exception. Cách nhận diện constraint cụ thể phụ thuộc provider và data-access implementation.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách ba lớp correctness:

1. **Broker delivery:** manual settlement chỉ complete sau khi processing đã đạt durable success hoặc đã xác định operation trước đó hoàn tất.
2. **Database invariant:** unique business key làm concurrent duplicate insert trở thành conflict có thể xử lý thay vì dựa vào check-then-act.
3. **External side effect:** carrier nhận stable idempotency key để retry sau ambiguous timeout không tạo label mới.

Điểm cốt lõi là không cố biến Azure Service Bus thành exactly-once business processing. Peek-Lock có thể redeliver; settlement cũng là một network operation có thể thất bại sau khi business work đã hoàn tất. Consumer vì vậy phải an toàn khi chạy lại.

Nếu shipment flow còn cần publish event `ShipmentCreated`, có thể thêm transactional outbox trong cùng SQL transaction với shipment rồi có dispatcher riêng. Chỉ thêm khi có requirement downstream thực sự; không cần đưa outbox vào chỉ để làm code “enterprise”.

## Trade-offs

- Manual settlement rõ correctness hơn nhưng application phải sở hữu failure classification và đảm bảo mọi code path settle/throw đúng.
- Unique constraint xử lý race ở SQL tốt nhưng không chống duplicate external side effect.
- Carrier idempotency key đơn giản nhất nếu provider hỗ trợ, nhưng behavior/retention của idempotency key phải được xác minh.
- Giảm `MaxConcurrentCalls` bảo vệ downstream nhưng có thể giảm throughput; phải điều chỉnh bằng measurement.
- Inbox/outbox/state machine tăng durability và khả năng recovery nhưng tăng schema, operational state và code complexity.
- DLQ tránh poison-message retry vô hạn nhưng tạo operational backlog cần ownership, dashboard và replay procedure.

## Cách kiểm thử

1. **Concurrency/integration test:** gửi cùng `FulfillmentRequestId` nhiều lần đồng thời qua nhiều worker instances; xác minh chỉ một durable shipment và carrier chỉ tạo một label khi dùng cùng idempotency key.
2. **Ambiguous-timeout failure test:** carrier tạo label rồi client nhận timeout; cho message redeliver và xác minh retry trả/reuse cùng label thay vì tạo label mới.
3. **Settlement failure test:** hoàn tất SQL commit rồi giả lập `CompleteMessageAsync` thất bại/lock loss; message được redeliver nhưng business result vẫn idempotent.
4. **Poison-message test:** payload/schema invalid phải đi DLQ với reason rõ; transient carrier `503` không bị dead-letter ngay và không bị auto-complete.
5. **Load/shutdown test:** chạy expected peak với nhiều instances, đo queue backlog, carrier throttling, SQL pool, processing latency; shutdown worker giữa in-flight message và xác minh redelivery an toàn.

## Quan sát trong production

Theo dõi:

- active message count, queue age/backlog và DLQ count;
- processing success/failure theo failure class;
- `DeliveryCount` distribution và duplicate business-key rate;
- carrier request latency, timeout/throttling và idempotency-replay rate;
- SQL unique-conflict count;
- message processing duration so với lock/renewal behavior;
- settlement success/failure và lock-lost exceptions;
- end-to-end trace/correlation từ `MessageId` → `FulfillmentRequestId` → carrier request → SQL shipment;
- alert khi DLQ, redelivery, carrier timeout hoặc oldest-message age vượt baseline/SLO.

## Câu hỏi phỏng vấn mở rộng

# Code Review Challenge 2 — SQL phân trang “đúng ở page 1” nhưng càng lật sâu càng chậm và còn bỏ sót order

**Chủ đề:** SQL Server, query optimization, sargability, composite indexes, keyset pagination, stable ordering, filtering, execution plans, production database observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một back-office API hiển thị lịch sử order cho từng tenant. SQL Server table `Orders` có khoảng 120 triệu rows; tenant lớn nhất có vài triệu orders.

UI hỗ trợ:

- filter theo tenant bắt buộc;
- filter thời gian từ ngày `@FromDate` đến trước `@ToDate`;
- optional filter theo status;
- optional tìm customer email;
- sort mới nhất trước;
- page size tối đa 100;
- người dùng có thể lật nhiều trang khi điều tra incident;
- dữ liệu vẫn tiếp tục được insert trong lúc user đang duyệt.

Production symptom:

- page đầu thường dưới 150 ms;
- page 2.000 có thể mất 8–20 giây và tăng CPU/reads trên SQL Server;
- cùng một user đôi lúc thấy một order xuất hiện ở hai trang hoặc một order “biến mất” khi order mới được insert;
- query timeout tăng trong giờ cao điểm;
- team đề xuất thêm `NOLOCK` và một index riêng cho từng filter.

Schema/query hiện tại:

## Đoạn code cần review

```sql
CREATE TABLE dbo.Orders
(
    Id              bigint          NOT NULL PRIMARY KEY,
    TenantId        uniqueidentifier NOT NULL,
    CustomerId      bigint          NOT NULL,
    CustomerEmail   nvarchar(320)   NOT NULL,
    Status          varchar(30)     NOT NULL,
    TotalAmount     decimal(18,2)   NOT NULL,
    CreatedAtUtc    datetime2(7)    NOT NULL
);

CREATE INDEX IX_Orders_CreatedAtUtc
ON dbo.Orders(CreatedAtUtc DESC);

DECLARE @PageNumber int = 2000;
DECLARE @PageSize int = 100;

SELECT
    o.Id,
    o.CustomerEmail,
    o.Status,
    o.TotalAmount,
    o.CreatedAtUtc
FROM dbo.Orders AS o
WHERE
    o.TenantId = @TenantId
    AND CONVERT(date, o.CreatedAtUtc) >= @FromDate
    AND CONVERT(date, o.CreatedAtUtc) <= @ToDate
    AND (@Status IS NULL OR o.Status = @Status)
    AND (
        @Email IS NULL
        OR LOWER(o.CustomerEmail) LIKE '%' + LOWER(@Email) + '%'
    )
ORDER BY
    o.CreatedAtUtc DESC
OFFSET (@PageNumber - 1) * @PageSize ROWS
FETCH NEXT @PageSize ROWS ONLY;
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong pagination/filter semantics.
2. Xác định performance và index/query-plan concerns.
3. Giải thích vì sao page sâu chậm dù `FETCH NEXT` chỉ lấy 100 rows.
4. Ưu tiên findings theo severity/business impact.
5. Đề xuất query/index/API pagination design đã sửa.
6. Giải thích cách test query correctness và performance với realistic data distribution.
7. Đề xuất production telemetry/evidence cần xem trước và sau khi deploy thay đổi.

## Câu hỏi gợi mở

1. `ORDER BY CreatedAtUtc` có tạo total ordering nếu nhiều orders có cùng timestamp không?
2. `OFFSET` phải làm bao nhiêu work khi `@PageNumber = 2000`?
3. `CONVERT(date, CreatedAtUtc)` tác động thế nào đến khả năng seek trên index theo timestamp?
4. Leading wildcard trong email search có thể tận dụng B-tree index thông thường như thế nào?
5. Index hiện tại bắt đầu bằng `CreatedAtUtc`, trong khi mọi request đều có `TenantId`; access pattern đó gợi ý gì về index key order?

## Gợi ý

### Gợi ý 1

Primary risk là sự kết hợp của **deep OFFSET pagination + non-sargable predicates + ordering không unique** trên tập dữ liệu lớn.

### Gợi ý 2

Hãy thiết kế query từ access pattern: equality predicate bắt buộc, time range, stable sort, cursor của trang trước và các optional filters — rồi mới quyết định index.

## Kết quả code review tham khảo

### High — Deep `OFFSET` làm work tăng theo vị trí trang

**Vấn đề:**  
Page 2.000 với size 100 yêu cầu engine bỏ qua khoảng 199.900 rows đủ điều kiện trước khi trả 100 rows tiếp theo.

**Tại sao xảy ra:**  
`OFFSET/FETCH` mô tả vị trí tương đối trong ordered result, không cung cấp một seek boundary từ row cuối trang trước.

**Ảnh hưởng production:**  
Logical reads, CPU, sort/scan work và latency tăng theo page depth. Nhiều users deep-page cùng lúc có thể gây database pressure vượt xa số rows thực sự trả về.

**Cách sửa:**  
Với navigation tuần tự, dùng keyset/seek pagination dựa trên stable sort key, ví dụ `(CreatedAtUtc, Id)`. Client gửi cursor từ row cuối của page trước thay vì page number lớn.

### High — `ORDER BY CreatedAtUtc` không tạo total ordering

**Vấn đề:**  
Nhiều orders có thể có cùng `CreatedAtUtc`; thứ tự giữa chúng không được xác định bởi query.

**Tại sao xảy ra:**  
Sort key không unique.

**Ảnh hưởng production:**  
Giữa executions, rows có cùng timestamp có thể đổi vị trí. Với OFFSET và concurrent inserts, user có thể thấy duplicate hoặc missing row giữa các pages.

**Cách sửa:**  
Thêm deterministic tie-breaker, ví dụ `ORDER BY CreatedAtUtc DESC, Id DESC`, và dùng cùng tuple trong cursor predicate.

### High — Pagination theo offset không ổn định khi dataset thay đổi giữa các request

**Vấn đề:**  
Nếu orders mới được insert trước vị trí hiện tại, ordinal position của các rows cũ bị dịch chuyển.

**Tại sao xảy ra:**  
Page N được định nghĩa theo “bỏ qua N rows hiện tại”, không theo một immutable boundary của lần đọc trước.

**Ảnh hưởng production:**  
Duplicate/missing items trong user journey ngay cả khi query mỗi page riêng lẻ là hợp lệ.

**Cách sửa:**  
Keyset pagination neo page tiếp theo vào key cuối đã nhìn thấy. Nếu requirement đòi snapshot hoàn toàn cố định xuyên nhiều phút, cần một snapshot/version boundary riêng; keyset chỉ đảm bảo traversal ổn định hơn chứ không tự tạo cross-request transaction snapshot.

### High — `CONVERT(date, CreatedAtUtc)` làm time predicate khó tận dụng index seek hiệu quả

**Vấn đề:**  
Function được áp lên indexed column trong predicate.

**Tại sao xảy ra:**  
Engine phải đánh giá expression trên column thay vì so sánh trực tiếp column với range boundaries.

**Ảnh hưởng production:**  
Có thể tăng scanned rows và giảm khả năng dùng index access path hiệu quả, đặc biệt trên hàng triệu rows mỗi tenant.

**Cách sửa:**  
Chuẩn hóa input thành UTC half-open range và dùng:

```sql
o.CreatedAtUtc >= @FromUtc
AND o.CreatedAtUtc < @ToUtcExclusive
```

Half-open range cũng tránh ambiguity ở fractional seconds cuối ngày.

### High — Email contains search với leading wildcard không phù hợp B-tree index thông thường

**Vấn đề:**  
`LIKE '%' + @Email + '%'` yêu cầu match substring ở bất kỳ vị trí nào; thêm `LOWER(column)` còn tạo expression trên column.

**Tại sao xảy ra:**  
B-tree index hữu ích nhất khi predicate có searchable leading portion phù hợp collation/index semantics; leading wildcard không cung cấp prefix seek.

**Ảnh hưởng production:**  
Một optional email filter có thể biến thành scan lớn và làm query plan rất khác giữa request có/không có filter.

**Cách sửa:**  
Làm rõ product requirement. Nếu chỉ cần exact/prefix email, normalize dữ liệu và dùng equality/prefix predicate phù hợp index. Nếu thật sự cần arbitrary substring search ở scale này, đánh giá full-text/search-specific solution dựa trên requirement; không thêm Elasticsearch chỉ vì một query đang chậm.

### High — Index hiện tại không align với tenant-scoped access pattern

**Vấn đề:**  
`IX_Orders_CreatedAtUtc` bắt đầu bằng timestamp, trong khi mọi query bắt buộc filter `TenantId`.

**Tại sao xảy ra:**  
Index được thiết kế theo sort column đơn lẻ thay vì access pattern tổng thể.

**Ảnh hưởng production:**  
Engine có thể phải đọc/range-scan nhiều rows của tenant khác rồi filter, hoặc chọn plan khác tốn kém.

**Cách sửa:**  
Một baseline index hợp lý cho path phổ biến có thể bắt đầu bằng `TenantId`, tiếp theo stable pagination keys:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt_Id
ON dbo.Orders
(
    TenantId,
    CreatedAtUtc DESC,
    Id DESC
)
INCLUDE
(
    CustomerEmail,
    Status,
    TotalAmount
);
```

Có nên include thêm/bớt cột hoặc thêm index cho status phải dựa trên workload, selectivity, write cost và execution plans thực tế.

### Medium — Optional predicate pattern có thể tạo plan không phù hợp cho mọi parameter shape

**Vấn đề:**  
`(@Status IS NULL OR Status = @Status)` và optional email filter làm cùng một statement phục vụ nhiều shapes có selectivity rất khác.

**Tại sao xảy ra:**  
Một plan tốt cho “không filter status/email” chưa chắc tốt cho một status hiếm hoặc search rất selective; behavior còn phụ thuộc SQL Server version/configuration/statistics và parameterization.

**Ảnh hưởng production:**  
Latency có thể biến động lớn theo parameter set; team dễ kết luận “index lúc được lúc không”.

**Cách sửa:**  
Trước hết capture actual execution plans/query-store evidence theo các parameter shapes. Có thể tách query variants/dynamic SQL parameterized an toàn cho các filter quan trọng, hoặc dùng database features phù hợp sau khi có evidence. Không mặc định thêm `OPTION (RECOMPILE)` cho mọi request vì nó có compilation cost.

### Medium — Date boundary semantics hiện tại dễ sai requirement

**Vấn đề:**  
Code dùng `>= @FromDate` và `<= @ToDate` sau `CONVERT(date, ...)`, nhưng chưa nói rõ `@ToDate` là ngày inclusive hay timestamp exclusive và timezone của UI.

**Tại sao xảy ra:**  
Calendar date của user và UTC timestamp trong database là hai concepts khác nhau.

**Ảnh hưởng production:**  
Order gần midnight có thể bị thiếu/thừa khi tenant/user ở timezone khác UTC; troubleshooting report không khớp UI.

**Cách sửa:**  
Define contract rõ: UI date range theo timezone nào, convert boundaries một lần ở application layer thành `[FromUtc, ToUtcExclusive)`, rồi query raw `datetime2`.

### Medium — “Thêm NOLOCK” không giải quyết root cause và thay đổi correctness semantics

**Vấn đề:**  
Team đề xuất `NOLOCK` để giảm blocking mà chưa có evidence blocking là nguyên nhân chính.

**Tại sao xảy ra:**  
`NOLOCK`/read-uncommitted cho phép dirty/inconsistent reads và không sửa deep offset, scans hay non-sargable predicates.

**Ảnh hưởng production:**  
Có thể giảm một số waits trong một số workload nhưng đổi lấy kết quả không đáng tin, trong khi CPU/reads gốc vẫn cao.

**Cách sửa:**  
Đo waits, blocking và execution plan trước. Nếu workload thực sự cần concurrency tốt hơn giữa readers/writers, đánh giá isolation strategy ở database/workload level; không dùng hint như performance patch mù.

### Low — Query trả `CustomerEmail` trực tiếp cần được cân nhắc về data minimization

**Vấn đề:**  
Back-office có thể cần email, nhưng đây là PII và hot query đang include field này.

**Tại sao xảy ra:**  
Projection/index design có thể vô tình mở rộng data exposure hoặc index footprint.

**Ảnh hưởng production:**  
Index lớn hơn và phạm vi PII trong data access/logging/export có thể tăng.

**Cách sửa:**  
Xác minh field có thực sự cần trong list view không. Nếu cần, giữ authorization/audit phù hợp; nếu không, loại khỏi projection/include. Đây không phải root cause latency chính.

## Phiên bản đề xuất

Giả sử API chủ yếu hỗ trợ “next page” theo thời gian và email search ở endpoint này được giới hạn thành exact match hoặc prefix search đã normalize.

Index baseline:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt_Id
ON dbo.Orders
(
    TenantId,
    CreatedAtUtc DESC,
    Id DESC
)
INCLUDE
(
    CustomerEmail,
    Status,
    TotalAmount
);
```

Page đầu:

```sql
SELECT TOP (@PageSize)
    o.Id,
    o.CustomerEmail,
    o.Status,
    o.TotalAmount,
    o.CreatedAtUtc
FROM dbo.Orders AS o
WHERE
    o.TenantId = @TenantId
    AND o.CreatedAtUtc >= @FromUtc
    AND o.CreatedAtUtc < @ToUtcExclusive
    AND (@Status IS NULL OR o.Status = @Status)
ORDER BY
    o.CreatedAtUtc DESC,
    o.Id DESC;
```

Page tiếp theo nhận cursor `(@LastCreatedAtUtc, @LastId)` từ row cuối page trước:

```sql
SELECT TOP (@PageSize)
    o.Id,
    o.CustomerEmail,
    o.Status,
    o.TotalAmount,
    o.CreatedAtUtc
FROM dbo.Orders AS o
WHERE
    o.TenantId = @TenantId
    AND o.CreatedAtUtc >= @FromUtc
    AND o.CreatedAtUtc < @ToUtcExclusive
    AND (@Status IS NULL OR o.Status = @Status)
    AND
    (
        o.CreatedAtUtc < @LastCreatedAtUtc
        OR (
            o.CreatedAtUtc = @LastCreatedAtUtc
            AND o.Id < @LastId
        )
    )
ORDER BY
    o.CreatedAtUtc DESC,
    o.Id DESC;
```

Nếu status filter là phổ biến và có selectivity đủ tốt, một index riêng như `(TenantId, Status, CreatedAtUtc DESC, Id DESC)` có thể đáng giá. Nhưng quyết định phải dựa trên workload/query plans và write amplification, không tạo một index cho mỗi optional filter một cách cơ học.

Với email, nên tách semantics:

```sql
-- Exact normalized email example
AND (@EmailNormalized IS NULL
     OR o.CustomerEmailNormalized = @EmailNormalized)
```

Sau đó cân nhắc index phù hợp nếu query shape đủ quan trọng. Nếu requirement bắt buộc contains search tự do trên hàng trăm triệu rows, đó là một access pattern khác và cần được benchmark/design riêng.

API response có thể trả opaque cursor thay vì raw page number:

```json
{
  "items": [ ... ],
  "nextCursor": "opaque-signed-or-encoded-cursor"
}
```

Cursor nên chứa đủ stable sort boundary và, nếu cần, filter/version metadata để server có thể validate rằng client không reuse cursor với query khác.

## Giải thích thiết kế sau khi sửa

Thiết kế chuyển từ “vị trí tương đối trong tập dữ liệu hiện tại” sang “tiếp tục từ stable key cuối đã nhìn thấy”. `(CreatedAtUtc, Id)` tạo total ordering, nên engine có thể seek/range từ boundary thay vì bỏ qua hàng trăm nghìn rows.

Index được align theo access pattern bắt buộc: tenant equality trước, sau đó ordering/pagination keys. Time filter vẫn áp trực tiếp lên raw column bằng half-open range, tránh function trên indexed timestamp.

Keyset pagination không giải quyết mọi requirement. Nó không cho phép nhảy trực tiếp tới “page 2.000” với chi phí O(1), và không tự tạo một immutable snapshot qua nhiều request. Nếu UI bắt buộc random page navigation hoặc exact total-page count, cần làm rõ product value và chấp nhận cost/thiết kế khác.

## Trade-offs

- Keyset pagination rất tốt cho next/previous traversal nhưng kém phù hợp với random jump theo page number.
- Composite covering index giảm reads cho hot query nhưng tăng storage và write amplification.
- Tách query variants theo optional filters có thể cho plan tốt hơn nhưng tăng code/query maintenance.
- Exact/prefix email search dễ tối ưu hơn arbitrary substring nhưng có thể thay đổi UX requirement.
- Snapshot-consistent browsing xuyên nhiều requests cần thêm state/version semantics và complexity; không nên thêm nếu user chỉ cần “latest list”.
- Thêm search engine có thể phù hợp với rich text/faceted search lớn nhưng tạo synchronization/eventual-consistency/operational cost đáng kể.

## Cách kiểm thử

1. **Database performance test:** seed data có distribution gần production (tenant lớn/nhỏ, status skew, timestamps trùng), so sánh actual execution plan, logical reads, CPU và duration giữa page đầu/page sâu cũ và keyset query.
2. **Pagination correctness test:** tạo nhiều rows cùng `CreatedAtUtc`; traverse toàn tập bằng cursor và xác minh không duplicate/skip.
3. **Concurrent-insert test:** insert orders mới trong lúc client lấy nhiều pages; xác minh keyset traversal không bị shift như OFFSET và document rõ semantics đối với rows mới.
4. **Filter-plan test:** benchmark combinations không status, status phổ biến/hiếm, exact email; kiểm tra Query Store/actual plans thay vì chỉ đo một parameter.
5. **Regression/load test:** chạy concurrent admin searches cùng write workload, theo dõi p95/p99, logical reads, CPU, lock/wait profile và write latency sau khi thêm index.

## Quan sát trong production

Theo dõi:

- Query Store: duration, CPU, logical reads, executions và plan changes của query family;
- actual/estimated execution plans từ representative parameter sets;
- index usage và maintenance/write overhead;
- waits, blocking và deadlocks trước khi kết luận cần isolation hint;
- p50/p95/p99 API latency theo filter shape và cursor depth;
- SQL CPU, I/O, memory grant/spill signals nếu có sort/hash pressure;
- timeout/error rate theo tenant/query type;
- alert khi logical reads hoặc p95 tăng đột biến sau deployment/index change;
- rollout theo canary hoặc staged deployment nếu query path có traffic lớn, với rollback plan cho index/API contract.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product bắt buộc cho phép nhảy trực tiếp tới page 2.000, bạn sẽ cân bằng UX, performance và consistency như thế nào?
2. Nếu `Status = 'Pending'` chỉ chiếm 0,1% rows nhưng được query rất nhiều, index strategy có thể thay đổi ra sao?
3. Nếu UI yêu cầu total count chính xác cùng mọi page, bạn sẽ đo cost và cân nhắc alternatives nào trước khi thêm cache?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message broker delivery và business side effect không tự tạo exactly-once processing; retry phải được thiết kế cùng idempotency.
- Swallow exception có thể thay đổi settlement semantics và biến retriable failure thành message loss.
- Database unique constraint là concurrency invariant mạnh hơn check-then-act trong application, nhưng không bảo vệ external side effect.
- Deep OFFSET pagination có cost tăng theo page depth và dễ bất ổn khi dataset thay đổi.
- Sargability, stable ordering và index key order phải xuất phát từ access pattern thực tế, không từ danh sách cột riêng lẻ.

## Mẫu tư duy cần nhớ

- Vẽ failure windows trước khi thiết kế retry.
- Đặt invariant ở nơi có thể enforce atomically.
- Design retry together with idempotency.
- Measure query plans/reads/waits before adding indexes or hints.
- Dùng stable cursor khi pagination phải hoạt động tốt trên dataset lớn và đang thay đổi.
