# Câu 1 — .NET: vì sao streaming file vẫn tăng memory khi client chậm?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18 phút  
**Kỹ năng được đánh giá:** C# async, ASP.NET Core, Stream, backpressure, GC, cancellation, Azure Blob Storage

## Bối cảnh

Một API .NET 8 làm gateway tải báo cáo từ Azure Blob Storage. Client có thể tải file 1–3 GB. Developer đổi từ `byte[]` sang `Stream` nhưng khi 300 client tải đồng thời qua mạng chậm, working set vẫn tăng, request kéo dài, đôi lúc pod bị OOMKilled. Một số request bị client hủy nhưng telemetry cho thấy tải Blob vẫn tiếp diễn. Pipeline còn có middleware ghi response body để audit; chưa rõ middleware có buffering hay không. Yêu cầu audit metadata, không cần lưu nội dung file.

## Câu hỏi chính

Giải thích cơ chế streaming, buffering, asynchronous I/O và backpressure từ Blob đến HTTP response; xác minh chính xác nơi memory tăng và đề xuất sửa mà không phá cancellation, audit và quyền truy cập.

## Câu hỏi làm rõ nên cân nhắc

1. Endpoint có `CopyToAsync`, `MemoryStream`, response buffering hay compression middleware nào?
2. Memory tăng là managed heap, LOH, native buffers hay page cache; có heap dump và allocation trace không?
3. Client có cần Range requests/resume, checksum và filename chính xác không?
4. Quyền tải Blob hiện được kiểm tra ở API hay qua SAS; dữ liệu có nhạy cảm không?
5. Proxy/CDN có timeout, buffering hoặc giới hạn connection nào?

## Gợi ý tư duy

### Gợi ý 1
`Stream` là abstraction, không tự bảo đảm end-to-end streaming.

### Gợi ý 2
Tìm các tầng tạo `byte[]` hoặc `MemoryStream`, kiểm tra tốc độ producer/consumer và cancellation.

### Gợi ý 3
Phân biệt throughput của Blob với tốc độ socket gửi client; kiểm tra `RequestAborted` và từng hop.

## Cấu trúc trả lời đề xuất

1. Xác nhận semantics tải file và audit.
2. Vẽ đường dữ liệu Blob → middleware → Kestrel → proxy → client.
3. Phân biệt buffered và streamed paths.
4. Đo allocations, GC, RSS, số download đồng thời, tốc độ mạng.
5. Chọn giải pháp, giới hạn tài nguyên, xử lý hủy.
6. Kiểm thử, rollout và theo dõi.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `Stream` có thể vẫn bị buffer ở middleware hoặc code ứng dụng; `MemoryStream` toàn file gây allocation lớn.
- `await CopyToAsync(response.Body, bufferSize, RequestAborted)` tạo đường truyền có backpressure khi writer chờ; kiểm tra từng tầng thay vì mặc định toàn pipeline không buffer.
- Truyền cancellation token tới thao tác Blob và copy; client disconnect không đồng nghĩa mọi tác vụ nền tự hủy.
- Phân biệt heap, native memory và OS cache trước khi kết luận memory leak.

### Điểm cộng
- Cân nhắc `FileStreamResult`, Range support, response headers, quota concurrent downloads.
- Audit metadata không cần body capture; dùng correlation ID và byte counts.

### Senior+
- So sánh backend proxy với short-lived user-scoped SAS/direct Blob download; kiểm soát quyền, thu hồi và logging.
- Phân tích slow-client resource exhaustion, proxy buffering và load shedding.

## Hướng giải quyết tham khảo

Đầu tiên lấy memory dump và `dotnet-counters` (GC heap size, allocation rate, LOH, Gen 2 collections), đồng thời đối chiếu RSS, active requests và thời lượng tải. Dùng tracing để đo Blob read, HTTP write và middleware; heap có nhiều `MemoryStream`/large arrays gợi ý buffering, còn RSS tăng không tương ứng managed heap cần kiểm tra native buffers và môi trường container.

Với quyền truy cập đã được kiểm tra phía server, có thể mở stream từ Blob rồi copy với bộ đệm hữu hạn:

```csharp
app.MapGet("/reports/{id}/download", async (
    string id, HttpContext http, IReportAccess access,
    BlobServiceClient blobs, CancellationToken ct) =>
{
    var report = await access.GetAuthorizedReportAsync(
        http.User, id, ct);
    if (report is null) return Results.NotFound();

    var blob = blobs.GetBlobContainerClient("reports")
                    .GetBlobClient(report.BlobName);
    var props = await blob.GetPropertiesAsync(cancellationToken: ct);
    http.Response.ContentType = "application/octet-stream";
    http.Response.ContentLength = props.Value.ContentLength;
    http.Response.Headers.ContentDisposition =
        "attachment; filename=\"report.bin\"";

    await using var source = await blob.OpenReadAsync(
        cancellationToken: ct);
    await source.CopyToAsync(http.Response.Body, 64 * 1024, ct);
    return Results.Empty;
}).RequireAuthorization();
```

Đây là ví dụ minh họa, cần rà soát xử lý lỗi sau khi headers được gửi, audit, request range và kiểm tra API/SDK thực tế trước khi đưa vào production. Không cố trả ProblemDetails sau khi response đã bắt đầu; ghi log với request ID và kết thúc connection thích hợp. Nếu cần resume, cân nhắc `Results.File` với seekable stream và `enableRangeProcessing` sau khi xác minh khả năng seek/semantics của source. Nếu tải lớn và quyền cho phép, SAS có scope và expiry ngắn giúp loại bỏ đường dữ liệu qua API, nhưng phải quản lý việc chia sẻ URL và audit.

Thử 300 slow clients, client disconnect và Blob throttling. Theo dõi p95 download duration, in-flight downloads, allocated bytes/request, RSS, GC pauses, aborted requests và downstream bandwidth. Quyết định chuyển kiến trúc tùy chính sách bảo mật, khả năng CDN và yêu cầu audit.

## Mẫu trả lời trong phỏng vấn

“Tôi không kết luận `Stream` sẽ dùng ít RAM nếu chưa kiểm tra toàn bộ pipeline. Tôi sẽ đo managed heap so với RSS, trace Blob read và HTTP write, tìm middleware audit đang buffer body. Khi client chậm, asynchronous copy cần chờ output để không đọc trước vô hạn. Tôi sẽ bỏ body capture, chỉ audit metadata, truyền `RequestAborted` xuyên suốt và giới hạn số download đồng thời. Sau đó load test với slow clients và disconnect. Nếu cần tải file lớn thường xuyên, tôi so sánh streaming proxy với scoped SAS; SAS giảm tải nhưng thay đổi mô hình kiểm soát quyền và audit.”

## Câu hỏi đào sâu

1. Nếu proxy bật buffering mặc dù ứng dụng đã stream, bạn chứng minh và khắc phục thế nào?
2. Nếu yêu cầu chống chia sẻ URL tuyệt đối, còn nên dùng SAS không?
3. Vì sao memory RSS tăng nhưng `GC.GetTotalMemory` ổn định?

## Lỗi trả lời thường gặp

- Coi mọi `Stream` là zero-copy và không buffer.
- Dùng `Task.Run` cho I/O streaming để “tăng tốc”.
- Không truyền cancellation hoặc không test disconnect.
- Tăng memory limit trước khi xác định nguồn allocation.
- Đề xuất SAS mà không xem xét authorization và audit.

## Thang điểm 0–10

- 1 điểm: làm rõ yêu cầu và đường dữ liệu.
- 2 điểm: giải thích buffering, async I/O, backpressure.
- 2 điểm: phân tích memory và xác minh bằng telemetry.
- 2 điểm: giải pháp cancellation, bounded resources, security.
- 2 điểm: trade-offs, load/failure testing, monitoring.
- 1 điểm: diễn đạt logic, phân biệt giả định với bằng chứng.

# Câu 2 — IIS/Windows Server: 503 sau release nhưng CPU thấp

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC/.NET Framework, CI/CD, Octopus Deploy, incident response, observability

## Bối cảnh

Một portal nội bộ ASP.NET MVC chạy .NET Framework 4.5 trên IIS/Windows Server, deploy bằng TeamCity + Octopus Deploy tới hai máy sau load balancer. Sau release, khoảng 12% request trả 503, số khác trả 200; CPU tổng thấp. Một số người dùng bị logout. Event Viewer có sự kiện App Pool recycle nhưng không rõ trước hay sau lỗi. Release có thay đổi `web.config`, connection string và thêm background warm-up; chỉ một node đã nhận config mới khi cảnh báo đầu tiên xuất hiện. Không được phép mất dữ liệu, rollback tối đa 10 phút.

## Câu hỏi chính

Hãy dẫn dắt incident từ bảo vệ người dùng tới xác định nguyên nhân, phân biệt App Pool failure, health routing, deployment/configuration, dependency failure và session affinity; đưa ra kế hoạch khắc phục có thể kiểm chứng.

## Câu hỏi làm rõ nên cân nhắc

1. 503 phát ra từ IIS, load balancer hay upstream proxy; status subcode, `sc-win32-status` và node ID?
2. App Pool đang stopped, rapid-fail protection, recycle theo lịch, memory limit hay config change?
3. Session dùng InProc, StateServer hay SQL; có sticky sessions và machineKey nhất quán không?
4. Octopus deploy song song hay tuần tự, health gate/rollback và artifact checksum thế nào?
5. Có thay đổi secrets, ACL, app identity, database schema hay runtime dependencies?

## Gợi ý tư duy

### Gợi ý 1
Không coi 503 là một nguyên nhân duy nhất.

### Gợi ý 2
Gắn timestamp của 503 với IIS logs, WAS events, deploy steps và từng node.

### Gợi ý 3
Phân biệt request routing tới node không healthy với process recycle và session mất khi worker process khởi động lại.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius và mức độ ảnh hưởng.
2. Stabilize: drain node xấu, rollback nếu cần và an toàn.
3. Thu thập chứng cứ có timestamp và node ID.
4. Lập ít nhất ba giả thuyết đối lập.
5. Kiểm tra từng giả thuyết, tránh thay đổi nhiều biến cùng lúc.
6. Xác định root cause khi bằng chứng đủ.
7. Remediate, verify và phòng ngừa.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Tách lỗi theo node, substatus và thời điểm.
- Kiểm tra WAS/App Pool, IIS logs, Event Viewer, health probe và release diff.
- Không rollback schema phá dữ liệu; ưu tiên rollback binary/config tương thích và drain.
- Logout có thể do InProc session/recycle hoặc machineKey/session affinity; không kết luận khi chưa kiểm tra.

### Điểm cộng
- Correlate artifact version, config hash, node health, request ID.
- Kiểm tra rapid-fail protection, identity/ACL, startup failure, dependency timeouts.

### Senior+
- Thiết kế deployment wave + health gate, immutable artifact, config validation, expand-contract database migration và runbook rollback.
- Phân biệt “CPU thấp” với app không nhận request hoặc dependency wait.

## Hướng giải quyết tham khảo

Trong 5 phút đầu, xác định tỷ lệ lỗi theo node và request path, kích hoạt incident communication, tạm ngừng rollout. Nếu một node lỗi, drain nó ở load balancer để giảm 503, không restart cả cluster. Xác minh node còn lại có đủ capacity và không tạo single-point overload. Nếu release thay đổi schema, kiểm tra backward compatibility trước khi rollback binary.

Thu IIS access logs (`sc-status`, `sc-substatus`, `sc-win32-status`, time-taken), HTTPERR, Windows Event Viewer (WAS, W3SVC), App Pool state, Failed Request Tracing nếu phù hợp, Octopus deployment timeline và diff config. Ba giả thuyết: (A) config mới làm startup crash/rapid fail, (B) health probe route tới node đang deploy, (C) dependency DB/credential khiến warm-up thất bại; logout là triệu chứng độc lập của InProc session hoặc machineKey mismatch. Đối chiếu event timing, worker process PID và node IDs. Nếu startup fail chỉ trên node mới, thử xác nhận trong môi trường cô lập, không sửa trực tiếp production khi chưa lưu bằng chứng.

Khắc phục có điều kiện: sửa config/secrets/ACL nếu được chứng minh; health probe chỉ cho nhận traffic sau startup readiness; rolling deploy một node một lần, drain trước khi recycle, smoke test rồi mới đưa vào pool. Với session, chuyển khỏi InProc khi cần survive recycle và cấu hình cryptographic keys đồng nhất phù hợp framework; không coi sticky sessions là bảo đảm continuity qua recycle. Dùng deployment artifact cố định, configuration diff validation và alert theo node, App Pool recycle rate, 503 substatus, login failure, dependency latency. Test rollout failure và rollback với schema đã migrate.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ đóng băng rollout, phân đoạn lỗi theo node, giảm tác động bằng cách drain node không healthy và kiểm tra capacity còn lại. Tôi không kết luận App Pool recycle là root cause chỉ vì Event Viewer có event đó. Tôi ghép IIS/HTTPERR logs, WAS events, PID và Octopus timeline, rồi kiểm tra config, health probe và dependency. Logout có thể liên quan InProc session nhưng cũng có thể là vấn đề machineKey hoặc affinity. Khi xác định được nguyên nhân, tôi khắc phục ở một node, smoke test và rollout tuần tự; rollback chỉ khi tương thích với database. Tôi sẽ bổ sung readiness gate, config validation và diễn tập rollback.”

## Câu hỏi đào sâu

1. Nếu App Pool không recycle nhưng IIS vẫn trả 503, bạn sẽ điều tra gì tiếp?
2. Nếu rollback binary không tương thích schema mới, bạn xử lý thế nào trong 10 phút?
3. Có nên chuyển ngay portal này sang Kubernetes để tránh incident tương tự không? Vì sao?

## Lỗi trả lời thường gặp

- Restart cả hai node trước khi thu thập evidence.
- Coi CPU thấp là bằng chứng DB không lỗi.
- Đồng nhất 503 với app crash.
- Rollback migration có thể mất dữ liệu.
- Đề xuất đổi hosting platform thay cho root-cause analysis.

## Thang điểm 0–10

- 2 điểm: impact, communication, stabilization.
- 2 điểm: chứng cứ theo node và timestamp.
- 2 điểm: giả thuyết đối lập, xác minh root cause.
- 2 điểm: rollback an toàn, session và deployment.
- 1 điểm: monitoring, failure testing.
- 1 điểm: giao tiếp rõ và có thứ tự ưu tiên.

# Câu 3 — Thiết kế đồng bộ product catalog từ CMS sang search và storefront

**Loại câu hỏi:** Architecture / system design / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Elasticsearch, e-commerce, Azure Service Bus, SQL, Akamai, Vue.js, ownership boundaries

## Bối cảnh

Một storefront Vue.js hiển thị sản phẩm từ hệ thống commerce, nội dung marketing từ Optimizely CMS và kết quả tìm kiếm từ Elasticsearch. Product price/stock cập nhật thường xuyên, CMS publish theo giờ, search index đôi lúc chậm vài phút. Dự kiến 200.000 SKU, nhiều locale, traffic đột biến trong chiến dịch. Business muốn “giá và tồn kho đúng”, “publish nội dung trong 1 phút”, và trang category tải nhanh. Chưa có định nghĩa SLA consistency, chưa rõ hệ thống nào là source of truth. Team đề xuất microservices + Service Bus cho mọi cập nhật và cache mọi endpoint ở Akamai.

## Câu hỏi chính

Hãy thiết kế ownership, API/read model, data synchronization, caching, consistency, failure recovery và rollout; so sánh phương án đơn giản với event-driven integration, nêu rõ khi nào mỗi phương án phù hợp.

## Câu hỏi làm rõ nên cân nhắc

1. Giá/stock có phải real-time khi checkout hay chỉ gần đúng ở listing; có reservation inventory không?
2. Commerce/CMS có webhook/change feed hoặc polling API với rate limit và version không?
3. SLA publish/search freshness và tolerance stale của từng loại dữ liệu?
4. Dữ liệu có personalized pricing/tenant/locale và yêu cầu cache privacy nào?
5. Team vận hành, ngân sách, peak RPS, RTO/RPO và chiến lược rollback?

## Gợi ý tư duy

### Gợi ý 1
Bắt đầu từ data ownership và các mức consistency khác nhau.

### Gợi ý 2
Tách search discovery khỏi xác nhận giá/tồn kho khi checkout.

### Gợi ý 3
Thiết kế idempotent update, version ordering, replay và reindex trước khi thêm queue.

## Cấu trúc trả lời đề xuất

1. Xác nhận source of truth và SLA.
2. Vẽ boundaries commerce/CMS/search/storefront.
3. Chọn sync API hay async events theo nhu cầu.
4. Thiết kế product projection, version, locale và security.
5. Xử lý cache/CDN, lỗi downstream và reindex.
6. So sánh operational cost, test và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Commerce sở hữu giá và tồn kho giao dịch; CMS sở hữu nội dung; Elasticsearch là read projection, không phải source of truth.
- Search index có thể eventual consistent; checkout phải validate giá/stock qua commerce authority.
- Cache key và TTL khác nhau cho public CMS content và personalized prices.
- Cần cơ chế retry, dedupe, out-of-order handling và reconciliation nếu dùng event pipeline.

### Điểm cộng
- Outbox nếu sự kiện phát từ DB transaction thuộc quyền kiểm soát; nếu vendor API thì dùng versioned polling/webhooks và reconciliation.
- Index alias/versioned reindex, poison events, backfill và lag dashboard.

### Senior+
- Định nghĩa freshness SLO theo từng domain, degrade gracefully khi search hỏng, kiểm soát chi phí vận hành và migration từng bước.
- Không áp dụng microservices mặc định; integration module trong Modular Monolith có thể đủ.

## Hướng giải quyết tham khảo

Đề xuất đầu tiên là xác nhận hợp đồng: commerce authority cho giá, inventory và checkout; CMS cho editorial content; Elasticsearch chỉ hỗ trợ tìm kiếm. Với listing, projection chứa product ID, locale, search fields, public price snapshot và `indexedVersion`; nếu giá theo user thì không lưu/cache công khai. Storefront lấy kết quả search rồi dùng batch API commerce để refresh giá/stock nếu business yêu cầu độ mới cao. Checkout bắt buộc revalidate theo transaction/reservation của commerce; UI phải hiển thị khi giá đổi.

Nếu cập nhật ít và SLA cho phép, một integration worker polling có cursor/version, batch upsert và reconciliation định kỳ đơn giản hơn queue. Nếu volume lớn hoặc nhiều consumer cần event, dùng Service Bus và idempotent consumer: event ID/version, per-product ordering strategy, retry có backoff, dead-letter triage, replay và full reconciliation. Không giả định delivery exactly-once; out-of-order event chỉ được áp dụng nếu version mới hơn. Khi reindex, xây index mới, verify counts/samples và đổi alias atomically theo khả năng Elasticsearch; duy trì rollback path. Không ghi dữ liệu search trở lại commerce.

Akamai cache public CMS pages/assets với key gồm locale và các biến thể public, invalidation sau publish theo SLA; giá cá nhân và authenticated responses không đi vào shared cache. Đặt freshness headers, cache hit/miss telemetry và origin fallback. Khi search outage, hiển thị category fallback có giới hạn hoặc thông báo tìm kiếm tạm không khả dụng; checkout không dựa vào stale index. Với team nhỏ, triển khai integration module + worker trong ứng dụng hiện có trước, tách service chỉ khi scaling/ownership thực sự đòi hỏi.

Testing: contract test commerce/CMS, duplicate/out-of-order event, replay sau outage, reindex while serving, stale price checkout, load test campaign và Playwright E2E cho publish/search/checkout. Telemetry: publish-to-visible lag p95/p99, index lag, DLQ depth, indexing errors, search latency, commerce dependency failures, CDN hit ratio và mismatch price. Rollout shadow index, compare samples, canary traffic, rollback alias nếu sai.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ chốt source of truth trước: commerce quyết định giá và tồn kho, CMS quyết định nội dung, Elasticsearch chỉ là read model. Tôi phân biệt freshness của listing với correctness của checkout; checkout luôn xác nhận lại ở commerce. Với team nhỏ và số cập nhật chưa rõ, tôi bắt đầu bằng integration worker có version và reconciliation, không mặc định microservices. Nếu cần nhiều consumer hoặc throughput cao, Service Bus hữu ích nhưng phải xử lý duplicate, ordering, replay và DLQ. Tôi cache public CMS content tại CDN, không cache personalized price trong shared cache. Tôi đo index lag, stale checkout và khả năng phục hồi trước khi mở rộng kiến trúc.”

## Câu hỏi đào sâu

1. Nếu commerce không cung cấp version hoặc change feed đáng tin, bạn đảm bảo reconciliation ra sao?
2. Nếu business yêu cầu mọi kết quả search phản ánh tồn kho tức thời, bạn sẽ thương lượng SLA hay thay đổi thiết kế thế nào?
3. Khi nào Service Bus/microservices làm hệ thống tệ hơn một worker trong Modular Monolith?

## Lỗi trả lời thường gặp

- Cho Elasticsearch làm authority cho checkout.
- Cache giá cá nhân ở CDN public.
- Giả định event luôn đúng thứ tự, chỉ gửi một lần.
- Đề xuất toàn bộ microservices mà không có cost/operational justification.
- Không có replay/reconciliation hoặc đo freshness.
