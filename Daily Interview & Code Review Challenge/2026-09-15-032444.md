# Code Review Challenge 1 — `Parallel.ForEachAsync` làm batch nhanh hơn nhưng EF Core bắt đầu lỗi ngẫu nhiên dưới tải

**Chủ đề:** C#/.NET 8, EF Core, concurrency, `DbContext` lifetime, bounded parallelism, cancellation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép supervisor chạy lại việc tính eligibility cho tối đa 500 employees sau khi policy thay đổi.

Mỗi employee cần:

- đọc employee và policy data từ SQL Server qua EF Core;
- gọi một external HR API để lấy trạng thái mới nhất;
- cập nhật một vài fields trong database;
- ghi audit record.

Phiên bản cũ xử lý tuần tự nên chậm. Developer thay bằng `Parallel.ForEachAsync` để giảm thời gian batch.

Production bắt đầu xuất hiện:

- thỉnh thoảng `InvalidOperationException` liên quan một operation mới bắt đầu trên `DbContext` trước khi operation trước hoàn tất;
- đôi lúc thiếu một vài audit rows;
- external HR API bị tăng request burst mạnh;
- cùng một request có lúc hoàn thành trong 8 giây, có lúc hơn 40 giây;
- SQL CPU chưa cao nhưng connection usage tăng;
- lỗi chủ yếu xuất hiện khi batch có vài trăm employees hoặc nhiều supervisors chạy batch đồng thời.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class EligibilityService
{
    private readonly AppDbContext _db;
    private readonly IHrClient _hr;
    private readonly ILogger<EligibilityService> _logger;

    public EligibilityService(
        AppDbContext db,
        IHrClient hr,
        ILogger<EligibilityService> logger)
    {
        _db = db;
        _hr = hr;
        _logger = logger;
    }

    public async Task RecalculateAsync(
        IReadOnlyCollection<Guid> employeeIds,
        CancellationToken cancellationToken)
    {
        var auditRows = new List<EligibilityAudit>();

        await Parallel.ForEachAsync(
            employeeIds,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 32,
                CancellationToken = cancellationToken
            },
            async (employeeId, ct) =>
            {
                var employee = await _db.Employees
                    .SingleAsync(x => x.Id == employeeId, ct);

                var policy = await _db.Policies
                    .SingleAsync(x => x.Id == employee.PolicyId, ct);

                var hrStatus = await _hr.GetStatusAsync(employee.ExternalId, ct);

                employee.IsEligible =
                    policy.IsEnabled && hrStatus.IsActive;

                auditRows.Add(new EligibilityAudit
                {
                    EmployeeId = employee.Id,
                    NewValue = employee.IsEligible,
                    CreatedAt = DateTimeOffset.UtcNow
                });
            });

        _db.EligibilityAudits.AddRange(auditRows);
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Recalculated eligibility for {Count} employees",
            employeeIds.Count);
    }
}
```

## Câu hỏi gợi mở

1. Một scoped `DbContext` có thể được dùng đồng thời từ nhiều iterations hay không?
2. `List<T>.Add` từ nhiều parallel callbacks có phải shared mutable state an toàn không?
3. `MaxDegreeOfParallelism = 32` đang bảo vệ dependency nào, và con số đó được chọn dựa trên evidence gì?
4. Có cần query `Policy` riêng cho từng employee không?
5. Nếu external HR API timeout ở một employee, batch nên fail toàn bộ, retry một phần hay tiếp tục phần còn lại?

## Gợi ý

### Gợi ý 1

Đừng coi `async` là đồng nghĩa với thread-safe. Hãy kiểm tra những object nào đang được chia sẻ giữa các iterations.

### Gợi ý 2

Tách pipeline thành các phần có concurrency characteristics khác nhau: database access, external I/O và database write không nhất thiết nên dùng cùng một mức parallelism.

## Kết quả code review tham khảo

### Critical — Dùng cùng một `DbContext` cho nhiều operations song song

**Vấn đề:**  
`_db` là scoped `AppDbContext`, nhưng mọi callback của `Parallel.ForEachAsync` cùng gọi query trên instance đó.

**Tại sao xảy ra:**  
`DbContext` không được thiết kế để thực hiện nhiều operations đồng thời. Một iteration có thể đang chờ query trong khi iteration khác bắt đầu query mới trên cùng context.

**Ảnh hưởng production:**  
Có thể phát sinh exception, batch fail không ổn định và behavior phụ thuộc timing. Tải càng cao thì xác suất overlap càng lớn.

**Cách sửa:**  
Không chia sẻ một `DbContext` giữa parallel operations. Ưu tiên giảm số queries bằng cách đọc dữ liệu cần thiết theo batch trước khi parallel external I/O. Nếu thực sự cần database work song song, tạo scope/context độc lập cho từng work item hoặc bounded worker, nhưng chỉ sau khi chứng minh parallel DB access là cần thiết.

---

### High — `List<EligibilityAudit>` bị mutate đồng thời

**Vấn đề:**  
Nhiều callbacks gọi `auditRows.Add(...)` trên cùng `List<T>`.

**Tại sao xảy ra:**  
`List<T>` không phải concurrent collection. Concurrent writes có thể race và làm kết quả không đáng tin cậy.

**Ảnh hưởng production:**  
Có thể thiếu audit rows hoặc gặp corruption/exception tùy timing.

**Cách sửa:**  
Tránh shared mutable state. Mỗi iteration trả về result riêng rồi aggregate sau khi parallel phase hoàn tất, hoặc dùng một cấu trúc concurrent khi thật sự phù hợp.

---

### High — Parallelism 32 có thể khuếch đại tải lên HR API

**Vấn đề:**  
Mỗi request được phép tạo tới 32 HR calls đồng thời. Nếu 20 supervisors chạy batch, dependency có thể thấy hàng trăm calls cùng lúc.

**Tại sao xảy ra:**  
`MaxDegreeOfParallelism` là per batch, không phải global budget cho process/dependency.

**Ảnh hưởng production:**  
429/throttling, timeout, retry amplification và tail latency có thể tăng dù mỗi batch riêng lẻ có vẻ nhanh hơn.

**Cách sửa:**  
Đặt bounded concurrency theo capacity/SLO của HR API. Nếu cần protection toàn service, dùng shared concurrency limiter/rate limiter hoặc queueing strategy thay vì chỉ limit riêng từng request.

---

### High — N+1 database access pattern trong parallel loop

**Vấn đề:**  
Mỗi employee chạy ít nhất hai queries: employee và policy.

**Tại sao xảy ra:**  
Implementation tối ưu wall-clock bằng parallelism nhưng không giảm tổng lượng database work.

**Ảnh hưởng production:**  
Batch 500 employees có thể tạo khoảng 1.000 queries trước cả `SaveChanges`. Nhiều batches đồng thời làm connection pool và database phải xử lý workload lớn không cần thiết.

**Cách sửa:**  
Load employee projection và policy data cần thiết bằng một số lượng queries bounded, ví dụ join/projection hoặc pre-load policies theo distinct IDs, rồi parallelize chỉ phần external I/O nếu cần.

---

### High — Failure semantics của batch không được định nghĩa

**Vấn đề:**  
Một HR call throw có thể làm toàn operation thất bại sau khi nhiều calls khác đã chạy; code không mô tả partial-success, retry hoặc reconciliation behavior.

**Tại sao xảy ra:**  
`Parallel.ForEachAsync` chỉ là execution primitive; nó không tự cung cấp business transaction cho external side effects và database state.

**Ảnh hưởng production:**  
Client có thể retry toàn batch dù một phần work đã thực hiện external reads, tạo burst lặp lại và khó biết employee nào cần retry.

**Cách sửa:**  
Định nghĩa explicit contract: fail-fast, best-effort với per-item result, hoặc durable background job. Với batch lớn/quan trọng, lưu per-item status hoặc job checkpoint để retry có mục tiêu.

---

### Medium — Change tracking giữ nhiều entities đến cuối batch

**Vấn đề:**  
Tất cả loaded `Employee` entities được tracked tới `SaveChangesAsync` cuối cùng.

**Tại sao xảy ra:**  
Một `DbContext` sống xuyên suốt batch và materialize nhiều entities.

**Ảnh hưởng production:**  
Memory/change-tracking overhead tăng theo batch size. Với limit 500 có thể chấp nhận, nhưng cần đo và không nên giả định scale tuyến tính vô hạn.

**Cách sửa:**  
Dùng bounded batch size và projection khi có thể. Nếu workload lớn hơn, chia thành chunks/worker jobs với transaction boundary rõ.

---

### Medium — Không xử lý duplicate employee IDs rõ ràng

**Vấn đề:**  
Input là `IReadOnlyCollection<Guid>` nhưng không đảm bảo uniqueness.

**Tại sao xảy ra:**  
Cùng employee có thể được xử lý hai lần trong một request nếu caller gửi duplicate IDs.

**Ảnh hưởng production:**  
Tăng dependency calls, audit duplication và tạo thêm race trên cùng entity.

**Cách sửa:**  
Validate/deduplicate input theo business contract trước khi thực hiện work.

---

### Medium — Telemetry chỉ ghi số input, không ghi behavior thực tế

**Vấn đề:**  
Log cuối không cho biết số thành công/thất bại, database query count, HR latency/throttling hay concurrency.

**Tại sao xảy ra:**  
Observability được thêm ở result-level thay vì execution-level.

**Ảnh hưởng production:**  
Khó chứng minh bottleneck nằm ở DB, HR API hay scheduler và khó chọn mức concurrency hợp lý.

**Cách sửa:**  
Ghi metrics/traces cho batch size, success/failure count, HR call latency/status, active concurrency, DB dependency count/duration, total duration và cancellation.

## Phiên bản đề xuất

Một design đơn giản hơn là đọc database theo batch, sau đó chỉ parallelize phần external I/O với bounded concurrency và aggregate results không dùng shared mutable state:

```csharp
public async Task RecalculateAsync(
    IReadOnlyCollection<Guid> employeeIds,
    CancellationToken cancellationToken)
{
    var ids = employeeIds.Distinct().ToArray();

    var employees = await _db.Employees
        .Where(x => ids.Contains(x.Id))
        .Select(x => new
        {
            x.Id,
            x.ExternalId,
            x.PolicyId
        })
        .ToListAsync(cancellationToken);

    var policyIds = employees.Select(x => x.PolicyId).Distinct().ToArray();

    var policies = await _db.Policies
        .Where(x => policyIds.Contains(x.Id))
        .ToDictionaryAsync(x => x.Id, cancellationToken);

    var results = new ConcurrentDictionary<Guid, bool>();

    await Parallel.ForEachAsync(
        employees,
        new ParallelOptions
        {
            MaxDegreeOfParallelism = 8,
            CancellationToken = cancellationToken
        },
        async (employee, ct) =>
        {
            var hrStatus = await _hr.GetStatusAsync(employee.ExternalId, ct);
            var policy = policies[employee.PolicyId];
            results[employee.Id] = policy.IsEnabled && hrStatus.IsActive;
        });

    var trackedEmployees = await _db.Employees
        .Where(x => results.Keys.Contains(x.Id))
        .ToListAsync(cancellationToken);

    foreach (var employee in trackedEmployees)
    {
        employee.IsEligible = results[employee.Id];
        _db.EligibilityAudits.Add(new EligibilityAudit
        {
            EmployeeId = employee.Id,
            NewValue = employee.IsEligible,
            CreatedAt = DateTimeOffset.UtcNow
        });
    }

    await _db.SaveChangesAsync(cancellationToken);
}
```

Đây vẫn chỉ là một hướng tham khảo. Con số `8` không phải giá trị mặc định đúng cho production; nó phải dựa trên capacity, rate limits, latency và load test. Nếu nhiều request đồng thời vẫn có thể vượt global HR API budget, cần limiter dùng chung ở application/process level hoặc chuyển thành queued background work.

## Giải thích thiết kế sau khi sửa

Database read không còn chạy song song trên một `DbContext`. Query count được bounded thay vì tỷ lệ trực tiếp 2× số employees. Parallelism chỉ được dùng ở phần external I/O độc lập và kết quả được gom bằng state an toàn.

Database update diễn ra sau parallel phase trên một execution flow. Điều này đơn giản hơn việc tạo hàng trăm DbContexts song song và thường là lựa chọn tốt hơn nếu SQL không phải bottleneck.

Nếu batch có thể lớn hơn đáng kể, chạy hàng chục phút hoặc cần retry từng item sau restart, tôi sẽ cân nhắc chuyển thành durable background job. HTTP request chỉ tạo job; worker xử lý theo chunks, lưu progress và retry per-item theo policy. Đó là complexity chỉ nên thêm khi requirement về durability/scale biện minh.

## Trade-offs

- Preloading theo batch giảm round trips nhưng tăng lượng dữ liệu giữ trong memory; cần batch-size limit.
- Lower concurrency bảo vệ dependency nhưng batch có thể lâu hơn.
- Global limiter bảo vệ HR API tốt hơn nhưng các requests cạnh tranh capacity và cần timeout/queue policy rõ.
- Một transaction cuối cùng đơn giản nhưng batch rất lớn có thể giữ transaction/write set lớn; chunking có thể phù hợp hơn nhưng tạo partial-completion semantics.
- Durable job tăng reliability cho long-running work nhưng thêm persistence, job lifecycle và operational complexity.

## Cách kiểm thử

1. **Concurrency test:** batch 500 employees phải không tạo concurrent operations trên cùng `DbContext` và đủ audit rows.
2. **Load test:** nhiều batches đồng thời; đo HR active concurrency, 429, p95/p99 và DB connection usage.
3. **Failure injection:** HR API timeout/429 ở một số items; xác minh behavior đúng với contract fail-fast/best-effort đã chọn.
4. **Cancellation test:** cancel giữa batch; xác minh external calls dừng sớm và database không commit state trái contract.
5. **Duplicate-input test:** gửi IDs trùng và xác minh chỉ xử lý theo semantics đã định.

## Quan sát trong production

Theo dõi ít nhất:

- batch size và duration;
- active HR calls / configured concurrency budget;
- HR dependency p95/p99, 429, timeout, retry count;
- SQL query count/duration theo batch;
- DB connection pool usage;
- per-batch success/failure/cancelled item count;
- exception rate, đặc biệt EF Core concurrency exceptions;
- `SaveChanges` duration và affected rows.

# Code Review Challenge 2 — Canonical redirect tưởng tốt cho SEO nhưng tạo redirect loop và có nguy cơ redirect sang host do client điều khiển

**Chủ đề:** ASP.NET Core, HTTP, reverse proxy/CDN, SEO engineering, canonical URL, forwarded headers, security, redirects  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một public marketing site ASP.NET Core chạy sau CDN và reverse proxy. Business muốn:

- mọi request public dùng HTTPS;
- hostname canonical là `www.example.com`;
- `/products/abc/` và `/products/abc` không tạo duplicate URLs;
- redirect cũ phải giữ SEO value;
- POST/API endpoints không được vô tình đổi method hoặc bị đưa qua canonical redirect logic dành cho pages;
- application chạy ở nhiều environments với host khác nhau.

Sau khi thêm middleware canonicalization, production xuất hiện:

- một số users gặp redirect loop khi CDN terminate TLS nhưng origin nhận HTTP;
- staging đôi lúc redirect sang production host;
- security review phát hiện application xây redirect URL từ request host;
- `/api/forms/submit` đôi lúc nhận redirect không mong muốn;
- crawler report thấy cả 301 và 302 cho cùng nhóm URL tùy route.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class CanonicalUrlMiddleware
{
    private readonly RequestDelegate _next;

    public CanonicalUrlMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var request = context.Request;

        if (!request.IsHttps)
        {
            var httpsUrl = $"https://{request.Host}{request.Path}{request.QueryString}";
            context.Response.Redirect(httpsUrl, permanent: true);
            return;
        }

        if (!request.Host.Host.StartsWith("www."))
        {
            var canonicalHost = "www." + request.Host.Host;
            var url = $"{request.Scheme}://{canonicalHost}{request.Path}{request.QueryString}";
            context.Response.Redirect(url, permanent: false);
            return;
        }

        if (request.Path.Value is { Length: > 1 } path && path.EndsWith('/'))
        {
            var url = path.TrimEnd('/') + request.QueryString;
            context.Response.Redirect(url, permanent: true);
            return;
        }

        await _next(context);
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review middleware như một thay đổi chuẩn bị rollout cho website public.

Bạn cần:

1. xác định correctness/security/SEO issues;
2. giải thích production impact khi chạy sau proxy/CDN;
3. phân biệt redirect policy cho pages với APIs/non-idempotent methods;
4. ưu tiên findings theo severity;
5. đề xuất corrected design;
6. nêu cách test ở local/staging/proxy environment;
7. nêu telemetry để phát hiện redirect loop hoặc canonicalization regression.

## Câu hỏi gợi mở

1. `Request.IsHttps` phản ánh client-facing scheme hay origin-facing scheme khi TLS terminate ở proxy?
2. `Request.Host` có luôn là một trusted canonical host không?
3. `StartsWith("www.")` có xử lý đúng staging/custom domains/ports không?
4. Redirect một POST bằng status code thông thường có thể ảnh hưởng method/body thế nào?
5. Canonicalization có nên áp dụng cho `/api`, health probes, admin routes và static assets giống public pages không?

## Gợi ý

### Gợi ý 1

Canonicalization chỉ đúng khi application hiểu **effective external request** sau trusted proxy processing.

### Gợi ý 2

Host canonical nên đến từ trusted configuration/domain mapping, không nên được suy ra bằng cách sửa chuỗi từ arbitrary incoming Host header.

## Dừng lại và tự review

## Kết quả code review tham khảo

### Critical — Redirect target được xây từ incoming `Host`

**Vấn đề:**  
Middleware dùng `request.Host` rồi thêm `www.` để tạo redirect URL.

**Tại sao xảy ra:**  
Incoming Host không nên tự động được coi là authority cho canonical destination. Nếu deployment/proxy không giới hạn Host đúng cách, client có thể ảnh hưởng redirect target.

**Ảnh hưởng production:**  
Có thể tạo open-redirect/host-header abuse, phishing-friendly links hoặc cache poisoning tùy hạ tầng phía trước.

**Cách sửa:**  
Canonical host phải lấy từ trusted application configuration hoặc explicit host-to-canonical mapping. Đồng thời cấu hình proxy/application host filtering phù hợp và chỉ trust forwarded headers từ known proxies/networks.

---

### High — `IsHttps` có thể sai khi TLS terminate ở reverse proxy

**Vấn đề:**  
Origin có thể nhận HTTP dù browser đã dùng HTTPS. Nếu forwarded scheme không được xử lý đúng, middleware luôn nghĩ request chưa HTTPS.

**Tại sao xảy ra:**  
Application đang dựa vào origin connection scheme thay vì effective external scheme.

**Ảnh hưởng production:**  
Redirect loop: client HTTPS → CDN → origin HTTP → app redirect HTTPS → client HTTPS → lặp lại.

**Cách sửa:**  
Thiết lập forwarded-header processing đúng thứ tự trước canonicalization, chỉ trust forwarded headers từ hạ tầng proxy đã cấu hình. Hoặc thực hiện HTTPS/canonical host redirect ở edge nếu đó là boundary đáng tin cậy và đơn giản hơn.

---

### High — Canonical host logic bằng `StartsWith("www.")` không phản ánh domain policy

**Vấn đề:**  
Code biến bất kỳ host nào không bắt đầu bằng `www.` thành `www.<incoming-host>`.

**Tại sao xảy ra:**  
Domain policy bị encode thành string manipulation thay vì environment-aware trusted configuration.

**Ảnh hưởng production:**  
Staging/custom domains có thể redirect sai; port/host aliases có thể tạo URL không hợp lệ hoặc sang environment khác.

**Cách sửa:**  
Định nghĩa allowed hosts và canonical host theo environment. Chỉ redirect các known public aliases sang canonical target tương ứng.

---

### High — Middleware áp dụng redirect cho mọi HTTP method và mọi route

**Vấn đề:**  
`POST /api/forms/submit` có thể bị redirect giống GET page.

**Tại sao xảy ra:**  
Canonicalization không phân biệt browser page navigation với API/non-idempotent operation.

**Ảnh hưởng production:**  
Client có thể đổi behavior khi theo redirect, mất body/method tùy redirect semantics/client, hoặc fail request. API consumers cũng nhận response contract ngoài dự kiến.

**Cách sửa:**  
Scope canonical page redirects vào safe methods/routes, thường GET/HEAD public content. Với APIs, thiết kế base URL đúng ở gateway/client và tránh page-style SEO redirect. Nếu redirect non-GET thực sự cần thiết, chọn status semantics có chủ đích và test clients cụ thể.

---

### Medium — Permanent/temporary redirect policy không nhất quán

**Vấn đề:**  
HTTPS và trailing slash dùng permanent redirect, host canonicalization dùng temporary redirect.

**Tại sao xảy ra:**  
Status code được chọn theo implementation convenience thay vì migration/SEO policy.

**Ảnh hưởng production:**  
Crawler/cache behavior không nhất quán; canonical signals có thể mất thời gian ổn định và rollback khó nếu permanent redirect bị cache ngoài dự kiến.

**Cách sửa:**  
Định nghĩa redirect matrix: legacy URL migration, scheme normalization, canonical host và trailing slash. Chọn 301/308/temporary variant có chủ đích theo method semantics, cache behavior và rollout safety.

---

### Medium — Trailing-slash normalization không xét route ownership

**Vấn đề:**  
Mọi path > 1 kết thúc `/` đều bị trim.

**Tại sao xảy ra:**  
Middleware áp global URL policy mà không biết route nào là page, endpoint đặc biệt hoặc resource cần slash semantics khác.

**Ảnh hưởng production:**  
Có thể làm thay đổi API/static/admin behavior hoặc tạo redirect chain với router/CDN rules khác.

**Cách sửa:**  
Áp canonicalization cho public page routes đã xác định, hoặc đưa rule về edge/routing layer nơi route ownership rõ hơn.

---

### Medium — Có thể tạo nhiều redirect hops thay vì một canonical redirect

**Vấn đề:**  
Một request `http://example.com/products/abc/` có thể đi qua HTTPS redirect, rồi host redirect, rồi trailing-slash redirect.

**Tại sao xảy ra:**  
Mỗi rule return riêng và chỉ sửa một dimension.

**Ảnh hưởng production:**  
Tăng latency, crawler work và làm debugging phức tạp hơn.

**Cách sửa:**  
Tính final canonical URL một lần từ trusted scheme/host/path rules, rồi redirect tối đa một hop khi có thể.

---

### Low — Không có observability cho lý do redirect

**Vấn đề:**  
Middleware không emit metric hoặc structured dimension về redirect reason.

**Tại sao xảy ra:**  
Redirect được coi như plumbing thay vì user-facing control flow.

**Ảnh hưởng production:**  
Redirect loops hoặc rule regression có thể chỉ được phát hiện qua crawler/user reports.

**Cách sửa:**  
Theo dõi redirect count/rate theo reason, source host, route group và final status; không log query values nhạy cảm tùy domain.

## Phiên bản đề xuất

Một hướng an toàn hơn là dùng trusted configuration và chỉ áp policy cho public GET/HEAD pages. Ví dụ rút gọn:

```csharp
public sealed class CanonicalUrlOptions
{
    public required string Scheme { get; init; }
    public required HostString Host { get; init; }
}

public sealed class CanonicalUrlMiddleware
{
    private readonly RequestDelegate _next;
    private readonly CanonicalUrlOptions _options;

    public CanonicalUrlMiddleware(
        RequestDelegate next,
        IOptions<CanonicalUrlOptions> options)
    {
        _next = next;
        _options = options.Value;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var request = context.Request;

        if (!HttpMethods.IsGet(request.Method) &&
            !HttpMethods.IsHead(request.Method))
        {
            await _next(context);
            return;
        }

        if (request.Path.StartsWithSegments("/api") ||
            request.Path.StartsWithSegments("/health"))
        {
            await _next(context);
            return;
        }

        var path = request.Path.Value ?? "/";
        if (path.Length > 1)
            path = path.TrimEnd('/');

        var alreadyCanonical =
            string.Equals(request.Scheme, _options.Scheme,
                StringComparison.OrdinalIgnoreCase) &&
            request.Host == _options.Host &&
            request.Path == path;

        if (alreadyCanonical)
        {
            await _next(context);
            return;
        }

        var target = $"{_options.Scheme}://{_options.Host}{path}{request.QueryString}";
        context.Response.StatusCode = StatusCodes.Status308PermanentRedirect;
        context.Response.Headers.Location = target;
    }
}
```

Điều kiện quan trọng: middleware này chỉ đúng nếu forwarded-header handling đã được cấu hình an toàn **trước nó** khi application chạy sau trusted proxy. Với nhiều hệ thống, scheme/host normalization nên được thực hiện ở CDN/reverse proxy để giảm logic ở app; app chỉ giữ route-level canonical policy cần thiết.

`308` trong ví dụ thể hiện permanent redirect có semantics giữ method, nhưng vì middleware đã giới hạn GET/HEAD nên mục tiêu chính là consistency. Việc dùng 301/308 hay temporary redirect trong rollout phải được quyết định theo cache/SEO/rollback requirements thực tế, không copy mặc định.

## Giải thích thiết kế sau khi sửa

Canonical destination không còn phụ thuộc arbitrary incoming Host. Environment config quyết định public host, và allowed-host/proxy configuration bảo vệ boundary phía trước.

Canonicalization được giới hạn vào public page traffic. API, health và non-idempotent methods không bị kéo vào SEO redirect flow.

Thay vì ba hops, code tính final canonical scheme/host/path rồi redirect một lần. Điều này giảm latency và làm telemetry dễ hiểu hơn.

Ở production, tôi vẫn ưu tiên xem CDN/reverse proxy có thể đảm nhận HTTPS + host redirect không. Edge thường biết external scheme/host rõ hơn origin và có thể giảm request không cần thiết vào application. Application giữ responsibility cho canonical page rules mà edge không hiểu.

## Trade-offs

- Redirect ở edge giảm latency/origin load nhưng policy bị chia giữa infrastructure và application; cần ownership/documentation rõ.
- Redirect trong app dễ test cùng code nhưng phụ thuộc forwarded headers/proxy trust đúng.
- Permanent redirects tốt cho stable canonicalization nhưng khó rollback hơn do browser/CDN caching; rollout mới có thể bắt đầu temporary trước khi chuyển permanent.
- Một host canonical duy nhất đơn giản, nhưng multi-brand/multi-country sites có thể cần explicit domain mapping thay vì một option toàn cục.

## Cách kiểm thử

1. **Proxy integration test:** external HTTPS → proxy HTTP origin; xác minh không redirect loop và final Location đúng.
2. **Host-header test:** gửi Host không nằm trong allow-list; xác minh app/proxy reject hoặc không tạo redirect dựa trên host đó.
3. **Route/method matrix:** GET/HEAD public pages được canonicalize; POST `/api/...` và health endpoints không bị SEO redirect.
4. **Redirect-chain test:** `http + alias host + trailing slash` phải tới canonical URL với số hop theo policy, lý tưởng một hop.
5. **Crawler regression test:** kiểm tra canonical routes, legacy redirects, status codes và query-string preservation trên representative URLs.

## Quan sát trong production

Theo dõi:

- redirect responses theo status code và reason;
- redirect rate trên từng host/path group;
- repeated requests cùng correlation/session qua nhiều redirects;
- 4xx do invalid/untrusted hosts;
- crawler reports và canonical-index coverage;
- page request latency trước/sau edge/app canonicalization;
- CDN cache behavior đối với redirect responses.

Một synthetic probe nên kiểm tra từ public internet ít nhất các trường hợp HTTP alias, HTTPS alias, canonical HTTPS và một POST/API path không được redirect.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn 301, 302, 307 hoặc 308 cho redirect, và yếu tố method/cache/rollback ảnh hưởng quyết định ra sao?
2. Nếu site có `example.co.uk`, `example.de` và `example.com`, canonical host mapping nên được model thế nào?
3. Nếu CDN và application đều có redirect rules, bạn ngăn redirect loop và configuration drift bằng cách nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `async`/parallel execution không làm `DbContext` hay collection mutable trở thành thread-safe.
- Tối ưu batch bằng concurrency phải đi cùng query-count reduction, dependency budgets và explicit failure semantics.
- `MaxDegreeOfParallelism` per request không phải global protection khi nhiều requests chạy cùng lúc.
- Canonical URL logic phải dựa trên trusted scheme/host sau proxy processing, không dựa vào arbitrary request host.
- SEO redirects, API behavior và reverse-proxy behavior là ba concerns liên quan nhưng không nên trộn thành một global middleware thiếu scope.

## Mẫu tư duy cần nhớ

1. **Tìm shared mutable state trước khi thêm parallelism.**
2. **Giảm tổng lượng work trước khi tăng concurrency.**
3. **Đặt concurrency budget theo dependency và toàn hệ thống, không chỉ theo một request.**
4. **Xác định trust boundary trước khi xây URL hoặc security-sensitive behavior từ request metadata.**
5. **Test production topology, không chỉ test application trực tiếp ở localhost.**
