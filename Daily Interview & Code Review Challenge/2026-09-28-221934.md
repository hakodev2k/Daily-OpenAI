# Câu 1 — SQL pagination càng về cuối càng chậm dù đã có index

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** SQL Server, EF Core, execution plan, composite index, OFFSET/FETCH, keyset pagination, query correctness, API design, performance measurement

## Bối cảnh

Một ASP.NET Core .NET 8 API phục vụ màn hình audit history. Bảng `AuditEvents` có khoảng 80 triệu rows và tiếp tục tăng. API dùng EF Core:

```csharp
var page = await db.AuditEvents
    .AsNoTracking()
    .Where(x => x.TenantId == tenantId && x.CreatedAt <= to)
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .Select(x => new AuditEventDto(x.Id, x.CreatedAt, x.Actor, x.Action))
    .ToListAsync(cancellationToken);
```

Có index hiện tại trên `(TenantId, CreatedAt DESC)`. Page 1 thường dưới 100 ms, nhưng page 2.000 có thể mất 2–5 giây và đọc rất nhiều pages. Team đề xuất tăng DTU/CPU hoặc thêm Redis. Product vẫn muốn người dùng có thể duyệt lịch sử ổn định trong lúc dữ liệu mới liên tục được ghi.

Chưa rõ distribution theo tenant, selectivity của `to`, execution plan thực tế, index có cover projection hay không, `Id` có nằm trong index key hay INCLUDE, và client có thực sự cần random access tới page số bất kỳ.

## Câu hỏi chính

Hãy giải thích SQL engine phải làm gì với `Skip/Take` ở deep page; vì sao một index “có đúng vài cột filter/sort” chưa chứng minh query sẽ scale; vai trò của deterministic ordering là gì; và bạn sẽ xác minh rồi thiết kế pagination thế nào nếu mục tiêu là latency ổn định khi dataset tăng?

## Câu hỏi làm rõ nên cân nhắc

1. UX có bắt buộc nhảy trực tiếp tới page 2.000 hay chỉ cần Next/Previous/infinite scroll?
2. Số rows và data skew theo từng `TenantId` ra sao?
3. Actual execution plan, logical reads, elapsed/CPU time và row estimates thay đổi thế nào giữa page 1 và deep page?
4. `CreatedAt` có duplicate nhiều không và `Id` có monotonic/unique phù hợp làm tie-breaker không?
5. Requirement về consistency khi rows mới được insert trong lúc user đang duyệt là gì?

## Gợi ý tư duy

### Gợi ý 1

`OFFSET` không biến những rows trước offset thành miễn phí. Hãy nghĩ về số rows engine phải tìm, sắp xếp/đi qua rồi bỏ.

### Gợi ý 2

Sort order có hai keys nhưng index hiện chỉ mô tả một phần ordering. Hãy xem seek predicate nào có thể đại diện cho “sau item cuối của trang trước”.

### Gợi ý 3

Pagination là cả API contract lẫn database access pattern. Cursor/keyset có lợi thế nhưng đánh đổi random page access và cần xử lý consistency semantics rõ ràng.

## Cấu trúc trả lời đề xuất

1. Xác nhận UX và consistency requirement.
2. Lấy actual plan và đo logical reads/CPU/duration theo page depth.
3. Giải thích OFFSET/FETCH work và ordering.
4. Kiểm tra index key order, coverage và selectivity.
5. So sánh offset pagination với keyset/cursor.
6. Thiết kế cursor từ `CreatedAt + Id` và predicate tương ứng.
7. Xử lý snapshot/boundary nếu dữ liệu mới được insert.
8. Load test trên data distribution thật.
9. Theo dõi latency và database resource sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Deep `Skip` yêu cầu database đi qua lượng rows ngày càng lớn trước khi trả `Take`; latency và logical reads có thể tăng theo offset.
- Index tồn tại không đồng nghĩa index phù hợp. Phải xem key order, tie-breaker, selectivity, coverage và actual execution plan.
- `CreatedAt` không nhất thiết unique; `ThenByDescending(Id)` tạo total/deterministic order cần thiết để tránh item nhảy/duplicate do ties.
- Keyset pagination dùng giá trị cuối trang trước để seek vào vị trí tiếp theo thay vì đếm/bỏ toàn bộ rows trước đó.
- Cần đo actual plan, logical reads, CPU, duration; không nhảy thẳng tới Redis hoặc scale-up.
- Cursor phải encode đủ sort keys và không được tin raw client values nếu API cần integrity/tamper resistance.

### Điểm cộng

- Predicate descending có dạng `CreatedAt < lastCreatedAt OR (CreatedAt = lastCreatedAt AND Id < lastId)`, cùng tenant/boundary.
- Composite index cần được đánh giá theo access pattern, ví dụ `(TenantId, CreatedAt DESC, Id DESC)`, với INCLUDE phù hợp sau khi đo; không mặc định INCLUDE mọi column.
- Nếu cần browsing ổn định trước concurrent inserts, giữ một upper-bound/snapshot timestamp hoặc cursor semantics rõ ràng.
- Count tổng số pages có thể tự nó đắt; UX không nên buộc database tính exact count nếu không cần.

### Senior+

- Phân biệt seekability với coverage; một covering index quá rộng làm tăng storage/write amplification.
- Thảo luận parameter sensitivity/data skew theo tenant và kiểm tra actual rows vs estimated rows.
- Nếu business thật sự cần random page number, keyset không thay thế hoàn toàn offset; có thể cần giới hạn deep navigation, anchor strategy hoặc một read model khác tùy requirement.
- Cursor là API contract cần versioning nếu sort semantics thay đổi.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng Redis. Đầu tiên tôi lấy actual execution plan và đo `STATISTICS IO/TIME` hoặc telemetry tương đương cho page 1, 100, 2.000 trên vài tenant có distribution khác nhau. Với offset pagination, database vẫn phải xác định ordered result rồi đi qua các rows trước offset. Vì vậy deep page có thể đọc/xử lý lượng dữ liệu lớn dù cuối cùng chỉ trả 50 rows.

Index hiện tại hỗ trợ filter theo tenant và một phần sort theo `CreatedAt`, nhưng query còn dùng `Id` làm tie-breaker. Tôi cần xem actual plan để biết có sort, lookup hay scan/range scan nào xảy ra. Nếu access pattern này quan trọng, một candidate index là `(TenantId, CreatedAt DESC, Id DESC)`; các cột projection có thể INCLUDE nếu evidence cho thấy lookup đáng kể và write/storage cost chấp nhận được.

Nếu UX chủ yếu Next/Previous, tôi ưu tiên keyset pagination. Response trả opaque cursor chứa `lastCreatedAt` và `lastId`. Trang kế tiếp filter:

```csharp
query = query.Where(x =>
    x.CreatedAt < cursor.CreatedAt ||
    (x.CreatedAt == cursor.CreatedAt && x.Id < cursor.Id));
```

sau đó giữ cùng `OrderByDescending(CreatedAt).ThenByDescending(Id).Take(pageSize)`. Với index phù hợp, database có thể bắt đầu gần boundary thay vì bỏ hàng chục nghìn rows.

Concurrent insert cần semantics rõ. Nếu user đang duyệt một “view” của lịch sử, tôi có thể thêm upper-bound timestamp/ID từ request đầu vào cursor để các event mới không làm dịch cửa sổ đang duyệt. Nếu requirement là live feed thì semantics khác. Tôi sẽ không hứa snapshot consistency nếu chưa có requirement/transaction strategy tương ứng.

Tôi verify bằng integration test có duplicate timestamps, concurrent inserts, page traversal không duplicate/missing trong semantics đã chọn, và load test trên dữ liệu gần production. Production theo dõi p50/p95/p99 theo endpoint, logical reads/query duration từ database telemetry, timeouts và page/cursor usage.

## Mẫu trả lời trong phỏng vấn

“Điểm tôi muốn chứng minh trước là chi phí tăng theo offset chứ không phải đoán do thiếu CPU. `Skip` sâu vẫn buộc SQL xử lý các rows đứng trước trang cần lấy. Tôi sẽ so actual plan, logical reads, CPU và duration giữa page đầu và page sâu, đồng thời kiểm tra data skew theo tenant. Index hiện có chưa đủ để kết luận tốt vì ordering thực tế là `TenantId, CreatedAt, Id`.

Nếu UX chỉ cần duyệt tuần tự, tôi đổi sang keyset pagination với cursor chứa `CreatedAt + Id`, vì `CreatedAt` có thể trùng. Predicate sẽ seek sau tuple cuối trang trước và index candidate sẽ align với tenant và hai sort keys. Tôi chỉ thêm INCLUDE sau khi đo lookup/write trade-off. Nếu concurrent insert phải không làm trang dịch chuyển, cursor sẽ mang một upper boundary từ request đầu. Nếu Product bắt buộc nhảy ngẫu nhiên tới page 2.000 thì tôi sẽ nói rõ keyset không đáp ứng trực tiếp và cùng Product xem lại UX hoặc thiết kế anchor/read model. Sau đó tôi verify bằng execution plan, load test và p95/p99 thay vì mặc định thêm Redis.”

## Câu hỏi đào sâu

1. Nếu Product bắt buộc “Go to page 2000”, bạn giữ latency predictable bằng cách nào và trade-off là gì?
2. Nếu teammate đề xuất index gồm toàn bộ columns của DTO để loại bỏ mọi lookup, bạn đánh giá recommendation đó thế nào?
3. Nếu `CreatedAt` có thể bị chỉnh sửa sau khi row được tạo, cursor design cần thay đổi gì?

## Lỗi trả lời thường gặp

- Chỉ nói “thêm index” mà không xem plan, key order và logical reads.
- Dùng `CreatedAt` một mình làm cursor dù giá trị có thể trùng.
- Cho rằng Redis tự giải quyết deep pagination.
- Chuyển sang keyset nhưng không nói trade-off random access.
- Không định nghĩa behavior khi có concurrent inserts.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất scale database/cache.
- **3–4:** Nhận ra OFFSET chậm nhưng giải pháp/index còn cảm tính.
- **5–6:** Giải thích đúng deep offset và keyset cơ bản.
- **7–8:** Bao quát deterministic ordering, index, measurement, concurrent writes và tests.
- **9–10:** Lập luận được API/database contract, data skew, index write cost, cursor integrity và conditional design theo UX.

# Câu 2 — Kubernetes rollout “xanh” nhưng người dùng nhận 502 và pod restart theo chu kỳ

**Loại câu hỏi:** Production Incident / Troubleshooting  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, readiness/liveness/startup behavior, resource limits, graceful shutdown, deployment safety, observability, production incident response

## Bối cảnh

Một ASP.NET Core API trước đây chạy Azure App Service, nay team đang đánh giá Kubernetes cho một workload có yêu cầu riêng về platform. Deployment có 6 replicas. Sau release mới, CI/CD báo rollout thành công nhưng trong 15 phút đầu người dùng thấy burst HTTP 502; một số pods restart sau khoảng vài phút. Dashboard cho thấy CPU trung bình toàn deployment không cao. Release mới thêm bước warm-up cache và tải metadata khi startup.

Manifest rút gọn:

```yaml
containers:
- name: api
  image: registry/example-api:2026.09.28
  ports:
  - containerPort: 8080
  resources:
    requests:
      cpu: "100m"
      memory: "128Mi"
    limits:
      cpu: "500m"
      memory: "256Mi"
  readinessProbe:
    httpGet:
      path: /health
      port: 8080
    initialDelaySeconds: 5
    periodSeconds: 5
  livenessProbe:
    httpGet:
      path: /health
      port: 8080
    initialDelaySeconds: 10
    periodSeconds: 10
```

Endpoint `/health` hiện kiểm tra cả SQL Server, Redis và một third-party API. Warm-up đôi lúc mất 20–40 giây. Chưa rõ restart reason là OOMKilled, failed liveness, process crash hay node eviction; chưa rõ ingress 502 đến từ zero ready endpoints, terminated pods, app exception hay upstream timeout. Team đề xuất tăng mọi probe timeout và memory limit ngay.

## Câu hỏi chính

Bạn đang xử lý incident. Hãy trình bày cách **impact → stabilize → collect evidence → hypotheses → narrow down → root cause → remediate → verify → prevent recurrence**. Bạn sẽ phân biệt probe misconfiguration, dependency degradation, resource pressure, slow startup và graceful termination như thế nào; và thiết kế health probes ra sao để tránh biến dependency failure thành restart storm?

## Câu hỏi làm rõ nên cân nhắc

1. `kubectl describe pod`/pod status cho biết `lastState`, exit code, restart reason và probe events gì?
2. 502 xuất hiện khi số Ready endpoints giảm, khi pod đang terminating hay khi pod vẫn Ready?
3. Memory working set/limit, CPU throttling và startup duration theo từng pod là bao nhiêu?
4. `/health` thất bại vì dependency nào, và dependency đó có thực sự làm process không thể phục vụ mọi request không?
5. Deployment strategy, `maxUnavailable/maxSurge`, termination grace period và ASP.NET Core shutdown behavior hiện thế nào?

## Gợi ý tư duy

### Gợi ý 1

Readiness trả lời “pod có nên nhận traffic không”; liveness trả lời “process có cần bị restart để hồi phục không”. Hai câu hỏi không nhất thiết dùng cùng dependency graph.

### Gợi ý 2

Đừng suy restart reason từ symptom. Pod status/events, container exit reason, probe result và resource metrics phải tạo được timeline.

### Gợi ý 3

Một third-party API chập chờn có thể làm readiness giảm; nếu cùng check đó điều khiển liveness, orchestrator có thể giết process khỏe và khuếch đại incident.

## Cấu trúc trả lời đề xuất

1. Xác định impact, error window và rollout timeline.
2. Stabilize bằng rollback/pause rollout nếu release correlation mạnh và user impact cao.
3. Thu pod events, restart reason, probe history, ingress/backend metrics.
4. Correlate ready endpoints với 502.
5. Tách startup, liveness, readiness và resource hypotheses.
6. Kiểm tra dependency-specific health và application logs/traces.
7. Sửa probe semantics và startup behavior.
8. Kiểm tra graceful shutdown/rolling update.
9. Load/failure test trước rollout lại.
10. Theo dõi restart rate, Ready endpoints và 5xx.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận restart do memory/probe trước khi đọc container termination reason và events.
- Readiness và liveness có mục đích khác nhau; liveness không nên thất bại chỉ vì một external dependency tạm thời down nếu process vẫn khỏe.
- Slow startup cần được xử lý sao cho liveness không giết container trước khi startup hợp lệ hoàn tất; cấu hình cụ thể phải dựa trên measured startup behavior.
- Readiness phải ngăn traffic vào instance chưa sẵn sàng nhưng không nên tạo global outage do check không phản ánh khả năng phục vụ.
- Memory limit có thể liên quan OOM nhưng phải chứng minh bằng `OOMKilled`/metrics; CPU average toàn deployment có thể che per-pod throttling/spikes.
- Rolling deployment cần xét ready capacity và graceful termination, không chỉ “pipeline green”.
- 502 phải correlate với ingress/upstream evidence và endpoint readiness.

### Điểm cộng

- Tách health endpoint thành semantics rõ: liveness chủ yếu process/self-health; readiness kiểm tra điều kiện cần để phục vụ traffic; startup probe có thể phù hợp khi startup dài/biến thiên.
- External dependency có thể cần timeout ngắn, degraded-mode semantics hoặc loại khỏi liveness tùy khả năng ứng dụng.
- Warm-up nặng cần bounded/cancellable; cân nhắc lazy/background warm-up nếu business semantics cho phép.
- Kiểm tra requests/limits từ measured working set và load thay vì tăng tùy ý.
- Theo dõi CPU throttling, memory working set, restart count, Ready replicas, ingress 5xx và dependency latency.

### Senior+

- Nhận ra health check chính nó có thể tạo load vào dependencies nếu mỗi probe của mọi pod gọi SQL/Redis/third-party thường xuyên.
- Khi readiness phụ thuộc dependency dùng chung, dependency outage có thể khiến mọi pod đồng thời NotReady; cần thiết kế degraded behavior theo chức năng thật.
- Graceful shutdown phải phối hợp readiness transition, termination signal, in-flight request draining và termination grace period.
- Đặt câu hỏi liệu Kubernetes có thực sự mang giá trị cho workload; không coi migration platform là mục tiêu tự thân.

## Hướng giải quyết tham khảo

Tôi sẽ stabilize trước nếu 502 có impact đáng kể và release mới tương quan mạnh: pause rollout hoặc rollback về artifact known-good nếu rollback tương thích. Đồng thời bảo toàn evidence. Sau đó dựng timeline theo pod: created → container started → probe failures → Ready → 502 → termination/restart.

Tôi đọc pod status/events để biết restart là `OOMKilled`, liveness failure hay application exit. Nếu OOMKilled, so working set/limit và heap/native memory; nếu liveness failure, xem response/latency của `/health`; nếu CPU throttling, xem per-container throttling thay vì CPU average.

Health semantics hiện đáng nghi vì cùng `/health` gọi SQL, Redis và third-party cho cả readiness/liveness. Third-party down không nhất thiết nghĩa process ASP.NET Core bị deadlock và cần restart. Liveness nên phản ánh khả năng process tự tiếp tục chạy; readiness phản ánh instance có nên nhận traffic. Nếu startup hợp lệ có thể mất 40 giây, startup probe hoặc cấu hình startup-aware tương đương giúp tránh liveness can thiệp quá sớm. Tôi không chọn thresholds bằng cảm tính; lấy distribution startup time và dependency timeout làm cơ sở.

Readiness cũng cần cẩn thận: nếu API có thể phục vụ phần lớn endpoints khi review provider down, việc đánh toàn pod NotReady có thể biến partial dependency outage thành total outage. Có thể expose degraded status qua telemetry trong khi readiness chỉ fail với dependency thực sự bắt buộc cho request path chính.

Tôi kiểm tra rolling update: minimum ready capacity, surge/unavailable settings, pod chỉ nhận traffic sau Ready, và khi terminate thì ngừng nhận traffic trước khi process bị kill, cho phép in-flight requests hoàn tất trong grace period phù hợp.

Verification gồm test slow startup, third-party timeout, Redis outage, memory pressure và rolling deployment dưới traffic. Success criteria: không 502 do rollout, không restart storm khi third-party fail, restart reason giải thích được, Ready replicas đủ capacity và alerts dựa trên user impact/restart/dependency signals.

## Mẫu trả lời trong phỏng vấn

“Tôi không tăng probe timeout hay memory trước khi biết pod chết vì gì. Tôi sẽ pause/rollback nếu release đang gây 502, rồi lấy pod termination reason, events, probe failures, per-pod memory/throttling và ingress 502 timeline. Điểm đáng nghi là readiness và liveness dùng chung endpoint gọi cả SQL, Redis và third-party. Liveness phải trả lời process có cần restart không; dependency bên ngoài chập chờn thường không phải lý do giết một process khỏe. Readiness quyết định nhận traffic và cũng phải phản ánh khả năng phục vụ thật, nếu không một dependency outage có thể làm toàn bộ replicas NotReady.

Vì startup đo được 20–40 giây, tôi sẽ dùng startup-aware probe design thay vì để liveness bắt đầu quá sớm. Đồng thời tôi kiểm tra OOMKilled và CPU throttling trước khi đổi limits. Sau đó kiểm tra rolling strategy và graceful shutdown để pod terminating không còn nhận request nhưng có thời gian drain in-flight work. Tôi verify bằng failure injection cho third-party, slow startup và rollout dưới load, rồi monitor ready replicas, restarts, ingress 5xx và dependency latency.”

## Câu hỏi đào sâu

1. Nếu Redis down nhưng API có thể fallback SQL với latency cao hơn, readiness nên phản ứng thế nào?
2. Một teammate muốn đưa SQL, Redis, Service Bus và mọi third-party vào liveness để “chắc chắn hệ thống healthy”; bạn phản biện ra sao?
3. Nếu restart reason xác nhận OOMKilled chứ không phải probe failure, investigation và remediation của bạn thay đổi thế nào?

## Lỗi trả lời thường gặp

- Tăng memory/probe timeout trước khi xem termination reason.
- Dùng một health endpoint giống nhau cho mọi probe mà không xét semantics.
- Coi external dependency failure là lý do mặc định restart process.
- Chỉ xem CPU trung bình toàn deployment.
- Bỏ qua rolling capacity và graceful termination.

## Thang điểm 0–10

- **0–2:** Thử chỉnh YAML ngẫu nhiên.
- **3–4:** Biết readiness/liveness nhưng không điều tra evidence.
- **5–6:** Có incident flow đúng và tách được probe/resource/startup.
- **7–8:** Bao quát rollout, graceful shutdown, degraded dependency và failure testing.
- **9–10:** Chứng minh theo timeline, tránh cascading failure, thiết kế probe theo service semantics và đặt đúng câu hỏi về complexity/platform fit.

# Câu 3 — Optimizely CMS + Akamai: thiết kế publish và cache invalidation mà không biến mọi request thành dynamic

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, Akamai/CDN, HTTP caching, cache invalidation, content modeling, SEO, availability, third-party integration, architecture trade-offs

## Bối cảnh

Một marketing/e-commerce website dùng Optimizely CMS để editors quản lý landing pages, campaign blocks và SEO metadata. Product catalog/price đến từ commerce APIs khác. Akamai đứng trước origin. Traffic có peak lớn khi campaign launch; phần lớn anonymous traffic có thể cache, nhưng một số blocks hiển thị theo market/language và một vùng header thay đổi theo authentication state.

Hiện tại team đặt `Cache-Control: no-store` cho gần như mọi HTML để tránh stale content. Kết quả là origin load cao và campaign launch từng gây latency spike. Business muốn:

- publish content nhìn thấy “gần như ngay”;
- anonymous pages tận dụng CDN mạnh;
- không leak personalized/authenticated content giữa users;
- canonical URL, redirects và metadata đúng cho SEO;
- nếu commerce/review API chậm, marketing page vẫn nên hiển thị được phần có thể dùng;
- editors không phải purge toàn site thủ công mỗi lần sửa một block dùng chung.

Một architect đề xuất chuyển toàn bộ sang microservices + headless CMS. Người khác đề xuất cache mọi HTML 24 giờ và purge wildcard sau mỗi publish.

Chưa rõ freshness SLA chính xác theo content type, số market/language variants, Akamai cache-key rules, Optimizely publish hooks, personalization boundary, purge API constraints, hay commerce data nào thực sự phải render server-side.

## Câu hỏi chính

Hãy thiết kế content delivery và caching strategy cho hệ thống này. Xác định ownership/boundaries, cacheability theo loại response, cache key/variation, publish invalidation, failure behavior của external dependencies, SEO correctness và observability. Đồng thời giải thích khi nào giữ kiến trúc hiện tại đơn giản hơn sẽ tốt hơn việc chuyển sang headless/microservices.

## Câu hỏi làm rõ nên cân nhắc

1. “Gần như ngay” là vài giây, một phút hay năm phút, và áp dụng cho content nào?
2. Anonymous/personalized traffic chiếm tỷ lệ bao nhiêu; personalization có thể tách thành client-side/API fragment không?
3. Một shared block có thể xuất hiện trên bao nhiêu pages và có dependency graph từ content tới URLs không?
4. Market/language được xác định bằng hostname/path/header/cookie nào và CDN cache key hiện gồm những dimensions nào?
5. Commerce price có freshness/legal requirement gì và page có thể degrade ra sao khi commerce/review provider lỗi?

## Gợi ý tư duy

### Gợi ý 1

Không có một TTL đúng cho toàn site. Phân loại response theo public/private, freshness và dependency trước khi chọn cache policy.

### Gợi ý 2

Publish invalidation cần biết content nào ảnh hưởng URL nào. Wildcard purge đơn giản nhưng có thể tạo origin stampede; TTL dài mà không invalidation thì vi phạm freshness.

### Gợi ý 3

Personalization boundary quyết định cache safety. Đừng để CDN cache một response chứa user-specific data chỉ vì phần lớn page là public.

## Cấu trúc trả lời đề xuất

1. Làm rõ freshness, personalization và SEO requirements.
2. Xác định source of truth và ownership cho CMS/catalog/auth/reviews.
3. Phân loại page/fragment theo cacheability.
4. Thiết kế cache key và response headers.
5. Thiết kế publish-to-invalidation flow.
6. Thiết kế dependency degradation/timeouts.
7. Đánh giá origin/CMS cache và CDN interaction.
8. Đảm bảo redirects/canonical/metadata correctness.
9. Test cache isolation, purge và failure paths.
10. So sánh current architecture với headless/microservices bằng measurable drivers.

## Ý chính của câu trả lời tốt

### Bắt buộc

- CMS content, catalog/price, identity và review data có ownership khác nhau; không tạo một source of truth giả.
- Public anonymous HTML có thể cache nếu response không chứa user-specific data và cache key bao quát đúng variant cần thiết.
- Authenticated/personalized content không được vô tình shared-cache giữa users; có thể tách personalized fragment/API khỏi cacheable shell nếu UX cho phép.
- TTL và invalidation phải theo content/freshness requirement; không chọn 24 giờ hoặc `no-store` toàn site theo phản xạ.
- Publish event/hook cần map content dependency tới affected URLs hoặc cache tags/keys theo khả năng platform; purge có mục tiêu tốt hơn full-site purge khi dependency graph đáng tin cậy.
- Purge/invalidation failure phải observable và retryable; CDN cache không được coi là magically consistent.
- External commerce/review calls cần timeout/fallback/degraded behavior; marketing page không nên bị kéo sập vô điều kiện bởi optional dependency.
- SEO outputs như canonical, redirect/status, metadata và crawlability phải nhất quán theo market/language và không bị cache sai variant.

### Điểm cộng

- Dùng stale-while-revalidate/stale-if-error chỉ khi CDN/browser semantics và business freshness cho phép; không hứa behavior nếu chưa xác minh Akamai configuration.
- Chống cache stampede sau purge bằng targeted invalidation, controlled pre-warm hoặc origin capacity strategy.
- Có correlation từ CMS publish/content ID → invalidation request → affected URL/cache key → edge hit/miss.
- Tách public page shell khỏi personalized header có thể tăng cacheability nhưng thêm client/API complexity và cần tránh layout/SEO regression.
- Cache key dimensions càng nhiều càng giảm hit ratio; chỉ vary theo dimension thực sự thay đổi representation.

### Senior+

- Shared block dependency graph là một architecture concern: publish một block phải tìm được các pages chịu ảnh hưởng hoặc dùng surrogate/tag invalidation nếu platform hỗ trợ và đã được xác minh.
- Không purge trước khi content version mới có thể được origin phục vụ ổn định; ordering publish/invalidation cần tránh edge miss quay về lấy phiên bản cũ.
- Headless có thể hữu ích khi nhiều channels/independent frontend release thật sự cần nó, nhưng kéo theo preview/editor experience, API contracts, caching, deployment và observability complexity.
- Microservices không giải quyết cache invalidation tự động; service boundaries chỉ đáng tách khi ownership/deployment/scaling/failure isolation tạo giá trị đủ lớn.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng classification thay vì chọn architecture buzzword. Optimizely tiếp tục là source of truth cho editorial content. Commerce service sở hữu catalog/price; identity sở hữu authentication; review provider là dependency riêng. Tôi xác định content nào phải server-render và content nào có thể fetch/degrade độc lập.

Với anonymous landing pages thuần public, tôi cho phép shared CDN caching với TTL theo content class. Market/language phải là một phần của URL hoặc cache-key dimension nếu representation khác nhau. Tôi tránh `Vary`/cookie dimensions rộng không cần thiết vì làm giảm hit ratio. Nếu header thật sự user-specific, tôi không cache nguyên authenticated response như public. Một lựa chọn là public cacheable shell + authenticated fragment/API, nếu UX/security/SEO cho phép.

Publish flow nên tạo invalidation có mục tiêu. Khi page đổi, purge URL/keys của page đó. Khi shared block đổi, cần dependency mapping từ block tới pages đang sử dụng hoặc cơ chế cache tag/surrogate tương đương nếu Akamai/configuration hiện tại hỗ trợ. Invalidation phải có retry, idempotency và telemetry. Tôi không purge toàn site mặc định vì campaign publish có thể tạo thundering herd vào origin. Ordering cũng quan trọng: version mới phải sẵn sàng ở origin trước khi edge miss được tạo.

TTL là safety net chứ không thay publish invalidation. Với content ít nhạy freshness, TTL dài hơn tăng hit ratio; với campaign/legal content, TTL ngắn hơn hoặc targeted purge SLA chặt hơn. Các stale directives chỉ dùng sau khi xác minh CDN behavior và business chấp nhận stale window.

Commerce/review calls có timeout budget. Optional review failure không làm toàn page 500; render fallback/omit component. Price nếu có correctness requirement cao có thể không phù hợp cache cùng TTL với editorial HTML; có thể tách price endpoint/client hydration hoặc dùng cache policy ngắn hơn tùy SEO/UX. Không quyết định trước khi làm rõ requirement.

SEO được test như contract: canonical per locale, redirect status, hreflang nếu dùng, metadata, sitemap và robots behavior. Cache key phải không làm English metadata phục vụ cho Vietnamese page hoặc authenticated variant leak sang anonymous.

Observability gồm CDN hit ratio, origin request rate/p95, cache status header/sample, purge success/latency/failure, publish-to-visible latency, dependency latency/error và correlation theo content/version. E2E/Playwright có thể publish test content trong environment phù hợp rồi verify edge behavior, locale, auth isolation và SEO metadata.

Tôi chỉ đề xuất headless khi có driver rõ như nhiều channels, independent frontend deployment hoặc delivery model cần API-first. Nếu vấn đề hiện tại chủ yếu là `no-store` và invalidation, sửa cache architecture trong monolith/CMS hiện tại thường rẻ và ít operational risk hơn. Microservices cũng không tự giải quyết stale cache.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng headless hay TTL 24 giờ. Trước hết tôi phân loại representation. Optimizely sở hữu editorial content; commerce sở hữu price/catalog; identity và reviews có boundary riêng. Anonymous HTML không có user data có thể shared-cache, nhưng cache key phải phản ánh market/language thực sự thay đổi response. Personalized header không được đi chung vào public cached HTML; nếu phù hợp tôi tách thành fragment/API để giữ shell cacheable.

Publish sẽ phát sinh targeted invalidation. Page đổi thì purge page; shared block đổi thì cần dependency mapping hoặc cache-tag mechanism đã được xác minh. Invalidation phải retryable và observable, và origin phải có version mới trước khi purge để edge miss không lấy lại bản cũ. Tôi tránh full-site purge vì dễ gây stampede.

Commerce/review có timeout và degraded behavior; optional dependency không kéo sập marketing page. Price có freshness khác editorial content nên có thể cần boundary/cache policy khác. Tôi đo CDN hit ratio, origin p95, purge latency và publish-to-visible SLA. Tôi chỉ chuyển headless/microservices nếu có driver về channels, ownership hoặc independent deployment đủ lớn; nếu vấn đề chỉ là cache policy, kiến trúc đơn giản hiện tại thường an toàn hơn.”

## Câu hỏi đào sâu

1. Nếu shared block được dùng trên 50.000 pages, targeted purge từng URL còn hợp lý không và bạn sẽ thay đổi design thế nào?
2. Nếu architect khẳng định “chuyển sang headless sẽ hết stale cache”, bạn phản biện bằng những failure modes nào?
3. Nếu price phải chính xác gần real-time nhưng editorial HTML muốn CDN TTL 6 giờ, bạn tách delivery boundary thế nào?

## Lỗi trả lời thường gặp

- Cache toàn HTML mà không phân biệt public/personalized.
- Purge toàn site sau mọi publish mà không xét stampede/origin capacity.
- Coi TTL là chiến lược invalidation duy nhất.
- Chuyển microservices/headless mà không nêu business/operational driver.
- Bỏ qua SEO variants và telemetry publish-to-visible.

## Thang điểm 0–10

- **0–2:** Chọn cache/headless theo khẩu hiệu.
- **3–4:** Có CDN/TTL nhưng thiếu security/invalidation/failure reasoning.
- **5–6:** Phân loại cache đúng và có publish invalidation cơ bản.
- **7–8:** Bao quát dependency graph, personalized isolation, degraded mode, SEO, observability và tests.
- **9–10:** Cân bằng freshness/hit ratio/origin risk, giải quyết invalidation ordering/stampede và chỉ tăng architecture complexity khi có driver rõ.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Deep offset pagination có chi phí tăng theo số rows phải đi qua; keyset pagination cần deterministic ordering và index phù hợp với access pattern.
- Kubernetes health probes là control-plane decisions với semantics khác nhau: readiness quyết định nhận traffic, liveness quyết định restart; dependency failure không nên tự động trở thành restart storm.
- CMS/CDN caching phải bắt đầu từ cacheability, personalization boundary và freshness requirement; publish invalidation là một distributed workflow cần retry và observability.
- Architecture tốt không bắt đầu bằng Redis, Kubernetes, headless hay microservices; bắt đầu bằng requirement, evidence, failure modes và cost of complexity.

## Mẫu tư duy cần nhớ

1. Measure before optimizing.
2. Stabilize before deep investigation.
3. Separate process health from dependency health.
4. Design cache invalidation together with cache policy.
5. Prefer the simplest architecture that satisfies measured requirements.
