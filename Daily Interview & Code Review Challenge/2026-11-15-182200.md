# Code Review Challenge 1 — Xuất báo cáo nhân sự vượt ranh giới tenant

**Chủ đề:** ASP.NET Core 8, authorization, EF Core, Azure Blob Storage  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút

## Bối cảnh

Một cổng quản trị đa tenant cung cấp API xuất báo cáo lương. JWT được xác thực bởi ASP.NET Core; mỗi nhân viên có thể thuộc nhiều tenant, nhưng chỉ vai trò `PayrollReader` trong tenant được chọn mới được xem dữ liệu. API chạy trên Azure App Service, 4 instances, có thể nhận 100 yêu cầu xuất cùng lúc. File xuất phải tồn tại 10 phút và không được công khai. Production ghi nhận một số link tải có thể được dùng ngoài tenant và request bị timeout khi báo cáo lớn. Giả định `PayrollDbContext`, `BlobContainerClient` và `PayrollRow` đã được đăng ký đúng.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/tenants/{tenantId:guid}/payroll")]
public sealed class PayrollExportController(
    PayrollDbContext db,
    BlobContainerClient blobs,
    ILogger<PayrollExportController> logger) : ControllerBase
{
    [HttpGet("export")]
    public async Task<IActionResult> Export(Guid tenantId, int year)
    {
        var rows = await db.PayrollEntries
            .Where(x => x.TenantId == tenantId && x.Year == year)
            .Include(x => x.Employee)
            .ToListAsync();

        var csv = new StringBuilder("Employee,Amount\n");
        foreach (var row in rows)
            csv.AppendLine($"{row.Employee.Name},{row.Amount}");

        var name = $"exports/{tenantId}/{Guid.NewGuid()}.csv";
        var blob = blobs.GetBlobClient(name);
        await blob.UploadAsync(
            BinaryData.FromString(csv.ToString()),
            overwrite: true);

        var sas = blob.GenerateSasUri(
            BlobSasPermissions.Read,
            DateTimeOffset.UtcNow.AddDays(1));

        logger.LogInformation(
            "Payroll export {TenantId} {Year} {Url}",
            tenantId, year, sas);

        return Ok(new { downloadUrl = sas.ToString() });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Broken tenant-level authorization

**Vấn đề:** Endpoint chỉ yêu cầu JWT hợp lệ, không kiểm tra membership/role trong tenant.  
**Tại sao xảy ra:** `tenantId` lấy từ route là input không đáng tin; `[Authorize]` không tự thực thi business policy.  
**Ảnh hưởng production:** Người dùng hợp lệ có thể lấy dữ liệu lương tenant khác.  
**Cách sửa:** Kiểm tra `PayrollReader` trên đúng tenant bằng policy/resource authorization từ nguồn quyền đáng tin, trước mọi truy vấn.

### [Critical] — SAS tồn tại quá lâu và có thể bị rò rỉ

**Vấn đề:** URL có quyền đọc sống 24 giờ, được ghi nguyên vào log.  
**Tại sao xảy ra:** SAS là credential nằm trong query string.  
**Ảnh hưởng production:** Bất kỳ người giữ URL đều có thể đọc dữ liệu đến khi token hết hạn hoặc bị vô hiệu theo cơ chế áp dụng.  
**Cách sửa:** Dùng private container; chỉ cấp read-only SAS ngắn hạn tối đa 10 phút, không log URL/token. Nếu cần thu hồi quyền tức thời, dùng authenticated download proxy hoặc cơ chế revoke phù hợp, không dựa riêng vào SAS.

### [High] — CSV injection và định dạng sai

**Vấn đề:** Nội dung tên nhân viên không được escape theo CSV và có thể bị spreadsheet diễn giải như formula.  
**Tại sao xảy ra:** Ghép chuỗi thủ công.  
**Ảnh hưởng production:** Sai cột, dữ liệu hỏng, spreadsheet formula injection khi mở bằng công cụ hỗ trợ công thức.  
**Cách sửa:** CSV writer tuân thủ quoting RFC 4180; áp dụng chính sách trung hòa formula cho các trường text không tin cậy khi file dành cho spreadsheet.

### [High] — Memory amplification

**Vấn đề:** Materialize toàn bộ entity graph, sau đó tạo CSV trong RAM rồi chuyển thành `BinaryData`.  
**Tại sao xảy ra:** Không projection/streaming; nhiều bản sao dữ liệu.  
**Ảnh hưởng production:** LOH/GC pressure, OOM khi tải đồng thời.  
**Cách sửa:** Projection `AsNoTracking`, streaming/chunked export hoặc background job với bounded concurrency.

### [High] — Thiếu cancellation và giới hạn workload

**Vấn đề:** Không truyền `RequestAborted`, không giới hạn year/range và kích thước export.  
**Tại sao xảy ra:** Không có resource budget.  
**Ảnh hưởng production:** Request đã đóng vẫn tiêu tốn SQL và Blob bandwidth; gây timeout và resource exhaustion.  
**Cách sửa:** Validate year, quota/rate limit, cancellation token, giới hạn đồng thời; với file lớn chuyển sang job queue.

### [Medium] — PII trong đường dẫn và logging

**Vấn đề:** Tenant identifier xuất hiện trong blob name; log chứa credential.  
**Tại sao xảy ra:** Thiếu data classification và logging policy.  
**Ảnh hưởng production:** Lộ metadata, khó đáp ứng retention policy.  
**Cách sửa:** Opaque blob key, structured log với exportId, tenantId có kiểm soát, không log secrets.

### [Medium] — Thiếu lifecycle/cleanup

**Vấn đề:** File có thể tồn tại vô hạn dù link hết hạn.  
**Tại sao xảy ra:** SAS expiry không phải blob deletion.  
**Ảnh hưởng production:** Tăng chi phí lưu trữ và thời gian tồn tại dữ liệu nhạy cảm.  
**Cách sửa:** Blob lifecycle policy hoặc cleanup worker theo retention được phê duyệt.

### [Medium] — Không có audit kết quả xuất

**Vấn đề:** Không ghi actor, scope, số dòng và outcome một cách an toàn.  
**Tại sao xảy ra:** Chỉ có một log thành công chứa URL.  
**Ảnh hưởng production:** Khó điều tra truy cập bất thường.  
**Cách sửa:** Audit trail theo actor/tenant/exportId, số dòng, duration, status và correlation ID.

## Phiên bản đề xuất

Thiết kế sau dùng các interface ứng dụng đã định nghĩa rõ: `ITenantPayrollAccess` kiểm tra quyền từ database/authorization service; `IPayrollExportJobQueue` ghi job vào durable store/queue; `IExportLinkService` chỉ cấp URL sau khi kiểm tra quyền và trạng thái. Không coi các interface này là API framework có sẵn.

```csharp
[Authorize]
[ApiController]
[Route("api/tenants/{tenantId:guid}/payroll")]
public sealed class PayrollExportController(
    ITenantPayrollAccess access,
    IPayrollExportJobQueue jobs,
    IExportLinkService links) : ControllerBase
{
    [HttpPost("exports")]
    public async Task<IActionResult> RequestExport(
        Guid tenantId, [FromBody] ExportRequest request,
        CancellationToken ct)
    {
        if (request.Year < 2000 || request.Year > DateTime.UtcNow.Year + 1)
            return BadRequest();

        if (!await access.CanReadPayrollAsync(User, tenantId, ct))
            return Forbid();

        var exportId = Guid.NewGuid();
        await jobs.EnqueueAsync(new PayrollExportJob(
            exportId, tenantId, request.Year,
            User.FindFirst("sub")?.Value
                ?? throw new InvalidOperationException("Missing subject")), ct);

        return AcceptedAtAction(nameof(GetExport),
            new { tenantId, exportId }, new { exportId });
    }

    [HttpGet("exports/{exportId:guid}")]
    public async Task<IActionResult> GetExport(
        Guid tenantId, Guid exportId, CancellationToken ct)
    {
        if (!await access.CanReadPayrollAsync(User, tenantId, ct))
            return Forbid();

        var result = await links.GetAuthorizedResultAsync(
            exportId, tenantId, ct);
        if (result is null) return NotFound();
        if (!result.IsReady) return Ok(new { status = "Processing" });

        var url = await links.CreateReadOnlyLinkAsync(
            result, TimeSpan.FromMinutes(10), ct);
        return Ok(new { status = "Ready", downloadUrl = url });
    }
}

public sealed record ExportRequest(int Year);
public sealed record PayrollExportJob(
    Guid ExportId, Guid TenantId, int Year, string RequestedBy);
```

Worker phải xử lý idempotent theo `ExportId`, truy vấn projection theo từng batch hoặc stream qua CSV writer, upload blob riêng tư, lưu trạng thái job bền vững, giới hạn số job đồng thời và dọn file theo retention. Cần xác thực lại quyền tại thời điểm cấp link; nếu chính sách yêu cầu thu hồi quyền ngay sau khi cấp link, thay SAS bằng download proxy có authorization trên mỗi request.

## Giải thích thiết kế sau khi sửa

Authorization xảy ra trước khi enqueue và trước khi phát link. Durable job tách thời gian xử lý file lớn khỏi HTTP timeout. `ExportId` là idempotency key cho retry; queue có thể deliver lại nên worker phải tránh publish nhiều bản không kiểm soát. CSV writer phải xử lý cả quoting và spreadsheet formula policy. Không đưa dữ liệu lương vào log hoặc telemetry attributes.

## Trade-offs

Background job cần queue, trạng thái, retry, cleanup và UX polling; với export nhỏ, streaming đồng bộ có thể đơn giản hơn nếu đáp ứng latency/memory budget. SAS giảm tải API nhưng bearer URL không tự enforce quyền sau khi phát hành; proxy tăng chi phí bandwidth và latency nhưng cho phép authorization liên tục.

## Cách kiểm thử

1. **Security integration:** user tenant A gọi export tenant B; không có job/file được tạo.
2. **CSV unit:** tên chứa comma, quote, newline, `=HYPERLINK(...)` được encode theo policy.
3. **Load:** nhiều export lớn đồng thời; memory và DB connections nằm trong budget.
4. **Failure-path:** worker chết sau upload trước khi update status; retry không tạo duplicate public result.
5. **Authorization lifecycle:** user bị thu hồi quyền trước khi tải; endpoint không cấp link mới, kiểm chứng chính sách với link đã cấp.

## Quan sát trong production

Theo dõi export requests/denials, job queue depth, age, retries, file size, rows processed, export duration p95/p99, memory/GC, SQL duration, Blob errors và audit theo exportId/correlation ID. Alert khi job tồn đọng, export bất thường theo tenant hoặc lỗi authorization tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Nếu yêu cầu revoke download ngay lập tức, bạn đổi kiến trúc thế nào?
2. Làm sao bảo đảm không có file orphan khi database commit thất bại?
3. Bạn quyết định ngưỡng chuyển từ streaming HTTP sang background job dựa trên số liệu nào?

# Code Review Challenge 2 — Rolling deployment Kubernetes gây gián đoạn checkout

## Bối cảnh

Một API checkout .NET 8 chạy 3 replicas trên Kubernetes. Mỗi lần deploy, khoảng 1–2% request gặp 502/503; đôi khi pod mới nhận traffic trước khi hoàn thành khởi tạo cache và connection pool. API cần tối thiểu 2 pod phục vụ trong rolling deployment; database là PostgreSQL dùng chung. Container lắng nghe port 8080, `/health/live` chỉ kiểm tra process, `/health/ready` kiểm tra khả năng phục vụ request. Pipeline deploy bằng `kubectl apply`.

## Đoạn code cần review

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 0
      maxUnavailable: 2
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
```

## Kết quả code review tham khảo

### [Critical] — Readiness và liveness bị đảo

**Vấn đề:** Readiness gọi `/health/live`, liveness gọi `/health/ready`.  
**Tại sao xảy ra:** Hai probe có semantics khác nhau.  
**Ảnh hưởng production:** Pod chưa sẵn sàng vẫn nhận traffic; lỗi dependency có thể khiến kubelet restart pod không cần thiết.  
**Cách sửa:** Readiness kiểm tra khả năng phục vụ, liveness chỉ kiểm tra trạng thái process có thể phục hồi bằng restart; startup probe nếu warm-up lâu.

### [High] — Availability budget không đạt SLA

**Vấn đề:** `maxUnavailable: 2` với 3 replicas cho phép chỉ còn 1 pod available trong rollout.  
**Tại sao xảy ra:** Strategy không phản ánh yêu cầu tối thiểu 2 pod.  
**Ảnh hưởng production:** Tăng latency/503 khi tải cao.  
**Cách sửa:** `maxUnavailable: 1`, `maxSurge: 1`; cân nhắc PodDisruptionBudget cho voluntary disruptions (PDB không thay thế rolling-update strategy).

### [High] — Credential nằm trong manifest

**Vấn đề:** Password được hardcode.  
**Tại sao xảy ra:** Secret được lưu như cấu hình thường.  
**Ảnh hưởng production:** Rò rỉ qua repository, CI logs, manifest.  
**Cách sửa:** Ưu tiên workload identity/managed identity nếu database hỗ trợ; nếu dùng password, dùng Kubernetes Secret hoặc external secret integration, RBAC tối thiểu, rotation. Kubernetes Secret không mặc định bảo đảm encryption at rest trong mọi cluster.

### [High] — Mutable image tag

**Vấn đề:** `latest` không pin artifact.  
**Tại sao xảy ra:** Cùng tag có thể trỏ tới image khác; apply không nhất thiết đổi Pod template nếu chỉ nội dung tag thay đổi.  
**Ảnh hưởng production:** Drift, rollback khó xác minh.  
**Cách sửa:** Pin image digest hoặc immutable version tag từ CI; ghi deployment revision.

### [High] — Thiếu graceful shutdown budget

**Vấn đề:** Không nêu termination behavior và drain handling.  
**Tại sao xảy ra:** Process có thể dừng khi request còn chạy hoặc endpoint propagation chưa hoàn tất.  
**Ảnh hưởng production:** 502/503 trong rollout.  
**Cách sửa:** ASP.NET Core xử lý SIGTERM và shutdown timeout phù hợp, terminationGracePeriodSeconds, readiness chuyển false khi drain; cân nhắc preStop có đo đạc khi ingress/LB propagation cần thời gian.

### [Medium] — Resource requests/limits chưa dựa trên đo lường

**Vấn đề:** 64Mi request và 128Mi limit có thể quá thấp với .NET 8 workload.  
**Tại sao xảy ra:** Không sizing từ working set, GC và tải thực.  
**Ảnh hưởng production:** OOMKilled, throttling/latency, scheduling sai.  
**Cách sửa:** Load test và quan sát memory/CPU, điều chỉnh request/limit theo evidence; thêm CPU limit chỉ khi phù hợp policy.

### [Medium] — Thiếu rollout verification

**Vấn đề:** `kubectl apply` đơn lẻ không xác nhận rollout hoàn tất.  
**Tại sao xảy ra:** Apply thành công không đồng nghĩa Pods ready.  
**Ảnh hưởng production:** Pipeline báo thành công khi bản mới chưa phục vụ.  
**Cách sửa:** `kubectl rollout status --timeout=...`, smoke test, kiểm tra error budget và rollback có điều kiện.

## Phiên bản đề xuất

Manifest dưới đây giả định secret `checkout-db` đã được tạo an toàn, image digest là giá trị do CI cung cấp (thay `<CI_IMAGE_DIGEST>` trước khi apply), endpoint readiness có semantics đúng và cluster đủ capacity cho surge.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
spec:
  replicas: 3
  minReadySeconds: 10
  progressDeadlineSeconds: 180
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          image: registry.example.com/checkout-api@sha256:<CI_IMAGE_DIGEST>
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: ConnectionStrings__Main
              valueFrom:
                secretKeyRef:
                  name: checkout-db
                  key: connectionString
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 5
            failureThreshold: 24
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
```

Các giá trị tài nguyên chỉ là điểm khởi đầu để load test, không phải sizing được xác nhận. CI thay placeholder digest bằng SHA256 thực, chạy `kubectl apply -f deployment.yaml`, `kubectl rollout status deployment/checkout-api --timeout=180s`, sau đó smoke test và theo dõi error rate. Nếu migration database không backward-compatible, phải thiết kế expand-contract trước rollout; không kỳ vọng rollback image tự rollback schema.

## Giải thích thiết kế sau khi sửa

Readiness quyết định pod có đủ điều kiện nhận traffic từ Service; liveness chỉ nên restart khi process thật sự cần phục hồi. Startup probe cho warm-up mà không khiến liveness giết pod sớm. Rollout budget bảo toàn ít nhất hai available replicas theo điều kiện controller; cần đủ node capacity và chú ý các sự cố ngoài rollout. Immutable image digest tạo release có thể kiểm chứng.

## Trade-offs

`maxSurge: 1` đòi hỏi thêm tài nguyên trong rollout. Readiness kiểm tra dependency quá nhạy có thể khiến toàn bộ pod unready khi dependency outage; cần thiết kế degraded mode nếu nghiệp vụ cho phép. Graceful drain tăng thời gian rollout. Secret management thêm vận hành và rotation; không thay thế kiểm soát truy cập và encryption.

## Cách kiểm thử

1. **Deployment validation:** rollout với tải ổn định, đo số available endpoints không xuống dưới 2 trong điều kiện không có lỗi độc lập.
2. **Failure injection:** PostgreSQL chậm/ngắt; readiness phản ánh chính sách phục vụ, liveness không tạo restart storm.
3. **Graceful shutdown:** gửi SIGTERM khi có request dài; đo 5xx, request completion và endpoint draining.
4. **Load test:** tăng RPS; theo dõi OOMKilled, CPU throttling, p95/p99 và pod startup duration.
5. **Release/rollback:** deploy digest A→B→A, xác nhận artifact và compatibility database.

## Quan sát trong production

Dashboard gồm rollout revision, desired/available replicas, readiness failures, restart count, OOMKilled, CPU throttling, memory working set, ingress 502/503, API p95/p99, active requests, dependency duration và trace correlation. Alert khi rollout vượt deadline, available replicas dưới ngưỡng hoặc 5xx tăng so với baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cluster không có capacity cho `maxSurge`, bạn điều chỉnh release strategy ra sao?
2. Vì sao PodDisruptionBudget không bảo đảm chống mọi loại outage?
3. Khi migration schema đã chạy, điều kiện nào cho phép rollback image an toàn?
