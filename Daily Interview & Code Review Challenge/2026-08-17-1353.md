# Code Review Challenge 1 — RabbitMQ consumer chạy song song nhưng xử lý message không an toàn

**Chủ đề:** Concurrency, EF Core lifetime, background processing, idempotency, cancellation, error handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một service .NET chạy dưới dạng worker và consume các message `EmployeeSyncRequested` từ RabbitMQ. Mỗi message yêu cầu đồng bộ thông tin nhân viên từ hệ thống ngoài vào SQL Server.

Service được deploy thành 3 replicas. Mỗi instance có thể nhận nhiều message liên tiếp. Production có lúc nhận burst khoảng vài trăm message/phút.

Sau khi tăng throughput bằng cách xử lý message song song, team ghi nhận:

- Thỉnh thoảng xuất hiện `A second operation was started on this context instance before a previous operation completed`.
- Một số employee bị gọi API ngoài nhiều lần.
- Một vài message mất sau khi worker restart.
- Khi external API chậm, memory và số task đang chạy tăng mạnh.
- Có message lỗi dữ liệu lặp đi lặp lại trong log nhưng không có cơ chế quarantine rõ ràng.

## Đoạn code cần review

```csharp
public sealed class EmployeeSyncWorker : BackgroundService
{
    private readonly AppDbContext _db;
    private readonly IEmployeeApi _employeeApi;
    private readonly IMessageQueue _queue;
    private readonly ILogger<EmployeeSyncWorker> _logger;

    public EmployeeSyncWorker(
        AppDbContext db,
        IEmployeeApi employeeApi,
        IMessageQueue queue,
        ILogger<EmployeeSyncWorker> logger)
    {
        _db = db;
        _employeeApi = employeeApi;
        _queue = queue;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var message in _queue.ReadAllAsync(stoppingToken))
        {
            _queue.Ack(message.Id);

            _ = Task.Run(async () =>
            {
                try
                {
                    var employee = await _db.Employees
                        .SingleOrDefaultAsync(x => x.Id == message.EmployeeId);

                    var profile = await _employeeApi
                        .GetEmployeeAsync(message.EmployeeId, CancellationToken.None);

                    if (employee == null)
                    {
                        employee = new Employee { Id = message.EmployeeId };
                        _db.Employees.Add(employee);
                    }

                    employee.DisplayName = profile.DisplayName;
                    employee.Department = profile.Department;
                    employee.UpdatedAt = DateTime.UtcNow;

                    await _db.SaveChangesAsync();
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex,
                        "Failed to process employee {EmployeeId}: {@Message}",
                        message.EmployeeId,
                        message);
                }
            });
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Inject `AppDbContext` trực tiếp vào `BackgroundService`

- **Problem:** Worker là long-lived service nhưng giữ một `DbContext` dùng xuyên suốt lifetime của worker.
- **Why it happens:** `DbContext` được thiết kế cho một unit of work ngắn và không thread-safe.
- **Production impact:** Nhiều task cùng thao tác trên một context dẫn đến exception, state tracking lẫn lộn và hành vi khó dự đoán.
- **Severity:** **Critical**
- **Recommended fix:** Inject `IServiceScopeFactory` hoặc `IDbContextFactory<AppDbContext>` và tạo context riêng cho mỗi message/unit of work.

### 2. Dùng cùng một `DbContext` từ nhiều `Task.Run` song song

- **Problem:** Nhiều task đọc/update/save đồng thời trên cùng context.
- **Why it happens:** `Task.Run` tạo concurrent execution nhưng context là shared mutable state.
- **Production impact:** Exception concurrency của EF Core, update sai entity, tracker phình to, operation fail ngẫu nhiên dưới tải.
- **Severity:** **Critical**
- **Recommended fix:** Mỗi message dùng scope/context riêng; không chia sẻ context giữa các task.

### 3. `Ack` message trước khi xử lý business operation thành công

- **Problem:** Message được xác nhận ngay khi vừa đọc.
- **Why it happens:** Queue coi message đã hoàn tất trước khi external API/database hoàn thành.
- **Production impact:** Nếu process crash, pod restart hoặc operation throw sau `Ack`, message có thể mất và không được xử lý lại.
- **Severity:** **Critical**
- **Recommended fix:** Chỉ ack sau khi operation hoàn tất thành công; failure cần nack/requeue hoặc chuyển sang dead-letter/quarantine policy tùy loại lỗi.

### 4. Fire-and-forget task không được quản lý

- **Problem:** `_ = Task.Run(...)` bỏ reference của task.
- **Why it happens:** Worker không await task và cũng không track lifecycle của chúng.
- **Production impact:** Shutdown có thể kết thúc process khi task chưa hoàn tất; exception bị catch nhưng completion không được host quản lý; backlog task có thể tăng vô hạn.
- **Severity:** **High**
- **Recommended fix:** Dùng bounded concurrency rõ ràng, ví dụ `SemaphoreSlim`, `Channel`, worker pool hoặc queue consumer concurrency được cấu hình có giới hạn.

### 5. Không có backpressure/bounded concurrency

- **Problem:** Mỗi message tạo thêm một task mới không có giới hạn.
- **Why it happens:** Throughput đầu vào có thể cao hơn tốc độ external API/database.
- **Production impact:** Memory tăng, nhiều request outbound đồng thời, DB connection pool pressure, timeout dây chuyền và cascading failure.
- **Severity:** **High**
- **Recommended fix:** Giới hạn parallelism theo capacity thực tế; đo latency downstream trước khi chọn concurrency.

### 6. Bỏ qua shutdown cancellation

- **Problem:** External API dùng `CancellationToken.None`; EF calls cũng không truyền `stoppingToken`.
- **Why it happens:** Operation tiếp tục chạy dù host yêu cầu dừng.
- **Production impact:** Shutdown chậm, rolling deployment có thể cắt ngang operation, duplicate work khi message được giao lại.
- **Severity:** **High**
- **Recommended fix:** Truyền cancellation token phù hợp cho I/O. Cần phân biệt shutdown cancellation với timeout/business retry.

### 7. Không có idempotency/business operation identity

- **Problem:** Delivery lại hoặc duplicate message có thể gọi external API và update DB nhiều lần.
- **Why it happens:** Hệ thống giả định một message chỉ được xử lý đúng một lần.
- **Production impact:** Duplicate side effects, unnecessary load, trạng thái cuối phụ thuộc thứ tự message.
- **Severity:** **High**
- **Recommended fix:** Có `MessageId`/`OperationId` ổn định, lưu processed state hoặc dùng unique constraint/conditional state transition. Business logic phải chịu được redelivery.

### 8. Race condition khi hai message cùng `EmployeeId`

- **Problem:** Hai worker có thể cùng đọc employee chưa tồn tại rồi cùng insert, hoặc ghi đè update của nhau.
- **Why it happens:** Read-then-write không có concurrency policy.
- **Production impact:** Unique constraint exception, lost update hoặc trạng thái cũ ghi đè trạng thái mới.
- **Severity:** **High**
- **Recommended fix:** Xác định ordering requirement. Dùng unique key, optimistic concurrency/version hoặc serialization theo business key nếu thực sự cần.

### 9. Catch mọi exception rồi chỉ log

- **Problem:** Không phân loại transient/permanent failure và không báo queue xử lý thất bại.
- **Why it happens:** Exception bị nuốt sau khi message đã ack.
- **Production impact:** Data silently inconsistent; retry policy không tồn tại; poison message không được quarantine.
- **Severity:** **High**
- **Recommended fix:** Phân loại lỗi: transient → retry/backoff; permanent validation error → dead-letter/quarantine; unexpected → fail và alert.

### 10. Log toàn bộ message bằng structured destructuring

- **Problem:** `{@Message}` có thể log các field nhạy cảm trong payload.
- **Why it happens:** Logging object tiện nhưng không kiểm soát dữ liệu.
- **Production impact:** PII/secrets có thể vào log aggregation.
- **Severity:** **Medium**
- **Recommended fix:** Log whitelist fields như `MessageId`, `EmployeeId`, attempt, correlation ID; redact dữ liệu nhạy cảm.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa một flow có bounded concurrency, scope riêng, ack sau success và xử lý failure rõ ràng. Chi tiết API của queue có thể khác tùy implementation thực tế.

```csharp
public sealed class EmployeeSyncWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly IMessageQueue _queue;
    private readonly ILogger<EmployeeSyncWorker> _logger;
    private readonly SemaphoreSlim _parallelism = new(8);

    public EmployeeSyncWorker(
        IServiceScopeFactory scopeFactory,
        IMessageQueue queue,
        ILogger<EmployeeSyncWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _queue = queue;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var running = new HashSet<Task>();

        await foreach (var message in _queue.ReadAllAsync(stoppingToken))
        {
            await _parallelism.WaitAsync(stoppingToken);

            var task = ProcessMessageAsync(message, stoppingToken)
                .ContinueWith(
                    _ => _parallelism.Release(),
                    CancellationToken.None,
                    TaskContinuationOptions.ExecuteSynchronously,
                    TaskScheduler.Default);

            running.Add(task);
            running.RemoveWhere(x => x.IsCompleted);
        }

        await Task.WhenAll(running);
    }

    private async Task ProcessMessageAsync(
        EmployeeSyncRequested message,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();

        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var employeeApi = scope.ServiceProvider.GetRequiredService<IEmployeeApi>();
        var processor = scope.ServiceProvider.GetRequiredService<IEmployeeSyncProcessor>();

        try
        {
            var alreadyProcessed = await db.ProcessedMessages
                .AnyAsync(x => x.MessageId == message.Id, cancellationToken);

            if (alreadyProcessed)
            {
                await _queue.AckAsync(message.Id, cancellationToken);
                return;
            }

            var profile = await employeeApi.GetEmployeeAsync(
                message.EmployeeId,
                cancellationToken);

            await processor.ApplyAsync(db, message, profile, cancellationToken);

            db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = message.Id,
                ProcessedAtUtc = DateTime.UtcNow
            });

            await db.SaveChangesAsync(cancellationToken);
            await _queue.AckAsync(message.Id, cancellationToken);
        }
        catch (PermanentMessageException ex)
        {
            _logger.LogWarning(ex,
                "Permanent failure for MessageId {MessageId}, EmployeeId {EmployeeId}",
                message.Id,
                message.EmployeeId);

            await _queue.DeadLetterAsync(message.Id, cancellationToken);
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Transient/unexpected failure for MessageId {MessageId}, EmployeeId {EmployeeId}",
                message.Id,
                message.EmployeeId);

            await _queue.NackAsync(message.Id, requeue: true, cancellationToken);
        }
    }
}
```

### Điểm cần bổ sung trong production

- `ProcessedMessages.MessageId` nên có unique constraint để idempotency không chỉ dựa vào `AnyAsync`.
- Nếu external API tạo side effect không idempotent, lưu `ProcessedMessages` sau external call vẫn chưa giải quyết hoàn toàn trường hợp crash giữa external success và DB commit. Khi đó cần API-level idempotency key, read-back/reconciliation hoặc một workflow state machine phù hợp.
- `SemaphoreSlim(8)` chỉ là ví dụ; concurrency phải dựa trên đo lường database/external API capacity.
- Retry cần giới hạn số lần, backoff và dead-letter policy; không requeue vô hạn.

## Trade-offs

- **Bounded concurrency** giảm throughput cực đại nhưng bảo vệ DB/external dependency khỏi overload.
- **Processed message table** tăng write/storage nhưng tạo audit trail và giúp duplicate suppression.
- **Distributed lock theo `EmployeeId`** có thể giảm race nhưng không thay thế idempotency, không giải quyết crash boundary và làm hệ thống phụ thuộc thêm vào lock infrastructure.
- Nếu business yêu cầu strict ordering theo employee, partition/serialization theo key có thể phù hợp hơn optimistic concurrency.

## Cách kiểm thử

1. **Concurrency test:** Gửi 20 message cùng `EmployeeId` từ nhiều workers, xác minh không có duplicate insert và final state đúng theo ordering rule.
2. **Redelivery test:** Xử lý cùng một `MessageId` hai lần, xác minh external side effect/database state không bị lặp ngoài mong muốn.
3. **Crash-after-side-effect test:** Giả lập external API thành công rồi throw trước DB commit; kiểm tra recovery/reconciliation strategy.
4. **Load test:** Burst vài nghìn messages, đo task count, memory, DB pool usage, external latency và queue lag.
5. **Poison message test:** Message invalid phải đi dead-letter/quarantine sau policy rõ ràng, không requeue vô hạn.

### Alerts

# Code Review Challenge 2 — Multi-tenant file download có authorization nhưng vẫn rò rỉ dữ liệu

## Bối cảnh

Một ASP.NET Core API cho phép user tải các report được tạo trước đó. Hệ thống là multi-tenant SaaS. File được lưu trên local/shared filesystem theo tenant.

Production có khoảng 20.000 report files. Một số file lớn 300–800 MB.

Security review phát hiện user của tenant A đôi khi đoán được `reportId` của tenant B. Team cho rằng không có vấn đề vì endpoint đã có `[Authorize]`.

Code hiện tại:

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IWebHostEnvironment _env;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        AppDbContext db,
        IWebHostEnvironment env,
        ILogger<ReportsController> logger)
    {
        _db = db;
        _env = env;
        _logger = logger;
    }

    [HttpGet("download")]
    public async Task<IActionResult> Download(
        string reportId,
        string fileName)
    {
        var report = await _db.Reports
            .FirstOrDefaultAsync(x => x.Id == reportId);

        if (report == null)
            return NotFound();

        var path = Path.Combine(
            _env.ContentRootPath,
            "reports",
            report.TenantId,
            fileName);

        _logger.LogInformation(
            "User {User} downloading {Path}",
            User.Identity?.Name,
            path);

        if (!System.IO.File.Exists(path))
            return NotFound();

        var bytes = await System.IO.File.ReadAllBytesAsync(path);

        Response.Headers["X-Source-Path"] = path;

        return File(
            bytes,
            "application/octet-stream",
            fileName);
    }
}
```

### Gợi ý 1

## Dừng lại và tự review

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

### 1. Broken object-level authorization / tenant isolation

- **Problem:** Query report chỉ theo `Id`.
- **Why it happens:** `[Authorize]` chỉ yêu cầu request đã được authenticate/đáp ứng policy cấu hình; nó không tự chứng minh report thuộc tenant/user hiện tại.
- **Production impact:** User tenant A có thể truy cập metadata/file của tenant B nếu đoán hoặc thu được `reportId`.
- **Severity:** **Critical**
- **Recommended fix:** Resolve tenant từ trusted claims/context và query `report.Id == reportId && report.TenantId == currentTenantId`; nếu cần owner/role policy thì enforce thêm.

### 2. `fileName` do user kiểm soát nhưng được dùng trực tiếp trong filesystem path

- **Problem:** User có thể truyền path traversal hoặc absolute/rooted path tùy platform/input.
- **Why it happens:** `Path.Combine` chỉ ghép path; nó không phải security validator.
- **Production impact:** Có thể đọc file ngoài thư mục report nếu path resolution cho phép.
- **Severity:** **Critical**
- **Recommended fix:** Tốt nhất không nhận `fileName` tùy ý từ client; lưu server-side storage key/path trong DB. Nếu bắt buộc nhận, canonicalize và xác minh final path nằm dưới tenant root.

### 3. File tải xuống không ràng buộc với metadata report

- **Problem:** Sau khi tìm report, code dùng một `fileName` độc lập do client cung cấp.
- **Why it happens:** Report record không quyết định chính xác file nào được phép đọc.
- **Production impact:** Một report hợp lệ có thể trở thành “vé vào cửa” để thử đọc file khác trong cùng tenant directory.
- **Severity:** **High**
- **Recommended fix:** Lấy storage key/file name từ `report` record; client chỉ truyền `reportId`.

### 4. Đọc toàn bộ file vào memory

- **Problem:** `ReadAllBytesAsync` allocate byte array bằng kích thước file.
- **Why it happens:** Endpoint buffer toàn bộ file trước khi gửi.
- **Production impact:** Nhiều download lớn đồng thời có thể gây memory pressure, GC pressure hoặc OOM.
- **Severity:** **High**
- **Recommended fix:** Stream file thay vì load toàn bộ vào memory, ví dụ `FileStreamResult` hoặc storage SDK streaming.

### 5. Không truyền request cancellation token cho file I/O và DB query

- **Problem:** Khi client disconnect, server vẫn có thể tiếp tục work không cần thiết.
- **Why it happens:** Không dùng `HttpContext.RequestAborted`.
- **Production impact:** Lãng phí I/O/DB resources, đặc biệt với download lớn hoặc load cao.
- **Severity:** **Medium**
- **Recommended fix:** Truyền `RequestAborted` vào async DB/storage operations khi API hỗ trợ.

### 6. Expose physical server path qua response header

- **Problem:** `X-Source-Path` trả đường dẫn filesystem thật.
- **Why it happens:** Debug information bị đưa vào response production.
- **Production impact:** Information disclosure về directory layout/server structure, hỗ trợ attacker xây path traversal payload tốt hơn.
- **Severity:** **High**
- **Recommended fix:** Xóa header. Dùng internal correlation ID nếu cần troubleshoot.

### 7. Log physical path và user identity không cần thiết

- **Problem:** Log ghi full path; tùy naming convention có thể chứa tenant/customer/file data nhạy cảm.
- **Why it happens:** Log theo debug convenience.
- **Production impact:** Sensitive metadata tồn tại lâu trong centralized logs.
- **Severity:** **Medium**
- **Recommended fix:** Log report ID, tenant ID đã chuẩn hóa, result status và correlation ID; tránh raw path.

### 8. Không dùng `AsNoTracking()` cho read-only metadata query

- **Problem:** Query chỉ đọc nhưng vẫn có thể tracking entity.
- **Why it happens:** Default EF Core tracking behavior.
- **Production impact:** Nhỏ hơn các security issue nhưng tăng unnecessary tracking overhead ở endpoint read-only.
- **Severity:** **Low**
- **Recommended fix:** Dùng projection + `AsNoTracking()` khi không update entity.

### 9. Content type và filename chưa được kiểm soát theo metadata

- **Problem:** Client quyết định download filename; content type luôn generic.
- **Why it happens:** Metadata file không được lưu/validate đầy đủ.
- **Production impact:** UX kém, audit khó, có thể tạo filename gây nhầm lẫn ở client.
- **Severity:** **Low/Medium**
- **Recommended fix:** Lấy sanitized download filename và content type từ trusted report metadata.

## Phiên bản code đề xuất

Giả định:

- Tenant ID được resolve từ một `ICurrentTenant` đã validate claim/context.
- `Report` lưu `StorageFileName`, `DownloadFileName`, `ContentType`.
- File nằm dưới một tenant root cố định do server kiểm soát.

```csharp
[Authorize]
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IWebHostEnvironment _env;
    private readonly ICurrentTenant _currentTenant;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        AppDbContext db,
        IWebHostEnvironment env,
        ICurrentTenant currentTenant,
        ILogger<ReportsController> logger)
    {
        _db = db;
        _env = env;
        _currentTenant = currentTenant;
        _logger = logger;
    }

    [HttpGet("{reportId}/download")]
    public async Task<IActionResult> Download(
        string reportId,
        CancellationToken cancellationToken)
    {
        var tenantId = _currentTenant.TenantId;

        var report = await _db.Reports
            .AsNoTracking()
            .Where(x => x.Id == reportId && x.TenantId == tenantId)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.StorageFileName,
                x.DownloadFileName,
                x.ContentType
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (report is null)
            return NotFound();

        var tenantRoot = Path.GetFullPath(Path.Combine(
            _env.ContentRootPath,
            "reports",
            report.TenantId));

        var fullPath = Path.GetFullPath(Path.Combine(
            tenantRoot,
            report.StorageFileName));

        var prefix = tenantRoot.EndsWith(Path.DirectorySeparatorChar)
            ? tenantRoot
            : tenantRoot + Path.DirectorySeparatorChar;

        if (!fullPath.StartsWith(prefix, StringComparison.OrdinalIgnoreCase))
        {
            _logger.LogWarning(
                "Rejected invalid report storage path for ReportId {ReportId}, TenantId {TenantId}",
                report.Id,
                report.TenantId);

            return NotFound();
        }

        if (!System.IO.File.Exists(fullPath))
            return NotFound();

        var stream = new FileStream(
            fullPath,
            FileMode.Open,
            FileAccess.Read,
            FileShare.Read,
            bufferSize: 64 * 1024,
            useAsync: true);

        _logger.LogInformation(
            "Report download started. ReportId {ReportId}, TenantId {TenantId}",
            report.Id,
            report.TenantId);

        return File(
            stream,
            string.IsNullOrWhiteSpace(report.ContentType)
                ? "application/octet-stream"
                : report.ContentType,
            report.DownloadFileName,
            enableRangeProcessing: true);
    }
}
```

### Recommendation tốt hơn nữa

Nếu hệ thống đã dùng object storage/blob storage, nên lưu một opaque storage key thay vì filesystem path và stream từ storage SDK. Authorization vẫn phải xảy ra trước khi phát URL hoặc stream object.

Nếu dùng pre-signed/SAS URL, URL phải:

- chỉ cấp cho object đã authorization;
- có lifetime ngắn;
- không cho phép list/write nếu chỉ cần read;
- được audit;
- không log token đầy đủ.

## Trade-offs

- **Streaming qua API:** kiểm soát authorization/audit tốt nhưng app server chịu bandwidth.
- **Signed URL từ object storage:** giảm bandwidth app server nhưng cần quản lý expiry/scope/token leakage cẩn thận.
- **Canonical path validation:** cần thiết nếu dùng filesystem, nhưng thiết kế mạnh hơn là không nhận raw filename/path từ client.
- Trả `404` thay vì `403` cho object tenant khác có thể giảm information disclosure, nhưng security team cần thống nhất policy/audit.

## Cách kiểm thử

1. **Tenant isolation test:** User tenant A gọi `reportId` của tenant B → không trả file và không lộ metadata tenant B.
2. **Path traversal test:** Storage/file metadata chứa `../`, absolute path hoặc separator variants → request phải bị reject.
3. **Large-file load test:** 20–50 concurrent downloads file lớn, quan sát memory không tăng tuyến tính theo tổng kích thước file.
4. **Client disconnect test:** Hủy request giữa chừng, đảm bảo stream/resource được cleanup và server không tiếp tục work không cần thiết.
5. **Authorization role test:** Nếu một report chỉ dành cho role cụ thể, authenticated user cùng tenant nhưng thiếu permission vẫn không tải được.

## Quan sát trong production

### Logs

- `ReportId`, tenant ID, user subject ID/correlation ID.
- Authorization denied / not found / success.
- Không log physical path, access token hoặc signed URL đầy đủ.

### Metrics

- Download count và failure count.
- Bytes served.
- Concurrent downloads.
- Download duration P50/P95/P99.
- 401/403/404 rate theo endpoint.
- File-not-found rate.
- Process memory và GC pressure.

### Traces

Trace:

`HTTP request → authorization/tenant resolution → DB metadata lookup → storage/file open → response stream`.

### Alerts

- Tăng đột biến cross-tenant authorization failures.
- Nhiều path-validation rejection.
- Memory pressure/OOM risk.
- Storage/file open errors tăng cao.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `DbContext` là unit-of-work object và không nên được chia sẻ giữa nhiều concurrent operations.
- Background processing cần thiết kế cho redelivery/retry thay vì giả định exactly-once execution.
- Ack message trước khi business transaction hoàn tất có thể gây mất dữ liệu.
- Bounded concurrency/backpressure là một phần của reliability, không chỉ là performance tuning.
- Authentication không đồng nghĩa object-level authorization.
- Multi-tenant query phải ràng buộc object với tenant/user hiện tại tại trusted boundary.
- `Path.Combine` không phải security boundary; raw filename/path từ client phải được loại bỏ hoặc canonicalize + validate.
- File lớn nên stream thay vì buffer toàn bộ vào memory.

## Mẫu tư duy cần nhớ

1. **Define the unit of work** — resource lifetime phải khớp boundary của operation.
2. **Assume retries and redelivery** — thiết kế business effect idempotent trước khi scale worker.
3. **Authorize the object, not only the request** — authenticated user vẫn có thể truy cập nhầm object nếu query không scope đúng.
4. **Validate at trust boundaries** — client-controlled path, identifier và metadata đều phải được coi là untrusted.
5. **Design backpressure explicitly** — downstream capacity phải quyết định concurrency.
