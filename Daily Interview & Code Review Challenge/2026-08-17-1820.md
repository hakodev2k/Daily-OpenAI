# Code Review Challenge 1 — Fire-and-forget trong API làm mất tác vụ và dùng `DbContext` sau khi request đã kết thúc

**Chủ đề:** async/await, resource lifetime, background jobs, error handling, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API nhận yêu cầu hoàn tất đơn hàng. Sau khi cập nhật trạng thái đơn hàng trong database, hệ thống cần thực hiện thêm ba việc:

- ghi audit record,
- gửi email xác nhận,
- gọi một service nội bộ để cập nhật reporting.

Để response nhanh hơn, team đã dùng `Task.Run` và không `await` phần xử lý sau. API chạy trên nhiều instance sau load balancer và được deploy bằng rolling deployment.

Lưu lượng bình thường khoảng 50–100 request/giây, nhưng trong campaign có thể tăng lên 500–800 request/giây. Production ghi nhận:

- đôi lúc đơn hàng đã `Completed` nhưng không có audit record,
- email có lúc không được gửi,
- log có `ObjectDisposedException` liên quan `AppDbContext`,
- khi deploy/restart, một số tác vụ biến mất,
- exception trong background task khó truy vết,
- CPU tăng mạnh khi burst traffic xảy ra.

Business yêu cầu trạng thái đơn hàng trong DB phải chính xác. Audit và email có thể eventual consistency trong vài phút, nhưng không được mất im lặng và phải có khả năng retry có kiểm soát.

## Đoạn code cần review

```csharp
public sealed class OrdersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly HttpClient _reportingClient;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(
        AppDbContext db,
        IEmailSender emailSender,
        HttpClient reportingClient,
        ILogger<OrdersController> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _reportingClient = reportingClient;
        _logger = logger;
    }

    [HttpPost("api/orders/{id:guid}/complete")]
    public async Task<IActionResult> Complete(
        Guid id,
        CancellationToken cancellationToken)
    {
        var order = await _db.Orders
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (order == null)
            return NotFound();

        order.Status = OrderStatus.Completed;
        order.CompletedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        Task.Run(async () =>
        {
            _db.AuditLogs.Add(new AuditLog
            {
                EntityId = order.Id,
                Action = "OrderCompleted",
                CreatedAt = DateTime.UtcNow
            });

            await _db.SaveChangesAsync();

            await _emailSender.SendOrderCompletedAsync(
                order.CustomerEmail,
                order.Id,
                CancellationToken.None);

            await _reportingClient.PostAsJsonAsync(
                "/api/order-events",
                new { order.Id, order.CompletedAt });

            _logger.LogInformation(
                "Post-completion work finished for {OrderId}",
                order.Id);
        });

        return Accepted(new { order.Id, order.Status });
    }
}
```

## Kết quả code review tham khảo

### 1. Dùng scoped `DbContext` sau khi request kết thúc

**Problem:** Background task capture `_db` từ controller.  
**Why it happens:** `AppDbContext` thường gắn với request scope; task có thể tiếp tục sau khi scope đã bị dispose.  
**Production impact:** `ObjectDisposedException`, mất audit record hoặc behavior không ổn định theo timing.  
**Severity:** Critical  
**Recommended fix:** Không capture scoped dependency vào fire-and-forget task. Tách work sang durable worker/job; worker tạo scope/context riêng cho mỗi execution.

### 2. Background work không durable và có thể mất khi process restart

**Problem:** `Task.Run` chỉ tồn tại trong memory của process hiện tại.  
**Why it happens:** Không có persistent queue/job record.  
**Production impact:** Rolling deployment, crash hoặc scale-in có thể làm task biến mất dù API đã trả `Accepted`.  
**Severity:** Critical  
**Recommended fix:** Persist work trong database/outbox hoặc enqueue vào durable background job/message system sau khi state transition được commit an toàn.

### 3. Exception của fire-and-forget task không được quan sát đúng cách

**Problem:** Task không được lưu, `await` hoặc supervision.  
**Why it happens:** Code dùng fire-and-forget như cách giảm latency.  
**Production impact:** Failure có thể chỉ xuất hiện thành unobserved/log rời rạc; caller đã nhận success và hệ thống không có retry state rõ ràng.  
**Severity:** High  
**Recommended fix:** Worker phải capture outcome, retry count, last error, next attempt và dead-letter/manual-review state khi cần.

### 4. Không có backpressure khi burst traffic

**Problem:** Mỗi request tạo một task mới ngay lập tức.  
**Why it happens:** `Task.Run` không giới hạn concurrency theo capacity của downstream dependencies.  
**Production impact:** Hàng trăm/hàng nghìn task đồng thời có thể tăng CPU, memory, connection pressure và làm dependency quá tải.  
**Severity:** High  
**Recommended fix:** Dùng bounded queue/worker concurrency hoặc background-job system có concurrency limit và rate control.

### 5. Side effects không idempotent khi retry

**Problem:** Audit, email và reporting nằm trong một chuỗi nhưng không có idempotency key hay trạng thái riêng cho từng side effect.  
**Why it happens:** Happy path giả định tất cả bước chỉ chạy một lần.  
**Production impact:** Nếu email thành công nhưng reporting fail rồi retry toàn task, email có thể gửi trùng.  
**Severity:** High  
**Recommended fix:** Mỗi external action cần idempotency semantics hoặc delivery record riêng; ví dụ `OperationId`/`OrderId + EventType` unique key.

### 6. Business transition `Completed` chưa có guard/idempotency rõ ràng

**Problem:** Endpoint có thể được gọi lặp lại và tiếp tục tạo post-completion work.  
**Why it happens:** Không kiểm tra current state hoặc operation identity.  
**Production impact:** Duplicate audit/email/reporting khi client retry hoặc hai request đến gần nhau.  
**Severity:** High  
**Recommended fix:** Enforce valid state transition và database invariant; nếu already completed thì trả kết quả idempotent theo contract.

### 7. Không propagate timeout/cancellation phù hợp cho downstream worker

**Problem:** Email dùng `CancellationToken.None`, reporting call cũng không có policy rõ ràng.  
**Why it happens:** Code tách khỏi request nhưng không thay bằng worker lifecycle token/timeout riêng.  
**Production impact:** Dependency treo có thể giữ worker lâu và chiếm concurrency slot.  
**Severity:** Medium  
**Recommended fix:** Worker dùng cancellation token của host/job và timeout riêng cho từng dependency call.

### 8. Capture tracked entity `order` vào background task

**Problem:** Background task dùng entity đã được load/tracked trong request scope.  
**Why it happens:** Closure capture object để tiện truy cập dữ liệu.  
**Production impact:** Dữ liệu có thể stale, coupling với EF tracking state và làm lifecycle khó reasoning.  
**Severity:** Medium  
**Recommended fix:** Persist immutable payload tối thiểu như `OrderId`, `CustomerId`, event timestamp; worker rehydrate dữ liệu cần thiết hoặc dùng payload đã versioned.

### 9. Observability thiếu operation/job identity

**Problem:** Chỉ log một dòng cuối với `OrderId`.  
**Why it happens:** Background flow không được model như một workflow độc lập.  
**Production impact:** Khó biết request nào tạo job, attempt thứ mấy, bước nào lỗi và retry bao lâu.  
**Severity:** Medium  
**Recommended fix:** Structured log với `OperationId`, `OrderId`, `JobId`, attempt, dependency, duration, result và trace correlation.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng transactional outbox đơn giản để ghi state change và intent xử lý hậu kỳ trong cùng transaction. Worker xử lý outbox ở scope độc lập.

```csharp
public sealed class OrderService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public OrderService(AppDbContext db, TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task<Guid> CompleteAsync(
        Guid orderId,
        CancellationToken cancellationToken)
    {
        var now = _timeProvider.GetUtcNow().UtcDateTime;
        var operationId = Guid.NewGuid();

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var order = await _db.Orders
            .SingleOrDefaultAsync(
                x => x.Id == orderId,
                cancellationToken)
            ?? throw new InvalidOperationException("Order not found.");

        if (order.Status == OrderStatus.Completed)
            return order.CompletionOperationId;

        if (order.Status != OrderStatus.Processing)
            throw new InvalidOperationException("Invalid state transition.");

        order.Status = OrderStatus.Completed;
        order.CompletedAt = now;
        order.CompletionOperationId = operationId;

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = operationId,
            Type = "OrderCompleted",
            AggregateId = order.Id,
            CreatedAt = now,
            Status = OutboxStatus.Pending
        });

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        return operationId;
    }
}

public sealed class OrderCompletedWorker
{
    private readonly IServiceScopeFactory _scopeFactory;

    public OrderCompletedWorker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task ProcessAsync(
        Guid messageId,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var email = scope.ServiceProvider.GetRequiredService<IEmailSender>();
        var reporting = scope.ServiceProvider.GetRequiredService<IReportingClient>();

        var message = await db.OutboxMessages
            .SingleAsync(x => x.Id == messageId, cancellationToken);

        if (message.Status == OutboxStatus.Completed)
            return;

        var order = await db.Orders
            .AsNoTracking()
            .SingleAsync(x => x.Id == message.AggregateId, cancellationToken);

        await email.SendOrderCompletedAsync(
            order.CustomerEmail,
            order.Id,
            message.Id,
            cancellationToken);

        await reporting.PublishOrderCompletedAsync(
            order.Id,
            order.CompletedAt!.Value,
            message.Id,
            cancellationToken);

        message.Status = OutboxStatus.Completed;
        message.CompletedAt = DateTime.UtcNow;
        await db.SaveChangesAsync(cancellationToken);
    }
}
```

Trong hệ thống thực tế, worker cần claim/lease message an toàn khi có nhiều instance, retry policy và trạng thái từng delivery nếu các side effect phải retry độc lập.

## Trade-offs

- Transactional outbox tăng schema và worker complexity nhưng đổi lại durability và auditability tốt hơn.
- Hangfire hoặc message broker có thể phù hợp hơn nếu hạ tầng đã có sẵn; tuy nhiên vẫn cần giải quyết khoảng trống giữa DB commit và enqueue nếu hai việc không atomic.
- Retry toàn event đơn giản nhưng dễ duplicate side effect; tracking từng delivery phức tạp hơn nhưng kiểm soát tốt hơn.
- `Accepted` phù hợp nếu contract nói rõ hậu xử lý là asynchronous; nếu client cần biết email/reporting đã hoàn tất thì cần status endpoint hoặc workflow state.

## Cách kiểm thử

1. **Integration test:** DB commit thành công và outbox message luôn được tạo cùng state transition.
2. **Restart test:** dừng process ngay sau HTTP response, khởi động lại và xác nhận pending outbox vẫn được xử lý.
3. **Failure-path test:** email thành công nhưng reporting timeout; xác nhận retry không tạo side effect trùng ngoài policy.
4. **Load test:** burst hàng trăm completion/giây, xác nhận queue depth tăng có kiểm soát và API không tạo task vô hạn.
5. **Concurrency test:** hai request complete cùng một order, xác nhận chỉ một logical completion event được tạo.

## Quan sát trong production

# Code Review Challenge 2 — Cập nhật quyền người dùng bị lost update khi hai admin thao tác đồng thời

**Chủ đề:** EF Core concurrency, authorization, transaction handling, correctness, logging & observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một trang quản trị cho phép admin cập nhật role và danh sách permission của user. Backend dùng ASP.NET Core + EF Core. Hai admin có thể mở cùng một user ở hai tab khác nhau rồi lưu thay đổi cách nhau vài giây.

Production ghi nhận một số trường hợp:

- Admin A thêm permission `Reports.Read`, sau đó Admin B đổi role và save; permission của A biến mất.
- UI vẫn báo update thành công cho cả hai admin.
- Audit log chỉ ghi trạng thái cuối, không biết thay đổi nào đã bị ghi đè.
- Có lúc admin có scope quản trị tenant A nhưng request truyền `userId` của tenant B.

Business yêu cầu không được silent lost update ở thay đổi quyền. Cross-tenant update phải bị chặn. Nếu dữ liệu đã thay đổi sau lúc admin tải form, API nên trả conflict để UI yêu cầu reload/merge thay vì tự động ghi đè.

## Đoạn code cần review

```csharp
public sealed class UsersController : ControllerBase
{
    private readonly AppDbContext _db;

    public UsersController(AppDbContext db)
    {
        _db = db;
    }

    [HttpPut("api/admin/users/{userId:guid}/access")]
    public async Task<IActionResult> UpdateAccess(
        Guid userId,
        UpdateAccessRequest request,
        CancellationToken cancellationToken)
    {
        var user = await _db.Users
            .Include(x => x.UserPermissions)
            .SingleOrDefaultAsync(
                x => x.Id == userId,
                cancellationToken);

        if (user == null)
            return NotFound();

        user.Role = request.Role;

        _db.UserPermissions.RemoveRange(user.UserPermissions);

        foreach (var permission in request.Permissions)
        {
            user.UserPermissions.Add(new UserPermission
            {
                UserId = user.Id,
                Permission = permission
            });
        }

        await _db.SaveChangesAsync(cancellationToken);

        return Ok(new
        {
            user.Id,
            user.Role,
            Permissions = request.Permissions
        });
    }
}
```

## Kết quả code review tham khảo

### 1. Thiếu tenant authorization trong query/update

**Problem:** User được lookup chỉ bằng `userId`.  
**Why it happens:** Authorization có thể đang được giả định ở UI hoặc endpoint-level role check nhưng không enforce resource scope.  
**Production impact:** Admin tenant A có thể sửa user tenant B nếu biết/đoán được `userId`, tùy policy và phần middleware bên ngoài.  
**Severity:** Critical  
**Recommended fix:** Enforce tenant/resource authorization server-side; query theo tenant được phép hoặc dùng authorization service/policy kiểm tra resource trước khi mutate.

### 2. Không có optimistic concurrency nên xảy ra silent lost update

**Problem:** Hai admin cùng đọc cùng state rồi lần save sau ghi đè lần save trước.  
**Why it happens:** Entity không có concurrency token/version được kiểm tra trong update.  
**Production impact:** Permission hoặc role có thể biến mất mà cả hai request đều trả success. Với access control đây là lỗi correctness và security governance nghiêm trọng.  
**Severity:** High  
**Recommended fix:** Dùng concurrency token/version; client gửi version đã đọc và API trả `409 Conflict` hoặc `412 Precondition Failed` theo contract khi version mismatch.

### 3. Xoá toàn bộ permission rồi insert lại làm conflict window lớn và audit kém

**Problem:** Mọi update đều remove toàn collection và recreate.  
**Why it happens:** Code xử lý desired state bằng replace-all đơn giản.  
**Production impact:** Tăng số database writes, dễ tạo conflict hơn và khó biết permission nào thực sự được add/remove.  
**Severity:** High  
**Recommended fix:** Tính diff giữa current và requested permissions; add/remove chỉ phần thay đổi, sau khi concurrency version được xác nhận.

### 4. Không validate permission values theo allow-list/policy

**Problem:** `request.Permissions` được dùng trực tiếp.  
**Why it happens:** Endpoint giả định client chỉ gửi permission hợp lệ.  
**Production impact:** Invalid hoặc không được phép assign permission có thể lọt vào DB nếu không có lớp validation khác.  
**Severity:** High  
**Recommended fix:** Validate permission name và kiểm tra admin có quyền grant từng permission/role hay không.

### 5. Không validate role transition hoặc privilege escalation

**Problem:** `user.Role = request.Role` không kiểm tra business/security rule.  
**Why it happens:** Authorization chỉ được xem là quyền gọi endpoint, không phải quyền cấp role cụ thể.  
**Production impact:** Một admin cấp thấp có thể tự/gián tiếp cấp role cao hơn mức mình được phép nếu policy ngoài endpoint không chặn.  
**Severity:** High  
**Recommended fix:** Enforce grant policy, ví dụ actor chỉ được assign roles nằm trong phạm vi cho phép.

### 6. Không có audit detail trước/sau và actor identity

**Problem:** Code không ghi change audit trong cùng business operation.  
**Why it happens:** Audit được xem là concern phụ.  
**Production impact:** Khó điều tra ai thêm/xoá permission nào và conflict xảy ra lúc nào.  
**Severity:** Medium  
**Recommended fix:** Audit structured gồm actor, target user, tenant, old/new role, permission diff, resource version, operation id và timestamp; không log secret/token.

### 7. Duplicate permission input có thể gây lỗi hoặc dữ liệu dư thừa

**Problem:** Không normalize/deduplicate `request.Permissions`.  
**Why it happens:** Client input được tin cậy.  
**Production impact:** Có thể vi phạm unique constraint hoặc tạo duplicate nếu database không enforce invariant.  
**Severity:** Medium  
**Recommended fix:** Normalize + distinct và có unique constraint `(UserId, Permission)`.

### 8. Không giới hạn/validate request size

**Problem:** Caller có thể gửi danh sách permission bất thường lớn.  
**Why it happens:** Không có boundary ở request validation.  
**Production impact:** Tăng write amplification và có thể trở thành abuse vector.  
**Severity:** Low  
**Recommended fix:** Giới hạn permission count theo domain rule và reject input bất hợp lý.

## Phiên bản code đề xuất

Ví dụ giả định `User.AccessVersion` là concurrency token tăng sau mỗi thay đổi access và client gửi `ExpectedVersion` từ lần đọc gần nhất.

```csharp
public sealed record UpdateAccessRequest(
    string Role,
    IReadOnlyCollection<string> Permissions,
    long ExpectedVersion);

public sealed class UserAccessService
{
    private readonly AppDbContext _db;
    private readonly ICurrentAdmin _currentAdmin;
    private readonly IAccessGrantPolicy _grantPolicy;

    public UserAccessService(
        AppDbContext db,
        ICurrentAdmin currentAdmin,
        IAccessGrantPolicy grantPolicy)
    {
        _db = db;
        _currentAdmin = currentAdmin;
        _grantPolicy = grantPolicy;
    }

    public async Task UpdateAsync(
        Guid userId,
        UpdateAccessRequest request,
        CancellationToken cancellationToken)
    {
        var tenantId = _currentAdmin.TenantId;

        var user = await _db.Users
            .Include(x => x.UserPermissions)
            .SingleOrDefaultAsync(
                x => x.Id == userId && x.TenantId == tenantId,
                cancellationToken)
            ?? throw new KeyNotFoundException("User not found.");

        if (user.AccessVersion != request.ExpectedVersion)
            throw new AccessVersionConflictException(user.AccessVersion);

        var desired = request.Permissions
            .Select(x => x.Trim())
            .Where(x => x.Length > 0)
            .Distinct(StringComparer.OrdinalIgnoreCase)
            .ToHashSet(StringComparer.OrdinalIgnoreCase);

        await _grantPolicy.EnsureCanGrantAsync(
            _currentAdmin.UserId,
            request.Role,
            desired,
            cancellationToken);

        var current = user.UserPermissions
            .ToDictionary(x => x.Permission, StringComparer.OrdinalIgnoreCase);

        foreach (var existing in current.Values)
        {
            if (!desired.Contains(existing.Permission))
                _db.UserPermissions.Remove(existing);
        }

        foreach (var permission in desired)
        {
            if (!current.ContainsKey(permission))
            {
                user.UserPermissions.Add(new UserPermission
                {
                    UserId = user.Id,
                    Permission = permission
                });
            }
        }

        user.Role = request.Role;
        user.AccessVersion++;

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException)
        {
            throw new AccessVersionConflictException();
        }
    }
}
```

Trong implementation thực tế, concurrency token có thể được model theo khả năng của database/provider và contract API. Quan trọng là version client đọc phải tham gia điều kiện update để stale write không silent overwrite dữ liệu mới hơn.

## Trade-offs

- Optimistic concurrency phù hợp khi conflict không thường xuyên; nếu cùng resource bị sửa liên tục, UX merge hoặc workflow locking có thể cần thiết.
- Replace-all đơn giản hơn nhưng write amplification và audit detail kém; diff update phức tạp hơn nhưng kiểm soát tốt hơn.
- Trả `409` giúp client hiểu conflict nhưng cần UI hỗ trợ reload/merge.
- Resource-based authorization tăng code/policy complexity nhưng không nên phụ thuộc vào UI để bảo vệ tenant boundary.

## Cách kiểm thử

1. **Concurrency integration test:** hai client đọc version 10, A save thành version 11, B save với version 10 phải nhận conflict.
2. **Security test:** admin tenant A gửi `userId` thuộc tenant B, xác nhận không update được resource.
3. **Privilege test:** admin cố assign role/permission vượt grant scope, xác nhận bị reject.
4. **Database test:** duplicate permission input không tạo duplicate record và unique constraint giữ invariant.
5. **Audit test:** successful update ghi đúng actor, target, old/new role, permission diff và version.

## Quan sát trong production

Nên theo dõi:

- `user_access_update_total`
- `user_access_conflict_total`
- `user_access_forbidden_total`
- latency của access update
- số permission add/remove mỗi operation
- audit event có actor/tenant/target/operation id/version
- alert khi forbidden cross-tenant attempts tăng bất thường
- trace từ API request tới database update/audit operation

1. Nếu UI cần merge hai thay đổi permission độc lập thay vì bắt reload toàn bộ, bạn thiết kế API thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Fire-and-forget trong request không tạo durability; background work quan trọng cần lifecycle, retry và persistence riêng.
- Scoped dependency như `DbContext` không nên bị capture để chạy vượt quá scope đã tạo nó.
- Retry phải được thiết kế cùng idempotency và backpressure, đặc biệt với side effect bên ngoài.
- Authorization phải enforce theo resource/tenant chứ không chỉ theo quyền gọi endpoint.
- Optimistic concurrency biến silent lost update thành conflict có thể phát hiện và xử lý rõ ràng.

## Mẫu tư duy cần nhớ

1. **Request success không đồng nghĩa background work đã durable.**
2. **Resource lifetime phải khớp execution lifetime.**
3. **Design retries together with idempotency and backpressure.**
4. **Authorize the resource, not only the endpoint.**
5. **Detect stale writes instead of accepting last-write-wins silently.**
