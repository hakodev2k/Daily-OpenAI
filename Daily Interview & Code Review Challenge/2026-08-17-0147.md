# Code Review Challenge 1 — Cancellation giả, `HttpClient` lifetime và background side effect bị bỏ rơi

**Chủ đề:** async/await, cancellation, HTTP client usage, resource lifetime, error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API có endpoint đồng bộ hồ sơ nhân viên sang một internal HR service. Endpoint chạy trong request path bình thường.

Traffic trung bình khoảng 50–100 request/giây, nhưng vào giờ cao điểm có thể burst cao hơn. External HR service đôi lúc chậm 5–15 giây hoặc trả lỗi 5xx. Team muốn endpoint phản hồi nhanh nên đã “đẩy phần đồng bộ ra background” bằng `Task.Run`.

Production gần đây có các triệu chứng:

- đôi lúc user nhận `200 OK` nhưng dữ liệu chưa bao giờ được sync;
- log có `ObjectDisposedException` và `TaskCanceledException` rải rác;
- số outbound TCP connections tăng mạnh khi tải cao;
- khi client hủy request, background work vẫn tiếp tục chạy;
- có những lỗi outbound không xuất hiện trong application logs;
- một số request sync trùng khi frontend retry.

Đoạn code hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeeSyncController : ControllerBase
{
    private readonly EmployeeDbContext _dbContext;
    private readonly ILogger<EmployeeSyncController> _logger;

    public EmployeeSyncController(
        EmployeeDbContext dbContext,
        ILogger<EmployeeSyncController> logger)
    {
        _dbContext = dbContext;
        _logger = logger;
    }

    [HttpPost("{employeeId:int}/sync")]
    public async Task<IActionResult> Sync(
        int employeeId,
        CancellationToken cancellationToken)
    {
        var employee = await _dbContext.Employees
            .FirstOrDefaultAsync(x => x.Id == employeeId, cancellationToken);

        if (employee is null)
            return NotFound();

        Task.Run(async () =>
        {
            try
            {
                using var client = new HttpClient
                {
                    Timeout = TimeSpan.FromSeconds(30)
                };

                var payload = JsonSerializer.Serialize(new
                {
                    employee.Id,
                    employee.Email,
                    employee.DisplayName,
                    employee.Department
                });

                using var content = new StringContent(
                    payload,
                    Encoding.UTF8,
                    "application/json");

                using var response = await client.PostAsync(
                    "https://hr-internal/api/users/sync",
                    content,
                    cancellationToken);

                response.EnsureSuccessStatusCode();

                employee.LastSyncedAt = DateTime.UtcNow;
                await _dbContext.SaveChangesAsync(cancellationToken);
            }
            catch (Exception ex)
            {
                _logger.LogWarning(ex, "Employee sync failed for {EmployeeId}", employeeId);
            }
        });

        return Ok(new { employeeId, status = "queued" });
    }
}
```

## Kết quả code review tham khảo

### 1. Background task dùng scoped `DbContext` sau khi request scope kết thúc

- **Problem:** `Task.Run` capture `_dbContext` và `employee`, trong khi controller cùng `DbContext` thuộc request scope.
- **Why it happens:** API trả `Ok` ngay; request kết thúc có thể làm DI scope bị dispose trước khi background lambda hoàn tất.
- **Production impact:** `ObjectDisposedException`, mất update `LastSyncedAt`, behavior không ổn định tùy timing.
- **Severity:** **Critical**
- **Recommended fix:** không chạy detached background work bằng dependency scoped của request. Dùng Hangfire, queue + `BackgroundService`, Azure Queue/Service Bus hoặc một application-level work queue; worker tạo DI scope riêng cho từng operation.

### 2. Fire-and-forget task không có owner và không được await

- **Problem:** `Task.Run(...)` bị bỏ rơi; endpoint không giữ reference hay await task.
- **Why it happens:** code cố “trả response nhanh” nhưng không có durable job abstraction.
- **Production impact:** process restart/deployment có thể làm mất work; không có retry đáng tin cậy; khó biết work đang pending hay thất bại.
- **Severity:** **Critical**
- **Recommended fix:** enqueue durable background job hoặc persist operation state trước khi trả response.

### 3. Request `CancellationToken` bị truyền vào detached background operation

- **Problem:** background task dùng token gắn với request.
- **Why it happens:** token hợp lệ trong request path nhưng không còn phù hợp cho operation tiếp tục độc lập sau response.
- **Production impact:** client disconnect có thể cancel sync ở điểm bất kỳ; trạng thái business có thể dang dở. Ngược lại, nếu token chưa cancel thì detached task vẫn tiếp tục mà không có lifecycle control tốt.
- **Severity:** **High**
- **Recommended fix:** khi enqueue, request token chỉ dùng cho thao tác enqueue/persist ban đầu. Worker dùng cancellation token của worker/job host, kết hợp timeout riêng cho external dependency.

### 4. Tạo `HttpClient` mới cho mỗi operation

- **Problem:** `new HttpClient()` per sync.
- **Why it happens:** hiểu nhầm `IDisposable` nghĩa là nên tạo/dispose per call.
- **Production impact:** giảm connection reuse, tăng TCP/TLS churn và có thể gây outbound socket/port pressure dưới tải.
- **Severity:** **High**
- **Recommended fix:** dùng `IHttpClientFactory`/typed client hoặc một long-lived client phù hợp với host lifetime và configuration.

### 5. Không có idempotency cho sync operation

- **Problem:** hai HTTP requests cho cùng `employeeId` có thể tạo hai outbound POST độc lập.
- **Why it happens:** API chỉ nhận `employeeId`, không có business operation identity hoặc unique constraint.
- **Production impact:** duplicate side effects, especially nếu downstream POST không naturally idempotent.
- **Severity:** **High**
- **Recommended fix:** tạo `SyncOperationId` hoặc idempotency key ổn định; persist operation với unique constraint và để worker kiểm tra trạng thái trước khi execute/retry.

### 6. Catch toàn bộ exception rồi chỉ log Warning

- **Problem:** mọi exception đều bị swallow.
- **Why it happens:** fire-and-forget code cố tránh unobserved exception.
- **Production impact:** không retry transient errors, không phân biệt permanent/transient failure, monitoring khó phát hiện tỷ lệ thất bại thực.
- **Severity:** **High**
- **Recommended fix:** background job framework nên quản lý retry; chỉ catch khi có chiến lược cụ thể. Log structured failure, attempt number, dependency status và operation ID.

### 7. API trả `200 OK` với trạng thái `queued` dù chưa có durable queue

- **Problem:** contract nói operation đã được queue nhưng thực tế chỉ start một in-process task không durable.
- **Why it happens:** response semantics không phản ánh guarantee thật.
- **Production impact:** client tin rằng work chắc chắn được xử lý dù process có thể chết ngay sau response.
- **Severity:** **High**
- **Recommended fix:** chỉ trả `202 Accepted` sau khi operation đã được persist/enqueue thành công; trả operation ID để query status.

### 8. Entity được capture và mutate ngoài request flow

- **Problem:** tracked `employee` được sử dụng lâu sau thời điểm query.
- **Why it happens:** lambda capture reference tới entity tracked bởi request `DbContext`.
- **Production impact:** stale state, disposed context, concurrency conflict khó kiểm soát.
- **Severity:** **Medium**
- **Recommended fix:** worker chỉ nhận primitive operation data/ID, sau đó query lại entity trong scope mới.

### 9. Timeout semantics chưa rõ và `TaskCanceledException` dễ bị hiểu sai

- **Problem:** một `TaskCanceledException` có thể đến từ caller cancellation hoặc HTTP timeout; code không phân loại.
- **Why it happens:** request token và `HttpClient.Timeout` cùng tham gia cancellation.
- **Production impact:** telemetry sai, retry decision sai.
- **Severity:** **Medium**
- **Recommended fix:** tách request enqueue cancellation, worker cancellation và dependency timeout; log cancellation reason/context rõ ràng.

### 10. Observability thiếu correlation và dependency telemetry

- **Problem:** log chỉ có `employeeId`.
- **Why it happens:** không có operation abstraction.
- **Production impact:** khó correlate retry, duplicate, worker instance và downstream request.
- **Severity:** **Medium**
- **Recommended fix:** dùng `OperationId`, trace/span, dependency duration, HTTP status, retry attempt, queue latency và final outcome.

## Phiên bản code đề xuất

Một hướng dùng durable job abstraction. Controller chỉ tạo operation và enqueue; worker chịu trách nhiệm xử lý.

```csharp
public sealed record EmployeeSyncRequest(int EmployeeId, Guid OperationId);

[ApiController]
[Route("api/employees")]
public sealed class EmployeeSyncController : ControllerBase
{
    private readonly EmployeeDbContext _dbContext;
    private readonly IBackgroundJobClient _jobs;

    public EmployeeSyncController(
        EmployeeDbContext dbContext,
        IBackgroundJobClient jobs)
    {
        _dbContext = dbContext;
        _jobs = jobs;
    }

    [HttpPost("{employeeId:int}/sync")]
    public async Task<IActionResult> Sync(
        int employeeId,
        CancellationToken cancellationToken)
    {
        var exists = await _dbContext.Employees
            .AsNoTracking()
            .AnyAsync(x => x.Id == employeeId, cancellationToken);

        if (!exists)
            return NotFound();

        var operation = new EmployeeSyncOperation
        {
            Id = Guid.NewGuid(),
            EmployeeId = employeeId,
            Status = "Pending",
            CreatedAt = DateTime.UtcNow
        };

        _dbContext.EmployeeSyncOperations.Add(operation);
        await _dbContext.SaveChangesAsync(cancellationToken);

        _jobs.Enqueue<EmployeeSyncJob>(
            job => job.ExecuteAsync(operation.Id, CancellationToken.None));

        return Accepted(new
        {
            operationId = operation.Id,
            status = operation.Status
        });
    }
}

public sealed class EmployeeSyncJob
{
    private readonly EmployeeDbContext _dbContext;
    private readonly HrClient _hrClient;
    private readonly ILogger<EmployeeSyncJob> _logger;

    public EmployeeSyncJob(
        EmployeeDbContext dbContext,
        HrClient hrClient,
        ILogger<EmployeeSyncJob> logger)
    {
        _dbContext = dbContext;
        _hrClient = hrClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(
        Guid operationId,
        CancellationToken cancellationToken)
    {
        var operation = await _dbContext.EmployeeSyncOperations
            .SingleAsync(x => x.Id == operationId, cancellationToken);

        if (operation.Status == "Completed")
            return;

        var employee = await _dbContext.Employees
            .AsNoTracking()
            .SingleAsync(x => x.Id == operation.EmployeeId, cancellationToken);

        await _hrClient.SyncAsync(
            new HrSyncRequest(
                employee.Id,
                employee.Email,
                employee.DisplayName,
                employee.Department,
                operation.Id),
            cancellationToken);

        operation.Status = "Completed";
        operation.CompletedAt = DateTime.UtcNow;
        await _dbContext.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Employee sync completed. OperationId={OperationId} EmployeeId={EmployeeId}",
            operation.Id,
            employee.Id);
    }
}

public sealed class HrClient
{
    private readonly HttpClient _httpClient;

    public HrClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task SyncAsync(
        HrSyncRequest request,
        CancellationToken cancellationToken)
    {
        using var response = await _httpClient.PostAsJsonAsync(
            "api/users/sync",
            request,
            cancellationToken);

        response.EnsureSuccessStatusCode();
    }
}
```

### Lưu ý về idempotency

Bản code trên vẫn cần business rule rõ ràng cho retry. Một implementation mạnh hơn nên có:

- `OperationId` hoặc idempotency key được downstream chấp nhận nếu API hỗ trợ;
- unique constraint nếu business không cho phép nhiều operation tương đương cùng thời điểm;
- state transition hợp lệ `Pending → Processing → Completed/Failed`;
- retry chỉ cho transient failure;
- xử lý case “timeout nhưng downstream đã xử lý thành công”.

## Trade-offs

- **Hangfire/durable queue** tăng hạ tầng và operational complexity nhưng cho retry, persistence, visibility và worker lifecycle rõ ràng.
- **In-process bounded queue + BackgroundService** đơn giản hơn nhưng có thể mất queued work khi process restart nếu không persist.
- **Await trực tiếp trong request** cho consistency đơn giản nhất nhưng user phải chờ downstream và dễ kéo latency của API lên cao.
- **Idempotency storage** thêm schema/state management nhưng cần thiết nếu operation có thể retry hoặc duplicate enqueue.

## Cách kiểm thử

1. **Integration test — request kết thúc trước worker:** API trả `202`, worker vẫn xử lý thành công trong scope riêng.
2. **Failure-path test — downstream timeout:** job fail theo policy, retry đúng số lần, không đánh dấu `Completed` sớm.
3. **Concurrency test — duplicate request:** gửi nhiều request cho cùng employee và xác minh idempotency/unique rule ngăn duplicate business effect.
4. **Restart test:** enqueue operation rồi restart worker process; job vẫn được xử lý nếu queue là durable.
5. **Load test:** hàng trăm concurrent sync; theo dõi connection reuse, queue latency, outbound error rate và memory/thread pool health.

# Code Review Challenge 2 — Tenant isolation bị phá vỡ bởi dynamic SQL và authorization kiểm tra sai chỗ

**Chủ đề:** authentication, authorization, SQL injection, input validation, sensitive-data exposure, multi-tenant security  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép manager tìm kiếm nhân viên trong tenant hiện tại.

JWT chứa các claims:

- `sub`: user id
- `tenant_id`: tenant của user
- `role`: `Manager`, `HR`, hoặc `Employee`

Requirement mong muốn:

- user chỉ được xem dữ liệu thuộc tenant của mình;
- `Manager` chỉ xem employee trong department mình quản lý;
- `HR` có thể xem toàn bộ employee trong tenant;
- API không được trả national ID hoặc personal email cho `Manager`;
- filter search là input do client cung cấp.

Production phát hiện một user thuộc tenant A đã nhìn thấy tên và email của employee tenant B thông qua endpoint search.

Đoạn code hiện tại:

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/employees")]
public sealed class EmployeeSearchController : ControllerBase
{
    private readonly SqlConnection _connection;
    private readonly ILogger<EmployeeSearchController> _logger;

    public EmployeeSearchController(
        SqlConnection connection,
        ILogger<EmployeeSearchController> logger)
    {
        _connection = connection;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        [FromQuery] string? q,
        [FromQuery] string? department,
        [FromQuery] int page = 1)
    {
        var tenantId = User.FindFirst("tenant_id")?.Value;
        var role = User.FindFirst("role")?.Value;

        var sql = $@"
            SELECT Id,
                   TenantId,
                   EmployeeCode,
                   DisplayName,
                   WorkEmail,
                   PersonalEmail,
                   NationalId,
                   Department
            FROM Employees
            WHERE IsDeleted = 0
              AND (DisplayName LIKE '%{q}%'
                   OR WorkEmail LIKE '%{q}%')";

        if (!string.IsNullOrWhiteSpace(department))
            sql += $" AND Department = '{department}'";

        if (role != "HR")
            sql += $" AND TenantId = '{tenantId}'";

        sql += $" ORDER BY DisplayName OFFSET {(page - 1) * 50} ROWS FETCH NEXT 50 ROWS ONLY";

        _logger.LogInformation(
            "Employee search by {User}. Sql={Sql}",
            User.Identity?.Name,
            sql);

        await _connection.OpenAsync();

        using var command = new SqlCommand(sql, _connection);
        using var reader = await command.ExecuteReaderAsync();

        var results = new List<object>();

        while (await reader.ReadAsync())
        {
            results.Add(new
            {
                Id = reader.GetInt32(0),
                TenantId = reader.GetString(1),
                EmployeeCode = reader.GetString(2),
                DisplayName = reader.GetString(3),
                WorkEmail = reader.GetString(4),
                PersonalEmail = reader.IsDBNull(5) ? null : reader.GetString(5),
                NationalId = reader.IsDBNull(6) ? null : reader.GetString(6),
                Department = reader.GetString(7)
            });
        }

        return Ok(results);
    }
}
```

## Kết quả code review tham khảo

### 1. HR role bỏ hoàn toàn tenant filter

- **Problem:** `if (role != "HR")` mới thêm `TenantId` condition.
- **Why it happens:** code diễn giải “HR xem tất cả employee” thành “HR xem tất cả tenants”.
- **Production impact:** HR của tenant A có thể đọc dữ liệu tenant B — tenant isolation breach.
- **Severity:** **Critical**
- **Recommended fix:** tenant filter phải luôn được áp dụng cho mọi role tenant-scoped. Role chỉ kiểm soát phạm vi bên trong tenant.

### 2. SQL injection qua `q`

- **Problem:** input `q` được interpolate trực tiếp vào SQL.
- **Why it happens:** dynamic SQL string concatenation.
- **Production impact:** attacker có thể thay đổi predicate/query semantics, đọc dữ liệu ngoài scope hoặc gây lỗi/DoS tùy database permissions.
- **Severity:** **Critical**
- **Recommended fix:** parameterized SQL hoặc ORM query translation; tuyệt đối không ghép raw user input vào SQL.

### 3. SQL injection qua `department`

- **Problem:** `department` cũng được concatenate trực tiếp.
- **Why it happens:** tương tự `q`.
- **Production impact:** bypass filter, data exfiltration, query manipulation.
- **Severity:** **Critical**
- **Recommended fix:** parameter `@Department`.

### 4. Manager authorization rule chưa hề được enforce

- **Problem:** requirement nói Manager chỉ xem department mình quản lý, nhưng code không kiểm tra department assignment của manager.
- **Why it happens:** chỉ dựa vào role claim mà thiếu resource/data-scope authorization.
- **Production impact:** Manager có thể search mọi department trong tenant và xem dữ liệu ngoài phạm vi công việc.
- **Severity:** **High**
- **Recommended fix:** resolve allowed departments từ authoritative source hoặc claims đã được thiết kế an toàn; query phải giới hạn theo allowed scope.

### 5. Sensitive columns được select và trả cho mọi role

- **Problem:** `PersonalEmail` và `NationalId` luôn được query và serialize.
- **Why it happens:** response model không tách theo role/policy.
- **Production impact:** vi phạm least privilege và privacy; manager đọc dữ liệu nhạy cảm không cần thiết.
- **Severity:** **High**
- **Recommended fix:** projection chỉ lấy columns role được phép xem. Không select sensitive data nếu caller không cần/không được phép.

### 6. Không validate tenant claim

- **Problem:** `tenantId` có thể null/invalid nhưng query logic vẫn tiếp tục.
- **Why it happens:** claim được assume luôn hợp lệ sau `[Authorize]`.
- **Production impact:** behavior khó đoán; có thể tạo query sai scope hoặc lỗi runtime.
- **Severity:** **High**
- **Recommended fix:** validate required claims upfront; nếu thiếu/invalid thì reject request.

### 7. Log toàn bộ SQL chứa user input và có thể chứa PII

- **Problem:** full SQL string được log.
- **Why it happens:** tiện debugging.
- **Production impact:** search keywords/email/department có thể xuất hiện trong logs; injection payload cũng được lưu; log platform trở thành nơi chứa sensitive data ngoài ý muốn.
- **Severity:** **Medium**
- **Recommended fix:** log structured metadata như tenant ID đã redacted/hashed nếu cần, role, result count, duration, query category; không log raw SQL/user PII ở information level.

### 8. `page` không được validate

- **Problem:** `page <= 0` tạo negative OFFSET expression.
- **Why it happens:** thiếu input validation.
- **Production impact:** SQL error, noisy logs, dễ bị abuse gây failure path.
- **Severity:** **Medium**
- **Recommended fix:** validate `page >= 1`, đặt max page size và cân nhắc cursor/keyset pagination ở dataset lớn.

### 9. Connection lifetime phụ thuộc cách DI đăng ký và không truyền cancellation token

- **Problem:** connection được inject trực tiếp, mở thủ công và không truyền request cancellation vào `OpenAsync`/`ExecuteReaderAsync`/`ReadAsync`.
- **Why it happens:** resource lifecycle không rõ và code bỏ qua cancellation.
- **Production impact:** resource usage kém tối ưu khi client disconnect; nếu service lifetime đăng ký sai có thể phát sinh concurrency/lifetime issues.
- **Severity:** **Medium**
- **Recommended fix:** dùng connection factory hoặc tạo connection theo operation; truyền cancellation token; dựa vào pooling của provider thay vì giữ shared live connection.

## Phiên bản code đề xuất

Ví dụ dưới đây giữ raw ADO.NET nhưng enforce tenant scope và parameterization. Trong production có thể dùng EF Core nếu phù hợp với codebase.

```csharp
public sealed record EmployeeSearchItem(
    int Id,
    string EmployeeCode,
    string DisplayName,
    string WorkEmail,
    string Department,
    string? PersonalEmail,
    string? NationalId);

[Authorize]
[ApiController]
[Route("api/employees")]
public sealed class EmployeeSearchController : ControllerBase
{
    private readonly string _connectionString;
    private readonly IManagerScopeService _managerScope;
    private readonly ILogger<EmployeeSearchController> _logger;

    public EmployeeSearchController(
        IConfiguration configuration,
        IManagerScopeService managerScope,
        ILogger<EmployeeSearchController> logger)
    {
        _connectionString = configuration.GetConnectionString("Default")!;
        _managerScope = managerScope;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        [FromQuery] string? q,
        [FromQuery] string? department,
        [FromQuery] int page = 1,
        CancellationToken cancellationToken = default)
    {
        if (page < 1)
            return BadRequest("page must be >= 1");

        var tenantId = User.FindFirst("tenant_id")?.Value;
        var role = User.FindFirst("role")?.Value;
        var userId = User.FindFirst("sub")?.Value;

        if (string.IsNullOrWhiteSpace(tenantId) ||
            string.IsNullOrWhiteSpace(role) ||
            string.IsNullOrWhiteSpace(userId))
        {
            return Forbid();
        }

        IReadOnlyCollection<string>? allowedDepartments = null;

        if (role == "Manager")
        {
            allowedDepartments = await _managerScope.GetDepartmentsAsync(
                tenantId,
                userId,
                cancellationToken);

            if (allowedDepartments.Count == 0)
                return Ok(Array.Empty<EmployeeSearchItem>());
        }
        else if (role != "HR")
        {
            return Forbid();
        }

        var includeSensitive = role == "HR";

        var sql = new StringBuilder();
        sql.AppendLine("SELECT Id, EmployeeCode, DisplayName, WorkEmail, Department");

        if (includeSensitive)
            sql.AppendLine(", PersonalEmail, NationalId");

        sql.AppendLine("FROM Employees");
        sql.AppendLine("WHERE IsDeleted = 0");
        sql.AppendLine("  AND TenantId = @TenantId");
        sql.AppendLine("  AND (@Q IS NULL OR DisplayName LIKE @Search OR WorkEmail LIKE @Search)");
        sql.AppendLine("  AND (@Department IS NULL OR Department = @Department)");

        if (role == "Manager")
        {
            var departmentParams = allowedDepartments!
                .Select((_, i) => $"@AllowedDepartment{i}")
                .ToArray();

            sql.AppendLine($"  AND Department IN ({string.Join(",", departmentParams)})");
        }

        sql.AppendLine("ORDER BY DisplayName, Id");
        sql.AppendLine("OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY;");

        await using var connection = new SqlConnection(_connectionString);
        await connection.OpenAsync(cancellationToken);

        await using var command = new SqlCommand(sql.ToString(), connection);
        command.Parameters.AddWithValue("@TenantId", tenantId);
        command.Parameters.AddWithValue("@Q", (object?)q ?? DBNull.Value);
        command.Parameters.AddWithValue(
            "@Search",
            string.IsNullOrWhiteSpace(q) ? DBNull.Value : $"%{q}%");
        command.Parameters.AddWithValue(
            "@Department",
            string.IsNullOrWhiteSpace(department) ? DBNull.Value : department);
        command.Parameters.AddWithValue("@Offset", (page - 1) * 50);
        command.Parameters.AddWithValue("@PageSize", 50);

        if (role == "Manager")
        {
            var i = 0;
            foreach (var allowed in allowedDepartments!)
            {
                command.Parameters.AddWithValue($"@AllowedDepartment{i}", allowed);
                i++;
            }
        }

        var results = new List<EmployeeSearchItem>();

        await using var reader = await command.ExecuteReaderAsync(cancellationToken);

        while (await reader.ReadAsync(cancellationToken))
        {
            var personalEmailOrdinal = includeSensitive ? 5 : -1;
            var nationalIdOrdinal = includeSensitive ? 6 : -1;

            results.Add(new EmployeeSearchItem(
                reader.GetInt32(0),
                reader.GetString(1),
                reader.GetString(2),
                reader.GetString(3),
                reader.GetString(4),
                includeSensitive && !reader.IsDBNull(personalEmailOrdinal)
                    ? reader.GetString(personalEmailOrdinal)
                    : null,
                includeSensitive && !reader.IsDBNull(nationalIdOrdinal)
                    ? reader.GetString(nationalIdOrdinal)
                    : null));
        }

        _logger.LogInformation(
            "Employee search completed. Tenant={TenantId} Role={Role} Page={Page} Count={Count}",
            tenantId,
            role,
            page,
            results.Count);

        return Ok(results);
    }
}
```

### Những điểm cần cải thiện thêm trong production

- Tránh `AddWithValue` nếu schema type/length quan trọng; define `SqlParameter` explicit để tránh implicit conversion hoặc plan issues.
- Nếu allowed departments nhiều, cân nhắc table-valued parameter, temp table hoặc query từ authorization table thay vì tạo `IN` quá dài.
- Có thể tách response DTO cho HR và Manager để tránh accidental sensitive-field exposure.
- Có thể enforce tenant scope ở nhiều lớp, ví dụ repository/query abstraction, database security policy hoặc EF Core global query filter — nhưng không nên dựa duy nhất vào một lớp nếu risk cao.

## Trade-offs

- **ADO.NET parameterized SQL** cho control trực tiếp nhưng verbose và dễ bỏ sót policy nếu code review không chặt.
- **EF Core** giúp parameterization và composition tự nhiên hơn nhưng vẫn không tự giải quyết authorization; developer vẫn phải enforce tenant/data scope.
- **Global query filters** giảm nguy cơ quên tenant predicate nhưng có edge cases và cần kiểm soát việc bypass filter.
- **Database row-level security** tạo defense-in-depth mạnh hơn nhưng tăng database-specific complexity và operational overhead.
- **Role-specific DTO** rõ ràng về security nhưng tăng số model/mapping paths.

## Cách kiểm thử

1. **Tenant isolation test:** user tenant A không thể đọc bất kỳ row tenant B nào, kể cả khi role là `HR`.
2. **SQL injection test:** `q` và `department` chứa payload như `' OR 1=1 --` vẫn được xử lý như literal input, không thay đổi query semantics.
3. **Manager scope test:** Manager chỉ nhìn thấy departments được assign; tự truyền `department` khác không mở rộng quyền.
4. **Sensitive-data test:** Manager response không chứa `PersonalEmail`/`NationalId`; HR trong cùng tenant mới nhận các field được policy cho phép.
5. **Claim validation test:** thiếu `tenant_id`, `sub`, role không hợp lệ hoặc forged scope phải bị deny.

Nên log:

- role;
- authorization decision;
- result count;

- authorization denials theo endpoint;

Trace nên phân biệt:

`authentication → tenant scope resolution → manager scope resolution → SQL execution → serialization`.

- một identity query nhiều tenant IDs bất thường;

- query result count lớn bất thường;

## Câu hỏi phỏng vấn mở rộng

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Background work không nên mượn lifetime của HTTP request hoặc scoped dependencies rồi tiếp tục chạy sau khi response kết thúc.
- `Task.Run` không biến một operation thành durable background job; ownership, retry, persistence và observability vẫn phải được thiết kế rõ ràng.
- Cancellation token phải phản ánh đúng lifecycle của operation; request cancellation và worker cancellation là hai phạm vi khác nhau.
- `HttpClient` nên được quản lý để reuse connection hợp lý thay vì tạo/dispose per operation dưới tải cao.
- Multi-tenant authorization phải coi tenant scope là invariant bắt buộc, không phải một condition tùy role.
- Authentication không thay thế authorization; role không đủ để mô tả row-level/column-level permission.
- Parameterization chống SQL injection nhưng không tự giải quyết data-scope authorization.
- Sensitive fields tốt nhất không được query nếu caller không có quyền xem.

## Mẫu tư duy cần nhớ

1. **Clarify lifetime before using async/background work** — request, scope, worker và dependency có lifecycle khác nhau.
2. **Design retries together with idempotency** — retry an toàn chỉ khi duplicate side effects đã được xử lý.
3. **Treat tenant scope as an invariant** — mọi data path phải giữ boundary tenant trừ khi có policy cross-tenant được kiểm soát rõ ràng.
4. **Authorize rows and columns, not just endpoints** — user được vào endpoint chưa có nghĩa được đọc mọi dữ liệu endpoint có thể truy cập.
5. **Observability must not leak secrets** — telemetry phải đủ để điều tra nhưng không trở thành nguồn rò rỉ PII/token.
