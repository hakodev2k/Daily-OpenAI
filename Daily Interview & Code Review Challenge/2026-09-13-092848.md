# Code Review Challenge 1 — App Service đọc Key Vault trong mỗi request, thỉnh thoảng tăng latency và vô tình log secret

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure App Service, Azure Key Vault, Managed Identity, `DefaultAzureCredential`, dependency injection lifetime, configuration, `HttpClient`, secret exposure, dependency failure, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API chạy trên Azure App Service. API gọi một third-party payment-status service. Credential của dịch vụ này được lưu trong Azure Key Vault.

Team muốn bỏ secret khỏi `appsettings.Production.json` nên đã sửa code để mỗi request tự lấy secret từ Key Vault. App Service đã bật Managed Identity và được cấp quyền đọc đúng secret.

Sau release, production có các triệu chứng:

- p95/p99 của endpoint tăng rõ rệt dù third-party API không chậm hơn;
- khi Key Vault có transient latency hoặc network issue, endpoint lỗi hàng loạt;
- Application Insights xuất hiện nhiều dependency calls tới Key Vault trên mỗi phút;
- đôi lúc log chứa nguyên API key khi request tới third-party thất bại;
- một developer đề xuất cache secret trong static field vô thời hạn;
- một developer khác đề xuất giữ fallback secret trong environment variable để “nếu Key Vault down thì vẫn chạy”.

Business yêu cầu:

- không lưu plaintext secret trong source code hoặc log;
- có thể rotate secret mà không cần build lại application;
- third-party failure không được làm leak credential;
- nếu Key Vault tạm lỗi, hệ thống cần degrade theo cách có kiểm soát thay vì tạo retry storm;
- solution không nên thêm infrastructure mới nếu App Service + Managed Identity + Key Vault đã đủ.

## Đoạn code cần review

```csharp
public sealed class PaymentStatusService
{
    private readonly ILogger<PaymentStatusService> _logger;
    private readonly IConfiguration _configuration;

    public PaymentStatusService(
        ILogger<PaymentStatusService> logger,
        IConfiguration configuration)
    {
        _logger = logger;
        _configuration = configuration;
    }

    public async Task<PaymentStatusDto?> GetStatusAsync(
        string paymentId,
        CancellationToken cancellationToken)
    {
        var vaultUrl = _configuration["KeyVault:Url"]!;

        var credential = new DefaultAzureCredential();
        var secretClient = new SecretClient(
            new Uri(vaultUrl),
            credential);

        var secret = await secretClient.GetSecretAsync(
            "PaymentProviderApiKey",
            cancellationToken: cancellationToken);

        var apiKey = secret.Value.Value;

        using var httpClient = new HttpClient
        {
            BaseAddress = new Uri("https://payments.example.internal")
        };

        httpClient.DefaultRequestHeaders.Add("X-Api-Key", apiKey);

        try
        {
            var response = await httpClient.GetAsync(
                $"/api/payments/{paymentId}/status",
                cancellationToken);

            if (!response.IsSuccessStatusCode)
            {
                _logger.LogError(
                    "Payment provider failed. PaymentId={PaymentId}, ApiKey={ApiKey}, Status={Status}",
                    paymentId,
                    apiKey,
                    response.StatusCode);

                return null;
            }

            return await response.Content
                .ReadFromJsonAsync<PaymentStatusDto>(
                    cancellationToken: cancellationToken);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Payment request failed with key {ApiKey}",
                apiKey);
            throw;
        }
    }
}
```

## Kết quả code review tham khảo

### Critical — Secret bị ghi trực tiếp vào structured logs

**Vấn đề:** Code log `apiKey` cả khi HTTP trả non-success và khi exception xảy ra.

**Tại sao xảy ra:** Credential bị coi như diagnostic context thông thường.

**Ảnh hưởng production:** Secret có thể xuất hiện trong Application Insights, log aggregation, support export hoặc retention dài hạn. Blast radius lớn hơn rất nhiều so với một request thất bại đơn lẻ.

**Cách sửa:** Tuyệt đối không log giá trị secret. Chỉ log secret name/version nếu thực sự cần và an toàn. Redaction phải là defense-in-depth, không phải lý do để cho secret đi vào logging call ngay từ đầu.

### High — Key Vault call nằm trên mọi request path

**Vấn đề:** Mỗi API request gọi `GetSecretAsync` trước khi gọi payment provider.

**Tại sao xảy ra:** Secret có lifecycle rất chậm nhưng code fetch với tần suất bằng request traffic.

**Ảnh hưởng production:** Tăng latency, dependency calls, failure coupling và có thể tạo burst load lên Key Vault khi traffic tăng. Một transient Key Vault issue làm endpoint user-facing fail dù secret cũ trong process vẫn có thể còn hợp lệ.

**Cách sửa:** Tải secret ở một configuration/service layer có caching và refresh policy rõ ràng. Có thể dùng configuration integration, App Service/Key Vault reference, hoặc một singleton provider cache giá trị trong bounded TTL. Chọn theo rotation SLO và deployment model.

### High — `SecretClient` và credential bị tạo lại mỗi request

**Vấn đề:** `DefaultAzureCredential` và `SecretClient` được new trong method.

**Tại sao xảy ra:** Azure SDK client được dùng như transient request object thay vì long-lived service dependency.

**Ảnh hưởng production:** Tăng allocations, setup/authentication overhead và làm lifecycle khó kiểm soát/test.

**Cách sửa:** Đăng ký credential/client trong DI với lifetime phù hợp và reuse. Trên App Service, Managed Identity là production identity phù hợp; local development có thể dùng developer credential qua `DefaultAzureCredential` mà không cần hard-code environment-specific secret.

### High — `HttpClient` được tạo mới cho mỗi request

**Vấn đề:** Method dùng `using var httpClient = new HttpClient(...)`.

**Tại sao xảy ra:** Connection pooling lifecycle bị gắn với từng business request.

**Ảnh hưởng production:** Có thể tăng connection churn, DNS/lifecycle complexity và resource pressure dưới load.

**Cách sửa:** Dùng `IHttpClientFactory`/typed client hoặc một long-lived `HttpClient` được quản lý đúng. Configure timeout/resilience ở client boundary thay vì rải trong business method.

### High — Exception path biến dependency failure thành request failure không phân loại

**Vấn đề:** Mọi exception được log rồi rethrow, không phân biệt Key Vault unavailable, timeout, cancellation hay third-party failure.

**Tại sao xảy ra:** Failure domains chưa được model rõ.

**Ảnh hưởng production:** Incident khó điều tra; retry ở layer ngoài có thể retry cả non-transient lỗi hoặc khuếch đại transient outage.

**Cách sửa:** Phân loại expected failures. Cancellation phải propagate. Third-party transient failure có thể dùng bounded retry/backoff nếu operation an toàn. Key Vault refresh failure có thể tiếp tục dùng cached secret còn trong freshness policy, nhưng không được âm thầm dùng stale secret vô hạn.

### High — Fallback plaintext secret tạo security regression

**Vấn đề:** Đề xuất giữ một secret copy trong environment variable chỉ để fallback.

**Tại sao xảy ra:** Reliability concern được giải quyết bằng cách nhân bản credential sang một storage/operational path khác.

**Ảnh hưởng production:** Tăng secret sprawl, rotation complexity và nguy cơ lộ qua config dump/deployment tooling.

**Cách sửa:** Không thêm fallback secret chỉ vì Key Vault có thể transient fail. Dùng cached last-known-good value với TTL/grace policy nếu business chấp nhận, hoặc fail closed có kiểm soát. Identity tới Key Vault nên dùng Managed Identity để tránh application credential riêng.

### Medium — Static cache vô thời hạn phá rotation semantics

**Vấn đề:** Cache secret không expiration sẽ giữ giá trị cũ tới khi process restart.

**Tại sao xảy ra:** Tối ưu latency nhưng bỏ qua requirement rotate secret.

**Ảnh hưởng production:** Rotation có thể làm application tiếp tục gửi credential cũ trong thời gian không xác định.

**Cách sửa:** Xác định freshness SLO, ví dụ refresh theo bounded TTL hoặc version-aware refresh. Giá trị TTL phải dựa trên rotation process chứ không phải con số tùy ý.

### Medium — `paymentId` được chèn thẳng vào URL path

**Vấn đề:** `paymentId` chưa được validate/encode rõ ràng.

**Tại sao xảy ra:** Identifier được giả định luôn là safe path segment.

**Ảnh hưởng production:** Có thể tạo malformed URL hoặc behavior ngoài contract nếu input chứa ký tự đặc biệt.

**Cách sửa:** Validate format theo domain invariant và encode path segment khi cần.

### Medium — Non-success response bị collapse thành `null`

**Vấn đề:** `404`, `401`, `429`, `500` đều trở thành `null`.

**Tại sao xảy ra:** Transport outcome bị map thẳng sang absence domain value.

**Ảnh hưởng production:** Caller không phân biệt payment không tồn tại với provider outage/auth failure. Monitoring và retry decision sai.

**Cách sửa:** Map status codes thành domain/result type có semantics rõ. Ví dụ `NotFound`, `TransientFailure`, `UnauthorizedDependency`, `Success`.

### Medium — Không có explicit timeout/resilience budget

**Vấn đề:** Method dựa vào defaults và caller cancellation mà chưa có dependency timeout budget rõ.

**Tại sao xảy ra:** Latency SLO chưa được map xuống outbound call.

**Ảnh hưởng production:** Slow dependency có thể giữ request/resources quá lâu hoặc retry chồng retry ở nhiều layer.

**Cách sửa:** Thiết kế timeout/retry theo end-to-end request budget, tránh retry storm và đảm bảo retry chỉ áp dụng cho operations an toàn.

## Phiên bản đề xuất

Một hướng thiết kế đơn giản là reuse Azure SDK client, dùng một provider có bounded cache cho secret và dùng typed `HttpClient`.

```csharp
public interface IPaymentApiKeyProvider
{
    Task<string> GetAsync(CancellationToken cancellationToken);
}

public sealed class PaymentApiKeyProvider : IPaymentApiKeyProvider
{
    private readonly SecretClient _secretClient;
    private readonly SemaphoreSlim _refreshLock = new(1, 1);

    private string? _cachedValue;
    private DateTimeOffset _refreshAfter = DateTimeOffset.MinValue;

    public PaymentApiKeyProvider(SecretClient secretClient)
        => _secretClient = secretClient;

    public async Task<string> GetAsync(CancellationToken cancellationToken)
    {
        var now = DateTimeOffset.UtcNow;

        if (_cachedValue is not null && now < _refreshAfter)
            return _cachedValue;

        await _refreshLock.WaitAsync(cancellationToken);
        try
        {
            now = DateTimeOffset.UtcNow;
            if (_cachedValue is not null && now < _refreshAfter)
                return _cachedValue;

            var response = await _secretClient.GetSecretAsync(
                "PaymentProviderApiKey",
                cancellationToken: cancellationToken);

            _cachedValue = response.Value.Value;
            _refreshAfter = now.AddMinutes(5);

            return _cachedValue;
        }
        finally
        {
            _refreshLock.Release();
        }
    }
}

public sealed class PaymentProviderClient
{
    private readonly HttpClient _httpClient;
    private readonly IPaymentApiKeyProvider _apiKeyProvider;
    private readonly ILogger<PaymentProviderClient> _logger;

    public PaymentProviderClient(
        HttpClient httpClient,
        IPaymentApiKeyProvider apiKeyProvider,
        ILogger<PaymentProviderClient> logger)
    {
        _httpClient = httpClient;
        _apiKeyProvider = apiKeyProvider;
        _logger = logger;
    }

    public async Task<PaymentStatusResult> GetStatusAsync(
        string paymentId,
        CancellationToken cancellationToken)
    {
        if (!PaymentId.TryParse(paymentId, out var parsedId))
            return PaymentStatusResult.InvalidId();

        var apiKey = await _apiKeyProvider.GetAsync(cancellationToken);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"api/payments/{Uri.EscapeDataString(parsedId.Value)}/status");

        request.Headers.Add("X-Api-Key", apiKey);

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return PaymentStatusResult.NotFound();

        if ((int)response.StatusCode >= 500 ||
            response.StatusCode == HttpStatusCode.TooManyRequests)
        {
            _logger.LogWarning(
                "Payment provider transient failure. PaymentId={PaymentId}, Status={Status}",
                parsedId.Value,
                response.StatusCode);

            return PaymentStatusResult.TransientFailure(response.StatusCode);
        }

        response.EnsureSuccessStatusCode();

        var payload = await response.Content
            .ReadFromJsonAsync<PaymentStatusDto>(
                cancellationToken: cancellationToken);

        return payload is null
            ? PaymentStatusResult.InvalidResponse()
            : PaymentStatusResult.Success(payload);
    }
}
```

Theo tài liệu Microsoft hiện hành, `DefaultAzureCredential` có thể dùng developer identity ở local và Managed Identity khi app chạy trên Azure; điều này cho phép giữ cùng programming model mà không hard-code production credential. Azure Key Vault client cũng được thiết kế để dùng thông qua Azure Identity thay vì nhúng secret của application vào source/config.

Nếu team dùng App Service Key Vault references hoặc Azure App Configuration + Key Vault references, application code có thể đơn giản hơn nữa: secret xuất hiện như configuration value được platform/configuration layer resolve. Tuy nhiên vẫn cần hiểu refresh semantics trước khi dựa vào nó cho rotation SLO.

## Giải thích thiết kế sau khi sửa

Hot request path không còn fetch Key Vault ở mọi request. Secret provider cache last-known-good value trong một bounded window và serialize refresh bằng `SemaphoreSlim` để tránh 500 concurrent cache misses cùng tạo 500 Key Vault calls.

Managed Identity xử lý application identity tới Azure resource; API key vẫn là credential của third-party, nên vẫn cần Key Vault. Hai loại credential này không nên bị nhầm lẫn.

Typed `HttpClient` tách outbound dependency boundary khỏi business service. Điều này giúp cấu hình timeout, telemetry và resilience tập trung hơn.

Cache secret cần policy rõ về refresh failure. Một lựa chọn có thể là: nếu refresh fail nhưng cached value chưa vượt một bounded grace period, tiếp tục dùng giá trị cũ và emit alert; nếu vượt grace period, fail closed. Nếu provider rotation ngay lập tức revoke old key, grace period có thể không phù hợp. Recommendation phụ thuộc contract thật của provider.

## Trade-offs

Caching secret giảm latency và Key Vault pressure nhưng tạo stale window. TTL càng dài thì rotation convergence càng chậm; TTL càng ngắn thì dependency calls càng nhiều.

Dùng `SemaphoreSlim` trong singleton giải quyết refresh stampede trong một process, không đồng bộ nhiều App Service instances. Điều này thường vẫn đủ vì mỗi instance chỉ cần tránh local burst. Nếu rotation yêu cầu đồng bộ tức thời trên toàn fleet, cần cơ chế khác hoặc platform configuration semantics phù hợp.

App Service Key Vault references giảm application code nhưng chuyển một phần control/observability sang platform. Custom provider cho control rõ hơn nhưng nhiều code và failure-path hơn.

Retry third-party request có thể cải thiện transient reliability nhưng có cost latency và load amplification. Chỉ retry operation idempotent/an toàn, bounded count và có backoff/jitter phù hợp.

## Cách kiểm thử

1. **Security test:** gây HTTP failure/exception và xác minh API key không xuất hiện trong logs, traces hoặc exception telemetry.
2. **Concurrency test:** chạy hàng trăm request khi cache secret expired; xác minh số Key Vault refresh calls được bound thay vì bằng số requests.
3. **Failure-path test:** làm Key Vault refresh timeout; xác minh behavior đúng với cached-value/grace policy và không tạo retry storm.
4. **Rotation integration test:** đổi secret, chờ refresh window và xác minh outbound request bắt đầu dùng version mới trong SLO đã định nghĩa.
5. **Load test:** đo p50/p95/p99, Key Vault dependency rate, outbound connection behavior và error rate trước/sau refactor.

## Quan sát trong production

Theo dõi:

- Key Vault dependency call count, duration, failure rate;
- secret refresh success/failure count và age của cached value, nhưng không log secret value;
- third-party request p50/p95/p99;
- HTTP status distribution, timeout count, retry count;
- App Service instance ID để điều tra per-instance cache behavior;
- outbound connection/errors;
- end-to-end request latency;
- cancellation count;
- auth/permission failures tới Key Vault;
- alert khi secret refresh failure kéo dài hoặc cached-value age vượt policy.

Trace nên cho thấy request → payment provider dependency; Key Vault refresh chỉ xuất hiện khi cache cần refresh, không xuất hiện như dependency bắt buộc của mọi request.

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky trên CI vì test dùng chung state và `waitForTimeout`

## Bối cảnh

async function login() {

test.beforeAll(async () => {

test('admin can deactivate user', async () => {

  await page.click('[data-testid="confirm"]');

  await expect(page.locator('[data-testid="status"]'))
    .toHaveText('Inactive');
});

test('employee list shows active users', async () => {
  await page.goto('/employees');
  await page.waitForTimeout(5000);

  await expect(page.getByText(employeeId)).toBeVisible();
});

## Nhiệm vụ của ứng viên

1. Xác định nguyên nhân khiến suite phụ thuộc thứ tự và flaky dưới parallel execution.
2. Review việc tự tạo browser/page trong `beforeAll` thay vì dùng fixtures mặc định.
3. Xác định các vấn đề của shared employee/account test data.
4. Review `waitForTimeout` và đề xuất synchronization dựa trên observable state.
5. Đánh giá việc bật nhiều retries như một cách “fix flaky test”.
6. Đề xuất test-data strategy giữ được parallelism mà vẫn deterministic.
7. Đề xuất cách thu thập trace/artifacts để điều tra CI failures.
8. Nêu cách phân biệt flaky test do test code với regression thật của application.

## Câu hỏi gợi mở

1. Test runner mặc định cung cấp `page` fixture với isolation semantics nào, và code hiện tại đã bỏ lợi ích gì khi dùng một global page?
2. Nếu hai tests cùng mutate `EMP-1001` trong cùng thời điểm, outcome nào là deterministic?
3. `waitForTimeout(5000)` đang chờ điều kiện business nào, hay chỉ chờ thời gian trôi qua?
4. Retry pass ở lần 2 chứng minh application đúng hay chỉ che một race condition?
5. Artifact nào giúp biết request nào xảy ra, locator thấy gì và DOM thay đổi ra sao ở thời điểm fail?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **shared mutable state** giữa tests và giữa workers. Parallelism chỉ làm bug xuất hiện rõ hơn.

### Gợi ý 2

Playwright có browser-context isolation mặc định cho từng test khi dùng fixtures của test runner. Hãy giữ isolation đó và tách test-data identity thay vì ép toàn suite chạy serial.

## Kết quả code review tham khảo

### High — Global `page` làm tests chia sẻ browser context/session

**Vấn đề:** `page` được tạo một lần trong `beforeAll` và dùng cho mọi test trong file.

**Tại sao xảy ra:** Code bypass fixture lifecycle mặc định của Playwright Test.

**Ảnh hưởng production/CI:** Test có thể để lại cookies, local storage, navigation state hoặc UI state cho test sau. Failure của một test ảnh hưởng test khác; parallel semantics trở nên khó reasoning.

**Cách sửa:** Dùng `page` fixture được inject vào từng test. Playwright Test tạo isolated browser context cho mỗi test theo mặc định, giúp state không leak giữa tests.

### High — Shared employee record tạo data race giữa tests

**Vấn đề:** Ba tests cùng dùng `EMP-1001`; một test deactivate record mà test khác lại kỳ vọng record active hoặc edit được.

**Tại sao xảy ra:** Browser isolation không đồng nghĩa backend/database isolation. Shared server-side data vẫn là mutable global state.

**Ảnh hưởng production/CI:** Failure phụ thuộc timing/worker scheduling; rerun thường pass; chạy serial vô tình che data coupling.

**Cách sửa:** Mỗi test tạo unique employee hoặc dùng worker/test-specific namespace. Cleanup phải best-effort và không là correctness dependency duy nhất; tốt hơn là test data có identity độc lập ngay từ đầu.

### High — `waitForTimeout` tạo synchronization theo thời gian thay vì trạng thái

**Vấn đề:** Tests ngủ 1–5 giây rồi giả định UI/backend đã đạt trạng thái mong muốn.

**Tại sao xảy ra:** Fixed sleep không liên hệ với network speed, rendering, queue latency hoặc CI load.

**Ảnh hưởng production/CI:** Chờ quá ngắn gây flaky; chờ quá dài làm suite chậm. Tăng sleep chỉ dịch xác suất failure.

**Cách sửa:** Chờ observable condition: `expect(locator).toHaveText(...)`, `toBeVisible()`, `page.waitForResponse(...)` khi thật sự cần network boundary, hoặc API polling cho eventual state có bounded timeout.

### High — Retries đang che flakiness thay vì xử lý nguyên nhân

**Vấn đề:** `retries: 3` được dùng như mitigation chính.

**Tại sao xảy ra:** Team coi pass sau retry là pass đáng tin tương đương first-attempt pass.

**Ảnh hưởng production/CI:** Pipeline xanh dù test race tồn tại; regression thật có thể bị nhiễu bởi flaky baseline; thời gian CI tăng.

**Cách sửa:** Retries có thể hữu ích để phân loại flaky và thu trace, nhưng flaky rate phải được theo dõi. Fix isolation/data/synchronization trước. Có policy fail/quarantine rõ cho tests flaky kéo dài.

### High — Shared login account có thể gây authorization/session coupling

**Vấn đề:** Tất cả tests dùng cùng `admin@test.local`.

**Tại sao xảy ra:** Test identity không được coi là resource cần isolation.

**Ảnh hưởng production/CI:** Nếu backend giới hạn session, audit state, lockout hoặc profile mutation, workers có thể ảnh hưởng nhau. Một test đổi permission/session có thể phá test khác.

**Cách sửa:** Nếu account thực sự read-only và stateless thì có thể share; nếu tests mutate identity/session-sensitive state, dùng account pool hoặc unique seeded users per worker/test. Decision dựa trên auth behavior thật.

### Medium — Browser/context lifecycle không được dispose

**Vấn đề:** `browser` và `context` được tạo trong `beforeAll` nhưng không đóng.

**Tại sao xảy ra:** Manual lifecycle quản lý không đầy đủ.

**Ảnh hưởng production/CI:** Resource leak trong test process, khó cleanup và có thể ảnh hưởng suite dài.

**Cách sửa:** Ưu tiên built-in fixtures. Nếu manual context là cần thiết cho multi-user scenario, dùng scoped fixture hoặc `try/finally`/`afterEach`/`afterAll` có lifecycle rõ.

### Medium — Locator phụ thuộc generic CSS và text không luôn phản ánh user-observable contract

**Vấn đề:** Một số selectors như `#email`, `button[type="submit"]` có thể brittle khi markup refactor.

**Tại sao xảy ra:** Test coupling vào implementation detail thay vì accessible role/name hoặc stable test contract.

**Ảnh hưởng production/CI:** False failure khi HTML thay đổi nhưng behavior không đổi.

**Cách sửa:** Ưu tiên `getByRole`, `getByLabel`, `getByTestId` khi thích hợp, theo user interaction semantics.

### Medium — Không có trace artifact cho failure investigation

**Vấn đề:** CI chỉ giữ screenshot.

**Tại sao xảy ra:** Debug artifacts chưa được cấu hình.

**Ảnh hưởng production/CI:** Không thấy timeline actions, network/DOM snapshots và locator state quanh failure; developer phải rerun nhiều lần.

**Cách sửa:** Bật trace phù hợp, ví dụ `trace: 'on-first-retry'` hoặc `retain-on-failure` tùy policy. Lưu HTML report, trace và screenshot/video khi cần.

### Medium — Tests chưa tự tạo precondition rõ ràng

**Vấn đề:** `employee list shows active users` giả định `EMP-1001` đang active dù test khác có thể vừa deactivate.

**Tại sao xảy ra:** Test dựa vào implicit suite history.

**Ảnh hưởng production/CI:** Test không thể chạy độc lập; shard/filter/single-test execution cho kết quả khác full suite.

**Cách sửa:** Mỗi test arrange dữ liệu nó cần qua API/fixture/seed endpoint kiểm soát hoặc immutable seed data phù hợp.

### Medium — Secret handling của test login chưa có guardrails rõ

**Vấn đề:** Password lấy từ env là hợp lý hơn hard-code nhưng chưa thấy redaction/CI secret handling policy.

**Tại sao xảy ra:** Test infra thường bị xem nhẹ về security.

**Ảnh hưởng production/CI:** Debug output hoặc failed command có thể làm lộ credential nếu pipeline/logging không kiểm soát.

**Cách sửa:** Dùng CI secret store, tránh echo env, dùng least-privilege test accounts và rotate định kỳ.

## Phiên bản đề xuất

Một hướng cải thiện là dùng fixtures mặc định, tạo test data riêng cho từng test và chờ state thay vì sleep.

```ts
import { test, expect } from '@playwright/test';

async function createEmployee(request: any, suffix: string) {
  const response = await request.post('/test-support/employees', {
    data: {
      externalId: `E2E-${suffix}`,
      displayName: `E2E Employee ${suffix}`,
      status: 'Active'
    }
  });

  expect(response.ok()).toBeTruthy();
  return await response.json();
}

test('employee can edit profile', async ({ page, request }) => {
  const employee = await createEmployee(
    request,
    test.info().testId.replace(/[^a-zA-Z0-9]/g, '-'));

  await page.goto(`/employees/${employee.id}`);

  await page.getByLabel('Phone').fill('+84123456789');

  const saveResponsePromise = page.waitForResponse(response =>
    response.url().includes(`/api/employees/${employee.id}`) &&
    response.request().method() === 'PUT');

  await page.getByRole('button', { name: 'Save' }).click();

  const saveResponse = await saveResponsePromise;
  expect(saveResponse.ok()).toBeTruthy();

  await expect(page.getByTestId('toast')).toHaveText('Saved');
});

test('admin can deactivate user', async ({ page, request }) => {
  const employee = await createEmployee(
    request,
    `${test.info().testId.replace(/[^a-zA-Z0-9]/g, '-')}-inactive`);

  await page.goto(`/employees/${employee.id}`);
  await page.getByRole('button', { name: 'Deactivate' }).click();
  await page.getByRole('button', { name: 'Confirm' }).click();

  await expect(page.getByTestId('status')).toHaveText('Inactive');
});

test('employee list shows active users', async ({ page, request }) => {
  const employee = await createEmployee(
    request,
    `${test.info().testId.replace(/[^a-zA-Z0-9]/g, '-')}-list`);

  await page.goto('/employees');

  await expect(
    page.getByRole('row', { name: new RegExp(employee.externalId) })
  ).toBeVisible();
});
```

`/test-support/employees` chỉ là scenario example. Nếu không được phép có test-support endpoint trong deployed app, CI có thể seed qua database fixture, dedicated test API, setup project hoặc backend API bình thường với privileged test identity. Điểm quan trọng là test tự sở hữu preconditions thay vì dựa vào thứ tự.

Theo tài liệu Playwright hiện hành, Playwright Test tạo một isolated browser context cho mỗi test khi dùng fixtures mặc định. Đây là cơ chế giúp cookies/local storage/session state không leak giữa tests. Tài liệu cũng hỗ trợ trace trên retry/failure để điều tra flaky test thay vì chỉ dựa vào screenshot.

## Giải thích thiết kế sau khi sửa

Browser isolation và test-data isolation là hai lớp khác nhau. Playwright có thể đảm bảo browser context riêng nhưng không thể tự cô lập record trong database của application.

Mỗi test vì vậy cần một server-side identity riêng hoặc dữ liệu immutable phù hợp. Khi test mutate employee, ID phải độc lập với test khác. Nhờ đó suite vẫn chạy parallel mà không cần serial hóa toàn bộ.

`expect(...)` của Playwright có auto-waiting semantics cho nhiều UI conditions, nên test nên chờ outcome người dùng quan sát được. `waitForResponse` chỉ nên dùng khi network event thật sự là part của assertion/coordination, không phải thay mọi UI assertion.

Retry có thể giữ ở mức nhỏ để thu trace và phân loại flaky nhưng không phải correctness mechanism. Một test chỉ pass sau retry vẫn là tín hiệu cần theo dõi.

## Trade-offs

Unique test data làm database test environment tăng dữ liệu và cần cleanup/TTL job. Cleanup có thể chạy theo namespace/build ID thay vì từng test synchronous delete để tránh suite chậm.

API-based setup nhanh và rõ nhưng có thể bypass UI path. Đây thường là trade-off hợp lý: E2E test tập trung vào behavior cần test, còn precondition setup không nhất thiết đi qua UI.

Dùng nhiều workers giảm wall-clock time nhưng tăng load lên test environment. Worker count phải phù hợp capacity; nếu test environment bị saturation, flaky do environment load vẫn có thể xuất hiện dù tests đã isolated.

Trace làm artifact lớn hơn và có thể chứa dữ liệu nhạy cảm. Retention/access phải phù hợp; tránh đưa production secrets/PII vào E2E test environment.

## Cách kiểm thử

1. **Parallel determinism test:** chạy cùng suite 20 lần với 6 workers; theo dõi flaky rate phải về gần 0 cho các tests đã sửa.
2. **Order independence test:** chạy từng test riêng, chạy reverse/filter/shard; outcome phải không phụ thuộc suite order.
3. **Data isolation test:** log namespace/test ID và xác minh không có hai tests mutate cùng employee record.
4. **Slow-environment test:** thêm artificial API latency; tests dùng state-based waits vẫn pass trong timeout budget hợp lý mà không cần tăng fixed sleep.
5. **Failure artifact validation:** cố tình làm một assertion fail và xác minh CI lưu trace/report/screenshot đủ để điều tra.

## Quan sát trong production

Đây là CI/test observability hơn là runtime production telemetry. Theo dõi:

- first-attempt pass rate;
- retry-pass rate;
- flaky rate theo test name/file;
- duration p50/p95 theo test;
- worker utilization và test-environment CPU/DB/API latency;
- failure category: assertion, timeout, setup, environment, application error;
- trace artifact availability;
- build/test namespace để truy ngược test data;
- quarantine count và age nếu có quarantine policy.

Không nên chỉ nhìn “pipeline cuối cùng xanh”. Dashboard phải phân biệt **pass first attempt**, **pass after retry** và **consistently failing**.

## Câu hỏi phỏng vấn mở rộng

1. Nếu suite đã isolated nhưng 6 workers vẫn flaky vì test environment database bị saturation, bạn chỉnh worker count hay scale environment dựa trên metric nào?
2. Bạn sẽ khi nào chấp nhận chạy một nhóm tests serial thay vì cố làm tất cả parallel?
3. Nếu trace chứa token hoặc PII từ test environment, bạn thiết kế artifact retention/redaction/access control như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Managed Identity giải quyết identity của application tới Azure resource; nó không có nghĩa mọi secret business đều biến mất, nhưng giúp tránh application credential riêng cho Key Vault.
- Secret retrieval không nên mặc định nằm trên hot request path. Caching/refresh policy phải gắn với rotation SLO và failure behavior.
- Không log secret; secret redaction chỉ là defense-in-depth, không thay thế việc loại credential khỏi logging arguments.
- `HttpClient` và Azure SDK clients cần lifecycle được quản lý thay vì tạo mới theo từng business request khi không cần thiết.
- Playwright browser isolation không thay thế backend test-data isolation. Parallel E2E tests chỉ deterministic khi cả client state và server-side mutable data được cô lập.
- Fixed sleeps và retries không sửa race condition. Chờ observable state, thu trace và đo flaky rate giúp tìm root cause thật.

## Mẫu tư duy cần nhớ

- Đừng đưa control-plane/configuration dependency vào hot path nếu không cần.
- Thiết kế secret rotation cùng với cache freshness và failure policy.
- Không bao giờ dùng log để chẩn đoán bằng cách lộ credential.
- Isolate mutable test data trước khi đổ lỗi cho parallelism.
- Retry giúp quan sát failure; retry không biến nondeterministic test thành test đúng.
