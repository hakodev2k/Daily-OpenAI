# Code Review Challenge 1 — Optimizely CMS component cache làm rò nội dung giữa visitor segments

**Chủ đề:** C#/.NET, Optimizely CMS, ASP.NET Core, caching, personalization, authorization, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một marketing website chạy Optimizely CMS trên nhiều Azure App Service instances. Homepage có block hiển thị promotion theo market, language và visitor segment. Editors có thể publish/unpublish promotion trong ngày. Team thêm `IMemoryCache` để giảm số lần gọi content API và pricing service.

Sau release, QA thỉnh thoảng thấy promotion của market khác; production có report rằng visitor anonymous nhìn thấy CTA vốn chỉ dành cho loyalty members. Sau publish, một số instances cập nhật ngay nhưng một số instances giữ nội dung cũ vài phút. Team đề xuất tăng TTL lên 30 phút để giảm backend load hơn nữa.

## Đoạn code cần review

```csharp
public sealed class PromotionBlockService
{
    private readonly IMemoryCache _cache;
    private readonly IContentLoader _contentLoader;
    private readonly IPricingClient _pricingClient;
    private readonly IHttpContextAccessor _httpContextAccessor;

    public PromotionBlockService(
        IMemoryCache cache,
        IContentLoader contentLoader,
        IPricingClient pricingClient,
        IHttpContextAccessor httpContextAccessor)
    {
        _cache = cache;
        _contentLoader = contentLoader;
        _pricingClient = pricingClient;
        _httpContextAccessor = httpContextAccessor;
    }

    public async Task<PromotionViewModel?> GetAsync(
        ContentReference contentLink,
        string market,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"promotion:{contentLink.ID}";

        if (_cache.TryGetValue(cacheKey, out PromotionViewModel? cached))
            return cached;

        var content = _contentLoader.Get<PromotionBlock>(contentLink);

        var user = _httpContextAccessor.HttpContext!.User;
        var loyaltyMember = user.IsInRole("LoyaltyMember");

        var price = await _pricingClient.GetCampaignPriceAsync(
            content.ProductCode,
            market);

        if (content.LoyaltyOnly && !loyaltyMember)
            return null;

        var model = new PromotionViewModel
        {
            Heading = content.Heading,
            ProductCode = content.ProductCode,
            Price = price,
            Market = market,
            LoyaltyOnly = content.LoyaltyOnly
        };

        _cache.Set(cacheKey, model, TimeSpan.FromMinutes(10));
        return model;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và data-isolation problems.
2. Xác định caching, personalization, reliability và performance concerns.
3. Giải thích production impact khi nhiều instances, markets, languages và visitor segments cùng truy cập.
4. Ưu tiên cross-segment/cross-market data leakage trước micro-optimization.
5. Đề xuất corrected implementation/design phù hợp CMS publishing và cache invalidation.
6. Giải thích testing cho personalization, publish/unpublish, concurrent cache miss và dependency failure.
7. Nêu telemetry production cần có để chứng minh cache an toàn và hiệu quả.

## Câu hỏi gợi mở

1. Cache key hiện encode những dimensions nào của output?
2. Một model đã được tạo cho loyalty member có thể được trả cho anonymous visitor không?
3. `IMemoryCache` trên nhiều App Service instances có invalidation semantics gì giữa processes?
4. Publish/unpublish CMS content nên tương tác với TTL-only cache như thế nào?
5. Điều gì xảy ra khi hàng trăm requests cùng miss một hot promotion key?

## Gợi ý

### Gợi ý 1

### Gợi ý 2

Hãy phân biệt cache của reusable content/pricing data với cache của user/segment-specific rendered model; multi-instance invalidation và cache stampede là hai vấn đề riêng.

## Kết quả code review tham khảo

### Critical — Cache key bỏ qua visitor authorization/personalization dimension

**Vấn đề:** cache key chỉ chứa `contentLink.ID`, trong khi output phụ thuộc `LoyaltyMember`.  
**Tại sao xảy ra:** rendered `PromotionViewModel` được cache sau khi authorization/personalization decision đã được áp dụng.  
**Ảnh hưởng production:** model được tạo cho loyalty member có thể được trả trực tiếp cho anonymous visitor ở lần cache hit tiếp theo.  
**Cách sửa:** không cache user-specific authorization result dưới shared key. Tốt hơn là cache reusable content/pricing data rồi áp authorization/personalization cho từng request; nếu segment-level caching thật sự cần thiết, key phải encode bounded, trusted segment dimensions và policy phải được review như một data-isolation boundary.

### High — Cache key bỏ qua market và language/content variation

**Vấn đề:** `market` ảnh hưởng price nhưng không có trong key; content language/variation cũng không được thể hiện.  
**Tại sao xảy ra:** cache identity không tương ứng với function inputs và CMS variation context.  
**Ảnh hưởng production:** visitor có thể thấy price/content của market hoặc language khác.  
**Cách sửa:** key reusable data theo tất cả dimensions ảnh hưởng kết quả, ví dụ content/version/language + market cho pricing; tránh một monolithic rendered-model cache nếu dimensions tăng nhanh.

### High — TTL-only cache không phản ánh CMS publish/unpublish

**Vấn đề:** content có thể thay đổi nhưng cache tồn tại tới 10 phút độc lập với publish event.  
**Tại sao xảy ra:** invalidation chỉ dựa thời gian.  
**Ảnh hưởng production:** stale campaign, CTA hoặc unpublished content tiếp tục xuất hiện.  
**Cách sửa:** tích hợp invalidation với content change/publish signals phù hợp kiến trúc CMS, hoặc dùng cache dependency/version token. TTL chỉ là safety bound, không thay thế event-aware invalidation khi freshness requirement chặt.

### High — `IMemoryCache` tạo cache state khác nhau trên từng instance

**Vấn đề:** mỗi App Service process có cache riêng.  
**Tại sao xảy ra:** in-memory cache không distributed.  
**Ảnh hưởng production:** sau publish, users nhận nội dung khác nhau tùy instance; hit ratio và invalidation behavior khó dự đoán.  
**Cách sửa:** nếu giữ local cache, cần distributed invalidation/version strategy. Distributed cache có thể là lựa chọn khác nhưng không tự giải quyết key correctness; chỉ thêm Redis khi operational cost và consistency requirement biện minh.

### Medium — Cache stampede trên hot key

**Vấn đề:** nhiều concurrent misses cùng gọi content/pricing dependency.  
**Tại sao xảy ra:** `TryGetValue` + fetch + `Set` không single-flight per key.  
**Ảnh hưởng production:** publish/expiry có thể tạo burst vào pricing service.  
**Cách sửa:** dùng bounded per-key single-flight/coalescing hoặc cache abstraction có stampede protection; luôn thiết kế cleanup/cancellation để không tạo lock leak.

### Medium — CancellationToken không truyền vào pricing dependency

**Vấn đề:** method nhận token nhưng dependency call không dùng token.  
**Tại sao xảy ra:** cancellation propagation bị đứt ở I/O boundary.  
**Ảnh hưởng production:** client disconnect/deploy vẫn để outbound work tiếp tục, tăng pressure khi dependency chậm.  
**Cách sửa:** propagate token nếu client API hỗ trợ; phân biệt request cancellation với dependency failure trong telemetry.

### Medium — Pricing failure không có degradation policy

**Vấn đề:** pricing dependency failure làm toàn promotion path fail mà không thể hiện business policy.  
**Tại sao xảy ra:** không định nghĩa stale-price/fallback/hide-promotion semantics.  
**Ảnh hưởng production:** transient pricing outage có thể làm homepage degradation rộng.  
**Cách sửa:** cùng Product quyết định fail-closed, hide price, stale bounded data hay fallback; implementation và monitoring phải phản ánh policy đó.

### Low — `HttpContext!` tạo assumption khó kiểm chứng và coupling cao

**Vấn đề:** service phụ thuộc ambient HTTP context và null-forgiving operator.  
**Tại sao xảy ra:** personalization input không được truyền rõ ràng.  
**Ảnh hưởng production:** reuse từ background/rendering context có thể fail; test khó hơn.  
**Cách sửa:** truyền một trusted request/visitor context hoặc authorization decision cần thiết vào service boundary.

## Phiên bản đề xuất

Ví dụ dưới đây cache content snapshot và market-specific price riêng, sau đó áp loyalty decision cho từng request. Cơ chế content version/invalidation chỉ mang tính kiến trúc minh họa; implementation cụ thể phải nối với publish/change notifications mà hệ thống Optimizely hiện tại thực sự cung cấp.

```csharp
public sealed class PromotionBlockService
{
    private readonly IMemoryCache _cache;
    private readonly IContentLoader _contentLoader;
    private readonly IPricingClient _pricingClient;

    public PromotionBlockService(
        IMemoryCache cache,
        IContentLoader contentLoader,
        IPricingClient pricingClient)
    {
        _cache = cache;
        _contentLoader = contentLoader;
        _pricingClient = pricingClient;
    }

    public async Task<PromotionViewModel?> GetAsync(
        ContentReference contentLink,
        string language,
        string market,
        bool loyaltyMember,
        CancellationToken cancellationToken)
    {
        var contentKey = $"promotion-content:{contentLink.ID}:{language}";

        var content = await _cache.GetOrCreateAsync(contentKey, entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            return Task.FromResult(_contentLoader.Get<PromotionBlock>(contentLink));
        });

        if (content is null)
            return null;

        if (content.LoyaltyOnly && !loyaltyMember)
            return null;

        var priceKey = $"promotion-price:{content.ProductCode}:{market}";

        var price = await _cache.GetOrCreateAsync(priceKey, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(1);
            return await _pricingClient.GetCampaignPriceAsync(
                content.ProductCode,
                market,
                cancellationToken);
        });

        return new PromotionViewModel
        {
            Heading = content.Heading,
            ProductCode = content.ProductCode,
            Price = price,
            Market = market,
            LoyaltyOnly = content.LoyaltyOnly
        };
    }
}
```

Production implementation còn cần content-change invalidation/versioning và, nếu hot-key load đáng kể, explicit single-flight thay vì giả định cache factory có guarantee phù hợp với yêu cầu concurrency.

## Giải thích thiết kế sau khi sửa

Authorization/personalization được áp sau shared cache lookup nên cache không chứa quyết định user-specific. Content và price có freshness/lifecycle khác nhau nên được cache riêng. Market được đưa vào price identity; language được đưa vào content identity. Nếu CMS content version hoặc variation context phức tạp hơn, key/invalidation phải dựa trên actual content identity thay vì chỉ string language.

## Trade-offs

Tách cache tăng số keys và logic invalidation nhưng giảm nguy cơ cross-user leakage. Local cache nhanh và đơn giản nhưng cần multi-instance invalidation; distributed cache tăng operational dependency và serialization cost. Short TTL giảm stale window nhưng tăng dependency load. Event-driven invalidation cải thiện freshness nhưng cần xử lý missed events và fallback TTL/version checks.

## Cách kiểm thử

1. **Security/integration test:** cùng content key, loyalty request trước rồi anonymous request; anonymous không bao giờ nhận loyalty-only promotion.
2. **Variation test:** hai markets/languages concurrent phải nhận đúng price/content tương ứng.
3. **Concurrency/load test:** hàng trăm requests sau expiry/publish; đo số dependency calls và kiểm tra stampede protection.
4. **CMS integration test:** publish, update và unpublish phải invalidate/version cache trong freshness SLO đã định nghĩa.
5. **Failure-path test:** pricing timeout; verify cancellation/degradation policy và telemetry đúng.

## Quan sát trong production

Theo dõi cache hit/miss theo cache category, invalidation count/lag, pricing dependency p95/p99/error rate, promotion render failures và content-version mismatch signals. Log structured dimensions như content ID/version, market, language và coarse segment policy; không log sensitive identity không cần thiết. Correlate publish event với cache invalidation trên từng instance.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận cache rendered HTML theo visitor segment, và key cardinality/security review sẽ thay đổi thế nào?
2. Nếu chuyển local cache sang Redis nhưng giữ nguyên key hiện tại, bug nào vẫn còn nguyên?
3. Nếu pricing service cho phép stale price tối đa 2 phút, bạn thiết kế stale-while-revalidate/failure fallback thế nào?

# Code Review Challenge 2 — Jenkins/Octopus pipeline deploy database trước application và rollback không thể khôi phục schema

**Chủ đề:** CI/CD, Jenkins, Octopus Deploy, SQL Server, database migration, artifact consistency, rollback, release safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core application được build bằng Jenkins và deploy lên IIS/Windows Server qua Octopus Deploy. Production có 8 web nodes sau load balancer. Team muốn zero/minimal downtime và có nút rollback nhanh nếu release lỗi.

Pipeline hiện build application package và một SQL script từ branch `main`. Deployment chạy SQL migration trước, sau đó lần lượt update web nodes. Release gần đây đổi cột `Customer.FullName` thành `DisplayName`; migration drop cột cũ ngay. Trong rolling deployment, nodes chạy version cũ bắt đầu trả 500 trước khi toàn fleet được cập nhật. Khi team rollback application package, database schema vẫn ở version mới nên lỗi tiếp tục.

## Đoạn code cần review

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                bat 'dotnet restore'
                bat 'dotnet publish src/Portal/Portal.csproj -c Release -o out'
                bat 'powershell Compress-Archive -Path out/* -DestinationPath portal.zip -Force'
            }
        }

        stage('Database Script') {
            steps {
                bat 'dotnet ef migrations script --project src/Infrastructure -o migration.sql'
            }
        }

        stage('Deploy Production') {
            steps {
                bat 'sqlcmd -S prod-sql -d Portal -i migration.sql'
                bat 'octo deploy-release --project Portal --releaseNumber latest --environment Production'
            }
        }
    }
}
```

Deployment convention trong Octopus:

```text
1. Stop IIS site on node
2. Copy portal.zip from shared folder
3. Start IIS site
4. Repeat for next node
5. If health check fails, redeploy previous portal.zip
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và release-safety problems.
2. Xác định artifact consistency, secret/configuration và rollback concerns.
3. Giải thích vì sao rolling deployment có thể fail dù migration và app mới đều đúng khi chạy riêng lẻ.
4. Ưu tiên backward-compatible schema evolution và immutable release artifacts.
5. Đề xuất pipeline/release strategy có expand-migrate-contract hoặc phương án tương đương.
6. Giải thích deployment validation, database testing và rollback/roll-forward strategy.
7. Nêu telemetry production cần theo dõi trong rollout.

## Câu hỏi gợi mở

1. Trong rolling deployment, version cũ và mới tồn tại đồng thời bao lâu và cùng kỳ vọng schema gì?
2. `releaseNumber latest` có đảm bảo application artifact vừa build chính là artifact được deploy không?
3. Migration script không chỉ rõ source/target migration có thể chứa những thay đổi nào?
4. Rollback binary có đảo ngược được destructive database migration không?
5. Database credentials và production execution permissions nên nằm ở đâu trong pipeline design?

## Gợi ý

### Gợi ý 1

Database rollback thường khó hơn binary rollback. Hãy thiết kế migration để version N và N+1 cùng hoạt động trong rollout, rồi contract destructive changes ở release sau khi compatibility window kết thúc.

## Kết quả code review tham khảo

### Critical — Destructive migration chạy trước mixed-version rollout

**Vấn đề:** drop/rename schema mà version cũ vẫn cần trước khi old nodes được loại khỏi traffic.  
**Tại sao xảy ra:** database được deploy như một atomic prerequisite nhưng application rollout là rolling/mixed-version.  
**Ảnh hưởng production:** old nodes query cột đã bị xóa và trả 500 ngay trong deployment.  
**Cách sửa:** dùng backward-compatible expand/migrate/contract: thêm `DisplayName` trước mà chưa xóa `FullName`, deploy code có compatibility strategy, backfill/migrate data, chuyển reads/writes, verify fleet/data, rồi drop cột ở release sau.

### Critical — Rollback application không rollback được destructive schema

**Vấn đề:** Octopus chỉ redeploy binary cũ.  
**Tại sao xảy ra:** database state là shared mutable dependency và migration có thể irreversible/data-destructive.  
**Ảnh hưởng production:** “rollback thành công” ở deployment tool nhưng application cũ vẫn incompatible.  
**Cách sửa:** ưu tiên forward-compatible migrations và roll-forward remediation. Chỉ có down migration khi thực sự safe và tested; backup/restore không phải instant generic rollback cho mọi production incident.

### High — `latest` phá immutable release identity

**Vấn đề:** deploy không pin release/package version cụ thể từ build hiện tại.  
**Tại sao xảy ra:** mutable alias nối build và deploy.  
**Ảnh hưởng production:** khó chứng minh binary nào chạy, rollback/reproduce/audit kém tin cậy.  
**Cách sửa:** tạo versioned artifact một lần, publish với checksum/version, tạo Octopus release pin đúng package version và promote chính release đó qua environments.

### High — Migration script không pin rõ target migration/release state

**Vấn đề:** command tạo script theo migration state/source checkout nhưng pipeline không chứng minh script tương ứng release artifact và production target.  
**Tại sao xảy ra:** application package và migration không được đóng gói thành cùng release manifest.  
**Ảnh hưởng production:** drift hoặc branch timing có thể deploy schema khác binary.  
**Cách sửa:** generate migration artifact trong build, version cùng release, validate migration range/idempotency strategy phù hợp và deploy đúng artifact đã qua test.

### High — Production DB mutation chạy trực tiếp từ generic Jenkins agent

**Vấn đề:** build agent có network/credential capability để mutate production.  
**Tại sao xảy ra:** separation giữa build và privileged deployment boundary yếu.  
**Ảnh hưởng production:** credential exposure hoặc compromised build job có blast radius lớn.  
**Cách sửa:** tách build khỏi production deployment; dùng scoped deployment worker/service identity, secret store, least privilege và approval/audit controls phù hợp tổ chức.

### Medium — Restore/build không bảo đảm reproducibility đầy đủ

**Vấn đề:** pipeline không thể hiện locked dependency/versioning, tests hay artifact manifest.  
**Tại sao xảy ra:** output được zip thủ công và shared folder là source deploy.  
**Ảnh hưởng production:** khó reproduce release và phát hiện artifact drift.  
**Cách sửa:** versioned package repository/feed, deterministic release metadata/checksum và promote artifact thay vì rebuild.

### Medium — Health check per node chưa chứng minh application/schema compatibility

**Vấn đề:** convention chỉ nói “health check” mà không nêu readiness/business smoke tests.  
**Tại sao xảy ra:** process-up có thể pass dù critical query fail.  
**Ảnh hưởng production:** rollout tiếp tục trong khi user paths đã lỗi.  
**Cách sửa:** pre/post deployment validation gồm DB compatibility check, readiness và bounded smoke tests; gate rollout theo error-rate/SLO signals.

### Medium — Không có explicit data backfill/dual-read-write transition

**Vấn đề:** rename semantic được coi như DDL-only change.  
**Tại sao xảy ra:** schema evolution không xét dữ liệu và mixed-version writes.  
**Ảnh hưởng production:** `DisplayName` có thể null/stale hoặc writes giữa versions diverge.  
**Cách sửa:** định nghĩa migration phases, backfill idempotent, write compatibility và verification trước contract.

### Low — Pipeline thiếu explicit automated quality gates

**Vấn đề:** snippet không chạy tests/static analysis/deployment validation trước production.  
**Tại sao xảy ra:** production stage nối trực tiếp sau build/script.  
**Ảnh hưởng production:** regression đơn giản đi tới release boundary.  
**Cách sửa:** thêm unit/integration/database migration tests, security/static checks và staging validation dựa trên risk; không coi coverage percentage là gate duy nhất.

## Phiên bản đề xuất

Ví dụ pipeline dưới đây minh họa nguyên tắc: build một release immutable, test migration compatibility, publish artifacts, sau đó deploy release ID cụ thể. Tên commands/feed là minh họa và phải map vào Jenkins/Octopus setup thực tế.

```groovy
pipeline {
    agent any

    environment {
        RELEASE_VERSION = "${BUILD_NUMBER}"
    }

    stages {
        stage('Build and Test') {
            steps {
                bat 'dotnet restore --locked-mode'
                bat 'dotnet test -c Release --no-restore'
                bat 'dotnet publish src/Portal/Portal.csproj -c Release --no-restore -o out'
            }
        }

        stage('Create Release Artifacts') {
            steps {
                bat 'dotnet ef migrations script --project src/Infrastructure --idempotent -o artifacts/migration.sql'
                bat 'powershell Compress-Archive -Path out/* -DestinationPath artifacts/Portal.%RELEASE_VERSION%.zip -Force'
                bat 'powershell ./build/write-release-manifest.ps1 %RELEASE_VERSION%'
            }
        }

        stage('Validate Migration') {
            steps {
                bat 'powershell ./build/test-migration-compatibility.ps1 artifacts/migration.sql'
            }
        }

        stage('Publish') {
            steps {
                bat 'powershell ./build/publish-release.ps1 %RELEASE_VERSION%'
            }
        }

        stage('Deploy Production') {
            steps {
                bat 'octo deploy-release --project Portal --releaseNumber %RELEASE_VERSION% --environment Production'
            }
        }
    }
}
```

Database change cho `FullName` → `DisplayName` nên tách release phases, ví dụ:

```sql
-- Release N: expand
ALTER TABLE Customer ADD DisplayName nvarchar(300) NULL;

-- Backfill phải được thiết kế idempotent/batched theo data volume.
UPDATE Customer
SET DisplayName = FullName
WHERE DisplayName IS NULL;

-- Release N+1/N+2 sau khi toàn fleet không còn phụ thuộc FullName:
-- ALTER TABLE Customer DROP COLUMN FullName;
```

Không nên copy nguyên script này vào production mà không đánh giá table size, locking, online behavior, transaction log và deployment window.

## Giải thích thiết kế sau khi sửa

Application package và migration artifact cùng release identity và được promote thay vì rebuild. Schema evolution hỗ trợ mixed-version window. Destructive contract được trì hoãn đến khi telemetry và deployment inventory chứng minh không còn consumers cũ. Privileged production mutation nên chạy trong deployment boundary có scoped identity thay vì generic build worker.

## Trade-offs

Expand/contract cần nhiều releases và tạm thời giữ duplicate schema/data logic. Dual-write có thể tăng complexity và phải xử lý partial failures; đôi khi application-level compatibility adapter hoặc database compatibility view phù hợp hơn. Idempotent migration script hữu ích nhưng không biến destructive migration thành safe. Canary/rolling validation làm deployment chậm hơn nhưng giảm blast radius.

## Cách kiểm thử

1. **Database compatibility test:** schema expanded phải chạy được cả application N và N+1.
2. **Migration test:** restore production-like schema/data snapshot, chạy migration/backfill hai lần nếu design yêu cầu idempotency, verify constraints/data.
3. **Deployment validation:** giữ một old node và một new node cùng traffic trong staging; verify critical user paths.
4. **Rollback test:** rollback binary trong expanded-schema phase phải hoạt động; document rõ phase nào chỉ hỗ trợ roll-forward.
5. **Load/failure test:** backfill trên representative data volume; đo locks, log growth, query latency và behavior khi migration bị gián đoạn.

## Quan sát trong production

Theo dõi release version trên từng node, HTTP 5xx/p95/p99 theo version, SQL dependency failures, migration duration, blocking/deadlocks, backfill progress và schema version. Application Insights/logs phải chứa release identifier để correlate mixed-version errors. Deployment gate nên dừng khi error budget/critical smoke tests xấu đi thay vì tiếp tục vì process đã start.

## Câu hỏi phỏng vấn mở rộng

1. Nếu không thể dual-write `FullName` và `DisplayName`, bạn có những compatibility options nào khác?
2. Khi nào blue/green deployment vẫn không giải quyết được database schema incompatibility?
3. Nếu migration cần thay đổi một bảng hàng trăm triệu rows, bạn tách schema change và data migration như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cache và deployment đều là bài toán về compatibility boundary. Cache key phải đại diện đúng mọi dimension ảnh hưởng dữ liệu và không được biến authorization decision thành shared state ngoài ý muốn. Release pipeline phải coi database là shared mutable dependency: binary rollback không tự đảo schema, và rolling deployment luôn tạo một khoảng thời gian nhiều application versions cùng tồn tại.

## Mẫu tư duy cần nhớ

- Cache identity phải phản ánh đầy đủ inputs và trust boundaries của output.
- Authorization/personalization không được vô tình biến thành shared cached decision.
- Thiết kế invalidation cùng lúc với cache; TTL chỉ là một freshness mechanism.
- Database migration phải tương thích với mixed-version deployment window.
- Build once, version immutably, promote the same artifact; thiết kế rollback trước khi release.
