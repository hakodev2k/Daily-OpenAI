# Code Review Challenge 1 — EF Core “claim jobs” gây duplicate processing dưới concurrency

**Chủ đề:** C#/.NET, EF Core, SQL Server, concurrency, transactions, background processing, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một hệ thống approval có bảng `WorkItems`. Nhiều application instances chạy cùng `BackgroundService` để lấy các item `Pending`, đánh dấu `Processing`, gọi API bên thứ ba, rồi chuyển sang `Completed`.

Team muốn tăng throughput nên mỗi worker lấy 50 items một lần. Sau khi scale từ 1 lên 6 instances, production xuất hiện duplicate external requests. SQL không báo deadlock đáng kể, CPU database vẫn thấp. Một số item ở trạng thái `Processing` vĩnh viễn sau khi pod restart.

Requirement: một logical work item không được tạo duplicate side effect ở hệ thống ngoài. Hệ thống phải phục hồi được sau crash. Không giả định database transaction có thể rollback side effect đã xảy ra ở external API.

## Đoạn code cần review

```csharp
public sealed class WorkItemProcessor
{
    private readonly AppDbContext _db;
    private readonly ExternalApprovalClient _client;
    private readonly ILogger<WorkItemProcessor> _logger;

    public WorkItemProcessor(
        AppDbContext db,
        ExternalApprovalClient client,
        ILogger<WorkItemProcessor> logger)
    {
        _db = db;
        _client = client;
        _logger = logger;
    }

    public async Task ProcessBatchAsync(CancellationToken cancellationToken)
    {
        var items = await _db.WorkItems
            .Where(x => x.Status == WorkItemStatus.Pending)
            .OrderBy(x => x.CreatedAt)
            .Take(50)
            .ToListAsync(cancellationToken);

        foreach (var item in items)
            item.Status = WorkItemStatus.Processing;

        await _db.SaveChangesAsync(cancellationToken);

        foreach (var item in items)
        {
            try
            {
                await _client.ApproveAsync(
                    item.Id,
                    item.Payload,
                    cancellationToken);

                item.Status = WorkItemStatus.Completed;
                item.CompletedAt = DateTimeOffset.UtcNow;

                await _db.SaveChangesAsync(cancellationToken);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed processing work item {WorkItemId}", item.Id);
            }
        }
    }
}
```

2. `Processing` hiện tại có phải một durable lease có thể recovery không?
3. Điều gì xảy ra nếu external API thành công nhưng process chết trước lần `SaveChangesAsync` cuối?

## Kết quả code review tham khảo

### Critical — Read-then-update không atomically claim work

**Vấn đề:** Nhiều workers có thể query cùng các row `Pending` trước khi bất kỳ worker nào persist `Processing`.

**Tại sao xảy ra:** Query và state transition là hai bước tách biệt. Default transaction behavior của từng `SaveChangesAsync` không biến query trước đó thành một atomic claim operation.

**Ảnh hưởng production:** Cùng work item có thể được nhiều instances xử lý và gọi external API nhiều lần.

**Cách sửa:** Thiết kế claim operation có concurrency control ở database: atomic conditional update/claim, optimistic concurrency token, hoặc database-specific locking/skip-locked strategy sau khi xác minh semantics phù hợp. Chỉ xử lý item mà worker thực sự claim thành công.

### Critical — External side effect không có idempotency boundary

**Vấn đề:** Nếu external call thành công nhưng local completion chưa persist, retry/recovery có thể gửi side effect lần nữa.

**Tại sao xảy ra:** Local database và external service không cùng transaction boundary.

**Ảnh hưởng production:** Duplicate approval/action dù local claim đã được sửa.

**Cách sửa:** Dùng stable operation ID/idempotency key nếu external contract hỗ trợ. Nếu không hỗ trợ, cần reconciliation/deduplication design phù hợp business semantics; không tuyên bố exactly-once nếu không có cơ chế chứng minh.

### High — `Processing` không có lease/expiry/recovery metadata

**Vấn đề:** Item được đổi sang `Processing` nhưng không lưu owner, claimed time hoặc lease expiry.

**Tại sao xảy ra:** State model coi `Processing` như terminal ownership thay vì một claim có thể bị orphan.

**Ảnh hưởng production:** Pod chết sau claim làm item mắc kẹt vĩnh viễn.

**Cách sửa:** Lưu `LeaseOwner`, `LeaseExpiresAt`, attempt metadata hoặc thiết kế queue/broker có lock/visibility semantics. Recovery chỉ reclaim khi lease hết hạn và phải phối hợp với idempotency/reconciliation.

### High — Catch-all biến cancellation thành processing failure

**Vấn đề:** `OperationCanceledException` cũng bị catch bởi `Exception`.

**Tại sao xảy ra:** Không phân biệt host shutdown/caller cancellation với dependency failure.

**Ảnh hưởng production:** Shutdown semantics mơ hồ; logs báo lỗi giả và loop có thể tiếp tục với context đã cancellation.

**Cách sửa:** Re-throw cancellation khi `cancellationToken.IsCancellationRequested`; phân loại transient/permanent/unknown outcomes riêng.

### High — Failed item không có durable retry state

**Vấn đề:** Exception chỉ được log; row vẫn `Processing`.

**Tại sao xảy ra:** Không persist retry count, next-attempt time, failure category hoặc terminal failure.

**Ảnh hưởng production:** Work silently stops sau transient failure.

**Cách sửa:** Có explicit retry state machine, bounded attempts/backoff/jitter và dead-letter/manual-review path tùy business requirement.

### High — Không phân loại unknown external outcome

**Vấn đề:** Timeout không chứng minh external API chưa thực hiện action.

**Tại sao xảy ra:** Transport outcome và business outcome bị đồng nhất.

**Ảnh hưởng production:** Retry mù quáng có thể duplicate side effect.

**Cách sửa:** Biểu diễn `Unknown`/reconciliation state khi cần; query external system bằng stable reference nếu contract hỗ trợ.

### Medium — Batch ownership quá dài

**Vấn đề:** Claim 50 items rồi xử lý tuần tự khiến item cuối giữ trạng thái `Processing` lâu dù chưa bắt đầu external call.

**Tại sao xảy ra:** Claim window lớn hơn processing concurrency thực tế.

**Ảnh hưởng production:** Recovery latency cao, lease sizing khó và unfairness khi worker chậm.

**Cách sửa:** Claim batch phù hợp bounded concurrency/lease duration; renew lease nếu workflow thực sự dài.

### Medium — `SaveChangesAsync` cho từng item tạo nhiều database round trips

**Vấn đề:** Completion persist từng row riêng lẻ.

**Tại sao xảy ra:** Persistence strategy bám vào loop thay vì transaction/state requirements.

**Ảnh hưởng production:** Tăng DB round trips và giảm throughput.

**Cách sửa:** Chỉ batch khi correctness cho phép; đừng gom transaction qua external calls. Có thể dùng short local commits và bounded parallelism.

### Medium — Không có concurrency token/state-transition guard

**Vấn đề:** Update state không chứng minh previous state/ownership vẫn hợp lệ.

**Tại sao xảy ra:** Entity không có `rowversion`/concurrency token hoặc conditional update equivalent.

**Ảnh hưởng production:** Stale worker có thể ghi đè state mới hơn.

**Cách sửa:** Guard transition bằng expected status + owner/version và xử lý zero-row/concurrency conflict như một expected outcome.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa design bằng short-lived lease và conditional claim. SQL cụ thể cần được kiểm chứng theo database/provider thực tế.

```csharp
public sealed record ClaimedWorkItem(
    Guid Id,
    string Payload,
    string LeaseOwner,
    DateTimeOffset LeaseExpiresAt);

public sealed class WorkItemProcessor
{
    private readonly WorkItemRepository _repository;
    private readonly ExternalApprovalClient _client;
    private readonly string _workerId;

    public WorkItemProcessor(
        WorkItemRepository repository,
        ExternalApprovalClient client,
        WorkerIdentity workerIdentity)
    {
        _repository = repository;
        _client = client;
        _workerId = workerIdentity.Id;
    }

    public async Task ProcessBatchAsync(CancellationToken ct)
    {
        var items = await _repository.ClaimAsync(
            workerId: _workerId,
            maxCount: 10,
            leaseDuration: TimeSpan.FromMinutes(2),
            cancellationToken: ct);

        foreach (var item in items)
        {
            ct.ThrowIfCancellationRequested();

            try
            {
                // Stable logical operation identity across retries/restarts.
                var operationId = item.Id.ToString("N");

                var result = await _client.ApproveAsync(
                    operationId,
                    item.Payload,
                    ct);

                await _repository.CompleteAsync(
                    item.Id,
                    item.LeaseOwner,
                    result.ExternalReference,
                    ct);
            }
            catch (OperationCanceledException) when (ct.IsCancellationRequested)
            {
                throw;
            }
            catch (KnownPermanentException ex)
            {
                await _repository.FailPermanentlyAsync(
                    item.Id,
                    item.LeaseOwner,
                    ex.Message,
                    ct);
            }
            catch (Exception ex)
            {
                await _repository.ScheduleRetryOrReconciliationAsync(
                    item.Id,
                    item.LeaseOwner,
                    ex,
                    ct);
            }
        }
    }
}
```

`ClaimAsync` phải thực hiện claim ở database như một atomic/guarded operation và chỉ trả các rows thực sự thuộc worker. Cách SQL chính xác phụ thuộc SQL Server/PostgreSQL và isolation/locking strategy; cần integration test trên engine thực tế.

## Giải thích thiết kế sau khi sửa

Claim ownership và business side effect là hai vấn đề riêng. Database có thể đảm bảo chỉ một worker sở hữu một lease tại một thời điểm nếu claim đúng, nhưng external call vẫn có partial-failure window. Stable idempotency key hoặc reconciliation là lớp bảo vệ cho boundary đó.

Lease cho phép recovery sau crash nhưng thời lượng phải dựa trên processing latency thực tế. Nếu lease có thể hết khi call vẫn đang chạy, cần renewal hoặc fencing/version guard để stale worker không commit kết quả sau khi ownership chuyển sang worker khác.

Không giữ database transaction mở trong lúc chờ external HTTP call vì làm tăng lock duration và coupling với network latency.

## Trade-offs

Atomic claim SQL có thể database-specific và phức tạp hơn EF Core CRUD thông thường. Durable broker có thể cung cấp lock/redelivery semantics tốt hơn nhưng thêm infrastructure và vẫn không loại bỏ nhu cầu idempotent consumer. Lease quá dài làm recovery chậm; lease quá ngắn tăng risk concurrent ownership nếu không renew/fence đúng.

## Cách kiểm thử

1. **Concurrency integration test:** chạy nhiều processors đồng thời trên cùng database và chứng minh mỗi claim chỉ có một owner.
2. **Failure-path test:** external side effect thành công nhưng local completion bị fail/crash; recovery không tạo side effect thứ hai.
3. **Crash/restart test:** kill worker sau claim, chờ lease hết và xác nhận item được reclaim.
4. **Cancellation test:** host shutdown không bị ghi thành permanent processing failure.
5. **Database integration test:** stale owner cố `CompleteAsync` sau khi lease đã chuyển; update phải bị reject.

## Quan sát trong production

Theo dõi pending depth, oldest pending age, claim rate, lease expiry/reclaim count, processing duration, retries, unknown outcomes, concurrency conflicts, duplicate-prevention events và external dependency latency/error rate. Trace/log dùng stable `WorkItemId`, worker ID và external correlation reference. Alert khi `Processing` age vượt lease/SLO hoặc reclaim tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Nếu external provider không hỗ trợ idempotency key cũng không có lookup API, bạn có thể thực sự đảm bảo exactly-once side effect không?
2. Nếu lease hết trong khi request HTTP cũ vẫn đang chạy, fencing mechanism nào ngăn stale worker commit?
3. Khi nào bạn chọn Azure Service Bus thay vì tự xây database-backed worker queue?

# Code Review Challenge 2 — React search page bị stale response, request storm và XSS từ highlight API

**Chủ đề:** React.js, TypeScript, REST API integration, async race condition, request cancellation, XSS, browser performance, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút

## Bối cảnh

Một product-search page gọi ASP.NET Core search API mỗi khi người dùng nhập text hoặc đổi category. Search backend đôi khi mất 1–2 giây khi Elasticsearch đang reindex. Người dùng báo kết quả thỉnh thoảng “nhảy ngược” về query cũ. Khi gõ nhanh, network tab có hàng chục requests. Backend trả `highlightHtml` để đánh dấu từ khóa trong snippet.

Product yêu cầu UI phản hồi nhanh, không hiển thị kết quả của query cũ và không đưa HTML không đáng tin cậy vào DOM. Search API hiện không đảm bảo responses về đúng thứ tự request.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type SearchItem = {
  id: string;
  name: string;
  highlightHtml: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [items, setItems] = useState<SearchItem[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (!query.trim()) {
      setItems([]);
      return;
    }

    setLoading(true);
    setError(null);

    fetch(`/api/search?q=${query}&category=${category}`)
      .then(response => response.json())
      .then(data => {
        setItems(data.items);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, [query, category]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />

      <select
        value={category}
        onChange={e => setCategory(e.target.value)}
      >
        <option value="all">All</option>
        <option value="parts">Parts</option>
      </select>

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}

      <ul>
        {items.map(item => (
          <li key={item.id}>
            <strong>{item.name}</strong>
            <div
              dangerouslySetInnerHTML={{ __html: item.highlightHtml }}
            />
          </li>
        ))}
      </ul>
    </section>
  );
}
```

## Kết quả code review tham khảo

### Critical — Raw `highlightHtml` được đưa trực tiếp vào DOM

**Vấn đề:** `dangerouslySetInnerHTML` render HTML từ API mà snippet không chứng minh đã được sanitize bằng policy đáng tin cậy.

**Tại sao xảy ra:** React escaping bị bypass tại boundary này.

**Ảnh hưởng production:** Nếu search/indexed content hoặc highlight payload chứa attacker-controlled markup, có thể tạo stored/reflected XSS tùy data flow.

**Cách sửa:** Ưu tiên API trả structured highlight segments/text và render bằng React nodes để React escape content. Nếu business bắt buộc HTML, sanitize bằng một policy/library được review ở boundary phù hợp và test payload độc hại; không tự viết sanitizer bằng regex.

### High — Older response có thể overwrite newer search state

**Vấn đề:** Mỗi effect completion đều gọi `setItems` mà không biết request đó còn là request hiện hành hay không.

**Tại sao xảy ra:** Network responses không đảm bảo completion order giống start order.

**Ảnh hưởng production:** User gõ query mới nhưng cuối cùng nhìn thấy kết quả query cũ.

**Cách sửa:** Hủy request cũ bằng `AbortController` trong effect cleanup và/hoặc guard bằng request generation ID. Backend vẫn phải chịu cancellation/timeout hợp lý; client cancellation không phải security/correctness boundary duy nhất.

### High — Mỗi keystroke lập tức tạo request

**Vấn đề:** Không debounce hoặc minimum-query policy.

**Tại sao xảy ra:** `query` thay đổi kích hoạt effect ngay.

**Ảnh hưởng production:** Request storm, wasted browser/network/backend/Elasticsearch capacity và UX loading flicker.

**Cách sửa:** Debounce input theo UX requirement; cancellation vẫn cần vì debounce không loại bỏ mọi overlap. Đo latency và request volume trước khi chọn delay.

### High — Không kiểm tra `response.ok`

**Vấn đề:** `fetch` không reject chỉ vì HTTP response là `4xx/5xx`; code vẫn cố parse và dùng payload như success.

**Tại sao xảy ra:** Promise của `fetch` chủ yếu reject cho network-level failures/abort, không cho mọi HTTP error status.

**Ảnh hưởng production:** Error response có thể biến thành malformed state hoặc lỗi khó hiểu.

**Cách sửa:** Kiểm tra status/`response.ok`, parse error contract có kiểm soát và map thành UX phù hợp.

### Medium — Query parameters không được encode an toàn/chính xác

**Vấn đề:** Nội suy trực tiếp `query` và `category` vào URL.

**Tại sao xảy ra:** Ký tự `&`, `#`, `+`, Unicode hoặc reserved characters có thể thay đổi request semantics.

**Ảnh hưởng production:** Search sai hoặc malformed URL; không nên nhầm đây tự thân là server-side injection protection.

**Cách sửa:** Dùng `URLSearchParams`; backend vẫn validate input độc lập.

### Medium — Empty query không reset loading/error nhất quán

**Vấn đề:** Khi query bị xóa trong lúc request cũ đang chạy, code chỉ `setItems([])`.

**Tại sao xảy ra:** Không có cleanup/cancellation và state transition đầy đủ.

**Ảnh hưởng production:** Request cũ có thể repopulate results; loading/error có thể stale.

**Cách sửa:** Abort previous request và reset relevant state cho empty query.

### Medium — Abort có thể bị hiển thị như user-facing error

**Vấn đề:** Nếu thêm cancellation nhưng vẫn catch mọi error giống nhau, expected abort sẽ thành alert.

**Tại sao xảy ra:** Cancellation là control flow bình thường trong type-ahead search.

**Ảnh hưởng production:** UI nhấp nháy lỗi khi user chỉ đang gõ.

**Cách sửa:** Phân biệt `AbortError` và không hiển thị nó như search failure.

### Medium — Error message trực tiếp từ runtime không phải UX/error contract tốt

**Vấn đề:** `err.message` được hiển thị thẳng.

**Tại sao xảy ra:** Technical failure representation bị trộn với user messaging.

**Ảnh hưởng production:** UX không ổn định, có thể lộ chi tiết không cần thiết tùy error source.

**Cách sửa:** Log/telemetry technical detail, hiển thị message ổn định cho user và correlation ID nếu support flow cần.

## Phiên bản đề xuất

Thiết kế tốt hơn là API trả highlight dạng structured text. Ví dụ component dưới đây không render raw HTML và hủy request cũ.

```tsx
import { useEffect, useState } from "react";

type HighlightPart = {
  text: string;
  highlighted: boolean;
};

type SearchItem = {
  id: string;
  name: string;
  highlights: HighlightPart[];
};

export function ProductSearch() {
  const [input, setInput] = useState("");
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [items, setItems] = useState<SearchItem[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const timer = window.setTimeout(() => {
      setQuery(input.trim());
    }, 250);

    return () => window.clearTimeout(timer);
  }, [input]);

  useEffect(() => {
    const controller = new AbortController();

    if (!query) {
      setItems([]);
      setLoading(false);
      setError(null);
      return () => controller.abort();
    }

    const load = async () => {
      setLoading(true);
      setError(null);

      const parameters = new URLSearchParams({ q: query, category });

      try {
        const response = await fetch(`/api/search?${parameters}`, {
          signal: controller.signal
        });

        if (!response.ok)
          throw new Error(`Search failed with HTTP ${response.status}`);

        const data: { items: SearchItem[] } = await response.json();
        setItems(data.items);
      } catch (error) {
        if (error instanceof DOMException && error.name === "AbortError")
          return;

        setError("Search is temporarily unavailable.");
      } finally {
        if (!controller.signal.aborted)
          setLoading(false);
      }
    };

    void load();

    return () => controller.abort();
  }, [query, category]);

  return (
    <section>
      <input
        value={input}
        onChange={e => setInput(e.target.value)}
        placeholder="Search products"
      />

      <select
        value={category}
        onChange={e => setCategory(e.target.value)}
      >
        <option value="all">All</option>
        <option value="parts">Parts</option>
      </select>

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}

      <ul>
        {items.map(item => (
          <li key={item.id}>
            <strong>{item.name}</strong>
            <p>
              {item.highlights.map((part, index) =>
                part.highlighted
                  ? <mark key={index}>{part.text}</mark>
                  : <span key={index}>{part.text}</span>
              )}
            </p>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

## Giải thích thiết kế sau khi sửa

Debounce giảm số request phát sinh khi gõ nhanh; `AbortController` xử lý lifecycle của request đã lỗi thời. Hai cơ chế giải quyết hai vấn đề khác nhau. Nếu cần bảo vệ tuyệt đối khỏi stale state trong abstraction phức tạp hơn, có thể thêm request generation guard hoặc dùng data-fetching library với query-key/cancellation semantics đã được hiểu rõ.

Structured highlights giữ escaping mặc định của React và thu hẹp trust boundary. Nếu Elasticsearch/backend hiện chỉ cung cấp HTML highlights, backend có thể chuyển chúng thành representation an toàn hoặc sanitize bằng policy được kiểm thử; lựa chọn phụ thuộc contract hiện tại.

250 ms ở ví dụ là một scenario assumption, không phải universal optimum. Nên xác minh bằng UX requirement, request volume và latency distribution.

## Trade-offs

Debounce làm tăng một ít perceived latency trước khi request bắt đầu. Cancellation không đảm bảo server đã ngừng toàn bộ work nếu request đã tới backend/dependency. Structured highlights làm API contract phức tạp hơn nhưng giảm XSS surface và coupling với HTML. Data-fetching library có thể đơn giản hóa cache/request lifecycle nhưng không nên được thêm chỉ để né hiểu race condition.

## Cách kiểm thử

1. **Frontend integration test:** mock request `car` trả chậm hơn `cars`; UI cuối cùng chỉ được hiển thị `cars`.
2. **Request-volume test:** fake timers và rapid typing để chứng minh debounce giới hạn số calls.
3. **Security test:** payload highlight chứa `<img onerror=...>` hoặc script-like markup phải xuất hiện như text/không execute.
4. **Failure-path test:** `500`, invalid JSON, network failure và abort phải tạo state đúng; abort không hiện error alert.
5. **Playwright E2E:** gõ nhanh, đổi category trong lúc request đang pending và xác nhận UI không quay về stale result.

## Quan sát trong production

Theo dõi frontend search request count/session, abort rate, error rate, latency và stale-response prevention nếu instrument được; backend theo dõi request duration, cancellation, Elasticsearch dependency p95/p99, timeout rate và query volume. Dùng correlation/request ID để nối browser/API/search dependency. Network waterfall và Real User Monitoring giúp phân biệt client amplification với backend latency.

## Câu hỏi phỏng vấn mở rộng

1. Nếu abort request ở browser nhưng Elasticsearch query vẫn tiếp tục chạy, bạn sẽ điều tra và propagate cancellation ở backend thế nào?
2. Nếu muốn cache search results phía client, query key phải chứa những dimensions nào và stale policy nên dựa vào đâu?
3. Nếu business bắt buộc backend trả HTML highlight, bạn đặt sanitization ở server hay client và kiểm chứng policy thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Multi-instance background processing cần một **atomic ownership/claim boundary**; read-then-update không tự tạo exclusivity.
- Database ownership không giải quyết partial failure với external side effects; retry phải đi cùng idempotency hoặc reconciliation.
- Lease phải có expiry/recovery và cần nghĩ tới stale worker/fencing khi ownership thay đổi.
- Frontend async requests có thể hoàn thành out-of-order; request lifecycle phải ngăn stale completion cập nhật state.
- Debounce, cancellation và XSS-safe rendering giải quyết các lớp vấn đề khác nhau; không nên thay thế lẫn nhau.

## Mẫu tư duy cần nhớ

- Xác định transaction/ownership boundary trước khi nói về exactly-once.
- Design retry cùng idempotency và recovery.
- Test crash window, không chỉ happy path.
- Với async UI, luôn hỏi response cũ có thể overwrite state mới không.
- Giữ untrusted data ở dạng structured data và tận dụng escaping mặc định thay vì render raw HTML.
