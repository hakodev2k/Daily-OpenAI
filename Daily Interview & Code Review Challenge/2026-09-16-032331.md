# Câu 1 — EF Core optimistic concurrency: vì sao `SaveChangesAsync` không tự ngăn lost update?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** EF Core, change tracking, optimistic concurrency, SQL, transactions, ASP.NET Core API

## Bối cảnh

Một approval API dùng ASP.NET Core và EF Core. Hai managers có thể mở cùng một request rồi cập nhật gần như đồng thời. Production thỉnh thoảng ghi nhận comment/status của người lưu sau ghi đè thay đổi trước đó mà không có cảnh báo. Team nói rằng “EF Core tracking entity rồi nên `SaveChangesAsync` sẽ biết record đã bị người khác sửa”.

Entity hiện chỉ có `Id`, `Status`, `Comment`, `UpdatedAtUtc`; không có concurrency token. Mỗi HTTP request dùng một scoped `DbContext`. Database là SQL Server. Business muốn phát hiện conflict thay vì silently overwrite, nhưng chưa chốt UX merge/retry.

## Câu hỏi chính

Hãy giải thích EF Core thực sự theo dõi gì trong `DbContext`, SQL update được tạo như thế nào khi không có concurrency token, vì sao hai request độc lập vẫn có thể tạo lost update, và bạn sẽ thiết kế conflict detection/handling ra sao mà không biến mọi conflict thành blind retry?

## Câu hỏi làm rõ nên cân nhắc

1. Hai managers được phép sửa cùng field hay có field ownership khác nhau?
2. API dùng tracked entity load-update hay attach DTO rồi mark modified?
3. Business muốn reject conflict, merge field-level hay cho phép last-write-wins ở một số field?
4. Client có thể round-trip concurrency token không?
5. Có background process nào cũng cập nhật request này không?

## Gợi ý tư duy

### Gợi ý 1

Change tracker chỉ biết state trong lifetime của chính `DbContext`; nó không phải distributed lock.

### Gợi ý 2

Hãy nhìn vào `WHERE` clause của `UPDATE`: điều gì khiến database biết row đã thay đổi kể từ lúc đọc?

### Gợi ý 3

Optimistic concurrency detection và conflict resolution là hai vấn đề khác nhau.

## Cấu trúc trả lời đề xuất

1. Làm rõ business conflict semantics.
2. Giải thích tracking/original/current values.
3. Mô tả SQL khi không có concurrency token.
4. Mô tả interleaving của hai requests.
5. Thêm concurrency token phù hợp.
6. Xử lý `DbUpdateConcurrencyException` theo policy.
7. Test concurrent updates.
8. Quan sát conflict rate trong production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Scoped `DbContext` của request A không biết tracked state của request B.
- Không có concurrency token thì update thường chỉ định danh row bằng key và có thể overwrite giá trị mới hơn.
- Optimistic concurrency cần token/original value tham gia update predicate để zero affected rows trở thành conflict.
- Không blind retry business update vì retry có thể tiếp tục ghi đè quyết định của người khác.

### Điểm cộng

- Phân biệt database transaction isolation với application-level optimistic concurrency.
- Đề xuất token được client round-trip qua DTO/ETag-style contract khi phù hợp.
- Xác định merge policy theo field/business invariant thay vì generic merge.

### Senior+

- Với SQL Server có thể dùng `rowversion` nếu phù hợp schema/provider; với portability có thể dùng application-managed concurrency token.
- Đánh giá bulk/direct update paths vì chúng có thể cần concurrency semantics riêng.
- Telemetry phân biệt genuine conflict với missing/deleted row.

## Hướng giải quyết tham khảo

EF Core change tracker giữ original/current state của entities trong một `DbContext`. Hai HTTP requests có hai contexts độc lập. Nếu cả hai đọc version ban đầu rồi request A save trước, request B vẫn có thể phát update sau đó. Khi không cấu hình concurrency token, database không có predicate đại diện cho “row vẫn ở version tôi đã đọc”.

Một hướng với SQL Server là thêm `rowversion` làm concurrency token:

```csharp
public sealed class ApprovalRequest
{
    public long Id { get; set; }
    public string Status { get; set; } = null!;
    public string? Comment { get; set; }
    public DateTime UpdatedAtUtc { get; set; }
    public byte[] Version { get; set; } = null!;
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<ApprovalRequest>()
        .Property(x => x.Version)
        .IsRowVersion();
}
```

Client phải gửi token của version đã đọc. Khi update, EF Core dùng original concurrency value trong predicate. Nếu row đã đổi, affected rows bằng 0 và EF Core có thể phát `DbUpdateConcurrencyException`.

Sau đó application quyết định: trả conflict cho client để reload/review; merge những field độc lập theo rule; hoặc retry chỉ khi operation thật sự safe/idempotent và business semantics cho phép. Không nên catch exception rồi reload + save lại vô điều kiện vì đó chỉ biến conflict detection thành last-write-wins kín đáo.

## Mẫu trả lời trong phỏng vấn

“EF Core tracking không đồng bộ giữa requests. Mỗi scoped DbContext chỉ biết entity state mà nó đã load. Nếu không có concurrency token, hai managers có thể cùng đọc version cũ; A update trước, B update sau và B vẫn match row theo primary key nên ghi đè. Tôi sẽ làm rõ business muốn reject hay merge conflict. Với SQL Server, rowversion là một lựa chọn tốt nếu phù hợp; token phải round-trip tới client. Khi SaveChanges phát hiện zero rows và ném DbUpdateConcurrencyException, tôi không blind retry. Tôi sẽ reload current state, so sánh với attempted changes và áp policy: 409/conflict UI, field-level merge hoặc retry chỉ cho operation safe. Tôi cũng viết integration test với hai DbContexts và đo conflict rate để biết đây là expected collaboration hay symptom của UX/workflow kém.”

## Câu hỏi đào sâu

1. Nếu chỉ `Comment` được phép merge nhưng `Status` không được phép overwrite, bạn thiết kế resolution thế nào?
2. Nếu API dùng `ExecuteUpdateAsync`, bạn sẽ bảo toàn concurrency semantics ra sao?
3. Tôi đề xuất dùng `Serializable` transaction cho mọi request thay vì concurrency token; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Nghĩ change tracking là cross-request locking.
- Catch concurrency exception rồi retry vô hạn.
- Không round-trip token từ client.
- Nhầm transaction isolation với business conflict detection.
- Chỉ sửa code mà không định nghĩa conflict UX/business rule.

## Thang điểm 0–10

- 0–3: chỉ nói “thêm rowversion” mà không giải thích mechanism.
- 4–6: hiểu tracking/token nhưng conflict handling còn generic.
- 7–8: giải thích SQL predicate, client token, tests và business resolution.
- 9–10: phân tích transaction/isolation, alternate update paths, observability và conditional trade-offs.

# Câu 2 — Production incident: ASP.NET Core API memory tăng và p99 spike khi middleware log request/response body

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core middleware, streams, memory allocation, GC/LOH, security logging, performance, Application Insights

## Bối cảnh

Sau một release bổ sung middleware “full HTTP logging”, API chạy trên Azure App Service bắt đầu có memory working set tăng mạnh trong giờ cao điểm, p99 latency spike và đôi lúc instance restart. Middleware buffer request/response body để log JSON phục vụ support. Một số endpoints upload payload vài MB và một endpoint export response lớn.

CPU trung bình không quá cao. GC telemetry chưa được phân tích. Log volume tăng đáng kể. Middleware có thể chứa PII/authentication data. Team đề xuất tăng memory tier ngay lập tức.

Chưa có bằng chứng middleware là nguyên nhân duy nhất; release còn vài thay đổi khác.

## Câu hỏi chính

Bạn sẽ xử lý incident từ stabilization đến root cause như thế nào? Hãy đưa ra competing hypotheses, evidence cần thu thập, cách xác minh allocation/buffering behavior, security impact của body logging, và thiết kế logging thay thế phù hợp production.

## Câu hỏi làm rõ nên cân nhắc

1. Middleware buffer bằng `MemoryStream`, string hay request buffering API nào?
2. Có size/content-type exclusions và sampling không?
3. Memory tăng là managed heap, native/process memory hay log exporter queue?
4. Restart do memory limit, health failure hay platform event?
5. Endpoint nào đóng góp nhiều nhất theo payload size/request rate?

## Gợi ý tư duy

### Gợi ý 1

Stabilize trước: có thể tắt/giảm full-body logging bằng config nếu reversible.

### Gợi ý 2

Đừng kết luận từ working set. Correlate allocation rate, Gen2/LOH, GC pause, request size, response size và logging/export telemetry.

### Gợi ý 3

Full-body logging là cả performance problem lẫn data-governance/security problem.

## Cấu trúc trả lời đề xuất

1. Xác định impact và timeline release.
2. Stabilize bằng feature flag/config/rollback phù hợp.
3. So sánh affected/unaffected instances/endpoints.
4. Thu thập memory/GC/allocation/log telemetry.
5. Form nhiều hypotheses.
6. Reproduce bằng load test với payload distributions thực tế.
7. Xác minh bằng profiler/dump khi cần.
8. Thiết kế bounded/redacted logging.
9. Test security/performance/failure path.
10. Thêm dashboard/alerts/regression gate.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định scale-up là RCA.
- Tắt/giảm body logging là stabilization hợp lý nếu change correlation mạnh và reversible.
- Đo managed allocation, heap/LOH/GC, working set, request/response sizes và exporter/backpressure.
- Không log secrets, authorization headers hoặc PII body một cách mặc định.

### Điểm cộng

- Nhận ra buffering có thể phá streaming semantics và nhân đôi memory copies.
- Phân loại endpoint/content type thay vì one-size-fits-all middleware.
- Structured metadata thường hữu ích hơn raw body: route, status, duration, size, correlation ID, safe business identifiers.

### Senior+

- Đề xuất bounded capture chỉ cho diagnostic sampling có explicit redaction/access/retention policy.
- Dùng load test và allocation profiler để chứng minh delta trước/sau.
- Đánh giá telemetry exporter queue/backpressure như competing hypothesis.

## Hướng giải quyết tham khảo

Đầu tiên correlate release timestamp với memory/p99/restarts. Nếu middleware có config switch, giảm hoặc tắt body capture ngay để ổn định; giữ metadata logging. Nếu rollback toàn release có risk lớn hơn, feature-level mitigation tốt hơn.

Thu thập App Service metrics, Application Insights request/dependency telemetry và .NET runtime metrics: allocation rate, GC heap size, Gen2 collections, pause time và LOH khi có. Phân nhóm theo endpoint/request size. Nếu cần, dùng profiler/dump theo operational policy để xem dominant object types/retention roots. Đồng thời kiểm tra log exporter buffering và ingestion throttling.

Một middleware đọc request vào memory rồi thay response stream bằng `MemoryStream`, sau đó convert thành string có thể tạo nhiều copies cho payload lớn. Nhưng reference answer không nên giả định implementation chưa thấy; cần inspect code/profiler để xác nhận.

Production logging nên mặc định metadata-first. Body capture chỉ cho payload nhỏ/content type cho phép, bounded, sampled, redacted và có explicit policy. Upload/download/streaming endpoints thường nên exclude. Sensitive headers/tokens/passwords/payment/PII phải được loại bỏ theo data policy.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ coi middleware là leading hypothesis vì incident bắt đầu sau release, nhưng chưa kết luận. Nếu có feature flag tôi tắt full-body capture để stabilize rồi so p99/memory. Tôi phân tích allocation rate, managed heap, Gen2/LOH, GC pause, request size và log exporter queue; working set một mình chưa đủ. Tôi cũng xem endpoint nào có upload/export lớn vì buffering có thể tạo nhiều copies và phá streaming. Về security, raw body logging có thể chứa PII hoặc credentials nên tôi chuyển sang metadata-first structured logs, body capture chỉ bounded/sampled/redacted cho diagnostic cases. Sau fix tôi chạy load test với payload distribution thực, so allocation/p99 trước-sau và thêm guardrail để logging change không tái tạo regression.”

## Câu hỏi đào sâu

1. Nếu heap dump không cho thấy retained large objects nhưng allocation rate rất cao, bạn diễn giải thế nào?
2. Nếu support nói bắt buộc cần body để điều tra một API nhạy cảm, bạn thiết kế controlled diagnostic mode ra sao?
3. Tôi đề xuất tăng App Service memory gấp đôi và giữ middleware nguyên trạng; khi nào giải pháp đó có thể chấp nhận tạm thời?

## Lỗi trả lời thường gặp

- Kết luận memory leak chỉ từ working set.
- Tăng tier rồi coi incident đã giải quyết.
- Log raw request/response mà không xem PII/secrets.
- Không phân biệt buffering với streaming.
- Không đo allocation/GC trước khi tối ưu.

## Thang điểm 0–10

- 0–3: chỉ đề xuất scale/rollback.
- 4–6: có metrics và logging fix nhưng thiếu competing hypotheses.
- 7–8: incident reasoning đầy đủ, security + performance + validation.
- 9–10: phân tích allocation/retention/exporter behavior, controlled diagnostics và regression prevention.

# Câu 3 — Thiết kế dịch vụ upload file lớn: backend proxy hay direct-to-Blob?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, security, API design, reliability, large-file transfer, observability

## Bối cảnh

Một enterprise portal cần cho users upload tài liệu từ vài KB tới nhiều GB. Hiện request đi qua ASP.NET Core API rồi API ghi vào Azure Blob Storage. Khi file lớn tăng, App Service bandwidth/connection duration và failure rate trở thành concern.

Team cân nhắc cho browser upload trực tiếp tới Blob bằng short-lived delegated access, nhưng security lo quyền truy cập, file validation và việc client báo “upload thành công” dù business record chưa hoàn tất. Một số tài liệu cần malware scanning trước khi được tải xuống.

Không có requirement rằng mọi file phải đi qua application process. Hệ thống phải giữ authorization theo user/business entity và không public container.

## Câu hỏi chính

Hãy thiết kế upload architecture và API contract. So sánh backend proxy với direct-to-Blob, mô tả authorization, temporary upload permission, metadata/state machine, large-file retry/resume, scanning/quarantine, cleanup, consistency và observability. Khi nào bạn vẫn chọn proxy?

## Câu hỏi làm rõ nên cân nhắc

1. File size distribution và concurrent uploads thực tế là bao nhiêu?
2. Browser/mobile clients có cần resumable/chunked upload không?
3. Malware scan là synchronous gate hay asynchronous workflow?
4. Business record phải tồn tại trước upload hay có thể ở trạng thái Pending?
5. Retention, encryption, legal/compliance và download authorization requirements là gì?

## Gợi ý tư duy

### Gợi ý 1

Tách control plane (authorization/metadata) khỏi data plane (bytes) nếu điều đó giảm tải mà vẫn giữ security boundary.

### Gợi ý 2

“Blob tồn tại” không đồng nghĩa “business upload hoàn tất và được phép sử dụng”.

### Gợi ý 3

Thiết kế explicit state machine và cleanup cho abandoned/failed uploads.

## Cấu trúc trả lời đề xuất

1. Làm rõ file/security/SLA requirements.
2. So sánh proxy/direct data path.
3. Thiết kế create-upload-session API.
4. Giới hạn quyền và lifetime của delegated access.
5. Thiết kế upload states.
6. Verify completion server-side.
7. Scan/quarantine/publish workflow.
8. Retry/resume/cleanup.
9. Test abuse/failure paths.
10. Monitor end-to-end upload funnel.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Authorization quyết định ở backend trước khi cấp quyền upload.
- Delegated permission phải scope hẹp, thời gian ngắn, đúng object/path và operation cần thiết.
- Client callback không phải source of truth duy nhất; backend verify blob/metadata theo contract.
- File chưa scan không được coi là safe/available nếu scanning là requirement.

### Điểm cộng

- State machine ví dụ: Pending → Uploaded → Scanning → Ready/Rejected/Failed/Expired.
- Cleanup abandoned uploads và orphan business records.
- Content type/name do client cung cấp không phải trusted security signal.

### Senior+

- Tách immutable blob identifier khỏi original filename.
- Cân nhắc event-driven scanning nhưng không bắt buộc messaging nếu synchronous/simple flow đáp ứng scale.
- Thiết kế download authorization riêng; không reuse upload credential.

## Hướng giải quyết tham khảo

Với file lớn và nhiều concurrent uploads, direct-to-Blob thường giảm việc application server proxy toàn bộ bytes. Backend vẫn là control plane: user gọi `POST /upload-sessions`, backend authorize business entity, tạo upload record `Pending`, sinh blob key server-controlled và cấp temporary permission chỉ cho object/operation/lifetime cần thiết theo cơ chế Azure được project xác minh từ official docs.

Client upload bytes trực tiếp. Sau đó client gọi complete endpoint hoặc backend nhận trusted storage event tùy architecture. Backend phải verify blob tồn tại và các properties cần thiết trước khi chuyển state. Nếu malware scanning bắt buộc, blob ở quarantine/container/path không được phục vụ download cho tới khi scan pass. Scan fail chuyển `Rejected`; abandoned session được lifecycle/cleanup job xử lý.

Không nên coi original filename/content type là authorization. Download endpoint kiểm tra quyền business hiện tại rồi cấp controlled read access hoặc stream tùy requirement.

Proxy vẫn hợp lý nếu files nhỏ, traffic thấp, application cần transform/inspect bytes synchronously, client không thể truy cập storage endpoint, hoặc compliance/network policy bắt buộc data đi qua service. Cost of complexity của direct upload phải được cân với measured load.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách control plane khỏi data plane nếu file nhiều GB và proxy đang là bottleneck. Backend vẫn authorize user/entity, tạo upload session và blob key do server kiểm soát, sau đó cấp quyền upload ngắn hạn chỉ cho đúng object và operation. Client upload trực tiếp nhưng không được tự tuyên bố business success; complete flow phải verify blob rồi chuyển state. Nếu cần malware scan, file ở quarantine với state Uploaded/Scanning và chỉ Ready mới được download. Tôi cũng có expiry/cleanup cho abandoned uploads, retry/resume cho file lớn và telemetry cho từng state. Tôi vẫn chọn backend proxy nếu file nhỏ, volume thấp hoặc application/compliance bắt buộc inspect bytes inline, vì direct upload thêm state/security complexity không phải lúc nào cũng đáng.”

## Câu hỏi đào sâu

1. Nếu user có upload permission rồi bị revoke quyền business trước khi upload hoàn tất, complete endpoint phải xử lý thế nào?
2. Nếu storage event được deliver duplicate hoặc out of order, state transition cần đặc tính gì?
3. Tôi đề xuất public container với unguessable GUID để đơn giản hóa download; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Cấp storage credential quá rộng hoặc quá lâu.
- Tin client nói upload thành công mà không verify.
- Cho download trước malware scan.
- Không có cleanup cho abandoned uploads.
- Mặc định direct upload luôn tốt hơn dù workload nhỏ.

## Thang điểm 0–10

- 0–3: chỉ nói “dùng SAS/direct upload”.
- 4–6: có auth và upload flow nhưng thiếu failure/state semantics.
- 7–8: state machine, scanning, cleanup, testing, observability và trade-offs đầy đủ.
- 9–10: phân tích control/data plane, revocation/race, compliance và điều kiện chọn proxy rõ ràng.
