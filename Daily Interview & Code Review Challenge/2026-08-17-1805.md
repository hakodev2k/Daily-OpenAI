# Code Review Challenge 1 — Background Job xử lý đơn hàng bị chạy trùng trong production

**Chủ đề:** Hangfire, idempotency, concurrency, EF Core transaction
**Độ khó:** Senior+
**Thời gian review đề xuất:** 35 phút
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một hệ thống xử lý thanh toán dùng ASP.NET Core + Hangfire. Job được chạy lại khi worker restart hoặc khi gặp exception. Production xuất hiện tình trạng một số khách hàng bị gửi email xác nhận nhiều lần và trạng thái thanh toán bị cập nhật lặp.

Yêu cầu:
- Payment phải chỉ được xử lý một lần theo business key.
- Email có thể retry nhưng không được gửi trùng không kiểm soát.
- Hệ thống chạy nhiều worker instance.

## Đoạn code cần review

```csharp
public class PaymentJob
{
    private readonly AppDbContext _db;
    private readonly IEmailService _email;

    public PaymentJob(AppDbContext db, IEmailService email)
    {
        _db = db;
        _email = email;
    }

    public async Task ProcessAsync(Guid paymentId)
    {
        var payment = await _db.Payments
            .FirstAsync(x => x.Id == paymentId);

        if (payment.Status == PaymentStatus.Completed)
            return;

        payment.Status = PaymentStatus.Completed;
        payment.CompletedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        await _email.SendAsync(payment.CustomerEmail,
            "Payment completed");
    }
}
```

## Nhiệm vụ của ứng viên

1. Tìm correctness, concurrency và reliability issues.
2. Giải thích production impact.
3. Đề xuất thiết kế retry an toàn.
4. Nêu cách test race condition và duplicate execution.
5. Đề xuất logs, metrics cần theo dõi.

## Câu hỏi gợi mở

- Hai worker cùng đọc một payment chưa completed thì điều gì xảy ra?
- Nếu email fail sau khi DB commit thì sao?
- Có thể retry toàn bộ job không?
- Business key nào cần dùng để chống duplicate?

## Gợi ý

### Gợi ý 1

Tách trạng thái business khỏi side effect bên ngoài.

### Gợi ý 2

Cần idempotency key, concurrency control và trạng thái xử lý bền vững.

## Kết quả code review tham khảo

- Không có concurrency control: nhiều worker có thể cùng xử lý một payment.
- Email gửi sau commit DB nhưng không có retry state.
- Retry Hangfire có thể gây duplicate email.
- Thiếu transaction/invariant bảo vệ trạng thái.
- Không có idempotency record.
- Thiếu structured logging theo operation id.

**Severity cao nhất:** Critical

## Phiên bản code đề xuất

Thiết kế nên gồm:

- Payment state transition có optimistic concurrency hoặc atomic update.
- Transaction ghi payment update và outbox message.
- Worker gửi email đọc outbox với retry + deduplication.

## Trade-offs

Outbox tăng độ phức tạp vận hành nhưng đổi lại đảm bảo recovery và audit tốt hơn.

## Cách kiểm thử

1. Hai worker xử lý cùng payment.
2. Email service timeout.
3. Worker crash sau DB commit.
4. Retry job nhiều lần.

## Quan sát production

- Payment processing duration.
- Duplicate execution count.
- Outbox backlog.
- Email delivery failure rate.

# Code Review Challenge 2 — EF Core query gây tải database khi dữ liệu tăng

**Chủ đề:** EF Core query execution, performance, memory allocation
**Độ khó:** Senior
**Thời gian review đề xuất:** 30 phút
**Số vấn đề cần tìm:** Khoảng 6 vấn đề

## Bối cảnh

API báo cáo lấy danh sách đơn hàng theo ngày. Khi dữ liệu tăng lên vài triệu record, API timeout và memory tăng cao.

## Đoạn code cần review

```csharp
public async Task<List<OrderDto>> GetOrders(DateTime from, DateTime to)
{
    var orders = await _db.Orders.ToListAsync();

    return orders
        .Where(x => x.CreatedAt >= from && x.CreatedAt <= to)
        .Select(x => new OrderDto
        {
            Id = x.Id,
            Customer = x.Customer.Name,
            Amount = x.Total
        })
        .ToList();
}
```

## Nhiệm vụ của ứng viên

1. Xác định vấn đề query execution.
2. Phân tích database và memory impact.
3. Đề xuất cải tiến.
4. Nêu cách benchmark và kiểm thử.

## Câu hỏi gợi mở

- Filter đang chạy ở database hay application?
- EF Core tracking có cần thiết không?
- Điều gì xảy ra khi bảng tăng 10 lần?
- Có cần pagination không?

## Gợi ý

### Gợi ý 1

Kiểm tra nơi thực thi LINQ expression.

### Gợi ý 2

Projection và AsNoTracking có thể giảm tải đáng kể.

## Kết quả code review tham khảo

- Toàn bộ bảng bị load vào memory trước khi filter.
- EF Core tracking không cần thiết cho read-only query.
- Không pagination.
- Projection nên thực hiện trong SQL.
- Thiếu index consideration.

**Severity cao nhất:** High

## Phiên bản code đề xuất

```csharp
public async Task<List<OrderDto>> GetOrders(DateTime from, DateTime to)
{
    return await _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from && x.CreatedAt <= to)
        .Select(x => new OrderDto
        {
            Id = x.Id,
            Customer = x.Customer.Name,
            Amount = x.Total
        })
        .Take(1000)
        .ToListAsync();
}
```

## Cách kiểm thử

- Compare SQL generated.
- Load test với dữ liệu lớn.
- Measure memory allocation.
- Verify index usage.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Database transaction không thể bao phủ external side effects.
- Retry phải đi cùng idempotency.
- EF Core cần hiểu query execution location.
- Observability là một phần của design.

## Mẫu tư duy cần nhớ

- Clarify business invariant trước khi code.
- Measure trước khi optimize.
- Stabilize trước khi investigate.
- Design retry cùng với idempotency.
- Validate output và side effect một cách deterministic.
