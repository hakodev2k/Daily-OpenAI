# Code Review Challenge 1 — RabbitMQ consumer `Ack` quá sớm làm mất message, nhưng retry lại có thể tạo side effect trùng

**Chủ đề:** Messaging, idempotency, transaction handling, background processing, failure recovery, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một worker .NET nhận message `EmployeeOffboardingRequested` từ RabbitMQ để thực hiện quy trình offboarding. Mỗi message cần:

- cập nhật trạng thái employee trong database,
- ghi `OffboardingHistory`,
- enqueue một Hangfire job xử lý bước tiếp theo,
- sau đó mới coi message là xử lý thành công.

Hệ thống chạy trên nhiều instance. Production ghi nhận hai loại lỗi trái ngược:

- đôi lúc message biến mất nhưng database chưa cập nhật,
- đôi lúc cùng một employee có hai history record và hai Hangfire job giống nhau,
- lỗi thường xuất hiện khi database timeout, worker restart hoặc network chập chờn,
- log chỉ cho biết `Processing message`, không có delivery tag/message id/correlation id đủ để lần theo.

RabbitMQ có thể redeliver message nếu consumer mất kết nối trước khi message được ack. Business yêu cầu quy trình có thể retry nhưng không được tạo duplicate business effect.

## Đoạn code cần review

```csharp
public sealed class OffboardingConsumer
{
    private readonly IModel _channel;
    private readonly AppDbContext _db;
    private readonly IBackgroundJobClient _jobs;
    private readonly ILogger<OffboardingConsumer> _logger;

    public OffboardingConsumer(
        IModel channel,
        AppDbContext db,
        IBackgroundJobClient jobs,
        ILogger<OffboardingConsumer> logger)
    {
        _channel = channel;
        _db = db;
        _jobs = jobs;
        _logger = logger;
    }

    public async Task HandleAsync(
        BasicDeliverEventArgs delivery,
        CancellationToken cancellationToken)
    {
        var message = JsonSerializer.Deserialize<EmployeeOffboardingRequested>(
            delivery.Body.Span)!;

        _channel.BasicAck(delivery.DeliveryTag, multiple: false);

        _logger.LogInformation(
            "Processing offboarding for employee {EmployeeId}",
            message.EmployeeId);

        var employee = await _db.Employees
            .SingleAsync(x => x.Id == message.EmployeeId, cancellationToken);

        if (employee.Status == EmployeeStatus.Inactive)
            return;

        employee.Status = EmployeeStatus.Inactive;

        _db.OffboardingHistories.Add(new OffboardingHistory
        {
            EmployeeId = employee.Id,
            Reason = message.Reason,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _jobs.Enqueue<OffboardingJob>(
            x => x.RunAsync(employee.Id, CancellationToken.None));
    }
}
```

## Gợi ý

### Gợi ý 1

Phân tích từng boundary riêng: **message broker → database → background-job storage**. Mỗi boundary có thể thành công hoặc thất bại độc lập.

### Gợi ý 2

## Kết quả code review tham khảo

### 1. Ack message trước khi business transaction hoàn tất

**Problem:** `BasicAck` được gọi ngay sau deserialize.  
**Why it happens:** Broker được báo rằng message đã xử lý thành công trước khi database được cập nhật.  
**Production impact:** Nếu DB timeout, process crash hoặc code ném exception sau ack, message không còn được redeliver và business event bị mất.  
**Severity:** Critical  
**Recommended fix:** Chỉ ack sau khi durable processing thành công; nếu xử lý thất bại thì nack/requeue hoặc đưa sang retry/dead-letter flow theo policy.

### 2. Không có idempotency key/inbox record

**Problem:** Consumer không lưu `MessageId` hoặc operation id đã xử lý.  
**Why it happens:** Code giả định mỗi message chỉ chạy một lần.  
**Production impact:** Redelivery hoặc duplicate publish có thể tạo duplicate history/job.  
**Severity:** Critical  
**Recommended fix:** Dùng message id ổn định và unique constraint ở bảng inbox/process log; toàn bộ thay đổi DB chỉ commit nếu message chưa được xử lý.

### 3. Check `employee.Status` không đủ để bảo đảm idempotency

**Problem:** Hai consumer có thể cùng đọc `Active` trước khi một bên commit.  
**Why it happens:** Check-then-act không atomic và không có concurrency control.  
**Production impact:** Hai history record có thể cùng được insert; state cuối vẫn `Inactive` nhưng side effect bị duplicate.  
**Severity:** High  
**Recommended fix:** Bảo vệ invariant bằng transaction + unique business key/concurrency token hoặc atomic state transition.

### 4. Database commit và Hangfire enqueue không atomic

**Problem:** `SaveChangesAsync` thành công nhưng `_jobs.Enqueue` có thể thất bại.  
**Why it happens:** Hai durable store khác nhau được cập nhật tuần tự.  
**Production impact:** Employee đã inactive nhưng workflow tiếp theo không bao giờ chạy.  
**Severity:** High  
**Recommended fix:** Lưu một outbox/work-item record trong cùng DB transaction rồi để dispatcher enqueue Hangfire sau; dispatcher phải retry idempotently.

### 5. Không có transaction cho inbox + state + history + outbox

**Problem:** Các thay đổi logic liên quan chưa được mô hình hóa thành một đơn vị commit rõ ràng.  
**Why it happens:** `SaveChangesAsync` hiện chỉ commit entity changes nhưng không có inbox/outbox để ràng buộc delivery semantics.  
**Production impact:** Khó chứng minh event đã được xử lý exactly-once ở mức business effect.  
**Severity:** High  
**Recommended fix:** Trong một DB transaction: insert inbox key, transition employee, insert history, insert outbox; commit xong mới ack broker.

### 6. Deserialization failure không có poison-message policy

**Problem:** Deserialize dùng null-forgiving operator và không có handling.  
**Why it happens:** Payload invalid có thể ném exception trước khi policy xử lý được áp dụng.  
**Production impact:** Message có thể retry vô hạn hoặc bị xử lý không nhất quán tùy consumer wrapper.  
**Severity:** Medium  
**Recommended fix:** Validate schema, bắt lỗi parse, đưa poison message sang DLQ hoặc quarantine với reason rõ ràng.

### 7. `CancellationToken.None` được truyền vào job payload/call expression

**Problem:** Job step tiếp theo bị tách khỏi cancellation semantics hiện tại theo cách không có chủ đích rõ ràng.  
**Why it happens:** Cancellation token của request/consumer không phù hợp để serialize làm durable job, nhưng code cũng chưa định nghĩa cancellation riêng cho job.  
**Production impact:** Khó quản lý shutdown/cancel workflow đúng cách.  
**Severity:** Medium  
**Recommended fix:** Thiết kế cancellation của durable job riêng; không serialize runtime token như business input.

### 8. Observability thiếu message identity và delivery context

**Problem:** Log chỉ có employee id.  
**Why it happens:** Không ghi message id, redelivery flag, correlation id, attempt hoặc outcome.  
**Production impact:** Khó điều tra duplicate/lost processing và xác định failure nằm ở broker, DB hay dispatcher.  
**Severity:** Medium  
**Recommended fix:** Structured logging/tracing với `MessageId`, `CorrelationId`, employee id, redelivery flag, processing outcome và latency.

## Phiên bản code đề xuất

```csharp
public sealed class OffboardingConsumer
{
    private readonly IModel _channel;
    private readonly AppDbContext _db;
    private readonly ILogger<OffboardingConsumer> _logger;

    public OffboardingConsumer(
        IModel channel,
        AppDbContext db,
        ILogger<OffboardingConsumer> logger)
    {
        _channel = channel;
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        BasicDeliverEventArgs delivery,
        CancellationToken cancellationToken)
    {
        EmployeeOffboardingRequested message;

        try
        {
            message = JsonSerializer.Deserialize<EmployeeOffboardingRequested>(
                delivery.Body.Span)
                ?? throw new JsonException("Message body is null");
        }
        catch (JsonException ex)
        {
            _logger.LogWarning(ex, "Invalid offboarding message");
            _channel.BasicNack(delivery.DeliveryTag, false, requeue: false);
            return;
        }

        var messageId = message.MessageId;

        try
        {
            await using var tx = await _db.Database
                .BeginTransactionAsync(cancellationToken);

            var alreadyProcessed = await _db.InboxMessages
                .AnyAsync(x => x.MessageId == messageId, cancellationToken);

            if (!alreadyProcessed)
            {
                var employee = await _db.Employees
                    .SingleAsync(x => x.Id == message.EmployeeId, cancellationToken);

                if (employee.Status != EmployeeStatus.Inactive)
                {
                    employee.Status = EmployeeStatus.Inactive;

                    _db.OffboardingHistories.Add(new OffboardingHistory
                    {
                        EmployeeId = employee.Id,
                        Reason = message.Reason,
                        CreatedAt = DateTime.UtcNow
                    });
                }

                _db.OutboxMessages.Add(OutboxMessage.For(
                    "OffboardingJobRequested",
                    new { message.EmployeeId }));

                _db.InboxMessages.Add(new InboxMessage
                {
                    MessageId = messageId,
                    ProcessedAt = DateTime.UtcNow
                });

                await _db.SaveChangesAsync(cancellationToken);
                await tx.CommitAsync(cancellationToken);
            }

            _channel.BasicAck(delivery.DeliveryTag, false);
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Failed offboarding message {MessageId} for employee {EmployeeId}",
                messageId,
                message.EmployeeId);

            _channel.BasicNack(delivery.DeliveryTag, false, requeue: true);
        }
    }
}
```

> Giả định `InboxMessages.MessageId` có unique constraint. Outbox dispatcher chạy độc lập, đọc các record chưa publish/enqueue, thực hiện retry và đánh dấu hoàn tất theo cách idempotent.

## Trade-offs

- Inbox/outbox thêm table, cleanup policy và dispatcher nhưng đổi lại failure semantics rõ ràng hơn đáng kể.
- Ack sau DB commit có thể dẫn tới redelivery nếu broker connection chết ngay trước ack; inbox biến redelivery đó thành harmless duplicate.
- Requeue mọi exception vô hạn là không tốt; cần retry count/backoff/DLQ cho lỗi không transient.
- Nếu Hangfire và business data dùng cùng một transactional storage theo cơ chế được framework hỗ trợ, có thể có lựa chọn khác; vẫn cần chứng minh atomicity và idempotency thay vì giả định.

## Cách kiểm thử

1. **Failure-path test:** DB fail sau khi message nhận nhưng trước commit; message phải chưa được ack và có thể retry.
2. **Crash test:** Commit DB xong nhưng giả lập crash trước ack; message redeliver nhưng không được tạo history/outbox trùng.
3. **Concurrency test:** Hai consumer xử lý cùng `MessageId` đồng thời; unique inbox key phải bảo vệ duplicate effect.
4. **Outbox test:** Dispatcher fail khi enqueue job rồi retry; cuối cùng chỉ tạo một logical workflow tiếp theo.
5. **Poison-message test:** Payload invalid đi vào DLQ/quarantine, không retry vô hạn.

## Quan sát trong production

- Metric: processed, duplicate, retry, nack, DLQ count, processing latency, outbox backlog.
- Log: `MessageId`, `CorrelationId`, employee id, delivery/redelivery flag, attempt, outcome.
- Trace: span cho consumer → DB transaction → outbox dispatcher → Hangfire enqueue.
- Alert khi outbox backlog tăng, retry rate tăng hoặc DLQ có message mới.
- Database observation: unique-constraint violations ở inbox có thể là tín hiệu duplicate delivery bình thường nhưng cần đo được.

## Câu hỏi phỏng vấn mở rộng

2. Nếu không muốn dùng outbox, bạn chấp nhận failure window nào và xử lý reconciliation ra sao?
3. Khi nào nên `Nack(requeue: false)` thay vì retry?

# Code Review Challenge 2 — SignalR Hub tin `tenantId` từ client và phát dữ liệu sang tenant khác

**Chủ đề:** Authentication & authorization, multi-tenancy, SignalR, input validation, sensitive-data exposure, connection lifecycle  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một portal nội bộ dùng SignalR để hiển thị real-time notification. Sau khi kết nối, client gọi `JoinTenant(tenantId)` để tham gia group tương ứng. Backend sau đó publish notification theo tenant bằng `Clients.Group(...)`.

Hệ thống có hàng trăm tenant. User được xác thực bằng bearer token; claim `tenant_id` đã có trong identity. Production security review phát hiện một user có thể sửa JavaScript trên browser và tự gọi `JoinTenant` với tenant id khác.

Ngoài ra:

- user có thể join nhiều group trong cùng connection,
- notification đôi lúc chứa employee name, email và trạng thái workflow,
- khi quyền user bị revoke, connection đang mở có thể tiếp tục tồn tại thêm một thời gian,
- team đang log cả notification payload để debug.

Business yêu cầu tenant isolation phải được enforce ở server; client input không được quyết định security boundary.

## Đoạn code cần review

```csharp
[Authorize]
public sealed class NotificationHub : Hub
{
    private readonly ILogger<NotificationHub> _logger;

    public NotificationHub(ILogger<NotificationHub> logger)
    {
        _logger = logger;
    }

public sealed class NotificationPublisher
{
    private readonly IHubContext<NotificationHub> _hub;
    private readonly ILogger<NotificationPublisher> _logger;

    public NotificationPublisher(
        IHubContext<NotificationHub> hub,
        ILogger<NotificationPublisher> logger)
    {
        _hub = hub;
        _logger = logger;
    }

    public async Task PublishAsync(
        Guid tenantId,
        EmployeeNotification notification,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Publishing {@Notification} to tenant {TenantId}",
            notification,
            tenantId);

        await _hub.Clients
            .Group($"tenant:{tenantId}")
            .SendAsync("employeeNotification", notification, cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### 1. Client kiểm soát trực tiếp tenant group

**Problem:** `JoinTenant(string tenantId)` nhận tenant id từ client rồi join ngay.  
**Why it happens:** Group name được coi là routing detail thay vì security boundary.  
**Production impact:** User hợp lệ có thể join group tenant khác và nhận dữ liệu cross-tenant.  
**Severity:** Critical  
**Recommended fix:** Suy ra tenant từ authenticated claims/server-side membership, hoặc authorize explicit tenant resource trước khi add group.

### 2. `[Authorize]` chỉ xác thực caller, chưa authorize resource

**Problem:** Bất kỳ authenticated user nào cũng gọi được method với tenant tùy ý.  
**Why it happens:** Authentication và authorization bị đánh đồng.  
**Production impact:** Tenant isolation bị phá dù endpoint có `[Authorize]`.  
**Severity:** Critical  
**Recommended fix:** Policy/resource authorization theo tenant membership; không tin `tenantId` từ UI.

### 3. User có thể join nhiều tenant group trong cùng connection

**Problem:** Không có guard giới hạn group membership theo identity hiện tại.  
**Why it happens:** Hub không lưu hoặc kiểm tra allowed tenant set.  
**Production impact:** Một connection có thể subscribe dữ liệu ngoài phạm vi được cấp.  
**Severity:** High  
**Recommended fix:** Với single-tenant user, tự join đúng group trong `OnConnectedAsync`; với multi-tenant user, validate mỗi tenant server-side và chỉ cho phép membership được authorize.

### 4. Connection dài hạn có thể giữ quyền cũ

**Problem:** Authorization được đánh giá lúc kết nối/call nhưng quyền có thể bị revoke sau đó.  
**Why it happens:** Long-lived connection không tự nhiên phản ánh mọi thay đổi policy ngay lập tức.  
**Production impact:** User bị thu hồi quyền vẫn có thể tiếp tục nhận notification cho tới khi connection kết thúc hoặc được revalidated.  
**Severity:** High  
**Recommended fix:** Định nghĩa revocation strategy: disconnect user, revalidate membership cho operation nhạy cảm, rút ngắn token/session lifetime phù hợp, hoặc có server-side connection registry để terminate connection khi revoke.

### 5. Log toàn bộ notification payload

**Problem:** Structured log ghi toàn bộ `EmployeeNotification`.  
**Why it happens:** Debug logging không có data-classification/redaction policy.  
**Production impact:** Email, tên nhân viên hoặc workflow data có thể bị lưu trong log ngoài retention/access policy mong muốn.  
**Severity:** High  
**Recommended fix:** Log notification id/type/tenant/outcome; redaction hoặc không log PII nếu không cần.

### 6. Tenant id trong publisher phải đến từ trusted business context

**Problem:** Publisher nhận `tenantId` như tham số bình thường; code không thể hiện nguồn dữ liệu đáng tin.  
**Why it happens:** Security assumption nằm ngoài method contract.  
**Production impact:** Nếu upstream truyền tenant sai, message vẫn đi đúng group name nhưng sai security domain.  
**Severity:** Medium  
**Recommended fix:** Thiết kế command/event chứa tenant id đã được xác lập từ domain/persistence context; validate invariant trước publish.

### 7. Không có audit/metric cho denied join hoặc suspicious tenant switching

**Problem:** Chỉ log successful join.  
**Why it happens:** Security telemetry chưa được thiết kế.  
**Production impact:** Khó phát hiện probing cross-tenant hoặc authorization regression.  
**Severity:** Medium  
**Recommended fix:** Metric/log cho authorization denied, invalid tenant attempts, connection count theo tenant và revoke/disconnect events.

### 8. Payload gửi ra client chưa thể hiện data minimization

**Problem:** `EmployeeNotification` có thể chứa nhiều field hơn UI thật sự cần.  
**Why it happens:** Domain object dễ bị dùng trực tiếp làm transport DTO.  
**Production impact:** Nếu authorization bug xảy ra, blast radius dữ liệu lớn hơn; ngay cả đúng tenant cũng có thể expose field không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Dùng notification DTO tối thiểu theo use case và role; tránh gửi PII không cần thiết.

## Phiên bản code đề xuất

```csharp
[Authorize]
public sealed class NotificationHub : Hub
{
    private readonly ITenantMembershipService _membership;
    private readonly ILogger<NotificationHub> _logger;

    public NotificationHub(
        ITenantMembershipService membership,
        ILogger<NotificationHub> logger)
    {
        _membership = membership;
        _logger = logger;
    }

    public override async Task OnConnectedAsync()
    {
        var userId = Context.User?.FindFirst("sub")?.Value
            ?? throw new HubException("Missing user identity");

        var tenants = await _membership.GetAllowedTenantIdsAsync(
            userId,
            Context.ConnectionAborted);

        foreach (var tenantId in tenants)
        {
            await Groups.AddToGroupAsync(
                Context.ConnectionId,
                $"tenant:{tenantId}",
                Context.ConnectionAborted);
        }

        _logger.LogInformation(
            "Connection {ConnectionId} authorized for {TenantCount} tenant groups",
            Context.ConnectionId,
            tenants.Count);

        await base.OnConnectedAsync();
    }
}

public sealed record EmployeeNotificationDto(
    Guid NotificationId,
    string Type,
    string Status,
    DateTime CreatedAt);

public sealed class NotificationPublisher
{
    private readonly IHubContext<NotificationHub> _hub;
    private readonly ILogger<NotificationPublisher> _logger;

    public NotificationPublisher(
        IHubContext<NotificationHub> hub,
        ILogger<NotificationPublisher> logger)
    {
        _hub = hub;
        _logger = logger;
    }

    public async Task PublishAsync(
        Guid tenantId,
        EmployeeNotificationDto notification,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Publishing notification {NotificationId} type {Type} to tenant {TenantId}",
            notification.NotificationId,
            notification.Type,
            tenantId);

        await _hub.Clients
            .Group($"tenant:{tenantId}")
            .SendAsync("employeeNotification", notification, cancellationToken);
    }
}
```

> Giả định user có thể thuộc nhiều tenant và `_membership` lấy membership từ nguồn server-side đáng tin cậy. Nếu hệ thống single-tenant-per-user, có thể đơn giản hơn bằng cách lấy trực tiếp `tenant_id` claim và join duy nhất một group.

## Trade-offs

- Auto-join tất cả tenant phù hợp với user có ít tenant; nếu một user có hàng nghìn tenant thì nên dùng explicit subscription nhưng vẫn authorize server-side.
- Revalidate quyền liên tục tăng chi phí; lựa chọn cadence phụ thuộc độ nhạy dữ liệu và tốc độ yêu cầu revoke.
- Connection registry giúp revoke gần real-time nhưng tăng state/coordination, đặc biệt khi scale-out nhiều instance.
- Data-minimized DTO có thêm mapping nhưng giảm exposure và coupling giữa domain model với transport contract.

## Cách kiểm thử

1. **Security test:** User tenant A cố gọi/join tenant B; phải bị từ chối và không nhận bất kỳ message B nào.
2. **Integration test:** Hai connection thuộc hai tenant khác nhau; publish cho A không được xuất hiện ở B.
3. **Reconnect test:** Sau reconnect, group membership phải được tính lại từ source of truth, không dựa vào client state cũ.
4. **Revocation test:** Thu hồi membership trong khi connection đang mở; verify behavior đúng với revocation strategy đã chọn.
5. **Data-leak test:** Log không chứa email/raw employee payload; notification DTO chỉ có field cần thiết.

## Quan sát trong production

- Metric: active connections, joins, authorization denied, disconnects, publish failures theo tenant ở cardinality có kiểm soát.
- Log: connection id, user id dạng phù hợp policy, tenant id, authorization outcome; không log token hoặc payload PII.
- Trace: connection lifecycle và publish operation với correlation id ổn định.
- Alert khi denied cross-tenant join tăng bất thường hoặc publish error rate tăng.
- Audit riêng cho thay đổi tenant membership/revocation nếu business yêu cầu truy vết.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một user hợp lệ thuộc 50 tenant, bạn thiết kế subscription UX/API thế nào mà vẫn giữ authorization server-side?
2. Khi scale SignalR qua nhiều instance, revocation gần real-time nên được triển khai thế nào?
3. Nếu notification chứa dữ liệu theo role trong cùng tenant, chỉ group theo tenant đã đủ chưa?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message broker acknowledgement không thay thế idempotency; ack timing và business durability phải được thiết kế cùng nhau.
- Exactly-once delivery hiếm khi là giả định an toàn; mục tiêu thực tế hơn là duplicate-tolerant processing và exactly-once business effect qua invariant/unique key.
- Khi một workflow chạm nhiều durable system, cần phân tích failure window giữa từng boundary; inbox/outbox là một cách phổ biến để giảm inconsistency.
- Trong hệ thống multi-tenant, group/channel/topic routing có thể trở thành security boundary; tenant phải được xác lập server-side.
- Long-lived connections cần có chiến lược xử lý permission revocation và data minimization.

## Mẫu tư duy cần nhớ

- Ack only after durable success; assume redelivery can happen.
- Design retries together with idempotency and unique business invariants.
- Treat every cross-system call as a potential partial-failure boundary.
- Never let client-controlled identifiers define authorization scope.
- Minimize sensitive data in both transport payloads and observability.
