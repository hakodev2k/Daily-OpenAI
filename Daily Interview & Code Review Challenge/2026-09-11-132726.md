# Code Review Challenge 1 — Retry payment `POST` giúp giảm lỗi mạng nhưng lại tạo duplicate charge khi response bị mất

**Chủ đề:** C#/.NET 8, ASP.NET Core, `HttpClient`, Polly-style retry, idempotency, partial failure, payment integration, EF Core, timeout ambiguity, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một ASP.NET Core checkout API gọi external payment provider để charge thẻ sau khi order được tạo trong SQL Server.

Yêu cầu:

- một checkout chỉ được charge tối đa một lần về mặt business;
- external provider đôi lúc timeout, trả `429`, `502`, `503` hoặc reset connection;
- application chạy nhiều instances;
- client/mobile gateway có thể retry checkout request nếu response timeout;
- provider hỗ trợ `Idempotency-Key` trên charge API;
- nếu outcome của network call không rõ ràng, hệ thống không được tự suy luận “charge chắc chắn thất bại”;
- không muốn distributed transaction giữa SQL Server và payment provider;
- production cần biết duplicate-attempt rate, retry rate, ambiguous outcomes, payment latency và reconciliation backlog.

Sau một incident mạng, finance phát hiện một số order bị charge hai lần. Team đã thêm retry để “tăng reliability”, và logs cho thấy cả hai charge đều đến từ cùng một order.

## Đoạn code cần review

```csharp
public sealed record ChargeRequest(
    Guid OrderId,
    decimal Amount,
    string Currency);

public sealed class PaymentGatewayClient
{
    private readonly HttpClient _httpClient;
    private readonly IAsyncPolicy<HttpResponseMessage> _retryPolicy;

    public PaymentGatewayClient(HttpClient httpClient)
    {
        _httpClient = httpClient;

        _retryPolicy = Policy<HttpResponseMessage>
            .Handle<HttpRequestException>()
            .Or<TaskCanceledException>()
            .OrResult(response =>
                (int)response.StatusCode >= 500 ||
                response.StatusCode == HttpStatusCode.TooManyRequests)
            .WaitAndRetryAsync(
                3,
                attempt => TimeSpan.FromMilliseconds(200 * attempt));
    }

    public Task<HttpResponseMessage> ChargeAsync(
        ChargeRequest request,
        CancellationToken cancellationToken)
    {
        return _retryPolicy.ExecuteAsync(async ct =>
        {
            using var message = new HttpRequestMessage(
                HttpMethod.Post,
                "/api/charges");

            message.Headers.Add(
                "Idempotency-Key",
                Guid.NewGuid().ToString("N"));

            message.Content = JsonContent.Create(request);

            return await _httpClient.SendAsync(message, ct);
        }, cancellationToken);
    }
}

public sealed class CheckoutService
{
    private readonly AppDbContext _db;
    private readonly PaymentGatewayClient _payments;

    public CheckoutService(
        AppDbContext db,
        PaymentGatewayClient payments)
    {
        _db = db;
        _payments = payments;
    }

    public async Task CompleteCheckoutAsync(
        Guid orderId,
        CancellationToken cancellationToken)
    {
        var order = await _db.Orders
            .SingleAsync(x => x.Id == orderId, cancellationToken);

        if (order.Status == OrderStatus.Paid)
            return;

        using var response = await _payments.ChargeAsync(
            new ChargeRequest(
                order.Id,
                order.Total,
                order.Currency),
            cancellationToken);

        response.EnsureSuccessStatusCode();

        order.Status = OrderStatus.Paid;
        order.PaidAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong retry/payment flow.
2. Xác định reliability, concurrency, data-consistency và maintainability concerns.
3. Giải thích production impact trong các failure windows khác nhau.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa mà không giả vờ có atomic transaction xuyên SQL Server và payment provider.
6. Giải thích testing cho timeout ambiguity, duplicate requests, retry và application crash.
7. Đề xuất production telemetry và reconciliation strategy.

## Câu hỏi gợi mở

1. Nếu provider đã charge thành công nhưng TCP connection bị reset trước khi response tới application, retry hiện tại sẽ làm gì?
2. `Idempotency-Key` mới được tạo ở đâu, và giá trị đó có ổn định xuyên các retry attempts của cùng logical payment không?

## Kết quả code review tham khảo

### Critical — Mỗi retry dùng một `Idempotency-Key` mới

**Vấn đề:**  
`Guid.NewGuid()` nằm bên trong delegate được policy thực thi lại cho từng attempt.

**Tại sao xảy ra:**  
Retry policy tạo một HTTP request mới cho mỗi attempt, và code đồng thời tạo một business idempotency identity mới. Provider vì thế có quyền coi từng attempt là một charge hoàn toàn khác.

**Ảnh hưởng production:**  
Nếu attempt đầu tiên đã charge nhưng response bị mất, attempt thứ hai có thể charge lại cùng order. Đây là failure mode trực tiếp dẫn tới duplicate payment.

**Cách sửa:**  
Tạo một stable payment-attempt identity trước network call, persist nó, và dùng cùng một idempotency key cho mọi retry/replay của cùng logical charge. Không tạo key theo transport attempt.

### Critical — Không có durable local payment-attempt state trước external side effect

**Vấn đề:**  
Code chỉ lưu `OrderStatus.Paid` sau khi provider trả success.

**Tại sao xảy ra:**  
External side effect xảy ra trước durable local record thể hiện rằng một payment attempt đã bắt đầu và có identity nào.

**Ảnh hưởng production:**  
Nếu provider charge thành công rồi process crash trước `SaveChangesAsync`, SQL vẫn thấy order chưa paid. Request sau có thể tạo một charge hoàn toàn mới.

**Cách sửa:**  
Persist `PaymentAttempt` hoặc equivalent durable state với stable `AttemptId`/idempotency key trước khi gọi provider. State machine tối thiểu có thể gồm `Pending`, `Succeeded`, `Failed`, `Unknown/ReconciliationRequired` tùy provider semantics.

### High — `order.Status == Paid` không phải concurrency control

**Vấn đề:**  
Hai requests/instances có thể cùng đọc `Pending` rồi cùng gọi provider.

**Tại sao xảy ra:**  
Check và external side effect không nằm trong atomic claim boundary. Không có optimistic concurrency token, unique active-attempt constraint hoặc durable claim.

**Ảnh hưởng production:**  
Concurrent duplicate checkout requests có thể tạo hai payment attempts trước khi request nào kịp ghi `Paid`.

**Cách sửa:**  
Dùng database invariant để đảm bảo một logical payment attempt cho order. Ví dụ unique constraint trên `(OrderId, PaymentPurpose)` hoặc state transition có concurrency token. Các callers cạnh tranh nên converge về cùng stable attempt identity thay vì mỗi caller tự charge.

### High — Retry policy không phân biệt timeout ambiguity với confirmed failure

**Vấn đề:**  
`HttpRequestException` và `TaskCanceledException` được retry chung mà không xét request đã được provider nhận/commit hay chưa.

**Tại sao xảy ra:**  
Distributed network failure không cho application luôn biết side effect đã xảy ra hay chưa. Timeout có thể xảy ra trước connect, trong upload, sau provider commit hoặc trong response transit.

**Ảnh hưởng production:**  
Retry mù làm tăng duplicate-risk nếu operation không idempotent; ngược lại, không retry gì cũng làm giảm availability.

**Cách sửa:**  
Chỉ retry cùng stable idempotency key khi provider contract bảo đảm deduplication phù hợp. Với outcome vẫn ambiguous, query/reconcile bằng provider transaction/idempotency identity thay vì tự kết luận.

### High — Retry `5xx`/`429` quá rộng nhưng không dùng provider semantics

**Vấn đề:**  
Mọi `5xx` và `429` đều dùng cùng số lần retry và linear delay.

**Tại sao xảy ra:**  
`429` có thể có `Retry-After`; một số `5xx` có thể là transient, một số response/body lại biểu diễn business/provider state cần xử lý khác. Retry budget cũng phải nằm trong end-to-end request deadline.

**Ảnh hưởng production:**  
Retry storm có thể khuếch đại outage hoặc rate-limit, tăng checkout latency và làm downstream recovery chậm hơn.

**Cách sửa:**  
Classify retryable outcomes theo provider documentation, honor `Retry-After` khi phù hợp, dùng bounded exponential backoff/jitter, và đặt total timeout/retry budget. Retry phải đi cùng idempotency.

### High — Local order update và provider charge là hai transaction boundaries độc lập

**Vấn đề:**  
Code ngầm coi “provider success → SQL save” như một atomic flow.

**Tại sao xảy ra:**  
Không có transaction chung giữa SQL Server và external HTTP provider, và không nên cố giả lập bằng giữ database transaction mở quanh network call.

**Ảnh hưởng production:**  
Partial success là trạng thái bình thường phải được thiết kế: provider paid nhưng local state pending, hoặc local attempt tồn tại nhưng provider chưa nhận request.

**Cách sửa:**  
Mô hình hóa state machine + reconciliation. Persist intent, execute external effect idempotently, persist observed result. Có job/process định kỳ reconcile `Pending/Unknown` dựa trên provider API/event/webhook nếu provider hỗ trợ.

### Medium — Response handling chưa đọc provider business payload

**Vấn đề:**  
`EnsureSuccessStatusCode()` chỉ kiểm tra HTTP status.

**Tại sao xảy ra:**  
Payment API thường có transaction ID, charge status, decline code hoặc asynchronous state trong body. HTTP 2xx không nhất thiết đồng nghĩa final settled state theo mọi provider contract.

**Ảnh hưởng production:**  
Local order có thể được đánh dấu `Paid` khi provider mới chỉ accepted/pending, hoặc mất transaction reference cần cho refund/reconciliation.

**Cách sửa:**  
Parse typed provider response và map explicit business states. Persist provider transaction/reference ID cùng payment attempt.

### Medium — Không có explicit total timeout budget

**Vấn đề:**  
Retry policy có delay nhưng không cho thấy request-level timeout budget hoặc separation giữa per-attempt timeout và total operation timeout.

**Tại sao xảy ra:**  
Ba retries có thể kéo checkout vượt upstream gateway/client timeout; client sau đó retry trong khi server vẫn đang xử lý.

**Ảnh hưởng production:**  
Tăng concurrent duplicate attempts và làm failure amplification khó kiểm soát.

**Cách sửa:**  
Define per-attempt timeout, overall deadline và retry budget phù hợp checkout SLO. Khi caller timeout không đồng nghĩa provider transaction phải bị xem là failed; durable state vẫn cần reconciliation.

### Medium — Không có domain result cho business decline vs infrastructure failure

**Vấn đề:**  
Method trả `HttpResponseMessage`, khiến caller phụ thuộc transport details.

**Tại sao xảy ra:**  
Payment integration boundary chưa map provider-specific protocol thành domain outcomes.

**Ảnh hưởng production:**  
Business decline, transient failure, duplicate/idempotent replay và unknown outcome dễ bị xử lý giống nhau.

**Cách sửa:**  
Return typed result như `Succeeded`, `Declined`, `Pending`, `Unknown`, `TransientFailure` với provider reference và error classification.

### Medium — Cancellation cần được hiểu đúng semantics

**Vấn đề:**  
Caller cancellation được propagate, nhưng code có thể coi cancellation exception như một retry trigger chung.

**Tại sao xảy ra:**  
Cancellation có thể đến từ caller disconnect hoặc timeout policy; hai trường hợp không nhất thiết có cùng retry semantics.

**Ảnh hưởng production:**  
Application có thể tiếp tục/retry work dù caller không còn chờ, hoặc ngược lại bỏ reconciliation của một payment đã có ambiguous outcome.

**Cách sửa:**  
Phân biệt cancellation ownership. Không retry khi caller explicitly canceled nếu policy không yêu cầu, nhưng vẫn persist/observe state của external operation nếu request đã có thể được gửi.

### Low — Thiếu payment-specific observability

**Vấn đề:**  
Đoạn code không emit telemetry về attempt identity, retries, ambiguous outcomes hay reconciliation.

**Tại sao xảy ra:**  
Operational success đang bị suy ra từ HTTP call và order status.

**Ảnh hưởng production:**  
Finance phát hiện duplicate trước engineering; khó chứng minh retry nào tương ứng cùng logical payment.

**Cách sửa:**  
Structured telemetry theo `OrderId`, internal `PaymentAttemptId`, provider transaction ID, attempt number, outcome class, latency, retry reason và reconciliation state. Không log PAN/CVV hoặc sensitive payment payload.

## Phiên bản đề xuất

Một hướng đơn giản là persist stable `PaymentAttempt` trước network call và dùng cùng idempotency key cho mọi transport retry.

```csharp
public enum PaymentAttemptStatus
{
    Pending,
    Succeeded,
    Declined,
    Unknown
}

public sealed class PaymentAttempt
{
    public Guid Id { get; init; }
    public Guid OrderId { get; init; }
    public decimal Amount { get; init; }
    public string Currency { get; init; } = default!;
    public PaymentAttemptStatus Status { get; set; }
    public string? ProviderTransactionId { get; set; }
    public DateTime CreatedAtUtc { get; init; }
}

public async Task<CheckoutResult> CompleteCheckoutAsync(
    Guid orderId,
    CancellationToken cancellationToken)
{
    var attempt = await GetOrCreatePaymentAttemptAsync(
        orderId,
        cancellationToken);

    if (attempt.Status == PaymentAttemptStatus.Succeeded)
        return CheckoutResult.AlreadyPaid;

    var idempotencyKey = attempt.Id.ToString("N");

    PaymentResult payment;

    try
    {
        payment = await _payments.ChargeAsync(
            new ChargeRequest(
                attempt.OrderId,
                attempt.Amount,
                attempt.Currency),
            idempotencyKey,
            cancellationToken);
    }
    catch (PaymentOutcomeUnknownException)
    {
        attempt.Status = PaymentAttemptStatus.Unknown;
        await _db.SaveChangesAsync(CancellationToken.None);

        return CheckoutResult.PendingReconciliation;
    }

    switch (payment.Status)
    {
        case PaymentStatus.Succeeded:
            attempt.Status = PaymentAttemptStatus.Succeeded;
            attempt.ProviderTransactionId = payment.TransactionId;

            var order = await _db.Orders
                .SingleAsync(
                    x => x.Id == orderId,
                    cancellationToken);

            order.Status = OrderStatus.Paid;
            order.PaidAtUtc = DateTime.UtcNow;
            break;

        case PaymentStatus.Declined:
            attempt.Status = PaymentAttemptStatus.Declined;
            break;

        default:
            attempt.Status = PaymentAttemptStatus.Unknown;
            break;
    }

    await _db.SaveChangesAsync(cancellationToken);

    return Map(payment.Status);
}
```

`GetOrCreatePaymentAttemptAsync` phải enforce database invariant để concurrent callers cho cùng order/purpose nhận cùng active attempt, ví dụ bằng unique constraint và conflict handling chứ không chỉ `SELECT` rồi `INSERT` không đồng bộ.

Client integration nên tạo HTTP request mới cho mỗi transport attempt nhưng reuse cùng `idempotencyKey`:

```csharp
public Task<PaymentResult> ChargeAsync(
    ChargeRequest request,
    string idempotencyKey,
    CancellationToken cancellationToken)
{
    return _retryPolicy.ExecuteAsync(
        async ct =>
        {
            using var message = new HttpRequestMessage(
                HttpMethod.Post,
                "/api/charges");

            message.Headers.Add(
                "Idempotency-Key",
                idempotencyKey);

            message.Content = JsonContent.Create(request);

            using var response = await _httpClient.SendAsync(
                message,
                HttpCompletionOption.ResponseHeadersRead,
                ct);

            return await MapProviderResponseAsync(response, ct);
        },
        cancellationToken);
}
```

Nếu provider cho phép query transaction theo idempotency key/reference, reconciliation worker nên xử lý `Unknown` bằng query đó. Nếu provider chỉ gửi webhook, webhook consumer cũng phải idempotent và correlate về cùng `PaymentAttempt`.

## Giải thích thiết kế sau khi sửa

Thiết kế mới phân biệt **logical payment attempt** với **transport attempt**. Retry có thể tạo nhiều HTTP requests, nhưng tất cả đại diện cho cùng một business operation qua stable idempotency key.

SQL Server không thể atomically commit cùng external payment provider. Thay vì che giấu thực tế đó, state machine lưu intent trước, external effect xảy ra sau, rồi local state được cập nhật dựa trên observed provider result. `Unknown` là state hợp lệ cần reconciliation chứ không phải lỗi cần đoán.

Không cần giữ database transaction mở trong lúc gọi HTTP. Điều đó chỉ kéo dài lock/connection lifetime mà vẫn không tạo atomicity với external provider.

## Trade-offs

- Persist `PaymentAttempt` làm data model và operational workflow phức tạp hơn, nhưng đổi lại có durable audit/recovery boundary.
- Stable idempotency phụ thuộc provider thực sự hỗ trợ semantics đủ mạnh; phải xác minh retention window và scope của key.
- Retry tăng availability với transient failures nhưng có thể khuếch đại overload nếu backoff/budget sai.
- Reconciliation tạo eventual consistency giữa provider và local database; UI/business flow cần thể hiện `Pending/Unknown` hợp lý.
- Có thể dùng queue/background processing cho payment ở một số domain, nhưng checkout đồng bộ có thể vẫn cần immediate response; không nên thêm messaging chỉ vì “distributed systems”.

## Cách kiểm thử

1. **Ambiguous timeout integration test:** provider simulator commit charge rồi drop connection; xác minh retry dùng cùng idempotency key và chỉ có một logical charge.
2. **Concurrency test:** gửi nhiều `CompleteCheckoutAsync` đồng thời từ nhiều service instances cho cùng `OrderId`; xác minh chỉ một active payment attempt được tạo.
3. **Crash-window test:** giả lập process crash sau provider success nhưng trước local `SaveChanges`; restart/retry phải recover/reconcile bằng cùng attempt identity thay vì charge mới.
4. **Rate-limit/failure test:** provider trả `429`/`503`; xác minh retry budget, `Retry-After` handling nếu contract hỗ trợ, latency tổng và không tạo retry storm.
5. **Business-state test:** decline, pending, success, duplicate/idempotent replay và malformed provider response được map thành domain outcomes đúng.

## Quan sát trong production

Theo dõi:

- payment attempts created/succeeded/declined/unknown;
- retries per logical attempt và retry reason;
- provider latency p50/p95/p99 và timeout rate;
- duplicate/idempotency replay rate;
- concurrent-attempt conflict count;
- reconciliation backlog age và success/failure rate;
- provider transaction ID ↔ internal payment attempt correlation;
- alerts cho tăng đột biến `Unknown`, duplicate finance reports hoặc retry amplification;
- logs/traces không chứa PAN, CVV, raw authorization token hoặc sensitive payment payload.

# Code Review Challenge 2 — Vue search autocomplete trả kết quả cũ đè kết quả mới và `v-html` mở cửa cho XSS

**Chủ đề:** Vue 3, TypeScript, Composition API, async race conditions, request cancellation, debounce, frontend security, XSS, browser auth storage, API error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một Vue 3 SPA có autocomplete tìm product. Backend search API dùng Elasticsearch và trả về `items` cùng đoạn highlight.

Yêu cầu:

- bắt đầu search khi user nhập từ 2 ký tự;
- UI phải luôn hiển thị kết quả tương ứng với query mới nhất;
- typing nhanh không được tạo tải request không giới hạn;
- component unmount hoặc query thay đổi phải hủy work không còn cần thiết khi có thể;
- API có thể trả `429`, `500`, timeout hoặc response chậm không theo thứ tự request;
- highlight không được tạo XSS;
- authentication hiện dùng bearer token trong SPA;
- production cần biết search latency, error rate, aborted requests và client-side stale-response rate.

Production xuất hiện:

- user gõ `camera`, đôi lúc UI cuối cùng lại hiển thị kết quả của `cam`;
- khi user xóa query, vài trăm milliseconds sau danh sách cũ tự xuất hiện lại;
- backend thấy request rate tăng mạnh khi users gõ nhanh;
- loading spinner đôi lúc biến mất dù request mới nhất vẫn đang chạy;
- security review phát hiện API highlight có thể chứa text từ product name do merchant nhập;
- team cho rằng `encodeURIComponent(query)` đã xử lý toàn bộ vấn đề security của search UI.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  name: string
  highlight: string
}

const query = ref('')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

watch(query, async value => {
  if (value.length < 2) {
    items.value = []
    return
  }

  loading.value = true
  error.value = null

  const token = localStorage.getItem('access_token')

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(value)}`,
      {
        headers: {
          Authorization: `Bearer ${token}`
        }
      })

    const data = await response.json()
    items.value = data.items
  } catch (e) {
    error.value = 'Search failed'
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <div>
    <input v-model="query" placeholder="Search products" />

    <span v-if="loading">Loading...</span>
    <div v-if="error">{{ error }}</div>

    <ul>
      <li v-for="item in items" :key="item.id">
        <strong>{{ item.name }}</strong>
        <div v-html="item.highlight"></div>
      </li>
    </ul>
  </div>
</template>
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong async search flow.
2. Xác định performance, security, reliability và maintainability concerns.
3. Giải thích production impact khi request hoàn tất out-of-order hoặc user typing nhanh.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa mà không thêm state-management library nếu component chưa cần.
6. Giải thích testing cho races, cancellation, XSS, rate-limit và component lifecycle.
7. Đề xuất browser/server telemetry để chứng minh search UX đúng và không tạo tải bất thường.

## Câu hỏi gợi mở

1. Nếu request cho `cam` mất 800 ms còn request cho `camera` chỉ mất 100 ms, assignment nào chạy sau cùng?
2. Khi query xuống dưới 2 ký tự, request cũ đang chạy bị xử lý thế nào?
3. Một request cũ chạy `finally` có thể thay đổi `loading` trong lúc request mới còn pending không?
4. `encodeURIComponent` bảo vệ URL query parameter, nhưng có liên quan gì tới DOM sink `v-html`?
5. Bearer token trong `localStorage` có threat model gì nếu page xảy ra XSS?

## Gợi ý

### Gợi ý 1

Primary risk về correctness là **out-of-order async completion**: response cũ có thể ghi đè state của query mới.

### Gợi ý 2

Ở phía security, hãy phân biệt URL encoding với HTML sanitization/DOM rendering. Chúng giải quyết hai context khác nhau.

## Kết quả code review tham khảo

### Critical — `v-html` với highlight không trusted có thể tạo XSS

**Vấn đề:**  
`item.highlight` được đưa trực tiếp vào `v-html`.

**Tại sao xảy ra:**  
`v-html` yêu cầu developer chịu trách nhiệm về trust/sanitization của HTML. Nếu highlight chứa content bắt nguồn từ merchant/user-controlled product text và backend trả markup không được sanitize theo policy an toàn, browser có thể interpret attacker-controlled HTML.

**Ảnh hưởng production:**  
XSS có thể thực thi code trong origin của SPA, đọc accessible tokens/data, thực hiện authenticated actions và compromise session.

**Cách sửa:**  
Ưu tiên tránh HTML string: backend trả structured highlight segments hoặc plain text để Vue render bằng interpolation. Nếu business bắt buộc rich HTML, sanitize bằng allowlist sanitizer phù hợp và áp dụng defense-in-depth như CSP; không tự viết regex sanitizer.

### High — Response cũ có thể ghi đè kết quả query mới

**Vấn đề:**  
Mỗi thay đổi query tạo một async callback độc lập; callback hoàn tất sau vẫn assign `items.value` bất kể query hiện tại là gì.

**Tại sao xảy ra:**  
Network responses không có ordering guarantee theo thời điểm request bắt đầu.

**Ảnh hưởng production:**  
User có thể thấy kết quả sai với text đang nhập, click nhầm product, hoặc kết quả cũ tái xuất hiện sau khi query đã được xóa.

**Cách sửa:**  
Cancel request trước bằng `AbortController` khi query đổi, và/hoặc dùng monotonically increasing request sequence để chỉ latest request được commit UI state.

### High — Không debounce nên typing nhanh tạo request amplification

**Vấn đề:**  
Mỗi keystroke từ ký tự thứ hai trở đi gọi API ngay.

**Tại sao xảy ra:**  
Watcher không có debounce/coalescing.

**Ảnh hưởng production:**  
Một user có thể tạo nhiều searches cho một intent; ở scale lớn làm tăng Elasticsearch/API load, rate-limit và chi phí.

**Cách sửa:**  
Debounce khoảng thời gian phù hợp UX, ví dụ được tune bằng measurement thay vì hard-code theo cảm tính. Kết hợp cancellation để request đã bắt đầu nhưng obsolete không tiếp tục không cần thiết.

### High — `loading` bị race giữa nhiều requests

**Vấn đề:**  
Mọi callback đều set `loading = false` trong `finally`.

**Tại sao xảy ra:**  
Request cũ có thể hoàn tất trước request mới và tắt spinner dù latest request vẫn pending.

**Ảnh hưởng production:**  
UI báo trạng thái sai, làm user nghĩ kết quả đã ổn định trong khi network vẫn đang chạy.

**Cách sửa:**  
Chỉ latest request được cập nhật loading/error/results, hoặc track active request identity/count có semantics rõ.

### High — Clear query không ngăn request cũ commit state

**Vấn đề:**  
Khi `value.length < 2`, code clear `items` rồi return nhưng không cancel request trước.

**Tại sao xảy ra:**  
Async work đã start vẫn có thể hoàn tất sau branch này.

**Ảnh hưởng production:**  
Danh sách cũ tự xuất hiện lại dù input rỗng, đúng như symptom production.

**Cách sửa:**  
Watcher cleanup phải abort pending request/timer trước khi xử lý value mới. Sequence guard là defense bổ sung.

### High — Không kiểm tra `response.ok`

**Vấn đề:**  
Code gọi `response.json()` và assign `data.items` cho cả `429`/`500` nếu body parse được.

**Tại sao xảy ra:**  
`fetch` chỉ reject promise chủ yếu với network-level failure; HTTP error status không tự throw.

**Ảnh hưởng production:**  
Error payload có thể bị coi như success, gây runtime error/state không hợp lệ; rate-limit không được phản ánh đúng cho UX.

**Cách sửa:**  
Check `response.ok`; map `401`, `403`, `429`, `5xx` thành outcome phù hợp. Không retry client mù làm tăng load khi server đã rate-limit.

### Medium — `localStorage` làm bearer token dễ bị lấy nếu XSS xảy ra

**Vấn đề:**  
Access token được đọc trực tiếp từ `localStorage`.

**Tại sao xảy ra:**  
Bất kỳ script chạy được trong origin đều có thể đọc web storage. Đây đặc biệt nguy hiểm khi cùng component có một `v-html` sink.

**Ảnh hưởng production:**  
Một XSS có thể chuyển từ DOM compromise thành token theft và session/API compromise cho tới khi token hết hạn/revoked.

**Cách sửa:**  
Đánh giá auth architecture thay vì coi một storage choice là universal rule. Nếu phù hợp, dùng secure `HttpOnly`/`SameSite` cookie với CSRF controls hoặc token strategy theo identity-provider guidance; nếu SPA bắt buộc bearer token client-side, giảm lifetime/scope và ưu tiên loại bỏ XSS sinks. Không kết luận rằng cookie tự động an toàn hơn trong mọi threat model.

### Medium — Không validate response shape

**Vấn đề:**  
`data.items` được tin tưởng trực tiếp dù TypeScript interface chỉ tồn tại compile-time.

**Tại sao xảy ra:**  
Runtime JSON có thể khác contract do backend regression, proxy/error body hoặc version mismatch.

**Ảnh hưởng production:**  
UI có thể crash hoặc render data không như mong đợi.

**Cách sửa:**  
Giữ API contract versioned và validate tối thiểu fields quan trọng ở boundary nếu rủi ro đáng kể; generated client/schema validation có thể phù hợp với hệ thống lớn.

### Medium — Component lifecycle cleanup chưa tồn tại

**Vấn đề:**  
Pending fetch không được abort khi component unmount.

**Tại sao xảy ra:**  
Watcher callback không dùng cleanup hook/controller lifecycle.

**Ảnh hưởng production:**  
Network work tiếp tục dù UI không còn cần, làm tăng wasted requests và có thể tạo noisy error/telemetry.

**Cách sửa:**  
Dùng watcher cleanup để clear debounce timer và abort controller của request hiện tại.

### Medium — Error state cũng có thể stale

**Vấn đề:**  
Một request cũ fail có thể set `error = 'Search failed'` sau khi request mới đã thành công.

**Tại sao xảy ra:**  
Error/result/loading đều không gắn với request identity.

**Ảnh hưởng production:**  
UI vừa hiển thị kết quả đúng vừa báo lỗi của request cũ, gây confusing UX.

**Cách sửa:**  
Chỉ latest request được commit bất kỳ async-derived state nào.

### Low — Thiếu client-side operational signals

**Vấn đề:**  
Không có telemetry cho query-to-result latency, aborted/stale responses hoặc request count trên một search interaction.

**Tại sao xảy ra:**  
Backend chỉ thấy HTTP calls nhưng không biết request nào obsolete do UI race.

**Ảnh hưởng production:**  
Khó chứng minh debounce/cancellation có hiệu quả hoặc xác định frontend đang amplification load.

**Cách sửa:**  
Track privacy-safe metrics cho request started/completed/aborted, stale-response discarded, frontend search latency và `429` rate; không log raw sensitive query nếu search text có thể chứa PII.

## Phiên bản đề xuất

Ví dụ dưới đây dùng debounce, watcher cleanup, `AbortController` và sequence guard. Highlight được render như text thay vì HTML string.

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  name: string
  highlightText: string
}

interface SearchResponse {
  items: SearchItem[]
}

const query = ref('')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

let sequence = 0

watch(query, (rawValue, _oldValue, onCleanup) => {
  const value = rawValue.trim()
  const currentSequence = ++sequence
  const controller = new AbortController()

  const timer = window.setTimeout(async () => {
    if (value.length < 2) {
      if (currentSequence === sequence) {
        items.value = []
        error.value = null
        loading.value = false
      }
      return
    }

    if (currentSequence === sequence) {
      loading.value = true
      error.value = null
    }

    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(value)}`,
        {
          signal: controller.signal,
          credentials: 'include'
        })

      if (!response.ok) {
        throw new Error(`Search HTTP ${response.status}`)
      }

      const data = await response.json() as SearchResponse

      if (currentSequence !== sequence)
        return

      items.value = data.items
    } catch (e) {
      if (controller.signal.aborted)
        return

      if (currentSequence === sequence)
        error.value = 'Search failed'
    } finally {
      if (currentSequence === sequence)
        loading.value = false
    }
  }, 250)

  onCleanup(() => {
    window.clearTimeout(timer)
    controller.abort()
  })
}, { immediate: true })
</script>

<template>
  <div>
    <input v-model="query" placeholder="Search products" />

    <span v-if="loading">Loading...</span>
    <div v-if="error">{{ error }}</div>

    <ul>
      <li v-for="item in items" :key="item.id">
        <strong>{{ item.name }}</strong>
        <div>{{ item.highlightText }}</div>
      </li>
    </ul>
  </div>
</template>
```

`credentials: 'include'` chỉ là ví dụ nếu hệ thống chọn cookie-based auth. Nếu application dùng OAuth/OIDC bearer token theo SPA architecture hiện tại, auth handling nên nằm trong một API client/auth abstraction thay vì mỗi component tự đọc `localStorage`.

Nếu highlight cần giữ markup như `<mark>`, một design tốt hơn là backend trả structured segments:

```ts
interface HighlightSegment {
  text: string
  matched: boolean
}
```

Template render `text` bằng interpolation và chỉ dùng component/tag do application kiểm soát, không inject raw HTML.

## Giải thích thiết kế sau khi sửa

Watcher cleanup được gọi khi dependency thay đổi hoặc watcher bị dispose, nên timer/request obsolete được hủy sớm. `AbortController` giảm wasted network work, nhưng sequence guard vẫn cần như defense cho cases cancellation đến muộn hoặc abstraction khác không hỗ trợ cancellation hoàn hảo.

State `items`, `error`, `loading` chỉ được latest sequence cập nhật. Nhờ đó một response cũ không thể override query mới.

Debounce giảm request amplification, nhưng con số `250 ms` chỉ là starting point; nên tune theo UX, backend latency và search infrastructure capacity.

Security fix quan trọng nhất là loại raw HTML sink. URL encoding query không sanitize HTML response; encoding phải đúng theo output context.

## Trade-offs

- Debounce giảm load nhưng thêm một chút perceived latency trước request.
- Abort request giảm wasted work phía browser; backend có thể đã nhận query trước khi cancellation propagate, nên server vẫn cần capacity/rate controls.
- Sequence guard thêm state logic nhưng làm correctness độc lập hơn với cancellation timing.
- Structured highlight an toàn hơn raw HTML nhưng tăng API contract complexity.
- Cookie auth giảm khả năng JavaScript đọc token nhưng tạo CSRF considerations; bearer-token SPA lại có storage/XSS trade-offs khác.
- Client retry cho search có thể hữu ích với network glitch nhưng không nên tự động retry `429`/server overload theo cách làm request storm nặng hơn.

## Cách kiểm thử

1. **Async race test:** mock `cam` response chậm và `camera` response nhanh; UI cuối cùng chỉ được hiển thị `camera`.
2. **Clear/unmount test:** bắt đầu request rồi clear query hoặc unmount component; request obsolete bị abort và không thể repopulate state.
3. **Security test:** backend trả product/highlight chứa `<img onerror=...>` hoặc `<script>`; UI không execute markup và render như text/structured segments.
4. **Load/typing test:** Playwright mô phỏng typing nhanh; đo số request thực tế, xác minh debounce/cancellation giảm amplification theo expectation.
5. **Failure-path test:** `429`, `500`, malformed JSON, network timeout; UI state/error/loading nhất quán và không có stale request override.

## Quan sát trong production

Theo dõi:

- search API request rate per active search interaction ở mức aggregate;
- browser search latency và backend dependency latency;
- aborted request count và stale-response-discarded count;
- `429`, `5xx`, network error rate;
- Elasticsearch query latency/CPU/query volume tương quan với frontend release;
- client-side error traces có release/version correlation;
- CSP violation reports nếu CSP được triển khai;
- không log raw access token hoặc raw search text nếu query có thể chứa dữ liệu nhạy cảm.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry một external side effect chỉ an toàn khi business operation có stable identity và retry semantics thật sự idempotent.
- Timeout trong distributed systems có thể tạo **ambiguous outcome**; không được suy luận timeout = chưa thực hiện side effect.
- Không có transaction atomic giữa SQL Server và external HTTP provider thì phải mô hình hóa partial success và reconciliation.
- Frontend async requests có thể hoàn tất out-of-order; latest user intent phải có ownership rõ đối với state.
- URL encoding, HTML sanitization và output escaping giải quyết các security context khác nhau.
- Cancellation giúp giảm wasted work nhưng không thay thế correctness guard hoặc durable state.

## Mẫu tư duy cần nhớ

- Tách **business operation identity** khỏi **transport attempt**.
- Thiết kế retry cùng idempotency và reconciliation.
- Với async UI, chỉ latest intent được commit state.
- Cancel obsolete work nhưng vẫn guard against late completion.
- Encode/sanitize theo đúng output context, không dùng một kỹ thuật security cho mọi context.
