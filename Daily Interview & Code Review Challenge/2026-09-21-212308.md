# Code Review Challenge 1 — EF Core optimistic concurrency bị vô hiệu hóa bởi “last write wins” retry

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, optimistic concurrency, SQL Server, HTTP semantics, distributed instances  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một enterprise approval portal cho phép manager approve hoặc reject expense requests. API chạy nhiều Azure App Service instances. Hai manager có thể mở cùng request; business rule yêu cầu quyết định đầu tiên đã commit phải thắng, quyết định sau phải nhận conflict và refresh dữ liệu.

Entity có SQL Server `rowversion`. Team gặp `DbUpdateConcurrencyException` và thêm retry để “tăng reliability”. Sau thay đổi, audit ghi nhận một số request được approve rồi vài giây sau chuyển thành rejected mà không có conflict trả về client.

## Đoạn code cần review

```csharp
public sealed class ExpenseRequest
{
    public Guid Id { get; set; }
    public string Status { get; set; } = "Pending";
    public string? DecisionBy { get; set; }
    public DateTimeOffset? DecisionAt { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = Array.Empty<byte>();
}

public sealed record DecideRequest(string Decision, byte[] Version);

[ApiController]
public sealed class ExpenseController : ControllerBase
{
    private readonly AppDbContext _db;

    public ExpenseController(AppDbContext db) => _db = db;

    [HttpPut("/expenses/{id:guid}/decision")]
    public async Task<IActionResult> Decide(
        Guid id,
        DecideRequest request,
        CancellationToken ct)
    {
        for (var attempt = 0; attempt < 3; attempt++)
        {
            var expense = await _db.ExpenseRequests
                .SingleOrDefaultAsync(x => x.Id == id, ct);

            if (expense is null)
                return NotFound();

            expense.Status = request.Decision;
            expense.DecisionBy = User.Identity!.Name;
            expense.DecisionAt = DateTimeOffset.UtcNow;

            try
            {
                await _db.SaveChangesAsync(ct);
                return Ok(new { expense.Id, expense.Status, expense.Version });
            }
            catch (DbUpdateConcurrencyException ex)
            {
                foreach (var entry in ex.Entries)
                    await entry.ReloadAsync(ct);
            }
        }

        return StatusCode(500);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems và concurrency semantics đang bị phá vỡ.
2. Xác định reliability/security/maintainability concerns liên quan.
3. Giải thích production impact khi nhiều instances xử lý quyết định đồng thời.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design sửa đúng business rule.
6. Nêu cách kiểm thử race condition một cách deterministic nhất có thể.
7. Nêu telemetry cần có để phát hiện conflict và quyết định bị ghi đè.

## Câu hỏi gợi mở

- `rowversion` bảo vệ điều gì và EF Core dùng original value như thế nào khi update?
- Sau `ReloadAsync`, state/original values của entity thay đổi ra sao đối với vòng retry kế tiếp?
- Client đã gửi `Version`, nhưng code hiện tại có thực sự dùng version đó làm concurrency precondition không?
- Retry một concurrency conflict có cùng semantics với retry một transient transport error không?

## Gợi ý

### Gợi ý 1

Rủi ro chính không phải exception; rủi ro là code biến một conflict có ý nghĩa business thành một write mới trên version mới nhất.

Optimistic concurrency chỉ hữu ích khi precondition của người dùng được giữ nguyên từ lúc họ đọc dữ liệu đến lúc ghi.

## Kết quả code review tham khảo

### Critical — Retry biến conflict thành “last write wins”

**Vấn đề:** Sau `DbUpdateConcurrencyException`, code reload entity rồi vòng sau áp lại quyết định lên version mới nhất.

**Tại sao xảy ra:** `ReloadAsync` đồng bộ tracked entity/original values với database. Vòng retry tiếp theo tạo một update mới dựa trên concurrency token hiện tại thay vì precondition ban đầu của người dùng.

**Ảnh hưởng production:** Quyết định đã commit có thể bị ghi đè bởi request stale, trái business rule “first committed decision wins”.

**Cách sửa:** Không tự retry semantic conflict. Trả `409 Conflict` hoặc `412 Precondition Failed` tùy API contract và yêu cầu client refresh/re-evaluate.

### High — Client concurrency token bị bỏ qua

**Vấn đề:** `request.Version` không được dùng.

**Tại sao xảy ra:** API load entity mới từ database ngay trước update; EF dùng version vừa đọc, không phải version client đã quan sát.

**Ảnh hưởng production:** Một client giữ màn hình stale vẫn có thể update thành công nếu không đụng race đúng trong khoảng query→save.

**Cách sửa:** Gắn client token vào concurrency original value hoặc dùng HTTP ETag/`If-Match` làm explicit precondition.

### High — Không enforce transition `Pending → Approved/Rejected`

**Vấn đề:** Code ghi bất kỳ `Decision` nào và không kiểm tra current state.

**Tại sao xảy ra:** Business invariant không được enforce ở command boundary.

**Ảnh hưởng production:** Invalid status hoặc quyết định lại một request đã terminal có thể lọt qua.

**Cách sửa:** Validate allowed decisions và state transition; concurrency token phải bảo vệ transition đó.

### High — Authorization không được thể hiện ở endpoint

**Vấn đề:** Code dùng `User.Identity.Name` nhưng không chứng minh caller có quyền quyết định expense này.

**Tại sao xảy ra:** Authentication identity không đồng nghĩa authorization.

**Ảnh hưởng production:** Nếu route không được bảo vệ ở layer khác, authenticated user có thể quyết định request ngoài scope.

**Cách sửa:** Áp policy/resource-based authorization phù hợp ownership/role/business rule.

### Medium — `User.Identity!.Name` giả định luôn tồn tại

**Vấn đề:** Null-forgiving operator che mất runtime assumption.

**Tại sao xảy ra:** Endpoint phụ thuộc authentication configuration nhưng code không thể hiện contract.

**Ảnh hưởng production:** Null audit identity hoặc exception nếu pipeline/config thay đổi.

**Cách sửa:** Enforce authorization và lấy stable subject/user identifier từ trusted claim theo contract.

### Medium — Trả `500` cho expected concurrency outcome

**Vấn đề:** Sau ba lần conflict, API trả generic server error.

**Tại sao xảy ra:** Conflict bị coi là infrastructure failure.

**Ảnh hưởng production:** Client retry sai, telemetry 5xx bị nhiễu và UX không biết phải refresh.

**Cách sửa:** Trả conflict response có current version/state cần thiết nhưng không leak dữ liệu không được phép.

### Medium — Không có audit event atomic với state change

**Vấn đề:** Snippet chỉ sửa entity; nếu audit được ghi ở hệ thống khác hoặc sau commit, có thể có gap.

**Tại sao xảy ra:** State transition và audit ownership chưa được thiết kế thành cùng consistency boundary.

**Ảnh hưởng production:** Điều tra quyết định tài chính khó hoặc audit không khớp state.

**Cách sửa:** Nếu audit là requirement bắt buộc, persist audit record trong cùng local transaction; publish ra ngoài bằng outbox nếu cần.

### Medium — Không validate payload/token

**Vấn đề:** `Decision` là free-form string và `Version` có thể rỗng/malformed.

**Tại sao xảy ra:** Input model không biểu diễn domain constraints.

**Ảnh hưởng production:** Invalid state và ambiguous errors.

**Cách sửa:** Dùng enum/value object hoặc validation rõ ràng; reject missing concurrency precondition.

### Low — Retry count là magic number và không có conflict telemetry

**Vấn đề:** Loop che giấu conflict nhưng không metric/log có cấu trúc.

**Tại sao xảy ra:** Retry được thêm như generic reliability technique.

**Ảnh hưởng production:** Team khó phát hiện contention/hot records và UX conflict rate.

**Cách sửa:** Không retry business conflict; metric conflict rate và structured event với entity ID/correlation ID, không log sensitive payload.

## Phiên bản đề xuất

```csharp
public sealed record DecideRequest(string Decision, byte[] Version);

[Authorize(Policy = "ExpenseApprover")]
[ApiController]
public sealed class ExpenseController : ControllerBase
{
    private readonly AppDbContext _db;

    public ExpenseController(AppDbContext db) => _db = db;

    [HttpPut("/expenses/{id:guid}/decision")]
    public async Task<IActionResult> Decide(
        Guid id,
        DecideRequest request,
        CancellationToken ct)
    {
        if (request.Decision is not ("Approved" or "Rejected") ||
            request.Version is not { Length: > 0 })
        {
            return BadRequest();
        }

        var expense = await _db.ExpenseRequests
            .SingleOrDefaultAsync(x => x.Id == id, ct);

        if (expense is null)
            return NotFound();

        // Resource-level authorization may additionally be required here.
        if (expense.Status != "Pending")
        {
            return Conflict(new
            {
                message = "Expense has already been decided.",
                currentStatus = expense.Status,
                currentVersion = expense.Version
            });
        }

        _db.Entry(expense)
            .Property(x => x.Version)
            .OriginalValue = request.Version;

        expense.Status = request.Decision;
        expense.DecisionBy = User.FindFirst("sub")?.Value
            ?? User.Identity?.Name
            ?? throw new InvalidOperationException("Authenticated user id missing.");
        expense.DecisionAt = DateTimeOffset.UtcNow;

        try
        {
            await _db.SaveChangesAsync(ct);
            return Ok(new { expense.Id, expense.Status, expense.Version });
        }
        catch (DbUpdateConcurrencyException)
        {
            var current = await _db.ExpenseRequests
                .AsNoTracking()
                .Where(x => x.Id == id)
                .Select(x => new { x.Status, x.Version })
                .SingleAsync(ct);

            return Conflict(new
            {
                message = "Expense changed since it was loaded.",
                current.Status,
                current.Version
            });
        }
    }
}
```

## Giải thích thiết kế sau khi sửa

Concurrency token đại diện cho version mà client thực sự đã đọc. API không tự “giải quyết” conflict bằng cách ghi đè state mới. Business transition được kiểm tra trước update và SQL concurrency predicate bảo vệ race giữa check và commit.

Trong API public/HTTP-oriented hơn, có thể encode `rowversion` thành ETag và yêu cầu `If-Match`; điều quan trọng là contract precondition rõ ràng, không phải tên DTO. Nếu authorization phụ thuộc chính expense, resource-based authorization nên chạy với resource đã load.

Nếu audit bắt buộc, audit row nên commit cùng state transition trong cùng database transaction. Không cần microservice hay messaging chỉ để giải quyết một invariant local.

## Trade-offs

Optimistic concurrency làm client phải xử lý conflict/refresh và có thể tăng friction khi contention cao. Đổi lại nó tránh pessimistic lock dài qua user think-time. ETag làm HTTP semantics sạch hơn nhưng cần encode/decode và contract frontend nhất quán. Pessimistic locking thường không phù hợp để giữ lock từ lúc user mở màn hình đến lúc bấm quyết định.

## Cách kiểm thử

- **Integration/concurrency test:** hai DbContext/request cùng đọc một version; cho request A commit rồi request B commit và xác nhận B nhận conflict, state A không bị ghi đè.
- **API test:** gửi stale `Version` sau khi record đã đổi trước khi request bắt đầu; phải conflict ngay ở save thay vì overwrite.
- **Authorization test:** authenticated user không có quyền/resource scope không thể quyết định expense.
- **Validation test:** decision/token invalid bị reject và không tạo SQL update.
- **Database test:** audit row và state transition cùng commit/rollback nếu audit là invariant.

## Quan sát trong production

Theo dõi conflict count/rate theo endpoint và entity type, decision latency, status-code distribution (`409/412/4xx/5xx`), database deadlock/timeout riêng với concurrency conflict, audit/state mismatch và correlation ID. Application Insights dependency traces giúp phân biệt SQL transient failure với expected optimistic-concurrency conflict. Alert nếu conflict rate tăng đột biến vì có thể phản ánh UX stale data, automation cạnh tranh hoặc hot entity.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn ETag/`If-Match` thay vì đưa `rowversion` trong JSON body?
2. Nếu requirement đổi thành “một Senior Approver được phép override quyết định trước”, bạn model command/audit/concurrency thế nào mà không biến mọi conflict thành last-write-wins?
3. Nếu database là PostgreSQL thay vì SQL Server, bạn sẽ giữ concurrency contract ở application như thế nào dù token implementation khác?

# Code Review Challenge 2 — Kubernetes probes gây restart storm và đưa Pod nhận traffic trước khi application sẵn sàng

**Chủ đề:** Kubernetes, ASP.NET Core hosting, readiness/liveness/startup probes, rolling deployment, resource limits, graceful termination  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core API được chuyển từ Azure App Service sang Kubernetes. Khi deploy version mới, application cần khoảng 35–70 giây để warm up một số metadata/cache. Trong giờ cao điểm, SQL có thể chậm vài giây nhưng application vẫn có khả năng phục vụ một phần request.

Sau khi thêm probes, deployment đôi khi tạo `CrashLoopBackOff`, traffic nhận nhiều `502/503`, và rollout mất ổn định. Team dùng cùng `/health` endpoint cho cả liveness và readiness; endpoint này kiểm tra SQL, Redis và một third-party API. Deployment hiện tại như sau.

## Đoạn code cần review

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 2
      maxSurge: 0
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      terminationGracePeriodSeconds: 5
      containers:
        - name: api
          image: registry.example/catalog-api:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "200m"
              memory: "256Mi"
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 3
            timeoutSeconds: 1
            failureThreshold: 1
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 1
            failureThreshold: 2
```

Giả sử Service selector/port mapping đúng và image có thể start bình thường khi chạy riêng.

## Nhiệm vụ của ứng viên

1. Xác định correctness/reliability/deployment problems trong cấu hình.
2. Giải thích vì sao dependency degradation có thể biến thành restart storm.
3. Phân tích rollout capacity khi `replicas=4`, `maxUnavailable=2`, `maxSurge=0`.
4. Ưu tiên vấn đề theo production impact và đề xuất cấu hình/design sửa.
5. Nêu cách validate probe semantics và resource sizing bằng evidence thay vì đoán.
6. Nêu test/deployment validation cho startup chậm, SQL/Redis failure và termination.
7. Nêu telemetry cần theo dõi trong rollout.

## Câu hỏi gợi mở

- Liveness nên trả lời “process có cần restart không?” hay “mọi dependency có khỏe không?”
- Readiness failure và liveness failure tác động tới Pod khác nhau thế nào?
- Khi application startup 70 giây nhưng liveness bắt đầu sau 5 giây, chuyện gì có thể xảy ra?
- CPU limit thấp có thể ảnh hưởng startup/warm-up và probe latency như thế nào, và cần đo metric nào để xác nhận?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở việc dùng một health signal cho ba quyết định khác nhau: startup, nhận traffic và restart process.

### Gợi ý 2

Một dependency tạm thời lỗi không nhất thiết được chữa bằng cách kill application process; đôi khi restart còn khuếch đại tải lên dependency đang yếu.

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc SQL/Redis/third-party API

**Vấn đề:** `/health` kiểm tra dependencies và được dùng làm liveness.

**Tại sao xảy ra:** Dependency outage làm liveness fail dù process không deadlocked/corrupt.

**Ảnh hưởng production:** Kubernetes restart các Pod khỏe về process đúng lúc dependencies degraded, tạo restart storm, cold starts và thêm connection/load lên downstream.

**Cách sửa:** Liveness nên phản ánh process có khả năng tiếp tục chạy; dependency health thường phù hợp hơn với readiness hoặc telemetry, tùy khả năng degraded service.

### Critical — Không có startup probe cho startup 35–70 giây

**Vấn đề:** Liveness bắt đầu sau 5 giây với failure budget rất ngắn.

**Tại sao xảy ra:** Warm-up hợp lệ bị diễn giải thành process failure.

**Ảnh hưởng production:** Container có thể bị kill lặp trước khi hoàn tất startup và rơi vào restart/backoff cycle.

**Cách sửa:** Thêm `startupProbe` với budget dựa trên measured worst-case startup; liveness/readiness bắt đầu có ý nghĩa sau startup success.

### High — Rollout cho phép mất 50% capacity mà không surge

**Vấn đề:** `maxUnavailable: 2` và `maxSurge: 0` với bốn replicas có thể giảm available capacity xuống đáng kể trong rollout.

**Tại sao xảy ra:** Không có temporary extra Pod và rollout được phép unavailable hai replicas.

**Ảnh hưởng production:** Hai Pod còn lại có thể quá tải, tăng latency/probe failures và tạo feedback loop.

**Cách sửa:** Chọn rollout budget theo capacity/SLO; ví dụ `maxUnavailable: 0` hoặc 1 và `maxSurge: 1` nếu cluster capacity cho phép. Không copy giá trị ví dụ mà phải capacity-test.

### High — Readiness quá nhạy và gộp dependency semantics

**Vấn đề:** `timeoutSeconds: 1`, `failureThreshold: 1`, period 3s và endpoint gọi nhiều dependencies.

**Tại sao xảy ra:** Một spike ngắn hoặc dependency chậm làm Pod lập tức rời endpoints.

**Ảnh hưởng production:** Capacity flapping; remaining Pods nhận thêm load và có thể cùng fail readiness.

**Cách sửa:** Tách/readiness design theo khả năng phục vụ thật; đặt timeout/threshold từ latency evidence và SLO. Nếu API có thể phục vụ degraded mode khi Redis/third-party lỗi, readiness không nên fail toàn bộ chỉ vì dependency đó.

### High — Image tag `latest` không tạo artifact identity rõ ràng

**Vấn đề:** Deployment không pin immutable image version/digest.

**Tại sao xảy ra:** `latest` có thể trỏ tới nội dung khác theo thời gian và làm rollback/audit khó xác định artifact.

**Ảnh hưởng production:** Replica/redeploy có thể chạy artifact không đồng nhất tùy pull policy/cache và release traceability kém.

**Cách sửa:** Dùng immutable version tag hoặc digest được pipeline promote qua environments.

### Medium — Resource sizing có dấu hiệu tùy ý

**Vấn đề:** Request/limit CPU và memory rất thấp nhưng không có evidence workload.

**Tại sao xảy ra:** Static numbers không dựa trên CPU throttling, working set, GC, startup profile hay load test.

**Ảnh hưởng production:** CPU throttling có thể kéo dài startup/request latency; memory limit quá thấp có thể dẫn đến OOMKill.

**Cách sửa:** Đo CPU usage/throttling, memory working set, GC, OOM events và load profile rồi size requests/limits; không kết luận chỉ từ con số YAML.

### Medium — `terminationGracePeriodSeconds: 5` có thể quá ngắn

**Vấn đề:** Pod chỉ có 5 giây để dừng.

**Tại sao xảy ra:** In-flight requests/background cleanup có thể cần lâu hơn.

**Ảnh hưởng production:** Request bị cắt, partial work hoặc connection reset trong rollout.

**Cách sửa:** Đo request duration/shutdown behavior; cấu hình grace period và application cancellation/drain phù hợp. Với work durable, bảo đảm redelivery/idempotency.

### Medium — Không thể hiện graceful traffic drain

**Vấn đề:** Snippet không cho thấy lifecycle/drain strategy khi Pod terminate.

**Tại sao xảy ra:** Endpoint removal, load-balancer propagation và process shutdown có timing khác nhau.

**Ảnh hưởng production:** Pod có thể nhận/đang xử lý request gần termination rồi bị kill.

**Cách sửa:** Thiết kế readiness transition/termination behavior phù hợp ingress/service topology; validate thực tế thay vì chỉ thêm sleep tùy ý.

### Medium — Probe endpoint có thể tự gây tải downstream

**Vấn đề:** Mỗi Pod probe rất thường xuyên và `/health` gọi ba dependencies.

**Tại sao xảy ra:** Health check trở thành active dependency traffic.

**Ảnh hưởng production:** Khi scale lớn, probes làm tăng QPS và có thể góp phần vào dependency degradation.

**Cách sửa:** Health checks phải nhẹ, có timeout và semantics rõ; tránh expensive queries/calls. Dùng telemetry riêng cho dependency health khi thích hợp.

```yaml
            - containerPort: 8080
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 18
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
```

Các giá trị resource/probe ở trên chỉ là **điểm khởi đầu minh họa**, không phải production recommendation cố định. Cần thay bằng số liệu từ startup distribution, request latency, CPU throttling, memory/GC và SLO thực tế.

## Giải thích thiết kế sau khi sửa

`startupProbe` dành riêng budget cho startup/warm-up; sau khi startup thành công, liveness mới có quyền quyết định restart. `/health/live` không nên fail chỉ vì SQL/Redis/third-party tạm thời unavailable nếu process vẫn healthy. `/health/ready` phản ánh “Pod có nên nhận traffic mới không?” và chỉ nên phụ thuộc các điều kiện thật sự khiến instance không thể phục vụ request theo contract.

Rollout strategy phải giữ đủ capacity. Nếu bốn replicas đang chạy gần 70–80% capacity, mất hai replicas là nguy hiểm; nếu cluster cho phép surge, thêm một Pod tạm thời thường an toàn hơn. Nhưng giá trị chính xác cần load/capacity evidence.

Resource limits cũng không thể review chỉ bằng “tăng lên”. Với .NET cần quan sát CPU throttling, working set, GC heap, allocation rate, OOMKilled và startup/request profile. Nếu CPU limit gây throttling, startup probe budget chỉ che symptom chứ không sửa capacity problem.

## Trade-offs

Startup probe budget dài tránh false restart nhưng cũng làm detection của một startup thực sự stuck chậm hơn. Readiness quá nhạy giảm traffic vào instance degraded nhưng có thể tạo capacity collapse; quá lỏng lại gửi traffic vào Pod không phục vụ được. `maxSurge` tăng rollout safety nhưng cần cluster headroom/cost. Grace period dài bảo vệ in-flight work nhưng làm termination/rollout chậm hơn.

## Cách kiểm thử

- **Deployment validation:** inject startup delay 70 giây; Pod không bị liveness kill và chỉ Ready sau khi startup hoàn tất.
- **Failure-path test:** làm SQL/Redis/third-party degraded riêng lẻ; xác nhận liveness không restart process và readiness phản ánh đúng degraded-service contract.
- **Load test:** rollout dưới production-like load; theo dõi available replicas, p95/p99, error rate và CPU throttling.
- **Termination test:** gửi long-running requests rồi terminate Pod; xác nhận behavior trong grace period và không tạo partial side effects ngoài contract.
- **Resource test:** chạy representative workload để xác nhận memory headroom, GC behavior, throttling và OOM margin.

## Quan sát trong production

Theo dõi Pod restart count/reasons, `CrashLoopBackOff`, readiness transitions, rollout duration, available replicas, CPU throttling, CPU/memory working set, OOMKilled, .NET GC metrics, request p50/p95/p99, 5xx, ingress 502/503, SQL/Redis/dependency latency và connection counts. Correlate deployment version/image digest với Application Insights request/dependency telemetry. Alert theo user-impact/SLO và restart anomalies, không chỉ theo một probe failure đơn lẻ.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Redis chỉ dùng cache-aside và application có thể fallback SQL, Redis outage có nên làm readiness fail không? Điều gì quyết định câu trả lời?
2. Nếu cluster không còn headroom cho `maxSurge: 1`, bạn sẽ cân bằng rollout safety và capacity thế nào?
3. Nếu startup probe luôn cần 5 phút sau khi tăng data volume, bạn sẽ tăng threshold hay điều tra lại startup architecture trước? Vì sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Optimistic concurrency không phải transient failure; conflict có thể mang business semantics và không được retry mù quáng.
- Concurrency precondition phải gắn với version mà client thực sự đã quan sát, không phải version server vừa đọc lại ngay trước write.
- Kubernetes startup, readiness và liveness là ba quyết định khác nhau; dùng cùng dependency-heavy endpoint có thể biến degradation thành restart storm.
- Rollout safety phụ thuộc capacity thực tế, probe semantics, resource headroom và graceful termination chứ không chỉ việc manifest deploy thành công.

## Mẫu tư duy cần nhớ

- Phân biệt **business conflict** với **transient infrastructure failure** trước khi retry.
- Giữ nguyên precondition của operation xuyên suốt read → decision → write.
- Thiết kế health signal theo quyết định mà platform sẽ thực hiện khi signal fail.
- Đo capacity và failure behavior trước khi chọn threshold/resource/rollout numbers.
- Test failure path và race condition, không chỉ happy path.
