# Code Review Challenge 1 — Consumer thanh toán xử lý trùng dưới tải cao

**Chủ đề:** Concurrency, background processing, idempotency, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service nhận message `PaymentCaptured` từ RabbitMQ. Mỗi message cập nhật invoice và gửi email xác nhận. Broker có thể redeliver message khi consumer mất kết nối hoặc process chết trước khi ACK. Production thỉnh thoảng ghi nhận khách hàng nhận hai email và một số invoice có trạng thái bất thường khi nhiều instance chạy đồng thời. Business yêu cầu không được ghi nhận cùng payment hai lần, nhưng email có thể retry nếu lần đầu thất bại.

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _email;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(AppDbContext db, IEmailSender email,
        ILogger<PaymentConsumer> logger)
    {
        _db = db;
        _email = email;
        _logger = logger;
    }

    public async Task HandleAsync(PaymentCaptured message)
    {
        _logger.LogInformation("Processing payment {PaymentId} for {Email}",
            message.PaymentId, message.CustomerEmail);

        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId);

        if (alreadyProcessed)
            return;

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId);

        invoice.PaidAmount += message.Amount;
        invoice.Status = invoice.PaidAmount >= invoice.Total
            ? "Paid"
            : "PartiallyPaid";

        await _db.SaveChangesAsync();

        await _email.SendPaymentReceiptAsync(
            message.CustomerEmail,
            message.PaymentId,
            message.Amount);

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không atomic — Critical

**Problem:** `AnyAsync()` và việc thêm `ProcessedMessage` nằm ở hai thời điểm riêng biệt.  
**Why:** Hai consumer có thể cùng thấy `false`.  
**Impact:** Cùng payment có thể cập nhật invoice nhiều lần.  
**Fix:** Dùng invariant được enforce bởi database, ví dụ unique index trên idempotency key, và thực hiện thay đổi business + ghi nhận inbox/idempotency trong cùng transaction.

### 2. Marker idempotency được ghi quá muộn — Critical

**Problem:** invoice được commit trước khi message được đánh dấu processed.  
**Why:** crash sau commit đầu tiên khiến redelivery chạy lại business mutation.  
**Impact:** `PaidAmount` bị cộng lần nữa.  
**Fix:** Một transaction chứa idempotency record và invoice mutation.

### 3. Side effect email không atomic với database — High

**Problem:** gửi email nằm giữa hai database commits.  
**Why:** không thể rollback email đã gửi bằng DB transaction.  
**Impact:** email trùng hoặc invoice đã cập nhật nhưng email thất bại.  
**Fix:** ghi `PaymentReceiptRequested` vào outbox cùng transaction; worker riêng gửi và retry idempotently.

### 4. Lost update trên invoice — High

**Problem:** read-modify-write không có concurrency policy rõ ràng.  
**Why:** hai payment khác nhau cho cùng invoice có thể đọc cùng giá trị cũ.  
**Impact:** tổng tiền có thể sai tùy concurrency behavior/schema.  
**Fix:** optimistic concurrency token + retry có kiểm soát, hoặc atomic database update/locking phù hợp invariant.

### 5. Idempotency key chưa gắn với business invariant — High

**Problem:** chỉ deduplicate theo `MessageId`.  
**Why:** producer có thể phát cùng payment với message ID khác.  
**Impact:** cùng payment business vẫn được áp dụng hai lần.  
**Fix:** xác định unique business key như `PaymentId`; có thể giữ cả message ID để tracing.

### 6. Không truyền cancellation token — Medium

**Problem:** EF/email calls không nhận cancellation.  
**Impact:** shutdown/deployment có thể kéo dài và tăng xử lý dang dở.  
**Fix:** nhận `CancellationToken` và truyền xuyên suốt; thiết kế ACK/retry theo outcome.

### 7. Logging PII không có policy rõ ràng — Medium

**Problem:** email khách hàng được ghi trực tiếp.  
**Impact:** tăng exposure của PII trong log store.  
**Fix:** log customer ID hoặc masked value nếu email không thực sự cần thiết.

## Phiên bản code đề xuất

```csharp
public sealed class PaymentConsumer
{
    private readonly AppDbContext _db;

    public PaymentConsumer(AppDbContext db) => _db = db;

    public async Task HandleAsync(PaymentCaptured message, CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        if (await _db.ProcessedPayments
            .AnyAsync(x => x.PaymentId == message.PaymentId, ct))
            return;

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId, ct);

        invoice.PaidAmount += message.Amount;
        invoice.Status = invoice.PaidAmount >= invoice.Total
            ? "Paid"
            : "PartiallyPaid";

        _db.ProcessedPayments.Add(new ProcessedPayment
        {
            PaymentId = message.PaymentId,
            MessageId = message.MessageId,
            ProcessedAtUtc = DateTime.UtcNow
        });

        _db.OutboxMessages.Add(OutboxMessage.Create(
            "PaymentReceiptRequested",
            new { message.PaymentId, message.CustomerEmail, message.Amount }));

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

`ProcessedPayments.PaymentId` cần unique constraint. Transaction không thay thế unique constraint: constraint là lớp bảo vệ invariant khi có concurrent requests. Nếu invoice có thể nhận nhiều payment đồng thời, cần thêm concurrency strategy cho invoice. Outbox dispatcher chịu trách nhiệm gửi email và đánh dấu outbox item đã dispatch; downstream email operation cũng nên có idempotency strategy nếu provider/API hỗ trợ hoặc service tự lưu delivery key.

## Trade-offs

Unique constraint + transaction đơn giản và phù hợp modular monolith, nhưng contention có thể tăng nếu cùng invoice bị cập nhật rất thường xuyên. Optimistic concurrency phù hợp khi conflict hiếm; atomic SQL update hoặc serialization/locking có thể hợp lý hơn nếu conflict cao. Outbox tăng schema và worker vận hành nhưng tách rõ database commit khỏi unreliable external side effect.

## Cách kiểm thử

1. Gửi đồng thời 20 bản sao cùng `PaymentId`: invoice chỉ tăng đúng một lần.
2. Giả lập crash sau DB commit nhưng trước ACK: redelivery không áp dụng payment lần hai.
3. Hai payment khác nhau cùng invoice chạy song song: tổng cuối cùng phải chính xác.
4. Email provider timeout: transaction business vẫn đúng và outbox retry được.
5. Test unique constraint trực tiếp ở integration/database layer.

## Quan sát trong production

Theo dõi `duplicate_payment_detected_total`, outbox backlog/age, retry count, dead-letter count, concurrency-conflict rate và payment-processing latency. Trace nên liên kết `MessageId`, `PaymentId`, invoice ID và outbox ID. Alert khi outbox oldest-age vượt SLO hoặc DLQ tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu payment provider không cung cấp idempotency key ổn định, bạn thiết kế deduplication thế nào?
2. Tại sao distributed transaction giữa database và email provider thường không phải lựa chọn đầu tiên?
3. Nếu throughput tăng 100 lần và nhiều payment cùng chạm một invoice, bạn thay đổi concurrency strategy ra sao?

# Code Review Challenge 2 — API tìm kiếm audit log: authorization và SQL động

**Chủ đề:** Authorization, SQL injection, sensitive-data exposure, query performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Một API nội bộ cho phép support team tra cứu audit log của nhiều tenant. Endpoint chạy trên ASP.NET Core, PostgreSQL và Dapper. Sau khi thêm filter/sort linh hoạt, security review phát hiện nguy cơ tenant data leakage; production cũng có một số truy vấn mất nhiều giây khi người dùng tìm khoảng thời gian lớn.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly NpgsqlDataSource _dataSource;
    private readonly ILogger<AuditController> _logger;

    public AuditController(NpgsqlDataSource dataSource,
        ILogger<AuditController> logger)
    {
        _dataSource = dataSource;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        string tenantId,
        string? text,
        string sort = "created_at desc",
        int page = 1,
        int pageSize = 100)
    {
        var sql = $"""
            select id, tenant_id, user_email, action, payload, created_at
            from audit_logs
            where tenant_id = '{tenantId}'
              and ('{text}' is null or payload::text ilike '%{text}%')
            order by {sort}
            offset {(page - 1) * pageSize}
            limit {pageSize}
            """;

        _logger.LogInformation("Audit query: {Sql}", sql);

        await using var connection = await _dataSource.OpenConnectionAsync();
        var rows = await connection.QueryAsync<AuditRow>(sql);
        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant authorization — Critical

**Problem:** bất kỳ authenticated user nào cũng truyền `tenantId`.  
**Why:** `[Authorize]` chỉ yêu cầu identity hợp lệ, không chứng minh user được đọc tenant được yêu cầu.  
**Impact:** cross-tenant data exposure.  
**Fix:** resolve tenant từ trusted claims/membership service và enforce authorization policy/resource authorization.

### 2. SQL injection qua `tenantId`, `text`, `sort` — Critical

**Problem:** dữ liệu client được interpolate vào SQL.  
**Impact:** đọc/sửa dữ liệu trái phép tùy quyền DB account.  
**Fix:** parameterize values; `sort` phải map từ allow-list tới SQL expression cố định.

### 3. Sensitive payload trả và log quá rộng — High

**Problem:** trả `payload` + `user_email` nguyên trạng và log full SQL chứa input.  
**Impact:** secret/PII có thể lan sang client hoặc logging system.  
**Fix:** DTO tối thiểu, redaction, authorization theo field/use case; structured log không chứa raw payload/query.

### 4. Page/pageSize không validation — High

**Problem:** client có thể yêu cầu size rất lớn hoặc giá trị bất hợp lệ.  
**Impact:** memory/DB pressure và abuse.  
**Fix:** giới hạn range; ví dụ `1..200` theo SLO thực tế.

### 5. Expensive unbounded text search — High

**Problem:** cast JSON/payload thành text rồi contains search có thể scan lượng dữ liệu lớn.  
**Impact:** latency và CPU/I/O tăng mạnh.  
**Fix:** bắt buộc time range hợp lý; index/search strategy phù hợp field thực sự cần tìm; xem `EXPLAIN (ANALYZE, BUFFERS)` trên dữ liệu đại diện.

### 6. OFFSET pagination giảm hiệu quả ở trang sâu — Medium

**Problem:** database vẫn phải đi qua nhiều row trước offset.  
**Fix:** keyset/cursor pagination theo `(created_at, id)` nếu UX phù hợp.

### 7. Cancellation không truyền xuống DB — Medium

**Fix:** nhận `CancellationToken` và truyền vào open/query command.

## Phiên bản code đề xuất

```csharp
[HttpGet]
public async Task<IActionResult> Search(
    string? text,
    string sort = "newest",
    int pageSize = 100,
    CancellationToken ct = default)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (tenantId is null)
        return Forbid();

    pageSize = Math.Clamp(pageSize, 1, 200);

    var orderBy = sort switch
    {
        "oldest" => "created_at asc, id asc",
        "newest" => "created_at desc, id desc",
        _ => "created_at desc, id desc"
    };

    var sql = $"""
        select id, action, created_at
        from audit_logs
        where tenant_id = @TenantId
          and (@Text is null or payload::text ilike '%' || @Text || '%')
        order by {orderBy}
        limit @PageSize
        """;

    await using var connection = await _dataSource.OpenConnectionAsync(ct);
    var command = new CommandDefinition(
        sql,
        new { TenantId = tenantId, Text = text, PageSize = pageSize },
        cancellationToken: ct);

    var rows = await connection.QueryAsync<AuditSummary>(command);
    return Ok(rows);
}
```

Đây mới là baseline an toàn hơn, chưa phải tối ưu cuối cùng. Production design nên có time-range bắt buộc, cursor pagination, explicit authorization cho support/admin cross-tenant use case và search/index design dựa trên fields cần truy vấn thay vì mặc định scan toàn bộ JSON text.

## Trade-offs

Claims-based tenant resolution đơn giản nhưng cần bảo đảm token lifecycle và membership changes được xử lý đúng; với support cross-tenant nên dùng explicit privileged workflow và audit chính thao tác đó. Keyset pagination nhanh và ổn định hơn ở dataset lớn nhưng khó hỗ trợ “nhảy tới trang N”. Full-text/trigram/search engine có thể cải thiện search nhưng tăng storage và operational complexity.

## Cách kiểm thử

1. User tenant A cố truy cập tenant B: phải bị từ chối dù thay query parameters.
2. Payload như `' OR 1=1 --` và malicious sort string không thay đổi SQL semantics.
3. `pageSize` cực lớn/âm được reject hoặc clamp theo contract.
4. Load test trên dataset production-like, bao gồm search range lớn và cursor sâu.
5. Kiểm tra response/log không chứa field nhạy cảm ngoài policy.

## Quan sát trong production

Theo dõi query latency p50/p95/p99, rows scanned/returned, DB CPU/I/O, timeout rate và authorization-denied count. Dùng tracing từ HTTP tới database; quan sát slow-query log/query plan cho query shape quan trọng. Alert khi latency/error vượt SLO, không log raw search payload nếu có thể chứa dữ liệu nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support bắt buộc search nhiều tenant, bạn thiết kế authorization và audit trail thế nào?
2. Khi nào PostgreSQL trigram/full-text search đủ tốt và khi nào nên cân nhắc search engine riêng?
3. Parameterization có bảo vệ `ORDER BY @sort` không? Vì sao allow-list phù hợp hơn?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào hai boundary thường gây incident nghiêm trọng: **message processing boundary** và **authorization/data boundary**. Với messaging, “at-least-once delivery” phải được giả định có duplicate; idempotency cần database-enforced invariant và external side effects cần chiến lược riêng như outbox. Với multi-tenant API, authentication không đồng nghĩa authorization; tenant isolation phải được enforce từ trusted identity context. SQL parameterization, data minimization và bounded query design là các lớp bảo vệ độc lập.

- Thiết kế retry cùng idempotency; đừng xử lý chúng tách rời.
- Đưa invariant xuống database thay vì chỉ dựa vào check trong application.
- Phân biệt database transaction với external side effect.
- Authentication trước, authorization theo resource/tenant sau.
- Parameterize values; allow-list identifiers; đo query plan trước khi tối ưu.
