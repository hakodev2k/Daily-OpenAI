# Code Review Challenge 1 — Đồng bộ 50.000 nhân viên bằng EF Core làm memory tăng vọt và dữ liệu cập nhật dở dang

**Chủ đề:** EF Core tracking, transaction handling, memory/allocation, performance, cancellation, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một background worker chạy mỗi đêm để đồng bộ nhân viên từ hệ thống directory về database nội bộ. Mỗi lần chạy có thể nhận 30.000–50.000 bản ghi, gồm cả nhân viên mới và nhân viên đã tồn tại.

Production ghi nhận memory tăng mạnh trong lúc job chạy, job chậm dần theo thời gian, và nếu một record gần cuối batch vi phạm constraint thì toàn bộ `SaveChangesAsync` thất bại. Khi deploy/restart giữa chừng, team cũng khó biết chính xác record nào đã được xử lý.

Yêu cầu business là không được tạo duplicate employee theo `EmployeeCode`, job phải retry an toàn và không được gây tải database quá lớn cho API chính.

## Đoạn code cần review

```csharp
public sealed class EmployeeSyncService
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeeSyncService> _logger;

    public EmployeeSyncService(
        AppDbContext db,
        ILogger<EmployeeSyncService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task SyncAsync(
        IReadOnlyCollection<DirectoryEmployee> employees,
        CancellationToken cancellationToken)
    {
        foreach (var source in employees)
        {
            var employee = await _db.Employees
                .FirstOrDefaultAsync(
                    x => x.EmployeeCode == source.EmployeeCode,
                    cancellationToken);

            if (employee == null)
            {
                employee = new Employee
                {
                    EmployeeCode = source.EmployeeCode,
                    CreatedAt = DateTime.UtcNow
                };

                _db.Employees.Add(employee);
            }

            employee.DisplayName = source.DisplayName;
            employee.Email = source.Email;
            employee.Department = source.Department;
            employee.Title = source.Title;
            employee.IsActive = source.IsActive;
            employee.UpdatedAt = DateTime.UtcNow;

            _logger.LogInformation(
                "Prepared employee {EmployeeCode}",
                source.EmployeeCode);
        }

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Employee sync completed. Total={Total}",
            employees.Count);
    }
}
```

## Kết quả code review tham khảo

### 1. N+1 query cho lookup employee

**Problem:** Mỗi record thực hiện một `FirstOrDefaultAsync` riêng.  
**Why it happens:** Code kiểm tra tồn tại theo từng employee thay vì load tập key theo batch.  
**Production impact:** Hàng chục nghìn round-trip tới database làm job kéo dài và tăng load.  
**Severity:** High  
**Recommended fix:** Chia input thành batch, query tập `EmployeeCode` của batch một lần rồi map thành dictionary.

### 2. `DbContext` track quá nhiều entity

**Problem:** Entity được query và entity mới đều nằm trong Change Tracker tới cuối job.  
**Why it happens:** Một `DbContext` sống xuyên suốt batch rất lớn.  
**Production impact:** Memory tăng, change detection tốn chi phí hơn và job chậm dần.  
**Severity:** High  
**Recommended fix:** Dùng context theo batch hoặc `SaveChangesAsync` rồi clear tracker sau mỗi batch.

### 3. Một `SaveChangesAsync` duy nhất tạo failure domain quá lớn

**Problem:** Tất cả thay đổi chỉ commit ở cuối.  
**Why it happens:** Không có transaction/batch boundary trung gian.  
**Production impact:** Một lỗi dữ liệu ở cuối làm toàn bộ lần ghi thất bại và retry tốn kém.  
**Severity:** High  
**Recommended fix:** Commit theo batch với kích thước được benchmark thực tế.

### 4. Check-then-insert không đủ để chống duplicate dưới concurrency

**Problem:** Hai tiến trình có thể cùng thấy employee chưa tồn tại rồi cùng insert.  
**Why it happens:** Check ở application layer không tạo atomic guarantee.  
**Production impact:** Duplicate hoặc unique constraint exception khi job chạy chồng.  
**Severity:** High  
**Recommended fix:** Có unique constraint trên `EmployeeCode`; nếu nhiều worker có thể chạy đồng thời thì thêm single-run coordination hoặc xử lý conflict/upsert phù hợp.

### 5. Không có chiến lược phân loại lỗi dữ liệu và lỗi transient

**Problem:** Tất cả lỗi đều khiến job thất bại như nhau.  
**Why it happens:** Không có checkpoint, retry policy hoặc quarantine logic.  
**Production impact:** Job có thể retry vô hạn ở cùng record lỗi.  
**Severity:** High  
**Recommended fix:** Theo dõi batch id, lỗi theo employee code và tách retry transient khỏi invalid-data handling.

### 6. Không normalize/validate input trước khi persistence

**Problem:** Key và field được dùng trực tiếp.  
**Why it happens:** Mapping và validation trộn trong cùng vòng lặp.  
**Production impact:** Whitespace/casing hoặc dữ liệu vượt giới hạn có thể gây duplicate logic hoặc batch fail.  
**Severity:** Medium  
**Recommended fix:** Normalize và validate trước khi xử lý; làm rõ comparison semantics theo business rule/database.

### 7. Logging per-record ở `Information`

**Problem:** Một run có thể tạo hàng chục nghìn log event.  
**Why it happens:** Không phân biệt diagnostic detail với operational summary.  
**Production impact:** Tăng log volume, chi phí lưu trữ và làm nhiễu dashboard.  
**Severity:** Medium  
**Recommended fix:** Log summary theo batch; per-record chỉ log khi lỗi hoặc ở mức debug.

### 8. Thiếu progress/checkpoint và metric

**Problem:** Chỉ có log tổng ở cuối job.  
**Why it happens:** Recovery và observability không được thiết kế cùng happy path.  
**Production impact:** Khi crash khó biết đã xử lý đến đâu và nguyên nhân chậm nằm ở đâu.  
**Severity:** Medium  
**Recommended fix:** Ghi run id, batch number, processed/inserted/updated/skipped/failed, duration và last successful checkpoint.

## Phiên bản code đề xuất

```csharp
public sealed class EmployeeSyncService
{
    private const int BatchSize = 500;

    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<EmployeeSyncService> _logger;

    public EmployeeSyncService(
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<EmployeeSyncService> logger)
    {
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task SyncAsync(
        IReadOnlyCollection<DirectoryEmployee> employees,
        CancellationToken cancellationToken)
    {
        var normalized = employees
            .Where(x => !string.IsNullOrWhiteSpace(x.EmployeeCode))
            .GroupBy(x => x.EmployeeCode.Trim(), StringComparer.OrdinalIgnoreCase)
            .Select(g => g.Last())
            .ToArray();

        var processed = 0;
        var inserted = 0;
        var updated = 0;

        foreach (var batch in normalized.Chunk(BatchSize))
        {
            cancellationToken.ThrowIfCancellationRequested();

            await using var db =
                await _dbFactory.CreateDbContextAsync(cancellationToken);

            var timestamp = DateTime.UtcNow;
            var codes = batch
                .Select(x => x.EmployeeCode.Trim())
                .ToArray();

            var existing = await db.Employees
                .Where(x => codes.Contains(x.EmployeeCode))
                .ToDictionaryAsync(x => x.EmployeeCode, cancellationToken);

            foreach (var source in batch)
            {
                var code = source.EmployeeCode.Trim();

                if (!existing.TryGetValue(code, out var employee))
                {
                    employee = new Employee
                    {
                        EmployeeCode = code,
                        CreatedAt = timestamp
                    };

                    db.Employees.Add(employee);
                    existing[code] = employee;
                    inserted++;
                }
                else
                {
                    updated++;
                }

                employee.DisplayName = source.DisplayName?.Trim();
                employee.Email = source.Email?.Trim();
                employee.Department = source.Department?.Trim();
                employee.Title = source.Title?.Trim();
                employee.IsActive = source.IsActive;
                employee.UpdatedAt = timestamp;
            }

            await db.SaveChangesAsync(cancellationToken);
            processed += batch.Length;

            _logger.LogInformation(
                "Employee sync batch completed. Processed={Processed} Inserted={Inserted} Updated={Updated}",
                processed,
                inserted,
                updated);
        }
    }
}
```

Database vẫn cần unique constraint trên `EmployeeCode`. Nếu nhiều worker có thể chạy đồng thời, cần single-run coordination hoặc conflict handling rõ ràng. `BatchSize = 500` chỉ là điểm khởi đầu và cần benchmark.

## Trade-offs

- Batch nhỏ giảm memory/failure domain nhưng tăng số lần commit.
- Batch lớn giảm overhead transaction nhưng tăng lock duration và rollback cost.
- `IDbContextFactory` giúp lifetime rõ ràng; scope per batch cũng là một lựa chọn hợp lệ.
- Với volume rất lớn, staging table hoặc bulk operation có thể phù hợp hơn nhưng làm persistence phức tạp hơn.
- Nếu business yêu cầu toàn bộ sync phải atomic, transaction design sẽ khác và cần cân nhắc lock/log growth.

## Bối cảnh

Một endpoint ASP.NET Core cho phép người dùng export timesheet của một project thành CSV. Với project nhỏ endpoint hoạt động tốt, nhưng một số project có 500.000–1.500.000 timesheet entries.

Production ghi nhận memory tăng mạnh khi nhiều người export cùng lúc, response chỉ bắt đầu tải sau thời gian dài, và ngay cả khi người dùng đóng browser thì server đôi lúc vẫn tiếp tục query/serialize dữ liệu. Database cũng bị tăng CPU trong giờ cao điểm.

Business muốn giữ CSV export nhưng không muốn endpoint làm ảnh hưởng các request thông thường.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/timesheets")]
public sealed class TimesheetExportController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<TimesheetExportController> _logger;

    public TimesheetExportController(
        AppDbContext db,
        ILogger<TimesheetExportController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("export")]
    public async Task<IActionResult> Export(Guid projectId)
    {
        var entries = await _db.TimesheetEntries
            .Where(x => x.ProjectId == projectId)
            .OrderBy(x => x.WorkDate)
            .ThenBy(x => x.Id)
            .ToListAsync();

        var csv = new StringBuilder();
        csv.AppendLine("Date,Employee,Hours,Note");

        foreach (var entry in entries)
        {
            csv.Append(entry.WorkDate.ToString("yyyy-MM-dd"));
            csv.Append(',');
            csv.Append(entry.EmployeeName);
            csv.Append(',');
            csv.Append(entry.Hours);
            csv.Append(',');
            csv.Append(entry.Note);
            csv.AppendLine();
        }

        var bytes = Encoding.UTF8.GetBytes(csv.ToString());

        _logger.LogInformation(
            "Exported {Count} rows for project {ProjectId}",
            entries.Count,
            projectId);

        return File(bytes, "text/csv", $"timesheet-{projectId}.csv");
    }
}
```

## Kết quả code review tham khảo

### 1. `ToListAsync` materialize toàn bộ dataset

**Problem:** Hàng trăm nghìn đến hơn một triệu entity được load vào memory cùng lúc.  
**Why it happens:** Query được materialize bằng `ToListAsync`.  
**Production impact:** Working set tăng mạnh, GC pressure cao và concurrent exports có thể dẫn tới OOM.  
**Severity:** High  
**Recommended fix:** Dùng projection và streaming/iteration tuần tự hoặc batch pagination phù hợp.

### 2. Query tracking không cần thiết cho read-only export

**Problem:** EF Core mặc định có thể track entity trong query read-write context.  
**Why it happens:** Không dùng `AsNoTracking` hoặc projection DTO rõ ràng.  
**Production impact:** Tăng memory và Change Tracker overhead không cần thiết.  
**Severity:** High  
**Recommended fix:** Dùng `AsNoTracking()` và `Select` chỉ các cột cần export.

### 3. `StringBuilder` giữ toàn bộ CSV trong memory

**Problem:** Sau khi đã giữ toàn bộ entities, code tiếp tục xây một chuỗi CSV lớn.  
**Why it happens:** Serialization hoàn tất trước khi response bắt đầu.  
**Production impact:** Memory amplification và time-to-first-byte lớn.  
**Severity:** High  
**Recommended fix:** Ghi từng dòng trực tiếp vào `Response.Body` hoặc stream trung gian bounded.

### 4. `csv.ToString()` rồi `Encoding.UTF8.GetBytes` tạo thêm bản sao lớn

**Problem:** Nội dung CSV tồn tại dưới dạng `StringBuilder`, `string` và `byte[]`.  
**Why it happens:** Toàn bộ output được chuyển đổi trước khi trả về.  
**Production impact:** Peak memory có thể cao hơn nhiều so với file cuối cùng.  
**Severity:** High  
**Recommended fix:** Dùng `StreamWriter` trên response stream và ghi incremental.

### 5. Không propagate cancellation

**Problem:** `ToListAsync()` không nhận `RequestAborted`; loop cũng không kiểm tra cancellation.  
**Why it happens:** Endpoint bỏ qua lifecycle của HTTP request.  
**Production impact:** Client đóng browser nhưng server vẫn query và build CSV, lãng phí DB/CPU/memory.  
**Severity:** High  
**Recommended fix:** Truyền `HttpContext.RequestAborted` cho EF và kiểm tra token trong quá trình export.

### 6. CSV escaping không đúng

**Problem:** `EmployeeName` hoặc `Note` chứa comma, quote hoặc newline sẽ làm hỏng định dạng CSV.  
**Why it happens:** Giá trị được append trực tiếp.  
**Production impact:** File import sang Excel/tool khác có cột lệch hoặc nội dung sai.  
**Severity:** Medium  
**Recommended fix:** Implement CSV escaping đúng hoặc dùng thư viện CSV phù hợp.

### 7. Query tải cả entity thay vì field cần thiết

**Problem:** Có thể đọc nhiều column không cần cho export.  
**Why it happens:** Query materialize `TimesheetEntry` đầy đủ.  
**Production impact:** Tăng network I/O, materialization cost và memory.  
**Severity:** Medium  
**Recommended fix:** `Select` đúng các field cần xuất.

### 8. Không có guardrail cho concurrent exports

**Problem:** Nhiều export lớn có thể chạy cùng lúc.  
**Why it happens:** Endpoint xử lý mọi request như request bình thường.  
**Production impact:** DB CPU, connection pool và app memory bị cạnh tranh với API chính.  
**Severity:** High  
**Recommended fix:** Đặt concurrency limit/rate limit hoặc chuyển export rất lớn sang background generation tùy SLA.

### 9. Thiếu observability về kích thước và thời gian export

**Problem:** Chỉ log số rows sau khi hoàn tất.  
**Why it happens:** Không instrument các stage.  
**Production impact:** Khó biết bottleneck nằm ở DB, serialization hay client throughput.  
**Severity:** Medium  
**Recommended fix:** Theo dõi row count, query duration, total duration, bytes written, cancellation và active exports.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/timesheets")]
public sealed class TimesheetExportController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<TimesheetExportController> _logger;

    public TimesheetExportController(
        AppDbContext db,
        ILogger<TimesheetExportController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("export")]
    public async Task Export(Guid projectId)
    {
        var cancellationToken = HttpContext.RequestAborted;

        Response.ContentType = "text/csv; charset=utf-8";
        Response.Headers.ContentDisposition =
            $"attachment; filename=timesheet-{projectId}.csv";

        await using var writer = new StreamWriter(
            Response.Body,
            new UTF8Encoding(encoderShouldEmitUTF8Identifier: false),
            bufferSize: 64 * 1024,
            leaveOpen: true);

        await writer.WriteLineAsync("Date,Employee,Hours,Note");

        var query = _db.TimesheetEntries
            .AsNoTracking()
            .Where(x => x.ProjectId == projectId)
            .OrderBy(x => x.WorkDate)
            .ThenBy(x => x.Id)
            .Select(x => new
            {
                x.WorkDate,
                x.EmployeeName,
                x.Hours,
                x.Note
            })
            .AsAsyncEnumerable();

        var count = 0;

        await foreach (var entry in query.WithCancellation(cancellationToken))
        {
            var line = string.Join(",",
                EscapeCsv(entry.WorkDate.ToString("yyyy-MM-dd")),
                EscapeCsv(entry.EmployeeName),
                EscapeCsv(entry.Hours.ToString(CultureInfo.InvariantCulture)),
                EscapeCsv(entry.Note));

            await writer.WriteLineAsync(line);
            count++;

            if (count % 1000 == 0)
                await writer.FlushAsync(cancellationToken);
        }

        await writer.FlushAsync(cancellationToken);

        _logger.LogInformation(
            "Timesheet export completed. ProjectId={ProjectId} Rows={Rows}",
            projectId,
            count);
    }

    private static string EscapeCsv(string? value)
    {
        value ??= string.Empty;

        if (value.Contains(',') || value.Contains('"') ||
            value.Contains('\r') || value.Contains('\n'))
        {
            return $"\"{value.Replace("\"", "\"\"")}\"";
        }

        return value;
    }
}
```

## Trade-offs

- Streaming giảm peak memory và time-to-first-byte nhưng khi response đã bắt đầu thì khó trả lỗi HTTP đẹp nếu lỗi xảy ra giữa export.
- Export dài vẫn giữ database query/connection lâu; với dataset cực lớn có thể dùng batch/keyset pagination hoặc background generation.
- Flush quá thường xuyên tăng I/O overhead; flush quá ít làm dữ liệu nằm trong buffer lâu hơn.
- Background export tăng độ bền và kiểm soát concurrency nhưng cần job status, storage, retention và cleanup.

## Cách kiểm thử

1. **Large dataset integration test:** export hơn 1 triệu rows, xác nhận memory giữ ổn định hơn cách materialize toàn bộ.
2. **CSV correctness test:** dữ liệu chứa comma, quote, newline và Unicode, xác nhận file parse đúng.
3. **Cancellation test:** ngắt request giữa chừng, xác nhận query/serialization dừng sớm.
4. **Load test:** chạy nhiều export đồng thời với API traffic thông thường, đo DB CPU, pool usage, latency và memory.
5. **Failure-path test:** database timeout hoặc exception giữa stream, xác nhận log/tracing đủ để điều tra và resource được release.

## Quan sát trong production

Nên theo dõi:

- active exports
- export duration
- rows exported
- bytes written
- cancelled exports
- failed exports theo reason
- DB query duration, connection pool pressure
- working set, GC heap, Gen 2 collections
- API p95/p99 latency khi export chạy đồng thời
- alert khi active export hoặc DB load vượt threshold vận hành

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển export từ synchronous streaming sang background job?
2. Nếu export cần snapshot-consistent data trong suốt 30 phút, bạn xử lý consistency như thế nào?
3. Nếu client download rất chậm, backpressure ảnh hưởng database query và resource lifetime ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với EF Core batch lớn, phải kiểm soát **query round-trip, Change Tracker lifetime, transaction boundary và retry semantics** cùng lúc.
- Database invariant như uniqueness phải được bảo vệ ở database, không chỉ bằng application-level check.
- Large export cần nhìn như một data pipeline: **DB → materialization → serialization → network**.
- Streaming giảm memory nhưng tạo trade-off về error handling, connection lifetime và backpressure.
- Cancellation và observability là một phần của production design, không phải phần bổ sung sau cùng.

## Mẫu tư duy cần nhớ

- Giảm failure domain bằng batch boundary rõ ràng.
- Đặt invariant quan trọng ở database.
- Stream thay vì buffer khi output lớn.
- Propagate cancellation xuyên suốt dependency chain.
- Thiết kế observability và recovery cùng happy path.
