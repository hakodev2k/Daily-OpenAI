# Câu 1 — Vì sao ASP.NET Core trả 200 nhưng dữ liệu JSON khác giữa các request?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18–22 phút  
**Kỹ năng được đánh giá:** ASP.NET Core middleware, HTTP caching, ETag, response compression, CDN, concurrency, diagnostics.

## Bối cảnh

Một API catalog .NET 8 cung cấp `GET /api/products/{id}` cho Vue.js. Origin có 4 instance Azure App Service, Akamai ở phía trước. Product có giá cập nhật nhiều lần mỗi ngày. Client đôi lúc nhận giá cũ sau khi backend đã ghi SQL Server thành công; cùng URL đôi lúc trả `200`, đôi lúc `304`. Nhóm vận hành thấy log controller ghi đúng giá mới, nhưng browser hiển thị giá cũ. Header thực tế chưa được cung cấp; chưa biết cache nằm ở browser, CDN hay ứng dụng. Một nhóm đề xuất tắt toàn bộ cache, nhóm khác đề xuất thêm Redis.

## Câu hỏi chính

Hãy giải thích cơ chế khiến cùng một URL có thể nhận `200` hoặc `304` và nội dung khác nhau, phân biệt các tầng caching/HTTP representation, rồi đề xuất cách xác minh và sửa mà không làm giảm hiệu năng một cách mù quáng.

## Câu hỏi làm rõ nên cân nhắc

1. API có yêu cầu authentication hoặc giá theo khách hàng/region không? Cache key có chứa các biến thể đó không?
2. `Cache-Control`, `ETag`, `Vary`, `Age`, `Last-Modified`, `Content-Encoding` và các header Akamai thực tế là gì?
3. `304` do browser conditional request hay do CDN revalidation? Có request thực sự đến origin không?
4. Giá mới được commit khi nào, và phiên bản product được tăng trong cùng transaction không?
5. Vue đang dùng browser cache, service worker hay client-side query cache nào?

## Gợi ý tư duy

### Gợi ý 1
Tách đường đi browser → CDN → origin → database; không giả định controller luôn chạy.

### Gợi ý 2
Xem xét freshness, validation và representation: `Cache-Control`, validator, `Vary`, key dimensions và compression.

### Gợi ý 3
Đối chiếu `Age` và validator qua các request; kiểm tra `304` có đi kèm representation body hay chỉ tái sử dụng body đã lưu.

## Cấu trúc trả lời đề xuất

1. Xác nhận scope dữ liệu, tính cá nhân hóa và mức stale chấp nhận được.
2. Vẽ request path và các nơi có thể lưu response.
3. Giải thích `200` vs `304` và điều kiện validator.
4. Thu thập evidence ở browser, edge, origin, SQL; lập nhiều giả thuyết.
5. Chọn chính sách cache theo loại dữ liệu, triển khai và rollback.
6. Kiểm thử consistency, security, performance và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc
Phân biệt cache freshness với conditional validation; `304 Not Modified` không có response body mới, client tái sử dụng cached representation; không kết luận database sai chỉ từ UI; kiểm tra cache key, variant, invalidation.

### Điểm cộng
Giải thích `Vary: Accept-Encoding`, strong/weak ETag, `private` vs `public`, `no-store` vs `no-cache`, CDN purge và cache key khi query/header/tenant thay đổi.

### Senior+
Thiết kế versioning/validator ổn định qua 4 instance, chính sách personalized pricing, contract test giữa browser/CDN/origin và staged rollout với rollback.

## Hướng giải quyết tham khảo

**Giả định:** Giá là dữ liệu public, không thay đổi theo user; nếu giá theo hợp đồng/tenant thì phải đổi thiết kế, tránh shared cache cho response cá nhân hóa. `200` mang representation; `304` là phản hồi cho conditional request khi validator còn phù hợp, browser/CDN dùng representation đã lưu. Không nên xem `304` là dấu hiệu backend trả JSON cũ.

**Cơ chế:** Browser có thể dùng cache mà không gọi network nếu response fresh. Nếu stale, nó có thể gửi `If-None-Match` hoặc `If-Modified-Since`; một cache hoặc origin quyết định có trả `304` không. CDN cũng có TTL riêng và có thể phục vụ cached `200` mà origin không biết. Response compression tạo biến thể encoding; `Vary` và cách tạo ETag phải nhất quán với representation được phục vụ. HTTP `no-cache` cho phép lưu nhưng yêu cầu validation trước khi tái sử dụng; `no-store` cấm lưu theo semantics của cache tuân chuẩn. Redis là cache dữ liệu ứng dụng, không giải quyết tự động HTTP edge/browser caching.

**Điều tra:** Trong DevTools kiểm tra response/request headers, Initiator, service worker và cache status. Gửi requests có/không `Cache-Control: no-cache` để so sánh, nhưng không xem một header request là bằng chứng duy nhất vì CDN config có thể override. Thu thập Akamai cache status/edge logs và origin trace ID; ghi `productId`, `version`, `updatedAt`, `etag`, `cachePolicy`, `instanceId` không log giá riêng tư. So sánh `SELECT` trên primary và transaction commit; xác minh read replica nếu có. Kiểm tra application response caching/output caching, frontend state cache và invalidation sau mutation. Tách giả thuyết: TTL chưa hết; purge sai key; validator không đổi khi giá đổi; shared cache thiếu tenant dimension; client giữ state cũ; SQL read replica lag.

**Thiết kế:** Với public catalog chấp nhận stale ngắn, có thể dùng TTL ngắn và version-based ETag dựa trên dữ liệu đã commit, cùng cơ chế purge hoặc versioned URL nếu yêu cầu. Với giá phải chính xác ngay tại checkout, API tính giá cuối cùng từ nguồn authoritative tại thời điểm đặt hàng; không tin giá trên UI. Với personalized price, dùng `Cache-Control: private` hoặc `no-store` tùy sensitivity, không cho shared CDN lưu. Tránh đưa Authorization vào shared cache mà không có chính sách rõ ràng. Nếu dùng CDN stale-while-revalidate, cần chấp nhận stale theo requirement.

**Xác minh:** Test thay đổi giá rồi revalidate; test hai tenants với giá khác nhau; test gzip/Brotli variants; test purge lỗi và cache miss; load test trước/sau để so sánh p95, origin RPS, hit ratio, stale duration. Rollout theo canary và có công tắc cấu hình rollback; theo dõi `Age`, ETag mismatch, cache status, version lệch và complaint rate. Tài liệu tham khảo: [RFC 9111 HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111), [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110), [ASP.NET Core response caching](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/response).

## Mẫu trả lời trong phỏng vấn

“Tôi chưa kết luận lỗi ở SQL hay Vue vì controller log đúng không chứng minh response đến browser đi qua controller. Trước tiên tôi hỏi giá có personalized không, mức stale được chấp nhận bao lâu và kiểm tra request/response headers ở từng hop. `304` có nghĩa cache được phép dùng representation đang giữ sau khi validation, không phải origin gửi JSON mới. Tôi sẽ so sánh ETag, product version, `Age`, cache status tại Akamai, browser cache và trace origin; đồng thời kiểm tra service worker và frontend query cache. Nếu ETag không đổi dù product đã commit, tôi sửa validator; nếu edge chưa purge, sửa invalidation; nếu cache key thiếu tenant, tôi coi đó là lỗi security nghiêm trọng. Với public catalog, TTL ngắn có thể chấp nhận; với checkout, giá cuối phải kiểm tra lại từ nguồn authoritative. Tôi không tắt cache toàn hệ thống hay thêm Redis trước khi chứng minh nguyên nhân. Sau fix, tôi test nhiều variant, cập nhật giá, concurrent requests, đo stale duration và p95, rồi rollout có rollback.”

## Câu hỏi đào sâu

1. Nếu ETag được hash từ compressed bytes, làm sao đảm bảo validators đúng khi `Accept-Encoding` thay đổi?
2. Nếu product có giá theo từng tenant, có nên tiếp tục dùng shared CDN cache không? Bảo vệ cache key như thế nào?
3. Nếu business yêu cầu UI thấy giá mới trong 1 giây nhưng có hàng triệu users, bạn thay đổi giải pháp ra sao?

## Lỗi trả lời thường gặp

- Đồng nhất `304` với “server trả dữ liệu cũ” mà không xem cached representation.
- Đề xuất Redis hoặc tắt toàn bộ cache trước khi đo.
- Bỏ qua service worker/client cache và Akamai edge.
- Cache personalized response bằng key chỉ có product ID.
- Không test invalidation khi mutation xảy ra cùng lúc với requests.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ consistency và personalization | 1.5 |
| Giải thích HTTP/cache/validator chính xác | 2.5 |
| Evidence và giả thuyết có thể kiểm chứng | 2 |
| Thiết kế sửa, security, trade-offs | 2 |
| Test, telemetry, trình bày rõ | 2 |

# Câu 2 — Production incident: Azure Service Bus backlog tăng sau release, nhưng CPU vẫn thấp

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 22–28 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, .NET BackgroundService, dependency latency, lock renewal, DLQ, incident management, tracing.

## Bối cảnh

Hệ thống xử lý đơn hàng bằng .NET 8 worker chạy trên Azure App Service, nhận message từ Azure Service Bus queue. Sau release, queue depth tăng từ khoảng 200 lên 90.000 trong 40 phút; p95 thời gian hoàn tất đơn hàng tăng từ 4 giây lên 12 phút. CPU worker chỉ 18%; số lượng `DeliveryCount` cao hơn bình thường; có message chuyển DLQ. SQL Server và third-party fulfillment API đều có thể là nút nghẽn. Chưa biết `MaxConcurrentCalls`, lock duration, auto-renew, prefetch, timeout hay retry policy. Business yêu cầu không mất đơn và không charge khách hai lần.

## Câu hỏi chính

Bạn là incident lead. Hãy trình bày thứ tự hành động từ xác định impact, ổn định hệ thống, phân tích bằng evidence, tìm root cause có điều kiện, sửa lỗi và phòng tái diễn; giải thích cơ chế message lock và duplicate delivery.

## Câu hỏi làm rõ nên cân nhắc

1. Queue depth là active, scheduled hay DLQ? Ingress rate và completion rate biến đổi ra sao?
2. Message có `MessageId`/business order ID ổn định và consumer idempotent không?
3. `DeliveryCount`, `LockedUntil`, auto-renew, `MaxConcurrentCalls` và handler duration phân bố thế nào?
4. Release thay đổi timeout/retry/HTTP connection pool/SQL transaction hay scaling?
5. Có thể tạm ngừng upstream, giảm concurrency hoặc rollback mà không làm mất trạng thái không?

## Gợi ý tư duy

### Gợi ý 1
Đừng tăng worker count ngay; xác định service rate, failure rate và bottleneck.

### Gợi ý 2
Message lock, timeout, retries và idempotency có quan hệ chặt chẽ với duplicate delivery.

### Gợi ý 3
Phân tách thời gian queue wait, handler execution, SQL dependency, HTTP dependency và settle/complete; kiểm tra message bị redeliver sau khi side effect đã xảy ra.

## Cấu trúc trả lời đề xuất

1. Business impact và incident severity.
2. Containment không mất đơn/không duplicate charge.
3. Dashboard ingress, backlog, completion, abandonment, DLQ, dependency p95.
4. Giả thuyết cạnh tranh và test phân biệt.
5. Root cause chỉ sau khi có bằng chứng.
6. Hotfix/rollback, replay an toàn, prevention, test và alert.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không xem at-least-once delivery là exactly-once processing; xử lý idempotent bằng business key, không dựa chỉ vào lock; DLQ không tự biến mất; ưu tiên an toàn side effects.

### Điểm cộng
Phân biệt lock lost do quá thời gian, network/settlement failure, process restart; đo arrival rate và throughput, Little's Law chỉ khi giả định ổn định; phân tích retry amplification.

### Senior+
Có kế hoạch rollback tương thích schema, replay DLQ có audit, rate limiting/backpressure, reconciliation với payment provider và runbook đo recovery time.

## Hướng giải quyết tham khảo

**Tác động và containment:** Xác định số đơn đang chậm, số giao dịch thanh toán có trạng thái chưa rõ và thông báo stakeholders. Nếu đang có nguy cơ duplicate charge, tạm dừng consumer hoặc disable đoạn side effect không idempotent; nếu có thể, rollback bản release sau khi kiểm tra tương thích dữ liệu. Không xóa queue hoặc replay DLQ hàng loạt. Bảo toàn message IDs và correlation IDs; tách DLQ để triage.

**Cơ chế:** Với Peek-Lock, message được lock trong một khoảng; consumer xử lý và `CompleteMessageAsync` trước khi lock mất hiệu lực. Nếu lock hết hạn, consumer chết hoặc settlement không thành công, message có thể được nhận lại, tăng `DeliveryCount`. Auto lock renewal hỗ trợ xử lý dài nhưng không phải bảo đảm tuyệt đối; xử lý thành công ở SQL/fulfillment vẫn có thể đi trước lỗi complete. `MaxDeliveryCount` có thể đẩy message sang DLQ. Prefetch và concurrency không nên tăng vô điều kiện khi downstream đang nghẽn.

**Evidence:** Dùng Azure Monitor Service Bus metrics (active/dead-letter count, incoming/outgoing, errors) và Application Insights dependency spans. Với mỗi message, log `MessageId`, `orderId` dạng định danh an toàn, `DeliveryCount`, `LockedUntil`, handler start/end, completion outcome, dependency status, retry count, worker version, instance ID. So sánh trước/sau deployment; truy vấn SQL waits, blocking, connection pool saturation, third-party API 429/5xx/latency. Kiểm tra queue ingress vs successful completion; CPU thấp vẫn có thể là I/O waiting, lock contention hoặc throttling.

**Giả thuyết và phép thử:** (A) fulfillment API chậm/429 → dependency p95 và retry count tăng; (B) SQL locks → waits và transaction duration tăng; (C) timeout/lock renewal bị thay đổi → lock-lost exceptions và redelivery tăng dù dependency không chậm; (D) exception handling swallow lỗi hoặc hoàn tất sai → abandoned/dead-letter pattern; (E) scale/config làm giảm consumers. Root cause chỉ chọn khi evidence khớp, không khẳng định trước.

**Sửa:** Giới hạn concurrency theo downstream capacity, retry transient với exponential backoff và jitter có tổng thời gian hợp lý; không retry vô hạn trong lock. Idempotency bằng unique constraint `(consumerName, businessOperationId)` hoặc business-state transition có transaction; cần bảo vệ external charge bằng idempotency key của provider và reconciliation khi response không rõ. Inbox/Outbox có thể phù hợp nếu transaction DB + publish event cần atomic intent; không biến message broker thành distributed transaction. Retry/DLQ có phân loại permanent vs transient và quarantine. Nếu rollback, kiểm tra schema backward compatibility. Nếu chọn tăng capacity, chỉ sau khi biết throughput per instance và giới hạn dependency.

**Recovery:** Replay có rate limit, kiểm tra duplicate bằng business state, audit operator và DLQ reason. Alert theo backlog age (quan trọng hơn count đơn lẻ), completion-to-ingress ratio, handler p95, lock lost, delivery count, DLQ growth, external API failure. Test crash sau side effect trước complete, lock expiry, provider timeout, duplicate message, replay và rolling restart. Tài liệu: [Azure Service Bus message transfers, locks and settlement](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-transfers-locks-settlement), [Dead-letter queues](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-dead-letter-queues).

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ phân loại mức độ ảnh hưởng theo đơn hàng chậm và nguy cơ charge hai lần, rồi ổn định hệ thống trước. Backlog tăng với CPU thấp không đủ để kết luận cần scale; có thể worker chờ SQL hoặc fulfillment API, hoặc lock hết hạn gây xử lý lặp. Tôi xem ingress, completion, backlog age, DLQ, `DeliveryCount`, handler duration và dependency traces trước/sau release. Tôi lập ít nhất ba giả thuyết: dependency chậm, lock/timeout cấu hình sai, hoặc retry amplification. Nếu side effect chưa idempotent, tôi tạm ngừng hoặc giới hạn consumer để tránh thiệt hại, sau đó rollback an toàn nếu bản release là yếu tố kích hoạt. Peek-Lock không đảm bảo exactly-once; xử lý xong external API nhưng fail complete vẫn nhận lại message. Vì vậy charge phải có idempotency key và reconciliation. Khi khôi phục, tôi replay DLQ theo batch, kiểm tra state, theo dõi backlog age và duplicate suppression. Phòng ngừa bằng fault-injection tests, telemetry theo từng stage và runbook rollback.”

## Câu hỏi đào sâu

1. Nếu external provider không hỗ trợ idempotency key, làm sao giảm duplicate side effects và xử lý trạng thái không xác định?
2. Nếu tăng `MaxConcurrentCalls` làm queue rút nhanh nhưng SQL deadlock tăng, bạn xác định mức concurrency tối ưu thế nào?
3. Nếu một số messages luôn thất bại do dữ liệu, bạn thiết kế DLQ triage và replay như thế nào để không tạo vòng lặp vô hạn?

## Lỗi trả lời thường gặp

- Tăng số worker ngay khi thấy queue depth cao.
- Cho rằng `Complete` thành công là điều kiện duy nhất để side effect tồn tại.
- Dùng in-memory deduplication trên nhiều instance.
- Replay toàn bộ DLQ khi chưa biết permanent errors.
- Chỉ đo CPU, bỏ qua dependency latency và backlog age.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact và containment an toàn | 2 |
| Hiểu lock, delivery, idempotency | 2 |
| Evidence, competing hypotheses, root cause | 2.5 |
| Recovery, trade-offs, rollback | 2 |
| Tests, monitoring, communication | 1.5 |

# Câu 3 — Quyết định kiến trúc: hiện đại hóa hệ thống approval .NET Framework 4.5 mà không gián đoạn nghiệp vụ

**Loại câu hỏi:** Architecture / system design / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** .NET modernization, IIS/Windows Server, SQL Server, Azure App Service, API boundaries, identity, CI/CD, rollout/rollback.

## Bối cảnh

Một enterprise approval portal chạy ASP.NET MVC trên .NET Framework 4.5, IIS/Windows Server, SQL Server, có jQuery frontend và nightly batch job. Hệ thống quản lý phê duyệt chi phí và file đính kèm, tích hợp ERP qua SOAP. Nhu cầu mới: thêm REST API cho mobile app và cải thiện tốc độ release; downtime tối đa 15 phút, lịch sử audit không được mất. Team 6 developers, 2 QA, vận hành có TeamCity và Octopus Deploy. Có đề xuất: (A) rewrite toàn bộ sang .NET 10 + Kubernetes; (B) strangler incremental trên Azure App Service; (C) giữ legacy, chỉ thêm API gateway. Chưa rõ thư viện bên thứ ba, session state, Windows-only APIs và ERP contract.

## Câu hỏi chính

Bạn sẽ chọn chiến lược modernization nào, xác định service boundaries và migration phases như thế nào để bảo toàn audit, authorization, backward compatibility và khả năng rollback? Khi nào bạn sẽ thay đổi lựa chọn?

## Câu hỏi làm rõ nên cân nhắc

1. Dependency nào chỉ chạy .NET Framework/Windows, có source code và license để nâng cấp không?
2. Approval state machine, transaction boundaries và audit log hiện nằm ở đâu? Có trigger/stored procedures không?
3. Mobile cần real-time approval hay chấp nhận eventual consistency? SLA và lượng người dùng?
4. Authentication hiện dùng Windows auth, forms auth hay external IdP? Mobile cần identity flow nào?
5. Session/file storage, scheduled jobs, ERP availability và release rollback constraints hiện tại ra sao?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt thay runtime, thay hosting và thay kiến trúc; không bắt buộc làm cùng lúc.

### Gợi ý 2
Chọn boundary theo nghiệp vụ và transaction ownership, không theo tên controller hoặc folder.

### Gợi ý 3
Ưu tiên contract compatibility, dữ liệu/audit, idempotent job, shadow traffic và rollback khi có schema changes.

## Cấu trúc trả lời đề xuất

1. Business constraints và inventory rủi ro.
2. So sánh ba options theo delivery risk, complexity, cost, operations.
3. Target architecture và boundaries.
4. Data ownership, API contracts, identity/security.
5. Phases triển khai, migration dữ liệu và deployment.
6. Failure recovery, tests, telemetry và decision triggers.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không coi rewrite là mặc định; giữ một nguồn sự thật cho approval state; tách audit khỏi log vận hành; xác định compatibility và rollback trước cutover.

### Điểm cộng
Dùng contract tests với SOAP/ERP, expand-contract DB migration, progressive routing, session externalization, job singleton/idempotency, observability.

### Senior+
Có decision record với điều kiện đảo quyết định, release gates định lượng, ownership rõ và kiểm soát dual-write/transaction boundaries.

## Hướng giải quyết tham khảo

**Đánh giá lựa chọn:** (A) Rewrite .NET 10 + Kubernetes có chi phí/rủi ro lớn, phù hợp chỉ nếu legacy không thể duy trì, có nguồn lực và yêu cầu platform rõ; Kubernetes không tự giải quyết migration. (B) Incremental strangler thường cân bằng rủi ro và tốc độ khi có thể định tuyến chức năng; vẫn phải xử lý shared DB và session. (C) Gateway-only có thể giải quyết routing/security trước mắt nhưng không xử lý technical debt, runtime lifecycle hay release coupling. Với dữ liệu hiện có, tôi thiên về (B) sau discovery, không chốt trước khi đo dependencies.

**Target architecture:** Giữ legacy approval write path làm owner trong giai đoạn đầu. Thêm ASP.NET Core REST API/BFF cho mobile với identity/authorization rõ, gọi qua adapter hoặc anti-corruption layer tới legacy service; tránh mobile ghi trực tiếp vào bảng approval. Các bounded capabilities có thể tách theo file service, read models, notifications khi transaction ownership rõ. SOAP ERP được bao trong adapter với timeout, circuit-breaking có kiểm soát và idempotent reconciliation. Audit log append-only ở transactional store hoặc cơ chế đáng tin cậy; log telemetry không thay thế audit. File attachments có thể chuyển dần sang Azure Blob Storage nếu access policy, retention, virus scan, SAS và data residency phù hợp; không buộc phải chuyển trong phase đầu.

**Data và consistency:** Mọi approval transition cần state machine, optimistic concurrency hoặc transaction có điều kiện, actor identity và audit event nhất quán. Tránh hai hệ thống cùng ghi một entity mà không có ownership. Nếu cần publish event, Outbox Pattern trong cùng DB transaction với business change là một lựa chọn; consumer phải idempotent. Với read models, eventual consistency chỉ khi UX chấp nhận và hiển thị trạng thái pending. Schema expand-contract: thêm cột/tables backward-compatible, dual-read có đo đạc, cutover sau khi old binary không còn phụ thuộc, rồi mới contract. Nếu cần rollback code, schema cũ vẫn phải đọc được.

**Security:** Inventory authentication; nếu dùng Microsoft Entra ID, thiết kế OIDC/OAuth flows phù hợp cho web/mobile, validate issuer/audience, policy-based authorization trên server, audit actor/delegation, không tin role từ frontend. Service-to-service identity qua Managed Identity khi Azure resource hỗ trợ; secrets trong Key Vault, least privilege. Kiểm tra CSRF cho cookie-auth legacy và token handling của mobile.

**Lộ trình:** Phase 0 baseline: inventory dependencies, data flows, latency, deployment, integration tests, backup/restore rehearsal. Phase 1 tách CI artifact bất biến qua TeamCity/Octopus, health checks, tracing, contract tests, database migration gates; ổn định legacy trước. Phase 2 tạo API facade và mobile read-only endpoints, route theo feature, canary; phase 3 chuyển từng use case write với owner rõ, kiểm thử concurrency/audit và reconciliation; phase 4 nâng cấp hoặc retire các phần legacy theo usage, cuối cùng cân nhắc hosting migration. Nếu Windows-only dependency tồn tại, giữ component Windows hoặc thay thư viện có kiểm chứng; App Service Linux không phải mặc định cho mọi module.

**Failure và vận hành:** Canary theo tenant/feature, route fallback, kill switch, rollback artifact + backward-compatible schema, không rollback bằng cách xóa audit. Batch job phải có single ownership hoặc idempotency khi chạy song song trong cutover. Test state transitions, concurrent approvals, SOAP failure, auth bypass, old/new API contracts, Playwright E2E, backup restore và release rehearsal. Dashboard: approval success/denied rates, p95, audit gaps, ERP errors, job duplicates, deployment version; alert theo business invariant. Ưu tiên Modular Monolith/clear layers nếu team 6 người và boundaries chưa đủ ổn định; Microservices chỉ khi autonomy và vận hành biện minh chi phí.

**Khi đổi quyết định:** Nếu hệ thống có nhiều Windows-only dependencies không thể thay, giảm phạm vi strangler; nếu nghiệp vụ thay nhanh và có domain ownership độc lập, cân nhắc service extraction; nếu mobile chỉ cần read-only trong 3 tháng, API facade có thể là bước hợp lý trước. Các giả định về throughput, downtime, cost và regulatory compliance phải được xác minh trước khi cam kết. Tài liệu tham khảo: [Microsoft .NET upgrade guidance](https://learn.microsoft.com/en-us/dotnet/core/porting/), [Azure architecture Strangler Fig](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig), [ASP.NET Core migration](https://learn.microsoft.com/en-us/aspnet/core/migration/).

Với team nhỏ và downtime giới hạn, tôi nghiêng về strangler incremental: giữ legacy làm owner approval state trong giai đoạn đầu, thêm ASP.NET Core API facade cho mobile và tách từng capability khi boundary rõ. Tôi dùng một nguồn sự thật cho state, kiểm soát concurrent approval, ghi audit cùng business transition và tránh dual-write thiếu cơ chế recovery. ## Câu hỏi đào sâu

1. Nếu legacy và new API bắt buộc cùng cập nhật một approval record trong 6 tháng, bạn kiểm soát race và transaction ownership ra sao?
2. Nếu business buộc cutover toàn bộ trong một đêm, bạn thay đổi release gates, rehearsal và rollback plan như thế nào?
3. Nếu mobile traffic tăng 50 lần nhưng legacy SOAP ERP chỉ xử lý 20 requests/second, bạn thiết kế backpressure và UX ra sao?

## Lỗi trả lời thường gặp

- Đồng nhất modernize với rewrite toàn bộ.
- Chia microservices theo controller, không có domain ownership.
- Dual-write vào cùng bảng mà không có concurrency/audit guarantees.
- Chuyển database schema không backward-compatible rồi tuyên bố rollback dễ.
- Bỏ qua identity, scheduled jobs và Windows-only dependencies.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Ba góc nhìn khác nhau: HTTP cache validators và các tầng representation; Azure Service Bus Peek-Lock, duplicate delivery và an toàn side effects; modernization dựa trên ownership, backward compatibility và incremental rollout thay vì rewrite mặc định. Trong cả ba, cần tách **hành vi đã xác minh** khỏi **giả thuyết** và **lựa chọn thiết kế**.

## Mẫu tư duy cần nhớ

1. Quan sát toàn bộ request/message path trước khi kết luận lỗi ở tầng cuối.
2. Stabilize trước, root-cause analysis sau; tránh để mitigation tạo thiệt hại mới.
3. Thiết kế retry đồng thời với idempotency và reconciliation.
4. Migrate theo ownership và expand-contract; rollback là requirement, không phải lời hứa.
5. Measure before optimize; chỉ thêm cache, worker hoặc hạ tầng khi evidence biện minh.
