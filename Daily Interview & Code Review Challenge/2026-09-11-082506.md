# Code Review Challenge 1 — MongoDB giữ chỗ tồn kho bằng read-then-write: code chạy đúng ở local nhưng oversell khi nhiều request đồng thời

**Chủ đề:** C#/.NET 8, ASP.NET Core, MongoDB, atomic single-document updates, optimistic concurrency, idempotency, retries, cancellation, inventory consistency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một e-commerce API dùng MongoDB để lưu tồn kho theo SKU. Mỗi document có dạng:

```json
{
  "_id": "SKU-123",
  "available": 12,
  "reserved": 3,
  "version": 41
}
```

Endpoint `POST /inventory/{sku}/reserve` được gọi khi checkout bắt đầu.

Yêu cầu:

- không được reserve nhiều hơn `available`;
- nhiều checkout có thể reserve cùng SKU đồng thời;
- client hoặc gateway có thể retry cùng request khi timeout;
- application chạy trên nhiều instances;
- request cancellation phải được propagate;
- một transient database/network failure không được biến thành duplicate reservation;
- không muốn dùng distributed transaction nếu single-document atomicity đã đủ;
- production cần biết conflict rate, duplicate request rate và inventory invariant violations.

Sau khi traffic tăng, business phát hiện một số SKU có `available < 0` dù từng request riêng lẻ đều kiểm tra đủ hàng trước khi update.

## Đoạn code cần review

```csharp
public sealed record ReserveRequest(
    string ReservationId,
    int Quantity);

public sealed class InventoryService
{
    private readonly IMongoCollection<InventoryItem> _items;
    private readonly IMongoCollection<Reservation> _reservations;

    public InventoryService(IMongoDatabase database)
    {
        _items = database.GetCollection<InventoryItem>("inventory");
        _reservations = database.GetCollection<Reservation>("reservations");
    }

    public async Task<bool> ReserveAsync(
        string sku,
        ReserveRequest request,
        CancellationToken cancellationToken)
    {
        var item = await _items
            .Find(x => x.Id == sku)
            .FirstOrDefaultAsync();

        if (item is null || item.Available < request.Quantity)
            return false;

        item.Available -= request.Quantity;
        item.Reserved += request.Quantity;
        item.Version++;

        await _items.ReplaceOneAsync(
            x => x.Id == sku,
            item);

        await _reservations.InsertOneAsync(new Reservation
        {
            Id = Guid.NewGuid().ToString(),
            ReservationId = request.ReservationId,
            Sku = sku,
            Quantity = request.Quantity,
            CreatedAtUtc = DateTime.UtcNow
        });

        return true;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong flow reserve.
2. Xác định concurrency, reliability và data-consistency concerns.
3. Giải thích production impact, đặc biệt khi nhiều request cùng SKU chạy đồng thời hoặc client retry.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa nhưng không thêm distributed complexity nếu chưa cần.
6. Giải thích testing cho concurrency, retry và partial failure.
7. Đề xuất production telemetry chứng minh inventory invariant vẫn đúng.

## Câu hỏi gợi mở

1. Hai request cùng đọc `available = 1` trước khi request nào ghi thì điều gì có thể xảy ra?
2. `ReplaceOneAsync(x => x.Id == sku, item)` có kiểm tra state/version mà request đã đọc hay không?
3. Nếu update inventory thành công nhưng insert reservation thất bại, lần retry tiếp theo sẽ nhìn thấy state nào?
4. `ReservationId` do caller gửi có đang được dùng như idempotency key thực sự không?
5. Cancellation token hiện được propagate tới MongoDB calls ở đâu?

## Gợi ý

### Gợi ý 1

Primary risk là **check-then-act race**: business invariant được kiểm tra trên một snapshot, nhưng write sau đó không ràng buộc rằng snapshot vẫn còn đúng.

### Gợi ý 2

MongoDB có atomicity ở mức single-document write. Hãy xem liệu invariant `available >= quantity` có thể được đưa trực tiếp vào filter của một atomic conditional update thay vì read rồi replace.

## Kết quả code review tham khảo

### Critical — Check-then-act cho phép oversell hoặc lost update dưới concurrency

**Vấn đề:** Code đọc document, kiểm tra `Available`, mutate object trong memory rồi `ReplaceOneAsync` chỉ theo `_id`.

**Tại sao xảy ra:** Hai requests có thể cùng đọc một state cũ. Điều kiện “còn đủ hàng” không nằm trong atomic write predicate. Write sau không chứng minh dữ liệu vẫn giống state đã đọc.

**Ảnh hưởng production:** Tùy interleaving, request có thể overwrite update của request khác hoặc business có thể ghi nhận reservations không phản ánh inventory state thực. Khi flow khác cũng mutate document, lost update trở thành rủi ro trực tiếp.

**Cách sửa:** Dùng conditional atomic update với filter chứa SKU và điều kiện `Available >= quantity`, sau đó `$inc` các counters. Kết quả `ModifiedCount == 1` là evidence reservation inventory đã được chấp nhận.

### Critical — Inventory update và reservation record không có atomic business boundary

**Vấn đề:** Inventory được update trước, reservation insert sau. Nếu process/network lỗi ở giữa, inventory đã bị trừ nhưng durable reservation có thể không tồn tại.

**Tại sao xảy ra:** Hai writes ở hai documents/collections độc lập, không có transaction hoặc data model đảm bảo một atomic business operation.

**Ảnh hưởng production:** Stock có thể bị “mất” vĩnh viễn, retry có thể trừ thêm lần nữa, reconciliation khó xác định request nào thực sự đã thắng.

**Cách sửa:** Ưu tiên remodel để reservation/idempotency state cần thiết nằm cùng inventory document nếu cardinality/lifetime cho phép và single-document atomicity đủ. Nếu business bắt buộc hai collections là source-of-truth đồng thời, đánh giá MongoDB transaction với retry semantics phù hợp thay vì giả vờ hai writes là atomic.

### High — `ReservationId` không tạo idempotency

**Vấn đề:** Caller gửi `ReservationId`, nhưng document `_id` lại là random GUID và không có unique guarantee được thể hiện trên business key.

**Tại sao xảy ra:** Retry cùng request tạo một reservation mới và có thể trừ stock lần nữa.

**Ảnh hưởng production:** Gateway retry, mobile retry hoặc timeout ambiguity có thể tạo duplicate reservation và sai tồn kho.

**Cách sửa:** Dùng idempotency key có unique constraint/representation phù hợp và define rõ response khi key đã được xử lý. Nếu embed reservation trong inventory document, atomic update cần đồng thời bảo đảm reservation key chưa tồn tại.

### High — `ReplaceOneAsync` có thể ghi đè field do workflow khác vừa thay đổi

**Vấn đề:** Full-document replacement dựa trên object đã đọc trước đó.

**Tại sao xảy ra:** Request không chỉ ghi các fields nó sở hữu; nó gửi lại toàn document snapshot.

**Ảnh hưởng production:** Một concurrent update vào metadata, counters hoặc state khác có thể bị mất dù không liên quan tới reservation.

**Cách sửa:** Dùng targeted update operators như `$inc`, `$set`, `$push`/schema phù hợp; nếu dùng optimistic concurrency, filter thêm expected version và xử lý `ModifiedCount == 0` như conflict.

### High — Retry sau ambiguous network failure không có cách phân biệt “write chưa chạy” với “write đã commit nhưng response bị mất”

**Vấn đề:** Client/application có thể thấy exception dù server đã áp dụng write.

**Tại sao xảy ra:** Distributed call có outcome ambiguity; retry mù một non-idempotent mutation có thể apply lần hai.

**Ảnh hưởng production:** Duplicate decrement dưới transient network failure.

**Cách sửa:** Thiết kế operation idempotent bằng stable reservation key và durable state. Retry policy chỉ được thêm sau khi operation có semantics retry-safe.

### Medium — `CancellationToken` không được truyền vào database operations

**Vấn đề:** Method nhận token nhưng các `FirstOrDefaultAsync`, `ReplaceOneAsync`, `InsertOneAsync` không dùng token.

**Tại sao xảy ra:** Cancellation không tự động propagate chỉ vì method signature có token.

**Ảnh hưởng production:** Request đã timeout/disconnect nhưng DB work vẫn tiếp tục, làm tăng resource consumption và khiến caller khó hiểu outcome.

**Cách sửa:** Truyền token vào tất cả async operations phù hợp. Tuy nhiên cancellation sau khi write đã commit vẫn là ambiguous outcome; không coi cancellation là rollback.

### Medium — Không validate `Quantity`

**Vấn đề:** `Quantity <= 0` chưa bị từ chối.

**Tại sao xảy ra:** Business input validation thiếu ở boundary.

**Ảnh hưởng production:** Negative quantity có thể tăng `Available` và giảm `Reserved`, phá invariant.

**Cách sửa:** Validate `Quantity > 0`, SKU và reservation key trước persistence.

### Medium — Không kiểm tra result của write

**Vấn đề:** Code không đọc `MatchedCount`/`ModifiedCount`.

**Tại sao xảy ra:** Nó giả định không exception đồng nghĩa business mutation đã thành công đúng điều kiện.

**Ảnh hưởng production:** Conflict hoặc no-match có thể bị báo success sai.

**Cách sửa:** Treat write result là một phần của domain decision; map no-match thành out-of-stock/conflict/idempotent replay tùy predicate.

### Medium — Không có explicit invariant/reconciliation telemetry

**Vấn đề:** Logs/metrics không cho biết reservation conflict, duplicate key, failed partial operation hoặc negative inventory.

**Tại sao xảy ra:** Observability chưa được thiết kế cùng correctness.

**Ảnh hưởng production:** Sai lệch tồn kho chỉ được phát hiện từ business report, root-cause khó reconstruct.

**Cách sửa:** Structured metrics/events theo SKU hash/category, reservation outcome, conflict/duplicate count, write latency và invariant checker; tránh log dữ liệu nhạy cảm không cần thiết.

## Phiên bản đề xuất

Một hướng đơn giản khi mỗi SKU document có thể giữ một bounded set các active reservation keys là đưa invariant và idempotency vào **cùng atomic document update**.

Ví dụ data model rút gọn:

```csharp
public sealed class InventoryItem
{
    public string Id { get; init; } = default!;
    public int Available { get; set; }
    public int Reserved { get; set; }
    public long Version { get; set; }
    public List<ReservationEntry> ActiveReservations { get; set; } = [];
}

public sealed record ReservationEntry(
    string ReservationId,
    int Quantity,
    DateTime CreatedAtUtc);
```

Implementation:

```csharp
public async Task<ReserveResult> ReserveAsync(
    string sku,
    ReserveRequest request,
    CancellationToken cancellationToken)
{
    if (string.IsNullOrWhiteSpace(sku))
        return ReserveResult.Invalid;

    if (string.IsNullOrWhiteSpace(request.ReservationId) ||
        request.Quantity <= 0)
        return ReserveResult.Invalid;

    var filter = Builders<InventoryItem>.Filter.And(
        Builders<InventoryItem>.Filter.Eq(x => x.Id, sku),
        Builders<InventoryItem>.Filter.Gte(
            x => x.Available,
            request.Quantity),
        Builders<InventoryItem>.Filter.Not(
            Builders<InventoryItem>.Filter.ElemMatch(
                x => x.ActiveReservations,
                r => r.ReservationId == request.ReservationId)));

    var reservation = new ReservationEntry(
        request.ReservationId,
        request.Quantity,
        DateTime.UtcNow);

    var update = Builders<InventoryItem>.Update
        .Inc(x => x.Available, -request.Quantity)
        .Inc(x => x.Reserved, request.Quantity)
        .Inc(x => x.Version, 1)
        .Push(x => x.ActiveReservations, reservation);

    var result = await _items.UpdateOneAsync(
        filter,
        update,
        cancellationToken: cancellationToken);

    if (result.ModifiedCount == 1)
        return ReserveResult.Reserved;

    var existing = await _items
        .Find(x => x.Id == sku)
        .Project(x => new
        {
            x.Available,
            AlreadyReserved = x.ActiveReservations.Any(
                r => r.ReservationId == request.ReservationId)
        })
        .FirstOrDefaultAsync(cancellationToken);

    if (existing is null)
        return ReserveResult.NotFound;

    if (existing.AlreadyReserved)
        return ReserveResult.AlreadyReserved;

    return ReserveResult.InsufficientStock;
}
```

Điểm cốt lõi không phải `ActiveReservations` luôn là schema tốt nhất. Nếu một SKU có hàng triệu reservations hoặc retention dài, array sẽ không phù hợp. Khi đó cần data model khác và có thể phải dùng transaction hoặc một reservation ledger riêng.

Nếu vẫn giữ two-collection model, một hướng là dùng MongoDB transaction để atomically:

1. insert idempotency/reservation record với stable unique key;
2. conditional update inventory;
3. commit;
4. retry transaction theo driver/server semantics nhưng toàn operation vẫn phải idempotent ở business level.

Không thêm transaction chỉ vì “an toàn hơn” nếu single-document model đáp ứng cardinality, lifecycle và query requirements.

MongoDB documentation xác nhận write operation trên một single document là atomic, và với concurrent updates có thể đưa expected current condition vào update filter để ngăn write dựa trên state đã stale. Tài liệu tham khảo: `https://www.mongodb.com/docs/manual/core/write-operations-atomicity/`

## Giải thích thiết kế sau khi sửa

Business invariant được đưa vào atomic predicate:

```text
_id == sku
AND available >= quantity
AND reservationId chưa tồn tại
```

Mutation và điều kiện cùng được database đánh giá trên một document. Điều này loại bỏ cửa sổ read-check-write ở application.

Stable `ReservationId` biến retry thành một business operation có identity. Caller nhận timeout không được suy luận “reserve thất bại”; retry cùng key phải trả lại outcome tương thích thay vì trừ kho lần nữa.

Việc đọc document sau `ModifiedCount == 0` chỉ để **phân loại lý do** cho response. Nó không còn quyết định correctness của mutation chính.

## Trade-offs

- Embedding active reservations cho phép single-document atomicity và thiết kế đơn giản, nhưng document growth/cardinality phải được giới hạn.
- Transaction qua nhiều documents giữ normalization rõ hơn nhưng tăng latency, retry complexity và operational cost.
- Optimistic version filter dễ reasoning nhưng dưới high contention có thể tăng conflict/retry; atomic `$inc` với invariant predicate thường trực tiếp hơn cho counter.
- Idempotency state cần retention policy; giữ mãi mọi key cũng tạo unbounded growth.
- Stronger write concern có thể phù hợp với inventory criticality nhưng tăng latency; chọn theo durability requirement thay vì mặc định cực đại.

## Cách kiểm thử

1. **Concurrency test:** khởi tạo `available = 10`, chạy 100 requests đồng thời mỗi request reserve 1 với unique IDs; tổng successful reservations không được vượt 10 và `available` không âm.
2. **Idempotency test:** gửi cùng `ReservationId` 10 lần song song; inventory chỉ bị trừ một lần và các retries nhận outcome nhất quán.
3. **Failure-path test:** inject network interruption/timeout quanh write rồi retry cùng key; không được double-decrement.
4. **Validation test:** quantity bằng 0, âm, quá tồn kho, SKU không tồn tại đều không mutate document.
5. **Load test:** đo p95/p99, conflict/no-match rate, document growth và MongoDB write latency trên hot SKU để quyết định có cần shard/queue/model khác hay không.

## Quan sát trong production

Theo dõi:

- `inventory_reserve_total{outcome=reserved|already_reserved|insufficient|conflict|error}`;
- duplicate/idempotent replay rate;
- MongoDB command duration/error category;
- hot-SKU contention rate ở dạng aggregate/hash phù hợp privacy;
- retry count và ambiguous timeout count;
- `available < 0` invariant violations phải bằng 0;
- active reservation array/document size nếu dùng embedded model;
- request correlation ID + reservation operation ID;
- application cancellation rate.

Alert theo invariant violation và sustained error/conflict rate, không chỉ theo CPU.

# Code Review Challenge 2 — Playwright suite chỉ fail trên CI: `waitForTimeout`, shared account và test order đang biến E2E thành lottery

## Kết quả code review tham khảo

### High — Hai tests phụ thuộc cùng shared backend data và có race khi chạy parallel

**Tại sao xảy ra:** BrowserContext cô lập cookies/storage giữa tests, nhưng backend database state vẫn dùng chung. `fullyParallel` làm tests có thể chạy đồng thời trên workers khác nhau.

**Ảnh hưởng production/CI:** Một test tạo/xóa/complete resource trong lúc test khác đang đọc hoặc mutate nó; failure phụ thuộc timing và worker scheduling.

**Cách sửa:** Mỗi test tạo test data riêng với unique identifier hoặc fixture cấp worker/test. Không dùng một mutable record toàn suite nếu tests cần parallel independence.

### High — `complete project` phụ thuộc side effect của test khác

**Vấn đề:** Test không tự tạo Project cần thiết.

**Tại sao xảy ra:** Nó ngầm giả định `create project` chạy trước và để lại data.

**Ảnh hưởng production/CI:** Playwright không bảo đảm test files/workers chạy theo business order khi parallel; chạy riêng test này cũng có thể fail.

**Cách sửa:** Arrange precondition trong chính test hoặc reusable fixture/API helper. Một test phải pass khi chạy độc lập.

### High — Fixed sleeps tạo false confidence thay vì synchronization

**Vấn đề:** `waitForTimeout(1500/2000/1000)` giả định UI/network hoàn tất trong thời gian cố định.

**Tại sao xảy ra:** CI CPU, database, network và cold start biến thiên. Sleep quá ngắn gây false failure; sleep quá dài làm suite chậm.

**Ảnh hưởng production/CI:** Flakiness tăng dưới load, pipeline kéo dài, root cause bị che.

**Cách sửa:** Dựa vào Playwright auto-waiting và web-first assertions; chờ URL/role-visible state/response hoặc domain-specific condition khi cần.

### High — `afterAll` cleanup có ownership sai

**Vấn đề:** Một cleanup xóa resource tên chung sau toàn file.

**Tại sao xảy ra:** Nó không biết record nào thuộc test nào; nếu tests parallel hoặc fail giữa chừng, cleanup có thể xóa data test khác hoặc bỏ sót data.

**Ảnh hưởng production/CI:** Cross-test interference và test pollution qua các runs.

**Cách sửa:** Fixture tạo resource ID riêng và cleanup đúng resource trong `finally`/fixture teardown. Backend test helper nên yêu cầu authenticated/isolated test environment.

### Medium — Retry 3 lần có thể che deterministic race

**Vấn đề:** Retry được dùng như reliability mechanism thay vì diagnostic safety net.

**Tại sao xảy ra:** Shared-state race có xác suất pass ở lần sau.

**Ảnh hưởng production/CI:** Pipeline “xanh” dù suite không deterministic; regressions thật có thể bị coi là flake.

**Cách sửa:** Theo dõi first-run failure rate riêng, fix isolation trước. Giữ retry thấp nếu cần thu trace/handle known infra variance, không coi retry-pass là chất lượng tương đương first-pass.

### Medium — Selectors dựa trên generic text dễ ambiguity

**Vấn đề:** `text=Save`, `text=Complete`, `text=Release Project` có thể match sai element khi UI thay đổi hoặc có nhiều projects.

**Tại sao xảy ra:** Selector không gắn với accessible role/name hoặc stable domain identity.

**Ảnh hưởng production/CI:** Test fail hoặc click nhầm element dù feature vẫn đúng.

**Cách sửa:** Dùng `getByRole`, `getByLabel`, locator scoped theo row/card và unique project title/id.

### Medium — Login UI lặp lại cho mọi test có thể làm suite chậm và tạo thêm failure surface

**Vấn đề:** Mỗi test thực hiện full UI login dù phần lớn test không đánh giá login.

**Tại sao xảy ra:** Setup chưa phân tách authentication concern khỏi business tests.

**Ảnh hưởng production/CI:** Tăng runtime, tải identity service, nhiều điểm flaky.

**Cách sửa:** Dùng authenticated storage state/fixture được tạo an toàn theo account/worker khi phù hợp; giữ một số dedicated login E2E tests riêng.

### Medium — CI artifacts chưa đủ để phân tích flake

**Vấn đề:** Chỉ screenshot failure không thể hiện action timeline, DOM snapshots, requests và timing.

**Tại sao xảy ra:** Test infrastructure không capture trace/video/network evidence có chọn lọc.

**Ảnh hưởng production/CI:** Debug mất nhiều thời gian và dẫn tới “thêm sleep” thay vì tìm nguyên nhân.

**Cách sửa:** Enable trace trên first retry hoặc retention phù hợp, giữ test output, console errors và server correlation ID.

### Low — Non-null assertion cho `E2E_PASSWORD` làm lỗi config khó hiểu

**Vấn đề:** `process.env.E2E_PASSWORD!` chỉ làm TypeScript im lặng, không validate runtime configuration.

**Tại sao xảy ra:** Missing secret trở thành login failure thay vì config failure rõ.

**Ảnh hưởng production/CI:** Tốn thời gian điều tra false auth failure.

**Cách sửa:** Validate required environment variables ở config/setup và fail fast với message không lộ secret.

## Phiên bản đề xuất

Một hướng là tạo mỗi Project qua API fixture với title unique, rồi E2E test chỉ kiểm tra hành vi UI cần thiết.

```ts
import {
  test as base,
  expect,
  APIRequestContext
} from '@playwright/test';

type Fixtures = {
  project: {
    id: string;
    title: string;
  };
};

async function createProject(
  request: APIRequestContext,
  title: string
) {
  const response = await request.post('/api/test-data/projects', {
    data: { title }
  });

  expect(response.ok()).toBeTruthy();
  return await response.json() as { id: string; title: string };
}

export const test = base.extend<Fixtures>({
  project: async ({ request }, use, testInfo) => {
    const title =
      `e2e-${testInfo.parallelIndex}-${testInfo.testId}`;

    const project = await createProject(request, title);

    try {
      await use(project);
    } finally {
      await request.delete(
        `/api/test-data/projects/${project.id}`);
    }
  }
});

test('complete project', async ({ page, project }) => {
  await page.goto(`/projects/${project.id}`);

  await expect(
    page.getByRole('heading', { name: project.title })
  ).toBeVisible();

  await page
    .getByRole('button', { name: 'Complete' })
    .click();

  await expect(
    page.getByText('Completed', { exact: true })
  ).toBeVisible();
});
```

Authentication có thể được đưa vào project-level setup/storage state nếu login không phải target của mỗi test. Test riêng cho login vẫn nên thực hiện UI flow đầy đủ.

Ví dụ config:

```ts
import { defineConfig } from '@playwright/test';

const baseURL = process.env.BASE_URL;
if (!baseURL) {
  throw new Error('BASE_URL is required');
}

export default defineConfig({
  fullyParallel: true,
  workers: process.env.CI ? 6 : undefined,
  retries: process.env.CI ? 1 : 0,
  use: {
    baseURL,
    trace: 'on-first-retry',
    screenshot: 'only-on-failure'
  }
});
```

Nếu create action chính là thứ cần test, test đó vẫn nên tạo **unique** project name và assert bằng observable state:

```ts
test('create project', async ({ page }, testInfo) => {
  const title = `project-${testInfo.testId}`;

  await page.goto('/projects');
  await page.getByRole('button', { name: 'New Project' }).click();
  await page.getByLabel('Title').fill(title);
  await page.getByRole('button', { name: 'Save' }).click();

  await expect(
    page.getByRole('heading', { name: title })
  ).toBeVisible();
});
```

Không cần fixed sleep nếu UI state/assertion đúng contract.

Playwright documentation mô tả mỗi test dùng isolated BrowserContext, nhưng cũng nhấn mạnh shared state bên ngoài test — ví dụ cùng backend record — vẫn phải được tách; test files chạy parallel mặc định và `fullyParallel` tăng mức song song. Tài liệu tham khảo:

- `https://playwright.dev/docs/browser-contexts`
- `https://playwright.dev/docs/test-parallel`

## Giải thích thiết kế sau khi sửa

Test isolation được định nghĩa ở cả hai tầng:

```text
Browser state isolation
+
Backend/test-data isolation
```

BrowserContext giải quyết cookies/local storage/session state giữa tests. Nó không thể tự cô lập database rows cùng account.

Fixture chịu trách nhiệm ownership của test data: create → provide → cleanup. Unique ID giúp parallel workers không tranh chấp cùng entity.

Web-first assertions thay fixed sleeps bằng điều kiện business/UI cụ thể. Nếu action save vẫn asynchronous ở backend, test có thể chờ UI state hoặc API response đúng contract; không đoán latency bằng milliseconds.

## Trade-offs

- API setup làm E2E nhanh và ổn định hơn, nhưng cần trusted test-only setup endpoint hoặc direct fixture layer được bảo vệ khỏi production.
- Một account riêng mỗi test cho isolation mạnh nhưng provisioning tốn thời gian; account per worker có thể là compromise nếu records vẫn unique.
- `workers: 1` có thể hữu ích để diagnose shared-state bug tạm thời, nhưng không phải fix nếu production pipeline cần parallelism.
- Trace/video tăng artifact size; chỉ giữ on-failure/on-first-retry thường cân bằng tốt hơn capture mọi run.
- UI login trong mọi test tăng realism nhưng duplication và failure surface cao; dedicated auth tests + storage state thường hiệu quả hơn.

## Cách kiểm thử

1. **Parallelism validation:** chạy suite nhiều lần với 1, 6 và số workers cao hơn; first-pass result phải ổn định và không có shared-record collision.
2. **Order-independence test:** chạy riêng từng test, đảo thứ tự hoặc shard suite; test không được phụ thuộc side effect của test khác.
3. **Slow-network test:** thêm deterministic latency cho create/complete endpoints; assertions vẫn pass mà không tăng fixed sleep.
4. **Failure cleanup test:** cố tình fail giữa test rồi xác minh fixture teardown không xóa data của test khác và không để pollution đáng kể.
5. **CI diagnostic test:** tạo một intentional test failure trong test infrastructure sandbox và xác minh trace, screenshot, console/server correlation artifacts được upload đúng.

## Quan sát trong production

Đây chủ yếu là CI/test observability, nên theo dõi:

- first-attempt pass rate;
- retry-pass rate;
- flaky-test rate theo test ID;
- duration p50/p95 theo test và worker;
- browser console errors;
- failed request URLs/status codes đã scrub secrets;
- Playwright trace trên failure/retry;
- screenshot và relevant server-side correlation ID;
- test-data creation/cleanup failures;
- CI worker/shard identifier;
- backend environment health khi suite chạy.

Một dashboard flake nên phân biệt:

```text
product regression
test-code race
test-data collision
environment outage
timeout/performance regression
```

Không biến “retry pass” thành success vô điều kiện mà mất signal về chất lượng suite.

## Câu hỏi phỏng vấn mở rộng

1. Nếu mỗi worker dùng một account riêng nhưng tests trong cùng worker vẫn mutate global organization settings, isolation còn thiếu ở đâu?
2. Khi nào bạn chấp nhận một test chạy serial thay vì tiếp tục đầu tư để làm nó parallel-safe?
3. Nếu E2E suite 20 phút nhưng business yêu cầu deployment gate dưới 8 phút, bạn chọn test nào giữ ở gate và test nào chuyển sang API/integration/post-deploy checks?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Business invariant dưới concurrency nên được đưa càng gần atomic database operation càng tốt; read-check-write ở application dễ bị stale state.
- MongoDB single-document atomicity có thể loại bỏ nhiều distributed coordination nếu data model được thiết kế theo invariant thực tế.
- Retry chỉ an toàn khi operation có stable identity/idempotency; timeout hoặc cancellation không chứng minh write chưa commit.
- Playwright BrowserContext cô lập browser state, không tự cô lập backend/database state.
- E2E synchronization nên chờ observable condition thay vì fixed sleep; parallelism thường phơi bày shared-state dependency vốn đã tồn tại.

## Mẫu tư duy cần nhớ

- **Move the invariant into the write:** đừng kiểm tra state rồi hy vọng nó không đổi trước mutation.
- **Design retry cùng idempotency:** mọi network write quan trọng đều có thể có ambiguous outcome.
- **Test isolation phải end-to-end:** browser isolated nhưng shared backend data vẫn có thể race.
- **Wait for condition, not time:** synchronization dựa trên state/event đáng tin cậy.
- **Đừng giảm concurrency để che bug:** dùng serial execution như diagnostic/explicit constraint, không như thuốc chữa shared-state race.
