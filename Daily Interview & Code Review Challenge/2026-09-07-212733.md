# Code Review Challenge 1 — Upload tài liệu lớn lên Azure Blob Storage làm API hết memory, lộ secret và tạo file không an toàn

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, file streaming, Managed Identity, upload security, cancellation, reliability, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 11–14 vấn đề

## Bối cảnh

Một enterprise portal viết bằng ASP.NET Core .NET 8 cho phép user upload tài liệu hợp đồng. Backend chạy trên Azure App Service on Linux, scale từ 2 đến 6 instances tùy traffic. File được lưu trong Azure Blob Storage.

Yêu cầu nghiệp vụ:

- user chỉ được upload tài liệu cho tenant của mình;
- kích thước file thông thường 1–20 MB, nhưng có thể lên tới 500 MB;
- hỗ trợ PDF, DOCX và một số image formats;
- upload có thể đi qua mobile network không ổn định;
- metadata file được lưu trong SQL Server;
- client cần nhận document ID sau khi upload thành công;
- file không được public;
- team muốn tránh lưu temporary file trên App Service local disk;
- production cần truy vết được upload nào fail ở database, application hay Blob Storage.

Sau khi traffic tăng, production ghi nhận:

- process memory tăng mạnh khi nhiều user upload file lớn đồng thời;
- một số request bị 502/500 sau vài phút;
- App Service instance đôi khi restart trong peak hour;
- client cancel upload nhưng backend vẫn tiếp tục upload Blob;
- support phát hiện filename có thể chứa `../` hoặc ký tự path đặc biệt;
- một penetration test upload file có extension `.pdf` nhưng content thực tế không phải PDF;
- connection string Blob Storage đang nằm trong application settings và developer từng log toàn bộ configuration khi debug;
- một số Blob đã tồn tại nhưng database không có metadata vì SQL insert fail sau upload;
- một số database rows tồn tại nhưng Blob lại không có do retry/error handling không nhất quán;
- team đề xuất đổi Blob container sang public read để frontend tải file trực tiếp cho đơn giản.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        IConfiguration configuration,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        var connectionString = configuration["Storage:ConnectionString"]!;
        var containerName = configuration["Storage:Container"]!;

        _container = new BlobContainerClient(
            connectionString,
            containerName);

        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(long.MaxValue)]
    public async Task<IActionResult> Upload(
        IFormFile file,
        [FromForm] Guid tenantId)
    {
        if (file.Length == 0)
        {
            return BadRequest("Empty file");
        }

        var extension = Path.GetExtension(file.FileName);

        if (extension is not ".pdf" and not ".docx" and not ".png" and not ".jpg")
        {
            return BadRequest("Unsupported file type");
        }

        await using var input = file.OpenReadStream();
        using var memory = new MemoryStream();

        await input.CopyToAsync(memory);

        var blobName = $"{tenantId}/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);

        await blob.UploadAsync(
            new BinaryData(memory.ToArray()),
            overwrite: true);

        var document = new Document
        {
            Id = Guid.NewGuid(),
            TenantId = tenantId,
            OriginalFileName = file.FileName,
            BlobName = blobName,
            ContentType = file.ContentType,
            Size = file.Length,
            CreatedUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Uploaded {FileName} to {BlobName} with connection {ConnectionString}",
            file.FileName,
            blobName,
            _container.AccountName);

        return Ok(new
        {
            document.Id,
            url = blob.Uri.ToString()
        });
    }
}
```

## Kết quả code review tham khảo

### Critical — Tenant authorization dựa trên `tenantId` do client gửi

**Vấn đề:**  
API nhận `tenantId` từ form rồi dùng trực tiếp để tạo Blob path và database row.

**Tại sao xảy ra:**  
Authentication được áp dụng bằng `[Authorize]`, nhưng resource authorization không được thực hiện. Caller authenticated không mặc định có quyền ghi vào mọi tenant.

**Ảnh hưởng production:**  
User có thể thử gửi tenant ID khác và tạo tài liệu trong namespace của tenant khác, dẫn đến broken access control và data isolation failure.

**Cách sửa:**  
Resolve tenant từ trusted authenticated context hoặc kiểm tra explicit membership/permission trước khi upload. Không xem tenant identifier từ client là authorization proof.

---

### High — Whole-file buffering tạo peak memory rất lớn

**Vấn đề:**  
Code copy file vào `MemoryStream`, sau đó gọi `memory.ToArray()` tạo thêm một `byte[]`, rồi bọc dữ liệu bằng `BinaryData` trước khi upload.

**Tại sao xảy ra:**  
Pipeline biến một stream thành nhiều in-memory representations thay vì stream trực tiếp tới storage.

**Ảnh hưởng production:**  
Một file hàng trăm MB có thể tạo memory pressure rất lớn. Nhiều upload đồng thời làm allocation/GC tăng, process có thể bị OOM/restart, request latency tăng và các request khác bị ảnh hưởng.

**Cách sửa:**  
Stream trực tiếp từ request/file stream tới Blob SDK khi phù hợp. Đặt bounded request/file-size policy theo requirement. Không gọi `ToArray()` cho large upload nếu không cần.

---

### High — `RequestSizeLimit(long.MaxValue)` loại bỏ safety boundary quan trọng

**Vấn đề:**  
Endpoint cho phép request cực lớn mà không có business limit hợp lý.

**Tại sao xảy ra:**  
Configuration ưu tiên “upload được mọi file” thay vì bảo vệ application resources.

**Ảnh hưởng production:**  
Authenticated user hoặc malfunctioning client có thể tiêu tốn bandwidth, request slots, memory/disk buffering và thời gian xử lý rất lớn, tạo DoS ở application layer.

**Cách sửa:**  
Đặt maximum size theo business requirement, ví dụ giới hạn rõ cho từng document type/tier. Validate cả request size và actual streamed bytes; reject sớm khi vượt giới hạn.

---

### High — Blob name dùng raw filename từ user

**Vấn đề:**  
`file.FileName` được đưa trực tiếp vào logical storage key.

**Tại sao xảy ra:**  
Display name và storage identity bị trộn thành một giá trị.

**Ảnh hưởng production:**  
Filename chứa separator, control characters hoặc pattern bất thường có thể tạo namespace khó kiểm soát, overwrite ngoài ý định hoặc gây logging/UI issues. Hai uploads cùng tên còn ghi đè vì `overwrite: true`.

**Cách sửa:**  
Sinh immutable internal document/blob ID, ví dụ `{tenantId}/{documentId}` hoặc versioned object key. Lưu original filename chỉ như metadata/display value sau khi normalize/validate cho presentation. Không dùng user filename làm identity.

---

### High — `overwrite: true` có thể phá dữ liệu khi trùng tên

**Vấn đề:**  
Hai files cùng `tenantId/fileName` dùng cùng Blob key.

**Tại sao xảy ra:**  
Storage identity không unique và overwrite được bật mặc định.

**Ảnh hưởng production:**  
Upload sau có thể thay content của document trước trong khi database vẫn chứa metadata cũ, gây data inconsistency hoặc cross-workflow corruption.

**Cách sửa:**  
Dùng server-generated unique Blob name. Nếu business có versioning, model version explicitly thay vì implicit overwrite.

---

### High — Kiểm tra extension không phải validation content

**Vấn đề:**  
API chỉ kiểm tra `Path.GetExtension(file.FileName)`.

**Tại sao xảy ra:**  
Filename và `Content-Type` đều là client-controlled metadata.

**Ảnh hưởng production:**  
File executable/malicious content có thể được đổi extension rồi upload. Nếu file sau này được render/process bởi browser, CMS, scanner hoặc third-party parser, risk tăng mạnh.

**Cách sửa:**  
Dùng allow-list theo business need, normalize extension, validate magic/signature khi có thể, không tin `file.ContentType`, scan malware theo threat model, và luôn phục vụ file với safe response headers. Với formats phức tạp, validation không đồng nghĩa “file chắc chắn an toàn”; cần defense-in-depth.

---

### High — Storage credential dùng shared connection string thay vì workload identity

**Vấn đề:**  
Application đọc Blob connection string có credential dài hạn từ configuration.

**Tại sao xảy ra:**  
Service authentication dựa trên secret thay vì Azure identity boundary.

**Ảnh hưởng production:**  
Secret có thể bị lộ qua configuration dump, log, support tooling hoặc rotation mistake. Blast radius tùy quyền của key/connection string.

**Cách sửa:**  
Khi deployment environment hỗ trợ, dùng Managed Identity với `DefaultAzureCredential`/appropriate Azure credential chain và RBAC least privilege cho container/account scope cần thiết. Secret vẫn có thể cần cho local/dev fallback, nhưng phải tách khỏi source/log và quản lý bằng secret store phù hợp.

---

### High — Blob + SQL là dual-write không atomic

**Vấn đề:**  
Blob được upload trước, sau đó SQL metadata mới được commit.

**Tại sao xảy ra:**  
Blob Storage và SQL Server không nằm trong cùng local database transaction.

**Ảnh hưởng production:**  
Nếu SQL save fail, orphan Blob tồn tại. Nếu flow đảo thứ tự và Blob fail sau SQL commit, dangling metadata tồn tại. Retry có thể tạo duplicate hoặc overwrite tùy key strategy.

**Cách sửa:**  
Thiết kế explicit workflow state, ví dụ:

- tạo `Document` row ở `PendingUpload` với server-generated ID;
- upload Blob bằng key chứa document ID;
- chuyển row sang `Ready` sau successful upload;
- nếu upload fail, mark `Failed` hoặc delete/retry;
- reconciliation job tìm orphan/dangling state;
- nếu client upload trực tiếp Blob bằng short-lived SAS, backend chỉ finalize metadata sau khi verify object tồn tại và thỏa policy.

Không giả định distributed atomic transaction.

---

### High — CancellationToken không được propagate

**Vấn đề:**  
Endpoint không nhận/use request cancellation token trong stream copy, Blob upload hoặc SQL save.

**Tại sao xảy ra:**  
Long-running I/O không được gắn với request lifecycle.

**Ảnh hưởng production:**  
Client disconnect vẫn có thể khiến backend tiếp tục consume bandwidth/storage/DB resources. Shutdown/redeploy cũng khó drain work predictably.

**Cách sửa:**  
Nhận `CancellationToken` và truyền xuống async I/O. Tuy nhiên cần thiết kế cleanup/reconciliation vì cancellation có thể xảy ra sau khi remote side effect đã hoàn thành nhưng trước khi client nhận kết quả.

---

### Medium — Controller tự tạo `BlobContainerClient` từ configuration

**Vấn đề:**  
Storage client construction nằm trong controller thay vì composition root/service boundary.

**Tại sao xảy ra:**  
Infrastructure concern bị trộn vào endpoint logic.

**Ảnh hưởng production:**  
Khó centralize credential policy, retry/client configuration, testing và telemetry. Đây không nhất thiết là runtime bug nhưng làm maintainability/consistency kém.

**Cách sửa:**  
Inject configured `BlobServiceClient`/storage abstraction từ DI và giữ container/path policy trong application/infrastructure service phù hợp.

---

### Medium — Log không đủ để điều tra workflow nhưng cũng có nguy cơ log sensitive configuration

**Vấn đề:**  
Log hiện tại không có document ID, tenant-safe correlation, duration, size bucket, Blob operation result hoặc DB stage. Team từng log toàn bộ configuration khi debug.

**Tại sao xảy ra:**  
Telemetry không được thiết kế như một phần của upload workflow.

**Ảnh hưởng production:**  
Khó xác định orphan xảy ra ở stage nào; đồng thời debug logging có thể vô tình làm lộ secret.

**Cách sửa:**  
Structured logs/traces theo `DocumentId`, safe tenant identifier, request/trace ID, content length, duration, storage dependency status và metadata-state transition. Redact secrets/tokens/SAS query strings.

---

### Medium — Trả raw Blob URI không giải quyết private download authorization

**Vấn đề:**  
Response trả `blob.Uri` như thể đó là downloadable URL.

**Tại sao xảy ra:**  
Storage location bị nhầm với authorization mechanism.

**Ảnh hưởng production:**  
Nếu container private, URL không tự cấp quyền. Nếu team chuyển container sang public để URL hoạt động, mọi ai biết URL có thể bypass application authorization.

**Cách sửa:**  
Giữ container private. Download có thể dùng backend-authorized proxy/stream hoặc backend cấp short-lived, least-privilege SAS sau khi kiểm tra resource authorization. Không publicize container chỉ để đơn giản frontend.

## Phiên bản đề xuất

Ví dụ dưới đây chọn flow backend-streaming cho file có giới hạn rõ ràng. Với file rất lớn hoặc traffic upload cao, direct-to-Blob bằng short-lived SAS có thể giảm tải application tier.

```csharp
[ApiController]
[Route("api/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxFileSize = 500L * 1024 * 1024;

    private readonly IDocumentStorage _storage;
    private readonly AppDbContext _db;
    private readonly ICurrentTenant _currentTenant;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        IDocumentStorage storage,
        AppDbContext db,
        ICurrentTenant currentTenant,
        ILogger<DocumentsController> logger)
    {
        _storage = storage;
        _db = db;
        _currentTenant = currentTenant;
        _logger = logger;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(MaxFileSize)]
    public async Task<IActionResult> Upload(
        IFormFile file,
        CancellationToken cancellationToken)
    {
        if (file.Length <= 0 || file.Length > MaxFileSize)
        {
            return BadRequest("Invalid file size.");
        }

        var validatedType = FileTypePolicy.Validate(
            file.FileName,
            file.ContentType);

        if (!validatedType.Allowed)
        {
            return BadRequest("Unsupported file type.");
        }

        var tenantId = _currentTenant.Id;
        var documentId = Guid.NewGuid();
        var blobName = $"{tenantId:N}/{documentId:N}";
        var safeDisplayName = FileNamePolicy.Normalize(file.FileName);

        var document = new Document
        {
            Id = documentId,
            TenantId = tenantId,
            OriginalFileName = safeDisplayName,
            BlobName = blobName,
            ContentType = validatedType.ContentType,
            Size = file.Length,
            Status = DocumentStatus.PendingUpload,
            CreatedUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(cancellationToken);

        try
        {
            await using var stream = file.OpenReadStream();

            await _storage.UploadAsync(
                blobName,
                stream,
                validatedType.ContentType,
                cancellationToken);

            document.Status = DocumentStatus.Ready;
            document.UploadedUtc = DateTime.UtcNow;

            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (Exception ex) when (!cancellationToken.IsCancellationRequested)
        {
            document.Status = DocumentStatus.Failed;
            document.LastErrorCode = "UploadFailed";

            await _db.SaveChangesAsync(CancellationToken.None);

            _logger.LogError(
                ex,
                "Document upload failed. DocumentId={DocumentId} TenantId={TenantId}",
                documentId,
                tenantId);

            throw;
        }

        return Accepted(new
        {
            document.Id,
            document.Status
        });
    }
}
```

Storage registration có thể dùng workload identity:

```csharp
builder.Services.AddSingleton(_ =>
{
    var serviceUri = new Uri(builder.Configuration["Storage:ServiceUri"]!);

```

`IDocumentStorage.UploadAsync` nên stream trực tiếp, không materialize toàn bộ file trong RAM, áp dụng metadata/content headers có kiểm soát và propagate cancellation.

Với direct upload flow, một thiết kế khả thi là:

1. client gọi API tạo `Document` ở trạng thái `PendingUpload`;
2. backend authorize tenant và tạo server-controlled Blob key;
3. backend cấp short-lived SAS chỉ có quyền cần thiết cho đúng object;
4. client upload trực tiếp Blob;
5. client gọi finalize hoặc backend xử lý event/reconciliation;
6. backend verify Blob properties/size/type policy rồi chuyển metadata sang `Ready`;
7. cleanup job xóa `PendingUpload` hết hạn/orphan objects.

## Giải thích thiết kế sau khi sửa

### 1. Storage identity không phụ thuộc user filename

Document ID do server sinh quyết định Blob key. Filename chỉ là presentation metadata.

### 2. Memory footprint được bounded

Upload được xử lý theo stream; application không giữ toàn bộ payload trong `MemoryStream` + `byte[]`.

### 3. Authorization nằm trước storage operation

Tenant được resolve từ trusted context, không từ form value.

### 4. Dual-write được model thành workflow state

`PendingUpload`, `Ready`, `Failed` làm failure window quan sát và recover được thay vì giả vờ SQL + Blob atomic.

### 5. Secret surface giảm

Managed Identity/RBAC thay shared credential khi deployment model cho phép.

## Trade-offs

- Backend streaming đơn giản về authorization nhưng giữ request/app resources lâu hơn direct-to-Blob upload.
- Direct SAS upload giảm bandwidth qua application tier nhưng cần finalize/reconciliation và SAS policy chặt chẽ hơn.
- Malware/content validation tăng latency và operational dependencies; policy phải dựa trên threat model.
- Workflow state + reconciliation phức tạp hơn dual-write tuần tự nhưng dễ phục hồi và audit hơn.
- Private download qua backend tăng egress/load ở app; short-lived SAS giảm app load nhưng phải quản lý expiry và authorization cẩn thận.

## Cách kiểm thử

1. **Load test:** nhiều upload 100–500 MB đồng thời; đo working set, allocations, GC, request duration và App Service stability.
2. **Authorization/security test:** caller tenant A không thể tạo/download document dưới tenant B; filename traversal/control chars không ảnh hưởng Blob identity.
3. **Failure-path test:** inject SQL failure sau Blob upload và Blob failure sau metadata create; reconciliation phải đưa state về tình trạng xác định.
4. **Cancellation test:** client disconnect giữa upload; backend dừng I/O hợp lý và không để state không thể phục hồi.
5. **File-validation test:** extension/MIME mismatch, oversized payload và malicious sample phải bị xử lý theo policy.

## Quan sát trong production

Theo dõi:

- upload request count và success/failure rate;
- bytes uploaded và size distribution;
- p50/p95/p99 duration;
- process memory, allocation rate và GC;
- active concurrent uploads;
- Blob dependency duration/error/throttle metrics;
- count/age của `PendingUpload` và `Failed` documents;
- orphan Blob reconciliation count;
- cancellation/disconnect count;
- storage authorization failures;
- trace correlation theo `DocumentId` + request ID + storage dependency;
- tuyệt đối không log account keys, connection strings hoặc SAS query strings.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn backend streaming thay vì direct-to-Blob SAS upload?
2. Nếu antivirus scanning mất 30 giây cho file lớn, bạn sẽ thay đổi state machine và download policy thế nào?
3. Nếu cần resumable upload cho mobile network không ổn định, bạn sẽ thiết kế boundary giữa client, application metadata và Blob Storage ra sao?

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc external systems nên dependency outage biến thành restart storm

**Vấn đề:**  
`/health` kiểm tra SQL, Redis và third-party pricing API, rồi được dùng làm `livenessProbe`.

**Tại sao xảy ra:**  
Liveness đang trả lời câu hỏi “mọi dependency có healthy không?” thay vì “process này còn sống và có khả năng tiếp tục vận hành không?”.

**Ảnh hưởng production:**  
Pricing API chậm/down có thể khiến mọi Pod fail liveness và bị restart. Restart không sửa external dependency nhưng tạo thêm cold start, connection churn, cache loss và capacity reduction — có thể khuếch đại incident.

**Cách sửa:**  
Tạo liveness endpoint rất nông, chỉ phản ánh process/runtime condition mà restart có khả năng khắc phục. External dependency health nên đi vào readiness/degraded telemetry tùy business semantics, không tự động biến mọi dependency outage thành process restart.

---

### High — Readiness và liveness dùng chung endpoint nên mất failure semantics

**Vấn đề:**  
Hai probes cùng gọi `/health` với cùng dependency set.

**Tại sao xảy ra:**  
Health checks được thiết kế như một boolean tổng quát thay vì các signals có mục đích khác nhau.

**Ảnh hưởng production:**  
Một lỗi có thể vừa loại Pod khỏi traffic vừa restart Pod, dù chỉ một trong hai action là phù hợp. Ngược lại, team khó phân biệt degraded dependency với hung process.

**Cách sửa:**  
Tách `/health/live` và `/health/ready` bằng health-check tags/predicates hoặc explicit endpoints. Readiness chỉ kiểm tra các điều kiện cần để nhận traffic an toàn. Liveness tránh remote dependencies trừ khi có lý do rất mạnh.

---

### High — Chạy EF Core migration trong startup của mọi replica tạo race và coupling deploy

**Vấn đề:**  
Mỗi Pod startup gọi `MigrateAsync()`.

**Tại sao xảy ra:**  
Database schema lifecycle bị gắn vào application process lifecycle.

**Ảnh hưởng production:**  
Nhiều replicas rollout có thể cùng attempt migration, tăng lock/contention và failure complexity. Một destructive/non-backward-compatible migration còn có thể phá các old Pods đang chạy trong rolling window.

**Cách sửa:**  
Tách migration thành controlled deployment step/job với một execution path rõ ràng. Quan trọng hơn, thiết kế schema change theo expand/contract để old/new application versions có compatibility window. Không coi “chỉ chạy migration một lần” là đủ nếu migration tự nó phá backward compatibility.

---

### High — `replicas: 1` làm availability mong manh trong rollout/failure

**Vấn đề:**  
Deployment chỉ có một replica.

**Tại sao xảy ra:**  
Manifest dev được dùng cho environment cần production availability.

**Ảnh hưởng production:**  
Nếu Pod duy nhất chưa ready, bị restart hoặc bị terminate trong rollout, Service có thể không còn endpoint sẵn sàng. Tùy rolling settings/capacity, có thể xuất hiện 503 window.

**Cách sửa:**  
Chọn replica count dựa trên availability/capacity requirement; cấu hình rolling update `maxUnavailable`/`maxSurge` phù hợp và kiểm tra thực tế. Nếu workload không cần Kubernetes, App Service multi-instance có thể vẫn đơn giản hơn.

---

### High — Image tag `latest` phá artifact traceability và reproducibility

**Vấn đề:**  
Manifest deploy `company.azurecr.io/pricing-api:latest`.

**Tại sao xảy ra:**  
Mutable tag không phải immutable release identity.

**Ảnh hưởng production:**  
Hai Pods có thể không rõ đang chạy cùng binary nào; rollback/RCA khó chứng minh exact artifact. Cache/pull behavior còn làm tag-name không đủ để audit content.

**Cách sửa:**  
Deploy immutable version tag hoặc image digest gắn với build/commit/release. Expose build/version metadata trong telemetry để correlation incident.

---

### High — Database password nằm trong ConfigMap

**Vấn đề:**  
Connection string chứa password trong ConfigMap plain configuration.

**Tại sao xảy ra:**  
Non-secret config và credentials bị trộn chung.

**Ảnh hưởng production:**  
Credential có thể lộ qua repository, manifest output, debugging hoặc người có quyền đọc ConfigMap. Kubernetes `Secret` cũng không tự động giải quyết toàn bộ secret-management problem; access control và storage policy vẫn quan trọng.

**Cách sửa:**  
Tách secret khỏi ConfigMap; dùng workload identity/Managed Identity khi SQL/deployment model hỗ trợ, hoặc secret-management integration phù hợp với platform. Áp least privilege và tránh đưa secret vào logs/manifests không cần thiết.

---

### High — Không có resource requests/limits nên scheduling và contention khó dự đoán

**Vấn đề:**  
Container không khai báo CPU/memory requests/limits.

**Tại sao xảy ra:**  
Application manifest không mô tả resource envelope.

**Ảnh hưởng production:**  
Scheduler/capacity planning thiếu signal; noisy-neighbor behavior và node pressure khó kiểm soát. Đặt limit tùy tiện cũng có thể gây throttling/OOM, nên không thể sửa bằng copy một con số chung.

**Cách sửa:**  
Đo CPU/memory trên representative load, đặt requests theo steady-state needs và limits theo tested safety envelope/platform policy. Theo dõi throttling/OOM/restarts rồi điều chỉnh bằng evidence.

---

### High — Graceful shutdown không được thiết kế cho request kéo dài

**Vấn đề:**  
`preStop` chỉ sleep 2 giây; không thấy termination grace period, drain semantics hoặc application cancellation policy cho request 20–40 giây.

**Tại sao xảy ra:**  
Lifecycle hook được dùng như delay thay cho graceful termination design.

**Ảnh hưởng production:**  
Pod có thể bị terminate khi request đang xử lý, client nhận lỗi và side effect có thể ở trạng thái một phần tùy endpoint.

**Cách sửa:**  
Thiết kế readiness/draining để Pod ngừng nhận traffic mới trước termination, cấu hình grace period dựa trên workload, propagate cancellation và làm long-running operations idempotent/recoverable. Không dựa vào sleep cố định như guarantee.

---

### Medium — Probe timing được hard-code mà không dựa trên startup behavior

**Vấn đề:**  
`initialDelaySeconds`, `periodSeconds` được chọn cố định dù startup có thể chạy migration và dependency checks.

**Tại sao xảy ra:**  
Probe tuning không dựa trên measured startup distribution.

**Ảnh hưởng production:**  
Pod chậm hợp lệ có thể bị đánh fail quá sớm hoặc lỗi thật bị phát hiện quá muộn.

**Cách sửa:**  
Đo startup/warm-up. Nếu app có startup phase dài, cân nhắc startup probe hoặc readiness sequencing phù hợp; giữ liveness semantics riêng. Không tăng threshold vô hạn để che nguyên nhân.

---

### Medium — Health check third-party dependency cần phân loại business semantics

**Vấn đề:**  
Pricing API được coi như binary dependency cho toàn API.

**Tại sao xảy ra:**  
Không phân biệt endpoint nào bắt buộc pricing API và endpoint nào vẫn phục vụ được degraded mode.

**Ảnh hưởng production:**  
Nếu pricing API down mà API vẫn có thể phục vụ catalog/read-only flows, readiness fail toàn Pod có thể làm availability tệ hơn dependency outage ban đầu.

**Cách sửa:**  
Xác định dependency criticality. Có thể giữ Pod ready và trả degraded/503 chỉ ở feature phụ thuộc pricing, kết hợp timeout/circuit breaker/cache fallback nếu phù hợp. Nếu mọi request thực sự cần pricing thì readiness policy có thể nghiêm hơn.

---

### Medium — Kubernetes được chọn như default target mà chưa chứng minh lợi ích so với App Service

**Vấn đề:**  
Migration platform có nguy cơ tăng complexity mà không gắn với requirement cụ thể.

**Tại sao xảy ra:**  
Team đồng nhất “platform chuẩn” với “kiến trúc tốt hơn”.

**Ảnh hưởng production:**  
Tăng surface area về probes, manifests, autoscaling, networking, security, node/capacity và operational skills mà chưa chắc tạo business value.

**Cách sửa:**  
So sánh requirement thật: portability, workload diversity, scheduling/control, sidecars, platform standardization, cost/operations. Nếu App Service đáp ứng scale/availability và team chưa cần Kubernetes features, giữ giải pháp đơn giản có thể tốt hơn.

Database migration được tách khỏi application startup:

```text

2. Chạy backward-compatible expand migration bằng controlled release step/job.

4. Roll out application replicas.
```

## Giải thích thiết kế sau khi sửa

### 1. Probes có semantics riêng

Liveness trả lời “restart có thể giúp process này không?”. Readiness trả lời “Pod có nên nhận traffic mới không?”. Dependency telemetry trả lời “hệ thống đang degraded ở đâu?”.

### 2. Release artifact immutable

Image version/digest làm rollout và rollback có identity rõ ràng.

### 3. Schema lifecycle độc lập process lifecycle

Migration trở thành controlled release operation, không phải side effect của mỗi replica startup.

### 4. Graceful shutdown được coi là correctness concern

Drain + cancellation + idempotency/recovery bảo vệ long-running work trong rollout.

### 5. Kubernetes không được coi là mục tiêu mặc định

Nếu operational control không tạo đủ value, App Service có thể là lựa chọn hợp lý hơn và ít complexity hơn.

## Trade-offs

- Nhiều replicas + `maxUnavailable: 0` tăng temporary capacity requirement trong rollout.
- Tách probes cần hiểu dependency criticality; readiness quá nghiêm có thể tự làm outage, quá lỏng có thể route traffic vào Pod không phục vụ được.
- Resource limits bảo vệ node nhưng limit thấp có thể throttle/OOM; phải tune bằng measurement.
- Controlled migration job tăng pipeline steps nhưng giảm race và làm release state rõ hơn.
- Kubernetes cho control mạnh hơn nhưng kéo theo platform/operational complexity đáng kể.

## Cách kiểm thử

1. **Dependency failure test:** làm pricing API timeout; Pod không được restart storm nếu process vẫn healthy và design cho phép degraded mode.
2. **Rolling deployment test:** deploy version mới dưới representative load; đo 5xx, ready endpoints và long-running request completion.
3. **Migration compatibility test:** old app chạy trên expanded schema và new app rollout đồng thời không lỗi; migration không chạy đồng thời từ nhiều Pods.
4. **Resource/load test:** tăng traffic để đo CPU throttling, memory working set, OOM/restart và latency trước khi chốt requests/limits.
5. **Shutdown test:** terminate Pod khi có request dài; xác minh drain/cancellation/retry semantics và không tạo partial business side effect không recoverable.

## Quan sát trong production

Theo dõi:

- desired/available/ready replica counts;
- Pod restart reason/count;
- readiness/liveness failure counts;
- rollout duration và unavailable endpoints;
- 4xx/5xx, p50/p95/p99 latency;
- CPU usage/throttling, memory working set và OOM events;
- dependency telemetry cho SQL/Redis/pricing API;
- active request count và shutdown/drain duration;
- application image digest/build version;
- migration version/status;
- node/pod placement chỉ ở mức cần cho application troubleshooting;
- alerts phải phân biệt process failure, readiness degradation và external dependency incident.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Large file handling phải được thiết kế theo streaming và bounded resource usage, không materialize payload nhiều lần trong memory.
- Authentication không thay thế resource authorization; tenant/resource ownership phải được kiểm tra ở trusted boundary.
- Filename, MIME type và extension đều là untrusted metadata; storage identity nên do server kiểm soát.
- Blob Storage + SQL Server tạo dual-write workflow, không phải một atomic transaction; cần state machine và reconciliation.
- Managed Identity/least privilege giúp giảm shared-secret surface trong Azure-hosted workloads khi platform hỗ trợ.
- Kubernetes liveness, readiness và dependency health có semantics khác nhau; probe sai có thể khuếch đại outage.
- Database migration không nên bị coi đơn giản là startup side effect khi application chạy nhiều replicas.
- Immutable artifacts, graceful shutdown và measured resource envelopes là một phần của production correctness.
- Kubernetes chỉ đáng giá khi operational/control requirements biện minh cho complexity của nó.

## Mẫu tư duy cần nhớ

1. **Stream large data; bound memory, time and concurrency.**
2. **Authenticate identity, then authorize the concrete resource.**
3. **Model cross-system writes as a recoverable workflow, not a fake transaction.**
4. **Separate liveness, readiness and dependency degradation signals.**
5. **Do not add platform complexity unless requirements justify its operational cost.**
