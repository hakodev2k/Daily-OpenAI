# Code Review Challenge 1 — Parallel EF Core processing chạy nhanh ở local nhưng vỡ dưới concurrency và làm dữ liệu cập nhật không nhất quán

**Chủ đề:** C#/.NET, async/concurrency, Entity Framework Core, DbContext lifetime, SQL Server, transactions, CancellationToken, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 API có endpoint dành cho operations team để xử lý hàng loạt pending invoices.

Flow hiện tại:

- lấy tối đa 500 invoices ở trạng thái `Pending`;
- với mỗi invoice, gọi external tax API;
- cập nhật `TaxAmount`, `TaxCalculatedUtc` và trạng thái `Ready`;
- có thể chạy nhiều request cùng lúc từ UI nội bộ;
- production có 4 Azure App Service instances;
- external tax API đôi khi mất 100–2000 ms và có rate limit;
- SQL Server đôi khi ghi nhận blocking và deadlock;
- team muốn tăng throughput nên vừa refactor sang `Parallel.ForEachAsync`.

Sau refactor, production ghi nhận:

- thỉnh thoảng có `InvalidOperationException` liên quan tới một operation khác đang chạy trên cùng `DbContext`;
- một số invoices bị tax calculation lặp hai lần;
- có invoice đã gọi external API thành công nhưng vẫn còn trạng thái `Pending`;
- request bị client cancel nhưng một phần work vẫn tiếp tục;
- CPU không cao nhưng SQL connection usage tăng mạnh;
- một số request trả 500 sau vài giây trong khi nhiều invoice đã được thay đổi;
- Application Insights chỉ có request-level trace, không có invoice-level correlation hoặc dependency duration theo invoice.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/invoices")]
[Authorize(Policy = "Operations")]
public sealed class InvoiceBatchController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITaxClient _taxClient;
    private readonly ILogger<InvoiceBatchController> _logger;

    public InvoiceBatchController(
        AppDbContext db,
        ITaxClient taxClient,
        ILogger<InvoiceBatchController> logger)
    {
        _db = db;
        _taxClient = taxClient;
        _logger = logger;
    }

    [HttpPost("calculate-tax")]
    public async Task<IActionResult> CalculateTax(
        CancellationToken cancellationToken)
    {
        var invoices = await _db.Invoices
            .Where(x => x.Status == InvoiceStatus.Pending)
            .OrderBy(x => x.CreatedUtc)
            .Take(500)
            .ToListAsync(cancellationToken);

        await Parallel.ForEachAsync(
            invoices,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 32
            },
            async (invoice, ct) =>
            {
                var tax = await _taxClient.CalculateAsync(
                    invoice.CustomerId,
                    invoice.TotalAmount,
                    CancellationToken.None);

                invoice.TaxAmount = tax.Amount;
                invoice.TaxCalculatedUtc = DateTime.UtcNow;
                invoice.Status = InvoiceStatus.Ready;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Calculated tax for invoice {InvoiceId}",
                    invoice.Id);
            });

        return Ok(new
        {
            processed = invoices.Count
        });
    }
}
```

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### Critical — Dùng cùng một `DbContext` cho nhiều operation song song

**Vấn đề:**  
`_db` là dependency scoped của controller nhưng được dùng đồng thời bởi nhiều delegate trong `Parallel.ForEachAsync`.

**Tại sao xảy ra:**  
Một `DbContext` đại diện cho một unit-of-work và giữ mutable state như change tracker. Nó không được thiết kế để chạy nhiều database operations đồng thời trên cùng instance.

**Ảnh hưởng production:**  
Có thể phát sinh exception về concurrent operations, change-tracker state khó dự đoán, transaction/connection behavior không ổn định và request fail sau khi một phần invoices đã được xử lý.

**Cách sửa:**  
Không chia sẻ một `DbContext` giữa parallel workers. Nếu cần parallelism thật sự, tạo scope/`DbContext` riêng cho từng bounded unit-of-work bằng `IDbContextFactory<AppDbContext>` hoặc scope factory. Tuy nhiên, trước khi thêm parallelism, cần xác định bottleneck và downstream capacity.

---

### Critical — Nhiều request/instances có thể cùng xử lý một invoice

**Vấn đề:**  
Query chỉ đọc `Pending` rồi xử lý sau. Không có atomic claim hoặc concurrency token.

**Tại sao xảy ra:**  
Read và ownership transition không nằm trong một atomic state change. Với 4 App Service instances hoặc hai user bấm endpoint gần nhau, cùng một invoice có thể xuất hiện trong nhiều batch.

**Ảnh hưởng production:**  
Tax API có thể được gọi nhiều lần, state bị overwrite và audit khó xác định ai thực sự sở hữu work.

**Cách sửa:**  
Thiết kế claim semantics. Một lựa chọn là chuyển invoice `Pending -> Processing` bằng atomic update có điều kiện và chỉ xử lý rows thực sự claim thành công. Có thể dùng optimistic concurrency/version column, SQL pattern phù hợp hoặc queue-based work distribution nếu complexity được chứng minh là cần thiết.

---

### Critical — External tax side effect không atomic với database state

**Vấn đề:**  
Tax API call xảy ra trước database commit.

**Tại sao xảy ra:**  
External HTTP dependency không nằm trong cùng local SQL transaction.

**Ảnh hưởng production:**  
Failure windows gồm:

- tax API thành công, DB save fail;
- API timeout nhưng provider thực tế đã xử lý;
- app crash sau external call trước commit;
- database commit thành công nhưng response request fail.

Retry có thể gọi tax provider lại.

**Cách sửa:**  
Xác định contract của tax API. Nếu API hỗ trợ idempotency key, dùng stable key theo invoice calculation/version. Persist processing state, attempt count và correlation ID. Nếu workflow cần durability cao, cân nhắc background job/outbox/queue thay vì giữ toàn bộ work trong request HTTP.

---

### High — `SaveChangesAsync()` trong từng iteration có thể lưu thay đổi của nhiều entities ngoài iteration hiện tại

**Vấn đề:**  
Do các invoices đều được tracked bởi cùng `_db`, mỗi call `SaveChangesAsync()` không chỉ thuộc riêng invoice đang xử lý.

**Tại sao xảy ra:**  
Change tracker chứa toàn bộ 500 entities. Nhiều delegates cùng mutate tracked entities.

**Ảnh hưởng production:**  
Một iteration có thể flush changes của invoice khác đang được mutate, tạo race và khiến log “invoice X đã save” không phản ánh transaction boundary thật.

**Cách sửa:**  
Tạo một isolated context per work item/batch hoặc thực hiện bounded sequential batches. Mỗi transaction phải có ownership rõ ràng.

---

### High — Cancellation bị cắt đứt ở external API và database writes

**Vấn đề:**  
Tax client dùng `CancellationToken.None`; `SaveChangesAsync()` không nhận token.

**Tại sao xảy ra:**  
Code không propagate cancellation từ request/parallel worker.

**Ảnh hưởng production:**  
Client disconnect hoặc app shutdown không dừng được I/O hợp lý; work tiếp tục chiếm connection và làm tăng khoảng thời gian shutdown/deploy.

**Cách sửa:**  
Truyền token phù hợp vào tax call và database operations. Tuy nhiên cancellation không phải rollback mechanism cho external side effect; vẫn cần idempotency và recovery state.

---

### High — Parallelism 32 không gắn với downstream capacity

**Vấn đề:**  
`MaxDegreeOfParallelism = 32` là magic number.

**Tại sao xảy ra:**  
Không dựa trên tax API rate limit, connection pool, DB latency hoặc app instance count.

**Ảnh hưởng production:**  
4 instances × 32 concurrent tax calls có thể tạo burst 128 requests, đồng thời mở nhiều DB operations. Điều này có thể làm throttling, timeout, pool pressure và tail latency xấu hơn.

**Cách sửa:**  
Đo latency/throughput thật. Đặt bounded concurrency từ configuration và tune theo bottleneck. Cần tính aggregate concurrency toàn fleet, không chỉ một process.

---

### High — Partial-success semantics không rõ

**Vấn đề:**  
Một exception trong một iteration có thể làm whole operation fail trong khi các iteration khác đã thay đổi external system hoặc database.

**Tại sao xảy ra:**  
Batch HTTP response được coi như một transaction, nhưng thực tế work gồm nhiều independent distributed operations.

**Ảnh hưởng production:**  
Caller nhận 500 và có thể retry toàn batch, dẫn đến duplicate processing.

**Cách sửa:**  
Định nghĩa API semantics: endpoint chỉ enqueue/claim work và trả job ID, hoặc trả per-item result nếu xử lý đồng bộ. Persist status từng invoice. Không dùng một HTTP 500 làm nguồn sự thật duy nhất cho trạng thái batch.

---

### High — Trạng thái chỉ có `Pending` và `Ready` nên không mô tả processing lifecycle

**Vấn đề:**  
Không có trạng thái `Processing`, `Failed`, `RetryAt` hoặc processing owner/version.

**Tại sao xảy ra:**  
Business state và execution state bị trộn quá đơn giản.

**Ảnh hưởng production:**  
Khó reclaim stuck work sau crash, khó biết invoice nào đang retry và khó xây reconciliation.

**Cách sửa:**  
Thiết kế state machine tối thiểu, ví dụ:

```text
Pending -> Processing -> Ready
                 -> RetryPending
                 -> Failed
```

Có `ProcessingStartedUtc`, attempt count, optional lease/owner token và policy reclaim stale work.

---

### Medium — Load 500 tracked entities dù chỉ cần bounded claims

**Vấn đề:**  
Query materialize và track 500 entities trước khi biết invoice nào thực sự sẽ được xử lý độc quyền.

**Tại sao xảy ra:**  
Read batch và claim batch chưa được thiết kế cùng nhau.

**Ảnh hưởng production:**  
Memory/change-tracker overhead tăng và race window dài hơn.

**Cách sửa:**  
Claim một bounded batch bằng database operation phù hợp, sau đó load/process chỉ claimed IDs. Nếu dùng direct SQL cho atomic claim thì cần giữ mapping/domain boundary rõ và test kỹ.

---

### Medium — Telemetry không đủ để điều tra mỗi invoice

**Vấn đề:**  
Chỉ log thành công theo `InvoiceId`.

**Tại sao xảy ra:**  
Thiếu batch ID, attempt, tax dependency duration/result, claim outcome, instance và DB save duration.

**Ảnh hưởng production:**  
Không thể phân biệt duplicate claim, retry, slow provider hay database contention.

**Cách sửa:**  
Tạo `BatchId`/operation ID và structured telemetry cho `InvoiceId`, attempt, state transition, dependency duration, DB duration, worker instance và correlation/trace ID.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa một design đơn giản hơn: endpoint tạo một batch request, background worker claim bounded invoices và mỗi invoice dùng `DbContext` riêng. Chi tiết atomic claim phụ thuộc schema/database và phải được triển khai bằng một update có điều kiện hoặc transaction phù hợp.

```csharp
public sealed class InvoiceTaxWorker : BackgroundService
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ITaxClient _taxClient;
    private readonly ILogger<InvoiceTaxWorker> _logger;
    private readonly SemaphoreSlim _parallelism;

    public InvoiceTaxWorker(
        IDbContextFactory<AppDbContext> dbFactory,
        ITaxClient taxClient,
        IOptions<TaxWorkerOptions> options,
        ILogger<InvoiceTaxWorker> logger)
    {
        _dbFactory = dbFactory;
        _taxClient = taxClient;
        _logger = logger;
        _parallelism = new SemaphoreSlim(options.Value.MaxConcurrency);
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var claimedIds = await ClaimBatchAsync(
                batchSize: 50,
                stoppingToken);

            if (claimedIds.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(2), stoppingToken);
                continue;
            }

            var tasks = claimedIds.Select(id => ProcessOneAsync(id, stoppingToken));
            await Task.WhenAll(tasks);
        }
    }

    private async Task ProcessOneAsync(
        Guid invoiceId,
        CancellationToken cancellationToken)
    {
        await _parallelism.WaitAsync(cancellationToken);

        try
        {
            await using var db = await _dbFactory.CreateDbContextAsync(
                cancellationToken);

            var invoice = await db.Invoices
                .SingleAsync(x => x.Id == invoiceId, cancellationToken);

            if (invoice.Status != InvoiceStatus.Processing)
            {
                return;
            }

            try
            {
                var result = await _taxClient.CalculateAsync(
                    invoice.CustomerId,
                    invoice.TotalAmount,
                    idempotencyKey: $"invoice-tax:{invoice.Id}:{invoice.Version}",
                    cancellationToken);

                invoice.TaxAmount = result.Amount;
                invoice.TaxCalculatedUtc = DateTime.UtcNow;
                invoice.Status = InvoiceStatus.Ready;
                invoice.LastError = null;
            }
            catch (TransientTaxException ex)
            {
                invoice.AttemptCount++;
                invoice.Status = InvoiceStatus.RetryPending;
                invoice.NextAttemptUtc = CalculateBackoff(invoice.AttemptCount);
                invoice.LastError = ex.Code;
            }

            await db.SaveChangesAsync(cancellationToken);
        }
        finally
        {
            _parallelism.Release();
        }
    }

    private Task<IReadOnlyList<Guid>> ClaimBatchAsync(
        int batchSize,
        CancellationToken cancellationToken)
    {

        throw new NotImplementedException();
    }
}
```

Một phương án đơn giản hơn vẫn có thể là **không parallel trong application** nếu tax API throughput thấp hoặc volume chưa đủ lớn. Sequential bounded batches đôi khi dễ vận hành, debug và retry hơn.

## Giải thích thiết kế sau khi sửa

### 1. `DbContext` ownership rõ ràng

Mỗi processing unit có context riêng, tránh shared mutable EF state giữa concurrent tasks.

### 2. Claim trước, process sau

Database quyết định worker nào sở hữu work trước khi external side effect bắt đầu.

### 3. Parallelism có giới hạn và cấu hình được

Concurrency được xem là capacity control, không phải càng lớn càng tốt.

### 4. Workflow có durable state

Crash/restart có thể reclaim hoặc retry dựa trên persisted state thay vì suy luận từ HTTP response.

### 5. External dependency được coi là failure-prone

Timeout, ambiguous success và retry phải gắn với idempotency semantics.

## Trade-offs

- Background processing tăng operational complexity so với endpoint đồng bộ.
- Claim/lease state thêm cột và logic reconciliation.
- Context per item tăng số context instances, nhưng context nhẹ hơn nhiều so với chia sẻ sai một context giữa concurrent tasks.
- Bounded parallelism có thể giảm peak throughput nhưng tăng predictability.
- Queue/message broker có thể giúp distribution tốt hơn nhưng không cần thiết nếu SQL-backed claim đã đủ cho scale hiện tại.

## Cách kiểm thử

1. **Concurrency test:** hai worker instances cùng claim batch; cùng invoice không được xử lý song song.
2. **EF Core integration test:** nhiều processing tasks không chia sẻ cùng `DbContext` và không phát sinh concurrent-operation exception.
3. **Failure-path test:** tax API thành công nhưng database save bị inject failure; retry phải tuân theo idempotency contract.
4. **Load test:** tăng concurrency từng bước, đo tax API latency/throttle, SQL connection usage, blocking và p95/p99.
5. **Cancellation/shutdown test:** worker shutdown trong lúc đang xử lý; work phải kết thúc hoặc được reclaim theo policy, không mất trạng thái.

## Quan sát trong production

Theo dõi:

- pending/processing/retry/failed invoice counts;
- age của oldest pending item;
- claim conflict/reclaim count;
- processing duration p50/p95/p99;
- tax API dependency duration, timeout và throttle rate;

# Code Review Challenge 2 — Playwright suite xanh ở local nhưng flaky trên CI, ghi đè dữ liệu lẫn nhau và che mất regression thật

```ts
      await page.waitForTimeout(1000)
    } catch (error) {
      await page.screenshot({ path: 'delete-failure.png' })
    }
  })
})
```

## Nhiệm vụ của ứng viên

Hãy review test suite như một Senior engineer chịu trách nhiệm release quality, không chỉ “làm cho test pass”.

Bạn cần:

1. tìm nguyên nhân flakiness;
2. phân tích fixed timeout so với condition-based waiting;
3. phân tích test-data collisions khi chạy parallel;
4. đánh giá shared-account/shared-state risk;
5. đánh giá selectors hiện tại;
6. tìm false-positive trong test delete;
7. đánh giá blanket retry 3 lần;
8. đề xuất test isolation strategy;
9. đề xuất corrected Playwright implementation/configuration;
10. giải thích telemetry/artifacts cần giữ khi CI fail.

## Câu hỏi gợi mở

1. Nếu backend response mất 100 ms ở local nhưng 4 giây trên CI, `waitForTimeout(3000)` có đúng synchronization primitive không?
2. Nếu 8 workers cùng dùng `Test Employee`, test nào sở hữu record đó?
3. Một `catch` block không `throw` lại exception có thể làm test thất bại trở thành test pass không?
4. Retry 3 lần giúp reliability hay chỉ che một race condition?
5. Selector `.btn-primary`, `table tr:nth...` có gắn với business meaning hay layout implementation?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **thiếu deterministic synchronization và thiếu isolation giữa tests chạy song song**.

### Gợi ý 2

Phân biệt:

- chờ một điều kiện có ý nghĩa;
- chờ một khoảng thời gian đoán trước;
- retry để xử lý transient infrastructure;
- retry đang che một bug thật.

## Kết quả code review tham khảo

### Critical — Test delete có thể fail nhưng vẫn được báo pass

**Vấn đề:**  
Mọi exception bị catch, chỉ chụp screenshot rồi không throw lại.

**Tại sao xảy ra:**  
Test runner chỉ biết test fail nếu assertion/operation throw hoặc test được đánh dấu fail theo cơ chế phù hợp.

**Ảnh hưởng production:**  
Release gate có false-positive: chức năng delete có thể hỏng nhưng pipeline vẫn xanh.

**Cách sửa:**  
Không nuốt exception. Playwright đã có screenshot/trace artifacts. Nếu cần custom diagnostics, capture artifact rồi `throw error` lại hoặc dùng test hooks/fixtures thay vì biến lỗi thành success.

---

### High — Shared deterministic test data tạo race giữa workers

**Vấn đề:**  
Các tests dùng cùng tên/email `Test Employee`.

**Tại sao xảy ra:**  
Parallel workers cùng thao tác trên một shared staging database mà không có unique namespace hoặc isolated fixture.

**Ảnh hưởng production:**  
Create có thể duplicate, edit đọc record test khác, delete xóa dữ liệu mà test khác đang dùng. Flakiness tăng khi số workers tăng là tín hiệu mạnh của shared-state collision.

**Cách sửa:**  
Mỗi test hoặc worker cần unique data identity, ví dụ random suffix/worker index/run ID. Tốt hơn nữa, tạo dữ liệu qua test API/fixture và cleanup theo ownership rõ ràng.

---

### High — Test phụ thuộc thứ tự ngầm giữa create/edit/delete

**Vấn đề:**  
`edit employee` và `delete employee` giả định record `Test Employee` đã tồn tại.

**Tại sao xảy ra:**  
Các tests được viết như một sequence nhưng runner có thể chạy độc lập/parallel và order không phải business contract.

**Ảnh hưởng production:**  
Test pass/fail phụ thuộc execution order, retry hoặc dữ liệu còn sót từ run trước.

**Cách sửa:**  
Mỗi test setup dữ liệu nó cần. Nếu thật sự muốn kiểm thử một end-to-end user journey tuần tự, gộp thành một test có scope rõ hoặc dùng serial mode có chủ đích, nhưng không dùng serial để che thiếu isolation toàn suite.

---

### High — Fixed waits tạo vừa flakiness vừa lãng phí thời gian

**Vấn đề:**  
Dùng `waitForTimeout(3000/2000/1500/1000)` làm synchronization.

**Tại sao xảy ra:**  
Thời gian tuyệt đối không chứng minh UI/backend đã đạt trạng thái mong muốn.

**Ảnh hưởng production:**  
CI chậm hơn local thì wait quá ngắn và fail; CI nhanh thì wait chỉ làm test suite chậm.

**Cách sửa:**  
Chờ observable condition: URL, visible/hidden state, specific response, enabled button hoặc assertion auto-waiting. Chỉ dùng fixed delay cho tình huống đặc biệt đã được chứng minh, không làm default sync primitive.

---

### High — Blanket retries có thể che regression và tăng thời gian feedback

**Vấn đề:**  
Mọi test retry 3 lần bất kể loại failure.

**Tại sao xảy ra:**  
Retry được dùng như stabilization mechanism thay vì diagnostic signal.

**Ảnh hưởng production:**  
Race condition hoặc regression có thể pass ở lần 2/3, làm pipeline xanh nhưng chất lượng không deterministic. CI duration cũng tăng mạnh khi có nhiều lỗi.

**Cách sửa:**  
Giảm retries và theo dõi flaky-rate. Có thể cho retry hạn chế trên CI để thu thập evidence, nhưng test flaky phải được coi là defect và quarantine/fix theo policy rõ ràng. Không dùng retry để thay condition-based waiting hoặc data isolation.

---

### High — Selectors dựa trên layout dễ vỡ và có thể chọn sai element

**Vấn đề:**  
`.btn-primary`, `.create-button`, `table tr`.nth(1), `.confirm-dialog .btn-danger` dựa nhiều vào CSS/layout.

**Tại sao xảy ra:**  
Selector không biểu đạt user-facing intent hoặc stable test contract.

**Ảnh hưởng production:**  
UI refactor không đổi behavior vẫn phá test; ngược lại selector quá rộng có thể click nhầm element mà test vẫn tiếp tục.

**Cách sửa:**  
Ưu tiên role/name/label hoặc stable `data-testid` khi semantic locator không đủ. Ví dụ `getByRole('button', { name: 'Create employee' })`, `getByLabel('Email')`.

---

### High — Login fixture lặp UI flow và dùng wait không có semantic

**Vấn đề:**  
Mỗi test login qua UI rồi chờ 3 giây.

**Tại sao xảy ra:**  
Authentication setup bị trộn vào từng business test.

**Ảnh hưởng production:**  
Suite chậm và mọi auth/network jitter làm nhiều tests fail cùng lúc, che signal của chức năng employee management.

**Cách sửa:**  
Nếu mục tiêu test không phải login, dùng authenticated storage state/fixture đã được tạo theo pipeline và user role phù hợp. Giữ một số test riêng kiểm thử login UI thực sự.

---

### Medium — Shared admin account có thể tạo state coupling và audit ambiguity

**Vấn đề:**  
8 workers dùng cùng một identity.

**Tại sao xảy ra:**  
Test isolation chỉ xét browser context mà không xét application/database state theo user.

**Ảnh hưởng production:**  
Session limits, audit logs, per-user preferences hoặc server-side state có thể collide. Debug khó biết action đến từ test nào.

**Cách sửa:**  
Tùy app semantics, có thể dùng worker-scoped test users hoặc cùng user nhưng unique run/test correlation. Không cần tạo vô số accounts nếu backend state không phụ thuộc user; quyết định dựa trên actual isolation boundary.

---

### Medium — Assertion chưa đủ mạnh để chứng minh business outcome

**Vấn đề:**  
Create chỉ kiểm tra toast; edit chỉ kiểm tra text chứa `Updated`; delete không có assertion.

**Tại sao xảy ra:**  
UI feedback được coi là đồng nghĩa với persisted business state.

**Ảnh hưởng production:**  
Backend save có thể fail sau optimistic UI update hoặc selector có thể đọc stale element.

**Cách sửa:**  
Chọn assertion dựa trên risk. Với create/edit/delete, có thể verify qua UI sau reload/search hoặc qua test API khi phù hợp. Không cần duplicate mọi layer, nhưng release-critical workflow cần chứng minh persisted outcome.

---

### Medium — Trace bị tắt trong CI nơi cần diagnostic nhất

**Vấn đề:**  
Config `trace: 'off'`.

**Tại sao xảy ra:**  
Artifacts được tối ưu cho local thay vì failure investigation.

**Ảnh hưởng production:**  
Khi flaky test fail trên CI, team thiếu timeline, network/action evidence và DOM state cần thiết để RCA.

**Cách sửa:**  
Bật trace theo policy tiết kiệm storage, ví dụ `retain-on-failure` hoặc `on-first-retry`, cùng screenshot/video khi phù hợp. Giữ artifact theo CI retention policy.

---

## Phiên bản đề xuất

Ví dụ dưới đây dùng test-specific data và condition-based assertions. Giả định hệ thống có test-only API fixture để tạo/xóa employee trong staging test environment; nếu không có, có thể tạo qua UI nhưng vẫn cần unique identity và cleanup.

```ts
import { test, expect } from '@playwright/test'

function uniqueEmployee(testId: string) {
  const suffix = `${testId}-${Date.now()}-${Math.random()
    .toString(16)
    .slice(2)}`

  return {
    name: `E2E Employee ${suffix}`,
    email: `e2e-${suffix}@example.test`
  }
}

test.describe('Employee management', () => {
  test('create employee', async ({ page }, testInfo) => {
    const employee = uniqueEmployee(testInfo.testId)

    await page.goto('/employees')
    await page.getByRole('button', {
      name: 'Create employee'
    }).click()

    await page.getByLabel('Name').fill(employee.name)
    await page.getByLabel('Email').fill(employee.email)

    await Promise.all([
      page.waitForResponse(response =>
        response.url().includes('/api/employees') &&
        response.request().method() === 'POST' &&
        response.ok()),
      page.getByRole('button', { name: 'Save' }).click()
    ])

    await expect(
      page.getByRole('status')
    ).toContainText('Employee created')

    await page.getByPlaceholder('Search employees')
      .fill(employee.email)

    await expect(
      page.getByRole('row', { name: new RegExp(employee.email) })
    ).toBeVisible()
  })

  test('edit employee', async ({ page, request }, testInfo) => {
    const employee = uniqueEmployee(testInfo.testId)

    const created = await createEmployeeFixture(request, employee)

    await page.goto(`/employees/${created.id}`)
    await page.getByLabel('Name').fill(`${employee.name} Updated`)
    await page.getByRole('button', { name: 'Save' }).click()

    await expect(
      page.getByTestId('employee-name')
    ).toHaveText(`${employee.name} Updated`)
  })

  test('delete employee', async ({ page, request }, testInfo) => {
    const employee = uniqueEmployee(testInfo.testId)
    const created = await createEmployeeFixture(request, employee)

    await page.goto(`/employees/${created.id}`)
    await page.getByRole('button', { name: 'Delete' }).click()
    await page.getByRole('button', { name: 'Confirm delete' }).click()

    await expect(page).toHaveURL(/\/employees$/)

    await page.getByPlaceholder('Search employees')
      .fill(employee.email)

    await expect(
      page.getByText(employee.email)
    ).toHaveCount(0)
  })
})
```

Config có thể theo hướng:

```ts
export default defineConfig({
  workers: process.env.CI ? 4 : undefined,
  retries: process.env.CI ? 1 : 0,
  use: {
    baseURL: process.env.APP_URL,
    storageState: 'playwright/.auth/admin.json',
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure'
  }
})
```

`workers: 4` chỉ là ví dụ để bắt đầu sau khi đo lại; con số đúng phụ thuộc capacity của staging environment và test isolation. Nếu suite đã isolation hoàn toàn và backend chịu tải tốt, workers có thể tăng. Nếu environment có shared bottleneck, giảm workers có thể hợp lý hơn.

## Giải thích thiết kế sau khi sửa

### 1. Test data thuộc sở hữu của test

Mỗi test có identity riêng và không dựa vào dữ liệu còn sót từ run trước.

### 2. Synchronization dựa trên state thật

Test chờ response/locator/URL có ý nghĩa thay vì ngủ một khoảng thời gian cố định.

### 3. Business tests không bị auth setup làm nhiễu

Authenticated storage state tách login mechanics khỏi employee workflow. Login có suite riêng.

### 4. Retry là diagnostic aid, không phải correctness mechanism

Một test chỉ pass sau retry vẫn cần được theo dõi như flaky signal.

### 5. CI artifacts là một phần của test design

Trace, screenshot, logs và correlation ID giúp phân biệt app regression, test bug và environment issue.

## Trade-offs

- Unique test data làm database staging tăng nhanh nếu cleanup kém; cần TTL hoặc deterministic cleanup.
- API fixture nhanh và ổn định hơn UI setup nhưng có thể bỏ qua một phần user journey; vì vậy vẫn cần một số full UI flows thực sự.
- Semantic locators phụ thuộc accessibility semantics; nếu UI chưa có label/role tốt, việc cải thiện accessibility cũng giúp testability.
- Giảm workers tăng pipeline duration nhưng có thể cần thiết nếu staging capacity nhỏ.
- Trace/video tăng artifact storage; nên chỉ giữ khi fail/retry theo policy.

## Cách kiểm thử

1. **Parallel isolation test:** chạy cùng suite với 1, 4 và 8 workers; kết quả không được thay đổi do data collisions.
2. **Repeated-run test:** chạy suite nhiều lần liên tiếp trên cùng environment; flaky rate phải gần zero và không phụ thuộc data còn sót.
3. **Failure-injection test:** làm backend create trả 500; test phải fail rõ thay vì chỉ chờ timeout rồi pass ở retry.
4. **Selector-resilience test:** thay đổi CSS class nhưng giữ role/label; core tests không nên vỡ nếu behavior không đổi.
5. **CI diagnostics validation:** cố ý gây một failure và xác minh trace/screenshot/network evidence đủ để RCA.

## Quan sát trong production

Đối với E2E pipeline/staging, theo dõi:

- pass/fail/flaky rate theo test;
- retries per test;
- duration p50/p95 của từng spec;
- worker count và queueing time;
- staging API error/latency trong lúc test chạy;
- test-data creation/cleanup failures;
- CI run ID, test ID và application deployment version;
- Playwright trace/screenshot artifact link;
- backend correlation ID khi business API fail;
- danh sách tests quarantine và tuổi của flaky defect để tránh biến quarantine thành vĩnh viễn.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận chạy một describe block ở serial mode?
2. Bạn phân biệt flaky test do test code với flaky behavior thật của application như thế nào?
3. Nếu E2E suite mất 45 phút, bạn sẽ tối ưu pyramid/test selection thế nào mà không làm release gate yếu đi?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `DbContext` không nên bị chia sẻ giữa concurrent operations; unit-of-work ownership phải rõ ràng.
- Parallelism chỉ an toàn khi concurrency model, downstream capacity và failure semantics được thiết kế cùng nhau.
- Nhiều app instances cần atomic claim hoặc ownership protocol để tránh duplicate work.
- External side effect và database commit không tự trở thành một transaction; idempotency và recovery state là bắt buộc khi retry có thể xảy ra.
- Playwright stability đến từ deterministic synchronization và test isolation, không phải tăng `waitForTimeout`.
- Retry có thể hữu ích để thu thập evidence nhưng không nên che race condition hoặc regression.
- E2E release gate chỉ có giá trị khi test có assertion đủ mạnh và failure không bị nuốt.

## Mẫu tư duy cần nhớ

1. **Own the unit of work before running it concurrently.**
2. **Bound concurrency by downstream capacity, not by CPU count alone.**
3. **Design retry together with idempotency and persisted state.**
4. **Wait for conditions, not guessed time.**
5. **A flaky test is a defect signal, not a reason to add more sleep.**
