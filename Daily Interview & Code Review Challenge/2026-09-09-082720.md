# Code Review Challenge 1 — API “Import từ URL” mở cửa SSRF, giữ connection quá lâu và dễ sập khi upstream trả payload lớn

**Chủ đề:** ASP.NET Core, C#, HttpClient, SSRF, streaming, cancellation, timeout, resource limits, external API integration  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–12 vấn đề

## Bối cảnh

Một ASP.NET Core API trên .NET 8 cho phép user nhập URL của một file JSON do đối tác cung cấp để import dữ liệu sản phẩm.

Business yêu cầu:

- chỉ import dữ liệu từ các đối tác đã được phê duyệt;
- file thường 1–10 MB nhưng đôi lúc có thể lớn hơn;
- request không được treo vô hạn nếu upstream chậm;
- user hủy request thì hệ thống nên dừng download/parse sớm khi có thể;
- một upstream lỗi không được làm application cạn socket/memory;
- endpoint không được truy cập tài nguyên nội bộ hoặc metadata endpoint ngoài ý muốn.

Sau khi feature lên production:

- một số request giữ connection 1–2 phút;
- memory tăng mạnh khi nhiều import chạy cùng lúc;
- Application Insights có dependency timeout nhưng request vẫn tiếp tục chạy lâu;
- security team phát hiện URL do client gửi có thể trỏ tới hostname tùy ý;
- một developer đề xuất chỉ chặn chuỗi `localhost` là đủ;
- code review trước đó cho rằng tạo `new HttpClient()` trong `using` mỗi request là “an toàn vì đã Dispose”.

Code hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/imports")]
public sealed class ProductImportController : ControllerBase
{
    [HttpPost("from-url")]
    public async Task<IActionResult> ImportFromUrl(
        [FromBody] ImportFromUrlRequest request)
    {
        if (!Uri.TryCreate(request.Url, UriKind.Absolute, out var uri))
        {
            return BadRequest("Invalid URL");
        }

        if (uri.Host.Contains("localhost", StringComparison.OrdinalIgnoreCase))
        {
            return BadRequest("Host is not allowed");
        }

        using var client = new HttpClient();
        client.Timeout = TimeSpan.FromMinutes(2);

        var response = await client.GetAsync(uri);
        response.EnsureSuccessStatusCode();

        var json = await response.Content.ReadAsStringAsync();
        var items = JsonSerializer.Deserialize<List<ProductImportItem>>(json);

        if (items is null || items.Count == 0)
        {
            return BadRequest("No products found");
        }

        await _importService.ImportAsync(items);

        return Ok(new { imported = items.Count });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề về security, correctness và reliability.
2. Xác định memory/network/resource risks khi payload lớn hoặc upstream chậm.
3. Giải thích vì sao một blacklist đơn giản cho hostname không đủ để chống SSRF.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation/design đã sửa.
6. Mô tả cách kiểm thử SSRF, timeout, cancellation, large payload và upstream failure.
7. Đề xuất production telemetry để chứng minh endpoint an toàn và ổn định hơn.

## Câu hỏi gợi mở

1. URL có thể resolve tới địa chỉ private/link-local/loopback dù hostname không chứa `localhost` không?
2. Redirect từ một host được phép sang host nội bộ được xử lý thế nào?
3. `GetAsync` hiện buffer response tới mức nào và code đang materialize payload thêm bao nhiêu lần?
4. `HttpClient` lifetime hiện ảnh hưởng DNS/socket reuse và connection pooling ra sao?
5. `HttpContext.RequestAborted` đang được propagate xuống download, deserialize và import ở đâu?

## Gợi ý

### Gợi ý 1

Hãy xem URL do user cung cấp như một untrusted network destination, không chỉ là một string cần validate format.

### Gợi ý 2

Payload lớn + buffering + deserialize toàn bộ + nhiều concurrent imports có thể tạo memory amplification ngay cả khi mỗi file riêng lẻ không quá lớn.

## Kết quả code review tham khảo

### Critical — SSRF vì client được phép chọn arbitrary destination

**Vấn đề:** Endpoint nhận URL từ client rồi cho server gọi trực tiếp tới host bất kỳ, chỉ chặn chuỗi `localhost`.

**Tại sao xảy ra:** Validation đang dựa trên hostname text thay vì một allowlist/network policy đáng tin cậy. Host có thể là IP literal, DNS name resolve tới loopback/private/link-local address, hoặc redirect sang destination không được phép.

**Ảnh hưởng production:** Attacker có thể khiến server truy cập internal services, metadata endpoints, admin panels hoặc network resources mà browser của attacker không truy cập được trực tiếp.

**Cách sửa:** Không cho user chọn arbitrary origin nếu business chỉ có một tập đối tác hữu hạn. Dùng allowlist chính xác theo partner/domain/endpoint đã cấu hình server-side. Resolve/validate network destination theo policy phù hợp, không cho loopback/private/link-local/internal ranges khi không có nhu cầu. Redirect phải bị disable hoặc được revalidate từng hop. Egress/network policy ở infrastructure nên được xem như defense-in-depth, không thay application validation.

### High — `HttpClient` được tạo mới cho mỗi request

**Vấn đề:** `new HttpClient()` trong endpoint tạo handler/connection-pool lifecycle không phù hợp cho high-throughput server code.

**Tại sao xảy ra:** Dispose object không đồng nghĩa connection/network resources được quản lý tối ưu cho repeated outbound traffic. Tạo client/handler liên tục có thể giảm connection reuse và làm behavior DNS/connection khó kiểm soát.

**Ảnh hưởng production:** Tăng connection churn, có thể góp phần vào socket/port pressure và latency dưới load.

**Cách sửa:** Dùng `IHttpClientFactory` với named/typed client cho partner integration, cấu hình handler, timeout, redirect policy và telemetry tập trung. Nếu dùng một long-lived client theo design khác cũng phải quản lý handler/DNS lifecycle có chủ đích.

### High — Không propagate cancellation

**Vấn đề:** `RequestAborted` không được truyền vào `GetAsync`, đọc content, deserialize/import.

**Tại sao xảy ra:** Method không nhận hoặc không sử dụng `CancellationToken`.

**Ảnh hưởng production:** User/ngateway đã bỏ request nhưng server vẫn download, parse và ghi database, làm lãng phí CPU, memory, network và connection capacity.

**Cách sửa:** Nhận `CancellationToken` từ action hoặc dùng `HttpContext.RequestAborted`, propagate xuyên suốt các API hỗ trợ cancellation. Với business operation không nên bị hủy sau một commit boundary cụ thể, cần xác định boundary rõ thay vì bỏ cancellation toàn bộ flow.

### High — Buffer/materialize toàn bộ payload vào string rồi list

**Vấn đề:** `ReadAsStringAsync()` tạo một chuỗi chứa toàn bộ JSON; deserialize tiếp thành toàn bộ `List<ProductImportItem>`.

**Tại sao xảy ra:** Flow giả định payload nhỏ và không có memory budget.

**Ảnh hưởng production:** Peak memory có thể lớn hơn payload nhiều lần do byte buffer, decoded string, JSON parser allocations và object graph cùng tồn tại. Nhiều imports đồng thời có thể tạo GC/LOH pressure hoặc OOM.

**Cách sửa:** Đặt hard size limit và concurrency limit. Khi format/business cho phép, dùng response streaming (`ResponseHeadersRead`) và deserialize stream/batch tuần tự thay vì materialize toàn bộ payload. Nếu cần full validation trước commit, có thể stream vào staging storage/table rồi validate/promote.

### High — Không có explicit response-size/content policy

**Vấn đề:** Code tin server upstream về payload size và content.

**Tại sao xảy ra:** Không kiểm tra Content-Length khi có, không có byte limit khi stream, không xác thực Content-Type theo contract.

**Ảnh hưởng production:** Một upstream bị compromise hoặc URL malicious có thể trả payload rất lớn, vô hạn hoặc sai format, làm application giữ tài nguyên lâu và tăng memory/CPU.

**Cách sửa:** Định nghĩa max compressed/uncompressed bytes phù hợp, validate content metadata nhưng vẫn enforce limit trong lúc đọc vì header có thể thiếu/sai. Reject format/content type không đúng contract khi policy yêu cầu.

### High — Redirect có thể bypass destination validation

**Vấn đề:** URL ban đầu có thể hợp lệ theo allowlist nhưng HTTP redirect đưa request sang host khác.

**Tại sao xảy ra:** Redirect behavior nằm ở handler và code không revalidate destination cuối/each hop.

**Ảnh hưởng production:** SSRF protection có thể bị bypass qua open redirect của đối tác hoặc endpoint bị compromise.

**Cách sửa:** Với import endpoint nhạy cảm, ưu tiên disable automatic redirects trừ khi thực sự cần. Nếu cần redirect, giới hạn số hop và revalidate từng destination theo cùng allowlist/network policy.

### Medium — Timeout 2 phút là một con số global, không phải end-to-end budget

**Vấn đề:** Chỉ đặt một `HttpClient.Timeout` lớn mà không liên hệ với API SLO, proxy timeout, import duration và downstream behavior.

**Tại sao xảy ra:** Timeout được dùng như config đơn lẻ thay vì request budget.

**Ảnh hưởng production:** Request có thể giữ server resources rất lâu; upstream chậm hàng loạt làm concurrency tăng và tạo cascading latency.

**Cách sửa:** Định nghĩa connect/request/read/overall timeout theo contract và SLO. Có thể tách import dài thành asynchronous job nếu synchronous HTTP không còn phù hợp. Retry chỉ dùng cho transient safe operations và phải bounded; không tự động retry một payload lớn nhiều lần nếu không cần.

### Medium — Error handling để exception bubble thành response không có contract rõ

**Vấn đề:** DNS failure, timeout, JSON invalid, non-success HTTP và import failure không được map thành error semantics nhất quán.

**Tại sao xảy ra:** Happy-path-centric implementation.

**Ảnh hưởng production:** User nhận 500 không rõ nghĩa; logs khó phân biệt bad upstream, bad payload, timeout hay internal DB failure.

**Cách sửa:** Dùng centralized exception handling/ProblemDetails và phân loại lỗi: invalid request, forbidden destination, upstream timeout/unavailable, payload invalid, internal persistence failure. Không log raw sensitive payload/credentials trong URL.

### Medium — Không giới hạn concurrency của một operation resource-heavy

**Vấn đề:** Mỗi API request có thể mở một outbound connection và giữ memory/import work; không có admission control.

**Tại sao xảy ra:** Concurrency được quyết định hoàn toàn bởi incoming traffic.

**Ảnh hưởng production:** Một burst hợp lệ hoặc abuse có thể làm cạn outbound connections, memory và DB throughput.

**Cách sửa:** Dùng rate limit/concurrency limiter per tenant/user/partner hoặc chuyển sang job queue với bounded workers khi workload dài. Chọn limit dựa trên memory/network/DB capacity evidence.

### Medium — URL có thể chứa credential/query secret và bị log ngoài ý muốn

**Vấn đề:** Full partner URL có thể chứa token/query signature.

**Tại sao xảy ra:** Không có policy tách destination identity khỏi credentials.

**Ảnh hưởng production:** Structured logs, traces hoặc exception messages có thể làm lộ secret.

**Cách sửa:** Ưu tiên server-side partner configuration + secret store. Nếu URL buộc phải chứa sensitive query, redaction phải được enforce trong logging/telemetry.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa typed client + server-side allowlist + streaming + byte limit + cancellation. Network validation thực tế nên nằm trong một reusable policy/service được test kỹ, không nhét toàn bộ logic DNS/IP vào controller.

```csharp
public sealed record ImportFromUrlRequest(string Url);

[ApiController]
[Route("api/imports")]
public sealed class ProductImportController : ControllerBase
{
    private const long MaxResponseBytes = 25 * 1024 * 1024;

    private readonly PartnerImportClient _partnerClient;
    private readonly IProductImportService _importService;

    public ProductImportController(
        PartnerImportClient partnerClient,
        IProductImportService importService)
    {
        _partnerClient = partnerClient;
        _importService = importService;
    }

    [HttpPost("from-url")]
    public async Task<IActionResult> ImportFromUrl(
        ImportFromUrlRequest request,
        CancellationToken cancellationToken)
    {
        if (!Uri.TryCreate(request.Url, UriKind.Absolute, out var uri))
        {
            return BadRequest(new ProblemDetails
            {
                Title = "Invalid import URL"
            });
        }

        if (!_partnerClient.IsAllowedDestination(uri))
        {
            return BadRequest(new ProblemDetails
            {
                Title = "Import destination is not allowed"
            });
        }

        await using var responseStream = await _partnerClient
            .OpenJsonStreamAsync(uri, MaxResponseBytes, cancellationToken);

        var result = await _importService.ImportJsonStreamAsync(
            responseStream,
            cancellationToken);

        return Ok(new { imported = result.ImportedCount });
    }
}

public sealed class PartnerImportClient
{
    private readonly HttpClient _httpClient;
    private readonly IPartnerDestinationPolicy _destinationPolicy;

    public PartnerImportClient(
        HttpClient httpClient,
        IPartnerDestinationPolicy destinationPolicy)
    {
        _httpClient = httpClient;
        _destinationPolicy = destinationPolicy;
    }

    public bool IsAllowedDestination(Uri uri) =>
        uri.Scheme == Uri.UriSchemeHttps &&
        _destinationPolicy.IsAllowed(uri);

    public async Task<Stream> OpenJsonStreamAsync(
        Uri uri,
        long maxBytes,
        CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(HttpMethod.Get, uri);
        var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        response.EnsureSuccessStatusCode();

        if (response.Content.Headers.ContentLength is long length &&
            length > maxBytes)
        {
            response.Dispose();
            throw new InvalidDataException("Import payload is too large.");
        }

        var stream = await response.Content.ReadAsStreamAsync(cancellationToken);
        return new SizeLimitedResponseStream(stream, response, maxBytes);
    }
}
```

`SizeLimitedResponseStream` ở ví dụ trên đại diện cho một wrapper giữ ownership của `HttpResponseMessage`, đếm số bytes thực tế đọc và throw khi vượt budget. Không nên chỉ tin `Content-Length`.

Typed client nên được đăng ký bằng `IHttpClientFactory`; handler có thể disable redirect mặc định và cấu hình timeout phù hợp với integration contract. Destination policy nên dùng allowlist server-side và được kiểm thử với IP literal, DNS resolution, redirect và các network ranges bị cấm theo kiến trúc thực tế.

## Giải thích thiết kế sau khi sửa

- Destination trust được quyết định server-side thay vì blacklist string.
- HTTP connection management được tập trung qua typed client/`IHttpClientFactory`.
- Download dùng streaming và byte budget để giảm memory amplification.
- Cancellation được propagate end-to-end.
- Redirect policy, timeout và telemetry có một ownership rõ.
- Import service nhận stream để có thể parse/batch mà không buộc materialize toàn payload.
- Nếu workload lớn/đắt, endpoint có thể tiến hóa thành asynchronous job thay vì giữ request HTTP lâu.

## Trade-offs

- Streaming parser/import phức tạp hơn `ReadAsStringAsync` + deserialize list.
- Strict allowlist yêu cầu operational process khi thêm partner mới.
- DNS/IP validation cần cẩn thận với DNS rebinding và network topology; application policy không thay egress firewall/network controls.
- Disable redirect có thể làm một số partner integration không hoạt động nếu họ phụ thuộc redirect; nếu bật lại phải revalidate từng hop.
- Asynchronous import tăng reliability/capacity control nhưng thêm job state, polling/notification và retry/idempotency requirements.

## Cách kiểm thử

1. **Security test:** URL trỏ tới loopback, private IP, link-local, IP literal, alternate hostname và redirect sang destination cấm phải bị reject.
2. **Failure-path integration test:** upstream timeout, DNS failure, 500, invalid JSON và connection reset phải trả error contract đúng, không làm process treo.
3. **Large-payload/load test:** nhiều imports đồng thời ở gần size limit; đo heap, GC, outbound connections, p95/p99 và verify limit hoạt động cả khi thiếu/sai `Content-Length`.
4. **Cancellation test:** client hủy request giữa download/parse; verify outbound request và import work dừng, không tiếp tục ghi ngoài boundary đã định.
5. **Partner-contract test:** allowlisted HTTPS endpoint hợp lệ, content type/size đúng và payload được stream/import thành công.

## Quan sát trong production

- outbound dependency duration/error/timeout theo partner;
- concurrent active imports và rejection do concurrency/size policy;
- bytes downloaded/import request;
- request cancellation count;
- process memory, GC, LOH/allocation nếu workload lớn;
- socket/connection failures và HTTP dependency pool metrics khi có;
- SSRF policy rejection count theo category, không log raw secret URL;
- import success/failure/invalid-payload rate;
- p95/p99 của download, parse và persistence tách riêng qua traces.

## Câu hỏi phỏng vấn mở rộng

1. Nếu partner bắt buộc dùng signed URL trên một CDN có hostname thay đổi, bạn thiết kế trust model thế nào mà không mở arbitrary egress?
2. Nếu payload 5 GB nhưng business vẫn muốn import, bạn chuyển synchronous endpoint thành architecture nào?
3. Nếu network team nói đã có outbound firewall nên application không cần SSRF validation nữa, bạn phản biện thế nào?

# Code Review Challenge 2 — Optimizely CMS + Akamai cache public nhầm preview/personalized content và không purge đúng sau publish

**Chủ đề:** Optimizely CMS, ASP.NET Core, Akamai/CDN, Cache-Control, personalization, preview, content freshness, SEO, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–10 vấn đề

## Bối cảnh

Một marketing website dùng Optimizely CMS và ASP.NET Core. Public pages được cache qua Akamai để giảm origin load và cải thiện Core Web Vitals.

Site có:

- published content theo locale;
- editor preview cho draft content;
- một số block hiển thị khác nhau theo authenticated user segment;
- SEO metadata từ CMS;
- campaign pages cần cập nhật nhanh sau publish;
- CDN cache hit ratio là KPI quan trọng.

Sau một release tối ưu caching:

- editor đôi lúc mở preview nhưng thấy nội dung public cũ;
- một số user báo block personalized hiển thị nội dung không đúng segment;
- campaign page đã publish nhưng edge vẫn trả bản cũ vài phút;
- SEO crawler đôi lúc thấy metadata không đồng nhất theo locale;
- origin logs giảm mạnh nhưng incident khó debug vì log không cho biết response đến từ cache layer nào;
- team đề xuất tăng TTL lên 24 giờ để tăng cache hit ratio.

Code/header policy hiện tại được rút gọn như sau:

## Đoạn code cần review

```csharp
public sealed class CmsPageController : Controller
{
    private readonly ICmsPageService _pages;

    public CmsPageController(ICmsPageService pages)
    {
        _pages = pages;
    }

    [HttpGet("/{**path}")]
    public async Task<IActionResult> Page(
        string? path,
        string? lang,
        bool preview = false)
    {
        var language = string.IsNullOrWhiteSpace(lang) ? "en" : lang;

        var page = await _pages.GetAsync(
            path ?? "/",
            language,
            includeDraft: preview);

        if (page is null)
        {
            return NotFound();
        }

        Response.Headers.CacheControl = "public,max-age=300,s-maxage=3600";
        Response.Headers.Vary = "Accept-Encoding";
        Response.Headers["X-Page-Key"] = page.ContentId.ToString();

        return View("CmsPage", page);
    }
}
```

Akamai behavior hiện được mô tả ở mức policy:

```yaml
cache:
  match:
    path: "/*"
  cache_key:
    include:
      - path
      - query: "lang"
  ttl: 3600
  honor_origin_cache_control: true

purge:
  on_publish:
    path: "/{contentSlug}"
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề về cache correctness, privacy/security và content freshness.
2. Giải thích vì sao cùng URL có thể không đại diện cho cùng representation khi có preview, authentication, personalization và locale.
3. Xác định các SEO/performance trade-offs trong cache-key và TTL design.
4. Ưu tiên issue theo severity.
5. Đề xuất caching/header/purge strategy đã sửa.
6. Mô tả test cho preview, personalization, publish, locale và CDN behavior.
7. Đề xuất telemetry để phân biệt browser cache, CDN HIT/MISS và origin behavior.

## Câu hỏi gợi mở

1. Một response chứa draft content có bao giờ được phép `public` cache không?
2. Authentication/user segment có tham gia cache key hoặc bypass policy ở đâu?
3. `preview=true` có tham gia Akamai cache key hiện tại không?
4. Publish một shared block có thể ảnh hưởng bao nhiêu page URLs ngoài `contentSlug` của chính block?
5. Locale được lấy từ query, route, domain, cookie hay CMS context; cache key hiện đã phản ánh đúng source đó chưa?

## Gợi ý

### Gợi ý 1

CDN chỉ an toàn khi mọi request có cùng cache key thực sự được phép nhận cùng representation.

### Gợi ý 2

Invalidation không chỉ là purge “URL của content vừa publish”; dependency graph giữa page và shared blocks có thể làm nhiều URLs trở nên stale.

## Kết quả code review tham khảo

### Critical — Preview/draft response bị đánh dấu `public`

**Vấn đề:** Controller luôn set `Cache-Control: public` kể cả khi `preview=true` và `includeDraft` được bật.

**Tại sao xảy ra:** Cache policy không phân biệt editorial preview với public published representation.

**Ảnh hưởng production:** Draft/unpublished content có nguy cơ được lưu ở shared cache/CDN rồi phục vụ cho request public khác nếu cache key/cookie/routing trùng. Đây vừa là correctness vừa có thể là content confidentiality issue.

**Cách sửa:** Preview/editor request phải bypass shared CDN cache và thường dùng `private, no-store` hoặc policy tương đương phù hợp với preview architecture. Preview mode nên được xác định từ trusted editor/auth context, không chỉ một query boolean do anonymous client bật.

### Critical — Personalized/authenticated content có thể bị shared-cache dùng chung

**Vấn đề:** Response luôn `public`, trong khi page có block phụ thuộc user segment/authentication; cache key không chứa identity/segment và policy không bypass authenticated requests.

**Tại sao xảy ra:** Origin caching coi page là một representation public duy nhất dù rendering thực tế phụ thuộc request context.

**Ảnh hưởng production:** User A có thể nhận HTML đã render cho segment/user B. Nếu block chứa dữ liệu nhạy cảm, đây là data leak; kể cả không nhạy cảm vẫn là business correctness issue.

**Cách sửa:** Không shared-cache full HTML nếu response chứa user-specific/private data. Một lựa chọn là bypass CDN cache cho authenticated/personalized pages; một lựa chọn khác là tách public shell/cacheable fragments khỏi personalized data được tải client/server-side riêng với authorization. Chỉ cache theo segment nếu segment nhỏ, không nhạy cảm và contract cho phép, với key rõ ràng và invalidation manageable.

### High — Preview query không nằm trong CDN cache key

**Vấn đề:** Akamai key chỉ có `path + lang`, bỏ `preview`.

**Tại sao xảy ra:** Cache key không phản ánh representation dimension.

**Ảnh hưởng production:** Request preview có thể HIT public cache cũ hoặc nếu origin response bị cache, draft có thể poison public key.

**Cách sửa:** Tốt nhất bypass cache hoàn toàn cho preview thay vì thêm `preview=true` vào shared cache key. Preview should not become a public cache namespace.

### High — `preview` được trust từ anonymous query parameter

**Vấn đề:** Bất kỳ caller nào cũng có thể gửi `?preview=true` và controller yêu cầu service lấy draft.

**Tại sao xảy ra:** Editorial authorization không gắn với preview capability.

**Ảnh hưởng production:** Nếu service trả draft chỉ dựa trên flag này, anonymous users có thể xem unpublished content ngay cả khi CDN đã bypass đúng.

**Cách sửa:** Preview phải yêu cầu authenticated editor context/policy/token do CMS preview workflow phát hành. `includeDraft` chỉ được true sau authorization server-side.

### High — Purge theo một slug không xử lý shared-content dependencies

**Vấn đề:** `on_publish` chỉ purge `/{contentSlug}`.

**Tại sao xảy ra:** CMS content được giả định map một-một với URL. Trong thực tế shared block/component có thể xuất hiện trên nhiều pages; navigation/metadata/data source cũng có dependency rộng hơn.

**Ảnh hưởng production:** Publish block/header/footer/campaign component có thể để nhiều cached pages stale tới hết TTL.

**Cách sửa:** Xây invalidation theo rendered-content dependency hoặc cache tag/surrogate-key concept nếu CDN/integration hỗ trợ phù hợp. Tối thiểu maintain mapping content → affected URLs và purge bounded set. Nếu dependency quá rộng, versioned cache namespace/short TTL + targeted purge có thể đơn giản hơn.

### High — Locale/cache-key semantics có thể không khớp cách CMS chọn culture thực tế

**Vấn đề:** Controller lấy locale từ query `lang`, trong khi production site có thể dùng route/domain/cookie/request culture. CDN key cũng chỉ nhìn query `lang`.

**Tại sao xảy ra:** Origin và edge không có một canonical locale dimension.

**Ảnh hưởng production:** User/crawler có thể nhận HTML/metadata sai locale từ cache; canonical/hreflang/SEO signals trở nên không nhất quán.

**Cách sửa:** Chọn một canonical URL/culture strategy, ví dụ locale trong route hoặc domain. CDN key phải phản ánh đúng public representation. Tránh để cookie hoặc implicit culture silently thay HTML mà cache key không biết.

### Medium — `Vary: Accept-Encoding` không giải quyết các representation dimensions quan trọng

**Vấn đề:** Origin chỉ `Vary` theo compression nhưng page còn khác theo preview/auth/locale/personalization.

**Tại sao xảy ra:** `Vary` được dùng như generic cache fix nhưng không thể thay business cache segmentation.

**Ảnh hưởng production:** Shared cache vẫn có thể mix representations nếu edge config không bypass đúng.

**Cách sửa:** Dùng explicit CDN behavior/cache key/bypass rules. Không thêm `Vary: Cookie` một cách mù vì có thể làm cache cardinality nổ và gần như triệt tiêu hit ratio.

### Medium — TTL 1 giờ không được liên kết với freshness SLO

**Vấn đề:** `s-maxage=3600` và CDN TTL 3600 được đặt cố định.

**Tại sao xảy ra:** TTL được chọn để tăng hit ratio thay vì dựa trên publish freshness requirement và purge reliability.

**Ảnh hưởng production:** Khi purge fail hoặc dependency mapping thiếu, campaign content stale một giờ. Tăng lên 24 giờ sẽ làm blast radius lớn hơn.

**Cách sửa:** Định nghĩa freshness SLO. Với purge đáng tin, TTL có thể dài hơn như safety net; nếu purge chưa đáng tin, TTL ngắn hơn có thể giảm stale risk. Quyết định bằng hit ratio, origin capacity, publish frequency và stale-content impact.

### Medium — Không có cache-debug metadata tiêu chuẩn hóa

**Vấn đề:** `X-Page-Key` chỉ nói content ID, không cho biết response là published/preview, locale nào, origin version nào, edge HIT/MISS hay cache age.

**Tại sao xảy ra:** Cache observability chưa được thiết kế end-to-end.

**Ảnh hưởng production:** Incident khó xác định stale ở browser, Akamai hay origin/CMS cache.

**Cách sửa:** Correlate release/content version, locale, publish version và CDN diagnostics headers phù hợp. Ở production, chỉ expose metadata không nhạy cảm. Log cache purge event + outcome + content dependency set.

### Medium — Catch-all route/cache policy có thể vô tình cache endpoints không phải public CMS pages

**Vấn đề:** `/{**path}` và CDN `/*` quá rộng nếu cùng host còn auth/API/preview routes.

**Tại sao xảy ra:** Cache behavior dựa trên path wildcard tổng quát.

**Ảnh hưởng production:** Dynamic/private endpoint có thể bị áp public caching ngoài ý muốn khi routing thay đổi.

**Cách sửa:** Positive-match cacheable public routes/content types và explicit bypass cho `/api`, `/account`, preview/editor paths, authenticated requests và responses có `Set-Cookie`/private semantics tùy architecture.

## Phiên bản đề xuất

Dưới đây là pseudo-code/pseudo-policy nhằm thể hiện cache semantics. API cụ thể của Optimizely/Akamai nên được map theo implementation hiện tại của dự án.

```csharp
[HttpGet("/{culture}/{**path}")]
public async Task<IActionResult> Page(
    string culture,
    string? path,
    CancellationToken cancellationToken)
{
    var previewContext = await _previewContext.TryGetAuthorizedAsync(
        HttpContext,
        cancellationToken);

    var page = await _pages.GetAsync(
        path ?? "/",
        culture,
        includeDraft: previewContext.IsAuthorized,
        cancellationToken);

    if (page is null)
    {
        return NotFound();
    }

    if (previewContext.IsAuthorized || User.Identity?.IsAuthenticated == true)
    {
        Response.Headers.CacheControl = "private,no-store";
        Response.Headers["X-Cache-Mode"] = "bypass";
    }
    else if (page.ContainsPersonalizedContent)
    {
        Response.Headers.CacheControl = "private,no-store";
        Response.Headers["X-Cache-Mode"] = "bypass-personalized";
    }
    else
    {
        Response.Headers.CacheControl = "public,max-age=60,s-maxage=1800";
        Response.Headers["X-Cache-Tag"] = string.Join(
            ",",
            page.DependencyContentIds.Select(x => $"content-{x}"));
        Response.Headers["X-Content-Version"] = page.PublishedVersion;
    }

    return View("CmsPage", page);
}
```

Akamai policy ở mức nguyên tắc:

```yaml
cache:
  public_cms_pages:
    match:
      route: "/{culture}/**"
      method: GET
      anonymous_only: true
      preview: false
    bypass_if:
      - authenticated: true
      - response_cache_control: "private|no-store"
      - path_prefix: "/api"
      - path_prefix: "/cms-preview"
    cache_key:
      include:
        - normalized_path
        - culture
    honor_origin_cache_control: true

purge:
  on_publish:
    strategy: dependency-tags-or-affected-urls
    retry: bounded
    audit: true
```

Nếu personalized content chỉ chiếm một block nhỏ, một architecture tốt hơn có thể là cache public page shell ở CDN và tải block personalized qua authenticated API riêng. Điều này giữ hit ratio cao mà không shared-cache dữ liệu user-specific.

## Giải thích thiết kế sau khi sửa

- Preview được authorize và bypass shared cache hoàn toàn.
- Authenticated/personalized responses không dùng public full-page cache.
- Locale trở thành phần canonical của URL/cache key thay vì implicit request state.
- Public cache chỉ áp cho representations thật sự dùng chung giữa anonymous users.
- Publish invalidation đi theo dependency thay vì một slug đơn lẻ.
- TTL được xem là freshness/capacity control, không phải KPI tối đa hóa càng lớn càng tốt.
- Cache observability có content version + purge audit + edge diagnostics.

## Trade-offs

- Bypass personalized pages làm giảm CDN hit ratio và tăng origin load.
- Tách personalized fragment thành API tăng frontend/API complexity nhưng giữ public shell cacheable.
- Dependency-based purge cần mapping/tagging và operational integration với CDN.
- Locale trong URL có thể cần redirects/canonical migration nếu site hiện dùng cookie/query.
- TTL ngắn giảm stale risk nhưng tăng origin traffic; TTL dài cần purge reliability cao hơn.
- Không nên cache theo mọi cookie/user attribute vì cache-key cardinality có thể làm hit ratio sụp và tăng privacy risk.

## Cách kiểm thử

1. **Preview security/integration test:** anonymous `preview=true` không được thấy draft; authorized editor thấy draft và response không shared-cache.
2. **Personalization test:** hai authenticated users/segments không nhận HTML của nhau qua CDN; public cache không chứa personalized output.
3. **Publish/purge test:** publish một shared block xuất hiện trên nhiều pages; verify tất cả affected URLs/tags bị invalidated trong freshness SLO.
4. **Locale/SEO test:** cùng content ở nhiều locales trả đúng title/meta/canonical/hreflang và cache không cross-locale; crawler path nhận server-rendered metadata đúng.
5. **CDN failure-path test:** purge API fail hoặc delayed; verify retry/alert và TTL safety net behavior, đồng thời đo stale window.

## Quan sát trong production

- CDN HIT/MISS/BYPASS ratio theo route/culture;
- `Age`/edge diagnostics headers phù hợp và origin cache mode;
- content published version vs version thực tế được serve;
- purge request count, latency, failure/retry và affected tags/URLs;
- origin request volume, p95/p99 và CPU sau policy change;
- preview cache-bypass verification;
- stale-content incident count/freshness lag;
- SEO crawl monitoring cho status/canonical/locale consistency;
- cache hit ratio phải được đọc cùng freshness/privacy correctness, không dùng như KPI độc lập.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business muốn cache cả personalized pricing theo 12 customer segments, bạn quyết định cache-at-edge hay tách API dựa trên tiêu chí nào?
2. Nếu shared block xuất hiện trên 50.000 pages, purge toàn bộ URLs sau mỗi publish còn hợp lý không; bạn thiết kế cache version/tag strategy thế nào?
3. Nếu tăng TTL từ 30 phút lên 24 giờ làm hit ratio tăng rõ nhưng purge success chỉ 99%, bạn đánh giá rủi ro và quyết định ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- URL do user cung cấp là một **network trust boundary**; format validation hoặc blacklist hostname không đủ để chống SSRF.
- Outbound HTTP integration cần được thiết kế cùng connection reuse, redirect policy, timeout, cancellation, response-size limit và streaming.
- Resource-heavy endpoints cần bounded concurrency/admission control; nếu workload dài hoặc payload rất lớn, asynchronous job thường là boundary hợp lý hơn synchronous HTTP.
- CDN full-page cache chỉ an toàn khi mọi request có cùng cache key được phép nhận cùng representation.
- Preview, authentication, personalization, locale và CMS dependency graph phải là input trực tiếp của cache/invalidation design.
- Cache hit ratio cao không có giá trị nếu đổi lấy rò draft/private content hoặc stale campaign/SEO metadata.

## Mẫu tư duy cần nhớ

1. **Validate trust boundaries, not strings:** URL, identity và cache key đều phải phản ánh security semantics thật.
2. **Bound expensive work:** giới hạn bytes, time và concurrency thay vì tin upstream/traffic sẽ luôn “bình thường”.
3. **Stream when the full dataset need not live at once.**
4. **Cache only equivalent representations:** nếu output phụ thuộc user/preview/locale thì cache key hoặc bypass policy phải phản ánh điều đó.
5. **Design invalidation and observability together:** publish/purge chỉ đáng tin khi có dependency model, audit và freshness telemetry.
