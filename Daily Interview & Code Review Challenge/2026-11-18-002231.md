# Câu 1 — Cơ chế keyset pagination với dữ liệu thay đổi

**Loại câu hỏi:** Internal mechanism  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** SQL Server, EF Core, LINQ, indexes

## Bối cảnh

API .NET 8 phục vụ 5 triệu Orders, React tải 50 dòng/trang. OFFSET 100.000 có p95 2,5 giây; cursor chỉ có CreatedAt khiến đôi lúc thiếu/trùng đơn. CreatedAt có thể trùng, Id là bigint duy nhất. Có concurrent inserts và status updates.

## Câu hỏi chính

Giải thích cơ chế OFFSET và keyset, sửa cursor và xác định consistency contract.

## Câu hỏi làm rõ nên cân nhắc

1. Sort key có bất biến không?
2. Cần live feed hay snapshot?
3. Filter tenant/status nào phổ biến?
4. Có cần nhảy trang N không?

## Gợi ý tư duy

### Gợi ý 1

Xem thứ tự có unique không.

### Gợi ý 2

So sánh số rows phải skip với index seek.

### Gợi ý 3

Dùng cặp (CreatedAt, Id) và xét concurrent writes.

## Cấu trúc trả lời đề xuất

1. Làm rõ semantics
2. Phân tích execution plan
3. Thiết kế query/index/cursor
4. Kiểm chứng concurrency
5. Đo production

## Ý chính của câu trả lời tốt

### Bắt buộc

Total ordering theo CreatedAt DESC, Id DESC; cursor predicate phải xử lý tie; keyset không tự đảm bảo snapshot.

### Điểm cộng

Composite index theo tenant/sort; cursor opaque signed, filter-bound; pageSize+1.

### Senior+

Snapshot qua nhiều HTTP requests cần materialization/as-of semantics; một transaction snapshot riêng mỗi request không tạo snapshot chung.

## Hướng giải quyết tham khảo

OFFSET phải đi qua và loại nhiều rows khi trang sâu; chi phí thực tế phụ thuộc index và plan. Cursor chỉ CreatedAt với dấu < bỏ sót rows cùng timestamp; <= lặp rows. Với CreatedAt immutable, truy vấn:
```sql
SELECT TOP (@Take) Id, CreatedAt, Status
FROM dbo.Orders
WHERE TenantId = @TenantId
AND (@LastTime IS NULL OR CreatedAt < @LastTime
  OR (CreatedAt = @LastTime AND Id < @LastId))
ORDER BY CreatedAt DESC, Id DESC;
```
Take = pageSize+1, cursor lấy từ row cuối thực sự trả. Đánh giá index (TenantId, CreatedAt DESC, Id DESC) INCLUDE các trường projection; nếu Status equality phổ biến, benchmark index có Status trước sort. Kiểm tra actual plan, logical reads, Query Store, write overhead. Concurrent inserts phía trước cursor không xuất hiện ở trang tiếp; status changes có thể làm rows chuyển khỏi filter. Nếu cần snapshot bất biến, lưu snapshot IDs hoặc versioned/as-of view; watermark một mình không chống sửa/xóa. Không giữ SQL transaction mở qua nhiều HTTP requests. Test hàng trăm timestamp trùng, insert/update/delete giữa các trang, benchmark offsets sâu và monitor p95, logical reads, duplicate rates.

## Mẫu trả lời trong phỏng vấn

Tôi sẽ hỏi UI cần live list hay snapshot. OFFSET chậm vì phải bỏ qua nhiều hàng; keyset tốt hơn nếu có index phù hợp. Cursor chỉ timestamp là sai khi có ties, nên tôi sắp xếp và lọc bằng (CreatedAt, Id). Tôi đo plan/IO trước khi thêm index. Live pagination không hứa snapshot dưới concurrent writes. Nếu business cần danh sách bất biến, tôi chọn snapshot/materialization hoặc versioned query, chấp nhận thêm storage và complexity. Tôi kiểm thử concurrency và theo dõi latency cùng correctness.

## Câu hỏi đào sâu

1. Status đổi giữa hai trang thì guarantee gì?
2. Cần jump-to-page 1000 thì chọn gì?
3. Index nào khi có 20 filter? 

## Lỗi trả lời thường gặp

- Chỉ sửa ORDER BY mà không sửa cursor predicate
- Khẳng định keyset luôn snapshot-consistent
- Thêm index không đo IO/write cost
- Dùng NOLOCK để tăng tốc

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Clarification | 2 |
| Technical correctness | 3 |
| Debugging / reasoning | 2 |
| Trade-offs & production readiness | 2 |
| Communication | 1 |

# Câu 2 — App Service 503 sau slot swap dù CPU thấp

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Azure App Service Linux, Managed Identity, Key Vault, Application Insights

## Bối cảnh

API .NET 8 có 4 App Service instances. Sau slot swap, 18% HTTP 500/503, CPU dưới 35%, có instance restart. Startup đọc Key Vault, vài HTTP dependencies timeout. Chưa rõ lỗi do platform, identity, network, readiness hay regression. Khách không submit được đơn.

## Câu hỏi chính

Điều hành incident từ stabilization đến RCA, dùng bằng chứng để phân biệt ít nhất ba giả thuyết.

## Câu hỏi làm rõ nên cân nhắc

1. 503 do platform hay process?
2. Slot settings/identity/network có thay đổi không?
3. Secret đọc startup hay mỗi request?
4. Readiness/liveness kiểm tra gì?
5. Rollback có tương thích schema không?

## Gợi ý tư duy

### Gợi ý 1

Tách ingress, startup, dependencies.

### Gợi ý 2

CPU thấp không chứng minh healthy.

### Gợi ý 3

Đối chiếu deployment timeline, slot settings, Key Vault logs, probe failures.

## Cấu trúc trả lời đề xuất

1. Định lượng impact
2. Stabilize/rollback có điều kiện
3. Thu thập traces theo instance
4. Đặt giả thuyết cạnh tranh
5. Thử bác bỏ từng giả thuyết
6. Fix, verify, prevent

## Ý chính của câu trả lời tốt

### Bắt buộc

Phân biệt HTTP 500 và 503, kiểm tra startup logs, platform logs, dependency telemetry, instance health; không kết luận từ CPU.

### Điểm cộng

Kiểm tra identity RBAC, slot-specific settings, DNS/TLS/private endpoints, timeouts, retry storms.

### Senior+

Readiness không quá nhạy khiến toàn fleet bị loại; staged rollout và rollback gate theo 5xx/healthy instances.

## Hướng giải quyết tham khảo

Trong 5 phút đầu: incident commander, impact, tạm dừng deployment, đánh giá rollback code/config có an toàn với DB schema không. Phân loại 503 từ App Service frontend so với 500 trong app bằng request IDs và ingress logs. Lấy Application Insights requests/dependencies/exceptions, startup stdout, restart reasons, health check, deployment diff và telemetry theo instance.

Giả thuyết A: slot settings hoặc Managed Identity/RBAC khác sau swap → xác thực token acquisition, secret URI, Key Vault 401/403. B: DNS/private endpoint/firewall gây timeout → kiểm tra outbound connectivity, dependency traces. C: startup probe phụ thuộc Key Vault làm instances không ready → đối chiếu startup/probe/restart timeline. D: code regression hoặc connection pool/ThreadPool saturation → xem counters, traces và dependency pools. Mỗi giả thuyết cần phép thử độc lập; chưa đủ dữ liệu để khẳng định RCA.

Nếu chứng minh identity/config sai, sửa đúng slot/permission tối thiểu; nếu network sai, sửa routing; nếu probe quá nhạy, thiết kế liveness chỉ kiểm process và readiness theo khả năng phục vụ. Retry chỉ transient errors với timeout/backoff/jitter, không retry vô hạn 403; tránh log secrets. Rollout canary, smoke test submit thật với identity đúng, theo dõi 5xx, p95, dependency latency, healthy instances, restart count. Thêm pre-swap validation, synthetic transactions và alert per-instance.

## Mẫu trả lời trong phỏng vấn

Tôi sẽ ưu tiên phục hồi submit orders, đóng băng deploy và đánh giá rollback an toàn. CPU thấp không loại trừ lỗi startup hoặc dependency. Tôi phân biệt 503 do platform với lỗi app, so sánh telemetry từng instance và slot configuration. Tôi điều tra song song identity/RBAC, network tới Key Vault, health checks và regression. Chỉ sửa khi có bằng chứng; sau đó canary và đo 5xx, p95, restart và dependency health. RCA phải có timeline và biện pháp ngăn lặp.

## Câu hỏi đào sâu

1. Rollback code không sửa được slot identity thì sao?
2. Có nên fail readiness khi Key Vault outage ngắn?
3. 429 và retry storm xử lý thế nào?

## Lỗi trả lời thường gặp

- Restart toàn bộ trước khi giữ evidence
- Cho rằng CPU thấp là không saturation
- Log token/secret để debug
- Retry vô hạn hoặc rollback schema không tương thích

|---|---:|
| Clarification | 2 |

# Câu 3 — Thiết kế workflow duyệt tuyển dụng có audit và delegation

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 35 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, PostgreSQL, React, Entra ID, Outbox

## Bối cảnh

MVP 8 tuần cho 1.500 hiring requests/ngày: Line Manager → Superior Manager → HR. Có Draft, Submit, Request Changes, resubmit, delegation và admin reassignment. Audit phải giải thích actor, authority, revision. Email có thể outage; chưa rõ SLA hay parallel approvals.

## Câu hỏi chính

Thiết kế state machine, authorization, transaction boundaries và deployment architecture tối giản nhưng an toàn.

## Câu hỏi làm rõ nên cân nhắc

1. Approval tuần tự hay quorum?
2. Resubmit reset approvals nào?
3. Delegation có thời hạn và approval không?
4. Notification SLA là gì?
5. Retention/audit requirements nào?

## Gợi ý tư duy

### Gợi ý 1

Tách request state và approval assignment.

### Gợi ý 2

Role không đủ, phải kiểm actor theo stage/revision.

### Gợi ý 3

Xét concurrency, outbox và chi phí complexity.

## Cấu trúc trả lời đề xuất

1. Làm rõ invariants
2. Model request/step/decision
3. Chọn transaction boundary
4. Thiết kế authorization/retry
5. So sánh kiến trúc
6. Test/observe/rollout

## Ý chính của câu trả lời tốt

### Bắt buộc

Server-side transition validation, actor assignment/delegation, optimistic concurrency, append-only audit và revision.

### Điểm cộng

Outbox và idempotency, conflict response, notification backlog, additive migrations.

### Senior+

Cân nhắc revoke/delegation và policy changes, chỉ chọn workflow engine nếu branching thay đổi phức tạp.

## Hướng giải quyết tham khảo

Chọn Modular Monolith ASP.NET Core + PostgreSQL + React cho MVP, tách modules Requisition, Approval, Identity, Notification; chưa cần microservices. Model Requisition(Id, OwnerId, Status, Revision, Version), ApprovalStep(RequestId, Revision, StepOrder, AssignedPrincipal, State), ApprovalDecision(StepId, ActorId, ActingForId?, Action, Reason, At), AssignmentHistory và Outbox. Không giả định PostgreSQL có SQL Server rowversion: dùng integer version với conditional update hoặc concurrency token phù hợp.

State machine Draft → PendingLM → PendingSuperior → PendingHR → Approved; Request Changes → NeedsChanges → revision mới khi resubmit. Server kiểm stage, revision, tenant, actor được assign/delegate còn hiệu lực, conflict và policy self-approval. Trong một DB transaction: update request/step, append decision/audit và insert outbox. Unique constraints và idempotency key ngăn double transition; race approve/reject chỉ một commit thắng. Admin reassignment có reason và audit old/new principal. Notification worker gửi từ outbox, retry có backoff, DLQ/manual repair nếu cần; không cam kết email exactly-once do provider acknowledgment ambiguity. Nếu tải/SLA cần, có thể thêm Azure Service Bus, không bắt buộc cho MVP.

Test unit state machine, integration concurrent approve/reject, security delegation expiry, duplicate submission, failure injection email, Playwright E2E resubmit. Observe pending age, transition conflicts, outbox lag, delivery errors, audit completeness. Deploy additive migrations, feature flag, pilot nhỏ và rollback không mất audit. Trade-off: monolith đơn giản vận hành nhưng phải giữ boundaries; outbox thêm worker nhưng tránh dual-write; workflow engine chỉ đáng đầu tư khi rules động/phân nhánh nhiều.

## Mẫu trả lời trong phỏng vấn

Tôi làm rõ các transition và delegation trước. Với MVP và tải hiện tại, tôi ưu tiên Modular Monolith, không mặc định microservices. Mỗi request có revision; mỗi step có assignment; quyết định lưu audit append-only. API xác thực người duyệt theo assignment hiện tại và trạng thái, dùng optimistic concurrency để chặn hai action đồng thời. Ghi outbox cùng transaction, gửi notification bất đồng bộ để email outage không làm mất approval. Tôi kiểm thử security, concurrency, retry và pilot có telemetry trước rollout rộng.

## Câu hỏi đào sâu

1. Admin đổi Superior sau khi HR đã duyệt thì sao?
2. Khi có 20 workflow dynamic, có cần engine không?
3. Email gửi trùng có thể gây approve trùng không?

## Lỗi trả lời thường gặp

- Chọn microservices trước khi rõ invariants
- Chỉ kiểm role HR mà không kiểm assignment
- Gửi email trong DB transaction
- Ghi đè audit khi resubmit
- Không test concurrent approve/reject
