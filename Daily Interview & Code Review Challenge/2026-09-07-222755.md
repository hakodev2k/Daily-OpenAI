# Code Review Challenge 1 — API multi-tenant tin nhầm JWT claims và cho phép đọc/sửa dữ liệu tenant khác

**Chủ đề:** C#/.NET, ASP.NET Core, Authentication vs Authorization, JWT claims, Microsoft Entra ID concepts, policy-based authorization, multi-tenant isolation, EF Core, sensitive logging, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 11–14 vấn đề

## Bối cảnh

Một enterprise management portal chạy ASP.NET Core .NET 8 trên Azure App Service. Frontend dùng React và gọi REST API bằng bearer token do identity provider phát hành.

Hệ thống phục vụ nhiều tenant. Một user bình thường chỉ được đọc và sửa dữ liệu thuộc tenant của mình. Một nhóm support nội bộ có thể truy cập tenant khác nhưng chỉ khi có role phù hợp và mọi cross-tenant access phải được audit.

API hiện xử lý customer profiles. Production/security review ghi nhận:

- một user ở tenant A có thể thay `tenantId` trên URL và đôi lúc đọc được customer của tenant B;
- endpoint update chỉ có `[Authorize]`, không có resource-level authorization;
- code đọc claim `tenant_id` và `role` trực tiếp mà không centralize validation;
- một số access token có nhiều role claims;
- support role được check bằng string search;
- API log toàn bộ `Authorization` header khi debug authentication failures;
- query `GetCustomer` tìm theo `customerId` trước, rồi mới so tenant trong application code;
- update endpoint attach entity từ request DTO và đánh dấu toàn bộ entity modified;
- team đề xuất “ẩn tenantId khỏi URL” như fix chính;
- hệ thống chạy nhiều App Service instances nên không thể dựa vào per-instance session state để giữ tenant context;
- penetration test phát hiện một token hợp lệ nhưng thiếu claim mong đợi dẫn tới fallback tenant mặc định;
- Product yêu cầu cross-tenant support access phải có reason/ticket ID để phục vụ audit.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/customers")]
[Authorize]
public sealed class CustomersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<CustomersController> _logger;

    public CustomersController(
        AppDbContext db,
        ILogger<CustomersController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{customerId:guid}")]
    public async Task<IActionResult> GetCustomer(
        Guid tenantId,
        Guid customerId,
        CancellationToken cancellationToken)
    {
        var tokenTenant = User.FindFirst("tenant_id")?.Value;
        var roles = string.Join(",", User.FindAll("role").Select(x => x.Value));

        var isSupport = roles.Contains("Support", StringComparison.OrdinalIgnoreCase);

        if (tokenTenant == null)
        {
            tokenTenant = "00000000-0000-0000-0000-000000000001";
        }

        _logger.LogInformation(
            "Authorization={Authorization}; tenant={TenantId}; customer={CustomerId}; tokenTenant={TokenTenant}; roles={Roles}",
            Request.Headers.Authorization.ToString(),
            tenantId,
            customerId,
            tokenTenant,
            roles);

        var customer = await _db.Customers
            .SingleOrDefaultAsync(
                x => x.Id == customerId,
                cancellationToken);

        if (customer == null)
        {
            return NotFound();
        }

        if (!isSupport && customer.TenantId.ToString() != tokenTenant)
        {
            return Forbid();
        }

        return Ok(customer);
    }

    [HttpPut("{customerId:guid}")]
    public async Task<IActionResult> UpdateCustomer(
        Guid tenantId,
        Guid customerId,
        CustomerDto dto,
        CancellationToken cancellationToken)
    {
        var entity = new Customer
        {
            Id = customerId,
            TenantId = tenantId,
            Name = dto.Name,
            Email = dto.Email,
            CreditLimit = dto.CreditLimit,
            IsVip = dto.IsVip
        };

        _db.Attach(entity);
        _db.Entry(entity).State = EntityState.Modified;

        await _db.SaveChangesAsync(cancellationToken);

        return NoContent();
    }
}
```

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### Critical — Update endpoint không thực hiện tenant/resource authorization

**Vấn đề:**  
`UpdateCustomer` chỉ dựa vào `[Authorize]` ở controller và lấy `tenantId` trực tiếp từ route để gán vào entity.

**Tại sao xảy ra:**  
Authentication bị dùng như authorization. Không có bước chứng minh caller được phép sửa `customerId` trong `tenantId` đó.

**Ảnh hưởng production:**  
Một authenticated user có thể thay route tenant/customer ID và cố cập nhật dữ liệu ngoài phạm vi quyền của mình. Nếu record tồn tại và EF update thành công, đây là broken object-level authorization.

**Cách sửa:**  
Resolve caller tenant/permissions từ trusted authorization context, sau đó query resource với tenant scope ngay trong predicate. Với support cross-tenant access, yêu cầu explicit policy + validated support role + audit reason/ticket context. Không dùng route tenant như bằng chứng quyền sở hữu.

---

### Critical — Full entity attach + `Modified` tạo overposting/mass-assignment risk

**Vấn đề:**  
Endpoint tạo entity mới từ DTO rồi đánh dấu toàn bộ entity modified, bao gồm các field nhạy cảm như `CreditLimit`, `IsVip`, `TenantId`.

**Tại sao xảy ra:**  
Data-binding contract bị coi như business authorization contract.

**Ảnh hưởng production:**  
Client có thể thay đổi field mà role hiện tại không được phép sửa. Ngoài ra, các property không có trong DTO nhưng tồn tại trên entity có thể bị overwrite tùy mapping/defaults.

**Cách sửa:**  
Load entity đã được tenant-scoped authorization, sau đó update explicit allowed fields. Với field nhạy cảm, áp dụng policy/business permission riêng. DTO nên phản ánh command semantics thay vì mirror toàn bộ entity.

---

### Critical — Fallback tenant khi claim thiếu là fail-open

**Vấn đề:**  
Nếu token không có `tenant_id`, code gán một tenant mặc định có thật.

**Tại sao xảy ra:**  
Missing security context được biến thành một identity hợp lệ thay vì bị reject.

**Ảnh hưởng production:**  
Token thiếu/sai claim có thể truy cập nhầm tenant mặc định nếu các điều kiện khác phù hợp.

**Cách sửa:**  
Fail closed. Nếu tenant claim là bắt buộc cho loại principal đó, trả 403/401 theo authentication design phù hợp. Nếu support principal không có tenant cố định, route qua một authorization path riêng thay vì dùng fallback tenant.

---

### High — Role authorization dùng substring matching

**Vấn đề:**  
`roles.Contains("Support")` chạy trên string đã join nhiều claims.

**Tại sao xảy ra:**  
Role membership bị thay bằng substring search.

**Ảnh hưởng production:**  
Role như `CustomerSupportViewer`, `NotSupport`, hoặc format claim bất ngờ có thể match sai. Khi có nhiều role claims, behavior còn khó audit hơn.

**Cách sửa:**  
Dùng exact claim/role semantics thông qua policy-based authorization, `User.IsInRole` khi role mapping đã cấu hình đúng, hoặc requirement handler kiểm tra exact allowed values.

---

### High — Query không tenant-scope tại database boundary

**Vấn đề:**  
`GetCustomer` query bằng `customerId` trước, rồi mới kiểm tra tenant sau khi entity đã materialize.

**Tại sao xảy ra:**  
Authorization được đặt sau data retrieval thay vì được encode vào query predicate.

**Ảnh hưởng production:**  
Tăng nguy cơ data leakage qua logging/debugging hoặc future refactor bỏ quên check. Với unique IDs, code vẫn có thể xác nhận resource tồn tại ngoài tenant bằng timing/status differences.

**Cách sửa:**  
Với user tenant-bound, query theo cả `Id` và `TenantId`. Với support flow, dùng branch rõ ràng được policy authorize trước rồi query theo resource ID/tenant yêu cầu. Authorization boundary phải rõ và testable.

---

### High — Support cross-tenant access không có explicit policy và audit context

**Vấn đề:**  
Chỉ cần substring role chứa `Support` là bỏ qua tenant ownership check.

**Tại sao xảy ra:**  
Privileged path không được mô hình hóa thành application capability riêng.

**Ảnh hưởng production:**  
Không có least privilege, không có reason/ticket requirement, khó chứng minh ai đã truy cập tenant nào và vì sao.

**Cách sửa:**  
Tạo policy như `CrossTenantCustomerAccess` với authorization handler kiểm tra exact support role/claim và requirement bổ sung. Yêu cầu support request chứa ticket/reason hợp lệ và ghi audit event structured, không chứa secret/token.

---

### High — Sensitive token bị log

**Vấn đề:**  
Toàn bộ `Authorization` header được ghi vào application log.

**Tại sao xảy ra:**  
Debugging authentication được thực hiện bằng cách log credential.

**Ảnh hưởng production:**  
Bearer token có thể xuất hiện trong Application Insights/Kibana, mở rộng blast radius sang bất kỳ ai có quyền đọc logs.

**Cách sửa:**  
Không log bearer token. Log token validation outcome, issuer/audience identifiers an toàn, subject/object ID đã pseudonymize nếu cần, tenant-safe identifier, authorization policy và denial reason code. Áp dụng log redaction.

---

### High — `tenantId` từ route được dùng như trusted security input

**Vấn đề:**  
Client tự chọn tenant trong URL và update path dùng giá trị này để persist.

**Tại sao xảy ra:**  
Routing input bị nhầm với principal context.

**Ảnh hưởng production:**  
IDOR/broken object-level authorization nếu thiếu check ở bất kỳ endpoint nào.

**Cách sửa:**  
Route tenant có thể giữ lại để làm resource locator/API ergonomics, nhưng phải được so với trusted tenant context hoặc được policy authorize cho cross-tenant access. Không có URL design nào thay thế authorization.

---

### Medium — String conversion của tenant claim thiếu normalization/validation rõ ràng

**Vấn đề:**  
So sánh `customer.TenantId.ToString()` với raw claim string.

**Tại sao xảy ra:**  
Security identifier được giữ ở dạng string tùy format.

**Ảnh hưởng production:**  
Format/casing/claim mapping khác nhau có thể gây denial sai hoặc tạo fallback logic nguy hiểm về sau.

**Cách sửa:**  
Parse claim thành typed identifier một lần trong current-principal abstraction. Nếu parse fail, reject principal/context thay vì “best effort”.

---

### Medium — API trả entity trực tiếp

**Vấn đề:**  
`return Ok(customer)` serialize database entity.

**Tại sao xảy ra:**  
Persistence model bị dùng như response contract.

**Ảnh hưởng production:**  
Future entity fields có thể vô tình được expose. Có thể tạo coupling và over-fetch.

**Cách sửa:**  
Projection sang response DTO chỉ gồm fields caller được phép xem.

---

### Medium — Thiếu audit/authorization telemetry có cấu trúc

**Vấn đề:**  
Log hiện tại chứa token nhưng lại thiếu policy outcome, support reason, resource tenant, caller category và denial code.

**Tại sao xảy ra:**  
Telemetry tập trung vào raw input thay vì security decision.

**Ảnh hưởng production:**  
Khó điều tra cross-tenant incident và khó tạo alert cho privileged access bất thường.

**Cách sửa:**  
Ghi structured security audit cho cross-tenant access: actor ID an toàn, actor type, requested tenant, resource ID, policy, ticket/reason, outcome, trace ID, timestamp. Không log credential hoặc sensitive customer fields.

## Phiên bản đề xuất

Ví dụ dưới đây giả định:

- user thường có tenant ID bắt buộc;
- support user có policy riêng;
- route vẫn chứa tenant ID nhưng không được tin như authorization source;
- customer update chỉ cho phép sửa name/email ở endpoint này.

```csharp
public interface ICurrentPrincipal
{
    Guid? TenantId { get; }
    string SubjectId { get; }
    bool IsSupport { get; }
}

[ApiController]
[Route("api/tenants/{tenantId:guid}/customers")]
[Authorize]
public sealed class CustomersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ICurrentPrincipal _principal;
    private readonly IAuthorizationService _authorization;
    private readonly ISecurityAuditWriter _audit;

    public CustomersController(
        AppDbContext db,
        ICurrentPrincipal principal,
        IAuthorizationService authorization,
        ISecurityAuditWriter audit)
    {
        _db = db;
        _principal = principal;
        _authorization = authorization;
        _audit = audit;
    }

    [HttpGet("{customerId:guid}")]
    public async Task<IActionResult> GetCustomer(
        Guid tenantId,
        Guid customerId,
        [FromHeader(Name = "X-Support-Ticket")] string? supportTicket,
        CancellationToken cancellationToken)
    {
        var ownTenant = _principal.TenantId;
        var crossTenant = ownTenant != tenantId;

        if (crossTenant)
        {
            var auth = await _authorization.AuthorizeAsync(
                User,
                new CrossTenantAccessResource(
                    tenantId,
                    customerId,
                    supportTicket),
                "CrossTenantCustomerAccess");

            if (!auth.Succeeded)
            {
                return Forbid();
            }
        }
        else if (ownTenant is null)
        {
            return Forbid();
        }

        var customer = await _db.Customers
            .AsNoTracking()
            .Where(x => x.Id == customerId && x.TenantId == tenantId)
            .Select(x => new CustomerResponse(
                x.Id,
                x.Name,
                x.Email))
            .SingleOrDefaultAsync(cancellationToken);

        if (customer is null)
        {
            return NotFound();
        }

        if (crossTenant)
        {
            await _audit.WriteAsync(
                new SecurityAuditEvent(
                    _principal.SubjectId,
                    "CrossTenantCustomerRead",
                    tenantId,
                    customerId,
                    supportTicket!),
                cancellationToken);
        }

        return Ok(customer);
    }

    [HttpPut("{customerId:guid}")]
    public async Task<IActionResult> UpdateCustomer(
        Guid tenantId,
        Guid customerId,
        UpdateCustomerRequest request,
        CancellationToken cancellationToken)
    {
        if (_principal.TenantId != tenantId)
        {
            return Forbid();
        }

        var customer = await _db.Customers
            .SingleOrDefaultAsync(
                x => x.Id == customerId && x.TenantId == tenantId,
                cancellationToken);

        if (customer is null)
        {
            return NotFound();
        }

        customer.Name = request.Name.Trim();
        customer.Email = request.Email.Trim();

        await _db.SaveChangesAsync(cancellationToken);

        return NoContent();
    }
}

public sealed record UpdateCustomerRequest(
    string Name,
    string Email);

public sealed record CustomerResponse(
    Guid Id,
    string Name,
    string Email);
```

Một current-principal implementation nên parse claims một lần và fail-closed:

```csharp
public sealed class HttpCurrentPrincipal : ICurrentPrincipal
{
    public Guid? TenantId { get; }
    public string SubjectId { get; }
    public bool IsSupport { get; }

    public HttpCurrentPrincipal(IHttpContextAccessor accessor)
    {
        var user = accessor.HttpContext?.User
            ?? throw new InvalidOperationException("No current principal.");

        SubjectId = user.FindFirst("sub")?.Value
            ?? throw new SecurityException("Missing subject claim.");

        var tenantClaim = user.FindFirst("tenant_id")?.Value;

        if (tenantClaim is not null)
        {
            if (!Guid.TryParse(tenantClaim, out var tenantId))
            {
                throw new SecurityException("Invalid tenant claim.");
            }

            TenantId = tenantId;
        }

        IsSupport = user.Claims.Any(
            x => x.Type == "role" &&
                 x.Value == "SupportAgent");
    }
}
```

Nếu identity provider hoặc token schema khác nhau giữa user và service principal, abstraction nên model rõ từng principal type thay vì nhét mọi trường hợp vào một fallback generic.

## Giải thích thiết kế sau khi sửa

### 1. Authorization được đặt gần resource boundary

Một user không được quyền truy cập customer chỉ vì token hợp lệ. Quyền được đánh giá dựa trên tenant ownership hoặc explicit cross-tenant policy.

### 2. Data query cũng encode tenant isolation

Tenant ID không chỉ được check sau khi materialize entity. Predicate database chứa cả resource ID và tenant ID.

### 3. Fail closed khi security context thiếu/sai

Không có tenant fallback. Claim thiếu hoặc invalid phải dẫn tới denial hoặc principal path riêng.

### 4. DTO và command semantics giới hạn field update

Endpoint chỉ update fields mà operation này cho phép. Field nhạy cảm phải có endpoint/policy riêng nếu cần.

### 5. Privileged support access là một capability có audit

Cross-tenant support access cần exact policy, business reason/ticket và security audit event.

## Trade-offs

- Resource authorization handler tăng code và test surface nhưng làm policy rõ, tái sử dụng được.
- Tenant-scoped queries có thể cần composite indexes phù hợp với query patterns, ví dụ `(TenantId, Id)` hoặc index theo schema thực tế.
- Trả 404 thay vì 403 cho một số unauthorized resource có thể giảm resource enumeration nhưng cần thống nhất API semantics và audit nội bộ.
- Audit cross-tenant access tăng storage/operational cost nhưng là yêu cầu hợp lý nếu privileged access có compliance impact.
- Một global query filter có thể giảm nguy cơ quên tenant predicate, nhưng cũng có thể che logic và gây bypass bất ngờ nếu dùng `IgnoreQueryFilters`; không nên xem nó là lớp bảo vệ duy nhất.

## Cách kiểm thử

1. **Authorization integration test:** user tenant A không thể GET/PUT customer tenant B dù biết đúng `customerId`.
2. **Support-policy test:** support role đúng nhưng thiếu ticket/reason phải bị deny nếu đó là requirement; support hợp lệ phải tạo audit event.
3. **Claim-validation test:** token thiếu hoặc có `tenant_id` không parse được phải fail closed, không fallback.
4. **Overposting test:** request cố gửi `CreditLimit`, `IsVip`, `TenantId` không được làm thay đổi các fields này qua endpoint update thông thường.
5. **Sensitive-logging test:** logs/traces không chứa bearer token hoặc raw `Authorization` header.

## Quan sát trong production

Theo dõi:

- authorization denial rate theo policy/endpoint;
- cross-tenant access count theo actor type;
- privileged access thiếu/invalid support ticket;
- 401 vs 403 vs 404 distribution;
- suspicious repeated access tới nhiều tenant/resource IDs;
- token validation failures theo reason category nhưng không log token;
- database query duration cho tenant-scoped lookups;
- trace correlation giữa request, authorization decision và security audit event;
- alert khi privileged cross-tenant access tăng bất thường hoặc xuất hiện ngoài expected support workflows.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn dùng global query filter cho multi-tenancy và khi nào không nên dựa hoàn toàn vào nó?
2. Nếu support cần quyền read-only cross-tenant nhưng tuyệt đối không được update, bạn sẽ model policy/resource handlers như thế nào?
3. Nếu service-to-service token không có `tenant_id`, bạn sẽ phân biệt machine principal với end-user principal ra sao mà không tạo fallback nguy hiểm?

# Code Review Challenge 2 — SQL pagination càng về cuối càng chậm, query plan bất ổn và API làm database quá tải

**Chủ đề:** SQL Server, query optimization, composite indexes, execution plans, pagination, keyset pagination, parameter sensitivity, blocking, API performance, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ màn hình transaction history cho enterprise portal. Database là SQL Server.

Bảng `Transactions` hiện có khoảng 180 triệu rows và tăng khoảng 3–5 triệu rows mỗi tháng.

UI cho phép:

- lọc theo `tenantId`;
- optional filter theo `status`;
- optional search theo `reference`;
- chọn khoảng thời gian;
- sort mặc định `CreatedUtc DESC`;
- page size 50;
- user có thể nhảy tới page bất kỳ;
- support đôi khi export dữ liệu nhưng đây là flow riêng.

Production ghi nhận:

- page 1 thường dưới 200 ms nhưng page 2000 có thể mất 8–20 giây;
- CPU SQL Server tăng cao trong giờ peak;
- logical reads tăng mạnh khi page number lớn;
- query có lúc dùng index seek, lúc scan;
- khi `status` null thì plan khác đáng kể so với khi có status;
- filter `reference` dùng `%term%` làm query chậm mạnh;
- một số request bị timeout nhưng SQL query vẫn chạy thêm một lúc;
- API cho phép `pageSize=5000` nếu client tự chỉnh request;
- một index mới được thêm riêng trên `CreatedUtc` nhưng improvement rất ít;
- team đề xuất thêm Redis cache cho mọi trang kết quả.

Stored procedure hiện tại:

## Đoạn code cần review

```sql
CREATE OR ALTER PROCEDURE dbo.GetTransactions
    @TenantId uniqueidentifier,
    @Status nvarchar(50) = NULL,
    @Reference nvarchar(100) = NULL,
    @FromUtc datetime2 = NULL,
    @ToUtc datetime2 = NULL,
    @PageNumber int = 1,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        t.Id,
        t.TenantId,
        t.Reference,
        t.Status,
        t.Amount,
        t.CreatedUtc,
        t.PayloadJson
    FROM dbo.Transactions t
    WHERE
        t.TenantId = @TenantId
        AND (@Status IS NULL OR t.Status = @Status)
        AND (@Reference IS NULL OR t.Reference LIKE '%' + @Reference + '%')
        AND (@FromUtc IS NULL OR t.CreatedUtc >= @FromUtc)
        AND (@ToUtc IS NULL OR t.CreatedUtc <= @ToUtc)
    ORDER BY t.CreatedUtc DESC
    OFFSET (@PageNumber - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
```

## Kết quả code review tham khảo

### High — Deep OFFSET pagination có chi phí tăng theo vị trí trang

**Vấn đề:**  
`OFFSET (@PageNumber - 1) * @PageSize` buộc engine phải tìm/order rồi bỏ qua số lượng rows ngày càng lớn trước khi trả page nhỏ cuối cùng.

**Tại sao xảy ra:**  
Offset pagination định vị theo số lượng row bị bỏ qua, không theo key của row cuối trang trước.

**Ảnh hưởng production:**  
Page đầu nhanh nhưng page sâu tạo nhiều reads/CPU hơn, giữ resource lâu hơn và làm tail latency tăng mạnh dưới concurrency.

**Cách sửa:**  
Nếu UX chủ yếu Next/Previous hoặc infinite scroll, dùng keyset/seek pagination dựa trên stable sort key, ví dụ `(CreatedUtc, Id)`.

---

### High — Index không align với tenant-first query pattern

**Vấn đề:**  
Index hiện tại chỉ có `CreatedUtc DESC`, trong khi mọi query business đều filter chính xác theo `TenantId` trước.

**Tại sao xảy ra:**  
Index được thiết kế theo `ORDER BY` nhưng bỏ qua highly selective equality predicate và multi-tenant access pattern.

**Ảnh hưởng production:**  
SQL Server có thể phải scan/range nhiều rows của các tenant khác trước khi lọc, đặc biệt khi table rất lớn.

**Cách sửa:**  
Đánh giá index bắt đầu bằng `TenantId`, sau đó sort keys, ví dụ:

```sql
CREATE INDEX IX_Transactions_Tenant_Created_Id
ON dbo.Transactions (
    TenantId,
    CreatedUtc DESC,
    Id DESC)
INCLUDE (
    Reference,
    Status,
    Amount);
```

Đây chỉ là baseline. Nếu `Status` là filter phổ biến và selective, có thể cần alternative index/query strategy. Phải xác minh bằng workload và actual plans, không tạo index theo checklist.

---

### High — Sort không deterministic nếu nhiều rows có cùng `CreatedUtc`

**Vấn đề:**  
`ORDER BY CreatedUtc DESC` không có tie-breaker.

**Tại sao xảy ra:**  
Nhiều transactions có thể cùng timestamp.

**Ảnh hưởng production:**  
Rows có thể nhảy giữa pages hoặc xuất hiện duplicate/missing khi dữ liệu mới được insert giữa các page requests.

**Cách sửa:**  
Dùng deterministic order như `ORDER BY CreatedUtc DESC, Id DESC` và keyset cursor chứa cả hai values.

---

### High — Optional predicates có thể tạo plan không ổn định

**Vấn đề:**  
Pattern `(@Status IS NULL OR t.Status = @Status)` và tương tự cho dates/reference gom nhiều query shapes rất khác nhau vào một statement.

**Tại sao xảy ra:**  
Cardinality phụ thuộc mạnh vào parameter combination. Một plan phù hợp cho tenant nhỏ/status selective có thể kém cho tenant lớn/status null.

**Ảnh hưởng production:**  
Latency biến động, scans/reads tăng, có hiện tượng “lúc nhanh lúc chậm”.

**Cách sửa:**  
Đầu tiên xác minh actual plans và parameter distributions. Tùy workload có thể dùng dynamic SQL parameterized để chỉ đưa predicates thực sự có mặt, hoặc các procedure/query shapes riêng cho các cases quan trọng. `OPTION (RECOMPILE)` có thể hữu ích trong một số workload nhưng tăng compile cost; không nên dùng mặc định.

---

### High — `%term%` search không phù hợp B-tree search thông thường

**Vấn đề:**  
`Reference LIKE '%' + @Reference + '%'` yêu cầu substring search.

**Tại sao xảy ra:**  
Leading wildcard làm mất khả năng seek theo prefix trong index B-tree thông thường.

**Ảnh hưởng production:**  
Search theo reference có thể scan rất nhiều rows trong tenant/date range.

**Cách sửa:**  
Làm rõ semantics. Nếu reference search thực tế là exact hoặc prefix, chuyển sang `=` hoặc `LIKE @Reference + '%'` và index phù hợp. Nếu business thật sự cần arbitrary substring/full-text-like behavior, đánh giá full-text/search engine hoặc normalized lookup strategy dựa trên requirement, không ép B-tree làm việc nó không tối ưu.

---

### High — Over-fetch `PayloadJson` trên list endpoint

**Vấn đề:**  
Procedure select `PayloadJson` cho mọi row dù list UI có thể không cần.

**Tại sao xảy ra:**  
Persistence shape bị dùng nguyên làm list projection.

**Ảnh hưởng production:**  
Tăng page reads, memory grant/network payload, serialization cost và API latency. Nếu JSON lớn, impact đáng kể dưới load.

**Cách sửa:**  
Projection chỉ fields cần cho list. Detail endpoint tải payload riêng khi user mở transaction.

---

### High — Không giới hạn `pageSize`, `pageNumber` và date range

**Vấn đề:**  
Client có thể gửi page size rất lớn hoặc range nhiều năm.

**Tại sao xảy ra:**  
API contract không có guardrails theo workload.

**Ảnh hưởng production:**  
Một request hợp lệ về cú pháp có thể trở thành expensive query/DoS vector.

**Cách sửa:**  
Validate page size bounded, page number > 0, date range hợp lý theo use case. Export khối lượng lớn nên là flow riêng với asynchronous processing nếu cần.

---

### Medium — Cancellation không phải guarantee rằng SQL work dừng ngay lập tức

**Vấn đề:**  
API truyền `CancellationToken`, nhưng team có thể giả định client disconnect sẽ lập tức giải phóng database resource.

**Tại sao xảy ra:**  
Cancellation là cooperative. Provider/command phải gửi cancel và server phải xử lý; query có thể mất thời gian để kết thúc cleanup.

**Ảnh hưởng production:**  
Timeout/cancel bursts vẫn có thể tạo database load tồn dư.

**Cách sửa:**  
Giữ cancellation propagation, đặt command timeout phù hợp, nhưng quan trọng hơn là làm query bounded/efficient. Theo dõi canceled/timeout queries ở app và database side.

---

### Medium — Random page navigation và keyset pagination có trade-off UX

**Vấn đề:**  
Keyset không hỗ trợ “nhảy trực tiếp page 2000” theo cách offset làm.

**Tại sao xảy ra:**  
Seek pagination định vị theo cursor, không theo ordinal page.

**Ảnh hưởng production:**  
Nếu Product thật sự cần random access, không thể chỉ thay API mà bỏ requirement.

**Cách sửa:**  
Làm rõ user behavior. Nếu random page hiếm, UI có thể dùng search/date filters + Next/Previous. Nếu random page bắt buộc, cân nhắc bounded offset trong partition nhỏ, precomputed anchors, separate reporting path, hoặc chấp nhận cost có đo lường. Không có một pagination strategy tốt nhất cho mọi UX.

---

### Medium — Redis cache không xử lý root cause chung

**Vấn đề:**  
Team muốn cache mọi page.

**Tại sao xảy ra:**  
Cache được dùng để che query shape tốn kém.

**Ảnh hưởng production:**  
High-cardinality combinations của tenant/status/reference/date/page tạo hit ratio thấp; invalidation transaction history phức tạp; stale data có thể không phù hợp.

**Cách sửa:**  
Đo query và fix data access/index/pagination trước. Chỉ cache nếu workload có reuse đủ cao, freshness requirement cho phép và cache outage behavior đã rõ.

## Phiên bản đề xuất

Nếu UX cho phép cursor pagination, API có thể dùng cursor `(CreatedUtc, Id)`:

```sql
CREATE OR ALTER PROCEDURE dbo.GetTransactionsPage
    @TenantId uniqueidentifier,
    @Status nvarchar(50) = NULL,
    @FromUtc datetime2 = NULL,
    @ToUtc datetime2 = NULL,
    @AfterCreatedUtc datetime2 = NULL,
    @AfterId uniqueidentifier = NULL,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 200
        THROW 50001, 'Invalid page size.', 1;

    SELECT TOP (@PageSize)
        t.Id,
        t.Reference,
        t.Status,
        t.Amount,
        t.CreatedUtc
    FROM dbo.Transactions t
    WHERE
        t.TenantId = @TenantId
        AND (@Status IS NULL OR t.Status = @Status)
        AND (@FromUtc IS NULL OR t.CreatedUtc >= @FromUtc)
        AND (@ToUtc IS NULL OR t.CreatedUtc <= @ToUtc)
        AND (
            @AfterCreatedUtc IS NULL
            OR t.CreatedUtc < @AfterCreatedUtc
            OR (
                t.CreatedUtc = @AfterCreatedUtc
                AND t.Id < @AfterId
            )
        )
    ORDER BY
        t.CreatedUtc DESC,
        t.Id DESC;
END
```

Index baseline:

```sql

ON dbo.Transactions (
    TenantId,
    CreatedUtc DESC,
    Id DESC)
INCLUDE (
    Reference,
    Status,
    Amount);
```

## Giải thích thiết kế sau khi sửa

### 1. Pagination dựa trên stable key thay vì số rows phải bỏ qua

Keyset pagination giữ cost ổn định hơn khi user đi sâu, miễn index align với sort/filter.

### 2. Index phản ánh access pattern

`TenantId` là equality boundary chính, sau đó là deterministic sort keys.

### 3. Projection giảm I/O

List endpoint không tải `PayloadJson` nếu không cần.

### 4. API có workload guardrails

Page size/date range được giới hạn để một request không chiếm quá nhiều database resource.

### 5. Search semantics được làm rõ trước khi chọn công nghệ

Exact/prefix/substring là ba requirements khác nhau và dẫn đến query/index architecture khác nhau.

## Trade-offs

- Keyset pagination khó hỗ trợ random page numbers và tổng số trang chính xác theo thời gian thực.
- Composite covering index tăng storage và write amplification; cần kiểm tra write workload trước khi thêm INCLUDE columns.
- Dynamic SQL parameterized có thể cải thiện plan specificity nhưng tăng code/maintenance complexity.
- `OPTION (RECOMPILE)` giảm reuse plan cho statement đó và tăng CPU compile; chỉ dùng khi measurement chứng minh phù hợp.
- Full-text/search engine thêm operational complexity; không nên dùng nếu prefix/exact search đã đáp ứng business requirement.
- Cursor phải được encode/validate an toàn và cần định nghĩa semantics khi dữ liệu thay đổi giữa các requests.

## Cách kiểm thử

1. **Database performance test:** so sánh logical reads, CPU, duration và actual plan giữa page 1/page 2000 của OFFSET và keyset trên data volume gần production.
2. **Correctness test:** nhiều rows cùng `CreatedUtc` không được duplicate/missing qua nhiều cursor pages.
3. **Load test:** nhiều tenants query đồng thời; đo p95/p99, SQL CPU, waits, connection pool và timeout rate.
4. **Query-shape test:** status null vs populated, date range nhỏ vs lớn, reference exact/prefix/substr để xác định plan behavior và index utility.
5. **Cancellation/timeout test:** client cancel/command timeout phải được observable; query không nên tiếp tục tiêu thụ resource bất thường lâu sau request lifecycle.

## Quan sát trong production

Theo dõi:

- request p50/p95/p99 theo endpoint/query shape;
- SQL duration, CPU time và logical reads;
- actual/estimated row gaps trong representative execution plans;
- top queries theo total CPU/reads;
- waits, blocking/deadlocks nếu có;
- command timeout/cancellation count;
- page depth hoặc cursor usage distribution;
- response row count và payload bytes;
- query count theo tenant size bucket;
- plan regressions sau deploy/index change;
- connection-pool saturation ở application;
- cache hit ratio chỉ nếu caching được áp dụng có chủ đích.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc hiển thị “Page 1 of 3,600,000” chính xác real-time, bạn sẽ đánh giá cost và alternatives thế nào?
2. Nếu một tenant chiếm 70% toàn bộ transactions, index/partitioning strategy có cần thay đổi không?
3. Khi nào `OPTION (RECOMPILE)`, dynamic SQL parameterized hoặc multiple stored procedures là lựa chọn hợp lý cho optional filters?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication chỉ chứng minh identity/token đã đáp ứng authentication scheme; resource authorization vẫn phải được đánh giá theo tenant, role/policy và business permission.
- Multi-tenant isolation nên được enforce ở cả authorization layer và data-query boundary, không dựa vào route/input hiding.
- Security context thiếu hoặc invalid phải fail closed; fallback tenant là anti-pattern nguy hiểm.
- Không log bearer token; observability nên ghi security decision, policy outcome và audit metadata an toàn.
- Deep OFFSET pagination có cost tăng theo page depth và cần được đánh giá bằng actual execution plans/logical reads.
- Index phải phản ánh access pattern thực tế, không chỉ một cột trong `ORDER BY`.
- Keyset pagination, deterministic ordering, bounded query inputs và projection là các công cụ mạnh để giữ interactive APIs ổn định ở data volume lớn.

## Mẫu tư duy cần nhớ

1. **Authenticate identity, then authorize the resource.** Hai bước này không thay thế nhau.
2. **Fail closed when security context is missing.** Không biến thiếu claim thành một giá trị mặc định có quyền.
3. **Push isolation predicates toward the data boundary.** Đừng fetch cross-tenant data rồi mới hy vọng check phía sau luôn đúng.
4. **Measure query cost before prescribing cache or indexes.** Dùng execution plan, logical reads, waits và p95/p99.
5. **Choose pagination from UX + data scale + consistency semantics.** Offset và keyset đều có trade-offs.
