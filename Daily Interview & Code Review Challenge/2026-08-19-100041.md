# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để xử lý các cấu hình offboarding đã hết hạn. Job có thể chạy trên nhiều worker instance. Mỗi record cần reset trạng thái trong database và gọi một external mail service. Gần đây production xuất hiện trường hợp cùng một mailbox được reset hai lần, một số record đã được đánh dấu hoàn thành nhưng external operation thất bại, và thỉnh thoảng job retry tạo thêm side effect. Yêu cầu nghiệp vụ là có thể retry an toàn và không được bỏ sót record.

## Đoạn code cần review

```csharp
public sealed class OffboardingResetJob
{
    private readonly AppDbContext _db;
    private readonly IMailboxService _mailboxService;
    private readonly ILogger<OffboardingResetJob> _logger;

    public OffboardingResetJob(
        AppDbContext db,
        IMailboxService mailboxService,
        ILogger<OffboardingResetJob> logger)
    {
        _db = db;
        _mailboxService = mailboxService;
        _logger = logger;
    }

    public async Task RunAsync()
    {
        var expired = await _db.OffboardingConfigs
            .Where(x => x.EndTime <= DateTime.UtcNow && !x.IsReset)
            .ToListAsync();

        foreach (var config in expired)
        {
            try
            {
                config.IsReset = true;
                config.ResetAt = DateTime.UtcNow;
                await _db.SaveChangesAsync();

                await _mailboxService.ResetAsync(config.UserEmail);

                _logger.LogInformation(
                    "Reset mailbox {Email} for config {ConfigId}",
                    config.UserEmail,
                    config.Id);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed to reset mailbox {Email}",
                    config.UserEmail);
            }
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Tìm rủi ro concurrency, retry và transaction.
3. Giải thích impact khi nhiều Hangfire worker chạy đồng thời.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation có thể retry an toàn.
6. Giải thích cách kiểm thử dưới concurrency/failure.
7. Đề xuất logs, traces và metrics cần theo dõi.

## Câu hỏi gợi mở

- Hai worker có thể cùng đọc một record `IsReset = false` không?
- Điều gì xảy ra nếu `SaveChangesAsync` thành công nhưng `ResetAsync` thất bại?
- Catch exception tại từng record ảnh hưởng thế nào tới retry semantics của Hangfire?
- Idempotency nên được đảm bảo ở database, job hay external operation?
- Nếu job xử lý hàng chục nghìn record thì query hiện tại có vấn đề gì?

## Gợi ý

### Gợi ý 1

Hãy xem thao tác “đọc record → đánh dấu → side effect bên ngoài” như một distributed workflow chứ không phải một transaction đơn giản.

### Gợi ý 2

Database transaction không thể tự làm external mailbox operation atomic; cần thiết kế state machine/idempotency và cơ chế claim công việc rõ ràng.

## Kết quả code review tham khảo

### 1. Đánh dấu hoàn thành trước khi external operation thành công

**Problem:** `IsReset = true` được commit trước `ResetAsync`.  
**Why:** database và external service không nằm trong cùng atomic transaction.  
**Impact:** external call fail nhưng record không được query lại; công việc có thể bị mất vĩnh viễn.  
**Severity:** Critical.  
**Recommended fix:** dùng trạng thái `Pending/Processing/Completed/Failed`, chỉ chuyển `Completed` sau khi external operation thành công; có recovery cho `Processing` quá hạn.

### 2. Race condition giữa nhiều worker

**Problem:** nhiều worker có thể cùng đọc record chưa reset.  
**Why:** query và claim không atomic, không có concurrency token/conditional update.  
**Impact:** side effect chạy nhiều lần.  
**Severity:** Critical.  
**Recommended fix:** claim record bằng atomic conditional update hoặc cơ chế locking phù hợp database; coi external call là at-least-once và yêu cầu idempotency.

### 3. Không có idempotency key cho external operation

**Problem:** retry sau timeout không biết request trước đã được áp dụng hay chưa.  
**Impact:** duplicate side effects.  
**Severity:** High.  
**Recommended fix:** nếu external API hỗ trợ, truyền operation/idempotency key ổn định; nếu không, thiết kế operation theo desired state và kiểm tra trạng thái trước/sau.

### 4. Nuốt exception làm Hangfire coi execution thành công

**Problem:** exception bị catch và không propagate.  
**Impact:** automatic retry ở cấp job có thể không xảy ra; failure dễ bị bỏ quên.  
**Severity:** High.  
**Recommended fix:** lưu failure state có chủ đích và/hoặc throw khi cần retry; phân loại transient/permanent errors.

### 5. Không truyền CancellationToken

**Problem:** DB/external calls không nhận cancellation.  
**Impact:** shutdown/deployment kéo dài và work tiếp tục ngoài lifecycle mong muốn.  
**Severity:** Medium.  
**Recommended fix:** truyền cancellation token phù hợp từ job abstraction nếu hỗ trợ.

### 6. Load toàn bộ expired records vào memory

**Problem:** `ToListAsync()` không giới hạn batch.  
**Impact:** memory pressure, transaction/work duration lớn khi backlog tăng.  
**Severity:** Medium.  
**Recommended fix:** xử lý theo batch có deterministic ordering.

### 7. Một DbContext tracking nhiều entity xuyên suốt batch

**Problem:** change tracker tích lũy khi batch lớn.  
**Impact:** memory và SaveChanges overhead tăng.  
**Severity:** Medium.  
**Recommended fix:** batch nhỏ/scoped context hoặc clear tracking sau batch phù hợp.

### 8. Logging email có thể là dữ liệu nhạy cảm

**Problem:** identifier cá nhân được ghi trực tiếp.  
**Impact:** tăng phạm vi dữ liệu nhạy cảm trong log.  
**Severity:** Low/Medium tùy policy.  
**Recommended fix:** log config/user identifier nội bộ hoặc masking theo chính sách.

## Phiên bản code đề xuất

```csharp
public sealed class OffboardingResetJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IMailboxService _mailbox;
    private readonly ILogger<OffboardingResetJob> _logger;

    public OffboardingResetJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IMailboxService mailbox,
        ILogger<OffboardingResetJob> logger)
    {
        _dbFactory = dbFactory;
        _mailbox = mailbox;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);
        var now = DateTime.UtcNow;

        var ids = await db.OffboardingConfigs
            .AsNoTracking()
            .Where(x => x.EndTime <= now && x.Status == ResetStatus.Pending)
            .OrderBy(x => x.Id)
            .Select(x => x.Id)
            .Take(100)
            .ToListAsync(ct);

        foreach (var id in ids)
        {
            ct.ThrowIfCancellationRequested();

            var claimed = await db.OffboardingConfigs
                .Where(x => x.Id == id && x.Status == ResetStatus.Pending)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, ResetStatus.Processing)
                    .SetProperty(x => x.ProcessingStartedAt, now), ct);

            if (claimed != 1)
                continue;

            try
            {
                var item = await db.OffboardingConfigs
                    .AsNoTracking()
                    .SingleAsync(x => x.Id == id, ct);

                await _mailbox.ResetAsync(
                    item.UserEmail,
                    operationId: $"offboarding-reset:{id}",
                    ct);

                await db.OffboardingConfigs
                    .Where(x => x.Id == id && x.Status == ResetStatus.Processing)
                    .ExecuteUpdateAsync(s => s
                        .SetProperty(x => x.Status, ResetStatus.Completed)
                        .SetProperty(x => x.ResetAt, DateTime.UtcNow), ct);
            }
            catch (Exception ex) when (!ct.IsCancellationRequested)
            {
                await db.OffboardingConfigs
                    .Where(x => x.Id == id)
                    .ExecuteUpdateAsync(s => s
                        .SetProperty(x => x.Status, ResetStatus.Failed), ct);

                _logger.LogError(ex, "Offboarding reset failed for {ConfigId}", id);
                throw;
            }
        }
    }
}
```

Đây là hướng thiết kế tham khảo. Việc dùng `ExecuteUpdateAsync` phụ thuộc phiên bản EF Core và provider; production implementation cần chính sách retry/recovery cho `Failed` và `Processing` bị orphan. Idempotency của external mailbox operation vẫn là yêu cầu quan trọng vì crash có thể xảy ra sau external success nhưng trước database update.

## Trade-offs

State machine làm schema và recovery phức tạp hơn nhưng thể hiện rõ workflow. Distributed lock có thể giảm duplicate execution nhưng không loại bỏ uncertainty giữa external side effect và DB commit. Nếu external operation thực chất là “set desired state” và tự idempotent, implementation có thể đơn giản hơn đáng kể. Với throughput rất lớn, có thể chuyển sang queue/outbox, nhưng không cần phân tán hệ thống chỉ để giải quyết workload nhỏ.

## Cách kiểm thử

1. **Concurrency test:** chạy 10 worker cùng claim một record, xác nhận chỉ một worker thắng conditional update.
2. **Failure-path:** external service fail trước khi side effect; record phải retry được.
3. **Ambiguous timeout:** external service thực hiện thành công nhưng client timeout; retry không tạo side effect sai.
4. **Crash recovery:** process chết sau khi chuyển `Processing`; recovery đưa record quá hạn về trạng thái retry hợp lệ.
5. **Load test:** backlog lớn được xử lý theo batch mà memory/DB latency ổn định.

## Quan sát trong production

Theo dõi số lượng record theo từng status, tuổi của record `Processing`, retry count, failure rate theo error category, external-call latency, batch duration và throughput. Trace nên liên kết `ConfigId`, operation ID và external request. Alert khi `Processing` vượt SLA hoặc `Failed` tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Outbox pattern giúp gì và không giúp gì trong trường hợp external API không tham gia transaction?
2. Nếu `ResetAsync` không hỗ trợ idempotency key, bạn thiết kế retry thế nào?
3. Bạn có dùng `[DisableConcurrentExecution]` rồi bỏ database claim không? Vì sao có hoặc không?

# Code Review Challenge 2 — API tìm kiếm người dùng: authorization và SQL injection

**Chủ đề:** Authentication/authorization, input validation, SQL correctness, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một internal ASP.NET Core API cho phép support staff tìm employee theo tên/email và tenant. Endpoint truy cập PostgreSQL qua EF Core. Sau một đợt pentest, đội security cảnh báo endpoint có khả năng vượt tenant boundary và log chứa dữ liệu không nên xuất hiện. API nhận vài chục request/giây nhưng có thể bị burst khi support chạy bulk investigation.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/users")]
public sealed class UsersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<UsersController> _logger;

    public UsersController(AppDbContext db, ILogger<UsersController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        string tenantId,
        string query,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "User {User} searches tenant {Tenant} for {Query}",
            User.Identity?.Name,
            tenantId,
            query);

        var sql = $@"
            SELECT *
            FROM users
            WHERE tenant_id = '{tenantId}'
              AND (email ILIKE '%{query}%'
                   OR display_name ILIKE '%{query}%')
            ORDER BY created_at DESC";

        var users = await _db.Users
            .FromSqlRaw(sql)
            .ToListAsync(cancellationToken);

        return Ok(users);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/security issues.
2. Phân tích authorization boundary và injection risk.
3. Giải thích production impact.
4. Ưu tiên vấn đề.
5. Đề xuất implementation an toàn hơn.
6. Nêu security/integration tests.
7. Đề xuất audit logs và metrics phù hợp.

## Câu hỏi gợi mở

- `[Authorize]` có đảm bảo caller được truy cập tenant trong query string không?
- `FromSqlRaw` xử lý interpolation này như thế nào?
- Có nên trả thẳng EF entity ra API không?
- Search term có cần giới hạn độ dài hay pagination không?
- Những dữ liệu nào nên xuất hiện trong application log/audit log?

## Gợi ý

### Gợi ý 1

Authentication chỉ chứng minh caller là ai; nó không tự quyết định caller được truy cập resource nào.

### Gợi ý 2

Hãy xem tenant ID và search term đều là untrusted input, đồng thời tách authorization, query construction và response projection.

## Dừng lại và tự review

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

---

## Kết quả code review tham khảo

### 1. SQL injection

**Problem:** `tenantId` và `query` được nối trực tiếp vào raw SQL.  
**Why:** string interpolation diễn ra trước khi `FromSqlRaw` nhận SQL.  
**Impact:** attacker có thể thay đổi câu SQL với quyền của DB principal.  
**Severity:** Critical.  
**Recommended fix:** dùng LINQ parameterized query hoặc parameter API thích hợp; không ghép input vào SQL text.

### 2. Broken tenant-level authorization

**Problem:** caller tự truyền `tenantId`; `[Authorize]` chỉ yêu cầu authenticated identity.  
**Impact:** authenticated user có thể thử tenant khác nếu không có policy/resource authorization.  
**Severity:** Critical.  
**Recommended fix:** derive allowed tenant(s) từ trusted claims/server-side mapping và enforce authorization trước query.

### 3. Trả trực tiếp database entity

**Problem:** `Ok(users)` serialize entity đầy đủ theo model hiện tại.  
**Impact:** field mới hoặc sensitive field có thể vô tình lộ qua API.  
**Severity:** High.  
**Recommended fix:** explicit DTO projection chỉ gồm field cần thiết.

### 4. Log raw search query và identity

**Problem:** search term có thể chứa email/PII hoặc dữ liệu nhạy cảm.  
**Impact:** sensitive data lan sang logging platform.  
**Severity:** Medium.  
**Recommended fix:** audit bằng stable identifiers, category và metadata tối thiểu; mask/hash khi policy cho phép.

### 5. Không giới hạn result/pagination

**Problem:** query có thể trả dataset rất lớn.  
**Impact:** DB load, memory allocation và response size tăng mạnh.  
**Severity:** Medium.  
**Recommended fix:** enforce page size và pagination/cursor.

### 6. Search input không có giới hạn hợp lý

**Problem:** empty/very long wildcard search được chấp nhận.  
**Impact:** expensive scans và abuse.  
**Severity:** Medium.  
**Recommended fix:** validate length/shape, rate-limit theo risk profile, cân nhắc search/index strategy.

### 7. Tracking không cần thiết cho read-only endpoint

**Problem:** entity được tracked mặc dù chỉ đọc.  
**Impact:** overhead không cần thiết.  
**Severity:** Low.  
**Recommended fix:** `AsNoTracking()` hoặc projection.

## Phiên bản code đề xuất

```csharp
[HttpGet("search")]
[Authorize(Policy = "SupportUser")]
public async Task<ActionResult<IReadOnlyList<UserSearchDto>>> Search(
    [FromQuery] string query,
    [FromQuery] int take = 25,
    CancellationToken cancellationToken = default)
{
    if (string.IsNullOrWhiteSpace(query) || query.Length is < 2 or > 100)
        return BadRequest("Search query must contain 2-100 characters.");

    take = Math.Clamp(take, 1, 100);

    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    _logger.LogInformation(
        "Authorized user search in tenant {TenantId}",
        tenantId);

    var pattern = $"%{query.Trim()}%";

    var users = await _db.Users
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId &&
            (EF.Functions.ILike(x.Email, pattern) ||
             EF.Functions.ILike(x.DisplayName, pattern)))
        .OrderByDescending(x => x.CreatedAt)
        .Take(take)
        .Select(x => new UserSearchDto(
            x.Id,
            x.DisplayName,
            x.Email))
        .ToListAsync(cancellationToken);

    return Ok(users);
}
```

`EF.Functions.ILike` là provider-specific cho PostgreSQL/Npgsql; nếu provider hoặc portability requirement khác, chọn search primitive tương ứng. Tenant claim cũng chỉ an toàn nếu issuer/trust model bảo đảm claim đó đáng tin và nghiệp vụ thực sự là một tenant/user; support cross-tenant cần resource authorization riêng thay vì lấy arbitrary query parameter.

## Trade-offs

LINQ giúp parameterization và maintainability tốt hơn nhưng wildcard `%term%` vẫn có thể tốn kém trên dataset lớn. Search quy mô lớn có thể cần index/search strategy khác. Claim-based tenant scoping đơn giản nhưng support staff có quyền nhiều tenant cần server-side entitlement lookup hoặc policy/resource authorization. DTO projection tăng mapping code nhưng giảm accidental data exposure.

## Cách kiểm thử

1. **Security test:** query chứa quote/SQL payload chỉ được coi là dữ liệu, không thay đổi SQL semantics.
2. **Authorization test:** user tenant A không thể đọc tenant B dù cố truyền/manipulate request.
3. **Response-contract test:** DTO không chứa sensitive columns.
4. **Load/database test:** broad search với dataset lớn vẫn bị giới hạn và có execution plan chấp nhận được.
5. **Logging test:** raw search term/sensitive user fields không xuất hiện trong application logs.

## Quan sát trong production

Audit authorized/denied access bằng actor ID, tenant ID và correlation ID; không cần log raw search text mặc định. Theo dõi query latency, rows returned, DB command duration, 4xx/403 rate, rate-limit events và anomalous cross-tenant authorization failures. Trace từ HTTP request tới DB query nhưng tránh gắn sensitive input làm span attributes.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support staff được phép truy cập nhiều tenant, bạn thiết kế authorization thế nào?
2. Parameterization đã giải quyết SQL injection; nó có giải quyết query-performance abuse không?
3. Nếu cần tìm substring trên hàng chục triệu user, bạn sẽ đánh giá index/search architecture ra sao trước khi thêm hạ tầng mới?
