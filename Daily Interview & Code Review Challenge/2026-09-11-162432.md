# Code Review Challenge 1 — CMS page bị cache quá “tốt”: user A nhìn thấy nội dung cá nhân hóa của user B sau khi đi qua CDN

**Chủ đề:** C#/.NET 8, ASP.NET Core, Optimizely CMS architecture, `IMemoryCache`, Akamai/CDN, HTTP caching, cache key design, personalization, cache invalidation, cache stampede, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một marketing/e-commerce website dùng Optimizely CMS làm nguồn nội dung. ASP.NET Core application render trang sản phẩm bằng cách kết hợp:

- nội dung editorial từ CMS;
- giá từ product API;
- trạng thái loyalty của user hiện tại;
- localized content theo `culture`;
- Akamai ở phía trước để cache response public.

Yêu cầu:

- phần editorial có thể cache vài phút;
- user đã đăng nhập có thể thấy banner giảm giá riêng theo loyalty tier;
- user anonymous không được nhìn thấy dữ liệu dành cho user đã đăng nhập;
- publish content mới trong CMS cần xuất hiện trong thời gian hợp lý;
- website chạy nhiều application instances;
- traffic có thể tăng mạnh khi campaign bắt đầu;
- upstream CMS/product API có thể chậm hoặc lỗi tạm thời;
- request cancellation phải propagate;
- operations cần biết origin hit rate, application cache hit ratio, CDN hit ratio, stale-content incidents và dependency latency.

Sau một campaign lớn, support nhận được các báo cáo:

- một số user anonymous thấy banner “Gold Member” sau khi refresh;
- hai user ở hai quốc gia đôi lúc thấy cùng ngôn ngữ dù `culture` khác nhau;
- editor publish nội dung mới nhưng một số users vẫn thấy bản cũ hơn 20 phút;
- khi cache hết hạn đúng lúc traffic tăng, CPU và outbound calls tăng mạnh;
- khi product API timeout, hàng loạt requests cùng gọi lại upstream;
- team nói “chúng ta đã cache ở cả `IMemoryCache` và Akamai nên performance chắc chắn tốt”.

## Đoạn code cần review

```csharp
public sealed class ProductPageService
{
    private readonly IMemoryCache _cache;
    private readonly CmsContentClient _cms;
    private readonly ProductApiClient _products;
    private readonly LoyaltyClient _loyalty;

    public ProductPageService(
        IMemoryCache cache,
        CmsContentClient cms,
        ProductApiClient products,
        LoyaltyClient loyalty)
    {
        _cache = cache;
        _cms = cms;
        _products = products;
        _loyalty = loyalty;
    }

    public async Task<ProductPageVm> GetAsync(
        string slug,
        string culture,
        ClaimsPrincipal user,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"product-page:{slug}";

        if (_cache.TryGetValue(cacheKey, out ProductPageVm? cached))
            return cached!;

        var content = await _cms.GetProductPageAsync(
            slug,
            culture);

        var product = await _products.GetAsync(
            content.ProductCode);

        LoyaltyStatus? loyalty = null;
        if (user.Identity?.IsAuthenticated == true)
        {
            loyalty = await _loyalty.GetStatusAsync(
                user.FindFirst("sub")!.Value);
        }

        var vm = new ProductPageVm(
            content.Title,
            content.DescriptionHtml,
            product.Price,
            culture,
            loyalty?.Tier,
            loyalty?.DiscountPercent);

        _cache.Set(
            cacheKey,
            vm,
            TimeSpan.FromMinutes(10));

        return vm;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong cache behavior và personalization boundary.
2. Xác định security, performance, reliability và maintainability concerns.
3. Giải thích production impact khi nhiều users/cultures cùng truy cập và khi cache hết hạn dưới tải cao.
4. Ưu tiên findings theo severity.
5. Đề xuất corrected implementation/design với cache layers và ownership rõ ràng.
6. Giải thích testing cho cross-user leakage, localization, invalidation, dependency failure và cache stampede.
7. Đề xuất production telemetry chứng minh cache đang tăng performance mà không phá correctness.

## Câu hỏi gợi mở

1. Cache key hiện chứa những dimensions nào và đang bỏ sót dimensions nào ảnh hưởng response?
2. Một `ProductPageVm` chứa loyalty data có an toàn để cache theo `slug` rồi chia sẻ giữa requests không?
3. `Cache-Control: public` nói gì với CDN/proxy về khả năng reuse response giữa users?
4. Nếu 2.000 requests cùng thấy cache miss sau 10 phút, có bao nhiêu upstream calls có thể bắt đầu cùng lúc?
5. Publish event từ CMS và TTL của application/CDN đang liên hệ với nhau như thế nào?

## Gợi ý

### Gợi ý 1

Primary risk là **cache key và HTTP cache policy không phản ánh personalization boundary**, nên dữ liệu user-specific có thể bị reuse cho user khác ở cả application cache và CDN.

### Gợi ý 2

Tách dữ liệu thành phần nào thực sự public/cacheable và phần nào request-specific; sau đó reasoning riêng cho application cache, CDN cache, invalidation và stampede control.

## Kết quả code review tham khảo

### Critical — Cache application có thể làm rò rỉ loyalty data giữa users

**Vấn đề:**  
`ProductPageVm` chứa `Tier` và `DiscountPercent`, nhưng cache key chỉ là `product-page:{slug}`.

**Tại sao xảy ra:**  
Request đầu tiên tạo cache entry quyết định payload được chia sẻ cho mọi request tiếp theo cùng slug trong process, bất kể user identity hoặc authentication state.

**Ảnh hưởng production:**  
User anonymous hoặc user khác có thể nhìn thấy loyalty tier/discount không dành cho họ. Đây là cross-user data leakage và cũng có thể tạo pricing/display correctness bug.

**Cách sửa:**  
Không cache object đã trộn public CMS/product data với user-specific data dưới public/shared key. Cache phần public riêng, sau đó compose personalization per request. Chỉ cache loyalty riêng nếu có key theo stable user identity, TTL phù hợp và business/security chấp nhận.

### Critical — `Cache-Control: public` cho personalized HTML cho phép shared CDN cache reuse giữa users

**Vấn đề:**  
Controller luôn đặt `public, max-age=600`, kể cả response có loyalty data.

**Tại sao xảy ra:**  
`public` cho phép shared cache như CDN lưu response và phục vụ lại cho requests khác nếu cache key ở edge match.

**Ảnh hưởng production:**  
Cross-user leakage có thể vượt ra ngoài một application instance và lan qua CDN PoP. Một personalized response bị cache ở edge có thể được phục vụ cho nhiều users.

**Cách sửa:**  
Không đánh dấu personalized full-page response là public-cacheable. Tách public page shell/content khỏi user-specific fragment hoặc dùng client/server composition mà private fragment không đi qua shared cache. Nếu response thực sự personalized, dùng policy phù hợp như `private`/`no-store` tùy requirement và không dựa vào CDN shared cache cho phần đó.

### High — Cache key bỏ qua `culture`

**Vấn đề:**  
`culture` ảnh hưởng CMS content nhưng không nằm trong cache key.

**Tại sao xảy ra:**  
Page được cache theo slug duy nhất.

**Ảnh hưởng production:**  
Request đầu tiên cho `en-US` có thể khiến `vi-VN`, `fr-FR` hoặc culture khác nhận nhầm localized content.

**Cách sửa:**  
Public cache key phải chứa mọi dimension làm thay đổi public representation, ví dụ normalized `slug`, `culture`, content/site identifier và version dimension cần thiết. Không thêm user ID vào full public-page cache như một workaround nếu có thể tách personalization.

### High — Không propagate `CancellationToken` tới dependencies

**Vấn đề:**  
Method nhận `cancellationToken` nhưng `_cms`, `_products`, `_loyalty` calls không truyền token.

**Tại sao xảy ra:**  
Cancellation không tự propagate chỉ vì caller có token.

**Ảnh hưởng production:**  
Client đã rời đi nhưng application vẫn tiếp tục gọi CMS/product/loyalty APIs, làm tăng connection pressure và cost khi load cao.

**Cách sửa:**  
Propagate cancellation tới SDK/client calls hỗ trợ token. Với shared cache fill, cần phân biệt cancellation của một caller với lifetime của shared computation nếu áp dụng single-flight.

### High — Cache miss đồng thời có thể tạo stampede

**Vấn đề:**  
`TryGetValue` rồi fetch upstream rồi `_cache.Set` không có single-flight/per-key coordination.

**Tại sao xảy ra:**  
Nhiều requests cùng quan sát miss có thể cùng gọi CMS/product API.

**Ảnh hưởng production:**  
Khi TTL hết hạn đúng lúc campaign tăng traffic, upstream load tăng đột ngột, latency kéo dài, timeout tăng và tạo feedback loop.

**Cách sửa:**  
Dùng per-key single-flight/async cache factory phù hợp, TTL có jitter hoặc stale-while-revalidate pattern nếu business cho phép. Không dùng global lock làm serialize mọi product.

### High — Invalidation giữa CMS publish, application cache và CDN chưa được thiết kế

**Vấn đề:**  
Cache application có TTL 10 phút; CDN cũng có max-age 10 phút, nhưng không có publish invalidation/purge/version strategy rõ.

**Tại sao xảy ra:**  
Mỗi cache layer giữ state độc lập. Publish ở CMS không tự động invalidates custom application cache hoặc CDN trừ khi được tích hợp.

**Ảnh hưởng production:**  
Content mới có thể bị stale theo tổng hợp nhiều layer hoặc lâu hơn nếu TTL/purge behavior không như team giả định.

**Cách sửa:**  
Define freshness SLO. Nếu cần near-real-time sau publish, phát content-change signal để evict relevant application keys và purge/version CDN cache. Nếu chấp nhận TTL-based freshness, document worst-case staleness và đo nó.

### Medium — Public data và personalized data bị coupling trong cùng view model

**Vấn đề:**  
CMS content, product price và loyalty state được load/composed trong một method rồi cache cùng nhau.

**Tại sao xảy ra:**  
Boundary cacheability không trùng boundary của data ownership/freshness.

**Ảnh hưởng production:**  
Khó chọn TTL đúng: editorial content, price và loyalty có freshness khác nhau. Thay đổi một phần làm invalidate toàn object.

**Cách sửa:**  
Tách `PublicProductPageData` khỏi `UserProductContext`. Cache public content với policy riêng; price có cache policy riêng nếu business cho phép; loyalty được resolve theo request/user.

### Medium — Các upstream calls chạy tuần tự dù một số có thể độc lập

**Vấn đề:**  
CMS phải chạy trước để lấy product code, nhưng sau đó product lookup và loyalty lookup có thể độc lập nếu user authenticated.

**Tại sao xảy ra:**  
Implementation await tuần tự.

**Ảnh hưởng production:**  
Cache miss latency là tổng latency của dependencies. Tuy nhiên đổi thẳng sang unbounded parallelism không phải lúc nào cũng đúng.

**Cách sửa:**  
Sau khi có content, có thể chạy independent I/O calls song song có kiểm soát nếu dependency capacity cho phép. Quan trọng hơn là tránh duplicate work qua stampede control.

### Medium — Null-forgiving `sub` claim che authorization/identity assumption

**Vấn đề:**  
`user.FindFirst("sub")!.Value` giả định authenticated principal luôn có claim này.

**Tại sao xảy ra:**  
Authentication scheme/claim mapping có thể khác nhau.

**Ảnh hưởng production:**  
Một principal hợp lệ nhưng thiếu claim có thể gây 500. Nếu loyalty lookup dùng sai identity claim còn có thể gây authorization/correctness bug.

**Cách sửa:**  
Xác định canonical user identifier từ authentication contract và xử lý claim thiếu rõ ràng; không chỉ suppress nullable warning.

### Medium — Failure/degradation policy chưa rõ

**Vấn đề:**  
CMS, product API hoặc loyalty API fail đều có thể làm toàn page fail.

**Tại sao xảy ra:**  
Không phân loại critical dependency và optional personalization.

**Ảnh hưởng production:**  
Loyalty outage có thể biến thành website outage dù core product page vẫn có thể phục vụ; ngược lại, hiển thị stale price có thể không được business chấp nhận.

**Cách sửa:**  
Define per-dependency contract. Ví dụ loyalty có thể degrade bằng cách bỏ banner; editorial có thể dùng stale public cache có giới hạn; price cần tuân theo pricing correctness requirement. Retry/circuit breaker phải có timeout budget và không nhân traffic khi dependency đang lỗi.

### Medium — `DescriptionHtml` cần trust/sanitization contract rõ

**Vấn đề:**  
View model chứa HTML từ CMS.

**Tại sao xảy ra:**  
CMS-authored rich text thường cần explicit trust boundary; cách Razor render field quyết định XSS risk.

**Ảnh hưởng production:**  
Nếu content source/editor permissions hoặc rendering pipeline không đảm bảo sanitization/trusted markup, HTML có thể trở thành XSS vector.

**Cách sửa:**  
Xác định rõ content nào là trusted editorial HTML và sanitization/rendering policy. Không dùng raw rendering cho arbitrary external/user content.

### Low — Observability không tách cache layers và dependency outcomes

**Vấn đề:**  
Code không cho biết request là app-cache hit, CDN hit, origin miss hay upstream degradation.

**Tại sao xảy ra:**  
Cache được coi như implementation detail thay vì operational subsystem.

**Ảnh hưởng production:**  
Team biết latency tăng nhưng khó biết cache layer nào sai hoặc stampede bắt đầu ở đâu.

**Cách sửa:**  
Thêm metrics/traces cho application hit/miss/fill duration, concurrent fills, upstream calls, content age, CDN cache status header, purge result và personalized/public response class.

## Phiên bản đề xuất

Một hướng đơn giản là cache **public page data** theo đúng representation key, rồi compose loyalty per request. Ví dụ dưới đây không giả định một API Optimizely cụ thể; `CmsContentClient` đại diện integration layer của ứng dụng.

```csharp
public sealed record PublicProductPageData(
    string Title,
    string DescriptionHtml,
    decimal Price,
    string Culture);

public sealed record ProductPageVm(
    PublicProductPageData Public,
    string? LoyaltyTier,
    decimal? DiscountPercent);

public sealed class ProductPageService
{
    private readonly IMemoryCache _cache;
    private readonly CmsContentClient _cms;
    private readonly ProductApiClient _products;
    private readonly LoyaltyClient _loyalty;
    private readonly IAsyncKeyedLock _keyedLock;

    public ProductPageService(
        IMemoryCache cache,
        CmsContentClient cms,
        ProductApiClient products,
        LoyaltyClient loyalty,
        IAsyncKeyedLock keyedLock)
    {
        _cache = cache;
        _cms = cms;
        _products = products;
        _loyalty = loyalty;
        _keyedLock = keyedLock;
    }

    public async Task<ProductPageVm> GetAsync(
        string slug,
        string culture,
        ClaimsPrincipal user,
        CancellationToken ct)
    {
        var normalizedCulture = CultureInfo
            .GetCultureInfo(culture)
            .Name;

        var publicKey = $"product-page:v2:{slug}:{normalizedCulture}";

        if (!_cache.TryGetValue(
            publicKey,
            out PublicProductPageData? publicData))
        {
            await using var lease = await _keyedLock
                .AcquireAsync(publicKey, ct);

            if (!_cache.TryGetValue(publicKey, out publicData))
            {
                var content = await _cms.GetProductPageAsync(
                    slug,
                    normalizedCulture,
                    ct);

                var product = await _products.GetAsync(
                    content.ProductCode,
                    ct);

                publicData = new PublicProductPageData(
                    content.Title,
                    content.DescriptionHtml,
                    product.Price,
                    normalizedCulture);

                _cache.Set(
                    publicKey,
                    publicData,
                    TimeSpan.FromMinutes(5));
            }
        }

        string? tier = null;
        decimal? discount = null;

        if (user.Identity?.IsAuthenticated == true)
        {
            var subject = user.FindFirst("sub")?.Value
                ?? throw new InvalidOperationException(
                    "Authenticated user is missing canonical subject claim.");

            var loyalty = await _loyalty.GetStatusAsync(
                subject,
                ct);

            tier = loyalty.Tier;
            discount = loyalty.DiscountPercent;
        }

        return new ProductPageVm(
            publicData!,
            tier,
            discount);
    }
}
```

Controller policy có thể tách theo authentication state. Một phương án an toàn là **không public-cache full HTML nếu view vẫn chứa personalization**:

```csharp
[HttpGet("/products/{slug}")]
public async Task<IActionResult> Product(
    string slug,
    string culture,
    CancellationToken ct)
{
    var model = await _pages.GetAsync(
        slug,
        culture,
        User,
        ct);

    if (User.Identity?.IsAuthenticated == true)
    {
        Response.Headers.CacheControl = "private, no-store";
    }
    else
    {
        Response.Headers.CacheControl = "public, max-age=300";
    }

    return View("Product", model);
}
```

Tốt hơn nữa, nếu product requirement cần CDN cache mạnh cho page shell, có thể render public page hoàn toàn không chứa loyalty data và tải personalized fragment qua private API sau khi page load, hoặc dùng một server-side composition design mà shared-cache boundary không bao giờ chứa user-specific payload.

`IAsyncKeyedLock` ở ví dụ chỉ biểu diễn per-key single-flight abstraction; implementation cụ thể phải được review để tránh memory leak và contention. Nếu hệ thống chạy nhiều instances, per-process single-flight không ngăn mọi instance cùng refresh, nhưng vẫn giảm amplification nội bộ. Distributed coordination chỉ nên thêm khi evidence cho thấy cần.

## Giải thích thiết kế sau khi sửa

Thiết kế mới bắt đầu từ **cacheability boundary**, không bắt đầu từ lựa chọn cache technology. Public editorial/product data và personalized loyalty data có ownership, freshness và security khác nhau nên không nên bị cache như một object duy nhất.

Application cache key chứa `slug` và normalized `culture`, là hai dimensions làm thay đổi public representation trong scenario này. Nếu site, currency, catalog hoặc experiment variant cũng thay đổi output thì chúng cũng phải được đưa vào key hoặc tách thành layer riêng.

CDN chỉ được phép cache response thật sự public. Nếu authenticated HTML vẫn chứa personalization, shared caching cần bị vô hiệu hóa cho response đó. Nếu muốn tận dụng CDN tối đa, architecture nên tách public shell khỏi private fragment thay vì tạo một cache key khổng lồ theo user.

Publish invalidation phải được thiết kế xuyên các layers. CMS publish event có thể evict application cache và trigger CDN purge/versioning cho affected content. Nếu team chọn TTL-only để giảm complexity, freshness SLA phải chấp nhận worst-case staleness đó.

## Trade-offs

- Tách public/private fragments tăng số request hoặc complexity composition, nhưng làm security boundary rõ hơn và CDN hiệu quả hơn.
- Short TTL giảm stale duration nhưng tăng origin load; long TTL giảm load nhưng tăng invalidation pressure.
- Per-instance single-flight đơn giản nhưng không coordination toàn cluster; distributed lock mạnh hơn nhưng thêm failure modes và operational cost.
- Purge-on-publish cho freshness tốt hơn nhưng phụ thuộc reliability của invalidation pipeline.
- Caching product price có thể tốt cho performance nhưng chỉ hợp lệ nếu pricing business rule cho phép stale window tương ứng.

## Cách kiểm thử

1. **Security/concurrency test:** user Gold, user Standard và anonymous cùng request một slug/culture với interleaving khác nhau; không response nào được reuse sai personalization.
2. **Localization integration test:** request cùng slug với nhiều cultures; application cache và CDN cache key không trả nhầm localized content.
3. **Stampede load test:** làm cache expire rồi bắn hàng nghìn concurrent requests; đo số CMS/product upstream calls và xác minh single-flight/bounded refresh hoạt động.
4. **Publish/invalidation test:** publish content mới; xác minh application cache, CDN purge/version và observed freshness nằm trong SLA đã định nghĩa.
5. **Failure-path test:** loyalty timeout, CMS timeout, product API 5xx và request cancellation; xác minh degradation policy, timeout budget, telemetry và không tạo retry storm.

## Quan sát trong production

Theo dõi:

- application cache hit/miss/fill duration theo public key class;
- concurrent fills/single-flight waiter count;
- CDN/Akamai hit ratio, origin request rate và cache status headers;
- content age/staleness sampled theo published version;
- CMS/product/loyalty dependency p50/p95/p99 và error rate;
- authenticated vs anonymous cache policy distribution;
- purge/invalidation success/failure và propagation latency;
- security alert/incident signal cho personalized content xuất hiện trong shared-cache response;
- correlation ID xuyên origin request và dependency calls.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business muốn authenticated users vẫn nhận phần lớn page từ CDN, bạn sẽ tách public/private fragments theo những cách nào?
2. Nếu 20 application instances cùng refresh một key sau publish, khi nào bạn chấp nhận duplicate refresh và khi nào mới cân nhắc distributed coordination?
3. Nếu product price chỉ được phép stale tối đa 5 giây nhưng CMS content được stale 10 phút, bạn sẽ tách cache model ra sao?

## Bối cảnh

Một ASP.NET Core application chạy 8 instances trên Azure App Service. Team dùng CI pipeline tạo artifact và CD pipeline deploy qua staging slot rồi swap sang production.

Release mới đổi domain model từ một cột `CustomerName` sang hai cột `FirstName` và `LastName`. Developer tạo EF Core migration có thao tác rename/drop để “giữ schema sạch”.

Yêu cầu:

- deployment phải gần zero-downtime;
- trong rollout có thể tồn tại app version cũ và mới trong một khoảng thời gian;
- rollback application phải khả thi nếu error rate tăng sau swap;
- production database lớn và migration không được giữ lock dài ngoài dự kiến;
- chỉ một migration runner được apply schema change;
- artifact deploy phải đúng artifact đã qua CI/test;
- production secret không được ghi vào repository hoặc logs;
- migration status, duration và failure phải quan sát được.

Pipeline hiện tại chạy như sau:

```yaml
steps:
  - name: checkout
    run: git checkout main

  - name: build
    run: dotnet publish src/Web/Web.csproj -c Release -o ./publish

  - name: migrate-production
    run: >
      dotnet ef database update
      --project src/Infrastructure/Infrastructure.csproj
      --startup-project src/Web/Web.csproj
      --connection "Server=prod-sql;Database=AppDb;User Id=deploy;Password=P@ssw0rd!"

  - name: deploy-staging
    run: az webapp deploy --slot staging --src-path ./publish.zip

  - name: smoke-test
    run: curl -f https://app-staging.example.com/health

  - name: swap
    run: az webapp deployment slot swap --slot staging --target-slot production
```

Migration trong release:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "CustomerName",
        table: "Orders",
        newName: "FirstName");

    migrationBuilder.AddColumn<string>(
        name: "LastName",
        table: "Orders",
        type: "nvarchar(200)",
        nullable: false,
        defaultValue: "");
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropColumn(
        name: "LastName",
        table: "Orders");

    migrationBuilder.RenameColumn(
        name: "FirstName",
        table: "Orders",
        newName: "CustomerName");
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và deployment-safety problems trong pipeline/migration.
2. Xác định security, availability, rollback và maintainability concerns.
3. Giải thích production impact khi app version cũ và mới cùng tồn tại hoặc khi migration thành công nhưng deployment/swap thất bại.
4. Ưu tiên findings theo severity.
5. Đề xuất rollout/migration strategy đã sửa với backward compatibility rõ ràng.
6. Giải thích testing cho migration, mixed-version operation, failure giữa các bước và rollback.
7. Đề xuất production telemetry/evidence để quyết định tiếp tục hay rollback release.

## Câu hỏi gợi mở

1. Sau khi `CustomerName` bị rename, production instances đang chạy version cũ sẽ query/write cột nào?
2. Nếu migration thành công nhưng deploy staging hoặc swap thất bại, database đang tương thích với app version nào?
3. `Down()` có phải một rollback production an toàn khi dữ liệu mới đã được ghi vào `FirstName`/`LastName` không?
4. Pipeline đang build artifact nào, và có chắc đó chính là commit/artifact đã qua CI review/test không?
5. Connection string production đang xuất hiện ở đâu trong execution history/logs?

## Gợi ý

### Gợi ý 1

Primary risk là **destructive schema change được apply trước khi rollout app và không tương thích với version cũ**, làm mất khả năng mixed-version deployment và rollback an toàn.

### Gợi ý 2

Reasoning theo **expand → migrate/backfill → switch reads/writes → contract** thay vì cố hoàn tất rename/drop trong một release duy nhất.

## Kết quả code review tham khảo

### Critical — Migration phá backward compatibility trước khi app mới được deploy

**Vấn đề:**  
`CustomerName` bị rename thành `FirstName` trước bước deploy staging/swap.

**Tại sao xảy ra:**  
Các production instances version cũ vẫn đang chạy và vẫn expect schema cũ trong khoảng migration/deployment.

**Ảnh hưởng production:**  
Ngay sau migration, app cũ có thể bắt đầu lỗi query/write dù app mới chưa phục vụ traffic. Release pipeline có thể tự gây outage trước khi smoke test version mới.

**Cách sửa:**  
Dùng expand/contract. Release đầu thêm `FirstName`/`LastName` nhưng giữ `CustomerName`; deploy code tương thích cả schema cũ/mới hoặc dual-write/backfill. Chỉ drop/rename cột cũ ở release sau khi không còn version nào phụ thuộc nó.

### Critical — Rollback application không còn an toàn sau destructive schema migration

**Vấn đề:**  
Sau migration, rollback bằng cách swap app version cũ trở lại không đảm bảo version cũ chạy được.

**Tại sao xảy ra:**  
Database là shared mutable state và đã vượt qua compatibility boundary của old binary.

**Ảnh hưởng production:**  
Khi app mới có regression, operator mất rollback path nhanh nhất; incident recovery kéo dài.

**Cách sửa:**  
Thiết kế schema migration sao cho cả N và N-1 binaries hoạt động trong rollback window. Contract step chỉ thực hiện sau khi release mới ổn định và rollback window đóng.

### Critical — Production database credential hard-code trong pipeline

**Vấn đề:**  
Connection string chứa username/password plaintext trong command.

**Tại sao xảy ra:**  
Command có thể xuất hiện trong repository, pipeline configuration, process list hoặc logs.

**Ảnh hưởng production:**  
Credential exposure và privilege escalation vào production SQL.

**Cách sửa:**  
Dùng approved secret store/service connection/Managed Identity khi phù hợp, inject secret ngoài source control, mask logs và cấp migration principal đúng least privilege cần thiết.

### High — Pipeline build lại từ `main` thay vì deploy immutable artifact đã qua CI

**Vấn đề:**  
CD pipeline `git checkout main` rồi `dotnet publish` lại.

**Tại sao xảy ra:**  
`main` có thể thay đổi giữa CI validation và deployment; build environment cũng có thể khác.

**Ảnh hưởng production:**  
Artifact được deploy có thể không phải artifact đã review/test/scan. Reproduce và rollback khó tin cậy.

**Cách sửa:**  
CI tạo immutable versioned artifact từ exact commit SHA, chạy tests/scans, publish artifact. CD chỉ promote artifact đó qua environments.

### High — Migration và app deployment không có explicit compatibility gate

**Vấn đề:**  
Pipeline coi `database update` thành step kỹ thuật đơn lẻ rồi deploy app.

**Tại sao xảy ra:**  
Không có evidence rằng schema sau migration tương thích với current production binary và target binary.

**Ảnh hưởng production:**  
Một migration “thành công” về SQL vẫn có thể phá runtime contract.

**Cách sửa:**  
Mỗi migration cần compatibility classification. Pipeline/release plan phải biết migration là expand-only, backfill, switch hay contract. Contract migration không được chạy trước khi old binaries đã retired.

### High — `Down()` không đảm bảo rollback dữ liệu an toàn

**Vấn đề:**  
`Down()` drop `LastName` rồi rename `FirstName` trở lại `CustomerName`.

**Tại sao xảy ra:**  
Dữ liệu đã được tách thành hai fields có thể không recombine losslessly; drop cột xóa data.

**Ảnh hưởng production:**  
Chạy database downgrade trong incident có thể biến application incident thành data-loss incident.

**Cách sửa:**  
Không coi `Down()` là production rollback strategy mặc định. Prefer forward-fix/backward-compatible schema. Nếu database rollback thực sự cần, phải có tested data transformation/backup/restore plan và RPO/RTO rõ.

### High — Không có backfill strategy cho dữ liệu cũ

**Vấn đề:**  
`FirstName` thực chất là old `CustomerName`, còn `LastName` mặc định rỗng; semantic data model mới chưa được tạo đúng.

**Tại sao xảy ra:**  
Schema transform bị nhầm với domain data migration.

**Ảnh hưởng production:**  
App mới có thể hiển thị/sort/search tên sai. Với hàng triệu rows, backfill đồng bộ trong schema migration còn có thể giữ lock/log growth lâu.

**Cách sửa:**  
Tách expand schema khỏi data backfill. Backfill theo batches, resumable, observable và idempotent. Xác định parsing rule/business ambiguity trước; không giả định mọi `CustomerName` có thể split chính xác.

### High — Migration runner ownership chưa được đảm bảo

**Vấn đề:**  
Scenario yêu cầu chỉ một runner apply migration nhưng pipeline snippet không thể hiện lease/serialization/environment lock.

**Tại sao xảy ra:**  
Hai release jobs hoặc retry/manual trigger có thể chạy cùng environment.

**Ảnh hưởng production:**  
Concurrent deployment/migration tạo race, lock contention và khó xác định release ownership.

**Cách sửa:**  
Dùng environment-level deployment lock/concurrency control trong CI/CD platform. Migration command cũng phải fail rõ nếu schema state không đúng expectation.

### Medium — Health smoke test quá hẹp

**Vấn đề:**  
`curl /health` chỉ chứng minh process trả health endpoint.

**Tại sao xảy ra:**  
Health endpoint có thể không exercise changed schema/read-write path.

**Ảnh hưởng production:**  
Staging pass nhưng production traffic vào `Orders` path mới mới phát hiện mapping/data bug.

**Cách sửa:**  
Thêm release validation cho critical changed behavior: database connectivity/schema compatibility, representative read/write API, auth, dependency health và synthetic transaction với safe test data.

### Medium — Không có preflight về migration cost/locking

**Vấn đề:**  
Pipeline chạy migration trực tiếp trên production DB mà không cho thấy estimate/validation cho bảng lớn.

**Tại sao xảy ra:**  
DDL behavior/cost phụ thuộc operation, SQL Server version/schema/indexes/data size.

**Ảnh hưởng production:**  
Migration có thể giữ schema locks, tăng transaction log hoặc block workload lâu hơn deployment budget.

**Cách sửa:**  
Review generated SQL, test trên production-like data volume, đo duration/locks/log growth và có maintenance/online strategy nếu operation đắt. Không giả định mọi EF migration là “nhanh”.

### Medium — Pipeline failure windows chưa có explicit recovery state

**Vấn đề:**  
Không định nghĩa xử lý nếu migration pass nhưng deploy fail, smoke fail, swap fail hoặc swap pass rồi metrics xấu.

**Tại sao xảy ra:**  
Pipeline chỉ mô tả happy path.

**Ảnh hưởng production:**  
Operator improvises trong incident và có thể chạy lại migration/swap sai thứ tự.

**Cách sửa:**  
Document machine-readable/manual recovery playbook theo từng checkpoint, artifact version, schema version và slot state. Mỗi step nên idempotent hoặc có clear guard.

### Low — Không ghi release/schema identity vào telemetry

**Vấn đề:**  
Snippet không cho thấy app log commit/build version hoặc schema version.

**Tại sao xảy ra:**  
Release evidence không được coi như phần observability.

**Ảnh hưởng production:**  
Khó correlate error spike với exact binary/schema migration.

**Cách sửa:**  
Expose build SHA/version, slot, schema migration version và deployment marker trong logs/Application Insights release annotations/dashboard.

## Phiên bản đề xuất

Thay vì rename/drop trong một release, dùng migration nhiều phase.

### Release A — Expand schema

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>(
        name: "FirstName",
        table: "Orders",
        type: "nvarchar(200)",
        nullable: true);

    migrationBuilder.AddColumn<string>(
        name: "LastName",
        table: "Orders",
        type: "nvarchar(200)",
        nullable: true);
}
```

Application version N+1 trong release này phải vẫn tương thích `CustomerName`. Một hướng là:

1. read từ new columns khi đã populated, fallback `CustomerName`;
2. write `CustomerName` và new fields trong compatibility window nếu business mapping rõ;
3. chạy backfill riêng theo batches;
4. đo completion/validation;
5. sau khi toàn fleet chạy N+1 ổn định, release kế tiếp chuyển primary reads sang new fields;
6. chỉ contract/drop `CustomerName` sau khi rollback window đã đóng và không còn consumer phụ thuộc.

Pipeline cũng nên promote immutable artifact:

```yaml
steps:
  - name: download-ci-artifact
    run: artifact download web-${COMMIT_SHA}.zip

  - name: acquire-production-deployment-lock
    run: deployment-lock acquire production

  - name: migration-preflight
    run: migration-tool verify --expected-compatible-with N,N+1

  - name: apply-expand-migrations
    run: migration-tool apply --environment production

  - name: deploy-staging
    run: az webapp deploy --slot staging --src-path web-${COMMIT_SHA}.zip

  - name: validate-staging
    run: ./scripts/smoke-critical-paths.sh staging

  - name: swap
    run: az webapp deployment slot swap --slot staging --target-slot production

  - name: observe
    run: ./scripts/release-gate.sh --window 10m
```

Các placeholder như `artifact`, `deployment-lock`, `migration-tool` biểu diễn capabilities cần có; không ngụ ý một sản phẩm cụ thể. Nếu CI/CD platform đã có environment concurrency/approvals và secret integration, dùng native capability thay vì tự viết lock service.

Backfill nên là operation riêng, ví dụ job resumable theo primary key ranges. Nó phải ghi progress, retry an toàn, có throttle để không làm hỏng OLTP workload, và validate số rows/semantic conversion trước khi contract.

## Giải thích thiết kế sau khi sửa

Schema evolution trong zero-downtime system là một **compatibility problem**, không chỉ là chạy migration thành công. Trong rollout, old và new binaries có thể cùng truy cập một database; do đó database state ở mỗi phase phải tương thích với cả hai trong khoảng cần thiết.

Expand/contract cho phép tách risk thành các bước nhỏ: thêm schema trước, deploy code tương thích, backfill dữ liệu, chuyển behavior, sau đó mới xóa legacy column. Điều này làm rollback app đơn giản hơn vì old schema vẫn tồn tại trong rollback window.

Không nên tự động downgrade database trong incident. Dữ liệu mới có thể đã được ghi theo semantics mà old schema không biểu diễn được. Application rollback + backward-compatible database thường an toàn hơn; contract migration được thực hiện sau khi confidence đủ cao.

Immutable artifact cũng là requirement correctness: thứ deploy production phải là binary đã được CI test, không phải một build mới từ branch mutable.

## Trade-offs

- Expand/contract cần nhiều releases và temporary duplicate columns/code paths, đổi lại rollback safety tốt hơn.
- Dual-write làm code phức tạp và cần consistency monitoring; nếu có thể tránh bằng compatibility adapter/backfill sequence đơn giản hơn thì nên tránh.
- Backfill theo batches mất thời gian nhưng giảm lock/log pressure so với một transaction lớn.
- Environment lock làm giảm parallel deployment throughput nhưng tránh concurrent schema ownership.
- Giữ legacy column lâu hơn tăng technical debt ngắn hạn nhưng rẻ hơn outage/data loss từ contract quá sớm.

## Cách kiểm thử

1. **Migration integration test:** restore database snapshot production-like, apply expand migration, chạy cả app N và N+1 against cùng schema; critical read/write paths đều pass.
2. **Mixed-version E2E test:** traffic đồng thời qua old/new instances trong simulated rolling deployment; không query/write failure và data remains semantically valid.
3. **Failure-window test:** inject failure sau migration, sau deploy staging, trước swap và sau swap; xác minh recovery steps không cần destructive database downgrade.
4. **Backfill/load test:** chạy batch migration trên data volume gần production, đo locks, transaction log, CPU, duration và OLTP p95; throttle/resume an toàn.
5. **Security/release test:** artifact checksum/commit SHA đúng CI output; pipeline logs không expose connection secret; migration identity chỉ có least-required permissions.

## Quan sát trong production

Theo dõi:

- deployment/build SHA và slot identity;
- current schema migration/version marker;
- migration duration, lock waits, deadlocks, transaction log growth;
- backfill progress, rows succeeded/failed/retried;
- API p50/p95/p99, 5xx và database dependency latency trước/sau swap;
- error rate phân tách theo app version trong mixed window;
- synthetic critical-path success;
- App Service instance/slot health;
- release gate với threshold rõ để continue, hold hoặc rollback application;
- alert nếu old-version instances gọi query không tương thích schema.

## Câu hỏi phỏng vấn mở rộng

1. Nếu bảng `Orders` có 500 triệu rows, bạn sẽ thiết kế backfill và validation thế nào để không làm OLTP workload sụp?
2. Trường hợp nào bạn chấp nhận migration destructive trong cùng release thay vì expand/contract nhiều phase?
3. Nếu N+1 đã ghi dữ liệu không thể biểu diễn bằng schema N, rollback strategy của bạn sẽ thay đổi như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache correctness bắt đầu từ representation/security boundary; shared cache không được chứa user-specific data nếu key/policy không partition đúng.
- Application cache và CDN là hai stateful layers độc lập; TTL, invalidation, personalization và stampede phải được thiết kế xuyên suốt.
- Zero-downtime database migration là bài toán compatibility giữa nhiều app versions và một shared schema.
- `Down()` migration không đồng nghĩa production rollback an toàn, đặc biệt khi dữ liệu mới đã được ghi.
- CI/CD an toàn cần immutable artifact, secret management, migration ownership, failure-window recovery và release telemetry.

## Mẫu tư duy cần nhớ

- Cache only what has a stable sharing boundary.
- Design invalidation and failure behavior together with caching.
- Evolve shared schemas bằng expand → migrate → switch → contract.
- Preserve N/N-1 compatibility trong rollback window.
- Treat deployment as a distributed state transition, không phải một chuỗi happy-path commands.
