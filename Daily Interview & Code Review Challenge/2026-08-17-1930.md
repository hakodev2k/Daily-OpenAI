# Code Review Challenge 1 — Telemetry làm tăng memory, chi phí log và vô tình lộ dữ liệu nhạy cảm

**Chủ đề:** Logging & observability, sensitive-data exposure, memory/allocation, performance, error handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API multi-tenant vừa bổ sung middleware quan sát request để phục vụ điều tra production incident. Team muốn mỗi request có trace, metric latency và log đủ chi tiết để tìm lỗi nhanh.

Sau vài tuần production ghi nhận:

- memory và CPU tăng đáng kể vào giờ cao điểm,
- backend telemetry bắt đầu throttle/drop dữ liệu,
- số lượng time series tăng rất nhanh,
- dashboard query chậm và chi phí observability tăng mạnh,
- log đôi lúc chứa access token, email người dùng và query parameter nhạy cảm,
- một số request upload hoặc export lớn làm middleware allocate nhiều MB,
- endpoint có ID động như `/api/employees/{guid}` tạo rất nhiều metric dimensions khác nhau.

API chạy trên 8 instance và đạt 1.000–2.000 request/giây ở peak. Business yêu cầu vẫn phải truy vết incident theo tenant/request, nhưng telemetry không được trở thành nguyên nhân làm giảm availability hoặc lộ secret/PII.

## Đoạn code cần review

```csharp
public sealed class RequestTelemetryMiddleware
{
    private static readonly ConcurrentDictionary<string, long> RequestCounts = new();

    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

    public RequestTelemetryMiddleware(
        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        var originalBody = context.Response.Body;

        await using var responseBuffer = new MemoryStream();
        context.Response.Body = responseBuffer;

        var routeKey = context.Request.Path + context.Request.QueryString;
        var user = context.User.Identity?.Name ?? "anonymous";
        var authorization = context.Request.Headers.Authorization.ToString();

        RequestCounts.AddOrUpdate(
            $"{routeKey}|{user}",
            1,
            (_, count) => count + 1);

        Activity.Current?.SetTag("http.url", context.Request.GetDisplayUrl());
        Activity.Current?.SetTag("enduser.id", user);
        Activity.Current?.SetTag("authorization", authorization);

        await _next(context);

        responseBuffer.Position = 0;
        var body = await new StreamReader(responseBuffer)
            .ReadToEndAsync();

        var elapsedMs = Stopwatch.GetElapsedTime(started).TotalMilliseconds;

        _logger.LogInformation(
            "{Method} {Url} User={User} Authorization={Authorization} Status={Status} DurationMs={DurationMs} Response={Response}",
            context.Request.Method,
            context.Request.GetDisplayUrl(),
            user,
            authorization,
            context.Response.StatusCode,
            elapsedMs,
            body);

        responseBuffer.Position = 0;
        await responseBuffer.CopyToAsync(originalBody);
        context.Response.Body = originalBody;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong middleware lifecycle.
2. Xác định rủi ro security, memory, performance và telemetry cardinality.
3. Giải thích production impact dưới tải cao hoặc response lớn.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation observability an toàn và có giới hạn hơn.
6. Giải thích cách test response lớn, exception, streaming response và dữ liệu nhạy cảm.
7. Đề xuất logs, traces và metrics nào thực sự nên giữ ở production.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### 1. Ghi access token vào log và trace

**Problem:** Header `Authorization` được ghi nguyên văn vào log và Activity tag.  
**Why it happens:** Middleware coi header là diagnostic context thông thường.  
**Production impact:** Credential có thể xuất hiện trong log backend, trace storage, export hoặc support tooling; người có quyền đọc telemetry có thể thấy secret.  
**Severity:** Critical  
**Recommended fix:** Không log credential. Redact/drop hoàn toàn `Authorization`, cookie, API key và các header nhạy cảm.

### 2. Metric key có cardinality gần như không giới hạn

**Problem:** `RequestCounts` dùng raw path, query string và username làm key.  
**Why it happens:** Mỗi ID, query value hoặc user có thể tạo một key mới.  
**Production impact:** Dictionary tăng không giới hạn theo thời gian, gây memory growth; nếu cùng dimensions được gửi sang metrics backend thì số time series cũng tăng mạnh.  
**Severity:** Critical  
**Recommended fix:** Chỉ dùng dimensions cardinality thấp, ví dụ route template, HTTP method, status-class; không dùng user ID, request ID, raw URL hoặc query value làm metric label.

### 3. Buffer toàn bộ response trong memory

**Problem:** Mọi response đều được ghi vào `MemoryStream` rồi đọc thành `string`.  
**Why it happens:** Middleware muốn log full response body.  
**Production impact:** Response lớn tạo allocation lớn, tăng GC pressure, latency và nguy cơ OOM khi concurrency cao.  
**Severity:** High  
**Recommended fix:** Không buffer full response mặc định. Chỉ capture payload nhỏ theo allowlist/content type và hard size limit; ưu tiên metadata thay vì body.

### 4. Middleware phá semantics của streaming

**Problem:** Response không được gửi tới client cho tới khi downstream hoàn tất và buffer được copy ngược lại.  
**Why it happens:** `context.Response.Body` bị thay bằng `MemoryStream`.  
**Production impact:** SSE, streaming file, progressive response hoặc response rất lớn mất khả năng stream và time-to-first-byte tăng mạnh.  
**Severity:** High  
**Recommended fix:** Không intercept body cho streaming endpoint; nếu cần capture thì dùng tee/limited stream rất cẩn thận hoặc tắt body logging cho các route này.

### 5. Response body không được khôi phục nếu pipeline ném exception

**Problem:** `context.Response.Body = originalBody` chỉ chạy ở cuối happy path.  
**Why it happens:** Không có `try/finally` quanh việc thay response stream.  
**Production impact:** Exception path có thể để context ở trạng thái không mong muốn và làm error middleware khó xử lý đúng response stream.  
**Severity:** High  
**Recommended fix:** Khôi phục body trong `finally`; logging exception nên phối hợp với centralized exception handling.

### 6. Raw URL/query string được ghi vào telemetry

**Problem:** `GetDisplayUrl()` và `QueryString` được dùng nguyên bản.  
**Why it happens:** Team muốn log request chính xác.  
**Production impact:** Query parameter có thể chứa email, token, search text hoặc dữ liệu business nhạy cảm; đồng thời làm cardinality trace/log tăng.  
**Severity:** High  
**Recommended fix:** Log route template và các query field allowlisted/redacted; không ghi toàn bộ URL nếu không cần.

### 7. User identity được dùng như metric dimension

**Problem:** Username nằm trong key counter và trace tag cho mọi request.  
**Why it happens:** Muốn phân tích usage theo user trực tiếp từ telemetry.  
**Production impact:** Cardinality lớn, tăng chi phí và có thể tạo privacy concern.  
**Severity:** High  
**Recommended fix:** Metric không gắn user ID. Nếu cần audit theo user, dùng audit/event store riêng với retention/access policy phù hợp; trace chỉ gắn identity khi thật sự cần và đã qua privacy review.

### 8. `ConcurrentDictionary` là metric store tự chế không có lifecycle

**Problem:** Counter sống suốt process, không có eviction/export/reset.  
**Why it happens:** Dùng dictionary như một metrics backend đơn giản.  
**Production impact:** Memory chỉ tăng và dữ liệu không nhất quán giữa 8 instance.  
**Severity:** Medium  
**Recommended fix:** Dùng metrics API/backend phù hợp; giữ process-local aggregation với bounded dimensions và để monitoring system tổng hợp đa instance.

### 9. Logging full body ở `Information` cho mọi request

**Problem:** Mọi response đều tạo log event lớn.  
**Why it happens:** Không có sampling hoặc route policy.  
**Production impact:** CPU serialize, network egress, storage cost và ingestion throttling tăng; signal quan trọng bị chìm trong noise.  
**Severity:** Medium  
**Recommended fix:** Structured access log ngắn gọn ở mức phù hợp; body logging chỉ bật có mục tiêu, sampling và giới hạn kích thước.

### 10. Thiếu duration/error instrumentation khi exception xảy ra

**Problem:** Duration và status chỉ được log sau khi `_next` thành công.  
**Why it happens:** Happy-path instrumentation.  
**Production impact:** Các request lỗi nhất lại thiếu telemetry quan trọng.  
**Severity:** Medium  
**Recommended fix:** Đo latency trong `finally`; record outcome/error class mà không duplicate exception stack ở nhiều layer.

## Phiên bản code đề xuất

```csharp
public sealed class RequestTelemetryMiddleware
{
    private static readonly Meter Meter = new("Company.Api");
    private static readonly Histogram<double> DurationMs =
        Meter.CreateHistogram<double>("http.server.duration.ms");

    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

    public RequestTelemetryMiddleware(
        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? failure = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            failure = ex;
            throw;
        }
        finally
        {
            var elapsedMs = Stopwatch
                .GetElapsedTime(started)
                .TotalMilliseconds;

            var endpoint = context.GetEndpoint();
            var route = endpoint is RouteEndpoint routeEndpoint
                ? routeEndpoint.RoutePattern.RawText ?? "unknown"
                : "unmatched";

            var status = context.Response.StatusCode;
            var outcome = failure is null ? "completed" : "exception";

            DurationMs.Record(
                elapsedMs,
                new KeyValuePair<string, object?>("http.method", context.Request.Method),
                new KeyValuePair<string, object?>("http.route", route),
                new KeyValuePair<string, object?>("http.status_class", $"{status / 100}xx"));

            _logger.LogInformation(
                "HTTP request completed Method={Method} Route={Route} Status={Status} DurationMs={DurationMs} Outcome={Outcome} TraceId={TraceId}",
                context.Request.Method,
                route,
                status,
                elapsedMs,
                outcome,
                Activity.Current?.TraceId.ToString());
        }
    }
}
```

Nếu cần body diagnostics cho một số endpoint, nên triển khai một component riêng với allowlist route/content type, giới hạn vài KB phù hợp policy, redaction và sampling; không bật mặc định cho mọi request.

## Trade-offs

- Metric cardinality thấp giảm khả năng drill-down trực tiếp theo user, nhưng giúp hệ thống metrics ổn định và rẻ hơn.
- Không log full body làm forensic ít chi tiết hơn; bù lại dùng trace ID, audit event chuyên biệt và targeted diagnostics khi cần.
- Sampling giảm ingestion cost nhưng có thể bỏ qua request hiếm; error traces và security/audit event có thể có sampling policy khác.
- Route template phù hợp aggregation; raw URL chỉ nên xuất hiện trong controlled diagnostic flow đã redaction.

## Cách kiểm thử

1. **Load test:** 1.000–2.000 RPS với hàng trăm nghìn user/path IDs khác nhau; xác nhận memory và số metric dimensions không tăng tuyến tính theo ID.
2. **Security test:** gửi bearer token, email, secret query parameter; xác nhận không xuất hiện trong log/trace.
3. **Large-response test:** file download hoặc response hàng trăm MB; xác nhận middleware không buffer toàn bộ payload và time-to-first-byte không bị phá.
4. **Failure-path test:** endpoint ném exception; xác nhận latency/outcome vẫn được ghi và error pipeline vẫn hoạt động.
5. **Streaming test:** endpoint streaming; xác nhận dữ liệu được flush tới client bình thường.

## Quan sát trong production

Nên theo dõi:

- request rate theo route template,
- latency histogram theo route/method/status class,
- error rate,
- process memory/GC allocation rate,
- telemetry export queue/drop/throttle,
- số active metric series ở backend,
- average log event size và ingestion volume,
- trace sampling rate,
- alert khi telemetry exporter failure hoặc cardinality tăng bất thường.

# Code Review Challenge 2 — `ExecuteUpdateAsync` cập nhật DB nhưng entity đang track vẫn ghi đè dữ liệu mới

**Chủ đề:** EF Core tracking, query execution, transaction/correctness, concurrency, performance  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một application service quản lý employee status. Team vừa tối ưu thao tác “deactivate toàn bộ nhân viên của một department” bằng bulk update để tránh load hàng nghìn entity vào memory.

Trong cùng workflow, service cũng load department owner để cập nhật `LastReviewedAt` và ghi audit metadata. Sau khi chuyển sang bulk update, production thỉnh thoảng ghi nhận owner vẫn trở lại trạng thái `Active` dù câu bulk update vừa đặt toàn bộ department thành `Inactive`.

Hiện tượng không xảy ra ở mọi request. Nó thường xuất hiện khi owner đã được load/tracked trước bulk update và sau đó có thêm thay đổi khác được `SaveChangesAsync` trong cùng `DbContext`.

Business yêu cầu:

- tất cả employee thuộc department phải thành `Inactive`,
- owner cũng phải được cập nhật `LastReviewedAt`,
- không được phát sinh lost update âm thầm,
- thao tác phải xử lý được concurrency với workflow khác đang chỉnh sửa employee.

## Đoạn code cần review

```csharp
public sealed class DepartmentService
{
    private readonly AppDbContext _db;
    private readonly ILogger<DepartmentService> _logger;

    public DepartmentService(
        AppDbContext db,
        ILogger<DepartmentService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task DeactivateAsync(
        Guid departmentId,
        Guid ownerId,
        CancellationToken cancellationToken)
    {
        var owner = await _db.Employees
            .SingleAsync(
                x => x.Id == ownerId && x.DepartmentId == departmentId,
                cancellationToken);

        var now = DateTime.UtcNow;

        var affected = await _db.Employees
            .Where(x => x.DepartmentId == departmentId)
            .ExecuteUpdateAsync(
                setters => setters
                    .SetProperty(x => x.Status, EmployeeStatus.Inactive)
                    .SetProperty(x => x.UpdatedAt, now),
                cancellationToken);

        owner.LastReviewedAt = now;
        owner.UpdatedAt = now;

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Deactivated department {DepartmentId}. Affected={Affected} Owner={OwnerId}",
            departmentId,
            affected,
            ownerId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problem giữa bulk update và Change Tracker.
2. Phân tích những gì thực sự xảy ra trong database và trong trạng thái entity đang track.
3. Giải thích production impact, bao gồm lost update hoặc trạng thái bị ghi đè.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation rõ ràng về transaction và tracking semantics.
6. Giải thích cách test tracked-state conflict và concurrent update.
7. Đề xuất logs, traces và database observations phù hợp.

## Câu hỏi gợi mở

1. `ExecuteUpdateAsync` có cập nhật object `owner` đang nằm trong Change Tracker không?
2. Sau bulk update, `owner.Status` trong memory đang là giá trị nào?
3. Khi `SaveChangesAsync` chạy sau đó, EF có thể phát sinh `UPDATE` cho owner với những property nào?
4. Hai câu lệnh database có đang nằm trong cùng atomic transaction theo business requirement không?
5. Nếu workflow khác đồng thời sửa owner, invariant được bảo vệ bằng gì?

## Gợi ý

### Gợi ý 1

Hãy tách hai “thế giới”: **database state** sau bulk SQL và **tracked entity state** trong `DbContext`.

### Gợi ý 2

## Kết quả code review tham khảo

### 1. Tracked `owner` không tự đồng bộ sau `ExecuteUpdateAsync`

**Problem:** Database đã đặt `owner.Status = Inactive`, nhưng object `owner` trong Change Tracker vẫn giữ trạng thái cũ đã load trước đó.  
**Why it happens:** Bulk update thực thi trực tiếp ở database và không cập nhật tracked entity state trong context hiện tại.  
**Production impact:** Application tiếp tục ra quyết định dựa trên stale state; thay đổi sau đó có thể ghi đè một phần dữ liệu vừa bulk update.  
**Severity:** Critical  
**Recommended fix:** Không trộn tracked entity stale với bulk update trong cùng unit of work mà không refresh/clear tracker hoặc tái cấu trúc flow.

### 2. `SaveChangesAsync` có thể ghi đè giá trị vừa bulk update tùy model/update behavior

**Problem:** `owner` vẫn được tracked từ trước bulk update rồi tiếp tục được sửa.  
**Why it happens:** Original/current values trong tracker không biết DB đã thay đổi bên ngoài tracker. Tùy cấu hình/model và properties được đánh dấu modified, update sau có thể tạo lost update.  
**Production impact:** Owner có thể trở lại trạng thái cũ hoặc một giá trị mới ở DB bị ghi đè mà không có cảnh báo.  
**Severity:** Critical  
**Recommended fix:** Refresh entity từ DB trước khi tiếp tục tracked update, hoặc thực hiện owner update bằng bulk/conditional update tương thích, hoặc tách context/boundary rõ ràng.

### 3. Hai thao tác không thể hiện một business transaction rõ ràng

**Problem:** Bulk deactivate và owner review update là hai database command tách biệt.  
**Why it happens:** Code dựa vào flow tuần tự nhưng không nói rõ atomicity requirement.  
**Production impact:** Nếu bulk update thành công nhưng `SaveChangesAsync` thất bại, department bị deactivate nhưng review metadata chưa được cập nhật.  
**Severity:** High  
**Recommended fix:** Nếu business yêu cầu atomicity, mở explicit transaction bao quanh cả hai thao tác hoặc thiết kế state machine/recovery phù hợp.

### 4. Không có concurrency policy cho owner

**Problem:** Workflow khác có thể chỉnh owner đồng thời.  
**Why it happens:** Không có concurrency token hoặc conditional update semantics được thể hiện.  
**Production impact:** Last-write-wins có thể làm mất thay đổi hợp lệ của workflow khác.  
**Severity:** High  
**Recommended fix:** Dùng optimistic concurrency token/row version hoặc conditional update theo version khi invariant cần phát hiện conflict.

### 5. Không xác nhận `ownerId` là owner business thực sự

**Problem:** Code chỉ kiểm tra employee thuộc department, không chứng minh đó là owner theo domain model.  
**Why it happens:** `ownerId` do caller truyền vào và query chỉ filter DepartmentId.  
**Production impact:** Một employee bất kỳ trong department có thể được cập nhật `LastReviewedAt` nếu caller sai hoặc bị lạm dụng.  
**Severity:** High  
**Recommended fix:** Resolve owner từ trusted department relationship hoặc validate role/invariant ở server.

### 6. Không kiểm tra số lượng `affected` theo expectation

**Problem:** Bulk update trả số row bị tác động nhưng code chỉ log.  
**Why it happens:** Không có sanity/invariant check.  
**Production impact:** Department sai ID, filter sai hoặc dữ liệu không như mong đợi có thể đi qua mà không bị phát hiện.  
**Severity:** Medium  
**Recommended fix:** Định nghĩa expectation phù hợp; với zero rows hoặc abnormal count, log/raise domain error tùy business semantics.

### 7. Dùng cùng timestamp nhưng không có source-of-time abstraction

**Problem:** `DateTime.UtcNow` khó kiểm soát trong test và nhiều workflow khác nhau có thể dùng clock khác nhau.  
**Why it happens:** Time được lấy trực tiếp trong service.  
**Production impact:** Không nghiêm trọng về correctness chính, nhưng làm test boundary/time semantics khó hơn.  
**Severity:** Low  
**Recommended fix:** Với domain quan trọng về thời gian, dùng `TimeProvider` hoặc clock abstraction.

### 8. Observability chưa đủ để phát hiện stale/lost-update conflict

**Problem:** Log chỉ có affected count.  
**Why it happens:** Không record version/concurrency conflict hoặc before/after state.  
**Production impact:** Khi owner bị trạng thái bất thường, khó chứng minh update nào ghi đè update nào.  
**Severity:** Medium  
**Recommended fix:** Ghi operation ID, department ID, owner ID, affected count, concurrency conflict count và audit state transition cần thiết.

## Phiên bản code đề xuất

Một cách đơn giản là tránh giữ tracked entity stale qua bulk update. Ví dụ dùng transaction và cập nhật owner bằng câu lệnh có điều kiện riêng, sau khi resolve owner từ department.

```csharp
public sealed class DepartmentService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<DepartmentService> _logger;

    public DepartmentService(
        AppDbContext db,
        TimeProvider timeProvider,
        ILogger<DepartmentService> logger)
    {
        _db = db;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    public async Task DeactivateAsync(
        Guid departmentId,
        CancellationToken cancellationToken)
    {
        var now = _timeProvider.GetUtcNow().UtcDateTime;

        var ownerId = await _db.Departments
            .AsNoTracking()
            .Where(x => x.Id == departmentId)
            .Select(x => x.OwnerEmployeeId)
            .SingleAsync(cancellationToken);

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var affected = await _db.Employees
            .Where(x => x.DepartmentId == departmentId)
            .ExecuteUpdateAsync(
                setters => setters
                    .SetProperty(x => x.Status, EmployeeStatus.Inactive)
                    .SetProperty(x => x.UpdatedAt, now),
                cancellationToken);

        var ownerAffected = await _db.Employees
            .Where(x => x.Id == ownerId && x.DepartmentId == departmentId)
            .ExecuteUpdateAsync(
                setters => setters
                    .SetProperty(x => x.LastReviewedAt, now)
                    .SetProperty(x => x.UpdatedAt, now),
                cancellationToken);

        if (ownerAffected != 1)
            throw new InvalidOperationException("Department owner was not updated.");

        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Department deactivated. DepartmentId={DepartmentId} OwnerId={OwnerId} Affected={Affected}",
            departmentId,
            ownerId,
            affected);
    }
}
```

Nếu owner update cần optimistic concurrency theo version hiện có, dùng conditional predicate theo concurrency token/version và coi `0 rows affected` là conflict cần xử lý thay vì last-write-wins.

Một lựa chọn khác là bulk update xong gọi `ChangeTracker.Clear()` rồi query lại owner trước khi cập nhật bằng tracked entity. Tuy nhiên boundary đó phải rất rõ để không vô tình detach những entity khác đang cần được save.

## Trade-offs

- Bulk update giảm memory và round-trip so với load toàn bộ entity, nhưng bỏ qua Change Tracker nên developer phải hiểu rõ stale-state semantics.
- Explicit transaction tăng atomicity nhưng có thể kéo dài lock duration; transaction nên ngắn và không chứa external I/O.
- `ChangeTracker.Clear()` đơn giản nhưng ảnh hưởng toàn bộ tracked graph trong context; context nhỏ/scope rõ ràng thường an toàn hơn.
- Conditional update theo concurrency token rõ về conflict nhưng yêu cầu caller quyết định retry, reject hay merge.
- Nếu domain logic cho từng employee phức tạp và cần domain event per entity, bulk update có thể không còn là lựa chọn phù hợp.

## Cách kiểm thử

1. **Integration test stale tracker:** load owner tracked với `Active`, chạy bulk update rồi tiếp tục cập nhật owner; xác nhận bản sửa không làm owner trở lại `Active`.
2. **Atomicity test:** inject failure ở owner update; nếu requirement atomic, xác nhận bulk deactivate rollback.
3. **Concurrency test:** workflow khác sửa owner/version đồng thời; xác nhận conflict được phát hiện thay vì silent last-write-wins.
4. **Large department test:** hàng chục nghìn employee; xác nhận memory không tăng do materialize toàn bộ entity.
5. **Correct-owner test:** department owner relationship sai/missing; xác nhận operation fail rõ ràng và không cập nhật employee tùy ý.

## Quan sát trong production

Nên theo dõi:

- bulk update affected rows,
- operation duration,
- transaction duration,
- concurrency conflict count,
- DB lock/deadlock/timeout,
- unexpected zero-row update,
- audit state transition `Department -> Inactive`,
- trace span cho từng database command,
- alert nếu owner update fail sau khi workflow bắt đầu.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn `ExecuteUpdateAsync` thay vì load entity + `SaveChangesAsync`?
2. Nếu cần phát domain event cho từng employee bị deactivate, bulk update còn phù hợp không?
3. Nếu transaction bao quanh 100.000-row update gây lock lâu, bạn sẽ cân bằng atomicity và availability như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Observability cũng là một subsystem có giới hạn tài nguyên; metric cardinality và payload size phải được thiết kế có chủ đích.
- Không đưa secret, credential hoặc PII không cần thiết vào logs/traces.
- Metric labels nên cardinality thấp; correlation chi tiết nên dựa vào trace ID/audit store thay vì user/raw URL dimensions.
- Bulk update trực tiếp ở database có thể không đồng bộ với entity đang được EF Core Change Tracker giữ trong memory.
- Khi trộn bulk SQL và tracked updates, cần transaction boundary, tracker strategy và concurrency semantics rõ ràng.

## Mẫu tư duy cần nhớ

- Treat observability as production workload, not free diagnostics.
- Keep metric dimensions bounded; use trace IDs for detail.
- Never assume database bulk updates refresh tracked objects.
- Define atomicity and concurrency policy before optimizing persistence.
- Test failure and stale-state paths, not only happy path.
