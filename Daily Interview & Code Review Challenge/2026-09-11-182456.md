# Code Review Challenge 1 — Upload ảnh chạy ổn ở staging nhưng có thể ghi đè file, vượt tenant boundary và làm đầy disk production

**Chủ đề:** C#/.NET 8, ASP.NET Core, file upload security, authorization, path traversal, resource exhaustion, content validation, cancellation, static file serving, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép nhân viên của từng tenant upload ảnh dùng trong campaign marketing. File được lưu trên local disk của application và sau đó được phục vụ qua static files.

Yêu cầu:

- chỉ user đã được cấp quyền trong tenant tương ứng mới được upload;
- chỉ cho phép JPEG/PNG;
- file tối đa 8 MB;
- nhiều user có thể upload đồng thời;
- tên file từ client không được quyết định physical path trên server;
- một upload lỗi hoặc client disconnect không được để lại file dở dang;
- deployment chạy nhiều application instances;
- dữ liệu không được vô tình public nếu chưa qua business approval;
- operations cần biết upload rate, rejected uploads, size distribution, disk usage và security failures.

Sau khi traffic tăng, team quan sát thấy:

- disk của một instance tăng nhanh hơn các instance khác;
- đôi lúc hai campaign cùng tham chiếu tới một file name nhưng nội dung không giống nhau;
- support phát hiện user có thể thay đổi `tenantId` trên URL;
- một vài request upload rất lớn giữ connection lâu dù business chỉ cho phép 8 MB;
- file vừa upload có thể truy cập trực tiếp dưới `/uploads/...`;
- team cho rằng `[Authorize]` và kiểm tra extension `.jpg/.png` đã đủ an toàn.

## Đoạn code cần review

```csharp
[ApiController]
[Authorize]
[Route("api/tenants/{tenantId}/assets")]
public sealed class CampaignAssetsController : ControllerBase
{
    private readonly IWebHostEnvironment _environment;
    private readonly AppDbContext _db;

    public CampaignAssetsController(
        IWebHostEnvironment environment,
        AppDbContext db)
    {
        _environment = environment;
        _db = db;
    }

    [HttpPost]
    [RequestFormLimits(MultipartBodyLengthLimit = long.MaxValue)]
    public async Task<IActionResult> Upload(
        string tenantId,
        IFormFile file)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
        if (extension is not ".jpg" and not ".jpeg" and not ".png")
            return BadRequest("Unsupported file type");

        var uploadRoot = Path.Combine(
            _environment.WebRootPath,
            "uploads",
            tenantId);

        Directory.CreateDirectory(uploadRoot);

        var path = Path.Combine(uploadRoot, file.FileName);

        await using (var output = System.IO.File.Create(path))
        {
            await file.CopyToAsync(output);
        }

        var asset = new CampaignAsset
        {
            TenantId = tenantId,
            FileName = file.FileName,
            ContentType = file.ContentType,
            PhysicalPath = path,
            CreatedAtUtc = DateTime.UtcNow
        };

        _db.CampaignAssets.Add(asset);
        await _db.SaveChangesAsync();

        return Ok(new
        {
            asset.Id,
            Url = $"/uploads/{tenantId}/{file.FileName}"
        });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và security trong upload flow.
2. Xác định các vấn đề reliability, performance và maintainability.
3. Giải thích production impact, đặc biệt dưới concurrent uploads, malicious input và deployment nhiều instances.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa nhưng không thêm hạ tầng phức tạp nếu chưa có requirement.
6. Giải thích testing cho authorization, file validation, size limits, concurrency và failure path.
7. Đề xuất production telemetry để phát hiện abuse, disk pressure và upload failures.

## Câu hỏi gợi mở

1. `[Authorize]` chứng minh user đã đăng nhập, nhưng có chứng minh user được phép thao tác với `tenantId` trên route không?
2. `file.FileName` là dữ liệu do ai kiểm soát và có nên tham gia physical path trực tiếp không?
3. Extension `.jpg` có chứng minh bytes bên trong thực sự là JPEG không?
4. `MultipartBodyLengthLimit = long.MaxValue` tương tác thế nào với requirement file tối đa 8 MB và resource exhaustion?
5. Local disk của sáu application instances có phải một shared durable store hay không?

## Gợi ý

### Gợi ý 1

Primary risk là **trusting client-controlled metadata at security and storage boundaries**: tenant identifier, filename, extension và content type đều cần được xử lý theo trust model rõ ràng.

### Gợi ý 2

Review flow theo thứ tự: authenticate → authorize resource → reject oversized request → validate actual content → generate server-owned storage key → persist safely → publish/access-control separately.

## Kết quả code review tham khảo

### Critical — Authentication không thay thế tenant-level authorization

**Vấn đề:**  
Controller có `[Authorize]`, nhưng `tenantId` từ URL được dùng trực tiếp mà không kiểm tra caller có quyền trên tenant đó.

**Tại sao xảy ra:**  
Authentication chỉ chứng minh identity. Resource authorization cần kiểm tra identity đó có permission đối với tenant/campaign cụ thể.

**Ảnh hưởng production:**  
Một authenticated user có thể thay `tenantId` để ghi asset vào tenant khác, dẫn tới broken access control và cross-tenant data corruption/exposure.

**Cách sửa:**  
Resolve tenant membership/permission từ trusted authorization context hoặc dùng policy/resource-based authorization trước khi xử lý file. Không lấy tenant ownership từ request rồi tin trực tiếp.

### Critical — Client filename được dùng trực tiếp để tạo physical path

**Vấn đề:**  
`file.FileName` được đưa vào `Path.Combine` và trở thành tên file thật trên server.

**Tại sao xảy ra:**  
Filename trong multipart request là untrusted input. Nó có thể chứa path components, platform-specific separators hoặc tên trùng với file khác.

**Ảnh hưởng production:**  
Tùy normalization/platform, có nguy cơ path traversal/path manipulation; ngoài ra filename trùng có thể ghi đè nội dung upload trước và phá referential integrity giữa metadata với file.

**Cách sửa:**  
Không dùng client filename làm storage key. Chỉ giữ một sanitized display name nếu business cần; physical object key phải do server sinh, ví dụ GUID/random ID, và path sau normalize phải nằm trong root dự kiến.

### High — File type validation chỉ dựa trên extension và client-provided `ContentType`

**Vấn đề:**  
Code chỉ kiểm tra `.jpg/.jpeg/.png`; `ContentType` lại được lưu trực tiếp từ request.

**Tại sao xảy ra:**  
Cả filename lẫn MIME header đều do client kiểm soát và không chứng minh actual bytes.

**Ảnh hưởng production:**  
Non-image hoặc crafted/polyglot content có thể được lưu rồi phục vụ như trusted asset. Nếu static serving/content-sniffing/configuration không chặt, risk có thể mở rộng thành active-content delivery.

**Cách sửa:**  
Validate signature/magic bytes và tốt hơn là decode ảnh bằng thư viện image parser an toàn nếu business thật sự cần image. Khi cần, re-encode ảnh sang server-controlled format. Không suy ra trust chỉ từ extension/MIME header.

### High — Request size limit bị mở vô hạn trái requirement 8 MB

**Vấn đề:**  
`MultipartBodyLengthLimit = long.MaxValue` cho phép request cực lớn đi sâu vào pipeline.

**Tại sao xảy ra:**  
Application-level check chỉ kiểm tra `file.Length == 0`, không enforce maximum size trước/đúng lúc parsing request body.

**Ảnh hưởng production:**  
Attacker hoặc client lỗi có thể giữ connection, tiêu tốn temp storage/memory/disk/network và làm giảm capacity của toàn instance.

**Cách sửa:**  
Đặt request/multipart limit phù hợp requirement, kiểm tra `file.Length <= 8 MB`, và đồng bộ giới hạn ở reverse proxy/ingress nếu có. Reject càng sớm càng tốt.

### High — File được ghi vào public `WebRootPath` trước khi business approval

**Vấn đề:**  
Binary được đặt dưới `wwwroot/uploads` và response trả URL static trực tiếp.

**Tại sao xảy ra:**  
Storage boundary và publication boundary bị gộp thành một. Static File Middleware có thể phục vụ file mà không đi qua application authorization/approval logic.

**Ảnh hưởng production:**  
Asset chưa approved hoặc asset của tenant private có thể bị truy cập nếu URL bị biết/đoán/chia sẻ.

**Cách sửa:**  
Lưu private upload ngoài public web root hoặc private object storage. Chỉ publish/copy/promote sang public delivery path sau approval, hoặc phục vụ qua authorized endpoint/signed URL theo requirement.

### High — Local disk không phù hợp nếu asset phải nhất quán trên nhiều instances

**Vấn đề:**  
Mỗi application instance ghi file vào local filesystem của chính nó.

**Tại sao xảy ra:**  
Horizontal scale không biến local disk thành shared store. Request sau có thể hit instance khác không có file; restart/redeployment cũng có thể làm mất dữ liệu tùy hosting model.

**Ảnh hưởng production:**  
Asset có thể “lúc có lúc không”, disk usage lệch giữa instances và deployment/restart tạo data loss hoặc stale files.

**Cách sửa:**  
Nếu asset là durable/shared data, dùng shared object storage phù hợp như Azure Blob Storage. Nếu local storage chỉ là temporary staging, phải mô hình hóa rõ lifecycle và không trả nó như durable URL.

### High — File và database metadata không có failure-safe boundary

**Vấn đề:**  
File được ghi xong trước rồi mới `SaveChangesAsync`.

**Tại sao xảy ra:**  
Filesystem/object storage và SQL là hai resource boundaries khác nhau, không có atomic transaction chung.

**Ảnh hưởng production:**  
DB save fail để lại orphan file; ngược lại nếu sau này đổi thứ tự, DB row có thể trỏ tới file chưa tồn tại. Retry với cùng filename còn có thể overwrite.

**Cách sửa:**  
Dùng server-generated immutable storage key, persist trạng thái upload rõ ràng (`Pending`/`Ready`), cleanup orphan theo deterministic process, hoặc upload temporary key rồi promote sau metadata commit. Không giả vờ cần distributed transaction cho một workflow có thể thiết kế idempotent/compensatable.

### Medium — Cancellation không được propagate

**Vấn đề:**  
Action không nhận `CancellationToken`; `CopyToAsync` và `SaveChangesAsync` không nhận request-abort token.

**Tại sao xảy ra:**  
Client disconnect không tự động cancel mọi I/O nếu token không được propagate.

**Ảnh hưởng production:**  
Server có thể tiếp tục ghi file hoặc DB work sau khi caller đã rời đi, đặc biệt tốn kém với upload lớn.

**Cách sửa:**  
Nhận `CancellationToken`/dùng `HttpContext.RequestAborted` và propagate đến operations hỗ trợ token. Đồng thời cleanup partial file trên cancellation/failure.

### Medium — Concurrent filename collision có thể tạo overwrite/race

**Vấn đề:**  
`File.Create(path)` dùng cùng path cho cùng tenant + filename và truncate file hiện có.

**Tại sao xảy ra:**  
Storage key không unique và operation không có create-only semantics.

**Ảnh hưởng production:**  
Hai uploads đồng thời có thể tranh chấp/ghi đè; metadata rows có thể cùng chỉ tới một path nhưng business nghĩ đó là hai assets khác nhau.

**Cách sửa:**  
Dùng immutable unique server-generated key. Nếu deduplication là requirement, làm bằng content hash/version model có concurrency semantics rõ thay vì filename.

### Medium — Không có cleanup cho partial file khi copy thất bại

**Vấn đề:**  
Nếu request bị ngắt, disk đầy hoặc I/O exception giữa chừng, partial file có thể còn lại.

**Tại sao xảy ra:**  
Write trực tiếp vào final path và không có temporary-file cleanup/finalization step.

**Ảnh hưởng production:**  
Disk leak, corrupted assets và khó phân biệt file hoàn chỉnh với incomplete upload.

**Cách sửa:**  
Write vào generated temporary key/path, validate đầy đủ, sau đó finalize atomically trong cùng storage system khi có thể; cleanup trong failure path và có background reconciliation cho orphan hiếm gặp.

### Low — Thiếu telemetry cho security và capacity signals

**Vấn đề:**  
Flow không emit structured signals cho rejected size/type, authorization denial, upload duration, disk/object-store errors hoặc orphan cleanup.

**Tại sao xảy ra:**  
Observability chưa được coi là một phần của upload design.

**Ảnh hưởng production:**  
Team chỉ biết disk tăng hoặc user báo lỗi, khó phân biệt abuse, traffic growth và software bug.

**Cách sửa:**  
Theo dõi metrics/traces có cardinality kiểm soát cho accepted/rejected uploads, bytes, duration, authorization failures, storage errors, cleanup và storage utilization.

## Phiên bản đề xuất

Một hướng phù hợp cho deployment nhiều instances là dùng private object storage với server-generated key. Ví dụ dưới đây minh họa boundary; `IAssetStorage` có thể được implement bằng Azure Blob Storage private container.

```csharp
[ApiController]
[Authorize]
[Route("api/tenants/{tenantId}/assets")]
public sealed class CampaignAssetsController : ControllerBase
{
    private const long MaxFileBytes = 8 * 1024 * 1024;

    private readonly IAuthorizationService _authorization;
    private readonly IAssetStorage _storage;
    private readonly AppDbContext _db;

    public CampaignAssetsController(
        IAuthorizationService authorization,
        IAssetStorage storage,
        AppDbContext db)
    {
        _authorization = authorization;
        _storage = storage;
        _db = db;
    }

    [HttpPost]
    [RequestFormLimits(MultipartBodyLengthLimit = MaxFileBytes)]
    public async Task<IActionResult> Upload(
        string tenantId,
        IFormFile file,
        CancellationToken cancellationToken)
    {
        var auth = await _authorization.AuthorizeAsync(
            User,
            tenantId,
            "UploadCampaignAsset");

        if (!auth.Succeeded)
            return Forbid();

        if (file.Length <= 0 || file.Length > MaxFileBytes)
            return BadRequest("Invalid file size");

        await using var input = file.OpenReadStream(MaxFileBytes);

        var detected = await ImageContentValidator.DetectAsync(
            input,
            cancellationToken);

        if (detected is not ImageKind.Jpeg and not ImageKind.Png)
            return BadRequest("Unsupported file type");

        input.Position = 0;

        var assetId = Guid.NewGuid();
        var storageKey = $"{tenantId}/{assetId:N}.{detected.Extension()}";

        await _storage.UploadPrivateAsync(
            storageKey,
            input,
            detected.ContentType(),
            cancellationToken);

        try
        {
            var asset = new CampaignAsset
            {
                Id = assetId,
                TenantId = tenantId,
                StorageKey = storageKey,
                OriginalFileName = Path.GetFileName(file.FileName),
                ContentType = detected.ContentType(),
                Status = AssetStatus.PendingApproval,
                CreatedAtUtc = DateTime.UtcNow
            };

            _db.CampaignAssets.Add(asset);
            await _db.SaveChangesAsync(cancellationToken);

            return CreatedAtAction(
                nameof(GetMetadata),
                new { tenantId, id = asset.Id },
                new { asset.Id, asset.Status });
        }
        catch
        {
            await _storage.TryDeleteAsync(storageKey, CancellationToken.None);
            throw;
        }
    }

    [HttpGet("{id:guid}")]
    public IActionResult GetMetadata(string tenantId, Guid id)
        => throw new NotImplementedException();
}
```

Trong production, content validation nên dùng implementation đã được kiểm thử kỹ; nếu parser cần seek nhưng stream không seekable, có thể spool bounded payload tối đa 8 MB vào temporary storage/buffer có giới hạn. Cleanup trong `catch` là best-effort; vẫn nên có reconciliation job để xóa orphan nếu process crash trước cleanup.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách bốn concerns: authorization, validation, durable private storage và publication. Client filename chỉ còn là display metadata, không còn quyết định storage path. Storage key immutable giúp tránh overwrite và làm retry/reconciliation dễ reasoning hơn.

Không cần distributed transaction giữa SQL và object storage. Thay vào đó, workflow chấp nhận có một failure window nhỏ nhưng làm nó recoverable bằng trạng thái, immutable key và orphan reconciliation.

Private storage cũng giúp business approval thực sự có ý nghĩa: asset chỉ trở thành public khi một bước publish riêng quyết định điều đó.

## Trade-offs

- Object storage thêm network dependency nhưng giải quyết durability/shared-storage tốt hơn local disk trong multi-instance deployment.
- Deep image decoding/re-encoding tăng CPU cost nhưng nâng confidence rằng content thực sự là ảnh.
- Temporary staging + reconciliation phức tạp hơn write thẳng final path nhưng làm failure behavior rõ ràng.
- Strict 8 MB limit giảm abuse surface nhưng cần phối hợp với product requirement nếu ảnh chất lượng cao vượt ngưỡng.
- Malware scanning có thể cần cho một số business/compliance contexts, nhưng không nên tự động thêm nếu threat model và file types không yêu cầu.

## Cách kiểm thử

1. **Authorization/security integration test:** authenticated user tenant A thử upload vào tenant B; phải bị từ chối trước storage write.
2. **Validation test:** gửi renamed executable/HTML/polyglot giả `.jpg`, invalid JPEG/PNG và content-type giả; validator phải reject theo actual content policy.
3. **Size/resource test:** gửi request >8 MB và nhiều concurrent uploads; request bị reject theo limit và resource usage vẫn bounded.
4. **Concurrency test:** nhiều uploads có cùng client filename; storage keys phải unique, không overwrite và metadata trỏ đúng object.
5. **Failure-path test:** inject storage/DB failure và client cancellation; kiểm tra partial/orphan cleanup, trạng thái DB và reconciliation behavior.

## Quan sát trong production

Theo dõi:

- upload requests/success/rejection theo reason;
- authorization-denied count;
- bytes uploaded và size percentile;
- upload duration p50/p95/p99;
- active uploads và cancellation count;
- object-storage error/latency;
- orphan cleanup/reconciliation count;
- local temp disk/storage utilization nếu có staging;
- alerts khi rejected oversized uploads, storage failures hoặc storage growth tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cần upload file 5–20 GB, bạn sẽ đổi sang direct-to-Blob/SAS flow như thế nào để backend vẫn giữ authorization control?
2. Khi nào re-encode ảnh là đáng giá hơn chỉ kiểm tra magic bytes?
3. Nếu asset phải được public qua CDN sau approval, bạn sẽ thiết kế publish/invalidation boundary thế nào?

# Code Review Challenge 2 — Orders API càng phân trang sâu càng chậm, đồng thời user thấy record trùng hoặc biến mất giữa các trang

**Chủ đề:** SQL Server, query optimization, keyset pagination, sargability, deterministic ordering, indexes, optional filters, parameter sensitivity, concurrency, execution plans, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một enterprise Orders API đọc từ SQL Server. Bảng `Orders` có khoảng 80 triệu rows và tiếp tục tăng. Mỗi tenant thường có vài trăm nghìn đến vài triệu orders.

UI cho phép:

- lọc theo tenant bắt buộc;
- tùy chọn `Status`;
- tùy chọn một ngày tạo order;
- search theo customer email;
- sort mới nhất trước;
- phân trang 50 rows;
- user có thể nhảy tới trang sâu;
- dữ liệu vẫn có insert mới trong lúc user đang duyệt.

Production symptoms:

- page 1 thường dưới 150 ms nhưng page 2.000 có thể mất nhiều giây;
- SQL CPU tăng mạnh khi nhiều users search email;
- cùng một order đôi lúc xuất hiện ở hai trang liên tiếp hoặc bị bỏ qua khi có order mới insert;
- query plan thay đổi đáng kể theo tổ hợp filters;
- team đề xuất “thêm một index chứa tất cả columns” và giữ nguyên `OFFSET`.

## Đoạn code cần review

```sql
DECLARE @Offset int = (@PageNumber - 1) * @PageSize;

SELECT
    o.Id,
    o.TenantId,
    o.CreatedAtUtc,
    o.Status,
    o.TotalAmount,
    c.Email,
    COUNT_BIG(*) OVER() AS TotalRows
FROM dbo.Orders AS o
JOIN dbo.Customers AS c
    ON c.Id = o.CustomerId
WHERE
    o.TenantId = @TenantId
    AND (@Status IS NULL OR o.Status = @Status)
    AND (
        @CreatedDate IS NULL
        OR CONVERT(date, o.CreatedAtUtc) = @CreatedDate
    )
    AND (
        @Search IS NULL
        OR LOWER(c.Email) LIKE '%' + LOWER(@Search) + '%'
    )
ORDER BY o.CreatedAtUtc DESC
OFFSET @Offset ROWS
FETCH NEXT @PageSize ROWS ONLY;
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong pagination/result stability.
2. Xác định performance, scalability và maintainability concerns.
3. Giải thích production impact dựa trên data volume và concurrent inserts.
4. Ưu tiên findings theo severity thay vì chỉ nói “thiếu index”.
5. Đề xuất query/API design đã sửa và index strategy dựa trên access pattern.
6. Giải thích testing với execution plans, deep pages, concurrent writes và representative parameter sets.
7. Đề xuất production telemetry để chứng minh remediation hiệu quả.

## Câu hỏi gợi mở

1. SQL Server phải làm gì với hàng nghìn rows đứng trước `OFFSET` trước khi trả 50 rows ở page sâu?
2. `ORDER BY o.CreatedAtUtc DESC` có tạo total ordering nếu nhiều orders có cùng timestamp không?
3. Nếu order mới được insert giữa request page 1 và page 2, offset của các rows cũ thay đổi thế nào?
4. `CONVERT(date, o.CreatedAtUtc)` và `LIKE '%term%'` ảnh hưởng index seek ra sao?
5. `COUNT_BIG(*) OVER()` có thể làm query trả 50 rows nhưng vẫn phải xử lý bao nhiêu rows để tính tổng?

## Gợi ý

### Gợi ý 1

Primary risk là **offset pagination trên tập dữ liệu lớn và đang thay đổi**: chi phí thường tăng theo độ sâu, còn vị trí row không ổn định dưới concurrent inserts/deletes.

### Gợi ý 2

Tách bài toán “fetch page tiếp theo nhanh và ổn định” khỏi “search arbitrary text” và “tính exact total count”; ba yêu cầu này có thể cần chiến lược khác nhau.

## Kết quả code review tham khảo

### High — `ORDER BY CreatedAtUtc` không deterministic khi timestamp trùng

**Vấn đề:**  
Nhiều orders có thể có cùng `CreatedAtUtc`, nhưng query không có unique tie-breaker.

**Tại sao xảy ra:**  
SQL chỉ bảo đảm ordering theo expressions được nêu. Các rows có cùng timestamp không có thứ tự ổn định bắt buộc giữa executions.

**Ảnh hưởng production:**  
Row có thể chuyển vị trí giữa page calls, tạo duplicate/missing rows ngay cả khi dataset không thay đổi đáng kể.

**Cách sửa:**  
Dùng total ordering, ví dụ `ORDER BY CreatedAtUtc DESC, Id DESC`, và cursor chứa cả hai values.

### High — OFFSET pagination suy giảm theo page depth

**Vấn đề:**  
Để lấy 50 rows ở page sâu, engine vẫn phải định vị/xử lý các rows đứng trước offset theo plan được chọn.

**Tại sao xảy ra:**  
`OFFSET` mô hình hóa vị trí tương đối trong ordered result chứ không cho engine một seek boundary từ row cuối đã biết.

**Ảnh hưởng production:**  
Latency và CPU/I/O tăng mạnh ở page sâu; nhiều concurrent deep-page requests có thể gây database saturation.

**Cách sửa:**  
Cho browse-next/previous, ưu tiên keyset/seek pagination với cursor `(CreatedAtUtc, Id)`. Nếu product bắt buộc nhảy trực tiếp page 2.000, cần thảo luận UX/requirement hoặc chấp nhận cost/thiết kế riêng thay vì giả định keyset hỗ trợ random page number miễn phí.

### High — Offset result không ổn định dưới concurrent inserts/deletes

**Vấn đề:**  
Page number dựa trên số row đứng trước. Insert mới ở đầu result làm toàn bộ offset phía sau dịch chuyển.

**Tại sao xảy ra:**  
Mỗi request page chạy trên một snapshot thời điểm khác nếu không có snapshot-consistency contract xuyên nhiều requests.

**Ảnh hưởng production:**  
User thấy record lặp hoặc bị bỏ qua khi chuyển trang trong hệ thống đang ghi liên tục.

**Cách sửa:**  
Keyset cursor neo trang tiếp theo vào sort key của row cuối đã thấy. Nếu requirement cần một immutable snapshot của toàn phiên browse, cần explicit snapshot/version strategy; không nên giữ DB transaction dài qua nhiều HTTP requests.

### High — `CONVERT(date, CreatedAtUtc)` làm predicate khó tận dụng index seek trên datetime key

**Vấn đề:**  
Function được áp lên indexed column trong predicate.

**Tại sao xảy ra:**  
Engine không còn một range predicate trực tiếp trên raw `CreatedAtUtc` để seek theo cách đơn giản.

**Ảnh hưởng production:**  
Có thể tăng scan/read đáng kể trên tenant lớn.

**Cách sửa:**  
Chuyển ngày thành half-open range ở application/query boundary: `CreatedAtUtc >= @StartUtc AND CreatedAtUtc < @EndUtc`, xử lý timezone/business date rõ ràng.

### High — Contains search `LIKE '%term%'` trên normalized email không phù hợp B-tree seek thông thường

**Vấn đề:**  
Leading wildcard buộc match substring bất kỳ; `LOWER()` còn thêm expression trên column.

**Tại sao xảy ra:**  
B-tree index hữu ích nhất khi predicate có searchable leading boundary phù hợp. `%term%` không có prefix cố định.

**Ảnh hưởng production:**  
Search email trên hàng triệu customers có thể gây scans, CPU cao và kéo theo expensive join.

**Cách sửa:**  
Làm rõ requirement. Nếu cần exact/prefix email, normalize email khi write và query bằng equality/prefix để index được. Nếu thực sự cần arbitrary substring/full-text behavior, dùng search capability phù hợp thay vì ép OLTP index giải bài toán đó.

### High — Exact `COUNT_BIG(*) OVER()` có thể phá lợi ích của việc chỉ trả 50 rows

**Vấn đề:**  
UI cần một page nhỏ nhưng query đồng thời yêu cầu exact count trên toàn filtered result.

**Tại sao xảy ra:**  
Database phải tính count cho qualifying set; optimizer có thể cần xử lý lượng dữ liệu lớn trước/đồng thời với paging.

**Ảnh hưởng production:**  
Page latency và resource usage bị chi phối bởi count, đặc biệt trên broad filter.

**Cách sửa:**  
Xác minh UX có thật sự cần exact total mỗi request không. Có thể trả `hasMore`, estimate/cached count, hoặc tách count endpoint/query khi cần. Nếu exact count bắt buộc, đo và tối ưu riêng.

### Medium — Optional-filter OR pattern có thể tạo plan không tối ưu cho mọi parameter shape

**Vấn đề:**  
`(@Status IS NULL OR o.Status = @Status)` và các optional conditions gom nhiều selectivity shapes vào một statement.

**Tại sao xảy ra:**  
Một plan tốt cho tenant + status rất selective có thể không tốt cho broad tenant-only query; parameter sensitivity/statistics ảnh hưởng cardinality estimates.

**Ảnh hưởng production:**  
Latency biến động lớn theo parameters và plan cache state.

**Cách sửa:**  
Đầu tiên đo actual execution plans/query store theo parameter sets. Sau đó cân nhắc dynamic SQL parameterized để chỉ emit predicates thực sự dùng, separate query shapes, hoặc các SQL Server mitigation phù hợp phiên bản/workload. Không mặc định `OPTION (RECOMPILE)` cho mọi request.

### Medium — Không giới hạn/validate page parameters được thể hiện

**Vấn đề:**  
`@PageSize`, `@PageNumber` đi trực tiếp vào offset calculation.

**Tại sao xảy ra:**  
API boundary không được thể hiện là đang enforce upper/lower bounds.

**Ảnh hưởng production:**  
Page size rất lớn hoặc page number cực sâu có thể tạo expensive queries; multiplication cũng cần type/range handling an toàn.

**Cách sửa:**  
Validate page size và cursor ở API boundary. Với keyset pagination, cursor cần parse/validate và có thể được opaque-sign/encode nếu không muốn client tự cấu trúc.

### Medium — “Một index chứa tất cả columns” không phải index strategy

**Vấn đề:**  
Query có nhiều optional paths, join và search pattern khác nhau; một giant covering index có thể rất rộng nhưng vẫn không giải quyết substring search/deep offset.

**Tại sao xảy ra:**  
Index design phải theo leading predicates, sort order, selectivity và write cost chứ không phải số columns được include.

**Ảnh hưởng production:**  
Wide index tăng storage, memory footprint và write/update cost nhưng vẫn có thể không được optimizer dùng hiệu quả.

**Cách sửa:**  
Dùng execution plans + Query Store để xác định dominant access patterns. Một candidate cho browse path có thể bắt đầu bằng tenant + filter dimensions quan trọng + `(CreatedAtUtc DESC, Id DESC)`, với INCLUDE tối thiểu cần thiết; exact order phụ thuộc workload thực tế.

### Medium — Join customer search vào mọi query dù search có thể absent

**Vấn đề:**  
`JOIN Customers` luôn xảy ra để trả email và phục vụ optional search.

**Tại sao xảy ra:**  
Query shape không tách broad browse khỏi search-specific work.

**Ảnh hưởng production:**  
Có thể tăng join cost/read footprint cho hot browse path, đặc biệt nếu API không phải lúc nào cũng cần email hoặc có denormalized/read model phù hợp hơn.

**Cách sửa:**  
Đo plan trước. Có thể giữ join nếu index/foreign-key lookup rẻ và email luôn cần trong projection; nếu search là distinct use case, cân nhắc separate query path/read model. Không denormalize chỉ vì giả định.

### Low — Query không tự cung cấp evidence để phân biệt CPU, I/O, blocking hay estimate problem

**Vấn đề:**  
Triệu chứng “slow” dễ bị rút gọn thành “thêm index”.

**Tại sao xảy ra:**  
Không có investigation loop gắn với actual plan, reads, waits và parameter set.

**Ảnh hưởng production:**  
Team có thể deploy index tốn kém nhưng không sửa bottleneck thật.

**Cách sửa:**  
Dùng Query Store/actual execution plan, duration, CPU, logical reads, waits, row estimates vs actuals và parameter shape để xác nhận root cause.

## Phiên bản đề xuất

Một browse path theo keyset pagination có thể dùng cursor gồm `CreatedAtUtc` và `Id` của row cuối trang trước.

```sql
-- @AfterCreatedAtUtc và @AfterId đều NULL cho trang đầu.
-- @StartUtc/@EndUtc được tính ở application khi lọc theo ngày.

SELECT TOP (@PageSize)
    o.Id,
    o.TenantId,
    o.CreatedAtUtc,
    o.Status,
    o.TotalAmount,
    c.Email
FROM dbo.Orders AS o
JOIN dbo.Customers AS c
    ON c.Id = o.CustomerId
WHERE
    o.TenantId = @TenantId
    AND (@Status IS NULL OR o.Status = @Status)
    AND (
        @StartUtc IS NULL
        OR (o.CreatedAtUtc >= @StartUtc AND o.CreatedAtUtc < @EndUtc)
    )
    AND (
        @AfterCreatedAtUtc IS NULL
        OR o.CreatedAtUtc < @AfterCreatedAtUtc
        OR (
            o.CreatedAtUtc = @AfterCreatedAtUtc
            AND o.Id < @AfterId
        )
    )
ORDER BY
    o.CreatedAtUtc DESC,
    o.Id DESC;
```

Nếu `@Status`/date combinations tạo plan instability đáng kể, production implementation có thể dùng parameterized dynamic SQL hoặc separate prepared query shapes để chỉ thêm predicates đang active. Search email nên được tách theo requirement:

```sql
-- Nếu business chấp nhận exact normalized email lookup:
AND c.NormalizedEmail = @NormalizedEmail
```

Một candidate index cho browse path, cần được validate bằng actual workload, có thể là:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt_Id
ON dbo.Orders
(
    TenantId,
    CreatedAtUtc DESC,
    Id DESC
)
INCLUDE
(
    CustomerId,
    Status,
    TotalAmount
);
```

Nếu `Status` gần như luôn được filter và có selectivity hữu ích, thứ tự key/index khác có thể tốt hơn. Không nên thêm index chỉ từ snippet mà bỏ qua write rate, existing indexes và Query Store evidence.

## Giải thích thiết kế sau khi sửa

Keyset pagination biến “hãy bỏ qua N rows” thành “hãy tiếp tục sau key cuối đã thấy”. Với index phù hợp, engine có cơ hội seek gần boundary và chi phí page sau không tăng tuyến tính theo page number như offset sâu.

Tie-breaker `Id` tạo total ordering. Cursor dựa trên `(CreatedAtUtc, Id)` cũng ổn định hơn khi có rows mới insert ở đầu result, vì page tiếp theo tiếp tục từ vị trí logic đã thấy thay vì position count.

Giải pháp không tuyên bố keyset giải quyết mọi UX. Nếu product bắt buộc random-access đến trang số bất kỳ hoặc exact total count tức thời, đó là requirement khác và cần cân nhắc cost/alternative riêng.

## Trade-offs

- Keyset pagination nhanh và ổn định cho next/previous nhưng không tự nhiên cho “jump to page 2.000”.
- Exact total count cho UX đẹp nhưng có thể rất đắt trên filter rộng; `hasMore` rẻ hơn nhưng ít thông tin hơn.
- Index rộng giảm lookup cho read path nhưng tăng write amplification/storage/memory.
- Dynamic query shapes có thể cải thiện plans nhưng tăng query-generation/testing complexity.
- Search engine hoặc specialized search index có thể phù hợp arbitrary substring hơn SQL OLTP, nhưng thêm eventual consistency và operational complexity; chỉ dùng khi requirement/scale chứng minh cần.

## Cách kiểm thử

1. **Execution-plan/database test:** chạy representative tenants và filter shapes; so sánh actual plan, logical reads, CPU, duration và estimated vs actual rows trước/sau.
2. **Deep-pagination load test:** so sánh page 1 và equivalent deep traversal dưới concurrency; keyset latency không được tăng theo offset depth như implementation cũ.
3. **Correctness concurrency test:** insert orders mới giữa các page requests và tạo nhiều rows cùng `CreatedAtUtc`; xác minh cursor không duplicate/miss rows thuộc traversal contract.
4. **Search test:** đo exact/prefix/substr email use cases riêng để xác nhận query strategy phù hợp requirement thay vì benchmark một pattern duy nhất.
5. **Index write-cost test:** đo insert/update throughput, index size và maintenance impact trước khi rollout index mới trên production-sized data distribution.

## Quan sát trong production

Theo dõi:

- endpoint p50/p95/p99 theo query shape, không log raw search data nhạy cảm;
- SQL duration, CPU, logical reads và rows returned;
- Query Store top resource-consuming plans và plan regressions;
- waits/blocking nếu incident có concurrency pressure;
- cursor/page-size distribution và tỷ lệ requests dùng expensive search;
- database CPU/I/O, buffer/cache pressure và index usage;
- alert khi p95, logical reads hoặc plan regression vượt baseline sau deploy.

## Câu hỏi phỏng vấn mở rộng

1. Nếu UX bắt buộc nhảy tới page 10.000, bạn sẽ trao đổi requirement và thiết kế những lựa chọn nào?
2. Nếu exact email search rất nhanh nhưng substring search vẫn bắt buộc, khi nào bạn đưa Elasticsearch/search service vào kiến trúc?
3. Nếu nhiều orders có cùng timestamp và `Id` là GUID không tuần tự, index/cursor trade-off sẽ thay đổi ra sao?
