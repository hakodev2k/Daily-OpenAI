# Câu 1 — Async/Await, Thread Pool và API bị chậm dưới tải cao

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** .NET runtime, async behavior, performance diagnosis

## Bối cảnh

Một ASP.NET Core API xử lý yêu cầu đồng bộ dữ liệu từ Microsoft Graph và database. Khi traffic tăng, latency tăng mạnh dù CPU không đạt 100%. Một developer thay toàn bộ code thành Task.Run để "tận dụng nhiều thread hơn".

## Câu hỏi chính

Giải thích điều gì xảy ra bên trong với async/await, Task và Thread Pool. Vì sao thay đổi trên có thể làm hệ thống tệ hơn? Bạn kiểm chứng bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Dependency bên ngoài có hỗ trợ async thật không?
- Có block bằng .Result hoặc .Wait() không?
- Thread Pool metrics hiện tại thế nào?

## Gợi ý tư duy

- Gợi ý 1: Phân biệt CPU bound và I/O bound.
- Gợi ý 2: Xem continuation và Thread Pool starvation.
- Gợi ý 3: Dùng metrics để xác nhận thay vì đoán.

## Hướng giải quyết tham khảo

Async phù hợp cho I/O bound. Không nên bọc I/O async bằng Task.Run trong ASP.NET Core. Cần kiểm tra blocking call, connection pool, external latency và Thread Pool.

## Câu hỏi đào sâu

- Khi nào Task.Run hợp lý?
- Làm sao phát hiện Thread Pool starvation?
- Có nên tăng ThreadPool minimum threads không?

# Câu 2 — Thiết kế nền tảng xử lý Background Job cho hệ thống doanh nghiệp

**Loại câu hỏi:** System Design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Architecture, reliability, distributed processing

## Bối cảnh

Một hệ thống .NET cần xử lý email notification, đồng bộ AD, Exchange Online và các tác vụ báo cáo. Hiện tại Hangfire bị duplicate job khi deploy.

## Câu hỏi chính

Thiết kế lại nền tảng background processing với khả năng retry, idempotency, monitoring và recovery.

## Câu hỏi làm rõ nên cân nhắc

- Job quan trọng đến mức nào?
- Có yêu cầu exactly-once không?
- Có bao nhiêu worker chạy đồng thời?

## Gợi ý tư duy

- Gợi ý 1: Retry không đủ nếu operation không idempotent.
- Gợi ý 2: Cần lưu state execution.
- Gợi ý 3: Observability là một phần của design.

## Hướng giải quyết tham khảo

Dùng modular monolith cho MVP, lưu execution history, thiết kế command idempotent, có distributed lock khi cần, structured logging và metrics.

# Câu 3 — AI Agent hỗ trợ Code Review cho dự án .NET

**Loại câu hỏi:** AI Engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Agent architecture, context engineering, evaluation

## Bối cảnh

Team muốn tạo AI agent đọc Pull Request, issue, coding rules và architecture docs để đưa review comment.

## Câu hỏi chính

Bạn thiết kế workflow AI review như thế nào để đảm bảo chất lượng, bảo mật và tránh phụ thuộc hoàn toàn vào LLM?

## Gợi ý tư duy

- Gợi ý 1: Context quan trọng hơn prompt dài.
- Gợi ý 2: Permission boundary cần rõ ràng.
- Gợi ý 3: Cần evaluation dataset.

## Hướng giải quyết tham khảo

Kết hợp retrieval context, structured output, deterministic checks, human approval, quality metrics và audit logs.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Hiểu runtime behavior trước khi tối ưu.
- Thiết kế retry cùng idempotency.
- AI production cần validation và evaluation.

## Mẫu tư duy cần nhớ

- Clarify before designing.
- Measure before optimizing.
- Treat observability as part of architecture.
- Validate AI output deterministically.
