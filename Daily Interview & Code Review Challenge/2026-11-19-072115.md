# Code Review Challenge 1 — Azure Service Bus mất message khi gửi vé

**Chủ đề:** C#/.NET 8, Azure Service Bus, BackgroundService, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** khoảng 9

## Bối cảnh

Hệ thống đăng ký sự kiện nhận `RegistrationConfirmed` từ Azure Service Bus queue (PeekLock), gọi vendor phát vé và lưu trạng thái SQL Server. Worker chạy trên 5 Azure App Service instances. Khi vendor trả 429/timeout, khách có thể không nhận vé hoặc nhận trùng. Producer có thể redeliver cùng `MessageId`; chưa xác nhận liệu có nhiều event ID cho cùng registration. Không được âm thầm bỏ việc.

## Đoạn code cần review

```csharp
public sealed class TicketWorker : BackgroundService
{
    private readonly ServiceBusClient _client;
    private readonly IServiceProvider _services;
    private readonly ILogger<TicketWorker> _log;

    public TicketWorker(ServiceBusClient client, IServiceProvider services,
        ILogger<TicketWorker> log)
    {
        _client = client;
        _services = services;
        _log = log;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var receiver = _client.CreateReceiver("confirmed-registrations");
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await receiver.ReceiveMessageAsync(
                TimeSpan.FromSeconds(5), stoppingToken);
            if (message is null) continue;

            await receiver.CompleteMessageAsync(message);
            _ = ProcessAsync(message);
        }
    }

    private async Task ProcessAsync(ServiceBusReceivedMessage message)
    {
        try
        {
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var vendor = scope.ServiceProvider.GetRequiredService<ITicketVendor>();
            var evt = JsonSerializer.Deserialize<RegistrationConfirmed>(
                message.Body.ToString())!;

            var registration = await db.Registrations
                .SingleAsync(x => x.Id == evt.RegistrationId);
            if (registration.TicketSent) return;

            await vendor.SendTicketAsync(registration.Email, registration.Id);
            registration.TicketSent = true;
            await db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _log.LogError(ex, "Ticket processing failed");
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Complete trước khi xử lý

**Vấn đề:** Message được complete trước business operation.  
**Tại sao xảy ra:** Queue xóa message khỏi luồng xử lý trước khi biết vendor/DB thành công.  
**Ảnh hưởng production:** Crash hoặc lỗi vendor khiến công việc mất vĩnh viễn.  
**Cách sửa:** Complete sau khi ghi durable intent hoặc hoàn thành xử lý có kiểm chứng.

### [Critical] — External side effect không idempotent

**Vấn đề:** `TicketSent` là read-check-write không atomic và không bảo vệ timeout sau khi vendor đã nhận request.  
**Tại sao xảy ra:** SQL và vendor không có shared transaction.  
**Ảnh hưởng production:** Phát vé hai lần.  
**Cách sửa:** Unique business key, durable dispatch, vendor idempotency key hoặc reconciliation; không hứa exactly-once nếu vendor không hỗ trợ.

### [High] — Fire-and-forget không giới hạn

**Vấn đề:** Task không await, không track, không backpressure.  
**Tại sao xảy ra:** Vòng receive chạy nhanh hơn dependency.  
**Ảnh hưởng production:** Memory/connection spike, mất task khi shutdown.  
**Cách sửa:** Await hoặc dùng `ServiceBusProcessor` với bounded `MaxConcurrentCalls`, lifecycle và cancellation.

### [High] — Nuốt lỗi và không phân loại retry

**Vấn đề:** Exception chỉ được log.  
**Tại sao xảy ra:** Không có settle/retry/DLQ policy theo loại lỗi.  
**Ảnh hưởng production:** Khó khôi phục, poison message lặp vô hạn nếu sửa settlement một cách ngây thơ.  
**Cách sửa:** Transient retry có backoff; invalid payload vào DLQ; theo dõi delivery count.

### [High] — Lock expiry và duplicate delivery

**Vấn đề:** Không có lock renewal hoặc bound xử lý.  
**Tại sao xảy ra:** Vendor chậm hơn lock duration.  
**Ảnh hưởng production:** Lock lost, redelivery và duplicate.  
**Cách sửa:** Cấu hình auto lock renewal theo SLA và idempotency; ưu tiên xử lý ngắn.

### [Medium] — Thiếu cancellation/timeout

**Vấn đề:** DB/vendor không nhận token.  
**Tại sao xảy ra:** `ProcessAsync` không truyền cancellation.  
**Ảnh hưởng production:** Shutdown treo, HTTP call kéo dài.  
**Cách sửa:** Propagate token, timeout từng dependency, giới hạn retry.

### [Medium] — Payload không validate

**Vấn đề:** Null-forgiving deserialize, không kiểm tra event schema.  
**Tại sao xảy ra:** Tin message body hợp lệ.  
**Ảnh hưởng production:** Poison work và sai dữ liệu.  
**Cách sửa:** Validate event version, registration ID, quyền sở hữu dữ liệu và dead-letter có kiểm soát.

### [Medium] — Resource lifecycle

**Vấn đề:** Receiver không dispose.  
**Tại sao xảy ra:** Không dùng `await using`.  
**Ảnh hưởng production:** AMQP resources không đóng có kiểm soát.  
**Cách sửa:** Dispose receiver/processor trong hosted service lifecycle.

### [Low] — Thiếu structured telemetry

**Vấn đề:** Log không có MessageId, delivery count, dispatch ID, duration.  
**Tại sao xảy ra:** Chưa thiết kế observability.  
**Ảnh hưởng production:** Khó chứng minh mất/trùng message.  
**Cách sửa:** Correlation ID và metrics, không log email/PII.

## Phiên bản đề xuất

Một phương án: ingress handler chỉ persist `TicketDispatch` (unique `RegistrationId + Operation`) rồi complete message. Dispatcher khác atomic-claim row và gọi vendor bằng idempotency key nếu vendor hỗ trợ. Đoạn sau là ingress, **không** phải implementation đầy đủ của dispatcher:

```csharp
public sealed class TicketIngress
{
    private readonly IServiceScopeFactory _scopes;
    public TicketIngress(IServiceScopeFactory scopes) => _scopes = scopes;

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var ct = args.CancellationToken;
        RegistrationConfirmed? evt;
        try
        {
            evt = JsonSerializer.Deserialize<RegistrationConfirmed>(
                args.Message.Body.ToString());
            if (evt is null || evt.RegistrationId == Guid.Empty)
                throw new JsonException("Invalid event");
        }
        catch (JsonException)
        {
            await args.DeadLetterMessageAsync(args.Message,
                "InvalidPayload", "Invalid registration event", ct);
            return;
        }

        await using var scope = _scopes.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        // DB schema: unique (RegistrationId, Operation).
        // Atomic insert-if-absent phải triển khai theo DB provider.
        await db.Database.ExecuteSqlInterpolatedAsync(
            $@"INSERT INTO TicketDispatches
                (RegistrationId, Operation, State)
               SELECT {evt.RegistrationId}, {"SendTicket"}, {"Pending"}
               WHERE NOT EXISTS
               (SELECT 1 FROM TicketDispatches WITH (UPDLOCK, HOLDLOCK)
                WHERE RegistrationId = {evt.RegistrationId}
                AND Operation = {"SendTicket"})", ct);

        await args.CompleteMessageAsync(args.Message, ct);
    }
}
```

**Giới hạn và điều kiện:** SQL trên giả định SQL Server, unique constraint vẫn bắt buộc để xử lý race; cần xác minh registration tồn tại và xử lý foreign-key failure bằng retry/DLQ policy. Trong production nên dùng stored procedure/parameterized command và transaction nếu có nhiều thay đổi cần atomic. `AutoCompleteMessages=false`; lỗi DB phải propagate để broker redeliver. Dispatcher claim bằng atomic update/lease, retry bounded với jitter và `Retry-After` cho 429; trạng thái ambiguous timeout phải được đối chiếu với vendor. Nếu vendor không có idempotency/lookup, không thể bảo đảm exactly-once external side effect.

## Giải thích thiết kế sau khi sửa

Durable intent làm queue acknowledgment độc lập với vendor outage. Unique key chống duplicate ở ingress. Dispatcher có thể khôi phục lease khi instance crash; trạng thái pending/failed cần reconciliation. Nếu workload nhỏ và vendor hỗ trợ idempotency mạnh, handler trực tiếp cũng hợp lý nhưng phải xử lý settlement và crash window.

## Trade-offs

Thêm bảng dispatch, worker và monitoring tăng operational cost và latency. Bù lại giảm mất công việc và dễ điều tiết vendor outage. Không nên tự thêm distributed lock nếu unique constraint + atomic claim đã đủ.

## Cách kiểm thử

1. **Concurrency:** 10 duplicate messages cùng lúc chỉ tạo một dispatch.
2. **Failure-path:** Crash sau DB commit trước complete; redelivery không tạo duplicate.
3. **Vendor:** 429, 503, timeout sau side effect; kiểm tra backoff/reconciliation.
4. **Deployment:** Stop/restart 5 instances khi đang xử lý; xác minh recovery.
5. **Database:** Unique constraint và FK violations được phân loại đúng.

## Quan sát trong production

Application Insights: MessageId, DispatchId, correlation ID, retry count, lock-lost, vendor status/latency, dispatch age p95. Azure Monitor: active messages, DLQ depth, oldest pending age. Alert theo SLA, đối soát số registration confirmed và vé phát hành; không log email hay payload nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Vendor không hỗ trợ idempotency hay lookup: bạn cam kết mức độ bảo đảm nào?
2. Làm sao ngăn một registration lỗi mãi làm starvation các registration khác?
3. Nếu yêu cầu thứ tự event theo registration, bạn thay đổi message contract thế nào?

import { ref, watch, onMounted } from 'vue'

type Product = {
  id: string
  name: string
  descriptionHtml: string
  price: number
}
type Result = { items: Product[]; total: number }

const query = ref('')
const page = ref(1)

## Kết quả code review tham khảo

### [Critical] — Stored XSS qua v-html

**Vấn đề:** Render HTML không tin cậy.  
**Tại sao xảy ra:** `v-html` không áp dụng escaping như interpolation.

### [High] — Stale response overwrite

**Vấn đề:** Request cũ hoàn thành sau request mới và ghi đè state.  
**Tại sao xảy ra:** Không có generation ID/cancellation.  
**Ảnh hưởng production:** Sai kết quả tìm kiếm và total.  
**Cách sửa:** Abort previous request và chỉ commit khi generation còn mới nhất.

### [High] — HTTP error bị coi là thành công

**Tại sao xảy ra:** `fetch` không tự reject 4xx/5xx.  
**Ảnh hưởng production:** State sai, che lỗi API.

## Phiên bản đề xuất

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

type Product = { id: string; name: string; descriptionHtml: string }
type Result = { items: Product[]; total: number }
const query = ref('')
const page = ref(1)
const items = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
const selected = ref<Product | null>(null)
const pageSize = 20
let generation = 0
let controller: AbortController | undefined
let timer: ReturnType<typeof setTimeout> | undefined

function schedule() {
  if (timer) clearTimeout(timer)
  controller?.abort()
  const id = ++generation
  loading.value = true
  error.value = ''
  timer = setTimeout(() => { void load(id) }, 250)
}
async function load(id: number) {
  const abort = new AbortController()
  controller = abort
  const params = new URLSearchParams({
    q: query.value.trim(), page: String(page.value)
  })
  try {
    const response = await fetch('/api/products?' + params, {
      signal: abort.signal
    })
    if (!response.ok) throw new Error('HTTP ' + response.status)
    const data: unknown = await response.json()
    if (!valid(data)) throw new Error('Invalid response')
    if (id !== generation) return
    items.value = data.items
    total.value = data.total
  } catch {
    if (id !== generation || abort.signal.aborted) return
    items.value = []
    total.value = 0
    error.value = 'Không tải được sản phẩm.'
  } finally {
    if (id === generation) loading.value = false
  }
}
function valid(x: unknown): x is Result {
  if (!x || typeof x !== 'object') return false
  const v = x as Record<string, unknown>
  return Number.isInteger(v.total) && (v.total as number) >= 0
    && Array.isArray(v.items)
    && v.items.every((p: unknown) =>
      !!p && typeof p === 'object'
      && typeof (p as Product).id === 'string'
      && typeof (p as Product).name === 'string'
      && typeof (p as Product).descriptionHtml === 'string')
}
watch(query, () => {
  page.value = 1
  selected.value = null
  schedule()
})
watch(page, schedule)
schedule()
onBeforeUnmount(() => {
  generation++
  if (timer) clearTimeout(timer)
  controller?.abort()
})
</script>

<template>
  <input v-model="query" placeholder="Search" />
  <p v-if="loading">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <div v-for="product in items" :key="product.id">
    <button @click="selected = product">{{ product.name }}</button>
    <p>{{ product.descriptionHtml }}</p>
  </div>
  <p>Total: {{ total }}</p>
  <p v-if="selected">{{ selected.descriptionHtml }}</p>
  <button :disabled="loading || page * pageSize >= total"
    @click="page++">Next</button>
</template>
```

## Giải thích thiết kế sau khi sửa

Generation ID ngăn stale commits ngay cả khi abort quá muộn. Debounce tránh request dư thừa; khi query đổi ở page khác 1, hai watchers có thể schedule liên tiếp nhưng timer trước bị hủy. `URLSearchParams` encode input. Interpolation render text thay vì parse HTML. Runtime validation chỉ bảo vệ contract tối thiểu, không thay server-side authorization/validation.

## Trade-offs

Debounce tăng độ trễ cảm nhận 250 ms nhưng giảm QPS. Abort không chứng minh server đã ngừng xử lý. Plain text làm mất formatting; rich text đòi hỏi sanitization policy được kiểm thử. Page size 20 là giả định cần xác minh với API.

## Cách kiểm thử

1. **Component race:** A chậm hơn B; UI chỉ hiển thị B.
2. **Security:** Malicious HTML không tạo executable DOM.
3. **API:** 400/500, invalid JSON, offline hiển thị lỗi an toàn.
4. **Playwright E2E:** Gõ nhanh trên page 3, reset page và selection đúng.
5. **Load:** Đo request count, abort ratio và backend p95.

## Quan sát trong production

Browser RUM: search-to-render latency, stale-response-discarded count, request aborted/error rate, page transitions. Application Insights: QPS, HTTP 429/5xx, p95/p99, dependency latency. Correlation ID để đối chiếu browser/backend; không log raw query nếu có PII.
