# Code Review Challenge 1 — Hai quản lý duyệt cùng một yêu cầu và quyết định đến sau âm thầm ghi đè quyết định trước

**Chủ đề:** C#/.NET 8, ASP.NET Core, EF Core optimistic concurrency, SQL Server `rowversion`, HTTP preconditions, state transition, production observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal approval portal chạy ASP.NET Core .NET 8, EF Core và SQL Server. Mỗi approval request có thể được một trong nhiều manager có quyền phù hợp mở và quyết định `Approve` hoặc `Reject`.

Entity đã có `RowVersion` và EF Core đã cấu hình nó là concurrency token vì team muốn tránh lost update. Tuy nhiên UI hiện không gửi version của record khi user submit quyết định.

Production xuất hiện tình huống:

- Manager A mở request lúc 09:00 và thấy trạng thái `Pending`.
- Manager B cũng mở request lúc 09:01 và thấy `Pending`.
- A chọn `Reject` lúc 09:05.
- B vẫn đang ở màn hình cũ và chọn `Approve` lúc 09:07.
- Kết quả cuối cùng trong database đôi lúc là `Approved`, dù B chưa từng nhìn thấy quyết định mới của A.
- Team cho rằng `RowVersion` đã đủ để EF Core tự phát hiện mọi stale update.
- Một developer còn thêm retry trong `DbUpdateConcurrencyException` để “giảm lỗi cho user”.

Business yêu cầu một decision không được âm thầm ghi đè decision đã được commit trước đó. Nếu dữ liệu user nhìn thấy đã stale, UI phải biết và yêu cầu user review lại trạng thái mới. Hệ thống chạy nhiều application instances sau load balancer.

## Đoạn code cần review

```csharp
public sealed class ApprovalRequest
{
    public int Id { get; set; }
    public ApprovalStatus Status { get; set; }
    public string? DecisionComment { get; set; }
    public string? DecidedBy { get; set; }
    public DateTimeOffset? DecidedAt { get; set; }
    public byte[] RowVersion { get; set; } = [];
}

public sealed record UpdateDecisionRequest(
    string Decision,
    string? Comment);

[ApiController]
[Route("api/approvals")]
public sealed class ApprovalsController : ControllerBase
{
    private readonly AppDbContext _db;

    public ApprovalsController(AppDbContext db)
    {
        _db = db;
    }

    [Authorize(Policy = "Approvals.Decide")]
    [HttpPut("{id:int}/decision")]
    public async Task<IActionResult> UpdateDecision(
        int id,
        UpdateDecisionRequest request,
        CancellationToken cancellationToken)
    {
        var approval = await _db.ApprovalRequests
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (approval is null)
            return NotFound();

        approval.Status = request.Decision == "approve"
            ? ApprovalStatus.Approved
            : ApprovalStatus.Rejected;

        approval.DecisionComment = request.Comment;
        approval.DecidedBy = User.Identity!.Name;
        approval.DecidedAt = DateTimeOffset.UtcNow;

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException)
        {
            await _db.Entry(approval).ReloadAsync(cancellationToken);

            approval.Status = request.Decision == "approve"
                ? ApprovalStatus.Approved
                : ApprovalStatus.Rejected;

            approval.DecisionComment = request.Comment;
            approval.DecidedBy = User.Identity!.Name;
            approval.DecidedAt = DateTimeOffset.UtcNow;

            await _db.SaveChangesAsync(cancellationToken);
        }

        return NoContent();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định vì sao code vẫn có thể ghi đè một stale decision dù entity đã có `RowVersion`.
2. Phân biệt concurrency giữa **query và save trong cùng request** với stale state tồn tại từ lúc user đọc dữ liệu trên UI.
3. Review retry trong `DbUpdateConcurrencyException` và giải thích production impact.
4. Xác định các vấn đề correctness trong parsing decision và state transition.
5. Đề xuất contract/API giúp client gửi lại version mà nó đã nhìn thấy.
6. Đề xuất behavior HTTP hợp lý khi precondition không còn đúng.
7. Nêu tests và telemetry để chứng minh không còn silent lost update dưới concurrent requests.

## Câu hỏi gợi mở

1. `RowVersion` mà EF Core dùng trong câu `UPDATE ... WHERE RowVersion = ...` hiện đến từ thời điểm nào?
2. Khi B submit lúc 09:07, endpoint query record mới nhất trước rồi mới update. EF đang so version nào với version nào?
3. Catch concurrency exception rồi `ReloadAsync` và ghi lại cùng decision có còn bảo vệ ý nghĩa business của optimistic concurrency không?
4. `request.Decision` nhận mọi chuỗi khác `"approve"` thành `Rejected` có an toàn không?
5. Nếu request đã chuyển từ `Pending` sang `Rejected`, có nên cho một request cũ chuyển thẳng sang `Approved` chỉ vì user vẫn có permission `Approvals.Decide` không?

## Gợi ý

### Gợi ý 1

Rủi ro chính không phải EF Core “không hỗ trợ concurrency”, mà là **client-visible version chưa được round-trip về server**. Hãy xác định version nào đại diện cho snapshot user thực sự đã nhìn thấy.

### Gợi ý 2

Optimistic concurrency chỉ có giá trị khi conflict được đưa trở lại business flow. Nếu catch conflict rồi reload và overwrite tự động, bạn có thể biến cơ chế bảo vệ thành last-write-wins có thêm một vòng retry.

## Kết quả code review tham khảo

### Critical — `RowVersion` không bảo vệ stale UI state vì client không gửi version đã đọc

**Vấn đề:** Endpoint query entity mới nhất tại thời điểm B submit. EF Core lấy `RowVersion` hiện tại từ database và dùng chính version đó làm original concurrency value cho lần `SaveChangesAsync` kế tiếp.

**Tại sao xảy ra:** Optimistic concurrency của EF phát hiện thay đổi xảy ra **sau khi entity được query vào DbContext và trước khi `SaveChanges`**. Trong scenario này, stale state nằm ngoài request: B đã nhìn snapshot cũ từ nhiều phút trước, nhưng endpoint không nhận lại version của snapshot đó.

**Ảnh hưởng production:** A có thể commit `Rejected`; sau đó B submit một request mới, endpoint đọc record đã `Rejected` cùng `RowVersion` mới rồi đổi sang `Approved`. Không có concurrent DB modification giữa query và save của B nên EF không nhất thiết ném `DbUpdateConcurrencyException`. Business lost update xảy ra dù technical concurrency token vẫn hoạt động đúng theo phạm vi của nó.

**Cách sửa:** Round-trip một expected version từ read model tới client rồi về mutation request. Có thể dùng `RowVersion` trong DTO hoặc expose nó dưới dạng ETag và yêu cầu `If-Match`. Khi update, server phải dùng version client đã nhìn thấy làm expected/original concurrency token. Nếu version không khớp, không overwrite; trả conflict/precondition failure để client reload và review trạng thái mới.

### Critical — Retry sau `DbUpdateConcurrencyException` cố tình ghi đè dữ liệu mới hơn

**Vấn đề:** Catch block gọi `ReloadAsync`, lấy state/version mới nhất rồi áp lại decision cũ và save lần nữa.

**Tại sao xảy ra:** Conflict bị coi như transient technical error cần retry thay vì tín hiệu rằng assumption của user đã stale.

**Ảnh hưởng production:** Nếu một update khác thật sự xảy ra giữa query và save, code chủ động xóa ý nghĩa của optimistic concurrency bằng cách cập nhật trên version mới nhất mà không yêu cầu user review. Đây là silent conflict resolution theo last-write-wins.

**Cách sửa:** Không retry mutation business một cách mù quáng. Catch `DbUpdateConcurrencyException`, load current database values để trả thông tin phù hợp hoặc chỉ trả `412 Precondition Failed`/`409 Conflict` theo API contract. User hoặc business policy mới quyết định merge/retry.

### High — State transition không enforce invariant `Pending → Approved/Rejected`

**Vấn đề:** Endpoint cho phép gán decision mới bất kể trạng thái hiện tại.

**Tại sao xảy ra:** Code coi status như field CRUD thay vì state machine/business invariant.

**Ảnh hưởng production:** Request đã `Approved`/`Rejected` có thể bị đổi ngược lại bởi một request sau đó. Nếu downstream process đã chạy theo decision đầu tiên, trạng thái aggregate và side effects có thể mâu thuẫn.

**Cách sửa:** Xác định transition hợp lệ rõ ràng. Nếu business chỉ cho quyết định một lần, mutation phải yêu cầu current state là `Pending`. Điều kiện state và version nên được enforce trong cùng write path để tránh time-of-check/time-of-use race.

### High — Parsing decision biến mọi input lạ thành `Rejected`

**Vấn đề:** Chỉ chuỗi chính xác `"approve"` mới thành `Approved`; typo, casing khác hoặc value không hợp lệ đều thành `Rejected`.

**Tại sao xảy ra:** Transport input không được validate thành domain command rõ ràng.

**Ảnh hưởng production:** Client bug hoặc malformed request có thể tạo quyết định sai nhưng vẫn trả success.

**Cách sửa:** Dùng enum/strongly typed command với validation rõ ràng, hoặc explicit switch chỉ chấp nhận tập giá trị hợp lệ và trả `400 Bad Request` cho input ngoài domain.

### High — Authorization capability chưa chứng minh quyền quyết định resource cụ thể

**Vấn đề:** `[Authorize(Policy = "Approvals.Decide")]` có thể chỉ chứng minh user có capability chung, không nhất thiết chứng minh user được phép quyết định approval `id` này.

**Tại sao xảy ra:** Resource-level authorization bị ngầm bỏ qua.

**Ảnh hưởng production:** User có role phù hợp nhưng thuộc sai department/approval scope có thể tác động record không thuộc quyền quản lý.

**Cách sửa:** Nếu business permission phụ thuộc resource, dùng explicit access predicate hoặc resource-based authorization sau khi load metadata tối thiểu. Không giả định một global policy luôn đủ.

### High — Conflict response không tồn tại trong API contract

**Vấn đề:** Endpoint luôn cố đi tới `204 No Content` nếu retry thành công.

**Tại sao xảy ra:** API không mô hình hóa stale write như một kết quả hợp lệ của optimistic concurrency.

**Ảnh hưởng production:** Frontend không có cách phân biệt success với “dữ liệu tôi nhìn thấy đã lỗi thời”. User không được yêu cầu review decision mới.

**Cách sửa:** Định nghĩa contract cho precondition. Nếu dùng HTTP ETag, `If-Match` là cách tự nhiên để client nói “chỉ update nếu representation vẫn ở version này”; mismatch có thể trả `412 Precondition Failed`. Nếu version nằm trong body, `409 Conflict` cũng là lựa chọn hợp lý nếu API contract nhất quán. Quan trọng là không silently overwrite.

### Medium — `User.Identity!.Name` dùng null-forgiving thay cho invariant rõ ràng

**Vấn đề:** Code giả định authenticated identity luôn có `Name`.

**Tại sao xảy ra:** Authorization thành công không tự đảm bảo claim mapping tạo `Identity.Name` đúng theo mọi identity provider/configuration.

**Ảnh hưởng production:** Có thể ghi null/identity không ổn định hoặc ném lỗi nếu authentication mapping thay đổi.

**Cách sửa:** Dùng stable user identifier claim được contract hóa, validate nó trước mutation và lưu cả immutable subject/user id; display name chỉ là metadata nếu cần.

### Medium — Không có durable audit trail cho conflict và decision transition

**Vấn đề:** Entity chỉ giữ decision cuối cùng; code không thể hiện append-only audit event cho ai đã thử quyết định gì và conflict xảy ra lúc nào.

**Tại sao xảy ra:** Current state bị dùng như nguồn duy nhất cho operational investigation.

**Ảnh hưởng production:** Khi user báo “tôi reject nhưng sau đó lại thấy approved”, khó tái dựng timeline giữa concurrent attempts.

**Cách sửa:** Nếu audit là requirement, ghi immutable audit record trong cùng local transaction với successful transition. Conflict/rejected attempts có thể được structured-log riêng với correlation/user/resource/version metadata nhưng tránh log comment nhạy cảm nếu không cần.

### Medium — Không trả version mới cho client sau successful mutation

**Vấn đề:** `204` không cung cấp ETag/version mới.

**Tại sao xảy ra:** API chưa thiết kế representation version như một phần của concurrency contract.

**Ảnh hưởng production:** Client muốn thực hiện mutation tiếp theo phải refetch hoặc có nguy cơ dùng version cũ.

**Cách sửa:** Sau successful update, trả representation mới cùng ETag hoặc có endpoint GET chuẩn hóa ETag. Chọn `200`, `204` + ETag header, hoặc pattern khác theo API contract; cần nhất quán.

## Phiên bản đề xuất

Một hướng là dùng `RowVersion` làm ETag. Khi GET, API trả version hiện tại dưới dạng opaque ETag. Client gửi lại `If-Match` khi quyết định.

Ví dụ service-level implementation:

```csharp
public enum DecisionCommand
{
    Approve,
    Reject
}

public sealed record UpdateDecisionRequest(
    DecisionCommand Decision,
    string? Comment);

public sealed record DecisionResult(
    bool Succeeded,
    bool NotFound,
    bool Conflict,
    byte[]? CurrentVersion);

public sealed class ApprovalService
{
    private readonly AppDbContext _db;

    public ApprovalService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<DecisionResult> DecideAsync(
        int id,
        UpdateDecisionRequest request,
        byte[] expectedVersion,
        string decidedBy,
        CancellationToken cancellationToken)
    {
        var approval = await _db.ApprovalRequests
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (approval is null)
            return new(false, true, false, null);

        if (approval.Status != ApprovalStatus.Pending)
            return new(false, false, true, approval.RowVersion);

        var entry = _db.Entry(approval);
        entry.Property(x => x.RowVersion).OriginalValue = expectedVersion;

        approval.Status = request.Decision switch
        {
            DecisionCommand.Approve => ApprovalStatus.Approved,
            DecisionCommand.Reject => ApprovalStatus.Rejected,
            _ => throw new ArgumentOutOfRangeException(nameof(request.Decision))
        };

        approval.DecisionComment = request.Comment;
        approval.DecidedBy = decidedBy;
        approval.DecidedAt = DateTimeOffset.UtcNow;

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
            return new(true, false, false, approval.RowVersion);
        }
        catch (DbUpdateConcurrencyException)
        {
            await entry.ReloadAsync(cancellationToken);
            return new(false, false, true, approval.RowVersion);
        }
    }
}
```

Controller cần parse `If-Match` thành expected version theo encoding đã chọn, validate format, resolve stable authenticated user ID và thực hiện resource authorization nếu permission model yêu cầu. Khi `Conflict = true`, trả precondition failure/conflict cùng thông tin tối thiểu để UI refetch. Không tự động áp lại command trên version mới.

Một lựa chọn khác là không expose ETag mà đưa `rowVersion` Base64 trong response DTO và mutation body. Về correctness, điều quan trọng là version phải đại diện cho snapshot client đã đọc, không phải version server vừa query lại trong request mutation.

Nếu muốn enforce transition mạnh hơn nữa, có thể dùng một conditional update với cả `Id`, expected `RowVersion` và expected `Status = Pending`; số rows affected bằng 0 nghĩa precondition không còn đúng. Cách triển khai cụ thể phải giữ semantics rõ ràng và vẫn cập nhật concurrency token đúng theo database/provider.

## Giải thích thiết kế sau khi sửa

Concurrency contract mới nối ba thời điểm với nhau:

1. Server đọc row và gửi version V1 cho client.
2. User quyết định dựa trên representation có V1.
3. Mutation chỉ được commit nếu database vẫn thỏa expected version V1 và business transition còn hợp lệ.

Nếu A commit trước, `RowVersion` chuyển thành V2. Request của B vẫn mang V1 nên update không được phép silently overwrite V2. UI phải reload và cho B thấy decision của A.

Điểm quan trọng là concurrency token không thay thế domain invariant. `RowVersion` trả lời “row có thay đổi không”; business rule trả lời “transition này còn hợp lệ không”. Cả hai cần được xét trong write path.

Không cần distributed lock chỉ vì hệ thống có nhiều application instances. Database concurrency token/conditional write là coordination point phù hợp cho một row trong SQL Server và tránh thêm operational complexity của distributed lock.

## Trade-offs

Optimistic concurrency làm user có thể gặp conflict và phải review/retry. Đây là chi phí UX có chủ đích để đổi lấy việc không silent overwrite. Nếu conflict frequency rất cao, cần xem lại workflow ownership hoặc serialization strategy thay vì chỉ tăng retry.

ETag tận dụng HTTP semantics và giữ version opaque, nhưng frontend/backend phải thống nhất encoding, quoting và cache behavior. Version trong body đơn giản hơn với một số client nhưng làm concurrency contract mang tính application-specific hơn.

Một conditional SQL update có thể giảm round trip, nhưng dễ làm domain logic/authorization khó đọc nếu nhồi quá nhiều điều kiện. Direct EF Core entity + explicit concurrency vẫn hợp lý khi throughput không yêu cầu tối ưu cực đoan.

Append-only audit tăng storage/write cost nhưng có giá trị cao nếu approval là nghiệp vụ cần accountability. Không nên log toàn bộ sensitive comment chỉ để debug concurrency.

## Cách kiểm thử

1. **Database concurrency integration test:** hai client đọc cùng version V1; A commit `Reject`, B dùng V1 commit `Approve`; B phải nhận conflict/precondition failure và final state vẫn là `Rejected`.
2. **Concurrent-request test:** chạy hai mutation song song từ hai DbContext/process paths; chỉ một valid transition từ `Pending` được commit.
3. **State-transition test:** request đã `Approved`/`Rejected` không được đổi ngược nếu business rule là single-decision.
4. **API contract test:** missing/malformed `If-Match` hoặc version body được xử lý theo contract rõ ràng; input decision ngoài domain trả validation error, không biến thành `Rejected`.
5. **Authorization test:** user có capability chung nhưng không có quyền trên resource cụ thể không thể quyết định record đó.

## Quan sát trong production

Theo dõi:

- số optimistic concurrency conflicts theo endpoint/resource type;
- tỷ lệ `409`/`412` và xu hướng theo release;
- successful decision transitions theo current→next state;
- correlation ID, approval ID, user subject và expected/current version dưới dạng safe hash/representation phù hợp;
- p95/p99 latency của mutation và SQL dependency;
- số lần invalid state transition bị từ chối;
- audit timeline cho successful decisions;
- alert nếu conflict rate tăng đột biến sau frontend/backend release vì có thể contract version bị sai.

Telemetry phải giúp trả lời: user đã nhìn version nào, server đang có version nào, transition nào được commit và request nào bị từ chối — mà không cần log dữ liệu nhạy cảm không liên quan.

## Câu hỏi phỏng vấn mở rộng

1. Nếu approval cho phép nhiều người vote chứ không phải một final decision duy nhất, bạn sẽ thay đổi data model/concurrency boundary như thế nào?
2. Khi nào pessimistic locking hợp lý hơn optimistic concurrency cho workflow kiểu này, và chi phí operational của nó là gì?
3. Nếu frontend offline vài giờ rồi submit command với version cũ, API nên trả gì và UX nên xử lý conflict ra sao?

# Code Review Challenge 2 — Octopus deploy copy đè trực tiếp vào IIS site gây 503, mixed binaries và rollback không đáng tin cậy

**Chủ đề:** IIS, Windows Server, Octopus Deploy, PowerShell, ASP.NET Core deployment, artifact immutability, load balancer draining, configuration/secrets, database migration, rollback  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một enterprise management portal ASP.NET Core chạy trên 4 Windows Server nodes sau load balancer. Mỗi node host application bằng IIS. Release package được TeamCity build một lần rồi Octopus Deploy triển khai lên các server.

Team muốn “zero downtime gần đúng” nên không stop toàn bộ website. Deployment step hiện copy package trực tiếp vào thư mục live của IIS từng server, chạy EF Core migration trên từng node rồi recycle App Pool.

Production thỉnh thoảng gặp:

- 502/503 trong vài chục giây khi release;
- request bắt đầu trước deploy nhưng kết thúc sau deploy có lỗi load assembly/file;
- 4 nodes đôi khi không chạy cùng một build sau một failed deployment;
- migration đôi lúc bị chạy đồng thời từ nhiều deployment targets;
- rollback application package không rollback được database schema;
- support khó xác định node nào đang chạy artifact nào;
- connection string production xuất hiện trong deployment script variable output ở một số log.

Deployment PowerShell step hiện tại:

## Gợi ý

### Gợi ý 1

Rủi ro chính là **mutating live deployment in place** trong khi node vẫn nhận traffic. Hãy xem artifact, process lifetime và load balancer membership như một deployment transaction có nhiều bước.

Application rollback và database rollback là hai bài toán khác nhau. Muốn rolling deployment an toàn, schema thường cần tương thích với cả old và new binaries trong cửa sổ chuyển tiếp.

## Kết quả code review tham khảo

### Critical — Secret bị ghi thẳng vào deployment log

**Vấn đề:** Script `Write-Host "Database: $connectionString"` in toàn bộ production connection string.

**Tại sao xảy ra:** Sensitive variable bị xử lý như diagnostic text bình thường.

**Ảnh hưởng production:** Credential có thể tồn tại trong Octopus task logs, export/log retention hoặc nơi người có quyền xem deployment log truy cập được. Blast radius có thể kéo dài tới khi rotate secret.

**Cách sửa:** Không log secret. Dùng sensitive variable/secret mechanism của deployment platform và truyền secret cho application/migration bằng kênh không expose trong command/log. Ưu tiên identity-based access khi platform/architecture hỗ trợ. Rotate credential nếu đã từng bị lộ.

### Critical — Copy đè trực tiếp vào live directory tạo mixed-version deployment

**Vấn đề:** `Copy-Item -Force` thay file từng bước trong thư mục IIS đang serve.

**Tại sao xảy ra:** Files của version mới và cũ có thể cùng tồn tại trong khoảng copy. Process cũ có thể đang giữ một số assemblies, còn static files/config/runtime load path thấy file mới. Một request mới cũng có thể chạm hệ thống giữa deployment.

**Ảnh hưởng production:** Lỗi assembly/file mismatch, static asset mismatch, startup failure, 5xx và behavior nondeterministic khó tái hiện. Nếu copy fail giữa chừng, live directory ở trạng thái không đại diện cho artifact nào hoàn chỉnh.

**Cách sửa:** Deploy artifact vào **versioned release directory riêng**, ví dụ `C:\Sites\EmployeePortal\releases\2026.09.13.32746`, validate đầy đủ, sau đó chuyển application path/symlink/junction hoặc cấu hình deployment target theo một atomic-ish cutover có kiểm soát. Không mutate artifact đang live file-by-file.

### Critical — Node vẫn nhận traffic trong lúc deploy/recycle

**Vấn đề:** Load balancer không drain node trước khi copy/recycle.

**Tại sao xảy ra:** Deployment orchestration không phối hợp với traffic management.

**Ảnh hưởng production:** In-flight request có thể bị cắt hoặc chạy qua mixed-version state; new requests tiếp tục vào node đang unavailable, tạo 502/503.

**Cách sửa:** Trước deployment, mark node unavailable/draining ở load balancer, chờ in-flight requests về dưới threshold hoặc hết bounded drain period, deploy/warm node, chạy readiness/smoke checks qua đúng network path cần thiết, rồi mới đưa node trở lại pool. Roll lần lượt để giữ capacity.

### High — Migration có thể chạy trên mọi deployment target

**Vấn đề:** Mỗi server chạy `dotnet EmployeePortal.dll --migrate`.

**Tại sao xảy ra:** Database migration bị đặt trong per-node deployment step thay vì có một migration owner.

**Ảnh hưởng production:** Nhiều migration processes có thể cạnh tranh lock, fail lẫn nhau hoặc tạo undefined operational behavior với migration script không idempotent. Deployment outcome giữa nodes khó đồng bộ.

**Cách sửa:** Tách migration thành explicit once-per-release step/job do một owner thực hiện. Migration phải được verify trước khi rollout app tiếp tục. Không giả định framework locking sẽ biến multi-node orchestration sai thành design đúng.

### High — Binary rollback không bảo đảm tương thích với schema mới

**Vấn đề:** Rollback chỉ deploy package cũ; database migration đã chạy có thể là breaking change.

**Tại sao xảy ra:** Application và schema lifecycle bị coi như có thể rollback cùng nhau bằng một thao tác file copy.

**Ảnh hưởng production:** Old binary có thể fail ngay sau rollback nếu column/table/API contract database đã bị đổi hoặc xóa.

**Cách sửa:** Thiết kế migrations theo **expand/contract** khi cần rolling/rollback safety: phase đầu thêm schema tương thích, deploy code chuyển tiếp, backfill nếu cần, chỉ remove old schema ở release sau khi không còn consumer cũ. Với destructive migration, cần explicit backup/recovery plan và rollback decision riêng.

### High — Health check sau `Start-Sleep 5` vừa brittle vừa kiểm tra chưa đủ

**Vấn đề:** Script chờ cố định 5 giây rồi gọi `http://localhost/health` một lần.

**Tại sao xảy ra:** Startup time được giả định cố định và localhost success bị dùng thay cho readiness qua production path.

**Ảnh hưởng production:** App chậm warm-up nhưng khỏe có thể bị coi là fail; app trả 200 quá sớm nhưng dependency/config chưa usable vẫn được đưa vào traffic nếu orchestration bên ngoài chỉ nhìn step success.

**Cách sửa:** Poll readiness có timeout/budget hữu hạn, yêu cầu consecutive success nếu cần, và xác minh endpoint phản ánh khả năng serve traffic. Sau local warm-up, có thể chạy smoke check qua node-specific/load-balancer path trước khi re-enable. Không biến deep dependency health thành liveness restart trigger một cách mù quáng.

### High — Không có immutable release identity trong deployment layout

**Vấn đề:** Tất cả release copy vào cùng `C:\Sites\EmployeePortal`.

**Tại sao xảy ra:** Artifact identity bị mất sau deployment.

**Ảnh hưởng production:** Support khó biết chính xác build nào đang chạy; rollback phải overwrite lại live directory; failed copy có thể để lại file thừa từ version khác.

**Cách sửa:** Mỗi release có directory immutable riêng và metadata chứa build/version/commit. Application expose safe build info endpoint hoặc telemetry dimension `service.version`. Cutover chỉ trỏ IIS tới release đã validate. Giữ một số release trước theo retention policy để rollback nhanh.

### High — Không có strategy cho in-flight request và graceful process shutdown

**Vấn đề:** Script recycle App Pool mà không thể hiện drain semantics hay bounded graceful shutdown.

**Tại sao xảy ra:** Process lifecycle bị xem như chỉ cần restart sau copy.

**Ảnh hưởng production:** Request dài, upload/export hoặc background work có thể bị cắt giữa chừng; retry phía client có thể tạo duplicate side effect nếu endpoint không idempotent.

**Cách sửa:** Drain traffic trước, cấu hình shutdown timeout phù hợp với request profile, propagate cancellation trong application và đảm bảo mutation quan trọng có idempotency khi client/proxy có thể retry. Không giữ drain vô hạn; có timeout và escalation rõ ràng.

### Medium — Script không fail-fast rõ ràng cho external command

**Vấn đề:** PowerShell không tự động biến mọi non-zero exit code của `dotnet ...` thành terminating error trong mọi cách gọi/script style.

**Tại sao xảy ra:** Script không kiểm tra `$LASTEXITCODE` sau migration command.

**Ảnh hưởng production:** Migration có thể fail nhưng script vẫn tiếp tục recycle/health-check; release state trở nên khó đoán.

**Cách sửa:** Kiểm tra exit code và throw ngay. Dùng wrapper/helper chuẩn hóa execution của native commands. Mỗi deployment phase phải có explicit success criterion.

### Medium — Rollout capacity và target ordering chưa được kiểm soát

**Vấn đề:** Flow không thể hiện số nodes tối đa được deploy cùng lúc.

**Tại sao xảy ra:** Per-target script không đủ để mô hình hóa cluster-level availability.

**Ảnh hưởng production:** Nếu nhiều nodes drain/recycle cùng lúc, remaining capacity không đủ cho traffic và gây latency/503 dù từng node deploy “đúng”.

**Cách sửa:** Orchestrate rolling batches, thường một node tại một thời điểm khi capacity nhỏ, hoặc một batch size được chứng minh bằng headroom/load data. Abort rollout khi error budget/readiness không đạt.

### Medium — Local health check không chứng minh configuration/network production path

**Vấn đề:** `localhost` bypass load balancer, TLS termination, host header/routing và một phần network path.

**Tại sao xảy ra:** Smoke test chỉ kiểm tra process trên node.

**Ảnh hưởng production:** Node có thể local-healthy nhưng lỗi certificate binding, host routing hoặc LB membership vẫn làm user request fail.

**Cách sửa:** Dùng nhiều lớp validation: local readiness để biết process sẵn sàng; node-specific synthetic qua ingress/LB path nếu platform cho phép; sau re-enable theo dõi real traffic/error telemetry trước khi chuyển node tiếp theo.

### Medium — Không có explicit cleanup/retention cho release artifacts và failed releases

**Vấn đề:** Nếu chuyển sang versioned directories nhưng không có lifecycle policy, disk sẽ tăng không giới hạn.

**Tại sao xảy ra:** Rollback retention thường được thêm sau cùng.

**Ảnh hưởng production:** Disk pressure có thể làm deployment/startup fail và tạo incident mới.

**Cách sửa:** Giữ N release gần nhất hoặc retention theo policy, không xóa current/previous known-good release, monitor disk space trước deployment.

## Phiên bản đề xuất

Một deployment flow an toàn hơn nên do Octopus orchestration điều khiển ở cấp cluster, còn script trên từng node chỉ thực hiện thao tác deterministic cho một release cụ thể.

Ví dụ node-level PowerShell rút gọn:

```powershell
$ErrorActionPreference = "Stop"

$siteName = "EmployeePortal"
$appPool = "EmployeePortalPool"
$releaseId = $OctopusParameters["Octopus.Release.Number"]
$packagePath = $OctopusParameters["Octopus.Action.Package.InstallationDirectoryPath"]
$root = "C:\Sites\EmployeePortal"
$releasePath = Join-Path $root "releases\$releaseId"

Import-Module WebAdministration

if (Test-Path $releasePath) {
    throw "Release directory already exists: $releasePath"
}

New-Item -ItemType Directory -Path $releasePath | Out-Null
Copy-Item -Path "$packagePath\*" -Destination $releasePath -Recurse

# Validate expected files before cutover.
$entryAssembly = Join-Path $releasePath "EmployeePortal.dll"
if (-not (Test-Path $entryAssembly)) {
    throw "Missing EmployeePortal.dll"
}

# Traffic draining is performed by an Octopus/LB step before this script.
# Database migration is a separate run-once release step.

$appPath = "IIS:\Sites\$siteName"
Set-ItemProperty $appPath -Name physicalPath -Value $releasePath

Restart-WebAppPool -Name $appPool

$deadline = (Get-Date).AddMinutes(2)
$ready = $false

while ((Get-Date) -lt $deadline) {
    try {
        $response = Invoke-WebRequest `
            -Uri "http://localhost/health/ready" `
            -UseBasicParsing `
            -TimeoutSec 3

        if ($response.StatusCode -eq 200) {
            $ready = $true
            break
        }
    }
    catch {
        Start-Sleep -Seconds 3
        continue
    }

    Start-Sleep -Seconds 3
}

if (-not $ready) {
    throw "Node did not become ready before timeout"
}

Write-Host "Release $releaseId is ready on $env:COMPUTERNAME"
```

Flow cấp release nên tách thành các phase:

1. Build package **một lần** trong TeamCity; artifact có immutable version/commit identity.
2. Pre-deployment validation: capacity, disk, backup/recovery preconditions và release metadata.
3. Run database migration **một lần** nếu release cần; migration phải compatible với old/new app trong rolling window.
4. Với từng node/batch:
   - remove/drain khỏi load balancer;
   - chờ bounded in-flight drain;
   - copy package vào release directory mới;
   - validate artifact;
   - switch IIS physical path/cutover;
   - start/recycle process;
   - poll readiness;
   - chạy smoke test;
   - đưa node trở lại load balancer;
   - quan sát error/latency trước khi tiếp tục.
5. Nếu node fail, dừng rollout và trỏ node về known-good release directory khi schema vẫn backward-compatible.
6. Cleanup old releases theo retention sau khi rollout ổn định.

Secret không được echo. Connection string/migration credential cần lấy từ secure deployment variable hoặc secret store, và command invocation không nên làm secret xuất hiện trong task log/process diagnostics nếu có thể tránh.

## Giải thích thiết kế sau khi sửa

Trọng tâm là biến artifact thành immutable unit. Thay vì “biến đổi thư mục live từ version A thành B”, deployment chuẩn bị hoàn chỉnh version B ở nơi khác rồi mới cut over. Nếu prepare fail, version A không bị mutate.

Traffic drain tách user availability khỏi file/process mutation. Node chỉ quay lại load balancer sau khi application đã warm và readiness pass. Rolling orchestration giữ đủ capacity trong suốt release.

Migration có owner riêng vì database là shared resource. Với 4 app nodes, schema change không phải per-node concern. Expand/contract giúp old binaries và new binaries cùng tồn tại tạm thời trong rolling deployment mà không phá nhau.

Rollback application đáng tin cậy hơn khi chỉ cần trỏ lại known-good release directory. Tuy nhiên rollback chỉ an toàn nếu schema hiện tại vẫn tương thích. Vì vậy release design phải quyết định rollback strategy trước khi chạy destructive migration.

## Trade-offs

Versioned directories dùng thêm disk và cần cleanup. Đổi lại, artifact identity, rollback và forensic debugging rõ ràng hơn.

Draining từng node làm deployment lâu hơn so với deploy song song toàn cluster. Đổi lại availability risk thấp hơn. Batch size nên dựa trên traffic headroom/SLO, không phải một con số cố định cho mọi hệ thống.

Expand/contract làm schema migration kéo dài qua nhiều release và tăng temporary complexity. Với hệ thống downtime được phép, maintenance window có thể đơn giản hơn và đôi khi là quyết định đúng. Senior-level design phải cân cost of zero downtime với business requirement thật.

Một local readiness endpoint không thể chứng minh toàn bộ production path; synthetic check qua load balancer tăng confidence nhưng cũng cần route/node targeting hợp lý. Không nên làm deployment phụ thuộc vào một health check quá sâu và flaky.

Giữ previous release giúp rollback nhanh nhưng không thay thế backup/data recovery. Nếu release có data transformation không đảo ngược, cần explicit recovery strategy.

## Cách kiểm thử

1. **Deployment rehearsal:** deploy A→B trên staging với representative traffic; xác minh không có mixed binaries và node không nhận request trong cutover window.
2. **Failure-path test:** cố tình làm copy/validation của release B fail trước cutover; IIS phải vẫn trỏ tới A và A vẫn phục vụ được.
3. **Rolling capacity/load test:** giữ tải gần expected peak, drain/deploy từng node và theo dõi p95/p99, 5xx cùng remaining capacity.
4. **Migration compatibility test:** chạy old binary với expanded schema và new binary với cùng transitional schema; xác minh cả hai hoạt động trong rolling window và rollback app vẫn khả thi.
5. **Secret/log validation:** scan task logs/artifacts để bảo đảm connection string/password không xuất hiện; xác minh release/version metadata được phát ra đúng trên mỗi node.

## Quan sát trong production

Theo dõi:

- `service.version`/release ID/commit SHA theo từng server;
- load balancer node state: draining, healthy, unhealthy;
- active/in-flight request count trước cutover;
- HTTP 5xx/502/503 và p50/p95/p99 theo node/version;
- App Pool/process restart count và startup duration;
- readiness/smoke-check duration và failures;
- deployment phase duration theo node;
- database migration version, duration và outcome;
- IIS/ASP.NET Core logs correlated với release ID;
- disk free space và số retained release directories;
- alert nếu cluster đồng thời có nhiều version ngoài expected rolling window hoặc node không trở lại healthy trong deployment budget.

Một dashboard release nên cho phép trả lời ngay: “node nào đang chạy build nào, từ lúc nào, migration version nào đã apply, node nào đang drain và error rate thay đổi từ bước nào”.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- EF Core concurrency token chỉ bảo vệ đúng khi expected version đại diện cho state mà caller thực sự dựa vào. `RowVersion` nằm trên entity nhưng không round-trip qua client không tự giải quyết stale UI updates.
- `DbUpdateConcurrencyException` là tín hiệu conflict cần business resolution; reload rồi overwrite tự động có thể vô hiệu hóa optimistic concurrency.
- Business state transition và database concurrency là hai lớp khác nhau: một record không đổi version vẫn có thể ở trạng thái không cho phép command hiện tại.
- IIS/Windows deployment an toàn không nên mutate live artifact file-by-file trong lúc node vẫn nhận traffic.
- Artifact immutability, traffic draining, release identity, readiness, migration ownership và rollback compatibility đều là một phần của application reliability.
- Database schema rollout phải được thiết kế cùng application rollout; rollback binary không đồng nghĩa rollback schema.

## Mẫu tư duy cần nhớ

- Concurrency control phải bảo vệ **assumption mà user/client đã nhìn thấy**, không chỉ khoảng thời gian query→save trong một request.
- Conflict không phải lúc nào cũng là transient error để retry; đôi khi nó là business information cần đưa về caller.
- Chuẩn bị artifact hoàn chỉnh trước, rồi cut over; đừng biến production directory thành workspace build/deploy.
- Drain → deploy → warm → verify → re-enable → observe trước khi chuyển sang node tiếp theo.
- Thiết kế migration cùng rollback path và cửa sổ coexistence của old/new versions.
