# Câu 1 — `IAsyncDisposable`, streaming và resource lifetime khi request bị hủy

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET, `IAsyncDisposable`, `await using`, ASP.NET Core cancellation, streaming, resource lifetime

## Bối cảnh

Một ASP.NET Core endpoint tạo file export lớn. Service mở một resource bất đồng bộ, đọc dữ liệu theo stream rồi ghi ra response. Trong load test, khi client đóng browser giữa chừng, một số resource vẫn giữ lâu hơn dự kiến và số connection tới dependency tăng. Team đang tranh luận liệu chỉ cần `using`, `await using`, hay `try/finally`.

Dependency implements `IAsyncDisposable`; việc cleanup có thể cần I/O. Endpoint nhận `HttpContext.RequestAborted`. Không có bằng chứng rằng GC pressure là nguyên nhân chính.

## Câu hỏi chính

Hãy giải thích cơ chế resource lifetime trong flow async này, sự khác nhau thực tế giữa `IDisposable` và `IAsyncDisposable`, `await using` được hạ xuống thành control flow nào, cancellation ảnh hưởng đến operation và cleanup ra sao, và bạn sẽ xác minh resource leak/slow cleanup trong production như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Resource có implement cả `IDisposable` và `IAsyncDisposable` không, và contract cleanup của dependency là gì?
2. Cancellation xảy ra ở read, write response hay trong cleanup?
3. Cleanup có được phép bị hủy hay phải cố hoàn tất để trả resource về pool?
4. Connection count tăng là active, idle, leaked hay pool waiters?
5. Endpoint có buffering toàn bộ file hay streaming từng chunk?

## Gợi ý tư duy

### Gợi ý 1

Đừng đồng nhất cancellation với disposal; đây là hai lifecycle concerns liên quan nhưng không giống nhau.

### Gợi ý 2

Hãy hình dung `await using` như `try/finally` có `await DisposeAsync()` trong đường thoát scope.

### Gợi ý 3

Xem xét mọi exit path: success, exception, request cancellation và exception phát sinh trong cleanup.

## Cấu trúc trả lời đề xuất

1. Làm rõ resource contract.
2. Giải thích lexical scope và compiler-generated cleanup path.
3. Phân biệt synchronous và asynchronous cleanup.
4. Theo cancellation từ request tới read/write.
5. Xác định cleanup guarantee và failure behavior.
6. Đề xuất implementation.
7. Test cancellation/failure.
8. Đo resource/pool telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `await using` bảo đảm `DisposeAsync()` được await khi rời scope, kể cả khi body throw.
- Cancellation token không tự động dispose resource; code phải propagate token vào operations hỗ trợ cancellation và vẫn giữ cleanup path.
- Không nên dựa vào finalizer/GC để giải phóng scarce external resource đúng lúc.
- Cleanup cần tuân theo contract của dependency; không tự giả định `DisposeAsync` nhận request token.

### Điểm cộng

- Phân biệt cancellation của business operation với cleanup thường cần hoàn tất để restore invariant/trả resource.
- Nhắc đến exception handling khi body và disposal đều có thể fail.
- Đo pool usage, active resource count, request abort count, dependency duration và cleanup duration.

### Senior+

- Phân tích ownership: method nào tạo resource thì method đó thường chịu trách nhiệm dispose, trừ khi ownership được transfer rõ ràng.
- Không giữ resource sống lâu hơn streaming scope cần thiết.
- Nếu response streaming phụ thuộc resource, disposal chỉ được xảy ra sau lần đọc cuối/stream completion.

## Hướng giải quyết tham khảo

Nếu factory trả object implement `IAsyncDisposable`, code nên giữ ownership rõ ràng:

```csharp
public async Task StreamExportAsync(
    HttpResponse response,
    CancellationToken cancellationToken)
{
    await using var export = await _factory.OpenAsync(cancellationToken);

    await foreach (var chunk in export.ReadAsync(cancellationToken)
                                      .WithCancellation(cancellationToken))
    {
        await response.Body.WriteAsync(chunk, cancellationToken);
    }
}
```

`await using` conceptually tạo `try/finally`; khi scope kết thúc, `DisposeAsync()` được gọi và await. Request cancellation có thể làm `OpenAsync`, enumeration hoặc `WriteAsync` throw `OperationCanceledException`, nhưng stack unwinding vẫn đi qua disposal path.

Không nên mặc định truyền request cancellation vào cleanup nếu API không hỗ trợ hoặc nếu hủy cleanup có thể để resource ở trạng thái không an toàn. Cần đọc contract của dependency. Nếu cleanup có thể treo lâu, đó là một vấn đề riêng cần timeout/telemetry theo API được hỗ trợ, không phải lý do bỏ disposal.

Để xác minh production, correlate request abort với active dependency connections, pool wait time, cleanup duration và exception telemetry. Nếu connection count chỉ cao do dependency latency, sửa disposal sẽ không giải quyết root cause.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ bắt đầu bằng ownership và contract của resource. Nếu method mở một resource có async cleanup thì tôi dùng `await using` để bảo đảm mọi exit path đều await `DisposeAsync`. Cancellation của request chỉ dừng những operation mà token được propagate tới; nó không thay thế disposal. Nếu client disconnect trong lúc stream, read hoặc response write có thể throw cancellation, sau đó stack unwind và cleanup vẫn phải chạy. Tôi cũng không mặc định cleanup nên dùng cùng request token vì có những resource cần hoàn tất cleanup để trả connection về pool. Tôi sẽ xác minh bằng telemetry: request abort, active connections, pool wait, dependency duration và cleanup duration. Sau đó viết integration test hủy request giữa stream, test dependency throw và kiểm tra resource luôn được dispose đúng một lần.”

## Câu hỏi đào sâu

1. Nếu resource implement cả `IDisposable` và `IAsyncDisposable`, bạn chọn đường nào và dựa trên contract gì?
2. Nếu `DisposeAsync()` mất 10 giây khi dependency gặp sự cố, bạn sẽ xử lý mà không biến cleanup thành resource leak như thế nào?
3. Tôi đề xuất copy toàn bộ export vào `MemoryStream`, dispose dependency sớm rồi mới gửi response; bạn phản biện thế nào với file 2 GB?

## Lỗi trả lời thường gặp

- Nói cancellation tự động giải phóng resource.
- Dựa vào GC/finalizer cho connection/file/network resource.
- Dùng `using` cho mọi async resource mà không xem contract.
- Không xem ownership và streaming lifetime.
- Chẩn đoán “leak” chỉ từ connection count mà không đo pool/dependency behavior.

## Thang điểm 0–10

- 0–3: chỉ định nghĩa `Dispose`/`DisposeAsync`, không giải thích lifecycle.
- 4–6: hiểu `await using`, cancellation và exception path nhưng thiếu production verification.
- 7–8: reasoning đúng về ownership, cleanup, streaming, tests và telemetry.
- 9–10: phân tích conditional behavior, cleanup failure, pool/resource evidence và trade-offs rõ ràng.

# Câu 2 — Production incident: Cosmos DB latency và RU tăng đột biến sau khi mở rộng traffic

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partitioning, query cost, ASP.NET Core, Azure Monitor/Application Insights, incident response

## Bối cảnh

Một ASP.NET Core API đọc lịch sử hoạt động từ Cosmos DB. Sau khi một khách hàng enterprise tăng traffic, p95 API tăng từ mức bình thường lên vài giây; một số requests bị throttling/retry. Tổng RU consumption tăng mạnh dù tổng document count chỉ tăng nhẹ.

Container hiện dùng partition key `/tenantId`. Endpoint phổ biến lọc theo `tenantId`, `userId` và khoảng thời gian. Một tenant mới chiếm phần lớn traffic. Team đề xuất ngay lập tức tăng provisioned throughput và thêm Redis.

Chưa có bằng chứng kết luận hot partition, query shape, SDK retry hay downstream network là root cause duy nhất.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ stabilization đến root cause và long-term prevention như thế nào? Hãy nêu evidence cần thu thập, các competing hypotheses, cách kiểm tra partition/query assumptions, và khi nào scale throughput, redesign partitioning hoặc cache là hợp lý.

## Câu hỏi làm rõ nên cân nhắc

1. Workload là point read, query trong một partition hay cross-partition query?
2. RU/429 phân bố theo tenant/partition key và operation type như thế nào?
3. Data/traffic skew của tenant lớn đến mức nào và có temporal hot key không?
4. SDK retry policy và end-to-end request timeout hiện tại ra sao?
5. Freshness/consistency requirement có cho phép cache không?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu bằng impact và stabilization, không bắt đầu bằng redesign partition key.

### Gợi ý 2

Tách “tổng RU cao” khỏi “một logical/physical partition bị nóng”; cần evidence theo operation/partition.

### Gợi ý 3

Query shape, indexing, result cardinality, partition targeting, traffic skew và retry amplification đều có thể cùng góp phần.

## Cấu trúc trả lời đề xuất

1. Xác định business/user impact.
2. Stabilize bằng biện pháp reversible.
3. Thu thập p95/p99, 429, RU/request, dependency telemetry.
4. Phân nhóm operation/query/tenant.
5. Đưa ra nhiều hypotheses.
6. Kiểm tra partition targeting và query/index behavior.
7. Chọn short-term remediation.
8. Đánh giá partition redesign/cache/scale cho dài hạn.
9. Load/failure test.
10. Thiết lập SLO/dashboard/alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận chỉ từ tổng RU.
- Đo RU charge/request, 429/throttling, latency, retry, tenant/partition distribution và query shape.
- Stabilization có thể gồm tăng throughput tạm thời nếu evidence cho thấy capacity pressure và cost chấp nhận được.
- Cache chỉ phù hợp nếu read reuse và freshness semantics hỗ trợ.

### Điểm cộng

- Phân biệt point reads với queries.
- Xem query có target đúng partition key không và index policy có phù hợp query pattern không.
- Nhận ra `/tenantId` có thể tốt cho isolation/query locality nhưng tenant cực lớn có thể tạo skew; redesign cần migration plan.

### Senior+

- Đánh giá hierarchical/synthetic partitioning như một design alternative theo capability/version hiện hành thay vì khẳng định API cụ thể không kiểm chứng.
- Xem retry amplification: 429 + automatic retries có thể kéo end-to-end latency lên.
- Xây per-tenant fairness/rate limit nếu business cần bảo vệ noisy-neighbor behavior.

## Hướng giải quyết tham khảo

Đầu tiên xác định scope: tenant nào, endpoint nào, thời điểm nào, error/latency percentile nào bị ảnh hưởng. Nếu 429 và RU saturation rõ ràng, có thể tăng throughput tạm thời để giảm impact trong khi điều tra; đây là stabilization, không phải RCA.

Từ Application Insights/Azure Monitor và Cosmos diagnostics, phân tích request charge, status/substatus phù hợp, retry, duration, operation/query và partition targeting. Kiểm tra endpoint có truyền `tenantId` theo cách cho phép SDK/service target partition hay vô tình chạy broader query. So sánh query plan/index utilization theo tooling chính thức hiện hành.

Các hypotheses gồm: tenant traffic skew tạo hot partition; query mới trả nhiều records; index/query regression; retry amplification; một code release bỏ partition-key constraint; hoặc dependency/network issue không liên quan RU. Mỗi hypothesis cần evidence riêng.

Nếu `/tenantId` không còn đáp ứng scale vì một tenant vượt giới hạn/throughput distribution phù hợp, redesign partitioning là data-model migration, không phải config toggle. Cần dual-read/write hoặc backfill strategy, validation, rollback/roll-forward và cost analysis. Redis chỉ nên thêm nếu access pattern có high reuse và stale tolerance; cache không sửa write hot partition và tạo invalidation/outage modes mới.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng Redis hay đổi partition key. Trước hết tôi xác định tenant và operation nào tạo p95/429, rồi nếu capacity đang gây user impact thì scale throughput tạm thời như một biện pháp reversible. Sau đó tôi dùng Cosmos diagnostics và Application Insights để xem RU per request, retry, query shape, partition targeting và traffic distribution. Tôi giữ nhiều hypotheses: hot tenant, query regression, cross-partition behavior, indexing, retry amplification hoặc network. Nếu tenantId vẫn cho query locality tốt nhưng một tenant quá lớn, tôi mới đánh giá partitioning strategy khác và migration plan. Cache chỉ có ý nghĩa nếu dữ liệu được đọc lặp lại và freshness cho phép. Cuối cùng tôi load-test workload skew, alert trên 429, RU/request và p95/p99 thay vì chỉ tổng RU.”

## Câu hỏi đào sâu

1. Nếu tăng throughput làm 429 biến mất nhưng RU/request vẫn tăng gấp 10, bạn kết luận gì tiếp theo?
2. Nếu tenant lớn cần strong freshness cho activity feed, đề xuất Redis của bạn thay đổi thế nào?
3. Nếu Product yêu cầu onboarding tenant lớn trong hai tuần, bạn chọn mitigation ngắn hạn nào thay vì partition migration lớn?

## Lỗi trả lời thường gặp

- Thấy 429 là lập tức “tăng RU” và dừng điều tra.
- Thấy read chậm là mặc định thêm Redis.
- Không phân tích traffic skew/partition targeting.
- Không đo RU/request và retry amplification.
- Đề xuất repartition production data mà không có migration/verification strategy.

## Thang điểm 0–10

- 0–3: giải pháp theo công cụ, thiếu evidence.
- 4–6: biết RU/partition/query nhưng RCA tuyến tính và thiếu stabilization/telemetry.
- 7–8: incident reasoning đầy đủ, hypotheses và trade-offs tốt.
- 9–10: kết nối workload skew, retry, partition model, migration, cost và SLO một cách có điều kiện.

# Câu 3 — Thiết kế nền tảng E2E testing bằng Playwright cho nhiều frontend và backend environments

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Playwright, testing architecture, CI/CD, test data, ASP.NET Core integration, release safety, observability

## Bối cảnh

Một tổ chức có React/Vue frontend và ASP.NET Core APIs. Hiện QA chạy manual regression trước release; một số teams đã thêm Playwright tests nhưng tests flaky, dùng chung account và phụ thuộc dữ liệu tồn tại sẵn trong staging. CI có parallel workers; các suites đôi lúc sửa cùng một order/user rồi fail ngẫu nhiên.

Mục tiêu là tạo E2E platform đủ tin cậy để chặn release với một tập critical journeys, nhưng không biến toàn bộ test pyramid thành browser tests. Environments có giới hạn dữ liệu và third-party integrations không phải lúc nào cũng ổn định.

## Câu hỏi chính

Hãy thiết kế testing strategy và architecture cho Playwright E2E: test boundaries, data isolation, authentication, parallelism, external dependencies, CI artifacts, flakiness policy, release gates và cách kết hợp với unit/integration/API tests. Nêu trade-offs giữa realism, speed, determinism và maintenance cost.

## Câu hỏi làm rõ nên cân nhắc

1. Critical user journeys nào thực sự phải được browser-level verification?
2. Có API/test fixture nào được phép tạo dữ liệu riêng cho mỗi test/worker không?
3. Third-party nào cần test thật và dependency nào có thể stub ở lower environments?
4. CI budget và acceptable release-gate duration là bao nhiêu?
5. Authentication có MFA/SSO khiến UI login mỗi test không thực tế không?

## Gợi ý tư duy

### Gợi ý 1

Flaky test thường là test architecture/data ownership problem, không chỉ là “cần retry”.

### Gợi ý 2

Tách deterministic setup khỏi browser interaction; mỗi worker cần ownership dữ liệu rõ ràng.

### Gợi ý 3

Release gate nên nhỏ, high-signal và có artifacts đủ để debug; broad regression có thể chạy ở tầng/lịch khác.

## Cấu trúc trả lời đề xuất

1. Xác định risk và critical journeys.
2. Phân tầng test pyramid.
3. Thiết kế environment/test-data ownership.
4. Authentication/session strategy.
5. Parallelism/isolation.
6. External dependency strategy.
7. CI execution và artifacts.
8. Flake quarantine/retry policy.
9. Release gate criteria.
10. Telemetry và maintenance governance.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không dùng shared mutable account/data cho parallel tests.
- E2E chỉ cover critical cross-boundary behavior; logic chi tiết ở unit/integration/API tests.
- Test setup phải deterministic và cleanup/unique namespace rõ ràng.
- Retry không được dùng để che nondeterminism.
- Lưu trace/screenshot/video/logs có chọn lọc cho failure diagnosis.

### Điểm cộng

- Worker-scoped identities/test data.
- API-based setup thay vì click UI để tạo mọi prerequisite.
- Storage state/session reuse theo security constraints thay vì login UI mỗi test.
- Contract/sandbox strategy cho third-party.

### Senior+

- Phân biệt release-gating suite với broader scheduled regression.
- Quarantine policy có owner/expiry thay vì bỏ qua flaky test vô thời hạn.
- Correlate browser test với backend trace/correlation ID để debug end-to-end.

## Hướng giải quyết tham khảo

Bắt đầu từ risk: chọn vài journeys như login/authorization, checkout/approval hoặc critical CRUD flow làm gate. Business rules và edge cases nên nằm chủ yếu ở unit/integration/API layers vì nhanh và deterministic hơn.

Mỗi Playwright worker/test cần data namespace riêng: unique user/order IDs hoặc fixture API tạo dữ liệu. Không phụ thuộc staging state tồn tại từ hôm qua. Setup bằng API/database fixture được kiểm soát thường nhanh và ổn định hơn dùng UI cho prerequisite; UI chỉ nên test behavior cần browser.

Authentication có thể dùng pre-authenticated storage state theo role nếu security model cho phép, nhưng phải bảo vệ secrets và tránh share mutable session sai cách. Third-party critical contract có thể có một số sandbox tests; phần lớn gate nên kiểm soát dependency để không biến outage của vendor thành false release failure nếu mục tiêu test là application behavior.

CI lưu Playwright trace cho failure, screenshot/video khi hữu ích, console/network errors và backend correlation. Retry có thể dùng hạn chế để thu thập signal nhưng một test chỉ pass sau retry phải được đo như flaky, không coi là healthy. Release gate cần timeout rõ, owner và policy khi infrastructure failure khác product regression.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chuyển manual regression thành hàng trăm browser tests. Tôi chọn critical journeys có giá trị cross-boundary để làm Playwright gate, còn business logic nằm ở unit, integration và API tests. Vấn đề flaky hiện tại trước hết là shared state: mỗi worker phải có identity và data riêng, setup deterministic qua fixture/API thay vì dựa vào staging. Tôi sẽ reuse authenticated storage state theo role nếu security cho phép, nhưng không share mutable user state. Với third-party, tôi phân biệt contract/sandbox verification với deterministic release gate. Khi fail, CI phải giữ trace và correlation để nối browser với backend telemetry. Retry không phải fix; tôi đo flake rate, quarantine có owner/expiry, và chỉ giữ gate nhỏ, nhanh, high-signal.”

## Câu hỏi đào sâu

1. Nếu QA yêu cầu mọi E2E đều chạy với real third-party sandbox trước mỗi release, bạn sẽ thương lượng architecture và risk như thế nào?
2. Nếu database không cho phép cleanup dữ liệu test, bạn thiết kế isolation/retention ra sao?
3. Tôi đề xuất `retries: 3` và chỉ fail pipeline khi cả bốn attempts đều fail; tại sao cách đó có thể làm release gate mất giá trị?

## Lỗi trả lời thường gặp

- Dùng Playwright để test mọi business rule.
- Shared account/data giữa parallel workers.
- Dùng retry để che flakiness.
- Không lưu trace/artifacts nên failure không debug được.
- Gate trực tiếp trên unstable third-party mà không định nghĩa mục tiêu test/failure ownership.

## Thang điểm 0–10

- 0–3: chỉ nói viết thêm E2E tests.
- 4–6: biết Playwright/CI nhưng thiếu data isolation và flake governance.
- 7–8: strategy cân bằng pyramid, deterministic setup, artifacts và release gates.
- 9–10: reasoning rõ về risk, environment ownership, external dependencies, security, observability và operational cost.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Resource ownership phải rõ ràng ngay cả khi request bị cancellation; cancellation không thay thế disposal.
