# Câu 1 — React effect, closure và kết quả tìm kiếm bị đảo thứ tự

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** React, TypeScript, JavaScript event loop, HTTP cancellation

## Bối cảnh

Portal nhân sự React + ASP.NET Core có ô tìm kiếm nhân viên. Người dùng nhập 'an' rồi 'anna'; đôi khi UI hiển thị kết quả 'an' dù input là 'anna'. Mỗi thay đổi query chạy useEffect gọi fetch và setResults. Response latency 50–800 ms, HTTP đều 200. Product không muốn thay đổi API contract.

## Câu hỏi chính

Giải thích chính xác runtime behavior, chứng minh nguyên nhân và sửa state correctness dưới response reorder, unmount và network failure.

## Câu hỏi làm rõ nên cân nhắc

1. Effect có cleanup không và query có debounce?
2. Có cache/service worker hoặc request deduplication?
3. Có giữ kết quả cũ trong lúc loading không?
4. Lỗi chỉ ở React StrictMode development hay cả production?
5. Có yêu cầu tránh log PII trong search query?

## Gợi ý tư duy

### Gợi ý 1

Xem thứ tự hoàn tất của promises, không chỉ thứ tự gửi.

### Gợi ý 2

Mỗi effect giữ closure riêng; cleanup không tự động chặn mọi callback.

### Gợi ý 3

Kết hợp AbortController và guard trước mọi state commit.

## Cấu trúc trả lời đề xuất

1. Xác định invariant UI-query.
2. Dựng timeline hai request.
3. Đo và tái hiện.
4. Thiết kế cancellation + commit guard.
5. Test race/failure và đo production.

## Ý chính của câu trả lời tốt

### Bắt buộc

Giải thích stale response ghi đè state; phân biệt debounce và correctness; xử lý success/error/loading.

### Điểm cộng

AbortController giảm request thừa nhưng không thay thế guard; encodeURIComponent, non-2xx và empty query.

### Senior+

Phân tích query-key cache, stale display UX, request identity, PII-safe telemetry.

## Hướng giải quyết tham khảo

Giả sử render A giữ query='an', render B giữ query='anna'. B hoàn thành trước, cập nhật đúng danh sách; A hoàn thành sau và ghi đè. React không đảm bảo network responses theo thứ tự gửi. Một implementation tối thiểu, giả định Employee/EmployeeList đã có:

```tsx
function EmployeeSearch({ query }: { query: string }) {
  const [items, setItems] = React.useState<Employee[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState<string | null>(null);
  React.useEffect(() => {
    const controller = new AbortController();
    let active = true;
    const q = query.trim();
    if (!q) {
      setItems([]); setLoading(false); setError(null);
      return () => { active = false; controller.abort(); };
    }
    setLoading(true); setError(null); setItems([]);
    (async () => {
      try {
        const response = await fetch(
          `/api/employees?q=${encodeURIComponent(q)}`,
          { signal: controller.signal });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const result: Employee[] = await response.json();
        if (active) setItems(result);
      } catch (e) {
        if (active && !controller.signal.aborted)
          setError("Không tải được danh sách");
      } finally {
        if (active) setLoading(false);
      }
    })();
    return () => { active = false; controller.abort(); };
  }, [query]);
  return <EmployeeList items={items} loading={loading} error={error} />;
}
```

Cleanup vô hiệu hóa effect cũ ngay cả khi promise resolve sau abort. Reset items khi query đổi để không hiển thị sai dữ liệu; nếu UX muốn previous results, gắn results với query và đánh dấu stale. Debounce chỉ giảm traffic. Chứng minh bằng test mock delay đảo thứ tự, Network waterfall, log request sequence và state commit (không log query nhạy cảm). StrictMode có thể khiến effect chạy thêm trong development nhưng không phải điều kiện cần. Backend cancellation không đảm bảo request chưa gây side effects; ở đây GET phải không có side effects.

## Mẫu trả lời trong phỏng vấn

Em kiểm tra request timeline trước. Mỗi useEffect giữ query của render tương ứng nhưng response có thể về ngược thứ tự; callback cũ vẫn setState sau callback mới. Em mô phỏng request đầu chậm hơn request sau, rồi thêm cleanup AbortController và guard active cho success, error và loading. Debounce chỉ giảm request, không bảo đảm correctness. Khi query đổi, em làm rõ UX có cho hiển thị previous results không. Sau đó em test rapid typing, unmount, timeout và theo dõi latency, abort count, UI mismatch mà không log PII.

## Câu hỏi đào sâu

1. Nếu fetch hoàn tất nhưng response.json còn pending lúc cleanup thì sao?
2. Nếu muốn giữ previous results để tránh layout shift, state model nào phù hợp?
3. Data-fetching library có loại bỏ mọi stale-data risk không?

## Lỗi trả lời thường gặp

- Đổ lỗi cho backend khi chưa có evidence.
- Chỉ thêm debounce.
- Bỏ qua stale error/loading.
- Chỉ test response theo đúng thứ tự.

## Thang điểm 0–10

- Clarification/invariant: 1
- Runtime mechanism: 2
- Evidence và competing hypotheses: 2
- Correctness fix: 2
- Trade-offs: 1
- Tests/telemetry/communication: 2

# Câu 2 — Service Bus DLQ tăng sau rollout schema

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, schema evolution, idempotency, CRM integration

## Bối cảnh

E-commerce phát OrderConfirmed lên Azure Service Bus topic; .NET Worker Service đọc subscription để cập nhật CRM. Sau rollout producer, DLQ và backlog tăng, consumer CPU thấp, health check xanh; log có deserialization errors và CRM timeouts. Không được mất order. SLA đồng bộ 15 phút là giả định cần xác nhận. Producer/consumer deploy độc lập.

## Câu hỏi chính

Điều tra incident theo impact → stabilize → evidence → hypotheses → verification → root cause → remediation → prevention, bảo toàn dữ liệu và tránh duplicate CRM writes.

## Câu hỏi làm rõ nên cân nhắc

1. DLQ reason, delivery count, oldest age theo version?
2. CRM có idempotent upsert, rate limit, Retry-After không?
3. Producer đã đổi schema thế nào, có consumer version cũ?
4. Có sessions/ordering requirements không?
5. Có runbook replay và audit chưa?

## Gợi ý tư duy

### Gợi ý 1

Tách permanent failures và transient failures.

### Gợi ý 2

Health check process xanh không chứng minh xử lý message thành công.

### Gợi ý 3

CRM write và CompleteMessageAsync không atomic.

## Cấu trúc trả lời đề xuất

1. Đo business impact, SLA và message age.
2. Stabilize và không purge DLQ.
3. Thu samples/telemetry và deployment diff.
4. Kiểm chứng nhiều giả thuyết.
5. Canary fix, replay có idempotency.
6. Monitor, test và postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc

Không purge DLQ; phân biệt schema error với CRM timeout; bounded retries; at-least-once và idempotency.

### Điểm cộng

Versioned consumers, poison messages, lock expiry, exponential backoff, CRM throttling.

### Senior+

Inbox/deduplication boundary, audit replay, reconciliation và điều kiện rollback producer.

## Hướng giải quyết tham khảo

Bước đầu tính số orders chưa cập nhật CRM, oldest message age, error rate và SLA breach; thông báo mức ảnh hưởng. Tạm giới hạn concurrency/retry khi CRM 429/timeout, giữ message/DLQ, cân nhắc rollback producer nếu diff chứng minh contract incompatibility; rollback không sửa message đã phát.

Thu DLQ reason, MessageId, schemaVersion, enqueue time, delivery count, exception đã redacted, dependency telemetry. Kiểm chứng ít nhất: (A) đổi field/type làm consumer cũ deserialization fail; (B) CRM 429/5xx gây retry vượt MaxDeliveryCount; (C) lock hết hạn gây redelivery; (D) subscription filter/routing sai. Không kết luận một root cause khi chưa có evidence; A và B có thể cùng xảy ra.

Sửa bằng versioned schema handlers hoặc expand/contract message contract. Invalid payload là permanent failure cần DLQ có reason an toàn; CRM timeout/429 là transient cần retry bounded, jitter, concurrency cap và tôn trọng Retry-After. Sau CRM write nhưng trước settlement có thể bị crash; Service Bus at-least-once nên logical operation ID ổn định (OrderId + event type/version), CRM idempotent upsert hoặc inbox/reconciliation. Không coi MessageId duy nhất nếu producer tạo ID mới khi retry cùng logical event. Bảng inbox tự nó không tạo atomic transaction với external CRM, nên phải xử lý trạng thái uncertain.

Replay DLQ theo batch nhỏ, checkpoint, canary, audit, theo dõi duplicate updates, backlog age và CRM throttling. Không replay poison messages vô hạn. Contract tests đa version, deployment compatibility gates, failure injection, DLQ runbook và alerts theo oldest age/error ratio. Metrics cần active/dead-letter count, complete/abandon rates, CRM p95/429, message version, traces và correlation IDs.

## Mẫu trả lời trong phỏng vấn

Em ưu tiên bảo toàn order và SLA, không purge DLQ hay tăng consumers ngay. Em đo backlog age, phân nhóm DLQ reason và đối chiếu schemaVersion với deployment. Vì có cả deserialization và CRM timeout, em giữ nhiều giả thuyết, kiểm tra payload version và dependency telemetry trước khi chốt nguyên nhân. Em triển khai compatibility fix hoặc rollback producer nếu phù hợp, giảm concurrency khi CRM bị throttle, retry có giới hạn. Do CRM write và Service Bus settlement không atomic, em yêu cầu idempotency theo logical order event và replay DLQ theo batch có audit. Sau đó thêm contract tests, alerts và runbook.

## Câu hỏi đào sâu

1. CRM write thành công nhưng CompleteMessageAsync timeout thì sao?
2. Rollback producer không khả thi vì consumer khác cần schema mới: phương án nào?
3. Khi nào dead-letter ngay thay vì retry?

## Lỗi trả lời thường gặp

- Scale consumer khi CRM rate limited.
- Replay toàn bộ DLQ không idempotency.
- Đồng nhất health check xanh với processing healthy.
- Gộp schema lỗi với timeout vào cùng retry policy.
- Tuyên bố exactly-once end-to-end.

## Thang điểm 0–10

- Impact/clarification: 1
- Stabilization: 2
- Evidence/hypotheses: 2
- Idempotency/retry: 2
- Trade-offs/recovery: 1
- Testing/observability/communication: 2

# Câu 3 — Hiện đại hóa TeamCity–Octopus–IIS mà không làm hỏng rollback

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** .NET Framework, IIS, Windows Server, TeamCity, Octopus Deploy, App Service, CI/CD

## Bối cảnh

Website quản lý sự kiện ASP.NET MVC trên .NET Framework 4.5, SQL Server, hai IIS servers. TeamCity build, Octopus Deploy. Mỗi release downtime 10–20 phút, rollback code đôi khi không tương thích DB schema. Có thư viện Windows-only và batch job trong web app. Team 5 developers + 1 QA, không có Kubernetes platform team; mục tiêu 3 tháng giảm release risk, chưa bắt buộc chuyển cloud. Traffic và budget chưa rõ.

## Câu hỏi chính

Thiết kế lộ trình giảm downtime/release risk, so sánh tiếp tục IIS, Azure App Service và container, giải thích migration/rollback/data compatibility và trade-offs.

## Câu hỏi làm rõ nên cân nhắc

1. SLA downtime, RTO/RPO, peak load và load balancer capabilities?
2. Windows-only library phụ thuộc COM/registry/authentication gì?
3. Batch có chạy trên cả hai IIS nodes, có local session/files không?
4. DB migrations nào destructive và lock lâu?
5. Budget, compliance, network và ownership hạ tầng?

## Gợi ý tư duy

### Gợi ý 1

Không bắt buộc đổi hosting để giảm release risk.

### Gợi ý 2

Một immutable artifact, traffic drain và DB expand/contract là các cơ chế cốt lõi.

### Gợi ý 3

Phân biệt rollback code với rollback dữ liệu; tách batch khỏi web lifecycle.

## Cấu trúc trả lời đề xuất

1. Xác nhận SLO, constraints, baseline.
2. Inventory dependencies và risk.
3. So sánh phương án hosting.
4. Thiết kế các phase có gates.
5. Định nghĩa DB migration/rollback.
6. Tests, telemetry, release governance.

## Ý chính của câu trả lời tốt

### Bắt buộc

Incremental modernization, immutable artifacts, rolling deployment, expand/contract DB, tách job và rollback boundary.

### Điểm cộng

Compatibility inventory, Windows dependency, secrets, Playwright smoke tests, feature flags.

### Senior+

Migration rehearsal, strangler by module, release gates, rollback vs roll-forward khi schema đã đổi.

## Hướng giải quyết tham khảo

Giả định có load balancer hỗ trợ drain; nếu không có, không hứa zero downtime. Đo baseline deployment failure rate, MTTR, p95, 5xx, downtime minutes và migration duration. Trong 3 tháng ưu tiên cải thiện pipeline trên IIS thay vì đồng thời rewrite, chuyển Linux và thay công cụ.

Phase 1: TeamCity build immutable artifact một lần, Octopus promote qua environments với checksum; cấu hình và secrets tách khỏi binary, preflight validation, backup/restore drill, readiness endpoint, smoke/Playwright critical-flow tests, release runbook. Không lưu secrets trong artifact.

Phase 2: rolling deploy node A rồi B: drain traffic, deploy, warm-up, smoke, rejoin. Nếu session in-memory hoặc local filesystem, phải chuyển shared storage/session hoặc chấp nhận sticky-session tạm thời và giới hạn của nó. App Pool recycle có thể ngắt in-flight requests; kiểm tra drain timeout. Tách batch khỏi web process, lưu durable job state, idempotency hoặc singleton coordination khi multi-instance.

DB migration dùng expand/contract: thêm schema tương thích cả app cũ/mới, backfill theo batch, deploy code, chỉ xóa field cũ ở release sau. Code rollback chỉ an toàn nếu schema và dữ liệu còn tương thích; nếu dữ liệu đã ghi format mới có thể phải roll-forward hoặc dùng migration bù đã kiểm chứng. Rehearse locking/log growth.

Phase 3: inventory dependencies, POC module ít rủi ro sang modern .NET. Không thể chỉ đổi target framework từ .NET Framework 4.5. Windows-only integration có thể buộc giữ Windows hosting hoặc tách boundary. Azure App Service Windows/Linux có operational benefits nhưng cần đánh giá compatibility, networking, managed identity, deployment slots, cost và cutover. Containers chỉ khi packaging benefits đủ lớn; Kubernetes không phải mặc định cho team nhỏ.

Giữ transaction ownership rõ ràng nếu tách module, tránh phân tán DB transaction quá sớm. Monitor release version, p95, 5xx, DB waits, batch duplicates, user journeys, alerts. Go/no-go theo SLO và rollback rehearsal; nếu bắt buộc zero downtime và không có load balancer, đầu tư điều phối traffic/blue-green trước.

## Mẫu trả lời trong phỏng vấn

Em sẽ xác định mục tiêu là giảm release risk trong ba tháng, nên không chuyển runtime, hosting và pipeline cùng lúc. Em đo downtime và failed deploys, inventory Windows-only dependencies, rồi giữ TeamCity/Octopus/IIS để build artifact một lần và rolling deploy từng node có drain, warm-up và smoke tests. Em tách batch khỏi web lifecycle và xử lý session/local files. Với database, em dùng expand/contract để version cũ/mới cùng chạy; rollback code không tự khôi phục dữ liệu. Khi pipeline ổn định, em làm POC module lên modern .NET và so sánh App Service Windows/Linux với chi phí, compatibility và vận hành. Kubernetes không mặc định phù hợp. Em dùng p95, 5xx, MTTR và release failures làm quyết định.

## Câu hỏi đào sâu

1. Migration đã xóa cột app cũ cần: rollback ra sao?
2. Nếu lãnh đạo yêu cầu Kubernetes ngay, bạn phản biện bằng tiêu chí gì?
3. Hai IIS nodes dùng in-memory session và batch trong app: ưu tiên sửa thứ tự nào?

## Lỗi trả lời thường gặp

- Mặc định rewrite hoặc Kubernetes.
- Cho rằng rollback binary rollback luôn DB.
- Bỏ qua Windows-only dependency và session.
- Không có traffic drain hoặc readiness gate.
- Không đo SLO hay rehearsal.

## Thang điểm 0–10

- Requirements/constraints: 2
- Architecture phases/boundaries: 2
- Deployment/DB correctness: 2
- Trade-offs: 2
- Testing/observability/communication: 2
