# Code Review Challenge 1 — Middleware ghi log request/response làm tăng memory và rò rỉ dữ liệu nhạy cảm

**Chủ đề:** Logging & observability, sensitive-data exposure, memory/allocation, resource lifetime, async/cancellation  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ web/mobile đang có middleware tự viết để ghi toàn bộ request và response body nhằm hỗ trợ điều tra lỗi production.

Lưu lượng bình thường khoảng 150–250 request/giây, nhưng có các đợt peak 800–1.200 request/giây. Một số endpoint upload JSON lớn hoặc trả về payload vài MB. API cũng có các endpoint đăng nhập, refresh token, cập nhật hồ sơ cá nhân và tích hợp Microsoft Graph.

Sau khi middleware được bật ở production, team quan sát thấy:

- Memory tăng mạnh vào giờ cao điểm và Gen 2 GC xuất hiện thường xuyên hơn.
- Một số request lớn có latency tăng đáng kể.
- Có vài log chứa access token, email, số điện thoại và nội dung request nhạy cảm.
- Thỉnh thoảng response trả về rỗng khi downstream pipeline ném exception.
- Khi client huỷ request, server vẫn tiếp tục copy/log body trong một số trường hợp.

Team muốn giữ khả năng trace request/response để debug, nhưng không chấp nhận rò rỉ dữ liệu nhạy cảm hoặc gây áp lực memory lớn.

## Đoạn code cần review

```csharp
public sealed class RequestResponseLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestResponseLoggingMiddleware> _logger;

    public RequestResponseLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestResponseLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var requestReader = new StreamReader(
            context.Request.Body,
            Encoding.UTF8,
            detectEncodingFromByteOrderMarks: false,
            leaveOpen: true);

        var requestBody = await requestReader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        _logger.LogInformation(
            "HTTP Request {Method} {Path} Headers={Headers} Body={Body}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers,
            requestBody);

        var originalResponseBody = context.Response.Body;
        await using var buffer = new MemoryStream();
        context.Response.Body = buffer;

        await _next(context);

        buffer.Position = 0;
        var responseBody = await new StreamReader(buffer).ReadToEndAsync();

        _logger.LogInformation(
            "HTTP Response {StatusCode} Headers={Headers} Body={Body}",
            context.Response.StatusCode,
            context.Response.Headers,
            responseBody);

        buffer.Position = 0;
        await buffer.CopyToAsync(originalResponseBody);
        context.Response.Body = originalResponseBody;
    }
}
```

## Kết quả code review tham khảo

### 1. Log toàn bộ headers và body có thể làm lộ secrets/PII

**Problem:** Middleware ghi nguyên `Request.Headers`, `Response.Headers`, request body và response body.

**Why it happens:** Header có thể chứa `Authorization`, cookie, API key hoặc correlation information nhạy cảm. Body có thể chứa password, refresh token, email, phone, personal data hoặc dữ liệu business nhạy cảm.

**Production impact:** Credential có thể bị lưu lâu dài trong hệ thống logging, bị truy cập bởi nhiều người hơn mức cần thiết, tăng blast radius khi log storage bị compromise và có thể vi phạm chính sách bảo mật/compliance.

**Severity:** Critical

**Recommended fix:**

- Không log secrets theo mặc định.
- Dùng allow-list thay vì log mọi header.
- Redact các trường như `Authorization`, `Cookie`, `Set-Cookie`, token, password, secret.
- Với body JSON, chỉ log field đã được whitelist hoặc dùng structured redaction.
- Với endpoint authentication/token/payment/profile nhạy cảm, thường chỉ log metadata chứ không log body.

### 2. Buffer toàn bộ response trong `MemoryStream` gây memory amplification dưới tải

**Problem:** Mỗi request giữ toàn bộ response body trong RAM trước khi gửi cho client.

**Why it happens:** `MemoryStream` phải tăng capacity theo payload. Đồng thời code còn chuyển toàn bộ nội dung sang `string`, tạo thêm allocation lớn.

**Production impact:** Với response lớn và concurrency cao, memory usage tăng mạnh, gây GC pressure, allocation lớn, latency spike và có thể dẫn tới OOM hoặc pod/process restart.

**Severity:** High

**Recommended fix:**

- Không capture toàn bộ response ở mọi request.
- Giới hạn số byte được capture, ví dụ vài KB đầu tiên cho diagnostics.
- Chỉ capture trên endpoint/sampling/diagnostic mode cụ thể.
- Với payload lớn hoặc streaming response, chỉ log metadata như status code, content type, content length, elapsed time.

### 3. Request body cũng bị materialize toàn bộ thành `string`

**Problem:** `ReadToEndAsync()` đọc toàn bộ request body rồi tạo một chuỗi lớn.

**Why it happens:** Middleware dùng body logging như một tính năng mặc định thay vì một tính năng có giới hạn.

**Production impact:** Upload JSON lớn hoặc nhiều request đồng thời làm tăng allocation và latency. Request body lớn còn có thể khiến buffering chuyển sang file tùy ngưỡng/cấu hình, tạo thêm I/O và resource pressure.

**Severity:** High

**Recommended fix:**

- Áp limit body logging độc lập với request body size limit.
- Chỉ đọc tối đa N byte.
- Bỏ qua binary/multipart/streaming content.
- Chỉ bật body logging cho một tập endpoint hoặc khi troubleshooting có kiểm soát.

### 4. Response stream không được restore bằng `finally`

**Problem:** Nếu `_next(context)` hoặc phần đọc/log response ném exception, `context.Response.Body` có thể vẫn trỏ vào `MemoryStream` tạm.

**Why it happens:** Việc thay thế stream có side effect lên `HttpContext` nhưng cleanup không được đặt trong `try/finally`.

**Production impact:** Exception handler phía ngoài middleware có thể ghi vào stream đã dispose hoặc không phải stream gốc; client có thể nhận response rỗng/không đầy đủ; việc điều tra incident trở nên khó hơn.

**Severity:** High

**Recommended fix:** Đặt việc restore `context.Response.Body = originalResponseBody` trong `finally`.

### 5. Middleware phá streaming semantics và tăng time-to-first-byte

**Problem:** Response không được chuyển cho client cho đến khi downstream hoàn tất và middleware copy toàn bộ buffer sang stream gốc.

**Why it happens:** Toàn bộ response bị giữ lại để đọc nội dung trước khi gửi.

**Production impact:** Server-Sent Events, file download, large export hoặc response streaming bị phá hoặc mất lợi ích streaming. Time-to-first-byte tăng.

**Severity:** High

**Recommended fix:** Với streaming/large response không capture body. Nếu cần inspect, dùng wrapper stream giới hạn số byte quan sát nhưng vẫn forward dữ liệu ngay xuống stream gốc.

### 6. Cancellation chưa được propagate khi đọc/copy

**Problem:** Các thao tác đọc/copy không sử dụng `context.RequestAborted`.

**Why it happens:** Code coi logging là bước phụ không cần cancellation.

**Production impact:** Client disconnect nhưng server vẫn tiếp tục đọc, serialize log hoặc copy buffer; dưới tải có thể giữ CPU/memory/I/O không cần thiết.

**Severity:** Medium

**Recommended fix:** Dùng overload hỗ trợ `CancellationToken` khi phù hợp và kiểm tra `RequestAborted`. Logging diagnostic không nên tiếp tục công việc nặng sau khi request đã bị huỷ.

### 7. Log payload nguyên bản làm tăng chi phí logging và có thể tạo backpressure

**Problem:** Mỗi request có thể ghi hàng KB đến nhiều MB log.

**Why it happens:** Không có size cap, sampling hoặc log level policy.

**Production impact:** Log ingestion cost tăng, log pipeline có thể bị nghẽn, storage nhanh đầy, index/search chậm và application latency có thể bị ảnh hưởng nếu sink gặp vấn đề.

**Severity:** Medium

**Recommended fix:**

- Log metadata mặc định.
- Áp max payload length.
- Sampling cho success path.
- Fuller diagnostics chỉ khi error hoặc feature flag có thời hạn.
- Không biến logging thành dependency bắt buộc cho correctness của request.

### 8. Không phân biệt content type

**Problem:** Code đọc mọi body như UTF-8 text.

**Why it happens:** Middleware giả định tất cả payload là text.

**Production impact:** Binary upload/download tạo dữ liệu log vô nghĩa, allocation lớn và có thể làm hỏng cách diễn giải nội dung.

**Severity:** Medium

**Recommended fix:** Chỉ body-log các content type cho phép như JSON/text và bỏ qua `multipart/form-data`, octet-stream, file response, media hoặc content được đánh dấu streaming.

### 9. Headers được log trực tiếp có cardinality và kích thước khó kiểm soát

**Problem:** Toàn bộ collection headers được đưa vào log.

**Why it happens:** Không có allow-list và không chuẩn hoá trường observability.

**Production impact:** Log khó query, có thể tạo field cardinality cao, tăng chi phí indexing và chứa dữ liệu không liên quan.

**Severity:** Low

**Recommended fix:** Chỉ log một số metadata ổn định: method, route template, status, elapsed time, content length, trace id, tenant id an toàn, user id dạng nội bộ nếu policy cho phép.

## Phiên bản code đề xuất

Ví dụ dưới đây ưu tiên metadata logging, chỉ capture request body JSON nhỏ, có redaction cơ bản, giới hạn kích thước và không thay thế response stream để tránh memory amplification. Trong hệ thống thực tế, redaction nên được chuẩn hoá ở một component riêng và policy phải phù hợp với dữ liệu của tổ chức.

```csharp
public sealed class SafeHttpLoggingMiddleware
{
    private const int MaxLoggedBodyBytes = 8 * 1024;

    private static readonly HashSet<string> AllowedHeaders =
        new(StringComparer.OrdinalIgnoreCase)
        {
            "User-Agent",
            "Content-Type",
            "Content-Length",
            "X-Correlation-Id"
        };

    private readonly RequestDelegate _next;
    private readonly ILogger<SafeHttpLoggingMiddleware> _logger;

    public SafeHttpLoggingMiddleware(
        RequestDelegate next,
        ILogger<SafeHttpLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        string? requestBodyPreview = null;

        if (ShouldCaptureRequestBody(context.Request))
        {
            requestBodyPreview = await ReadBodyPreviewAsync(
                context.Request,
                context.RequestAborted);
        }

        var safeHeaders = context.Request.Headers
            .Where(h => AllowedHeaders.Contains(h.Key))
            .ToDictionary(h => h.Key, h => h.Value.ToString());

        try
        {
            await _next(context);
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            _logger.LogInformation(
                "HTTP {Method} {Path} => {StatusCode} in {ElapsedMs} ms. " +
                "TraceId={TraceId} Headers={Headers} RequestPreview={RequestPreview}",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                context.TraceIdentifier,
                safeHeaders,
                Redact(requestBodyPreview));
        }
    }

    private static bool ShouldCaptureRequestBody(HttpRequest request)
    {
        if (request.ContentLength is null || request.ContentLength <= 0)
            return false;

        if (request.ContentLength > MaxLoggedBodyBytes)
            return false;

        return request.ContentType?.StartsWith(
            "application/json",
            StringComparison.OrdinalIgnoreCase) == true;
    }

    private static async Task<string?> ReadBodyPreviewAsync(
        HttpRequest request,
        CancellationToken cancellationToken)
    {
        request.EnableBuffering();

        var buffer = new byte[MaxLoggedBodyBytes];
        var read = await request.Body.ReadAsync(
            buffer.AsMemory(0, buffer.Length),
            cancellationToken);

        request.Body.Position = 0;
        return Encoding.UTF8.GetString(buffer, 0, read);
    }

    private static string? Redact(string? value)
    {
        if (string.IsNullOrWhiteSpace(value))
            return value;

        // Production code nên parse JSON và redact theo field allow-list/deny-list rõ ràng.
        return value.Length <= MaxLoggedBodyBytes
            ? value
            : value[..MaxLoggedBodyBytes];
    }
}
```

### Lưu ý thiết kế

Bản sửa trên cố tình **không capture response body**. Nếu business bắt buộc cần response preview, một hướng tốt hơn là dùng một stream wrapper vừa forward dữ liệu ngay xuống stream gốc vừa giữ lại tối đa N byte đầu tiên, thay vì buffer toàn bộ response. Tuy nhiên cần kiểm tra kỹ với streaming response, compression middleware và exception handling.

## Trade-offs

- **Không log full body** làm giảm khả năng debug một số lỗi, đổi lại giảm đáng kể security risk và resource cost.
- **Sampling** giảm chi phí nhưng có thể bỏ lỡ request lỗi hiếm; có thể luôn giữ metadata và tăng sampling trên error path.
- **Redaction theo deny-list** dễ bỏ sót field mới; allow-list thường an toàn hơn nhưng ít thông tin hơn.
- **Capture preview** vẫn có allocation; nếu traffic rất cao, chỉ nên bật theo route/feature flag hoặc sampling.
- Nếu tổ chức đã có tracing/APM tốt, nhiều trường hợp metadata + trace correlation hiệu quả hơn full payload logging.

## Cách kiểm thử

1. **Security test:** Gửi request chứa `Authorization`, cookie, password, refresh token, email nhạy cảm và xác nhận chúng không xuất hiện trong log.
2. **Large-payload/load test:** Chạy hàng trăm request đồng thời với payload lớn và so sánh allocation rate, GC pause, working set, p95/p99 latency trước/sau bản sửa.
3. **Failure-path test:** Cho downstream middleware/controller ném exception; xác nhận exception pipeline vẫn hoạt động và response không bị hỏng do stream lifecycle.
4. **Cancellation test:** Client huỷ request trong khi server đang xử lý; xác nhận middleware không tiếp tục công việc logging nặng và cancellation được propagate.
5. **Content-type test:** JSON nhỏ được preview theo policy; file upload, multipart và binary response không bị capture body.

## Quan sát trong production

Nên theo dõi:

- Request duration p50/p95/p99 theo route.
- Allocation rate, GC collections, Gen 2 collections, heap size và process working set.
- Kích thước request/response theo distribution, không chỉ average.
- Số request bị client abort/cancel.
- Logging throughput, dropped logs, queue/backpressure của log sink nếu có.
- Tỷ lệ request được body-sampled.
- Traces có `trace_id`, route, dependency spans và status thay vì phụ thuộc vào full payload.
- Alert nếu memory tăng bất thường hoặc log ingestion volume tăng đột biến sau deployment.

# Code Review Challenge 2 — API phân trang đơn hàng trả thiếu/trùng dữ liệu và ngày càng chậm

**Chủ đề:** EF Core query execution, SQL performance & correctness, pagination, tracking, deterministic ordering  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút

## Bối cảnh

Một API ASP.NET Core phục vụ trang lịch sử đơn hàng cho khách hàng doanh nghiệp. Bảng `Orders` có khoảng 25 triệu row, mỗi tenant có thể có từ vài nghìn đến hơn 2 triệu đơn hàng.

Frontend gọi API theo `page` và `pageSize`, cho phép lọc theo khoảng ngày và trạng thái. Người dùng báo rằng:

- Khi đang có đơn hàng mới được tạo, chuyển từ page 1 sang page 2 đôi khi thấy một order bị lặp hoặc một order biến mất.
- Page càng sâu càng chậm; một số tenant có page 1.000 mất vài giây.
- Database CPU tăng khi nhiều user mở màn hình này cùng lúc.
- API đôi khi trả nhiều dữ liệu hơn mức cần thiết và memory process tăng.

Business yêu cầu sort theo `CreatedAt` mới nhất trước, nếu hai order có cùng `CreatedAt` thì kết quả vẫn phải ổn định. Không được để tenant này đọc order của tenant khác.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    private readonly AppDbContext _db;

    public OrdersController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet]
    public async Task<IActionResult> GetOrders(
        int page = 1,
        int pageSize = 100,
        DateTime? from = null,
        DateTime? to = null,
        string? status = null)
    {
        var tenantId = User.FindFirst("tenant_id")!.Value;

        var orders = await _db.Orders
            .Include(x => x.Items)
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        if (from.HasValue)
            orders = orders.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            orders = orders.Where(x => x.CreatedAt <= to.Value).ToList();

        if (!string.IsNullOrWhiteSpace(status))
            orders = orders.Where(x => x.Status == status).ToList();

        var total = orders.Count;

        var result = orders
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.CreatedAt,
                x.Status,
                TotalItems = x.Items.Count,
                x.TotalAmount
            })
            .ToList();

        return Ok(new
        {
            page,
            pageSize,
            total,
            items = result
        });
    }
}
```

## Kết quả code review tham khảo

### 1. Query materialize toàn bộ order của tenant trước khi filter và paginate

**Problem:** `ToListAsync()` chạy ngay sau `Where(TenantId)` và `OrderBy`, trước `from`, `to`, `status`, `Skip`, `Take`.

**Why it happens:** Sau `ToListAsync()`, biến `orders` là collection trong memory; các filter phía sau không còn được translate sang SQL.

**Production impact:** Tenant lớn có thể tải hàng trăm nghìn hoặc hàng triệu order vào application memory, tăng DB I/O, network transfer, allocation, GC pressure và latency.

**Severity:** Critical

**Recommended fix:** Giữ query dưới dạng `IQueryable<Order>` đến khi toàn bộ filter, projection và pagination đã được áp dụng.

### 2. `Include(Items)` tải toàn bộ item collection không cần thiết

**Problem:** API chỉ cần `TotalItems = x.Items.Count` nhưng lại eager-load toàn bộ `Items`.

**Why it happens:** Code dùng entity graph trước rồi mới project trong memory.

**Production impact:** Số row và dữ liệu truyền từ DB tăng lớn; một order có nhiều item sẽ làm query nặng hơn đáng kể. Nếu query join collection, kết quả vật lý còn có thể phình ra do lặp dữ liệu order theo item.

**Severity:** High

**Recommended fix:** Project trực tiếp sang DTO trong SQL và để provider translate `x.Items.Count()`/`x.Items.Count` thành aggregate/correlated query phù hợp thay vì tải item entities.

### 3. Ordering không deterministic khi nhiều row có cùng `CreatedAt`

**Problem:** Chỉ sort bằng `CreatedAt`.

**Why it happens:** Khi nhiều order có cùng timestamp, database không bắt buộc trả chúng theo một thứ tự ổn định nếu không có tie-breaker.

**Production impact:** Các lần query khác nhau có thể sắp xếp các row bằng nhau khác thứ tự, dẫn tới duplicate/missing row giữa các page ngay cả khi dataset không thay đổi đáng kể.

**Severity:** High

**Recommended fix:** Thêm tie-breaker duy nhất và ổn định, ví dụ `OrderByDescending(CreatedAt).ThenByDescending(Id)`.

### 4. Offset pagination có thể duplicate/miss row khi có insert mới giữa các lần request

**Problem:** `Skip((page - 1) * pageSize)` dựa vào vị trí tương đối trong tập dữ liệu đang thay đổi.

**Why it happens:** Nếu row mới được insert vào đầu danh sách giữa request page 1 và page 2, offset của các row cũ dịch chuyển.

**Production impact:** User có thể thấy row lặp hoặc bỏ sót row khi chuyển trang.

**Severity:** High

**Recommended fix:** Với feed/history sort theo thời gian, ưu tiên keyset/seek pagination dùng cursor `(CreatedAt, Id)` của item cuối cùng trên page hiện tại.

Ví dụ điều kiện page tiếp theo khi sort giảm dần:

```text
CreatedAt < lastCreatedAt
OR (CreatedAt == lastCreatedAt AND Id < lastId)
```

### 5. Deep `OFFSET/SKIP` ngày càng đắt

**Problem:** Page 1.000 hoặc sâu hơn yêu cầu database bỏ qua rất nhiều row trước khi lấy page hiện tại.

**Why it happens:** Offset pagination thường vẫn phải scan/traverse lượng row tương ứng với offset theo execution plan/index.

**Production impact:** Latency và CPU/reads tăng theo độ sâu của page, nhất là trên tenant lớn.

**Severity:** High

**Recommended fix:** Keyset pagination nếu UX không yêu cầu nhảy ngẫu nhiên tới page N. Nếu business bắt buộc page number, cần đánh giá index/plan, giới hạn page depth hoặc dùng chiến lược khác theo use case.

### 6. Endpoint read-only nhưng vẫn dùng entity tracking mặc định

**Problem:** Query tạo tracked entities dù sau đó chỉ đọc.

**Why it happens:** Không dùng projection trực tiếp hoặc `AsNoTracking()`.

**Production impact:** Change tracker giữ metadata cho nhiều entity, làm tăng memory/CPU, đặc biệt nghiêm trọng do query hiện tại materialize rất nhiều row.

**Severity:** Medium

**Recommended fix:** Project trực tiếp DTO; trong trường hợp vẫn materialize entity read-only thì dùng `AsNoTracking()`.

### 7. `page` và `pageSize` không được validate

**Problem:** `page <= 0`, `pageSize <= 0` hoặc `pageSize` cực lớn đều được chấp nhận.

**Why it happens:** Không có input constraints.

**Production impact:** Có thể tạo exception, hành vi khó đoán hoặc request quá nặng; một client có thể vô tình/ác ý yêu cầu hàng trăm nghìn row.

**Severity:** Medium

**Recommended fix:** Validate `page >= 1`, giới hạn `pageSize` bằng giá trị hợp lý, ví dụ 20–200 tùy product requirement.

### 8. `total` được tính sau khi tải toàn bộ dataset vào memory

**Problem:** `orders.Count` đếm collection đã materialize thay vì `COUNT(*)` có filter ở database.

**Why it happens:** Query architecture đã chuyển sang LINQ-to-Objects quá sớm.

**Production impact:** Phải tải toàn bộ row chỉ để biết count; tăng chi phí rất lớn.

**Severity:** Medium

**Recommended fix:** Nếu total là bắt buộc, dùng `CountAsync()` trên filtered `IQueryable`. Tuy nhiên total count trên dataset rất lớn cũng có chi phí; cân nhắc UX có thực sự cần exact total hay chỉ cần `hasMore`.

### 9. Cancellation token không được nhận từ request

**Problem:** `ToListAsync()` không dùng `HttpContext.RequestAborted`.

**Why it happens:** Action không nhận `CancellationToken`.

**Production impact:** Client rời trang nhưng query nặng vẫn tiếp tục chạy, giữ DB connection và resource không cần thiết.

**Severity:** Medium

**Recommended fix:** Nhận `CancellationToken` trong action và truyền xuống `CountAsync`, `ToListAsync`.

## Phiên bản code đề xuất

Với dataset lớn và feed sort mới nhất trước, lựa chọn ưu tiên là **keyset pagination**. Ví dụ DTO + cursor:

```csharp
public sealed record OrderListItemDto(
    long Id,
    DateTime CreatedAt,
    string Status,
    int TotalItems,
    decimal TotalAmount);

public sealed record OrdersPageResponse(
    IReadOnlyList<OrderListItemDto> Items,
    DateTime? NextCreatedAt,
    long? NextId,
    bool HasMore);

[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    private readonly AppDbContext _db;

    public OrdersController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet]
    public async Task<ActionResult<OrdersPageResponse>> GetOrders(
        int pageSize = 50,
        DateTime? from = null,
        DateTime? to = null,
        string? status = null,
        DateTime? cursorCreatedAt = null,
        long? cursorId = null,
        CancellationToken cancellationToken = default)
    {
        if (pageSize is < 1 or > 200)
            return BadRequest("pageSize must be between 1 and 200.");

        var tenantId = User.FindFirst("tenant_id")?.Value;
        if (string.IsNullOrWhiteSpace(tenantId))
            return Forbid();

        IQueryable<Order> query = _db.Orders
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value);

        if (!string.IsNullOrWhiteSpace(status))
            query = query.Where(x => x.Status == status);

        if (cursorCreatedAt.HasValue && cursorId.HasValue)
        {
            var lastCreatedAt = cursorCreatedAt.Value;
            var lastId = cursorId.Value;

            query = query.Where(x =>
                x.CreatedAt < lastCreatedAt ||
                (x.CreatedAt == lastCreatedAt && x.Id < lastId));
        }

        var rows = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Select(x => new OrderListItemDto(
                x.Id,
                x.CreatedAt,
                x.Status,
                x.Items.Count,
                x.TotalAmount))
            .Take(pageSize + 1)
            .ToListAsync(cancellationToken);

        var hasMore = rows.Count > pageSize;
        if (hasMore)
            rows.RemoveAt(rows.Count - 1);

        var last = rows.LastOrDefault();

        return Ok(new OrdersPageResponse(
            rows,
            hasMore ? last?.CreatedAt : null,
            hasMore ? last?.Id : null,
            hasMore));
    }
}
```

### Index gợi ý

Index cụ thể phải được xác nhận bằng execution plan và workload thực tế, nhưng với query chính theo tenant và sort giảm dần theo `CreatedAt`, `Id`, một candidate index thường cần bắt đầu từ các key có selectivity/query order phù hợp, ví dụ về mặt ý tưởng:

```text
(TenantId, CreatedAt, Id)
```

Nếu `Status` là filter rất phổ biến và đủ selective, có thể cần index khác hoặc thay đổi key order. Không nên thêm index chỉ dựa trên suy đoán; cần quan sát actual query patterns, execution plan, logical reads và write overhead.

## Trade-offs

- **Keyset pagination** rất tốt cho next/previous scrolling nhưng không hỗ trợ tự nhiên việc nhảy thẳng tới page 1.000.
- **Exact total count** có thể đắt trên dataset lớn; UI có thể chỉ cần `hasMore` hoặc approximate total tùy requirement.
- **Projection** giảm dữ liệu tải về nhưng query aggregate như `Items.Count` vẫn cần execution plan phù hợp.
- **Composite index** cải thiện read nhưng làm tăng storage và write cost; cần cân bằng với write throughput.
- Nếu business bắt buộc snapshot-consistent pagination trên một tập dữ liệu thay đổi liên tục, có thể cần thêm snapshot/version boundary, ví dụ cố định `CreatedAt <= snapshotTime`, thay vì chỉ đổi pagination algorithm.

## Cách kiểm thử

1. **Correctness test với timestamp trùng nhau:** Tạo nhiều order có cùng `CreatedAt`; phân trang nhiều lần và xác nhận không duplicate/missing nhờ `ThenBy(Id)`.
2. **Concurrent insert test:** Đọc page 1, chèn thêm nhiều order mới, sau đó đọc page tiếp theo bằng cursor; xác nhận không lặp/mất các row thuộc chuỗi pagination cũ.
3. **Tenant isolation test:** Tạo dữ liệu hai tenant và xác nhận mọi query/cursor đều không thể trả order của tenant khác.
4. **Load/database test:** So sánh p95/p99 latency, logical reads, CPU và rows transferred giữa implementation cũ và keyset trên tenant có hàng triệu row.
5. **Cancellation test:** Huỷ HTTP request khi DB query đang chạy; xác nhận cancellation được propagate và resource được giải phóng hợp lý.

## Quan sát trong production

Nên theo dõi:

- API latency p50/p95/p99 theo route và tenant-size bucket.
- Database duration, CPU, logical reads, rows examined/returned.
- Execution plan thay đổi sau deployment hoặc data growth.
- Tỷ lệ query timeout/cancelled.
- Connection pool usage và DB wait statistics phù hợp với hệ quản trị đang dùng.
- Số page/cursor depth phổ biến để xác nhận UX pattern thực tế.
- Payload size và allocation rate của API process.
- Slow query logs/APM traces gắn `trace_id` với DB span.
- Alert khi p95 hoặc DB reads vượt baseline sau release.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Observability không đồng nghĩa với việc ghi toàn bộ request/response; log phải được thiết kế cùng security, privacy, cost và resource limits.
- Middleware thay đổi stream hoặc buffer payload phải xử lý lifecycle, exception và cancellation cẩn thận.
- Với EF Core, thời điểm materialize query quyết định phần nào chạy ở database và phần nào chạy trong memory.
- Pagination đúng không chỉ là `Skip/Take`; thứ tự phải deterministic và algorithm phải phù hợp với dữ liệu thay đổi.
- Deep offset thường có scalability kém; keyset pagination là lựa chọn tốt cho feed/history tuần tự.
- Index là một phần của thiết kế query nhưng phải được xác nhận bằng execution plan và workload thực tế.

## Mẫu tư duy cần nhớ

1. **Log metadata by default, payload by exception.** Chỉ ghi body khi thật sự cần, có giới hạn và redaction.
2. **Do not materialize before the database has done the work.** Filter, project và paginate trước `ToListAsync()`.
3. **Stable ordering before pagination.** Sort key phải deterministic, thường cần tie-breaker duy nhất.
4. **Design for the failure path, not only the happy path.** Cleanup, cancellation và exception behavior là một phần của correctness.
5. **Measure before adding infrastructure or indexes.** Dùng traces, query plans, logical reads, GC/memory metrics để xác nhận giả thuyết.
