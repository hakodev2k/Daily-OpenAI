# Code Review Challenge 1 — Service Bus consumer hoàn tất message trước khi transaction business an toàn

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, idempotency, retry, transaction boundary, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một order integration service nhận `OrderPaid` từ Azure Service Bus và tạo fulfillment request trong SQL Server. Service chạy nhiều instances trên Azure App Service. Producer có thể retry publish khi network timeout; consumer cũng có thể nhận lại message sau transient failure.

Sau một đợt dependency instability, production xuất hiện một số fulfillment trùng. Ở vài trường hợp khác, Service Bus cho thấy message đã được xử lý nhưng fulfillment record lại không tồn tại. Team muốn tăng retry count để “đảm bảo không mất message”.

Business yêu cầu một payment event không được tạo nhiều fulfillment cho cùng order. External warehouse API không hỗ trợ distributed transaction với SQL Server.

## Đoạn code cần review

```csharp
public sealed class OrderPaidProcessor
{
    private readonly AppDbContext _db;
    private readonly WarehouseClient _warehouse;
    private readonly ServiceBusReceiver _receiver;
    private readonly ILogger<OrderPaidProcessor> _logger;

    public OrderPaidProcessor(
        AppDbContext db,
        WarehouseClient warehouse,
        ServiceBusReceiver receiver,
        ILogger<OrderPaidProcessor> logger)
    {
        _db = db;
        _warehouse = warehouse;
        _receiver = receiver;
        _logger = logger;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        CancellationToken cancellationToken)
    {
        var payload = message.Body.ToObjectFromJson<OrderPaid>();

        var exists = await _db.Fulfillments
            .AnyAsync(x => x.OrderId == payload.OrderId, cancellationToken);

        if (exists)
        {
            await _receiver.CompleteMessageAsync(message, cancellationToken);
            return;
        }

        var requestId = await _warehouse.CreateFulfillmentAsync(
            payload.OrderId,
            payload.Items,
            cancellationToken);

        await _receiver.CompleteMessageAsync(message, cancellationToken);

        _db.Fulfillments.Add(new Fulfillment
        {
            OrderId = payload.OrderId,
            WarehouseRequestId = requestId,
            CreatedUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Created fulfillment for order {OrderId}",
            payload.OrderId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong message settlement và business transaction.
2. Xác định concurrency/retry/reliability concerns.
3. Giải thích impact khi duplicate delivery hoặc process crash xảy ra ở từng điểm.
4. Ưu tiên findings theo khả năng mất work hoặc tạo side effect trùng.
5. Đề xuất corrected design mà không giả định distributed transaction là khả dụng.
6. Giải thích concurrency, failure-path và integration tests.
7. Nêu telemetry production để phân biệt duplicate delivery, duplicate side effect và processing failure.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu process crash ngay sau `CompleteMessageAsync` nhưng trước `SaveChangesAsync`?
2. Hai instances có thể cùng nhận hai bản duplicate và cùng thấy `exists == false` không?
3. Unique constraint trong SQL có ngăn external warehouse side effect bị gọi hai lần không?
4. Retry có an toàn nếu warehouse đã tạo fulfillment nhưng response bị timeout?
5. Message ID, business idempotency key và `OrderId` có nhất thiết cùng semantics không?

## Gợi ý

### Gợi ý 1

Primary risk là transaction boundary bị chia giữa broker, database và external side effect.

### Gợi ý 2

At-least-once style processing phải được thiết kế cùng idempotency. Một check-then-act bằng `AnyAsync` không phải atomic concurrency control.

## Kết quả code review tham khảo

### Critical — Message được complete trước khi database state được durable

**Vấn đề:** message settlement xảy ra trước `SaveChangesAsync`.  
**Tại sao xảy ra:** broker acknowledgement và SQL write không nằm trong một atomic transaction.  
**Ảnh hưởng production:** process crash hoặc database failure sau completion có thể khiến broker không redeliver trong khi fulfillment record chưa tồn tại.  
**Cách sửa:** chỉ settle message sau khi durable local state cần thiết đã được commit. Nếu workflow cần external side effect, thiết kế state machine/outbox-inbox style boundary thay vì giả định ba systems có một transaction chung.

### Critical — External warehouse call không idempotent trước duplicate/retry

**Vấn đề:** warehouse side effect được gọi trước khi consumer có durable marker chứng minh event đã được claim/processed.  
**Tại sao xảy ra:** retry sau timeout không biết request trước đã được warehouse áp dụng hay chưa.  
**Ảnh hưởng production:** duplicate fulfillment thực tế dù local database cuối cùng chỉ có một row.  
**Cách sửa:** nếu warehouse hỗ trợ idempotency key, gửi stable business key và persist mapping. Nếu không hỗ trợ, cần workflow reconciliation/claim state phù hợp và phải thừa nhận không thể tạo exactly-once external side effect chỉ bằng local transaction.

### High — `AnyAsync` rồi insert có race condition

**Vấn đề:** check và insert là hai operations tách biệt.  
**Tại sao xảy ra:** hai consumers có thể cùng quan sát “không tồn tại” trước khi một bên commit.  
**Ảnh hưởng production:** cả hai gọi warehouse và sau đó cùng cố insert.  
**Cách sửa:** enforce unique business invariant ở database, ví dụ unique index trên `OrderId` hoặc event identity phù hợp, đồng thời thiết kế claim/processing state atomically. Unique constraint là last line of defense cho local data, không tự giải quyết external duplicate.

### High — Không có durable processing state cho partial failure

**Vấn đề:** chỉ tồn tại final `Fulfillment`; không có trạng thái `Pending/Requested/Completed/Failed` hoặc inbox marker.  
**Tại sao xảy ra:** workflow được code như một synchronous happy path.  
**Ảnh hưởng production:** khó resume/reconcile khi failure xảy ra giữa SQL và warehouse.  
**Cách sửa:** persist durable processing intent/state trước external work, commit transaction, sau đó perform side effect và update state; tùy requirement có thể dùng inbox + outbox/worker để tách message consumption khỏi external call.

### High — Retry có thể khuếch đại side effects

**Vấn đề:** tăng retry count mà không có idempotency strategy.  
**Tại sao xảy ra:** retry xử lý uncertainty như thể mọi failure đều xảy ra trước side effect.  
**Ảnh hưởng production:** dependency timeout có thể tạo nhiều fulfillment hơn.  
**Cách sửa:** classify failures, retry bounded với backoff, stable idempotency key và reconciliation cho ambiguous outcome.

### Medium — Deserialization và message validation thiếu guard

**Vấn đề:** payload được tin tưởng và dùng trực tiếp.  
**Tại sao xảy ra:** không validate schema/business identifiers.  
**Ảnh hưởng production:** malformed poison message có thể retry liên tục.  
**Cách sửa:** validate contract; xác định dead-letter policy cho permanent invalid messages và log reason có cấu trúc.

### Medium — Settlement responsibility bị trộn vào business handler

**Vấn đề:** handler trực tiếp phụ thuộc `ServiceBusReceiver`.  
**Tại sao xảy ra:** transport semantics và domain workflow gắn chặt.  
**Ảnh hưởng production:** khó test failure boundaries và dễ complete sai thời điểm.  
**Cách sửa:** để transport adapter quyết định complete/abandon/dead-letter dựa trên explicit processing result, hoặc ít nhất cô lập settlement logic rõ ràng.

### Medium — Logging không có message identity/correlation

**Vấn đề:** success log chỉ có `OrderId`.  
**Tại sao xảy ra:** không capture message ID, delivery count, correlation ID, processing attempt.  
**Ảnh hưởng production:** khó phân biệt producer duplicate với broker redelivery hoặc consumer retry.  
**Cách sửa:** structured logging/tracing với business key và transport metadata, tránh log sensitive payload.

### Low — `DateTime.UtcNow` khó kiểm thử và không phản ánh external event time

**Vấn đề:** timestamp local được hard-code và có semantics mơ hồ.  
**Tại sao xảy ra:** processing time và event/business time chưa được phân biệt.  
**Ảnh hưởng production:** reconciliation/audit khó hơn.  
**Cách sửa:** dùng injected clock khi cần testability và lưu rõ processing timestamp so với event timestamp.

## Phiên bản đề xuất

Một hướng an toàn hơn là consumer chỉ atomically ghi durable inbox/work item, sau đó worker xử lý warehouse. Ví dụ rút gọn:

```csharp
public sealed class OrderPaidConsumer
{
    private readonly AppDbContext _db;

    public OrderPaidConsumer(AppDbContext db) => _db = db;

    public async Task ConsumeAsync(
        ServiceBusReceivedMessage message,
        CancellationToken ct)
    {
        var payload = message.Body.ToObjectFromJson<OrderPaid>()
            ?? throw new InvalidDataException("Invalid OrderPaid payload.");

        var inbox = new FulfillmentInbox
        {
            MessageId = message.MessageId,
            OrderId = payload.OrderId,
            PayloadJson = JsonSerializer.Serialize(payload),
            Status = FulfillmentStatus.Pending,
            CreatedUtc = DateTime.UtcNow
        };

        _db.FulfillmentInbox.Add(inbox);

        try
        {
            await _db.SaveChangesAsync(ct);
        }
        catch (DbUpdateException ex) when (IsUniqueViolation(ex))
        {
            // Duplicate business/message identity already persisted.
        }
    }
}

public sealed class FulfillmentWorker
{
    private readonly AppDbContext _db;
    private readonly WarehouseClient _warehouse;

    public FulfillmentWorker(AppDbContext db, WarehouseClient warehouse)
    {
        _db = db;
        _warehouse = warehouse;
    }

    public async Task ProcessAsync(long inboxId, CancellationToken ct)
    {
        var item = await _db.FulfillmentInbox
            .SingleAsync(x => x.Id == inboxId, ct);

        if (item.Status == FulfillmentStatus.Completed)
            return;

        var idempotencyKey = $"fulfillment:{item.OrderId}";

        var requestId = await _warehouse.CreateFulfillmentAsync(
            item.OrderId,
            item.GetItems(),
            idempotencyKey,
            ct);

        item.WarehouseRequestId = requestId;
        item.Status = FulfillmentStatus.Completed;
        item.CompletedUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(ct);
    }
}
```

Schema cần unique constraint theo business invariant thực tế, ví dụ `OrderId` nếu đúng là mỗi order chỉ có một fulfillment, hoặc event/business operation ID nếu một order có thể có nhiều legitimate fulfillment events. Transport adapter chỉ complete Service Bus message sau khi inbox record đã được persisted thành công hoặc duplicate đã được xác nhận an toàn.

Nếu warehouse không hỗ trợ idempotency key, worker cần state/reconciliation strategy cho ambiguous timeout; code không được tuyên bố exactly-once guarantee mà dependency không hỗ trợ.

## Giải thích thiết kế sau khi sửa

Thiết kế tách durable acceptance khỏi external side effect. Service Bus redelivery có thể được absorb bằng unique inbox/business key. Database trở thành source cho processing state, cho phép retry/reconciliation. External call vẫn cần idempotency contract hoặc một cách xử lý ambiguous outcome; outbox/inbox không thần kỳ biến external API thành transactional resource.

## Trade-offs

Workflow nhiều trạng thái tăng schema, code và operational complexity. Với system nhỏ và warehouse API có strong idempotency key, có thể dùng implementation đơn giản hơn nhưng vẫn cần unique local invariant và settlement đúng thứ tự. Nếu throughput thấp, không nên thêm distributed architecture chỉ vì pattern phổ biến; complexity phải tương xứng failure cost.

## Cách kiểm thử

1. **Concurrency test:** hai duplicate messages xử lý song song; chỉ một durable business operation được claim.
2. **Failure-path test:** crash/fail sau inbox commit nhưng trước warehouse call; message redelivery không tạo duplicate claim và work vẫn recoverable.
3. **Ambiguous timeout test:** warehouse áp dụng request nhưng response timeout; retry với cùng idempotency key không tạo fulfillment thứ hai.
4. **Integration test:** SQL unique constraint thực sự bảo vệ invariant dưới concurrent transactions.
5. **DLQ test:** malformed/permanently invalid message được dead-letter theo policy thay vì retry vô hạn.

## Quan sát trong production

Theo dõi Service Bus active/dead-letter counts, delivery count, processing latency, retry count, inbox `Pending/Failed` age, duplicate-detected count, warehouse request latency/status và reconciliation mismatches. Correlate `MessageId`, business operation ID, `OrderId` và warehouse request ID qua Application Insights traces/logs.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một order hợp lệ có thể tạo nhiều fulfillment theo shipment split, bạn đổi idempotency key và unique constraint thế nào?
2. Outbox Pattern giải quyết phần nào của workflow này và phần nào nó không giải quyết?
3. Bạn sẽ chọn retry, dead-letter hay reconciliation như thế nào cho HTTP timeout có outcome không xác định?

# Code Review Challenge 2 — Kubernetes deployment pass health check nhưng rollout gây 5xx và mất request đang xử lý

**Chủ đề:** Kubernetes, ASP.NET Core hosting, readiness/liveness, graceful shutdown, resources, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core API được chuyển từ Azure App Service sang Kubernetes. API gọi SQL Server và một third-party pricing API. Deployment có 6 replicas. Bình thường request mất 100–400 ms, nhưng một số checkout request có thể mất 10–20 giây khi dependency chậm.

Sau mỗi rolling deployment, monitoring ghi nhận spike 502/503 trong khoảng một phút. Một số pods restart nhiều lần khi traffic tăng. Team nói “health endpoint luôn trả 200 nên Kubernetes configuration chắc không phải nguyên nhân”. Cluster team yêu cầu application team review manifest trước khi tăng replica count.

## Đoạn code cần review

```yaml

metadata:
  name: checkout-api
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 3
      maxSurge: 0
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
    spec:
      containers:

              path: /health

            periodSeconds: 5

## Nhiệm vụ của ứng viên

1. Xác định deployment/reliability/security problems.
2. Giải thích tại sao cùng một `/health` endpoint cho readiness và liveness có thể tạo failure amplification.
3. Phân tích resource requests/limits và shutdown window thay vì mặc định “tăng replicas”.
4. Ưu tiên risks ảnh hưởng availability và secrets.
5. Đề xuất manifest/design cải thiện, nêu rõ assumptions cần verify.
6. Giải thích deployment validation/load/failure tests.
7. Nêu Kubernetes và application telemetry cần quan sát.

## Câu hỏi gợi mở

1. Readiness và liveness trả lời hai câu hỏi operational giống nhau hay khác nhau?
2. Nếu `/health` kiểm tra SQL hoặc pricing dependency, dependency outage ảnh hưởng liveness thế nào?
3. `terminationGracePeriodSeconds: 5` có phù hợp request có thể chạy 20 giây không?
4. `maxUnavailable: 3` với 6 replicas thay đổi serving capacity ra sao trong rollout?
5. CPU limit thấp có thể tạo latency/throttling symptom gì dưới load?

## Gợi ý

### Gợi ý 1

Primary risk nằm ở rollout capacity, probe semantics và process lifecycle; “endpoint trả 200” không chứng minh cấu hình đúng.

### Gợi ý 2

Readiness quyết định pod có nhận traffic; liveness quyết định container có bị restart. Dependency health không nên vô tình biến một dependency outage thành restart storm của toàn application fleet.

## Kết quả code review tham khảo

### Critical — Production secret nằm trực tiếp trong Deployment manifest

**Vấn đề:** SQL username/password được hard-code trong YAML.  
**Tại sao xảy ra:** configuration và secret management bị trộn.  
**Ảnh hưởng production:** credential có thể lộ qua repository, rendered manifests hoặc access paths không cần biết secret.  
**Cách sửa:** dùng Kubernetes Secret hoặc external secret mechanism phù hợp; tốt hơn nữa, nếu platform/database hỗ trợ identity-based authentication, đánh giá workload identity/Managed Identity equivalent để giảm static credentials. Least privilege và rotation vẫn cần.

### High — Readiness và liveness dùng cùng dependency-sensitive endpoint

**Vấn đề:** cùng `/health` được dùng cho hai semantics khác nhau.  
**Tại sao xảy ra:** nếu endpoint fail khi SQL/pricing fail, liveness có thể restart process dù process bản thân vẫn healthy.  
**Ảnh hưởng production:** dependency outage có thể gây restart storm, cold start và giảm capacity thêm.  
**Cách sửa:** tách `/health/live` kiểm tra process viability tối thiểu và `/health/ready` kiểm tra điều kiện cần để nhận traffic theo dependency policy. Cần xác minh endpoint hiện tại thực sự check gì trước khi kết luận root cause.

### High — Graceful shutdown window ngắn hơn request hợp lệ

**Vấn đề:** termination grace chỉ 5 giây trong khi checkout có thể mất 10–20 giây.  
**Tại sao xảy ra:** pod có thể bị terminate trước khi in-flight work hoàn tất.  
**Ảnh hưởng production:** dropped requests, partial side effects hoặc client retries.  
**Cách sửa:** align application shutdown, readiness transition và termination grace với measured request/dependency behavior; đảm bảo app ngừng nhận traffic rồi có đủ budget drain in-flight work.

### High — RollingUpdate giảm capacity mạnh

**Vấn đề:** `maxUnavailable: 3`, `maxSurge: 0` cho phép capacity giảm đáng kể trong rollout.  
**Tại sao xảy ra:** không tạo pod bổ sung và cho phép nhiều replicas unavailable.  
**Ảnh hưởng production:** remaining pods nhận load cao hơn đúng lúc startup/termination diễn ra, dễ tạo latency/5xx.  
**Cách sửa:** chọn rollout parameters dựa trên capacity headroom/SLO; ví dụ cho phép surge và giảm unavailable nếu cluster capacity hỗ trợ. Không có một giá trị universal đúng cho mọi workload.

### High — Resource limits có dấu hiệu không grounded bằng measurement

**Vấn đề:** 100m CPU/128Mi memory có thể quá thấp cho ASP.NET Core API, nhưng scenario không cung cấp profile thực tế.  
**Tại sao xảy ra:** limits có vẻ được đặt tùy ý.  
**Ảnh hưởng production:** CPU throttling hoặc OOMKilled có thể giải thích pod restart/latency.  
**Cách sửa:** kiểm tra `container_cpu_cfs_throttled`, working set, OOMKilled reason, GC/memory và load profile; sau đó right-size requests/limits. Không đơn giản xóa limits mà không hiểu cluster policy.

### Medium — Image dùng mutable `latest`

**Vấn đề:** deployment không pin immutable artifact identity.  
**Tại sao xảy ra:** tag `latest` có thể trỏ tới image khác theo thời gian.  
**Ảnh hưởng production:** rollback/reproducibility và audit kém.  
**Cách sửa:** deploy versioned immutable tag và tốt hơn là digest trong release pipeline.

### Medium — Probe startup timing quá aggressive nếu startup thực tế chậm

**Vấn đề:** readiness/liveness bắt đầu rất sớm.  
**Tại sao xảy ra:** không có startup probe và timings không dựa trên measured startup.  
**Ảnh hưởng production:** slow startup có thể bị liveness kill trước khi ready ổn định.  
**Cách sửa:** nếu startup có thể kéo dài, cân nhắc startupProbe và tune thresholds dựa trên measured startup distribution.

### Medium — Không thể hiện explicit probe thresholds/timeouts

**Vấn đề:** manifest dựa nhiều vào defaults thay vì operational intent rõ ràng.  
**Tại sao xảy ra:** probe policy chưa được thiết kế từ failure budget.  
**Ảnh hưởng production:** transient latency có thể tạo readiness flapping hoặc restart behavior không mong muốn.  
**Cách sửa:** cấu hình timeout/failureThreshold/successThreshold nơi phù hợp sau khi đo endpoint behavior.

### Low — Không có deployment metadata giúp trace artifact

**Vấn đề:** snippet không thể hiện version/commit metadata.  
**Tại sao xảy ra:** artifact traceability chưa rõ.  
**Ảnh hưởng production:** incident correlation với release khó hơn.  
**Cách sửa:** expose deployment version qua labels/telemetry và Application Insights/OpenTelemetry resource attributes.

          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
```

Application phải implement readiness/liveness semantics tương ứng. Khi termination bắt đầu, pod cần ngừng nhận new traffic và application cần cooperate với host shutdown/cancellation. Nếu external checkout side effects không idempotent, client retry sau dropped request là một business correctness concern riêng cần xử lý.

## Giải thích thiết kế sau khi sửa

Manifest tách process health khỏi serving readiness, tăng rollout headroom và cho application nhiều thời gian drain request. Immutable image digest cải thiện reproducibility. Secret reference giảm exposure trong Deployment object nhưng Kubernetes Secret không tự động giải quyết encryption/access governance; RBAC, secret storage/rotation và cluster configuration vẫn phải được review.

Resource numbers không phải recommendation production. Chúng chỉ cho thấy requests và limits phải được thiết kế dựa trên measurement thay vì copy một template.

## Trade-offs

`maxSurge` cần cluster spare capacity. Grace period dài hơn có thể làm rollout chậm. Readiness check quá dependency-heavy có thể remove toàn bộ fleet khi shared dependency fail; quá shallow lại route traffic tới pods không thể phục vụ. Resource limits cao hơn tăng reserved/possible cluster consumption; limits quá thấp gây throttling/OOM. Probe semantics phải bám SLO và failure behavior thực tế.

## Cách kiểm thử

1. **Deployment validation:** rolling deploy dưới representative load; verify error rate và serving capacity không spike ngoài SLO.
2. **Graceful shutdown test:** giữ request 15–20 giây rồi terminate pod; verify request drain behavior và side-effect correctness.
3. **Failure injection:** làm pricing/SQL dependency fail; readiness behavior phải đúng policy và liveness không tạo restart storm nếu process vẫn healthy.
4. **Load test:** đo CPU throttling, memory, GC, p95/p99 để right-size resources.
5. **Security validation:** manifest/release artifacts không chứa plaintext production credential; service account/secret access tuân least privilege.

## Quan sát trong production

Theo dõi pod restart reason, OOMKilled, CPU throttling, memory working set, readiness transitions, unavailable replicas, rollout duration, request 5xx/p95/p99, termination events và dependency latency. Correlate application version/pod name với Application Insights traces. Alert trên restart storm, readiness flapping và rollout error-rate regression thay vì chỉ alert “health endpoint != 200”.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào readiness nên fail vì SQL unavailable, và khi nào giữ pod ready nhưng degrade functionality sẽ tốt hơn?
2. Bạn chứng minh `terminationGracePeriodSeconds` đủ bằng telemetry/test nào thay vì chọn một số tùy ý?
3. Nếu cluster không có capacity cho `maxSurge`, bạn thiết kế rollout safety thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Message processing và container orchestration đều yêu cầu reasoning về failure boundaries thay vì happy path. Với Service Bus, retry phải đi cùng idempotency và durable state; acknowledgement quá sớm có thể làm mất work, còn retry mù có thể nhân side effect. Với Kubernetes, readiness, liveness, shutdown và rollout capacity là các cơ chế khác nhau; cấu hình sai có thể biến dependency degradation thành fleet-wide failure.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency và ambiguous-outcome handling.
- Đặt durable transaction boundary trước khi acknowledgement external work.
- Phân biệt process liveness với khả năng phục vụ traffic.
- Đo capacity và failure behavior trước khi chỉnh replicas/resources.
- Test deployment và shutdown như production failure paths, không chỉ test steady state.
