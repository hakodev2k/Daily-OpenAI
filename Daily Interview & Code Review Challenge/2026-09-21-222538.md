# Code Review Challenge 1 — EF Core transaction giữ SQL connection qua HTTP call gây connection-pool starvation

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, SQL Server, transactions, connection pooling, third-party API, latency, concurrency, resilience  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một order API cần reserve inventory ở SQL Server và gọi shipping provider để tạo shipment. Team muốn “đảm bảo atomic” nên mở EF Core transaction trước khi đọc/cập nhật database, sau đó giữ transaction trong lúc gọi HTTP API bên ngoài.

Production chạy 6 replicas. Bình thường shipping provider trả trong 150–300 ms, nhưng vài lần mỗi ngày latency tăng lên 8–20 giây. Khi đó API latency tăng mạnh, SQL connection pool xuất hiện timeout, các endpoint không liên quan cũng chậm theo. Một số request retry từ gateway làm tình hình nặng hơn.

Bạn được giao review implementation sau. Không giả định local database transaction có thể làm remote HTTP side effect trở thành atomic.

## Đoạn code cần review

```csharp
public sealed class OrderService
{
    private readonly AppDbContext _db;
    private readonly HttpClient _shipping;

    public OrderService(AppDbContext db, HttpClient shipping)
    {
        _db = db;
        _shipping = shipping;
    }

    public async Task<string> ConfirmAsync(
        Guid orderId,
        CancellationToken ct)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(ct);

        var order = await _db.Orders
            .Include(x => x.Items)
            .SingleAsync(x => x.Id == orderId, ct);

        if (order.Status != "Pending")
            throw new InvalidOperationException("Order is not pending");

        foreach (var item in order.Items)
        {
            var stock = await _db.Stocks
                .SingleAsync(x => x.Sku == item.Sku, ct);

            if (stock.Available < item.Quantity)
                throw new InvalidOperationException("Out of stock");

            stock.Available -= item.Quantity;
        }

        await _db.SaveChangesAsync(ct);

        var response = await _shipping.PostAsJsonAsync(
            "/shipments",
            new { order.Id, order.Address },
            ct);

        response.EnsureSuccessStatusCode();

        var shipment = await response.Content
            .ReadFromJsonAsync<ShipmentResponse>(cancellationToken: ct);

        order.ShipmentId = shipment!.Id;
        order.Status = "Confirmed";

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);

        return shipment.Id;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, availability và scalability problems trong transaction boundary.
2. Giải thích vì sao giữ transaction qua network call có thể gây connection-pool starvation và lock amplification.
3. Phân tích các failure windows giữa inventory update, remote shipment side effect và local commit.
4. Đề xuất workflow bảo vệ inventory invariant nhưng không giả vờ có distributed transaction với shipping provider.
5. Nêu idempotency/reconciliation strategy nếu HTTP outcome không chắc chắn.
6. Đề xuất tests và telemetry để chứng minh bản sửa chịu được downstream latency, timeout và crash.

## Câu hỏi gợi mở

- SQL transaction đang giữ những resource nào trong thời gian chờ HTTP?
- Nếu provider đã tạo shipment nhưng response bị mất, rollback SQL có “xóa” shipment đó không?
- Nếu gateway retry request, điều gì ngăn shipment thứ hai được tạo?
- Transaction ngắn hơn có nghĩa business workflow phải biểu diễn intermediate state như thế nào?

## Gợi ý

### Gợi ý 1

Hãy dựng timeline riêng cho local database và remote provider; không có một commit point chung giữa hai hệ thống.

### Gợi ý 2

Connection pool là bounded shared resource. Một dependency chậm có thể giữ connection/transaction lâu hơn hàng chục lần bình thường.

## Kết quả code review tham khảo

### Critical — Giữ database transaction qua remote HTTP call

**Vấn đề:** Transaction bắt đầu trước SQL work và chỉ commit sau khi shipping provider trả về.

**Tại sao xảy ra:** Team cố dùng local transaction như một atomic boundary cho cả database và HTTP dependency.

**Ảnh hưởng production:** Khi provider chậm, SQL connection/transaction sống lâu; lock duration tăng, pool bị chiếm, request khác phải chờ connection và có thể timeout dây chuyền.

**Cách sửa:** Giữ local transaction ngắn, chỉ bao quanh invariants/local state cần atomic. Model external side effect thành workflow riêng với durable state.

### Critical — Remote side effect không rollback cùng SQL transaction

**Vấn đề:** Provider có thể tạo shipment rồi application fail trước `CommitAsync`.

**Tại sao xảy ra:** HTTP service không tham gia SQL transaction.

**Ảnh hưởng production:** SQL rollback về `Pending` nhưng shipment thật đã tồn tại; retry có thể tạo shipment thứ hai.

**Cách sửa:** Dùng stable operation/idempotency key nếu provider hỗ trợ; persist workflow state và reconcile unknown outcome.

### High — Inventory locks bị kéo dài bởi network latency

**Vấn đề:** Stock rows có thể bị update/lock rồi transaction chờ HTTP nhiều giây.

**Tại sao xảy ra:** External latency nằm bên trong critical section.

**Ảnh hưởng production:** Contention tăng, deadlock/lock timeout và throughput giảm ngay cả khi SQL query bản thân nhanh.

**Cách sửa:** Thiết kế reservation transaction ngắn, commit reservation/pending-shipment state rồi xử lý external work ngoài transaction.

### High — Không có idempotency boundary cho shipment creation

**Vấn đề:** `POST /shipments` không có stable operation key trong snippet.

**Tại sao xảy ra:** Retry được xem như request-level concern thay vì logical-operation concern.

**Ảnh hưởng production:** Gateway/client retry hoặc recovery sau unknown outcome có thể tạo duplicate shipment.

**Cách sửa:** Stable key theo logical shipment attempt/order; reuse qua retry/restart, kết hợp local uniqueness/state machine.

### High — Không có durable intermediate workflow state

**Vấn đề:** Order chỉ chuyển thẳng từ `Pending` sang `Confirmed` sau remote success.

**Tại sao xảy ra:** Workflow nhiều hệ thống bị model như một synchronous transaction.

**Ảnh hưởng production:** Crash/timeout không có trạng thái để recovery worker biết phải create, query hay compensate.

**Cách sửa:** Model states như `InventoryReserved`, `ShipmentPending`, `ShipmentUnknown`, `Confirmed`, `Failed/CompensationRequired` tùy domain.

### High — Concurrent confirmations có thể tranh cùng order/stock

**Vấn đề:** Snippet không thể hiện optimistic concurrency token, atomic conditional update hoặc locking strategy có chủ đích.

**Tại sao xảy ra:** Read-check-write dựa vào transaction mặc định nhưng business concurrency contract chưa rõ.

**Ảnh hưởng production:** Nhiều requests có thể contend mạnh; tùy isolation/invariants, oversell hoặc duplicate workflow có thể xảy ra.

**Cách sửa:** Enforce order transition và stock reservation bằng database constraints/conditional updates/concurrency token phù hợp, kèm unique logical operation.

### Medium — N+1 stock queries kéo dài transaction

**Vấn đề:** Mỗi order item chạy một `SingleAsync` riêng.

**Tại sao xảy ra:** Query theo item trong loop.

**Ảnh hưởng production:** Nhiều round trips và transaction duration dài hơn, tăng lock/pool pressure.

**Cách sửa:** Batch-load/update stocks cần thiết; vẫn phải giữ correctness khi concurrent reservations xảy ra.

### Medium — Response không được dispose rõ ràng

**Vấn đề:** `HttpResponseMessage` không dùng `using`/`await using` phù hợp.

**Ảnh hưởng production:** Resource lifetime kém rõ ràng; dưới tải cao có thể làm HTTP resource usage khó kiểm soát.

**Cách sửa:** Dispose response sau khi đọc xong; cấu hình `HttpClient` qua factory/resilience pipeline theo architecture.

### Medium — Business failure dùng generic exception

**Vấn đề:** `Out of stock` và invalid order state ném `InvalidOperationException`.

**Ảnh hưởng production:** API có thể trả 500 cho expected domain conflict, kích hoạt retry sai ở gateway/client.

**Cách sửa:** Map domain outcomes sang explicit API semantics (`409`, validation/domain result...) và chỉ retry transient infrastructure failures có contract rõ.

### Medium — Không có timeout budget/resilience contract rõ ràng

**Vấn đề:** External call dùng request token nhưng không thể hiện per-dependency timeout, retry classification hay total request budget.

**Ảnh hưởng production:** Slow dependency chiếm request capacity lâu; retry nhiều layer có thể nhân tải.

**Cách sửa:** Thiết kế timeout/retry budget end-to-end, không retry non-idempotent operation nếu chưa có idempotency guarantee.

## Phiên bản thiết kế đề xuất

Một hướng là tách thành hai phase:

1. Trong transaction ngắn: validate order, atomically reserve stock, tạo `ShipmentOperation` với stable ID/idempotency key và chuyển order sang `ShipmentPending`; commit.
2. Worker hoặc synchronous orchestrator gọi provider ngoài SQL transaction bằng stable key.
3. Persist result trong transaction ngắn. Nếu timeout sau khi request đã rời process, đánh dấu `Unknown` và reconcile bằng idempotency key/provider reference thay vì tạo operation mới.
4. Nếu shipment chắc chắn thất bại, release reservation bằng explicit compensation có concurrency/idempotency protection.

Nếu việc phát job ra broker xảy ra sau DB commit, dùng transactional outbox để tránh dual-write gap. Consumer phải idempotent vì at-least-once delivery có thể redeliver.

Không phải mọi hệ thống cần saga framework. Điều cần thiết là explicit state machine, durable intent, stable identity và recovery path cho từng failure window.

## Trade-offs

Transaction ngắn giảm lock/pool pressure nhưng workflow trở thành eventually consistent. Client có thể nhận trạng thái pending thay vì shipment ID ngay lập tức. Durable outbox/worker tăng implementation và operational complexity, đổi lại hệ thống chịu crash/retry tốt hơn. Compensation cũng không tương đương rollback tuyệt đối; domain phải xác định điều gì xảy ra nếu release inventory hoặc cancel shipment thất bại.

## Cách kiểm thử

- **Load/fault test:** provider latency tăng từ 200 ms lên 20 s; SQL pool usage và unrelated endpoint latency không được tăng tuyến tính theo external latency.
- **Crash test:** kill process sau provider side effect nhưng trước local result persistence; recovery không tạo shipment thứ hai.
- **Concurrency test:** nhiều requests confirm cùng order và nhiều orders tranh cùng SKU; inventory invariant không bị phá.
- **Unknown-outcome test:** provider commit rồi drop response; workflow chuyển `Unknown`/reconcile đúng.
- **Outbox test:** DB commit thành công nhưng publisher crash; event vẫn được phát sau restart.
- **Compensation test:** permanent provider failure release reservation đúng một lần.

## Quan sát trong production

Theo dõi SQL connection-pool wait/timeout, active transactions, transaction duration, lock waits/deadlocks, shipping dependency latency/error/timeout, workflow state age, unknown-outcome count, retry count, duplicate-prevention events, outbox backlog và oldest pending shipment age. Correlate bằng order ID + stable shipment-operation ID; không log address/payment-sensitive data ngoài nhu cầu tối thiểu.

## Câu hỏi phỏng vấn mở rộng

1. Nếu shipping provider không hỗ trợ idempotency key hoặc query-by-client-reference, bạn giảm duplicate risk thế nào và chấp nhận limitation nào?
2. Nếu inventory reservation phải hết hạn sau 15 phút, bạn thiết kế expiration/compensation thế nào để không release stock của một workflow đã confirmed?
3. Khi nào một synchronous workflow vẫn hợp lý thay vì outbox + worker?

# Code Review Challenge 2 — MongoDB pagination bằng `Skip` + sort không ổn định gây duplicate/missing records

**Chủ đề:** MongoDB, C# MongoDB Driver, pagination, indexes, query plans, consistency, API design, performance, distributed writes  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một audit API lưu hàng chục triệu events trong MongoDB. UI hiển thị 100 records mỗi page, newest-first. Collection liên tục nhận writes từ nhiều application instances.

Team dùng `Skip(page * pageSize)` và sort theo `CreatedAt` descending. Khi người dùng đi từ page 1 sang page 2, đôi lúc thấy record lặp hoặc một số record “biến mất”. Với page sâu, latency tăng từ dưới 100 ms lên vài giây dù filter giống nhau. `CreatedAt` chỉ có độ chính xác milliseconds và nhiều events có cùng timestamp.

## Đoạn code cần review

```csharp
public async Task<IReadOnlyList<AuditEvent>> GetPageAsync(
    string tenantId,
    DateTimeOffset? from,
    DateTimeOffset? to,
    int page,
    int pageSize,
    CancellationToken ct)
{
    var filter = Builders<AuditEvent>.Filter
        .Eq(x => x.TenantId, tenantId);

    if (from is not null)
        filter &= Builders<AuditEvent>.Filter
            .Gte(x => x.CreatedAt, from.Value);

    if (to is not null)
        filter &= Builders<AuditEvent>.Filter
            .Lte(x => x.CreatedAt, to.Value);

    return await _collection.Find(filter)
        .SortByDescending(x => x.CreatedAt)
        .Skip(page * pageSize)
        .Limit(pageSize)
        .ToListAsync(ct);
}
```

Collection hiện có index:

```javascript
{ TenantId: 1, CreatedAt: -1 }
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và performance problems của pagination hiện tại.
2. Giải thích vì sao concurrent inserts làm offset pagination dịch chuyển giữa requests.
3. Giải thích vì sao sort chỉ bằng `CreatedAt` không tạo total order khi timestamps trùng nhau.
4. Đề xuất cursor/keyset pagination phù hợp MongoDB và compound index tương ứng.
5. Nêu semantics của cursor khi filter/time range thay đổi giữa pages.
6. Đề xuất tests/query-plan evidence và telemetry trước khi rollout.

## Câu hỏi gợi mở

- `Skip(N)` buộc server làm gì với N records đứng trước page cần lấy?
- Nếu 50 records mới được insert trước khi client lấy page 2, offset cũ còn trỏ cùng vị trí logic không?
- Với hai documents có cùng `CreatedAt`, field nào có thể tạo tie-breaker ổn định?
- Cursor có nên chỉ chứa `_id`, hay phải encode toàn bộ sort boundary?

## Gợi ý

### Gợi ý 1

Pagination ổn định cần một total order. `CreatedAt` một mình không đảm bảo điều đó nếu nhiều documents có cùng timestamp.

### Gợi ý 2

Keyset pagination hỏi “records sau boundary này” thay vì “bỏ qua N records từ đầu result set hiện tại”.

## Kết quả code review tham khảo

### High — Offset pagination dịch chuyển dưới concurrent inserts

**Vấn đề:** Page 2 được tính bằng offset trên result set tại thời điểm request thứ hai, không phải snapshot của page 1.

**Tại sao xảy ra:** Records mới được insert ở đầu sort order làm các records cũ dịch vị trí.

**Ảnh hưởng production:** User có thể thấy duplicate hoặc missing records khi browse liên tiếp.

**Cách sửa:** Dùng cursor/keyset dựa trên sort boundary ổn định; nếu requirement là snapshot-consistent toàn phiên browse thì cần contract mạnh hơn riêng.

### High — Sort không có deterministic tie-breaker

**Vấn đề:** Nhiều events có cùng `CreatedAt` nhưng query chỉ sort field này.

**Tại sao xảy ra:** Timestamp không tạo total order.

**Ảnh hưởng production:** Thứ tự giữa documents cùng timestamp có thể không ổn định giữa queries/plans, làm pagination boundary mơ hồ.

**Cách sửa:** Sort `{ CreatedAt: -1, _id: -1 }` hoặc stable unique key tương đương và encode cả hai trong cursor.

### High — Deep `Skip` có cost tăng theo offset

**Vấn đề:** Page sâu yêu cầu server đi qua/bỏ qua nhiều index entries/documents trước khi trả `Limit` nhỏ.

**Ảnh hưởng production:** Latency và work tăng theo page number, làm deep navigation đắt và dễ gây resource pressure.

**Cách sửa:** Keyset range query bắt đầu từ boundary gần vị trí cần đọc thay vì offset từ đầu.

### High — Index chưa hỗ trợ tie-breaker mới tối ưu

**Vấn đề:** Index `{ TenantId: 1, CreatedAt: -1 }` không chứa `_id` làm sort key thứ hai.

**Ảnh hưởng production:** Query mới có thể cần sort/work thêm hoặc không tận dụng index như mong muốn.

**Cách sửa:** Đánh giá compound index `{ TenantId: 1, CreatedAt: -1, _id: -1 }` bằng `explain` trên data distribution thực tế.

### Medium — Không validate `page`/`pageSize`

**Vấn đề:** Negative/huge values có thể tạo lỗi hoặc expensive query.

**Ảnh hưởng production:** Abuse hoặc bug client gây tải lớn.

**Cách sửa:** Với cursor API, giới hạn `pageSize` rõ ràng; reject invalid cursor/filter combination.

### Medium — Cursor/filter contract chưa tồn tại

**Vấn đề:** Nếu client đổi tenant/time filter nhưng reuse cursor cũ, boundary có thể không còn nghĩa.

**Cách sửa:** Cursor nên được ký/opaque và gắn với relevant filter/sort version hoặc server phải validate compatibility.

### Medium — Inclusive time boundaries có thể gây semantic ambiguity

**Vấn đề:** `Gte(from)`/`Lte(to)` có thể đúng hoặc sai tùy API contract, đặc biệt khi các batch adjacent dùng chung boundary.

**Cách sửa:** Document rõ inclusive/exclusive semantics; không sửa máy móc nếu requirement hiện tại cần inclusive range.

### Medium — Không có projection

**Vấn đề:** Nếu `AuditEvent` lớn nhưng list UI chỉ cần vài fields, query đọc/deserializes nhiều dữ liệu hơn cần thiết.

**Ảnh hưởng production:** Network, CPU và memory tăng.

**Cách sửa:** Projection cho list view khi phù hợp; giữ detail endpoint riêng.

### Medium — Không có evidence từ query plan

**Vấn đề:** Có index không đồng nghĩa query luôn hiệu quả trên production cardinality.

**Cách sửa:** Kiểm tra `explain`/execution stats, keys examined, docs examined, sort stage, returned count và latency theo tenant/time-range thực tế.

## Phiên bản đề xuất

Với sort descending `(CreatedAt, _id)`, cursor chứa boundary cuối page trước: `lastCreatedAt` và `lastId`. Query page tiếp theo lấy documents nhỏ hơn boundary theo lexicographic order:

```csharp
var filter = Builders<AuditEvent>.Filter
    .Eq(x => x.TenantId, tenantId);

// Apply validated time-range filters first.

if (cursor is not null)
{
    var olderTimestamp = Builders<AuditEvent>.Filter
        .Lt(x => x.CreatedAt, cursor.CreatedAt);

    var sameTimestampOlderId =
        Builders<AuditEvent>.Filter.Eq(x => x.CreatedAt, cursor.CreatedAt) &
        Builders<AuditEvent>.Filter.Lt(x => x.Id, cursor.Id);

    filter &= olderTimestamp | sameTimestampOlderId;
}

var rows = await _collection.Find(filter)
    .Sort(Builders<AuditEvent>.Sort
        .Descending(x => x.CreatedAt)
        .Descending(x => x.Id))
    .Limit(pageSize + 1)
    .Project(x => new AuditListItem
    {
        Id = x.Id,
        CreatedAt = x.CreatedAt,
        Action = x.Action,
        ActorId = x.ActorId
    })
    .ToListAsync(ct);
```

Index candidate:

```javascript
{ TenantId: 1, CreatedAt: -1, _id: -1 }
```

Lấy `pageSize + 1` giúp xác định `hasNextPage` mà không cần `CountDocuments` cho mỗi page. Cursor nên opaque đối với client, encode boundary + query version/filter fingerprint cần thiết và được integrity-protected nếu client không được phép sửa.

Lưu ý: keyset pagination làm traversal ổn định hơn trước inserts mới ở đầu, nhưng không tự cung cấp snapshot isolation xuyên nhiều HTTP requests. Nếu business yêu cầu “toàn bộ browse session phải thấy đúng một snapshot”, cần snapshot token/materialized result/consistent-read strategy riêng và đánh đổi resource/complexity.

## Trade-offs

Cursor pagination rất tốt cho next/previous traversal và deep datasets nhưng không hỗ trợ “nhảy thẳng page 10.000” theo cách offset đơn giản. Nếu UI thật sự cần random page numbers, cần cân nhắc UX hoặc một indexing/search strategy khác. Compound index tăng storage và write amplification; chỉ tạo index sau khi đo query workload thực tế.

## Cách kiểm thử

- **Deterministic ordering test:** tạo nhiều documents có cùng `CreatedAt`; traverse toàn bộ bằng cursor và xác nhận không duplicate/missing.
- **Concurrent insert test:** lấy page 1, insert records mới hơn, lấy page 2 bằng cursor; page 2 không lặp records page 1.
- **Deep dataset benchmark:** so sánh page sâu bằng `Skip` và keyset trên hàng triệu records.
- **Explain-plan test:** xác nhận index được dùng, không có unexpected blocking sort và `keysExamined/docsExamined` hợp lý.
- **Cursor validation test:** sửa tenant/time range hoặc tamper cursor phải bị reject theo API contract.
- **Boundary test:** timestamps trùng nhau, first/last page, empty result, pageSize max.

## Quan sát trong production

Theo dõi query latency p50/p95/p99, `keysExamined`, `docsExamined`, returned count, slow-query rate, cursor decode/validation failures, page depth/traversal rate và MongoDB CPU/IO. Phân tách metric theo query shape/tenant cardinality nhưng tránh high-cardinality labels chứa raw tenant/user IDs nếu telemetry backend không phù hợp.

## Câu hỏi phỏng vấn mở rộng

1. Nếu UI bắt buộc hiển thị tổng số pages chính xác trong khi collection liên tục nhận writes, bạn định nghĩa “total” tại thời điểm nào và chấp nhận cost/consistency nào?
2. Nếu `_id` không tương quan thời gian với `CreatedAt`, nó vẫn dùng được làm tie-breaker không? Điều kiện cần là gì?
3. Nếu user cần browse backward lẫn forward, cursor và sort/query boundary thay đổi thế nào?

## Cách tự luyện hôm nay

Với mỗi challenge, hãy tự dành khoảng 30–35 phút trước phần đáp án:

1. Viết findings theo format **Severity → Evidence → Failure scenario → Fix → Test**.
2. Xác định rõ resource/consistency boundary trước khi chọn library hoặc pattern.
3. Phân biệt **correctness**, **reliability**, **performance**, **security** và **operability**.
4. Nêu ít nhất một test có thể tái tạo failure deterministically.
5. Sau đó mới đối chiếu phần review tham khảo và tự chấm mức độ reasoning của mình.
