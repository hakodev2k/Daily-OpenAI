# Code Review Challenge 1 — Phát hành vé trùng khi Azure Service Bus retry

**Chủ đề:** .NET 8, Azure Service Bus, SQL Server, distributed consistency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** Khoảng 9

## Bối cảnh

Ứng dụng đặt vé có 4 worker instance, nhận `BookingPaid` từ queue, ghi SQL và gọi đối tác phát hành vé. Lưu lượng peak 60 message/s. Có khách nhận hai vé; có booking Paid nhưng không có vé. Đối tác có thể timeout sau khi đã phát hành; chưa rõ có hỗ trợ idempotency key hoặc lookup hay không. Không được thay đổi producer trong hotfix đầu tiên.

## Đoạn code cần review

```csharp
public record BookingPaid(Guid EventId, Guid BookingId, decimal Amount);

public sealed class TicketWorker : BackgroundService
{
    private readonly ServiceBusClient _client;
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly HttpClient _http;
    private readonly ILogger<TicketWorker> _log;

    public TicketWorker(ServiceBusClient client, IServiceScopeFactory scopeFactory,
        HttpClient http, ILogger<TicketWorker> log)
    {
        _client = client;
        _scopeFactory = scopeFactory;
        _http = http;
        _log = log;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await using var processor = _client.CreateProcessor("booking-paid",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = true,
                MaxConcurrentCalls = 32
            });
        processor.ProcessMessageAsync += async args =>
        {
            var evt = args.Message.Body.ToObjectFromJson<BookingPaid>();
            using var scope = _scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var booking = await db.Bookings.FindAsync(evt.BookingId);
            if (booking == null) return;

            booking.PaymentStatus = "Paid";
            await db.SaveChangesAsync();
            var response = await _http.PostAsJsonAsync("/tickets/issue",
                new { evt.BookingId, evt.Amount });
            if (!response.IsSuccessStatusCode)
                _log.LogWarning("Provider failed: {Status}", response.StatusCode);
            _log.LogInformation("Processed {EventId}", evt.EventId);
        };
        processor.ProcessErrorAsync += args =>
        {
            _log.LogError(args.Exception, "Processor error");
            return Task.CompletedTask;
        };
        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — External side effect không idempotent

**Vấn đề:** Không deduplicate theo EventId và không có stable request key.  
**Tại sao xảy ra:** At-least-once delivery, lock expiry và ambiguous timeout cho phép xử lý lại.  
**Ảnh hưởng production:** Phát hành vé hai lần, chi phí và tranh chấp.  
**Cách sửa:** Unique EventId trong inbox; ticket request durable, stable idempotency key với provider nếu hỗ trợ; nếu không, reconciliation trước retry và trạng thái Unknown.

### [Critical] — Complete message dù phát hành vé thất bại

**Vấn đề:** HTTP non-2xx chỉ log rồi handler return.  
**Tại sao xảy ra:** AutoCompleteMessages=true và không throw.  
**Ảnh hưởng production:** Queue báo thành công nhưng khách không có vé.  
**Cách sửa:** Explicit settlement sau durable commit; retry/DLQ cho failure phân loại.

### [High] — SQL và HTTP không atomic

**Vấn đề:** PaymentStatus=Paid commit trước external call.  
**Tại sao xảy ra:** SQL transaction không bao trùm provider.  
**Ảnh hưởng production:** Crash tạo trạng thái Paid không có vé.  
**Cách sửa:** Ghi payment và TicketRequest Pending trong một SQL transaction; dispatcher riêng xử lý.

### [High] — Duplicate check nếu chỉ làm ở application không đủ

**Vấn đề:** Nhiều worker có thể đồng thời claim cùng event.  
**Tại sao xảy ra:** Read-then-write race.  
**Ảnh hưởng production:** Hai request đến provider.  
**Cách sửa:** Database UNIQUE(EventId), conditional claim/lease và xử lý duplicate-key chính xác.

### [High] — Không truyền CancellationToken hoặc timeout

**Vấn đề:** DB và HTTP có thể chạy sau shutdown/lock-loss.  
**Tại sao xảy ra:** Không truyền args.CancellationToken, không đặt request budget.  
**Ảnh hưởng production:** Duplicate, worker shutdown chậm, backlog.  
**Cách sửa:** Propagate cancellation, bounded timeout, không xem cancellation là rollback side effect.

### [High] — Không quản lý processing time và lock renewal

**Vấn đề:** 32 concurrent handlers chờ external API.  
**Tại sao xảy ra:** Handler giữ queue lock trong I/O không giới hạn.  
**Ảnh hưởng production:** Lock expire và redelivery.  
**Cách sửa:** Handler chỉ commit durable intent rồi settle; tune concurrency theo dependency metrics.

### [Medium] — Thiếu schema validation

**Vấn đề:** EventId rỗng, Amount không hợp lệ, payload lỗi chưa được xử lý.  
**Tại sao xảy ra:** Tin tưởng dữ liệu message.  
**Ảnh hưởng production:** Poison-message retry hoặc trạng thái sai.  
**Cách sửa:** Validate version/schema, dead-letter permanent invalid payload.

### [Medium] — Booking null bị bỏ qua

**Vấn đề:** Return khiến message được complete.  
**Tại sao xảy ra:** Không phân biệt delayed data với invalid booking.  
**Ảnh hưởng production:** Mất event hợp lệ đến sớm.  
**Cách sửa:** Bounded scheduled retry hoặc DLQ theo business SLA.

### [Medium] — Telemetry không phản ánh nghiệp vụ

**Vấn đề:** Log Processed kể cả ticket issuance failed.  
**Tại sao xảy ra:** Chỉ đo handler, không đo ticket state.  
**Ảnh hưởng production:** Dashboard xanh giả.  
**Cách sửa:** Correlate EventId, BookingId, TicketRequestId; theo dõi Pending, Issued, Unknown, retries, age và DLQ.

## Phiên bản đề xuất

Tách queue ingestion và external dispatcher. Ví dụ handler dưới đây giả định EF Core model đã có InboxEvent(EventId UNIQUE), TicketRequest(EventId UNIQUE, BookingId, Status), migration và mapping. `IsInboxDuplicate` phải kiểm tra đúng constraint, không nuốt các DB errors khác.

```csharp
public async Task HandleAsync(ProcessMessageEventArgs args)
{
    BookingPaid evt;
    try
    {
        evt = args.Message.Body.ToObjectFromJson<BookingPaid>();
        if (evt.EventId == Guid.Empty || evt.BookingId == Guid.Empty ||
            evt.Amount <= 0) throw new JsonException("Invalid event");
    }
    catch (JsonException)
    {
        await args.DeadLetterMessageAsync(args.Message,
            "InvalidPayload", cancellationToken: args.CancellationToken);
        return;
    }

    try
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await using var tx =
            await db.Database.BeginTransactionAsync(args.CancellationToken);
        db.InboxEvents.Add(new InboxEvent { EventId = evt.EventId });
        var booking = await db.Bookings.SingleOrDefaultAsync(
            b => b.Id == evt.BookingId, args.CancellationToken);
        if (booking is null) throw new BookingNotReadyException();
        booking.PaymentStatus = "Paid";
        db.TicketRequests.Add(new TicketRequest {
            EventId = evt.EventId, BookingId = evt.BookingId, Status = "Pending"
        });
        await db.SaveChangesAsync(args.CancellationToken);
        await tx.CommitAsync(args.CancellationToken);
    }
    catch (DbUpdateException ex) when (IsInboxDuplicate(ex))
    {
        // Existing durable event: no new ticket request.
    }
    catch (BookingNotReadyException)
    {
        await args.AbandonMessageAsync(args.Message,
            cancellationToken: args.CancellationToken);
        return;
    }

    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
}
```

Nếu `CommitAsync` trả kết quả không rõ do mất kết nối, kiểm tra InboxEvent trước khi quyết định retry. Nếu booking chưa sẵn sàng, tránh hot-loop abandon bằng scheduled backoff. Dispatcher cần atomic lease/claim cho TicketRequest, stable key, bounded retry và trạng thái Unknown khi không thể biết provider đã phát hành hay chưa. Nếu business cho phép nhiều vé trên một booking, unique key phải theo business operation, không nhất thiết BookingId.

## Giải thích thiết kế sau khi sửa

Transaction chỉ bảo đảm SQL payment + durable intent; queue complete sau commit. Redelivery được UNIQUE(EventId) hấp thụ. External call không được xem là exactly-once nếu provider không hỗ trợ idempotency/reconciliation. Không nên giữ SQL transaction trong suốt HTTP call.

## Trade-offs

Thêm table, dispatcher, operational monitoring và eventual consistency; đổi lại có thể khôi phục sau crash. Nếu provider không hỗ trợ lookup hoặc idempotency, cần manual reconciliation cho Unknown thay vì blind retry. Concurrency thấp giảm tải provider nhưng tăng queue latency; phải đo và tune.

## Cách kiểm thử

1. Concurrency integration: 100 duplicate EventId qua 4 workers tạo đúng một TicketRequest.
2. Failure injection: kill worker sau SQL commit trước queue complete; redelivery không tạo duplicate.
3. Provider timeout sau success: không phát hành lần hai khi có idempotency/lookup.
4. Malformed payload và missing booking: DLQ hoặc scheduled retry có kiểm soát.
5. Load test peak 60/s: theo dõi queue age, SQL waits, provider 429 và p95.

## Quan sát trong production

Azure Monitor: ActiveMessages, DLQ count, oldest Pending age; Application Insights traces EventId → SQL → TicketRequest → provider, request duration và outcome; SQL unique conflicts, transaction waits; business metrics Paid/Issued/Unknown. Alert theo SLA issuance, không dựa riêng message completion.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không hỗ trợ idempotency lẫn lookup, bạn xử lý Unknown thế nào?
2. Nếu một booking có nhiều lần thanh toán hợp lệ, unique key phải thay đổi ra sao?
3. Nếu SQL commit thành công nhưng queue Complete timeout, bạn xác minh và retry thế nào?

import { ref, watch, onMounted } from "vue";

type Product = { id: string; name: string; descriptionHtml: string };
const tenantId = ref(localStorage.getItem("tenant") || "tenant-a");
const query = ref("");
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref("");

async function search() {
  loading.value = true;
  error.value = "";
  try {
    const url = "/api/products?tenantId=" + tenantId.value +
      "&q=" + query.value + "&pageSize=500";
    const response = await fetch(url, {
      headers: { Authorization: "Bearer " +
        localStorage.getItem("access_token") }
    });
    const data = await response.json();
    products.value = data.items;
    total.value = data.total;
  } catch (e) {
    error.value = String(e);
  } finally {
    loading.value = false;
  }
}

watch([tenantId, query], search);
onMounted(search);

function switchTenant(id: string) {
  tenantId.value = id;
  localStorage.setItem("tenant", id);
}
</script>

<template>
  <input v-model="query" />
  <select :value="tenantId"
    @change="switchTenant(($event.target as HTMLSelectElement).value)">
    <option value="tenant-a">Tenant A</option>
    <option value="tenant-b">Tenant B</option>
  </select>
  <div v-if="loading">Loading...</div>
  <p v-if="error">{{ error }}</p>
  <p>{{ total }} results</p>
  <article v-for="p in products" :key="p.id">
    <h3>{{ p.name }}</h3>
    <div v-html="p.descriptionHtml"></div>
  </article>
</template>

## Kết quả code review tham khảo

### [Critical] — Tenant authorization có thể bị bypass

**Vấn đề:** tenantId do client cung cấp; chưa có bằng chứng API enforce membership.  
**Tại sao xảy ra:** UI filtering không phải security boundary.  
**Ảnh hưởng production:** Nếu backend tin tenantId, có nguy cơ IDOR/cross-tenant leakage.  
**Cách sửa:** Backend kiểm tra user/tenant membership và áp tenant scope ở query; test trực tiếp API. Đây là rủi ro có điều kiện, cần kiểm tra backend.

### [High] — Untrusted CMS HTML qua v-html

**Vấn đề:** Render HTML chưa được sanitize.  
**Tại sao xảy ra:** v-html bỏ escaping mặc định.  
**Ảnh hưởng production:** Stored XSS nếu nguồn HTML độc hại.  
**Cách sửa:** Dùng text interpolation nếu có thể; nếu cần rich text, sanitization allowlist được duy trì và CSP defense-in-depth.

### [High] — Race condition response ghi đè

**Vấn đề:** Request A hoàn thành sau request B có thể overwrite state.  
**Tại sao xảy ra:** Không cancellation hoặc request identity.  
**Ảnh hưởng production:** Hiển thị dữ liệu tenant cũ.  
**Cách sửa:** AbortController + generation counter, chỉ current request được cập nhật UI.

### [High] — Access token lưu localStorage

**Vấn đề:** XSS có thể đọc bearer token.  
**Tại sao xảy ra:** Script cùng origin truy cập localStorage.  
**Ảnh hưởng production:** Token theft nếu XSS thành công.  
**Cách sửa:** Cân nhắc BFF với HttpOnly Secure SameSite cookie, CSRF controls; nếu SPA bearer, giảm scope/lifetime và tránh persistent storage khi có thể.

### [Medium] — Không kiểm tra response.ok

**Vấn đề:** 4xx/5xx vẫn parse JSON rồi cập nhật state.  
**Tại sao xảy ra:** fetch không reject theo HTTP status.  
**Ảnh hưởng production:** UI sai và không có auth/error handling.  
**Cách sửa:** Check response.ok, validate payload và phân biệt 401/403/5xx.

### [Medium] — Request amplification

**Vấn đề:** Không debounce và pageSize=500.  
**Tại sao xảy ra:** Watch chạy mỗi thay đổi query.  
**Ảnh hưởng production:** API/DB quá tải, p95 tăng.  
**Cách sửa:** Debounce ~300ms, pageSize 25, server-side cap và pagination.

### [Medium] — Loading/error bị request cũ ghi đè

**Vấn đề:** finally của request cũ đặt loading=false khi request mới còn chạy.  
**Tại sao xảy ra:** Shared flags không gắn generation.  
**Ảnh hưởng production:** UX báo sai.  
**Cách sửa:** Chỉ latest request thay đổi loading/error.

### [Medium] — Dữ liệu tenant trước còn hiển thị trong lúc loading

**Vấn đề:** Không clear hoặc partition state khi tenant đổi.  
**Tại sao xảy ra:** Shared products array.  
**Ảnh hưởng production:** Nhầm lẫn thao tác hoặc lộ thông tin trên màn hình.  
**Cách sửa:** Clear ngay khi đổi tenant, hoặc cache keyed theo identity+tenant.

### [Low] — Không cleanup request khi unmount

**Vấn đề:** In-flight fetch không bị cancel khi component rời trang.  
**Tại sao xảy ra:** Không onUnmounted/cleanup.  
**Ảnh hưởng production:** Lãng phí network và khó đo telemetry.  
**Cách sửa:** Abort in-flight requests và cleanup debounce timer.

## Phiên bản đề xuất

Ví dụ dưới đây giả định API dùng BFF/session cookie; server phải enforce tenant authorization và page-size cap. Backend trả plain-text description; nếu business cần rich HTML, phải có sanitization policy riêng.

```vue
<script setup lang="ts">
import { ref, watch } from "vue";

type Product = { id: string; name: string; descriptionText: string };
type Result = { items: Product[]; total: number };
const tenantId = ref("tenant-a");
const query = ref("");
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref("");
let generation = 0;

watch([tenantId, query], (_now, _old, onCleanup) => {
  const id = ++generation;
  const controller = new AbortController();
  products.value = [];
  total.value = 0;
  loading.value = true;
  error.value = "";

  const timer = setTimeout(async () => {
    const params = new URLSearchParams({
      tenantId: tenantId.value, q: query.value.trim(),
      page: "1", pageSize: "25"
    });
    try {
      const response = await fetch("/api/products?" + params, {
        signal: controller.signal, credentials: "same-origin"
      });
      if (!response.ok) throw new Error("HTTP " + response.status);
      const data: unknown = await response.json();
      if (!isResult(data)) throw new Error("Invalid response");
      if (id === generation && !controller.signal.aborted) {
        products.value = data.items;
        total.value = data.total;
      }
    } catch {
      if (id === generation && !controller.signal.aborted)
        error.value = "Không thể tải sản phẩm";
    } finally {
      if (id === generation) loading.value = false;
    }
  }, 300);

  onCleanup(() => {
    clearTimeout(timer);
    controller.abort();
  });
}, { immediate: true });

function isResult(value: unknown): value is Result {
  if (!value || typeof value !== "object") return false;
  const x = value as Record<string, unknown>;
  return typeof x.total === "number" && Number.isFinite(x.total) &&
    x.total >= 0 && Array.isArray(x.items) &&
    x.items.every((p: unknown) => !!p && typeof p === "object" &&
      typeof (p as Product).id === "string" &&
      typeof (p as Product).name === "string" &&
      typeof (p as Product).descriptionText === "string");
}
</script>

<template>
  <input v-model="query" aria-label="Search products" />
  <select v-model="tenantId" aria-label="Tenant">
    <option value="tenant-a">Tenant A</option>
    <option value="tenant-b">Tenant B</option>
  </select>
  <p v-if="loading">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <p>{{ total }} results</p>
  <article v-for="p in products" :key="p.id">
    <h3>{{ p.name }}</h3>
    <p>{{ p.descriptionText }}</p>
  </article>
</template>
```

Production implementation cần tenant options từ API có quyền, pagination đầy đủ, auth UX cho 401/403 và CSRF protection với cookie session. AbortController giúp tiết kiệm tài nguyên nhưng không chứng minh server đã ngừng xử lý; generation guard bảo đảm latest response wins.

## Giải thích thiết kế sau khi sửa

Request identity giữ UI nhất quán khi response đảo thứ tự. Query encoding tránh URL sai. Text interpolation escape HTML. Tenant authorization thuộc backend, không thuộc select. Bounded page size và debounce giảm request amplification.

## Trade-offs

Debounce tăng độ trễ cảm nhận khoảng 300ms; clear list tránh stale tenant nhưng có thể flicker. BFF/cookie đòi hỏi CSRF design; SPA bearer có trade-offs riêng. Rich HTML sanitization có chi phí vận hành; plain text không giữ formatting CMS. Server-side pagination làm tăng tương tác khi duyệt nhiều trang nhưng giảm payload.

## Cách kiểm thử

1. Playwright: delay response tenant A, chuyển sang B, A trả sau; UI vẫn là B.
2. API security: user A yêu cầu tenant B không có quyền, backend từ chối/không trả dữ liệu B.
3. XSS: mô tả chứa HTML độc hại không thực thi script.
4. HTTP errors: 401/403/500 và invalid JSON không render state lỗi.
5. Load: gõ nhanh 10 ký tự, đo request count, payload và p95 API/SQL.

## Quan sát trong production

Browser Network và RUM: requests/search, aborted requests, discarded stale responses, UX latency. Application Insights: p50/p95/p99, dependency SQL, status 4xx/5xx, authorization denial và tenant-scoped metrics. Không log access token hoặc query nhạy cảm. Alert khi request rate và p95 cùng tăng; nếu dùng Akamai/CDN, kiểm tra cache key không trộn tenant/private response.

## Câu hỏi phỏng vấn mở rộng

1. Khi dùng Akamai cache cho catalog, bạn tránh cross-tenant cache leakage ra sao?
2. Nếu CMS bắt buộc rich HTML, nên sanitize tại ingestion hay render boundary?
3. Nếu dùng Vue Query, rủi ro authorization và stale cache nào vẫn tồn tại?

4. Enforce authorization ở trust boundary thực sự.
