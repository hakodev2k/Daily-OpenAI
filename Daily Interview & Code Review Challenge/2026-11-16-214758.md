# Câu 1 — Cơ chế SQL Server keyset pagination khi lọc theo tenant

**Loại câu hỏi:** Internal Mechanism  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** SQL Server, EF Core, indexes, execution plans

## Bối cảnh

API ASP.NET Core 8 phân trang 12 triệu Transactions, lọc TenantId, Status và ngày, sắp xếp CreatedAt DESC, Id DESC. Có index (CreatedAt DESC, Id DESC); một số tenant mất 4 giây dù Take(50), tenant khác 40 ms. Chưa rõ phân bố dữ liệu, actual plan và SQL do EF Core sinh ra.

## Câu hỏi chính

Giải thích optimizer, index access, keyset predicate và plan variability; thiết kế cách xác minh và cải thiện mà không tối ưu mù.

## Câu hỏi làm rõ nên cân nhắc

1. TenantId có luôn bắt buộc, phân bố tenant/status có lệch không?
2. Cursor gồm CreatedAt và Id chưa; yêu cầu consistency qua nhiều trang?
3. Actual plan, logical reads, Query Store và waits khác nhau thế nào?
4. Có bao nhiêu truy vấn có/không có Status và workload ghi ra sao?

## Gợi ý tư duy

### Gợi ý 1

TOP(50) không đồng nghĩa chỉ đọc 50 rows.

### Gợi ý 2

Residual predicate có thể lọc rất nhiều dòng sau khi index access.

### Gợi ý 3

So sánh composite index bắt đầu bằng TenantId và các query shape khác nhau.

## Cấu trúc trả lời đề xuất

Xác nhận contract → đọc SQL → actual execution plan/STATISTICS IO → kiểm tra cardinality và parameter sensitivity → thử index/query shape → benchmark read/write → rollout/rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

Predicate cho thứ tự giảm dần phải là CreatedAt < cursorDate OR (CreatedAt = cursorDate AND Id < cursorId); cần thứ tự unique. Index chỉ theo thời gian có thể phải quét nhiều rows không cùng tenant. AsNoTracking không thay thế SQL optimization.

### Điểm cộng

So sánh index (TenantId, Status, CreatedAt DESC, Id DESC) với (TenantId, CreatedAt DESC, Id DESC); kiểm tra key lookup, covering index, Query Store, skew và statistics.

### Senior+

Thảo luận plan reuse, parameter-sensitive workloads, index write amplification, canary, consistency và cursor validation.

## Hướng giải quyết tham khảo

Giả định TenantId bắt buộc, Status optional. Xác minh LINQ dịch đúng predicate keyset và ORDER BY hai cột. Actual plan cho biết Index Seek có thực sự seek theo tenant hay chỉ seek cursor rồi residual filter; đo actual/estimated rows, logical reads, duration và waits theo tenant lớn/nhỏ. Thử xây predicate động theo status thay vì OR nullable cho mọi trường hợp; benchmark hai composite indexes, INCLUDE các projection columns cần thiết, kiểm tra chi phí insert/update và disk. Query Store giúp so sánh plan và regression; parameter sniffing hoặc parameter-sensitive plans là giả thuyết cần kiểm chứng theo SQL Server version, không phải kết luận mặc định. Nếu insert mới xảy ra giữa các trang, keyset không bảo đảm snapshot xuyên request; cân nhắc watermark hoặc contract eventual list. Triển khai index có giám sát p95/p99, reads và rollback; không thêm Redis nếu chưa xác định bottleneck.

## Mẫu trả lời trong phỏng vấn

> Em sẽ kiểm tra SQL thực tế, cursor và actual execution plan trước. TOP 50 không đảm bảo SQL chỉ đọc 50 rows: index theo ngày có thể lọc rất nhiều rows không thuộc tenant. Em so sánh logical reads và estimates giữa tenant lớn, nhỏ, kiểm tra plan reuse và statistics. Sau đó em benchmark index bắt đầu bằng TenantId và query shape có hoặc không có Status, đo cả read lẫn write overhead. Em rollout có canary và rollback, đồng thời xác định consistency contract khi dữ liệu thay đổi giữa các trang.

## Câu hỏi đào sâu

1. Vì sao một composite index không tối ưu cho cả truy vấn có và không có Status?
2. Nếu index mới làm insert chậm 25%, bạn quyết định thế nào?
3. Nếu cần nhảy tới trang thứ 500, API contract nên thay đổi ra sao?

## Lỗi trả lời thường gặp

1. Cho rằng Take(50) nghĩa là 50 rows được đọc.
2. Bỏ Id khi timestamp trùng nhau.
3. Thêm index không xem actual plan và chi phí ghi.
4. Đổ lỗi EF Core tracking mà không đo SQL.

## Thang điểm 0–10

Clarification 2; mechanism 3; evidence 2; trade-offs/production 2; communication 1.

# Câu 2 — Service Bus backlog và duplicate notifications sau release

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, .NET BackgroundService, retries, idempotency, observability

## Bối cảnh

Worker .NET 8 đọc queue và gọi CRM để gửi thông báo cho workflow duyệt. Sau release 30 phút, active messages tăng từ 300 lên 85.000, có email trùng và DLQ tăng. CRM trả 429/503, App Service healthy và CPU 35%. Chưa rõ lock duration, settlement, prefetch, max concurrency, retry policy và CRM idempotency.

## Câu hỏi chính

Là incident lead, bạn xử lý 30 phút đầu và 24 giờ tiếp theo thế nào để giảm backlog mà không làm mất nghiệp vụ hay nhân đôi side effects?

## Câu hỏi làm rõ nên cân nhắc

1. Ingress, successful distinct completions/sec và oldest age?
2. CRM hỗ trợ idempotency key, Retry-After hoặc lookup operation không?
3. PeekLock hay ReceiveAndDelete, auto/manual completion?
4. DeliveryCount, lock-lost, DLQ reason, dependency spans và release diff?

## Gợi ý tư duy

### Gợi ý 1

Worker healthy không đồng nghĩa message hoàn thành.

### Gợi ý 2

Lock expiry và retry có thể giao lại message sau side effect thành công.

### Gợi ý 3

Đo successful unique operations thay vì chỉ attempted calls.

## Cấu trúc trả lời đề xuất

Impact → stabilize → evidence → competing hypotheses → verify → remediate → controlled recovery → test → alert.

## Ý chính của câu trả lời tốt

### Bắt buộc

Không purge queue hoặc tăng concurrency mù quáng. At-least-once delivery cần idempotent side effects. CRM timeout có thể xảy ra sau khi CRM đã commit. Phân biệt complete message với business operation success.

### Điểm cộng

Bounded concurrency, Retry-After, exponential backoff+jitter, DLQ triage, correlation IDs, lock renewal và graceful shutdown.

### Senior+

Tính net drain rate, recovery ETA, giới hạn atomicity giữa DB inbox và CRM, rollout canary và reconciliation.

## Hướng giải quyết tham khảo

Đầu tiên xác định impact bằng oldest age, số distinct operations trễ và duplicate count, thông báo SLA cho stakeholders. Tạm dừng rollout; nếu tương thích schema, cân nhắc rollback worker. Giảm concurrency khi CRM trả 429, không purge/replay DLQ hàng loạt. Đặt giả thuyết: concurrency tăng gây throttling; lock hết hạn vì CRM chậm; thay đổi auto-complete; poison payload; connection starvation. Kiểm chứng qua dependency traces, DeliveryCount, lock-lost, DLQ reason, deployment version và CRM headers. Với immutable OperationId, dùng CRM idempotency key nếu có. Inbox unique constraint chỉ chặn duplicate local processing, không tạo atomic transaction với CRM: nếu CRM thành công rồi timeout, cần lookup/reconciliation và state Unknown. Complete message khi trạng thái nghiệp vụ được xác nhận an toàn; retry bounded và DLQ cho lỗi vĩnh viễn. Tính drain rate = distinct successful operations/sec trừ arrival rate; nếu <=0, chưa có ETA. Canary replay DLQ sau phân loại. Test crash sau CRM call, 429, 503, timeout after commit, lock lost, scale-out. Alert queue age, completion rate, DLQ, duplicates và downstream 429.

## Mẫu trả lời trong phỏng vấn

> Em sẽ đo tuổi backlog và successful distinct operations, không chỉ CPU. Trước mắt em ngừng rollout và giảm áp lực CRM, giữ nguyên queue durable. Em điều tra concurrency, lock expiry, settlement và retry vì message có thể redeliver sau khi CRM đã xử lý. Em cần operation ID, idempotency ở CRM hoặc reconciliation nếu CRM không hỗ trợ. Sau fix em canary, tính net drain rate, replay DLQ có kiểm soát và bổ sung alert oldest age, lock-lost, duplicate side effects.

## Câu hỏi đào sâu

1. Nếu CRM không có idempotency hoặc lookup, bạn có thể cam kết điều gì?
2. Vì sao tăng MaxConcurrentCalls có thể làm throughput giảm?
3. Nếu rollback không tương thích message schema mới thì sao?

## Lỗi trả lời thường gặp

1. Purge queue để giảm dashboard backlog.
2. Giả định at-least-once là exactly-once side effects.
3. Retry vô hạn không tôn trọng 429 và lock.
4. Chỉ nhìn health endpoint/CPU.
5. Cho rằng unique inbox row làm CRM call atomic.

## Thang điểm 0–10

Impact/clarification 2; stabilization 2; hypotheses/evidence 2; distributed correctness 2; recovery/testing 1; communication 1.

# Câu 3 — Chọn PostgreSQL hay Elasticsearch cho product search

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** PostgreSQL, Elasticsearch, CQRS read model, security, API design

## Bối cảnh

Catalog 2 triệu sản phẩm trên PostgreSQL. React admin tìm SKU, status, giá; website cần full-text, typo tolerance, facets và ranking. Giá, tồn kho và visibility theo market cập nhật liên tục. Team 6 .NET developers, ngân sách vận hành hạn chế; target p95 300ms nhưng chưa xác định peak QPS. Cân nhắc PostgreSQL-only, PostgreSQL + Elasticsearch hoặc search microservice.

## Câu hỏi chính

Thiết kế ownership, API, indexing, consistency, authorization, failure recovery và rollout; khi nào thêm search engine hay microservice là đáng giá?

## Câu hỏi làm rõ nên cân nhắc

1. Peak QPS và relevance/facet/language requirements có thật sự bắt buộc?
2. Freshness SLA cho mô tả, giá, tồn kho và unpublish?
3. Visibility theo market, tenant hay user?
4. Khi search down, degraded mode hay 503 được chấp nhận?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt source of truth và read projection.

### Gợi ý 2

Indexing event có thể trùng hoặc đến sai thứ tự.

### Gợi ý 3

Stale visibility có thể là security incident, không chỉ UX bug.

## Cấu trúc trả lời đề xuất

Requirements/SLO → boundaries/ownership → API/data model → sync/replay → authorization/consistency → alternatives/cost → test/observability/rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

PostgreSQL giữ authoritative product/price/visibility. Search index là derived read model. Admin exact SKU có thể query DB. Public API enforce visibility an toàn, không tin stale index.

### Điểm cộng

Transactional outbox, idempotent indexer, versioning, alias reindex, reconciliation, shadow traffic, kill switch.

### Senior+

Đánh giá fail-closed visibility race, cost of complexity, ownership-based service boundary, SQL fallback capacity và consistency SLA riêng theo field.

## Hướng giải quyết tham khảo

Giả định exact admin lookup cần correctness và public relevance có thể eventual consistent cho mô tả; visibility không được leak. Benchmark PostgreSQL full-text/trigram và indexes trước. Nếu typo tolerance, multi-language analyzers và facets đòi hỏi vượt SQL, thêm Elasticsearch làm read model, không tự động tách microservice. DB transaction ghi Product và OutboxEvent; worker xử lý idempotent theo ProductId/Version, tránh older event ghi đè newer, có retry, DLQ/reconciliation và full reindex qua alias switch. Public API GET /search?q=&market= dùng validated filters, bounded pagination và market authorization; client không query search cluster trực tiếp. Index filter giảm tải nhưng không đủ để bảo đảm unpublish tức thì: cần authoritative visibility verification/denylist có bảo đảm hoặc fail closed. Giá/tồn kho có thể đọc từ DB nếu freshness nghiêm ngặt; nếu dùng read model cần SLA rõ. Khi Elasticsearch down, admin exact lookup tiếp tục; public fallback SQL chỉ khi load test chứng minh capacity, nếu không trả 503 có kiểm soát. Đo p95/p99, index lag, stale visibility blocks, zero-results, relevance, DB load và cost. Shadow queries trước cutover, feature flag và rollback. Microservice chỉ hợp lý khi ownership/release cadence độc lập bù được network, deployment và operational overhead.

## Mẫu trả lời trong phỏng vấn

> Em sẽ làm rõ relevance, QPS và freshness SLA trước. PostgreSQL vẫn là source of truth; admin SKU lookup có thể đi thẳng DB. Em benchmark PostgreSQL trước, chỉ thêm Elasticsearch khi yêu cầu full-text/facets chứng minh giá trị. Nếu thêm, em dùng outbox và idempotent indexer, có reindex và reconciliation. Quan trọng nhất là visibility: index stale không được làm lộ sản phẩm ẩn, nên API cần authoritative check hoặc fail-closed path. Em giữ modular monolith nếu team nhỏ và chưa cần independent deployment, rồi mới cân nhắc microservice khi lợi ích vận hành rõ.

## Câu hỏi đào sâu

1. Làm sao chứng minh không leak khi unpublish trước lúc index cập nhật?
2. Nếu PostgreSQL đạt p95 180ms hiện tại, khi nào nên đầu tư Elasticsearch?
3. Làm sao tránh event version 12 ghi đè version 13?

## Lỗi trả lời thường gặp

1. Mặc định microservices/search cluster là tốt hơn.
2. Tin rằng outbox bảo đảm consistency tức thì.
3. Dùng stale index làm nguồn quyền truy cập.
4. Không có reindex/rollback/reconciliation.
5. Không đo relevance và load.

## Thang điểm 0–10

Requirements 2; ownership/API 2; consistency/security 2; trade-offs 2; testing/observability 1; communication 1.
