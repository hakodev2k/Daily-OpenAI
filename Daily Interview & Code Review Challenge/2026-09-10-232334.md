# Câu 1 — `await using` có thực sự “dispose async” mọi thứ, và GC có tự dọn resource giúp bạn không?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, .NET 8, `IDisposable`, `IAsyncDisposable`, `await using`, `DisposeAsync`, `ValueTask`, GC, resource lifetime, streams, database/network resources, exception handling, production verification

## Bối cảnh

Một ASP.NET Core .NET 8 API tạo report lớn từ SQL Server rồi stream dữ liệu sang Azure Blob Storage. Một phần code được refactor như sau:

```csharp
public async Task GenerateAsync(
    Stream output,
    CancellationToken cancellationToken)
{
    await using var connection = new SqlConnection(_connectionString);
    await connection.OpenAsync(cancellationToken);

    await using var command = connection.CreateCommand();
    command.CommandText = "SELECT Id, Payload FROM ReportRows ORDER BY Id";

    await using var reader = await command.ExecuteReaderAsync(
        CommandBehavior.SequentialAccess,
        cancellationToken);

    using var gzip = new GZipStream(
        output,
        CompressionLevel.Fastest,
        leaveOpen: true);

    while (await reader.ReadAsync(cancellationToken))
    {
        var payload = reader.GetString(1);
        var bytes = Encoding.UTF8.GetBytes(payload);
        await gzip.WriteAsync(bytes, cancellationToken);
    }
}
```

Code chạy đúng trong phần lớn trường hợp. Tuy nhiên team đang tranh luận:

- một developer nói chỉ cần `using`, vì GC cuối cùng cũng cleanup resource;
- developer khác đổi mọi `using` thành `await using` vì “async luôn nhanh hơn”;
- một số resource implement cả `IDisposable` và `IAsyncDisposable`;
- API có tải cao, nhiều request bị cancellation giữa chừng;
- `output` được sở hữu bởi caller và không được đóng bởi method này;
- team chưa xác minh việc flush/finalization của `GZipStream` khi exception/cancellation xảy ra;
- database connection pool đôi khi tăng số connection đang bận trong các burst;
- chưa có evidence chứng minh disposal hiện tại là nguyên nhân chính.

Không giả định mọi loại resource có cùng disposal semantics.

## Câu hỏi chính

Hãy giải thích `IDisposable`, `IAsyncDisposable`, `using`, `await using` và GC liên hệ với nhau như thế nào. Vì sao GC không phải cơ chế thay thế deterministic disposal cho database/network/file resources? Khi một type implement cả hai interface thì bạn chọn sync hay async disposal dựa trên tiêu chí nào? Sau đó review flow trên, chỉ ra các lifetime/ownership điểm cần xác minh, cách xử lý exception/cancellation, và cách đo xem disposal/resource lifetime có thực sự gây production impact hay không.

## Câu hỏi làm rõ nên cân nhắc

1. `SqlConnection`, command, reader và `GZipStream` đang chạy trên provider/runtime version nào, và từng type thực sự implement disposal interfaces nào?
2. `output` là HTTP response stream, Blob stream hay một wrapper khác, và ai chịu trách nhiệm close/flush cuối cùng?
3. Khi request bị cancel giữa quá trình ghi gzip, business muốn giữ partial output, xóa output hay mark artifact failed?
4. Connection-pool pressure correlate với long-running query, slow output stream, cancellation hay disposal delay?
5. Report có thể lớn tới mức nào, và allocation từ `Encoding.UTF8.GetBytes` có đang tạo áp lực lớn hơn disposal cost không?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt **managed memory lifetime** với **external resource lifetime**. GC quản lý object memory; resource bên ngoài thường cần release theo contract riêng.

### Gợi ý 2

`await using` không phải optimization flag. Nó chọn asynchronous disposal path của một resource hỗ trợ `IAsyncDisposable`.

### Gợi ý 3

Trong pipeline streaming, lifetime của resource phía upstream và downstream liên kết với nhau. Một consumer chậm có thể giữ database reader/connection lâu dù disposal code hoàn toàn đúng.

## Cấu trúc trả lời đề xuất

1. Xác định ownership của từng resource.
2. Giải thích deterministic disposal vs GC/finalization.
3. Giải thích compile-time/runtime behavior của `using` và `await using` ở mức cần thiết.
4. Phân biệt sync và async cleanup cost.
5. Xem xét disposal order khi scope kết thúc hoặc exception xảy ra.
6. Phân tích cancellation và partial-output semantics.
7. Điều tra connection lifetime thực tế.
8. Tối ưu allocations/streaming nếu evidence chỉ ra bottleneck khác.
9. Test failure paths.
10. Instrument resource lifetime và dependency duration.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `using` bảo đảm `Dispose()` được gọi khi scope kết thúc, kể cả khi exception đi qua scope, theo semantics tương đương `try/finally`.
- `await using` gọi asynchronous disposal pattern (`DisposeAsync`) và await completion của cleanup.
- `IAsyncDisposable` hữu ích khi cleanup bản thân có asynchronous I/O hoặc cần chờ asynchronous completion; nó không mặc định “nhanh hơn”.
- GC reclaim managed memory nhưng không cung cấp deterministic release timing cho scarce external resources như database connections, sockets hoặc file handles.
- Finalizer, nếu có, chỉ là safety net của một số types và không thay thế deterministic disposal; timing không nên được dùng làm business/resource-management mechanism.
- Khi resource implement cả sync và async disposal, lựa chọn phải dựa trên resource contract, execution context, cost của cleanup và guidance của type/provider chứ không phải rule “async everywhere”.
- `leaveOpen: true` thể hiện ownership boundary: disposing `GZipStream` không được đóng `output`, nhưng vẫn cần dispose/finalize compression state đúng lúc.
- Slow downstream write có thể giữ `SqlDataReader` và `SqlConnection` sống lâu; connection-pool pressure không nhất thiết do quên dispose.

### Điểm cộng

- Disposal order của local resources theo scope cần bảo đảm dependent resource được dispose trước resource mà nó dựa vào, ví dụ reader trước connection.
- Nếu compression stream cần ghi footer/trailer khi dispose, không dispose đúng sẽ tạo output không hoàn chỉnh dù tất cả `WriteAsync` đã thành công.
- Cancellation nên propagate vào reads/writes, nhưng cleanup vẫn phải xảy ra; business cần policy cho partial artifact.
- Có thể giảm thời gian giữ DB connection bằng cách tách extraction khỏi slow destination nếu dữ liệu/scale cho phép, nhưng trade-off là buffer/storage trung gian.
- Có thể dùng streaming encoding hoặc reusable buffer để tránh allocation per-row nếu profiling chứng minh allocation là bottleneck.

### Senior+

- Nhận ra deterministic disposal giải quyết **when cleanup begins**, nhưng không tự giải quyết end-to-end resource occupancy nếu critical path giữ resource trong suốt slow downstream I/O.
- Không dispose object do caller sở hữu trừ khi contract nói rõ ownership transfer.
- Khi một component có cả sync và async cleanup, API design nên giữ ownership explicit và tránh sync-over-async để không tạo blocking không cần thiết.
- Đánh giá connection pool bằng thời gian giữ connection, query duration, downstream latency và concurrency thay vì chỉ nhìn số object đã dispose.

## Hướng giải quyết tham khảo

GC và disposal giải hai bài toán khác nhau.

GC quản lý lifetime của managed objects. Khi một object không còn reachable, memory của object có thể được thu hồi vào một thời điểm do GC quyết định. Nhưng một `SqlConnection`, stream hoặc socket thường đại diện cho một resource ngoài managed heap. Application không nên chờ GC để release resource đó, vì thời điểm collection không deterministic và resource có thể khan hiếm hơn memory.

`using` tương đương về ý tưởng với:

```csharp
var resource = CreateResource();
try
{
    Use(resource);
}
finally
{
    resource?.Dispose();
}
```

`await using` dùng async-dispose pattern:

```csharp
var resource = CreateAsyncDisposableResource();
try
{
    await UseAsync(resource);
}
finally
{
    if (resource is not null)
    {
        await resource.DisposeAsync();
    }
}
```

Điểm quan trọng là `DisposeAsync()` có thể trả `ValueTask`, cho phép resource thực hiện asynchronous cleanup mà không cần blocking thread trong trường hợp cleanup cần I/O.

Tôi không đổi mọi `using` thành `await using`. Tôi kiểm tra type contract. Nếu type chỉ có `IDisposable`, dùng `using`. Nếu type có `IAsyncDisposable` và provider documentation khuyến nghị async disposal trong asynchronous flow, `await using` thường hợp lý. Nếu một type hỗ trợ cả hai, tôi xem cleanup có thể block hay flush I/O không và giữ API consistent với flow hiện tại.

Với code ví dụ, ownership quan trọng nhất là:

```csharp
using var gzip = new GZipStream(
    output,
    CompressionLevel.Fastest,
    leaveOpen: true);
```

`gzip` do method sở hữu và phải dispose để hoàn tất compression stream. `output` do caller sở hữu nên `leaveOpen: true` hợp lý nếu contract thực sự như vậy.

Nếu `ReadAsync` hoặc `WriteAsync` ném exception/cancellation, các `using`/`await using` scopes vẫn phải cleanup khi unwind. Tuy nhiên business artifact có thể đã bị ghi một phần. Vì vậy cần policy riêng, ví dụ:

```text
start upload
  -> stream report
  -> if success: commit/mark ready
  -> if failure/cancel: abort/delete partial blob or mark incomplete
```

Connection-pool pressure cần đo thay vì suy luận từ code. Timeline có thể là:

```text
Open SQL connection
  -> ExecuteReader
  -> Read row
  -> await slow Blob/network write
  -> Read next row
  -> ...
  -> Dispose reader/connection
```

Nếu Blob/network write chậm, connection bị giữ trong toàn bộ duration. Disposal vẫn chính xác nhưng resource occupancy cao.

Evidence nên gồm:

- SQL dependency duration;
- total request duration;
- time from connection open đến dispose;
- rows processed;
- output write duration;
- cancellation rate;
- connection-pool wait/errors;
- allocations/GC nếu payload conversion lớn.

Nếu đo thấy database query nhanh nhưng destination chậm, có thể cân nhắc architecture khác, ví dụ ghi vào temporary storage/buffer có giới hạn rồi release connection sớm. Nhưng không nên buffer toàn bộ report lớn vào memory chỉ để giảm connection lifetime.

Testing quan trọng:

1. successful report tạo gzip hợp lệ;
2. cancellation giữa chừng vẫn release reader/connection;
3. output write failure vẫn cleanup upstream resources;
4. caller-owned output vẫn mở sau khi method kết thúc nếu contract yêu cầu;
5. repeated concurrent reports không làm pool exhaustion ngoài expected concurrency.

Tài liệu tham khảo:

- Microsoft Learn — Implement a DisposeAsync method: `https://learn.microsoft.com/dotnet/standard/garbage-collection/implementing-disposeasync`
- Microsoft Learn — Using objects that implement IDisposable: `https://learn.microsoft.com/dotnet/standard/garbage-collection/using-objects`

## Mẫu trả lời trong phỏng vấn

“Em tách managed memory khỏi external resource. GC quyết định khi nào reclaim object memory, nhưng connection, socket hay file handle cần deterministic cleanup nên em dùng `using` hoặc `await using` theo contract của resource.

`using` gọi `Dispose`, còn `await using` await `DisposeAsync`. Async disposal không mặc định nhanh hơn; nó hữu ích khi cleanup có asynchronous work và tránh blocking không cần thiết. Nếu type support cả hai, em dựa vào provider guidance và cleanup semantics, không đổi tất cả sang async theo phong trào.

Trong flow này em chú ý ownership: method dispose `GZipStream` nhưng không đóng caller-owned `output` vì `leaveOpen=true`. Em cũng verify cancellation/failure vẫn dispose reader và connection. Nếu pool pressure tăng, em không kết luận quên dispose ngay: stream sang Blob chậm có thể giữ SQL connection suốt report. Em đo connection lifetime, SQL duration và output-write duration rồi mới quyết định có cần thay pipeline hay không.”

## Câu hỏi đào sâu

1. Nếu một type implement cả `IDisposable` và `IAsyncDisposable`, bạn có luôn chọn `DisposeAsync` trong ASP.NET Core không? Khi nào sync disposal vẫn hợp lý?
2. Nếu connection được dispose đúng nhưng pool vẫn thường xuyên exhausted, bạn sẽ thu evidence nào để chứng minh resource occupancy nằm ở đâu?
3. Một teammate đề xuất load toàn bộ report vào `MemoryStream`, đóng SQL connection sớm rồi upload sau. Khi nào giải pháp này tốt, và khi nào nó chuyển bottleneck sang memory/GC?

## Lỗi trả lời thường gặp

- Nói GC sẽ sớm tự đóng database connection nên dispose không quan trọng.
- Cho rằng `await using` luôn nhanh hơn `using`.
- Không phân biệt ownership của wrapper stream và underlying stream.
- Chỉ nhìn cleanup ở cuối method mà bỏ qua thời gian resource bị giữ trong cả pipeline.
- Không test cancellation/failure path và partial output.

## Thang điểm 0–10

- **0–2:** chỉ biết “using để giải phóng memory”.
- **3–4:** biết `Dispose`/`DisposeAsync` nhưng chưa phân biệt GC và external resource lifetime.
- **5–6:** giải thích đúng deterministic disposal, `await using`, ownership và exception cleanup.
- **7–8:** reasoning được connection lifetime trong streaming pipeline, cancellation và measurement.
- **9–10:** cân bằng sync/async cleanup theo resource contract, phân tích resource occupancy end-to-end và đưa redesign dựa trên evidence thay vì pattern máy móc.

# Câu 2 — Azure Service Bus xử lý một message hai lần sau khi scale-out: bug ở lock, retry, settlement hay business idempotency?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, .NET, competing consumers, PeekLock, message settlement, lock renewal, retries, duplicate delivery, idempotency, DLQ, SQL Server, Application Insights, distributed systems, incident response

## Bối cảnh

Một order-integration service nhận message từ Azure Service Bus queue. Mỗi message yêu cầu:

1. cập nhật trạng thái order trong SQL Server;
2. gọi external fulfillment API;
3. lưu fulfillment reference;
4. complete message.

Service chạy trên Azure App Service và vừa scale từ 2 lên 8 instances trong giờ cao điểm.

Sau scale-out, business phát hiện một số order được fulfillment hai lần. Telemetry cho thấy:

- queue depth tăng trước incident rồi giảm nhanh sau scale;
- một số message có `DeliveryCount > 1`;
- có `MessageLockLost`/settlement-related exceptions rải rác;
- external fulfillment API latency p95 tăng mạnh trong cùng thời gian;
- SQL update thường thành công trước khi external API call hoàn tất;
- receiver bật prefetch và concurrent processing tương đối cao;
- code có retry cho external API;
- sender đặt business order ID trong payload nhưng `MessageId` không được chuẩn hóa nhất quán;
- consumer chưa có inbox/idempotency table;
- team giả định “Service Bus queue chỉ giao mỗi message đúng một lần”;
- một developer đề xuất tăng lock duration thật lớn;
- một developer khác muốn complete message ngay khi nhận để tránh duplicate.

Không giả định root cause duy nhất là lock expiration; network detach, receiver restart, settlement ambiguity, retry behavior và non-idempotent external side effect đều phải được xem xét.

## Câu hỏi chính

Bạn đang xử lý production incident này. Hãy trình bày cách đánh giá business impact và stabilize hệ thống trước, cách thu evidence để phân biệt lock expiration, settlement failure, retry amplification, receiver restart hoặc duplicate send, và vì sao duplicate processing vẫn có thể xảy ra với PeekLock. Sau đó thiết kế consumer an toàn hơn khi workflow vừa có SQL transaction vừa có external side effect không nằm trong cùng transaction.

## Câu hỏi làm rõ nên cân nhắc

1. External fulfillment API có hỗ trợ idempotency key hoặc query-by-order-id để phát hiện operation đã thành công hay không?
2. Message processing duration p95/p99 là bao nhiêu so với effective lock/auto-renew window và prefetch behavior?
3. Duplicate fulfillment có cùng `MessageId`, cùng business order ID hay thực sự là hai messages khác nhau từ sender?
4. SQL state hiện được commit trước hay sau external call, và state model có biểu diễn `Processing`, `Succeeded`, `Unknown` không?
5. Receiver restart/deployment/network errors có correlate với timestamps của duplicate delivery không?

## Gợi ý tư duy

### Gợi ý 1

Với PeekLock, hãy nghĩ theo **at-least-once processing possibility**, không theo “exactly once end-to-end”.

### Gợi ý 2

Một failure sau khi external side effect thành công nhưng trước khi message được settled có thể tạo tình huống ambiguous: consumer không biết lần trước đã hoàn thành đến đâu.

### Gợi ý 3

Lock renewal giảm một failure mode nhưng không biến non-idempotent business operation thành exactly-once operation.

## Cấu trúc trả lời đề xuất

1. Xác định số order bị ảnh hưởng và hậu quả business.
2. Stabilize concurrency/traffic mà không làm mất message.
3. Correlate `MessageId`, business key, delivery count, instance và external reference.
4. Xác định processing timeline trên từng duplicate.
5. So sánh hypotheses: lock lost, settlement failed, restart, duplicate send, retry side effect.
6. Xác định transaction boundary và ambiguous outcomes.
7. Thiết kế idempotent consumer/inbox + external idempotency.
8. Thiết kế retry/DLQ/lock handling.
9. Test concurrency/failure injection.
10. Monitor duplicate-attempt và business duplicate metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- PeekLock giữ message trong trạng thái locked cho receiver cho tới khi settle hoặc lock bị mất/hết hạn; nếu message không được complete thành công, nó có thể được redeliver.
- Duplicate delivery là behavior phải được thiết kế chịu đựng; Service Bus không tự cung cấp exactly-once business side effects qua SQL + external API.
- `Complete` có thể fail hoặc không đến service do network/lock conditions; nếu business work đã xảy ra trước đó, redelivery có thể xử lý lại cùng work.
- Tăng lock duration hoặc auto-renew có thể giảm lock-expiry risk cho legitimate long processing nhưng không giải quyết settlement ambiguity, restarts hoặc duplicate sends.
- Complete message ngay khi nhận chuyển failure mode từ duplicate sang message loss/business work chưa hoàn tất; không phù hợp nếu work phải được bảo đảm.
- Consumer cần idempotency dựa trên stable message/business identity.
- External side effect cần idempotency mechanism riêng nếu có thể, vì SQL transaction không bao phủ external API.
- Prefetch/concurrency phải phù hợp processing capacity; prefetch quá cao có thể làm message bị lock trong client trước khi thực sự được xử lý kịp.

### Điểm cộng

- Có inbox table với unique constraint trên business operation/message key để atomically record processing state cùng local SQL changes khi phù hợp.
- External API idempotency key nên ổn định theo business operation, không generate UUID mới ở mỗi retry.
- Nếu external API timeout sau khi request đã được gửi, outcome có thể là unknown; retry mù có thể duplicate side effect.
- Có state machine `Pending → Processing → Succeeded / Failed / Unknown` và reconciliation flow cho ambiguous outcomes.
- Bounded retry + backoff/jitter; non-transient hoặc poison messages được dead-letter có reason/diagnostic context.

### Senior+

- Phân biệt **message deduplication** ở broker với **business idempotency** ở consumer. Sender-side duplicate detection không thay thế idempotent receive processing.
- Dùng transactional outbox/inbox cho local state transitions nhưng không giả vờ distributed transaction với external fulfillment API nếu provider không hỗ trợ.
- Nếu provider hỗ trợ query/status lookup bằng idempotency/business key, reconciliation sau timeout có thể xác định request đã thành công trước khi retry.
- Điều chỉnh concurrency dựa trên end-to-end service time, lock behavior và dependency capacity; scale consumer vượt capacity của downstream có thể làm incident nặng hơn.
- Thiết kế incident telemetry đủ để reconstruct một message lifecycle qua multiple deliveries/instances.

## Hướng giải quyết tham khảo

Đầu tiên tôi sẽ bảo vệ business khỏi tạo thêm duplicate fulfillment. Nếu evidence cho thấy concurrency tăng làm downstream latency tăng mạnh, có thể tạm giảm consumer concurrency hoặc số active instances về mức downstream chịu được. Tôi không chuyển sang `ReceiveAndDelete` hay complete message ngay khi nhận vì điều đó có thể làm mất work nếu process chết sau settlement.

Tôi xây timeline theo business order ID và message identity:

```text
order_id
message_id
service_bus_sequence_number
DeliveryCount
instance_id
receive_timestamp
lock_lost_timestamp
sql_state_before/after
external_request_id
external_response_status
complete_attempt/result
```

Một failure pattern khả thi:

```text
T0 receive message M, DeliveryCount=1
T1 SQL marks order processing
T2 call fulfillment API
T3 provider creates fulfillment successfully
T4 network timeout / lock lost / settlement fails
T5 message becomes available again
T6 another instance receives M, DeliveryCount=2
T7 consumer calls fulfillment API again
T8 duplicate fulfillment created
```

Ở đây Service Bus chỉ biết message chưa được settled thành công. Nó không biết external fulfillment đã tạo side effect.

Theo Microsoft Learn, PeekLock yêu cầu explicit settlement và message có thể được redeliver khi lock expires hoặc settlement không thể hoàn tất. Vì vậy consumer phải assume possible duplicate processing.

Thiết kế cải thiện gồm hai lớp idempotency.

### 1. Local inbox/business operation guard

Ví dụ table:

```sql
CREATE TABLE ProcessedFulfillmentMessages
(
    OperationKey nvarchar(100) NOT NULL PRIMARY KEY,
    OrderId uniqueidentifier NOT NULL,
    Status nvarchar(30) NOT NULL,
    ExternalReference nvarchar(200) NULL,
    UpdatedAt datetime2 NOT NULL
);
```

`OperationKey` phải stable, ví dụ `fulfill:{orderId}:{fulfillmentVersion}` nếu business operation có version. Unique constraint chặn hai consumers tạo cùng local operation record đồng thời.

Pseudo-flow:

```text
receive
  -> load/create idempotency record
  -> if Succeeded: complete message
  -> if Processing/Unknown: reconcile according to policy
  -> otherwise attempt external operation with stable idempotency key
  -> persist result
  -> complete message
```

### 2. External idempotency

Nếu fulfillment API hỗ trợ idempotency key:

```http
Idempotency-Key: fulfill-<order-id>-<version>
```

Mọi retry phải reuse cùng key. Nếu provider không hỗ trợ idempotency key nhưng cho query theo client reference/order ID, dùng client-generated stable reference và check status trước retry.

Nếu provider không hỗ trợ cả idempotency lẫn lookup, exactly-once external effect không thể được đảm bảo đơn giản. Business cần reconciliation/compensation strategy.

Lock handling vẫn quan trọng. Processing phải hoàn tất trong lock/renewal semantics phù hợp. Tôi kiểm tra:

- processing duration p95/p99;
- configured lock duration;
- automatic lock renewal window;
- prefetch count;
- max concurrent calls;
- downstream p95/p99;
- instance restarts/network detach.

Nếu prefetch 500 nhưng một instance chỉ xử lý được 20 messages đồng thời và mỗi message mất lâu, nhiều messages có thể ngồi trong client-side prefetch buffer trong khi lock time đang trôi. Vì vậy prefetch phải được right-size theo actual throughput.

Retry external API cũng phải hiểu ambiguity. Timeout không chứng minh request failed. Với operation non-idempotent:

```text
timeout
  -> query provider by stable key/reference
  -> if succeeded: persist success, do not resend
  -> if definitely absent: retry bounded
  -> if unknown: route to reconciliation/manual path
```

DLQ dùng cho poison/non-recoverable cases, không phải nơi bỏ tất cả transient failures. Mỗi dead-letter cần reason và diagnostic metadata đủ để xử lý.

Testing nên gồm:

1. consumer crash sau external success nhưng trước `Complete`;
2. lock lost trước settlement;
3. two instances nhận redelivery gần nhau;
4. external API timeout nhưng operation thực tế succeeded;
5. duplicate message send với cùng business operation key;
6. downstream slowdown + high prefetch/load.

Production metrics:

- delivery count distribution;
- lock-lost rate;
- complete/abandon/dead-letter counts;
- duplicate-attempts blocked by inbox;
- external idempotency replays;
- queue depth/age;
- processing p95/p99;
- fulfillment duplicate business KPI;
- DLQ depth and oldest age.

Tài liệu tham khảo:

- Microsoft Learn — Message transfers, locks, and settlement: `https://learn.microsoft.com/azure/service-bus-messaging/message-transfers-locks-settlement`
- Microsoft Learn — Prevent message loss and duplicate processing in Azure Service Bus: `https://learn.microsoft.com/azure/service-bus-messaging/service-bus-message-loss-and-duplicates`

## Mẫu trả lời trong phỏng vấn

“Em không coi Service Bus là exactly-once end-to-end. Với PeekLock, message chỉ bị remove sau settlement. Nếu processing thành công nhưng lock mất hoặc Complete không tới broker, message có thể được giao lại.

Trong incident này em giảm blast radius trước, có thể hạ consumer concurrency nếu scale-out đang làm fulfillment API chậm hơn. Sau đó em correlate `MessageId`, business order ID, DeliveryCount, instance, external request/reference và complete result để reconstruct timeline.

Fix chính không phải tăng lock duration thật lớn. Em thiết kế idempotency ở business level: một stable operation key có unique constraint/inbox record ở SQL, và nếu external API hỗ trợ thì gửi cùng idempotency key cho mọi retry. Nếu timeout sau external call, em coi outcome là unknown và query/reconcile trước khi resend.

Lock renewal, prefetch và concurrency vẫn phải tune theo processing p99, nhưng chúng chỉ giảm duplicate probability chứ không thay business idempotency. Em test crash sau external success trước Complete, lock loss và duplicate delivery trên nhiều instances.”

## Câu hỏi đào sâu

1. Nếu external provider không hỗ trợ idempotency key nhưng có API tra cứu fulfillment theo client reference, bạn thiết kế timeout/retry/reconciliation thế nào?
2. Nếu inbox table chặn duplicate local processing nhưng external API đã được gọi trước khi insert inbox record, race nào vẫn còn và bạn sửa flow ra sao?
3. Một teammate đề xuất bật broker duplicate detection rồi bỏ idempotency ở consumer. Bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Giả định queue bảo đảm exactly-once business processing.
- Complete message trước khi business work hoàn tất chỉ để tránh duplicate.
- Chỉ tăng message lock duration mà không thiết kế idempotency.
- Retry external API mù sau timeout dù outcome có thể đã thành công.
- Không correlate business key với `MessageId`, `DeliveryCount` và instance khi điều tra.

## Thang điểm 0–10

- **0–2:** chỉ nói tăng lock hoặc retry.
- **3–4:** biết PeekLock có redelivery nhưng chưa giải quyết external side effect.
- **5–6:** có idempotent consumer, stable identity, bounded retry và incident evidence.
- **7–8:** xử lý settlement ambiguity, prefetch/concurrency, external idempotency và reconciliation.
- **9–10:** reasoning rõ local transaction vs external side effect, duplicate detection vs business idempotency, ambiguous outcome và thiết kế end-to-end resilience dựa trên measurable capacity.

# Câu 3 — SQL search đang đủ dùng hay đã đến lúc cần Elasticsearch? Thiết kế search platform mà không biến index thành “database thứ hai” khó kiểm soát

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server/PostgreSQL, search architecture, inverted index, analyzers, text vs keyword, eventual consistency, outbox pattern, indexing pipeline, reindexing, aliases, REST API design, observability, failure recovery, architecture trade-offs

## Bối cảnh

Một e-commerce platform có khoảng vài triệu products. Product source of truth hiện nằm trong relational database. Search API hiện dùng SQL với nhiều điều kiện:

- free-text search theo product name/description;
- exact filter theo brand/category/status;
- price range;
- sorting;
- pagination;
- autocomplete;
- một số market/language khác nhau.

Hiện tại traffic trung bình chưa quá lớn, nhưng campaign tạo burst đáng kể. Business phản ánh:

- free-text relevance chưa tốt;
- autocomplete khó mở rộng;
- một số query SQL có nhiều `LIKE '%term%'` và trở nên chậm;
- filters exact-match vẫn chạy ổn;
- product updates phải xuất hiện trong search trong vài phút, không nhất thiết ngay lập tức;
- checkout/product detail vẫn phải đọc authoritative data từ relational DB;
- team đã có Elasticsearch/Kibana experience nhưng không muốn thêm distributed infrastructure nếu chưa cần;
- product schema thay đổi thường xuyên;
- search result cần chịu được index rebuild;
- nếu search cluster lỗi, website vẫn nên có degradation path cho một số flows;
- chưa có quyết định về CDC, Outbox, polling hay synchronous dual-write;
- một architect đề xuất “ghi DB và Elasticsearch trong cùng request, nếu một bên fail thì rollback cả hai”.

## Câu hỏi chính

Hãy quyết định khi nào relational search hiện tại vẫn đủ và khi nào Elasticsearch được justify. Nếu chọn Elasticsearch, hãy thiết kế end-to-end search architecture: source of truth, index document model, mapping/analyzers, update pipeline, consistency, API, pagination, reindex/schema migration, zero/low-downtime index switch, failure degradation, security, observability và deployment. Giải thích rõ vì sao synchronous dual-write không tạo một transaction atomic giữa SQL và Elasticsearch, và đưa ra recommendation có điều kiện dựa trên requirements/scale thay vì mặc định thêm Elasticsearch.

## Câu hỏi làm rõ nên cân nhắc

1. Search SLO, traffic p95/p99, peak QPS và current SQL execution-plan/bottleneck thực tế là gì?
2. Relevance yêu cầu tới mức nào: stemming, synonyms, typo tolerance, multi-language analyzers hay chỉ substring/prefix search đơn giản?
3. Business chấp nhận độ trễ indexing bao lâu và hành vi gì khi product vừa update nhưng search chưa phản ánh?
4. Result pages cần deep pagination tới đâu, hay UX chủ yếu browse vài trang đầu?
5. Khi Elasticsearch unavailable, requirement là fail search hoàn toàn, fallback limited SQL search hay serve cached popular results?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn search engine chỉ vì query SQL xấu. Trước tiên phân biệt **relational filtering** với **information retrieval/relevance**.

### Gợi ý 2

Nếu Elasticsearch là projection của source-of-truth database, câu hỏi trung tâm là cách giữ projection đủ đồng bộ và recover/rebuild được.

### Gợi ý 3

Reindex không chỉ là copy data. Mapping/analyzer changes có thể yêu cầu index mới, backfill, verification và controlled cutover.

## Cấu trúc trả lời đề xuất

1. Chốt search capabilities và SLO.
2. Measure current SQL behavior.
3. So sánh SQL optimization/full-text options với Elasticsearch.
4. Xác định source of truth và ownership boundary.
5. Thiết kế search document/mapping/analyzers.
6. Thiết kế change propagation và consistency model.
7. Thiết kế read/search API và pagination.
8. Thiết kế reindex + alias cutover + rollback.
9. Thiết kế failure/degradation + security.
10. Test/load/observe và nêu điều kiện recommendation thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Elasticsearch không nên mặc định trở thành authoritative product database nếu relational DB đang là system of record cho transactional product state.
- Elasticsearch phù hợp khi requirements thực sự cần full-text relevance, analyzers, autocomplete, flexible search/filter composition hoặc scale mà relational solution không đáp ứng tốt với chi phí hợp lý.
- Nếu current requirement chủ yếu exact filter + modest text search, SQL indexes/full-text capability hoặc query redesign có thể đơn giản và đủ tốt.
- Synchronous dual-write SQL + Elasticsearch không tạo distributed atomic transaction; request có thể commit một bên và fail bên kia.
- Search index nên được coi là rebuildable projection từ authoritative data/event history.
- Update pipeline cần idempotency/retry và cơ chế phát hiện/recover drift.
- Mapping phân biệt text fields cần analysis với exact-match/filter fields thường dùng keyword-like semantics.
- Schema/analyzer change lớn thường nên tạo index version mới, reindex/backfill, verify rồi switch alias thay vì mutate production index tùy tiện.
- Eventual consistency phải được explicit trong product behavior và SLO.

### Điểm cộng

- Dùng Outbox Pattern để atomically commit domain change + integration event trong relational transaction, sau đó asynchronous indexer publish/update Elasticsearch.
- Document model denormalize theo search/read use case, nhưng không copy mọi relational table một cách máy móc.
- Indexer dùng stable product ID làm document ID để upsert idempotently.
- Có periodic reconciliation so sánh source version/update timestamp/count/hash để phát hiện missed events.
- Với deep pagination, tránh offset cực lớn nếu search engine/query pattern không phù hợp; cân nhắc cursor/search-after style theo product requirement.

### Senior+

- Thiết kế versioning để out-of-order events không overwrite document mới bằng state cũ, ví dụ source version/updated sequence check.
- Alias switch cho phép application dùng logical index name và cutover giữa versioned indices với downtime thấp; rollback có thể đổi alias lại nếu old index còn valid.
- Reindex pipeline phải handle writes diễn ra trong lúc backfill: snapshot + catch-up hoặc dual-publish có versioning, không giả định dữ liệu đứng yên.
- Search failure degradation nên theo business priority: category browse/known-item lookup có thể fallback khác free-text search.
- Chọn Elasticsearch còn phải tính operational cost: cluster sizing, shard/index lifecycle, mapping governance, monitoring, upgrade, incident ownership.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng việc xác định Elasticsearch có thực sự giải đúng vấn đề hay không.

Nếu current workload chủ yếu là:

```text
brand = X
category = Y
status = Active
price between A and B
sort by price
```

relational database với đúng indexes/query design thường rất mạnh. Việc có vài query `LIKE '%term%'` chậm không tự động nghĩa phải thêm Elasticsearch; có thể đánh giá full-text search của database hoặc thay UX/query semantics trước.

Elasticsearch trở nên hợp lý hơn khi business cần:

- relevance scoring;
- tokenization/analyzers;
- language-specific text processing;
- autocomplete;
- flexible full-text + filters;
- search-centric query volume lớn.

Nếu chọn Elasticsearch, relational DB vẫn là source of truth:

```text
Product Command/API
      |
      v
Relational DB  <-- authoritative
      |
   Outbox
      |
      v
Indexer Worker
      |
      v
Elasticsearch
      |
      v
Search API
```

### Tại sao không synchronous dual-write

Flow sau không atomic:

```text
BEGIN SQL TX
UPDATE Product
CALL Elasticsearch
COMMIT SQL
```

Nếu Elasticsearch update thành công nhưng SQL commit fail, index đi trước DB. Nếu SQL commit thành công rồi Elasticsearch call timeout/fail, index bị stale. Không có local transaction đơn giản bao trùm cả hai systems.

Outbox giải quyết local atomicity:

```sql
BEGIN TRANSACTION;

UPDATE Products
SET Name = @Name,
    UpdatedAt = SYSUTCDATETIME(),
    Version = Version + 1
WHERE Id = @Id;

INSERT INTO OutboxEvents(...);

COMMIT;
```

Indexer đọc outbox/event và upsert search document bằng product ID. Nếu process crash, event retry. Upsert phải idempotent.

### Search document model

Không mirror schema relational từng bảng. Tạo document theo read/search use case:

```json
{
  "id": "P123",
  "name": "Running Shoe Pro",
  "description": "...",
  "brandId": "B9",
  "brandName": "Contoso",
  "categoryIds": ["C1", "C7"],
  "market": "vi-VN",
  "status": "active",
  "price": 1299000,
  "sourceVersion": 481
}
```

Conceptually:

- `name`, `description`: analyzed text;
- IDs/status/market: exact filter fields;
- autocomplete có mapping/analyzer riêng theo UX requirement;
- price là numeric field cho range/sort.

Analyzer phải phù hợp language/behavior. Không chọn stemming/synonym strategy trước khi có relevance tests.

### Eventual consistency

Business nói search update trong vài phút, nên async projection phù hợp. Search response có thể stale ngắn hạn; product detail/checkout luôn re-read authoritative product state trước operation quan trọng.

Ví dụ user tìm thấy product vừa bị disable nhưng index chưa catch up. Product detail/checkout phải validate state từ authoritative service/database và từ chối nếu đã inactive.

### Out-of-order events

Giả sử events arrive:

```text
v10 update price
v11 disable product
```

nhưng indexer xử lý v11 trước rồi v10 sau. Nếu upsert mù, v10 có thể “hồi sinh” stale state. Document cần source version và indexer bỏ event cũ hơn current version, hoặc architecture bảo đảm ordering theo key.

### Reindex và schema change

Dùng versioned index:

```text
products-v17
products-v18
```

Application query logical alias:

```text
products-current
```

Reindex flow:

1. create `products-v18` với mapping/analyzers mới;
2. backfill từ source of truth;
3. trong lúc backfill, capture/catch up changes;
4. verify document counts/sample queries/relevance/business invariants;
5. atomically switch alias `products-current` sang v18 bằng aliases API;
6. monitor;
7. giữ v17 trong rollback window nếu storage/cost cho phép;
8. delete old index sau khi confidence đủ.

Elastic documentation nêu aliases có thể dùng để thay đổi index mà application sử dụng và hỗ trợ reindexing without downtime ở mức logical routing/cutover.

### Failure degradation

Nếu Elasticsearch unavailable:

- search endpoint có thể trả degraded error rõ ràng hoặc cached popular results;
- known-product/detail route vẫn đọc relational system;
- limited category browse có thể fallback SQL nếu load/UX cho phép;
- không gửi mọi search traffic sang fallback DB nếu điều đó sẽ đánh sập transactional database.

Fallback phải được capacity-tested.

### API

Ví dụ:

```http
GET /api/search/products?q=shoe&brand=B9&market=vi-VN&cursor=...
```

Response nên tách search metadata khỏi authoritative transactional state. Nếu price cực kỳ freshness-sensitive, có thể query search IDs trước rồi hydrate authoritative price cho top N, nhưng trade-off là latency và fan-out. Không làm nếu requirement không cần.

### Observability

Tôi theo dõi:

- search p50/p95/p99;
- error rate;
- indexing lag;
- outbox backlog/oldest event;
- failed indexing/retry count;
- index document count vs source count;
- query slow logs/profile samples;
- zero-result rate;
- relevance evaluation set;
- alias/index version;
- cluster health/capacity;
- fallback activation count.

Tài liệu tham khảo:

- Elastic Docs — Aliases: `https://www.elastic.co/docs/manage-data/data-store/aliases`
- Elastic Docs — Reindex API: `https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-reindex`

## Mẫu trả lời trong phỏng vấn

“Em không thêm Elasticsearch chỉ vì có vài query LIKE chậm. Em chốt trước search requirement: relevance, analyzers, autocomplete, peak QPS và SLO. Nếu exact filtering vẫn là phần lớn use case và SQL tối ưu đáp ứng được, solution đơn giản có thể tốt hơn.

Nếu requirements thật sự là search-centric, em giữ relational DB làm source of truth và coi Elasticsearch là rebuildable projection. Em không synchronous dual-write rồi gọi đó là atomic, vì SQL và Elasticsearch có thể commit/fail độc lập. Em dùng Outbox để commit product change + event cùng transaction, rồi indexer upsert idempotently theo product ID/version.

Mapping tách analyzed text khỏi exact filter fields. Schema/analyzer change lớn tạo index version mới, backfill + catch-up updates, verify rồi switch alias. Product detail/checkout vẫn validate authoritative state vì search có eventual consistency.

Em cũng thiết kế failure degradation có capacity control; không tự động đổ toàn bộ search traffic về primary SQL. Monitoring phải có indexing lag, outbox backlog, search p95/error, alias version và drift reconciliation.”

## Câu hỏi đào sâu

1. Nếu backfill `products-v18` mất 6 giờ trong khi product updates vẫn diễn ra liên tục, bạn làm thế nào để cutover mà không mất changes phát sinh trong 6 giờ đó?
2. Nếu Elasticsearch down và Product đề xuất fallback toàn bộ free-text search sang primary SQL Server, bạn cần capacity/evidence gì trước khi đồng ý?
3. Một architect muốn cho checkout đọc trực tiếp price từ Elasticsearch để giảm load database. Khi nào có thể chấp nhận, và consistency/risk controls nào bắt buộc?

## Lỗi trả lời thường gặp

- Chọn Elasticsearch chỉ vì “search engine nhanh hơn SQL”.
- Synchronous dual-write rồi cho rằng rollback SQL sẽ rollback luôn Elasticsearch.
- Coi search index là source of truth mà không có rebuild/reconciliation strategy.
- Reindex trực tiếp production index mà không có version/cutover/rollback plan.
- Không định nghĩa eventual consistency hoặc behavior khi search result stale.

## Thang điểm 0–10

- **0–2:** chỉ nói dùng Elasticsearch vì full-text nhanh.
- **3–4:** biết index/search basics nhưng chưa giải quyết consistency/update pipeline.
- **5–6:** có source-of-truth boundary, async indexing, mapping và failure handling cơ bản.
- **7–8:** có Outbox, idempotency/versioning, reindex + alias cutover, reconciliation và observability.
- **9–10:** cân bằng SQL vs Elasticsearch theo measured requirement, xử lý concurrent reindex updates, out-of-order events, fallback capacity và operational complexity như một architecture decision thực sự.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `using`/`await using` là deterministic resource-lifetime mechanisms; GC quản lý managed memory và không thay thế cleanup đúng thời điểm cho database/network/file resources.
- `await using` không mặc định tốt hơn `using`; lựa chọn phụ thuộc resource contract và cleanup semantics.
- Azure Service Bus PeekLock phải được thiết kế với khả năng redelivery. Lock renewal giảm một số failure modes nhưng business idempotency mới bảo vệ side effects khỏi duplicate processing.
- External API timeout có thể tạo ambiguous outcome; retry phải đi cùng stable idempotency key hoặc reconciliation strategy.
- Elasticsearch nên là search projection khi relational DB là source of truth; synchronous dual-write không tạo atomic cross-system transaction.
- Reindex an toàn cần versioned index, catch-up changes, verification, alias cutover và rollback window.

## Mẫu tư duy cần nhớ

- **Ownership trước cleanup:** xác định ai sở hữu resource và khi nào lifetime phải kết thúc.
- **At-least-once → idempotency:** mọi workflow message-driven phải giả định duplicate/redelivery nếu side effect quan trọng.
- **Timeout không chứng minh failure:** với external side effect, outcome có thể là unknown và cần reconciliation.
- **Projection phải rebuild được:** search/cache/read model không nên trở thành source of truth ngoài ý muốn.
- **Complexity phải được justify bằng requirement và measurement:** đừng thêm async disposal, messaging hay Elasticsearch chỉ vì pattern phổ biến.
