# Code Review Challenge 1 — Upload file qua ASP.NET Core làm tăng memory theo concurrency, cho phép overwrite blob và mở rộng blast radius của Azure Storage

**Chủ đề:** C#, .NET 8, ASP.NET Core, Azure Blob Storage, file streaming, memory, cancellation, authorization, Managed Identity, SAS, reliability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một ASP.NET Core API trên .NET 8 cho phép user upload tài liệu lên Azure Blob Storage. Mỗi file thường 5–20 MB, nhưng một số khách hàng upload file 200–500 MB. Application chạy nhiều instances trên Azure App Service.

Business yêu cầu:

- file của user này không được ghi đè hoặc đọc được file của user khác;
- upload lớn không được làm application tăng memory mất kiểm soát;
- user hủy request thì server nên dừng I/O còn có thể hủy;
- storage account không được public ngoài use case đã phê duyệt;
- tên file hiển thị cho user phải được giữ lại, nhưng object key trong storage không nhất thiết giống tên file gốc;
- API phải chịu được nhiều uploads đồng thời;
- production cần biết upload fail ở application, network hay Azure Storage;
- application đang dùng Managed Identity ở Azure và team muốn tránh giữ storage account key nếu không cần.

Production bắt đầu xuất hiện:

- p99 tăng mạnh khi có nhiều uploads lớn;
- process memory tăng nhanh và GC hoạt động dày hơn;
- hai user từng upload cùng tên `report.pdf`, sau đó một người thấy file của mình bị thay bằng nội dung khác;
- một security review phát hiện container đang cho phép anonymous blob read;
- khi browser đóng tab giữa upload, server đôi khi vẫn tiếp tục xử lý một lúc;
- team đề xuất tăng App Service memory và đổi container thành public để client tải trực tiếp cho đơn giản.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/files")]
public sealed class FilesController : ControllerBase
{
    private readonly BlobServiceClient _blobServiceClient;
    private readonly IConfiguration _configuration;

    public FilesController(
        BlobServiceClient blobServiceClient,
        IConfiguration configuration)
    {
        _blobServiceClient = blobServiceClient;
        _configuration = configuration;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(long.MaxValue)]
    public async Task<IActionResult> Upload(IFormFile file)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        var container = _blobServiceClient
            .GetBlobContainerClient("uploads");

        await container.CreateIfNotExistsAsync(
            PublicAccessType.Blob);

        var blob = container.GetBlobClient(file.FileName);

        await using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        buffer.Position = 0;

        await blob.UploadAsync(
            buffer,
            overwrite: true);

        var url = blob.Uri.ToString();

        return Ok(new
        {
            fileName = file.FileName,
            size = file.Length,
            url
        });
    }
}
```

Application registration hiện tại:

```csharp
builder.Services.AddSingleton(_ =>
{
    var connectionString = builder.Configuration[
        "Storage:ConnectionString"];

    return new BlobServiceClient(connectionString);
});
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề security, correctness, performance và reliability.
2. Giải thích memory amplification khi nhiều file lớn upload đồng thời.
3. Phân tích rủi ro của việc dùng `file.FileName` làm blob key và `overwrite: true`.
4. Đánh giá việc tạo container với `PublicAccessType.Blob` và trả raw blob URL.
5. Đề xuất cách dùng Managed Identity / Microsoft Entra ID thay vì storage account key khi phù hợp.
6. Đề xuất architecture cho upload lớn: proxy qua API hay direct-to-Blob bằng scoped SAS.
7. Giải thích cancellation, size limits, content validation và telemetry cần có.

## Câu hỏi gợi mở

1. `IFormFile` và `MemoryStream` hiện tạo bao nhiêu lớp buffering/materialization trước khi bytes tới Blob Storage?
2. Hai user cùng upload `report.pdf` sẽ tác động tới cùng object key hay hai object khác nhau?
3. Có requirement nào thực sự cần anonymous public read không?
4. Nếu application đã có Managed Identity, connection string chứa account key còn cần thiết không?
5. Với direct upload bằng SAS, SAS có nên cấp quyền ở container-level trong nhiều giờ hay chỉ ở một blob cụ thể với lifetime ngắn?

### Gợi ý 1

## Kết quả code review tham khảo

### Critical — Blob key lấy trực tiếp từ `file.FileName` và upload cho phép overwrite

**Vấn đề:** Mọi user ghi vào cùng namespace container bằng tên file do client cung cấp. Hai uploads cùng tên trỏ tới cùng blob key.

**Tại sao xảy ra:** Code đồng nhất display filename với storage object identity và không scope key theo owner/tenant hoặc generated ID.

**Ảnh hưởng production:** User có thể vô tình hoặc cố ý overwrite file của user khác nếu biết/đoán tên blob. Đây là correctness issue và có thể trở thành authorization/data-isolation issue.

**Cách sửa:** Server tạo object key không collision, ví dụ `{tenantId}/{userId}/{fileId}` hoặc generated immutable ID. Tên file gốc chỉ lưu dưới dạng metadata/database field sau khi sanitize cho display. Nếu overwrite là business feature, phải có resource-level authorization + concurrency/version semantics rõ ràng.

### Critical — Container được bật anonymous blob read không dựa trên business requirement

**Vấn đề:** `CreateIfNotExistsAsync(PublicAccessType.Blob)` cho phép anonymous read ở blob-level nếu storage account policy cho phép public access.

**Tại sao xảy ra:** Team dùng public URL như một shortcut cho download authorization.

**Ảnh hưởng production:** Bất kỳ ai có URL có thể đọc blob theo public-access semantics; URL có thể bị log, share hoặc leak ngoài ý muốn. Với private documents, đây là sai trust model.

**Cách sửa:** Container mặc định private. Download đi qua authorization layer hoặc dùng short-lived narrowly scoped SAS khi cần client truy cập trực tiếp. Nếu anonymous public assets là requirement riêng, tách container/account/policy cho public content thay vì trộn private uploads.

### High — File lớn bị copy toàn bộ vào `MemoryStream`

**Vấn đề:** `file.CopyToAsync(buffer)` materialize toàn bộ file trong managed memory trước khi upload tới Blob Storage.

**Tại sao xảy ra:** Code dùng in-memory staging để đơn giản hóa API call.

**Ảnh hưởng production:** Một file 500 MB có thể tạo large managed allocations; nhiều concurrent uploads làm peak live set tăng theo concurrency, gây GC/LOH pressure, process memory spikes và có thể OOM hoặc tăng p99 nghiêm trọng.

**Cách sửa:** Không copy toàn bộ file sang `MemoryStream`. Nếu vẫn proxy qua API, stream từ request/file stream trực tiếp vào Blob SDK với bounded server limits và cancellation. Với workload upload lớn, cân nhắc direct-to-Blob để bytes không đi xuyên application process.

### High — `[RequestSizeLimit(long.MaxValue)]` loại bỏ guardrail quan trọng

**Vấn đề:** Endpoint gần như không có server-side maximum payload size.

**Tại sao xảy ra:** Team muốn “hỗ trợ file lớn” bằng cách bỏ giới hạn thay vì định nghĩa contract rõ.

**Ảnh hưởng production:** Một request cực lớn hoặc nhiều concurrent requests có thể chiếm network, temp storage, memory và request slots trong thời gian dài; abuse có thể trở thành DoS vector.

**Cách sửa:** Đặt business maximum rõ ràng. Với direct upload, giới hạn bằng upload policy/workflow và validate size sau upload trước khi promote object thành usable. Với proxy upload, enforce request/file size ở ingress và application layer phù hợp.

### High — Cancellation không được propagate

**Vấn đề:** Action không nhận `CancellationToken`; `CopyToAsync` và `UploadAsync` không nhận `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Upload được coi là work phải hoàn tất dù client đã rời đi.

**Ảnh hưởng production:** Browser disconnect nhưng server vẫn tiếp tục đọc/copy/upload, lãng phí CPU, memory, bandwidth và storage transactions.

**Cách sửa:** Nhận `CancellationToken cancellationToken` trong action và truyền tới mọi I/O hỗ trợ cancellation. Với direct upload, browser upload trực tiếp tới storage nên API process không còn giữ large upload stream.

### High — Dùng storage account key/connection string dù workload có thể dùng Managed Identity

**Vấn đề:** Application config chứa credential có quyền rộng hơn cần thiết nếu connection string mang account key.

**Tại sao xảy ra:** Shared Key là cách cấu hình quen thuộc nhưng không tận dụng Microsoft Entra identity của workload.

**Ảnh hưởng production:** Secret leakage có thể cấp quyền storage rộng và tồn tại tới khi rotate key; rotation ảnh hưởng các workload dùng cùng key.

**Cách sửa:** Khi platform hỗ trợ, dùng `DefaultAzureCredential`/Managed Identity và cấp Azure RBAC role tối thiểu cho workload. Microsoft hiện khuyến nghị Microsoft Entra credentials khi có thể; nếu cần SAS cho client, ưu tiên user delegation SAS thay vì SAS ký bằng account key.

Tài liệu xác minh: Microsoft Learn — `https://learn.microsoft.com/azure/storage/common/storage-sas-overview` và `https://learn.microsoft.com/azure/storage/blobs/security-recommendations`.

### High — Upload authorization/resource ownership không thể hiện trong endpoint

**Vấn đề:** Snippet không cho thấy `[Authorize]`, policy hoặc owner/tenant scope.

**Tại sao xảy ra:** Storage operation đang được thiết kế như file utility thay vì business resource operation.

**Ảnh hưởng production:** Nếu application không có global authorization policy, endpoint có thể bị gọi anonymous. Nếu có global authentication nhưng không có resource scope, user vẫn có thể tác động namespace chung.

**Cách sửa:** Cần xác minh global auth trước khi kết luận endpoint hiện anonymous. Thiết kế đúng phải require authenticated principal, derive owner/tenant server-side, enforce quota/policy và không lấy owner identity từ client-supplied field.

### High — Không có content/type validation hoặc malware workflow

**Vấn đề:** Bất kỳ content nào cũng được chấp nhận; filename extension và client Content-Type không phải bằng chứng content an toàn.

**Tại sao xảy ra:** Upload được xem là byte storage thuần túy nhưng downstream có thể preview/download/process file.

**Ảnh hưởng production:** Có thể lưu executable/malicious content, polyglot files hoặc payload gây rủi ro cho preview/parser/downstream user. Nếu sau này serve inline cùng origin, risk XSS/content-sniffing còn tăng.

**Cách sửa:** Xác định allowlist theo business use case; kiểm tra signature/magic bytes khi phù hợp; scan malware theo risk model; lưu upload ở trạng thái quarantine/pending trước khi publish/serve; set safe content-disposition/content-type khi download.

### Medium — `CreateIfNotExistsAsync` nằm trong request path

**Vấn đề:** Mỗi upload đều thực hiện management-like existence call/container creation attempt.

**Tại sao xảy ra:** Infrastructure provisioning bị trộn với data-plane request flow.

**Ảnh hưởng production:** Tăng round-trip/dependency noise và làm behavior khó kiểm soát; production identity có thể cần quyền tạo container rộng hơn thực tế.

**Cách sửa:** Provision container bằng IaC/deployment. Runtime identity chỉ cần data permissions cho blob operations cần thiết.

### Medium — Raw blob URL bị coi như download authorization

**Vấn đề:** Response trả `blob.Uri` trực tiếp.

**Tại sao xảy ra:** URL identity và access authorization bị trộn.

**Ảnh hưởng production:** Với private container, URL không tự có quyền đọc; với public container lại mở quyền quá rộng. API contract trở nên phụ thuộc storage topology.

**Cách sửa:** Trả application file ID/resource URL. Khi user download, authorize rồi proxy hoặc mint short-lived read SAS cho đúng blob nếu architecture cần direct download.

### Medium — Không có upload idempotency/state model

**Vấn đề:** Request retry có thể tạo overwrite hoặc nhiều uploads tùy naming strategy; không có persisted upload state.

**Tại sao xảy ra:** File upload được xử lý như một stateless request duy nhất.

**Ảnh hưởng production:** Network timeout khiến client không biết upload đã hoàn tất chưa; retry khó phân biệt new upload với continuation/retry của cùng logical file.

**Cách sửa:** Tạo `UploadSession/FileId` trước upload. Persist state `Pending → Uploaded → Validated/Rejected`. Retry cùng operation dùng stable ID. Direct upload flow có finalize endpoint verify blob properties before marking complete.

## Phiên bản đề xuất

Với file lớn, một hướng tốt là **API cấp một upload session + blob-level user delegation SAS ngắn hạn**, browser upload trực tiếp tới Blob Storage, sau đó gọi finalize. API không đi qua payload bytes lớn.

Ví dụ rút gọn cho phần tạo upload session:

```csharp
public sealed record CreateUploadRequest(
    string FileName,
    long ExpectedSize,
    string ContentType);

public sealed record CreateUploadResponse(
    Guid FileId,
    Uri UploadUri,
    DateTimeOffset ExpiresAtUtc);

[Authorize]
[ApiController]
[Route("api/files")]
public sealed class FilesController : ControllerBase
{
    private readonly BlobServiceClient _blobService;
    private readonly IFileRepository _files;
    private readonly IUserContext _user;

    public FilesController(
        BlobServiceClient blobService,
        IFileRepository files,
        IUserContext user)
    {
        _blobService = blobService;
        _files = files;
        _user = user;
    }

    [HttpPost("upload-session")]
    public async Task<ActionResult<CreateUploadResponse>> CreateUploadSession(
        CreateUploadRequest request,
        CancellationToken cancellationToken)
    {
        const long maxFileBytes = 500L * 1024 * 1024;

        if (request.ExpectedSize <= 0 ||
            request.ExpectedSize > maxFileBytes)
        {
            return BadRequest("Invalid file size");
        }

        if (!AllowedContentTypes.Contains(request.ContentType))
        {
            return BadRequest("Unsupported content type");
        }

        var fileId = Guid.NewGuid();
        var ownerId = _user.RequireUserId();
        var blobName = $"users/{ownerId:N}/{fileId:N}";

        await _files.CreatePendingAsync(
            fileId,
            ownerId,
            request.FileName,
            request.ExpectedSize,
            request.ContentType,
            blobName,
            cancellationToken);

        var blob = _blobService
            .GetBlobContainerClient("private-uploads")
            .GetBlobClient(blobName);

        var expiresAt = DateTimeOffset.UtcNow.AddMinutes(10);

        var uploadUri = await CreateBlobWriteUserDelegationSasAsync(
            blob,
            expiresAt,
            cancellationToken);

        return Ok(new CreateUploadResponse(
            fileId,
            uploadUri,
            expiresAt));
    }
}
```

`CreateBlobWriteUserDelegationSasAsync` cần tạo **blob-scoped**, HTTPS-only, short-lived SAS với chỉ permission cần cho upload. Runtime dùng Microsoft Entra/Managed Identity có RBAC tối thiểu để request user delegation key và quản lý blob theo design.

Finalize endpoint cần:

- authorize đúng owner;
- đọc blob properties server-side;
- xác minh blob tồn tại;
- kiểm tra actual size so với expected/max size;
- kiểm tra metadata/content policy phù hợp;
- trigger malware/content validation nếu risk model yêu cầu;
- chỉ chuyển file sang trạng thái usable sau validation;
- cleanup các `Pending` upload hết hạn bằng job có giới hạn.

Nếu direct upload không phù hợp — ví dụ cần transform/inspect bytes synchronously — API vẫn có thể proxy, nhưng nên dùng bounded streaming thay vì `MemoryStream` toàn file:

```csharp
[Authorize]
[HttpPost("proxy-upload")]
[RequestSizeLimit(500L * 1024 * 1024)]
public async Task<IActionResult> ProxyUpload(
    IFormFile file,
    CancellationToken cancellationToken)
{
    if (file.Length <= 0 || file.Length > 500L * 1024 * 1024)
        return BadRequest("Invalid file size");

    var fileId = Guid.NewGuid();
    var ownerId = _user.RequireUserId();
    var blobName = $"users/{ownerId:N}/{fileId:N}";

    var blob = _blobService
        .GetBlobContainerClient("private-uploads")
        .GetBlobClient(blobName);

    await using var input = file.OpenReadStream();

    await blob.UploadAsync(
        input,
        overwrite: false,
        cancellationToken);

    return Ok(new { fileId });
}
```

Lưu ý: với multipart upload qua ASP.NET Core, cần hiểu hosting/model-binding buffering semantics của cấu hình hiện tại. Nếu mục tiêu là end-to-end streaming thực sự cho payload rất lớn, có thể cần đọc multipart stream trực tiếp thay vì dựa hoàn toàn vào `IFormFile` model binding.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách **file metadata** khỏi **blob object identity**. User giữ filename gốc để hiển thị, nhưng blob key do server sinh và scope theo owner.

Direct-to-Blob giảm application bandwidth/memory pressure và giúp App Service không trở thành data pipe cho hàng trăm MB mỗi request. Tuy nhiên direct upload không miễn validation: file chỉ được coi là hoàn tất sau finalize + server-side verification.

Managed Identity giải quyết workload-to-storage authentication. User delegation SAS chỉ được mint khi client thật sự cần direct access và phải có scope/lifetime tối thiểu. Microsoft khuyến nghị user delegation SAS khi dùng SAS vì nó dựa trên Microsoft Entra credentials thay vì account key.

Container provisioning và anonymous-public policy chuyển ra khỏi request path. Runtime identity chỉ có data-plane permissions cần thiết.

## Trade-offs

- **Direct upload:** giảm tải API đáng kể nhưng thêm upload-session/finalize state machine và cleanup cho abandoned uploads.
- **Proxy streaming:** đơn giản hơn về control/inspection nhưng application chịu toàn bộ network throughput và concurrency.
- **User delegation SAS:** an toàn hơn account-key SAS nhưng cần Microsoft Entra/RBAC setup đúng và quy trình mint/revoke rõ ràng.
- **Strict validation/scanning:** tăng latency/cost trước khi file usable; mức kiểm tra phải theo threat model và loại file.
- **Immutable generated blob keys:** loại collision/overwrite ngoài ý muốn nhưng muốn versioning/replace file sẽ cần business metadata thay vì overwrite cùng key.

## Cách kiểm thử

1. **Concurrency/load test:** 20–50 uploads lớn đồng thời; so sánh process memory, GC, p95/p99 và network giữa bản `MemoryStream`, proxy streaming và direct upload.
2. **Security test:** hai user upload cùng filename; xác minh blob keys khác nhau và user A không thể finalize/download file của user B.
3. **Cancellation test:** ngắt client giữa proxy upload; xác minh server dừng I/O sớm và không để file state ở `Completed` sai.
4. **Policy test:** upload vượt max size, content type bị cấm, SAS hết hạn/permission vượt yêu cầu; system phải reject fail-closed.
5. **Failure-path integration test:** Blob Storage timeout/503 hoặc finalize thất bại; retry cùng `FileId` không tạo ambiguous overwrite và cleanup xử lý abandoned blobs.

## Quan sát trong production

- request/upload duration p50/p95/p99 và bytes uploaded;
- active concurrent uploads;
- process working set, managed heap, allocation rate và GC pause/time;
- Blob Storage dependency latency/status/retry telemetry qua Application Insights/Azure Monitor;
- count upload sessions theo trạng thái `Pending/Uploaded/Validated/Rejected/Expired`;
- SAS issuance audit: scope, permission class, expiry, actor/file ID — không log full SAS token;
- alert cho anonymous public-access configuration ngoài approved container;
- metric canceled/disconnected uploads và orphaned pending blobs;
- quota/rate-limit events theo user/tenant nếu workload multi-tenant.

## Câu hỏi phỏng vấn mở rộng

1. Nếu file phải virus-scan trước khi user khác có thể tải, bạn thiết kế state transition và asynchronous scanning như thế nào?
2. Nếu browser cần resumable upload hàng GB, bạn dùng Azure Block Blob upload semantics/direct client SDK ra sao mà vẫn giữ authorization boundary?
3. Khi nào proxy upload qua API vẫn tốt hơn direct SAS upload dù tốn application bandwidth hơn?

# Code Review Challenge 2 — Elasticsearch search càng xuống trang sâu càng chậm, autocomplete dùng wildcard tốn CPU và catalog update vẫn có thể để search stale

**Chủ đề:** Elasticsearch, TypeScript, search API design, deep pagination, analyzers, indexing consistency, eventual consistency, performance, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một e-commerce catalog lưu product source-of-truth trong SQL Server và dùng Elasticsearch cho search. Search API viết bằng TypeScript và được gọi từ frontend khi user gõ từ khóa.

Business yêu cầu:

- autocomplete/search phải phản hồi nhanh;
- user có thể sort theo `updatedAt`, `price`, `name`;
- catalog có khoảng 8 triệu products;
- product update trong SQL phải xuất hiện trong search trong vài giây đến mức chấp nhận được;
- deep export không cần dùng cùng API với interactive search nếu architecture khác tốt hơn;
- application phải chạy ổn khi nhiều users gõ tìm kiếm đồng thời;
- UI không được thấy duplicate/missing item do pagination instability nhiều hơn semantics đã chấp nhận;
- khi Elasticsearch tạm unavailable, update trong SQL không được “mất luôn” khỏi search index.

Production có các triệu chứng:

- page 1 nhanh nhưng page 200 trở đi chậm mạnh;
- một số requests fail khi page rất sâu;
- CPU trên Elasticsearch data nodes tăng khi user gõ vài ký tự phổ biến;
- `track_total_hits` tốn nhiều thời gian ở query có hàng triệu matches;
- cùng product đôi lúc xuất hiện ở cuối page N và đầu page N+1;
- catalog update đã commit SQL nhưng search vẫn giữ dữ liệu cũ sau một incident Elasticsearch;
- team đề xuất tăng `index.max_result_window`, dùng wildcard mạnh hơn và đặt `refresh: true` cho mọi update.

## Đoạn code cần review

```ts

export class ProductSearchService {
  constructor(
    private readonly elastic: Client,
    private readonly db: CatalogDb) {}

  async search(input: {
    q: string;
    page: number;
    pageSize: number;
    sortField: string;
  }) {
    const from = (input.page - 1) * input.pageSize;

    return this.elastic.search({
      index: 'products-v1',
      from,
      size: input.pageSize,
      track_total_hits: true,
      sort: [
        { [input.sortField]: 'desc' }
      ],
      query: {
        wildcard: {
          'name.keyword': {
            value: `*${input.q.toLowerCase()}*`
          }
        }
      }
    });
  }

  async updateProduct(productId: string, patch: ProductPatch) {
    const product = await this.db.products.update(productId, patch);

    await this.elastic.index({
      index: 'products-v1',
      id: product.id,
      document: product,
      refresh: true
    });

    return product;
  }
}
```

## Kết quả code review tham khảo

### Critical — SQL commit và Elasticsearch indexing không có durable handoff

**Vấn đề:** `db.products.update()` commit source-of-truth trước; sau đó mới gọi Elasticsearch. Nếu process crash, network timeout hoặc Elasticsearch unavailable, SQL đã đổi nhưng không có durable record bắt buộc index update phải được retry.

**Tại sao xảy ra:** Code xử lý SQL + search projection như hai writes tuần tự nhưng không có transaction chung hoặc durable integration boundary.

**Ảnh hưởng production:** Search có thể stale vô thời hạn sau một failure window, nhất là nếu không có periodic reconciliation. Client retry không chắc sửa được vì request có thể không retry hoặc retry patch khác.

**Cách sửa:** Persist change event/outbox cùng SQL transaction, sau đó worker/indexer consume và upsert Elasticsearch idempotently. Có retry + poison handling + reconciliation job so SQL version/checkpoint với search index. Search index phải được xem là rebuildable projection, không phải source-of-truth.

### High — Deep pagination bằng `from + size` tăng memory/CPU và chạm `max_result_window`

**Vấn đề:** `from` tăng theo page number. Distributed search phải xét/giữ đủ hits để bỏ qua toàn bộ previous window trên từng shard trước khi merge kết quả.

**Tại sao xảy ra:** Offset pagination từ relational/API thinking được áp thẳng vào distributed search.

**Ảnh hưởng production:** Page sâu làm heap/CPU tăng và latency xấu dần; mặc định Elasticsearch không cho `from + size` vượt 10,000 hits qua `index.max_result_window` safeguard.

**Cách sửa:** Interactive result set thường nên giới hạn depth. Nếu thật sự cần next-page traversal, dùng `search_after` với stable sort; khi cần consistent snapshot qua nhiều pages, dùng Point in Time (PIT) + `search_after`. Deep export là workload khác, nên có export pipeline riêng.

Tài liệu xác minh: Elastic Docs — `https://www.elastic.co/docs/reference/elasticsearch/rest-apis/paginate-search-results`.

### High — Leading wildcard trên `name.keyword` là query shape đắt và search quality kém

**Vấn đề:** Query `*term*` trên exact-value `keyword` field buộc pattern matching không tận dụng full-text analysis theo use case autocomplete.

**Tại sao xảy ra:** Team dùng wildcard để giả lập substring/autocomplete thay vì thiết kế analyzer/index cho query pattern thực tế.

**Ảnh hưởng production:** Term phổ biến hoặc query ngắn có thể match rất rộng, tăng CPU/latency. Search quality cũng nghèo vì không có tokenization/relevance semantics phù hợp.

**Cách sửa:** Xác định UX: prefix autocomplete, full-text search hay contains search. Với autocomplete, cân nhắc `search_as_you_type`, edge-ngram analyzer hoặc completion suggester tùy requirement. Với full-text, map `name` là `text` và có subfield `keyword` cho exact sort/filter.

### High — Mapping `name` chỉ là `keyword` không phù hợp cho full-text search

**Vấn đề:** `name` không được analyze/tokenize.

**Tại sao xảy ra:** Schema được thiết kế theo exact storage value chứ không theo search behavior.

**Ảnh hưởng production:** Search theo nhiều từ, morphology/case/token boundaries khó có relevance tốt; team dễ bù bằng wildcard ngày càng đắt.

**Cách sửa:** Ví dụ:

```json
"name": {
  "type": "text",
  "analyzer": "product_name_index",
  "search_analyzer": "product_name_search",
  "fields": {
    "keyword": {
      "type": "keyword",
      "ignore_above": 256
    }
  }
}
```

Analyzer cụ thể phải được chọn bằng dữ liệu/query corpus thực tế, không chỉ theo template.

### High — Sort field lấy trực tiếp từ client và không có stable tie-breaker

**Vấn đề:** Client chọn arbitrary field name và sort chỉ có một field như `updatedAt` hoặc `price`.

**Tại sao xảy ra:** API không whitelist sortable fields và không thiết lập total ordering.

**Ảnh hưởng production:** Query có thể sort vào field không phù hợp/không có doc values hoặc tạo expensive/invalid requests. Nhiều docs có cùng sort value làm ordering giữa requests không ổn định; page boundaries dễ duplicate/missing hơn khi index thay đổi.

**Cách sửa:** Whitelist sort modes server-side. Thêm stable unique tiebreaker, ví dụ `id.keyword`/dedicated keyword field. Với `search_after`, gửi lại đầy đủ sort values của hit cuối. Nếu cần consistent pagination qua concurrent updates, dùng PIT.

Elastic Docs cũng cảnh báo documents có cùng sort values có thể order không nhất quán giữa replicas nếu dựa vào internal doc IDs; stable explicit tiebreaker là cần thiết cho application pagination.

### High — `pageSize` không bị giới hạn

**Vấn đề:** Client có thể yêu cầu page cực lớn.

**Tại sao xảy ra:** API chuyển raw pagination input sang Elasticsearch mà không có contract/resource budget.

**Ảnh hưởng production:** Một request có thể tạo large response, heap pressure, network cost và long-running search.

**Cách sửa:** Clamp/validate page size ở API, ví dụ 20–100 theo UX/SLO. Export số lượng lớn đi qua separate bounded job/pipeline.

### High — `track_total_hits: true` cho mọi interactive query có thể tạo chi phí không cần thiết

**Vấn đề:** API bắt Elasticsearch đếm chính xác tổng hits cho mọi search dù UI có thể chỉ cần “còn trang tiếp theo” hoặc approximate total.

**Tại sao xảy ra:** Exact total được xem như free metadata.

**Ảnh hưởng production:** Query match rộng có thể tốn thêm work đáng kể, nhất là autocomplete/typing traffic cao.

**Cách sửa:** Xác minh UX requirement. Nếu exact total không cần, dùng default/threshold behavior hoặc bounded count strategy; frontend có thể dựa vào `hasMore`/cursor. Exact analytics count có thể tách khỏi hot interactive path.

### High — `refresh: true` trên mọi update làm giảm indexing throughput

**Vấn đề:** Mỗi index write yêu cầu immediate refresh behavior thay vì để Elasticsearch batching/refresh cadence hoạt động hiệu quả.

**Tại sao xảy ra:** Team muốn read-after-write nhanh bằng cách ép refresh từng document.

**Ảnh hưởng production:** Nhiều catalog updates có thể làm refresh overhead tăng, tạo nhiều small segments/work và cạnh tranh tài nguyên với search.

**Cách sửa:** Xác định freshness SLO thực tế. Thường chấp nhận near-real-time vài giây và để refresh interval/batching phù hợp. Nếu một workflow đặc biệt cần read-your-write, cân nhắc `refresh: wait_for` hoặc application-level acknowledgement semantics thay vì `true` mọi write, nhưng vẫn phải benchmark theo workload/version.

### Medium — Search query không có cancellation/timeout budget ở application layer

**Vấn đề:** Snippet không thể hiện request abort hoặc application timeout propagation.

**Tại sao xảy ra:** Search client call được xem như bounded tự nhiên.

**Ảnh hưởng production:** Browser/user đã rời đi nhưng backend/cluster có thể tiếp tục work; slow query burst làm capacity bị giữ lâu.

**Cách sửa:** Propagate request cancellation/abort theo client framework và đặt end-to-end timeout budget phù hợp SLO. Kết hợp server-side query guardrails và circuit/degradation behavior thay vì chỉ timeout ở HTTP layer.

### Medium — Hard-code physical index name `products-v1`

**Vấn đề:** Application phụ thuộc trực tiếp versioned physical index.

**Tại sao xảy ra:** Index lifecycle/mapping migration chưa được abstraction bằng alias.

**Ảnh hưởng production:** Reindex/mapping migration yêu cầu coordinated application deploy hoặc downtime/race khi switch.

**Cách sửa:** Dùng logical read/write alias phù hợp với architecture. Reindex sang `products-v2`, validate count/sample/query quality, rồi atomically switch alias. Writer synchronization strategy phải tính event replay/checkpoint trong lúc reindex.

### Medium — Không có query normalization/empty-query policy rõ

**Vấn đề:** `q.toLowerCase()` đơn giản không định nghĩa semantics cho whitespace, Unicode, empty input hoặc rất ngắn query.

**Tại sao xảy ra:** Query normalization bị nhét vào controller/service thay vì search contract/analyzer design.

**Ảnh hưởng production:** Query 1 ký tự hoặc empty-like value có thể match cực rộng, làm tải cluster tăng và UX không nhất quán.

**Cách sửa:** Đặt min query length/rate limiting/debounce ở UX/API theo requirement; normalize ở analyzer/query layer có chủ đích; empty query dùng endpoint/sort khác nếu cần browse catalog.

## Phiên bản đề xuất

Một thiết kế tốt hơn tách **interactive search** khỏi **index synchronization**.

Ví dụ TypeScript service cho interactive search dùng cursor (`search_after`) và whitelist sort:

```ts
import { Client } from '@elastic/elasticsearch';

const MAX_PAGE_SIZE = 50;

type SortMode = 'relevance' | 'updated' | 'price_asc' | 'price_desc';

type SearchCursor = Array<string | number>;

export class ProductSearchService {
  constructor(private readonly elastic: Client) {}

  async search(input: {
    q: string;
    pageSize: number;
    sort: SortMode;
    cursor?: SearchCursor;
  }) {
    const q = input.q.trim();
    const size = Math.min(Math.max(input.pageSize, 1), MAX_PAGE_SIZE);

    if (q.length < 2) {
      throw new Error('Search term is too short');
    }

    const sort = buildSort(input.sort);

    const response = await this.elastic.search({
      index: 'products-read',
      size,
      sort,
      search_after: input.cursor,
      track_total_hits: false,
      query: {
        multi_match: {
          query: q,
          fields: ['name^3', 'description'],
          type: 'best_fields'
        }
      }
    });

    const hits = response.hits.hits;
    const last = hits.at(-1);

    return {
      items: hits.map(x => x._source),
      nextCursor: last?.sort ?? null
    };
  }
}

function buildSort(sort: SortMode) {
  switch (sort) {
    case 'updated':
      return [
        { updatedAt: 'desc' as const },
        { id: 'asc' as const }
      ];

    case 'price_asc':
      return [
        { price: 'asc' as const },
        { id: 'asc' as const }
      ];

    case 'price_desc':
      return [
        { price: 'desc' as const },
        { id: 'asc' as const }
      ];

    default:
      return [
        { _score: 'desc' as const },
        { id: 'asc' as const }
      ];
  }
}
```

Nếu UX cần stable multi-page snapshot trong khi catalog liên tục update, dùng PIT + `search_after` theo Elastic guidance. Cursor phải encode sort values + PIT/token state phù hợp và có validation/versioning, không expose raw arbitrary query DSL từ client.

Autocomplete cần benchmark một mapping/query riêng (`search_as_you_type`, edge-ngram hoặc completion suggester) thay vì mặc định dùng `*term*` wildcard. Lựa chọn phụ thuộc prefix semantics, ranking, index-size budget và language requirements.

SQL-to-Elasticsearch synchronization nên dùng durable outbox/change feed pattern:

```text
SQL transaction:
  UPDATE Product
  INSERT ProductSearchOutbox(ProductId, Version, EventType, CreatedAtUtc)
  COMMIT

Indexer worker:
  read pending outbox in bounded batches
  load current product projection
  upsert Elasticsearch document idempotently
  record processed checkpoint / mark outbox delivered
  retry transient failures with backoff
  quarantine poison events

Reconciliation job:
  compare SQL version/checkpoint vs Elasticsearch version
  repair missing/stale documents
```

Không cần distributed transaction giữa SQL và Elasticsearch. Search index là eventually consistent projection nhưng update intent không được mất.

## Giải thích thiết kế sau khi sửa

Thiết kế mới phân biệt interactive search và export. Interactive search giới hạn result depth/page size, dùng stable sort + cursor, và chỉ thực hiện query phù hợp với UX latency SLO.

Search field mapping được thiết kế theo query patterns: `text` cho analyzed search, `keyword` subfield cho exact filter/sort khi cần. Autocomplete có analyzer/data structure riêng thay vì wildcard contains query mặc định.

SQL là source-of-truth. Elasticsearch update được xem là asynchronous projection update với durable handoff. Khi Elasticsearch outage, outbox giữ thay đổi để retry; reconciliation sửa drift lâu dài.

Physical index name không đi thẳng vào application contract. Alias cho phép reindex/mapping migration với controlled cutover.

## Trade-offs

- **`search_after` cursor:** hiệu quả hơn deep offset nhưng không hỗ trợ random jump page 200 theo UX truyền thống; UI có thể phải chuyển sang next/previous/infinite scroll.
- **PIT:** cho snapshot consistency tốt hơn nhưng giữ search context và cần lifecycle/expiry management.
- **Edge-ngram/search-as-you-type:** autocomplete nhanh hơn wildcard nhưng tăng index size/write cost; cần benchmark analyzer.
- **Outbox/indexer:** thêm eventual consistency và operational component, nhưng loại failure window “SQL committed, search update lost”.
- **Exact total hits bỏ đi:** giảm cost nhưng UI không có con số chính xác tức thời; phải xác minh product requirement.
- **Alias/reindex:** thêm deployment/index lifecycle logic nhưng giảm downtime và coupling khi mapping thay đổi.

## Cách kiểm thử

1. **Load test:** query 2–4 ký tự phổ biến với 500–1000 concurrent requests; so sánh wildcard hiện tại với analyzer-based query về p95/p99, CPU, heap và rejected tasks.
2. **Pagination correctness test:** nhiều documents có cùng `updatedAt`; mutate index giữa pages và kiểm tra behavior của offset pagination vs `search_after`, rồi PIT + `search_after` nếu requirement cần snapshot consistency.
3. **Failure-path integration test:** SQL commit thành công, Elasticsearch unavailable; xác minh outbox giữ event và index tự hội phục khi dependency trở lại.
4. **Reindex validation:** build `products-v2`, replay/update song song, so document counts/version samples/query relevance trước khi alias switch; rollback alias nếu validation fail.
5. **API guardrail test:** invalid sort field, pageSize quá lớn, query quá ngắn và malformed cursor phải bị reject mà không gửi expensive query vào cluster.

## Quan sát trong production

- Elasticsearch search latency p50/p95/p99 theo query type;
- node CPU, JVM heap, GC, search thread-pool queue/rejections;
- slow search logs/profile samples cho high-cost queries;
- query cardinality theo normalized query length, không log raw sensitive search terms nếu privacy policy cấm;
- result-window/deep-pagination rejection count;
- outbox backlog age/count và indexing retry rate;
- SQL product version vs Elasticsearch document version drift metrics;
- reindex progress, alias target và failed document count;
- dashboard search freshness lag: SQL commit timestamp → index visible timestamp;
- frontend/API request cancellation và duplicate typing requests nếu autocomplete traffic lớn.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product yêu cầu user phải nhảy trực tiếp tới page 500, bạn phản biện requirement hay thiết kế architecture nào để vẫn đáp ứng được?
2. Khi nào bạn chọn `search_as_you_type`, edge-ngram hoặc completion suggester cho autocomplete?
3. Nếu Elasticsearch outage kéo dài 6 giờ và outbox backlog hàng chục triệu events, bạn recovery thế nào để không làm cluster vừa hồi phục bị quá tải?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Upload lớn cần được thiết kế theo **bounded resources**, explicit ownership và clear trust boundaries; “đọc hết vào memory rồi upload” không scale theo concurrency.
- Azure Blob access nên dùng least privilege: private-by-default, Managed Identity cho workload và narrowly scoped short-lived SAS khi client cần direct access.
- Storage object key không nên dùng raw user filename làm identity khi hệ thống multi-user.
- Elasticsearch interactive search, deep export và indexing synchronization là ba workload khác nhau; không nên dùng một query/update pattern cho tất cả.
- `from + size`, leading wildcard, exact total hits và per-write refresh đều có production cost cần đo bằng evidence.
- Search index là projection: correctness đến từ durable handoff, idempotent indexing và reconciliation chứ không phải cố tạo distributed ACID transaction với SQL.

## Mẫu tư duy cần nhớ

1. **Bound resource usage trước khi scale hạ tầng.**
2. **Tách display identity khỏi security/resource identity.**
3. **Thiết kế query/index theo access pattern, không theo dữ liệu đang có sẵn.**
4. **Durable handoff trước retry khi đồng bộ hai hệ thống.**
5. **Measure p95/p99, memory, CPU và dependency behavior trước khi tối ưu.**
