# Code Review Challenge 1 — Upload chứng từ lên Azure Blob Storage: authorization, streaming và failure recovery

**Chủ đề:** ASP.NET Core, Azure Blob Storage, EF Core, multi-tenant security, resource management  
**Độ khó:** Senior+

## Bối cảnh

Một API .NET 8 phục vụ hệ thống phê duyệt chứng từ nhiều tenant. Người dùng đăng nhập qua Microsoft Entra ID, upload PDF hoặc ảnh. API lưu blob vào container private, ghi metadata vào SQL Server, sau đó trả URL cho frontend. Giả định request thường 2–20 MB nhưng đôi khi 200 MB; ba Azure App Service instances; có retry từ mobile khi mạng chập chờn. Mỗi người chỉ được upload vào hồ sơ thuộc tenant mình và phải xem được chứng từ sau khi lưu thành công. Một số file lớn gây memory spike; đôi khi có blob không có metadata và người dùng báo thấy file của hồ sơ khác. Chưa có bằng chứng xác định root cause.

Code dưới đây là bản rút gọn có thể chạy trong một ứng dụng đã cấu hình DI, routing và Blob SDK. Giả sử `_db` là scoped EF Core DbContext, `_container` là BlobContainerClient, `Document` có `CaseId`, `TenantId`, `BlobName`, `OriginalName`, `ContentType`, `Size`.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/cases/{caseId:guid}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly BlobContainerClient _container;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(AppDbContext db,
        BlobContainerClient container, ILogger<DocumentsController> logger)
    {
        _db = db;
        _container = container;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> Upload(Guid caseId, IFormFile file)
    {
        var tenantId = Request.Headers["X-Tenant-Id"].ToString();
        var target = await _db.Cases.FirstOrDefaultAsync(x => x.Id == caseId);
        if (target == null) return NotFound();

        var blobName = $"{tenantId}/{caseId}/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);
        using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        buffer.Position = 0;

        await blob.UploadAsync(buffer, overwrite: true);
        var record = new Document
        {
            CaseId = caseId,
            TenantId = tenantId,
            BlobName = blobName,
            OriginalName = file.FileName,
            ContentType = file.ContentType,
            Size = file.Length
        };
        _db.Documents.Add(record);
        await _db.SaveChangesAsync();

        _logger.LogInformation("Uploaded {File} for {Tenant}",
            file.FileName, tenantId);
        return Ok(new { url = blob.Uri.ToString(), id = record.Id });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Tenant ID lấy từ header không đáng tin cậy

**Vấn đề:** `X-Tenant-Id` là input do client tự cung cấp; `[Authorize]` chỉ yêu cầu authenticated user.  
**Tại sao xảy ra:** Không có bước đối chiếu tenant với identity/membership đáng tin cậy.  
**Ảnh hưởng production:** Ghi nhầm namespace, spoof tenant và có thể dẫn tới cross-tenant data exposure khi kết hợp các lỗi khác.  
**Cách sửa:** Resolve tenant từ principal đã được xác minh hoặc kiểm tra membership server-side; không lấy tenant từ header rồi tin ngay.

### [Critical] — Không kiểm tra quyền trên case

**Vấn đề:** Query chỉ lọc `Id`, không lọc tenant hoặc quyền của user.  
**Tại sao xảy ra:** Authentication bị nhầm thành resource authorization.  
**Ảnh hưởng production:** Người dùng hợp lệ có thể upload vào case không thuộc quyền của mình; metadata sai tenant.  
**Cách sửa:** Query theo tenant và case; enforce quyền upload theo policy/ACL; trả `404` hoặc `403` nhất quán theo security policy.

### [High] — Overwrite blob và collision tên file

**Vấn đề:** `file.FileName` trở thành key và `overwrite: true`.  
**Tại sao xảy ra:** Tên file không unique, không được chuẩn hóa, có thể chứa ký tự đường dẫn; retry hoặc user khác có thể thay nội dung blob đang được metadata tham chiếu.  
**Ảnh hưởng production:** Mất dữ liệu, nội dung không khớp record, audit khó truy vết.  
**Cách sửa:** Server-generated opaque blob key (`Guid`/ULID), `overwrite: false`, giữ original filename chỉ như metadata đã làm sạch.

### [High] — Blob và SQL không atomic

**Vấn đề:** Blob upload xong mới ghi SQL; DB fail để lại orphan blob.  
**Tại sao xảy ra:** Không có distributed transaction tự động giữa Azure Blob Storage và SQL Server.  
**Ảnh hưởng production:** Storage leak, retry tạo bản sao hoặc metadata sai trạng thái.  
**Cách sửa:** Lưu trạng thái `Pending` trước, upload, đánh dấu `Ready` sau; dùng cleanup/reconciliation cho `Pending` quá hạn và orphan; idempotency key cho retry. Không giả định SQL transaction bao trùm blob.

### [High] — Buffer toàn bộ file trong RAM

**Vấn đề:** `MemoryStream` nhận toàn bộ nội dung file.  
**Tại sao xảy ra:** `CopyToAsync` materialize file vào memory, tăng allocation/LOH/GC; `IFormFile` còn có buffering ở tầng ASP.NET Core tùy cấu hình.  
**Ảnh hưởng production:** Memory pressure, GC pause, OOM hoặc instance recycle dưới concurrency.  
**Cách sửa:** Streaming với giới hạn kích thước, request-body limits phù hợp, kiểm soát concurrency và backpressure; với file rất lớn cân nhắc direct upload bằng SAS ngắn hạn.

### [High] — Thiếu giới hạn và kiểm tra file

**Vấn đề:** Không kiểm tra null, length, extension, magic bytes, loại nội dung và malware policy.  
**Tại sao xảy ra:** `ContentType` và filename là metadata do client khai báo.  
**Ảnh hưởng production:** Storage abuse, upload payload nguy hiểm, tăng chi phí và rủi ro nếu file được serve sai content type.  
**Cách sửa:** Enforce size allowlist, kiểm tra signature theo loại file, scan/quarantine nếu threat model yêu cầu, download qua endpoint có authorization với safe headers.

### [Medium] — Thiếu CancellationToken

**Vấn đề:** DB, stream và blob operations không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Tác vụ tiếp tục dù client đã ngắt kết nối; cũng cần thiết kế riêng khi commit cuối cùng không nên bị hủy giữa chừng.  
**Ảnh hưởng production:** Lãng phí I/O, tài nguyên và orphan tăng khi timeout.  
**Cách sửa:** Truyền cancellation vào các thao tác có thể hủy; thiết kế reconciliation cho trạng thái chưa hoàn tất.

### [Medium] — Response URL không có hợp đồng truy cập

**Vấn đề:** Trả `blob.Uri` của private container như thể đó là download URL.  
**Tại sao xảy ra:** URI chỉ định danh object; không cấp quyền đọc.  
**Ảnh hưởng production:** Browser nhận 403 hoặc nhóm phát triển vô tình bật public access để chữa cháy.  
**Cách sửa:** Trả document ID và authenticated download endpoint; nếu dùng SAS, phát hành SAS read-only ngắn hạn sau authorization.

### [Medium] — Không có idempotency và observability theo upload

**Vấn đề:** Retry sinh record trùng hoặc overwrite; log không có operation ID, outcome và failure stage.  
**Tại sao xảy ra:** Không có unique request key và state machine.  
**Ảnh hưởng production:** Không phân biệt retry với upload mới, khó xác định orphan, lỗi phân tán giữa SQL và Blob.  
**Cách sửa:** Unique `(TenantId, IdempotencyKey)`, trạng thái, correlation ID, metric upload bytes, failure stage, pending age; không log file contents hoặc token.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa luồng backend proxy; các helper là abstraction cần implement/test riêng. Giả định `ITenantAccess` lấy identity từ authenticated principal, `IFilePolicy` thực hiện size/type/signature validation trước khi ghi, `UploadKey` là unique per tenant trong DB, và DB có concurrency/unique constraints. `Pending` records được worker reconcile; upload status có thể được client query. Đây không phải giải pháp antivirus hoặc authorization hoàn chỉnh chỉ bằng vài dòng.

```csharp
[Authorize]
[ApiController]
[Route("api/cases/{caseId:guid}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly BlobContainerClient _container;
    private readonly ITenantAccess _access;
    private readonly IFilePolicy _files;

    public DocumentsController(AppDbContext db, BlobContainerClient container,
        ITenantAccess access, IFilePolicy files)
        => (_db, _container, _access, _files) = (db, container, access, files);

    [HttpPost]
    public async Task<IActionResult> Upload(
        Guid caseId, IFormFile file,
        [FromHeader(Name = "Idempotency-Key")] string key,
        CancellationToken ct)
    {
        var tenant = await _access.GetAuthorizedTenantAsync(User, ct);
        if (string.IsNullOrWhiteSpace(key) || key.Length > 128)
            return BadRequest("Valid Idempotency-Key required");
        if (file is null || !await _files.IsAllowedAsync(file, ct))
            return BadRequest("Unsupported file");
        if (!await _access.CanUploadToCaseAsync(User, tenant, caseId, ct))
            return NotFound();

        // Claim operation atomically via unique (TenantId, UploadKey).
        var claim = await _db.ClaimUploadAsync(
            tenant, caseId, key, file.Length, ct);
        if (!claim.IsNew)
            return Accepted(new { id = claim.DocumentId, status = claim.Status });

        var blob = _container.GetBlobClient(claim.BlobName);
        try
        {
            await using var input = file.OpenReadStream();
            await blob.UploadAsync(input,
                new Azure.Storage.Blobs.Models.BlobUploadOptions
                {
                    Conditions = new Azure.Storage.Blobs.Models.BlobRequestConditions
                    {
                        IfNoneMatch = Azure.ETag.All
                    }
                }, ct);
            await _db.MarkUploadReadyAsync(claim.DocumentId, ct);
            return CreatedAtAction(nameof(GetStatus),
                new { caseId, id = claim.DocumentId },
                new { id = claim.DocumentId, status = "Ready" });
        }
        catch (Exception) when (!ct.IsCancellationRequested)
        {
            // Durable Pending state enables reconciliation and safe retries.
            throw;
        }
    }

    [HttpGet("{id:guid}/status")]
    public async Task<IActionResult> GetStatus(Guid caseId, Guid id,
        CancellationToken ct)
    {
        var tenant = await _access.GetAuthorizedTenantAsync(User, ct);
        if (!await _access.CanReadCaseAsync(User, tenant, caseId, ct))
            return NotFound();
        var status = await _db.GetUploadStatusAsync(tenant, caseId, id, ct);
        return status is null ? NotFound() : Ok(status);
    }
}
```

**Điều kiện để implementation trên an toàn:** `ClaimUploadAsync` phải dùng DB unique constraint, xử lý race duplicate key và trả trạng thái hiện tại; cùng idempotency key với payload khác phải bị từ chối (lưu hash/size và metadata để so sánh). `BlobName` phải do server sinh, không trùng, không chứa filename user. `MarkUploadReadyAsync` phải có điều kiện trạng thái; worker reconcile xử lý blob đã tồn tại nhưng DB còn `Pending`, upload dở, timeout và retry; worker không được tự động xóa blob của operation đang chạy. `IFilePolicy` phải giới hạn kích thước ngay ở HTTP ingress và scan/validate stream theo threat model; `IFormFile` vẫn có thể buffering nên cần đổi sang multipart streaming hoặc direct-to-Blob cho tải lớn. Exception handling tập trung trả `ProblemDetails`, tránh lộ storage details. Với client cancellation sau upload, reconciliation vẫn phải hoàn thành eventual state.

## Giải thích thiết kế sau khi sửa

Authorization áp dụng ở resource boundary trước khi cấp quyền ghi. Blob key opaque tách identity storage khỏi tên user. Durable `Pending → Ready` biến partial failure thành trạng thái quan sát và sửa được; unique idempotency key xử lý retry across instances. Private blob không được expose như public URL. Nếu yêu cầu chống malware, trạng thái nên là `PendingScan → Ready` và không cho download trước khi scan hoàn tất.

## Trade-offs

- Proxy streaming giữ authorization và kiểm soát upload tại backend nhưng tiêu thụ network/compute của App Service; direct SAS giảm tải backend nhưng cần scope cực hẹp, expiry, upload-finalization API và kiểm tra nội dung sau upload.
- Pending state + reconciliation tăng schema và operational complexity; đổi lại có recovery rõ ràng thay vì hy vọng hai service commit cùng lúc.
- Quét file làm tăng latency; có thể dùng asynchronous quarantine nếu business chấp nhận delayed availability.
- Idempotency storage có retention và cleanup; cần quy định thời hạn retry và payload mismatch.

## Cách kiểm thử

1. **Security integration:** user tenant A thử upload vào case tenant B; đổi header và case ID; xác minh không có blob hoặc DB record nào được tạo.
2. **Concurrency:** 50 request cùng idempotency key trên ba instances; chỉ một operation được claim; key trùng nhưng payload khác bị reject.
3. **Failure injection:** Blob upload thành công, DB mark-ready fail; reconciliation đưa trạng thái về Ready mà không nhân bản object.
4. **Load test:** upload 20–200 MB đồng thời; đo peak memory, GC, p95, 413/429, throttling và request cancellation.
5. **Security/file test:** MIME giả, file signature sai, tên chứa path separator, file vượt quota, blob private và download không đủ quyền.

## Quan sát trong production

Dùng Application Insights distributed traces với `operationId`, `documentId`, `tenantId` đã được phân loại an toàn; spans cho authorize, claim, blob upload, SQL finalize. Metrics: upload throughput/bytes, p95 duration, memory/GC, Blob 4xx/5xx, DB errors, `Pending` age, orphan count, retry/collision rate. Alert khi Pending backlog hoặc cross-tenant authorization denial tăng bất thường; không ghi token, SAS hay nội dung file vào log.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Product = { id: string; name: string; highlight: string }
type SearchResponse = { items: Product[]; total: number }

const query = ref('')
const category = ref('all')
const page = ref(1)
const products = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
const token = localStorage.getItem('access_token')

async function search() {
  loading.value = true
  error.value = ''
  const url = '/api/products/search?q=' + query.value +
    '&category=' + category.value + '&page=' + page.value
  try {
    const response = await fetch(url, {
      headers: { Authorization: 'Bearer ' + token }
    })
    const data = await response.json() as SearchResponse
    products.value = data.items
    total.value = data.total
  } catch (e) {
    error.value = String(e)
  }
  loading.value = false
}

watch([query, category, page], search)
onMounted(search)
</script>

<template>
  <input v-model="query" placeholder="Search products" />
  <select v-model="category">
    <option value="all">All</option>
    <option value="electronics">Electronics</option>
  </select>
  <button @click="page++">Next</button>
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <p>{{ total }} results</p>
  <div v-for="p in products" :key="p.id">
    <strong>{{ p.name }}</strong>
    <div v-html="p.highlight"></div>
  </div>
</template>
```

## Kết quả code review tham khảo

### [High] — Render HTML không tin cậy bằng v-html

**Vấn đề:** `p.highlight` được render trực tiếp như HTML.  
**Tại sao xảy ra:** Dữ liệu search index có thể chứa content do bên thứ ba hoặc CMS cung cấp; `v-html` không escape HTML.  
**Ảnh hưởng production:** XSS nếu attacker kiểm soát dữ liệu và không có sanitization bảo đảm; rủi ro session/data compromise tùy threat model.  
**Cách sửa:** Ưu tiên text rendering hoặc structured highlight tokens; nếu bắt buộc HTML, sanitize bằng allowlist được kiểm chứng ở trust boundary và áp dụng CSP như defense in depth.

### [High] — Response race làm stale results ghi đè

**Vấn đề:** Các request độc lập đều cập nhật `products`.  
**Tại sao xảy ra:** Network completion order không đảm bảo giống thứ tự user nhập.  
**Ảnh hưởng production:** Người dùng xem sản phẩm không khớp query/filter, có thể đưa ra quyết định sai.  
**Cách sửa:** Abort request cũ và dùng monotonic sequence guard để chỉ request mới nhất được phép commit state.

### [High] — HTTP error bị coi là thành công

**Vấn đề:** `fetch` resolve bình thường với HTTP 4xx/5xx; code không kiểm tra `response.ok`.  
**Tại sao xảy ra:** Chỉ network errors/abort mới thường reject promise.  
**Ảnh hưởng production:** JSON error object bị gán vào `items`, gây UI lỗi hoặc silent failure.  
**Cách sửa:** Kiểm tra status, xử lý 401/403/429/5xx có phân loại; không render dữ liệu invalid.

### [Medium] — Mỗi phím gõ gây request

**Vấn đề:** Watcher chạy ngay theo thay đổi của query.  
**Tại sao xảy ra:** Không debounce, không minimum query policy và không cancellation.  
**Ảnh hưởng production:** API pressure, Elasticsearch QPS tăng, rate limiting và latency xấu.  
**Cách sửa:** Debounce text input, cancel stale request; backend vẫn enforce rate limit.

### [Medium] — Loading/error state không thuộc request hiện hành

**Vấn đề:** Request cũ có thể set `loading=false` sau khi request mới bắt đầu hoặc ghi error cũ.  
**Tại sao xảy ra:** Shared flags không có request ownership.  
**Ảnh hưởng production:** Spinner sai, thông báo lỗi lạc ngữ cảnh.  
**Cách sửa:** Guard mọi state update theo request sequence; dùng `finally`.

### [Medium] — Query string không encode và thiếu validation

**Vấn đề:** Concatenation raw query/category.  
**Tại sao xảy ra:** Ký tự `&`, `#`, Unicode hoặc reserved characters có thể đổi nghĩa URL.  
**Ảnh hưởng production:** Search sai hoặc filter bị biến dạng; server vẫn phải validate.  
**Cách sửa:** `URLSearchParams`, whitelist category, clamp page; server-side validation.

### [Medium] — Token snapshot và localStorage threat model

**Vấn đề:** Token đọc một lần khi component setup, không refresh; lưu token trong `localStorage` làm tăng tác động nếu có XSS.  
**Tại sao xảy ra:** Auth lifecycle không tích hợp API client.  
**Ảnh hưởng production:** Token hết hạn gây 401 kéo dài; XSS có thể đọc token nếu lưu ở localStorage.  
**Cách sửa:** Dùng auth client quản lý token refresh/reauth; cân nhắc HttpOnly Secure SameSite cookie với CSRF defense khi phù hợp, hoặc short-lived token lưu trong memory; không mặc định một cơ chế là luôn đúng.

### [Medium] — Pagination không reset khi filter đổi

**Vấn đề:** Đổi query/category vẫn giữ page hiện tại.  
**Tại sao xảy ra:** Page là state độc lập nhưng phụ thuộc filter.  
**Ảnh hưởng production:** Trang trống dù có nhiều kết quả ở page 1.  
**Cách sửa:** Reset page khi query/category đổi; disable Next khi không còn trang và validate total/page size.

### [Low] — Thiếu cleanup và accessibility feedback

**Vấn đề:** Không hủy request/timer khi component unmount, không có status accessible.  
**Tại sao xảy ra:** Lifecycle không được quản lý đầy đủ.  
**Ảnh hưởng production:** Request thừa, state cập nhật không cần thiết, trải nghiệm keyboard/screen-reader kém.  
**Cách sửa:** `onUnmounted` cleanup; `aria-live` và disabled state.

## Phiên bản đề xuất

Giả định `getAccessToken()` là hàm của auth layer, xử lý refresh/reauth và có thể throw; backend trả schema đúng và giới hạn `page`/`category`. Highlight chuyển thành plain text (không giữ markup). Nếu muốn giữ phần bôi đậm, dùng structured ranges do server cung cấp rồi render bằng Vue text bindings, không tin HTML thô.

```vue
<script setup lang="ts">
import { ref, watch, onUnmounted } from 'vue'
import { getAccessToken } from '@/auth/client'

type Product = { id: string; name: string; highlight: string }
type Result = { items: Product[]; total: number }

const query = ref('')
const category = ref('all')
const page = ref(1)
const products = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
const pageSize = 20

let timer: ReturnType<typeof setTimeout> | undefined
let controller: AbortController | undefined
let generation = 0

function invalidate() {
  generation++
  controller?.abort()
  clearTimeout(timer)
  loading.value = false
}

watch([query, category], () => {
  page.value = 1
}, { flush: 'sync' })

watch([query, category, page], () => {
  invalidate()
  const mine = generation
  const q = query.value.trim()
  const c = category.value
  const p = page.value
  loading.value = true
  error.value = ''
  timer = setTimeout(async () => {
    const active = new AbortController()
    controller = active
    try {
      const token = await getAccessToken()
      if (mine !== generation) return
      const params = new URLSearchParams({
        q, category: c, page: String(p)
      })
      const response = await fetch('/api/products/search?' + params, {
        headers: { Authorization: 'Bearer ' + token },
        signal: active.signal
      })
      if (!response.ok) throw new Error('HTTP ' + response.status)
      const data: Result = await response.json()
      if (!Array.isArray(data.items) || !Number.isFinite(data.total))
        throw new Error('Invalid search response')
      if (mine !== generation) return
      products.value = data.items
      total.value = data.total
    } catch (e) {
      if (mine === generation && !active.signal.aborted) {
        error.value = e instanceof Error ? e.message : 'Search failed'
        products.value = []
        total.value = 0
      }
    } finally {
      if (mine === generation) {
        loading.value = false
        controller = undefined
      }
    }
  }, 250)
}, { immediate: true })

onUnmounted(invalidate)
</script>

<template>
  <input v-model="query" aria-label="Search products" />
  <select v-model="category" aria-label="Category">
    <option value="all">All</option>
    <option value="electronics">Electronics</option>
  </select>
  <button :disabled="loading || page * pageSize >= total"
          @click="page++">Next</button>
  <p role="status" aria-live="polite" v-if="loading">Loading...</p>
  <p role="alert" v-if="error">{{ error }}</p>
  <p>{{ total }} results</p>
  <div v-for="p in products" :key="p.id">
    <strong>{{ p.name }}</strong>
    <div>{{ p.highlight }}</div>
  </div>
</template>
```

**Giới hạn cần xác minh:** watcher `flush: 'sync'` reset page đồng bộ khi query/category thay đổi; nhiều reactive changes trong cùng thao tác vẫn có thể làm watcher scheduling phức tạp, nên kiểm thử bằng fake timers và delayed responses. Khi `getAccessToken()` mất nhiều thời gian, generation guard chặn request cũ sau khi token resolve. `AbortController` chỉ hủy request client; không đảm bảo Elasticsearch ngừng xử lý ngay. Không hiển thị error raw body/token. Cần schema validation đầy đủ nếu API không đáng tin hoặc thay đổi thường xuyên. Nếu endpoint là public search, bỏ Bearer header khi không cần authentication.

## Giải thích thiết kế sau khi sửa

Mỗi lần input thay đổi, generation tăng và request cũ bị hủy; chỉ generation hiện tại được update UI. Debounce giảm số request khi gõ nhanh, nhưng cancellation + generation mới bảo vệ correctness. `URLSearchParams` encode query. `response.ok` phân biệt HTTP errors. Text interpolation mặc định escape nội dung, giảm nguy cơ XSS. Auth lifecycle được tách khỏi component.

## Trade-offs

- Debounce 250 ms giảm request nhưng thêm độ trễ cảm nhận; chọn giá trị dựa trên telemetry, không coi 250 ms là universal optimum.
- Abort tiết kiệm network/client work nhưng không thay thế rate limit, server cancellation và Elasticsearch query controls.
- Xóa kết quả khi lỗi tránh hiển thị stale data nhưng có thể gây UX nhấp nháy; có thể giữ dữ liệu cũ với nhãn rõ `stale` nếu Product chấp nhận.
- SSR/pre-render cần xem xét nếu trang listing phải crawlable/SEO; client-only search không nhất thiết sai với trang tìm kiếm nội bộ.

## Cách kiểm thử

1. **Component test:** fake timers, gõ liên tục và xác nhận debounce chỉ gửi request cuối cùng sau idle.
2. **Race test:** request A trả chậm hơn B; A không được overwrite products/total/loading của B.
3. **Failure-path:** HTTP 401, 429, 500, invalid JSON, network offline và auth token refresh fail; hiển thị lỗi phù hợp, không treo spinner.
4. **Security test:** highlight chứa `<img onerror=...>` hoặc `<script>` được render như text, không thực thi; kiểm tra CSP và token handling.
5. **Playwright E2E:** đổi category tại page sâu, back/forward navigation nếu dùng URL state, disable Next và kiểm tra screen reader status.

## Quan sát trong production

Frontend RUM ghi search input-to-results latency, abort rate, request count per interaction, error status, stale-result prevention count, không gửi raw search term nếu chứa PII. Backend Application Insights theo correlation ID ghi HTTP p50/p95/p99, 429/5xx, Elasticsearch dependency duration, timeout và query volume. So sánh trước/sau bằng canary rollout; theo dõi UX và server load, không chỉ số request.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business yêu cầu chia sẻ URL và browser Back/Forward giữ nguyên search state, bạn đồng bộ route query với reactive state ra sao để tránh vòng lặp?
2. Nếu search API dùng Elasticsearch highlight markup, thiết kế contract structured highlighting thế nào để không cần `v-html`?
3. Nếu server trả 429 kèm `Retry-After`, bạn xử lý retry như thế nào mà không phát lại query đã lỗi thời?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication không thay thế resource-level authorization; tenant identity phải được xác minh và áp dụng nhất quán ở read/write boundary.
- Blob Storage và relational database không tự động chia sẻ transaction; retry phải đi cùng idempotency, durable state và reconciliation.
- Streaming, upload limits và concurrency control quan trọng hơn chỉ tăng memory instance.
- Vue reactive state không bảo đảm network responses hoàn thành đúng thứ tự; cancellation và generation guard giải quyết hai vấn đề khác nhau.
- Frontend không được tin HTML từ API; HTTP error handling phải kiểm tra status và xử lý auth lifecycle.

## Mẫu tư duy cần nhớ

1. Xác định trust boundary và ownership trước khi đọc/ghi resource.
2. Thiết kế partial failure, retry và idempotency như một contract thống nhất.
3. Đo memory, latency và queue/backlog trước khi tối ưu.
4. Gắn mọi asynchronous result với request/version hiện hành.
5. Kiểm thử failure path, concurrency và security thay vì chỉ happy path.
