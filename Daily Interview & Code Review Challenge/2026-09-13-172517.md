# Code Review Challenge 1 — Upload file lớn qua ASP.NET Core làm memory tăng mạnh và Blob Storage chứa object nửa vời

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Blob Storage, streaming, memory allocation, request limits, cancellation, content validation, failure recovery, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal document platform cho phép user upload các file video, ZIP và PDF lên Azure Blob Storage. API chạy trên Azure App Service Linux với nhiều instances.

Requirement hiện tại:

- file thông thường từ vài MB đến khoảng 2 GB;
- upload phải chịu được client disconnect hoặc deployment restart;
- application không được giữ toàn bộ file trong RAM;
- chỉ các file type được phép mới được lưu thành object hợp lệ;
- object upload lỗi giữa chừng không được bị nhầm là file hoàn chỉnh;
- metadata business được lưu trong SQL Server sau khi blob sẵn sàng;
- user không được chọn arbitrary blob path ngoài phạm vi document của mình;
- production cần quan sát được throughput, failure rate và resource pressure.

Sau release gần đây, production có các triệu chứng:

- memory của App Service tăng nhanh khi nhiều user upload file lớn cùng lúc;
- GC activity tăng, request p95/p99 của các endpoint không liên quan cũng xấu đi;
- một số instance restart khi traffic upload tăng;
- khi client đóng browser giữa upload, backend vẫn tiếp tục copy dữ liệu một lúc lâu;
- Blob Storage có một số blob tồn tại nhưng SQL không có document record tương ứng;
- một số blob có kích thước nhỏ bất thường nhưng vẫn được downstream processor coi là file hoàn chỉnh;
- log chứa nguyên file name do client gửi, đôi khi có ký tự lạ và path-like value;
- team đề xuất tăng memory tier của App Service và `RequestSizeLimit` lên lớn hơn để giải quyết.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(long.MaxValue)]
    public async Task<IActionResult> Upload(
        IFormFile file,
        [FromQuery] string folder,
        CancellationToken cancellationToken)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        var blobName = $"{folder}/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);

        await using var input = file.OpenReadStream();
        using var memory = new MemoryStream();

        await input.CopyToAsync(memory, CancellationToken.None);

        var bytes = memory.ToArray();

        await blob.UploadAsync(
            new BinaryData(bytes),
            overwrite: true,
            cancellationToken: CancellationToken.None);

        var document = new Document
        {
            BlobName = blobName,
            OriginalFileName = file.FileName,
            Size = bytes.Length,
            UploadedAt = DateTimeOffset.UtcNow,
            Status = "Ready"
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Uploaded {FileName} to {BlobName}, {Size} bytes",
            file.FileName,
            blobName,
            bytes.Length);

        return Ok(new { document.Id });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề về memory, streaming, cancellation, security và consistency trong endpoint.
2. Giải thích vì sao `MemoryStream` + `ToArray()` làm memory pressure tăng mạnh khi nhiều file lớn upload đồng thời.
3. Phân tích ảnh hưởng của `CancellationToken.None` khi client disconnect, request timeout hoặc application shutdown.
4. Review việc client kiểm soát `folder` và `file.FileName` để tạo blob path.
5. Đánh giá `RequestSizeLimit(long.MaxValue)` dưới góc nhìn reliability và abuse protection.
6. Giải thích tình huống blob upload thành công nhưng SQL `SaveChangesAsync` thất bại, và ngược lại requirement “Ready” nên được model thế nào.
7. Đề xuất strategy để object đang upload hoặc upload chưa hoàn tất không bị downstream processor coi là file hợp lệ.
8. Đề xuất implementation streaming/bounded-resource phù hợp với file lớn.
9. Nêu cách validate file type mà không chỉ tin extension hoặc client-provided `Content-Type`.
10. Nêu tests và telemetry cần có để chứng minh endpoint ổn định dưới concurrent large uploads và failure injection.

## Câu hỏi gợi mở

1. Với file 1 GB, endpoint hiện tại có thể giữ bao nhiêu bản sao dữ liệu trong managed memory ở các thời điểm khác nhau?
2. `CancellationToken` do ASP.NET Core cung cấp cho action đại diện cho điều gì khi request bị abort?
3. Blob Storage và SQL Server có cùng một transaction boundary không?
4. Nếu file upload thành công nhưng process chết trước khi insert SQL record, cleanup/reconciliation diễn ra ở đâu?
5. Nếu client gửi file tên `../../something.zip`, application có nên dùng trực tiếp tên đó làm storage key không?

## Kết quả code review tham khảo

### Critical — Toàn bộ file bị buffer trong managed memory

**Vấn đề:** Endpoint copy toàn bộ `IFormFile` vào `MemoryStream`, sau đó `ToArray()` tạo thêm một `byte[]` chứa toàn bộ nội dung trước khi upload Blob Storage.

**Tại sao xảy ra:** Code biến một workload có thể streaming thành workload cần giữ payload lớn trong RAM. Với nhiều concurrent uploads, memory consumption tăng gần tuyến tính theo tổng kích thước file đang xử lý, chưa tính các buffer khác của ASP.NET Core và SDK.

**Ảnh hưởng production:** Large allocations, LOH pressure, GC pause/CPU tăng, memory exhaustion hoặc process recycle. Các endpoint khác cùng process cũng bị ảnh hưởng dù không liên quan upload.

**Cách sửa:** Stream trực tiếp từ request/file stream sang Blob Storage API hỗ trợ stream. Không gọi `ToArray()` cho payload lớn. Đồng thời giới hạn số upload đồng thời hoặc dùng admission control nếu resource budget yêu cầu.

### Critical — Client-controlled path được dùng trực tiếp làm blob key

**Vấn đề:** `folder` và `file.FileName` đi thẳng vào `blobName`.

**Tại sao xảy ra:** Storage identity đang được derive từ untrusted input thay vì server-owned document identity.

**Ảnh hưởng production:** User có thể ghi đè blob khác nếu naming convention va chạm, tạo object ở prefix không thuộc quyền, làm log/path khó xử lý, hoặc gây confusion giữa tenant/document boundaries.

**Cách sửa:** Server generate blob key từ trusted identifiers, ví dụ `{tenantId}/{documentId}/{generatedObjectId}`. Chỉ lưu original file name như metadata đã normalize/validate, không dùng nó làm authority cho storage path.

### High — `CancellationToken.None` cắt đứt request cancellation

**Vấn đề:** Cả copy và Blob upload bỏ qua token của request.

**Tại sao xảy ra:** Work tiếp tục dù client đã disconnect hoặc host đang shutdown.

**Ảnh hưởng production:** Wasted network/CPU/storage operations, shutdown chậm, instance có thể bị kill giữa upload, và resource pressure tăng trong incident.

**Cách sửa:** Propagate request cancellation tới stream copy và Blob SDK. Kết hợp dependency timeout/budget riêng nếu cần. Cancellation không thay thế recovery vì process có thể chết đột ngột.

### High — Blob và SQL không có atomic transaction chung

**Vấn đề:** Blob được upload trước rồi SQL mới insert. Nếu `SaveChangesAsync` fail, blob trở thành orphan. Nếu flow được đảo lại, SQL có thể trỏ tới blob chưa hoàn tất.

**Tại sao xảy ra:** Azure Blob Storage và SQL Server là hai resource managers độc lập; code hiện tại không có protocol để reconcile partial success.

**Ảnh hưởng production:** Orphan blobs, missing documents, inconsistent UI, cleanup khó và storage cost tăng.

**Cách sửa:** Model explicit state machine. Ví dụ tạo document record `Uploading` trước, dùng server-generated blob key, stream upload, validate/finalize, sau đó transition sang `Ready`. Nếu failure, mark `Failed`/`Abandoned` và có cleanup/reconciliation job. Hoặc upload trước vào staging prefix rồi promote logical state sau validation. Không giả định distributed transaction.

### High — `Status = "Ready"` được set quá sớm về mặt business semantics

**Vấn đề:** Blob existence được coi là đủ để document sẵn sàng cho downstream processing.

**Tại sao xảy ra:** Không có trạng thái phân biệt upload hoàn tất, validation hoàn tất và business registration hoàn tất.

**Ảnh hưởng production:** File truncated/không hợp lệ hoặc object orphan có thể bị processor đọc như input hợp lệ.

**Cách sửa:** Dùng states như `Uploading`, `Uploaded`, `Validating`, `Ready`, `Failed`. Downstream chỉ đọc `Ready`. Transition phải dựa trên validation/checksum/metadata cần thiết.

### High — `RequestSizeLimit(long.MaxValue)` loại bỏ một lớp protection quan trọng

**Vấn đề:** Endpoint chấp nhận payload cực lớn mà không có business limit thực tế.

**Tại sao xảy ra:** “Cho phép file lớn” bị đồng nhất với “không có giới hạn”.

**Ảnh hưởng production:** Accidental hoặc malicious uploads có thể chiếm bandwidth, connections, memory/storage và làm giảm availability.

**Cách sửa:** Đặt explicit maximum theo requirement, ví dụ 2 GB hoặc tier-specific limit, cộng quota theo user/tenant nếu cần. Reject sớm khi metadata/request vượt policy.

### High — Không có file-content validation đáng tin cậy

**Vấn đề:** Code không validate content type/signature; downstream có thể tin extension hoặc tên file.

**Tại sao xảy ra:** Client-controlled metadata được coi là đủ để phân loại file.

**Ảnh hưởng production:** Unsupported hoặc malicious content có thể đi vào processing pipeline; nếu file sau này được serve inline có thể tạo thêm security risk.

**Cách sửa:** Validate extension như một tín hiệu, nhưng kiểm tra magic bytes/signature hoặc parser phù hợp đối với loại file hỗ trợ. Với nội dung nguy hiểm, dùng quarantine/scanning flow trước `Ready` nếu threat model yêu cầu.

### Medium — `IFormFile` có thể khiến request body đã được buffering trước khi code bắt đầu xử lý

**Vấn đề:** Multipart model binding với `IFormFile` không đồng nghĩa toàn bộ flow là streaming end-to-end.

**Tại sao xảy ra:** Framework có buffering behavior/configuration riêng cho multipart form files.

**Ảnh hưởng production:** Dù bỏ `MemoryStream`, application vẫn có thể chịu disk/memory buffering không mong muốn cho file rất lớn.

**Cách sửa:** Với multi-GB uploads, đánh giá streaming multipart reader hoặc direct-to-Blob upload bằng short-lived SAS nếu architecture/threat model phù hợp. Nếu vẫn proxy qua API, verify actual buffering behavior/configuration thay vì giả định.

### Medium — `overwrite: true` có thể che giấu collision/corruption

**Vấn đề:** Cùng blob key có thể bị ghi đè mà không có explicit version/ownership check.

**Tại sao xảy ra:** Blob naming không immutable theo document instance.

**Ảnh hưởng production:** User/request concurrent có thể thay nội dung của logical document mà metadata SQL không phản ánh đúng.

**Cách sửa:** Server-generated immutable blob names hoặc conditional write semantics nếu business cho phép replace. Replace phải là explicit operation có concurrency control.

### Medium — Logging client-controlled file name/path thiếu normalization và audit context

**Vấn đề:** Log raw file name và blob name nhưng thiếu actor/document/correlation identifiers.

**Tại sao xảy ra:** Logging tập trung vào payload metadata thay vì operation identity.

**Ảnh hưởng production:** Log injection/confusion có thể xảy ra với ký tự control; incident investigation khó correlate một upload với user/document state.

**Cách sửa:** Normalize log values, tránh log raw path-like input khi không cần, và ghi structured fields như document id, tenant id, actor id, blob key server-generated, size, duration, outcome, correlation id.

## Phiên bản đề xuất

Ví dụ dưới đây giữ upload qua backend nhưng streaming trực tiếp tới Blob Storage và model explicit document state. Tên state/schema chỉ là minh họa; production cần align với domain thực tế.

```csharp
[Authorize]
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxFileSize = 2L * 1024 * 1024 * 1024;

    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ICurrentUser _currentUser;
    private readonly IFileValidator _validator;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ICurrentUser currentUser,
        IFileValidator validator,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _currentUser = currentUser;
        _validator = validator;
        _logger = logger;
    }

    [HttpPost("upload")]
    [RequestSizeLimit(MaxFileSize)]
    public async Task<IActionResult> Upload(
        IFormFile file,
        CancellationToken cancellationToken)
    {
        if (file.Length <= 0 || file.Length > MaxFileSize)
            return BadRequest("Invalid file size");

        var documentId = Guid.NewGuid();
        var blobName =
            $"{_currentUser.TenantId}/{documentId:N}/content";

        var document = new Document
        {
            Id = documentId,
            TenantId = _currentUser.TenantId,
            BlobName = blobName,
            OriginalFileName = NormalizeFileName(file.FileName),
            ExpectedSize = file.Length,
            Status = DocumentStatus.Uploading,
            CreatedAt = DateTimeOffset.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(cancellationToken);

        var blob = _container.GetBlobClient(blobName);

        try
        {
            await using var input = file.OpenReadStream();

            await _validator.ValidateHeaderAsync(
                input,
                file.FileName,
                cancellationToken);

            if (input.CanSeek)
                input.Position = 0;

            await blob.UploadAsync(
                input,
                overwrite: false,
                cancellationToken: cancellationToken);

            var properties = await blob.GetPropertiesAsync(
                cancellationToken: cancellationToken);

            if (properties.Value.ContentLength != file.Length)
                throw new InvalidDataException("Uploaded size mismatch");

            document.ActualSize = properties.Value.ContentLength;
            document.Status = DocumentStatus.Ready;
            document.UploadedAt = DateTimeOffset.UtcNow;

            await _db.SaveChangesAsync(cancellationToken);

            _logger.LogInformation(
                "Document upload completed {DocumentId} tenant {TenantId} size {Size}",
                document.Id,
                document.TenantId,
                document.ActualSize);

            return Ok(new { document.Id });
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            document.Status = DocumentStatus.Abandoned;
            await TryPersistFailureStateAsync(document.Id, DocumentStatus.Abandoned);
            throw;
        }
        catch (Exception ex)
        {
            document.Status = DocumentStatus.Failed;
            await TryPersistFailureStateAsync(document.Id, DocumentStatus.Failed);

            _logger.LogError(
                ex,
                "Document upload failed {DocumentId} tenant {TenantId}",
                document.Id,
                document.TenantId);

            throw;
        }
    }

    private static string NormalizeFileName(string fileName) =>
        Path.GetFileName(fileName).Trim();

    private Task TryPersistFailureStateAsync(
        Guid documentId,
        DocumentStatus status)
    {
        // Implementation should use a fresh short-lived unit of work
        // because the request DbContext may already be in a failed state.
        return Task.CompletedTask;
    }
}
```

Đối với file multi-GB và traffic lớn, một architecture khác thường đáng cân nhắc là backend cấp SAS ngắn hạn, scope hẹp cho một server-generated blob key, rồi browser upload trực tiếp lên Blob Storage. Backend sau đó verify blob properties/checksum và finalize document state. Hướng này giảm bandwidth qua App Service nhưng thêm complexity cho SAS issuance, CORS, client retry, finalize protocol và cleanup. Không nên mặc định chọn nếu volume chưa cần.

## Giải thích thiết kế sau khi sửa

Payload không còn được materialize thành một `byte[]` khổng lồ trong application. Blob SDK nhận stream và chịu trách nhiệm upload theo cơ chế phù hợp của SDK.

Blob key do server sở hữu và gắn với tenant/document identity. Original filename chỉ là metadata, không quyết định quyền hoặc vị trí object.

Document state machine làm partial failure có thể quan sát và reconcile. Một background cleanup có thể tìm `Uploading/Abandoned/Failed` quá lâu để xóa orphan blob hoặc đánh dấu cần điều tra.

`CancellationToken` được propagate xuống I/O. Tuy nhiên process crash vẫn có thể xảy ra mà không chạy catch block, vì vậy reconciliation job vẫn cần nếu consistency quan trọng.

## Trade-offs

Proxy upload qua backend đơn giản hơn về authorization flow và audit tập trung, nhưng tốn bandwidth/connection time của App Service. Direct-to-Blob upload giảm pressure cho application nhưng tăng complexity phía client và SAS lifecycle.

Persist record `Uploading` trước blob upload có thể tạo SQL rows không bao giờ hoàn tất nếu process chết. Đây là expected intermediate state và phải có cleanup/reconciliation thay vì cố giả vờ toàn bộ workflow atomic.

Content scanning làm tăng latency và infrastructure cost. Chỉ áp dụng mức scanning phù hợp threat model và loại file; có thể quarantine rồi async scan thay vì block request nếu business chấp nhận.

Kiểm tra size sau upload phát hiện một số lỗi nhưng không chứng minh content integrity hoàn toàn. Nếu integrity là requirement, cần checksum/hash contract phù hợp và tránh tính hash bằng cách buffer toàn bộ file.

## Cách kiểm thử

1. **Load test:** chạy nhiều concurrent uploads 500 MB–2 GB; đo process memory, allocations/GC, CPU, request latency và verify memory không tăng tuyến tính theo tổng payload như implementation cũ.
2. **Cancellation test:** client abort giữa upload; xác minh backend nhận cancellation, ngừng work sớm và document không chuyển sang `Ready`.
3. **Failure-path integration test:** Blob upload thành công nhưng SQL finalize fail; xác minh record/blob được reconciliation phát hiện và không downstream processor nào đọc nó như `Ready`.
4. **Security test:** gửi file name/path bất thường và cố gắng chọn blob prefix của tenant khác; xác minh storage key luôn do server generate và không overwrite object ngoài scope.
5. **Validation test:** upload file có extension `.pdf` nhưng signature không phải PDF; xác minh document không được finalize thành `Ready`.

## Quan sát trong production

Theo dõi:

- active uploads và concurrent upload count;
- bytes uploaded/sec;
- upload duration p50/p95/p99 theo size bucket;
- request aborted/cancelled rate;
- App Service memory, GC pause/allocation rate và CPU;
- Blob dependency latency/error rate;
- SQL finalize failure rate;
- số document ở `Uploading`, `Failed`, `Abandoned` quá ngưỡng thời gian;
- orphan blob reconciliation count;
- size mismatch/validation failure count;
- correlation từ request → document id → blob operation → finalize state.

Alert khi memory/GC tăng bất thường, số stuck uploads vượt threshold, hoặc orphan/finalize failures tăng liên tục.

1. Khi nào bạn chuyển từ backend-proxied upload sang direct-to-Blob SAS, và controls nào phải có trước khi mở client upload trực tiếp?
2. Nếu cần tính SHA-256 cho file 2 GB, bạn làm thế nào để không buffer toàn bộ file và vẫn giữ throughput hợp lý?
3. Nếu downstream antivirus scan mất vài phút, bạn thay đổi document state machine và UX như thế nào?

# Code Review Challenge 2 — SQL transaction deadlock khi hai workflow cập nhật cùng dữ liệu theo thứ tự khác nhau

**Chủ đề:** SQL Server, transactions, locking, deadlocks, isolation, transaction scope, indexing, retry, observability, application workflow design  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một enterprise order platform có hai workflows chạy đồng thời:

- `ConfirmOrder`: xác nhận order và reserve inventory;
- `CancelOrder`: hủy order và hoàn inventory.

SQL Server là source of truth. Application dùng explicit transaction để giữ business state nhất quán.

Production có các triệu chứng:

- dưới tải bình thường gần như không lỗi;
- vào giờ cao điểm, API thỉnh thoảng nhận SQL deadlock victim exception;
- retry từ client có lúc thành công;
- deadlock graph cho thấy `Orders` và `Inventory` xuất hiện trong cùng cycle;
- `ConfirmOrder` thường lock `Orders` trước rồi `Inventory`;
- `CancelOrder` thường lock `Inventory` trước rồi `Orders`;
- transaction giữ mở trong lúc gọi một internal HTTP pricing service để ghi audit reason;
- team đề xuất tăng transaction isolation lên `Serializable` để “không còn race condition”;
- một developer khác đề xuất catch mọi SQL exception rồi retry 10 lần ngay lập tức.

Business yêu cầu:

- không được confirm và cancel cùng order thành công đồng thời;
- inventory không được âm;
- HTTP dependency failure không nên giữ database locks lâu hơn cần thiết;
- nếu retry deadlock thì operation phải an toàn và bounded;
- cần evidence từ production thay vì đoán deadlock root cause.

## Đoạn code cần review

```csharp
public sealed class OrderService
{
    private readonly AppDbContext _db;
    private readonly IPricingClient _pricing;

    public OrderService(AppDbContext db, IPricingClient pricing)
    {
        _db = db;
        _pricing = pricing;
    }

    public async Task ConfirmOrderAsync(
        long orderId,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var order = await _db.Orders
            .SingleAsync(x => x.Id == orderId, cancellationToken);

        var inventory = await _db.Inventory
            .SingleAsync(x => x.ProductId == order.ProductId, cancellationToken);

        if (order.Status != OrderStatus.Pending)
            throw new InvalidOperationException("Order is not pending");

        if (inventory.Available < order.Quantity)
            throw new InvalidOperationException("Insufficient inventory");

        inventory.Available -= order.Quantity;
        order.Status = OrderStatus.Confirmed;

        var price = await _pricing.GetCurrentPriceAsync(
            order.ProductId,
            cancellationToken);

        order.ConfirmedPrice = price;

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }

    public async Task CancelOrderAsync(
        long orderId,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var inventory = await _db.Inventory
            .SingleAsync(
                x => x.ProductId == _db.Orders
                    .Where(o => o.Id == orderId)
                    .Select(o => o.ProductId)
                    .Single(),
                cancellationToken);

        var order = await _db.Orders
            .SingleAsync(x => x.Id == orderId, cancellationToken);

        if (order.Status != OrderStatus.Confirmed)
            return;

        inventory.Available += order.Quantity;
        order.Status = OrderStatus.Cancelled;

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề về lock ordering, transaction duration, concurrency correctness và retry strategy.
2. Giải thích một deadlock cycle có thể hình thành khi `ConfirmOrder` và `CancelOrder` chạy đồng thời.
3. Phân tích ảnh hưởng của HTTP call `_pricing.GetCurrentPriceAsync` khi transaction đang giữ locks.
4. Đánh giá đề xuất tăng isolation level lên `Serializable`.
5. Đánh giá đề xuất retry mọi SQL exception 10 lần ngay lập tức.
6. Đề xuất cách giữ lock acquisition order nhất quán giữa workflows.
7. Nêu phương án bảo vệ business invariant khi cùng order bị thao tác concurrent, ví dụ optimistic concurrency/version hoặc conditional update.
8. Phân tích index/query nào cần verify để giảm lock footprint mà không “thêm index mù”.
9. Đề xuất retry policy cho deadlock victim, bao gồm idempotency và backoff.
10. Nêu telemetry/evidence cần thu thập để chứng minh root cause và xác minh fix.

## Câu hỏi gợi mở

1. Nếu transaction A giữ lock trên `Orders` và chờ `Inventory`, còn transaction B giữ lock trên `Inventory` và chờ `Orders`, SQL Server có thể làm gì để phá cycle?
2. HTTP call kéo dài 2 giây có ảnh hưởng gì nếu database locks đã được giữ trước đó?
3. `Serializable` thường làm lock footprint nhỏ hơn hay lớn hơn?
4. Retry deadlock có an toàn nếu operation đã tạo external side effect trước khi transaction fail không?
5. Deadlock khác blocking dài ở điểm nào và telemetry nào giúp phân biệt?

## Kết quả code review tham khảo

### Critical — Hai workflows acquire shared resources theo thứ tự khác nhau

**Vấn đề:** `ConfirmOrder` đọc/lock logical order trước rồi inventory; `CancelOrder` bắt đầu bằng inventory rồi mới order.

**Tại sao xảy ra:** Dưới concurrent write, mỗi transaction có thể giữ lock mà transaction kia cần và đồng thời chờ lock còn lại.

**Ảnh hưởng production:** SQL Server phát hiện deadlock cycle và chọn một transaction làm victim để rollback. API thấy intermittent exception dù từng workflow riêng lẻ chạy đúng.

**Cách sửa:** Chuẩn hóa resource access order giữa workflows, ví dụ luôn xác định/read order trước rồi inventory. Quan trọng là verify actual lock behavior bằng deadlock graph/execution plan thay vì chỉ dựa trên thứ tự dòng C#.

### High — Transaction giữ mở trong lúc gọi HTTP dependency

**Vấn đề:** `ConfirmOrder` gọi pricing service sau khi đã đọc/mutate entities trong transaction.

**Tại sao xảy ra:** Remote I/O latency kéo dài database transaction lifetime.

**Ảnh hưởng production:** Locks tồn tại lâu hơn, blocking/deadlock probability tăng, connection pool bị giữ, và dependency degradation lan sang database contention.

**Cách sửa:** Nếu current price không cần cùng database transaction để bảo vệ invariant, lấy price trước transaction hoặc tách workflow để transaction chỉ bao quanh database-critical section. Nếu price phải được validated atomically theo version/rule, model điều kiện đó trong database operation thay vì giữ transaction chờ HTTP.

### High — Read-check-write có concurrency window cho order state

**Vấn đề:** Hai requests có thể đọc cùng state rồi cùng đưa ra decision nếu isolation/locking không bảo vệ đúng business transition.

**Tại sao xảy ra:** Business invariant đang được kiểm tra ở application memory sau read, không nhất thiết được enforce tại write boundary.

**Ảnh hưởng production:** Concurrent confirm/cancel hoặc duplicate confirm có thể tạo state/inventory update không mong muốn nếu transaction semantics thay đổi hoặc query path khác xuất hiện.

**Cách sửa:** Dùng concurrency token/version hoặc conditional SQL update. Ví dụ transition order chỉ khi `Status = Pending AND Version = expectedVersion`; affected rows = 0 nghĩa là conflict. Inventory decrement cũng cần predicate `Available >= quantity` nếu invariant phải được enforce atomically.

### High — Retry mọi SQL exception là sai classification

**Vấn đề:** Không phải mọi SQL lỗi đều transient hoặc retryable.

**Tại sao xảy ra:** Deadlock victim, timeout, constraint violation, syntax/schema error và permission error có semantics khác nhau.

**Ảnh hưởng production:** Retry storm, tăng load đúng lúc database đang contention, che giấu bug và làm latency tệ hơn.

**Cách sửa:** Chỉ retry các lỗi được xác định transient phù hợp, với số lần bounded, exponential backoff/jitter và cancellation budget. Deadlock retry phải replay toàn bộ transaction từ đầu bằng fresh state.

### High — `Serializable` không phải generic deadlock fix

**Vấn đề:** Tăng isolation có thể giữ nhiều/range locks lâu hơn.

**Tại sao xảy ra:** Isolation level cao hơn giảm một số anomalies bằng cách tăng locking/versioning constraints, không tự sửa inconsistent resource ordering.

**Ảnh hưởng production:** Blocking/deadlock có thể tăng, throughput giảm.

**Cách sửa:** Chọn isolation dựa trên invariant cụ thể. Giảm transaction scope, thống nhất order, dùng optimistic concurrency/conditional writes khi phù hợp và đo actual contention trước khi nâng isolation.

### Medium — Query trong `CancelOrder` khó reasoning và có thể tăng lock/query footprint

**Vấn đề:** Inventory query chứa subquery vào `Orders`, sau đó application query `Orders` lần nữa.

**Tại sao xảy ra:** Workflow truy cập cùng logical data qua nhiều query paths.

**Ảnh hưởng production:** Tăng database round trips, khó đảm bảo resource access order, và execution plan có thể acquire locks theo cách không trực quan.

**Cách sửa:** Load minimal order projection trước để lấy `ProductId` và state/version, sau đó access inventory theo cùng canonical order như confirm. Hoặc dùng stored procedure/explicit SQL cho critical transition nếu cần kiểm soát lock semantics rõ hơn.

### Medium — Không có explicit idempotency semantics cho command retry

**Vấn đề:** Nếu client hoặc server retry `ConfirmOrder`, code chỉ dựa vào state check và exception.

**Tại sao xảy ra:** Command identity không được model hóa.

**Ảnh hưởng production:** Khó distinguish replay của cùng logical operation với một command mới; nếu future flow thêm external side effect, retry sẽ nguy hiểm hơn.

**Cách sửa:** Với command có retry/network ambiguity, cân nhắc operation id/idempotency record hoặc đảm bảo state transition bản thân idempotent theo business semantics.

### Medium — Index strategy chưa được chứng minh bằng plan/deadlock evidence

**Vấn đề:** Code giả định lookup theo `Orders.Id` và `Inventory.ProductId` đủ selective nhưng không nêu uniqueness/indexing.

**Tại sao xảy ra:** Missing/poor index có thể làm scan nhiều rows và tăng lock footprint.

**Ảnh hưởng production:** Blocking/deadlock probability tăng dưới load.

**Cách sửa:** Verify execution plans và schema. `Orders.Id` thường là PK; `Inventory.ProductId` nên có suitable unique/selective index nếu model yêu cầu một row/product. Không thêm index cho mọi cột mà không đo reads/writes/selectivity.

### Medium — Early `return` trong transaction làm semantics không rõ

**Vấn đề:** `CancelOrder` return khi status không phải `Confirmed` mà không explicit commit.

**Tại sao xảy ra:** Dispose transaction sẽ rollback/uncommit transaction, dù không có write. Điều này không sai correctness nhưng flow khó đọc và telemetry không phân biệt idempotent no-op với conflict.

**Ảnh hưởng production:** Operational diagnosis khó; caller có thể tưởng cancellation thành công dù order ở state khác như `Pending` hoặc `Failed`.

**Cách sửa:** Define command outcome rõ: already-cancelled có thể là idempotent success; pending/not-confirmed có thể conflict tùy business rule. Return typed result và log outcome.

### Low — Không có correlation/transaction telemetry cho contention

**Vấn đề:** Code không log operation id, attempt hoặc duration của critical section.

**Tại sao xảy ra:** Database concurrency được xem như implementation detail.

**Ảnh hưởng production:** Khi incident xảy ra, khó correlate API request với deadlock graph và retry attempts.

**Cách sửa:** Instrument command id/order id, transaction duration, retry count, deadlock victim count và dependency timing mà không log sensitive data.

## Phiên bản đề xuất

Một hướng là lấy external pricing trước database-critical section nếu business cho phép, sau đó dùng short transaction và optimistic concurrency/conditional state transition. Dưới đây là minh họa ở application level; exact SQL/concurrency token cần phù hợp schema thực tế.

```csharp
public async Task ConfirmOrderAsync(
    long orderId,
    string operationId,
    CancellationToken cancellationToken)
{
    var snapshot = await _db.Orders
        .AsNoTracking()
        .Where(x => x.Id == orderId)
        .Select(x => new
        {
            x.Id,
            x.ProductId,
            x.Quantity,
            x.Status,
            x.Version
        })
        .SingleAsync(cancellationToken);

    if (snapshot.Status != OrderStatus.Pending)
        throw new OrderConflictException(orderId, snapshot.Status);

    var price = await _pricing.GetCurrentPriceAsync(
        snapshot.ProductId,
        cancellationToken);

    await ExecuteDeadlockRetryAsync(async ct =>
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(ct);

        var order = await _db.Orders
            .SingleAsync(x => x.Id == orderId, ct);

        if (order.Status != OrderStatus.Pending ||
            order.Version != snapshot.Version)
        {
            throw new OrderConflictException(orderId, order.Status);
        }

        var inventory = await _db.Inventory
            .SingleAsync(x => x.ProductId == order.ProductId, ct);

        if (inventory.Available < order.Quantity)
            throw new InsufficientInventoryException(order.ProductId);

        inventory.Available -= order.Quantity;
        order.Status = OrderStatus.Confirmed;
        order.ConfirmedPrice = price;
        order.Version++;
        order.LastOperationId = operationId;

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }, cancellationToken);
}
```

Trong production, một stronger approach có thể dùng database-enforced conditional updates cho inventory và order state, hoặc stored procedure nếu team cần lock semantics dễ kiểm soát hơn. Ví dụ decrement inventory chỉ khi `Available >= @quantity` và kiểm tra affected rows. Điều quan trọng là invariant được enforce ở write boundary, không chỉ bởi check trong C#.

`ExecuteDeadlockRetryAsync` phải:

- chỉ retry deadlock/transient condition đã classify;
- tạo lại unit-of-work/transaction cho mỗi attempt nếu DbContext state không còn an toàn;
- dùng bounded attempts, backoff + jitter;
- tôn trọng total cancellation/deadline;
- không retry validation/business conflicts;
- bảo đảm operation idempotent nếu side effects ngoài DB tồn tại.

## Giải thích thiết kế sau khi sửa

Remote HTTP call được đưa ra ngoài critical database transaction nếu business cho phép, giảm thời gian locks được giữ.

Cả confirm và cancel nên dùng cùng canonical acquisition order: order → inventory. Điều này không chứng minh deadlock hoàn toàn biến mất, nhưng loại bỏ một cycle pattern rõ ràng.

Optimistic version/state check giúp detect stale command thay vì silently overwrite. Với inventory, atomic predicate tại database tốt hơn read-then-check nếu contention cao.

Deadlock được coi là một transient concurrency outcome có thể retry có kiểm soát, không phải exception cần che giấu vô hạn.

## Trade-offs

Lấy price trước transaction tạo possibility price trở nên cũ trước khi commit. Nếu business yêu cầu price phải đúng tại exact commit time, cần version/timestamp contract với pricing source hoặc một rule khác; không nên giữ DB lock chờ remote service chỉ để “chắc chắn”.

Optimistic concurrency hoạt động tốt khi conflict rate vừa phải. Nếu cùng một inventory row là hot spot cực lớn, retries có thể thành retry storm; lúc đó cần đo để cân nhắc serialization/queue/sharding hoặc data-model change.

Stored procedure có thể cho lock/query control rõ hơn nhưng tăng logic trong database và deployment coupling. Không mặc định tốt hơn EF Core; dùng khi critical workflow cần và team vận hành được.

Deadlock retry tăng tail latency. SLO/deadline phải giới hạn tổng số attempt thay vì để retry tự do.

## Cách kiểm thử

1. **Concurrency integration test:** chạy hàng chục `ConfirmOrder`/`CancelOrder` concurrent trên cùng order; xác minh chỉ transition hợp lệ commit và inventory không âm/sai lệch.
2. **Deadlock reproduction test:** dùng controlled transactions acquire resources theo thứ tự ngược để verify retry chỉ áp dụng deadlock victim và replay transaction từ đầu.
3. **Dependency-delay test:** làm pricing call delay vài giây; xác minh transaction/database locks chưa được mở trong thời gian chờ nếu design cho phép price fetch trước.
4. **Failure classification test:** constraint/business conflict không bị retry như deadlock; deadlock retry bounded với backoff và cancellation.
5. **Load test:** đo deadlock rate, lock waits, transaction duration, SQL CPU/reads và API p95/p99 trước/sau fix.

## Quan sát trong production

Thu thập:

- SQL Server deadlock graph/XML deadlock events;
- deadlock victim count theo endpoint/operation;
- lock waits, blocked-process duration và transaction duration;
- execution plan/query duration cho order/inventory lookups;
- retry attempts/success/exhausted count;
- API p50/p95/p99 và timeout rate;
- pricing dependency latency tách khỏi SQL transaction latency;
- order conflict rate và inventory invariant violations;
- correlation id/operation id từ API request đến DB command/retry attempt.

Deadlock graph là evidence quan trọng để xác định exact resources/index keys và lock modes tham gia cycle. Không nên kết luận chỉ từ stack trace “deadlock victim”.

## Câu hỏi phỏng vấn mở rộng

1. Nếu sau khi thống nhất lock order vẫn còn deadlock trên secondary indexes, bạn sẽ đọc deadlock graph và execution plan theo thứ tự nào?
2. Khi nào `READ COMMITTED SNAPSHOT` có thể giảm blocking, và tại sao nó không tự giải quyết write-write conflict?
3. Nếu inventory row của một flash-sale product trở thành hot spot với hàng nghìn requests/giây, bạn sẽ đo gì trước khi thay đổi architecture?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- File lớn nên được xử lý theo streaming/bounded-resource model; buffering toàn payload trong memory tạo resource amplification rất nhanh dưới concurrency.
- Cross-system workflow Blob Storage + SQL không có atomic transaction chung; cần explicit state machine và reconciliation cho partial failure.
- Storage key, path và authorization boundary phải do server kiểm soát, không dựa trực tiếp vào client-provided file name/folder.
- Database deadlock là cycle của resource waits; cần evidence từ deadlock graph và lock/query behavior thay vì đoán từ exception.
- Transaction nên ngắn và không giữ database locks trong lúc chờ network dependency nếu business invariant không yêu cầu.
- Consistent lock order, database-enforced invariants và bounded retry thường hiệu quả hơn việc tăng isolation hoặc retry mù.

## Mẫu tư duy cần nhớ

- **Stream large payloads; do not materialize them unless truly necessary.**
- **Cross-system consistency cần state machine + reconciliation, không phải giả định atomicity.**
- **Keep database transactions short and deterministic.**
- **Use evidence from lock/deadlock telemetry before changing isolation or indexes.**
- **Retry only classified transient failures, with idempotency and a bounded budget.**
