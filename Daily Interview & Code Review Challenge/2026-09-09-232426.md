# Code Review Challenge 1 — Port legacy ASP.NET sang .NET 8 nhưng giữ static tenant context, sync-over-async và fire-and-forget work

**Chủ đề:** C#, .NET 8, ASP.NET Core, .NET Framework modernization, async/await, request context, concurrency, BackgroundService, reliability, IIS/App Service migration  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một hệ thống approval nội bộ được xây dựng từ nhiều năm trước bằng .NET Framework 4.5 và ASP.NET MVC trên IIS. Team đang migrate dần sang ASP.NET Core .NET 8 mà không rewrite toàn bộ hệ thống.

Trong phase đầu, một controller cũ được “port cơ học” sang ASP.NET Core. Hệ thống chạy multi-tenant theo company. Tenant được lấy từ authenticated user sau login. Mỗi request có thể gọi một HR API bên ngoài để lấy employee metadata và gửi audit event sau khi approval được cập nhật.

Sau khi deploy bản .NET 8 lên Azure App Service với 4 instances, production xuất hiện:

- thỉnh thoảng request của company A ghi audit với tenant ID của company B;
- p95/p99 tăng mạnh khi HR API chậm;
- CPU không cao nhưng request queue tăng;
- restart hoặc scale-in đôi lúc làm mất audit events;
- một số approval đã commit DB nhưng audit chưa được gửi;
- khi traffic tăng, có lúc API gần như đứng dù downstream HR API vẫn còn phản hồi;
- team đề xuất tăng ThreadPool minimum threads và tiếp tục dùng static context “vì legacy code đang dùng như vậy”.

Business yêu cầu:

- tenant context tuyệt đối không được cross-request/cross-user;
- approval DB update là source-of-truth;
- audit event không được silently mất sau khi DB commit;
- external HR API có thể chậm hoặc timeout;
- migration phải incremental, có rollback path;
- không được assume full rewrite là phương án tốt nhất.

## Đoạn code cần review

```csharp
public static class LegacyTenantContext
{
    public static Guid CurrentTenantId { get; set; }
}

[Authorize]
[ApiController]
[Route("api/approvals")]
public sealed class ApprovalsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly HttpClient _hrClient;
    private readonly IAuditClient _auditClient;

    public ApprovalsController(
        AppDbContext db,
        HttpClient hrClient,
        IAuditClient auditClient)
    {
        _db = db;
        _hrClient = hrClient;
        _auditClient = auditClient;
    }

    [HttpPost("{approvalId:guid}/approve")]
    public IActionResult Approve(
        Guid approvalId,
        CancellationToken cancellationToken)
    {
        LegacyTenantContext.CurrentTenantId =
            Guid.Parse(User.FindFirst("tenant_id")!.Value);

        var employeeId = User.FindFirst("employee_id")!.Value;

        var employee = _hrClient
            .GetFromJsonAsync<EmployeeDto>(
                $"/api/employees/{employeeId}",
                cancellationToken)
            .Result;

        var approval = _db.Approvals
            .Single(x =>
                x.Id == approvalId &&
                x.TenantId == LegacyTenantContext.CurrentTenantId);

        approval.Status = ApprovalStatus.Approved;
        approval.ApprovedBy = employee!.DisplayName;
        approval.ApprovedAtUtc = DateTime.UtcNow;

        _db.SaveChanges();

        Task.Run(async () =>
        {
            await _auditClient.SendAsync(new AuditEvent
            {
                TenantId = LegacyTenantContext.CurrentTenantId,
                ApprovalId = approval.Id,
                Action = "Approved",
                Actor = employee.DisplayName
            });
        });

        return Ok();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, concurrency, async, reliability, security và migration design.
2. Giải thích vì sao `static CurrentTenantId` có thể bị request khác ghi đè khi application xử lý concurrent requests.
3. Phân tích `GetFromJsonAsync(...).Result` trong ASP.NET Core và vì sao sync-over-async vẫn có thể làm throughput xấu dù không còn classic ASP.NET SynchronizationContext như .NET Framework.
4. Review `Task.Run` fire-and-forget cho audit side effect.
5. Phân tích failure window giữa `SaveChanges()` và audit delivery.
6. Đề xuất incremental modernization path thay vì rewrite toàn bộ controller/domain ngay lập tức.
7. Đề xuất tests, telemetry và rollout/rollback strategy.

## Câu hỏi gợi mở

1. `static` field có scope theo request, user, instance hay process?
2. Nếu request A set tenant A rồi request B set tenant B trước khi Task.Run của request A đọc field, audit event sẽ chứa tenant nào?
3. `.Result` có cần deadlock mới trở thành production problem không?
4. Nếu process recycle ngay sau `SaveChanges()` nhưng trước khi background lambda chạy, audit event ở đâu?
5. Nếu audit API timeout, cơ chế nào đảm bảo retry không tạo duplicate event?

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Static tenant context gây cross-request data contamination

**Vấn đề:** `LegacyTenantContext.CurrentTenantId` là mutable static state dùng chung trong toàn process.

**Tại sao xảy ra:** Nhiều requests chạy concurrent trên cùng instance. Request A có thể set tenant A, request B set tenant B, sau đó request A tiếp tục đọc lại field đã bị đổi.

**Ảnh hưởng production:** Query, audit hoặc bất kỳ logic downstream nào đọc field này có thể dùng sai tenant. Đây là data-isolation/security bug, không chỉ là race nhỏ.

**Cách sửa:** Tenant context phải là request-scoped immutable state được resolve từ authenticated principal và validate server-side. Có thể tạo `ICurrentTenant` scoped service. Không giữ tenant/user identity trong static mutable field.

### Critical — Fire-and-forget `Task.Run` không cung cấp durability cho audit event

**Vấn đề:** Audit được gửi trong background task không được await và không được persist.

**Tại sao xảy ra:** Request trả `200 OK` sau DB commit, còn audit chỉ tồn tại trong memory queue của process/ThreadPool.

**Ảnh hưởng production:** Process recycle, App Service scale-in, deployment, crash hoặc host shutdown có thể làm task chưa chạy hoặc bị cắt giữa chừng. Audit silently mất dù approval đã commit.

**Cách sửa:** Nếu audit là required integration side effect, persist một outbox record cùng transaction với approval update. Background worker đọc outbox và gửi audit với retry/idempotency. Nếu business chấp nhận best-effort audit thì phải ghi rõ contract; scenario này yêu cầu không silently mất nên fire-and-forget không phù hợp.

### High — Sync-over-async bằng `.Result` làm giảm throughput

**Vấn đề:** Request thread bị block trong lúc HTTP I/O đang chờ.

**Tại sao xảy ra:** `GetFromJsonAsync` vốn asynchronous nhưng `.Result` biến request path thành synchronous wait.

**Ảnh hưởng production:** Khi HR API latency tăng, nhiều ThreadPool threads bị giữ ở trạng thái chờ. Request queue tăng, ThreadPool phải inject thêm threads và tail latency xấu hơn. Không cần classic ASP.NET deadlock để đây trở thành production issue.

**Cách sửa:** Chuyển action thành `async Task<IActionResult>` và `await` I/O end-to-end. Propagate `CancellationToken` hợp lý.

### High — Approval query phụ thuộc static tenant state thay vì local verified value

**Vấn đề:** Ngay cả query chính cũng đọc lại `LegacyTenantContext.CurrentTenantId`.

**Tại sao xảy ra:** Legacy global context đã trở thành implicit dependency.

**Ảnh hưởng production:** Race có thể khiến request đọc approval của tenant khác nếu ID collision/authorization model cho phép, hoặc trả sai NotFound/error. Tệ hơn, các call khác trong request có thể bị scope sai.

**Cách sửa:** Resolve tenant một lần thành local immutable value từ `ICurrentTenant`; tất cả data access phải dùng local/scoped context đó.

### High — Failure window giữa DB commit và audit delivery không có recovery

**Vấn đề:** `SaveChanges()` commit trước, audit gửi sau ở process memory.

**Tại sao xảy ra:** Hai side effects nằm ở hai systems nhưng không có durable handoff.

**Ảnh hưởng production:** DB thành công + process crash = audit mất. Audit timeout + manual retry có thể tạo duplicate nếu provider không idempotent.

**Cách sửa:** Outbox record + approval update trong cùng SQL transaction. Worker send theo stable event ID. Receiver/client nên hỗ trợ idempotency hoặc deduplicate theo event ID.

### High — Không await audit nên exception có thể không được quan sát đúng

**Vấn đề:** Exception trong `Task.Run` không đi vào request error handling và có thể chỉ xuất hiện như unobserved/background logging tùy implementation.

**Tại sao xảy ra:** Background task bị tách khỏi lifecycle/request pipeline.

**Ảnh hưởng production:** Monitoring có thể ghi request success trong khi audit fail. Incident metrics không phản ánh business incompleteness.

**Cách sửa:** Durable worker có structured logs, retry state, dead-letter/failed state và metrics rõ ràng.

### Medium — Claim parsing dùng null-forgiving và `Guid.Parse` không có failure classification

**Vấn đề:** Code assume claim luôn tồn tại và hợp lệ.

**Tại sao xảy ra:** Authentication và authorization contract chưa được enforce rõ qua policy.

**Ảnh hưởng production:** Missing/malformed claim có thể thành 500 thay vì 401/403 hoặc policy failure có ý nghĩa.

**Cách sửa:** Dùng policy-based authorization/claim validation hoặc tenant resolver fail-closed với response phù hợp.

### Medium — Sync EF Core calls trong request path làm mất lợi ích async I/O

**Vấn đề:** `Single` và `SaveChanges` chạy synchronous database I/O.

**Tại sao xảy ra:** Port cơ học từ legacy code.

**Ảnh hưởng production:** Under load, threads tiếp tục bị block bởi DB I/O.

**Cách sửa:** `SingleAsync`/`SaveChangesAsync` khi request path đã async. Không đổi chỉ vì style; mục tiêu là tránh blocking I/O trên high-concurrency server path.

### Medium — External HR API chưa có timeout/resilience contract rõ

**Vấn đề:** Snippet chỉ truyền request cancellation token, chưa thể hiện timeout budget, retry classification hay degraded behavior.

**Tại sao xảy ra:** Legacy integration thường chỉ xử lý happy path.

**Ảnh hưởng production:** Slow dependency kéo dài request latency. Blind retry nếu được thêm sau này có thể tăng load hoặc duplicate side effects nếu endpoint không idempotent.

**Cách sửa:** Đặt bounded timeout theo request SLO, retry chỉ với transient conditions phù hợp, có backoff/jitter nếu cần, và đo dependency latency/error rate. Với read-only employee lookup, retry strategy có thể khác write API.

### Medium — Migration chưa có compatibility/rollout boundary

**Vấn đề:** Port code nhưng giữ legacy globals/fire-and-forget semantics khiến runtime behavior khác môi trường cũ theo cách khó quan sát.

**Tại sao xảy ra:** Migration được coi là syntax/framework conversion thay vì behavior migration.

**Ảnh hưởng production:** Regression xuất hiện sau scale-out hoặc restart dù functional tests vẫn pass.

**Cách sửa:** Tạo characterization tests cho legacy behavior, tách tenant resolution, async I/O và audit delivery thành từng migration step có observability và rollback riêng.

## Phiên bản đề xuất

Một bước modernization tương đối nhỏ nhưng loại ba rủi ro chính: scoped tenant context, async end-to-end và transactional outbox.

```csharp
[Authorize]
[ApiController]
[Route("api/approvals")]
public sealed class ApprovalsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly HttpClient _hrClient;
    private readonly ICurrentTenant _currentTenant;

    public ApprovalsController(
        AppDbContext db,
        HttpClient hrClient,
        ICurrentTenant currentTenant)
    {
        _db = db;
        _hrClient = hrClient;
        _currentTenant = currentTenant;
    }

    [HttpPost("{approvalId:guid}/approve")]
    public async Task<IActionResult> Approve(
        Guid approvalId,
        CancellationToken cancellationToken)
    {
        var tenantId = _currentTenant.RequireTenantId();
        var employeeId = User.FindFirst("employee_id")?.Value;

        if (string.IsNullOrWhiteSpace(employeeId))
            return Forbid();

        var employee = await _hrClient
            .GetFromJsonAsync<EmployeeDto>(
                $"/api/employees/{employeeId}",
                cancellationToken);

        if (employee is null)
            return Problem("Employee metadata unavailable");

        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var approval = await _db.Approvals.SingleOrDefaultAsync(
            x => x.Id == approvalId && x.TenantId == tenantId,
            cancellationToken);

        if (approval is null)
            return NotFound();

        approval.Status = ApprovalStatus.Approved;
        approval.ApprovedBy = employee.DisplayName;
        approval.ApprovedAtUtc = DateTime.UtcNow;

        var eventId = Guid.NewGuid();

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = eventId,
            Type = "ApprovalApproved",
            Payload = JsonSerializer.Serialize(new AuditEvent
            {
                EventId = eventId,
                TenantId = tenantId,
                ApprovalId = approval.Id,
                Action = "Approved",
                Actor = employee.DisplayName
            }),
            CreatedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
        await transaction.CommitAsync(cancellationToken);

        return Ok();
    }
}
```

Outbox worker cần claim/process records an toàn khi nhiều application instances chạy đồng thời, retry với backoff phù hợp, và đánh dấu sent sau khi audit endpoint xác nhận. Nếu audit endpoint hỗ trợ idempotency key, dùng stable `EventId`; nếu không, cần receiver-side deduplication hoặc contract khác để tránh duplicate business audit.

## Giải thích thiết kế sau khi sửa

Tenant context được đưa từ implicit static state về scoped dependency/local value. Điều này giảm blast radius mà không yêu cầu rewrite toàn bộ domain.

Async được áp dụng end-to-end cho network/database I/O để request thread không bị block trong lúc chờ.

Approval update và outbox record cùng transaction SQL nên trạng thái “approval committed nhưng không có durable audit intent” bị loại bỏ. Việc gửi audit vẫn eventual nhưng recoverable.

Đây là incremental modernization: trước tiên khóa correctness/reliability semantics, sau đó mới xem xét Clean Architecture, CQRS hay refactor lớn hơn nếu evidence cho thấy cần.

## Trade-offs

- **Outbox:** tăng table, worker, retry/cleanup/monitoring complexity nhưng đổi lại có durable handoff.
- **Async end-to-end:** code path thay đổi rộng hơn một chút và cần tránh mixing sync/async ở downstream layers.
- **Scoped tenant service:** thêm abstraction nhưng loại global state nguy hiểm.
- **HR call trong request:** giữ UX đơn giản nhưng request latency phụ thuộc HR API; nếu requirement cho phép, có thể cache/reference employee metadata hoặc tách lookup khỏi critical path.
- **Incremental migration:** mất thời gian duy trì interoperability tạm thời nhưng giảm rollout risk so với big-bang rewrite.

## Cách kiểm thử

1. **Concurrency test:** chạy hàng trăm requests từ nhiều tenants trên cùng instance; xác minh không có tenant contamination trong DB/outbox.
2. **Failure-path integration test:** commit approval rồi kill process trước audit worker send; sau restart outbox vẫn được gửi.
3. **Dependency latency test:** inject HR API latency/timeout; đo request throughput, ThreadPool queue và p95/p99 giữa `.Result` và `await` implementation.
4. **Idempotency test:** làm audit response timeout sau khi receiver đã nhận event; retry cùng `EventId` không tạo duplicate logical audit.
5. **Migration regression test:** chạy characterization tests trên critical approval flows của legacy và modern implementation trước rollout.

## Quan sát trong production

- ASP.NET Core request p50/p95/p99 và request queue;
- ThreadPool thread count/queue length khi HR dependency chậm;
- HR API dependency duration, timeout/error rate;
- SQL duration/connection pool pressure;
- outbox pending count, oldest-message age, retry count và permanent failures;
- audit send latency và duplicate-detection count;
- structured logs có tenant ID, approval ID, event ID, correlation ID nhưng không log sensitive claims/token;
- deployment version + instance ID để xác định lỗi chỉ xuất hiện khi scale-out hay không.

# Code Review Challenge 2 — Cosmos DB partition key theo status tạo hot partition, query fan-out và RU spike khi traffic tăng

**Chủ đề:** Azure Cosmos DB, C#, document modeling, partition key, hot partition, RU consumption, query patterns, point reads, pagination, consistency, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một notification service mới đang được đánh giá để dùng Azure Cosmos DB thay cho SQL cho phần lưu notification history. Đây là một design alternative đang được xem xét, không giả định rằng mọi workload trước đây đã chạy Cosmos DB.

Mỗi notification có:

- `id`;
- `userId`;
- `tenantId`;
- `status`: `Unread`, `Read`, `Deleted`;
- `createdAtUtc`;
- payload nhỏ vài KB.

Traffic hiện tại khoảng vài triệu notifications/tháng. Read pattern chính:

1. lấy 20 notification mới nhất của một user;
2. mark một notification là `Read`;
3. đếm unread theo user;
4. cleanup dữ liệu cũ theo retention policy.

Team tạo container với partition key `/status` vì cho rằng chỉ có ba giá trị nên dễ query. Production test cho thấy:

- partition `Unread` nhận phần lớn writes;
- RU consumption tăng nhanh khi load test;
- query “latest 20 notifications của user” đắt hơn dự kiến;
- latency tăng khi unread backlog lớn;
- một developer đề xuất tăng throughput thật cao và thêm Redis trước khi xem lại data model.

## Đoạn code cần review

```csharp
public sealed class NotificationRepository
{
    private readonly Container _container;

    public NotificationRepository(Container container)
    {
        _container = container;
    }

    public async Task CreateAsync(
        NotificationDocument notification,
        CancellationToken cancellationToken)
    {
        await _container.CreateItemAsync(
            notification,
            new PartitionKey(notification.Status),
            cancellationToken: cancellationToken);
    }

    public async Task<IReadOnlyList<NotificationDocument>>
        GetLatestForUserAsync(
            Guid userId,
            CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT TOP 20 * FROM c " +
            "WHERE c.userId = @userId " +
            "ORDER BY c.createdAtUtc DESC")
            .WithParameter("@userId", userId.ToString());

        var iterator = _container.GetItemQueryIterator<NotificationDocument>(
            query);

        var items = new List<NotificationDocument>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            items.AddRange(page);
        }

        return items;
    }

    public async Task MarkReadAsync(
        NotificationDocument notification,
        CancellationToken cancellationToken)
    {
        notification.Status = "Read";

        await _container.ReplaceItemAsync(
            notification,
            notification.Id,
            new PartitionKey(notification.Status),
            cancellationToken: cancellationToken);
    }
}
```

Container configuration:

```text
Partition key: /status
Default indexing policy
Autoscale throughput enabled
```

## Nhiệm vụ của ứng viên

1. Xác định vấn đề data modeling, partitioning, correctness, performance và cost.
2. Giải thích vì sao `/status` có cardinality rất thấp và có thể tạo hot logical partition.
3. Phân tích query latest-by-user khi partition key không chứa `userId`.
4. Review `MarkReadAsync`: việc đổi giá trị partition key có thể được xử lý như một replace đơn giản hay cần model/workflow khác?
5. Đề xuất partition key phù hợp hơn dựa trên dominant access patterns.
6. Phân tích khi nào point read tốt hơn query.
7. Đề xuất pagination, indexing, TTL/retention và production telemetry.

## Câu hỏi gợi mở

1. Phần lớn notifications ban đầu có status nào?
2. Query có biết partition key value để route tới một logical partition không?
3. Nếu partition key là thuộc tính tham gia identity/placement của item, chuyện gì xảy ra khi đổi `Unread` → `Read`?
4. User-based partition key có phù hợp hơn không, và nếu một user cực lớn thì có trade-off gì?
5. Tăng RU hoặc thêm Redis có sửa root cause của poor partitioning không?

## Gợi ý

### Gợi ý 1

Bắt đầu từ **access pattern → partition key → item identity → query routing**, không bắt đầu từ throughput setting.

### Gợi ý 2

Hãy xem `status` như mutable business state. Mutable, low-cardinality field thường là tín hiệu đáng nghi khi dùng trực tiếp làm partition key cho workload này.

### Critical — `/status` là partition key low-cardinality và tạo hotspot rõ ràng

**Vấn đề:** Chỉ có vài giá trị `Unread`, `Read`, `Deleted`, trong đó writes ban đầu tập trung gần như toàn bộ vào `Unread`.

**Tại sao xảy ra:** Partitioning không phân phối workload theo high-cardinality dimension mà gom nhiều users vào cùng logical partition.

**Ảnh hưởng production:** Một logical partition trở thành bottleneck về storage/throughput characteristics và làm RU/latency không scale đều theo tổng provisioned throughput.

**Cách sửa:** Chọn partition key dựa trên dominant access pattern và cardinality/distribution. Với scenario user-centric, `/userId` hoặc hierarchical/compound strategy phù hợp hơn cần được đánh giá, tùy tenant model, per-user data volume và current Cosmos DB capabilities/configuration.

### Critical — `MarkReadAsync` dùng partition key mới cho item đã được tạo dưới partition key cũ

**Vấn đề:** Item được tạo với partition key `Unread`, sau đó object đổi `Status = "Read"` và code gọi replace với partition key `Read`.

**Tại sao xảy ra:** Code giả định partition key là mutable routing field giống column thông thường.

**Ảnh hưởng production:** Replace không thể đơn giản “di chuyển” item sang logical partition khác bằng cách đổi partition key value. Operation có thể fail vì item identity phải được address bằng partition key hiện tại; thay đổi partition placement thường cần create-new/delete-old hoặc data model tránh partition key mutable.

**Cách sửa:** Không dùng mutable `status` làm partition key trong model này. Chọn stable key như user/tenant-user boundary. Sau đó `status` chỉ là mutable indexed property.

### High — Latest-by-user query không scope partition key nên thành cross-partition query

**Vấn đề:** Query filter theo `userId` nhưng container partition theo `status`.

**Tại sao xảy ra:** Query pattern và partitioning không align.

**Ảnh hưởng production:** Query engine phải fan out qua partitions thay vì route trực tiếp tới user partition. Cost/latency tăng theo scale và data distribution.

**Cách sửa:** Nếu read pattern chủ đạo là per-user history, partition theo stable user-centric key để query có partition key scope. Query options nên truyền partition key khi biết.

### High — `TOP 20` không đồng nghĩa iterator chỉ luôn trả đúng 20 items hiệu quả

**Vấn đề:** Code vẫn loop toàn bộ iterator pages và không đặt rõ pagination contract/continuation behavior cho API.

**Tại sao xảy ra:** SQL-like mental model được áp sang distributed query mà không thiết kế continuation token/page boundary.

**Ảnh hưởng production:** API khó mở rộng sang next page; query cost/latency khó kiểm soát; client có thể yêu cầu deep browsing bằng offset pattern không phù hợp.

**Cách sửa:** Thiết kế cursor/continuation-token pagination. Đọc page size phù hợp, trả continuation token opaque cho client nếu product requirement cần next page.

### High — Đề xuất “thêm Redis” che poor data model thay vì sửa root cause

**Vấn đề:** Cache được đề xuất trước khi query routing/partitioning đúng.

**Tại sao xảy ra:** Team coi high RU như pure read-volume issue.

**Ảnh hưởng production:** Cache có thể giảm một số reads nhưng writes vẫn hotspot, invalidation phức tạp hơn và query pattern gốc vẫn đắt khi cache miss.

**Cách sửa:** Sửa partitioning/data model trước. Chỉ thêm cache khi measured workload và freshness requirement chứng minh benefit.

### High — Unread count có thể trở thành expensive aggregate nếu query trực tiếp lớn dần

**Vấn đề:** Requirement đếm unread theo user chưa có design riêng.

**Tại sao xảy ra:** Team assume có thể query aggregate trực tiếp mọi lúc.

**Ảnh hưởng production:** Khi history lớn, repeated count queries có thể tiêu RU đáng kể.

**Cách sửa:** Đo thực tế trước. Nếu count thường xuyên và scale lớn, có thể giữ counter/materialized state per user với concurrency semantics rõ; hoặc query trong user partition nếu volume vẫn hợp lý. Không pre-optimize nếu data nhỏ.

### Medium — Không có partition-aware point-read API cho lookup theo ID

**Vấn đề:** Repository tập trung query nhưng chưa model `(id, partitionKey)` như resource identity.

**Tại sao xảy ra:** Thiết kế giống relational repository abstraction chung.

**Ảnh hưởng production:** Những operation có đủ `id + partition key` có thể bị implement thành query tốn RU hơn point read.

**Cách sửa:** Khi caller biết item ID và stable partition key, dùng point read/replace với đúng partition key. Repository API nên phản ánh Cosmos access pattern thay vì che hết bằng generic abstraction.

### Medium — Retention chưa tận dụng TTL/data lifecycle semantics

**Vấn đề:** Cleanup requirement có thể bị triển khai thành scan/delete job nếu không thiết kế trước.

**Tại sao xảy ra:** Retention bị coi là operation ứng dụng thông thường.

**Ảnh hưởng production:** Cleanup scans consume RU và vận hành phức tạp.

**Cách sửa:** Đánh giá Cosmos DB TTL theo retention requirement. Nếu business cần archive trước delete, thiết kế lifecycle riêng; không bật TTL mù nếu audit/compliance yêu cầu giữ dữ liệu khác nhau theo tenant.

### Medium — Indexing policy chưa được review theo query workload

**Vấn đề:** Dùng default indexing mà chưa xác định field nào cần sort/filter/query.

**Tại sao xảy ra:** Container configuration để mặc định trước khi benchmark.

**Ảnh hưởng production:** Có thể index fields không cần thiết hoặc thiếu composite indexing cho query pattern cụ thể, làm write RU/query efficiency không tối ưu.

**Cách sửa:** Bắt đầu bằng query workload thật, quan sát index metrics/query diagnostics rồi tune. Không tối ưu indexing chỉ bằng phỏng đoán.

### Medium — Telemetry chưa theo dõi RU theo operation/partition key pattern

**Vấn đề:** Team chỉ nhìn aggregate RU tăng.

**Tại sao xảy ra:** Không có request-charge/query diagnostics breakdown.

**Ảnh hưởng production:** Khó phân biệt hot partition, fan-out query, indexing cost hay traffic increase.

**Cách sửa:** Track request charge, latency, throttling/429, retry count, operation type, query vs point read, hot-key distribution và diagnostics có sampling phù hợp.

## Phiên bản đề xuất

Ví dụ dưới đây dùng `userId` làm stable partition key cho scenario user-centric. Đây là recommendation theo assumptions hiện tại; nếu một user có thể tạo volume cực lớn hoặc tenant isolation/throughput model khác, cần đánh giá hierarchical key/bucketing strategy thay vì mặc định một key duy nhất.

```csharp
public sealed class NotificationRepository
{
    private readonly Container _container;

    public NotificationRepository(Container container)
    {
        _container = container;
    }

    public async Task CreateAsync(
        NotificationDocument notification,
        CancellationToken cancellationToken)
    {
        await _container.CreateItemAsync(
            notification,
            new PartitionKey(notification.UserId),
            cancellationToken: cancellationToken);
    }

    public async Task<NotificationDocument?> GetAsync(
        string userId,
        string notificationId,
        CancellationToken cancellationToken)
    {
        try
        {
            var response = await _container.ReadItemAsync<NotificationDocument>(
                notificationId,
                new PartitionKey(userId),
                cancellationToken: cancellationToken);

            return response.Resource;
        }
        catch (CosmosException ex)
            when (ex.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
    }

    public async Task<IReadOnlyList<NotificationDocument>>
        GetLatestForUserAsync(
            string userId,
            CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT TOP 20 * FROM c " +
            "WHERE c.userId = @userId " +
            "ORDER BY c.createdAtUtc DESC")
            .WithParameter("@userId", userId);

        using var iterator =
            _container.GetItemQueryIterator<NotificationDocument>(
                query,
                requestOptions: new QueryRequestOptions
                {
                    PartitionKey = new PartitionKey(userId),
                    MaxItemCount = 20
                });

        if (!iterator.HasMoreResults)
            return Array.Empty<NotificationDocument>();

        var page = await iterator.ReadNextAsync(cancellationToken);
        return page.Resource.ToList();
    }

    public async Task MarkReadAsync(
        NotificationDocument notification,
        CancellationToken cancellationToken)
    {
        notification.Status = "Read";

        await _container.ReplaceItemAsync(
            notification,
            notification.Id,
            new PartitionKey(notification.UserId),
            cancellationToken: cancellationToken);
    }
}
```

Container partition key giả định đổi thành `/userId`. Nếu application là multi-tenant và `userId` chỉ unique trong tenant, stable key phải bao gồm tenant dimension theo data model thực tế, ví dụ một synthetic `tenantUserKey` hoặc hierarchical approach phù hợp.

## Giải thích thiết kế sau khi sửa

Partition key được align với dominant read/write ownership: notifications chủ yếu được tạo, đọc và update theo user.

`status` trở lại đúng vai trò mutable business property. Mark-read không còn cố thay đổi placement của item.

Point read được dùng khi caller biết cả `id` và partition key. Latest query được scope đúng partition nên tránh cross-partition fan-out theo assumptions hiện tại.

Cache chưa được thêm vì chưa có evidence query đúng partition vẫn không đáp ứng SLO/cost target.

## Trade-offs

- **Partition theo user:** rất tự nhiên cho per-user reads, nhưng một user có volume cực lớn có thể trở thành hot/key-heavy case.
- **Synthetic tenant-user key:** isolation rõ hơn nhưng application phải consistently derive key.
- **Hierarchical/bucketing strategy:** scale tốt hơn trong một số workload nhưng tăng complexity truy vấn và migration.
- **Materialized unread counter:** read rẻ hơn nhưng thêm consistency/concurrency logic.
- **TTL:** giảm cleanup complexity nhưng có thể không phù hợp với archive/compliance requirements.
- **Redis:** có thể hữu ích cho ultra-hot reads nhưng chỉ sau khi partition/query model đã đúng và freshness semantics rõ.

## Cách kiểm thử

1. **Load test:** tạo/read notifications cho nhiều users với skewed distribution; so RU/latency giữa `/status` và user-centric partitioning.
2. **Hot-user test:** một user có traffic cao bất thường; quan sát throttling và xác định khi nào cần bucketing/hierarchical strategy.
3. **Correctness test:** mark `Unread → Read` giữ nguyên item identity và không cần cross-partition move.
4. **Query test:** latest-20 query có partition key scope; ghi lại request charge và diagnostics.
5. **Failure/throttling test:** inject/observe 429 throttling, xác minh SDK retry behavior phù hợp và API SLO/telemetry không che latency amplification.

## Quan sát trong production

- RU/request theo operation type;
- 429/throttling rate và retry latency;
- p50/p95/p99 cho create, point read, latest query, mark-read;
- query diagnostics/fan-out indicators;
- logical partition traffic distribution/hot-key signals;
- document size distribution;
- continuation-token/page usage;
- unread count strategy cost;
- TTL deletion/lifecycle metrics nếu dùng;
- Azure Monitor alerts cho throttling và sustained RU saturation.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Modernization không chỉ là đổi target framework; phải giữ và kiểm chứng concurrency, lifecycle, failure và deployment semantics.
- Request/user/tenant context không được đặt trong mutable static state.
- Sync-over-async có thể làm throughput xấu nghiêm trọng ngay cả khi không xảy ra classic deadlock.
- Business side effect quan trọng cần durable handoff; `Task.Run` trong request không phải queue bền vững.
- Cosmos DB partition key phải xuất phát từ access pattern, cardinality và data distribution.
- Mutable low-cardinality state như `status` thường là partition-key choice kém cho user-centric workload.
- Tăng throughput hoặc thêm cache không sửa được root cause của poor partitioning.

## Mẫu tư duy cần nhớ

- Preserve behavior before refactoring architecture during modernization.
- Never store request identity in global mutable state.
- Durable side effects require persisted intent and idempotent recovery.
- Design partition keys from dominant access patterns, not from convenient fields.
- Fix data/query shape before adding cache or throughput.
