# Code Review Challenge 1 — Hangfire job gửi email bị thực thi lặp khi retry

**Chủ đề:** Background jobs, idempotency, transaction handling, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để xử lý email thông báo sau khi một workflow được phê duyệt. Mỗi lần phê duyệt, API enqueue một job. Production thỉnh thoảng ghi nhận người dùng nhận 2–3 email giống nhau, đặc biệt khi dịch vụ email timeout hoặc worker restart. Database cho thấy bản ghi `Notification` cuối cùng vẫn có trạng thái `Sent`.

Hệ thống chạy nhiều Hangfire workers trên hai application instances. Business chấp nhận retry khi lỗi tạm thời nhưng không muốn gửi trùng email.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task SendAsync(long notificationId)
    {
        var notification = await _db.Notifications
            .SingleAsync(x => x.Id == notificationId);

        if (notification.Status == "Sent")
            return;

        notification.AttemptCount++;
        notification.LastAttemptAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        await _emailSender.SendAsync(
            notification.To,
            notification.Subject,
            notification.Body);

        notification.Status = "Sent";
        notification.SentAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Notification {NotificationId} sent to {Recipient}",
            notification.Id,
            notification.To);
    }
}
```

## Gợi ý

### Gợi ý 1

### Gợi ý 2

Phân tích từng crash point giữa: claim job → DB write → external side effect → DB write cuối.

## Kết quả code review tham khảo

### 1. External side effect không idempotent

- **Problem:** retry có thể gọi `SendAsync` nhiều lần cho cùng notification.
- **Why it happens:** email có thể đã được provider chấp nhận nhưng process lỗi trước khi lưu `Sent`.
- **Production impact:** gửi email trùng.
- **Severity:** Critical
- **Recommended fix:** nếu provider hỗ trợ idempotency key, gửi một stable key như `notification:{id}`; nếu không, phải chấp nhận giới hạn của at-least-once và thiết kế deduplication ở boundary phù hợp.

### 2. Race condition giữa nhiều workers

- **Problem:** hai worker có thể cùng đọc trạng thái chưa gửi rồi cùng gửi.
- **Why it happens:** check-then-act không atomic và không có concurrency control.
- **Production impact:** duplicate delivery ngay cả khi không có timeout.
- **Severity:** Critical
- **Recommended fix:** atomic claim bằng conditional update/concurrency token hoặc trạng thái `Processing` kèm lease; chỉ worker claim thành công mới được xử lý.

### 3. Failure window giữa gửi email và lưu `Sent`

- **Problem:** external call thành công nhưng `SaveChangesAsync` cuối thất bại.
- **Why it happens:** SQL transaction không bao phủ được external provider.
- **Production impact:** DB vẫn thấy chưa gửi và retry tạo duplicate.
- **Severity:** Critical
- **Recommended fix:** idempotency tại external boundary là giải pháp mạnh nhất; state machine chỉ giảm race chứ không loại bỏ ambiguity sau timeout.

### 4. `AttemptCount` không phản ánh chắc chắn số lần external send

- **Problem:** counter được commit trước external call.
- **Why it happens:** một attempt có thể crash trước khi gửi hoặc gửi xong nhưng chưa cập nhật status.
- **Production impact:** telemetry gây hiểu nhầm.
- **Severity:** Medium
- **Recommended fix:** phân biệt `ProcessingAttemptCount`, provider request ID và outcome.

### 5. Không có cancellation/timeout contract rõ ràng

- **Problem:** job không thể hiện cancellation semantics và timeout policy của provider.
- **Why it happens:** dependency call không nhận token trong API hiện tại.
- **Production impact:** worker bị giữ lâu khi downstream treo; retry chồng lên failure kéo dài.
- **Severity:** High
- **Recommended fix:** cấu hình timeout hữu hạn ở HTTP client/provider SDK; hỗ trợ cancellation nơi phù hợp.

### 6. Retry mọi exception với cùng policy

- **Problem:** permanent failures như invalid recipient có thể bị retry như transient failure.
- **Why it happens:** policy không phân loại lỗi.
- **Production impact:** lãng phí worker/provider quota và làm chậm queue.
- **Severity:** Medium
- **Recommended fix:** classify transient/permanent failures; retry có backoff, đưa permanent failure sang terminal state/dead-letter workflow.

### 7. String status dễ tạo state transition không hợp lệ

- **Problem:** domain state không được mô hình hóa rõ.
- **Why it happens:** magic string và không có transition guard.
- **Production impact:** khó bảo đảm state machine khi thêm `Processing`, `Failed`, `Cancelled`.
- **Severity:** Medium
- **Recommended fix:** enum/value object và transition rules rõ ràng.

### 8. Logging chứa recipient trực tiếp

- **Problem:** email address là dữ liệu cá nhân có thể không cần xuất hiện trong log thông thường.
- **Why it happens:** structured log ghi nguyên recipient.
- **Production impact:** tăng phạm vi dữ liệu nhạy cảm trong logging pipeline.
- **Severity:** Medium
- **Recommended fix:** log notification ID/provider request ID; mask/hash recipient nếu thực sự cần correlation.

## Phiên bản code đề xuất

Giả sử provider hỗ trợ stable idempotency key và entity có concurrency token:

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task SendAsync(long notificationId, CancellationToken ct)
    {
        var notification = await _db.Notifications
            .SingleAsync(x => x.Id == notificationId, ct);

        if (notification.Status == NotificationStatus.Sent)
            return;

        if (notification.Status == NotificationStatus.FailedPermanent)
            return;

        notification.Status = NotificationStatus.Processing;
        notification.AttemptCount++;
        notification.LastAttemptAt = DateTime.UtcNow;

        try
        {
            await _db.SaveChangesAsync(ct);
        }
        catch (DbUpdateConcurrencyException)
        {
            _logger.LogInformation(
                "Notification {NotificationId} was claimed by another worker",
                notificationId);
            return;
        }

        var idempotencyKey = $"notification:{notificationId}";

        var result = await _emailSender.SendAsync(
            notification.To,
            notification.Subject,
            notification.Body,
            idempotencyKey,
            ct);

        notification.Status = NotificationStatus.Sent;
        notification.SentAt = DateTime.UtcNow;
        notification.ProviderMessageId = result.MessageId;

        await _db.SaveChangesAsync(ct);

        _logger.LogInformation(
            "Notification {NotificationId} sent. ProviderMessageId={ProviderMessageId}",
            notificationId,
            result.MessageId);
    }
}
```

> `Processing` + optimistic concurrency ngăn nhiều worker cùng claim trong phần lớn race conditions, nhưng **không tự giải quyết ambiguous external outcome**. Stable provider idempotency key mới là thành phần quan trọng để retry an toàn nếu provider thực sự hỗ trợ semantics đó.

## Trade-offs

- Provider idempotency đơn giản và mạnh nhưng phụ thuộc capability của provider.
- Distributed lock có thể giảm concurrent sends nhưng vẫn không xử lý crash sau external side effect; lock không thay thế idempotency.
- Outbox phù hợp để bảo đảm việc tạo notification/job không bị mất giữa business transaction và enqueue, nhưng outbox cũng thường mang semantics at-least-once nên consumer vẫn cần idempotent.
- Nếu email chỉ mang tính informational, duplicate có thể được chấp nhận hơn so với complexity của một hệ thống dedupe riêng.

## Cách kiểm thử

1. **Concurrency test:** 20 workers cùng xử lý một ID; chỉ một worker claim và provider nhận một logical request.
2. **Ambiguous timeout:** provider nhận request rồi client timeout; retry cùng idempotency key không tạo email thứ hai.
3. **Crash test:** process chết ngay sau provider success nhưng trước DB update; retry phải recover an toàn.
4. **Permanent failure:** invalid recipient chuyển terminal state và không retry vô ích.
5. **Transient failure:** 429/5xx được retry theo policy và telemetry ghi đúng attempt/outcome.

## Quan sát trong production

- Metric `notification_send_attempts_total` theo outcome.
- Metric duplicate/idempotency-replay nếu provider cung cấp.
- Queue latency, retry count, failed jobs và processing duration.
- Trace từ Hangfire job → email provider call.
- Log `NotificationId`, attempt, provider request/message ID, outcome; tránh log body hoặc recipient đầy đủ.
- Alert khi retry rate hoặc queue age vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không hỗ trợ idempotency key, bạn sẽ định nghĩa delivery guarantee với business thế nào?
2. Outbox pattern giải quyết phần nào của bài toán và phần nào nó không giải quyết?
3. Bạn có dùng distributed lock không? Vì sao lock vẫn chưa đủ để đảm bảo exactly-once side effect?

# Code Review Challenge 2 — Export API kéo toàn bộ dữ liệu vào memory

**Chủ đề:** EF Core query execution, memory allocation, streaming, cancellation, performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một API cho phép admin export audit logs ra CSV. Dataset của tenant nhỏ chỉ vài nghìn rows nên chạy tốt, nhưng tenant lớn có thể có hàng triệu rows. Production xuất hiện memory spike, Gen 2 GC tăng, request timeout và đôi lúc container bị restart khi nhiều admin export cùng lúc.

Endpoint phải giữ đúng authorization theo tenant. Business muốn giữ chức năng export nhưng không bắt buộc file phải được tạo đồng bộ trong một HTTP request.

## Đoạn code cần review

```csharp
[Authorize(Roles = "Admin")]
[HttpGet("audit/export")]
public async Task<IActionResult> Export(
    DateTime? from,
    DateTime? to,
    string? search)
{
    var tenantId = int.Parse(User.FindFirst("tenant_id")!.Value);

    var logs = await _db.AuditLogs
        .Include(x => x.User)
        .Where(x => x.TenantId == tenantId)
        .OrderByDescending(x => x.CreatedAt)
        .ToListAsync();

    if (from.HasValue)
        logs = logs.Where(x => x.CreatedAt >= from.Value).ToList();

    if (to.HasValue)
        logs = logs.Where(x => x.CreatedAt <= to.Value).ToList();

    if (!string.IsNullOrWhiteSpace(search))
    {
        logs = logs
            .Where(x => x.Action.Contains(search) ||
                        x.User.Email.Contains(search))
            .ToList();
    }

    var csv = new StringBuilder();
    csv.AppendLine("Time,User,Action,Details");

    foreach (var log in logs)
    {
        csv.AppendLine(
            $"{log.CreatedAt:o},{log.User.Email},{log.Action},{log.Details}");
    }

    return File(
        Encoding.UTF8.GetBytes(csv.ToString()),
        "text/csv",
        $"audit-{DateTime.UtcNow:yyyyMMddHHmmss}.csv");
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ tenant trước khi filter

- **Problem:** `ToListAsync()` chạy trước `from`, `to`, `search`.
- **Why it happens:** các filter sau đó chạy trên `List<T>` bằng LINQ-to-Objects.
- **Production impact:** đọc hàng triệu rows không cần thiết, tăng DB I/O, network, allocation và latency.
- **Severity:** Critical
- **Recommended fix:** giữ query dưới dạng `IQueryable`, áp filter/projection trước khi execute.

### 2. Tạo nhiều bản sao lớn của output trong memory

- **Problem:** entity list + `StringBuilder` + `csv.ToString()` + UTF-8 byte array cùng tồn tại trong lifecycle request.
- **Why it happens:** toàn bộ CSV được buffer trước khi response.
- **Production impact:** LOH/Gen 2 pressure, OOM/container restart khi concurrent exports.
- **Severity:** Critical
- **Recommended fix:** stream theo batch/`IAsyncEnumerable`, hoặc chuyển export lớn sang background job + object storage.

### 3. Không truyền request cancellation

- **Problem:** query và export tiếp tục khi client disconnect.
- **Why it happens:** thiếu `HttpContext.RequestAborted`/`CancellationToken`.
- **Production impact:** wasted DB/CPU/memory trong incident timeout.
- **Severity:** High
- **Recommended fix:** propagate cancellation xuyên suốt query/streaming path.

### 4. CSV không escape dữ liệu

- **Problem:** commas, quotes và newline trong `Action`, `Details`, `Email` phá cấu trúc CSV.
- **Why it happens:** interpolation trực tiếp.
- **Production impact:** file sai dữ liệu; ngoài ra spreadsheet formula injection cần được threat-model nếu field do user kiểm soát và file được mở bằng spreadsheet software.
- **Severity:** High
- **Recommended fix:** dùng CSV writer/library có escaping chuẩn; cân nhắc neutralize spreadsheet formulas theo threat model.

### 5. `Include` + full entity load dư thừa

- **Problem:** load entity graph trong khi chỉ cần một số columns.
- **Why it happens:** không projection DTO.
- **Production impact:** nhiều data transfer/tracking/allocation hơn cần thiết.
- **Severity:** High
- **Recommended fix:** `AsNoTracking()` và `Select` đúng fields cần export.

### 6. Không giới hạn export range

- **Problem:** admin có thể vô tình yêu cầu toàn bộ lịch sử.
- **Why it happens:** `from/to` optional và không có policy về maximum range/rows.
- **Production impact:** một request hợp lệ về authorization vẫn có thể gây resource exhaustion.
- **Severity:** High
- **Recommended fix:** validate range, rate-limit/concurrency-limit export; dùng async export cho dataset lớn.

### 7. Claim parsing không defensive

- **Problem:** `FindFirst(...)!` và `int.Parse` giả định claim luôn tồn tại/hợp lệ.
- **Why it happens:** authorization policy chưa đảm bảo claim contract tại boundary.
- **Production impact:** malformed/missing claim tạo 500 thay vì authorization failure rõ ràng.
- **Severity:** Medium
- **Recommended fix:** policy-based authorization/tenant context service validate claim một lần.

### 8. Index/query shape chưa được xem xét

- **Problem:** query lớn filter/order theo `TenantId`, thời gian và có thể search text.
- **Why it happens:** application code không chứng minh execution plan phù hợp.
- **Production impact:** scan/sort lớn, latency và DB CPU tăng.
- **Severity:** Medium
- **Recommended fix:** kiểm tra actual execution plan; thiết kế index theo workload thực tế, không đoán index chỉ từ code.

## Phiên bản code đề xuất

Với export vừa phải có thể stream trực tiếp; export rất lớn nên chuyển sang background workflow. Ví dụ streaming tối giản:

```csharp
[Authorize(Policy = "TenantAdmin")]
[HttpGet("audit/export")]
public async Task Export(
    DateTime from,
    DateTime to,
    string? search,
    CancellationToken ct)
{
    if (to <= from || to - from > TimeSpan.FromDays(31))
        throw new BadHttpRequestException("Invalid export range.");

    var tenantId = _tenantContext.TenantId;

    var query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId &&
                    x.CreatedAt >= from &&
                    x.CreatedAt < to);

    if (!string.IsNullOrWhiteSpace(search))
    {
        query = query.Where(x =>
            x.Action.Contains(search) ||
            x.User.Email.Contains(search));
    }

    var rows = query
        .OrderBy(x => x.Id)
        .Select(x => new
        {
            x.CreatedAt,
            Email = x.User.Email,
            x.Action,
            x.Details
        })
        .AsAsyncEnumerable();

    Response.ContentType = "text/csv; charset=utf-8";
    Response.Headers.ContentDisposition =
        $"attachment; filename=\"audit-{DateTime.UtcNow:yyyyMMddHHmmss}.csv\"";

    await using var writer = new StreamWriter(
        Response.Body,
        new UTF8Encoding(false),
        leaveOpen: true);

    await writer.WriteLineAsync("Time,User,Action,Details");

    await foreach (var row in rows.WithCancellation(ct))
    {
        await writer.WriteAsync(CsvEscape(row.CreatedAt.ToString("O")));
        await writer.WriteAsync(',');
        await writer.WriteAsync(CsvEscape(row.Email));
        await writer.WriteAsync(',');
        await writer.WriteAsync(CsvEscape(row.Action));
        await writer.WriteAsync(',');
        await writer.WriteLineAsync(CsvEscape(row.Details));
    }
}

private static string CsvEscape(string? value)
{
    value ??= string.Empty;
    return $"\"{value.Replace("\"", "\"\"")}\"";
}
```

Trong production, nên ưu tiên CSV library đã được kiểm thử thay vì tự viết escaping. Với export hàng triệu rows, hướng tốt hơn thường là tạo `ExportRequest`, enqueue background job, stream theo batch ra Blob Storage, rồi cấp download URL có thời hạn và authorization phù hợp.

## Trade-offs

- Streaming HTTP giảm peak memory nhưng request vẫn sống lâu và giữ DB connection lâu hơn.
- Background export tăng complexity/state/storage nhưng tốt hơn cho file lớn, retry và user experience.
- Pagination theo keyset/batch giúp kiểm soát resource tốt hơn; offset pagination có thể đắt ở dataset lớn và có consistency trade-offs khi dữ liệu thay đổi trong lúc export.
- Search `%term%` đơn giản nhưng có thể không scale; full-text/search engine chỉ nên thêm khi requirement và đo lường chứng minh cần thiết.

## Cách kiểm thử

1. **Large dataset test:** hàng triệu audit rows; đo peak memory, allocations, DB duration và throughput.
2. **Filter correctness:** xác minh SQL chỉ lấy tenant/range/search cần thiết.
3. **Cancellation test:** client disconnect; DB enumeration và response writing phải dừng nhanh.
4. **CSV correctness/security:** commas, quotes, CR/LF và values bắt đầu bằng `=`, `+`, `-`, `@` theo threat model.
5. **Concurrent export load:** nhiều admin export đồng thời; xác minh concurrency limit và container không memory spike bất thường.

## Quan sát trong production

- Export duration, rows exported, bytes written, cancellation/failure rate.
- Concurrent exports và queue age nếu dùng background job.
- Process working set, GC heap size, Gen 2 collections, allocation rate.
- DB query duration, rows read, timeout và execution plan cho query lớn.
- Distributed trace từ API/job tới database và object storage.
- Alert khi export failure rate, memory pressure hoặc DB latency vượt baseline.

3. Nếu business yêu cầu export 2 năm dữ liệu, bạn sẽ bảo vệ database và giới hạn concurrency như thế nào?

- Retry của background job phải được thiết kế cùng **idempotency**; trạng thái `Sent` đơn thuần không loại bỏ ambiguous failure window.
- SQL transaction không thể tự biến external side effect thành exactly-once operation.
- EF Core performance phụ thuộc mạnh vào thời điểm query được materialize; filter/projection nên được đẩy xuống database khi phù hợp.
- Export lớn cần xem cả query plan, managed-memory lifecycle, cancellation và delivery architecture.
- Authorization đúng không đồng nghĩa request được phép tiêu thụ tài nguyên không giới hạn.

## Mẫu tư duy cần nhớ

- **Enumerate every crash point before declaring a workflow reliable.**
- **Design retries together with idempotency.**
- **Keep `IQueryable` until the database-relevant filters/projection are complete.**
- **Bound expensive operations by range, concurrency and cancellation.**
- **Treat observability and failure recovery as part of the design.**
