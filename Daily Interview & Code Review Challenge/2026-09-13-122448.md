# Code Review Challenge 1 — Tenant authorization bị kiểm tra ở controller nhưng query vẫn có thể đọc dữ liệu tenant khác

**Chủ đề:** C#/.NET 8, ASP.NET Core, policy-based authorization, claims, EF Core, multi-tenant data isolation, IDOR/BOLA, caching, structured logging, integration testing  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ back-office cho nhiều customer tenant. User đăng nhập qua Microsoft Entra ID. Token chứa claim `tenant_id` do application mapping từ identity sang tenant nội bộ.

Endpoint `GET /api/orders/{orderId}` dùng để xem chi tiết order. Business rule là user chỉ được xem order thuộc tenant của mình. Một số support user có quyền đặc biệt `orders.read.any-tenant` để hỗ trợ incident.

Production vừa phát hiện một security incident: một user bình thường thay `orderId` trên URL và đọc được order thuộc tenant khác. Team kiểm tra lại thấy endpoint có `[Authorize]` và còn so sánh tenant sau khi lấy dữ liệu nên ban đầu cho rằng không thể leak.

Các constraint:

- không được tin `tenantId` do client gửi lên nếu có thể derive từ authenticated identity;
- support access phải explicit, auditable và không được mở rộng ngầm cho user thường;
- order details có PII nên log không được chứa toàn bộ payload;
- API có Redis cache cho order summary nhằm giảm tải SQL;
- hệ thống chạy nhiều App Service instances;
- fix cần ưu tiên correctness/security trước performance.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(
        AppDbContext db,
        IDistributedCache cache,
        ILogger<OrdersController> logger)
    {
        _db = db;
        _cache = cache;
        _logger = logger;
    }

    [Authorize]
    [HttpGet("{orderId:long}")]
    public async Task<IActionResult> Get(
        long orderId,
        [FromQuery] int tenantId,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"order:{orderId}";
        var cached = await _cache.GetStringAsync(cacheKey, cancellationToken);

        if (cached is not null)
        {
            return Content(cached, "application/json");
        }

        var order = await _db.Orders
            .Include(x => x.Customer)
            .SingleOrDefaultAsync(x => x.Id == orderId, cancellationToken);

        if (order is null)
            return NotFound();

        var claimTenant = User.FindFirst("tenant_id")?.Value;
        var canReadAnyTenant = User.IsInRole("orders.read.any-tenant");

        if (!canReadAnyTenant && claimTenant != tenantId.ToString())
            return Forbid();

        var response = new
        {
            order.Id,
            order.TenantId,
            order.Status,
            order.Total,
            Customer = new
            {
                order.Customer.Name,
                order.Customer.Email
            }
        };

        var json = JsonSerializer.Serialize(response);

        await _cache.SetStringAsync(
            cacheKey,
            json,
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            },
            cancellationToken);

        _logger.LogInformation(
            "User {User} read order {OrderId} for tenant {TenantId}: {Payload}",
            User.Identity?.Name,
            order.Id,
            order.TenantId,
            json);

        return Ok(response);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi authorization, tenant isolation, caching, logging và API-design trong đoạn code.
2. Giải thích vì sao `[Authorize]` không đồng nghĩa với object-level authorization.
3. Chỉ ra cách user có thể lợi dụng `tenantId` query parameter để vượt qua check hiện tại.
4. Phân tích vì sao cache key `order:{orderId}` có thể làm leak dữ liệu tenant khác ngay cả khi database authorization được sửa.
5. Đánh giá việc dùng role string `orders.read.any-tenant` và đề xuất policy/authorization design rõ ràng hơn.
6. Đề xuất query/design để tenant filter nằm ngay tại data-access boundary thay vì đọc row rồi mới check.
7. Phân tích trade-off giữa trả `403` và `404` cho object thuộc tenant khác.
8. Nêu cách audit support access mà không log PII hoặc toàn bộ JSON response.
9. Đề xuất tests để chứng minh không còn BOLA/IDOR khi gọi trực tiếp URL với `orderId` của tenant khác.
10. Nêu production telemetry/alerting hữu ích để phát hiện access pattern đáng ngờ.

## Câu hỏi gợi mở

1. `tenantId` query parameter có authority gì so với tenant claim đã được server xác thực?
2. Nếu cache hit xảy ra trước mọi authorization check thì request còn đi tới database hoặc đoạn check phía dưới không?
3. Điều gì bảo đảm `order.TenantId == tenantId` trong code hiện tại?
4. Nếu support user được phép cross-tenant, authorization decision nên nằm ở controller ad-hoc hay một policy/service có audit context?
5. Có nên log `Customer.Email` chỉ để phục vụ audit việc đọc order không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **object-level authorization** và **tenant isolation**, không phải authentication. Hãy lần theo request từ identity → cache → query → authorization decision.

## Kết quả code review tham khảo

### Critical — Cache hit trả dữ liệu trước bất kỳ authorization check nào

**Vấn đề:** `GetStringAsync` chạy ngay đầu action và dữ liệu cache được trả trực tiếp nếu tồn tại.

**Tại sao xảy ra:** Cache được coi như một performance shortcut nhưng không giữ cùng authorization invariant với database path.

**Ảnh hưởng production:** Bất kỳ authenticated user nào biết `orderId` có thể nhận cached response của tenant khác. Đây là cross-tenant data disclosure nghiêm trọng.

**Cách sửa:** Không trả cached tenant-scoped resource trước authorization. Cache key phải chứa security scope phù hợp, ví dụ tenant + order id, và access decision vẫn phải dựa trên authenticated server context. Với support cross-tenant access, dùng explicit path/service có policy riêng thay vì bypass ngầm.

### Critical — Client-controlled `tenantId` được dùng trong authorization decision

**Vấn đề:** Code so sánh claim tenant với `tenantId` từ query string nhưng không so sánh `tenantId` với `order.TenantId`.

**Tại sao xảy ra:** Một input do attacker điều khiển được nhầm là security context.

**Ảnh hưởng production:** User tenant 10 có thể gọi `/api/orders/999?tenantId=10`; nếu order 999 thuộc tenant 20 thì check vẫn pass vì claim tenant = query tenant.

**Cách sửa:** Không nhận tenant id từ client cho endpoint tenant-local khi không cần. Derive tenant từ authenticated identity. Query phải bao gồm `x.TenantId == currentTenantId` cho user thường.

### Critical — Object-level authorization không được enforce ở data-access boundary

**Vấn đề:** Query chỉ filter `Id == orderId`, sau đó application mới thực hiện check rời rạc.

**Tại sao xảy ra:** Security invariant không được biểu diễn trong query/data access contract.

**Ảnh hưởng production:** Dễ phát sinh BOLA/IDOR khi một code path quên check hoặc thêm cache/early return.

**Cách sửa:** Với user thường, query `Orders.Where(x => x.Id == orderId && x.TenantId == currentTenantId)`. Có thể encapsulate trong tenant-aware repository/query service hoặc global query filter nếu team hiểu rõ trade-offs và support path có explicit bypass.

### High — `IsInRole` đang dùng role như permission mà không có policy boundary rõ ràng

**Vấn đề:** Code hard-code một string có semantics giống permission nhưng dùng role check trực tiếp trong controller.

**Tại sao xảy ra:** Authentication claims mapping và business authorization bị trộn vào endpoint implementation.

**Ảnh hưởng production:** Khó audit, khó test policy, dễ drift giữa endpoints và dễ mở rộng quyền ngoài ý muốn.

**Cách sửa:** Dùng policy-based authorization, ví dụ `OrdersReadAnyTenant`, được map từ validated claims/permissions. Cross-tenant access nên đi qua một authorization service nhận resource/tenant context và phát audit event riêng.

### High — Cache key không chứa tenant/security scope

**Vấn đề:** `order:{orderId}` giả định `orderId` toàn cục là đủ để xác định cache object nhưng bỏ qua authorization context.

**Tại sao xảy ra:** Cache model chỉ phản ánh data identity, không phản ánh security boundary.

**Ảnh hưởng production:** Dễ trả cùng payload cho nhiều tenant hoặc làm support-access cache ảnh hưởng user thường.

**Cách sửa:** Với tenant-local cache dùng key như `tenant:{tenantId}:order:{orderId}`. Tuy nhiên key đúng không thay thế authorization; request vẫn phải xác định tenant từ trusted identity trước khi đọc cache.

### High — Log toàn bộ JSON response chứa PII

**Vấn đề:** `json` chứa customer name/email được ghi vào structured log.

**Tại sao xảy ra:** Audit và debug logging bị đồng nhất với payload logging.

**Ảnh hưởng production:** PII bị nhân bản sang log store, tăng blast radius, retention/compliance risk và quyền truy cập dữ liệu nhạy cảm.

**Cách sửa:** Chỉ log metadata tối thiểu như actor id, actor tenant, target tenant, order id, access mode, outcome, correlation id. Với support cross-tenant, emit explicit audit event không chứa business payload.

### Medium — `User.Identity.Name` không phải lúc nào cũng là stable audit identifier

**Vấn đề:** Display name/email có thể thay đổi và có thể không unique theo cách audit cần.

**Tại sao xảy ra:** Human-readable identity bị dùng thay stable subject/object id.

**Ảnh hưởng production:** Điều tra incident khó correlate chính xác actor.

**Cách sửa:** Log stable subject/user object id từ validated claims cùng tenant id; display name chỉ là optional enrichment.

### Medium — Trả raw serialized cache bằng `Content` tạo hai response paths khác nhau

**Vấn đề:** Cache hit trả JSON string trực tiếp, cache miss trả `Ok(response)`.

**Tại sao xảy ra:** Cache implementation leak lên HTTP layer.

**Ảnh hưởng production:** Header/content negotiation/serialization behavior có thể khác nhau; future response contracts dễ drift.

**Cách sửa:** Cache DTO typed hoặc serialized DTO nhưng deserialize/return theo cùng contract. Tốt hơn là cache ở application/query layer thay vì controller response layer.

### Medium — `Include(Customer)` lấy nhiều dữ liệu hơn authorization cần trước khi tenant được xác định

**Vấn đề:** PII được materialize trước khi resource access được đảm bảo.

**Tại sao xảy ra:** Query ưu tiên convenience hơn least-data access.

**Ảnh hưởng production:** Tăng risk trong memory/logging và tốn IO nếu request cuối cùng bị từ chối.

**Cách sửa:** Filter tenant trước và project đúng DTO cần thiết. Với support flow, authorize target tenant trước rồi mới fetch sensitive fields.

### Low — Không có audit semantics riêng cho cross-tenant support access

**Vấn đề:** Log hiện tại không phân biệt normal tenant-local read và privileged support read.

**Tại sao xảy ra:** Authorization mode không được model hóa như business/security event.

**Ảnh hưởng production:** Khó alert hoặc review privileged access.

**Cách sửa:** Ghi audit event có `AccessMode=SupportCrossTenant`, actor, reason/ticket nếu business yêu cầu, target tenant, resource id, timestamp, correlation id và outcome.

## Phiên bản đề xuất

Ví dụ dưới đây tách normal tenant-local access khỏi privileged cross-tenant authorization. Policy names chỉ là application design example; claim mapping cụ thể phải phù hợp identity configuration thực tế.

```csharp
public interface ICurrentUser
{
    string SubjectId { get; }
    int TenantId { get; }
}

public sealed class OrderQueryService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public OrderQueryService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    public async Task<OrderDetailsDto?> GetForTenantAsync(
        long orderId,
        int tenantId,
        CancellationToken cancellationToken)
    {
        var key = $"tenant:{tenantId}:order:{orderId}";

        var cached = await _cache.GetStringAsync(key, cancellationToken);
        if (cached is not null)
            return JsonSerializer.Deserialize<OrderDetailsDto>(cached);

        var dto = await _db.Orders
            .AsNoTracking()
            .Where(x => x.Id == orderId && x.TenantId == tenantId)
            .Select(x => new OrderDetailsDto(
                x.Id,
                x.TenantId,
                x.Status,
                x.Total,
                x.Customer.Name,
                x.Customer.Email))
            .SingleOrDefaultAsync(cancellationToken);

        if (dto is null)
            return null;

        await _cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(dto),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            },
            cancellationToken);

        return dto;
    }
}

[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    private readonly ICurrentUser _currentUser;
    private readonly OrderQueryService _orders;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(
        ICurrentUser currentUser,
        OrderQueryService orders,
        ILogger<OrdersController> logger)
    {
        _currentUser = currentUser;
        _orders = orders;
        _logger = logger;
    }

    [Authorize]
    [HttpGet("{orderId:long}")]
    public async Task<ActionResult<OrderDetailsDto>> Get(
        long orderId,
        CancellationToken cancellationToken)
    {
        var order = await _orders.GetForTenantAsync(
            orderId,
            _currentUser.TenantId,
            cancellationToken);

        if (order is null)
            return NotFound();

        _logger.LogInformation(
            "Order read by subject {SubjectId} tenant {TenantId} order {OrderId}",
            _currentUser.SubjectId,
            _currentUser.TenantId,
            orderId);

        return Ok(order);
    }
}
```

Privileged support access nên là một explicit use case khác, ví dụ `GetForSupportAsync(orderId, targetTenantId)` và phải gọi `IAuthorizationService.AuthorizeAsync(...)` với policy/resource context trước khi query/cached response được trả. Audit event của support flow cần phân biệt rõ với normal flow.

Một global query filter cho tenant isolation có thể giảm nguy cơ quên filter, nhưng nó cũng có trade-off: privileged/system jobs cần bypass có kiểm soát; developer phải hiểu `IgnoreQueryFilters()` là security-sensitive. Vì vậy không nên coi global filter là magic replacement cho authorization design.

## Giải thích thiết kế sau khi sửa

Tenant identity được derive từ authenticated principal, không từ request query parameter. Normal endpoint không cho client chọn tenant nên attack surface nhỏ hơn.

Security predicate được đưa vào database query. Điều này làm unauthorized resource trông như không tồn tại đối với normal user, đồng thời tránh materialize PII rồi mới reject.

Cache key gắn với tenant scope và cache chỉ được truy cập sau khi trusted tenant context đã có. Cache trở thành optimization của một authorized query chứ không phải authorization bypass.

Support cross-tenant flow được tách riêng vì semantics, audit và test khác normal read. Điều này giảm nguy cơ một boolean `canReadAnyTenant` làm endpoint trở nên khó reasoning.

## Trade-offs

Tenant-aware cache keys làm tăng số cache entries nếu cùng resource có nhiều representations hoặc support path cache riêng. Đổi lại, security isolation rõ ràng hơn.

Trả `404` cho resource tenant khác giúp giảm information disclosure về existence. Một số internal support API có thể cần `403` để operator hiểu quyền bị thiếu; lựa chọn phải theo threat model và UX, không có một đáp án tuyệt đối.

Global query filter giảm boilerplate nhưng có thể che giấu query behavior và tạo nguy cơ khi code bypass filter. Explicit query predicate dễ audit hơn ở critical paths nhưng phụ thuộc discipline.

Policy-based authorization thêm abstraction so với `IsInRole`, nhưng đổi lại có testability, consistency và audit boundary tốt hơn. Không cần xây một authorization framework quá phức tạp nếu hệ thống chỉ có vài policies rõ ràng.

## Cách kiểm thử

1. **Integration security test:** user tenant A gọi order của tenant B bằng direct `orderId`; response không được chứa dữ liệu, kể cả khi item đã được cache trước bởi tenant B.
2. **Cache isolation test:** warm cache cho tenant B, sau đó gọi cùng `orderId` bằng identity tenant A; bảo đảm không hit nhầm payload tenant B.
3. **Support policy test:** user thường không thể gọi cross-tenant support use case; principal có đúng permission mới được phép và phải sinh audit event.
4. **PII logging test:** dùng test logger để xác minh email/name không xuất hiện trong application logs khi request thành công hoặc bị từ chối.
5. **Regression/E2E test:** enumerate nhiều `orderId` ngoài tenant và xác minh không resource nào bị leak; kết hợp rate-limit/security monitoring nếu enumeration là concern thực tế.

## Quan sát trong production

Theo dõi:

- denied resource-access count theo actor/tenant;
- số lần một actor truy cập nhiều order ids liên tiếp không tồn tại trong tenant;
- privileged cross-tenant reads theo subject/target tenant;
- cache hit/miss theo tenant scope mà không log payload;
- authorization policy failures;
- correlation id từ request → authorization → query → audit event;
- unusual spike của `404/403` trên object endpoints;
- Redis/database latency riêng biệt để performance issue không dẫn tới bypass security shortcut.

Alert cho bất thường như một principal thử hàng trăm order ids trong thời gian ngắn hoặc privileged support access tăng ngoài expected pattern.

3. Nếu support user cần tạm thời impersonate tenant UI để debug, bạn thiết kế authorization và audit trail thế nào để tránh silent privilege escalation?

# Code Review Challenge 2 — Vue search hiển thị kết quả cũ do request về sai thứ tự và watcher tạo duplicate calls

**Chủ đề:** Vue 3, TypeScript, Composition API, browser fetch, async race condition, request cancellation, stale state, debounce, error handling, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal product-management portal dùng Vue 3 + TypeScript. Trang search gọi ASP.NET Core API `/api/products` theo `q`, `category` và `page`.

User thường gõ nhanh, đổi category liên tục rồi chuyển trang. API response trung bình 100–300 ms nhưng có lúc một request mất hơn 2 giây do search backend degrade.

Production có các triệu chứng:

- user gõ `camera`, sau đó sửa thành `camera lens`, nhưng UI đôi lúc lại hiển thị kết quả của `camera`;
- DevTools thấy một thay đổi filter có thể tạo 2–3 requests gần giống nhau;
- spinner thỉnh thoảng biến mất trong khi request mới hơn vẫn đang chạy;
- khi request cũ fail sau request mới thành công, UI lại hiện error banner dù dữ liệu mới đang đúng;
- khi component unmount, một số request vẫn tiếp tục;
- backend team thấy burst traffic lớn hơn số thao tác user thực tế;
- team đề xuất chỉ thêm debounce 500 ms và cho rằng như vậy sẽ hết race condition.

Không có requirement phải giữ mọi intermediate search. UI chỉ cần hiển thị **kết quả tương ứng với state filter mới nhất**.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { onMounted, ref, watch } from 'vue'

interface Product {
  id: number
  name: string
}

interface SearchResponse {
  items: Product[]
  total: number
}

const q = ref('')
const category = ref<string | null>(null)
const page = ref(1)

const items = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref<string | null>(null)

async function loadProducts() {
  loading.value = true
  error.value = null

  const params = new URLSearchParams()
  params.set('q', q.value)
  params.set('page', page.value.toString())

  if (category.value) {
    params.set('category', category.value)
  }

  try {
    const response = await fetch(`/api/products?${params}`)

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    const data = await response.json() as SearchResponse

    items.value = data.items
    total.value = data.total
  } catch (e) {
    error.value = e instanceof Error ? e.message : 'Unknown error'
  } finally {
    loading.value = false
  }
}

watch(q, () => {
  page.value = 1
  loadProducts()
})

watch(category, () => {
  page.value = 1
  loadProducts()
})

watch(page, () => {
  loadProducts()
})

onMounted(() => {
  loadProducts()
})
</script>
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, duplicate requests, race condition và lifecycle trong component.
2. Giải thích timeline cụ thể khiến request cho query cũ overwrite state của query mới.
3. Chỉ ra vì sao `watch(q)` và `watch(category)` có thể gây thêm request qua việc cùng thay `page`.
4. Giải thích vì sao `loading` boolean hiện tại không phản ánh đúng khi nhiều requests overlap.
5. Phân tích cách error từ request cũ có thể overwrite UI state sau khi request mới đã thành công.
6. Đánh giá việc chỉ thêm debounce 500 ms: vấn đề nào được giảm và vấn đề nào vẫn còn.
7. Đề xuất implementation chỉ cho response của search state mới nhất được phép commit vào UI.
8. Đề xuất cancellation strategy khi filter đổi hoặc component unmount.
9. Nêu tests để reproduce deterministic out-of-order responses thay vì dựa vào timing ngẫu nhiên.
10. Nêu browser/frontend telemetry và backend metrics hữu ích để chứng minh burst traffic giảm.

## Câu hỏi gợi mở

1. Nếu request A bắt đầu trước request B nhưng B hoàn tất trước A thì code hiện tại response nào thắng?
2. `page.value = 1` có trigger `watch(page)` khi page đang khác 1 không?
3. Một `loading` boolean có biểu diễn đúng hai request đang chạy song song không?
4. Debounce có ngăn được một request cũ đã gửi đi trả về sau request mới không?
5. `fetch` hỗ trợ cơ chế nào để hủy request khi component không còn quan tâm tới kết quả?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **latest state vs request completion order**. UI hiện commit state theo thứ tự response về, không theo thứ tự intent của user.

### Gợi ý 2

Hãy tách hai bài toán: giảm số request không cần thiết bằng debounce/coalescing, và bảo đảm correctness bằng cancellation hoặc request version/generation guard.

## Kết quả code review tham khảo

### High — Response cũ có thể overwrite kết quả mới

**Vấn đề:** Mọi request sau khi hoàn tất đều ghi trực tiếp `items` và `total`.

**Tại sao xảy ra:** Promise completion order không đảm bảo giống request start order. Network/backend latency thay đổi theo từng request.

**Ảnh hưởng production:** UI có thể hiển thị dữ liệu không tương ứng với filter hiện tại; user ra quyết định trên stale result.

**Cách sửa:** Dùng `AbortController` để cancel request trước khi gửi request mới và/hoặc dùng monotonically increasing request id/generation. Chỉ request mới nhất được phép commit state.

### High — Request cũ có thể overwrite error state của request mới

**Vấn đề:** `catch` luôn gán `error`, kể cả request đã stale.

**Tại sao xảy ra:** Error handling không gắn với current request generation.

**Ảnh hưởng production:** UI hiển thị error banner sau khi request mới đã thành công, gây contradictory state.

**Cách sửa:** Bỏ qua `AbortError`; với lỗi khác chỉ commit nếu request id vẫn là latest request.

### High — `loading` boolean sai khi requests overlap

**Vấn đề:** Request đầu tiên hoàn tất có thể set `loading=false` trong khi request mới vẫn chạy.

**Tại sao xảy ra:** Một boolean shared state không biết request nào đang sở hữu loading state.

**Ảnh hưởng production:** Spinner biến mất sớm, user có thể tiếp tục thao tác dựa trên UI tưởng đã ổn định.

**Cách sửa:** Chỉ latest request được phép clear loading, hoặc maintain pending count nếu UI cần phản ánh mọi request. Với latest-search semantics, request generation guard đơn giản hơn.

### High — Watchers có thể tạo duplicate requests khi reset page

**Vấn đề:** Khi `q` hoặc `category` thay đổi và `page` đang khác 1, watcher đầu tiên set `page=1` rồi gọi `loadProducts`; `watch(page)` lại gọi `loadProducts` lần nữa.

**Tại sao xảy ra:** Derived state transition và side effect được tách thành nhiều independent watchers.

**Ảnh hưởng production:** Burst traffic, wasted backend work, tăng xác suất race và rate-limit/load issue.

**Cách sửa:** Có một orchestration path cho search state. Ví dụ watcher cho `[q, category]` chỉ reset page, còn một watcher duy nhất trên effective query state chạy fetch; hoặc dùng computed request key + debounced watcher.

### Medium — Không cancel request khi filter đổi

**Vấn đề:** Browser tiếp tục download/process response mà UI không còn cần.

**Tại sao xảy ra:** Không dùng `AbortController`.

**Ảnh hưởng production:** Lãng phí bandwidth/server work và tăng stale response complexity.

**Cách sửa:** Abort previous controller trước request mới. Truyền `signal` vào `fetch`.

### Medium — Không cleanup request khi component unmount

**Vấn đề:** In-flight fetch vẫn tiếp tục sau khi component không còn hiển thị.

**Tại sao xảy ra:** Lifecycle cleanup chưa được implement.

**Ảnh hưởng production:** Wasted work và khó reasoning state nếu component mount/unmount nhanh.

**Cách sửa:** `onBeforeUnmount(() => controller?.abort())` hoặc dùng cleanup callback của `watch` để abort work liên quan iteration trước.

### Medium — Không debounce user typing

**Vấn đề:** Mỗi keystroke của `q` có thể gửi request.

**Tại sao xảy ra:** Watcher gọi network trực tiếp.

**Ảnh hưởng production:** Request amplification và backend load không cần thiết.

**Cách sửa:** Debounce text input hợp lý theo UX, nhưng coi đây là load optimization chứ không phải correctness guarantee.

### Medium — Query state được đọc mutable tại thời điểm function chạy thay vì snapshot explicit

**Vấn đề:** `loadProducts()` tự đọc nhiều refs global.

**Tại sao xảy ra:** Request input không được biểu diễn như immutable search criteria.

**Ảnh hưởng production:** Khó test và khó correlate request/response với exact UI state.

**Cách sửa:** Tạo `SearchCriteria` snapshot rồi pass vào fetch function; request id và telemetry nên đi cùng snapshot đó.

### Medium — Error message kỹ thuật được expose trực tiếp

**Vấn đề:** UI hiển thị `HTTP 500`/raw error message.

**Tại sao xảy ra:** Transport error và user-facing message bị dùng chung.

**Ảnh hưởng production:** UX kém và có thể expose chi tiết không cần thiết nếu future code throw raw server text.

**Cách sửa:** Map error type/status sang user-safe message; log diagnostic metadata riêng.

### Low — Không có frontend telemetry cho request superseded/aborted

**Vấn đề:** Team chỉ nhìn backend burst nhưng không biết bao nhiêu request bị tạo do UI orchestration.

**Tại sao xảy ra:** Không instrument search interaction.

**Ảnh hưởng production:** Khó xác minh fix có giảm duplicate request và stale commits.

**Cách sửa:** Track request count, aborted count, stale-response-discard count, search latency và effective user search count.

## Phiên bản đề xuất

Dưới đây là một hướng giữ semantics “latest search wins”. Debounce có thể bọc quanh trigger cho `q`; phần quan trọng là cancellation + generation guard.

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue'

interface Product {
  id: number
  name: string
}

interface SearchResponse {
  items: Product[]
  total: number
}

interface SearchCriteria {
  q: string
  category: string | null
  page: number
}

const q = ref('')
const category = ref<string | null>(null)
const page = ref(1)

const items = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref<string | null>(null)

let activeController: AbortController | null = null
let requestGeneration = 0
let debounceHandle: ReturnType<typeof setTimeout> | null = null

function snapshotCriteria(): SearchCriteria {
  return {
    q: q.value.trim(),
    category: category.value,
    page: page.value
  }
}

async function loadProducts(criteria: SearchCriteria) {
  activeController?.abort()

  const controller = new AbortController()
  activeController = controller

  const generation = ++requestGeneration
  loading.value = true
  error.value = null

  const params = new URLSearchParams({
    q: criteria.q,
    page: criteria.page.toString()
  })

  if (criteria.category) {
    params.set('category', criteria.category)
  }

  try {
    const response = await fetch(`/api/products?${params}`, {
      signal: controller.signal
    })

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    const data = await response.json() as SearchResponse

    if (generation !== requestGeneration)
      return

    items.value = data.items
    total.value = data.total
  } catch (e) {
    if (controller.signal.aborted)
      return

    if (generation !== requestGeneration)
      return

    error.value = 'Không thể tải danh sách sản phẩm.'
  } finally {
    if (generation === requestGeneration) {
      loading.value = false
    }
  }
}

function scheduleSearch(delayMs: number) {
  if (debounceHandle) {
    clearTimeout(debounceHandle)
  }

  debounceHandle = setTimeout(() => {
    void loadProducts(snapshotCriteria())
  }, delayMs)
}

watch([q, category], () => {
  if (page.value !== 1) {
    page.value = 1
    return
  }

  scheduleSearch(250)
})

watch(page, () => {
  scheduleSearch(0)
}, { immediate: true })

onBeforeUnmount(() => {
  if (debounceHandle) {
    clearTimeout(debounceHandle)
  }

  activeController?.abort()
})
</script>
```

Implementation trên là một lựa chọn, không phải duy nhất. Có thể dùng watcher với cleanup function, composable riêng, hoặc data-fetching library nếu project đã có. Điều quan trọng là semantics phải rõ: search state nào là current, work nào đã superseded, và response nào được phép commit.

Nếu backend hỗ trợ expensive search, cancellation client-side không đảm bảo server luôn dừng work ngay lập tức; điều đó phụ thuộc request cancellation propagation phía ASP.NET Core và downstream dependencies. Vì vậy vẫn cần backend observability/load protection riêng.

## Giải thích thiết kế sau khi sửa

`requestGeneration` tạo ordering theo user intent. Dù một stale request không abort được ở network layer, response của nó vẫn không thể update UI.

`AbortController` giảm work không còn cần thiết và cleanup tốt hơn khi component unmount. Generation guard vẫn được giữ vì cancellation không nên là correctness guarantee duy nhất.

Watch flow được gom để tránh `q/category` vừa gọi fetch trực tiếp vừa thay `page` khiến page watcher fetch thêm lần nữa. Khi filter đổi ở page > 1, code chỉ reset page; page watcher là trigger request duy nhất. Khi đang page 1, filter watcher tự schedule search.

Debounce 250 ms chỉ là UX/performance choice cần đo bằng behavior thực tế. Không nên chọn 500 ms như một con số magic nếu làm UI cảm giác chậm.

## Trade-offs

Cancellation thường xuyên có thể làm backend ghi nhận nhiều aborted requests nếu user gõ rất nhanh. Đây vẫn thường tốt hơn hoàn thành mọi expensive search, nhưng phải đo.

Generation guard thêm state logic. Nếu application đã dùng TanStack Query/Vue Query hoặc abstraction tương đương, có thể tái sử dụng cancellation/cache/dedup semantics thay vì tự viết. Không nên thêm library mới chỉ để giải quyết một component đơn giản nếu team chưa dùng nó.

Debounce giảm backend traffic nhưng tăng perceived latency sau keystroke. Với search suggestion, có thể dùng 150–300 ms; với explicit submit, có thể không cần debounce. Đây là product/UX trade-off cần đo.

Abort client request không có nghĩa toàn bộ SQL/Elasticsearch work downstream chắc chắn bị hủy. ASP.NET Core phải propagate `RequestAborted`, và dependency client/query cũng phải respect cancellation.

## Cách kiểm thử

1. **Deterministic race test:** mock request A (`camera`) delay 2 giây, request B (`camera lens`) delay 100 ms; xác minh A hoàn tất sau cũng không overwrite B.
2. **Duplicate-request test:** đang ở page 5 rồi đổi category; xác minh chỉ một effective request được gửi cho page 1.
3. **Error ordering test:** request A fail muộn sau khi B success; xác minh error banner không xuất hiện và B data vẫn giữ nguyên.
4. **Unmount/cancellation test:** unmount component khi fetch đang chạy; xác minh controller abort và không có state commit sau cleanup.
5. **Browser/E2E test:** Playwright nhập nhanh nhiều ký tự, đổi category/page, intercept network với delays khác nhau; xác minh UI cuối cùng luôn khớp filter cuối cùng.

Theo dõi frontend/browser:

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication chỉ xác nhận identity; object-level authorization vẫn phải kiểm tra quyền trên resource cụ thể.
- Tenant isolation nên dùng server-owned security context và được enforce tại data/query boundary, không dựa trên input do client kiểm soát.
- Cache là một phần của security architecture: cache key và lookup order không được bypass authorization invariant.
- Trong frontend async flow, request start order không đảm bảo response completion order; UI phải có semantics rõ ràng cho “latest intent wins”.
- Debounce là traffic optimization, không phải correctness mechanism cho out-of-order responses.
- Cancellation nên đi cùng generation/version guard khi stale result không được phép commit.

## Mẫu tư duy cần nhớ

- **Authenticate identity, authorize the resource.**
- **Không dùng client-controlled input làm security authority.**
- **Mọi optimization path như cache phải giữ nguyên security invariant.**
- **Latest user intent phải thắng latest network completion.**
- **Giảm request bằng debounce, bảo đảm correctness bằng cancellation/versioning.**
