# Code Review Challenge 1 — Upload tài liệu làm tăng memory, ghi đè blob và tạo dữ liệu không nhất quán

**Chủ đề:** ASP.NET Core, C#/.NET, Azure Blob Storage, file upload security, reliability, data consistency  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép người dùng upload tài liệu vào hồ sơ khách hàng.

Hệ thống hiện tại:

- chạy trên Azure App Service với nhiều instance;
- dùng Azure Blob Storage để lưu file;
- dùng SQL Server thông qua Entity Framework Core để lưu metadata;
- endpoint đã yêu cầu authentication;
- file thường có kích thước 1–20 MB, nhưng thỉnh thoảng có file 200–500 MB;
- traffic bình thường thấp, nhưng vào cuối tháng có thể có nhiều upload đồng thời;
- client mobile đôi khi retry request khi mất mạng hoặc timeout;
- production đã ghi nhận một số hiện tượng:
  - memory của App Service tăng mạnh khi nhiều người upload cùng lúc;
  - một số document record trong database trỏ tới nội dung không đúng với file người dùng đã upload;
  - đôi khi blob tồn tại nhưng không có record tương ứng trong SQL;
  - một số request bị client hủy nhưng server vẫn tiếp tục upload;
  - support phát hiện hai user có thể dùng cùng tên file như `statement.pdf`.

Một developer đề xuất endpoint sau.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/customers/{customerId}/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpPost]
    public async Task<ActionResult<object>> Upload(
        string customerId,
        IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Empty file.");

        var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        buffer.Position = 0;

        var blobName = $"{customerId}/{file.FileName}";
        var blobClient = _container.GetBlobClient(blobName);

        await blobClient.UploadAsync(buffer, overwrite: true);

        var document = new Document
        {
            Id = Guid.NewGuid(),
            CustomerId = customerId,
            BlobName = blobName,
            OriginalFileName = file.FileName,
            ContentType = file.ContentType,
            Size = file.Length,
            Status = "Ready",
            CreatedUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Uploaded {FileName} to {BlobUri} for customer {CustomerId}",
            file.FileName,
            blobClient.Uri,
            customerId);

        return Ok(new
        {
            document.Id,
            document.OriginalFileName,
            document.Size
        });
    }
}
```

## Kết quả code review tham khảo

### Critical — Broken object-level authorization trên `customerId`

**Vấn đề:**  
Endpoint chỉ có `[Authorize]`, nhưng không kiểm tra principal hiện tại có quyền upload document cho `customerId` hay không.

**Tại sao xảy ra:**  
Authentication chỉ xác nhận user là ai. Nó không tự động đảm bảo user có authorization trên resource cụ thể được chọn bằng route parameter.

**Ảnh hưởng production:**  
Một user hợp lệ có thể thử thay `customerId` và upload file vào hồ sơ của customer khác. Đây là broken object-level authorization và có thể dẫn tới data tampering hoặc data leakage ở các flow downstream.

**Cách sửa:**  
Thực hiện resource-based authorization hoặc query ownership/permission trước khi chấp nhận upload. Không tin trực tiếp `customerId` từ URL chỉ vì request đã authenticated.

---

### High — Toàn bộ file được buffer vào memory trước khi upload

**Vấn đề:**  
`MemoryStream` chứa toàn bộ nội dung file.

**Tại sao xảy ra:**  
`CopyToAsync(buffer)` sao chép toàn bộ `IFormFile` vào managed memory trước khi Blob upload bắt đầu.

**Ảnh hưởng production:**  
Nhiều file lớn upload đồng thời có thể làm tăng allocation, Gen 2/LOH pressure, GC pause và thậm chí dẫn tới process recycle hoặc out-of-memory. Với nhiều App Service instance, vấn đề vẫn tồn tại trên từng instance.

**Cách sửa:**  
Stream trực tiếp từ `file.OpenReadStream()` sang Blob Storage, đồng thời cấu hình request/body size limit phù hợp. Không dùng memory làm staging area nếu không thực sự cần random access hoặc transformation.

---

### High — User-controlled filename được dùng làm blob identity và `overwrite: true`

**Vấn đề:**  
Blob name là `customerId/file.FileName` và upload cho phép overwrite.

**Tại sao xảy ra:**  
Tên file do client gửi lên không phải một stable unique identifier.

**Ảnh hưởng production:**  
Hai upload cùng tên có thể ghi đè lẫn nhau. Database có thể có nhiều `Document` record khác nhau nhưng cùng `BlobName`; tất cả có thể trỏ tới blob cuối cùng. Retry cũng có thể thay đổi nội dung của blob đã được record trước đó.

**Cách sửa:**  
Tạo `DocumentId` độc lập và dùng ID đó làm blob key, ví dụ `{customerId}/{documentId:N}`. Lưu original filename chỉ như metadata hiển thị. Không dùng tên file do user cung cấp làm storage identity.

---

### High — Không có idempotency cho client retry

**Vấn đề:**  
Mỗi retry tạo một `Guid` mới và thực hiện upload mới.

**Tại sao xảy ra:**  
Endpoint không nhận idempotency key hoặc request identity bền vững.

**Ảnh hưởng production:**  
Client timeout sau khi server đã xử lý thành công nhưng chưa nhận response có thể retry và tạo duplicate document. Trong flow có billing, workflow hoặc downstream event, duplicate có thể gây side effect lớn hơn.

**Cách sửa:**  
Cho client gửi `Idempotency-Key` hoặc upload command ID; tạo unique constraint theo tenant/customer + idempotency key. Khi nhận retry, trả lại kết quả trước đó hoặc tiếp tục state machine thay vì tạo resource mới.

---

### High — SQL và Blob Storage có partial-failure window

**Vấn đề:**  
Blob được upload trước, rồi metadata mới được commit vào SQL.

**Tại sao xảy ra:**  
Hai storage system không cùng transaction boundary.

**Ảnh hưởng production:**  
Nếu Blob upload thành công nhưng SQL fail, blob orphan sẽ tồn tại. Nếu đảo thứ tự mà không có state machine, có thể xuất hiện record trỏ tới blob chưa tồn tại.

**Cách sửa:**  
Thiết kế explicit lifecycle, ví dụ `Pending → Ready / Failed`. Tạo metadata trước với unique document ID, upload blob, sau đó chuyển trạng thái sang `Ready`. Nếu upload thất bại, mark `Failed` và/hoặc chạy cleanup. Nếu business yêu cầu mạnh hơn, dùng outbox/background reconciliation thay vì giả định atomicity.

---

### High — Không propagate `CancellationToken`

**Vấn đề:**  
`CopyToAsync`, Blob upload và `SaveChangesAsync` đều không nhận request cancellation.

**Tại sao xảy ra:**  
Action không nhận `CancellationToken` hoặc dùng `HttpContext.RequestAborted`.

**Ảnh hưởng production:**  
Khi client đóng kết nối hoặc timeout, server có thể tiếp tục consume CPU, network và Blob throughput cho một request mà caller không còn chờ.

**Cách sửa:**  
Nhận `CancellationToken cancellationToken` trong action và truyền xuyên suốt các operation hỗ trợ cancellation. Đồng thời xác định rõ bước nào cần hoàn tất dù client đã disconnect để tránh để resource ở trạng thái không xác định.

---

### Medium — Không giới hạn kích thước và thiếu validation file thực tế

**Vấn đề:**  
Code chỉ kiểm tra `Length > 0`.

**Tại sao xảy ra:**  
Không có application-level policy cho max size, extension/type, signature, allowed business document types hoặc malware scanning.

**Ảnh hưởng production:**  
Có thể bị resource exhaustion, storage abuse, upload file không được phép hoặc content type giả.

**Cách sửa:**  
Áp dụng size limit ở reverse proxy/server và application. Treat `ContentType` và filename từ client như untrusted metadata. Nếu business yêu cầu, kiểm tra file signature và đưa file vào quarantine/scanning flow trước khi mark `Ready`.

---

### Medium — `MemoryStream` không được dispose

**Vấn đề:**  
`MemoryStream` không nằm trong `using`/ `await using`.

**Tại sao xảy ra:**  
Code tạo stream thủ công rồi bỏ reference sau request.

**Ảnh hưởng production:**  
Với `MemoryStream`, rủi ro chính vẫn là managed memory pressure hơn là native handle leak, nhưng lifecycle không rõ ràng và pattern này dễ trở thành leak nghiêm trọng khi thay bằng stream có unmanaged resource.

**Cách sửa:**  
Dùng scoped disposal hoặc tốt hơn là tránh intermediate buffer hoàn toàn.

---

### Medium — Không có explicit failure state hoặc cleanup/reconciliation

**Vấn đề:**  
Record chỉ được tạo ở trạng thái `Ready`; failure path không lưu trạng thái tiến trình.

**Tại sao xảy ra:**  
Implementation coi upload + DB write như một operation nguyên tử.

**Ảnh hưởng production:**  
Support khó phân biệt upload đang xử lý, upload thất bại và orphan blob. Retry logic cũng khó an toàn.

**Cách sửa:**  
Mô hình hóa state rõ ràng, có cleanup job/reconciliation cho `Pending` quá lâu, `Failed` hoặc orphan blob.

---

### Medium — Logging chưa đủ để điều tra distributed failure

**Vấn đề:**  
Log chỉ ghi filename, blob URI và customer ID sau thành công.

**Tại sao xảy ra:**  
Không có document ID, idempotency key, duration, blob upload result, failure stage hoặc correlation context.

**Ảnh hưởng production:**  
Khó trace một request qua API → SQL → Blob Storage, đặc biệt khi client retry.

**Cách sửa:**  
Structured log theo `DocumentId`, `CustomerId`, `IdempotencyKey`, correlation/trace ID, size, duration và state transition. Không log SAS token, secrets hoặc file content.

## Phiên bản đề xuất

Ví dụ dưới đây giả định:

- đã có resource authorization service;
- client gửi `Idempotency-Key`;
- database có unique constraint cho `(CustomerId, IdempotencyKey)`;
- original filename chỉ là metadata;
- file policy cho phép tối đa 100 MB trong endpoint này;
- malware scanning, nếu bắt buộc, sẽ là một bước riêng trước khi chuyển sang `Ready`.

```csharp
[HttpPost]
public async Task<ActionResult<object>> Upload(
    string customerId,
    IFormFile file,
    [FromHeader(Name = "Idempotency-Key")] string idempotencyKey,
    CancellationToken cancellationToken)
{
    if (!await _authorization.CanUploadDocumentAsync(
            User, customerId, cancellationToken))
        return Forbid();

    if (file is null || file.Length == 0)
        return BadRequest("Empty file.");

    const long maxBytes = 100L * 1024 * 1024;
    if (file.Length > maxBytes)
        return BadRequest("File too large.");

    if (string.IsNullOrWhiteSpace(idempotencyKey))
        return BadRequest("Idempotency-Key is required.");

    var existing = await _db.Documents
        .SingleOrDefaultAsync(
            x => x.CustomerId == customerId &&
                 x.IdempotencyKey == idempotencyKey,
            cancellationToken);

    if (existing is not null)
    {
        return Ok(new
        {
            existing.Id,
            existing.OriginalFileName,
            existing.Size,
            existing.Status
        });
    }

    var documentId = Guid.NewGuid();
    var blobName = $"{customerId}/{documentId:N}";

    var document = new Document
    {
        Id = documentId,
        CustomerId = customerId,
        IdempotencyKey = idempotencyKey,
        BlobName = blobName,
        OriginalFileName = Path.GetFileName(file.FileName),
        ContentType = file.ContentType,
        Size = file.Length,
        Status = "Pending",
        CreatedUtc = DateTime.UtcNow
    };

    _db.Documents.Add(document);
    await _db.SaveChangesAsync(cancellationToken);

    try
    {
        await using var input = file.OpenReadStream();

        await _container.UploadBlobAsync(
            blobName,
            input,
            cancellationToken);

        document.Status = "Ready";
        document.ReadyUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Document {DocumentId} uploaded for customer {CustomerId}. Size={Size}",
            document.Id,
            customerId,
            document.Size);

        return Ok(new
        {
            document.Id,
            document.OriginalFileName,
            document.Size,
            document.Status
        });
    }
    catch (OperationCanceledException)
    {
        document.Status = "Failed";
        await TryPersistFailureState(document, CancellationToken.None);
        throw;
    }
    catch (Exception ex)
    {
        document.Status = "Failed";
        await TryPersistFailureState(document, CancellationToken.None);

        _logger.LogError(
            ex,
            "Upload failed for document {DocumentId} customer {CustomerId}",
            document.Id,
            customerId);

        throw;
    }
}
```

Điểm cần lưu ý: implementation trên vẫn không tạo atomic transaction giữa SQL và Blob Storage. Nó chủ động biến partial failure thành state có thể quan sát và reconcile. Với hệ thống có yêu cầu cao hơn, có thể chuyển phần upload/finalization sang asynchronous workflow và dùng outbox/reconciliation.

## Giải thích thiết kế sau khi sửa

### 1. Tách storage identity khỏi filename

`DocumentId` là identity của object. Filename do user gửi chỉ còn là display metadata. Điều này loại bỏ collision theo tên file và tránh việc overwrite một blob cũ chỉ vì người dùng upload lại `statement.pdf`.

### 2. Stream thay vì buffer toàn bộ file

Streaming giảm peak managed-memory usage. Nó không làm network hoặc storage miễn phí; request dài vẫn chiếm connection và throughput, nhưng không cần giữ toàn bộ file trong process memory.

### 3. Explicit state machine

`Pending`, `Ready`, `Failed` làm failure observable. Một reconciliation job có thể tìm `Pending` quá lâu, kiểm tra blob, retry hoặc cleanup theo policy.

### 4. Idempotency được thiết kế cùng retry

Retry là hành vi bình thường của mobile/networked systems. Idempotency key + unique constraint giúp duplicate request không biến thành duplicate business resource.

### 5. Authorization ở resource boundary

User phải được authorize trên chính customer/document scope chứ không chỉ authenticated.

## Trade-offs

- Tạo record `Pending` trước upload có thể để lại record thất bại; đổi lại hệ thống có audit trail và dễ reconcile.
- Idempotency key cần database constraint và policy retention.
- Streaming khiến server vẫn làm proxy cho toàn bộ file. Với file rất lớn hoặc traffic cao, direct-to-Blob bằng short-lived SAS có thể giảm tải API, nhưng sẽ cần flow riêng cho authorization, finalize, validation/scanning và cleanup.
- Malware scanning/quarantine tăng latency và complexity nhưng có thể bắt buộc với tài liệu do user upload.
- Không nên chọn max file size chỉ theo cảm tính; phải dựa trên product requirement, App Service/network/storage constraints và load test.

## Cách kiểm thử

1. **Integration test — authorization:** user A thử upload vào `customerId` của user B và phải bị từ chối.
2. **Concurrency/idempotency test:** gửi nhiều request đồng thời với cùng `Idempotency-Key`; chỉ một business document được tạo.
3. **Load test:** upload đồng thời nhiều file lớn và quan sát working set, GC, request duration, throughput và failure rate.
4. **Failure-path test:** inject Blob failure sau khi tạo `Pending`; record phải chuyển `Failed` hoặc được reconciliation xử lý.
5. **Cancellation test:** hủy request khi đang upload; xác minh operation dừng hợp lý và state không bị báo sai là `Ready`.

## Quan sát trong production

Theo dõi:

- request rate và request duration cho upload endpoint;
- p95/p99 upload duration theo file-size bucket;
- process memory, GC heap size, Gen 2 collections và allocation rate;
- HTTP 4xx/5xx;
- Blob dependency duration/failure trong Application Insights;
- SQL dependency duration/failure;
- số record theo `Pending/Ready/Failed`;
- số `Pending` vượt SLA nội bộ;
- duplicate idempotency-key hits;
- orphan cleanup count;
- correlation giữa request trace, `DocumentId` và Blob operation;
- alert khi failure rate, memory hoặc số `Pending` tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển từ backend-proxy upload sang direct upload bằng SAS, và authorization/finalization sẽ thay đổi thế nào?
2. Nếu business yêu cầu virus scanning trước khi file được tải xuống, bạn sẽ thiết kế state machine và storage layout ra sao?
3. Nếu SQL commit `Ready` thất bại sau khi Blob upload thành công, reconciliation sẽ xác định source of truth như thế nào?

# Code Review Challenge 2 — Kubernetes rollout biến dependency degradation thành restart storm

**Chủ đề:** Kubernetes, ASP.NET Core hosting, probes, deployment safety, resource management, graceful shutdown  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 7–10 vấn đề

## Bối cảnh

Một ASP.NET Core API đang được chuyển từ IIS/Windows Server sang Kubernetes.

Thông tin production:

- deployment có 4 replicas;
- ứng dụng khởi động bình thường mất khoảng 20–35 giây;
- khi startup, code hiện tại có thể chạy EF Core migration nếu `RUN_MIGRATIONS_ON_STARTUP=true`;
- endpoint `/health/dependencies` kiểm tra:
  - SQL Server;
  - Redis;
  - một third-party review API;
- mất Redis không làm core transaction ngừng hoàn toàn: ứng dụng có thể fallback xuống database với performance thấp hơn;
- mất third-party review API chỉ làm một widget review tạm thời unavailable;
- request business dài nhất thường khoảng 15–20 giây;
- telemetry gần đây cho thấy một pod có:
  - memory bình thường khoảng 180 MiB;
  - peak khoảng 320 MiB;
  - CPU p95 khoảng 0.6 core trong giờ cao điểm;
- deployment gần đây gặp hiện tượng:
  - pods restart liên tục khi Redis chập chờn;
  - rollout đôi khi giảm capacity đáng kể;
  - rollback khó xác định chính xác image nào đã chạy;
  - có request đang xử lý bị terminate giữa chừng.

## Đoạn code cần review

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: customer-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 2
      maxSurge: 2
  selector:
    matchLabels:
      app: customer-api
  template:
    metadata:
      labels:
        app: customer-api
    spec:
      terminationGracePeriodSeconds: 10
      containers:
        - name: api
          image: contoso.azurecr.io/customer-api:latest
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: RUN_MIGRATIONS_ON_STARTUP
              value: "true"
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: customer-api-secrets
                  key: main-db
          readinessProbe:
            httpGet:
              path: /health/dependencies
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 1
            failureThreshold: 1
          livenessProbe:
            httpGet:
              path: /health/dependencies
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 1
            failureThreshold: 1
          resources:
            requests:
              cpu: "100m"
```

## Nhiệm vụ của ứng viên

Hãy review manifest và deployment design trên.

Bạn cần:

1. xác định correctness/reliability risks;
2. chỉ ra vấn đề nào giải thích restart storm;
3. đánh giá readiness, liveness và startup behavior;
4. đánh giá rolling deployment và graceful shutdown;
5. đánh giá cách chạy database migration;
6. đánh giá image/versioning và resource configuration;
7. đề xuất manifest/design tốt hơn;
8. giải thích cách validate rollout và telemetry cần quan sát.

## Câu hỏi gợi mở

1. Một external dependency fail có đồng nghĩa process ASP.NET Core cần bị restart không?
2. Với startup 20–35 giây, liveness bắt đầu sau 5 giây có thể gây điều gì?
3. Khi 4 replicas cùng startup với `RUN_MIGRATIONS_ON_STARTUP=true`, chuyện gì có thể xảy ra?
4. `maxUnavailable: 2` có phù hợp khi production đang tải cao không?
5. Với memory peak 320 MiB, limit 256 MiB có ý nghĩa gì?

## Gợi ý

### Gợi ý 1

Rủi ro lớn nhất nằm ở việc **đồng nhất process health với dependency health**, cộng với rollout/startup configuration quá aggressive.

### Gợi ý 2

Hãy phân biệt rõ:

- **startup probe**: app đã khởi động xong chưa;
- **liveness probe**: process có bị stuck và cần restart không;
- **readiness probe**: pod có nên nhận traffic lúc này không.

Một dependency không critical không nên tự động biến thành liveness failure.

## Kết quả code review tham khảo

### Critical — Liveness probe phụ thuộc SQL, Redis và third-party API

**Vấn đề:**  
`livenessProbe` gọi `/health/dependencies`, endpoint kiểm tra cả dependency bên ngoài.

**Tại sao xảy ra:**  
Manifest dùng cùng một health endpoint cho nhiều semantics khác nhau.

**Ảnh hưởng production:**  
Khi Redis hoặc third-party API chập chờn, kubelet có thể coi container là unhealthy và restart process dù bản thân ASP.NET Core process vẫn khỏe. Nhiều pod cùng fail dependency sẽ cùng restart, tạo restart storm và làm outage nặng hơn.

**Cách sửa:**  
Tạo liveness endpoint chỉ kiểm tra process-level health, ví dụ `/health/live`, không phụ thuộc remote service. Dependency degradation cần được xử lý bằng readiness hoặc application-level fallback tùy mức criticality.

---

### High — Không có startup probe trong khi startup mất 20–35 giây

**Vấn đề:**  
Liveness bắt đầu sau `initialDelaySeconds: 5` và chỉ chịu một failure.

**Tại sao xảy ra:**  
Container chưa hoàn tất startup đã bị đánh giá theo liveness policy.

**Ảnh hưởng production:**  
Pod có thể bị restart trước khi startup xong, dẫn tới crash/restart loop dù application không có bug runtime.

**Cách sửa:**  
Dùng `startupProbe` với budget đủ cho startup thực tế. Khi startup probe tồn tại, liveness/readiness sẽ không bắt đầu cho tới khi startup probe thành công.

---

### High — Readiness gắn với dependency không critical

**Vấn đề:**  
`/health/dependencies` fail nếu Redis hoặc third-party review API fail.

**Tại sao xảy ra:**  
Health model không phân biệt core dependency với degraded optional capability.

**Ảnh hưởng production:**  
Nếu Redis hoặc review provider outage, tất cả pod có thể trở thành unready và bị rút khỏi Service dù API vẫn có thể phục vụ phần lớn chức năng. Một partial dependency failure bị khuếch đại thành full application outage.

**Cách sửa:**  
Readiness chỉ nên phản ánh các điều kiện thực sự khiến pod không thể phục vụ traffic an toàn. Với Redis có fallback và review API là optional, chúng nên được báo qua metrics/degraded status thay vì bắt buộc readiness fail. SQL có thể vẫn là readiness-critical nếu core request không thể xử lý thiếu SQL.

---

### High — Chạy EF Core migration từ mỗi replica khi startup

**Vấn đề:**  
`RUN_MIGRATIONS_ON_STARTUP=true` trên toàn bộ replicas.

**Tại sao xảy ra:**  
Rolling deployment có thể start nhiều pod mới đồng thời.

**Ảnh hưởng production:**  
Nhiều instance có thể cạnh tranh migration, lock schema hoặc fail startup theo thứ tự không đoán trước. Với migration destructive/non-backward-compatible, rollout và rollback càng rủi ro.

**Cách sửa:**  
Tách migration thành deployment step/job có ownership rõ ràng và chạy một lần. Thiết kế migration theo backward-compatible rollout khi có zero-downtime requirement. Application pods không nên mặc định tự tranh nhau migrate production schema.

---

### High — Resource limits thấp hơn observed production peak

**Vấn đề:**  
Memory limit là 256 MiB trong khi observed peak khoảng 320 MiB; CPU limit 250m trong khi p95 khoảng 0.6 core.

**Tại sao xảy ra:**  
Resource values có vẻ được chọn thấp hơn workload thực tế.

**Ảnh hưởng production:**  
Memory vượt cgroup limit có thể dẫn tới OOM termination. CPU limit thấp có thể gây throttling, làm startup/probe/request latency xấu hơn và tạo feedback loop với probe failures.

**Cách sửa:**  
Đặt requests/limits dựa trên measured workload và load test, có headroom hợp lý. Với dữ liệu scenario này, values hiện tại rõ ràng cần tăng và tiếp tục tuning bằng telemetry.

---

### High — `latest` làm artifact không deterministic

**Vấn đề:**  
Deployment sử dụng `customer-api:latest`.

**Tại sao xảy ra:**  
Tag mutable không chỉ ra build/release cụ thể.

**Ảnh hưởng production:**  
Hai pod tạo ở thời điểm khác nhau có thể pull các image khác nhau dù manifest không đổi. Rollback và incident investigation khó xác định artifact thực tế.

**Cách sửa:**  
Dùng immutable version tag hoặc image digest. Release pipeline phải ghi nhận chính xác image identifier được deploy.

---

### Medium — Rolling update có thể làm mất quá nhiều capacity

**Vấn đề:**  
Với 4 replicas, `maxUnavailable: 2` cho phép 50% desired capacity unavailable trong rollout.

**Tại sao xảy ra:**  
Policy không phản ánh capacity requirement của production.

**Ảnh hưởng production:**  
Trong giờ cao điểm, còn 2 pod có thể không đủ tải. Nếu pod mới còn startup chậm hoặc fail readiness, rollout càng dễ gây latency/5xx.

**Cách sửa:**  
Nếu requirement cần giữ full serving capacity, dùng `maxUnavailable: 0` và `maxSurge: 1` hoặc policy khác dựa trên cluster headroom và traffic. Không có một con số đúng cho mọi hệ thống.

---

### Medium — Graceful shutdown budget ngắn hơn request dài nhất

**Vấn đề:**  
`terminationGracePeriodSeconds: 10` trong khi request có thể kéo dài 15–20 giây.

**Tại sao xảy ra:**  
Pod có thể nhận SIGTERM nhưng chưa đủ thời gian drain in-flight request trước khi bị force kill.

**Ảnh hưởng production:**  
Client nhận reset/5xx hoặc operation bị cắt giữa chừng. Nếu request có side effect, retry có thể tạo duplicate nếu API không idempotent.

**Cách sửa:**  
Thiết kế graceful shutdown, readiness transition/draining và termination grace period theo request characteristics thực tế. Với scenario này, 10 giây là thấp hơn observed request duration nên cần điều chỉnh.

---

### Medium — Probe thresholds quá nhạy với transient latency

**Vấn đề:**  
`timeoutSeconds: 1` và `failureThreshold: 1`.

**Tại sao xảy ra:**  
Một transient slow response có thể lập tức thay đổi pod state.

**Ảnh hưởng production:**  
Under load hoặc network jitter, pod có thể flap giữa ready/unready; nếu áp dụng cho liveness thì còn có thể restart không cần thiết.

**Cách sửa:**  
Tune timeout, period và failure threshold bằng startup/runtime SLO và telemetry. Không dùng probe như request-level SLA monitor.

## Phiên bản đề xuất

Ví dụ dưới đây dùng các giả định:

- application cung cấp `/health/startup`, `/health/live`, `/health/ready`;
- `/health/live` không gọi remote dependency;
- `/health/ready` chỉ fail với dependency thật sự critical;
- migration đã được tách ra khỏi application startup;
- image tag là immutable release identifier;
- resources dựa trên số liệu scenario và vẫn cần tiếp tục load-test/tuning.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: customer-api
spec:
  replicas: 4
  progressDeadlineSeconds: 600
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: customer-api
  template:
    metadata:
      labels:
        app: customer-api
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          image: contoso.azurecr.io/customer-api:2026.09.07.1
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: customer-api-secrets
                  key: main-db

          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3

          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3

          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"

  name: customer-api
```

Database migration nên được thực hiện bằng một release step hoặc Kubernetes Job riêng có đảm bảo chỉ một migration owner thực thi tại một thời điểm. Với zero-downtime rollout, migration cần được thiết kế backward compatible giữa old và new application version.

## Giải thích thiết kế sau khi sửa

### 1. Ba health semantics tách biệt

- `startupProbe`: bảo vệ app trong giai đoạn khởi động.
- `livenessProbe`: xác định process có cần restart không.
- `readinessProbe`: xác định pod có nên nhận traffic không.

Việc tách ba semantics ngăn một transient dependency outage biến thành restart storm.

### 2. Degraded dependency không tự động bằng unavailable application

Redis có fallback và review API là optional. Chúng cần metrics/alert riêng. Chỉ dependency thật sự quyết định khả năng serve request mới nên ảnh hưởng readiness.

### 3. Rollout giữ capacity

`maxUnavailable: 0` giữ các pod cũ phục vụ cho tới khi pod mới ready, đổi lại cần cluster có headroom để surge thêm pod.

### 4. Artifact immutable

Versioned tag/digest cho phép biết chính xác release nào đang chạy và rollback về artifact cụ thể.

### 5. Resources dựa trên measurement

Scenario đã cho thấy 256 MiB limit thấp hơn peak memory 320 MiB và CPU 250m thấp hơn p95 load. Sample mới cho headroom lớn hơn, nhưng vẫn phải xác nhận bằng load test và production telemetry.

## Trade-offs

- `maxUnavailable: 0` cần dư cluster capacity; nếu cluster không có headroom, rollout có thể pending.
- Startup probe quá rộng có thể che startup bug lâu hơn; budget phải dựa trên measured startup time.
- Readiness chỉ kiểm tra critical dependency giúp tránh cascading outage, nhưng application phải implement fallback đúng và expose degraded metrics rõ ràng.
- Resource limit cao hơn giảm nguy cơ throttling/OOM nhưng có thể giảm bin-packing density và tăng infrastructure cost.
- Tách migration khỏi pod startup tăng pipeline complexity nhưng làm ownership, ordering và rollback rõ ràng hơn.
- Graceful shutdown dài hơn làm pod termination chậm hơn; cần cân bằng với maximum request duration và idempotency behavior.

## Cách kiểm thử

1. **Deployment validation:** rollout release mới dưới synthetic traffic; xác minh không có 5xx spike và desired capacity luôn được duy trì theo policy.
2. **Dependency failure test:** làm Redis hoặc review API unavailable; pod không được restart hàng loạt và core API vẫn phục vụ theo fallback design.
3. **Startup test:** artificially kéo dài startup khoảng 30 giây; startup probe cho phép app khởi động mà liveness không restart sớm.
4. **Resource/load test:** tạo workload gần production peak và quan sát CPU throttling, memory working set, OOM kills, latency và probe failures.
5. **Graceful shutdown test:** terminate pod khi có request 15–20 giây đang chạy; xác minh draining, completion/cancellation behavior và client retry semantics.

## Quan sát trong production

Theo dõi:

- pod restart count và restart reason;
- `OOMKilled`, container exit code;
- readiness/liveness/startup probe failures;
- rollout duration và số available/unavailable replicas;
- CPU usage, CPU throttling;
- memory working set và memory limit utilization;
- request rate, p95/p99 latency và 5xx;
- dependency telemetry cho SQL, Redis và third-party API;
- fallback activation count;
- pod termination duration và request failures trong rollout;
- image digest/version thực tế của từng pod;
- migration job status riêng biệt;
- Kubernetes events liên quan scheduling, probe failure và eviction.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL Server fail hoàn toàn, readiness nên phản ứng thế nào và tại sao khác với Redis outage?
2. Khi cluster không đủ capacity cho `maxSurge: 1`, bạn sẽ cân bằng rollout safety với infrastructure cost ra sao?
3. Nếu migration cần thay đổi schema không backward compatible, bạn sẽ chia release thành các phase thế nào để old và new version cùng tồn tại an toàn?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- File upload trong ASP.NET Core cần được nhìn như một **streaming + authorization + storage consistency** problem, không chỉ là API nhận `IFormFile`.
- User-controlled filename không nên trở thành storage identity.
- Retry phải được thiết kế cùng idempotency; không nên chờ production duplicate rồi mới bổ sung.
- SQL và Blob Storage không có transaction chung, vì vậy cần state machine, compensating action và reconciliation.
- Kubernetes probe không phải ba tên gọi cho cùng một health check:
  - startup xác định app đã boot xong;
  - liveness xác định process có cần restart;
  - readiness xác định pod có nên nhận traffic.
- External dependency degradation không nên tự động kích hoạt liveness restart.
- Deployment safety phụ thuộc artifact immutability, rollout capacity, resource measurement, graceful shutdown và database migration ordering.

## Mẫu tư duy cần nhớ

1. **Authorize the resource, not only the caller.**
2. **Stream large payloads; do not buffer by default.**
3. **Design retry together with idempotency and transaction boundaries.**
4. **Separate process health from dependency health.**
5. **Measure capacity before setting resource limits or rollout policy.**
