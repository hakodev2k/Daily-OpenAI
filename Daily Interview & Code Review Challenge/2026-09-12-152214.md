# Câu 1 — `HttpClient` “đã dùng async” nhưng production vẫn timeout, socket tăng và backend đổi IP thì lỗi kéo dài

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** C#/.NET 8, `HttpClient`, `SocketsHttpHandler`, connection pooling, DNS, timeout/cancellation, retries, resilience, ASP.NET Core, production diagnostics

## Bối cảnh

Một ASP.NET Core API gọi sang internal Pricing API cho mỗi request. Cả hai service đều chạy nhiều replicas phía sau load balancer. Pricing API đôi lúc rolling deployment làm backend IP thay đổi.

Code hiện tại:

```csharp
public sealed class PricingService
{
    public async Task<PriceDto?> GetPriceAsync(
        string productId,
        CancellationToken ct)
    {
        using var client = new HttpClient
        {
            BaseAddress = new Uri("https://pricing.internal")
        };

        client.DefaultRequestHeaders.Add("X-Caller", "orders-api");

        for (var attempt = 0; attempt < 3; attempt++)
        {
            try
            {
                using var response = await client.GetAsync(
                    $"/api/prices/{productId}", ct);

                if ((int)response.StatusCode >= 500)
                    continue;

                response.EnsureSuccessStatusCode();
                return await response.Content
                    .ReadFromJsonAsync<PriceDto>(cancellationToken: ct);
            }
            catch (HttpRequestException) when (attempt < 2)
            {
                await Task.Delay(100, ct);
            }
        }

        return null;
    }
}
```

Trong production:

- traffic bình thường khoảng 250 requests/second;
- khi promotion bắt đầu, traffic tăng lên 1,000 requests/second;
- outbound connection count tăng mạnh;
- một số instances bắt đầu có nhiều `HttpRequestException` và timeout;
- CPU application chưa quá cao;
- Pricing API vẫn healthy khi gọi trực tiếp từ cùng network;
- sau một rolling deployment của Pricing API, một vài Orders API instances tiếp tục lỗi lâu hơn các instances khác;
- team đề xuất hai hướng trái ngược: “tạo `HttpClient` mới mỗi request để luôn resolve DNS mới” và “dùng một singleton `HttpClient` mãi mãi để reuse socket”.

## Câu hỏi chính

Hãy giải thích lifecycle thực sự của `HttpClient`/HTTP connection trong .NET, vì sao code trên có thể gây vấn đề ở production dù mọi call đều `async`, trade-off giữa tạo client liên tục và giữ client quá lâu, cách `IHttpClientFactory`/`SocketsHttpHandler` giúp quản lý connection pooling và DNS refresh, và bạn sẽ thiết kế timeout/retry/cancellation thế nào để không biến một dependency chậm thành retry storm.

## Câu hỏi làm rõ nên cân nhắc

1. Pricing API dùng HTTP/1.1 hay HTTP/2, và có proxy/service mesh/load balancer ở giữa không?
2. Timeout hiện đến từ caller cancellation, `HttpClient.Timeout`, reverse proxy hay downstream?
3. Retry áp dụng với những status/error nào, có jitter/backoff và retry budget không?
4. Endpoint chỉ là GET idempotent hay sau này cùng policy được reuse cho POST/payment-like operations?
5. DNS TTL/load-balancer behavior và connection lifetime hiện được cấu hình thế nào?

## Gợi ý tư duy

### Gợi ý 1

`HttpClient` là abstraction ở trên một handler có connection pool. Disposing client liên tục không có nghĩa OS/network resources lập tức trở về trạng thái sạch.

### Gợi ý 2

Reuse connection tốt cho throughput, nhưng connection sống quá lâu có thể làm instance tiếp tục dùng endpoint cũ lâu hơn mong muốn. DNS refresh gắn với lúc tạo connection mới, không phải “mỗi request luôn resolve lại DNS”.

### Gợi ý 3

Retry là traffic amplification. Ba retries trên 1,000 RPS có thể biến downstream degradation thành nhiều nghìn attempts/second nếu không có backoff, jitter, timeout budget và giới hạn phù hợp.

## Cấu trúc trả lời đề xuất

1. Giải thích `HttpClient` → handler → connection pool.
2. Phân tích failure mode của tạo `new HttpClient()` mỗi request.
3. Phân tích failure mode của connection lifetime vô hạn.
4. Nêu vai trò của `IHttpClientFactory`/configured `SocketsHttpHandler`.
5. Thiết kế timeout/cancellation/retry theo end-to-end latency budget.
6. Đề xuất telemetry để phân biệt DNS, connection pool, downstream latency và retry amplification.
7. Nêu cách load test và failure injection trước rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra `async` không giải quyết socket/connection-pool management.
- Không tạo/dispose `HttpClient` per request trong high-throughput path theo cách trên.
- Hiểu connection pooling nằm ở handler và reuse connection giảm handshake/socket churn.
- Hiểu DNS thay đổi không đồng nghĩa mọi existing connection tự chuyển ngay sang IP mới.
- Đề xuất connection lifetime có giới hạn/configurable thay vì “singleton forever” một cách mù quáng.
- Retry phải có bounded attempts, backoff/jitter và chỉ cho lỗi phù hợp.
- Propagate `CancellationToken` và có timeout budget rõ ràng.

### Điểm cộng

- Phân biệt connection timeout, overall request timeout và caller cancellation.
- Đề cập `PooledConnectionLifetime`, `MaxConnectionsPerServer` khi workload cần.
- Dùng typed/named client để tập trung base address, headers và resilience policy.
- Không retry tất cả `5xx` hoặc mọi exception theo cùng policy.
- Đề cập connection metrics/dependency traces thay vì chỉ app CPU.

### Senior+

- Giải thích retry amplification và failure synchronization nếu mọi instance retry cùng 100 ms không jitter.
- Cân nhắc hedging/circuit breaker chỉ khi có evidence và idempotency phù hợp, không thêm pattern theo checklist.
- Định nghĩa end-to-end deadline: caller có 2 giây thì không thể cho ba attempts mỗi attempt 2 giây.
- Biết rằng DNS/service discovery behavior còn phụ thuộc proxy/LB/network topology; không khẳng định một cấu hình universal.

## Hướng giải quyết tham khảo

Một mental model tốt là: `HttpClient` không phải một TCP socket duy nhất. Nó gửi request thông qua `HttpMessageHandler`; với modern .NET, `SocketsHttpHandler` quản lý connection pools. Connection có thể được reuse cho nhiều requests, giảm TCP/TLS handshake và outbound resource churn.

Trong code hiện tại, mỗi application request tạo một `HttpClient` mới rồi dispose. Ở tải cao, pattern này tạo handler/connection churn thay vì tận dụng stable pool. Các connections vừa đóng còn có lifecycle ở OS/network stack; dưới burst traffic, hệ thống có thể cạn ephemeral ports/SNAT capacity hoặc chịu handshake overhead trước khi CPU application trông có vẻ bão hòa.

Giải pháp đối lập “một singleton client giữ mọi connection mãi mãi” cũng cần nuance. Reuse client/handler là đúng direction, nhưng long-lived pooled connections có thể tiếp tục đi tới endpoint cũ cho đến khi connection được đóng/replaced. Nếu infrastructure dựa vào DNS để thay backend, cần một connection lifetime phù hợp với expected DNS/service-discovery behavior.

`IHttpClientFactory` giúp centralize cấu hình và quản lý handler reuse/lifetime. Một typed client có thể như sau:

```csharp
builder.Services
    .AddHttpClient<PricingClient>(client =>
    {
        client.BaseAddress = new Uri("https://pricing.internal");
        client.DefaultRequestHeaders.Add("X-Caller", "orders-api");
    })
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5),
        ConnectTimeout = TimeSpan.FromSeconds(1),
        MaxConnectionsPerServer = 200
    });
```

Các con số trên chỉ là minh họa, phải tune từ topology, RPS và latency thực tế. Không copy `5 minutes`, `200 connections` sang production mà không đo.

Tiếp theo là resilience. Retry loop hiện tại có vài vấn đề:

- retry gần như ngay sau 100 ms và tất cả instances có thể đồng bộ retry;
- `500`, `503`, connection reset và timeout không nhất thiết nên có cùng policy;
- không có end-to-end deadline rõ;
- không ghi attempt count/elapsed time;
- khi cả ba attempts fail, trả `null` có thể che giấu dependency failure thành “không có price”.

Tôi sẽ bắt đầu từ request budget. Ví dụ Orders API có SLO 2 giây và Pricing thường p95 120 ms. Có thể cho một attempt timeout ngắn hơn tổng budget, tối đa 1–2 retries cho transient GET failures với exponential backoff + jitter, nhưng phải bảo đảm tổng thời gian không vượt deadline. Caller cancellation phải dừng retries ngay.

Với non-idempotent request, retry cần idempotency contract hoặc không được áp dụng mù quáng. Một policy dùng được cho GET không nên tự động reuse cho POST tạo order/payment.

Về telemetry, tôi muốn:

- dependency latency/error theo destination;
- attempts per logical request;
- retry rate và retry-success rate;
- active/queued outbound requests nếu có metric phù hợp;
- connection establishment/TLS/DNS evidence từ runtime/network diagnostics khi cần;
- `HttpRequestException` category và timeout/cancellation classification;
- Pricing API server-side RPS để thấy amplification;
- instance correlation để tìm lỗi chỉ ở một subset hosts.

Load test phải có cả steady-state và failure injection: tăng RPS, làm downstream chậm, trả `503`, reset connection, đổi backend/DNS theo deployment model. Success criteria không chỉ là “request cuối cùng pass”; phải xác minh socket/connection behavior ổn định, retries không nhân traffic quá mức, p99 và error rate phục hồi đúng.

## Mẫu trả lời trong phỏng vấn

“Điểm tôi sửa đầu tiên là mental model: `async` chỉ giúp thread không bị block khi chờ network; nó không quản lý connection pool cho chúng ta. Code này tạo một `HttpClient` mỗi request, tức là ở tải 1,000 RPS chúng ta tạo/dispose client/handler liên tục và làm tăng connection churn. Tôi muốn reuse handler/connection pool bằng `IHttpClientFactory` hoặc một properly configured long-lived client.

Nhưng tôi cũng không chọn singleton connections sống vô hạn. DNS thường được áp dụng khi tạo connection mới, nên nếu backend IP thay đổi mà pool giữ connection lâu thì một instance có thể tiếp tục dùng endpoint cũ. Tôi sẽ cấu hình connection lifetime phù hợp với infrastructure và đo behavior thực tế.

Retry cũng cần sửa. Ba attempts đồng loạt trên 1,000 RPS có thể biến outage thành retry storm. Tôi sẽ đặt end-to-end deadline, retry chỉ transient/idempotent operations, dùng backoff + jitter và dừng ngay khi caller cancellation xảy ra. Không trả `null` để che dependency failure nếu business cần phân biệt price-not-found với downstream-unavailable.

Trước khi rollout tôi load test cả normal traffic và fault injection, rồi theo dõi logical request rate, attempt rate, dependency latency/error, connection behavior và downstream RPS. Tôi muốn chứng minh pool ổn định và retry không khuếch đại incident.”

## Câu hỏi đào sâu

1. Nếu sau khi dùng `IHttpClientFactory`, một vài requests vẫn đi vào backend cũ sau DNS change, bạn sẽ điều tra connection lifetime/proxy behavior ra sao trước khi giảm lifetime xuống cực thấp?
2. Nếu Pricing API p99 là 800 ms nhưng Orders API end-to-end budget chỉ 1 giây, retry policy của bạn thay đổi thế nào?
3. Tôi đề xuất circuit breaker 30 giây cho mọi lỗi; bạn đồng ý hay phản đối dựa trên traffic pattern và recovery semantics nào?

## Lỗi trả lời thường gặp

- Nói “`HttpClient` phải luôn là singleton” mà không bàn handler/connection lifetime và DNS.
- Nghĩ `async` tự ngăn socket exhaustion.
- Retry mọi `5xx`/exception ba lần theo cùng policy.
- Không phân biệt timeout với cancellation.
- Chỉ benchmark success path, không test degraded downstream.

## Thang điểm 0–10

- **0–2:** Biết `HttpClient` có vấn đề nhưng chỉ nói “dùng singleton”.
- **3–4:** Hiểu connection reuse nhưng thiếu DNS/retry/timeout reasoning.
- **5–6:** Đề xuất `IHttpClientFactory`, connection lifetime và bounded retry hợp lý.
- **7–8:** Kết nối connection pooling, DNS, deadlines, retry amplification và telemetry.
- **9–10:** Thiết kế được resilience theo idempotency/SLO/topology, có failure-injection validation và biết tránh cả socket churn lẫn over-engineering.

# Câu 2 — Sau signing-key rotation, chỉ một số API instances trả `401` dù token của user vẫn hợp lệ

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** ASP.NET Core authentication, OAuth 2.0/OIDC, JWT validation, signing keys/JWKS, caching, clock skew, multi-instance diagnostics, security, observability, incident response

## Bối cảnh

Một employee platform dùng enterprise Identity Provider phát JWT access token. ASP.NET Core APIs validate token theo issuer/audience/signature. Hệ thống chạy 8 application instances phía sau load balancer.

Để “tối ưu latency”, một developer trước đây viết custom key cache:

```csharp
public sealed class SigningKeyProvider
{
    private readonly HttpClient _httpClient;
    private IReadOnlyList<JsonWebKey>? _cachedKeys;

    public SigningKeyProvider(HttpClient httpClient)
        => _httpClient = httpClient;

    public async Task<IReadOnlyList<JsonWebKey>> GetKeysAsync(
        CancellationToken ct)
    {
        if (_cachedKeys is not null)
            return _cachedKeys;

        var document = await _httpClient
            .GetFromJsonAsync<JwksDocument>(
                "https://identity.example.com/.well-known/jwks.json", ct);

        _cachedKeys = document!.Keys;
        return _cachedKeys;
    }
}
```

Một custom authentication handler lấy `kid` từ JWT header, tìm key trong list trên rồi validate signature.

Incident lúc 09:10:

- khoảng 18% authenticated requests bắt đầu trả `401`;
- login lại không luôn giải quyết được;
- token cùng một user gọi instance A thì `200`, instance B có thể `401`;
- Identity Provider dashboard cho biết vừa thực hiện signing-key rotation;
- restart toàn bộ API instances làm error rate về gần 0 nhưng 30 phút sau một subset lại xuất hiện `401` trong một test environment đang rotate keys thường xuyên;
- team đề xuất “nếu không tìm thấy `kid`, bỏ signature validation rồi chỉ check `exp` để user không bị gián đoạn”.

## Câu hỏi chính

Bạn sẽ xử lý incident theo thứ tự nào, xác định chính xác failure nằm ở token, key discovery/cache hay instance state ra sao, và thiết kế JWT validation/key refresh thế nào để chịu được signing-key rotation mà không giảm security? Hãy nêu cả mitigation khẩn cấp, root-cause fix, tests và telemetry.

## Câu hỏi làm rõ nên cân nhắc

1. Tỷ lệ `401` có correlate với một `kid`, issuer, audience hay một subset instances không?
2. API dùng built-in `JwtBearer` metadata discovery ở đâu, hay toàn bộ validation đã bị custom hóa?
3. `_cachedKeys` có lifetime singleton/process lifetime và có refresh/invalidation mechanism nào không?
4. Servers có time synchronization ổn định không, và failures là signature, issuer, audience, lifetime hay authorization sau authentication?
5. IdP giữ old signing keys trong JWKS trong overlap window bao lâu, và token lifetime là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

`401` chỉ là HTTP outcome. Trước tiên phải phân loại validation failure: signature key missing, invalid issuer/audience, expired/not-yet-valid token hay downstream authorization.

### Gợi ý 2

Một key cache “load một lần rồi giữ mãi” biến key rotation thành process-state bug. Multi-instance làm symptom phụ thuộc instance restart time/cache contents.

### Gợi ý 3

Không tìm thấy signing key là lý do để **refresh trusted metadata/key set**, không phải lý do để bỏ signature validation.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius và security posture.
2. Phân loại `401` theo validation exception/reason.
3. Correlate `kid` và instance/version/cache state.
4. Mitigate mà vẫn giữ cryptographic validation.
5. Sửa metadata/key refresh theo framework-supported path nếu có thể.
6. Kiểm thử overlapping old/new keys, propagation delay và IdP outage.
7. Bổ sung telemetry/alerts mà không log raw access tokens.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Tuyệt đối không bỏ signature validation để giữ availability.
- Nhận ra custom cache không bao giờ refresh là root-cause candidate mạnh.
- Correlate `kid` trong token với trusted key set từng instance.
- Phân biệt authentication failure với authorization failure.
- Ưu tiên built-in OIDC/JWT bearer metadata management thay vì custom crypto/cache khi không cần thiết.
- Có refresh path khi gặp unknown `kid`/key rollover.
- Không log full JWT/token vào production logs.

### Điểm cộng

- Đề cập issuer, audience, lifetime/clock và algorithm validation ngoài signature.
- Có overlap strategy: old token signed bằng key cũ vẫn phải valid nếu IdP còn publish/trust key đó.
- Có bounded metadata refresh/retry để không DDoS IdP discovery endpoint.
- Có cache refresh telemetry và instance correlation.
- Xử lý IdP metadata endpoint outage mà không accept untrusted keys.

### Senior+

- Biết key rotation là distributed consistency problem với propagation window và cache state.
- Không viết custom refresh-on-every-request; có throttling/single-flight/backoff.
- Phân biệt “refresh metadata” với “trust bất kỳ JWK nào tải được từ URL không được pin/validated”.
- Thiết kế tests cho old key/new key overlap, unknown key, malicious token, issuer mismatch và clock drift.

## Hướng giải quyết tham khảo

Đầu tiên, tôi từ chối mitigation “bỏ signature validation”. Nếu API chỉ check `exp` mà không xác minh signature/issuer/audience, attacker có thể tự tạo token và đặt expiry tùy ý. Availability incident không biện minh cho bypass authentication trust boundary.

Tôi sẽ xác định failure reason. Trong ASP.NET Core authentication events/logs, ghi structured reason an toàn như:

- `signature_key_not_found`;
- `invalid_signature`;
- `invalid_issuer`;
- `invalid_audience`;
- `token_expired`;
- `token_not_yet_valid`.

Không log raw bearer token. Có thể log `kid`, issuer đã normalize/allow-list, instance ID, auth middleware version và correlation ID vì những fields này hữu ích hơn.

Nếu 18% failures tập trung vào một `kid` mới và chỉ các instances cache JWKS cũ lỗi, hypothesis rất mạnh: process-level `_cachedKeys` không refresh. Restart làm cache load lại, vì vậy symptom tạm hết — đúng với incident.

Fix dài hạn là bỏ custom key management nếu framework đã hỗ trợ OIDC/JWT bearer discovery phù hợp. Cấu hình `AddJwtBearer` với trusted authority/issuer/audience để framework quản lý metadata/signing keys và rollover. Khi unknown signing key xuất hiện, validation pipeline có cơ chế refresh metadata phù hợp thay vì một list load đúng một lần.

Nếu business bắt buộc custom provider, nó cần ít nhất:

- cache có expiry/refresh lifecycle;
- lookup theo `kid`;
- khi `kid` không tồn tại, trigger một bounded refresh từ trusted metadata endpoint;
- single-flight/concurrency control để 1,000 requests không cùng refresh;
- retry/backoff hợp lý cho metadata endpoint;
- giữ last-known-good key set trong phạm vi an toàn khi refresh endpoint transiently unavailable;
- không xóa old keys quá sớm nếu tokens cũ vẫn còn hợp lệ và IdP còn công bố chúng.

Pseudo-flow:

```text
validate token header/algorithm
    ↓
find kid in current trusted key set
    ├─ found → validate signature + issuer + audience + lifetime
    └─ missing → request one throttled metadata refresh
                   ↓
                retry lookup once
                   ├─ found → validate normally
                   └─ missing → reject token
```

Điều quan trọng là “refresh once” vẫn kết thúc bằng reject nếu key không trở thành trusted. Không fetch arbitrary URL từ token header và không trust key do client chỉ định.

Mitigation khẩn cấp trong incident có thể là rolling restart/correct key-cache refresh nếu đó là cách nhanh nhất đã biết, nhưng phải làm controlled để không mất toàn bộ capacity và không coi restart là permanent fix. Nếu built-in config change đơn giản và đã được test, deploy nó canary trước.

Tests nên bao gồm:

1. token signed bằng old key trước rotation vẫn valid trong overlap window;
2. JWKS thêm new key, new-token first request trigger refresh và sau đó valid;
3. random unknown `kid` vẫn `401`;
4. token đúng key nhưng wrong issuer/audience bị reject;
5. expired/not-yet-valid token bị reject theo clock policy;
6. metadata endpoint timeout: system không bypass validation hoặc tạo request storm;
7. 100 concurrent tokens với same new `kid` chỉ gây bounded metadata refresh.

Telemetry:

- auth failures theo reason;
- unknown-`kid` count;
- metadata refresh attempts/success/failure/duration;
- current key-set age/version fingerprint nếu có cách an toàn;
- error rate theo instance;
- issuer/audience mismatch counts;
- system clock health.

Alert khi signature-key-not-found tăng đột biến hoặc nhiều instances có key-set age bất thường. Dashboard IdP rotation event/correlation giúp root cause nhanh hơn lần sau.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chấp nhận bỏ signature validation. Unknown `kid` là lý do refresh trusted signing metadata, không phải lý do tin token.

Tôi sẽ phân loại 401 trước: signature key missing, invalid signature, issuer, audience, lifetime hay authorization. Sau đó correlate `kid` và instance. Với code này, `_cachedKeys` load một lần rồi tồn tại hết process lifetime, nên việc chỉ một số instances lỗi sau signing-key rotation và restart tạm chữa được là bằng chứng rất mạnh cho stale JWKS cache.

Tôi ưu tiên bỏ custom key-cache/crypto path và dùng ASP.NET Core `JwtBearer` + trusted authority/metadata handling nếu requirements cho phép. Nếu phải custom, cache cần refresh lifecycle và khi không thấy `kid` thì thực hiện một bounded, single-flight refresh rồi validate lại đúng một lần. Nếu vẫn không thấy key trusted thì reject.

Tôi test cả old/new key overlap, unknown kid, wrong issuer/audience, metadata outage và concurrent refresh. Telemetry ghi failure reason, `kid`, instance và metadata refresh status nhưng không log raw JWT. Mitigation production có thể rolling restart để nạp key mới trong lúc deploy fix, nhưng không biến restart thành design.”

## Câu hỏi đào sâu

1. Nếu IdP metadata endpoint down đúng lúc key mới bắt đầu được dùng, bạn cân bằng availability và security thế nào?
2. Nếu old key biến mất khỏi JWKS trước khi tất cả token cũ hết hạn, responsibility nằm ở đâu và API nên phản ứng thế nào?
3. Tại sao “fetch JWKS mỗi request để luôn mới” cũng là một thiết kế tệ, và bạn chống refresh storm ra sao?

## Lỗi trả lời thường gặp

- Bỏ signature validation hoặc chấp nhận token khi unknown key.
- Restart pods rồi coi incident đã giải quyết.
- Log toàn bộ JWT để debug.
- Chỉ kiểm tra expiry mà bỏ issuer/audience/algorithm.
- Custom key refresh nhưng mọi request cùng gọi metadata endpoint.

## Thang điểm 0–10

- **0–2:** Đề xuất bypass validation hoặc chỉ restart.
- **3–4:** Nhận ra stale key cache nhưng thiếu secure refresh/validation design.
- **5–6:** Có đúng incident investigation, key refresh và framework-supported direction.
- **7–8:** Xử lý overlap, metadata outage, concurrency/throttling và telemetry tốt.
- **9–10:** Giữ security boundary chặt trong degraded conditions, hiểu distributed key rotation và thiết kế được tests/operations đủ mạnh mà không custom crypto không cần thiết.

# Câu 3 — Multi-tenant SaaS nên dùng shared database, schema-per-tenant hay database-per-tenant?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, EF Core, SQL Server/Azure SQL, multi-tenancy, data isolation, security, scalability, migrations, backup/restore, cost, observability, architecture trade-offs

## Bối cảnh

Team đang xây một B2B employee-management SaaS bằng ASP.NET Core + EF Core + SQL Server/Azure SQL.

Dự kiến 18 tháng tới:

- khoảng 500 tenant companies;
- 80% tenants có dưới 500 employees;
- 15% có 500–5,000 employees;
- khoảng 5% enterprise tenants có 20,000–100,000 employees;
- core domain giống nhau cho mọi tenant;
- một số tenant cần custom retention policy;
- enterprise sales bắt đầu hỏi về stronger data isolation và point-in-time restore cho riêng tenant;
- hiện team 7 backend developers + 2 DevOps/infra engineers;
- chưa có requirement mỗi tenant chạy code version riêng;
- deployment hiện muốn giữ một application version chung;
- budget infrastructure có giới hạn;
- compliance chưa bắt buộc physical database separation cho mọi khách hàng.

Ba đề xuất:

1. **Shared database + shared schema**, mọi bảng có `TenantId`.
2. **Schema-per-tenant** trong cùng SQL database.
3. **Database-per-tenant**, mỗi tenant có database riêng.

Một developer nói: “database-per-tenant an toàn nhất nên cứ chọn từ đầu”. Developer khác nói: “500 tenants thì shared DB luôn rẻ và đơn giản nhất, `HasQueryFilter(x => x.TenantId == currentTenant)` là đủ isolation”.

## Câu hỏi chính

Bạn sẽ đưa ra quyết định tenancy/data-isolation architecture thế nào? Hãy phân tích security boundary, noisy-neighbor risk, migrations, connection management, backup/restore, analytics/reporting, cost, operational burden và growth path. Nếu chọn hybrid model, hãy mô tả cách tenant được route đến đúng data store và cách tránh để abstraction migration/tenant-routing trở thành nguồn data leak.

## Câu hỏi làm rõ nên cân nhắc

1. Compliance/SLA có tenant nào bắt buộc dedicated database, region hoặc encryption key riêng không?
2. Restore requirement là restore toàn hệ thống hay restore một tenant về thời điểm cụ thể mà không ảnh hưởng tenants khác?
3. Workload có cross-tenant analytics/reporting ở operational database không?
4. Tenant size/RPS distribution có cực lệch không, và large tenant có thể gây lock/CPU/storage pressure cho small tenants không?
5. Team có tooling tự động provision/migrate/backup hàng trăm databases chưa?

## Gợi ý tư duy

### Gợi ý 1

Không có một tenancy model “an toàn nhất” tuyệt đối. Isolation mạnh hơn thường đổi lấy provisioning, migration, connection, observability và cost complexity.

### Gợi ý 2

EF Core global query filter là một guardrail, không phải toàn bộ security boundary. Raw SQL, missing filter, admin paths, background jobs và cache keys vẫn có thể leak cross-tenant data.

### Gợi ý 3

Hãy tách **logical tenant ownership** khỏi **physical placement**. Nếu application có `Tenant → DatabaseShard/Database` mapping rõ, có thể bắt đầu pooled/shared rồi đưa enterprise tenants sang dedicated storage khi requirement xuất hiện.

## Cấu trúc trả lời đề xuất

1. Làm rõ isolation/compliance/SLO/restore requirements.
2. So sánh ba options theo security, operations, performance và cost.
3. Xác định workload distribution và noisy-neighbor thresholds.
4. Chọn initial model + migration path.
5. Thiết kế tenant resolution/routing/security guardrails.
6. Thiết kế schema migration/provisioning/backup/restore.
7. Đề xuất observability và capacity planning per tenant.
8. Nêu trigger rõ để move tenant giữa placement tiers.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi `HasQueryFilter` là đủ security.
- Không mặc định database-per-tenant nếu operations chưa đáp ứng.
- So sánh restore/migration/cost/noisy-neighbor chứ không chỉ query convenience.
- Có tenant identity từ trusted authentication context, không lấy `TenantId` tùy ý từ request body/query.
- Tất cả caches/background jobs/files phải có tenant scoping.
- Có plan cho enterprise outliers thay vì thiết kế chỉ theo average tenant.

### Điểm cộng

- Đề xuất hybrid/pool model: shared database cho small tenants, dedicated database cho tenants có compliance/scale/SLA đặc biệt.
- Có central tenant catalog để map `TenantId` → placement/connection metadata.
- Có migration automation theo database fleet với version tracking và bounded rollout.
- Có per-tenant metrics/quota/throttling.
- Tách analytics khỏi OLTP khi cross-tenant reporting lớn.

### Senior+

- Thiết kế tenant move/rebalancing an toàn giữa databases.
- Có encryption/secrets/connection credential strategy.
- Cân nhắc blast radius của schema migration và backup restore.
- Có explicit data-leak defenses ở repository/query/cache/logging/observability layers.
- Nhận ra hybrid architecture chỉ đáng dùng nếu routing/provisioning automation đủ mature; nếu không, complexity có thể lớn hơn benefit.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu từ requirements thay vì chọn model theo khẩu hiệu.

### Shared database + shared schema

Ưu điểm:

- provisioning đơn giản;
- ít databases/connections cần vận hành;
- schema migration một nơi;
- cross-tenant analytics dễ hơn;
- cost utilization tốt cho hàng trăm small tenants.

Nhược điểm:

- blast radius lớn: migration/query lỗi có thể ảnh hưởng nhiều tenants;
- noisy neighbor nếu một enterprise tenant scan/lock/consume resources mạnh;
- per-tenant restore khó hơn vì backup là database-level, thường cần logical restore/export workflow;
- application bugs thiếu tenant predicate có thể leak dữ liệu.

Nếu dùng shared schema, `TenantId` phải là first-class key ở data model. Index strategy thường cần tenant dimension phù hợp với access pattern. Nhưng tôi không dựa vào EF global filter một mình. Tenant phải được resolve từ authenticated identity/host mapping/trusted tenant context; repository/query paths cần tests; raw SQL phải có review/guardrails; cache key phải chứa tenant; background jobs persist tenant ownership; authorization kiểm tra resource thuộc tenant.

### Schema-per-tenant

Nó tạo một chút namespace isolation nhưng thường mang phần lớn operational pain của nhiều schemas mà không có đầy đủ isolation/restore benefits của database-per-tenant. Migrations qua hàng trăm schemas, object count, tooling và query complexity tăng. Tôi chỉ chọn nếu platform/database constraints hoặc legacy model có lý do cụ thể, không coi đây là automatic middle ground.

### Database-per-tenant

Ưu điểm:

- blast radius/data isolation tốt hơn;
- backup/restore và tenant-specific maintenance dễ tách hơn;
- large tenant có thể scale/tune độc lập;
- compliance/dedicated-region requirements dễ đáp ứng hơn.

Nhược điểm:

- 500 databases cần automated provisioning, schema migrations, secret/connection management, monitoring và backup policies;
- deployment có fleet-migration problem: app version phải tương thích khi không phải mọi DB upgrade cùng millisecond;
- connection pools/cost có thể tăng;
- cross-tenant reporting khó hơn nếu query trực tiếp operational stores.

Với distribution hiện tại, tôi có xu hướng **hybrid placement** nếu enterprise requirements thực sự đủ mạnh: phần lớn small tenants ở một hoặc vài shared databases/shards; enterprise/compliance tenants có thể dedicated database. Nhưng tôi chỉ chọn hybrid nếu team xây được tenant catalog + automation đủ an toàn.

Một conceptual tenant catalog:

```text
TenantCatalog
---------------------------------------------
TenantId | PlacementType | DatabaseId | Region
A123     | Shared        | shard-01   | SEA
B456     | Dedicated     | tenant-b   | SEA
C789     | Shared        | shard-02   | EU
```

Request flow:

```text
authenticated principal
      ↓
resolve trusted TenantId
      ↓
TenantCatalog lookup/cache
      ↓
resolve database placement
      ↓
create tenant-scoped DbContext
      ↓
repository/query authorization guards
```

Không cho client gửi `TenantId=B456` rồi application đổi connection string theo input đó. Tenant identity phải được authorize trước. Catalog cache cần invalidation khi tenant move; một move nên có explicit state để tránh một phần traffic ghi DB cũ, phần khác DB mới.

### Tenant move

Nếu chuyển enterprise tenant từ shared sang dedicated DB, tôi cần workflow reversible:

1. provision target DB với đúng schema version;
2. initial copy tenant data;
3. capture/reconcile writes trong cutover window hoặc có controlled maintenance/read-only period;
4. validate row counts/checksums/business invariants;
5. atomically switch catalog placement;
6. monitor;
7. giữ source data theo rollback policy rồi cleanup sau.

Không nên tự phát minh dual-write dài hạn nếu requirement không cần; dual-write consistency rất dễ tạo failure modes mới.

### Migrations

Shared DB migration vẫn cần backward-compatible expand/contract khi rolling deploy. Với database fleet, migration runner phải track schema version per DB, bounded concurrency, retry transient failures, pause khi failure threshold vượt mức và application cần compatibility window giữa versions. Không chạy destructive change trước khi mọi app/database states liên quan đã chuyển an toàn.

### Backup/restore

Nếu enterprise contract yêu cầu restore riêng tenant tới timestamp cụ thể, dedicated DB rất có giá trị. Shared DB có thể làm logical tenant export/replay nhưng complexity và RTO/RPO khác hẳn. Requirement restore phải được benchmark/test, không ghi trong architecture doc rồi chưa từng restore thật.

### Noisy neighbor

Đo RPS, query CPU, rows scanned, storage, lock waits và job usage theo tenant. Có quotas/rate limits cho expensive exports/reporting. Nếu một tenant thường xuyên vượt shared-tier capacity hoặc có SLO riêng, đó là trigger move dedicated — không phải chỉ employee count.

### Analytics

Cross-tenant BI lớn không nên ép OLTP topology quyết định hết architecture. Có thể đưa dữ liệu sang analytics store/warehouse theo pipeline phù hợp. Như vậy database-per-tenant không bắt buộc phải join live 500 databases cho mọi dashboard.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn database-per-tenant chỉ vì nghe ‘an toàn nhất’, cũng không chọn shared DB rồi coi EF global query filter là security boundary. Tôi bắt đầu từ compliance, restore granularity, tenant size/RPS, noisy-neighbor và operational capacity của team.

Với 500 tenants nhưng phần lớn nhỏ, shared schema có cost và migration simplicity tốt. Tuy nhiên 5% enterprise có thể tạo capacity/SLA/restore requirements khác. Tôi có xu hướng thiết kế logical tenant boundary và tenant catalog từ đầu để physical placement có thể thay đổi: small tenants ở shared shards, enterprise tenant có thể dedicated khi có trigger rõ.

Tenant ID phải đến từ trusted authenticated context, không từ request body. Global query filter là defense-in-depth; repository, raw SQL, caches, background jobs, files và authorization đều phải tenant-scoped. Nếu dùng hybrid, catalog map tenant sang database và connection metadata. Move tenant phải là controlled workflow với copy, validation, cutover và rollback, không dual-write vô hạn.

Tôi cũng tính migration fleet, backup/restore drills và per-tenant observability. Database-per-tenant chỉ hiệu quả nếu provisioning/migrations/secrets/monitoring được automate. Trigger chuyển dedicated nên dựa vào compliance, SLO, restore requirement hoặc measured resource consumption, không phải cảm tính.”

## Câu hỏi đào sâu

1. Nếu một tenant ở shared DB yêu cầu restore dữ liệu về trạng thái 4 giờ trước nhưng 499 tenants còn lại không được rollback, bạn có các lựa chọn nào và trade-off ra sao?
2. Nếu tenant catalog cache trên một instance stale sau cutover và vẫn route write sang DB cũ, bạn thiết kế transition để tránh split-brain thế nào?
3. Tôi yêu cầu tất cả 500 tenants database-per-tenant vì security team thích isolation; bạn cần những automation/operational controls tối thiểu nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- “Global query filter nên không thể leak tenant data”.
- Database-per-tenant nhưng không có migration/provisioning/monitoring automation.
- Shared DB nhưng không bàn restore/noisy-neighbor/blast radius.
- Cho client tự chọn `TenantId`/connection.
- Đề xuất hybrid nhưng không giải thích routing và tenant move consistency.

## Thang điểm 0–10

- **0–2:** Chọn model theo khẩu hiệu, gần như không bàn security/operations.
- **3–4:** So sánh được options nhưng thiếu trusted tenant resolution hoặc migration/restore strategy.
- **5–6:** Có quyết định hợp lý, guardrails và operational trade-offs rõ.
- **7–8:** Thiết kế được hybrid/catalog, tenant move, migration fleet và per-tenant observability.
- **9–10:** Cân bằng security, cost, blast radius, restore/SLO và team maturity; biết giữ logical ownership ổn định trong khi physical placement có thể tiến hóa theo evidence.
