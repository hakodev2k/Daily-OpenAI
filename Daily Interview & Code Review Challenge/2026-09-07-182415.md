# Code Review Challenge 1 — API trả `202 Accepted` nhưng background work biến mất sau request và deploy

**Chủ đề:** C#/.NET, ASP.NET Core, DI lifetime, fire-and-forget, `Task.Run`, scoped services, `CancellationToken`, BackgroundService, graceful shutdown, reliability, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một enterprise document platform chạy ASP.NET Core .NET 8 trên Azure App Service Linux. API cho phép user yêu cầu regenerate metadata cho một document sau khi upload.

Yêu cầu nghiệp vụ:

- endpoint cần phản hồi nhanh, không giữ HTTP request trong 1–3 phút;
- metadata regeneration đọc document record từ SQL Server bằng EF Core;
- gọi một third-party document-analysis API;
- cập nhật metadata và trạng thái xử lý;
- production chạy 4 App Service instances;
- deploy có thể restart process bất kỳ lúc nào;
- một document không nên bị regenerate đồng thời nhiều lần;
- client cần biết trạng thái `Pending`, `Running`, `Succeeded`, `Failed`;
- lỗi phải có khả năng retry có kiểm soát;
- request cancellation không đồng nghĩa business job phải bị hủy sau khi API đã chấp nhận job.

Production hiện ghi nhận:

- API thường trả `202 Accepted`, nhưng một số document mãi ở trạng thái cũ;
- deploy/restart giữa lúc xử lý làm job biến mất;
- thỉnh thoảng log có `ObjectDisposedException` liên quan tới `AppDbContext`;
- có document bị xử lý hai lần khi user bấm retry nhanh;
- một số exception từ background task không xuất hiện trong Application Insights;
- team tăng App Service instance từ 2 lên 4 nhưng throughput không ổn định;
- support không có `JobId` để correlate request với background execution;
- developer đề xuất bọc thêm `try/catch` quanh `Task.Run` và coi như đủ.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IDocumentAnalysisClient _analysisClient;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        AppDbContext db,
        IDocumentAnalysisClient analysisClient,
        ILogger<DocumentsController> logger)
    {
        _db = db;
        _analysisClient = analysisClient;
        _logger = logger;
    }

    [HttpPost("{documentId:guid}/regenerate-metadata")]
    public async Task<IActionResult> RegenerateMetadata(
        Guid documentId,
        CancellationToken cancellationToken)
    {
        var document = await _db.Documents
            .SingleOrDefaultAsync(
                x => x.Id == documentId,
                cancellationToken);

        if (document is null)
        {
            return NotFound();
        }

        Task.Run(async () =>
        {
            try
            {
                document.Status = "Running";
                await _db.SaveChangesAsync();

                var result = await _analysisClient.AnalyzeAsync(
                    document.BlobUri,
                    CancellationToken.None);

                document.Title = result.Title;
                document.Keywords = string.Join(',', result.Keywords);
                document.Status = "Succeeded";
                document.ProcessedUtc = DateTime.UtcNow;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Metadata regenerated for document {DocumentId}",
                    documentId);
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Metadata regeneration failed for {DocumentId}",
                    documentId);
            }
        });

        return Accepted(new
        {
            documentId,
            status = "Accepted"
        });
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review implementation như một Senior .NET Developer/Technical Lead chịu trách nhiệm production reliability.

Bạn cần:

1. xác định correctness problems;
2. giải thích ASP.NET Core request scope và lifetime của `DbContext` trong đoạn code;
3. phân tích `Task.Run` fire-and-forget trong web process;
4. đánh giá behavior khi App Service restart/deploy;
5. phân tích duplicate execution khi user gọi endpoint nhiều lần;
6. đánh giá cancellation semantics;
7. phân tích ownership và trạng thái job;
8. đề xuất implementation/design phù hợp hơn;
9. giải thích khi nào in-process queue đủ và khi nào cần durable queue;
10. giải thích testing và production telemetry cần có.

## Câu hỏi gợi mở

1. `AppDbContext` và entity `document` được resolve/materialize trong request scope; chuyện gì xảy ra khi request kết thúc trước `Task.Run`?
2. `202 Accepted` có nghĩa background work đã được lưu durable ở đâu chưa?

## Kết quả code review tham khảo

### Critical — Capture `DbContext` và tracked entity từ request scope vào background task

**Vấn đề:**  
`_db` và `document` được tạo trong request scope rồi được closure của `Task.Run` sử dụng sau khi action đã return.

**Tại sao xảy ra:**  
`DbContext` thường được đăng ký scoped trong ASP.NET Core. Khi request kết thúc, scope có thể dispose `DbContext`. Entity `document` vẫn là một object trong memory nhưng tracking/session mà code kỳ vọng không còn là một lifetime an toàn để dùng.

**Ảnh hưởng production:**  
Background task có thể gặp `ObjectDisposedException`, behavior phụ thuộc timing, hoặc fail sau khi API đã trả `202`.

**Cách sửa:**  
Không capture scoped service hoặc tracked entity từ request vào fire-and-forget work. Durable worker nên nhận immutable job payload như `JobId`, `DocumentId`, tenant/user context cần thiết, rồi tạo DI scope mới cho mỗi execution và reload dữ liệu từ database.

---

### Critical — `Task.Run` không tạo durable background job

**Vấn đề:**  
API trả `202 Accepted` ngay sau khi schedule work vào process-local ThreadPool.

**Tại sao xảy ra:**  
`Task.Run` chỉ tạo một task trong process hiện tại. Nó không persist job, không retry sau crash, không chuyển ownership giữa instances và không cung cấp delivery guarantee.

**Ảnh hưởng production:**  
App Service restart, deployment, crash hoặc process recycle có thể làm job biến mất vĩnh viễn sau khi client đã được báo accepted.

**Cách sửa:**  
Nếu business requirement yêu cầu work phải sống qua restart, persist job trước khi trả `202`. Có thể dùng database-backed job table + BackgroundService, hoặc durable queue như Azure Service Bus/Azure Functions tùy requirement. Không tự động thêm messaging nếu reliability requirement thấp; nhưng với trạng thái async business job cần recovery, durable state gần như bắt buộc.

---

### Critical — Không có idempotency/concurrency control cho cùng một document

**Vấn đề:**  
Hai request gần nhau cùng tạo hai tasks độc lập cho cùng `documentId`.

**Tại sao xảy ra:**  
Không có unique active-job invariant, version check, lease hoặc compare-and-set state transition.

**Ảnh hưởng production:**  
Hai workers có thể gọi external API hai lần, overwrite metadata lẫn nhau và tạo trạng thái cuối không phản ánh execution nào thắng.

**Cách sửa:**  
Persist `MetadataJob` với unique constraint hoặc conditional state transition đảm bảo chỉ có một active job cho mỗi document. Ví dụ unique filtered constraint theo document + active status, hoặc atomic update `Pending -> Running` có concurrency token. Retry phải reuse hoặc supersede job theo rule rõ ràng.

---

### High — Exception handling chỉ log, không cập nhật durable failure state

**Vấn đề:**  
Catch exception rồi log nhưng không đảm bảo document/job chuyển sang `Failed`.

**Tại sao xảy ra:**  
Trạng thái business nằm trong cùng fragile request-scoped context.

**Ảnh hưởng production:**  
UI có thể thấy document mãi `Running` hoặc trạng thái cũ. Support không phân biệt task bị mất, dependency timeout hay application error.

**Cách sửa:**  
Worker phải update durable job status và error classification trong một scope độc lập. Nếu update failure state cũng fail, cần reconciliation dựa trên lease/heartbeat/timeout.

---

### High — `202 Accepted` response không trả `JobId` hoặc status resource

**Vấn đề:**  
Client chỉ nhận `documentId` và string `Accepted`.

**Tại sao xảy ra:**  
API không mô hình hóa asynchronous operation như một resource có identity.

**Ảnh hưởng production:**  
Client/support không poll được execution cụ thể, không biết retry đang tạo job mới hay xem lại job cũ, và telemetry khó correlate.

**Cách sửa:**  
Tạo `JobId`, persist job, trả `202` cùng location/status endpoint, ví dụ `/api/document-metadata-jobs/{jobId}`. Response nên thể hiện state machine rõ ràng.

---

### High — Không xác định authorization boundary của background job

**Vấn đề:**  
Action chỉ kiểm tra document tồn tại; snippet không cho thấy tenant/resource authorization, và background task cũng không persist authorization context.

**Tại sao xảy ra:**  
Authenticated request bị coi như đủ quyền trên arbitrary document ID.

**Ảnh hưởng production:**  
Trong hệ thống multi-tenant, user có thể trigger processing trên document không thuộc phạm vi của họ nếu query không filter/authorize theo resource.

**Cách sửa:**  
Authorize resource/tenant trước khi enqueue. Persist trusted identifiers cần thiết như `TenantId`, `RequestedByUserId` để audit. Worker không nên tin raw user-controlled claims được serialize tùy tiện; nó phải reload/validate business ownership cần thiết.

---

### High — Cancellation semantics bị bỏ qua thay vì được thiết kế

**Vấn đề:**  
`CancellationToken.None` được truyền vào external API và `SaveChangesAsync()` không nhận cancellation token.

**Tại sao xảy ra:**  
Code không phân biệt request cancellation với worker shutdown cancellation.

**Ảnh hưởng production:**  
Task có thể chạy vô hạn lâu hơn mong đợi trong shutdown, hoặc bị process kill giữa side effect. Ngược lại, dùng request token trực tiếp cũng sai nếu job phải tiếp tục sau khi request disconnect.

**Cách sửa:**  
Sau khi job đã được durable-accept, request token chỉ áp dụng cho enqueue transaction. Worker dùng host stopping token kết hợp timeout riêng cho dependency call. Business cancellation cần một explicit job-cancel mechanism nếu requirement có.

---

### High — Không có timeout/retry policy rõ ràng cho third-party API

**Vấn đề:**  
`AnalyzeAsync` có thể chậm hoặc fail nhưng code không cho thấy bounded timeout, retry classification hay idempotency semantics.

**Tại sao xảy ra:**  
External dependency được xem như local method call.

**Ảnh hưởng production:**  
Worker có thể giữ job ở `Running` quá lâu; retry mù có thể tạo duplicate provider work nếu API không idempotent.

**Cách sửa:**  
Thiết kế timeout, retry budget, backoff và idempotency key theo contract của provider. Permanent validation failure khác với transient network failure.

---

### Medium — Entity state được dùng như job state nhưng không có state machine/invariants

**Vấn đề:**  
`document.Status` vừa đại diện business document vừa đại diện processing lifecycle.

**Tại sao xảy ra:**  
Không tách document aggregate state khỏi asynchronous operation state.

**Ảnh hưởng production:**  
Khó biểu diễn retry, attempt count, queued/running/failed reason, superseded job hoặc timeout.

**Cách sửa:**  
Tạo job table/resource nếu lifecycle có ý nghĩa riêng. Document có thể giữ `MetadataStatus` tổng hợp, nhưng execution chi tiết thuộc `MetadataJob`.

---

### Medium — Logging thiếu execution identity và timing

**Vấn đề:**  
Log chỉ có `DocumentId`.

**Tại sao xảy ra:**  
Không có `JobId`, attempt, instance, duration, dependency timing hoặc transition logs.

**Ảnh hưởng production:**  
Khó RCA lost job, duplicate processing hoặc dependency failure.

**Cách sửa:**  
Dùng structured telemetry với `JobId`, `DocumentId`, tenant, attempt, status transition, worker instance, dependency duration, retry reason, processing duration và trace/correlation ID.

## Phiên bản đề xuất

Ví dụ dưới đây dùng database-backed job table để giữ kiến trúc đơn giản khi throughput chưa cần message broker. Nếu volume/reliability/decoupling tăng, cùng contract job có thể chuyển sang Azure Service Bus.

Controller:

```csharp
[HttpPost("{documentId:guid}/regenerate-metadata")]
public async Task<IActionResult> RegenerateMetadata(
    Guid documentId,
    CancellationToken cancellationToken)
{
    var document = await _db.Documents
        .AsNoTracking()
        .SingleOrDefaultAsync(
            x => x.Id == documentId &&
                 x.TenantId == _currentTenant.Id,
            cancellationToken);

    if (document is null)
    {
        return NotFound();
    }

    var existing = await _db.MetadataJobs
        .AsNoTracking()
        .Where(x =>
            x.DocumentId == documentId &&
            (x.Status == MetadataJobStatus.Pending ||
             x.Status == MetadataJobStatus.Running))
        .OrderByDescending(x => x.CreatedUtc)
        .FirstOrDefaultAsync(cancellationToken);

    if (existing is not null)
    {
        return AcceptedAtAction(
            nameof(GetMetadataJob),
            new { jobId = existing.Id },
            new { jobId = existing.Id, status = existing.Status });
    }

    var job = new MetadataJob
    {
        Id = Guid.NewGuid(),
        DocumentId = documentId,
        TenantId = _currentTenant.Id,
        RequestedByUserId = _currentUser.Id,
        Status = MetadataJobStatus.Pending,
        AttemptCount = 0,
        CreatedUtc = DateTime.UtcNow
    };

    _db.MetadataJobs.Add(job);
    await _db.SaveChangesAsync(cancellationToken);

    return AcceptedAtAction(
        nameof(GetMetadataJob),
        new { jobId = job.Id },
        new { jobId = job.Id, status = job.Status });
}
```

Worker outline:

```csharp
public sealed class MetadataWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<MetadataWorker> _logger;

    public MetadataWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<MetadataWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<IMetadataJobProcessor>();

            var processed = await processor.TryProcessNextAsync(
                stoppingToken);

            if (!processed)
            {
                await Task.Delay(TimeSpan.FromSeconds(2), stoppingToken);
            }
        }
    }
}
```

Processor cần claim job atomically trước khi chạy. Với SQL Server có thể dùng update có concurrency token/lease semantics để nhiều App Service instances không cùng lấy một job. Worker tạo scope riêng cho mỗi iteration/job, reload document, gọi dependency với bounded timeout, update `Succeeded`/`Failed`, và có retry policy dựa trên attempt count + failure classification.

Một state machine ví dụ:

```text
Pending
  -> Running
  -> Succeeded
  -> FailedTransient -> Pending (retry)
  -> FailedPermanent
  -> Cancelled
```

Nếu job phải survive database outage dài, cần queue durability độc lập, high throughput, hoặc fan-out nhiều consumers, Azure Service Bus là một lựa chọn hợp lý hơn. Nhưng không nên chọn messaging chỉ vì “background work thì phải dùng queue”; database-backed queue có thể đủ với workload nhỏ/trung bình và team vận hành đơn giản.

## Giải thích thiết kế sau khi sửa

### 1. Request chỉ chịu trách nhiệm accept và persist intent

HTTP lifecycle không còn quyết định lifecycle của business processing.

### 2. Worker tạo DI scope riêng

Mỗi execution có `DbContext` riêng, không capture scoped object từ controller.

### 3. Job có durable identity

`JobId` giúp polling, retry, telemetry và support investigation.

### 4. Multi-instance được coi là trạng thái bình thường

Claim/lease/idempotency phải hoạt động khi 4 instances cùng polling.

### 5. Cancellation có semantics riêng

Request cancellation, host shutdown và business cancel không bị trộn lẫn.

## Trade-offs

- Database-backed queue đơn giản hơn messaging nhưng polling tăng DB traffic và cần claim/index design tốt.
- Azure Service Bus tăng operational dependency nhưng phù hợp hơn khi throughput, decoupling hoặc durable delivery requirements tăng.
- Tách `MetadataJob` tăng schema và code nhưng đổi lại recovery/audit rõ ràng.
- Retry tăng khả năng phục hồi transient failure nhưng cần limit để không tạo retry storm.
- Unique active-job rule có thể làm UX “retry” trở thành reuse existing job; business cần xác định semantics mong muốn.

## Cách kiểm thử

1. **Scope/lifecycle integration test:** request trả `202`; worker xử lý sau khi request scope đã dispose mà không dùng controller `DbContext`.
2. **Concurrency test:** 4 worker instances cùng claim jobs; một `JobId` chỉ có một owner active tại một thời điểm.
3. **Restart recovery test:** kill process khi job đang `Running`; lease/timeout cho phép job được recover theo policy.
4. **Failure-path test:** third-party API timeout/5xx/permanent validation error; verify retry classification và final state.
5. **Authorization test:** user tenant A không thể enqueue job cho document tenant B.

Theo dõi:

- pending/running/failed job count;
- age của oldest pending job;
- processing duration p50/p95/p99;
- claim success/conflict rate;
- retry attempts theo reason;

# Code Review Challenge 2 — MongoDB query chạy nhanh lúc đầu nhưng chậm dần, pagination sai và update làm mất dữ liệu

**Chủ đề:** MongoDB, document modeling, indexes, query patterns, pagination, optimistic concurrency, denormalization, production performance, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một CRM-related service lưu customer activity feed trong MongoDB. Mỗi document activity có cấu trúc gần như:

```json
{
  "_id": "...",
  "tenantId": "tenant-a",
  "customerId": "customer-123",
  "type": "NoteAdded",
  "summary": "...",
  "createdUtc": "...",
  "tags": ["sales", "priority"],
  "customerSnapshot": {
    "displayName": "Acme Ltd",
    "segment": "Enterprise"
  }
}
```

Yêu cầu:

- UI hiển thị activity của một tenant/customer, mới nhất trước;
- filter tùy chọn theo `type` và `tags`;
- page size tối đa 100;
- support đôi khi search summary theo chuỗi;
- collection đã tăng lên khoảng 80 triệu documents;
- một vài tenant lớn chiếm phần đáng kể traffic;
- customer display name có thể đổi, nhưng historical activity không nhất thiết phải rewrite ngay;
- API phải chịu concurrent updates vào tags;
- production chạy nhiều instances.

Production hiện ghi nhận:

- page đầu nhanh nhưng page sâu ngày càng chậm;
- query theo `summary` làm CPU của MongoDB tăng mạnh;
- cùng một activity đôi khi xuất hiện ở hai page hoặc bị bỏ qua khi feed có insert mới;
- hai request cùng thêm tag có thể làm mất tag của request còn lại;
- support cho rằng mọi `customerSnapshot.displayName` phải luôn đồng bộ tức thời với bảng Customer bên SQL Server;
- team đề xuất tạo index riêng cho mọi field và chạy background job rewrite toàn bộ activity mỗi khi customer đổi tên.

Repository hiện tại:

## Đoạn code cần review

```csharp
public sealed class ActivityRepository
{
    private readonly IMongoCollection<ActivityDocument> _collection;

    public ActivityRepository(IMongoDatabase database)
    {
        _collection = database
            .GetCollection<ActivityDocument>("activities");
    }

    public async Task<IReadOnlyList<ActivityDocument>> SearchAsync(
        string tenantId,
        string customerId,
        string? type,
        string? tag,
        string? text,
        int page,
        int pageSize,
        CancellationToken cancellationToken)
    {
        var filter = Builders<ActivityDocument>.Filter.Eq(
            x => x.TenantId,
            tenantId);

        filter &= Builders<ActivityDocument>.Filter.Eq(
            x => x.CustomerId,
            customerId);

        if (!string.IsNullOrWhiteSpace(type))
        {
            filter &= Builders<ActivityDocument>.Filter.Eq(
                x => x.Type,
                type);
        }

        if (!string.IsNullOrWhiteSpace(tag))
        {
            filter &= Builders<ActivityDocument>.Filter.AnyEq(
                x => x.Tags,
                tag);
        }

        if (!string.IsNullOrWhiteSpace(text))
        {
            filter &= Builders<ActivityDocument>.Filter.Regex(
                x => x.Summary,
                new BsonRegularExpression(text, "i"));
        }

        return await _collection.Find(filter)
            .SortByDescending(x => x.CreatedUtc)
            .Skip((page - 1) * pageSize)
            .Limit(pageSize)
            .ToListAsync(cancellationToken);
    }

    public async Task AddTagAsync(
        string activityId,
        string tag,
        CancellationToken cancellationToken)
    {
        var activity = await _collection.Find(
                x => x.Id == activityId)
            .SingleAsync(cancellationToken);

        activity.Tags.Add(tag);

        await _collection.ReplaceOneAsync(
            x => x.Id == activityId,
            activity,
            cancellationToken: cancellationToken);
    }
}
```

```javascript
db.activities.createIndex({ customerId: 1 })
db.activities.createIndex({ createdUtc: -1 })
db.activities.createIndex({ type: 1 })
```

## Nhiệm vụ của ứng viên

Hãy review implementation như một Senior backend engineer chịu trách nhiệm MongoDB performance và data correctness.

Bạn cần:

1. xác định query/index problems;
2. phân tích vì sao nhiều single-field indexes không đồng nghĩa query chính sẽ tối ưu;
3. đánh giá `Skip` pagination ở deep page;
4. phân tích pagination consistency khi có inserts mới;
5. đánh giá regex search hiện tại;
6. phân tích lost update trong `AddTagAsync`;
7. đánh giá tenant isolation trong update path;
8. phân tích denormalized `customerSnapshot` và consistency requirement;
9. đề xuất query/index/update design tốt hơn;
10. giải thích testing và production telemetry cần có.

## Câu hỏi gợi mở

1. Query thường xuyên nhất filter theo `tenantId + customerId` rồi sort `createdUtc DESC`; index hiện tại có phản ánh query shape đó không?
2. Deep `Skip` yêu cầu database làm gì với các documents đứng trước page cần lấy?
3. Nếu activity mới được insert giữa request page 1 và page 2, offset pagination có giữ một snapshot ổn định không?
4. Hai request cùng đọc document rồi `ReplaceOneAsync` toàn bộ document sẽ tương tác thế nào?
5. Search substring case-insensitive bằng regex có scale giống exact lookup không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **index không theo query shape + offset pagination + read-modify-replace không atomic ở field level**.

### Gợi ý 2

Hãy xem riêng ba boundary:

- read path: filter + sort + pagination;
- write path: atomicity/concurrency;
- denormalized snapshot: historical semantics vs synchronization semantics.

## Kết quả code review tham khảo

### High — Index strategy không bám theo query shape chính

**Vấn đề:**  
Collection có nhiều single-field indexes nhưng query chính kết hợp `tenantId`, `customerId` và sort theo `createdUtc DESC`.

**Tại sao xảy ra:**  
Index usefulness phụ thuộc filter/sort pattern, selectivity và execution plan. Nhiều single-field indexes không tự động tương đương một compound index tối ưu cho query phổ biến.

**Ảnh hưởng production:**  
Database có thể scan/sort nhiều documents hơn cần thiết, latency và CPU tăng khi collection lớn.

**Cách sửa:**  
Bắt đầu từ workload thật và `explain`. Một candidate index cho feed chính có thể là:

```javascript
db.activities.createIndex({
  tenantId: 1,
  customerId: 1,
  createdUtc: -1,
  _id: -1
})
```

Nếu `type` là filter phổ biến và selective, có thể cần index variant chứa `type`; nhưng không nên tạo index cho mọi tổ hợp trước khi đo vì write/storage cost sẽ tăng.

---

### High — Deep `Skip` pagination scale kém

**Vấn đề:**  
`Skip((page - 1) * pageSize)` dùng offset pagination.

**Tại sao xảy ra:**  
Để đến page sâu, server vẫn phải đi qua nhiều matching entries trước khi trả page cần thiết.

**Ảnh hưởng production:**  
Latency và work tăng theo offset; page 50.000 có thể rất đắt dù chỉ trả 50 rows.

**Cách sửa:**  
Dùng keyset/cursor pagination dựa trên stable sort key, ví dụ `(createdUtc, _id)`. Client gửi cursor của item cuối page trước.

---

### High — Sort chỉ theo `createdUtc` chưa tạo total ordering

**Vấn đề:**  
Nhiều activities có thể có cùng `CreatedUtc`.

**Tại sao xảy ra:**  
Sort key không unique.

**Ảnh hưởng production:**  
Pagination có thể reorder giữa requests, dẫn tới duplicate/missing item ngay cả khi dùng cursor không đầy đủ.

**Cách sửa:**  
Sort theo `CreatedUtc DESC, Id DESC` và cursor phải chứa cả hai giá trị.

---

### High — Offset pagination không ổn định khi feed có insert mới

**Vấn đề:**  
Page 1 và page 2 được tính bằng vị trí tương đối tại hai thời điểm khác nhau.

**Tại sao xảy ra:**  
New insert đẩy offsets của documents cũ.

**Ảnh hưởng production:**  
User có thể thấy duplicate hoặc bỏ sót items khi scroll.

**Cách sửa:**  
Keyset pagination theo cursor ổn định. Nếu UX yêu cầu snapshot tuyệt đối tại thời điểm bắt đầu, cần thêm upper-bound cursor/snapshot semantics rõ ràng.

---

### High — Regex substring search có thể trở thành expensive query

**Vấn đề:**  
User input đi vào case-insensitive regex search trên `Summary`.

**Tại sao xảy ra:**  
Arbitrary substring regex không có cùng access pattern với exact/index-prefix query; tùy pattern có thể cần scan lượng dữ liệu lớn.

**Ảnh hưởng production:**  
CPU tăng, latency cao và noisy-neighbor effect ở tenant lớn.

**Cách sửa:**  
Xác định requirement search thật. Nếu chỉ prefix có thể thiết kế index/prefix strategy phù hợp. Nếu cần full-text/relevance, cân nhắc MongoDB text/search capability hoặc Elasticsearch đã có trong stack, nhưng chỉ sau khi đánh giá operational complexity. Luôn giới hạn query, validate input và đo execution plan.

---

### Critical — Read-modify-replace có lost update dưới concurrency

**Vấn đề:**  
`AddTagAsync` đọc full document, mutate local list rồi replace toàn bộ document.

**Tại sao xảy ra:**  
Hai requests A/B có thể cùng đọc version ban đầu. A thêm `sales`, B thêm `priority`; replace cuối cùng overwrite toàn bộ document state từ snapshot cũ.

**Ảnh hưởng production:**  
Một update hợp lệ có thể biến mất mà không có exception.

**Cách sửa:**  
Dùng atomic field update như `$addToSet` cho tag semantics:

```csharp
var filter = Builders<ActivityDocument>.Filter.And(
    Builders<ActivityDocument>.Filter.Eq(x => x.Id, activityId),
    Builders<ActivityDocument>.Filter.Eq(x => x.TenantId, tenantId));

var update = Builders<ActivityDocument>.Update
    .AddToSet(x => x.Tags, tag);

var result = await _collection.UpdateOneAsync(
    filter,
    update,
    cancellationToken: cancellationToken);
```

Nếu update bao gồm nhiều fields với invariant phức tạp, cân nhắc version field + optimistic concurrency hoặc transaction khi thật sự cần.

---

### Critical — Update path không filter theo tenant

**Vấn đề:**  
`AddTagAsync` lookup/replace chỉ theo `activityId`.

**Tại sao xảy ra:**  
Repository method không encode multi-tenant ownership boundary.

**Ảnh hưởng production:**  
Nếu caller có thể cung cấp ID của tenant khác, application có thể sửa activity ngoài tenant hiện tại.

**Cách sửa:**  
Tenant key phải nằm trong filter của read/write path và authorization phải được áp dụng ở application boundary. Không chỉ dựa vào frontend hoặc tính khó đoán của ID.

---

### High — `ReplaceOneAsync` có blast radius lớn hơn cần thiết

**Vấn đề:**  
Thêm một tag nhưng replace toàn document.

**Tại sao xảy ra:**  
Repository dùng entity-style aggregate replacement cho operation field-level đơn giản.

**Ảnh hưởng production:**  
Ngoài lost update, code có thể ghi đè field mới được service khác update hoặc field schema mới mà object cũ không giữ đúng.

**Cách sửa:**  
Dùng atomic update operator cho operation đơn giản. Chỉ replace whole document khi aggregate semantics thực sự yêu cầu và có concurrency control.

---

### Medium — Không validate/clamp pagination input

**Vấn đề:**  
Snippet không giới hạn `page`, `pageSize` dù requirement nói tối đa 100.

**Tại sao xảy ra:**  
Repository tin input upstream.

**Ảnh hưởng production:**  
Caller có thể yêu cầu page size rất lớn hoặc page invalid gây load không cần thiết.

**Cách sửa:**  
Validate ở API boundary và có defensive limit ở data access layer nếu cần.

---

### Medium — Snapshot denormalization bị hiểu sai thành dữ liệu phải strong-consistent với SQL

**Vấn đề:**  
Team muốn rewrite toàn bộ historical activities mỗi khi customer đổi display name.

**Tại sao xảy ra:**  
Không xác định semantics của `customerSnapshot`.

**Ảnh hưởng production:**  
Background rewrite hàng triệu documents tạo write amplification, index churn và operational risk mà có thể không đem lại giá trị business.

**Cách sửa:**  
Quyết định rõ snapshot là “giá trị tại thời điểm event” hay “current projection”. Nếu là historical snapshot, stale so với current customer là đúng semantics. Nếu UI cần current display name, có thể query/join ở application layer, maintain một current-customer read model, hoặc update selective fields theo eventual consistency. Không mặc định rewrite lịch sử.

---

### Medium — Observability không cho biết query plan/scan cost

**Vấn đề:**  
Không có telemetry về query shape, examined docs/keys, duration hoặc tenant distribution.

**Tại sao xảy ra:**  
Data access được đo như API latency tổng thay vì database workload.

**Ảnh hưởng production:**  
Khó phân biệt index miss, regex scan, hot tenant hay network latency.

**Cách sửa:**  
Theo dõi slow queries, `explain` trong investigation, query duration, docs/keys examined, result count, tenant cardinality bucket, error rate và connection-pool behavior.

## Phiên bản đề xuất

Cursor model:

```csharp

    DateTime CreatedUtc,
    string Id);
```

Query feed chính:

```csharp
public async Task<ActivityPage> GetPageAsync(
    string tenantId,
    string customerId,
    string? type,
    string? tag,
    ActivityCursor? cursor,
    int pageSize,
    CancellationToken cancellationToken)
{
    pageSize = Math.Clamp(pageSize, 1, 100);

    var f = Builders<ActivityDocument>.Filter;

    var filter = f.Eq(x => x.TenantId, tenantId) &
                 f.Eq(x => x.CustomerId, customerId);

    if (!string.IsNullOrWhiteSpace(type))
    {
        filter &= f.Eq(x => x.Type, type);
    }

    if (!string.IsNullOrWhiteSpace(tag))
    {
        filter &= f.AnyEq(x => x.Tags, tag);
    }

    if (cursor is not null)
    {
        filter &= f.Or(
            f.Lt(x => x.CreatedUtc, cursor.CreatedUtc),
            f.And(
                f.Eq(x => x.CreatedUtc, cursor.CreatedUtc),
                f.Lt(x => x.Id, cursor.Id)));
    }

    var items = await _collection.Find(filter)
        .Sort(Builders<ActivityDocument>.Sort
            .Descending(x => x.CreatedUtc)
            .Descending(x => x.Id))
        .Limit(pageSize + 1)
        .ToListAsync(cancellationToken);

    var hasMore = items.Count > pageSize;
    if (hasMore)
    {
        items.RemoveAt(items.Count - 1);
    }

    var next = hasMore && items.Count > 0
        ? new ActivityCursor(
            items[^1].CreatedUtc,
            items[^1].Id)
        : null;

    return new ActivityPage(items, next);
}
```

Atomic tag update:

```csharp
public async Task<bool> AddTagAsync(
    string tenantId,
    string activityId,
    string tag,
    CancellationToken cancellationToken)
{
    var filter = Builders<ActivityDocument>.Filter.And(
        Builders<ActivityDocument>.Filter.Eq(
            x => x.TenantId,
            tenantId),
        Builders<ActivityDocument>.Filter.Eq(
            x => x.Id,
            activityId));

        .AddToSet(x => x.Tags, tag);

    var result = await _collection.UpdateOneAsync(
        filter,
        update,
        cancellationToken: cancellationToken);

    return result.MatchedCount == 1;
}
```

## Giải thích thiết kế sau khi sửa

### 1. Index theo workload

Compound index phản ánh prefix filters và sort phổ biến thay vì “mỗi field một index”.

### 2. Pagination dùng stable cursor

`CreatedUtc + Id` tạo total ordering và tránh deep offset cost.

### 3. Update dùng atomic operator

`$addToSet` phù hợp operation “thêm tag nếu chưa có” và giảm lost-update risk.

### 4. Tenant nằm trong read/write boundary

Data isolation không chỉ dựa vào caller convention.

### 5. Denormalization có semantics rõ ràng

Historical snapshot có thể intentionally stale. Consistency target phải xuất phát từ business meaning.

## Trade-offs

- Cursor pagination không hỗ trợ nhảy trực tiếp tới “page 20.000” như offset; UX/API contract cần thay đổi.
- Compound indexes tăng write/storage cost và cần chọn theo workload thực tế.
- Search chuyên dụng như Elasticsearch tăng capability nhưng thêm synchronization và operational complexity.
- Atomic field updates đơn giản và an toàn hơn, nhưng aggregate invariant phức tạp có thể vẫn cần optimistic concurrency hoặc transaction.
- Giữ historical snapshot giảm rewrite cost nhưng UI cần source khác nếu muốn current customer metadata.

## Cách kiểm thử

1. **Pagination consistency test:** insert activities mới giữa page 1/page 2; cursor pagination không duplicate/skip items trong traversal semantics đã định.
2. **Concurrency test:** hai requests cùng thêm hai tags khác nhau; cả hai tags tồn tại sau completion.
3. **Tenant isolation test:** tenant A không thể update activity tenant B bằng ID hợp lệ.
4. **Load/query-plan test:** benchmark feed query ở tenant nhỏ và tenant lớn; kiểm tra index usage, keys/docs examined và p95/p99.
5. **Search failure/performance test:** regex/text search với input dài/phổ biến; verify guardrails, timeout và fallback strategy.

## Quan sát trong production

Theo dõi:

- MongoDB query duration p50/p95/p99;
- slow query count;
- keys/docs examined so với documents returned;
- query rate theo operation và tenant-size bucket;
- cursor/page request distribution;
- write conflict/update matched count anomalies;
- regex/search endpoint CPU impact;
- connection-pool usage;
- index size và write latency;
- hot tenant contribution;
- API timeout/error rate;
- correlation ID giữa request và database operation.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào offset pagination vẫn chấp nhận được hơn cursor pagination?
2. Nếu requirement bắt buộc search arbitrary substring trên `summary`, bạn sẽ đánh giá MongoDB native capabilities và Elasticsearch như thế nào?
3. Khi nào denormalized snapshot nên được immutable, eventually updated hoặc loại bỏ để đọc từ source khác?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Task.Run` trong ASP.NET Core không biến request work thành durable background job.
- Scoped services như `DbContext` không nên bị capture vượt quá request scope.
- `202 Accepted` nên đại diện cho một asynchronous operation đã có durable identity/state nếu business yêu cầu recovery.
- Multi-instance background processing cần claim/idempotency/lease semantics thay vì dựa vào process-local state.
- MongoDB index design phải bám theo query shape và sort pattern, không phải tạo một index cho mỗi field.
- Deep offset pagination vừa tốn chi phí vừa dễ tạo duplicate/missing items khi dataset thay đổi.
- Atomic update operators giúp tránh lost update trong các field-level operations.
- Denormalization chỉ đúng khi consistency semantics được xác định rõ.

## Mẫu tư duy cần nhớ

1. **Persist intent before acknowledging durable asynchronous work.**
2. **Never let scoped lifetime accidentally become business-work lifetime.**
3. **Design multi-instance execution as the default, not an edge case.**
4. **Index for query shape and verify with evidence.**
5. **Choose consistency semantics before choosing synchronization machinery.**
