# Câu 1 — `Task.WhenAll` làm endpoint nhanh hơn ở local, nhưng vì sao production lại lỗi `A second operation was started on this context` và kéo SQL connection pool lên cao?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** C#/.NET 8, `Task.WhenAll`, async concurrency, EF Core, `DbContext` lifetime/thread safety, SQL Server connection pooling, bounded parallelism, cancellation, performance measurement

## Bối cảnh

Một ASP.NET Core endpoint dựng trang dashboard tổng hợp từ nhiều nguồn dữ liệu trong cùng SQL Server database.

Code ban đầu chạy tuần tự:

```csharp
public async Task<DashboardDto> GetDashboardAsync(
    int employeeId,
    CancellationToken ct)
{
    var profile = await _db.Employees
        .AsNoTracking()
        .SingleAsync(x => x.Id == employeeId, ct);

    var approvals = await _db.Approvals
        .AsNoTracking()
        .Where(x => x.EmployeeId == employeeId && x.Status == "Pending")
        .CountAsync(ct);

    var recentDocuments = await _db.Documents
        .AsNoTracking()
        .Where(x => x.EmployeeId == employeeId)
        .OrderByDescending(x => x.CreatedAt)
        .Take(10)
        .ToListAsync(ct);

    return new DashboardDto(profile, approvals, recentDocuments);
}
```

Một developer muốn giảm latency nên đổi sang:

```csharp
public async Task<DashboardDto> GetDashboardAsync(
    int employeeId,
    CancellationToken ct)
{
    var profileTask = _db.Employees
        .AsNoTracking()
        .SingleAsync(x => x.Id == employeeId, ct);

    var approvalsTask = _db.Approvals
        .AsNoTracking()
        .Where(x => x.EmployeeId == employeeId && x.Status == "Pending")
        .CountAsync(ct);

    var documentsTask = _db.Documents
        .AsNoTracking()
        .Where(x => x.EmployeeId == employeeId)
        .OrderByDescending(x => x.CreatedAt)
        .Take(10)
        .ToListAsync(ct);

    await Task.WhenAll(profileTask, approvalsTask, documentsTask);

    return new DashboardDto(
        await profileTask,
        await approvalsTask,
        await documentsTask);
}
```

Ở local với SQLite/in-memory test setup, benchmark có vẻ nhanh hơn. Nhưng staging dùng SQL Server và bắt đầu xuất hiện:

```text
InvalidOperationException:
A second operation was started on this context instance before a previous operation completed.
```

Developer sửa lần hai bằng cách inject `IDbContextFactory<AppDbContext>` rồi tạo ba context riêng:

```csharp
await using var db1 = await _factory.CreateDbContextAsync(ct);
await using var db2 = await _factory.CreateDbContextAsync(ct);
await using var db3 = await _factory.CreateDbContextAsync(ct);

var profileTask = LoadProfileAsync(db1, employeeId, ct);
var approvalsTask = LoadApprovalsAsync(db2, employeeId, ct);
var documentsTask = LoadDocumentsAsync(db3, employeeId, ct);

await Task.WhenAll(profileTask, approvalsTask, documentsTask);
```

Exception biến mất. Tuy nhiên dưới load test 400 concurrent HTTP requests:

- SQL Server CPU tăng từ khoảng 45% lên 85–95%;
- active database connections tăng mạnh;
- p50 giảm từ 220 ms xuống 160 ms;
- p99 lại tăng từ khoảng 700 ms lên 2.8 giây;
- một số requests timeout khi lấy connection;
- application CPU vẫn chưa bão hòa;
- team kết luận “parallel queries vẫn đúng vì p50 tốt hơn, chỉ cần tăng `Max Pool Size`”.

## Câu hỏi chính

Hãy giải thích vì sao cùng một `DbContext` không thể được dùng cho nhiều EF Core operations đồng thời, `Task.WhenAll` thực sự tạo loại concurrency nào trong trường hợp này, vì sao tạo nhiều contexts có thể loại bỏ exception nhưng vẫn làm hệ thống chậm hơn dưới tải, và bạn sẽ quyết định query nào nên chạy tuần tự, query nào có thể song song, hay nên hợp nhất thành một read model/query khác dựa trên production evidence như thế nào.

## Câu hỏi làm rõ nên cân nhắc

1. Ba queries có thật sự độc lập về transaction/consistency hay dashboard yêu cầu một snapshot logic thống nhất?
2. Mỗi HTTP request có thể đồng thời tạo bao nhiêu SQL commands sau khi tính cả middleware, authorization và các service khác?
3. SQL Server connection pool hiện có `Max Pool Size`, acquisition wait và connection lifetime như thế nào?
4. Query plans/indexes của ba queries có ổn không, hay parallelism đang che latency của query kém?
5. Dashboard có cần dữ liệu fresh tuyệt đối hay có thể dùng precomputed/read-model/cache cho một phần dữ liệu?
6. Production peak concurrency là bao nhiêu và DB còn bao nhiêu headroom cho các workloads khác?

## Gợi ý tư duy

### Gợi ý 1

`DbContext` đại diện cho một unit-of-work có change tracker, state và database operation lifecycle. EF Core không hỗ trợ nhiều operations active đồng thời trên cùng context.

### Gợi ý 2

`Task.WhenAll` không “tạo thread” theo nghĩa đơn giản, nhưng nó cho phép nhiều asynchronous database operations cùng in-flight. Nếu mỗi request tăng từ 1 connection active tại một thời điểm lên 3, concurrency toàn hệ thống có thể tăng rất nhanh.

### Gợi ý 3

Tối ưu latency của **một request** có thể làm throughput và p99 của **toàn hệ thống** xấu đi. Hãy tính concurrency amplification và kiểm tra database saturation thay vì chỉ nhìn benchmark single-user.

## Cấu trúc trả lời đề xuất

1. Giải thích lifecycle/thread-safety của `DbContext`.
2. Mô tả timeline tuần tự và timeline `Task.WhenAll`.
3. Phân tích vì sao nhiều contexts sửa correctness ở application layer nhưng tăng database concurrency.
4. Tính amplification dưới 400 concurrent requests.
5. Phân biệt connection-pool exhaustion, SQL saturation và query-plan problem.
6. Đề xuất các phương án: tuần tự, bounded parallelism, query consolidation/read model, caching khi phù hợp.
7. Nêu consistency semantics và cancellation behavior.
8. Thiết kế load test representative và telemetry trước/sau.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết `DbContext` không thread-safe và không được chạy nhiều EF operations song song trên cùng instance.
- Không cho rằng `Task.WhenAll` tự động tốt hơn chỉ vì các operations là I/O-bound.
- Nhận ra ba contexts có thể dùng ba pooled SQL connections đồng thời cho mỗi request.
- Tính được concurrency amplification: 400 requests × tối đa 3 DB operations có thể tạo lượng in-flight work lớn hơn rất nhiều so với phiên bản tuần tự.
- Nhận ra tăng `Max Pool Size` không sửa root cause nếu SQL Server đã saturated.
- So sánh p95/p99/throughput/DB CPU/connection-wait chứ không chỉ p50.
- Propagate `CancellationToken` và không để abandoned work tiếp tục gây tải sau khi request hết deadline.

### Điểm cộng

- Phân biệt `DbContext` pooling với ADO.NET connection pooling.
- Nhận ra mỗi EF query không nhất thiết giữ connection suốt cả request; connection thường được open/use/return theo operation nếu không có explicit transaction/connection handling.
- Cân nhắc một query/projection hoặc stored procedure/read model trả dashboard data nếu access pattern ổn định và điều đó giảm round trips.
- Không ép join mọi thứ thành một Cartesian query khổng lồ chỉ để “một round trip”.
- Cân nhắc consistency: ba parallel queries có thể quan sát các database states hơi khác nhau nếu business cần snapshot semantics.

### Senior+

- Đặt optimization trong capacity model: DB service time, peak request concurrency, connection pool wait, query CPU/logical reads và SLO.
- Biết bounded concurrency chỉ có ý nghĩa khi áp đúng boundary; semaphore per request không giải quyết global amplification nếu mỗi request vẫn được ba slots riêng.
- Cân nhắc bulkhead/admission control ở application hoặc endpoint khi dashboard là expensive workload.
- Thiết kế experiment so sánh sequential vs parallel vs consolidated query ở production-like concurrency, không dùng benchmark một request.
- Có rollback threshold rõ khi p99, DB CPU hoặc connection acquisition vượt budget.

## Hướng giải quyết tham khảo

Lỗi đầu tiên là vấn đề correctness. Một `DbContext` không phải một stateless query gateway. Nó chứa state của unit-of-work và EF Core không hỗ trợ nhiều operations chạy đồng thời trên cùng context. Khi ba queries được khởi động trước khi query trước hoàn tất, EF Core có thể phát hiện overlapping operation và ném `InvalidOperationException`.

Điểm cần nói rõ là `Task.WhenAll` không nhất thiết tạo ba OS threads. Các SQL calls là asynchronous I/O; ba commands có thể cùng ở trạng thái in-flight và ba continuations hoàn tất khi I/O trả về. Nhưng từ góc nhìn SQL Server, đó vẫn là nhiều commands/connections concurrent hơn.

Tạo ba contexts riêng có thể hợp lệ về lifecycle nếu từng context chỉ được một flow sử dụng. Nhưng nó thay đổi load shape. Phiên bản tuần tự thường chỉ cần một query active tại một thời điểm cho request đó. Phiên bản song song có thể có ba queries active cùng lúc. Với 400 requests đồng thời, upper bound thô có thể tiến gần 1,200 concurrent commands/connections thay vì khoảng 400 active operations — chưa tính endpoints khác.

Điều này giải thích vì sao single-request p50 giảm nhưng p99 toàn hệ thống tăng: mỗi request giành nhiều database capacity cùng lúc, SQL CPU tăng, connection pool bắt đầu có waiters, scheduler/locks/I/O cạnh tranh hơn. Queueing delay tăng mạnh ở tail.

Tăng `Max Pool Size` có thể làm symptom “wait for a pooled connection” giảm tạm thời nhưng cũng có thể cho phép application dồn nhiều work hơn vào SQL Server đang 95% CPU. Connection pool là một admission boundary vô tình; mở boundary mà không tăng downstream capacity có thể làm incident nặng hơn.

Tôi sẽ đo:

- endpoint RPS và concurrency;
- EF/SQL dependency duration p50/p95/p99;
- ADO.NET connection pool counters/connection acquisition wait nếu observability stack cung cấp;
- SQL CPU, waits, logical reads, execution count và query plans;
- active requests/queued requests;
- timeout/cancellation counts;
- DB calls per HTTP request.

Sau đó chạy load test representative với ba variants:

1. tuần tự;
2. ba contexts parallel;
3. consolidated/read-model approach.

Nếu ba queries đều rất nhỏ và DB có headroom lớn, limited parallelism có thể hợp lý cho một endpoint latency-sensitive. Nhưng decision phải dựa trên total capacity. Nếu DB là shared bottleneck, chạy tuần tự thường cho throughput/tail latency tốt hơn dù một request isolated chậm hơn vài chục milliseconds.

Tôi cũng kiểm tra liệu ba queries có thể được thiết kế thành một read model rõ ràng hơn. Ví dụ profile là một row, pending count là aggregate, recent documents là top-N. Không nhất thiết một LINQ query duy nhất sẽ đẹp; có thể dùng một optimized stored procedure với multiple result sets hoặc một denormalized dashboard read model nếu endpoint rất hot và business chấp nhận freshness phù hợp. Nhưng đây chỉ đáng làm khi measurement cho thấy round trips/query cost là vấn đề.

Nếu product cần snapshot consistency giữa profile/count/documents, ba độc lập parallel reads dưới mặc định isolation không tự bảo đảm “cùng một thời điểm” về business semantics. Có thể cần transaction/isolation phù hợp hoặc read model versioned. Ngược lại, nếu dashboard chỉ best-effort/current-ish thì không nên thêm transaction chỉ vì kiến trúc đẹp.

Cuối cùng, cancellation phải đi xuyên xuống EF commands. Khi HTTP deadline/caller disconnect xảy ra, work không còn giá trị nên nên được cancel nếu provider hỗ trợ. Nhưng cancellation không thay thế capacity control.

## Mẫu trả lời trong phỏng vấn

“Có hai vấn đề khác nhau. Thứ nhất, cùng một `DbContext` không được chạy nhiều EF Core operations đồng thời. `Task.WhenAll` ở version đầu làm ba queries overlap trên cùng unit-of-work nên exception là expected failure mode.

Tạo ba contexts loại bỏ conflict đó, nhưng không có nghĩa optimization tốt cho hệ thống. Mỗi request giờ có thể tạo ba SQL commands và ba pooled connections cùng in-flight. Ở 400 concurrent requests, chúng ta có thể amplify database concurrency lên gần ba lần. Vì vậy p50 của một request giảm nhưng SQL CPU, connection wait và p99 tăng là hoàn toàn hợp lý.

Tôi sẽ không tăng `Max Pool Size` trước. Nếu SQL đã 95% CPU, mở pool có thể chỉ cho nhiều requests cùng đập vào bottleneck. Tôi muốn đo DB calls/request, active connections, acquisition wait, query duration, waits/logical reads và load test sequential versus parallel ở concurrency production-like.

Nếu DB có headroom và ba operations thật sự độc lập, parallel reads bằng contexts riêng có thể được giữ. Nếu DB là bottleneck, tôi ưu tiên tuần tự hoặc giảm round trips bằng một read model/query được thiết kế riêng. Tôi cũng hỏi dashboard cần snapshot consistency đến đâu, vì ba reads riêng có thể thấy dữ liệu ở các thời điểm khác nhau.

Mục tiêu không phải tối thiểu latency của một request trong isolation; mục tiêu là đạt SLO p99 và throughput mà không đẩy shared SQL Server vào saturation.”

## Câu hỏi đào sâu

1. Nếu ba queries mỗi query chỉ mất 20 ms nhưng endpoint gọi thêm hai downstream APIs, bạn có còn ưu tiên tuần tự SQL không? Bạn cần số liệu nào để quyết định?
2. Nếu tôi tăng `Max Pool Size` từ 100 lên 500 và timeout biến mất trong load test nhỏ, bạn cần bằng chứng gì trước khi cho production?
3. Nếu business yêu cầu cả ba phần dashboard phản ánh cùng một logical snapshot, bạn sẽ thay đổi transaction/query design như thế nào?

## Lỗi trả lời thường gặp

- Nói “EF Core async nên chạy song song trên cùng `DbContext` được”.
- Nghĩ `Task.WhenAll` luôn tối ưu I/O-bound workload.
- Chỉ fix bằng nhiều contexts nhưng không tính database concurrency amplification.
- Tăng connection-pool size như solution mặc định.
- Chỉ nhìn p50/single-user benchmark.
- Không bàn consistency hoặc cancellation semantics.

## Thang điểm 0–10

- **0–2:** Không hiểu `DbContext` concurrency restriction hoặc cho rằng `Task.WhenAll` luôn tốt hơn.
- **3–4:** Biết cần contexts riêng nhưng bỏ qua SQL capacity và connection pool.
- **5–6:** Phân tích đúng concurrency amplification, có load test và production telemetry cơ bản.
- **7–8:** Cân bằng per-request latency với system throughput/p99, consistency và downstream capacity.
- **9–10:** Kết nối runtime/EF lifecycle → pool → DB queueing → capacity model → alternative read design → rollout/rollback evidence một cách chặt chẽ.

# Câu 2 — SQL queries chỉ 30 ms nhưng API vẫn timeout: connection pool đã cạn trước khi command kịp chạy

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** SQL Server, ADO.NET connection pooling, EF Core, transactions, streaming readers, ASP.NET Core, timeout taxonomy, production diagnostics, incident response, capacity management

## Bối cảnh

Một ASP.NET Core Orders API dùng EF Core và SQL Server. Trong hai tuần gần đây, production thỉnh thoảng có burst lỗi 5–10 phút.

Symptom:

- Application Insights cho các SQL dependencies đã thực sự chạy thường chỉ 20–50 ms;
- SQL Server CPU khoảng 40%, không có spike rõ;
- database team nói query plans ổn;
- API p99 tăng từ 400 ms lên hơn 15 giây;
- logs có nhiều timeout trước khi thấy SQL command log;
- restart một application instance thường làm instance đó khỏe lại tạm thời;
- số requests và traffic chỉ tăng khoảng 20%, không phải 10×;
- một endpoint export CSV mới được release gần cùng thời điểm incident bắt đầu.

Connection string dùng mặc định pooling và có `Max Pool Size=100`.

Export endpoint rút gọn:

```csharp
[HttpGet("api/orders/export")]
public async Task Export(CancellationToken ct)
{
    Response.ContentType = "text/csv";

    await using var connection = new SqlConnection(_connectionString);
    await connection.OpenAsync(ct);

    await using var transaction =
        (SqlTransaction)await connection.BeginTransactionAsync(ct);

    await using var command = connection.CreateCommand();
    command.Transaction = transaction;
    command.CommandText = """
        SELECT Id, CustomerName, Total, CreatedAt
        FROM Orders
        WHERE CreatedAt >= @from
        ORDER BY CreatedAt
        """;

    command.Parameters.AddWithValue("@from", DateTime.UtcNow.AddMonths(-6));

    await using var reader = await command.ExecuteReaderAsync(ct);

    while (await reader.ReadAsync(ct))
    {
        await Response.WriteAsync(
            $"{reader.GetInt32(0)},{reader.GetString(1)},{reader.GetDecimal(2)}\n",
            ct);

        await Response.Body.FlushAsync(ct);
    }

    await transaction.CommitAsync(ct);
}
```

Một export có thể mất 2–8 phút nếu client tải chậm. Cùng lúc có thể có 20–40 exports.

Một developer nói:

> “Query trong SQL chỉ nhanh vài chục milliseconds, nên database connection chắc chắn không phải vấn đề. Pool size 100 nghĩa là 100 connections luôn có sẵn.”

## Câu hỏi chính

Bạn sẽ điều tra incident này theo thứ tự nào? Hãy giải thích ADO.NET connection pooling thực sự hoạt động ra sao, tại sao command duration ngắn không bác bỏ connection starvation, connection/reader/transaction lifetime trong endpoint export ảnh hưởng thế nào, cách phân biệt pool-acquisition timeout với SQL command timeout, và cách sửa sao cho không chỉ che symptom bằng cách tăng `Max Pool Size`.

## Câu hỏi làm rõ nên cân nhắc

1. Timeout exception/message/stack trace cụ thể cho thấy đang chờ `OpenAsync`, command execution hay HTTP deadline?
2. Có bao nhiêu distinct connection strings thực tế? Khác whitespace/credentials/database/application name có tạo pools khác nhau không?
3. Export có thật sự cần transaction mở suốt 2–8 phút không?
4. Response/client download rate distribution là bao nhiêu? Có slow clients giữ request rất lâu không?
5. Có code path nào mở connection/transaction nhưng không dispose đúng khi exception/cancellation xảy ra không?
6. Pool counters hoặc runtime diagnostics có cho biết active/free/pooled connection counts và waiters không?

## Gợi ý tư duy

### Gợi ý 1

Một pooled connection chỉ trở lại pool khi logical owner đóng/dispose connection đúng lifecycle. Một query hoàn tất nhanh nhưng connection vẫn có thể bị giữ lâu bởi transaction, data reader hoặc application flow.

### Gợi ý 2

Ở endpoint trên, lifetime cần nhìn từ `OpenAsync()` tới cuối response streaming — không chỉ nhìn thời gian SQL Server thực thi `SELECT`.

### Gợi ý 3

20–40 exports giữ connection nhiều phút có thể tiêu thụ phần đáng kể pool 100. Các requests ngắn còn lại bắt đầu queue khi gọi `OpenAsync`, nên Application Insights có thể không có SQL dependency tương ứng vì command chưa bao giờ được gửi.

## Cấu trúc trả lời đề xuất

1. Xác định timeout đang xảy ra ở layer nào.
2. Vẽ lifecycle connection → transaction → reader → response stream.
3. Thu pool/runtime telemetry và correlate với export concurrency.
4. Kiểm tra code leaks và cancellation paths.
5. Tách database read duration khỏi client download duration.
6. Đề xuất remediation ngắn hạn có blast radius thấp.
7. Thiết kế export flow dài hạn phù hợp workload.
8. Load/failure test và rollout/rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết `Max Pool Size=100` là upper bound cho pool tương ứng, không phải 100 idle connections luôn sẵn.
- Biết `Open/OpenAsync` trên pooled connection có thể phải chờ khi pool exhausted.
- Nhận ra query timing chỉ đo command sau khi connection đã được acquire.
- Nhận ra endpoint giữ connection, transaction và reader trong suốt việc stream tới slow client.
- Hỏi timeout stack/message cụ thể thay vì gọi mọi timeout là SQL timeout.
- Không mặc định tăng pool size là root fix.
- Có mitigation tách DB resource lifetime khỏi slow network/client lifetime.

### Điểm cộng

- Nhận ra explicit transaction cho read-only export dài có thể không cần thiết và còn tăng lock/versioning/resource lifetime tùy isolation.
- Cân nhắc đọc theo bounded batches/keyset rồi ghi output mà không giữ một reader/connection nhiều phút.
- Cân nhắc generate export ra temporary/durable file/object storage trước rồi client download tách biệt nếu business flow cho phép.
- Có endpoint-level concurrency/admission limit cho expensive exports.
- Phân biệt connection pool per exact connection configuration/credential context và không coi toàn process chỉ có một pool duy nhất trong mọi trường hợp.

### Senior+

- Phân tích trade-off giữa streaming trực tiếp từ DB (low application buffering) và holding scarce DB connection theo tốc độ client.
- Đề xuất capacity model: short-request connection demand + long-export occupancy + headroom.
- Kiểm tra pool fragmentation do multiple connection strings/identity modes.
- Có telemetry cho connection acquisition duration riêng với command duration.
- Thiết kế failure/cancellation test với slow clients và aborted downloads.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng exception/stack trace, không bắt đầu bằng `Max Pool Size`. “Timeout” có thể là:

- timeout khi `SqlConnection.Open/OpenAsync` chờ pooled connection;
- SQL command timeout sau khi command đã gửi;
- transaction timeout;
- ASP.NET Core/reverse-proxy/request deadline;
- client cancellation.

Symptom “không thấy SQL dependency trước timeout” cộng với “restart app khỏe lại tạm thời” và export mới giữ connections lâu khiến pool starvation là hypothesis mạnh, nhưng vẫn cần đo.

ADO.NET pooling giữ physical database connections để reuse. Khi code gọi `OpenAsync`, nếu pool có một usable idle connection thì nó được checkout nhanh. Nếu pool đã đạt max và mọi connection đang được sử dụng, caller phải chờ connection được trả về. `Max Pool Size=100` không có nghĩa có sẵn 100 idle connections; nó nghĩa pool đó không mở vô hạn quá configured maximum trong normal pooling semantics.

Endpoint export mở connection trước query rồi giữ nó cho tới cuối method. Reader phụ thuộc command/connection; transaction cũng gắn connection. `await using` bảo đảm cleanup khi scope kết thúc, nhưng scope kết thúc sau khi toàn bộ CSV đã được đẩy cho client. Nếu client nhận dữ liệu chậm, một connection có thể bị chiếm 8 phút dù SQL Server đã produce phần lớn rows rất sớm hoặc đang chờ flow của reader.

Giả sử 40 exports concurrent, chúng có thể giữ 40/100 connections. Các API khác, background work và burst traffic dùng phần còn lại. Chỉ cần một số paths giữ connection lâu hoặc pool bị fragment, headroom có thể biến mất nhanh. Khi đó short request chờ ở `OpenAsync`; SQL Server CPU vẫn thấp vì nhiều work chưa tới server.

Tôi sẽ instrument/thu thập:

- duration của connection acquisition riêng với command execution;
- active/idle pooled connection signals nếu provider/runtime counters cho phép;
- số concurrent exports và export duration;
- request duration/client disconnect rate;
- SQL sessions theo application name/host;
- connection string variants/pool fragmentation;
- command/transaction duration;
- exceptions tại exact call site.

Remediation ngắn hạn có thể là giới hạn concurrent exports, ví dụ admission/semaphore ở mức service-wide phù hợp deployment topology, hoặc feature flag giảm endpoint traffic. Tăng pool size chỉ cân nhắc nếu SQL Server và app đều có capacity và capacity model chứng minh pool đang quá nhỏ cho legitimate concurrency; không dùng như first reflex.

Về code, tôi đặt câu hỏi đầu tiên: transaction có cần cho export read-only kéo dài nhiều phút không? Nếu không có consistency requirement cụ thể, bỏ explicit long transaction. Nhưng ngay cả bỏ transaction, reader vẫn giữ connection trong thời gian enumerate.

Có ba design directions tùy requirement:

1. **Direct streaming** nếu export nhỏ/nhanh và client speed đủ ổn định. Giữ implementation đơn giản nhưng limit concurrency.
2. **Batch/keyset extraction**: đọc một batch rows, đóng reader/connection, ghi batch vào output, rồi tiếp tục theo stable key. Cần semantics cho dữ liệu thay đổi giữa batches.
3. **Asynchronous generated export**: worker đọc database trong bounded fashion, ghi CSV vào Blob/file durable, sau đó HTTP download chỉ đọc object storage. Đây là lựa chọn mạnh khi export dài và user không cần synchronous generation.

Không có một lựa chọn universal. Nếu consistency bắt buộc là snapshot 6 tháng tại đúng một thời điểm, batching không có transaction có thể thấy changes giữa batches; cần snapshot-capable design/read replica/export snapshot hoặc business semantics khác. Nhưng giữ OLTP connection/transaction 8 phút cũng có cost rất lớn.

Testing phải có slow-client simulation. Một load test chỉ đọc response ở LAN tốc độ cao sẽ bỏ lỡ root cause. Tôi tạo 30–40 clients đọc vài KB/s, đồng thời chạy representative short API traffic và quan sát acquisition wait/p99. Test thêm client abort giữa download để xác minh reader/connection được dispose nhanh. Sau fix, success criteria là pool headroom ổn, acquisition latency thấp và short API p99 không bị export kéo lên.

## Mẫu trả lời trong phỏng vấn

“SQL dependency 30 ms không loại trừ connection starvation vì dependency thường chỉ bắt đầu sau khi đã acquire được connection. Tôi muốn xem stack trace timeout có nằm ở `OpenAsync` hay command execution.

Ở endpoint này, connection mở trước query và chỉ dispose khi method kết thúc. Reader và transaction cũng sống trong scope đó. Nếu client tải CSV trong 8 phút, database connection có thể bị giữ gần 8 phút. 40 exports có thể chiếm 40% một pool size 100 trước khi tính mọi API khác. Khi pool hết, short requests queue ở `OpenAsync`; SQL CPU thậm chí có thể vẫn thấp vì work chưa tới database.

Tôi sẽ đo connection-acquisition duration, concurrent exports, pool/session counts và connection-string variants. Ngắn hạn tôi giới hạn exports thay vì chỉ tăng pool. Dài hạn tôi xem có thể bỏ long read transaction, batch extraction hoặc tốt hơn là generate export ra Blob rồi tách download khỏi database lifetime.

Tôi cũng test bằng slow clients và aborted downloads. Mục tiêu là database resource lifetime phụ thuộc vào thời gian cần đọc dữ liệu, không phụ thuộc trực tiếp vào tốc độ internet của user.”

## Câu hỏi đào sâu

1. Nếu product bắt buộc CSV phải phản ánh một transactionally consistent snapshot tại thời điểm user bấm Export, bạn thiết kế thế nào mà không giữ OLTP transaction 8 phút theo tốc độ client?
2. Nếu tăng pool từ 100 lên 200 giúp p99 tốt ngay và SQL CPU vẫn 50%, khi nào bạn chấp nhận đó là một phần fix hợp lệ?
3. Nếu application chạy 6 replicas, mỗi replica có pool 100, bạn sẽ capacity-plan tổng SQL connections thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất query execution time với thời gian giữ connection.
- Nghĩ pool size 100 nghĩa luôn có 100 connection rảnh.
- Chỉ tăng `Max Pool Size`.
- Bỏ qua slow-client behavior.
- Không phân biệt `OpenAsync` timeout, command timeout và request timeout.
- Không test abort/cancellation cleanup.

## Thang điểm 0–10

- **0–2:** Chỉ đổ lỗi SQL query hoặc tăng timeout/pool size.
- **3–4:** Nhận ra connection lifetime dài nhưng investigation/measurement còn yếu.
- **5–6:** Phân biệt acquisition vs command, có concurrency limit và lifecycle fix.
- **7–8:** Có capacity model, slow-client test, batch/async export trade-offs và pool fragmentation analysis.
- **9–10:** Điều tra evidence-driven từ symptom → pool semantics → resource lifetime → business consistency → architecture/rollout, đồng thời bảo vệ OLTP workload rõ ràng.

# Câu 3 — Phân quyền portal 35 modules: dùng role trong JWT, policy-based authorization hay lưu quyền theo resource trong database?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core authorization, claims, RBAC, permission model, resource-based authorization, multi-tenancy, enterprise identity, security architecture, caching/revocation, auditability, testing, operational trade-offs

## Bối cảnh

Một enterprise employee portal có khoảng 35 modules:

- Employee Profile
- Timesheet
- Leave
- Approval
- Documents
- Finance claims
- Admin
- Reporting
- Support tools

Authentication do enterprise Identity Provider thực hiện. ASP.NET Core nhận JWT access token có các claims cơ bản như:

```json
{
  "sub": "user-1281",
  "tenant_id": "42",
  "department": "FINANCE",
  "roles": ["Employee", "Manager"]
}
```

Hiện code authorization phát triển tự phát theo từng module:

```csharp
if (User.IsInRole("Admin")) { ... }
```

```csharp
if (User.HasClaim("department", "FINANCE")) { ... }
```

```csharp
if (document.OwnerId == currentUserId || user.IsManager) { ... }
```

```csharp
[Authorize(Roles = "Manager,Admin")]
```

Business sắp thêm các rules:

- manager chỉ được approve employees thuộc reporting line của mình;
- Finance Reviewer được xem claims của một legal entity nhất định nhưng không phải entity khác;
- document owner có thể share một document cho một user/group cụ thể;
- Support được impersonate/read một số screens trong 30 phút sau khi ticket được approved;
- quyền phải revoke trong vài phút khi employee chuyển department hoặc bị disable;
- tenant A tuyệt đối không được truy cập resource tenant B;
- security team cần audit được “ai có quyền gì, do rule nào”;
- không muốn access token phình thành hàng nghìn permissions/resource IDs;
- API có nhiều endpoints và sẽ tiếp tục tăng.

Trong design review có ba ý kiến:

1. “Đưa toàn bộ permissions vào JWT; API đọc claims là nhanh nhất và stateless.”
2. “Chỉ dùng roles: `Employee`, `Manager`, `Finance`, `Admin`; code tự kiểm tra dữ liệu cần thiết.”
3. “Mọi authorization request đều query database để đảm bảo realtime; đừng tin claims ngoài `sub`.”

## Câu hỏi chính

Bạn sẽ thiết kế authorization model cho hệ thống này như thế nào? Hãy phân biệt authentication, coarse-grained roles/claims, permissions và resource-based authorization; quyết định dữ liệu nào nên nằm trong token, dữ liệu nào nên resolve ở application/database; cách xử lý tenant isolation, revocation, caching, support impersonation, audit và testing; đồng thời giải thích vì sao một mô hình “mọi thứ trong JWT” hoặc “mọi request query DB” đều có trade-off đáng kể.

## Câu hỏi làm rõ nên cân nhắc

1. Identity Provider có hỗ trợ groups/app roles/claims transformation và token lifetime bao lâu?
2. Reporting-line/legal-entity membership thay đổi với frequency nào và source of truth ở đâu?
3. Quyền share document có số lượng/độ phân tán như thế nào — vài ACL entries hay hàng triệu?
4. SLA cho revocation là “ngay lập tức”, dưới 5 phút hay theo token expiration?
5. Support impersonation cần “act as user” thật sự hay chỉ elevated read with explicit actor/subject audit?
6. Có API-to-API service identities/background jobs cần cùng permission model không?

## Gợi ý tư duy

### Gợi ý 1

Token claims phù hợp với identity/coarse attributes tương đối ổn định. Quyền phụ thuộc **resource hiện tại** thường cần resource context và source of truth mới đánh giá được.

### Gợi ý 2

`Manager` không tự trả lời câu hỏi “manager của employee 9182 có phải user hiện tại không?”. Role có thể cho biết loại capability; relationship quyết định instance cụ thể.

### Gợi ý 3

Authorization architecture không chỉ là `Allow/Deny`. Hãy nghĩ tới reason/audit, revocation latency, cache invalidation và cách ngăn developer quên check ở một endpoint mới.

## Cấu trúc trả lời đề xuất

1. Tách authentication khỏi authorization.
2. Liệt kê các authorization dimensions: tenant, role, relationship, resource ACL, temporary privilege.
3. Xác định source of truth cho từng dimension.
4. Thiết kế policy/resource-based authorization API trong ASP.NET Core.
5. Quyết định token claim scope và revocation strategy.
6. Thiết kế cache có bounded staleness.
7. Thiết kế impersonation/elevation an toàn và auditable.
8. Enforce tenant isolation/defense-in-depth.
9. Test matrix và observability/audit.
10. Rollout từ code checks hiện tại sang policy model.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Phân biệt authentication (“ai”) với authorization (“được làm gì trên resource nào”).
- Không dùng vài coarse roles để thay thế resource relationship checks.
- Không nhét hàng nghìn resource permissions vào JWT.
- Token có thể chứa stable/coarse identity attributes nhưng dynamic resource authorization cần lookup/source-of-truth phù hợp.
- Dùng ASP.NET Core policy/resource-based authorization hoặc abstraction tương đương để centralize semantics.
- Tenant ID phải được kiểm tra như security boundary, không chỉ UI filter.
- Có revocation semantics rõ gắn với token/cache lifetime.
- Có audit cho privileged/support actions.

### Điểm cộng

- Phân biệt role, permission/capability và resource constraint.
- Dùng authorization handler nhận resource cụ thể thay vì rải `if` khắp controller/service.
- Cache manager/reporting-line relationship với TTL/version/event invalidation có chủ đích, không cache forever.
- Có policy naming/permission catalog để tránh string literals phân tán.
- Có test negative/cross-tenant quan trọng hơn chỉ happy-path.

### Senior+

- Thiết kế explainable authorization result/reason để security audit/debug mà không leak sensitive information cho caller.
- Xử lý stale JWT claims bằng short token lifetime, security stamp/session revocation hoặc high-risk online check tùy IdP capability.
- Support elevation dùng actor + subject semantics, expiry, approval reference và immutable audit; tránh tạo token indistinguishable với user thật nếu compliance cần attribution.
- Cân nhắc database Row-Level Security cho high-risk tenant isolation nhưng hiểu operational complexity và không coi nó thay application authorization.
- Có migration strategy giúp endpoint mới không bypass authorization abstraction.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng việc tách hai câu hỏi:

- **Authentication:** token có hợp lệ không, ai là caller, tenant/issuer/audience là gì?
- **Authorization:** caller đó có được thực hiện operation X trên resource Y ở thời điểm hiện tại không?

JWT rất phù hợp mang `sub`, issuer/audience, tenant, một số app roles hoặc stable coarse attributes. Nó không phù hợp làm một database snapshot khổng lồ của mọi document IDs, every reporting-line edge hay temporary support grant. Token càng nhiều dynamic permissions thì càng lớn, càng stale và càng khó revoke.

Tôi sẽ định nghĩa một permission/capability catalog ở application, ví dụ:

```text
Employee.ReadSelf
Employee.ReadManaged
Leave.Approve
FinanceClaim.Review
Document.Read
Document.Share
Support.ElevatedRead
```

Roles map tới **candidate capabilities**, nhưng resource rule vẫn quyết định cuối cùng. `Manager` có thể là prerequisite cho `Leave.Approve`, nhưng handler phải kiểm tra target employee có nằm trong reporting line hiện tại của manager hay không.

Trong ASP.NET Core, direction có thể là policy + resource-based authorization:

```csharp
public sealed record ApproveLeaveRequirement : IAuthorizationRequirement;

public sealed class ApproveLeaveHandler
    : AuthorizationHandler<ApproveLeaveRequirement, LeaveRequest>
{
    private readonly IReportingLineService _reporting;

    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        ApproveLeaveRequirement requirement,
        LeaveRequest resource)
    {
        var userId = context.User.FindFirstValue("sub");
        var tenantId = context.User.FindFirstValue("tenant_id");

        if (userId is null || tenantId != resource.TenantId.ToString())
            return;

        if (!context.User.IsInRole("Manager"))
            return;

        if (await _reporting.IsManagerOfAsync(userId, resource.EmployeeId))
            context.Succeed(requirement);
    }
}
```

Code cụ thể có thể khác, nhưng invariant là authorization logic có một home rõ ràng và endpoint/service không tự viết một version khác của rule.

Với document sharing, ACL/resource grants nên nằm ở database hoặc permission store vì cardinality/resource-specific nature. Token chỉ cần identity/coarse role. Query resource/ACL có thể tối ưu bằng join/index hoặc precomputed grants nếu workload lớn; không nên đưa danh sách document IDs vào JWT.

Với Finance legal entity, nếu membership khá ổn định có thể đưa một small set entity claims vào token, nhưng requirement revocation phải quyết định. Nếu employee transfer phải có hiệu lực dưới 5 phút mà token sống 60 phút, token-only check vi phạm requirement. Options gồm short-lived tokens, IdP revocation/session controls, online authorization lookup cho high-risk action hoặc cache TTL/version dưới 5 phút.

Tôi không mặc định “mọi request query DB”. Có những checks rẻ từ token như authenticated tenant + coarse role. Dynamic relationship có thể cache, nhưng cache phải có staleness budget. Ví dụ reporting-line cache TTL 2 phút và invalidation event khi HR data thay đổi. Với high-risk finance approval, có thể bypass cache hoặc require fresher version. Đây là risk/cost decision.

Tenant isolation cần defense-in-depth. Mọi resource load nên scope theo tenant lấy từ trusted identity context, không nhận `TenantId` từ request body làm authority. Repository queries có tenant predicate/global filters; authorization handler vẫn validate resource tenant. Với sensitivity cao có thể cân nhắc SQL Row-Level Security, nhưng RLS không thay thế business permissions và làm deployment/debug phức tạp hơn.

Support impersonation cần đặc biệt cẩn trọng. Thay vì phát một identity không phân biệt được với target user, tôi muốn giữ:

```text
actor = support-user-17
subject = employee-9182
reason/ticket = INC-4821
expires_at = ...
approved_by = ...
```

Mọi privileged action ghi audit cả actor và subject. Grant tự hết hạn và có revoke path. UI hiển thị rõ elevated mode. Nếu support chỉ cần read, đừng cấp write chỉ vì impersonation mechanism thuận tiện.

Testing gồm policy matrix:

- same tenant allow/deny;
- cross-tenant always deny;
- manager of target vs manager of unrelated employee;
- stale/revoked finance membership;
- document owner/shared/unshared;
- expired support grant;
- service identity/background job cases.

Nên có integration tests ở endpoint boundary để chứng minh một endpoint mới không bỏ qua policy. Security logging ghi policy outcome/reason code, actor, resource type/id hash hoặc safe identifier; không log full sensitive document data.

Rollout từ hệ thống `if` rải rác có thể làm theo module. Tạo permission catalog + authorization service, migrate high-risk Finance/Admin/Documents trước, thêm test guardrails/code review convention, rồi remove legacy checks sau khi parity verified. Không cần rewrite 35 modules một lúc.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn một trong ba cực đoan. JWT nên chứng minh identity và mang một số coarse attributes/roles tương đối ổn định; nó không nên chứa hàng nghìn resource permissions. Ngược lại, không phải check nào cũng cần query DB.

Tôi định nghĩa permissions như `Leave.Approve` hoặc `Document.Share`, rồi dùng ASP.NET Core policy/resource-based handlers. Role `Manager` chỉ là prerequisite; khi approve leave, handler còn kiểm tra employee có nằm trong reporting line của manager và cùng tenant hay không. Document ACL và temporary grants nằm ở server-side source of truth vì chúng dynamic và resource-specific.

Revocation quyết định cache/token strategy. Nếu permission phải revoke trong 5 phút, token sống 1 giờ không thể là source duy nhất. Tôi dùng short token lifetime, online lookup hoặc cache có TTL/version phù hợp mức risk. Tenant isolation được enforce cả khi load resource và authorization; không tin tenant ID từ payload.

Support elevation phải giữ actor và subject riêng, có expiry/ticket/approval và audit đầy đủ. Cuối cùng tôi có negative integration tests, đặc biệt cross-tenant và revoked grants, rồi migrate từng module khỏi các `if` authorization rải rác.

Mục tiêu là rules có một nơi định nghĩa, giải thích được tại sao allow/deny, revoke được đúng SLO và đủ nhanh cho production — chứ không phải stateless bằng mọi giá.”

## Câu hỏi đào sâu

1. Nếu IdP chỉ phát access token 60 phút và không hỗ trợ token revocation, nhưng Finance permission phải revoke trong 2 phút, bạn thiết kế online check/cache thế nào?
2. Nếu reporting-line service bị outage, approval endpoint nên fail-open hay fail-closed? Điều gì quyết định lựa chọn?
3. Tôi muốn dùng SQL Row-Level Security cho tenant + ACL và bỏ hầu hết application authorization handlers; bạn đồng ý đến mức nào?

## Lỗi trả lời thường gặp

- Nhầm authentication với authorization.
- Dùng `Admin/Manager` roles cho mọi business rule.
- Nhét resource IDs/permissions khổng lồ vào JWT.
- Query database cho mọi check mà không có performance/failure model.
- Cache authorization indefinitely và quên revocation SLO.
- Impersonation nhưng audit chỉ ghi target user, mất actor thật.
- Chỉ test allow path, không test cross-tenant/deny/revocation.

## Thang điểm 0–10

- **0–2:** Chỉ nói roles/JWT chung chung, không có resource semantics.
- **3–4:** Có policy-based authorization nhưng thiếu revocation, tenant isolation hoặc audit.
- **5–6:** Phân tách token/dynamic lookup hợp lý, có resource handler, cache TTL và negative tests.
- **7–8:** Xử lý tốt revocation, impersonation, defense-in-depth, failure semantics và migration từ legacy checks.
- **9–10:** Thiết kế authorization có explicit invariants, explainability, bounded staleness, operational telemetry và trade-offs rõ giữa security, latency, complexity và availability.
