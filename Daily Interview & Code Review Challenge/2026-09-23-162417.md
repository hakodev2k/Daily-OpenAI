# Code Review Challenge 1 — Optimizely CMS cache làm rò nội dung theo market và không invalidation khi publish

**Chủ đề:** C#/.NET, Optimizely CMS, ASP.NET Core, caching, content delivery, multi-site/market correctness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một marketing website chạy ASP.NET Core + Optimizely CMS trên nhiều application instances. Trang product landing lấy content đã publish từ CMS, sau đó bổ sung giá và CTA theo `market`/`language`. Để giảm latency, team thêm một custom in-memory cache trong service.

Sau khi scale-out, editor báo rằng một số user ở `vi-VN` thỉnh thoảng thấy CTA tiếng Anh; sau publish, instance A hiển thị content mới nhưng instance B vẫn giữ content cũ nhiều phút. Một incident khác cho thấy request của market `VN` nhận dữ liệu giá đã cache từ market `SG`. Team đề xuất tăng TTL lên 30 phút để giảm tải CMS hơn nữa.

Không được giả định rằng custom cache này có tích hợp sẵn với Optimizely content invalidation. Hãy review dựa trên code và các invariant: content đúng language, dữ liệu thương mại đúng market, publish phải hội tụ có kiểm soát, và cache failure không được làm sai authorization/business boundary.

## Đoạn code cần review

```csharp
public sealed class ProductLandingService
{
    private static readonly Dictionary<int, ProductLandingDto> Cache = new();

    private readonly IContentLoader _contentLoader;
    private readonly IPriceClient _priceClient;
    private readonly ILogger<ProductLandingService> _logger;

    public ProductLandingService(
        IContentLoader contentLoader,
        IPriceClient priceClient,
        ILogger<ProductLandingService> logger)
    {
        _contentLoader = contentLoader;
        _priceClient = priceClient;
        _logger = logger;
    }

    public async Task<ProductLandingDto> GetAsync(
        ContentReference contentLink,
        string language,
        string market,
        CancellationToken cancellationToken)
    {
        if (Cache.TryGetValue(contentLink.ID, out var cached))
            return cached;

        var page = _contentLoader.Get<ProductLandingPage>(contentLink);

        var price = await _priceClient.GetPriceAsync(
            page.ProductCode,
            market,
            cancellationToken);

        var dto = new ProductLandingDto
        {
            Id = contentLink.ID,
            Name = page.Name,
            HeroText = page.HeroText,
            ProductCode = page.ProductCode,
            Price = price.Amount,
            Currency = price.Currency,
            Market = market,
            Language = language
        };

        Cache[contentLink.ID] = dto;

        _logger.LogInformation(
            "Cached product page {ContentId} for {Language}/{Market}",
            contentLink.ID,
            language,
            market);

        return dto;
    }
}
```

Service được đăng ký:

```csharp
services.AddScoped<ProductLandingService>();
```

Production có 4 replicas phía sau load balancer.

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong cache key, content selection và concurrent access.
2. Xác định performance/reliability concerns khi traffic tăng và khi `_priceClient` chậm.
3. Giải thích production impact, đặc biệt cross-market/cross-language contamination và stale publish.
4. Xếp severity theo data correctness, concurrency và availability.
5. Đề xuất corrected implementation/design phù hợp với CMS và scale-out.
6. Giải thích test strategy cho language, market, publish invalidation, concurrency và dependency failure.
7. Nêu telemetry đủ để chứng minh cache đang đúng thay vì chỉ có hit ratio cao.

## Câu hỏi gợi mở

1. `contentLink.ID` có đủ để định danh output khi cùng page được yêu cầu với nhiều language/market không?
2. `Dictionary<TKey,TValue>` static sẽ hành xử thế nào khi nhiều request đọc/ghi đồng thời?
3. Parameter `language` hiện có thực sự quyết định content version được load không?
4. Publish event trên một CMS node có tự động làm custom static dictionary trên mọi web replica mất entry không?
5. Giá từ external service nên có cùng lifecycle/invalidation với editorial content không?

### Gợi ý 1

Rủi ro chính là cache correctness: identity của cached representation đang nhỏ hơn identity thật của dữ liệu.

### Gợi ý 2

Tách editorial content khỏi market-specific commercial data; sau đó reasoning về invalidation, multi-instance consistency và cache stampede.

## Kết quả code review tham khảo

### Critical — Cache key bỏ qua market

**Vấn đề:** Cache chỉ dùng `contentLink.ID` nhưng DTO chứa `Price`, `Currency`, `Market`.  
**Tại sao xảy ra:** Representation phụ thuộc market nhưng market không nằm trong identity của cache entry.  
**Ảnh hưởng production:** Request cho market sau có thể nhận giá/currency của market trước. Đây là data correctness bug, không chỉ là stale-cache issue.  
**Cách sửa:** Không cache market-specific data bằng key chỉ có content ID. Tách content cache và price cache hoặc dùng composite key có market cùng semantics/TTL phù hợp.

### Critical — Cache key bỏ qua language và content load không dùng language explicit

**Vấn đề:** DTO có `Language` nhưng cache key không có language; code cũng không thể hiện việc chọn language branch khi load content.  
**Tại sao xảy ra:** Input `language` chỉ được copy vào output.  
**Ảnh hưởng production:** User có thể nhận content của language request trước hoặc content được resolve theo ambient/default language thay vì requested language.  
**Cách sửa:** Resolve content bằng language-aware API/context phù hợp với phiên bản Optimizely đang dùng và đưa language vào cache identity. Cần xác minh fallback behavior mong muốn thay vì ngầm dựa vào ambient context.

### High — Static `Dictionary` không thread-safe

**Vấn đề:** Nhiều request có thể đọc/ghi dictionary đồng thời.  
**Tại sao xảy ra:** Static mutable collection dùng làm shared cache nhưng không có synchronization.  
**Ảnh hưởng production:** Race condition, duplicate population và behavior không an toàn dưới load.  
**Cách sửa:** Dùng caching abstraction thread-safe (`IMemoryCache` cho per-instance cache) hoặc distributed cache khi thật sự cần; vẫn phải thiết kế key/invalidation đúng.

### High — Custom cache không gắn với publish invalidation

**Vấn đề:** Entry không có TTL, eviction hay invalidation hook.  
**Tại sao xảy ra:** Cache lifecycle độc lập CMS lifecycle.  
**Ảnh hưởng production:** Content có thể stale cho tới process restart; scale-out làm mỗi replica giữ một trạng thái khác nhau.  
**Cách sửa:** Ưu tiên tận dụng caching/content-loading semantics của CMS nơi phù hợp. Nếu cần derived cache, gắn invalidation với content-change signal có thể propagate giữa nodes hoặc dùng bounded TTL + versioned key/revalidation tùy consistency requirement.

### High — Cache không có bounded size/lifetime

**Vấn đề:** Static dictionary tăng theo số content ID từng được truy cập.  
**Tại sao xảy ra:** Không eviction/size limit.  
**Ảnh hưởng production:** Long-lived process có thể giữ object không giới hạn, tăng memory footprint.  
**Cách sửa:** Dùng cache có eviction/expiration và đo working set; không dùng dictionary như cache production.

### High — Cache miss có thể tạo stampede vào price service

**Vấn đề:** Nhiều request cùng key miss đồng thời đều gọi `_priceClient`.  
**Tại sao xảy ra:** Không có request coalescing/single-flight hoặc cache riêng cho price.  
**Ảnh hưởng production:** Traffic burst sau deploy/invalidation khuếch đại load lên dependency và tăng latency.  
**Cách sửa:** Chỉ thêm coalescing nếu evidence cho thấy cần; dùng bounded concurrency/timeout và cache policy riêng cho price nếu business cho phép stale price.

### Medium — Editorial content và volatile price bị đóng gói vào cùng cache lifecycle

**Vấn đề:** Hai loại dữ liệu có owner, freshness và invalidation khác nhau nhưng bị cache cùng entry.  
**Tại sao xảy ra:** Cache DTO cuối cùng vì tiện.  
**Ảnh hưởng production:** Hoặc content stale theo price TTL, hoặc price stale theo content TTL; invalidation khó reason.  
**Cách sửa:** Cache theo data ownership: CMS content theo content lifecycle; commercial data theo market/product và business freshness requirement; compose ở request boundary.

### Medium — Không có explicit timeout/resilience semantics cho price dependency

**Vấn đề:** Cancellation từ request có truyền xuống nhưng code không thể hiện timeout budget/fallback policy.  
**Tại sao xảy ra:** Dependency call được coi như luôn nhanh.  
**Ảnh hưởng production:** Slow price service kéo dài request latency và có thể gây cascading saturation.  
**Cách sửa:** Đặt timeout/retry theo dependency contract; retry chỉ transient failure và phải nằm trong request budget. Fallback sang stale price chỉ khi business chấp nhận và phải đánh dấu rõ.

### Medium — Telemetry không phân biệt cache correctness

**Vấn đề:** Log “Cached” không cho biết hit/miss, key dimensions, content version hay dependency latency.  
**Tại sao xảy ra:** Observability chỉ ghi action, không ghi evidence cho freshness/correctness.  
**Ảnh hưởng production:** Khó điều tra cross-market/language và stale-node incidents.  
**Cách sửa:** Metrics cho hit/miss/eviction, dimensions an toàn cho language/market, content version/change timestamp, price dependency latency và per-instance cache state khi cần.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa việc **không cache DTO đã trộn content + price**. API Optimizely cụ thể để load language branch phải được chọn theo version/project configuration; phần đó được bọc sau abstraction để tránh giả định API/version:

```csharp
public sealed record ContentCacheKey(int ContentId, string Language);

public sealed class ProductLandingService
{
    private readonly IMemoryCache _cache;
    private readonly ILocalizedProductContentReader _contentReader;
    private readonly IPriceClient _priceClient;

    public ProductLandingService(
        IMemoryCache cache,
        ILocalizedProductContentReader contentReader,
        IPriceClient priceClient)
    {
        _cache = cache;
        _contentReader = contentReader;
        _priceClient = priceClient;
    }

    public async Task<ProductLandingDto> GetAsync(
        ContentReference link,
        string language,
        string market,
        CancellationToken ct)
    {
        var key = new ContentCacheKey(link.ID, language);

        var content = await _cache.GetOrCreateAsync(key, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            return await _contentReader.GetPublishedAsync(link, language, ct);
        });

        if (content is null)
            throw new InvalidOperationException("Published content not found.");

        var price = await _priceClient.GetPriceAsync(
            content.ProductCode,
            market,
            ct);

        return new ProductLandingDto
        {
            Id = link.ID,
            Name = content.Name,
            HeroText = content.HeroText,
            ProductCode = content.ProductCode,
            Price = price.Amount,
            Currency = price.Currency,
            Market = market,
            Language = language
        };
    }
}
```

Production implementation nên ưu tiên CMS-native cache/invalidation cho content nếu abstraction đó đã cung cấp semantics cần thiết. Nếu thêm custom cache, publish invalidation phải remove đúng `(ContentId, Language)` trên mọi replica hoặc chấp nhận bounded staleness được business phê duyệt. Price có thể có cache riêng `(ProductCode, Market)` chỉ nếu freshness requirement cho phép.

## Giải thích thiết kế sau khi sửa

Cache boundary được đặt theo ownership/freshness thay vì theo DTO tiện lợi. Editorial content và commercial price không còn chia sẻ một invalidation policy. Language là một phần của content identity; market là một phần của price identity. Multi-instance consistency được xem là requirement explicit, không mặc định static memory sẽ đồng bộ.

## Trade-offs

`IMemoryCache` đơn giản và nhanh nhưng per-instance; nếu publish cần gần như tức thời trên mọi node, cần distributed invalidation hoặc dựa vào cơ chế CMS đã có. Distributed cache tăng network dependency và serialization complexity, không tự giải quyết key correctness. TTL ngắn giảm stale window nhưng tăng origin load. Cache price có thể giảm latency nhưng làm tăng rủi ro stale commercial data.

## Cách kiểm thử

1. Integration test cùng content ID với `vi-VN` và `en-US`; assert representation không cross-contaminate.
2. Integration test cùng product với market `VN` và `SG`; assert price/currency đúng market ngay cả khi request chạy concurrent.
3. Concurrency/load test cold cache để đo duplicate dependency calls và memory behavior.
4. Multi-instance test publish/update content rồi route request qua từng replica; assert behavior đúng theo invalidation/SLA đã chọn.
5. Failure-path test price timeout; xác minh timeout budget, error/fallback semantics và không cache response lỗi như dữ liệu hợp lệ.

## Quan sát trong production

Theo dõi cache hit/miss/eviction theo cache type, dependency latency/error rate, content version/change age, stale-content incidents, price mismatch signals, process memory và request p95/p99. Correlate request với instance ID, content ID, language, market và product code ở mức không chứa PII. Alert khi dependency latency tăng hoặc freshness vượt SLA thay vì chỉ alert cache miss rate.

## Câu hỏi phỏng vấn mở rộng

1. Nếu editor yêu cầu publish phải xuất hiện trên mọi node trong 5 giây, bạn thay đổi invalidation design thế nào?
2. Khi nào distributed cache là cần thiết, và khi nào CMS-native caching + per-instance derived cache đơn giản hơn?
3. Nếu price service cho phép stale price tối đa 60 giây, bạn chống stampede mà vẫn giữ market isolation thế nào?

# Code Review Challenge 2 — Deployment pipeline chạy database migration trước khi biết artifact có deploy được

**Chủ đề:** CI/CD, TeamCity, Octopus Deploy, SQL migration, release safety, secrets, rollback, immutable artifacts  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core application được build bằng TeamCity và deploy qua Octopus Deploy tới IIS/Windows Server. Release gồm web artifact và SQL migration script. Production có 6 web nodes phía sau load balancer.

Team muốn deployment “nhanh và tự động” nên step migration chạy đầu tiên. Gần đây một release đã `ALTER COLUMN` trước khi web package mới deploy xong; package sau đó fail health check ở node thứ hai. Rollback application về version cũ nhưng schema đã thay đổi, khiến version cũ không chạy được. Một incident khác cho thấy cùng migration được chạy lại khi operator retry deployment.

Đây là deployment script hiện tại được gọi bởi release process.

## Đoạn code cần review

```powershell
param(
    [string]$PackagePath,
    [string]$SqlServer,
    [string]$Database,
    [string]$DbUser,
    [string]$DbPassword
)

$connectionString = "Server=$SqlServer;Database=$Database;User Id=$DbUser;Password=$DbPassword;TrustServerCertificate=True"

Write-Host "Deploying package $PackagePath"
Write-Host "Database connection: $connectionString"

sqlcmd -S $SqlServer -d $Database -U $DbUser -P $DbPassword -i ".\migrations\latest.sql"

Stop-WebAppPool -Name "CatalogAppPool"

Copy-Item $PackagePath "C:\inetpub\catalog" -Recurse -Force

Start-WebAppPool -Name "CatalogAppPool"

Invoke-WebRequest "https://catalog.internal/health" -UseBasicParsing

Write-Host "Deployment completed"
```

Release process gọi script tuần tự trên từng node, nhưng migration command cũng nằm trong script nên mỗi node chạy lại cùng `latest.sql`.

## Nhiệm vụ của ứng viên

1. Xác định correctness/release-safety problems trong migration và deployment ordering.
2. Xác định security concerns quanh credentials/logging/TLS behavior.
3. Giải thích impact khi deployment fail giữa chừng hoặc operator retry release.
4. Xếp severity theo data/schema risk, credential exposure và availability.
5. Đề xuất corrected release design; không cần phụ thuộc UI cụ thể của TeamCity/Octopus.
6. Giải thích deployment validation, rollback/roll-forward strategy và database compatibility testing.
7. Nêu telemetry/audit evidence cần giữ cho mỗi release.

## Câu hỏi gợi mở

1. Migration có nên chạy một lần cho release hay một lần cho mỗi web node?
2. Nếu schema mới không backward-compatible với version cũ, rolling deployment có an toàn không?
3. `sqlcmd` failure có chắc chắn dừng PowerShell script hiện tại không?
4. Log connection string chứa thông tin gì và ai có thể đọc release logs?
5. “Rollback web package” có đồng nghĩa “rollback database” không?

### Gợi ý 2

Reasoning theo expand/contract compatibility, idempotent/versioned migrations, secret handling và failure propagation của external processes.

## Kết quả code review tham khảo

### Critical — Database password bị ghi vào deployment log

**Vấn đề:** Script log toàn bộ connection string chứa password.  
**Tại sao xảy ra:** Secret được ghép thành plain string rồi `Write-Host`.  
**Ảnh hưởng production:** Bất kỳ principal nào đọc release logs có thể lấy database credential; log retention làm tăng exposure window.  
**Cách sửa:** Dùng secret variable/secret store của deployment platform hoặc integrated/service identity phù hợp; không log secret và rotate credential nếu đã lộ.

### Critical — Migration chạy lặp lại trên mỗi web node

**Vấn đề:** `latest.sql` được execute mỗi lần script chạy cho node.  
**Tại sao xảy ra:** Database migration bị đặt trong node deployment step thay vì release-level database step.  
**Ảnh hưởng production:** Non-idempotent DDL/DML có thể fail hoặc mutate data nhiều lần; retry deployment làm rủi ro tăng.  
**Cách sửa:** Migration là một release-level operation, có version/history table hoặc migration framework kiểm soát đã áp dụng gì; concurrency guard nếu release process có thể chạy song song.

### Critical — Destructive schema change trước application rollout phá rollback compatibility

**Vấn đề:** Schema có thể thay đổi không backward-compatible trước khi biết web artifact mới chạy ổn.  
**Tại sao xảy ra:** Không có expand/contract strategy hay compatibility window.  
**Ảnh hưởng production:** Nếu rollout fail, old app rollback có thể không chạy trên schema mới; outage kéo dài và data rollback có thể nguy hiểm.  
**Cách sửa:** Thiết kế migration theo expand/contract: additive schema trước, deploy code tương thích old+new, backfill/verify, rồi contract destructive change ở release sau khi old version không còn phụ thuộc.

### High — External command failure không được kiểm tra rõ ràng

**Vấn đề:** Script không kiểm tra exit code của `sqlcmd` và không bật error handling cho cmdlet failures.  
**Tại sao xảy ra:** PowerShell và native process failure semantics bị coi như exception tự động.  
**Ảnh hưởng production:** Migration có thể fail nhưng deployment tiếp tục, tạo mixed application/schema state.  
**Cách sửa:** Dùng `$ErrorActionPreference = 'Stop'`, kiểm tra `$LASTEXITCODE` sau native commands và fail release ngay với diagnostic an toàn.

### High — Node bị stop trước khi có drain/traffic coordination

**Vấn đề:** App Pool bị stop trực tiếp.  
**Tại sao xảy ra:** Script không remove/drain node khỏi load balancer trước deployment.  
**Ảnh hưởng production:** In-flight request có thể fail; rolling release tạo 5xx dù còn capacity.  
**Cách sửa:** Mark node unavailable/drain traffic, chờ in-flight budget, deploy, local health/readiness validate, rồi add node lại.

### High — Copy trực tiếp vào live directory không có atomic artifact switch

**Vấn đề:** `Copy-Item -Recurse -Force` thay file trong live directory.  
**Tại sao xảy ra:** Không có staged extraction/versioned directory.  
**Ảnh hưởng production:** Partial copy/failure có thể để mixed-version files; rollback khó chứng minh.  
**Cách sửa:** Stage immutable artifact vào versioned directory, verify checksum, rồi switch deployment target theo hosting strategy; giữ previous artifact cho rollback.

### High — Health check chỉ chạy qua shared URL

**Vấn đề:** `catalog.internal/health` có thể được load balancer route tới node khác.  
**Tại sao xảy ra:** Validation không target chính node vừa deploy.  
**Ảnh hưởng production:** Broken node có thể được coi là healthy vì request trả từ healthy node khác.  
**Cách sửa:** Validate local/node-specific endpoint trước khi đưa node lại pool, sau đó chạy synthetic/shared endpoint validation.

### Medium — `TrustServerCertificate=True` bỏ qua certificate-chain validation

**Vấn đề:** Connection explicitly trusts presented server certificate.  
**Tại sao xảy ra:** Convenience setting thường được thêm để tránh TLS certificate configuration issue.  
**Ảnh hưởng production:** Giảm assurance của TLS server identity nếu connection dùng encryption theo cấu hình driver/server.  
**Cách sửa:** Cấu hình certificate/hostname trust đúng cho production; không dùng bypass như default fix. Cần xác minh SQL client encryption settings thực tế trước khi kết luận transport behavior.

### Medium — Artifact identity chưa được verify

**Vấn đề:** Script nhận arbitrary path và không ghi version/checksum.  
**Tại sao xảy ra:** Build artifact và release artifact không có evidence immutable trong script.  
**Ảnh hưởng production:** Khó audit chính xác bits nào đã chạy và khó chứng minh rollback dùng đúng artifact.  
**Cách sửa:** Promote cùng immutable artifact từ build qua environments; record package version/hash và deployment ID.

### Medium — Không có post-migration verification/backfill gate

**Vấn đề:** Release coi `sqlcmd` success là đủ.  
**Tại sao xảy ra:** Không kiểm tra schema version/data invariants.  
**Ảnh hưởng production:** Migration syntactically thành công nhưng data/backfill có thể incomplete trước rollout.  
**Cách sửa:** Thêm verification query/invariant gate và telemetry trước khi chuyển sang application rollout.

## Phiên bản đề xuất

Một release flow an toàn hơn có thể được mô tả bằng script/pipeline pseudo-code sau; platform-specific steps có thể map vào TeamCity/Octopus mà không phụ thuộc UI:

```powershell
$ErrorActionPreference = 'Stop'

# Release-level step: chạy đúng một lần
Invoke-VersionedMigration -Package $MigrationPackage -SecretRef $DatabaseSecretRef
Assert-DatabaseCompatibility -RequiredVersion $RequiredSchemaVersion

foreach ($node in $WebNodes) {
    Disable-Traffic -Node $node
    Wait-ForDrain -Node $node -TimeoutSeconds 30

    $releaseDir = Stage-ImmutableArtifact `
        -Node $node `
        -Package $WebPackage `
        -ExpectedSha256 $WebPackageSha256

    Switch-WebDeployment -Node $node -ReleaseDirectory $releaseDir
    Start-Application -Node $node

    Assert-NodeHealth -Node $node
    Enable-Traffic -Node $node
}

Assert-SyntheticSmokeTest -BaseUrl $ProductionUrl
Record-ReleaseEvidence -ArtifactSha $WebPackageSha256 -Schema $RequiredSchemaVersion
```

Database evolution nên dùng sequence như:

```text
Release N:   EXPAND schema (additive, old app vẫn chạy)
Release N:   deploy app hỗ trợ old/new representation
Release N:   backfill + verify
Release N+1: CONTRACT sau khi không còn old readers/writers
```

Nếu migration là destructive hoặc data transform không reversible, rollback plan thường là **roll forward application** hoặc restore/recovery theo tested database procedure, không phải giả định chạy một down-script sẽ an toàn.

## Giải thích thiết kế sau khi sửa

Migration được tách khỏi per-node deployment và có versioned history. Artifact được build một lần rồi promote immutable. Mỗi node được drain, deploy, validate riêng trước khi nhận traffic lại. Schema evolution giữ compatibility window để application rollback không phụ thuộc vào việc đảo ngược destructive database change.

## Trade-offs

Expand/contract cần nhiều release hơn và tạm thời giữ schema dư thừa. Per-node drain/health gate làm deployment chậm hơn nhưng giảm blast radius. Database backup/restore có RTO/RPO và data-loss implications nên không thể coi là nút rollback thông thường. Immutable artifact staging cần disk space và cleanup policy. Secret store/service identity tăng setup nhưng giảm credential exposure.

## Cách kiểm thử

1. Database integration test chạy migration trên production-like schema snapshot; verify version, constraints và data invariants.
2. Idempotency/retry test chạy release migration step lần hai; expected behavior phải rõ: skip đã-applied version hoặc fail-safe, không duplicate mutation.
3. Compatibility test chạy old app và new app lần lượt trên expanded schema trước destructive contract.
4. Deployment failure injection ở node thứ hai; assert node lỗi không vào load balancer và các node còn lại vẫn phục vụ traffic.
5. Rollback/roll-forward rehearsal với immutable previous artifact và schema version thực tế.

## Quan sát trong production

Lưu release ID, artifact version/hash, schema version, migration duration/result, node deployment state, health-check result, request 5xx/p95/p99 trong rollout và database errors. Audit ai/automation nào chạy migration mà không log secret. Alert nếu node health fail, migration vượt budget, schema version lệch expectation hoặc error rate tăng sau từng deployment wave.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc zero-downtime nhưng migration cần đổi data type của cột rất lớn, bạn chia migration thành các phase thế nào?
2. Khi nào rollback application là hợp lý, và khi nào roll-forward an toàn hơn sau database migration?
3. Nếu hai release pipelines có thể chạy đồng thời, bạn bảo vệ migration ordering và deployment ownership ở đâu?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache correctness phụ thuộc vào identity, ownership, freshness và invalidation; hit ratio cao không chứng minh cache đúng.
- Trong CMS scale-out, custom per-process cache cần explicit strategy cho language, publish invalidation và multi-instance convergence.
- Editorial content và commercial data thường có lifecycle khác nhau; cache chung một DTO có thể làm correctness khó kiểm soát.
- Database migration và application deployment không tạo thành một atomic transaction; release safety cần compatibility window và failure-aware ordering.
- Immutable artifact, secret hygiene, node-specific health validation và release evidence là một phần của correctness chứ không chỉ DevOps convenience.

## Mẫu tư duy cần nhớ

- Cache key phải đại diện đầy đủ cho mọi dimension làm thay đổi output.
- Tách dữ liệu có owner/freshness khác nhau trước khi chọn cache policy.
- Thiết kế schema theo expand → migrate/backfill → contract khi cần rolling deployment.
- Không coi rollback code là rollback database.
- Test retry, partial failure và deployment giữa chừng thay vì chỉ test happy path.
