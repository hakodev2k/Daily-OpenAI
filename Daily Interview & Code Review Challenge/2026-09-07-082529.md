# Code Review Challenge 1 — Migration từ .NET Framework 4.5 sang modern .NET nhưng giữ lại sync-over-async, static state và blocking I/O

**Chủ đề:** C#/.NET, .NET modernization, ASP.NET Core, async/await, HttpClient, DI lifetime, configuration, backward compatibility  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một internal employee platform cũ đang được migrate từ ASP.NET MVC trên .NET Framework 4.5 sang ASP.NET Core trên modern .NET.

Team quyết định migrate theo hướng incremental thay vì rewrite toàn bộ. Một phần business logic được copy gần như nguyên trạng sang service mới để giảm risk.

System hiện tại:

- chạy trên Azure App Service on Linux;
- gọi third-party HR API qua HTTPS;
- lưu configuration trong environment/app settings;
- chạy nhiều application instance;
- có khoảng 300–500 concurrent users vào giờ cao điểm;
- một số endpoint gọi HR API mất 100–800 ms;
- production đã ghi nhận:
  - latency tăng mạnh khi traffic tăng;
  - CPU không quá cao nhưng request queue dài;
  - đôi lúc application restart làm mất một số state cache tạm;
  - khi HR API chậm, nhiều request bị treo lâu;
  - test environment chạy ổn nhưng production scale-out xuất hiện inconsistency.

Developer đã chuyển class cũ thành service sau:

## Đoạn code cần review

```csharp
public sealed class EmployeeDirectoryService
{
    private static readonly Dictionary<string, EmployeeDto> Cache = new();
    private static string? _token;

    private readonly IConfiguration _configuration;

    public EmployeeDirectoryService(IConfiguration configuration)
    {
        _configuration = configuration;
    }

    public EmployeeDto GetEmployee(string employeeId)
    {
        if (Cache.TryGetValue(employeeId, out var cached))
            return cached;

        var baseUrl = _configuration["HrApi:BaseUrl"];
        var clientId = _configuration["HrApi:ClientId"];
        var clientSecret = _configuration["HrApi:ClientSecret"];

        if (_token == null)
        {
            using var authClient = new HttpClient();

            var tokenResponse = authClient.PostAsJsonAsync(
                $"{baseUrl}/oauth/token",
                new { clientId, clientSecret })
                .Result;

            _token = tokenResponse.Content
                .ReadFromJsonAsync<TokenResponse>()
                .Result!
                .AccessToken;
        }

        using var client = new HttpClient();
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", _token);

        var response = client
            .GetAsync($"{baseUrl}/employees/{employeeId}")
            .Result;

        response.EnsureSuccessStatusCode();

        var employee = response.Content
            .ReadFromJsonAsync<EmployeeDto>()
            .Result!;

        Cache[employeeId] = employee;
        return employee;
    }
}
```

Service được đăng ký:

```csharp
builder.Services.AddSingleton<EmployeeDirectoryService>();
```

Controller gọi trực tiếp:

```csharp

{
```

## Kết quả code review tham khảo

### Critical — `Dictionary` static bị truy cập concurrent mà không synchronization

**Vấn đề:**  
`Cache` là `Dictionary<string, EmployeeDto>` static và được đọc/ghi bởi nhiều request thread.

**Tại sao xảy ra:**  
`Dictionary<TKey,TValue>` không cung cấp thread-safety cho concurrent writes/reads khi collection đang mutate.

**Ảnh hưởng production:**  
Dưới concurrency có thể xảy ra race, exception hoặc state không đáng tin cậy. Bug có thể khó tái hiện ở test traffic thấp nhưng xuất hiện khi production load tăng.

**Cách sửa:**  
Nếu cache thực sự cần thiết, dùng abstraction phù hợp như `IMemoryCache` cho per-instance cache hoặc một thread-safe structure với lifecycle/expiration rõ ràng. Không giữ static mutable cache chỉ để preserve legacy behavior.

---

### High — Sync-over-async bằng `.Result` làm block request thread

**Vấn đề:**  
Các network I/O dùng `PostAsJsonAsync`, `GetAsync`, `ReadFromJsonAsync` nhưng ngay lập tức `.Result`.

**Tại sao xảy ra:**  
Async operation giải phóng thread trong lúc chờ I/O; `.Result` biến flow thành blocking wait.

**Ảnh hưởng production:**  
Trong ASP.NET Core, classic `SynchronizationContext` deadlock pattern của ASP.NET cũ không phải vấn đề chính, nhưng blocking nhiều request vẫn có thể làm ThreadPool thiếu worker, tăng queueing và latency dưới load.

**Cách sửa:**  
Chuyển toàn bộ call chain sang `async Task<T>` và `await` từ service tới controller.

---

### High — Tạo `HttpClient` mới cho từng call

**Vấn đề:**  
Mỗi auth request và employee request đều tạo `new HttpClient()`.

**Tại sao xảy ra:**  
Legacy pattern được giữ nguyên mà không sử dụng HTTP client lifecycle management của ASP.NET Core.

**Ảnh hưởng production:**  
Có thể làm connection reuse kém, tăng socket/connection churn và giảm hiệu quả dưới tải.

**Cách sửa:**  
Dùng `IHttpClientFactory` hoặc typed client. Cấu hình base address, timeout, default headers và resilience policy ở client boundary thay vì rải trong business method.

---

### High — Token cache không có expiration hoặc refresh semantics

**Vấn đề:**  
`_token` chỉ được lấy một lần khi null.

**Tại sao xảy ra:**  
Không lưu expiry, không refresh trước expiration, không xử lý 401/revocation.

**Ảnh hưởng production:**  
Sau khi token hết hạn, mọi call có thể tiếp tục dùng token cũ và fail cho tới khi process restart hoặc có code reset token.

**Cách sửa:**  
Tách `IAccessTokenProvider`; lưu token cùng expiration; refresh trước expiry; xử lý concurrent refresh để tránh stampede. Nếu 401 xảy ra, invalidate token một cách kiểm soát và retry tối đa theo policy an toàn.

---

### High — Token initialization có race condition

**Vấn đề:**  
Nhiều request đầu tiên có thể cùng thấy `_token == null` rồi đồng thời gọi auth endpoint.

**Tại sao xảy ra:**  
Check-then-act trên shared state không atomic.

**Ảnh hưởng production:**  
Auth service bị burst request không cần thiết; nếu token issuance có rate limit, migration có thể gây failure ngay khi app scale/restart.

**Cách sửa:**  
Serialize refresh bằng `SemaphoreSlim` hoặc token-provider pattern có single-flight behavior.

---

### High — Cache semantics sai khi scale-out

**Vấn đề:**  
Static cache chỉ tồn tại trong một process.

**Tại sao xảy ra:**  
Mỗi App Service instance có memory riêng.

**Ảnh hưởng production:**  
4 instances có thể chứa 4 version khác nhau của employee data; restart một instance làm cache mất; behavior phụ thuộc load balancer route.

**Cách sửa:**  
Trước tiên xác định requirement freshness. Nếu vài phút stale chấp nhận được, per-instance `IMemoryCache` với TTL có thể đủ. Nếu cần cross-instance consistency, xem xét distributed cache hoặc bỏ cache. Không thêm Redis chỉ vì scale-out nếu requirement không cần.

---

### High — Không có timeout/cancellation boundary rõ ràng

**Vấn đề:**  
Service không nhận `CancellationToken`; controller cũng sync.

**Tại sao xảy ra:**  
Legacy method signature được giữ nguyên.

**Ảnh hưởng production:**  
Client disconnect hoặc upstream timeout nhưng server có thể vẫn chờ HR API. Khi dependency chậm hàng loạt, request giữ resource lâu và latency chain tăng.

**Cách sửa:**  
Propagate `CancellationToken` từ controller xuống `HttpClient.SendAsync`; cấu hình timeout hợp lý theo SLO và dependency characteristics.

---

### High — Không validate configuration và secret handling không rõ ràng

**Vấn đề:**  
`baseUrl`, `clientId`, `clientSecret` được đọc mỗi call và có thể null. `clientSecret` nằm trong generic configuration surface.

**Tại sao xảy ra:**  
Migration giữ nguyên kiểu string lookup thay vì typed options + validation.

**Ảnh hưởng production:**  
Sai config chỉ fail khi request thật chạy; secret governance khó kiểm soát.

**Cách sửa:**  
Dùng typed `IOptions<HrApiOptions>` với startup validation. Ở Azure, ưu tiên secret store/Managed Identity khi integration hỗ trợ; nếu third-party buộc client secret thì lấy từ secure configuration source như Key Vault integration, không hard-code hoặc log.

---

### Medium — Cache không có TTL/invalidation

**Vấn đề:**  
Employee đã cache thì tồn tại cho tới khi process restart.

**Tại sao xảy ra:**  
Không có expiration policy.

**Ảnh hưởng production:**  
User có thể thấy department/title/manager cũ trong thời gian không xác định.

**Cách sửa:**  
Định nghĩa freshness requirement rồi dùng absolute/sliding expiration phù hợp. Nếu source có event/change feed thì có thể invalidate chủ động, nhưng không cần phức tạp nếu TTL đủ.

---

### Medium — Không encode route segment

**Vấn đề:**  
`employeeId` được nối trực tiếp vào URL string.

**Tại sao xảy ra:**  
Code giả định ID luôn là safe path segment.

**Ảnh hưởng production:**  
ID có ký tự đặc biệt có thể tạo request sai hoặc ambiguity.

**Cách sửa:**  
Dùng URI construction/escaping phù hợp hoặc API client abstraction quản lý path parameter.

---

### Medium — Error handling không phân biệt dependency failure

**Vấn đề:**  
`EnsureSuccessStatusCode()` ném exception chung và controller không map failure semantics.

**Tại sao xảy ra:**  
Business service phụ thuộc trực tiếp low-level HTTP behavior.

**Ảnh hưởng production:**  
404, 401, 429, timeout và 500 có thể bị xử lý giống nhau; observability và client behavior kém.

**Cách sửa:**  
Map external API result sang typed outcome/domain-specific exception hoặc result; retry chỉ cho transient case phù hợp; không retry mọi lỗi.

## Phiên bản đề xuất

```csharp
public sealed class HrApiOptions
{
    public required Uri BaseUrl { get; init; }
    public required string ClientId { get; init; }
}

public sealed class EmployeeDirectoryClient
{
    private readonly HttpClient _httpClient;
    private readonly IAccessTokenProvider _tokenProvider;
    private readonly IMemoryCache _cache;

    public EmployeeDirectoryClient(
        HttpClient httpClient,
        IAccessTokenProvider tokenProvider,
        IMemoryCache cache)
    {
        _httpClient = httpClient;
        _tokenProvider = tokenProvider;
        _cache = cache;
    }

    public async Task<EmployeeDto?> GetEmployeeAsync(
        string employeeId,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"employee:{employeeId}";

        if (_cache.TryGetValue(cacheKey, out EmployeeDto? cached))
            return cached;

        var token = await _tokenProvider.GetTokenAsync(cancellationToken);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"employees/{Uri.EscapeDataString(employeeId)}");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();

        var employee = await response.Content
            .ReadFromJsonAsync<EmployeeDto>(cancellationToken: cancellationToken);

        if (employee is null)
            throw new InvalidOperationException("HR API returned an empty payload.");

        _cache.Set(
            cacheKey,
            employee,
            TimeSpan.FromMinutes(5));

        return employee;
    }
}
```

```csharp
{
```

`IAccessTokenProvider` nên chịu trách nhiệm token caching, expiration và concurrent refresh. Không nhất thiết cần distributed token cache nếu mỗi instance có thể tự lấy token với chi phí hợp lý.

## Giải thích thiết kế sau khi sửa

### 1. Async all the way

Network wait không block request thread. Điều này không làm dependency nhanh hơn, nhưng giúp application sử dụng ThreadPool hiệu quả hơn dưới concurrent I/O.

### 2. HTTP client có lifecycle rõ ràng

Typed client gom base URL, timeout, telemetry và resilience ở integration boundary.

### 3. Cache là optimization có explicit policy

`IMemoryCache` thể hiện rõ đây là per-instance optimization với TTL. Nếu business cần cross-instance consistency, architecture mới cần thay đổi.

### 4. Token lifecycle tách khỏi business method

Token acquisition không làm method `GetEmployeeAsync` gánh auth concurrency/expiry logic.

### 5. Migration incremental

Không cần rewrite domain architecture trước khi fix runtime behavior. Có thể migrate theo thứ tự:

1. thêm characterization/integration tests cho legacy behavior;
2. chuyển HTTP calls sang async + typed client;
3. tách token provider;
4. thay static cache;
5. thêm telemetry;
6. rollout canary/slot;
7. sau khi behavior ổn mới refactor sâu hơn.

## Trade-offs

- `IMemoryCache` đơn giản nhưng mỗi instance có cache khác nhau.
- Distributed cache tăng consistency nhưng thêm network dependency và invalidation complexity.
- Typed client tạo abstraction tốt hơn nhưng không nên bọc mọi `HttpClient` call bằng nhiều layer không cần thiết.
- Retry có thể hữu ích với transient network failure nhưng phải kết hợp timeout/backoff và không retry 401/validation blindly.
- Giữ migration incremental giảm blast radius nhưng có thể tạm thời tồn tại hybrid architecture.

## Cách kiểm thử

1. **Load test:** 300–500 concurrent requests, so sánh ThreadPool queue/latency giữa `.Result` version và async version.
2. **Concurrency test:** nhiều request cùng cache miss một employee ID; đảm bảo cache/token provider không race nghiêm trọng.
3. **Failure-path integration test:** HR API timeout/500/429/401 và xác minh mapping/retry policy.
4. **Scale-out validation:** chạy nhiều instances, kiểm tra per-instance cache behavior đúng với freshness requirement.
5. **Migration regression test:** cùng input representative phải giữ business output tương thích với legacy system, trừ behavior được chủ động thay đổi.

## Quan sát trong production

Theo dõi:

- request rate, p50/p95/p99;
- ThreadPool queue length/starvation indicators;
- HR API dependency duration/failure rate;
- HTTP timeout count;
- token acquisition count/failure rate;
- cache hit ratio;
- 401/429/5xx từ HR API;
- process memory và restart count;
- App Service instance-specific latency để phát hiện skew;
- rollout regression theo release version.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào `IMemoryCache` đủ tốt và khi nào bạn thực sự cần Redis cho employee directory?
2. Nếu HR API không hỗ trợ idempotency nhưng endpoint này chỉ là GET, retry policy nên khác write operation như thế nào?
3. Nếu migration bắt buộc giữ compatibility với một client cũ đang phụ thuộc exact error code, bạn sẽ rollout thay đổi error mapping ra sao?

### Critical — Production secret bị bake vào artifact

**Vấn đề:**  
Build step append `PARTNER_API_SECRET` vào `appsettings.Production.json` trước khi zip package.

**Tại sao xảy ra:**  
Secret injection bị thực hiện ở CI artifact creation thay vì deployment/runtime configuration boundary.

**Ảnh hưởng production:**  
Secret tồn tại trong artifact storage, có thể xuất hiện trong logs/cache, và package không còn environment-neutral. Nếu artifact được tải xuống hoặc promote sai environment, secret exposure tăng.

**Cách sửa:**  
Artifact không chứa secret. Inject secret qua Octopus sensitive variables, environment variable, Key Vault integration hoặc runtime secret provider phù hợp. CI chỉ build code/config template không có secret.

---

### Critical — Secret được khai báo trực tiếp trong pipeline parameter

**Vấn đề:**  
`PARTNER_API_SECRET: "production-secret-value"` thể hiện secret như plain configuration.

**Tại sao xảy ra:**  
Không dùng secret/sensitive variable store.

**Ảnh hưởng production:**  
Secret có nguy cơ lộ qua source control, build configuration export hoặc logs.

**Cách sửa:**  
Dùng TeamCity password parameter/credential storage hoặc external secret store; đảm bảo masking nhưng không coi masking là security boundary duy nhất.

---

### High — Artifact không có immutable version/commit identity

**Vấn đề:**  
Version là `latest`, package tên cố định `commerce-api.zip`.

**Tại sao xảy ra:**  
Release pipeline không gắn artifact với immutable build number/commit SHA.

**Ảnh hưởng production:**  
Khó chứng minh Production đang chạy commit nào; rollback có thể chọn nhầm package “previous” có cùng tên.

**Cách sửa:**  
Package có immutable version, ví dụ `commerce-api.2026.09.07.123.zip` hoặc semantic version/build number; release metadata lưu commit SHA, build ID và artifact hash.

---

### High — “Build once, promote” bị phá nếu mutate config trong package

**Vấn đề:**  
Đề xuất sửa `appsettings.Production.json` trước mỗi environment deploy làm package khác nhau theo environment.

**Tại sao xảy ra:**  
Configuration và artifact bị trộn.

**Ảnh hưởng production:**  
UAT không còn test chính binary/package sẽ chạy ở Production. Reproducibility và audit giảm.

**Cách sửa:**  
Giữ package immutable. Inject environment-specific values ngoài package qua deployment variables/environment variables/runtime config.

---

### High — Database migration chạy sau khi application đã start

**Vấn đề:**  
Pipeline deploy app → start app → mới migration.

**Tại sao xảy ra:**  
Schema change bị coi như post-deploy maintenance step.

**Ảnh hưởng production:**  
App mới có thể nhận traffic khi schema cũ chưa compatible, gây runtime exception hoặc write sai.

**Cách sửa:**  
Thiết kế migration ordering theo compatibility. Với zero-downtime, ưu tiên expand/contract migration: deploy additive backward-compatible schema trước, rồi deploy app, sau đó cleanup ở release sau.

---

### High — Rollback chỉ rollback binary, không xử lý schema compatibility

**Vấn đề:**  
Rollback chỉ redeploy previous package.

**Tại sao xảy ra:**  
Giả định application rollback độc lập với database.

**Ảnh hưởng production:**  
Nếu schema đã destructive/irreversible, binary cũ có thể không chạy được trên schema mới.

**Cách sửa:**  
Thiết kế migration backward-compatible để binary N và N-1 có overlap compatibility trong rollout window. Với migration irreversible, rollback plan phải là forward-fix hoặc restore/recovery procedure rõ ràng, không giả vờ binary rollback là đủ.

---

### High — Health gate quá yếu

**Vấn đề:**  
Chỉ smoke test `/health` sau toàn bộ deploy.

**Tại sao xảy ra:**  
Health endpoint có thể chỉ chứng minh process up, không chứng minh critical integration hoạt động.

**Ảnh hưởng production:**  
Release có thể được coi thành công dù Partner API auth/config hoặc database path sai.

**Cách sửa:**  
Có deployment validation theo risk: readiness/health + một số synthetic/smoke test critical path, kiểm tra config binding và dependency telemetry. Không gọi destructive business flow trong smoke test nếu không kiểm soát được.

---

### High — Multi-node rollout không thể hiện deployment strategy

**Vấn đề:**  
Pipeline chỉ nói “Deploy application package”, không nói rolling/batched/slot strategy.

**Tại sao xảy ra:**  
Release process thiếu capacity/traffic-management semantics.

**Ảnh hưởng production:**  
Có thể xảy ra mixed version trong vài phút mà schema/config không tương thích; hoặc tất cả node bị restart cùng lúc.

**Cách sửa:**  
Định nghĩa rolling/batch/slot deployment với health gate giữa các step. Đảm bảo N và N+1 coexistence được hỗ trợ khi rollout không atomic.

---

### Medium — Build output chưa thể hiện deterministic dependency lock

**Vấn đề:**  
Pipeline chỉ restore/build mà không thể hiện package-lock/version pinning policy.

**Tại sao xảy ra:**  
Build reproducibility phụ thuộc dependency declaration hiện có.

**Ảnh hưởng production:**  
Nếu dependency range hoặc external feed mutable, hai build từ cùng commit có thể khác nhau.

**Cách sửa:**  
Dùng lock/versioning strategy phù hợp cho NuGet dependencies và lưu artifact hash. Không cần rebuild khi promote environment.

---

### Medium — Thiếu release provenance/audit metadata

**Vấn đề:**  
Không thấy commit SHA, build ID, approver, migration version, artifact checksum.

**Tại sao xảy ra:**  
Release được xem như copy package thay vì audited change.

**Ảnh hưởng production:**  
Incident investigation và rollback decision chậm.

**Cách sửa:**  
Mỗi release record nên trace được source commit → CI build → artifact checksum → deployment environment → approver → migration version → rollout result.

## Phiên bản đề xuất

Pseudo-flow tối giản hơn:

```yaml
teamcity:
  build:
    version: "${BUILD_NUMBER}"
    steps:
      - run: dotnet restore src/Commerce.Integration.sln
      - run: dotnet test src/Commerce.Integration.sln --no-restore
      - run: dotnet publish src/Api/Api.csproj -c Release -o out --no-restore
      - run: zip -r "commerce-api.${BUILD_NUMBER}.zip" out
      - run: sha256sum "commerce-api.${BUILD_NUMBER}.zip"

    artifacts:
      - "commerce-api.${BUILD_NUMBER}.zip"
      - "commerce-api.${BUILD_NUMBER}.zip.sha256"

    metadata:
      commit_sha: "${GIT_COMMIT}"

octopus:
  release:
    package: "commerce-api.${BUILD_NUMBER}.zip"

    variables:
      PartnerApi__BaseUrl: environment-scoped
      PartnerApi__ClientSecret: sensitive-variable-or-secret-store

    deploy_process:
      - step: Validate release metadata and artifact checksum
      - step: Apply backward-compatible database migration
      - step: Deploy application to first batch / slot
      - step: Readiness and critical-path smoke validation
      - step: Promote traffic / continue rolling deployment
      - step: Validate application and dependency telemetry
      - step: Mark release successful
```

Database process có thể tách migration package/job riêng nếu team cần ownership rõ hơn. Điều quan trọng là migration version cũng phải traceable tới release và không tự động assume down-migration sẽ an toàn.

## Giải thích thiết kế sau khi sửa

### 1. Build once

CI tạo một immutable artifact duy nhất. Development, UAT và Production promote đúng artifact đó.

### 2. Config outside artifact

Base URL, connection string và secret được inject theo environment ở deploy/runtime. UAT test cùng code package với Production nhưng dùng config khác có chủ đích.

### 3. Release traceability

Build number + commit SHA + artifact hash cho phép chứng minh chính xác code nào đã chạy.

### 4. Database compatibility là phần của deployment design

Migration không phải một script phụ. Nó ảnh hưởng coexistence giữa old/new app và rollback.

### 5. Progressive rollout

Health gate giữa batches/slot giảm blast radius. Không nhất thiết cần Kubernetes/canary platform phức tạp nếu Octopus + deployment slots/batches đã đủ.

## Trade-offs

- Immutable versioning làm artifact storage tăng, cần retention policy.
- Expand/contract migration có thể yêu cầu 2 release thay vì 1 nhưng đổi lại rollback/coexistence an toàn hơn.
- Progressive rollout chậm hơn deploy all-at-once nhưng giảm blast radius.
- External secret store tăng dependency quản trị; sensitive deployment variables có thể đủ với hệ thống nhỏ nếu governance tốt.
- Smoke test càng sâu càng tăng confidence nhưng cũng tăng deployment time và risk của test side effect.

## Cách kiểm thử

1. **Artifact provenance test:** cùng release promoted từ UAT sang Production phải có cùng artifact hash.
2. **Secret leakage test:** scan artifact và CI logs; không được chứa production secret plaintext.
3. **Migration compatibility test:** chạy app version N và N+1 cùng lúc trên schema migration mới; critical paths vẫn hoạt động.
4. **Rollback rehearsal:** deploy N+1 rồi rollback app về N trong staging-like environment; xác minh schema vẫn compatible.
5. **Deployment failure test:** fail smoke test ở first batch/slot; pipeline phải dừng promotion thay vì tiếp tục toàn bộ nodes.

## Quan sát trong production

Mỗi release nên lưu/quan sát:

- release version;
- commit SHA;
- CI build ID;
- artifact checksum;
- migration version;
- deployment start/end time;
- approver/change ticket nếu process yêu cầu;
- node/slot version;
- health/readiness result;
- p95/p99 latency;
- 5xx rate;
- dependency failures;
- config validation errors;
- rollback/forward-fix event;
- release annotations trong Application Insights/monitoring dashboard.

## Câu hỏi phỏng vấn mở rộng

1. Nếu migration phải drop một column được version N đang đọc, bạn sẽ chia release thành các phase thế nào?
2. Khi nào bạn chọn deployment slot swap thay vì rolling deployment từng node?
3. Nếu Production cần hotfix gấp nhưng UAT pipeline đang fail do test không liên quan, bạn sẽ giữ release governance thế nào mà vẫn xử lý incident nhanh?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Migration từ .NET Framework sang modern .NET không chỉ là đổi target framework; cần review lại runtime assumptions như sync-over-async, static state, HTTP client lifecycle, configuration và scale-out behavior.
- `.Result` có thể không gây classic ASP.NET deadlock nhưng vẫn làm giảm khả năng scale khi I/O concurrency tăng.
- `HttpClient` nên có lifecycle được quản lý và integration boundary rõ ràng.
- Cache per-process, distributed cache và source-of-truth consistency là ba khái niệm khác nhau.
- CI/CD an toàn cần **immutable artifact + environment-scoped config + secret isolation + release provenance + schema compatibility**.
- Rollback binary không đồng nghĩa rollback toàn hệ thống nếu database đã thay đổi.
- Database migration cần được thiết kế cùng rollout, coexistence và recovery strategy.

## Mẫu tư duy cần nhớ

1. **Modernize behavior before modernizing architecture.**
2. **Async I/O only helps scalability when the call chain stays async.**
3. **Build once; inject environment configuration later.**
4. **Design schema changes for coexistence, not only for the final state.**
5. **A rollback plan is valid only if every changed state remains compatible or recoverable.**
