# Câu 1 — Memory tăng theo traffic nhưng không “leak” rõ ràng: GC, LOH và allocation pressure đang làm gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, Garbage Collector, generations, LOH, allocation, object lifetime, ASP.NET Core, profiling, production verification

## Bối cảnh

Một ASP.NET Core API xử lý import dữ liệu CSV và trả về báo cáo JSON. Service chạy nhiều instance trên Azure App Service. Trong giờ cao điểm:

- memory của process tăng từ khoảng 700 MB lên 2.5–3 GB;
- CPU tăng vừa phải nhưng đôi lúc latency p99 nhảy mạnh;
- sau khi traffic giảm, memory không lập tức quay về mức ban đầu;
- không có bằng chứng rõ ràng rằng số object sống tăng mãi qua nhiều giờ;
- endpoint import tạo nhiều `byte[]`, `string`, DTO và một vài buffer lớn;
- team đề xuất gọi `GC.Collect()` sau mỗi import vì “GC không dọn đủ nhanh”.

Một developer khác kết luận đây chắc chắn là memory leak chỉ vì working set không giảm ngay sau traffic.

## Câu hỏi chính

Hãy giải thích internal behavior của managed allocation, GC generations, object lifetime và LOH đủ để lý giải vì sao working set có thể tăng mà chưa chứng minh được memory leak. Bạn sẽ thu thập evidence nào để phân biệt allocation pressure, retained objects, LOH pressure và native/unmanaged memory; và trong trường hợp nào việc gọi `GC.Collect()` thủ công có thể làm latency tệ hơn?

## Câu hỏi làm rõ nên cân nhắc

1. Memory metric đang nhìn là managed heap size, process private bytes hay working set?
2. Sau mỗi chu kỳ traffic, số object sống và managed heap sau GC có tiếp tục tăng qua nhiều chu kỳ hay ổn định?
3. Kích thước và lifetime của các `byte[]`/buffer lớn là bao nhiêu, có pooling hay giữ reference trong cache/static collection không?
4. Endpoint có dùng library native, stream, compression hoặc resource cần `Dispose` không?
5. p99 spike có tương quan với GC pause, allocation rate hay import concurrency không?

## Gợi ý tư duy

### Gợi ý 1

Đừng dùng một process-memory graph để suy ra trực tiếp “managed memory leak”. Phân biệt memory được cấp cho process, managed heap và object thực sự còn reachable.

### Gợi ý 2

GC tối ưu theo generations và object lifetime; allocation rate, promotion và object lớn có thể làm cost thay đổi đáng kể ngay cả khi cuối cùng object vẫn collectible.

### Gợi ý 3

So sánh allocation rate, heap size sau GC, generation/LOH size, GC pause và object-retention path. Nếu managed heap không giải thích process memory, mở rộng điều tra sang native memory/resource.

## Cấu trúc trả lời đề xuất

1. Làm rõ metric và symptom thực sự.
2. Giải thích allocation + generational GC ở mức runtime behavior.
3. Phân biệt reachable/retained object với memory process chưa trả ngay cho OS.
4. Xác minh LOH/buffer allocation và promotion behavior.
5. Thu runtime counters, trace/profile và heap snapshot ở các thời điểm có kiểm soát.
6. So sánh competing hypotheses: high allocation, retention, cache, native memory, resource leak.
7. Sửa nguyên nhân có evidence thay vì ép GC.
8. Load-test lại với concurrency thực tế.
9. Theo dõi p95/p99, allocation rate, GC pause, heap size và process memory.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Working set/private memory không đồng nghĩa trực tiếp với số managed objects còn sống.
- GC dựa trên reachability và generations; object sống lâu có thể được promoted, còn object ngắn hạn thường được thu gom ở generation trẻ.
- Allocation pressure có thể gây nhiều GC và latency dù không có leak lâu dài.
- Object/buffer lớn cần được xem riêng vì có thể tạo áp lực lên LOH và memory footprint.
- Phải dùng counters/profile/heap evidence để xác định object type nào đang allocate và type nào đang retained.
- `GC.Collect()` trong request path không phải default fix; forced collection có thể tạo pause/cost và che nguyên nhân thực.

### Điểm cộng

- Phân biệt allocation rate với retained size.
- So sánh heap snapshot sau các full GC ở các thời điểm tương đương thay vì so snapshot ngẫu nhiên.
- Kiểm tra static references, caches không bounded, event subscriptions, queues và long-lived collections khi retained objects tăng.
- Xem xét streaming thay vì materialize toàn bộ file/report, giảm temporary allocations và dùng pooling khi profiling chứng minh lợi ích.
- Kiểm tra `IDisposable`/native handles khi managed heap không giải thích process footprint.

### Senior+

- Nhận ra optimization phải cân bằng throughput, pause time và memory headroom thay vì chỉ “giảm MB”.
- Đề xuất giới hạn import concurrency/bounded work để tránh nhiều request đồng thời nhân allocation peak.
- Phân biệt symptom của memory leak thực sự với high-water mark và runtime/process memory management; yêu cầu evidence theo thời gian.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng `GC.Collect()`. Trước hết cần xác định graph đang hiển thị metric nào. Nếu working set tăng nhưng managed heap sau các GC ổn định, kết luận “managed leak” là quá sớm. Ngược lại, nếu live managed heap và số instance của một số type tăng qua nhiều chu kỳ tương đương, cần tìm retention path.

Ở endpoint import, tôi sẽ đo allocation rate, GC count/pause, generation sizes và LOH, sau đó capture trace/heap profile khi load thấp và khi peak. Các buffer lớn, `string` trung gian, materialized DTO collections và serialization buffers là ứng viên allocation pressure. Tôi cũng kiểm tra xem cache/static collection/event handler/background queue có giữ object lâu hơn dự kiến hay không.

Nếu report được xây hoàn toàn trong memory, một cải tiến có thể là streaming pipeline: đọc file theo chunk/record, tránh copy không cần thiết và stream output khi contract cho phép. Nếu buffer có lifecycle rõ ràng và profiling cho thấy allocation cost đáng kể, pooling có thể hữu ích, nhưng pooling cũng làm ownership phức tạp và phải tránh dùng buffer sau khi trả pool.

Nếu managed heap không giải thích phần lớn process memory, tôi kiểm tra native allocations, compression/native libraries, handles và resource disposal. Tôi cũng correlate p99 với GC pause và import concurrency để tránh nhầm downstream latency với GC.

`GC.Collect()` chỉ nên được cân nhắc trong các trường hợp rất đặc thù khi application thực sự biết một pha allocation lớn vừa kết thúc và hiểu cost; nó không nên được gọi sau mỗi request như cơ chế cleanup. Fix chính phải dựa trên nguyên nhân: giảm allocation, bỏ retention ngoài ý muốn, giới hạn concurrency, dispose resource hoặc thay đổi processing model.

Sau khi sửa, tôi chạy load test có distribution file size và concurrency gần production, so sánh throughput, p95/p99, allocation rate, heap-after-GC, LOH và process memory qua nhiều chu kỳ traffic.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak chỉ vì working set không giảm ngay. Tôi cần tách process memory khỏi managed heap và đặc biệt nhìn live heap sau GC qua nhiều chu kỳ tương đương. Nếu live object graph tăng liên tục thì tôi tìm retention path; nếu live heap ổn định nhưng allocation rate rất cao thì vấn đề có thể là GC pressure chứ không phải leak.

Với endpoint import, tôi sẽ profile `byte[]`, `string`, DTO và buffer lớn, correlate allocation/LOH/GC pause với p99. Tôi cũng kiểm tra cache, static collections, event subscriptions và native resources. Nếu code materialize toàn bộ input/output, streaming hoặc giảm copy có thể tốt hơn; nếu concurrency làm nhiều import cùng peak memory thì cần bounded concurrency.

Tôi không dùng `GC.Collect()` sau mỗi request vì forced collection có thể tăng pause và không sửa retention hay allocation design. Tôi muốn chứng minh loại object nào allocate, loại nào còn sống và vì sao trước khi tối ưu.”

## Câu hỏi đào sâu

1. Nếu heap snapshot cho thấy phần lớn `byte[]` đã collectible nhưng process memory vẫn cao, bạn điều tra tiếp theo hướng nào?
2. Nếu pooling giảm allocation nhưng tạo bug data corruption hiếm gặp, bạn nghi ngờ ownership/lifetime issue nào?
3. Tôi đề xuất tăng memory limit thay vì sửa code vì rẻ hơn engineering time; bạn cần dữ liệu nào để chấp nhận hoặc phản đối?

## Lỗi trả lời thường gặp

- Đồng nhất working set với managed heap.
- Kết luận memory leak từ một snapshot duy nhất.
- Gọi `GC.Collect()` như cleanup API sau mỗi request.
- Tối ưu bằng pooling/`Span<T>` trước khi có allocation profile.
- Chỉ nhìn average latency mà bỏ qua GC pause và p99 dưới concurrency.

## Thang điểm 0–10

- **0–2:** Chỉ nói “GC tự dọn memory” hoặc “gọi GC.Collect”.
- **3–4:** Biết generations/LOH nhưng không gắn với evidence production.
- **5–6:** Phân biệt allocation và retention, biết dùng counters/profile/heap snapshot.
- **7–8:** Có competing hypotheses, native-memory branch, load verification và trade-offs.
- **9–10:** Kết nối runtime mechanism → measurable evidence → workload design → safe optimization → production verification rất rõ ràng.

# Câu 2 — Optimizely publish thành công nhưng người dùng vẫn thấy nội dung cũ: CMS, Akamai hay application cache?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS caching, Akamai/CDN, HTTP caching, ASP.NET Core, distributed systems, observability, incident investigation, cache invalidation

## Bối cảnh

Một marketing website dùng Optimizely CMS và ASP.NET Core, chạy nhiều application instances phía sau Akamai. Editors publish thay đổi cho một campaign page lúc 09:00. Khoảng 30% người dùng vẫn thấy nội dung cũ trong 20–40 phút, nhưng một số người thấy nội dung mới ngay.

Thông tin ban đầu:

- CMS UI báo publish thành công;
- origin đôi lúc trả nội dung mới, đôi lúc team chưa chắc request đang vào instance nào;
- Akamai đang cache một số HTML responses;
- application có in-memory cache cho một vài content projections;
- browser cũng nhận `Cache-Control` headers;
- team chưa có correlation giữa content version, application instance và CDN cache status;
- business muốn cập nhật campaign khẩn cấp nhưng không muốn purge toàn site nếu không cần thiết.

Một developer muốn restart toàn bộ App Service. Người khác muốn purge toàn bộ CDN. Chưa có evidence chứng minh cache layer nào giữ stale content.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo trình tự nào để giảm impact nhưng vẫn xác định đúng cache layer gây stale content? Hãy đưa ra competing hypotheses cho CMS/application/CDN/browser, evidence cần thu, cách khôi phục ngắn hạn, root-cause verification và thiết kế invalidation/observability để tránh tái diễn.

## Câu hỏi làm rõ nên cân nhắc

1. Requirement về freshness sau publish là bao lâu và page nào thực sự cần gần-real-time invalidation?
2. Origin bypass CDN có trả cùng content version trên tất cả instances không?
3. Response headers hiện có `Cache-Control`, `Age`, `ETag` hoặc CDN-specific cache diagnostics nào?
4. Application cache key có chứa content/version/language/site/variant cần thiết không, và invalidation event có đến mọi instance không?
5. Akamai cache key/purge strategy cho HTML page này là gì, có variation theo host/query/cookie/header không?

## Gợi ý tư duy

### Gợi ý 1

Có nhiều cache layer nối tiếp nhau. Hãy tìm layer đầu tiên mà content version bắt đầu sai thay vì purge/restart tất cả.

### Gợi ý 2

Trong multi-instance environment, in-memory invalidation chỉ ở một process có thể tạo symptom “lúc mới, lúc cũ”. CDN có thể khuếch đại một response stale thành nhiều user requests.

### Gợi ý 3

Dùng request path có kiểm soát: CMS/source → từng origin instance → CDN edge → browser. Gắn content version và cache diagnostics để chứng minh layer nào đang phục vụ bản nào.

## Cấu trúc trả lời đề xuất

1. Xác định business impact và freshness SLO của campaign.
2. Freeze các thay đổi cache/publish không cần thiết để giữ evidence.
3. So sánh source content version với origin bypass CDN.
4. Kiểm tra từng instance/application cache nếu origin không nhất quán.
5. Nếu origin đúng, kiểm tra CDN cache key, age/status và targeted invalidation.
6. Nếu CDN đúng, kiểm tra browser caching/client behavior.
7. Stabilize bằng targeted purge/bypass/TTL adjustment phù hợp evidence.
8. Verify từ nhiều request paths/locations.
9. Sửa invalidation design và cache-key/version contract.
10. Thêm telemetry/alerts và failure-path tests.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không purge toàn site hoặc restart toàn cluster trước khi xác định layer.
- Phải phân biệt CMS source state, application cache, CDN cache và browser cache.
- Multi-instance application làm local in-memory invalidation trở thành một giả thuyết quan trọng.
- Cache headers và cache key semantics là một phần của behavior, không chỉ infrastructure detail.
- Recovery phải verify end-to-end rằng user nhận đúng content version.

### Điểm cộng

- Thêm `contentVersion`/publish timestamp vào structured logs hoặc diagnostic response có kiểm soát.
- Correlate instance ID, CDN cache status/age, request ID và content identifier.
- Dùng targeted purge theo URL/surrogate grouping/tagging nếu platform/configuration hỗ trợ và được thiết kế trước, thay vì blanket purge.
- Xác định rõ page nào được phép stale và page nào cần event-driven invalidation hoặc TTL ngắn.
- Kiểm tra cache key có thiếu language, site, authentication state hoặc variant dimension.

### Senior+

- Nhận ra invalidation là distributed consistency problem: publish thành công ở source không tự đảm bảo mọi cache layer đồng thời cập nhật.
- Thiết kế degradation/failure behavior khi purge API hoặc invalidation event thất bại.
- Đặt freshness SLO và đo publish-to-visible latency thay vì chỉ monitor HTTP availability.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng impact: campaign nào, traffic bao nhiêu, freshness requirement là gì. Sau đó tôi tạo một chuỗi kiểm tra từ source ra ngoài. Đầu tiên xác nhận published content/version ở CMS. Tiếp theo bypass CDN và gọi origin có cách phân biệt từng instance. Nếu các instances trả khác version, CDN chưa phải root cause đầu tiên; tôi điều tra application cache key và cơ chế invalidation giữa instances.

Nếu tất cả origin instances đều trả bản mới, tôi kiểm tra CDN response headers/diagnostics, cache key và age. Nếu edge đang giữ object cũ vượt freshness requirement, targeted purge hoặc tạm bypass cache cho đúng URL có thể là stabilization phù hợp hơn purge toàn site. Nếu CDN trả bản mới nhưng một browser vẫn cũ, tôi kiểm tra browser cache headers/revalidation behavior.

Tôi không restart toàn App Service chỉ để “xóa cache” vì hành động đó có thể mất evidence, gây cold-start impact và không sửa CDN/browser stale state. Tương tự, purge toàn CDN có blast radius lớn và có thể tạo origin load spike.

Về thiết kế, tôi muốn cache policy theo content class: static assets có versioned URLs và TTL dài; dynamic campaign HTML có freshness contract rõ; application cache key bao gồm các dimensions business cần; publish event kích hoạt invalidation có retry/telemetry; CDN invalidation có targeted scope. Nếu invalidation là best-effort, TTL phải đóng vai trò safety bound phù hợp.

Observability nên cho phép trả lời “request này nhận content version nào từ instance nào và CDN có hit/miss/stale không”. Tôi theo dõi publish-to-visible latency, invalidation failure, CDN hit ratio, origin traffic sau purge và stale-content incidents.

Testing gồm multi-instance integration test cho publish/invalidation, CDN staging validation nếu có, cache-key variation tests và failure injection khi invalidation event/purge call thất bại.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là một distributed cache-consistency incident. Tôi không restart hay purge toàn site trước khi biết stale bắt đầu ở đâu. Tôi sẽ xác nhận content version trong CMS, sau đó bypass CDN và kiểm tra từng origin instance. Nếu origin instances khác nhau, tôi tập trung vào application cache/invalidation. Nếu origin đều mới nhưng edge cũ, tôi kiểm tra CDN key, age/status và targeted purge. Nếu edge đúng mà browser cũ thì mới xuống browser cache policy.

Stabilization phụ thuộc evidence: với campaign khẩn cấp, targeted purge hoặc temporary bypass cho đúng page có thể hợp lý; blanket purge có thể tạo origin spike. Sau incident, tôi muốn cache policy theo content class, invalidation có retry và telemetry, TTL làm safety bound, và logs chứa content version + instance + correlation để đo publish-to-visible latency.

Điểm quan trọng là publish success không đồng nghĩa mọi cache layer đã converged.”

## Câu hỏi đào sâu

1. Nếu targeted purge API bị lỗi trong 10 phút nhưng business yêu cầu content mới trong 2 phút, bạn thiết kế fallback thế nào?
2. Nếu local in-memory cache cho performance rất tốt nhưng invalidation cross-instance phức tạp, bạn giữ nó hay bỏ nó? Dựa trên dữ liệu nào?
3. Tôi muốn đặt TTL của mọi HTML về 0 để loại bỏ stale content; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Quy stale content ngay cho CDN mà không kiểm tra origin.
- Restart application để xóa local cache nhưng bỏ qua multi-layer caching.
- Purge toàn site không đánh giá origin load/blast radius.
- Không hỏi freshness requirement nên không thể chọn TTL/invalidation strategy.
- Chỉ monitor availability, không đo content freshness/version propagation.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/purge.
- **3–4:** Nhận ra nhiều cache layer nhưng investigation chưa có thứ tự/evidence.
- **5–6:** Có source→origin→CDN→browser reasoning và stabilization hợp lý.
- **7–8:** Có multi-instance invalidation, cache-key reasoning, failure handling, tests và telemetry.
- **9–10:** Xử lý được incident đồng thời thiết kế freshness SLO, bounded staleness, targeted invalidation và operational observability với trade-offs rõ ràng.

# Câu 3 — Modernize hệ thống .NET Framework: giữ IIS, chuyển App Service hay đưa lên Kubernetes?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework 4.5, .NET 8, IIS, Windows Server, Azure App Service, Kubernetes, migration strategy, architecture boundaries, CI/CD, rollback, observability, cost of complexity

## Bối cảnh

Một enterprise management portal đã vận hành nhiều năm trên .NET Framework 4.5 + ASP.NET MVC + IIS/Windows Server. Hệ thống có:

- khoảng 35 business modules trong một deployable application;
- SQL Server là primary database;
- một số scheduled jobs chạy trong cùng application process;
- file export/import ghi vào local filesystem;
- Windows-integrated/legacy authentication ở một số internal flows;
- jQuery ở phần lớn UI và một số màn hình mới dùng React;
- deployment hiện tại qua Jenkins + Octopus Deploy;
- release mỗi 2–3 tuần, downtime ngắn vẫn đang được chấp nhận nhưng business muốn tiến tới deployment an toàn hơn;
- team mạnh về C#/.NET và Azure App Service, mới ở mức application-developer với Kubernetes.

Mục tiêu 12–18 tháng là chuyển phần server-side sang modern .NET, giảm phụ thuộc Windows Server và cải thiện deployment/reliability. CTO hỏi liệu nên:

1. migrate dần nhưng vẫn giữ IIS/Windows một thời gian;
2. chuyển target sang .NET 8 và Azure App Service on Linux;
3. containerize rồi chạy Kubernetes ngay để “future-proof”.

Chưa có requirement chứng minh cần independent scaling theo module hoặc orchestration phức tạp.

## Câu hỏi chính

Bạn sẽ xây modernization strategy như thế nào để giảm rủi ro production mà vẫn tiến tới modern .NET? Hãy phân tích dependency/compatibility, application boundaries, authentication, filesystem, background jobs, database migration, hosting, CI/CD, testing, observability và rollback. Bạn sẽ chọn IIS, App Service hay Kubernetes ở từng giai đoạn nào, và điều kiện nào sẽ làm bạn thay đổi quyết định?

## Câu hỏi làm rõ nên cân nhắc

1. Những dependency nào chỉ chạy trên .NET Framework/Windows hoặc dùng API không tương thích modern .NET?
2. Authentication requirement thực tế là gì, có thể chuyển sang Microsoft Entra ID/standards-based flow hay phải giữ Windows-specific behavior?
3. Local filesystem đang lưu temporary files hay là durable business data cần shared/object storage?
4. Scheduled jobs có yêu cầu exactly-once hay idempotency, chạy bao lâu và hiện chịu ảnh hưởng thế nào khi process recycle/deploy?
5. Business chấp nhận coexistence old/new trong bao lâu, và rollback/data compatibility requirement là gì?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn hosting platform trước khi lập compatibility inventory và xác định Windows-only dependencies.

### Gợi ý 2

Modernization không bắt buộc đồng nghĩa microservices. Một Modular Monolith hoặc application được modularize tốt vẫn có thể là đích phù hợp.

### Gợi ý 3

Tách migration thành các reversible steps: runtime/code compatibility, externalized state, background processing, deployment model và hosting có thể tiến hóa ở tốc độ khác nhau.

## Cấu trúc trả lời đề xuất

1. Chốt business goals và non-functional requirements.
2. Inventory dependencies, Windows coupling và unsupported APIs.
3. Thiết lập characterization/integration/E2E tests cho critical flows.
4. Tách state khỏi process: filesystem, session/cache, jobs.
5. Xác định module boundaries nhưng chưa bắt buộc tách services.
6. Chọn incremental runtime migration strategy và compatibility seam.
7. Thiết kế database changes backward-compatible khi coexistence.
8. Nâng CI/CD, deployment verification, observability và rollback.
9. Chọn hosting dựa trên requirement và team capability.
10. Đặt exit criteria cho từng phase và điều kiện cân nhắc Kubernetes/microservices sau này.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu bằng dependency/compatibility inventory, không bằng “rewrite”.
- Không giả định Kubernetes là modern hơn nên mặc định tốt hơn.
- Local filesystem và in-process jobs là coupling cần xử lý trước khi horizontal scaling/ephemeral hosting.
- Migration cần test safety net và rollback/data compatibility.
- Database migration phải xét giai đoạn old/new versions coexist.
- Hosting choice phải gắn với operational requirements và team capability.

### Điểm cộng

- Dùng characterization tests cho legacy behavior trước khi refactor sâu.
- Externalize durable files sang phù hợp như Azure Blob Storage khi requirement cho phép; temporary files có lifecycle khác.
- Tách scheduled jobs khỏi web-process lifecycle khi reliability/scaling yêu cầu, đồng thời thiết kế idempotency/concurrency control.
- Dùng expand/contract database changes cho rolling/coexistence deployment.
- Có strangler-style seam ở module/integration boundary khi cần migration dần, nhưng không tách service chỉ vì pattern phổ biến.

### Senior+

- Đề xuất decision records/exit criteria: App Service là default nếu đáp ứng requirement; Kubernetes chỉ được đưa vào khi có workload/orchestration/portability/operational requirement đủ mạnh để trả complexity cost.
- Phân biệt modernization của runtime, architecture và infrastructure; không buộc ba việc phải xảy ra cùng lúc.
- Thiết kế rollback theo cả application + schema + external side effects, không chỉ redeploy binary cũ.

## Hướng giải quyết tham khảo

Tôi sẽ chia chương trình thành nhiều bước có thể kiểm chứng. Phase đầu là inventory: NuGet/package dependencies, Windows-only APIs, authentication, filesystem, scheduled jobs, configuration, IIS assumptions và các integration. Song song, tôi tạo characterization/integration/E2E tests cho các business flows có rủi ro cao để biết migration có làm đổi behavior không.

Tôi không chọn Kubernetes làm target mặc định. Với thông tin hiện có, team đã mạnh App Service và chưa có requirement về orchestration/independent scaling. Nếu modern .NET application có thể chạy Linux và state đã externalized, App Service on Linux có thể là target đơn giản hơn về operations. Kubernetes chỉ đáng cân nhắc nếu sau này xuất hiện requirement cụ thể như nhiều independently deployable workloads, scheduling/networking/platform controls mà App Service không đáp ứng tốt, và organization sẵn sàng vận hành cluster/platform.

Trước khi chuyển hosting, tôi xử lý process coupling. Durable files không nên phụ thuộc local filesystem nếu application sẽ scale/redeploy; có thể chuyển sang Blob Storage nếu access/security/lifecycle requirement phù hợp. Scheduled jobs cần tách khỏi web lifecycle nếu chúng phải đáng tin cậy qua recycle/deploy; lựa chọn có thể là Worker Service, Functions hoặc scheduler khác tùy duration, trigger, retry và operational model. Dù dùng gì, job phải xét duplicate execution/idempotency khi chạy nhiều instance.

Về code, tôi xác định module boundaries và giảm coupling trước, nhưng chưa cần tách microservices. Có thể giữ Modular Monolith trên modern .NET nếu deployment/scale boundaries chưa yêu cầu tách. Với dependency không thể port ngay, tôi tạo seam hoặc tạm giữ phần Windows/legacy riêng trong giai đoạn coexistence thay vì block toàn bộ chương trình.

Database changes phải hỗ trợ old/new coexistence nếu rollout không atomic. Tôi ưu tiên additive/expand changes trước, deploy code tương thích cả schema cũ/mới trong window cần thiết, migrate data, rồi contract sau khi old version đã rút. Rollback plan phải xác định migration nào reversible và side effects nào không thể đơn giản undo.

CI/CD cần build reproducible artifact, automated tests, security/static analysis phù hợp, environment-specific configuration không nằm trong artifact, deployment validation, health/readiness và rollback. Observability phải có version marker, structured logs, traces, dependency metrics và business transaction success để so old/new.

Tôi có thể giữ IIS/Windows như một transition platform nếu dependency chưa Linux-compatible; đây không phải thất bại mà là cách giảm số biến thay đổi cùng lúc. Sau khi runtime/dependencies ổn định và state được externalize, mới chuyển hosting. Mỗi phase có exit criteria dựa trên compatibility, error rate, latency, deployment success và rollback drill.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách modernization thành runtime, application architecture và hosting thay vì đổi cả ba cùng lúc. Bước đầu là inventory Windows/.NET Framework coupling và tạo characterization tests cho critical flows. Sau đó tôi externalize state như durable files, xử lý scheduled jobs không phụ thuộc web process và làm database changes tương thích old/new trong migration window.

Tôi chưa thấy lý do chọn Kubernetes. Team mạnh App Service và chưa có independent-scaling/orchestration requirement, nên nếu application đã chạy được modern .NET trên Linux, App Service có cost vận hành thấp hơn và vẫn đạt mục tiêu giảm Windows dependency. IIS có thể được giữ tạm thời cho các phần chưa port được.

Tôi cũng không mặc định tách microservices. Tôi sẽ modularize boundaries trước và chỉ tách khi ownership, scaling hoặc deployment independence có giá trị thực. Mỗi phase phải có automated tests, telemetry, rollout criteria và rollback plan bao gồm schema/side effects, không chỉ binary. Nếu sau này workload chứng minh cần orchestration phức tạp và team có operational capability, lúc đó Kubernetes mới trở thành quyết định cần đánh giá lại.”

1. Nếu một vendor SDK quan trọng chỉ hỗ trợ .NET Framework/Windows trong 18 tháng nữa, bạn tránh để nó block toàn bộ migration thế nào?
2. Nếu CTO vẫn yêu cầu Kubernetes vì “mọi hệ thống mới đều phải containerized”, bạn cần đưa ra evidence/cost model nào để thảo luận quyết định?
3. Nếu database migration đã chạy và old application không đọc được schema mới, rollback strategy của bạn thay đổi thế nào?

## Lỗi trả lời thường gặp

- Đề xuất rewrite-from-scratch mà không có incremental migration/rollback.
- Đồng nhất modernization với microservices/Kubernetes.
- Bỏ qua Windows-specific authentication và filesystem coupling.
- Chỉ migrate code nhưng giữ scheduled jobs phụ thuộc web process rồi scale nhiều instances.
- Không thiết kế database compatibility cho old/new coexistence.

## Thang điểm 0–10

- **0–2:** Chọn platform theo xu hướng, không phân tích dependency/risk.
- **3–4:** Có migration plan nhưng thiếu coexistence, rollback hoặc operational reasoning.
- **5–6:** Có inventory, tests, state externalization, database compatibility và hosting trade-offs.
- **7–8:** Có phased strategy, reversible decisions, observability, CI/CD và criteria để chọn App Service/Kubernetes.
- **9–10:** Phân tách rõ runtime/architecture/infrastructure modernization, quản lý legacy constraints thực tế và tối ưu total complexity/risk thay vì tối đa hóa công nghệ mới.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Memory production phải được phân tích bằng managed heap, allocation, retention, GC/LOH và process memory evidence; working set tăng chưa đủ để kết luận leak.
- Cache freshness trong CMS/CDN là vấn đề consistency xuyên nhiều layer; cần truy vết source → origin instance → CDN → browser bằng content version và cache diagnostics.
- Modernization an toàn là chuỗi thay đổi có thể kiểm chứng và rollback; modern runtime không bắt buộc đi cùng microservices hoặc Kubernetes.
- Senior engineering ưu tiên evidence và cost of complexity hơn các “default solution” như `GC.Collect()`, blanket cache purge hoặc Kubernetes.

## Mẫu tư duy cần nhớ

1. **Phân biệt metric trước khi chẩn đoán:** process memory, managed heap, live objects và allocation rate trả lời các câu hỏi khác nhau.
2. **Đi theo đường truyền của dữ liệu:** với stale content, tìm layer đầu tiên mà version trở nên sai.
3. **Stabilize có kiểm soát:** giảm impact nhưng tránh hành động có blast radius lớn hoặc phá evidence.
4. **Tách các chiều modernization:** runtime, architecture và infrastructure có thể tiến hóa độc lập.
5. **Chỉ trả complexity cost khi requirement chứng minh giá trị:** cache, messaging, microservices hay Kubernetes đều không phải mục tiêu tự thân.
