# Câu 1 — EF Core trả về object “cũ” dù SQL đã thay đổi: Change Tracker, identity resolution và tracking query đang làm gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** Entity Framework Core, DbContext, Change Tracker, tracking, identity resolution, concurrency, ASP.NET Core, debugging, data consistency

## Bối cảnh

Một ASP.NET Core API dùng Entity Framework Core và SQL Server để quản lý hồ sơ sản phẩm.

Trong một request xử lý dài, service làm các bước sau:

1. load `Product` bằng `FindAsync(productId)`;
2. gọi một stored procedure thông qua một repository khác để cập nhật trực tiếp giá và trạng thái của cùng product;
3. tiếp tục query lại `Product` bằng cùng `DbContext` để tạo response;
4. response đôi khi vẫn chứa giá/trạng thái trước khi stored procedure chạy.

Team thử chạy SQL trực tiếp thì thấy database đã có giá trị mới. Một developer kết luận SQL Server đang trả stale data. Người khác đề xuất thêm Redis invalidation dù endpoint này không dùng Redis.

Một đoạn code rút gọn:

```csharp
var product = await dbContext.Products.FindAsync(
    new object[] { productId }, cancellationToken);

await pricingRepository.ApplyPriceAsync(productId, newPrice, cancellationToken);

var refreshed = await dbContext.Products
    .SingleAsync(x => x.Id == productId, cancellationToken);

return new ProductDto(
    refreshed.Id,
    refreshed.Price,
    refreshed.Status);
```

Chưa biết chắc:

- stored procedure có dùng cùng connection/transaction hay không;
- entity `Product` đang ở state nào trong Change Tracker;
- query thứ hai có tracking hay `AsNoTracking`;
- repository khác có dùng DbContext khác;
- business có thực sự cần đọc lại giá trị database ngay trong cùng unit of work;
- có concurrency update từ request khác hay không.

## Câu hỏi chính

Hãy giải thích vì sao cùng một `DbContext` có thể trả lại instance đã được tracking thay vì tạo object mới phản ánh toàn bộ giá trị vừa thay đổi bên ngoài Change Tracker, identity resolution liên quan thế nào, và bạn sẽ xác minh rồi sửa flow này ra sao mà không mặc định rằng database hoặc cache bị stale.

## Câu hỏi làm rõ nên cân nhắc

1. Stored procedure cập nhật database bằng cùng `DbContext`, cùng transaction hay một connection/context khác?
2. Sau lần load đầu tiên, `dbContext.Entry(product).State` và các original/current values là gì?
3. Query sau stored procedure có tracking không, và có thực sự phát SQL không?
4. Requirement cần một snapshot nhất quán trong transaction hay cần đọc đúng state mới nhất đã commit từ database?
5. Có update cạnh tranh từ request khác khiến “giá trị mới nhất” không chỉ có một phiên bản hay không?

## Gợi ý tư duy

### Gợi ý 1

`DbContext` không chỉ là wrapper để chạy SQL; nó giữ một identity map/change-tracking state trong lifetime của context.

### Gợi ý 2

Một tracking query có thể dùng entity instance đã được track cho cùng primary key. Việc query có phát SQL không đồng nghĩa mọi property của instance hiện có sẽ tự động được ghi đè theo cách bạn kỳ vọng.

### Gợi ý 3

Hãy phân biệt ba mục tiêu khác nhau: tiếp tục làm việc với state đang track, reload state từ database, và query read-only không tracking.

## Cấu trúc trả lời đề xuất

1. Làm rõ transaction/context boundaries.
2. Mô tả Change Tracker và identity resolution.
3. Giải thích behavior của `FindAsync` và tracking query.
4. Xác minh SQL command + tracked state bằng logging/debugging.
5. Phân biệt external database update với EF-managed update.
6. Chọn `ReloadAsync`, `AsNoTracking`, context boundary hoặc redesign flow theo requirement.
7. Xử lý concurrency/versioning nếu có writer khác.
8. Kiểm thử với hai contexts/transactions.
9. Theo dõi correctness và query behavior sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `DbContext` duy trì Change Tracker và một entity instance cho một key có thể đã được tracking.
- `FindAsync` có thể trả entity từ Change Tracker nếu entity với key đó đã được track, thay vì luôn truy vấn database.
- Tracking queries thực hiện identity resolution: nếu một entity cùng key đã được track, EF Core dùng instance hiện có.
- Một update thực hiện ngoài Change Tracker không tự động cập nhật current values của entity đang track.
- Không kết luận “SQL stale” trước khi kiểm tra SQL command, transaction và tracked state.
- Nếu cần state mới từ database, phải chọn semantics rõ ràng như reload entity, dùng context/read path phù hợp hoặc `AsNoTracking` tùy tình huống.
- `AsNoTracking` không phải fix toàn cục; write workflows vẫn cần tracking khi phù hợp.
- Nếu nhiều writers cùng cập nhật, phải xét optimistic concurrency/business invariant thay vì chỉ refresh object.

### Điểm cộng

- Dùng `ChangeTracker.DebugView`, logging hoặc debugger để xem tracked entries và state.
- Phân biệt `ReloadAsync` với `Entry(...).CurrentValues.SetValues(...)` và với một query read-only mới.
- Nhận ra một `DbContext` quá dài làm tracked state khó reasoning hơn; web request thường nên có unit-of-work boundary rõ.
- Nếu stored procedure là một phần business transaction, cân nhắc đưa việc thực thi vào cùng abstraction/context/transaction thay vì hidden side effect ở repository khác.

### Senior+

- Giải thích rằng “freshness” phải được định nghĩa theo transaction/isolation semantics, không chỉ theo thời điểm wall-clock.
- Nếu stored procedure thay đổi nhiều rows/derived fields, cân nhắc invalidate/reload đúng aggregate thay vì detach toàn bộ Change Tracker tùy tiện.
- Đưa concurrency token như `rowversion` vào thiết kế khi lost update là rủi ro.
- Thiết kế integration test chứng minh behavior với một context tracking entity và một context khác cập nhật cùng row.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng việc bỏ giả thuyết Redis hay SQL stale vì endpoint chưa có evidence cho hai nguyên nhân đó. Điểm đáng chú ý là cùng một `DbContext` đã load `Product` trước khi một đường code khác thay đổi row trong database.

`DbContext` giữ Change Tracker. Khi một entity được tracking, EF Core giữ instance và state của nó trong context. `FindAsync` đặc biệt có thể trả instance đã track theo primary key mà không cần query database. Tracking query cũng làm identity resolution: nếu kết quả SQL tương ứng một entity đã track, EF sử dụng instance đang có cho key đó.

Vì stored procedure cập nhật row bên ngoài Change Tracker, EF không tự biết current values của `product` đã đổi. Do đó tôi sẽ xác minh:

- command SQL nào thực sự chạy;
- stored procedure commit ở đâu;
- context có track `Product` không;
- query thứ hai có tracking không;
- state/current/original values của entry trước và sau stored procedure.

Nếu requirement là “sau external database update, lấy lại canonical values từ DB”, một phương án rõ ràng là reload tracked entity:

```csharp
await dbContext.Entry(product).ReloadAsync(cancellationToken);
```

Sau đó response dùng instance đã được refresh. Nhưng recommendation phụ thuộc transaction semantics: nếu stored procedure dùng transaction khác chưa commit hoặc isolation level không cho transaction hiện tại thấy update, reload cũng không giải quyết theo cách team mong đợi.

Nếu flow chỉ cần read-only snapshot cuối cùng và không cần tiếp tục tracking aggregate, có thể tách read path bằng một DbContext mới hoặc query `AsNoTracking` sau khi transaction/update boundary đã rõ. Tôi không dùng `AsNoTracking` như blanket policy cho mọi repository.

Nếu stored procedure thực sự là phần của cùng business unit of work, tôi xem lại abstraction. Hidden database mutation qua repository khác trong khi context đang giữ tracked aggregate khiến correctness khó reasoning. Có thể gọi stored procedure qua cùng context/transaction, hoặc redesign để một component sở hữu mutation boundary rõ ràng.

Nếu có concurrent writers, bài toán không chỉ là refresh. Tôi cần business rule cho conflict và có thể dùng `rowversion`/optimistic concurrency để phát hiện lost update.

Testing nên có integration test với hai contexts: context A load entity và giữ tracking; context B update row rồi commit; context A query/reload để xác nhận semantics mong muốn. Tôi cũng assert final database state, không chỉ object state trong memory.

## Mẫu trả lời trong phỏng vấn

“Em sẽ kiểm tra Change Tracker trước khi nói SQL stale. `DbContext` giữ entity theo key; `FindAsync` có thể trả object đã track và tracking query dùng identity resolution. Nếu stored procedure hoặc DbContext khác update row, Change Tracker của context hiện tại không tự biết các property đã đổi.

Em sẽ log SQL, xem transaction boundary và inspect entry state/current values. Nếu requirement là đọc lại giá trị canonical sau update, em có thể `ReloadAsync` entity hoặc dùng một read context/query no-tracking sau khi commit, tùy transaction semantics. Nếu stored procedure thuộc cùng unit of work, em ưu tiên làm boundary đó rõ hơn thay vì để mutation ẩn qua repository khác.

Nếu còn concurrent writers, em thêm concurrency model như `rowversion` thay vì chỉ refresh. Em sẽ integration-test bằng hai DbContexts để chứng minh behavior thực tế.”

## Câu hỏi đào sâu

1. Nếu `ReloadAsync` vẫn đọc giá trị cũ, bạn sẽ điều tra transaction/isolation và commit boundary như thế nào?
2. Một teammate muốn gọi `ChangeTracker.Clear()` sau mọi stored procedure để “chắc chắn fresh”; bạn phản biện ra sao?
3. Nếu endpoint vừa cần tracking để update aggregate vừa cần một read model luôn phản ánh committed database state mới nhất, bạn tách boundary thế nào?

## Lỗi trả lời thường gặp

- Quy mọi stale object cho Redis/database cache.
- Nghĩ rằng query lại cùng key luôn tạo một entity instance mới.
- Dùng `AsNoTracking` cho mọi query như một rule không điều kiện.
- Gọi `ChangeTracker.Clear()` hoặc detach toàn bộ mà không xét pending changes.
- Bỏ qua transaction isolation và concurrent writers.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/cache invalidation.
- **3–4:** Biết DbContext cache entity nhưng giải thích mơ hồ về tracking.
- **5–6:** Hiểu Change Tracker, identity resolution, reload/no-tracking và transaction boundary.
- **7–8:** Có evidence plan, concurrency semantics và integration test tốt.
- **9–10:** Kết nối object identity, database transaction semantics, business concurrency và unit-of-work design thành recommendation có điều kiện.

# Câu 2 — Akamai vẫn phục vụ nội dung cũ sau publish và một số user thấy nhầm phiên bản campaign

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** CDN, Akamai, HTTP caching, cache keys, purge/invalidation, CMS, ASP.NET Core, observability, incident response, deployment safety

## Bối cảnh

Một website marketing toàn cầu dùng CMS + ASP.NET Core ở origin và Akamai ở edge. Content editors publish landing pages cho một campaign theo nhiều locale.

Ngay sau một đợt publish:

- editor nhìn thấy content mới trong CMS preview;
- một số user thấy content mới, một số vẫn thấy version cũ trong 20–40 phút;
- khác biệt không đồng đều theo region;
- origin logs cho thấy khi request chạm origin thì response đã là version mới;
- một số URLs có query parameter cho campaign tracking;
- site dùng redirects và locale trong path;
- có HTML edge caching, browser caching và một số API responses cũng cache;
- publish workflow gọi một purge/invalidation integration nhưng team chưa chắc mọi URL variant đều được purge;
- một developer muốn đặt `Cache-Control: no-store` cho toàn bộ website;
- developer khác muốn purge toàn bộ CDN mỗi lần publish;
- business yêu cầu content campaign quan trọng xuất hiện trên public site trong vài phút, nhưng vẫn muốn cache hit ratio cao.

Chưa biết chắc:

- cache key đang gồm host/path/query/locale/header nào;
- purge request dùng URL purge, cache tag/key hay wildcard strategy;
- purge API có success nhưng propagation/coverage ra sao;
- browser cache TTL khác edge TTL thế nào;
- tracking query parameters có tạo cache variants hay bị normalize;
- authenticated/preview traffic có dùng cùng hostname/cache rules public hay không;
- có stale-if-error/stale-while-revalidate behavior nào được cấu hình hay không.

## Câu hỏi chính

Bạn sẽ stabilize incident và xác định stale content nằm ở browser, Akamai edge, origin hay publish/invalidation workflow như thế nào? Sau đó hãy thiết kế cache-key, TTL và purge strategy để content publish đạt freshness SLO mà không biến hệ thống thành “no-cache everywhere” hoặc purge toàn bộ CDN mỗi lần thay đổi.

## Câu hỏi làm rõ nên cân nhắc

1. Một URL cụ thể bị stale có response headers/cache diagnostics gì ở browser và qua các regions khác nhau?
2. Cache key có phân biệt query parameters, locale, host hoặc cookies nào mà purge request không cover không?
3. Publish event biết chính xác những pages/variants nào bị ảnh hưởng hay chỉ biết một content item chung?
4. Freshness SLO khác nhau thế nào giữa breaking campaign content, evergreen pages và static assets?
5. Preview/draft content có được bảo vệ khỏi public cache hoàn toàn chưa?

## Gợi ý tư duy

### Gợi ý 1

“User thấy stale” chưa chỉ ra layer nào stale. Phải trace cùng URL qua browser cache, edge cache và origin.

### Gợi ý 2

Invalidation chỉ chính xác nếu cache key và publish dependency graph được hiểu đúng.

### Gợi ý 3

TTL ngắn hơn, targeted purge và versioned immutable assets giải quyết những loại freshness khác nhau; không nên dùng một policy cho mọi resource.

## Cấu trúc trả lời đề xuất

1. Xác định business impact và affected URLs/locales.
2. So sánh browser/edge/origin response có cùng request signature.
3. Thu response headers/cache status/request IDs/purge records.
4. Liệt kê competing hypotheses.
5. Xác định cache-key mismatch hoặc invalidation gap nếu có.
6. Mitigate bằng targeted purge/TTL adjustment phù hợp.
7. Redesign publish-to-purge mapping.
8. Tách HTML/API/static-asset cache policies.
9. Test multi-region + URL variants + preview safety.
10. Monitor freshness SLO và purge failures.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Phân biệt browser cache, CDN edge cache và origin state bằng evidence.
- Không mặc định origin đúng nghĩa là mọi edge đã được invalidated đúng cache key.
- Kiểm tra URL/query/locale/host/header dimensions của cache key.
- Kiểm tra purge request status và đúng tập variants cần purge.
- Không dùng `no-store` toàn site nếu business vẫn cần CDN benefit.
- Không purge toàn bộ CDN mỗi publish như default vì tăng origin load và blast radius.
- Xác định freshness SLO để chọn TTL/purge policy.
- Preview/draft content không được leak vào public edge cache.
- Static assets có thể dùng content-hashed/versioned URLs với long immutable caching thay vì purge thường xuyên.

### Điểm cộng

- Normalize/ignore tracking parameters trong cache key nếu semantics cho phép, trong khi giữ functional query parameters cần thiết.
- Dùng surrogate/cache tags hoặc dependency mapping nếu CDN/publishing stack hỗ trợ, thay vì enumerate thiếu variants.
- Đặt observability cho purge request, completion/failure và synthetic freshness probes theo region.
- Có stale-serving policy có chủ đích cho origin outage thay vì vô tình serve stale security-sensitive content.
- Canh chỉnh browser `max-age` và edge TTL độc lập nếu platform hỗ trợ semantics phù hợp.

### Senior+

- Xây publish event chứa content version và affected routes/locales để invalidation deterministic hơn.
- Thiết kế post-publish verification: fetch edge từ nhiều regions và so content/version marker.
- Phân loại content theo consequence of staleness, không chỉ traffic volume.
- Đưa cache hit ratio, origin QPS, purge rate và publish-to-visible latency vào cùng SLO/cost model.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu từ một vài URL cụ thể mà user báo stale. Với cùng hostname, path, query và locale, tôi so response ở browser, request bypass/diagnostic phù hợp nếu có, edge regions và origin. Tôi ghi lại response headers, age/cache status, ETag/version marker và request correlation để biết layer nào đang trả version cũ.

Nếu origin luôn trả version mới nhưng một edge trả cũ, tôi kiểm tra cache key thực tế và purge coverage. Ví dụ `/en/campaign?utm_source=a` và `/en/campaign?utm_source=b` có thể là cùng nội dung business nhưng thành hai cache variants nếu query parameters nằm trong key. Purge chỉ canonical URL có thể không tác động mọi variant, tùy cấu hình. Ngược lại, nếu tracking params được ignore thì không nên giả định chúng tạo variant.

Tôi cũng xem locale, host aliases và redirects. Publish một content item có thể ảnh hưởng `/en/...`, `/fr/...`, listing page, navigation fragment hoặc API projection. Nếu integration chỉ purge một URL thì dependency graph thiếu.

Mitigation trong incident là targeted invalidation cho affected routes/variants và, nếu cần, giảm TTL tạm thời cho class nội dung đó. Tôi không chuyển toàn site sang `no-store`, vì nó loại edge caching và có thể đẩy load lớn về origin. Tôi cũng không purge toàn bộ site mặc định, vì mỗi publish nhỏ sẽ gây cache-miss wave.

Thiết kế dài hạn nên phân lớp:

- HTML campaign pages: TTL vừa phải + targeted purge theo publish event/freshness SLO.
- API/read models: cache theo semantics dữ liệu và authorization; private/personalized response không share public cache.
- static JS/CSS/images đã fingerprint: URL versioned/content-hashed + cache lâu/immutable.
- preview/draft: hostname/path/cookie rule riêng và bypass public cache.

Publish pipeline cần biết content version và affected public routes/locales. Nếu stack hỗ trợ cache tags/surrogate keys phù hợp, content item có thể map tới tag và purge đúng dependents. Nếu không, hệ thống cần route dependency index đáng tin cậy.

Tôi thêm post-publish verification: synthetic checks từ nhiều regions đọc một content-version marker hoặc expected content hash. Metrics gồm publish-to-visible latency, purge failure/rate, edge hit ratio, origin QPS, stale-content incidents và cache-key cardinality.

Testing phải cover query parameter variants, locales, redirects, browser cache, preview isolation, simultaneous publish và origin failure. Recommendation thay đổi nếu business thực sự yêu cầu sub-second global freshness; khi đó architecture/cache policy phải trả chi phí tương ứng thay vì giả vờ TTL dài vẫn đáp ứng được.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng purge toàn bộ CDN. Em chọn một URL stale và trace cùng request signature qua browser, edge và origin, xem cache headers/status, age, version marker và purge logs. Nếu origin mới nhưng edge cũ, em kiểm tra cache-key dimensions — host, locale, query, headers — và xem publish purge có cover đúng variants/dependencies không.

Mitigation là targeted purge cho affected routes và có thể giảm TTL của class nội dung này. Dài hạn em tách policy: HTML có TTL + publish invalidation, static assets dùng hashed URL/cache lâu, preview bypass public cache, personalized responses không share cache. Tracking params nên normalize/ignore nếu không ảnh hưởng nội dung.

Em cũng đưa freshness thành SLO đo được: publish-to-visible latency từ nhiều regions, purge failures, cache hit ratio và origin QPS. Như vậy team tối ưu được cả freshness lẫn CDN efficiency thay vì chọn no-cache everywhere.”

## Câu hỏi đào sâu

1. Nếu cache key hiện ignore mọi query parameter nhưng một parameter thật sự thay đổi nội dung page, bạn sửa thế nào mà không làm cardinality cache bùng nổ?
2. Một teammate đề xuất TTL HTML chỉ 5 giây để khỏi cần purge; bạn đánh giá trade-off bằng dữ liệu nào?
3. Nếu origin down ngay sau publish và CDN được cấu hình serve stale-on-error, content security-sensitive vừa bị gỡ nên được xử lý khác ra sao?

## Lỗi trả lời thường gặp

- Đồng nhất stale content với origin cache mà không trace từng layer.
- `no-store` toàn site để né invalidation design.
- Purge toàn bộ CDN cho mọi publish.
- Bỏ qua query/locale/host variants và browser cache.
- Không tách preview/personalized content khỏi public caching.

## Thang điểm 0–10

- **0–2:** Chỉ purge all hoặc tắt cache.
- **3–4:** Biết kiểm tra CDN nhưng thiếu cache-key/publish dependency reasoning.
- **5–6:** Có layer-by-layer evidence, targeted invalidation, TTL strategy và tests.
- **7–8:** Có deterministic publish mapping, regional verification, preview security và measurable freshness SLO.
- **9–10:** Cân bằng freshness, origin protection, cache economics, security và failure-mode behavior theo từng content class.

# Câu 3 — Thiết kế Notification Platform gửi In-app + Email + Browser Push mà không gửi trùng hoặc làm business transaction phụ thuộc nhà cung cấp

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** system design, ASP.NET Core, SQL Server, messaging, background processing, email, browser push, idempotency, retries, consistency, security, observability

## Bối cảnh

Một SaaS enterprise muốn có Notification Platform dùng chung cho nhiều modules: Tasks, Projects, Billing, Security và Support.

Một business event có thể tạo thông báo qua ba kênh:

- In-app;
- Email;
- Browser Push.

Ví dụ `TaskDueSoon` có thể gửi cả ba; `PasswordChanged` bắt buộc gửi security notification ngay; marketing-like informational events có thể chỉ gửi In-app tùy preference.

Yêu cầu ban đầu:

- API business không nên fail chỉ vì email/push provider đang lỗi;
- user có notification preferences theo loại sự kiện, trừ một số security events bắt buộc;
- một event không được gửi email/push trùng vì retry;
- in-app notifications cần read/unread, mark-all-read và deep link;
- email/push provider có thể throttle, timeout hoặc outage;
- hệ thống chạy nhiều instances;
- throughput ban đầu trung bình nhưng có burst lớn sau scheduled jobs;
- cần audit được notification nào đã được tạo/gửi/fail;
- browser push subscription có thể hết hạn;
- sau này có thể thêm SMS/Slack nhưng Release hiện tại chưa cần.

Team đang tranh luận:

1. mỗi business module gọi trực tiếp email/push provider sau khi commit database;
2. tạo một notification microservice riêng ngay từ đầu;
3. giữ modular monolith nhưng dùng durable outbox/queue + workers;
4. lưu toàn bộ notification state trong Redis vì “nhanh hơn SQL”.

Chưa biết chắc:

- exact throughput/SLA theo event class;
- email provider và push provider cụ thể;
- security notifications cho phép delay tối đa bao nhiêu;
- delivery receipt capability của từng provider;
- retention/audit requirement;
- multi-region requirement có tồn tại hay không;
- user preference model có cần quiet hours/digest sau này hay không.

## Câu hỏi chính

Hãy thiết kế Notification Platform từ business event đến per-channel delivery, bao gồm API/contracts, data model, durable publication, preference evaluation, idempotency, retries, dead-letter/recovery, provider abstraction, security, observability và deployment boundary. So sánh direct provider calls, modular-monolith workers và microservice; nêu điều kiện khiến bạn chọn mỗi phương án.

## Câu hỏi làm rõ nên cân nhắc

1. Security-critical notifications có latency SLO và retry policy khác notification thường không?
2. “Sent” được định nghĩa là provider accepted, delivered, hay user actually received/opened?
3. Preference được snapshot tại thời điểm event hay evaluate tại thời điểm delivery?
4. Audit/retention yêu cầu giữ payload, recipient và provider response bao lâu, có PII nào cần hạn chế không?
5. Burst lớn nhất dự kiến là bao nhiêu và provider có quota/rate limit nào?

## Gợi ý tư duy

### Gợi ý 1

Đừng đặt external provider call trong transaction boundary của business operation nếu provider không thể tham gia cùng consistency model.

### Gợi ý 2

Một logical notification có thể fan-out thành nhiều channel deliveries; idempotency nên có identity rõ ở cả notification và từng channel attempt.

### Gợi ý 3

Service boundary nên đi theo ownership/scale/deployment requirements, không chỉ vì có asynchronous messaging.

## Cấu trúc trả lời đề xuất

1. Clarify event classes, SLO, preferences và audit.
2. Định nghĩa canonical notification/event contract.
3. Chọn source of truth và transaction boundary.
4. Thiết kế outbox/durable queue.
5. Thiết kế fan-out per channel và idempotency.
6. Thiết kế provider adapters, retry/rate limiting/DLQ.
7. Thiết kế in-app query/read model.
8. Thiết kế security/privacy/preferences.
9. Chọn modular monolith vs microservice bằng criteria.
10. Test, deploy, recover và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Business transaction không gọi provider như correctness dependency mặc định.
- Có durable handoff giữa committed business event và notification processing, ví dụ transactional outbox + queue/worker hoặc tương đương.
- Logical notification và per-channel delivery có stable IDs/idempotency keys.
- Duplicate message/retry không được tạo duplicate business delivery nếu provider/idempotency contract hỗ trợ ngăn chặn.
- Retry phải bounded, phân loại transient/permanent errors và có DLQ/recovery path.
- Provider throttling cần backoff/rate limiting/backpressure.
- In-app notification cần persistent state phù hợp với read/unread/audit; Redis không mặc định là canonical store.
- User preferences không được áp dụng cho event bắt buộc nếu security policy nói phải gửi.
- Browser push invalid subscriptions cần được phát hiện và disable/remove có kiểm soát.
- Không mặc định microservice là tốt hơn modular monolith.

### Điểm cộng

- Data model tách `Notification` khỏi `NotificationDelivery` theo channel.
- Unique constraint như `(NotificationId, Channel)` hoặc stable `DeliveryId` để chống duplicate fan-out.
- Template versioning để audit nội dung đã gửi mà không lưu quá nhiều sensitive data.
- Provider adapter không làm domain contract phụ thuộc vendor-specific response.
- Có priority queue/worker lanes cho security-critical notifications để bulk informational traffic không làm chậm chúng.

### Senior+

- Phân biệt “provider accepted” với guaranteed end-user delivery; model status phải phản ánh capability thật.
- Có outbox dispatcher idempotent và consumer dedupe/retry strategy end-to-end.
- Xử lý event ordering khi preference/account state thay đổi gần thời điểm notification.
- Đưa PII minimization, encryption/secrets, audit access và retention vào design.
- Định nghĩa trigger để extract microservice sau này: independent scale, team ownership, failure isolation, release cadence hoặc cross-product reuse đủ lớn.

## Hướng giải quyết tham khảo

Tôi sẽ giữ business transaction và external delivery tách nhau. Ví dụ khi Task chuyển trạng thái và cần `TaskDueSoon`, module ghi business change và một outbox event trong cùng SQL transaction. Sau commit, dispatcher phát event vào durable queue hoặc chuyển trực tiếp cho background worker theo kiến trúc hiện tại. Như vậy email provider outage không rollback business transaction và event không bị mất trong failure window “DB commit xong process chết trước publish”.

Notification processing tạo một logical `Notification` với stable ID, event type, user, resource/deep link, created time, template/version và policy metadata. Sau khi evaluate channel policy/preferences, nó tạo `NotificationDelivery` cho InApp/Email/BrowserPush. Mỗi delivery có ID ổn định, status, attempt count, next-attempt time, provider reference và last error category.

Idempotency phải xuất hiện ở nhiều boundary. Outbox dispatcher có thể phát duplicate nên consumer phải biết event đã materialize chưa. Fan-out có unique constraint trên notification + channel. Nếu provider hỗ trợ idempotency key, worker gửi stable `DeliveryId`; nếu provider không hỗ trợ, local idempotency giảm duplicate attempts nhưng không thể tự đảm bảo external side effect exactly-once qua crash/timeout. Khi outcome không chắc chắn, provider lookup/reconciliation capability quyết định recovery.

Retry chỉ dành cho transient conditions. 429/temporary 5xx dùng bounded exponential backoff/jitter phù hợp và respect provider rate limits; invalid recipient/subscription là permanent hoặc cần cleanup. Sau ngưỡng, delivery đi trạng thái failed/DLQ để operator/recovery job xử lý. Tôi không retry vô hạn.

In-app notifications phù hợp với persistent relational/read store vì có read/unread, retention, audit và query theo user/time. Redis có thể hỗ trợ cache/counter nếu evidence cần, nhưng không là source of truth mặc định. `MarkAllRead` nên được thiết kế tránh update hàng triệu rows không cần thiết nếu scale lớn, ví dụ có thể dùng per-user read watermark tùy semantics; nhưng chỉ thêm complexity nếu data volume chứng minh cần.

Security events có policy riêng: không cho user opt out, có priority lane và SLO chặt hơn. Tuy nhiên “email sent” chỉ nên có nghĩa đúng capability provider: accepted/queued không phải chứng minh user đã đọc. Model status không được hứa guarantee mà provider không cung cấp.

Browser Push cần subscription lifecycle. 404/410 hoặc signal invalid từ provider dẫn tới disable endpoint sau policy thích hợp. Email hard bounce cũng cần suppression/cleanup nếu provider hỗ trợ feedback.

Tôi chưa tách microservice chỉ vì workflow async. Nếu platform hiện là modular monolith, một notification module + outbox + workers có thể đơn giản hơn, cùng deployment/observability và ít distributed-system overhead. Tôi tách service khi notification có independent scaling, provider integrations lớn, nhiều product/team cùng dùng, cần failure isolation hoặc release cadence riêng.

Testing gồm duplicate event, provider 429/timeout, worker crash sau provider acceptance, invalid push subscription, preference changes, huge burst, DLQ replay và security-priority starvation test. Metrics gồm event-to-created latency, event-to-provider-accepted latency theo channel/class, queue age, retry rate, provider errors/429, duplicate suppressed, DLQ count, invalid subscription rate và in-app query latency.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không để Task/Billing gọi email provider trực tiếp trong business transaction. Em ghi business change + outbox trong cùng SQL transaction, rồi worker xử lý notification bất đồng bộ. Một logical notification fan-out thành từng `NotificationDelivery`, mỗi delivery có stable ID, channel, status và attempt metadata.

Retry phải idempotent và bounded. Nếu provider hỗ trợ idempotency key em dùng DeliveryId ổn định; 429 thì backoff/rate-limit-aware, lỗi permanent đi failed/DLQ. In-app state em giữ persistent vì cần read/unread/audit; Redis chỉ là optimization nếu có evidence.

Security events có priority/SLO và không cho opt-out. Em cũng phân biệt provider accepted với actual delivery. Về boundary, em bắt đầu bằng module + workers nếu hệ thống hiện là modular monolith; chỉ extract microservice khi independent scale/ownership/failure isolation thực sự trả được distributed complexity. Em failure-test duplicate, crash-after-send, provider outage và burst, rồi monitor queue age, delivery latency, retries và DLQ.”

## Câu hỏi đào sâu

1. Nếu email provider không hỗ trợ idempotency và worker timeout sau khi request đã gửi đi nhưng chưa nhận response, bạn ngăn duplicate/reconcile thế nào?
2. Một architect yêu cầu tách Notification thành microservice ngay vì “mọi async component nên là service riêng”; bạn dùng tiêu chí nào để phản biện hoặc đồng ý?
3. Nếu một burst 10 triệu informational notifications xuất hiện cùng lúc với security alerts, bạn bảo đảm alert không bị starvation thế nào?

## Lỗi trả lời thường gặp

- Gọi email/push provider trực tiếp rồi rollback business operation khi provider down.
- Hứa “exactly once delivery” mà không xác định boundary/provider guarantee.
- Retry vô hạn hoặc bỏ qua 429/backpressure.
- Dùng Redis làm canonical notification store chỉ vì nhanh.
- Tách microservice mặc định mà không nêu ownership/scale/failure-isolation requirement.

## Thang điểm 0–10

- **0–2:** Chỉ nói dùng queue và email provider.
- **3–4:** Có async delivery nhưng thiếu durability/idempotency/failure semantics.
- **5–6:** Có outbox, delivery model, bounded retry, preferences, DLQ và persistent in-app state.
- **7–8:** Có provider ambiguity, priority lanes, security/privacy, failure tests và observability.
- **9–10:** Cân bằng transaction boundaries, delivery guarantees, scale, operability và service-boundary economics thành architecture có điều kiện rõ ràng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `DbContext` là unit-of-work/change-tracking boundary, không chỉ là SQL executor. Tracking, identity resolution và external database mutations phải được reasoning cùng transaction semantics.
- CDN freshness là bài toán nhiều tầng: browser, edge, origin, cache key và publish invalidation. Cần trace evidence thay vì tắt cache toàn hệ thống.
- Notification delivery phải thiết kế cho duplicate, retry, provider outage và ambiguous outcomes. Durable handoff + idempotency + bounded retries quan trọng hơn lời hứa “exactly once”.
- Kiến trúc tốt tách business correctness khỏi external provider availability và chỉ thêm distributed boundaries khi có yêu cầu thực sự.

## Mẫu tư duy cần nhớ

1. **Inspect state before blaming infrastructure:** xem Change Tracker/cache layer/transaction boundary bằng evidence.
2. **Trace the full delivery path:** browser → edge → origin hoặc business event → queue → provider.
3. **Design retry together with idempotency.**
4. **Use SLOs to choose TTL, priority và retry policy.**
5. **Prefer the simplest deployment boundary that still meets ownership, scale and failure-isolation requirements.**
