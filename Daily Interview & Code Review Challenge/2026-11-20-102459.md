# Câu 1 — Cosmos DB: TOP 20 nhưng RU tăng bất thường

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Cosmos DB, .NET 8, partitioning, indexing, RU, query diagnostics

## Bối cảnh

API ASP.NET Core truy vấn 20 lịch đặt chỗ mới nhất từ Cosmos DB container có partition key /tenantId, nhưng query chỉ filter branchId và status, không truyền QueryRequestOptions.PartitionKey. Sau khi thêm một tenant lớn, p95 từ 180 ms lên 1.8 giây, RU/request tăng. Chưa có diagnostics hoặc phân bố tải. TOP 20 là giới hạn kết quả, không phải cam kết chi phí đọc.

## Câu hỏi chính

Giải thích cơ chế định tuyến partition, query execution, indexing và throttling; phân biệt giả thuyết, kiểm chứng và đề xuất cải tiến mà vẫn bảo đảm tenant isolation.

## Câu hỏi làm rõ nên cân nhắc

1. branchId có ánh xạ duy nhất đến tenantId được xác thực không?
2. RU, 429, retries và số partitions được truy vấn là bao nhiêu?
3. Indexing policy và ORDER BY startAt hiện thế nào?
4. Có hot tenant hay cross-tenant administrative query không?
5. Consistency, pagination và SLO là gì?

## Gợi ý tư duy

### Gợi ý 1

Số document trả về không đồng nghĩa số document được xử lý.

### Gợi ý 2

Thiếu partition key request có thể khiến query fan-out.

### Gợi ý 3

Dùng SDK diagnostics, RequestCharge, query metrics và phân bố 429 để tách nguyên nhân.

## Cấu trúc trả lời đề xuất

1. Chốt quyền tenant và query contract.
2. Mô tả partition routing, index, TOP và RU.
3. Đo fan-out, index, throttling và retries.
4. Thử partition-scoped query và so sánh cùng dataset.
5. Đánh giá thay đổi schema, cache, testing và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- TOP không bảo đảm query rẻ; request không cung cấp partition key có thể fan-out.
- RU chịu ảnh hưởng query/index/data distribution; 429 retries có thể tăng latency.
- Xác minh tenantId trước khi truyền PartitionKey, tránh lộ dữ liệu tenant khác.

### Điểm cộng

- Đọc RequestCharge, diagnostics, query metrics, 429 rate.
- So sánh query cùng filter, index và dataset; dùng continuation token.

### Senior+

- Phân tích hot logical partition, synthetic partition key/read model, backfill và transaction boundary.
- Thiết kế SLO và migration rollback.

## Hướng giải quyết tham khảo

Cosmos DB for NoSQL dùng partition key để phân bố document. Khi có partition key chính xác trong request, truy vấn có thể được định tuyến tới logical partition; nếu không, có thể phải tìm qua nhiều partition. TOP 20 chỉ giới hạn output, không bảo đảm ít RU. Indexing policy, ORDER BY, query shape và kích thước document cũng ảnh hưởng cost. Thu thập RequestCharge, SDK diagnostics, query metrics, 429/retry counts, per-partition load và execution timings trên một request chậm. Nếu tenantId đã được xác minh từ identity và dữ liệu được partition theo /tenantId, truyền QueryRequestOptions.PartitionKey; benchmark trước/sau, kiểm tra composite index theo truy vấn thực tế thay vì mặc định thêm index. Nếu một tenant nóng, đánh giá partition strategy mới hoặc read model; thay partition key là migration dữ liệu chứ không phải đổi cấu hình đơn giản. Cache chỉ phù hợp khi có hit rate, freshness contract và invalidation. Kiểm thử tenant isolation, continuation token, duplicate timestamps, skewed load, 429 failure và RU regression. Theo dõi RU/request, 429, p95/p99, retry delay và authorization failures.

## Mẫu trả lời trong phỏng vấn

> Tôi không kết luận thêm Redis. TOP 20 giới hạn kết quả chứ không bảo đảm chỉ đọc 20 document. Tôi kiểm tra partition key, index và diagnostics, đặc biệt RU và 429 retries. Nếu request thiếu tenantId partition key, tôi xác thực tenant context rồi thử scoped query trên dữ liệu tương đương. Nếu bottleneck là hot tenant, tôi đánh giá lại phân vùng hoặc read model với migration plan. Tôi đo lại p95, RU và độ đúng dữ liệu trước khi rollout.

## Câu hỏi đào sâu

1. Nếu tenant lớn chiếm 80% traffic thì truyền PartitionKey có đủ không?
2. Làm thế nào migrate partition strategy mà không mất dữ liệu?
3. Nếu admin cần cross-tenant search, API và authorization nên thay đổi thế nào?

## Lỗi trả lời thường gặp

- Cho rằng TOP 20 chỉ đọc 20 document.
- Đề xuất Redis mà không đo RU.
- Tin tenantId do client cung cấp.
- Không phân biệt 429/retry với query execution.
- Tuyên bố composite index luôn giải quyết được.

## Thang điểm 0–10

- **0–2:** Không làm rõ yêu cầu, cơ chế hoặc tác động; giải pháp chủ yếu là đoán.
- **3–4:** Nhận diện một số vấn đề nhưng thiếu chứng cứ và phân tích trade-offs.
- **5–6:** Đúng kỹ thuật cơ bản, có hướng kiểm chứng và khắc phục.
- **7–8:** Lập luận sâu, kiểm thử failure paths, security, observability và rollout.
- **9–10:** Quyết định có điều kiện theo evidence/SLO, quản lý rủi ro production, rollback và giao tiếp rõ ràng.

# Câu 2 — IIS App Pool recycle sau Octopus release

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, .NET Framework 4.5, TeamCity, Octopus Deploy, session, observability

## Bối cảnh

Portal ASP.NET MVC chạy trên hai Windows Server sau load balancer. Sau TeamCity/Octopus release, một số request 503, user mất phiên và worker PID thay đổi. Release đổi cấu hình và dependency. Chưa biết đó là scheduled recycle, crash, AppDomain restart, memory threshold hay load balancer gửi request tới node chưa sẵn sàng.

## Câu hỏi chính

Bạn là incident lead: xác định tác động, ổn định dịch vụ, điều tra các nguyên nhân cạnh tranh và thiết kế biện pháp khắc phục, kiểm thử, rollout và giám sát.

## Câu hỏi làm rõ nên cân nhắc

1. Lỗi xảy ra ở node nào và bắt đầu tại deployment step nào?
2. Session InProc hay external; machineKey giữa các node có đồng nhất không?
3. WAS/IIS ghi recycle reason, crash hoặc rapid-fail protection gì?
4. Health checks, connection draining và warm-up có không?
5. Artifact, web.config transform, credentials và dependency có giống nhau giữa nodes không?

## Gợi ý tư duy

### Gợi ý 1

PID thay đổi là triệu chứng, chưa phải root cause.

### Gợi ý 2

InProc session mất khi worker/AppDomain restart; auth cookie còn phụ thuộc key/config.

### Gợi ý 3

Ghép timeline release, WAS, HTTPERR, Windows events, application logs và load balancer health.

## Cấu trúc trả lời đề xuất

1. Đo blast radius, 503, session failure và business impact.
2. Dừng rollout, drain node lỗi hoặc rollback có điều kiện.
3. Thu thập evidence theo node và release ID.
4. So sánh crash/recycle/config/session/probe hypotheses.
5. Fix có kiểm chứng, canary, warm-up, rollback và alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Ổn định trước, giữ evidence, không restart bừa.
- Phân biệt IIS recycle, crash, AppDomain restart và 503 origin.
- Hiểu InProc session và machineKey web farm.

### Điểm cộng

- So sánh artifact/config checksums, WAS events, HTTPERR, event logs, memory counters.
- Triển khai rolling deployment, health/readiness probes và warm-up.

### Senior+

- Runbook rollback tương thích database, postmortem và SLO alerts.
- Session migration với trade-offs latency/complexity.

## Hướng giải quyết tham khảo

Đầu tiên xác định ảnh hưởng theo node và thời điểm. Ngừng rollout, drain node có vấn đề nếu node còn lại đủ capacity; nếu cả hai lỗi, rollback artifact/config đã biết tốt sau khi xác minh schema migration tương thích. Giữ event logs trước khi restart. Điều tra theo timeline Octopus steps, web.config/file changes, WAS/W3SVC, HTTPERR, Windows Application/System logs, crash dumps khi phù hợp, App Pool recycle schedule, memory threshold, rapid-fail protection, permissions và load balancer probes. Nếu session InProc, recycle/AppDomain restart làm mất session; sticky sessions không giải quyết recycle. Nếu Forms Authentication machineKey không đồng nhất, chuyển node có thể làm cookie không đọc được; không log keys/cookies. Nếu node chưa warm-up, load balancer có thể gửi request quá sớm. Sửa đúng nguyên nhân; dùng rolling deploy, drain, warm-up, smoke tests và canary. Đánh giá external session store nếu business cần survive recycle. Kiểm thử auth/session cross-node, forced recycle, one-node outage, deployment rollback và load/cold start. Theo dõi 503/500 theo node, process uptime, recycle events, session failure, startup latency và request queue. Root cause chỉ xác nhận khi evidence khớp.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ tách triệu chứng PID đổi khỏi nguyên nhân. Đầu tiên đo 503 và mất phiên theo node, dừng rollout, drain node lỗi hoặc rollback nếu cần. Tôi ghép timeline Octopus với WAS, HTTPERR, crash logs và load balancer probes. Mất phiên có thể do InProc session hoặc machineKey khác nhau, còn 503 có thể do worker chưa sẵn sàng. Tôi sẽ xác minh từng giả thuyết, sửa theo bằng chứng, canary với warm-up và thêm alert theo node.

## Câu hỏi đào sâu

1. Nếu không thể chuyển InProc ngay, giảm tác động thế nào?
2. Nếu schema đã migrate không backward-compatible, rollback ra sao?
3. Nếu WAS không ghi rõ recycle reason, thu thập bằng chứng gì tiếp?

## Lỗi trả lời thường gặp

- Coi mọi PID change là crash.
- Restart cả cụm trước khi thu thập logs.
- Nghĩ sticky session cứu được recycle.
- Bỏ qua machineKey và config drift.
- Không có rollback hoặc health gate.

## Thang điểm 0–10

- **0–2:** Không làm rõ yêu cầu, cơ chế hoặc tác động; giải pháp chủ yếu là đoán.
- **3–4:** Nhận diện một số vấn đề nhưng thiếu chứng cứ và phân tích trade-offs.
- **5–6:** Đúng kỹ thuật cơ bản, có hướng kiểm chứng và khắc phục.

# Câu 3 — Optimizely CMS + Akamai: publish đúng phiên bản trong hai phút

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai, ASP.NET Core, Vue.js, SEO, caching, distributed systems

## Bối cảnh

Website marketing dùng Optimizely CMS, Vue.js và ASP.NET Core. Page có blocks, localized content, metadata SEO và review widget bên thứ ba. Akamai cache public HTML và assets. Product đặt SLO giả định: phần lớn người dùng thấy bản publish mới trong hai phút; preview phải xem được draft nhưng không được lộ public. Đôi khi title mới đi cùng block cũ; marketing muốn Purge all. Peak campaign traffic gấp 15 lần.

## Câu hỏi chính

Thiết kế content delivery, preview isolation, revision consistency và invalidation/rebuild pipeline. So sánh ít nhất hai kiến trúc hợp lý, đánh giá SEO, failure, chi phí và vận hành.

## Câu hỏi làm rõ nên cân nhắc

1. Trang nào cần crawl/index SEO, trang nào personalized?
2. Page và blocks có cùng published revision/snapshot không?
3. Cache key theo host, locale, path, cookies và query thế nào?
4. CDN hỗ trợ purge theo path/tag/key trong cấu hình hiện tại không?
5. SLO áp dụng p95 hay toàn bộ người dùng, có chấp nhận stale không?

## Gợi ý tư duy

### Gợi ý 1

CMS là source of truth; CDN/browser cache là các bản sao.

### Gợi ý 2

Một publish event có thể ảnh hưởng nhiều routes và content blocks.

### Gợi ý 3

Thiết kế versioned delivery, dependency graph, idempotent invalidation và synthetic verification theo vùng.

## Cấu trúc trả lời đề xuất

1. Xác định freshness, SEO, preview và security contract.
2. Định nghĩa content model, version và cache boundaries.
3. So sánh SSR+edge cache với static/incremental generation.
4. Thiết kế durable publish event, retry và affected-route invalidation.
5. Đưa ra deployment, rollback, tests và publish-to-visible telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Preview authenticated và no-store, tách public CDN cache.
- Cache key có host/locale và không cache personalized data public.
- Publish cần revision-aware invalidation và đo freshness.
- SEO cần crawlable content, canonical, redirects, sitemap phù hợp.

### Điểm cộng

- Dependency graph page-block và immutable assets.
- Retries, out-of-order events, DLQ/reconciliation và CDN failure.

### Senior+

- Trade-offs SSR vs static build, cache-miss storm và cost-of-complexity.
- Rollback revision, regional probes, staged rollout và observability.

## Hướng giải quyết tham khảo

Giữ CMS làm source of truth; delivery projection gắn page/block published revision hoặc generation để tránh title mới/block cũ. Lưu dependency graph page→blocks để xác định affected routes. Phương án A: SSR HTML qua ASP.NET Core/Optimizely, Vue hydrate phần tương tác, Akamai cache public HTML theo host/path/locale với TTL và purge theo affected paths; ưu điểm ít hệ thống, SEO rõ, nhược điểm origin load và invalidation fan-out. Phương án B: static/incremental generation với immutable assets và atomic manifest/pointer theo generation; ưu điểm edge delivery nhanh, nhược điểm build queue và publish latency, nhất là personalization. Chọn theo số routes, publish frequency, SEO và vận hành, không tự động microservices. Pipeline: durable publish event có contentId/revision → compute affected routes → invalidate/rebuild → synthetic probes kiểm tra version tại edge → mark propagation. Retry bounded + idempotency, kiểm tra latest revision để không áp dụng event cũ; khi purge API hỏng, dùng TTL/fallback theo freshness contract và escalation cho urgent takedown. Không mặc định purge all vì cache-miss storm. Preview dùng authenticated host/route, Cache-Control private,no-store, không index và kiểm soát authorization; robots.txt không thay thế bảo mật. SEO: canonical, hreflang nếu đa ngôn ngữ, 301/404, sitemap và server-rendered crawlable HTML. Review widget có timeout/fallback, sanitize output. Test Playwright SEO/public/preview, out-of-order events, purge failure, region mismatch, high load, rollback. Metrics publish-to-visible p95/p99, purge error, queue age, CDN hit ratio, origin RPS, mixed revisions và Core Web Vitals.

## Mẫu trả lời trong phỏng vấn

> Tôi làm rõ freshness SLO, SEO và personalization trước. CMS là nguồn dữ liệu chuẩn; CDN là bản sao nên cần revision-aware publish và dependency invalidation. Với hệ thống vừa phải tôi ưu tiên SSR public HTML và Akamai cache theo locale/path, thêm durable job purge affected routes, retry và probes kiểm chứng version. Preview phải authenticated và no-store. Nếu content chủ yếu static, tôi so sánh incremental generation với manifest versioned. Tôi không dùng purge all thường xuyên vì origin overload; quyết định dựa trên publish latency và cache hit metrics.

## Câu hỏi đào sâu

1. Khi Akamai purge API lỗi 30 phút nhưng cần gỡ nội dung khẩn, xử lý thế nào?
2. Một block nằm trên 10.000 pages: giảm invalidation storm ra sao?
3. Preview shareable link nên có authorization và expiry thế nào?

## Lỗi trả lời thường gặp

- Cho rằng CMS publish tức là CDN cập nhật ngay.
- Purge all cho mọi thay đổi.
- Cache draft hoặc personalized content ở public edge.
- Bỏ qua canonical, status codes và crawler tests.
- Không xử lý duplicate/out-of-order events.

- **3–4:** Nhận diện một số vấn đề nhưng thiếu chứng cứ và phân tích trade-offs.
- **5–6:** Đúng kỹ thuật cơ bản, có hướng kiểm chứng và khắc phục.
