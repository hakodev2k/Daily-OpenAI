# Code Review Challenge 1 — Upload file lớn qua ASP.NET Core làm tăng memory và che lỗi security

**Chủ đề:** ASP.NET Core, C#/.NET, Azure Blob Storage, file streaming, security, cancellation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một API cho phép người dùng đã đăng nhập upload tài liệu lên Azure Blob Storage. Production chạy nhiều Azure App Service instances. Sau khi tăng giới hạn file lên 500 MB, memory của instance tăng mạnh khi có nhiều upload đồng thời; một số request timeout nhưng backend vẫn tiếp tục truyền dữ liệu. Security review cũng phát hiện tên file và MIME type từ client đang được tin tưởng quá mức.

Business yêu cầu file lớn phải upload ổn định, không ghi đè file của tenant khác, không expose storage credential và phải có telemetry đủ để điều tra upload thất bại.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/files")]
public sealed class FilesController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly ILogger<FilesController> _logger;

    public FilesController(
        BlobContainerClient container,
        ILogger<FilesController> logger)
    {
        _container = container;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> Upload(IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest();

        var memory = new MemoryStream();
        await file.CopyToAsync(memory);

        memory.Position = 0;

        var blobName = file.FileName;
        var blob = _container.GetBlobClient(blobName);

        await blob.UploadAsync(
            memory,
            new BlobHttpHeaders
            {
                ContentType = file.ContentType
            });

        _logger.LogInformation(
            "Uploaded {FileName} ({Length}) as {ContentType}",
            file.FileName,
            file.Length,
            file.ContentType);

        return Ok(new
        {
            file.FileName,
            Url = blob.Uri.ToString()
        });
    }
}
```

## Kết quả code review tham khảo

### Critical — Storage key lấy trực tiếp từ tên file do client cung cấp

**Vấn đề:** `file.FileName` được dùng làm blob name.  
**Tại sao xảy ra:** Client kiểm soát metadata này; tên trùng có thể va chạm và naming không thể hiện tenant ownership.  
**Ảnh hưởng production:** Có thể ghi đè/đụng namespace hoặc làm sai authorization boundary tùy cấu hình upload.  
**Cách sửa:** Sinh storage key server-side, ví dụ `tenantId/{generatedId}`; lưu original filename chỉ như metadata đã sanitize.

### High — Copy toàn bộ file vào MemoryStream

**Vấn đề:** Request tạo thêm một bản đầy đủ của file trong managed memory.  
**Tại sao xảy ra:** `CopyToAsync(memory)` materialize toàn bộ payload trước khi Blob upload.  
**Ảnh hưởng production:** Concurrent large uploads gây allocation lớn, GC pressure, memory exhaustion và instance recycle.  
**Cách sửa:** Stream từ input tới Blob hoặc dùng direct-to-Blob upload/SAS khi requirement cho phép; áp dụng size/concurrency limits.

### High — Không propagate cancellation

**Vấn đề:** Không truyền `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Các async call chạy với cancellation mặc định.  
**Ảnh hưởng production:** Client disconnect nhưng server vẫn đọc/gửi file, tiêu tốn bandwidth, connection và compute.  
**Cách sửa:** Truyền cancellation token tới copy/upload và xử lý cancellation như expected termination.

### High — Thiếu server-side file validation

**Vấn đề:** Chỉ kiểm tra length > 0.  
**Tại sao xảy ra:** Tin metadata client.  
**Ảnh hưởng production:** File quá lớn/không được phép hoặc payload nguy hiểm có thể đi vào storage.  
**Cách sửa:** Enforce max size, allowed types theo requirement, kiểm tra signature/content khi cần và tích hợp malware scanning/quarantine nếu threat model yêu cầu.

### Medium — Tin `ContentType` từ client

**Vấn đề:** MIME type được ghi thẳng vào blob.  
**Tại sao xảy ra:** `ContentType` là client-supplied.  
**Ảnh hưởng production:** Sai content handling; nếu blob được phục vụ trực tiếp có thể tạo security/content-sniffing risk.  
**Cách sửa:** Xác định content type server-side theo policy; dùng safe download headers và không inline untrusted active content.

### Medium — Resource lifetime của MemoryStream không rõ

**Vấn đề:** Stream không được dispose.  
**Tại sao xảy ra:** Không có `await using`/`using`.  
**Ảnh hưởng production:** Với implementation hiện tại, managed buffer vẫn chờ GC; kết hợp file lớn làm memory pressure tệ hơn.  
**Cách sửa:** Tránh buffer toàn bộ; mọi owned stream cần dispose rõ ràng.

### Medium — API trả raw Blob URI mà chưa xác định access model

**Vấn đề:** Response giả định URI có thể dùng an toàn.  
**Tại sao xảy ra:** Storage authorization/public access chưa được xét.  
**Ảnh hưởng production:** Có thể expose path không nên lộ hoặc tạo URL không dùng được nếu container private.  
**Cách sửa:** Trả application file ID; download qua authorized endpoint hoặc short-lived SAS khi phù hợp.

### Medium — Thiếu idempotency/collision policy

**Vấn đề:** Retry có thể tạo kết quả không xác định.  
**Tại sao xảy ra:** Không có upload ID/idempotency key hoặc overwrite policy rõ.  
**Ảnh hưởng production:** Duplicate uploads hoặc overwrite ngoài ý muốn.  
**Cách sửa:** Generated immutable blob key + database record/idempotency strategy theo business semantics.

### Low — Telemetry chưa đủ để điều tra

**Vấn đề:** Log chỉ có filename/length/type.  
**Tại sao xảy ra:** Không có correlation, tenant-safe identifier, duration, result hay dependency telemetry.  
**Ảnh hưởng production:** Khó phân biệt client abort, Blob failure, throttling và server pressure.  
**Cách sửa:** Structured telemetry với upload ID, sanitized tenant/file IDs, duration, bytes, outcome và Blob dependency trace; không log sensitive content.

## Phiên bản đề xuất

```csharp
[HttpPost]
[RequestSizeLimit(524_288_000)]
public async Task<IActionResult> Upload(
    IFormFile file,
    CancellationToken cancellationToken)
{
    if (file is null || file.Length <= 0 || file.Length > 524_288_000)
        return BadRequest();

    var tenantId = GetAuthorizedTenantId(User);
    var fileId = Guid.NewGuid();
    var blobName = $"{tenantId:N}/{fileId:N}";

    var safeContentType = DetectAllowedContentType(file);
    if (safeContentType is null)
        return BadRequest("Unsupported file type.");

    var blob = _container.GetBlobClient(blobName);

    await using var input = file.OpenReadStream();

    await blob.UploadAsync(
        input,
        new BlobUploadOptions
        {
            HttpHeaders = new BlobHttpHeaders
            {
                ContentType = safeContentType
            },
            Metadata = new Dictionary<string, string>
            {
                ["fileId"] = fileId.ToString("N")
            }
        },
        cancellationToken);

    _logger.LogInformation(
        "Upload completed {FileId} {TenantId} {Bytes}",
        fileId, tenantId, file.Length);

    return CreatedAtAction(
        nameof(GetFile),
        new { id = fileId },
        new { id = fileId });
}
```

Trong hệ thống tải file rất lớn hoặc concurrency cao, còn cần đánh giá direct-to-Blob upload bằng scoped SAS thay vì proxy toàn bộ bytes qua API. SAS phải ngắn hạn, giới hạn permission/path/content policy phù hợp; backend vẫn giữ authorization và metadata workflow.

## Giải thích thiết kế sau khi sửa

Storage key do server sinh và namespace theo tenant. API không dùng original filename làm identity. Payload được stream thay vì tạo thêm full-size managed buffer. Cancellation được propagate. Validation và access model được coi là security boundary riêng.

## Trade-offs

Proxy streaming qua API đơn giản hóa authorization và scanning nhưng vẫn tiêu tốn App Service bandwidth/connections. Direct upload giảm tải backend nhưng làm flow phức tạp hơn: SAS issuance, completion verification, scanning/quarantine và cleanup orphaned blobs. Content inspection có thể cần staging thay vì stream thẳng vào vùng trusted.

## Cách kiểm thử

1. Integration test upload file sát size limit và vượt limit.
2. Concurrency/load test nhiều large uploads, quan sát memory/GC và throughput.
3. Failure-path test client abort giữa upload, xác minh operation dừng/cleanup policy.
4. Security test filename/MIME giả, cross-tenant access và unauthorized download.
5. Integration test Blob transient failure/retry và idempotency semantics.

## Quan sát trong production

Theo dõi request p95/p99, concurrent uploads, bytes uploaded, process memory, allocation/GC, App Service restarts, request cancellations, Blob dependency duration/failure/throttling và completion ratio. Correlate bằng upload ID; không log file contents hoặc secrets.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn direct-to-Blob SAS thay vì proxy qua ASP.NET Core?
2. Nếu cần antivirus scan trước khi file được tải xuống, lifecycle của blob nên thiết kế thế nào?
3. Nếu Blob Storage chậm nhưng API instances vẫn khỏe, bạn giới hạn concurrency/backpressure ở đâu?

# Code Review Challenge 2 — Kubernetes rolling deployment tạo restart loop dù ứng dụng không lỗi

**Chủ đề:** Kubernetes, ASP.NET Core health checks, deployment stability, resource management, configuration, graceful shutdown  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API chuyển từ Azure App Service sang Kubernetes. Deployment thành công ở staging nhưng production có pod restart liên tục trong giờ cao điểm. Khi release, một số request bị 5xx. Startup cần khoảng 35–60 giây vì warm-up metadata; endpoint `/health` kiểm tra cả SQL Server và một third-party API. Third-party đôi lúc chậm 10–15 giây nhưng API vẫn có thể phục vụ nhiều endpoint không phụ thuộc trực tiếp vào nó.

## Đoạn code cần review

```yaml

  name: catalog-api

  replicas: 4
  strategy:
    type: RollingUpdate
```

4. Phân tích resource requests/limits dựa trên evidence thay vì đoán.

## Kết quả code review tham khảo

### Critical — Production database credential nằm trực tiếp trong manifest

**Vấn đề:** Username/password được commit/deploy dưới dạng plain environment value.  
**Tại sao xảy ra:** Configuration và secret management bị trộn vào deployment manifest.  
**Ảnh hưởng production:** Secret leakage qua repository, CI logs, manifest access hoặc operational tooling.  
**Cách sửa:** Dùng Kubernetes Secret/external secret integration hoặc workload identity/managed identity khi platform hỗ trợ; áp dụng least privilege và rotation.

### High — Liveness phụ thuộc SQL và third-party

**Vấn đề:** `/health` fail khi dependency chậm.  
**Tại sao xảy ra:** Một endpoint dùng cho cả monitoring, readiness và liveness.  
**Ảnh hưởng production:** Kubernetes restart process khỏe chỉ vì dependency degraded, tạo restart storm và tăng tải dependency.  
**Cách sửa:** Liveness chỉ kiểm tra process có khả năng tiếp tục hoạt động; dependency checks thường phù hợp readiness/diagnostics tùy semantics.

### High — Không có startupProbe cho startup 35–60 giây

**Vấn đề:** Liveness bắt đầu sau 5 giây.  
**Tại sao xảy ra:** Probe window ngắn hơn startup behavior thực tế.  
**Ảnh hưởng production:** Container bị kill trước khi startup hoàn tất.  
**Cách sửa:** Dùng `startupProbe` với budget dựa trên measured startup distribution; sau khi startup success mới để liveness/readiness đảm nhiệm.

### High — Readiness quá nhạy và dùng cùng dependency set

**Vấn đề:** Một timeout 2 giây với failureThreshold 1 loại pod khỏi traffic ngay.  
**Tại sao xảy ra:** Probe không phản ánh khả năng phục vụ request thực tế.  
**Ảnh hưởng production:** Transient dependency latency làm capacity giảm đồng loạt.  
**Cách sửa:** Readiness chỉ fail khi pod thực sự không nên nhận traffic; chọn threshold/timeouts từ SLO và failure semantics.

### High — Image tag `latest`

**Vấn đề:** Artifact không immutable/traceable.  
**Tại sao xảy ra:** Tag mutable không định danh chính xác image đã chạy.  
**Ảnh hưởng production:** Rollback/audit khó; các pod có thể lấy image khác nhau theo registry/cache timing.  
**Cách sửa:** Deploy immutable version tag hoặc digest.

### Medium — Resource values không có evidence

**Vấn đề:** CPU/memory limit có thể quá thấp.  
**Tại sao xảy ra:** Không dựa trên profiling/load metrics.  
**Ảnh hưởng production:** CPU throttling hoặc OOMKilled có thể bị nhầm thành application bug.  
**Cách sửa:** Baseline CPU, working set, GC, p95/p99 dưới load rồi đặt requests/limits có headroom phù hợp.

### Medium — RollingUpdate safety chưa explicit

**Vấn đề:** Không đặt `maxUnavailable`, `maxSurge`, `minReadySeconds` theo availability requirement.  
**Tại sao xảy ra:** Dùng defaults mà chưa kiểm tra startup/readiness behavior.  
**Ảnh hưởng production:** Capacity giảm trong rollout hoặc pod mới được coi là ready quá sớm.  
**Cách sửa:** Chọn rollout parameters theo replica count, startup time và SLO.

### Medium — Thiếu graceful termination design

**Vấn đề:** Manifest không thể hiện shutdown budget/preStop strategy; application behavior chưa xác minh.  
**Tại sao xảy ra:** Chỉ tập trung startup.  
**Ảnh hưởng production:** Pod bị terminate khi còn request đang xử lý.  
**Cách sửa:** Propagate SIGTERM cancellation, stop nhận traffic, drain inflight work và đặt termination grace period theo measured behavior.

## Giải thích thiết kế sau khi sửa

`startupProbe` bảo vệ startup chậm khỏi liveness kill. `livenessProbe` trả lời “process có cần restart không?”. `readinessProbe` trả lời “pod có nên nhận traffic lúc này không?”. Chúng không nên dùng chung dependency policy một cách máy móc. Image immutable giúp audit/rollback. Secret được tách khỏi manifest; production tốt hơn nữa có thể dùng external secret/workload identity tùy platform.

## Trade-offs

Readiness quá permissive có thể gửi traffic vào pod không phục vụ được; quá strict có thể loại toàn bộ capacity khi shared dependency degraded. Startup budget quá dài làm phát hiện startup failure chậm; quá ngắn tạo restart loop. Bỏ CPU limit có thể tránh throttling nhưng cần cluster governance phù hợp; đặt limit phải dựa trên workload và platform policy.

## Cách kiểm thử

1. Deployment test với startup cố ý 60 giây: pod không bị liveness restart.
2. Failure injection làm third-party timeout: xác minh process không restart nếu vẫn healthy.
3. Load test rollout 4 replicas: theo dõi 5xx và available capacity.
4. Memory/CPU stress test để xác định OOM/throttling thresholds.
5. Graceful shutdown test với inflight requests khi pod nhận SIGTERM.

## Quan sát trong production

Theo dõi pod restart count/reason, OOMKilled, CPU throttling, working set, GC, readiness transitions, startup duration, rollout duration, request p95/p99/5xx và dependency telemetry trong Application Insights. Alert nên phân biệt process failure với dependency degradation.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào dependency database nên nằm trong readiness probe, và khi nào không?
2. Nếu tất cả replicas cùng fail readiness vì một shared dependency, Service sẽ hành xử thế nào và user impact ra sao?
3. Bạn chọn requests/limits thế nào từ load-test và production telemetry thay vì copy cấu hình từ service khác?
