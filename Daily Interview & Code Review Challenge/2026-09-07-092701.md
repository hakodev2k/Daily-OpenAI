# Code Review Challenge 1 — Search index “thỉnh thoảng đúng, thỉnh thoảng thiếu” sau khi update product

**Chủ đề:** C#/.NET, Elasticsearch, SQL Server, eventual consistency, async integration, failure handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một e-commerce backend dùng SQL Server làm source of truth cho product catalog và Elasticsearch để phục vụ full-text search.

Flow hiện tại:

- admin cập nhật product qua ASP.NET Core API;
- API lưu product vào SQL Server bằng EF Core;
- ngay trong request đó, API gọi Elasticsearch để index document;
- storefront search chỉ đọc từ Elasticsearch;
- hệ thống chạy 6 application instances trên Azure App Service;
- traffic update không lớn, nhưng bulk import có thể update hàng chục nghìn product trong vài phút;
- production ghi nhận:
  - API update đôi khi trả 500 dù product đã được lưu trong SQL;
  - có product đã update trong SQL nhưng search vẫn hiển thị dữ liệu cũ;
  - retry request có lúc tạo nhiều index operation gần nhau;
  - bulk import làm p95 API latency tăng mạnh;
  - khi Elasticsearch chậm, request thread tăng và App Service scale-out nhiều hơn;
  - support khó xác định một product search document được index từ version nào của SQL row.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductService
{
    private readonly AppDbContext _db;
    private readonly IElasticsearchClient _search;
    private readonly ILogger<ProductService> _logger;

    public ProductService(
        AppDbContext db,
        IElasticsearchClient search,
        ILogger<ProductService> logger)
    {
        _db = db;
        _search = search;
        _logger = logger;
    }

    public async Task<ProductDto> UpdateAsync(
        Guid productId,
        UpdateProductRequest request)
    {
        var product = await _db.Products
            .SingleAsync(x => x.Id == productId);

        product.Name = request.Name;
        product.Description = request.Description;
        product.Price = request.Price;
        product.UpdatedUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        try
        {
            var document = new ProductSearchDocument
            {
                Id = product.Id,
                Name = product.Name,
                Description = product.Description,
                Price = product.Price,
                UpdatedUtc = product.UpdatedUtc
            };

            var response = await _search.IndexAsync(
                document,
                indexName: "products");

            if (!response.IsValid)
            {
                throw new InvalidOperationException(
                    response.ErrorReason ?? "Indexing failed");
            }

            await _search.RefreshAsync("products");
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Product indexing failed for {ProductId}",
                product.Id);

            throw;
        }

        return new ProductDto(
            product.Id,
            product.Name,
            product.Price,
            product.UpdatedUtc);
    }
}
```

Controller:

```csharp
[HttpPut("api/products/{productId:guid}")]
public async Task<ActionResult<ProductDto>> Update(
    Guid productId,
    UpdateProductRequest request)
{
    var result = await _productService.UpdateAsync(productId, request);
    return Ok(result);
}
```

## Nhiệm vụ của ứng viên

Hãy review implementation này như một Senior .NET Developer phụ trách cả API reliability và search correctness.

Bạn cần:

1. xác định correctness problems;
2. phân tích transaction boundary giữa SQL Server và Elasticsearch;
3. phân tích failure sau `SaveChangesAsync` nhưng trước/sau index operation;
4. đánh giá việc gọi Elasticsearch synchronously trong request path;
5. đánh giá `RefreshAsync` sau từng document;
6. đánh giá retry và duplicate indexing;
7. phân tích stale document / out-of-order update risk;
8. đề xuất architecture tốt hơn nhưng không over-engineer;
9. giải thích testing;
10. giải thích telemetry để điều tra lag giữa SQL và search.

## Câu hỏi gợi mở

1. Nếu SQL commit thành công nhưng Elasticsearch timeout thì API nên trả success hay failure?
2. Nếu client thấy 500 rồi retry cùng update, điều gì có thể xảy ra với SQL và search document?
3. Hai request update cùng product gần nhau có thể index out-of-order không?
4. `RefreshAsync` sau mỗi write giải quyết consistency hay chỉ làm search visibility nhanh hơn?
5. Nếu Elasticsearch unavailable 20 phút, hệ thống có cách nào tự repair index sau khi service hồi phục không?

## Kết quả code review tham khảo

### Critical — Dual-write giữa SQL Server và Elasticsearch không atomic

**Vấn đề:**  
`SaveChangesAsync()` commit SQL trước, sau đó mới index Elasticsearch.

**Tại sao xảy ra:**  
SQL Server transaction không bao phủ Elasticsearch. Hai hệ thống có failure boundary độc lập.

**Ảnh hưởng production:**  
SQL có thể chứa version mới trong khi Elasticsearch vẫn chứa version cũ hoặc không có document. API có thể trả 500 dù business update thực tế đã commit thành công.

**Cách sửa:**  
Chọn SQL làm source of truth và persist một durable change event cùng transaction với product update, ví dụ Outbox record. Một background consumer đọc outbox rồi cập nhật Elasticsearch. Không cố giả lập distributed transaction giữa SQL và Elasticsearch.

---

### High — Throw sau khi SQL đã commit tạo response semantics gây hiểu nhầm

**Vấn đề:**  
Nếu indexing fail, method `throw` làm controller trả 5xx dù product update đã commit.

**Tại sao xảy ra:**  
API coi search indexing là một phần atomic của product update trong khi thực tế không atomic.

**Ảnh hưởng production:**  
Client có thể retry vì tưởng update chưa xảy ra. Retry có thể tạo thêm write, thay đổi `UpdatedUtc` và phát sinh nhiều indexing attempt.

**Cách sửa:**  
Tách business commit khỏi search propagation. Nếu requirement cho phép eventual consistency, API trả success sau SQL commit và expose search propagation state/lag qua observability. Nếu search freshness là hard requirement, phải thiết kế workflow/status rõ hơn thay vì trả 500 giả định toàn bộ operation rollback.

---

### High — Không có durable retry khi Elasticsearch unavailable

**Vấn đề:**  
Failure chỉ được log rồi throw.

**Tại sao xảy ra:**  
Không có queue, outbox, retry store hoặc reconciliation source.

**Ảnh hưởng production:**  
Khi Elasticsearch outage, product đã commit trong SQL có thể không bao giờ được index lại nếu client không retry đúng product.

**Cách sửa:**  
Persist pending index work durably. Consumer retry transient failure với backoff và DLQ/failed state phù hợp. Có reconciliation job để so sánh/index lại từ SQL khi cần.

---

### High — Out-of-order indexing có thể ghi version cũ đè version mới

**Vấn đề:**  
Hai update gần nhau có thể hoàn tất Elasticsearch write theo thứ tự khác với SQL commit order.

**Tại sao xảy ra:**  
Network latency và concurrent request không đảm bảo order giữa external write operations.

**Ảnh hưởng production:**  
Search document có thể quay về state cũ dù SQL đã có state mới.

**Cách sửa:**  
Gắn version/sequence từ source of truth, ví dụ rowversion hoặc monotonic update version. Consumer chỉ cho phép update search document nếu event version mới hơn version đã index. Nếu client library/index design hỗ trợ optimistic concurrency phù hợp thì tận dụng; nếu không, kiểm tra version trong consumer/document metadata.

---

### High — Synchronous search indexing làm tăng latency và coupling

**Vấn đề:**  
API request phải chờ Elasticsearch hoàn tất.

**Tại sao xảy ra:**  
Search propagation được đặt trong request path.

**Ảnh hưởng production:**  
Elasticsearch latency trực tiếp trở thành API latency. Khi search cluster chậm, request duration tăng, connection giữ lâu hơn và hệ thống bị cascading degradation.

**Cách sửa:**  
Nếu requirement chấp nhận eventual consistency, chuyển indexing sang asynchronous pipeline. API update latency chỉ phụ thuộc transaction chính.

---

### High — `RefreshAsync` sau mỗi document làm write path đắt và giảm throughput

**Vấn đề:**  
Mỗi update gọi explicit refresh toàn index.

**Tại sao xảy ra:**  
Code cố ép document searchable ngay lập tức sau từng write.

**Ảnh hưởng production:**  
Trong bulk import, rất nhiều refresh làm tăng overhead, giảm indexing throughput và tăng latency.

**Cách sửa:**  
Không refresh sau từng document mặc định. Xác định freshness SLA thực tế. Để search engine refresh theo lifecycle phù hợp hoặc batch/bulk indexing khi workload cần. Chỉ dùng stronger visibility behavior khi product requirement thực sự yêu cầu.

---

### High — Bulk import dùng per-document request pattern

**Vấn đề:**  
Mỗi product update tạo một network round trip index + refresh.

**Tại sao xảy ra:**  
Write model không phân biệt interactive update với bulk workload.

**Ảnh hưởng production:**  
Hàng chục nghìn updates tạo lượng request lớn, tăng p95/p99 và pressure lên search cluster.

**Cách sửa:**  
Consumer có thể batch/bulk index nhiều pending changes khi phù hợp, nhưng vẫn giữ version/idempotency semantics.

---

### Medium — Không propagate `CancellationToken`

**Vấn đề:**  
EF Core và Elasticsearch call không nhận request cancellation.

**Tại sao xảy ra:**  
Method signature không có `CancellationToken`.

**Ảnh hưởng production:**  
Client disconnect nhưng request có thể tiếp tục chờ external dependency. Trong architecture mới, cancellation chỉ nên điều khiển request path; durable outbox work không được mất chỉ vì client disconnect sau commit.

**Cách sửa:**  
Propagate cancellation trước commit. Sau khi transaction đã commit, durable outbox bảo đảm propagation tiếp tục độc lập với request lifecycle.

---

### Medium — Không có concurrency control khi update product

**Vấn đề:**  
Hai admin có thể cùng load row rồi `SaveChangesAsync()` theo last-write-wins ngoài ý muốn.

**Tại sao xảy ra:**  
Không có concurrency token/version check trong scenario hiện tại.

**Ảnh hưởng production:**  
Một update có thể ghi đè update khác mà không cảnh báo, đồng thời làm search version reasoning khó hơn.

**Cách sửa:**  
Nếu business yêu cầu phát hiện conflicting edit, dùng optimistic concurrency token/rowversion và trả conflict semantics phù hợp.

---

### Medium — Observability thiếu version và propagation latency

**Vấn đề:**  
Log chỉ có `ProductId` khi indexing fail.

**Tại sao xảy ra:**  
Không log source version, event ID, attempt count hay duration.

**Ảnh hưởng production:**  
Khó xác định search document hiện tại đến từ update nào và lag bao lâu so với SQL.

**Cách sửa:**  
Log/metric theo `ProductId`, source version, outbox/event ID, attempt, duration, index result và search propagation lag.

## Phiên bản đề xuất

Ví dụ đơn giản dùng Outbox Pattern trong cùng transaction với product update:

```csharp
public async Task<ProductDto> UpdateAsync(
    Guid productId,
    UpdateProductRequest request,
    CancellationToken cancellationToken)
{
    var product = await _db.Products
        .SingleAsync(x => x.Id == productId, cancellationToken);

    product.Name = request.Name;
    product.Description = request.Description;
    product.Price = request.Price;
    product.UpdatedUtc = DateTime.UtcNow;
    product.Version++;

    _db.OutboxMessages.Add(new OutboxMessage
    {
        Id = Guid.NewGuid(),
        Type = "ProductSearchIndexRequested",
        AggregateId = product.Id,
        Version = product.Version,
        Payload = JsonSerializer.Serialize(new
        {
            product.Id,
            product.Version
        }),
        CreatedUtc = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(cancellationToken);

    return new ProductDto(
        product.Id,
        product.Name,
        product.Price,
        product.UpdatedUtc);
}
```

Background processor:

```csharp
public async Task HandleAsync(
    ProductSearchIndexRequested message,
    CancellationToken cancellationToken)
{
    var product = await _db.Products
        .AsNoTracking()
        .SingleOrDefaultAsync(
            x => x.Id == message.ProductId,
            cancellationToken);

    if (product is null)
    {
        await _search.DeleteIfOlderOrEqualAsync(
            message.ProductId,
            message.Version,
            cancellationToken);
        return;
    }

    var document = new ProductSearchDocument
    {
        Id = product.Id,
        Name = product.Name,
        Description = product.Description,
        Price = product.Price,
        Version = product.Version,
        UpdatedUtc = product.UpdatedUtc
    };

    await _search.UpsertIfNewerAsync(
        document,
        cancellationToken);
}
```

`UpsertIfNewerAsync` ở đây là abstraction của application, không giả định một API cụ thể. Requirement quan trọng là consumer phải chống stale/out-of-order write dựa trên version của source.

## Giải thích thiết kế sau khi sửa

### 1. SQL là source of truth

Search index là read model có thể rebuild. Business update không phụ thuộc availability tức thời của Elasticsearch.

### 2. Outbox giải quyết mất event sau commit

Product change và outbox record được persist trong cùng relational transaction. Nếu app crash sau commit, worker vẫn có durable work để xử lý.

### 3. Consumer phải idempotent và version-aware

Retry cùng event không được làm sai state. Event cũ đến sau event mới cũng không được ghi đè document mới.

### 4. Reconciliation là safety net

Có thể chạy periodic job để kiểm tra missing/stale documents hoặc rebuild index từ SQL khi cần.

## Trade-offs

- Eventual consistency nghĩa là search có thể trễ so với admin UI trong một khoảng thời gian.
- Outbox thêm table, cleanup và background processor.
- Version-aware indexing làm implementation phức tạp hơn direct index call nhưng đổi lại correctness rõ ràng.
- Bulk indexing tăng throughput nhưng cần kiểm soát batch size, retry và partial failure.
- Nếu system nhỏ, một worker trong cùng application có thể đủ; không cần thêm message broker chỉ để có architecture “đẹp”.

## Cách kiểm thử

1. **Integration test — SQL success, Elasticsearch down:** update phải commit, outbox còn pending và được index sau khi search hồi phục.
2. **Ordering test:** event version 12 xử lý trước version 11; document cuối cùng vẫn phải là version 12.
3. **Idempotency test:** cùng event xử lý nhiều lần không làm sai state hoặc tạo duplicate semantic.
4. **Load test:** bulk update nhiều nghìn product; đo API p95/p99, outbox backlog và indexing throughput.
5. **Reconciliation test:** xóa một document khỏi Elasticsearch rồi chạy reconciliation; index được repair từ SQL.

## Quan sát trong production

Theo dõi:

- outbox pending count;
- oldest pending age;
- indexing success/failure rate;
- retry count;
- Elasticsearch dependency duration;
- bulk batch size và partial failure count;
- search propagation lag từ SQL version tới indexed version;
- count stale event bị bỏ qua;
- reconciliation mismatch count;
- p95/p99 update API latency;
- correlation giữa `ProductId`, source version, outbox ID và trace ID.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product bị delete trong SQL, bạn sẽ propagate delete tới Elasticsearch thế nào để không resurrect document cũ?
2. Khi nào bạn dùng Azure Service Bus giữa outbox publisher và search consumer thay vì worker trực tiếp đọc outbox?
3. Nếu business yêu cầu search phải reflect update trong dưới 1 giây, bạn sẽ đo và thiết kế SLA đó thế nào mà không quay lại dual-write brittle?

# Code Review Challenge 2 — Deployment script “chạy được” nhưng migration và rollback có thể phá production

**Chủ đề:** TeamCity, Octopus Deploy, IIS/Windows Server, CI/CD, database migration, configuration, rollback, release safety  
**Độ khó:** Senior

## Bối cảnh

Một enterprise management portal vẫn chạy trên IIS/Windows Server. Team dùng TeamCity để build artifact và Octopus Deploy để release lên 4 web servers sau load balancer.

Application đang được migrate dần từ .NET Framework sang modern .NET, nhưng deployment hiện tại vẫn dùng một PowerShell step chung cho tất cả environment.

Production topology:

- 4 IIS nodes;
- shared SQL Server database;
- load balancer route traffic tới tất cả healthy nodes;
- deployment package chứa application binaries và EF Core migration executable;
- release gần đây gặp các vấn đề:
  - một node chạy version mới trong khi node khác vẫn version cũ;
  - migration chạy nhiều lần;
  - rollback application thành công nhưng database schema không rollback tương ứng;
  - secret production từng xuất hiện trong deployment log;
  - có request 500 trong lúc file đang được copy;
  - release pipeline đôi khi lấy artifact “latest successful” thay vì artifact đã được QA approve.

Deployment step hiện tại:

## Đoạn code cần review

```powershell
$ErrorActionPreference = "Continue"

$package = "C:\packages\Portal-latest.zip"
$siteName = "EnterprisePortal"
$deployPath = "C:\inetpub\EnterprisePortal"

Write-Host "Deploying package: $package"
Write-Host "DB connection: $env:PORTAL_DB_CONNECTION"

Import-Module WebAdministration

Expand-Archive -Path $package `
    -DestinationPath $deployPath `
    -Force

Set-Location $deployPath

if (Test-Path ".\Portal.Migrations.exe") {
    .\Portal.Migrations.exe `
        --connection "$env:PORTAL_DB_CONNECTION"
}

Restart-WebAppPool -Name $siteName

Invoke-WebRequest `
    -Uri "http://localhost/health" `
    -UseBasicParsing

Write-Host "Deployment completed"
```

TeamCity build configuration cũng publish artifact theo tên cố định:

```text

Deployment trigger: deploy latest successful build
```

## Kết quả code review tham khảo

### Critical — Secret database connection bị ghi ra deployment log

**Vấn đề:**  
Script `Write-Host` toàn bộ `PORTAL_DB_CONNECTION`.

**Tại sao xảy ra:**  
Deployment log thường được lưu, search và truy cập bởi nhiều role hơn production secret store.

**Ảnh hưởng production:**  
Credential có thể bị lộ trong build/deploy history và tồn tại lâu ngay cả khi release đã kết thúc.

**Cách sửa:**  
Không log secret. Dùng sensitive/secret variable của deployment system và đảm bảo command/tool không echo secret. Rotate credential nếu đã từng lộ.

---

### Critical — Mutable artifact `Portal-latest.zip` phá traceability

**Vấn đề:**  
Build output luôn dùng tên `latest` và deployment trigger lấy “latest successful build”.

**Tại sao xảy ra:**  
Artifact identity không gắn immutable với commit/build/release đã QA approve.

**Ảnh hưởng production:**  
Production có thể deploy package khác package đã test. Rollback cũng khó xác định chính xác binary nào từng chạy.

**Cách sửa:**  
Artifact phải immutable và versioned, ví dụ theo build number + commit SHA. Promote chính artifact đã qua QA từ environment trước sang production, không rebuild/re-resolve “latest”.

---

### High — Migration có thể chạy trên mọi IIS node

**Vấn đề:**  
Mỗi node chạy cùng script và mỗi script có thể execute `Portal.Migrations.exe`.

**Tại sao xảy ra:**  
Database là shared resource nhưng migration ownership gắn với node deployment step.

**Ảnh hưởng production:**  
Nhiều migration process có thể tranh schema lock, fail ngẫu nhiên hoặc cùng cố apply migration. Với custom migration tool không idempotent, rủi ro lớn hơn.

**Cách sửa:**  
Tách migration thành một release step duy nhất với ownership rõ ràng trước/giữa rollout theo plan. Chỉ application rollout chạy per-node.

---

### High — In-place unzip vào live directory tạo mixed-version state

**Vấn đề:**  
`Expand-Archive -Force` ghi trực tiếp vào folder IIS đang serve.

**Tại sao xảy ra:**  
Trong khoảng copy, một request có thể load tập file cũ + mới không đồng nhất.

**Ảnh hưởng production:**  
Có thể phát sinh runtime exception, missing assembly/static asset mismatch hoặc transient 500.

**Cách sửa:**  
Drain node khỏi load balancer, stop/disable app pool hoặc deploy vào versioned staging directory rồi switch application path/symlink theo cơ chế kiểm soát. Chỉ đưa node trở lại traffic sau health verification.

---

### High — `$ErrorActionPreference = "Continue"` có thể che failure

**Vấn đề:**  
Script tiếp tục sau lỗi ở một số command.

**Tại sao xảy ra:**  
Pipeline không fail-fast theo step critical.

**Ảnh hưởng production:**  
Migration, unzip hoặc health check có thể fail nhưng script vẫn đi tiếp và ghi “Deployment completed”.

**Cách sửa:**  
Dùng fail-fast cho command critical, check exit code và explicit exception handling chỉ ở nơi có recovery logic thật.

---

### High — Rollback binary không đồng nghĩa rollback schema

**Vấn đề:**  
Team có thể restore app package cũ nhưng database migration đã thay schema.

**Tại sao xảy ra:**  
Release plan xem app và DB như hai artifact độc lập có thể đảo ngược tùy ý.

**Ảnh hưởng production:**  
Old version có thể không tương thích schema mới, khiến rollback làm outage nặng hơn.

**Cách sửa:**  
Thiết kế migration backward-compatible theo expand/contract khi cần zero-downtime. Rollback strategy thường là roll-forward application hoặc giữ schema tương thích, không mặc định chạy down migration destructive trong incident.

---

### High — Không có staged rollout / capacity protection

**Vấn đề:**  
Script không thể hiện drain, canary hoặc sequential node gate.

**Tại sao xảy ra:**  
Deployment coi 4 nodes như các copy độc lập thay vì một serving fleet.

**Ảnh hưởng production:**  
Nhiều node có thể cùng unavailable hoặc cùng nhận bad release trước khi health signal được đánh giá.

**Cách sửa:**  
Rollout từng node hoặc small batch: remove/drain khỏi load balancer → deploy → startup → health check → synthetic request → đưa lại traffic → quan sát → tiếp tục node kế tiếp.

---

### High — Health check quá hẹp

**Vấn đề:**  
Chỉ gọi `http://localhost/health`.

**Tại sao xảy ra:**  
Local process health không chứng minh DNS/load balancer/TLS/config/runtime integration đúng.

**Ảnh hưởng production:**  
Node có thể pass localhost nhưng fail external route hoặc critical dependency.

**Cách sửa:**  
Dùng nhiều gate: process/startup health, dependency-critical readiness nếu phù hợp, và synthetic request qua route gần giống production traffic. Không để optional dependency biến health check thành false outage.

---

### Medium — Không verify package integrity/version trước deploy

**Vấn đề:**  
Script chỉ đọc file path cố định.

**Tại sao xảy ra:**  
Không check expected build metadata/hash/version.

**Ảnh hưởng production:**  
Có thể deploy nhầm package hoặc package bị thay thế.

**Cách sửa:**  
Pipeline truyền explicit artifact version và verify manifest/hash/signature theo capability hiện có.

---

### Medium — Restart app pool không có graceful drain semantics

**Vấn đề:**  
App pool bị restart sau khi file đã ghi.

**Tại sao xảy ra:**  
Không tách traffic draining khỏi process lifecycle.

**Ảnh hưởng production:**  
In-flight request có thể fail; user nhận 5xx hoặc partial operation.

**Cách sửa:**  
Drain traffic trước deployment và chờ in-flight request theo timeout phù hợp. Sau deploy mới start và health-check node.

---

### Medium — Không có release metadata trong telemetry

**Vấn đề:**  
Script không publish version/commit/release ID để correlate với logs/metrics.

**Tại sao xảy ra:**  
Artifact được coi như file, không phải release identity.

**Ảnh hưởng production:**  
Incident team khó biết request lỗi chạy trên node/version nào.

**Cách sửa:**  
Expose release version trong application telemetry, structured logs, health/info endpoint và deployment annotations.

## Phiên bản đề xuất

Ví dụ deployment flow ở mức script/pipeline, vẫn giữ IIS + TeamCity + Octopus:

```powershell
$ErrorActionPreference = "Stop"

$releaseVersion = $OctopusParameters["Release.Version"]
$packagePath = $OctopusParameters["Package.Path"]
$siteName = "EnterprisePortal"
$stagingPath = "C:\deploy\EnterprisePortal\$releaseVersion"
$currentPath = "C:\inetpub\EnterprisePortal"

Write-Host "Deploying EnterprisePortal version $releaseVersion"

if (-not (Test-Path $packagePath)) {
    throw "Package not found: $packagePath"
}

New-Item -ItemType Directory -Force -Path $stagingPath | Out-Null
Expand-Archive -Path $packagePath -DestinationPath $stagingPath -Force

& "C:\ops\Drain-Node.ps1" -Site $siteName

Stop-WebAppPool -Name $siteName

try {
    & "C:\ops\Switch-PortalVersion.ps1" `
        -Source $stagingPath `
        -Target $currentPath

    Start-WebAppPool -Name $siteName

    & "C:\ops\Wait-ForHealth.ps1" `
        -Url "http://localhost/health/live" `
        -TimeoutSeconds 60

    & "C:\ops\Synthetic-Check.ps1" `
        -Url "https://portal.example.internal/health/ready"

    & "C:\ops\Enable-Node.ps1" -Site $siteName
}
catch {
    Write-Error $_
    throw
}
```

Database migration không nằm trong per-node script. Pipeline nên có flow khái niệm:

```text
Build once
→ create immutable artifact
→ QA deploy/test same artifact
→ approve exact artifact version
→ run one database compatibility migration step
→ deploy node 1 + health gate
→ observe
→ deploy node 2
→ deploy node 3
→ deploy node 4
→ post-deploy validation
```

Nếu migration destructive, cần tách expand/contract qua nhiều release thay vì chạy destructive schema change trước khi old version rời fleet.

## Giải thích thiết kế sau khi sửa

### 1. Build once, promote same artifact

Một binary đã QA test phải là binary production nhận. Không dùng `latest successful` làm deployment contract.

### 2. Migration có single owner

Database là shared dependency nên migration là release-level step, không phải node-level step.

### 3. Drain trước, switch sau

Node không nhận traffic khi binary đang thay đổi. Health pass rồi mới quay lại load balancer.

### 4. Rollback được thiết kế cùng schema compatibility

Không giả định database luôn có thể down-migrate an toàn. Backward-compatible migration giúp app version cũ và mới cùng tồn tại trong rollout window.

## Trade-offs

- Sequential rollout chậm hơn deploy đồng thời nhưng giảm blast radius.
- Staging/versioned directories dùng thêm disk space.
- Expand/contract migration cần nhiều release hơn nhưng giúp zero-downtime và rollback an toàn hơn.
- Health gate phức tạp hơn localhost ping nhưng phát hiện nhiều lớp failure hơn.
- Immutable artifact discipline yêu cầu pipeline quản lý version rõ ràng, đổi lại traceability tốt hơn.

## Cách kiểm thử

1. **Deployment validation:** deploy một node trong staging environment bằng đúng pipeline production-like; xác minh drain/switch/health/re-enable hoạt động.
2. **Failure-path test:** cố tình làm health check fail; pipeline phải dừng trước các node tiếp theo.
3. **Migration compatibility test:** chạy old app và new app cùng schema sau expand migration; cả hai phải hoạt động trong rollout window.
4. **Rollback rehearsal:** deploy version N+1 rồi rollback binary về N khi schema đã ở trạng thái backward-compatible.
5. **Security test:** kiểm tra deployment logs không chứa connection string, secret hoặc token.

## Quan sát trong production

Theo dõi:

- release version theo từng IIS node;
- request 5xx theo node/version;
- p95/p99 latency trong rollout;
- health-check failure;
- load balancer healthy node count;
- app pool restart count;
- migration duration/status;
- SQL blocking/deadlock trong migration window;
- deployment step duration;
- synthetic-check pass/fail;
- release annotation trong Application Insights/Kibana;
- error-rate delta trước và sau từng node rollout.

## Câu hỏi phỏng vấn mở rộng

1. Nếu migration cần rename một column đang được old version đọc, bạn sẽ chia expand/contract qua các release nào?
2. Nếu node 1 pass health nhưng error rate tăng nhẹ sau 10 phút, bạn đặt release gate tiếp theo dựa trên signal nào?
3. Khi nào blue/green deployment đáng dùng cho IIS fleet này, và khi nào sequential rolling deployment đơn giản hơn là đủ?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Elasticsearch nên được xem như read model/search projection, không phải transaction partner của SQL Server.
- Dual-write trực tiếp giữa database và external index tạo partial-failure window; durable propagation như Outbox giúp repair được failure.
- Retry chỉ an toàn khi consumer/idempotency/version semantics được thiết kế rõ.
- Search consistency cần phân biệt **source consistency**, **indexing order** và **search visibility**; `refresh` không giải quyết transaction atomicity.
- CI/CD reliability phụ thuộc artifact immutability, migration ownership, rollout blast radius và rollback compatibility.
- Database migration là release-level concern; không nên để mỗi application node tự quyết định schema change.
- “Rollback app” không luôn đồng nghĩa “rollback database”. Backward-compatible expand/contract thường an toàn hơn destructive down migration trong incident.

## Mẫu tư duy cần nhớ

1. **Treat external read models as rebuildable projections, not transactional peers.**
2. **Design retry together with idempotency and ordering.**
3. **Build once, promote the exact same artifact.**
4. **Own database migration once per release, not once per node.**
5. **Reduce blast radius before optimizing deployment speed.**
