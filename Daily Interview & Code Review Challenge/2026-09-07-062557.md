# Code Review Challenge 1 — Service Bus consumer xử lý thanh toán hai lần khi lock hết hạn và retry

**Chủ đề:** C#/.NET, Azure Service Bus, at-least-once delivery, message settlement, idempotency, EF Core, external API integration, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một e-commerce backend nhận message `OrderPaymentRequested` từ Azure Service Bus. Consumer chịu trách nhiệm:

- kiểm tra order trong SQL Server;
- gọi payment provider bên ngoài để charge thẻ đã tokenized;
- cập nhật order sang `Paid`;
- gửi email xác nhận;
- complete message sau khi xử lý thành công.

Hệ thống chạy nhiều instance trên Azure App Service. Service Bus dùng Peek Lock. Bình thường mỗi message xử lý trong 2–8 giây, nhưng payment provider đôi khi chậm 45–90 giây. Network giữa application và Azure Service Bus cũng có lúc gián đoạn ngắn.

Production gần đây ghi nhận:

- một số order bị charge hai lần;
- cùng một `OrderId` xuất hiện nhiều log entry với `DeliveryCount` khác nhau;
- có message bị xử lý business logic thành công nhưng sau đó `CompleteMessageAsync` fail;
- một số poison message bị retry rất nhiều lần trước khi vào DLQ;
- khi scale out, cùng order đôi khi được hai instance xử lý gần nhau;
- email confirmation đôi khi gửi trùng;
- support khó xác định một lần charge cụ thể đến từ message delivery nào.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class PaymentMessageHandler
{
    private readonly AppDbContext _db;
    private readonly IPaymentGateway _payments;
    private readonly IEmailSender _email;
    private readonly ILogger<PaymentMessageHandler> _logger;

    public PaymentMessageHandler(
        AppDbContext db,
        IPaymentGateway payments,
        IEmailSender email,
        ILogger<PaymentMessageHandler> logger)
    {
        _db = db;
        _payments = payments;
        _email = email;
        _logger = logger;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var payload = args.Message.Body.ToObjectFromJson<OrderPaymentRequested>();

        _logger.LogInformation(
            "Processing payment for OrderId={OrderId} MessageId={MessageId} Delivery={Delivery}",
            payload.OrderId,
            args.Message.MessageId,
            args.Message.DeliveryCount);

        var order = await _db.Orders
            .SingleAsync(x => x.Id == payload.OrderId);

        if (order.Status == "Paid")
        {
            await args.CompleteMessageAsync(args.Message);
            return;
        }

        try
        {
            var charge = await _payments.ChargeAsync(
                order.PaymentToken,
                order.TotalAmount);

            order.Status = "Paid";
            order.PaymentReference = charge.Reference;
            order.PaidUtc = DateTime.UtcNow;

            await _db.SaveChangesAsync();

            await _email.SendPaymentConfirmationAsync(
                order.CustomerEmail,
                order.Id,
                order.TotalAmount);

            await args.CompleteMessageAsync(args.Message);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Payment processing failed for OrderId={OrderId}",
                payload.OrderId);

            await args.AbandonMessageAsync(args.Message);
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review consumer trên như một Senior .NET Developer phụ trách hệ thống production có tiền thật và side effect bên ngoài.

Bạn cần:

1. xác định correctness problems;
2. xác định duplicate-processing risks;
3. giải thích behavior khi message lock hết hạn hoặc settlement fail;
4. đánh giá transaction boundary giữa SQL Server, payment provider và email provider;
5. đánh giá idempotency ở cả consumer và external payment call;
6. đánh giá retry, poison message và DLQ handling;
7. đề xuất implementation/design tốt hơn;
8. giải thích testing;
9. giải thích telemetry cần quan sát trong production.

Không giả định rằng `CompleteMessageAsync` thành công chỉ vì business logic đã thành công.

## Câu hỏi gợi mở

1. Nếu payment provider đã charge thành công nhưng process mất lock trước khi complete message thì delivery tiếp theo sẽ làm gì?

## Kết quả code review tham khảo

### Critical — Payment call không có idempotency key

**Vấn đề:**  
`ChargeAsync` được gọi bằng token và amount, không có business idempotency key gắn với order/payment attempt.

**Tại sao xảy ra:**  
Service Bus Peek Lock cho phép redelivery. Consumer không thể giả định mỗi message chỉ chạy một lần. Nếu processing thành công nhưng settlement thất bại hoặc lock hết hạn, cùng message có thể được giao lại.

**Ảnh hưởng production:**  
Một delivery thứ hai có thể tạo charge thứ hai ở payment provider, dù message logical chỉ đại diện cho một yêu cầu thanh toán.

**Cách sửa:**  
Dùng một idempotency key ổn định ở payment provider, ví dụ `OrderId` hoặc `PaymentAttemptId` nếu provider hỗ trợ. Nếu provider không hỗ trợ, cần một orchestration design chặt hơn và reconciliation với provider; không thể chỉ dựa vào Service Bus settlement để đảm bảo exactly-once side effect.

---

### Critical — Check `Paid` không ngăn race giữa nhiều consumer

**Vấn đề:**  
Hai delivery có thể cùng đọc `order.Status == "Pending"` rồi cùng gọi payment provider.

**Tại sao xảy ra:**  
Check-then-act không được bảo vệ bởi optimistic concurrency, unique constraint, distributed business key hoặc durable inbox/claim.

**Ảnh hưởng production:**  
Hai instance có thể charge cùng order gần như đồng thời trước khi một instance kịp cập nhật SQL.

**Cách sửa:**  
Tạo một atomic claim/state transition trong database, ví dụ `Pending → Processing` với concurrency token hoặc conditional update. Đồng thời vẫn phải dùng provider idempotency key vì database claim không bảo vệ hoàn toàn khỏi crash sau external side effect.

---

### High — Business success nhưng settlement fail vẫn dẫn tới redelivery

**Vấn đề:**  
Code coi `CompleteMessageAsync` như phần cuối đơn giản của flow, nhưng settlement có thể fail do lost lock/network/receiver state.

**Tại sao xảy ra:**  
Trong Peek Lock, message chỉ được remove sau successful settlement. Nếu lock mất trước complete, broker có thể redeliver.

**Ảnh hưởng production:**  
Một charge hợp lệ có thể được thực hiện lại ở delivery sau nếu consumer không idempotent.

**Cách sửa:**  
Thiết kế consumer để duplicate delivery là expected behavior. Complete chỉ sau khi durable processing state đã được lưu. Nếu settlement fail, log rõ `MessageId`, business key và state; lần delivery sau phải nhận ra operation đã hoàn tất và settle an toàn mà không lặp side effect.

---

### High — Không có strategy cho long-running processing và lock renewal

**Vấn đề:**  
Payment provider đôi khi mất 45–90 giây; code không thể hiện policy về message lock duration hoặc automatic lock renewal của processor.

**Tại sao xảy ra:**  
Processing time có thể tiến sát hoặc vượt lock budget cấu hình, đặc biệt khi có thêm DB/email latency.

**Ảnh hưởng production:**  
Message có thể bị redeliver khi delivery đầu vẫn đang chạy, tạo concurrent duplicate processing.

**Cách sửa:**  
Đảm bảo processing time phù hợp lock configuration và dùng lock renewal khi legitimately cần long-running work. Tuy nhiên lock renewal chỉ giảm duplicate do timeout; nó không thay thế idempotency vì network failure, process crash hoặc settlement ambiguity vẫn tồn tại.

---

### High — SQL transaction không bao phủ payment provider

**Vấn đề:**  
Charge xảy ra trước `SaveChangesAsync`, nhưng SQL và external payment provider không nằm trong cùng transaction.

**Tại sao xảy ra:**  
Đây là distributed side effect qua hai hệ thống độc lập.

**Ảnh hưởng production:**  
Provider charge thành công nhưng SQL update fail → tiền đã bị charge, order vẫn `Pending`. Retry có thể charge lại.

**Cách sửa:**  
Mô hình hóa payment như state machine: `Pending → Processing → Paid / Failed / RequiresReconciliation`. Persist attempt identity trước external call; dùng idempotency key ở provider; sau call, persist result. Nếu response ambiguous, reconcile theo provider reference/idempotency key thay vì blind retry.

---

### High — Email failure làm retry lại toàn bộ payment flow

**Vấn đề:**  
Email gửi sau khi SQL đã lưu `Paid`. Nếu email fail, catch block abandon message.

**Tại sao xảy ra:**  
Payment và notification được gộp vào cùng failure boundary.

**Ảnh hưởng production:**  
Delivery tiếp theo có thể thấy `Paid` và complete ngay, nghĩa là email không được retry; hoặc nếu race/state khác, flow có thể lặp side effect. Business semantics của payment và notification bị trộn lẫn.

**Cách sửa:**  
Payment success phải là durable business fact độc lập. Sau khi `Paid`, tạo outbox event `PaymentSucceeded`; email consumer riêng xử lý notification với retry/idempotency riêng. Không để lỗi email quyết định việc rollback/retry payment.

---

### High — Catch-all rồi abandon mọi exception

**Vấn đề:**  
Mọi exception đều `AbandonMessageAsync`.

**Tại sao xảy ra:**  
Code không phân loại transient, permanent, validation, poison data hay business rejection.

**Ảnh hưởng production:**  
Malformed payload hoặc invalid business state bị retry vô ích, tăng queue churn và làm DLQ chậm đầy thông tin hữu ích.

**Cách sửa:**  
Phân loại lỗi:

- malformed/unsupported payload → dead-letter có reason rõ;
- transient dependency failure → retry theo policy hoặc abandon có kiểm soát;
- duplicate/already-processed → complete;
- ambiguous payment outcome → move vào reconciliation path, không blind retry.

---

### High — Không có durable inbox / processed-message record

**Vấn đề:**  
`MessageId` chỉ được log, không dùng để chống duplicate.

**Tại sao xảy ra:**  
Consumer không persist fact rằng một message/business command đã được xử lý.

**Ảnh hưởng production:**  
Restart, redelivery hoặc concurrent processing không có durable marker để phân biệt new work với replay.

**Cách sửa:**  
Dùng inbox table keyed bởi `MessageId` hoặc business command ID, tốt nhất cùng transaction với business-state update khi có thể. Unique constraint phải xử lý race giữa nhiều consumer.

---

### Medium — Không propagate `CancellationToken`

**Vấn đề:**  
EF Core, payment và email calls không nhận cancellation token từ processing context.

**Tại sao xảy ra:**  
Handler bỏ qua cancellation semantics của processor/shutdown.

**Ảnh hưởng production:**  
Khi instance shutdown hoặc processor dừng, in-flight operation có thể tiếp tục lâu hơn cần thiết. Nếu cancellation xảy ra giữa external side effect và persistence, state càng khó reason.

**Cách sửa:**  
Truyền cancellation token khi operation hỗ trợ, nhưng không dùng cancellation một cách máy móc sau khi external charge đã có thể thành công. Sau điểm side effect, cần ưu tiên persist/reconcile state an toàn.

---

### Medium — Thiếu concurrency control trên Order

**Vấn đề:**  
Không có optimistic concurrency token hoặc conditional transition.

**Tại sao xảy ra:**  
Hai handler có thể ghi chồng state theo thứ tự không dự đoán được.

**Ảnh hưởng production:**  
Payment reference, status hoặc audit metadata có thể bị overwrite.

**Cách sửa:**  
Dùng rowversion/concurrency token hoặc atomic update có điều kiện theo expected status/version.

---

### Medium — Observability chưa đủ để reconcile payment

**Vấn đề:**  
Log có `OrderId`, `MessageId`, `DeliveryCount` nhưng thiếu `PaymentAttemptId`, provider idempotency key, provider reference, lock-loss/settlement result và processing duration.

**Tại sao xảy ra:**  
Telemetry tập trung vào handler, không tập trung vào distributed business operation.

**Ảnh hưởng production:**  
Khó trả lời câu hỏi: “charge này đến từ attempt nào, message delivery nào, provider đã nhận idempotency key gì, SQL state lúc đó ra sao?”

**Cách sửa:**  
Structured telemetry xuyên suốt `OrderId`, `MessageId`, `PaymentAttemptId`, provider reference, delivery count, duration, outcome, settlement outcome và trace/correlation ID. Không log payment token hoặc secret.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa một hướng an toàn hơn. Giả định:

- `Order` có concurrency token;
- có `PaymentAttempt` và inbox table với unique constraint;
- payment provider hỗ trợ idempotency key;
- email được tách sang outbox flow riêng;
- processor được cấu hình lock renewal phù hợp với latency thực tế.

```csharp
public sealed class PaymentMessageHandler
{
    private readonly AppDbContext _db;
    private readonly IPaymentGateway _payments;
    private readonly ILogger<PaymentMessageHandler> _logger;

    public PaymentMessageHandler(
        AppDbContext db,
        IPaymentGateway payments,
        ILogger<PaymentMessageHandler> logger)
    {
        _db = db;
        _payments = payments;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        OrderPaymentRequested payload;

        try
        {
            payload = args.Message.Body
                .ToObjectFromJson<OrderPaymentRequested>()
                ?? throw new InvalidOperationException("Empty payload.");
        }
        catch (Exception ex)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                deadLetterReason: "InvalidPayload",
                deadLetterErrorDescription: ex.Message,
                cancellationToken: cancellationToken);
            return;
        }

        var alreadyProcessed = await _db.InboxMessages
            .AnyAsync(x => x.MessageId == args.Message.MessageId, cancellationToken);

        if (alreadyProcessed)
        {
            await args.CompleteMessageAsync(args.Message, cancellationToken);
            return;
        }

        var order = await _db.Orders
            .SingleAsync(x => x.Id == payload.OrderId, cancellationToken);

        if (order.Status == OrderStatus.Paid)
        {
            _db.InboxMessages.Add(new InboxMessage
            {
                MessageId = args.Message.MessageId,
                ProcessedUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
            await args.CompleteMessageAsync(args.Message, cancellationToken);
            return;
        }

        var attempt = await _db.PaymentAttempts
            .SingleOrDefaultAsync(
                x => x.OrderId == order.Id && x.IsActive,
                cancellationToken);

        if (attempt is null)
        {
            attempt = new PaymentAttempt
            {
                Id = Guid.NewGuid(),
                OrderId = order.Id,
                IdempotencyKey = $"order:{order.Id:N}",
                Status = PaymentAttemptStatus.Processing,
                CreatedUtc = DateTime.UtcNow,
                IsActive = true
            };

            _db.PaymentAttempts.Add(attempt);
            await _db.SaveChangesAsync(cancellationToken);
        }

        PaymentResult result;

        try
        {
            result = await _payments.ChargeAsync(
                order.PaymentToken,
                order.TotalAmount,
                attempt.IdempotencyKey,
                cancellationToken);
        }
        catch (PaymentOutcomeUnknownException ex)
        {
            attempt.Status = PaymentAttemptStatus.RequiresReconciliation;
            attempt.LastError = ex.Message;
            await _db.SaveChangesAsync(CancellationToken.None);

            _logger.LogWarning(
                ex,
                "Payment outcome unknown OrderId={OrderId} AttemptId={AttemptId} MessageId={MessageId}",
                order.Id,
                attempt.Id,
                args.Message.MessageId);

            throw;
        }

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        order.Status = OrderStatus.Paid;
        order.PaymentReference = result.Reference;
        order.PaidUtc = DateTime.UtcNow;

        attempt.Status = PaymentAttemptStatus.Succeeded;
        attempt.ProviderReference = result.Reference;
        attempt.IsActive = false;

        _db.OutboxMessages.Add(OutboxMessage.Create(
            "PaymentSucceeded",
            new { order.Id, order.CustomerEmail, order.TotalAmount }));

        _db.InboxMessages.Add(new InboxMessage
        {
            MessageId = args.Message.MessageId,
            ProcessedUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Payment succeeded OrderId={OrderId} AttemptId={AttemptId} MessageId={MessageId} Delivery={Delivery}",
            order.Id,
            attempt.Id,
            args.Message.MessageId,
            args.Message.DeliveryCount);

        await args.CompleteMessageAsync(args.Message, cancellationToken);
    }
}
```

Implementation production vẫn cần xử lý race khi tạo `PaymentAttempt`/`InboxMessage` bằng unique constraint và map duplicate-key thành duplicate/replay path. Nếu settlement fail sau transaction commit, delivery sau sẽ thấy inbox record và complete mà không charge lại.

## Giải thích thiết kế sau khi sửa

### 1. Idempotency được đặt ở nơi side effect thực sự xảy ra

Consumer-level inbox quan trọng, nhưng provider idempotency key mới bảo vệ external charge khi process crash hoặc response bị mất sau provider success.

### 2. Payment và notification tách failure boundary

Thanh toán thành công tạo outbox event. Email retry độc lập, không biến lỗi notification thành payment retry.

### 3. Durable state tồn tại trước và sau external call

`PaymentAttempt` cho phép phân biệt processing, success và ambiguous outcome. Incident/reconciliation không còn phải suy luận chỉ từ log.

### 4. Duplicate delivery là normal case

Handler không cố “ngăn Service Bus gửi lại”; nó đảm bảo delivery lại không tạo thêm business side effect.

## Trade-offs

- Inbox/outbox/payment-attempt tables tăng schema và operational complexity.
- Provider idempotency semantics cần được xác minh theo API thực tế; không phải provider nào cũng giống nhau.
- Lock renewal giảm duplicate do long processing nhưng giữ message locked lâu hơn và không chữa được crash/network ambiguity.
- Tách email sang outbox làm notification eventual-consistent.
- Reconciliation workflow cần tooling cho support/operations.

## Cách kiểm thử

1. **Duplicate delivery test:** gửi cùng `MessageId` nhiều lần, kể cả song song; chỉ một charge business được tạo.
2. **Settlement failure test:** inject failure ở `CompleteMessageAsync` sau SQL commit; redelivery phải complete mà không charge lại.
3. **Lock-expiry/concurrency test:** cố tình làm payment call chậm và chạy nhiều consumer; provider idempotency + DB constraints phải ngăn duplicate business effect.
4. **Ambiguous provider test:** provider charge thành công nhưng client timeout; attempt phải đi vào reconciliation, không blind retry với key mới.
5. **Email failure test:** payment vẫn ở `Paid`; outbox retry email mà không chạy lại payment.

## Quan sát trong production

Theo dõi:

- queue active message count;
- DLQ count;
- delivery count distribution;
- message processing p95/p99;
- message lock lost / settlement failure count;
- duplicate inbox hit count;
- payment idempotency replay count;
- ambiguous payment attempts;
- reconciliation backlog;
- payment-provider latency/error rate;
- outbox backlog và oldest event age;
- `OrderId` ↔ `MessageId` ↔ `PaymentAttemptId` ↔ provider reference correlation;
- alerts khi duplicate charge suspicion hoặc DLQ tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu payment provider không hỗ trợ idempotency key, bạn sẽ giảm duplicate-charge risk bằng architecture nào?
2. Duplicate detection của Azure Service Bus giải quyết sender retry nhưng vì sao vẫn không đủ cho consumer side effect?
3. Nếu business yêu cầu strict ordering của payment events theo `OrderId`, bạn sẽ đánh giá Service Bus sessions hay một thiết kế khác như thế nào?

# Code Review Challenge 2 — React search page hiển thị kết quả cũ do race condition và render HTML không tin cậy

**Chủ đề:** React.js, TypeScript, browser async behavior, request cancellation, stale state, API integration, XSS, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề

## Bối cảnh

Một product-search page trong React gọi ASP.NET Core API `/api/products/search` khi user thay đổi keyword, category hoặc page.

Hệ thống có behavior thực tế:

- user thường gõ nhanh 4–8 ký tự liên tiếp;
- API latency dao động từ 80 ms đến 2 giây tùy query và Elasticsearch load;
- mobile network có thể reorder response theo thời gian hoàn tất;
- backend trả `highlightHtml` chứa đoạn text đã highlight từ search engine;
- authentication dùng bearer token;
- UI có pagination và category filter;
- production ghi nhận:
  - user gõ từ mới nhưng đôi lúc thấy kết quả của keyword cũ;
  - đổi category nhưng page vẫn ở số cao và trả empty result;
  - request count tăng mạnh khi user gõ nhanh;
  - khi API trả 401, UI chỉ hiện “No products found”;
  - security review phát hiện `dangerouslySetInnerHTML` với dữ liệu từ API;
  - component unmount trong lúc request chạy vẫn có warning/telemetry noise từ state update path tùy environment/tooling.

Code hiện tại:

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

interface Product {
  id: string;
  name: string;
  highlightHtml: string;
}

interface SearchResponse {
  items: Product[];
  total: number;
}

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [items, setItems] = useState<Product[]>([]);
  const [total, setTotal] = useState(0);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    setLoading(true);

    const token = localStorage.getItem("access_token");

    fetch(
      `/api/products/search?q=${query}&category=${category}&page=${page}`,
      {
        headers: {
          Authorization: `Bearer ${token}`
        }
      })
      .then(r => r.json())
      .then((data: SearchResponse) => {
        setItems(data.items);
        setTotal(data.total);
        setLoading(false);
      })
      .catch(() => {
        setItems([]);
        setTotal(0);
        setLoading(false);
      });
  }, [query, category, page]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />

      <select
        value={category}
        onChange={e => setCategory(e.target.value)}
      >
        <option value="all">All</option>
        <option value="books">Books</option>
        <option value="electronics">Electronics</option>
      </select>

      {loading && <p>Loading...</p>}

      {!loading && items.length === 0 && <p>No products found.</p>}

      <ul>
        {items.map(product => (
          <li key={product.id}>
            <strong>{product.name}</strong>
            <div
              dangerouslySetInnerHTML={{
                __html: product.highlightHtml
              }}
            />
          </li>
        ))}
      </ul>

      <button disabled={page === 1} onClick={() => setPage(page - 1)}>
        Previous
      </button>
      <button onClick={() => setPage(page + 1)}>
        Next
      </button>

      <p>Total: {total}</p>
    </section>
  );
}
```

Bạn cần:

2. đánh giá request cancellation và duplicate/unnecessary requests;
3. xác định security risk;

8. giải thích testing;
9. giải thích browser/network telemetry cần quan sát.

## Câu hỏi gợi mở

1. Nếu request cho `q=car` mất 1.8 giây còn `q=cargo` chỉ mất 200 ms, state cuối cùng có chắc là `cargo` không?
2. `fetch` có tự throw khi server trả HTTP 401 hoặc 500 không?

## Kết quả code review tham khảo

### Critical — `dangerouslySetInnerHTML` render dữ liệu không được chứng minh là trusted

**Vấn đề:**  
`highlightHtml` từ API được đưa trực tiếp vào DOM bằng `dangerouslySetInnerHTML`.

**Tại sao xảy ra:**  
Frontend giả định dữ liệu từ backend luôn an toàn. Nhưng backend có thể chứa user-generated content, search-index content, compromised data hoặc escaping bug.

**Ảnh hưởng production:**  
Nếu payload chứa HTML/script-compatible markup, có thể tạo XSS trong browser context của user.

**Cách sửa:**  
Ưu tiên API trả structured highlight segments, ví dụ `{ text, highlighted }[]`, rồi React render text node và `<mark>`. Nếu business bắt buộc nhận HTML, phải sanitize bằng policy/library được review và vẫn giới hạn allowed tags/attributes.

---

### High — Out-of-order response có thể overwrite state mới

**Vấn đề:**  
Mọi request đều gọi `setItems` khi hoàn tất, không kiểm tra request đó còn là request hiện tại hay không.

**Tại sao xảy ra:**  
Network response có thể hoàn tất khác thứ tự request được gửi.

**Ảnh hưởng production:**  
User gõ `car` rồi `cargo`; response `cargo` về trước và hiển thị đúng, sau đó response `car` về muộn hơn và overwrite UI bằng kết quả cũ.

**Cách sửa:**  
Abort request cũ bằng `AbortController` trong effect cleanup hoặc dùng request sequence/ignore flag để không commit stale response. React documentation cũng khuyến nghị cleanup để tránh race khi fetch trong Effect.

---

### High — Không cancel request cũ khi dependency thay đổi hoặc component unmount

**Vấn đề:**  
Effect không có cleanup.

**Tại sao xảy ra:**  
Mỗi change tạo request mới nhưng request trước tiếp tục chạy.

**Ảnh hưởng production:**  
Tăng network load, backend query load và khả năng stale update. Khi component unmount, response cũ vẫn tiếp tục xử lý JavaScript path dù UI không còn cần nó.

**Cách sửa:**  
Tạo `AbortController` cho mỗi effect run, truyền `signal` vào `fetch`, gọi `abort()` trong cleanup và không coi `AbortError` là user-visible failure.

---

### High — Không kiểm tra `response.ok`

**Vấn đề:**  
Code gọi `r.json()` cho mọi HTTP response.

**Tại sao xảy ra:**  
`fetch` resolve promise cho nhiều HTTP error status; nó không tự throw chỉ vì 401/404/500.

**Ảnh hưởng production:**  
401 có thể bị parse như response bình thường hoặc rơi vào generic catch, cuối cùng UI hiển thị “No products found” thay vì authentication/session error. 500 cũng bị biến thành empty business state.

**Cách sửa:**  
Kiểm tra `response.ok` và phân loại 401/403, 4xx, 5xx. Error state phải tách khỏi empty-result state.

---

### High — Access token trong `localStorage` làm tăng blast radius của XSS

**Vấn đề:**  
Token được đọc trực tiếp từ `localStorage`.

**Tại sao xảy ra:**  
Bất kỳ JavaScript chạy trong origin, bao gồm script chèn qua XSS, có thể đọc token.

**Ảnh hưởng production:**  
XSS có thể biến thành credential theft.

**Cách sửa:**  
Authentication storage strategy phải được đánh giá cùng threat model. Với browser app, cân nhắc secure HttpOnly cookie/BFF pattern hoặc token handling architecture giảm khả năng JavaScript đọc long-lived credential. Không thể sửa riêng bằng component này nếu toàn bộ app architecture đang dùng bearer token trong local storage.

---

### Medium — Query parameters không được encode an toàn

**Vấn đề:**  
`query` và `category` được nối trực tiếp vào URL string.

**Tại sao xảy ra:**  
Các ký tự như `&`, `?`, `+`, `#` có thể thay đổi semantics của query string.

**Ảnh hưởng production:**  
Search text đặc biệt có thể tạo request sai hoặc khó reproduce.

**Cách sửa:**  
Dùng `URLSearchParams` hoặc `encodeURIComponent` theo đúng semantics.

---

### Medium — Mỗi keystroke tạo request ngay lập tức

**Vấn đề:**  
`query` thay đổi là effect chạy ngay.

**Tại sao xảy ra:**  
Không có debounce hoặc minimum query policy.

**Ảnh hưởng production:**  
User gõ nhanh có thể tạo nhiều Elasticsearch/API request không cần thiết, tăng load và làm stale-response race dễ xảy ra hơn.

**Cách sửa:**  
Debounce input 200–400 ms tùy UX requirement, hoặc search on submit. Vẫn cần cancellation vì debounce không loại bỏ mọi overlap.

---

### Medium — Category/query change không reset page

**Vấn đề:**  
User ở page cao, thay category/query nhưng `page` giữ nguyên.

**Tại sao xảy ra:**  
Pagination state không được model như dependency của search criteria.

**Ảnh hưởng production:**  
Filter mới có ít result hơn và page hiện tại có thể rỗng, tạo false impression “No products found”.

**Cách sửa:**  
Reset page về 1 khi query/category thay đổi. Tránh tạo double-fetch không cần thiết bằng cách thiết kế state transition/debounced criteria rõ ràng.

---

### Medium — `loading` có thể bị request cũ tắt sai thời điểm

**Vấn đề:**  
Mỗi request đều `setLoading(false)` khi hoàn tất.

**Tại sao xảy ra:**  
Không gắn loading state với request identity.

**Ảnh hưởng production:**  
Request cũ về trước/giữa request mới có thể tắt loading trong khi request hiện tại vẫn đang chạy.

**Cách sửa:**  
Abort stale request hoặc dùng request ID để chỉ current request được phép update loading/items/error.

---

### Medium — Generic catch làm mất phân loại lỗi

**Vấn đề:**  
Network failure, JSON parse error, 401 flow và abort đều bị đối xử giống nhau.

**Tại sao xảy ra:**  
Không có explicit error model.

**Ảnh hưởng production:**  
UI khó hướng dẫn user; telemetry cũng khó biết lỗi do auth, backend, network hay cancellation bình thường.

**Cách sửa:**  
Model `error: { type, message } | null`, phân loại HTTP/network/parse, và bỏ qua intentional abort.

## Phiên bản đề xuất

Ví dụ sau:

- debounce query;
- reset page khi criteria thay đổi;
- dùng `AbortController`;
- kiểm tra HTTP status;
- không render raw HTML;
- dùng structured highlight data.

Giả định backend đổi contract thành `highlights: Array<{ text: string; highlighted: boolean }>`.

```tsx
import { useEffect, useMemo, useState } from "react";

interface HighlightPart {
  text: string;
  highlighted: boolean;
}

interface Product {
  id: string;
  name: string;
  highlights: HighlightPart[];
}

interface SearchResponse {
  items: Product[];
  total: number;
}

type SearchError =
  | { type: "auth"; message: string }
  | { type: "server"; message: string }
  | { type: "network"; message: string };

function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = window.setTimeout(() => setDebounced(value), delayMs);
    return () => window.clearTimeout(timer);
  }, [value, delayMs]);

  return debounced;
}

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [items, setItems] = useState<Product[]>([]);
  const [total, setTotal] = useState(0);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<SearchError | null>(null);

  const debouncedQuery = useDebouncedValue(query.trim(), 300);

  useEffect(() => {
    setPage(1);
  }, [debouncedQuery, category]);

  const searchUrl = useMemo(() => {
    const qs = new URLSearchParams({
      q: debouncedQuery,
      category,
      page: String(page)
    });

    return `/api/products/search?${qs.toString()}`;
  }, [debouncedQuery, category, page]);

  useEffect(() => {
    const controller = new AbortController();

    async function load() {
      setLoading(true);
      setError(null);

      try {
        const response = await fetch(searchUrl, {
          signal: controller.signal,
          credentials: "include"
        });

        if (response.status === 401 || response.status === 403) {
          setError({
            type: "auth",
            message: "Your session is not authorized for this request."
          });
          return;
        }

        if (!response.ok) {
          setError({
            type: "server",
            message: `Search failed with HTTP ${response.status}.`
          });
          return;
        }

        const data = (await response.json()) as SearchResponse;
        setItems(data.items);
        setTotal(data.total);
      } catch (err) {
        if (err instanceof DOMException && err.name === "AbortError") {
          return;
        }

        setError({
          type: "network",
          message: "Search request could not be completed."
        });
      } finally {
        if (!controller.signal.aborted) {
          setLoading(false);
        }
      }
    }

    void load();

    return () => controller.abort();
  }, [searchUrl]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />

      <select
        value={category}
        onChange={e => setCategory(e.target.value)}
      >
        <option value="all">All</option>
        <option value="books">Books</option>
        <option value="electronics">Electronics</option>
      </select>

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error.message}</p>}

      {!loading && !error && items.length === 0 && (
        <p>No products found.</p>
      )}

      <ul>
        {items.map(product => (
          <li key={product.id}>
            <strong>{product.name}</strong>
            <p>
              {product.highlights.map((part, index) =>
                part.highlighted ? (
                  <mark key={index}>{part.text}</mark>
                ) : (
                  <span key={index}>{part.text}</span>
                )
              )}
            </p>
          </li>
        ))}
      </ul>

      <button
        disabled={page === 1 || loading}
        onClick={() => setPage(p => Math.max(1, p - 1))}
      >
        Previous
      </button>

      <button
        disabled={loading || page * 20 >= total}
        onClick={() => setPage(p => p + 1)}
      >
        Next
      </button>

      <p>Total: {total}</p>
    </section>
  );
}
```

`credentials: "include"` ở ví dụ này chỉ hợp lệ nếu application authentication architecture thực sự dùng cookie/BFF. Nếu hệ thống bắt buộc bearer token, cần một token provider abstraction và security design phù hợp thay vì đọc token trực tiếp trong component.

## Giải thích thiết kế sau khi sửa

### 1. Cleanup ngăn stale request commit state

Khi criteria thay đổi, effect cleanup abort request cũ. Response cũ không còn cơ hội overwrite result mới.

### 2. Debounce giảm load nhưng không thay thế cancellation

Debounce giảm số request khi typing. Cancellation vẫn cần vì request có thể overlap do network latency hoặc criteria khác thay đổi.

### 3. Empty result và error là hai state khác nhau

“No products found” là business outcome hợp lệ. 401, 500 hay network failure phải có UI/telemetry riêng.

### 4. Structured highlight tránh raw HTML trust boundary

React render text node mặc định escape content. API contract dạng segments giữ được highlight mà không cần render arbitrary HTML.

### 5. Pagination là một phần của search state

Query/category mới thường phải reset page về 1. Functional state update cho button tránh phụ thuộc stale closure khi click nhanh.

## Trade-offs

- Debounce 300 ms thêm intentional latency trước request; cần tune theo UX.
- Abort request phía browser không đảm bảo backend luôn dừng ngay; server/API/database cũng cần propagate cancellation để tiết kiệm compute.
- Structured highlights làm API contract phức tạp hơn nhưng giảm XSS risk đáng kể.
- Cookie/BFF architecture tăng backend responsibility nhưng giảm JavaScript exposure của credential.
- Client-side fetching trong `useEffect` có thể đủ cho app nội bộ; với application lớn có caching/prefetch/routing requirements, data-fetching library/framework pattern có thể giảm boilerplate nhưng vẫn phải hiểu race/error semantics bên dưới.

## Cách kiểm thử

1. **Race-condition test:** mock `car` response chậm hơn `cargo`; UI cuối cùng phải luôn hiển thị `cargo`.
2. **Cancellation test:** đổi query liên tục; request trước bị abort và không update state.
3. **Security test:** backend trả highlight text chứa `<img onerror=...>`; UI phải render như text, không execute markup.
4. **HTTP error test:** 401, 403, 500 và network failure phải tạo error state đúng, không hiển thị như empty result.
5. **Pagination test:** đang page 7 rồi đổi category/query; page reset về 1 và không sinh ra incorrect stale result.

## Quan sát trong production

Theo dõi:

- số request search trên mỗi user interaction;
- aborted-request count;
- search API p50/p95/p99;
- frontend error rate phân loại HTTP/network/parse;
- 401/403 rate;
- backend Elasticsearch query rate so với user keystroke/search intent;
- Core Web Vitals phù hợp với page;
- browser Performance/Network timing cho search;
- stale-response prevention metrics nếu instrumentation có request sequence;
- CSP violation reports/XSS telemetry nếu application sử dụng CSP;

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend search rất đắt, bạn sẽ chọn debounce, search-on-submit hay server-side caching dựa trên metric nào?
2. Nếu product data phải sync vào URL để hỗ trợ back/forward navigation, bạn sẽ tổ chức search state thế nào để tránh double fetch?
3. Nếu backend bắt buộc trả HTML highlight vì search engine contract hiện tại, bạn sẽ xây sanitization boundary ở frontend hay backend và tại sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Service Bus Peek Lock tạo **at-least-once processing semantics**; duplicate delivery là một failure mode bình thường cần được thiết kế từ đầu.
- Settlement success không đồng nghĩa business side effect chỉ xảy ra một lần; ngược lại business success cũng không đảm bảo settlement success.
- Với external payment, **idempotency key + durable attempt state + inbox/outbox + reconciliation** quan trọng hơn cố tạo “exactly once” bằng retry logic đơn giản.
- Failure boundary nên tách payment khỏi notification để một email outage không kéo payment workflow quay lại.
- React/network request có thể hoàn tất khác thứ tự gửi; UI phải chống stale response bằng cleanup/cancellation hoặc request identity.
- `fetch` error handling phải tách HTTP error khỏi network error và tách technical error khỏi empty business result.
- Raw HTML từ API vẫn là untrusted input cho browser; structured rendering an toàn hơn `dangerouslySetInnerHTML`.

## Mẫu tư duy cần nhớ

1. **Design retry together with idempotency.**
2. **Treat settlement and business success as separate failure boundaries.**
3. **Persist enough state to reconcile ambiguous external outcomes.**
4. **Cancel or ignore stale asynchronous work before it can commit state.**
5. **Treat data crossing a trust boundary as untrusted, even when it comes from your own API.**
