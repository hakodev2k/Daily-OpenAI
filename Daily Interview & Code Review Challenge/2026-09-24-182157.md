# Câu 1 — Vue search box trả đúng API nhưng UI đôi lúc hiển thị kết quả của query cũ

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Vue.js, TypeScript, JavaScript event loop, Promise, async race condition, request cancellation, state correctness, browser/network debugging

## Bối cảnh

Một enterprise portal dùng Vue 3 + TypeScript. Trang tìm kiếm gọi ASP.NET Core API mỗi khi user thay đổi keyword. Team đã thêm debounce 300 ms để giảm request. Trong test thông thường mọi thứ hoạt động tốt.

Ở production, một số user gõ nhanh hoặc dùng mạng có latency không ổn định thì đôi lúc UI hiển thị kết quả của keyword trước đó. Network tab cho thấy tất cả request đều trả `200`, backend log cũng cho thấy mỗi request nhận đúng keyword và trả đúng dữ liệu. Bug khó reproduce trên máy developer có mạng nhanh.

Một developer nói: “JavaScript chạy single-thread nên không thể có race condition.” Người khác muốn tăng debounce lên 1 giây. Một người khác muốn bỏ `async/await` và dùng `.then()` vì cho rằng Promise đang chạy sai thứ tự.

Giả sử component hiện có logic tương đương:

```ts
const keyword = ref('')
const results = ref<SearchResult[]>([])
const loading = ref(false)

watch(keyword, async (value) => {
  if (!value.trim()) {
    results.value = []
    return
  }

  loading.value = true

  const response = await fetch(`/api/search?q=${encodeURIComponent(value)}`)
  const data = await response.json()

  results.value = data.items
  loading.value = false
})
```

## Câu hỏi chính

Giải thích vì sao đoạn code vẫn có thể tạo race condition dù JavaScript execution trên main thread là single-threaded; mô tả thứ tự có thể xảy ra giữa các Promise/network completion; sau đó đề xuất cách sửa sao cho UI chỉ commit state của request còn hợp lệ và giải thích cách bạn chứng minh fix hoạt động.

## Câu hỏi làm rõ nên cân nhắc

1. Requirement là latest keyword wins hay mọi request đều phải được xử lý theo thứ tự?
2. Có debounce implementation nào bên ngoài đoạn code và watcher có cleanup lifecycle không?
3. Search API có side effect hay hoàn toàn read-only?
4. Component có thể unmount/remount trong lúc request đang chạy không?
5. `loading` cần biểu diễn “có request đang chạy” hay “request của keyword hiện tại đang chạy”?

## Gợi ý tư duy

### Gợi ý 1

Single-threaded execution không có nghĩa asynchronous operations hoàn tất theo thứ tự chúng được bắt đầu.

### Gợi ý 2

Hãy xét hai request A và B: A bắt đầu trước nhưng response A về sau B. Mỗi continuation sau `await` đều có thể ghi shared reactive state.

### Gợi ý 3

Có hai hướng chính: hủy work không còn cần thiết và/hoặc kiểm tra identity/version trước khi commit state. Cancellation giúp tiết kiệm work nhưng correctness không nên phụ thuộc mù quáng vào việc mọi dependency luôn hủy ngay lập tức.

## Cấu trúc trả lời đề xuất

1. Làm rõ semantics “latest wins”.
2. Mô tả event loop/Promise continuation ở mức cần thiết.
3. Dựng timeline A/B gây stale overwrite.
4. Chỉ ra cả `results` và `loading` đều có thể bị ghi sai.
5. Chọn cancellation/versioning strategy.
6. Xử lý abort/error/unmount rõ ràng.
7. Test bằng latency đảo thứ tự có chủ đích.
8. Quan sát Network/console/telemetry để verify.
9. Đánh giá debounce như optimization, không phải correctness mechanism.
10. Kiểm tra accessibility/loading UX sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Single-threaded JavaScript vẫn có asynchronous race trên thứ tự completion.
- `await` không serialize các lần callback khác nhau của watcher.
- Request A có thể hoàn tất sau B và overwrite `results` mới hơn.
- Debounce giảm số request nhưng không bảo đảm response order.
- Fix phải encode semantics latest-request-wins.

### Điểm cộng

- Dùng `AbortController` và watcher cleanup để abort request cũ.
- Dùng monotonically increasing request/version token để chỉ latest request được commit state.
- Xử lý `AbortError` riêng với real failure.
- `loading` cũng phải được bảo vệ khỏi stale `finally`.

### Senior+

- Nhận ra cancellation là resource optimization còn version/identity guard là correctness boundary hữu ích khi cancellation không thể được đảm bảo xuyên suốt.
- Thiết kế deterministic test với controlled Promise completion thay vì dựa vào `setTimeout` ngẫu nhiên.
- Phân biệt read-only search với mutation API: “latest wins” không thể áp dụng máy móc cho side effects.

## Hướng giải quyết tham khảo

JavaScript có thể execute callback trên một main thread nhưng network I/O là asynchronous. Mỗi lần watcher chạy tạo một async operation độc lập. `await` chỉ tạm dừng continuation của invocation hiện tại; nó không ngăn watcher được gọi lần nữa. Vì vậy A có thể gửi `q=car`, B gửi `q=card`, B hoàn tất trước và ghi kết quả đúng, sau đó A hoàn tất và ghi đè UI bằng kết quả `car`.

Tăng debounce chỉ giảm xác suất/tần suất request; nếu hai request vẫn overlap thì response vẫn có thể đảo thứ tự. Chuyển `await` sang `.then()` cũng không thay đổi ordering semantics.

Nếu requirement là latest keyword wins, một implementation phù hợp có thể tạo `AbortController` cho mỗi watcher invocation và abort controller trước trong cleanup. Đồng thời có thể dùng request sequence để bảo đảm chỉ request mới nhất được commit. Ví dụ:

```ts
let requestVersion = 0

watch(keyword, async (value, _, onCleanup) => {
  const version = ++requestVersion
  const query = value.trim()

  if (!query) {
    results.value = []
    loading.value = false
    return
  }

  const controller = new AbortController()
  onCleanup(() => controller.abort())

  loading.value = true

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal })

    if (!response.ok) {
      throw new Error(`Search failed: ${response.status}`)
    }

    const data = await response.json()

    if (version === requestVersion) {
      results.value = data.items
    }
  } catch (error) {
    if (!(error instanceof DOMException && error.name === 'AbortError')) {
      if (version === requestVersion) {
        // Map to the application's normal error state.
      }
    }
  } finally {
    if (version === requestVersion) {
      loading.value = false
    }
  }
})
```

Chi tiết API cleanup cần khớp version Vue đang dùng, nhưng nguyên tắc là explicit ownership của request lifecycle và guarded state commit. Nếu cancellation thành công, browser/backend có thể tiết kiệm work; tuy nhiên correctness của UI vẫn nên dựa trên việc stale operation không được commit state.

Testing nên điều khiển response A/B có chủ đích: start A, start B, resolve B trước, resolve A sau và assert UI vẫn là B. Test thêm empty keyword, abort, HTTP error, component unmount và rapid typing. Browser Network panel có thể xác minh request cũ bị canceled; frontend telemetry nên phân biệt canceled request với real failure để không tạo alert noise.

## Mẫu trả lời trong phỏng vấn

“Single-threaded không loại bỏ race condition ở async workflow. Mỗi lần watcher chạy tạo một Promise chain riêng. Nếu A bắt đầu trước B nhưng network response B về trước, B có thể set `results`, sau đó continuation của A chạy và overwrite state bằng dữ liệu cũ. `await` chỉ tuần tự bên trong một invocation, không tuần tự giữa các invocation.

Nếu requirement là latest query wins, em sẽ gắn identity/version cho request và chỉ latest version được commit. Em cũng dùng `AbortController` qua watcher cleanup để hủy request cũ, nhưng coi cancellation là tối ưu resource chứ không phải correctness guarantee duy nhất. `loading` và error state cũng phải được guard theo version.

Em sẽ viết test điều khiển hai Promise hoàn tất ngược thứ tự để bug deterministic, rồi test abort/unmount/error. Debounce vẫn giữ để giảm traffic nhưng không dùng nó để giải quyết ordering.”

## Câu hỏi đào sâu

1. Nếu search endpoint bắt đầu ghi analytics hoặc tạo side effect, việc abort/latest-wins thay đổi như thế nào?
2. Nếu bạn chỉ dùng `AbortController` mà không dùng version guard, trong trường hợp nào bạn vẫn muốn thêm guard?
3. Nếu Product muốn cache kết quả theo keyword ở client, bạn thiết kế cache thế nào để không tái tạo stale-state bug?

## Lỗi trả lời thường gặp

- Nói single-thread nghĩa là không có race condition.
- Tăng debounce và coi bug đã được sửa.
- Đổi `async/await` sang `.then()` để “giữ thứ tự”.
- Chỉ bảo vệ `results` nhưng để stale request đổi `loading/error`.
- Test bằng timing ngẫu nhiên khiến test flaky.

## Thang điểm 0–10

- **0–2:** Không giải thích được ordering hoặc chỉ tăng debounce.
- **3–4:** Nhận ra stale response nhưng fix/test còn mơ hồ.
- **5–6:** Giải thích đúng Promise ordering và latest-wins guard.
- **7–8:** Có cancellation, lifecycle, deterministic tests và telemetry.
- **9–10:** Phân biệt correctness/resource cancellation, side-effect semantics và đưa trade-off rõ ràng.

# Câu 2 — Deployment slot swap xong nhưng một phần request vẫn 5xx và dùng configuration sai

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure App Service, deployment slots, ASP.NET Core configuration, Managed Identity, Key Vault, health checks, CI/CD, production troubleshooting, observability

## Bối cảnh

Một ASP.NET Core API chạy Azure App Service với nhiều instances. Team deploy release mới vào staging slot, smoke test rồi swap sang production để giảm downtime. Application dùng SQL Server, một third-party API và một secret lấy qua Azure configuration/Key Vault integration. Một số settings khác nhau giữa staging và production.

Sau một release, khoảng 10–15% request production trả `500/503` trong vài phút. Một nhóm request gọi third-party sandbox endpoint thay vì production. Sau đó hệ thống tự ổn định một phần nhưng vẫn có một instance tiếp tục lỗi cho tới khi restart. Pipeline báo deployment và swap thành công.

Application Insights hiện có request/dependency telemetry nhưng log chưa luôn ghi instance identity, effective environment/config version hoặc deployment revision. Team chưa xác minh setting nào được đánh dấu slot-specific. Health endpoint hiện chỉ kiểm tra process trả HTTP, không kiểm tra dependency/configuration readiness.

Một engineer muốn rollback ngay mọi lần có 5xx; người khác nói slot swap là atomic nên configuration không thể là nguyên nhân. Một người đề xuất thêm `Thread.Sleep(30000)` vào startup để “đợi Key Vault ổn định”.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo impact → stabilize → evidence → competing hypotheses → verification → remediation → prevention như thế nào, đặc biệt để phân biệt configuration/slot-setting problem, instance warm-up/readiness problem, dependency failure và application regression?

## Câu hỏi làm rõ nên cân nhắc

1. Settings nào phải theo slot và settings nào phải đi cùng artifact/release?
2. 5xx có correlate với một App Service instance, deployment revision hoặc dependency endpoint cụ thể không?
3. Swap/warm-up behavior và health-check configuration hiện được thiết lập thế nào?
4. Application resolve secret/config lúc startup hay runtime; failure mode khi dependency/config unavailable là gì?
5. Database schema/API compatibility có cho phép safe swap-back hay release đã thực hiện irreversible change?

## Gợi ý tư duy

### Gợi ý 1

“Swap thành công” ở platform level không chứng minh mọi instance đã có đúng effective configuration và sẵn sàng phục vụ business request.

### Gợi ý 2

Tách artifact, deployment revision, slot-specific configuration, process readiness và external dependency thành các failure domains riêng.

### Gợi ý 3

Correlation theo instance + revision + dependency target thường giúp biến “10–15% request lỗi” thành một hypothesis cụ thể hơn. Rollback cũng phải xét schema/config compatibility chứ không chỉ image/code.

## Cấu trúc trả lời đề xuất

1. Xác định customer/business impact.
2. Stabilize traffic và ngăn gọi sandbox nếu có data/business risk.
3. Correlate failures theo instance/revision/endpoint.
4. Capture effective non-secret config metadata.
5. So sánh healthy vs unhealthy instance.
6. Form competing hypotheses.
7. Verify slot settings/warm-up/dependency/schema.
8. Chọn rollback hoặc forward fix theo compatibility.
9. Reproduce bằng deployment validation.
10. Bổ sung release telemetry và readiness gates.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi successful swap là bằng chứng application-level readiness.
- Phải xác minh slot-specific settings thay vì giả định.
- Correlate lỗi theo instance và dependency target.
- Không log secret value để debug configuration.
- Rollback phải xét database/schema và external side effects.

### Điểm cộng

- Structured startup log ghi configuration source/version hoặc sanitized endpoint identity.
- Health/readiness phản ánh dependency/config cần thiết để phục vụ request, nhưng không biến mọi optional dependency outage thành restart storm.
- Smoke test sau swap và synthetic check theo critical path.
- Managed Identity/Key Vault permissions được kiểm tra theo đúng slot/app identity model thực tế.

### Senior+

- Phân biệt configuration thuộc environment với configuration thuộc release và định nghĩa ownership rõ ràng.
- Thiết kế deployment contract để artifact immutable, settings auditable và rollback reproducible.
- Dùng per-instance telemetry để phát hiện partial fleet failure thay vì chỉ aggregate error rate.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định sandbox call có tạo side effect hoặc rò dữ liệu production không. Nếu có, ưu tiên chặn route/feature hoặc chuyển traffic khỏi revision/instance lỗi trước khi deep-debug. Rollback chỉ thực hiện khi biết swap-back tương thích với schema/config hiện tại; nếu release có migration breaking thì “rollback code” có thể làm incident nặng hơn.

Evidence cần được phân lớp. Từ Application Insights, group `5xx` theo cloud role instance, operation, deployment/release identifier và dependency target. Nếu 10–15% gần bằng traffic share của một instance và lỗi tập trung ở đó, hypothesis partial instance/config/warm-up mạnh hơn. Nếu tất cả instances cùng lỗi khi gọi một dependency, hướng điều tra khác.

Tôi sẽ so effective configuration giữa staging/production theo **metadata không nhạy cảm**: environment name, endpoint host, feature/config version, secret reference name/version nếu policy cho phép, không log secret value. Đồng thời kiểm tra deployment configuration xem setting nào được đánh dấu slot-specific và expected ownership của từng setting. Third-party production endpoint thường là environment configuration; pipeline phải validate nó trước khi nhận traffic.

Các hypothesis nên tồn tại song song: slot setting sai hoặc không sticky như kỳ vọng; instance chưa warm/readiness nhưng đã nhận traffic; Managed Identity/secret resolution khác giữa slots; third-party dependency lỗi; application regression; schema incompatibility; stale process/config cache. Mỗi hypothesis cần evidence riêng thay vì dùng restart như diagnostic duy nhất.

`Thread.Sleep` không tạo readiness guarantee; nó chỉ trì hoãn và che race. Tốt hơn là startup/readiness logic phải fail rõ nếu required configuration không hợp lệ, và deployment health gate phải kiểm tra critical path phù hợp. Tuy nhiên health check không nên gọi mọi remote dependency trong liveness semantics và gây restart storm khi dependency ngoài app down.

Sau incident, tôi muốn mỗi request/dependency trace có release revision và instance identity; startup event ghi sanitized effective config fingerprint/version; dashboard hiển thị error rate theo instance/revision/dependency host. Pipeline validate slot settings, smoke test staging, swap, rồi post-swap synthetic test. Nếu phát hiện một instance unhealthy, operational procedure cần có cách remove/recycle có kiểm soát và giữ evidence trước khi restart khi có thể.

Testing gồm deployment rehearsal với intentional wrong slot setting, secret access failure, slow startup, one-instance dependency/config failure và swap-back compatibility. Release process phải định nghĩa database migration strategy sao cho rollback thực tế có thể thực hiện hoặc biết rõ khi nào chỉ có forward fix.

## Mẫu trả lời trong phỏng vấn

“Em không coi swap thành công là application readiness. Trước hết em xác định sandbox call có business/security impact để chặn ngay nếu cần. Sau đó em group 5xx theo App Service instance, release revision và dependency target. Nếu lỗi tập trung khoảng traffic share của một instance, em so instance đó với healthy instances về sanitized effective config, endpoint host, identity/secret resolution và startup/readiness state.

Em giữ nhiều hypothesis: slot-specific setting sai, warm-up chưa đủ, Managed Identity/Key Vault failure, dependency outage hoặc code/schema regression. Em verify từng cái bằng telemetry/configuration thay vì restart ngay. Rollback chỉ khi schema và side effects cho phép.

Về prevention, em làm artifact immutable, phân loại rõ environment settings vs release config, validate slot settings trong pipeline, thêm post-swap synthetic checks và telemetry theo instance/revision. Em không dùng `Thread.Sleep`; readiness phải phản ánh app thật sự có thể phục vụ critical path.”

## Câu hỏi đào sâu

1. Nếu 5xx chỉ xảy ra ở một instance nhưng effective config fingerprint giống các instance khác, bạn điều tra tiếp những gì?
2. Nếu database migration mới không backward-compatible, chiến lược slot swap/rollback phải thay đổi ra sao?
3. Bạn sẽ đưa những dependency nào vào readiness và dependency nào chỉ nên monitor riêng? Vì sao?

## Lỗi trả lời thường gặp

- Tin rằng slot swap thành công nghĩa là mọi instance/application state đều đúng.
- Restart trước khi thu thập evidence cần thiết.
- Log secret để so configuration.
- Thêm sleep cố định thay cho readiness.
- Rollback code mà không xét schema/external side effects.

## Thang điểm 0–10

- **0–2:** Chỉ restart/rollback.
- **3–4:** Kiểm tra config nhưng thiếu instance correlation và competing hypotheses.
- **5–6:** Có per-instance/dependency evidence và slot-setting reasoning.
- **7–8:** Có readiness, release telemetry, rollback compatibility và deployment validation.
- **9–10:** Điều phối incident theo risk, cô lập partial fleet failure và thiết kế deployment contract có thể kiểm chứng.

# Câu 3 — Optimizely CMS + Akamai: thiết kế cache để nhanh nhưng editor vẫn publish đúng và rollback được

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, content modeling, Akamai/CDN, cache invalidation, SEO engineering, ASP.NET Core, Elasticsearch/search, reliability, observability, deployment trade-offs

## Bối cảnh

Một marketing/e-commerce website toàn cầu dùng Optimizely CMS cho editorial content và ASP.NET Core cho delivery. Website có page types, reusable content blocks, product data từ external commerce APIs và search riêng. Akamai đứng trước origin để cache public pages/assets.

Traffic đọc cao, còn publish content tương đối thấp. Business muốn giảm origin load và cải thiện Core Web Vitals, nhưng editor yêu cầu nội dung quan trọng sau publish phải xuất hiện nhanh. Một số pages có cùng content block được reuse ở hàng trăm URLs. Product price/availability thay đổi thường xuyên hơn CMS content. Một số trang được cá nhân hóa theo market/language; authenticated pages không nên bị public cache nhầm.

Team đang tranh luận ba hướng:

- Cache HTML toàn page ở CDN với TTL dài và purge khi publish.
- Chỉ cache static assets ở CDN, mọi HTML luôn về origin.
- Cache mọi thứ bằng Redis ở application để tránh purge CDN phức tạp.

Chưa có con số chính xác cho publish freshness SLO, purge rate limit, traffic theo market, tỷ lệ personalized pages hoặc mức chấp nhận stale product data. SEO yêu cầu canonical/redirect/status/metadata phải đúng theo URL/market.

## Câu hỏi chính

Bạn sẽ thiết kế content-delivery/cache architecture và decision framework thế nào để cân bằng performance, editorial freshness, correctness, personalization, SEO và operational complexity? Hãy giải thích cache key/boundary, invalidation, failure behavior, observability và rollout; không mặc định CDN/Redis hay headless architecture luôn tốt hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Freshness SLO sau publish là vài giây, vài phút hay chỉ “càng nhanh càng tốt”?
2. URL nào public/cacheable, URL nào phụ thuộc user identity, cookie, market hoặc entitlement?
3. Product price/availability có được phép stale bao lâu và có thể tách khỏi CMS HTML không?
4. Khi một shared block thay đổi, hệ thống có dependency map từ content item tới affected URLs không?
5. Akamai purge/invalidation capability và current cache-key configuration thực tế là gì?

## Gợi ý tư duy

### Gợi ý 1

Không có một TTL cho toàn website. Hãy phân loại response theo data volatility, personalization và correctness risk.

### Gợi ý 2

Invalidation cần biết **cái gì phụ thuộc vào content vừa publish**. Shared block làm bài toán phức tạp hơn purge đúng một URL.

### Gợi ý 3

Tách CMS content, commerce data và user-specific data có thể cho phép cache boundary khác nhau. Nhưng mỗi boundary thêm integration/consistency complexity; chỉ dùng nếu requirement biện minh.

## Cấu trúc trả lời đề xuất

1. Clarify freshness/security/SEO SLO.
2. Phân loại content theo cacheability/volatility.
3. Xác định origin/CDN/application cache responsibilities.
4. Thiết kế cache key cho market/language/variant.
5. Thiết kế publish invalidation/dependency mapping.
6. Tách dynamic product/user data nếu cần.
7. Định nghĩa stale/failure behavior.
8. Thiết kế observability và purge audit.
9. Rollout theo page cohort/market.
10. Load/performance/SEO/E2E test và rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không public-cache authenticated/personalized response nếu cache key/policy không bảo đảm isolation.
- TTL/invalidation phải dựa trên content/data volatility và freshness SLO.
- Shared blocks cần dependency-aware invalidation hoặc strategy chấp nhận bounded staleness.
- Product data có lifecycle khác CMS content.
- SEO correctness phải được test cùng cache/redirect/canonical behavior.

### Điểm cộng

- Cache key gồm đúng dimensions như host/market/language/content variant khi thực sự ảnh hưởng representation.
- Dùng surrogate keys/tags/dependency identifiers nếu CDN/platform hỗ trợ và đã xác minh capability.
- Có stale-while-revalidate hoặc bounded stale strategy cho content phù hợp, nhưng không áp dụng cho dữ liệu nhạy cảm/không được stale.
- Redis chỉ thêm khi có measured origin computation/data-access problem mà CDN không giải quyết.

### Senior+

- Thiết kế invalidation event idempotent/retryable và reconciliation khi purge thất bại.
- Phân biệt cache invalidation correctness với cache warming/performance.
- Có purge storm/backpressure strategy khi editor publish một shared component ảnh hưởng rất nhiều URLs.
- Chấp nhận thiết kế đơn giản hơn nếu traffic/SLO không cần multi-layer caching.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng classification thay vì chọn tool. Public editorial pages có representation ổn định theo market/language thường là candidate tốt cho CDN cache. Authenticated/user-specific pages phải bypass hoặc có isolation semantics được chứng minh; mặc định an toàn là không public-cache response phụ thuộc identity/cookie nếu chưa có thiết kế rõ. Product price/availability có volatility và business risk khác CMS copy nên không nên mặc định nhận cùng TTL.

Cache key phải chứa đúng dimensions làm response thay đổi, ví dụ host/market/language nếu chúng thật sự quyết định representation. Thêm quá nhiều dimensions làm hit ratio giảm; thiếu dimension có thể trả sai nội dung giữa markets. Cookie/header nào tham gia key phải được review cẩn thận để tránh cache fragmentation hoặc data leak.

Publish invalidation là phần khó. Nếu editor sửa một page độc lập, purge URL có thể đủ. Nếu sửa shared block được render ở hàng trăm pages, cần dependency mapping từ content item tới rendered URLs hoặc một tagging/surrogate-key mechanism nếu capability CDN hiện tại hỗ trợ. Tôi sẽ không giả định Akamai API/feature cụ thể mà chưa kiểm tra contract đang dùng. Nếu số affected URLs rất lớn, purge storm cần batching/rate control; một bounded TTL có thể là fallback nếu freshness SLO cho phép.

CMS publish event nên tạo invalidation work có identity, retry và audit. Nếu purge call timeout, trạng thái không nên bị coi là chắc chắn thất bại hay thành công nếu API semantics không cho phép; cần idempotent retry/reconciliation theo capability thực tế. Quan trọng là publish success và cache invalidation success phải được quan sát riêng: content đã publish ở origin nhưng edge vẫn stale là một failure mode cần dashboard/alert.

Product data có thể được tách khỏi long-lived cached HTML nếu requirement freshness cao, ví dụ client/server fragment/API call có cache policy ngắn hơn. Nhưng điều đó thêm request, rendering complexity và có thể ảnh hưởng SEO/Core Web Vitals, nên phải đo. Nếu price là SEO-critical server-rendered content thì strategy khác với availability widget không cần index.

Redis không thay CDN. Redis giảm application/data-source work nhưng request vẫn tới origin; CDN giảm network/origin traffic ở edge. Nếu origin rendering/database không phải bottleneck, thêm Redis chỉ tăng invalidation/state complexity. Tôi chỉ thêm application cache khi profiling cho thấy repeated expensive computation/data access và failure behavior khi Redis down đã được thiết kế.

Failure policy cần phân loại: public marketing copy có thể serve bounded stale trong origin outage nếu business chấp nhận; authenticated hoặc sensitive representation không được fallback sang public cached variant. Nếu commerce API down, có thể hiển thị controlled degradation thay vì cache price vô hạn. Mỗi policy phải được Product chấp thuận.

Observability gồm CDN hit/miss/bypass, age/cache status, origin request rate/p95, purge success/failure/latency, queue/backlog của invalidation work, publish-to-edge freshness, cache-key dimensions sampled an toàn, commerce dependency latency/error và synthetic checks theo market. SEO regression tests kiểm tra canonical, redirects, status codes, metadata, robots/crawl behavior và content consistency qua cache hit/miss.

Rollout nên theo một page type/market cohort, so origin load, hit ratio, p75/p95 web performance và freshness incidents trước khi mở rộng. Có kill switch/bypass để đưa traffic về origin khi cache rule sai. Nếu requirements đơn giản và origin đã đủ nhanh, CDN static assets + selective HTML caching có thể tốt hơn một hệ thống invalidation phức tạp.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chọn CDN-all hay Redis-all trước khi phân loại response. Public editorial pages ổn định theo market/language có thể cache ở Akamai; authenticated hoặc user-specific response mặc định bypass public cache. Product price/availability có freshness khác CMS content nên em tách policy thay vì dùng một TTL.

Cache key chỉ chứa dimensions thật sự đổi representation. Với invalidation, page publish có thể purge URL, nhưng shared block cần dependency map hoặc tag/surrogate mechanism nếu CDN contract hỗ trợ. Publish event tạo invalidation work retryable/auditable; purge failure phải có reconciliation. Nếu một block ảnh hưởng hàng nghìn URL, em cần batching/backpressure hoặc bounded TTL thay vì tạo purge storm.

Redis chỉ dùng nếu đo thấy origin computation/data access là bottleneck; nó không thay vai trò edge cache. Em monitor hit ratio, origin load, purge success, publish-to-edge freshness và synthetic checks theo market. Rollout theo cohort với bypass kill switch, đồng thời test canonical/redirect/status và personalized-cache isolation.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu mọi publish xuất hiện toàn cầu dưới 5 giây nhưng một shared block ảnh hưởng 50.000 URLs, bạn thay đổi thiết kế thế nào?
2. Nếu CDN hit ratio cao nhưng Core Web Vitals vẫn xấu, bạn điều tra những lớp nào trước khi thêm cache?
3. Team muốn đưa market vào cookie và cache HTML theo cookie value; bạn đánh giá security/correctness/cache-fragmentation risk thế nào?

## Lỗi trả lời thường gặp

- Cache toàn bộ HTML mà không phân biệt authenticated/personalized content.
- Dùng một TTL cho CMS, product và user-specific data.
- Purge đúng URL editor đang sửa nhưng quên shared block dependencies.
- Thêm Redis như giải pháp mặc định dù origin chưa phải bottleneck.
- Chỉ đo cache hit ratio mà không đo publish-to-edge freshness và SEO correctness.

## Thang điểm 0–10

- **0–2:** Chọn tool theo cảm tính, bỏ qua correctness/security.
- **3–4:** Hiểu CDN/TTL nhưng invalidation và personalization còn yếu.
- **5–6:** Có classification, cache key, dependency invalidation và failure policy.
- **7–8:** Có retry/reconciliation, purge-storm handling, observability và rollout.
- **9–10:** Cân bằng freshness/performance/SEO/security/complexity bằng conditional design và measurable SLO.
