# Code Review Challenge 1 — Upload file lớn chạy ổn ở local nhưng production tăng LOH, GC pause và OOM khi nhiều user upload đồng thời

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Blob Storage, streaming, memory allocation, LOH/GC, bounded concurrency, CancellationToken, file-upload security, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal document service chạy ASP.NET Core .NET 8. API cho phép user upload tối đa 8 tài liệu trong một request. Mỗi file thường 5–30 MB, nhưng business cho phép file lên tới 150 MB.

Sau khi production traffic tăng, team thấy:

- memory của process tăng rất nhanh trong giờ cao điểm;
- Gen 2 GC và pause time tăng rõ rệt;
- đôi lúc container bị OOMKilled khi nhiều user upload file lớn cùng lúc;
- request p95 tăng mạnh dù Azure Blob Storage latency không tăng tương ứng;
- CPU có lúc tăng trong khi phần lớn workload đáng lẽ là I/O-bound;
- khi client hủy upload, backend đôi khi vẫn tiếp tục upload blob;
- một request có 6–8 file lớn thường làm memory tăng theo cấp số nhân hơn một file đơn lẻ.

Team nghi Azure Blob Storage chậm và đề xuất tăng memory limit cho container. Service hiện tại:

## Đoạn code cần review

```csharp
public sealed class DocumentUploadService
{
    private readonly BlobContainerClient _container;
    private readonly ILogger<DocumentUploadService> _logger;

    public DocumentUploadService(
        BlobServiceClient blobServiceClient,
        ILogger<DocumentUploadService> logger)
    {
        _container = blobServiceClient
            .GetBlobContainerClient("documents");
        _logger = logger;
    }

    public async Task<IReadOnlyList<string>> UploadAsync(
        IReadOnlyList<IFormFile> files,
        string employeeId,
        CancellationToken cancellationToken)
    {
        var tasks = files.Select(file => Task.Run(async () =>
        {
            await using var memory = new MemoryStream();

            await file.CopyToAsync(memory, CancellationToken.None);

            var bytes = memory.ToArray();
            var base64 = Convert.ToBase64String(bytes);
            var payload = Encoding.UTF8.GetBytes(base64);

            var blobName = $"{employeeId}/{file.FileName}";
            var blob = _container.GetBlobClient(blobName);

            await using var uploadStream = new MemoryStream(payload);

            await blob.UploadAsync(
                uploadStream,
                overwrite: true,
                cancellationToken: CancellationToken.None);

            _logger.LogInformation(
                "Uploaded {FileName} for {EmployeeId}, {Bytes} bytes",
                file.FileName,
                employeeId,
                payload.Length);

            return blobName;
        })).ToArray();

        return await Task.WhenAll(tasks);
    }
}

[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly DocumentUploadService _service;

    public DocumentsController(DocumentUploadService service)
    {
        _service = service;
    }

    [HttpPost("upload")]
    public async Task<ActionResult<IReadOnlyList<string>>> Upload(
        [FromForm] List<IFormFile> files,
        CancellationToken cancellationToken)
    {
        var result = await _service.UploadAsync(
            files,
            User.Identity!.Name!,
            cancellationToken);

        return Ok(result);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, performance, memory, security và reliability trong implementation hiện tại.
2. Giải thích tại sao nhiều bước buffer/copy có thể làm memory amplification lớn hơn kích thước file gốc rất nhiều.
3. Phân tích vai trò của `Task.Run`, `Task.WhenAll` và việc xử lý nhiều file đồng thời trong workload I/O-bound.
4. Giải thích vì sao tăng container memory limit có thể chỉ che triệu chứng thay vì sửa root cause.
5. Đề xuất implementation/design có streaming, cancellation và bounded concurrency hợp lý.
6. Review blob naming, overwrite behavior, file size/type validation và authorization boundary.
7. Đề xuất tests và telemetry đủ để chứng minh memory behavior dưới production load.

## Câu hỏi gợi mở

1. Một file 100 MB đi qua bao nhiêu representation cùng lúc trong code hiện tại?
2. `MemoryStream.ToArray()`, Base64 và `Encoding.UTF8.GetBytes` ảnh hưởng allocation profile như thế nào?
3. `Task.Run` có giúp một async I/O operation nhanh hơn hay chỉ đưa thêm work vào ThreadPool?
4. Nếu 8 file lớn được xử lý song song, peak memory phụ thuộc vào tổng kích thước input hay từng file riêng lẻ?
5. API có nên dùng tên file do client gửi làm blob key cuối cùng không?

## Gợi ý

### Gợi ý 1

Rủi ro chính không nằm ở Azure Blob Storage mà ở **memory amplification + unbounded per-request concurrency** trước khi dữ liệu tới Blob Storage.

### Gợi ý 2

Theo dõi lifetime của từng buffer: `IFormFile` → `MemoryStream` → `byte[]` → Base64 `string` → UTF-8 `byte[]` → `MemoryStream`. Sau đó nhân với số file xử lý đồng thời.

## Kết quả code review tham khảo

### Critical — Toàn bộ file bị buffer và copy nhiều lần trước khi upload

**Vấn đề:** Code copy file vào `MemoryStream`, gọi `ToArray()`, chuyển toàn bộ byte array thành Base64 string, rồi lại encode string thành một `byte[]` khác trước khi upload.

**Tại sao xảy ra:** Mỗi bước tạo thêm một representation toàn bộ payload. Base64 còn làm dữ liệu lớn hơn file nhị phân ban đầu. Với object lớn, nhiều allocation có thể đi vào Large Object Heap và tồn tại đủ lâu để tăng áp lực Gen 2 GC.

**Ảnh hưởng production:** Peak memory có thể cao hơn nhiều lần kích thước file thực tế. Nhiều upload đồng thời làm process memory tăng rất nhanh, tăng GC pause, allocation rate và nguy cơ OOM.

**Cách sửa:** Nếu Blob Storage cần lưu file nhị phân, stream trực tiếp từ source stream tới `BlobClient.UploadAsync`. Không Base64 file nhị phân trừ khi một external contract thực sự yêu cầu text encoding. Không dùng `ToArray()` nếu không cần materialize toàn payload.

### Critical — `Task.WhenAll` cho toàn bộ files tạo concurrency không giới hạn theo kích thước request

**Vấn đề:** Tất cả file trong request được xử lý đồng thời.

**Tại sao xảy ra:** `Select(...).ToArray()` tạo một task cho mỗi file, sau đó `Task.WhenAll` cho chúng chạy song song. Khi mỗi task giữ nhiều large buffers, memory amplification diễn ra đồng thời.

**Ảnh hưởng production:** Một request có thể chiếm hàng trăm MB hoặc hơn; nhiều requests đồng thời có thể vượt memory limit rất nhanh. Tail latency và GC pressure cũng tăng.

**Cách sửa:** Giới hạn concurrency theo resource budget. Với 8 file/request và file lớn, xử lý tuần tự có thể là lựa chọn hợp lý. Nếu cần parallelism, dùng `SemaphoreSlim`, `Parallel.ForEachAsync` với `MaxDegreeOfParallelism` nhỏ hoặc queue/background workflow tùy SLO. Giá trị phải dựa trên memory, network throughput và load test.

### High — `Task.Run` quanh async I/O là không cần thiết và có thể tăng ThreadPool pressure

**Vấn đề:** Mỗi file được bọc trong `Task.Run(async () => ...)` dù phần nặng là async stream/network I/O.

**Tại sao xảy ra:** `Task.Run` phù hợp khi muốn đưa CPU-bound work sang ThreadPool; nó không biến async I/O thành “async hơn”.

**Ảnh hưởng production:** Tạo thêm scheduling overhead và ThreadPool work items. Dưới load cao, CPU/thread scheduling có thể tăng trong khi throughput không cải thiện.

**Cách sửa:** Gọi async operations trực tiếp. Nếu có bước CPU-bound thật sự như antivirus scanning/compression/hash nặng, đo riêng và quản lý concurrency cho bước đó.

### High — Cancellation từ HTTP request bị cắt đứt

**Vấn đề:** `file.CopyToAsync` và `blob.UploadAsync` đều dùng `CancellationToken.None`.

**Tại sao xảy ra:** Method nhận `cancellationToken` nhưng không propagate xuống I/O operations.

**Ảnh hưởng production:** Client disconnect hoặc request timeout vẫn có thể để server tiếp tục đọc/upload dữ liệu, tiêu tốn memory, bandwidth và Blob transactions không còn giá trị cho user.

**Cách sửa:** Truyền request token xuống toàn bộ pipeline. Phân biệt cancellation dự kiến với dependency failure trong logs/metrics. Nếu workflow cần tiếp tục sau khi client disconnect thì phải chuyển sang durable background job có contract rõ ràng, không vô tình bỏ token.

### High — Không có file size/resource budget ở service boundary

**Vấn đề:** Service không xác minh số file, size từng file hoặc tổng bytes của request.

**Tại sao xảy ra:** Code tin rằng upstream/model binding luôn bảo vệ resource usage đủ tốt.

**Ảnh hưởng production:** Một request hợp lệ về syntax nhưng quá lớn có thể tạo memory/network pressure lớn. Giới hạn ở reverse proxy/server và giới hạn ở business layer cần nhất quán.

**Cách sửa:** Xác định explicit limits: max file count, max bytes/file và max total bytes/request. Reject sớm trước khi expensive work. Với file rất lớn, cân nhắc direct-to-Blob upload bằng short-lived SAS theo policy phù hợp để app không proxy toàn bộ bytes.

### High — Blob key dùng trực tiếp `file.FileName` và `overwrite: true`

**Vấn đề:** Client-controlled filename trở thành một phần của storage identity và upload có thể overwrite blob hiện hữu.

**Tại sao xảy ra:** Tên hiển thị của file bị dùng như identifier bền vững.

**Ảnh hưởng production:** Hai file cùng tên có thể ghi đè nhau; filename có thể chứa ký tự/segment gây khó quản lý, ambiguity hoặc downstream security issues khi hiển thị lại. Nếu employee identity không đủ isolation, còn có rủi ro object-level overwrite.

**Cách sửa:** Sinh blob ID server-side, ví dụ GUID/ULID, và lưu original filename dưới metadata/database sau khi sanitize cho mục đích hiển thị. Dùng authorization/tenant scope rõ ràng. Chỉ overwrite khi đó là business operation có precondition cụ thể.

### High — Thiếu validation cho content và policy upload

**Vấn đề:** Không kiểm tra content length, allowed file types, extension/content mismatch hoặc malware policy.

**Tại sao xảy ra:** Upload được coi như byte transport thuần túy.

**Ảnh hưởng production:** Có thể lưu executable/script/content nguy hiểm rồi phát lại ở context không an toàn. Nếu blob được public hoặc download với MIME sai, blast radius tăng.

**Cách sửa:** Xác định allowlist theo business need, giới hạn size, kiểm tra metadata/content signature khi phù hợp, đặt server-generated `Content-Type`, và tích hợp malware scanning nếu threat model yêu cầu. Không tin extension hoặc client-provided MIME một mình.

### Medium — API gộp upload nhiều file vào một request nhưng không định nghĩa partial-failure semantics

**Vấn đề:** Nếu file thứ 5 fail sau khi 4 file đã upload, toàn request ném lỗi nhưng 4 blobs đã tồn tại.

**Tại sao xảy ra:** HTTP request được ngầm coi như transaction dù Blob Storage writes độc lập.

**Ảnh hưởng production:** Client retry toàn batch có thể tạo duplicate/overwrite behavior; database metadata và blob state có thể lệch nhau.

**Cách sửa:** Chọn semantics rõ ràng: per-file result, idempotency key, cleanup compensating action hoặc workflow hai pha tùy requirement. Không giả định distributed rollback miễn phí.

### Medium — Log filename/employee identifier cần data-minimization và correlation tốt hơn

**Vấn đề:** Log hiện focus vào original filename nhưng thiếu operation ID/blob ID/request correlation và outcome dimensions.

**Tại sao xảy ra:** Logging được thêm để debug đơn lẻ thay vì thiết kế cho incident investigation.

**Ảnh hưởng production:** Khó correlate memory spike với batch size, file size, blob latency và cancellation; original filename có thể chứa dữ liệu nhạy cảm không cần thiết.

**Cách sửa:** Structured logging theo upload operation ID, blob ID, size bucket, duration, result, cancellation, dependency latency; chỉ log original filename nếu policy cho phép và thật sự cần.

### Medium — `IFormFile` không đồng nghĩa với end-to-end streaming

**Vấn đề:** Dù service sửa để dùng `OpenReadStream`, multipart handling phía ASP.NET Core có thể vẫn buffer request theo hosting/form configuration.

**Tại sao xảy ra:** Streaming ở storage layer không tự động chứng minh toàn HTTP path không buffering.

**Ảnh hưởng production:** Team có thể giảm allocation trong service nhưng vẫn thấy temp-disk/memory pressure từ request parsing ở tầng trước.

**Cách sửa:** Đo thực tế request pipeline. Nếu workload có file rất lớn và throughput cao, cân nhắc streaming multipart reader hoặc direct client-to-Blob upload, tùy security và product requirements.

## Phiên bản đề xuất

Một implementation đơn giản hơn có thể xử lý file tuần tự, stream trực tiếp tới Blob Storage và giữ resource usage bounded:

```csharp
public sealed class DocumentUploadService
{
    private const int MaxFiles = 8;
    private const long MaxFileBytes = 150L * 1024 * 1024;

    private readonly BlobContainerClient _container;
    private readonly ILogger<DocumentUploadService> _logger;

    public DocumentUploadService(
        BlobServiceClient blobServiceClient,
        ILogger<DocumentUploadService> logger)
    {
        _container = blobServiceClient
            .GetBlobContainerClient("documents");
        _logger = logger;
    }

    public async Task<IReadOnlyList<UploadedDocument>> UploadAsync(
        IReadOnlyList<IFormFile> files,
        string employeeId,
        CancellationToken cancellationToken)
    {
        if (files.Count is 0 or > MaxFiles)
            throw new ValidationException("Invalid file count.");

        var results = new List<UploadedDocument>(files.Count);

        foreach (var file in files)
        {
            cancellationToken.ThrowIfCancellationRequested();

            if (file.Length <= 0 || file.Length > MaxFileBytes)
                throw new ValidationException("Invalid file size.");

            ValidateAllowedFile(file);

            var documentId = Guid.NewGuid().ToString("N");
            var blobName = $"{employeeId}/{documentId}";
            var blob = _container.GetBlobClient(blobName);

            await using var source = file.OpenReadStream(MaxFileBytes);

            var options = new BlobUploadOptions
            {
                HttpHeaders = new BlobHttpHeaders
                {
                    ContentType = GetSafeContentType(file)
                },
                Metadata = new Dictionary<string, string>
                {
                    ["documentId"] = documentId
                }
            };

            var started = Stopwatch.GetTimestamp();

            await blob.UploadAsync(
                source,
                options,
                cancellationToken);

            var elapsed = Stopwatch.GetElapsedTime(started);

            _logger.LogInformation(
                "Uploaded document {DocumentId} with {Bytes} bytes in {DurationMs} ms",
                documentId,
                file.Length,
                elapsed.TotalMilliseconds);

            results.Add(new UploadedDocument(
                documentId,
                blobName,
                file.FileName,
                file.Length));
        }

        return results;
    }

    private static void ValidateAllowedFile(IFormFile file)
    {
        var extension = Path.GetExtension(file.FileName);
        var allowed = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
        {
            ".pdf", ".docx", ".xlsx"
        };

        if (!allowed.Contains(extension))
            throw new ValidationException("File type is not allowed.");
    }

    private static string GetSafeContentType(IFormFile file)
        => Path.GetExtension(file.FileName).ToLowerInvariant() switch
        {
            ".pdf" => "application/pdf",
            ".docx" => "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
            ".xlsx" => "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
            _ => "application/octet-stream"
        };
}
```

Đoạn trên cố tình dùng **sequential upload** vì mục tiêu đầu tiên là bound peak memory và đơn giản hóa failure behavior. Nếu load test chứng minh network underutilized và memory headroom đủ, có thể tăng concurrency có kiểm soát, ví dụ tối đa 2 file/request. Không nên suy ra rằng “nhiều parallel tasks hơn” luôn tăng throughput.

Nếu workload chủ yếu là file rất lớn và application chỉ đứng giữa client và Blob Storage, một alternative đáng cân nhắc là backend authorize request rồi cấp short-lived, least-privilege SAS cho client upload trực tiếp. Cách này giảm bandwidth/memory pressure trên API nhưng tăng complexity ở authorization, upload completion verification, malware scanning và orphan cleanup.

Nếu business yêu cầu database metadata và blob phải đồng bộ, cần định nghĩa state machine như `PendingUpload → Uploaded → Verified` thay vì cố tạo distributed transaction. Cleanup job có thể xóa orphan blobs sau TTL.

## Giải thích thiết kế sau khi sửa

Thiết kế mới giữ file dưới dạng stream thay vì chuyển qua nhiều full-size buffers. Điều này làm allocation gần hơn với buffer kích thước nhỏ do SDK/streaming layer quản lý, thay vì materialize toàn payload nhiều lần.

Processing tuần tự giới hạn số upload cùng request cùng giữ resources. Đây là một trade-off có chủ đích: throughput mỗi request có thể thấp hơn, nhưng system-wide stability tốt hơn. Nếu cần parallelism, concurrency limit phải dựa trên load test với file size distribution thật.

Server-generated blob identity tách storage key khỏi filename do client kiểm soát. Original filename trở thành metadata/business data, không phải unique key.

Cancellation được propagate tới source đọc và Blob upload. Nếu user hủy request, operation có thể dừng cooperative thay vì tiếp tục làm work vô ích. Nếu product cần upload bền vững sau client disconnect, workflow phải được redesign thành background/durable flow chứ không chỉ bỏ cancellation.

## Trade-offs

Streaming trực tiếp làm việc inspect toàn file trước upload khó hơn. Nếu malware scan cần random access hoặc full-file analysis, có thể cần temp file/quarantine blob hoặc scanning pipeline riêng. Quyết định đó phải dựa trên threat model.

Sequential upload giảm peak resource usage nhưng kéo dài wall-clock time của batch. Bounded parallelism có thể cải thiện latency nhưng phải trả bằng memory/network concurrency cao hơn.

Direct-to-Blob bằng SAS giảm tải backend đáng kể nhưng đòi hỏi policy chặt về permission, expiry, blob naming, completion verification và cleanup. Không nên áp dụng chỉ vì “cloud-native hơn”.

## Cách kiểm thử

1. **Load test:** nhiều concurrent requests với file distribution 5 MB, 30 MB và 150 MB; đo working set, allocation rate, Gen 2 GC, LOH size, p95/p99 và OOM.
2. **Cancellation test:** bắt đầu upload file lớn rồi abort HTTP request; xác minh Blob upload dừng sớm hoặc partial artifact được xử lý theo policy.
3. **Security test:** filename trùng nhau, filename lạ, extension/content mismatch, oversized file; xác minh không overwrite ngoài ý muốn và request bị reject đúng boundary.
4. **Failure-path test:** Blob Storage timeout/network reset ở giữa batch; xác minh partial-success semantics/idempotency và cleanup behavior.
5. **Concurrency test:** so sánh sequential, max concurrency 2 và unbounded concurrency để chọn cấu hình dựa trên memory/throughput evidence.

## Quan sát trong production

Theo dõi:

- process working set/private bytes;
- allocation rate, Gen 0/1/2 collections, GC pause time, LOH size;
- active upload count và bytes in flight;
- upload duration p50/p95/p99 theo size bucket;
- Blob dependency duration/error/throttle metrics;
- request cancellation/disconnect count;
- rejected file count theo reason;
- OOM/container restart count;
- ThreadPool queue length/worker availability nếu nghi starvation;
- correlation ID từ HTTP request tới blob operation.

Alert nên dựa trên memory headroom, OOM/restart, elevated GC pause và error rate; không chỉ alert khi Blob latency tăng.

## Câu hỏi phỏng vấn mở rộng

1. Nếu antivirus engine bắt buộc phải scan toàn file trước khi file có thể được tải xuống, bạn thiết kế quarantine/verification flow như thế nào mà vẫn tránh giữ file lớn trong RAM?
2. Nếu user cần upload 20 file mỗi file 500 MB, bạn còn giữ proxy upload qua ASP.NET Core hay chuyển sang direct-to-Blob? Tiêu chí quyết định là gì?
3. Nếu direct SAS upload được dùng, bạn ngăn user upload blob ngoài scope hoặc giữ orphan uploads vô thời hạn như thế nào?

# Code Review Challenge 2 — Octopus rollout lên IIS farm có lúc full outage, schema mismatch và rollback không thật sự rollback

**Chủ đề:** TeamCity, Octopus Deploy, IIS, Windows Server, CI/CD, immutable artifacts, rolling deployment, database migration ordering, secrets, health checks, rollback  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một enterprise ASP.NET Core application vẫn chạy trên hai Windows Server phía sau load balancer. IIS reverse-proxy request vào ASP.NET Core process. Build được tạo bởi TeamCity và release qua Octopus Deploy.

Team muốn “zero-downtime gần nhất có thể” trong giới hạn kiến trúc hiện tại. Production database là SQL Server dùng chung cho cả hai nodes.

Sau vài release gần đây xuất hiện các sự cố:

- cả hai nodes bị unavailable cùng lúc trong một khoảng ngắn;
- node A chạy app version mới trong khi node B vẫn chạy version cũ, nhưng migration vừa thay đổi schema theo cách version cũ không hiểu;
- rollback package cũ xong application vẫn lỗi vì database đã migrate forward;
- có deployment mà hai nodes chạy binary khác nhau do package `latest` trỏ sang build mới;
- connection string xuất hiện trong deployment logs;
- app pool được start lại nhưng chưa warm xong đã được đưa vào load balancer;
- team chạy migration ở từng node để “node nào deploy cũng tự đảm bảo DB mới nhất”.

## Nhiệm vụ của ứng viên

1. Review release process theo availability, artifact integrity, migration safety, secrets và rollback.
2. Giải thích vì sao chạy hai nodes gần như đồng thời có thể gây full outage dù mỗi script chỉ stop một app pool.
3. Review việc dùng `latest.zip` thay vì một immutable artifact version.
4. Phân tích migration ordering và backward compatibility khi old/new app cùng chạy trong rolling deployment.
5. Giải thích tại sao file rollback không đồng nghĩa database rollback.
6. Review health check/warm-up trước khi node được đưa lại vào traffic.
7. Đề xuất deployment flow an toàn hơn nhưng không bắt buộc chuyển sang Kubernetes hoặc microservices.

## Câu hỏi gợi mở

1. Nếu migration drop/rename column trước khi node cũ rời traffic, node cũ sẽ phản ứng như thế nào?
2. Nếu rollback binary nhưng schema mới đã được áp dụng, “rollback thành công” có ý nghĩa gì?
3. `latest.zip` có cho phép chứng minh chính xác commit/build nào đang chạy trên từng node không?
4. Health endpoint trả `200` một lần có đủ chứng minh node đã warm, dependency ổn và sẵn sàng nhận production traffic không?
5. Có cần stop cả app pool trước khi package được chuẩn bị và validate không?

## Kết quả code review tham khảo

### Critical — Database migration chạy trên từng node và không có một migration owner duy nhất

**Vấn đề:** Mỗi IIS node chạy `EmployeePortal.Migrations.dll` trong deployment step riêng.

**Tại sao xảy ra:** Schema migration bị gắn vào lifecycle của application node thay vì release lifecycle.

**Ảnh hưởng production:** Hai nodes có thể chạy migration cạnh nhau, tạo lock contention/failure ambiguity. Quan trọng hơn, schema có thể thay đổi trong khi node cũ vẫn nhận traffic. Nếu migration không backward-compatible, old binary có thể fail ngay giữa rollout.

**Cách sửa:** Tách migration thành một explicit release step có một owner duy nhất. Migration phải được thiết kế tương thích với giai đoạn mixed-version nếu rolling rollout. Với breaking changes, dùng expand/contract: thêm cấu trúc mới trước, deploy code chuyển tiếp, migrate/backfill data, rồi chỉ remove cấu trúc cũ ở release sau khi không còn consumer cũ.

### Critical — Hai nodes deploy gần như đồng thời có thể làm mất toàn bộ serving capacity

**Vấn đề:** Release process không drain/serialize nodes; cả hai app pools có thể dừng hoặc warm cùng lúc.

**Tại sao xảy ra:** Script chỉ biết local machine state, không biết farm capacity hay node khác đang available không.

**Ảnh hưởng production:** Load balancer có thể không còn healthy backend, tạo 502/503 hoặc outage toàn hệ thống.

**Cách sửa:** Rolling deployment từng node. Trước khi chạm node B phải chứng minh node A đã healthy và đang nhận traffic. Drain node khỏi load balancer, deploy, warm, health/readiness verify, trả node vào pool, sau đó mới chuyển node kế tiếp.

### Critical — `latest.zip` phá tính immutable/reproducible của artifact

**Vấn đề:** Deployment lấy một mutable path `latest.zip`.

**Tại sao xảy ra:** Artifact identity không gắn với build/version cụ thể.

**Ảnh hưởng production:** Hai nodes trong cùng release có thể nhận hai binary khác nhau nếu `latest` thay đổi giữa các lần tải. Audit, rollback và incident reproduction trở nên không đáng tin cậy.

**Cách sửa:** TeamCity build artifact một lần với immutable version/digest. Octopus release phải pin chính xác artifact đó. Promote cùng binary qua environments; environment-specific config được inject lúc deploy, không rebuild artifact.

### High — Secret bị in ra deployment log

**Vấn đề:** Script log toàn bộ connection string.

**Tại sao xảy ra:** Diagnostic logging không phân biệt operational metadata với secret.

**Ảnh hưởng production:** Credential có thể tồn tại lâu trong CI/CD logs, backup hoặc export. Blast radius phụ thuộc quyền đọc release logs.

**Cách sửa:** Không echo secret. Dùng sensitive variable/secret store phù hợp và least privilege. Log tên target/database nếu cần nhưng redact credential/token/password.

### High — Binary rollback không rollback database schema

**Vấn đề:** Operator deploy package cũ và coi đó là rollback hoàn chỉnh.

**Tại sao xảy ra:** Application artifact và database state có lifecycle khác nhau.

**Ảnh hưởng production:** Old binary có thể không tương thích với schema mới; rollback có thể làm incident nặng hơn.

**Cách sửa:** Mỗi release phải có rollback/roll-forward plan. Ưu tiên backward-compatible schema để binary rollback vẫn hoạt động. Với destructive migration, cần explicit recovery strategy và backup/restore implications; không tự động down-migrate production chỉ để giống local development.

### High — Node chưa được drain khỏi load balancer trước khi stop app pool

**Vấn đề:** Script stop IIS app pool mà không remove node khỏi traffic trước.

**Tại sao xảy ra:** Deployment chỉ thao tác application process, không coordinate traffic routing.

**Ảnh hưởng production:** In-flight/new requests có thể fail khi process dừng. Nếu cả hai nodes cùng làm vậy, outage xảy ra ngay.

**Cách sửa:** Drain node trước: mark/remove khỏi LB, chờ bounded drain period cho in-flight requests, rồi mới stop/deploy. Sau deploy chỉ add lại khi readiness pass.

### High — Một lần `GET /health` với timeout 2 giây chưa đủ làm readiness gate

**Vấn đề:** Script start app pool rồi lập tức gọi health endpoint một lần.

**Tại sao xảy ra:** App có thể cần warm-up, JIT, config load, connection establishment hoặc cache initialization. Một transient 200 cũng không chứng minh behavior ổn dưới dependency checks cần thiết.

**Ảnh hưởng production:** Node được đưa lại vào traffic quá sớm hoặc deployment fail giả do app chưa kịp start.

**Cách sửa:** Dùng bounded polling/warm-up gate với timeout tổng hợp, ví dụ poll mỗi vài giây trong một window; health endpoint phải phân biệt process-alive và ready-to-serve theo system semantics. Chỉ return traffic khi readiness đạt ổn định.

### High — Xóa deployment directory trước khi artifact được validate tạo failure window lớn

**Vấn đề:** Script xóa toàn bộ site trước, sau đó mới expand package.

**Tại sao xảy ra:** Không có staging directory hoặc atomic-ish switch strategy.

**Ảnh hưởng production:** Nếu unzip fail, disk full hoặc package corrupt, node không còn working app để restart nhanh.

**Cách sửa:** Stage artifact vào versioned directory, verify package/hash/required files/config trước. Sau đó switch deployment target theo cơ chế phù hợp với IIS/hosting setup hoặc copy từ staged content trong maintenance window đã drain. Giữ previous version để rollback binary nhanh.

### Medium — Environment variable được set trong process script nhưng chưa chứng minh persistent configuration cho IIS worker process

**Vấn đề:** `$env:ASPNETCORE_ENVIRONMENT = "Production"` chỉ thay đổi environment của deployment process và child processes của nó; không nên mặc định rằng IIS-hosted app sẽ luôn nhận đúng config từ setting này theo cách mong muốn.

**Tại sao xảy ra:** Deployment-time shell environment bị nhầm với durable application configuration.

**Ảnh hưởng production:** Node có thể chạy sai environment/config nếu hosting config không được set đúng chỗ.

**Cách sửa:** Quản lý environment/config tại IIS/web.config/machine/application scope hoặc deployment-variable mechanism đã chuẩn hóa, rồi verify effective configuration không chứa secret ngoài ý muốn.

### Medium — Không verify version đang chạy sau deployment

**Vấn đề:** Health check chỉ xác nhận endpoint trả response, không chứng minh artifact version đúng.

**Tại sao xảy ra:** Release process thiếu deployment identity telemetry.

**Ảnh hưởng production:** Hai nodes có thể healthy nhưng chạy khác build. Incident diagnosis và rollback khó.

**Cách sửa:** Expose safe version/build metadata qua diagnostic endpoint/health details hoặc Application Insights custom dimension. Verify expected version trên từng node trước khi hoàn tất release.

### Medium — Không có explicit release-wide post-deploy verification

**Vấn đề:** Mỗi machine tự báo “completed”, nhưng không có kiểm tra toàn farm sau rollout.

**Tại sao xảy ra:** Success được định nghĩa ở node-level thay vì service-level.

**Ảnh hưởng production:** Release có thể hoàn tất dù error rate/p95 tăng hoặc hai nodes lệch version/config.

**Cách sửa:** Sau node cuối cùng, chạy smoke/API checks, verify versions, error rate, dependency health và key business path trước khi đóng release.

## Phiên bản đề xuất

Một release flow an toàn hơn có thể giữ nguyên TeamCity + Octopus + IIS, không cần đổi platform:

```text
1. TeamCity
   - Build một lần.
   - Chạy unit/integration tests.
   - Publish artifact immutable:
       EmployeePortal.2026.09.13.7421.zip
   - Gắn commit SHA/build number.

2. Octopus release preparation
   - Pin đúng artifact version.
   - Resolve environment config/secrets bằng sensitive variables/secret store.
   - Validate artifact/package metadata.

3. Database migration — chạy một lần cho toàn release
   - Acquire release-level migration ownership.
   - Chạy backward-compatible migration.
   - Verify schema version.
   - Stop release nếu migration không đạt.

4. Rolling node A
   - Drain node A khỏi load balancer.
   - Chờ in-flight requests kết thúc trong bounded timeout.
   - Stage artifact vào versioned directory.
   - Validate config/files.
   - Stop/recycle app pool nếu cần.
   - Activate version mới.
   - Start app pool.
   - Warm up.
   - Poll readiness trong bounded window.
   - Verify expected build/version.
   - Add node A trở lại load balancer.
   - Verify node A dưới traffic.

5. Rolling node B
   - Chỉ bắt đầu khi node A đã healthy.
   - Lặp lại cùng quy trình.

6. Release-wide verification
   - Smoke test business endpoints.
   - Check error rate, p95/p99, dependency failures.
   - Confirm cả hai nodes chạy cùng expected version.
```

Một PowerShell fragment cho readiness gate có thể ở dạng:

```powershell
$deadline = (Get-Date).AddMinutes(3)
$ready = $false

while ((Get-Date) -lt $deadline) {
    try {
        $response = Invoke-WebRequest `
            -Uri "http://localhost/health/ready" `
            -UseBasicParsing `
            -TimeoutSec 5

        if ($response.StatusCode -eq 200) {
            $ready = $true
            break
        }
    }
    catch {
        Start-Sleep -Seconds 5
        continue
    }

    Start-Sleep -Seconds 5
}

if (-not $ready) {
    throw "Node did not become ready within deployment window."
}
```

Đây chỉ là gate minh họa. Release thật còn phải coordinate với load balancer và verify expected version.

Với schema changes, nguyên tắc quan trọng là mixed-version compatibility. Ví dụ thay vì rename `DisplayName` thành `PreferredName` ngay lập tức:

1. add `PreferredName` nhưng giữ `DisplayName`;
2. deploy code đọc được cả hai và ghi theo strategy chuyển tiếp;
3. backfill data;
4. chuyển toàn bộ readers/writers;
5. sau khi không còn old version, remove field cũ ở release sau.

## Giải thích thiết kế sau khi sửa

Điểm chính là biến deployment từ một script local thành một **coordinated service rollout**.

Artifact immutable giải quyết câu hỏi “binary nào đang chạy?”. Migration step riêng giải quyết câu hỏi “ai sở hữu schema transition?”. Rolling node flow giải quyết availability. Readiness gate giải quyết câu hỏi “process đã thật sự phục vụ được chưa?”. Release-wide verification giải quyết câu hỏi “service sau rollout có khỏe không?”.

Không cần Kubernetes để có những nguyên tắc này. IIS farm nhỏ vẫn hưởng lợi từ immutable artifact, drain, rolling deployment, backward-compatible migration và observability.

## Trade-offs

Rolling deployment lâu hơn parallel deployment. Đổi lại, blast radius nhỏ hơn và capacity không mất đồng thời. Nếu traffic rất thấp và maintenance window được business chấp nhận, controlled downtime có thể đơn giản hơn zero-downtime giả tạo.

Expand/contract migration kéo dài lifecycle thay đổi schema và có thể cần dual-read/dual-write tạm thời. Đây là complexity có giá trị khi availability và rollback quan trọng. Với internal system có maintenance window rõ ràng, một migration trực tiếp trong downtime có thể rẻ hơn.

Giữ previous artifact giúp binary rollback nhanh nhưng tốn disk và không giải quyết destructive database change. Rollback plan phải xét cả application, schema, config và external integrations.

## Cách kiểm thử

1. **Deployment validation:** release hai nodes với synthetic traffic; xác minh luôn còn ít nhất một healthy backend và không có 5xx spike không mong muốn.
2. **Migration compatibility test:** chạy old app với expanded schema và new app với transitional schema để chứng minh mixed-version window hoạt động.
3. **Rollback test:** deploy version N+1 rồi rollback binary N; xác minh backward-compatible schema cho phép rollback path như thiết kế.
4. **Failure-path test:** làm node A fail readiness sau deploy; pipeline phải dừng trước khi đụng node B và giữ service capacity.
5. **Secret/artifact test:** scan logs để bảo đảm credential không xuất hiện; verify exact artifact checksum/version trên cả hai nodes.

## Quan sát trong production

Theo dõi:

- build/version/commit trên từng node;
- number of healthy backends trong load balancer;
- deployment phase và node hiện đang drain/deploy/ready;
- request rate, 5xx, p50/p95/p99 trong rollout;
- IIS/app process restart count và startup duration;
- Application Insights dependency failures;
- SQL migration duration, lock/blocking và schema version;
- config/version drift giữa nodes;
- rollback attempts và outcome;
- deployment logs không chứa secret.

Alert quan trọng nhất trong rollout là service capacity, error rate và node readiness; không chỉ pipeline step status.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business chấp nhận 5 phút maintenance window mỗi tháng, bạn có còn chọn rolling zero-downtime với expand/contract cho mọi schema change không? Vì sao?
2. Nếu migration mất 20 phút và lock một bảng lớn, bạn sẽ thay đổi migration strategy như thế nào trước khi nghĩ tới tăng timeout deployment?
3. Nếu node A healthy sau deploy nhưng p99 tăng gấp 4 lần khi nhận traffic thật, pipeline nên tự động quyết định gì và dựa trên metric nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Streaming không chỉ là API style; nó là công cụ giới hạn peak memory và giảm full-payload allocations trong workload file lớn.
- Nhiều bản copy của cùng payload cộng với Base64 và parallel processing có thể gây memory amplification, LOH pressure và Gen 2 GC dù dependency network vẫn khỏe.
- Async I/O không cần `Task.Run`; concurrency phải được giới hạn theo resource budget, không theo số lượng item đầu vào.
- Upload pipeline phải propagate cancellation, giới hạn size/count, tách client filename khỏi storage identity và định nghĩa partial-failure semantics.
- CI/CD production correctness phụ thuộc vào immutable artifact, một migration owner rõ ràng, backward-compatible schema, rolling node replacement, readiness gate và release-wide verification.
- Binary rollback không tự động rollback database state; rollback phải được thiết kế từ trước.

## Mẫu tư duy cần nhớ

- Theo dõi lifetime và số bản copy của dữ liệu trước khi tăng memory limit.
- Bound concurrency trước khi tối ưu throughput.
- Build once, promote the same immutable artifact.
- Tách schema transition khỏi node lifecycle.
- Drain → deploy → warm → verify → return traffic → next node.
