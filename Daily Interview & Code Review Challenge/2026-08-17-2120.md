# Code Review Challenge 1 — Cache quyền người dùng bằng object mutable làm authorization sai giữa request và giữa các instance

**Chủ đề:** Caching, authentication & authorization, concurrency, mutable state, multi-instance consistency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API có nhiều endpoint nội bộ cần kiểm tra permission của user. Để giảm số query tới database, team cache `UserPermissions` trong `IMemoryCache` trong 10 phút.

Hệ thống chạy trên 6 instance sau load balancer. Mỗi user có thể được admin thêm hoặc thu hồi permission bất kỳ lúc nào. Một số endpoint còn thêm permission tạm thời vào collection trong lúc xử lý để phục vụ logic riêng của request.

Production ghi nhận:

- user vừa bị thu hồi quyền vẫn truy cập được một số endpoint trong vài phút,
- cùng một user đôi khi được authorize khác nhau tùy instance,
- một permission tạm thời thêm ở request A đôi lúc xuất hiện ở request B,
- bug chỉ xuất hiện khi nhiều request chạy đồng thời,
- restart instance làm lỗi tạm biến mất,
- log chỉ có `Forbidden` hoặc `Allowed`, không biết quyết định dựa trên cache version nào.

Business yêu cầu việc thu hồi các permission nhạy cảm phải có hiệu lực gần như ngay lập tức, còn các permission ít nhạy cảm có thể chấp nhận eventual consistency ngắn.

## Đoạn code cần review

```csharp
public sealed class UserPermissions
{
    public Guid UserId { get; init; }
    public List<string> Permissions { get; init; } = new();
}

public sealed class PermissionService
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;

    public PermissionService(
        IMemoryCache cache,
        AppDbContext db)
    {
        _cache = cache;
        _db = db;
    }

    public async Task<UserPermissions> GetAsync(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var key = $"permissions:{userId}";

        if (_cache.TryGetValue(key, out UserPermissions? cached))
            return cached!;

        var permissions = await _db.UserPermissions
            .Where(x => x.UserId == userId)
            .Select(x => x.PermissionCode)
            .ToListAsync(cancellationToken);

        var result = new UserPermissions
        {
            UserId = userId,
            Permissions = permissions
        };

        _cache.Set(key, result, TimeSpan.FromMinutes(10));
        return result;
    }
}

public sealed class ReportsController : ControllerBase
{
    private readonly PermissionService _permissions;

    public ReportsController(PermissionService permissions)
    {
        _permissions = permissions;
    }

    [HttpGet("api/reports/export")]
    public async Task<IActionResult> Export(
        CancellationToken cancellationToken)
    {
        var userId = Guid.Parse(User.FindFirst("sub")!.Value);
        var permissions = await _permissions.GetAsync(userId, cancellationToken);

        permissions.Permissions.Add("Reports.Export.RequestScope");

        if (!permissions.Permissions.Contains("Reports.Export"))
            return Forbid();

        return Ok(new { status = "started" });
    }
}
```

## Kết quả code review tham khảo

### 1. Trả trực tiếp mutable object từ cache cho mọi request

**Problem:** `UserPermissions` chứa `List<string>` mutable và object cache được trả trực tiếp cho caller.  
**Why it happens:** `IMemoryCache` giữ reference object; nó không tự clone dữ liệu mỗi lần đọc.  
**Production impact:** Một request có thể thay đổi state mà request khác hoặc request tương lai nhìn thấy. Authorization có thể sai theo thứ tự request.  
**Severity:** Critical  
**Recommended fix:** Cache immutable representation như `ImmutableHashSet<string>` hoặc DTO/read-only structure và tuyệt đối không mutate cache entry trong request.

### 2. Request thêm permission tạm thời vào chính collection đang cache

**Problem:** `permissions.Permissions.Add(...)` sửa shared cached state.  
**Why it happens:** Logic request-scope và cache-scope bị trộn lẫn.  
**Production impact:** Permission tạm thời có thể rò sang request khác và trở thành authorization bypass nếu logic sau dựa vào collection này.  
**Severity:** Critical  
**Recommended fix:** Nếu cần permission tạm thời, tạo local copy hoặc biến riêng của request; không ghi ngược vào cache.

### 3. Cache không có cơ chế invalidation khi permission bị revoke

**Problem:** User bị thu hồi quyền vẫn dùng entry cũ cho đến khi TTL hết.  
**Why it happens:** Cache chỉ dựa vào absolute expiration 10 phút.  
**Production impact:** Revocation của permission nhạy cảm không có hiệu lực theo SLA security.  
**Severity:** Critical  
**Recommended fix:** Thiết kế invalidation theo event/version hoặc không cache các permission cần revoke gần như tức thời. Có thể cache theo `permission_version` và kiểm tra version đáng tin cậy.

### 4. `IMemoryCache` chỉ có phạm vi process

**Problem:** Mỗi instance có cache riêng.  
**Why it happens:** In-memory cache không chia sẻ state giữa 6 instance.  
**Production impact:** Cùng một user có thể được authorize khác nhau tùy request vào instance nào.  
**Severity:** High  
**Recommended fix:** Với consistency cross-instance, dùng distributed cache + invalidation/versioning hoặc publish invalidation event cho tất cả instance; với quyền cực nhạy cảm, cân nhắc authoritative check.

### 5. Có race khi nhiều request đồng thời mutate `List<string>`

**Problem:** `List<T>` không phải collection thread-safe cho concurrent writes/reads.  
**Why it happens:** Cùng reference được dùng bởi nhiều request.  
**Production impact:** Kết quả authorization không xác định, dữ liệu collection có thể quan sát trạng thái không mong muốn và lỗi khó tái hiện dưới tải.  
**Severity:** High  
**Recommended fix:** Dùng immutable collection và không mutate cache entry.

### 6. Cache stampede khi entry miss

**Problem:** Nhiều request cùng miss có thể cùng query database.  
**Why it happens:** `TryGetValue` rồi query/set không có single-flight coordination.  
**Production impact:** Khi cache hết hạn hàng loạt, DB nhận burst query không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Dùng per-key async coordination/single-flight phù hợp, hoặc distributed strategy nếu load đủ lớn.

### 7. Không encode version/source của quyết định authorization

**Problem:** Không biết permission lấy từ cache hay DB, tạo lúc nào, version nào.  
**Why it happens:** Cache layer không expose metadata observability.  
**Production impact:** Điều tra incident revoke chậm rất khó.  
**Severity:** Medium  
**Recommended fix:** Log/trace decision metadata ở mức an toàn: source, cache age, permission version, policy name, outcome; không log toàn bộ permission nhạy cảm nếu không cần.

### 8. Cache key không thể hiện tenant/security boundary nếu user id không global-unique

**Problem:** Key chỉ có `userId`.  
**Why it happens:** Thiết kế giả định user ID là global identity.  
**Production impact:** Nếu hệ thống multi-tenant cho phép cùng identifier hoặc permission phụ thuộc tenant/context, có thể trả sai authorization state.  
**Severity:** High nếu permission phụ thuộc tenant; nếu `userId` global và permission global thì không áp dụng.  
**Recommended fix:** Include đúng security scope trong key, ví dụ tenant + user + permission version, dựa trên identity đáng tin cậy.

## Phiên bản code đề xuất

```csharp
public sealed record PermissionSnapshot(
    Guid UserId,
    long Version,
    ImmutableHashSet<string> Permissions,
    DateTimeOffset LoadedAt);

public sealed class PermissionService
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;
    private readonly IUserPermissionVersionStore _versionStore;

    public PermissionService(
        IMemoryCache cache,
        AppDbContext db,
        IUserPermissionVersionStore versionStore)
    {
        _cache = cache;
        _db = db;
        _versionStore = versionStore;
    }

    public async Task<PermissionSnapshot> GetAsync(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var currentVersion = await _versionStore.GetVersionAsync(
            userId,
            cancellationToken);

        var key = $"permissions:{userId}:v{currentVersion}";

        if (_cache.TryGetValue(key, out PermissionSnapshot? cached))
            return cached!;

        var values = await _db.UserPermissions
            .AsNoTracking()
            .Where(x => x.UserId == userId)
            .Select(x => x.PermissionCode)
            .ToListAsync(cancellationToken);

        var snapshot = new PermissionSnapshot(
            userId,
            currentVersion,
            values.ToImmutableHashSet(StringComparer.Ordinal),
            DateTimeOffset.UtcNow);

        _cache.Set(key, snapshot, TimeSpan.FromMinutes(2));
        return snapshot;
    }
}

[Authorize]
[HttpGet("api/reports/export")]
public async Task<IActionResult> Export(
    CancellationToken cancellationToken)
{
    var userId = Guid.Parse(User.FindFirst("sub")!.Value);
    var snapshot = await _permissions.GetAsync(userId, cancellationToken);

    if (!snapshot.Permissions.Contains("Reports.Export"))
        return Forbid();

    var requestScopedFlags = new HashSet<string>
    {
        "Reports.Export.RequestScope"
    };

    return Ok(new
    {
        status = "started",
        permissionVersion = snapshot.Version
    });
}
```

> Đây là một **recommended approach**, không phải duy nhất. Với permission nhạy cảm cần revoke gần tức thì, việc đọc version từ distributed store vẫn phải có SLA phù hợp; trong một số hệ thống, authoritative authorization check trực tiếp có thể hợp lý hơn cache.

## Trade-offs

- Immutable snapshot tăng allocation nhẹ khi refresh nhưng loại bỏ shared mutation và đơn giản hóa concurrency reasoning.
- Version check thêm một lookup. Nếu lookup đó cũng remote, cần cân bằng latency với security SLA.
- Distributed cache giúp cross-instance consistency hơn nhưng vẫn cần invalidation strategy; nó không tự giải quyết stale cache nếu không có version/event.
- Permission ít nhạy cảm có thể dùng TTL dài hơn; permission đặc quyền nên TTL ngắn hoặc authoritative check.

## Cách kiểm thử

1. **Concurrency test:** 100 request song song cùng đọc permission; không request nào được mutate snapshot của request khác.
2. **Revocation integration test:** revoke `Reports.Export`, tăng version, request tiếp theo phải bị từ chối theo SLA đã định.
3. **Multi-instance test:** hai instance cache version cũ; sau invalidation/version bump, cả hai phải chuyển sang version mới.
4. **Stampede/load test:** cho cache expire hàng loạt và đo số DB query thực tế.
5. **Security test:** verify cache key/security scope đúng tenant và không có permission bleed giữa identity.

## Quan sát trong production

- Metric: cache hit/miss, permission version mismatch, authorization allow/deny theo policy, cache refresh duration.
- Trace: span cho permission load/version check với `source=cache|db`, không gắn full permission list.
- Log: user/tenant pseudonymous identifier phù hợp policy, policy name, decision, permission version, cache age.
- Alert khi deny/allow pattern thay đổi bất thường sau permission deployment hoặc khi cache refresh error tăng.

# Code Review Challenge 2 — `SaveChangesInterceptor` ghi audit bằng cùng `DbContext` gây recursive save và làm transaction khó kiểm soát

**Chủ đề:** EF Core transaction handling, resource/lifetime boundaries, error handling, observability, reliability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Team muốn tự động ghi audit mỗi khi entity được thêm/sửa/xóa trong EF Core. Một `SaveChangesInterceptor` được đăng ký cho `AppDbContext` và dùng `IAuditWriter` để insert bản ghi audit.

Production xuất hiện các triệu chứng:

- một số request update đơn giản lại gọi `SaveChanges` nhiều lần,
- thỉnh thoảng stack trace rất sâu hoặc request timeout,
- audit record có lúc thiếu, có lúc duplicate,
- rollback business transaction nhưng audit lại vẫn tồn tại ở một số flow,
- khi audit database chậm, latency của mọi API ghi dữ liệu tăng mạnh,
- team khó xác định audit nên thuộc cùng transaction hay transaction riêng.

Business yêu cầu audit cho các thay đổi nhạy cảm không được mất, nhưng cũng không muốn lỗi audit làm toàn bộ hệ thống ngừng hoạt động nếu audit storage tạm thời có vấn đề. Yêu cầu này chưa được phân loại chi tiết theo loại action.

## Đoạn code cần review

```csharp
public sealed class AuditSaveChangesInterceptor : SaveChangesInterceptor
{
    private readonly IAuditWriter _auditWriter;

    public AuditSaveChangesInterceptor(IAuditWriter auditWriter)
    {
        _auditWriter = auditWriter;
    }

    public override async ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        var db = (AppDbContext)eventData.Context!;

        var entries = db.ChangeTracker
            .Entries()
            .Where(x => x.State is EntityState.Added
                or EntityState.Modified
                or EntityState.Deleted)
            .ToList();

        foreach (var entry in entries)
        {
            await _auditWriter.WriteAsync(new AuditEntry
            {
                EntityName = entry.Metadata.ClrType.Name,
                EntityId = entry.Property("Id").CurrentValue?.ToString(),
                Operation = entry.State.ToString(),
                CreatedAt = DateTime.UtcNow
            }, cancellationToken);
        }

        return await base.SavingChangesAsync(
            eventData,
            result,
            cancellationToken);
    }
}

public sealed class AuditWriter : IAuditWriter
{
    private readonly AppDbContext _db;

    public AuditWriter(AppDbContext db)
    {
        _db = db;
    }

    public async Task WriteAsync(
        AuditEntry entry,
        CancellationToken cancellationToken)
    {
        _db.AuditEntries.Add(entry);
        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### 1. Recursive `SaveChangesAsync()` qua cùng interceptor

**Problem:** Interceptor gọi `IAuditWriter`, writer lại gọi `_db.SaveChangesAsync()`.  
**Why it happens:** Cùng `AppDbContext` và interceptor pipeline được dùng lại cho nested save.  
**Production impact:** Có thể recursion, repeated interception, duplicate work, stack growth hoặc timeout.  
**Severity:** Critical  
**Recommended fix:** Không gọi `SaveChanges` trên cùng intercepted context từ `SavingChanges`. Thêm audit entity vào cùng Unit of Work mà không save nested, hoặc tách audit pipeline rõ ràng.

### 2. Audit entry tự nó cũng bị ChangeTracker coi là entity cần audit

**Problem:** Khi `AuditEntry` được add, lần save tiếp theo interceptor có thể audit chính audit record.  
**Why it happens:** Query ChangeTracker không exclude loại entity audit.  
**Production impact:** Recursive/duplicate audit và tăng dữ liệu vô hạn trong case xấu.  
**Severity:** Critical  
**Recommended fix:** Exclude audit entities khỏi audit discovery; tốt hơn nữa là thiết kế flow không nested save.

### 3. Transaction semantics không rõ ràng

**Problem:** Không định nghĩa audit phải atomic với business mutation hay độc lập.  
**Why it happens:** Cross-cutting concern được thêm trước khi business requirement về failure semantics được quyết định.  
**Production impact:** Có thể business rollback nhưng audit tồn tại, hoặc business commit mà audit mất, tùy cách context/transaction thực tế vận hành.  
**Severity:** High  
**Recommended fix:** Phân loại audit. Với audit bắt buộc atomic, ghi cùng transaction. Với audit cần durable async, ghi outbox cùng transaction rồi publish sau commit.

### 4. Audit I/O nằm trên critical path của mọi write

**Problem:** Mỗi entity change thực hiện `WriteAsync` tuần tự trước khi save business.  
**Why it happens:** Audit write đồng bộ trong interceptor.  
**Production impact:** Audit storage chậm làm p95/p99 latency tất cả write endpoint tăng và có thể kéo theo timeout.  
**Severity:** High  
**Recommended fix:** Nếu business cho phép, ghi lightweight audit/outbox row trong cùng transaction rồi xử lý hậu kỳ. Nếu bắt buộc synchronous, batch writes và có SLA riêng.

### 5. Một `SaveChanges` có N changed entries tạo N nested saves

**Problem:** `foreach` gọi writer cho từng entry.  
**Why it happens:** Không batch audit entries.  
**Production impact:** Tăng round-trip DB, lock duration và latency đáng kể.  
**Severity:** High  
**Recommended fix:** Build collection audit entries và add range một lần vào Unit of Work hoặc outbox.

### 6. Audit chưa capture before/after values hoặc actor/correlation

**Problem:** Chỉ ghi entity name/id/operation.  
**Why it happens:** Audit model quá tối giản.  
**Production impact:** Khó điều tra field nào thay đổi, ai thay đổi và request nào gây ra.  
**Severity:** Medium  
**Recommended fix:** Capture actor, tenant, correlation id và changed fields theo policy; tránh lưu secret/PII không cần thiết.

### 7. Retry có thể tạo duplicate audit

**Problem:** Nếu save/retry execution strategy hoặc application retry chạy lại, audit generation không có stable operation identifier.  
**Why it happens:** Audit entry không idempotent theo business operation.  
**Production impact:** Duplicate audit và khó phân biệt retry với thao tác thật sự lặp lại.  
**Severity:** Medium  
**Recommended fix:** Gắn operation/correlation ID ổn định và unique constraint/idempotency phù hợp nếu duplicate không được phép.

### 8. Assumption về property `Id` có thể không đúng với mọi entity

**Problem:** `entry.Property("Id")` giả định entity nào cũng có scalar property tên `Id`.  
**Why it happens:** Generic interceptor không dùng metadata primary key thực tế.  
**Production impact:** Runtime error hoặc audit thiếu key với composite/nonstandard keys.  
**Severity:** Medium  
**Recommended fix:** Dùng EF metadata để đọc primary key properties và xử lý composite key.

```csharp
public sealed class AuditSaveChangesInterceptor : SaveChangesInterceptor

    public AuditSaveChangesInterceptor(ICurrentActor actor)

        _actor = actor;

        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        var db = (AppDbContext)eventData.Context!;

        var changedEntries = db.ChangeTracker
            .Entries()
            .Where(x => x.Entity is not AuditEntry)
            .Where(x => x.State is EntityState.Added
                or EntityState.Modified
                or EntityState.Deleted)
            .ToList();

        var auditEntries = changedEntries
            .Select(entry => new AuditEntry
            {
                Id = Guid.NewGuid(),
                OperationId = _actor.OperationId,
                ActorId = _actor.UserId,
                EntityName = entry.Metadata.ClrType.Name,
                EntityKey = BuildPrimaryKey(entry),
                Operation = entry.State.ToString(),
                CreatedAt = DateTime.UtcNow
            })
            .ToList();

        if (auditEntries.Count > 0)
            db.AuditEntries.AddRange(auditEntries);

        return base.SavingChangesAsync(
            eventData,
            result,
            cancellationToken);
    }

    private static string BuildPrimaryKey(EntityEntry entry)
    {
        var key = entry.Metadata.FindPrimaryKey();
        if (key is null)
            return "<no-key>";

        return string.Join(
            ",",
            key.Properties.Select(p =>
                $"{p.Name}={entry.Property(p.Name).CurrentValue}"));
    }
}
```

Trong phiên bản này, audit rows được add vào **cùng `AppDbContext` và cùng lần `SaveChanges`**, nên chúng có cùng transaction semantics với business changes nếu transaction hiện tại bao trùm save. Không có nested `SaveChanges`.

Nếu audit cần gửi sang external audit store nhưng vẫn không được mất, một hướng khác là ghi `AuditOutbox` cùng transaction, sau đó background worker publish sang store ngoài với retry + idempotency.

## Trade-offs

- Audit cùng transaction đảm bảo atomicity nhưng làm transaction lớn hơn và business write phụ thuộc database audit table.
- Outbox giảm dependency synchronous vào external audit system, nhưng audit visible trễ và cần worker/retry/cleanup.
- Capture full before/after values hữu ích nhưng tăng storage, privacy risk và write amplification; nên allowlist field cần audit.
- Interceptor tiện cho cross-cutting behavior nhưng domain-specific audit đôi khi nên explicit ở application layer để semantics rõ hơn.

## Cách kiểm thử

1. **Integration test:** business update + audit cùng commit; rollback phải rollback cả hai khi dùng atomic strategy.
2. **Failure-path test:** ép insert audit lỗi và verify business behavior đúng theo policy đã chọn.
3. **Retry test:** chạy cùng operation ID nhiều lần và verify duplicate handling/idempotency.
4. **Batch test:** thay đổi 100 entities trong một `SaveChanges`; verify không có nested save và số round-trip hợp lý.
5. **Metadata test:** entity dùng composite key/nonstandard key vẫn tạo audit key đúng.

## Quan sát trong production

- Metric: audit rows generated/save, audit failures, outbox backlog nếu dùng outbox, processing lag.
- Trace: child span cho audit persistence/publish, correlation với business operation.
- Log: operation id, actor, entity count, outcome; tránh log raw sensitive before/after nếu policy không cho phép.
- Alert khi audit failure rate, outbox age hoặc duplicate rate vượt threshold.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào audit nên nằm trong domain/application layer thay vì EF interceptor?
2. Nếu external audit service bắt buộc nhận dữ liệu trong vài giây nhưng có thể down 30 phút, bạn thiết kế recovery thế nào?
3. Với dữ liệu lương hoặc thông tin cá nhân, bạn quyết định field nào được ghi vào audit và retention ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache authorization phải được coi là một phần của security design, không chỉ là performance optimization.
- Shared mutable state trong cache có thể biến bug concurrency thành authorization bug.
- Multi-instance deployment buộc phải suy nghĩ về cache scope, invalidation và consistency SLA.
- Không gọi nested `SaveChanges` từ `SaveChangesInterceptor` trên cùng context nếu không kiểm soát recursion/lifecycle.
- Audit cần transaction semantics rõ ràng: atomic cùng business transaction hoặc durable asynchronous qua outbox.

## Mẫu tư duy cần nhớ

- Security cache phải thiết kế cùng invalidation, không chỉ TTL.
- Cache immutable data; request-scope state không được mutate shared cache entries.
- Xác định transaction boundary trước khi thêm cross-cutting persistence logic.
- Không thực hiện nested persistence trên cùng lifecycle nếu nó kích hoạt lại chính pipeline hiện tại.
- Observability phải trả lời được quyết định được tạo từ version/source nào.
