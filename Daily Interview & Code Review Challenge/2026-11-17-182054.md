# Code Review Challenge 1 — Service Bus consumer ghi nhận thanh toán trùng

**Chủ đề:** C#/.NET 8, Azure Service Bus, PostgreSQL, distributed systems  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Hệ thống e-commerce nhận sự kiện `PaymentCaptured` từ Azure Service Bus queue. Một đơn hàng chỉ được cộng doanh thu và cấp quyền sử dụng một lần. Có 6 consumer replicas, thỉnh thoảng database chậm 40 giây. Sau deployment, dashboard xuất hiện doanh thu tăng gấp đôi và một số message vào dead-letter queue. Publisher có thể gửi lại cùng business event với MessageId khác; chưa có cam kết thứ tự message. Database PostgreSQL là nguồn dữ liệu chuẩn.

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly IServiceProvider _services;
    private readonly ServiceBusProcessor _processor;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        IServiceProvider services,
        ServiceBusClient client,
        ILogger<PaymentConsumer> logger)
    {
        _services = services;
        _logger = logger;
        _processor = client.CreateProcessor("payment-captured",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = true,
                MaxConcurrentCalls = 16
            });
        _processor.ProcessMessageAsync += Handle;
        _processor.ProcessErrorAsync += Error;
    }

    private async Task Handle(ProcessMessageEventArgs args)
    {
        var evt = args.Message.Body.ToObjectFromJson<PaymentCaptured>();
        using var scope = _services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<CommerceDbContext>();

        if (await db.ProcessedMessages.AnyAsync(
            x => x.MessageId == args.Message.MessageId))
            return;

        var order = await db.Orders.SingleAsync(x => x.Id == evt.OrderId);
        order.Status = "Paid";
        db.RevenueEntries.Add(new RevenueEntry
        {
            OrderId = evt.OrderId,
            Amount = evt.Amount
        });
        await db.SaveChangesAsync();

        db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = args.Message.MessageId
        });
        await db.SaveChangesAsync();

        await args.CompleteMessageAsync(args.Message);
        _logger.LogInformation("Payment handled: {Payload}", evt);
    }

    private Task Error(ProcessErrorEventArgs args)
    {
        _logger.LogError(args.Exception, "Payment handler failed");
        return Task.CompletedTask;
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Side effects và inbox không atomic

**Vấn đề:** Revenue entry được commit trước khi ghi processed marker.  
**Tại sao xảy ra:** Hai `SaveChangesAsync` tạo hai transaction riêng (trong cấu hình thông thường). Crash giữa chúng khiến retry cộng doanh thu lần nữa.  
**Ảnh hưởng production:** Sai số liệu tài chính và cấp quyền trùng.  
**Cách sửa:** Ghi business changes và inbox marker trong một database transaction; bổ sung unique constraint.

### [Critical] — Check-then-insert race giữa replicas

**Vấn đề:** `AnyAsync` không bảo đảm chỉ một consumer xử lý.  
**Tại sao xảy ra:** Hai transaction có thể cùng đọc “chưa xử lý” trước khi insert.  
**Ảnh hưởng production:** Double processing dưới concurrency.  
**Cách sửa:** Unique index trên stable business event ID; dùng insert-first và bắt unique violation có kiểm soát, hoặc transaction phù hợp. Không dựa vào lock trong bộ nhớ.

### [High] — Idempotency key sai cấp độ nghiệp vụ

**Vấn đề:** Dùng broker `MessageId` khi publisher có thể retry với ID mới.  
**Tại sao xảy ra:** Message identity khác payment identity.  
**Ảnh hưởng production:** Một payment được ghi nhiều lần.  
**Cách sửa:** Dùng `PaymentId`/event ID bất biến do nguồn phát hành bảo đảm; unique index cho `RevenueEntries.PaymentId` và inbox key. Nếu không có khóa ổn định, phải sửa event contract trước.

### [High] — Settlement thủ công cùng auto-complete

**Vấn đề:** Processor bật `AutoCompleteMessages` nhưng handler tự complete.  
**Tại sao xảy ra:** Hai cơ chế cùng quản lý settlement; có thể phát sinh lỗi settlement hoặc trạng thái khó phân tích.  
**Ảnh hưởng production:** Retry không dự đoán được và log nhiễu.  
**Cách sửa:** Đặt `AutoCompleteMessages = false` và chỉ complete sau khi commit; xử lý duplicate đã commit bằng complete.

### [High] — Không xử lý lock expiry và cancellation

**Vấn đề:** DB chậm có thể vượt thời hạn lock; không truyền cancellation token.  
**Tại sao xảy ra:** Broker lock có hạn và tự gia hạn cũng có giới hạn; thao tác DB không được hủy theo lifecycle handler.  
**Ảnh hưởng production:** Message bị phát lại khi consumer cũ còn chạy, tăng contention.  
**Cách sửa:** Cấu hình lock renewal phù hợp, timeout có đo đạc, truyền cancellation token và bảo đảm DB idempotency dù lock hết hạn.

### [Medium] — Không xác thực event contract và trạng thái order

**Vấn đề:** Không kiểm tra payment amount, currency, trạng thái đơn, event version.  
**Tại sao xảy ra:** Handler tin payload và cập nhật `Paid` vô điều kiện.  
**Ảnh hưởng production:** Ghi nhận payment không hợp lệ hoặc đảo trạng thái nghiệp vụ.  
**Cách sửa:** Validate schema, quan hệ payment-order và state transition; quyết định rõ chính sách event đến sai thứ tự.

### [Medium] — Logging dữ liệu nhạy cảm và thiếu correlation

**Vấn đề:** Log toàn bộ payload mà không có stable event key, delivery count và trace context.  
**Tại sao xảy ra:** Structured logging chưa giới hạn field và chưa thiết kế cho incident.  
**Ảnh hưởng production:** Rò rỉ dữ liệu và khó xác định duplicate.  
**Cách sửa:** Log event ID, order ID, delivery count, outcome, duration; không log raw payment payload.

### [Medium] — Lifecycle processor chưa được quản lý trong snippet

**Vấn đề:** Không thấy start/stop/dispose processor.  
**Tại sao xảy ra:** Class không thể hiện tích hợp với `IHostedService`.  
**Ảnh hưởng production:** Consumer có thể không chạy hoặc shutdown không sạch nếu không được quản lý ở nơi khác.  
**Cách sửa:** Bọc processor trong `BackgroundService` hoặc `IHostedService`, start/stop/dispose rõ ràng; kiểm tra wiring thực tế trước khi kết luận.

## Phiên bản đề xuất

Đoạn dưới minh họa phần xử lý chính; giả định `PaymentId` là business key ổn định, `ProcessedPayments.PaymentId` và `RevenueEntries.PaymentId` có unique index. `IsUniqueViolation` là helper phân loại mã lỗi PostgreSQL `23505` đúng constraint. Processor được tạo và quản lý vòng đời ở hosted service với `AutoCompleteMessages = false`.

```csharp
private async Task Handle(ProcessMessageEventArgs args)
{
    var ct = args.CancellationToken;
    PaymentCaptured? evt;
    try
    {
        evt = args.Message.Body.ToObjectFromJson<PaymentCaptured>();
        if (evt is null || evt.PaymentId == Guid.Empty ||
            evt.OrderId == Guid.Empty || evt.Amount <= 0)
            throw new InvalidDataException("Invalid payment event");
    }
    catch (Exception ex) when (ex is JsonException or InvalidDataException)
    {
        await args.DeadLetterMessageAsync(args.Message,
            "InvalidPayload", ex.GetType().Name, ct);
        return;
    }

    await using var scope = _services.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<CommerceDbContext>();

    try
    {
        await using var tx = await db.Database.BeginTransactionAsync(ct);
        db.ProcessedPayments.Add(new ProcessedPayment
        {
            PaymentId = evt.PaymentId
        });

        var order = await db.Orders.SingleAsync(x => x.Id == evt.OrderId, ct);
        // Validate payment/order ownership, currency and allowed state transitions.
        ValidatePayment(order, evt);

        order.Status = "Paid";
        db.RevenueEntries.Add(new RevenueEntry
        {
            PaymentId = evt.PaymentId,
            OrderId = evt.OrderId,
            Amount = evt.Amount
        });

        await db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
    catch (DbUpdateException ex) when (IsUniqueViolation(ex))
    {
        // Verify which unique constraint failed and that this event
        // was already committed; otherwise rethrow for investigation.
        db.ChangeTracker.Clear();
        if (!await db.ProcessedPayments.AsNoTracking()
            .AnyAsync(x => x.PaymentId == evt.PaymentId, ct))
            throw;
    }

    await args.CompleteMessageAsync(args.Message, ct);
}
```

**Điều kiện triển khai:** `ValidatePayment` phải thực hiện các kiểm tra nghiệp vụ cụ thể; unique violation trên constraint không liên quan không được coi là duplicate. Nếu order có thể bị nhiều payment event khác nhau cập nhật đồng thời, cần optimistic concurrency hoặc conditional update và kiểm tra tổng số tiền. Lỗi không xác định nên để processor retry theo policy; phân loại poison event trước khi dead-letter.

## Giải thích thiết kế sau khi sửa

Database là ranh giới atomicity: inbox marker, revenue và order state commit cùng nhau. Complete broker message xảy ra sau commit; nếu complete thất bại, delivery tiếp theo thấy business key đã commit và complete an toàn. Unique index mới là cơ chế loại trừ race giữa các replica, không phải bước đọc `AnyAsync`.

## Trade-offs

Unique index và transaction làm tăng write contention nhưng giảm rủi ro dữ liệu tài chính. Một transaction dài giữ lock lâu; nên tối thiểu hóa I/O bên trong transaction. Inbox table cần retention policy gắn với thời gian replay nghiệp vụ, không xóa tùy tiện. Nếu hệ thống yêu cầu ordering theo order, cân nhắc Service Bus sessions hoặc versioned state transitions sau khi đo chi phí throughput.

## Cách kiểm thử

1. **Concurrency test:** 50 delivery cùng `PaymentId` trên nhiều worker; chỉ một revenue entry.
2. **Failure-path test:** Kill process sau DB commit nhưng trước complete; retry không tạo side effect.
3. **Integration test:** Publisher gửi cùng `PaymentId` với hai `MessageId` khác nhau.
4. **Database test:** Hai payment khác nhau cập nhật cùng order; xác minh invariant, currency và concurrency.
5. **Deployment test:** Scale out/in, graceful shutdown và lock expiry dưới DB latency injection.

## Quan sát trong production

Theo dõi `payment_processed_total{outcome}`, duplicate rate, handler duration p95/p99, DB transaction failures, unique-constraint conflicts, Service Bus active/dead-letter counts, delivery count và lock-lost errors. Trace nối `PaymentId`, `OrderId`, `MessageId` và correlation ID qua Application Insights; alert khi revenue duplicate invariant bị vi phạm hoặc DLQ tăng.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business event có thể bị sửa nội dung nhưng giữ `PaymentId`, bạn phát hiện conflict như thế nào?
2. Khi cần gửi email sau commit, bạn dùng Outbox Pattern ở đâu và vì sao?
3. Khi nào nên dùng Service Bus sessions thay vì optimistic concurrency trong database?

# Code Review Challenge 2 — Vue product search hiển thị sai tenant và kết quả cũ

## Bối cảnh

Admin portal dùng Vue 3 để tìm sản phẩm theo tenant. Người dùng chuyển tenant mà không reload trang. API ASP.NET Core yêu cầu Bearer token và tự thực thi tenant authorization. Support ghi nhận search result đôi khi quay về tenant trước, thao tác nhanh tạo nhiều request và một số nội dung product description xuất hiện như HTML. Có thể có nhiều request chồng nhau, token có thể hết hạn giữa phiên.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from "vue";

type Product = { id: string; name: string; description: string };
const props = defineProps<{
  tenantId: string;
  accessToken: string;
}>();

const query = ref("");
const products = ref<Product[]>([]);
const loading = ref(false);
const error = ref("");
const selected = ref<Product | null>(null);

async function loadProducts() {
  loading.value = true;
  error.value = "";
  const url = "/api/products?tenantId=" + props.tenantId +
    "&q=" + query.value;
  try {
    const response = await fetch(url, {
      headers: { Authorization: "Bearer " + props.accessToken }
    });
    const data = await response.json();
    products.value = data.items;
    sessionStorage.setItem("last-products", JSON.stringify(data.items));
  } catch (e) {
    error.value = String(e);
  } finally {
    loading.value = false;
  }
}

watch(query, loadProducts);
watch(() => props.tenantId, loadProducts);

onMounted(() => {
  const cached = sessionStorage.getItem("last-products");
  if (cached) products.value = JSON.parse(cached);
  loadProducts();
});

function choose(p: Product) {
  selected.value = p;
}
</script>

<template>
  <input v-model="query" aria-label="Search products" />
  <p v-if="error">{{ error }}</p>
  <p v-if="loading">Loading...</p>
  <ul>
    <li v-for="p in products" :key="p.id">
      <button @click="choose(p)">{{ p.name }}</button>
      <div v-html="p.description"></div>
    </li>
  </ul>
  <p v-if="selected">Selected: {{ selected.name }}</p>
</template>
```

## Kết quả code review tham khảo

### [Critical] — Unsafe HTML rendering

**Vấn đề:** `v-html` render description từ dữ liệu không được chứng minh là trusted HTML.  
**Tại sao xảy ra:** Vue không escape HTML qua directive này.  
**Ảnh hưởng production:** Stored XSS nếu nội dung do người dùng hoặc integration kiểm soát.  
**Cách sửa:** Render text bằng interpolation; nếu business thực sự cần rich text, sanitize theo allowlist ở boundary thích hợp và áp dụng CSP defense-in-depth.

### [High] — Cache không phân tách tenant/user

**Vấn đề:** Session storage dùng chung một key, không xóa khi đổi tenant.  
**Tại sao xảy ra:** State persistence không gắn identity và authorization context.  
**Ảnh hưởng production:** UI có thể hiển thị dữ liệu tenant trước, nhất là khi chuyển account trong cùng tab.  
**Cách sửa:** Không lưu sensitive results trong browser storage nếu không cần; nếu cần, partition theo user/tenant/query và invalidate khi auth context đổi. Backend vẫn phải kiểm tra tenant permission trên từng request.

### [High] — Race condition từ out-of-order responses

**Vấn đề:** Request cũ có thể overwrite kết quả request mới.  
**Tại sao xảy ra:** Watcher kích hoạt async calls độc lập không hủy hoặc xác thực response còn current.  
**Ảnh hưởng production:** Hiển thị kết quả sai tenant/query và chọn nhầm sản phẩm.  
**Cách sửa:** Abort request cũ và dùng generation counter để bỏ response stale; reset selected khi context thay đổi.

### [High] — Không xử lý HTTP error status

**Vấn đề:** `fetch` vẫn resolve đối với HTTP 401/403/500.  
**Tại sao xảy ra:** Code gọi `response.json()` và tin `data.items`.  
**Ảnh hưởng production:** UI hiển thị lỗi sai, stale data hoặc crash ở format không mong đợi.  
**Cách sửa:** Kiểm tra `response.ok`, phân loại auth failure và server failure; không tự động retry 401 vô hạn.

### [Medium] — Query string không encode

**Vấn đề:** Tenant và search term nối thẳng vào URL.  
**Tại sao xảy ra:** Không dùng `URLSearchParams`.  
**Ảnh hưởng production:** Search sai khi có `&`, `#`, Unicode hoặc dấu cách; không tự động biến thành SQL injection nếu backend parameterize đúng.  
**Cách sửa:** Dùng `URLSearchParams` và backend validation.

### [Medium] — Không debounce và loading state không chính xác

**Vấn đề:** Mỗi phím bấm phát request, request cũ có thể set `loading=false` khi request mới còn chạy.  
**Tại sao xảy ra:** Không có debounce hoặc current-request ownership.  
**Ảnh hưởng production:** Tăng tải API, nhấp nháy và UX sai.  
**Cách sửa:** Debounce search có giới hạn, chỉ request hiện hành được cập nhật loading.

### [Medium] — Selected product tồn tại sau tenant switch

**Vấn đề:** `selected` không reset theo tenant/query.  
**Tại sao xảy ra:** Component giữ local state độc lập với auth context.  
**Ảnh hưởng production:** Người dùng có thể thao tác trên product không thuộc tenant hiện hành.  
**Cách sửa:** Clear selection khi tenant hoặc identity thay đổi; backend luôn authorize mọi mutation.

## Phiên bản đề xuất

Ví dụ bỏ browser persistence và render description như plain text. Giả định `accessToken` được cung cấp từ auth layer và backend xác thực tenant; trong production nên cân nhắc auth service chịu trách nhiệm refresh token. `watch` được cleanup khi component unmount.

```vue
<script setup lang="ts">
import { ref, watch } from "vue";

type Product = { id: string; name: string; description: string };
const props = defineProps<{
  tenantId: string;
  accessToken: string;
}>();

const query = ref("");
const products = ref<Product[]>([]);
const selected = ref<Product | null>(null);
const loading = ref(false);
const error = ref("");
let generation = 0;

watch(
  [query, () => props.tenantId, () => props.accessToken],
  ([search, tenantId, token], _old, onCleanup) => {
    const id = ++generation;
    const controller = new AbortController();
    let timer: ReturnType<typeof setTimeout> | undefined;
    onCleanup(() => {
      controller.abort();
      if (timer) clearTimeout(timer);
    });

    products.value = [];
    selected.value = null;
    error.value = "";
    loading.value = true;

    timer = setTimeout(async () => {
      try {
        const params = new URLSearchParams({ tenantId, q: search });
        const response = await fetch("/api/products?" + params, {
          headers: { Authorization: "Bearer " + token },
          signal: controller.signal
        });
        if (!response.ok)
          throw new Error("Product search failed: HTTP " + response.status);

        const body: unknown = await response.json();
        if (!isProductResponse(body))
          throw new Error("Unexpected product response");

        if (id === generation) products.value = body.items;
      } catch (e) {
        if (id === generation && !controller.signal.aborted)
          error.value = e instanceof Error ? e.message : "Search failed";
      } finally {
        if (id === generation) loading.value = false;
      }
    }, 250);
  },
  { immediate: true }
);

function isProductResponse(v: unknown): v is { items: Product[] } {
  if (typeof v !== "object" || v === null || !("items" in v))
    return false;
  const items = v.items;
  return Array.isArray(items) && items.every(p =>
    p !== null && typeof p === "object" &&
    typeof p.id === "string" &&
    typeof p.name === "string" &&
    typeof p.description === "string");
}
</script>

<template>
  <input v-model="query" aria-label="Search products" />
  <p v-if="error" role="alert">{{ error }}</p>
  <p v-if="loading">Loading...</p>
  <ul>
    <li v-for="p in products" :key="p.id">
      <span>{{ p.name }}</span>
      <p>{{ p.description }}</p>
      <button @click="selected = p">Select</button>
    </li>
  </ul>
  <p v-if="selected">Selected: {{ selected.name }}</p>
</template>
```

**Lưu ý:** Đây là ví dụ component, chưa bao gồm pagination, refresh-token orchestration và giới hạn response size. `AbortController` giúp giảm công việc thừa nhưng không thay thế generation guard; server có thể đã xử lý request trước khi hủy.

## Giải thích thiết kế sau khi sửa

State gắn với bộ ba query/tenant/token; khi bất kỳ context nào đổi, dữ liệu và selection cũ được xóa. Generation guard chặn response không còn hợp lệ ngay cả khi abort đến muộn. Không dùng `v-html` tránh đưa untrusted data vào HTML parser. Backend authorization vẫn là ranh giới bảo mật cuối cùng.

## Trade-offs

Xóa cache làm tăng request khi quay lại search; có thể thêm cache phân vùng và TTL sau khi xác minh requirement, data sensitivity và invalidation. Debounce giảm tải nhưng tăng độ trễ cảm nhận khoảng 250ms; điều chỉnh dựa trên telemetry. Runtime validation tốn CPU nhưng giúp phát hiện API contract drift. Không cần thêm global state library nếu local component đủ đơn giản.

## Cách kiểm thử

1. **Component test:** Request cũ trả về sau request mới; UI chỉ hiển thị kết quả mới.
2. **Security test:** Description chứa HTML/script payload; DOM chỉ hiển thị text.
3. **E2E Playwright:** Chuyển tenant và user liên tiếp; không còn result hoặc selection từ context cũ.
4. **API integration test:** Tenant A token truy cập tenant B phải nhận 403 hoặc response được giới hạn theo policy.
5. **Failure-path test:** 401, 500, malformed JSON, abort và slow network; loading/error đúng, không phát sinh unhandled rejection.

## Quan sát trong production

Đo search request rate, cancellation count, p95 latency, 401/403/5xx, frontend error rate, stale-response discarded count (không ghi query chứa PII). Dùng correlation ID từ browser đến ASP.NET Core/Application Insights; theo dõi tenant authorization denials và network waterfall. Không ghi access token vào log.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product description phải hỗ trợ rich text từ CMS, bạn thiết kế sanitization và CSP thế nào?
2. Khi chuyển sang server-side pagination, làm sao tránh trộn các page từ hai query khác nhau?
3. Nếu dùng shared query cache như TanStack Query, cache key và invalidation policy cần chứa gì?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- At-least-once delivery đòi hỏi business idempotency, atomic database writes và explicit message settlement.
- Browser async request có thể hoàn thành sai thứ tự; cancel request không đủ nếu không bảo vệ state.
- Tenant isolation phải được thực thi ở backend, đồng thời frontend không được hiển thị dữ liệu stale.
- Security và observability là phần của correctness, không phải công việc bổ sung sau release.

## Mẫu tư duy cần nhớ

1. Xác định business invariant trước khi tối ưu throughput.
2. Thiết kế retry cùng transaction boundary và idempotency key.
3. Mọi dữ liệu từ external boundary đều cần validation và encoding phù hợp.
4. Test failure window và concurrency thay vì chỉ happy path.
5. Dùng metrics và traces để chứng minh giả thuyết production.
