# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, query execution, Change Tracker, performance diagnosis, observability

## Bối cảnh

Một ASP.NET Core API lấy danh sách nhân viên để phục vụ màn hình quản trị. Sau một thay đổi refactor, endpoint vẫn trả dữ liệu đúng nhưng số SQL command tăng mạnh, latency p95 tăng từ mức bình thường lên vài giây khi có nhiều request đồng thời. Code xây dựng một `IQueryable<Employee>`, sau đó gọi `CountAsync()`, tiếp tục thêm projection và gọi `ToListAsync()`. Một số helper còn enumerate cùng query để kiểm tra dữ liệu. Developer nói: “`IQueryable` đã lấy dữ liệu một lần rồi nên các lần dùng sau chỉ thao tác trên memory”.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra bên trong EF Core/LINQ, tại sao số SQL command có thể tăng dù chỉ có một biến `IQueryable`, misconception nằm ở đâu, production risk là gì và bạn sẽ chứng minh giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint có cần cả total count và page data không?
- Query có `Include`, lazy loading hoặc navigation access sau materialization không?
- Query dùng tracking hay read-only?
- Helper nào enumerate query và bao nhiêu lần?
- SQL thực tế, số round-trip và execution plan hiện tại ra sao?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt “xây expression tree” và “thực thi query”.
- **Gợi ý 2:** Xem các terminal operation như `CountAsync`, `AnyAsync`, `ToListAsync` và enumeration là execution boundary.
- **Gợi ý 3:** Đo SQL command count, generated SQL, tracking overhead và khả năng N+1 thay vì suy luận từ source code.

## Cấu trúc trả lời đề xuất

1. Làm rõ luồng query.
2. Giải thích deferred execution.
3. Xác định mọi execution boundary.
4. Phân biệt tracking với caching kết quả.
5. Đưa giả thuyết về round-trip/N+1.
6. Đo bằng logs/traces/profiler.
7. Tối ưu dựa trên requirement.
8. Regression test và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` đại diện cho query/expression, không phải tập kết quả đã materialize.
- Mỗi terminal operation có thể tạo một database query riêng.
- Change Tracker không đồng nghĩa EF Core sẽ cache và tái sử dụng toàn bộ kết quả của arbitrary query.
- Phải kiểm tra generated SQL và số command thực tế.

### Điểm cộng

- Read-only query cân nhắc `AsNoTracking()`.
- Projection chỉ lấy cột cần thiết.
- Pagination và count là hai query hợp lệ nếu UI thực sự cần total; vấn đề là round-trip ngoài ý muốn.
- Kiểm tra N+1 do navigation/lazy loading nếu có.

### Nâng cao

- Dùng tracing để correlate một HTTP request với từng DB span.
- Đánh giá execution plan/index thay vì chỉ tối ưu LINQ.
- Thiết lập regression test giới hạn số SQL command cho critical query khi phù hợp.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only, cần total count và một page dữ liệu. `IQueryable` chỉ xây biểu thức cho đến khi được materialize. `CountAsync()` thực thi một SQL count; `ToListAsync()` sau projection/pagination thực thi SQL khác. Nếu helper gọi `AnyAsync()` hoặc enumerate thì lại có round-trip khác. Nếu navigation được load riêng, số query còn có thể tăng theo số entity.

Không nên sửa bằng cách luôn `ToListAsync()` sớm rồi count/filter trong memory vì có thể chuyển chi phí sang network và memory. Thay vào đó, giữ filtering/pagination ở database, chỉ materialize tại boundary rõ ràng, dùng projection và `AsNoTracking()` cho read-only khi phù hợp. Nếu total count không thực sự cần, bỏ nó hoặc đổi UX sang `hasNextPage`. Nếu cần count chính xác thì chấp nhận query riêng và tối ưu nó.

Xác minh bằng EF Core command logging có kiểm soát, OpenTelemetry/APM DB spans, `ToQueryString()` trong diagnostics, database profiler/query store và execution plan. Không log dữ liệu nhạy cảm tùy tiện. Load test trước/sau và theo dõi query count/request, DB duration, p95/p99 latency, connection-pool pressure.

Khuyến nghị thay đổi nếu requirement đòi snapshot consistency giữa count và page data; khi đó cần cân nhắc transaction/isolation và trade-off về locking/versioning tùy database.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ không giả định `IQueryable` đã chứa dữ liệu. Nó chủ yếu giữ expression tree; khi gặp terminal operation như `CountAsync` hoặc `ToListAsync`, EF Core mới translate và gửi SQL. Vì vậy cùng một biến query có thể tạo nhiều round-trip. Change Tracker theo dõi entity đã materialize nhưng không biến arbitrary LINQ query thành result cache. Tôi sẽ map từng request sang DB spans để đếm command, xem generated SQL và execution plan, đồng thời kiểm tra navigation có gây N+1 không. Với endpoint read-only, tôi thường projection đúng field và cân nhắc `AsNoTracking`. Tôi không materialize sớm chỉ để tránh query thứ hai vì có thể kéo quá nhiều dữ liệu vào memory. Nếu UI cần total count thì hai query count và page có thể hoàn toàn hợp lý; mục tiêu là loại bỏ những execution ngoài ý muốn và tối ưu từng query. Sau fix tôi sẽ load test và monitor p95, DB duration, query count/request và connection-pool pressure.”

## Câu hỏi đào sâu

1. `AsNoTracking()` giúp gì và không giúp gì trong tình huống này?
2. Nếu count và page phải phản ánh cùng một snapshot dữ liệu, thiết kế thay đổi thế nào?
3. Nếu chỉ có hai SQL command nhưng latency vẫn cao, bước điều tra tiếp theo là gì?

## Lỗi trả lời thường gặp

- Nói `IQueryable` là cache.
- Materialize toàn bộ bảng để “chỉ query một lần”.
- Quy mọi vấn đề cho EF Core mà không xem SQL/execution plan.
- Bật verbose/sensitive logging trên production mà không xét dữ liệu nhạy cảm.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.0
- Communication: 1.0

# Câu 2 — Incident: Hangfire job offboarding chạy trùng và external side effect không nhất quán

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, database concurrency, external API, recovery

## Bối cảnh

Một job xử lý cấu hình offboarding đọc các mailbox đến hạn, cập nhật database rồi gọi Exchange Online/Microsoft 365 để gỡ forwarding/delegation. Sau deployment, support báo một số mailbox được xử lý hai lần, một số DB ghi “completed” nhưng external state chưa đúng, và retry làm log khó hiểu. Hệ thống có nhiều application instances. Không có bằng chứng chắc chắn rằng chỉ Hangfire gây lỗi.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ impact assessment đến root cause, short-term mitigation và thiết kế phòng ngừa dài hạn như thế nào khi database transaction không thể atomic với external Exchange operation?

## Câu hỏi làm rõ nên cân nhắc

- Job được trigger bằng recurring schedule, manual retry hay cả hai?
- Một mailbox có stable operation/idempotency key không?
- Thứ tự DB update và external call hiện tại là gì?
- External command nào idempotent, command nào có side effect/error khi chạy lại?
- Có distributed lock, unique constraint hay optimistic concurrency không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “job được thực thi nhiều lần” khỏi “business effect bị thực hiện nhiều lần”.
- **Gợi ý 2:** Không có distributed transaction tự nhiên giữa SQL và Exchange Online.
- **Gợi ý 3:** Thiết kế state machine + idempotency + reconciliation thay vì phụ thuộc vào exactly-once execution.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius.
2. Giảm side effect nguy hiểm.
3. Thu thập timeline/evidence.
4. Lập nhiều giả thuyết.
5. Reproduce và tìm root cause.
6. Fix ngắn hạn.
7. Thiết kế idempotent state machine/reconciliation.
8. Monitor và recovery drill.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không hứa exactly-once chỉ nhờ scheduler.
- Có idempotency/business key ở persistence layer.
- Phân biệt local DB transaction và remote side effect.
- Retry phải đi cùng idempotency và trạng thái có thể phục hồi.

### Điểm cộng

- State như Pending/Processing/Applied/Failed/NeedsReconciliation với attempt metadata.
- Unique constraint để chặn duplicate logical operation.
- Query external state trước/sau khi command nếu API/PowerShell semantics phù hợp.
- Backoff và phân loại transient/permanent failure.

### Nâng cao

- Lease/claim với timeout để recovery worker có thể tiếp quản abandoned work.
- Reconciliation job định kỳ so desired state với observed external state.
- Correlation ID xuyên job attempt, DB record và external operation.

## Hướng giải quyết tham khảo

Trước hết xác định mailbox bị ảnh hưởng, side effect nào nguy hiểm và có cần tạm dừng recurring execution hay chỉ giảm concurrency. Thu thập Hangfire history, application logs, DB state transitions, deployment timeline và external audit/state. Giả thuyết gồm duplicate enqueue, retry sau timeout dù remote đã thành công, hai node cùng claim record, crash giữa external call và DB commit, hoặc command external chỉ thành công một phần.

Thiết kế bền vững không dựa vào exactly-once execution. Tạo logical operation có unique business key, lưu desired state và state machine. Worker atomically claim operation bằng concurrency control/conditional update. External action nên được viết theo kiểu converge-to-desired-state khi có thể: đọc observed state, chỉ thực hiện thay đổi cần thiết, sau đó verify. Nếu process chết sau remote success nhưng trước DB update, lần retry phải có khả năng nhận ra state đã đạt mục tiêu và đánh dấu hoàn tất thay vì gây side effect mới.

Không giữ DB transaction mở trong suốt remote network call nếu điều đó tạo lock dài. Thay vào đó commit state transition ngắn, gọi remote, rồi commit result; chấp nhận intermediate state và dùng reconciliation. Theo dõi success/failure/retry rate, operation age, duplicate suppression, external latency và số record stuck.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ coi đây là distributed consistency problem chứ chưa kết luận Hangfire bị duplicate. Đầu tiên tôi xác định blast radius và nếu side effect có rủi ro thì tạm giảm hoặc dừng execution mới trong khi vẫn giữ evidence. Tôi correlate Hangfire attempts, DB transition và external state để phân biệt duplicate enqueue, concurrent claim, timeout-after-success hay crash giữa remote call và DB commit. Về thiết kế, tôi không dựa vào exactly-once. Mỗi mailbox/action cần logical operation key duy nhất; worker claim operation bằng atomic DB update hoặc concurrency token. Tôi lưu state machine và attempt metadata. Remote action nên converge về desired state và verify state sau call. Nếu remote đã thành công nhưng process chết trước khi update DB, retry phải phát hiện external state đã đúng và hoàn tất an toàn. Tôi cũng thêm reconciliation job cho các operation stuck hoặc mismatch. Trade-off là nhiều state và logic hơn, nhưng đổi lại retry và recovery trở nên deterministic và audit được.”

## Câu hỏi đào sâu

1. Vì sao distributed lock một mình chưa giải quyết crash sau external success?
2. Bạn thiết kế unique key cho operation như thế nào nếu cùng mailbox có nhiều action theo thời gian?
3. Nếu đọc external state cũng có eventual consistency, reconciliation xử lý ra sao?

## Lỗi trả lời thường gặp

- Chỉ thêm `[DisableConcurrentExecution]` rồi coi vấn đề đã giải quyết.
- Retry vô hạn mà không idempotency.
- Giữ SQL transaction qua remote call dài.
- Đánh dấu Completed trước remote call mà không có reconciliation.
- Không phân biệt transient và permanent failure.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.0
- Communication: 1.0

# Câu 3 — Thiết kế AI QA Agent có quyền chạy test và tạo đề xuất sửa code

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, deterministic validation, evaluation, auditability, security

## Bối cảnh

Team muốn nâng cấp Playwright QA automation thành agent có thể đọc test case, chạy browser test, phân tích screenshot/log/video, tìm code liên quan và đề xuất patch. Mục tiêu là giảm thời gian triage nhưng không được để model tự ý deploy, truy cập production secrets hoặc sửa repository chính mà không kiểm soát. Test đôi khi flaky; context repository lớn; mỗi run cần audit được vì AI có thể kết luận sai.

## Câu hỏi chính

Bạn sẽ thiết kế workflow AI QA Agent như thế nào để AI thực sự tạo giá trị nhưng execution, permission, validation, hallucination control, evaluation và recovery vẫn đủ an toàn cho production engineering?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ triage hay được tạo branch/PR?
- Environment nào được phép chạy test và dữ liệu test có nhạy cảm không?
- Success criterion là tìm root cause, tạo patch hay chỉ tạo evidence package?
- Tool nào cần read, tool nào cần write?
- Flaky test hiện được nhận diện thế nào?

## Gợi ý tư duy

- **Gợi ý 1:** Tách reasoning không xác định khỏi action có thể kiểm chứng.
- **Gợi ý 2:** Quyền tool phải theo least privilege; output model không phải ground truth.
- **Gợi ý 3:** Xây workflow plan → execute → collect evidence → propose → deterministic verify → human approval, với checkpoint và budget.

## Cấu trúc trả lời đề xuất

1. Làm rõ outcome và risk boundary.
2. Chọn phần cần AI và phần deterministic.
3. Thiết kế context package.
4. Định nghĩa tool/permission.
5. Structured output + evidence binding.
6. Verification/evaluation.
7. Approval/recovery.
8. Audit, cost và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho triage/reasoning, không thay thế deterministic test runner.
- Tool permissions tối thiểu và environment isolation.
- Structured output có evidence/reference.
- Patch phải build/test/lint/security check trước khi con người xem xét merge.
- Có fallback khi model/tool fail.

### Điểm cộng

- Context retrieval theo task thay vì nhét toàn repository.
- Run state/checkpoint để resume.
- Retry budget và stop conditions.
- Phân biệt flaky failure với deterministic regression bằng rerun policy có giới hạn.

### Nâng cao

- Evaluation dataset từ historical bugs/test failures.
- Metrics riêng: triage precision, patch acceptance, false-positive rate, regression escape, token/tool cost, time-to-diagnosis.
- Audit log gồm prompt version, model/version identifier khi có, tool calls, artifacts, approvals và test evidence.

## Hướng giải quyết tham khảo

AI chỉ nên xử lý phần cần semantic reasoning: tóm tắt failure, chọn evidence cần đọc, tạo hypotheses, tìm vùng code liên quan và đề xuất patch. Browser execution, test assertions, repository permissions, schema validation, build/test và policy checks phải deterministic.

Context được tạo theo từng run: requirement/test case, failure trace, screenshot/video metadata, relevant logs, git diff/recent changes và code chunks được retrieval theo evidence. Không đưa secrets hoặc dữ liệu production không cần thiết vào context.

Tool layer chia quyền: browser/test runner trên QA sandbox; repository mặc định read-only; nếu cho phép write thì chỉ branch/PR scoped và cần approval trước thao tác nhạy cảm. Model trả structured result gồm hypothesis, confidence, evidence IDs, proposed changes và verification plan. Backend reject output sai schema hoặc citation/evidence không tồn tại.

Workflow có checkpoint sau mỗi phase. Patch được áp dụng trong isolated workspace rồi chạy deterministic build, targeted tests và regression suite phù hợp. Failure không tự động “được giải thích” bởi model; evidence phải xác nhận. Human approval là gate trước merge/deploy. Khi model unavailable hoặc vượt budget, fallback là evidence package cho developer triage thủ công.

Evaluation dùng bộ historical incidents với expected diagnosis/accepted fix, đo precision của triage, false positive, patch acceptance, test pass nhưng regression sau merge, latency và cost. Audit mọi tool call và artifact để tái dựng run.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không thiết kế agent theo kiểu model được shell và repository write rồi tự quyết định mọi thứ. Tôi tách semantic reasoning khỏi deterministic execution. Test runner chạy Playwright trong QA sandbox; model nhận test case, trace, logs, screenshot metadata và code chunks liên quan, sau đó trả structured hypotheses có evidence IDs. Repository ban đầu read-only; nếu business muốn agent tạo patch thì write chỉ vào isolated branch hoặc workspace và merge luôn cần human approval. Patch phải qua build, targeted tests, regression checks và policy checks. Với flaky test tôi dùng rerun policy có giới hạn và lưu evidence, không để model tự gắn nhãn flaky. Workflow có checkpoint, retry budget và stop condition để long-running run có thể resume nhưng không loop vô hạn. Tôi đánh giá agent bằng historical failures: triage precision, false positives, patch acceptance, regression escape, latency và cost. Nếu model hoặc tool thất bại, fallback là evidence package để engineer tiếp tục thủ công. Như vậy AI giúp giảm triage time nhưng quyền thay đổi hệ thống vẫn deterministic và audit được.”

## Câu hỏi đào sâu

1. Nếu agent có MCP tool cho GitHub, bạn enforce read/write boundary ở đâu ngoài prompt?
2. Nếu patch vượt tất cả tests nhưng reasoning của model dựa trên evidence sai thì sao?
3. Khi repository quá lớn, bạn chọn context retrieval strategy thế nào và đánh giá retrieval quality ra sao?

## Lỗi trả lời thường gặp

- Cho model quyền rộng rồi dựa vào prompt “không được làm X”.
- Xem test pass là bằng chứng tuyệt đối patch đúng business requirement.
- Không có structured output/evidence binding.
- Không có evaluation dataset và quality metrics.
- Không thiết kế stop condition/cost budget cho agent loop.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` là mô tả query; materialization/terminal operation mới là execution boundary quan trọng.
- Background job cần idempotency và recovery ở business layer; scheduler không thể tự bảo đảm exactly-once side effect qua external systems.
- Khi SQL và external service không cùng transaction boundary, state machine và reconciliation thường thực tế hơn transaction kéo dài.
- AI agent nên bị giới hạn bởi deterministic permission/policy layer, structured validation và human approval ở action có rủi ro.
- Observability là một phần của thiết kế: cần correlation xuyên request/job/DB/external tool.

## Mẫu tư duy cần nhớ

- Clarify execution boundaries before optimizing.
- Measure SQL/tool calls instead of inferring from source code.
- Design retries together with idempotency and reconciliation.
- Keep remote side effects recoverable rather than pretending they are atomic.
- Validate AI output deterministically and enforce permissions outside the prompt.
