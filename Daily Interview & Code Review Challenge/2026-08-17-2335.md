# Code Review Challenge 1 — Race condition khi xử lý đặt lịch sự kiện

**Chủ đề:** Concurrency, EF Core transaction, Idempotency
**Độ khó:** Senior
**Thời gian review đề xuất:** 25 phút
**Số vấn đề cần tìm:** 6

## Bối cảnh

Một hệ thống quản lý lịch họp sử dụng ASP.NET Core và EF Core. Khi người dùng tạo cuộc họp, hệ thống kiểm tra số lượng người tham gia còn chỗ rồi tạo bản ghi đăng ký. Trong giờ cao điểm, khách hàng phản ánh có lúc số lượng người tham gia vượt giới hạn.

Code chạy trên nhiều instance API phía sau load balancer. Không có thông tin thêm về isolation level và database constraint.

## Đoạn code cần review

```csharp
public async Task<bool> RegisterAsync(Guid eventId, Guid userId)
{
    var meeting = await _db.Meetings
        .FirstAsync(x => x.Id == eventId);

    if (meeting.CurrentUsers >= meeting.MaxUsers)
    {
        return false;
    }

    var registration = new Registration
    {
        MeetingId = eventId,
        UserId = userId,
        CreatedAt = DateTime.UtcNow
    };

    _db.Registrations.Add(registration);

    meeting.CurrentUsers++;
    await _db.SaveChangesAsync();

    return true;
}
```

## Nhiệm vụ của ứng viên

1. Xác định vấn đề correctness, concurrency, performance và reliability.
2. Giải thích tác động production.
3. Đề xuất thứ tự ưu tiên xử lý.
4. Thiết kế cách sửa.
5. Nêu cách kiểm thử và quan sát production.

- Database có đang bảo vệ business rule này không?
- Nếu request retry sau timeout thì chuyện gì xảy ra?

## Kết quả code review tham khảo

### 1. Race condition khi kiểm tra số lượng

- **Severity:** Critical
- **Vấn đề:** Nhiều request có thể cùng thấy còn chỗ rồi cùng insert.
- **Impact:** Vượt giới hạn người tham gia.
- **Fix:** Transaction với concurrency control hoặc atomic database operation.

### 2. Không có idempotency

- **Severity:** High
- **Vấn đề:** Retry request có thể tạo duplicate registration.
- **Fix:** Unique constraint và idempotency handling.

### 3. Business counter dễ lệch

- **Severity:** High
- **Vấn đề:** CurrentUsers có thể không đồng bộ với Registration.
- **Fix:** Tính toán từ source of truth hoặc cập nhật atomic.

## Phiên bản code đề xuất

```csharp
await using var tx = await _db.Database.BeginTransactionAsync();

var exists = await _db.Registrations.AnyAsync(x =>
    x.MeetingId == eventId && x.UserId == userId);

if (exists) return true;

var meeting = await _db.Meetings
    .SingleAsync(x => x.Id == eventId);

if (meeting.CurrentUsers >= meeting.MaxUsers)
    return false;

_db.Registrations.Add(new Registration
{
    MeetingId = eventId,
    UserId = userId
});

meeting.CurrentUsers++;
await _db.SaveChangesAsync();
await tx.CommitAsync();
```

## Cách kiểm thử

- Concurrent requests tạo cùng event.
- Retry sau timeout.
- Load test nhiều instance API.
- Kiểm tra duplicate constraint.

## Quan sát production

- Log correlation id.
- Metric registration failure.
- Database lock monitoring.
- Trace transaction duration.

# Code Review Challenge 2 — HTTP Client và cancellation trong Background Worker

**Chủ đề:** async/await, resource lifetime, external API failure
**Độ khó:** Senior+
**Thời gian review đề xuất:** 25 phút
**Số vấn đề cần tìm:** 5

## Bối cảnh

Một Azure Worker Service đồng bộ dữ liệu từ Microsoft Graph mỗi 5 phút. Sau khi chạy vài ngày, service bị tăng memory và đôi lúc không shutdown đúng khi deploy.

## Đoạn code cần review

```csharp
public class GraphSyncWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            using var client = new HttpClient();

            var response = await client.GetAsync(
                "https://graph.microsoft.com/v1.0/users",
                stoppingToken);

            var json = await response.Content.ReadAsStringAsync();

            await SyncUsers(json);

            await Task.Delay(TimeSpan.FromMinutes(5));
        }
    }
}
```

## Nhiệm vụ của ứng viên

- Tìm lỗi runtime.
- Đánh giá lifecycle của dependency.
- Phân tích shutdown behavior.
- Đề xuất thiết kế production-ready.
- Nêu cách test.

## Câu hỏi gợi mở

- Worker có thực sự dừng khi application shutdown không?
- HttpClient lifetime nên quản lý thế nào?
- Điều gì xảy ra khi API bên ngoài chậm?

## Gợi ý

### Gợi ý 1
Xem xét cancellation propagation và resource management.

### Gợi ý 2
Xem xét IHttpClientFactory, timeout, retry và backoff.

## Kết quả code review tham khảo

### 1. Vòng lặp bỏ qua cancellation

- **Severity:** High
- **Impact:** Service không shutdown đúng.
- **Fix:** while (!stoppingToken.IsCancellationRequested).

### 2. Tạo HttpClient liên tục

- **Severity:** High
- **Impact:** Socket exhaustion và overhead.
- **Fix:** IHttpClientFactory.

### 3. Không xử lý HTTP failure

- **Severity:** Medium
- **Impact:** Sync lỗi không có recovery.
- **Fix:** retry policy, logging, alert.

### 4. Delay không nhận cancellation

- **Severity:** Medium
- **Impact:** Chậm shutdown.
- **Fix:** Task.Delay(..., stoppingToken).

## Phiên bản code đề xuất

```csharp
public class GraphSyncWorker : BackgroundService
{
    private readonly IHttpClientFactory _factory;

    public GraphSyncWorker(IHttpClientFactory factory)
    {
        _factory = factory;
    }

    protected override async Task ExecuteAsync(CancellationToken token)
    {
        while (!token.IsCancellationRequested)
        {
            try
            {
                var client = _factory.CreateClient("graph");
                var response = await client.GetAsync("users", token);
                response.EnsureSuccessStatusCode();

                await SyncUsers(await response.Content.ReadAsStringAsync(token));
            }
            catch (OperationCanceledException) when (token.IsCancellationRequested)
            {
                break;
            }

            await Task.Delay(TimeSpan.FromMinutes(5), token);
        }
    }
}
```

## Cách kiểm thử

- Shutdown khi job đang chạy.
- External API timeout.
- API trả 429.
- Memory test chạy nhiều ngày.
