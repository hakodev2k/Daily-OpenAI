# Code Review Challenge 1 — EF Core query trả đúng dữ liệu nhưng làm database và API quá tải vì cartesian explosion

**Chủ đề:** EF Core query execution, tracking, performance, memory/allocation, database behavior, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút

## Bối cảnh

Một ASP.NET Core API cung cấp màn hình chi tiết dự án. Mỗi project có khoảng 20–100 members, 100–500 tasks và vài chục recent comments. Endpoint được gọi thường xuyên bởi portal nội bộ.

Ban đầu dữ liệu nhỏ nên endpoint phản hồi dưới 300 ms. Sau vài tháng, production ghi nhận:

- một số request mất 5–12 giây,
- SQL Server/PostgreSQL CPU tăng mạnh khi nhiều user mở project cùng lúc,
- số row đọc ở database lớn hơn nhiều so với số entity thực tế,
- memory allocation phía API tăng mạnh,
- p95/p99 latency xấu nhưng p50 vẫn tương đối tốt,
- cùng một project khi có nhiều members và tasks thì latency tăng không tuyến tính.

Business yêu cầu response vẫn phải trả summary project, danh sách member đang active, 50 task gần nhất và 20 comment gần nhất. API chỉ đọc dữ liệu, không cần tracking entity để update.

## Đoạn code cần review

```csharp
public sealed class ProjectQueryService
{
    private readonly AppDbContext _db;

    public ProjectQueryService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<ProjectDetailsDto?> GetAsync(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var project = await _db.Projects
            .Include(x => x.Members)
                .ThenInclude(x => x.Employee)
            .Include(x => x.Tasks)
                .ThenInclude(x => x.Assignee)
            .Include(x => x.Comments)
                .ThenInclude(x => x.Author)
            .SingleOrDefaultAsync(
                x => x.Id == projectId,
                cancellationToken);

        if (project == null)
            return null;

        return new ProjectDetailsDto
        {
            Id = project.Id,
            Name = project.Name,
            Members = project.Members
                .Where(x => x.IsActive)
                .Select(x => new ProjectMemberDto(
                    x.Employee.Id,
                    x.Employee.DisplayName))
                .ToList(),
            Tasks = project.Tasks
                .OrderByDescending(x => x.CreatedAt)
                .Take(50)
                .Select(x => new ProjectTaskDto(
                    x.Id,
                    x.Title,
                    x.Status,
                    x.Assignee!.DisplayName))
                .ToList(),
            Comments = project.Comments
                .OrderByDescending(x => x.CreatedAt)
                .Take(20)
                .Select(x => new CommentDto(
                    x.Id,
                    x.Body,
                    x.Author.DisplayName,
                    x.CreatedAt))
                .ToList()
        };
    }
}
```

## Kết quả code review tham khảo

### 1. Nhiều collection `Include` có thể tạo cartesian explosion

**Problem:** `Members`, `Tasks` và `Comments` được eager-load trong cùng một query graph.  
**Why it happens:** Khi relational provider join nhiều collection cùng cấp, số row kết quả có thể bị nhân chéo theo số phần tử ở từng collection.  
**Production impact:** Database đọc/truyền rất nhiều row lặp, tăng CPU, network payload, materialization cost và latency.  
**Severity:** Critical  
**Recommended fix:** Không load toàn bộ graph nếu response không cần. Projection theo DTO hoặc tách query có chủ đích; nếu vẫn eager-load graph lớn, đánh giá split-query behavior và consistency requirement.

### 2. `Take(50)` và `Take(20)` diễn ra sau khi collection đã được load

**Problem:** Giới hạn task/comment nằm trên collection trong memory.  
**Why it happens:** `project.Tasks` và `project.Comments` đã được materialize bởi `Include`.  
**Production impact:** Có thể load hàng trăm/hàng nghìn row rồi mới bỏ phần lớn dữ liệu.  
**Severity:** High  
**Recommended fix:** Đưa sort/limit vào query database thông qua projection/query riêng.

### 3. Tracking không cần thiết cho read-only endpoint

**Problem:** Query mặc định theo dõi toàn bộ entity graph.  
**Why it happens:** Không dùng `AsNoTracking` hoặc projection DTO.  
**Production impact:** Change Tracker giữ thêm state và tăng allocation/CPU, đặc biệt với graph lớn.  
**Severity:** High  
**Recommended fix:** Dùng projection hoặc `AsNoTracking()` nếu không update entity.

### 4. Over-fetching rất nhiều cột và entity

**Problem:** `Include` tải toàn bộ entity trong khi DTO chỉ dùng một số field.  
**Why it happens:** Entity graph được dùng như intermediate model cho response.  
**Production impact:** Tăng network payload từ database, memory và materialization cost.  
**Severity:** High  
**Recommended fix:** Select trực tiếp đúng các field cần thiết.

### 5. Filtering active members xảy ra sau materialization

**Problem:** Chỉ active members mới cần nhưng toàn bộ members đã được load.  
**Why it happens:** Filter nằm trên navigation collection sau query.  
**Production impact:** I/O và allocation không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Filter trong projection/query database.

### 6. Assignee bị giả định luôn tồn tại

**Problem:** `x.Assignee!.DisplayName` dùng null-forgiving operator nhưng không chứng minh invariant.  
**Why it happens:** Code bỏ qua khả năng task chưa assign hoặc data cũ không thỏa invariant.  
**Production impact:** NullReferenceException ở production với một số task hợp lệ hoặc dữ liệu legacy.  
**Severity:** Medium  
**Recommended fix:** Làm rõ requirement; hỗ trợ `AssigneeName = null` hoặc enforce invariant ở domain/database.

### 7. Một query lớn dễ tạo latency tail xấu

**Problem:** Request phụ thuộc vào một SQL query phức tạp với nhiều join và lượng row phụ thuộc mạnh vào cardinality của project.  
**Why it happens:** Query shape không bounded theo output thực tế.  
**Production impact:** p95/p99 tăng mạnh ở project lớn dù p50 còn tốt.  
**Severity:** Medium  
**Recommended fix:** Thiết kế bounded queries và đo theo project size; có thể chia thành 3–4 query nhỏ chạy tuần tự hoặc song song có kiểm soát tùy connection/database load.

### 8. Không có guardrail về kích thước/đặc tính project

**Problem:** Endpoint xử lý project nhỏ và project rất lớn bằng cùng một strategy.  
**Why it happens:** Không có scale assumptions hoặc metrics theo cardinality.  
**Production impact:** Một vài project lớn có thể gây outlier và ảnh hưởng toàn DB.  
**Severity:** Medium  
**Recommended fix:** Theo dõi member/task/comment count, latency theo size; cân nhắc cache summary hoặc phân tách endpoint nếu dữ liệu rất lớn.

### 9. Thiếu observability cho query shape

**Problem:** Chỉ nhìn API latency sẽ khó biết bottleneck là database row explosion hay app materialization.  
**Why it happens:** Không thu thập SQL duration, row count, allocation và trace correlation.  
**Production impact:** Dễ tối ưu sai chỗ hoặc đổ lỗi cho database mà không có bằng chứng.  
**Severity:** Low  
**Recommended fix:** Trace query duration, số row, DB CPU/reads, application allocation và generated SQL ở môi trường phù hợp.

## Phiên bản code đề xuất

```csharp
public sealed class ProjectQueryService
{
    private readonly AppDbContext _db;

    public ProjectQueryService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<ProjectDetailsDto?> GetAsync(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var header = await _db.Projects
            .AsNoTracking()
            .Where(x => x.Id == projectId)
            .Select(x => new
            {
                x.Id,
                x.Name
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (header == null)
            return null;

        var members = await _db.ProjectMembers
            .AsNoTracking()
            .Where(x => x.ProjectId == projectId && x.IsActive)
            .OrderBy(x => x.Employee.DisplayName)
            .Select(x => new ProjectMemberDto(
                x.Employee.Id,
                x.Employee.DisplayName))
            .ToListAsync(cancellationToken);

        var tasks = await _db.ProjectTasks
            .AsNoTracking()
            .Where(x => x.ProjectId == projectId)
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(50)
            .Select(x => new ProjectTaskDto(
                x.Id,
                x.Title,
                x.Status,
                x.Assignee == null ? null : x.Assignee.DisplayName))
            .ToListAsync(cancellationToken);

        var comments = await _db.ProjectComments
            .AsNoTracking()
            .Where(x => x.ProjectId == projectId)
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(20)
            .Select(x => new CommentDto(
                x.Id,
                x.Body,
                x.Author.DisplayName,
                x.CreatedAt))
            .ToListAsync(cancellationToken);

        return new ProjectDetailsDto
        {
            Id = header.Id,
            Name = header.Name,
            Members = members,
            Tasks = tasks,
            Comments = comments
        };
    }
}
```

Điểm quan trọng của bản sửa không phải “nhiều query luôn tốt hơn một query”, mà là mỗi query có output bounded, projection rõ ràng và tránh row multiplication. Nếu yêu cầu consistency snapshot nghiêm ngặt giữa các query, cần cân nhắc transaction/isolation phù hợp. Nếu traffic read rất lớn và dữ liệu thay đổi ít, cache có thể hữu ích nhưng chỉ sau khi đo bottleneck thực tế.

## Trade-offs

- **Một query projection lớn:** ít round-trip hơn nhưng dễ phức tạp và có nguy cơ duplicate row nếu shape không phù hợp.
- **Nhiều query nhỏ:** dễ kiểm soát cardinality, SQL và memory hơn, đổi lại có thêm round-trip và cần suy nghĩ về consistency giữa các query.
- **Split query:** có thể giảm row duplication khi eager-loading graph, nhưng vẫn phải đánh giá số round-trip, consistency và lượng dữ liệu thật sự cần load.
- **Cache:** giảm DB load cho read-heavy endpoint nhưng thêm invalidation/staleness complexity.
- **Parallelize các query:** có thể giảm wall-clock latency trong vài tình huống nhưng cũng tăng concurrent DB work/connection pressure; không nên mặc định dùng nếu database đã là bottleneck.

## Cách kiểm thử

1. **Integration test correctness:** project có 80 members, 500 tasks, 100 comments; xác minh chỉ active members, đúng 50 task và 20 comment theo thứ tự.
2. **Database/performance test:** so sánh generated SQL, logical reads/row count, DB duration giữa bản cũ và bản mới.
3. **Load test:** nhiều request đồng thời trên project lớn; theo dõi p95/p99, DB CPU, connection pool và allocation.
4. **Edge-case test:** task không có assignee, project không tồn tại, project không có member/task/comment.
5. **Consistency test:** cập nhật project/task trong lúc endpoint chạy để xác định mức consistency thực tế có chấp nhận được hay cần transaction snapshot.

# Code Review Challenge 2 — Telemetry có high-cardinality làm observability backend tăng chi phí và tự gây latency

## Bối cảnh

Một team vừa thêm custom metrics và tracing cho API thanh toán nội bộ. Mục tiêu là quan sát latency, lỗi và dependency call theo tenant/user/request.

Sau khi deploy, production ghi nhận:

- số lượng time series trong metrics backend tăng rất nhanh,
- chi phí observability tăng mạnh,
- export telemetry đôi lúc tiêu tốn CPU đáng kể,
- dashboard query chậm,
- log/trace chứa email, query string và raw exception message từ downstream,
- cùng một exception được log nhiều lần ở service, controller và middleware.

Traffic khoảng 1.000–3.000 request/giây. Hệ thống multi-tenant với hàng chục nghìn user. Business cần biết tenant nào có vấn đề, endpoint nào chậm, tỷ lệ lỗi và dependency latency, nhưng không yêu cầu metric riêng cho từng user/request.

## Đoạn code cần review

```csharp
public sealed class PaymentService
{
    private static readonly Meter Meter =
        new("Payments.Api");

    private static readonly Histogram<double> Duration =
        Meter.CreateHistogram<double>("payment.duration.ms");

    private readonly HttpClient _bankClient;
    private readonly ILogger<PaymentService> _logger;

    public PaymentService(
        HttpClient bankClient,
        ILogger<PaymentService> logger)
    {
        _bankClient = bankClient;
        _logger = logger;
    }

    public async Task<PaymentResult> PayAsync(
        Guid tenantId,
        Guid userId,
        string email,
        string callbackUrl,
        decimal amount,
        CancellationToken cancellationToken)
    {
        var started = Stopwatch.GetTimestamp();
        var requestId = Guid.NewGuid().ToString();

        using var activity = new Activity("payment.process").Start();
        activity?.SetTag("tenant.id", tenantId.ToString());
        activity?.SetTag("user.id", userId.ToString());
        activity?.SetTag("user.email", email);
        activity?.SetTag("request.id", requestId);
        activity?.SetTag("callback.url", callbackUrl);
        activity?.SetTag("payment.amount", amount);

        try
        {
            var response = await _bankClient.PostAsJsonAsync(
                "/payments",
                new { tenantId, userId, amount, callbackUrl },
                cancellationToken);

            var body = await response.Content
                .ReadAsStringAsync(cancellationToken);

            if (!response.IsSuccessStatusCode)
            {
                throw new InvalidOperationException(body);
            }

            return JsonSerializer.Deserialize<PaymentResult>(body)!;
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Payment failed for tenant {TenantId}, user {UserId}, email {Email}, callback {CallbackUrl}",
                tenantId,
                userId,
                email,
                callbackUrl);

            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            Duration.Record(
                elapsed.TotalMilliseconds,
                new KeyValuePair<string, object?>("tenant.id", tenantId),
                new KeyValuePair<string, object?>("user.id", userId),
                new KeyValuePair<string, object?>("request.id", requestId),
                new KeyValuePair<string, object?>("email", email),
                new KeyValuePair<string, object?>("callback.url", callbackUrl));
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Metric dimensions có cardinality cực cao

**Problem:** `user.id`, `request.id`, `email`, `callback.url` được dùng làm metric tags.  
**Why it happens:** Thiết kế cố dùng metrics để truy vết từng request/user.  
**Production impact:** Time-series count tăng cực nhanh, tăng memory/cost ở telemetry backend, query dashboard chậm và có thể gây drop telemetry.  
**Severity:** Critical  
**Recommended fix:** Metrics chỉ dùng dimensions bounded như endpoint/operation, outcome, dependency, environment, có thể tenant-tier hoặc tenant-id nếu số tenant nhỏ và đã đánh giá cardinality. Request/user-level data nên nằm ở trace/log nếu policy cho phép.

### 2. Telemetry chứa PII và dữ liệu có thể nhạy cảm

**Problem:** Email và callback URL được ghi vào trace, log và metric labels.  
**Why it happens:** Không có data-classification/redaction policy cho telemetry.  
**Production impact:** Rủi ro privacy/security, query string có thể chứa token/secret và dữ liệu nhạy cảm bị replicate sang nhiều observability systems.  
**Severity:** Critical  
**Recommended fix:** Redact/remove PII và secret-bearing fields. Chỉ log host/path đã sanitize nếu thật sự cần; email nên loại bỏ hoặc tokenize/hash theo policy được phê duyệt.

### 3. Raw downstream response body được đưa vào exception

**Problem:** `InvalidOperationException(body)` mang toàn bộ response downstream.  
**Why it happens:** Dùng body như error message trực tiếp.  
**Production impact:** Secret/PII/downstream internals có thể lan vào logs, traces và error reporting.  
**Severity:** High  
**Recommended fix:** Parse mã lỗi an toàn/bounded; lưu response chi tiết chỉ ở kênh kiểm soát nếu business yêu cầu và có redaction.

### 4. Có nguy cơ duplicate exception logging

**Problem:** Service log exception rồi rethrow; tầng controller/middleware có thể log lần nữa.  
**Why it happens:** Không có ownership rõ ràng cho error logging.  
**Production impact:** Noise, tăng telemetry volume/cost và làm incident analysis khó hơn.  
**Severity:** Medium  
**Recommended fix:** Quy định một layer log unhandled exception; service chỉ log khi bổ sung context/actionable event mà upstream không có.

### 5. Activity được tạo thủ công bằng `new Activity`

**Problem:** Instrumentation ownership và source filtering khó kiểm soát.  
**Why it happens:** Không dùng một `ActivitySource` chuyên dụng cho component.  
**Production impact:** Khó cấu hình sampling/listener nhất quán và quản lý semantic conventions nội bộ.  
**Severity:** Medium  
**Recommended fix:** Dùng `ActivitySource` dùng chung cho component và chỉ tạo custom span khi nó bổ sung giá trị so với auto-instrumentation.

### 6. Payment amount được gắn vào trace mà chưa làm rõ policy

**Problem:** `payment.amount` có thể là business-sensitive data và không phải lúc nào cũng cần ở trace.  
**Why it happens:** Gắn toàn bộ input vào telemetry.  
**Production impact:** Tăng dữ liệu nhạy cảm/cost và tạo governance burden.  
**Severity:** Medium  
**Recommended fix:** Làm rõ use case; nếu cần phân tích, cân nhắc bucket/range hoặc aggregate metric thay vì giá trị từng payment.

### 7. Response body luôn được buffer thành string

**Problem:** Mọi response đều `ReadAsStringAsync`, kể cả payload lớn hoặc lỗi lớn.  
**Why it happens:** Client code assume response nhỏ.  
**Production impact:** Tăng allocation và có thể khuếch đại memory pressure dưới throughput cao.  
**Severity:** Medium  
**Recommended fix:** Giới hạn response size theo contract; deserialize từ stream khi phù hợp và không nhét raw body lớn vào error path.

### 8. Metrics thiếu outcome/status dimension hữu ích

**Problem:** Histogram chỉ có identity-like tags, không có outcome bounded như success/error/timeout.  
**Why it happens:** Tập trung vào “ai/request nào” thay vì “hệ thống đang hoạt động thế nào”.  
**Production impact:** Dashboard aggregate không trả lời tốt các câu hỏi operational cơ bản.  
**Severity:** Medium  
**Recommended fix:** Record tags bounded như `operation`, `result`, `dependency`, `status_class` hoặc error category.

## Phiên bản code đề xuất

```csharp
public sealed class PaymentService
{
    private static readonly ActivitySource ActivitySource =
        new("Payments.Api.PaymentService");

    private static readonly Meter Meter =
        new("Payments.Api");

    private static readonly Histogram<double> Duration =
        Meter.CreateHistogram<double>("payment.duration.ms");

    private readonly HttpClient _bankClient;

    public PaymentService(HttpClient bankClient)
    {
        _bankClient = bankClient;
    }

    public async Task<PaymentResult> PayAsync(
        Guid tenantId,
        Guid userId,
        string callbackUrl,
        decimal amount,
        CancellationToken cancellationToken)
    {
        var started = Stopwatch.GetTimestamp();
        var result = "success";

        using var activity = ActivitySource.StartActivity(
            "payment.process",
            ActivityKind.Internal);

        activity?.SetTag("payment.operation", "create");
        activity?.SetTag("tenant.id", tenantId.ToString());

        try
        {
            using var response = await _bankClient.PostAsJsonAsync(
                "/payments",
                new
                {
                    tenantId,
                    userId,
                    amount,
                    callbackUrl
                },
                cancellationToken);

            if (!response.IsSuccessStatusCode)
            {
                result = "dependency_error";
                activity?.SetTag(
                    "dependency.status_code",
                    (int)response.StatusCode);

                throw new PaymentDependencyException(
                    (int)response.StatusCode);
            }

            await using var stream = await response.Content
                .ReadAsStreamAsync(cancellationToken);

            return await JsonSerializer.DeserializeAsync<PaymentResult>(
                stream,
                cancellationToken: cancellationToken)
                ?? throw new InvalidDataException(
                    "Payment response was empty or invalid.");
        }
        catch (OperationCanceledException)
            when (cancellationToken.IsCancellationRequested)
        {
            result = "cancelled";
            throw;
        }
        catch
        {
            result = "error";
            throw;
        }
        finally
        {
            Duration.Record(
                Stopwatch.GetElapsedTime(started).TotalMilliseconds,
                new KeyValuePair<string, object?>(
                    "operation",
                    "create"),
                new KeyValuePair<string, object?>(
                    "result",
                    result));
        }
    }
}

public sealed class PaymentDependencyException : Exception
{
    public PaymentDependencyException(int statusCode)
        : base($"Payment dependency returned HTTP {statusCode}.")
    {
        StatusCode = statusCode;
    }

    public int StatusCode { get; }
}
```

Bản sửa cố tình không log email/user/request id trong metric. Nếu cần điều tra một request cụ thể, nên dựa vào trace context/correlation id do tracing infrastructure quản lý. Tenant ID có thể được giữ ở trace; nếu muốn dùng tenant trong metrics cần đánh giá rõ số lượng tenant và chi phí cardinality trước khi quyết định.

## Trade-offs

- **Metrics ít label:** rẻ, ổn định và tốt cho dashboard/alert; đổi lại không thể drill down tới từng request.
- **Trace chi tiết:** phù hợp cho request-level investigation nhưng cần sampling và retention strategy.
- **Logs có cấu trúc:** hữu ích cho audit/incident nhưng dễ tốn chi phí và lộ dữ liệu nếu không có redaction.
- **Tenant dimension:** hữu ích cho multi-tenant operations nhưng có thể trở thành high-cardinality nếu số tenant rất lớn.
- **Sampling:** giảm cost nhưng có thể bỏ mất request hiếm; error/slow-trace sampling cần policy riêng.

## Cách kiểm thử

1. **Cardinality test:** mô phỏng hàng trăm nghìn request/user khác nhau và xác minh metric series chỉ tăng theo bounded labels.
2. **Sensitive-data test:** scan exported logs/traces để đảm bảo email, raw callback URL, token/query secret và raw downstream body không xuất hiện.
3. **Failure-path test:** downstream trả 400/500/timeout; xác minh error category, trace status và metric outcome đúng, không duplicate log.
4. **Load test:** 1.000–3.000 request/giây; đo telemetry CPU/allocation/export queue và API latency.
5. **Sampling/trace test:** xác minh request chậm/lỗi vẫn đủ correlation để điều tra mà không cần metric per-request.

## Quan sát trong production

- Metric series count/cardinality theo instrument.
- Telemetry export queue/drop count và exporter latency.
- CPU/allocation do telemetry pipeline.
- API p95/p99 theo outcome/dependency.
- Error rate theo bounded error category.
- Trace sampling rate và số trace lỗi được giữ lại.
- Alert khi series count hoặc telemetry ingestion volume tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào tenant ID có thể chấp nhận được làm metric dimension, và bạn sẽ đặt guardrail nào?
2. Nếu security yêu cầu không lưu PII trong observability platform, bạn vẫn hỗ trợ điều tra user-specific incident như thế nào?
3. Nếu metric backend đã bị high-cardinality trong nhiều tháng, bạn sẽ migration dashboard và instrumentation ra sao mà không làm mất khả năng quan sát?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với EF Core, hãy đánh giá query theo **SQL shape, cardinality và row duplication**, không chỉ theo số entity mong đợi trong C#.
- Projection và giới hạn dữ liệu ở database thường quan trọng hơn việc materialize full entity graph rồi xử lý trong memory.
- Read-only workload nên tránh tracking không cần thiết.
- Metrics cần dimensions có cardinality thấp/bounded; request/user-level detail phù hợp hơn với traces hoặc logs có kiểm soát.
- Observability cũng là một workload production: telemetry quá chi tiết có thể tự gây CPU, memory, cost và privacy risk.

## Mẫu tư duy cần nhớ

- Measure the SQL shape, not only the LINQ shape.
- Bound data before materialization.
- Use metrics for aggregation, traces for request-level diagnosis.
- Treat telemetry fields as production data with privacy and cost constraints.
- Optimize based on p95/p99 and evidence, not only p50 or local tests.
