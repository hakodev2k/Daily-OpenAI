# Code Review Challenge 1 — Upload chứng từ lên Azure Blob Storage dưới tải lớn

**Chủ đề:** ASP.NET Core .NET 8, Azure Blob Storage, security, streaming, cancellation, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** khoảng 9

## Bối cảnh

API quản lý chi phí cho phép nhân viên tải hóa đơn PDF/JPEG/PNG, tối đa 25 MiB/file; nhiều nhân viên có thể upload đồng thời. Hệ thống chạy ba Azure App Service instances; Blob container dùng lưu trữ riêng tư. Một số request trả 500 khi traffic tăng; bộ nhớ tăng nhanh, có chứng từ xuất hiện trên Blob nhưng không có metadata trong SQL Server. Người dùng chỉ được tải chứng từ thuộc hồ sơ được cấp quyền. Bảo mật yêu cầu không public file, không lưu secrets trong source và không ghi nội dung file vào logs.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/expenses/{expenseId:guid}/attachments")]
public sealed class AttachmentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly ExpensesDbContext _db;
    private readonly ILogger<AttachmentsController> _log;

    public AttachmentsController(
        IConfiguration config, ExpensesDbContext db,
        ILogger<AttachmentsController> log)
    {
        _container = new BlobContainerClient(
            config["Storage:ConnectionString"], "expense-files");
        _db = db;
        _log = log;
    }

    [HttpPost]
    [RequestSizeLimit(100_000_000)]
    public async Task<IActionResult> Upload(Guid expenseId, IFormFile file)
    {
        var expense = await _db.Expenses.FindAsync(expenseId);
        if (expense == null) return NotFound();

        using var ms = new MemoryStream();
        await file.CopyToAsync(ms);
        var name = $"{expenseId}/{file.FileName}";
        var blob = _container.GetBlobClient(name);
        ms.Position = 0;

        await blob.UploadAsync(ms, overwrite: true);
        var record = new ExpenseAttachment
        {
            ExpenseId = expenseId,
            BlobName = name,
            ContentType = file.ContentType,
            Size = file.Length
        };
        _db.ExpenseAttachments.Add(record);
        await _db.SaveChangesAsync();

        _log.LogInformation("Uploaded {Name} for {ExpenseId}", name, expenseId);
        return Ok(new { record.Id, name });
    }

    [HttpGet("{attachmentId:guid}")]
    public async Task<IActionResult> Download(Guid expenseId, Guid attachmentId)
    {
        var record = await _db.ExpenseAttachments
            .FindAsync(attachmentId);
        if (record == null) return NotFound();

        var blob = _container.GetBlobClient(record.BlobName);
        var response = await blob.DownloadStreamingAsync();
        return File(response.Value.Content, record.ContentType);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Thiếu resource-level authorization

**Vấn đề:** Chỉ xác thực danh tính; bất kỳ người dùng đăng nhập nào biết `expenseId` hoặc `attachmentId` có thể upload/download vào hồ sơ khác. Download còn không kiểm tra `record.ExpenseId == expenseId`.

**Tại sao xảy ra:** `[Authorize]` không tự áp dụng quy tắc ownership.

**Ảnh hưởng production:** Lộ chứng từ và sửa dữ liệu liên tenant.

**Cách sửa:** Lấy tenant/user từ trusted claims; kiểm tra quyền trên expense trước mọi thao tác; query attachment gắn cả expenseId và tenant; trả 404/403 theo chính sách tiết lộ tài nguyên.

### [High] — Memory amplification và giới hạn file sai

**Vấn đề:** `MemoryStream` giữ toàn bộ file trong RAM; request limit 100 MB không thực thi yêu cầu 25 MiB/file.

**Tại sao xảy ra:** Mỗi upload copy một lần nữa vào managed memory; buffering của `IFormFile` có thể còn dùng memory/temp disk.

**Ảnh hưởng production:** GC pressure, LOH allocations, out-of-memory hoặc request failures khi nhiều uploads.

**Cách sửa:** Kiểm tra `file.Length` và streaming qua `OpenReadStream` với kích thước tối đa; cân nhắc streaming multipart trực tiếp cho throughput lớn và kiểm tra reverse-proxy limits.

### [High] — Ghi đè và tên Blob không an toàn

**Vấn đề:** Client kiểm soát `file.FileName`; hai request trùng tên ghi đè do `overwrite: true`.

**Tại sao xảy ra:** Blob key dựa vào input không duy nhất.

**Ảnh hưởng production:** Mất nội dung file cũ, metadata trỏ sai bytes, audit không đáng tin.

**Cách sửa:** Dùng server-generated opaque key (GUID), lưu original filename riêng sau sanitization, upload không overwrite.

### [High] — Không nhất quán Blob và database

**Vấn đề:** Upload thành công nhưng `SaveChangesAsync` thất bại để lại orphan Blob; client retry có thể tạo kết quả không dự đoán được.

**Tại sao xảy ra:** Không có atomic transaction xuyên SQL và Blob.

**Ảnh hưởng production:** Rác storage, chi phí, khó đối soát và retry.

**Cách sửa:** Trạng thái `Pending/Ready/Failed`, idempotency key nếu API yêu cầu retry an toàn, compensating deletion có kiểm soát và scheduled reconciliation.

### [High] — Tin MIME type và nội dung chưa kiểm tra

**Vấn đề:** `file.ContentType` do client cung cấp; không kiểm tra magic bytes, loại file, malware policy.

**Tại sao xảy ra:** Metadata request không chứng minh nội dung.

**Ảnh hưởng production:** Upload nội dung trái chính sách, nguy cơ khi phục vụ file về browser.

**Cách sửa:** Allowlist extension và signature, kiểm tra nội dung, quarantine/scan khi cần; khi download dùng safe Content-Type và `Content-Disposition: attachment`.

### [Medium] — Không truyền CancellationToken

**Vấn đề:** Database, copy, Blob upload/download không nhận `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Code bỏ qua cancellation.

**Ảnh hưởng production:** Công việc tiếp tục sau khi client ngắt kết nối, lãng phí bandwidth và connections.

**Cách sửa:** Truyền token xuyên call chain; không coi cancellation là cơ chế rollback.

### [Medium] — Blob client tạo trong controller và credential management

**Vấn đề:** Tạo client mỗi request; connection string phụ thuộc cấu hình secret.

**Tại sao xảy ra:** Không dùng DI/shared SDK client và identity-based authentication.

**Ảnh hưởng production:** Quản trị credential khó, chi phí kết nối/khởi tạo không cần thiết.

**Cách sửa:** Đăng ký `BlobServiceClient` singleton qua DI, ưu tiên `DefaultAzureCredential`/Managed Identity và RBAC tối thiểu; không khẳng định connection string luôn lộ nếu đã lưu trong Key Vault.

### [Medium] — Không xử lý Blob missing và response lifecycle

**Vấn đề:** SQL metadata có thể tồn tại khi Blob bị xóa hoặc storage outage; thiếu mapping lỗi 404/503 và telemetry theo dependency.

**Tại sao xảy ra:** Không có exception mapping và reconciliation.

**Ảnh hưởng production:** 500 khó chẩn đoán, UI không phân biệt file mất với lỗi tạm thời.

**Cách sửa:** Mapping `RequestFailedException` theo status, metrics, cleanup, trả ProblemDetails phù hợp.

### [Low] — Log tên file do người dùng cung cấp

**Vấn đề:** Log chứa filename tùy ý, có thể chứa thông tin nhạy cảm hoặc gây log pollution.

**Tại sao xảy ra:** Dùng blob key chứa original filename.

**Ảnh hưởng production:** Rủi ro privacy và khó correlation.

**Cách sửa:** Log attachment ID, expense ID đã được kiểm soát và operation ID; tránh original filename.

## Phiên bản đề xuất

Ví dụ minh họa core flow, giả định `IAccessPolicy` thực thi authorization theo resource, `IFileInspector` xác thực file signature và `IUploadReconciler` dọn trạng thái lỗi. Cấu hình DI/Managed Identity, migrations, malware scanning và exception middleware được triển khai riêng.

```csharp
[Authorize]
[ApiController]
[Route("api/expenses/{expenseId:guid}/attachments")]
public sealed class AttachmentsController(
    ExpensesDbContext db,
    BlobContainerClient container,
    IAccessPolicy access,
    IFileInspector inspector,
    ILogger<AttachmentsController> log) : ControllerBase
{
    private const long MaxBytes = 25L * 1024 * 1024;

    [HttpPost]
    [RequestSizeLimit(27L * 1024 * 1024)]
    public async Task<IActionResult> Upload(
        Guid expenseId, IFormFile file, CancellationToken ct)
    {
        if (!await access.CanEditExpenseAsync(User, expenseId, ct))
            return Forbid();
        if (file is null || file.Length == 0 || file.Length > MaxBytes)
            return BadRequest("Invalid file size.");
        if (!await inspector.IsAllowedAsync(file, ct))
            return BadRequest("Unsupported file content.");

        var id = Guid.NewGuid();
        var key = $"expenses/{expenseId:N}/{id:N}";
        var entry = new ExpenseAttachment {
            Id = id, ExpenseId = expenseId, BlobName = key,
            ContentType = inspector.SafeContentType(file),
            Size = file.Length, Status = "Pending"
        };
        db.ExpenseAttachments.Add(entry);
        await db.SaveChangesAsync(ct);

        try
        {
            await using var source = file.OpenReadStream(MaxBytes);
            await container.GetBlobClient(key).UploadAsync(
                source, overwrite: false, cancellationToken: ct);
            entry.Status = "Ready";
            await db.SaveChangesAsync(ct);
            log.LogInformation("Attachment ready {AttachmentId}", id);
            return Created($"/api/expenses/{expenseId}/attachments/{id}",
                new { id });
        }
        catch (Exception ex) when (ex is not OperationCanceledException)
        {
            log.LogError(ex, "Attachment upload incomplete {AttachmentId}", id);
            // Pending remains reconcilable; do not assume compensating
            // deletion or DB update can always succeed.
            throw;
        }
    }

    [HttpGet("{attachmentId:guid}")]
    public async Task<IActionResult> Download(
        Guid expenseId, Guid attachmentId, CancellationToken ct)
    {
        if (!await access.CanReadExpenseAsync(User, expenseId, ct))
            return Forbid();
        var entry = await db.ExpenseAttachments.AsNoTracking()
            .SingleOrDefaultAsync(x => x.Id == attachmentId &&
                x.ExpenseId == expenseId && x.Status == "Ready", ct);
        if (entry is null) return NotFound();
        try
        {
            var response = await container.GetBlobClient(entry.BlobName)
                .DownloadStreamingAsync(cancellationToken: ct);
            return File(response.Value.Content,
                "application/octet-stream", $"{attachmentId:N}.bin");
        }
        catch (Azure.RequestFailedException ex) when (ex.Status == 404)
        {
            log.LogError(ex, "Missing blob for {AttachmentId}", attachmentId);
            return Problem(statusCode: 503, title: "Attachment unavailable");
        }
    }
}
```

**Lưu ý triển khai:** `IFileInspector.IsAllowedAsync` phải đọc stream theo cách không làm mất bytes của stream upload tiếp theo; đối với `IFormFile`, mỗi `OpenReadStream` mở stream mới. `RequestSizeLimit` cần tính multipart overhead và đồng bộ cấu hình IIS/App Service/proxy. Để phân biệt upload đã thành công nhưng bước đánh dấu Ready thất bại, reconciliation phải kiểm tra Blob tồn tại và metadata/length phù hợp; không tự động xóa Blob còn có thể được phục hồi. `CancellationToken` trong bước finalize cần chính sách rõ ràng vì client disconnect có thể để lại Pending. Download stream cần được ASP.NET Core quản lý và giải phóng sau response; xác nhận hành vi qua integration tests.

## Giải thích thiết kế sau khi sửa

Resource authorization áp dụng cho cả upload và download. Opaque Blob keys loại bỏ overwrite ngoài ý muốn. `Pending` tạo recovery point trước I/O bên ngoài. Không coi việc nhận `Created` là đảm bảo nếu client timeout; idempotency key + unique constraint cần bổ sung nếu UX cho phép retry cùng thao tác. Blob container private; quyền đọc/ghi do backend/Managed Identity kiểm soát.

## Trade-offs

Streaming giảm peak memory nhưng không loại bỏ buffering mặc định của multipart model binding; streaming multipart parser trực tiếp phức tạp hơn. Quarantine/virus scanning tăng latency và chi phí. Hai-phase state + reconciliation thêm operational burden nhưng cần khi không có distributed transaction. Direct-to-Blob upload với short-lived user-scoped SAS có thể giảm backend bandwidth, đổi lại cần thiết kế completion verification và quyền SAS rất hẹp.

## Cách kiểm thử

1. **Security integration:** User A truy cập expense/attachment của User B, kể cả URL trộn expenseId và attachmentId, đều bị từ chối.
2. **Concurrency/load:** 100 uploads trùng original filename không overwrite; đo heap, GC và temporary disk.
3. **Failure-path:** Blob thành công nhưng SQL finalize thất bại; reconciliation khôi phục Ready an toàn.
4. **Validation:** File vượt 25 MiB, MIME giả, file signature sai và empty upload bị từ chối.
5. **Cancellation/dependency:** Client abort, Blob 404/503, DB timeout; kiểm tra status, không leak stream và telemetry.

## Quan sát trong production

Application Insights: request p95/p99, exception rate, dependency duration và status Blob/SQL, correlation ID, memory working set, GC, upload throughput; metric `attachment_pending_age_seconds`, orphan count, reconciliation success/failure. Alert theo Pending vượt ngưỡng và tỷ lệ 5xx, không log file bytes hay credentials.

## Câu hỏi phỏng vấn mở rộng

1. Khi chuyển sang direct-to-Blob SAS upload, backend xác thực completion và ownership thế nào?
2. Nếu cần xóa chứng từ theo chính sách retention, làm sao tránh xóa nhầm trong lúc retry?
3. Khi nào dùng background malware scan và trạng thái Quarantined thay vì đồng bộ trong request?

# Code Review Challenge 2 — Vue.js product filter trả dữ liệu cũ sau thao tác nhanh

**Độ khó:** Senior

## Bối cảnh

Trang catalog của một CMS/e-commerce website dùng Vue 3 và ASP.NET Core search API. Người dùng đổi category, keyword, sort và trang nhanh liên tục. Search API có latency biến động 100 ms–3 s, đôi lúc trả 429/503. Production ghi nhận danh sách hiển thị không khớp bộ lọc, lỗi mạng làm mất dữ liệu đang xem và UI bị chậm sau khi chuyển route. Yêu cầu: chỉ kết quả của filter mới nhất được hiển thị; pagination phải nhất quán; không gửi request cho mỗi phím gõ khi không cần.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from "vue";

type Product = { id: string; name: string; price: number };
const keyword = ref("");
const category = ref("all");
const sort = ref("relevance");
const page = ref(1);
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref("");

async function loadProducts() {
  loading.value = true;
  error.value = "";
  const params = new URLSearchParams({
    q: keyword.value,
    category: category.value,
    sort: sort.value,
    page: String(page.value)
  });

  try {
    const response = await fetch("/api/products?" + params);
    const data = await response.json();
    products.value = data.items;
    total.value = data.total;
  } catch (e) {
    products.value = [];
    error.value = "Không tải được sản phẩm";
  } finally {
    loading.value = false;
  }
}

watch([keyword, category, sort, page], loadProducts);
onMounted(loadProducts);
</script>

<template>
  <input v-model="keyword" placeholder="Search" />
  <select v-model="category">
    <option value="all">All</option>
    <option value="books">Books</option>
  </select>
  <select v-model="sort">
    <option value="relevance">Relevance</option>
    <option value="price">Price</option>
  </select>
  <p v-if="error">{{ error }}</p>
  <p v-if="loading">Loading...</p>
  <ul>
    <li v-for="p in products" :key="p.id">{{ p.name }} - {{ p.price }}</li>
  </ul>
  <button @click="page++">Next</button>
  <span>{{ total }}</span>
</template>
```

## Kết quả code review tham khảo

### [High] — Response race ghi đè kết quả mới

**Vấn đề:** Request cũ hoàn thành muộn vẫn gán `products` và `total`.

**Tại sao xảy ra:** Không có request identity/cancellation.

**Ảnh hưởng production:** Hiển thị sản phẩm không thuộc filter đang chọn, gây quyết định sai.

**Cách sửa:** `AbortController` + sequence guard, chỉ commit state từ request mới nhất.

### [High] — HTTP 429/503 bị xem như thành công

**Vấn đề:** `fetch` không reject cho non-2xx; `response.json()` có thể trả ProblemDetails không có `items`.

**Tại sao xảy ra:** Không kiểm tra `response.ok` và response shape.

**Ảnh hưởng production:** UI rỗng hoặc lỗi khó hiểu; có thể làm mất state hợp lệ.

**Cách sửa:** Check status, validate response contract; hiện retry affordance, xử lý 429 theo `Retry-After` khi thích hợp.

### [Medium] — Loading/error race

**Vấn đề:** `finally` của request cũ đặt `loading=false` dù request mới đang chạy; error cũ cũng có thể hiện sai.

**Tại sao xảy ra:** Flags dùng chung không được guard.

**Ảnh hưởng production:** Flicker, loading indicator sai, người dùng thao tác nhầm.

**Cách sửa:** Chỉ update flags nếu sequence vẫn là mới nhất.

### [Medium] — Không debounce keyword

**Vấn đề:** Mỗi ký tự gõ kích hoạt request.

**Tại sao xảy ra:** Watch trực tiếp input.

**Ảnh hưởng production:** Request amplification, 429, tăng chi phí và network contention.

**Cách sửa:** Debounce keyword; category/sort/page có thể trigger ngay.

### [Medium] — Pagination không reset khi filter đổi

**Vấn đề:** `page` vẫn giữ khi keyword/category/sort thay đổi.

**Tại sao xảy ra:** Không định nghĩa transition giữa filter và page.

**Ảnh hưởng production:** Empty results dù có sản phẩm ở trang đầu.

**Cách sửa:** Reset page về 1; giới hạn Next theo total và page size.

### [Medium] — Lifecycle cleanup thiếu

**Vấn đề:** Không abort request hoặc timer khi component bị unmount.

**Tại sao xảy ra:** Không cleanup asynchronous work.

**Ảnh hưởng production:** Network thừa và cập nhật state của view không còn hoạt động.

**Cách sửa:** Cleanup controller/timer trong `onUnmounted`; `watch` cleanup cho request cũ.

### [Low] — Không bảo vệ response schema và retry UX

**Vấn đề:** Gán trực tiếp JSON không xác minh `items` array và `total` hợp lệ; lỗi luôn xóa danh sách.

**Tại sao xảy ra:** Tin API response hoàn toàn.

**Ảnh hưởng production:** UI lỗi khó debug; trải nghiệm kém khi outage ngắn.

**Cách sửa:** Runtime validation nhẹ, giữ dữ liệu cũ với stale indicator hoặc clear theo product policy; Retry button rõ ràng.

## Phiên bản đề xuất

Ví dụ Vue 3 dùng watcher với `onCleanup`, sequence guard và debounce keyword; `PAGE_SIZE` cần khớp contract API. `fetch` abort có thể xảy ra sau khi response đã đến, vì vậy sequence guard vẫn cần thiết.

```vue
<script setup lang="ts">
import { computed, onUnmounted, ref, watch } from "vue";

type Product = { id: string; name: string; price: number };
type SearchResult = { items: Product[]; total: number };
const PAGE_SIZE = 20;
const keyword = ref("");
const search = ref("");
const category = ref("all");
const sort = ref("relevance");
const page = ref(1);
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref("");
let debounceTimer: ReturnType<typeof setTimeout> | undefined;
let sequence = 0;

watch(keyword, value => {
  clearTimeout(debounceTimer);
  debounceTimer = setTimeout(() => { search.value = value.trim(); }, 300);
});
watch([search, category, sort], () => { page.value = 1; }, {
  flush: "sync"
});
const query = computed(() => ({
  q: search.value, category: category.value,
  sort: sort.value, page: page.value
}));

watch(query, async (q, _previous, onCleanup) => {
  const current = ++sequence;
  const controller = new AbortController();
  onCleanup(() => controller.abort());
  loading.value = true;
  error.value = "";

  try {
    const params = new URLSearchParams({
      q: q.q, category: q.category, sort: q.sort,
      page: String(q.page)
    });
    const response = await fetch("/api/products?" + params, {
      signal: controller.signal
    });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data: SearchResult = await response.json();
    if (!Array.isArray(data.items) ||
        !Number.isFinite(data.total) || data.total < 0)
      throw new Error("Invalid response");
    if (current !== sequence) return;
    products.value = data.items;
    total.value = data.total;
  } catch (e) {
    if (current !== sequence || controller.signal.aborted) return;
    error.value = "Không tải được sản phẩm. Hãy thử lại.";
  } finally {
    if (current === sequence) loading.value = false;
  }
}, { immediate: true });

const canNext = computed(() =>
  !loading.value && page.value * PAGE_SIZE < total.value);
onUnmounted(() => {
  clearTimeout(debounceTimer);
  sequence++;
});
</script>

<template>
  <input v-model="keyword" placeholder="Search" />
  <select v-model="category">
    <option value="all">All</option><option value="books">Books</option>
  </select>
  <select v-model="sort">
    <option value="relevance">Relevance</option>
    <option value="price">Price</option>
  </select>
  <p v-if="error" role="alert">{{ error }}</p>
  <p v-if="loading" role="status">Loading...</p>
  <ul>
    <li v-for="p in products" :key="p.id">{{ p.name }} - {{ p.price }}</li>
  </ul>
  <button :disabled="page === 1 || loading" @click="page--">Previous</button>
  <button :disabled="!canNext" @click="page++">Next</button>
  <span>{{ total }} results</span>
</template>
```

**Lưu ý:** Với `flush: "sync"`, reset page có thể tạo thêm invalidation khi nhiều refs đổi cùng tick; đo request count trong test. Để tối ưu hơn, gom filter state vào một reducer/composable và xây query atomically. Bản minh họa giữ stale results khi lỗi; UI production cần gắn nhãn stale, hoặc clear results nếu chính sách không cho hiển thị dữ liệu của filter trước. Khi unmount, watcher cleanup sẽ abort request đang chạy; sequence increment bổ sung guard. Retry UI có thể dùng `retryNonce` trong computed query.

## Giải thích thiết kế sau khi sửa

Debounce chỉ áp dụng input text; request mới có `sequence` mới và abort request trước. Response non-2xx không được coi là data. Loading/error chỉ thuộc request mới nhất. Pagination reset theo filter. API nên hỗ trợ stable ordering và xác định page size để `canNext` đúng.

## Trade-offs

Debounce giảm load nhưng tăng độ trễ 300 ms; cancellation không đảm bảo backend đã dừng xử lý. Giữ stale results cải thiện UX trong outage nhưng có thể gây nhầm lẫn nếu không hiển thị filter tương ứng. Dùng TanStack Query/Vue Query có thể đơn giản hóa caching/retry trong app lớn, nhưng là dependency và policy bổ sung, không bắt buộc cho trang nhỏ.

## Cách kiểm thử

1. **Unit/component:** Request A chậm hơn B; chỉ B được render, loading không tắt sớm.
2. **Playwright E2E:** Gõ nhanh, đổi category khi ở page 8; request count được giới hạn, page reset về 1.
3. **Failure-path:** 429, 503, invalid JSON/schema và network disconnect hiển thị error phù hợp, không crash.
4. **Lifecycle:** Navigate away khi request pending; không có stale commit hoặc uncaught rejection.
5. **Integration:** Search API đảm bảo stable sorting, `total` và page size nhất quán với UI.

## Quan sát trong production

Browser RUM: request duration, aborted count, HTTP 429/503, time-to-results, client-side exceptions; backend Application Insights: endpoint p95, dependency timings, query parameters đã redacted, request rate, 429 ratio, correlation ID. Alert khi lỗi search hoặc request amplification tăng sau release.

## Câu hỏi phỏng vấn mở rộng

1. Nếu search API hỗ trợ cursor pagination thay vì page number, UI state thay đổi thế nào?
2. Khi nào nên cache kết quả theo query key, và làm sao tránh hiển thị dữ liệu cache không còn hợp lệ?
3. Làm sao đo hiệu quả debounce và cancellation mà không đánh đồng canceled request với server error?
