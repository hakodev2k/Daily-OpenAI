## Đoạn code cần review

```csharp
public sealed class ProductService(
    CatalogDbContext db,
    SearchIndexer indexer,
    ILogger<ProductService> logger)
{
    public async Task UpdateAsync(
        Guid productId, UpdateProductRequest request,
        CancellationToken cancellationToken)
    {
        var product = await db.Products
            .SingleAsync(p => p.Id == productId, cancellationToken);

        product.Name = request.Name;
        product.Price = request.Price;
        product.IsPublished = request.IsPublished;
        product.UpdatedAt = DateTime.UtcNow;

        await db.SaveChangesAsync(cancellationToken);
        _ = indexer.IndexAsync(product, CancellationToken.None);
        logger.LogInformation("Product {ProductId} updated", productId);
    }
}

public sealed class SearchIndexer(
    HttpClient client,
    ILogger<SearchIndexer> logger)
{
    public async Task IndexAsync(Product product, CancellationToken ct)
    {
        var document = new
        {
            product.Id, product.Name, product.Price,
            product.IsPublished, product.UpdatedAt
        };

        var response = await client.PutAsJsonAsync(
            $"/products/_doc/{product.Id}", document, ct);

        if (!response.IsSuccessStatusCode)
            logger.LogWarning(
                "Indexing failed for {ProductId}: {Status}",
                product.Id, response.StatusCode);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Không bảo đảm sự kiện indexing được ghi bền vững

**Vấn đề:** Database commit thành công nhưng `IndexAsync` chỉ được gọi fire-and-forget.  
**Tại sao xảy ra:** Không có transaction chung giữa PostgreSQL và Elasticsearch; Task không được await hoặc lưu vào durable queue.  
**Ảnh hưởng production:** Mất cập nhật vĩnh viễn khi process crash/recycle; giá hoặc published status sai.  
**Cách sửa:** Ghi transactional outbox cùng transaction với product update, dùng dispatcher và worker có retry; thêm reconciliation định kỳ.

### [High] — Kết quả index có thể bị ghi đè bởi bản cũ

**Vấn đề:** Hai update cùng product có thể đến Elasticsearch đảo thứ tự.  
**Tại sao xảy ra:** HTTP request và worker chạy song song; `UpdatedAt` không phải cơ chế chống stale write đáng tin cậy.  
**Ảnh hưởng production:** Product hiển thị giá cũ dù database mới.  
**Cách sửa:** Dùng version đơn điệu theo product (DB concurrency token hoặc sequence được kiểm soát), áp dụng Elasticsearch external versioning hoặc conditional update có kiểm soát; kiểm thử thứ tự đảo. Không dùng timestamp wall-clock như bảo đảm ordering.

### [High] — Không có retry, DLQ hoặc cơ chế replay

**Vấn đề:** 429/503 chỉ log Warning.  
**Tại sao xảy ra:** Response lỗi không biến thành durable failed work.  
**Ảnh hưởng production:** Search index lệch lâu dài sau outage.  
**Cách sửa:** Retry có exponential backoff + jitter, giới hạn attempts, phân biệt lỗi permanent, lưu trạng thái failed/dead-letter để replay và reconciliation.

### [High] — Không bảo đảm optimistic concurrency ở database

**Vấn đề:** Hai editor có thể ghi đè thay đổi nhau mà không nhận conflict.  
**Tại sao xảy ra:** Entity được load rồi SaveChanges nhưng không có concurrency token trong hợp đồng.  
**Ảnh hưởng production:** Lost update ở source of truth; search chỉ phản ánh một trong các trạng thái.  
**Cách sửa:** Dùng concurrency token/version và trả HTTP 409 hoặc 412 theo API contract; xác nhận chính sách merge với Product.

### [Medium] — Truyền tracked entity sang tác vụ không được await

**Vấn đề:** `product` được đưa vào async method ngoài lifecycle request.  
**Tại sao xảy ra:** Mutable reference không phải snapshot bất biến; caller không kiểm soát thời gian thực thi.  
**Ảnh hưởng production:** Khó tái hiện bug, payload không rõ phiên bản; exception có thể không được quan sát.  
**Cách sửa:** Lưu immutable event chứa productId, version và snapshot cần thiết; worker dùng scope riêng.

### [Medium] — CancellationToken.None và thiếu shutdown semantics

**Vấn đề:** Work vẫn chạy sau khi request hoàn thành mà không có cơ chế graceful drain.  
**Tại sao xảy ra:** Không có hosted worker sở hữu lifecycle.  
**Ảnh hưởng production:** Task bị cắt khi deployment, không có checkpoint.  
**Cách sửa:** Hosted worker nhận stoppingToken, lease work và commit trạng thái; không phụ thuộc vòng đời HTTP request.

### [Medium] — Không có chính sách timeout và giới hạn concurrency

**Vấn đề:** Indexer có thể tích lũy outbound calls khi cluster search chậm.  
**Tại sao xảy ra:** Không có bounded worker, rate limiting hoặc timeout policy được thể hiện.  
**Ảnh hưởng production:** Socket pressure, backlog, contention và chi phí vận hành tăng.  
**Cách sửa:** HttpClient qua IHttpClientFactory, timeout hợp lý, bounded concurrency, backpressure; chỉ retry lỗi transient.

### [Medium] — Thiếu observability về index freshness

**Vấn đề:** Chỉ log cập nhật product và warning HTTP.  
**Tại sao xảy ra:** Không có outbox age, delivery attempts, version mismatch, correlation.  
**Ảnh hưởng production:** Không chứng minh được SLA và không phân biệt lỗi API với lỗi indexing.  
**Cách sửa:** Metrics queue age p95/p99, failed events, search index lag, traces theo eventId/productId/version, alert theo SLO.

### [Low] — Thiếu validation và HTTP error detail có kiểm soát

**Vấn đề:** Request có thể chứa price không hợp lệ; response không được dispose rõ ràng.  
**Tại sao xảy ra:** Validation ở boundary và disposal không được thể hiện.  
**Ảnh hưởng production:** Dữ liệu không hợp lệ và resource giữ lâu hơn cần thiết.  
**Cách sửa:** Validate business rules, dùng `using var response`, log mã lỗi và thông tin an toàn, tránh payload nhạy cảm.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa atomic write vào DB + outbox. Giả định `Product.Version` là concurrency token được tăng atomically trong DB transaction, `OutboxEvent` có unique `EventId`, và worker có cơ chế claim/lease an toàn giữa nhiều replica. Đây là phần cốt lõi, không phải toàn bộ production infrastructure.

```csharp
public sealed record ProductIndexChanged(
    Guid EventId, Guid ProductId, long Version,
    string Name, decimal Price, bool IsPublished);

public sealed class ProductService(CatalogDbContext db)
{
    public async Task UpdateAsync(
        Guid id, UpdateProductRequest input, long expectedVersion,
        CancellationToken ct)
    {
        if (input.Price < 0) throw new ArgumentException("Invalid price");

        await using var tx = await db.Database.BeginTransactionAsync(ct);
        var product = await db.Products.SingleAsync(x => x.Id == id, ct);
        if (product.Version != expectedVersion)
            throw new ProductConflictException(id);

        product.Name = input.Name;
        product.Price = input.Price;
        product.IsPublished = input.IsPublished;
        product.Version++;
        product.UpdatedAt = DateTimeOffset.UtcNow;

        var evt = new ProductIndexChanged(
            Guid.NewGuid(), product.Id, product.Version,
            product.Name, product.Price, product.IsPublished);

        db.OutboxEvents.Add(new OutboxEvent
        {
            Id = evt.EventId,
            AggregateId = id,
            AggregateVersion = evt.Version,
            Type = nameof(ProductIndexChanged),
            Payload = JsonSerializer.Serialize(evt),
            CreatedAt = DateTimeOffset.UtcNow
        });

        await db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

Worker algorithm (pseudocode, cần hiện thực với PostgreSQL locking và Elasticsearch API/version contract đã kiểm thử):

```text
loop until shutdown:
  claim a bounded batch of pending outbox rows using a lease
  for each event:
    index immutable snapshot with productId and monotonic version
    if external version rejects an older event: mark superseded
    if success: mark delivered
    if transient error: schedule bounded retry with jitter
    if permanent error or attempts exhausted: quarantine and alert
  release expired leases for crash recovery
periodically:
  compare DB version with indexed version and repair drift
```

Cần xử lý `DbUpdateConcurrencyException` thành conflict response; nếu dùng PostgreSQL xmin hoặc rowversion-like token, thiết kế lại cách cấp version cho nhất quán. Worker có thể nhận bản mới hơn trước bản cũ; external versioning phải được kiểm chứng với phiên bản Elasticsearch đang triển khai. Khi unpublish, chọn xóa document hoặc giữ document nhưng filter `IsPublished` bắt buộc; quyết định theo security/search requirements.

## Giải thích thiết kế sau khi sửa

Transactional outbox giải quyết atomicity của **database state + intent to publish**, không biến Elasticsearch thành transaction participant. Delivery có thể at-least-once, vì vậy `EventId` và `Version` cần xử lý duplicate và out-of-order. Lease bảo vệ nhiều worker; lease expiry vẫn có thể tạo duplicate, nên consumer phải idempotent. Nếu search freshness là hard requirement, cần có circuit breaker/alert, graceful degradation và phương án đọc trực tiếp database cho các tác vụ nhạy cảm.

## Trade-offs

Outbox tăng số bảng, write amplification, cleanup và độ trễ eventual consistency; không miễn phí. Nếu catalog rất nhỏ, có thể dùng synchronous indexing có await và reconciliation nhưng vẫn tồn tại commit/index gap. Message broker chỉ nên thêm khi throughput/decoupling đòi hỏi; không thay thế outbox nếu không có atomic write. Reconciliation tạo thêm tải DB/search, nên phải phân trang, rate limit và đo lường.

## Cách kiểm thử

1. **Integration:** kill process ngay sau DB commit, restart worker; mọi outbox event phải được xử lý.
2. **Concurrency:** update cùng product đồng thời, xác nhận conflict và version không lùi.
3. **Failure-path:** Elasticsearch trả 429, 503, timeout rồi phục hồi; retry bounded, không mất event.
4. **Ordering:** cố ý giao version 12 trước 11, indexed state cuối cùng vẫn là 12.
5. **Load:** đo p95 index freshness khi 4 worker cùng chạy và cluster search chậm; xác nhận SLA hoặc alert breach.

## Quan sát trong production

Theo dõi `outbox_pending_total`, oldest pending age, `index_attempts_total` theo status, `index_version_lag`, p95/p99 indexing delay, HTTP dependency latency, PostgreSQL locks/connection pool và Elasticsearch rejection rate. Structured logs chứa `eventId`, `productId`, `version`, `traceId`; không log toàn bộ product nếu có thông tin nhạy cảm. Alert khi oldest pending age vượt ngưỡng cảnh báo trước mốc 2 phút.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business yêu cầu trạng thái unpublish có hiệu lực ngay lập tức, thay đổi API/search contract như thế nào?
2. Khi outbox có 20 triệu event, bạn thiết kế retention, partition và reconciliation ra sao?
3. Có trường hợp nào bạn chọn bỏ Elasticsearch để query PostgreSQL trực tiếp không?

## Kết quả code review tham khảo

### [Critical] — Credential nằm trực tiếp trong manifest

**Vấn đề:** Connection string chứa password dạng plaintext trong YAML.  
**Tại sao xảy ra:** Cấu hình được đưa thẳng vào source/deployment artifact.  
**Ảnh hưởng production:** Lộ credential qua repository, CI logs hoặc người có quyền đọc manifest.  
**Cách sửa:** Rotate credential đã lộ; dùng Kubernetes Secret hoặc external secret integration, RBAC và encryption-at-rest; ưu tiên workload identity khi driver/service hỗ trợ. Secret không tự động an toàn nếu quyền đọc quá rộng.

### [High] — Liveness phụ thuộc chung vào readiness

**Vấn đề:** Cả hai probe dùng `/health`; nếu endpoint kiểm tra PostgreSQL thì lỗi DB có thể làm Kubernetes restart các pod khỏe mạnh.  
**Tại sao xảy ra:** Dependency availability bị đánh đồng với process liveness.  
**Ảnh hưởng production:** Restart storm, mất capacity, kéo dài outage.  
**Cách sửa:** `/health/live` kiểm tra process, `/health/ready` kiểm tra khả năng phục vụ request; dependency readiness phải có timeout và chính sách phù hợp.

### [High] — Probe khởi động không phù hợp thời gian warm-up

**Vấn đề:** Liveness bắt đầu sau 10 giây, failureThreshold 2; startup có thể 70 giây.  
**Tại sao xảy ra:** Không có startupProbe.  
**Ảnh hưởng production:** Pod bị restart trước khi sẵn sàng, CrashLoopBackOff.  
**Cách sửa:** Thêm startupProbe với budget lớn hơn worst-case warm-up được đo, sau đó mới kích hoạt liveness/readiness.

### [High] — RollingUpdate cho phép giảm capacity quá mạnh

**Vấn đề:** `maxUnavailable: 2` với 3 replica, `maxSurge: 0`.  
**Tại sao xảy ra:** Rollout có thể chỉ còn 1 pod available trong lúc thay thế.  
**Ảnh hưởng production:** Tăng latency, 503 khi traffic spike.  
**Cách sửa:** Dùng `maxUnavailable: 0`, `maxSurge: 1` khi cluster đủ capacity; bổ sung PodDisruptionBudget cho voluntary disruption (không thay thế rollout strategy), kiểm tra quotas.

### [High] — Termination grace quá ngắn

**Vấn đề:** Chỉ 5 giây để drain và shutdown.  
**Tại sao xảy ra:** ASP.NET Core có thể đang xử lý request, background task hoặc DB transaction.  
**Ảnh hưởng production:** Request bị ngắt, client retry tạo duplicate writes.  
**Cách sửa:** Tăng grace dựa trên request duration; ứng dụng xử lý SIGTERM, dừng nhận request mới và chờ inflight work; bảo đảm idempotency cho write API.

### [Medium] — Image tag mutable

**Vấn đề:** `:latest` không xác định artifact cố định.  
**Tại sao xảy ra:** Tag có thể bị ghi đè giữa các lần deploy.  
**Ảnh hưởng production:** Rollback khó kiểm chứng; replica chạy artifact khác nhau.  
**Cách sửa:** Pin image bằng digest hoặc immutable release tag; ghi build SHA trong deployment metadata.

### [Medium] — Không có resource requests

**Vấn đề:** Chỉ có limits, không khai báo requests rõ ràng.  
**Tại sao xảy ra:** Scheduler có thể dùng giá trị mặc định từ limit/admission, không phản ánh nhu cầu thực.  
**Ảnh hưởng production:** Scheduling và capacity planning khó dự đoán.  
**Cách sửa:** Đo CPU/memory p95 và startup, đặt requests có căn cứ, giới hạn hợp lý; quan sát OOMKilled và CPU throttling.

### [Medium] — Chưa có bằng chứng và gate cho rollout

**Vấn đề:** Manifest không thể hiện kiểm thử, rollout monitoring, rollback criteria.  
**Tại sao xảy ra:** Deployment chỉ được xem như cập nhật YAML.  
**Ảnh hưởng production:** Regression có thể lan ra toàn bộ replica.  
**Cách sửa:** Pipeline kiểm tra artifact, smoke test, `kubectl rollout status`, canary/blue-green nếu rủi ro cao, rollback theo error budget.

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddCheck<StartupCompletedCheck>("startup", tags: ["startup"])
    .AddCheck<DatabaseReadinessCheck>("database", tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("live")
});
app.MapHealthChecks("/health/startup", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("startup")
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("ready")
});
```

`StartupCompletedCheck` phải phản ánh thực tế warm-up đã hoàn tất; `DatabaseReadinessCheck` phải bounded và không gây thêm tải DB. Nếu DB outage ngắn và app vẫn phục vụ cached reads, không nhất thiết loại mọi pod khỏi Service; readiness policy phải dựa trên chức năng user cần. Với write API, cần đánh giá connection drain và retry safety riêng.

## Giải thích thiết kế sau khi sửa

Startup probe ngăn liveness can thiệp khi ứng dụng đang warm-up; readiness điều khiển routing; liveness chỉ restart process khi không còn khỏe. `maxUnavailable: 0` bảo toàn số pod available trong rollout nếu capacity và readiness đủ. Graceful shutdown chỉ giảm lỗi nếu app xử lý SIGTERM và ingress/service routing cập nhật kịp; không bảo đảm tuyệt đối không mất request. Immutable image làm rollback có thể audit.

## Trade-offs

Surge cần thêm CPU/memory và có thể bị quota chặn. Grace dài làm rollout chậm. Readiness phụ thuộc DB có thể giảm traffic vào pod nhưng cũng làm toàn bộ Service mất endpoint nếu DB outage; cần định nghĩa degradation mode. Kubernetes đòi hỏi platform engineering, RBAC, cluster patching, ingress và telemetry; nếu App Service đáp ứng scaling/availability thì giữ App Service có thể đơn giản và ít rủi ro hơn.

## Cách kiểm thử

1. **Deployment validation:** cold start 70 giây, rollout vẫn thành công, không restart do startupProbe.
2. **Failure injection:** chặn PostgreSQL 30 giây, đo readiness/liveness và bảo đảm không restart storm.
3. **Load test:** rollout khi traffic đạt p95 peak, đo 502/503, p99 latency và số available replicas.
4. **Graceful shutdown:** gửi SIGTERM khi có request/transaction dài, kiểm tra drain và idempotent retries.
5. **Security/deployment:** xác minh image digest đúng release, secret không nằm trong manifest/log, rollback về digest cũ.

## Quan sát trong production

Theo dõi `kube_pod_container_status_restarts_total`, pod Ready/Unavailable, rollout duration, OOMKilled, CPU throttling, memory working set, HTTP 502/503, p95/p99 latency, active requests, database dependency failures và termination events. Dùng Application Insights distributed traces cho API và PostgreSQL, Kubernetes events cho probe failures; alert khi available replicas giảm, error rate tăng hoặc rollout không tiến triển. Đối chiếu từng spike với deployment revision và image digest.

## Câu hỏi phỏng vấn mở rộng

1. Nếu DB outage 60 giây làm tất cả readiness fail, bạn giữ hay thay đổi readiness policy?
2. Làm sao triển khai database schema migration backward compatible qua hai phiên bản API?
3. Trong điều kiện nào Azure App Service là lựa chọn tốt hơn Kubernetes cho hệ thống này?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Tính đúng đắn của read model đòi hỏi durable intent, version ordering, idempotency và reconciliation; không thể dựa vào fire-and-forget sau database commit. Deployment availability cần phân biệt startup, readiness, liveness, graceful shutdown, immutable artifact và capacity budget. Với cả hai tình huống, thiết kế phải có recovery và bằng chứng quan sát được thay vì chỉ happy path.

## Mẫu tư duy cần nhớ

1. **Atomicity boundary trước tiên:** xác định điều gì được commit cùng transaction và điều gì chỉ eventual consistent.
2. **Failure là trạng thái bình thường:** thiết kế retry cùng idempotency, ordering và dead-letter/replay.
3. **Đo trước khi điều chỉnh:** lấy queue lag, p95/p99, probe failures và capacity trước khi đổi cấu hình.
4. **Tách các tín hiệu vận hành:** liveness khác readiness; DB state khác search projection.
5. **So sánh chi phí phức tạp:** chỉ chọn broker hoặc Kubernetes khi requirement chứng minh cần thiết.
