# Câu 1 — API không leak memory nhưng GC pause và allocation làm p99 tăng vọt

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, Garbage Collector, allocations, LOH, object lifetime, ASP.NET Core, serialization, profiling, performance

## Bối cảnh

Một ASP.NET Core .NET 8 API chạy trên Azure App Service xử lý endpoint export preview. Endpoint đọc dữ liệu từ SQL Server, dựng một JSON payload lớn rồi trả về client. Traffic trung bình không cao, nhưng mỗi request có thể tạo payload từ vài trăm KB đến vài MB.

Sau một release, memory của process tăng theo tải rồi giảm lại sau GC; không có xu hướng tăng vô hạn. Tuy vậy p95 tăng từ khoảng 180 ms lên 600–900 ms và p99 đôi lúc vượt 2 giây. CPU có các spike ngắn. Team thấy GC collections tăng và kết luận “đây chắc chắn là memory leak”. Một developer đề xuất gọi `GC.Collect()` sau mỗi export; người khác muốn chuyển mọi buffer sang `ArrayPool<byte>`.

Đoạn code rút gọn:

```csharp
public async Task<IResult> PreviewAsync(
    ExportRequest request,
    CancellationToken cancellationToken)
{
    var rows = await _db.ExportRows
        .AsNoTracking()
        .Where(x => x.BatchId == request.BatchId)
        .Select(x => new ExportRowDto(
            x.Id,
            x.Name,
            x.Description,
            x.MetadataJson))
        .ToListAsync(cancellationToken);

    var json = JsonSerializer.Serialize(rows);
    var bytes = Encoding.UTF8.GetBytes(json);

    return Results.File(
        bytes,
        "application/json",
        "preview.json");
}
```

Chưa rõ allocation rate trước/sau release, kích thước object thực tế, generation distribution, GC pause time, heap size, request concurrency, payload distribution, hay liệu client có thực sự cần toàn bộ document được materialize trong memory.

## Câu hỏi chính

Hãy giải thích object allocation và generational GC của .NET liên quan thế nào tới đoạn code này; vì sao memory tăng rồi giảm không đủ để kết luận memory leak; các allocation lớn và object sống đủ lâu có thể ảnh hưởng latency ra sao; vì sao `GC.Collect()` hoặc `ArrayPool<byte>` không phải automatic fix; và bạn sẽ dùng evidence nào để xác định root cause trước khi tối ưu?

## Câu hỏi làm rõ nên cân nhắc

1. Payload size distribution và số request export đồng thời ở p95/p99 là bao nhiêu?
2. Allocation rate, Gen 0/1/2 collection rate, GC pause duration và heap size thay đổi thế nào giữa release tốt và release lỗi?
3. Có object nào được giữ ngoài request lifetime bởi cache, static collection, event handler hoặc long-lived service không?
4. Endpoint bắt buộc trả một JSON document hoàn chỉnh hay có thể stream/chunk dữ liệu?
5. Bottleneck thực tế nằm ở SQL materialization, JSON serialization, UTF-16 string trung gian, UTF-8 buffer, network hay GC?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt **high allocation pressure** với **memory retention/leak**. Hai hiện tượng có thể cùng làm memory cao nhưng cơ chế và cách sửa khác nhau.

### Gợi ý 2

Trong code có nhiều representation của cùng dữ liệu cùng tồn tại: entity projection/list, JSON `string`, rồi `byte[]`. Hãy suy nghĩ về lifetime và peak live memory dưới concurrency.

### Gợi ý 3

Đừng tối ưu từ tên API. Hãy đo allocation hot paths, heap retention và GC pause trước; sau đó mới quyết định streaming, pooling, giảm materialization hay thay đổi query/payload.

## Cấu trúc trả lời đề xuất

1. Làm rõ symptom và payload/concurrency.
2. Phân biệt allocation pressure, retained memory và leak.
3. Giải thích generations, promotion và collection cost ở mức thực dụng.
4. Map các allocation/lifetime chính trong request.
5. Thu thập runtime counters/profile/trace.
6. Xác định bottleneck bằng evidence.
7. So sánh giảm allocation, streaming, pooling và giới hạn payload.
8. Kiểm thử load với payload representative.
9. Theo dõi p95/p99, allocation rate, heap và GC pause sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Managed object được cấp phát và GC thu hồi object không còn reachable; memory process tăng rồi giảm có thể chỉ là hành vi GC bình thường, không tự chứng minh leak.
- Generational GC dựa trên giả định nhiều object chết sớm; object sống qua collection có thể được promote và collection generation cao thường đắt hơn.
- Request hiện materialize toàn bộ rows, tạo một JSON `string`, sau đó tạo thêm `byte[]`; peak memory có thể nhân lên khi nhiều request lớn chạy đồng thời.
- Large allocations cần được xem xét riêng vì chúng tạo pressure và có đặc tính collection khác object nhỏ; không nên suy ra threshold/cost cụ thể nếu chưa đo runtime/version/workload.
- `GC.Collect()` cưỡng bức collection có thể làm latency xấu hơn và phá heuristic của GC; chỉ nên dùng trong những trường hợp rất đặc biệt có evidence.
- Pooling giảm một số allocation nhưng tăng complexity, ownership risk và nguy cơ giữ buffer lớn; không nên pool mọi thứ theo phản xạ.
- Cần đo allocation rate, GC pause, heap/generation, retained objects và request latency correlation.

### Điểm cộng

- Nhận ra `JsonSerializer.Serialize(rows)` tạo `string` trung gian rồi `Encoding.UTF8.GetBytes` tạo buffer khác; cân nhắc serialize trực tiếp ra response/stream khi semantics cho phép.
- Đề xuất pagination/export-as-job/Blob download nếu business không cần synchronous multi-MB preview.
- Phân biệt working set/process memory với managed heap.
- Dùng load test với payload distribution thật thay vì benchmark một request nhỏ.

### Senior+

- Đặt memory budget theo concurrency: peak live bytes/request × concurrent large requests là một capacity concern.
- Cân nhắc backpressure/concurrency limit cho endpoint nặng thay vì chỉ micro-optimize allocations.
- Chỉ dùng `ArrayPool<T>` khi profile chứng minh buffer churn đáng kể và ownership/return semantics có thể đảm bảo.
- Kết hợp runtime metrics với trace/profile để chứng minh causality, không chỉ correlation.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng giả định leak. Leak trong managed runtime thường biểu hiện bằng object vẫn reachable ngoài lifetime mong muốn và retained heap tăng qua nhiều chu kỳ GC. Ở đây memory tăng theo tải rồi giảm lại là tín hiệu cần điều tra allocation pressure trước, dù vẫn chưa loại trừ retention.

Trong request này có ít nhất ba lớp dữ liệu sống đồng thời: danh sách DTO được materialize từ EF Core, `string` JSON và `byte[]` UTF-8. Với payload vài MB và nhiều request đồng thời, peak live memory có thể lớn hơn nhiều kích thước response cuối. Allocation rate cao làm GC chạy thường xuyên hơn; object sống qua collection có thể được promote, làm các collection sau tốn hơn. Large buffers cũng cần được quan sát riêng.

Tôi sẽ correlate p95/p99 với runtime counters: allocation rate, heap size, Gen collections, pause time, CPU và request concurrency. Sau đó capture allocation profile/trace ở workload đại diện để biết hot allocation site; nếu nghi retention thì xem heap snapshot/dominator/root để biết object nào đang giữ dữ liệu.

Tôi sẽ không thêm `GC.Collect()` vào request path. GC đã có heuristic riêng và forced collection có thể trực tiếp thêm pause. Tôi cũng không đưa `ArrayPool<byte>` vào trước khi biết buffer allocation có phải phần đáng kể hay không; pooling tạo ownership complexity và buffer phải được return an toàn.

Nếu evidence cho thấy materialization/serialization là nguyên nhân, hướng ưu tiên là giảm peak live data: projection tối thiểu, giới hạn payload, serialize trực tiếp ra response stream hoặc thiết kế export asynchronous ra Blob nếu requirement cho phép. Nếu synchronous endpoint vẫn cần tồn tại, có thể thêm concurrency control để bảo vệ process. Sau đó load-test với distribution payload thật và so sánh p50/p95/p99, allocation rate, GC pause và throughput.

Khuyến nghị thay đổi nếu profiling cho thấy bottleneck thực tế là SQL, network hoặc một retained object ngoài request. Khi đó tối ưu serialization sẽ không giải quyết root cause.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak vì memory tăng rồi giảm theo GC chưa chứng minh object bị giữ ngoài lifetime. Tôi sẽ tách hai khả năng: allocation pressure và retention. Đoạn code đang materialize toàn bộ rows, tạo JSON string rồi thêm một byte array, nên với payload vài MB và concurrency cao, peak live memory có thể lớn.

Về runtime, object ngắn hạn thường được thu gom ở generation trẻ; object sống lâu hơn có thể được promote và collection generation cao tốn hơn. Tôi cần correlate allocation rate, GC collections/pause, heap size và p99 với request concurrency, rồi dùng allocation profile hoặc heap snapshot để biết object nào được tạo nhiều hay bị giữ.

Tôi sẽ không gọi GC.Collect trong request path vì có thể tự tạo pause, và cũng không dùng ArrayPool cho mọi buffer nếu chưa có profile. Nếu serialization/materialization là root cause, tôi ưu tiên giảm dữ liệu sống cùng lúc: stream JSON trực tiếp nếu contract cho phép, giới hạn payload hoặc chuyển export lớn thành background job rồi tải từ Blob. Cuối cùng tôi load-test với payload thật và xác nhận p95/p99, GC pause và allocation rate đều cải thiện.”

## Câu hỏi đào sâu

1. Nếu heap snapshot cho thấy không có retention bất thường nhưng p99 vẫn correlate mạnh với Gen 2 collections, bạn sẽ thay đổi thiết kế endpoint theo thứ tự nào?
2. Nếu streaming giảm peak memory nhưng giữ HTTP connection lâu hơn, trade-off về capacity và timeout là gì?
3. Team chứng minh `ArrayPool<byte>` giảm allocation 30%, nhưng code xử lý buffer phức tạp hơn đáng kể; tiêu chí nào quyết định có giữ optimization đó?

## Lỗi trả lời thường gặp

- Thấy memory cao là kết luận ngay “memory leak”.
- Đề xuất `GC.Collect()` như một cách dọn memory định kỳ.
- Nói “LOH xấu” rồi tối ưu mà không đo object size/allocation profile.
- Dùng pooling mà không bàn ownership, return, concurrency và complexity.
- Chỉ nhìn average latency thay vì p95/p99 và correlation với GC/load.

## Thang điểm 0–10

- **0–2:** Chỉ nêu GC thu hồi memory hoặc đề xuất forced GC.
- **3–4:** Biết generations/allocation nhưng không liên hệ được với code và symptom.
- **5–6:** Phân biệt allocation pressure với leak, nhận ra các intermediate allocations và đề xuất profiling hợp lý.
- **7–8:** Có evidence plan rõ, giải thích lifetime/promotion/peak memory, đưa ra optimization có điều kiện và load-test.
- **9–10:** Reasoning theo capacity và p99, cân nhắc streaming/backpressure/pooling trade-off, phân biệt managed heap với process memory và thay đổi recommendation theo evidence.

# Câu 2 — Search index “healthy” nhưng khách hàng vẫn thấy sản phẩm cũ sau khi cập nhật

**Loại câu hỏi:** Production Incident / Troubleshooting  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, eventual consistency, background processing, distributed systems, observability, cache/CDN reasoning, incident response

## Bối cảnh

Một e-commerce platform dùng SQL Server làm source of truth cho product catalog và Elasticsearch làm read model cho search. Khi Product team cập nhật tên, giá hoặc trạng thái bán của sản phẩm, transaction SQL commit trước; một background process sau đó đồng bộ thay đổi sang Elasticsearch.

Sau một deployment, một số khách hàng tìm kiếm vẫn thấy giá cũ trong 10–20 phút. Product detail page đọc SQL trực tiếp nên hiển thị giá mới. Elasticsearch cluster báo healthy, search latency bình thường và không có spike rõ ràng về HTTP 5xx. Restart background worker làm backlog giảm tạm thời nhưng vài giờ sau symptom quay lại.

Một engineer muốn reindex toàn bộ catalog. Engineer khác muốn giảm Elasticsearch refresh interval. Người thứ ba nghi Akamai/CDN cache dù API search response hiện được cho là dynamic.

Chưa rõ cơ chế capture change, retry semantics, queue/backlog, checkpoint, poison item, mapping/indexing error, version ordering, worker concurrency, hay có cache nào nằm giữa browser và search API.

## Câu hỏi chính

Bạn đang on-call. Hãy trình bày cách **stabilize → collect evidence → form hypotheses → narrow down → remediate → verify → prevent recurrence** cho incident này. Bạn sẽ phân biệt lỗi ở change capture/background worker, message ordering/retry, Elasticsearch indexing/refresh, application cache/CDN và dữ liệu source như thế nào, và vì sao chưa nên reindex toàn bộ hoặc thay refresh interval ngay?

## Câu hỏi làm rõ nên cân nhắc

1. Mỗi product update được đồng bộ bằng polling, queue/event hay Outbox; checkpoint/offset được lưu ở đâu?
2. “10–20 phút” là delay từ SQL commit đến worker nhận item, từ worker đến Elasticsearch visibility, hay từ Elasticsearch đến client?
3. Có metric về oldest pending age, backlog depth, processing rate, retry count và failed/poison items không?
4. Một product có thể được update nhiều lần nhanh chóng không, và consumer có cơ chế chống event cũ overwrite event mới không?
5. Search API có application cache, Redis, browser cache hoặc CDN rule nào áp dụng cho response không?

## Gợi ý tư duy

### Gợi ý 1

Cluster “healthy” và query nhanh chỉ chứng minh một phần của pipeline. Hãy dựng timeline của **một product cụ thể** từ write source đến response client.

### Gợi ý 2

Tách **transport lag**, **processing lag**, **index visibility**, **ordering/version correctness** và **response caching**. Chúng tạo symptom giống nhau nhưng evidence khác nhau.

### Gợi ý 3

Restart worker làm backlog giảm là evidence đáng chú ý nhưng chưa phải root cause. Hãy hỏi tại sao throughput worker suy giảm hoặc progress bị kẹt theo thời gian.

## Cấu trúc trả lời đề xuất

1. Xác định impact/SLA và phạm vi affected products.
2. Stabilize an toàn, tránh destructive reindex khi chưa hiểu lỗi.
3. Chọn vài product IDs làm trace mẫu.
4. Dựng end-to-end timestamp/correlation timeline.
5. Kiểm tra source SQL và change publication.
6. Kiểm tra backlog/checkpoint/retry/poison/concurrency.
7. Kiểm tra Elasticsearch document/version/indexing response.
8. Bypass từng cache layer để cô lập.
9. Sửa root cause và replay/reconcile có kiểm soát.
10. Verify bằng freshness SLI và ngăn recurrence.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Xác nhận SQL là source of truth và so sánh một product cụ thể qua từng stage.
- Không đồng nhất cluster health/search latency với indexing freshness.
- Đo lag/backlog của pipeline, không chỉ error rate.
- Kiểm tra retry, poison item, checkpoint và failure có bị swallow hay không.
- Xem xét out-of-order update nếu cùng product có nhiều version/event.
- Bypass cache/CDN để xác định stale data đến từ Elasticsearch hay downstream cache.
- Reindex toàn bộ có blast radius/cost và có thể chỉ che symptom nếu sync pipeline vẫn lỗi.
- Refresh interval liên quan visibility sau indexing, nhưng không chữa event chưa được xử lý hoặc worker backlog.
- Sau fix phải reconcile dữ liệu bị miss/stale, không chỉ restart worker.

### Điểm cộng

- Đề xuất correlation fields như productId, source version/update timestamp, event ID, worker attempt, index result.
- Dùng freshness SLI: thời gian từ source commit đến searchable document.
- Phân biệt retryable failure với permanent mapping/data error.
- Nếu có messaging, thiết kế idempotent consumer và version guard để event cũ không overwrite state mới.

### Senior+

- Stabilization có thể giảm worker concurrency nếu downstream bị overload, hoặc tăng có kiểm soát nếu bottleneck là capacity và dependency chịu được; không scale mù.
- Reconciliation job so sánh source version với indexed version có thể phát hiện silent drift.
- Nếu publication và SQL commit không atomic, cân nhắc Outbox Pattern thay vì dual-write mong manh.
- Alert theo oldest-event age/freshness lag thường hữu ích hơn chỉ alert queue depth.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định impact: tỷ lệ sản phẩm stale, tenant/region nào, chỉ price hay mọi field, và SLA freshness. Nếu giá cũ có business risk, tôi cân nhắc tạm thời vô hiệu hóa search price hoặc route critical detail về source of truth tùy product requirement, thay vì lập tức reindex.

Tôi chọn vài product IDs bị lỗi và dựng timeline: SQL `UpdatedAt/version` → change/event created → worker received → attempt/retry → Elasticsearch index response → document/version đọc trực tiếp từ Elasticsearch → search API response → response khi bypass cache. Mục tiêu là tìm stage đầu tiên mà version diverge.

Nếu event chưa được tạo sau SQL commit, lỗi nằm ở publication/change capture. Nếu event tồn tại nhưng oldest pending age tăng, kiểm tra worker throughput, checkpoint, poison item, retry loop, dependency timeout và resource exhaustion. Nếu worker báo success nhưng Elasticsearch document vẫn cũ, kiểm tra index target/alias, mapping rejection, response handling và ordering. Nếu document trong Elasticsearch đã mới nhưng client vẫn cũ, bypass Redis/application cache/CDN/browser để tìm cache layer.

Restart worker giúp backlog giảm gợi ý worker có degradation theo thời gian: resource leak, stuck partition, retry storm, checkpoint issue, connection exhaustion hoặc concurrency bug là các hypothesis cần evidence. Tôi không coi restart là fix.

Tôi chưa giảm refresh interval vì 10–20 phút stale có thể chủ yếu là processing lag; cần đo thời gian từ successful index operation đến search visibility trước. Tôi cũng không full reindex khi chưa biết sync path có ổn, vì reindex tốn tài nguyên và stale sẽ tái diễn.

Sau root-cause fix, tôi replay/reconcile các product bị miss bằng idempotent process. Nếu ordering có thể đảo, document update nên có source version/timestamp guard phù hợp để event cũ không ghi đè mới. Nếu SQL update và event publication hiện là hai bước độc lập dễ mất event, Outbox là một lựa chọn đáng đánh giá.

Cuối cùng tôi thêm dashboard/alert cho freshness lag, oldest pending age, processing throughput, retries/permanent failures và indexing failures; log structured theo product/event/version; và có reconciliation định kỳ nếu business yêu cầu độ tin cậy cao.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng reindex. Cluster healthy chỉ nói cluster có thể phục vụ workload; nó không chứng minh dữ liệu đã đi từ SQL sang index đúng thời gian.

Tôi lấy một product bị stale và dựng timeline end-to-end: version trong SQL, event/change record, thời điểm worker nhận, retry, Elasticsearch index response, version đọc trực tiếp từ Elasticsearch rồi response API khi bypass cache. Nếu event chưa tồn tại thì điều tra publication; nếu backlog age tăng thì worker/queue; nếu worker success nhưng document cũ thì kiểm tra index alias, rejection hoặc ordering; nếu Elasticsearch đã mới mà client cũ thì mới tập trung cache/CDN.

Restart worker làm backlog giảm là một clue về degradation nhưng chưa phải root cause. Tôi đo throughput, oldest pending age, retry và resource metrics để biết worker kẹt ở đâu. Tôi cũng không giảm refresh interval nếu event còn chưa được xử lý.

Sau khi sửa, tôi reconcile/replay các item stale theo cách idempotent, rồi thêm freshness SLI từ SQL commit đến searchable document và alert theo oldest lag. Nếu publication có cửa sổ mất event giữa SQL commit và publish, tôi sẽ đánh giá Outbox để đóng failure window đó.”

## Câu hỏi đào sâu

1. Nếu worker xử lý nhanh, Elasticsearch document đọc trực tiếp đã mới sau vài giây nhưng user vẫn thấy cũ 15 phút, bạn sẽ cô lập cache layers thế nào?
2. Nếu event A(version 41) retry muộn và đến sau event B(version 42), consumer/indexing design nào ngăn A ghi đè B?
3. Nếu Product yêu cầu search phản ánh price gần như ngay lập tức nhưng catalog search vẫn dùng eventual consistency, bạn sẽ thách thức hoặc thay đổi kiến trúc ở đâu?

## Lỗi trả lời thường gặp

- Thấy Elasticsearch stale là lập tức full reindex.
- Đồng nhất cluster health với data freshness.
- Chỉ kiểm tra error logs mà không đo backlog age/processing lag.
- Restart worker rồi coi incident đã giải quyết.
- Bỏ qua ordering, idempotency và cache layers.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/reindex.
- **3–4:** Biết kiểm tra worker và Elasticsearch nhưng không có phương pháp cô lập stage.
- **5–6:** Dựng được pipeline, dùng product/version cụ thể và xem backlog/retry/cache.
- **7–8:** Incident reasoning có stabilization, hypotheses, evidence, replay và observability.
- **9–10:** Xử lý ordering/idempotency/publication gap, freshness SLI, reconciliation và thay đổi kiến trúc có điều kiện theo consistency requirement.

# Câu 3 — Modernize hệ thống .NET Framework: chuyển thẳng lên Kubernetes hay đi từng bước?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework 4.5, ASP.NET MVC, IIS/Windows Server, modern .NET, Azure App Service, Kubernetes, migration strategy, CI/CD, rollback, observability, architecture trade-offs

## Bối cảnh

Một internal management portal khoảng 9 năm tuổi đang chạy ASP.NET MVC trên .NET Framework 4.5, IIS và Windows Server. Hệ thống dùng SQL Server, Windows-integrated assumptions ở một số module, filesystem local để lưu temporary/export files, một số scheduled jobs chạy trong web application, và vài thư viện third-party cũ.

Ứng dụng vẫn phục vụ business ổn nhưng deployment mất khoảng 40 phút, rollback thủ công, production patch rủi ro và framework/dependency đã cũ. Team muốn tiến tới modern .NET và Linux hosting. Một proposal đề xuất:

1. rewrite toàn bộ sang .NET 10,
2. containerize,
3. tách thành microservices,
4. deploy lên Kubernetes,
5. thay toàn bộ pipeline cùng lúc.

Một proposal khác muốn giữ nguyên IIS thêm vài năm và chỉ nâng package khi cần.

Business không chấp nhận downtime dài. Team có 6 developers, vẫn phải giao feature hàng sprint, và chưa có nhiều kinh nghiệm vận hành Kubernetes. Chưa rõ test coverage, dependency compatibility, Windows-only integration, traffic profile, module coupling, database boundaries hay yêu cầu scaling thực tế.

## Câu hỏi chính

Bạn là Technical Lead chịu trách nhiệm modernization roadmap. Hãy thiết kế một chiến lược migration giảm rủi ro từ .NET Framework 4.5 tới modern .NET, quyết định khi nào nên giữ IIS/Windows, khi nào Azure App Service/Linux hoặc container có giá trị, và tiêu chí nào mới đủ để Kubernetes/microservices đáng chi phí. Hãy trình bày dependency assessment, migration boundary, rollout/rollback, database strategy, CI/CD, testing và observability mà không mặc định rewrite-from-scratch.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào phụ thuộc Windows-specific API, COM, GDI, Windows Authentication, filesystem hoặc third-party library không hỗ trợ modern .NET/Linux?
2. Kiến trúc hiện tại là monolith có module boundaries rõ hay shared database/shared static state rất chặt?
3. Test pyramid hiện có gì: unit, integration, API, Playwright E2E, regression manual?
4. Traffic/availability/scaling requirement nào thực sự không được IIS/App Service hiện tại đáp ứng?
5. Release frequency, acceptable rollback time, data migration tolerance và maintenance window của business là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

Modernization là bài toán **risk decomposition**, không phải chọn hosting platform trước. Hãy inventory dependency và tìm migration seams.

### Gợi ý 2

Tách ba quyết định: **runtime modernization**, **application architecture**, và **deployment/orchestration platform**. Chúng không bắt buộc phải xảy ra cùng lúc.

### Gợi ý 3

Một roadmap tốt tạo ra các checkpoint có thể deploy, đo và rollback. “Big-bang rewrite” làm mất những checkpoint đó.

## Cấu trúc trả lời đề xuất

1. Làm rõ business/SLO/release constraints.
2. Inventory dependencies và Windows-specific assumptions.
3. Baseline behavior, telemetry và regression coverage.
4. Xác định module seams và migration sequence.
5. Tách runtime, architecture và hosting decisions.
6. Chọn target hosting đơn giản nhất đáp ứng requirement.
7. Thiết kế data/compatibility boundary.
8. Xây CI/CD, automated validation và rollback.
9. Migrate incrementally bằng canary/parallel path khi phù hợp.
10. Đánh giá lại Kubernetes/microservices bằng evidence sau từng phase.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không đồng nhất “modern .NET” với “microservices + Kubernetes”.
- Inventory package/API/hosting/Windows dependencies trước khi cam kết Linux.
- Tạo regression safety net trước hoặc song song với migration.
- Ưu tiên incremental modernization khi có thể; chia migration thành các deployable checkpoints.
- Scheduled jobs không nên tiếp tục phụ thuộc tùy tiện vào web-process lifetime nếu correctness yêu cầu execution đáng tin cậy.
- Local filesystem assumption phải được đánh giá trước scale-out/ephemeral hosting; durable file cần storage phù hợp.
- Database migration phải backward-compatible với rollout/rollback khi old/new version chạy song song.
- CI/CD phải tạo artifact nhất quán, automated test, health verification và rollback path.
- Kubernetes chỉ hợp lý khi requirement/operational capability biện minh cho orchestration complexity.
- Microservices chỉ nên tách khi service boundary, ownership/scaling/deployment autonomy hoặc reliability need đủ rõ.

### Điểm cộng

- Dùng characterization tests/Playwright cho critical user journeys khi legacy unit coverage thấp.
- Có thể modernize monolith trước thành modular monolith để giảm coupling và tìm boundaries.
- Dùng strangler-style routing cho một số module nếu boundary đủ rõ, thay vì rewrite toàn bộ.
- Đưa configuration/secrets ra khỏi machine-specific state; dùng managed secret/identity approach khi platform phù hợp.
- Baseline telemetry trước migration để biết “mới” có thực sự tốt hơn.

### Senior+

- Tách schema evolution theo expand/contract để old/new code coexist.
- Đặt exit criteria cho từng phase: compatibility, error budget, latency, deployment/rollback time, incident rate.
- Tính cả cognitive/operational cost của Kubernetes cho team 6 người.
- Nếu App Service đáp ứng SLO và scaling, chọn nó có thể là quyết định kiến trúc tốt hơn Kubernetes.
- Xác định rollback data semantics: code rollback không đủ nếu schema/data transformation không reversible.

## Hướng giải quyết tham khảo

Tôi sẽ chia bài toán thành ba decision tracks: runtime, application boundaries và hosting. Proposal big-bang đang ghép cả ba nên blast radius rất lớn.

Phase đầu là discovery và safety net. Tôi inventory target framework/package compatibility, Windows-only APIs, authentication, filesystem, scheduled jobs, IIS-specific config và third-party dependencies. Tôi baseline production behavior: critical flows, latency/error, deployment time và operational pain. Nếu unit coverage thấp, tôi ưu tiên characterization/integration/Playwright E2E cho các journey business quan trọng để bảo vệ behavior trong migration.

Sau đó tôi tìm seams. Nếu monolith có module tương đối độc lập, có thể tách dependency và modernize từng phần hoặc dùng strangler approach. Nếu coupling quá cao, bước hợp lý có thể là modularize monolith trước, không phải microservices. Tôi muốn mỗi phase tạo artifact deployable và có rollback.

Tôi cũng loại bỏ assumptions gây khó scale/host: durable files không nằm trên local filesystem; scheduled jobs có execution model rõ; config/secrets không gắn với machine; session/state được hiểu rõ. Nhưng tôi chỉ thay khi requirement cần, tránh refactor tất cả cùng lúc.

Về hosting, nếu modernized application chạy tốt trên Azure App Service/Linux và SLO không đòi orchestration phức tạp, đó có thể là target đơn giản hơn. Container có thể hữu ích cho artifact/runtime consistency nhưng container không bắt buộc kéo theo Kubernetes. Tôi chỉ chọn Kubernetes nếu có nhu cầu thực như nhiều independently deployed workloads, orchestration capability, scaling/availability requirement và team đủ năng lực vận hành. Với 6 developers chưa có nhiều Kubernetes experience, operational cost là một yếu tố lớn.

Database cần migration tương thích giữa old/new version. Tôi ưu tiên expand/contract: thêm schema mới tương thích, deploy code có thể coexist, backfill/verify, chuyển read/write, rồi mới remove old schema. Không để một migration irreversible phá rollback.

CI/CD được nâng dần: build reproducible artifact, automated tests, security/static checks phù hợp, deploy staging, smoke/health checks, progressive rollout nếu platform hỗ trợ, và rollback đã diễn tập. Telemetry phải có correlation, request/dependency metrics và business-critical signals để so sánh trước/sau.

Tôi sẽ không giữ .NET Framework vô thời hạn, nhưng cũng không coi “latest runtime + Kubernetes + microservices” là một migration unit. Roadmap tốt là giảm unsupported/legacy risk theo từng bước, mỗi bước tạo giá trị và giữ khả năng quay lại. Sau khi monolith đã modernized và boundaries/traffic/ownership được đo rõ, lúc đó mới đánh giá service extraction bằng evidence.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách ba quyết định đang bị gộp: nâng runtime, thay architecture và đổi hosting. Không có lý do kỹ thuật nào buộc modern .NET phải đi cùng microservices và Kubernetes.

Đầu tiên tôi inventory package và Windows-specific dependencies, filesystem, authentication, scheduled jobs và IIS assumptions. Đồng thời tạo regression safety net cho critical flows bằng integration hoặc Playwright nếu legacy unit coverage thấp. Sau đó tôi tìm module seams và chọn migration nhỏ có thể deploy/rollback; nếu coupling cao, tôi ưu tiên modularize monolith trước.

Với hosting, tôi chọn platform đơn giản nhất đáp ứng SLO. Nếu App Service/Linux đủ, tôi không đưa Kubernetes vào chỉ vì container hóa. Kubernetes chỉ đáng giá khi workload và operating model cần orchestration, và team có năng lực chịu operational cost.

Database migration phải cho old/new code coexist, ví dụ expand/contract, vì rollback code không có nghĩa rollback data an toàn. Pipeline cần reproducible artifact, automated validation, health checks và rollback đã test. Tôi baseline telemetry trước migration rồi đặt exit criteria cho từng phase.

Mục tiêu của tôi không phải rewrite nhanh nhất mà là giảm legacy risk liên tục, mỗi bước có giá trị, có evidence và có đường lui.”

## Câu hỏi đào sâu

1. Nếu một third-party library critical chỉ chạy trên .NET Framework/Windows và vendor chưa có replacement, bạn thay đổi roadmap thế nào?
2. Nếu CTO yêu cầu Kubernetes vì “đó là platform chuẩn của công ty” nhưng team hiện chỉ có một monolith và ít operational experience, bạn sẽ đánh giá và trình bày trade-off ra sao?
3. Nếu schema migration mới đã backfill hàng trăm triệu rows, code rollback cần thực hiện nhưng data không thể rollback nhanh, bạn thiết kế compatibility từ trước như thế nào?

## Lỗi trả lời thường gặp

- Coi rewrite-from-scratch là mặc định vì code cũ “khó”.
- Gộp runtime upgrade, microservices và Kubernetes thành một migration duy nhất.
- Bỏ qua Windows-only dependencies và filesystem/process assumptions.
- Chỉ nói về code mà không có rollout, rollback, schema compatibility và observability.
- Chọn Kubernetes theo xu hướng thay vì requirement và operating cost.

## Thang điểm 0–10

- **0–2:** Chỉ chọn rewrite hoặc giữ nguyên legacy mà không phân tích.
- **3–4:** Có migration steps nhưng thiếu dependency/data/rollback reasoning.
- **5–6:** Tách được runtime/architecture/hosting, có inventory, tests và incremental rollout.
- **7–8:** Có compatibility strategy, CI/CD, observability, modularization và platform trade-off rõ.
- **9–10:** Roadmap có deployable checkpoints, expand/contract data strategy, measurable exit criteria, operating-cost analysis và biết khi nào không nên dùng microservices/Kubernetes.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **GC/performance:** memory cao không tự đồng nghĩa memory leak; cần phân biệt allocation pressure, retained objects và peak live memory, rồi dùng profiling/metrics để chứng minh bottleneck.
- **Distributed search pipeline:** một read model có thể “healthy” nhưng stale nếu change publication, backlog, retry, ordering hoặc cache layer có vấn đề; freshness phải được quan sát end-to-end.
- **Modernization:** runtime, architecture và hosting là các quyết định độc lập. Incremental migration với compatibility và rollback thường giảm rủi ro hơn big-bang rewrite.
- **Production engineering:** symptom giống nhau có thể xuất phát từ nhiều layer; telemetry phải giúp xác định stage đầu tiên diverge khỏi expected state.

## Mẫu tư duy cần nhớ

- Measure before optimizing.
- Trace one concrete entity/request end-to-end before generalizing.
- Stabilize before deep investigation.
- Separate runtime, architecture and platform decisions.
- Design rollout together with rollback and data compatibility.
