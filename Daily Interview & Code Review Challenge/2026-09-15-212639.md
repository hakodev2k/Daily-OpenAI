# Code Review Challenge 1 — Optimizely content cache giữ dữ liệu theo tenant sai và tạo stampede khi content publish

**Chủ đề:** C#/.NET, Optimizely CMS, ASP.NET Core, caching, concurrency, content freshness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40–50 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một marketing website dùng Optimizely CMS để quản lý landing pages cho nhiều market. Backend có service dựng navigation model từ published content. Để giảm số lần đọc CMS, team thêm singleton cache tự viết.

Production chạy 6 application instances sau CDN. Mỗi request có `market` và `language`. Khi editor publish thay đổi, một số users vẫn thấy navigation cũ vài phút; nghiêm trọng hơn, đôi lúc navigation của market `US` xuất hiện ở request `CA`. Khi một key hết hạn trong giờ cao điểm, CPU và CMS/content-read latency tăng đột biến. Local test một instance gần như không tái hiện được.

Business chấp nhận eventual freshness khoảng 60 giây, nhưng không chấp nhận cross-market data leakage. Không có yêu cầu bắt buộc phải dùng Redis.

## Đoạn code cần review

```csharp
public sealed class NavigationService
{
    private readonly IContentLoader _contentLoader;
    private readonly Dictionary<string, CacheEntry> _cache = new();

    public NavigationService(IContentLoader contentLoader)
    {
        _contentLoader = contentLoader;
    }

    public Task<IReadOnlyList<NavigationItem>> GetAsync(
        ContentReference root,
        string market,
        string language,
        CancellationToken cancellationToken)
    {
        var key = root.ID.ToString();

        if (_cache.TryGetValue(key, out var cached) &&
            cached.ExpiresAtUtc > DateTime.UtcNow)
        {
            return Task.FromResult(cached.Items);
        }

        var pages = _contentLoader
            .GetChildren<PageData>(root)
            .Where(x => x.VisibleInMenu)
            .OrderBy(x => x.SortOrder)
            .ToList();

        var items = pages
            .Select(x => new NavigationItem(
                x.ContentLink.ID,
                x.Name,
                x.LinkURL))
            .ToList();

        _cache[key] = new CacheEntry(
            items,
            DateTime.UtcNow.AddMinutes(5));

        return Task.FromResult<IReadOnlyList<NavigationItem>>(items);
    }

    private sealed record CacheEntry(
        IReadOnlyList<NavigationItem> Items,
        DateTime ExpiresAtUtc);
}

builder.Services.AddSingleton<NavigationService>();
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, isolation và concurrency problems.
2. Giải thích vì sao cache key hiện tại có thể trả dữ liệu sai market/language.
3. Phân tích behavior khi nhiều requests cùng miss một hot key.
4. Ưu tiên findings theo production impact, đặc biệt cross-market leakage.
5. Đề xuất implementation/design cải thiện mà không mặc định thêm distributed cache.
6. Giải thích testing cho market/language isolation, concurrent miss, publish/invalidation và multi-instance behavior.
7. Đề xuất telemetry chứng minh cache hit/freshness đúng thay vì chỉ đo request latency.

## Câu hỏi gợi mở

1. Hai request cùng `root.ID` nhưng khác market/language có dùng cùng cache entry không?
2. Singleton service có thể bị bao nhiêu request threads truy cập đồng thời?
3. Điều gì xảy ra khi 500 requests cùng tới ngay sau expiration?
4. TTL 5 phút có phù hợp requirement freshness khoảng 60 giây không?
5. Sáu instances có chia sẻ cùng cache state hoặc cùng thời điểm invalidation không?

### Gợi ý 1

Rủi ro lớn nhất không phải performance mà là **cache identity không biểu diễn đầy đủ identity của dữ liệu**.

### Gợi ý 2

Sau correctness, hãy xem shared mutable state, cache stampede, publish invalidation và semantics giữa nhiều instances.

## Kết quả code review tham khảo

### Critical — Cache key bỏ qua market và language

**Vấn đề:** Key chỉ dùng `root.ID`, trong khi output phụ thuộc ít nhất vào market/language và có thể còn phụ thuộc content version/context.

**Tại sao xảy ra:** Cache identity hẹp hơn data identity. Request đầu tiên populate entry có thể quyết định dữ liệu trả cho các request context khác.

**Ảnh hưởng production:** Cross-market/cross-language content leakage và dữ liệu nghiệp vụ sai. Đây là correctness/security boundary, không chỉ là stale cache.

**Cách sửa:** Xác định đầy đủ dimensions làm thay đổi output và đưa chúng vào normalized cache key; ví dụ root + market + language + relevant content context. Không cache dữ liệu contextual nếu không thể xác định key an toàn.

### High — Mutable `Dictionary` trong singleton bị truy cập đồng thời

**Vấn đề:** `_cache` được đọc/ghi từ nhiều requests trên cùng process mà không có synchronization phù hợp.

**Tại sao xảy ra:** Singleton là shared state; request concurrency làm operations interleave.

**Ảnh hưởng production:** Race conditions và behavior khó tái hiện trong local single-user test.

**Cách sửa:** Dùng cache abstraction thread-safe như `IMemoryCache` hoặc synchronization/concurrent structure phù hợp với semantics cần thiết.

### High — Cache stampede khi entry hết hạn

**Vấn đề:** Nhiều requests cùng miss sẽ cùng load children và build navigation.

**Tại sao xảy ra:** Check-then-load không có per-key single-flight/coalescing.

**Ảnh hưởng production:** Content repository/CPU load tăng đúng lúc hot key expire, tạo latency spike.

**Cách sửa:** Nếu telemetry chứng minh stampede đáng kể, coalesce concurrent loads theo key. Tránh global lock làm các market/root không liên quan chặn nhau.

### High — Freshness policy mâu thuẫn business requirement

**Vấn đề:** TTL cố định 5 phút trong khi business chấp nhận stale khoảng 60 giây.

**Tại sao xảy ra:** Cache policy không được derive từ freshness contract.

**Ảnh hưởng production:** Editor publish nhưng users tiếp tục thấy content cũ vượt expectation.

**Cách sửa:** Định nghĩa freshness SLO và chọn TTL/invalidation theo SLO. Nếu CMS cung cấp publish/change notification phù hợp với architecture, có thể invalidate local entries; vẫn cần fallback TTL vì invalidation có thể fail.

### Medium — Multi-instance local cache có freshness độc lập

**Vấn đề:** Sáu instances có sáu cache state.

**Tại sao xảy ra:** In-memory cache không tự đồng bộ giữa processes.

**Ảnh hưởng production:** Users có thể thấy version khác nhau tùy instance trong freshness window.

**Cách sửa:** Nếu 60 giây eventual freshness được chấp nhận, local cache với TTL ngắn có thể đủ và đơn giản. Nếu publish phải propagate nhanh trên mọi instance, cân nhắc shared invalidation/version signal. Redis chỉ là một lựa chọn, không phải mặc định.

### Medium — CancellationToken không tham gia content loading

**Vấn đề:** Method nhận token nhưng implementation không dùng nó; API content loader được gọi synchronously.

**Tại sao xảy ra:** Async signature tạo cảm giác cancellation-aware nhưng operation thực tế không cooperative.

**Ảnh hưởng production:** Request cancellation không dừng phần work này; dưới overload có thể tiếp tục tiêu tốn resources.

**Cách sửa:** Không giả vờ async nếu dependency là synchronous; giữ synchronous core hoặc dùng API async thật sự nếu stack/version hỗ trợ và semantics phù hợp. Chỉ truyền cancellation nơi API hỗ trợ.

### Medium — Custom cache không có bounded eviction policy

**Vấn đề:** Expired entries chỉ bị overwrite khi cùng key được truy cập lại; cardinality root/context có thể tăng.

**Tại sao xảy ra:** Dictionary không có eviction/size management.

**Ảnh hưởng production:** Memory tăng theo số key đã từng truy cập.

**Cách sửa:** Dùng cache abstraction có expiration/eviction và cân nhắc size limit dựa trên measured cardinality.

### Low — Wall-clock dependency làm expiration tests khó deterministic

**Vấn đề:** `DateTime.UtcNow` nằm trực tiếp trong logic.

**Tại sao xảy ra:** Time không được abstract.

**Ảnh hưởng production:** Không phải outage root cause nhưng tests TTL dễ chậm/flaky.

**Cách sửa:** Dùng time abstraction phù hợp runtime/project khi cần deterministic tests.

## Phiên bản đề xuất

Một hướng giữ solution đơn giản là local `IMemoryCache`, key đầy đủ và per-key single-flight. Ví dụ rút gọn:

```csharp
public sealed class NavigationService
{
    private readonly IContentLoader _contentLoader;
    private readonly IMemoryCache _cache;
    private readonly ConcurrentDictionary<string, SemaphoreSlim> _gates = new();

    public NavigationService(IContentLoader contentLoader, IMemoryCache cache)
    {
        _contentLoader = contentLoader;
        _cache = cache;
    }

    public async Task<IReadOnlyList<NavigationItem>> GetAsync(
        ContentReference root,
        string market,
        string language,
        CancellationToken cancellationToken)
    {
        var key = $"nav:{root.ID}:{market.ToUpperInvariant()}:{language.ToLowerInvariant()}";

        if (_cache.TryGetValue<IReadOnlyList<NavigationItem>>(key, out var cached))
            return cached!;

        var gate = _gates.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
        await gate.WaitAsync(cancellationToken);

        try
        {
            if (_cache.TryGetValue<IReadOnlyList<NavigationItem>>(key, out cached))
                return cached!;

            // The exact Optimizely language/market selection mechanism must follow
            // the application's content model and installed Optimizely version.
            var pages = _contentLoader
                .GetChildren<PageData>(root)
                .Where(x => x.VisibleInMenu)
                .OrderBy(x => x.SortOrder)
                .ToList();

            var items = pages
                .Select(x => new NavigationItem(x.ContentLink.ID, x.Name, x.LinkURL))
                .ToArray();

            _cache.Set(key, items, TimeSpan.FromSeconds(60));
            return items;
        }
        finally
        {
            gate.Release();
        }
    }
}
```

Đoạn trên cố ý không khẳng định API cụ thể để chọn Optimizely market/language vì điều đó phụ thuộc content model và version đang dùng; production implementation phải xác minh official API hiện hành. Ngoài ra cần cleanup strategy cho `_gates` nếu key cardinality lớn.

## Giải thích thiết kế sau khi sửa

Correct cache key là điều kiện tiên quyết; cache nhanh nhưng trả sai tenant/market là failure nghiêm trọng hơn cache miss. `IMemoryCache` giải quyết phần thread-safe storage/expiration tốt hơn custom dictionary. Per-key gate chỉ nên thêm nếu load test/telemetry cho thấy concurrent misses gây stampede đáng kể.

TTL 60 giây minh họa business freshness assumption, không phải universal value. Nếu publish event có thể invalidate đúng keys trên từng instance một cách đáng tin cậy, invalidation giúp freshness tốt hơn; TTL vẫn hữu ích như safety net.

Không tự động dùng Redis. Distributed cache thêm network latency, serialization và outage mode. Nếu local cache đáp ứng correctness/freshness SLO, solution đơn giản hơn có thể tốt hơn.

## Trade-offs

- Key nhiều dimensions tăng cardinality và memory footprint.
- Per-key gates tăng state/cleanup complexity.
- TTL ngắn tăng CMS reads; TTL dài tăng stale window.
- Publish-driven invalidation giảm stale time nhưng thêm coupling với CMS event lifecycle.
- Distributed invalidation/cache cải thiện cross-instance coordination nhưng thêm dependency và operational complexity.

## Cách kiểm thử

1. **Isolation test:** cùng root nhưng US/en và CA/fr phải tạo/đọc entry riêng, không cross-leak.
2. **Concurrency test:** hàng trăm concurrent requests cho một expired key; đo số content loads thực tế.
3. **Freshness test:** advance fake time/publish content và xác minh stale window không vượt contract.
4. **Multi-instance integration test:** mô phỏng hai cache instances và xác minh behavior phù hợp eventual-freshness assumption.
5. **Failure/load test:** content dependency chậm hoặc lỗi; xác minh request pressure, fallback/error behavior và telemetry.

## Quan sát trong production

Theo dõi cache hit/miss theo normalized market/language/root, load duration, concurrent loaders per key, entry count và content freshness age. Application Insights/Kibana nên có structured fields cho market, language, root content ID, cache outcome và application instance nhưng không log sensitive content.

Alert khi cross-market invariant bị vi phạm, content load dependency latency tăng mạnh hoặc miss rate bất thường. Với publish flow, đo `publish-to-visible` latency thay vì chỉ HTTP response time.

## Câu hỏi phỏng vấn mở rộng

1. Nếu editor yêu cầu publish phải visible toàn cầu dưới 5 giây, bạn sẽ thay đổi invalidation architecture thế nào?
2. Khi nào bạn bỏ cache hoàn toàn thay vì tiếp tục tăng cache complexity?
3. Nếu navigation phụ thuộc thêm user segment, bạn sẽ quyết định cache key hay không cache dựa trên cardinality/security như thế nào?

# Code Review Challenge 2 — CI/CD chạy database migration trước rollout và làm production không rollback được

**Chủ đề:** CI/CD, TeamCity/Jenkins concepts, Octopus Deploy, EF Core migrations, release safety, rollback, secrets  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một ASP.NET Core API được build một lần rồi deploy qua environments bằng TeamCity và Octopus Deploy. Release mới thêm column `DisplayName` và code mới bắt đầu đọc column đó. Team cũng muốn xóa column legacy `Name` trong cùng release.

Production có 8 instances phía sau load balancer. Deployment hiện chạy migration trước, sau đó lần lượt thay application package. Nếu deployment fail ở instance thứ 3, operator dùng Octopus rollback về package cũ.

Gần đây staging fail giữa rollout: schema đã thay đổi nhưng một số instances vẫn chạy code cũ. Rollback package không phục hồi được service. Pipeline configuration rút gọn:

## Đoạn code cần review

```yaml

  - name: restore
    run: dotnet restore src/Catalog.Api/Catalog.Api.csproj

  - name: build
    run: dotnet build src/Catalog.Api/Catalog.Api.csproj -c Release

  - name: migrate-production
    run: dotnet ef database update --project src/Catalog.Data

      ConnectionStrings__CatalogDb: "Server=prod-db;Database=Catalog;User Id=deploy;Password=P@ssw0rd!"

protected override void Up(MigrationBuilder migrationBuilder)

## Kết quả code review tham khảo

### Critical — Drop `Name` trước khi code cũ rời production

**Vấn đề:** Migration destructive chạy trước rolling deployment, trong khi 8 instances code cũ vẫn có thể đọc `Name`.

**Tại sao xảy ra:** Database schema và application versions có independent rollout timing; pipeline giả định cutover atomic.

**Ảnh hưởng production:** Các instances cũ có thể lỗi SQL ngay sau migration, trước khi package mới được deploy. Partial rollout làm mixed-version failure kéo dài.

**Cách sửa:** Dùng expand/contract. Release A thêm `DisplayName` nhưng giữ `Name`; code trong transition đọc/ghi tương thích theo strategy đã định. Backfill và verify. Chỉ drop `Name` ở release sau khi không còn old readers/writers và rollback window đã đóng.

### Critical — Production database secret hard-code trong pipeline

**Vấn đề:** Connection string chứa username/password plaintext.

**Tại sao xảy ra:** Secret được coi như pipeline configuration thường.

**Ảnh hưởng production:** Credential có thể lộ qua repository, pipeline config/history/logging và khó rotate.

**Cách sửa:** Dùng secret store/variable scoping của deployment platform với least privilege; trên Azure cân nhắc identity-based access/Managed Identity khi supported. Không echo secret và tách migration principal permissions khỏi application permissions.

### High — Application rollback không rollback schema safely

**Vấn đề:** Operator rollback package cũ sau destructive migration.

**Tại sao xảy ra:** Database state là shared persistent state; package rollback chỉ thay executable artifact.

**Ảnh hưởng production:** Old code có thể không tương thích schema hiện tại; rollback làm outage tệ hơn.

**Cách sửa:** Thiết kế forward/backward compatibility qua rollback window. Ưu tiên roll-forward schema fix; destructive contract migration chỉ sau khi old version không còn là rollback target.

### High — Data backfill nằm trong migration blocking path

**Vấn đề:** `UPDATE Products ...` có thể chạm toàn bộ table trong deployment transaction/path.

**Tại sao xảy ra:** Schema evolution và potentially large data migration được gộp một bước.

**Ảnh hưởng production:** Locking, transaction log growth, deployment timeout và database pressure tùy table size/provider/configuration.

**Cách sửa:** Đo row count/execution plan/locking behavior. Với bảng lớn, backfill theo bounded batches bằng operational job/script có checkpoint, throttling và observability; chỉ enforce final constraint sau khi verify data.

### High — Build/publish/deploy artifact không rõ immutable identity

**Vấn đề:** Pipeline dùng `latest` cho release và build/publish trong cùng flow mà không thể hiện immutable artifact promotion.

**Tại sao xảy ra:** Release identity không gắn rõ commit/build/package checksum/version.

**Ảnh hưởng production:** Khó chứng minh binary nào đang chạy và rollback đúng artifact nào.

**Cách sửa:** Build/test/package một lần, gắn immutable version, promote cùng artifact qua environments. Octopus release phải tham chiếu version cụ thể, không `latest` trong production deployment decision.

### Medium — Không thấy pre-deployment compatibility validation

**Vấn đề:** Pipeline chạy migration production mà không thể hiện test schema compatibility giữa N và N-1 application versions.

**Tại sao xảy ra:** Test strategy tập trung compile/deploy thay vì mixed-version contract.

**Ảnh hưởng production:** Breaking schema change chỉ lộ khi rollout thật.

**Cách sửa:** Integration test application N-1 với expanded schema và application N với pre/post-backfill schema; validate migration trên production-like data volume.

### Medium — Không có explicit migration concurrency/ownership control

**Vấn đề:** Flow không cho thấy guarantee chỉ một deployment actor chạy migration cho một release.

**Tại sao xảy ra:** Khi pipelines/retries/deployment workers overlap, migration ownership có thể mơ hồ.

**Ảnh hưởng production:** Concurrent migration attempts, lock contention hoặc confusing failure state.

**Cách sửa:** Có một controlled migration step với deployment lock/ownership và auditable schema version. Không chạy startup migration từ mọi web instance.

### Medium — Không có health gate/automatic halt theo rollout telemetry

**Vấn đề:** Deploy step không thể hiện gate dựa trên health/error rate sau từng phase.

**Tại sao xảy ra:** Pipeline coi deployment command success là service success.

**Ảnh hưởng production:** Regression có thể tiếp tục lan sang nhiều instances.

**Cách sửa:** Canary/rolling health gates phù hợp platform; verify readiness, error rate, latency và dependency failures trước khi tiếp tục rollout.

    run: ./deploy/verify-production-health.sh ${IMMUTABLE_VERSION}
```

Contract migration `DROP COLUMN Name` không nằm trong release này. Nó là release sau, chỉ chạy khi telemetry/repository search/schema usage analysis xác nhận không còn old application version, report/query/job nào dùng `Name`, và rollback policy không còn cần N-1 code phụ thuộc column đó.

Migration expand có thể chỉ thêm nullable/new column trước, tùy domain constraint. Sau backfill và application transition mới enforce `NOT NULL` nếu requirement cần. Exact SQL/locking strategy phải được kiểm chứng trên database engine và production-like volume.

## Giải thích thiết kế sau khi sửa

Expand/contract biến schema evolution thành compatibility protocol. Trong rolling deployment, cả old và new code phải cùng hoạt động với expanded schema. Destructive change bị trì hoãn tới khi dependency graph cho phép.

Build-once/promote-many với immutable version làm artifact traceable. Database migration có ownership riêng, audit riêng và không chạy từ mỗi web instance. Backfill được tách để có thể throttle/resume thay vì giữ deployment hostage bởi một transaction lớn.

Không mặc định cần blue/green, Kubernetes hay microservices. Nếu Octopus rolling deployment hiện tại đáp ứng availability requirement, cải thiện compatibility và release discipline có thể đủ.

## Trade-offs

- Expand/contract cần nhiều release và temporary duplicate schema/data.
- Dual-read/dual-write nếu dùng có complexity và phải có exit plan.
- Batched backfill kéo dài thời gian transition nhưng giảm blast radius.
- Health gates làm deployment chậm hơn nhưng giới hạn regression propagation.
- Immutable artifact/release governance cần CI/CD discipline và storage retention.
- Giữ old column lâu hơn có technical debt tạm thời nhưng đổi lại rollback safety.

## Cách kiểm thử

1. **Compatibility integration test:** application N-1 chạy trên expanded schema và application N chạy trong cùng transition window.
2. **Migration test:** restore production-like database snapshot đã anonymize, chạy expand/backfill và đo duration, locks, log growth.
3. **Failure-path test:** dừng backfill giữa chừng rồi resume; không duplicate/corrupt data.
4. **Partial rollout test:** fail deployment sau 3/8 instances; mixed versions vẫn phục vụ đúng và operator có safe recovery path.
5. **Rollback validation:** rollback application N về N-1 trước contract migration; service vẫn hoạt động và schema không cần destructive reverse migration.

## Quan sát trong production

Ghi audit cho immutable application version, migration version, migration start/end/result và deployment actor. Application Insights/Azure Monitor cần dashboard theo version cho request count, p95/p99, 5xx và SQL dependency failures. Database monitoring cần lock waits, blocking, CPU/IO, transaction log growth và backfill progress.

Trong rollout, gate nên so sánh new-version error/latency với baseline và dừng propagation khi vượt threshold đã định. Octopus/CI logs phải tham chiếu release version cụ thể nhưng không chứa credentials.

## Câu hỏi phỏng vấn mở rộng

1. Nếu `Products` có 500 triệu rows và backfill cần nhiều giờ, bạn sẽ throttle/checkpoint/verify như thế nào?
2. Khi nào một backward-incompatible migration có thể chấp nhận được?
3. Nếu một legacy reporting job ngoài repository vẫn đọc `Name`, bạn sẽ phát hiện và quản lý dependency đó trước contract phase ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cache correctness bắt đầu từ data identity và isolation, không phải hit ratio. Với CMS/content systems, market/language/context phải được xem như một phần của cache contract; multi-instance freshness và publish invalidation cần được đánh giá theo business SLO.

Database migration trong rolling deployment là compatibility problem. Application rollback không tự rollback persistent schema; destructive changes cần được tách khỏi expand/backfill/application transition để mixed versions và rollback window vẫn an toàn.

## Mẫu tư duy cần nhớ

- **Correctness before cache performance:** key phải biểu diễn đầy đủ identity của dữ liệu.
- **Measure before adding distributed cache:** local cache có thể đủ nếu freshness/isolation contract cho phép.
- **Design schema changes for mixed versions:** expand trước, contract sau.
- **Treat persistent state differently from application artifacts:** package rollback không phải database rollback.
- **Test the failure window:** concurrent miss, partial rollout, migration interruption và dependency failure.
