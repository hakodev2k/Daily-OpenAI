# Câu 1 — EF Core ExecuteUpdate và Change Tracker: vì sao dữ liệu vừa sửa lại bị ghi đè?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18–22 phút  
**Kỹ năng được đánh giá:** EF Core, Change Tracker, SQL update, optimistic concurrency, transaction, debugging.

## Bối cảnh

Một API ASP.NET Core dùng EF Core và PostgreSQL cập nhật trạng thái xử lý đơn hàng. Để giảm thời gian xử lý batch, team thay vòng lặp entity bằng `ExecuteUpdateAsync`. Một request khác vẫn tải entity bằng `SingleAsync`, sửa `Note` rồi gọi `SaveChangesAsync`. QA phát hiện trạng thái đôi khi quay về giá trị cũ; hiện chưa rõ mapping, SQL được phát ra, hay có `rowversion`/concurrency token. Hệ thống xử lý khoảng 100.000 đơn/ngày; sai trạng thái gây gửi thông báo nhầm.

Ví dụ hai đường ghi (giản lược):

```csharp
var order = await db.Orders.SingleAsync(x => x.Id == id, ct);
await db.Orders.Where(x => x.Id == id)
    .ExecuteUpdateAsync(s => s.SetProperty(x => x.Status, "Shipped"), ct);
order.Note = "Customer notified";
await db.SaveChangesAsync(ct);
```

## Câu hỏi chính

Hãy giải thích chính xác điều gì xảy ra trong EF Core và database ở từng bước; khi nào `Status` có thể bị ghi đè hoặc không, cách xác minh, và đề xuất cơ chế cập nhật an toàn khi có nhiều request đồng thời.

## Câu hỏi làm rõ nên cân nhắc

1. `Status` có được đánh dấu modified không, có dùng `Update(order)` hay mapper ghi toàn bộ thuộc tính?
2. Có concurrency token, trigger hoặc interceptor nào không?
3. Hai thao tác có nằm trong cùng transaction và isolation level nào?
4. Các request khác có cập nhật cùng bản ghi, có business invariant chuyển trạng thái không?
5. SQL thực tế và số dòng affected đã được ghi nhận chưa?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt trạng thái trong database và snapshot của entity đang tracked.

### Gợi ý 2

Xem cột nào thật sự xuất hiện trong `UPDATE` do `SaveChangesAsync` phát ra.

### Gợi ý 3

`ExecuteUpdateAsync` không đồng bộ Change Tracker; kết quả còn phụ thuộc cách đánh dấu property modified và cơ chế concurrency.

## Cấu trúc trả lời đề xuất

1. Xác định trạng thái entity ban đầu và business invariant.
2. Mô tả tracking, original values, modified properties.
3. Phân tích SQL của hai đường ghi và tình huống concurrent writer.
4. Thu thập SQL/trace để phân biệt giả thuyết.
5. Đề xuất atomic conditional update, concurrency và xử lý conflict.
6. Thiết kế tests cùng metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `ExecuteUpdateAsync` chạy SQL trực tiếp, không cập nhật tracked instance và không tự gọi `SaveChanges`.
- Với entity tracked bình thường, chỉ sửa `Note` thì `SaveChanges` thường chỉ update `Note`; không được khẳng định chắc chắn `Status` bị ghi đè.
- `Update(order)`, mapper hoặc đánh dấu toàn entity modified có thể ghi lại `Status` cũ.
- Conditional update và kiểm tra affected rows để bảo vệ chuyển trạng thái.

### Điểm cộng

- Đề cập optimistic concurrency token và việc `ExecuteUpdate` cần tự đưa token vào predicate.
- Phân biệt stale read, lost update, invalid state transition, và side effect gửi thông báo.

### Senior+

- Thiết kế state transition có điều kiện, audit/outbox, xử lý retry và concurrency conflict theo nghiệp vụ.

## Hướng giải quyết tham khảo

**Giả định:** EF Core hỗ trợ `ExecuteUpdateAsync`; chưa có thông tin mapping concurrency. Sau `SingleAsync`, entity tracked giữ `Status` cũ. `ExecuteUpdateAsync` phát một `UPDATE` trực tiếp tới DB; bản tracked không tự được refresh. Khi chỉ `order.Note` thay đổi, change detection thường tạo SQL chỉ cập nhật `Note`. Vì vậy kết luận “`SaveChanges` chắc chắn ghi đè `Status`” là sai. Nếu dùng `db.Update(order)`, gán lại toàn bộ DTO hoặc `Entry(order).State = Modified`, SQL có thể ghi `Status` cũ và gây lost update. Nếu hai request cùng thay `Status`, dù không có mapper, business transition vẫn có race.

**Xác minh:** bật EF Core command logging ở môi trường an toàn, xem SQL parameters đã redacted, `ChangeTracker.DebugView`, trạng thái từng property và audit log; tái hiện bằng hai `DbContext` riêng và barrier điều phối concurrency. Không log PII hoặc full payload production. Kiểm tra trigger, interceptor, transaction và database logs trước khi kết luận.

**Thiết kế đề xuất:** tránh pha trộn tracked entity và set-based write cho cùng aggregate trong một unit of work nếu không chủ động reload. Với transition `Pending → Shipped`, dùng:

```csharp
var changed = await db.Orders
    .Where(x => x.Id == id && x.Status == "Pending")
    .ExecuteUpdateAsync(
        s => s.SetProperty(x => x.Status, "Shipped"),
        ct);

if (changed != 1)
    return Results.Conflict(new { message = "Order state changed" });
```

Predicate là compare-and-swap trên trạng thái, không phải optimistic concurrency đầy đủ nếu nhiều field có invariant liên quan. Nếu dùng concurrency token, đưa token kỳ vọng vào `Where` và kiểm tra affected rows; `ExecuteUpdate` không tự thực hiện concurrency check của `SaveChanges`. Nếu cần cập nhật nhiều bảng và ghi outbox, bao các thao tác trong transaction phù hợp; đồng bộ side effect qua outbox sau commit. Khi cần entity tracked mới nhất, `ReloadAsync` hoặc dùng context mới, nhưng reload không thay thế concurrency control. Lựa chọn transaction/isolation phụ thuộc yêu cầu invariant; Serializable có chi phí contention và cần retry có kiểm soát.

**Kiểm thử:** test integration PostgreSQL với hai contexts, case chỉ Note modified, case full entity modified, case concurrent state transitions; kiểm tra exactly-one successful transition, affected rows và outbox. **Theo dõi:** conflict rate, số lần transition bất hợp lệ, SQL update duration, deadlock/retry và độ trễ notification.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không kết luận ngay `SaveChanges` ghi đè `Status`. `ExecuteUpdateAsync` bypass Change Tracker, nên object tracked vẫn giữ giá trị cũ, nhưng EF Core thường chỉ cập nhật property được đánh dấu modified. Tôi sẽ kiểm tra SQL và entity state, nhất là mapper hoặc `Update(order)`. Dù không ghi đè trực tiếp, hai writer vẫn có thể vi phạm transition nghiệp vụ. Tôi ưu tiên atomic update với predicate trạng thái hoặc version, kiểm tra affected rows, xử lý conflict rõ ràng. Nếu cập nhật cần phát event, tôi sẽ dùng transaction cùng outbox; kiểm thử hai DbContext chạy đồng thời và theo dõi conflict rate. Cách sửa cuối cùng tùy invariant và tần suất contention.”

## Câu hỏi đào sâu

1. Nếu thêm `xmin` hoặc concurrency token thì `ExecuteUpdateAsync` có tự kiểm tra token không?
2. Khi nào nên dùng tracked aggregate thay vì set-based update?
3. Nếu 1% update bị conflict trong giờ cao điểm, retry tự động có luôn đúng không?

## Lỗi trả lời thường gặp

- Khẳng định mọi `SaveChanges` sẽ ghi toàn bộ cột.
- Nghĩ `ExecuteUpdate` tự cập nhật entity tracked.
- Dùng transaction mà không kiểm tra điều kiện chuyển trạng thái.
- Retry mọi conflict mà không xét business invariant.
- Chỉ unit test với InMemory provider, không kiểm tra SQL thực.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ assumptions và invariant | 1.5 |
| Giải thích tracking/SQL chính xác | 2.5 |
| Phân biệt các giả thuyết và cách xác minh | 2 |
| Concurrency control và trade-offs | 2 |
| Tests, observability, diễn đạt | 2 |

# Câu 2 — Cosmos DB RU tăng đột biến và 429 chỉ xảy ra với một nhóm khách hàng

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Cosmos DB partitioning, production triage, Azure Monitor, query diagnostics, resilience.

## Bối cảnh

Một hệ thống quản lý lịch hẹn lưu document vào Azure Cosmos DB for NoSQL. Sau khi triển khai màn hình tìm lịch sử theo tổ chức, p95 API tăng từ khoảng 180 ms lên 3.5 giây (số liệu giả định của tình huống). Một số tổ chức lớn nhận 429, tổ chức nhỏ ít bị ảnh hưởng. CPU App Service thấp, không có thay đổi rõ ràng ở tổng số request. Team muốn tăng RU/s ngay. Chưa biết partition key, query plan, RU distribution, indexing policy hay SDK retry.

## Câu hỏi chính

Bạn là người trực incident: hãy trình bày trình tự ổn định hệ thống, bằng chứng cần lấy để phân biệt nguyên nhân, cách khắc phục ngắn hạn và phương án thay đổi lâu dài mà không mặc định “tăng RU/s”.

## Câu hỏi làm rõ nên cân nhắc

1. Partition key hiện tại là gì, các tenant có phân bố đều không?
2. 429 xuất hiện ở operation nào, tại partition nào, có retry-after và diagnostics không?
3. Query mới có filter partition key, `ORDER BY`, cross-partition fan-out, continuation token không?
4. Autoscale/manual throughput và mức tiêu thụ RU theo partition ra sao?
5. SLO, tenant quan trọng, khả năng rollback feature và giới hạn chi phí là gì?

## Gợi ý tư duy

### Gợi ý 1

Tổng RU/s chưa mô tả đầy đủ mức nghẽn của từng partition.

### Gợi ý 2

Xem RU charge, partition-key distribution, 429 và SDK diagnostics theo operation.

### Gợi ý 3

Phân biệt hot logical partition, expensive cross-partition query, index behavior và retry amplification.

## Cấu trúc trả lời đề xuất

1. Xác định ảnh hưởng theo tenant/endpoint và thời điểm.
2. Giảm tải, rollback hoặc tắt query mới có điều kiện.
3. Thu thập request charge, throttling, partition distribution, traces.
4. Đặt nhiều giả thuyết, kiểm tra từng giả thuyết.
5. Chọn hotfix và xác nhận SLO.
6. Thiết kế dữ liệu/index/query dài hạn.
7. Thử nghiệm và theo dõi sau release.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Xác định 429 là throttling, nhưng không mặc định mọi 429 là incident nghiêm trọng nếu SDK retry hấp thụ trong SLO.
- Xem per-partition distribution và RU per query thay vì chỉ CPU App Service.
- Stabilize trước: feature flag, rollback query, giới hạn concurrency hoặc traffic, ưu tiên tenant bị ảnh hưởng.
- Đo latency và RU charge trước/sau thay đổi.

### Điểm cộng

- Hiểu cross-partition query, index, pagination và retry behavior.
- Tách capacity issue khỏi skew/hot partition; không khẳng định có một root cause duy nhất.

### Senior+

- Đề xuất partition-key redesign/tenant sharding có kế hoạch migration, dual read/write được kiểm soát và consistency validation.

## Hướng giải quyết tham khảo

**Impact:** lập dashboard theo endpoint, tenant, request rate, 429, p95/p99 và số booking bị lỗi. **Stabilize:** nếu tương quan chặt với màn hình mới, disable query hoặc rollback bằng feature flag; đặt bounded concurrency, pagination và request timeout; ưu tiên read path thiết yếu. Có thể tăng throughput tạm thời nếu evidence cho thấy thiếu capacity tổng thể và ngân sách cho phép, nhưng tăng tổng RU không đảm bảo chữa hot partition.

**Bằng chứng:** lấy Azure Monitor metrics về normalized RU consumption, throttled requests, partition-key range khi khả dụng; Cosmos SDK diagnostics gồm request charge, status/substatus, retry count, elapsed time, activity ID; query text đã loại PII, index metrics/plan khi phù hợp. So sánh trước/sau deployment, tenant lớn/nhỏ, point reads/query, query có partition key/không, số kết quả, pagination. Không suy diễn từ CPU App Service thấp rằng DB không nghẽn.

**Giả thuyết cạnh tranh:** (A) query lịch sử thiếu partition-key filter gây fan-out; (B) tenant lớn là hot partition; (C) filter/sort mới làm RU/query tăng vì index không phù hợp; (D) SDK retry và nhiều request đồng thời khuếch đại tail latency; (E) một background job cùng partition tạo contention. Thử với replay workload đã ẩn dữ liệu, phân tách RU per operation và partition, so sánh query shapes. Chỉ chốt root cause sau khi một phép thử hoặc telemetry loại trừ các giả thuyết còn lại.

**Ngắn hạn:** thêm tenant scope bắt buộc, giới hạn page size, dùng continuation token, giới hạn concurrency, kiểm soát retry/backoff và cancellation; cân nhắc index thay đổi sau khi đo tác động write RU. **Dài hạn:** nếu workload chủ yếu theo tenant và tenant size không vượt giới hạn partition thì tenantId có thể phù hợp; nếu tenant rất lớn hoặc hot, xem xét synthetic partition key và điều chỉnh read/query pattern. Thay partition key thường cần container mới và migration; thiết kế dual-write, backfill, kiểm tra consistency, cutover, rollback và chi phí trước khi làm. Nếu yêu cầu truy vấn toàn hệ thống, cân nhắc read model riêng hoặc search index, chấp nhận eventual consistency có khai báo.

**Verification:** load test tenant skew, 429/retry test, so sánh RU/query, p95/p99 và chi phí; release canary theo tenant. **Monitoring:** alert theo SLO user-visible, throttling kéo dài, RU utilization/skew, query charge và retry count; correlation giữa App Insights dependency và Cosmos activity ID.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác định khách hàng và endpoint bị ảnh hưởng, sau đó giảm tải hoặc rollback màn hình mới để bảo vệ thao tác booking. 429 cho thấy Cosmos đang throttle request, nhưng tôi cần biết tỷ lệ retry có gây lỗi thực tế hay không. Tôi sẽ lấy request charge, partition distribution, diagnostics, latency theo tenant, so sánh query cũ và mới. Các giả thuyết gồm cross-partition scan, hot partition, index không phù hợp hoặc retry amplification. Tăng RU có thể là mitigation tạm thời nhưng không phải kết luận. Sau khi xác minh, tôi tối ưu query và pagination; nếu partition key sai với workload thì lập kế hoạch migration có canary và rollback. Thành công được đo bằng SLO, RU/query và tỷ lệ throttling, không phải chỉ hết alert.”

## Câu hỏi đào sâu

1. Vì sao tổng RU utilization còn dư nhưng một số request vẫn bị 429?
2. Khi nào synthetic partition key làm read path phức tạp hơn và không đáng dùng?
3. Nếu query cần tìm kiếm xuyên tenant, bạn chọn Cosmos query, read model SQL hay Elasticsearch dựa trên tiêu chí nào?

## Lỗi trả lời thường gặp

- Tăng RU/s trước khi xác định partition/query.
- Xem 429 như lỗi ứng dụng không thể retry hoặc mặc định retry vô hạn.
- Chỉ theo dõi average latency, bỏ qua p95/p99 và tenant skew.
- Đổi partition key trực tiếp như một thay đổi schema đơn giản.
- Thiếu rollback, cost control và verification sau hotfix.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact và stabilization | 2 |
| Evidence, diagnostics, competing hypotheses | 3 |
| Cơ chế partition/query/RU chính xác | 2 |
| Mitigation, trade-offs và migration | 2 |
| Testing, monitoring và communication | 1 |

# Câu 3 — Hiện đại hóa cổng nhân sự ASP.NET MVC + jQuery sang Vue và ASP.NET Core theo từng bước

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** legacy modernization, frontend/backend boundaries, authentication, CI/CD, data consistency, rollout.

## Bối cảnh

Một portal nội bộ dùng ASP.NET MVC trên .NET Framework 4.5, jQuery và IIS. Chức năng gồm yêu cầu nghỉ phép, phê duyệt nhiều cấp, lịch sử thay đổi và xuất báo cáo. Team muốn giao diện Vue.js và backend ASP.NET Core, nhưng hệ thống phải hoạt động liên tục trong giờ hành chính. Có 600 người dùng, khoảng 30 người duyệt đồng thời; số liệu là giả định cho bài toán. Không được mất lịch sử phê duyệt; ngân sách hạn chế; chưa rõ authentication, shared database, tích hợp báo cáo và thời gian bảo trì cho phép.

## Câu hỏi chính

Hãy đề xuất một lộ trình migration khả thi theo từng phần, nêu boundaries, API, data ownership, authentication, consistency, deployment/rollback và tiêu chí quyết định giữa incremental modernization và rewrite.

## Câu hỏi làm rõ nên cân nhắc

1. Hiện portal dùng Forms Authentication, Windows Authentication hay OIDC/Entra ID?
2. Có module nào phụ thuộc trực tiếp `System.Web`, Session, file system hoặc third-party assemblies?
3. Business rules approval nằm ở controller, stored procedure hay service layer?
4. RTO/RPO, cửa sổ deploy, audit retention và yêu cầu pháp lý thế nào?
5. Có thể duy trì hai giao diện trong giai đoạn chuyển đổi và đo tỷ lệ lỗi theo module không?

## Gợi ý tư duy

### Gợi ý 1

Phân chia migration theo business capability thay vì chỉ thay framework hoặc thư mục.

### Gợi ý 2

Chú ý auth/session, shared data writes, backward compatibility và khả năng rollback.

### Gợi ý 3

Strangler-style routing, API contract tests và expand–migrate–contract có thể giảm rủi ro, nhưng cũng làm tăng complexity tạm thời.

## Cấu trúc trả lời đề xuất

1. Khảo sát dependency và risk.
2. Đặt mục tiêu đo được và ưu tiên module.
3. Đề xuất target architecture tối giản.
4. Thiết kế API, ownership, auth và migration data.
5. Lập release sequence/canary/rollback.
6. Đánh giá chi phí và điểm dừng.
7. Kiểm thử, telemetry và governance.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite toàn bộ hoặc Microservices.
- Bảo vệ approval invariant và audit log.
- Đề xuất incremental rollout, API contract và rollback.
- Giải quyết auth/session/cookie, CORS/CSRF tùy topology.

### Điểm cộng

- Module boundary rõ, migration database có backward compatibility.
- Phân biệt strangler routing với hai ứng dụng cùng ghi bảng và nguy cơ split ownership.

### Senior+

- Có release gates, feature flags, anti-corruption layer, migration observability và kế hoạch loại bỏ legacy.

## Hướng giải quyết tham khảo

**Giả định:** portal hiện vẫn có thể bảo trì, database SQL Server dùng chung và không bắt buộc thay thế toàn bộ trong một quý. Trước hết inventory route, package, `System.Web` dependencies, IIS config, auth, stored procedures, integrations và browser behavior. Đo baseline lỗi, thời gian thao tác approval, p95, deployment rollback time, tỷ lệ test coverage theo critical flows.

**Target:** ưu tiên modular monolith ASP.NET Core với API rõ theo LeaveRequest, Approval, Audit và Reporting; Vue frontend theo module. Có thể đặt reverse proxy định tuyến `/legacy/*` và `/app/*`, nhưng cần xác minh cookie/session và SameSite/CSRF trước khi chọn same-origin. Nếu Entra/OIDC sẵn có, chuẩn hóa auth qua identity provider; backend kiểm tra authorization theo request, approver, stage, tenant chứ không tin role/UI flag. Không chuyển access token nhạy cảm vào URL hoặc log.

**API và data model:** `POST /api/leave-requests`, `POST /api/leave-requests/{id}/decisions`, `GET /api/leave-requests/{id}/history`; quyết định phê duyệt cần idempotency key hoặc unique decision constraint, expected version và atomic transition. Audit lưu actor, action, timestamp, previous/new state và correlation ID; bảo vệ bất biến không phê duyệt trùng stage. Trong thời gian shared DB, chỉ một module là owner ghi cho mỗi business capability; nếu hai app cùng ghi, phải định nghĩa compatibility contract, không dựa vào “cùng schema nên an toàn”. Schema migration theo expand–migrate–contract, tránh drop/rename cột trước khi mọi consumer tương thích. Report read path có thể tạm dùng database cũ qua adapter với giới hạn rõ.

**Release:** (1) characterization tests cho approval; (2) tách business logic khỏi MVC controllers khi có thể; (3) dựng ASP.NET Core API và auth; (4) chuyển một module ít rủi ro sang Vue; (5) canary nhóm nhân viên, quan sát telemetry; (6) chuyển approval có feature flag và shadow validation chỉ đọc, tuyệt đối không double-submit decision; (7) dọn legacy khi không còn traffic. Rollback phải khả thi cả code và schema; dữ liệu được tạo ở phiên bản mới phải vẫn đọc được bởi phiên bản cũ hoặc có rollback plan dữ liệu. Nếu auth/session integration không thể an toàn trong thời gian coexist, có thể chọn migration theo route lớn hơn hoặc cutover có bảo trì có kiểm soát.

**Trade-offs:** incremental migration giảm blast radius nhưng kéo dài chi phí vận hành hai stack; rewrite đơn giản hóa target design nhưng tăng risk và mất behavior ngầm. Kubernetes không cần thiết cho 600 users nếu IIS/App Service đáp ứng SLO; chọn hosting theo operational capability, compliance và cost. Vue SPA không tự bảo đảm SEO hoặc performance; portal nội bộ ưu tiên accessibility, bundle size và API latency.

**Testing:** contract tests giữa Vue và API; integration tests concurrency approval, CSRF/auth, backward-compatible schema; Playwright E2E cho submit–approve–reject–audit; deployment smoke test và rollback drill. **Telemetry:** structured logs có correlation ID, trace qua proxy/API/DB, error rate theo route/version, approval conflict, session failure, browser errors, migration progress dashboard.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không rewrite ngay vì workflow phê duyệt và audit có nhiều behavior ngầm. Tôi bắt đầu bằng inventory dependency và characterization tests, sau đó chọn một module nhỏ để triển khai Vue cùng ASP.NET Core API. Tôi ưu tiên modular monolith, phân ownership của từng nghiệp vụ và dùng reverse proxy để coexist nếu auth cho phép. API phê duyệt phải enforce authorization, idempotency và concurrency ở server. Schema migration cần backward-compatible để rollback code không làm hỏng dữ liệu. Tôi triển khai canary, feature flag, Playwright E2E và theo dõi lỗi theo module. Chỉ khi evidence cho thấy legacy không thể tách an toàn hoặc chi phí coexist quá cao, tôi mới cân nhắc cutover lớn hơn.”

3. Trong điều kiện deadline ba tháng, có trường hợp nào rewrite một module hoàn toàn hợp lý hơn strangler không?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- EF Core set-based writes và tracked entities là hai cơ chế khác nhau; kiểm tra SQL thực tế trước khi quy trách nhiệm cho Change Tracker.
- Cosmos DB troubleshooting cần nhìn theo request charge, query shape và phân bố partition, không chỉ tổng throughput.
- Legacy modernization là bài toán quản lý invariant, ownership, compatibility và release risk, không chỉ đổi ngôn ngữ hoặc UI framework.

## Mẫu tư duy cần nhớ

1. **Phân biệt cơ chế với giả thuyết:** quan sát SQL, traces và state trước khi kết luận.
2. **Stabilize trước, tối ưu sau:** bảo vệ SLO rồi mới điều tra sâu.
3. **Concurrency đi cùng business invariant:** kiểm tra affected rows, version và idempotency.
4. **Measure before optimize:** tối ưu theo RU/query, p95/p99 và tác động người dùng.
5. **Migration phải có rollback dữ liệu:** compatibility quan trọng ngang deployment.
