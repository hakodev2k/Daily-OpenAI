# Code Review Challenge 1 — Giữ chỗ tồn kho bị oversell khi nhiều request chạy đồng thời

**Chủ đề:** Concurrency & race condition, EF Core transaction handling, correctness, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống bán vé nội bộ có API giữ chỗ trong 5 phút trước khi người dùng thanh toán. Mỗi SKU có số lượng tồn kho giới hạn. API hiện chạy trên nhiều instance ASP.NET Core phía sau load balancer.

Trong giờ cao điểm, cùng một SKU có thể nhận hàng trăm request giữ chỗ trong vài giây. Production xuất hiện các triệu chứng:

- Một số SKU có `AvailableQuantity` âm.
- Hai request đồng thời đôi khi đều nhận kết quả thành công mặc dù chỉ còn 1 đơn vị.
- Khi database latency tăng, số lần lỗi `DbUpdateException` và timeout tăng mạnh.
- Team thêm `lock` trong service nhưng oversell vẫn xảy ra sau khi scale lên nhiều instance.
- Có request bị client huỷ nhưng database vẫn tiếp tục xử lý trong một số trường hợp.

Yêu cầu business quan trọng: không được bán vượt tồn kho. Team không muốn serializable transaction cho toàn bộ hệ thống nếu không cần thiết vì lo ảnh hưởng throughput.

## Đoạn code cần review

```csharp
public sealed class InventoryService
{
    private static readonly object Gate = new();

    private readonly AppDbContext _db;
    private readonly ILogger<InventoryService> _logger;

    public InventoryService(
        AppDbContext db,
        ILogger<InventoryService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<ReservationResult> ReserveAsync(
        Guid skuId,
        int quantity,
        Guid userId,
        CancellationToken cancellationToken)
    {
        InventoryItem? item;

        lock (Gate)
        {
            item = _db.InventoryItems
                .FirstOrDefault(x => x.SkuId == skuId);

            if (item is null)
                return ReservationResult.NotFound();

            if (item.AvailableQuantity < quantity)
                return ReservationResult.OutOfStock();

            item.AvailableQuantity -= quantity;
        }

        var reservation = new InventoryReservation
        {
            Id = Guid.NewGuid(),
            SkuId = skuId,
            UserId = userId,
            Quantity = quantity,
            ExpiresAtUtc = DateTime.UtcNow.AddMinutes(5)
        };

        _db.InventoryReservations.Add(reservation);

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Reserved {Quantity} units of {SkuId} for {UserId}. Remaining={Remaining}",
            quantity,
            skuId,
            userId,
            item.AvailableQuantity);

        return ReservationResult.Success(reservation.Id);
    }
}
```

## Kết quả code review tham khảo

### 1. `read -> check -> decrement -> SaveChanges` tạo race condition dẫn đến oversell

**Problem:** Code đọc tồn kho, kiểm tra điều kiện và cập nhật entity ở các bước tách biệt.

**Why it happens:** Hai request ở hai transaction/process khác nhau có thể cùng đọc cùng một giá trị tồn kho trước khi một trong hai commit. Mỗi request đều kết luận rằng còn hàng và đều thực hiện update.

**Production impact:** Đây là lỗi correctness nghiêm trọng: hệ thống có thể bán vượt tồn kho, tạo reservation không thể fulfil và gây hậu quả business trực tiếp.

**Severity:** Critical

**Recommended fix:** Chuyển invariant `AvailableQuantity >= requestedQuantity` xuống database. Ví dụ dùng một lệnh update có điều kiện:

```sql
UPDATE InventoryItems
SET AvailableQuantity = AvailableQuantity - @quantity
WHERE SkuId = @skuId
  AND AvailableQuantity >= @quantity;
```

Sau đó kiểm tra affected rows. Nếu bằng 0 thì không còn đủ tồn kho hoặc SKU không tồn tại. Với EF Core có thể thực hiện qua SQL parameterized hoặc API bulk-update phù hợp với phiên bản đang dùng.

Một lựa chọn khác là optimistic concurrency bằng concurrency token và retry có giới hạn. Cách nào phù hợp phụ thuộc contention, database và mô hình domain.

### 2. `lock (Gate)` chỉ đồng bộ trong một process

**Problem:** Service dùng static process-local lock như thể nó là distributed lock.

**Why it happens:** Static state chỉ được chia sẻ giữa threads trong cùng process. Mỗi application instance/container có một `Gate` riêng.

**Production impact:** Khi scale-out, request đi vào các instance khác nhau hoàn toàn không bị serialize. Team có thể có cảm giác sai rằng race condition đã được xử lý.

**Severity:** High

**Recommended fix:** Đặt concurrency guarantee ở database nếu invariant thuộc database. Chỉ cân nhắc distributed lock khi thực sự cần serialize workflow rộng hơn và đã đánh giá failure semantics, lease expiry, fencing/token ownership.

### 3. Query synchronous bên trong `lock` chặn thread và kéo dài critical section

**Problem:** `FirstOrDefault` thực hiện blocking database I/O trong monitor lock.

**Why it happens:** Query EF Core tới database là I/O nhưng code dùng synchronous API trong critical section.

**Production impact:** Dưới latency cao, thread giữ lock lâu; các request khác trong cùng process bị block. Thread pool pressure và tail latency có thể tăng mạnh dù lock vẫn không giải quyết concurrency cross-instance.

**Severity:** High

**Recommended fix:** Bỏ process-local lock khỏi invariant này. Dùng async database operations và cơ chế concurrency ở database.

### 4. `CancellationToken` bị bỏ qua trong database calls

**Problem:** Method nhận `cancellationToken` nhưng không truyền vào query/`SaveChangesAsync`.

**Why it happens:** Signature có cancellation nhưng implementation không propagate.

**Production impact:** Client disconnect hoặc upstream timeout nhưng database operation vẫn chạy. Khi tải cao, công việc vô ích tiếp tục giữ connection, CPU, locks và resource.

**Severity:** Medium

**Recommended fix:** Truyền token đến mọi async operation hỗ trợ cancellation, đồng thời phân biệt cancellation với lỗi hệ thống trong logging.

### 5. Không validate `quantity`

**Problem:** Không kiểm tra `quantity > 0` và giới hạn hợp lý.

**Why it happens:** Code tin rằng input phía caller luôn hợp lệ.

**Production impact:** `quantity = 0` tạo reservation vô nghĩa; `quantity < 0` có thể làm **tăng** tồn kho vì phép trừ số âm. Đây có thể trở thành lỗi business hoặc abuse vector.

**Severity:** High

**Recommended fix:** Validate tại application boundary và giữ invariant trong domain/service. Reject `quantity <= 0`; cân nhắc max quantity theo business rule.

### 6. Không có cơ chế xử lý concurrent update conflict rõ ràng

**Problem:** Code giả định `SaveChangesAsync` thành công là đủ nhưng không có chiến lược rõ ràng khi concurrent update, deadlock hoặc transient database failure xảy ra.

**Why it happens:** Workflow chưa mô hình hoá failure path của write operation.

**Production impact:** Request có thể trả 500 thay vì phản hồi business phù hợp; retry mù quáng có thể tạo thêm load hoặc duplicate reservation nếu logic sau này phát triển thêm side effect.

**Severity:** Medium

**Recommended fix:** Chỉ retry những lỗi thật sự transient, có giới hạn và jitter. Nếu dùng optimistic concurrency, xử lý conflict như một outcome expected và re-read/retry có giới hạn hoặc trả out-of-stock/conflict phù hợp.

### 7. Không có idempotency cho request từ client

**Problem:** Nếu client timeout sau khi server commit rồi gửi lại request, hệ thống có thể tạo reservation thứ hai.

**Why it happens:** API không có request identifier/idempotency key.

**Production impact:** Người dùng có thể giữ gấp đôi số lượng hoặc tạo nhiều reservation không mong muốn dù mỗi transaction riêng lẻ đều đúng.

**Severity:** Medium

**Recommended fix:** Với endpoint có khả năng retry từ mobile/web/network, cân nhắc `Idempotency-Key` hoặc business request id có unique constraint. Một key đã xử lý phải trả lại kết quả cũ thay vì thực hiện write lần nữa.

### 8. Timestamp hết hạn dùng trực tiếp `DateTime.UtcNow` làm việc test và consistency khó hơn

**Problem:** Clock được hard-code trong service.

**Why it happens:** Domain time phụ thuộc trực tiếp system clock.

**Production impact:** Không phải lỗi production nghiêm trọng, nhưng test expiry khó deterministic; logic time ở nhiều nơi dễ lệch.

**Severity:** Low

**Recommended fix:** Dùng abstraction về time như `TimeProvider` hoặc domain clock phù hợp với phiên bản .NET của dự án.

### 9. Log “Remaining” dựa trên tracked entity có thể không phản ánh giá trị authoritative cuối cùng dưới cạnh tranh

**Problem:** Log dùng `item.AvailableQuantity` trong memory làm số tồn kho cuối cùng.

**Why it happens:** Giá trị tracked trong request không nhất thiết là snapshot authoritative sau tất cả concurrent commits.

**Production impact:** Incident investigation có thể bị nhiễu vì log tạo cảm giác đây là tồn kho toàn cục sau commit.

**Severity:** Low

**Recommended fix:** Log delta, reservation id, SKU, quantity, outcome và row count/version. Nếu thực sự cần remaining authoritative, lấy nó từ database operation hoặc query riêng với mục đích rõ ràng.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng conditional update ở database để giữ invariant tại nơi có thể nhìn thấy mọi concurrent request. Cú pháp SQL cần được điều chỉnh theo database cụ thể; tham số phải luôn parameterized.

```csharp
public sealed class InventoryService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<InventoryService> _logger;

    public InventoryService(
        AppDbContext db,
        TimeProvider timeProvider,
        ILogger<InventoryService> logger)
    {
        _db = db;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    public async Task<ReservationResult> ReserveAsync(
        Guid skuId,
        int quantity,
        Guid userId,
        CancellationToken cancellationToken)
    {
        if (quantity <= 0)
            return ReservationResult.InvalidQuantity();

        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var affected = await _db.Database.ExecuteSqlInterpolatedAsync(
            $"""
            UPDATE InventoryItems
            SET AvailableQuantity = AvailableQuantity - {quantity}
            WHERE SkuId = {skuId}
              AND AvailableQuantity >= {quantity}
            """,
            cancellationToken);

        if (affected != 1)
        {
            await transaction.RollbackAsync(cancellationToken);
            return ReservationResult.OutOfStock();
        }

        var reservation = new InventoryReservation
        {
            Id = Guid.NewGuid(),
            SkuId = skuId,
            UserId = userId,
            Quantity = quantity,
            ExpiresAtUtc = _timeProvider.GetUtcNow().AddMinutes(5).UtcDateTime
        };

        _db.InventoryReservations.Add(reservation);
        await _db.SaveChangesAsync(cancellationToken);
        await transaction.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Inventory reservation succeeded. ReservationId={ReservationId} " +
            "SkuId={SkuId} UserId={UserId} Quantity={Quantity}",
            reservation.Id,
            skuId,
            userId,
            quantity);

        return ReservationResult.Success(reservation.Id);
    }
}
```

Điểm quan trọng của ví dụ không phải là “raw SQL luôn tốt hơn EF Core”, mà là invariant được thực thi bằng một write có điều kiện tại database. Nếu dự án dùng optimistic concurrency token, stored procedure hoặc database-specific locking strategy, implementation có thể khác.

## Trade-offs

- **Conditional atomic update** đơn giản và hiệu quả cho một invariant cục bộ trên một row, nhưng có thể cần database-specific SQL/API.
- **Optimistic concurrency token** giữ code gần domain model và phù hợp contention thấp; dưới contention cao có thể sinh nhiều conflict/retry.
- **Pessimistic locking / stronger isolation** có thể đơn giản hoá reasoning cho workflow phức tạp hơn nhưng làm tăng lock duration, deadlock risk và giảm throughput.
- **Distributed lock** không nên là lựa chọn mặc định khi database đã là source of truth. Nếu dùng, phải thiết kế lease expiry, ownership, process crash và split-brain semantics rất cẩn thận.
- Transaction nên nhỏ nhất có thể: không gọi external API hay thực hiện công việc chậm trong lúc giữ database transaction.

## Cách kiểm thử

1. **Concurrency test:** Khởi tạo tồn kho = 1, bắn 50 request song song quantity = 1; xác nhận đúng 1 request thành công và tồn kho không âm.
2. **Load test:** Nhiều SKU với distribution lệch, trong đó một số hot SKU bị contention cao; đo p95/p99 latency, deadlocks/conflicts, DB CPU và connection pool.
3. **Validation test:** `quantity = 0`, số âm và số vượt giới hạn phải bị reject mà không thay đổi database.
4. **Cancellation/failure-path test:** Huỷ request khi database đang chậm; xác nhận không tạo reservation nửa chừng và transaction được rollback.
5. **Idempotency test nếu hỗ trợ key:** Gửi cùng request key nhiều lần/đồng thời; chỉ một reservation được tạo và các lần sau nhận cùng kết quả.

## Quan sát trong production

- Log structured: `ReservationId`, `SkuId`, `Quantity`, outcome, conflict/out-of-stock reason, trace id.
- Metrics: reservation success/failure rate, out-of-stock rate, concurrency conflict rate, DB command duration, transaction duration.
- Alert khi `AvailableQuantity < 0`; đây nên được coi là invariant violation.
- Theo dõi deadlock, lock wait, slow queries và connection pool saturation tại database.
- Distributed trace từ API request tới database command; không log dữ liệu thanh toán hoặc token nhạy cảm.

# Code Review Challenge 2 — Webhook sender retry sai cách làm cạn connection và gửi duplicate

**Chủ đề:** HTTP client usage, async/cancellation, resource lifetime, error handling, retries, observability  
**Độ khó:** Senior

## Bối cảnh

Một ASP.NET Core service gửi webhook cho hệ thống đối tác khi đơn hàng thay đổi trạng thái. Mỗi webhook được đẩy vào một worker nội bộ rồi gọi HTTP tới URL đã được cấu hình trước cho từng partner.

Bình thường hệ thống gửi khoảng 20–50 webhook/giây, nhưng khi batch import hoặc recovery sau outage có thể tăng lên 500 webhook/giây. Đối tác đôi khi trả `429`, `500`, timeout hoặc đóng connection giữa chừng.

Production ghi nhận:

- Sau một đợt partner outage, worker có latency tăng mạnh và số connection outbound tăng bất thường.
- Có webhook được partner xử lý nhiều lần.
- Một số payload bị retry liên tục trong vài phút làm backlog tăng nhanh.
- Khi service shutdown/deploy, một phần task vẫn tiếp tục chạy hoặc log exception muộn.
- Ops khó xác định webhook nào đang retry lần thứ mấy và partner nào gây backlog.

Partner hỗ trợ một header idempotency riêng nếu caller cung cấp stable event id.

## Đoạn code cần review

```csharp
public sealed class WebhookSender
{
    private readonly ILogger<WebhookSender> _logger;

    public WebhookSender(ILogger<WebhookSender> logger)
    {
        _logger = logger;
    }

    public async Task SendAsync(
        string url,
        string json,
        Guid eventId,
        CancellationToken cancellationToken)
    {
        for (var attempt = 1; attempt <= 10; attempt++)
        {
            try
            {
                var client = new HttpClient();
                client.Timeout = TimeSpan.FromSeconds(60);

                var content = new StringContent(
                    json,
                    Encoding.UTF8,
                    "application/json");

                var response = await client.PostAsync(url, content);

                if (response.IsSuccessStatusCode)
                {
                    _logger.LogInformation(
                        "Webhook sent to {Url}: {Body}",
                        url,
                        json);
                    return;
                }

                var responseBody = await response.Content.ReadAsStringAsync();

                _logger.LogWarning(
                    "Webhook failed. Url={Url}, Status={Status}, Body={Body}",
                    url,
                    (int)response.StatusCode,
                    responseBody);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Webhook exception for {Url}", url);
            }

            await Task.Delay(TimeSpan.FromSeconds(1));
        }

        throw new InvalidOperationException("Webhook delivery failed after retries.");
    }
}
```

## Kết quả code review tham khảo

### 1. Tạo `HttpClient` mới cho từng attempt gây connection churn và có thể dẫn đến socket/port pressure

**Problem:** Mỗi retry tạo một `HttpClient` mới và không dispose rõ ràng.

**Why it happens:** Code coi `HttpClient` như một request-scoped wrapper thay vì client có handler/connection pool cần được quản lý đúng lifecycle.

**Production impact:** Dưới burst/retry storm, hệ thống tạo nhiều connection/handler không cần thiết, tăng handshake/DNS/TCP/TLS overhead và có thể gây outbound port/socket pressure.

**Severity:** High

**Recommended fix:** Dùng `IHttpClientFactory` hoặc `HttpClient` được quản lý/reuse phù hợp. Cấu hình timeout, handler lifetime, DNS refresh policy và limits ở nơi tập trung thay vì tạo client trong loop.

### 2. Không dispose `HttpResponseMessage`

**Problem:** `response` không được dispose.

**Why it happens:** Resource lifetime bị bỏ qua sau mỗi attempt.

**Production impact:** Response/content resources có thể được giữ lâu hơn cần thiết; trong high-throughput retry loop, resource pressure và connection reuse có thể xấu đi.

**Severity:** High

**Recommended fix:** `using var response = await ...` hoặc `using` phù hợp sau khi đọc/capture phần cần thiết.

### 3. Không truyền `CancellationToken` vào HTTP call

**Problem:** `PostAsync` không nhận token từ caller.

**Why it happens:** Method có token nhưng không propagate.

**Production impact:** Khi host shutdown, request bị huỷ hoặc job hết deadline, outbound request vẫn có thể chạy đến timeout. Deploy/shutdown kéo dài và task kết thúc muộn.

**Severity:** High

**Recommended fix:** Truyền `cancellationToken` vào `SendAsync/PostAsync`. Phân biệt cancellation do caller với timeout/network failure; không retry khi operation bị chủ động huỷ.

### 4. `Task.Delay` không hỗ trợ cancellation

**Problem:** Delay giữa retry luôn chờ đủ một giây.

**Why it happens:** Không truyền token.

**Production impact:** Worker shutdown chậm và backlog task linger lâu không cần thiết.

**Severity:** Medium

**Recommended fix:** `await Task.Delay(delay, cancellationToken)`.

### 5. Retry mọi lỗi với cùng policy là không đúng

**Problem:** Mọi non-success response và mọi exception đều retry tối đa 10 lần.

**Why it happens:** Retry policy không phân loại transient/permanent failure.

**Production impact:** `400`, `401`, `403`, malformed payload hoặc invalid URL có thể bị retry vô ích, làm backlog tăng và gây thêm tải cho partner. Một số exception do bug programming cũng bị nuốt rồi retry.

**Severity:** High

**Recommended fix:** Phân loại:

- `2xx`: success.
- `408`, `429`, selected `5xx`, network timeout/failure: có thể retry.
- Hầu hết `4xx` khác: thường permanent cho payload/config hiện tại, đưa sang failed/dead-letter workflow để điều tra.
- Cancellation do caller: không retry.

Policy cụ thể phải theo contract của partner.

### 6. Fixed one-second retry tạo retry storm

**Problem:** Tất cả attempt delay đúng 1 giây.

**Why it happens:** Không có exponential backoff/jitter hay server hint.

**Production impact:** Khi partner outage, hàng nghìn webhook có thể retry đồng nhịp, tạo thundering herd và làm partner khó hồi phục hơn.

**Severity:** High

**Recommended fix:** Exponential backoff có giới hạn + jitter. Với `429`/`503`, cân nhắc `Retry-After` khi contract cho phép. Có global/per-partner rate limit hoặc circuit-breaker nếu cần bảo vệ hệ thống.

### 7. Không dùng `eventId` để hỗ trợ idempotency

**Problem:** Partner có hỗ trợ idempotency header nhưng code bỏ qua `eventId`.

**Why it happens:** Delivery được coi như “retry POST là được” mà chưa xử lý ambiguous outcome.

**Production impact:** Partner có thể đã commit side effect nhưng response bị mất; sender retry và partner xử lý lần hai.

**Severity:** Critical

**Recommended fix:** Gửi stable event id/idempotency key theo contract của partner trong mọi retry của cùng event. Key phải không thay đổi giữa attempts. Sender cũng nên lưu trạng thái delivery để không tạo event mới cho cùng business event một cách vô tình.

### 8. Log toàn bộ request/response body có thể làm lộ dữ liệu nhạy cảm và tăng log volume

**Problem:** Success path log toàn bộ outgoing JSON; failure path log toàn bộ partner response.

**Why it happens:** Logging được dùng thay cho structured delivery telemetry.

**Production impact:** Payload có thể chứa PII/business data. Dưới burst, log volume và ingestion cost tăng mạnh.

**Severity:** Medium

**Recommended fix:** Log event id, partner id, attempt, status, duration, payload size, safe error code. Redact hoặc không log body mặc định; chỉ capture bounded diagnostic data khi thật sự cần.

### 9. Retry loop giữ request payload `string` và recreate content trên mỗi attempt mà không có policy về kích thước

**Problem:** Payload được materialize dưới dạng `string` và `StringContent` được tạo lại mỗi lần.

**Why it happens:** Implementation tối ưu cho sự đơn giản, chưa xét burst/backlog.

**Production impact:** Với payload lớn và nhiều retry đồng thời, allocation tăng. Đây không phải vấn đề lớn nhất nhưng có thể đáng kể trong outage.

**Severity:** Low

**Recommended fix:** Đặt payload size limit; serialize một lần ở boundary hợp lý; tránh capture thêm bản sao trong log. Với payload rất lớn, reconsider webhook contract.

### 10. `throw new InvalidOperationException` mất context delivery quan trọng

**Problem:** Sau retry chỉ ném exception chung chung.

**Why it happens:** Không có domain-specific failure model.

**Production impact:** Upstream khó biết partner, event id, last status, số attempts, retryability và reason để dead-letter/reconcile.

**Severity:** Medium

**Recommended fix:** Trả/throw structured result hoặc domain exception chứa safe metadata; worker nên persist delivery state và quyết định dead-letter/escalation rõ ràng.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng `IHttpClientFactory` thông qua một named client, stable idempotency key, cancellation propagation và retry có backoff. Retry rules phải điều chỉnh theo contract của đối tác; không nên copy máy móc cho mọi API.

```csharp
public sealed class WebhookSender
{
    private readonly HttpClient _client;
    private readonly ILogger<WebhookSender> _logger;

    public WebhookSender(
        IHttpClientFactory httpClientFactory,
        ILogger<WebhookSender> logger)
    {
        _client = httpClientFactory.CreateClient("partner-webhooks");
        _logger = logger;
    }

    public async Task SendAsync(
        Uri url,
        string json,
        Guid eventId,
        CancellationToken cancellationToken)
    {
        const int maxAttempts = 5;

        for (var attempt = 1; attempt <= maxAttempts; attempt++)
        {
            cancellationToken.ThrowIfCancellationRequested();

            using var request = new HttpRequestMessage(HttpMethod.Post, url)
            {
                Content = new StringContent(
                    json,
                    Encoding.UTF8,
                    "application/json")
            };

            request.Headers.TryAddWithoutValidation(
                "Idempotency-Key",
                eventId.ToString("N"));

            var started = Stopwatch.GetTimestamp();

            try
            {
                using var response = await _client.SendAsync(
                    request,
                    HttpCompletionOption.ResponseHeadersRead,
                    cancellationToken);

                var elapsed = Stopwatch.GetElapsedTime(started);

                if (response.IsSuccessStatusCode)
                {
                    _logger.LogInformation(
                        "Webhook delivered. EventId={EventId} Attempt={Attempt} " +
                        "Status={Status} DurationMs={DurationMs}",
                        eventId,
                        attempt,
                        (int)response.StatusCode,
                        elapsed.TotalMilliseconds);
                    return;
                }

                if (!ShouldRetry(response.StatusCode) || attempt == maxAttempts)
                {
                    throw new WebhookDeliveryException(
                        eventId,
                        (int)response.StatusCode,
                        attempt);
                }

                var delay = GetRetryDelay(response, attempt);

                _logger.LogWarning(
                    "Webhook transient failure. EventId={EventId} Attempt={Attempt} " +
                    "Status={Status} RetryDelayMs={RetryDelayMs}",
                    eventId,
                    attempt,
                    (int)response.StatusCode,
                    delay.TotalMilliseconds);

                await Task.Delay(delay, cancellationToken);
            }
            catch (OperationCanceledException)
                when (cancellationToken.IsCancellationRequested)
            {
                throw;
            }
            catch (HttpRequestException ex) when (attempt < maxAttempts)
            {
                var delay = BackoffWithJitter(attempt);

                _logger.LogWarning(
                    ex,
                    "Webhook network failure. EventId={EventId} Attempt={Attempt} " +
                    "RetryDelayMs={RetryDelayMs}",
                    eventId,
                    attempt,
                    delay.TotalMilliseconds);

                await Task.Delay(delay, cancellationToken);
            }
        }

        throw new WebhookDeliveryException(eventId, null, maxAttempts);
    }

    private static bool ShouldRetry(HttpStatusCode statusCode) =>
        statusCode == HttpStatusCode.RequestTimeout ||
        (int)statusCode == 429 ||
        (int)statusCode >= 500;

    private static TimeSpan GetRetryDelay(
        HttpResponseMessage response,
        int attempt)
    {
        if (response.Headers.RetryAfter?.Delta is { } retryAfter)
            return retryAfter;

        return BackoffWithJitter(attempt);
    }

    private static TimeSpan BackoffWithJitter(int attempt)
    {
        var baseSeconds = Math.Min(Math.Pow(2, attempt - 1), 30);
        var jitterMs = Random.Shared.Next(0, 500);
        return TimeSpan.FromSeconds(baseSeconds) +
               TimeSpan.FromMilliseconds(jitterMs);
    }
}
```

Lưu ý: nếu hệ thống dùng resilience library/pipeline được chuẩn hoá trong dự án, nên đặt retry/circuit-breaker/rate-limit policy ở tầng đó thay vì tự viết loop ở mọi sender. Tuy nhiên vẫn phải giữ semantics về idempotency, cancellation và classification của endpoint cụ thể.

## Trade-offs

- `IHttpClientFactory` giúp quản lý handler/connection lifecycle tập trung, nhưng vẫn cần cấu hình timeout, connection limit và policy phù hợp từng partner.
- Retry nhiều hơn tăng khả năng recover transient failure nhưng đồng thời tăng latency, outbound load và backlog. Retry phải có budget.
- Circuit breaker giúp tránh đập liên tục vào partner đang down, nhưng có thể trì hoãn recovery nếu thresholds/cooldown không phù hợp.
- Idempotency key giảm rủi ro duplicate side effect chỉ khi partner thực sự implement đúng contract và giữ key trong thời gian đủ dài.
- Với delivery quan trọng, nên persist trạng thái webhook/outbox thay vì để reliability phụ thuộc vào lifetime của process.

## Cách kiểm thử

1. **Transient HTTP test:** Partner mock trả `500, 500, 200`; xác nhận đúng 3 attempts, cùng idempotency key và delay policy được áp dụng.
2. **Permanent failure test:** Partner trả `400` hoặc `401`; xác nhận không retry mù quáng và failure được phân loại rõ.
3. **Cancellation test:** Huỷ token trong lúc request hoặc backoff; method phải dừng sớm và không retry tiếp.
4. **Ambiguous delivery test:** Mock partner xử lý event nhưng đóng connection trước response; sender retry với cùng idempotency key và partner chỉ tạo một side effect.
5. **Load/failure test:** 500 webhook/giây trong partner outage; theo dõi connection count, queue depth, memory, CPU, p95/p99, retry rate và khả năng recovery khi partner trở lại.

## Quan sát trong production

- Structured log: `EventId`, `PartnerId`, `Attempt`, `Outcome`, `StatusCode`, `DurationMs`, `RetryDelayMs`, trace id.
- Metrics theo partner: success rate, retry rate, permanent failure rate, timeout rate, 429 rate, queue depth, oldest message age.
- Outbound HTTP metrics: active connections, request duration, DNS/connect/TLS errors nếu platform telemetry hỗ trợ.
- Alert khi backlog age vượt SLA, retry rate tăng bất thường hoặc một partner có failure ratio cao.
- Distributed trace từ event creation → queue/worker → outbound HTTP call.
- Không log token, secret header hoặc full payload mặc định.

## Câu hỏi phỏng vấn mở rộng

1. Nếu service crash sau khi partner trả 200 nhưng trước khi bạn đánh dấu delivery thành công trong DB, bạn thiết kế recovery ra sao?
2. Bạn chọn queue + outbox, Hangfire hay worker trực tiếp cho webhook delivery dựa trên tiêu chí nào?
3. Nếu mỗi partner có retry policy và rate limit khác nhau, bạn tổ chức configuration và isolation như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Invariant chịu concurrent access phải được bảo vệ tại nơi nhìn thấy toàn bộ concurrent actors; process-local `lock` không giải quyết scale-out.
- Với tồn kho, ưu tiên biến `check + update` thành một operation atomic/conditional hoặc dùng optimistic concurrency có chiến lược conflict rõ ràng.
- Retry network call phải đi cùng idempotency; nếu không, retry có thể biến availability problem thành duplicate side effect.
- `HttpClient`/handler/connection pool cần lifecycle đúng; tránh tạo client mới trong hot retry loop.
- Cancellation, backoff, failure classification và observability là một phần của design, không phải chi tiết phụ thêm sau cùng.

## Mẫu tư duy cần nhớ

1. **Protect the invariant at the source of truth.**
2. **Design retries together with idempotency.**
3. **Classify failures before retrying.**
4. **Propagate cancellation through every expensive dependency call.**
5. **Treat observability as part of correctness and recovery.**
