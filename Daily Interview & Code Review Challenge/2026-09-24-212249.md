# Câu 1 — Cosmos DB vẫn “nhanh” nhưng RU tăng gấp 8 lần sau khi thêm bộ lọc

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, query execution, indexing, RU, data modeling, observability

## Bối cảnh

Một ASP.NET Core API lưu khoảng 25 triệu activity documents trong Azure Cosmos DB. Container dùng partition key `/tenantId`. Mỗi tenant thông thường có 20–100 nghìn documents, nhưng vài tenant lớn có hơn 2 triệu.

Endpoint cũ luôn nhận `tenantId` và khoảng thời gian, sau đó trả tối đa 100 records mới nhất. Sau một feature mới, UI cho phép tìm theo `status`, `employeeName` và một chuỗi search tự do. API vẫn trả trong khoảng 200–400 ms nên team cho rằng performance ổn, nhưng Azure cost alert cho thấy RU consumption tăng khoảng 8 lần vào giờ cao điểm. Một developer đề xuất tăng provisioned throughput; người khác muốn chuyển toàn bộ dữ liệu sang SQL Server.

Team chưa thu thập normalized RU/query, số physical partitions bị chạm, index metrics hoặc distribution của query shape. Không rõ mọi query có luôn chứa `tenantId` hay không.

## Câu hỏi chính

Hãy giải thích Cosmos DB phải làm gì khi query có hoặc không có partition key, vì sao latency có thể vẫn chấp nhận được trong khi RU tăng mạnh, và bạn sẽ chứng minh nguyên nhân trước khi thay đổi indexing, partition key hoặc database như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Mọi request có exact `tenantId` hay có màn hình admin tìm xuyên nhiều tenant?
2. Query text/parameters thực tế của các request RU cao là gì và RU charge theo từng shape bao nhiêu?
3. `employeeName`, `status`, timestamp và search field hiện được index theo policy nào?
4. Tenant lớn có tạo hot partition về storage/throughput hoặc workload concentration không?
5. Search tự do cần semantics gì: exact/filter, prefix hay full-text/relevance?

## Gợi ý tư duy

### Gợi ý 1

Latency và resource cost là hai dimension khác nhau. Một query có thể trả nhanh vì hệ thống có đủ throughput nhưng vẫn tiêu tốn nhiều RU.

### Gợi ý 2

Hãy reason từ query routing: khi có exact partition key, request có thể được scope hẹp hơn; khi thiếu nó, query có thể phải fan out qua nhiều partitions.

### Gợi ý 3

Đừng thay partition key hoặc thêm index theo cảm tính. Capture query shape, request charge, diagnostics và index behavior trước; sau đó xem data model có phù hợp với access patterns hay không.

## Cấu trúc trả lời đề xuất

1. Làm rõ access patterns và consistency requirement.
2. Phân loại single-partition và cross-partition queries.
3. Giải thích routing/index/query cost ở mức phù hợp.
4. Đo RU theo query shape và tenant size.
5. Kiểm tra diagnostics/index metrics và hot-partition evidence.
6. Tách filter/search requirement.
7. So sánh các lựa chọn: query rewrite, index policy, derived/search store, repartition hoặc database khác.
8. Đánh giá migration cost và consistency.
9. Load-test bằng distribution thực tế.
10. Thiết lập cost/performance telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Exact partition key là thông tin routing quan trọng; query thiếu partition key có thể trở thành cross-partition query.
- Latency thấp không chứng minh query rẻ về RU.
- RU phải được đo theo query shape, data distribution và result cardinality.
- Không đề xuất partition-key migration chỉ vì một symptom chưa được đo.
- Full-text-like requirement không nên bị ép thành arbitrary substring scanning nếu workload/search semantics không phù hợp.

### Điểm cộng

- Nhận ra vài tenant rất lớn có thể làm `/tenantId` vẫn tạo workload skew/hot-key concern dù tenant isolation thuận tiện.
- Phân biệt operational store với dedicated search/read model khi requirement search trở nên phức tạp.
- Đề xuất giới hạn query shape/pagination và tránh trả hoặc scan dữ liệu không cần thiết.

### Senior+

- Đưa ra conditional recommendation: giữ partition key nếu tenant-scoped workload chiếm đa số và scale phù hợp; tạo separate search projection/index nếu cross-tenant/full-text là access pattern khác.
- Xem migration/repartition như data migration có dual-write/backfill/cutover/rollback, không phải đổi một annotation.
- Theo dõi RU/request cùng p95/p99 và throttling thay vì tối ưu một metric.

## Hướng giải quyết tham khảo

Tôi bắt đầu từ access pattern. Nếu endpoint có exact `tenantId`, Cosmos DB có thể route query tới logical partition tương ứng thay vì phải fan out toàn container. Nếu query không có partition key, hệ thống có thể cần thực hiện cross-partition query và aggregate kết quả từ nhiều partitions; dù latency vẫn thấp nhờ throughput/parallelism, tổng work và RU có thể cao hơn đáng kể.

Tôi không suy ra ngay rằng index hay partition key là sai. Tôi sẽ log một normalized query identifier cùng request charge, result count, tenant size và duration; lấy Cosmos diagnostics cho representative expensive requests và kiểm tra index metrics/policy. Sau đó nhóm theo query shape: tenant + time; tenant + status + time; tenant + employee; cross-tenant admin search; free-text. Mục tiêu là biết feature nào tạo RU amplification.

Nếu `status` và timestamp là filter phổ biến, index policy/query shape có thể được tối ưu theo evidence. Nhưng nếu “search tự do” thực chất yêu cầu full-text, relevance, typo tolerance hoặc nhiều field, Cosmos operational query có thể không phải công cụ tốt nhất cho phần đó. Một search index/read model riêng như Elasticsearch có thể là alternative để đánh giá, với trade-off eventual consistency và synchronization complexity. Điều đó không có nghĩa phải chuyển source of truth khỏi Cosmos DB.

Với `/tenantId`, tôi kiểm tra distribution. Nếu phần lớn traffic tenant-scoped thì đây có thể vẫn là partitioning strategy hợp lý. Nếu một số tenant cực lớn hoặc workload tập trung tạo hot logical partition, cần đánh giá limits và alternative modeling dựa trên measured growth/access pattern. Thay partition key là migration đáng kể: cần backfill, validation, cutover và rollback; không làm chỉ vì cost spike của một query mới.

Tăng throughput chỉ có thể che symptom nếu query đang làm unnecessary work; chuyển sang SQL Server cũng không tự giải quyết access pattern/search design. Tôi sẽ ưu tiên giảm scanned/work scope, bảo đảm query luôn truyền partition key khi business scope cho phép, chỉ lấy fields/result cần thiết, và tách cross-tenant/search workload nếu nó có semantics khác.

Sau thay đổi, benchmark trên tenant nhỏ/lớn và concurrency production-like. Theo dõi RU/request theo operation, total RU, throttling, p95/p99, failure rate và distribution theo tenant/query shape. Cost regression phải trở thành observable signal chứ không chỉ billing surprise.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không tăng throughput hay migrate database trước khi biết query nào đang tiêu RU. Với Cosmos DB, exact partition key giúp scope/routing request; nếu feature mới bỏ `tenantId` hoặc tạo cross-partition search thì query có thể fan out và tổng RU tăng dù latency vẫn ổn vì hệ thống còn đủ throughput.

Em sẽ nhóm telemetry theo normalized query shape, đo request charge, result count, tenant size và diagnostics/index behavior. Sau đó mới biết vấn đề là query scope, index, hot tenant hay requirement search không phù hợp với operational store.

Nếu đa số workload vẫn tenant-scoped thì em có thể giữ `/tenantId`. Nếu free-text thực sự cần search semantics, em cân nhắc một search projection riêng thay vì ép Cosmos làm mọi thứ. Repartition chỉ khi distribution/access-pattern evidence chứng minh cần, vì đó là migration dữ liệu chứ không phải config nhỏ. Sau fix em theo dõi cả RU/request, total RU, throttling và p95/p99.”

## Câu hỏi đào sâu

1. Nếu tất cả query đều có `tenantId` nhưng một tenant duy nhất vẫn tiêu phần lớn RU, bạn điều tra tiếp gì?
2. Nếu business yêu cầu cross-tenant admin search với strong consistency ngay sau write, việc tách Elasticsearch read model thay đổi trade-off thế nào?
3. Bạn sẽ thiết kế migration ra sao nếu cuối cùng phải thay partitioning strategy mà không dừng hệ thống lâu?

## Lỗi trả lời thường gặp

- Chỉ nhìn latency và bỏ qua RU/request.
- Nói “thêm index” mà không đo query/index behavior.
- Đổi partition key ngay mà không xét migration/data distribution.
- Chuyển toàn bộ sang SQL chỉ vì một query shape mới.
- Dùng Cosmos DB như full-text search engine mà không làm rõ search semantics.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng RU hoặc đổi database.
- **3–4:** Biết partition key nhưng thiếu measurement strategy.
- **5–6:** Phân biệt single/cross-partition, biết đo RU và index/query shape.
- **7–8:** Reason tốt về skew, search workload, migration và telemetry.
- **9–10:** Đưa conditional architecture decision dựa trên access pattern, consistency, cost và migration risk.

# Câu 2 — Editor publish đúng nhưng người dùng vẫn thấy nội dung cũ qua Akamai

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai/CDN, HTTP caching, cache invalidation, SEO/web engineering, production troubleshooting, observability

## Bối cảnh

Một marketing website dùng Optimizely CMS. Editor publish thay đổi giá trị banner, metadata và một landing page quan trọng. Trong CMS preview và khi gọi trực tiếp origin, nội dung mới xuất hiện gần như ngay lập tức. Tuy nhiên một phần người dùng public vẫn thấy nội dung cũ trong 15–40 phút.

Website đi qua Akamai. HTML response có `Cache-Control` do application/CDN policy phối hợp tạo ra. Một số route có query string cho campaign tracking. Team cũng có browser caching và một application-level cache cho content projection. Sau release gần đây, CDN configuration và redirect/canonical handling có thay đổi.

Incident ảnh hưởng một campaign có thời điểm launch cố định. Search crawler cũng có thể nhận stale title/canonical URL. Team chưa biết stale response đến từ browser, Akamai edge, application cache hay một origin instance. Một engineer muốn purge toàn bộ CDN; người khác muốn đặt `no-store` cho mọi HTML.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo trình tự impact → stabilize → evidence → competing hypotheses → verification → remediation → prevention như thế nào, và làm sao xác định chính xác cache layer nào đang phục vụ stale content trước khi thay đổi policy?

## Câu hỏi làm rõ nên cân nhắc

1. Stale response có xuất hiện ở mọi geography/POP, browser và URL variant hay chỉ một subset?
2. Response headers nào cho biết age/cache status, `Cache-Control`, `Vary`, ETag hoặc surrogate behavior?
3. Publish event hiện có trigger invalidation/purge nào cho CDN/application cache không?
4. Query-string/canonical/redirect policy có tạo nhiều cache keys cho cùng logical page không?
5. Application chạy nhiều instances không, và content/application cache invalidation có đồng bộ giữa instances không?

## Gợi ý tư duy

### Gợi ý 1

“CMS đã publish” và “public response đã fresh ở mọi cache layer” là hai trạng thái khác nhau.

### Gợi ý 2

So sánh cùng URL qua browser, edge và origin; thu response headers và cache metadata thay vì purge trước rồi mất evidence.

### Gợi ý 3

Cache invalidation phải gắn với cache key và content dependency. Hãy kiểm tra URL variants, TTL, purge propagation và application-level cache trước khi quy kết cho CDN.

## Cấu trúc trả lời đề xuất

1. Xác định campaign/SEO impact và freshness requirement.
2. Stabilize có phạm vi nhỏ nhất.
3. Capture stale/fresh samples trước purge.
4. So sánh browser → edge → origin.
5. Lập nhiều hypotheses theo cache layer/key/invalidation.
6. Verify bằng headers, logs và origin checks.
7. Purge/fix targeted objects.
8. Sửa invalidation/cache policy.
9. Test publish + URL variants + multiple regions.
10. Monitor freshness và purge failures.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không purge toàn CDN trước khi capture evidence nếu chưa cần emergency mitigation.
- Không dùng `no-store` cho mọi HTML như blanket fix.
- Phân biệt browser cache, CDN edge cache, application cache và CMS/origin freshness.
- Kiểm tra cache keys/query strings/headers/invalidation path.
- Có strategy riêng cho content cần launch-time freshness.

### Điểm cộng

- Nhận ra canonical/redirect/query variants vừa ảnh hưởng caching vừa ảnh hưởng SEO correctness.
- Dùng targeted purge/versioning hoặc short TTL theo content class thay vì một policy cho mọi page.
- Kiểm tra multi-instance application cache invalidation.

### Senior+

- Thiết kế cache policy theo content semantics: immutable static assets, frequently updated HTML, campaign-critical pages.
- Có freshness synthetic checks từ nhiều regions và alert khi origin version khác edge version quá SLO.
- Xem purge là failure-prone distributed operation cần telemetry/retry, không phải magic button.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định business deadline và blast radius. Nếu campaign đang live và stale content gây thiệt hại, có thể targeted purge các affected URLs ngay sau khi capture tối thiểu evidence cần thiết; không nhất thiết chờ full RCA. Nhưng purge toàn CDN làm tăng origin load và xóa evidence, nên chỉ dùng nếu phạm vi thực sự rộng và risk biện minh.

Tôi lấy một stale URL cụ thể và so response ở nhiều tầng. Browser devtools giúp kiểm tra local cache; request bypass browser cache hoặc một clean client giúp loại lớp này. Sau đó xem response headers/cache diagnostics từ Akamai và gọi origin theo đường kiểm soát được để xác nhận origin version. Nếu origin mới nhưng edge cũ, tập trung vào edge key/TTL/purge. Nếu origin instance đôi lúc cũ, kiểm tra application cache hoặc content synchronization giữa instances.

Các hypothesis phải cạnh tranh: publish không invalidates application cache; purge event không được gửi hoặc thất bại; Akamai cache key khác vì query-string policy; redirect/canonical tạo URL variant chưa purge; `Cache-Control`/TTL bị thay đổi; `Vary` tạo variants; một origin instance giữ stale projection. Release gần đây thay CDN/canonical config là signal nhưng không phải bằng chứng root cause.

Sau khi xác định layer, recovery nên targeted. Ví dụ nếu `/landing?utm_source=x` và `/landing` bị cache như keys khác nhau, purge logic/policy phải phù hợp với desired query normalization. Tracking parameters thường không nên vô tình tạo vô hạn content variants nếu response semantics giống nhau, nhưng quyết định phải phù hợp Akamai configuration và analytics requirement. Nếu application cache giữ content projection, invalidation phải dựa trên content publish event/dependency và hoạt động trên multi-instance deployment.

Không đặt `no-store` cho toàn bộ HTML nếu site hưởng lợi từ edge caching. Thay vào đó phân loại content: static fingerprinted assets có TTL dài; HTML thường có TTL/revalidation phù hợp; campaign-critical page có TTL ngắn hơn hoặc explicit purge workflow. SEO-sensitive canonical/title cần được kiểm tra qua public edge, không chỉ CMS preview.

Prevention gồm publish-to-public freshness metric, purge success/failure telemetry, cache hit/age observations, synthetic checks từ nhiều regions và dashboard so content/version marker giữa origin và edge khi khả thi. Test phải bao gồm publish, republish, rollback, query variants, redirects, multiple POPs và CDN failure/degraded behavior.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xác định trước stale content ảnh hưởng campaign/SEO tới đâu. Nếu cần stabilize ngay, em targeted purge affected URLs nhưng vẫn capture một vài stale samples trước để giữ evidence.

Em trace cùng URL từ browser tới Akamai rồi origin. Nếu origin mới nhưng edge cũ, em kiểm tra cache key, TTL, query-string handling và purge history. Nếu origin đôi lúc cũ thì em chuyển sang application cache/multi-instance content state. Em không mặc định release CDN là root cause chỉ vì timing trùng nhau.

Sau RCA, em sửa invalidation theo logical content và URL variants, đồng thời phân loại cache policy thay vì `no-store` toàn site. Static assets có thể cache dài, HTML có TTL/revalidation phù hợp, còn campaign-critical page có explicit purge/freshness SLO. Em thêm synthetic checks nhiều regions và telemetry cho purge/freshness để lần sau biết stale nằm ở layer nào.”

## Câu hỏi đào sâu

1. Nếu origin và một Akamai POP đều fresh nhưng người dùng cụ thể vẫn stale, bạn kiểm tra tiếp gì?
2. Nếu Product yêu cầu mọi publish public trong dưới 5 giây toàn cầu, bạn sẽ challenge hoặc thiết kế requirement này thế nào?
3. Query tracking parameters nên tham gia cache key hay bị normalize bỏ đi? Điều gì quyết định lựa chọn?

## Lỗi trả lời thường gặp

- Purge toàn CDN ngay và mất evidence.
- Đặt `no-store` toàn bộ site.
- Chỉ kiểm tra CMS preview/origin.
- Bỏ qua query-string/cache-key variants.
- Không xét SEO/canonical và multi-instance application cache.

## Thang điểm 0–10

- **0–2:** Chỉ purge/restart.
- **3–4:** Biết CDN cache nhưng không isolate layers.
- **5–6:** Có headers/cache-key/invalidation reasoning và targeted recovery.
- **7–8:** Có layered cache policy, SEO, multi-region tests và telemetry.
- **9–10:** Cân bằng incident stabilization, cache economics, freshness SLO và distributed invalidation failure.

# Câu 3 — Thiết kế release pipeline cho monolith .NET + database mà không biến CI/CD thành “deploy script khổng lồ”

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Git, CI/CD, TeamCity/Jenkins, Octopus Deploy, Azure App Service/IIS, database migrations, release safety, rollback, testing, engineering process

## Bối cảnh

Một enterprise ASP.NET Core monolith được phát triển bởi 3 squads nhưng deploy như một artifact. Production hiện chạy trên Azure App Service; một số khách hàng legacy vẫn có deployment IIS/Windows Server riêng. CI dùng TeamCity, deployment dùng Octopus Deploy. SQL Server schema được thay đổi bằng migration scripts đi cùng release.

Hiện pipeline build lại source ở nhiều environment. Một số configuration values được copy thủ công. Database migration chạy ngay trước application deployment; nếu application deployment fail, team thường rollback package nhưng không có quy tắc rõ database rollback. Hotfix đôi lúc được build từ branch riêng và sau đó quên merge lại main. Automated integration/E2E tests còn giới hạn.

Team đề xuất “chuẩn hóa” bằng cách đưa mọi thứ vào một script duy nhất: build, test, migrate DB, deploy, smoke test và rollback. Một nhóm khác muốn tách thành nhiều microservices để các squads deploy độc lập. Business chỉ yêu cầu giảm deployment failure và recovery time; chưa yêu cầu independent scaling.

## Câu hỏi chính

Bạn sẽ thiết kế lại release workflow và ownership như thế nào để đạt artifact consistency, safe database evolution, environment configuration, verification và rollback tốt hơn mà không mặc định microservices hay một orchestration script phức tạp là lời giải?

## Câu hỏi làm rõ nên cân nhắc

1. Azure App Service và IIS customer deployments có cùng release cadence/approval/compliance requirement không?
2. Database migrations hiện là backward-compatible hay có destructive changes trong cùng release?
3. Secrets/configuration nào thuộc artifact, environment hay customer-specific deployment?
4. Recovery objective là rollback trong bao lâu, và có deployment slots/canary capability ở target nào?
5. Những regression nào hiện chỉ QA manual mới bắt được và có thể tự động hóa ở integration/Playwright E2E level?

## Gợi ý tư duy

### Gợi ý 1

Tách “build artifact” khỏi “promote artifact”. Một release đáng tin cậy cần biết chính xác binary nào đã được test và đang chạy.

### Gợi ý 2

Application rollback không đồng nghĩa database rollback. Schema evolution cần compatibility strategy riêng.

### Gợi ý 3

Đừng dùng microservices để chữa pipeline discipline. Trước hết làm monolith release deterministic, observable và recoverable.

## Cấu trúc trả lời đề xuất

1. Làm rõ release/SLO/compliance constraints.
2. Xác định immutable build artifact và provenance.
3. Tách build, verification và deployment stages.
4. Externalize environment configuration/secrets.
5. Thiết kế database migration strategy.
6. Chọn deployment strategy theo hosting target.
7. Thêm automated gates theo risk.
8. Thiết kế rollback/roll-forward và hotfix flow.
9. Ghi release telemetry/audit.
10. Chỉ đánh giá service decomposition nếu có independent business/operational boundary.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Build once, promote same immutable artifact qua environments.
- Không rebuild source riêng cho production.
- Secrets/config không hard-code vào artifact.
- Database migration cần backward compatibility/expand-contract khi rollback/coexistence yêu cầu.
- Rollback phải được test, không chỉ có nút “redeploy previous package”.

### Điểm cộng

- App Service deployment slots/canary được dùng khi phù hợp nhưng không giả định IIS target có capability giống hệt.
- Release manifest liên kết Git commit, artifact version/hash, DB migration version và deployment result.
- Hotfix flow yêu cầu reconcile về main để tránh branch divergence.
- Playwright chỉ cover critical journeys thay vì cố biến mọi test thành E2E.

### Senior+

- Phân biệt rollback code với roll-forward schema/data remediation.
- Có pre/post-deployment verification và automatic stop conditions dựa trên telemetry.
- Nhận ra customer-hosted IIS có thể cần packaging/approval khác nhưng vẫn nên dùng cùng immutable application artifact khi compatibility cho phép.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng nguyên tắc build once. TeamCity/Jenkins tạo immutable application artifact từ một commit, chạy compile/unit/static analysis và gắn version/hash/provenance. Artifact đó được promote qua environments; production không rebuild source vì rebuild có thể tạo binary/dependency khác với thứ đã test.

Configuration được phân loại. Non-secret environment settings nằm ngoài artifact theo deployment target; secrets lấy từ secret-management mechanism phù hợp và quyền tối thiểu. Pipeline không copy tay connection strings. Với customer IIS deployments, có thể cần environment/customer-specific configuration package hoặc deployment parameters, nhưng application binary nên giữ identity rõ ràng.

Database migration là phần rủi ro nhất. Tôi không coi “rollback package” là database rollback. Nếu release cần zero/low downtime hoặc rollback code, schema change nên ưu tiên expand/contract: thêm compatible schema trước, deploy code hỗ trợ trạng thái chuyển tiếp, backfill nếu cần, rồi remove old schema ở release sau. Destructive migration phải có explicit backup/recovery/data strategy và approval phù hợp. Trong nhiều incident, roll-forward an toàn hơn cố reverse một data migration đã chạy.

Pipeline có stages/gates rõ nhưng không cần một script khổng lồ. Build/test là CI concern; release orchestration có thể do Octopus Deploy quản lý theo environment, với migration step có ownership rõ, deployment, smoke/integration checks và telemetry verification. Tool cụ thể ít quan trọng hơn deterministic artifact, idempotent/repeatable steps, auditability và failure boundaries.

Với App Service, deployment slots có thể hỗ trợ warm-up/verification/swap nếu application và configuration semantics phù hợp. IIS deployment có thể dùng staged rollout theo server/customer group và health verification. Không giả định hai hosting targets giống nhau; vẫn giữ cùng release identity.

Testing dựa trên risk: unit/static analysis sớm; integration test cho DB/external contracts; một số Playwright critical journeys; smoke tests sau deploy; migration compatibility test với representative schema/data. Release dashboard theo dõi version, error rate, latency, health và deployment status. Automatic halt/rollback chỉ dùng khi action thực sự an toàn; database incompatibility có thể khiến roll-forward là lựa chọn đúng hơn.

Hotfix phải bắt nguồn từ known production revision, có review/test tối thiểu, và thay đổi phải được merge/cherry-pick có kiểm soát trở lại main để không mất fix. Git history và release manifest phải trả lời được “commit nào, artifact nào, schema nào đang chạy”.

Tôi không tách microservices chỉ để squads deploy độc lập khi business chưa cần và boundaries chưa rõ. Trước hết làm monolith deploy an toàn. Nếu sau đó independent deployment vẫn là bottleneck có evidence và modules có ownership/data boundaries rõ, decomposition mới là một architecture decision riêng.

## Mẫu trả lời trong phỏng vấn

“Em sẽ sửa release discipline trước khi đổi architecture. CI build một lần từ commit xác định, chạy tests/static analysis và tạo immutable artifact có version/hash. Cùng artifact đó được promote qua staging và production; environment config/secrets nằm ngoài binary.

DB migration em tách khỏi khái niệm application rollback. Nếu cần coexistence hoặc rollback code, em ưu tiên expand/contract để schema tương thích qua nhiều release. Destructive data migration cần recovery plan riêng; đôi khi roll-forward an toàn hơn reverse.

Octopus có thể orchestrate migration, deploy, smoke test và verification, nhưng mỗi step phải có failure boundary/audit rõ thay vì một script opaque. App Service có thể dùng slot khi phù hợp; IIS rollout có strategy riêng nhưng giữ cùng artifact identity. Em thêm integration tests và vài Playwright critical journeys, release telemetry và hotfix reconciliation về main.

Em không dùng microservices để chữa pipeline yếu. Chỉ tách service khi independent deployment mang value đủ lớn và boundary/ownership thật sự rõ.”

## Câu hỏi đào sâu

1. Nếu migration đã drop một column và application mới fail sau deploy, “rollback previous package” có còn an toàn không? Bạn xử lý thế nào?
2. Nếu customer IIS deployments phải giữ version cũ sáu tháng, bạn quản lý backward compatibility và support matrix ra sao?
3. Nếu squads vẫn bị block bởi monolith release cadence sau khi pipeline đã tốt, evidence nào khiến bạn cân nhắc Modular Monolith hoặc service extraction?

## Lỗi trả lời thường gặp

- Rebuild source ở mỗi environment.
- Coi application rollback là database rollback.
- Nhét secrets/config vào artifact.
- Tách microservices chỉ để sửa CI/CD pain.
- Dùng toàn bộ E2E tests như gate duy nhất và bỏ qua integration/migration tests.

## Thang điểm 0–10

- **0–2:** Chỉ nói “thêm pipeline automation”.
- **3–4:** Có CI/CD stages nhưng thiếu artifact/database reasoning.
- **5–6:** Build-once/promote, config, migration và rollback hợp lý.
- **7–8:** Có compatibility, hosting-specific rollout, test strategy, telemetry và hotfix discipline.
- **9–10:** Cân bằng release safety, database reality, organizational needs và cost of architectural complexity.
