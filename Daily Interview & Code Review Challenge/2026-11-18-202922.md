# Câu 1 — Elasticsearch: vì sao alias chuyển index nhưng người dùng vẫn thấy dữ liệu cũ?

**Loại câu hỏi:** Internal mechanism  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Elasticsearch alias, refresh, replica, consistency, HTTP caching

## Bối cảnh

Một API ASP.NET Core đọc catalog từ Elasticsearch. Sau khi reindex 2 triệu sản phẩm, đội vận hành đổi read alias từ products-v7 sang products-v8. Một số người dùng vẫn thấy giá cũ trong 30 giây, một số truy vấn trả kết quả khác nhau. API cũng có Akamai ở phía trước. Không có bằng chứng rằng Elasticsearch là nguyên nhân duy nhất.

## Câu hỏi chính

Giải thích các cơ chế nào có thể tạo ra hiện tượng này, cách phân biệt chúng bằng bằng chứng và cách bảo đảm giá thanh toán không bị quyết định bởi search index.

## Câu hỏi làm rõ nên cân nhắc

1. Giá trong search chỉ để hiển thị hay dùng để chốt đơn?
2. Alias swap thực hiện atomic bằng một request update aliases hay nhiều request?
3. Có CDN/browser/API cache không và cache key/TTL thế nào?
4. Tất cả request đi cùng cluster/index và cùng query không?
5. Pipeline đồng bộ dữ liệu từ SQL có tiếp tục ghi vào index cũ không?

## Gợi ý tư duy

### Gợi ý 1

Tách consistency của search index và các tầng cache.

### Gợi ý 2

Xem refresh visibility, alias target, routing và nguồn dữ liệu gốc.

### Gợi ý 3

Đối chiếu index UUID, alias state, response cache headers và timestamp của bản ghi.

## Cấu trúc trả lời đề xuất

1. Lập sơ đồ read path từ browser đến Elasticsearch.
2. Phân biệt stale cache, stale index, đồng bộ chậm và truy vấn không ổn định.
3. Đo từng tầng và đề xuất rollout/rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

Alias là tên trỏ index, đổi alias không tự purge CDN và không làm dữ liệu nguồn nhất quán; Elasticsearch near-real-time search phụ thuộc refresh; cần xác định nguồn giá authoritative.

### Điểm cộng

Kiểm tra alias atomic update, writes trong giai đoạn chuyển, document version, cache headers, correlation ID.

### Senior+

Thiết kế blue/green reindex có checkpoint, dual-write hoặc replay theo event version và cơ chế phát hiện lag.

## Hướng giải quyết tham khảo

Giả định SQL là source of truth. Trước tiên thu thập response headers (Age, Cache-Control, cache status), request ID, index được truy vấn và document updatedAt/version. Nếu response được phục vụ ở Akamai thì alias swap không liên quan tới response đó; kiểm tra cache key, TTL và purge có chọn lọc. Nếu request tới Elasticsearch, kiểm tra GET _alias/products-read, target index, trạng thái shard và so sánh query trực tiếp tới products-v8. Alias update trong một request có tính atomic ở metadata cluster, nhưng không đảm bảo tất cả hệ thống upstream hết cache. Search visibility có thể chậm đến refresh, còn ingestion async có thể lag lâu hơn. Kiểm tra timestamp event, dead-letter/retry và version để tránh event cũ ghi đè event mới. Không dùng search result làm giá giao dịch: checkout đọc giá authoritative từ service/database và kiểm tra lại trước khi commit. Khi rollout, build v8, backfill, kiểm tra count và sample, replay delta, swap alias atomic, quan sát error/lag, rollback alias nếu cần; tránh giả định rollback index cũng rollback dữ liệu phát sinh sau swap. Test alias switch, cache TTL, concurrent writes và stale events. Theo dõi freshness lag p95, index failure, query latency và CDN hit/stale ratio.

## Mẫu trả lời trong phỏng vấn

Tôi sẽ không kết luận alias lỗi ngay. Tôi xác định read path và nguồn giá chuẩn trước. Alias swap thay đổi đích tìm kiếm nhưng không xóa cache ở CDN, và index có thể chưa nhận hết event. Tôi so sánh cùng một sản phẩm ở SQL, index v8 và response HTTP với version và cache headers. Nếu lỗi nằm ở CDN, xử lý cache policy/purge; nếu ở ingestion, xử lý checkpoint, retry và thứ tự event. Search chỉ phục vụ khám phá; checkout phải xác minh giá từ nguồn authoritative. Tôi triển khai reindex có kiểm chứng, swap alias atomic, dashboard lag và rollback được.

## Câu hỏi đào sâu

1. Nếu CDN không thể purge tức thời, bạn bảo vệ giá hiển thị như thế nào?
2. Nếu event cập nhật đến sai thứ tự, bạn dùng versioning nào?
3. Vì sao refresh Elasticsearch không thay thế được chiến lược consistency?

## Lỗi trả lời thường gặp

1. Khẳng định alias swap tự đồng bộ mọi cache.
2. Dùng search index làm giá thanh toán cuối cùng.
3. Không kiểm tra event lag và out-of-order.
4. Purge toàn bộ CDN mà không đánh giá tác động.
5. Không lưu version để truy vết.

## Thang điểm 0–10

Làm rõ 1; cơ chế 2; phân biệt giả thuyết và chứng cứ 2; thiết kế an toàn 2; trade-offs 1; test/telemetry 1; giao tiếp 1.

# Câu 2 — Kubernetes: p99 tăng sau rollout nhưng CPU vẫn thấp

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, probes, networking, tracing, deployment

## Bối cảnh

Một backend .NET 8 chạy 6 Pods trên Kubernetes. Sau rolling deployment, p99 của API tìm kiếm tăng từ 400 ms lên 8 s; p50 gần như không đổi, CPU dưới 35%, tỷ lệ 504 tăng, một số Pod restart. Readiness probe chỉ gọi /health trả 200. Đội vận hành không được phép dừng hoàn toàn dịch vụ.

## Câu hỏi chính

Bạn sẽ xử lý incident theo thứ tự nào để giảm tác động, phân biệt các giả thuyết và quyết định rollback hay hotfix?

## Câu hỏi làm rõ nên cân nhắc

1. Có bao nhiêu request bị ảnh hưởng theo endpoint, region và Pod version?
2. 504 phát sinh từ ingress, reverse proxy hay downstream?
3. Probe readiness có kiểm tra khả năng nhận traffic và thời gian warm-up không?
4. Có thay đổi connection pool, HttpClient, DNS, DB hoặc dependency trong release không?
5. Có request/limit memory, OOMKilled, rollout maxUnavailable/maxSurge và graceful termination không?

## Gợi ý tư duy

### Gợi ý 1

Tập trung tail latency và traffic distribution, không suy từ CPU trung bình.

### Gợi ý 2

Liên hệ readiness, lifecycle, downstream timeouts và connection reuse.

### Gợi ý 3

Đối chiếu trace từng Pod, termination reason và deployment timeline.

## Cấu trúc trả lời đề xuất

1. Định lượng ảnh hưởng và đóng băng rollout.
2. Giảm tải hoặc rollback theo SLO.
3. Lập bảng giả thuyết và tín hiệu phân biệt.
4. Xác minh fix bằng canary, load và alert.

## Ý chính của câu trả lời tốt

### Bắt buộc

Đánh giá business impact, rollback an toàn, đọc kubectl describe/events, termination reason, traces, p99 per Pod và 504 origin; không dùng CPU thấp để loại trừ contention hoặc I/O.

### Điểm cộng

Phân tích startup/readiness, termination grace, connection pool, queueing và dependency telemetry.

### Senior+

Thiết kế canary SLO gates, probe semantics, preStop/termination behavior và capacity headroom.

## Hướng giải quyết tham khảo

Đầu tiên xác định lỗi ảnh hưởng bao nhiêu user và giao dịch; tạm dừng rollout, giảm blast radius bằng rollback tới image/config đã biết tốt nếu tương thích schema, hoặc chuyển traffic khỏi Pod lỗi. Không xóa Pod hàng loạt vì có thể giảm capacity. Dùng kubectl rollout status/history, describe pod, events, logs --previous, containerStatuses.lastState, OOMKilled, readiness transitions; phân tách 504 từ ingress hay upstream bằng trace ID. So sánh p95/p99 theo Pod/version, số request đang xử lý, thread pool queue, GC pauses, outbound connection pool, DNS errors, DB waits, request timeout và dependency duration. Các giả thuyết gồm probe báo ready quá sớm, warm-up cache, downstream connection starvation, timeout mới, pod termination cắt request, resource throttling hoặc skew traffic. CPU thấp không loại trừ I/O wait, lock contention hay pool exhaustion. Thử thay đổi một biến trong staging/canary; kiểm tra startupProbe và readiness phản ánh khả năng phục vụ, không nhồi các dependency không thiết yếu vào liveness. Thiết kế graceful shutdown, terminationGracePeriodSeconds phù hợp, retry có jitter và budget, timeout có phân tầng. Test rolling deployment dưới tải, dependency latency injection, Pod drain, rollback và schema backward compatibility. Dashboard p99/504 theo release, readiness transitions, restarts, in-flight requests và downstream errors; alert theo error budget.

## Mẫu trả lời trong phỏng vấn

Tôi sẽ ưu tiên giảm lỗi cho người dùng, dừng rollout và xem rollback có an toàn với database migration hay không. Tôi so sánh Pod mới/cũ, nguồn 504 và trace request chậm; CPU thấp không chứng minh backend khỏe. Các giả thuyết gồm readiness quá sớm, connection pool, dependency timeout và Pod bị terminate giữa request. Tôi lấy events, previous logs, traces và p99 theo version để phân biệt. Sau đó kiểm chứng bằng canary có traffic thực, test Pod drain và downstream failure. Tôi chỉ mở rollout lại khi latency và error budget đạt ngưỡng.

## Câu hỏi đào sâu

1. Nếu migration database không backward-compatible thì rollback bằng cách nào?
2. Tại sao liveness không nên phụ thuộc trực tiếp vào mọi downstream service?
3. Nếu chỉ 1% request chậm, bạn chọn metrics và sampling trace ra sao?

## Lỗi trả lời thường gặp

1. Scale Pod ngay mà không biết bottleneck.
2. Dựa CPU trung bình để kết luận không có vấn đề.
3. Đổi liveness thành dependency check khiến restart storm.
4. Rollback mà không kiểm tra schema compatibility.
5. Không phân biệt ingress 504 với ứng dụng trả 504.

## Thang điểm 0–10

Impact/stabilization 2; hypothesis/evidence 2; runtime/Kubernetes depth 2; remediation 1; test 1; observability 1; communication 1.

# Câu 3 — Thiết kế dịch vụ import file lớn: App Service hay Azure Functions, Blob và SQL?

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, ASP.NET Core, Azure Functions, SQL, idempotency, security

## Bối cảnh

Một nền tảng nhân sự cần import CSV 500 MB chứa tối đa 1 triệu dòng. Người dùng muốn upload, xem tiến độ, tải báo cáo dòng lỗi và có thể retry khi mạng gián đoạn. Backend hiện là ASP.NET Core trên Azure App Service, SQL Server lưu dữ liệu. Nhóm nhỏ, ưu tiên vận hành đơn giản, không yêu cầu kết quả tức thì.

## Câu hỏi chính

Đề xuất kiến trúc end-to-end, giải thích lựa chọn upload trực tiếp Blob hay qua API, xử lý bằng Worker/Functions hay trong request, transaction boundary, retry và bảo mật.

## Câu hỏi làm rõ nên cân nhắc

1. Mỗi tenant có giới hạn dung lượng, throughput và thời hạn lưu file không?
2. Import là insert-only hay upsert, có unique business key không?
3. Có yêu cầu atomic toàn file hay chấp nhận partial success?
4. Ai được phép tải báo cáo lỗi, retention và dữ liệu nhạy cảm?
5. SLA tiến độ và số import đồng thời dự kiến là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

Tách upload khỏi xử lý và không giữ HTTP request suốt import.

### Gợi ý 2

Cần state machine và idempotency cho từng job/batch.

### Gợi ý 3

Đặt giới hạn bảo mật và quan sát được từ đầu.

## Cấu trúc trả lời đề xuất

1. Nêu giả định và API contract.
2. Thiết kế data model và state transitions.
3. Chọn compute/queue/storage tối giản.
4. Phân tích consistency, security, cost và failure recovery.
5. Đề xuất test và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

Upload Blob qua short-lived scoped SAS hoặc backend streaming theo chính sách; tạo import job và xử lý async; trạng thái rõ ràng; giới hạn size/type; validate CSV; retry idempotent; tenant isolation.

### Điểm cộng

Batch transaction, checkpoint, poison jobs, upload finalize, progress semantics, cancellation.

### Senior+

So sánh App Service BackgroundService với Functions/queue và Worker, tránh dual-write bằng outbox hoặc reconciliation, bảo vệ PII.

## Hướng giải quyết tham khảo

Giả định partial success được phép và SQL là nguồn dữ liệu chuẩn. API POST /imports tạo job với tenantId, ownerId, status=PendingUpload, expected checksum/size; cấp SAS ngắn hạn chỉ cho blob riêng nếu policy cho phép, hoặc upload qua API streaming khi cần kiểm soát inline. Client upload block blob có thể resume, sau đó POST /imports/{id}/complete; server kiểm tra blob tồn tại, length, checksum nếu có, MIME không đáng tin và scan malware theo risk. Job chuyển Uploaded→Queued→Processing→Completed/CompletedWithErrors/Failed, lưu counters, checkpoint và row error blob. Queue chứa jobId; Worker hoặc Functions lấy blob bằng Managed Identity, stream parse, validate schema/encoding, xử lý batch và ghi SQL bằng unique (tenantId, importId, rowNumber) hoặc business idempotency key. Mỗi batch commit cùng checkpoint trong SQL khi có thể; nếu queue delivery lặp, batch đã commit được bỏ qua. Không giả định exactly-once. Với đội nhỏ, Functions queue-trigger hợp lý nếu execution characteristics và hosting plan phù hợp; Worker Service/BackgroundService có thể đủ khi tải thấp nhưng phải xử lý multi-instance ownership, restart và shutdown. Queue được ưu tiên nếu cần bền vững; có thể dùng Azure Storage Queue hoặc Service Bus tùy routing/DLQ cần thiết. Upload completion và enqueue là hai hệ thống: dùng outbox hoặc periodic reconciler cho job Uploaded chưa queued. GET /imports/{id} trả trạng thái, counts và ETag; GET /imports/{id}/errors cấp quyền tenant và URL ngắn hạn. Blob private, Managed Identity, encryption, TTL retention, quota, CSV formula injection khi export, rate limits, audit. Load test 1M rows, partial blob, duplicated queue message, worker crash giữa commit, concurrent imports, unauthorized tenant access; theo dõi queue age, processing rate, failed rows, retries, DB waits, storage egress. Không tự động chọn microservices hoặc Kubernetes.

## Mẫu trả lời trong phỏng vấn

Tôi tách upload và import để tránh timeout HTTP. API tạo import job, client upload Blob bằng quyền ngắn hạn, rồi xác nhận hoàn tất. Một worker xử lý streaming theo batch và ghi checkpoint, vì retry hoặc queue redelivery là chuyện bình thường. Tôi dùng SQL để giữ trạng thái và uniqueness, không hứa exactly-once. Nếu lưu lượng nhỏ, một worker triển khai cùng hệ thống có thể đủ, nhưng khi cần xử lý bền vững và scale độc lập tôi chọn queue với Functions hoặc Worker. Tôi đặt tenant authorization, private Blob, quota, retention và dashboard tiến độ ngay trong thiết kế.

## Câu hỏi đào sâu

1. Nếu yêu cầu toàn bộ file phải atomic, bạn thay đổi transaction và staging ra sao?
2. Nếu queue enqueue thành công nhưng update SQL thất bại thì xử lý thế nào?
3. Khi nào bạn không chọn Azure Functions cho workload này?

## Lỗi trả lời thường gặp

1. Upload 500 MB vào memory và xử lý trong một HTTP request.
2. Tin rằng queue bảo đảm exactly-once.
3. Không phân quyền Blob và báo cáo lỗi theo tenant.
4. Dùng transaction SQL kéo dài toàn bộ file.
5. Không có checkpoint hay cách resume.

## Thang điểm 0–10

Clarification 1; API/data model 2; reliability/idempotency 2; architecture trade-offs 2; security 1; testing/observability 1; communication 1.
