# Code Review Challenge 1 — Upload file lớn làm API tăng memory và có lỗ hổng đường dẫn lưu file

**Chủ đề:** Input validation, sensitive-data exposure, resource lifetime, memory/allocation, async/cancellation, performance  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép người dùng upload tài liệu đính kèm cho hồ sơ nhân viên. File phổ biến 1–20 MB, nhưng đôi lúc có file 200–500 MB. API chạy trên nhiều instance sau load balancer.

Production ghi nhận khi nhiều người upload file lớn cùng lúc:

- memory của process tăng nhanh và GC hoạt động mạnh,
- request latency tăng,
- một số request tiếp tục ghi file dù client đã ngắt kết nối,
- disk usage tăng vì file lỗi không được dọn,
- security review cảnh báo code đang tin `FileName` và `ContentType` từ client.

Business yêu cầu giới hạn kích thước, chống ghi file ra ngoài thư mục cho phép, không tin metadata do client gửi, tránh giữ toàn bộ file trong memory và phải cleanup khi lỗi.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/files")]
public sealed class FilesController : ControllerBase
{
    private readonly IWebHostEnvironment _env;
    private readonly AppDbContext _db;
    private readonly ILogger<FilesController> _logger;

    public FilesController(
        IWebHostEnvironment env,
        AppDbContext db,
        ILogger<FilesController> logger)
    {
        _env = env;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(
        IFormFile file,
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        var extension = Path.GetExtension(file.FileName);
        if (extension != ".pdf" && extension != ".docx")
            return BadRequest("Unsupported file type");

        await using var input = file.OpenReadStream();
        using var memory = new MemoryStream();
        await input.CopyToAsync(memory);

        var path = Path.Combine(
            _env.ContentRootPath,
            "uploads",
            employeeId.ToString(),
            file.FileName);

        Directory.CreateDirectory(Path.GetDirectoryName(path)!);
        await System.IO.File.WriteAllBytesAsync(
            path,
            memory.ToArray());

        _db.EmployeeFiles.Add(new EmployeeFile
        {
            EmployeeId = employeeId,
            OriginalName = file.FileName,
            ContentType = file.ContentType,
            Path = path,
            Size = file.Length,
            UploadedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Uploaded {FileName} for employee {EmployeeId} to {Path}",
            file.FileName,
            employeeId,
            path);

        return Ok();
    }
}
```

2. Xác định rủi ro memory, disk, resource lifetime và cancellation.

## Câu hỏi gợi mở

2. `file.FileName` có đáng tin để dùng trực tiếp làm path segment không?

## Kết quả code review tham khảo

### 1. Dùng `file.FileName` trực tiếp trong storage path

**Problem:** Tên file từ client được dùng làm path segment.  
**Why it happens:** Code coi metadata multipart là dữ liệu đáng tin.  
**Production impact:** Có thể gây path manipulation, ghi đè tên trùng hoặc tạo tên file bất thường tùy nền tảng/storage semantics.  
**Severity:** Critical  
**Recommended fix:** Không dùng client filename làm storage key. Tạo tên server-side bằng `Guid`/opaque id; chỉ lưu original name như metadata đã sanitize.

### 2. Không có giới hạn kích thước rõ ràng

**Problem:** Chỉ kiểm tra `Length == 0`.  
**Why it happens:** Không enforce upload quota/application limit.  
**Production impact:** File rất lớn hoặc nhiều upload đồng thời có thể gây memory/disk exhaustion và giảm availability.  
**Severity:** High  
**Recommended fix:** Enforce request/form limit và application-level max size; nếu stream thủ công thì dừng khi vượt ngưỡng.

### 3. Buffer toàn bộ file trong memory rồi lại copy lần nữa

**Problem:** File được copy vào `MemoryStream`, sau đó `ToArray()` tạo thêm buffer.  
**Why it happens:** Pipeline không stream trực tiếp từ input tới destination.  
**Production impact:** Large allocations, LOH pressure, GC pause và OOM khi concurrency tăng.  
**Severity:** High  
**Recommended fix:** Stream trực tiếp từ source sang destination với buffer giới hạn.

### 4. Cancellation token không được truyền cho `CopyToAsync` và file write

**Problem:** Hai thao tác I/O dài không dùng request cancellation token.  
**Why it happens:** Gọi overload không nhận token.  
**Production impact:** Client disconnect nhưng server vẫn tiếp tục đọc/ghi file và tiêu thụ tài nguyên.  
**Severity:** High  
**Recommended fix:** Truyền `cancellationToken` cho toàn bộ async I/O có hỗ trợ.

### 5. Chỉ kiểm tra extension để quyết định loại file

**Problem:** Extension do client kiểm soát.  
**Why it happens:** File type validation chỉ dựa trên tên file.  
**Production impact:** File nội dung khác vẫn có thể được upload dưới đuôi hợp lệ.  
**Severity:** High  
**Recommended fix:** Dùng allowlist extension + content validation phù hợp business, ví dụ kiểm tra signature/magic bytes hoặc parser an toàn; không tin `ContentType` như bằng chứng duy nhất.

### 6. Storage write và database write không atomic

**Problem:** File có thể ghi thành công nhưng DB insert thất bại.  
**Why it happens:** Filesystem và DB là hai resource độc lập.  
**Production impact:** Orphan files làm tăng disk usage và khó quản trị.  
**Severity:** High  
**Recommended fix:** Nếu DB fail, cleanup file best-effort; tốt hơn là ghi vào temporary location rồi finalize sau khi metadata persistence thành công, hoặc có reconciliation job.

### 7. Không kiểm tra employee tồn tại/quyền upload vào employee đó

**Problem:** `employeeId` được nhận trực tiếp nhưng không thấy authorization boundary.  
**Why it happens:** Endpoint tập trung vào upload, bỏ qua resource authorization.  
**Production impact:** Người dùng có thể gắn file sai employee nếu endpoint không được bảo vệ ở lớp khác.  
**Severity:** High  
**Recommended fix:** Enforce authorization theo resource/tenant trước khi lưu file.

### 8. Có nguy cơ overwrite khi tên file trùng

**Problem:** Hai upload cùng employee và cùng filename ghi cùng path.  
**Why it happens:** Storage key phụ thuộc filename client.  
**Production impact:** Race condition và mất dữ liệu do file sau ghi đè file trước.  
**Severity:** Medium  
**Recommended fix:** Dùng unique server-side key và unique metadata id.

### 9. Log full path và filename người dùng cung cấp

**Problem:** Log chứa internal storage path và nguyên bản filename.  
**Why it happens:** Operational log ghi quá nhiều chi tiết.  
**Production impact:** Có thể lộ cấu trúc filesystem hoặc metadata nhạy cảm.  
**Severity:** Medium  
**Recommended fix:** Log file id, employee id, size, outcome; sanitize filename nếu thực sự cần.

### 10. Không có quota/cleanup/reconciliation lifecycle

**Problem:** Không thấy chính sách retention, orphan cleanup hoặc disk threshold.  
**Why it happens:** Storage lifecycle chưa được xem là một phần thiết kế.  
**Production impact:** Disk có thể đầy dần theo thời gian dù traffic bình thường.  
**Severity:** Medium  
**Recommended fix:** Có quota, retention, cleanup job và alert disk usage.

## Phiên bản code đề xuất

```csharp
[HttpPost("upload")]
public async Task<IActionResult> Upload(
    IFormFile file,
    Guid employeeId,
    CancellationToken cancellationToken)
{
    const long maxBytes = 50L * 1024 * 1024;

    if (file.Length <= 0 || file.Length > maxBytes)
        return BadRequest("Invalid file size");

    var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
    if (extension is not ".pdf" and not ".docx")
        return BadRequest("Unsupported file type");

    var canUpload = await _db.Employees
        .AnyAsync(x => x.Id == employeeId, cancellationToken);

    if (!canUpload)
        return NotFound();

    var fileId = Guid.NewGuid();
    var safeName = fileId + extension;
    var directory = Path.Combine(
        _env.ContentRootPath,
        "uploads",
        employeeId.ToString("N"));

    Directory.CreateDirectory(directory);
    var finalPath = Path.Combine(directory, safeName);
    var tempPath = finalPath + ".tmp";

    try
    {
        await using (var source = file.OpenReadStream())
        await using (var destination = new FileStream(
            tempPath,
            FileMode.CreateNew,
            FileAccess.Write,
            FileShare.None,
            bufferSize: 64 * 1024,
            useAsync: true))
        {
            await source.CopyToAsync(
                destination,
                64 * 1024,
                cancellationToken);
        }

        await ValidateFileContentAsync(
            tempPath,
            extension,
            cancellationToken);

        System.IO.File.Move(tempPath, finalPath);

        _db.EmployeeFiles.Add(new EmployeeFile
        {
            Id = fileId,
            EmployeeId = employeeId,
            OriginalName = Path.GetFileName(file.FileName),
            ContentType = file.ContentType,
            Path = finalPath,
            Size = file.Length,
            UploadedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        return Ok(new { fileId });
    }
    catch
    {
        TryDelete(tempPath);
        TryDelete(finalPath);
        throw;
    }
}
```

`ValidateFileContentAsync` cần triển khai theo policy thực tế và parser/library phù hợp. Với production lớn, object storage thường phù hợp hơn filesystem local vì nhiều instance cần chia sẻ dữ liệu và quản lý durability/lifecycle tốt hơn.

## Trade-offs

- Streaming giảm memory nhưng làm validation phức tạp hơn nếu cần inspect toàn bộ nội dung.
- Filesystem local đơn giản nhưng khó chia sẻ giữa nhiều instance và khó scale/recovery hơn object storage.
- Temporary file + finalize cải thiện consistency nhưng vẫn không tạo transaction thật giữa DB và storage.
- Content scanning sâu tăng latency; có thể chuyển sang asynchronous scanning nếu business chấp nhận trạng thái `PendingScan`.

## Cách kiểm thử

1. **Security test:** filename chứa path separator, Unicode bất thường hoặc tên trùng; xác nhận storage key vẫn server-controlled.
2. **Load test:** nhiều upload 20–50 MB đồng thời; theo dõi memory/GC/disk throughput.
3. **Cancellation test:** client disconnect giữa upload; xác nhận I/O dừng và temp file được cleanup.
4. **Failure-path test:** DB fail sau khi storage write; xác nhận cleanup/reconciliation hoạt động.
5. **File-type test:** extension hợp lệ nhưng content không hợp lệ; xác nhận bị từ chối theo policy.

# Code Review Challenge 2 — Redis rate limiter bị vượt giới hạn vì `GET` + `SET` không atomic

**Chủ đề:** Caching, concurrency/race conditions, correctness, performance, error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API public giới hạn mỗi API key tối đa 100 request/phút. Hệ thống chạy trên 8 instance và dùng Redis để chia sẻ counter.

Khi traffic thấp, rate limiter hoạt động đúng. Trong load test hoặc burst thực tế, team thấy một số client gửi được 130–180 request trong cùng cửa sổ. Đôi lúc Redis timeout khiến toàn bộ request bị lỗi 500. Một số key cũng tồn tại lâu bất thường trong Redis.

Business yêu cầu rate limit phải nhất quán đủ để bảo vệ downstream, latency thấp, không tạo single-instance state và cần có policy rõ khi Redis tạm thời unavailable.

## Đoạn code cần review

```csharp
public sealed class RedisRateLimiter
{
    private readonly IDatabase _redis;

    public RedisRateLimiter(IConnectionMultiplexer connection)
    {
        _redis = connection.GetDatabase();
    }

    public async Task<bool> AllowAsync(
        string apiKey,
        CancellationToken cancellationToken)
    {
        var minute = DateTime.UtcNow.ToString("yyyyMMddHHmm");
        var key = $"rate:{apiKey}:{minute}";

        var current = await _redis.StringGetAsync(key);
        var count = current.HasValue
            ? (int)current
            : 0;

        if (count >= 100)
            return false;

        count++;

        await _redis.StringSetAsync(
            key,
            count,
            TimeSpan.FromMinutes(1));

        return true;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problem trong counter update.
2. Xác định race condition giữa nhiều request/instance.
3. Giải thích vì sao limit bị vượt dưới load.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation atomic hơn.
6. Giải thích cách test concurrency và Redis failure.
7. Đề xuất metrics/logs/traces cho rate limiter.

## Câu hỏi gợi mở

1. Hai request cùng đọc `99` rồi cùng ghi `100` có thể xảy ra không?
2. Việc reset TTL ở mỗi `SET` ảnh hưởng window semantics thế nào?
3. Cancellation token có thực sự được dùng trong các Redis call này không?
4. Khi Redis timeout, hệ thống nên fail-open hay fail-closed?
5. Fixed-window có tạo burst ngay tại ranh giới phút không?

## Gợi ý

### Gợi ý 1

Counter increment và việc thiết lập expiry cần được nhìn như một thao tác concurrency-sensitive, không phải hai bước read-modify-write ở application layer.

### Gợi ý 2

Dùng atomic increment phía Redis; thiết lập TTL chỉ khi key vừa được tạo, hoặc dùng Lua/script/transaction nếu cần nhiều điều kiện trong một atomic operation. Sau đó xác định rõ fail-open/fail-closed theo mức độ bảo vệ của endpoint.

## Kết quả code review tham khảo

### 1. Read-modify-write không atomic

**Problem:** `GET -> increment local -> SET` có race condition.  
**Why it happens:** Nhiều request đọc cùng giá trị trước khi request khác ghi kết quả mới.  
**Production impact:** Lost update làm counter thấp hơn traffic thực tế, vì vậy client vượt rate limit.  
**Severity:** Critical  
**Recommended fix:** Dùng atomic `INCR` phía Redis hoặc script atomic nếu logic phức tạp hơn.

### 2. TTL bị reset sau mỗi request

**Problem:** Mỗi `StringSetAsync` lại đặt expiry một phút kể từ request cuối.  
**Why it happens:** Counter update và expiry được gộp bằng `SET` mỗi lần.  
**Production impact:** Key có thể sống lâu hơn intended fixed-window semantics; hành vi cửa sổ không còn rõ ràng.  
**Severity:** High  
**Recommended fix:** Chỉ đặt TTL khi counter được tạo lần đầu hoặc tính expiration đến ranh giới window.

### 3. Fixed-window có burst ở ranh giới phút

**Problem:** Client có thể dùng gần 100 request cuối phút rồi tiếp tục gần 100 request đầu phút sau.  
**Why it happens:** Key theo `yyyyMMddHHmm` chia cửa sổ thành bucket cứng.  
**Production impact:** Downstream vẫn có thể nhận burst gần gấp đôi trong khoảng thời gian rất ngắn.  
**Severity:** High  
**Recommended fix:** Xác nhận requirement; nếu cần smooth rate dùng sliding window, token bucket hoặc leaky bucket.

### 4. Không có failure policy khi Redis unavailable

**Problem:** Redis exception bubble lên caller.  
**Why it happens:** Rate limiter không định nghĩa behavior khi dependency lỗi.  
**Production impact:** Outage Redis có thể biến thành outage API hoặc ngược lại, nếu team sau đó bypass thủ công thì downstream mất protection.  
**Severity:** High  
**Recommended fix:** Chọn fail-open/fail-closed theo endpoint và threat model; log/metric rõ ràng.

### 5. API key được nhúng nguyên bản vào Redis key

**Problem:** Credential identifier có thể xuất hiện trực tiếp trong keyspace/telemetry.  
**Why it happens:** Dùng raw api key làm namespace.  
**Production impact:** Tăng nguy cơ lộ secret nếu API key chính là credential đầy đủ.  
**Severity:** High  
**Recommended fix:** Dùng stable identifier hoặc hash/HMAC của key, không lưu credential nguyên bản.

### 6. Không validate chiều dài/format identifier

**Problem:** Key segment do caller cung cấp có thể quá dài hoặc cardinality rất lớn.  
**Why it happens:** Không normalize/validate identity trước khi tạo Redis key.  
**Production impact:** Tăng memory/cardinality và gây khó observability.  
**Severity:** Medium  
**Recommended fix:** Dùng server-resolved API key id hoặc fixed-length digest.

### 7. Không có metric remaining/rejected/dependency latency

**Problem:** Chỉ trả bool, không có operational signal.  
**Why it happens:** Rate limiting được coi là utility thay vì production control plane.  
**Production impact:** Khó phát hiện limiter bị bypass hoặc Redis latency tăng.  
**Severity:** Medium  
**Recommended fix:** Metric allow/deny, Redis latency/error, limiter fallback mode và key cardinality.

### 8. Không làm rõ clock/window semantics

**Problem:** Window dựa vào clock application instance.  
**Why it happens:** Timestamp bucket được tạo ở app.  
**Production impact:** Clock skew nhỏ giữa instance có thể tạo bucket khác nhau gần ranh giới phút.  
**Severity:** Medium  
**Recommended fix:** Đồng bộ clock tốt hoặc dùng server-side time/window logic nếu cần semantics chặt.

## Phiên bản code đề xuất

```csharp
public sealed class RedisRateLimiter
{
    private readonly IDatabase _redis;
    private readonly ILogger<RedisRateLimiter> _logger;

    public RedisRateLimiter(
        IConnectionMultiplexer connection,
        ILogger<RedisRateLimiter> logger)
    {
        _redis = connection.GetDatabase();
        _logger = logger;
    }

    public async Task<bool> AllowAsync(
        string apiKeyId,
        CancellationToken cancellationToken)
    {
        var now = DateTimeOffset.UtcNow;
        var windowStart = new DateTimeOffset(
            now.Year,
            now.Month,
            now.Day,
            now.Hour,
            now.Minute,
            0,
            TimeSpan.Zero);

        var key = $"rate:{apiKeyId}:{windowStart:yyyyMMddHHmm}";

        try
        {
            var count = await _redis.StringIncrementAsync(key);

            if (count == 1)
            {
                var ttl = windowStart.AddMinutes(1) - now
                    + TimeSpan.FromSeconds(5);

                await _redis.KeyExpireAsync(key, ttl);
            }

            return count <= 100;
        }
        catch (RedisException ex)
        {
            _logger.LogError(ex,
                "Redis rate limiter unavailable for key {ApiKeyId}",
                apiKeyId);

            return false;
        }
    }
}
```

Ví dụ trên dùng fixed-window và fail-closed để minh họa một policy bảo vệ downstream. Trong hệ thống thật, policy có thể khác. Nếu cần đảm bảo `INCR` và TTL được thiết lập như một thao tác atomic hoàn toàn, dùng Lua script phù hợp.

## Trade-offs

- Fixed-window đơn giản và rẻ nhưng burst ở boundary.
- Sliding window chính xác hơn nhưng tốn storage/CPU hơn.
- Token bucket phù hợp burst có kiểm soát nhưng semantics khác request-per-minute cố định.
- Fail-closed bảo vệ downstream nhưng Redis outage có thể làm mất availability.
- Fail-open giữ availability nhưng giảm protection khi dependency lỗi.

## Cách kiểm thử

1. **Concurrency test:** 1.000 request song song trên nhiều app instance; xác nhận số request được allow phù hợp policy.
2. **Boundary test:** gửi traffic sát cuối và đầu phút; đo burst thực tế.
3. **Failure test:** Redis timeout/disconnect; xác nhận fail-open/fail-closed đúng thiết kế.
4. **TTL test:** xác nhận key expire theo window, không bị kéo dài vô hạn.
5. **Security test:** xác nhận raw API secret không xuất hiện trong Redis key/log/metric label.

## Quan sát trong production

- `rate_limit_allowed_total`
- `rate_limit_rejected_total`
- Redis command latency/error rate
- limiter fallback/failure mode count
- key cardinality
- downstream request rate sau limiter
- alert khi Redis errors tăng hoặc reject ratio thay đổi bất thường

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn sliding window thay vì fixed window?
2. Nếu Redis cluster bị partition, bạn chấp nhận consistency level nào cho limiter?
3. Nếu mỗi tenant có nhiều API key và quota chung theo tenant, data model của limiter sẽ thay đổi ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Dữ liệu từ client như filename, content type và identifier phải được coi là untrusted input.
- Streaming và bounded resource usage quan trọng khi file hoặc traffic có kích thước lớn.
- Side effect giữa nhiều storage/resource cần recovery/cleanup vì không có transaction tự nhiên giữa chúng.
- Distributed counters phải dùng atomic operation; read-modify-write ở application layer dễ race dưới concurrency.
- Failure policy của dependency như Redis phải được thiết kế rõ, không để exception quyết định hành vi hệ thống một cách ngẫu nhiên.

## Mẫu tư duy cần nhớ

- Validate before persisting.
- Stream instead of buffering large payloads.
- Design cleanup together with the happy path.
- Prefer atomic server-side operations for distributed counters.
- Define fail-open/fail-closed explicitly for protective infrastructure.
