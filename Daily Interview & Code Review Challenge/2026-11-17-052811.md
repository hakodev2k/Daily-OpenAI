# Code Review Challenge 1 — Đồng bộ product catalog sang Elasticsearch sau khi thay đổi giá

## Bối cảnh

Một hệ thống e-commerce lưu product và giá chuẩn trong PostgreSQL; Elasticsearch chỉ phục vụ tìm kiếm. Sau khi nhân viên sửa giá, API trả về thành công nhưng kết quả search đôi khi vẫn hiển thị giá cũ. Hệ thống có 3 replicas trên Kubernetes, khoảng 100 nghìn products và các đợt import cập nhật hàng nghìn sản phẩm. Khi Elasticsearch mất kết nối 10 phút, một số thay đổi không bao giờ xuất hiện. Product yêu cầu giá trên trang checkout luôn lấy từ nguồn dữ liệu chuẩn; search có thể trễ tối đa vài phút. Chưa có bằng chứng về bottleneck chính.

## Đoạn code cần review

```csharp
public sealed class CatalogService
{
    private readonly CatalogDbContext _db;
    private readonly ElasticsearchClient _search;
    private readonly ILogger<CatalogService> _logger;

    public CatalogService(CatalogDbContext db,
        ElasticsearchClient search, ILogger<CatalogService> logger)
    {
        _db = db;
        _search = search;
        _logger = logger;
    }

    public async Task UpdatePriceAsync(Guid id, decimal price)
    {
        var product = await _db.Products.SingleAsync(x => x.Id == id);
        product.Price = price;
        await _db.SaveChangesAsync();

        _ = Task.Run(async () =>
        {
            try
            {
                await _search.IndexAsync(new
                {
                    product.Id, product.Name, product.Price
                }, i => i.Index("products").Id(product.Id.ToString()));
            }
            catch (Exception ex)
            {
                _logger.LogWarning(ex, "Index failed for {ProductId}", id);
            }
        });
    }
}

public sealed class CatalogReindexWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly ElasticsearchClient _search;

    public CatalogReindexWorker(IServiceScopeFactory scopes, ElasticsearchClient search)
    {
        _scopes = scopes;
        _search = search;
    }

    protected override async Task ExecuteAsync(CancellationToken token)
    {
        while (!token.IsCancellationRequested)
        {
            using var scope = _scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
            var products = await db.Products.ToListAsync(token);
            foreach (var product in products)
                await _search.IndexAsync(product,
                    i => i.Index("products").Id(product.Id.ToString()), token);
            await Task.Delay(TimeSpan.FromMinutes(5), token);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Database commit và indexing không có durable handoff

**Vấn đề:** API commit PostgreSQL trước rồi chạy fire-and-forget task.  
**Tại sao xảy ra:** Task không được lưu bền vững; process crash, pod restart hoặc lỗi indexing làm mất update.  
**Ảnh hưởng production:** Search tồn tại giá cũ vô thời hạn cho đến lần reindex thành công.  
**Cách sửa:** Transactional Outbox: ghi product và outbox event trong cùng transaction; worker riêng đọc và xử lý event.

### [High] — Stale write có thể ghi đè phiên bản mới

**Vấn đề:** Hai task indexing cho cùng product chạy đồng thời.  
**Tại sao xảy ra:** Network latency và retry có thể đảo thứ tự hoàn tất; reindex worker cũng tranh chấp.  
**Ảnh hưởng production:** Search lùi về giá cũ dù database đúng.  
**Cách sửa:** Dùng monotonically increasing product version; bảo vệ thứ tự theo entity bằng serialization/partitioned processing hoặc Elasticsearch external versioning phù hợp, và luôn xác minh semantics của API client.

### [High] — Không kiểm tra kết quả indexing

**Vấn đề:** Chỉ catch exception; một response báo unsuccessful không nhất thiết throw.  
**Tại sao xảy ra:** Client trả response chứa trạng thái lỗi.  
**Ảnh hưởng production:** Log báo yên ổn nhưng index chưa cập nhật.  
**Cách sửa:** Kiểm tra response validity/status, phân loại retryable/permanent errors và đưa permanent failures vào dead-letter workflow.

### [High] — Reindex full scan trên mỗi replica

**Vấn đề:** Mỗi 5 phút tất cả replicas đọc toàn bộ products và gửi request từng document.  
**Tại sao xảy ra:** BackgroundService được host trong mọi pod; không có coordination.  
**Ảnh hưởng production:** DB load, Elasticsearch write amplification, GC và thời gian reindex tăng.  
**Cách sửa:** Dedicated worker với lease/partitioning, incremental checkpoint, bounded batch và Bulk API; full rebuild là maintenance workflow riêng.

### [Medium] — Capturing EF entity sau scope/request lifetime

**Vấn đề:** Closure dùng mutable tracked entity ở background task.  
**Tại sao xảy ra:** Không có immutable snapshot, entity có thể thay đổi và lifetime của task không được quản lý.  
**Ảnh hưởng production:** Dữ liệu không nhất quán, khó debug và shutdown.  
**Cách sửa:** Durable event chỉ chứa identity/version; worker tạo scope riêng và truy vấn authoritative snapshot.

### [Medium] — Không có cancellation/backpressure

**Vấn đề:** Task.Run không được await và không có cancellation; vòng lặp indexing tuần tự không giới hạn thời gian.  
**Tại sao xảy ra:** Không có queue capacity, bounded concurrency hoặc shutdown drain.  
**Ảnh hưởng production:** Backlog không đo được; rollout có thể ngắt tác vụ.  
**Cách sửa:** Bounded worker, CancellationToken, retry policy có jitter, timeout và shutdown-aware checkpoint.

### [Medium] — Index schema và projection thiếu kiểm soát

**Vấn đề:** Một luồng index anonymous object, luồng khác index toàn bộ EF entity.  
**Tại sao xảy ra:** Không có search document contract thống nhất.  
**Ảnh hưởng production:** Mapping drift, trường nhạy cảm vô tình bị index, query inconsistency.  
**Cách sửa:** Explicit ProductSearchDocument projection, versioned mapping và alias-based reindex.

### [Medium] — Không có visibility về freshness

**Vấn đề:** Không có lag, oldest pending event, retry hoặc poison event metrics.  
**Tại sao xảy ra:** Chỉ ghi warning theo exception.  
**Ảnh hưởng production:** Vi phạm freshness SLA không được phát hiện.  
**Cách sửa:** Metrics về outbox lag, pending count, failed count, indexing latency, reconciliation mismatch.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa **transactional outbox** và durable handoff. Giả định database có unique constraint trên `OutboxMessages.EventId`, `Products.Version` được tăng khi thay đổi và một worker chuyên trách claim events với lease an toàn. Phần lease, retry và index-version enforcement là các hợp đồng bắt buộc cần triển khai/test riêng, không được coi là đã giải quyết chỉ bởi đoạn code này.

```csharp
public sealed record ProductPriceChanged(Guid ProductId, long Version);

public sealed class CatalogService
{
    private readonly CatalogDbContext _db;
    public CatalogService(CatalogDbContext db) => _db = db;

    public async Task UpdatePriceAsync(Guid id, decimal price, CancellationToken ct)
    {
        if (price < 0) throw new ArgumentOutOfRangeException(nameof(price));
        await using var tx = await _db.Database.BeginTransactionAsync(ct);
        var product = await _db.Products.SingleAsync(x => x.Id == id, ct);
        product.Price = price;
        product.Version++;
        _db.OutboxMessages.Add(new OutboxMessage
        {
            EventId = Guid.NewGuid(),
            AggregateId = id,
            AggregateVersion = product.Version,
            EventType = "ProductPriceChanged",
            Payload = JsonSerializer.Serialize(
                new ProductPriceChanged(id, product.Version)),
            CreatedAtUtc = DateTimeOffset.UtcNow
        });
        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}

// Worker contract (pseudocode):
// 1. Claim a bounded batch of pending outbox rows with a DB-safe lease.
// 2. For each row, load the authoritative product projection and version.
// 3. Index with a version guard; older writes must not replace newer versions.
// 4. Check the Elasticsearch response, not only thrown exceptions.
// 5. Mark delivered after confirmed success; retries must be idempotent.
// 6. Record attempts, next retry time and terminal failures.
// 7. Reconcile DB versions against index versions periodically.
```

## Giải thích thiết kế sau khi sửa

Outbox bảo đảm sự kiện cập nhật không biến mất khi process chết sau commit; không bảo đảm exactly-once delivery. Consumer phải idempotent, index phải chống stale overwrite và DB vẫn là source of truth. Một dedicated worker đơn giản thường phù hợp hơn đưa messaging infrastructure vào khi throughput chưa đòi hỏi. Nếu nhiều writers cùng sửa product, cần concurrency token/optimistic concurrency để không mất update ngay trong database.

## Trade-offs

Outbox tăng storage, worker operation và eventual consistency; đổi lại có replay/audit. External versioning cần xác nhận khả năng hỗ trợ và semantics theo Elasticsearch client/version đang triển khai. Full rebuild với alias swap phức tạp hơn nhưng cần thiết khi mapping thay đổi; không nên chạy thường xuyên như delta sync.

## Cách kiểm thử

1. **Integration:** Kill process sau database commit trước khi indexing; restart worker và xác nhận event được xử lý.
2. **Concurrency:** Gửi hai price changes cùng product, đảo thứ tự network completion và xác nhận index giữ version mới nhất.
3. **Failure-path:** Elasticsearch trả 429/503 và unsuccessful response; xác nhận retry, backoff, dead-letter và không mất event.
4. **Load:** Import 20 nghìn products, đo DB reads, bulk throughput, lag p95 và giới hạn memory.
5. **Reconciliation:** Cố ý bỏ một event rồi xác minh detector phát hiện và sửa lệch version.

## Quan sát trong production

Theo dõi `outbox_pending`, `oldest_event_age_seconds`, `index_success_rate`, `index_retry_total`, `index_version_mismatch`, Bulk API latency, PostgreSQL locks/CPU và Elasticsearch rejected writes. Dùng correlation ID từ product update đến event và indexing attempt; cảnh báo khi freshness lag vượt SLA.

## Câu hỏi phỏng vấn mở rộng

1. Nếu phải hỗ trợ full reindex không downtime khi thay đổi analyzer, bạn sẽ dùng alias và cutover như thế nào?
2. Nếu checkout phải strong consistency nhưng search eventual consistency, đâu là boundary cần bảo vệ?
3. Khi nào polling outbox là đủ và khi nào cần CDC hoặc message broker?

import { ref, watch, onMounted } from 'vue';

type Product = { id: string; name: string; description: string };
const keyword = ref('');
const category = ref('all');
const page = ref(1);
const products = ref<Product[]>([]);
const loading = ref(false);
const error = ref('');
const total = ref(0);

async function search() {
  loading.value = true;
  error.value = '';
  try {
    const url = '/api/products?keyword=' + keyword.value
      + '&category=' + category.value + '&page=' + page.value;

    total.value = data.total;

    loading.value = false;

watch([keyword, category, page], search);
onMounted(search);
</script>

<template>

## Phiên bản đề xuất

Ví dụ component dưới đây sửa race, HTTP errors, pagination và XSS; đồng bộ URL qua Vue Router. Giả định API trả `{items,total}` với page size 20, query params đã được backend validate. Production nên bổ sung schema validation runtime cho response.

```vue
<script setup lang="ts">
import { computed, onBeforeUnmount, ref, watch } from 'vue';
import { useRoute, useRouter } from 'vue-router';

type Product = { id: string; name: string; description: string };
type Result = { items: Product[]; total: number };
const route = useRoute();
const router = useRouter();
const readPage = () => Math.max(1, Number.parseInt(String(route.query.page ?? '1'), 10) || 1);
const keyword = ref(String(route.query.keyword ?? ''));
const category = ref(String(route.query.category ?? 'all'));
const page = ref(readPage());
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref('');
let controller: AbortController | undefined;
let sequence = 0;
let timer: ReturnType<typeof setTimeout> | undefined;

watch(() => route.query, () => {
  keyword.value = String(route.query.keyword ?? '');
  category.value = String(route.query.category ?? 'all');
  page.value = readPage();
}, { immediate: true });

watch([keyword, category], () => {
  page.value = 1;
  schedule(250);
});
watch(page, () => schedule(0));

function schedule(delay: number) {
  if (timer) clearTimeout(timer);
  controller?.abort();
  const id = ++sequence;
  loading.value = true;
  timer = setTimeout(() => void search(id), delay);
}
async function search(id: number) {
  const local = new AbortController();
  controller = local;
  const params = new URLSearchParams({
    keyword: keyword.value, category: category.value, page: String(page.value)
  });
  try {
    const response = await fetch('/api/products?' + params, { signal: local.signal });
    if (!response.ok) throw new Error('HTTP ' + response.status);
    const data = await response.json() as Result;
    if (id !== sequence) return;
    products.value = data.items;
    total.value = data.total;
    error.value = '';
    await router.replace({ query: { keyword: keyword.value, category: category.value, page: String(page.value) } });
  } catch (e) {
    if (id === sequence && !local.signal.aborted)
      error.value = 'Không tải được danh sách sản phẩm.';
  } finally {
    if (id === sequence) loading.value = false;
  }
}
function next() { if (page.value * 20 < total.value) page.value++; }
function previous() { if (page.value > 1) page.value--; }
schedule(0);
onBeforeUnmount(() => { if (timer) clearTimeout(timer); controller?.abort(); });
</script>
<template>
  <input v-model="keyword" aria-label="Keyword" />
  <select v-model="category" aria-label="Category">
    <option value="all">All</option>
    <option value="hardware">Hardware</option>
    <option value="software">Software</option>
  </select>
  <p v-if="error" role="alert">{{ error }}</p>
  <p v-if="loading">Loading...</p>
  <div v-for="item in products" :key="item.id">
    <h3>{{ item.name }}</h3>
    <div>{{ item.description }}</div>
  </div>
  <button :disabled="page <= 1" @click="previous">Previous</button>
  <button :disabled="page * 20 >= total" @click="next">Next</button>
  <p>Total: {{ total }}</p>
</template>
```

**Lưu ý production:** Ví dụ dùng `router.replace` nên không tạo một history entry cho mỗi thao tác filter. Nếu requirement đòi Back/Forward qua từng filter state, phải dùng `router.push` theo các mốc tương tác đã định nghĩa. Đồng thời cần xử lý cẩn thận chiều đồng bộ router → refs để tránh watcher reset page khi browser Back; giải pháp bền vững là coi router query là single source of truth, dùng computed setters hoặc một state transition function duy nhất, thay vì các watcher hai chiều. Đây là điểm cần hoàn thiện trước khi merge.

## Giải thích thiết kế sau khi sửa

Sequence token bảo vệ state kể cả khi abort không kịp chặn response; `AbortController` giảm tài nguyên client. `URLSearchParams` encode ký tự đặc biệt; `response.ok` tách HTTP failure khỏi network failure. Plain-text interpolation ngăn render HTML không tin cậy. Backend vẫn phải validate page/filter và enforce authorization.

## Trade-offs

Debounce giảm request nhưng thêm độ trễ ngắn. Cancellation không đảm bảo server đã ngừng xử lý. Router state tăng độ phức tạp synchronization; có thể trích thành composable và dùng query cache nếu có nhu cầu thật. Không nên thêm thư viện state management chỉ để giải quyết một form nhỏ.

## Cách kiểm thử

1. **Playwright E2E:** Intercept hai requests, cho response cũ về cuối và xác nhận UI vẫn hiển thị filter mới.
2. **Security:** Description chứa payload HTML/script; xác nhận hiển thị như text, không thực thi.
3. **API failure:** Trả 500, malformed JSON và network abort; xác nhận loading/error hợp lý.
4. **Navigation:** Test page 1/last page, đổi category, bookmark và Back/Forward theo UX contract.
5. **Load/browser:** Gõ nhanh 30 ký tự trên mạng throttled, đo request count, cancelled requests và p95 search latency.

## Quan sát trong production

Theo dõi client search request duration, aborted count, non-2xx rate, keyword-change-to-render latency và backend p95/p99. Dùng correlation ID/trace ID qua frontend–API; không gửi raw keyword chứa PII vào analytics. Dashboard nên phân biệt user cancellation với genuine API failures.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào cần server-side rendering để SEO cho catalog và khi nào client rendering đủ?
2. Nếu API hỗ trợ cursor pagination thay vì page number, bạn thay đổi URL và navigation contract thế nào?
3. Nếu search API phụ thuộc Elasticsearch đang degraded, frontend và backend nên hiển thị fallback ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Database commit không tự bảo đảm search index cập nhật; durable outbox và idempotent indexing xử lý failure boundary.
- Eventual consistency cần freshness SLA, version ordering và reconciliation, không chỉ retry.
- Browser network responses có thể về sai thứ tự; state update cần ownership/sequence.
- Untrusted HTML không được đưa trực tiếp vào DOM; HTTP error handling phải tách khỏi network errors.
- Đo lường lag, failure rate và p95 trước khi tăng hạ tầng hoặc thêm abstraction.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và transaction boundary trước khi thiết kế sync.
2. Thiết kế retry đồng thời với idempotency và version ordering.
3. Với mọi async response, xác định ai được quyền cập nhật state.
4. Kiểm thử crash, reorder, timeout và dependency degradation thay vì chỉ happy path.
5. Đặt observability cạnh acceptance criteria để chứng minh hệ thống hoạt động đúng.
