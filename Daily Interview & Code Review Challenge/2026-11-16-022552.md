# Câu 1 — Vì sao cùng một request tạo ra hai phiên bản dữ liệu khác nhau?

**Loại câu hỏi:** Internal mechanism — EF Core, SQL Server, transaction isolation  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** EF Core change tracker, identity resolution, SQL isolation, optimistic concurrency

## Bối cảnh

API .NET 8 đọc `Order` cùng `OrderLines` để duyệt đơn hàng. Một request dùng `DbContext` scoped, gọi `FindAsync(orderId)`, sau đó một service khác cập nhật trạng thái đơn bằng SQL trực tiếp; service đầu tiếp tục gọi `FindAsync` và thấy trạng thái cũ. Khi chuyển sang `AsNoTracking`, một số kết quả lại khác. Hai nhân viên có thể duyệt cùng đơn đồng thời. Cần giữ latency thấp; chưa biết isolation level, thời điểm transaction và cách cập nhật ngoài EF Core.

## Câu hỏi chính

Hãy giải thích chính xác các lớp cache/tracking/transaction liên quan, vì sao đọc lại có thể không phản ánh cập nhật, và thiết kế luồng duyệt đơn tránh lost update mà không khóa toàn hệ thống.

## Câu hỏi làm rõ nên cân nhắc

1. Các lần đọc có dùng cùng `DbContext` và cùng transaction không?
2. SQL trực tiếp chạy cùng connection/transaction hay connection khác?
3. Trạng thái phải phản ánh thay đổi tức thì hay snapshot nhất quán?
4. Đơn có concurrency token và quy tắc chuyển trạng thái không?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt object đã tracked với câu SQL mới.

### Gợi ý 2

`FindAsync` và LINQ tracking query không nhất thiết có cùng hành vi khi entity đã tracked.

### Gợi ý 3

Phân biệt identity map, database isolation và conditional update.

## Cấu trúc trả lời đề xuất

Xác định identity/lifetime → tái hiện timeline → giải thích tracking và isolation → xác định invariant → chọn concurrency control → kiểm thử hai writer.

## Ý chính của câu trả lời tốt

### Bắt buộc

`FindAsync` có thể trả entity đang tracked mà không query DB; tracking query identity resolution giữ instance hiện có, không tự ghi đè current values; `AsNoTracking` tạo đối tượng không tracked nhưng vẫn phụ thuộc snapshot/isolation; tránh kết luận chỉ do SQL cache.

### Điểm cộng

So sánh `ReloadAsync`, `ChangeTracker.Clear`, context mới, projection và `rowversion`/concurrency token; phân biệt concurrency exception với business conflict.

### Senior+

Thiết kế transition idempotent, audit trail, conflict HTTP 409, retry có giới hạn và metric conflict rate.

## Hướng giải quyết tham khảo

**Giả định:** SQL Server với `READ COMMITTED`, các câu SQL chạy ngoài EF context, chưa có token. Trước tiên log `DbContext.ContextId`, SQL command và transaction ID để tái hiện. `FindAsync` kiểm tra local tracked entities; vì vậy đọc lần hai có thể không gửi SQL. `AsNoTracking` bỏ tracking nhưng không bảo đảm nhìn thấy commit mới nếu query đang trong snapshot transaction; SQL Server `READ_COMMITTED_SNAPSHOT` và `SNAPSHOT` có semantics khác nhau. Không dùng `AsNoTracking` như giải pháp concurrency. Với update nghiệp vụ, thêm `rowversion` (SQL Server) hoặc token tương đương và update theo expected version; EF Core sẽ kiểm tra số dòng ảnh hưởng và ném `DbUpdateConcurrencyException` khi điều kiện không còn đúng. Bắt exception, đọc trạng thái mới bằng context phù hợp, trả 409 hoặc áp dụng merge có quy tắc; không tự động retry mọi thao tác duyệt. Cần transaction cho thay đổi trạng thái và audit/outbox nếu phát sự kiện. `ExecuteUpdate`/SQL trực tiếp không tự đồng bộ tracked objects và cần predicate concurrency thủ công. Test hai approver cùng version: chỉ một transition hợp lệ; xác minh số SQL, trạng thái cuối và audit. Quan sát conflict count, transaction duration, deadlocks, SQL waits và p95.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ xác minh hai lần đọc có cùng `DbContext` và transaction hay không. Nếu `FindAsync` đã có entity tracked, lần gọi sau có thể lấy object cũ từ identity map, không đọc SQL. `AsNoTracking` chỉ thay đổi tracking; database isolation vẫn có thể giữ snapshot. Tôi sẽ tái hiện timeline bằng SQL logs và transaction metadata. Về correctness, tôi không dùng reload như cơ chế chống ghi đè: tôi định nghĩa transition hợp lệ và dùng optimistic concurrency token, trả conflict khi hai người cùng duyệt. Nếu phát event, transaction và outbox phải bảo đảm không phát event cho update thất bại. Đổi lại người dùng phải xử lý conflict, nhưng ta tránh giữ lock dài và dễ scale hơn.

## Câu hỏi đào sâu

1. Nếu dùng PostgreSQL thay SQL Server, bạn chọn token gì và vì sao?
2. Nếu 409 tăng đột biến, khi nào pessimistic locking hợp lý hơn?
3. Nếu cập nhật bằng `ExecuteUpdateAsync`, bạn bảo toàn concurrency như thế nào?

## Lỗi trả lời thường gặp

1. Đồng nhất tracking cache với Redis/database cache.
2. Tin `AsNoTracking` bảo đảm fresh read.
3. Retry vô hạn mọi concurrency exception.
4. Không kiểm tra transition nghiệp vụ và audit.

## Thang điểm 0–10

Làm rõ 1; tracking/isolation chính xác 3; cơ chế concurrency 2; bằng chứng và test 2; trade-off và trình bày 2.

# Câu 2 — Sau rollout, Akamai trả trang cũ dù CMS đã publish

**Loại câu hỏi:** Production incident — Optimizely CMS, Akamai, HTTP caching, SEO  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** CDN cache keys, purge, HTTP headers, CMS publish, incident response, observability

## Bối cảnh

Website marketing sử dụng Optimizely CMS và Akamai. Sau khi publish chiến dịch, người dùng ở một số vùng thấy nội dung cũ 20–40 phút; editor thấy bản mới khi preview. Một số trang tiếng Việt trả canonical URL của trang tiếng Anh. Origin CPU bình thường, cache hit ratio cao. Rollback deployment không làm tình trạng biến mất. Chưa rõ cơ chế purge, cache key theo locale, cookies, query string và cách SSR tạo canonical.

## Câu hỏi chính

Bạn sẽ ổn định tác động kinh doanh, phân biệt các giả thuyết, chứng minh root cause và triển khai biện pháp ngắn hạn/dài hạn như thế nào mà không purge toàn CDN tùy tiện?

## Câu hỏi làm rõ nên cân nhắc

1. Publish webhook có được nhận và ack không; có retry hay DLQ không?
2. Cache key có chứa host, path, locale, query và vary headers nào?
3. Trang public có personalized content hay cookies ảnh hưởng render không?
4. TTL, stale-while-revalidate và origin Cache-Control được cấu hình ở đâu?
5. Canonical được render tại origin, edge hay client?

## Gợi ý tư duy

### Gợi ý 1

Preview thường bypass các lớp cache của public delivery.

### Gợi ý 2

So sánh cùng URL tại origin, edge và từng POP.

### Gợi ý 3

Phân biệt lỗi invalidation với cache key thiếu biến thể và lỗi render metadata.

## Cấu trúc trả lời đề xuất

Định lượng impact → tạm thời bảo vệ các URL quan trọng → thu thập header/POP/timestamp → lập giả thuyết → test đối chứng origin/edge → fix → verify đa vùng → guardrail.

## Ý chính của câu trả lời tốt

### Bắt buộc

Kiểm tra `Age`, `Cache-Control`, `Vary`, Akamai cache status, POP, publish timestamp, purge response; kiểm tra canonical tại origin và edge; không mặc định CPU thấp chứng minh origin đúng.

### Điểm cộng

Kiểm tra stale policy, race giữa publish và purge, surrogate keys, locale key, cookie bypass và conditional requests.

### Senior+

Đề xuất contract publish→invalidate có idempotency, retry, audit, canary và SEO regression gates.

## Hướng giải quyết tham khảo

**Impact:** phân loại landing pages và chiến dịch có rủi ro thông tin sai; đo tỷ lệ URL/POP lỗi, SEO canonical sai và thời gian từ publish đến public. **Stabilize:** purge chọn lọc URL/keys bị ảnh hưởng nếu được phép; tạm giảm TTL cho nhóm nội dung thay đổi nhanh, không purge toàn bộ nếu chưa đánh giá origin load. **Evidence:** lưu response headers, body hash, canonical và thời gian tại edge nhiều POP; đối chiếu origin trực tiếp (đúng Host/locale, bypass CDN an toàn), CMS publish logs, webhook/queue logs, Akamai purge request IDs và kết quả. **Hypotheses:** webhook không gửi/không retry; purge sai key; cache key thiếu locale; stale-while-revalidate còn phục vụ stale; canonical SSR sai ngay tại origin; propagation delay hoặc cache ở browser. Dùng ma trận URL × locale × POP × cache bypass để phân biệt. **Fix:** đồng bộ cache key với variant thực tế, chỉ cache public responses có chính sách rõ, invalidate theo content dependency (listing và detail), publish event idempotent có retry/backoff và quan sát thất bại. Canonical phải dựa vào canonical URL của từng locale, kiểm tra server-rendered HTML; không dùng client-only sửa SEO. **Verify:** test sau publish tại nhiều POP, kiểm tra stale window thực đo, origin load, Lighthouse/SEO crawl, cảnh báo purge lag và tỷ lệ mismatch. Nếu origin đã sai thì CDN purge không giải quyết; nếu personalized pages thì phải xem lại chính sách public caching.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ coi đây là incident về freshness và SEO, không mặc định do CDN. Đầu tiên xác định URL và thị trường bị ảnh hưởng, sau đó so sánh response tại origin và từng edge POP cùng headers `Age`, cache status, canonical và publish time. Nếu origin đúng nhưng edge sai, tôi truy purge pipeline, TTL và cache key theo locale; nếu origin sai, tôi điều tra CMS delivery và SSR. Có thể purge chọn lọc landing pages để giảm impact nhưng phải giám sát origin traffic. Fix dài hạn là invalidation đáng tin cậy, cache key đúng biến thể, test publish-to-public và alert khi stale vượt SLO. Trade-off là TTL thấp tăng origin load, còn TTL dài cần invalidation tốt.

## Câu hỏi đào sâu

1. Nếu purge API báo thành công nhưng một POP vẫn stale, bạn điều tra gì tiếp?
2. Khi nào bỏ CDN caching cho HTML là lựa chọn hợp lý?
3. Làm sao kiểm tra canonical/hreflang trong CI và production?

## Lỗi trả lời thường gặp

1. Purge toàn bộ mà không đánh giá tải origin.
2. Nhầm CMS preview với public origin response.
3. Chỉ nhìn cache hit ratio, bỏ qua freshness.
4. Không phân biệt canonical lỗi tại origin hay edge.
5. Đưa ra một root cause khi chưa có bằng chứng.

## Thang điểm 0–10

Impact/stabilization 2; hypotheses/evidence 3; mechanism 1; fix và verification 2; trade-offs/communication 2.

# Câu 3 — Chọn kiến trúc đồng bộ product catalog đa nguồn với search

**Loại câu hỏi:** Architecture / engineering decision — PostgreSQL, Elasticsearch, Service Bus, Vue  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** Data ownership, event-driven integration, consistency, search, rollout, cost of complexity

## Bối cảnh

Nền tảng B2B có 3 nhà cung cấp gửi product feeds theo lịch và API. PostgreSQL lưu product catalog chuẩn hóa; website Vue hiển thị tìm kiếm, lọc, giá và tồn kho. Một số feeds đến trễ, sửa lại record cũ, có duplicate và schema khác nhau. Search hiện tại dùng SQL LIKE; đội sản phẩm cân nhắc Elasticsearch và Azure Service Bus. 200 nghìn sản phẩm ban đầu, tăng trưởng chưa chắc chắn. Giá cần đúng tại checkout, search có thể trễ vài phút. Đội vận hành nhỏ, yêu cầu có rollback và trace nguồn dữ liệu.

## Câu hỏi chính

Thiết kế giải pháp có thể triển khai theo giai đoạn, giải thích khi nào giữ PostgreSQL search và khi nào bổ sung Elasticsearch/Service Bus; làm rõ consistency, data ownership, failure recovery và chi phí vận hành.

## Câu hỏi làm rõ nên cân nhắc

1. SLO p95 cho search, ingestion lag và tỷ lệ cập nhật mỗi giờ là bao nhiêu?
2. Có multilingual relevance, typo tolerance, faceting, autocomplete không?
3. Nguồn nào thắng khi feeds mâu thuẫn, và dữ liệu có version/timestamp đáng tin không?
4. Giá/tồn kho được xác thực lại ở checkout như thế nào?
5. Ràng buộc ngân sách, compliance và kỹ năng vận hành search/queue?

## Gợi ý tư duy

### Gợi ý 1

Đừng biến search index thành source of truth.

### Gợi ý 2

Tách ingestion, canonical product model và read model.

### Gợi ý 3

Định nghĩa replay và idempotency trước khi chọn message broker.

## Cấu trúc trả lời đề xuất

Xác định SLO/invariants → phân chia ownership → thiết kế ingestion & canonical storage → read path → failure/replay → bảo mật/observability → staged rollout & alternatives.

## Ý chính của câu trả lời tốt

### Bắt buộc

PostgreSQL là source of truth; ingestion có dedupe, validation, supplier mapping và provenance; search eventual consistency; checkout revalidate giá/tồn kho; giải thích SQL index/full-text trước Elasticsearch.

### Điểm cộng

Outbox hoặc change-feed thích hợp, version ordering, reindex alias/cutover, poison records, backpressure, zero-downtime migrations.

### Senior+

SLO-based architecture decision record, capacity test, rollback plan, operational runbook và threat model.

## Hướng giải quyết tham khảo

**Giả định:** search freshness chấp nhận vài phút; checkout cần dữ liệu giá/tồn kho mới nhất từ nguồn có thẩm quyền. Thiết kế modular monolith trước: adapter từng supplier đưa raw feed vào blob/object storage có checksum, source ID và import batch; parse/validate theo schema version, canonicalize SKU và ghi PostgreSQL bằng upsert có khóa tự nhiên + source version/timestamp và conflict policy minh bạch. Bảng `SupplierOffer` giữ provenance, `Product` canonical; không gộp giá/tồn kho thiếu quy tắc. Transaction ghi dữ liệu và outbox event cho thay đổi; worker đọc outbox, cập nhật read model/search với idempotency theo entity/version, retry backoff và DLQ/quarantine cho bản ghi hỏng. Nếu PostgreSQL `tsvector`/GIN + indexes đáp ứng relevance/filter/p95, giữ SQL để giảm complexity; nếu cần typo tolerance, multilingual analyzers, faceting phức tạp và SQL không đạt benchmark, thử Elasticsearch với shadow indexing, dual-read comparison, alias-based cutover và full reindex. Service Bus hữu ích nếu nhiều consumers, bursts hoặc cần decouple; với workload nhỏ có thể dùng durable DB job/outbox trước. Search chỉ là projection eventual-consistent; checkout kiểm tra lại authoritative offer và xử lý conflict. API `/products?cursor=...` có filter/sort allowlist, tenant authorization, giới hạn page size; không dùng client-provided price. Vue xử lý abort requests, loading/error và version mismatch. Metrics: feed age, validation reject rate, outbox lag, index lag, search p95, checkout mismatch, DLQ, supplier failure. Deploy theo canary, feature flag và rollback read path; bảo đảm replay từ raw feeds/outbox.

## Mẫu trả lời trong phỏng vấn

> Tôi sẽ không chọn Elasticsearch hay Service Bus ngay. Tôi xác nhận SLO tìm kiếm và yêu cầu relevance trước. PostgreSQL giữ canonical catalog và provenance; ingestion phải idempotent, version-aware, lưu raw feed để replay. Search là read model có thể trễ, còn checkout phải xác thực lại giá và tồn kho. Nếu full-text PostgreSQL đạt benchmark thì giữ hệ đơn giản. Khi nhu cầu autocomplete, relevance và faceting vượt khả năng hoặc hiệu năng đã đo, tôi thêm Elasticsearch theo shadow index và feature flag. Service Bus chỉ được đưa vào khi cần decouple consumers và hấp thụ burst; đổi lại có duplicate, retry và vận hành DLQ. Tôi sẽ theo dõi lag, mismatch, p95 và chuẩn bị rollback đường đọc.

## Câu hỏi đào sâu

1. Nếu supplier gửi bản cập nhật cũ sau bản mới, bạn xác định thứ tự đúng thế nào?
2. Nếu Elasticsearch outage 2 giờ, bạn giữ chức năng tìm kiếm ra sao?
3. Nếu chỉ có một engineer trực vận hành, bạn bỏ bớt thành phần nào?

## Lỗi trả lời thường gặp

1. Đưa giá trong search index thành giá checkout đáng tin.
2. Dùng timestamp của server nhận feed để kết luận version nguồn.
3. Chọn microservices/broker/search cluster mà không có SLO.
4. Không có replay, provenance hoặc reindex.
5. Không có phương án rollback read path.

## Thang điểm 0–10

Requirements/invariants 2; data/consistency 2; alternatives/trade-offs 2; failure/replay 2; testing/observability/communication 2.
