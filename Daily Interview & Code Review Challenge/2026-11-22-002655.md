# Câu 1 — Vì sao request đọc dữ liệu lớn làm tăng GC pause dù SQL nhanh?

**Loại câu hỏi:** Internal mechanism + practical runtime behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET 8, allocation, LOH, GC, ASP.NET Core response streaming, profiling

## Bối cảnh

Một ASP.NET Core API xuất dữ liệu giao dịch cho hệ thống nội bộ. Mỗi request truy vấn khoảng 40.000 bản ghi từ SQL Server; SQL execution time chỉ 180 ms nhưng p99 API tăng từ 800 ms lên 8 giây khi 40 người xuất báo cáo đồng thời. Memory usage tăng nhanh, Gen 2 GC xuất hiện dày, đôi khi container bị restart. Code hiện tại lấy toàn bộ rows bằng `ToListAsync()`, map sang DTO, `JsonSerializer.Serialize(...)` thành chuỗi rồi trả `Content(json, "application/json")`. Yêu cầu giữ JSON contract và có thể giới hạn số lượng xuất.

## Câu hỏi chính

Hãy giải thích cơ chế allocation/GC và request pipeline có thể tạo ra triệu chứng trên; thiết kế cách chứng minh giả thuyết và cải tiến mà không làm hỏng response hoặc làm tăng tải SQL quá mức.

## Câu hỏi làm rõ nên cân nhắc

1. Kích thước JSON thực tế mỗi lần xuất và phân phối p50/p95/p99?
2. Giới hạn memory/container, GC mode và thời điểm restart?
3. Client cần tải trọn JSON hay hỗ trợ pagination, NDJSON hoặc file download?
4. SQL query có streaming thực sự hay provider buffering/retry strategy?
5. Có yêu cầu snapshot consistency và xử lý client disconnect không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt thời gian database và thời gian giữ dữ liệu trong managed heap.

### Gợi ý 2
Xem xét `List<T>`, DTO, chuỗi JSON, UTF-16, buffer và Large Object Heap.

### Gợi ý 3
Đo allocations/request, GC pause, `dotnet-counters`, trace và streaming end-to-end; lưu ý stream không tự động bảo đảm consistency.

## Cấu trúc trả lời đề xuất

1. Xác nhận triệu chứng và giới hạn.
2. Vẽ đường đi dữ liệu từ SQL → EF Core → DTO → serializer → HTTP.
3. Ước lượng peak live memory khi nhiều request cùng chạy.
4. Thu thập runtime counters và trace để phân biệt GC, CPU, I/O, ThreadPool.
5. Đề xuất cải tiến theo mức độ can thiệp.
6. Kiểm chứng contract, cancellation, tải và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc
Giải thích `ToListAsync` materialization, nhiều bản sao dữ liệu, JSON string allocation, LOH với object đủ lớn, Gen 2/GC pressure; không kết luận GC là root cause chỉ vì có Gen 2. Đo trước và sau.

### Điểm cộng
Projection trực tiếp, `AsNoTracking`, `AsAsyncEnumerable`, `JsonSerializer.SerializeAsync`, `CancellationToken`, giới hạn concurrent exports, backpressure, paging/keyset, kiểm thử client disconnect.

### Senior+
Nhận diện trade-off giữa consistency, query lifetime, database connection occupancy và streaming; cân nhắc tạo file export bất đồng bộ trên Blob Storage cho job lớn thay vì giữ HTTP request.

## Hướng giải quyết tham khảo

**Giả định cần xác minh:** API đang tạo đồng thời danh sách entity, danh sách DTO và một JSON string lớn. `ToListAsync` buộc materialize kết quả; `Serialize` tạo string riêng. Chuỗi lớn có thể được cấp phát trên LOH (ngưỡng kích thước object khoảng 85 KB), làm tăng áp lực GC và peak live set. Gen 2 collections không mặc nhiên là bằng chứng GC gây ra toàn bộ latency; cần GC pause duration, allocation rate, heap size và trace correlation.

**Đo lường:** Gắn `Activity`/Application Insights cho SQL, mapping, serialization và response writing; thu `dotnet-counters monitor System.Runtime` với allocation rate, GC heap size, Gen 2 GC count, time in GC; lấy memory dump khi được phép và profiling dưới tải đại diện. Đối chiếu p99 với GC pauses và container restarts. Xem SQL connection occupancy, query plan và thời gian đọc toàn bộ rows, không chỉ execution time trên server.

**Cải tiến có điều kiện:** Trước hết giới hạn số dòng và concurrent exports; dùng `Select` projection để chỉ lấy cột cần thiết, `AsNoTracking` khi read-only. Nếu contract là JSON array và client hỗ trợ chunked transfer, serialize trực tiếp ra `Response.Body` bằng `JsonSerializer.SerializeAsync` trên `IAsyncEnumerable<ExportRow>` với cancellation, kiểm chứng EF Core provider/strategy không buffer toàn bộ dữ liệu. Tránh viết JSON thủ công vì nguy cơ escaping và partial malformed response. Streaming giảm buffering ở application nhưng giữ database connection lâu hơn và có thể phát response không hoàn chỉnh khi lỗi giữa stream. Không thể đổi status code sau khi response đã bắt đầu. Nếu cần snapshot nhất quán qua nhiều phút, cần chiến lược snapshot/isolation phù hợp, không mặc định stream đảm bảo. Với exports rất lớn, queue background job, lưu file trong Blob Storage với access control và TTL, trả `202 Accepted` + status endpoint.

**Trade-offs:** Pagination giảm peak memory nhưng đổi API contract; async export tăng hạ tầng và eventual completion; concurrency limit tăng queue wait; streaming cải thiện memory nhưng kéo dài transaction/connection lifetime. Thử với dataset skew, slow client, cancellation, high concurrency, response validation và rollback theo feature flag. Theo dõi allocated bytes/request, GC pause p99, export duration, failure ratio, SQL connections, throttled requests.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không vội tăng RAM hay thêm Redis vì SQL 180 ms chưa giải thích tổng latency. Tôi tách thời gian truy vấn, materialization, mapping, serialization và network write, rồi đo allocation và GC pause tương ứng với p99. Với `ToListAsync` và `Serialize`, một request có thể giữ nhiều bản sao của cùng dataset; 40 request làm peak heap tăng mạnh. Nếu profiling xác nhận, tôi giảm dữ liệu materialize bằng projection, cân nhắc serialize trực tiếp từ async stream, giới hạn số exports đồng thời và xử lý cancellation. Tuy nhiên streaming có thể giữ connection lâu và trả JSON dở dang khi lỗi, nên cần kiểm thử client chậm và contract. Nếu báo cáo quá lớn, tôi chọn background export sang Blob Storage, theo dõi queue, TTL và quyền tải. Tôi quyết định dựa trên benchmark p95/p99, allocation và database impact.”

## Câu hỏi đào sâu

1. Nếu bật EF Core retrying execution strategy khiến query buffer nội bộ, bạn kiểm tra và điều chỉnh thế nào?
2. Khi client ngắt kết nối sau khi nhận 30% JSON, làm sao bảo đảm không còn query chạy vô ích?
3. Nếu business yêu cầu một snapshot nhất quán của 40.000 dòng trong khi dữ liệu thay đổi liên tục, streaming có còn phù hợp?

## Lỗi trả lời thường gặp

- Đồng nhất SQL execution time với end-to-end query duration.
- Khẳng định mọi object lớn đều nằm LOH mà không xét kích thước.
- Tuyên bố `IAsyncEnumerable` chắc chắn không buffer ở mọi layer.
- Tăng heap/container limit mà không kiểm tra concurrency và allocations.
- Bỏ qua cancellation, slow clients và tính toàn vẹn response.

## Thang điểm 0–10

|---|---:|
| Làm rõ workload và contract | 1 |
| Giải thích runtime/allocation chính xác | 2 |
| Đề xuất bằng chứng và phân biệt giả thuyết | 2 |
| Thiết kế tối ưu thực tế | 2 |

# Câu 2 — Sau release, trang CMS trả 200 nhưng canonical sai và traffic organic giảm

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai CDN, SEO engineering, Azure App Service, observability, release investigation

## Bối cảnh

Một marketing website đa ngôn ngữ dùng Optimizely CMS trên ASP.NET Core, Azure App Service và Akamai CDN. Sau release routing/canonical URL, trang sản phẩm ở `/vi-vn/products/...` đôi khi trả canonical trỏ về `/en-us/...`; một số URL mới redirect nhiều bước, sitemap vẫn liệt kê URL cũ. HTTP 200 và API health checks bình thường. Product báo lượng truy cập organic giảm; chưa có dữ liệu chứng minh mức giảm do SEO hay do tracking. Có 3 App Service instances, CDN cache HTML, CMS editors tiếp tục publish nội dung.

## Câu hỏi chính

Bạn sẽ điều phối incident, khoanh vùng lỗi và triển khai remediation an toàn thế nào để bảo vệ crawlability và tránh phá vỡ cache, routing, content publishing?

## Câu hỏi làm rõ nên cân nhắc

1. Thời điểm bắt đầu sai lệch so với deployment, CDN purge và CMS publish?
2. Canonical/hreflang/redirect thay đổi theo host, locale, query string, cookie hay user agent?
3. HTML được cache theo key nào, có vary theo host/locale không?
4. Có bằng chứng từ access logs, Google Search Console hoặc analytics về crawl/indexing chưa?
5. Có rollback route config độc lập với schema/content model không?

## Gợi ý tư duy

### Gợi ý 1
Health check 200 không chứng minh nội dung HTML và SEO metadata đúng.

### Gợi ý 2
Phân biệt origin response, edge cache và browser; kiểm tra cache key, redirects, canonical/hreflang.

### Gợi ý 3
Lấy ma trận URL × locale × host × cache hit/miss, so sánh trước/sau release, triển khai canary và targeted purge.

## Cấu trúc trả lời đề xuất

1. Impact và incident severity.
2. Stabilization không làm mất content.
3. Thu evidence từ origin/CDN/analytics.
4. Ít nhất ba competing hypotheses.
5. Thử nghiệm cô lập nguyên nhân.
6. Root cause có chứng cứ.
7. Hotfix/rollback/purge có kiểm soát.
8. Regression tests, release gates, monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không suy diễn organic traffic giảm chỉ từ tương quan; kiểm tra canonical thực tế, redirects, sitemap, locale và edge/origin. Cân nhắc rollback và purge có chọn lọc.

### Điểm cộng
So sánh HTML của cache HIT/MISS, URL inspection, crawler, App Insights, edge response headers, Playwright smoke tests, 301/302 semantics và canonical absolute URLs.

### Senior+
Phân biệt SEO impact có độ trễ với tracking outage; kế hoạch cache invalidation tránh thundering herd, multi-locale regression matrix, ownership giữa CMS/CDN/frontend/release team.

## Hướng giải quyết tham khảo

**Impact:** Xác định số URL/locale ảnh hưởng, tỷ lệ canonical sai và redirect chains; không tuyên bố mất ranking khi chưa có dữ liệu indexing. Ưu tiên trang có traffic cao, URL indexable, đường dẫn checkout không bị ảnh hưởng.

**Stabilize:** Freeze thay đổi routing/canonical và publish liên quan trong phạm vi cần thiết; nếu lỗi xuất hiện ngay sau release, đánh giá rollback artifact/config khi compatible với content schema. Tránh purge toàn bộ CDN không kiểm soát vì có thể tăng origin load. Nếu fix nhỏ, canary trước rồi targeted invalidate các path liên quan.

**Evidence:** Lấy response `curl -I -L` và HTML thực tế từ edge và origin theo host/locale, ghi lại `Cache-Control`, `Age`, CDN cache status (nếu được cấu hình), `Location`, canonical, hreflang, robots, sitemap entries. So sánh kết quả trên từng instance/deployment slot nếu có thể. Truy vấn Application Insights cho request path, redirect status, dependency errors và correlation; CMS publish logs để đối chiếu content version. Kiểm tra Search Console coverage/indexing và analytics tag firing để phân biệt indexing vs measurement.

**Competing hypotheses:** (A) route generator dùng default locale khi request thiếu culture context; (B) CDN cache key không phân biệt host/locale nên phục vụ HTML sai; (C) canonical helper tạo absolute URL sai scheme/host sau reverse proxy; (D) sitemap job còn dùng route mapping cũ; (E) analytics regression gây ảo giác traffic giảm. Thử cache bypass và direct origin; cùng một URL với HIT/MISS; kiểm tra forwarded headers config và locale resolver; kiểm tra sitemap generation version.

**Remediation:** Chỉ sửa giả thuyết được xác nhận. Nếu origin sai, sửa locale-aware URL generation và trusted forwarded headers; nếu edge sai, sửa cache-key/TTL/vary strategy theo chính sách Akamai thực tế; nếu sitemap sai, regenerate và kiểm tra URL canonical. Đảm bảo canonical self-reference hoặc trỏ đúng preferred URL theo chính sách SEO, hreflang reciprocal khi cần, redirects không tạo loop/chain và 404/410 phù hợp. Deploy canary, targeted purge, kiểm tra origin capacity và rollback. Không giả định purge xóa browser cache.

**Prevention:** Integration tests cho route generation, Playwright crawling ma trận locale × host × content type, sitemap vs canonical consistency, synthetic probes kiểm tra HTML semantics chứ không chỉ 200, release gate kiểm tra cache HIT/MISS, dashboard canonical mismatch rate, redirect chain length, cache hit ratio, 5xx, crawl metrics và alert. Kết luận root cause chỉ sau khi đối chiếu bằng chứng.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xem đây là incident về tính đúng đắn của nội dung, không chỉ availability. Trước tiên tôi đo phạm vi URL bị canonical sai, kiểm tra redirect chain và xác nhận organic drop có phải tracking hay indexing. Tôi so sánh cùng URL tại CDN và origin, với locale/host khác nhau và cache HIT/MISS để tách lỗi route generator khỏi cache key. Nếu xác nhận regression sau release, tôi cân nhắc rollback hoặc hotfix canary và purge chọn lọc, tránh làm quá tải origin. Tôi kiểm tra sitemap, hreflang, canonical và status code bằng automated crawler trước khi mở rollout. Cuối cùng tôi bổ sung synthetic SEO checks và telemetry theo locale để lỗi 200-but-wrong-content được phát hiện sớm.”

## Câu hỏi đào sâu

1. Nếu origin đúng nhưng CDN HIT sai chỉ ở một số quốc gia, bạn thiết kế thử nghiệm nào?
2. Nếu rollback code làm content type mới không tương thích, bạn giảm tác động bằng phương án nào?
3. Nếu Product yêu cầu purge toàn bộ CDN ngay, bạn đánh giá rủi ro và thuyết phục bằng số liệu gì?

## Lỗi trả lời thường gặp

- Coi HTTP 200 là bằng chứng SEO khỏe mạnh.
- Khẳng định organic traffic giảm do canonical mà chưa loại trừ tracking.
- Purge tất cả cache ngay mà không ước lượng origin load.
- Chỉ sửa sitemap, bỏ qua canonical/hreflang/redirect.
- Không kiểm tra khác biệt giữa edge, origin và browser.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Xác định impact và clarification | 1.5 |
| Stabilization và rollback judgment | 1.5 |
| Competing hypotheses + evidence | 2.5 |
| SEO/CDN/CMS technical depth | 2 |

| Incident communication | 0.5 |

# Câu 3 — Chọn kiến trúc tích hợp dữ liệu giá sản phẩm với Cosmos DB hay SQL Server?

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** SQL Server, Cosmos DB, Azure Functions, Azure Service Bus, API design, consistency, idempotency, architecture trade-offs

## Bối cảnh

Một e-commerce platform nhận price updates từ 12 nhà cung cấp qua REST/webhook. Mỗi supplier có format riêng, gửi cập nhật trễ hoặc trùng; đôi khi cùng SKU có hai update đến sai thứ tự. Hệ thống phải lưu lịch sử giá để audit, trả giá hiện hành qua ASP.NET Core API, và phát sự kiện khi giá thay đổi. Peak giả định 1.000 updates/phút, 3 triệu SKU, 3 vùng địa lý đọc dữ liệu; SLA đọc giá 99.9% và yêu cầu không hiển thị giá chưa được phê duyệt. Team đang dùng SQL Server/Azure App Service, có thể cân nhắc Cosmos DB, Azure Functions, Service Bus, nhưng không muốn tăng operational complexity không cần thiết. Chưa rõ latency, consistency và quy định data residency.

## Câu hỏi chính

Bạn sẽ thiết kế ingestion, approval, current-price read model, audit và event publishing thế nào; khi nào giữ SQL Server, khi nào bổ sung Cosmos DB hoặc messaging, và cách chứng minh quyết định?

## Câu hỏi làm rõ nên cân nhắc

1. Giá được duyệt tự động hay cần manual approval; SLA từ approval tới read API?
2. Supplier cung cấp sequence/version hay chỉ timestamp có thể không tin cậy?
3. SKU unique theo supplier, tenant, region, currency hay catalog toàn cục?
4. Read QPS, phân bố hot SKUs, yêu cầu read-your-writes và multi-region write?
5. Audit retention, compliance, budget, RPO/RTO và data residency?

## Gợi ý tư duy

### Gợi ý 1
Tách raw supplier input, approved state và customer-visible price.

### Gợi ý 2
Sự kiện trùng/đảo thứ tự cần xử lý tại data boundary; queue không tự tạo exactly-once.

### Gợi ý 3
So sánh SQL transactions/constraints/outbox với Cosmos partition key, RU, consistency và read locality dựa trên workload đo được.

## Cấu trúc trả lời đề xuất

1. Chốt invariant và non-functional requirements.
2. Thiết kế ownership và data model.
3. Ingestion, validation, approval, deduplication và ordering.
4. Transaction/event boundary.
5. Read API, indexing, caching, multi-region.
6. Đánh giá SQL-only, SQL+messaging, Cosmos alternatives.
7. Security, telemetry, rollout và failure recovery.

## Ý chính của câu trả lời tốt

### Bắt buộc
Giữ giá chưa duyệt ngoài public read model; deduplicate theo supplier event ID/version; xử lý stale updates; atomic approval/current-price transition; audit; failure-safe publishing; không mặc định Cosmos hoặc microservices là bắt buộc.

### Điểm cộng
Inbox/outbox, unique constraints, optimistic concurrency, Service Bus DLQ, replay, partition-key modeling, cost/RU benchmark, Managed Identity, schema versioning.

### Senior+
Tách consistency invariant theo aggregate, data residency, migration dual-read/dual-write risks, failover and reconciliation, explicit SLOs, cost of complexity.

## Hướng giải quyết tham khảo

**Assumptions:** Chưa có yêu cầu multi-region active-active writes hay latency dưới 50 ms. Trước mắt SQL Server là system of record; không quyết định Cosmos DB chỉ vì 3 triệu SKU. Supplier update chưa được duyệt không được ghi đè bảng giá public.

**Data model:** `SupplierPriceEvent(SupplierId, ExternalEventId, Sku, Currency, Price, SourceVersion, ReceivedAt, PayloadHash, Status)` có unique constraint theo supplier/event ID; `PriceProposal` có approval status và metadata; `CurrentPrice(Sku, Market, Currency, Price, ApprovedVersion, UpdatedAt, RowVersion)`; `PriceAudit` append-only; `Outbox` lưu domain event trong cùng transaction cập nhật giá. Nếu supplier không có version đáng tin, cần policy xử lý xung đột (review/manual reconciliation), không lấy arrival time làm business truth vô điều kiện.

**Ingestion:** Webhook xác thực chữ ký/identity, giới hạn payload, rate limit, schema validation và lưu idempotently. Với peak 1.000/phút, ASP.NET Core + SQL có thể đủ nếu benchmark chứng minh; queue giúp absorb bursts và cô lập supplier downtime, không tự đảm bảo thứ tự hay exactly-once. Nếu dùng Service Bus, consumer idempotent, retry có giới hạn, DLQ và operator replay. Với order per SKU, chỉ dùng sessions nếu throughput/ordering requirements biện minh, và vẫn kiểm tra source version. Không trộn update của nhiều supplier nếu chưa có priority/price selection policy.

**Approval:** Transaction kiểm tra proposal/version, ghi current price, audit và outbox. Optimistic concurrency hoặc row-level locking + unique constraints ngăn approve trùng. Outbox dispatcher publish at-least-once; consumer có inbox/dedup. Nếu external event publish thất bại, trạng thái SQL vẫn đúng và outbox sẽ retry. Cần monitor outbox lag và replay, không gửi event trong transaction trước commit.

**Reads:** API đọc current approved price theo SKU/market/currency với covering index theo query shape. Nếu p95/QPS cần, thử read replicas/cache với invalidation và stale-price policy; không cache giá chưa duyệt. Trường hợp giá phải strong-consistent ngay sau approval, route đọc đến authoritative store hoặc enforce version check; cache eventual consistency phải được Product chấp thuận.

**Cosmos option:** Chỉ cân nhắc nếu benchmark chứng minh nhu cầu global distribution, access patterns phù hợp partition key, latency/cost/operational trade-off tốt hơn SQL. Partition key ví dụ `tenant-or-market + sku bucket` cần kiểm thử cardinality, hot partitions, cross-partition query, RU, item size và consistency options. Cosmos không thay thế approval invariants tự động, và giao dịch bị giới hạn bởi partition scope; multi-region conflict resolution cần thiết kế riêng. Có thể dùng Cosmos làm derived read model đồng bộ từ outbox, nhưng làm tăng eventual consistency và reconciliation burden.

**Rollout:** Bắt đầu modular monolith + SQL + outbox, optional Service Bus cho ingestion spikes; feature flag shadow read nếu thử Cosmos, compare price/version, rollback theo source of truth, load test 1.000/min và bursts cao hơn, chaos tests với queue outage, duplicate/out-of-order events, approval race, DB failover, replay và supplier invalid payload. Security: secrets trong Key Vault, Managed Identity khi phù hợp, RBAC cho approval, audit actor và PII minimization. Metrics: ingest latency, duplicate/stale rate, approval-to-visible p95, outbox age, DLQ depth, query p99, SQL waits, RU/partition utilization nếu Cosmos.

**Điều kiện đổi quyết định:** Nếu đa vùng bắt buộc local reads với latency thấp, data sovereignty hoặc active-active writes, thiết kế lại data placement/consistency dựa trên số đo và business invariants. Nếu volume thấp, queue có thể không đáng giá; nếu supplier burst lớn, buffer có giá trị.

## Mẫu trả lời trong phỏng vấn

“Tôi bắt đầu từ invariant: giá chưa duyệt không được xuất hiện trong API. Tôi tách raw supplier event, proposal, approved current price và audit. Với quy mô hiện tại, SQL Server có transaction, constraint và index phù hợp, nên tôi chưa thêm Cosmos DB. Tôi dùng idempotency key và version check để xử lý duplicate/out-of-order, ghi current price cùng audit và outbox trong một transaction, rồi publish sự kiện với retry và consumer dedup. Nếu burst làm ingestion ảnh hưởng API, Service Bus có thể buffer; cần DLQ, replay và metrics. Tôi benchmark p95 reads, write contention, SQL cost và multi-region latency trước khi thử Cosmos làm read model. Trade-off của Cosmos là RU, partitioning và eventual consistency; tôi chỉ chọn khi yêu cầu thực tế bù được độ phức tạp. Tôi kiểm thử race approval, duplicate, outage và reconciliation trước production.”

## Câu hỏi đào sâu

1. Nếu supplier không cung cấp event ID/version và có thể gửi giá cũ sau giá mới, bạn xác định đúng-sai thế nào?
2. Nếu business bắt buộc multi-region active-active approval với consistency mạnh, bạn thay đổi thiết kế ra sao?
3. Nếu outbox backlog kéo dài 20 phút trong khi API trả giá mới ngay, downstream consumers nên xử lý SLA và reconciliation thế nào?

## Lỗi trả lời thường gặp

- Chọn Cosmos DB chỉ dựa trên số lượng SKU.
- Giả định Service Bus bảo đảm exactly-once và global ordering.
- Cho supplier webhook ghi thẳng vào public current price.
- Gửi event trước khi transaction commit mà không có recovery.
- Thiếu approval race tests, cost modeling và data residency.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Runtime:** Phân biệt allocation/GC pressure với SQL time; tối ưu theo profile và cân nhắc response streaming, connection lifetime, cancellation.
- **Production:** HTTP 200 không chứng minh canonical, hreflang, sitemap và CDN cache đúng; điều tra bằng chứng theo origin/edge/locale.
- **Architecture:** Xác định business invariant trước khi chọn SQL, Cosmos DB hoặc Service Bus; thiết kế approval, idempotency và outbox như một hệ thống.

## Mẫu tư duy cần nhớ

1. **Measure before optimize:** Liên kết latency với allocations, GC pauses, SQL, network bằng telemetry.
2. **Stabilize before deep investigation:** Hạn chế blast radius và giữ đường rollback khả thi.
3. **Separate correctness from availability:** API 200 vẫn có thể phục vụ nội dung sai.
4. **Design retry together with idempotency:** Duplicate/out-of-order là điều kiện bình thường trong tích hợp phân tán.
5. **Choose the simplest architecture meeting invariants:** Chỉ thêm distributed components khi workload/SLO chứng minh lợi ích.
