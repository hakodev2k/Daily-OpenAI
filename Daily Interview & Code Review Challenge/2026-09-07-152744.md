# Code Review Challenge 1 — Scheduled job chạy 4 lần sau scale-out và tạo duplicate invoice

**Chủ đề:** C#/.NET, BackgroundService, async/concurrency, horizontal scaling, SQL Server, distributed coordination, idempotency, graceful shutdown, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một enterprise billing platform chạy ASP.NET Core .NET 8 trên Azure App Service. Ứng dụng có một `BackgroundService` chạy mỗi phút để tìm các invoice đến hạn và gửi chúng sang third-party billing API.

Ban đầu production chỉ chạy 1 instance nên hệ thống có vẻ ổn. Sau khi scale-out lên 4 instances để xử lý traffic web, team ghi nhận:

- cùng một invoice đôi khi được gửi tới billing provider 2–4 lần;
- database có nhiều row `InvoiceAttempt` cho cùng invoice trong cùng phút;
- một số invoice bị xử lý lại sau deployment/restart;
- khi billing provider chậm, số task đồng thời tăng và SQL connection usage tăng mạnh;
- `OperationCanceledException` xuất hiện khi deployment nhưng log bị ghi như error;
- support không biết instance nào đã xử lý invoice nào;
- team đề xuất dùng `SemaphoreSlim(1,1)` để “bảo đảm chỉ một job chạy trên toàn hệ thống”.

Implementation hiện tại:

## Đoạn code cần review

```csharp
public sealed class InvoiceScheduler : BackgroundService
{
    private static readonly SemaphoreSlim Gate = new(1, 1);

    private readonly IServiceProvider _services;
    private readonly ILogger<InvoiceScheduler> _logger;

    public InvoiceScheduler(
        IServiceProvider services,
        ILogger<InvoiceScheduler> logger)
    {
        _services = services;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await Task.Delay(TimeSpan.FromMinutes(1));

            _ = ProcessDueInvoicesAsync();
        }
    }

    private async Task ProcessDueInvoicesAsync()
    {
        await Gate.WaitAsync();

        try
        {
            using var scope = _services.CreateScope();

            var db = scope.ServiceProvider
                .GetRequiredService<AppDbContext>();

            var billingClient = scope.ServiceProvider
                .GetRequiredService<IBillingClient>();

            var dueInvoices = await db.Invoices
                .Where(x =>
                    x.Status == InvoiceStatus.Pending &&
                    x.DueUtc <= DateTime.UtcNow)
                .OrderBy(x => x.DueUtc)
                .Take(100)
                .ToListAsync();

            await Parallel.ForEachAsync(
                dueInvoices,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = 20
                },
                async (invoice, cancellationToken) =>
                {
                    await billingClient.SendAsync(
                        invoice.Id,
                        invoice.Total,
                        CancellationToken.None);

                    invoice.Status = InvoiceStatus.Sent;

                    db.InvoiceAttempts.Add(new InvoiceAttempt
                    {
                        Id = Guid.NewGuid(),
                        InvoiceId = invoice.Id,
                        CreatedUtc = DateTime.UtcNow
                    });
                });

            await db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Invoice scheduler failed");
        }
        finally
        {
            Gate.Release();
        }
    }
}
```

## Kết quả code review tham khảo

### Critical — `SemaphoreSlim` chỉ đồng bộ trong một process

**Vấn đề:**  
`static SemaphoreSlim` chỉ được chia sẻ giữa các threads trong cùng application process.

**Tại sao xảy ra:**  
Mỗi App Service instance/process có memory riêng. Mỗi process có một `Gate` riêng.

**Ảnh hưởng production:**  
Khi chạy 4 instances, cả 4 có thể cùng query các invoice `Pending` và cùng gửi một invoice.

**Cách sửa:**  
Không coi in-memory lock là distributed lock. Ưu tiên thiết kế work claiming/idempotency ở durable store. Ví dụ atomic update từ `Pending` sang `Processing` với concurrency token/lease và chỉ instance claim thành công mới xử lý.

---

### Critical — External billing side effect không idempotent với database state

**Vấn đề:**  
Billing API được gọi trước khi trạng thái `Sent` được commit vào SQL Server.

**Tại sao xảy ra:**  
External API và SQL Server không nằm trong cùng local transaction.

**Ảnh hưởng production:**  
Billing provider có thể xử lý thành công, nhưng process crash hoặc `SaveChangesAsync` fail. Invoice vẫn là `Pending`, nên lần sau sẽ gửi lại.

**Cách sửa:**  
Dùng stable idempotency key nếu billing provider hỗ trợ, ví dụ invoice ID/business operation ID. Lưu workflow state rõ ràng (`Pending → Processing → Sent/Failed`) và thiết kế reconciliation cho trạng thái không chắc chắn. Nếu provider không có idempotency semantics, phải nêu rõ giới hạn guarantee và có cơ chế business reconciliation.

---

### Critical — `DbContext` bị dùng đồng thời trong `Parallel.ForEachAsync`

**Vấn đề:**  
Nhiều iterations cùng dùng một scoped `DbContext`, mutate tracked entities và gọi `db.InvoiceAttempts.Add(...)`.

**Tại sao xảy ra:**  
`DbContext` không được thiết kế để thực hiện nhiều operations đồng thời từ nhiều execution flows.

**Ảnh hưởng production:**  
Có thể gặp runtime exceptions, inconsistent change tracking hoặc unpredictable behavior.

**Cách sửa:**  
Không chia sẻ một `DbContext` giữa parallel workers. Có thể xử lý batch tuần tự nếu throughput đủ; hoặc mỗi claimed invoice/batch dùng scope/`DbContext` riêng với bounded concurrency. Trước khi parallelize, đo bottleneck thật.

---

### High — Fire-and-forget làm mất lifecycle control

**Vấn đề:**  
`_ = ProcessDueInvoicesAsync();` bỏ qua task.

**Tại sao xảy ra:**  
Scheduler không await work trước khi loop tiếp tục hoặc shutdown.

**Ảnh hưởng production:**  
Nhiều runs có thể overlap; exceptions có thể không được propagate đúng lifecycle; host shutdown có thể kết thúc process khi work còn chạy.

**Cách sửa:**  
Await run hiện tại hoặc dùng một bounded worker architecture rõ ràng. Nếu requirement là không overlap, loop chỉ schedule run tiếp theo sau khi run hiện tại hoàn tất.

---

### High — `Task.Delay` không truyền cancellation token

**Vấn đề:**  
`Task.Delay(TimeSpan.FromMinutes(1))` không bị cancel khi host shutdown.

**Tại sao xảy ra:**  
Delay tách khỏi `stoppingToken`.

**Ảnh hưởng production:**  
Shutdown chậm hơn và lifecycle khó predict.

**Cách sửa:**  
Dùng `await Task.Delay(interval, stoppingToken)` hoặc `PeriodicTimer` với cancellation semantics phù hợp.

---

### High — Billing call dùng `CancellationToken.None`

**Vấn đề:**  
External I/O không nhận shutdown token.

**Tại sao xảy ra:**  
Cancellation không được propagate.

**Ảnh hưởng production:**  
Deployment/restart có thể giữ request lâu hoặc terminate process giữa side effect và state update.

**Cách sửa:**  
Truyền token phù hợp, đồng thời vẫn dựa vào idempotency vì cancellation không bảo đảm external side effect chưa xảy ra.

---

### High — Query-then-process không claim ownership

**Vấn đề:**  
Nhiều instances cùng chạy query `Status == Pending`, rồi cùng nhận cùng 100 rows.

**Tại sao xảy ra:**  
Read không thay đổi durable ownership state trước processing.

**Ảnh hưởng production:**  
Duplicate processing dưới horizontal scaling là expected behavior.

**Cách sửa:**  
Dùng atomic claiming strategy. Ví dụ:

- lease fields như `ProcessingBy`, `ProcessingUntilUtc`;
- optimistic concurrency token;
- transactionally update eligible rows sang `Processing`;
- chỉ xử lý rows claim thành công;
- lease expiry/recovery cho worker crash.

Với SQL Server, implementation cụ thể phải được kiểm chứng bằng transaction/isolation/query plan phù hợp; không mặc định rằng một `SELECT` rồi `UPDATE` tách rời là atomic.

---

### High — Fixed parallelism 20 không gắn với downstream capacity

**Vấn đề:**  
Mỗi instance có thể chạy 20 billing calls; với 4 instances là khoảng 80 concurrent calls, chưa kể overlapping runs.

**Tại sao xảy ra:**  
Concurrency được cấu hình theo code thay vì measured capacity.

**Ảnh hưởng production:**  
Có thể gây throttling billing provider, SQL connection pressure, network saturation và tail latency.

**Cách sửa:**  
Đặt bounded concurrency theo rate limit/SLO/connection capacity và đo p95/p99. Có thể dùng queue/worker pool nếu cần điều tiết rõ hơn.

---

### High — Generic catch làm mất failure semantics

**Vấn đề:**  
Tất cả failure được log giống nhau.

**Tại sao xảy ra:**  
Không phân biệt cancellation, transient provider failure, permanent business rejection và database concurrency conflict.

**Ảnh hưởng production:**  
Retry strategy không chính xác; shutdown bình thường bị ghi thành lỗi; support khó RCA.

**Cách sửa:**  
Phân loại failure. `OperationCanceledException` do host shutdown không nên được xem như production defect. Permanent provider rejection cần state khác với transient timeout.

---

### Medium — Delay tạo schedule drift và không định nghĩa semantics

**Vấn đề:**  
Job “mỗi phút” thực chất là delay một phút kể từ lần loop trước, không định nghĩa catch-up hoặc skipped-run semantics.

**Tại sao xảy ra:**  
Requirement scheduler chưa rõ: fixed interval, wall-clock schedule hay continuously poll.

**Ảnh hưởng production:**  
Khi work chậm, execution timing drift; behavior sau downtime không rõ.

**Cách sửa:**  
Làm rõ requirement. Với work queue từ database, thường không cần “chính xác đúng phút”; polling bounded + durable due time có thể đủ. Nếu cần scheduler chuyên dụng, đánh giá công cụ phù hợp thay vì tự xây quá mức cần thiết.

---

### Medium — Telemetry không đủ để chứng minh duplicate source

**Vấn đề:**  
Log chỉ có lỗi scheduler chung.

**Tại sao xảy ra:**  
Không có run ID, instance ID, invoice ID, claim result, provider correlation hoặc duration.

**Ảnh hưởng production:**  
Khó biết duplicate do multi-instance claim, retry, provider ambiguity hay overlapping run.

**Cách sửa:**  
Structured logs/traces/metrics với `RunId`, `InstanceId`, `InvoiceId`, claim result, attempt number, provider idempotency key/correlation ID, duration và state transition.

## Phiên bản đề xuất

Ví dụ dưới đây chọn hướng **claim từng batch bằng durable state**, xử lý với bounded concurrency và mỗi unit of work dùng `DbContext` riêng.

```csharp
public sealed class InvoiceScheduler : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<InvoiceScheduler> _logger;

    public InvoiceScheduler(
        IServiceScopeFactory scopeFactory,
        ILogger<InvoiceScheduler> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        try
        {
            while (await timer.WaitForNextTickAsync(stoppingToken))
            {
                await ProcessBatchAsync(stoppingToken);
            }
        }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested)
        {
            _logger.LogInformation("Invoice scheduler stopping");
        }
    }

    private async Task ProcessBatchAsync(
        CancellationToken cancellationToken)
    {
        IReadOnlyList<Guid> claimedIds;

        await using (var scope = _scopeFactory.CreateAsyncScope())
        {
            var claimer = scope.ServiceProvider
                .GetRequiredService<IInvoiceClaimer>();

            claimedIds = await claimer.ClaimDueAsync(
                batchSize: 100,
                leaseDuration: TimeSpan.FromMinutes(5),
                cancellationToken);
        }

        await Parallel.ForEachAsync(
            claimedIds,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 8,
                CancellationToken = cancellationToken
            },
            async (invoiceId, token) =>
            {
                await ProcessInvoiceAsync(invoiceId, token);
            });
    }

    private async Task ProcessInvoiceAsync(
        Guid invoiceId,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();

        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var billing = scope.ServiceProvider.GetRequiredService<IBillingClient>();

        var invoice = await db.Invoices
            .SingleAsync(x => x.Id == invoiceId, cancellationToken);

        var idempotencyKey = $"invoice:{invoice.Id}";

        try
        {
            var result = await billing.SendAsync(
                invoice.Id,
                invoice.Total,
                idempotencyKey,
                cancellationToken);

            invoice.MarkSent(result.ProviderReference, DateTime.UtcNow);

            db.InvoiceAttempts.Add(
                InvoiceAttempt.Success(
                    invoice.Id,
                    idempotencyKey,
                    result.ProviderReference));

            await db.SaveChangesAsync(cancellationToken);
        }
        catch (TransientBillingException ex)
        {
            invoice.ReleaseForRetry(
                DateTime.UtcNow.AddMinutes(2),
                ex.ErrorCode);

            await db.SaveChangesAsync(cancellationToken);
        }
    }
}
```

`IInvoiceClaimer` phải thực hiện **atomic claim** ở database và có concurrency protection phù hợp. Ví dụ domain state có thể gồm:

```text
Pending
  → Processing(LeaseOwner, ProcessingUntilUtc)
      → Sent
      → Pending(nextRetryUtc)
      → FailedPermanent
```

Unique constraint hoặc concurrency token nên bảo vệ invariant cần thiết. Nếu billing provider hỗ trợ idempotency key, cùng một invoice phải reuse cùng stable key qua retries.

## Giải thích thiết kế sau khi sửa

### 1. Không dùng global scheduler lock nếu không cần

Claim từng invoice/batch cho phép nhiều instances cùng làm việc mà không duplicate ownership. Đây thường scalable hơn “chỉ một instance được chạy scheduler”.

### 2. Idempotency bảo vệ external side effect

Database claiming ngăn hai workers cùng chủ động xử lý, nhưng crash/network ambiguity vẫn có thể xảy ra. Provider idempotency key giải quyết một failure boundary khác.

### 3. Mỗi parallel unit có riêng `DbContext`

Không chia sẻ scoped mutable state giữa concurrent execution flows.

### 4. Shutdown trở thành một phần của design

Timer và I/O nhận cancellation token; cancellation bình thường được phân biệt với incident.

### 5. Lease cho phép recovery

Nếu worker chết sau claim, lease có thể hết hạn và work được reclaim theo policy. Cần tránh lease quá ngắn so với p99 processing duration.

## Trade-offs

- Claim/lease state làm schema và retry logic phức tạp hơn.
- Một distributed lock duy nhất có thể đơn giản hơn nếu workload thật sự chỉ cần một scheduler và throughput thấp, nhưng tạo single-worker bottleneck và vẫn không thay thế idempotency.
- Provider idempotency key phụ thuộc contract của provider.
- Parallelism thấp hơn có thể giảm throughput nhưng tăng reliability.
- Lease cần reconciliation cho stuck/expired work.

## Cách kiểm thử

1. **Concurrency test:** 4 worker instances cùng claim 1.000 invoices; mỗi invoice chỉ có một active owner tại một thời điểm.
2. **Crash-window test:** kill worker sau provider success nhưng trước SQL commit; retry không được tạo duplicate charge nếu provider hỗ trợ idempotency.
3. **DbContext concurrency test:** verify mỗi parallel work item dùng scope/context riêng.
4. **Shutdown test:** cancel host giữa batch; worker dừng bounded và work chưa hoàn tất có thể recovery qua lease.
5. **Load test:** đo billing concurrency, SQL pool usage, claim latency, p95/p99 và retry rate.

## Quan sát trong production

Theo dõi:

- due invoice backlog và oldest due age;
- claim success/conflict rate;
- processing lease count và expired lease count;
- provider calls, latency, timeout, throttle rate;
- duplicate/idempotency-hit count phía provider nếu có;
- SQL connection pool, lock/blocking và transaction duration;
- processing duration p50/p95/p99;
- retry count theo reason;
- instance ID/run ID;
- scheduler cancellation/shutdown duration;
- invoice state transition anomalies.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào distributed lock toàn scheduler lại hợp lý hơn per-item claiming?
2. Nếu billing provider không hỗ trợ idempotency key, bạn sẽ giảm duplicate risk và reconciliation thế nào?
3. Nếu một invoice mất 20 phút để xử lý nhưng lease chỉ 5 phút, hệ thống cần cơ chế gì?

4. đánh giá việc dùng cùng `/health` cho readiness và liveness;
5. phân tích resource requests/limits so với workload thực;
6. đánh giá image tag `latest` và rollout reproducibility;
7. xác định secret exposure;
8. phân tích graceful shutdown và rolling update;
9. đề xuất manifest/app health design tốt hơn;
10. giải thích testing, rollout validation và telemetry.

## Câu hỏi gợi mở

1. Nếu external product API chậm, có nên làm liveness probe fail và restart process không?
2. Pod dùng 400–700 MiB nhưng memory limit chỉ 256 MiB thì điều gì có thể xảy ra?
3. `readinessProbe` bắt đầu sau 2 giây trong khi startup mất 20–40 giây có tạo failure gì, và startup probe có giúp rõ semantics hơn không?
4. `image: latest` có giúp xác định chính xác binary đang chạy khi rollback/RCA không?
5. `preStop: sleep 2` có đủ cho ứng dụng cần khoảng 15 giây drain request không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **probe semantics không phản ánh application state + resource limits không dựa trên measurement + rollout không có graceful drain**.

### Gợi ý 2

Phân biệt rõ:

- process đã start;
- application đã sẵn sàng nhận traffic;
- process còn sống nhưng dependency đang degraded;
- pod đang termination và cần drain traffic.

## Kết quả code review tham khảo

### Critical — Secret được hard-code trực tiếp trong Deployment manifest

**Vấn đề:**  
Connection string chứa username/password nằm trong YAML.

**Tại sao xảy ra:**  
Configuration và secret lifecycle không được tách.

**Ảnh hưởng production:**  
Credential có thể bị lộ qua Git history, CI logs, manifest exports hoặc người có quyền đọc workload spec.

**Cách sửa:**  
Không lưu plaintext production secret trong manifest source. Dùng Kubernetes Secret hoặc external secret/identity mechanism phù hợp platform. Nếu chạy Azure và dependency hỗ trợ Microsoft Entra/Managed Identity-equivalent workload identity, đánh giá identity-based access để giảm long-lived secret. RBAC và secret access phải theo least privilege.

---

### Critical — Memory limit thấp hơn workload thực tế

**Vấn đề:**  
Pod thường dùng 250–400 MiB, đôi khi khoảng 700 MiB, nhưng limit là 256 MiB.

**Tại sao xảy ra:**  
Resource config không dựa trên measurement.

**Ảnh hưởng production:**  
Container có thể bị terminated do vượt memory limit; user nhìn thấy restart/5xx và team có thể nhầm với application bug.

**Cách sửa:**  
Đo working set/RSS, managed heap, peak dưới load và headroom cần thiết. Chọn request/limit dựa trên baseline + burst profile + node capacity. Sau đó load test lại. Không đặt limit chỉ để “tiết kiệm”.

---

### High — Readiness và liveness dùng cùng một health signal quá nông

**Vấn đề:**  
Cả hai gọi `/health`, endpoint chỉ kiểm tra process đang chạy.

**Tại sao xảy ra:**  
Health model không phân biệt “alive” với “ready to serve”.

**Ảnh hưởng production:**  
Pod có thể được coi ready dù startup/warm-up chưa hoàn tất; ngược lại nếu sau này `/health` được sửa để phụ thuộc external API, liveness có thể restart healthy process chỉ vì downstream đang chậm.

**Cách sửa:**  
Thiết kế endpoint riêng hoặc health-check tags riêng:

- liveness: process/runtime có bị deadlock/corrupt nghiêm trọng hay không;
- readiness: instance có thể nhận traffic ở thời điểm này hay không;
- dependency degradation: chỉ đưa dependency vào readiness nếu application thật sự không thể serve mà dependency đó mất; không tự động đưa mọi downstream vào liveness.

---

### High — Startup behavior không được model đúng

**Vấn đề:**  
Application cần 20–40 giây, nhưng readiness bắt đầu sau 2 giây và liveness sau 5 giây.

**Tại sao xảy ra:**  
Probe timing không phản ánh startup profile.

**Ảnh hưởng production:**  
Nếu health endpoint chưa phục vụ sớm, liveness có thể gây restart loop. Nếu endpoint trả 200 sớm nhưng app chưa warm, readiness có thể route traffic quá sớm.

**Cách sửa:**  
Cân nhắc `startupProbe` cho startup dài/biến động, và readiness chỉ pass khi application thật sự sẵn sàng. Probe thresholds phải dựa trên measured startup p95/p99 và failure requirements, không hard-code tùy ý.

---

### High — CPU request/limit quá thấp và chưa được chứng minh

**Vấn đề:**  
Request 50m và limit 100m cho ASP.NET Core API có burst traffic.

**Tại sao xảy ra:**  
Không có evidence từ profiling/load test.

**Ảnh hưởng production:**  
CPU throttling có thể làm latency tăng, startup/warm-up chậm và khiến probe timing tệ hơn.

**Cách sửa:**  
Đo CPU usage theo p50/p95/p99 load, request throughput và startup. Chọn requests phục vụ scheduling ổn định; limit policy phải cân nhắc throttling trade-off và cluster governance.

---

### High — `latest` làm artifact identity không reproducible

**Vấn đề:**  
Deployment dùng mutable tag.

**Tại sao xảy ra:**  
Tag không encode immutable build identity.

**Ảnh hưởng production:**  
Hai pods cùng manifest có thể pull image khác ở các thời điểm khác nhau; rollback/RCA khó chứng minh chính xác version đang chạy.

**Cách sửa:**  
Dùng immutable version tag và tốt hơn là digest trong critical environments. Ghi commit/build version vào application telemetry.

---

### High — Graceful shutdown không đáp ứng drain requirement

**Vấn đề:**  
`preStop` chỉ sleep 2 giây trong khi app cần khoảng 15 giây để ngừng nhận request mới và hoàn tất in-flight work.

**Tại sao xảy ra:**  
Termination lifecycle chưa được thiết kế theo application behavior.

**Ảnh hưởng production:**  
Rolling update có thể terminate pod khi request còn chạy, tạo 502/503 hoặc partial work.

**Cách sửa:**  
Application phải xử lý SIGTERM/graceful shutdown, readiness nên chuyển false khi termination bắt đầu và termination grace period phải đủ cho measured drain time. `preStop` chỉ là một phần của solution; không nên thay thế application-level shutdown semantics bằng sleep tùy ý.

---

### High — RollingUpdate strategy thiếu explicit availability constraints

**Vấn đề:**  
Không cấu hình `maxUnavailable`/`maxSurge` theo SLO và capacity.

**Tại sao xảy ra:**  
Team dựa vào default behavior mà chưa chứng minh capacity khi một số pods unavailable/warming.

**Ảnh hưởng production:**  
Trong rollout, số ready pods có thể không đủ chịu traffic, đặc biệt khi startup chậm hoặc resources bị throttle.

**Cách sửa:**  
Chọn rollout parameters dựa trên replica count, capacity headroom và availability target. Ví dụ có thể đặt `maxUnavailable: 0` và `maxSurge: 1` nếu cluster đủ capacity, nhưng đây là quyết định theo workload chứ không phải universal rule.

---

### Medium — Environment configuration copy-paste làm tăng drift

**Vấn đề:**  
Mỗi environment dùng một ConfigMap copy-paste.

**Tại sao xảy ra:**  
Không có cấu trúc configuration/versioning rõ ràng.

**Ảnh hưởng production:**  
Setting khác nhau ngoài ý muốn, rollback khó và validation thiếu consistency.

**Cách sửa:**  
Dùng immutable deployment/config pipeline với base + environment-specific overrides hoặc một configuration management approach rõ ràng. Validate required configuration tại startup và log safe effective config metadata, không log secrets.

---

### Medium — Telemetry không đủ cho rollout RCA

**Vấn đề:**  
Log chỉ có pod name.

**Tại sao xảy ra:**  
Không correlate application version, deployment revision, node/pod restart reason, probe status và request failures.

**Ảnh hưởng production:**  
Khó phân biệt app regression, OOM, CPU throttling, probe loop hay downstream outage.

**Cách sửa:**  
Expose deployment/build version, pod UID/name, restart count, termination reason, resource metrics, probe failures, request p95/p99 và dependency telemetry. Kết nối logs/traces với Kubernetes events/metrics.

## Phiên bản đề xuất

Ví dụ dưới đây chỉ minh họa các nguyên tắc chính; giá trị resource/probe phải được tune bằng measurement thực tế.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: catalog-api
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: catalog-api
          image: registry.example.com/catalog-api:2026.09.07.152744
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: catalog-api-secrets
                  key: main-db
            - name: ProductApi__BaseUrl
              valueFrom:
                configMapKeyRef:
                  name: catalog-api-config
                  key: product-api-base-url
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1000m"
              memory: "1Gi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 5"]
```

Các con số CPU/memory ở trên là **scenario example**, không phải recommendation chung. Trước production phải thay bằng values dựa trên load test và telemetry thực.

Application có thể expose health endpoints với semantics riêng:

```csharp
builder.Services
    .AddHealthChecks()
    .AddCheck<StartupHealthCheck>(
        "startup",
        tags: new[] { "startup" })
    .AddCheck<ReadinessHealthCheck>(
        "readiness",
        tags: new[] { "ready" });

app.MapHealthChecks(
    "/health/live",
    new HealthCheckOptions
    {
        Predicate = _ => false
    });

app.MapHealthChecks(
    "/health/ready",
    new HealthCheckOptions
    {
        Predicate = check => check.Tags.Contains("ready")
    });

app.MapHealthChecks(
    "/health/startup",
    new HealthCheckOptions
    {
        Predicate = check => check.Tags.Contains("startup")
    });
```

Liveness không nên fail chỉ vì một optional downstream dependency timeout. Readiness dependency policy phải phụ thuộc vào việc API có thể degrade/serve partial functionality hay không.

## Giải thích thiết kế sau khi sửa

### 1. Probe semantics phản ánh application lifecycle

Startup, ready và alive là ba câu hỏi khác nhau.

### 2. Resource sizing dựa trên evidence

Requests/limits ảnh hưởng scheduling, throttling và OOM behavior; chúng là production tuning parameters, không phải boilerplate.

### 3. Deployment artifact có identity bất biến

Version/digest giúp rollback, RCA và correlation với telemetry.

### 4. Shutdown được thiết kế thay vì sleep tùy ý

Application nhận termination signal, dừng nhận traffic và có bounded thời gian hoàn tất in-flight work.

### 5. Secret và config có lifecycle khác nhau

Không để credential trong source manifest; config non-secret và secret phải được quản lý/rotate/audit theo policy phù hợp.

## Trade-offs

- `maxUnavailable: 0` cần extra capacity trong rollout.
- Startup probe quá rộng có thể che startup regression; quá hẹp tạo restart loop.
- Memory limit cao hơn giảm OOM risk nhưng cần cluster capacity và cost phù hợp.
- Liveness quá đơn giản có thể bỏ sót deadlock; quá phụ thuộc downstream lại gây restart storm.
- External secret/workload identity solution tăng platform complexity nhưng giảm long-lived secret exposure.
- Kubernetes không mặc định tốt hơn App Service; nếu workload không cần orchestration capability, App Service có thể là lựa chọn đơn giản hơn.

## Cách kiểm thử

1. **Startup test:** inject startup 40–50 giây; pod không bị liveness restart và chỉ nhận traffic khi ready.
2. **Dependency-failure test:** external product API timeout; xác minh liveness/readiness behavior đúng degradation policy.
3. **Load/resource test:** chạy burst traffic và request lớn; đo CPU throttling, RSS, GC, OOM và p95/p99.
4. **Rolling-deployment test:** deploy version mới dưới load; đo 5xx và in-flight request completion.
5. **Secret/config validation:** manifest/repository không chứa production secret; pod fail-fast với required config thiếu.

## Quan sát trong production

Theo dõi:

- pod restart count và termination reason;
- OOMKilled events;
- CPU usage/throttling;
- memory working set/RSS;
- startup duration;
- readiness/liveness failure count;
- ready replica count trong rollout;
- HTTP 5xx, p50/p95/p99;
- in-flight requests khi termination;
- deployment revision/image digest;
- dependency latency/error rate;
- Kubernetes events;
- node/pod saturation;
- application version trong logs/traces.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào downstream SQL Server nên làm readiness fail và khi nào không?
2. Nếu workload này chạy tốt trên Azure App Service, lý do kỹ thuật nào đủ mạnh để chuyển sang Kubernetes?
3. Bạn sẽ xác định `terminationGracePeriodSeconds` bằng measurement nào thay vì chọn theo cảm tính?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- In-memory synchronization không trở thành distributed coordination khi ứng dụng scale-out nhiều processes/instances.
- Background processing cần durable work ownership, idempotency và shutdown semantics rõ ràng.
- `DbContext` không nên được chia sẻ cho concurrent operations.
- External side effect và SQL state thường nằm ở các transaction boundary khác nhau; crash window phải được thiết kế trước.
- Kubernetes readiness, liveness và startup là các health semantics khác nhau.
- Resource requests/limits, rollout strategy và termination behavior phải dựa trên measurement và SLO.
- Kubernetes không nên được chọn chỉ vì “production-grade”; cost of complexity là một phần của quyết định kiến trúc.

## Mẫu tư duy cần nhớ

1. **Process-local lock ≠ distributed coordination.**
2. **Claim durable work before processing; make retries idempotent.**
3. **Do not share mutable scoped state across concurrent operations.**
4. **Separate alive, ready and degraded states.**
5. **Measure resource usage and shutdown behavior before tuning deployment settings.**
