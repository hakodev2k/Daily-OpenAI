# Câu 1 — Upload file lớn gây Full GC và p99 latency spike

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, GC, memory allocation, ASP.NET Core, Azure Blob Storage, performance

## Bối cảnh

Một ASP.NET Core API nhận file 20–150 MB rồi upload sang Azure Blob Storage. Sau một thay đổi, code đọc request vào `MemoryStream`, gọi `ToArray()` rồi truyền `byte[]` sang storage layer. Production bắt đầu có working set dao động mạnh, Gen 2/Full GC tăng, p99 latency spike và một số instance restart khi nhiều upload chạy đồng thời. CPU trung bình vẫn thấp.

Team đề xuất tăng RAM hoặc gọi `GC.Collect()` sau mỗi upload. Chưa có allocation profile, chưa biết concurrency thực tế và chưa xác minh restart là OOM hay platform/health recycle.

## Câu hỏi chính

Giải thích cơ chế memory/GC có thể tạo triệu chứng này, vì sao một file có thể tạo nhiều hơn một allocation lớn, cách bạn chứng minh hypothesis và cách thiết kế lại upload path để giảm memory pressure nhưng vẫn đảm bảo validation, cancellation và failure recovery.

## Câu hỏi làm rõ nên cân nhắc

1. Request body đã bị buffer ở tầng nào trước application code chưa?
2. Có bao nhiêu upload đồng thời và max file size thực tế?
3. Storage layer có bắt buộc nhận `byte[]` hay hỗ trợ stream?
4. Restart evidence là OOM, health failure hay recycle?
5. File có cần scan/hash toàn bộ trước khi commit không?

## Gợi ý tư duy

### Gợi ý 1

`MemoryStream` và `ToArray()` có thể khiến nhiều buffers lớn cùng tồn tại.

### Gợi ý 2

Hãy phân biệt memory leak với high allocation rate/temporary retention.

### Gợi ý 3

Đo allocation/GC trước khi ép GC hoặc tăng instance size.

## Cấu trúc trả lời đề xuất

1. Clarify buffering/concurrency.
2. Vẽ allocation lifetime.
3. Giải thích large-object/Gen 2 pressure.
4. Thu runtime evidence.
5. Phân biệt leak với allocation pressure.
6. Đề xuất streaming/bounded buffering.
7. Xử lý limits/cancellation/failure.
8. Load test và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `MemoryStream` + `ToArray()` có thể tạo thêm copy lớn; peak memory tăng theo concurrency.
- Không dùng `GC.Collect()` như root fix; forced collection không loại bỏ allocation source và có thể tăng pause.
- Đo allocation rate, managed heap, Gen 2 count/pause, working set, file size và concurrency.
- Không kết luận leak chỉ từ working set tăng.
- Ưu tiên stream request sang Blob Storage hoặc bounded chunks nếu requirement cho phép.
- Có file-size/concurrency limit, cancellation và partial-upload cleanup.

### Điểm cộng

- Kiểm tra multipart/request buffering trước khi khẳng định số copies.
- Nếu cần scan/hash, cân nhắc streaming pipeline hoặc temporary storage.
- Correlate restart logs với OOM/platform evidence.

### Senior+

- Tính memory budget theo concurrent uploads/buffer strategy.
- So sánh backend proxy với direct-to-Blob theo security, authorization, scanning và observability.

## Hướng giải quyết tham khảo

Tôi chưa tăng RAM hay gọi `GC.Collect()`. Tôi dựng allocation path: request buffering, `MemoryStream` capacity, `ToArray()` copy và bất kỳ buffer nào storage layer tạo thêm. Với nhiều file 100 MB đồng thời, peak live memory có thể tăng rất nhanh dù request rate trung bình không đổi.

Tôi đo allocation rate, heap size, Gen 2 collections/pause, working set và correlate với upload concurrency/file size; allocation profile hoặc dump dùng khi cần xác định object/retention. Restart phải được xác minh bằng process/platform logs.

Nếu business cho phép, contract storage chuyển sang stream/bounded buffer thay vì `byte[]`. Cancellation truyền xuyên suốt. Nếu cần scan toàn file trước commit, có thể dùng temporary storage hoặc pipeline phù hợp thay vì mặc định giữ toàn file trong managed heap. Tôi đặt size/concurrency limits theo memory budget và load-test với distribution thực tế.

## Mẫu trả lời trong phỏng vấn

“Đây có thể là allocation pressure chứ chưa chắc leak. `MemoryStream` giữ buffer và `ToArray()` tạo thêm copy; với nhiều uploads đồng thời, peak memory tăng mạnh và large allocations làm Gen 2/GC pressure tăng. Tôi sẽ đo allocation rate, heap, GC pause, working set và correlate với file size/concurrency, đồng thời xác minh nguyên nhân restart.

Root fix là tránh materialize toàn file nếu không cần: stream hoặc bounded-buffer sang Blob, truyền cancellation, giới hạn size/concurrency và xử lý partial failure. Nếu cần scan/hash tôi thiết kế pipeline hoặc temporary storage. Tôi không dùng `GC.Collect()` như fix vì nó không loại bỏ allocation source.”

## Câu hỏi đào sâu

1. Nếu virus scan phải hoàn tất trước khi final Blob được commit, design thay đổi thế nào?
2. Nếu managed heap giảm nhưng process memory vẫn tăng, bạn điều tra gì tiếp?
3. Direct-to-Blob có trade-off gì so với backend proxy?

## Lỗi trả lời thường gặp

- Kết luận leak chỉ từ working set.
- Gọi `GC.Collect()` sau request.
- Chỉ tăng RAM mà không tính concurrency.
- Nói “stream” nhưng bỏ qua validation/cancellation/failure.

## Thang điểm 0–10

- **0–2:** Chỉ tăng RAM/ép GC.
- **3–4:** Nhận ra file lớn nhưng chưa giải thích copy/lifetime.
- **5–6:** Có profiling, streaming và limits.
- **7–8:** Có concurrency, failure/security và load test.
- **9–10:** Có memory-budget reasoning và evidence-driven trade-offs.

# Câu 2 — Elasticsearch trả product cũ và full reindex làm search chậm

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, eventual consistency, indexing, production troubleshooting, observability

## Bối cảnh

Một e-commerce backend lưu product master data trong SQL Server và dùng Elasticsearch cho full-text search. Sau campaign import, search đôi khi hiển thị tên/availability cũ 10–40 phút dù product detail đã đúng. Operations chạy full reindex, nhưng search p95 tăng mạnh và queries bắt đầu timeout.

Pipeline có background job đọc `UpdatedAt > lastCheckpoint`, transform rồi bulk-index; checkpoint ghi sau mỗi batch. Chưa rõ timestamp precision, bulk partial failures, checkpoint semantics hay concurrent updates. Elasticsearch không phải source of truth.

## Câu hỏi chính

Bạn xử lý incident theo impact → stabilization → evidence → hypotheses → verification → remediation thế nào? Thiết kế lại synchronization/reindex ra sao để tránh missed updates, xử lý partial failures và rebuild index mà không làm search availability suy giảm nghiêm trọng?

## Câu hỏi làm rõ nên cân nhắc

1. Stale được so bằng source version/timestamp nào?
2. Checkpoint advance khi mọi bulk item thành công hay chỉ khi request trả về?
3. Có nhiều updates cùng timestamp/precision boundary không?
4. Full reindex ghi active index hay index mới?
5. Cluster có indexing pressure/rejections/heap/query latency gì lúc incident?

## Gợi ý tư duy

### Gợi ý 1

Bulk request thành công không nhất thiết mọi item đều thành công.

### Gợi ý 2

Checkpoint polling phải chứng minh không tạo gap.

### Gợi ý 3

Recovery workload cũng phải bảo vệ production SLO.

## Cấu trúc trả lời đề xuất

1. Định lượng impact/backlog/freshness.
2. Stabilize reindex/load.
3. Correlate source version, checkpoint và indexed version.
4. Kiểm tra partial failures/out-of-order writes.
5. Kiểm tra cluster capacity.
6. Sửa incremental sync.
7. Thiết kế rebuild/cutover.
8. Test replay/concurrency.
9. Monitor freshness/search SLO.

## Ý chính của câu trả lời tốt

### Bắt buộc

- SQL/product system là source of truth; Elasticsearch là projection.
- Không full-reindex mù khi cluster đang degraded.
- Inspect bulk result theo từng item và không làm mất failed changes khi advance progress.
- `UpdatedAt > checkpoint` có thể tạo boundary risk nếu ties/precision/order không chắc chắn.
- Retry phải idempotent; permanent failures cần visibility/quarantine.
- Theo dõi source-to-index freshness lag.
- Rebuild nên bảo vệ active search path và có validate/cutover strategy.

### Điểm cộng

- Dùng monotonic change ID nếu source có, hoặc composite cursor `(UpdatedAt, Id)`/overlap + dedup phù hợp.
- Lưu source version trong search document để phát hiện lag/out-of-order.
- Rate-limit reindex để bảo vệ query SLO.

### Senior+

- Cân nhắc outbox/change-feed/CDC-style approach nếu reliability SLA thực sự yêu cầu.
- Tách projection correctness khỏi search-engine refresh visibility delay.
- Có index versioning, rollback và cleanup plan.

## Hướng giải quyết tham khảo

Tôi giảm/pause full reindex nếu nó đang làm search SLO xấu thêm. Tôi chọn vài stale product IDs và so source version, pipeline logs, checkpoint, bulk item result và indexed version. Hypotheses gồm checkpoint gap, partial bulk failure, transform failure, out-of-order write, refresh delay và indexing pressure.

Nếu polling tiếp tục, cursor phải deterministic. Timestamp-only `>` có thể bỏ records ở boundary nếu ties/precision không như assumption. Tôi ưu tiên monotonic change sequence hoặc composite cursor ổn định; overlap + idempotent upsert cũng là lựa chọn khi phù hợp. Progress chỉ advance khi failed changes đã được xử lý/persist để replay.

Full rebuild tạo index version mới, index với controlled rate, validate counts/samples/freshness rồi cut over logical target. Active index tiếp tục phục vụ query. Tôi theo dõi indexing lag, failed items, throughput, rejected operations và search p95/p99.

## Mẫu trả lời trong phỏng vấn

“Tôi coi Elasticsearch là projection nên phải chứng minh stale phát sinh ở stage nào. Tôi lấy sample IDs, so source version, checkpoint, bulk item result và indexed version; đồng thời giảm reindex nếu nó đang phá search SLO.

Tôi không tin `UpdatedAt > checkpoint` nếu chưa chứng minh ordering/tie semantics. Tôi dùng monotonic sequence hoặc composite cursor, inspect bulk per-item, retry idempotent và lưu source version để đo lag/out-of-order. Khi rebuild, tôi build index mới với rate control, validate rồi cut over; active index vẫn phục vụ search. Nếu polling không đáp ứng reliability SLA, lúc đó mới cân nhắc stronger change-capture design.”

## Câu hỏi đào sâu

1. Nếu source chỉ có `UpdatedAt`, bạn tránh missed rows thế nào?
2. Updates vẫn tiếp tục trong lúc rebuild; cutover thế nào để không mất changes?
3. Khi nào SQL fallback cho search là hợp lý?

## Lỗi trả lời thường gặp

- Reindex ngay mà không tìm pipeline gap.
- Coi bulk HTTP success là mọi item success.
- Không xét timestamp ties/precision.
- Tăng cluster trước khi đo pressure.

## Thang điểm 0–10

- **0–2:** Chỉ restart/reindex.
- **3–4:** Biết eventual consistency nhưng không tìm checkpoint failure.
- **5–6:** Có deterministic progress, per-item retry, freshness telemetry.
- **7–8:** Có ordering protection và safe rebuild.
- **9–10:** Reasoning end-to-end về projection correctness, recovery capacity và change-capture trade-offs.

# Câu 3 — Modernize .NET Framework 4.5 monolith mà không big-bang rewrite

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, architecture, IIS, SQL Server, CI/CD, testing, rollout/rollback

## Bối cảnh

Một enterprise platform 8 năm tuổi chạy .NET Framework 4.5 trên IIS/Windows Server, ASP.NET MVC, SQL Server và jQuery. Có 25 business modules trong cùng solution, shared database, nhiều stored procedures và scheduled jobs trong web process. Release cần maintenance window; rollback chủ yếu bằng artifact/database backup.

Business muốn trong 12–18 tháng giảm deployment risk, đưa backend mới lên modern .NET và có khả năng host workload phù hợp trên Azure App Service/Linux. Team 7 developers vẫn phải giao features.

Một proposal muốn rewrite toàn bộ sang .NET 10, Clean Architecture, Microservices, Kubernetes, React và Cosmos DB trước release tiếp theo. Proposal khác muốn giữ nguyên cho đến khi có thời gian rewrite. Chưa có dependency inventory, coupling map, test baseline hay SLO rõ.

## Câu hỏi chính

Đề xuất modernization strategy theo giai đoạn. Bạn xác định migration boundaries, dependency compatibility, database strategy, testing, deployment, observability và rollback thế nào để old/new coexist? Khi nào giữ nguyên module, refactor in place, hoặc tách thành deployable riêng?

## Câu hỏi làm rõ nên cân nhắc

1. Dependency nào khóa hệ thống vào .NET Framework/IIS/Windows?
2. Module nào thay đổi thường xuyên hoặc gây incident nhiều?
3. Shared DB có cross-module transactions nào?
4. Có thể route old/new song song theo feature không?
5. Deployment failure/rollback time/test baseline hiện tại là gì?

## Gợi ý tư duy

### Gợi ý 1

Runtime, architecture, database, frontend và infrastructure không cần đổi cùng lúc.

### Gợi ý 2

Boundary tốt đến từ ownership/change patterns/data coupling, không chỉ folder structure.

### Gợi ý 3

Thiết kế coexistence và rollback trước migration đầu tiên.

## Cấu trúc trả lời đề xuất

1. Inventory và baseline.
2. Xác định outcomes/SLO.
3. Map module/data dependencies.
4. Chọn migration seam/pilot.
5. Tăng test/observability.
6. Thiết kế schema/API compatibility.
7. Controlled rollout/rollback.
8. Lặp theo evidence.
9. Đặt criteria cho extraction/platform changes.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định big-bang rewrite.
- Inventory runtime/dependencies/coupling và production baseline trước.
- Old/new phải có incremental coexistence seam.
- Database changes cần backward/forward compatibility khi versions cùng tồn tại.
- Ưu tiên tests cho critical behavior/integration boundaries, không chờ 100% coverage.
- Có observability trước khi chuyển traffic.
- Rollback là phần của migration design.
- Không đổi database/frontend/Kubernetes chỉ vì nâng .NET.

### Điểm cộng

- Characterization tests cho legacy behavior.
- Expand/contract schema migration.
- Route/feature-level strangler approach khi phù hợp.
- Contract/integration tests giữa old/new.
- Tách scheduled jobs khỏi web process nếu lifecycle/reliability là pain point.

### Senior+

- Shared database được xử lý như coupling constraint thật.
- Criteria tách deployable: independent scale/deploy, failure isolation, ownership, security boundary.
- Phân biệt runtime modernization, architecture modernization và infrastructure modernization.
- Có migration KPIs: deployment failure, rollback time, incidents, migrated workload.

## Hướng giải quyết tham khảo

Tôi tách modernization thành nhiều dimensions. Giai đoạn đầu inventory libraries, Windows/IIS-specific APIs, auth, filesystem, jobs, integrations, stored procedures và cross-module transactions; baseline incidents/deployment/latency. Tôi thêm characterization/integration tests cho critical flows và structured observability.

Sau đó chọn một vertical slice có boundary tương đối rõ. Old/new coexist qua API/routing seam. Shared DB có thể là transitional coupling nhưng schema changes dùng expand/contract: add trước, migrate/backfill, switch consumers, remove sau. Pilot chạy trên supported modern .NET và hạ tầng đơn giản mà team vận hành tốt; traffic cutover có health/telemetry và rollback path.

Module ổn định ít thay đổi có thể ở legacy lâu hơn. Module coupling cao có thể modularize/refactor trước. Tôi chỉ tách deployable khi independent deployment/scaling/isolation/ownership đem lại lợi ích đủ lớn hơn distributed-system cost. Scheduled jobs trong web process là candidate xem xét riêng vì process lifecycle, nhưng Worker Service/Functions được chọn theo workload.

jQuery và SQL Server không cần thay chỉ vì backend nâng .NET. Kubernetes chỉ hợp lý khi platform/workload/operations requirements chứng minh giá trị. Thành công đo bằng release safety, rollback time, incident rate và migrated workload chứ không phải số công nghệ mới.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không đổi runtime, architecture, database, frontend và hosting cùng lúc. Tôi inventory dependencies/coupling, baseline production và thêm characterization/integration tests cùng observability trước.

Sau đó chọn một vertical slice có boundary rõ để chạy modern .NET, cho old/new coexist qua route/API seam. Shared DB có thể tồn tại tạm nhưng schema phải backward-compatible bằng expand/contract để rollback được. Tôi dùng hạ tầng đơn giản team đã vận hành tốt và chuyển traffic có kiểm soát.

Tôi chỉ tách service khi có independent scaling/deployment, failure isolation hoặc ownership thực sự; không chọn microservices/Kubernetes như mục tiêu. Module ổn định có thể để legacy lâu hơn. Migration được đo bằng release safety, rollback time và incidents, không phải số lượng rewrites.”

## Câu hỏi đào sâu

1. Nếu module pilot cần atomic transaction với ba legacy modules, bạn còn tách deployable không?
2. Nếu management bắt buộc Kubernetes trong 6 tháng, bạn giảm số biến thay đổi đồng thời thế nào?
3. Old/new cùng ghi shared schema sáu tháng; bạn bảo vệ rollback thế nào?

## Lỗi trả lời thường gặp

- Rewrite toàn bộ trước khi giao giá trị.
- Đổi đồng thời .NET, database, frontend và infrastructure.
- Chọn service boundaries theo folder.
- Không thiết kế schema compatibility/rollback.
- Chờ test coverage hoàn hảo hoặc migration không có safety net.

## Thang điểm 0–10

- **0–2:** Rewrite hoặc giữ nguyên vô thời hạn.
- **3–4:** Incremental nhưng thiếu coexistence/rollback.
- **5–6:** Có inventory, pilot, tests, compatibility, observability.
- **7–8:** Có boundary criteria, rollout/rollback và shared-data reasoning.
- **9–10:** Phân tách các modernization dimensions và quản lý transitional coupling dựa trên evidence/cost.

- **Treat derived indexes as rebuildable projections.**
