# Code Review Challenge 1 — Cache miss biến thành “thundering herd”: Redis lock có nhưng vẫn làm database quá tải và đôi lúc xóa lock của request khác

**Chủ đề:** C#/.NET, ASP.NET Core, Redis, cache-aside, cache stampede, distributed locking, failure handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp pricing summary cho e-commerce frontend. Dữ liệu gốc nằm trong SQL Server và khá tốn thời gian để tính vì cần join nhiều bảng và gọi thêm một rules engine nội bộ.

Đặc điểm production:

- khoảng 1.500–2.500 requests/second ở giờ cao điểm;
- cùng một `productId` có thể nhận hàng trăm requests đồng thời khi campaign bắt đầu;
- cache TTL hiện là 5 phút;
- ứng dụng chạy 8 instances;
- Redis là shared cache;
- database vẫn đủ capacity ở steady state nhưng CPU tăng mạnh đúng thời điểm nhiều cache keys hết hạn;
- p99 API tăng từ khoảng 250 ms lên hơn 8 giây trong các spike;
- Redis latency vẫn bình thường;
- SQL dependency count tăng gấp nhiều lần request rate bình thường cho cùng một nhóm products;
- thỉnh thoảng dashboard cho thấy lock key biến mất trước khi request đang regenerate cache hoàn tất.

Team đã thêm một distributed lock đơn giản để “chỉ một request được rebuild cache”. Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductPricingService
{
    private readonly IDatabase _redis;
    private readonly PricingDbContext _db;
    private readonly ILogger<ProductPricingService> _logger;

    public ProductPricingService(
        IConnectionMultiplexer redis,
        PricingDbContext db,
        ILogger<ProductPricingService> logger)
    {
        _redis = redis.GetDatabase();
        _db = db;
        _logger = logger;
    }

    public async Task<ProductPriceDto> GetAsync(
        Guid productId,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"price:{productId}";
        var cached = await _redis.StringGetAsync(cacheKey);

        if (cached.HasValue)
        {
            return JsonSerializer.Deserialize<ProductPriceDto>(cached!)!;
        }

        var lockKey = $"lock:{cacheKey}";
        var acquired = await _redis.StringSetAsync(
            lockKey,
            Environment.MachineName,
            TimeSpan.FromSeconds(5),
            When.NotExists);

        if (!acquired)
        {
            await Task.Delay(100, cancellationToken);

            cached = await _redis.StringGetAsync(cacheKey);
            if (cached.HasValue)
            {
                return JsonSerializer.Deserialize<ProductPriceDto>(cached!)!;
            }
        }

        try
        {
            var price = await _db.Products
                .Where(x => x.Id == productId)
                .Select(x => new ProductPriceDto(
                    x.Id,
                    x.BasePrice,
                    x.DiscountRules.Sum(r => r.Amount),
                    x.UpdatedAt))
                .SingleAsync(cancellationToken);

            await _redis.StringSetAsync(
                cacheKey,
                JsonSerializer.Serialize(price),
                TimeSpan.FromMinutes(5));

            return price;
        }
        finally
        {
            await _redis.KeyDeleteAsync(lockKey);
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code như một thay đổi chuẩn bị deploy production.

Bạn cần:

1. xác định các vấn đề correctness và concurrency;
2. xác định rủi ro performance/reliability khi nhiều instances cùng nhận cache miss;
3. giải thích vì sao database vẫn có thể bị stampede dù đã có lock;
4. ưu tiên findings theo severity;
5. đề xuất corrected implementation/design;
6. nêu chiến lược testing;
7. nêu telemetry cần theo dõi để chứng minh hệ thống thực sự ổn định hơn.

## Câu hỏi gợi mở

1. Request không lấy được lock nhưng sau 100 ms cache vẫn chưa có dữ liệu thì code hiện tại làm gì?
2. Giá trị lock đang dùng có đủ để chứng minh request hiện tại là owner của lock khi `finally` chạy không?
3. Điều gì xảy ra nếu query/rebuild mất hơn 5 giây nhưng TTL của lock chỉ là 5 giây?
4. Tất cả cache keys cùng TTL cố định 5 phút có thể tạo pattern tải gì ở thời điểm hết hạn?
5. Nếu Redis tạm thời unavailable, API nên fail hoàn toàn hay degrade về database với concurrency protection nào?

## Gợi ý

### Gợi ý 1

Primary risk nằm ở **cache stampede + ownership sai của distributed lock**, không chỉ ở việc “thiếu retry”.

### Gợi ý 2

Một lock phân tán an toàn cần ít nhất một ownership token duy nhất cho operation và release phải chỉ xóa lock nếu token vẫn còn khớp. Đồng thời cần nghĩ về lock expiry, bounded waiting và database fallback.

## Kết quả code review tham khảo

### Critical — Request không sở hữu lock vẫn tiếp tục rebuild cache

**Vấn đề:**  
Nếu `StringSet(... When.NotExists)` trả về `false`, request chỉ chờ 100 ms và đọc cache thêm một lần. Nếu cache vẫn miss, request rơi xuống `try` và tự query database như request đang giữ lock.

**Tại sao xảy ra:**  
Lock không thực sự gate đường đi vào expensive regeneration path. Nó chỉ tạo một cơ hội ngắn để chờ cache xuất hiện.

**Ảnh hưởng production:**  
Trong campaign spike, hàng trăm requests ở nhiều instances có thể cùng đi xuống database sau 100 ms. Điều này giải thích SQL dependency count tăng mạnh dù Redis lock tồn tại.

**Cách sửa:**  
Request không lấy được lock phải theo một bounded-wait policy rõ ràng: poll/retry cache với deadline hợp lý, hoặc trả stale value nếu business cho phép, hoặc fail/degrade theo policy. Không được tự động trở thành regenerator nếu lock vẫn thuộc operation khác.

### Critical — `finally` có thể xóa lock của request khác

**Vấn đề:**  
Mọi request đi vào `try` đều gọi `KeyDeleteAsync(lockKey)` trong `finally`, kể cả request chưa từng acquire lock. Ngoài ra, nếu lock của request A hết TTL rồi request B acquire lock mới, request A hoàn tất muộn vẫn có thể xóa lock của B.

**Tại sao xảy ra:**  
Lock chỉ dùng một key chung và release không kiểm tra ownership token.

**Ảnh hưởng production:**  
Mutual exclusion bị phá. Hai hoặc nhiều requests có thể tin rằng chúng được phép regenerate cùng lúc, tạo stampede khó tái hiện và dễ xuất hiện dưới load/latency spike.

**Cách sửa:**  
Mỗi acquire dùng một token ngẫu nhiên duy nhất. Release phải là compare-and-delete atomic: chỉ xóa key nếu value hiện tại đúng token của operation. Không dùng `Environment.MachineName` vì nhiều operations trên cùng instance có cùng value.

### High — Lock TTL 5 giây có thể ngắn hơn thời gian regenerate thực tế

**Vấn đề:**  
Nếu query/rules computation mất hơn 5 giây, lock hết hạn trước khi cache được populate.

**Tại sao xảy ra:**  
TTL được hard-code mà không gắn với latency distribution của regeneration path.

**Ảnh hưởng production:**  
Request khác acquire lock mới trong khi request cũ vẫn đang chạy, tạo overlapping regeneration và tăng database pressure đúng lúc hệ thống đã chậm.

**Cách sửa:**  
Chọn lock lease dựa trên measured p99 + margin, hoặc có safe renewal nếu implementation thực sự cần. Một phương án khác là tránh distributed lock khi không cần và dùng stale-while-revalidate / background refresh để giảm contention. Dù dùng cách nào cũng cần deadline/cancellation rõ.

### High — TTL đồng loạt 5 phút có thể tạo synchronized expiration wave

**Vấn đề:**  
Nhiều hot keys được set cùng thời điểm với cùng TTL chính xác.

**Tại sao xảy ra:**  
Không có jitter và không có proactive refresh.

**Ảnh hưởng production:**  
Campaign hoặc deploy có thể làm hàng nghìn keys cùng expire trong một cửa sổ ngắn, tạo load spike vào database/rules engine dù traffic trung bình không tăng tương ứng.

**Cách sửa:**  
Thêm TTL jitter hợp lý hoặc refresh hot data trước expiry nếu business/use case justify. Jitter không thay thế lock correctness; nó chỉ làm phẳng expiration distribution.

### High — Không có strategy rõ khi Redis unavailable

**Vấn đề:**  
Mọi thao tác Redis đều nằm trên critical path nhưng không có phân loại cache failure, fallback policy hay protection cho database khi Redis lỗi.

**Tại sao xảy ra:**  
Code coi cache như dependency luôn available dù Redis chỉ là optimization layer trong scenario này.

**Ảnh hưởng production:**  
Redis outage có thể biến thành full API outage; hoặc nếu team sau này catch lỗi rồi fallback trực tiếp database, có thể tạo database stampede lớn hơn bình thường.

**Cách sửa:**  
Xác định policy: nếu Redis lỗi, cho phép bounded database fallback theo concurrency budget, circuit breaker/admission control hoặc stale local value nếu phù hợp. Không được “catch rồi query DB vô hạn”.

### Medium — Không propagate cancellation vào Redis operations

**Vấn đề:**  
Database query nhận `CancellationToken`, nhưng Redis reads/writes/lock operations trong đoạn code không có request cancellation semantics tương đương.

**Tại sao xảy ra:**  
Cache layer không được thiết kế cùng request deadline.

**Ảnh hưởng production:**  
Client đã hủy request nhưng một phần work có thể tiếp tục, làm tăng wasted work trong load spike. Mức ảnh hưởng cụ thể phụ thuộc client library và operation duration.

**Cách sửa:**  
Thiết kế request deadline ở service level; nơi client API hỗ trợ cancellation/timeout thì sử dụng. Quan trọng hơn, đừng để regeneration sống vô hạn sau khi caller không còn cần result nếu business không yêu cầu background refresh.

### Medium — Deserialization failure có thể biến cache corruption/schema drift thành 500 lặp lại

**Vấn đề:**  
`JsonSerializer.Deserialize(... )!` giả định payload luôn hợp lệ và đúng schema.

**Tại sao xảy ra:**  
Cache data có thể stale từ version cũ, bị partial migration, hoặc serialization contract thay đổi.

**Ảnh hưởng production:**  
Một hot key lỗi có thể làm hàng nghìn requests cùng fail cho tới khi key expire/manual delete.

**Cách sửa:**  
Version cache key/schema, xử lý deserialize failure bằng telemetry + invalidate có kiểm soát, rồi regenerate qua cùng concurrency gate.

### Medium — Query path chưa có explicit no-tracking intent

**Vấn đề:**  
Đây là read-only projection nhưng query không thể hiện rõ intent `AsNoTracking()`.

**Tại sao xảy ra:**  
EF Core có change tracking mặc định cho entity queries; projection behavior cụ thể phụ thuộc shape của query, nên review nên dựa trên generated SQL/tracking evidence thay vì chỉ thêm API máy móc.

**Ảnh hưởng production:**  
Trong một số query shapes, tracking có thể tạo overhead không cần thiết. Đây không phải root cause chính của stampede.

**Cách sửa:**  
Xác minh generated SQL/tracking behavior và dùng no-tracking cho read-only access khi phù hợp. Không ưu tiên finding này cao hơn concurrency correctness.

## Phiên bản đề xuất

Một phương án vẫn dùng Redis lock nhưng giữ logic đơn giản hơn:

```csharp
public sealed class ProductPricingService
{
    private readonly IDatabase _redis;
    private readonly IDbContextFactory<PricingDbContext> _dbFactory;
    private readonly ILogger<ProductPricingService> _logger;

    private static readonly TimeSpan CacheTtl = TimeSpan.FromMinutes(5);
    private static readonly TimeSpan LockTtl = TimeSpan.FromSeconds(20);
    private static readonly TimeSpan WaitBudget = TimeSpan.FromSeconds(3);

    public ProductPricingService(
        IConnectionMultiplexer redis,
        IDbContextFactory<PricingDbContext> dbFactory,
        ILogger<ProductPricingService> logger)
    {
        _redis = redis.GetDatabase();
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task<ProductPriceDto> GetAsync(
        Guid productId,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"price:v2:{productId}";

        var cached = await TryReadAsync(cacheKey);
        if (cached is not null)
        {
            return cached;
        }

        var lockKey = $"lock:{cacheKey}";
        var token = Guid.NewGuid().ToString("N");

        var acquired = await _redis.StringSetAsync(
            lockKey,
            token,
            LockTtl,
            When.NotExists);

        if (!acquired)
        {
            var deadline = DateTimeOffset.UtcNow + WaitBudget;

            while (DateTimeOffset.UtcNow < deadline)
            {
                await Task.Delay(TimeSpan.FromMilliseconds(100), cancellationToken);

                cached = await TryReadAsync(cacheKey);
                if (cached is not null)
                {
                    return cached;
                }
            }

            throw new TimeoutException(
                $"Price regeneration did not complete within wait budget for {productId}.");
        }

        try
        {
            cached = await TryReadAsync(cacheKey);
            if (cached is not null)
            {
                return cached;
            }

            await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

            var price = await db.Products
                .AsNoTracking()
                .Where(x => x.Id == productId)
                .Select(x => new ProductPriceDto(
                    x.Id,
                    x.BasePrice,
                    x.DiscountRules.Sum(r => r.Amount),
                    x.UpdatedAt))
                .SingleAsync(cancellationToken);

            var jitterSeconds = Random.Shared.Next(0, 30);

            await _redis.StringSetAsync(
                cacheKey,
                JsonSerializer.Serialize(price),
                CacheTtl + TimeSpan.FromSeconds(jitterSeconds));

            return price;
        }
        finally
        {
            await ReleaseLockIfOwnedAsync(lockKey, token);
        }
    }

    private async Task<ProductPriceDto?> TryReadAsync(string key)
    {
        var value = await _redis.StringGetAsync(key);
        if (!value.HasValue)
        {
            return null;
        }

        try
        {
            return JsonSerializer.Deserialize<ProductPriceDto>(value!);
        }
        catch (JsonException ex)
        {
            _logger.LogWarning(ex, "Invalid cache payload for {CacheKey}", key);
            await _redis.KeyDeleteAsync(key);
            return null;
        }
    }

    private Task ReleaseLockIfOwnedAsync(string lockKey, string token)
    {
        const string script = """
            if redis.call('GET', KEYS[1]) == ARGV[1] then
                return redis.call('DEL', KEYS[1])
            else
                return 0
            end
            """;

        return _redis.ScriptEvaluateAsync(
            script,
            new RedisKey[] { lockKey },
            new RedisValue[] { token });
    }
}
```

Đây vẫn chưa phải “một implementation đúng cho mọi hệ thống”. Các giá trị `LockTtl`, `WaitBudget`, TTL và jitter phải dựa trên measurement thực tế. Nếu regeneration p99 có thể vượt lock lease, cần redesign lease/renewal hoặc chọn strategy khác.

Một phương án thường đơn giản hơn khi business cho phép là **stale-while-revalidate**:

- giữ một soft-expiry để data cũ vẫn usable trong một khoảng ngắn;
- chỉ một operation refresh background;
- các requests khác vẫn nhận stale-but-valid data;
- hard-expiry chỉ dùng khi data quá cũ hoặc không an toàn để phục vụ.

Cách này giảm áp lực phải block hàng trăm requests trên một distributed mutex. Tuy nhiên nó chỉ phù hợp nếu pricing freshness requirement cho phép.

## Giải thích thiết kế sau khi sửa

Điểm quan trọng là tách ba quyết định:

1. **Ai được regenerate?**  
   Chỉ owner của lock hoặc coordinator hợp lệ.

2. **Những request còn lại làm gì?**  
   Chờ có bounded deadline, dùng stale data nếu được phép, hoặc fail/degrade rõ ràng. Không tự do query database.

3. **Khi dependency cache lỗi thì sao?**  
   Fallback phải được giới hạn để tránh biến cache outage thành database outage.

Distributed lock chỉ là một công cụ. Nếu service chỉ chạy một instance, in-process request coalescing có thể đủ đơn giản hơn. Khi chạy nhiều instances và cùng một hot key có thể stampede toàn cluster, distributed coordination có thể hợp lý, nhưng phải đánh đổi complexity, Redis dependency và failure modes mới.

Không nên áp lock cho mọi cache key một cách máy móc. Với keys ít hot, việc regenerate song song đôi khi rẻ hơn complexity của distributed lock. Senior-level decision cần dựa trên load profile và cost của regeneration.

## Trade-offs

- Distributed lock giảm duplicate regeneration nhưng thêm network round trips, lease semantics và failure modes.
- Bounded wait bảo vệ hệ thống nhưng có thể làm một số requests timeout thay vì “cố chạy đến cùng”. Đây có thể là lựa chọn tốt hơn nếu mục tiêu là giữ toàn service ổn định.
- Stale-while-revalidate cải thiện availability/latency nhưng chấp nhận bounded staleness.
- TTL jitter làm phẳng expiry wave nhưng không giải quyết ownership bug.
- Fallback về database tăng availability khi Redis lỗi nhưng phải có concurrency/rate budget để tránh overload downstream.

## Cách kiểm thử

1. **Concurrency test:** 500 concurrent requests cùng một `productId`, xác minh chỉ một regeneration query xảy ra trong cache miss window.
2. **Lease-expiry test:** cố ý làm regeneration lâu hơn lock TTL; xác minh old owner không xóa lock mới và telemetry phát hiện overlapping lease risk.
3. **Redis failure test:** inject timeout/unavailability, xác minh fallback hoặc failure policy không tạo unbounded SQL traffic.
4. **Expiration-wave load test:** tạo hàng nghìn keys cùng lúc rồi so sánh database spike với/không có TTL jitter hoặc refresh strategy.
5. **Cache corruption test:** ghi payload schema cũ/invalid JSON, xác minh key được xử lý có kiểm soát và chỉ một regeneration xảy ra.

## Quan sát trong production

Theo dõi ít nhất:

- cache hit/miss ratio theo endpoint/key group;
- regeneration count và duration;
- distributed lock acquire success/failure rate;
- wait duration của non-owner requests;
- lock lease expiration trước khi regeneration hoàn tất;
- SQL dependency count cho mỗi hot key/window;
- SQL CPU, query duration, connection pool pressure;
- Redis latency/error/timeout rate;
- API p50/p95/p99 và timeout rate;
- stale-response count nếu dùng stale-while-revalidate;
- correlation ID nối request → cache → lock → database regeneration.

Một fix tốt phải chứng minh rằng cùng một cache miss burst không còn khuếch đại thành hàng trăm database queries.

## Câu hỏi phỏng vấn mở rộng

1. Nếu pricing data chỉ được phép stale tối đa 2 giây, bạn còn dùng stale-while-revalidate không? Bạn thay đổi design thế nào?
2. Nếu Redis outage kéo dài 10 phút, bạn sẽ bảo vệ SQL Server thế nào mà vẫn giữ một phần traffic hoạt động?
3. Khi nào bạn bỏ distributed lock hoàn toàn và chấp nhận duplicate cache regeneration?

# Code Review Challenge 2 — Jenkins deploy cùng tag `latest`: build green nhưng production không biết chính xác artifact nào đang chạy

**Chủ đề:** Jenkins, Git, CI/CD, container image provenance, immutable artifacts, secret handling, deployment reliability, rollback, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core application được build bằng Jenkins, đóng gói thành container image và deploy lên một managed container platform.

Team có ba environments: dev, staging, production. Mục tiêu ban đầu là:

- cùng một commit đã pass staging phải là artifact được promote lên production;
- rollback phải xác định được chính xác version trước đó;
- production secrets không được xuất hiện trong Jenkins logs;
- deploy không được phụ thuộc vào workspace cũ hoặc trạng thái mutable trên agent;
- sau deploy phải biết version/commit nào đang phục vụ traffic.

Gần đây xảy ra incident:

- staging pass lúc 14:00;
- production deploy lúc 16:00 từ cùng branch name;
- trong khoảng giữa có thêm hai commits được merge;
- production chạy code khác staging dù release ticket ghi cùng build number;
- một rollback dùng lại `latest` nhưng thực tế kéo image mới nhất chứ không phải image trước incident;
- Jenkins console log từng hiển thị một phần connection string khi shell command fail;
- team khó xác định container đang chạy tương ứng với commit SHA nào.

## Đoạn code cần review

```groovy
pipeline {
    agent any

    environment {
        REGISTRY = 'registry.example.internal'
        IMAGE = 'employee-portal'
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'git@github.com:company/employee-portal.git'
            }
        }

        stage('Build') {
            steps {
                sh 'dotnet restore'
                sh 'dotnet test --configuration Release'
                sh 'docker build -t $REGISTRY/$IMAGE:latest .'
            }
        }

        stage('Push') {
            steps {
                sh 'docker push $REGISTRY/$IMAGE:latest'
            }
        }

        stage('Deploy Staging') {
            steps {
                sh '''
                  deployctl set-image staging \
                    $REGISTRY/$IMAGE:latest
                '''
            }
        }

        stage('Deploy Production') {
            when {
                branch 'main'
            }
            steps {
                withCredentials([string(
                    credentialsId: 'prod-db',
                    variable: 'PROD_DB')]) {
                    sh '''
                      echo "Deploying with database=$PROD_DB"
                      deployctl set-env production ConnectionStrings__Default="$PROD_DB"
                      deployctl set-image production $REGISTRY/$IMAGE:latest
                    '''
                }
            }
        }
    }

    post {
        failure {
            sh 'docker images'
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review pipeline như một thay đổi chuẩn bị trở thành release pipeline chính thức.

Bạn cần:

1. xác định correctness/release-safety problems;
2. xác định security và secret-handling risks;
3. giải thích vì sao staging và production có thể chạy artifacts khác nhau dù cùng branch/release ticket;
4. ưu tiên findings theo severity;
5. đề xuất corrected pipeline/design;
6. nêu testing/deployment validation cần có;
7. nêu telemetry/metadata giúp điều tra production release nhanh chóng.

## Câu hỏi gợi mở

1. `latest` đại diện cho artifact cụ thể hay chỉ là một mutable reference có thể thay đổi?
2. Pipeline đang **promote artifact đã test** hay đang checkout/build lại state của branch ở thời điểm chạy?
3. Rollback bằng `latest` có thể chứng minh đang quay về image trước đó không?
4. Secret có thể xuất hiện ở đâu ngoài explicit `echo`, ví dụ shell tracing, process arguments hoặc error output?
5. Sau deploy, application/runtime có metadata nào cho biết commit SHA, image digest và pipeline build ID đang chạy không?

## Gợi ý

### Gợi ý 1

Primary risk là **artifact identity không immutable**, dẫn đến staging validation và production deployment không còn nói về cùng một binary/image.

### Gợi ý 2

Hãy xem release như chuỗi: **source commit → build artifact → digest → promotion → runtime identity**. Mỗi bước phải truy vết được mà không làm lộ secrets.

## Kết quả code review tham khảo

### Critical — Dùng mutable tag `latest` làm mất artifact identity

**Vấn đề:**  
Build, push, staging deploy và production deploy đều tham chiếu `$IMAGE:latest`.

**Tại sao xảy ra:**  
`latest` là một tag có thể được cập nhật bởi build khác. Release ticket không khóa image digest hoặc unique version.

**Ảnh hưởng production:**  
Staging có thể test image A nhưng production vài giờ sau kéo image B. Rollback dùng `latest` cũng không bảo đảm quay về version cũ.

**Cách sửa:**  
Tag image bằng immutable release identity như commit SHA/build ID và tốt hơn nữa lưu/triển khai bằng image digest. Production promotion phải tham chiếu đúng artifact đã pass staging.

### Critical — Pipeline đang build từ branch state, không pin source revision như một release input

**Vấn đề:**  
`git branch: 'main'` lấy state hiện tại của branch khi job chạy.

**Tại sao xảy ra:**  
Release không truyền một immutable commit SHA đã được phê duyệt/test làm input.

**Ảnh hưởng production:**  
Hai executions cùng “main” có thể build source khác nhau. Điều này phá reproducibility và auditability.

**Cách sửa:**  
Release build phải pin commit SHA. Build artifact một lần từ SHA đó; staging và production chỉ promote artifact đã tạo, không rebuild từ branch.

### Critical — Secret bị in trực tiếp ra Jenkins console

**Vấn đề:**  
`echo "Deploying with database=$PROD_DB"` ghi secret vào log.

**Tại sao xảy ra:**  
Credential injection bị dùng như ordinary environment variable trong shell output.

**Ảnh hưởng production:**  
Connection string có thể bị lưu trong build logs/artifacts, accessible cho nhiều người hơn quyền truy cập secret store ban đầu.

**Cách sửa:**  
Không log secret value. Truyền secret qua cơ chế secret reference/runtime secret store nếu platform hỗ trợ. Jenkins credential masking là defense-in-depth, không phải lý do để echo secrets.

### High — Configuration mutation và image rollout không có transactional/release boundary rõ

**Vấn đề:**  
Pipeline gọi `set-env` rồi `set-image` thành hai operations riêng.

**Tại sao xảy ra:**  
Environment configuration và application artifact được mutate tuần tự mà không có explicit versioned release object hay rollback plan.

**Ảnh hưởng production:**  
Nếu bước image deploy fail sau khi config đã đổi, production có thể ở trạng thái config mới + image cũ. Nếu config không backward-compatible, incident xảy ra dù image rollout chưa hoàn tất.

**Cách sửa:**  
Thiết kế environment config compatibility và release sequencing rõ. Ưu tiên versioned configuration/secret references, preflight validation và rollback strategy. Nếu platform hỗ trợ declarative revision/release, deploy artifact + config reference như một versioned unit.

### High — Không có post-deploy health/critical-path validation

**Vấn đề:**  
Pipeline coi `deployctl set-image` thành công là deploy thành công.

**Tại sao xảy ra:**  
Không có readiness/health gate, smoke test hoặc observation window.

**Ảnh hưởng production:**  
Image có thể pull/start được nhưng application vẫn lỗi config, dependency hoặc business workflow.

**Cách sửa:**  
Sau deploy, chờ rollout readiness, kiểm tra health endpoint và ít nhất một critical smoke test phù hợp trước khi đánh dấu release successful.

### High — Rollback không có explicit previous immutable revision

**Vấn đề:**  
Pipeline không lưu previous digest/release metadata.

**Tại sao xảy ra:**  
Release identity dựa trên mutable tag thay vì version graph.

**Ảnh hưởng production:**  
Khi incident xảy ra, operations không biết chắc image nào là last-known-good.

**Cách sửa:**  
Lưu release manifest gồm commit SHA, image digest, config version, pipeline run ID, deploy timestamp và previous revision. Rollback chọn explicit immutable revision.

### Medium — `agent any` + local Docker state có thể làm build phụ thuộc node state

**Vấn đề:**  
Pipeline có thể chạy trên bất kỳ Jenkins agent nào và `post failure` còn dump local `docker images`.

**Tại sao xảy ra:**  
Build environment chưa được mô tả là clean/reproducible. Docker layer cache không phải vấn đề tự thân, nhưng stale workspace/toolchain/node differences có thể làm debugging khó nếu không kiểm soát.

**Ảnh hưởng production:**  
Reproducibility giảm; behavior có thể khác giữa agents. Dump local image list cũng tạo noisy logs và có thể expose internal repository/tag metadata không cần thiết.

**Cách sửa:**  
Dùng ephemeral/controlled build agents hoặc workspace cleanup/toolchain pinning. Log artifact metadata có chủ đích thay vì dump toàn bộ host state.

### Medium — Không publish test/build provenance như release metadata

**Vấn đề:**  
Không có manifest nối test results với exact commit/image digest.

**Tại sao xảy ra:**  
Pipeline tập trung chạy commands nhưng không tạo provenance record.

**Ảnh hưởng production:**  
Sau incident khó trả lời “image này đã chạy bộ test nào, từ commit nào, build nào?”.

**Cách sửa:**  
Publish release metadata/manifest và expose version endpoint hoặc application telemetry properties chứa commit SHA + build ID + image digest/revision.

### Medium — Production deployment tự động chỉ dựa trên branch condition

**Vấn đề:**  
`when { branch 'main' }` không đại diện cho release approval, environment promotion hay policy gate.

**Tại sao xảy ra:**  
Source-control branch và release-management decision bị trộn làm một.

**Ảnh hưởng production:**  
Một merge vào main có thể vô tình kích hoạt production path tùy job setup, hoặc pipeline không có explicit promotion semantics.

**Cách sửa:**  
Tách build pipeline và deployment/promotion workflow. Production release nên lấy immutable artifact + release policy/approval phù hợp với team process, không rebuild theo branch.

## Phiên bản đề xuất

Một hướng đơn giản hơn là **build once, promote many**. Ví dụ Jenkinsfile rút gọn:

```groovy
pipeline {
    agent { label 'ephemeral-linux-builder' }

    environment {
        REGISTRY = 'registry.example.internal'
        IMAGE = 'employee-portal'
    }

    stages {
        stage('Checkout exact revision') {
            steps {
                checkout scm
                script {
                    env.GIT_SHA = sh(
                        script: 'git rev-parse HEAD',
                        returnStdout: true
                    ).trim()
                    env.IMAGE_TAG = env.GIT_SHA
                }
            }
        }

        stage('Build and test') {
            steps {
                sh 'dotnet restore --locked-mode'
                sh 'dotnet test --configuration Release --no-restore'
                sh 'docker build --pull -t $REGISTRY/$IMAGE:$IMAGE_TAG .'
                sh 'docker push $REGISTRY/$IMAGE:$IMAGE_TAG'
            }
        }

        stage('Resolve immutable image') {
            steps {
                script {
                    env.IMAGE_DIGEST = sh(
                        script: 'resolve-image-digest $REGISTRY/$IMAGE:$IMAGE_TAG',
                        returnStdout: true
                    ).trim()
                }
            }
        }

        stage('Deploy staging') {
            steps {
                sh '''
                  deployctl set-image staging \
                    $REGISTRY/$IMAGE@$IMAGE_DIGEST
                  deployctl wait-ready staging
                  smoke-test https://staging.example.internal/health
                '''
            }
        }

        stage('Promote production') {
            steps {
                input message: "Promote tested artifact ${GIT_SHA}?"

                withCredentials([string(
                    credentialsId: 'prod-db-secret-ref',
                    variable: 'PROD_DB_SECRET_REF')]) {
                    sh '''
                      deployctl set-secret-ref production \
                        ConnectionStrings__Default "$PROD_DB_SECRET_REF"

                      deployctl set-image production \
                        $REGISTRY/$IMAGE@$IMAGE_DIGEST

                      deployctl wait-ready production
                      smoke-test https://prod.example.internal/health
                    '''
                }
            }
        }
    }

    post {
        always {
            sh '''
              publish-release-metadata \
                --commit "$GIT_SHA" \
                --image-digest "$IMAGE_DIGEST" \
                --build-id "$BUILD_ID"
            '''
        }
    }
}
```

Đoạn trên minh họa principles chứ không giả định `deployctl`, `resolve-image-digest` hay `publish-release-metadata` là tooling có sẵn của mọi tổ chức. Điều cần giữ là:

- source revision immutable;
- image identity immutable;
- staging và production dùng cùng image digest;
- secret value không bị log;
- rollout có health gate;
- release metadata truy vết được.

Nếu organization không cần manual approval, `input` có thể thay bằng automated policy gate. Requirement release process phải quyết định, không phải mặc định cứ manual mới an toàn.

## Giải thích thiết kế sau khi sửa

Build pipeline và deploy pipeline có thể là hai jobs riêng, nhưng mental model phải là:

```text
Git commit SHA
    ↓
build/test once
    ↓
immutable image digest
    ↓
staging validation
    ↓
promote same digest
    ↓
production revision
```

Điểm quan trọng là **không rebuild production artifact sau khi staging đã pass**. Rebuild có thể khác vì source branch đổi, dependency restore đổi, base image đổi hoặc build environment khác.

Container tag như commit SHA tốt hơn `latest`, nhưng digest là identity mạnh hơn vì tag về nguyên tắc vẫn có thể bị retag nếu registry policy cho phép. Registry policy nên ngăn overwrite immutable release tags nếu có thể.

Secret cũng không nên trở thành release metadata plaintext. Release manifest chỉ cần secret reference/version identifier phù hợp, không chứa actual value.

Ứng dụng nên expose version metadata theo cách không leak sensitive info, ví dụ structured telemetry property hoặc internal `/version` endpoint chứa commit SHA/build ID/revision. Khi incident xảy ra, operations có thể correlate request traces với release.

## Trade-offs

- Immutable artifact promotion cần registry retention và metadata discipline, nhưng đổi lại rollback/audit đơn giản hơn nhiều.
- Pin dependency/base image tăng reproducibility nhưng cần quy trình cập nhật security patches chủ động; pinning không có nghĩa là không update.
- Manual approval giảm automation tốc độ; automated policy gates có thể phù hợp hơn với team có deployment maturity cao.
- Health check chỉ chứng minh một lớp correctness. Critical-path smoke test tăng confidence nhưng cũng làm pipeline lâu hơn và cần test data ổn định.
- Tách build/deploy jobs tăng số workflow objects nhưng làm security boundary rõ hơn: build job không nhất thiết cần production credentials.

## Cách kiểm thử

1. **Artifact identity test:** build một commit, merge thêm commit khác sau staging, rồi xác minh production vẫn deploy đúng digest đã pass staging.
2. **Rollback drill:** deploy release N+1 rồi rollback explicit về digest N; xác minh runtime version metadata khớp release manifest.
3. **Secret leakage test:** cố ý làm deploy command fail; kiểm tra console/artifacts không chứa connection string hoặc secret value.
4. **Agent reproducibility test:** chạy cùng commit trên hai clean agents; xác minh artifact provenance/toolchain/dependency inputs được kiểm soát đủ để giải thích khác biệt nếu digest khác.
5. **Post-deploy failure test:** deploy image start được nhưng health/smoke test fail; xác minh pipeline không đánh dấu release successful và rollback/escalation policy hoạt động.

## Quan sát trong production

Mỗi release nên có metadata truy vết được:

- Git commit SHA;
- image digest;
- pipeline build/run ID;
- deployment revision ID;
- deploy timestamp;
- environment;
- previous revision;
- config version/secret reference version, không chứa secret value.

Trong application telemetry nên gắn release identity vào:

- request traces;
- exceptions;
- dependency failures;
- startup logs;
- health/readiness events.

Dashboard release nên cho phép correlate error rate, p95/p99, restart count và critical-business KPI trước/sau mỗi revision. Khi incident xảy ra, câu hỏi “version nào đang chạy?” phải trả lời được trong vài giây, không cần suy luận từ branch name hay `latest`.

## Câu hỏi phỏng vấn mở rộng

1. Nếu base image có security patch quan trọng sau khi staging đã pass, bạn rebuild cùng commit hay promote digest cũ? Bạn tổ chức re-validation thế nào?
2. Nếu registry cho phép overwrite tag commit SHA, vì sao deploy bằng digest vẫn an toàn hơn deploy bằng tag?
3. Nếu production config phải thay đổi độc lập với application release, bạn version/audit/rollback config thế nào mà không đưa secret plaintext vào Git?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache-aside dưới concurrency cao cần xử lý **stampede**, không chỉ đọc/ghi Redis đúng cú pháp.
- Distributed lock phải có ownership rõ ràng; lock expiry và release race có thể phá mutual exclusion nếu thiết kế sơ sài.
- Cache outage cần fallback policy có giới hạn, nếu không Redis failure có thể trở thành database failure.
- CI/CD an toàn cần **build once, promote many**: staging và production phải chạy cùng immutable artifact.
- `latest` và branch name không phải release identity. Commit SHA, image digest và release metadata mới cung cấp audit/rollback đáng tin cậy.
- Secret handling là một phần của pipeline architecture; masking không thay thế việc không đưa secret vào logs ngay từ đầu.

## Mẫu tư duy cần nhớ

1. **Thiết kế cache cùng failure path và concurrency behavior, không chỉ happy path.**
2. **Một distributed lock chỉ có ý nghĩa khi ownership, lease và release semantics đều đúng.**
3. **Khi dependency tối ưu hóa bị lỗi, bảo vệ source-of-truth khỏi fallback stampede.**
4. **Build một lần, promote đúng artifact đã test; đừng rebuild theo branch state.**
5. **Mọi production revision phải truy vết được từ runtime về commit, artifact và deployment record.**
