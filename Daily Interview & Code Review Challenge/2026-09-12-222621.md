# Câu 1 — Request đã trả `202` nhưng background task vẫn dùng `DbContext` và `HttpContext`: DI scope thực sự sống bao lâu và vì sao lỗi chỉ xuất hiện ngẫu nhiên?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** C#/.NET 8, ASP.NET Core, Dependency Injection, scoped lifetime, `DbContext`, `HttpContext`, `Task`, background work, execution context, cancellation, production diagnostics

## Bối cảnh

Một ASP.NET Core API cho phép employee submit một document-processing request. Team muốn endpoint trả nhanh nên sau khi lưu metadata, họ khởi chạy processing bằng `Task.Run`:

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IDocumentProcessor _processor;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        AppDbContext db,
        IDocumentProcessor processor,
        ILogger<DocumentsController> logger)
    {
        _db = db;
        _processor = processor;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> Create(
        CreateDocumentRequest request,
        CancellationToken ct)
    {
        var document = new Document
        {
            Id = Guid.NewGuid(),
            EmployeeId = User.GetEmployeeId(),
            Status = "Pending",
            CreatedAt = DateTimeOffset.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(ct);

        _ = Task.Run(async () =>
        {
            _logger.LogInformation(
                "Processing {DocumentId} for {User}",
                document.Id,
                HttpContext.User.Identity?.Name);

            var result = await _processor.ProcessAsync(document.Id);

            document.Status = "Completed";
            document.OutputPath = result.Path;
            await _db.SaveChangesAsync();
        });

        return Accepted(new { document.Id });
    }
}
```

`AppDbContext` và `IDocumentProcessor` đều được đăng ký `Scoped`.

Ở development code gần như luôn chạy đúng. Production chạy 6 instances và traffic cao hơn thì xuất hiện:

- thỉnh thoảng `ObjectDisposedException` liên quan `DbContext`;
- có request trả `202` nhưng document mãi ở `Pending`;
- một số logs không còn user name hoặc có dữ liệu request context không như kỳ vọng;
- deployment/restart có thể làm processing dừng giữa chừng;
- Sentry/Application Insights thấy exception trong task nhưng request tương ứng đã trả success từ trước;
- một developer muốn sửa bằng cách inject `IServiceScopeFactory` vào controller rồi tạo scope bên trong `Task.Run`;
- developer khác nói chỉ cần clone entity `document` để không dùng object bị track bởi request scope;
- team chưa thống nhất vấn đề nào là lifetime bug và vấn đề nào là durability/design bug.

## Câu hỏi chính

Hãy giải thích lifetime của request scope trong ASP.NET Core, vì sao việc capture `_db`, `document` và `HttpContext` vào một fire-and-forget task có thể trở nên không hợp lệ sau khi HTTP request kết thúc, và tại sao chỉ tạo một DI scope mới bên trong `Task.Run` vẫn chưa giải quyết toàn bộ bài toán production. Sau đó hãy đề xuất design đúng cho cả hai trường hợp: background work chỉ là best-effort và background work đã được `202 Accepted` nhưng business yêu cầu không được mất khi process restart.

## Câu hỏi làm rõ nên cân nhắc

1. `202 Accepted` trong business contract có nghĩa server đã nhận trách nhiệm hoàn tất processing hay chỉ là best-effort notification?
2. Processing thường mất bao lâu, có thể retry không, và operation có idempotent theo `DocumentId` không?
3. `IDocumentProcessor` phụ thuộc những scoped services nào ngoài `DbContext`?
4. User identity nào thực sự cần cho processing: full `HttpContext`, hay chỉ cần persisted `EmployeeId/TenantId` đã được authorize tại request boundary?
5. Khi host nhận SIGTERM/redeploy, outstanding jobs cần drain, retry hay được worker khác reclaim?

## Gợi ý tư duy

### Gợi ý 1

Request-scoped services được tạo cho một HTTP request và được dispose khi request scope kết thúc. Một `Task` sống lâu hơn request không tự kéo dài scope đó.

### Gợi ý 2

Tách hai khái niệm: **lifetime correctness** và **durability**. Tạo scope mới có thể sửa lifetime của services, nhưng work vẫn chỉ nằm trong RAM của process.

### Gợi ý 3

Persist những dữ liệu cần thiết cho work thay vì capture `HttpContext`/tracked entity. Background worker nên resolve dependencies trong scope thuộc chính work item của nó.

## Cấu trúc trả lời đề xuất

1. Xác định request scope bắt đầu/kết thúc ở đâu.
2. Liệt kê những object bị capture và lifetime tương ứng.
3. Giải thích vì sao lỗi có tính timing-dependent.
4. Phân biệt giải pháp cho best-effort work và durable work.
5. Thiết kế ownership của `DbContext`, identity context và cancellation.
6. Mô tả shutdown/retry/idempotency semantics.
7. Nêu tests và telemetry chứng minh design hoạt động.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết `DbContext` mặc định thường là scoped và không được dùng sau khi scope bị dispose.
- Nhận ra tracked entity `document` đang thuộc cùng context/request lifetime.
- Không xem `HttpContext` là durable object để dùng sau request.
- Nhận ra fire-and-forget task không được ASP.NET Core host quản lý như durable job.
- Tách việc tạo scope mới khỏi bài toán process crash/redeploy.
- Đề xuất persist minimal execution context (`DocumentId`, tenant/user ownership, parameters) thay vì capture request state.

### Điểm cộng

- Nêu rõ `DbContext` không thread-safe và không nên chia sẻ đồng thời giữa request/task.
- Phân biệt request cancellation với host shutdown và job cancellation.
- Dùng `BackgroundService` + bounded queue cho best-effort in-process work.
- Dùng durable queue/job table khi `202` tạo reliability commitment.
- Có state machine `Pending → Running → Completed/Failed/Retry` và idempotency.

### Senior+

- Nhận ra `IServiceScopeFactory` trong detached `Task.Run` chỉ giải quyết dependency scope chứ không có backpressure, ownership, exception supervision hay durability.
- Thiết kế atomic persistence/enqueue boundary hoặc transactional outbox/job table nếu cần tránh “DB commit thành công nhưng enqueue thất bại”.
- Không lưu toàn bộ claims principal/request object nếu chỉ cần stable identifiers đã được authorization.
- Có lease/claim/recovery semantics nếu nhiều instances cùng xử lý durable jobs.

## Hướng giải quyết tham khảo

Ở mức runtime, `DocumentsController`, `AppDbContext` và các scoped dependencies được resolve từ request scope. Khi middleware pipeline hoàn tất request, scope đó được dispose. `Task.Run` được tạo bên trong request không làm request scope tồn tại lâu hơn. Nếu task chậm hơn request, `_db.SaveChangesAsync()` chạy sau đó có thể chạm một `DbContext` đã dispose. Nếu task chạy nhanh ở development, race không lộ ra nên bug trông “ngẫu nhiên”.

`document` cũng không phải một detached durable representation. Nó đang là entity được track bởi `_db`. Thay `document` bằng một object clone có thể tránh tracking của entity cũ, nhưng `_db` vẫn sai lifetime và toàn bộ work vẫn không có supervisor/durability.

`HttpContext` thuộc HTTP request. Background work nên trích xuất stable facts tại boundary, ví dụ `EmployeeId`, `TenantId`, `DocumentId`, locale nếu thực sự cần, sau khi authorization hoàn tất. Không nên giữ reference tới `HttpContext` rồi kỳ vọng identity/request services còn hợp lệ nhiều giây hoặc nhiều phút sau.

Nếu business nói work chỉ là **best effort**, một thiết kế tối thiểu tốt hơn là bounded in-process queue được một `BackgroundService` consume. Controller enqueue một immutable work item. Worker tạo scope riêng cho mỗi item, resolve `DbContext`/processor từ scope đó và await work trong hosted-service lifecycle. Queue phải bounded để có backpressure; shutdown phải stop admission và cho worker drain trong grace period hoặc bỏ work theo semantics đã công bố.

Ví dụ hướng thiết kế:

```csharp
public sealed record DocumentWorkItem(
    Guid DocumentId,
    int EmployeeId,
    int TenantId);

public sealed class DocumentWorker : BackgroundService
{
    private readonly Channel<DocumentWorkItem> _queue;
    private readonly IServiceScopeFactory _scopeFactory;

    public DocumentWorker(
        Channel<DocumentWorkItem> queue,
        IServiceScopeFactory scopeFactory)
    {
        _queue = queue;
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var item in _queue.Reader.ReadAllAsync(stoppingToken))
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<IDocumentJobHandler>();

            await processor.HandleAsync(item, stoppingToken);
        }
    }
}
```

Điểm quan trọng là scope thuộc work item, không phải request. Nhưng đây vẫn là **in-memory queue**: process chết thì queue mất.

Nếu API trả `202` với contract rằng job đã được accept và phải hoàn tất/retry, tôi sẽ persist job trước khi response thành công. Có thể dùng SQL job table cho volume vừa phải hoặc một durable message broker khi requirements phù hợp. Job record chứa identifiers/parameters cần thiết và status. Worker claim atomically, tạo scope mới, load fresh entity bằng fresh `DbContext`, process rồi update state.

Cần giải quyết failure window. Ví dụ nếu transaction lưu `Document` commit nhưng enqueue broker thất bại, không thể giả định hai operations là atomic. Một SQL-backed job table trong cùng transaction là lựa chọn đơn giản. Hoặc transactional outbox ghi event cùng transaction rồi dispatcher publish sau. Không nhất thiết phải thêm broker nếu SQL polling đáp ứng throughput.

Job handler phải idempotent hoặc có deduplication theo `DocumentId`. Nếu worker chết sau external side effect nhưng trước khi mark `Completed`, retry không được tạo output/charge/email lặp ngoài ý muốn. Với multiple instances, claim/lease cần đảm bảo một active owner hoặc ít nhất duplicate execution được thiết kế chịu được.

Cancellation cũng cần tách rõ:

- request token chỉ còn ý nghĩa khi tạo/persist job;
- worker token phản ánh host shutdown;
- user-requested cancel nếu có phải là persisted job state riêng;
- dependency timeout nên có policy riêng, không dùng host token như mọi timeout.

Production telemetry nên có accepted jobs, queue depth/pending count, oldest pending age, active jobs, completed/failed/retry counts, processing duration, lease recovery và exception correlation theo `DocumentId`. Logs cần biết worker instance/version nhưng không phụ thuộc `HttpContext`.

## Mẫu trả lời trong phỏng vấn

“Bug đầu tiên là lifetime ownership. `DbContext` được resolve từ request scope, scope bị dispose khi request kết thúc, nhưng `Task.Run` có thể chạy sau đó. Task đang capture `_db`, một tracked entity và `HttpContext`, nên nó dùng request-owned state ngoài lifetime của request. Vì timing khác nhau nên local có thể luôn pass còn production mới thấy `ObjectDisposedException`.

Tạo `IServiceScopeFactory` và scope mới trong task sẽ sửa một phần — worker có thể có `DbContext` riêng — nhưng vẫn chưa làm fire-and-forget task trở thành reliable background processing. Process restart vẫn mất work, exception không có workflow state, không có backpressure và `202` có thể nói dối reliability contract.

Nếu work chỉ best-effort, tôi dùng bounded queue + `BackgroundService`; mỗi item là immutable IDs/parameters, worker tạo scope mới cho item và await work. Nếu `202` nghĩa job đã được accept bền vững, tôi persist job trước khi trả response, dùng durable job table hoặc broker phù hợp, có claim/retry/idempotency và shared status.

Tôi cũng không capture `HttpContext`; tôi authorize trong request rồi persist `EmployeeId/TenantId` cần thiết. Khi worker chạy, nó load fresh state bằng fresh context. Tôi test request kết thúc ngay, concurrent load, process kill, shutdown và retry sau side effect; telemetry phải cho biết pending age, active jobs, failures và recovery.”

## Câu hỏi đào sâu

1. Nếu controller persist job trong SQL rồi publish message lên Service Bus nhưng publish thất bại, bạn tránh job “nằm im” như thế nào?
2. Nếu processing gọi external OCR API không hỗ trợ idempotency key, worker crash ngay sau OCR success nhưng trước khi lưu status thì retry semantics nên thế nào?
3. Tôi cho rằng chỉ cần `Task.Run` + `IServiceScopeFactory` vì job tối đa 300 ms; bạn sẽ phản biện dựa trên requirement nào thay vì dựa trên “best practice” chung chung?

## Lỗi trả lời thường gặp

- Chỉ nói “`DbContext` không thread-safe” mà bỏ qua request-scope disposal.
- Cho rằng clone entity sẽ sửa toàn bộ lỗi.
- Tạo scope mới rồi tuyên bố background job đã reliable.
- Capture `HttpContext.User` vào work item thay vì persist minimal identity facts.
- Không phân biệt request cancellation, host shutdown và durable job cancellation.

## Thang điểm 0–10

- **0–2:** Chỉ sửa exception cục bộ hoặc thêm try/catch vào `Task.Run`.
- **3–4:** Nhận ra scoped lifetime nhưng chưa giải quyết background ownership/durability.
- **5–6:** Thiết kế được `BackgroundService` + per-job scope, hiểu cancellation và request-context boundary.
- **7–8:** Phân biệt best-effort/durable processing, có persistence, retry, idempotency và multi-instance semantics.
- **9–10:** Kết nối chặt DI lifetime → execution ownership → durability boundary → atomic enqueue/persistence → recovery/observability và chọn complexity đúng theo business contract.

# Câu 2 — API bắt đầu timeout hàng loạt sau khi downstream đổi IP: `HttpClient`, socket pool, DNS và retry đang tương tác thế nào?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, `HttpClient`, `SocketsHttpHandler`, `IHttpClientFactory`, DNS, TCP connection pooling, SNAT/socket exhaustion, timeout, retry, resilience, Application Insights, incident response

## Bối cảnh

Một ASP.NET Core employee platform gọi internal Payroll API qua hostname:

```text
https://payroll.internal.example/api/...
```

Platform chạy 8 application instances. Payroll API nằm sau internal load balancer và có thể thay backend IP khi deploy/failover.

Team có hai clients được viết ở hai thời điểm khác nhau:

```csharp
public sealed class PayrollClientA
{
    public async Task<string> GetAsync(string path, CancellationToken ct)
    {
        using var client = new HttpClient();
        client.Timeout = TimeSpan.FromSeconds(30);
        return await client.GetStringAsync(path, ct);
    }
}
```

và:

```csharp
public sealed class PayrollClientB
{
    private static readonly HttpClient Client = new()
    {
        BaseAddress = new Uri("https://payroll.internal.example"),
        Timeout = TimeSpan.FromSeconds(30)
    };

    public Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request,
        CancellationToken ct)
        => Client.SendAsync(request, ct);
}
```

Một thư viện resilience bên ngoài còn retry tối đa 3 lần cho timeout/5xx, không có jitter.

Incident lúc 14:10:

- Payroll deploy một version mới và internal load balancer thay backend pool;
- khoảng 14:12, một phần requests từ employee platform bắt đầu timeout;
- restart một application instance làm instance đó tốt trở lại tạm thời;
- một số instances có số outbound connections/TIME_WAIT tăng mạnh;
- CPU application không cao;
- retries làm outbound request volume tăng gần 4 lần;
- DNS lookup từ diagnostic shell trả IP mới;
- một developer kết luận static `HttpClient` “cache DNS vĩnh viễn” nên phải tạo client mới mỗi request;
- developer khác kết luận cứ singleton `HttpClient` là đúng và lỗi chắc chắn ở Payroll;
- networking team nghi SNAT/socket pressure nhưng chưa có correlation theo instance.

## Câu hỏi chính

Bạn sẽ điều tra incident theo thứ tự nào để phân biệt stale connection/DNS behavior, socket/SNAT exhaustion, downstream latency và retry amplification? Hãy giải thích `HttpClient`/handler connection pooling ở mức đủ sâu để lựa chọn lifetime đúng, sau đó đề xuất cấu hình `IHttpClientFactory`/`SocketsHttpHandler`, timeout/retry policy và telemetry phù hợp mà không áp dụng công thức “new mỗi request” hay “singleton mãi mãi” một cách máy móc.

## Câu hỏi làm rõ nên cân nhắc

1. Client A thực tế truyền absolute URL hay relative path, và volume của A/B khác nhau bao nhiêu?
2. DNS TTL/load-balancer failover behavior của `payroll.internal.example` là gì?
3. Metrics theo instance cho active connections, connection establishment errors, TIME_WAIT/SNAT ports và request latency ra sao?
4. Timeout xảy ra ở connect, TLS handshake, response headers hay body download?
5. Payroll API có idempotent operations nào; retries hiện áp dụng cả GET và write requests hay không?

## Gợi ý tư duy

### Gợi ý 1

`HttpClient` là API facade; connection pooling nằm ở handler. Câu hỏi lifetime cần xét cả client **và** underlying handler/pooled connections.

### Gợi ý 2

Tạo/dispose client + handler quá thường xuyên có thể gây connection churn/TIME_WAIT. Ngược lại, pooled connections tồn tại quá lâu có thể không thích nghi đủ nhanh với DNS/backend changes tùy cấu hình.

### Gợi ý 3

Retry là traffic multiplier. Nếu failure probability/latency tăng, retry đồng loạt không jitter có thể biến downstream degradation thành cascading incident.

## Cấu trúc trả lời đề xuất

1. Stabilize và giảm retry amplification nếu cần.
2. Correlate failures theo app instance và downstream endpoint.
3. Tách DNS resolution, TCP connect, TLS và server response timing.
4. Giải thích handler/connection pool lifetime.
5. Kiểm tra Client A và Client B bằng evidence.
6. Thiết kế client lifetime, timeouts và retries theo operation semantics.
7. Test DNS/failover và socket pressure.
8. Bổ sung observability/alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tạo `HttpClient`/handler mới per request như default solution.
- Biết connection pooling thuộc `HttpMessageHandler`/`SocketsHttpHandler`.
- Nhận ra long-lived pooled connections và DNS changes cần lifecycle policy có chủ đích.
- Tách timeout nguyên nhân thay vì gộp mọi `TaskCanceledException`.
- Nhận ra retry × instances × concurrency tạo amplification.
- Chỉ retry operations/failures có semantics an toàn.

### Điểm cộng

- Biết `IHttpClientFactory` quản lý/recycle handler lifetime và hỗ trợ named/typed clients.
- Đề cập `PooledConnectionLifetime` để buộc connections được thay định kỳ theo DNS/failover needs.
- Phân biệt `PooledConnectionIdleTimeout` và lifetime.
- Có connect timeout riêng và overall/request timeout budget.
- Có exponential backoff + jitter và retry budget.

### Senior+

- Correlate DNS TTL với `PooledConnectionLifetime` thay vì chọn số ngẫu nhiên.
- Xem retry, timeout, concurrency limit/circuit behavior như một resilience budget tổng thể.
- Kiểm tra SNAT/ephemeral-port pressure theo hosting topology, không khẳng định mọi `TIME_WAIT` đều là socket exhaustion.
- Thiết kế failover test chủ động: đổi DNS/backend trong lúc giữ sustained traffic rồi quan sát connection replacement.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng stabilization. Nếu retries đang làm traffic tăng 4 lần trong khi Payroll degraded, có thể tạm giảm retry count hoặc áp concurrency/rate protection theo runbook để tránh self-amplification. Không restart toàn bộ instances ngay vì restart có thể xóa evidence và tạo đồng thời connection storm.

Sau đó phân loại theo instance. Nếu chỉ một subset instances fail và restart tạm sửa, tôi muốn xem:

- dependency duration/error code theo instance;
- TCP connect/TLS errors;
- DNS result và resolution timing;
- active/new connections;
- TIME_WAIT/ephemeral/SNAT counters tùy environment;
- handler/client implementation được route tới từng operation;
- downstream telemetry cùng timestamp.

`HttpClient` bản thân không phải “một socket”. Underlying `SocketsHttpHandler` giữ connection pools theo endpoint. Reusing handler giúp reuse connections, giảm TCP/TLS overhead và tránh churn. Vì vậy `new HttpClient()` cùng handler mới cho mỗi request là pattern nguy hiểm ở high throughput: dispose client/handler không có nghĩa network resources ngay lập tức biến mất; connection churn có thể tăng TIME_WAIT/port pressure.

Nhưng “một static client sống mãi” cũng không tự động là policy hoàn hảo. Long-lived pooled connections có thể tiếp tục nói chuyện với backend cũ cho đến khi connection đóng. Khi DNS/failover semantics yêu cầu connections refresh, cấu hình `PooledConnectionLifetime` có thể giới hạn tuổi của connection trong pool để connections mới định kỳ resolve/connect lại. Giá trị phải dựa trên DNS TTL, load-balancer behavior, failover SLO và connection establishment cost.

Với modern .NET, tôi thường dùng typed client qua `IHttpClientFactory` hoặc long-lived `HttpClient` với properly configured `SocketsHttpHandler`. Ví dụ:

```csharp
builder.Services
    .AddHttpClient<PayrollClient>(client =>
    {
        client.BaseAddress = new Uri("https://payroll.internal.example");
        client.Timeout = Timeout.InfiniteTimeSpan;
    })
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(2),
        PooledConnectionIdleTimeout = TimeSpan.FromMinutes(1),
        ConnectTimeout = TimeSpan.FromSeconds(3),
        MaxConnectionsPerServer = 100
    });
```

Các con số chỉ là ví dụ; phải load test và khớp environment. `MaxConnectionsPerServer` cũng không nên copy mù quáng: quá thấp tạo queue, quá cao có thể đẩy overload sang downstream.

Timeout nên là budget. Nếu request inbound có SLO 2 giây, một downstream timeout 30 giây × 4 attempts là vô nghĩa. Có thể tách connect timeout ngắn, per-attempt timeout và overall operation deadline. Cancellation từ inbound request nên propagate khi caller không còn cần kết quả.

Retry chỉ dùng cho transient classes phù hợp. GET/idempotent reads thường dễ retry hơn POST tạo side effect. Với write, cần idempotency key hoặc documented safe retry semantics. Backoff cần jitter để 8 instances không đồng loạt retry ở cùng millisecond. Retry count phải được tính cùng timeout và concurrency; ba layers đều retry là một anti-pattern nếu không có centralized policy.

DNS shell trả IP mới không chứng minh process đang dùng IP nào cho existing connections. Tôi muốn dependency/network trace hoặc controlled experiment. Nếu suspected stale connections, failover test phải chạy sustained traffic, đổi backend/DNS, rồi đo thời gian các connections chuyển sang endpoint mới với từng `PooledConnectionLifetime`.

Nếu suspected socket/SNAT pressure, chứng minh bằng port/connection counters và failure codes. TIME_WAIT tăng một mình không đủ kết luận; cần xem available port/SNAT utilization, connection creation rate và whether Client A volume correlate với incident.

Telemetry dài hạn:

- request count/error/latency per downstream operation;
- retry attempt count và retry outcome;
- timeout category;
- connection establishment latency/errors;
- active/queued outbound requests;
- instance/version dimension;
- DNS/failover test signals;
- downstream 429/5xx split.

Không nên log full sensitive URLs/tokens. Alert vào retry amplification hoặc downstream saturation trước khi user-facing p99 bùng nổ.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn giữa ‘new HttpClient mỗi request’ và ‘static forever’ bằng slogan. Tôi cần xem handler và pooled connection lifetime. Per-request handler tạo connection churn và có thể gây TIME_WAIT/SNAT pressure. Long-lived handler thì tốt cho reuse, nhưng connections cũng cần refresh phù hợp DNS/failover behavior.

Trong incident tôi giảm retry amplification nếu nó đang gây cascade, rồi correlate timeout theo instance với connect/TLS/server timings, connection counters và Payroll telemetry. DNS shell thấy IP mới chưa chứng minh existing pooled connections đã chuyển.

Tôi sẽ dùng typed client qua `IHttpClientFactory` hoặc một configured `SocketsHttpHandler`, đặt `PooledConnectionLifetime` dựa trên DNS/failover requirement, có connect timeout và overall operation budget. Retry chỉ cho transient + idempotent operations, exponential backoff có jitter và không nhân lên qua nhiều layers.

Sau đó tôi chạy failover test dưới sustained load: đổi backend IP, đo recovery time, connection creation, error rate và port usage. Mục tiêu là chứng minh client thích nghi với endpoint change mà không tạo connection storm.”

## Câu hỏi đào sâu

1. Nếu DNS TTL là 30 giây nhưng một request có thể stream 10 phút, `PooledConnectionLifetime` có cắt ngang request đang chạy không và bạn mong đợi behavior gì?
2. Nếu Payroll POST hỗ trợ `Idempotency-Key`, retry policy cho connect timeout trước/sau khi bytes đã được gửi cần suy nghĩ gì?
3. Nếu networking chứng minh SNAT ports không hề cạn nhưng restart instance vẫn tạm sửa, bạn sẽ mở rộng hypotheses theo hướng nào?

## Lỗi trả lời thường gặp

- Nói “`HttpClient` phải singleton” mà không hiểu handler/connection lifetime.
- Tạo client mới cho từng request để “refresh DNS”.
- Thấy TIME_WAIT rồi khẳng định socket exhaustion.
- Retry mọi exception ba lần mà không xét idempotency/deadline.
- Restart toàn fleet trước khi thu evidence.

## Thang điểm 0–10

- **0–2:** Chỉ đổi static/new `HttpClient` theo kinh nghiệm cá nhân.
- **3–4:** Biết reuse client nhưng chưa hiểu DNS/handler pooling hoặc retry amplification.
- **5–6:** Điều tra đúng layers, dùng factory/handler lifetime và timeout/retry hợp lý.
- **7–8:** Có evidence-driven failover/socket diagnosis, DNS-aware lifetime, jitter/idempotency và load testing.
- **9–10:** Kết nối network internals → connection pooling → DNS/failover → resilience budget → production evidence, đồng thời tránh both over-retry và premature complexity.

# Câu 3 — Multi-tenant SaaS: chỉ dùng `TenantId` + EF Core Global Query Filter đã đủ isolation chưa, hay cần Row-Level Security / database riêng?

**Loại câu hỏi:** Architecture / Security / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, EF Core, SQL Server, multi-tenancy, authorization, Global Query Filters, Row-Level Security, data isolation, migrations, backup/restore, compliance, observability, architecture trade-offs

## Bối cảnh

Một B2B employee-management product chuẩn bị chuyển từ single-customer deployments sang multi-tenant SaaS.

Dự kiến trong 18 tháng:

- 300–500 tenants;
- tenant nhỏ có vài chục users, tenant lớn 30.000–80.000 users;
- SQL Server/Azure SQL là transactional store chính;
- ASP.NET Core + EF Core;
- phần lớn tables có thể gắn `TenantId`;
- một số global reference tables dùng chung;
- một số customers yêu cầu export toàn bộ dữ liệu của riêng họ;
- 5–10 enterprise customers có thể yêu cầu stronger isolation/compliance sau này;
- team 8–10 developers, chưa muốn vận hành hàng trăm databases nếu không cần;
- cross-tenant analytics cần aggregate ở mức product, nhưng tenant users tuyệt đối không được đọc data của tenant khác.

Một engineer đề xuất shared database/shared schema và EF Core Global Query Filter:

```csharp
modelBuilder.Entity<Employee>()
    .HasQueryFilter(x => x.TenantId == _tenantContext.TenantId);
```

Một engineer khác yêu cầu SQL Server Row-Level Security vì “defense in depth”.

Security architect đề xuất database-per-tenant để blast radius nhỏ nhất.

Product team còn muốn support staff có controlled cross-tenant troubleshooting access, phải audit đầy đủ.

## Câu hỏi chính

Bạn sẽ chọn tenant-isolation architecture như thế nào giữa shared schema + application filters, SQL Row-Level Security, schema-per-tenant và database-per-tenant? Hãy phân tích security boundary, performance/noisy-neighbor risk, migrations, connection pooling, backup/restore, tenant export/delete, support access, analytics và operational cost. Nếu chọn hybrid model, hãy mô tả routing/ownership/migration path sao cho không biến hệ thống thành hai kiến trúc không kiểm soát.

## Câu hỏi làm rõ nên cân nhắc

1. Compliance/contracts có yêu cầu physical/logical isolation cụ thể hay chỉ yêu cầu chứng minh access control?
2. Restore một tenant riêng lẻ từ backup là hard requirement hay export/import application-level là đủ?
3. Largest tenant chiếm bao nhiêu % dữ liệu/throughput, và noisy-neighbor SLO là gì?
4. Có raw SQL, stored procedures, Dapper, ETL hoặc background jobs nào bypass EF Core không?
5. Support cross-tenant access cần break-glass, approval, time limit và audit như thế nào?

## Gợi ý tư duy

### Gợi ý 1

Global Query Filter là một developer convenience và guardrail, nhưng hãy hỏi nó có phải **security boundary duy nhất** mà bạn sẵn sàng đặt niềm tin cho mọi data path hay không.

### Gợi ý 2

Isolation không chỉ là “SELECT có TenantId”. Hãy xét unique constraints, foreign keys, caches, background jobs, object storage keys, search indexes, exports, logs và backups.

### Gợi ý 3

Database-per-tenant tăng isolation nhưng cũng nhân migration, connection management, monitoring, backup/restore và incident surface. Hybrid có thể hợp lý nếu tenant tiers thực sự khác biệt.

## Cấu trúc trả lời đề xuất

1. Chốt threat model/compliance/SLO.
2. Inventory mọi data path, không chỉ EF queries.
3. So sánh isolation models theo security và operations.
4. Chọn default tier và exception criteria.
5. Thiết kế tenant context/authentication/authorization.
6. Thiết kế data model, indexes và constraints tenant-aware.
7. Xử lý support, analytics, backup/export/delete.
8. Mô tả migration path/hybrid routing.
9. Test isolation và observability liên tục.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi EF Global Query Filter là toàn bộ multi-tenant security strategy.
- Tenant identity phải đến từ trusted authenticated context, không chỉ request body/query string.
- Mọi unique key/foreign-key/access path cần xem xét tenant dimension.
- Phân tích raw SQL/background jobs/cache/search/blob storage ngoài EF Core.
- So sánh operational cost của database-per-tenant thực tế.
- Có automated cross-tenant isolation tests.

### Điểm cộng

- Dùng composite keys/indexes như `(TenantId, BusinessKey)` khi semantics yêu cầu.
- Cân nhắc RLS như defense-in-depth cho shared DB nếu team có khả năng vận hành/test session context đúng.
- Tách product analytics pipeline khỏi tenant-facing transactional access.
- Có controlled support impersonation/break-glass flow thay vì special “admin bypass” khó audit.
- Thiết kế tenant-aware cache keys và object-storage prefixes/authorization.

### Senior+

- Nhận ra RLS cũng có failure modes: session context, privileged roles, migrations, query plans/performance, connection pooling hygiene.
- Có hybrid policy: shared pool cho standard tenants, dedicated DB cho regulated/very-large tenants dựa trên explicit criteria.
- Thiết kế tenant placement registry/routing và online migration có verification/rollback.
- Có per-tenant resource/quota telemetry để phát hiện noisy neighbor.

## Hướng giải quyết tham khảo

Tôi sẽ không chọn database-per-tenant hoặc shared database chỉ từ số tenant. Trước hết phải chốt threat model và contractual requirements. Nếu một nhóm khách hàng bắt buộc physical isolation/dedicated encryption/independent restore theo contract, đó là hard driver. Nếu không, shared database có thể giảm operational cost rất lớn cho hàng trăm small tenants.

### Shared database + shared schema

Đây thường là điểm khởi đầu kinh tế nhất. Mọi tenant-owned row có `TenantId`; indexes và constraints được thiết kế tenant-aware. Ví dụ email chỉ unique trong tenant thì unique index là `(TenantId, NormalizedEmail)` chứ không phải chỉ `NormalizedEmail`.

EF Core Global Query Filter là guardrail hữu ích:

```csharp
modelBuilder.Entity<Employee>()
    .HasQueryFilter(e => e.TenantId == _tenantContext.TenantId);
```

Nhưng tôi không coi nó là security strategy duy nhất. Developer có thể dùng `IgnoreQueryFilters()`, raw SQL, stored procedure hoặc một data path không qua EF. Background jobs có thể resolve tenant context sai. Vì vậy tenant authorization phải được thiết kế ở application boundary, repository/query conventions phải được review/test, và mọi alternate path phải inventory.

Tenant ID không được lấy trực tiếp từ body rồi tin tưởng. Request đi qua authentication, membership/authorization xác định caller được access tenant nào, sau đó server tạo trusted tenant context. Nếu route có tenant slug/id, nó chỉ là resource selector và phải được authorize.

### SQL Row-Level Security

RLS có thể thêm defense in depth cho shared DB: database predicate tự lọc rows theo trusted session context. Nó đặc biệt hữu ích khi có nhiều data-access paths và security risk đủ lớn.

Nhưng RLS không phải checkbox miễn phí. Connection pooling làm session-context hygiene quan trọng; mỗi checked-out connection phải có đúng tenant context và không leak context từ prior usage. Privileged roles/bypass behavior phải kiểm soát. Migrations, admin jobs, support/reporting và query performance cần test với policy thật. Nếu team không hiểu/vận hành RLS tốt, một cấu hình sai có thể tạo false confidence.

Tôi sẽ spike RLS với representative workload trước khi quyết định default. Nếu dùng, integration tests phải cố truy cập cross-tenant qua EF, raw SQL và stored procedures, đồng thời verify context reset/reuse dưới connection pooling.

### Database-per-tenant

Dedicated DB tạo isolation blast radius tốt hơn và có lợi cho per-tenant backup/restore, maintenance hoặc noisy-neighbor control. Nhưng với 500 tenants nó tạo nhiều operational objects: schema migration orchestration, connection strings/secrets, health monitoring, backup policy, alerting và version skew. Connection pools cho hàng trăm databases cũng cần xem xét.

Tôi chỉ mặc định database-per-tenant khi compliance/restore/isolation requirements biện minh chi phí. Nếu chỉ 5–10 enterprise tenants cần dedicated isolation, hybrid có thể hợp lý.

### Hybrid model

Ví dụ:

- standard tenants → shared Azure SQL databases theo pool/shard;
- very-large/regulatory tenants → dedicated database;
- một `TenantPlacement` registry map `TenantId → data store/shard`;
- application data access resolve placement từ trusted tenant context;
- schema contract/version được quản lý chung, migration orchestration biết tất cả placements.

Không nên để business code rải `if (enterprise) use different repository`. Routing nằm ở data-access infrastructure. Dedicated và shared stores nên giữ cùng logical schema/API càng lâu càng tốt để tránh hai sản phẩm.

Tenant migration shared → dedicated là workflow có state:

1. tạo target DB/schema version đúng;
2. copy/backfill tenant data;
3. validate row counts/checksums/business invariants;
4. xử lý delta bằng dual-write/change capture hoặc maintenance window tùy SLO;
5. atomic switch placement registry;
6. observe;
7. rollback window;
8. xóa source sau retention/safety period.

Không tự động dùng dual-write nếu maintenance window vài phút được chấp nhận; chọn complexity theo requirement.

### Những nơi thường bị quên

Isolation phải cover:

- cache key: luôn include tenant dimension;
- Blob/object storage: server-owned tenant prefix/container + authorization, không tin path từ client;
- search index: tenant filter/partition và query construction an toàn;
- message/job payload: tenant ID + authorization provenance;
- logs/traces: tránh PII leakage và support search phải audited;
- exports: query phải tenant-scoped, output access cũng tenant-scoped;
- analytics: copy dữ liệu vào governed analytics pipeline thay vì cấp tenant-facing app quyền query cross-tenant trực tiếp.

### Support access

Support không nên có một boolean `IsAdmin` rồi bypass mọi filter. Với sensitive access, dùng explicit support session/break-glass flow: operator identity, target tenant, ticket/reason, approval nếu cần, expiration, scope, immutable audit log. UI phải cho thấy đang ở tenant nào để giảm human error.

### Noisy neighbor

Shared DB cần per-tenant request/query/job quotas và telemetry. Theo dõi DB CPU/IO không đủ; cần tenant dimension ở traces/logs và sampled/controlled metrics để biết tenant lớn nào gây load. Có thể đưa tenant rất nóng sang dedicated placement nếu threshold/SLO được xác định trước.

### Testing

Tôi sẽ tạo automated isolation matrix:

- tenant A user thử đọc/update/delete tenant B resource bằng guessed ID;
- raw SQL/repository paths;
- background jobs;
- cache collision tests;
- search/export/download URLs;
- support mode;
- connection-pool reuse nếu có RLS;
- migration shared↔dedicated.

Security test phải chạy CI, không chỉ penetration test hàng năm.

## Mẫu trả lời trong phỏng vấn

“Tôi không coi Global Query Filter là security boundary duy nhất. Nó là guardrail rất hữu ích, nhưng raw SQL, `IgnoreQueryFilters`, background jobs, cache, search và blob storage đều có thể bypass nó. Tenant identity phải được resolve từ authenticated/authorized context, rồi mọi data path dùng trusted tenant context.

Với 300–500 tenants và chỉ một nhóm nhỏ cần stronger isolation, tôi nghiêng về shared schema cho standard tenants để giữ operations đơn giản, thiết kế composite tenant-aware constraints/indexes và thêm isolation tests. Tôi sẽ đánh giá SQL RLS như defense in depth nếu threat model xứng đáng, nhưng chỉ sau khi chứng minh session-context handling đúng với connection pooling và admin/background paths.

Database-per-tenant tôi dành cho contractual/compliance requirement, independent restore hoặc tenants đủ lớn gây noisy neighbor. Nếu dùng hybrid, tôi tạo tenant-placement registry và một data-access routing layer; business code không biết tenant nằm shared hay dedicated. Migration shared→dedicated là workflow có backfill, validation, cutover và rollback.

Ngoài SQL tôi audit cache keys, Blob paths, search, messages, exports và logs. Support access dùng explicit time-bound audited session chứ không có global bypass. Cuối cùng, tôi muốn CI có cross-tenant negative tests và production telemetry cho per-tenant load/authorization failures.”

## Câu hỏi đào sâu

1. Nếu dùng RLS với `SESSION_CONTEXT`, bạn bảo đảm context không leak giữa tenants khi ADO.NET connection pooling reuse physical connections thế nào?
2. Một customer yêu cầu point-in-time restore riêng của họ về 14:05 hôm qua nhưng vẫn đang ở shared database; bạn có thể đáp ứng theo những cách nào và requirement đó có làm thay đổi placement strategy không?
3. Tôi muốn đưa mọi enterprise tenant sang database riêng từ ngày đầu “để an toàn”; bạn sẽ định lượng operational cost/risk và phản biện hoặc đồng ý theo tiêu chí nào?

## Lỗi trả lời thường gặp

- Tin rằng có `TenantId` column là đủ multi-tenancy.
- Lấy tenant ID từ request body rồi áp filter mà không authorize membership.
- Cho rằng Global Query Filter không thể bị bypass.
- Cho rằng RLS tự động giải quyết mọi security problem.
- Chọn database-per-tenant nhưng không có migration/versioning/connection/monitoring strategy.
- Quên cache, search, Blob, exports và background jobs.

## Thang điểm 0–10

- **0–2:** Chọn một isolation model theo khẩu hiệu, thiếu threat model.
- **3–4:** Có tenant filter/authorization nhưng bỏ sót alternate data paths và operations.
- **5–6:** So sánh shared/RLS/dedicated hợp lý, có trusted tenant context và isolation tests.
- **7–8:** Thiết kế hybrid/routing/migration, support access, noisy-neighbor controls và non-SQL isolation.
- **9–10:** Cân bằng security/compliance/performance/restore/operational cost chặt chẽ, có defense-in-depth mà không tạo false confidence hoặc vận hành quá mức cần thiết.
