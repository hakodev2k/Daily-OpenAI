# Code Review Challenge 1 — Hangfire job gửi thông báo bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một Hangfire job đọc các notification đang `Pending`, gửi qua external API rồi cập nhật trạng thái `Sent`. Hệ thống chạy nhiều Hangfire worker trên hai application instances. Bình thường hoạt động tốt, nhưng khi traffic tăng hoặc external API chậm, một số khách hàng nhận cùng thông báo hai lần. Có lúc API bên ngoài đã nhận request nhưng job bị retry do exception.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task SendPendingAsync()
    {
        var items = await _db.Notifications
            .Where(x => x.Status == "Pending")
            .OrderBy(x => x.CreatedAt)
            .Take(100)
            .ToListAsync();

        foreach (var item in items)
        {
            try
            {
                var response = await _httpClient.PostAsJsonAsync(
                    "/notifications",
                    new { item.UserId, item.Message });

                response.EnsureSuccessStatusCode();

                item.Status = "Sent";
                item.SentAt = DateTime.UtcNow;
                await _db.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed to send notification {NotificationId}", item.Id);
                throw;
            }
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Tìm các vấn đề correctness.
2. Phân tích rủi ro concurrency, retry và performance.
3. Giải thích production impact.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách test khi nhiều worker chạy đồng thời và external API lỗi.
7. Đề xuất logs, traces và metrics.

## Câu hỏi gợi mở

- Hai worker có thể đọc cùng một notification không?
- Điều gì xảy ra nếu external API xử lý thành công nhưng connection bị ngắt trước khi client nhận response?
- Transaction database có thể làm external HTTP call trở thành exactly-once không?
- Retry của Hangfire tương tác thế nào với side effect bên ngoài?
- Có cần lưu trạng thái xử lý trung gian hoặc idempotency key không?

## Gợi ý

### Gợi ý 1

Đừng chỉ nhìn vào `SaveChangesAsync`; hãy xác định ranh giới atomicity giữa database và external system.

### Gợi ý 2

Một distributed job thường phải giả định **at-least-once execution** và thiết kế side effect theo hướng idempotent.

## Kết quả code review tham khảo

### 1. Không có cơ chế claim/lock notification — High

**Problem:** nhiều worker có thể query cùng các row `Pending`.  
**Why:** đọc rồi gửi là hai bước riêng biệt, không có atomic claim/concurrency guard.  
**Impact:** duplicate notification dưới concurrency.  
**Fix:** claim batch atomically bằng trạng thái `Processing` + worker/lease, hoặc database-specific locking/atomic update phù hợp.

### 2. External side effect không idempotent — Critical

**Problem:** request có thể được external API xử lý nhưng client không nhận được success response.  
**Why:** distributed systems có failure window giữa remote commit và local acknowledgement.  
**Impact:** Hangfire retry gửi lại và người dùng nhận duplicate.  
**Fix:** tạo stable idempotency key theo notification ID nếu provider hỗ trợ; nếu không, thiết kế adapter/deduplication phù hợp với khả năng provider.

### 3. Retry toàn job sau lỗi giữa batch — High

**Problem:** `throw` làm job fail sau một item lỗi. Các item trước đó đã tạo side effect; lần retry phải xử lý cẩn thận.  
**Impact:** tăng duplicate risk và head-of-line blocking.  
**Fix:** xử lý từng item với state/retry count rõ ràng; chỉ retry item cần thiết hoặc enqueue từng notification thành job độc lập khi phù hợp.

### 4. Không có trạng thái failure/retry metadata — Medium

Không lưu `AttemptCount`, `LastAttemptAt`, `LastError`, `NextAttemptAt`; khó kiểm soát backoff và điều tra incident.

### 5. Cancellation không được truyền xuống — Medium

Không nhận `CancellationToken`; shutdown/deployment khó dừng công việc có kiểm soát.

### 6. SaveChanges cho từng item — Medium

Tạo nhiều database round trips. Với batch lớn, throughput giảm. Tuy nhiên không nên batch-save một cách mù quáng vì cần bảo toàn state của từng side effect.

### 7. Response không được dispose rõ ràng — Low

Nên `using var response = ...` để giải phóng response content/resource sớm, đặc biệt khi throughput lớn.

### 8. Status dùng magic string — Low

Dễ typo và khó đảm bảo state transition hợp lệ. Nên dùng enum/value mapping hoặc constants và enforce transition.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định notification đã được **claim atomically** bởi repository và provider hỗ trợ idempotency key:

```csharp
public sealed class NotificationJob
{
    private readonly INotificationRepository _repository;
    private readonly HttpClient _client;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        INotificationRepository repository,
        HttpClient client,
        ILogger<NotificationJob> logger)
    {
        _repository = repository;
        _client = client;
        _logger = logger;
    }

    public async Task SendPendingAsync(CancellationToken cancellationToken)
    {
        var items = await _repository.ClaimBatchAsync(100, cancellationToken);

        foreach (var item in items)
        {
            cancellationToken.ThrowIfCancellationRequested();

            try
            {
                using var request = new HttpRequestMessage(HttpMethod.Post, "/notifications")
                {
                    Content = JsonContent.Create(new
                    {
                        item.UserId,
                        item.Message
                    })
                };

                request.Headers.TryAddWithoutValidation(
                    "Idempotency-Key", item.Id.ToString());

                using var response = await _client.SendAsync(request, cancellationToken);
                response.EnsureSuccessStatusCode();

                await _repository.MarkSentAsync(item.Id, DateTime.UtcNow, cancellationToken);
            }
            catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
            {
                throw;
            }
            catch (Exception ex)
            {
                await _repository.MarkFailedAttemptAsync(
                    item.Id, ex.Message, DateTime.UtcNow, cancellationToken);

                _logger.LogError(ex,
                    "Notification {NotificationId} failed", item.Id);
            }
        }
    }
}
```

`ClaimBatchAsync` phải thực hiện claim bằng một thao tác/transaction có concurrency protection thích hợp cho SQL Server/PostgreSQL. Không nên triển khai bằng `SELECT Pending` rồi lần lượt `UPDATE` mà không có guard, vì vẫn còn race window.

## Trade-offs

Atomic claiming làm state machine phức tạp hơn và cần xử lý lease timeout khi worker chết. Tách mỗi notification thành một Hangfire job giúp isolation/retry tốt hơn nhưng tăng số job và overhead. Database transaction không thể tự đảm bảo exactly-once cho HTTP side effect; idempotency tại boundary thường quan trọng hơn. Outbox hữu ích khi cần atomically ghi business data và ý định gửi message, nhưng vẫn cần idempotent consumer/provider cho end-to-end reliability.

## Cách kiểm thử

1. **Concurrency test:** chạy 10 worker claim cùng batch; mỗi notification chỉ được claim bởi một worker tại một thời điểm.
2. **Ambiguous failure:** fake provider xử lý request rồi làm client nhận timeout; retry với cùng idempotency key không tạo side effect thứ hai.
3. **Worker crash:** worker chết sau claim; lease hết hạn và item có thể được recovery.
4. **Partial batch failure:** item thứ 3 lỗi không làm mất trạng thái chính xác của các item khác.
5. **Load test:** đo throughput, DB round trips, external latency và queue age khi backlog tăng.

## Quan sát trong production

Theo dõi `pending_count`, `processing_count`, `retry_count`, `dead_letter/failed_count`, notification age, send latency và duplicate-detection count. Log `NotificationId`, attempt, worker/job ID và provider correlation ID. Trace từ Hangfire job → DB claim → HTTP dependency. Alert khi backlog age, retry rate hoặc provider error rate vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Outbox pattern giải quyết phần nào của bài toán và phần nào nó không giải quyết?
2. Nếu provider không hỗ trợ idempotency key, bạn giảm duplicate risk thế nào?
3. Bạn chọn một job cho mỗi notification hay batch job trong trường hợp nào?

# Code Review Challenge 2 — Search API tải dữ liệu vào memory trước khi filter

**Chủ đề:** EF Core query execution, SQL performance, cancellation, API correctness  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một ASP.NET Core API tìm outlet theo country, keyword và bounding box. Bảng có hàng triệu records. QA thấy một số request mất vài giây và application memory tăng mạnh khi nhiều người pan/zoom bản đồ cùng lúc. Endpoint chủ yếu là read-only.

## Đoạn code cần review

```csharp
[HttpGet("outlets")]
public async Task<IActionResult> Search(
    string country,
    string? keyword,
    double minLat,
    double maxLat,
    double minLng,
    double maxLng)
{
    var outlets = await _db.Outlets
        .Where(x => x.Country == country)
        .ToListAsync();

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        outlets = outlets
            .Where(x => x.Name.ToLower().Contains(keyword.ToLower()))
            .ToList();
    }

    var result = outlets
        .Where(x => x.Latitude >= minLat && x.Latitude <= maxLat)
        .Where(x => x.Longitude >= minLng && x.Longitude <= maxLng)
        .OrderBy(x => x.Name)
        .Select(x => new
        {
            x.Id,
            x.Name,
            x.Latitude,
            x.Longitude,
            x.Description
        })
        .ToList();

    _logger.LogInformation(
        "Search {Country} {Keyword} returned {@Result}",
        country, keyword, result);

    return Ok(result);
}
```

## Nhiệm vụ của ứng viên

1. Tìm correctness/performance risks.
2. Xác định phần nào chạy trong database và phần nào chạy trong memory.
3. Giải thích production impact khi dataset và concurrency tăng.
4. Ưu tiên issue.
5. Viết lại query hợp lý hơn.
6. Đề xuất test performance/correctness.
7. Đề xuất observability.

## Câu hỏi gợi mở

- `ToListAsync()` đầu tiên thay đổi query pipeline thế nào?
- Endpoint read-only có cần EF Core tracking không?
- Có nên trả toàn bộ matching rows cho map viewport không?
- Logging toàn bộ result có ảnh hưởng gì?
- Bounding box input cần validation gì?

## Kết quả code review tham khảo

### 1. Materialize quá sớm — High

`ToListAsync()` sau filter country tải toàn bộ outlet của country vào application. Keyword, bounding box, sort và projection sau đó chạy trong memory. Với dataset lớn, điều này tăng DB transfer, allocation, GC pressure và latency.

**Fix:** xây dựng `IQueryable` đầy đủ rồi materialize một lần ở cuối.

### 2. Không giới hạn result size — High

Viewport lớn có thể trả lượng dữ liệu rất lớn, gây DB/API/network pressure. Cần business limit, pagination hoặc map-specific aggregation/clustering tùy requirement.

### 3. Query read-only vẫn tracking entities — Medium

Nếu không cần update entity, `AsNoTracking()` giảm tracking overhead. Projection trực tiếp cũng giúp tránh materialize entity đầy đủ.

### 4. `ToLower()` trong memory và semantics không rõ — Medium

Case-insensitive search phụ thuộc database/collation/provider. Không nên tự giả định một expression sẽ có cùng semantics/performance trên SQL Server và PostgreSQL. Chọn strategy phù hợp provider, requirement và index rồi kiểm tra generated SQL/execution plan.

### 5. Không validate bounding box — Medium

Cần kiểm tra latitude/longitude range và `min <= max`; trường hợp crossing antimeridian cần requirement riêng nếu hệ thống hỗ trợ toàn cầu.

### 6. Log toàn bộ result object — Medium

Structured logging hàng nghìn rows làm tăng allocation, log volume, chi phí và có thể lộ dữ liệu không cần thiết. Log criteria an toàn, count, duration và correlation ID thay vì payload đầy đủ.

### 7. Không truyền cancellation token — Medium

Client disconnect/deadline không hủy DB work kịp thời. Truyền `HttpContext.RequestAborted` hoặc action `CancellationToken` tới EF async operation.

## Phiên bản code đề xuất

```csharp
[HttpGet("outlets")]
public async Task<IActionResult> Search(
    string country,
    string? keyword,
    double minLat,
    double maxLat,
    double minLng,
    double maxLng,
    CancellationToken cancellationToken)
{
    if (string.IsNullOrWhiteSpace(country) ||
        minLat < -90 || maxLat > 90 || minLat > maxLat ||
        minLng < -180 || maxLng > 180 || minLng > maxLng)
    {
        return BadRequest("Invalid search criteria.");
    }

    var query = _db.Outlets
        .AsNoTracking()
        .Where(x => x.Country == country)
        .Where(x => x.Latitude >= minLat && x.Latitude <= maxLat)
        .Where(x => x.Longitude >= minLng && x.Longitude <= maxLng);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x => x.Name.Contains(term));
    }

    var result = await query
        .OrderBy(x => x.Name)
        .Select(x => new
        {
            x.Id,
            x.Name,
            x.Latitude,
            x.Longitude
        })
        .Take(500)
        .ToListAsync(cancellationToken);

    _logger.LogInformation(
        "Outlet search Country={Country} Count={Count}",
        country, result.Count);

    return Ok(result);
}
```

`Contains` ở đây chỉ minh họa việc giữ filter trong database. Case sensitivity và index strategy phải được thiết kế theo DB/provider và business semantics. Nếu outlet đã có spatial point và workload chủ yếu là map viewport, spatial predicate/index có thể phù hợp hơn; cần benchmark bằng generated SQL và execution plan thay vì mặc định rằng nó luôn nhanh hơn.

## Trade-offs

`Take(500)` bảo vệ service nhưng cần API contract rõ ràng để client biết kết quả bị giới hạn. Offset pagination đơn giản nhưng không lý tưởng cho dataset lớn/thay đổi liên tục; keyset pagination phù hợp hơn cho danh sách tuần tự. Spatial index có thể cải thiện viewport query nhưng thêm storage/write cost và phụ thuộc provider/query shape. Projection giảm dữ liệu nhưng nếu UI cần description thì có thể cần endpoint detail riêng.

## Cách kiểm thử

1. **Integration test:** xác nhận filter được translate và chỉ trả rows trong bounding box.
2. **Boundary test:** latitude/longitude invalid, min > max và viewport biên.
3. **Load test:** nhiều concurrent map requests trên dataset production-like; đo p50/p95/p99 và allocation.
4. **Database test:** xem generated SQL, execution plan, rows scanned/read và index usage.
5. **Cancellation test:** hủy request và xác nhận query được cancel/terminate theo khả năng provider.

## Quan sát trong production

Theo dõi endpoint duration p95/p99, result count, DB command duration, rows/read metrics có sẵn từ DB/APM, allocation/GC pressure và cancellation rate. Trace request → EF command. Không log toàn bộ result. Alert theo latency/error saturation thay vì chỉ average response time.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào spatial `STIntersects` + spatial index đáng dùng hơn latitude/longitude predicates?
2. Vì sao một query có thể nhanh hơn ngay cả trước khi thêm index?
3. Bạn benchmark thay đổi query trên QA thế nào để tránh kết luận sai do cache hoặc dataset không đại diện?
