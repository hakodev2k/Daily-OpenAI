# Câu 1 — Vì sao một middleware đo latency sai và làm mất correlation?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core middleware pipeline, exception handling, Activity, async, response lifecycle, Application Insights

## Bối cảnh

Một ASP.NET Core .NET 8 API chạy trên Azure App Service. Nhóm phát triển thêm middleware đo thời gian bằng `Stopwatch`, ghi log sau `await next(context)`, đồng thời tạo một `Activity` mới cho mỗi request. Dashboard báo p95 chỉ 35 ms, trong khi gateway đo p95 1,2 giây. Một số request 500 không có log hoàn tất; trace của dependency SQL đôi lúc không nằm dưới request span. Middleware được đặt trước `UseExceptionHandler`, còn response compression và authentication được cấu hình ở các vị trí khác. Chưa có bằng chứng về sampling, proxy buffering, streaming hoặc middleware ordering thực tế.

## Câu hỏi chính

Giải thích cơ chế thực thi pipeline, exception propagation, Activity context và thời điểm response hoàn tất; đề xuất cách đo và liên kết telemetry để giải thích chênh lệch latency.

## Câu hỏi làm rõ nên cân nhắc

1. Middleware đo từ khi nào đến khi nào; log ở `finally` hay chỉ sau `next`?
2. Gateway tính thời gian đến first byte hay last byte; endpoint có streaming không?
3. `Activity.Current` và OpenTelemetry/Application Insights instrumentation hiện tại hoạt động thế nào?
4. Sampling, reverse proxy, compression và exception handler nằm ở đâu?
5. Có correlation ID từ gateway và trace propagation qua outbound calls không?

## Gợi ý tư duy

### Gợi ý 1
Một `await next(context)` không đồng nghĩa client đã nhận hết bytes.

### Gợi ý 2
Một exception có thể ngăn code phía sau `next` chạy, nhưng `finally` vẫn thực thi khi stack unwind.

### Gợi ý 3
Xem parent/child span và lifecycle của response; không tạo root Activity tùy tiện.

## Cấu trúc trả lời đề xuất

1. Làm rõ định nghĩa latency và vị trí đo.
2. Mô tả request delegate, middleware nesting và exception propagation.
3. Đối chiếu gateway, server, dependency telemetry theo cùng trace.
4. Thử nghiệm phân lập streaming, proxy và sampling.
5. Đề xuất instrumentation, kiểm thử, rollout và cảnh báo.

## Ý chính của câu trả lời tốt

### Bắt buộc
Phân biệt thời gian xử lý pipeline với end-to-end transfer; giải thích `try/finally`, exception handler và `Activity.Current` trong asynchronous flow.

### Điểm cộng
Đề xuất so sánh TTFB/TTLB, kiểm tra response completion, traceparent, dependency spans, sampling và clock/aggregation windows.

### Senior+
Thiết kế semantic conventions, đo overhead và sampling hợp lý; tránh high-cardinality tags và thông tin nhạy cảm.

## Hướng giải quyết tham khảo

ASP.NET Core thực thi middleware theo thứ tự đăng ký ở chiều đi vào và đảo chiều khi quay ra. Middleware bọc `await next(context)` trong `try/finally` sẽ đo khoảng thời gian đến khi downstream delegate trả về hoặc ném exception; phép đo này **không bảo đảm** toàn bộ response đã được chuyển qua mạng tới client. Nếu downstream ném exception và không được xử lý bên trong, statement sau `await next` sẽ bị bỏ qua. `UseExceptionHandler` có thể bắt và tạo response lỗi tùy vị trí trong pipeline. Cần xác minh bằng trace thực tế, không suy diễn rằng mọi 500 đều thiếu log.

ASP.NET Core instrumentation thường đã tạo server Activity; tạo một root Activity mới không đúng parent có thể làm đứt trace. Dùng `Activity.Current`, propagation theo W3C trace context và instrumentation chuẩn. Middleware riêng chỉ bổ sung metric/tag cần thiết; `finally` ghi duration của pipeline, status khi đã xác định, error flag và trace ID, với lưu ý status có thể chưa phản ánh lỗi nếu exception được xử lý ở tầng ngoài. Tránh log token, header chứa secret và URL có PII.

Để điều tra: lấy cùng một trace ID, đối chiếu gateway total duration, request server duration, outbound dependencies, TTFB/TTLB, response size và compression. Tạo endpoint trả JSON nhỏ, endpoint streaming, endpoint ném exception trước/sau headers; đo riêng. Nếu server duration thấp nhưng gateway duration cao, kiểm tra buffering, network, downstream transfer, client read speed. Nếu instrumentation sampling làm thiếu dependency span, điều chỉnh sampling/diagnostic trước khi kết luận mất correlation. Kiểm tra `HttpContext.Response.OnCompleted` khi cần quan sát callback sau khi response hoàn tất ở server, nhưng không diễn giải nó là xác nhận client đã nhận bytes. Triển khai canary, so sánh p50/p95/p99 và tỷ lệ trace liên kết trước/sau.

## Mẫu trả lời trong phỏng vấn

“Em sẽ thống nhất trước định nghĩa latency: gateway đo end-to-end còn middleware có thể chỉ đo thời gian chạy downstream delegate. Em kiểm tra vị trí middleware, xử lý exception và việc log có nằm trong finally không. Tiếp theo em lấy trace ID để so sánh server span, SQL dependencies, gateway timing và thời gian truyền response. Activity thường đã được instrumentation tạo; em không tạo root span mới làm mất parent. Nếu chênh lệch chủ yếu ở streaming hoặc proxy, em xử lý đúng tầng đó thay vì tối ưu SQL theo cảm tính. Em bổ sung metric và kiểm thử failure path, rollout nhỏ rồi đối chiếu p95 cùng một cửa sổ thời gian.”

## Câu hỏi đào sâu

1. Nếu endpoint sử dụng Server-Sent Events, nên định nghĩa request duration và alert như thế nào?
2. Nếu sampling 10% khiến trace của lỗi 500 bị thiếu, bạn thay đổi chiến lược sampling ra sao?
3. Có nên thay toàn bộ middleware đo thời gian bằng OpenTelemetry instrumentation mặc định không? Khi nào vẫn cần custom metric?

## Lỗi trả lời thường gặp

- Đồng nhất server middleware duration với thời gian client nhận toàn bộ response.
- Chỉ thêm `Stopwatch` mà không kiểm tra exception path.
- Tạo Activity root mới và làm đứt trace hierarchy.
- Kết luận SQL chậm chỉ từ gateway p95.
- Gắn user ID/raw URL vào metric labels gây cardinality và rủi ro bảo mật.

## Thang điểm 0–10

- 0–2: Làm rõ latency, scope và triệu chứng.
- 0–3: Cơ chế pipeline, exception và Activity chính xác.
- 0–2: Giả thuyết và bằng chứng kiểm chứng.
- 0–2: Giải pháp, test, observability, trade-offs.
- 0–1: Trình bày rõ ràng, có thứ tự ưu tiên.

# Câu 2 — IIS recycle sau deployment khiến người dùng mất phiên và request 503

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC, session state, deployment, incident response, Octopus Deploy

## Bối cảnh

Một cổng quản trị ASP.NET MVC trên .NET Framework 4.5 chạy trên hai Windows Server sau load balancer. Sau bản phát hành bằng Octopus Deploy, một số người dùng bị đăng xuất hoặc mất dữ liệu form chưa lưu; khoảng 6 phút có 503 rải rác. IIS Application Pool có recycle, nhưng chưa rõ nguyên nhân là deployment thay `web.config`, scheduled recycle, memory limit, process crash hay load balancer health-check. Một số session có thể lưu InProc; authentication dùng cookie. Chưa có bằng chứng về machineKey, affinity, warm-up hoặc khả năng rollback package.

## Câu hỏi chính

Bạn sẽ điều hành incident này ra sao, phân biệt nguyên nhân cạnh tranh, phục hồi dịch vụ an toàn và thiết kế quy trình deploy giảm gián đoạn mà không vội rewrite ứng dụng?

## Câu hỏi làm rõ nên cân nhắc

1. 503 xuất hiện trên cả hai node hay chỉ một node, và tại những thời điểm nào?
2. Session mode, cookie auth, machineKey và load balancer affinity được cấu hình thế nào?
3. IIS Event Viewer, WAS/W3SVC logs và process crash dump ghi gì?
4. Deployment có sửa `bin`/`web.config`, chạy database migration hoặc restart App Pool không?
5. Có drain connections, warm-up, health checks và rollback artifact đáng tin cậy không?

## Gợi ý tư duy

### Gợi ý 1
Recycle, process crash và load balancer routing có thể cho triệu chứng giống nhau.

### Gợi ý 2
InProc session và multi-node routing tạo ra một lớp rủi ro riêng với cookie authentication.

### Gợi ý 3
Tách việc khôi phục dịch vụ khỏi điều tra root cause; đừng bỏ qua request đang xử lý khi drain node.

## Cấu trúc trả lời đề xuất

1. Xác định phạm vi ảnh hưởng, mức độ ưu tiên và thông báo incident.
2. Ổn định traffic, rollback hoặc loại node lỗi theo bằng chứng.
3. Thu thập event logs, IIS logs, deploy timeline, health probes.
4. Lập ít nhất ba giả thuyết cạnh tranh và cách bác bỏ.
5. Xác nhận root cause, fix, regression tests và release guardrails.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không coi recycle là root cause duy nhất; nhận diện rủi ro InProc session và cấu hình multi-node.

### Điểm cộng
Phân tích machineKey/cookie validation, overlapped recycling, application initialization, LB draining, deployment orchestration và rollback.

### Senior+
Thiết kế zero/low-downtime deployment có giới hạn, phân biệt session durability với auth validity và kế hoạch migration session có rủi ro tương thích.

## Hướng giải quyết tham khảo

**Impact:** định lượng số request 503, thời lượng, node, tỷ lệ mất session, tác vụ người dùng bị gián đoạn. **Stabilize:** nếu một node lỗi, drain và loại khỏi rotation sau khi kiểm tra capacity node còn lại; nếu cả hai lỗi do release, cân nhắc rollback package và schema compatibility. Tránh restart đồng loạt làm mất thêm session. Thông báo tình trạng và ETA theo bằng chứng.

**Evidence:** so sánh Octopus deployment timeline, IIS request logs, HTTPERR logs, Windows Event Viewer (WAS, W3SVC, .NET Runtime), application logs, memory/private bytes, process uptime, load balancer probe results. Kiểm tra cấu hình App Pool recycle, rapid-fail protection, application initialization, `web.config` changes và startup errors. Thu thập dump có kiểm soát nếu crash.

**Hypotheses:** (A) deployment cập nhật `bin`/`web.config` gây AppDomain restart; (B) memory pressure hoặc crash; (C) node nhận traffic trước khi warm-up hoàn tất; (D) session InProc bị mất khi recycle hoặc khi request chuyển node; (E) machineKey không đồng nhất khiến auth cookie không giải mã/validate được. Mỗi giả thuyết cần dấu hiệu đối chiếu, không khẳng định chỉ một nguyên nhân.

**Fix:** tổ chức deploy từng node với drain, health probe phản ánh readiness, warm-up, smoke test, rồi mới đưa node trở lại. Cố định machineKey giữa nodes theo cách quản lý secret phù hợp với ứng dụng legacy; xem xét out-of-process session khi yêu cầu duy trì session qua recycle, đồng thời kiểm tra serializability, latency, TTL và compatibility. Bảo vệ form dài bằng draft persistence nếu nghiệp vụ yêu cầu; session ngoài process không tự giải quyết form chưa lưu. Thiết lập immutable artifact, migration expand/contract, rollback drill và cảnh báo 503/process restarts. Overlapped recycle giúp giảm downtime trong một số trường hợp nhưng không đảm bảo giữ InProc session hay tránh mọi gián đoạn.

**Verification:** test login/cookie qua hai node, recycle từng node khi đang có session, deploy canary, load test dưới traffic và failure injection; theo dõi 503, login failures, session loss, startup time và error budget. Nếu dữ liệu cho thấy lỗi do crash chứ không phải deployment, ưu tiên phân tích dump và memory leak trước khi thay session architecture.

## Mẫu trả lời trong phỏng vấn

“Em ưu tiên xác định node nào lỗi và tác động đến người dùng, rồi drain node lỗi hoặc rollback nếu release là nguyên nhân khả dĩ và rollback an toàn. Em lấy timeline deploy, IIS/HTTPERR logs, Event Viewer và load balancer probes để phân biệt recycle do file change, crash, memory hay startup. Vì chạy hai node, em kiểm tra InProc session, machineKey và routing; mất session không nhất thiết cùng nguyên nhân với 503. Ngắn hạn em deploy từng node, warm-up và kiểm tra health trước khi nhận traffic. Dài hạn em xem xét session persistence, draft form, regression test qua recycle và đo tỷ lệ lỗi sau release. Em không đề xuất rewrite khi chưa chứng minh cần thiết.”

## Câu hỏi đào sâu

1. Nếu schema migration đã chạy và không backward-compatible, rollback binary có còn an toàn không?
2. Nếu chuyển sang distributed session làm latency tăng, bạn đo và quyết định thế nào?
3. Nếu App Pool recycle vẫn xảy ra định kỳ ngoài giờ deploy, làm sao chứng minh giải pháp đã xử lý đúng nguyên nhân?

## Lỗi trả lời thường gặp

- Restart cả hai node ngay lập tức mà không đánh giá ảnh hưởng.
- Coi sticky session là giải pháp bảo đảm session tồn tại qua recycle.
- Gộp auth cookie invalidation và InProc session loss thành một hiện tượng.
- Chỉ xem application logs, bỏ qua IIS/HTTPERR và Windows Event Viewer.
- Hứa zero downtime mà không kiểm tra startup, drain, session và schema compatibility.

## Thang điểm 0–10

- 0–2: Impact, stabilization, communication.
- 0–3: Evidence, hypotheses và xác minh root cause.
- 0–2: IIS/session/auth technical depth.
- 0–2: Rollout, rollback, testing, monitoring.
- 0–1: Ưu tiên và diễn đạt rõ ràng.

# Câu 3 — Thiết kế pipeline publish nội dung CMS ra website có CDN

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai CDN, SEO, content modeling, cache invalidation, Azure hosting, reliability, Vue.js

## Bối cảnh

Một website marketing có khoảng 200.000 trang đa ngôn ngữ, biên tập trong Optimizely CMS; một phần frontend dùng Vue.js. Trang sản phẩm kết hợp CMS blocks, dữ liệu sản phẩm từ một API nội bộ và đánh giá từ đối tác. Sau khi editor publish, nội dung cần hiển thị sớm nhưng không được lộ draft hoặc nội dung chưa được duyệt. Akamai CDN đang cache HTML; đội SEO yêu cầu canonical URL, sitemap, redirect và HTML có thể crawl. Hệ thống có nhiều vùng địa lý; yêu cầu consistency, traffic, SLA và ngân sách chưa được chốt.

## Câu hỏi chính

Bạn chọn kiến trúc render, publish, cache và invalidation nào để cân bằng editorial correctness, SEO, tốc độ, độ phức tạp và khả năng chịu lỗi của external APIs?

## Câu hỏi làm rõ nên cân nhắc

1. Publish-to-visible SLA là vài giây hay vài phút; có emergency unpublish không?
2. Nội dung nào public, personalized, region/language-specific hoặc cần authorization?
3. CDN có hỗ trợ purge theo URL/tag trong cấu hình thực tế và có rate limits nào?
4. Product/review API có freshness SLA, timeout và fallback policy gì?
5. Traffic theo region, preview workflow, rollback content version và SEO canonical policy ra sao?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt nội dung editorial, dữ liệu sản phẩm và dữ liệu người dùng cá nhân hóa.

### Gợi ý 2
Cache invalidation không chỉ là TTL; publish và unpublish có hậu quả khác nhau.

### Gợi ý 3
Chọn render strategy theo crawlability, personalization và operational cost; không mặc định SPA hoặc microservices.

## Cấu trúc trả lời đề xuất

1. Phân loại content, yêu cầu freshness và security.
2. Chọn rendering model và ownership của từng nguồn dữ liệu.
3. Thiết kế publish/versioning/invalidation với failure recovery.
4. Thiết kế caching và dependency degradation.
5. Định nghĩa SEO, test, observability, rollout và trade-offs.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không cache draft public; tách preview và publish; có chiến lược CDN invalidation, stale behavior, crawlable HTML và dependency fallback.

### Điểm cộng
Cache key theo locale/region, purge idempotency, content version, retries, observability, redirect/sitemap, circuit breaking và content rollback.

### Senior+
Phân tích consistency window, emergency unpublish với fail-closed, origin overload khi purge hàng loạt và chi phí vận hành của SSR/SSG/hybrid.

## Hướng giải quyết tham khảo

**Assumptions:** nếu trang marketing chủ yếu public, thay đổi không quá thường xuyên và SEO quan trọng, ưu tiên server-rendered hoặc pre-rendered HTML cho phần nội dung chính; Vue.js có thể hydrate các tương tác cần thiết. Không mặc định toàn bộ site là SPA. Với trang personalized, dùng endpoint riêng hoặc cache policy `private`/`no-store` phù hợp; không cache chung response chứa dữ liệu người dùng.

**Boundaries:** CMS sở hữu page types, blocks, editorial workflow và published content version; product API sở hữu giá/tồn kho và business semantics; review provider sở hữu rating. Composition layer quyết định timeout, fallback và render. Preview dùng endpoint/quyền riêng, auth và `no-store`, không đi vào public cache. Chỉ published version mới được origin public phục vụ; authorization phải được thực thi tại origin, không dựa vào CDN làm security boundary.

**Publish flow:** lưu phiên bản đã duyệt, phát sự kiện publish/unpublish có định danh duy nhất; worker xử lý idempotently, cập nhật materialized output hoặc origin cache, rồi purge các URL/locale/related listing cần thiết. Nếu sự kiện được tạo cùng transaction DB, dùng transactional outbox khi hạ tầng cho phép; nếu không, cần reconciliation job để quét chênh lệch published version và cache version. Purge thất bại phải retry có backoff, DLQ/alert và audit; không hứa atomic consistency giữa CMS và CDN. Emergency unpublish cần cơ chế fail-closed phù hợp SLA, ví dụ kiểm soát origin/edge và purge ưu tiên; TTL đơn thuần có thể không đáp ứng.

**Caching:** đặt `Cache-Control` theo content type, locale và freshness; thiết kế cache key có whitelist dimensions, tránh cache fragmentation; stale-while-revalidate chỉ dùng cho nội dung được phép stale, không dùng cho nội dung bị thu hồi vì lý do pháp lý. Dữ liệu giá/tồn kho có TTL ngắn hoặc fetch runtime nếu yêu cầu chính xác cao. External review API timeout và fallback sang snapshot đã kiểm duyệt nếu policy cho phép, hoặc ẩn module; không để provider failure làm toàn bộ trang 500.

**SEO & accessibility:** HTML có title, meta, canonical và hreflang phù hợp, server redirects 301/308 khi URL đổi, sitemap cập nhật sau publish, robots policy đúng môi trường. Test render bằng crawler không chạy JS, Lighthouse/Core Web Vitals, canonical/redirect chain và Playwright E2E cho preview/publish/unpublish.

**Deployment & telemetry:** canary render/cache changes, feature flag, versioned artifacts, rollback; dashboard publish-to-visible latency, purge failures, cache HIT/MISS, origin p95, 5xx, crawl errors, dependency timeouts. So sánh SSR vs SSG/hybrid theo số trang, tần suất publish và cost: pre-render toàn bộ 200.000 trang mỗi lần sửa một block là không hợp lý; incremental rebuild hoặc SSR caching có thể phù hợp hơn. Nếu yêu cầu personalization nặng và freshness sát thời gian thực, kiến trúc sẽ khác.

## Mẫu trả lời trong phỏng vấn

“Em bắt đầu bằng phân loại dữ liệu public, preview và personalized, rồi làm rõ publish latency và emergency unpublish. Với website marketing cần SEO, em nghiêng về server-rendered hoặc incremental pre-rendered HTML, Vue.js cho tương tác. CMS quản lý published version; product và review API giữ ownership riêng. Publish tạo invalidation event idempotent, có retry và reconciliation vì CDN không thể commit cùng CMS. Em tách cache key theo locale và tránh cache dữ liệu cá nhân. Khi review provider lỗi, module có fallback được business chấp nhận thay vì làm hỏng toàn trang. Em đo publish-to-visible latency, cache hit ratio, origin p95 và crawlability trước khi tối ưu. Nếu SLA unpublish rất chặt, em cần thêm cơ chế fail-closed thay vì dựa vào TTL.”

## Câu hỏi đào sâu

1. Nếu Akamai purge bị lỗi trong 20 phút sau khi unpublish nội dung nhạy cảm, bạn bảo đảm điều gì và giới hạn nào phải công bố?
2. Nếu 90% traffic là logged-in personalized, bạn có giữ nguyên SSR + CDN HTML cache không?
3. Nếu editor sửa shared block xuất hiện trên 50.000 trang, làm sao tránh purge storm và origin overload?

## Lỗi trả lời thường gặp

- Cho rằng CDN purge và CMS transaction có thể atomic.
- Cache HTML chứa dữ liệu cá nhân trên shared CDN.
- Dùng TTL dài cho nội dung phải emergency unpublish.
- Chọn SPA chỉ vì frontend dùng Vue.js mà bỏ qua SEO.
- Đề xuất microservices/queue phức tạp mà không xác định scale và failure requirements.

## Thang điểm 0–10

- 0–2: Requirement clarification, content classification.
- 0–2: Boundaries, rendering và security.
- 0–2: Publish/invalidation/failure recovery.
- 0–2: Trade-offs, performance, SEO.
- 0–2: Testing, monitoring, rollout và communication.

# Tổng kết hôm nay

## Kiến thức trọng tâm

ASP.NET Core pipeline và distributed tracing cần cùng định nghĩa thời gian đo; IIS recycle, session và load balancer là những failure domains khác nhau; CMS publish và CDN invalidation là quy trình eventually consistent cần reconciliation, security boundary và observability.

## Mẫu tư duy cần nhớ

1. Thống nhất metric definition trước khi so sánh số liệu.
2. Stabilize trước, xác minh root cause bằng nhiều nguồn telemetry.
3. Tách correctness, availability và freshness thành các requirement riêng.
4. Thiết kế retry cùng idempotency và reconciliation.
5. Chọn kiến trúc đơn giản nhất đáp ứng failure mode đã xác minh.
