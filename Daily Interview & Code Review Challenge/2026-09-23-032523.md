# Code Review Challenge 1 — Đồng bộ Elasticsearch trong request làm SQL đúng nhưng search mất dữ liệu

**Chủ đề:** C#/.NET, EF Core, Elasticsearch, distributed consistency, retry, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API quản lý product catalog. SQL Server là source of truth; Elasticsearch phục vụ full-text search. Khi product được cập nhật, API lưu SQL rồi index document sang Elasticsearch ngay trong cùng request để người dùng “thấy dữ liệu mới ngay”.

Production đôi lúc Elasticsearch timeout hoặc trả lỗi tạm thời. Support ghi nhận có product đã cập nhật đúng trong SQL nhưng search vẫn trả version cũ nhiều giờ. Team thêm retry vào controller nhưng sau đó latency tăng và một số request client nhận 500 dù SQL đã commit. API chạy nhiều instances và cùng một product có thể được cập nhật gần đồng thời.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/products")]
public sealed class ProductsController : ControllerBase
{
    private readonly CatalogDbContext _db;
    private readonly IElasticClient _elastic;
    private readonly ILogger<ProductsController> _logger;

    public ProductsController(
        CatalogDbContext db,
        IElasticClient elastic,
        ILogger<ProductsController> logger)
    {
        _db = db;
        _elastic = elastic;
        _logger = logger;
    }

    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id,
        UpdateProductRequest request,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (product is null)
            return NotFound();

        product.Name = request.Name;
        product.Description = request.Description;
        product.Price = request.Price;
        product.UpdatedAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        for (var attempt = 0; attempt < 3; attempt++)
        {
            try
            {
                var response = await _elastic.IndexDocumentAsync(product);
                if (response.IsValid)
                    return NoContent();
            }
            catch (Exception ex)
            {
                _logger.LogWarning(ex,
                    "Failed to index product {ProductId}", id);
            }
        }

        return StatusCode(500, "Search indexing failed");
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và consistency problems giữa SQL và Elasticsearch.
2. Phân tích failure window, retry và concurrent update risks.
3. Giải thích vì sao client có thể nhận 500 dù business update đã commit.
4. Ưu tiên findings theo production severity.
5. Đề xuất corrected design có source-of-truth và recovery semantics rõ ràng.
6. Nêu cách test dependency failure, ordering, concurrency và eventual consistency.
7. Nêu telemetry cần có để phát hiện index drift và backlog.

## Câu hỏi gợi mở

1. `SaveChangesAsync` thành công rồi Elasticsearch thất bại thì rollback SQL bằng cách nào?
2. Hai request cập nhật cùng product và index hoàn tất ngược thứ tự có thể tạo trạng thái gì?
3. Retry ngay trong HTTP request có đảm bảo eventual synchronization sau khi request kết thúc không?
4. Search index nên là source of truth hay projection có thể rebuild?
5. Hệ thống biết bằng cách nào rằng một document đã bị bỏ sót hàng giờ trước?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **dual write không atomic + thiếu durable recovery path**.

### Gợi ý 2

Hãy xem Elasticsearch như một projection bên ngoài transaction SQL; retry trong memory không biến hai systems thành một transaction.

## Kết quả code review tham khảo

### Critical — Dual write không có durable recovery

**Vấn đề:** SQL commit trước, Elasticsearch index sau; nếu bước thứ hai thất bại thì không có durable record yêu cầu đồng bộ lại.  
**Tại sao xảy ra:** Hai systems không cùng local transaction và retry chỉ tồn tại trong lifetime của request.  
**Ảnh hưởng production:** SQL chứa dữ liệu mới nhưng search có thể stale vô thời hạn.  
**Cách sửa:** Ghi product change và một durable outbox/index-work record trong cùng SQL transaction; worker xử lý projection sang Elasticsearch với retry và trạng thái quan sát được.

### High — API trả 500 sau khi business update đã commit

**Vấn đề:** Client thấy failure nhưng SQL update thực tế đã thành công.  
**Tại sao xảy ra:** HTTP outcome bị gắn với non-transactional projection sau commit.  
**Ảnh hưởng production:** Client/user có thể retry update, gây duplicate side effects hoặc hiểu sai trạng thái.  
**Cách sửa:** Xác định contract rõ: update source of truth thành công thì trả success/accepted phù hợp; trạng thái indexing được xử lý bất đồng bộ và monitor riêng nếu business cho phép eventual consistency.

### High — Concurrent updates có thể index ngược version

**Vấn đề:** Request A và B có thể commit/index theo timing khác nhau; index operation cũ hoàn tất sau operation mới.  
**Tại sao xảy ra:** Document không có ordering/version guard ở projection workflow.  
**Ảnh hưởng production:** Search có thể regress về dữ liệu cũ dù SQL đang đúng.  
**Cách sửa:** Mang version/sequence từ source of truth vào event/projection và bảo đảm consumer không áp dụng version cũ hơn version đã xử lý; lựa chọn implementation cụ thể phải phù hợp client/API Elasticsearch đang dùng.

### High — Retry nóng trong request khuếch đại dependency outage

**Vấn đề:** Ba lần retry liên tiếp không backoff/jitter và giữ request chờ Elasticsearch.  
**Tại sao xảy ra:** Retry được dùng thay durable delivery/recovery.  
**Ảnh hưởng production:** Tăng p95/p99, outbound load và nguy cơ cascading failure khi cluster search đang suy giảm.  
**Cách sửa:** Đưa retry sang worker với bounded exponential backoff/jitter và failure policy; request path không phụ thuộc synchronous search indexing nếu requirement cho phép.

### Medium — Cancellation semantics không nhất quán

**Vấn đề:** EF nhận `CancellationToken` nhưng Elasticsearch call không truyền token trong snippet.  
**Tại sao xảy ra:** Dependency calls không cùng cancellation policy.  
**Ảnh hưởng production:** Work có thể tiếp tục sau client cancellation; ngược lại không nên để client cancellation làm mất durable indexing work sau khi SQL commit.  
**Cách sửa:** Trước commit có thể honor request cancellation; sau commit, durable outbox đảm bảo projection độc lập với client lifetime.

### Medium — Không có validation/concurrency control cho business update

**Vấn đề:** Snippet không thể hiện validation của price/name hay optimistic concurrency cho simultaneous edits.  
**Tại sao xảy ra:** Last-write-wins đang được ngầm chấp nhận mà chưa rõ requirement.  
**Ảnh hưởng production:** User edits có thể ghi đè nhau ngoài ý muốn.  
**Cách sửa:** Làm rõ requirement; nếu cần phát hiện lost update, dùng concurrency token/version và trả conflict phù hợp.

### Medium — Logging thiếu projection state và correlation

**Vấn đề:** Chỉ log exception, không có durable attempt/version/backlog/correlation state.  
**Tại sao xảy ra:** Indexing được coi như một method call thay vì asynchronous projection.  
**Ảnh hưởng production:** Khó biết document nào stale và retry đến đâu.  
**Cách sửa:** Structured telemetry theo product ID, source version, outbox ID, attempt, latency, result và correlation ID.

### Low — Controller gánh orchestration infrastructure

**Vấn đề:** HTTP controller trực tiếp điều phối persistence và search projection.  
**Tại sao xảy ra:** Boundary business/application/infrastructure chưa rõ.  
**Ảnh hưởng production:** Khó test failure semantics và thay đổi delivery strategy.  
**Cách sửa:** Đưa update use case và durable publication vào application boundary phù hợp; không cần thêm Clean Architecture layers nếu một service đơn giản đã đủ.

## Phiên bản đề xuất

```csharp
public sealed class ProductService
{
    private readonly CatalogDbContext _db;

    public ProductService(CatalogDbContext db) => _db = db;

    public async Task<UpdateResult> UpdateAsync(
        Guid id,
        UpdateProductRequest request,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (product is null)
            return UpdateResult.NotFound;

        product.Name = request.Name;
        product.Description = request.Description;
        product.Price = request.Price;
        product.UpdatedAtUtc = DateTime.UtcNow;
        product.Version++;

        _db.SearchOutbox.Add(new SearchOutboxMessage
        {
            Id = Guid.NewGuid(),
            ProductId = product.Id,
            ProductVersion = product.Version,
            CreatedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
        return UpdateResult.Success;
    }
}

public sealed class SearchProjectionWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public SearchProjectionWorker(IServiceScopeFactory scopeFactory) =>
        _scopeFactory = scopeFactory;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _scopeFactory.CreateScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<SearchOutboxProcessor>();

            var processed = await processor.ProcessBatchAsync(stoppingToken);
            if (processed == 0)
                await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
        }
    }
}
```

`SearchOutboxProcessor` cần claim work an toàn khi có nhiều instances, đọc product/version từ source of truth, index document theo version policy, đánh dấu success chỉ sau khi Elasticsearch xác nhận, và retry có backoff. Chi tiết locking/claiming phải phù hợp SQL engine và throughput thực tế; không nên giả định một implementation duy nhất.

## Giải thích thiết kế sau khi sửa

SQL vẫn là source of truth. Product update và outbox record cùng local transaction nên không có window “SQL đã đổi nhưng không còn dấu vết cần index”. Search là projection eventual-consistent có thể retry/rebuild. Version giúp xử lý out-of-order delivery; worker tách dependency outage khỏi HTTP request.

Không cần mặc định thêm Service Bus: SQL outbox + worker có thể đủ cho một ứng dụng nếu throughput và operational requirements phù hợp. Nếu nhiều consumers hoặc independent scaling yêu cầu broker, outbox vẫn hữu ích để publish reliably nhưng complexity phải được justify.

## Trade-offs

- Search không còn guaranteed fresh ngay tại thời điểm HTTP response; cần xác định acceptable lag với Product.
- Outbox thêm storage, cleanup, worker và monitoring.
- Version/order handling làm projection phức tạp hơn nhưng tránh stale overwrite.
- Nếu business thực sự yêu cầu read-after-write search ngay lập tức, cần xem lại UX/read path hoặc consistency requirement thay vì giả vờ dual write là atomic.

## Cách kiểm thử

1. **Integration test:** SQL commit thành công trong khi Elasticsearch unavailable; outbox vẫn tồn tại và được xử lý sau recovery.
2. **Ordering/concurrency test:** phát version N và N+1 nhưng hoàn tất delivery đảo thứ tự; index cuối cùng phải phản ánh version mới nhất.
3. **Failure-path test:** worker crash sau index nhưng trước khi mark outbox complete; retry không được làm document regress.
4. **Load test:** backlog tăng khi Elasticsearch chậm rồi drain có kiểm soát sau recovery, không làm cluster bị retry storm.
5. **Database test:** nhiều worker instances claim batch mà không làm mất work hoặc xử lý uncontrolled duplicate.

## Quan sát trong production

Theo dõi outbox backlog depth/oldest age, indexing success/failure rate, retry count, Elasticsearch dependency latency/error, projection lag theo source version và số document drift phát hiện qua reconciliation. Log có `ProductId`, `ProductVersion`, `OutboxId`, correlation ID và attempt. Alert theo backlog age/failure ratio thay vì chỉ exception count.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn SQL outbox worker thay vì Azure Service Bus cho projection này?
2. Bạn thiết kế reconciliation job thế nào để phát hiện index drift mà không scan toàn bộ catalog quá thường xuyên?
3. Nếu Product yêu cầu search thấy update trong dưới 500 ms, requirement đó thay đổi design và SLA monitoring ra sao?

# Code Review Challenge 2 — Kubernetes rollout báo Ready quá sớm và làm traffic chạm vào Pod chưa khởi động xong

**Chủ đề:** Kubernetes, ASP.NET Core, probes, rolling deployment, resource limits, configuration, secrets, release safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API được chuyển từ Azure App Service sang Kubernetes như một lựa chọn hạ tầng mới mà team đang đánh giá. Sau deployment, rollout đôi lúc hoàn tất nhưng người dùng gặp 502/503 trong vài phút. Pod có thể mất 30–60 giây để warm up vì tải configuration, khởi tạo connection và kiểm tra dependency. Khi traffic tăng, một số Pod bị restart; team chưa biết đó là health probe, memory pressure hay application crash.

Manifest hiện tại deploy được và hoạt động ở tải thấp. Team muốn tăng replica count để “fix availability”, nhưng chưa có evidence rằng vấn đề nằm ở số replica.

## Kết quả code review tham khảo

### Critical — Production credential nằm trực tiếp trong manifest

**Vấn đề:** SQL username/password được hard-code trong deployment YAML.  
**Tại sao xảy ra:** Configuration và secret management bị trộn vào source/deployment artifact.  
**Ảnh hưởng production:** Credential có thể lộ qua repository, CI logs, rendered manifests hoặc người có quyền đọc workload spec.  
**Cách sửa:** Dùng secret-management mechanism phù hợp và least privilege; trên Azure có thể cân nhắc workload identity/Managed Identity nếu dependency hỗ trợ, hoặc Kubernetes Secret kết hợp external secret store theo platform policy. Không commit plaintext credential.

### High — Liveness có thể restart Pod trong startup/dependency disturbance

**Vấn đề:** Liveness bắt đầu rất sớm và dùng cùng `/health` với readiness.  
**Tại sao xảy ra:** Endpoint có thể fail vì app chưa warm hoặc dependency tạm thời unavailable dù process không bị deadlock.  
**Ảnh hưởng production:** Restart loop kéo dài outage và làm rollout mất capacity.  
**Cách sửa:** Định nghĩa semantics riêng; dùng `startupProbe` khi startup có thể dài, readiness để quyết định nhận traffic, liveness chỉ phản ánh trạng thái cần restart process.

### High — Readiness endpoint/policy có thể đưa Pod vào traffic sai thời điểm

**Vấn đề:** Manifest không chứng minh `/health` phản ánh đúng readiness và startup chỉ có 2 giây grace.  
**Tại sao xảy ra:** Health endpoint được dùng như boolean chung.  
**Ảnh hưởng production:** Pod nhận traffic trước khi dependencies/config/warmup cần thiết sẵn sàng, gây 502/503.  
**Cách sửa:** Thiết kế readiness check theo những điều kiện thật sự bắt buộc để phục vụ request; cấu hình thresholds/timing dựa trên measured startup distribution.

### High — `latest` làm artifact không immutable

**Vấn đề:** Deployment không pin image version/digest.  
**Tại sao xảy ra:** Tag mutable không xác định chính xác artifact đang chạy.  
**Ảnh hưởng production:** Rollback, audit và so sánh environment khó tin cậy.  
**Cách sửa:** Dùng unique version tag hoặc digest do CI tạo; promote cùng artifact qua environments.

### High — Resource requests/limits không có evidence

**Vấn đề:** CPU/memory values rất thấp nhưng scenario không có profiling chứng minh phù hợp.  
**Tại sao xảy ra:** Resource configuration được chọn bằng guess.  
**Ảnh hưởng production:** Có thể CPU throttling, OOM kill, scheduling sai capacity hoặc ngược lại over-reservation nếu tăng mù.  
**Cách sửa:** Đo working set, allocation/GC, CPU usage/throttling và load profile; đặt request/limit theo SLO và headroom có chủ đích.

### Medium — RollingUpdate không nêu availability/surge policy

**Vấn đề:** Manifest dựa vào defaults thay vì explicit rollout requirement.  
**Tại sao xảy ra:** Team chưa chuyển business availability constraint thành deployment policy.  
**Ảnh hưởng production:** Capacity trong rollout có thể không phù hợp traffic/SLO.  
**Cách sửa:** Xác định `maxUnavailable`/`maxSurge` dựa trên capacity và availability requirement; kết hợp readiness đúng để rollout chỉ tiến khi Pod mới phục vụ được.

### Medium — Thiếu graceful termination design

**Vấn đề:** Manifest không thể hiện termination behavior; application có thể đang xử lý request khi Pod bị terminate.  
**Tại sao xảy ra:** Rollout chỉ được nhìn từ startup, không xét shutdown.  
**Ảnh hưởng production:** Request đang chạy có thể bị cắt, đặc biệt với operation dài.  
**Cách sửa:** ASP.NET Core phải honor shutdown/cancellation; đặt termination grace phù hợp với measured request duration và đảm bảo traffic được drain theo platform behavior.

### Medium — Health failure khó chẩn đoán nếu thiếu telemetry

**Vấn đề:** YAML không giải thích restart nguyên nhân; team đang đoán giữa probe/OOM/app crash.  
**Tại sao xảy ra:** Chưa có operational investigation path.  
**Ảnh hưởng production:** Scale replicas hoặc tăng limits có thể che symptom mà không sửa root cause.  
**Cách sửa:** Quan sát Pod events/status, restart reason, exit code, probe failures, container memory/CPU/throttling và application logs/traces.


Các resource values ở phiên bản đề xuất chỉ là **scenario placeholder**, không phải recommendation mặc định. Production values phải lấy từ load/profile evidence. Tương tự, thresholds của probes phải được hiệu chỉnh theo startup/request behavior thực tế. Kubernetes Secret cũng không tự động là secret-management strategy hoàn chỉnh; cần xét encryption/access/external secret integration theo platform policy.

## Giải thích thiết kế sau khi sửa

`startupProbe` bảo vệ process có startup dài khỏi bị liveness restart quá sớm. Readiness quyết định Pod có nhận traffic; liveness chỉ nên phát hiện trạng thái process cần restart. Artifact được pin để rollback/audit deterministic. Secret không còn hard-code trong workload manifest. Rolling update explicit availability policy giúp review deployment behavior theo SLO.

Điểm quan trọng là không copy resource numbers hoặc probe thresholds giữa services. Health endpoint phải có semantics rõ: một downstream dependency outage không nhất thiết đồng nghĩa process phải restart. Nếu API có thể degrade gracefully, readiness policy cũng cần phản ánh điều đó thay vì loại toàn bộ Pod khỏi service và làm outage nặng hơn.

## Trade-offs

- `maxUnavailable: 0` và `maxSurge: 1` cần cluster có capacity cho Pod bổ sung; không miễn phí.
- Startup/readiness probes quá khoan dung làm detection chậm; quá aggressive tạo false failures.
- External secret integration tăng platform complexity nhưng giảm credential exposure và hỗ trợ rotation tốt hơn.
- Memory limit bảo vệ node nhưng hard limit quá thấp có thể dẫn tới OOM; CPU limit có thể gây throttling. Cần đo trước khi chỉnh.

## Cách kiểm thử

1. **Deployment validation:** deploy image có startup 60 giây; không được nhận traffic trước readiness và không restart bởi liveness trong startup window.
2. **Failure-path test:** làm một optional downstream dependency lỗi; xác minh health semantics/degraded behavior đúng requirement, không restart storm.
3. **Load test:** đo CPU, throttling, memory, GC, request p95/p99 và restart behavior để hiệu chỉnh resources.
4. **Rolling-update test:** chạy traffic liên tục trong rollout và kiểm tra error rate/capacity/rollback với immutable image versions.
5. **Security validation:** bảo đảm plaintext production credential không xuất hiện trong source/rendered CI output và service account/secret access tuân least privilege.

## Quan sát trong production

Theo dõi Kubernetes Pod events, container state/restart reason, probe failure counts, CPU usage/throttling, memory working set/OOM events, deployment available/ready replicas và rollout duration. Correlate với ASP.NET Core request p95/p99, 5xx, startup duration, GC/memory và Application Insights traces. Alert cần phân biệt capacity loss với application error để tránh phản ứng “scale replicas” cho mọi symptom.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào một database health check nên ảnh hưởng readiness nhưng không ảnh hưởng liveness?
2. Nếu cluster không đủ capacity cho `maxSurge: 1`, bạn sẽ thay đổi rollout strategy hay capacity như thế nào?
3. Bạn cần evidence gì trước khi quyết định bỏ CPU limit hoặc tăng memory limit gấp bốn lần?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Dual write giữa SQL và Elasticsearch không trở thành atomic chỉ nhờ retry; cần durable recovery và ordering/version strategy khi search là projection.
- HTTP success/failure phải phản ánh business transaction semantics rõ ràng, tránh trả 500 sau khi source-of-truth update đã commit mà không giải thích recovery model.
- Kubernetes health checks cần tách startup, readiness và liveness semantics; probe sai có thể tự khuếch đại outage.
- Resource limits, replica count và rollout policy phải dựa trên telemetry/SLO thay vì guess.
- Immutable artifacts và secret management là một phần của release correctness, không chỉ DevOps hygiene.

## Mẫu tư duy cần nhớ

- Với dual write, luôn tìm failure window và durable recovery path.
- Thiết kế retry cùng idempotency, ordering và backoff.
- Phân biệt “alive”, “ready” và “starting”.
- Measure before changing capacity/resource limits.
- Thiết kế rollback và observability cùng với deployment.
