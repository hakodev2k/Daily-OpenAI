# Code Review Challenge 1 — Service Bus consumer mất message và tạo side effect không nhất quán

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, idempotency, message settlement, retries, distributed failure, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–12

## Bối cảnh

Một order platform nhận message `OrderConfirmed` từ Azure Service Bus. Consumer tạo shipment record trong SQL Server và gọi một carrier API để tạo shipping label. Production chạy nhiều application instances.

Support ghi nhận hai nhóm lỗi khó tái hiện: một số order đã bị mất khỏi queue nhưng không có shipment trong database; một số order lại có hai shipping labels sau khi carrier API timeout. Queue sử dụng at-least-once delivery. Carrier API có hỗ trợ idempotency key nhưng code hiện tại chưa dùng. Team muốn tăng `MaxDeliveryCount` và retry toàn bộ handler để “chắc chắn xử lý thành công”.

Không có distributed transaction giữa Service Bus, SQL Server và carrier API.

## Đoạn code cần review

```csharp
public sealed class OrderConfirmedConsumer
{
    private readonly AppDbContext _db;
    private readonly CarrierClient _carrier;
    private readonly ServiceBusReceiver _receiver;
    private readonly ILogger<OrderConfirmedConsumer> _logger;

    public OrderConfirmedConsumer(
        AppDbContext db,
        CarrierClient carrier,
        ServiceBusReceiver receiver,
        ILogger<OrderConfirmedConsumer> logger)
    {
        _db = db;
        _carrier = carrier;
        _receiver = receiver;
        _logger = logger;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        CancellationToken cancellationToken)
    {
        var command = message.Body.ToObjectFromJson<OrderConfirmed>();

        await _receiver.CompleteMessageAsync(message, cancellationToken);

        var existing = await _db.Shipments
            .FirstOrDefaultAsync(
                x => x.OrderId == command.OrderId,
                cancellationToken);

        if (existing != null)
            return;

        var label = await _carrier.CreateLabelAsync(
            command.OrderId,
            command.Address,
            cancellationToken);

        _db.Shipments.Add(new Shipment
        {
            Id = Guid.NewGuid(),
            OrderId = command.OrderId,
            TrackingNumber = label.TrackingNumber,
            CreatedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Created shipment {OrderId} {TrackingNumber}",
            command.OrderId,
            label.TrackingNumber);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong settlement và processing order.
2. Xác định reliability/concurrency concerns khi nhiều delivery hoặc nhiều consumer instances xử lý cùng logical order.
3. Giải thích production impact của từng issue.
4. Xếp severity theo khả năng mất message, duplicate external side effect và data inconsistency.
5. Đề xuất implementation/design đã sửa.
6. Nêu testing strategy cho duplicate delivery, timeout và crash windows.
7. Nêu telemetry đủ để chứng minh hoặc bác bỏ các failure hypothesis.

## Câu hỏi gợi mở

1. Nếu process chết ngay sau `CompleteMessageAsync` thì message còn được redeliver không?
2. `FirstOrDefaultAsync` rồi `Add` có bảo vệ được hai consumer xử lý đồng thời cùng `OrderId` không?
3. Nếu carrier đã tạo label nhưng HTTP response bị mất, retry handler có thể biết side effect đã xảy ra hay chưa?
4. Database unique constraint và carrier idempotency key bảo vệ hai boundary khác nhau như thế nào?
5. Message lock expiration và settlement failure nên được quan sát ra sao?

## Gợi ý

### Gợi ý 1

Tìm các failure window giữa ba hệ thống độc lập: Service Bus, SQL Server và carrier.

### Gợi ý 2

At-least-once delivery yêu cầu idempotency; “đã query thấy chưa tồn tại” không phải một atomic guarantee dưới concurrency.

## Kết quả code review tham khảo

### Critical — Complete message trước khi durable processing hoàn tất

**Vấn đề:** Message được settlement thành công trước khi carrier call và SQL write hoàn tất.  
**Tại sao xảy ra:** Handler coi việc nhận message như đã hoàn thành business operation.  
**Ảnh hưởng production:** Nếu process crash, database lỗi hoặc carrier call thất bại sau `CompleteMessageAsync`, message không còn để retry và order có thể mất shipment vĩnh viễn.  
**Cách sửa:** Chỉ complete sau khi durable processing đạt trạng thái thành công theo delivery contract; failure transient phải để message được retry/abandon theo processor strategy.

### Critical — External side effect không idempotent ở application flow

**Vấn đề:** `CreateLabelAsync` không truyền stable idempotency key dù provider hỗ trợ.  
**Tại sao xảy ra:** Retry được xem như gọi lại cùng code thay vì replay cùng logical operation.  
**Ảnh hưởng production:** Carrier có thể tạo label thành công nhưng response timeout; redelivery/retry tạo label thứ hai.  
**Cách sửa:** Dùng stable key gắn với logical shipment, ví dụ `shipment:{OrderId}`, và giữ key không đổi qua retry.

### High — Check-then-insert không chống duplicate concurrent consumer

**Vấn đề:** Hai handler có thể cùng đọc `existing == null` rồi cùng gọi carrier.  
**Tại sao xảy ra:** Query và insert không tạo atomic uniqueness guarantee.  
**Ảnh hưởng production:** Duplicate labels và duplicate shipment rows nếu schema cho phép.  
**Cách sửa:** Enforce unique constraint/index trên `Shipments(OrderId)` và thiết kế idempotent processing; database constraint là guard cuối cho persisted state nhưng không tự undo external side effect.

### High — Không có durable representation của external operation state

**Vấn đề:** Chỉ lưu shipment sau khi carrier trả thành công.  
**Tại sao xảy ra:** Không có state machine như `PendingLabel`, `LabelRequested`, `Completed`, hoặc durable operation/idempotency record.  
**Ảnh hưởng production:** Crash/timeout tạo ambiguity: hệ thống không biết cần retry hay reconcile.  
**Cách sửa:** Nếu workflow cần recovery mạnh, lưu durable processing state trước external call, dùng provider idempotency key và reconciliation/status lookup nếu provider hỗ trợ.

### High — Không phân loại transient và permanent failure

**Vấn đề:** Handler không thể hiện strategy cho invalid payload, business-invalid message, `429`, timeout, `5xx` hay permanent `4xx`.  
**Tại sao xảy ra:** Mọi exception bị đẩy về infrastructure mặc định.  
**Ảnh hưởng production:** Poison message có thể retry vô ích; transient failure có thể DLQ quá sớm hoặc tạo retry storm.  
**Cách sửa:** Phân loại lỗi, bounded retry/backoff ở đúng layer, DLQ non-recoverable messages và ghi reason/diagnostics phù hợp.

### Medium — Deserialization/validation không được xử lý rõ

**Vấn đề:** Payload có thể malformed hoặc thiếu dữ liệu business bắt buộc.  
**Tại sao xảy ra:** Handler giả định message hợp lệ.  
**Ảnh hưởng production:** Repeated delivery của poison message, khó điều tra.  
**Cách sửa:** Validate schema/version/business identifiers; dead-letter có chủ đích với reason an toàn khi lỗi không thể retry.

### Medium — Cancellation semantics có thể tạo trạng thái mơ hồ

**Vấn đề:** Host shutdown có thể cancel carrier call hoặc DB write ở giữa workflow.  
**Tại sao xảy ra:** Cancellation đúng là cần thiết nhưng phải đi cùng idempotency/recovery semantics.  
**Ảnh hưởng production:** Redelivery sau shutdown có thể lặp side effect nếu operation trước đã tới carrier.  
**Cách sửa:** Propagate cancellation nhưng thiết kế retry-safe; không dùng cancellation như correctness mechanism.

### Medium — Logging chưa mô tả message identity và attempt

**Vấn đề:** Success log không có message ID, delivery count, correlation/operation ID.  
**Tại sao xảy ra:** Telemetry tập trung happy path.  
**Ảnh hưởng production:** Khó nối duplicate carrier call với Service Bus redelivery.  
**Cách sửa:** Structured logging/tracing với `MessageId`, `OrderId`, delivery count, carrier idempotency key hash/identifier, settlement result và dependency telemetry; không log sensitive address.

### Medium — Tăng `MaxDeliveryCount` không giải quyết correctness

**Vấn đề:** Tăng retry count chỉ tăng số lần replay.  
**Tại sao xảy ra:** Nhầm retry với reliability guarantee.  
**Ảnh hưởng production:** Nếu handler không idempotent, retry nhiều hơn có thể tạo nhiều duplicate side effects hơn.  
**Cách sửa:** Thiết kế idempotency + failure classification trước; sau đó mới chọn delivery/retry policy dựa trên recovery behavior.

## Phiên bản đề xuất

Một implementation tối thiểu tốt hơn có thể giữ workflow đơn giản nhưng bảo vệ hai invariant chính: persisted shipment unique theo `OrderId` và carrier call dùng stable idempotency key.

```csharp
public async Task HandleAsync(
    ServiceBusReceivedMessage message,
    CancellationToken cancellationToken)
{
    OrderConfirmed command;

    try
    {
        command = message.Body.ToObjectFromJson<OrderConfirmed>();
        Validate(command);
    }
    catch (Exception ex) when (IsNonRetryableMessage(ex))
    {
        await _receiver.DeadLetterMessageAsync(
            message,
            "InvalidOrderConfirmed",
            "Payload cannot be processed",
            cancellationToken);
        return;
    }

    var operationKey = $"shipment:{command.OrderId:N}";

    var shipment = await _db.Shipments
        .SingleOrDefaultAsync(
            x => x.OrderId == command.OrderId,
            cancellationToken);

    if (shipment is null)
    {
        var label = await _carrier.CreateLabelAsync(
            command.OrderId,
            command.Address,
            operationKey,
            cancellationToken);

        _db.Shipments.Add(new Shipment
        {
            Id = Guid.NewGuid(),
            OrderId = command.OrderId,
            TrackingNumber = label.TrackingNumber,
            CreatedAtUtc = DateTime.UtcNow
        });

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsUniqueOrderViolation(ex))
        {
            _db.ChangeTracker.Clear();
        }
    }

    await _receiver.CompleteMessageAsync(message, cancellationToken);
}
```

Database phải có unique constraint/index trên `OrderId`:

```sql
CREATE UNIQUE INDEX UX_Shipments_OrderId
ON Shipments(OrderId);
```

Đoạn code trên vẫn cần hiểu giới hạn: unique constraint chỉ ngăn duplicate persisted shipment; carrier idempotency key mới giúp external side effect an toàn khi cùng logical request bị replay. Nếu carrier idempotency semantics có thời hạn hoặc khác với giả định, phải xác minh contract đó trước khi dựa vào nó.

Với workflow phức tạp hơn, có thể dùng durable state/outbox-style orchestration để tách việc consume event khỏi external carrier operation, nhưng không nên thêm messaging layer thứ hai nếu requirement chưa cần recovery/throughput đó.

## Giải thích thiết kế sau khi sửa

Correctness được đặt ở boundary có thể enforce: SQL dùng unique constraint, carrier dùng idempotency contract, Service Bus chỉ complete sau durable success. Retry được coi là normal behavior chứ không phải exceptional edge case. Không cố tạo distributed transaction giả giữa ba hệ thống.

## Trade-offs

Giữ carrier call trực tiếp trong message handler đơn giản hơn nhưng message lock và throughput phụ thuộc dependency latency. Durable intermediate state/worker giúp recovery và reconciliation tốt hơn nhưng tăng schema, orchestration và operational complexity. Auto lock renewal có thể cần cho handler dài, nhưng không thay thế idempotency và không nên dùng để che một workflow quá dài không kiểm soát.

## Cách kiểm thử

1. Integration test gửi cùng `OrderId` đồng thời cho hai handler; assert chỉ một shipment persisted và carrier nhận cùng idempotency key.
2. Failure-path test carrier tạo label rồi giả lập response timeout; redelivery không được tạo logical label thứ hai khi provider idempotency hoạt động.
3. Crash-window test sau SQL success nhưng trước Service Bus complete; redelivery phải kết thúc idempotently.
4. Poison-message test malformed payload/permanent validation error; message được DLQ thay vì retry vô hạn.
5. Transient dependency test `429`/`503`/timeout; đo bounded retry/delivery behavior và cuối cùng success hoặc DLQ theo policy.

## Quan sát trong production

Theo dõi Service Bus active/dead-letter message count, delivery count distribution, processing duration, lock-lost/settlement failures, carrier dependency latency/status, duplicate/idempotency responses, SQL unique-constraint conflicts và end-to-end correlation từ `MessageId` → `OrderId` → carrier operation. Alert trên sustained DLQ growth, processing latency và carrier failure rate.

## Câu hỏi phỏng vấn mở rộng

1. Nếu carrier không hỗ trợ idempotency key hoặc status lookup, bạn có thể guarantee điều gì và không thể guarantee điều gì?
2. Khi nào bạn sẽ tách carrier call sang một durable outbound-work table/outbox thay vì giữ trực tiếp trong Service Bus handler?
3. Nếu processing vượt message lock duration, lock renewal giải quyết phần nào và không giải quyết phần nào của correctness?

# Code Review Challenge 2 — Vue search page tạo XSS từ API và làm lộ token qua browser storage

**Chủ đề:** Vue.js, TypeScript, frontend security, XSS, authentication, API integration, browser storage, error handling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một internal product catalog dùng Vue 3 + TypeScript và ASP.NET Core API. Người dùng có thể tìm sản phẩm; backend trả `highlightHtml` chứa đoạn text đã highlight từ search engine. Frontend hiện lưu access token trong `localStorage` và render highlight bằng `v-html`.

Security test cho thấy một product name được import từ hệ thống đối tác có thể chứa HTML. Team nói hệ thống là “internal” và access token chỉ sống 30 phút nên rủi ro thấp. Production cũng ghi nhận khi API trả `401`, page đôi lúc tiếp tục hiển thị kết quả cũ khiến user tưởng dữ liệu vừa được refresh thành công.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref } from 'vue'

interface SearchItem {
  id: string
  name: string
  highlightHtml: string
}

const query = ref('')
const items = ref<SearchItem[]>([])
const error = ref('')

async function search() {
  error.value = ''

  const token = localStorage.getItem('access_token')
  const response = await fetch(
    `/api/products?q=${encodeURIComponent(query.value)}`,
    {
      headers: {
        Authorization: `Bearer ${token}`
      }
    })

  if (!response.ok) {
    error.value = await response.text()
    return
  }

  items.value = await response.json()
}
</script>

<template>
  <form @submit.prevent="search">
    <input v-model="query" />
    <button type="submit">Search</button>
  </form>

  <p v-if="error" class="error">{{ error }}</p>

  <ul>
    <li v-for="item in items" :key="item.id">
      <a :href="`/products/${item.id}`" v-html="item.highlightHtml"></a>
    </li>
  </ul>
</template>
```

4. Đánh giá token storage dựa trên threat model, không chỉ thời gian sống token.
5. Đề xuất corrected frontend/API contract.
6. Nêu security/integration/E2E tests.
7. Nêu browser/API telemetry cần có nhưng không làm lộ token hoặc sensitive data.

## Kết quả code review tham khảo

### Critical — Render untrusted HTML bằng `v-html`

**Vấn đề:** `highlightHtml` được đưa trực tiếp vào DOM dưới dạng HTML.  
**Tại sao xảy ra:** Data từ partner/search/API bị coi là trusted presentation markup.  
**Ảnh hưởng production:** Nếu payload chứa executable/unsafe markup và không được sanitize đúng ở trusted boundary, attacker có thể thực thi XSS trong application origin.  
**Cách sửa:** Ưu tiên API trả structured highlight fragments/text để Vue render bằng escaped interpolation. Nếu business bắt buộc HTML, sanitize bằng giải pháp được duy trì và policy chặt ở boundary phù hợp; không tự viết regex sanitizer.

### High — Access token trong `localStorage` làm tăng hậu quả của XSS

**Vấn đề:** JavaScript chạy trong origin có thể đọc token từ `localStorage`.  
**Tại sao xảy ra:** Credential được lưu trong storage accessible từ script.  
**Ảnh hưởng production:** XSS có thể exfiltrate bearer token và sử dụng ngoài browser cho tới khi token hết hạn/revoked theo identity design.  
**Cách sửa:** Trước hết phải xác minh authentication architecture. Với browser app, cân nhắc BFF/session cookie `HttpOnly`, `Secure`, phù hợp `SameSite`, hoặc token strategy giảm exposure; mỗi lựa chọn có trade-off CSRF/session/backend complexity. Không tuyên bố một storage model luôn đúng nếu chưa biết flow.

### High — UI giữ stale result khi request thất bại

**Vấn đề:** Khi response không OK, `items` cũ vẫn hiển thị.  
**Tại sao xảy ra:** Error state được set nhưng result state không có freshness semantics.  
**Ảnh hưởng production:** User có thể hiểu nhầm dữ liệu cũ là kết quả của query mới; đặc biệt nguy hiểm khi `401/403` hoặc query thay đổi.  
**Cách sửa:** Thiết kế explicit loading/error/result state; clear hoặc đánh dấu stale theo UX requirement. `401` cần đi qua auth recovery flow thay vì hiển thị raw response.

### High — Raw server error được đưa vào UI contract

**Vấn đề:** Client hiển thị `response.text()` trực tiếp.  
**Tại sao xảy ra:** API error body bị dùng như user-facing message.  
**Ảnh hưởng production:** Có thể lộ implementation detail/sensitive diagnostic nếu backend trả lỗi không được chuẩn hóa; UX không nhất quán.  
**Cách sửa:** API dùng stable error contract như ProblemDetails phù hợp; frontend map error code/status sang safe message và correlation ID.

### Medium — Gửi `Bearer null` khi token không tồn tại

**Vấn đề:** Header vẫn được tạo khi `localStorage` trả `null`.  
**Tại sao xảy ra:** Không có auth-state guard.  
**Ảnh hưởng production:** Request lỗi không cần thiết, telemetry nhiễu và auth UX khó hiểu.  
**Cách sửa:** Centralize authenticated API client/auth flow; không tự dựng header trong từng component.

### Medium — Security contract của highlight bị phân tán

**Vấn đề:** Frontend type tên `highlightHtml` khiến raw HTML trở thành API contract mặc định.  
**Tại sao xảy ra:** Search presentation bị coupling với HTML rendering.  
**Ảnh hưởng production:** Các component khác dễ tái sử dụng field theo cách unsafe.  
**Cách sửa:** Trả structured fragments, ví dụ `{ text, highlighted }[]`, hoặc plain text + match offsets; render markup do component sở hữu.

### Medium — Thiếu loading/disabled state và duplicate-submit handling

**Vấn đề:** User có thể submit nhiều lần trong khi request trước chưa xong.  
**Tại sao xảy ra:** Không track in-flight state.  
**Ảnh hưởng production:** Tăng load và tạo confusing result ordering nếu latency khác nhau.  
**Cách sửa:** Disable/serialize theo UX hoặc cancel superseded request bằng `AbortController`; nếu cho parallel requests, chỉ apply result tương ứng request hiện hành.

### Medium — Product URL dùng raw ID mà không xác minh route contract

**Vấn đề:** Client trực tiếp interpolate `item.id`.  
**Tại sao xảy ra:** API và route assumptions chưa được validate.  
**Ảnh hưởng production:** Với ID không đúng format có thể tạo malformed navigation; authorization vẫn phải nằm ở backend, không dựa vào obscurity của ID.  
**Cách sửa:** Validate typed ID/route generation và luôn enforce object authorization ở API product detail.

Component minh họa:

```vue
<script setup lang="ts">
import { ref } from 'vue'

const query = ref('')
const items = ref<SearchItem[]>([])
const error = ref('')
const loading = ref(false)
let controller: AbortController | null = null

async function search() {
  controller?.abort()
  controller = new AbortController()

  loading.value = true
  error.value = ''
  items.value = []

  try {
    const response = await apiFetch(
      `/api/products?q=${encodeURIComponent(query.value)}`,
      { signal: controller.signal })

    if (!response.ok) {
      if (response.status === 401) {
        await handleUnauthenticated()
        return
      }

      error.value = 'Không thể tải kết quả tìm kiếm.'
      return
    }

    items.value = await response.json()
  } catch (e) {
    if (!(e instanceof DOMException && e.name === 'AbortError')) {
      error.value = 'Không thể tải kết quả tìm kiếm.'
    }
  } finally {
    loading.value = false
  }
}
</script>

<template>
  <form @submit.prevent="search">
    <input v-model="query" />
    <button type="submit" :disabled="loading">Search</button>
  </form>

  <p v-if="error" class="error">{{ error }}</p>

  <ul>
    <li v-for="item in items" :key="item.id">
      <a :href="`/products/${encodeURIComponent(item.id)}`">
        <template v-for="(part, index) in item.highlight" :key="index">
          <mark v-if="part.highlighted">{{ part.text }}</mark>
          <span v-else>{{ part.text }}</span>
        </template>
      </a>
    </li>
  </ul>
</template>
```

`apiFetch` và `handleUnauthenticated` phụ thuộc authentication architecture thực tế. Nếu application dùng BFF + cookie session, client không cần đọc bearer token. Nếu là SPA token flow, cần đánh giá current identity library, token lifetime, refresh strategy, CSP và XSS defenses trước khi chọn storage. Không nên chuyển token sang một nơi khác chỉ bằng khẩu hiệu mà không xét CSRF/XSS và deployment model.

## Giải thích thiết kế sau khi sửa

Presentation markup được tạo bởi component, còn API chỉ cung cấp data. Điều này thu hẹp trust boundary và tận dụng escaping mặc định của Vue. Auth concern được centralize thay vì mỗi component đọc credential. UI có explicit request state và cancellation cho superseded search.

## Trade-offs

Structured highlight làm API contract dài hơn và search backend phải chuyển match information thành fragments/offsets. Sanitized HTML có thể đơn giản hơn nếu search engine đã trả markup phức tạp, nhưng sanitizer policy trở thành security-critical dependency. BFF giảm bearer-token exposure với browser JavaScript nhưng thêm server/session infrastructure và yêu cầu CSRF strategy phù hợp.

## Cách kiểm thử

1. Security test product/search text chứa `<img onerror=...>`, `<script>` và encoded variants; không được thực thi script.
2. Playwright E2E cho `401`, `403`, `500`: stale result không được trình bày như fresh result và auth UX đúng contract.
3. Integration test API highlight contract với special characters/Unicode và match fragments.
4. Browser test submit liên tiếp với response đảo thứ tự; superseded request không overwrite current result.
5. Security test object authorization cho `/products/{id}` độc lập với route/link frontend.

## Quan sát trong production

Theo dõi API search latency/error status, `401/403` rate, frontend error events, aborted request count, CSP violation reports nếu CSP được triển khai, correlation ID và search dependency telemetry. Không log access token, raw authorization header hoặc partner payload có thể chứa sensitive data.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc render rich HTML từ CMS/search engine, bạn đặt sanitization boundary và test policy ở đâu?
2. BFF + `HttpOnly` cookie giảm loại rủi ro nào và đưa thêm loại rủi ro/complexity nào vào hệ thống?
3. CSP có thể giúp gì trong XSS defense, và tại sao nó không thay thế việc loại bỏ unsafe rendering?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- At-least-once messaging phải được thiết kế cùng idempotency; retry không tự tạo correctness.
- Message settlement phải xảy ra theo durable success boundary, không phải ngay khi handler bắt đầu.
- Database uniqueness và external-provider idempotency giải quyết các failure boundary khác nhau.
- Frontend phải coi dữ liệu đi qua API/search/CMS/partner vẫn có thể là untrusted input.
- Tránh raw HTML contract khi presentation có thể biểu diễn bằng structured data và framework escaping.

## Mẫu tư duy cần nhớ

- Vẽ failure windows giữa các hệ thống trước khi thiết kế retry.
- Retry luôn đi cùng idempotency và failure classification.
- Enforce invariant ở boundary có khả năng enforce nó.
- Dữ liệu đi qua backend không tự động trở thành trusted.
- Security decision phải dựa trên threat model và authentication architecture thực tế.
