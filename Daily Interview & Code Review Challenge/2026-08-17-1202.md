# Code Review Challenge 1 — Cache-aside làm mất cập nhật dưới tải cao

**Chủ đề:** Caching, concurrency, EF Core, consistency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core API trả cấu hình quyền của user. Dữ liệu gốc nằm trong SQL Server/PostgreSQL và được cache Redis trong 10 phút. Endpoint update được gọi bởi portal quản trị; endpoint read có lưu lượng cao và nhiều application instance cùng phục vụ.

Production thỉnh thoảng trả quyền cũ vài phút ngay sau khi admin cập nhật. Khi một key hết hạn trong giờ cao điểm, database CPU tăng đột biến. Team cho rằng “xóa cache sau `SaveChanges` là đủ để luôn đúng”.

Chưa rõ business yêu cầu read-after-write mạnh đến mức nào và việc user thấy quyền cũ trong vài giây có chấp nhận được hay không.

## Đoạn code cần review

```csharp
public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public PermissionService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    public async Task<UserPermissionDto?> GetAsync(Guid userId)
    {
        var key = $"permission:{userId}";
        var json = await _cache.GetStringAsync(key);

        if (json != null)
            return JsonSerializer.Deserialize<UserPermissionDto>(json);

        var permission = await _db.UserPermissions
            .Where(x => x.UserId == userId)
            .Select(x => new UserPermissionDto(
                x.UserId, x.CanApprove, x.CanExport, x.UpdatedAt))
            .SingleOrDefaultAsync();

        if (permission != null)
        {
            await _cache.SetStringAsync(
                key,
                JsonSerializer.Serialize(permission),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
                });
        }

        return permission;
    }

    public async Task UpdateAsync(Guid userId, UpdatePermissionRequest request)
    {
        var permission = await _db.UserPermissions
            .SingleAsync(x => x.UserId == userId);

        permission.CanApprove = request.CanApprove;
        permission.CanExport = request.CanExport;
        permission.UpdatedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync();
        await _cache.RemoveAsync($"permission:{userId}");
    }
}
```

2. Tìm rủi ro concurrency, stale cache và performance.
3. Giải thích production impact.
4. Ưu tiên các vấn đề theo mức độ ảnh hưởng.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử race condition.
7. Đề xuất logs, traces và metrics.

## Câu hỏi gợi mở

- Điều gì xảy ra nếu một cache miss đang đọc DB đồng thời admin update?

- Khi 1.000 request cùng miss một key thì chuyện gì xảy ra?

## Kết quả code review tham khảo

### 1. Race condition có thể tái tạo stale cache sau invalidation

- **Problem:** Reader cache miss có thể đọc DB trước update nhưng ghi cache sau khi writer commit và remove key.
- **Why it happens:** Cache fill và cache invalidation không có ordering/version coordination.
- **Production impact:** Permission cũ có thể tồn tại toàn TTL 10 phút; với authorization-related data đây có thể thành security risk.
- **Severity:** Critical
- **Recommended fix:** Thiết kế consistency theo requirement: versioned cache/value, write-through/update cache sau commit, hoặc kiểm tra version trước cache fill. Với dữ liệu authorization nhạy cảm, cân nhắc TTL ngắn/bypass cache cho quyết định quan trọng.

### 2. Cache stampede khi key hết hạn

- **Problem:** Nhiều request cùng miss sẽ cùng query database.
- **Why it happens:** Không có request coalescing/single-flight hay distributed coordination.
- **Production impact:** DB load spike và latency tăng đúng lúc key nóng hết hạn.
- **Severity:** High
- **Recommended fix:** Single-flight per instance, distributed lock có timeout nếu thật sự cần, stale-while-revalidate phù hợp với dữ liệu cho phép stale, hoặc TTL jitter để giảm synchronized expiry.

### 3. DB commit thành công nhưng cache invalidation thất bại

- **Problem:** Hai hệ thống không nằm trong một transaction.
- **Why it happens:** Redis call có thể timeout/fail sau `SaveChangesAsync`.
- **Production impact:** API báo lỗi dù DB đã thay đổi và cache cũ vẫn tồn tại; retry semantics trở nên khó hiểu.
- **Severity:** High
- **Recommended fix:** Xem DB là source of truth; có retry/reconciliation cho invalidation, hoặc transactional outbox phát cache-invalidation event. Không tuyên bố atomicity giữa DB và Redis.

### 4. Không có optimistic concurrency cho concurrent admin updates

- **Problem:** Hai update có thể ghi đè nhau theo last-writer-wins ngoài ý muốn.
- **Why it happens:** Entity không có concurrency token/version được kiểm tra.
- **Production impact:** Lost update và cache phản ánh một trạng thái mà admin khác không mong đợi.
- **Severity:** High
- **Recommended fix:** Dùng concurrency token phù hợp với provider/schema và trả conflict để caller reload/merge khi business yêu cầu phát hiện concurrent edits.

### 5. Cache key không chứa schema/version

- **Problem:** DTO thay đổi sau deployment có thể không tương thích dữ liệu cache cũ.
- **Why it happens:** Key chỉ chứa user ID.
- **Production impact:** Deserialize failure hoặc semantic mismatch trong rolling deployment.
- **Severity:** Medium
- **Recommended fix:** Version cache namespace, ví dụ `permission:v2:{userId}`.

### 6. Không truyền CancellationToken

- **Problem:** Request cancellation không được truyền tới EF Core/Redis.
- **Why it happens:** API methods không nhận token.
- **Production impact:** Công việc thừa tiếp tục sau client disconnect/shutdown và tăng áp lực khi hệ thống quá tải.
- **Severity:** Medium
- **Recommended fix:** Truyền `CancellationToken` xuyên suốt.

### 7. Không có telemetry cho hit/miss/fill/invalidation

- **Problem:** Không phân biệt DB chậm với Redis miss/stampede.
- **Why it happens:** Cache behavior không được instrument.
- **Production impact:** Điều tra incident khó và tuning TTL thiếu dữ liệu.
- **Severity:** Medium
- **Recommended fix:** Metrics cache hit ratio, miss, fill latency, invalidation failure, DB fallback và hot-key load.

### 8. Fixed TTL có thể tạo synchronized expiration

- **Problem:** Nhiều key được warm cùng thời điểm có thể hết hạn cùng lúc.
- **Why it happens:** TTL giống hệt nhau.
- **Production impact:** Periodic load spikes.
- **Severity:** Low
- **Recommended fix:** Thêm bounded TTL jitter khi semantics cho phép.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng versioned value và update cache sau DB commit. Nó giảm stale-fill race khi reader chỉ cache dữ liệu nếu version vẫn là version hiện hành; production nên kết hợp outbox/reconciliation nếu invalidation/update cache là bắt buộc phải eventual-success.

```csharp
public sealed record PermissionCacheValue(
    Guid UserId,
    bool CanApprove,
    bool CanExport,
    long Version);

public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public PermissionService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    private static string Key(Guid userId) => $"permission:v2:{userId}";

    public async Task<PermissionCacheValue?> GetAsync(
        Guid userId,
        CancellationToken ct)
    {
        var cached = await _cache.GetStringAsync(Key(userId), ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<PermissionCacheValue>(cached);

        var value = await _db.UserPermissions
            .AsNoTracking()
            .Where(x => x.UserId == userId)
            .Select(x => new PermissionCacheValue(
                x.UserId, x.CanApprove, x.CanExport, x.Version))
            .SingleOrDefaultAsync(ct);

        if (value is null)
            return null;

        var currentVersion = await _db.UserPermissions
            .Where(x => x.UserId == userId)
            .Select(x => x.Version)
            .SingleAsync(ct);

        if (currentVersion == value.Version)
        {
            await _cache.SetStringAsync(
                Key(userId),
                JsonSerializer.Serialize(value),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow =
                        TimeSpan.FromMinutes(2) +
                        TimeSpan.FromSeconds(Random.Shared.Next(0, 30))
                },
                ct);
        }

        return value;
    }

    public async Task UpdateAsync(
        Guid userId,
        UpdatePermissionRequest request,
        long expectedVersion,
        CancellationToken ct)
    {
        var affected = await _db.UserPermissions
            .Where(x => x.UserId == userId && x.Version == expectedVersion)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.CanApprove, request.CanApprove)
                .SetProperty(x => x.CanExport, request.CanExport)
                .SetProperty(x => x.UpdatedAt, DateTime.UtcNow)
                .SetProperty(x => x.Version, x => x.Version + 1), ct);

        if (affected == 0)
            throw new ConcurrencyException();

        var latest = await _db.UserPermissions
            .AsNoTracking()
            .Where(x => x.UserId == userId)
            .Select(x => new PermissionCacheValue(
                x.UserId, x.CanApprove, x.CanExport, x.Version))
            .SingleAsync(ct);

        await _cache.SetStringAsync(
            Key(userId),
            JsonSerializer.Serialize(latest),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(2)
            },
            ct);
    }
}
```

Code trên minh họa nguyên tắc, không biến DB + Redis thành atomic transaction. Nếu quyền có tác động bảo mật nghiêm trọng, recommendation có thể thay đổi: database hoặc một authoritative authorization store nên quyết định quyền, còn cache chỉ là optimization với bounded staleness rõ ràng.

## Trade-offs

Write-through làm read-after-write tốt hơn nhưng cache write failure vẫn cần recovery. Version check thêm DB query cho miss; có thể thay bằng database-generated version đi cùng snapshot hoặc Lua/Redis version protocol nếu cần tối ưu. Distributed lock chống stampede có thêm failure modes và không nên dùng chỉ vì “có concurrency”. Stale-while-revalidate rất tốt cho catalog nhưng có thể không phù hợp với permission revocation.

## Cách kiểm thử

1. **Race test:** reader đọc version N, writer commit N+1 và update cache, sau đó reader tiếp tục; cache cuối không được quay về N.
2. **Concurrent update:** hai admin cùng expected version; chỉ một update thành công, request còn lại nhận conflict.
3. **Redis failure:** DB update thành công nhưng cache write timeout; verify reconciliation/fallback semantics và không rollback giả tạo DB.
4. **Load test hot key:** hàng trăm request cùng cache miss; đo DB query count và latency để phát hiện stampede.
5. **Security test:** revoke quyền và xác minh đường authorization quan trọng không chấp nhận stale permission quá giới hạn business cho phép.

## Quan sát trong production

Theo dõi cache hit/miss ratio, fill rate, Redis latency/error, DB fallback queries, permission version mismatch, invalidation/update failures và latency p95/p99. Trace nên nối HTTP request → cache → DB. Alert khi miss ratio hoặc DB fallback tăng đột biến sau deployment/Redis incident.

## Câu hỏi phỏng vấn mở rộng

1. Tại sao distributed lock không tự động giải quyết stale-fill race?
2. Nếu Redis hoàn toàn unavailable 20 phút, hệ thống nên fail-open hay fail-closed cho authorization?
3. Nếu permission changes rất hiếm nhưng reads cực lớn, bạn thay đổi chiến lược cache thế nào?

# Code Review Challenge 2 — Proxy tải file từ external API gây socket, memory và cancellation problems

**Chủ đề:** HTTP client usage, resource disposal, async/cancellation, memory, error handling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core endpoint tải report từ dịch vụ bên ngoài rồi trả file cho mobile/web client. Report thường 2–10 MB nhưng đôi lúc trên 200 MB. Production chạy nhiều instance; giờ cao điểm có hàng trăm download đồng thời.

Sau khi traffic tăng, team thấy memory spike, GC pressure, đôi lúc outbound request timeout và latency tăng. Khi client hủy download, backend vẫn tiếp tục tải file từ upstream. Developer đã thêm `using HttpClient` vì nghĩ dispose sớm sẽ “giải phóng tài nguyên tốt hơn”.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly IConfiguration _configuration;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        IConfiguration configuration,
        ILogger<ReportsController> logger)
    {
        _configuration = configuration;
        _logger = logger;
    }

    [HttpGet("{reportId}/download")]
    public async Task<IActionResult> Download(string reportId)
    {
        using var client = new HttpClient();
        client.Timeout = TimeSpan.FromMinutes(5);

        var token = _configuration["ExternalApi:Token"];
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        var url = _configuration["ExternalApi:BaseUrl"] +
                  "/reports/" + reportId + "/file";

        try
        {
            var response = await client.GetAsync(url);

            if (!response.IsSuccessStatusCode)
            {
                var body = await response.Content.ReadAsStringAsync();
                _logger.LogError(
                    "Report API failed. Id={ReportId}, Status={Status}, Body={Body}",
                    reportId,
                    response.StatusCode,
                    body);

                return StatusCode(502, body);
            }

            var bytes = await response.Content.ReadAsByteArrayAsync();
            var fileName = response.Content.Headers.ContentDisposition?.FileName
                           ?? $"{reportId}.pdf";

            return File(bytes, "application/pdf", fileName);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Download failed for {ReportId}", reportId);
            return StatusCode(500, ex.Message);
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Buffer toàn bộ file vào managed memory

- **Problem:** `ReadAsByteArrayAsync` giữ toàn bộ response trong byte array trước khi gửi client.
- **Why it happens:** Endpoint không stream dữ liệu.
- **Production impact:** Large allocations, GC pressure, memory spike/OOM risk khi nhiều download lớn đồng thời.
- **Severity:** Critical
- **Recommended fix:** Stream upstream response tới downstream response với bounded buffers và cancellation.

### 2. Tạo/dispose `HttpClient` cho mỗi request

- **Problem:** Mỗi request tạo client/handler mới thay vì dùng managed handler lifetime.
- **Why it happens:** Hiểu sai rằng dispose client per request là best practice.
- **Production impact:** Mất lợi ích connection pooling hiệu quả, tăng connection churn và có thể góp phần socket/port pressure.
- **Severity:** High
- **Recommended fix:** Dùng `IHttpClientFactory`/typed client hoặc long-lived client với handler lifetime/DNS behavior được quản lý phù hợp.

### 3. Không propagate request cancellation

- **Problem:** Client disconnect không hủy `GetAsync`, body read hay copy.
- **Why it happens:** Không truyền `HttpContext.RequestAborted`.
- **Production impact:** Backend tiếp tục dùng bandwidth, socket, memory và upstream capacity cho request không còn consumer.
- **Severity:** High
- **Recommended fix:** Truyền cancellation token xuyên suốt và xử lý `OperationCanceledException` đúng semantics.

### 4. Mặc định `GetAsync` có thể buffer content trước khi trả về

- **Problem:** Code không yêu cầu completion ngay khi headers đến.
- **Why it happens:** Không dùng `HttpCompletionOption.ResponseHeadersRead` cho streaming scenario.
- **Production impact:** Streaming bị trì hoãn và memory/resource usage tăng tùy content/handler behavior.
- **Severity:** High
- **Recommended fix:** Dùng `SendAsync(..., ResponseHeadersRead, ct)` rồi stream content.

### 5. Leak thông tin upstream cho caller

- **Problem:** Trả raw upstream body và `ex.Message`.
- **Why it happens:** Diagnostic detail bị trộn với public API contract.
- **Production impact:** Có thể lộ internal identifiers, topology hoặc thông tin nhạy cảm.
- **Severity:** High
- **Recommended fix:** Trả stable ProblemDetails/error code; log diagnostic detail nội bộ với redaction/size limits.

### 6. Không dispose rõ ràng `HttpResponseMessage`

- **Problem:** Response lifetime không được quản lý bằng `using`.
- **Why it happens:** Chỉ dispose client.
- **Production impact:** Response/content resources có thể giữ lâu hơn cần thiết, đặc biệt trong streaming/failure paths.
- **Severity:** Medium
- **Recommended fix:** `using var response = ...`; stream phải được consume/dispose trong lifetime đó.

### 7. Trust upstream filename/content type thiếu kiểm soát

- **Problem:** Filename lấy trực tiếp từ upstream; content type bị hard-code PDF.
- **Why it happens:** Không validate metadata.
- **Production impact:** Filename xấu/không phù hợp và API metadata sai; tùy downstream handling có thể tạo security/usability issues.
- **Severity:** Medium
- **Recommended fix:** Sanitize filename, allow-list extension/content type và dùng safe fallback.

### 8. Error logging có thể quá lớn hoặc chứa dữ liệu nhạy cảm

- **Problem:** Log toàn bộ upstream body.
- **Why it happens:** Không giới hạn kích thước/redaction.
- **Production impact:** Log cost tăng, PII/token-like data có thể bị lưu ngoài ý muốn.
- **Severity:** Medium
- **Recommended fix:** Log status, correlation ID và body đã truncate/redact khi thực sự cần.

## Phiên bản code đề xuất

Ví dụ dùng typed `HttpClient` và stream trực tiếp. Việc đăng ký client nên cấu hình `BaseAddress`, authentication handler và timeout/resilience policy ở composition root thay vì dựng trong controller.

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly HttpClient _client;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        HttpClient client,
        ILogger<ReportsController> logger)
    {
        _client = client;
        _logger = logger;
    }

    [HttpGet("{reportId:guid}/download")]
    public async Task Download(Guid reportId, CancellationToken ct)
    {
        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"reports/{reportId}/file");

        using var response = await _client.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            ct);

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogWarning(
                "Upstream report download failed {ReportId} {StatusCode}",
                reportId,
                (int)response.StatusCode);

            Response.StatusCode = StatusCodes.Status502BadGateway;
            await Response.WriteAsJsonAsync(
                new ProblemDetails
                {
                    Status = StatusCodes.Status502BadGateway,
                    Title = "Report service is unavailable"
                },
                ct);
            return;
        }

        var fileName = $"{reportId}.pdf";
        Response.StatusCode = StatusCodes.Status200OK;
        Response.ContentType = "application/pdf";
        Response.Headers.ContentDisposition =
            $"attachment; filename=\"{fileName}\"";

        if (response.Content.Headers.ContentLength is long length)
            Response.ContentLength = length;

        await using var upstream = await response.Content.ReadAsStreamAsync(ct);
        await upstream.CopyToAsync(Response.Body, 64 * 1024, ct);
    }
}
```

Nếu cần retry, phải phân biệt failure trước khi response body bắt đầu được gửi và failure giữa stream. Sau khi downstream response đã bắt đầu, thường không thể chuyển sang một JSON error response sạch; cần abort/log và để caller retry toàn request nếu API contract cho phép. Retry GET chỉ nên áp dụng có giới hạn và dựa trên failure semantics của upstream.

## Trade-offs

Streaming giảm memory nhưng giữ connection mở trong suốt download và làm retry giữa stream phức tạp hơn. Buffering vẫn hợp lý với payload nhỏ và khi cần inspect/transform toàn bộ nội dung. `IHttpClientFactory` giúp quản lý handler lifetime; long-lived `HttpClient` cũng có thể đúng nếu handler/DNS lifetime được cấu hình đúng. Không nên thêm retry hàng loạt nếu upstream đang quá tải vì có thể khuếch đại incident.

## Cách kiểm thử

1. **Large-file load test:** hàng trăm download 200 MB; kiểm tra working set/GC và throughput không tăng tuyến tính theo tổng file đang tải.
2. **Cancellation test:** client abort giữa file; outbound request/stream phải dừng sớm và metric cancellation tăng.
3. **Slow upstream:** headers nhanh nhưng body chậm; endpoint bắt đầu stream mà không buffer toàn file.
4. **Upstream 4xx/5xx:** caller chỉ nhận sanitized gateway error; logs không chứa raw sensitive body.
5. **Mid-stream failure:** upstream ngắt connection sau một phần file; verify resource disposal, trace và caller-visible behavior được xác định rõ.

## Quan sát trong production

Theo dõi active downloads, bytes streamed, download duration, cancellations, upstream latency/error rate, active outbound connections, connection establishment rate, process working set, allocation/GC counters và failed streams. Distributed trace nên nối inbound request với outbound report request nhưng không ghi token hoặc file content.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào long-lived `HttpClient` hợp lý hơn typed client từ `IHttpClientFactory`?
2. Nếu cần virus scanning file trước khi trả client, streaming architecture sẽ thay đổi thế nào?
3. Bạn có retry khi stream đã gửi 80% file cho client không? Vì sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cache-aside không tự đảm bảo consistency khi reader và writer chạy đồng thời; invalidation đúng thứ tự là một distributed-systems problem. Với authorization data, bounded staleness phải là quyết định business/security chứ không chỉ là TTL kỹ thuật. Ở HTTP pipeline, `HttpClient`/handler lifetime, streaming và cancellation quyết định khả năng chịu tải; buffer file lớn có thể biến traffic bình thường thành memory incident.

## Mẫu tư duy cần nhớ

- Vẽ timeline concurrency trước khi kết luận cache invalidation là an toàn.
- Xác định source of truth và consistency requirement trước khi chọn caching strategy.
- Đừng biến hai data stores thành “atomic” bằng giả định; thiết kế recovery/reconciliation.
- Stream payload lớn và propagate cancellation end-to-end.
- Treat observability và failure paths như một phần của design, không phải phần bổ sung sau cùng.
