# Code Review Challenge 1 — Singleton cache giữ Scoped DbContext: chạy ổn lúc startup nhưng vỡ dưới concurrent requests

**Chủ đề:** C#/.NET, ASP.NET Core DI lifetimes, EF Core DbContext, concurrency, caching, resource lifetime, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp thông tin cấu hình sản phẩm cho nhiều frontend. Dữ liệu nằm trong SQL Server và thay đổi không thường xuyên. Để giảm database traffic, team thêm một in-memory cache service.

Production chạy 6 application instances. Mỗi instance nhận khoảng 150–300 requests/second ở giờ cao điểm. Sau deployment, hệ thống có các symptom không ổn định:

- thỉnh thoảng xuất hiện `InvalidOperationException` liên quan đến EF Core concurrent operation;
- một số request đọc dữ liệu cũ lâu hơn TTL mong đợi;
- khi database chậm, số request timeout tăng mạnh;
- logs đôi lúc có exception sau khi application shutdown/restart;
- local test với một user gần như luôn pass.

Registration và implementation hiện tại:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("AppDb")));

builder.Services.AddSingleton<ProductConfigCache>();

public sealed class ProductConfigCache
{
    private readonly AppDbContext _db;
    private readonly ILogger<ProductConfigCache> _logger;
    private readonly Dictionary<string, CacheEntry> _cache = new();

    public ProductConfigCache(
        AppDbContext db,
        ILogger<ProductConfigCache> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<ProductConfigDto?> GetAsync(
        string productCode,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(productCode, out var entry) &&
            entry.ExpiresAtUtc > DateTime.UtcNow)
        {
            return entry.Value;
        }

        var entity = await _db.ProductConfigs
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.ProductCode == productCode,
                cancellationToken);

        if (entity is null)
            return null;

        var value = new ProductConfigDto(
            entity.ProductCode,
            entity.DisplayName,
            entity.SettingsJson);

        _cache[productCode] = new CacheEntry(
            value,
            DateTime.UtcNow.AddMinutes(5));

        _logger.LogInformation(
            "Loaded product config {ProductCode} from database",
            productCode);

        return value;
    }

    private sealed record CacheEntry(
        ProductConfigDto Value,
        DateTime ExpiresAtUtc);
}
```

Team muốn giữ solution đơn giản. Redis đang có trong platform nhưng chưa có bằng chứng rằng distributed cache là cần thiết cho use case này.

## Kết quả code review tham khảo

### Critical — Singleton giữ `DbContext` có scoped lifetime

**Vấn đề:** `ProductConfigCache` là singleton nhưng constructor nhận `AppDbContext`, vốn được đăng ký scoped bởi `AddDbContext` theo cấu hình thông thường.

**Tại sao xảy ra:** Singleton sống lâu hơn request scope. Nếu scope validation bắt lỗi thì application có thể fail startup; nếu cấu hình/runtime path cho phép object bị capture, cùng một context có thể bị giữ quá lâu và dùng từ nhiều requests.

**Ảnh hưởng production:** Lifetime mismatch, concurrent EF Core operations, stale tracking/state assumptions, resource lifetime khó kiểm soát và exception không ổn định dưới load.

**Cách sửa:** Không giữ request-scoped `DbContext` trong singleton. Với singleton cần truy cập database theo operation, dùng `IDbContextFactory<AppDbContext>` hoặc tạo scope đúng cách; nếu cache service chỉ cần request-scoped behavior thì thay lifetime tương ứng. Chọn theo ownership thực tế.

### High — `DbContext` bị dùng đồng thời

**Vấn đề:** Nhiều calls vào singleton có thể chạy `SingleOrDefaultAsync` đồng thời trên cùng `_db`.

**Tại sao xảy ra:** `DbContext` không phải shared concurrent session cho nhiều operations song song.

**Ảnh hưởng production:** Exception kiểu “second operation started”, request failures và behavior phụ thuộc timing.

**Cách sửa:** Mỗi database operation dùng context riêng phù hợp lifetime, ví dụ context tạo từ `IDbContextFactory`.

### High — `_cache` là mutable `Dictionary` được truy cập đồng thời

**Vấn đề:** `Dictionary` thường không phải lựa chọn an toàn cho concurrent writes/reads kiểu này.

**Tại sao xảy ra:** Singleton được tất cả request threads trong process truy cập.

**Ảnh hưởng production:** Race conditions, inconsistent behavior và failure khó tái hiện bằng single-user test.

**Cách sửa:** Dùng abstraction cache thread-safe như `IMemoryCache`, hoặc synchronization/concurrent collection phù hợp với semantics cần thiết.

### High — Cache stampede trên hot key

**Vấn đề:** Khi key hết hạn, mọi request miss đều query database độc lập.

**Tại sao xảy ra:** Check-then-load không có single-flight/coalescing cho cùng key.

**Ảnh hưởng production:** Một database slowdown có thể tạo positive feedback: cache expires → nhiều queries → DB chậm hơn → nhiều requests chờ/timeout.

**Cách sửa:** Nếu measurement cho thấy cần, coalesce concurrent loads per key bằng keyed synchronization/single-flight strategy. Phải dọn lock state và tránh global lock chặn các keys không liên quan.

### Medium — Cache growth không có size policy

**Vấn đề:** Entry hết hạn không nhất thiết được chủ động loại khỏi custom dictionary, và số product codes có thể tăng.

**Tại sao xảy ra:** Code chỉ overwrite khi key được request lại; không có eviction/size limit.

**Ảnh hưởng production:** Memory có thể tăng theo cardinality của keys đã từng truy cập.

**Cách sửa:** Dùng cache abstraction có expiration/eviction và cân nhắc size limit dựa trên workload thực tế.

### Medium — Negative result không được cache

**Vấn đề:** Product code không tồn tại luôn đi database.

**Tại sao xảy ra:** `null` trả về trước khi tạo entry.

**Ảnh hưởng production:** Invalid/missing hot key có thể tạo repeated database traffic hoặc abuse amplification.

**Cách sửa:** Nếu domain cho phép, negative-cache với TTL ngắn và semantics rõ. Không làm vậy nếu existence thay đổi cần phản ánh ngay.

### Medium — TTL chỉ là local per-instance freshness contract

**Vấn đề:** Sáu instances có sáu cache độc lập và có thể load dữ liệu tại thời điểm khác nhau.

**Tại sao xảy ra:** In-memory cache không chia sẻ invalidation/state giữa processes.

**Ảnh hưởng production:** Hai users đi vào hai instances có thể thấy version khác nhau trong TTL window.

**Cách sửa:** Trước hết xác định business freshness requirement. Nếu stale tối đa 5 phút được chấp nhận, local cache có thể hoàn toàn hợp lý. Nếu update phải thấy nhanh trên mọi instance, thêm invalidation/version strategy; Redis chỉ là một lựa chọn, không phải mặc định.

### Low — Dùng wall-clock trực tiếp làm testing expiration khó hơn

**Vấn đề:** `DateTime.UtcNow` nằm trực tiếp trong logic.

**Tại sao xảy ra:** Time dependency không injectable.

**Ảnh hưởng production:** Không phải outage risk lớn nhưng expiration tests dễ flaky/chậm.

**Cách sửa:** Dùng time abstraction phù hợp với runtime/project để deterministic test.

## Phiên bản đề xuất

Một phương án giữ kiến trúc đơn giản là local `IMemoryCache` + context factory + per-key single-flight. Ví dụ rút gọn:

```csharp
builder.Services.AddDbContextFactory<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("AppDb")));

builder.Services.AddMemoryCache();
builder.Services.AddSingleton<ProductConfigCache>();

public sealed class ProductConfigCache
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IMemoryCache _cache;
    private readonly ConcurrentDictionary<string, SemaphoreSlim> _gates = new();

    public ProductConfigCache(
        IDbContextFactory<AppDbContext> dbFactory,
        IMemoryCache cache)
    {
        _dbFactory = dbFactory;
        _cache = cache;
    }

    public async Task<ProductConfigDto?> GetAsync(
        string productCode,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue<ProductConfigDto>(productCode, out var cached))
            return cached;

        var gate = _gates.GetOrAdd(productCode, _ => new SemaphoreSlim(1, 1));
        await gate.WaitAsync(cancellationToken);

        try
        {
            if (_cache.TryGetValue<ProductConfigDto>(productCode, out cached))
                return cached;

            await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

            var value = await db.ProductConfigs
                .AsNoTracking()
                .Where(x => x.ProductCode == productCode)
                .Select(x => new ProductConfigDto(
                    x.ProductCode,
                    x.DisplayName,
                    x.SettingsJson))
                .SingleOrDefaultAsync(cancellationToken);

            if (value is not null)
            {
                _cache.Set(
                    productCode,
                    value,
                    TimeSpan.FromMinutes(5));
            }

            return value;
        }
        finally
        {
            gate.Release();
        }
    }
}
```

Production implementation cần thêm chiến lược cleanup cho `_gates` nếu key cardinality lớn; ví dụ trên cố ý tập trung vào lifetime và single-flight mechanism chứ không khẳng định đây là library hoàn chỉnh.

## Giải thích thiết kế sau khi sửa

`IDbContextFactory` cho mỗi load một context riêng, tránh capture scoped context trong singleton và tránh concurrent operations trên cùng context. `IMemoryCache` cung cấp cache abstraction phù hợp hơn custom dictionary cho local process cache.

Per-key gate cho phép hai product codes khác nhau load song song nhưng coalesce concurrent miss của cùng key. Sau khi lấy gate phải kiểm tra cache lần nữa vì request khác có thể đã populate entry trong lúc caller chờ.

Không tự động chuyển sang Redis. Nếu requirement cho phép mỗi instance stale tối đa 5 phút, local cache đơn giản hơn và tránh thêm network dependency. Nếu product yêu cầu invalidate gần như ngay lập tức trên mọi instance, distributed cache hoặc pub/sub invalidation/versioned cache có thể đáng cân nhắc.

## Trade-offs

- Per-key synchronization thêm state và cleanup complexity.
- Local cache không có global consistency giữa instances.
- Distributed cache cải thiện shared state nhưng thêm latency, serialization, outage mode và operational dependency.
- TTL ngắn giảm stale window nhưng tăng database load.
- Negative caching giảm repeated misses nhưng có thể trì hoãn visibility của newly created keys.

## Cách kiểm thử

1. **Concurrency test:** 100 concurrent requests cùng một missing cache key chỉ tạo số database loads phù hợp với single-flight expectation.
2. **Integration test:** context được tạo/dispose đúng và concurrent keys không gây EF Core concurrent-operation exception.
3. **Expiration test:** dùng controllable time để xác minh hit trước expiry và reload sau expiry.
4. **Failure-path test:** database timeout khi cache miss không corrupt cache/gate; request sau có thể retry bình thường.
5. **Load test:** đo database query rate, p95/p99 latency và memory với cache disabled/enabled để chứng minh lợi ích.

## Quan sát trong production

Theo dõi:

- cache hit/miss ratio theo bounded dimensions;
- database query rate và dependency p95/p99;
- cache-load duration và failures;
- số concurrent waiters/single-flight contention cho hot keys;
- process memory và cache entry count;
- EF Core exceptions;
- request p95/p99 và timeout rate;
- config freshness/version nếu business cần kiểm chứng stale behavior.

Alert nên tập trung vào user impact và dependency degradation, không chỉ cache miss ratio.

1. Nếu product yêu cầu config update phải visible trên mọi instance trong 10 giây, bạn thay đổi design thế nào?
2. Khi nào bạn bỏ cache hoàn toàn và tối ưu database/query thay vì tiếp tục tăng cache complexity?
3. Nếu Redis đã tồn tại trong platform, điều đó có đủ để kết luận nên dùng Redis cho use case này không? Vì sao?

# Code Review Challenge 2 — Vue search page trả kết quả của request cũ và render HTML từ API

**Chủ đề:** Vue.js, TypeScript, async race conditions, request cancellation, stale state, XSS, API integration, browser performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một e-commerce administration portal có trang tìm product. Backend ASP.NET Core search API gọi Elasticsearch và trả về `name`, `descriptionHtml`, `price` cùng product metadata.

Frontend dùng Vue 3 + TypeScript. Khi user gõ nhanh, UI đôi lúc hiển thị kết quả không khớp text đang nằm trong search box. Trên mạng chậm, số requests tăng đáng kể. Security review cũng phát hiện API có thể trả `descriptionHtml` chứa nội dung được nhập từ một upstream catalog system.

Requirements:

- chỉ search khi query có ít nhất 2 ký tự;
- user gõ nhanh không được làm result cũ overwrite result mới;
- request không còn cần thiết nên được cancel khi hợp lý;
- loading/error state phải phản ánh request hiện hành;
- product description có formatting nhưng upstream content không được mặc định tin cậy;
- component có thể bị unmount khi user đổi route;
- không cần một state-management framework mới chỉ cho page này.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface Product {
  id: string
  name: string
  descriptionHtml: string
  price: number
}

const query = ref('')
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')

watch(query, async (value) => {
  if (value.length < 2) {
    products.value = []
    return
  }

  loading.value = true
  error.value = ''

  try {
    const response = await fetch(`/api/products/search?q=${value}`)
    const data = await response.json()
    products.value = data.items
  } catch (e) {
    error.value = String(e)
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <article v-for="product in products" :key="product.id">
      <h3>{{ product.name }}</h3>
      <div v-html="product.descriptionHtml"></div>
      <strong>{{ product.price }}</strong>
    </article>
  </section>
</template>
```

Backend có rate limiting ở mức cơ bản nhưng không muốn frontend phát request vô ích. Không có guarantee rằng request A gửi trước request B sẽ hoàn thành trước B.

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong asynchronous state updates.
2. Xác định security risk ở rendering path.
3. Giải thích impact trên slow network và khi user gõ nhanh.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất corrected component/design mà không thêm state-management framework không cần thiết.
6. Nêu testing cho race condition, cancellation, errors và XSS boundary.
7. Nêu browser/backend telemetry giúp xác minh behavior production.

## Câu hỏi gợi mở

1. Request cho `ab` và request cho `abc` có thể hoàn thành theo thứ tự nào?
2. `finally` của một request cũ có quyền đặt `loading = false` trong khi request mới còn chạy không?
3. `fetch` có tự throw cho mọi HTTP 4xx/5xx không?
4. Query string đang được tạo từ input user như thế nào?
5. `v-html` có implication gì khi HTML đến từ upstream content không được tin cậy?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **nhiều asynchronous operations cùng ghi vào một shared UI state mà không biết operation nào còn current**.

### Gợi ý 2

Cancellation giải quyết wasted work, nhưng correctness vẫn nên có cơ chế không cho stale completion commit state; security boundary của HTML rendering là một vấn đề độc lập.

## Kết quả code review tham khảo

### Critical — `v-html` render upstream HTML không đáng tin cậy

**Vấn đề:** `descriptionHtml` được đưa trực tiếp vào DOM bằng `v-html` dù upstream catalog content không được coi là trusted.

**Tại sao xảy ra:** HTML rendering bypass text escaping bình thường và có thể tạo XSS nếu content chứa dangerous markup/payload phù hợp với browser execution context.

**Ảnh hưởng production:** Stored/content-sourced XSS có thể chạy trong browser của admin, dẫn đến session/action abuse tùy authentication model và browser protections.

**Cách sửa:** Ưu tiên render plain text nếu formatting không bắt buộc. Nếu business bắt buộc HTML, sanitize bằng một well-maintained allowlist-based sanitizer ở trust boundary phù hợp và có security tests. Không tự viết regex sanitizer.

### High — Stale request có thể overwrite kết quả mới

**Vấn đề:** Mọi request completion đều gán `products.value`.

**Tại sao xảy ra:** Network completion order không đảm bảo giống request creation order.

**Ảnh hưởng production:** User gõ `laptop`, nhưng request cũ cho `lap` hoàn thành sau và UI hiển thị dữ liệu không tương ứng query hiện tại.

**Cách sửa:** Cancel previous request và/hoặc dùng request generation/token để chỉ current request được commit state.

### High — Loading/error state cũng có race condition

**Vấn đề:** `finally` của request cũ có thể set `loading = false`; `catch` của request cũ có thể ghi error sau khi request mới đã thành công.

**Tại sao xảy ra:** State không gắn với request identity.

**Ảnh hưởng production:** Spinner biến mất quá sớm hoặc UI hiển thị lỗi stale.

**Cách sửa:** Chỉ current request được update `products`, `loading`, `error`; AbortError của superseded request không nên hiển thị như user-facing failure.

### Medium — Không cancel request superseded hoặc khi component unmount

**Vấn đề:** Requests cũ tiếp tục dùng browser/backend/network resources.

**Tại sao xảy ra:** Không có `AbortController` lifecycle.

**Ảnh hưởng production:** Gõ nhanh tạo nhiều unnecessary searches; backend/Elasticsearch load tăng và completion cũ tiếp tục tranh chấp state.

**Cách sửa:** Abort request trước khi bắt đầu request mới và abort khi watcher invalidated/component unmount. Vue watcher cleanup có thể được dùng phù hợp với version/project conventions.

### Medium — Không kiểm tra `response.ok`

**Vấn đề:** Code gọi `response.json()` rồi coi payload như success ngay cả với HTTP error response nếu body parse được.

**Tại sao xảy ra:** `fetch` không tự reject chỉ vì server trả HTTP 4xx/5xx.

**Ảnh hưởng production:** Error response có thể bị xử lý sai shape, tạo misleading UI error hoặc runtime failure.

**Cách sửa:** Kiểm tra `response.ok`, map expected API errors và xử lý malformed payload phù hợp.

### Medium — Query không được encode đúng cách

**Vấn đề:** Raw `value` được nối trực tiếp vào URL.

**Tại sao xảy ra:** Ký tự `&`, `#`, `?`, Unicode hoặc reserved characters có thể thay đổi query semantics.

**Ảnh hưởng production:** Search sai hoặc request URL không như user mong đợi.

**Cách sửa:** Dùng `URLSearchParams` hoặc encoding API chuẩn.

### Medium — Không debounce input

**Vấn đề:** Mỗi keystroke hợp lệ phát request ngay.

**Tại sao xảy ra:** Watcher không có delay/coalescing cho typing burst.

**Ảnh hưởng production:** Wasted requests và Elasticsearch/backend load cao hơn cần thiết.

**Cách sửa:** Debounce một khoảng phù hợp UX và đo thực tế; cancellation vẫn cần vì debounce không loại bỏ mọi overlap.

### Low — Error hiển thị trực tiếp từ exception string

**Vấn đề:** `String(e)` có thể tạo thông báo kỹ thuật không phù hợp user và không phân loại network/abort/server error.

**Tại sao xảy ra:** UI và diagnostics dùng chung representation.

**Ảnh hưởng production:** UX kém; debugging context có thể thiếu dù user thấy technical text.

**Cách sửa:** User-facing error ổn định; diagnostics chi tiết gửi telemetry có kiểm soát.

## Phiên bản đề xuất

Ví dụ sau tập trung vào request identity, cancellation và URL construction. Phần HTML được đổi sang plain text vì scenario chưa chứng minh rich HTML là bắt buộc:

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface Product {
  id: string
  name: string
  description: string
  price: number
}

const query = ref('')
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')
let generation = 0

watch(query, async (rawValue, _oldValue, onCleanup) => {
  const value = rawValue.trim()
  const currentGeneration = ++generation

  if (value.length < 2) {
    products.value = []
    loading.value = false
    error.value = ''
    return
  }

  const controller = new AbortController()
  onCleanup(() => controller.abort())

  loading.value = true
  error.value = ''

  try {
    const params = new URLSearchParams({ q: value })
    const response = await fetch(
      `/api/products/search?${params.toString()}`,
      { signal: controller.signal })

    if (!response.ok) {
      throw new Error(`Search failed with status ${response.status}`)
    }

    const data = await response.json()

    if (currentGeneration === generation) {
      products.value = data.items
    }
  } catch (e) {
    if (controller.signal.aborted)
      return

    if (currentGeneration === generation) {
      error.value = 'Search is temporarily unavailable.'
    }
  } finally {
    if (currentGeneration === generation) {
      loading.value = false
    }
  }
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <article v-for="product in products" :key="product.id">
      <h3>{{ product.name }}</h3>
      <div>{{ product.description }}</div>
      <strong>{{ product.price }}</strong>
    </article>
  </section>
</template>
```

Nếu rich HTML là requirement thực sự, contract phải đổi thành sanitized content hoặc frontend phải dùng sanitizer đã được security review. Vị trí sanitize phụ thuộc ownership/trust boundary; không nên coi tên field `descriptionHtml` là bằng chứng rằng content an toàn.

Production version cũng nên debounce input. Debounce implementation có thể là composable nhỏ hoặc utility hiện có trong codebase; không cần đưa thêm global state manager.

## Giải thích thiết kế sau khi sửa

Watcher cleanup abort request cũ khi query thay đổi hoặc watcher bị invalidated. `generation` tạo correctness guard độc lập: ngay cả khi một async completion không bị cancel kịp, chỉ generation hiện hành mới được ghi shared state.

`URLSearchParams` bảo đảm query được encode theo URL semantics. `response.ok` tách HTTP failure khỏi success payload.

Việc render plain text loại trust problem mạnh nhất. Nếu formatting là business requirement, sanitation phải được thiết kế như security boundary với allowlist, dependency maintenance và tests.

Debounce và cancellation giải quyết hai vấn đề khác nhau: debounce giảm số request bắt đầu; cancellation dừng request đã bắt đầu nhưng không còn cần; generation guard bảo vệ UI correctness.

## Trade-offs

- Debounce quá dài làm search cảm giác chậm; quá ngắn giảm ít load.
- Cancellation không đảm bảo backend đã ngừng mọi work nếu request đã đi sâu vào dependency; backend vẫn cần propagate cancellation khi phù hợp.
- Generation token thêm state nhỏ nhưng giúp correctness rõ ràng.
- Sanitizing rich HTML giữ formatting nhưng thêm dependency/security maintenance; plain text đơn giản và an toàn hơn nếu product chấp nhận.
- Client-side fixes không thay thế backend rate limiting/query cost controls.

## Cách kiểm thử

1. **Concurrency/race test:** mock request A chậm và B nhanh; xác minh A hoàn thành sau không overwrite B.
2. **Cancellation test:** đổi query/unmount component và xác minh request trước nhận abort; AbortError không hiển thị lỗi.
3. **HTTP integration test:** 400/429/500 và malformed payload tạo state hợp lý, không được coi là success.
4. **Security test:** malicious upstream description không execute script/event handler; nếu dùng sanitizer, test allowlist/bypass cases quan trọng.
5. **E2E/Playwright test:** gõ nhanh trên simulated slow network, xác minh result cuối cùng khớp query hiện tại và loading state không nhấp nháy sai.

## Quan sát trong production

Theo dõi ở browser và backend:

- search requests per user/session hoặc per page interaction ở mức aggregate phù hợp privacy;
- client abort count;
- request duration và HTTP status distribution;
- backend search API p95/p99;
- Elasticsearch dependency latency/query volume;
- 429/error rate;
- frontend error telemetry với route/release correlation;
- Content Security Policy violation reports nếu platform có sử dụng;
- tỷ lệ stale-result bug có thể được phát hiện qua client instrumentation có kiểm soát trong quá trình rollout.

Không log raw search terms nếu chúng có thể chứa dữ liệu nhạy cảm mà chưa có policy phù hợp.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend đã nhận request trước khi browser abort, cancellation ở frontend có đảm bảo Elasticsearch query dừng ngay không?
2. Nếu product bắt buộc rich HTML từ nhiều upstream vendors, bạn đặt sanitation boundary ở frontend, backend hay ingestion pipeline và dựa trên tiêu chí nào?
3. Debounce 300 ms thường được dùng trong ví dụ, nhưng bạn sẽ chọn con số production bằng evidence nào thay vì copy một giá trị mặc định?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- DI lifetime phải phản ánh ownership: singleton không được vô tình capture request-scoped state như `DbContext`.
- `DbContext` không phải shared concurrent unit-of-work cho nhiều requests; lifetime mismatch thường chỉ lộ rõ dưới load.
- Cache design phải xét concurrency, stampede, bounded growth, freshness và failure behavior; “đã có Redis” không tự động nghĩa là phải dùng Redis.
- Trong frontend async flow, cancellation giúp tiết kiệm work nhưng request identity/generation mới bảo vệ state khỏi stale completion một cách rõ ràng.
- `v-html` hoặc tương đương là trust boundary; upstream content không trở thành trusted chỉ vì nó đến từ một backend API.
- Performance optimization cần được chứng minh bằng telemetry: cache hit ratio, dependency load, p95/p99 và resource usage.

## Mẫu tư duy cần nhớ

1. **Kiểm tra lifetime và ownership trước khi chia sẻ mutable state.**
2. **Thiết kế cache cùng stampede, invalidation, failure và measurement.**
3. **Async completion order không phải request creation order.**
4. **Cancellation giảm wasted work; identity guard bảo vệ correctness.**
5. **Xác định trust boundary trước khi render hoặc lưu dữ liệu từ external systems.**
