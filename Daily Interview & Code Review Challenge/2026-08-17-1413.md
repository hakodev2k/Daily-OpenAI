# Code Review Challenge 1 — SignalR presence tracking bị sai dưới tải cao

**Chủ đề:** Concurrency, race condition, shared state, resource lifetime, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một ứng dụng nội bộ dùng ASP.NET Core SignalR để hiển thị trạng thái online/offline của nhân viên theo thời gian thực. Mỗi user có thể mở nhiều tab trình duyệt, có thể dùng cả web và mobile cùng lúc.

Hệ thống chạy 3 instance sau load balancer. Trong giờ cao điểm có khoảng 6.000–10.000 kết nối đồng thời. QA báo rằng một số user đang online nhưng UI lại hiển thị offline; đôi khi user disconnect một tab thì bị đánh dấu offline dù vẫn còn tab khác đang mở. Production log thỉnh thoảng xuất hiện `KeyNotFoundException`, và sau khi scale-out số liệu online giữa các instance lệch nhau đáng kể.

Team muốn giữ implementation đơn giản, không thêm hạ tầng mới nếu chưa thực sự cần thiết.

## Đoạn code cần review

```csharp
using Microsoft.AspNetCore.SignalR;

public sealed class PresenceHub : Hub
{
    private static readonly Dictionary<string, List<string>> Connections = new();
    private static int _onlineUsers;

    private readonly ILogger<PresenceHub> _logger;
    private readonly IUserStatusRepository _repository;

    public PresenceHub(
        ILogger<PresenceHub> logger,
        IUserStatusRepository repository)
    {
        _logger = logger;
        _repository = repository;
    }

    public override async Task OnConnectedAsync()
    {
        var userId = Context.UserIdentifier!;

        if (!Connections.ContainsKey(userId))
        {
            Connections[userId] = new List<string>();
            _onlineUsers++;
        }

        Connections[userId].Add(Context.ConnectionId);

        await _repository.SetOnlineAsync(userId, true);

        await Clients.All.SendAsync(
            "presenceChanged",
            userId,
            true,
            _onlineUsers);

        _logger.LogInformation(
            "User {UserId} connected. Connections={Count}, Online={Online}",
            userId,
            Connections[userId].Count,
            _onlineUsers);

        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        var userId = Context.UserIdentifier!;

        Connections[userId].Remove(Context.ConnectionId);

        if (Connections[userId].Count == 0)
        {
            Connections.Remove(userId);
            _onlineUsers--;
            await _repository.SetOnlineAsync(userId, false);
        }

        await Clients.All.SendAsync(
            "presenceChanged",
            userId,
            false,
            _onlineUsers);

        _logger.LogInformation(
            "User {UserId} disconnected. Online={Online}",
            userId,
            _onlineUsers);

        await base.OnDisconnectedAsync(exception);
    }
}
```

## Kết quả code review tham khảo

### 1. Shared `Dictionary` và `List` không thread-safe

- **Problem:** `Dictionary` và `List` static bị đọc/ghi đồng thời từ nhiều hub invocation.
- **Why it happens:** SignalR có thể xử lý nhiều connection song song; các thao tác `ContainsKey`, assignment, `Add`, `Remove`, `Count` không tạo thành một critical section nguyên tử.
- **Production impact:** Lost update, duplicate initialization, `KeyNotFoundException`, corruption logic, số connection sai.
- **Severity:** Critical
- **Recommended fix:** Dùng cấu trúc thread-safe cộng với atomic operation thực sự, hoặc encapsulate mutation bằng synchronization rõ ràng. Không chỉ thay `Dictionary` thành `ConcurrentDictionary` rồi giữ `List` mutable bên trong.

### 2. Check-then-act race khi connect

- **Problem:** Hai connection cùng user có thể cùng thấy `ContainsKey(userId) == false`.
- **Why it happens:** Check và insert là hai bước riêng biệt.
- **Production impact:** `_onlineUsers` có thể tăng hai lần; list connection có thể bị thay thế; trạng thái presence sai.
- **Severity:** High
- **Recommended fix:** Dùng `GetOrAdd` với một container thread-safe và xác định rõ transition `0 -> 1` connection.

### 3. `_onlineUsers++` và `--` không an toàn và có thể drift

- **Problem:** Counter static mutable không gắn chặt với transition của state.
- **Why it happens:** Increment/decrement độc lập với dictionary mutation và không được đồng bộ.
- **Production impact:** Dashboard online count sai, thậm chí âm trong các failure/race edge case.
- **Severity:** High
- **Recommended fix:** Không duy trì redundant counter nếu có thể tính từ authoritative store; nếu cần counter thì update atomically cùng transition logic.

### 4. Disconnect một connection nhưng broadcast user offline

- **Problem:** Code luôn gửi `presenceChanged(..., false, ...)` sau disconnect.
- **Why it happens:** Broadcast không phụ thuộc việc user còn connection khác hay không.
- **Production impact:** User có nhiều tab/device bị hiển thị offline sai.
- **Severity:** High
- **Recommended fix:** Chỉ phát `offline` khi transition thực sự từ ít nhất 1 connection về 0 connection.

### 5. In-memory state không đúng khi chạy 3 instance

- **Problem:** `static` chỉ chia sẻ trong một process, không phải toàn cluster.
- **Why it happens:** Mỗi app instance có memory riêng.
- **Production impact:** User có connection trên instance A nhưng instance B không biết; count online khác nhau; restart/scale làm mất state.
- **Severity:** High
- **Recommended fix:** Xác định requirement. Nếu chỉ cần per-instance telemetry, in-memory có thể chấp nhận. Nếu cần global presence, cần shared/distributed state hoặc cơ chế presence chuyên dụng; tránh coi Redis backplane đơn thuần như authoritative presence store nếu chưa thiết kế semantics rõ ràng.

### 6. Repository state có thể bị ghi sai khi user còn connection ở instance khác

- **Problem:** Instance A có thể set user offline khi connection cuối cùng trên A disconnect, dù user vẫn đang kết nối với instance B.
- **Why it happens:** Logic không biết tổng connection toàn cluster.
- **Production impact:** Persistent status sai, downstream system hiểu nhầm user offline.
- **Severity:** High
- **Recommended fix:** Nếu persistence cần phản ánh global presence, cập nhật theo distributed connection count hoặc lease/heartbeat model thay vì per-instance disconnect đơn lẻ.

### 7. Failure giữa state mutation, DB update và broadcast gây inconsistency

- **Problem:** Memory state thay đổi trước, sau đó repository/broadcast có thể throw.
- **Why it happens:** Không có atomic boundary giữa các side effect.
- **Production impact:** Một phần hệ thống nghĩ online, phần khác nghĩ offline; retry callback có thể làm state lệch thêm.
- **Severity:** Medium
- **Recommended fix:** Chọn source of truth, thiết kế eventual consistency rõ ràng, tách state transition khỏi notification và có retry/repair mechanism khi cần.

### 8. Giả định `UserIdentifier` luôn có giá trị

- **Problem:** Null-forgiving operator che mất trường hợp identity không được resolve.
- **Why it happens:** Authentication hoặc `IUserIdProvider` có thể không cung cấp identifier.
- **Production impact:** Exception khi connect/disconnect; khó chẩn đoán auth/presence issue.
- **Severity:** Medium
- **Recommended fix:** Validate identifier và reject/log connection có cấu trúc nếu thiếu identity.

### 9. Logging thiếu correlation và exception context hữu ích

- **Problem:** Log chỉ có userId và count, không có instance, connectionId, transition, exception/disconnect reason.
- **Why it happens:** Logging tập trung vào happy path.
- **Production impact:** Rất khó điều tra race và cross-instance inconsistency.
- **Severity:** Medium
- **Recommended fix:** Structured logs với `ConnectionId`, `UserId`, `InstanceId`, connection count trước/sau, transition, exception category và activity/trace id.

## Phiên bản code đề xuất

Ví dụ dưới đây chỉ giải quyết đúng semantics và thread-safety **trong một instance**. Nếu requirement là global presence trên nhiều instance, cần shared source of truth hoặc lease/heartbeat model ở tầng khác.

```csharp
using System.Collections.Concurrent;
using Microsoft.AspNetCore.SignalR;

public sealed class PresenceTracker
{
    private readonly ConcurrentDictionary<string, ConcurrentDictionary<string, byte>> _users = new();

    public bool Add(string userId, string connectionId, out int connectionCount)
    {
        var connections = _users.GetOrAdd(
            userId,
            static _ => new ConcurrentDictionary<string, byte>());

        var added = connections.TryAdd(connectionId, 0);
        connectionCount = connections.Count;

        return added && connectionCount == 1;
    }

    public bool Remove(string userId, string connectionId, out int connectionCount)
    {
        connectionCount = 0;

        if (!_users.TryGetValue(userId, out var connections))
            return false;

        connections.TryRemove(connectionId, out _);
        connectionCount = connections.Count;

        if (connectionCount != 0)
            return false;

        return _users.TryRemove(
            new KeyValuePair<string, ConcurrentDictionary<string, byte>>(userId, connections));
    }

    public int OnlineUsers => _users.Count;
}

public sealed class PresenceHub : Hub
{
    private readonly PresenceTracker _tracker;
    private readonly IUserStatusRepository _repository;
    private readonly ILogger<PresenceHub> _logger;

    public PresenceHub(
        PresenceTracker tracker,
        IUserStatusRepository repository,
        ILogger<PresenceHub> logger)
    {
        _tracker = tracker;
        _repository = repository;
        _logger = logger;
    }

    public override async Task OnConnectedAsync()
    {
        var userId = Context.UserIdentifier;
        if (string.IsNullOrWhiteSpace(userId))
        {
            Context.Abort();
            return;
        }

        var becameOnline = _tracker.Add(
            userId,
            Context.ConnectionId,
            out var connectionCount);

        if (becameOnline)
        {
            await _repository.SetOnlineAsync(userId, true);
            await Clients.All.SendAsync(
                "presenceChanged",
                userId,
                true,
                _tracker.OnlineUsers,
                Context.ConnectionAborted);
        }

        _logger.LogInformation(
            "Presence connected UserId={UserId} ConnectionId={ConnectionId} " +
            "Connections={Connections} BecameOnline={BecameOnline} OnlineUsers={OnlineUsers}",
            userId,
            Context.ConnectionId,
            connectionCount,
            becameOnline,
            _tracker.OnlineUsers);

        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        var userId = Context.UserIdentifier;
        if (string.IsNullOrWhiteSpace(userId))
            return;

        var becameOffline = _tracker.Remove(
            userId,
            Context.ConnectionId,
            out var connectionCount);

        if (becameOffline)
        {
            await _repository.SetOnlineAsync(userId, false);
            await Clients.All.SendAsync(
                "presenceChanged",
                userId,
                false,
                _tracker.OnlineUsers);
        }

        _logger.LogInformation(
            exception,
            "Presence disconnected UserId={UserId} ConnectionId={ConnectionId} " +
            "Connections={Connections} BecameOffline={BecameOffline} OnlineUsers={OnlineUsers}",
            userId,
            Context.ConnectionId,
            connectionCount,
            becameOffline,
            _tracker.OnlineUsers);

        await base.OnDisconnectedAsync(exception);
    }
}
```

### Nếu cần global presence trên nhiều instance

Một hướng thiết kế tốt hơn là:

- mỗi connection tạo một record/lease theo `userId + connectionId + instanceId`;
- record có TTL hoặc heartbeat;
- user được coi online khi còn ít nhất một lease hợp lệ;
- disconnect cố gắng remove lease nhưng correctness không phụ thuộc hoàn toàn vào callback disconnect;
- instance crash được xử lý nhờ TTL;
- broadcast chỉ phản ánh transition global `0 -> 1` và `1 -> 0`.

Không nhất thiết phải triển khai distributed mechanism nếu business chỉ cần approximate presence. Requirement về độ chính xác phải được làm rõ trước.

## Trade-offs

- In-memory tracker đơn giản, nhanh, ít dependency nhưng chỉ đúng trong một process và mất state khi restart.
- Distributed store cho global presence tăng độ chính xác nhưng thêm latency, cost và failure mode mới.
- Heartbeat/lease chịu được abrupt disconnect tốt hơn callback-only model nhưng tạo thêm write load.
- Persist trạng thái online vào relational DB cho từng connect/disconnect có thể tạo write amplification; nếu chỉ dùng cho UI realtime, một transient/distributed store phù hợp hơn.
- `ConcurrentDictionary` không tự động làm mọi multi-step invariant trở nên atomic; vẫn phải thiết kế transition rõ ràng.

## Cách kiểm thử

1. **Concurrency test:** 100 connection cùng một user connect đồng thời; chỉ có một transition online và tổng connection chính xác.
2. **Multi-tab test:** user có 3 connection, disconnect 1 rồi 2 connection; không phát offline; chỉ disconnect connection cuối mới phát offline.
3. **Failure-path test:** repository throw khi set online/offline; kiểm tra behavior mong muốn, logging và reconciliation strategy.
4. **Scale-out integration test:** mô phỏng user kết nối vào hai instance; xác nhận in-memory implementation không được dùng như global source of truth hoặc kiểm tra distributed implementation nếu đã có.
5. **Load test:** hàng nghìn connect/disconnect ngẫu nhiên, quan sát exception rate, CPU, memory, count drift và event correctness.

# Code Review Challenge 2 — Middleware logging request/response gây memory spike và rò dữ liệu nhạy cảm

## Bối cảnh

Team thêm một middleware để log toàn bộ request và response body nhằm hỗ trợ debug production. Sau deployment, API bắt đầu có memory spike và Gen 2 GC tăng mạnh trong giờ cao điểm. Một endpoint upload/import file thường nhận request 20–80 MB. Một endpoint export báo cáo có response 30–100 MB.

Security team đồng thời phát hiện log có chứa access token, email, phone và đôi lúc có cả dữ liệu HR nhạy cảm. SRE nhận thấy p95 latency tăng đáng kể khi bật middleware, nhưng khi tắt logging thì hệ thống ổn định trở lại.

Yêu cầu business: vẫn cần đủ dữ liệu để điều tra lỗi, nhưng không được log secret hoặc toàn bộ payload lớn.

## Đoạn code cần review

```csharp
public sealed class BodyLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<BodyLoggingMiddleware> _logger;

    public BodyLoggingMiddleware(
        RequestDelegate next,
        ILogger<BodyLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var requestReader = new StreamReader(context.Request.Body);
        var requestBody = await requestReader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        var originalBody = context.Response.Body;
        await using var responseBuffer = new MemoryStream();
        context.Response.Body = responseBuffer;

        _logger.LogInformation(
            "HTTP Request {Method} {Path} Headers={Headers} Body={Body}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers,
            requestBody);

        try
        {
            await _next(context);

            responseBuffer.Position = 0;
            var responseBody = await new StreamReader(responseBuffer)
                .ReadToEndAsync();

            _logger.LogInformation(
                "HTTP Response {StatusCode} Headers={Headers} Body={Body}",
                context.Response.StatusCode,
                context.Response.Headers,
                responseBody);

            responseBuffer.Position = 0;
            await responseBuffer.CopyToAsync(originalBody);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Unhandled exception. RequestBody={RequestBody}",
                requestBody);
            throw;
        }
        finally
        {
            context.Response.Body = originalBody;
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Log toàn bộ headers có thể làm lộ secret

- **Problem:** `context.Request.Headers` bị log toàn bộ.
- **Why it happens:** Header có thể chứa `Authorization`, cookies, API keys hoặc token khác.
- **Production impact:** Credential leakage vào log platform; tăng blast radius nếu log bị truy cập trái phép.
- **Severity:** Critical
- **Recommended fix:** Allowlist header an toàn hoặc redact rõ ràng các header nhạy cảm. Không dùng blacklist nhỏ như biện pháp duy nhất.

### 2. Log toàn bộ request/response body làm lộ PII và dữ liệu nghiệp vụ

- **Problem:** Payload được log raw.
- **Why it happens:** Middleware không biết schema, classification hay field sensitivity.
- **Production impact:** Vi phạm data-minimization, privacy/security policy, có thể chứa HR data, email, phone, token hoặc document content.
- **Severity:** Critical
- **Recommended fix:** Mặc định không log body. Chỉ log metadata; nếu endpoint thật sự cần payload sample thì dùng allowlist endpoint + redaction theo schema + truncation + environment policy.

### 3. Buffer toàn bộ request body vào memory/string

- **Problem:** `ReadToEndAsync()` materialize toàn payload thành string.
- **Why it happens:** Request được buffer rồi decode toàn bộ text.
- **Production impact:** Allocation lớn, LOH pressure, Gen 2 GC, memory spike; binary upload còn có thể bị xử lý sai như text.
- **Severity:** High
- **Recommended fix:** Không đọc body cho upload/binary endpoint. Nếu cần diagnostic sampling, giới hạn số byte rất nhỏ và chỉ với content type phù hợp.

### 4. Buffer toàn bộ response trong `MemoryStream`

- **Problem:** Mọi response bị chặn vào memory cho đến khi downstream hoàn tất.
- **Why it happens:** Middleware thay `Response.Body` bằng `MemoryStream`.
- **Production impact:** Streaming bị phá vỡ; time-to-first-byte tăng; response lớn giữ nhiều memory; concurrency làm memory amplification nghiêm trọng.
- **Severity:** High
- **Recommended fix:** Không buffer response mặc định. Log status/size/timing; nếu cần capture body, chỉ capture giới hạn nhỏ bằng tee/capped stream trong endpoint phù hợp.

### 5. Nhiều bản sao payload cùng tồn tại

- **Problem:** Payload tồn tại dưới dạng request buffer, string, response bytes và response string.
- **Why it happens:** Buffering + `ReadToEndAsync` + log formatter/storage.
- **Production impact:** Peak memory cao hơn kích thước payload thực tế nhiều lần.
- **Severity:** High
- **Recommended fix:** Tránh materialization toàn bộ; capture có giới hạn; ưu tiên structured metadata.

### 6. Middleware phá semantics của streaming/SSE/file download

- **Problem:** Client không nhận dữ liệu cho đến khi toàn response hoàn tất.
- **Why it happens:** Response bị giữ trong `MemoryStream`.
- **Production impact:** Timeout, latency tăng, không tương thích endpoint streaming hoặc file rất lớn.
- **Severity:** High
- **Recommended fix:** Bypass body capture cho streaming, file, SSE và content type không phù hợp.

### 7. Cancellation chưa được truyền đầy đủ

- **Problem:** Các operation đọc/copy không nhất quán dùng `context.RequestAborted`.
- **Why it happens:** Cancellation token bị bỏ qua trong hot-path I/O.
- **Production impact:** Client đã disconnect nhưng server vẫn copy/đọc dữ liệu không cần thiết.
- **Severity:** Medium
- **Recommended fix:** Truyền `context.RequestAborted` vào các async operation hỗ trợ cancellation.

### 8. Đọc request như text mà không xét content type/encoding

- **Problem:** Mọi body được đọc bằng `StreamReader` mặc định.
- **Why it happens:** Middleware giả định payload text.
- **Production impact:** Binary content vô nghĩa, log phình to, encoding sai, tăng CPU/allocation.
- **Severity:** Medium
- **Recommended fix:** Chỉ capture với text media type đã allowlist; bỏ qua multipart, octet-stream và file upload.

### 9. Logging hot path quá nặng ngay cả với payload nhỏ

- **Problem:** Hai log event lớn cho mỗi request.
- **Why it happens:** Logging được coi như dump thay vì telemetry.
- **Production impact:** Tăng serialization CPU, network I/O tới log sink, storage cost, throttling/backpressure từ logging pipeline.
- **Severity:** Medium
- **Recommended fix:** Log metadata có cấu trúc, sampling phù hợp, log level theo outcome và diagnostic mode có thời hạn.

### 10. Failure path có thể log lại chính dữ liệu nhạy cảm

- **Problem:** Catch block log `requestBody` thêm lần nữa.
- **Why it happens:** Error logging mặc định dump payload.
- **Production impact:** Dữ liệu nhạy cảm dễ xuất hiện đúng lúc incident và thường được giữ lâu hơn.
- **Severity:** Medium
- **Recommended fix:** Error log chỉ chứa correlation id, route, status/error type và sanitized diagnostic fields.

## Phiên bản code đề xuất

Một baseline an toàn hơn là **không log body mặc định**. Log metadata có cấu trúc, latency, status, route template và correlation id. Body capture nên là capability riêng, bounded và allowlisted.

```csharp
using System.Diagnostics;

public sealed class RequestTelemetryMiddleware
{
    private static readonly HashSet<string> SafeHeaders =
        new(StringComparer.OrdinalIgnoreCase)
        {
            "Content-Type",
            "Content-Length",
            "User-Agent",
            "X-Request-Id"
        };

    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

    public RequestTelemetryMiddleware(
        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        var requestId = context.TraceIdentifier;

        try
        {
            await _next(context);
        }
        catch (OperationCanceledException)
            when (context.RequestAborted.IsCancellationRequested)
        {
            _logger.LogInformation(
                "Request cancelled RequestId={RequestId} Method={Method} Path={Path}",
                requestId,
                context.Request.Method,
                context.Request.Path);

            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Request failed RequestId={RequestId} Method={Method} Path={Path}",
                requestId,
                context.Request.Method,
                context.Request.Path);

            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            var safeHeaders = context.Request.Headers
                .Where(x => SafeHeaders.Contains(x.Key))
                .ToDictionary(x => x.Key, x => x.Value.ToString());

            _logger.LogInformation(
                "HTTP {Method} {Path} completed Status={StatusCode} " +
                "ElapsedMs={ElapsedMs} ContentLength={ContentLength} Headers={Headers} RequestId={RequestId}",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                context.Request.ContentLength,
                safeHeaders,
                requestId);
        }
    }
}
```

Nếu business bắt buộc cần sample body để điều tra một nhóm endpoint cụ thể, nên tách thành một component bounded, ví dụ:

```csharp
public static bool CanCaptureBody(HttpRequest request)
{
    if (request.ContentLength is > 16_384)
        return false;

    if (request.ContentType is null)
        return false;

    return request.ContentType.StartsWith("application/json", StringComparison.OrdinalIgnoreCase)
        || request.ContentType.StartsWith("text/", StringComparison.OrdinalIgnoreCase);
}
```

Và vẫn cần:

- allowlist route;
- giới hạn bytes;
- redaction theo field/schema;
- không capture `Authorization`, cookies hoặc secret;
- sampling;
- feature flag có audit;
- retention ngắn hơn nếu chứa diagnostic payload;
- disable cho upload/download/streaming endpoint.

## Trade-offs

- Metadata-only logging giảm đáng kể forensic detail so với raw payload nhưng an toàn và rẻ hơn rất nhiều.
- Sampling body giúp điều tra incident nhưng có nguy cơ bỏ lỡ request cần thiết; correlation id + domain audit log thường hữu ích hơn raw body.
- Redaction động theo JSON field name có thể bỏ sót secret nếu schema thay đổi; allowlist field thường an toàn hơn blacklist.
- Tee stream giới hạn byte vẫn thêm overhead trên hot path; chỉ nên bật khi có requirement rõ ràng.
- Application logging không nên thay thế distributed tracing, metrics và audit log chuyên biệt.

## Cách kiểm thử

1. **Large payload load test:** 50–100 concurrent request với upload 50 MB và response lớn; so sánh memory, GC, p95/p99 trước/sau fix.
2. **Security test:** request có `Authorization`, cookie, email, phone, password/token field; xác nhận chúng không xuất hiện trong log.
3. **Streaming test:** file download/streaming endpoint bắt đầu trả dữ liệu ngay thay vì đợi toàn bộ payload hoàn tất.
4. **Cancellation test:** client hủy request giữa chừng; server dừng công việc liên quan và log cancellation đúng mức.
5. **Failure-path test:** downstream throw; log vẫn có request id, route, elapsed/error information nhưng không dump body.

## Quan sát trong production

Nên có:

- Histogram request duration theo route/status.
- Request/response size distribution.
- Process memory, GC heap size, Gen 2 collections, allocation rate.
- Log ingestion bytes/sec và dropped/throttled log count nếu log sink hỗ trợ.
- Trace span cho slow request và downstream dependency.
- Metric số lần diagnostic body capture được bật.
- Audit khi thay đổi feature flag liên quan payload logging.
- Alert khi allocation rate, Gen 2 GC, memory working set hoặc p95/p99 latency vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product owner yêu cầu “phải log full body để debug”, bạn sẽ thương lượng requirement và đưa ra lựa chọn kỹ thuật nào?
2. Nếu chỉ log 4 KB đầu của JSON body thì đã đủ an toàn chưa? Vì sao?
3. Trong trường hợp cần audit nghiệp vụ lâu dài, vì sao audit log có schema riêng thường tốt hơn HTTP body logging?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Shared mutable state trong realtime system phải được phân tích cả ở cấp thread, process và cluster.
- `ConcurrentDictionary` không tự động bảo đảm invariant nhiều bước; cần thiết kế state transition rõ ràng.
- Presence của user khác với connection lifetime: một user có thể có nhiều connection và disconnect callback không nên là nguồn sự thật duy nhất.
- Middleware nằm trên hot path nên mọi buffering, allocation và logging overhead đều được nhân theo concurrency.
- Raw request/response logging tạo cùng lúc rủi ro security, privacy, memory, latency và log-cost.
- Observability tốt ưu tiên structured metadata, trace, metric và correlation hơn data dump.

## Mẫu tư duy cần nhớ

1. **Phân biệt scope:** thread-safe trong một process không đồng nghĩa đúng khi scale-out.
2. **Thiết kế theo state transition:** chỉ phát side effect khi state thực sự chuyển từ trạng thái A sang B.
3. **Hot path phải bounded:** bất kỳ buffer, retry, allocation hoặc log payload nào cũng cần giới hạn.
4. **Data minimization:** đừng thu thập dữ liệu chỉ vì “có thể hữu ích khi debug”.
5. **Observability là một phần của design:** log, metric, trace phải giúp xác minh hypothesis mà không tự tạo incident mới.
