# Code Review Challenge 1 — Hai approver cùng duyệt leave và quota bị trừ hai lần

**Chủ đề:** Concurrency, EF Core transaction handling, optimistic concurrency, correctness  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Đây là một application ASP.NET Core nội bộ xử lý leave request. Một request có thể được nhiều approver nhìn thấy cùng lúc. Khi người cuối cùng approve, hệ thống chuyển request sang `Approved` và trừ số ngày phép còn lại của nhân viên.

Trong giờ cao điểm, có trường hợp hai approver click gần như đồng thời. Production thỉnh thoảng ghi nhận:

- leave balance bị trừ hai lần;
- cùng request có hai audit rows `Approved`;
- đôi khi request trả HTTP 200 ở cả hai phía;
- rất khó reproduce khi test thủ công;
- không có lỗi database rõ ràng trong log.

SQL Server đang dùng mặc định transaction isolation của application. Team muốn tránh distributed lock nếu có thể.

## Đoạn code cần review

```csharp
public sealed class LeaveApprovalService
{
    private readonly AppDbContext _db;
    private readonly ILogger<LeaveApprovalService> _logger;

    public LeaveApprovalService(
        AppDbContext db,
        ILogger<LeaveApprovalService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<bool> ApproveAsync(
        int leaveRequestId,
        int approverId,
        CancellationToken cancellationToken)
    {
        var request = await _db.LeaveRequests
            .Include(x => x.Employee)
            .FirstOrDefaultAsync(
                x => x.Id == leaveRequestId,
                cancellationToken);

        if (request == null)
            return false;

        if (request.Status == LeaveStatus.Approved)
            return true;

        var canApprove = await _db.LeaveApprovers
            .AnyAsync(
                x => x.LeaveRequestId == leaveRequestId &&
                     x.ApproverId == approverId,
                cancellationToken);

        if (!canApprove)
            throw new UnauthorizedAccessException();

        request.Status = LeaveStatus.Approved;
        request.ApprovedBy = approverId;
        request.ApprovedAt = DateTime.UtcNow;

        request.Employee.RemainingLeaveDays -= request.TotalDays;

        _db.LeaveHistories.Add(new LeaveHistory
        {
            LeaveRequestId = leaveRequestId,
            Action = "Approved",
            ActorId = approverId,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Leave request {LeaveRequestId} approved by {ApproverId}",
            leaveRequestId,
            approverId);

        return true;
    }
}
```

## Kết quả code review tham khảo

### 1. Lost update / double-decrement khi hai approver xử lý đồng thời

- **Problem:** Hai requests có thể cùng đọc `Pending` và cùng trừ `RemainingLeaveDays`.
- **Why it happens:** Read-check-write không có concurrency token hoặc conditional update bảo vệ.
- **Production impact:** Leave balance sai, dữ liệu tài chính/HR không nhất quán.
- **Severity:** Critical
- **Recommended fix:** Dùng optimistic concurrency (`rowversion`/concurrency token) hoặc atomic conditional update để chỉ một request có thể transition từ `Pending` sang `Approved`.

### 2. Status check không bảo đảm idempotency dưới concurrency

- **Problem:** `if (request.Status == Approved)` chỉ hữu ích nếu request thứ hai đọc sau commit của request thứ nhất.
- **Why it happens:** Hai requests có snapshot tại các thời điểm khác nhau trong hai DbContext độc lập.
- **Production impact:** Cả hai request đều chạy business side effects.
- **Severity:** Critical
- **Recommended fix:** Make transition conditional ở database: chỉ update khi `Status = Pending`; nếu affected rows = 0, treat as already processed/conflict.

### 3. Duplicate history records

- **Problem:** Hai requests đều insert `LeaveHistory` với action `Approved`.
- **Why it happens:** Không có unique business constraint hoặc idempotency key.
- **Production impact:** Audit trail sai, khó điều tra incident.
- **Severity:** High
- **Recommended fix:** Gắn history với operation/version hoặc unique constraint phù hợp với business invariant.

### 4. Employee leave balance là aggregate khác nhưng bị update cùng flow mà không có concurrency strategy rõ ràng

- **Problem:** `Employee.RemainingLeaveDays` có thể bị race với leave request khác của cùng employee.
- **Why it happens:** Nhiều leave requests độc lập có thể đồng thời modify cùng employee row.
- **Production impact:** Lost update hoặc balance sai ngay cả khi mỗi leave request chỉ approve một lần.
- **Severity:** High
- **Recommended fix:** Thêm concurrency token cho employee hoặc dùng atomic SQL update có điều kiện `RemainingLeaveDays >= requestedDays`.

### 5. Không validate balance trước khi trừ

- **Problem:** Có thể tạo negative leave balance nếu business rule không cho phép.
- **Why it happens:** Không kiểm tra đủ quota tại thời điểm update.
- **Production impact:** Dữ liệu nghiệp vụ sai.
- **Severity:** High
- **Recommended fix:** Enforce condition atomically ở database hoặc transaction có concurrency control.

### 6. `UnauthorizedAccessException` không phải lúc nào cũng map thành response phù hợp

- **Problem:** Throw generic exception có thể trở thành 500 nếu middleware mapping không đúng.
- **Why it happens:** Authorization failure đang được biểu diễn bằng exception chung.
- **Production impact:** Sai semantics, log noise, client retry không cần thiết.
- **Severity:** Medium
- **Recommended fix:** Dùng authorization layer/policy hoặc domain result rõ ràng và map về 403.

### 7. Query materialize `Employee` entity đầy đủ dù chỉ cần balance/version

- **Problem:** `Include(x => x.Employee)` có thể lấy nhiều dữ liệu hơn cần thiết.
- **Why it happens:** Entity graph được load để update một field.
- **Production impact:** Tăng allocation/query payload, đặc biệt dưới tải.
- **Severity:** Low
- **Recommended fix:** Chỉ giữ nếu cần tracked entity; nếu redesign sang atomic updates thì có thể bỏ `Include`.

### 8. Logging thiếu outcome metadata cho conflict/retry

- **Problem:** Chỉ log success path.
- **Why it happens:** Không có structured events cho concurrent conflict, stale write hoặc already-approved case.
- **Production impact:** Khó phân tích race trong production.
- **Severity:** Medium
- **Recommended fix:** Log operation ID, request ID, approver, previous/current status, concurrency conflict và duration.

## Phiên bản code đề xuất

Một hướng dùng optimistic concurrency với `rowversion` cho `LeaveRequest` và `Employee`:

```csharp
public sealed class LeaveApprovalService
{
    private readonly AppDbContext _db;
    private readonly ILogger<LeaveApprovalService> _logger;

    public LeaveApprovalService(
        AppDbContext db,
        ILogger<LeaveApprovalService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<ApproveLeaveResult> ApproveAsync(
        int leaveRequestId,
        int approverId,
        CancellationToken cancellationToken)
    {
        var canApprove = await _db.LeaveApprovers
            .AsNoTracking()
            .AnyAsync(
                x => x.LeaveRequestId == leaveRequestId &&
                     x.ApproverId == approverId,
                cancellationToken);

        if (!canApprove)
            return ApproveLeaveResult.Forbidden();

        var request = await _db.LeaveRequests
            .Include(x => x.Employee)
            .SingleOrDefaultAsync(
                x => x.Id == leaveRequestId,
                cancellationToken);

        if (request is null)
            return ApproveLeaveResult.NotFound();

        if (request.Status == LeaveStatus.Approved)
            return ApproveLeaveResult.AlreadyApproved();

        if (request.Status != LeaveStatus.Pending)
            return ApproveLeaveResult.InvalidState(request.Status);

        if (request.Employee.RemainingLeaveDays < request.TotalDays)
            return ApproveLeaveResult.InsufficientBalance();

        request.Status = LeaveStatus.Approved;
        request.ApprovedBy = approverId;
        request.ApprovedAt = DateTime.UtcNow;
        request.Employee.RemainingLeaveDays -= request.TotalDays;

        _db.LeaveHistories.Add(new LeaveHistory
        {
            LeaveRequestId = leaveRequestId,
            Action = "Approved",
            ActorId = approverId,
            CreatedAt = DateTime.UtcNow
        });

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException ex)
        {
            _logger.LogWarning(
                ex,
                "Concurrent approval detected for LeaveRequestId={LeaveRequestId}, ApproverId={ApproverId}",
                leaveRequestId,
                approverId);

            return ApproveLeaveResult.Conflict();
        }

        return ApproveLeaveResult.Approved();
    }
}
```

Một hướng khác, thường mạnh hơn cho state transition đơn giản, là dùng atomic conditional SQL/update: chỉ update khi trạng thái vẫn là `Pending`, kiểm tra số rows affected, sau đó thực hiện phần còn lại trong transaction phù hợp. Lựa chọn cụ thể phụ thuộc việc update `Employee`, history và business invariants có cần atomic cùng nhau hay không.

## Trade-offs

- **Optimistic concurrency:** đơn giản, phù hợp khi conflict hiếm; khi conflict nhiều, retries có thể tăng.
- **Conditional update:** rất rõ semantics cho state machine, nhưng code có thể gần database hơn.
- **Higher isolation level:** có thể giúp nhưng tăng lock/blocking; không nên chọn trước khi hiểu workload.
- **Distributed lock:** có thể serialize xử lý nhưng thêm dependency, failure mode và không thay thế database constraints.

```csharp
public sealed class RequestDebugMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestDebugMiddleware> _logger;

    public RequestDebugMiddleware(
        RequestDelegate next,
        ILogger<RequestDebugMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var reader = new StreamReader(
            context.Request.Body,
            leaveOpen: true);

        var body = await reader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        _logger.LogInformation(
            "Request {Method} {Path} Authorization={Authorization} Body={Body}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers.Authorization.ToString(),
            body);

        await _next(context);
    }
}

public sealed class ProfileExportService
{
    private readonly HttpClient _httpClient;

    public ProfileExportService(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task<string> ExportAsync(
        string employeeId,
        string accessToken,
        CancellationToken cancellationToken)
    {
        _httpClient.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        var response = await _httpClient.GetAsync(
            $"/internal/profiles/{employeeId}",
            cancellationToken);

        return await response.Content.ReadAsStringAsync(cancellationToken);
    }
}

## Kết quả code review tham khảo

### 1. Bearer token bị ghi nguyên văn vào logs

- **Problem:** Middleware log toàn bộ `Authorization` header.
- **Why it happens:** Debug logging không redaction secrets.
- **Production impact:** Token leakage có thể dẫn tới account/session compromise nếu log system bị truy cập.
- **Severity:** Critical
- **Recommended fix:** Không log bearer token. Redact hoặc chỉ log authentication metadata không nhạy cảm.

### 2. Mutate `DefaultRequestHeaders.Authorization` trên shared `HttpClient`

- **Problem:** Token là mutable shared state.
- **Why it happens:** Typed/named `HttpClient` thường được reuse; nhiều requests có thể chạy đồng thời.
- **Production impact:** Request của user A có thể bị gửi bằng token user B.
- **Severity:** Critical
- **Recommended fix:** Tạo `HttpRequestMessage` riêng và set `request.Headers.Authorization` per request.

### 3. Không có object-level authorization cho `employeeId`

- **Problem:** Service nhận `employeeId` từ caller nhưng snippet không chứng minh caller có quyền export employee đó.
- **Why it happens:** Authentication bị nhầm với authorization.
- **Production impact:** IDOR/BOLA-style data exposure giữa users.
- **Severity:** Critical
- **Recommended fix:** Authorization theo subject/tenant/role trước downstream call; không tin `employeeId` chỉ vì user đã login.

### 4. Log toàn bộ request body

- **Problem:** Body có thể chứa PII, passwords, tokens hoặc business data.
- **Why it happens:** Generic debug middleware log không phân loại endpoint/content.
- **Production impact:** Privacy breach, compliance risk, log storage explosion.
- **Severity:** High
- **Recommended fix:** Default không log body; nếu thật sự cần, allowlist endpoint/fields, redact, truncate và kiểm soát environment.

### 5. `EnableBuffering` + `ReadToEndAsync` có thể tăng memory/I/O pressure

- **Problem:** Middleware đọc toàn bộ request body trước pipeline.
- **Why it happens:** Không có size limit/truncation.
- **Production impact:** Latency tăng, allocation tăng, có thể bị abuse bởi large payload.
- **Severity:** High
- **Recommended fix:** Không log full body; nếu cần, giới hạn bytes và content types.

### 6. Không gọi `EnsureSuccessStatusCode()` hoặc xử lý status code có chủ đích

- **Problem:** 401/403/500 downstream vẫn bị đọc như data bình thường.
- **Why it happens:** Không validate response semantics.
- **Production impact:** Caller có thể nhận error payload dưới dạng export thành công; khó observability.
- **Severity:** High
- **Recommended fix:** Handle expected status codes, map errors và throw/return domain result phù hợp.

### 7. Không dispose `HttpResponseMessage`

- **Problem:** `response` không được dispose.
- **Why it happens:** Missing `using`.
- **Production impact:** Resource lifecycle kém, có thể giữ response resources lâu hơn cần thiết.
- **Severity:** Medium
- **Recommended fix:** `using var response = await ...` và đọc content trong lifetime đó.

### 8. Không validate/escape `employeeId` khi build URI path

- **Problem:** Path component được interpolate trực tiếp.
- **Why it happens:** Input được tin tưởng.
- **Production impact:** Routing ambiguity hoặc path manipulation tùy format input/downstream.
- **Severity:** Medium
- **Recommended fix:** Validate expected employee ID format và escape path segment.

### 9. Logging không có correlation nhưng chứa quá nhiều raw data

- **Problem:** Log rất nhiều content nhưng lại thiếu metadata giúp debug an toàn.
- **Why it happens:** Debugging dựa vào raw payload thay vì structured telemetry.
- **Production impact:** Log noise, chi phí cao, khó tìm incident.
- **Severity:** Medium
- **Recommended fix:** Log request ID, authenticated subject ID dạng safe identifier, endpoint, downstream status, duration; không log secrets.

### 10. Không phân biệt timeout/cancellation/downstream errors

- **Problem:** Mọi lỗi có thể bubble không có context.
- **Why it happens:** Service không classify dependency failure.
- **Production impact:** Retry sai, khó alert đúng nguyên nhân.
- **Severity:** Medium
- **Recommended fix:** Preserve cancellation, classify timeout/transient/authorization failures, expose metrics riêng.

public sealed class RequestTelemetryMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)

        _logger = logger;

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();

        try
        {
            await _next(context);
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            _logger.LogInformation(
                "HTTP {Method} {Path} StatusCode={StatusCode} TraceId={TraceId} DurationMs={DurationMs}",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                context.TraceIdentifier,
                elapsed.TotalMilliseconds);
        }
    }
}

public sealed class ProfileExportService
{
    private readonly HttpClient _httpClient;
    private readonly IProfileAuthorizationService _authorization;

    public ProfileExportService(
        HttpClient httpClient,
        IProfileAuthorizationService authorization)
    {
        _httpClient = httpClient;
        _authorization = authorization;

    public async Task<string> ExportAsync(
        ClaimsPrincipal user,
        string employeeId,
        string accessToken,
        CancellationToken cancellationToken)
    {
        if (!EmployeeId.TryParse(employeeId, out var parsedEmployeeId))
            throw new ArgumentException("Invalid employee id.", nameof(employeeId));

        var allowed = await _authorization.CanExportAsync(
            user,
            parsedEmployeeId,
            cancellationToken);

        if (!allowed)
            throw new ForbiddenException();

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"/internal/profiles/{Uri.EscapeDataString(parsedEmployeeId.Value)}");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.Forbidden)
            throw new DownstreamAuthorizationException();

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadAsStringAsync(cancellationToken);
    }
}
```

Nếu access token cần được lấy từ token acquisition service thay vì truyền từ controller, có thể dùng delegating handler hoặc token provider phù hợp, nhưng handler cũng phải bảo đảm token được resolve theo từng request/user context và không lưu mutable user token trong singleton/shared state.

## Trade-offs

- **Per-request `HttpRequestMessage`:** an toàn cho user-specific headers, thêm một ít code nhưng rõ ràng.
- **DelegatingHandler:** giảm duplication và centralize auth header, nhưng cần lifetime đúng và tránh capture scoped/user state sai cách.
- **Body logging:** đôi khi hữu ích ở dev/test, nhưng production nên default deny và chỉ allowlist có redaction/limits.
- **Verbose telemetry:** cần cân bằng khả năng debug với privacy, cost và cardinality.

## Cách kiểm thử

1. **Concurrency auth isolation test:** 100 concurrent requests với 100 tokens khác nhau; downstream test server phải thấy đúng token ứng với từng request.
2. **Authorization test:** user A gọi `employeeId` của user B → phải 403 và downstream không được gọi.
3. **Sensitive logging test:** gửi bearer token, password/PII trong body; capture logs và assert không chứa secret.
4. **Failure-path test:** downstream trả 401/403/500/timeout; API phải map outcome đúng và giữ cancellation semantics.
5. **Load test:** large request bodies + high RPS; xác minh middleware không buffer/log body và allocation không tăng bất thường.

## Quan sát trong production

**Logs**

- trace/correlation ID
- route template
- safe subject/user identifier nếu policy cho phép
- downstream status code
- dependency duration
- error classification

Không log:

- bearer/access/refresh token
- raw `Authorization` header
- passwords
- secrets
- full PII body

**Metrics**

- downstream request count
- 401/403/5xx rate
- timeout rate
- dependency P50/P95/P99
- authorization denial count
- request/response size distributions nếu an toàn

**Traces**

- inbound API span
- authorization check span
- downstream HTTP dependency span

**Alerts**

- spike 401/403 từ downstream
- timeout/error-rate threshold
- unusual cross-tenant/authorization denial patterns

## Câu hỏi phỏng vấn mở rộng

1. Khi nào nên dùng `DelegatingHandler` để attach access token thay vì set header trực tiếp trong service?
2. Nếu token acquisition cần refresh tự động, bạn ngăn thundering herd như thế nào?
3. Nếu security team yêu cầu request-body logging cho một endpoint cụ thể, bạn thiết kế redaction, size limit và access control cho logs ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `SaveChangesAsync` có tính transaction cho các thay đổi trong một lần save, nhưng không tự ngăn hai DbContext thực hiện cùng một read-check-write flow đồng thời.
- Business state transition quan trọng nên có concurrency control và database-enforced invariants.
- Idempotency và optimistic concurrency là hai khái niệm liên quan nhưng không đồng nhất.
- Authentication không thay thế object-level authorization.
- Shared `HttpClient` không nên chứa mutable per-user state như bearer token trong `DefaultRequestHeaders`.
- Logging phải được xem là security boundary: secrets/PII lọt vào logs vẫn là data exposure.
- Observability tốt ưu tiên structured metadata, correlation và timings thay vì raw payload.

## Mẫu tư duy cần nhớ

1. **Read-check-write luôn đặt câu hỏi về concurrency.**
2. **Enforce critical invariants càng gần database càng tốt.**
3. **Per-request identity phải là per-request state.**
4. **Không log thứ mà bạn không muốn attacker đọc được.**
5. **Test failure/concurrency paths, không chỉ happy path.**
