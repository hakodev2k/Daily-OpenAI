# Câu 1 — EF Core Tracking và truy vấn dữ liệu trong API có tải cao

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 15 phút
**Kỹ năng được đánh giá:** EF Core, runtime behavior, performance diagnosis

## Bối cảnh

Một ASP.NET Core API quản lý đơn hàng sử dụng EF Core. Sau khi tăng lượng người dùng, một endpoint đọc danh sách đơn hàng bắt đầu chậm dần. Developer đã thêm `AsNoTracking()` vào một số query nhưng chưa hiểu rõ vì sao có lúc cải thiện, có lúc không.

## Câu hỏi chính

Hãy giải thích EF Core thực hiện query và tracking như thế nào bên trong. Vì sao cùng một query nhưng thời gian xử lý có thể khác nhau? Bạn sẽ kiểm chứng giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint này là read-only hay có cập nhật entity sau khi đọc?
- Số lượng record trung bình và lớn nhất là bao nhiêu?
- Query có Include nhiều navigation không?
- Có paging và index phù hợp chưa?

## Gợi ý tư duy

- Gợi ý 1: Xem xét chi phí ngoài SQL execution.
- Gợi ý 2: Phân tích change tracker, materialization và memory.
- Gợi ý 3: Đo bằng execution plan, logging SQL và profiling.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu tracking tạo snapshot và quản lý identity resolution.
- Phân biệt database time và application processing time.

### Điểm cộng

- Biết đánh giá projection DTO.
- Biết kiểm tra N+1 query.

### Nâng cao

- Đề cập compiled query, caching và profiling production.

# Câu 2 — Production Incident: API latency tăng sau khi tích hợp Microsoft Graph

**Loại câu hỏi:** Production incident
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** Troubleshooting, integration design, reliability

## Bối cảnh

Một hệ thống .NET gửi lịch họp tới Microsoft Graph. Sau deployment mới, API tạo event tăng latency từ 500ms lên 8 giây. Một số request timeout nhưng không phải tất cả.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào từ lúc nhận alert đến khi có root cause và biện pháp phòng ngừa?

## Câu hỏi làm rõ nên cân nhắc

- Timeout xảy ra ở API, database hay Graph call?
- Có retry không?
- Có giới hạn concurrency không?
- Có log correlation id không?

## Gợi ý tư duy

- Gợi ý 1: Ổn định hệ thống trước khi tìm nguyên nhân.
- Gợi ý 2: Kiểm tra dependency latency và connection usage.
- Gợi ý 3: Thiết kế timeout, retry, circuit breaker phù hợp.

## Hướng giải quyết tham khảo

- Thu thập metrics, traces, logs.
- Xác định bottleneck.
- Áp dụng mitigation như giảm tải hoặc queue hóa.
- Cải thiện resilience với timeout, retry có kiểm soát, monitoring.

# Câu 3 — AI Engineering: Xây dựng Code Review Agent cho dự án .NET

**Loại câu hỏi:** AI engineering
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** Agent architecture, context engineering, AI safety

## Bối cảnh

Team muốn xây dựng agent hỗ trợ review pull request C#/.NET. Agent có thể đọc code, gọi tool lấy repository context và đưa feedback.

## Câu hỏi chính

Bạn thiết kế agent này như thế nào để feedback hữu ích, giảm hallucination và đảm bảo bảo mật source code?

## Câu hỏi làm rõ nên cân nhắc

- Agent chạy cloud hay self-host?
- Repository có dữ liệu nhạy cảm không?
- Feedback cần tự động merge hay chỉ đề xuất?

## Gợi ý tư duy

- Gợi ý 1: Không để LLM tự quyết định toàn bộ.
- Gợi ý 2: Thiết kế context, tools và validation.
- Gợi ý 3: Có evaluation dataset và human approval.

## Tổng kết hôm nay

## Kiến thức trọng tâm

- Hiểu runtime behavior quan trọng hơn thuộc lòng API.
- Production troubleshooting cần measurement trước optimization.
- AI system cần deterministic validation và permission boundary.

## Mẫu tư duy cần nhớ

- Clarify before designing.
- Measure before optimizing.
- Stabilize before investigating.
- Validate AI output deterministically.
- Treat observability as part of design.
