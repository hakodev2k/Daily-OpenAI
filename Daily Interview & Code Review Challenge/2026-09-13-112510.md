# Code Review Challenge 1 — Scheduled reconciliation chạy chồng nhau, dùng sai `DbContext` lifetime và xử lý trùng khi scale-out

**Chủ đề:** C#/.NET 8, `BackgroundService`, `System.Threading.Timer`, `PeriodicTimer`, dependency injection lifetime, EF Core, concurrency, multi-instance scheduling, graceful shutdown, idempotency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core application chạy trên Azure App Service với 4 instances. Application có background reconciliation job chạy mỗi 5 phút để đồng bộ trạng thái invoice với một external accounting API.

Mỗi lần chạy, job:

- đọc tối đa 500 invoices đang ở trạng thái `PendingSync`;
- gọi accounting API cho từng invoice;
- cập nhật `ExternalStatus`, `LastSyncedAt` và `RetryCount` trong SQL Server;
- business chấp nhận một invoice được kiểm tra lại nhiều lần, nhưng **không chấp nhận** cùng một transition gây side effect lặp ở external system;
- khi deploy/restart, job cần dừng có kiểm soát và không để dữ liệu ở trạng thái nửa chừng.

Production có các triệu chứng:

- sau khi scale từ 1 lên 4 instances, accounting API nhận nhiều request giống nhau cho cùng `InvoiceId`;
- có lúc cùng một instance chạy hai batch chồng lên nhau khi accounting API chậm;
- thỉnh thoảng log xuất hiện lỗi liên quan tới EF Core tracking/concurrent operation;
- một số lần deploy mất rất lâu vì background callback vẫn tiếp tục chạy;
- khi accounting API timeout, `RetryCount` tăng bất thường nhanh;
- team cho rằng `Timer` “mỗi 5 phút chạy một lần” nên không thể overlap;
- một developer đề xuất chỉ thêm `SemaphoreSlim` static để bảo đảm job không chạy trùng.

Job hiện được đăng ký như sau:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

builder.Services.AddHttpClient<IAccountingClient, AccountingClient>();
builder.Services.AddHostedService<InvoiceReconciliationWorker>();
```

## Đoạn code cần review

```csharp
public sealed class InvoiceReconciliationWorker : IHostedService, IDisposable
{
    private readonly AppDbContext _db;
    private readonly IAccountingClient _accountingClient;
    private readonly ILogger<InvoiceReconciliationWorker> _logger;
    private Timer? _timer;

    public InvoiceReconciliationWorker(
        AppDbContext db,
        IAccountingClient accountingClient,
        ILogger<InvoiceReconciliationWorker> logger)
    {
        _db = db;
        _accountingClient = accountingClient;
        _logger = logger;
    }

    public Task StartAsync(CancellationToken cancellationToken)
    {
        _timer = new Timer(
            async _ => await ReconcileAsync(),
            null,
            TimeSpan.Zero,
            TimeSpan.FromMinutes(5));

        return Task.CompletedTask;
    }

    private async Task ReconcileAsync()
    {
        var invoices = await _db.Invoices
            .Where(x => x.Status == InvoiceStatus.PendingSync)
            .OrderBy(x => x.Id)
            .Take(500)
            .ToListAsync();

        await Task.WhenAll(invoices.Select(async invoice =>
        {
            var result = await _accountingClient.SyncAsync(
                invoice.Id,
                invoice.Amount,
                CancellationToken.None);

            invoice.ExternalStatus = result.Status;
            invoice.LastSyncedAt = DateTimeOffset.UtcNow;
            invoice.RetryCount++;
        }));

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Reconciled {Count} invoices",
            invoices.Count);
    }

    public Task StopAsync(CancellationToken cancellationToken)
    {
        _timer?.Change(Timeout.Infinite, Timeout.Infinite);
        return Task.CompletedTask;
    }

    public void Dispose() => _timer?.Dispose();
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, concurrency, DI lifetime và shutdown behavior trong worker.
2. Giải thích vì sao callback có thể overlap trên **một instance** khi một batch chạy quá 5 phút.
3. Giải thích vì sao scale-out thành 4 application instances khiến cùng invoice có thể bị xử lý song song dù mỗi instance chỉ có một timer.
4. Review cách `AppDbContext` và tracked entities đang được dùng với `Task.WhenAll`.
5. Phân tích rủi ro của `CancellationToken.None` đối với deploy, restart và dependency timeout.
6. Đánh giá đề xuất `static SemaphoreSlim` và chỉ rõ phạm vi mà nó bảo vệ được hoặc không bảo vệ được.
7. Đề xuất design bảo đảm job không tạo duplicate business side effect khi chạy nhiều instances.
8. Đề xuất implementation có bounded concurrency, graceful shutdown và idempotency phù hợp.
9. Nêu tests và production telemetry cần có để chứng minh job hoạt động đúng khi load cao, dependency chậm hoặc instance restart.

## Kết quả code review tham khảo

### Critical — Hosted service giữ trực tiếp scoped `DbContext`

**Vấn đề:** `InvoiceReconciliationWorker` được đăng ký bằng `AddHostedService`, còn `AppDbContext` được đăng ký scoped. Hosted service là long-lived service và không có request scope tự động bao quanh mỗi lần chạy.

**Tại sao xảy ra:** Background worker bị dùng như request handler. `DbContext` vốn phù hợp với một unit-of-work hữu hạn; giữ một instance sống lâu làm change tracker tích lũy state, tăng nguy cơ dùng cùng context cho nhiều asynchronous execution và phá lifetime expectation.

**Ảnh hưởng production:** Có thể gặp concurrent operation errors, stale tracked state, memory tăng theo thời gian hoặc behavior khó đoán khi timer callback overlap.

**Cách sửa:** Inject `IServiceScopeFactory` hoặc một scoped application service. Mỗi iteration tạo một async scope mới bằng `CreateAsyncScope()`, resolve `AppDbContext` trong scope đó, thực hiện unit-of-work rồi dispose scope.

### Critical — Multi-instance execution xử lý cùng invoice mà không có durable claim/idempotency

**Vấn đề:** Mỗi application instance chạy timer riêng và cùng query `Status == PendingSync`.

**Tại sao xảy ra:** Không có lease, claim state, unique processing token hay queue ownership. `OrderBy(...).Take(500)` không phải coordination primitive.

**Ảnh hưởng production:** Nhiều instances có thể gọi external API cho cùng invoice gần như đồng thời. Nếu external operation có side effect, duplicate request có thể tạo duplicate business action.

**Cách sửa:** Dùng durable coordination. Ví dụ claim rows atomically bằng trạng thái `Pending → Processing`, `LeaseOwner`, `LeaseUntil`, hoặc phát work vào queue với idempotent consumer. Quan trọng hơn, external call phải mang một stable idempotency key nếu provider hỗ trợ, hoặc application phải có durable side-effect deduplication.

### Critical — External side effect không được bảo vệ khỏi ambiguous timeout/retry

**Vấn đề:** Nếu accounting API đã nhận và xử lý request nhưng network timeout xảy ra trước khi response về, application không biết side effect đã xảy ra hay chưa.

**Tại sao xảy ra:** Distributed call không có atomic transaction chung với SQL Server.

**Ảnh hưởng production:** Retry có thể tạo duplicate external transition dù local DB chưa ghi success.

**Cách sửa:** Thiết kế retry cùng với idempotency. Gửi `InvoiceId` + operation/version như một idempotency key ổn định nếu provider hỗ trợ. Nếu provider không hỗ trợ, cần API reconciliation/query-status hoặc một business protocol cho phép phát hiện operation đã được áp dụng trước khi retry destructive side effect.

### High — `System.Threading.Timer` callback có thể overlap

**Vấn đề:** Callback mới có thể được queue theo chu kỳ trong khi callback trước vẫn đang chạy.

**Tại sao xảy ra:** `System.Threading.Timer` chạy callback trên ThreadPool theo due time/period; nó không biến asynchronous callback thành một serialized worker loop.

**Ảnh hưởng production:** Hai batch cùng process chung rows trên một instance, tăng duplicate calls, race condition và pressure lên SQL/external API.

**Cách sửa:** Với yêu cầu “batch sau chỉ bắt đầu sau batch trước”, dùng `BackgroundService` + loop/`PeriodicTimer` để await toàn bộ iteration trước khi chờ tick tiếp theo. Nếu scheduler semantics yêu cầu cố định theo wall clock, cần explicit overlap policy thay vì ngầm dựa vào timer.

### High — Async lambda của timer không cung cấp lifecycle/error boundary tốt

**Vấn đề:** Callback `async _ => await ReconcileAsync()` được truyền vào callback kiểu `void`; asynchronous exception và completion không được host theo dõi như `ExecuteAsync` của `BackgroundService`.

**Tại sao xảy ra:** Timer callback API không trả `Task` để host await.

**Ảnh hưởng production:** Exception handling, shutdown coordination và health visibility kém hơn; lỗi sau `await` có thể trở thành unhandled exception thay vì được quản lý trong một worker loop rõ ràng.

**Cách sửa:** Dùng `BackgroundService.ExecuteAsync` và bắt exception ở iteration boundary. Cho host sở hữu lifecycle của task dài hạn.

### High — Dùng cùng `DbContext`/tracked entities trong `Task.WhenAll`

**Vấn đề:** Nhiều tasks cùng mutate entities được track bởi cùng một `DbContext`, sau đó save một lần.

**Tại sao xảy ra:** Code song song hóa network call nhưng đồng thời chia sẻ unit-of-work mutable state giữa nhiều asynchronous tasks.

**Ảnh hưởng production:** Khó kiểm soát thread safety, exception semantics và partial success. Chỉ một task fail khiến `Task.WhenAll` throw, trong khi một số external calls có thể đã success nhưng local state chưa save.

**Cách sửa:** Không dùng một tracked `DbContext` như concurrent mutable container. Claim items trước, sau đó xử lý từng item bằng isolated scope/unit-of-work hoặc dùng bounded worker model. Local state transition của từng invoice cần phản ánh outcome riêng, không phụ thuộc một `SaveChangesAsync` cuối batch cho hàng trăm external calls.

### High — `CancellationToken.None` cắt đứt graceful shutdown

**Vấn đề:** External call và EF operations không nhận stopping token.

**Tại sao xảy ra:** Cancellation contract của host không được propagate.

**Ảnh hưởng production:** Deploy/restart có thể phải chờ work không còn hữu ích, giữ connections/sockets lâu hơn, hoặc bị process kill giữa operation.

**Cách sửa:** Truyền `stoppingToken` xuống SQL và HTTP calls. Kết hợp với timeout/budget riêng cho dependency. Cancellation là cooperative; vẫn cần idempotency vì process có thể chết đột ngột.

### High — `StopAsync` không đợi batch đang chạy hoàn tất

**Vấn đề:** `Change(Timeout.Infinite, Timeout.Infinite)` chỉ ngăn tick mới; code trả `Task.CompletedTask` ngay.

**Tại sao xảy ra:** Worker không giữ/await một task đại diện cho current execution.

**Ảnh hưởng production:** Host có thể tiến tới shutdown khi callback vẫn đang mutate state hoặc gọi dependency.

**Cách sửa:** Dùng `BackgroundService`, nơi host await `ExecuteAsync`, propagate cancellation, và bảo đảm loop kết thúc trước khi shutdown budget hết.

### Medium — `static SemaphoreSlim` chỉ bảo vệ trong một process

**Vấn đề:** Static lock không coordinate 4 App Service instances.

**Tại sao xảy ra:** Mỗi process có static memory riêng.

**Ảnh hưởng production:** Có thể ngăn overlap trong một instance nhưng vẫn có 4 independent executions trên 4 instances. Nếu instance recycle, lock state cũng biến mất.

**Cách sửa:** Dùng serialized worker loop cho in-process overlap; dùng durable DB/queue coordination cho cross-instance ownership. Không dùng distributed lock nếu một simple claim state machine đã đủ.

### Medium — Parallelism không bị giới hạn theo dependency capacity

**Vấn đề:** `Task.WhenAll` tạo request cho toàn bộ 500 invoices gần như cùng lúc.

**Tại sao xảy ra:** Batch size bị nhầm thành concurrency limit.

**Ảnh hưởng production:** Burst connection, rate-limit, timeout, ThreadPool continuation pressure và retry storm khi external API degrade.

**Cách sửa:** Dùng bounded concurrency, ví dụ `Parallel.ForEachAsync` với `MaxDegreeOfParallelism` được chọn dựa trên provider limits và latency evidence. Kết hợp backoff/jitter cho transient retry.

### Medium — `RetryCount++` không mô tả đúng retry semantics

**Vấn đề:** Code tăng `RetryCount` kể cả khi operation success và save cùng batch cuối.

**Tại sao xảy ra:** Field đang bị dùng như “attempt count” nhưng tên/logic gợi ý failure retry count.

**Ảnh hưởng production:** Telemetry và operational decisions dựa trên retry count bị sai; threshold DLQ/manual intervention có thể kích hoạt nhầm.

**Cách sửa:** Tách `AttemptCount`, `LastAttemptAt`, `LastError`, `NextAttemptAt` hoặc chỉ tăng `RetryCount` khi một retryable failure thực sự xảy ra.

## Phiên bản đề xuất

Một hướng đơn giản hơn là biến timer callback thành serialized `BackgroundService`, tạo scope theo iteration, claim work bằng database và giới hạn concurrency. Đoạn dưới minh họa application-side flow; phần `ClaimBatchAsync` phải được implement bằng transaction/atomic SQL phù hợp để hai instances không claim cùng row.

```csharp
public sealed class InvoiceReconciliationWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<InvoiceReconciliationWorker> _logger;

    public InvoiceReconciliationWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<InvoiceReconciliationWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));

        await RunIterationAsync(stoppingToken);

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await RunIterationAsync(stoppingToken);
        }
    }

    private async Task RunIterationAsync(CancellationToken stoppingToken)
    {
        try
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<IInvoiceReconciliationProcessor>();

            var claimed = await processor.ClaimBatchAsync(
                maxItems: 100,
                leaseDuration: TimeSpan.FromMinutes(10),
                stoppingToken);

            await Parallel.ForEachAsync(
                claimed,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = 8,
                    CancellationToken = stoppingToken
                },
                async (item, ct) =>
                {
                    await processor.ProcessOneAsync(item, ct);
                });
        }
        catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Invoice reconciliation iteration failed");
        }
    }
}
```

Scoped processor có thể xử lý từng invoice bằng isolated unit-of-work:

```csharp
public sealed class InvoiceReconciliationProcessor
    : IInvoiceReconciliationProcessor
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IAccountingClient _accountingClient;

    public InvoiceReconciliationProcessor(
        IDbContextFactory<AppDbContext> dbFactory,
        IAccountingClient accountingClient)
    {
        _dbFactory = dbFactory;
        _accountingClient = accountingClient;
    }

    public async Task ProcessOneAsync(
        ClaimedInvoice item,
        CancellationToken cancellationToken)
    {
        var idempotencyKey =
            $"invoice-sync:{item.InvoiceId}:{item.SyncVersion}";

        AccountingResult result;

        try
        {
            result = await _accountingClient.SyncAsync(
                item.InvoiceId,
                item.Amount,
                idempotencyKey,
                cancellationToken);
        }
        catch (Exception ex) when (IsRetryable(ex))
        {
            await MarkRetryAsync(item, ex, cancellationToken);
            return;
        }

        await using var db =
            await _dbFactory.CreateDbContextAsync(cancellationToken);

        var invoice = await db.Invoices
            .SingleAsync(x => x.Id == item.InvoiceId, cancellationToken);

        if (invoice.SyncVersion != item.SyncVersion)
            return;

        invoice.ExternalStatus = result.Status;
        invoice.LastSyncedAt = DateTimeOffset.UtcNow;
        invoice.Status = InvoiceStatus.Synced;

        await db.SaveChangesAsync(cancellationToken);
    }
}
```

`SyncVersion` ở đây là scenario design choice để gắn một external operation với một business version cụ thể. Nếu accounting provider có native idempotency key, dùng chính contract đó. Nếu provider không hỗ trợ, cần thiết kế reconciliation protocol khác; không nên giả định HTTP retry có thể biến một non-idempotent side effect thành an toàn.

`ClaimBatchAsync` nên atomically chuyển rows từ `PendingSync` sang `Processing` cùng `LeaseOwner` và `LeaseUntil`, hoặc dùng một durable queue. Lease cho phép item được reclaim nếu instance chết. Claim phải được enforce ở database/queue layer, không bằng in-memory lock.

Nếu business job chỉ cần một scheduler toàn hệ thống và volume rất nhỏ, một dedicated worker instance cũng có thể đơn giản hơn distributed coordination. Tuy nhiên ngay cả khi chỉ có một scheduler, idempotency vẫn cần cho crash/retry ambiguity.

## Giải thích thiết kế sau khi sửa

`BackgroundService` biến execution thành một async loop mà host có thể theo dõi. `PeriodicTimer` giúp iteration tiếp theo không bắt đầu trước khi code đã await iteration hiện tại; nó giải quyết overlap trong một worker loop nhưng không phải distributed lock.

Mỗi iteration tạo scope mới, còn mỗi item có unit-of-work riêng khi cần. Điều này tránh giữ `DbContext` dài hạn và tránh commit toàn bộ batch sau hàng trăm external calls có outcome khác nhau.

Database claim giải quyết work ownership giữa nhiều instances. Idempotency key giải quyết lớp khác: dù cùng operation bị retry vì timeout hoặc crash, external system vẫn có cơ hội nhận diện nó là cùng logical operation.

Bounded concurrency là protection mechanism cho dependency. Con số `8` chỉ là minh họa; phải đo accounting API latency, rate limit, SQL connection usage và desired completion time trước khi chọn.

## Trade-offs

Durable claim/lease thêm schema và state transitions như `Pending`, `Processing`, `RetryScheduled`, `Synced`. Nếu workload rất nhỏ và chỉ chạy một worker cố định, complexity này có thể không đáng giá. Nhưng khi production đã scale nhiều instances và duplicate side effect gây business impact, coordination trở thành correctness requirement.

Per-item `DbContext` tăng số context/connection acquisitions so với một context cho cả batch, nhưng isolation tốt hơn. Có thể xử lý theo chunk nếu profiling chứng minh overhead đáng kể.

`PeriodicTimer` cho semantics “đợi interval giữa các lần bắt đầu sau khi iteration trước đã hoàn thành” theo flow code. Nếu business yêu cầu đúng lịch 00/05/10 phút bất kể duration, cần scheduler semantics riêng và explicit policy cho missed/overlapping runs.

Lease duration quá ngắn có thể làm item bị reclaim khi worker vẫn xử lý; quá dài làm recovery chậm sau crash. Có thể cần heartbeat/renewal cho operation dài.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 4 worker instances cùng thời điểm trên cùng 1.000 invoices; xác minh mỗi invoice chỉ có một active claim và không có duplicate external side effect.
2. **Overlap test:** làm một iteration kéo dài hơn 5 phút theo simulated clock/dependency delay; xác minh cùng worker không bắt đầu iteration thứ hai song song.
3. **Failure-path test:** external API xử lý thành công rồi client timeout; retry phải dùng cùng idempotency key và không tạo side effect thứ hai.
4. **Shutdown test:** trigger host cancellation giữa batch; xác minh worker ngừng nhận work mới, propagate cancellation và leased items có thể recovery sau lease expiry.
5. **Load test:** đo throughput/error rate với các mức concurrency khác nhau; quan sát SQL pool, outbound connections, accounting API p95/p99 và rate-limit response.

## Quan sát trong production

Theo dõi:

- worker instance ID và iteration ID;
- số `Pending`, `Processing`, `RetryScheduled`, `Synced`;
- oldest pending age;
- claim conflicts và expired leases;
- số operation bị deduplicate bởi idempotency key;
- attempts/retries theo invoice;
- accounting API latency, timeout và 429/5xx;
- active processing concurrency;
- SQL connection pool usage và command duration;
- iteration duration p50/p95/p99;
- graceful shutdown duration;
- correlation từ `InvoiceId` → claim → external request → local commit.

Alert khi oldest pending age vượt SLO, expired lease tăng bất thường, duplicate-side-effect signal xuất hiện hoặc external dependency error rate gây retry backlog.

# Code Review Challenge 2 — SQL search API càng về trang sâu càng chậm, cùng query nhưng plan tốt/xấu thay đổi theo filter

**Chủ đề:** SQL Server, query optimization, execution plan, sargability, optional filters, deep pagination, keyset pagination, indexing, cardinality/selectivity, exact vs contains search, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một back-office ASP.NET Core API truy vấn SQL Server để hiển thị lịch sử orders. Bảng `Orders` có khoảng 180 triệu rows, phân bố trên nhiều tenant.

Các yêu cầu UI hiện tại:

- user luôn thuộc đúng một tenant;
- filter tùy chọn theo `Status`, khoảng ngày và free-text `q`;
- sort mặc định `CreatedAt DESC`;
- UI hiển thị “tổng số kết quả”;
- page size thường là 50;
- user có thể nhảy tới page 1, 2, 3… và đôi khi tới page vài nghìn;
- business muốn query thường dưới khoảng vài trăm milliseconds ở tenant trung bình, nhưng chưa có SLO chính thức cho tenant cực lớn.

Production có các triệu chứng:

- page 1 thường nhanh, page 2.000 có thể mất vài giây;
- cùng stored procedure lúc nhanh lúc chậm tùy combination của filters;
- CPU SQL tăng mạnh khi nhiều user search text;
- logical reads tăng rất nhiều ở deep pages;
- một tenant lớn chiếm phần lớn workload;
- team đã thêm vài index riêng lẻ cho `Status`, `CreatedAt`, `CustomerName` nhưng hiệu quả không ổn định;
- một developer đề xuất “thêm Redis trước SQL” mà chưa có execution plan hay query metrics;
- một developer khác đề xuất thêm index cho mọi cột trong `WHERE`.

## Đoạn code cần review

```sql
CREATE OR ALTER PROCEDURE dbo.SearchOrders
    @TenantId   int,
    @Status     varchar(30) = NULL,
    @FromDate   date = NULL,
    @ToDate     date = NULL,
    @Q          nvarchar(200) = NULL,
    @Page       int = 1,
    @PageSize   int = 50,
    @Sort       varchar(20) = 'createdAt'
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @Offset int = (@Page - 1) * @PageSize;

    SELECT
        o.Id,
        o.Status,
        o.CustomerName,
        o.ReferenceNo,
        o.CreatedAt,
        o.Total,
        COUNT(*) OVER() AS TotalCount
    FROM dbo.Orders o
    WHERE o.TenantId = @TenantId
      AND (@Status IS NULL OR o.Status = @Status)
      AND (@FromDate IS NULL OR CONVERT(date, o.CreatedAt) >= @FromDate)
      AND (@ToDate IS NULL OR CONVERT(date, o.CreatedAt) <= @ToDate)
      AND (
            @Q IS NULL
            OR o.CustomerName LIKE N'%' + @Q + N'%'
            OR o.ReferenceNo LIKE '%' + CONVERT(varchar(200), @Q) + '%'
          )
    ORDER BY
        CASE WHEN @Sort = 'createdAt' THEN o.CreatedAt END DESC,
        CASE WHEN @Sort = 'total' THEN o.Total END DESC,
        o.Id DESC
    OFFSET @Offset ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề performance và query-plan stability trong stored procedure.
2. Giải thích vì sao deep `OFFSET` có thể làm logical reads/work tăng dù chỉ trả 50 rows.
3. Review việc áp function `CONVERT(date, o.CreatedAt)` lên column trong predicate.
4. Phân tích free-text search với `LIKE '%...%'` trên bảng rất lớn và index thường có thể/không thể giúp tới đâu.
5. Review optional predicates dạng `@Param IS NULL OR Column = @Param` và tác động của selectivity/plan reuse; không được giả định một root cause duy nhất nếu chưa xem actual plan.
6. Phân tích `COUNT(*) OVER()` trong cùng query khi result set lớn.
7. Đề xuất pagination strategy khác nếu UX không bắt buộc random page jump tuyệt đối.
8. Đề xuất index strategy dựa trên access pattern thay vì “index mọi column”.
9. Nêu cách đo bằng execution plan, Query Store/DMVs, duration, reads và waits trước khi quyết định cache.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### High — Deep `OFFSET/FETCH` buộc database làm nhiều work cho rows bị bỏ qua

**Vấn đề:** Pagination dựa trên page number chuyển trực tiếp thành offset lớn.

**Tại sao xảy ra:** Để trả rows sau offset, engine vẫn phải xác định ordered result và bỏ qua phần trước theo plan đã chọn. Cost thường tăng khi offset tăng, đặc biệt khi sort/filter không được hỗ trợ tốt bởi index.

**Ảnh hưởng production:** Page đầu nhanh nhưng page sâu tăng logical reads, CPU và latency. Nhiều deep-page requests song song có thể làm SQL pressure tăng mạnh.

**Cách sửa:** Nếu UX chủ yếu là next/previous sequential, dùng keyset/seek pagination theo stable sort key, ví dụ `(CreatedAt, Id)`. Nếu business bắt buộc random jump tới page N, `OFFSET` có thể vẫn cần; khi đó phải chấp nhận/đo cost hoặc thay đổi UX/architecture.

### High — Function trên `CreatedAt` làm predicate kém sargable

**Vấn đề:** `CONVERT(date, o.CreatedAt)` được tính trên column trong `WHERE`.

**Tại sao xảy ra:** Predicate không còn là range trực tiếp trên indexed datetime column theo access pattern thông thường.

**Ảnh hưởng production:** Optimizer khó dùng efficient range seek theo `CreatedAt`; reads tăng trên tenant/date range lớn.

**Cách sửa:** Chuyển input thành boundaries và so sánh column trực tiếp, ví dụ `CreatedAt >= @FromUtc` và `CreatedAt < @ToExclusiveUtc`. Cần xác định timezone/business-date semantics trước khi convert boundary.

### High — Contains search bằng leading wildcard không phù hợp với B-tree index thông thường

**Vấn đề:** `CustomerName LIKE '%q%'` và `ReferenceNo LIKE '%q%'` yêu cầu match substring ở bất kỳ vị trí nào.

**Tại sao xảy ra:** Leading wildcard loại bỏ khả năng seek theo prefix trong B-tree index thông thường.

**Ảnh hưởng production:** Với 180 triệu rows, text search có thể scan lượng dữ liệu lớn trong tenant/filter range, tăng CPU và I/O.

**Cách sửa:** Làm rõ search semantics. Nếu `ReferenceNo` có thể prefix/exact search, dùng `ReferenceNo = @Q` hoặc `LIKE @Q + '%'`. Nếu business cần contains/tokenized search trên tên, cân nhắc SQL Server Full-Text Search hoặc search engine đã có trong hệ thống. Không thêm Elasticsearch chỉ vì một query nếu operational cost không được biện minh.

### High — Một query shape phục vụ nhiều optional filters có thể cho plan không phù hợp với parameter distribution

**Vấn đề:** `(@Status IS NULL OR o.Status = @Status)` và nhiều optional branches tạo parameter shapes có selectivity rất khác nhau.

**Tại sao xảy ra:** Một plan phù hợp tenant nhỏ/no-status có thể không phù hợp tenant lớn + status selective, hoặc ngược lại. Behavior cụ thể phụ thuộc SQL Server version, compatibility level, statistics và feature configuration, nên phải xác minh bằng Query Store/actual plans thay vì gán mọi vấn đề cho “parameter sniffing”.

**Ảnh hưởng production:** Cùng procedure có latency biến động mạnh giữa parameter combinations.

**Cách sửa:** Thu thập plans theo parameter shapes. Tùy evidence, cân nhắc branching thành vài query shapes, parameterized dynamic SQL chỉ thêm predicates thực sự có, `OPTION (RECOMPILE)` cho query ít gọi nhưng parameter variance lớn, hoặc các feature optimizer hiện có phù hợp với SQL Server version. Mỗi lựa chọn có cost riêng.

### High — `COUNT(*) OVER()` gắn exact total count vào mọi page request

**Vấn đề:** Query vừa lấy 50 rows vừa yêu cầu exact count của toàn bộ filtered result.

**Tại sao xảy ra:** Window count phải biết cardinality của toàn result set thỏa filter, nên có thể phá mục tiêu “dừng sớm sau đủ 50 rows”.

**Ảnh hưởng production:** Search có hàng triệu matches vẫn làm nhiều work chỉ để UI hiện total exact.

**Cách sửa:** Xác minh UX requirement. Có thể tách count endpoint/query, chỉ count khi user yêu cầu, cache count ngắn nếu chấp nhận stale, dùng “has more” cho infinite/next-page UI, hoặc approximate count nếu business chấp nhận. Không tối ưu query trước khi hỏi total exact có thực sự cần hay không.

### High — Dynamic sort bằng `CASE` làm một index khó phục vụ tất cả sort modes

**Vấn đề:** Một `ORDER BY` cố hỗ trợ cả `CreatedAt` và `Total`.

**Tại sao xảy ra:** Physical order cần thiết thay đổi theo sort mode. Query plan có thể phải sort thay vì đọc trực tiếp theo index order.

**Ảnh hưởng production:** Sort operator, memory grant và tempdb pressure tăng ở result set lớn.

**Cách sửa:** Whitelist sort modes ở application/procedure rồi dùng query shape riêng cho từng sort quan trọng. Không concatenate raw user input vào SQL. Thiết kế index cho các sort/filter thật sự có usage cao.

### Medium — Pagination có thể bị page drift khi dữ liệu thay đổi giữa requests

**Vấn đề:** Page-number pagination dựa trên tập dữ liệu mutable. Insert/update giữa page 1 và page 2 có thể làm row bị lặp hoặc bỏ sót.

**Tại sao xảy ra:** Offset là vị trí tương đối trong ordered set tại thời điểm query, không phải cursor của một snapshot cố định.

**Ảnh hưởng production:** User có thể thấy duplicate/missing orders khi browse live data.

**Cách sửa:** Keyset pagination với stable unique order `(CreatedAt DESC, Id DESC)` giảm drift cho sequential navigation. Nếu UX cần consistent snapshot qua nhiều phút, requirement mạnh hơn và cần snapshot/version semantics riêng.

### Medium — Index riêng lẻ trên từng column không tương đương index phù hợp access pattern

**Vấn đề:** Team thêm index đơn trên `Status`, `CreatedAt`, `CustomerName` mà không dựa trên leading predicates/sort/projection.

**Tại sao xảy ra:** Composite index order quyết định khả năng seek/order; included columns có thể giảm lookup, nhưng index nào tốt phụ thuộc query pattern và write cost.

**Ảnh hưởng production:** Nhiều index làm write/update đắt hơn nhưng query vẫn sort/scan lớn.

**Cách sửa:** Bắt đầu từ dominant access pattern. Ví dụ query tenant-scoped, sort newest-first thường có candidate index bắt đầu bằng `TenantId`, sau đó các equality predicate thường dùng và `CreatedAt`, với selected columns ở `INCLUDE` khi justified. Không có một index duy nhất tối ưu cả status/no-status + multiple sorts + substring search.

### Medium — Input validation cho pagination/sort chưa rõ ràng

**Vấn đề:** `@Page`, `@PageSize`, `@Sort` chưa được giới hạn/whitelist trong procedure.

**Tại sao xảy ra:** Query giả định caller luôn gửi giá trị hợp lệ.

**Ảnh hưởng production:** Page/page size bất thường có thể tạo offset overflow hoặc expensive query; sort value không hợp lệ làm order chỉ còn `Id DESC`, dễ tạo behavior không như contract.

**Cách sửa:** Validate `Page >= 1`, giới hạn page size và whitelist sort values ở API boundary/procedure.

### Medium — Cache được đề xuất trước khi xác định bottleneck

**Vấn đề:** Team muốn thêm Redis dù query shape chưa được đo.

**Tại sao xảy ra:** Cache bị dùng như default performance fix.

**Ảnh hưởng production:** Thêm invalidation/staleness/operational complexity nhưng SQL vẫn yếu; query combinations có high cardinality nên cache hit ratio có thể thấp.

**Cách sửa:** Đo duration, logical reads, CPU, actual execution plan, Query Store, waits và frequency. Chỉ cache khi reuse/freshness pattern chứng minh giá trị.

## Phiên bản đề xuất

Nếu UX chấp nhận next/previous cursor và sort mặc định theo `CreatedAt DESC`, một baseline đơn giản hơn là keyset pagination. Ví dụ:

```sql
CREATE OR ALTER PROCEDURE dbo.SearchOrdersByCursor
    @TenantId       int,
    @Status         varchar(30) = NULL,
    @FromUtc        datetime2(3) = NULL,
    @ToExclusiveUtc datetime2(3) = NULL,
    @AfterCreatedAt datetime2(3) = NULL,
    @AfterId        bigint = NULL,
    @ReferencePrefix varchar(50) = NULL,
    @PageSize       int = 50
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 200
        THROW 50001, 'Invalid page size', 1;

    SELECT TOP (@PageSize + 1)
        o.Id,
        o.Status,
        o.CustomerName,
        o.ReferenceNo,
        o.CreatedAt,
        o.Total
    FROM dbo.Orders o
    WHERE o.TenantId = @TenantId
      AND (@Status IS NULL OR o.Status = @Status)
      AND (@FromUtc IS NULL OR o.CreatedAt >= @FromUtc)
      AND (@ToExclusiveUtc IS NULL OR o.CreatedAt < @ToExclusiveUtc)
      AND (
            @ReferencePrefix IS NULL
            OR o.ReferenceNo LIKE @ReferencePrefix + '%'
          )
      AND (
            @AfterCreatedAt IS NULL
            OR o.CreatedAt < @AfterCreatedAt
            OR (o.CreatedAt = @AfterCreatedAt AND o.Id < @AfterId)
          )
    ORDER BY o.CreatedAt DESC, o.Id DESC;
END
```

Application trả 50 rows và dùng row thứ 51 để xác định `hasNextPage`, không cần exact count trên mỗi request. Cursor có thể encode `(CreatedAt, Id)` và phải được validate/tamper-protected nếu exposed externally.

Candidate index cho access pattern **phải được validate bằng actual plan**, ví dụ một baseline:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt_Id
ON dbo.Orders
(
    TenantId,
    CreatedAt DESC,
    Id DESC
)
INCLUDE
(
    Status,
    CustomerName,
    ReferenceNo,
    Total
);
```

Nếu `Status` filter xuất hiện rất thường xuyên và selective, một index khác dạng `(TenantId, Status, CreatedAt DESC, Id DESC)` có thể có lợi. Không nên tạo cả hai chỉ vì lý thuyết; phải dựa trên workload/write cost.

Đoạn procedure trên vẫn có optional `Status`, nên với parameter distribution cực lệch có thể vẫn cần query branching/dynamic SQL/optimizer feature phù hợp. Đây là điểm cần đo bằng Query Store và actual plans, không nên coi baseline code là “plan tối ưu universal”.

Với free-text `CustomerName contains`, nên tách path rõ ràng. Nếu business thật sự cần tokenized/contains search ở scale lớn, dùng Full-Text Search hoặc một search platform phù hợp. Nếu user chủ yếu tìm exact/prefix `ReferenceNo`, đừng trả cost full-text cho mọi request.

Nếu business bắt buộc random jump tới page 2.000 và exact total count, keyset không đáp ứng hoàn toàn UX đó. Khi ấy cần giữ offset/count cho use case này, nhưng nên đo và có SLO riêng thay vì giả định cùng latency với page 1.

## Giải thích thiết kế sau khi sửa

Keyset pagination biến “vị trí trang” thành boundary theo sort key thay vì số lượng rows phải skip. Với index cùng order, engine có cơ hội seek gần vị trí cursor rồi đọc tiếp page size nhỏ.

`CreatedAt` được so sánh trực tiếp với datetime boundaries, tránh function trên column. `Id` là tie-breaker giúp order deterministic khi nhiều orders có cùng timestamp.

`TOP (@PageSize + 1)` trả lời câu hỏi “còn dữ liệu không?” rẻ hơn exact total count cho UI chỉ cần next page. Đây là requirement simplification, không phải mẹo SQL.

Index tập trung tenant + sort vì mọi query bắt buộc tenant-scoped. `INCLUDE` có thể giảm lookup cho projection, nhưng làm index lớn hơn và tăng write/storage cost.

## Trade-offs

Keyset pagination không hỗ trợ random page number tự nhiên. Nếu Product yêu cầu nhập “page 500”, offset hoặc một mapping strategy khác vẫn cần.

Cursor phải encode sort/filter context. Nếu user đổi filter/sort, cursor cũ không còn hợp lệ.

Tách query shapes giúp optimizer có lựa chọn tốt hơn nhưng tăng code/procedure complexity. `OPTION (RECOMPILE)` có thể giảm vấn đề plan reuse cho workload phù hợp nhưng tăng compile CPU. Parameterized dynamic SQL linh hoạt hơn nhưng phải whitelist identifiers/sort và parameterize values để tránh SQL injection.

Full-Text Search/search engine thêm operational/indexing complexity. Nếu free-text usage thấp, product có thể chấp nhận prefix search thay vì thêm một subsystem.

Covering index tăng read speed nhưng làm writes và storage đắt hơn. Với 180 triệu rows, index size phải được capacity-plan và đo fragmentation/maintenance.

## Cách kiểm thử

1. **Database performance test:** chạy representative tenant nhỏ/lớn, status có/không có, date range hẹp/rộng; capture actual plans, logical reads, CPU và duration.
2. **Deep-pagination comparison:** so sánh page sâu bằng `OFFSET` với keyset cursor ở cùng dataset; đo reads và latency, không chỉ elapsed time một lần.
3. **Plan-variance test:** execute các parameter shapes có selectivity rất khác nhau; dùng Query Store để xem plan/runtime distribution trước khi chọn mitigation.
4. **Correctness test:** chèn orders mới giữa khi client đọc page 1 và page 2; xác minh keyset không tạo duplicate theo cursor contract.
5. **Search test:** benchmark exact/prefix `ReferenceNo` và contains `CustomerName`; xác minh lựa chọn Full-Text/search subsystem chỉ khi requirement và evidence hỗ trợ.

## Quan sát trong production

Theo dõi:

- query duration p50/p95/p99 theo endpoint;
- logical reads và CPU theo query hash/procedure;
- Query Store plan/runtime changes;
- actual/estimated row mismatch ở sampled investigation;
- sort spills/memory grant warnings khi có;
- tempdb pressure;
- blocking/waits;
- page depth distribution;
- filter/sort combination frequency;

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `BackgroundService`/hosted service là long-lived; scoped dependencies như `DbContext` cần explicit scope/unit-of-work thay vì giữ suốt lifetime worker.
- In-process serialization và cross-instance coordination là hai vấn đề khác nhau. `PeriodicTimer` hoặc `SemaphoreSlim` không tự giải quyết duplicate work giữa nhiều application instances.
- Retry external side effect phải được thiết kế cùng idempotency vì timeout có thể để lại outcome mơ hồ.
- Bounded concurrency, cancellation và graceful shutdown là một phần của correctness của background processing, không chỉ là performance tuning.
- Với SQL, cần tách cost của filtering, sorting, pagination, counting và text search; “thêm index” hoặc “thêm Redis” không thay thế execution-plan investigation.
- Deep `OFFSET`, function trên indexed column, contains search và exact count có thể cộng dồn thành một query rất đắt dù page size chỉ 50.
- Keyset pagination là một lựa chọn tốt khi UX cho phép sequential navigation và stable cursor semantics, nhưng không phải drop-in replacement cho random page jump.

## Mẫu tư duy cần nhớ

- Tách in-process concurrency khỏi distributed coordination.
- Thiết kế retry cùng idempotency và ambiguous failure.
- Scope resource theo unit-of-work thay vì lifetime của process.
- Measure execution plan/reads trước khi thêm cache hoặc index.
- Hỏi lại UX requirement trước khi trả cost của exact count và deep page navigation.
