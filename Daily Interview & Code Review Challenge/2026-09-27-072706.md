# Code Review Challenge 1 — API download hóa đơn tin vào tenant từ request

**Chủ đề:** ASP.NET Core, authorization, EF Core, multi-tenant security, Azure Blob Storage, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Một enterprise portal chạy ASP.NET Core .NET 8 trên Azure App Service. Người dùng đăng nhập bằng Microsoft Entra ID và có thể tải PDF hóa đơn của công ty mình. Metadata hóa đơn nằm trong SQL Server; file PDF nằm trong Azure Blob Storage.

API nhận khoảng 300 requests/phút ở giờ cao điểm. Sau một đợt pentest, team nghi ngờ một user có thể thay đổi query string để đọc metadata hoặc file của tenant khác. Production cũng có các log chứa URL Blob đầy đủ. Team muốn vá nhanh nhưng không được phá luồng download hiện tại.

Chưa rõ claim nào thực sự đại diện cho tenant, tenant membership được quản lý ở token hay database, Blob container là private hay public, và URL do storage client trả về là SAS hay URL nội bộ.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/invoices")]
[Authorize]
public sealed class InvoicesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly BlobServiceClient _blob;
    private readonly ILogger<InvoicesController> _logger;

    public InvoicesController(
        AppDbContext db,
        BlobServiceClient blob,
        ILogger<InvoicesController> logger)
    {
        _db = db;
        _blob = blob;
        _logger = logger;
    }

    [HttpGet("{invoiceId:guid}/download")]
    public async Task<IActionResult> Download(
        Guid invoiceId,
        [FromQuery] Guid tenantId)
    {
        var invoice = await _db.Invoices
            .FirstOrDefaultAsync(x =>
                x.Id == invoiceId &&
                x.TenantId == tenantId);

        if (invoice is null)
            return NotFound();

        var container = _blob.GetBlobContainerClient("invoices");
        var client = container.GetBlobClient(invoice.BlobPath);

        var properties = await client.GetPropertiesAsync();

        _logger.LogInformation(
            "User {User} downloads invoice {InvoiceId} from {BlobUri}",
            User.Identity?.Name,
            invoice.Id,
            client.Uri);

        var stream = await client.OpenReadAsync();

        Response.Headers["Content-Disposition"] =
            $"attachment; filename={invoice.FileName}";

        return File(
            stream,
            properties.Value.ContentType ?? "application/pdf");
    }
}
```

## Câu hỏi gợi mở

## Gợi ý

### Gợi ý 1

Rủi ro chính là object-level authorization: identity đã được xác thực nhưng resource ownership vẫn phải được kiểm tra từ trusted context.

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Broken object-level authorization qua `tenantId` do client kiểm soát

**Vấn đề:** Endpoint chỉ yêu cầu `[Authorize]` rồi dùng `tenantId` từ query string để lọc invoice.  
**Tại sao xảy ra:** Authentication chỉ xác nhận identity. Code chưa chứng minh identity hiện tại thuộc tenant được yêu cầu hoặc có quyền đọc invoice.  
**Ảnh hưởng production:** Nếu attacker biết/đoán được `invoiceId` và tenant ID, họ có thể đọc tài liệu tenant khác. Đây là data-boundary violation.  
**Cách sửa:** Derive tenant/resource scope từ trusted authorization context và kiểm tra policy/resource authorization. Nếu membership nằm trong database, lookup membership bằng stable subject/object identifier từ token; không tin tenant ID từ browser như bằng chứng quyền truy cập.

### High — Blob access không có defense-in-depth rõ ràng

**Vấn đề:** API lấy Blob trực tiếp sau database lookup; snippet không thể hiện container access policy hay service identity.  
**Tại sao xảy ra:** Authorization ở application không thay thế storage authorization. Nếu container hoặc credential quá rộng, một lỗi application khác có thể mở rộng blast radius.  
**Ảnh hưởng production:** Data exposure lớn hơn khi application credential hoặc URL bị lộ.  
**Cách sửa:** Giữ container private, dùng Managed Identity/RBAC với least privilege khi phù hợp, và không phát hành SAS rộng/không cần thiết. Nếu chọn direct-download bằng SAS, scope SAS vào đúng blob, quyền read và lifetime ngắn theo requirement.

### High — Không propagate request cancellation

**Vấn đề:** EF Core và Blob operations không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Các overload không truyền `CancellationToken`.  
**Ảnh hưởng production:** Client đã rời đi nhưng SQL/Blob I/O và streaming setup có thể tiếp tục tiêu thụ resource.  
**Cách sửa:** Nhận `CancellationToken` ở action và truyền xuyên `SingleOrDefaultAsync`, Blob calls và stream operation hỗ trợ cancellation.

### Medium — `Content-Disposition` được xây từ filename không được chuẩn hóa

**Vấn đề:** Header được nối chuỗi trực tiếp từ dữ liệu lưu trữ.  
**Tại sao xảy ra:** Filename là data, không nên được coi là header syntax đáng tin cậy.  
**Ảnh hưởng production:** Header malformed hoặc injection risk nếu dữ liệu filename không được kiểm soát đúng.  
**Cách sửa:** Dùng API/framework overload hỗ trợ download filename hoặc `ContentDispositionHeaderValue`; validate/sanitize filename tại write boundary.

### Medium — Log có thể làm lộ storage topology hoặc query component nhạy cảm

**Vấn đề:** Log toàn bộ `client.Uri`.  
**Tại sao xảy ra:** URI được coi như metadata vô hại. Trong các design khác, URI có thể chứa SAS query; ngay cả khi hiện tại không có SAS, path/storage account vẫn là thông tin không cần thiết.  
**Ảnh hưởng production:** Secret/data leakage qua log và tăng blast radius cho người có quyền đọc log.  
**Cách sửa:** Log logical identifiers như InvoiceId/TenantId đã authorize, outcome, duration; tuyệt đối không log SAS token.

### Medium — Read query dùng tracking không cần thiết

**Vấn đề:** Invoice chỉ được đọc để download nhưng query mặc định tracking.  
**Tại sao xảy ra:** `DbContext` tracking được bật mặc định cho entity query.  
**Ảnh hưởng production:** Overhead nhỏ nhưng không cần thiết trên hot read path.  
**Cách sửa:** Dùng `AsNoTracking()` và projection chỉ lấy fields cần thiết.

### Medium — Phân biệt 403/404 và information disclosure chưa được quyết định có chủ đích

**Vấn đề:** Snippet không tách “resource không tồn tại” khỏi “resource tồn tại nhưng user không có quyền”.  
**Tại sao xảy ra:** Authorization được trộn vào query dựa trên untrusted tenant.  
**Ảnh hưởng production:** Có thể leak existence hoặc làm telemetry authorization mơ hồ.  
**Cách sửa:** Chọn semantics 404/403 theo threat model/API contract; internal telemetry vẫn phải phân biệt denied/not-found mà không leak chi tiết cho client.

### Low — Không giới hạn rõ content type/expected object metadata

**Vấn đề:** API tin `ContentType` lưu ở Blob.  
**Tại sao xảy ra:** Storage metadata được chuyển thẳng ra response.  
**Ảnh hưởng production:** Nếu upload pipeline bị compromise hoặc cho phép type tùy ý, browser behavior có thể khác kỳ vọng.  
**Cách sửa:** Validate upload path/type và, nếu domain chỉ cho PDF, enforce invariant tại ingest; cân nhắc `X-Content-Type-Options: nosniff` ở security headers policy.

## Phiên bản đề xuất

Ví dụ dưới đây giả định tenant membership được resolve từ một trusted service dựa trên identity hiện tại; implementation thực tế phải khớp mô hình authorization của hệ thống.

```csharp
[ApiController]
[Route("api/invoices")]
[Authorize]
public sealed class InvoicesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly BlobServiceClient _blob;
    private readonly ICurrentTenantAccessor _tenant;
    private readonly ILogger<InvoicesController> _logger;

    public InvoicesController(
        AppDbContext db,
        BlobServiceClient blob,
        ICurrentTenantAccessor tenant,
        ILogger<InvoicesController> logger)
        => (_db, _blob, _tenant, _logger) = (db, blob, tenant, logger);

    [HttpGet("{invoiceId:guid}/download")]
    public async Task<IActionResult> Download(
        Guid invoiceId,
        CancellationToken ct)
    {
        var tenantId = await _tenant.GetAuthorizedTenantIdAsync(User, ct);

        var invoice = await _db.Invoices
            .AsNoTracking()
            .Where(x => x.Id == invoiceId && x.TenantId == tenantId)
            .Select(x => new
            {
                x.Id,
                x.BlobPath,
                x.FileName
            })
            .SingleOrDefaultAsync(ct);

        if (invoice is null)
        {
            _logger.LogWarning(
                "Invoice download denied or not found. InvoiceId={InvoiceId}",
                invoiceId);
            return NotFound();
        }

        var blob = _blob
            .GetBlobContainerClient("invoices")
            .GetBlobClient(invoice.BlobPath);

        var download = await blob.DownloadStreamingAsync(
            cancellationToken: ct);

        _logger.LogInformation(
            "Invoice download authorized. InvoiceId={InvoiceId} TenantId={TenantId}",
            invoice.Id,
            tenantId);

        return File(
            download.Value.Content,
            "application/pdf",
            fileDownloadName: Path.GetFileName(invoice.FileName),
            enableRangeProcessing: true);
    }
}
```

`ICurrentTenantAccessor` ở đây không phải một abstraction bắt buộc. Điểm quan trọng là authorization scope phải đến từ trusted identity/membership data. Nếu một user có thể chuyển tenant hợp lệ, API có thể nhận tenant selection nhưng vẫn phải validate selection đó với membership/policy trước khi query resource.

## Giải thích thiết kế sau khi sửa

Resource lookup bị ràng buộc bởi tenant đã authorize, nên object-level authorization nằm ngay trên data access boundary. Read path dùng projection và no-tracking. Cancellation đi xuyên SQL và Blob I/O. Storage URI không xuất hiện trong log. File response dùng framework API thay vì tự ghép header.

Nếu file lớn và backend proxy trở thành bottleneck, có thể cân nhắc short-lived read-only SAS hoặc front-door/CDN design, nhưng chỉ sau khi authorization hoàn tất. Direct Blob download giảm bandwidth qua API nhưng tăng yêu cầu về SAS lifetime, revocation assumptions, logging và browser exposure.

## Trade-offs

Resource authorization qua database có thể thêm lookup; có thể cache membership nếu threat model và invalidation semantics cho phép. Proxy stream qua API đơn giản hóa policy và audit nhưng tốn App Service bandwidth/connections. Direct SAS giảm tải backend nhưng capability URL phải được bảo vệ như credential tạm thời. Trả 404 cho cả denied/not-found giảm enumeration signal nhưng làm client/debugging ít chi tiết hơn.

## Cách kiểm thử

1. **Integration/security test:** user tenant A thử tải invoice tenant B bằng invoice ID hợp lệ; phải bị từ chối mà không gọi Blob.
2. **Authorization test:** user có membership nhiều tenant chỉ truy cập được tenant đang được policy cho phép.
3. **Failure-path test:** Blob trả 404/timeout; API không leak URI/credential và telemetry ghi đúng dependency failure.
4. **Cancellation test:** abort request khi đang download file lớn; xác minh cancellation được quan sát và resource được giải phóng.
5. **Load test:** nhiều concurrent downloads; đo App Service connections, memory, Blob latency và p95/p99 trước khi quyết định proxy hay direct download.

## Quan sát trong production

Theo dõi structured logs với subject hash/stable user ID phù hợp policy, TenantId, InvoiceId, authorization outcome và correlation ID. Trong Application Insights, theo dõi request duration, Blob/SQL dependency duration, cancellation và failure rate. Alert khi authorization-denied rate tăng bất thường hoặc một identity truy cập nhiều invoice/tenant bất thường. Audit Azure Storage access và Managed Identity/RBAC; không đưa SAS token vào logs.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một user hợp lệ có quyền chuyển giữa 20 tenant, bạn thiết kế tenant selection và authorization cache thế nào để revoke quyền vẫn có hiệu lực đủ nhanh?
2. Nếu file 2 GB làm App Service proxy download trở thành bottleneck, bạn chuyển sang SAS/direct download như thế nào mà không làm yếu authorization?
3. Nếu security team yêu cầu audit “ai đã thực sự tải xong file”, việc chỉ log lúc API cấp stream/SAS có đủ không?

# Code Review Challenge 2 — Vue search hiển thị kết quả cũ sau request mới

**Chủ đề:** Vue.js, TypeScript, browser networking, async race condition, request cancellation, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7

## Bối cảnh

Một Vue 3 portal có màn hình tìm sản phẩm. Khi user gõ từ khóa hoặc đổi category, UI tự search. API thường trả trong 200–500 ms nhưng đôi lúc một query cũ mất 2–3 giây do cache miss. Production ghi nhận kết quả trên màn hình thỉnh thoảng không khớp keyword đang hiển thị. Khi user gõ nhanh, browser tạo nhiều request đồng thời và backend thấy traffic burst.

Team muốn giữ trải nghiệm responsive, không được yêu cầu user bấm nút Search. Chưa rõ search API có rate limit, response có cache semantics gì, và requirement khi query rỗng là hiển thị popular products hay không có kết quả.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from "vue";

type Product = {
  id: string;
  name: string;
  price: number;
};

const query = ref("");
const category = ref("all");
const products = ref<Product[]>([]);
const loading = ref(false);
const error = ref("");

async function search() {
  loading.value = true;
  error.value = "";

  try {
    const url =
      "/api/products/search?q=" +
      query.value +
      "&category=" +
      category.value;

    const response = await fetch(url);

    if (!response.ok) {
      throw new Error(await response.text());
    }

    products.value = await response.json();
  } catch (e) {
    error.value = String(e);
    products.value = [];
  } finally {
    loading.value = false;
  }
}

watch(query, search);
watch(category, search);

search();
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <select v-model="category">
      <option value="all">All</option>
      <option value="books">Books</option>
      <option value="software">Software</option>
    </select>

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="product in products" :key="product.id">
        {{ product.name }} — {{ product.price }}
      </li>
    </ul>
  </section>
</template>
```

### Gợi ý 1

## Kết quả code review tham khảo

### High — Stale response có thể overwrite kết quả mới

**Vấn đề:** Mọi invocation đều ghi vào cùng `products` khi response hoàn tất.  
**Tại sao xảy ra:** Network completion order không được đảm bảo. Request cho `q=a` có thể hoàn thành sau `q=abc` và overwrite state.  
**Ảnh hưởng production:** UI hiển thị dữ liệu không khớp filter hiện tại; user có thể ra quyết định dựa trên kết quả cũ.  
**Cách sửa:** Abort request trước bằng `AbortController` và/hoặc dùng monotonically increasing request ID để chỉ current request được commit state.

### High — Không debounce input tạo request burst

**Vấn đề:** Mỗi thay đổi của `query` gọi API ngay.  
**Tại sao xảy ra:** `watch` phản ứng theo từng update model.  
**Ảnh hưởng production:** Nhiều request vô ích, backend/cache/database load tăng và race dễ xuất hiện hơn.  
**Cách sửa:** Debounce search text theo UX/SLA phù hợp. Category change có thể trigger ngay; không cần ép mọi input dùng cùng delay.

### Medium — `loading` có race

**Vấn đề:** Request cũ có thể chạy `finally` và đặt `loading=false` trong khi request mới vẫn đang chạy.  
**Tại sao xảy ra:** Một boolean không biểu diễn ownership của concurrent request.  
**Ảnh hưởng production:** Loading indicator biến mất sớm.  
**Cách sửa:** Chỉ current request được cập nhật loading, hoặc dùng request generation/count có semantics rõ.

### Medium — Query parameters không được encode đúng

**Vấn đề:** URL được nối trực tiếp từ input.  
**Tại sao xảy ra:** Ký tự như `&`, `+`, `#` có semantics trong URL.  
**Ảnh hưởng production:** Search sai hoặc request bị biến dạng.  
**Cách sửa:** Dùng `URLSearchParams`.

### Medium — Abort bị hiển thị như lỗi

**Vấn đề:** Nếu thêm cancellation nhưng vẫn catch mọi exception như nhau, `AbortError` sẽ làm UI báo lỗi và xóa kết quả.  
**Tại sao xảy ra:** Expected control flow bị trộn với dependency failure.  
**Ảnh hưởng production:** Flicker/error giả khi user gõ nhanh.  
**Cách sửa:** Nhận diện abort và không commit error state cho request obsolete.

### Medium — Error body từ server được đưa trực tiếp vào UI state

**Vấn đề:** `response.text()` có thể chứa chi tiết không phù hợp cho end user. Vue text interpolation mặc định escape HTML, nên đây không tự động là XSS trong template hiện tại, nhưng vẫn có risk information disclosure/poor UX.  
**Tại sao xảy ra:** API diagnostic text được coi là user-facing message.  
**Ảnh hưởng production:** Lộ implementation detail/correlation data hoặc message khó hiểu.  
**Cách sửa:** Map status/problem response sang message an toàn; giữ diagnostic detail trong telemetry phù hợp.

### Low — Initial search semantics chưa rõ

**Vấn đề:** `search()` chạy ngay với query rỗng và category `all`.  
**Tại sao xảy ra:** Code tự chọn behavior thay vì thể hiện requirement.  
**Ảnh hưởng production:** Có thể tạo query rộng/tốn kém hoặc UX không đúng mong muốn.  
**Cách sửa:** Xác minh requirement; nếu empty search hợp lệ, API phải có bounded result/pagination. Nếu không, skip request.

## Phiên bản đề xuất

Ví dụ này debounce text input, trigger category ngay, abort request obsolete và dùng generation để tránh stale commit ngay cả khi abort xảy ra quá muộn.

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from "vue";

type Product = {
  id: string;
  name: string;
  price: number;
};

const query = ref("");
const category = ref("all");
const products = ref<Product[]>([]);
const loading = ref(false);
const error = ref("");

let controller: AbortController | null = null;
let generation = 0;
let debounceTimer: ReturnType<typeof setTimeout> | null = null;

async function executeSearch() {
  const currentGeneration = ++generation;

  controller?.abort();
  controller = new AbortController();

  const params = new URLSearchParams({
    q: query.value.trim(),
    category: category.value
  });

  loading.value = true;
  error.value = "";

  try {
    const response = await fetch(
      `/api/products/search?${params.toString()}`,
      { signal: controller.signal }
    );

    if (!response.ok) {
      throw new Error(`Search failed with HTTP ${response.status}`);
    }

    const result = (await response.json()) as Product[];

    if (currentGeneration === generation) {
      products.value = result;
    }
  } catch (e) {
    if (e instanceof DOMException && e.name === "AbortError") {
      return;
    }

    if (currentGeneration === generation) {
      error.value = "Không thể tải kết quả tìm kiếm.";
    }
  } finally {
    if (currentGeneration === generation) {
      loading.value = false;
    }
  }
}

function scheduleTextSearch() {
  if (debounceTimer !== null) {
    clearTimeout(debounceTimer);
  }

  debounceTimer = setTimeout(() => {
    void executeSearch();
  }, 300);
}

watch(query, scheduleTextSearch);

watch(category, () => {
  if (debounceTimer !== null) {
    clearTimeout(debounceTimer);
    debounceTimer = null;
  }
  void executeSearch();
});

onBeforeUnmount(() => {
  if (debounceTimer !== null) clearTimeout(debounceTimer);
  controller?.abort();
});

void executeSearch();
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <select v-model="category">
      <option value="all">All</option>
      <option value="books">Books</option>
      <option value="software">Software</option>
    </select>

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="product in products" :key="product.id">
        {{ product.name }} — {{ product.price }}
      </li>
    </ul>
  </section>
</template>
```

Trong production code, debounce utility/composable có thể phù hợp hơn implementation thủ công. Con số 300 ms chỉ là scenario choice, không phải universal optimum; cần tune bằng UX và telemetry.

## Giải thích thiết kế sau khi sửa

Debounce giảm request khi user đang nhập. AbortController giảm work obsolete ở browser/network path khi cancellation được quan sát. Generation là correctness guard: chỉ invocation mới nhất được quyền commit `products`, `error` và `loading`. Hai cơ chế bổ sung nhau; cancellation không nên là điều kiện duy nhất để đảm bảo state correctness.

`URLSearchParams` đảm bảo encoding đúng. Expected abort không được coi là application error. Khi component unmount, pending timer/request được cleanup.

## Trade-offs

Debounce tăng một lượng latency có chủ đích trước khi search; delay quá dài làm UX chậm, quá ngắn ít giảm traffic. Abort client không đảm bảo backend/database lập tức dừng nếu server không propagate cancellation, vì vậy backend vẫn cần guardrails. Request generation thêm state logic nhưng bảo vệ correctness ngay cả khi cancellation race. Nếu search result có thể cache, cần thiết kế cache key theo normalized query/category và freshness requirement thay vì chỉ dựa vào frontend.

## Cách kiểm thử

1. **Unit/component test:** fake timers xác minh gõ 5 ký tự nhanh chỉ tạo số request theo debounce policy.
2. **Race test:** request A chậm, request B nhanh; sau khi cả hai settle, UI phải giữ kết quả B.
3. **Cancellation test:** đổi query khi request đang pending; abort không được hiển thị như error.
4. **E2E Playwright:** nhập nhanh, đổi category và điều hướng khỏi page; xác minh UI cuối cùng khớp filter và không có stale state.
5. **Load test end-to-end:** so sánh request rate, API p95/p99 và backend dependency load trước/sau debounce/cancellation.

## Quan sát trong production

Frontend telemetry nên ghi search duration, HTTP status, aborted/failed/succeeded outcome và một normalized query-shape indicator không chứa raw sensitive search text nếu policy không cho phép. Backend Application Insights theo dõi request rate, cancellations, dependency duration và p95/p99. Browser/network observation giúp xác nhận request obsolete thực sự bị abort. Nếu backend vẫn tốn nhiều SQL sau client abort, trace cancellation propagation ở server thay vì tăng debounce vô hạn.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend không thể cancel SQL query sau khi browser abort, frontend fix này giải quyết được phần nào và phần nào vẫn còn?
2. Nếu Product yêu cầu kết quả xuất hiện gần như tức thì sau mỗi keystroke, bạn cân bằng debounce, caching và backend capacity thế nào?
3. Nếu chuyển sang một data-fetching library có request deduplication/cache, bạn vẫn cần hiểu những correctness invariant nào thay vì mặc định library đã giải quyết hết?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Authorization phải được kiểm tra trên resource và trusted identity context; authentication không đủ để bảo vệ multi-tenant data. Với external storage, cần defense-in-depth, least privilege, cancellation và log hygiene. Ở frontend async, request order và completion order là hai thứ khác nhau; correctness cần bảo đảm stale work không được commit state, còn debounce/cancellation chủ yếu kiểm soát waste và UX.

## Mẫu tư duy cần nhớ

- Authentication không thay thế resource authorization.
- Không tin dữ liệu từ client để chứng minh quyền truy cập của chính client đó.
- Tách correctness guard khỏi optimization: ignore stale result vẫn cần thiết dù đã abort request.
- Giảm work obsolete ở mọi boundary nhưng không giả định cancellation luôn tức thì.
- Test failure path và race condition, không chỉ happy path.
