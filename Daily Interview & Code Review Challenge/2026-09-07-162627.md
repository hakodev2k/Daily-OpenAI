# Code Review Challenge 1 — API đã `[Authorize]` nhưng user vẫn đọc và sửa dữ liệu tenant khác

**Chủ đề:** C#/.NET, ASP.NET Core, JWT claims, policy-based authorization, resource-based authorization, multi-tenant isolation, EF Core, security, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một enterprise management portal chạy ASP.NET Core .NET 8. Frontend React gọi REST API bằng JWT do Microsoft Entra ID phát hành. Hệ thống là multi-tenant: mỗi user chỉ được xem và sửa project thuộc tenant của mình.

JWT thường chứa các claim đại diện cho subject/user, tenant và role. Backend hiện tại dùng `[Authorize]` ở controller level và một số action kiểm tra `role=Admin` trực tiếp từ claim.

Production vừa xuất hiện incident:

- user tenant A có thể đoán `projectId` rồi đọc project của tenant B;
- một số user có role `ProjectAdmin` ở tenant A nhưng lại update project của tenant B;
- support phát hiện nhiều endpoint chỉ filter theo primary key;
- frontend ẩn nút edit với user không có quyền nên team trước đây cho rằng đủ an toàn;
- một vài integration test chỉ kiểm tra 401/200 nhưng không kiểm tra cross-tenant access;
- log ghi `ProjectId` nhưng không ghi tenant resolved từ identity, authorization result hoặc policy;
- team đề xuất thêm claim `CanEditAnyProject=true` vào JWT để giảm số query authorization xuống database.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/projects")]
[Authorize]
public sealed class ProjectsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ProjectsController> _logger;

    public ProjectsController(
        AppDbContext db,
        ILogger<ProjectsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{projectId:guid}")]
    public async Task<IActionResult> Get(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var project = await _db.Projects
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == projectId,
                cancellationToken);

        if (project is null)
        {
            return NotFound();
        }

        return Ok(project);
    }

    [HttpPut("{projectId:guid}")]
    public async Task<IActionResult> Update(
        Guid projectId,
        UpdateProjectRequest request,
        CancellationToken cancellationToken)
    {
        var role = User.FindFirst("role")?.Value;

        if (role != "ProjectAdmin" && role != "GlobalAdmin")
        {
            return Forbid();
        }

        var project = await _db.Projects
            .SingleOrDefaultAsync(
                x => x.Id == projectId,
                cancellationToken);

        if (project is null)
        {
            return NotFound();
        }

        project.Name = request.Name;
        project.Description = request.Description;
        project.OwnerUserId = request.OwnerUserId;

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Project {ProjectId} updated by {User}",
            project.Id,
            User.Identity?.Name);

        return NoContent();
    }
}

public sealed record UpdateProjectRequest(
    string Name,
    string? Description,
    Guid OwnerUserId);
```

## Câu hỏi gợi mở

1. `[Authorize]` hiện tại chứng minh caller được phép làm gì ngoài việc đã authenticated?
2. Nếu `projectId` đúng nhưng thuộc tenant khác, query hiện tại có boundary nào ngăn data leak?
3. Role claim có đủ để quyết định authorization khi cùng một role có scope khác nhau theo tenant/project không?

### Gợi ý 1

Rủi ro chính là **authentication được dùng thay cho resource authorization**, trong khi `projectId` là untrusted resource identifier.

Tách ba câu hỏi:

- caller là ai;
- caller thuộc tenant/scope nào;
- caller có quyền thực hiện operation này trên resource cụ thể này không.

## Kết quả code review tham khảo

### Critical — Broken object-level authorization / cross-tenant data leak

**Vấn đề:**  
GET query chỉ filter `Id == projectId`.

**Tại sao xảy ra:**  
`[Authorize]` chỉ yêu cầu authenticated principal nếu không có policy/role cụ thể. Nó không tự xác minh resource thuộc tenant của caller.

**Ảnh hưởng production:**  
Authenticated user có thể đọc project tenant khác nếu biết/đoán ID.

**Cách sửa:**  
Resolve tenant từ trusted identity/application context rồi enforce tenant scope trong data access hoặc resource authorization. Ví dụ query theo `(TenantId, ProjectId)` thay vì chỉ `ProjectId`. Với security-sensitive multi-tenant systems, tenant boundary nên được enforce nhất quán qua application abstraction/global query strategy phù hợp và vẫn phải có integration tests chứng minh isolation.

---

### Critical — Update authorization chỉ kiểm tra role, không kiểm tra resource scope

**Vấn đề:**  
User có `ProjectAdmin` ở tenant A có thể update project tenant B.

**Tại sao xảy ra:**  
Role được xem như global permission mặc dù business permission thực tế scoped theo tenant/resource.

**Ảnh hưởng production:**  
Privilege escalation và cross-tenant modification.

**Cách sửa:**  
Dùng policy/resource-based authorization hoặc service chuyên trách authorization để kiểm tra operation trên resource cụ thể. Role chỉ là một input; tenant/project membership hoặc global-admin semantics phải được xác minh rõ.

---

### High — Raw claim string được hard-code trong controller

**Vấn đề:**  
Controller tự parse `role` và tự quyết định business authorization.

**Tại sao xảy ra:**  
Security policy bị phân tán trong endpoint code.

**Ảnh hưởng production:**  
Dễ lệch claim type/mapping, duplicate logic giữa endpoints, khó audit và khó thay đổi policy.

**Cách sửa:**  
Dùng ASP.NET Core policy-based authorization cho coarse-grained requirements và `IAuthorizationService`/resource handler cho resource-specific rules. ASP.NET Core hỗ trợ authorization theo policies/requirements; authenticated access không đồng nghĩa với quyền trên mọi resource.

---

### High — Tenant identifier không được đưa vào query boundary

**Vấn đề:**  
Data lookup dựa trên global primary key.

**Tại sao xảy ra:**  
Tenant isolation là convention thay vì invariant có thể kiểm thử.

**Ảnh hưởng production:**  
Một endpoint mới hoặc refactor nhỏ rất dễ quên filter tenant.

**Cách sửa:**  
Thiết kế repository/query service/application service để tenant scope là input bắt buộc hoặc được resolve từ trusted context. Tùy hệ thống, có thể cân nhắc query filters, database RLS hoặc composite constraints như defense-in-depth; không nên dựa duy nhất vào một mechanism mà không hiểu bypass cases.

---

### High — Cho client trực tiếp đổi `OwnerUserId` mà không authorize target owner

**Vấn đề:**  
Request có thể chuyển owner sang bất kỳ `Guid` nào.

**Tại sao xảy ra:**  
Backend validate shape nhưng không validate business invariant và authorization của relationship mới.

**Ảnh hưởng production:**  
Có thể gán project cho user tenant khác, tạo data integrity leak hoặc privilege escalation gián tiếp.

**Cách sửa:**  
Validate target owner tồn tại trong tenant, caller có quyền reassign ownership, và relationship hợp lệ. Nếu đổi owner là operation nhạy cảm, tách endpoint/command riêng để policy rõ hơn.

---

### High — DTO update có nguy cơ mở rộng thành mass assignment không kiểm soát

**Vấn đề:**  
Hiện tại mapping thủ công còn giới hạn field, nhưng việc cho phép field security-sensitive như owner nằm chung với content update làm boundary mơ hồ.

**Tại sao xảy ra:**  
Command không phản ánh privilege level của từng mutation.

**Ảnh hưởng production:**  
Sau refactor dùng auto-mapper/entity binding, risk có thể tăng mạnh.

**Cách sửa:**  
Dùng command DTO theo use case, ví dụ `UpdateProjectDetails` và `TransferProjectOwnership` riêng, với policy riêng.

---

### High — Đề xuất nhét permission động vào long-lived JWT có stale-authorization trade-off

**Vấn đề:**  
`CanEditAnyProject=true` có thể trở nên stale sau khi permission bị revoke.

**Tại sao xảy ra:**  
JWT là self-contained snapshot trong lifetime của token trừ khi hệ thống có cơ chế khác để re-evaluate/revoke.

**Ảnh hưởng production:**  
User có thể tiếp tục dùng quyền cũ tới khi token hết hạn hoặc bị chặn bởi cơ chế khác.

**Cách sửa:**  
Chỉ đưa stable identity/coarse claims vào token khi phù hợp. Với dynamic/resource-sensitive authorization, resolve từ authoritative application data/cache có bounded TTL hoặc security-stamp/version strategy. Quyết định dựa trên latency, revocation requirement và risk.

---

### Medium — Không có optimistic concurrency cho update

**Vấn đề:**  
Hai admins có thể cùng đọc/sửa và last-write-wins âm thầm.

**Tại sao xảy ra:**

**Ảnh hưởng production:**

**Cách sửa:**  
Nếu business yêu cầu phát hiện concurrent edit, dùng row version/concurrency token và trả conflict phù hợp. Nếu last-write-wins được chấp nhận, document assumption.

### Medium — Response trả entity trực tiếp

**Vấn đề:**

**Tại sao xảy ra:**

**Ảnh hưởng production:**

**Cách sửa:**

**Vấn đề:**  
Log chỉ có project ID và user display/name.

**Tại sao xảy ra:**

**Ảnh hưởng production:**

## Phiên bản đề xuất

Ví dụ dưới đây giả định tenant được resolve từ trusted identity context và project permissions cần resource-based authorization:

```csharp
[ApiController]
[Route("api/projects")]
[Authorize]
public sealed class ProjectsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ICurrentTenant _currentTenant;
    private readonly IAuthorizationService _authorization;

    public ProjectsController(
        AppDbContext db,
        ICurrentTenant currentTenant,
        IAuthorizationService authorization)
    {
        _db = db;
        _currentTenant = currentTenant;
        _authorization = authorization;
    }

    [HttpGet("{projectId:guid}")]
    public async Task<ActionResult<ProjectResponse>> Get(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var tenantId = _currentTenant.Id;

        var project = await _db.Projects
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.Id == projectId)
            .Select(x => new ProjectResource
            {
                Id = x.Id,
                TenantId = x.TenantId,
                Name = x.Name,
                Description = x.Description,
                OwnerUserId = x.OwnerUserId
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (project is null)
        {
            return NotFound();
        }

        var authorization = await _authorization.AuthorizeAsync(
            User,
            project,
            ProjectOperations.Read);

        if (!authorization.Succeeded)
        {
            return Forbid();
        }

        return Ok(new ProjectResponse(
            project.Id,
            project.Name,
            project.Description,
            project.OwnerUserId));
    }
}
```

## Giải thích thiết kế sau khi sửa

### 1. Authentication không còn được dùng thay authorization

Identity chỉ xác định caller. Access decision dựa trên operation + resource + scope.

### 2. Tenant boundary nằm ngay trong data retrieval

Không load resource tenant khác rồi mới vô tình expose. Tùy threat model, có thể trả `404` cho cross-tenant resource để giảm information disclosure, nhưng behavior phải nhất quán và intentional.

### 3. Policy được tập trung hóa

Controller không tự hard-code role strings cho mọi use case.

### 4. Sensitive mutation được tách use case

Đổi owner có policy riêng thay vì đi cùng update description.

### 5. Token claims được coi là snapshot

Permission quá động hoặc cần revoke nhanh không nên mặc định phụ thuộc hoàn toàn vào long-lived self-contained claim.

## Trade-offs

- Resource authorization có thể thêm database/cache lookup và latency.
- Dùng policy/handler tăng số abstraction nhưng giảm scattered security logic.
- Query-level tenant filtering rất hiệu quả nhưng cần thiết kế để background/admin flows vẫn explicit.
- Database RLS tăng defense-in-depth nhưng cũng tăng operational/debugging complexity.
- Permission cache giảm latency nhưng tạo revocation/staleness window.

## Cách kiểm thử

1. **Cross-tenant integration test:** tenant A không thể GET/PUT project tenant B dù biết ID.
2. **Privilege test:** `ProjectAdmin` tenant A không có quyền trên tenant B; `GlobalAdmin` chỉ được phép nếu policy business quy định rõ.
3. **Ownership security test:** không thể transfer owner sang user ngoài tenant hoặc khi thiếu permission.
4. **Token-staleness test:** revoke permission và xác minh behavior theo documented token/cache revocation window.
5. **Concurrency test:** nếu dùng concurrency token, hai update đồng thời phải tạo conflict thay vì silent overwrite.

## Quan sát trong production

Theo dõi:

- authorization allow/deny count theo operation/policy;
- cross-tenant deny attempts;
- 401/403/404 distribution;
- subject + tenant + resource correlation an toàn;
- policy evaluation latency nếu có data lookup;
- permission-cache hit/miss/staleness indicator nếu dùng cache;
- anomalous access pattern theo project IDs;
- deployment version và trace ID;
- audit trail cho sensitive operations như ownership transfer.

1. Khi nào query filter theo tenant là đủ, và khi nào vẫn cần resource-based authorization?
2. Bạn sẽ thiết kế revocation thế nào nếu JWT access token sống 60 phút nhưng permission phải thu hồi gần như ngay lập tức?
3. Nếu support staff cần cross-tenant read-only access, bạn thêm exception vào role hay thiết kế explicit support policy/context riêng?

# Code Review Challenge 2 — SQL pagination càng về cuối càng chậm và update order gây deadlock dưới tải

**Chủ đề:** SQL Server, PostgreSQL concepts, pagination, composite indexes, execution plans, blocking, deadlocks, transaction scope, keyset pagination, API performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một order-management API có bảng `Orders` khoảng 120 triệu rows trên SQL Server. UI cho phép:

- filter theo tenant và status;
- sort mới nhất trước;
- mở trang sâu để support tra cứu lịch sử;
- bulk update status của một nhóm orders;
- traffic đọc cao, nhưng giờ cao điểm vẫn có nhiều update đồng thời.

Production ghi nhận:

- page 1 trả trong khoảng dưới 200 ms nhưng page 20.000 có thể mất nhiều giây;
- CPU và logical reads tăng mạnh khi offset lớn;
- API đôi lúc timeout khi user export/scroll lịch sử sâu;
- deadlock xuất hiện giữa bulk status update và một background reconciliation job;
- team đề xuất thêm index riêng cho từng cột filter và tăng command timeout lên 120 giây;
- support muốn dữ liệu pagination “không nhảy lung tung” khi có order mới được insert liên tục.

CREATE INDEX IX_Orders_Status

## Nhiệm vụ của ứng viên

1. Xác định performance problems trong pagination.
2. Phân tích vì sao nhiều single-column indexes chưa chắc phục vụ query tốt.
3. Đề xuất composite/covering index dựa trên query shape.
4. Phân tích OFFSET pagination khi page rất sâu.
5. Đánh giá consistency/stability của pagination khi dữ liệu thay đổi liên tục.
6. Phân tích deadlock possibility giữa hai transaction paths.
7. Đánh giá transaction scope và batch size.
8. Đề xuất keyset pagination khi phù hợp.
9. Giải thích cách dùng execution plan/wait/deadlock evidence trước khi tối ưu.
10. Giải thích testing và telemetry production.

## Câu hỏi gợi mở

1. Với predicate `TenantId + Status` rồi `ORDER BY CreatedUtc DESC`, ba index riêng lẻ có tương đương một index khớp query shape không?
2. SQL engine phải làm gì với hàng triệu rows trước offset khi user mở page rất sâu?
3. Nếu nhiều rows có cùng `CreatedUtc`, pagination order hiện tại có deterministic hoàn toàn không?
4. Hai transaction acquire locks trên `Orders` và `OrderSummaries` theo cùng thứ tự hay khác thứ tự?
5. Tăng command timeout có xử lý root cause của blocking/deadlock hoặc excessive reads không?

### Gợi ý 1

## Kết quả code review tham khảo

### High — Deep OFFSET pagination có chi phí tăng theo vị trí trang

**Vấn đề:**  
Page càng sâu, engine vẫn phải locate/order/skip lượng rows trước offset rồi mới trả page hiện tại.

**Tại sao xảy ra:**  
OFFSET/FETCH mô tả vị trí tương đối, không cung cấp seek anchor từ page trước.

**Ảnh hưởng production:**  
Logical reads, CPU và duration tăng khi page number lớn; tail latency xấu và dễ timeout dưới concurrency.

**Cách sửa:**  
Nếu UX cho phép next/previous hoặc cursor-based navigation, dùng keyset/seek pagination dựa trên deterministic sort key. Nếu business bắt buộc random page number sâu, OFFSET có thể vẫn cần nhưng phải hiểu cost, giới hạn depth hoặc dùng alternate search/report workflow.

---

### High — Các single-column indexes không khớp predicate + sort của query

**Vấn đề:**  
Có index riêng trên `Status`, `TenantId`, `CreatedUtc`.

**Tại sao xảy ra:**  
Query filter equality trên `TenantId`, `Status` rồi sort/range theo `CreatedUtc`. Một composite index có thứ tự key phù hợp thường hữu ích hơn cho seek + ordered retrieval so với nhiều single indexes, nhưng quyết định phải dựa trên execution plan/cardinality/workload.

**Ảnh hưởng production:**  
Engine có thể scan, sort hoặc perform expensive lookups thay vì seek ordered range hiệu quả.

**Cách sửa:**  
Candidate index để đánh giá:

```sql
CREATE INDEX IX_Orders_Tenant_Status_Created_Id
ON dbo.Orders(
    TenantId,
    Status,
    CreatedUtc DESC,
    Id DESC)
INCLUDE(
    CustomerId,
    TotalAmount);
```

Không tự động tạo index này trên production mà chưa kiểm tra write overhead, index size, selectivity và existing workload.

---

### High — Ordering không deterministic khi nhiều rows có cùng `CreatedUtc`

**Vấn đề:**  
`ORDER BY CreatedUtc DESC` không định nghĩa thứ tự duy nhất giữa rows cùng timestamp.

**Tại sao xảy ra:**  
Sort key không unique.

**Ảnh hưởng production:**  
Rows có thể xuất hiện lặp/thiếu giữa các pages khi execution/data changes, đặc biệt dưới concurrent inserts.

**Cách sửa:**  
Thêm stable tie-breaker, thường `Id`:

```sql
ORDER BY CreatedUtc DESC, Id DESC
```

Keyset cursor phải chứa cả hai values.

---

### High — Offset pagination không cho stable snapshot khi dữ liệu thay đổi giữa requests

**Vấn đề:**  
Insert order mới giữa page 1 và page 2 có thể dịch vị trí các rows cũ.

**Tại sao xảy ra:**  
Mỗi request paginate trên trạng thái dữ liệu mới tại thời điểm riêng.

**Ảnh hưởng production:**  
User có thể thấy duplicate hoặc miss row giữa pages.

**Cách sửa:**  
Keyset pagination ổn định hơn cho forward traversal theo anchor, nhưng vẫn không phải snapshot transaction qua nhiều HTTP requests. Nếu requirement là exact historical snapshot, cần explicit snapshot/version/export semantics chứ không chỉ đổi pagination algorithm.

---

### Critical — Hai transaction acquire resources theo thứ tự khác nhau

**Vấn đề:**  
Bulk update: `Orders → OrderSummaries`. Reconciliation: `OrderSummaries → Orders`.

**Tại sao xảy ra:**  
Concurrent transactions có thể giữ lock ở resource A rồi chờ resource B theo vòng ngược nhau.

**Ảnh hưởng production:**  
Deadlock victim bị rollback; nếu retry không idempotent hoặc monitoring kém, user thấy 500/timeouts và throughput giảm.

**Cách sửa:**  
Đầu tiên xác minh bằng deadlock graph. Sau đó chuẩn hóa lock acquisition order giữa code paths nếu có thể, thu hẹp transaction, giảm số rows/lock duration, tối ưu indexes để update tìm rows nhanh hơn và implement bounded retry cho deadlock victim khi operation an toàn/idempotent.

---

### High — Reconciliation update có thể lock quá nhiều rows trong một transaction

**Vấn đề:**  
`UPDATE Orders ... WHERE TenantId = ... AND ReconciledUtc IS NULL` không batch.

**Tại sao xảy ra:**  
Một transaction có thể chạm lượng rows rất lớn.

**Ảnh hưởng production:**  
Lock duration, transaction log, blocking và deadlock probability tăng.

**Cách sửa:**  
Batch theo deterministic key/range nếu eventual reconciliation cho phép. Mỗi batch commit riêng và có restart/retry semantics rõ. Nếu requirement cần atomic toàn tenant, trade-off phải được nêu rõ.

---

### High — `@ChangedCount` có thể lệch số rows thực sự update

**Vấn đề:**  
Summary update dựa trên parameter riêng thay vì số rows thực tế bị update.

**Tại sao xảy ra:**  
Concurrency hoặc predicate changes có thể làm actual affected rows khác expected count.

**Ảnh hưởng production:**  
`OrderSummaries` drift khỏi source data.

**Cách sửa:**  
Capture affected IDs/count trong cùng transaction bằng `OUTPUT` hoặc stored procedure logic phù hợp, hoặc thiết kế summary như derived data có reconciliation rõ ràng.

---

### Medium — Query trong `IN (SELECT...)` thiếu unique tie-breaker

**Vấn đề:**  
Batch chọn 500 rows theo `CreatedUtc` nhưng nếu timestamp trùng, subset có thể không deterministic.

**Tại sao xảy ra:**  
Sort không unique.

**Ảnh hưởng production:**  
Khó reasoning/retry, batch có thể chọn tập khác giữa executions.

**Cách sửa:**  
Order bằng `CreatedUtc, Id` hoặc chọn theo keyset/claim semantics phù hợp.

---

### Medium — Tăng command timeout chỉ che symptom

**Vấn đề:**  
Team đề xuất tăng timeout lên 120 giây.

**Tại sao xảy ra:**  
Timeout được xem như performance tuning thay vì circuit breaker/upper bound.

**Ảnh hưởng production:**  
Request giữ connection/thread/task resources lâu hơn; blocking chain có thể trầm trọng hơn.

**Cách sửa:**  
Đo query duration, waits, blocking, deadlocks, execution plan và logical reads trước. Chỉ điều chỉnh timeout sau khi hiểu expected legitimate duration.

---

### Medium — Index thêm mới có write/storage cost

**Vấn đề:**  
Một covering composite index lớn không miễn phí.

**Tại sao xảy ra:**  
Mỗi insert/update status có thể phải maintain index; included columns tăng storage.

**Ảnh hưởng production:**  
Write latency, log volume, storage và maintenance cost tăng.

**Cách sửa:**  
Benchmark read gain so với write overhead. Xóa duplicate/redundant indexes nếu evidence cho phép, thay vì chỉ thêm index mãi.

## Phiên bản đề xuất

Keyset query cho next-page flow:

```sql
SELECT TOP (@PageSize)
    Id,
    TenantId,
    Status,
    CustomerId,
    TotalAmount,
    CreatedUtc
FROM dbo.Orders
WHERE TenantId = @TenantId
  AND Status = @Status
  AND (
        @AfterCreatedUtc IS NULL
        OR CreatedUtc < @AfterCreatedUtc
        OR (
            CreatedUtc = @AfterCreatedUtc
            AND Id < @AfterId
        )
      )
ORDER BY CreatedUtc DESC, Id DESC;
```

Cursor trả về client có thể encode/sign cặp:

```text
CreatedUtc + Id + filter/sort version
```

để client không tự sửa scope/query semantics.

Candidate index:

```sql
CREATE INDEX IX_Orders_Tenant_Status_Created_Id
ON dbo.Orders(
    TenantId,
    Status,
    CreatedUtc DESC,
    Id DESC)
INCLUDE(
    CustomerId,
    TotalAmount);
```

Với deadlock, một hướng refactor là thống nhất transaction order:

```text
1. Resolve/claim target order IDs nhanh và deterministic.
2. Update Orders batch.
3. Update OrderSummaries.
4. Commit sớm.
```

Mọi code path khác chạm hai resources cũng nên theo cùng acquisition order nếu business semantics cho phép.

Reconciliation có thể batch:

```sql
;WITH batch AS
(
    SELECT TOP (500) Id
    FROM dbo.Orders
    WHERE TenantId = @TenantId
      AND ReconciledUtc IS NULL
    ORDER BY Id
)
UPDATE o
SET ReconciledUtc = SYSUTCDATETIME()
FROM dbo.Orders o
JOIN batch b ON b.Id = o.Id;
```

Cần lặp với cancellation/backoff và commit từng batch theo requirement.

## Giải thích thiết kế sau khi sửa

### 1. Pagination chuyển từ “skip N rows” sang “seek after cursor”

Cost theo page depth giảm đáng kể khi index hỗ trợ seek pattern.

### 2. Sort key trở nên deterministic

`CreatedUtc + Id` tạo total ordering phù hợp pagination.

### 3. Index được thiết kế từ query shape

Equality predicates đứng trước, sau đó sort/seek keys; INCLUDE chỉ các projection thực sự đáng cover.

### 4. Deadlock được xử lý từ evidence

Không đoán root cause. Deadlock graph phải cho thấy wait cycle và lock resources trước khi sửa.

### 5. Transaction được giữ ngắn

Batching và consistent acquisition order giảm lock duration/risk nhưng phải cân bằng với atomicity requirement.

## Trade-offs

- Keyset pagination không hỗ trợ “nhảy thẳng page 20.000” tự nhiên như OFFSET.
- Cursor token tăng API contract complexity.
- Composite covering index tăng write/storage cost.
- Batch reconciliation giảm lock footprint nhưng mất atomicity toàn bộ dataset.
- Deadlock retry hữu ích cho transient victim nhưng không thay thế root-cause fix.
- Snapshot-consistent browsing qua nhiều HTTP requests cần design riêng và có thể tăng storage/complexity.

## Cách kiểm thử

1. **Performance test:** so sánh OFFSET page sâu với keyset trên volume gần production; đo logical reads, CPU, p95/p99.
2. **Plan/index test:** capture actual execution plan và chứng minh seek/sort/lookups thay đổi như kỳ vọng.
3. **Pagination correctness test:** nhiều rows cùng `CreatedUtc`, concurrent inserts giữa requests; không duplicate/miss ngoài documented consistency semantics.
4. **Deadlock concurrency test:** chạy bulk update và reconciliation song song nhiều lần; thu deadlock graph trước/sau refactor.
5. **Failure-path test:** inject deadlock victim/timeout; retry chỉ thực hiện với bounded policy và operation idempotent.

## Quan sát trong production

Theo dõi:

- query duration p50/p95/p99 theo pagination method/depth;
- logical reads và CPU của top query shapes;
- execution-plan regressions;
- database waits/blocking chains;
- deadlock count và deadlock graph;
- rows affected/batch duration;
- transaction-log growth;
- index usage/write overhead;
- API timeout/cancellation rate;
- cursor pagination error/tamper rate nếu cursor signed;
- summary reconciliation drift metrics.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào OFFSET/FETCH vẫn là lựa chọn hợp lý hơn keyset pagination?
2. Nếu product yêu cầu jump-to-page chính xác và dataset thay đổi liên tục, bạn sẽ làm rõ requirement nào trước khi thiết kế?
3. Nếu execution plan vẫn scan dù có composite index, bạn sẽ kiểm tra cardinality, parameter sensitivity và statistics như thế nào trước khi thêm index khác?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `[Authorize]` xác minh access theo policy đã cấu hình; authenticated không đồng nghĩa với được phép truy cập mọi resource.
- Multi-tenant security cần enforce tenant/resource scope ở backend, không phụ thuộc frontend hiding.
- Role claim thường là một input của authorization, không phải toàn bộ resource-authorization model.
- Dynamic permission trong JWT có trade-off về staleness/revocation.
- Deep OFFSET pagination có cost tăng theo vị trí trang; keyset pagination phù hợp hơn cho cursor traversal khi requirement cho phép.
- Composite index nên phản ánh predicate + sort/query shape thay vì tạo index rời rạc theo từng column.
- Deadlock cần được điều tra bằng wait cycle/deadlock graph và thường liên quan lock acquisition order, transaction duration và access path.

## Mẫu tư duy cần nhớ

1. **Authenticate identity, authorize operation on resource.**
2. **Treat every resource ID from the client as untrusted until scope is verified.**
3. **Design indexes from query shape and evidence, not from column names.**
4. **Prefer deterministic ordering for pagination and batching.**
5. **Use evidence → hypothesis → verification before changing timeout, index or isolation behavior.**
