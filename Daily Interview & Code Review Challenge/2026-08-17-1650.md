# Code Review Challenge 1 — Redis cache-aside gây cache stampede và dữ liệu cũ dưới tải cao

**Chủ đề:** Caching, concurrency, performance, cancellation, error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API trả về cấu hình quyền và feature flags của user sau khi đăng nhập. Dữ liệu gốc nằm trong PostgreSQL, nhưng team dùng Redis để giảm tải database vì endpoint này được gọi từ nhiều request khác nhau trong cùng một session.

Lưu lượng bình thường khoảng 300 request/giây, peak khoảng 1.500 request/giây sau giờ bắt đầu làm việc. Redis TTL hiện là 5 phút. Sau một đợt scale-out từ 2 lên 8 instance, production xuất hiện các triệu chứng:

- PostgreSQL CPU tăng mạnh theo chu kỳ gần 5 phút.
- Một số thời điểm hàng trăm query giống nhau chạy đồng thời.
- Khi admin cập nhật quyền user, một số request vẫn đọc dữ liệu cũ khá lâu.
- Khi Redis chập chờn, latency API tăng mạnh thay vì fallback ổn định.
- Log khó xác định request lấy dữ liệu từ cache hay database.

Team muốn giữ cache-aside đơn giản, chưa muốn đưa thêm message broker chỉ để invalidation.

## Đoạn code cần review

```csharp
public sealed class UserAccessService
{
    private readonly IDatabase _redis;
    private readonly AppDbContext _db;
    private readonly ILogger<UserAccessService> _logger;

    public UserAccessService(
        IConnectionMultiplexer redis,
        AppDbContext db,
        ILogger<UserAccessService> logger)
    {
        _redis = redis.GetDatabase();
        _db = db;
        _logger = logger;
    }

    public async Task<UserAccessDto> GetAccessAsync(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var key = $"user-access:{userId}";
        var cached = await _redis.StringGetAsync(key);

        if (cached.HasValue)
        {
            return JsonSerializer.Deserialize<UserAccessDto>(cached!)!;
        }

        var user = await _db.Users
            .Include(x => x.Roles)
            .ThenInclude(x => x.Permissions)
            .SingleAsync(x => x.Id == userId, cancellationToken);

        var dto = new UserAccessDto(
            user.Id,
            user.Roles.SelectMany(x => x.Permissions)
                .Select(x => x.Code)
                .Distinct()
                .ToArray(),
            user.FeatureFlags.ToDictionary(x => x.Key, x => x.Enabled));

        var json = JsonSerializer.Serialize(dto);

        await _redis.StringSetAsync(
            key,
            json,
            TimeSpan.FromMinutes(5));

        _logger.LogInformation(
            "Loaded access for {UserId}: {Payload}",
            userId,
            json);

        return dto;
    }

    public async Task UpdateRoleAsync(
        Guid userId,
        Guid roleId,
        CancellationToken cancellationToken)
    {
        var user = await _db.Users
            .Include(x => x.Roles)
            .SingleAsync(x => x.Id == userId, cancellationToken);

        var role = await _db.Roles
            .SingleAsync(x => x.Id == roleId, cancellationToken);

        user.Roles.Clear();
        user.Roles.Add(role);

        await _db.SaveChangesAsync(cancellationToken);
        await _redis.KeyDeleteAsync($"user-access:{userId}");
    }
}
```

## Kết quả code review tham khảo

### 1. Cache stampede khi key hết hạn

**Problem:** Mọi request cùng miss cache đều chạy query database và cùng rebuild cùng một key.

**Why it happens:** Không có single-flight/lock/coalescing theo cache key.

**Production impact:** Khi TTL hết hoặc Redis bị flush, database có thể nhận hàng trăm/hàng nghìn query giống nhau trong thời gian ngắn, tạo CPU spike, connection pressure và latency cascade.

**Severity:** High

**Recommended fix:** Dùng single-flight theo key trong mỗi instance và, nếu cần chống stampede cross-instance, dùng distributed lock có lease ngắn hoặc chiến lược stale-while-revalidate. Không giữ distributed lock quá lâu và luôn re-check cache sau khi lấy lock.

### 2. TTL cố định tạo synchronized expiration

**Problem:** Mọi entry dùng đúng 5 phút.

**Why it happens:** Không có jitter và nhiều key có thể được warm gần cùng thời điểm.

**Production impact:** Expiration theo cụm gây traffic spike định kỳ vào database/Redis.

**Severity:** High

**Recommended fix:** Thêm random jitter hợp lý vào TTL, ví dụ base TTL + một khoảng ngẫu nhiên nhỏ.

### 3. Database update thành công nhưng invalidation Redis thất bại

**Problem:** `SaveChangesAsync` và `KeyDeleteAsync` không phải một transaction chung.

**Why it happens:** Database và Redis là hai hệ thống độc lập.

**Production impact:** Cache cũ có thể tiếp tục tồn tại đến khi TTL hết, dẫn đến authorization/feature behavior lỗi thời.

**Severity:** High

**Recommended fix:** Đặt TTL đủ ngắn theo business risk, retry invalidation có giới hạn, ghi metric/log khi invalidation thất bại. Với yêu cầu consistency nghiêm ngặt hơn, cân nhắc versioned cache key hoặc outbox/event-driven invalidation; nhưng không cần nâng cấp kiến trúc nếu business chấp nhận bounded staleness.

### 4. Query đọc dùng tracking và load entity graph lớn hơn cần thiết

**Problem:** `Include`/`ThenInclude` materialize entity graph rồi mới map DTO.

**Why it happens:** Query không project trực tiếp dữ liệu cần thiết.

**Production impact:** Tăng allocation, tracking overhead, lượng dữ liệu transfer và thời gian query.

**Severity:** Medium

**Recommended fix:** Dùng `AsNoTracking()` và projection trực tiếp sang DTO hoặc anonymous projection nếu provider translate tốt.

### 5. Redis failure làm request path phụ thuộc quá mạnh vào cache

**Problem:** `StringGetAsync`, `StringSetAsync` và `KeyDeleteAsync` không có degradation strategy rõ ràng.

**Why it happens:** Cache được dùng như dependency bắt buộc thay vì optimization.

**Production impact:** Redis outage có thể biến thành API outage/latency spike mặc dù database vẫn hoạt động.

**Severity:** High

**Recommended fix:** Với read path, có thể fallback database khi cache read lỗi và ghi metric rõ ràng; cache write failure thường không nên làm fail response đọc. Với mutation path, invalidation failure phải được ghi nhận và retry/reconcile theo policy.

### 6. Cache key không có version/schema namespace

**Problem:** Key chỉ chứa user id.

**Why it happens:** Không dự phòng thay đổi shape/logic cache giữa các deployment.

**Production impact:** Deployment thay DTO hoặc rule tính quyền có thể deserialize lỗi hoặc đọc semantic cũ.

**Severity:** Medium

**Recommended fix:** Namespace/version key như `user-access:v2:{userId}` hoặc dùng version theo permission model.

### 7. Logging toàn bộ payload quyền

**Problem:** Log chứa toàn bộ danh sách permission/feature flags.

**Why it happens:** Logging diagnostic quá chi tiết ở success path.

**Production impact:** Tăng log volume, có thể lộ cấu trúc authorization nội bộ và làm log khó query.

**Severity:** Medium

**Recommended fix:** Log metadata như user id, source=cache/db, permission count, elapsed time, cache key version; tránh dump payload.

### 8. Không có metric cache hit/miss/rebuild/failure

**Problem:** Chỉ có log khi load từ database.

**Why it happens:** Cache chưa được coi là một thành phần cần observability.

**Production impact:** Khó phân biệt database slowdown, Redis slowdown, stampede hoặc cache hit ratio thấp.

**Severity:** Medium

**Recommended fix:** Ghi counters/histograms cho hit, miss, rebuild, Redis error, database fallback, invalidation failure và rebuild duration.

### 9. Không re-check cache sau khi giành quyền rebuild

**Problem:** Nếu thêm lock một cách ngây thơ nhưng không double-check, nhiều waiter vẫn có thể query database tuần tự.

**Why it happens:** Lock chỉ serialize nhưng không xác nhận request khác đã populate cache.

**Production impact:** Giảm concurrency nhưng vẫn tạo query thừa và latency nối đuôi.

**Severity:** Medium

**Recommended fix:** Sau khi lấy lock, đọc lại cache trước khi query DB.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng single-flight trong từng process, TTL jitter, projection no-tracking, graceful cache failure và observability rõ hơn. Nếu nhiều instance vẫn tạo tải quá lớn cùng lúc, có thể bổ sung distributed lock ngắn hạn hoặc stale-while-revalidate.

```csharp
public sealed class UserAccessService
{
    private readonly IDatabase _redis;
    private readonly AppDbContext _db;
    private readonly ILogger<UserAccessService> _logger;
    private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

    public UserAccessService(
        IConnectionMultiplexer redis,
        AppDbContext db,
        ILogger<UserAccessService> logger)
    {
        _redis = redis.GetDatabase();
        _db = db;
        _logger = logger;
    }

    public async Task<UserAccessDto> GetAccessAsync(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var key = $"user-access:v2:{userId}";

        var cached = await TryGetAsync(key);
        if (cached is not null)
        {
            _logger.LogDebug("User access cache hit for {UserId}", userId);
            return cached;
        }

        var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
        await gate.WaitAsync(cancellationToken);

        try
        {
            cached = await TryGetAsync(key);
            if (cached is not null)
                return cached;

            var dto = await _db.Users
                .AsNoTracking()
                .Where(x => x.Id == userId)
                .Select(x => new UserAccessDto(
                    x.Id,
                    x.Roles.SelectMany(r => r.Permissions)
                        .Select(p => p.Code)
                        .Distinct()
                        .ToArray(),
                    x.FeatureFlags.ToDictionary(f => f.Key, f => f.Enabled)))
                .SingleAsync(cancellationToken);

            var ttl = TimeSpan.FromSeconds(
                240 + Random.Shared.Next(0, 90));

            try
            {
                await _redis.StringSetAsync(
                    key,
                    JsonSerializer.Serialize(dto),
                    ttl);
            }
            catch (RedisException ex)
            {
                _logger.LogWarning(ex,
                    "Redis write failed for user access {UserId}", userId);
            }

            _logger.LogInformation(
                "User access rebuilt from DB for {UserId}; Permissions={Count}",
                userId,
                dto.Permissions.Length);

            return dto;
        }
        finally
        {
            gate.Release();
        }
    }

    private async Task<UserAccessDto?> TryGetAsync(string key)
    {
        try
        {
            var value = await _redis.StringGetAsync(key);
            return value.HasValue
                ? JsonSerializer.Deserialize<UserAccessDto>(value!)
                : null;
        }
        catch (RedisException ex)
        {
            _logger.LogWarning(ex, "Redis read failed for {CacheKey}", key);
            return null;
        }
    }
}
```

## Trade-offs

- In-process single-flight chỉ chống stampede trong một instance; 8 instance vẫn có thể cùng rebuild. Nếu database đủ khỏe, đây có thể đã là trade-off hợp lý và đơn giản.
- Distributed lock chống cross-instance stampede tốt hơn nhưng thêm failure modes: lease expiry, lock owner crash, latency Redis và complexity.
- TTL ngắn giảm staleness nhưng tăng database/cache churn.
- Versioned keys đơn giản hoá deployment nhưng có thể để lại key cũ cho tới khi expire.
- Nếu authorization thay đổi phải có hiệu lực gần như tức thời, cache-aside với TTL đơn thuần có thể không đủ; cần strategy invalidation/versioning chặt hơn.

2. **Load test:** Nhiều key hết hạn gần nhau; so sánh database QPS/latency trước và sau TTL jitter.
3. **Failure-path test:** Redis read/write timeout; API vẫn trả dữ liệu từ DB và có metric/log fallback.

# Code Review Challenge 2 — Import nhân viên bằng EF Core chậm, partial update và giữ quá nhiều entity trong ChangeTracker

## Bối cảnh

Một admin API nhận file đã parse thành danh sách 5.000–30.000 nhân viên để đồng bộ dữ liệu từ hệ thống HR sang ứng dụng nội bộ. Mỗi record có `EmployeeCode`, email, department và trạng thái active/inactive.

Hiện tại team gọi service dưới đây sau khi parse file. Production có các triệu chứng:

- Import 20.000 record mất vài phút.
- Memory của process tăng mạnh trong quá trình import.
- Nếu record thứ 12.000 lỗi unique constraint thì khoảng 11.999 record trước đó đã được ghi xuống DB.
- Có đợt retry khiến dữ liệu bị update một phần, khó xác định import nào đã hoàn tất.
- Log có hàng nghìn dòng warning nhưng không có summary rõ ràng.

## Đoạn code cần review

```csharp
public sealed class EmployeeImportService
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeeImportService> _logger;

    public EmployeeImportService(
        AppDbContext db,
        ILogger<EmployeeImportService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<int> ImportAsync(
        IReadOnlyList<EmployeeImportRow> rows,
        CancellationToken cancellationToken)
    {
        var updated = 0;

        foreach (var row in rows)
        {
            var employee = await _db.Employees
                .FirstOrDefaultAsync(
                    x => x.EmployeeCode == row.EmployeeCode,
                    cancellationToken);

            if (employee is null)
            {
                employee = new Employee
                {
                    EmployeeCode = row.EmployeeCode
                };
                _db.Employees.Add(employee);
            }

            employee.Email = row.Email.Trim().ToLowerInvariant();
            employee.DepartmentCode = row.DepartmentCode;
            employee.IsActive = row.IsActive;
            employee.UpdatedAtUtc = DateTime.UtcNow;

            try
            {
                await _db.SaveChangesAsync(cancellationToken);
                updated++;
            }
            catch (DbUpdateException ex)
            {
                _logger.LogWarning(
                    ex,
                    "Failed importing employee {EmployeeCode}",
                    row.EmployeeCode);
            }
        }

        return updated;
    }
}
```

## Kết quả code review tham khảo

### 1. `SaveChangesAsync` cho từng record tạo rất nhiều round-trip

**Problem:** Mỗi row có ít nhất một SELECT và một SaveChanges.

**Why it happens:** Persistence được thực hiện trong vòng lặp từng record.

**Production impact:** Với 20.000 record có thể tạo hàng chục nghìn database round-trip, latency cao, transaction log churn và connection usage không hiệu quả.

**Severity:** High

**Recommended fix:** Xử lý theo batch/chunk, preload existing records theo tập key, rồi SaveChanges theo chunk hoặc một lần tùy memory/transaction strategy.

### 2. Không có transaction semantics rõ ràng cho cả batch

**Problem:** Mỗi `SaveChangesAsync` thành công độc lập; lỗi giữa batch không rollback các record trước.

**Why it happens:** Không có explicit transaction hoặc import status model.

**Production impact:** Partial update không kiểm soát, retry khó dự đoán, downstream không biết batch đã hoàn tất hay chưa.

**Severity:** High

**Recommended fix:** Chốt business semantics. Với all-or-nothing, dùng một transaction bao phủ batch hợp lý. Với partial-success, ghi nhận trạng thái từng row và batch summary, thiết kế retry idempotent.

### 3. N+1 query theo EmployeeCode

**Problem:** Mỗi row gọi `FirstOrDefaultAsync`.

**Why it happens:** Không preload existing employees theo các code trong batch.

**Production impact:** Database QPS cao, import chậm và tăng contention.

**Severity:** High

**Recommended fix:** Chia `EmployeeCode` thành chunk và query existing employees theo `Contains`/set phù hợp với provider, sau đó map vào dictionary.

### 4. Nuốt `DbUpdateException` nhưng giữ entity lỗi trong ChangeTracker

**Problem:** Sau exception, entity Added/Modified gây lỗi có thể vẫn còn tracked.

**Why it happens:** Catch chỉ log rồi tiếp tục.

**Production impact:** Các lần `SaveChangesAsync` sau có thể tiếp tục cố persist entity lỗi, tạo chuỗi failure khó hiểu.

**Severity:** High

**Recommended fix:** Không dùng save-per-row/catch-per-row theo kiểu này. Nếu partial-success, xử lý theo unit rõ ràng và detach/reset state của entity lỗi hoặc dùng DbContext scope/chunk riêng.

### 5. Không validate input trước khi chạm database

**Problem:** Email, employee code, department code và duplicate rows chưa được validate upfront.

**Why it happens:** Validation trộn với persistence.

**Production impact:** Lỗi data xuất hiện muộn, transaction dài hơn cần thiết, retry khó và feedback cho admin kém.

**Severity:** Medium

**Recommended fix:** Validate format, required fields, duplicate codes trong file và business rules trước persistence.

### 6. ChangeTracker có thể phình lớn với batch lớn

**Problem:** Khi refactor sang save theo batch nhưng không clear tracker, hàng chục nghìn entity vẫn có thể được giữ trong DbContext.

**Why it happens:** DbContext sống cho cả import lớn.

**Production impact:** Memory tăng, DetectChanges tốn CPU và thời gian SaveChanges tăng dần.

**Severity:** Medium

**Recommended fix:** Xử lý theo chunk hợp lý; sau khi save chunk, `ChangeTracker.Clear()` nếu không cần giữ tracked state, hoặc dùng DbContext scope mới cho mỗi chunk khi semantics cho phép.

### 7. `DateTime.UtcNow` gọi từng row tạo timestamp không đồng nhất cho cùng batch

**Problem:** Mỗi employee nhận thời điểm khác nhau.

**Why it happens:** Timestamp được lấy trong vòng lặp.

**Production impact:** Audit một batch khó hơn, đặc biệt khi import kéo dài vài phút.

**Severity:** Low

**Recommended fix:** Capture `batchTimestampUtc` một lần nếu business muốn cùng một thời điểm logic.

### 8. Normalization email chưa đủ để đảm bảo business correctness

**Problem:** `.Trim().ToLowerInvariant()` được áp dụng trực tiếp nhưng không xử lý null/invalid format và có thể không phù hợp với chính sách identity của hệ thống.

**Why it happens:** Normalization bị coi như validation.

**Production impact:** Null exception, dữ liệu invalid hoặc khác semantics với source system.

**Severity:** Medium

**Recommended fix:** Validate rõ ràng; chỉ normalize theo policy đã định nghĩa.

### 9. Không có import id/status để hỗ trợ retry và audit

**Problem:** Method chỉ trả số record update.

**Why it happens:** Batch import chưa được model thành workflow có trạng thái.

**Production impact:** Khó trả lời batch nào chạy, batch nào failed, retry có bị trùng hay không.

**Severity:** Medium

**Recommended fix:** Tạo `ImportBatch` với id, checksum/source, status, started/completed time, success/failure counts và error summary.

### 10. Log từng row lỗi nhưng thiếu summary

**Problem:** Hàng nghìn warning có thể được tạo ra.

**Why it happens:** Logging ở granularity quá thấp mà không aggregate.

**Production impact:** Log noise, ingestion cost tăng, khó nhìn bức tranh batch.

**Severity:** Low

**Recommended fix:** Log summary theo batch; chỉ log chi tiết số lượng giới hạn hoặc lưu error report riêng.

## Phiên bản code đề xuất

Ví dụ dưới đây chọn **partial-success theo chunk**: validate trước, preload existing employees theo chunk, save mỗi chunk trong transaction riêng, clear tracker và trả summary. Nếu business yêu cầu all-or-nothing cho toàn file, transaction scope phải được mở rộng cho toàn batch và cần cân nhắc thời gian giữ lock/log.

```csharp
public sealed class EmployeeImportService
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<EmployeeImportService> _logger;

    public EmployeeImportService(
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<EmployeeImportService> logger)
    {
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task<ImportResult> ImportAsync(
        IReadOnlyList<EmployeeImportRow> rows,
        CancellationToken cancellationToken)
    {
        var validRows = ValidateAndNormalize(rows);
        var succeeded = 0;
        var failed = 0;
        var batchTime = DateTime.UtcNow;

        foreach (var chunk in validRows.Chunk(500))
        {
            await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);
            await using var tx = await db.Database.BeginTransactionAsync(cancellationToken);

            try
            {
                var codes = chunk.Select(x => x.EmployeeCode).ToArray();

                var existing = await db.Employees
                    .Where(x => codes.Contains(x.EmployeeCode))
                    .ToDictionaryAsync(x => x.EmployeeCode, cancellationToken);

                foreach (var row in chunk)
                {
                    if (!existing.TryGetValue(row.EmployeeCode, out var employee))
                    {
                        employee = new Employee { EmployeeCode = row.EmployeeCode };
                        db.Employees.Add(employee);
                    }

                    employee.Email = row.Email;
                    employee.DepartmentCode = row.DepartmentCode;
                    employee.IsActive = row.IsActive;
                    employee.UpdatedAtUtc = batchTime;
                }

                await db.SaveChangesAsync(cancellationToken);
                await tx.CommitAsync(cancellationToken);
                succeeded += chunk.Length;
            }
            catch (DbUpdateException ex)
            {
                await tx.RollbackAsync(cancellationToken);
                failed += chunk.Length;
                _logger.LogError(ex,
                    "Employee import chunk failed. Size={ChunkSize}",
                    chunk.Length);
            }
        }

        _logger.LogInformation(
            "Employee import completed. Total={Total} Succeeded={Succeeded} Failed={Failed}",
            rows.Count,
            succeeded,
            failed);

        return new ImportResult(rows.Count, succeeded, failed);
    }

    private static EmployeeImportRow[] ValidateAndNormalize(
        IReadOnlyList<EmployeeImportRow> rows)
    {
        var duplicate = rows
            .GroupBy(x => x.EmployeeCode, StringComparer.OrdinalIgnoreCase)
            .FirstOrDefault(g => g.Count() > 1);

        if (duplicate is not null)
            throw new InvalidOperationException(
                $"Duplicate employee code in import: {duplicate.Key}");

        return rows.Select(x => x with
        {
            EmployeeCode = x.EmployeeCode.Trim(),
            Email = x.Email.Trim().ToLowerInvariant(),
            DepartmentCode = x.DepartmentCode.Trim()
        }).ToArray();
    }
}
```

## Trade-offs

- Chunk transaction giới hạn transaction duration và memory, nhưng cho phép partial-success giữa các chunk.
- All-or-nothing transaction dễ reasoning hơn cho business nhưng với 30.000 rows có thể giữ transaction lâu, tăng lock/log pressure và làm rollback tốn kém.
- Preload bằng `Contains` tốt hơn N+1, nhưng phải chunk để tránh query quá lớn hoặc parameter limits tùy provider.
- `IDbContextFactory` giúp DbContext lifetime rõ ràng cho chunk, nhưng thêm một abstraction và cần đảm bảo transaction semantics phù hợp.
- Bulk library/database-native bulk operation có thể nhanh hơn đáng kể, nhưng thêm dependency, behavior provider-specific và cần đánh giá transaction/audit semantics.

## Cách kiểm thử

1. **Integration test:** 20.000 rows với 70% existing, xác nhận số query không tăng tuyến tính theo từng record.
2. **Failure-path test:** Một chunk có unique violation; xác nhận chỉ chunk đó rollback trong partial-success mode và summary đúng.
3. **All-or-nothing variant test:** Nếu business chọn atomic batch, inject failure giữa batch và xác nhận toàn bộ rollback.
4. **Memory/load test:** Import 30.000 rows, theo dõi allocation, GC và thời gian từng chunk.
5. **Retry/idempotency test:** Chạy cùng file hai lần; kết quả cuối không tạo duplicate và batch audit thể hiện rõ retry.

## Quan sát trong production

- Metric: import duration, rows/sec, success/failure count, chunk failure count.
- Histogram: DB query duration, SaveChanges duration, transaction duration.
- Gauge: process memory, GC collections, DbContext tracked entity count trong diagnostic environment.
- Database: lock waits, transaction log growth, query count và top statements trong thời gian import.
- Structured log theo `ImportBatchId`, chunk number, row count, failed codes summary.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc all-or-nothing cho 30.000 record, bạn sẽ giữ transaction thế nào để giảm risk?
2. Khi nào bạn chọn EF Core thông thường, `ExecuteUpdate`, `COPY`/bulk API hoặc thư viện bulk chuyên dụng?
3. Nếu import có dependency tới Microsoft Graph sau khi DB commit, bạn thiết kế workflow thế nào để không giữ database transaction trong lúc gọi external API?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache không chỉ là `GET/SET`; phải thiết kế stampede control, bounded staleness, failure behavior và observability.
- TTL cố định có thể tạo synchronized expiration; jitter là biện pháp đơn giản nhưng hữu ích.
- Cache invalidation sau database mutation là distributed consistency problem; cần chốt mức staleness business chấp nhận.
- Batch processing cần chốt transaction semantics trước khi tối ưu code.
- EF Core import lớn phải kiểm soát round-trip, ChangeTracker lifetime, transaction duration và error isolation.

## Mẫu tư duy cần nhớ

- Xác định semantics correctness trước khi tối ưu throughput.
- Thiết kế cache miss path cho tình huống nhiều request cùng xảy ra, không chỉ happy path một request.
- Cache phải fail mềm nếu nó chỉ là optimization.
- Batch lớn nên xử lý theo chunk có chủ đích, không phải vòng lặp `SaveChanges` từng record.
- Observability phải cho biết hệ thống đang dùng cache, database hay fallback path nào.
