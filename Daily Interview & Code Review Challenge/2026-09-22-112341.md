# Câu 1 — React hiển thị dữ liệu của request cũ dù request mới đã được gửi sau

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** JavaScript event loop, Promise, React hooks, async race condition, request cancellation, state correctness, browser/network behavior

## Bối cảnh

Một React search page gọi ASP.NET Core API khi người dùng đổi `categoryId`. Component hiện có logic tương đương:

```tsx
useEffect(() => {
  setLoading(true);

  fetch(`/api/products?categoryId=${categoryId}`)
    .then(r => r.json())
    .then(data => {
      setProducts(data);
      setLoading(false);
    })
    .catch(() => setLoading(false));
}, [categoryId]);
```

Khi user đổi nhanh `A → B`, DevTools cho thấy request A được gửi trước nhưng đôi lúc hoàn tất sau request B. UI khi đó hiển thị product của A trong khi filter đang là B. Backend logs xác nhận cả hai response đều đúng với request tương ứng. Một developer cho rằng Promise callbacks luôn chạy theo thứ tự request được tạo nên đây phải là React rendering bug.

Chưa biết component có bị unmount/remount, development có bật behavior làm effect dễ quan sát nhiều lần hay API có caching. Hãy tập trung trước vào race có thể xảy ra ngay cả khi mỗi effect chỉ tạo đúng một request.

## Câu hỏi chính

Giải thích cơ chế khiến state cuối cùng có thể chứa dữ liệu của request A dù request B được tạo sau. Phân biệt thứ tự network completion, Promise continuation/microtask và React state update; chỉ ra assumption sai; sau đó thiết kế cách ngăn stale result cập nhật UI và cách xác minh fix.

## Câu hỏi làm rõ nên cân nhắc

1. Requirement khi filter đổi là cancel request cũ hay chỉ bỏ qua kết quả cũ?
2. `loading` đại diện cho request nào khi nhiều request cùng tồn tại?
3. API có side effect hay đây hoàn toàn là GET/read-only request?
4. Có data-fetching library/cache layer nào khác đang sở hữu request lifecycle không?
5. User có thể đổi filter nhanh đến mức hàng chục request cùng in-flight không?

## Gợi ý tư duy

### Gợi ý 1

Thứ tự **request start** không tạo guarantee cho thứ tự **response completion**.

### Gợi ý 2

Mỗi `.then(...)` đóng trên execution context của request tương ứng; callback nào trở nên runnable trước phụ thuộc Promise được resolve khi nào.

### Gợi ý 3

Hãy xác định ownership của effect instance: khi dependency đổi, cleanup có thể invalidate/cancel work cũ trước khi result được phép commit vào state.

## Cấu trúc trả lời đề xuất

1. Dựng timeline A/B.
2. Giải thích network completion và Promise scheduling.
3. Giải thích vì sao closure cũ vẫn có thể gọi setter.
4. Phân biệt cancel transport với ignore stale result.
5. Đề xuất ownership/cancellation implementation.
6. Xử lý loading/error theo request hiện hành.
7. Test race deterministically.
8. Quan sát browser/API telemetry nếu issue tái diễn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Promise không đảm bảo các request độc lập resolve theo thứ tự được tạo.
- Timeline hợp lệ: A start → B start → B complete/set B → A complete/set A; state cuối cùng vì vậy stale.
- Event loop/microtask queue chỉ quyết định callback đã sẵn sàng được chạy thế nào; nó không biến network operations độc lập thành FIFO completion.
- Effect cũ vẫn có closure và có thể gọi `setProducts` nếu không bị invalidated.
- Cần gắn state commit với request/effect hiện hành, ví dụ cleanup + `AbortController`, hoặc generation/request ID để ignore stale completion.
- `loading` cũng phải thuộc lifecycle hiện hành; request cũ không được phép set `loading=false` cho request mới.

### Điểm cộng

- `AbortController` giảm work/network không còn cần thiết khi fetch hỗ trợ cancellation, nhưng code vẫn nên reason rõ về stale-result ownership.
- Nếu dùng library quản lý server state, nên tận dụng query key/cancellation/stale semantics của library thay vì xây hai ownership systems cạnh tranh.
- Không dùng debounce như correctness fix duy nhất; debounce giảm request volume nhưng race vẫn có thể tồn tại.
- Phân biệt abort với server-side cancellation: client disconnect/cancel không bảo đảm mọi backend/downstream work đã dừng nếu cancellation không được propagate.

### Senior+

- Thiết kế state machine/request identity để `data`, `error`, `loading` cùng thuộc một generation.
- Test bằng controlled deferred responses thay vì dựa vào `setTimeout` ngẫu nhiên.
- Nếu request có side effect, client cancellation không thể được coi là transaction rollback; cần idempotency/business semantics phía server.

## Hướng giải quyết tham khảo

Race nằm ở ownership của asynchronous result. Hai `fetch` độc lập không có ordering guarantee. Nếu B response về trước, Promise B resolve và continuation của B có thể set state. Sau đó A response mới về, continuation của A vẫn hợp lệ về mặt JavaScript và gọi cùng React setter, ghi đè B.

Một implementation đơn giản dùng `AbortController` theo effect:

```tsx
useEffect(() => {
  const controller = new AbortController();
  let active = true;

  setLoading(true);
  setError(null);

  (async () => {
    try {
      const response = await fetch(
        `/api/products?categoryId=${encodeURIComponent(categoryId)}`,
        { signal: controller.signal }
      );

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`);
      }

      const data = await response.json();

      if (active) {
        setProducts(data);
      }
    } catch (error) {
      if (active && !(error instanceof DOMException && error.name === "AbortError")) {
        setError(error instanceof Error ? error.message : "Unknown error");
      }
    } finally {
      if (active) {
        setLoading(false);
      }
    }
  })();

  return () => {
    active = false;
    controller.abort();
  };
}, [categoryId]);
```

`active` biểu diễn quyền commit state của effect instance; abort cố dừng work cũ. Có thể dùng monotonically increasing request ID thay cho boolean khi abstraction phức tạp hơn. Nếu dùng server-state library, query key nên bao gồm `categoryId` và lifecycle/cancellation nên theo contract của library.

Để verify, test deterministic: giữ response A pending, trigger B, resolve B trước rồi A sau; UI cuối phải vẫn là B và loading/error phải phản ánh request hiện hành. Test thêm unmount, abort, HTTP error và rapid filter changes. Browser Network panel giúp xác nhận request order/completion; frontend telemetry có thể ghi request generation/category/duration nhưng tránh logging dữ liệu nhạy cảm.

## Mẫu trả lời trong phỏng vấn

“Assumption sai là Promise callbacks của các request độc lập chạy theo thứ tự request được tạo. A có thể start trước nhưng network response A về sau B. Khi B resolve, continuation set data B; sau đó closure của effect A vẫn tồn tại và set data A, nên React chỉ đang thực hiện state update hợp lệ nhưng stale về mặt business.

Tôi sẽ làm ownership explicit: mỗi effect tạo `AbortController`; cleanup khi `categoryId` đổi sẽ invalidate effect cũ và abort request cũ. Chỉ effect còn active mới được set data, error hoặc loading. Debounce có thể giảm volume nhưng không phải correctness guarantee.

Tôi sẽ test bằng deferred responses: cho A pending, resolve B trước rồi A, và assert UI vẫn là B. Nếu backend work đắt, tôi cũng kiểm tra cancellation token có được propagate phía API/downstream hay không, nhưng client abort không được coi là rollback cho side effects.”

## Câu hỏi đào sâu

1. Nếu bạn chỉ dùng `AbortController` mà không có explicit result ownership, trong abstraction phức tạp hơn còn race nào cần cân nhắc?
2. Nếu endpoint đổi từ GET sang command có side effect, cancellation phía browser có đủ để đảm bảo operation không xảy ra không?
3. Nếu team đề xuất debounce 300 ms và bỏ cancellation vì “đã giảm request”, bạn đồng ý hay phản biện thế nào?

## Lỗi trả lời thường gặp

- Cho rằng Promise hoặc event loop đảm bảo FIFO theo request start order.
- Dùng debounce như correctness guarantee.
- Cancel request nhưng vẫn cho request cũ cập nhật `loading`/`error` state.
- Đổ lỗi cho backend dù từng response đúng với input của nó.
- Dùng timeout ngẫu nhiên trong test nên race test flaky.

## Thang điểm 0–10

- **0–2:** Không dựng được timeline race.
- **3–4:** Nhận ra stale request nhưng chỉ thêm debounce.
- **5–6:** Hiểu network/Promise ordering và implement cancellation/invalidation đúng.
- **7–8:** Quản lý toàn bộ data/error/loading ownership, deterministic tests và backend cancellation implications.
- **9–10:** Giải thích rõ event loop vs I/O completion, thiết kế reusable request-state semantics và trade-offs với server-state abstractions.

# Câu 2 — Cosmos DB RU tăng đột biến sau khi thêm dashboard đa tenant

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, RU consumption, query patterns, indexing, throttling, ASP.NET Core, observability, production troubleshooting

## Bối cảnh

Một multi-tenant event-management backend lưu `Registration` documents trong Azure Cosmos DB. API chính trước đây luôn truy vấn theo `tenantId` và `eventId`. Sau release mới, team thêm dashboard cho operations để tìm registrations theo `email`, `status`, khoảng thời gian và sort theo `createdAt` trên nhiều tenant.

Ngay sau rollout, p95 API latency tăng mạnh, RU consumption tăng nhiều lần và một số request bị throttling. CPU của ASP.NET Core App Service vẫn thấp. Team đề xuất tăng provisioned throughput ngay và thêm Redis để cache dashboard.

Chưa biết partition key hiện tại, query metrics, index policy, số partitions, data distribution, request frequency hay dashboard freshness SLA. Dashboard được dùng ít hơn API customer-facing nhưng một query có thể quét tập dữ liệu lớn.

## Câu hỏi chính

Bạn sẽ stabilize và điều tra incident thế nào để phân biệt partition fan-out, inefficient query/indexing, hot partition, pagination/sort cost, retry amplification và application-side behavior? Sau khi có evidence, bạn sẽ quyết định giữa thay query, index, data model/projection, throughput scaling hoặc cache như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Partition key hiện tại là gì và distribution/storage/request rate theo partition ra sao?
2. Dashboard query có partition-key equality hay trở thành cross-partition query?
3. RU charge, query metrics và continuation behavior của từng query shape là gì?
4. SDK/app retry/throttling telemetry cho thấy bao nhiêu 429 và tổng latency bị retry khuếch đại ra sao?
5. Dashboard cần freshness/consistency mức nào và operations có thực sự cần arbitrary cross-tenant search không?

## Gợi ý tư duy

### Gợi ý 1

CPU web thấp không loại trừ data-store bottleneck. Hãy bắt đầu từ request charge, partition distribution và query shape.

### Gợi ý 2

Một query thuận tiện cho UI có thể không phù hợp với partition model tối ưu cho transactional access path hiện tại.

### Gợi ý 3

Đừng mặc định sửa một access pattern mới bằng cách phá partition key tốt cho workload chính. Có thể cần một read model/projection riêng nếu requirement thực sự khác bản chất.

## Cấu trúc trả lời đề xuất

1. Định lượng user/business impact và bảo vệ customer traffic.
2. Stabilize dashboard traffic/concurrency nếu cần.
3. Thu RU/query/partition/throttling evidence.
4. Lập competing hypotheses.
5. Reproduce từng query shape với representative data.
6. Xác định access pattern và ownership thực sự.
7. So sánh query/index/model/projection/scale/cache options.
8. Rollout fix có guardrail.
9. Test load/failure/correctness.
10. Monitor RU efficiency và latency sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tăng throughput hoặc thêm Redis trước khi biết RU được tiêu ở đâu.
- Xác định partition key và việc query có target một logical partition hay fan-out.
- Đo request charge/query metrics theo query shape, p95/p99, 429/throttling và retry behavior.
- Kiểm tra data/request skew để phân biệt expensive cross-partition query với hot partition.
- Pagination phải dùng continuation semantics phù hợp; không giả định offset-style deep pagination là miễn phí.
- Index policy phải dựa trên query patterns; thêm index cũng có write/storage cost.
- Nếu dashboard access pattern fundamentally khác transactional path, cân nhắc derived read model/search projection thay vì đổi primary model mù quáng.

### Điểm cộng

- Tạm rate-limit/constrain dashboard để bảo vệ customer-facing workload trong incident.
- Cache chỉ hợp lý nếu repeated queries, freshness và invalidation economics chứng minh giá trị; arbitrary high-cardinality filters có thể có hit ratio thấp.
- Search-oriented workload theo email/status/time trên nhiều tenant có thể phù hợp với projection/search system, nhưng cần consistency/rebuild/failure semantics.
- Autoscale/provisioned throughput có thể là một capacity tool, không phải substitute cho query efficiency.
- Theo dõi RU per successful business operation, không chỉ tổng RU.

### Senior+

- Phân biệt logical partition design, physical partition behavior và workload skew mà không suy diễn metric chưa có.
- Thiết kế projection eventual consistency với checkpoint/rebuild và visibility của lag nếu business cho phép.
- Xử lý retry amplification: throttling + aggressive retries có thể tăng latency/load perception; cần bounded behavior theo SDK/service guidance thực tế.

## Hướng giải quyết tham khảo

Tôi sẽ bảo vệ customer-facing traffic trước. Nếu dashboard là nguồn tải mới và không critical, có thể tạm giảm concurrency, rate-limit hoặc disable expensive filter combinations trong khi thu evidence. Tôi không thêm Redis ngay vì query combinations có thể high-cardinality và cache hit ratio rất thấp.

Investigation bắt đầu bằng partition key, request charge và query metrics cho từng shape. Tôi so sánh baseline API cũ với dashboard mới: query nào target partition, query nào cross-partition; RU/query; documents/index entries examined; latency; continuation pages; 429; retry duration. Đồng thời xem request distribution theo tenant/partition để phát hiện hot key.

Các hypothesis gồm: cross-partition fan-out; filter/sort không được index phù hợp; deep pagination; một tenant quá nóng; dashboard frontend gửi duplicate queries; throttling gây retry amplification; hoặc data volume distribution khác assumption. Mỗi hypothesis phải có metric/query trace chứng minh.

Nếu chỉ một vài query shape sai, tối ưu query và indexing trước. Index mới phải được đánh giá cả read benefit lẫn write/storage cost. Nếu operations thực sự cần arbitrary cross-tenant search theo nhiều dimensions, tôi không nhất thiết đổi partition key của transactional container vì có thể làm hỏng workload chính. Một derived read model hoặc Elasticsearch/search projection có thể phù hợp hơn nếu team chấp nhận eventual consistency và operational complexity. Projection cần idempotent updates, lag metric, retry và rebuild path.

Nếu query đã hiệu quả nhưng workload hợp lệ vượt capacity, tăng throughput là capacity decision có cơ sở. Cache chỉ thêm khi đo được repeated access và freshness SLA cho phép. Nếu dashboard data có thể trễ 1–5 phút, materialized projection/cache có nhiều lựa chọn hơn so với strong real-time requirement.

Test gồm representative data distribution, worst-case filters, pagination, concurrent dashboard users, hot-tenant simulation và throttling/failure behavior. Production alert trên RU/request, normalized RU per business operation, 429 rate, p95/p99, cross-partition expensive-query signatures và projection lag nếu có.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tăng RU hay thêm Redis trước khi biết access pattern nào tạo cost. Vì customer API bị ảnh hưởng bởi dashboard mới, tôi ưu tiên stabilize bằng cách giới hạn dashboard concurrency/query shape nếu cần, rồi đo request charge, query metrics, partition distribution, 429 và retry latency.

Tôi cần biết partition key. Nếu API cũ luôn target tenant nhưng dashboard mới search xuyên tenant, đây có thể là fan-out workload fundamentally khác. Tôi sẽ phân biệt nó với hot partition và indexing/sort problem bằng metrics thực tế.

Nếu query có thể tối ưu bằng predicate/index thì làm ở đó. Nếu requirement là arbitrary cross-tenant search, tôi cân nhắc read/search projection thay vì phá partition model của transactional workload. Throughput scaling chỉ sau khi query đã hợp lý; Redis chỉ khi hit ratio/freshness/invalidation chứng minh đáng giá. Sau fix tôi theo dõi RU per successful operation, 429, p95/p99 và nếu có projection thì cả index lag.”

## Câu hỏi đào sâu

1. Nếu partition key hiện tại tối ưu hoàn hảo cho customer workload nhưng operations bắt buộc search toàn bộ tenants real-time, bạn đánh đổi consistency/cost/complexity thế nào?
2. Nếu tăng throughput làm 429 biến mất nhưng RU per dashboard query vẫn rất cao, bạn coi incident đã được giải quyết chưa?
3. Nếu team muốn Redis cache mọi combination của email/status/date filters, bạn yêu cầu số liệu nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- Thêm Redis ngay mà không đo cacheability.
- Kết luận “partition key sai” chỉ vì có cross-partition query mới.
- Chỉ tăng RU mà không đo RU/query.
- Không kiểm tra duplicate frontend calls hoặc retry amplification.
- Đề xuất projection nhưng bỏ qua lag, rebuild và failure recovery.

## Thang điểm 0–10

- **0–2:** Chỉ scale throughput hoặc thêm cache.
- **3–4:** Biết xem partition key nhưng chưa có evidence-driven investigation.
- **5–6:** Phân tích RU/query, partition/fan-out/index/throttling đúng và có stabilization.
- **7–8:** So sánh data-model/projection/cache/scale bằng workload và consistency requirements.
- **9–10:** Thiết kế incident + long-term access-pattern architecture với cost, retry, observability và recovery trade-offs rõ ràng.

# Câu 3 — Thiết kế dịch vụ upload tài liệu lớn: API proxy hay direct-to-Blob?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS concepts, security, large-file upload, asynchronous processing, SQL metadata, reliability, observability, deployment, failure recovery

## Bối cảnh

Một internal document platform cần cho web client upload PDF/ZIP từ vài MB đến vài GB. Hiện tại browser gửi multipart file qua ASP.NET Core API; API đọc stream rồi upload sang Azure Blob Storage. Khi file lớn và nhiều người upload cùng lúc, App Service bandwidth/memory/connection pressure tăng, request dễ timeout và deployment/restart làm upload đang chạy thất bại.

Business muốn hỗ trợ upload lớn đáng tin cậy, progress UI, virus/malware scanning trước khi file được người khác tải xuống, authorization theo project và audit trail. Team đang cân nhắc hai hướng:

1. tiếp tục proxy toàn bộ bytes qua backend;
2. backend cấp quyền upload có giới hạn để browser upload trực tiếp Blob Storage, sau đó backend hoàn tất workflow.

Chưa biết exact file-size distribution, concurrency, compliance requirement, browser/network reliability hay liệu client có được phép kết nối trực tiếp tới storage endpoint.

## Câu hỏi chính

Hãy thiết kế upload workflow và so sánh backend-proxy với direct-to-Blob. Nếu chọn direct upload, bạn sẽ thiết kế authorization, short-lived upload permission, blob naming, metadata/state machine, completion verification, scanning/quarantine, retry/resume, cleanup và download authorization như thế nào? Khi nào proxy qua backend vẫn là lựa chọn đúng hơn?

## Câu hỏi làm rõ nên cân nhắc

1. File-size/concurrency distribution và upload success SLO là gì?
2. Network/compliance policy có cho browser truy cập storage endpoint trực tiếp không?
3. File có được phép tải xuống trước khi scan hoàn tất không và scan SLA là bao lâu?
4. Có cần resumable/chunked upload qua unstable network không?
5. Authorization là theo user/project/file và download có public/shared-link use case hay hoàn toàn private?

## Gợi ý tư duy

### Gợi ý 1

Tách **control plane** khỏi **data plane**: backend có thể quyết định ai được upload mà không nhất thiết chuyển từng byte.

### Gợi ý 2

Direct upload không có nghĩa client được quyền rộng trên storage. Permission phải giới hạn resource, operation và thời gian.

### Gợi ý 3

“Blob tồn tại” chưa đồng nghĩa “document hợp lệ và có thể publish”. Hãy thiết kế explicit lifecycle từ initiated đến verified/scanned/available.

## Cấu trúc trả lời đề xuất

1. Làm rõ constraints và threat model.
2. So sánh proxy/direct data path.
3. Xác định control-plane APIs và authorization.
4. Thiết kế storage naming/permissions.
5. Thiết kế upload lifecycle/state machine.
6. Thiết kế scan/quarantine và async processing.
7. Xử lý retries, duplicate completion và orphan cleanup.
8. Thiết kế download authorization.
9. Test security/failure/load paths.
10. Thiết kế telemetry/SLO và deployment behavior.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không để browser có storage account key hoặc credential dài hạn.
- Backend authenticate/authorize user trước khi cấp upload capability; capability phải giới hạn đúng resource/operation/time theo mechanism được platform hỗ trợ.
- Blob key/path không được dùng như authorization boundary duy nhất.
- Metadata/database record cần state rõ như `Initiated → Uploaded → Scanning → Available/Rejected/Failed` thay vì coi upload thành công là publish thành công.
- File chưa scan phải nằm trong quarantine/logical unavailable state và download path phải enforce state/authorization.
- Completion callback từ client không được tin mù; backend cần verify blob properties/expected upload identity và enforce size/type/business constraints phù hợp.
- Retry/completion phải idempotent; abandoned uploads cần cleanup lifecycle.
- Direct upload giảm bytes đi qua App Service và tách upload durability khỏi web-process lifetime, nhưng tăng client/storage workflow complexity.

### Điểm cộng

- Backend-to-storage access nên dùng Managed Identity/least privilege thay vì static secrets khi environment hỗ trợ.
- Large uploads có thể dùng block/chunk semantics và retry từng phần theo SDK/platform capabilities đã xác minh.
- Content type/file extension không đủ để chứng minh file an toàn; scanning pipeline và download disposition cần threat-model phù hợp.
- Async scan có thể dùng queue/event/workflow, nhưng không cần messaging nếu scale đơn giản và polling/job đủ đáp ứng; complexity phải được biện minh.
- Có immutable audit events hoặc durable audit data cho initiate/complete/scan/download decisions tùy compliance.

### Senior+

- Xử lý race: client gọi complete hai lần; upload permission hết hạn giữa chừng; blob upload xong nhưng completion API fail; scan worker crash; file bị thay đổi sau verification nếu permission còn write.
- Thiết kế untrusted-to-trusted promotion: quarantine container/path và publish/copy/move/logical state theo storage semantics phù hợp.
- Download cũng là capability decision: backend authorization + short-lived read capability hoặc backend streaming tùy policy; direct upload không bắt buộc direct download.

## Hướng giải quyết tham khảo

Với file tới vài GB và concurrency đáng kể, tôi ưu tiên tách control plane khỏi data plane nếu compliance/network cho phép. ASP.NET Core API authenticate user, kiểm tra quyền project, tạo `DocumentUpload` record với server-generated document/blob identity và trạng thái `Initiated`, sau đó cấp một short-lived upload capability chỉ cho blob cụ thể và operation cần thiết. Client không nhận account key.

Browser upload trực tiếp storage. Với file lớn, client dùng upload mechanism hỗ trợ chunk/block và retry/resume phù hợp với SDK/storage contract. Backend không coi callback “done” là bằng chứng duy nhất. Client gọi completion API bằng upload ID; server authorize lại, kiểm tra record state và verify blob tồn tại/properties cần thiết. Completion endpoint phải idempotent.

Sau verification, document chuyển `Uploaded/Scanning`. File chưa được phép download. Scanner chạy asynchronous; nếu clean thì state thành `Available`, nếu malicious/invalid thì `Rejected` và retention/deletion theo policy. Nếu scanner crash, work phải retry/reconcile mà không publish file trước khi có kết quả. Nếu messaging được dùng, consumer cần idempotency; nhưng với volume thấp, một durable scheduled scanner có thể đơn giản hơn.

Storage naming dùng opaque server-generated IDs thay vì raw user filenames. Original filename là metadata đã sanitize/encode khi hiển thị. Authorization dựa trên application/project policy, không dựa trên việc user đoán được URL. Backend access storage bằng Managed Identity và least privilege khi phù hợp.

Upload permission cần scope/time nhỏ nhất đáp ứng UX. Sau completion, không nên để client tiếp tục có khả năng mutate trusted object ngoài intended window. Có thể dùng quarantine location và promotion/logical lock sau scan tùy storage workflow. Cần verify exact platform semantics trước implementation thay vì giả định rename/atomic behavior.

Failure cases:

- permission hết hạn: backend có thể issue capability mới cho cùng upload session nếu policy cho phép;
- blob hoàn tất nhưng completion API fail: client retry completion; endpoint idempotent;
- completion chưa bao giờ tới: reconciliation job phát hiện orphan blob/session;
- scan fail transient: retry bounded + alert; permanent failure chuyển state rõ;
- deployment/restart backend: upload bytes vẫn tiếp tục giữa browser/storage nếu capability còn hợp lệ; control-plane operations có thể retry;
- duplicate upload attempt: document/upload session IDs và state transition bảo vệ workflow.

Download có thể backend authorize rồi cấp short-lived read capability, hoặc proxy stream nếu compliance yêu cầu bytes đi qua application/control point. Chỉ `Available` document mới được tải. Audit ghi actor, document, project, action, result và correlation ID phù hợp policy.

Proxy backend vẫn hợp lý nếu network policy cấm direct storage, application bắt buộc transform/inspect stream inline, file nhỏ/volume thấp khiến complexity direct upload không đáng, hoặc compliance yêu cầu central gateway. Nhưng với multi-GB uploads, proxy tạo double network hop và buộc web tier chịu long-lived data-plane traffic, nên phải có lý do rõ.

Tests: authorization isolation giữa projects; expired/over-scoped capability; multi-GB/chunk retry; blob-complete nhưng API-complete fail; duplicate completion; malicious file remains unavailable; scanner crash/retry; orphan cleanup; load test concurrent uploads; deployment during upload. Telemetry gồm initiated/completed/abandoned count, bytes, upload duration, completion verification failures, scan queue age/duration/result, orphan count, download-denied reasons và storage/API dependency errors.

## Mẫu trả lời trong phỏng vấn

“Với file vài GB, nếu policy cho phép tôi sẽ tách control plane khỏi data plane. Backend vẫn authenticate và authorize project, tạo upload session/blob ID và cấp capability ngắn hạn chỉ cho blob/operation cần thiết; browser không bao giờ nhận account key. Bytes đi trực tiếp tới Blob Storage nên App Service không phải giữ connection và forward toàn bộ payload.

Tôi không coi upload xong là document available. Database có state `Initiated`, `Uploaded`, `Scanning`, rồi `Available` hoặc `Rejected`. Completion API idempotent và backend verify blob trước khi chuyển state. File ở quarantine và download authorization chỉ cho phép state `Available`. Scanner chạy async, có retry/reconciliation; orphan sessions được cleanup.

Direct upload tăng workflow complexity nên nếu file nhỏ, volume thấp hoặc compliance bắt buộc proxy thì backend streaming vẫn có thể đúng. Tôi sẽ quyết định bằng file-size/concurrency, network policy, security và operational cost chứ không mặc định một pattern.”

## Câu hỏi đào sâu

1. Nếu security team cấm browser kết nối trực tiếp storage endpoint, bạn thiết kế proxy path thế nào để vẫn tránh buffering multi-GB files trong memory?
2. Nếu upload capability còn quyền write sau khi scanner đánh dấu file clean, attacker có thể tạo race gì và bạn đóng boundary đó thế nào?
3. Nếu volume chỉ 20 file/ngày, mỗi file dưới 10 MB, bạn có vẫn chọn direct-to-Blob workflow đầy đủ không? Vì sao?

## Lỗi trả lời thường gặp

- Gửi storage account key cho browser.
- Dùng blob URL khó đoán như authorization.
- Cho download ngay khi upload hoàn tất, trước scan.
- Tin completion callback mà không verify server-side state/blob.
- Thêm queue/microservice/Kubernetes mặc định dù workload không cần.

## Thang điểm 0–10

- **0–2:** Chỉ nói “dùng Blob Storage” mà không có security/lifecycle.
- **3–4:** Có direct upload nhưng permission hoặc state boundary còn mơ hồ.
- **5–6:** Có scoped capability, metadata state, verification, scan và download authorization.
- **7–8:** Xử lý retries/orphans/races, Managed Identity, tests và observability.
- **9–10:** Thiết kế control/data plane rõ, threat model đầy đủ, failure recovery tốt và biết khi proxy đơn giản hơn là lựa chọn đúng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async UI correctness phụ thuộc ownership của result; request start order không tạo response completion order.
- Event loop/Promise scheduling không thay thế application-level stale-result protection.
- Cosmos DB performance phải được điều tra từ access pattern, partitioning, RU/query và throttling evidence trước khi scale/cache.
- Một access pattern cross-tenant/search mới có thể cần projection riêng thay vì phá primary transactional data model.
- Với large-file upload, tách control plane khỏi data plane có thể giảm web-tier pressure nhưng đòi hỏi authorization capability, state machine, quarantine và recovery rõ ràng.

## Mẫu tư duy cần nhớ

- **Async result chỉ được commit nếu owner của nó vẫn còn hiện hành.**
- **Measure cost per operation before scaling capacity.**
- **Protect the primary access pattern; add a projection when a new workload is fundamentally different.**
- **Separate upload completion from trust/publish state.**
- **Choose complexity from constraints and failure modes, not from pattern popularity.**
