# Code Review Challenge 1 — EF Core query trả đúng dữ liệu nhưng bùng nổ row, memory và latency khi dữ liệu lớn

**Chủ đề:** EF Core tracking, query execution, performance, memory/allocation, SQL correctness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API dashboard tải thông tin một project cùng employees, timesheets, tasks và tags để dựng màn hình tổng quan. Với project nhỏ, endpoint chạy dưới 300 ms. Với project lớn có 300–500 employees, vài chục nghìn timesheet entries và nhiều task/tag, latency tăng lên 8–20 giây, memory process tăng mạnh và SQL Server/PostgreSQL đều ghi nhận lượng rows trả về rất lớn.

Production còn có các triệu chứng:

- CPU application tăng trong lúc materialize object graph,
- GC hoạt động nhiều,
- một số request bị timeout,
- query log nhìn qua chỉ thấy một câu SQL nhưng số rows đọc lớn bất thường,
- endpoint chỉ đọc dữ liệu nhưng Change Tracker vẫn chứa hàng nghìn entity,
- team cho rằng “một query luôn nhanh hơn nhiều query” nên cố gắng `Include` tất cả navigation trong một lần.

Business chỉ cần dữ liệu tóm tắt cho dashboard; không cần toàn bộ entity graph và không sửa dữ liệu trong request này.

## Đoạn code cần review

```csharp
public sealed class ProjectDashboardService
{
    private readonly AppDbContext _db;

    public ProjectDashboardService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<ProjectDashboardDto> GetAsync(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        var project = await _db.Projects
            .Include(x => x.Employees)
                .ThenInclude(x => x.Timesheets)
            .Include(x => x.Tasks)
                .ThenInclude(x => x.Tags)
            .Include(x => x.Tasks)
                .ThenInclude(x => x.Assignees)
            .SingleAsync(
                x => x.Id == projectId,
                cancellationToken);

        return new ProjectDashboardDto
        {
            ProjectId = project.Id,
            ProjectName = project.Name,
            EmployeeCount = project.Employees.Count,
            TotalHours = project.Employees
                .SelectMany(x => x.Timesheets)
                .Sum(x => x.Hours),
            OpenTaskCount = project.Tasks.Count(x => !x.IsCompleted),
            TagNames = project.Tasks
                .SelectMany(x => x.Tags)
                .Select(x => x.Name)
                .Distinct()
                .OrderBy(x => x)
                .ToArray(),
            AssigneeCount = project.Tasks
                .SelectMany(x => x.Assignees)
                .Select(x => x.EmployeeId)
                .Distinct()
                .Count()
        };
    }
}
```

## Kết quả code review tham khảo

### 1. Eager-load nhiều collection có thể gây cartesian explosion

**Problem:** Nhiều collection navigation được join trong cùng query.  
**Why it happens:** Mỗi tổ hợp employee/timesheet/task/tag/assignee có thể tạo thêm rows trung gian.  
**Production impact:** Database đọc và truyền lượng dữ liệu lớn hơn nhiều so với dữ liệu logic cần trả; latency, network I/O và memory tăng mạnh.  
**Severity:** High  
**Recommended fix:** Tránh load toàn graph. Projection trực tiếp sang DTO hoặc chia query hợp lý khi cần nhiều collection thực sự.

### 2. Materialize hàng nghìn entity chỉ để tính aggregate

**Problem:** Toàn bộ timesheet/task/tag/assignee được load rồi mới `Count`, `Sum`, `Distinct`.  
**Why it happens:** Aggregate chạy trên collection đã materialize.  
**Production impact:** Tăng allocation, GC và thời gian materialization.  
**Severity:** High  
**Recommended fix:** Dùng LINQ projection để database tính aggregate và chỉ trả scalar/collection nhỏ cần thiết.

### 3. Query read-only nhưng vẫn tracking entity

**Problem:** Không dùng no-tracking cho một request chỉ đọc.  
**Why it happens:** EF Core mặc định tracking entity query.  
**Production impact:** Change Tracker giữ state cho lượng entity lớn, tăng memory và CPU.  
**Severity:** High  
**Recommended fix:** Dùng projection không materialize entity hoặc `AsNoTracking()` khi phải load entity read-only.

### 4. Payload dữ liệu từ DB lớn hơn nhiều so với DTO cuối cùng

**Problem:** Query đọc nhiều cột/entity nhưng output chỉ vài aggregate và tag names.  
**Why it happens:** Thiết kế query theo domain graph thay vì nhu cầu read model.  
**Production impact:** Lãng phí DB I/O, network và application memory.  
**Severity:** High  
**Recommended fix:** Tạo read-model query chuyên biệt cho dashboard.

### 5. `SingleAsync` trên object graph lớn làm toàn bộ query phải hoàn thành trước khi tạo DTO

**Problem:** Request phụ thuộc vào materialization đầy đủ một graph lớn.  
**Why it happens:** Aggregate được tính sau khi entity graph đã load.  
**Production impact:** Không có lợi ích streaming thực tế; timeout xảy ra trước khi application bắt đầu trả dữ liệu.  
**Severity:** Medium  
**Recommended fix:** Tách các aggregate thành query tối ưu hoặc projection duy nhất nếu provider dịch tốt.

### 6. Không giới hạn phạm vi timesheet theo nhu cầu business

**Problem:** Mọi timesheet lịch sử của employees trong project đều được load.  
**Why it happens:** Requirement dashboard chưa được biến thành filter dữ liệu cụ thể.  
**Production impact:** Dataset tăng theo thời gian, latency xấu dần dù số employee không đổi.  
**Severity:** Medium  
**Recommended fix:** Làm rõ dashboard cần all-time hay khoảng thời gian; filter sớm tại database.

### 7. Không có explicit strategy cho multiple collection queries

**Problem:** Team giả định “một query luôn tốt hơn nhiều query”.  
**Why it happens:** Bỏ qua trade-off giữa round-trip và row multiplication.  
**Production impact:** Một SQL statement có thể tệ hơn vài query nhỏ hơn nếu join fan-out quá lớn.  
**Severity:** Medium  
**Recommended fix:** Đo actual row count/plan; dùng projection trước, split query khi phù hợp và hiểu consistency trade-off.

### 8. Thiếu metric về rows/materialization/query duration theo endpoint

**Problem:** Chỉ nhìn latency tổng nên khó biết bottleneck ở DB, network hay materialization.  
**Why it happens:** Observability chưa gắn với query shape.  
**Production impact:** Dễ tối ưu sai chỗ.  
**Severity:** Medium  
**Recommended fix:** Theo dõi DB duration, rows read/returned khi có thể, request allocation/memory, GC, query count và endpoint latency percentile.

## Phiên bản code đề xuất

```csharp
public sealed class ProjectDashboardService
{
    private readonly AppDbContext _db;

    public ProjectDashboardService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<ProjectDashboardDto> GetAsync(
        Guid projectId,
        DateTime fromUtc,
        CancellationToken cancellationToken)
    {
        var summary = await _db.Projects
            .AsNoTracking()
            .Where(x => x.Id == projectId)
            .Select(x => new
            {
                x.Id,
                x.Name,
                EmployeeCount = x.Employees.Count(),
                TotalHours = x.Employees
                    .SelectMany(e => e.Timesheets)
                    .Where(t => t.WorkDate >= fromUtc)
                    .Sum(t => (decimal?)t.Hours) ?? 0,
                OpenTaskCount = x.Tasks.Count(t => !t.IsCompleted),
                AssigneeCount = x.Tasks
                    .SelectMany(t => t.Assignees)
                    .Select(a => a.EmployeeId)
                    .Distinct()
                    .Count()
            })
            .SingleAsync(cancellationToken);

        var tagNames = await _db.Tasks
            .AsNoTracking()
            .Where(t => t.ProjectId == projectId)
            .SelectMany(t => t.Tags)
            .Select(t => t.Name)
            .Distinct()
            .OrderBy(x => x)
            .ToArrayAsync(cancellationToken);

        return new ProjectDashboardDto
        {
            ProjectId = summary.Id,
            ProjectName = summary.Name,
            EmployeeCount = summary.EmployeeCount,
            TotalHours = summary.TotalHours,
            OpenTaskCount = summary.OpenTaskCount,
            TagNames = tagNames,
            AssigneeCount = summary.AssigneeCount
        };
    }
}
```

## Trade-offs

Projection giảm mạnh dữ liệu materialize và thường là lựa chọn tốt nhất cho read model, nhưng query aggregate quá phức tạp vẫn cần kiểm tra execution plan. Hai query riêng tạo thêm round-trip và có thể thấy dữ liệu thay đổi giữa hai lần đọc nếu cần snapshot consistency nghiêm ngặt. Nếu business cần snapshot tuyệt đối đồng nhất, có thể cân nhắc transaction/isolation phù hợp hoặc materialized read model.

`AsSplitQuery` hữu ích khi thực sự phải materialize nhiều collection navigation, nhưng không nên dùng như cách chữa mặc định nếu bản chất endpoint chỉ cần aggregate.

# Code Review Challenge 2 — Metric gắn `UserId`, URL và exception message làm nổ cardinality, chi phí và có thể lộ dữ liệu

**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một ASP.NET Core API đã thêm custom metrics để theo dõi request theo tenant, user, route và lỗi. Sau vài tuần production, backend metrics tăng storage rất nhanh, dashboard query chậm, cardinality vượt dự kiến và chi phí observability tăng mạnh.

Team còn phát hiện:

- metric labels chứa `UserId`, raw URL và query string,
- exception message đôi lúc chứa email, token fragment hoặc dữ liệu từ downstream,
- mỗi request tự tạo `Meter` và `Counter`,
- metric `request_duration_ms` dùng `Counter<long>` nên không thể quan sát distribution đúng nghĩa,
- route được lấy từ `Request.Path`, khiến `/employees/{id}` tạo label value khác nhau theo từng id,
- tenant mới có thể làm tăng hàng loạt time series.

Business vẫn cần biết latency/error rate theo endpoint và tenant tier, nhưng không cần metric theo từng user cụ thể.

## Đoạn code cần review

```csharp
public sealed class RequestMetricsMiddleware
{
    private readonly RequestDelegate _next;

    public RequestMetricsMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var meter = new Meter("Company.Api.Requests");
        var requests = meter.CreateCounter<long>("http_requests_total");
        var duration = meter.CreateCounter<long>("request_duration_ms");
        var errors = meter.CreateCounter<long>("http_errors_total");

        var started = Stopwatch.GetTimestamp();

        try
        {
            await _next(context);

            requests.Add(1,
                new("tenant", context.Request.Headers["X-Tenant-Id"].ToString()),
                new("user", context.User.FindFirst("sub")?.Value ?? "anonymous"),
                new("route", context.Request.Path.ToString()),
                new("url", context.Request.GetDisplayUrl()),
                new("status", context.Response.StatusCode));
        }
        catch (Exception ex)
        {
            errors.Add(1,
                new("tenant", context.Request.Headers["X-Tenant-Id"].ToString()),
                new("route", context.Request.Path.ToString()),
                new("error", ex.Message));

            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            duration.Add((long)elapsed.TotalMilliseconds,
                new("tenant", context.Request.Headers["X-Tenant-Id"].ToString()),
                new("user", context.User.FindFirst("sub")?.Value ?? "anonymous"),
                new("route", context.Request.Path.ToString()));
        }
    }
}
```

## Kết quả code review tham khảo

### 1. `UserId` tạo cardinality gần như không giới hạn

**Problem:** Mỗi user có thể tạo một series riêng cho mỗi metric/tag combination.  
**Why it happens:** Metric dùng identity-level dimension.  
**Production impact:** Tăng memory/storage/backend cost, dashboard chậm và có thể vượt quota của hệ thống telemetry.  
**Severity:** High  
**Recommended fix:** Loại `user` khỏi metric tags; dùng trace/log correlation khi cần điều tra user cụ thể.

### 2. Raw URL và `Request.Path` tạo cardinality theo resource id/query string

**Problem:** `/employees/123` và `/employees/456` thành các label values khác nhau.  
**Why it happens:** Dùng path/url thực tế thay vì route template.  
**Production impact:** Số time series tăng theo dữ liệu nghiệp vụ.  
**Severity:** High  
**Recommended fix:** Tag bằng route template ổn định như `/employees/{id}`; không đưa raw URL/query string vào metrics.

### 3. Exception message được dùng làm metric tag

**Problem:** Message có cardinality cao và có thể chứa dữ liệu nhạy cảm.  
**Why it happens:** Metric được dùng như error log.  
**Production impact:** Bùng cardinality, rò dữ liệu và khó aggregate lỗi theo loại.  
**Severity:** High  
**Recommended fix:** Tag bằng exception type/error code có tập giá trị giới hạn; chi tiết message chỉ ở log được redaction phù hợp.

### 4. Duration dùng `Counter<long>` sai semantics

**Problem:** Cộng tổng milliseconds không biểu diễn distribution latency.  
**Why it happens:** Chọn instrument không phù hợp.  
**Production impact:** Không tính percentile/histogram tốt, khó phát hiện tail latency.  
**Severity:** High  
**Recommended fix:** Dùng `Histogram<double>` hoặc instrument phù hợp cho duration.

### 5. Tạo `Meter` và instruments trên mỗi request

**Problem:** Mỗi invocation tạo object mới thay vì reuse instruments.  
**Why it happens:** Telemetry lifecycle gắn sai vào request lifecycle.  
**Production impact:** Allocation/overhead không cần thiết và khó quản lý registration.  
**Severity:** Medium  
**Recommended fix:** Tạo `Meter`/instruments một lần trong singleton/static metrics holder hoặc qua DI.

### 6. Tenant id lấy trực tiếp từ header không phải identity đáng tin

**Problem:** Tag tenant dựa trên header user-controlled nếu chưa được validate/enrich ở upstream.  
**Why it happens:** Middleware dùng raw request input.  
**Production impact:** Cardinality injection và metrics sai tenant.  
**Severity:** Medium  
**Recommended fix:** Lấy tenant context đã xác thực từ application identity/context; cân nhắc tag theo tenant tier/region thay vì tenant id nếu tenant count lớn.

### 7. Success counter chỉ ghi nếu pipeline không ném exception

**Problem:** Tổng request count và error count có semantics không đồng nhất nếu không định nghĩa rõ.  
**Why it happens:** `requests.Add` nằm trong success path.  
**Production impact:** Dashboard request/error rate dễ bị hiểu sai.  
**Severity:** Medium  
**Recommended fix:** Định nghĩa rõ metric: total requests ghi trong `finally`, status/error dimension riêng có bounded values.

### 8. Không giới hạn dimension `status`/route/error theo schema thống nhất

**Problem:** Metric contract chưa được chuẩn hóa.  
**Why it happens:** Instrumentation được thêm ad-hoc trong middleware.  
**Production impact:** Khó query và dễ tạo dimension khác nhau giữa service.  
**Severity:** Medium  
**Recommended fix:** Chuẩn hóa metric names, units và tag keys; ưu tiên semantic conventions phù hợp hệ observability đang dùng.

### 9. Metrics đang chứa dữ liệu phù hợp hơn với logs/traces

**Problem:** URL, user identity và exception detail bị nhét vào time-series metrics.  
**Why it happens:** Không phân biệt mục đích của metrics, logs và traces.  
**Production impact:** Vừa đắt vừa giảm khả năng aggregate.  
**Severity:** Medium  
**Recommended fix:** Metrics: low-cardinality aggregates; traces: request/dependency correlation; logs: structured event chi tiết với redaction.

## Phiên bản code đề xuất

```csharp
public sealed class ApiMetrics
{
    private readonly Meter _meter = new("Company.Api.Requests");

    public Counter<long> Requests { get; }
    public Histogram<double> DurationMs { get; }

    public ApiMetrics()
    {
        Requests = _meter.CreateCounter<long>("http.server.requests");
        DurationMs = _meter.CreateHistogram<double>(
            "http.server.request.duration",
            unit: "ms");
    }
}

public sealed class RequestMetricsMiddleware
{
    private readonly RequestDelegate _next;

    public RequestMetricsMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(
        HttpContext context,
        ApiMetrics metrics,
        ITenantContext tenantContext)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? failure = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            failure = ex;
            throw;
        }
        finally
        {
            var route = context.GetEndpoint()
                ?.Metadata
                .GetMetadata<RouteNameMetadata>()
                ?.RouteName
                ?? "unknown";

            var statusClass = $"{context.Response.StatusCode / 100}xx";
            var outcome = failure is null ? "success" : "error";
            var tenantTier = tenantContext.Tier ?? "unknown";

            metrics.Requests.Add(1,
                new("route", route),
                new("status_class", statusClass),
                new("outcome", outcome),
                new("tenant_tier", tenantTier));

            metrics.DurationMs.Record(
                Stopwatch.GetElapsedTime(started).TotalMilliseconds,
                new("route", route),
                new("status_class", statusClass),
                new("outcome", outcome),
                new("tenant_tier", tenantTier));
        }
    }
}
```

## Trade-offs

Loại user/tenant-id cụ thể khỏi metrics làm mất khả năng drill-down trực tiếp theo identity, nhưng đó thường là trade-off đúng để giữ cardinality hữu hạn. Khi cần điều tra một user/tenant cụ thể, dùng traces/logs có sampling, retention và access control phù hợp.

Nếu số tenant nhỏ và bounded, tenant id có thể chấp nhận trong một số metric chuyên biệt; nhưng quyết định này nên dựa trên số lượng tenant tối đa, retention và giới hạn backend telemetry thay vì thêm mặc định vào mọi metric.

## Cách kiểm thử

1. **Cardinality test:** sinh hàng chục nghìn user/resource ids và xác minh số tag values vẫn bounded.
2. **Integration test:** route parameter khác nhau vẫn ghi cùng route template/name.
3. **Metric correctness:** request success/error đều tăng total và duration histogram đúng.
4. **Security test:** URL/query string, user id và exception message không xuất hiện trong metric tags.
5. **Load test:** so allocation/CPU trước và sau khi reuse instruments.

## Quan sát trong production

Theo dõi số active time series, telemetry ingest rate/cost, dropped telemetry, dashboard query latency và cardinality theo tag key. Dùng traces để xem dependency latency, logs cho exception detail đã redaction, và metric histogram cho p50/p95/p99 endpoint latency.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào tenant id là metric tag hợp lý và khi nào nên dùng tenant tier?
2. Bạn phân chia thông tin nào vào metrics, logs và traces trong một incident thực tế?
3. Nếu cần debug một user cụ thể mà metric không còn user id, bạn thiết kế correlation thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với read-only dashboard, query nên được thiết kế theo dữ liệu đầu ra thay vì materialize toàn bộ domain graph.
- Nhiều collection `Include` có thể làm số row trung gian tăng mạnh; “một query” không đồng nghĩa với “ít công việc hơn”.
- Projection và aggregate tại database thường giảm đáng kể network, allocation và Change Tracker overhead.
- Observability cũng là một hệ thống phải thiết kế: metric dimensions cần bounded cardinality và semantics đúng.
- Metrics, logs và traces phục vụ mục đích khác nhau; không nên đưa identity/error detail tùy ý vào metric labels.

## Mẫu tư duy cần nhớ

- Query theo output cần dùng, không theo toàn bộ object graph.
- Measure rows, allocations và execution plan trước khi tối ưu.
- “Ít round-trip hơn” không tự động nghĩa là “nhanh hơn”.
- Metric tags phải bounded và ổn định.
- Dùng metrics cho aggregate, traces/logs cho chi tiết điều tra.
