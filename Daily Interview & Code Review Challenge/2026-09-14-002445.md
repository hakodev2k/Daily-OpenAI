# Câu 1 — `IQueryable` thoát khỏi scope và lỗi chỉ xuất hiện khi enumerate

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** C#, LINQ, EF Core, deferred execution, `IQueryable`, expression tree, `DbContext` lifetime, connection usage, async enumeration, API design

## Bối cảnh

Một ASP.NET Core application dùng EF Core để truy vấn SQL Server. Team có một query service nhằm tái sử dụng filter logic giữa API, scheduled export và admin screen.

Một method hiện trả về `IQueryable<Order>` để caller thêm filter hoặc projection. Trong một API endpoint, developer tạo một DI scope thủ công, lấy query service, nhận về `IQueryable`, dispose scope rồi mới gọi `ToListAsync()`.

Code rút gọn:

```csharp
public sealed class OrderQueryService
{
    private readonly AppDbContext _db;

    public OrderQueryService(AppDbContext db)
    {
        _db = db;
    }

    public IQueryable<Order> BuildOpenOrdersQuery(int tenantId)
    {
        return _db.Orders
            .Where(x => x.TenantId == tenantId)
            .Where(x => x.Status == OrderStatus.Open)
            .OrderByDescending(x => x.CreatedAt);
    }
}

public sealed class ReportService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public ReportService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task<IReadOnlyList<OrderDto>> LoadAsync(
        int tenantId,
        CancellationToken cancellationToken)
    {
        IQueryable<Order> query;

        using (var scope = _scopeFactory.CreateScope())
        {
            var service = scope.ServiceProvider
                .GetRequiredService<OrderQueryService>();

            query = service.BuildOpenOrdersQuery(tenantId);
        }

        return await query
            .Take(100)
            .Select(x => new OrderDto(
                x.Id,
                x.ReferenceNo,
                x.Total,
                x.CreatedAt))
            .ToListAsync(cancellationToken);
    }
}
```

Trong test với in-memory fake, code có vẻ hoạt động. Ở production với SQL Server, team thỉnh thoảng nhận `ObjectDisposedException` liên quan `DbContext` hoặc database connection. Một developer cho rằng `BuildOpenOrdersQuery()` đã “chạy query” vì đã gọi `Where` và `OrderByDescending`, nên dispose scope sau method này là an toàn.

Một developer khác đề xuất gọi `.ToList()` ngay trong `BuildOpenOrdersQuery()` để “fix dứt điểm”, nhưng application có nhiều màn hình chỉ cần một projection nhỏ và đôi khi caller cần thêm filter trước khi execute.

## Câu hỏi chính

Hãy giải thích chính xác chuyện gì xảy ra từ lúc `BuildOpenOrdersQuery()` được gọi tới khi `ToListAsync()` thực sự execute; chỉ ra assumption nào của team đang sai; phân tích production impact của việc để `IQueryable` thoát khỏi lifetime của `DbContext`; sau đó đề xuất API/design phù hợp hơn mà vẫn giữ được khả năng tái sử dụng query logic mà không tạo hidden lifetime coupling.

## Câu hỏi làm rõ nên cân nhắc

1. `OrderQueryService` và `AppDbContext` đang được đăng ký với lifetime nào trong DI container?
2. Query có cần compose thêm filter/projection từ nhiều caller hay chỉ cần vài use case cố định?
3. Caller có cần streaming nhiều rows hay chỉ materialize một page nhỏ?
4. Có requirement nào bắt buộc query builder phải tồn tại ngoài request scope không?
5. Production đang dùng provider SQL Server thật hay có provider khác với execution behavior khác trong test?

## Gợi ý tư duy

### Gợi ý 1

Tập trung vào khác biệt giữa **xây dựng expression** và **thực thi query**.

### Gợi ý 2

Theo dõi object graph thật sự mà `IQueryable` giữ tham chiếu: provider, query context và lifetime của `DbContext`/connection khi enumeration bắt đầu.

### Gợi ý 3

Thiết kế tốt không nhất thiết là “không bao giờ trả `IQueryable`”. Hãy xác định boundary nơi composition được phép xảy ra và boundary nơi lifetime phải còn hợp lệ.

## Cấu trúc trả lời đề xuất

1. Xác nhận lifetime và execution boundary.
2. Giải thích deferred execution và expression tree.
3. Chỉ ra vì sao `Where`/`OrderBy` chưa chạy SQL.
4. Liên hệ `IQueryable` với `DbContext` đã bị dispose.
5. Phân tích khác biệt giữa test fake và relational provider thực.
6. Đề xuất 2–3 design alternatives.
7. Chọn design theo mức độ cần composition.
8. Nêu performance implications của projection/materialization.
9. Nêu tests để chứng minh lifetime đúng.
10. Nêu telemetry/debugging evidence nếu production gặp lại lỗi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` từ EF Core chủ yếu biểu diễn query chưa được execute.
- `Where`, `OrderByDescending`, `Take`, `Select` tiếp tục xây expression/query pipeline.
- SQL thường được gửi khi terminal operation/enumeration như `ToListAsync`, `SingleAsync`, `FirstAsync`, `await foreach` xảy ra.
- Query provider vẫn phụ thuộc vào `DbContext`; dispose scope trước execution làm query mất execution context hợp lệ.
- Fix bằng cách giữ scope/context sống xuyên suốt composition + execution, hoặc chuyển composition vào method/service chịu trách nhiệm materialize.
- Không nên materialize toàn bộ entity sớm chỉ để né lifetime issue nếu caller chỉ cần projection/filter nhỏ.

### Điểm cộng

- Nhận ra test fake/in-memory có thể che giấu relational lifetime/provider behavior và không phải bằng chứng production-safe.
- Phân biệt query composition API với repository trả collection đã materialize.
- Nhấn mạnh projection trước materialization để giảm columns, tracking và network IO.
- Dùng `AsNoTracking()` khi read-only và phù hợp.
- Đề xuất specification/query-object hoặc strongly typed query methods nếu muốn reuse predicate mà không expose `IQueryable` qua boundary rộng.

### Senior+

- Chỉ ra rằng returning `IQueryable` không tự thân là anti-pattern; rủi ro nằm ở abstraction boundary và lifetime ownership không rõ.
- Phân tích hidden coupling: caller tưởng đang thao tác collection nhưng thực chất đang mở rộng database query sẽ execute sau.
- Đề xuất expression-based reusable filters, ví dụ `Expression<Func<Order, bool>>`, hoặc query object áp dụng trong scope hiện tại.
- Phân biệt streaming với materialization: `IAsyncEnumerable` cũng vẫn cần `DbContext` sống trong suốt enumeration.
- Nêu rằng correctness boundary phải rõ hơn convenience abstraction.

## Hướng giải quyết tham khảo

`BuildOpenOrdersQuery()` không execute query khi gọi `Where` và `OrderByDescending`. Với EF Core, các operator LINQ này xây thêm expression/query representation mà provider sẽ translate khi một terminal operation thực sự cần dữ liệu.

Trong code hiện tại, `query` được lấy từ `OrderQueryService` trong một scope. `OrderQueryService` giữ `_db`, và `IQueryable` được tạo từ `_db.Orders`. Khi scope bị dispose, scoped `AppDbContext` cũng bị dispose. Sau đó code mới gọi `Take`, `Select`, `ToListAsync`. Chính `ToListAsync` mới cần provider dùng context để translate/execute SQL và materialize rows. Lúc đó execution infrastructure đã không còn hợp lệ, vì vậy lỗi dispose là hợp lý.

Assumption “gọi `Where` nghĩa là query đã chạy” là sai. `Where` trên `IQueryable<T>` khác với filter trên một collection đã materialize. Nó thường thêm node vào expression tree/query model. Cũng vì deferred execution, code nhìn có vẻ hợp lệ trong lúc build query nhưng fail trễ ở enumeration.

Một fix đơn giản là giữ scope cho tới sau `ToListAsync`:

```csharp
public async Task<IReadOnlyList<OrderDto>> LoadAsync(
    int tenantId,
    CancellationToken cancellationToken)
{
    await using var scope = _scopeFactory.CreateAsyncScope();

    var service = scope.ServiceProvider
        .GetRequiredService<OrderQueryService>();

    return await service.BuildOpenOrdersQuery(tenantId)
        .AsNoTracking()
        .Take(100)
        .Select(x => new OrderDto(
            x.Id,
            x.ReferenceNo,
            x.Total,
            x.CreatedAt))
        .ToListAsync(cancellationToken);
}
```

Cách này giữ composition linh hoạt nhưng lifetime ownership vẫn nằm cùng method. Nó phù hợp nếu `ReportService` thực sự chịu trách nhiệm orchestration và caller không làm query sống lâu hơn method.

Một design khác là không expose `IQueryable` qua application boundary. Query service nhận criteria và trả DTO đã materialize:

```csharp
public async Task<IReadOnlyList<OrderDto>> LoadOpenOrdersAsync(
    int tenantId,
    int take,
    CancellationToken cancellationToken)
{
    return await _db.Orders
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId)
        .Where(x => x.Status == OrderStatus.Open)
        .OrderByDescending(x => x.CreatedAt)
        .Take(take)
        .Select(x => new OrderDto(
            x.Id,
            x.ReferenceNo,
            x.Total,
            x.CreatedAt))
        .ToListAsync(cancellationToken);
}
```

Cách này có abstraction boundary rõ và dễ test hơn, nhưng giảm arbitrary composition. Nếu use cases hữu hạn, đây thường là trade-off tốt.

Nếu team cần tái sử dụng predicate mà vẫn để execution trong caller scope, có thể reuse expression/specification thay vì return live `IQueryable` đã gắn với một disposed context:

```csharp
public static class OrderSpecifications
{
    public static Expression<Func<Order, bool>> OpenForTenant(int tenantId)
        => x => x.TenantId == tenantId &&
                x.Status == OrderStatus.Open;
}
```

Caller sau đó áp dụng expression lên `DbSet` của chính `DbContext` mà nó sở hữu.

Đề xuất `.ToList()` ngay trong `BuildOpenOrdersQuery()` có thể loại deferred-lifetime issue nhưng dễ kéo toàn bộ entity/columns vào memory sớm, làm mất server-side composition và có thể biến filter/projection phía sau thành in-memory work. Nếu data lớn, đó là fix correctness bằng cách tạo performance problem mới.

Nếu requirement là streaming, ví dụ trả hàng trăm nghìn rows qua CSV, chuyển sang `IAsyncEnumerable` cũng không loại lifetime requirement. Context phải sống suốt enumeration; cancellation phải propagate; và scope cần được dispose sau khi stream kết thúc.

Testing nên có relational integration test thay vì chỉ in-memory fake. Test phải execute query sau các lifetime transition thật, xác minh SQL projection, cancellation và không dùng disposed scope. Nếu team giữ API trả `IQueryable`, nên document rõ ownership: query chỉ được compose/execute trong scope tạo ra nó và không được cache/store/return qua asynchronous boundary ngoài scope.

Telemetry hữu ích khi production lỗi gồm exception type, operation/correlation id, query use case, request path và trace dependency SQL. Không log raw SQL parameter chứa sensitive data nếu không cần.

## Mẫu trả lời trong phỏng vấn

“Điểm chính là `IQueryable` ở đây chưa phải dữ liệu. `Where` và `OrderBy` chỉ tiếp tục xây query representation. SQL chỉ thực sự chạy khi mình enumerate, ở đây là `ToListAsync`. Query provider này được tạo từ `DbContext`, nên khi scope bị dispose trước `ToListAsync`, mình vẫn giữ một query object nhưng execution context phía sau đã chết. Vì vậy lỗi xuất hiện trễ ở lúc enumerate.

Tôi sẽ không fix bằng cách materialize toàn bộ entity ngay trong query builder nếu caller còn cần filter/projection, vì như vậy dễ kéo quá nhiều dữ liệu và mất server-side composition. Có ba lựa chọn: giữ scope sống đến sau execution; chuyển query service thành method trả DTO/materialized result cho từng use case; hoặc reuse predicate/specification rồi để caller áp dụng lên `DbContext` mà caller sở hữu.

Nếu application chỉ có vài use case rõ ràng, tôi nghiêng về typed query methods trả DTO vì lifetime ownership rõ hơn. Nếu cần composition mạnh, trả `IQueryable` vẫn chấp nhận được nhưng chỉ trong boundary nơi context lifetime được bảo đảm. Tôi cũng sẽ có relational integration test vì in-memory fake có thể không tái hiện execution semantics của production provider.”

## Câu hỏi đào sâu

1. Nếu thay `ToListAsync()` bằng `AsAsyncEnumerable()` rồi trả `IAsyncEnumerable<OrderDto>` ra ngoài service, lifetime problem có biến mất không?
2. Khi nào bạn chấp nhận repository trả `IQueryable`, và khi nào bạn xem đó là abstraction leak nguy hiểm?
3. Nếu team muốn reusable filters nhưng không muốn expose EF Core ra application layer, bạn sẽ thiết kế query/specification abstraction thế nào mà không biến nó thành framework phức tạp?

## Lỗi trả lời thường gặp

- Nói rằng `Where()` luôn execute SQL ngay.
- Chỉ đề xuất `.ToList()` càng sớm càng tốt mà không xét performance/projection.
- Kết luận “không bao giờ được return `IQueryable`” mà không bàn abstraction boundary và lifetime ownership.
- Bỏ qua việc streaming cũng cần context sống trong suốt enumeration.
- Tin rằng in-memory test đủ chứng minh relational query behavior.

## Thang điểm 0–10

- **0–2:** Không hiểu deferred execution; không xác định được lifetime root cause.
- **3–4:** Biết `IQueryable` lazy nhưng giải thích mơ hồ, fix chủ yếu bằng materialize sớm.
- **5–6:** Giải thích đúng execution boundary, `DbContext` lifetime và đưa ra fix an toàn.
- **7–8:** So sánh được nhiều design alternatives, projection, testing và abstraction trade-offs.
- **9–10:** Giải thích internal mechanism rõ, phân biệt composition/streaming/materialization, thiết kế lifetime ownership tốt và nêu được khi nào `IQueryable` là hợp lý hoặc nguy hiểm.

# Câu 2 — Sau khi publish CMS, một phần người dùng vẫn thấy nội dung cũ qua Akamai

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai/CDN, HTTP caching, cache invalidation, `Cache-Control`, TTL, purge, multi-layer caching, incident response, observability, deployment/content operations

## Bối cảnh

Một marketing website chạy ASP.NET Core + Optimizely CMS phía origin và dùng Akamai làm CDN. Site có traffic lớn theo nhiều quốc gia. Editors publish campaign page và kỳ vọng nội dung mới xuất hiện trong vài phút.

Sau một campaign launch, production ghi nhận:

- editor preview trong CMS thấy nội dung mới ngay;
- một số user tại Việt Nam thấy nội dung mới, nhưng user ở một số location khác vẫn thấy bản cũ trong 20–30 phút;
- hard refresh đôi khi vẫn ra bản cũ;
- gọi trực tiếp origin nội bộ trả nội dung mới;
- Akamai cache hit ratio vẫn cao;
- không có outage tổng thể;
- một số page có `Cache-Control` khác nhau do middleware và CMS code được thay đổi qua nhiều năm;
- application cũng có in-memory cache cho một số content projection;
- team có purge API nhưng hiện purge theo URL thủ công sau publish;
- canonical URLs có cả biến thể có/không trailing slash và một số query parameters dùng cho campaign tracking;
- một developer đề xuất tắt toàn bộ CDN cache trong ngày launch;
- developer khác đề xuất giảm TTL mọi page xuống 10 giây.

Business impact là campaign pricing/message có thể khác nhau giữa user, gây complaint và mất niềm tin. Team cần vừa khôi phục consistency đủ nhanh, vừa tránh tạo origin traffic spike không cần thiết.

Thông tin hiện tại chưa đủ để kết luận root cause duy nhất.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo trình tự nào từ stabilization tới root-cause analysis? Hãy đưa ra các competing hypotheses cho việc user thấy stale content, chỉ rõ evidence cần thu thập ở từng layer, cách xác định cache layer nào đang giữ bản cũ, cách remediation ngắn hạn, và thiết kế lâu dài để publish/invalidation đáng tin cậy hơn mà không đơn giản vô hiệu hóa toàn bộ caching.

## Câu hỏi làm rõ nên cân nhắc

1. Response headers từ user bị stale cho biết `Age`, cache status, surrogate/cache key hoặc `Cache-Control` thế nào?
2. Akamai cache key có normalize host, path, trailing slash, query parameters và locale giống expectation không?
3. Purge hiện tại là theo exact URL, cache tag/key hay wildcard/path pattern?
4. Origin có bao nhiêu instances và in-memory cache có invalidation theo publish event hay TTL riêng?
5. Có SSR/fragment/API calls nào bị cache độc lập với HTML page không?

## Gợi ý tư duy

### Gợi ý 1

Đừng nhảy thẳng tới “CDN bị lỗi”. Hãy dựng **cache hierarchy** và xác định stale response phát sinh ở layer nào.

### Gợi ý 2

So sánh cùng một URL qua browser, edge POP, origin và các URL variants. Header/evidence quan trọng hơn cảm giác “hard refresh rồi mà vẫn cũ”.

### Gợi ý 3

Publish consistency là một protocol giữa CMS, origin cache và CDN invalidation. TTL ngắn chỉ là một safety net, không phải protocol hoàn chỉnh.

## Cấu trúc trả lời đề xuất

1. Xác định business impact và scope.
2. Stabilize: chọn biện pháp giảm stale exposure có kiểm soát.
3. Thu evidence từ client/edge/origin.
4. Vẽ cache layers và cache keys.
5. Đưa ra 3–5 hypotheses cạnh tranh.
6. Dùng headers/logs/purge audit để loại trừ từng hypothesis.
7. Remediate layer đang sai.
8. Thiết kế publish → invalidation → verification flow lâu dài.
9. Test URL variants, regions và failure paths.
10. Thiết lập monitoring/alerting cho stale propagation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận một root cause trước khi xem evidence.
- Kiểm tra edge headers/cache status, `Age`, `Cache-Control`, cache key behavior.
- So sánh direct origin với CDN cùng URL variant.
- Xét cả Akamai, browser cache, reverse proxy/application cache và CMS content cache.
- Kiểm tra purge có cover đúng cache variants không.
- Không chọn “disable all caching” hoặc TTL cực thấp như permanent fix.
- Có publish/invalidation workflow tự động và verification.

### Điểm cộng

- Nhận ra query parameters/trailing slash/locale/host có thể tạo nhiều cache objects.
- Phân biệt stale HTML với stale API/fragment/resource.
- Dùng content version/publish timestamp/ETag-like diagnostic marker để trace version đang được serve.
- Có fallback khi purge API lỗi hoặc partial failure.
- Xét cache stampede/origin overload khi purge diện rộng.

### Senior+

- Thiết kế invalidation idempotent và observable, có correlation từ CMS publish event tới CDN purge request và verification.
- Xác định TTL là upper bound cho stale duration khi invalidation fail, không phải cơ chế duy nhất.
- Dùng cache tags/surrogate keys/content dependencies nếu platform/CDN setup hỗ trợ, thay vì maintain danh sách URL thủ công dễ thiếu.
- Xét rollout/operational ownership: ai chịu trách nhiệm khi publish thành công nhưng purge thất bại.
- Cân bằng correctness, cache hit ratio, origin capacity và complexity.

## Hướng giải quyết tham khảo

Bước đầu tiên là xác định scope và giảm business impact. Nếu campaign content có giá/message nhạy cảm, tôi có thể tạm thời purge các affected objects cụ thể hoặc hạ cacheability cho đúng route/campaign page trong thời gian điều tra. Tôi không tắt toàn CDN nếu chỉ một nhóm URL bị ảnh hưởng, vì điều đó có thể đẩy traffic đột ngột về origin và tạo outage thứ hai.

Sau đó tôi cần evidence trên cùng một URL. Với user stale, lấy response headers từ edge: cache status, `Age`, `Cache-Control`, `Vary`, host/path/query và các diagnostic headers CDN nếu tổ chức đã expose. So sánh với request cùng URL đi trực tiếp origin. Nếu origin luôn trả version mới nhưng edge trả version cũ với cache hit/age tăng, suspicion nghiêng về invalidation/cache-key mismatch. Nếu edge miss nhưng vẫn nhận stale từ origin, phải điều tra application/CMS cache.

Các hypotheses tôi sẽ giữ song song gồm:

1. Purge chỉ invalidate exact URL nhưng cache có nhiều variants do trailing slash, locale, host hoặc query string.
2. Purge request fail/partial success ở CDN hoặc publish workflow không gọi purge trong một số path.
3. Origin application có in-memory cache stale trên một số instances; edge miss tại POP nào đó re-fill từ instance stale.
4. `Cache-Control`/TTL khác nhau giữa routes khiến một subset objects giữ lâu hơn dự kiến.
5. HTML mới nhưng một API/fragment phía client vẫn cache dữ liệu cũ, khiến user perception là page cũ.
6. Browser/service worker cache nếu application có service worker hoặc custom client caching.

Tôi sẽ gắn version marker có thể quan sát an toàn, ví dụ content publish version/timestamp trong response header nội bộ hoặc diagnostic metadata. Mục đích là biết response đang mang content version nào mà không cần diff HTML thủ công.

Về purge, nếu workflow hiện purge URL thủ công, đây là một reliability gap. Publish event nên phát sinh invalidation command có định danh/correlation id. Invalidation service biết cache keys/paths phụ thuộc content và gọi CDN purge API. Request/response của purge phải được log structured: content id/version, URLs/tags, result, duration, retry status.

Nếu một content block được reuse trên 50 pages, manual URL list rất dễ thiếu. Nếu architecture/CDN integration hỗ trợ content dependency tags/surrogate keys, invalidation theo dependency có thể đáng tin cậy hơn. Nếu không hỗ trợ, cần duy trì reverse dependency mapping hoặc chọn TTL hợp lý cho shared fragments. Không nên giả định một feature cụ thể của CDN nếu chưa verify account/configuration hiện tại.

Application in-memory cache cũng cần invalidation theo publish event hoặc version-aware key. Nếu site chạy nhiều origin instances, local memory cache invalidation phải được phân phối hoặc TTL/versioning phải đảm bảo không có instance giữ stale quá lâu. Không nên purge edge xong rồi để edge re-populate từ một origin instance stale.

TTL vẫn hữu ích như safety net. Ví dụ business có thể chấp nhận stale tối đa vài phút; TTL nên phản ánh requirement và origin capacity. Nhưng giảm mọi page xuống 10 giây thường làm cache hit ratio giảm mạnh và tăng origin load. Nên phân loại content: campaign-sensitive dynamic pages có policy ngắn hơn; static assets có TTL dài và content-hashed URLs; content thường có invalidation + TTL phù hợp.

Long-term verification nên có synthetic check sau publish: gọi một tập đại diện URL/regions hoặc ít nhất edge endpoints khả dụng, xác minh content version đã đổi trong SLO. Nếu purge API success nhưng synthetic check vẫn thấy stale quá ngưỡng, alert phải kích hoạt.

Testing gồm URL normalization variants, query parameters, localization, multi-instance origin cache, purge failure, repeated publish/purge, và load test sau mass purge để bảo đảm origin chịu được cache miss burst.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không kết luận ngay là Akamai lỗi. Tôi sẽ dựng cache hierarchy: browser → Akamai edge → origin/app cache → CMS content. Vì direct origin đã thấy nội dung mới, edge invalidation là hypothesis mạnh nhưng vẫn cần headers để chứng minh.

Tôi sẽ lấy stale response và xem cache status, `Age`, `Cache-Control`, URL variant, query string và so sánh với cùng request ở origin. Sau đó kiểm tra purge audit: exact URL nào đã purge, có trailing-slash/locale/query variants không, purge có fail hoặc partial không. Tôi cũng kiểm tra in-memory cache trên origin instances vì edge có thể purge đúng rồi re-fill từ một instance stale.

Ngắn hạn, tôi purge đúng affected objects hoặc tạm giảm cacheability cho campaign route, không tắt toàn CDN. Lâu dài, publish phải trigger invalidation tự động, có correlation id, retry/idempotency và verification. TTL chỉ là safety net. Nếu content block được reuse rộng, tôi muốn invalidation dựa trên dependency/cache tags nếu setup hỗ trợ, thay vì URL list thủ công.

Cuối cùng tôi sẽ có synthetic post-publish checks và alert nếu version mới chưa propagate trong SLO, đồng thời test mass purge để tránh giải quyết stale content bằng cách gây origin overload.”

## Câu hỏi đào sâu

1. Nếu purge thành công theo API nhưng một vài POP vẫn serve stale content, bạn sẽ thu thêm evidence và định nghĩa SLO/verification thế nào?
2. Nếu origin có 8 instances với local memory cache và chỉ một instance nhận publish invalidation, bạn sẽ thiết kế cache consistency ra sao mà không bắt buộc thêm Redis nếu chưa cần?
3. Nếu business yêu cầu campaign price phải nhất quán gần như ngay lập tức nhưng marketing images có thể stale 30 phút, bạn sẽ tách cache policy thế nào?

## Lỗi trả lời thường gặp

- Tắt toàn bộ CDN cache như permanent fix.
- Giảm TTL mọi resource xuống vài giây mà không xét origin load.
- Chỉ kiểm tra CMS publish status, không xem edge headers/cache key.
- Quên URL variants, query parameters, locale hoặc application cache.
- Coi purge API trả success là bằng chứng chắc chắn user đã nhận content mới.

## Thang điểm 0–10

- **0–2:** Đoán root cause và đề xuất tắt cache.
- **3–4:** Biết kiểm tra CDN nhưng thiếu cache hierarchy/evidence.
- **5–6:** Có incident flow, competing hypotheses, headers, purge và origin-cache investigation.
- **7–8:** Thiết kế được automated invalidation, TTL strategy, tests và observability.
- **9–10:** Xử lý đầy đủ multi-layer caching, invalidation protocol, regional verification, failure recovery và cost-of-complexity/origin-capacity trade-offs.

# Câu 3 — Thiết kế upload tài liệu lớn: API proxy hay direct upload tới Azure Blob Storage?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS concepts, SQL metadata, asynchronous processing, security, file upload, reliability, observability, architecture trade-offs

## Bối cảnh

Một enterprise portal cần tính năng upload tài liệu cho hồ sơ khách hàng.

Requirement ban đầu:

- file phổ biến 1–20 MB, nhưng có thể tới 2 GB;
- user đăng nhập qua Microsoft Entra ID;
- mỗi file thuộc một business record và tenant cụ thể;
- application metadata lưu trong SQL Server;
- file binary dự kiến lưu ở Azure Blob Storage;
- sau upload cần virus/malware scanning và extract metadata cơ bản;
- user chỉ được download file mà họ có quyền với business record tương ứng;
- upload qua mobile/đường truyền không ổn định là use case thực tế;
- audit phải biết ai upload, lúc nào, file nào, trạng thái scan;
- portal hiện chạy ASP.NET Core trên Azure App Service;
- hệ thống chưa dùng Kubernetes;
- team đang tranh luận giữa hai hướng:
  - mọi upload đi xuyên qua ASP.NET Core API rồi API stream sang Blob;
  - API cấp quyền upload giới hạn thời gian để browser/client upload trực tiếp Blob.

Một architect đề xuất thêm microservice, Service Bus, Functions, Redis, Kubernetes ngay từ đầu “để scale”. Một developer khác muốn giữ toàn bộ xử lý synchronous trong request để implementation đơn giản.

Thông tin như traffic peak, compliance retention, exact malware scanner và requirement resumable upload chưa được chốt.

## Câu hỏi chính

Hãy thiết kế solution cho file-upload flow này và quyết định khi nào chọn backend proxy upload, khi nào chọn direct-to-Blob upload. Trình bày APIs, data model, authorization boundary, upload lifecycle, scan workflow, failure recovery, observability và deployment. Bạn phải nêu rõ assumptions nào cần xác minh trước khi quyết định, đồng thời tránh thêm distributed-system complexity nếu requirement chưa biện minh.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent uploads và bandwidth profile dự kiến là bao nhiêu?
2. Client có bắt buộc resumable/chunked upload cho file lớn và mobile network không?
3. File phải được malware scan trước khi có thể download hay có workflow quarantine riêng?
4. Compliance yêu cầu retention, encryption key ownership, legal hold hoặc geographic residency thế nào?
5. Có cần hỗ trợ public/external users hay chỉ authenticated enterprise users?

## Gợi ý tư duy

### Gợi ý 1

Tách **control plane** và **data plane**: API quyết định ai được phép upload gì; binary bytes không nhất thiết phải đi qua application server.

### Gợi ý 2

Direct upload giảm bandwidth qua App Service nhưng làm upload lifecycle/state machine rõ ràng hơn: `PendingUpload`, `Uploaded`, `Scanning`, `Available`, `Rejected`, `Failed`.

### Gợi ý 3

Đừng tự động chọn Service Bus/Kubernetes. Chỉ thêm asynchronous infrastructure khi scan/retry/throughput/operational requirements cần nó.

## Cấu trúc trả lời đề xuất

1. Clarify scale, security và scan requirements.
2. Chọn control-plane/data-plane boundary.
3. Thiết kế upload initiation API.
4. Thiết kế blob naming/ownership và SQL metadata.
5. Thiết kế finalize/verification step.
6. Thiết kế malware scan/quarantine flow.
7. Thiết kế download authorization.
8. Xử lý retry, orphan blobs và partial failure.
9. So sánh proxy vs direct upload.
10. Chọn deployment/observability tối giản phù hợp.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cho client tự quyết định arbitrary blob path/container quyền rộng.
- Authorization vẫn nằm ở application/business layer.
- Blob access phải least privilege và giới hạn scope/time.
- Metadata state phải phản ánh upload chưa hoàn tất, scanning và available status.
- File chưa scan không được phục vụ như file hợp lệ nếu business yêu cầu quarantine.
- Có cleanup cho abandoned uploads/orphan blobs.
- Có idempotency/finalization semantics và audit trail.
- So sánh network/app-resource cost giữa proxy và direct upload.

### Điểm cộng

- Tách logical `DocumentId` khỏi physical blob name.
- Dùng immutable/randomized blob path để tránh overwrite/collision.
- Verify blob properties/size/content metadata sau upload thay vì tin hoàn toàn dữ liệu client khai báo.
- Download cũng có thể dùng short-lived delegated access sau application authorization thay vì proxy bytes mọi lúc.
- Nêu checksum/hash khi integrity requirement có giá trị.

### Senior+

- Thiết kế state transitions và failure recovery rõ ràng.
- Xét race giữa finalize, scan callback và deletion.
- Xét malware scanner failure/dependency degradation.
- Phân biệt authentication/authorization ở API với storage credential delegation.
- Đưa ra evolution path: bắt đầu App Service + Blob + SQL, sau đó thêm queue/Functions/worker khi asynchronous workload thực sự cần.
- Nêu operational metrics như pending age, scan latency, orphan count, failed finalization, upload success rate.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng cách tách control plane khỏi file data plane.

ASP.NET Core API chịu trách nhiệm xác thực user, kiểm tra quyền trên business record/tenant, tạo logical `Document` record và cấp capability upload giới hạn. Binary file không bắt buộc phải đi xuyên App Service nếu file có thể tới 2 GB và client network không ổn định.

Một data model tối thiểu có thể là:

```text
Document
- Id
- TenantId
- BusinessRecordId
- BlobName
- OriginalFileName
- ContentTypeDeclared
- SizeDeclared
- SizeActual
- Status
- UploadedBySubjectId
- CreatedAt
- UploadedAt
- ScanStartedAt
- ScanCompletedAt
- ScanResult
- Version
```

Status có thể gồm:

```text
PendingUpload
Uploaded
Scanning
Available
Rejected
Failed
Deleted
```

Flow direct upload có thể là:

1. Client gọi `POST /api/records/{recordId}/documents/uploads` với file metadata sơ bộ.
2. API authorize user đối với record/tenant.
3. API tạo `DocumentId` + server-generated blob name, ví dụ theo tenant/document id/random suffix.
4. API cấp một upload capability ngắn hạn, scope chỉ đúng object/path và operation cần thiết. Credential cụ thể phải theo storage design được phê duyệt; principle là least privilege, short lifetime, không đưa storage account key dài hạn cho client.
5. Client upload trực tiếp tới Blob Storage.
6. Client gọi finalize endpoint hoặc system nhận storage event để xác nhận object tồn tại.
7. Server verify actual blob properties như size/content metadata cần thiết, chuyển state `Uploaded`.
8. Scanner xử lý blob trong quarantine/untrusted area hoặc trạng thái chưa downloadable.
9. Nếu sạch, state chuyển `Available`; nếu malicious, `Rejected` và thực hiện policy delete/quarantine.

Điểm quan trọng là direct upload không có nghĩa client được tự quyết định quyền storage. API vẫn là nơi cấp capability sau business authorization.

Về authentication giữa App Service và Blob Storage, server-side code nên dùng managed identity/service identity phù hợp thay vì hard-code account keys khi platform setup cho phép. Với client delegation, quyền phải ngắn hạn và chỉ cho đúng blob/operation. Exact mechanism cần verify theo Azure Storage security policy của tổ chức trước implementation.

Upload proxy qua API vẫn hợp lý trong một số trường hợp:

- file nhỏ và traffic thấp;
- application cần inspect/transform stream inline;
- network/security policy cấm direct client-to-storage;
- client ecosystem quá đơn giản và operational cost direct upload không đáng.

Nhưng với 2 GB file và concurrent upload đáng kể, proxy khiến App Service gánh ingress + egress-to-storage bytes, connection duration, timeout/resource pressure và scale cost. Nếu API chỉ đứng giữa để chuyển bytes, direct upload thường là boundary đáng cân nhắc.

Tôi sẽ không tự động thêm Kubernetes. App Service có thể tiếp tục host control-plane API. Malware scan có thể bắt đầu bằng một hosted worker hoặc Azure Function tùy workload/runtime của scanner, nhưng quyết định phải dựa trên execution duration, concurrency, retry và integration model. Nếu scan workload cần durable retries và decoupling, một queue như Azure Service Bus có thể hợp lý; nếu volume rất thấp và scanner API synchronous nhanh, một simpler worker flow có thể đủ.

Điều tôi không làm là giữ HTTP upload request mở cho tới khi malware scan xong. Scan là hậu xử lý có thể thất bại/retry và làm upload latency khó kiểm soát. User-facing API nên trả upload accepted/completed-transfer rồi expose processing status riêng.

Finalization phải idempotent. Client mobile có thể retry `finalize` nếu mất mạng. API nên kiểm tra current state/version và cho cùng logical completion request trả kết quả ổn định thay vì tạo document mới.

Abandoned upload là failure mode bình thường. Scheduled cleanup job có thể tìm `PendingUpload` quá TTL, xác minh blob có/không và cleanup metadata/blob. Ngược lại, orphan blob không có metadata cũng cần lifecycle/cleanup strategy.

Download flow không nên chỉ nhận blob name từ client rồi stream. Client gọi `/documents/{id}/download`; application authorize document qua tenant/business record, kiểm tra `Status == Available`, rồi hoặc proxy stream hoặc cấp short-lived read capability. Chọn cách nào phụ thuộc audit, client, bandwidth và compliance requirement.

Security thêm gồm file-name normalization, không tin MIME type do client khai báo, size limits, malware scan, content-disposition an toàn, không cho executable content được serve inline nếu policy không cho phép, và không log delegated tokens/capabilities.

Observability tôi muốn có:

- upload initiated/completed/failed count;
- bytes uploaded và duration;
- finalize failure/idempotent retry count;
- documents theo state;
- oldest `PendingUpload`/`Scanning` age;
- scan latency/error/retry;
- rejected malware count;
- orphan cleanup count;
- storage dependency errors;
- correlation `DocumentId` từ API → blob → scan → availability.

Để tránh overengineering, phase 1 có thể chỉ cần App Service + SQL + Blob + một processing mechanism tối giản. Service Bus/Functions chỉ thêm khi scan cần durable asynchronous behavior hoặc throughput tăng. Kubernetes chưa có requirement nào rõ ràng trong scenario này.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách authorization/control plane khỏi file data plane. API xác thực user, kiểm tra quyền trên business record, tạo `DocumentId` và server-generated blob name. Với file có thể tới 2 GB, tôi nghiêng về direct upload tới Blob bằng capability ngắn hạn, scope đúng một blob và đúng operation, thay vì cho toàn bộ bytes đi qua App Service.

Sau upload, document không lập tức `Available`. Tôi sẽ có state như `PendingUpload → Uploaded → Scanning → Available/Rejected`. Finalize endpoint phải idempotent vì mobile client có thể retry. Server verify actual blob properties thay vì tin metadata client.

Malware scan tôi tách asynchronous khỏi request. Nếu volume thấp có thể dùng worker đơn giản; nếu cần durable retry/decoupling thì thêm Service Bus/Function. Tôi không thêm Kubernetes chỉ vì file lớn.

Download vẫn đi qua business authorization. Sau khi authorize và xác nhận file đã clean, API có thể stream hoặc cấp short-lived read capability. Tôi cũng sẽ có cleanup cho abandoned uploads/orphan blobs và metrics cho pending age, scan latency, failures và correlation theo `DocumentId`.

Nếu compliance cấm direct storage access hoặc file luôn nhỏ/traffic thấp, proxy upload là lựa chọn hợp lý hơn. Quyết định phụ thuộc scale, resumability, network policy và audit requirement.”

## Câu hỏi đào sâu

1. Nếu client upload xong blob nhưng crash trước khi gọi finalize, bạn recovery document thế nào mà không tạo orphan vĩnh viễn?
2. Nếu malware scanner bị outage 6 giờ, bạn sẽ giữ upload availability, retry và user experience thế nào?
3. Nếu security team cấm SAS-like delegated client access hoàn toàn, bạn sẽ làm proxy upload chịu được file 2 GB và mobile network không ổn định ra sao?

## Lỗi trả lời thường gặp

- Cho client storage account key hoặc quyền rộng thay vì capability giới hạn.
- Cho file download ngay khi upload xong trước khi scan hoàn tất.
- Giữ request synchronous tới khi scan xong.
- Tự động chọn Microservices/Kubernetes/Service Bus mà không gắn với requirement.
- Không thiết kế cleanup/idempotency cho upload/finalize retry và partial failure.

## Thang điểm 0–10

- **0–2:** Chỉ nói “upload Blob” nhưng không có authorization/lifecycle/security.
- **3–4:** Có Blob + SQL nhưng không xử lý scan, partial failure hoặc file lớn.
- **5–6:** Có control/data boundary, direct vs proxy trade-off, state machine và authorization.
- **7–8:** Có idempotency, cleanup, async scan, least privilege, observability và deployment đơn giản.
- **9–10:** Thiết kế conditional theo scale/compliance, xử lý failure recovery sâu, không overengineer và có evolution path rõ từ simple architecture tới durable asynchronous processing khi thực sự cần.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` thể hiện query composition; execution thường xảy ra ở terminal operation/enumeration, nên lifetime của `DbContext` phải bao phủ execution.
- Deferred execution tạo hidden coupling nếu query object sống lâu hơn scope/provider đã tạo ra nó.
- Production caching phải được reasoning theo toàn bộ hierarchy: browser, CDN, origin/application cache và CMS content layer.
- Cache invalidation nên là một observable workflow gắn với content version/publish event; TTL là safety net chứ không thay thế invalidation.
- Trong file upload architecture, application có thể giữ control-plane authorization trong API nhưng đưa binary data plane trực tiếp tới object storage khi scale/file size biện minh.
- Senior architecture judgment cần cân bằng correctness, reliability và cost of complexity; không tự động thêm Microservices, Kubernetes, messaging hay distributed cache.
