# Câu 1 — Vì sao hai API “chạy nhanh khi test riêng” nhưng production lại deadlock và timeout khi chạy đồng thời?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** SQL Server, Entity Framework Core, transactions, locking, deadlocks, isolation, execution plans, concurrency, ASP.NET Core, observability

## Bối cảnh

Một ASP.NET Core API trên .NET 8 dùng Entity Framework Core và SQL Server cho hệ thống approval nội bộ.

Hai use case chính:

- `ApproveRequest`: cập nhật `ApprovalRequests`, sau đó cập nhật `EmployeeBalances`.
- `CancelRequest`: cập nhật `EmployeeBalances`, sau đó cập nhật `ApprovalRequests`.

Mỗi API chạy trong transaction riêng. Khi developer test từng API độc lập trên staging thì thời gian thường dưới 100 ms.

Trong production, vào giờ cao điểm xuất hiện:

- một số request mất 5–15 giây rồi fail;
- log thỉnh thoảng có SQL deadlock victim error;
- p99 tăng mạnh nhưng p50 vẫn bình thường;
- CPU application và SQL Server đều chưa chạm 100%;
- retry ở application làm một số request thành công ở lần sau;
- team đề xuất tăng command timeout lên 60 giây;
- một developer nói deadlock chỉ xảy ra khi “database quá tải”;
- một developer khác đề xuất chuyển isolation level xuống thấp hơn mà chưa xem execution plan hay lock graph.

Chưa biết chắc:

- hai transaction có thực sự chạm cùng rows/index keys hay không;
- thứ tự SQL statements thực tế do EF Core phát ra;
- execution plan có scan nhiều rows ngoài dự kiến không;
- indexes có phù hợp predicates không;
- transaction mở trong bao lâu;
- có external API call hoặc business logic dài nằm bên trong transaction không;
- deadlock graph hiện chưa được team xem.

## Câu hỏi chính

Hãy giải thích deadlock có thể hình thành như thế nào dù từng API chạy rất nhanh khi test riêng, vì sao tăng timeout không giải quyết nguyên nhân, và bạn sẽ thu thập evidence rồi sửa thiết kế/query/transaction như thế nào mà không mặc định rằng chỉ cần đổi isolation level.

## Câu hỏi làm rõ nên cân nhắc

1. Hai use case có thể tác động cùng `ApprovalRequestId` hoặc cùng `EmployeeId` đồng thời không?
2. EF Core transaction bắt đầu ở đâu và kết thúc ở đâu; có code chờ network/I/O khác nằm trong transaction không?
3. Deadlock graph cho thấy resource nào và statement nào đang giữ/chờ lock?
4. Query predicates hiện có index hỗ trợ hay execution plan đang scan phạm vi lớn?
5. Business có yêu cầu serialization tuyệt đối cho approve/cancel cùng request hay có thể reject thao tác cạnh tranh bằng optimistic concurrency?

## Gợi ý tư duy

### Gợi ý 1

Deadlock không cần CPU cao. Nó cần một chu kỳ chờ tài nguyên giữa các transactions.

### Gợi ý 2

Thứ tự truy cập resource, phạm vi lock, transaction duration và execution plan đều có thể thay đổi xác suất deadlock.

### Gợi ý 3

Retry có thể là resilience policy hợp lý cho một deadlock đã xảy ra, nhưng retry không thay thế việc giảm điều kiện tạo deadlock và bảo đảm operation idempotent/correct.

## Cấu trúc trả lời đề xuất

1. Làm rõ concurrency/business invariant.
2. Mô tả lock/wait cycle có thể xảy ra.
3. Thu deadlock graph và correlate với request/SQL.
4. Kiểm tra transaction boundary và statement ordering.
5. Kiểm tra execution plan/indexes để giảm lock footprint.
6. So sánh consistent ordering, shorter transaction, optimistic concurrency và isolation choices.
7. Đánh giá retry semantics.
8. Kiểm thử concurrency.
9. Theo dõi deadlock/blocking/latency sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Deadlock là chu kỳ chờ, không đồng nghĩa database phải CPU-saturated.
- Nhận ra hai flow truy cập resources theo thứ tự ngược nhau có thể tạo cycle.
- Yêu cầu deadlock graph/evidence trước khi kết luận.
- Phân biệt blocking dài với deadlock.
- Giảm transaction duration và tránh I/O ngoài database bên trong transaction nếu không cần thiết.
- Kiểm tra query plan/index để tránh scan và lock phạm vi lớn không cần thiết.
- Cân nhắc thống nhất thứ tự truy cập resources giữa các flows.
- Retry deadlock phải bounded và operation phải chịu được retry.
- Không tăng timeout như root-cause fix.

### Điểm cộng

- Dùng optimistic concurrency token khi business cho phép phát hiện conflict thay vì serialize mọi thao tác.
- Phân biệt transaction isolation semantics với deadlock prevention; isolation thấp hơn không bảo đảm hết deadlock.
- Xem xét `SaveChanges` boundaries và SQL ordering thực tế thay vì suy luận từ thứ tự code C#.
- Đề xuất correlation ID/request ID gắn với SQL telemetry.

### Senior+

- Dựa trên deadlock graph để chỉ ra victim, lock modes, objects/indexes và acquisition order.
- Phân tích khả năng execution plan regression làm lock footprint thay đổi dù code application không đổi.
- Thiết kế invariant cho approve/cancel đồng thời, ví dụ row-version/state transition có điều kiện.
- Phân biệt correctness fix với throughput optimization.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng tăng timeout. Timeout dài hơn chỉ cho request chờ lâu hơn; deadlock thật sự là một cycle và SQL Server phải chọn một transaction làm victim để phá cycle.

Một tình huống khả dĩ là:

- Transaction A của `ApproveRequest` lock row/key ở `ApprovalRequests`, sau đó cần lock `EmployeeBalances`.
- Transaction B của `CancelRequest` đã lock `EmployeeBalances`, sau đó cần lock `ApprovalRequests`.
- A chờ B, B chờ A → cycle.

Nhưng tôi sẽ không coi đây là root cause đã được chứng minh. Tôi cần deadlock graph từ SQL Server tooling/Extended Events hoặc telemetry phù hợp để biết chính xác statements, objects/indexes, lock modes và transaction nào bị chọn làm victim.

Tôi cũng kiểm tra blocking riêng. Một request chờ 10 giây chưa chắc là deadlock; có thể nó đang bị block bởi transaction dài rồi cuối cùng chạy tiếp. Blocking chain, wait stats và deadlock graph trả lời hai câu hỏi khác nhau.

Sau khi có evidence, tôi xem bốn nhóm nguyên nhân chính.

**1. Resource ordering**

Nếu hai business flows luôn cần cùng hai resources, tôi cố gắng truy cập theo một thứ tự nhất quán. Ví dụ cả approve và cancel đều lock/update request trước rồi balance sau, nếu business/data model cho phép. Consistent lock acquisition order làm giảm một class deadlock phổ biến.

**2. Transaction lifetime**

Tôi xem transaction có bị mở sớm không. Nếu code bắt transaction rồi gọi external API, serialize payload lớn, hoặc làm nhiều computation trước khi commit, lock bị giữ lâu hơn cần thiết. Tôi thu transaction xuống boundary nhỏ nhất vẫn giữ đúng atomicity.

**3. Query/index footprint**

Một update tưởng chỉ chạm một row nhưng predicate thiếu index có thể scan/lock nhiều keys/pages hơn. Tôi xem actual execution plan, row estimates/actuals, index usage và predicates. Fix index/query có thể vừa giảm latency vừa giảm lock footprint.

**4. Concurrency model**

Nếu approve và cancel trên cùng request là conflict nghiệp vụ, tôi cân nhắc optimistic concurrency. Ví dụ có `rowversion` hoặc state transition dạng `UPDATE ... WHERE Id = @id AND Status = 'Pending'`. Một transaction thắng; transaction còn lại nhận conflict rõ ràng thay vì cả hai giả định cùng thành công.

Isolation level phải được quyết định từ consistency requirement. Chuyển xuống isolation yếu hơn chỉ để “hết deadlock” có thể tạo anomaly khác và cũng không bảo đảm loại bỏ mọi deadlock. Tương tự, snapshot-based options có thể giảm một số reader/writer blocking nhưng không loại bỏ writer/writer conflicts.

Về retry: SQL deadlock victim là loại transient failure có thể retry nếu operation được thiết kế an toàn. Tôi dùng bounded retry với backoff phù hợp, nhưng tránh retry mù nếu request có side effect bên ngoài transaction hoặc không idempotent. Retry là lớp resilience sau khi đã tối ưu lock behavior, không phải lý do bỏ qua deadlock rate cao.

Testing nên có concurrency test tạo approve/cancel cùng resource hàng trăm/lặp nhiều lần, không chỉ unit test. Tôi verify final state invariant, không chỉ assert HTTP 200. Ngoài ra cần load test với data volume/index statistics gần production.

Production telemetry tôi muốn có:

- deadlock count/rate;
- blocked request duration;
- SQL dependency p95/p99;
- transaction duration;
- deadlock victim query fingerprint;
- execution-plan changes nếu có khả năng regression;
- retry count/success;
- business conflict count nếu dùng optimistic concurrency.

Nếu deadlock graph cho thấy resource khác hoàn toàn giả thuyết ban đầu, recommendation sẽ thay đổi theo evidence thay vì cố ép design vào một pattern đã đoán trước.

## Mẫu trả lời trong phỏng vấn

“Em sẽ phân biệt deadlock với database quá tải. Deadlock là cycle chờ tài nguyên; hai API có thể chạy dưới 100 ms riêng lẻ nhưng khi concurrent lại lock resource theo thứ tự ngược nhau. Em cần deadlock graph trước để biết statements, objects/indexes và lock modes thực tế.

Sau đó em kiểm tra transaction boundary, có I/O nào giữ transaction lâu không, SQL ordering EF Core thực sự phát ra, execution plan có scan/lock nhiều hơn dự kiến không và hai flow có thể thống nhất resource order không. Nếu approve/cancel là business conflict, em cân nhắc optimistic concurrency/state transition có điều kiện thay vì serialize quá rộng.

Em không tăng timeout để sửa deadlock. Retry deadlock có thể hợp lý nhưng phải bounded và operation phải retry-safe. Cuối cùng em chạy concurrency test, verify final business state và theo dõi deadlock rate, blocking, transaction duration và p99 sau fix.”

## Câu hỏi đào sâu

1. Nếu deadlock graph cho thấy hai statements đều update cùng một table nhưng qua hai indexes khác nhau, bạn điều tra tiếp điều gì?
2. Nếu bật snapshot-based isolation làm reader/writer blocking giảm nhưng writer/writer deadlock vẫn còn, bạn giải thích thế nào?
3. Một teammate muốn đặt retry 10 lần cho mọi SQL exception để “tăng reliability”; bạn phản biện ra sao?

## Lỗi trả lời thường gặp

- Đồng nhất deadlock với CPU/database overload.
- Tăng command timeout mà không xem deadlock graph.
- Đổi isolation level theo cảm tính.
- Không xem execution plan/index/transaction duration.
- Retry mọi lỗi SQL mà không xét idempotency và business side effects.

## Thang điểm 0–10

- **0–2:** Chỉ tăng timeout/retry hoặc “scale database”.
- **3–4:** Hiểu deadlock cycle nhưng thiếu evidence và transaction/query analysis.
- **5–6:** Có deadlock graph, ordering, transaction scope, index/plan và concurrency testing.
- **7–8:** Phân biệt blocking/deadlock, có optimistic concurrency, retry semantics và production telemetry tốt.
- **9–10:** Kết nối lock mechanism, execution plan, business invariant và operability thành một phương án có điều kiện, evidence-driven.

# Câu 2 — Kubernetes rollout làm pod restart liên tục dù application “vẫn chạy được”

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, readiness/liveness/startup probes, deployments, resource limits, graceful shutdown, observability, production incident response

## Bối cảnh

Một ASP.NET Core .NET 8 API trước đây chạy ổn trên Azure App Service được containerize và deploy lên Kubernetes.

Sau một release, production xuất hiện:

- một số Pods chuyển `Running` rồi restart;
- user thấy 502/503 theo từng đợt trong rollout;
- `kubectl describe pod` cho thấy liveness probe failures ở một số Pods;
- readiness và liveness hiện cùng gọi endpoint `/health`;
- `/health` kiểm tra cả SQL Server, Redis và một external review provider;
- khi review provider latency tăng, `/health` đôi lúc trả non-2xx;
- container startup mất 40–90 giây vì warm-up cache và load configuration;
- liveness bắt đầu kiểm tra khá sớm;
- resource limits vừa được giảm trong release để tăng density;
- team đề xuất tăng số replicas gấp đôi;
- một developer muốn bỏ toàn bộ probes vì “probe làm app restart”.

Chưa biết chắc:

- restart reason là probe failure, OOMKilled hay process crash cho từng Pod;
- CPU/memory throttling có xảy ra không;
- rollout strategy/maxUnavailable/maxSurge hiện tại;
- termination grace period và ASP.NET Core graceful shutdown có đủ không;
- `/health` response time và dependency breakdown;
- external review provider có thực sự là dependency bắt buộc để API nhận traffic hay chỉ một feature phụ.

## Câu hỏi chính

Bạn sẽ stabilize incident và phân biệt probe misconfiguration, resource pressure, application failure và dependency degradation như thế nào; sau đó bạn sẽ thiết kế lại startup/readiness/liveness để Kubernetes chỉ restart container khi đúng failure mode, đồng thời ngừng gửi traffic khi Pod chưa sẵn sàng?

## Câu hỏi làm rõ nên cân nhắc

1. `lastState`, exit code và events của Pods cho biết restart vì probe, OOM hay application exit?
2. API có thể phục vụ core requests khi Redis/review provider down không, hay dependency nào thật sự required?
3. Startup time distribution p50/p95 là bao nhiêu và warm-up có bắt buộc trước khi nhận traffic không?
4. CPU/memory usage, throttling và working set có chạm requests/limits không?
5. Khi rollout/termination, in-flight requests và background work được xử lý ra sao?

## Gợi ý tư duy

### Gợi ý 1

`Running` không đồng nghĩa `Ready`, và restart reason phải được xác minh từ Pod/container state cùng events.

### Gợi ý 2

Readiness và liveness trả lời hai câu hỏi khác nhau. Liveness không nên biến một dependency tạm thời chậm thành restart storm nếu process vẫn có thể hồi phục.

### Gợi ý 3

Startup probe có thể bảo vệ ứng dụng khởi động chậm khỏi bị liveness giết quá sớm; resource limits và rollout behavior vẫn phải được điều tra độc lập.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact và rollback/pause rollout nếu cần.
2. Phân loại restart reason bằng Pod events/container state.
3. Correlate probes với CPU/memory/dependency latency.
4. Tách startup/readiness/liveness semantics.
5. Xác định critical vs degradable dependencies.
6. Thiết kế resource requests/limits dựa trên measurement.
7. Thiết kế graceful termination và rollout safety.
8. Failure/load/dependency tests.
9. Monitoring và alerting.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định mọi restart đều do liveness chỉ vì có probe failure logs.
- Kiểm tra `OOMKilled`, exit code, events, restart count và resource metrics.
- Phân biệt startup, readiness và liveness.
- Liveness tập trung vào khả năng process/app tự tiến triển, không phụ thuộc tùy tiện vào mọi external dependency.
- Readiness quyết định có nên nhận traffic tại thời điểm hiện tại.
- Startup probe phù hợp với app có startup lâu khi cần trì hoãn liveness/readiness cho tới khi startup hoàn tất.
- Phân loại required dependency và optional/degradable dependency.
- Có graceful shutdown/traffic draining trong rollout.
- Không chỉ tăng replicas nếu mỗi Pod vẫn bị cùng lỗi cấu hình hoặc resource pressure.

### Điểm cộng

- Health endpoints rẻ, bounded-time và tránh tạo dependency amplification.
- Readiness có thể fail nếu critical dependency khiến Pod không thể phục vụ core contract, nhưng external feature phụ không nhất thiết làm cả Pod unready.
- Đề xuất separate health checks/tags cho liveness/readiness thay vì một endpoint chứa mọi dependency.
- Load test để đặt resource requests/limits từ working set/CPU thực tế.
- Quan sát throttling và OOM riêng với application latency.

### Senior+

- Phân tích cascading failure khi liveness restart Pods dưới dependency outage/high load, làm tải dồn lên Pods còn lại.
- Thiết kế rollout với surge/unavailable hợp lý theo capacity và readiness.
- Xử lý preStop/termination grace/in-flight request behavior có điều kiện theo workload.
- Đưa dependency degradation vào API design thay vì coi health probe là nơi duy nhất xử lý resilience.

## Hướng giải quyết tham khảo

Tôi sẽ stabilize trước. Nếu incident bắt đầu cùng release và error rate tăng, tôi cân nhắc pause/rollback rollout dựa trên blast radius. Tôi không chỉnh probes ngẫu nhiên ngay trong production trước khi biết restart reason.

Với từng Pod, tôi xem:

- previous container state;
- exit code/reason;
- `OOMKilled`;
- restart count;
- Kubernetes events;
- liveness/readiness failure timeline;
- CPU/memory usage và throttling;
- application logs/traces.

Nếu container bị OOMKilled, probe tuning không phải root fix. Nếu process exit do unhandled exception, cũng khác. Nếu container bị kubelet restart sau repeated liveness failures trong lúc process vẫn khỏe, probe semantics/config là suspect mạnh.

Theo Kubernetes documentation hiện hành, readiness quyết định Pod có sẵn sàng nhận traffic hay không, còn repeated liveness failure có thể khiến kubelet restart container. Startup probe, nếu cấu hình, trì hoãn liveness/readiness cho đến khi startup thành công. Vì vậy dùng cùng `/health` cho cả ba purpose thường dễ trộn failure modes.

Tôi sẽ tách conceptually:

- `/health/live`: kiểm tra process/app có còn khả năng hoạt động/tiến triển; không gọi external review provider và thường không phụ thuộc SQL/Redis nếu dependency outage không làm process “chết”.
- `/health/ready`: kiểm tra app đã initialization xong và những dependencies thật sự bắt buộc để đáp ứng core API contract có sẵn sàng hay không.
- startup probe: cho phép 40–90 giây warm-up mà không bị liveness xử lý quá sớm, với thresholds dựa trên startup distribution thực tế.

Tôi không đưa mọi dependency vào readiness một cách máy móc. Nếu review provider chỉ phục vụ ratings và API có thể trả response degraded/không có rating, review outage không nên làm toàn bộ Pod rời service. Ngược lại, nếu SQL là bắt buộc cho mọi request thì readiness có thể phản ánh inability to serve, nhưng check cần timeout ngắn và không tạo thêm load lớn lên SQL trong outage.

Resource limits cũng phải điều tra độc lập. Nếu release vừa giảm memory limit và Pods bị OOMKilled, tôi rollback/tăng limit dựa trên observed working set và peak allocation. Với CPU, quá thấp có thể tăng throttling, làm request/probe timeout rồi tạo secondary symptoms. Requests/limits phải capacity-plan bằng load test và production metrics.

Graceful rollout:

- readiness phải chuyển false trước khi Pod nhận traffic mới khi termination path bắt đầu theo platform lifecycle;
- application cần xử lý SIGTERM/graceful shutdown và dừng nhận work mới;
- `terminationGracePeriodSeconds` phải phù hợp in-flight request duration/background work;
- long-running background work nên có idempotency/requeue strategy thay vì giả định Pod sống đến completion.

Tôi xem Deployment strategy: nếu capacity chỉ vừa đủ mà rollout cho quá nhiều unavailable Pods, error rate tăng dù từng Pod bình thường. `maxUnavailable`/`maxSurge` phải phù hợp capacity và startup time.

Testing trước release gồm:

- startup 2 phút;
- SQL unavailable;
- Redis unavailable;
- optional provider timeout;
- CPU throttling;
- memory pressure;
- SIGTERM khi có in-flight requests;
- rolling deployment dưới load.

Monitoring cần:

- restart count/reason;
- readiness/liveness failures theo endpoint;
- startup duration;
- CPU throttling;
- memory working set/OOM;
- request error/p95/p99;
- dependency latency;
- available/ready replica count;
- rollout duration.

Tài liệu chính thức Kubernetes về probes: https://kubernetes.io/docs/concepts/workloads/pods/probes/

## Mẫu trả lời trong phỏng vấn

“Em sẽ không kết luận probe là root cause chỉ vì thấy liveness failure. Em kiểm tra previous container state, exit code, OOMKilled, events, CPU/memory và timeline probe trước. Nếu release đang gây 5xx, em pause/rollback để giảm impact.

Sau đó em tách health semantics. Liveness chỉ nên trả lời app có cần restart để hồi phục hay không; readiness trả lời Pod có nên nhận traffic; startup probe bảo vệ app startup 40–90 giây khỏi bị liveness giết quá sớm. Em không để optional review provider làm liveness fail và tạo restart storm. Critical dependencies chỉ đưa vào readiness nếu thật sự làm core API không thể phục vụ.

Em cũng kiểm tra resource limits và rollout capacity, vì OOM/throttling có thể tạo probe failure thứ cấp. Cuối cùng em test dependency outage, slow startup, SIGTERM, rolling deployment dưới load và monitor restart reason, ready replicas, throttling, OOM, probe failures và p99.”

## Câu hỏi đào sâu

1. Nếu SQL Server down toàn vùng trong 10 phút, readiness của API nên fail hay vẫn pass? Điều gì quyết định?
2. Nếu liveness endpoint chỉ kiểm tra process nhưng app bị ThreadPool starvation và gần như không phục vụ request, bạn thiết kế signal nào để tránh false healthy/false restart?
3. Một teammate đề xuất tăng `failureThreshold` rất lớn để không restart nữa; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Xóa probes hoàn toàn thay vì sửa semantics.
- Dùng cùng dependency-heavy endpoint cho liveness và readiness.
- Bỏ qua OOMKilled/resource throttling.
- Tăng replicas mà không sửa restart storm hoặc capacity bottleneck.
- Không kiểm tra graceful shutdown/rollout behavior.

## Thang điểm 0–10

- **0–2:** Chỉ tăng replicas hoặc bỏ probes.
- **3–4:** Biết readiness/liveness khác nhau nhưng thiếu evidence và resource analysis.
- **5–6:** Tách probes đúng, kiểm tra restart reason, resources và dependencies.
- **7–8:** Có startup, graceful rollout, degradation strategy, load/failure tests và telemetry.
- **9–10:** Phân tích được cascading failure và thiết kế health/resource/deployment semantics theo workload, không theo checklist.

# Câu 3 — Thiết kế release pipeline cho .NET + SQL sao cho deploy nhanh nhưng rollback không phá dữ liệu

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** CI/CD, Git, Jenkins, TeamCity, Octopus Deploy, Azure App Service, SQL Server, database migrations, deployment safety, rollback, testing, observability, architecture decision-making

## Bối cảnh

Một enterprise web platform gồm:

- ASP.NET Core .NET 8 API;
- Vue.js frontend;
- SQL Server;
- Redis;
- Azure App Service;
- source code trong Git/Azure Repos;
- CI hiện dùng Jenkins;
- deployment environments hiện được Octopus Deploy điều phối;
- một số team khác trong công ty dùng TeamCity.

Hiện release process có các vấn đề:

- build lại artifact ở từng environment;
- database migration chạy tự động khi application startup;
- migration đôi khi mất vài phút và giữ locks;
- deploy application và schema change diễn ra cùng lúc;
- rollback application version có thể gặp schema mới không tương thích;
- config/secrets khác nhau giữa environments và từng có lỗi “staging chạy, production fail”;
- smoke test chủ yếu thủ công;
- một hotfix gần đây rollback code thành công nhưng database đã drop một column cũ nên version trước không chạy được.

Leadership muốn release nhiều lần mỗi tuần và giảm downtime.

Một developer đề xuất chuyển toàn bộ sang Kubernetes để có rolling deployment. Một người khác muốn giữ Jenkins + Octopus nhưng “thêm nút rollback”. Một architect muốn mỗi deploy chạy migration destructive trước để database luôn ở schema mới nhất.

Chưa biết chắc:

- application có thể chạy song song hai versions trong rollout hay không;
- schema change types thường gặp;
- data volume/table sizes;
- RTO/RPO và downtime budget;
- App Service deployment slots có phù hợp networking/config hiện tại không;
- test automation hiện có mức nào;
- secrets/config đang quản lý qua Key Vault hay variable store khác;
- team có thực sự cần đổi CI tool không.

## Câu hỏi chính

Hãy thiết kế một release pipeline và database-evolution strategy cho hệ thống này sao cho artifact nhất quán, application/database tương thích trong rolling hoặc slot-based rollout, có automated validation, rollback/recovery rõ ràng và không tăng complexity chỉ để đổi công cụ.

## Câu hỏi làm rõ nên cân nhắc

1. Trong lúc rollout, old và new application version có thể cùng truy cập một database không?
2. Những migration nào có nguy cơ lock/rewrite bảng lớn hoặc destructive change?
3. Rollback requirement là code rollback trong vài phút hay cần cả data rollback?
4. App Service deployment slots hiện có thể dùng với configuration/secrets/network dependencies không?
5. CI/CD pain hiện tại đến từ Jenkins/Octopus hay từ pipeline design, artifact/config/migration practices?

## Gợi ý tư duy

### Gợi ý 1

“Build once, promote the same artifact” giải quyết một class drift mà đổi CI product không tự động giải quyết.

### Gợi ý 2

Code rollback và database rollback là hai bài toán khác nhau. Destructive schema change thường cần expand/contract qua nhiều releases.

### Gợi ý 3

Deployment strategy phải bảo đảm old/new version compatibility trong transition window, có health validation và observable rollback trigger.

## Cấu trúc trả lời đề xuất

1. Làm rõ availability/rollback/data constraints.
2. Chuẩn hóa build artifact và provenance.
3. Tách configuration/secrets khỏi artifact.
4. Thiết kế test gates theo risk.
5. Thiết kế backward-compatible schema evolution.
6. Chọn deployment slots/rolling strategy theo hosting hiện tại.
7. Thiết kế migration execution/locking safety.
8. Thiết kế rollback và forward-fix paths.
9. Observability + automated verification.
10. Đánh giá có cần đổi Jenkins/Octopus/hosting hay không.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Build artifact một lần và promote cùng artifact qua environments.
- Không chạy migration nguy hiểm một cách implicit ở mọi application startup/multiple instances.
- Schema changes phải backward-compatible khi old/new versions coexist.
- Dùng expand-contract cho rename/drop/type migration phức tạp.
- Tách secrets/config khỏi artifact và validate config trước cutover.
- Có automated tests/smoke/health checks trước và sau deploy.
- Rollback code chỉ an toàn nếu schema vẫn tương thích.
- Có kế hoạch cho long-running/blocking migrations.
- Không mặc định Kubernetes là cần thiết để có deployment an toàn.

### Điểm cộng

- Versioned artifact + commit SHA/build metadata/SBOM hoặc provenance phù hợp.
- Dedicated migration step/job với single execution, timeout/lock awareness và audit.
- Slot/canary rollout khi App Service đáp ứng requirement.
- Feature flags tách code deployment khỏi feature activation ở use case phù hợp.
- Synthetic/Playwright smoke tests cho critical journeys.

### Senior+

- Thiết kế multi-release expand-contract cho data backfill lớn.
- Có pre-deploy compatibility check giữa app version và schema version.
- Có rollback decision based on telemetry/error budget chứ không chỉ manual observation.
- Phân biệt reversible migration, irreversible migration và recovery bằng backup/restore/forward-fix.
- Đánh giá tool migration theo business value thay vì preference.

## Hướng giải quyết tham khảo

Tôi sẽ giữ nguyên nguyên tắc trước khi chọn tool: **build once, promote the exact same artifact**. CI tạo một immutable/versioned backend artifact và frontend artifact hoặc image/package theo deployment model; artifact mang commit SHA/build metadata. Staging và production không rebuild source vì rebuild có thể tạo dependency/toolchain drift.

Configuration và secrets được inject theo environment. Secrets không nằm trong repo/artifact; Azure Key Vault/Managed Identity hoặc cơ chế organization-approved có thể dùng tùy architecture. Pipeline có preflight validation để fail sớm nếu required config/secret/reference thiếu.

Tôi không để mọi application instance tự chạy migration ở startup cho production nếu migration có thể dài/destructive. Khi scale-out hoặc rolling deploy, nhiều instances cùng khởi động có thể cạnh tranh migration và startup coupling làm deployment khó kiểm soát. Tôi dùng một explicit migration stage/job với ownership, logging và failure handling rõ.

Database evolution theo expand-contract.

Ví dụ cần đổi `Customer.FullName` thành hai fields mới:

**Release A — Expand**

- add nullable/new columns hoặc schema mới backward-compatible;
- old application vẫn chạy được;
- new application có thể dual-write/read fallback nếu cần.

**Backfill**

- chạy batch có throttling/checkpoint;
- theo dõi locks, log growth, duration và error;
- có khả năng resume.

**Release B — Switch**

- new application đọc schema mới;
- vẫn giữ old fields đủ lâu cho rollback window nếu requirement cần.

**Release C — Contract**

- chỉ drop old column/constraint sau khi tất cả versions phụ thuộc cũ đã hết và rollback window đóng.

Với table lớn, tôi không coi DDL “chỉ vài dòng” là harmless. Tôi estimate execution/locking, test trên data volume gần production, chọn online/low-lock technique nếu SQL Server edition/operation hỗ trợ và business justify, hoặc backfill theo batches.

Deployment trên Azure App Service có thể dùng deployment slots nếu application/config/networking phù hợp. Flow có thể là:

1. deploy exact artifact vào staging slot;
2. run configuration/health checks;
3. run integration/synthetic tests;
4. warm up;
5. swap/cutover;
6. monitor telemetry;
7. rollback/swap back nếu app regression và schema vẫn compatible.

Nếu slots không phù hợp, vẫn có thể dùng staged/canary deployment pattern khác. Kubernetes không phải prerequisite cho release safety; chuyển platform chỉ để có rolling deployment tạo thêm operational cost không cần thiết nếu App Service đáp ứng NFR.

Test gates nên risk-based:

- unit/static analysis/SonarQube ở CI;
- integration/API tests với database contracts;
- migration test từ production-like previous schema snapshot;
- backward-compatibility tests old/new app với transitional schema khi cần;
- Playwright E2E cho critical flows;
- post-deploy smoke/synthetic checks.

Rollback design:

- application rollback là deploy/swap artifact trước;
- database rollback không mặc định `Down()` ngay cho destructive migrations;
- reversible schema change có thể reverse nếu đã test;
- data-destructive operation cần backup/recovery hoặc forward-fix strategy;
- vì vậy expand-contract làm code rollback khả thi hơn.

Redis/cache cũng cần compatibility: nếu serialized cache value/schema thay đổi, cache key versioning hoặc backward-compatible serialization tránh old/new versions đọc nhầm format.

Observability trước cutover phải có baseline và deployment marker:

- HTTP 5xx/error rate;
- p95/p99 latency;
- dependency errors;
- DB waits/locks/deadlocks;
- migration duration/failure;
- Redis errors;
- business KPI/synthetic journey;
- App Service instance/slot health.

Pipeline có automated stop/rollback threshold ở nơi đáng tin cậy, nhưng với migration irreversible tôi không quảng cáo “one-click rollback” giả tạo. Có những change cần forward-fix hoặc restore/recovery procedure.

Về Jenkins, TeamCity và Octopus: tôi không đổi chỉ vì team khác dùng tool khác. Tôi đánh giá reproducibility, security, maintainability, plugin/support risk, deployment features và operational ownership. Nếu Jenkins + Octopus hiện đáp ứng và pain nằm ở pipeline design, tôi sửa design trước. Tool migration là project riêng chỉ khi có business/operational benefit rõ.

## Mẫu trả lời trong phỏng vấn

“Em bắt đầu từ build once, promote same artifact; staging và production không rebuild. Config/secrets được inject và validate riêng. Database migration production không chạy implicit trên mỗi app startup mà có explicit migration stage với telemetry và single execution.

Để rollback code an toàn khi old/new versions coexist, em dùng expand-contract: release đầu add schema backward-compatible, backfill theo batch, release sau switch reads/writes, chỉ drop schema cũ sau khi rollback window đóng. Với table lớn em test lock/duration trên production-like data và không chạy destructive DDL theo cảm tính.

Trên App Service em ưu tiên slot/canary nếu phù hợp, warm-up + smoke/Playwright + health checks rồi cutover và monitor. Kubernetes không cần chỉ để có rollout tốt. Nếu telemetry xấu, code có thể swap/deploy lại version trước miễn schema vẫn compatible; irreversible data change có recovery/forward-fix riêng.

Em chỉ đổi Jenkins/Octopus khi tool thật sự là bottleneck; nếu pain nằm ở artifact, migration và validation thì đổi tool không giải quyết root cause.”

## Câu hỏi đào sâu

1. Nếu migration cần backfill 500 triệu rows trong nhiều giờ, bạn tách release và điều phối backfill thế nào để không block feature delivery?
2. Nếu old và new app versions serialize Redis value khác nhau, bạn bảo đảm rollout/rollback ra sao?
3. CTO yêu cầu chuyển sang Kubernetes vì “App Service không đủ enterprise”; bạn dùng tiêu chí nào để quyết định thay vì tranh luận theo preference?

## Lỗi trả lời thường gặp

- Rebuild artifact ở từng environment.
- Auto-migrate destructive schema ở application startup.
- Coi rollback code đồng nghĩa rollback database.
- Drop/rename column trong cùng release mà old version vẫn có thể chạy.
- Đổi CI/CD tool hoặc Kubernetes hóa trước khi sửa release-engineering fundamentals.

## Thang điểm 0–10

- **0–2:** Chỉ nói thêm nút rollback hoặc đổi platform/tool.
- **3–4:** Có CI/CD stages nhưng chưa giải quyết database compatibility.
- **5–6:** Có immutable artifact, explicit migration, automated validation và rollback cơ bản.
- **7–8:** Có expand-contract, slot/canary, large-data migration, cache compatibility và telemetry-driven rollout.
- **9–10:** Thiết kế release/data evolution theo failure modes và business constraints, phân biệt rõ reversible/irreversible change và cost của platform complexity.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Deadlock là concurrency cycle, không phải synonym của database overload:** cần deadlock graph, transaction boundary, execution plan và lock ordering để chẩn đoán đúng.
- **Health probes phải phản ánh đúng failure semantics:** startup, readiness và liveness có mục đích khác nhau; dependency degradation không nên vô tình tạo restart storm.
- **Resource limits và probe failures có thể tạo triệu chứng chồng lấn:** luôn xác minh OOM, throttling, container exit và events trước khi tune.
- **Release safety phụ thuộc compatibility, không phụ thuộc nút rollback:** old/new application và transitional schema phải coexist an toàn trong rollout window.
- **Expand-contract giúp giữ đường rollback:** destructive database changes nên tách khỏi thời điểm code cutover.
- **Tooling không thay thế engineering fundamentals:** Jenkins, TeamCity, Octopus, App Service hay Kubernetes chỉ tạo giá trị khi giải quyết requirement cụ thể.

## Mẫu tư duy cần nhớ

1. **Observe the wait/restart/deployment evidence before guessing the fix.**
2. **Reduce critical-section scope before increasing timeout or retries.**
3. **Model health by failure semantics, not by one generic `/health` endpoint.**
4. **Build once, promote the same artifact.**
5. **Design schema evolution for coexistence before designing rollback.**
