# Câu 1 — Vì sao ASP.NET Core trả file lớn làm tăng memory dù đã dùng async?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, streams, buffering, GC/LOH, cancellation, HTTP, Azure Blob Storage.

## Bối cảnh

API quản lý hồ sơ chạy .NET 8 trên Azure App Service Linux, bốn instances. Endpoint GET /api/documents/{id}/download lấy file từ Azure Blob Storage, kiểm tra quyền rồi trả về trình duyệt. File thường 2–15 MB, đôi khi 400 MB. Sau khi triển khai tính năng download đồng thời, memory tăng theo số request, p99 tăng và một số instance restart. Developer khẳng định endpoint “đã async hoàn toàn” vì dùng await ở mọi I/O. Không biết hiện tại code dùng DownloadContentAsync, MemoryStream, OpenReadAsync hay FileStreamResult; cũng chưa có memory dump.

## Câu hỏi chính

Giải thích cơ chế memory allocation, buffering, streaming và HTTP response pipeline khiến async không bảo đảm memory thấp. Bạn sẽ xác minh nguyên nhân và thiết kế lại endpoint thế nào để xử lý file lớn an toàn, kể cả client disconnect hoặc Blob Storage chậm?

## Câu hỏi làm rõ nên cân nhắc

1. API có phải proxy toàn bộ file, hay có thể cấp quyền tải trực tiếp bằng SAS ngắn hạn?
2. Endpoint đang đọc toàn bộ bytes trước khi ghi response hay copy theo từng chunk? Có reverse proxy/CDN buffering không?
3. File có yêu cầu Range requests, Content-Disposition, audit log hay kiểm tra quyền trước mỗi lần tải?
4. Memory tăng ở managed heap, LOH, native memory hay container working set? Số downloads đồng thời và giới hạn instance?
5. Khi client disconnect, request cancellation có truyền đến Blob SDK và response copy không?

## Gợi ý tư duy

### Gợi ý 1
Async giải phóng thread trong lúc chờ I/O; nó không tự giảm dung lượng dữ liệu đang giữ trong RAM.

### Gợi ý 2
Phân biệt materialize toàn bộ blob thành byte[] với sao chép tuần tự giữa hai stream.

### Gợi ý 3
Theo dõi allocation rate, LOH, GC pause, active downloads và peak concurrency; cân nhắc direct-to-Blob có kiểm soát.

## Cấu trúc trả lời đề xuất

1. Xác nhận contract download, authorization và constraints.
2. Vẽ đường đi Blob → process → HTTP client.
3. Giải thích allocation và lifetime của buffer, GC, backpressure.
4. Thu thập memory/trace/HTTP evidence và đối chiếu theo concurrency.
5. So sánh proxy streaming, direct SAS và buffering.
6. Đề xuất implementation, timeout/cancellation, giới hạn concurrency.
7. Kiểm thử tải, failure path, bảo mật và theo dõi sau deploy.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Phân biệt asynchronous I/O với streaming và buffering.
- Nhận diện full-file allocation, concurrent requests, LOH/GC pressure là **giả thuyết cần kiểm chứng**, không kết luận trước khi có số liệu.
- Nêu cách truyền CancellationToken và dispose streams đúng.
- Bảo vệ authorization và không để lộ Blob container công khai.

### Điểm cộng
- Hiểu HTTP response backpressure, Range requests, Content-Length, Content-Type, Content-Disposition.
- Phân tích chi phí outbound bandwidth, thời gian giữ kết nối và proxy buffering.
- Đề xuất giới hạn đồng thời theo năng lực instance và phương án giảm tải.

### Senior+
- Đưa ra lựa chọn có điều kiện giữa streaming qua API và direct download bằng user-scoped short-lived SAS.
- Đề cập revoke/expiry, audit, object version, kiểm soát filename, malware scanning trước khi cho tải.
- Có kế hoạch canary, rollback, SLO và kiểm chứng bằng load profile thực tế.

## Hướng giải quyết tham khảo

**Giả định:** File được lưu trong private Azure Blob Storage; API bắt buộc authorize user theo document ownership. Chưa có bằng chứng nguyên nhân memory.

**Cơ chế:** await cho phép thread không bị block trong lúc I/O đang chờ; nếu dùng DownloadContentAsync rồi chuyển toàn bộ dữ liệu thành BinaryData/byte[], hoặc CopyToAsync vào MemoryStream rồi ToArray, mỗi request vẫn giữ nhiều MB hoặc hàng trăm MB. Với N downloads đồng thời, tổng lượng memory có thể xấp xỉ N × kích thước file, cộng buffer, overhead, serialization, TLS và phần khác. Các allocation lớn có thể nằm trên Large Object Heap (LOH); Gen 2/LOH collection và memory fragmentation gây pressure. Không nên mặc định rằng mọi memory spike là LOH: phải đo.

**Xác minh:** Đọc code thực tế; capture dotnet-counters (GC Heap Size, allocation rate, Gen 2 GC count, working set), memory dump/heap profiling trong môi trường được phép, Application Insights request duration và dependency duration; so sánh theo file size, downloads đồng thời và thời điểm restart. Kiểm tra container OOM/restart reason và reverse proxy settings. Thử workload 1 MB, 100 MB, 400 MB với 1/10/50 concurrent clients và clients đọc chậm.

**Phương án A — proxy streaming:** Sau authorization, dùng BlobClient.OpenReadAsync với cancellation token và trả stream bằng FileStreamResult hoặc CopyToAsync trực tiếp vào response body; không materialize toàn bộ file. Gắn Content-Type từ metadata đã xác thực, Content-Disposition attachment và filename an toàn. Nếu cần Range, chọn API hỗ trợ range và kiểm tra behavior trên stack cụ thể; không tự tuyên bố hỗ trợ Range khi stream không seekable. ASP.NET Core có thể quản lý disposal cho stream được trả từ FileResult; với manual copy dùng await using và truyền RequestAborted. Cần cân nhắc response đã bắt đầu thì không thể trả ProblemDetails bình thường.

**Phương án B — direct Blob:** API xác thực và authorize rồi cấp user delegation SAS giới hạn read, blob cụ thể và thời gian ngắn qua Managed Identity; client tải trực tiếp từ Blob. Phương án này giảm memory, egress và connection pressure trên API, nhưng làm phức tạp CORS, audit từng lần tải, revocation, cache policy và khả năng hạn chế chia sẻ URL. SAS là bearer credential; không log token, dùng HTTPS và thời hạn tối thiểu.

**Giảm rủi ro:** Không dùng unbounded semaphore theo request nếu có thể dẫn đến backlog; áp concurrency cap/429 hoặc 503 có Retry-After theo capacity. Đặt timeout có chủ đích, truyền cancellation xuyên suốt, quan sát client disconnect; giới hạn file size theo nghiệp vụ. Cân nhắc scanning/quarantine và access logging. Không tối ưu compression cho dữ liệu đã nén như zip/pdf nếu lợi ích không đáng kể.

**Thử nghiệm và rollout:** Integration test file bytes/checksum, authorization, Range nếu hỗ trợ; load test peak memory và p95/p99; fault injection Blob slow/timeout, client disconnect; canary 5–10% traffic với rollback flag. Chỉ kết luận cải thiện khi cùng workload chứng minh memory/GC/latency giảm mà data integrity không đổi.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không suy ra memory leak chỉ từ việc App Service restart. Đầu tiên em hỏi endpoint đang materialize blob thành byte[] hay stream, file size và concurrency thực tế, rồi kiểm tra heap/LOH, allocation rate, GC và container OOM. await chỉ giải phóng thread trong lúc I/O chờ, không ngăn request giữ 400 MB trong RAM. Nếu API cần proxy, em chuyển sang streaming với cancellation, disposal và backpressure, xác minh Range/headers theo client contract. Nếu không cần API giữ kết nối, em cân nhắc user delegation SAS ngắn hạn sau authorization; đổi lại phải kiểm soát token, audit và expiry. Em chạy load test có client đọc chậm và fault injection, canary rollout, theo dõi p99, memory, GC và tỷ lệ lỗi trước khi mở rộng.”

## Câu hỏi đào sâu

1. Nếu client yêu cầu resume download bằng Range và Blob SDK stream không seekable, bạn xử lý thế nào?
2. Nếu compliance yêu cầu mọi byte đi qua API để DLP scanning, bạn còn chọn direct SAS không?
3. Khi memory ổn định nhưng p99 vẫn tăng dưới 100 downloads đồng thời, bạn đo và phân biệt network backpressure với ThreadPool starvation ra sao?

## Lỗi trả lời thường gặp

- Khẳng định async/await tự động tối ưu memory.
- Đề xuất GC.Collect hoặc tăng instance size mà không có profiling.
- Cấp SAS rộng quyền hoặc thời hạn quá dài.
- Bỏ qua client disconnect, stream disposal, headers và authorization.
- Không benchmark với slow consumers và nhiều downloads đồng thời.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ yêu cầu, giả định và security contract | 1.5 |
| Giải thích đúng buffering/async/GC | 2 |
| Đo đạc, phân biệt giả thuyết | 2 |
| Thiết kế streaming/direct SAS và trade-offs | 2 |
| Testing, telemetry, rollout và rollback | 1.5 |
| Trình bày rõ ràng, có thứ tự | 1 |

# Câu 2 — Sau deploy Octopus, IIS trả 503 ngắt quãng và App Pool recycle

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, .NET Framework 4.5 modernization, TeamCity/Octopus Deploy, health checks, incident response.

## Bối cảnh

Ứng dụng quản lý nhân sự ASP.NET MVC trên .NET Framework 4.5 chạy IIS/Windows Server sau load balancer, hai nodes. TeamCity build artifact; Octopus Deploy triển khai lần lượt lên hai nodes. Sau release, người dùng gặp 503 theo đợt, login session bị mất và một số request ghi dữ liệu thất bại. Event Viewer có sự kiện worker process restart, nhưng chưa biết đó là nguyên nhân hay hệ quả. CPU trung bình 35%, SQL Server vẫn phục vụ hệ thống khác bình thường. SLA nội bộ yêu cầu khôi phục trong 15 phút. Không được đổi kiến trúc trong incident.

## Câu hỏi chính

Bạn là on-call Technical Lead. Hãy trình bày trình tự xử lý từ business impact đến stabilization, chứng cứ, giả thuyết cạnh tranh, xác định root cause, hotfix/rollback, kiểm chứng và ngăn tái diễn; đặc biệt phân biệt App Pool recycle với deploy-induced downtime, session loss và lỗi upstream.

## Câu hỏi làm rõ nên cân nhắc

1. 503 do IIS trên node, load balancer hay reverse proxy tạo? Có correlation theo node, thời điểm, URL?
2. Octopus có drain node và health check trước/sau deployment không? Artifact/config trên hai nodes có giống nhau?
3. App Pool recycle theo schedule, memory limit, rapid-fail protection, config change, process crash hay deployment step?
4. Session là InProc, StateServer, SQLServer hay cookie-based? Có sticky sessions không?
5. Ứng dụng có startup warmup, dependency health checks, connection-string/secret changes, database migration hoặc file locking không?

## Gợi ý tư duy

### Gợi ý 1
503 không đủ để kết luận SQL hoặc CPU; xác định lớp tạo status và node ảnh hưởng.

### Gợi ý 2
Tách recycle bình thường, crash, startup failure, application_offline.htm và load balancer routing.

### Gợi ý 3
Dùng timeline ghép deployment steps, WAS/W3SVC Event Viewer, IIS logs, app logs và health transitions.

## Cấu trúc trả lời đề xuất

1. Xác định phạm vi tác động, tỷ lệ lỗi và luồng nghiệp vụ quan trọng.
2. Stabilize bằng rollback/drain node/disable traffic tùy tình trạng.
3. Thu thập timeline theo node, release, HTTP status/substatus, Event Viewer và telemetry.
4. Nêu ít nhất ba giả thuyết, bằng chứng xác nhận/bác bỏ.
5. Xác minh root cause bằng repro hoặc đối chiếu log.
6. Hotfix hoặc rollback có điều kiện, tránh làm mất dữ liệu.
7. Test release process, session strategy và recovery.
8. Báo cáo incident, SLO và hành động phòng ngừa.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Ưu tiên khôi phục dịch vụ; không thay đổi nhiều biến cùng lúc.
- Không đánh đồng recycle, crash, deployment outage và 503 từ load balancer.
- Phân tích session InProc có thể mất khi worker process restart.
- Thu thập evidence trước khi tuyên bố root cause.

### Điểm cộng
- IIS status/substatus, HTTPERR logs, WAS Event IDs, Windows Event Viewer, Failed Request Tracing khi phù hợp.
- So sánh build checksum, config transforms và Octopus release/task log từng node.
- Phân biệt request đã commit DB với client nhận 503; kiểm tra idempotency trước khi retry.

### Senior+
- Thiết kế zero/low-downtime release với drain/health gate/warmup/rollback.
- Nhận diện rủi ro database migration không backward compatible.
- Đưa ra điều kiện dừng rollout và runbook có owner, timeline, verification.

## Hướng giải quyết tham khảo

**Giả định chưa được xác minh:** Có hai IIS nodes sau load balancer; lỗi bắt đầu sau release. Tương quan thời gian không chứng minh deploy là root cause.

**Impact & stabilization:** Trong 2–3 phút đầu xác nhận login, write workflows, tỷ lệ 503 và node nào lỗi. Nếu một node healthy, drain node lỗi khỏi load balancer và theo dõi capacity; nếu cả hai lỗi sau release, xem xét rollback artifact/config sang bản đã biết tốt. Không rollback database migration phá compatibility khi chưa đánh giá. Thông báo ETA/impact cho stakeholders; tạm hạn chế retry các POST không idempotent.

**Evidence:** Tạo timeline UTC từ Octopus deployment log, IIS W3C logs (sc-status/sc-substatus/sc-win32-status), HTTPERR, Event Viewer Application/System (WAS/W3SVC/.NET Runtime), App Pool advanced settings, process crash dumps nếu có, Application Insights và load balancer health logs. So sánh artifact SHA, web.config transforms, machine keys, connection strings và IIS App Pool identity. Kiểm tra process start times, rapid-fail protection và application initialization. CPU 35% trung bình không loại trừ startup spike, crash hoặc node-specific issues.

**Các giả thuyết cạnh tranh:**
- H1: Deployment thay web.config/bin khiến AppDomain restart, health check chưa chờ warmup; LB gửi traffic quá sớm. Xác minh timestamp recycle, health probes và request 503 tập trung vào warmup window.
- H2: Worker process crash/rapid-fail protection do missing dependency, quyền filesystem hoặc configuration secret sai. Xác minh Event Viewer, crash exception, startup logs, app pool stopped state.
- H3: App Pool recycle do private memory limit/schedule/idle timeout hoặc manual recycle step. Xác minh IIS settings, recycle reason và memory/process counters.
- H4: Session InProc mất do recycle; nếu LB không stickiness hoặc machineKey khác nhau, login có thể fail khi chuyển node ngay cả khi app healthy. Xác minh session mode, auth cookie decryption, machineKey consistency.
- H5: LB health probe quá nông hoặc cấu hình routing sai, đưa node chưa sẵn sàng vào pool. Xác minh probe response, grace period và routing.

**Root cause:** Chỉ xác nhận sau khi bằng chứng loại trừ các H còn lại. Ví dụ *nếu* deploy log và WAS restart trùng thời điểm, LB route trước khi warmup, đồng thời InProc session reset, kết luận có thể là deployment health gating + session architecture; không được khẳng định nếu chưa có log.

**Khắc phục:** Khôi phục node tốt/rollback bản release, đảm bảo health check readiness đúng, warmup trước khi đưa traffic trở lại; bảo đảm shared machineKey/compatible session store nếu nghiệp vụ yêu cầu session sống qua recycle. Session store tập trung có trade-off latency/operational dependency; không nhất thiết triển khai trong hotfix. Tách deploy artifact khỏi config secret và kiểm tra per-node.

**Phòng ngừa:** TeamCity tạo immutable artifact, Octopus deploy từng node với drain → deploy → warmup → readiness → restore traffic; automated smoke tests login/read/write, rollback gate theo 5xx và p95. Schema changes theo expand-contract. Theo dõi IIS App Pool recycles, process crashes, 503 per node, LB unhealthy nodes, login failures và session resets. Game day mô phỏng recycle và rollback.

## Mẫu trả lời trong phỏng vấn

“Em ưu tiên khôi phục SLA trước. Em xác định 503 phát sinh ở IIS hay load balancer, node nào bị ảnh hưởng, rồi drain node lỗi hoặc rollback release nếu cần. Đồng thời ghép timeline Octopus với IIS/HTTPERR logs, WAS/Event Viewer, process restart và health checks. Em sẽ kiểm tra ít nhất ba khả năng: deployment gây restart nhưng LB gửi traffic quá sớm; worker crash do config/dependency; App Pool recycle do settings. Session loss có thể do InProc restart hoặc auth key giữa nodes không đồng nhất, nên không gộp mọi triệu chứng thành một root cause. Sau khi có evidence, em sửa health gating/warmup và session strategy phù hợp, chạy smoke test và canary rollout, theo dõi 503 theo node và recycle count. Database migration phải kiểm tra backward compatibility trước rollback.”

## Câu hỏi đào sâu

1. Nếu rollback application thành công nhưng schema migration đã thay đổi không tương thích, bạn khôi phục an toàn ra sao?
2. Nếu business không chấp nhận shared session store, có thể giảm session loss bằng cách nào và giới hạn của phương án đó?
3. Nếu 503 chỉ xuất hiện 20 giây mỗi lần deploy và không có crash, bạn chứng minh LB readiness là nguyên nhân thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng RAM hoặc restart IIS mà không xác định tầng phát lỗi.
- Kết luận “deploy lỗi” dựa trên tương quan thời gian.
- Bỏ qua InProc session, machineKey và rolling deployment.
- Rollback DB migration tùy tiện khi dữ liệu đã được ghi.
- Không có điều kiện kiểm chứng recovery và stop-the-line.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Xác định impact, ưu tiên stabilization | 2 |
| Thu thập evidence đúng tầng và timeline | 2 |
| Giả thuyết cạnh tranh, xác minh root cause | 2 |
| Remediation, rollback, session/deploy trade-offs | 2 |
| Testing, monitoring, incident communication | 1 |
| Trình bày rõ ràng, có ưu tiên | 1 |

# Câu 3 — Thiết kế luồng duyệt nội dung Optimizely CMS và phát hành đa kênh

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, content modeling, Vue.js, CDN/Akamai, REST API, Elasticsearch, security, consistency, deployment.

## Bối cảnh

Một doanh nghiệp vận hành website marketing và product landing pages. Editor dùng Optimizely CMS để soạn page types và content blocks, workflow yêu cầu Reviewer duyệt trước khi publish. Nội dung được hiển thị trên website ASP.NET Core và một Vue.js mobile web client; search sử dụng Elasticsearch, edge cache sử dụng Akamai. Mục tiêu: editor publish nội dung mới trong vài phút; bản chưa duyệt không được xuất hiện trên public site/search/CDN. Đôi khi chiến dịch phải rollback nội dung ngay lập tức. Team có sáu developers, vận hành một hệ thống CMS hiện hữu, ngân sách hạn chế; chưa rõ traffic, SLA và Optimizely version.

## Câu hỏi chính

Bạn sẽ thiết kế boundaries, content versioning, approval/publish workflow, delivery API, cache/search synchronization, security, rollback và observability như thế nào? Khi nào nên giữ monolith/CMS rendering, khi nào nên tách headless delivery, và bạn sẽ quyết định dựa trên bằng chứng gì?

## Câu hỏi làm rõ nên cân nhắc

1. Optimizely CMS version/hosting, content workflow capabilities và license hiện tại? Có multi-site/multi-language không?
2. Publish SLA là dưới 1 phút hay vài phút? Có yêu cầu rollback “ngay lập tức” theo giây không?
3. Traffic peak, cache hit rate, SEO/SSR, Core Web Vitals và mức độ personalization?
4. Search phải strong consistency với published content hay chấp nhận eventual consistency có cảnh báo?
5. Preview cho editor có được chia sẻ URL không? Quyền reviewer, audit và legal retention thế nào?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt draft, approved, published và publicly visible.

### Gợi ý 2
Mỗi downstream system (search index, CDN, frontend) có timeline riêng.

### Gợi ý 3
Định nghĩa một publish version/epoch và bảo đảm không để draft rò ra qua cache hoặc search.

## Cấu trúc trả lời đề xuất

1. Chốt yêu cầu publish/rollback, SEO, preview, scale và ngân sách.
2. Xác định content ownership, version và workflow states.
3. Phân ranh CMS authoring, delivery, search indexing, CDN, client.
4. Thiết kế API/content contract, localization và cache keys.
5. Chọn sync/async propagation và consistency contract.
6. Thiết kế security, preview isolation và rollback.
7. So sánh CMS-rendered, headless và hybrid.
8. Lập kế hoạch rollout, testing, observability và vận hành.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Draft/preview không truy cập công khai, không index, không cache chung.
- Published version là nguồn sự thật cho public delivery.
- Cache invalidation và search lag phải có chiến lược.
- Phân biệt CMS content ownership với Elasticsearch read model và CDN cache.

### Điểm cộng
- SEO với SSR/prerendering, canonical URLs, sitemap và redirect handling.
- Event/outbox hoặc retryable publish jobs có idempotency, reconciliation.
- Version-aware cache keys, purge strategy và rollback playbook.

### Senior+
- Định nghĩa SLA và tính khả thi của rollback khi CDN/search eventual consistency.
- Cân nhắc operational cost, editorial ergonomics, migration risk và team capacity.
- Threat modeling preview links, stale permissions, XSS trong rich text và content injection.

## Hướng giải quyết tham khảo

**Giả định:** CMS là source of truth, publish workflow của version đang dùng được xác minh trước; vài phút eventual consistency được chấp nhận cho search, nhưng draft leakage tuyệt đối không chấp nhận. Nếu business đòi atomic global visibility, cần nêu rằng CMS + CDN + search không tự cung cấp distributed atomic commit.

**Data model:** ContentId, Locale, RevisionId, WorkflowState, ApprovedBy, ApprovedAt, PublishedRevision, PublishedAt, Slug, CanonicalUrl, dependencies tới blocks/assets. Phân biệt approval với publish; một approved revision không tự động public nếu chưa qua publish transition. Validate references: published page không được embed draft block hoặc private asset. Cấu hình role-based approval, audit immutable và separation of duties theo requirement.

**Boundaries:** CMS authoring/approval giữ ownership. Delivery layer chỉ đọc published revision đã được authorize cho public; search index chứa published projection; Akamai cache public responses theo locale/path/version. Vue.js dùng delivery API có schema ổn định; nếu website yêu cầu SEO, server-rendered ASP.NET Core hoặc SSR cho Vue phải được cân nhắc. Không tách microservices chỉ để “đúng kiến trúc”.

**Publish flow:** Trong CMS transaction/state transition ghi published revision và durable event/outbox nếu kiến trúc hỗ trợ; worker idempotent đồng bộ search và trigger targeted CDN purge. Event chứa content ID + revision/sequence; worker chỉ apply version mới hơn, retry/backoff, DLQ/failed-job dashboard và reconciliation định kỳ. Outbox chỉ bảo đảm event không mất trong transaction DB nếu được triển khai đúng; không tự bảo đảm exactly-once ở external systems. Nếu CMS không hỗ trợ transactional outbox trực tiếp, dùng CMS events + persisted retry queue với reconciliation và chấp nhận rõ failure window.

**Cache/search:** Public API trả ETag/Cache-Control phù hợp; cache key gồm locale và content version hoặc purge URL/dependencies khi publish. Tránh cache personalized response dưới public key. Akamai purge propagation có độ trễ, cần xác minh theo contract nhà cung cấp; “rollback ngay” phải được lượng hóa. Search index dùng version-aware updates và tombstone khi unpublish; query filter published status không thay thế việc bảo đảm index không chứa draft. Reconciliation so sánh CMS published revision với search revision. Cần thiết kế fallback khi Elasticsearch down: hiển thị message/search degraded, không trả nội dung chưa duyệt.

**Preview/security:** Preview qua authenticated editor endpoint hoặc signed, short-lived preview token giới hạn revision, đặt Cache-Control: private, no-store, X-Robots-Tag: noindex; tách domain hoặc cache namespace khỏi public. Sanitize rich text, CSP và kiểm soát file uploads. Không cho public client tự chọn draft revision bằng query parameter không kiểm tra quyền.

**Rollback:** Chuyển published pointer về approved revision trước đó (hoặc unpublish), phát revision event mới có sequence tăng, purge CDN/search và xác minh public endpoints ở nhiều POPs. “Rollback” là publish operation mới; không đảo sequence về số cũ. Nếu legal/security cần chặn ngay nội dung độc hại, có emergency edge block hoặc deny rule riêng, thay vì tin rằng purge tức thì.

**Lựa chọn kiến trúc:** Nếu website hiện tại server-rendered đáp ứng SEO và Vue chỉ cần vài endpoints, giữ CMS-rendered + API mỏng để giảm cost. Nếu nhiều channels độc lập, UI releases riêng và content contracts rõ, cân nhắc headless/hybrid. Quyết định sau khi đo editorial throughput, p95, cache hit, release coupling và total cost; không rewrite toàn bộ khi chưa có migration plan.

**Testing & operations:** Integration tests state transitions, role separation, block references, revision monotonicity; E2E preview/public/search; fault injection event duplicate/out-of-order, search outage, purge failure; Playwright kiểm tra canonical/meta, noindex preview và published-only. Dashboard publish-to-visible lag p50/p95, stale index count, purge failures, leaked-draft security alarms, cache hit ratio, 4xx/5xx. Canary trên một locale/site, shadow compare content versions trước migration.

## Mẫu trả lời trong phỏng vấn

“Em bắt đầu bằng việc chốt publish SLA, rollback RTO, SEO và version Optimizely, vì các ràng buộc này quyết định có cần headless không. CMS giữ quyền sở hữu draft/approved/published revisions; public API chỉ expose published revision. Sau publish, em đồng bộ search và purge CDN qua retryable, idempotent jobs với revision sequence, vì các downstream không thể cập nhật atomically. Em tách preview khỏi public cache và enforce authorization, không cho draft đi vào index. Với rollback, em publish lại revision đã duyệt như một transition mới rồi verify CDN/search; nếu cần chặn ngay nội dung nguy hiểm, em dùng emergency edge block. Em ưu tiên giữ kiến trúc CMS hiện có nếu nó đáp ứng SEO và delivery, chỉ tách headless khi có nhu cầu đa kênh rõ ràng. Em kiểm chứng bằng E2E, failure injection và dashboard publish lag.”

## Câu hỏi đào sâu

1. Nếu business yêu cầu tất cả CDN POPs và search đổi nội dung cùng một thời điểm tuyệt đối, bạn giải thích giới hạn và đề xuất contract nào?
2. Nếu Optimizely version hiện tại không hỗ trợ transactional outbox, bạn làm thế nào để không mất publish events?
3. Nếu chỉ có một website SSR và một Vue.js widget nhỏ, liệu headless architecture có đáng chi phí không?

## Lỗi trả lời thường gặp

- Tự động đề xuất microservices/headless mà không có business driver.
- Coi approval và publish là cùng một trạng thái.
- Chỉ purge CDN mà bỏ qua search, browser cache và versioning.
- Để preview dùng chung cache key với public.
- Hứa hẹn strong consistency tức thời trên CDN/search mà không có cơ chế chứng minh.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Streaming không đồng nghĩa async:** Phải phân biệt non-blocking I/O với allocation, full buffering, GC/LOH và HTTP backpressure.
