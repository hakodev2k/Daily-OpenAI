# Code Review Challenge 1 — RabbitMQ consumer: retry làm phát sinh xử lý trùng

**Chủ đề:** Concurrency, message processing, idempotency, EF Core transaction
**Độ khó:** Senior+
**Thời gian review đề xuất:** 25 phút
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core worker nhận message `IssueTicket` từ RabbitMQ. Mỗi message tạo ticket trong SQL Server, trừ quota của event và gửi push notification. Hệ thống chạy 4 replicas. Khi downstream notification chậm hoặc worker restart, production đôi lúc có hai ticket cho cùng một booking, quota bị trừ hai lần, nhưng dashboard RabbitMQ không cho thấy message bị mất. Business yêu cầu ưu tiên không phát hành ticket trùng; notification có thể gửi chậm vài phút.

## Đoạn code cần review

```csharp
public sealed class TicketConsumer
{
    private readonly AppDbContext _db;
    private readonly INotificationService _notifications;
    private readonly ILogger<TicketConsumer> _logger;

    public TicketConsumer(
        AppDbContext db,
        INotificationService notifications,
        ILogger<TicketConsumer> logger)
    {
        _db = db;
        _notifications = notifications;
        _logger = logger;
    }

    public async Task HandleAsync(IssueTicket message)
    {
        var booking = await _db.Bookings
            .Include(x => x.Event)
            .SingleAsync(x => x.Id == message.BookingId);

        if (booking.TicketIssued)
            return;

        if (booking.Event.RemainingQuota <= 0)
            throw new InvalidOperationException("No quota");

        booking.Event.RemainingQuota--;

        var ticket = new Ticket
        {
            Id = Guid.NewGuid(),
            BookingId = booking.Id,
            UserId = booking.UserId,
            IssuedAtUtc = DateTime.UtcNow
        };

        _db.Tickets.Add(ticket);
        booking.TicketIssued = true;

        await _db.SaveChangesAsync();

        await _notifications.SendTicketIssuedAsync(
            booking.UserId,
            ticket.Id);

        _logger.LogInformation(
            "Ticket {TicketId} issued for booking {BookingId}",
            ticket.Id,
            booking.Id);
    }
}
```

- Quota có thể xuống sai khi nhiều booking khác nhau được xử lý đồng thời không?

## Kết quả code review tham khảo

### 1. Check-then-act không atomic — **Critical**

**Problem:** Nhiều consumers có thể cùng đọc `TicketIssued=false` rồi cùng tạo ticket.
**Why:** Isolation mặc định không biến chuỗi read/check/write thành mutual exclusion.
**Impact:** Duplicate ticket và sai quota.
**Fix:** Dùng invariant ở DB: unique constraint trên `Tickets.BookingId`; kết hợp concurrency control phù hợp cho booking/event hoặc atomic conditional update.

### 2. Quota update có lost update/concurrency anomaly — **Critical**

**Problem:** Nhiều booking của cùng event cùng decrement giá trị đã đọc.
**Impact:** oversell hoặc remaining quota không phản ánh số ticket thực tế.
**Fix:** Atomic conditional update (`RemainingQuota > 0`) hoặc concurrency token/transaction với retry có kiểm soát.

### 3. DB commit và notification không atomic — **High**

**Problem:** DB có thể commit rồi notification timeout. Broker retry sẽ chạy lại handler.
**Impact:** Side effect không nhất quán; nếu idempotency yếu có duplicate ticket, nếu return sớm thì notification có thể mất vĩnh viễn.
**Fix:** Transactional outbox: commit ticket + outbox record trong cùng DB transaction; worker riêng gửi notification và đánh dấu outbox processed.

### 4. Không có business idempotency key/invariant — **High**

**Problem:** Code dựa vào boolean mutable thay vì invariant mạnh.
**Fix:** Unique index theo booking hoặc business operation key. Application check chỉ là optimization, không phải correctness boundary.

### 5. Không truyền cancellation token — **Medium**

**Problem:** DB/external calls tiếp tục chạy khi consumer đang shutdown/cancel.
**Fix:** Propagate cancellation token theo contract của consumer.

### 6. External call nằm trên critical execution path — **Medium**

**Problem:** Notification latency kéo dài thời gian xử lý message.
**Fix:** Outbox/background delivery; retry riêng với backoff.

### 7. Failure classification chưa rõ — **Medium**

**Problem:** `No quota`, transient SQL failure và notification timeout cần retry policy khác nhau.
**Fix:** Phân loại permanent/transient errors; dead-letter hoặc mark business rejection thay vì retry vô hạn.

### 8. Observability chưa đủ — **Low**

**Problem:** Log success không có message/correlation/idempotency identifier và không đo retry/outbox lag.
**Fix:** Structured logs + tracing + metrics.

## Phiên bản code đề xuất

```csharp
public sealed class TicketIssuer
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public TicketIssuer(AppDbContext db, TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task HandleAsync(
        IssueTicket message,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        if (await _db.Tickets.AnyAsync(
                x => x.BookingId == message.BookingId,
                cancellationToken))
        {
            await tx.CommitAsync(cancellationToken);
            return;
        }

        var booking = await _db.Bookings
            .SingleAsync(x => x.Id == message.BookingId, cancellationToken);

        var affected = await _db.Events
            .Where(x => x.Id == booking.EventId && x.RemainingQuota > 0)
            .ExecuteUpdateAsync(
                setters => setters.SetProperty(
                    x => x.RemainingQuota,
                    x => x.RemainingQuota - 1),
                cancellationToken);

        if (affected != 1)
            throw new InvalidOperationException("No quota available.");

        var ticket = new Ticket
        {
            Id = Guid.NewGuid(),
            BookingId = booking.Id,
            UserId = booking.UserId,
            IssuedAtUtc = _timeProvider.GetUtcNow().UtcDateTime
        };

        _db.Tickets.Add(ticket);
        _db.OutboxMessages.Add(OutboxMessage.ForTicketIssued(ticket));

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }
}
```

Database phải có unique index trên `Tickets.BookingId`. Nếu hai consumers vượt qua `AnyAsync` cùng lúc, unique constraint vẫn là correctness boundary; duplicate-key conflict được phân loại thành idempotent success sau khi xác nhận record tương ứng đã tồn tại. Outbox dispatcher chịu trách nhiệm notification retry.

## Trade-offs

Unique constraint đơn giản và mạnh nhưng cần mapping business invariant chính xác. Optimistic concurrency phù hợp khi conflict hiếm; atomic conditional update thường tốt hơn cho hot counter. Serializable/pessimistic locking có thể đơn giản hóa reasoning nhưng tăng blocking/deadlock risk. Outbox thêm bảng, dispatcher và cleanup nhưng loại bỏ dual-write window giữa DB và notification.

## Cách kiểm thử

1. Chạy 20 handlers đồng thời với cùng `BookingId`: chỉ một ticket và quota chỉ giảm một.
2. Chạy đồng thời nhiều booking khi quota còn 3: không quá 3 ticket được phát hành.
3. Crash ngay sau DB commit: retry không tạo ticket thứ hai và outbox vẫn được gửi.
4. Notification fail nhiều lần: ticket không rollback; outbox retry và cuối cùng xử lý thành công hoặc chuyển trạng thái cần can thiệp.
5. Cancellation/shutdown: DB operation nhận cancellation và không để transaction dang dở.

## Quan sát trong production

Theo dõi `ticket_issue_attempts`, idempotent duplicates, DB concurrency conflicts, quota rejection rate, consumer retry/dead-letter count, outbox pending count/oldest age và notification failure latency. Trace nên nối message ID → DB transaction → outbox → notification. Alert khi outbox oldest age hoặc DLQ tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Unique constraint đã đủ chưa nếu quota thuộc một aggregate khác?
2. Nếu throughput rất cao trên một event duy nhất, bạn giảm contention trên quota như thế nào?
3. Nếu notification provider không hỗ trợ idempotency key, bạn đảm bảo mức nào và communicate guarantee ra sao?

# Code Review Challenge 2 — API tìm outlet: query tưởng chạy ở SQL nhưng kéo dữ liệu về memory

**Chủ đề:** EF Core query execution, SQL performance, cancellation, input bounds
**Độ khó:** Senior
**Thời gian review đề xuất:** 20 phút
**Số vấn đề cần tìm:** Khoảng 6–8 vấn đề

## Bối cảnh

Một API tìm outlet trong viewport bản đồ. Bảng `Outlets` có hàng triệu records. Sau khi traffic tăng, endpoint có p95 vài giây, memory allocation tăng và DB read cao. API cho phép client truyền bounding box và search text. Product yêu cầu response tối đa 200 outlets.

## Đoạn code cần review

```csharp
public async Task<IReadOnlyList<OutletDto>> SearchAsync(
    OutletSearchRequest request)
{
    var outlets = await _db.Outlets
        .Include(x => x.Brand)
        .Where(x => x.IsActive)
        .ToListAsync();

    var filtered = outlets
        .Where(x =>
            x.Latitude >= request.BottomLeftLat &&
            x.Latitude <= request.TopRightLat &&
            x.Longitude >= request.BottomLeftLng &&
            x.Longitude <= request.TopRightLng)
        .Where(x => string.IsNullOrWhiteSpace(request.Text) ||
                    x.Name.ToLower().Contains(request.Text.ToLower()))
        .OrderByDescending(x => x.Priority)
        .Take(200)
        .Select(x => new OutletDto(
            x.Id,
            x.Name,
            x.Brand.Name,
            x.Latitude,
            x.Longitude))
        .ToList();

    return filtered;
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ active outlets trước khi filter — **Critical**

**Problem:** `ToListAsync()` execute SQL trước bounding-box/text/order/take.
**Impact:** DB trả lượng dữ liệu lớn qua network; app filter/sort trong memory; allocation và latency tăng theo dataset.
**Fix:** Giữ `IQueryable` cho tới projection và `Take`, rồi `ToListAsync` cuối cùng.

### 2. Bounding-box filtering không được DB/index xử lý — **High**

**Problem:** Vì materialization sớm, mọi spatial/selective filtering xảy ra trong process.
**Fix:** Push predicate xuống SQL. Nếu workload phù hợp và DB lưu spatial point, cân nhắc spatial predicate/index; nếu dùng scalar lat/lng thì benchmark composite/covering/index strategy dựa execution plan thay vì giả định.

### 3. `Include(Brand)` tải entity graph không cần thiết — **High**

**Problem:** Endpoint chỉ cần DTO projection.
**Impact:** Extra columns/tracking/materialization.
**Fix:** Project trực tiếp `Select` sang DTO; EF có thể tạo join cần thiết cho `Brand.Name`.

### 4. Tracking không cần cho read-only endpoint — **Medium**

**Problem:** Entity query mặc định có tracking nếu context cấu hình mặc định.
**Fix:** `AsNoTracking()` cho read-only projection/entity query khi phù hợp.

### 5. `ToLower().Contains()` phía client gây allocation và semantics mơ hồ — **Medium**

**Problem:** Current code lowercase từng outlet trong memory; culture/case behavior không được xác định rõ.
**Fix:** Xác định requirement về case sensitivity/accent và dùng DB collation/operator phù hợp; PostgreSQL và SQL Server có khả năng/index strategy khác nhau.

### 6. Không validate bounding box — **Medium**

**Problem:** Invalid ranges hoặc viewport quá rộng có thể tạo expensive request hoặc kết quả sai, đặc biệt quanh antimeridian nếu sản phẩm hỗ trợ phạm vi đó.
**Fix:** Validate latitude/longitude/range/viewport policy và định nghĩa semantics rõ.

### 7. Không propagate cancellation — **Medium**

**Problem:** Client disconnect nhưng DB query có thể tiếp tục.
**Fix:** Nhận và truyền `CancellationToken` tới EF async call.

### 8. Ordering không có deterministic tie-breaker — **Low**

**Problem:** Nhiều rows cùng Priority có thể làm top 200 không ổn định.
**Fix:** Thêm secondary stable order phù hợp, ví dụ `ThenBy(x => x.Id)`.

## Phiên bản code đề xuất

```csharp
public async Task<IReadOnlyList<OutletDto>> SearchAsync(
    OutletSearchRequest request,
    CancellationToken cancellationToken)
{
    ValidateBoundingBox(request);

    var query = _db.Outlets
        .AsNoTracking()
        .Where(x => x.IsActive)
        .Where(x =>
            x.Latitude >= request.BottomLeftLat &&
            x.Latitude <= request.TopRightLat &&
            x.Longitude >= request.BottomLeftLng &&
            x.Longitude <= request.TopRightLng);

    if (!string.IsNullOrWhiteSpace(request.Text))
    {
        var text = request.Text.Trim();
        query = query.Where(x => x.Name.Contains(text));
    }

    return await query
        .OrderByDescending(x => x.Priority)
        .ThenBy(x => x.Id)
        .Take(200)
        .Select(x => new OutletDto(
            x.Id,
            x.Name,
            x.Brand.Name,
            x.Latitude,
            x.Longitude))
        .ToListAsync(cancellationToken);
}
```

Đoạn code trên sửa materialization boundary nhưng không tự khẳng định đây là index strategy tối ưu. Với hệ thống đã lưu geographic point và workload viewport search lớn, một spatial predicate/index có thể phù hợp hơn scalar latitude/longitude; quyết định phải dựa trên generated SQL, actual execution plan và benchmark với distribution dữ liệu production-like.

## Trade-offs

Scalar bbox dễ hiểu và portable nhưng index efficiency phụ thuộc selectivity và query shape. Spatial type/index phù hợp cho geographic queries phức tạp hơn nhưng tăng schema/provider complexity. `AsNoTracking` giảm tracking overhead cho reads nhưng không phù hợp nếu entity cần được update trong cùng context. Text search bằng `Contains` đơn giản nhưng có thể không scale cho search nâng cao; full-text/trigram/search engine chỉ nên thêm khi requirement và measurement chứng minh cần thiết.

## Cách kiểm thử

1. Integration test xác nhận generated query chỉ trả tối đa 200 rows và filtering diễn ra ở DB.
2. Benchmark viewport nhỏ/vừa/lớn với dataset production-like; đo p50/p95, logical reads, CPU và allocations.
3. Test invalid latitude/longitude, reversed corners và viewport vượt policy.
4. Test search case/collation theo business requirement trên DB engine thật.
5. Cancel request giữa query và xác nhận cancellation được propagate.

## Quan sát trong production

Theo dõi endpoint duration p50/p95/p99, returned row count, DB command duration, logical reads/query plan regressions, app allocation/GC, cancellation rate và timeout rate. Trace EF database span theo endpoint và lưu benchmark/execution-plan evidence khi thay đổi index/query.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao push filter xuống SQL vẫn có thể chậm dù chỉ trả 200 rows?
2. Khi nào spatial index tốt hơn index trên latitude/longitude?
3. Bạn chứng minh improvement là do query shape hay do warm cache như thế nào?

Hai challenge tập trung vào hai boundary thường gây lỗi production: **correctness boundary** của hệ thống concurrent/retry và **execution boundary** của EF Core query.
