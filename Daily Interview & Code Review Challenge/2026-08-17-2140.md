# Code Review Challenge 1 — Logic hết hạn dùng giờ local và hàm trên cột làm sai dữ liệu, bỏ index dưới tải

## Bối cảnh

Một Hangfire job chạy mỗi 5 phút để reset các cấu hình forwarding/delegation đã hết hạn. Dữ liệu được tạo từ nhiều nguồn: portal nội bộ, API mobile và một số integration chạy trên Azure. Một số server chạy UTC, một số môi trường cũ vẫn dùng local time.

Bảng `EmployeeMailConfigs` có khoảng 8 triệu record. Chỉ một phần nhỏ record active và có `EndTime` đã tới hạn tại mỗi lần chạy.

Production gần đây ghi nhận:

- có cấu hình bị reset sớm hoặc muộn vài giờ,
- behavior khác nhau giữa môi trường dev và production,
- sau khi dữ liệu tăng, query của job từ vài trăm ms lên hơn 20 giây,
- execution plan đôi lúc scan một lượng record rất lớn dù có index trên `EndTime`,
- một số record ở đúng boundary phút bị xử lý lặp lại ở nhiều lần chạy,
- khi job timeout, team không biết đang chậm ở query, update hay external cleanup,
- developer trước đó “fix” bằng cách tăng command timeout từ 30s lên 120s.

Giả định business rule là: mọi timestamp lưu trong database phải được hiểu theo UTC; một config cần reset khi `EndTime <= nowUtc`; job phải idempotent và không phụ thuộc timezone của process.

## Đoạn code cần review

```csharp
public sealed class ExpiredMailConfigJob
{
    private readonly AppDbContext _db;
    private readonly ILogger<ExpiredMailConfigJob> _logger;

    public ExpiredMailConfigJob(
        AppDbContext db,
        ILogger<ExpiredMailConfigJob> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        var now = DateTime.Now;

        var expired = await _db.EmployeeMailConfigs
            .Where(x =>
                x.IsActive &&
                x.EndTime.HasValue &&
                x.EndTime.Value.Date <= now.Date &&
                x.EndTime.Value.Hour <= now.Hour)
            .OrderBy(x => x.EndTime)
            .Take(5000)
            .ToListAsync(cancellationToken);

        foreach (var config in expired)
        {
            config.IsActive = false;
            config.ResetAt = DateTime.Now;

            _logger.LogInformation(
                "Reset expired mail config {ConfigId} with EndTime {EndTime}",
                config.Id,
                config.EndTime);
        }

        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### 1. Dùng `DateTime.Now` trong khi business timestamp được định nghĩa là UTC

**Problem:** `now` phụ thuộc timezone của process/server.  
**Why it happens:** `DateTime.Now` trả local time, trong khi business rule yêu cầu so sánh theo UTC.  
**Production impact:** Cùng một record có thể hết hạn sớm hoặc muộn tùy nơi job chạy; behavior có thể khác giữa dev, container, VM hoặc Azure.  
**Severity:** Critical  
**Recommended fix:** Dùng một nguồn UTC thống nhất như `DateTime.UtcNow` hoặc abstraction clock; chuẩn hóa storage và comparison theo UTC.

### 2. Predicate `Date + Hour` không tương đương `EndTime <= now`

**Problem:** So sánh ngày và giờ riêng lẻ bỏ qua phút, giây và có thể sai logic giữa các ngày.  
**Why it happens:** Business condition đơn giản bị tách thành các thành phần calendar. Ví dụ record hôm qua lúc 23:30 và `now` hôm nay 08:00 có `Date <=` đúng nhưng `Hour <=` sai, nên record đã hết hạn lại không được chọn.  
**Production impact:** Record có thể bị bỏ sót nhiều giờ hoặc tới lần chạy khác không xác định.  
**Severity:** Critical  
**Recommended fix:** So sánh trực tiếp `x.EndTime <= nowUtc`.

### 3. Gọi `.Date` và `.Hour` trên cột làm predicate kém sargable

**Problem:** Query biến đổi column trước khi so sánh.  
**Why it happens:** Database thường phải tính function/expression trên nhiều row thay vì dùng range predicate trực tiếp trên index column.  
**Production impact:** Index trên `EndTime` có thể không được tận dụng hiệu quả; scan/CPU/I/O tăng khi bảng lớn.  
**Severity:** High  
**Recommended fix:** Dùng range comparison trực tiếp trên column: `EndTime <= @nowUtc` và giữ các predicate khác theo dạng index-friendly.

### 4. `ResetAt` tiếp tục dùng local time

**Problem:** Metadata ghi nhận reset time không cùng semantic với `EndTime`.  
**Why it happens:** Code dùng `DateTime.Now` ở cả query và update.  
**Production impact:** Audit timeline khó đối chiếu; log, DB và external system có thể hiển thị timestamp lệch nhau.  
**Severity:** High  
**Recommended fix:** Ghi `ResetAt = nowUtc` từ cùng một clock value của lần xử lý hoặc lấy một timestamp UTC mới nếu business cần thời điểm commit gần hơn.

### 5. Không có cơ chế chống nhiều worker xử lý cùng batch

**Problem:** Hai job instance có thể đọc cùng các row `IsActive = true` trước khi worker nào commit.  
**Why it happens:** Selection và claim/update không atomic.  
**Production impact:** Dễ tạo duplicate downstream cleanup nếu sau này job có external side effect; log trùng; lock/update conflict.  
**Severity:** High  
**Recommended fix:** Nếu chỉ update DB idempotent thì duplicate có thể chấp nhận ở mức nhất định, nhưng nếu có side effect cần claim/lease, optimistic concurrency hoặc atomic state transition trước khi thực hiện bước ngoài DB.

### 6. Batch `Take(5000)` chưa có strategy rõ ràng khi backlog lớn

**Problem:** Query chỉ lấy 5.000 record nhưng không thể hiện rõ cách job tiếp tục cho tới khi hết backlog.  
**Why it happens:** Một lần run xử lý đúng một batch rồi dừng.  
**Production impact:** Nếu throughput tạo mới/hết hạn cao hơn tốc độ job, backlog tăng và record hết hạn bị trễ.  
**Severity:** Medium  
**Recommended fix:** Lặp theo batch với stop condition và max runtime, hoặc schedule worker liên tục; theo dõi `oldest_expired_age` để biết backlog có đang tăng.

### 7. Ordering chỉ theo `EndTime` chưa deterministic hoàn toàn

**Problem:** Nhiều row có thể cùng `EndTime`.  
**Why it happens:** Không có tie-breaker duy nhất.  
**Production impact:** Nếu mở rộng sang keyset pagination, cursor có thể skip/duplicate row ở boundary.  
**Severity:** Medium  
**Recommended fix:** Order theo `(EndTime, Id)` và dùng composite cursor nếu pagination theo keyset.

### 8. Tracking 5.000 entity chỉ để đổi hai field có thể tạo overhead không cần thiết

**Problem:** EF Core materialize và track toàn bộ entity.  
**Why it happens:** Job dùng `ToListAsync` rồi update từng entity.  
**Production impact:** Memory allocation và change detection tăng; job dài hơn khi backlog lớn.  
**Severity:** Medium  
**Recommended fix:** Tùy version/provider và yêu cầu audit, cân nhắc bulk/update set-based; nếu giữ entity update thì dùng batch nhỏ, context ngắn và chỉ select dữ liệu cần thiết.

### 9. Log một dòng cho từng record dễ tạo log storm

**Problem:** 5.000 row mỗi run tạo tối đa 5.000 log info.  
**Why it happens:** Audit và operational logging bị trộn lẫn.  
**Production impact:** Tăng I/O, cost và làm log quan trọng bị chìm.  
**Severity:** Medium  
**Recommended fix:** Log summary theo batch; nếu cần audit từng record, dùng audit store/event riêng hoặc sampling/policy phù hợp.

### 10. Tăng command timeout chỉ che triệu chứng

**Problem:** Timeout lớn hơn không sửa predicate sai hoặc query plan kém.  
**Why it happens:** Điều trị symptom thay vì root cause.  
**Production impact:** Request/job giữ connection và resource lâu hơn, có thể làm pool pressure xấu hơn.  
**Severity:** Medium  
**Recommended fix:** Đo execution plan, rows read, index usage và sửa query shape trước; timeout chỉ là guardrail phù hợp với workload sau khi query đã đúng.

## Phiên bản code đề xuất

```csharp
public interface IClock
{
    DateTime UtcNow { get; }
}

public sealed class ExpiredMailConfigJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IClock _clock;
    private readonly ILogger<ExpiredMailConfigJob> _logger;

    public ExpiredMailConfigJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IClock clock,
        ILogger<ExpiredMailConfigJob> logger)
    {
        _dbFactory = dbFactory;
        _clock = clock;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        const int batchSize = 1000;
        const int maxBatches = 20;

        var nowUtc = _clock.UtcNow;
        var processed = 0;

        for (var batch = 0; batch < maxBatches; batch++)
        {
            await using var db = await _dbFactory
                .CreateDbContextAsync(cancellationToken);

            var configs = await db.EmployeeMailConfigs
                .Where(x =>
                    x.IsActive &&
                    x.EndTime.HasValue &&
                    x.EndTime <= nowUtc)
                .OrderBy(x => x.EndTime)
                .ThenBy(x => x.Id)
                .Take(batchSize)
                .ToListAsync(cancellationToken);

            if (configs.Count == 0)
                break;

            foreach (var config in configs)
            {
                if (!config.IsActive)
                    continue;

                config.IsActive = false;
                config.ResetAt = nowUtc;
            }

            await db.SaveChangesAsync(cancellationToken);
            processed += configs.Count;

            _logger.LogInformation(
                "Reset {Count} expired mail configs in batch {Batch}",
                configs.Count,
                batch + 1);

            if (configs.Count < batchSize)
                break;
        }

        _logger.LogInformation(
            "Expired mail config job completed. Processed {Processed} configs at {NowUtc}",
            processed,
            nowUtc);
    }
}
```

> Đây là phiên bản cải thiện tối thiểu theo hướng correctness + batching. Nếu job còn gọi Microsoft Graph/Exchange Online hoặc side effect bên ngoài, cần thêm state machine/claim/lease/idempotency thay vì chỉ dựa vào `IsActive`.

## Trade-offs

- Giữ EF tracking giúp implementation và audit đơn giản, nhưng với backlog rất lớn sẽ kém hiệu quả hơn set-based update.
- Set-based update có throughput cao hơn nhưng có thể bỏ qua domain logic, per-record audit hoặc hook đang dựa trên entity tracking.
- Batch nhỏ giảm transaction duration và memory nhưng tăng số round-trip.
- Dùng một `nowUtc` cố định cho cả run tạo boundary nhất quán. Nếu run kéo dài rất lâu và business muốn “mọi record vừa hết hạn trong lúc run cũng được xử lý”, có thể refresh clock theo batch.
- Nếu có nhiều worker, có thể cần claim/lease hoặc DB locking strategy tùy provider. Không nên thêm distributed lock nếu chưa xác định invariant cần bảo vệ.

## Cách kiểm thử

1. **Boundary test:** `EndTime` trước, đúng bằng và sau `nowUtc` 1 tick/1 giây; chỉ `<= nowUtc` được chọn.
2. **Timezone test:** Chạy cùng dataset với process timezone khác nhau; kết quả phải giống nhau vì logic chỉ dùng UTC.
3. **Database performance test:** Seed vài triệu row, đa số chưa hết hạn; kiểm tra execution plan/rows read và latency với index phù hợp.
4. **Backlog test:** Tạo 25.000 row hết hạn; verify batch loop xử lý theo giới hạn thiết kế và không bỏ sót.
5. **Concurrency/retry test:** Chạy hai job đồng thời hoặc kill job giữa chừng; verify DB state cuối cùng đúng và side effect (nếu có) không duplicate ngoài policy.

## Quan sát trong production

- Metric: `expired_config_backlog_count`, `oldest_expired_age`, `processed_per_run`, `job_duration`, `db_query_duration`.
- Structured log: run id, batch number, count, min/max `EndTime`, outcome; tránh log từng record ở mức Information.
- Trace: span riêng cho select batch và save batch.
- Database: execution plan, index seek/scan, logical reads, rows read vs rows returned, lock wait, command timeout.
- Alert nếu `oldest_expired_age` tăng liên tục hoặc job duration tiến gần schedule interval.

# Code Review Challenge 2 — `BackgroundService` tạo task chồng lấn mỗi tick, bỏ cancellation và tự khuếch đại outage downstream

**Chủ đề:** async/await và cancellation, background jobs, concurrency, HTTP client usage, failure recovery, performance, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một service .NET chạy nền để đồng bộ trạng thái lịch từ một external API. Team muốn mỗi phút trigger một lượt sync. Một lượt bình thường mất 20–30 giây, nhưng khi external API chậm hoặc trả throttling, một lượt có thể kéo dài 3–5 phút.

Production ghi nhận:

- số request outbound tăng mạnh đúng lúc external API đang chậm,
- cùng một user có thể được sync nhiều lượt đồng thời,
- memory và số task active tăng dần trong thời gian outage,
- deploy/restart mất lâu vì process không shutdown nhanh,
- log có nhiều exception `TaskCanceledException` nhưng khó phân biệt request timeout với application shutdown,
- một số sync vẫn chạy sau khi host đã nhận tín hiệu stop,
- tăng số replica làm áp lực lên downstream tệ hơn.

Business yêu cầu:

- không được có hai full-sync cycle chồng lấn trên cùng instance,
- khi host shutdown thì không bắt đầu cycle mới và cycle đang chạy phải nhận cancellation,
- lỗi của một cycle không được làm service chết vĩnh viễn,
- cần backoff khi dependency chậm/throttled,
- nếu sau này cần scale nhiều instance thì phải xác định rõ coordination có cần global hay không.

## Đoạn code cần review

```csharp
public sealed class CalendarSyncWorker : BackgroundService
{
    private readonly CalendarSyncService _syncService;
    private readonly ILogger<CalendarSyncWorker> _logger;

    public CalendarSyncWorker(
        CalendarSyncService syncService,
        ILogger<CalendarSyncWorker> logger)
    {
        _syncService = syncService;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        while (await timer.WaitForNextTickAsync())
        {
            _ = Task.Run(async () =>
            {
                try
                {
                    _logger.LogInformation("Starting calendar sync");

                    await _syncService.SyncAllUsersAsync(
                        CancellationToken.None);

                    _logger.LogInformation("Calendar sync completed");
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex, "Calendar sync failed");
                }
            });
        }
    }
}

public sealed class CalendarSyncService
{
    private readonly HttpClient _httpClient;
    private readonly AppDbContext _db;

    public CalendarSyncService(
        HttpClient httpClient,
        AppDbContext db)
    {
        _httpClient = httpClient;
        _db = db;
    }

    public async Task SyncAllUsersAsync(CancellationToken cancellationToken)
    {
        var userIds = await _db.Users
            .Where(x => x.IsActive)
            .Select(x => x.Id)
            .ToListAsync(cancellationToken);

        foreach (var userId in userIds)
        {
            var response = await _httpClient.GetAsync(
                $"api/calendar/{userId}",
                cancellationToken);

            response.EnsureSuccessStatusCode();
        }
    }
}
```

## Gợi ý

## Kết quả code review tham khảo

### 1. Fire-and-forget `Task.Run` làm cycle chồng lấn không giới hạn theo thời gian

**Problem:** Mỗi tick tạo một task mới và loop không await cycle đó.  
**Why it happens:** `Task.Run` được fire-and-forget; timer tiếp tục tick mỗi phút.  
**Production impact:** Nếu một cycle mất 5 phút, có thể có nhiều cycle active cùng lúc; khi downstream chậm, hệ thống lại gửi nhiều request hơn và khuếch đại outage.  
**Severity:** Critical  
**Recommended fix:** Nếu requirement là không overlap trên instance, await `SyncAllUsersAsync` trực tiếp trong loop hoặc dùng một coordination primitive rõ ràng; không fire-and-forget.

### 2. `CancellationToken.None` làm cycle không dừng khi host shutdown

**Problem:** Tín hiệu stop của host bị bỏ qua.  
**Why it happens:** Token được thay bằng `CancellationToken.None`.  
**Production impact:** Deploy/restart chậm, outbound request tiếp tục chạy trong shutdown, state có thể dở dang.  
**Severity:** Critical  
**Recommended fix:** Truyền `stoppingToken` xuyên suốt DB query, HTTP call, delay/backoff và các bước con.

### 3. `WaitForNextTickAsync()` không nhận `stoppingToken`

**Problem:** Worker có thể tiếp tục chờ tick dù host đã yêu cầu dừng.  
**Why it happens:** Overload không truyền cancellation token được dùng.  
**Production impact:** Shutdown có thể chậm tới tick kế tiếp hoặc behavior stop kém rõ ràng.  
**Severity:** High  
**Recommended fix:** Dùng `WaitForNextTickAsync(stoppingToken)` và xử lý `OperationCanceledException` như shutdown bình thường.

### 4. Task fire-and-forget không nằm trong lifecycle được `BackgroundService` await

**Problem:** `ExecuteAsync` không đại diện cho lifetime của các cycle đã tạo.  
**Why it happens:** Task con bị bỏ tham chiếu.  
**Production impact:** Host có thể coi worker đã dừng trong khi task con vẫn hoạt động; exception/lifecycle khó quản lý.  
**Severity:** High  
**Recommended fix:** Structured concurrency: task con quan trọng phải được await hoặc được quản lý bởi queue/worker framework có lifecycle rõ ràng.

### 5. Không có backoff/throttling strategy khi dependency chậm

**Problem:** Cycle mới vẫn được trigger theo lịch cố định dù external API đang lỗi/chậm.  
**Why it happens:** Scheduling không phản ứng với dependency health.  
**Production impact:** Thundering herd/self-amplification, tăng timeout, tăng throttling và recovery chậm hơn.  
**Severity:** High  
**Recommended fix:** Sau transient failure, dùng bounded retry/backoff/jitter hoặc delay cycle tiếp theo theo policy; không retry vô hạn và không retry lỗi permanent.

### 6. `HttpResponseMessage` không được dispose

**Problem:** Response object không có `using`.  
**Why it happens:** Code chỉ gọi `EnsureSuccessStatusCode()`.  
**Production impact:** Tài nguyên response có thể được giữ lâu hơn cần thiết; dưới workload lớn làm resource pressure tăng.  
**Severity:** Medium  
**Recommended fix:** `using var response = await _httpClient.GetAsync(...)`; nếu body lớn, cân nhắc `ResponseHeadersRead` và consume/dispose có chủ đích.

### 7. Load toàn bộ active user id vào memory mỗi cycle

**Problem:** `ToListAsync` materialize toàn bộ user id trước khi xử lý.  
**Why it happens:** Service batch model đơn giản.  
**Production impact:** Với hàng trăm nghìn user, allocation lớn và cycle dài; dễ làm overlap nếu scheduling sai.  
**Severity:** Medium  
**Recommended fix:** Batch/keyset pagination hoặc stream theo batch; theo dõi throughput/cursor.

### 8. Failure ở một user làm dừng toàn bộ cycle

**Problem:** `EnsureSuccessStatusCode()` ném exception và `foreach` kết thúc.  
**Why it happens:** Không có per-item error classification.  
**Production impact:** Một user lỗi có thể ngăn các user còn lại được sync; cycle tiếp theo lặp lại từ đầu.  
**Severity:** Medium  
**Recommended fix:** Tùy business, xử lý failure theo user với attempt/backoff/dead-letter hoặc tiếp tục các user khác; phân biệt auth/permanent/transient.

### 9. Không phân biệt cancellation do shutdown với timeout/dependency failure

**Problem:** `catch (Exception)` log mọi lỗi như `Calendar sync failed`.  
**Why it happens:** Cancellation không được coi là control flow hợp lệ.  
**Production impact:** Alert noise, khó biết shutdown bình thường hay dependency incident.  
**Severity:** Medium  
**Recommended fix:** Catch `OperationCanceledException` khi `stoppingToken.IsCancellationRequested` và log ở mức phù hợp; timeout độc lập cần metric/error code khác.

### 10. Không có coordination strategy khi scale nhiều replica

**Problem:** Không overlap chỉ trên một instance chưa chắc đủ nếu business muốn global single execution.  
**Why it happens:** Scope của invariant chưa được làm rõ.  
**Production impact:** 6 replica có thể chạy 6 full-sync song song và cùng sync một user.  
**Severity:** Medium  
**Recommended fix:** Làm rõ requirement. Nếu global exclusivity thực sự cần, dùng scheduler/queue partitioning/lease phù hợp; nếu không cần, partition workload theo user/tenant để scale có chủ đích.

## Phiên bản code đề xuất

```csharp
public sealed class CalendarSyncWorker : BackgroundService
{
    private static readonly TimeSpan Interval = TimeSpan.FromMinutes(1);

    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<CalendarSyncWorker> _logger;

    public CalendarSyncWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<CalendarSyncWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var started = Stopwatch.GetTimestamp();

            try
            {
                await using var scope = _scopeFactory.CreateAsyncScope();
                var syncService = scope.ServiceProvider
                    .GetRequiredService<CalendarSyncService>();

                _logger.LogInformation("Starting calendar sync cycle");

                await syncService.SyncAllUsersAsync(stoppingToken);

                _logger.LogInformation("Calendar sync cycle completed");
            }
            catch (OperationCanceledException)
                when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Calendar sync cycle failed");
            }

            var elapsed = Stopwatch.GetElapsedTime(started);
            var delay = elapsed >= Interval
                ? TimeSpan.Zero
                : Interval - elapsed;

            try
            {
                await Task.Delay(delay, stoppingToken);
            }
            catch (OperationCanceledException)
                when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
        }
    }
}

public sealed class CalendarSyncService
{
    private readonly HttpClient _httpClient;
    private readonly AppDbContext _db;
    private readonly ILogger<CalendarSyncService> _logger;

    public CalendarSyncService(
        HttpClient httpClient,
        AppDbContext db,
        ILogger<CalendarSyncService> logger)
    {
        _httpClient = httpClient;
        _db = db;
        _logger = logger;
    }

    public async Task SyncAllUsersAsync(CancellationToken cancellationToken)
    {
        const int batchSize = 500;
        Guid? lastId = null;

        while (!cancellationToken.IsCancellationRequested)
        {
            var query = _db.Users
                .AsNoTracking()
                .Where(x => x.IsActive);

            if (lastId.HasValue)
                query = query.Where(x => x.Id.CompareTo(lastId.Value) > 0);

            var userIds = await query
                .OrderBy(x => x.Id)
                .Select(x => x.Id)
                .Take(batchSize)
                .ToListAsync(cancellationToken);

            if (userIds.Count == 0)
                break;

            foreach (var userId in userIds)
            {
                cancellationToken.ThrowIfCancellationRequested();

                try
                {
                    using var response = await _httpClient.GetAsync(
                        $"api/calendar/{userId}",
                        cancellationToken);

                    response.EnsureSuccessStatusCode();
                }
                catch (OperationCanceledException)
                    when (cancellationToken.IsCancellationRequested)
                {
                    throw;
                }
                catch (HttpRequestException ex)
                {
                    _logger.LogWarning(
                        ex,
                        "Calendar sync failed for user {UserId}",
                        userId);
                }
            }

            lastId = userIds[^1];
        }
    }
}
```

> Ví dụ trên tập trung vào non-overlap, cancellation và lifecycle. Retry/backoff thực tế nên được thiết kế dựa trên semantics của external API và policy của `HttpClient`; không nên retry mọi status code hoặc mọi operation một cách mù quáng.

## Trade-offs

- Await cycle trực tiếp bảo đảm non-overlap nhưng nếu một cycle kéo dài 10 phút thì tần suất thực tế không còn mỗi phút. Đây thường là trade-off đúng nếu business ưu tiên không overlap.
- Nếu requirement là “mỗi phút phải tạo một unit of work” thay vì “mỗi phút phải bắt đầu full sync”, queue/scheduler có backpressure sẽ phù hợp hơn periodic full scan.
- Per-user error isolation tăng tiến độ nhưng có thể che một dependency outage toàn cục; cần circuit breaker/admission control ở mức phù hợp.
- Batch tuần tự an toàn nhưng throughput thấp. Có thể thêm bounded concurrency, nhưng phải giới hạn rõ và không dùng `Task.WhenAll` trên toàn bộ user.
- Multi-instance coordination chỉ nên thêm khi global exclusivity là requirement thật; nếu không, partition workload thường scale tốt hơn distributed lock.

## Cách kiểm thử

1. **Slow dependency test:** Mỗi HTTP call delay đủ để cycle vượt 1 phút; verify chỉ có một cycle active trên một instance.
2. **Shutdown test:** Gửi cancellation giữa DB query và giữa HTTP call; worker phải dừng hợp lý, không tạo cycle mới.
3. **Failure-path test:** External API trả 500/429/401 cho một số user; verify behavior đúng theo classification và không làm mất toàn bộ observability.
4. **Load test:** Hàng chục nghìn user, theo dõi memory, active tasks, outbound concurrency và cycle duration.
5. **Multi-replica test:** Chạy 3–6 instance; xác minh business requirement về duplicate/global coordination và đo tổng outbound pressure.

## Quan sát trong production

- Metric: `sync_cycle_duration`, `sync_cycle_active`, `users_processed`, `user_sync_failures`, `outbound_requests`, `outbound_latency`, `throttled_count`.
- Gauge/alert: nếu `sync_cycle_active > 1` trên cùng instance thì implementation đã vi phạm invariant.
- Log structured: cycle id, batch cursor, user id, outcome, cancellation reason, downstream status category.
- Trace: span cho cycle, batch và outbound HTTP; correlation với downstream request id nếu có.
- Alert nếu cycle duration tăng liên tục, throttling tăng, hoặc số user processed/cycle giảm mạnh.

## Câu hỏi phỏng vấn mở rộng

1. Nếu muốn parallel 10 user cùng lúc nhưng vẫn bảo vệ downstream, bạn thiết kế bounded concurrency và cancellation thế nào?
2. Nếu mỗi user phải được sync đúng một lần trong một cửa sổ 5 phút trên toàn cluster, bạn partition/claim workload ra sao?
3. Khi nào dùng Hangfire/queue scheduler sẽ phù hợp hơn tự viết `BackgroundService` + timer?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Time semantics phải là một phần của contract: nếu database lưu UTC thì mọi comparison, audit và boundary test phải nhất quán UTC.
- SQL predicate nên diễn đạt trực tiếp business condition và tránh biến đổi indexed column nếu một range predicate đơn giản có thể giải quyết.
- Background scheduling phải quản lý lifecycle của work; fire-and-forget trong service dài hạn dễ tạo overlapping task, mất cancellation và khuếch đại incident downstream.
- Cancellation token cần được truyền xuyên suốt từ host tới DB, HTTP và delay; shutdown là control flow hợp lệ chứ không phải lúc nào cũng là error.
- Batch processing cần deterministic ordering, throughput/backlog metric và strategy rõ ràng khi workload lớn hơn capacity.

## Mẫu tư duy cần nhớ

1. **Chuẩn hóa time semantics trước khi viết query.**
2. **Viết predicate theo business invariant, rồi kiểm tra generated SQL và execution plan.**
3. **Structured concurrency: task quan trọng phải được quản lý và await.**
4. **Downstream càng chậm, hệ thống của mình càng phải giảm áp lực thay vì tạo thêm concurrency.**
5. **Thiết kế observability cho backlog, cancellation và dependency pressure ngay từ đầu.**
