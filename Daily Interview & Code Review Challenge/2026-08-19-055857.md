# Code Review Challenge 1 — Hangfire gửi thông báo bị trùng khi retry và chạy đồng thời

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để gửi email nhắc lịch. API tạo một `Notification` trong SQL Server rồi enqueue job. Production chạy nhiều Hangfire workers trên hai application instances. Bình thường hệ thống ổn, nhưng khi Microsoft Graph hoặc SMTP gateway timeout, một số người dùng nhận 2–3 email giống nhau. Có trường hợp job báo failed dù email thực tế đã được gửi. Team muốn giữ cơ chế retry vì lỗi mạng thường chỉ tạm thời.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    public async Task SendAsync(long notificationId)
    {
        var notification = await _db.Notifications
            .FirstOrDefaultAsync(x => x.Id == notificationId);

        if (notification == null || notification.Status == "Sent")
            return;

        notification.Status = "Processing";
        notification.AttemptCount++;
        await _db.SaveChangesAsync();

        try
        {
            await _emailSender.SendAsync(
                notification.Email,
                notification.Subject,
                notification.Body);

            notification.Status = "Sent";
            notification.SentAtUtc = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            notification.Status = "Failed";
            notification.LastError = ex.ToString();
            await _db.SaveChangesAsync();

            _logger.LogError(ex,
                "Failed sending notification {@Notification}", notification);

            throw;
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Tìm rủi ro concurrency, retry và reliability.
3. Giải thích vì sao duplicate có thể xuất hiện dù có check `Status == "Sent"`.
4. Ưu tiên vấn đề theo mức ảnh hưởng.
5. Đề xuất implementation tốt hơn.
6. Giải thích cách kiểm thử failure window khó tái hiện.
7. Đề xuất logs, traces và metrics cần theo dõi.

## Câu hỏi gợi mở

- Hai worker có thể đọc cùng một row trước khi worker nào ghi `Processing` không?
- Nếu email provider nhận request thành công nhưng connection timeout trước khi client nhận response thì hệ thống biết email đã gửi hay chưa?
- `Processing` có thực sự là một distributed lock không?
- Retry một side effect bên ngoài khác retry một database transaction ở điểm nào?
- Có nên lưu toàn bộ `notification` vào structured log không?

## Gợi ý

### Gợi ý 1

Tách hai vấn đề: **nhiều worker cùng thực thi** và **không xác định được kết quả của external side effect sau lỗi mạng**.

### Gợi ý 2

Một transaction SQL không thể tự động biến thao tác gửi email qua mạng thành exactly-once. Hãy nghĩ đến atomic claim, optimistic concurrency, idempotency key/outbox và reconciliation.

## Kết quả code review tham khảo

### 1. Check-then-act không atomic

**Problem:** Hai worker có thể cùng đọc `Status != Sent`, sau đó đều gửi email.  
**Why:** Query và update `Processing` là các thao tác riêng; không có conditional atomic claim.  
**Production impact:** Duplicate side effects dưới concurrency.  
**Severity:** Critical.  
**Recommended fix:** Claim row atomically, ví dụ conditional `UPDATE ... WHERE Status IN (...)` và chỉ worker update thành công mới xử lý; hoặc dùng concurrency token phù hợp.

### 2. Retry không thể giải quyết ambiguous external outcome

**Problem:** Provider có thể đã nhận/gửi email nhưng client timeout trước response.  
**Why:** Database và email provider không nằm trong cùng atomic transaction.  
**Production impact:** Throw khiến Hangfire retry và gửi lại.  
**Severity:** Critical.  
**Recommended fix:** Nếu provider hỗ trợ idempotency/deduplication key thì dùng stable operation ID. Nếu không, thiết kế trạng thái `Unknown/NeedsReconciliation`, reconciliation hoặc chấp nhận at-least-once và làm side effect có khả năng dedupe ở boundary phù hợp.

### 3. `Processing` không ngăn worker khác

**Problem:** Việc ghi status không phải lock và code cũng không loại `Processing` khỏi điều kiện ban đầu.  
**Why:** Mọi status khác `Sent` đều tiếp tục.  
**Production impact:** Retry hoặc job duplicate có thể chạy đồng thời.  
**Severity:** High.  
**Recommended fix:** State machine rõ ràng và atomic transition `Pending/Retryable -> Processing`.

### 4. Không có recovery cho job chết sau khi claim

**Problem:** Nếu process crash sau khi chuyển `Processing`, row có thể mắc kẹt nếu implementation sau này bỏ qua `Processing`.  
**Why:** Không có lease/claimed timestamp.  
**Production impact:** Notification không bao giờ gửi.  
**Severity:** High.  
**Recommended fix:** Lưu `ProcessingStartedAtUtc`, lease expiry hoặc reconciliation job.

### 5. Không truyền cancellation token

**Problem:** EF và email operation không nhận cancellation token.  
**Why:** Signature không expose token.  
**Production impact:** Shutdown hoặc cancellation kéo dài, làm recovery khó dự đoán.  
**Severity:** Medium.  
**Recommended fix:** Propagate cancellation khi framework/job abstraction cho phép và phân biệt cancellation với retryable failure.

### 6. Catch mọi exception như retryable

**Problem:** Invalid email, invalid template và timeout đều bị xử lý giống nhau.  
**Why:** Không có error classification.  
**Production impact:** Retry vô ích, tăng tải và noise.  
**Severity:** Medium.  
**Recommended fix:** Phân loại permanent/transient/ambiguous failure; chỉ retry lỗi phù hợp.

### 7. Log có nguy cơ lộ dữ liệu

**Problem:** `{@Notification}` có thể serialize email/body hoặc dữ liệu nhạy cảm.  
**Why:** Log toàn entity.  
**Production impact:** PII/sensitive content đi vào logging backend.  
**Severity:** Medium.  
**Recommended fix:** Log ID, state, provider operation ID, attempt và error category; tránh body và dữ liệu nhạy cảm.

### 8. Dùng string làm state

**Problem:** State machine không được mô hình hóa chặt.  
**Why:** String dễ tạo trạng thái sai hoặc transition không hợp lệ.  
**Production impact:** Maintainability và correctness giảm.  
**Severity:** Low.  
**Recommended fix:** Enum/value mapping hoặc domain transition methods cùng database constraints nếu phù hợp.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa atomic claim bằng conditional update. Nó giảm duplicate do concurrent workers, nhưng **không tự giải quyết ambiguous outcome của email provider**.

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IEmailSender emailSender,
        TimeProvider timeProvider,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    public async Task SendAsync(long id, CancellationToken ct = default)
    {
        var now = _timeProvider.GetUtcNow();

        var claimed = await _db.Notifications
            .Where(x => x.Id == id &&
                        (x.Status == "Pending" || x.Status == "Retryable"))
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.ProcessingStartedAtUtc, now)
                .SetProperty(x => x.AttemptCount, x => x.AttemptCount + 1), ct);

        if (claimed == 0)
            return;

        var n = await _db.Notifications
            .AsNoTracking()
            .SingleAsync(x => x.Id == id, ct);

        try
        {
            await _emailSender.SendAsync(
                n.Email,
                n.Subject,
                n.Body,
                operationId: $"notification:{n.Id}",
                cancellationToken: ct);

            await _db.Notifications
                .Where(x => x.Id == id && x.Status == "Processing")
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "Sent")
                    .SetProperty(x => x.SentAtUtc, now), ct);
        }
        catch (EmailPermanentException ex)
        {
            await MarkAsync(id, "DeadLetter", ex.GetType().Name, ct);
            throw;
        }
        catch (Exception ex)
        {
            await MarkAsync(id, "Retryable", ex.GetType().Name, ct);
            _logger.LogWarning(ex,
                "Notification send failed. Id={NotificationId}", id);
            throw;
        }
    }

    private Task MarkAsync(long id, string status, string error, CancellationToken ct) =>
        _db.Notifications
            .Where(x => x.Id == id && x.Status == "Processing")
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, status)
                .SetProperty(x => x.LastError, error), ct);
}
```

Trong production, nếu việc tạo notification phải atomic với một business transaction khác, có thể dùng transactional outbox: commit business state + outbox record trong cùng database transaction, sau đó dispatcher gửi ra ngoài. Outbox đảm bảo không mất intent khi transaction commit nhưng không biến external delivery thành exactly-once; consumer/provider-side idempotency vẫn quan trọng.

## Trade-offs

Atomic conditional update đơn giản và phù hợp modular monolith, nhưng cần recovery cho lease bị treo. Distributed lock có thể hữu ích trong một số workload nhưng không giải quyết ambiguous external outcome và thêm failure modes. Outbox tăng schema, dispatcher và operational complexity nhưng mạnh khi cần đảm bảo intent không bị mất. Nếu provider có idempotency key, đó thường là boundary tốt để chống duplicate do retry.

## Cách kiểm thử

1. **Concurrency test:** enqueue cùng ID nhiều lần với nhiều workers; xác nhận chỉ một worker claim thành công.
2. **Failure-path test:** fake provider thực hiện side effect rồi throw timeout; xác minh hệ thống đưa operation vào trạng thái có thể reconciliation thay vì giả định chắc chắn failed.
3. **Crash recovery:** dừng worker sau atomic claim; xác minh lease/reconciliation có thể recover.
4. **Permanent failure:** invalid recipient không retry vô hạn.
5. **Load test:** đo duplicate rate, queue latency và DB contention khi tăng số worker.

## Quan sát trong production

Theo dõi `notification_attempt_total`, `notification_duplicate_detected_total`, `notification_processing_age`, retry count, dead-letter count và provider latency/error category. Trace nên nối Hangfire job ID, notification ID và provider operation ID. Alert khi số row `Processing` quá lease threshold hoặc retry rate tăng đột biến. Log không chứa email body/token.

## Câu hỏi phỏng vấn mở rộng

1. Transactional outbox giải quyết được điều gì và **không** giải quyết được điều gì?
2. Nếu provider không hỗ trợ idempotency key, bạn sẽ chọn at-least-once hay reconciliation như thế nào?
3. Có nên dùng `[DisableConcurrentExecution]` làm giải pháp duy nhất cho bài toán này không? Vì sao?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log vừa chậm vừa có lỗ hổng authorization

**Chủ đề:** Authorization, EF Core query execution, sensitive data, pagination, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép quản trị viên của từng công ty xem audit logs. Bảng có hàng triệu rows. Sau khi thêm tính năng search, P95 tăng mạnh và memory của API tăng vào giờ cao điểm. Security review đồng thời phát hiện khả năng một tenant truy cập dữ liệu tenant khác nếu biết identifier. Endpoint đang được gọi từ portal nội bộ nhưng vẫn phải coi request input là không đáng tin cậy.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    [Authorize]
    public async Task<IActionResult> Search(
        string tenantId,
        string? keyword,
        int page = 1,
        int pageSize = 100)
    {
        var logs = await _db.AuditLogs
            .Include(x => x.User)
            .OrderByDescending(x => x.CreatedAtUtc)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            logs = logs
                .Where(x => x.Message.Contains(keyword,
                    StringComparison.OrdinalIgnoreCase))
                .ToList();
        }

        var result = logs
            .Where(x => x.TenantId == tenantId)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.Message,
                UserEmail = x.User.Email,
                x.IpAddress,
                x.CreatedAtUtc
            })
            .ToList();

        _logger.LogInformation(
            "Audit search tenant={TenantId}, keyword={Keyword}, result={@Result}",
            tenantId, keyword, result);

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object/tenant-level authorization

**Problem:** Caller tự cung cấp `tenantId`; `[Authorize]` chỉ yêu cầu authenticated principal, không chứng minh quyền trên tenant đó.  
**Why:** Không bind/filter tenant theo trusted claims hoặc resource authorization.  
**Production impact:** Cross-tenant data exposure.  
**Severity:** Critical.  
**Recommended fix:** Resolve tenant từ authenticated context hoặc authorize resource/tenant trước query; luôn áp tenant predicate tại database boundary.

### 2. Materialize toàn bộ bảng trước khi filter

**Problem:** `ToListAsync()` chạy trước tenant filter/search/pagination.  
**Why:** Các thao tác sau đó chạy LINQ-to-Objects.  
**Production impact:** Đọc hàng triệu rows, memory spike, GC pressure, latency và DB/network load cao.  
**Severity:** High.  
**Recommended fix:** Giữ query dưới dạng `IQueryable` tới cuối và materialize sau filters/projection/pagination.

### 3. Search chạy trong memory

**Problem:** `StringComparison.OrdinalIgnoreCase` ở đây được áp sau materialization.  
**Why:** Query đã thành `List<T>`.  
**Production impact:** CPU/memory API tăng và search không tận dụng database strategy.  
**Severity:** High.  
**Recommended fix:** Dùng database-translatable predicate phù hợp provider; với search lớn cần cân nhắc full-text/search index thay vì wildcard scan.

### 4. Không giới hạn `pageSize` và validate page

**Problem:** Caller có thể yêu cầu page cực lớn hoặc giá trị bất hợp lệ.  
**Why:** Không có validation/cap.  
**Production impact:** Resource abuse, overflow/expensive query.  
**Severity:** Medium.  
**Recommended fix:** `page >= 1`, cap page size; với deep pagination lớn cân nhắc keyset pagination.

### 5. `Include(User)` không cần thiết

**Problem:** Load entity graph dù cuối cùng chỉ projection một số fields.  
**Why:** `Include` được dùng trước materialization.  
**Production impact:** Thêm data transfer, tracking và allocation.  
**Severity:** Medium.  
**Recommended fix:** Projection trực tiếp từ query; thường không cần `Include` khi projection navigation property được translate.

### 6. Tracking không cần thiết cho read-only endpoint

**Problem:** Entities được tracking.  
**Why:** Query entity mặc định có tracking.  
**Production impact:** Change tracker memory/CPU không cần thiết.  
**Severity:** Medium.  
**Recommended fix:** Projection DTO thường đã giảm đáng kể tracking concern; hoặc `AsNoTracking()` khi query entity read-only.

### 7. Sensitive data bị log

**Problem:** `{@Result}` có thể chứa audit message, user email, IP address. Keyword cũng có thể chứa dữ liệu nhạy cảm.  
**Why:** Log request/result trực tiếp.  
**Production impact:** Data leakage và tăng log volume/cost.  
**Severity:** Medium.  
**Recommended fix:** Log tenant-safe identifier, query duration, result count, pagination và correlation ID; không log result payload/PII.

### 8. Offset pagination xuống cấp ở deep pages

**Problem:** `Skip` lớn có thể tốn chi phí đáng kể.  
**Why:** Database vẫn phải tìm/bỏ qua nhiều rows theo execution plan.  
**Production impact:** Tail latency tăng với deep navigation.  
**Severity:** Low/Medium tùy workload.  
**Recommended fix:** Keyset/cursor pagination theo `(CreatedAtUtc, Id)` nếu UX phù hợp.

## Phiên bản code đề xuất

```csharp
public sealed record AuditLogDto(
    long Id,
    string Message,
    string? UserEmail,
    DateTime CreatedAtUtc);

[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AppDbContext db,
        ITenantContext tenantContext,
        ILogger<AuditController> logger)
    {
        _db = db;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    [HttpGet]
    [Authorize(Policy = "AuditReader")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        [FromQuery] string? keyword,
        [FromQuery] int page = 1,
        [FromQuery] int pageSize = 50,
        CancellationToken ct = default)
    {
        if (page < 1)
            return BadRequest("page must be >= 1");

        pageSize = Math.Clamp(pageSize, 1, 100);
        var tenantId = _tenantContext.RequiredTenantId;

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            var normalized = keyword.Trim();
            query = query.Where(x => x.Message.Contains(normalized));
        }

        var rows = await query
            .OrderByDescending(x => x.CreatedAtUtc)
            .ThenByDescending(x => x.Id)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new AuditLogDto(
                x.Id,
                x.Message,
                x.User.Email,
                x.CreatedAtUtc))
            .ToListAsync(ct);

        _logger.LogInformation(
            "Audit search completed. Tenant={TenantId} Page={Page} PageSize={PageSize} Count={Count}",
            tenantId, page, pageSize, rows.Count);

        return Ok(rows);
    }
}
```

`Contains` trong ví dụ chỉ minh họa việc giữ filter trong database; behavior về case sensitivity và hiệu năng phụ thuộc database/provider/collation. Với SQL Server/PostgreSQL và dữ liệu lớn, cần chọn search strategy/index dựa trên requirement thật thay vì giả định một expression sẽ tối ưu cho mọi provider.

## Trade-offs

Offset pagination đơn giản và dễ tích hợp UI, nhưng deep page có thể chậm; keyset pagination nhanh và ổn định hơn cho feed-style navigation nhưng khó hỗ trợ nhảy trực tiếp tới page N. Lấy tenant từ trusted context giảm flexibility cho super-admin; nếu có cross-tenant admin thật, nên mô hình hóa thành policy/resource authorization rõ ràng thay vì tin query parameter. Full-text/search engine cải thiện search phức tạp nhưng tăng infrastructure và consistency considerations.

## Cách kiểm thử

1. **Security integration test:** user tenant A gửi tenant identifier của B hoặc thay đổi URL; không được nhận dữ liệu B.
2. **Database test:** xác minh query trả đúng tenant và pagination deterministic khi nhiều rows có cùng timestamp.
3. **Load test:** dataset hàng triệu rows; đo P95/P99, allocated memory và DB reads trước/sau fix.
4. **Input test:** `page=0`, negative, pageSize rất lớn, keyword dài hoặc ký tự đặc biệt.
5. **Privacy test:** kiểm tra logs không chứa audit body, email, IP hoặc secrets.

## Quan sát trong production

Theo dõi endpoint latency P50/P95/P99, DB query duration, rows scanned/returned khi có telemetry phù hợp, request rate, timeout rate, allocation/GC và database CPU. Trace request → EF/database span. Alert khi latency/error tăng hoặc xuất hiện authorization-denied spike bất thường. Query plans và index usage cần được kiểm tra trên database thật với representative data.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ thiết kế composite index nào nếu query chủ yếu là `TenantId + CreatedAtUtc + Id`, và bạn cần kiểm tra execution plan ra sao trước khi kết luận?
2. Khi nào keyset pagination đáng đổi UX/API contract?
3. Nếu có global support admin được phép xem nhiều tenant, bạn sẽ thiết kế authorization mà không phá tenant isolation thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge hôm nay tập trung vào hai boundary thường gây incident nghiêm trọng ở backend: **side effect boundary** và **security/data boundary**. Hangfire retry không đồng nghĩa exactly-once; concurrent workers cần atomic state transition và external side effect cần idempotency/reconciliation. Với multi-tenant API, authentication không thay thế authorization; tenant isolation phải được enforce trước khi dữ liệu rời database. EF Core query cũng cần giữ ở dạng query tới khi filters, projection và pagination đã được compose.

## Mẫu tư duy cần nhớ

- **Retry + side effect ⇒ nghĩ ngay đến idempotency và ambiguous outcome.**
- **Check rồi update ở hai bước ⇒ kiểm tra race condition và atomic transition.**
- **Authenticated ≠ authorized cho resource/tenant cụ thể.**
- **Materialize muộn:** filter, project và paginate tại database khi có thể.
- **Observability là một phần của design, nhưng telemetry không được trở thành kênh rò rỉ dữ liệu.**
