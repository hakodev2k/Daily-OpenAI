# Code Review Challenge 1 — Azure Service Bus: thanh toán đối soát bị ghi nhận hai lần

**Chủ đề:** .NET 8, Azure Service Bus, SQL Server, idempotent consumer, transaction boundary  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Hệ thống đặt hàng nhận sự kiện `PaymentCaptured` từ Azure Service Bus queue. Mỗi event phải tạo đúng một ledger entry và cập nhật trạng thái đơn hàng, sau đó gửi yêu cầu phát hành hóa đơn. Worker chạy trên Azure App Service, scale từ 1 lên 4 instances. Sau khi upstream retry do timeout, một số đơn hàng có hai ledger entries và hai hóa đơn; thỉnh thoảng worker mất kết nối SQL Server. Queue được cấu hình theo cơ chế giao nhận có thể lặp lại; không có distributed transaction giữa SQL Server và Service Bus. Chưa biết `MessageId` có ổn định qua các lần upstream publish hay không.

## Đoạn code cần review

```csharp
public sealed class PaymentWorker : BackgroundService
{
    private readonly ServiceBusProcessor _processor;
    private readonly IServiceScopeFactory _scopes;
    private readonly ILogger<PaymentWorker> _logger;
    private readonly HttpClient _billing;

    public PaymentWorker(ServiceBusClient client,
        IServiceScopeFactory scopes,
        IHttpClientFactory clients,
        ILogger<PaymentWorker> logger)
    {
        _processor = client.CreateProcessor("payments", new ServiceBusProcessorOptions
        {
            MaxConcurrentCalls = 16,
            AutoCompleteMessages = true
        });
        _scopes = scopes;
        _billing = clients.CreateClient("billing");
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _processor.ProcessMessageAsync += ProcessAsync;
        _processor.ProcessErrorAsync += args =>
        {
            _logger.LogError(args.Exception, "Queue error");
            return Task.CompletedTask;
        };
        await _processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }

    private async Task ProcessAsync(ProcessMessageEventArgs args)
    {
        var payment = JsonSerializer.Deserialize<PaymentCaptured>(
            args.Message.Body.ToString())!;

        using var scope = _scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var order = await db.Orders.SingleAsync(x => x.Id == payment.OrderId);
        if (order.Status == "Paid")
            return;

        db.LedgerEntries.Add(new LedgerEntry
        {
            OrderId = payment.OrderId,
            PaymentId = payment.PaymentId,
            Amount = payment.Amount
        });
        order.Status = "Paid";
        await db.SaveChangesAsync();

        var response = await _billing.PostAsJsonAsync(
            "/invoices", new { payment.OrderId, payment.PaymentId });
        response.EnsureSuccessStatusCode();
        _logger.LogInformation("Payment processed {PaymentId}", payment.PaymentId);
    }

    public override async Task StopAsync(CancellationToken cancellationToken)
    {
        await _processor.StopProcessingAsync(cancellationToken);
        await base.StopAsync(cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### Critical — Check-then-act không atomic, tạo ledger trùng

**Vấn đề:** Hai consumer có thể cùng thấy `order.Status != "Paid"`, rồi cùng insert.  
**Tại sao xảy ra:** Read-check-write không được bảo vệ bằng unique constraint hoặc concurrency control; nhiều process không chia sẻ lock trong memory.  
**Ảnh hưởng production:** Sai số đối soát, thanh toán/ghi nhận trùng, hậu quả tài chính.  
**Cách sửa:** Unique index trên business identity `(Provider, PaymentId)` (hoặc khóa thanh toán được xác minh duy nhất), transaction gắn ledger và order update; xử lý unique conflict như duplicate hợp lệ sau khi kiểm tra payload tương ứng.

### Critical — HTTP side effect ngoài SQL transaction

**Vấn đề:** Commit SQL rồi gọi invoice API; timeout khiến message retry và có thể phát hành hóa đơn lặp.  
**Tại sao xảy ra:** SQL commit và HTTP call không atomic; client timeout không chứng minh remote chưa xử lý.  
**Ảnh hưởng production:** Invoice trùng hoặc bị bỏ sót tùy logic skip `Paid`.  
**Cách sửa:** Transactional outbox cho yêu cầu invoice, dispatcher retry với stable idempotency key, phía invoice API enforce idempotency.

### High — Trả về sớm khi Paid làm mất invoice chưa phát hành

**Vấn đề:** `Status == Paid` được coi là toàn bộ workflow hoàn tất.  
**Tại sao xảy ra:** Không theo dõi độc lập trạng thái phát hành invoice.  
**Ảnh hưởng production:** SQL đã commit nhưng crash trước HTTP call; lần retry bỏ qua invoice vĩnh viễn.  
**Cách sửa:** Tách trạng thái payment/ledger và durable invoice intent; outbox được ghi trong cùng transaction.

### High — Không xác thực message contract và business invariants

**Vấn đề:** Deserialize với null-forgiving, không validate amount, currency, IDs, event version hoặc nguồn sự kiện.  
**Tại sao xảy ra:** Tin tưởng payload queue như dữ liệu hợp lệ.  
**Ảnh hưởng production:** Poison messages, sai số tiền, ledger gắn nhầm order.  
**Cách sửa:** Versioned schema, validation, đối chiếu order/payment từ nguồn đáng tin, DLQ cho invalid payload, không log dữ liệu nhạy cảm.

### High — Auto-completion và lock duration không được chủ động kiểm soát

**Vấn đề:** Settlement tự động không thể hiện chính sách retry, lock renewal và poison handling.  
**Tại sao xảy ra:** Mặc định processor quyết định complete/abandon theo callback; processing lâu có thể vượt lock nếu renewal không đủ.  
**Ảnh hưởng production:** Redelivery và side effects lặp, backlog.  
**Cách sửa:** `AutoCompleteMessages=false`, complete chỉ sau durable commit; cấu hình `MaxAutoLockRenewalDuration`, retry classification, DLQ sau ngưỡng rõ ràng. Explicit settlement vẫn không thay thế idempotency.

### Medium — Không truyền CancellationToken

**Vấn đề:** EF query, SaveChanges và HTTP call không nhận cancellation.  
**Tại sao xảy ra:** Callback bỏ qua `args.CancellationToken`.  
**Ảnh hưởng production:** Shutdown kéo dài, request chạy sau khi lock mất, lãng phí tài nguyên.  
**Cách sửa:** Truyền token đến I/O; nếu hủy trước commit, để message được retry.

### Medium — Processor lifecycle chưa được dispose rõ ràng

**Vấn đề:** Worker dừng processor nhưng không dispose processor trong lifecycle.  
**Tại sao xảy ra:** Thiếu `DisposeAsync`/cleanup khi shutdown và exception.  
**Ảnh hưởng production:** Resource leak khi host tái tạo worker hoặc test nhiều vòng.  
**Cách sửa:** Dùng `await using` hoặc dispose processor trong `finally`; unregister handler nếu tái sử dụng.

### Medium — Thiếu telemetry để phân biệt retry và business duplicate

**Vấn đề:** Log chỉ `PaymentId` sau thành công.  
**Tại sao xảy ra:** Không log `MessageId`, `DeliveryCount`, event ID, correlation, stage và outcome.  
**Ảnh hưởng production:** Khó điều tra mismatch và DLQ.  
**Cách sửa:** Structured logs không chứa secrets, trace liên kết queue→SQL→invoice, counters duplicate/invalid/retry/outbox lag.

## Phiên bản đề xuất

Một thiết kế tối thiểu gồm **ingest worker + SQL transaction + outbox dispatcher**. Các đoạn sau là khung triển khai; entity mapping, migrations, provider verification và exception classification cần hoàn thiện theo hệ thống thực.

```csharp
// SQL: UNIQUE (Provider, PaymentId) on LedgerEntries
// SQL: UNIQUE (EventKey) on InboxEvents
// SQL: UNIQUE (EventKey, Kind) on OutboxMessages

public async Task HandleAsync(
    PaymentCaptured evt, CancellationToken ct)
{
    Validate(evt);
    await using var db = await _factory.CreateDbContextAsync(ct);
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var eventKey = $"{evt.Provider}:{evt.PaymentId}";
    if (await db.InboxEvents.AnyAsync(x => x.EventKey == eventKey, ct))
    {
        await tx.CommitAsync(ct);
        return;
    }

    var order = await db.Orders.SingleAsync(x => x.Id == evt.OrderId, ct);
    VerifyPaymentBelongsToOrder(evt, order);

    db.InboxEvents.Add(new InboxEvent { EventKey = eventKey });
    db.LedgerEntries.Add(new LedgerEntry {
        Provider = evt.Provider, PaymentId = evt.PaymentId,
        OrderId = evt.OrderId, Amount = evt.Amount
    });
    order.Status = "Paid";
    db.OutboxMessages.Add(new OutboxMessage {
        EventKey = eventKey, Kind = "IssueInvoice",
        Payload = JsonSerializer.Serialize(new {
            evt.OrderId, evt.PaymentId, evt.Provider
        }),
        Status = "Pending"
    });

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}

// Processor callback: deserialize/validate, HandleAsync, then
// CompleteMessageAsync; transient failures remain retryable.
// Concurrent unique-key conflicts: reload and compare stored
// business payload; acknowledge only when it is the same event.

// Outbox dispatcher: claim pending row atomically with lease,
// send stable Idempotency-Key = EventKey + ":invoice",
// persist success; retry ambiguous timeout using same key.
// Invoice service MUST implement idempotency independently.
```

**Điều kiện quan trọng:** Nếu một payment có nhiều event hợp lệ với cùng `PaymentId` nhưng khác event semantics, không dùng `PaymentId` một cách mù quáng làm inbox key; phải phân biệt event identity với business uniqueness. Dispatcher phải claim row bằng DB lease/atomic update để tránh nhiều instances cùng dispatch; dù vậy remote idempotency vẫn bắt buộc.

## Giải thích thiết kế sau khi sửa

SQL transaction bảo đảm ledger, order và invoice intent được ghi cùng nhau. Unique constraints là hàng rào cuối cùng trước race condition. Queue ack xảy ra sau durable commit; mất ack chỉ gây retry an toàn. Invoice được xử lý eventually consistent; dispatcher ghi trạng thái và lịch sử attempt, hỗ trợ replay có kiểm soát.

## Trade-offs

Outbox tăng bảng dữ liệu, polling/dispatch lag, cleanup và vận hành. Nếu invoice API có idempotency và độ tin cậy tốt, có thể cân nhắc workflow đơn giản hơn, nhưng không thể đảm bảo cả **không trùng** lẫn **không mất** chỉ bằng `Status == Paid`. Không cần Microservices hoặc distributed transaction để giải quyết bài toán này.

## Cách kiểm thử

1. **Concurrency/integration:** 100 deliveries cùng business payment vào 4 consumers; xác minh một ledger, một outbox intent.
2. **Failure-path:** SQL commit xong crash trước ack; redelivery không thêm ledger và invoice intent.
3. **HTTP failure:** Invoice API nhận request rồi timeout; retry cùng idempotency key chỉ có một invoice.
4. **Poison message:** Payload sai schema/amount, xác minh DLQ và không ghi ledger.
5. **Shutdown/load:** Cancel khi đang xử lý, kiểm tra lock renewal, queue backlog, outbox lag và eventual completion.

## Quan sát trong production

Theo dõi Service Bus active/dead-letter count, delivery count, lock lost, processing latency; SQL unique violations, transaction failures; outbox pending age, dispatch attempts, invoice duplicate rejection; distributed traces qua `PaymentId` đã mask, event key và correlation ID. Alert khi outbox oldest age vượt SLO, DLQ tăng, ledger/invoice reconciliation lệch.

## Câu hỏi phỏng vấn mở rộng

1. Nếu upstream tạo `MessageId` mới mỗi retry nhưng `PaymentId` không đổi, thiết kế thay đổi thế nào?
2. Nếu invoice provider không hỗ trợ idempotency, bạn giảm thiểu và đối soát duplicate ra sao?
3. Khi SQL transaction commit thành công nhưng client mất kết nối trước nhận kết quả, làm sao xử lý outcome không chắc chắn?

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Employee = {
  id: string
  name: string
  department: string
}
const props = defineProps<{
  tenantId: string
  accessToken: string
}>()

const search = ref('')
const department = ref('all')
const rows = ref<Employee[]>([])
const loading = ref(false)
const error = ref('')
const cache = new Map<string, Employee[]>()

async function loadEmployees() {
  const key = search.value + ':' + department.value
  if (cache.has(key)) {
    rows.value = cache.get(key)!
    return
  }

  loading.value = true
  error.value = ''
  try {
    const url = '/api/employees?tenant=' + props.tenantId
      + '&q=' + search.value
      + '&department=' + department.value
    const response = await fetch(url, {
      headers: { Authorization: 'Bearer ' + props.accessToken }
    })
    const data = await response.json()
    cache.set(key, data.items)
    rows.value = data.items
  } catch (e) {
    error.value = 'Không thể tải dữ liệu'
  }
  loading.value = false
}

watch([search, department], loadEmployees)
onMounted(loadEmployees)
</script>

<template>
  <section>
    <input v-model="search" placeholder="Search employees" />
    <select v-model="department">
      <option value="all">All</option>
      <option value="engineering">Engineering</option>
      <option value="hr">HR</option>
    </select>
    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>
    <table>
      <tr v-for="row in rows" :key="row.id">
        <td>{{ row.name }}</td><td>{{ row.department }}</td>
      </tr>
    </table>
  </section>
</template>
```

## Kết quả code review tham khảo

### Critical — Cache không scope theo tenant hoặc user

**Vấn đề:** Cache key chỉ gồm search/department.  
**Tại sao xảy ra:** Component giữ `Map` khi props thay đổi; dữ liệu tenant/account trước có thể được dùng lại.  
**Ảnh hưởng production:** Hiển thị thông tin nhân sự sai tenant ngay cả khi backend có authorization đúng; rủi ro privacy và trust.  
**Cách sửa:** Mặc định bỏ cache nhạy cảm hoặc scope theo tenant + stable user identity + permission/version; clear khi auth context thay đổi. Không lưu access token làm key.

### High — Out-of-order responses ghi đè state mới

**Vấn đề:** Nhiều fetch chạy đồng thời, response cũ có thể cập nhật `rows` sau response mới.  
**Tại sao xảy ra:** Không cancel hoặc kiểm tra request generation.  
**Ảnh hưởng production:** Search hiển thị sai, người dùng thao tác trên kết quả không đúng filter.  
**Cách sửa:** Abort previous request và kiểm tra monotonically increasing request ID trước khi commit state.

### High — Không theo dõi tenantId/accessToken

**Vấn đề:** Watch chỉ lắng nghe `search` và `department`.  
**Tại sao xảy ra:** Props thay đổi không kích hoạt reload; state cũ vẫn hiện.  
**Ảnh hưởng production:** Sai context sau switch tenant/logout.  
**Cách sửa:** Watch auth identity/tenant, clear rows ngay khi context thay đổi; component key theo session nếu phù hợp.

### High — Không kiểm tra HTTP status hoặc response contract

**Vấn đề:** `fetch` không reject khi 401/403/500; JSON error có thể bị gán vào cache dưới dạng `undefined`.  
**Tại sao xảy ra:** Giả định HTTP non-2xx sẽ throw.  
**Ảnh hưởng production:** Lỗi âm thầm, bảng trắng hoặc runtime error.  
**Cách sửa:** Kiểm tra `response.ok`, xử lý 401/403 riêng, validate shape của response trước khi render.

### Medium — Query string chưa encode

```vue
const props = defineProps<{ tenantId: string; accessToken: string }>()

const department = ref('all')

let generation = 0

watch(search, value => {
  clearTimeout(debounce)
  debounce = setTimeout(() => { debouncedSearch.value = value }, 300)

watch(
  [debouncedSearch, department,
   () => props.tenantId, () => props.accessToken],
  async (_values, _oldValues, onCleanup) => {
    const current = ++generation
    const controller = new AbortController()
    onCleanup(() => controller.abort())
    rows.value = []
    error.value = ''
    loading.value = true

    try {
      if (!props.tenantId || !props.accessToken) return
      const params = new URLSearchParams({
        tenant: props.tenantId,
        q: debouncedSearch.value,
        department: department.value
      })
      const response = await fetch('/api/employees?' + params, {
        headers: { Authorization: 'Bearer ' + props.accessToken },
        signal: controller.signal,
        cache: 'no-store'
      })
      if (!response.ok) throw new Error('HTTP ' + response.status)
      const payload: unknown = await response.json()
      if (!isEmployeePage(payload)) throw new Error('Invalid response')
      if (current === generation) rows.value = payload.items
    } catch (e) {
      if (current === generation && !controller.signal.aborted)
        error.value = 'Không thể tải dữ liệu'
    } finally {
      if (current === generation) loading.value = false
    }
  },
  { immediate: true }
)

function isEmployeePage(value: unknown): value is { items: Employee[] } {
  if (!value || typeof value !== 'object' || !('items' in value))
    return false
  const items = (value as { items: unknown }).items
  return Array.isArray(items) && items.every(x =>
    x && typeof x === 'object' &&
    typeof x.id === 'string' &&
    typeof x.name === 'string' &&
    typeof x.department === 'string')
}

onUnmounted(() => clearTimeout(debounce))
</script>

<template>
  <section>
    <input v-model="search" placeholder="Search employees" />
    <select v-model="department">
      <option value="all">All</option>
      <option value="engineering">Engineering</option>
      <option value="hr">HR</option>
    </select>
    <p v-if="loading">Loading...</p>
    <p v-if="error" role="alert">{{ error }}</p>
    <table>
      <tbody>
        <tr v-for="row in rows" :key="row.id">
          <td>{{ row.name }}</td><td>{{ row.department }}</td>
        </tr>
      </tbody>
    </table>
  </section>
</template>
```

**Giới hạn:** `watch` trên `accessToken` có thể reload mỗi lần refresh token; production nên dùng stable session identity và refresh auth interceptor phù hợp. Việc hủy request không đảm bảo backend ngừng xử lý; server vẫn cần pagination, authorization, query bounds và rate limiting. `cache: 'no-store'` là client fetch policy, không thay thế server `Cache-Control: private, no-store` cho dữ liệu nhạy cảm.

## Giải thích thiết kế sau khi sửa

Reactive watcher bao gồm tất cả input ảnh hưởng đến kết quả. Generation ID bảo vệ state kể cả khi abort không kịp. Clear rows trước request mới để tránh hiển thị thông tin tenant cũ. Runtime validation giúp phát hiện response contract mismatch. Server là nơi quyết định quyền truy cập, client chỉ quản lý UX/state.

## Trade-offs

Không cache làm tăng số request nhưng giảm nguy cơ dữ liệu cũ và complexity; có thể thêm query cache có scope theo session nếu có số liệu chứng minh cần thiết. Debounce tăng độ trễ hiển thị nhỏ; request cancellation có thể giảm traffic nhưng không đảm bảo tiết kiệm toàn bộ CPU server. Khi search lớn cần server-side pagination và request limits thay vì tải toàn bộ dữ liệu.

## Cách kiểm thử

1. **Race/E2E Playwright:** Mock response A chậm hơn B; UI chỉ hiện B.
2. **Tenant/session switch:** Đổi tenant/account khi request cũ đang pending; không xuất hiện dữ liệu cũ, kể cả cache/browser back navigation.
3. **API failure:** 401, 403, 500 và invalid JSON; không crash, không giữ rows của phiên trước.
4. **Input encoding:** Search `R&D + Hà Nội`; server nhận đúng tham số.
5. **Load/network:** Gõ nhanh 20 ký tự, đo số requests, cancellation và latency; unmount không tạo state update.

## Quan sát trong production

Frontend: request duration, cancellation rate, non-2xx, request-generation stale drop, error rate (không log access token hoặc tên nhân viên). Backend: tenant-scoped 403/401, query latency p95/p99, result count, database waits và request volume. Correlation ID kết nối browser error với Application Insights; alert khi 5xx hoặc p95 vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product yêu cầu offline search trong một phiên, bạn thiết kế cache có scope và expiry ra sao?
2. Khi token tự refresh mỗi 5 phút, làm thế nào tránh reload không cần thiết nhưng vẫn bảo vệ logout?
3. Nếu search API hỗ trợ cursor pagination, bạn bảo vệ ordering và reset cursor khi filter thay đổi thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Distributed processing:** At-least-once delivery cần idempotency ở business boundary; database commit, queue acknowledgement và HTTP side effect không tự động atomic.
- **Frontend state:** Dữ liệu hiển thị phải gắn với tenant/session/filter và request generation; backend authorization không thay thế client data isolation.
- **Production reasoning:** Phân biệt duplicate delivery với duplicate business effect; phân biệt network timeout với remote failure; đo đạc và kiểm thử failure paths trước khi kết luận.

## Mẫu tư duy cần nhớ

1. Xác định identity và transaction boundary trước khi thiết kế retry.
2. Bảo vệ invariant bằng database constraint, không chỉ bằng check trong application code.
3. Khi kết quả remote không chắc chắn, retry phải dùng stable idempotency key.
4. Mọi asynchronous response phải được kiểm tra còn thuộc context hiện tại hay không.
5. Test concurrency, partial failure và tenant switching thay vì chỉ happy path.
