# Code Review Challenge 1 — Permission Cache bị stale và race condition khi nhiều request cập nhật cùng lúc

**Chủ đề:** Caching, concurrency, authorization, race condition  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core application dùng Redis để cache permission theo user. Endpoint dưới đây được gọi khi admin thay đổi role của một user.

Hệ thống chạy 6 instances sau load balancer. Lưu lượng bình thường khoảng 150–250 request/giây. Production gần đây xuất hiện hiện tượng:

- User vừa bị remove role nhưng vẫn có quyền thêm vài phút.
- Một số request sau update đọc được quyền mới, request khác lại đọc quyền cũ.
- Redis CPU không cao.
- SQL Server không có lỗi rõ ràng.
- Incident thường xảy ra khi có nhiều admin update cùng lúc hoặc khi traffic cao.

Business yêu cầu thay đổi quyền quan trọng phải có hiệu lực gần như ngay sau khi admin hoàn tất thao tác.

## Đoạn code cần review

```csharp
public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IDatabase _redis;
    private static readonly Dictionary<string, List<string>> LocalCache = new();

    public PermissionService(
        AppDbContext db,
        IConnectionMultiplexer redis)
    {
        _db = db;
        _redis = redis.GetDatabase();
    }

    public async Task<List<string>> GetPermissionsAsync(
        int tenantId,
        int userId)
    {
        var key = $"permissions:{tenantId}:{userId}";

        if (LocalCache.TryGetValue(key, out var local))
            return local;

        var cached = await _redis.StringGetAsync(key);

        if (cached.HasValue)
        {
            var permissions = JsonSerializer.Deserialize<List<string>>(cached!)!;
            LocalCache[key] = permissions;
            return permissions;
        }

        var permissionsFromDb = await _db.UserRoles
            .Where(x => x.TenantId == tenantId && x.UserId == userId)
            .SelectMany(x => x.Role.Permissions)
            .Select(x => x.Code)
            .Distinct()
            .ToListAsync();

        await _redis.StringSetAsync(
            key,
            JsonSerializer.Serialize(permissionsFromDb),
            TimeSpan.FromMinutes(30));

        LocalCache[key] = permissionsFromDb;

        return permissionsFromDb;
    }

    public async Task UpdateRolesAsync(
        int tenantId,
        int userId,
        IReadOnlyCollection<int> roleIds)
    {
        var current = await _db.UserRoles
            .Where(x => x.TenantId == tenantId && x.UserId == userId)
            .ToListAsync();

        _db.UserRoles.RemoveRange(current);

        foreach (var roleId in roleIds)
        {
            _db.UserRoles.Add(new UserRole
            {
                TenantId = tenantId,
                UserId = userId,
                RoleId = roleId
            });
        }

        await _db.SaveChangesAsync();

        var key = $"permissions:{tenantId}:{userId}";
        await _redis.KeyDeleteAsync(key);
    }
}
```

## Câu hỏi gợi mở

1. `LocalCache` có an toàn khi nhiều thread truy cập đồng thời không?
2. Xóa Redis key có đảm bảo tất cả application instances bỏ cache cũ không?
3. Điều gì xảy ra nếu request A đọc DB trước khi update commit, nhưng ghi cache sau khi update đã xóa cache?
4. Business requirement “permission change gần như ngay lập tức” có phù hợp với TTL 30 phút không?
5. Nếu hai admin cùng update role cho cùng user, kết quả cuối cùng được xác định như thế nào?

## Gợi ý

## Kết quả code review tham khảo

### 1. Local cache không được invalidated khi role thay đổi

- **Problem:** `UpdateRolesAsync` chỉ xóa Redis key nhưng không xóa `LocalCache`.
- **Why it happens:** mỗi process giữ một bản cache riêng trong static dictionary.
- **Production impact:** user có thể tiếp tục dùng permission cũ vô thời hạn cho tới khi process restart hoặc key bị ghi đè bởi logic khác.
- **Severity:** Critical
- **Recommended fix:** không dùng unbounded static cache cho authorization state; nếu cần local cache, phải có bounded TTL và cơ chế invalidation/versioning giữa instances.

### 2. `Dictionary<TKey,TValue>` không phù hợp cho concurrent access kiểu này

- **Problem:** static `Dictionary` bị đọc/ghi từ nhiều request threads mà không synchronization.
- **Why it happens:** `Dictionary` không được thiết kế cho concurrent writes.
- **Production impact:** race condition, trạng thái không nhất quán, exception hoặc behavior khó dự đoán dưới tải.
- **Severity:** High
- **Recommended fix:** nếu vẫn cần local cache, dùng `IMemoryCache` hoặc cấu trúc thread-safe phù hợp; nhưng correctness authorization phải không phụ thuộc chỉ vào thread-safe container.

### 3. Cache repopulation race sau invalidation

- **Problem:** request đọc permission cũ từ DB rồi ghi Redis/local cache sau khi admin đã update và xóa cache.
- **Why it happens:** read path và write/invalidate path không có version/checkpoint chung.
- **Production impact:** cache cũ có thể được tái sinh ngay sau invalidation và tồn tại tiếp 30 phút.
- **Severity:** Critical
- **Recommended fix:** dùng permission version/security stamp hoặc versioned cache key; chỉ chấp nhận cache entry nếu version khớp state hiện tại.

### 4. TTL 30 phút không phù hợp với security requirement

- **Problem:** authorization cache có stale window quá lớn nếu invalidation bị miss.
- **Why it happens:** thiết kế dựa nhiều vào invalidation hoàn hảo.
- **Production impact:** quyền đã revoke vẫn có thể tồn tại lâu.
- **Severity:** High
- **Recommended fix:** dùng TTL ngắn hơn cho high-risk permission, hoặc version validation tại sensitive operation.

### 5. Không có concurrency control khi hai admin update cùng user

- **Problem:** hai request cùng đọc `current`, cùng remove/add, rồi commit theo thứ tự không rõ.
- **Why it happens:** không có optimistic concurrency token, serialized operation hoặc conflict detection.
- **Production impact:** lost update; kết quả role cuối cùng có thể không phản ánh thao tác người dùng mong muốn.
- **Severity:** High
- **Recommended fix:** dùng optimistic concurrency/version trên aggregate phù hợp, hoặc command model có expected version.

### 6. Update roles và cache invalidation không atomic

- **Problem:** DB commit có thể thành công nhưng Redis delete thất bại.
- **Why it happens:** cache là external system ngoài DB transaction.
- **Production impact:** dữ liệu authoritative đã đổi nhưng cache vẫn cũ.
- **Severity:** High
- **Recommended fix:** chấp nhận invalidation là eventual signal nhưng bổ sung version check; nếu requirement cao, phát event/outbox sau commit để invalidate các cache layers đáng tin cậy hơn.

### 7. Không truyền `CancellationToken`

- **Problem:** EF Core và Redis calls không nhận cancellation từ request.
- **Why it happens:** method signatures thiếu token.
- **Production impact:** work tiếp tục sau khi client disconnect hoặc request timeout; làm tăng resource usage dưới tải.
- **Severity:** Medium
- **Recommended fix:** truyền `CancellationToken` xuyên suốt nơi API hỗ trợ.

### 8. Cache object mutable được trả trực tiếp

- **Problem:** method trả `List<string>` đang lưu trong cache.
- **Why it happens:** caller có thể mutate list.
- **Production impact:** một request có thể vô tình làm thay đổi permission cache dùng chung trong process.
- **Severity:** Medium
- **Recommended fix:** trả immutable/read-only representation hoặc clone nếu cần.

### 9. Không giới hạn kích thước local cache

- **Problem:** static dictionary không eviction.
- **Why it happens:** mỗi user/tenant key có thể tồn tại mãi.
- **Production impact:** memory growth lâu dài.
- **Severity:** Medium
- **Recommended fix:** dùng `IMemoryCache` với TTL/size policy hoặc bỏ local layer nếu không cần.

### 10. Thiếu observability cho cache source và permission version

- **Problem:** không biết request lấy permission từ local, Redis hay DB.
- **Why it happens:** không có structured telemetry.
- **Production impact:** incident khó phân tích và khó chứng minh stale source.
- **Severity:** Medium
- **Recommended fix:** log/metric cache source, permission version, tenant/user correlation, invalidation result và instance ID.

## Phiên bản code đề xuất

Một hướng đơn giản hơn là dùng Redis làm shared cache duy nhất và thêm permission version để chống stale repopulation. Với flow security-sensitive, local cache có thể bỏ hoàn toàn trước khi chứng minh nó thực sự cần thiết.

```csharp
public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IDatabase _redis;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        AppDbContext db,
        IConnectionMultiplexer redis,
        ILogger<PermissionService> logger)
    {
        _db = db;
        _redis = redis.GetDatabase();
        _logger = logger;
    }

    public async Task<IReadOnlyList<string>> GetPermissionsAsync(
        int tenantId,
        int userId,
        CancellationToken cancellationToken)
    {
        var version = await _db.Users
            .Where(x => x.TenantId == tenantId && x.Id == userId)
            .Select(x => x.PermissionVersion)
            .SingleAsync(cancellationToken);

        var cacheKey = $"permissions:{tenantId}:{userId}:v{version}";

        var cached = await _redis.StringGetAsync(cacheKey);
        if (cached.HasValue)
        {
            _logger.LogDebug(
                "Permission cache hit for TenantId={TenantId}, UserId={UserId}, Version={Version}",
                tenantId,
                userId,
                version);

            return JsonSerializer.Deserialize<string[]>(cached!)
                ?? Array.Empty<string>();
        }

        var permissions = await _db.UserRoles
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.UserId == userId)
            .SelectMany(x => x.Role.Permissions)
            .Select(x => x.Code)
            .Distinct()
            .ToArrayAsync(cancellationToken);

        await _redis.StringSetAsync(
            cacheKey,
            JsonSerializer.Serialize(permissions),
            TimeSpan.FromMinutes(5));

        return permissions;
    }

    public async Task UpdateRolesAsync(
        int tenantId,
        int userId,
        IReadOnlyCollection<int> roleIds,
        CancellationToken cancellationToken)
    {
        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var user = await _db.Users
            .SingleAsync(
                x => x.TenantId == tenantId && x.Id == userId,
                cancellationToken);

        var current = await _db.UserRoles
            .Where(x => x.TenantId == tenantId && x.UserId == userId)
            .ToListAsync(cancellationToken);

        _db.UserRoles.RemoveRange(current);

        foreach (var roleId in roleIds.Distinct())
        {
            _db.UserRoles.Add(new UserRole
            {
                TenantId = tenantId,
                UserId = userId,
                RoleId = roleId
            });
        }

        user.PermissionVersion++;

        await _db.SaveChangesAsync(cancellationToken);
        await transaction.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Permissions changed for TenantId={TenantId}, UserId={UserId}, Version={Version}",
            tenantId,
            userId,
            user.PermissionVersion);
    }
}
```

Điểm chính của thiết kế trên là **không cần delete cache cũ để correctness được đảm bảo**. Sau khi `PermissionVersion` tăng, request mới sử dụng cache key mới. Cache cũ tự expire sau TTL.

Nếu hệ thống cần local cache để giảm Redis traffic, có thể cache theo cả permission version và TTL ngắn. Tuy nhiên version authoritative vẫn phải đến từ nguồn đáng tin cậy hoặc được propagated đúng cách.

## Trade-offs

- Versioned key tăng số lượng key trong Redis trong thời gian ngắn, nhưng đổi lại giảm phụ thuộc vào invalidation hoàn hảo.
- Đọc `PermissionVersion` từ DB cho mỗi request có thể làm giảm lợi ích của cache; có thể cache version riêng với TTL rất ngắn hoặc dùng token/security stamp tùy kiến trúc.
- Pub/sub invalidation có latency thấp nhưng không nên là correctness guarantee duy nhất vì subscriber có thể miss event.
- Authoritative re-check tại high-risk action làm tăng DB traffic nhưng phù hợp nếu business yêu cầu revoke gần như tức thì.

## Cách kiểm thử

1. **Concurrency test:** 100 request đọc permission song song trong khi một admin revoke role; xác minh không có permission cũ sau version change theo guarantee đã định nghĩa.
2. **Race test:** cố tình delay DB read trước khi update commit rồi cho read path ghi cache sau update; xác minh versioned key không làm stale data thành current data.
3. **Two-admin test:** hai update cùng user với expected version; xác minh conflict được phát hiện thay vì silent lost update.
4. **Redis failure test:** DB commit thành công nhưng Redis unavailable; xác minh authorization vẫn không quay về state cũ ngoài stale window cho phép.
5. **Load test:** đo DB/Redis traffic, P95 latency và memory trước/sau khi bỏ static local cache.

## Quan sát trong production

Nên có:

- Log: `TenantId`, `UserId`, permission version, cache source, instance ID.
- Metrics: local/Redis hit ratio, DB fallback rate, permission-version mismatch, invalidation failures.
- Trace: authorization lookup duration tách theo cache/DB.
- Alert: Redis error rate, unusual DB fallback spike, authorization failures tăng đột biến.
- Database observation: lock waits, deadlocks, update conflicts trên user/role tables.

# Code Review Challenge 2 — External API client che mất lỗi thật và tạo retry storm

**Chủ đề:** HTTP client usage, async/cancellation, error handling, logging, observability  
**Độ khó:** Senior

## Bối cảnh

Một ASP.NET Core backend gọi external partner API để tạo shipment. Partner đôi lúc trả `429`, `503` hoặc timeout.

Production có các triệu chứng:

- Log đầy các message “Shipment API failed”.
- Team khó biết request nào timeout, request nào bị rate limit.
- Có lúc partner nhận hai shipment giống nhau.
- Application CPU bình thường nhưng số outbound requests tăng mạnh trong incident.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ShipmentClient
{
    private readonly ILogger<ShipmentClient> _logger;

    public ShipmentClient(ILogger<ShipmentClient> logger)
    {
        _logger = logger;
    }

    public async Task<bool> CreateShipmentAsync(ShipmentRequest request)
    {
        using var client = new HttpClient();
        client.Timeout = TimeSpan.FromSeconds(30);

        for (var attempt = 1; attempt <= 5; attempt++)
        {
            try
            {
                var response = await client.PostAsJsonAsync(
                    "https://partner.example.com/api/shipments",
                    request);

                if (response.IsSuccessStatusCode)
                    return true;

                _logger.LogError(
                    "Shipment API failed. Status={Status}, Body={Body}",
                    response.StatusCode,
                    await response.Content.ReadAsStringAsync());
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Shipment API failed");
            }

            await Task.Delay(1000);
        }

        return false;
    }
}
```

## Kết quả code review tham khảo

### 1. Retry `POST` có thể tạo duplicate shipment

- **Problem:** mọi non-success/exception đều có thể dẫn tới retry cùng request.
- **Why it happens:** code giả định failure response đồng nghĩa side effect chưa xảy ra.
- **Production impact:** timeout-after-success có thể tạo shipment thứ hai.
- **Severity:** Critical
- **Recommended fix:** dùng idempotency key ổn định nếu partner hỗ trợ; nếu không, cần read-back/reconciliation hoặc business operation state để xử lý unknown outcome.

### 2. Retry mọi HTTP status code

- **Problem:** `400`, `401`, `403`, validation errors cũng retry 5 lần.
- **Why it happens:** không phân loại permanent vs transient.
- **Production impact:** tăng latency, tăng load partner và làm log noisy.
- **Severity:** High
- **Recommended fix:** chỉ retry transient conditions đã xác định, ví dụ một số `5xx`, `429`, network failures tùy contract.

### 3. Retry cố định 1 giây có thể tạo retry storm

- **Problem:** tất cả requests retry cùng nhịp.
- **Why it happens:** fixed delay, không jitter, không xét server guidance.
- **Production impact:** synchronized traffic spike, làm dependency đang lỗi càng quá tải.
- **Severity:** High
- **Recommended fix:** exponential backoff + jitter; nếu contract có `Retry-After` thì cân nhắc tôn trọng nó.

### 4. Tạo `HttpClient` mới mỗi operation

- **Problem:** mỗi call tạo/dispose client/handler riêng.
- **Why it happens:** lifetime management không hợp lý cho high-throughput service.
- **Production impact:** giảm connection reuse, tăng TCP/TLS churn và outbound resource pressure.
- **Severity:** High
- **Recommended fix:** dùng injected `HttpClient` qua `IHttpClientFactory`/typed client hoặc long-lived client tùy architecture.

### 5. Không có `CancellationToken`

- **Problem:** caller không thể cancel toàn bộ retry loop.
- **Why it happens:** method không nhận token và `Task.Delay` không dùng token.
- **Production impact:** request đã timeout nhưng retry vẫn chạy tiếp, làm tăng background work và dependency load.
- **Severity:** High
- **Recommended fix:** truyền token xuyên suốt HTTP call và delay.

### 6. Catch `Exception` quá rộng

- **Problem:** cancellation và programming errors bị xử lý như transient dependency failure.
- **Why it happens:** blanket catch.
- **Production impact:** che mất lỗi thật, khó shutdown graceful, sai retry semantics.
- **Severity:** High
- **Recommended fix:** catch các exception categories phù hợp; để cancellation propagate.

### 7. `HttpResponseMessage` không được dispose rõ ràng

- **Problem:** response được tạo mỗi attempt nhưng không `using`.
- **Why it happens:** code trả sớm hoặc loop tiếp.
- **Production impact:** resource release chậm hơn cần thiết, đặc biệt trong retry loop lớn.
- **Severity:** Medium
- **Recommended fix:** `using var response = ...` hoặc thiết kế wrapper phù hợp.

### 8. Log toàn response body có thể lộ sensitive data

- **Problem:** body từ partner được log nguyên văn ở Error level.
- **Why it happens:** debug convenience.
- **Production impact:** PII/token/internal details có thể vào log storage.
- **Severity:** High
- **Recommended fix:** sanitize/redact; log error code/correlation ID thay vì raw payload nếu không cần.

### 9. Thiếu correlation/idempotency/attempt metadata

- **Problem:** log chỉ có status/body.
- **Why it happens:** chưa thiết kế observability theo operation.
- **Production impact:** không thể trace một shipment qua nhiều attempts.
- **Severity:** Medium
- **Recommended fix:** log `ShipmentOperationId`, attempt, duration, partner request ID, result classification.

### 10. `bool` làm mất thông tin failure

- **Problem:** caller chỉ biết true/false.
- **Why it happens:** result model quá nghèo.
- **Production impact:** caller không biết permanent failure, retry exhausted hay unknown outcome.
- **Severity:** Medium
- **Recommended fix:** trả typed result hoặc throw domain-specific exception theo policy.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định partner hỗ trợ `Idempotency-Key` và application đã đăng ký typed `HttpClient`.

```csharp
public sealed class ShipmentClient
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<ShipmentClient> _logger;

    public ShipmentClient(
        HttpClient httpClient,
        ILogger<ShipmentClient> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<ShipmentResult> CreateShipmentAsync(
        ShipmentRequest request,
        string idempotencyKey,
        CancellationToken cancellationToken)
    {
        const int maxAttempts = 4;

        for (var attempt = 1; attempt <= maxAttempts; attempt++)
        {
            using var message = new HttpRequestMessage(
                HttpMethod.Post,
                "api/shipments");

            message.Headers.TryAddWithoutValidation(
                "Idempotency-Key",
                idempotencyKey);

            message.Content = JsonContent.Create(request);

            var started = Stopwatch.GetTimestamp();

            try
            {
                using var response = await _httpClient.SendAsync(
                    message,
                    HttpCompletionOption.ResponseHeadersRead,
                    cancellationToken);

                var elapsed = Stopwatch.GetElapsedTime(started);

                if (response.IsSuccessStatusCode)
                {
                    _logger.LogInformation(
                        "Shipment created. IdempotencyKey={IdempotencyKey}, Attempt={Attempt}, DurationMs={DurationMs}",
                        idempotencyKey,
                        attempt,
                        elapsed.TotalMilliseconds);

                    return ShipmentResult.Success();
                }

                if (!IsTransient(response.StatusCode) || attempt == maxAttempts)
                {
                    _logger.LogWarning(
                        "Shipment request failed permanently. IdempotencyKey={IdempotencyKey}, Status={Status}, Attempt={Attempt}",
                        idempotencyKey,
                        (int)response.StatusCode,
                        attempt);

                    return ShipmentResult.Failed(
                        $"HTTP {(int)response.StatusCode}");
                }

                var delay = CalculateDelay(attempt);

                _logger.LogWarning(
                    "Transient shipment failure. IdempotencyKey={IdempotencyKey}, Status={Status}, Attempt={Attempt}, RetryInMs={RetryInMs}",
                    idempotencyKey,
                    (int)response.StatusCode,
                    attempt,
                    delay.TotalMilliseconds);

                await Task.Delay(delay, cancellationToken);
            }
            catch (OperationCanceledException)
                when (cancellationToken.IsCancellationRequested)
            {
                throw;
            }
            catch (HttpRequestException ex) when (attempt < maxAttempts)
            {
                var delay = CalculateDelay(attempt);

                _logger.LogWarning(
                    ex,
                    "Transient network failure. IdempotencyKey={IdempotencyKey}, Attempt={Attempt}, RetryInMs={RetryInMs}",
                    idempotencyKey,
                    attempt,
                    delay.TotalMilliseconds);

                await Task.Delay(delay, cancellationToken);
            }
        }

        return ShipmentResult.Failed("Retry attempts exhausted");
    }

    private static bool IsTransient(HttpStatusCode statusCode)
        => statusCode == HttpStatusCode.TooManyRequests
           || statusCode == HttpStatusCode.RequestTimeout
           || (int)statusCode >= 500;

    private static TimeSpan CalculateDelay(int attempt)
    {
        var exponentialMs = 250 * Math.Pow(2, attempt - 1);
        var jitterMs = Random.Shared.Next(0, 250);
        return TimeSpan.FromMilliseconds(exponentialMs + jitterMs);
    }
}
```

`ShipmentResult` nên phân biệt ít nhất:

- Success
- Permanent failure
- Retry exhausted
- Unknown outcome nếu contract không cho xác định chắc chắn

Nếu partner **không hỗ trợ idempotency key**, retry `POST` phải được xem xét cẩn thận hơn. Có thể cần application-side operation table và API read-back/reconciliation trước khi retry.

## Trade-offs

- Retry làm tăng availability trước transient failures nhưng cũng tăng latency và dependency load.
- Timeout ngắn giảm resource occupation nhưng có thể tăng false timeout nếu partner thực sự cần thời gian xử lý.
- Idempotency key yêu cầu partner hỗ trợ semantics đúng; chỉ gửi header không tự tạo idempotency nếu server bỏ qua.
- Resilience library/policy framework giúp chuẩn hóa retry, circuit breaker và timeout nhưng vẫn không thay thế business-level idempotency.

## Cách kiểm thử

1. **Timeout-after-success:** fake partner tạo shipment rồi ngắt kết nối; xác minh cùng idempotency key không tạo duplicate.
2. **429 test:** trả 429 nhiều lần rồi success; xác minh delay/backoff và attempt count đúng.
3. **400 test:** xác minh không retry validation error.
4. **Cancellation test:** cancel request trong lúc delay hoặc HTTP call; xác minh loop dừng ngay.
5. **Load/failure test:** 500 concurrent requests khi partner trả 503; đo outbound request amplification, P95/P99 và retry distribution.

## Quan sát trong production

Nên có:

- Logs: operation/idempotency key, attempt, result category, HTTP status, partner request ID.
- Metrics: request count, retry count, retry-exhausted count, 429/5xx rate, timeout rate.
- Traces: từng HTTP attempt là dependency span con của shipment operation.
- Histogram: partner latency và total operation latency.
- Alerts: retry ratio tăng bất thường, 429 spike, timeout spike, unknown-outcome count.

## Câu hỏi phỏng vấn mở rộng

1. Circuit breaker nên đặt ở đâu và có thể gây side effect gì nếu cấu hình quá aggressive?
2. Nếu partner mất 20 giây để xử lý nhưng client timeout 10 giây, bạn phân biệt timeout với operation thất bại thực sự thế nào?
3. Khi nào retry nên đặt ở application layer, khi nào ở message-consumer/background-job layer?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache invalidation không chỉ là “xóa một key”; khi có nhiều cache layers và nhiều instances, cần thiết kế consistency rõ ràng.
- Authorization state là security-sensitive data, vì vậy stale window và failure semantics phải được xác định như business requirement.
- Race condition thường xuất hiện ở khoảng giữa **read**, **commit**, **invalidate** và **repopulate cache**.
- Retry chỉ an toàn khi hiểu rõ operation có idempotent hay không.
- Timeout không đồng nghĩa side effect chưa xảy ra.
- `HttpClient` lifetime, cancellation và retry policy đều ảnh hưởng trực tiếp tới reliability dưới tải.
- Observability phải giúp trả lời: request nào, attempt nào, source nào và failure category nào.

## Mẫu tư duy cần nhớ

1. **Make authoritative state explicit** — xác định source of truth và version của state quan trọng.
2. **Design cache together with invalidation/failure semantics** — không thêm cache trước rồi nghĩ tới correctness sau.
3. **Design retries together with idempotency** — retry và duplicate prevention là một bài toán chung.
4. **Classify failures before retrying** — transient, permanent và unknown outcome cần xử lý khác nhau.
5. **Treat observability as part of the design** — log/metrics/traces phải đủ để chứng minh giả thuyết production.
