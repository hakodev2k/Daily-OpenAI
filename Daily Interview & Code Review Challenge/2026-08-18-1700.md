# Câu 1 — EF Core Tracking và truy vấn phát sinh ngoài dự kiến

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 15 phút
**Kỹ năng được đánh giá:** EF Core runtime, database performance, debugging

## Bối cảnh
Một API ASP.NET Core quản lý Timesheet có lượng dữ liệu lớn. Sau khi thêm màn hình báo cáo, một endpoint từ 500ms tăng lên 8-10 giây. Developer kiểm tra thấy câu lệnh LINQ khá đơn giản và cho rằng EF Core tự tối ưu.

## Câu hỏi chính
Giải thích EF Core thực thi query, tracking, navigation loading như thế nào trong trường hợp này. Những misconception nào có thể khiến query chậm? Bạn xác minh nguyên nhân bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc
- Query đang dùng tracking hay AsNoTracking?
- Có lazy loading không?
- SQL sinh ra thực tế là gì?
- Số lượng bản ghi và execution plan thế nào?

## Gợi ý tư duy
- Không đánh giá hiệu năng chỉ từ LINQ.
- Kiểm tra SQL generated.
- Phân biệt memory processing và database execution.

## Cấu trúc trả lời đề xuất
1. Làm rõ triệu chứng.
2. Phân tích EF Core pipeline.
3. Kiểm tra bằng evidence.
4. Đề xuất tối ưu.
5. Đánh giá trade-off.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu tracking ảnh hưởng change tracker.
- Biết query có thể bị N+1.
- Biết đo trước khi tối ưu.

### Điểm cộng
- Đề cập projection DTO.
- Phân tích index và execution plan.

### Nâng cao
- Cân nhắc caching và pagination.

## Hướng giải quyết tham khảo
Dùng projection khi chỉ cần dữ liệu đọc, AsNoTracking cho read-only, kiểm tra SQL thực tế, tránh load graph quá lớn và tối ưu database khi cần.

## Mẫu trả lời trong phỏng vấn
"Em sẽ không tối ưu LINQ trước. Em cần xem SQL mà EF Core sinh ra, execution plan, số lượng dữ liệu và tracking behavior. Nhiều vấn đề performance đến từ cách query được thực thi chứ không nằm ở cú pháp LINQ."

## Câu hỏi đào sâu
- Khi nào không nên dùng AsNoTracking?
- Split query và single query khác nhau thế nào?
- Làm sao phát hiện N+1 trong production?

## Lỗi trả lời thường gặp
- Chỉ nói thêm index.
- Không kiểm tra SQL generated.
- Không đề cập data volume.

# Câu 2 — Thiết kế Background Job Platform cho xử lý tích hợp Microsoft Graph

**Loại câu hỏi:** System design
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 25 phút
**Kỹ năng được đánh giá:** Architecture, reliability, background processing

## Bối cảnh
Hệ thống cần đồng bộ người dùng từ Microsoft Graph, xử lý Exchange Online mailbox action và chạy nhiều job định kỳ. Hiện tại một số job bị chạy trùng khi deployment hoặc timeout.

## Câu hỏi chính
Thiết kế nền tảng background job cho hệ thống này như thế nào để đảm bảo reliability, idempotency và khả năng vận hành?

## Câu hỏi làm rõ nên cân nhắc
- Job có thể chạy lại không?
- Có yêu cầu thứ tự xử lý không?
- External API có rate limit không?
- Cần retry như thế nào?

## Gợi ý tư duy
- Retry phải đi cùng idempotency.
- Failure là trạng thái bình thường.
- Observability là một phần thiết kế.

## Hướng giải quyết tham khảo
Thiết kế modular monolith với scheduler, queue, worker, persistence trạng thái job, distributed lock khi cần, retry policy, dead-letter handling và audit log.

# Câu 3 — AI Engineering: Code Review Agent cho .NET Repository

**Loại câu hỏi:** AI engineering
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** AI architecture, evaluation, security

## Bối cảnh
Team muốn tạo AI agent tự động review pull request C#/.NET, phân tích security issue, performance problem và đề xuất fix.

## Câu hỏi chính
Thiết kế agent này như thế nào để kết quả đáng tin cậy thay vì chỉ gửi source code vào LLM?

## Câu hỏi làm rõ nên cân nhắc
- Agent có quyền comment hay sửa code không?
- Repository có dữ liệu nhạy cảm không?
- Đánh giá chất lượng review bằng cách nào?

## Gợi ý tư duy
- Context engineering quan trọng hơn prompt dài.
- AI output cần validation.
- Quyền của agent phải giới hạn.

## Hướng giải quyết tham khảo
Kết hợp static analysis, repository context, rules, MCP/tools có kiểm soát, structured output, human approval và evaluation dataset.

# Tổng kết hôm nay

## Kiến thức trọng tâm
- Hiểu cơ chế runtime trước khi tối ưu.
- Background job cần idempotency và observability.
- AI agent production cần validation và permission control.

## Mẫu tư duy cần nhớ
- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Treat observability as part of architecture.
- Validate AI output deterministically.
