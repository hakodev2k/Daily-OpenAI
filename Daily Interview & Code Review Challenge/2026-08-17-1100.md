# Code Review Challenge 1 — Job đồng bộ lịch bị chạy lặp và cập nhật sai trạng thái

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 8 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để đồng bộ thay đổi thời gian của sự kiện sang calendar của người dùng thông qua một external calendar API. Khi admin sửa sự kiện, backend enqueue job cho từng người tham gia. Production chạy nhiều Hangfire workers trên nhiều instance.

External API đôi khi timeout sau khi đã thực hiện request thành công. Hangfire có thể retry job khi exception xảy ra. Gần đây team quan sát thấy một số user nhận update nhiều lần, một số bản ghi `CalendarSync` có trạng thái không khớp với calendar thực tế, và thỉnh thoảng hai worker xử lý cùng một user/event gần như đồng thời.

Yêu cầu business chưa nói rõ liệu một event có thể được admin sửa liên tiếp trong lúc job cũ đang chạy hay không.

## Đoạn code cần review

```csharp
public sealed class CalendarSyncJob
{
    private readonly AppDbContext _db;
    private readonly ICalendarClient _calendarClient;
    private readonly ILogger<CalendarSyncJob> _logger;

    public CalendarSyncJob(
        AppDbContext db,
        ICalendarClient calendarClient,
        ILogger<CalendarSyncJob> logger)
    {
        _db = db;
        _calendarClient = calendarClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid syncId)
    {
        var sync = await _db.CalendarSyncs
            .Include(x => x.Event)
            .SingleAsync(x => x.Id == syncId);

        if (sync.Status == "Completed")
            return;

        sync.Status = "Processing";
        sync.AttemptCount++;
        await _db.SaveChangesAsync();

        try
        {
            await _calendarClient.UpdateEventAsync(
                sync.UserId,
                sync.ExternalEventId,
                sync.Event.StartTime,
                sync.Event.EndTime);

            sync.Status = "Completed";
            sync.CompletedAt = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            sync.Status = "Failed";
            sync.LastError = ex.ToString();
            await _db.SaveChangesAsync();

            _logger.LogError(ex,
                "Calendar sync failed for {SyncId} user {UserId}",
                sync.Id,
                sync.UserId);

            throw;
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không atomic

- **Problem:** Hai worker có thể cùng đọc trạng thái chưa `Completed` rồi cùng gọi external API.
- **Why it happens:** Việc đọc trạng thái và chuyển sang `Processing` không có cơ chế compare-and-set/concurrency control.
- **Production impact:** Duplicate external updates, race giữa các phiên bản dữ liệu và trạng thái cuối khó dự đoán.
- **Severity:** Critical
- **Recommended fix:** Claim job bằng atomic conditional update hoặc optimistic concurrency token; chỉ worker claim thành công mới được xử lý.

### 2. Timeout sau external success tạo ambiguous outcome

- **Problem:** HTTP timeout không chứng minh operation bên ngoài chưa thành công.
- **Why it happens:** Distributed call có thể hoàn tất ở server nhưng response bị mất hoặc client timeout.
- **Production impact:** Retry có thể thực hiện side effect lần nữa.
- **Severity:** Critical
- **Recommended fix:** Dùng idempotency/version semantics nếu API hỗ trợ; nếu không, đọc lại remote state để reconcile trước retry khi khả thi.

### 3. Không gắn job với version của event

- **Problem:** Job đọc `sync.Event.StartTime/EndTime` tại thời điểm thực thi.
- **Why it happens:** Payload chỉ chứa `syncId`, không xác định desired version/snapshot.
- **Production impact:** Job cũ có thể gửi dữ liệu mới hoặc cạnh tranh với job mới; không biết update nào job đang đại diện.
- **Severity:** High
- **Recommended fix:** Lưu desired version và desired state trong sync command, hoặc dùng monotonic event version và bỏ qua command stale.

### 4. `Failed` có thể là trạng thái sai

- **Problem:** Catch mọi exception rồi đánh dấu `Failed` ngay cả khi remote side effect đã xảy ra.
- **Why it happens:** Code coi transport exception là business outcome.
- **Production impact:** Database và remote calendar bất nhất; operator có thể retry thủ công gây duplicate.
- **Severity:** High
- **Recommended fix:** Phân biệt `Retryable`, `PermanentFailure`, `UnknownOutcome`; reconcile trường hợp không xác định.

### 5. Không có cancellation/timeout contract rõ ràng

- **Problem:** `ExecuteAsync` không nhận `CancellationToken`; external call cũng không truyền token trong API hiện tại.
- **Why it happens:** Job không hỗ trợ cooperative cancellation.
- **Production impact:** Shutdown/deployment có thể để operation kéo dài; recovery chậm.
- **Severity:** Medium
- **Recommended fix:** Truyền cancellation token xuyên suốt và cấu hình timeout tại HTTP layer phù hợp.

### 6. Lưu toàn bộ `ex.ToString()` vào database

- **Problem:** Persist raw exception có thể chứa URL, identifier hoặc dữ liệu nhạy cảm và tăng kích thước record.
- **Why it happens:** Diagnostic data không được phân loại.
- **Production impact:** Data exposure, record phình lớn, khó quản trị retention.
- **Severity:** Medium
- **Recommended fix:** Lưu error code/message đã sanitize và correlation ID; stack trace để structured logging có retention phù hợp.

### 7. Magic string cho state machine

- **Problem:** `"Processing"`, `"Completed"`, `"Failed"` không mô hình hóa state transition rõ ràng.
- **Why it happens:** State machine chỉ tồn tại ngầm trong code.
- **Production impact:** Dễ sinh transition không hợp lệ khi workflow mở rộng.
- **Severity:** Medium
- **Recommended fix:** Enum/value object và xác định transition hợp lệ.

### 8. Thiếu telemetry về attempt và external operation

- **Problem:** Chỉ log khi exception; không có duration/result/version/correlation cho success.
- **Why it happens:** Observability chưa được coi là một phần của workflow.
- **Production impact:** Khó phân biệt duplicate execution, stale command, timeout và remote failure.
- **Severity:** Medium
- **Recommended fix:** Structured logs, tracing và metrics cho claim, attempt, external latency, retry, stale skip, reconcile.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định `CalendarSync.Version` là concurrency token và mỗi sync chứa snapshot/version mong muốn. Production có thể dùng conditional `ExecuteUpdateAsync` để claim atomically thay vì load entity trước.

```csharp
public sealed class CalendarSyncJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ICalendarClient _calendarClient;
    private readonly ILogger<CalendarSyncJob> _logger;

    public CalendarSyncJob(
        IDbContextFactory<AppDbContext> dbFactory,
        ICalendarClient calendarClient,
        ILogger<CalendarSyncJob> logger)
    {
        _dbFactory = dbFactory;
        _calendarClient = calendarClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid syncId, CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.CalendarSyncs
            .Where(x => x.Id == syncId &&
                        (x.Status == SyncStatus.Pending ||
                         x.Status == SyncStatus.Retryable))
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, SyncStatus.Processing)
                .SetProperty(x => x.AttemptCount, x => x.AttemptCount + 1)
                .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

        if (claimed == 0)
            return;

        var sync = await db.CalendarSyncs
            .AsNoTracking()
            .SingleAsync(x => x.Id == syncId, ct);

        try
        {
            var result = await _calendarClient.UpdateEventAsync(
                sync.UserId,
                sync.ExternalEventId,
                sync.DesiredStartTime,
                sync.DesiredEndTime,
                sync.EventVersion,
                ct);

            await db.CalendarSyncs
                .Where(x => x.Id == syncId && x.Status == SyncStatus.Processing)
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, SyncStatus.Completed)
                    .SetProperty(x => x.CompletedAt, DateTime.UtcNow)
                    .SetProperty(x => x.RemoteVersion, result.Version), ct);
        }
        catch (CalendarOutcomeUnknownException ex)
        {
            await MarkAsync(db, syncId, SyncStatus.UnknownOutcome,
                ex.ErrorCode, ct);
            throw;
        }
        catch (CalendarTransientException ex)
        {
            await MarkAsync(db, syncId, SyncStatus.Retryable,
                ex.ErrorCode, ct);
            throw;
        }
        catch (CalendarPermanentException ex)
        {
            await MarkAsync(db, syncId, SyncStatus.Failed,
                ex.ErrorCode, ct);

            _logger.LogWarning(
                "Permanent calendar sync failure {SyncId} {ErrorCode}",
                syncId, ex.ErrorCode);
        }
    }

    private static Task<int> MarkAsync(
        AppDbContext db,
        Guid id,
        SyncStatus status,
        string errorCode,
        CancellationToken ct) =>
        db.CalendarSyncs
            .Where(x => x.Id == id && x.Status == SyncStatus.Processing)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, status)
                .SetProperty(x => x.LastErrorCode, errorCode), ct);
}
```

Thiết kế vẫn cần một recovery process cho record bị kẹt ở `Processing` do process crash và một reconciliation flow cho `UnknownOutcome`. Nếu external API không hỗ trợ idempotency/version, không nên tuyên bố exactly-once; mục tiêu thực tế là at-least-once execution cộng với idempotent/reconcilable effect.

## Trade-offs

Atomic database claim giảm duplicate worker nhưng không biến DB + external API thành một distributed transaction. Lease/lock có thể phù hợp nếu call dài, nhưng phải xử lý lease expiry và crash. Snapshot command giúp reproducibility nhưng tốn storage; latest-state synchronization đơn giản hơn nếu business chỉ quan tâm trạng thái cuối, khi đó job nên kiểm tra version và bỏ qua các version cũ.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 execution đồng thời cho cùng `syncId`; chỉ một execution được claim.
2. **Ambiguous failure:** fake calendar server thực hiện update rồi làm client timeout; verify workflow chuyển sang `UnknownOutcome` và reconcile thay vì blind retry.
3. **Version race:** enqueue version 10 và 11, cho version 10 chạy chậm; trạng thái remote cuối phải là version 11.
4. **Crash recovery:** worker chết sau khi claim; recovery process phải đưa record hết lease về trạng thái có thể xử lý lại.
5. **Permanent failure:** remote trả lỗi business/non-retryable; không tạo retry loop vô hạn.

## Quan sát trong production

Theo dõi `calendar_sync_attempt_total`, retry rate, unknown-outcome count, stale-command count, processing age, external latency/error rate và số record stuck. Trace nên nối Hangfire job → DB claim → HTTP request → reconciliation bằng correlation ID. Alert khi `Processing` vượt lease threshold hoặc `UnknownOutcome` tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu calendar API không có idempotency key, bạn thiết kế reconciliation thế nào?
2. Distributed lock bằng Redis có giải quyết hoàn toàn vấn đề duplicate không? Vì sao?
3. Nếu business chỉ yêu cầu eventual latest state thay vì xử lý mọi intermediate update, bạn sẽ đơn giản hóa thiết kế ra sao?

# Code Review Challenge 2 — API tìm kiếm audit log vừa chậm vừa có lỗ hổng authorization

**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép tenant admin tìm kiếm audit log. Bảng `AuditLogs` đã có hàng triệu record và tiếp tục tăng. QA báo endpoint đôi khi mất vài giây, memory của API tăng mạnh khi search khoảng thời gian dài. Security review cũng phát hiện có khả năng user của tenant A xem được log của tenant B nếu biết identifier.

Audit log có thể chứa email, request metadata và một phần payload phục vụ điều tra sự cố. Product chưa xác định rõ trường nào thực sự cần trả về màn hình danh sách.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit-logs")]
public sealed class AuditLogsController : ControllerBase
{
    private readonly AppDbContext _db;

    public AuditLogsController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        string tenantId,
        string? keyword,
        DateTime? from,
        DateTime? to,
        int page = 1,
        int pageSize = 1000)
    {
        var logs = await _db.AuditLogs
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(tenantId))
            logs = logs.Where(x => x.TenantId == tenantId).ToList();

        if (from.HasValue)
            logs = logs.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            logs = logs.Where(x => x.CreatedAt <= to.Value).ToList();

        if (!string.IsNullOrWhiteSpace(keyword))
            logs = logs.Where(x =>
                x.Message.Contains(keyword, StringComparison.OrdinalIgnoreCase) ||
                x.RequestBody.Contains(keyword, StringComparison.OrdinalIgnoreCase))
                .ToList();

        return Ok(logs
            .Skip((page - 1) * pageSize)
            .Take(pageSize));
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant authorization / IDOR-style data access

- **Problem:** Client tự truyền `tenantId`; endpoint chỉ yêu cầu authenticated user.
- **Why it happens:** Authentication không chứng minh user được phép truy cập tenant được yêu cầu.
- **Production impact:** Cross-tenant audit-log disclosure.
- **Severity:** Critical
- **Recommended fix:** Derive tenant scope từ trusted claims/server-side membership hoặc authorize requested tenant bằng policy/resource authorization; không tin query parameter.

### 2. Load toàn bộ bảng trước khi filter

- **Problem:** `ToListAsync()` chạy trước mọi predicate.
- **Why it happens:** Query được materialize thành `List<AuditLog>`; filter sau đó là LINQ-to-Objects.
- **Production impact:** Full-table read, memory pressure, GC pressure và latency tăng theo kích thước bảng.
- **Severity:** High
- **Recommended fix:** Giữ `IQueryable`, áp dụng tenant/date/search filters trước materialization.

### 3. Trả entity chứa dữ liệu nhạy cảm

- **Problem:** `Ok(logs...)` serialize entity đầy đủ, có thể gồm request payload hoặc fields nội bộ.
- **Why it happens:** Persistence model được dùng trực tiếp làm API contract.
- **Production impact:** PII/secrets hoặc payload nhạy cảm có thể bị lộ ngoài nhu cầu UI.
- **Severity:** High
- **Recommended fix:** Project sang DTO allowlist; redaction/masking; endpoint riêng có authorization mạnh hơn nếu cần xem detail payload.

### 4. Không giới hạn `pageSize`, page và time range

- **Problem:** Caller có thể gửi giá trị rất lớn hoặc page không hợp lệ.
- **Why it happens:** Thiếu input constraints.
- **Production impact:** Expensive queries, abuse/DoS và overflow/logic edge cases.
- **Severity:** High
- **Recommended fix:** Validate `page >= 1`, clamp `pageSize`, giới hạn time window hoặc yêu cầu filter phù hợp.

### 5. Search payload tùy ý khó scale

- **Problem:** Substring search trên message/body có thể buộc scan lớn; trong code hiện tại còn diễn ra trong memory.
- **Why it happens:** Không có search strategy/index phù hợp.
- **Production impact:** CPU/IO cao và latency khó dự đoán.
- **Severity:** Medium
- **Recommended fix:** Xác định search requirement; dùng database-supported search/index phù hợp hoặc search store chuyên dụng khi justified. Không mặc định kéo dữ liệu về app.

### 6. Pagination bằng offset có thể chậm và không ổn định

- **Problem:** `Skip` lớn tốn chi phí; order chỉ theo `CreatedAt` không deterministic khi timestamp bằng nhau.
- **Why it happens:** Offset pagination và thiếu tie-breaker.
- **Production impact:** Duplicate/missing rows giữa các page khi data mới được ghi; deep page chậm.
- **Severity:** Medium
- **Recommended fix:** Ít nhất order thêm `Id`; với volume lớn cân nhắc keyset pagination `(CreatedAt, Id)`.

### 7. Read-only query vẫn tracking nếu dùng entity mặc định

- **Problem:** Nếu query entity trực tiếp, EF Core mặc định tracking entity.
- **Why it happens:** Không dùng projection hoặc `AsNoTracking`.
- **Production impact:** Thêm memory/ChangeTracker overhead.
- **Severity:** Low
- **Recommended fix:** Projection DTO thường loại bỏ nhu cầu tracking; nếu trả entity read-only thì `AsNoTracking()`.

## Phiên bản code đề xuất

Ví dụ giả định tenant ID được lấy từ một `ICurrentTenant` đã được xác thực/authorize ở server và UI danh sách không cần request body.

```csharp
[Authorize(Policy = "TenantAuditReader")]
[ApiController]
[Route("api/audit-logs")]
public sealed class AuditLogsController : ControllerBase
{
    private const int MaxPageSize = 100;

    private readonly AppDbContext _db;
    private readonly ICurrentTenant _currentTenant;

    public AuditLogsController(
        AppDbContext db,
        ICurrentTenant currentTenant)
    {
        _db = db;
        _currentTenant = currentTenant;
    }

    [HttpGet]
    public async Task<ActionResult<IReadOnlyList<AuditLogListItem>>> Search(
        string? keyword,
        DateTimeOffset? from,
        DateTimeOffset? to,
        int page = 1,
        int pageSize = 50,
        CancellationToken ct = default)
    {
        if (page < 1)
            return BadRequest("page must be >= 1");

        pageSize = Math.Clamp(pageSize, 1, MaxPageSize);

        if (from.HasValue && to.HasValue && from > to)
            return BadRequest("from must be <= to");

        if (from.HasValue && to.HasValue &&
            to.Value - from.Value > TimeSpan.FromDays(31))
            return BadRequest("time range is too large");

        var query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == _currentTenant.Id);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value);

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            var term = keyword.Trim();
            query = query.Where(x => x.Message.Contains(term));
        }

        var items = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new AuditLogListItem(
                x.Id,
                x.CreatedAt,
                x.Action,
                x.Message,
                x.ActorId))
            .ToListAsync(ct);

        return Ok(items);
    }
}
```

`Contains` ở ví dụ chỉ minh họa query được server-side; semantics và SQL translation phụ thuộc provider/collation. Nếu cần case-insensitive hoặc full-text search, phải thiết kế theo SQL Server/PostgreSQL và indexing strategy cụ thể thay vì giả định hành vi giống nhau giữa providers.

## Trade-offs

Offset pagination dễ triển khai và đủ tốt cho các page đầu; keyset pagination tốt hơn cho dataset lớn nhưng API phức tạp hơn. Giới hạn 31 ngày và page size 100 chỉ là policy minh họa, phải chọn theo business và load testing chứ không coi là universal limit. Full-text/search infrastructure chỉ đáng thêm khi requirement và volume chứng minh cần thiết.

## Cách kiểm thử

1. **Security integration test:** user tenant A yêu cầu dữ liệu tenant B bằng mọi parameter có thể; không record tenant B được trả về.
2. **SQL/query test:** xác nhận generated SQL chứa tenant/date predicate và projection trước materialization.
3. **Load test:** dataset hàng triệu rows, kiểm tra latency/memory cho common filters và deep pagination.
4. **Sensitive-data test:** response list không chứa `RequestBody`, token, headers hoặc fields ngoài allowlist.
5. **Pagination test:** nhiều rows cùng timestamp và concurrent inserts không phá deterministic ordering; nếu dùng keyset, kiểm tra không duplicate/missing giữa cursor pages.

## Quan sát trong production

Theo dõi endpoint duration p50/p95/p99, rows returned, rejected oversized queries, DB query duration, logical reads/IO, timeout rate và process memory/GC. Log tenant từ trusted server context, không log raw request payload. Database cần theo dõi execution plan, index usage và các query scan lớn.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ thiết kế index khác nhau thế nào cho SQL Server và PostgreSQL nếu pattern phổ biến là tenant + date range?
2. Nếu security team yêu cầu support engineer xem cross-tenant logs, bạn thiết kế authorization và audit trail ra sao?
3. Khi nào bạn chuyển từ database search sang một search engine riêng, và chi phí consistency của quyết định đó là gì?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào distributed side effects: database transaction không thể tự đảm bảo exactly-once cho HTTP call; retry phải đi cùng idempotency, versioning và reconciliation. Challenge 2 tập trung vào hai boundary quan trọng của backend: authentication không thay thế tenant authorization, và vị trí materialize EF Core query quyết định phần lớn correctness/performance của data access.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng idempotency và ambiguous-outcome recovery.
- Với concurrent workers, biến “check rồi update” thành atomic claim/compare-and-set.
- Không tin tenant/resource identifier do client gửi; authorization phải dựa trên trusted server context.
- Giữ filter/projection trong `IQueryable` cho tới khi thật sự cần materialize.
- Observability là một phần của thiết kế workflow, không phải phần bổ sung sau incident.
