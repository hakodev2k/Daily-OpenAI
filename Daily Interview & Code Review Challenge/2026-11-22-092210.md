# Câu 1 — .NET GC và LOH: vì sao API xuất báo cáo tăng memory dù không có memory leak?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** C# memory allocation, GC, LOH, ASP.NET Core streaming, profiling, cancellation

## Bối cảnh

API .NET 8 tạo file CSV cho hệ thống timesheet. Endpoint đọc 200.000 dòng từ PostgreSQL, ghép một chuỗi CSV lớn bằng `StringBuilder`, gọi `ToString()`, sau đó `Encoding.UTF8.GetBytes()` và trả `File(byte[], "text/csv")`. Khi 40 người tải cùng lúc, working set tăng từ 600 MB lên 3 GB, p99 tăng mạnh; sau khi tải xong memory không giảm ngay. Không có bằng chứng về object bị giữ vô hạn. Một thành viên đề xuất gọi `GC.Collect()` sau mỗi response.

## Câu hỏi chính

Giải thích chính xác các allocation và cơ chế GC có thể gây triệu chứng này; bạn sẽ chứng minh giả thuyết và thiết kế export ít tốn memory, vẫn xử lý cancellation, lỗi giữa stream và client chậm như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Kích thước CSV sau encode, peak concurrent exports và giới hạn memory của host?
2. Dữ liệu được EF Core materialize toàn bộ hay đọc bằng forward-only reader?
3. Có proxy/CDN buffering, compression hoặc yêu cầu Content-Length không?
4. Export có cần snapshot nhất quán, file tải lại hoặc audit không?
5. Memory đo là managed heap, private bytes, working set hay container RSS?

## Gợi ý tư duy

### Gợi ý 1
Một báo cáo có thể tồn tại đồng thời dưới nhiều representation trong memory.

### Gợi ý 2
Đối chiếu allocation lớn với LOH, Gen 2 collection và khả năng giữ heap đã reserve.

### Gợi ý 3
Phân biệt streaming từ database với streaming tới HTTP; chỉ sửa một đầu chưa đủ.

## Cấu trúc trả lời đề xuất

1. Nêu giả định về export và consistency.
2. Vẽ data flow cùng kích thước allocation.
3. Phân biệt live heap, reserved heap và OS memory.
4. Thu thập allocation profile, GC counters và request traces.
5. So sánh streaming trực tiếp với background export ra Blob Storage.
6. Đánh giá failure, cancellation, giới hạn đồng thời, kiểm thử và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `StringBuilder`, `ToString()` và UTF-8 `byte[]` có thể tạo nhiều bản dữ liệu lớn cùng lúc; kích thước char UTF-16 không đồng nhất với byte UTF-8.
- Object đủ lớn được cấp phát trên LOH; thu gom và compact LOH có đặc tính khác small object heap, không thể suy từ working set rằng có leak.
- `GC.Collect()` cưỡng bức thường gây pause/throughput regression và không giải quyết peak allocation.
- Streaming phải tránh materialize cả database result lẫn response; truyền `RequestAborted` và xử lý client disconnect.

### Điểm cộng
- Đo `dotnet-counters`, `dotnet-gcdump`/`dotnet-trace` phù hợp môi trường, allocation rate, GC pause, Gen 2 count và số export đang chạy.
- Dùng `DbDataReader` async, `StreamWriter` trên `Response.Body`, ghi theo từng dòng, CSV escaping đúng quy tắc và flush hợp lý.
- Có concurrency limit, rate limit, timeout và test client chậm.

### Senior+
- Phân tích tính nhất quán khi dữ liệu thay đổi trong lúc đọc và rủi ro transaction kéo dài.
- So sánh export trực tiếp với job async + Azure Blob Storage + short-lived SAS; lưu ý quyền truy cập, retention và cleanup.
- Phân biệt response đã gửi headers với lỗi sau khi stream bắt đầu: không thể đơn giản đổi thành HTTP 500.

## Hướng giải quyết tham khảo

**Cơ chế:** `StringBuilder` giữ buffer ký tự; `ToString()` tạo string mới; `GetBytes()` tạo byte array mới. Các buffer lớn có thể tồn tại chồng lấp và tạo allocation rate cao. Với nhiều request, áp lực heap làm tăng GC, đặc biệt Gen 2/LOH. Managed heap có thể giữ lại committed/reserved memory để tái sử dụng sau khi object đã chết; working set không phải số byte còn reachable. Không kết luận leak khi chưa đo live objects qua nhiều chu kỳ GC.

**Kiểm chứng:** tái hiện với 1/10/40 export, so sánh peak bytes/request, allocation rate, GC pause time, thread pool queue length, database duration và p95/p99. Lấy heap snapshot ở trạng thái idle trước/sau để tìm retention; so sánh LOH size với private bytes. Kiểm tra proxy buffering trước khi tuyên bố streaming đã giảm memory end-to-end.

**Phương án:** đọc dữ liệu theo từng row bằng async reader, serialize CSV đúng escaping (quote, comma, CR/LF, formula injection nếu file mở trong spreadsheet), ghi qua `StreamWriter` vào HTTP response, `FlushAsync` theo batch, truyền cancellation. Đặt giới hạn export song song và max rows; đo backpressure khi client chậm. Ví dụ định hướng:

```csharp
app.MapGet("/exports/timesheets", async (
    HttpContext http, NpgsqlDataSource source) =>
{
    http.Response.ContentType = "text/csv; charset=utf-8";
    http.Response.Headers.ContentDisposition =
        "attachment; filename=\"timesheets.csv\"";
    await using var connection = await source.OpenConnectionAsync(
        http.RequestAborted);
    await using var command = connection.CreateCommand();
    command.CommandText = """
        SELECT employee_name, hours
        FROM timesheets
        ORDER BY id
        """;
    await using var reader = await command.ExecuteReaderAsync(
        System.Data.CommandBehavior.SequentialAccess,
        http.RequestAborted);
    await using var writer = new StreamWriter(
        http.Response.Body, new UTF8Encoding(false), leaveOpen: true);
    await writer.WriteLineAsync("Employee,Hours");
    while (await reader.ReadAsync(http.RequestAborted))
    {
        var name = reader.GetString(0);
        var safeName = "\"" + name.Replace("\"", "\"\"") + "\"";
        await writer.WriteLineAsync(
            $"{safeName},{reader.GetDecimal(1).ToString(System.Globalization.CultureInfo.InvariantCulture)}");
    }
    await writer.FlushAsync(http.RequestAborted);
});
```

Đây là minh họa cơ chế, chưa phải endpoint production hoàn chỉnh: cần authorization, quota, CSV injection policy, audit và exception handling trước khi response bắt đầu. Nếu export kéo dài nhiều phút hoặc phải resume, chuyển sang background job tạo object trong Blob Storage rồi cấp link tải có thời hạn; phải có cơ chế xác thực quyền tải.

**Trade-offs:** streaming giảm peak memory nhưng giữ connection DB lâu và không hỗ trợ resume tốt; background export thêm queue, storage, cleanup và eventual completion. Giới hạn đồng thời bảo vệ hệ thống nhưng tăng thời gian chờ. Không tối ưu khi chưa biết bottleneck là DB, CPU encode hay network.

**Testing/monitoring:** load test với 40 client và client đọc chậm; cancel giữa stream; CSV special characters; export trong khi DB thay đổi; memory regression. Theo dõi bytes/export, duration, active exports, GC heap/LOH, Gen 2 collections, allocation rate, response aborts và database pool usage.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak. Đầu tiên tôi xác định peak concurrent exports, kích thước file và memory metric. Pipeline hiện tại giữ dữ liệu dưới dạng ký tự và byte array, nên một export lớn có thể tạo nhiều allocation lớn, cộng dồn theo số request. LOH và GC có thể làm memory cao kéo dài ngay cả khi request kết thúc. Tôi sẽ chạy load test có profiling để phân biệt live object retention với heap reuse và GC pressure. Giải pháp ưu tiên là đọc DB từng dòng và ghi response từng batch, giới hạn concurrency, propagate cancellation và kiểm tra proxy buffering. Nếu cần export rất lớn, resumable hoặc audit, tôi chọn background job ghi Blob Storage. Tôi không gọi GC.Collect mỗi request vì chi phí pause và throughput. Tôi cũng theo dõi DB connection duration, backpressure và lỗi client disconnect để tránh đổi memory issue thành connection exhaustion.”

## Câu hỏi đào sâu

1. Nếu response đã gửi 100 MB rồi database timeout, API nên xử lý trạng thái tải thế nào?
2. Nếu streaming giữ connection 15 phút khiến pool cạn, bạn thay đổi thiết kế ra sao?
3. Vì sao LOH giảm sau GC nhưng RSS không giảm tương ứng?

## Lỗi trả lời thường gặp

- Khẳng định working set tăng là leak mà không đo live heap.
- Gọi `GC.Collect()` theo mỗi request.
- Chỉ stream HTTP nhưng vẫn `ToListAsync()` toàn bộ rows.
- Bỏ qua CSV escaping, authorization và cancellation.
- Không xem ảnh hưởng của export dài tới database pool.

## Thang điểm 0–10

- 0–2: Chỉ nói “memory leak” hoặc tăng RAM, không giải thích allocation.
- 3–4: Nhận ra buffer lớn nhưng chưa có bằng chứng hoặc failure handling.
- 5–6: Giải thích GC/LOH, đề xuất streaming và đo được metrics cơ bản.
- 7–8: Phân tích hai đầu DB/HTTP, concurrency, cancellation, testing và trade-offs.
- 9–10: Thiết kế có capacity guardrails, consistency contract, telemetry và chiến lược export async phù hợp; diễn đạt rõ giả định và bằng chứng.

# Câu 2 — IIS / Windows Server: sau deployment, App Pool recycle liên tục và người dùng nhận 502/503

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC, .NET Framework modernization, CI/CD, incident response, Application Insights

## Bối cảnh

Một cổng quản lý nhân sự ASP.NET MVC trên .NET Framework 4.5 chạy IIS/Windows Server, có SQL Server và tích hợp SSO. TeamCity build artifact; Octopus Deploy triển khai lên hai web nodes sau load balancer. Sau release, 15% request trả 502/503, đăng nhập chập chờn, CPU đôi lúc tăng; rollback trên một node làm lỗi giảm nhưng chưa hết. Nhật ký cho thấy App Pool recycle gần thời điểm lỗi; QA chỉ kiểm thử một node. Product cần phục hồi nhanh nhưng không muốn mất dữ liệu phiên đang xử lý. Chưa xác minh web garden, load balancer health checks, session mode, deployment config hoặc nguyên nhân recycle.

## Câu hỏi chính

Bạn là người điều phối incident. Hãy mô tả từ impact → stabilization → evidence → competing hypotheses → verification → root cause → remediation → prevention, phân biệt dấu hiệu App Pool recycle với nguyên nhân gốc, và thiết kế release an toàn cho hệ thống legacy này.

## Câu hỏi làm rõ nên cân nhắc

1. 502 do load balancer hay reverse proxy; 503 do IIS queue/app pool unavailable hay ứng dụng?
2. Session đang InProc, StateServer hay SQLServer; machineKey có đồng nhất giữa nodes?
3. Recycle do schedule, memory limit, rapid-fail protection, deployment file change hay crash?
4. Artifact/config/connection string/SSO certificate có giống nhau trên hai nodes?
5. Có maintenance window, drain connection và rollback DB schema tương thích không?

## Gợi ý tư duy

### Gợi ý 1
Phân tách nơi phát sinh status code và thời điểm worker process thay đổi.

### Gợi ý 2
Kết hợp Event Viewer, IIS logs, HTTPERR, deployment logs và health probes.

### Gợi ý 3
Một recycle có thể là triệu chứng, hành vi cấu hình bình thường hoặc hệ quả crash; tìm nguyên nhân có timestamp khớp.

## Cấu trúc trả lời đề xuất

1. Định lượng ảnh hưởng theo node, endpoint và login flow.
2. Ổn định bằng traffic drain, rollback tương thích, hoặc cô lập node lỗi.
3. Đồng bộ timeline deployment, recycle và error spikes.
4. Kiểm chứng nhiều giả thuyết độc lập.
5. Chọn remediation dựa trên bằng chứng.
6. Triển khai canary/rolling release với health gate.
7. Test failure paths và thiết lập alert/owner.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không kết luận recycle là root cause; phải xem Event Viewer/WAS/W3SVC, process exit và cấu hình App Pool.
- Phân biệt 502 upstream và 503 IIS, xác định node/instance bằng correlation.
- Rollback từng node phải xét DB migration backward compatibility và session continuity.
- Có stabilization trước deep diagnosis, timeline và hypotheses cạnh tranh.

### Điểm cộng
- Kiểm tra `web.config`, binding redirects, native dependencies, application startup, machineKey, certificate và health probe.
- Xem deployment artifact hashes và Octopus variable substitutions giữa environments/nodes.
- Thiết kế warmup, drain, canary, smoke test login/SSO, synthetic probes.

### Senior+
- Có runbook khôi phục, rollback gate, deployment audit, chiến lược session ngoài process và migration expand/contract.
- Truyền thông impact/ETA dựa trên dữ liệu, không suy đoán root cause.

## Hướng giải quyết tham khảo

**Impact:** phân loại 5xx theo node, URL, user journey, phút bắt đầu và error budget. Xác nhận login failure có liên quan recycle hay SSO callback; xác minh dữ liệu nghiệp vụ có bị ghi một phần không.

**Stabilize:** tạm dừng rollout; drain node nghi vấn khỏi load balancer, giữ node khỏe, rollback artifact nếu tương thích schema và config. Tránh recycle hàng loạt vì có thể làm mất InProc session. Nếu session InProc, nêu rõ rủi ro session loss ngay cả khi drain, và chuẩn bị thông báo người dùng. Không khôi phục backup database chỉ vì 5xx.

**Evidence:** đồng bộ UTC timestamps giữa TeamCity/Octopus, Windows Event Viewer, WAS/W3SVC, IIS access logs, HTTPERR, load balancer logs, Application Insights traces và SQL dependency telemetry. Kiểm tra App Pool start/stop, exit code, rapid-fail, private memory thresholds, scheduled recycle, `web.config` modification và deployment file locks. So sánh artifact hashes và cấu hình hai nodes.

**Giả thuyết A — config drift:** biến môi trường hoặc binding redirect sai trên node B làm app startup fail; kiểm chứng bằng diff config đã redacted, startup exceptions và smoke test trực tiếp từng node. **B — process crash/memory:** memory pressure hoặc native crash kích hoạt recycle; kiểm chứng crash dump, process private bytes và Windows events. **C — session/crypto:** InProc session và machineKey không đồng nhất làm login mất sau load balancing/recycle; kiểm chứng cookie validation failures, affinity và session mode. **D — load balancer health:** probe chỉ kiểm tra TCP hoặc trang tĩnh nên gửi traffic vào worker chưa warm; kiểm chứng backend pool health và startup duration. **E — SQL/SSO dependency:** connection pool exhaustion hoặc token validation failure trùng release; đối chiếu dependency telemetry. Chỉ công bố root cause sau khi một giả thuyết được xác minh bằng chứng và tái hiện/kiểm chứng sau fix.

**Remediation:** nếu lỗi config, khôi phục giá trị chuẩn và restart có kiểm soát; nếu startup failure, sửa binding/dependency; nếu session continuity là vấn đề, cân nhắc state ngoài process và cấu hình khóa bảo vệ nhất quán, sau khi đánh giá compatibility. Triển khai node-by-node: preflight artifact checksum, config validation, deploy, warmup, health check nghiệp vụ, smoke test SSO, quan sát 5xx và p95 trước khi chuyển traffic. Với DB migration, dùng expand/contract để old/new versions cùng hoạt động; rollback app không tự rollback data migration.

**Prevention:** immutable artifact, config-as-code, deploy variable review, automated post-deploy Playwright login flow, per-node health and alerts, rollback drill, crash-dump retention có kiểm soát và release checklist. Không khuyến nghị chuyển ngay lên Kubernetes hoặc rewrite .NET 10 giữa incident.

## Mẫu trả lời trong phỏng vấn

“Tôi ưu tiên giảm ảnh hưởng trước: dừng rollout, xác định node lỗi, drain hoặc rollback có kiểm tra schema compatibility. Recycle chỉ là tín hiệu; tôi phải đối chiếu Event Viewer, WAS, IIS, HTTPERR, load balancer và Octopus timeline để biết worker chết, bị recycle theo cấu hình hay chưa warmup. Tôi giữ ít nhất ba giả thuyết: startup/config drift, memory/crash và session/SSO inconsistency. Tôi kiểm chứng bằng so sánh node, crash events, cookie failures và dependency traces. Khi có root cause, tôi triển khai bản sửa qua một node, warmup và smoke test SSO rồi mới mở traffic. Sau incident, tôi bổ sung immutable artifacts, health gates, session strategy và rollback drill. Tôi không coi migrate toàn bộ hệ thống là biện pháp khẩn cấp.”

## Câu hỏi đào sâu

1. Nếu rollback binary nhưng migration đã xóa column mà bản cũ cần, bạn làm gì?
2. Nếu App Pool recycle đúng lịch nhưng lỗi chỉ xuất hiện sau release, bạn phân biệt correlation và causation ra sao?
3. Nếu session InProc đang được dùng, có thể bảo đảm zero session loss khi recycle không?

## Lỗi trả lời thường gặp

- Restart IIS toàn bộ cluster trước khi cô lập impact.
- Đồng nhất 502 với 503 hoặc không kiểm tra nguồn status.
- Kết luận memory leak chỉ vì App Pool recycle.
- Rollback không xét schema và session.
- Chỉ kiểm tra homepage, bỏ qua login và SSO callback.

## Thang điểm 0–10

- 0–2: Chỉ restart server, không đánh giá impact.
- 3–4: Biết xem logs nhưng thiếu hypotheses và rollback safety.
- 5–6: Có timeline, stabilization, phân tích IIS/SSO và test cơ bản.
- 7–8: Chứng minh root cause, rollout theo node, health gate và telemetry.
- 9–10: Quản lý rủi ro dữ liệu/session, migration compatibility, incident communication và phòng ngừa có đo lường.

# Câu 3 — Optimizely CMS, Akamai và e-commerce: thiết kế cập nhật nội dung đúng mà không purge toàn site

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, content modeling, Akamai CDN, cache invalidation, SEO, Vue.js, external APIs, Azure hosting, architecture trade-offs

## Bối cảnh

Một website marketing và catalog xe có Optimizely CMS quản lý page types/content blocks, ASP.NET Core backend, Vue.js frontend ở một số trang, Akamai CDN và product availability API từ đối tác. Biên tập viên publish giá trị marketing và banner thường xuyên; product availability thay đổi từng phút. Sau publish, người dùng ở vài khu vực thấy banner cũ; nếu purge toàn site thì origin tăng tải và p95 xấu đi. Product muốn nội dung mới xuất hiện “ngay lập tức”, SEO ổn định và availability không sai nghiêm trọng. Chưa rõ traffic, SLA freshness, cache keys, multi-language, personalization và khả năng purge theo surrogate keys.

## Câu hỏi chính

Hãy đề xuất kiến trúc content delivery, cache ownership, invalidation, frontend hydration và deployment phù hợp. So sánh ít nhất hai phương án, định nghĩa consistency/freshness contract và failure behavior; chỉ thêm complexity khi có lợi ích chứng minh được.

## Câu hỏi làm rõ nên cân nhắc

2. Nội dung nào public, personalized, theo locale/market và có user-specific pricing không?

4. Product availability có thể stale bao lâu và có quyền hiển thị “không xác định” không?
5. Vue được SSR, prerender hay client render; canonical, sitemap và metadata lấy từ đâu?

## Gợi ý tư duy

### Gợi ý 1

### Gợi ý 2

### Gợi ý 3

## Cấu trúc trả lời đề xuất

1. Chia dữ liệu theo ownership, sensitivity và freshness.
2. Làm rõ SLO, SEO, preview/publish workflow và traffic.
3. Vẽ request path browser → Akamai → origin → CMS/product API.
4. So sánh SSR/cacheable HTML, client API hydration và static generation.

7. Giải thích cost of complexity.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Tách cache policy cho public CMS HTML/blocks, static assets, personalized responses và product availability.
- Cache key phải xét locale, market, query parameters có ý nghĩa và authorization; không cache nhầm nội dung cá nhân ở shared CDN.
- Publish không đồng nghĩa mọi edge đã invalidated; xác định freshness SLA và kiểm chứng.
- Không purge toàn site theo mặc định; đánh giá targeted purge, TTL và versioned assets.

### Điểm cộng
- Có mapping content dependency: page A sử dụng block B, khi B publish cần invalidate các pages phụ thuộc.
- SEO: server-rendered metadata, canonical/hreflang phù hợp, sitemap và redirects.
- Phân biệt stale-while-revalidate với dữ liệu không được phép stale; có circuit breaker/fallback cho product API.

### Senior+
- Có event outbox/reconciliation cho publish invalidation nếu cần, nhưng không đưa queue chỉ để tăng kiến trúc.
- Xác định cache observability và thử nghiệm đa vùng; xử lý purge failure/partial propagation.
- Có lựa chọn đơn giản hơn khi traffic thấp hoặc CMS đã cung cấp invalidation phù hợp.

## Hướng giải quyết tham khảo

**Assumptions:** Marketing content public theo locale/market, availability là dữ liệu động từ đối tác và không có giá cá nhân trong shared HTML. Nếu giả định sai, phải thay đổi cache policy; không thể dùng cùng shared cache cho user-specific response.

**Phương án A — server-rendered CMS pages + targeted CDN caching:** ASP.NET Core render HTML/metadata từ Optimizely, Akamai cache public pages theo URL và biến thể locale/market được chuẩn hóa. Static assets dùng fingerprinted URLs và TTL dài. CMS publish hook xác định các page phụ thuộc content block và gọi purge theo URL hoặc cơ chế tag thực sự được Akamai contract hỗ trợ. Đặt TTL fallback để nội dung tự hết hạn nếu purge fail. Preview đi qua authenticated non-cache path; bảo vệ draft content. Ưu điểm: SEO rõ, vận hành đơn giản; nhược điểm: mapping dependencies, purge latency và origin load khi cold miss.

**Phương án B — CMS headless API + Vue rendering:** API cung cấp content model và frontend render; cần SSR/prerender nếu SEO và crawlability quan trọng. Có thể cache API theo content version/locale và hydrate availability riêng. Ưu điểm: frontend composability và reuse đa kênh; nhược điểm: thêm SSR deployment, cache layers và nguy cơ mismatch giữa HTML với hydration. Không chuyển headless chỉ vì đang dùng Vue ở một số trang.

**Availability:** dùng endpoint riêng với timeout ngắn, bulkhead và rate limiting; tùy yêu cầu có thể TTL rất ngắn hoặc không dùng shared cache. Nếu đối tác lỗi, hiển thị “tạm thời không xác định” thay vì khẳng định còn hàng; nếu được phép stale, hiển thị timestamp và quy tắc stale rõ ràng. Quyết định đặt hàng cuối cùng phải kiểm tra lại availability ở backend, không tin giá trị trình duyệt.

**Invalidation:** duy trì content ID → affected URL mapping; publish event mang content version, locale, affected URLs; deduplicate và retry có giới hạn khi purge API lỗi. Nếu yêu cầu độ bền cao, lưu publish event trong outbox và worker xử lý; nếu không, CMS hook có retry + periodic reconciliation có thể đủ. Với multi-region, đo time-to-freshness thực tế bằng synthetic probes; không giả định purge API accepted nghĩa là mọi edge đã cập nhật.

**Security & SEO:** xác minh cache key không bỏ qua market/locale; không đưa cookies/tokens vào shared cache; canonical URLs, localized hreflang, 301 redirects và server-visible metadata. Phân biệt `Cache-Control: private`, `no-store` và public cache theo sensitivity. CMS preview/draft phải bypass CDN public cache.

**Deployment/operations:** dùng feature flag cho policy mới, canary theo một nhóm URL, so sánh hit ratio, origin p95, publish-to-visible latency và SEO crawl behavior. Rollback policy không xóa nội dung đã publish. Nếu lượng traffic nhỏ, TTL ngắn và purge URL thủ công/đơn giản có thể an toàn hơn event-driven architecture phức tạp.

**Kiểm thử:** integration test publish block được dùng bởi nhiều pages; kiểm tra locale variants; test purge API 429/5xx và recovery; Playwright kiểm tra SSR metadata và availability degraded state; load test cold cache và stampede. **Observability:** Akamai cache status/hit ratio, origin RPS/p95, purge error rate, publish-to-visible lag, CMS event queue age nếu có, external API latency/failures và synthetic checks theo vùng.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn một cache policy cho toàn website. Trước hết tôi xác định content nào public, theo locale/market và freshness SLA; availability động phải tách khỏi marketing HTML. Với website SEO-heavy, tôi ưu tiên server-rendered CMS pages qua Akamai và targeted purge theo các URL phụ thuộc content block, kèm TTL fallback. Vue có thể hydrate availability qua API riêng; khi đối tác lỗi, UI phải hiển thị trạng thái không xác định thay vì dữ liệu chắc chắn sai. Tôi chỉ chuyển sang headless/SSR nếu có nhu cầu đa kênh đủ lớn để bù complexity. Tôi sẽ kiểm chứng cache key, preview isolation, publish-to-visible latency từ nhiều vùng và origin load sau purge. Nếu purge không đáng tin, thêm retry và reconciliation; queue/outbox chỉ khi reliability requirement thực sự cần. Thiết kế cuối cùng phụ thuộc SLA freshness và mức tải được đo.”

## Câu hỏi đào sâu

1. Nếu một content block được dùng trên 50.000 URLs, targeted purge có còn phù hợp không?
2. Nếu Product yêu cầu giá cá nhân hóa xuất hiện trong HTML có thể cache, bạn thiết kế lại boundary ra sao?
3. Nếu purge API trả success nhưng một edge vẫn stale, bạn chứng minh và khắc phục thế nào?

## Lỗi trả lời thường gặp

- Purge toàn bộ CDN sau mỗi publish mà không tính origin load.
- Cache availability và public CMS HTML với cùng TTL.
- Tin rằng purge accepted đồng nghĩa global consistency tức thì.
- Bỏ qua preview/draft isolation, locale và personalized content.
- Chuyển sang microservices/headless mặc định mà không định lượng lợi ích.

## Thang điểm 0–10

- 0–2: Chỉ đề xuất tăng TTL hoặc purge toàn site.
- 3–4: Tách static/dynamic nhưng thiếu freshness contract và security.
- 5–6: Có cache key, targeted invalidation, SEO và fallback.
- 7–8: So sánh kiến trúc, tests, observability, failure recovery và rollout.
- 9–10: Định lượng trade-offs, multi-region correctness, dependency graph và vận hành với complexity tối thiểu.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Memory pressure không đồng nghĩa memory leak: cần phân biệt allocation, reachable objects, GC, LOH và working set.
- Incident IIS phải tách symptom với root cause; khôi phục dịch vụ trước, xác minh bằng timeline đa nguồn và triển khai lại theo từng node.
- CMS/CDN consistency là một contract giữa publish, origin, edge và browser; dữ liệu có độ nhạy/freshness khác nhau cần cache ownership khác nhau.

## Mẫu tư duy cần nhớ

1. **Measure before optimize:** profile allocation và latency trước khi đổi thiết kế.
2. **Stabilize before root-cause investigation:** giảm blast radius rồi kiểm chứng nhiều giả thuyết.
3. **Define freshness and ownership:** xác định source of truth và độ trễ chấp nhận được.
4. **Test failure paths:** client disconnect, node recycle, purge failure và partner outage.
5. **Choose the simplest sufficient architecture:** thêm background jobs hoặc eventing chỉ khi requirement chứng minh cần.
