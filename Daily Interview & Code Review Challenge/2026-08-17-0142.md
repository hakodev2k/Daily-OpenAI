# Code Review Challenge 1 — Lost Update trong luồng cập nhật Billable Hours

**Chủ đề:** EF Core transaction handling, concurrency, correctness, performance  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Hệ thống timesheet cho phép người dùng chỉnh `ActualHours` và `BillableHours`. Business rule yêu cầu:

- `BillableHours <= ActualHours`.
- Không được ghi đè thay đổi mới hơn của người dùng khác.
- Một request có thể cập nhật nhiều entries.
- API chạy trên nhiều application instances sau load balancer.
- Peak traffic khoảng vài chục request cập nhật/giây, nhưng một số entries có thể bị nhiều user hoặc background job cập nhật gần cùng thời điểm.

Production thỉnh thoảng xuất hiện:

- `BillableHours` bị quay lại giá trị cũ.
- Validation đã pass nhưng dữ liệu cuối cùng lại vi phạm `BillableHours <= ActualHours`.
- Một số request mất 2–4 giây khi update khoảng 100 entries.
- Không có exception rõ ràng trong log.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class TimesheetService
{
    private readonly AppDbContext _db;

    public TimesheetService(AppDbContext db)
    {
        _db = db;
    }

    public async Task UpdateBillableHoursAsync(
        IReadOnlyCollection<UpdateBillableRequest> requests,
        CancellationToken cancellationToken)
    {
        foreach (var request in requests)
        {
            var entry = await _db.TimesheetEntries
                .FirstOrDefaultAsync(
                    x => x.Id == request.Id,
                    cancellationToken);

            if (entry == null)
                continue;

            if (request.BillableHours > entry.ActualHours)
                throw new InvalidOperationException("Billable hours cannot exceed actual hours.");

            entry.BillableHours = request.BillableHours;
            entry.BillableNote = request.BillableNote;

            await _db.SaveChangesAsync(cancellationToken);
        }
    }
}

public sealed record UpdateBillableRequest(
    long Id,
    decimal BillableHours,
    string? BillableNote);
```

## Kết quả code review tham khảo

### 1. Không có optimistic concurrency control

- **Problem:** Hai request có thể cùng đọc một `TimesheetEntry`, rồi request chạy sau ghi đè dữ liệu của request chạy trước.
- **Why it happens:** EF Core mặc định update dựa trên primary key. Nếu không cấu hình concurrency token như `rowversion`/version column, database không biết entity mà client đang sửa đã bị thay đổi.
- **Production impact:** Lost update, dữ liệu quay về giá trị cũ, khó phát hiện vì không nhất thiết có exception.
- **Severity:** Critical
- **Recommended fix:** Thêm concurrency token, ví dụ SQL Server `rowversion`, hoặc version column phù hợp với database; handle `DbUpdateConcurrencyException` và trả conflict rõ ràng.

### 2. Business invariant có thể bị phá vỡ do race condition

- **Problem:** Validation `request.BillableHours > entry.ActualHours` chỉ kiểm tra snapshot đã đọc.
- **Why it happens:** Sau khi đọc, request khác có thể giảm `ActualHours` trước khi request hiện tại commit.
- **Production impact:** Dữ liệu cuối cùng có thể có `BillableHours > ActualHours` dù từng request riêng lẻ đã pass validation.
- **Severity:** Critical
- **Recommended fix:** Bảo vệ invariant tại database boundary. Tùy thiết kế, dùng optimistic concurrency kết hợp re-validation sau conflict, transaction/isolation thích hợp, hoặc database constraint nếu invariant có thể biểu diễn trực tiếp.

### 3. `SaveChangesAsync` trong vòng lặp tạo nhiều round-trips

- **Problem:** Mỗi item thực hiện ít nhất một SELECT và một SAVE.
- **Why it happens:** Query + save được gọi tuần tự từng entry.
- **Production impact:** Latency tăng gần tuyến tính theo số item; transaction nhỏ rời rạc; throughput thấp hơn cần thiết.
- **Severity:** High
- **Recommended fix:** Load tất cả entries cần thiết bằng một query, validate toàn bộ, update tracked entities và gọi `SaveChangesAsync` một lần nếu business semantics cho phép.

### 4. Partial update khi request fail giữa chừng

- **Problem:** Nếu item thứ 51 fail sau khi 50 item trước đã save, request kết thúc lỗi nhưng database đã thay đổi một phần.
- **Why it happens:** Mỗi iteration commit riêng thông qua `SaveChangesAsync`.
- **Production impact:** Client không biết chính xác item nào đã áp dụng; retry có thể tạo state khó dự đoán.
- **Severity:** High
- **Recommended fix:** Xác định rõ semantics: all-or-nothing thì dùng một unit of work/transaction; partial success thì response phải trả kết quả từng item và operation phải idempotent.

### 5. Bỏ qua entry không tồn tại một cách im lặng

- **Problem:** `entry == null` thì `continue`.
- **Why it happens:** API không trả thông tin rằng ID không tồn tại hoặc user không có quyền thấy entry đó.
- **Production impact:** Client tưởng request thành công đầy đủ; debugging khó; có thể che giấu lỗi mapping dữ liệu.
- **Severity:** Medium
- **Recommended fix:** Quy định rõ behavior: reject toàn bộ, trả per-item not-found, hoặc validate IDs trước khi update.

### 6. Không có authorization/business ownership check trong service

- **Problem:** Code chỉ tìm theo `Id`.
- **Why it happens:** Không thấy tenant/user/project boundary được áp vào query.
- **Production impact:** Nếu controller/service phía trên validate thiếu, user có thể update entry ngoài phạm vi được phép.
- **Severity:** High
- **Recommended fix:** Scope query theo tenant/user/role/project authorization hoặc enforce policy trước khi mutate.

### 7. Duplicate IDs trong request có thể gây kết quả bất ngờ

- **Problem:** Cùng một `Id` có thể xuất hiện nhiều lần.
- **Why it happens:** Không normalize hoặc reject duplicate input.
- **Production impact:** Giá trị cuối phụ thuộc thứ tự request; tăng round-trips; khó audit.
- **Severity:** Medium
- **Recommended fix:** Reject duplicate IDs hoặc quy định deterministic merge behavior.

### 8. Thiếu validation cho `BillableHours` âm và note quá dài

- **Problem:** Chỉ validate upper bound với `ActualHours`.
- **Why it happens:** Không thấy lower bound, precision/scale, length constraints.
- **Production impact:** Invalid business data hoặc database exception.
- **Severity:** Medium
- **Recommended fix:** Validate request contract và có database constraints phù hợp.

### 9. Observability không đủ để điều tra lost update

- **Problem:** Không có operation ID/version/conflict log trong code path.
- **Why it happens:** Concurrency conflict hiện tại còn chưa được detect.
- **Production impact:** User báo dữ liệu quay lại giá trị cũ nhưng team khó reconstruct timeline.
- **Severity:** Medium
- **Recommended fix:** Log structured fields như `EntryId`, old/new version, actor, correlation ID, conflict count; audit business-critical changes nếu cần.

## Phiên bản code đề xuất

Giả sử SQL Server và entity có `RowVersion`:

```csharp
public sealed class TimesheetEntry
{
    public long Id { get; set; }
    public decimal ActualHours { get; set; }
    public decimal BillableHours { get; set; }
    public string? BillableNote { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}

public sealed record UpdateBillableRequest(
    long Id,
    decimal BillableHours,
    string? BillableNote,
    byte[] RowVersion);

public async Task UpdateBillableHoursAsync(
    IReadOnlyCollection<UpdateBillableRequest> requests,
    CancellationToken cancellationToken)
{
    if (requests.Count == 0)
        return;

    if (requests.GroupBy(x => x.Id).Any(g => g.Count() > 1))
        throw new ValidationException("Duplicate timesheet entry IDs are not allowed.");

    var ids = requests.Select(x => x.Id).ToArray();

    var entries = await _db.TimesheetEntries
        .Where(x => ids.Contains(x.Id))
        .ToDictionaryAsync(x => x.Id, cancellationToken);

    if (entries.Count != ids.Length)
        throw new KeyNotFoundException("One or more timesheet entries were not found.");

    foreach (var request in requests)
    {
        var entry = entries[request.Id];

        if (request.BillableHours < 0)
            throw new ValidationException("Billable hours cannot be negative.");

        if (request.BillableHours > entry.ActualHours)
            throw new ValidationException("Billable hours cannot exceed actual hours.");

        _db.Entry(entry)
            .Property(x => x.RowVersion)
            .OriginalValue = request.RowVersion;

        entry.BillableHours = request.BillableHours;
        entry.BillableNote = request.BillableNote?.Trim();
    }

    try
    {
        await _db.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateConcurrencyException ex)
    {
        throw new TimesheetConflictException(
            "One or more timesheet entries were changed by another operation. Reload and retry.",
            ex);
    }
}
```

### Ghi chú kiến trúc

- `RowVersion` giúp detect stale write, không tự merge conflict.
- Khi conflict, client thường cần reload state và quyết định retry/merge.
- Nếu business invariant cần bảo đảm ngay cả khi hai thuộc tính được update bởi các flow khác nhau, database constraint hoặc transaction/isolation phù hợp có thể cần thiết.
- Với PostgreSQL có thể dùng concurrency token/version column phù hợp thay vì SQL Server `rowversion`.

## Trade-offs

- **Optimistic concurrency** phù hợp khi conflict không quá thường xuyên và tránh giữ lock lâu.
- **Pessimistic locking** có thể đơn giản hóa một số workflow có contention cao nhưng tăng blocking/deadlock risk và làm giảm throughput.
- **Single transaction cho cả batch** đảm bảo all-or-nothing nhưng transaction lớn hơn có thể giữ lock lâu hơn.
- **Partial-success API** phù hợp cho batch rất lớn nhưng contract, retry và idempotency phức tạp hơn.

## Cách kiểm thử

1. **Concurrency test:** hai request đọc cùng version, request A save trước, request B phải nhận conflict thay vì silently overwrite.
2. **Invariant test:** một request giảm `ActualHours` đồng thời request khác tăng `BillableHours`; state cuối không được vi phạm rule.
3. **Batch atomicity test:** một item invalid trong batch; xác minh không item nào được commit nếu contract là all-or-nothing.
4. **Load test:** update batch 100 entries và so số SQL round-trips, P95/P99 trước/sau.
5. **Authorization/database test:** user không được phép update entry ngoài tenant/project scope.

## Quan sát trong production

- **Logs:** correlation ID, actor ID, entry IDs, row version conflicts, validation failures.
- **Metrics:** `timesheet_update_conflicts_total`, batch size, DB duration, update latency P95/P99.
- **Traces:** span cho database query và `SaveChanges`.
- **Alerts:** conflict rate tăng đột biến hoặc update latency vượt SLO.
- **Database observations:** blocking/deadlock, execution count, write duration, constraint violations.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn pessimistic locking thay vì optimistic concurrency cho case này?
2. Nếu batch gồm 5.000 entries, bạn có còn load và save tất cả trong một transaction không?
3. Nếu `ActualHours` và `BillableHours` được cập nhật bởi hai service khác nhau, bạn đặt invariant ở đâu?

Một ASP.NET Core API nội bộ cho phép HR tra cứu thông tin mailbox/offboarding. API xác thực bằng JWT bearer token. Endpoint gọi Microsoft Graph để lấy thông tin user rồi trả dữ liệu tổng hợp cho frontend.

Team nói rằng endpoint “đã an toàn vì có `[Authorize]`”. Production security review phát hiện một vài user bình thường có thể lấy thông tin của employee khác nếu biết email. Ngoài ra log aggregator đang chứa access token và một số dữ liệu nhạy cảm.

Code hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/mailbox")]
[Authorize]
public sealed class MailboxController : ControllerBase
{
    private readonly IHttpClientFactory _httpClientFactory;
    private readonly ILogger<MailboxController> _logger;

    public MailboxController(
        IHttpClientFactory httpClientFactory,
        ILogger<MailboxController> logger)
    {
        _httpClientFactory = httpClientFactory;
        _logger = logger;
    }

    [HttpGet("user")]
    public async Task<IActionResult> GetUser(
        [FromQuery] string email,
        CancellationToken cancellationToken)
    {
        var token = Request.Headers.Authorization.ToString();

        _logger.LogInformation(
            "Mailbox lookup email={Email}, token={Token}",
            email,
            token);

        var client = _httpClientFactory.CreateClient();
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", token.Replace("Bearer ", ""));

        var response = await client.GetAsync(
            $"https://graph.microsoft.com/v1.0/users/{email}?$select=id,displayName,mail,mobilePhone,jobTitle,officeLocation",
            cancellationToken);

        var body = await response.Content.ReadAsStringAsync(cancellationToken);

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogError(
                "Graph failed status={Status}, body={Body}",
                response.StatusCode,
                body);

            return StatusCode((int)response.StatusCode, body);
        }

        return Content(body, "application/json");
    }
}
```

## Kết quả code review tham khảo

### 1. Chỉ authentication, không có resource-level authorization

- **Problem:** Bất kỳ authenticated user nào cũng có thể truyền email bất kỳ.
- **Why it happens:** `[Authorize]` chỉ yêu cầu principal đã authenticated theo policy mặc định; code không kiểm tra role/claim/business scope cho target employee.
- **Production impact:** Horizontal privilege escalation / IDOR-like data exposure.
- **Severity:** Critical
- **Recommended fix:** Áp policy/role/permission phù hợp và resource-based authorization nếu quyền phụ thuộc employee/tenant/department.

### 2. Log access token

- **Problem:** Header Authorization được ghi vào log.
- **Why it happens:** Structured logging đang capture toàn token.
- **Production impact:** Người có quyền đọc log có thể lấy bearer credential còn hiệu lực; incident scope mở rộng sang logging system.
- **Severity:** Critical
- **Recommended fix:** Không log bearer tokens. Redact Authorization header ở middleware/logging pipeline và code review rules.

### 3. Forward caller token sang Microsoft Graph mà không kiểm tra token audience/scope/flow

- **Problem:** API lấy inbound token rồi dùng trực tiếp gọi Graph.
- **Why it happens:** Code giả định token cấp cho API cũng phù hợp làm Graph token.
- **Production impact:** Call có thể fail hoặc security model bị hiểu sai; token audience/scope có thể không phù hợp. Với delegated access, backend thường cần flow được thiết kế đúng, ví dụ on-behalf-of khi phù hợp với architecture.
- **Severity:** High
- **Recommended fix:** Xác định rõ auth architecture. API không nên coi mọi inbound bearer token là downstream token hợp lệ.

### 4. Trả nguyên Microsoft Graph error body cho caller

- **Problem:** `return StatusCode(..., body)` passthrough error response.
- **Why it happens:** Không có error normalization.
- **Production impact:** Có thể lộ request IDs, internal details hoặc dữ liệu không cần thiết; frontend phụ thuộc chặt vào downstream contract.
- **Severity:** High
- **Recommended fix:** Map lỗi sang application error contract; log sanitized diagnostics server-side.

### 5. Log nguyên downstream error body

- **Problem:** `body` có thể chứa identifiers hoặc data nhạy cảm.
- **Why it happens:** Logging full payload khi lỗi.
- **Production impact:** PII/sensitive metadata tồn tại lâu trong centralized logging.
- **Severity:** High
- **Recommended fix:** Log status, request/correlation ID, error code đã sanitize; không log full body mặc định.

### 6. User input được ghép trực tiếp vào URL path

- **Problem:** `email` được string interpolation trực tiếp vào URI.
- **Why it happens:** Không URL-encode path segment.
- **Production impact:** Request malformed hoặc semantic path bị thay đổi với input đặc biệt.
- **Severity:** Medium
- **Recommended fix:** `Uri.EscapeDataString(email)` hoặc API client abstraction xây URL an toàn.

### 7. Không validate input

- **Problem:** Không kiểm tra empty/format/length của `email`.
- **Why it happens:** Controller nhận string và dùng ngay.
- **Production impact:** Request lỗi không cần thiết, log noise, downstream load.
- **Severity:** Medium
- **Recommended fix:** Validate request contract trước khi gọi dependency.

### 8. Data minimization chưa rõ

- **Problem:** Endpoint trả cả `mobilePhone`, `officeLocation`, `jobTitle` mà chưa chứng minh caller cần tất cả field.
- **Why it happens:** API proxy gần như nguyên dữ liệu Graph.
- **Production impact:** Tăng phạm vi PII exposure.
- **Severity:** High
- **Recommended fix:** Trả DTO tối thiểu theo use case và authorization level.

### 9. Không có explicit timeout/resilience policy cho downstream client

- **Problem:** `CreateClient()` dùng unnamed client, config không thể hiện timeout/resilience policy của Graph integration.
- **Why it happens:** Integration boundary chưa được encapsulate.
- **Production impact:** Dependency chậm có thể kéo dài request, tăng resource usage và gây cascading latency.
- **Severity:** Medium
- **Recommended fix:** Typed/named client với timeout, retry policy phù hợp operation, telemetry và rate-limit handling.

### 10. API làm proxy thô thay vì domain boundary

- **Problem:** Controller biết URL Graph, auth header, raw JSON và raw error.
- **Why it happens:** Thiếu application/integration service boundary.
- **Production impact:** Khó test policy, khó đổi auth flow, dễ lặp security bugs.
- **Severity:** Medium
- **Recommended fix:** Tách `IGraphUserService`/integration client và application authorization layer.

## Phiên bản code đề xuất

Ví dụ hướng cải thiện, giả định caller phải có policy `Mailbox.Read` và downstream token được cấp bởi một token provider chuyên trách:

```csharp
[ApiController]
[Route("api/mailbox")]
[Authorize(Policy = "Mailbox.Read")]
public sealed class MailboxController : ControllerBase
{
    private readonly IGraphUserService _graphUserService;
    private readonly IAuthorizationService _authorizationService;

    public MailboxController(
        IGraphUserService graphUserService,
        IAuthorizationService authorizationService)
    {
        _graphUserService = graphUserService;
        _authorizationService = authorizationService;
    }

    [HttpGet("user")]
    public async Task<ActionResult<MailboxUserDto>> GetUser(
        [FromQuery] string email,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(email) || email.Length > 320)
            return BadRequest(new { code = "invalid_email" });

        var authorization = await _authorizationService.AuthorizeAsync(
            User,
            email,
            "MailboxUser.Read");

        if (!authorization.Succeeded)
            return Forbid();

        var user = await _graphUserService.GetUserAsync(
            email,
            cancellationToken);

        if (user is null)
            return NotFound();

        return Ok(new MailboxUserDto(
            user.Id,
            user.DisplayName,
            user.Mail,
            user.JobTitle));
    }
}
```

```csharp
public sealed class GraphUserService
{
    private readonly HttpClient _httpClient;
    private readonly IGraphTokenProvider _tokenProvider;
    private readonly ILogger<GraphUserService> _logger;

    public GraphUserService(
        HttpClient httpClient,
        IGraphTokenProvider tokenProvider,
        ILogger<GraphUserService> logger)
    {
        _httpClient = httpClient;
        _tokenProvider = tokenProvider;
        _logger = logger;
    }

    public async Task<GraphUser?> GetUserAsync(
        string email,
        CancellationToken cancellationToken)
    {
        var accessToken = await _tokenProvider.GetTokenAsync(cancellationToken);
        var encodedEmail = Uri.EscapeDataString(email);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"v1.0/users/{encodedEmail}?$select=id,displayName,mail,jobTitle");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogWarning(
                "Graph user lookup failed. StatusCode={StatusCode}",
                (int)response.StatusCode);

            throw new GraphDependencyException("Graph lookup failed.");
        }

        return await response.Content.ReadFromJsonAsync<GraphUser>(
            cancellationToken: cancellationToken);
    }
}
```

### Lưu ý xác thực

Cách lấy downstream Graph token phải phù hợp với architecture thực tế. Không nên suy luận rằng inbound token có thể luôn forward trực tiếp. Cần kiểm tra audience, delegated/application permission model và flow do identity platform hỗ trợ cho scenario của hệ thống.

## Trade-offs

- **Resource-based authorization** chính xác hơn role-only nhưng cần thêm domain lookup/policy logic.
- **Data minimization** giảm exposure nhưng có thể yêu cầu nhiều DTO/use-case endpoints hơn.
- **On-behalf-of/delegated flow** giữ user context nhưng phức tạp hơn service-level app permission.
- **Application permission** đơn giản cho daemon/background flow nhưng blast radius lớn hơn và cần governance chặt.
- **Detailed logs** hữu ích cho debugging nhưng phải cân bằng với secret/PII minimization.

## Cách kiểm thử

1. **Authorization test:** authenticated user không có quyền đọc employee khác phải nhận `403`.
2. **Security log test:** xác minh access token không xuất hiện trong application log, HTTP log hoặc exception telemetry.
3. **Input test:** email chứa ký tự cần encode không làm thay đổi request path ngoài ý muốn.
4. **Failure-path test:** Graph trả `401/403/429/500`; API không passthrough raw body và vẫn trả contract an toàn.
5. **Data minimization test:** response không chứa `mobilePhone`/field nhạy cảm nếu use case không cho phép.

## Quan sát trong production

- **Logs:** caller ID đã normalize, operation name, authorization result, downstream status code; tuyệt đối không log bearer token.
- **Metrics:** authorization denials, Graph latency/error rate, rate-limit responses, request volume.
- **Traces:** API span → authorization span → Graph dependency span, correlation/request ID.
- **Alerts:** tăng đột biến `403`, Graph `401/403`, hoặc downstream `429/5xx`.
- **Security observations:** secret scanning/log review để phát hiện Authorization header vô tình bị capture.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn dùng policy-based authorization và khi nào cần resource-based authorization?
2. Nếu backend cần hành động thay mặt user trên Microsoft Graph, bạn thiết kế token flow như thế nào?
3. Nếu security team yêu cầu audit ai đã xem dữ liệu employee nào nhưng đồng thời hạn chế PII trong log, bạn cân bằng hai yêu cầu đó ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- EF Core tracking không tự cung cấp optimistic concurrency; nếu cần phát hiện stale writes phải có concurrency token hoặc mechanism tương đương.
- Business invariant cần được bảo vệ ở thời điểm commit, không chỉ validate trên snapshot đã đọc.
- Batch update cần thiết kế rõ semantics: all-or-nothing hay partial success.
- Authentication không đồng nghĩa authorization; resource-level access phải được kiểm tra riêng.
- Bearer token là secret và không được log.
- API integration nên tránh passthrough raw downstream data/errors nếu không cần thiết.
- Data minimization và least privilege là một phần của application design, không chỉ security checklist.

## Mẫu tư duy cần nhớ

1. **Validate at the right boundary** — validation trước commit có thể stale dưới concurrency.
2. **Detect stale writes explicitly** — đừng kỳ vọng ORM tự ngăn lost update.
3. **Authentication answers “who”; authorization answers “may they do this?”**
4. **Never log credentials** — observability không được biến thành secret leakage.
5. **Minimize trust and data exposure across boundaries** — caller, API, downstream và logging system đều là trust boundaries riêng.
