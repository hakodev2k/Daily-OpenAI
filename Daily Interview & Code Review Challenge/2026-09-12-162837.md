# Câu 1 — `AddDbContextPool` giúp giảm allocation, nhưng vì sao lại có nguy cơ mang state của tenant A sang request tenant B?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** C#/.NET 8, ASP.NET Core DI, EF Core, `DbContext` pooling, change tracking, global query filters, multi-tenancy, lifetime/state management, performance measurement, security

## Bối cảnh

Một SaaS nội bộ dùng ASP.NET Core + EF Core + SQL Server. Mọi bảng business đều có `TenantId`. Team dùng global query filter để developer không phải nhớ thêm `.Where(x => x.TenantId == ...)` ở từng query.

Trước đây cấu hình:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Sau khi profiling cho thấy nhiều allocation liên quan việc tạo `DbContext`, một developer đổi sang:

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString), poolSize: 128);
```

`TenantContext` được đăng ký scoped:

```csharp
builder.Services.AddScoped<TenantContext>();
```

`AppDbContext` hiện tại:

```csharp
public sealed class AppDbContext : DbContext
{
    private readonly TenantContext _tenant;

    public AppDbContext(
        DbContextOptions<AppDbContext> options,
        TenantContext tenant)
        : base(options)
    {
        _tenant = tenant;
    }

    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == _tenant.TenantId);
    }
}
```

Middleware resolve tenant từ authenticated user và set:

```csharp
public async Task InvokeAsync(HttpContext httpContext, TenantContext tenant)
{
    tenant.TenantId = ResolveTenant(httpContext.User);
    await _next(httpContext);
}
```

Sau rollout, performance benchmark synthetic tốt hơn một chút. Tuy nhiên security test trong staging đôi lúc phát hiện request của tenant B trả về dữ liệu tenant A khi chạy test concurrency cao. Team chưa reproduce ổn định ở local.

Một developer nói:

> “`DbContext` vẫn được inject như scoped nên mỗi request chắc chắn có instance riêng. Pool chỉ tối ưu object allocation bên dưới, không thể ảnh hưởng tenant state.”

Một developer khác đề xuất bỏ global query filter và truyền `TenantId` thủ công vào mọi repository method.

## Câu hỏi chính

Hãy giải thích `DbContext` pooling thực sự thay đổi lifecycle nào, state nào EF Core reset được khi context được trả về pool, state nào do application tự thêm có thể không được reset theo cách team tưởng, tại sao pattern inject scoped tenant state vào pooled context là nguy hiểm, và bạn sẽ thiết kế multi-tenant `DbContext` an toàn thế nào mà vẫn giữ được lợi ích pooling nếu benchmark thực sự chứng minh nó đáng giá.

## Câu hỏi làm rõ nên cân nhắc

1. `TenantContext` được đọc ở constructor, query time hay thông qua một property mutable trên context?
2. Có `IDbContextFactory<TContext>` hoặc background workers nào cũng tạo context ngoài HTTP request không?
3. Pooling mang lại bao nhiêu lợi ích thực tế ở p95/p99, allocation/request và CPU sau khi đo với workload production-like?
4. Có raw SQL, `IgnoreQueryFilters()`, stored procedures hoặc direct connection access nào bypass tenant isolation không?
5. Tenant isolation chỉ là convenience filter hay là một security boundary bắt buộc phải có defense-in-depth ở database/application level?

## Gợi ý tư duy

### Gợi ý 1

Một pooled `DbContext` không bị dispose rồi biến mất theo nghĩa object lifetime thông thường; instance có thể được reset và **reuse cho request khác**.

### Gợi ý 2

EF Core biết cách reset state mà EF quản lý như change tracker. Nhưng EF không thể tự đoán semantics của mọi mutable field/property/service reference do application thêm vào context.

### Gợi ý 3

Global query filter chỉ an toàn nếu giá trị tenant mà expression đọc đúng cho **mỗi unit of work**. Hãy nghĩ xem tenant state được bind ở thời điểm nào và pooled instance sống qua bao nhiêu request.

## Cấu trúc trả lời đề xuất

1. Giải thích normal scoped `DbContext` lifecycle và pooled lifecycle.
2. Phân biệt EF-managed state với application-managed state.
3. Phân tích vì sao scoped dependency/tenant field có thể trở thành cross-request state trong pooled context.
4. Xác định security impact và các đường bypass khác của query filter.
5. Đề xuất safe construction/factory pattern hoặc bỏ pooling nếu complexity không đáng.
6. Nêu test strategy để chứng minh không leak tenant dưới concurrency.
7. Nêu telemetry/benchmark cần có trước và sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu pooled context instance có thể được tái sử dụng qua nhiều request.
- Không đồng nhất “service resolve như scoped” với “object chắc chắn được tạo mới cho request” khi dùng context pooling.
- Nhận ra application-owned tenant state là phần nguy hiểm nếu được giữ trên pooled context.
- Không coi global query filter là security mechanism duy nhất nếu có đường bypass như raw SQL/`IgnoreQueryFilters()`.
- Đề xuất cách gán tenant state per unit-of-work một cách explicit và reset-safe, hoặc không dùng pooling.
- Có concurrency/security tests giữa nhiều tenant, không chỉ unit test một tenant.

### Điểm cộng

- Phân biệt model caching/query-filter expression với runtime parameter/state.
- Biết context pooling và database connection pooling là hai cơ chế khác nhau.
- Nhận ra pooled context vẫn không thread-safe; pooling không cho phép dùng một context đồng thời ở nhiều tasks.
- Benchmark pooling dựa trên representative DB latency; nếu query I/O chiếm phần lớn latency thì lợi ích tạo context có thể rất nhỏ.
- Có database-side defense như row-level security khi threat model/requirements biện minh.

### Senior+

- Thiết kế tenant-aware factory/wrapper đảm bảo context được checkout, gán tenant state đúng một lần cho unit-of-work và không để stale state tồn tại khi return pool.
- Tách isolation correctness khỏi performance optimization: trước hết prove isolation, sau đó mới giữ pooling nếu có measurable gain.
- Có property-based/concurrency test tạo hàng nghìn interleaved requests với tenant IDs khác nhau và fail ngay nếu cross-tenant row xuất hiện.
- Đề cập observability/audit cho tenant mismatch mà không log sensitive business data.

## Hướng giải quyết tham khảo

Điểm quan trọng nhất là `AddDbContextPool` thay đổi mental model về lifetime. Với `AddDbContext`, một scoped `DbContext` thường được tạo trong request scope rồi dispose. Với pooling, một context instance có thể được checkout từ pool, dùng cho một scope, reset phần state EF Core quản lý, rồi trả lại pool để scope khác dùng lại.

Pooling không phải database connection pooling. SQL client vẫn có connection pooling riêng. `DbContext` pooling chủ yếu giảm setup/allocation của context và một số internal services. Vì vậy trước khi chấp nhận complexity, cần benchmark workload thật: nếu mỗi request chủ yếu chờ SQL 30–100 ms thì tiết kiệm vài allocation khi tạo context có thể không đáng so với risk.

Vấn đề của đoạn code là context giữ reference tới `TenantContext` như application state. Với pooled context, không nên giả định scoped dependency semantics hoạt động như một context mới được construct cho mỗi request. Pooled instance được tạo ít lần rồi reuse; state gắn vào instance có thể không được refresh theo request theo cách developer tưởng.

Một safer direction là context expose tenant identifier cho query filter nhưng tenant value phải được set một cách explicit cho mỗi checkout/unit-of-work thông qua một factory/wrapper có lifecycle rõ. Ví dụ conceptual design:

```csharp
public sealed class AppDbContext : DbContext
{
    public int TenantId { get; internal set; }

    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options) { }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == TenantId);
    }
}
```

Sau đó dùng pooled factory và một scoped tenant-aware factory:

```csharp
builder.Services.AddPooledDbContextFactory<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

builder.Services.AddScoped<TenantDbContextFactory>();

public sealed class TenantDbContextFactory
{
    private readonly IDbContextFactory<AppDbContext> _factory;
    private readonly TenantContext _tenant;

    public TenantDbContextFactory(
        IDbContextFactory<AppDbContext> factory,
        TenantContext tenant)
    {
        _factory = factory;
        _tenant = tenant;
    }

    public async Task<AppDbContext> CreateAsync(CancellationToken ct)
    {
        var db = await _factory.CreateDbContextAsync(ct);
        db.TenantId = _tenant.TenantId;
        return db;
    }
}
```

Pattern cụ thể phải bám theo version/documentation đang dùng và phải bảo đảm tenant state không thể bị bỏ quên. Nếu custom state cần reset khi return pool, design phải có invariant rõ; nếu team không thể bảo đảm invariant đơn giản, lựa chọn an toàn hơn là bỏ context pooling. Không nên hy sinh tenant isolation để tiết kiệm một optimization chưa chứng minh business value.

Global query filter cũng không phải magic security sandbox. `IgnoreQueryFilters()`, raw SQL hoặc code paths khác có thể bypass. Với highly sensitive multi-tenant data, tôi sẽ xem tenant authorization ở API/service boundary, integration tests cho repository, code review rules/analyzers nếu hữu ích, và cân nhắc SQL Row-Level Security nếu cần defense-in-depth. Nhưng RLS cũng có operational complexity; không thêm chỉ vì “best practice”.

Testing phải tập trung vào concurrency và reuse. Tôi sẽ tạo integration test với pool nhỏ, ví dụ 1–2 contexts, rồi chạy interleaved operations tenant A/B/C hàng nghìn lần để ép reuse mạnh. Mỗi result phải assert tất cả rows có expected tenant. Thêm tests cho exception/cancellation path vì stale state thường lộ ra khi lifecycle không đi happy path. Test cả `IgnoreQueryFilters`, raw SQL và background processing theo policy.

Cuối cùng benchmark với và không pooling: requests/sec, allocation/request, CPU, p95/p99 và DB time. Nếu gain chỉ rất nhỏ, bỏ optimization là một quyết định Senior hợp lý.

## Mẫu trả lời trong phỏng vấn

“Điểm nguy hiểm là `AddDbContextPool` làm context instance được reuse qua nhiều scopes. Scoped injection ở call site không có nghĩa pooled context object chắc chắn được construct lại mỗi request. EF Core reset state mà nó sở hữu như change tracker, nhưng application field/reference như tenant state không tự nhiên trở thành request-specific chỉ vì chúng ta muốn như vậy.

Tôi sẽ không inject scoped `TenantContext` vào pooled context rồi giữ reference như code hiện tại. Nếu pooling thật sự có measurable value, tôi dùng pooled factory và một scoped tenant-aware factory để checkout context rồi set tenant ID explicit cho unit-of-work. Query filter đọc property đó. Invariant phải là không context nào được query trước khi tenant được set đúng.

Tôi cũng không coi global query filter là defense duy nhất. Raw SQL hay `IgnoreQueryFilters()` có thể bypass, nên authorization, repository tests và nếu sensitivity đủ cao thì database-side isolation cần được cân nhắc.

Trước rollout tôi dùng pool rất nhỏ để ép reuse và chạy concurrent integration tests với nhiều tenants, bao gồm exception/cancellation paths. Sau đó benchmark pooling thực tế. Nếu chúng ta chỉ tiết kiệm rất ít latency nhưng tăng security complexity đáng kể, tôi sẽ bỏ pooling.”

## Câu hỏi đào sâu

1. Nếu tôi nói EF Core đã reset change tracker khi trả context về pool nên tenant state chắc chắn cũng được reset, bạn phản biện thế nào?
2. Nếu system có 10,000 tenants nhưng chỉ 50 concurrent active tenants, bạn có tạo model riêng theo tenant không? Vì sao?
3. Nếu raw SQL là bắt buộc cho một report lớn, bạn giữ tenant isolation bằng cách nào và test failure mode ra sao?

## Lỗi trả lời thường gặp

- Nhầm `DbContext` pooling với SQL connection pooling.
- Cho rằng DI scope guarantee pooled context object mới mỗi request.
- Chỉ sửa bằng “nhớ set TenantId” nhưng không tạo invariant/factory để enforce.
- Xem global query filter như security boundary tuyệt đối.
- Giữ optimization dù benchmark không cho thấy lợi ích đáng kể.

## Thang điểm 0–10

- **0–2:** Không hiểu pooling/reuse hoặc cho rằng scoped luôn đồng nghĩa object mới.
- **3–4:** Nhận ra stale state nhưng chưa đưa được safe lifecycle/test strategy.
- **5–6:** Có factory/per-request tenant state, test concurrency và hiểu query-filter limits.
- **7–8:** Phân biệt rõ EF state/application state, pooling/connection pooling, có benchmark và defense-in-depth.
- **9–10:** Thiết kế isolation invariant chặt, prove bằng concurrency/failure tests, cân bằng security với measurable performance gain và biết khi nào bỏ optimization.

# Câu 2 — Promotion traffic làm SQL deadlock tăng 50×: retry có chữa được root cause không?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** SQL Server, transactions, locking, deadlocks, EF Core, isolation levels, indexing, retry semantics, production diagnostics, observability, incident response

## Bối cảnh

Một Orders API trên ASP.NET Core + EF Core + SQL Server xử lý đặt hàng. Khi promotion bình thường, khoảng 60 orders/second. Trong flash sale, traffic tăng 6–8 lần.

Hai code path chính cùng update dữ liệu:

**Checkout path:**

```csharp
public async Task PlaceOrderAsync(
    Guid orderId,
    int productId,
    int quantity,
    CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var order = await _db.Orders
        .SingleAsync(x => x.Id == orderId, ct);

    order.Status = OrderStatus.Confirmed;
    await _db.SaveChangesAsync(ct);

    var inventory = await _db.Inventory
        .SingleAsync(x => x.ProductId == productId, ct);

    if (inventory.Available < quantity)
        throw new OutOfStockException();

    inventory.Available -= quantity;
    await _db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
}
```

**Inventory reconciliation job:**

```csharp
public async Task ReconcileAsync(
    int productId,
    IReadOnlyList<Guid> affectedOrderIds,
    CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var inventory = await _db.Inventory
        .SingleAsync(x => x.ProductId == productId, ct);

    inventory.LastReconciledAt = DateTimeOffset.UtcNow;
    await _db.SaveChangesAsync(ct);

    var orders = await _db.Orders
        .Where(x => affectedOrderIds.Contains(x.Id))
        .ToListAsync(ct);

    foreach (var order in orders)
        order.InventoryChecked = true;

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Trong incident:

- SQL Server CPU khoảng 65–75%, chưa chạm 100%;
- application error rate tăng vì SQL error `1205` deadlock victim;
- deadlocks tăng mạnh trên vài hot products;
- p99 checkout từ 700 ms lên 6 giây;
- team bật retry 5 lần cho mọi transaction và error rate giảm trong vài phút đầu nhưng DB load sau đó tăng thêm;
- một developer muốn chuyển toàn database sang `READ UNCOMMITTED` để “không lock nữa”;
- một developer khác muốn dùng `SERIALIZABLE` để “đảm bảo correctness tuyệt đối”;
- chưa ai đọc deadlock graph; mọi người chỉ xem exception count trong Application Insights.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào từ stabilization đến root-cause analysis? Hãy giải thích deadlock khác lock timeout/blocking ra sao, vì sao hai transaction trên có khả năng tạo circular wait, vì sao retry có thể là safety mechanism nhưng không phải root-cause fix, và bạn sẽ dùng deadlock graph/query plan/index/transaction design để giảm cả deadlock probability lẫn business-risk.

## Câu hỏi làm rõ nên cân nhắc

1. Deadlock graph cho thấy exact resources, indexes, lock modes và statements nào tham gia?
2. `Orders.Id` và `Inventory.ProductId` có unique/selective indexes phù hợp không?
3. Reconciliation có cần chạy đồng thời với flash-sale traffic hay có thể throttle/schedule?
4. Transaction business invariant thực sự là gì: order confirmed và inventory decrement phải atomic ở mức nào?
5. Có trigger, FK cascade, stored procedure hoặc secondary indexes nào tạo thêm lock resources không nhìn thấy trong snippet?

## Gợi ý tư duy

### Gợi ý 1

Checkout lock `Orders` trước rồi `Inventory`; reconciliation lock `Inventory` trước rồi `Orders`. Hai concurrent transactions có thể mỗi bên giữ resource bên kia cần.

### Gợi ý 2

Deadlock không có nghĩa database “thiếu CPU”. Nó là cycle trong wait-for graph; SQL Server chọn một victim để phá cycle.

### Gợi ý 3

Retry giảm user-visible failures nếu operation retry-safe, nhưng nhiều retries không jitter/backoff trong hot contention có thể tăng competing transactions và làm deadlock frequency cao hơn.

## Cấu trúc trả lời đề xuất

1. Stabilize traffic/background load và bound retries.
2. Thu deadlock graphs thay vì suy đoán từ error `1205`.
3. Xác định lock acquisition order/resources/index access.
4. Kiểm tra transaction duration và unnecessary work trong transaction.
5. Đề xuất consistent lock order/query/index changes.
6. Xác minh correctness/isolation requirements trước khi đổi isolation level.
7. Thiết kế retry policy chỉ cho deadlock victim và retry-safe operation.
8. Load/failure test và production telemetry sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Biết deadlock là circular wait và SQL Server chọn victim; khác với đơn thuần blocking dài.
- Nhìn ra lock ordering ngược nhau giữa hai code paths.
- Không chọn `READ UNCOMMITTED` hay `SERIALIZABLE` một cách reflex.
- Thu deadlock graph/Extended Events để xác định resources/statements thật.
- Rút ngắn transaction và dùng consistent resource ordering khi khả thi.
- Retry deadlock có bounded attempts + jitter/backoff và operation phải safe để retry.
- Kiểm tra indexes/query plans vì scan/range locks có thể mở rộng lock footprint.

### Điểm cộng

- Phân biệt optimistic row-versioning options như RCSI/Snapshot với việc “không có locks”; hiểu write-write conflicts/locks vẫn tồn tại.
- Đề cập transaction-level idempotency/business side effects ngoài database trước retry.
- Throttle reconciliation trên hot products hoặc tách scheduling khỏi checkout critical path.
- Dùng deterministic order khi update nhiều rows để giảm lock-order variation.
- Có metric deadlocks per transaction, victim endpoint/job và retry amplification.

### Senior+

- Đọc deadlock XML/graph để xác định owner/waiter, lock mode, index/key/hash và victim selection thay vì tối ưu theo code snippet giả định.
- Phân biệt correctness invariant với isolation-level folklore.
- Cân nhắc atomic SQL update cho inventory (`UPDATE ... WHERE Available >= @quantity`) để giảm read-modify-write window nếu domain phù hợp.
- Kiểm tra side effects như message/email nằm trong retry boundary để tránh duplicate external effects.
- Định nghĩa SLO/rollback criteria sau rollout thay đổi transaction/index.

## Hướng giải quyết tham khảo

Incident response nên bắt đầu bằng giảm amplification. Nếu reconciliation không time-critical, tôi có thể throttle/pause nó cho hot products trong flash sale để giảm contention. Đồng thời giảm retry policy từ “retry mọi thứ 5 lần” thành bounded retry chỉ cho known transient/deadlock errors với jitter và deadline. Đây là mitigation, chưa phải root-cause fix.

Sau đó lấy deadlock evidence. SQL Server Extended Events/system health thường có deadlock XML. Tôi muốn biết process A/B đang chạy statement nào, giữ lock nào, chờ lock nào, trên index/key nào. Chỉ nhìn error `1205` không đủ, vì trigger/index scan hoặc FK có thể tạo resource khác với mental model từ application code.

Snippet đã cho một hypothesis mạnh:

- Checkout: update `Orders` rồi update `Inventory`.
- Reconcile: update `Inventory` rồi update `Orders`.

Một interleaving đơn giản:

1. T1 giữ X lock trên order O1.
2. T2 giữ X lock trên inventory P1.
3. T1 chờ inventory P1.
4. T2 chờ order O1.
5. Cycle hình thành; SQL chọn một victim.

Primary structural fix thường là acquire/update resources theo **consistent order** ở mọi code path khi domain cho phép. Ví dụ cả hai flows đều touch inventory trước rồi orders, hoặc ngược lại. Nhưng không sửa mù quáng; deadlock graph phải xác nhận resources thật.

Transaction cũng nên ngắn. Không đưa network calls, heavy calculations hay unrelated queries vào transaction. Hai lần `SaveChangesAsync` không nhất thiết sai khi có explicit transaction, nhưng có thể làm lock giữ từ lần save đầu tới commit. Nếu có thể chuẩn bị dữ liệu trước transaction rồi thực hiện set of writes gọn hơn, lock duration giảm.

Indexes quan trọng. Nếu `SingleAsync` phải scan hoặc reconciliation `Contains` tạo plan với large scan, lock footprint tăng. Tôi kiểm tra actual execution plan/indexes/statistics, không chỉ thêm index theo tên column. Index đúng có thể giúp database tìm đúng rows nhanh hơn và giữ ít locks hơn; index dư thừa lại tăng write cost.

Với inventory decrement, domain có thể cho phép một atomic conditional update:

```sql
UPDATE dbo.Inventory
SET Available = Available - @quantity
WHERE ProductId = @productId
  AND Available >= @quantity;
```

Sau đó kiểm tra affected rows. Pattern này có thể giảm read-modify-write window và race, nhưng vẫn phải phối hợp order state transactionally. Không áp dụng nếu business rules phức tạp hơn.

Về isolation, `READ UNCOMMITTED` không phải deadlock cure an toàn; nó cho phép dirty/inconsistent reads và writes vẫn cần locks. `SERIALIZABLE` thường tăng range locking/contention, có thể làm tình hình tệ hơn nếu không thực sự cần semantics đó. RCSI/Snapshot có thể giảm reader-writer blocking trong một số workloads, nhưng không tự loại write-write deadlocks. Isolation level phải dựa trên invariant cụ thể.

Retry deadlock là reasonable vì SQL đã rollback victim transaction. Nhưng trước retry phải biết operation có external side effects chưa. Nếu transaction gửi email/event bên ngoài trước khi commit rồi retry toàn method, có thể duplicate. Giữ side effects ngoài transaction theo reliable pattern phù hợp hoặc dùng idempotency.

Testing: reproduce với concurrency cao tập trung cùng hot product, đồng thời chạy reconciliation. Assert không oversell inventory, order/inventory state consistent, retry count bounded và p99 không collapse. Capture deadlock graph trước/sau. Rollout có canary và monitor deadlocks per 1k transactions, DB CPU, lock waits, checkout p99, retries/logical request và reconciliation lag.

## Mẫu trả lời trong phỏng vấn

“Tôi không tăng retries trước khi hiểu deadlock graph. Deadlock là circular wait; SQL Server chọn một victim để phá cycle. CPU 70% không bác bỏ deadlock vì đây chủ yếu là lock-order/contention problem.

Snippet có một hypothesis rõ: checkout update Orders rồi Inventory, còn reconciliation làm ngược lại. Tôi sẽ lấy deadlock XML từ Extended Events để xác nhận exact statements, indexes và lock modes. Nếu đúng, structural fix đầu tiên là làm lock acquisition order nhất quán và rút ngắn transaction. Tôi cũng kiểm tra execution plans/indexes vì scans có thể làm lock footprint lớn hơn nhiều so với một row.

Retry chỉ là safety net. Tôi retry error 1205 có giới hạn, backoff+jitter và chỉ khi operation safe để retry. Retry 5 lần đồng loạt trên hot product có thể tự tăng contention. Tôi cũng không đổi toàn DB sang READ UNCOMMITTED hoặc SERIALIZABLE theo cảm tính; isolation phải phục vụ business invariant.

Trong flash sale tôi có thể throttle reconciliation để stabilize. Sau fix, tôi chạy concurrency test cùng hot product, assert inventory không âm/oversell, capture deadlocks trước-sau và monitor deadlocks per transaction, retries, lock waits và checkout p99.”

## Câu hỏi đào sâu

1. Nếu cả hai code paths đã update resources cùng thứ tự mà deadlock vẫn còn, bạn điều tra tiếp những resource nào trong deadlock graph?
2. Nếu bật RCSI làm reader-writer blocking giảm mạnh nhưng write-write deadlock vẫn xảy ra, điều đó có mâu thuẫn không?
3. Nếu tôi yêu cầu retry transaction tối đa 10 lần vì “cuối cùng cũng sẽ thành công”, bạn sẽ phản đối bằng reliability/capacity reasoning nào?

## Lỗi trả lời thường gặp

- Đồng nhất deadlock với “query chậm” hoặc CPU cao.
- Chỉ tăng retry count.
- Chuyển `READ UNCOMMITTED` để né locks mà bỏ qua dirty reads/correctness.
- Thêm `SERIALIZABLE` vì nghe “an toàn hơn” mà không xem contention.
- Không đọc deadlock graph và execution plan.
- Bỏ qua duplicate external side effects khi retry toàn operation.

## Thang điểm 0–10

- **0–2:** Chỉ biết deadlock là lỗi database và đề xuất retry/restart.
- **3–4:** Nhận ra lock order nhưng chưa có evidence/isolation/retry reasoning.
- **5–6:** Có deadlock graph, consistent ordering, transaction/index review và bounded retry.
- **7–8:** Phân tích isolation, query plans, side effects, hot-product contention và test correctness.
- **9–10:** Kết nối lock graph → structural fix → retry safety → business invariants → rollout telemetry một cách có hệ thống.

# Câu 3 — Reporting đang làm nghẽn OLTP: giữ query trực tiếp, dùng read replica, materialized read model hay dựng data warehouse?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** system design, SQL Server, OLTP vs analytical workloads, replication/read models, data freshness, consistency, ETL/CDC, failure recovery, observability, cost/complexity trade-offs

## Bối cảnh

Một employee platform dùng ASP.NET Core + SQL Server. Cùng một primary database phục vụ:

- profile/leave/timesheet transactional APIs;
- approval workflows;
- admin screens;
- 25 management reports với nhiều joins, aggregations và date-range filters.

Quy mô hiện tại:

- 2,000 writes/second ở peak trên các business tables;
- 50–100 report users active vào đầu giờ sáng và cuối tháng;
- một số reports scan hàng chục triệu rows và mất 10–40 giây;
- report users cần dữ liệu mới trong khoảng **5 phút**, không yêu cầu read-after-write tức thì;
- transactional API SLO: p95 < 300 ms;
- report SLO: 95% reports hoàn tất < 8 giây;
- team 8 developers, chưa có dedicated data engineering team;
- SQL Server hiện có HA setup, nhưng không có analytics warehouse riêng;
- business dự kiến data tăng 3× trong 18 tháng;
- một số reports chứa dữ liệu nhạy cảm theo department/role.

Trong tháng gần nhất, heavy reporting gây:

- buffer/cache pressure trên SQL primary;
- một số reporting queries cạnh tranh CPU/I/O với OLTP;
- deployment index change cho report làm write cost tăng đáng kể;
- teams bắt đầu thêm `NOLOCK` vào report query để “đỡ block”.

Có bốn đề xuất:

1. Tiếp tục query primary, chỉ tối ưu index/stored procedure.
2. Dùng SQL read replica cho tất cả reports.
3. Xây materialized reporting read model trong một database riêng, cập nhật gần real-time.
4. Dựng data warehouse/lakehouse + BI platform ngay lập tức.

## Câu hỏi chính

Bạn sẽ chọn và tiến hóa kiến trúc reporting như thế nào dựa trên SLO, freshness, team capacity và growth? Hãy so sánh bốn hướng theo isolation, consistency/freshness, operational complexity, query flexibility, schema evolution, security, failure recovery và cost; sau đó đề xuất migration path có thể ship dần mà không biến reporting project thành một data-platform rewrite kéo dài.

## Câu hỏi làm rõ nên cân nhắc

1. 25 reports có schema/query ổn định hay users cần ad-hoc analytics thường xuyên?
2. Freshness “5 phút” là hard SLA cho mọi report hay chỉ một subset?
3. SQL HA topology hiện tại có readable secondary phù hợp và replication lag observable không?
4. Reports cần historical snapshots/SCD, cross-system data hoặc chỉ dữ liệu từ một transactional database?
5. Security requirement có thể enforce ở reporting DB/read model theo department/user như thế nào?

## Gợi ý tư duy

### Gợi ý 1

“Read replica” giúp tách read load nhưng vẫn expose **OLTP schema** cho analytical queries. Nó không tự biến normalized transactional model thành reporting-friendly model.

### Gợi ý 2

Freshness 5 phút mở ra lựa chọn asynchronous replication/materialization. Không cần trả giá của synchronous dual-write chỉ để có read-after-write mà business không yêu cầu.

### Gợi ý 3

Data warehouse mạnh khi cần cross-domain history/ad-hoc analytics, nhưng team nhỏ và chỉ 25 known reports có thể chưa cần platform lớn ngay ngày đầu.

## Cấu trúc trả lời đề xuất

1. Phân loại reports theo freshness, complexity, sensitivity và usage.
2. Định nghĩa success metrics cho OLTP và reporting riêng.
3. So sánh primary optimization, replica, read model và warehouse.
4. Chọn smallest architecture đáp ứng requirement hiện tại.
5. Thiết kế ingestion/change propagation và rebuild/reconciliation semantics.
6. Thiết kế schema/indexes/security cho reporting workload.
7. Lập migration theo waves và rollback/fallback.
8. Định nghĩa signals để biết khi nào cần tiến lên warehouse/data platform.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tiếp tục để heavy analytical queries cạnh tranh primary nếu đã có production impact rõ.
- Không coi `NOLOCK` là performance fix miễn phí; hiểu dirty/non-repeatable/inconsistent reads.
- Nhận ra read replica và dedicated read model giải quyết hai lớp vấn đề khác nhau.
- Dùng freshness 5 phút làm input quan trọng cho asynchronous design.
- Có strategy rebuild/reconcile khi ingestion bị lag hoặc miss changes.
- Security/authorization phải được giữ ở reporting surface, không copy data rồi mặc định ai cũng đọc được.
- Chọn solution phù hợp team capacity; không mặc định warehouse/lakehouse.

### Điểm cộng

- Phân loại reports: operational near-real-time vs management historical/ad-hoc.
- Đề xuất projection/denormalized tables/materialized aggregates để giảm query complexity.
- Có watermark/version/checkpoint cho incremental ingestion.
- Theo dõi replication/materialization lag như SLO metric.
- Có backfill/rebuild path không khóa OLTP.

### Senior+

- Tách “load isolation” khỏi “data-model optimization”: readable secondary có thể là phase 1, reporting DB/read model là phase 2.
- Tránh synchronous dual-write giữa OLTP và reporting DB; dùng change capture/outbox/log-based feed phù hợp với nguồn dữ liệu và operational capabilities.
- Thiết kế idempotent upsert/version semantics để replay changes.
- Có point-in-time correctness story: report “as of” timestamp nào, xử lý late-arriving corrections thế nào.
- Biết trigger chuyển sang warehouse: nhiều source systems, long-term history/SCD, large ad-hoc analytics, governance/data-team maturity.

## Hướng giải quyết tham khảo

Tôi sẽ không chọn một option cho toàn bộ reporting trước khi phân loại 25 reports. Có thể chia ít nhất ba nhóm:

1. **Operational reports**: cần freshness ≤5 phút, scope hẹp, known query patterns.
2. **Heavy management reports**: nhiều joins/aggregations, chạy cuối tháng, chấp nhận vài phút lag.
3. **Ad-hoc/historical analytics**: nếu thực sự tồn tại, có nhu cầu history/cross-system khác với operational reporting.

Production evidence cho thấy primary đã chịu impact, nên “chỉ tiếp tục optimize primary” không còn là default tốt cho heavy reports. Tất nhiên vẫn phải sửa pathological queries/indexes, nhưng isolation workload là requirement architecture chứ không chỉ query tuning.

### Option 1 — Query primary

Ưu điểm: đơn giản, freshest data, không có replication pipeline. Nhược điểm: reporting cạnh tranh CPU/I/O/buffer cache với transactions; reporting indexes tăng write amplification; accidental scan có blast radius trực tiếp tới core APIs.

Tôi giữ primary cho lightweight operational lookups hoặc report nhỏ đã bounded, không cho arbitrary heavy analytics.

### Option 2 — Read replica

Readable secondary có thể là một **phase 1 rất thực dụng** nếu HA topology đã support. Nó tách nhiều read CPU/I/O khỏi primary và migration nhanh hơn xây data platform. Nhưng trade-offs:

- replication lag phải observable;
- query vẫn dựa trên normalized OLTP schema;
- reporting indexes/schema flexibility có thể bị giới hạn tùy replication/topology;
- failover/secondary availability semantics phải rõ;
- một heavy report vẫn có thể làm replica quá tải và ảnh hưởng HA strategy nếu dùng chung mục đích.

Replica giải quyết load isolation, chưa giải quyết reporting data model.

### Option 3 — Dedicated materialized read model

Với 25 known reports và freshness 5 phút, đây có thể là target hợp lý sau một phase ngắn. Tạo reporting database riêng với denormalized tables/aggregates theo access patterns. Changes từ OLTP được propagate asynchronously bằng mechanism platform support tốt: CDC/log-based capture, scheduled incremental extraction với watermark, hoặc outbox nếu cần domain-event semantics. Không nên synchronous dual-write trong request transaction vì sẽ coupling availability của OLTP với reporting DB.

Pipeline phải có:

- checkpoint/watermark;
- idempotent apply/upsert;
- lag measurement;
- retry;
- dead-letter/error audit nếu mechanism cần;
- full rebuild/backfill path;
- reconciliation checks giữa source và read model.

Ví dụ report monthly department totals không cần join hàng chục triệu raw rows mỗi request; có thể materialize daily/department aggregates rồi query nhanh.

### Option 4 — Warehouse/lakehouse

Tôi chỉ đi ngay nếu requirement thực sự có cross-system analytics, years of historical snapshots/SCD, ad-hoc exploration, BI governance và team/platform support. Nếu chỉ có 25 operational/management reports từ một SQL source, warehouse ngay lập tức có thể thêm ETL/orchestration/governance/tooling burden lớn hơn value.

Nhưng roadmap nên để ngỏ: reporting read model có thể là bước trung gian; không thiết kế proprietary format khóa đường sang warehouse sau này.

### Migration path

**Wave 0 — Measure:**

- Top report queries theo CPU/duration/logical reads.
- OLTP p95/p99, DB CPU/I/O, wait stats.
- Usage/freshness/security classification.

**Wave 1 — Contain blast radius:**

- Stop uncontrolled `NOLOCK` additions.
- Query limits/date-range bounds.
- Nếu readable secondary đã có và safe cho HA, route selected heavy reports sang secondary.
- Dashboard replication lag và replica resource health.

**Wave 2 — Materialize high-value reports:**

- Chọn 3–5 expensive stable reports.
- Tạo reporting schema/database và incremental ingestion.
- Dual-read verification: run old/new report calculation offline, compare totals/row counts.
- Canary users rồi migrate traffic.

**Wave 3 — Expand:**

- Migrate remaining stable operational reports.
- Add shared dimensions/aggregates có ownership rõ.
- Retire report-specific indexes trên primary khi không còn cần và sau impact analysis.

**Wave 4 — Re-evaluate warehouse:**

Nếu users cần ad-hoc analytics, cross-system data, years of history, slowly changing dimensions, governance/catalog/BI self-service, lúc đó warehouse có business driver rõ.

### Consistency/freshness

Report phải expose “Data updated through 10:32” hoặc equivalent nếu lag có ý nghĩa. Freshness 5 phút trở thành measurable SLO: `now - last_applied_source_position_time`. Nếu lag >5 phút, không nên âm thầm trả old data như thể current; UI/monitoring phải phản ánh degraded freshness theo business requirement.

### Security

Reporting DB không được coi là “copy nên ít nhạy cảm hơn”. Áp row/department authorization ở API/query layer, least-privilege DB credentials, audit sensitive report access và data retention. Nếu direct BI access được thêm sau này, security model phải được thiết kế riêng thay vì reuse app assumptions.

### Testing và operations

- Reconciliation sample/full checks source vs read model.
- Replay same batch nhiều lần để prove idempotency.
- Kill ingestion giữa batch rồi restart.
- Simulate source schema change.
- Load test 100 concurrent report users mà OLTP SLO vẫn ổn.
- Measure report p95 <8s và freshness ≤5m.

Observability gồm ingestion lag, rows/events processed, apply failures, reconciliation mismatch, report duration/error, reporting DB CPU/I/O, primary offload ratio và OLTP p95.

## Mẫu trả lời trong phỏng vấn

“Tôi tách vấn đề thành hai phần: isolation workload và data model. Read replica giúp tách read load khỏi primary nhưng vẫn bắt reports query OLTP schema. Dedicated reporting read model vừa isolate load vừa cho phép denormalized/aggregate schema phù hợp report.

Với chỉ 25 known reports, freshness 5 phút và team 8 người, tôi chưa dựng warehouse ngay. Phase đầu tôi đo top queries và nếu readable secondary đã tồn tại an toàn thì route một số heavy reads sang đó để giảm blast radius nhanh. Sau đó tôi migrate 3–5 report đắt nhất sang reporting database materialized asynchronously.

Tôi tránh synchronous dual-write từ request. Ingestion dùng CDC/log-based/incremental watermark tùy platform, nhưng bắt buộc có checkpoint, idempotent replay, lag metric và full rebuild/reconciliation path. UI phải biết data updated tới thời điểm nào vì 5 phút freshness là SLO thật.

`NOLOCK` không phải fix miễn phí; nó có thể trả dữ liệu không nhất quán. Security cũng phải được giữ khi copy data sang reporting store.

Tôi chỉ nâng lên warehouse/lakehouse khi xuất hiện driver như nhiều source systems, historical/SCD, ad-hoc BI hoặc governance needs. Mục tiêu là giảm OLTP risk và đạt report SLO từng wave, không mở một data-platform rewrite chỉ vì reports đang chậm.”

## Câu hỏi đào sâu

1. Nếu read replica lag 12 phút đúng lúc finance chạy report, bạn trả lỗi, trả stale data có cảnh báo hay fallback về primary? Decision dựa trên gì?
2. Nếu CDC pipeline miss một schema change và reporting DB sai totals trong 2 giờ, bạn thiết kế detection/rebuild/audit thế nào?
3. Tôi muốn synchronous dual-write để reporting data “luôn đúng ngay lập tức”; bạn phản biện bằng failure/transaction coupling nào?

## Lỗi trả lời thường gặp

- Thêm `NOLOCK` vào mọi report rồi coi vấn đề đã giải quyết.
- Nói “dùng replica” mà không bàn lag, HA impact và OLTP-shaped schema.
- Nhảy thẳng sang Kafka/lakehouse/data mesh khi requirement chưa cần.
- Synchronous dual-write OLTP + reporting DB mà không giải quyết partial failure.
- Không có rebuild/reconciliation strategy.
- Copy dữ liệu sang reporting DB rồi bỏ quên authorization/audit.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất thêm index hoặc tăng SQL Server size.
- **3–4:** Biết dùng replica/read model nhưng thiếu freshness/failure/rebuild reasoning.
- **5–6:** So sánh options hợp lý, chọn architecture theo team/SLO và có migration phases.
- **7–8:** Có idempotent ingestion, lag SLO, reconciliation, security và OLTP isolation metrics.
- **9–10:** Phân biệt rõ load isolation/data-model optimization/data-platform needs, đưa ra reversible roadmap có production evidence và biết chính xác khi complexity của warehouse đáng giá.
