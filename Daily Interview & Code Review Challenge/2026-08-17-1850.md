# Code Review Challenge 1 — Distributed lock bằng Redis vẫn cho phép hai worker cùng xử lý một job

**Chủ đề:** Concurrency và race conditions, caching/Redis, background jobs, idempotency, failure recovery, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một background worker chạy trên 4 instance dùng Redis để ngăn cùng một `PayrollJob` bị xử lý đồng thời. Mỗi job thường mất 20–90 giây nhưng đôi lúc có thể kéo dài vài phút khi database chậm.

Production ghi nhận rất hiếm nhưng có thật:

- hai instance cùng xử lý một `jobId`,
- payroll adjustment bị ghi hai lần,
- có log cho thấy worker A vẫn chạy nhưng lock đã biến mất,
- worker B đôi lúc xóa lock mà worker A vừa tạo lại,
- khi Redis/network chập chờn, job có lúc bị bỏ qua hoặc chạy trùng.

Business yêu cầu không được ghi trùng adjustment. Redis lock chỉ là cơ chế phối hợp; correctness cuối cùng vẫn phải được bảo vệ ở persistence layer.

## Đoạn code cần review

```csharp
public sealed class PayrollJobProcessor
{
    private readonly IDatabase _redis;
    private readonly AppDbContext _db;
    private readonly ILogger<PayrollJobProcessor> _logger;

    public PayrollJobProcessor(
        IConnectionMultiplexer redis,
        AppDbContext db,
        ILogger<PayrollJobProcessor> logger)
    {
        _redis = redis.GetDatabase();
        _db = db;
        _logger = logger;
    }

    public async Task ProcessAsync(
        Guid jobId,
        CancellationToken cancellationToken)
    {
        var key = $"payroll-lock:{jobId}";

        var acquired = await _redis.StringSetAsync(
            key,
            Environment.MachineName,
            TimeSpan.FromSeconds(30),
            When.NotExists);

        if (!acquired)
        {
            _logger.LogInformation(
                "Job {JobId} is already running",
                jobId);
            return;
        }

        try
        {
            var job = await _db.PayrollJobs
                .SingleAsync(x => x.Id == jobId, cancellationToken);

            if (job.Status == PayrollJobStatus.Completed)
                return;

            var adjustment = await CalculateAdjustmentAsync(
                job,
                cancellationToken);

            _db.PayrollAdjustments.Add(new PayrollAdjustment
            {
                JobId = jobId,
                EmployeeId = job.EmployeeId,
                Amount = adjustment,
                CreatedAt = DateTime.UtcNow
            });

            job.Status = PayrollJobStatus.Completed;
            await _db.SaveChangesAsync(cancellationToken);
        }
        finally
        {
            await _redis.KeyDeleteAsync(key);
        }
    }

    private static async Task<decimal> CalculateAdjustmentAsync(
        PayrollJob job,
        CancellationToken cancellationToken)
    {
        await Task.Delay(TimeSpan.FromSeconds(45), cancellationToken);
        return job.ExpectedAdjustment;
    }
}
```

## Kết quả code review tham khảo

### 1. TTL ngắn hơn thời gian xử lý thực tế

**Problem:** Lock hết hạn khi worker vẫn đang xử lý.  
**Why it happens:** TTL cố định 30 giây nhưng job có thể dài hơn.  
**Production impact:** Worker B acquire lock mới và xử lý cùng job với worker A.  
**Severity:** Critical  
**Recommended fix:** Dùng lease duration phù hợp kèm renewal có kiểm soát, hoặc cơ chế coordination khác phù hợp workload. Không dựa vào TTL ngắn cố định.

### 2. Unlock không kiểm tra owner/token

**Problem:** `KeyDeleteAsync(key)` xóa lock bất kể lock hiện tại thuộc ai.  
**Why it happens:** Không dùng unique token và compare-and-delete atomic.  
**Production impact:** Worker A có thể xóa lock mới của worker B sau khi lease cũ hết hạn.  
**Severity:** Critical  
**Recommended fix:** Mỗi acquisition dùng unique token; release phải atomic theo điều kiện “value hiện tại == token của tôi”.

### 3. Redis lock không bảo vệ business invariant ở database

**Problem:** Không có unique constraint đảm bảo mỗi `JobId` chỉ sinh một adjustment.  
**Why it happens:** Correctness phụ thuộc hoàn toàn vào distributed coordination.  
**Production impact:** Network partition, lease expiry hoặc bug lock có thể tạo duplicate tài chính.  
**Severity:** Critical  
**Recommended fix:** Tạo database invariant, ví dụ unique key trên `PayrollAdjustments(JobId)` hoặc idempotency key tương đương.

### 4. Read-then-write trạng thái không atomic dưới concurrency

**Problem:** Hai worker có thể cùng đọc `Status != Completed` trước khi một bên commit.  
**Why it happens:** Application check không phải compare-and-set tại database.  
**Production impact:** Cả hai cùng tính và insert.  
**Severity:** High  
**Recommended fix:** Dùng optimistic concurrency/conditional update hoặc unique invariant để chỉ một transaction thắng.

### 5. Không có lease renewal hoặc detection khi mất ownership

**Problem:** Worker không biết lock đã hết hạn hay bị mất.  
**Why it happens:** Không có heartbeat/renewal token-aware.  
**Production impact:** Worker tiếp tục side effect dù không còn quyền sở hữu lease.  
**Severity:** High  
**Recommended fix:** Nếu dùng lease, renewal phải atomic theo token; khi mất ownership cần policy rõ ràng để dừng hoặc chuyển sang database-controlled commit.

### 6. `Environment.MachineName` không phải unique owner token cho mỗi acquisition

**Problem:** Hai process/container có thể chia sẻ machine name hoặc cùng worker acquire nhiều lần.  
**Why it happens:** Value không đại diện duy nhất cho một lease instance.  
**Production impact:** Khó phân biệt owner và release an toàn.  
**Severity:** High  
**Recommended fix:** Dùng random opaque token cho mỗi lần acquire.

### 7. Không phân biệt lock contention với Redis failure

**Problem:** Code chỉ xử lý `acquired == false`; network exception bubble ra mà không có semantics rõ.  
**Why it happens:** Coordination dependency không có failure policy.  
**Production impact:** Job có thể bị retry mù hoặc bỏ qua tùy scheduler.  
**Severity:** Medium  
**Recommended fix:** Tách lock-not-acquired, Redis unavailable, timeout; ghi metric và quyết định retry/backoff rõ ràng.

### 8. `DbContext` lifetime phải phù hợp với background execution

**Problem:** Nếu processor sống lâu hơn scope dự kiến, `DbContext` có thể bị dùng sai lifetime.  
**Why it happens:** Background worker dễ bị đăng ký singleton trong khi context là scoped.  
**Production impact:** Lỗi concurrency/lifetime hoặc stale tracking nếu dùng sai DI scope.  
**Severity:** Medium  
**Recommended fix:** Tạo scope/context per job hoặc dùng factory phù hợp.

### 9. Thiếu operation/lease observability

**Problem:** Log không có lease token, acquisition duration, renewal, lock age hoặc attempt.  
**Why it happens:** Coordination state không được coi là first-class telemetry.  
**Production impact:** Khó chứng minh vì sao duplicate xảy ra.  
**Severity:** Medium  
**Recommended fix:** Log `JobId`, attempt, worker id, lease acquisition/release outcome, duration; metric contention, lease lost, duplicate prevented.

## Phiên bản code đề xuất

Ví dụ dưới đây nhấn mạnh database invariant là lớp bảo vệ cuối cùng. Phần Redis lease được giả định nằm sau abstraction có owner token và release an toàn.

```csharp
public sealed class PayrollJobProcessor
{
    private readonly IDistributedLeaseProvider _leaseProvider;
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<PayrollJobProcessor> _logger;

    public PayrollJobProcessor(
        IDistributedLeaseProvider leaseProvider,
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<PayrollJobProcessor> logger)
    {
        _leaseProvider = leaseProvider;
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task ProcessAsync(Guid jobId, CancellationToken cancellationToken)
    {
        await using var lease = await _leaseProvider.TryAcquireAsync(
            $"payroll-lock:{jobId}",
            TimeSpan.FromMinutes(2),
            cancellationToken);

        if (lease is null)
            return;

        await using var db =
            await _dbFactory.CreateDbContextAsync(cancellationToken);

        var job = await db.PayrollJobs
            .SingleAsync(x => x.Id == jobId, cancellationToken);

        if (job.Status == PayrollJobStatus.Completed)
            return;

        var amount = await CalculateAdjustmentAsync(job, cancellationToken);

        db.PayrollAdjustments.Add(new PayrollAdjustment
        {
            JobId = jobId,
            EmployeeId = job.EmployeeId,
            Amount = amount,
            CreatedAt = DateTime.UtcNow
        });

        job.Status = PayrollJobStatus.Completed;

        try
        {
            await db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsDuplicateJobAdjustment(ex))
        {
            _logger.LogInformation(
                "Duplicate payroll processing prevented by database for {JobId}",
                jobId);
        }
    }
}
```

Database nên có unique constraint/index phù hợp trên `PayrollAdjustments(JobId)` nếu business invariant thực sự là một adjustment cho một job. `IDistributedLeaseProvider` phải dùng owner token riêng cho mỗi acquisition và release/renew atomic theo token.

## Trade-offs

- Redis lease giảm duplicate work nhưng không thay thế database invariant.
- TTL dài giảm lease expiry nhưng làm recovery chậm hơn khi worker crash nếu không có renewal/expiry design tốt.
- Renewal tăng complexity và dependency vào Redis availability.
- Conditional update/unique constraint có thể đủ nếu duplicate work rẻ; khi đó Redis lock có thể chỉ là optimization.
- Với nghiệp vụ tài chính, ưu tiên correctness ở persistence hơn tối ưu tránh tính toán lặp.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 processor cùng `jobId`, xác nhận chỉ một adjustment tồn tại.
2. **Lease expiry test:** cho processing dài hơn TTL cũ, xác nhận worker khác không tạo duplicate.
3. **Crash/failure test:** kill worker sau khi acquire hoặc giữa processing; xác nhận hệ thống recover và invariant vẫn đúng.
4. **Redis outage test:** mô phỏng timeout/network error, xác nhận retry policy và telemetry đúng.
5. **Database race test:** bỏ Redis trong test, chạy hai transaction đồng thời và xác nhận unique invariant chặn duplicate.

# Code Review Challenge 2 — API báo cáo materialize toàn bộ dữ liệu rồi mới filter, vừa chậm vừa có nguy cơ lộ dữ liệu tenant khác

## Bối cảnh

Một endpoint ASP.NET Core trả báo cáo timesheet cho manager theo tenant, khoảng thời gian và optional employee filter. Database có hơn 20 triệu timesheet rows.

Production ghi nhận:

## Đoạn code cần review

```csharp
public sealed class TimesheetReportService
{
    private readonly AppDbContext _db;

    public TimesheetReportService(AppDbContext db)
    {
        _db = db;
    }

    public async Task<IReadOnlyList<TimesheetDto>> GetAsync(
        Guid tenantId,
        DateTime from,
        DateTime to,
        Guid? employeeId,
        int page,
        int pageSize,
        CancellationToken cancellationToken)
    {
        var rows = await _db.Timesheets
            .Include(x => x.Employee)
            .Include(x => x.Project)
            .ToListAsync(cancellationToken);

        var filtered = rows
            .Where(x => x.TenantId == tenantId)
            .Where(x => x.WorkDate >= from && x.WorkDate <= to)
            .Where(x => employeeId == null || x.EmployeeId == employeeId)
            .OrderByDescending(x => x.WorkDate)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new TimesheetDto(
                x.Id,
                x.Employee.DisplayName,
                x.Project.Name,
                x.WorkDate,
                x.Hours,
                x.Note))
            .ToList();

        return filtered;
    }
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ bảng trước khi filter

**Problem:** `ToListAsync` chạy trước mọi filter.  
**Why it happens:** Query chuyển từ database execution sang in-memory quá sớm.  
**Production impact:** Đọc hàng triệu row, tăng network, memory, GC và latency.  
**Severity:** Critical  
**Recommended fix:** Giữ `IQueryable`; áp dụng filter/order/paging/projection trước `ToListAsync`.

### 2. Tenant boundary chỉ được áp dụng trong process

**Problem:** Database trả cả row tenant khác về application rồi mới lọc.  
**Why it happens:** Tenant predicate không nằm trong SQL.  
**Production impact:** Tăng blast radius nếu code/log/debug/profiling vô tình expose dữ liệu; không đáp ứng nguyên tắc minimize data access.  
**Severity:** Critical  
**Recommended fix:** Tenant predicate phải là phần bắt buộc của database query và ideally được enforce nhất quán qua repository/query policy/global filter phù hợp thiết kế.

### 3. `Include` tải graph không cần thiết

**Problem:** Load full `Employee` và `Project` entity.  
**Why it happens:** Dùng eager loading dù chỉ cần vài trường cho DTO.  
**Production impact:** Tăng dữ liệu truyền, allocation và tracking overhead.  
**Severity:** High  
**Recommended fix:** Projection trực tiếp sang DTO trong SQL query.

### 4. Query read-only nhưng mặc định tracking entity

**Problem:** Hàng loạt entity được đưa vào Change Tracker.  
**Why it happens:** Query entity thông thường trong context tracking.  
**Production impact:** Memory và CPU cao hơn.  
**Severity:** High  
**Recommended fix:** Projection DTO thường tránh nhu cầu tracking; hoặc dùng `AsNoTracking` cho entity read-only khi phù hợp.

### 5. Pagination ordering không deterministic

**Problem:** Chỉ order theo `WorkDate`.  
**Why it happens:** Nhiều row có cùng ngày nhưng không có tie-breaker.  
**Production impact:** Row có thể bị lặp/thiếu giữa các page khi execution plan/data thay đổi.  
**Severity:** High  
**Recommended fix:** Thêm unique tie-breaker như `ThenByDescending(x => x.Id)`.

### 6. Không validate `page` và `pageSize`

**Problem:** Giá trị âm, 0 hoặc quá lớn chưa được chặn.  
**Why it happens:** Input validation thiếu.  
**Production impact:** Exception, query bất thường hoặc response quá lớn.  
**Severity:** Medium  
**Recommended fix:** Validate range và đặt max page size.

### 7. Deep OFFSET có thể ngày càng chậm

**Problem:** `Skip` lớn vẫn khiến DB phải đi qua nhiều row phù hợp trước đó.  
**Why it happens:** Offset pagination không scale tốt cho deep pages.  
**Production impact:** Latency tăng với page sâu.  
**Severity:** Medium  
**Recommended fix:** Với use case duyệt tuần tự lớn, cân nhắc keyset/cursor pagination dựa trên `(WorkDate, Id)`.

### 8. Date boundary có thể mơ hồ

**Problem:** `<= to` phụ thuộc semantics `to` là instant chính xác hay “hết ngày”.  
**Why it happens:** Requirement timezone/inclusive-exclusive chưa rõ.  
**Production impact:** Thiếu hoặc dư record ở boundary.  
**Severity:** Medium  
**Recommended fix:** Làm rõ timezone và ưu tiên half-open interval `[from, toExclusive)` nếu phù hợp business.

### 9. Thiếu index/query-shape consideration

**Problem:** Không thấy design index theo tenant/date/order/filter thực tế.  
**Why it happens:** Query và schema optimization chưa được xem cùng nhau.  
**Production impact:** Scan/sort lớn dù LINQ đã được sửa.  
**Severity:** Medium  
**Recommended fix:** Quan sát execution plan và cân nhắc index bắt đầu từ tenant + date/order key theo workload thực tế.

## Phiên bản code đề xuất

```csharp
public async Task<IReadOnlyList<TimesheetDto>> GetAsync(
    Guid tenantId,
    DateTime from,
    DateTime toExclusive,
    Guid? employeeId,
    int page,
    int pageSize,
    CancellationToken cancellationToken)
{
    if (page < 1)
        throw new ArgumentOutOfRangeException(nameof(page));

    if (pageSize is < 1 or > 200)
        throw new ArgumentOutOfRangeException(nameof(pageSize));

    var query = _db.Timesheets
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId)
        .Where(x => x.WorkDate >= from && x.WorkDate < toExclusive);

    if (employeeId.HasValue)
    {
        query = query.Where(x => x.EmployeeId == employeeId.Value);
    }

    return await query
        .OrderByDescending(x => x.WorkDate)
        .ThenByDescending(x => x.Id)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(x => new TimesheetDto(
            x.Id,
            x.Employee.DisplayName,
            x.Project.Name,
            x.WorkDate,
            x.Hours,
            x.Note))
        .ToListAsync(cancellationToken);
}
```

Nếu page sâu là use case chính, nên chuyển sang cursor/keyset pagination với sort key ổn định thay vì tăng `OFFSET` vô hạn.

## Trade-offs

- Offset pagination đơn giản và hỗ trợ nhảy tới page N, nhưng kém hiệu quả ở deep pages.
- Keyset pagination nhanh và ổn định hơn cho next/previous flow nhưng khó nhảy trực tiếp tới page bất kỳ.
- Projection tối ưu bandwidth/memory nhưng DTO query có thể cần maintenance khi schema thay đổi.
- Global query filter có thể giúp tenant isolation nhất quán, nhưng vẫn cần hiểu rõ các trường hợp bypass/admin cross-tenant.

## Cách kiểm thử

1. **Tenant isolation integration test:** seed nhiều tenant, xác nhận SQL/query result không chứa tenant khác.
2. **Query-shape test:** kiểm tra generated SQL có `WHERE TenantId`, date filter, `ORDER BY`, paging trước materialization.
3. **Load test:** dữ liệu hàng triệu row, đo latency/memory so với implementation cũ.
4. **Pagination correctness test:** nhiều record cùng `WorkDate`, xác nhận không lặp/thiếu giữa page liên tiếp.
5. **Boundary test:** kiểm tra `from`, `toExclusive`, timezone và employee filter.

## Quan sát trong production

Theo dõi:

- endpoint p50/p95/p99 latency
- rows returned và page depth
- DB command duration
- logical reads / execution plan / sort spill nếu database hỗ trợ quan sát
- process memory/GC trong giờ report cao điểm
- query timeout/error rate
- tenant id ở structured trace nhưng không log nội dung nhạy cảm

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn keyset pagination thay vì offset pagination?
2. Bạn thiết kế index thế nào nếu filter thường xuyên theo `TenantId`, `EmployeeId`, `WorkDate`?
3. Nếu global admin được xem nhiều tenant, bạn thiết kế authorization/query boundary ra sao để không vô tình bypass tenant isolation?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Distributed lock là coordination mechanism, không nên là lớp duy nhất bảo vệ business invariant.
- Lease cần owner token, expiry/renewal semantics và release atomic theo owner.
- Idempotency và database constraints là tuyến phòng thủ cuối cùng cho duplicate side effect.
- Với EF Core, vị trí materialization quyết định phần nào chạy ở database và phần nào chạy in-memory.
- Tenant isolation, filtering, projection và pagination nên được đưa xuống query càng sớm càng tốt.

## Mẫu tư duy cần nhớ

- Correctness trước optimization: bảo vệ invariant ở database.
- Distributed lock chỉ giảm contention; không thay thế idempotency.
- Giữ `IQueryable` tới khi filter, sort, project và page xong.
- Enforce authorization/tenant boundary trước khi dữ liệu rời database.
- Test failure path và concurrency bằng tình huống thực sự song song, không chỉ unit test happy path.
