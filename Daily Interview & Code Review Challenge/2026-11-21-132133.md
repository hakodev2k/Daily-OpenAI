# Code Review Challenge 1 — Azure Service Bus consumer ghi nhận thanh toán hai lần

**Chủ đề:** C#/.NET 8, Azure Service Bus, idempotency, transaction boundaries, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một hệ thống bán vé nhận sự kiện `PaymentCaptured` qua Azure Service Bus queue. Một sự kiện phải tạo đúng một ledger entry và cập nhật trạng thái đơn hàng. API thanh toán và worker triển khai độc lập trên Azure App Service; worker có thể chạy nhiều instance. Khi nhà cung cấp gửi lại sự kiện hoặc worker bị restart giữa chừng, bộ phận kế toán đôi khi thấy nhiều ledger entry cho cùng payment. Giả định `PaymentId` là định danh ổn định của một khoản thanh toán, còn `MessageId` không nhất thiết ổn định qua lần gửi lại từ nguồn. SQL Server là source of truth. Mục tiêu: xử lý at-least-once mà không mất giao dịch hợp lệ.

## Đoạn code cần review

```csharp
public sealed record PaymentCaptured(
    Guid PaymentId, Guid OrderId, decimal Amount, string Currency);

public sealed class PaymentConsumer(
    ServiceBusClient client,
    IServiceScopeFactory scopeFactory,
    ILogger<PaymentConsumer> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await using var processor = client.CreateProcessor(
            "payments", new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = true,
                MaxConcurrentCalls = 16
            });

        processor.ProcessMessageAsync += async args =>
        {
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var payment = JsonSerializer.Deserialize<PaymentCaptured>(
                args.Message.Body.ToString())!;

            if (await db.LedgerEntries.AnyAsync(
                    x => x.PaymentId == payment.PaymentId))
                return;

            db.LedgerEntries.Add(new LedgerEntry
            {
                PaymentId = payment.PaymentId,
                OrderId = payment.OrderId,
                Amount = payment.Amount,
                Currency = payment.Currency
            });

            var order = await db.Orders.FindAsync(payment.OrderId);
            if (order != null) order.Status = "Paid";

            await db.SaveChangesAsync();
            logger.LogInformation("Payment processed: {Body}",
                args.Message.Body.ToString());
        };

        processor.ProcessErrorAsync += args =>
        {
            logger.LogError(args.Exception, "Processor failed");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Check-then-insert không bảo đảm idempotency

**Vấn đề:** `AnyAsync` rồi `Add` không nguyên tử.  
**Tại sao xảy ra:** Hai consumer có thể cùng thấy chưa tồn tại và cùng insert.  
**Ảnh hưởng production:** Ledger trùng, báo cáo sai, reconciliation khó.  
**Cách sửa:** Unique index trên `LedgerEntries.PaymentId`, xử lý duplicate-key theo provider; transaction chứa các thay đổi nghiệp vụ liên quan. Không dựa vào in-memory lock.

### [Critical] — Auto-complete không phù hợp khi cần kiểm soát settlement

**Vấn đề:** Không chủ động `CompleteMessageAsync`, `AbandonMessageAsync` hoặc `DeadLetterMessageAsync`.  
**Tại sao xảy ra:** `AutoCompleteMessages=true` hoàn tất khi handler trả về bình thường, kể cả nhánh `return`.  
**Ảnh hưởng production:** Khó phân biệt duplicate hợp lệ, dữ liệu không hợp lệ và lỗi tạm thời; settlement không gắn rõ với kết quả nghiệp vụ.  
**Cách sửa:** `AutoCompleteMessages=false`, complete sau khi commit/nhận diện duplicate thành công; dead-letter thông điệp sai cấu trúc theo chính sách; để retry lỗi transient.

### [High] — Không kiểm tra schema và invariant nghiệp vụ

**Vấn đề:** JSON null, `Amount <= 0`, currency không hợp lệ, order thiếu hoặc dữ liệu không khớp đều có thể gây lỗi hoặc ledger không tương ứng order.  
**Tại sao xảy ra:** Deserialize và ghi thẳng không validation.  
**Ảnh hưởng production:** Poison messages, ledger sai và trạng thái đơn hàng bất nhất.  
**Cách sửa:** Validate event version, số tiền, currency, order/payment mapping; quy định rõ trường hợp order chưa xuất hiện là retry hay DLQ.

### [High] — Thiếu chính sách xử lý sự kiện mâu thuẫn

**Vấn đề:** Cùng `PaymentId` nhưng payload khác sẽ bị coi là duplicate hợp lệ.  
**Tại sao xảy ra:** Kiểm tra chỉ dựa vào ID, không đối chiếu giá trị bất biến.  
**Ảnh hưởng production:** Che giấu lỗi upstream hoặc hành vi bất thường.  
**Cách sửa:** So sánh amount, currency, order và audit mismatch; không ghi đè âm thầm.

### [High] — Lifecycle của processor không có shutdown có kiểm soát

**Vấn đề:** Processor nằm trong `ExecuteAsync`; `Task.Delay` bị cancel có thể kết thúc scope mà không gọi `StopProcessingAsync` một cách chủ động.  
**Tại sao xảy ra:** Không có `try/finally` điều phối stop.  
**Ảnh hưởng production:** In-flight handler bị cắt giữa commit/settlement; tăng retry và lock loss.  
**Cách sửa:** Stop processor trong `finally`, đặt timeout shutdown phù hợp và bảo đảm DB idempotency khi restart.

### [Medium] — Không truyền cancellation token vào I/O

**Vấn đề:** `AnyAsync`, `SaveChangesAsync` và `FindAsync` không dùng token của handler.  
**Tại sao xảy ra:** Bỏ qua `args.CancellationToken`.  
**Ảnh hưởng production:** Shutdown chậm và giữ connection không cần thiết.  
**Cách sửa:** Truyền token vào thao tác hỗ trợ cancellation; hiểu rằng cancellation sau DB commit vẫn có thể dẫn đến redelivery.

### [Medium] — Log nguyên body

**Vấn đề:** Ghi toàn bộ payload vào log.  
**Tại sao xảy ra:** Không giới hạn trường dữ liệu được log.  
**Ảnh hưởng production:** Rò rỉ dữ liệu và tăng chi phí logging.  
**Cách sửa:** Structured logging với `PaymentId`, `OrderId`, `MessageId`, delivery count, trace ID; không ghi raw body.

### [Medium] — Không có phân loại lỗi và cảnh báo DLQ

**Vấn đề:** Handler để exception lan truyền nhưng không có phân loại invalid/transient và không ghi metric theo kết quả.  
**Tại sao xảy ra:** Chỉ có `ProcessErrorAsync` ở mức processor.  
**Ảnh hưởng production:** Retry vô ích hoặc sự cố kéo dài không được phát hiện.  
**Cách sửa:** Chính sách DLQ cho invalid, retry cho transient, theo dõi delivery count, active/dead-letter messages và độ trễ xử lý.

### [Medium] — Concurrency chưa gắn với năng lực database

**Vấn đề:** `MaxConcurrentCalls=16` mỗi instance có thể tạo nhiều kết nối/transaction khi scale out.  
**Tại sao xảy ra:** Không giới hạn tổng tải toàn cụm.  
**Ảnh hưởng production:** SQL blocking, timeout và backlog tăng.  
**Cách sửa:** Load test, đo SQL waits/connection pool và điều chỉnh concurrency/prefetch dựa trên số instance.

## Phiên bản đề xuất

Phác thảo phần xử lý cốt lõi dưới đây giả định `PaymentId` có unique index, `LedgerEntry` và `Order` nằm trong cùng SQL Server database; một `PaymentId` chỉ đại diện một khoản thanh toán. `PaymentMismatchException` và `InvalidPaymentEventException` là exception nghiệp vụ do ứng dụng định nghĩa.

```csharp
public async Task HandleAsync(
    ProcessMessageEventArgs args,
    IServiceScopeFactory scopes,
    ILogger logger)
{
    PaymentCaptured payment;
    try
    {
        payment = JsonSerializer.Deserialize<PaymentCaptured>(
            args.Message.Body.ToString())
            ?? throw new JsonException("Empty event");

        if (payment.PaymentId == Guid.Empty ||
            payment.OrderId == Guid.Empty ||
            payment.Amount <= 0 ||
            string.IsNullOrWhiteSpace(payment.Currency))
            throw new JsonException("Invalid payment fields");
    }
    catch (JsonException)
    {
        await args.DeadLetterMessageAsync(
            args.Message, "InvalidPaymentEvent",
            cancellationToken: args.CancellationToken);
        return;
    }

    await using var scope = scopes.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    var ct = args.CancellationToken;

    try
    {
        await using var tx = await db.Database.BeginTransactionAsync(ct);
        var existing = await db.LedgerEntries
            .SingleOrDefaultAsync(x => x.PaymentId == payment.PaymentId, ct);

        if (existing is not null)
        {
            if (existing.OrderId != payment.OrderId ||
                existing.Amount != payment.Amount ||
                existing.Currency != payment.Currency)
                throw new PaymentMismatchException(payment.PaymentId);
        }
        else
        {
            var order = await db.Orders
                .SingleOrDefaultAsync(x => x.Id == payment.OrderId, ct)
                ?? throw new InvalidPaymentEventException("Unknown order");

            // Cần đối chiếu số tiền/currency với order theo domain policy.
            db.LedgerEntries.Add(new LedgerEntry
            {
                PaymentId = payment.PaymentId,
                OrderId = payment.OrderId,
                Amount = payment.Amount,
                Currency = payment.Currency
            });
            order.Status = "Paid";
            await db.SaveChangesAsync(ct);
        }

        await tx.CommitAsync(ct);
        await args.CompleteMessageAsync(args.Message, ct);
    }
    catch (PaymentMismatchException)
    {
        await args.DeadLetterMessageAsync(
            args.Message, "ConflictingPaymentId",
            cancellationToken: ct);
    }
    catch (InvalidPaymentEventException)
    {
        await args.DeadLetterMessageAsync(
            args.Message, "InvalidBusinessReference",
            cancellationToken: ct);
    }
}
```

**Điều kiện bắt buộc khi triển khai:** Thêm unique index trong migration: `HasIndex(x => x.PaymentId).IsUnique()`. Với hai transaction cạnh tranh, một transaction có thể nhận unique-constraint violation; cần nhận diện đúng mã lỗi SQL Server (2601/2627), dùng DbContext mới để đọc lại bản ghi đã commit, xác nhận payload khớp rồi complete. Không nuốt mọi `DbUpdateException` như duplicate. Khi dùng EF Core execution strategy có retry, transaction thủ công phải được thực thi qua strategy tương ứng và phải thiết kế retry an toàn sau kết quả commit không chắc chắn. Lỗi transient khác phải được propagate để Service Bus redeliver. Với `Unknown order`, chỉ DLQ nếu domain xác nhận không thể xuất hiện muộn; nếu event có thể đến trước order, cần retry có giới hạn. Cấu hình processor `AutoCompleteMessages=false`, `MaxConcurrentCalls` theo benchmark và stop/dispose trong `finally`.

## Giải thích thiết kế sau khi sửa

Database unique constraint là tuyến phòng thủ cuối cùng, hoạt động xuyên nhiều process. Transaction bảo vệ ledger và order trong cùng database; broker settlement diễn ra sau commit nên không có distributed atomic transaction. Nếu complete thất bại, redelivery là bình thường và phải được nhận diện như duplicate. Không gửi email/fulfillment trực tiếp trong transaction này; nếu cần downstream event, ghi Outbox trong cùng transaction rồi publish riêng.

## Trade-offs

Unique index tạo chi phí ghi và tranh chấp trên key nóng; đổi lại có bảo đảm correctness. DLQ cần quy trình vận hành và replay; không thể chỉ bỏ qua. Outbox tăng bảng và worker nhưng phù hợp khi cần phát sự kiện sau commit. Không cần Saga hoặc Microservices mới chỉ để xử lý một queue và một SQL database.

## Cách kiểm thử

1. **Concurrency/integration:** Gửi 100 bản sao cùng `PaymentId` qua nhiều worker, xác nhận đúng một ledger row và trạng thái order.
2. **Failure-path:** Kill worker sau SQL commit nhưng trước complete; xác nhận redelivery không tạo bản ghi mới.
3. **Security/validation:** JSON lỗi, amount âm, ID rỗng, payload mâu thuẫn; xác nhận chính sách DLQ/audit.
4. **Database:** Bơm unique-key race, kiểm tra xử lý đúng mã lỗi và so sánh payload.
5. **Load:** Scale 1→4 instance, đo throughput, SQL waits, lock duration và backlog.

## Quan sát trong production

Dùng Application Insights dependency traces cho SQL và Service Bus, correlation qua `PaymentId`/trace context; metrics: `processed`, `duplicate`, `conflict`, `failed`, delivery count, processing duration p95/p99, DLQ count, queue age và SQL deadlocks. Alert nếu DLQ tăng, queue age vượt SLO hoặc ledger reconciliation lệch. Không log thông tin thanh toán nhạy cảm.

## Đoạn code cần review

```sql
CREATE OR ALTER PROCEDURE dbo.GetOrderHistory
    @TenantId uniqueidentifier,
    @Status nvarchar(30) = NULL,
    @FromUtc datetime2 = NULL,
    @ToUtc datetime2 = NULL,
    @Page int = 1,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        o.Id, o.TenantId, o.CreatedAtUtc,
        o.Status, o.TotalAmount,
        c.DisplayName AS CustomerName
    FROM dbo.Orders o
    JOIN dbo.Customers c ON c.Id = o.CustomerId
    WHERE o.TenantId = @TenantId
      AND (@Status IS NULL OR o.Status = @Status)
      AND (@FromUtc IS NULL OR
           CONVERT(date, o.CreatedAtUtc) >= CONVERT(date, @FromUtc))
      AND (@ToUtc IS NULL OR
           CONVERT(date, o.CreatedAtUtc) <= CONVERT(date, @ToUtc))
    ORDER BY o.CreatedAtUtc DESC
    OFFSET (@Page - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;

    SELECT COUNT(*)
    FROM dbo.Orders o
    WHERE o.TenantId = @TenantId
      AND (@Status IS NULL OR o.Status = @Status);
END
```

## Kết quả code review tham khảo

### [High] — Thứ tự không xác định khi timestamp trùng

**Vấn đề:** `ORDER BY CreatedAtUtc DESC` không có tie-breaker.  
**Tại sao xảy ra:** Timestamp không unique.  
**Ảnh hưởng production:** Bản ghi có thể lặp hoặc biến mất giữa các trang ngay cả khi dữ liệu ít thay đổi.  
**Cách sửa:** `ORDER BY CreatedAtUtc DESC, Id DESC`; cursor gồm cả hai giá trị.

### [High] — OFFSET pagination không ổn định khi insert mới

**Vấn đề:** Offset dịch chuyển khi dữ liệu thay đổi.  
**Tại sao xảy ra:** Mỗi request chạy trên snapshot logic khác nhau.  
**Ảnh hưởng production:** Trùng/bỏ sót order trong hành trình duyệt.  
**Cách sửa:** Keyset cursor với điều kiện lexicographic; nếu yêu cầu snapshot nhất quán tuyệt đối qua nhiều request, cần thêm snapshot/as-of contract riêng.

### [High] — Count và list dùng bộ lọc khác nhau

**Vấn đề:** Count bỏ `FromUtc` và `ToUtc`.  
**Tại sao xảy ra:** Hai query không chia sẻ filter contract.  
**Ảnh hưởng production:** UI hiển thị tổng số và số trang sai.  
**Cách sửa:** Đồng bộ predicate; cân nhắc bỏ exact count khỏi đường request nóng hoặc trả count theo yêu cầu riêng.

### [High] — Date conversion thay đổi semantics và giảm khả năng seek

**Vấn đề:** `CONVERT(date, CreatedAtUtc)` biến timestamp thành ngày, và filter `ToUtc` trở thành inclusive theo ngày thay vì theo thời điểm.  
**Tại sao xảy ra:** Hàm áp lên column và làm mất thông tin thời gian.  
**Ảnh hưởng production:** Trả hàng ngoài khoảng yêu cầu; index access có thể kém hiệu quả.  
**Cách sửa:** So sánh trực tiếp `CreatedAtUtc >= @FromUtc AND CreatedAtUtc < @ToUtc` nếu API quy định khoảng half-open; với bộ lọc theo ngày, chuyển ngày địa phương thành UTC boundaries ở application layer.

### [High] — Deep OFFSET scan/sort lớn

**Vấn đề:** SQL phải bỏ qua nhiều hàng trước khi lấy 50 hàng.  
**Tại sao xảy ra:** `OFFSET` tăng theo trang và không tận dụng vị trí cuối của trang trước.  
**Ảnh hưởng production:** CPU, reads, memory grant và latency tăng.  
**Cách sửa:** Keyset pagination kết hợp index phù hợp.

### [Medium] — Optional predicates và parameter sniffing

**Vấn đề:** `(@Status IS NULL OR Status=@Status)` và nhiều filter tùy chọn có thể tạo plan không phù hợp giữa tenant lớn/nhỏ.  
**Tại sao xảy ra:** Cardinality khác biệt; cached plan không luôn phù hợp.  
**Ảnh hưởng production:** P95 dao động mạnh, scan không cần thiết.  
**Cách sửa:** Đo Query Store, actual plans, thử `OPTION(RECOMPILE)` cho truy vấn báo cáo nếu chi phí compile chấp nhận được, hoặc dynamic parameterized SQL/variant chuyên biệt; không áp dụng hint mù quáng.

### [Medium] — Chưa giới hạn input

**Vấn đề:** `@Page <= 0`, `@PageSize` quá lớn hoặc phép nhân offset overflow.  
**Tại sao xảy ra:** Không validate API boundary.  
**Ảnh hưởng production:** Lỗi, request đắt hoặc khai thác tài nguyên.  
**Cách sửa:** Validate page size, filter bounds, cursor, timeouts và rate limits.

### [Medium] — Join và covering index chưa được đánh giá

**Vấn đề:** Join customer trên từng dòng có thể gây lookup lớn nếu plan không tốt.  
**Tại sao xảy ra:** Index và statistics không được cung cấp; không thể kết luận chỉ từ SQL text.  
**Ảnh hưởng production:** Logical reads tăng, blocking khi hệ thống bận.  
**Cách sửa:** Kiểm tra actual execution plan và indexes, đảm bảo `Customers.Id` indexed; lấy page order IDs trước rồi join 50 dòng.

## Phiên bản đề xuất

API đổi sang `GET /orders?limit=50&cursor=...`; cursor được ký/validate, ràng buộc tenant, status, time range và sort. Ví dụ SQL dưới đây cho trường hợp `@Status` optional, `@ToUtc` exclusive, cursor là cặp `(@LastCreatedAtUtc, @LastId)`. `@LastCreatedAtUtc` và `@LastId` phải cùng null hoặc cùng có giá trị.

```sql
CREATE OR ALTER PROCEDURE dbo.GetOrderHistoryCursor
    @TenantId uniqueidentifier,
    @Status nvarchar(30) = NULL,
    @FromUtc datetime2 = NULL,
    @ToUtc datetime2 = NULL,
    @LastCreatedAtUtc datetime2 = NULL,
    @LastId bigint = NULL,
    @Limit int = 50
AS
BEGIN
    SET NOCOUNT ON;
    IF @Limit NOT BETWEEN 1 AND 100
        THROW 50001, 'Invalid limit', 1;
    IF (@LastCreatedAtUtc IS NULL AND @LastId IS NOT NULL)
       OR (@LastCreatedAtUtc IS NOT NULL AND @LastId IS NULL)
        THROW 50002, 'Invalid cursor', 1;
    IF @FromUtc IS NOT NULL AND @ToUtc IS NOT NULL
       AND @FromUtc >= @ToUtc
        THROW 50003, 'Invalid date range', 1;

    ;WITH PageIds AS
    (
        SELECT TOP (@Limit + 1)
            o.Id, o.CustomerId, o.CreatedAtUtc,
            o.TenantId, o.Status, o.TotalAmount
        FROM dbo.Orders o
        WHERE o.TenantId = @TenantId
          AND (@Status IS NULL OR o.Status = @Status)
          AND (@FromUtc IS NULL OR o.CreatedAtUtc >= @FromUtc)
          AND (@ToUtc IS NULL OR o.CreatedAtUtc < @ToUtc)
          AND (@LastCreatedAtUtc IS NULL
            OR o.CreatedAtUtc < @LastCreatedAtUtc
            OR (o.CreatedAtUtc = @LastCreatedAtUtc
                AND o.Id < @LastId))
        ORDER BY o.CreatedAtUtc DESC, o.Id DESC
    )
    SELECT p.Id, p.CreatedAtUtc, p.Status,
           p.TotalAmount, c.DisplayName AS CustomerName
    FROM PageIds p
    JOIN dbo.Customers c ON c.Id = p.CustomerId
    ORDER BY p.CreatedAtUtc DESC, p.Id DESC
    OPTION (RECOMPILE);
END
```

Application trả tối đa `@Limit` item; dòng thứ `limit+1` chỉ để tính `hasNextPage`. Nếu có trang tiếp, tạo cursor từ **item cuối thực sự trả về**, không phải dòng lookahead. Đề xuất index ban đầu để benchmark: `CREATE INDEX IX_Orders_Tenant_Created_Id ON dbo.Orders(TenantId, CreatedAtUtc DESC, Id DESC) INCLUDE (Status, CustomerId, TotalAmount);`. Với truy vấn luôn có status, cân nhắc thêm `(TenantId, Status, CreatedAtUtc DESC, Id DESC)` nhưng chỉ sau khi đo workload và write amplification. `OPTION(RECOMPILE)` là lựa chọn có điều kiện, không phải mặc định bắt buộc. Nếu `Customer` có thể bị xóa, xác minh inner join có đúng semantics không.

## Giải thích thiết kế sau khi sửa

Cursor giữ vị trí theo một total ordering. SQL tìm phần dữ liệu đứng sau vị trí đã trả, không phải bỏ qua hàng trăm nghìn row. Filter dùng UTC half-open để tránh lỗi biên. Index dẫn bằng tenant để giới hạn phạm vi và tiếp theo là sort keys. Keyset tránh dịch chuyển do insert mới đứng trước cursor, nhưng không bảo đảm snapshot bất biến nếu order bị xóa, sửa timestamp hay đổi status; requirement mạnh hơn cần snapshot version hoặc export job.

## Trade-offs

Keyset không hỗ trợ nhảy thẳng tới page N hoặc exact total count miễn phí. Cursor phải được bảo vệ khỏi sửa/đổi filter; ký HMAC và có expiry là một lựa chọn. Covering index tăng storage và write overhead; thêm nhiều index có thể khiến ingestion chậm. Exact count vẫn hợp lý cho báo cáo nhỏ hoặc tác vụ nền; không nên ép mọi request UI tính lại. `OPTION(RECOMPILE)` có thể tăng CPU compile và phải được đánh giá bằng Query Store.

## Cách kiểm thử

1. **Database correctness:** Tạo nhiều order trùng timestamp, duyệt toàn bộ trang và xác nhận mỗi ID xuất hiện đúng một lần khi dataset bất biến.
2. **Concurrency:** Insert order mới giữa hai request; xác nhận không trùng/bỏ sót các hàng cũ chưa duyệt.
3. **Boundary:** Kiểm tra UTC range, null status, cursor không khớp filter, limit 0/101 và tenant isolation.
4. **Load:** Benchmark tenant nhỏ/lớn, trang đầu và trang rất sâu; so sánh logical reads, CPU, p95/p99 và memory grant.
5. **Plan regression:** Dùng Query Store/actual execution plans với status phân bố lệch, kiểm tra index seek/scan, sort và compile CPU.

## Quan sát trong production

Thu request latency p50/p95/p99 theo tenant size bucket (không log PII), SQL duration, logical reads, CPU, waits, spills, Query Store plan changes, deadlocks và connection pool saturation. Theo dõi `hasNextPage`, số item/page và tỷ lệ invalid cursor. Alert khi latency hoặc SQL resource vượt SLO; xác minh bằng execution plan thay vì suy đoán rằng thiếu index.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product yêu cầu export toàn bộ một triệu order nhất quán tại một thời điểm, bạn thay đổi API và snapshot strategy ra sao?
2. Nếu status thay đổi trong lúc duyệt, keyset có còn bảo đảm không bỏ sót mọi order phù hợp hay không?
3. Nếu một tenant chiếm 80% dữ liệu, bạn sẽ đo và quyết định partitioning, index hay tách workload như thế nào?
