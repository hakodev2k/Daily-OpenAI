# Code Review Challenge 1 — Azure Service Bus consumer trừ tồn kho hai lần khi message được giao lại

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, SQL Server, at-least-once delivery, idempotency, message settlement, transaction boundary, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–40 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một e-commerce backend nhận `OrderConfirmed` qua Azure Service Bus để reserve inventory. Service chạy trên nhiều Azure App Service instances. Mỗi message chứa `OrderId` và danh sách SKU/quantity. SQL Server là source of truth cho inventory.

Production đôi lúc ghi nhận cùng một order làm giảm inventory hai lần. Một số incident xảy ra khi SQL đã commit nhưng worker bị restart trước khi message hoàn tất settlement. Khi SQL hoặc dependency chậm, queue backlog tăng và có message được xử lý lại. Team đề xuất tăng `MaxDeliveryCount` và gọi `CompleteMessageAsync` ngay khi bắt đầu handler để “chặn duplicate”.

Business invariant: một `OrderId` chỉ được áp dụng inventory reservation một lần. Nếu xử lý thất bại trước khi transaction commit thì message phải có khả năng retry. Không được giả định Azure Service Bus cung cấp exactly-once execution cho application side effects.

## Đoạn code cần review

```csharp
public sealed class OrderConfirmedConsumer
{
    private readonly InventoryDbContext _db;
    private readonly ILogger<OrderConfirmedConsumer> _logger;

    public OrderConfirmedConsumer(
        InventoryDbContext db,
        ILogger<OrderConfirmedConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var message = JsonSerializer.Deserialize<OrderConfirmed>(
            args.Message.Body)!;

        foreach (var line in message.Lines)
        {
            var inventory = await _db.Inventory
                .SingleAsync(x => x.Sku == line.Sku, cancellationToken);

            if (inventory.AvailableQuantity < line.Quantity)
                throw new InvalidOperationException(
                    $"Insufficient inventory for {line.Sku}");

            inventory.AvailableQuantity -= line.Quantity;

            _db.InventoryMovements.Add(new InventoryMovement
            {
                Id = Guid.NewGuid(),
                OrderId = message.OrderId,
                Sku = line.Sku,
                Quantity = -line.Quantity,
                CreatedAtUtc = DateTime.UtcNow
            });
        }

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Reserved inventory for order {OrderId}, message {MessageId}",
            message.OrderId,
            args.Message.MessageId);

        await args.CompleteMessageAsync(args.Message, cancellationToken);
    }
}
```

## Câu hỏi gợi mở

1. Nếu `SaveChangesAsync` thành công nhưng process chết trước `CompleteMessageAsync`, lần delivery tiếp theo sẽ làm gì?
2. `MessageId` và `OrderId` nên đóng vai trò gì trong idempotency boundary?
3. Nếu hai delivery của cùng order chạy đồng thời trên hai instances thì check idempotency ở application memory có đủ không?
4. Việc hoàn tất message trước khi SQL commit sẽ đổi failure mode thành gì?
5. Khi inventory không đủ là transient failure hay business-terminal failure, và settlement/DLQ policy nên khác nhau thế nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **at-least-once delivery + non-atomic side effect**. Hãy tìm invariant có thể enforce trong cùng SQL transaction.

### Gợi ý 2

Một check kiểu “đã xử lý chưa?” chỉ an toàn khi chính database bảo vệ nó trước concurrent consumers. Hãy nghĩ tới unique constraint/inbox record và transaction boundary.

## Kết quả code review tham khảo

### Critical — Handler không idempotent khi message được giao lại

**Vấn đề:** Mỗi lần handler chạy đều decrement inventory và thêm movement mới.  
**Tại sao xảy ra:** Service Bus settlement và SQL commit là hai operation độc lập. Nếu SQL commit xong nhưng message chưa được complete, message có thể được giao lại.  
**Ảnh hưởng production:** Cùng order có thể reserve inventory nhiều lần, làm sai tồn kho.  
**Cách sửa:** Enforce idempotency trong SQL bằng inbox/processed-message hoặc business key như `OrderId`, với unique constraint và update inventory trong cùng transaction với idempotency record.

### Critical — Không bảo vệ concurrent duplicate delivery ở database

**Vấn đề:** Hai consumers có thể đồng thời xử lý cùng business event trước khi một consumer complete message.  
**Tại sao xảy ra:** Không có unique database constraint hoặc atomic claim cho `OrderId`.  
**Ảnh hưởng production:** Race condition vẫn có thể double-decrement ngay cả khi application thêm một `SELECT` kiểm tra trước.  
**Cách sửa:** Tạo unique key, ví dụ `ProcessedMessages(Consumer, BusinessKey)` hoặc unique `InventoryReservation.OrderId`, và thực hiện insert idempotency marker + inventory mutation trong một SQL transaction.

### High — Read-modify-write inventory có concurrency risk độc lập với duplicate message

**Vấn đề:** `AvailableQuantity` được đọc rồi sửa trên tracked entity mà không có concurrency protection.  
**Tại sao xảy ra:** Nhiều order khác nhau có thể reserve cùng SKU đồng thời.  
**Ảnh hưởng production:** Lost update hoặc oversell tùy concurrency behavior/schema.  
**Cách sửa:** Dùng optimistic concurrency token với bounded retry hoặc atomic conditional update đảm bảo `AvailableQuantity >= requested`; giữ multi-line order trong transaction phù hợp.

### High — Không có explicit transaction cho toàn bộ business operation

**Vấn đề:** Code dựa vào một `SaveChangesAsync`, nhưng thiết kế idempotency cần transaction boundary rõ ràng giữa processed marker, inventory mutation và movement.  
**Tại sao xảy ra:** Message settlement không thể tham gia tự động vào SQL transaction này.  
**Ảnh hưởng production:** Nếu fix idempotency bằng nhiều `SaveChanges` rời rạc, có thể tạo trạng thái nửa vời.  
**Cách sửa:** Một local DB transaction ngắn cho toàn bộ SQL state transition; chỉ complete message sau commit.

### High — Không phân loại business failure và transient failure

**Vấn đề:** `Insufficient inventory` được throw giống lỗi hạ tầng.  
**Tại sao xảy ra:** Handler không có failure taxonomy.  
**Ảnh hưởng production:** Message business-invalid có thể retry nhiều lần vô ích, tăng delivery count/backlog rồi vào DLQ mà thiếu ngữ nghĩa.  
**Cách sửa:** Xác định policy: terminal business outcome có thể persist/reject/dead-letter với reason phù hợp; transient SQL/network failure thì abandon/retry theo policy.

### High — Deserialize không validate contract

**Vấn đề:** Dùng null-forgiving operator và không validate `OrderId`, empty lines, duplicate SKU, quantity <= 0.  
**Tại sao xảy ra:** Tin message contract tuyệt đối.  
**Ảnh hưởng production:** Poison message hoặc dữ liệu bất hợp lệ có thể gây exception/retry loop hay tăng inventory nếu quantity âm.  
**Cách sửa:** Validate schema/business invariants trước mutation; normalize duplicate SKU; xử lý poison message có chủ đích.

### Medium — `MaxConcurrentCalls = 16` không gắn với DB capacity

**Vấn đề:** Concurrency được cấu hình cố định mà không có evidence.  
**Tại sao xảy ra:** Processor throughput và SQL connection/lock capacity chưa được đo cùng nhau.  
**Ảnh hưởng production:** Có thể tăng contention, connection pressure và lock renewal risk khi downstream chậm.  
**Cách sửa:** Load test, đo queue throughput, DB waits/connection pool và handler duration trước khi tune concurrency.

### Medium — Log chưa đủ để điều tra delivery lifecycle

**Vấn đề:** Chỉ log success với `OrderId` và `MessageId`.  
**Tại sao xảy ra:** Không ghi delivery count, processing outcome, duration, idempotent replay hoặc settlement failure.  
**Ảnh hưởng production:** Khó chứng minh duplicate đến từ redelivery, concurrent processing hay producer duplication.  
**Cách sửa:** Structured telemetry với business key, message ID, delivery count, processing result, duplicate flag, SQL duration và settlement outcome; tránh log payload nhạy cảm.

### Medium — Settlement failure sau commit cần được coi là expected ambiguity

**Vấn đề:** `CompleteMessageAsync` có thể fail dù business transaction đã commit.  
**Tại sao xảy ra:** Network/service failure ở bước settlement.  
**Ảnh hưởng production:** Redelivery là khả năng bình thường; nếu handler không idempotent sẽ thành data corruption.  
**Cách sửa:** Thiết kế replay-safe; không cố “fix” bằng complete trước commit.

### Low — `DateTime.UtcNow` rải trực tiếp làm test khó hơn

**Vấn đề:** Clock không injectable.  
**Tại sao xảy ra:** Domain timestamp lấy trực tiếp từ static clock.  
**Ảnh hưởng production:** Không phải lỗi correctness chính, nhưng làm deterministic testing khó hơn.  
**Cách sửa:** Dùng `TimeProvider` khi cần kiểm soát thời gian trong test.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa idempotency bằng business key. Schema cần có unique constraint trên `ProcessedOrderMessages.OrderId` cho consumer này và concurrency strategy phù hợp cho inventory.

```csharp
public async Task HandleAsync(
    ProcessMessageEventArgs args,
    CancellationToken cancellationToken)
{
    OrderConfirmed message;

    try
    {
        message = JsonSerializer.Deserialize<OrderConfirmed>(args.Message.Body)
            ?? throw new JsonException("Message body is null.");

        Validate(message);
    }
    catch (Exception ex) when (ex is JsonException or ValidationException)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "InvalidContract",
            ex.Message,
            cancellationToken);
        return;
    }

    await using var tx = await _db.Database
        .BeginTransactionAsync(cancellationToken);

    try
    {
        _db.ProcessedOrderMessages.Add(new ProcessedOrderMessage
        {
            OrderId = message.OrderId,
            MessageId = args.Message.MessageId,
            ProcessedAtUtc = _timeProvider.GetUtcNow().UtcDateTime
        });

        foreach (var line in NormalizeLines(message.Lines))
        {
            var affected = await _db.Database.ExecuteSqlInterpolatedAsync($@"
                UPDATE Inventory
                SET AvailableQuantity = AvailableQuantity - {line.Quantity}
                WHERE Sku = {line.Sku}
                  AND AvailableQuantity >= {line.Quantity}", cancellationToken);

            if (affected != 1)
                throw new InsufficientInventoryException(line.Sku);

            _db.InventoryMovements.Add(new InventoryMovement
            {
                Id = Guid.NewGuid(),
                OrderId = message.OrderId,
                Sku = line.Sku,
                Quantity = -line.Quantity,
                CreatedAtUtc = _timeProvider.GetUtcNow().UtcDateTime
            });
        }

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }
    catch (DbUpdateException ex) when (IsProcessedOrderUniqueViolation(ex))
    {
        await tx.RollbackAsync(CancellationToken.None);

        _logger.LogInformation(
            "Idempotent replay ignored for order {OrderId}, message {MessageId}",
            message.OrderId,
            args.Message.MessageId);
    }
    catch (InsufficientInventoryException ex)
    {
        await tx.RollbackAsync(CancellationToken.None);

        await args.DeadLetterMessageAsync(
            args.Message,
            "InsufficientInventory",
            ex.Message,
            cancellationToken);
        return;
    }

    await args.CompleteMessageAsync(args.Message, cancellationToken);
}
```

Đây là một design option, không phải API/schema duy nhất. Nếu cùng `OrderId` có nhiều event version hợp lệ, idempotency key phải phản ánh event identity/version thay vì khóa toàn bộ `OrderId`. Nếu producer có thể gửi các event khác nhau cho cùng order, cần xác minh contract trước khi chọn unique key.

## Giải thích thiết kế sau khi sửa

Database chịu trách nhiệm bảo vệ invariant vì application chạy nhiều instances. Insert idempotency marker, inventory update và movement cùng nằm trong local SQL transaction. Message chỉ được complete sau commit. Nếu process chết sau commit, redelivery sẽ đụng unique constraint và trở thành replay không gây side effect lần hai.

Atomic conditional update bảo vệ quantity khỏi xuống dưới mức cho phép mà không cần giữ entity read-modify-write không được bảo vệ. Với nhiều SKU, transaction đảm bảo nếu một SKU không đủ thì các update trước đó rollback.

## Trade-offs

Inbox/idempotency table tăng storage và cần retention strategy. Unique key theo `OrderId` đơn giản nhưng có thể quá coarse nếu domain có nhiều event hợp lệ cho cùng order. Atomic SQL update giảm race nhưng tăng coupling với database-specific behavior. Transaction nhiều SKU có thể tăng lock contention; cần consistent ordering của SKU và retry policy cho deadlock/transient DB errors. Không nên mở transaction trong lúc gọi external dependency.

## Cách kiểm thử

1. **Concurrency integration test:** gửi cùng event đồng thời qua hai `DbContext`/consumer instances; assert chỉ một inventory mutation được commit.
2. **Failure-path test:** commit SQL rồi mô phỏng settlement failure; chạy lại message và assert inventory không giảm lần hai.
3. **Database test:** hai order khác nhau cạnh tranh SKU quantity = 1; assert tối đa một reservation thành công và quantity không âm.
4. **Contract/security test:** quantity âm/0, duplicate SKU, malformed JSON và oversized/unexpected payload không gây mutation.
5. **E2E test:** transient SQL failure rồi retry thành công; kiểm tra delivery count, DLQ policy và telemetry correlation.

## Quan sát trong production

Theo dõi queue active-message count, dead-letter count, delivery count distribution, processing duration, settlement failures, duplicate/idempotent replay count, SQL dependency latency, deadlocks, lock waits, connection-pool pressure và inventory business-conflict rate. Correlate `OrderId`, `MessageId` và trace ID trong Application Insights nhưng không log toàn bộ payload nếu chứa dữ liệu nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu producer phát hai event hợp lệ cho cùng `OrderId`, bạn thiết kế idempotency key/versioning thế nào?
2. Azure Service Bus duplicate detection có thay thế application-level idempotency cho SQL side effect không? Vì sao?
3. Nếu transaction inventory kéo dài và message lock gần hết hạn, bạn sẽ điều tra và thiết kế lại flow ra sao?

# Code Review Challenge 2 — React search hiển thị kết quả cũ và tạo request storm khi người dùng gõ nhanh

**Chủ đề:** React, TypeScript, browser fetch, async race condition, request cancellation, XSS, frontend observability, API integration  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal product-search portal dùng React + TypeScript gọi ASP.NET Core search API. Người dùng thường gõ nhanh 5–10 ký tự, thay đổi category và chuyển trang liên tục. API search có p95 khoảng vài trăm ms nhưng đôi lúc request cũ mất 2–3 giây do Elasticsearch downstream chậm.

Support báo UI đôi lúc hiển thị kết quả của query trước dù ô search đang chứa query mới. Backend thấy request rate tăng mạnh theo số keystroke. Khi component unmount hoặc user chuyển màn hình, các request cũ vẫn tiếp tục chạy. API trả về `highlightHtml` chứa đoạn text đã highlight từ search service; frontend render trực tiếp để giữ thẻ `<em>`.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type SearchItem = {
  id: string;
  name: string;
  highlightHtml: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [items, setItems] = useState<SearchItem[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    setLoading(true);
    setError(null);

    fetch(
      `/api/products/search?q=${query}&category=${category}&page=${page}`
    )
      .then((response) => response.json())
      .then((data) => {
        setItems(data.items);
        setLoading(false);
      })
      .catch((err) => {
        setError(err.message);
        setLoading(false);
      });
  }, [query, category, page]);

  return (
    <section>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Search products"
      />

      <select
        value={category}
        onChange={(e) => setCategory(e.target.value)}
      >
        <option value="all">All</option>
        <option value="cars">Cars</option>
        <option value="parts">Parts</option>
      </select>

      {loading && <div>Loading...</div>}
      {error && <div>{error}</div>}

      {items.map((item) => (
        <article key={item.id}>
          <h3>{item.name}</h3>
          <div
            dangerouslySetInnerHTML={{ __html: item.highlightHtml }}
          />
        </article>
      ))}
    </section>
  );
}
```

## Kết quả code review tham khảo

### Critical — Render HTML không đáng tin cậy bằng `dangerouslySetInnerHTML`

**Vấn đề:** `highlightHtml` từ API/search pipeline được đưa trực tiếp vào DOM.  
**Tại sao xảy ra:** Frontend giả định HTML từ backend/search index đã được sanitize đúng.  
**Ảnh hưởng production:** Nếu dữ liệu nguồn hoặc highlight pipeline có thể chứa attacker-controlled markup, đây có thể trở thành XSS.  
**Cách sửa:** Ưu tiên API trả structured highlight fragments/text để React escape mặc định; nếu business bắt buộc HTML, sanitize bằng cơ chế được review rõ ràng ở trust boundary và áp dụng CSP defense-in-depth.

### High — Response cũ có thể ghi đè kết quả mới

**Vấn đề:** Mọi request completion đều gọi `setItems`.  
**Tại sao xảy ra:** Network completion order không đảm bảo giống request start order.  
**Ảnh hưởng production:** Ô search hiển thị query mới nhưng kết quả thuộc query cũ, tạo lỗi correctness khó tái hiện.  
**Cách sửa:** Abort request cũ trong effect cleanup và/hoặc dùng request generation/token để chỉ latest request được phép commit state.

### High — Không hủy request khi dependency thay đổi/unmount

**Vấn đề:** Effect không trả cleanup function.  
**Tại sao xảy ra:** `fetch` không tự gắn với React lifecycle.  
**Ảnh hưởng production:** Work không còn cần vẫn tiêu tốn browser connection, backend capacity và Elasticsearch resources.  
**Cách sửa:** Tạo `AbortController` cho mỗi effect và abort trong cleanup; backend cũng cần propagate request cancellation tới downstream khi phù hợp.

### High — Gọi API trên mọi keystroke

**Vấn đề:** Mỗi thay đổi `query` tạo request ngay.  
**Tại sao xảy ra:** Không có debounce/minimum-query policy.  
**Ảnh hưởng production:** Request storm làm tăng load, chi phí search và latency tail; càng chậm càng tích lũy nhiều in-flight request.  
**Cách sửa:** Debounce input theo UX requirement, có minimum query length nếu phù hợp và vẫn giữ cancellation/latest-response protection.

### High — Không kiểm tra `response.ok`

**Vấn đề:** HTTP 4xx/5xx vẫn đi vào `response.json()` và có thể được xử lý như success nếu body parse được.  
**Tại sao xảy ra:** `fetch` không reject promise chỉ vì HTTP status là error.  
**Ảnh hưởng production:** UI có thể set state sai hoặc phát sinh lỗi parse không phản ánh nguyên nhân thực.  
**Cách sửa:** Kiểm tra `response.ok`; map lỗi có cấu trúc từ API và phân biệt abort với genuine failure.

### Medium — Loading state có race condition

**Vấn đề:** Request cũ hoàn thành có thể gọi `setLoading(false)` trong khi request mới vẫn chạy.  
**Tại sao xảy ra:** Một boolean dùng chung cho nhiều concurrent operations.  
**Ảnh hưởng production:** Spinner biến mất quá sớm, UI cho cảm giác đã hoàn tất dù latest query chưa xong.  
**Cách sửa:** Chỉ latest request được update loading/error hoặc model state theo request generation.

### Medium — Query parameters không được encode an toàn

**Vấn đề:** Chuỗi URL ghép trực tiếp từ input.  
**Tại sao xảy ra:** Không dùng `URLSearchParams`.  
**Ảnh hưởng production:** Ký tự `&`, `?`, unicode hoặc giá trị đặc biệt có thể làm sai request semantics.  
**Cách sửa:** Dùng `URLSearchParams`/URL API.

### Medium — Thay filter nhưng không reset pagination

**Vấn đề:** Nếu user đang ở page lớn rồi đổi query/category, page cũ vẫn được gửi.  
**Tại sao xảy ra:** State transitions không encode UX invariant.  
**Ảnh hưởng production:** User có thể thấy empty result dù query mới có dữ liệu ở page 1.  
**Cách sửa:** Reset page về 1 khi query/category thay đổi hoặc thiết kế reducer/state machine tránh inconsistent combinations.

### Medium — Hiển thị raw error message cho user

**Vấn đề:** `err.message` được render trực tiếp. React sẽ escape text, nên đây không phải XSS như HTML injection ở trên, nhưng message có thể không phù hợp UX hoặc làm lộ technical detail nếu wrapper đưa server detail vào Error.  
**Tại sao xảy ra:** Không có error mapping.  
**Ảnh hưởng production:** UX không nhất quán và có thể expose implementation detail.  
**Cách sửa:** Log/capture technical detail trong telemetry; UI hiển thị message an toàn, actionable.

## Phiên bản đề xuất

```tsx
import { useEffect, useMemo, useRef, useState } from "react";

type SearchItem = {
  id: string;
  name: string;
  highlightText: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [items, setItems] = useState<SearchItem[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const [debouncedQuery, setDebouncedQuery] = useState(query);
  const requestVersion = useRef(0);

  useEffect(() => {
    const timer = window.setTimeout(() => setDebouncedQuery(query), 300);
    return () => window.clearTimeout(timer);
  }, [query]);

  const searchParams = useMemo(() => {
    return new URLSearchParams({
      q: debouncedQuery,
      category,
      page: String(page)
    });
  }, [debouncedQuery, category, page]);

  useEffect(() => {
    const controller = new AbortController();
    const version = ++requestVersion.current;

    async function load() {
      setLoading(true);
      setError(null);

      try {
        const response = await fetch(
          `/api/products/search?${searchParams.toString()}`,
          { signal: controller.signal }
        );

        if (!response.ok)
          throw new Error(`Search failed with status ${response.status}`);

        const data = await response.json() as { items: SearchItem[] };

        if (version === requestVersion.current)
          setItems(data.items);
      } catch (error) {
        if (controller.signal.aborted)
          return;

        if (version === requestVersion.current)
          setError("Search is temporarily unavailable.");
      } finally {
        if (version === requestVersion.current)
          setLoading(false);
      }
    }

    void load();
    return () => controller.abort();
  }, [searchParams]);

  function onQueryChange(value: string) {
    setPage(1);
    setQuery(value);
  }

  function onCategoryChange(value: string) {
    setPage(1);
    setCategory(value);
  }

  return (
    <section>
      <input
        value={query}
        onChange={(e) => onQueryChange(e.target.value)}
        placeholder="Search products"
      />

      <select
        value={category}
        onChange={(e) => onCategoryChange(e.target.value)}
      >
        <option value="all">All</option>
        <option value="cars">Cars</option>
        <option value="parts">Parts</option>
      </select>

      {loading && <div>Loading...</div>}
      {error && <div>{error}</div>}

      {items.map((item) => (
        <article key={item.id}>
          <h3>{item.name}</h3>
          <div>{item.highlightText}</div>
        </article>
      ))}
    </section>
  );
}
```

`300 ms` ở đây chỉ là scenario value minh họa, không phải universal best value. Cần tune dựa trên UX, request cost và measurement. Nếu product requirement bắt buộc giữ rich highlight HTML, API contract và sanitization phải được thiết kế riêng thay vì đổi thành `highlightText` như ví dụ.

## Giải thích thiết kế sau khi sửa

Debounce giảm số request phát sinh. `AbortController` dừng request không còn cần ở browser side. `requestVersion` là lớp bảo vệ correctness để stale completion không commit state ngay cả khi cancellation không ngăn được mọi race tại boundary. `URLSearchParams` đảm bảo query serialization đúng. Response status được kiểm tra rõ ràng.

Quan trọng hơn, thiết kế bỏ raw HTML khỏi contract mẫu. React text rendering escape dữ liệu theo mặc định, giảm trust surface. Nếu backend cần highlight chính xác, có thể trả structured segments như `{ text, highlighted }[]` để frontend render `<em>` mà không nhận arbitrary HTML.

## Trade-offs

Debounce làm tăng một khoảng delay trước khi search bắt đầu; quá dài sẽ làm UX chậm, quá ngắn ít giảm load. Abort request ở browser không đảm bảo downstream server đã dừng ngay nếu backend không propagate cancellation. Request generation tăng một ít state complexity nhưng bảo vệ correctness. Structured highlight contract phức tạp hơn plain HTML nhưng có security boundary rõ hơn.

Nếu search UX cần cache client-side, thư viện data-fetching có thể hữu ích, nhưng không nên thêm abstraction chỉ để né hiểu lifecycle/race; cache key, stale policy và cancellation semantics vẫn phải đúng.

## Cách kiểm thử

1. **Frontend async test:** mock request `car` hoàn thành sau `cars`; assert UI cuối cùng chỉ hiển thị `cars`.
2. **Cancellation test:** đổi query/unmount và assert request cũ nhận abort signal; backend integration có thể kiểm tra request cancellation propagation riêng.
3. **Load/browser test:** mô phỏng gõ nhanh, đo số request thực tế và in-flight concurrency sau debounce.
4. **Security test:** backend trả payload chứa `<img onerror=...>`/script-like markup; assert UI không execute HTML với structured text contract.
5. **E2E Playwright:** gõ nhanh, đổi category/page, inject delayed API responses và xác minh loading/error/result state đúng.

## Quan sát trong production

Frontend nên thu thập search duration, aborted request count, error rate và correlation/trace ID khi phù hợp. Browser network waterfall giúp xác minh request storm và stale in-flight calls. Backend/Application Insights theo dõi request count per user/session aggregate, p95/p99, cancellation, Elasticsearch dependency duration/failure và query volume. Không log raw search terms nếu chúng có thể chứa dữ liệu nhạy cảm mà chưa có privacy policy phù hợp.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend không dừng Elasticsearch query khi browser abort, bạn sẽ trace cancellation qua ASP.NET Core và dependency layer thế nào?
2. Debounce, throttle và server-side rate limiting giải quyết các vấn đề khác nhau ra sao trong search UX này?
3. Nếu product bắt buộc trả highlight HTML từ Elasticsearch, bạn thiết kế trust/sanitization boundary và CSP như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với Azure Service Bus, retry/redelivery phải được thiết kế cùng idempotency; SQL side effect không trở thành exactly-once chỉ vì message có `MessageId` hoặc vì handler gọi `CompleteMessageAsync`.
- Business invariant chạy trên nhiều instances cần được bảo vệ ở shared durable boundary, thường bằng database constraint/transaction thay vì in-memory flag.
- Frontend async request có thể hoàn thành khác thứ tự khởi chạy; cancellation và latest-response protection là hai cơ chế liên quan nhưng không hoàn toàn thay thế nhau.
- `dangerouslySetInnerHTML` biến HTML contract thành security boundary; structured data + React escaping thường an toàn và dễ reason hơn.
- Performance fix phải dựa trên evidence: queue telemetry, SQL contention, browser waterfall, request volume và dependency latency.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency và xác định failure window trước/sau commit.
- Đưa invariant vào shared durable boundary khi hệ thống chạy nhiều instances.
- Tách “giảm work”, “hủy work cũ” và “ngăn stale result commit” thành ba vấn đề khác nhau.
- Treat external input và HTML như untrusted data cho tới khi trust boundary được chứng minh.
- Test failure path và concurrency bằng cách chủ động tạo đúng race/failure thay vì chỉ test happy path.
