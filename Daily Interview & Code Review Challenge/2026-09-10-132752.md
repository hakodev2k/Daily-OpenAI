# Câu 1 — Hai request cùng sửa một bản ghi nhưng không block nhau như team nghĩ: PostgreSQL MVCC và isolation thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** PostgreSQL, MVCC, transaction isolation, concurrent updates, lost update, row locking, optimistic concurrency, SQL, EF Core, production verification

## Bối cảnh

Một ASP.NET Core .NET 8 API dùng PostgreSQL để quản lý inventory reservation. Mỗi row trong bảng `inventory` có:

```sql
CREATE TABLE inventory
(
    product_id uuid PRIMARY KEY,
    available_quantity integer NOT NULL,
    updated_at_utc timestamptz NOT NULL
);
```

Business flow hiện tại đọc số lượng còn lại rồi tính giá trị mới ở application:

```csharp
public async Task<bool> ReserveAsync(
    Guid productId,
    int quantity,
    CancellationToken cancellationToken)
{
    await using var tx = await _db.Database.BeginTransactionAsync(cancellationToken);

    var item = await _db.Inventory
        .SingleAsync(x => x.ProductId == productId, cancellationToken);

    if (item.AvailableQuantity < quantity)
        return false;

    item.AvailableQuantity -= quantity;

    await _db.SaveChangesAsync(cancellationToken);
    await tx.CommitAsync(cancellationToken);

    return true;
}
```

Trong load test, hai request gần như đồng thời reserve cùng product. Team kỳ vọng transaction tự động khiến request thứ hai “đọc sau request thứ nhất”, nhưng đôi lúc business log cho thấy cả hai request đều vượt qua kiểm tra quantity mặc dù tổng lượng reserve vượt tồn kho ban đầu.

Một số dữ kiện:

- database đang dùng isolation mặc định của application/provider;
- chưa có concurrency token/version column;
- không có explicit `SELECT ... FOR UPDATE`;
- một developer đề xuất chuyển tất cả transaction lên `SERIALIZABLE`;
- một developer khác muốn dùng distributed lock bằng Redis;
- chưa có bằng chứng xác nhận anomaly cụ thể là lost update, write skew, retry bug hay log correlation sai;
- hệ thống có nhiều application instances;
- cùng một product có thể trở thành “hot row” trong flash-sale traffic.

## Câu hỏi chính

Hãy giải thích **MVCC trong PostgreSQL cho phép concurrent transactions nhìn dữ liệu như thế nào**, vì sao “đã mở transaction” không đồng nghĩa mọi read đều khóa row cho tới commit, và những race condition nào có thể xảy ra trong read-check-modify-write flow trên. Sau đó trình bày cách bạn xác minh anomaly thực tế và so sánh các hướng sửa như atomic SQL update, row locking, optimistic concurrency và mức isolation cao hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Isolation level thực tế của transaction là gì, và application/provider có retry transaction nào tự động không?
2. Requirement chính xác là không bao giờ cho `available_quantity` xuống dưới 0, hay còn invariant xuyên nhiều rows/tables?
3. Có bao nhiêu concurrent reservations cho cùng một `product_id` ở peak và thời gian transaction trung bình là bao nhiêu?
4. Khi hai request cùng chạy, SQL statements thực tế và số rows affected của mỗi update là gì?
5. Reservation có thể retry từ client/message consumer hay không, và request có idempotency key không?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt **snapshot/read visibility** với **row-level write locking**. Transaction boundary không tự biến một `SELECT` thường thành pessimistic lock.

### Gợi ý 2

Nếu invariant có thể được biểu diễn trực tiếp trong một atomic database statement, hãy đánh giá giải pháp đó trước khi thêm distributed coordination.

### Gợi ý 3

Đừng kết luận từ business log. Reproduce bằng hai database sessions, capture SQL thực tế và quan sát rows affected/locks/transaction outcome.

## Cấu trúc trả lời đề xuất

1. Làm rõ invariant và isolation level.
2. Giải thích MVCC/read snapshot ở mức cần thiết.
3. Phân biệt read visibility với write conflict/row locking.
4. Vẽ timeline hai concurrent transactions.
5. Liệt kê các anomaly khả dĩ và evidence để phân biệt.
6. Ưu tiên giải pháp giữ invariant gần database.
7. So sánh atomic update, `FOR UPDATE`, optimistic concurrency và stronger isolation.
8. Xem xét contention/hot-row throughput.
9. Thiết kế concurrency/load tests.
10. Bổ sung telemetry cho conflicts, retries và latency.

## Ý chính của câu trả lời tốt

### Bắt buộc

- PostgreSQL dùng MVCC để cho transactions đọc một version dữ liệu phù hợp với snapshot/statement semantics thay vì mặc định khóa mọi row được đọc.
- Một `SELECT` thông thường không có nghĩa row bị giữ exclusive lock để ngăn transaction khác đọc hoặc chuẩn bị update.
- Transaction chỉ định atomic boundary; nó không tự biến read-check-write ở application thành một atomic predicate update.
- Hai requests có thể cùng đọc một giá trị cũ trước khi một trong hai commit, nên business check trong application cần được thiết kế có concurrency semantics rõ ràng.
- Phải xác minh exact SQL do EF Core tạo ra, transaction isolation và rows affected trước khi gọi lỗi là “lost update”.
- Redis distributed lock không phải lựa chọn mặc định nếu invariant nằm trên một row trong cùng PostgreSQL database.
- Chuyển mọi transaction sang `SERIALIZABLE` có chi phí và có thể yêu cầu xử lý serialization failures/retries; không nên dùng như nút “fix concurrency” chung.

### Điểm cộng

- Đề xuất atomic conditional update như `UPDATE ... SET available_quantity = available_quantity - @q WHERE product_id = @id AND available_quantity >= @q`, rồi kiểm tra affected rows.
- Với workflow cần đọc nhiều dữ liệu trước khi quyết định, cân nhắc `SELECT ... FOR UPDATE` trong transaction để serialize writers trên row tương ứng.
- Có thể dùng optimistic concurrency/version token để phát hiện state đã thay đổi giữa read và update, rồi reject/retry theo business semantics.
- Nhận ra hot row có thể trở thành serialization point dù correctness đúng; cần đo lock wait/p95/p99 và throughput.
- Tách idempotency của request khỏi concurrency control: một retry duplicate vẫn có thể reserve hai lần nếu không có business idempotency.

### Senior+

- Nhận ra lựa chọn concurrency strategy phụ thuộc invariant scope: single-row invariant khác multi-row aggregate invariant.
- Biết stronger isolation không loại bỏ nhu cầu application xử lý transaction abort/retry.
- Tránh giữ row lock qua external API/network call để không kéo dài contention window.
- Đề xuất explicit constraint/check khi phù hợp như `CHECK (available_quantity >= 0)` như defense-in-depth, nhưng không coi constraint là toàn bộ business workflow.
- Phân biệt correctness guarantee với fairness/throughput trong flash-sale hot-key workload.

## Hướng giải quyết tham khảo

Điểm cần sửa đầu tiên trong mental model là: **transaction không đồng nghĩa pessimistic lock cho mọi read**.

PostgreSQL sử dụng MVCC, nên một transaction có thể đọc một version của row mà không chặn các readers khác theo cách một global read lock sẽ làm. Exact visibility phụ thuộc isolation level và statement/transaction snapshot semantics. Vì vậy hai transactions có thể bắt đầu gần nhau và đều quan sát `available_quantity = 5` trước khi business logic ở application trừ đi quantity.

Không nên mô tả anomaly cụ thể mà chưa xem SQL thực tế. EF Core thường tạo `UPDATE` dựa trên key và các concurrency predicates nếu được cấu hình. Nếu không có concurrency token, application có thể không có predicate để phát hiện rằng state dùng cho business calculation đã thay đổi.

Một cách tránh read-check-write race cho single-row inventory là đưa predicate và mutation vào cùng statement:

```sql
UPDATE inventory
SET available_quantity = available_quantity - @quantity,
    updated_at_utc = now()
WHERE product_id = @product_id
  AND available_quantity >= @quantity;
```

Sau đó application kiểm tra số rows affected:

```csharp
var affected = await _db.Database.ExecuteSqlInterpolatedAsync($"""
    UPDATE inventory
    SET available_quantity = available_quantity - {quantity},
        updated_at_utc = now()
    WHERE product_id = {productId}
      AND available_quantity >= {quantity}
    """, cancellationToken);

return affected == 1;
```

Database thực hiện predicate và update như một mutation, nên request thua contention sẽ không còn thỏa điều kiện sau khi concurrent update được resolve. Exact behavior vẫn cần được load-test với provider/version thực tế.

Nếu business logic cần nhiều reads trước khi quyết định, pessimistic row lock có thể phù hợp:

```sql
BEGIN;

SELECT available_quantity
FROM inventory
WHERE product_id = @product_id
FOR UPDATE;

-- validate and update

COMMIT;
```

Trade-off là concurrent writers cho cùng row phải chờ. Nếu transaction thực hiện thêm HTTP calls hoặc work chậm trong lúc giữ lock, tail latency có thể tăng mạnh.

Optimistic concurrency là hướng khác. Có thể thêm version/concurrency token và update chỉ khi version vẫn đúng. Nếu `0 rows affected`, application biết state đã đổi và có thể return conflict hoặc retry nếu operation an toàn/idempotent. Đây thường là lựa chọn tốt khi conflicts hiếm; nếu hot row conflict liên tục, retry storm có thể tốn kém.

`SERIALIZABLE` phù hợp khi invariant phức tạp hơn và muốn database phát hiện một số serialization anomalies, nhưng application phải chấp nhận transaction có thể abort và implement bounded retry. Dùng nó cho toàn hệ thống mà không đo contention/latency có thể làm throughput và operational behavior xấu đi.

Redis lock chưa được justify ở đây: source of truth và invariant đang nằm trong PostgreSQL. Thêm Redis tạo thêm failure mode như lock expiry, network partition, ownership/release semantics và coordination giữa hai stores. Distributed lock chỉ nên xuất hiện khi requirement thực sự vượt local database transaction boundary và failure model được xử lý.

Kế hoạch verify:

1. bật/capture SQL command telemetry cho flow này;
2. log correlation ID, product ID, requested quantity, rows affected và transaction outcome;
3. reproduce bằng hai sessions với barriers để ép interleaving;
4. kiểm tra `pg_stat_activity`, lock waits và database telemetry trong test/incident;
5. chạy concurrency test hàng trăm operations vào cùng product và kiểm tra invariant cuối;
6. test client retry/message redelivery riêng để xác nhận idempotency;
7. đo p95/p99 khi contention tăng để chọn pessimistic hay optimistic/atomic strategy.

Tài liệu chính thức cần đối chiếu khi triển khai:

- PostgreSQL — Transaction Isolation: `https://www.postgresql.org/docs/current/transaction-iso.html`
- PostgreSQL — Explicit Locking: `https://www.postgresql.org/docs/current/explicit-locking.html`

## Mẫu trả lời trong phỏng vấn

“Em sẽ không giả định transaction khiến request thứ hai đọc sau request thứ nhất. PostgreSQL dùng MVCC; một SELECT thường đọc version phù hợp với snapshot semantics và không tự khóa row theo kiểu pessimistic. Vì vậy read-check-modify ở application không phải một atomic operation chỉ vì nằm trong transaction.

Em sẽ lấy exact SQL và isolation level, reproduce bằng hai sessions và xem rows affected để biết anomaly thật là gì. Với invariant đơn giản `available_quantity >= quantity`, em ưu tiên atomic conditional UPDATE trong database rồi kiểm tra một row có được update hay không. Nếu business cần đọc nhiều state trước khi update thì có thể dùng `FOR UPDATE`, nhưng phải giữ transaction ngắn. Optimistic version token cũng hợp lý khi conflicts hiếm.

Em không bật SERIALIZABLE toàn cục hay thêm Redis lock trước. SERIALIZABLE có abort/retry cost; Redis tạo thêm distributed failure modes. Em sẽ load-test hot product, đo lock waits, conflict rate và p99, đồng thời xử lý idempotency của retries riêng với concurrency control.”

## Câu hỏi đào sâu

1. Nếu atomic conditional update đúng về correctness nhưng một flash-sale product có 10.000 concurrent reservations và p99 rất cao, bạn tối ưu tiếp theo hướng nào mà vẫn giữ invariant?
2. Nếu invariant là “tổng reservation ở ba warehouses không vượt tổng stock khả dụng” thay vì một row, strategy của bạn thay đổi ra sao?
3. Một teammate muốn dùng Redis Redlock để tránh mọi database lock. Bạn sẽ yêu cầu failure model và evidence gì trước khi chấp nhận thay đổi đó?

## Lỗi trả lời thường gặp

- Nghĩ rằng `BEGIN TRANSACTION` tự khóa mọi row đã đọc.
- Nhảy ngay sang Redis distributed lock cho invariant nằm trong một database.
- Bật `SERIALIZABLE` mà không nhắc transaction abort/retry và contention.
- Không kiểm tra SQL/rows affected thực tế của EF Core.
- Trộn idempotency của duplicate requests với concurrency control của simultaneous writes.

## Thang điểm 0–10

- **0–2:** chỉ nói “dùng transaction/lock”.
- **3–4:** biết MVCC nhưng chưa nối với read-check-write race.
- **5–6:** giải thích đúng read visibility, atomic update/row lock/optimistic options và trade-offs.
- **7–8:** có evidence plan, hot-row performance reasoning, retry/idempotency separation và high-value tests.
- **9–10:** chọn strategy theo invariant scope, contention profile và failure model; hiểu correctness, throughput và operational complexity như các trục riêng.

# Câu 2 — Vue search thỉnh thoảng hiển thị kết quả của từ khóa cũ: API nhanh nhưng UI vẫn sai dưới mạng chậm

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Vue.js, TypeScript, browser networking, async race conditions, request cancellation, stale state, REST API integration, observability, frontend/backend correlation, performance, UX reliability

## Bối cảnh

Một Vue.js search page gọi ASP.NET Core search API khi user nhập keyword. Team đã thêm debounce 250 ms để giảm số request.

Code giản lược:

```ts
import { ref, watch } from 'vue'

const query = ref('')
const results = ref<SearchResult[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

let timer: number | undefined

watch(query, (value) => {
  window.clearTimeout(timer)

  timer = window.setTimeout(async () => {
    if (!value.trim()) {
      results.value = []
      return
    }

    loading.value = true
    error.value = null

    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(value)}`
      )

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`)
      }

      results.value = await response.json()
    } catch (e) {
      error.value = 'Search failed'
    } finally {
      loading.value = false
    }
  }, 250)
})
```

Production symptom:

- user gõ nhanh `car`, sau đó đổi thành `career`;
- Network tab cho thấy request `career` có lúc hoàn thành trước request `car`;
- UI đôi khi hiển thị kết quả của `car` dù textbox đang là `career`;
- symptom dễ thấy hơn trên mobile network hoặc khi backend dependency có tail latency cao;
- backend p50 tốt và không có spike CPU;
- một số requests bị client bỏ trang nhưng backend vẫn tiếp tục search;
- error banner đôi lúc nháy lên từ một request cũ dù request mới đã thành công;
- team muốn tăng debounce lên 1000 ms để “hết race”;
- chưa biết component có bị mount/unmount thường xuyên, browser cache có tham gia hay API có request correlation/cancellation telemetry hay không.

## Câu hỏi chính

Bạn đang xử lý incident này. Hãy trình bày cách **xác định impact, stabilize UX, thu evidence, phân biệt competing hypotheses, xác minh root cause và sửa flow** để kết quả chỉ được apply khi còn tương ứng với user intent hiện tại. Đồng thời giải thích cách propagate cancellation xuống ASP.NET Core/search dependency khi hợp lý, và cách kiểm thử race condition một cách deterministic.

## Câu hỏi làm rõ nên cân nhắc

1. Search có được trigger chỉ bởi `query` hay còn filter/sort/page state tạo thêm request keys?
2. Backend có hỗ trợ `CancellationToken` từ request abort xuống query/search client hay không?
3. UI requirement khi request cũ fail nhưng request mới thành công là gì — có được hiển thị error của request cũ không?
4. Có caching layer/browser/service worker nào có thể trả stale response ngoài race condition không?
5. Search responses có request/query metadata hoặc correlation ID để nối frontend event với backend trace không?

## Gợi ý tư duy

### Gợi ý 1

Debounce giảm **số lần bắt đầu request**; nó không bảo đảm các request đã bắt đầu sẽ hoàn thành theo đúng thứ tự.

### Gợi ý 2

Phân biệt hai biện pháp: **không cho stale response mutate state** và **hủy work không còn cần thiết**. Correctness không nên phụ thuộc hoàn toàn vào cancellation thành công.

### Gợi ý 3

Hãy tạo test trong đó request A cố ý resolve sau request B. Nếu test không ép được ordering, race rất dễ trở thành flaky test.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact và frequency.
2. Reproduce với network throttling/delayed mock responses.
3. Correlate query/request/response ordering.
4. Liệt kê hypotheses: out-of-order responses, stale cache, duplicate watcher, component lifecycle, backend inconsistency.
5. Xác minh primary root cause.
6. Chặn stale state mutation bằng request identity/generation.
7. Hủy previous request bằng `AbortController` như resource optimization.
8. Propagate cancellation backend nếu dependency hỗ trợ.
9. Test success/error/unmount/race paths.
10. Instrument frontend + backend telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Async requests có thể hoàn thành khác thứ tự bắt đầu; “latest request started” không đồng nghĩa “latest response completed”.
- Debounce không giải quyết request race sau khi hai requests đã được gửi.
- UI phải chỉ apply response/error/loading transition nếu response còn thuộc request generation/query state hiện hành.
- `AbortController` giúp hủy fetch cũ, nhưng correctness vẫn nên có stale-result guard vì cancellation có race/failure semantics và downstream work có thể đã tiến xa.
- `loading` boolean đơn giản cũng có race: request cũ hoàn thành có thể set `loading=false` khi request mới vẫn đang chạy.
- Error của stale request không nên overwrite state của request mới thành công.
- Backend nên nhận request cancellation qua ASP.NET Core `CancellationToken` và propagate tới I/O/query APIs hỗ trợ cancellation khi work không còn cần thiết.
- Không nên tăng debounce lên 1000 ms như fix correctness; nó chủ yếu đổi UX/request rate.

### Điểm cộng

- Dùng monotonically increasing request ID/generation hoặc capture request key gồm query + filters + page.
- Abort previous controller khi query đổi và abort khi component unmount.
- Phân biệt `AbortError` với real error để không hiện banner sai.
- Backend không log cancellation do client disconnect như server error severity nếu đó là expected behavior.
- Có correlation giữa frontend request ID/query hash với Application Insights/backend dependency trace mà không log sensitive search text nếu policy không cho phép.

### Senior+

- Nhận ra state machine rõ ràng tốt hơn nhiều booleans độc lập khi component phức tạp: idle/loading/success/error với generation đi kèm.
- Nếu search API có pagination/filter, identity phải bao gồm toàn request parameters chứ không chỉ textbox.
- Biết cancellation là cooperative: code CPU-bound hoặc dependency không hỗ trợ token có thể vẫn tiếp tục.
- Có failure-path behavior khi previous request đã commit server-side side effect — dù search GET nên side-effect-free; nguyên tắc này không áp dụng mù cho mutation APIs.
- Đo tail latency/out-of-order rate thay vì chỉ backend average latency.

## Hướng giải quyết tham khảo

### 1. Stabilize và reproduce

Trước tiên xác nhận đây là stale-response race bằng browser/network telemetry hoặc mock API có delay điều khiển được. Ví dụ ép:

```text
request A: q=car     → delay 800 ms
request B: q=career  → delay 100 ms
```

Nếu B cập nhật UI trước rồi A overwrite sau, root cause đã được reproduce.

Tuy nhiên vẫn nên loại trừ:

- watcher/component được đăng ký hai lần;
- service worker/browser cache;
- backend search index eventual consistency;
- query parameters ngoài keyword;
- route/component remount.

### 2. Request generation guard

Một implementation đơn giản:

```ts
import { onBeforeUnmount, ref, watch } from 'vue'

const query = ref('')
const results = ref<SearchResult[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

let timer: number | undefined
let generation = 0
let controller: AbortController | null = null

watch(query, (rawValue) => {
  const value = rawValue.trim()
  const myGeneration = ++generation

  window.clearTimeout(timer)
  controller?.abort()
  controller = null

  if (!value) {
    results.value = []
    error.value = null
    loading.value = false
    return
  }

  timer = window.setTimeout(async () => {
    const currentController = new AbortController()
    controller = currentController

    if (myGeneration === generation) {
      loading.value = true
      error.value = null
    }

    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(value)}`,
        { signal: currentController.signal }
      )

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`)
      }

      const data: SearchResult[] = await response.json()

      if (myGeneration === generation) {
        results.value = data
      }
    } catch (e) {
      if (
        myGeneration === generation &&
        !(e instanceof DOMException && e.name === 'AbortError')
      ) {
        error.value = 'Search failed'
      }
    } finally {
      if (myGeneration === generation) {
        loading.value = false
      }
    }
  }, 250)
})

onBeforeUnmount(() => {
  ++generation
  window.clearTimeout(timer)
  controller?.abort()
})
```

Generation check là correctness guard. Abort giúp giảm browser/backend work không cần thiết.

Trong production code, có thể đóng gói behavior vào composable thay vì để toàn bộ logic trong component nếu nhiều screens dùng cùng pattern. Nhưng không cần tạo abstraction lớn nếu chỉ có một use case.

### 3. Backend cancellation

ASP.NET Core endpoint có thể nhận cancellation token:

```csharp
app.MapGet("/api/search", async (
    string q,
    ISearchService searchService,
    CancellationToken cancellationToken) =>
{
    var results = await searchService.SearchAsync(q, cancellationToken);
    return Results.Ok(results);
});
```

Service tiếp tục propagate token tới supported dependency APIs:

```csharp
public Task<IReadOnlyList<SearchResult>> SearchAsync(
    string query,
    CancellationToken cancellationToken)
{
    return _searchClient.SearchAsync(query, cancellationToken);
}
```

Cancellation là cooperative. Nếu dependency đã hoàn tất hoặc không hỗ trợ cancellation thì server work có thể không dừng ngay. Vì vậy frontend vẫn cần generation guard.

### 4. Loading/error state

Request cũ không được set loading false hoặc error cho generation mới. Nếu UI phức tạp, có thể model state:

```ts
type SearchState =
  | { kind: 'idle'; generation: number }
  | { kind: 'loading'; generation: number }
  | { kind: 'success'; generation: number; data: SearchResult[] }
  | { kind: 'error'; generation: number; message: string }
```

Điều này giảm invalid combinations như `loading=false`, `error!=null` nhưng results lại thuộc request mới.

### 5. Deterministic tests

High-value test phải kiểm soát completion order, không dựa vào random timeout:

1. A bắt đầu, B bắt đầu, resolve B trước, resolve A sau → UI vẫn là B.
2. A fail sau khi B success → error của A không xuất hiện.
3. Query bị clear khi request đang chạy → response cũ không repopulate results.
4. Component unmount → outstanding request bị abort/no state mutation.
5. Backend integration test xác nhận request cancellation được propagate tới dependency mock/handler.

Playwright có thể intercept routes và delay responses có chủ ý để reproduce browser behavior end-to-end.

### 6. Production telemetry

Đo:

- search request count/session;
- client cancellation count;
- frontend request generation/query fingerprint;
- backend canceled request count;
- p50/p95/p99 latency;
- dependency latency;
- stale-response-discard count;
- network/error rate theo browser/device nếu cần.

Nếu stale discard tăng đột biến, đó có thể là signal backend tail latency hoặc duplicated frontend requests, không chỉ một harmless UI metric.

## Mẫu trả lời trong phỏng vấn

“Em sẽ reproduce bằng cách ép request `car` hoàn thành sau `career`. Debounce chỉ giảm số request được khởi động; nó không bảo đảm completion order. Vì vậy response cũ có thể overwrite state mới, và cùng race còn ảnh hưởng loading/error.

Fix correctness của em là gắn một generation/request key cho mỗi user intent. Chỉ response có generation hiện tại mới được phép cập nhật results, error và loading. Đồng thời em dùng AbortController để abort request trước khi query đổi hoặc component unmount, nhưng em không phụ thuộc cancellation để đảm bảo correctness.

Ở ASP.NET Core em propagate request CancellationToken xuống search dependency nếu API hỗ trợ. Client disconnect cancellation được theo dõi riêng, không coi mặc định là server fault. Em test deterministic bằng delayed route: B resolve trước A, A fail sau B success, clear query, unmount và cancellation propagation.

Em sẽ không tăng debounce lên một giây để fix race vì đó chỉ làm UX chậm hơn và không loại bỏ out-of-order completion.”

## Câu hỏi đào sâu

1. Nếu Product muốn giữ previous results trên màn hình trong lúc request mới loading thay vì clear results, state model và stale guard của bạn thay đổi thế nào?
2. Nếu backend search gọi đồng thời ba dependencies và chỉ một dependency hỗ trợ cancellation, bạn propagate token và xử lý partial cancellation ra sao?
3. Một teammate nói chỉ cần AbortController nên generation ID là dư thừa. Bạn phản biện recommendation đó dựa trên failure/race semantics nào?

## Lỗi trả lời thường gặp

- Tăng debounce và coi đó là fix race condition.
- Chỉ cancel request mà không guard stale state mutation.
- Chỉ bảo vệ `results` nhưng để request cũ overwrite `error` hoặc `loading`.
- Không propagate request cancellation xuống backend I/O dù work đã vô ích.
- Viết test bằng random `setTimeout` khiến test race condition trở thành flaky.

## Thang điểm 0–10

- **0–2:** chỉ đổi debounce/loading indicator.
- **3–4:** nhận ra out-of-order response nhưng fix chưa bao phủ error/loading/lifecycle.
- **5–6:** có generation guard, AbortController và backend cancellation reasoning đúng.
- **7–8:** có deterministic tests, telemetry, lifecycle handling và phân biệt correctness với resource optimization.
- **9–10:** model state/identity đầy đủ cho query+filters, hiểu cooperative cancellation và dùng out-of-order telemetry để nối UX symptom với tail latency/downstream behavior.

# Câu 3 — Upload tài liệu 2 GB lên Azure Blob Storage: backend proxy hay direct upload bằng SAS, và xử lý security/failure thế nào?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, ASP.NET Core, file upload, streaming, SAS, Managed Identity, Azure Functions/background processing, security, malware scanning, authorization, idempotency, failure recovery, metadata, observability, Azure App Service

## Bối cảnh

Một enterprise document portal chạy ASP.NET Core trên Azure App Service. Product muốn cho user upload tài liệu từ vài KB tới khoảng 2 GB.

Requirements ban đầu:

- user phải authenticate và chỉ upload vào logical folder họ có quyền;
- upload lớn phải chịu được mạng mobile/chập chờn ở mức hợp lý;
- application không được load toàn bộ file vào memory;
- file mới chưa được phép download công khai cho tới khi validation/scanning hoàn tất;
- metadata business lưu ở SQL Server;
- binary lưu ở Azure Blob Storage;
- một antivirus/scanning engine sẽ được tích hợp nhưng provider cụ thể chưa chốt;
- application chạy nhiều instances;
- Product muốn progress UI và có thể retry upload;
- Ops muốn không làm App Service bandwidth/CPU trở thành bottleneck nếu không cần thiết;
- Security không muốn cấp storage credential rộng cho browser;
- một developer đề xuất browser upload thẳng vào Blob bằng account key để nhanh nhất;
- một developer khác muốn mọi byte đi qua ASP.NET Core để “backend kiểm soát được file”;
- chưa chốt exact retention, geography, encryption-key requirement, maximum concurrent uploads hay SLA cho scanning.

## Câu hỏi chính

Hãy thiết kế end-to-end file upload workflow. So sánh **backend-proxy streaming** với **direct-to-Blob upload bằng scoped SAS**, xác định authorization boundary, metadata/state model, retry/idempotency, validation/scanning, download gating, cleanup và observability. Nêu rõ khi nào bạn chọn giải pháp đơn giản qua backend và khi nào direct upload đáng complexity hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent uploads và typical file-size distribution là gì, không chỉ maximum 2 GB?
2. Browser có cần resumable/chunked upload sau network interruption hay retry toàn file được chấp nhận?
3. Antivirus scanner chạy ở đâu, hỗ trợ streaming hay chỉ scan blob hoàn chỉnh, và scan SLA là bao lâu?
4. File types nào được phép, có requirement preview/conversion hay active content như Office/PDF cần xử lý riêng không?
5. Compliance có yêu cầu region, customer-managed keys, immutable retention hoặc legal hold không?

## Gợi ý tư duy

### Gợi ý 1

Tách **authorization để được phép tạo upload** khỏi **data plane truyền hàng GB bytes**. Hai trách nhiệm không nhất thiết phải chạy qua cùng process.

### Gợi ý 2

Direct upload không có nghĩa browser được storage credential rộng. Hãy thiết kế capability ngắn hạn, scope hẹp và server-side validation sau upload.

### Gợi ý 3

Upload hoàn tất không đồng nghĩa document đã “Ready”. Modeling lifecycle rõ ràng giúp recovery, scanning và download authorization dễ hơn.

## Cấu trúc trả lời đề xuất

1. Clarify size/concurrency/resume/security/SLA.
2. Xác định data ownership: SQL metadata vs Blob binary.
3. Chọn upload path theo workload.
4. Thiết kế create-upload authorization handshake.
5. Thiết kế blob naming/key và scoped access.
6. Thiết kế upload completion/idempotency.
7. Thiết kế validation/scanning lifecycle.
8. Gate download theo document state.
9. Xử lý abandoned/failed uploads và cleanup.
10. Security/least privilege/secrets.
11. Testing/failure injection.
12. Observability và operational runbook.
13. Đánh giá trade-offs/cost of complexity.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cấp Azure Storage account key cho browser; đó là credential quá rộng và khó kiểm soát theo từng upload.
- Backend phải authorize user/business permission trước khi cấp quyền upload.
- Scoped, time-bounded SAS có thể cho browser quyền tới một blob/object scope cụ thể thay vì toàn account/container.
- Nếu backend proxy file, phải streaming thay vì buffer toàn file vào memory.
- Direct upload giảm application data-plane bandwidth và scale pressure nhưng tăng complexity ở upload lifecycle, completion verification và client retry.
- Blob existence không được đồng nghĩa document “Ready”. Cần state như `PendingUpload`, `Uploaded`, `Scanning`, `Ready`, `Rejected`/`Failed`.
- Download API phải kiểm tra authorization và document state; file chưa scan không được public serve chỉ vì blob URL tồn tại.
- File metadata/content type/extension do client gửi không được tin tuyệt đối; validation phải server-side theo risk requirement.
- Retry/completion callback phải idempotent vì client có thể gửi lại request sau timeout.
- Abandoned blobs và DB rows cần cleanup/reconciliation.

### Điểm cộng

- Backend dùng Managed Identity để thao tác Blob Storage và generate/access delegated capability theo supported Azure pattern thay vì giữ account key trong config.
- Blob key do server tạo ngẫu nhiên/opaque, không dùng raw user filename làm authorization boundary.
- Client gửi upload completion kèm upload/document ID; server verify blob properties/existence trước chuyển state.
- Scanner xử lý async qua durable queue/background mechanism, có retry/DLQ hoặc failed state phù hợp.
- Quarantine container/prefix hoặc access policy bảo đảm unscanned content không đi vào normal download path.
- Large-file upload dùng block blob/chunk semantics và retry từng block khi client SDK/browser strategy hỗ trợ.

### Senior+

- Nhận ra DB + Blob không có một local ACID transaction chung; lifecycle/reconciliation phải chịu partial failure giữa hai systems.
- Thiết kế idempotent state transitions và event processing khi upload-complete signal bị gửi lặp hoặc mất.
- Tách original filename dùng cho display khỏi internal blob key để tránh path/key injection assumptions.
- Có defense cho zip bombs, parser vulnerabilities, MIME confusion hoặc malicious active content tùy accepted file types; antivirus không phải toàn bộ file-security strategy.
- Chọn architecture theo workload: file nhỏ/traffic thấp có thể proxy streaming để giảm complexity; 2 GB/concurrency cao thường justify direct data plane.
- Download có thể dùng short-lived read SAS sau authorization thay vì proxy bytes qua backend nếu business/security/CDN requirements cho phép.

## Hướng giải quyết tham khảo

### 1. Data ownership và state model

SQL Server lưu business metadata và lifecycle:

```text
Document
- Id
- Owner/TenantId
- OriginalFileName
- BlobKey
- SizeExpected (optional)
- SizeActual
- State
- CreatedAtUtc
- UploadedAtUtc
- ScanCompletedAtUtc
- ScanResult
- Version/ConcurrencyToken
```

State machine ví dụ:

```text
PendingUpload
   ↓
Uploaded
   ↓
Scanning
  ↙   ↘
Ready  Rejected

PendingUpload → Expired
Uploaded/Scanning → Failed (when policy requires)
```

State transitions phải idempotent và có ownership check.

### 2. Option A — backend proxy streaming

Flow:

```text
Browser
  → ASP.NET Core
     → authorize
     → stream request body
        → Blob Storage
```

Ưu điểm:

- authorization/control flow đơn giản;
- server có thể enforce một số limits ngay trên path;
- browser không cần biết Blob endpoint/SAS lifecycle.

Nhược điểm:

- toàn bộ bytes đi qua App Service;
- connection sống lâu;
- scale/bandwidth/timeout pressure tăng;
- retry 2 GB request qua application khó hơn;
- deployment/restart có thể ảnh hưởng long-running uploads.

Nếu chọn path này, không dùng `MemoryStream` hoặc `ReadToEnd` cho file lớn. Stream body tới Blob SDK và propagate cancellation.

### 3. Option B — direct upload với scoped SAS

Flow có thể là:

```text
1. Browser → POST /documents/uploads
2. API authenticate + authorize folder/quota/type policy
3. API tạo Document(PendingUpload) + opaque BlobKey
4. API trả upload session + short-lived scoped SAS cho đúng blob
5. Browser → Blob Storage trực tiếp
6. Browser → POST /documents/{id}/complete
7. API verify blob + atomically chuyển state phù hợp
8. Async scanner xử lý blob
9. Scan clean → Ready
10. Download chỉ cấp quyền khi Ready + user authorized
```

SAS phải có:

- lifetime ngắn theo upload need;
- permissions tối thiểu cần thiết;
- resource scope hẹp;
- HTTPS requirement khi supported/configured;
- không expose account key.

Exact SAS generation mechanism phải theo Azure Storage SDK/current security guidance. Khi backend chạy Azure, Managed Identity nên được ưu tiên cho service-to-storage authentication nơi phù hợp.

Tài liệu chính thức:

- Microsoft Learn — Grant limited access to Azure Storage resources using SAS: `https://learn.microsoft.com/azure/storage/common/storage-sas-overview`
- Microsoft Learn — Authorize access to blobs using Microsoft Entra ID: `https://learn.microsoft.com/azure/storage/blobs/authorize-access-azure-active-directory`
- Microsoft Learn — Upload a block blob: `https://learn.microsoft.com/azure/storage/blobs/storage-blob-upload`

### 4. Completion không được tin client tuyệt đối

Client gọi `complete` chỉ là signal. Backend phải kiểm tra blob ở expected key và các properties cần thiết:

```csharp
public async Task CompleteUploadAsync(
    Guid documentId,
    ClaimsPrincipal user,
    CancellationToken ct)
{
    var doc = await _documents.GetAsync(documentId, ct);
    _authorization.EnsureCanManage(user, doc);

    if (doc.State is DocumentState.Uploaded or
        DocumentState.Scanning or
        DocumentState.Ready)
    {
        return; // idempotent completion
    }

    if (doc.State != DocumentState.PendingUpload)
        throw new InvalidOperationException("Upload cannot be completed.");

    var properties = await _blobStore.GetPropertiesAsync(doc.BlobKey, ct);

    ValidateSizeAndBasicPolicy(doc, properties);

    doc.MarkUploaded(properties.ContentLength);
    await _documents.SaveAsync(doc, ct);

    await _scanQueue.EnqueueAsync(
        new ScanDocumentCommand(doc.Id),
        ct);
}
```

Nếu SQL state update thành công nhưng queue publish thất bại, scan signal có thể mất. Giải pháp có thể là transactional outbox từ SQL hoặc một reconciliation worker quét `Uploaded` documents chưa scan. Không nhất thiết cần messaging nếu volume thấp; polling durable state cũng có thể đơn giản và đủ tốt.

### 5. Scanning/quarantine

Scanner là async dependency có thể timeout/fail. File không được chuyển `Ready` chỉ vì scanner tạm unavailable.

Possible policy:

```text
Uploaded → Scanning
Scanning → Ready      (clean)
Scanning → Rejected   (malicious)
Scanning → retry/Failed (scanner unavailable after bounded attempts)
```

Không render/parse file bằng privileged component trước khi security policy cho phép. Nếu cần preview/conversion, component đó cũng là untrusted-file parser và phải sandbox/isolate theo threat model.

### 6. Download

Có hai hướng:

**Proxy download:** backend authorize rồi stream Blob → client. Đơn giản control nhưng tốn data-plane bandwidth.

**Authorized redirect/read SAS:** backend authorize + kiểm tra `Ready`, sau đó cấp short-lived read SAS cho exact blob. Giảm backend bandwidth nhưng cần kiểm soát lifetime/cache/leakage semantics.

Không để quarantine container/blob public.

### 7. Partial failures/reconciliation

Các failure cần thiết kế trước:

- DB row tạo nhưng client không upload → expire + cleanup.
- blob upload xong nhưng client mất mạng trước `complete` → reconciliation hoặc user retry complete.
- complete được gọi hai lần → idempotent.
- SQL updated nhưng scan signal mất → outbox/reconciliation.
- scanner timeout → bounded retry + observable state.
- malicious file → retain/delete/quarantine theo policy.
- user xóa document trong lúc scan → state/version rule chống scanner hồi sinh deleted document.

### 8. Khi nào chọn giải pháp nào?

Nếu phần lớn file nhỏ, concurrency thấp và team ưu tiên simplicity, backend proxy streaming có thể hợp lý và dễ vận hành hơn.

Nếu hàng trăm MB tới 2 GB là common workload hoặc concurrent uploads cao, direct-to-Blob thường giảm App Service bottleneck đáng kể và tạo đường tốt hơn cho chunk/retry. Complexity tăng nằm ở SAS issuance, CORS/client upload, lifecycle, completion verification và cleanup.

Không cần microservice chỉ vì upload lớn. Một ASP.NET Core application + Blob Storage + durable background scanner có thể đủ. Tách worker/service khi scanning có scaling/security/lifecycle khác biệt rõ ràng.

### 9. Testing

- authorization test: user không thể xin SAS/blob key cho folder của user khác;
- large-file integration test không tạo memory spike tỷ lệ với file size;
- retry test cho interrupted block upload;
- completion idempotency test;
- upload-completed-but-callback-lost reconciliation test;
- malicious/unsupported file rejection test;
- scanner timeout/retry test;
- concurrent delete-versus-scan state transition test;
- expired SAS cannot upload after intended window;
- download denied trước `Ready` và sau authorization loss.

### 10. Observability

Theo dõi:

- upload sessions created/completed/expired;
- upload size histogram và duration;
- direct upload failure/retry rate từ client telemetry;
- pending/uploaded/scanning queue age;
- scan latency/error/retry/rejection rate;
- abandoned blob count/storage growth;
- API SAS issuance failures;
- Blob dependency latency/errors;
- download authorization failures;
- correlation bằng `DocumentId`/operation ID, không log SAS token.

SAS URL là sensitive capability; không được ghi đầy đủ vào application logs, analytics hoặc error reporting.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách control plane khỏi data plane. API vẫn authenticate và authorize user, tạo document record với opaque blob key rồi, nếu workload large-file/concurrency justify, cấp SAS ngắn hạn scope đúng blob để browser upload trực tiếp. Em không bao giờ đưa storage account key cho browser.

Blob tồn tại chưa có nghĩa document Ready. Em model lifecycle PendingUpload → Uploaded → Scanning → Ready/Rejected. Client gọi complete nhưng server phải verify blob và endpoint đó idempotent. Scanner chạy async; nếu signal scan có thể mất giữa SQL và queue thì em dùng outbox hoặc reconciliation tùy volume. Download chỉ được cấp sau authorization + state Ready.

Nếu traffic thấp và file chủ yếu nhỏ, backend proxy streaming có thể đơn giản hơn; nhưng phải stream, không buffer. Với file tới 2 GB và concurrency cao, direct-to-Blob tránh biến App Service thành data pipe và hỗ trợ chunk/retry tốt hơn.

Em test partial failures như upload xong mất callback, duplicate complete, scanner timeout và delete trong lúc scan. Telemetry theo document state/age, upload duration, scan backlog và Blob errors; tuyệt đối không log SAS token.”

## Câu hỏi đào sâu

1. Nếu Security yêu cầu browser không được có bất kỳ direct Blob URL nào, bạn thiết kế backend-proxy path để chịu 2 GB uploads mà không làm App Service memory/timeout trở thành bottleneck ra sao?
2. Nếu scanner mất 30 phút trong giờ cao điểm nhưng Product muốn file “có thể xem ngay”, bạn sẽ thương lượng requirement và thiết kế degraded workflow thế nào mà không bypass security boundary?
3. Một teammate muốn tách upload, metadata, scanning và download thành bốn microservices ngay từ Release 1. Bạn cần evidence nào để chấp nhận complexity đó?

## Lỗi trả lời thường gặp

- Gửi Storage account key xuống browser.
- Buffer toàn file trong memory trước khi upload Blob.
- Coi blob upload thành công là document đã an toàn để download.
- Không xử lý partial failure giữa SQL, Blob và scan queue.
- Dùng SAS quá rộng/quá lâu hoặc log SAS URL vào telemetry.

## Thang điểm 0–10

- **0–2:** chỉ chọn proxy/direct mà không có security/failure model.
- **3–4:** biết SAS/streaming nhưng lifecycle và partial failures còn mơ hồ.
- **5–6:** có authorization, scoped SAS, state machine, scanning và idempotent completion.
- **7–8:** có reconciliation/outbox trade-off, chunk/retry, download gating, telemetry và security tests.
- **9–10:** chọn architecture conditional theo workload, phân tích DB+Blob distributed consistency, untrusted-file threat model và cost-of-complexity một cách rõ ràng.

## Kiến thức trọng tâm

- PostgreSQL transaction và MVCC không tự biến read-check-write application logic thành một atomic business operation; concurrency strategy phải bám vào invariant thực tế.
- Debounce không giải quyết out-of-order async responses; frontend correctness cần request identity/stale-result guard, còn cancellation chủ yếu giảm work không cần thiết.
- Large-file upload architecture nên tách authorization/control plane khỏi data plane khi workload justify, nhưng direct upload vẫn cần least-privilege capability và server-side lifecycle verification.
- SQL, browser, Blob Storage và background scanner tạo ra nhiều failure boundaries; state transitions, idempotency và reconciliation phải được thiết kế từ đầu.
- Senior-level decision không phải chọn technology “mạnh nhất”, mà chọn minimum complexity đủ để giữ correctness, security và operability dưới failure thực tế.

## Mẫu tư duy cần nhớ

- **Put invariants as close as practical to the system that owns the data.**
- **Separate correctness guards from performance/resource optimizations.**
- **Treat every cross-system handoff as a partial-failure boundary.**
- **Model lifecycle explicitly when “created”, “uploaded”, “processed” and “ready” are different states.**
- **Choose added architecture complexity only when workload or failure requirements pay for it.**
