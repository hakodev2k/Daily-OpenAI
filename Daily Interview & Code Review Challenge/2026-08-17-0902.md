# Code Review Challenge 1 — Hangfire job thanh toán bị chạy trùng và ghi đè trạng thái

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý yêu cầu hoàn tiền. API tạo `RefundRequest`, sau đó enqueue job. Production chạy nhiều Hangfire workers trên nhiều instance. Trong vài tuần gần đây, một số khách hàng nhận hai yêu cầu hoàn tiền tới payment provider; một số record lại có trạng thái `Completed` dù lần gọi provider cuối cùng bị timeout.

Payment provider hỗ trợ một `Idempotency-Key` ở request header nhưng code hiện tại chưa sử dụng. Không giả định Hangfire chỉ thực thi một lần: job có thể được retry sau exception hoặc được thực thi lại khi worker gặp failure. Database dùng EF Core; chi tiết isolation level và unique constraints chưa được cung cấp.

## Đoạn code cần review

```csharp
public sealed class RefundJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<RefundJob> _logger;

    public RefundJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<RefundJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid refundId)
    {
        var refund = await _db.RefundRequests
            .FirstOrDefaultAsync(x => x.Id == refundId);

        if (refund == null)
            return;

        if (refund.Status == "Completed")
            return;

        refund.Status = "Processing";
        refund.AttemptCount++;
        await _db.SaveChangesAsync();

        var request = new
        {
            paymentId = refund.PaymentId,
            amount = refund.Amount,
            reason = refund.Reason
        };

        try
        {
            var response = await _httpClient.PostAsJsonAsync(
                "/api/refunds", request);

            var body = await response.Content.ReadAsStringAsync();

            refund.ProviderResponse = body;
            refund.Status = "Completed";
            refund.CompletedAt = DateTime.UtcNow;

            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Refund failed. RefundId={RefundId}, Request={@Request}",
                refundId, request);

            refund.Status = "Failed";
            refund.Error = ex.ToString();
            await _db.SaveChangesAsync();

            throw;
        }
    }
}
```

4. Ưu tiên các vấn đề theo mức độ nghiêm trọng.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử retry, concurrent execution và ambiguous failure.
7. Đề xuất logs, traces và metrics cần theo dõi.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### 1. External refund không có idempotency key

- **Problem:** Mỗi lần job chạy lại có thể gửi một refund request mới.
- **Why it happens:** Retry của background job không đồng nghĩa exactly-once execution; side effect bên ngoài không nằm trong database transaction của ứng dụng.
- **Production impact:** Có thể tạo duplicate refund nếu provider không tự deduplicate.
- **Severity:** Critical
- **Recommended fix:** Tạo một idempotency key ổn định theo logical refund, lưu trong DB và gửi cùng mọi retry tới provider. Không tạo key mới theo attempt.

### 2. Race condition ở `check Status -> set Processing`

- **Problem:** Nhiều worker có thể đọc cùng record trước khi bất kỳ worker nào commit `Processing`.
- **Why it happens:** Read-check-write là nhiều thao tác riêng biệt và không có optimistic/pessimistic concurrency guard.
- **Production impact:** Hai worker cùng gọi payment provider.
- **Severity:** Critical
- **Recommended fix:** Claim work atomically, ví dụ conditional update `Pending -> Processing` và chỉ worker update được đúng một row mới tiếp tục; hoặc dùng concurrency token phù hợp. Distributed lock có thể bổ sung nhưng không nên là lớp bảo vệ duy nhất cho business invariant.

### 3. HTTP error response vẫn bị đánh dấu `Completed`

- **Problem:** Code không kiểm tra `response.IsSuccessStatusCode` hay policy nghiệp vụ tương đương.
- **Why it happens:** `HttpClient` không tự throw chỉ vì nhận HTTP status lỗi; việc throw cần `EnsureSuccessStatusCode()` hoặc xử lý status rõ ràng.
- **Production impact:** 400/409/429/500 có thể bị lưu thành refund thành công.
- **Severity:** High
- **Recommended fix:** Phân loại response: success, retryable failure, permanent failure, và trạng thái ambiguous/reconciliation nếu cần.

### 4. Timeout sau khi provider đã commit tạo ambiguous outcome

- **Problem:** `catch` gắn `Failed` mặc dù provider có thể đã xử lý thành công.
- **Why it happens:** Client không thể suy ra trạng thái server chỉ từ network timeout.
- **Production impact:** Retry mù có thể duplicate side effect; UI và database có thể báo sai trạng thái.
- **Severity:** High
- **Recommended fix:** Dùng provider idempotency key và, nếu provider hỗ trợ, query/reconcile trạng thái theo operation/idempotency key trước khi quyết định retry hoặc đánh dấu failed.

### 5. Failure state được commit rồi exception lại được throw

- **Problem:** Hangfire có thể retry một record đang `Failed`, nhưng code chỉ skip `Completed`.
- **Why it happens:** State machine và retry policy không được thiết kế cùng nhau.
- **Production impact:** Retry behavior khó dự đoán, AttemptCount tăng và external call lặp lại.
- **Severity:** High
- **Recommended fix:** Định nghĩa state machine rõ ràng (`Pending`, `Processing`, `Succeeded`, `RetryableFailed`, `NeedsReconciliation`, `PermanentFailed`) và điều kiện claim hợp lệ.

### 6. Không truyền cancellation/timeout policy rõ ràng

- **Problem:** Database và HTTP operations không nhận cancellation token; timeout/retry policy của outbound request không được thể hiện.
- **Why it happens:** Job không model hóa cancellation/failure budget.
- **Production impact:** Worker bị giữ lâu khi dependency chậm; shutdown và recovery kém hơn.
- **Severity:** Medium
- **Recommended fix:** Truyền token nếu execution model cung cấp token phù hợp, cấu hình timeout và resilience policy có giới hạn; chỉ retry các lỗi an toàn khi idempotency đã có.

### 7. Log/error persistence có thể lưu dữ liệu nhạy cảm quá mức

- **Problem:** Serialize request và `ex.ToString()` vào log/DB mà chưa có data classification.
- **Why it happens:** Diagnostic data được lưu không qua redaction/retention policy.
- **Production impact:** Rò rỉ payment identifiers hoặc business-sensitive data; log phình lớn.
- **Severity:** Medium
- **Recommended fix:** Structured logging với identifier cần thiết, redact dữ liệu nhạy cảm và giới hạn error payload.

### 8. Provider response được lưu nguyên văn không giới hạn

- **Problem:** Response body có thể lớn hoặc chứa dữ liệu không nên persist.
- **Why it happens:** Không validate size/schema trước khi lưu.
- **Production impact:** Tăng storage, có thể lưu sensitive data hoặc gây vấn đề khi provider trả payload bất thường.
- **Severity:** Medium
- **Recommended fix:** Parse schema cần thiết, lưu provider operation ID/status; truncate/redact diagnostic body nếu thực sự cần.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng thiết kế; phần `TryClaimAsync` nên được hiện thực bằng conditional update atomic tại database.

```csharp
public sealed class RefundJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _client;
    private readonly ILogger<RefundJob> _logger;

    public RefundJob(
        AppDbContext db,
        HttpClient client,
        ILogger<RefundJob> logger)
    {
        _db = db;
        _client = client;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid refundId, CancellationToken ct)
    {
        var claimed = await _db.RefundRequests
            .Where(x => x.Id == refundId &&
                        (x.Status == "Pending" || x.Status == "RetryableFailed"))
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.AttemptCount, x => x.AttemptCount + 1), ct);

        if (claimed != 1)
            return;

        var refund = await _db.RefundRequests
            .AsNoTracking()
            .SingleAsync(x => x.Id == refundId, ct);

        using var message = new HttpRequestMessage(HttpMethod.Post, "/api/refunds")
        {
            Content = JsonContent.Create(new
            {
                paymentId = refund.PaymentId,
                amount = refund.Amount,
                reason = refund.Reason
            })
        };

        message.Headers.TryAddWithoutValidation(
            "Idempotency-Key", refund.IdempotencyKey);

        try
        {
            using var response = await _client.SendAsync(message, ct);

            if (response.IsSuccessStatusCode)
            {
                await MarkSucceededAsync(refundId, ct);
                return;
            }

            if (IsRetryable(response.StatusCode))
            {
                await MarkRetryableAsync(refundId, (int)response.StatusCode, ct);
                throw new HttpRequestException(
                    $"Retryable provider response: {(int)response.StatusCode}");
            }

            await MarkPermanentFailureAsync(
                refundId, (int)response.StatusCode, ct);
        }
        catch (OperationCanceledException) when (!ct.IsCancellationRequested)
        {
            await MarkNeedsReconciliationAsync(refundId, ct);
            throw;
        }
        catch (HttpRequestException)
        {
            await MarkNeedsReconciliationAsync(refundId, ct);
            throw;
        }
    }

    private static bool IsRetryable(HttpStatusCode status) =>
        status == HttpStatusCode.TooManyRequests ||
        (int)status >= 500;

    private Task MarkSucceededAsync(Guid id, CancellationToken ct) =>
        _db.RefundRequests.Where(x => x.Id == id)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Succeeded")
                .SetProperty(x => x.CompletedAt, DateTime.UtcNow), ct);

    private Task MarkRetryableAsync(Guid id, int code, CancellationToken ct) =>
        _db.RefundRequests.Where(x => x.Id == id)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "RetryableFailed")
                .SetProperty(x => x.LastProviderStatusCode, code), ct);

    private Task MarkPermanentFailureAsync(Guid id, int code, CancellationToken ct) =>
        _db.RefundRequests.Where(x => x.Id == id)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "PermanentFailed")
                .SetProperty(x => x.LastProviderStatusCode, code), ct);

    private Task MarkNeedsReconciliationAsync(Guid id, CancellationToken ct) =>
        _db.RefundRequests.Where(x => x.Id == id)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "NeedsReconciliation"), ct);
}
```

Lưu ý: implementation thực tế phải khớp với contract của provider. Nếu provider đảm bảo idempotency và trả operation identifier, reconciliation nên tận dụng contract đó. Nếu không có idempotency support, cần thiết kế quy trình chống duplicate và reconciliation thận trọng hơn thay vì retry tự động vô điều kiện.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi một database là source of truth, nhưng cần state recovery nếu worker chết sau khi claim. Có thể thêm lease timestamp và reclaim policy. Distributed lock có thể giảm concurrent work nhưng tạo thêm dependency/failure mode và vẫn không giải quyết ambiguous external side effect. Transaction không thể bao trùm một HTTP payment provider theo cách thông thường; vì vậy idempotency và reconciliation quan trọng hơn việc cố tạo “exactly once”.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời 20 executions cùng `refundId`; xác minh chỉ một execution claim được record và provider mock quan sát logical operation hợp lệ.
2. **Ambiguous failure test:** provider mock commit refund rồi client nhận timeout; retry phải dùng cùng idempotency key và không tạo refund thứ hai.
3. **HTTP status test:** 400 phải thành permanent failure; 429/5xx đi theo retry policy; 2xx mới được success.
4. **Worker crash test:** kill worker sau khi claim nhưng trước HTTP call; xác minh lease/recovery mechanism đưa record trở lại trạng thái xử lý được.
5. **Load test:** tăng số jobs và provider latency; theo dõi queue age, worker utilization, outbound latency và DB contention.

## Quan sát trong production

- Structured log: `RefundId`, stable operation/idempotency identifier, attempt, state transition, provider status; không log payload nhạy cảm.
- Metrics: refund success/failure/reconciliation rate, retries per refund, queue latency, processing duration, provider latency/status distribution.
- Trace: Hangfire execution → DB claim → outbound HTTP → state transition.
- Alert: duplicate-operation signal, `NeedsReconciliation` backlog, retry spike, provider 5xx/429 spike.
- Database observation: số record mắc ở `Processing`, age của lease, state-transition anomalies.

3. Bạn sẽ thiết kế recovery thế nào nếu worker chết ngay sau khi provider trả success nhưng trước khi DB được cập nhật?

# Code Review Challenge 2 — API tìm kiếm audit log có authorization leak và query tốn tài nguyên

**Chủ đề:** Authorization, input validation, EF Core query execution, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core portal cho phép tenant admin tìm audit logs của tenant mình. Endpoint dưới đây được thêm nhanh để hỗ trợ điều tra sự cố. Traffic bình thường không lớn, nhưng một tenant có thể có hàng triệu audit records. Sau release, database CPU tăng khi admin search; security review đồng thời phát hiện khả năng người dùng nhìn thấy log ngoài tenant của mình.

`AuditLog` có `TenantId`, `CreatedAt`, `UserEmail`, `Action`, `Payload`. `Payload` đôi khi chứa metadata nội bộ và không được phép trả toàn bộ ra UI. Authentication đã được cấu hình ở application, nhưng policy/claims contract cụ thể chưa được nêu.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? tenantId,
        string? keyword,
        DateTime? from,
        DateTime? to)
    {
        _logger.LogInformation(
            "Audit search tenant={TenantId}, keyword={Keyword}, user={User}",
            tenantId, keyword, User.Identity?.Name);

        var logs = await _db.AuditLogs
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(tenantId))
            logs = logs.Where(x => x.TenantId == tenantId).ToList();

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            logs = logs.Where(x =>
                    x.UserEmail.Contains(keyword) ||
                    x.Action.Contains(keyword) ||
                    x.Payload.Contains(keyword))
                .ToList();
        }

        if (from.HasValue)
            logs = logs.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            logs = logs.Where(x => x.CreatedAt <= to.Value).ToList();

        return Ok(logs
            .OrderByDescending(x => x.CreatedAt)
            .Take(500));
    }
}
```

2. Phân tích security, sensitive-data và performance risks.
3. Giải thích impact khi bảng có hàng triệu rows.
4. Ưu tiên các lỗi cần sửa trước.
5. Đề xuất implementation an toàn và scalable hơn.
6. Nêu cách test authorization boundary và database query.
7. Đề xuất telemetry để phát hiện abuse hoặc query degradation.

- Query hiện tại chạy phần nào ở database, phần nào ở memory?

## Kết quả code review tham khảo

### 1. Tenant ID do caller tự cung cấp

- **Problem:** Caller có thể truyền tenant khác hoặc bỏ `tenantId`.
- **Why it happens:** Authorization scope được lấy từ untrusted request input thay vì identity/authorized tenant context.
- **Production impact:** Cross-tenant data exposure; khi bỏ parameter có thể trả log của mọi tenant.
- **Severity:** Critical
- **Recommended fix:** Bắt buộc authentication/authorization policy phù hợp và lấy tenant scope từ validated claim/server-side tenant context. Nếu privileged support role cần cross-tenant access, dùng policy riêng và audit rõ ràng.

### 2. Materialize toàn bộ bảng trước khi filter

- **Problem:** `ToListAsync()` chạy trước mọi filter.
- **Why it happens:** Sau materialization, các `Where` tiếp theo là LINQ-to-Objects.
- **Production impact:** Full table read, network/memory allocation lớn, latency và DB CPU/I/O tăng; request có thể gây resource exhaustion.
- **Severity:** High
- **Recommended fix:** Giữ `IQueryable`, áp dụng tenant filter đầu tiên, sau đó các filter khác, projection/order/limit trước `ToListAsync`.

### 3. Trả trực tiếp entity bao gồm `Payload`

- **Problem:** API serialize toàn bộ `AuditLog` entity.
- **Why it happens:** Không có response DTO/projection allowlist.
- **Production impact:** Sensitive/internal metadata có thể bị lộ; API contract phụ thuộc persistence model.
- **Severity:** High
- **Recommended fix:** Project sang DTO chỉ chứa các field được phép hiển thị. Endpoint chi tiết, nếu có, phải authorization riêng và redact payload.

### 4. Search `Payload.Contains(keyword)` không có guardrail

- **Problem:** Arbitrary substring search trên payload lớn có thể rất đắt và cũng mở rộng phạm vi dữ liệu được dò tìm.
- **Why it happens:** Không có search strategy/index phù hợp và không giới hạn input.
- **Production impact:** Scan lớn, CPU/I/O cao, dễ bị abuse bởi authenticated user.
- **Severity:** High
- **Recommended fix:** Chỉ search các field business cần thiết; giới hạn keyword length; cân nhắc normalized/searchable columns hoặc search technology phù hợp nếu full-text payload search thực sự là requirement.

### 5. Không có pagination thực sự

- **Problem:** Chỉ lấy 500 record sau khi đã load toàn bộ bảng.
- **Why it happens:** Limit được áp dụng trong memory.
- **Production impact:** Không bảo vệ database và không hỗ trợ duyệt dữ liệu ổn định.
- **Severity:** Medium
- **Recommended fix:** Apply bounded page size trong SQL; với tập dữ liệu lớn, keyset pagination theo `(CreatedAt, Id)` thường tránh chi phí offset sâu.

### 6. Không validate date range

- **Problem:** `from > to`, range cực lớn hoặc timezone semantics không rõ.
- **Why it happens:** Endpoint không định nghĩa input contract.
- **Production impact:** Kết quả sai hoặc query phạm vi quá rộng.
- **Severity:** Medium
- **Recommended fix:** Validate range, xác định UTC semantics, và cân nhắc giới hạn maximum range theo use case.

### 7. Tracking không cần thiết cho read-only endpoint

- **Problem:** EF Core tracking entities dù endpoint chỉ đọc.
- **Why it happens:** Query mặc định tracking nếu không cấu hình khác.
- **Production impact:** Tăng memory/change-tracker overhead.
- **Severity:** Medium
- **Recommended fix:** Dùng `AsNoTracking()` hoặc projection trực tiếp sang DTO.

### 8. Logging raw keyword có thể ghi dữ liệu nhạy cảm

- **Problem:** Search keyword được log nguyên văn.
- **Why it happens:** User-controlled search term được coi là diagnostic-safe.
- **Production impact:** PII/secrets mà admin paste vào search có thể đi vào log store.
- **Severity:** Medium
- **Recommended fix:** Không log raw search term nếu không cần; log length/hash/category hoặc redact theo policy.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "TenantAuditReader")]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AppDbContext db,
        ITenantContext tenantContext,
        ILogger<AuditController> logger)
    {
        _db = db;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        [FromQuery] string? keyword,
        [FromQuery] DateTimeOffset? from,
        [FromQuery] DateTimeOffset? to,
        [FromQuery] int pageSize = 100,
        CancellationToken ct = default)
    {
        if (from.HasValue && to.HasValue && from > to)
            return BadRequest("from must be less than or equal to to");

        if (pageSize is < 1 or > 200)
            return BadRequest("pageSize must be between 1 and 200");

        keyword = keyword?.Trim();
        if (keyword?.Length > 100)
            return BadRequest("keyword is too long");

        var tenantId = _tenantContext.RequiredTenantId;

        _logger.LogInformation(
            "Audit search TenantId={TenantId}, HasKeyword={HasKeyword}, From={From}, To={To}",
            tenantId, !string.IsNullOrEmpty(keyword), from, to);

        var query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value.UtcDateTime);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value.UtcDateTime);

        if (!string.IsNullOrEmpty(keyword))
        {
            query = query.Where(x =>
                x.UserEmail.Contains(keyword) ||
                x.Action.Contains(keyword));
        }

        var result = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(pageSize)
            .Select(x => new AuditLogDto(
                x.Id,
                x.CreatedAt,
                x.UserEmail,
                x.Action))
            .ToListAsync(ct);

        return Ok(result);
    }
}

public sealed record AuditLogDto(
    long Id,
    DateTime CreatedAt,
    string UserEmail,
    string Action);
```

Đây là hướng tham khảo, không phải khẳng định index cụ thể cho mọi workload. Index cần được quyết định dựa trên query plan và access pattern thực tế. Với pattern tenant + thời gian, một composite index phù hợp có thể hữu ích; nhưng substring search trên arbitrary text thường cần chiến lược khác thay vì chỉ thêm B-tree index rồi kỳ vọng mọi `Contains` trở nên rẻ.

## Trade-offs

Không search `Payload` làm endpoint an toàn và predictable hơn nhưng có thể giảm khả năng điều tra. Nếu full-text payload search là business requirement, nên tách rõ dữ liệu searchable khỏi dữ liệu sensitive, áp dụng authorization/redaction và chọn cơ chế search phù hợp. Keyset pagination scalable hơn deep offset nhưng client phải dùng cursor và API phức tạp hơn. Global query filter cho tenant có thể tạo thêm lớp defense-in-depth, nhưng không thay thế authorization policy và cần đặc biệt cẩn thận với privileged workflows.

## Cách kiểm thử

1. **Security integration test:** tenant A không thể lấy bất kỳ record nào của tenant B, kể cả khi cố truyền ID/keyword liên quan tenant B.
2. **Authorization test:** user thiếu `TenantAuditReader` bị từ chối; privileged role nếu tồn tại phải theo policy riêng.
3. **Database test:** xác minh generated SQL có tenant predicate, date filters, ordering và limit; không load toàn bảng rồi filter memory.
4. **Sensitive-data test:** response DTO không bao giờ chứa `Payload` hoặc field persistence mới vô tình được thêm sau này.
5. **Load test:** chạy search trên dataset hàng triệu rows, theo dõi query latency, rows read, CPU/I/O và execution plan với các filter phổ biến.

## Quan sát trong production

- Logs: tenant identifier, actor identifier, filter presence, bounded range, result count, duration; tránh raw sensitive keyword.
- Metrics: audit-search latency p50/p95/p99, error/denied rate, rows/result count, timeout rate.
- Traces: request → authorization → EF query → database duration.
- Alerts: latency/timeout spike, unusual request rate theo actor/tenant, repeated denied access.
- Database: query plans, rows read vs rows returned, index usage, CPU/I/O, blocking và slow-query samples.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Background job và retry không tạo ra exactly-once side effect; idempotency phải là business design, đặc biệt với payment/external API.
- Read-check-write không atomic; concurrency invariant nên được enforce bằng database operation/concurrency control phù hợp.
- Network timeout tạo **ambiguous outcome**: không thể mặc định server chưa thực hiện operation.
- Multi-tenant authorization phải dựa trên trusted identity/server-side context, không dựa vào tenant ID do client tùy ý gửi.
- Với EF Core, vị trí materialization (`ToListAsync`) quyết định filter chạy ở database hay memory; projection và limit nên được đẩy xuống database khi có thể.
- DTO allowlist giúp ngăn sensitive-data exposure và tách API contract khỏi persistence model.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng với idempotency và reconciliation.
- Enforce security invariants càng gần data access boundary càng tốt.
- Giữ query composable cho tới khi filter, projection, ordering và limit hoàn tất.
- Không suy luận trạng thái remote system chỉ từ lỗi network.
- Observability phải cho phép trả lời: operation nào, attempt nào, state transition nào, dependency nào và tenant nào bị ảnh hưởng.
