# Code Review Challenge 1 — Service Bus consumer gửi email trùng và mất công việc khi retry

**Chủ đề:** C#/.NET, Azure Service Bus, idempotency, retries, message settlement, SQL Server, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một .NET 8 Worker Service xử lý event `ApprovalCompleted` từ Azure Service Bus. Mỗi event cần ghi audit vào SQL Server, gửi email qua third-party provider, lưu trạng thái notification và complete message. Production chạy 4 replicas. Gần đây có duplicate email, queue backlog, `MessageLockLostException`, message malformed retry nhiều lần và một số record audit bị thiếu sau deploy/restart.

## Đoạn code cần review

```csharp
public sealed class ApprovalNotificationWorker : IAsyncDisposable
{
    private readonly ServiceBusProcessor _processor;
    private readonly IServiceProvider _services;
    private readonly ILogger<ApprovalNotificationWorker> _logger;

    public ApprovalNotificationWorker(
        ServiceBusClient client,
        IServiceProvider services,
        IConfiguration configuration,
        ILogger<ApprovalNotificationWorker> logger)
    {
        _services = services;
        _logger = logger;

        _processor = client.CreateProcessor(
            configuration["ServiceBus:QueueName"],
            new ServiceBusProcessorOptions
            {
                MaxConcurrentCalls = 32,
                PrefetchCount = 500
            });

        _processor.ProcessMessageAsync += HandleMessageAsync;
        _processor.ProcessErrorAsync += HandleErrorAsync;
    }

    public Task StartAsync(CancellationToken cancellationToken)
        => _processor.StartProcessingAsync(cancellationToken);

    private async Task HandleMessageAsync(ProcessMessageEventArgs args)
    {
        var evt = args.Message.Body
            .ToObjectFromJson<ApprovalCompletedEvent>();

        using var scope = _services.CreateScope();

        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var emailClient = scope.ServiceProvider.GetRequiredService<IEmailClient>();

        try
        {
            db.ApprovalAudits.Add(new ApprovalAudit
            {
                Id = Guid.NewGuid(),
                ApprovalId = evt.ApprovalId,
                UserId = evt.UserId,
                CompletedUtc = evt.CompletedUtc
            });

            await db.SaveChangesAsync();

            await emailClient.SendApprovalCompletedAsync(
                evt.UserId,
                evt.ApprovalId,
                CancellationToken.None);

            db.NotificationStates.Add(new NotificationState
            {
                Id = Guid.NewGuid(),
                ApprovalId = evt.ApprovalId,
                UserId = evt.UserId,
                Status = "Sent",
                SentUtc = DateTime.UtcNow
            });

            await db.SaveChangesAsync();

            await args.CompleteMessageAsync(args.Message);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Failed processing approval {ApprovalId}",
                evt.ApprovalId);
        }
    }

    private Task HandleErrorAsync(ProcessErrorEventArgs args)
    {
        _logger.LogError(args.Exception, "Service Bus processor error");
        return Task.CompletedTask;
    }

    public async ValueTask DisposeAsync()
        => await _processor.DisposeAsync();
}
```

## Kết quả code review tham khảo

### Critical — Consumer không idempotent

**Vấn đề:** mỗi delivery tạo audit, email và notification mới.

**Tại sao xảy ra:** Service Bus có thể redeliver khi lock mất, worker crash hoặc settlement không thành công.

**Ảnh hưởng production:** duplicate audit/email/notification.

**Cách sửa:** dùng stable event/message ID và unique constraint trong database. Ví dụ `ProcessedMessages(MessageId)` hoặc business event ID. Xử lý unique-conflict như “already processed”.

### Critical — Exception bị nuốt

**Vấn đề:** catch mọi exception rồi return.

**Tại sao xảy ra:** với auto-complete mặc định, handler hoàn tất bình thường có thể dẫn tới complete message dù business work fail.

**Ảnh hưởng production:** mất công việc ở mức business.

**Cách sửa:** đặt `AutoCompleteMessages = false`, chỉ complete khi durable business state đã commit; transient failure nên propagate/abandon, permanent failure nên dead-letter.

### Critical — External email side effect không atomic với database

**Vấn đề:** email provider, SQL transaction và Service Bus settlement không cùng transaction.

**Tại sao xảy ra:** đây là distributed workflow.

**Ảnh hưởng production:** email thành công nhưng state chưa commit, state commit nhưng settlement fail, timeout không biết email đã gửi hay chưa.

**Cách sửa:** dùng Outbox. Consumer commit idempotency marker + audit + notification outbox trong một SQL transaction, sau đó complete message. Worker riêng gửi email từ outbox.

### High — Duplicate detection không giải quyết redelivery phía consumer

**Vấn đề:** team coi duplicate detection là exactly-once.

**Tại sao xảy ra:** duplicate detection chủ yếu loại duplicate sends theo `MessageId` trong window; consumer vẫn có thể nhận lại message do lock/crash/settlement uncertainty.

**Ảnh hưởng production:** duplicate side effect vẫn xảy ra.

**Cách sửa:** duplicate detection chỉ là defense-in-depth; consumer vẫn phải idempotent.

### High — Concurrency/prefetch không gắn với capacity

**Vấn đề:** `MaxConcurrentCalls=32`, `PrefetchCount=500` được hard-code.

**Tại sao xảy ra:** không dựa trên SQL pool, email provider rate limit, average processing time, lock renewal và worker CPU.

**Ảnh hưởng production:** throttling, connection exhaustion, lock expiry, redelivery, tail latency tăng.

**Cách sửa:** tune bằng measurement và load test; giữ prefetch đủ để bận processor nhưng không lock lượng work vượt khả năng xử lý hợp lý.

### High — Không truyền cancellation

**Vấn đề:** database operations không nhận token; email dùng `CancellationToken.None`.

**Tại sao xảy ra:** handler không liên kết work với lifecycle/shutdown.

**Ảnh hưởng production:** deploy/restart có thể terminate process giữa side effect và settlement.

**Cách sửa:** propagate token phù hợp; vẫn phải dựa vào idempotency vì cancellation không loại bỏ network ambiguity.

### High — Poison message không được phân loại

**Vấn đề:** malformed payload rơi vào generic catch.

**Tại sao xảy ra:** không phân biệt permanent vs transient failure.

**Ảnh hưởng production:** retry lặp vô ích, tăng backlog và DLQ noise.

**Cách sửa:** validate sớm; dead-letter permanent invalidity với reason/description; retry transient dependency failure.

### Medium — Telemetry thiếu message lifecycle

**Vấn đề:** log chỉ có `ApprovalId`.

**Tại sao xảy ra:** không có `MessageId`, `DeliveryCount`, entity, error source, settlement outcome.

**Ảnh hưởng production:** khó RCA duplicate, lock loss hoặc poison message.

**Cách sửa:** structured logs/metrics/traces theo message ID, business event ID, delivery count, duration, instance và settlement outcome.

## Phiên bản đề xuất

```csharp
var processor = client.CreateProcessor(
    queueName,
    new ServiceBusProcessorOptions
    {
        AutoCompleteMessages = false,
        MaxConcurrentCalls = configuredConcurrency,
        PrefetchCount = configuredPrefetch
    });

async Task HandleAsync(
    ProcessMessageEventArgs args,
    CancellationToken cancellationToken)
{
    var messageId = args.Message.MessageId;

    ApprovalCompletedEvent evt;
    try
    {
        evt = args.Message.Body.ToObjectFromJson<ApprovalCompletedEvent>();
    }
    catch (Exception ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "InvalidPayload",
            ex.GetType().Name,
            cancellationToken);
        return;
    }

    await using var db = await dbFactory.CreateDbContextAsync(cancellationToken);
    await using var tx = await db.Database.BeginTransactionAsync(cancellationToken);

    var exists = await db.ProcessedMessages
        .AsNoTracking()
        .AnyAsync(x => x.MessageId == messageId, cancellationToken);

    if (!exists)
    {
        db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = messageId,
            ProcessedUtc = DateTime.UtcNow
        });

        db.ApprovalAudits.Add(new ApprovalAudit
        {
            Id = Guid.NewGuid(),
            ApprovalId = evt.ApprovalId,
            UserId = evt.UserId,
            CompletedUtc = evt.CompletedUtc,
            SourceMessageId = messageId
        });

        db.NotificationOutbox.Add(new NotificationOutbox
        {
            Id = Guid.NewGuid(),
            IdempotencyKey = $"approval:{evt.ApprovalId}:{evt.UserId}",
            ApprovalId = evt.ApprovalId,
            UserId = evt.UserId,
            Status = "Pending",
            CreatedUtc = DateTime.UtcNow
        });

        await db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }

    await args.CompleteMessageAsync(args.Message, cancellationToken);
}
```

Outbox sender phải có claim/lease hoặc concurrency control để nhiều instances không gửi cùng một row; nếu email provider hỗ trợ idempotency key, truyền cùng stable key. Nếu provider không hỗ trợ, cần chấp nhận giới hạn guarantee trong trường hợp timeout không rõ kết quả.

## Giải thích thiết kế sau khi sửa

- Idempotency được lưu durable thay vì trong memory.
- Consumer chỉ chịu trách nhiệm commit local work.
- External email retry được tách khỏi message lock.
- DLQ trở thành một operational workflow có reason, dashboard và runbook.
- Concurrency được coi là capacity decision.

## Trade-offs

- Outbox tăng schema và worker complexity.
- Idempotency table cần retention.
- Manual settlement tăng code paths phải test.
- Giảm concurrency có thể giảm throughput nhưng tăng stability.
- Exactly-once external side effect không thể tự suy ra nếu provider không có idempotency semantics.

## Cách kiểm thử

1. Integration test cùng `MessageId` xử lý hai lần.
2. Crash test sau SQL commit nhưng trước message complete.
3. Failure-path test email timeout sau khi provider đã nhận request.
4. Load/concurrency test nhiều replicas và SQL pool pressure.
5. Poison-message test phải dead-letter đúng policy.

## Quan sát trong production

Theo dõi queue depth, oldest-message age, delivery count distribution, complete/abandon/DLQ rate, lock-loss count, idempotency-hit count, SQL latency/pool saturation, outbox pending age, email dependency duration/error rate, worker version và correlation giữa `MessageId` với notification.

## Câu hỏi phỏng vấn mở rộng

1. Nếu email provider không hỗ trợ idempotency key thì guarantee thực tế là gì?
2. Khi nào direct Service Bus → email vẫn chấp nhận được?
3. Nếu ordering theo approval là requirement, bạn đánh giá Service Bus sessions thế nào?

```csharp
public async Task RebuildAsync(CancellationToken cancellationToken)
{
    await _elastic.Indices.DeleteAsync("products");

    await _elastic.Indices.CreateAsync("products", x => x
        .Mappings(m => m
            .Properties<ProductDocument>(p => p
                .Text(t => t.Id)
                .Text(t => t.Name)
                .Text(t => t.Description)
                .Text(t => t.Brand)
                .Text(t => t.Market)
                .Text(t => t.Status)
                .Text(t => t.UpdatedUtc))));

    var products = await _db.Products
        .Where(x => x.IsActive)
        .ToListAsync(cancellationToken);

    foreach (var product in products)
    {
        await _elastic.IndexAsync(
            ProductDocument.From(product),
            x => x.Index("products"),
            cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### Critical — Reindex xóa production index trước khi replacement sẵn sàng

**Vấn đề:** `DeleteAsync("products")` chạy đầu tiên.

**Tại sao xảy ra:** logical search endpoint và physical index dùng cùng tên.

**Ảnh hưởng production:** bất kỳ failure nào sau delete đều gây outage hoặc partial search.

**Cách sửa:** tạo physical index versioned, bulk load, validate, atomically switch alias, giữ index cũ cho rollback window.

### High — Exact fields map sai thành `text`

**Vấn đề:** `brand`, `market`, `status`, `id` dùng `text`.

**Tại sao xảy ra:** `text` phục vụ analyzed full-text; equality/filter/identity cần keyword semantics.

**Ảnh hưởng production:** term filter có thể không match business value như kỳ vọng.

**Cách sửa:** dùng `keyword` hoặc multi-field nếu cần cả full-text và exact match.

### High — `updatedUtc` map sai kiểu

**Vấn đề:** timestamp là `text`.

**Tại sao xảy ra:** mapping không encode temporal semantics.

**Ảnh hưởng production:** sort/range phụ thuộc string representation.

**Cách sửa:** dùng `date` với format phù hợp.

### High — Leading wildcard/query_string gây cost và relevance kém

**Vấn đề:** `*shoe*` dùng như universal search.

**Tại sao xảy ra:** wildcard substring search có thể mở rộng term lớn; `query_string` còn có cú pháp phức tạp hơn intent business.

**Ảnh hưởng production:** CPU/latency tăng, relevance khó đoán.

**Cách sửa:** dùng `match`/`multi_match`; autocomplete dùng prefix/search-as-you-type/analyzer phù hợp.

### High — Full rebuild materialize toàn bộ dataset

**Vấn đề:** `ToListAsync()` với hàng triệu rows.

**Tại sao xảy ra:** batch nhỏ được áp vào workload production lớn.

**Ảnh hưởng production:** memory pressure/OOM.

**Cách sửa:** stream/page bounded batches, projection fields cần thiết.

### High — Index từng document tuần tự

**Vấn đề:** mỗi product là một network request.

**Tại sao xảy ra:** không dùng bulk API.

**Ảnh hưởng production:** throughput thấp, rebuild kéo dài, khó xử lý partial failure.

**Cách sửa:** bulk theo bounded batches, inspect item-level failures, retry transient failures.

### High — Cursor chỉ nằm trong memory

**Vấn đề:** restart làm mất checkpoint.

**Tại sao xảy ra:** sync state không durable.

**Ảnh hưởng production:** bỏ sót hoặc xử lý lặp updates.

**Cách sửa:** persist checkpoint hoặc dùng durable change/outbox event source.

### High — Cursor timestamp đơn lẻ có boundary race

**Vấn đề:** nhiều rows cùng timestamp; `>` có thể bỏ sót sau crash giữa batch.

**Tại sao xảy ra:** cursor không có total ordering.

**Ảnh hưởng production:** index lệch database vĩnh viễn mà không có lỗi rõ.

**Cách sửa:** dùng composite cursor `(updated_utc, id)`.

```sql
WHERE updated_utc > @lastUtc
   OR (updated_utc = @lastUtc AND id > @lastId)
ORDER BY updated_utc, id;
```

### High — Không có source version trong search document

**Vấn đề:** khó phát hiện stale/out-of-order writes.

**Tại sao xảy ra:** document chỉ lưu presentation data.

**Ảnh hưởng production:** update cũ có thể overwrite update mới; support không biết revision nguồn.

**Cách sửa:** lưu source version/row version/updated time đủ để thực hiện stale-write protection và reconciliation.

### Medium — Không validate index trước cutover

**Vấn đề:** “job chạy xong” bị coi như production-ready.

**Tại sao xảy ra:** thiếu validation gate.

**Ảnh hưởng production:** index thiếu documents/mapping sai vẫn được serve.

**Cách sửa:** validate counts, critical item failures, representative queries, latency và business samples trước alias swap.

```sql
SELECT id,
```

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Service Bus consumer phải được thiết kế theo at-least-once delivery.
- Retry cần đi cùng idempotency.
- SQL, Service Bus và external API là các transaction boundary khác nhau.
- Exception handling sai có thể biến transient failure thành data loss.
- Elasticsearch mapping phải phản ánh full-text/filter/sort semantics.
- Reindex an toàn cần versioned index + validation + alias cutover.
- Database-to-search sync cần durable checkpoint, deterministic ordering, idempotent writes và observability.

## Mẫu tư duy cần nhớ

1. **Design retry together with idempotency.**
2. **Identify the real transaction boundary before promising consistency.**
3. **Do not destroy the serving resource before replacement is validated.**
4. **Persist progress when restart must not lose correctness.**
5. **Measure and verify instead of inferring success from “job completed”.**
