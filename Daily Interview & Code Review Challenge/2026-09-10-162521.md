# Câu 1 — React search trả dữ liệu cũ dù request mới đã hoàn tất: render snapshot, closure và Promise ordering thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** React.js, TypeScript, JavaScript event loop, closures, render lifecycle, `useEffect`, Promise ordering, `AbortController`, API integration, state correctness, frontend observability

## Bối cảnh

Một React frontend gọi ASP.NET Core search API khi user nhập từ khóa. Team dùng code sau:

```tsx
function ProductSearch() {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    if (!query.trim()) {
      setProducts([]);
      return;
    }

    setLoading(true);

    fetch(`/api/products?q=${encodeURIComponent(query)}`)
      .then(r => r.json())
      .then(data => {
        setProducts(data.items);
        setLoading(false);
      })
      .catch(() => setLoading(false));
  }, [query]);

  return (
    <>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
      />
      {loading && <span>Loading...</span>}
      <ProductList items={products} />
    </>
  );
}
```

Production symptom:

- user gõ nhanh `car` rồi tiếp tục thành `cargo`;
- request cho `cargo` đôi lúc trả về trước request `car`;
- UI hiển thị kết quả `cargo` trong chốc lát rồi bị thay bằng kết quả cũ của `car`;
- log backend cho thấy cả hai requests đều trả 200 đúng dữ liệu;
- một developer cho rằng React phải tự biết state nào “mới nhất” vì effect phụ thuộc `[query]`;
- một developer khác muốn thêm `setTimeout(300)` trong `onChange` rồi coi vấn đề được giải quyết;
- chưa có cancellation, request sequence ID hoặc debounce abstraction;
- component có thể unmount khi user chuyển route;
- team muốn giảm duplicate calls nhưng không muốn làm mất tính đúng đắn của UI.

## Câu hỏi chính

Hãy giải thích **render snapshot, JavaScript closure, `useEffect`, Promise completion ordering và state updates liên quan với nhau như thế nào** trong scenario trên. Vì sao effect của query cũ vẫn có thể cập nhật state sau effect của query mới? Debounce có giải quyết hoàn toàn race condition không? Sau đó đề xuất implementation an toàn hơn và cách verify behavior dưới network reordering/unmount.

## Câu hỏi làm rõ nên cân nhắc

1. Requirement có cho phép hủy request cũ ngay khi query đổi hay backend vẫn cần hoàn thành request vì lý do khác?
2. Search response có pagination/cursor hoặc cache layer nào khiến response ordering khó hơn không?
3. Browser/API client hiện có retry tự động hoặc service worker nào nằm giữa request không?
4. Search result phải tương ứng chính xác với query cuối cùng hay chấp nhận stale-while-revalidate UX?
5. Có cần debounce để giảm request volume, và debounce window được chọn theo UX/load evidence nào?

## Gợi ý tư duy

### Gợi ý 1

Mỗi render tạo ra một snapshot của props/state và effect callback của render đó đóng trên snapshot tương ứng.

### Gợi ý 2

Promise hoàn thành theo thời điểm I/O kết thúc, không theo thứ tự request được phát đi.

### Gợi ý 3

Debounce giảm số request nhưng không phải correctness primitive. Hãy nghĩ tới cancellation hoặc cơ chế xác định response nào còn hợp lệ.

## Cấu trúc trả lời đề xuất

1. Xác định expected UI invariant.
2. Giải thích render/effect lifecycle.
3. Giải thích closure capture và response reordering.
4. Phân biệt request reduction với race prevention.
5. Đề xuất cancellation hoặc latest-request validation.
6. Xử lý loading/error state theo request hiện hành.
7. Xử lý unmount/cleanup.
8. Test deterministic network reordering.
9. Quan sát frontend + backend telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Mỗi render của React nhìn thấy state/props của render đó; effect callback được tạo trong render và đóng trên giá trị `query` của snapshot tương ứng.
- `[query]` quyết định khi effect chạy lại; nó không tự cancel asynchronous work từ effect trước.
- Request `car` có thể hoàn thành sau `cargo`; Promise callback cũ vẫn có thể gọi `setProducts`, nên stale response ghi đè result mới.
- Debounce chỉ làm ít requests hơn; vẫn có thể có hai requests overlap và hoàn thành đảo thứ tự.
- Effect cleanup nên cancel hoặc invalidates work cũ khi query đổi/unmount.
- `AbortController` là một cách phù hợp để hủy `fetch` cũ; code vẫn phải xử lý `AbortError` khác lỗi thật.
- Loading state cũng cần gắn với request hiện hành; request cũ không nên set `loading=false` trong khi request mới còn chạy.
- Correctness phải được test bằng artificial delay/reordering, không chỉ manual typing trên network nhanh.

### Điểm cộng

- Dùng request generation/sequence ID như defense bổ sung khi underlying client/dependency không hỗ trợ cancellation hoàn toàn.
- Debounce được đặt ngoài correctness logic; cancellation/latest-wins semantics vẫn tồn tại.
- Nếu dùng library như React Query/TanStack Query trong tương lai, vẫn cần hiểu query-key, cancellation/staleness semantics thay vì giả định library tự giải quyết mọi race.
- Encode query đúng và handle non-2xx trước `r.json()`.
- Không log raw sensitive search terms nếu chúng có thể chứa dữ liệu nhạy cảm.

### Senior+

- Phân biệt UI “latest intent wins” với backend request cancellation: browser abort không bảo đảm server-side work luôn dừng nếu cancellation không được propagate/observed.
- Nếu backend hỗ trợ `CancellationToken`, giải thích cách client disconnect có thể propagate qua ASP.NET Core request abort, nhưng application/downstream code phải observe token để tiết kiệm work.
- Thiết kế state machine rõ: idle/loading/success/error cho current request identity thay vì nhiều booleans độc lập dễ race.
- Nhận ra Strict Mode development behavior có thể expose effect bugs nhưng không nên dùng production-only assumptions để giải thích race chính.

## Hướng giải quyết tham khảo

Root cause không nằm ở việc backend trả sai dữ liệu. Hai HTTP calls là hai asynchronous operations độc lập. Effect chạy cho render có `query="car"`, rồi user gõ thêm và React render với `query="cargo"`; effect mới chạy. Cả hai Promise chains vẫn còn sống trừ khi cleanup chủ động hủy/invalidates operation cũ.

Một implementation phù hợp:

```tsx
function ProductSearch() {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const normalized = query.trim();

    if (!normalized) {
      setProducts([]);
      setLoading(false);
      setError(null);
      return;
    }

    const controller = new AbortController();

    async function run() {
      setLoading(true);
      setError(null);

      try {
        const response = await fetch(
          `/api/products?q=${encodeURIComponent(normalized)}`,
          { signal: controller.signal });

        if (!response.ok) {
          throw new Error(`Search failed: ${response.status}`);
        }

        const data: SearchResponse = await response.json();
        setProducts(data.items);
      } catch (err) {
        if (err instanceof DOMException && err.name === "AbortError") {
          return;
        }

        setError("Search failed");
      } finally {
        if (!controller.signal.aborted) {
          setLoading(false);
        }
      }
    }

    void run();

    return () => {
      controller.abort();
    };
  }, [query]);

  return (
    <>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
      />
      {loading && <span>Loading...</span>}
      {error && <span>{error}</span>}
      <ProductList items={products} />
    </>
  );
}
```

Nếu client library hoặc API không hỗ trợ cancellation đủ mạnh, có thể dùng sequence ID:

```tsx
const requestIdRef = useRef(0);

useEffect(() => {
  const requestId = ++requestIdRef.current;

  async function run() {
    const data = await search(query);

    if (requestId !== requestIdRef.current) {
      return;
    }

    setProducts(data.items);
  }

  void run();
}, [query]);
```

Debounce có thể đặt trước việc phát request để giảm load, nhưng vẫn giữ cancellation/latest-request check. Ví dụ user pause 250–300 ms mới search không làm race “bất khả thi”; network chậm vẫn có thể tạo overlap giữa hai debounce windows.

Test quan trọng:

- mock request A chậm 500 ms và B chậm 50 ms, assert cuối cùng UI chỉ hiện B;
- query đổi liên tục 10 lần;
- component unmount khi request pending;
- request cũ abort trong khi request mới success;
- 500/timeout cho request cũ không được ghi đè success state của request mới.

Trong production nên quan sát client request count, aborted count, search latency, backend cancellation/aborted request telemetry và correlation giữa query version/request ID với UI state transitions nếu cần debug.

Tài liệu tham khảo:

- React — Synchronizing with Effects: `https://react.dev/learn/synchronizing-with-effects`
- React — Lifecycle of Reactive Effects: `https://react.dev/learn/lifecycle-of-reactive-effects`
- MDN — AbortController: `https://developer.mozilla.org/docs/Web/API/AbortController`

## Mẫu trả lời trong phỏng vấn

“Em coi đây là race giữa hai asynchronous effects. Effect của render `car` đóng trên query `car`; effect của render `cargo` đóng trên `cargo`. Dependency array chỉ khiến effect mới chạy khi query đổi, nó không cancel fetch cũ. Vì network completion không theo request order, request `car` có thể resolve sau và setProducts bằng dữ liệu stale.

Em sẽ define invariant là latest user intent wins. Cleanup của effect abort request cũ bằng AbortController; nếu client không support cancellation đầy đủ, em thêm request sequence và chỉ cho response của current request commit state. Loading/error cũng gắn với request hiện hành để callback cũ không tắt loading của request mới.

Debounce chỉ giảm volume, không phải correctness fix, nên có thể dùng thêm nhưng không thay cancellation/latest-wins logic. Em test bằng artificial response reordering và unmount, đồng thời theo dõi aborted requests và backend cancellation để biết optimization có thực sự giảm work hay chỉ dừng client-side update.”

## Câu hỏi đào sâu

1. Nếu browser abort request nhưng backend vẫn tiếp tục query SQL 10 giây, bạn sẽ trace và sửa cancellation path end-to-end thế nào?
2. Nếu UX muốn giữ kết quả query cũ trong lúc query mới loading thay vì clear ngay, bạn thay state model thế nào mà vẫn tránh stale overwrite?
3. Một teammate nói “chuyển toàn bộ sang React Query thì không cần hiểu race này nữa”; bạn phản biện recommendation đó như thế nào?

## Lỗi trả lời thường gặp

- Nghĩ dependency array tự cancel asynchronous operation cũ.
- Dùng debounce như fix duy nhất cho stale-response race.
- Abort request nhưng catch mọi exception thành error UI, khiến normal cancellation trông như lỗi.
- Request cũ vẫn được phép set loading/error state sau request mới.
- Chỉ test happy path trên localhost với network quá nhanh.

## Thang điểm 0–10

- **0–2:** chỉ đề xuất debounce hoặc “await đúng thứ tự”.
- **3–4:** nhận ra race nhưng chưa giải thích render snapshot/closure/effect cleanup.
- **5–6:** giải thích đúng Promise ordering, cleanup và AbortController.
- **7–8:** xử lý request identity, loading/error races, deterministic tests và backend cancellation.
- **9–10:** reasoning rõ về latest-intent semantics, end-to-end cancellation, state-machine design và trade-off giữa UX/load/correctness.

# Câu 2 — Cosmos DB 429 tăng nhưng account vẫn còn RU/s tổng: hot partition, query cost hay traffic skew?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, logical/physical partitions, RU/s, 429 rate limiting, normalized RU consumption, query cost, SDK retries, hot partition, Azure Monitor, incident response, data modeling

## Bối cảnh

Một event-management platform dùng Azure Cosmos DB API for NoSQL lưu attendee activity. Container có partition key `/tenantId`.

Bình thường hệ thống ổn định. Trong một campaign lớn:

- API p95 tăng từ khoảng 200 ms lên 2–6 giây;
- Application Insights dependency telemetry ghi nhận nhiều calls tới Cosmos DB có retry/throttle behavior;
- Cosmos DB metrics có 429 tăng đáng kể;
- tổng provisioned throughput của container chưa nhìn như luôn bị sử dụng hết;
- một enterprise tenant chiếm khoảng 35% traffic trong campaign;
- phần lớn writes và point reads của tenant đó đi vào cùng `tenantId`;
- một dashboard query mới lọc `tenantId`, `eventType`, time range và sort theo `createdAt`;
- một engineer đề xuất tăng RU/s toàn container gấp 4;
- engineer khác đề xuất bỏ partition key filter để query “trải đều hơn”;
- SDK retry policy hiện tại chưa được review;
- chưa biết normalized RU consumption theo `PartitionKeyRangeId`, RU/query, index policy hoặc distribution của logical partition keys.

Không giả định trước root cause duy nhất là hot partition; query regression, indexing, retry amplification hoặc traffic burst đều có thể cùng góp phần.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident theo **impact → stabilize → evidence → competing hypotheses → investigation → root cause → remediation → prevention**. Giải thích vì sao một container có thể bị 429 trên một partition key range dù nhìn tổng RU/s còn headroom, cách phân biệt hot partition với expensive query hoặc toàn-container saturation, và khi nào thay partition key/data model mới là giải pháp đúng thay vì chỉ tăng throughput.

## Câu hỏi làm rõ nên cân nhắc

1. Normalized RU consumption theo từng `PartitionKeyRangeId` có một range ở gần 100% trong khi ranges khác thấp hơn không?
2. Tỷ lệ 429 thực tế đến từ point reads, writes hay dashboard queries; RU charge của từng operation thay đổi thế nào sau release?
3. Partition key `/tenantId` được chọn vì transactional/query boundary nào, và tenant lớn nhất có thể tăng tới bao nhiêu traffic/data?
4. SDK retry count/retry-after delay đang làm end-to-end latency tăng bao nhiêu trước khi error tới application?
5. Autoscale/manual throughput, indexing policy và query execution metrics hiện tại là gì?

## Gợi ý tư duy

### Gợi ý 1

Đừng nhìn chỉ tổng RU/s. Throughput được phân phối qua physical partitions; traffic skew có thể làm một range nóng trong khi range khác còn dư.

### Gợi ý 2

429 là signal phải đặt cạnh latency và retry behavior. Một số 429 có thể được SDK retry thành công nhưng vẫn làm p95/p99 tăng.

### Gợi ý 3

Partition key là data-model decision dài hạn. Trước khi thay, cần chứng minh access pattern và skew khiến logical partition hiện tại không còn scale phù hợp.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact.
2. Giảm pressure tức thời nếu cần.
3. Thu metrics theo partition range/operation/query.
4. Correlate 429, retry và latency.
5. So sánh hot-partition, query-cost, indexing và total-throughput hypotheses.
6. Chốt root cause theo evidence.
7. Chọn mitigation ngắn hạn.
8. Đánh giá throughput/index/query optimization.
9. Đánh giá repartition/data-model evolution.
10. Load test và monitor campaign pattern.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Provisioned throughput của container được phân bổ qua physical partitions; traffic tập trung có thể làm một partition key range đạt normalized RU 100% và bị 429 dù ranges khác chưa bão hòa.
- Logical partition key có traffic rất lớn như một tenant “elephant” có thể trở thành hot key/range.
- Tổng RU utilization thấp không đủ để loại trừ hot partition.
- Cần xem 429 theo operation và normalized RU by partition range, không chỉ aggregate count.
- SDK có thể retry 429; application có thể không thấy mọi 429 như final failure nhưng latency vẫn tăng.
- Expensive cross-partition/query/index behavior cũng có thể tăng RU và contention; phải đo request charge/query metrics.
- Bỏ partition key filter thường làm query fan-out rộng hơn chứ không phải cách “chia đều” workload miễn phí.
- Tăng RU/s có thể là mitigation nếu toàn workload cần capacity và physical distribution cho phép, nhưng không chữa partition-key skew vô hạn.
- Thay partition key thường cần data migration/new container strategy; không phải hotfix nhẹ.

### Điểm cộng

- Tách point-read/write path khỏi analytics/dashboard path; cân nhắc derived analytical/read model nếu dashboard query không phù hợp transactional container.
- Review composite indexes/index policy dựa trên query shape thay vì disable indexing tùy tiện.
- Dùng synthetic/composite partition key khi business access pattern cho phép shard tenant lớn, ví dụ tenant + bucket/entity dimension, nhưng phải xét query fan-out và transaction boundary.
- Có admission control/backoff cho campaign spikes để tránh retry storm.
- Dùng Azure Monitor diagnostics để correlate request charge, 429, normalized RU, latency và partition ranges.

### Senior+

- Nhận ra repartitioning thay đổi transaction/query locality và có cost dài hạn; sharding tenant lớn có thể giảm hot key nhưng tăng fan-out cho tenant-wide queries.
- Thiết kế routing/migration version để old/new partitioning coexist nếu zero-downtime requirement.
- Phân biệt data distribution problem với workload distribution problem: nhiều data không đồng nghĩa nhiều RU nếu traffic vẫn dồn vào một logical key.
- Định nghĩa SLO theo user-facing latency/error, không coi “0% 429” là mục tiêu tuyệt đối nếu retry rate thấp và latency vẫn đạt SLO.

## Hướng giải quyết tham khảo

### 1. Stabilize

Nếu campaign đang gây p95 2–6 giây, trước tiên xác định các endpoints bị ảnh hưởng và tenant nào tạo load. Có thể tạm giảm concurrency của non-critical dashboard refresh, tăng cache/batch ở layer phù hợp hoặc scale RU như mitigation có kiểm soát nếu metrics cho thấy capacity thực sự thiếu.

Không bỏ partition key filter. Điều đó có thể biến query targeted thành cross-partition fan-out và tăng RU/latency.

### 2. Evidence

Tôi sẽ thu:

- normalized RU consumption theo `PartitionKeyRangeId`;
- 429 rate theo operation/container;
- request charge của reads/writes/queries;
- query latency và diagnostics;
- partition-key traffic distribution;
- SDK retry count/retry delay;
- application p50/p95/p99;
- deployment/config timeline;
- dashboard request frequency;
- index policy/query plan diagnostics khi phù hợp.

Microsoft Learn mô tả rằng normalized RU 100% trên một partition key range có thể dẫn tới 429 cho requests tiếp tục nhắm vào range đó, trong khi ranges khác vẫn còn capacity. Tài liệu cũng khuyến nghị dùng normalized RU consumption để phát hiện hot partitions.

Tài liệu xác minh:

- Microsoft Learn — Monitor normalized RU/s: `https://learn.microsoft.com/azure/cosmos-db/monitor-normalized-request-units`
- Microsoft Learn — Partitioning and horizontal scaling: `https://learn.microsoft.com/azure/cosmos-db/partitioning`

### 3. Competing hypotheses

**Hypothesis A — Hot tenant/partition range.**  
Một tenant chiếm 35% traffic; nếu normalized RU của range chứa tenant đó gần 100% nhưng ranges khác thấp, đây là evidence mạnh.

**Hypothesis B — Query regression.**  
Dashboard query mới có thể consume RU lớn vì filter/sort/indexing không phù hợp hoặc fan-out ngoài dự kiến.

**Hypothesis C — Whole-container capacity.**  
Nếu nhiều ranges cùng gần 100%, aggregate demand có thể thực sự vượt throughput.

**Hypothesis D — Retry amplification.**  
Client retry có thể tăng request pressure/latency nếu workload liên tục vượt capacity.

Có thể A + B cùng xảy ra: query mới tốn RU nhất đúng lúc hot tenant tăng traffic.

### 4. Short-term mitigation

Nếu hot range là nguyên nhân:

- giảm frequency/concurrency của non-critical reads;
- cache bounded read result nếu semantics cho phép;
- optimize query/index;
- tách analytics path khỏi transactional hot path;
- tăng throughput nếu có hiệu quả và cost chấp nhận được;
- respect retry-after/backoff thay vì custom tight-loop retry.

Nếu tất cả ranges cùng saturated, tăng throughput/autoscale policy có thể là giải pháp chính xác hơn.

### 5. Partition-key redesign

Nếu một `tenantId` có thể phát triển tới mức một logical partition trở thành sustained hot key, partitioning model cần xem lại.

Một alternative concept:

```text
/partitionKey = tenantId + ':' + bucket
```

Trong đó bucket có thể theo event, hash hoặc bounded time window tùy access pattern. Nhưng trade-off là tenant-wide query phải fan-out nhiều buckets. Nếu transaction cần atomicity trong một tenant-wide logical partition, việc shard tenant có thể làm semantics phức tạp hơn.

Do đó không chọn synthetic key trước khi inventory queries/writes/transaction boundaries.

### 6. Dashboard isolation

Nếu dashboard query đọc time-range lớn và không yêu cầu strong freshness, có thể build projection/materialized summary riêng thay vì repeatedly scan transactional events. Đây có thể là Redis/cache, another Cosmos container, analytical store hoặc SQL/search projection tùy requirement; không mặc định một công nghệ.

### 7. Testing và monitoring

Load test phải mô phỏng **skew**, không chỉ uniform traffic. Ví dụ 35–50% requests vào một tenant lớn.

Theo dõi:

- user-facing p95/p99;
- 429 rate và SDK retries;
- normalized RU per range;
- RU/request theo operation;
- top partition keys by traffic;
- query latency/charge;
- autoscale/provisioned throughput;
- dashboard refresh volume.

Alert khi sustained hot range + latency vượt SLO, không chỉ alert mọi single 429.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhìn aggregate RU rồi kết luận account còn dư. Cosmos phân phối throughput qua physical partitions, nên một partition range có thể đạt normalized RU 100% trong khi ranges khác thấp; requests vào range đó vẫn bị 429. Với tenant chiếm 35% traffic, hot key là hypothesis mạnh nhưng em vẫn đo query charge và deployment timeline vì dashboard query mới cũng có thể làm RU tăng.

Em sẽ correlate 429 theo operation, normalized RU per range, request charge, SDK retries và p95/p99. Nếu chỉ một range nóng, tăng toàn container có thể giảm triệu chứng nhưng không sửa skew dài hạn. Nếu tất cả ranges nóng thì throughput increase/autoscale hợp lý hơn.

Em không bỏ tenant partition filter vì fan-out có thể tốn hơn. Với sustained elephant tenant, em đánh giá composite/synthetic partition key để shard tenant, nhưng chỉ sau khi xem transaction/query locality vì shard sẽ làm tenant-wide queries phức tạp hơn. Nếu dashboard là workload khác, em tách projection/read model thay vì ép transactional container phục vụ mọi access pattern.”

## Câu hỏi đào sâu

1. Nếu normalized RU chỉ có một range ở 100% nhưng tăng total RU/s gấp đôi làm 429 giảm, bạn có coi partition-key problem đã được giải quyết chưa?
2. Nếu shard một tenant theo tháng giúp write scale nhưng business thường query 24 tháng lịch sử trong một request, trade-off và alternatives là gì?
3. Nếu metrics có 3% 429 nhưng user p95 vẫn đạt SLO vì SDK retries nhanh, bạn có coi đây là incident cần loại bỏ hoàn toàn không?

## Lỗi trả lời thường gặp

- Chỉ nhìn total RU/s và bỏ qua normalized RU theo partition range.
- Thấy 429 là tăng RU ngay mà không đo skew/query cost.
- Bỏ partition key filter để “chia tải”.
- Repartition mà không xét query fan-out và transactional boundary.
- Viết custom immediate retry loop bỏ qua server retry guidance/backoff.

## Thang điểm 0–10

- **0–2:** chỉ tăng RU hoặc retry.
- **3–4:** biết hot partition nhưng không có evidence plan.
- **5–6:** hiểu physical/logical partition, normalized RU, query charge và SDK retries.
- **7–8:** có mitigation, skew load test, indexing/query analysis và repartition trade-offs.
- **9–10:** phân tích workload/data distribution sâu, migration/coexistence, SLO-based interpretation của 429 và biết khi nào tách read model thay vì đổi partition key.

# Câu 3 — Xử lý file theo lịch: Azure Functions hay .NET BackgroundService, và có cần Kubernetes chỉ vì workload sẽ tăng?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Azure Functions, .NET `BackgroundService`, Azure Blob Storage, Azure Service Bus, Azure App Service, scheduled jobs, retries, idempotency, scaling, deployment, observability, architecture trade-offs, cost of complexity

## Bối cảnh

Một enterprise platform cần xử lý file import từ đối tác.

Requirements ban đầu:

- đối tác upload CSV/JSON files vào Azure Blob Storage;
- bình thường khoảng 5.000 files/ngày, mỗi file 1–20 MB;
- cuối tháng có burst có thể gấp 10 lần;
- mỗi file cần validate schema, transform records, gọi SQL Server và một external REST API;
- processing time thường 20–90 giây/file, nhưng một số file lỗi hoặc external API chậm có thể kéo dài hơn;
- duplicate upload cùng logical batch có thể xảy ra;
- file lỗi phải được quarantine và có audit trail;
- business chấp nhận eventual processing trong vài phút, không cần synchronous HTTP response;
- platform hiện có ASP.NET Core App Service và vài `BackgroundService` jobs;
- team có kinh nghiệm Azure Functions nhưng không có dedicated Kubernetes/SRE team;
- một engineer đề xuất Blob-triggered Azure Function;
- engineer khác muốn dùng một `BackgroundService` polling Blob Storage mỗi 30 giây;
- architect đề xuất Kubernetes vì “burst 10x thì serverless hoặc worker đều khó control”;
- chưa có exact concurrency target, external API rate limit, retry policy, poison-file behavior, processing SLA hoặc cost budget.

## Câu hỏi chính

Hãy thiết kế processing architecture và quyết định khi nào chọn **Azure Functions, .NET BackgroundService/Worker Service, Service Bus-based worker hoặc Kubernetes**. Bạn phải phân tích trigger/delivery semantics, idempotency, duplicate processing, retries, concurrency/backpressure, external API limits, state tracking, failure recovery, observability, deployment và cost of operational complexity. Vấn đề có nhiều solution hợp lệ; không tự động reward serverless hay Kubernetes.

## Câu hỏi làm rõ nên cân nhắc

1. Processing SLA là 1 phút, 10 phút hay hàng giờ, và burst backlog tối đa chấp nhận là bao nhiêu?
2. External REST API có rate limit/idempotency key/bulk endpoint nào không?
3. Một file phải xử lý atomically toàn bộ hay có thể checkpoint/resume theo chunks/records?
4. Duplicate logical batch được nhận diện bằng filename, partner batch ID, checksum hay business key nào?
5. Team ưu tiên operational simplicity, predictable cost hay fine-grained scaling control ở mức nào?

## Gợi ý tư duy

### Gợi ý 1

Tách **event detection** khỏi **work execution**. Blob xuất hiện không nhất thiết có nghĩa worker phải xử lý toàn bộ file ngay trong cùng trigger invocation.

### Gợi ý 2

Autoscale mà không có downstream backpressure có thể biến external API rate limit thành retry storm.

### Gợi ý 3

Hãy chọn execution platform sau khi xác định workload semantics, không phải trước. Functions, Worker Service và Kubernetes đều không tự tạo idempotency.

## Cấu trúc trả lời đề xuất

1. Clarify SLA, burst và external constraints.
2. Xác định ingestion/event contract.
3. Thiết kế durable work queue/state.
4. Thiết kế idempotency/deduplication.
5. Chọn execution model.
6. Thiết kế concurrency/backpressure.
7. Retry/poison/quarantine.
8. Transaction/data consistency.
9. Deployment/rollout.
10. Observability/SLO.
11. So sánh operational cost và evolution path.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nên để polling nhiều instances tự xử lý Blob mà không có coordination/idempotency, vì duplicate work/race rất dễ xảy ra.
- Blob event/trigger nên được coi là potentially repeated; processing phải idempotent dựa trên stable logical batch identity.
- Với external API rate limit, scale-out phải có bounded concurrency/backpressure; nhiều workers hơn không luôn tăng throughput hữu ích.
- Azure Functions phù hợp khi event-driven workload, burst scaling và managed execution model có lợi; nhưng execution duration, hosting plan, trigger semantics và downstream limits phải được kiểm tra.
- `BackgroundService`/Worker Service phù hợp khi team muốn process lifecycle/configuration/concurrency rõ, workload steady hoặc cần control lâu dài; horizontal scaling vẫn cần distributed work coordination.
- Service Bus giữa ingestion và processing có thể tạo durable queue, retry/DLQ/backpressure seam tốt, nhưng chỉ nên thêm khi failure/retry/decoupling requirements justify complexity.
- Kubernetes không tự cần thiết chỉ vì burst 10x; App Service/Functions/managed queue có thể đơn giản hơn rất nhiều cho team không có platform ownership.
- File processing cần persisted state như Received/Processing/Succeeded/Failed/Quarantined và idempotent transitions.
- Retry cần phân biệt transient dependency failure với invalid file/poison work.
- Observability phải theo batch/file lifecycle, queue age, processing latency, failure reason và external dependency health.

### Điểm cộng

- Dùng Event Grid/Blob event hoặc trigger để tạo work item nhỏ chứa blob URI + immutable blob version/ETag + batch ID, rồi processor đọc file từ Blob.
- Nếu cần strict control, enqueue command vào Service Bus và worker consume theo bounded concurrency.
- Idempotency record có unique partner batch ID/checksum để duplicate event không tạo duplicate DB/API side effect.
- Nếu file lớn, stream/chunk thay vì load toàn bộ file vào memory.
- Quarantine original file + structured validation report; không retry invalid schema vô hạn.
- Dùng Managed Identity cho Blob/Service Bus/SQL-compatible Azure resources khi phù hợp và Key Vault cho secrets của external provider.

### Senior+

- Phân biệt platform retry với business retry; retry invocation không thay thế idempotent business operation.
- Nếu external API có ambiguous timeout, lưu operation state/idempotency key hoặc reconciliation thay vì retry create mù.
- Thiết kế lease/visibility/message-lock/checkpoint semantics để crash giữa processing không mất work.
- Nêu được trigger để migrate từ Functions sang dedicated workers hoặc ngược lại: measured cost, execution profile, scaling behavior, operational control—not preference.
- Nếu requirement cần multi-stage long-running workflow/checkpoints, cân nhắc orchestration/state-machine approach thay vì một invocation khổng lồ.

## Hướng giải quyết tham khảo

Một baseline architecture hợp lý:

```text
Partner
  ↓
Azure Blob Storage
  ↓ event/trigger
Ingestion handler
  ↓
ProcessingJobs state + durable queue
  ↓
Service Bus
  ↓
Processor (Azure Functions hoặc .NET Worker)
  ↓
SQL Server + External API
  ↓
Succeeded / Failed / Quarantined
```

Không phải mọi deployment cần toàn bộ components. Nếu workload nhỏ và Blob-triggered Function đã có retry/idempotency/state tốt, Service Bus có thể chưa cần. Nếu cần explicit backlog, DLQ, controlled consumption và decouple Blob event handling khỏi long processing, queue seam trở nên đáng giá.

### 1. Stable identity

Mỗi logical batch cần ID ổn định:

```text
PartnerId + BatchId
```

hoặc checksum nếu business contract không có BatchId. Database có unique constraint:

```sql
CREATE UNIQUE INDEX UX_ProcessingJob_Partner_Batch
ON ProcessingJobs(PartnerId, BatchId);
```

Duplicate event/upload chỉ resolve cùng job thay vì chạy side effect lần hai.

### 2. State machine

```text
Received
  → Queued
  → Processing
  → Succeeded
  → FailedTransient
  → Quarantined
```

State transition lưu attempt count, last error category, blob ETag/version, timestamps và correlation ID.

### 3. Functions option

Azure Functions tốt khi event-driven bursts cần managed scaling và team muốn ít infrastructure management. Nhưng phải chọn hosting plan theo execution profile và current platform limits, không dựa trên assumption.

Microsoft Learn hiện mô tả `functionTimeout` khác nhau theo hosting plan và HTTP-triggered Functions có additional response-time constraints; workload này không cần synchronous HTTP nên có thể dùng background/event trigger. Long-running hoặc multi-stage work vẫn nên được thiết kế để checkpoint/queue thay vì dựa vào một invocation vô hạn.

Tài liệu xác minh:

- Microsoft Learn — Azure Functions scale and hosting: `https://learn.microsoft.com/azure/azure-functions/functions-scale`

Nếu function xử lý 20–90 giây/file và burst cao, phải benchmark actual scale behavior và downstream capacity. Nếu external API chỉ cho 50 concurrent requests, Functions scale tới hàng trăm executions không phải success.

### 4. Worker Service option

Một .NET Worker/BackgroundService có thể consume Service Bus với explicit concurrency:

```csharp
public sealed class ImportWorker : BackgroundService
{
    private readonly IJobReceiver _receiver;
    private readonly IImportProcessor _processor;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in _receiver.ReadAllAsync(stoppingToken))
        {
            await _processor.ProcessAsync(job, stoppingToken);
        }
    }
}
```

Production implementation cần concurrency, settlement/retry, scoped dependencies và graceful shutdown chuẩn. Nếu scale nhiều worker instances, queue sẽ coordinate competing consumers tốt hơn tự polling Blob list.

Worker có thể host trên App Service/WebJob/container/VM tùy operational environment. Không nhất thiết Kubernetes.

### 5. Backpressure

Nếu external API limit 50 concurrent calls, processing concurrency nên bounded around proven capacity, ví dụ bằng consumer configuration hoặc `SemaphoreSlim` inside one process, nhưng distributed global limit cần design phù hợp provider/rate-limit semantics.

Không tạo 10.000 immediate retries khi provider trả 429/503. Dùng Retry-After khi có, exponential backoff/jitter và circuit/degradation strategy phù hợp.

### 6. Failure handling

- schema invalid → quarantine, không transient retry;
- SQL deadlock/transient network → bounded retry;
- external 429 → backoff/reschedule;
- external timeout sau possible success → reconcile/idempotency key;
- worker crash → message/work item được redeliver, processor vẫn idempotent;
- poison repeated failure → DLQ/manual workflow.

### 7. Kubernetes decision

Kubernetes chỉ đáng giá nếu organization đã có platform, cần standardized container orchestration, workload mix/placement/resource control hoặc operational requirements khác mà simpler managed hosting không đáp ứng.

Burst 10x một mình không đủ. Managed Functions + Service Bus hoặc dedicated workers autoscale trên queue length có thể đạt cùng business goal với ít operational surface hơn.

### 8. Deployment

- version work-message contracts backward-compatible;
- worker release canary/wave;
- schema migration additive khi mixed versions coexist;
- ability pause consumers;
- poison/DLQ replay tooling;
- deployment ID/version trong telemetry.

### 9. Observability

Dashboard:

- queue depth + oldest message age;
- files Received/Processing/Succeeded/Quarantined;
- p50/p95 processing duration;
- attempts/retry count;
- duplicate-suppression count;
- external API latency/429/5xx;
- SQL latency/errors;
- worker/function concurrency;
- poison/DLQ volume;
- end-to-end batch SLA.

Alert theo oldest-message-age và failure rate, không chỉ CPU.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chọn Functions hay Kubernetes trước khi chốt SLA và downstream limits. Em tách ingestion khỏi execution: Blob event tạo một durable job với stable PartnerId + BatchId; processor consume job và phải idempotent vì event/queue delivery có thể lặp.

Nếu workload event-driven, 20–90 giây/file và burst 10x, Azure Functions có thể rất phù hợp, nhưng em giới hạn concurrency theo external API capacity và kiểm tra hosting plan/execution semantics. Nếu cần control process/concurrency ổn định hơn, .NET Worker consume Service Bus cũng đơn giản và dễ vận hành. Service Bus đáng giá khi cần durable backlog, DLQ và decouple ingestion khỏi processing.

Em không chọn Kubernetes chỉ vì burst; với team không có platform/SRE, operational cost có thể lớn hơn lợi ích. Kubernetes chỉ vào khi có requirement orchestration/standard platform thực sự.

State machine Received → Processing → Succeeded/Quarantined, unique batch ID, bounded retry và reconciliation cho ambiguous external timeouts sẽ bảo đảm correctness. Em đo queue age, processing p95, retries, DLQ và downstream latency để scale theo bottleneck thực tế.”

## Câu hỏi đào sâu

1. Nếu Functions scale rất nhanh nhưng external API chỉ chịu 30 requests đồng thời, bạn implement global backpressure thế nào mà không mất lợi ích của queue?
2. Nếu một file 2 GB cần xử lý 3 giờ và checkpoint từng 100.000 records, recommendation Functions vs Worker của bạn thay đổi thế nào?
3. Một architect yêu cầu Kubernetes để “sau này dễ chuyển cloud”; bạn cần những evidence/requirements nào để chấp nhận complexity đó?

## Lỗi trả lời thường gặp

- Chọn Azure Functions chỉ vì “serverless tự scale” mà bỏ qua downstream rate limits.
- Dùng BackgroundService polling Blob trên nhiều instances nhưng không có coordination/idempotency.
- Retry invalid file như transient failure.
- Chọn Kubernetes vì burst/load mà không phân tích managed alternatives và team capability.
- Không có durable state/identity nên crash hoặc duplicate event tạo side effects lặp.

## Thang điểm 0–10

- **0–2:** chọn platform theo preference, không có failure model.
- **3–4:** có queue/worker idea nhưng idempotency/backpressure còn mơ hồ.
- **5–6:** có durable job, bounded concurrency, retries/quarantine và platform trade-off hợp lý.
- **7–8:** có state machine, ambiguous-failure handling, deployment compatibility và SLO telemetry.
- **9–10:** architecture tiến hóa theo measured workload, phân biệt trigger/execution/business guarantees, biết khi nào thêm hoặc tránh Service Bus/Kubernetes.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- React effect dependency không tự cancel asynchronous work; stale UI thường xuất phát từ response ordering và closure/render snapshot semantics.
- Debounce là load/UX optimization, không thay thế cancellation hoặc latest-request correctness.
- Cosmos DB có thể throttle một hot partition key range dù aggregate throughput nhìn còn headroom; cần normalized RU và request-charge evidence.
- Partition-key design phải dựa trên traffic/query/transaction locality; repartitioning có trade-off thực tế.
- Functions, Worker Service, Service Bus và Kubernetes là execution/coordination choices; không công nghệ nào tự tạo idempotency, backpressure hay reliable business semantics.
- Autoscaling phải xét downstream capacity, không chỉ queue depth hoặc traffic burst.

## Mẫu tư duy cần nhớ

- **Separate request reduction from correctness guarantees.**
- **Measure distribution, not only aggregate utilization.**
- **Design retry together with idempotency and backpressure.**
- **Separate event detection from durable work execution when failure semantics require it.**
- **Choose operational complexity only when requirements and evidence justify it.**
