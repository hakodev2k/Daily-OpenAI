# Code Review Challenge 1 — Upload tài liệu đối tác lên Azure Blob Storage

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Blob Storage, authorization, file-upload security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10

## Bối cảnh

Một ứng dụng B2B cho phép nhân viên của từng tenant tải hợp đồng PDF lên Azure Blob Storage. API chạy trên Azure App Service, sử dụng Managed Identity trong môi trường production nhưng mã hiện tại vẫn dùng connection string. Hệ thống có 60 tenant; một số tenant có nhiều người dùng cùng tải file. Metadata của tài liệu được ghi trong SQL Server bởi dịch vụ khác sau khi API trả kết quả. Tài liệu chỉ người có quyền trong tenant mới được xem. Đội vận hành phát hiện tên file trùng nhau, link tài liệu bị chia sẻ ra ngoài, bộ nhớ tăng đột biến khi tải file lớn và chi phí storage tăng. Giới hạn sản phẩm dự kiến: PDF tối đa 20 MiB. Chưa có cơ chế quét malware. Yêu cầu không làm gián đoạn tài liệu đã tồn tại.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobServiceClient _blobs;
    private readonly IConfiguration _config;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobServiceClient blobs,
        IConfiguration config,
        ILogger<DocumentsController> logger)
    {
        _blobs = blobs;
        _config = config;
        _logger = logger;
    }

    [HttpPost("{tenantId}/upload")]
    public async Task<IActionResult> Upload(
        string tenantId, IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Empty file");

        var container = _blobs.GetBlobContainerClient("contracts");
        await container.CreateIfNotExistsAsync(
            PublicAccessType.Blob);

        var blob = container.GetBlobClient(
            $"{tenantId}/{file.FileName}");

        using var memory = new MemoryStream();
        await file.CopyToAsync(memory);
        memory.Position = 0;

        await blob.UploadAsync(memory, overwrite: true);

        var sas = blob.GenerateSasUri(
            BlobSasPermissions.Read,
            DateTimeOffset.UtcNow.AddDays(30));

        _logger.LogInformation(
            "Uploaded {File} for {Tenant}, link {Link}",
            file.FileName, tenantId, sas);

        return Ok(new
        {
            url = sas.ToString(),
            fileName = file.FileName
        });
    }
}
```

## Kết quả code review tham khảo

### Critical — Container cho phép truy cập blob công khai

**Vấn đề:** `CreateIfNotExistsAsync(PublicAccessType.Blob)` yêu cầu anonymous blob access khi account cho phép.  
**Tại sao xảy ra:** Code nhầm SAS với quyền bảo vệ duy nhất; SAS không thu hồi quyền đọc công khai. Account có thể chặn anonymous access, khi đó lời gọi tạo container có thể thất bại hoặc thiết lập này không có hiệu lực.  
**Ảnh hưởng production:** Lộ hợp đồng nhạy cảm nếu anonymous access được cho phép.  
**Cách sửa:** Đảm bảo storage account cấm anonymous access và container private; kiểm toán container hiện tại, vô hiệu hóa public access, đánh giá dữ liệu đã lộ và thực hiện quy trình ứng phó sự cố.

### Critical — Không kiểm tra quyền tenant

**Vấn đề:** `tenantId` do client tự cung cấp, endpoint không có `[Authorize]` hay tenant-scoped authorization trong code.  
**Tại sao xảy ra:** Tin vào route parameter thay vì identity và policy.  
**Ảnh hưởng production:** Ghi dữ liệu sang tenant khác, tạo nội dung giả mạo hoặc khai thác quyền của API.  
**Cách sửa:** Bắt buộc authentication; kiểm tra quyền upload theo tenant từ trusted identity và dữ liệu phân quyền server-side, không chỉ so sánh chuỗi claim tùy ý.

### High — Ghi đè tài liệu bằng tên file

**Vấn đề:** Tên blob lấy từ `file.FileName`, `overwrite: true`.  
**Tại sao xảy ra:** Tên hiển thị bị dùng làm khóa lưu trữ duy nhất.  
**Ảnh hưởng production:** Mất phiên bản tài liệu; upload đồng thời gây last-writer-wins.  
**Cách sửa:** Dùng ID server-generated bất biến, upload với điều kiện không tồn tại; lưu tên gốc dưới dạng metadata đã sanitize.

### High — Không giới hạn và kiểm tra nội dung upload

**Vấn đề:** Không có limit ứng dụng, kiểm tra MIME/signature, quy trình malware scan hoặc trạng thái quarantine.  
**Tại sao xảy ra:** `IFormFile` được tin tưởng ngay sau khi có length.  
**Ảnh hưởng production:** Upload nội dung nguy hiểm, file không hợp lệ và tiêu tốn tài nguyên.  
**Cách sửa:** Giới hạn request ở reverse proxy/ASP.NET Core, kiểm tra độ dài, header và magic bytes, quét malware trước khi phát hành; không coi kiểm tra signature là bằng chứng file an toàn.

### High — SAS dài hạn và ghi secret vào log

**Vấn đề:** Trả SAS đọc 30 ngày và log nguyên URL.  
**Tại sao xảy ra:** Credential được xử lý như URL thông thường.  
**Ảnh hưởng production:** Link bị phát tán qua log hoặc client và còn hiệu lực lâu.  
**Cách sửa:** Trả document ID, phát URL ngắn hạn sau authorization tại endpoint download; tuyệt đối không log SAS. Cần xác minh cách cấp SAS: `GenerateSasUri` yêu cầu client có khả năng ký phù hợp, không tự hoạt động với mọi Managed Identity client.

### High — Không nhất quán giữa Blob và SQL

**Vấn đề:** API báo thành công trước khi metadata được ghi ở hệ thống khác.  
**Tại sao xảy ra:** Hai resource không chia sẻ transaction.  
**Ảnh hưởng production:** Blob mồ côi hoặc metadata trỏ tới tài liệu không có.  
**Cách sửa:** Thiết kế trạng thái Pending/Ready/Rejected, idempotency key, reconciliation job và cleanup có thời gian chờ; không giả định distributed transaction.

### Medium — Bộ nhớ và tài nguyên upload

**Vấn đề:** Copy toàn bộ `IFormFile` vào `MemoryStream`; multipart buffering có thể đã dùng memory/disk trước đó.  
**Tại sao xảy ra:** Thêm một bản sao toàn bộ file trước khi upload.  
**Ảnh hưởng production:** Allocation lớn, GC pressure và khả năng quá tải khi concurrency tăng.  
**Cách sửa:** Với file tối đa 20 MiB, sử dụng stream từ `OpenReadStream` cùng limits; với upload rất lớn, đánh giá direct-to-Blob bằng SAS ghi ngắn hạn theo object cụ thể.

### Medium — Không truyền CancellationToken

**Vấn đề:** Tạo container, copy và upload không gắn với `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Bỏ qua vòng đời HTTP request.  
**Ảnh hưởng production:** Tiếp tục I/O khi client đã rời đi.  
**Cách sửa:** Truyền token qua mọi API hỗ trợ; nếu tác vụ đã commit, reconciliation phải xử lý trạng thái cuối.

### Medium — Tạo container trong hot path

**Vấn đề:** Mỗi request gọi `CreateIfNotExistsAsync`.  
**Tại sao xảy ra:** Provisioning bị trộn vào nghiệp vụ.  
**Ảnh hưởng production:** Tăng dependency calls và mở rộng quyền của runtime identity không cần thiết.  
**Cách sửa:** Provision private container trong deployment/IaC, runtime chỉ có quyền dữ liệu tối thiểu.

## Phiên bản đề xuất

Ví dụ minh họa phần upload; giả định `ITenantAccess`, `IDocumentRegistry` và `IFileScanner` là các abstraction do ứng dụng triển khai. Registry có trạng thái Pending và cơ chế reconciliation riêng. Container được provision private từ trước. Middleware và reverse proxy cũng phải enforce request size.

```csharp
[Authorize]
[ApiController]
[Route("api/tenants/{tenantId}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxBytes = 20L * 1024 * 1024;
    private readonly BlobContainerClient _container;
    private readonly ITenantAccess _access;
    private readonly IDocumentRegistry _registry;
    private readonly IFileScanner _scanner;

    public DocumentsController(
        BlobContainerClient container,
        ITenantAccess access,
        IDocumentRegistry registry,
        IFileScanner scanner)
    {
        _container = container;
        _access = access;
        _registry = registry;
        _scanner = scanner;
    }

    [HttpPost]
    [RequestSizeLimit(22L * 1024 * 1024)]
    public async Task<IActionResult> Upload(
        string tenantId, IFormFile file,
        CancellationToken ct)
    {
        if (!await _access.CanUploadAsync(User, tenantId, ct))
            return Forbid();

        if (file is null || file.Length == 0 ||
            file.Length > MaxBytes)
            return BadRequest("Invalid file size");

        await using var input = file.OpenReadStream();
        if (!await PdfSignature.IsValidAsync(input, ct))
            return BadRequest("Unsupported content");
        input.Position = 0;

        var id = Guid.NewGuid().ToString("N");
        var key = $"{tenantId}/{id}";
        var blob = _container.GetBlobClient(key);

        await _registry.CreatePendingAsync(
            id, tenantId, key, ct);

        try
        {
            await blob.UploadAsync(
                input,
                new BlobUploadOptions
                {
                    Conditions = new BlobRequestConditions
                    {
                        IfNoneMatch = ETag.All
                    },
                    HttpHeaders = new BlobHttpHeaders
                    {
                        ContentType = "application/pdf"
                    }
                }, ct);

            var clean = await _scanner.ScanAsync(blob, ct);
            if (!clean)
            {
                await _registry.MarkRejectedAsync(id, ct);
                return UnprocessableEntity("File rejected");
            }

            await _registry.MarkReadyAsync(id, ct);
            return Created($"/api/documents/{id}", new { id });
        }
        catch
        {
            await _registry.MarkForReconciliationAsync(
                id, CancellationToken.None);
            throw;
        }
    }
}
```

**Lưu ý triển khai:** `PdfSignature.IsValidAsync` là helper giả định, phải giới hạn số byte đọc và reset stream nếu seekable; với stream không seekable cần buffered prefix hoặc wrapper. `IFileScanner` phải có quyền đọc blob quarantine, không expose blob trước trạng thái Ready. Nếu reconciliation call cũng thất bại, cần durable Pending record và periodic sweep; `catch` ở ví dụ chưa giải quyết tuyệt đối lỗi kép. Thiết kế production cần kiểm tra cancellation sau upload và không cho client tải blob trực tiếp khi Pending.

## Giải thích thiết kế sau khi sửa

Authorization diễn ra trước khi cấp quyền lưu trữ. Blob key tách khỏi tên người dùng nhập; container luôn private. File chỉ được công bố khi đã scan và metadata Ready. API trả ID thay vì credential dài hạn; endpoint download phải authorize từng lần và có thể tạo user-delegation SAS ngắn hạn nếu chọn Azure identity phù hợp. Registry và cleanup đảm nhiệm consistency xuyên resource.

## Trade-offs

Streaming giảm copy trong memory nhưng vẫn chịu buffering multipart và cần giới hạn ở nhiều lớp. Quét đồng bộ tăng latency; chuyển scan sang asynchronous worker giảm latency request nhưng phải trả `202 Accepted` và cung cấp status polling. Direct upload giảm tải App Service nhưng yêu cầu cấp write permission chặt, kiểm tra file sau upload và cleanup file chưa hoàn tất. Đổi key có thể ảnh hưởng link cũ; cần migration/compatibility có kiểm soát.

## Cách kiểm thử

1. **Security integration:** user tenant A không thể upload hoặc đọc tài liệu tenant B; anonymous request bị từ chối.
2. **Concurrency:** 100 upload trùng tên không ghi đè nhau, mỗi ID chỉ trỏ một object.
3. **Boundary:** file 0 byte, trên 20 MiB, MIME giả, signature sai và PDF độc hại đều được xử lý theo policy.
4. **Failure-path:** upload thành công nhưng SQL/scan lỗi; reconciliation đưa về Ready/Rejected hoặc cleanup an toàn.
5. **Load:** tải đồng thời file 20 MiB, đo memory, GC, request p95 và storage throttling.

## Quan sát trong production

Ghi structured logs với document ID, tenant ID được kiểm soát truy cập, correlation ID, trạng thái scan và error category; không ghi token/SAS hay nội dung hợp đồng. Theo dõi số Pending quá hạn, orphan blobs, rejected scans, upload duration p95/p99, memory/GC, 4xx/5xx, dependency failures qua Application Insights/Azure Monitor. Alert khi anonymous access bị bật, Pending backlog tăng hoặc upload failure rate vượt baseline. Audit storage permissions và thời gian tồn tại của credential.

# Code Review Challenge 2 — PostgreSQL phân bổ tồn kho khi checkout đồng thời

**Chủ đề:** PostgreSQL, SQL transaction, isolation, inventory correctness, e-commerce  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 7–9

## Bối cảnh

Một e-commerce API dùng PostgreSQL quản lý `inventory(product_id primary key, available integer not null)` và `reservations(id uuid primary key, order_id uuid, product_id bigint, quantity integer, status text)`. Checkout tạo reservation trước khi thanh toán; một order có thể retry do timeout. Nhiều instance API cùng xử lý một SKU hot. Sản phẩm có 2 đơn vị tồn nhưng đôi khi ghi nhận 3 reservation. Thỉnh thoảng đơn hàng bị trừ tồn hai lần. Đội Product muốn không bán quá tồn, chấp nhận trả `409 Conflict` khi hết hàng. Yêu cầu giữ trace được mỗi quyết định đặt hàng.

## Đoạn code cần review

```sql
CREATE OR REPLACE FUNCTION reserve_stock(
    p_order_id uuid,
    p_product_id bigint,
    p_quantity integer
) RETURNS uuid
LANGUAGE plpgsql
AS $$
DECLARE
    v_available integer;
    v_reservation_id uuid := gen_random_uuid();
BEGIN
    SELECT available
      INTO v_available
      FROM inventory
     WHERE product_id = p_product_id;

    IF v_available IS NULL THEN
        RAISE EXCEPTION 'Product not found';
    END IF;

    IF v_available < p_quantity THEN
        RAISE EXCEPTION 'Insufficient stock';
    END IF;

    UPDATE inventory
       SET available = v_available - p_quantity
     WHERE product_id = p_product_id;

    INSERT INTO reservations(
        id, order_id, product_id, quantity, status
    ) VALUES (
        v_reservation_id, p_order_id,
        p_product_id, p_quantity, 'Reserved'
    );

    RETURN v_reservation_id;
END;
$$;
```

Ứng dụng gọi hàm trong transaction mặc định `READ COMMITTED`; nếu client timeout, request được retry với cùng `order_id`. Không có unique constraint trên `reservations(order_id, product_id)`. Chưa xác định liệu một order được phép có nhiều reservation cho cùng SKU.

## Nhiệm vụ của ứng viên

1. Tìm lỗi correctness và concurrency, phân biệt lost update với oversell trong lịch thực thi cụ thể.
2. Phân tích retry sau timeout và trường hợp transaction đã commit nhưng response bị mất.
3. Xếp hạng rủi ro, nêu biện pháp ổn định production trước khi triển khai sửa.
4. Viết SQL/transaction strategy cải thiện atomicity và idempotency.
5. Đề xuất các test concurrency, failure-path và migration constraint an toàn.
6. Chỉ ra telemetry giúp phân biệt contention, deadlock, duplicate và thiếu tồn thật.

## Câu hỏi gợi mở

1. Hai transaction cùng đọc `available = 2` thì `UPDATE` có tự kiểm tra điều kiện đã đọc không?
2. `READ COMMITTED` đảm bảo điều gì cho mỗi statement, và điều gì không?
3. Retry cùng `order_id` có tạo reservation mới không?
4. Quantity bằng 0 hoặc âm gây ra kết quả gì?
5. Unique constraint nên áp vào khóa nghiệp vụ nào nếu order có nhiều line items?

## Gợi ý

### Gợi ý 1

Tập trung vào atomic conditional update, khóa nghiệp vụ và input invariants.

### Gợi ý 2

Đánh giá trạng thái transaction khi một lệnh `UPDATE` chờ row lock; so sánh giá trị đã đọc trước đó với predicate được PostgreSQL đánh giá lại sau khi lock được giải phóng.

## Kết quả code review tham khảo

### Critical — Lost update làm tồn kho không phản ánh số reservation

**Vấn đề:** `UPDATE` gán `available = v_available - p_quantity` từ snapshot đọc trước đó.  
**Tại sao xảy ra:** Hai transaction có thể cùng đọc 2 rồi lần lượt ghi 1; row lock serialize writes nhưng không tự biến biến PL/pgSQL đã đọc thành giá trị mới.  
**Ảnh hưởng production:** Hai reservation được tạo nhưng tồn chỉ giảm một lần, tạo điều kiện bán vượt lượng thực tế.  
**Cách sửa:** Atomic conditional decrement: `UPDATE inventory SET available = available - qty WHERE ... AND available >= qty RETURNING ...`, kiểm tra row count.

### Critical — Retry không idempotent

**Vấn đề:** Mỗi lần gọi tạo UUID mới và trừ tồn mới.  
**Tại sao xảy ra:** `order_id` không được bảo vệ bằng unique constraint hoặc logic phát hiện kết quả cũ.  
**Ảnh hưởng production:** Một đơn bị giữ tồn nhiều lần sau timeout.  
**Cách sửa:** Xác định business idempotency key, enforce unique constraint và trả reservation đã có nếu request payload tương đương; payload khác phải conflict.

### High — Quantity không được validate

**Vấn đề:** Không có `p_quantity > 0` hay `CHECK` constraint.  
**Tại sao xảy ra:** Logic chỉ so sánh `available < quantity`.  
**Ảnh hưởng production:** Quantity âm làm tăng tồn; zero tạo reservation vô nghĩa.  
**Cách sửa:** Validate tại API và database bằng `CHECK (quantity > 0)`, bảo vệ cả `inventory.available >= 0`.

### High — Thiếu ràng buộc uniqueness theo nghiệp vụ

**Vấn đề:** Nhiều reservation cùng `order_id/product_id` được tạo.  
**Tại sao xảy ra:** Chỉ có primary key trên UUID kỹ thuật.  
**Ảnh hưởng production:** Duplicate data, double hold, reconciliation khó.  
**Cách sửa:** Nếu một order chỉ có một reservation cho mỗi SKU, tạo unique index `(order_id, product_id)`; nếu có nhiều line items, dùng stable `order_line_id` hoặc request key riêng.

### Medium — Không phân loại failure rõ ràng

**Vấn đề:** Exception chung cho missing product và insufficient stock.  
**Tại sao xảy ra:** Function không có typed outcome/SQLSTATE theo hợp đồng API.  
**Ảnh hưởng production:** API dễ trả 500 thay vì 404/409; retry nhầm lỗi nghiệp vụ.  
**Cách sửa:** Mapping lỗi có kiểm soát, tránh retry vô hạn khi hết tồn.

### Medium — Thiếu transaction design cho release/cancel

**Vấn đề:** Chỉ mô tả reserve, không có transition an toàn cho expiry/payment/cancel.  
**Tại sao xảy ra:** State machine chưa được xác định.  
**Ảnh hưởng production:** Có thể cộng tồn hai lần nếu cùng reservation được release đồng thời.  
**Cách sửa:** Conditional status transition trong transaction và increment stock đúng một lần; định nghĩa expiry, payment timeout và audit.

### Medium — Không có operational guardrails cho hot SKU

**Vấn đề:** Không theo dõi lock waits, contention và retries.  
**Tại sao xảy ra:** Thiết kế chỉ xét correctness đường thành công.  
**Ảnh hưởng production:** p99 tăng, timeout dẫn tới retry storm.  
**Cách sửa:** Bounded retry cho transient database failures, request deadline, metrics và backpressure; không tự động retry business conflict.

## Phiên bản đề xuất

Giả định mỗi `(order_id, product_id)` là một yêu cầu reservation duy nhất, quantity không thay đổi khi retry. Migration phải dọn duplicate cũ trước khi tạo unique index.

```sql
ALTER TABLE inventory
  ADD CONSTRAINT inventory_nonnegative CHECK (available >= 0);

ALTER TABLE reservations
  ADD CONSTRAINT reservation_positive CHECK (quantity > 0);

CREATE UNIQUE INDEX ux_reservation_order_product
  ON reservations(order_id, product_id);

CREATE OR REPLACE FUNCTION reserve_stock(
    p_order_id uuid,
    p_product_id bigint,
    p_quantity integer
) RETURNS uuid
LANGUAGE plpgsql
AS $$
DECLARE
    v_existing reservations%ROWTYPE;
    v_id uuid := gen_random_uuid();
BEGIN
    IF p_order_id IS NULL OR p_product_id IS NULL
       OR p_quantity IS NULL OR p_quantity <= 0 THEN
        RAISE EXCEPTION 'Invalid reservation request'
            USING ERRCODE = '22023';
    END IF;

    -- Serialize requests sharing the same inventory row.
    PERFORM 1 FROM inventory
      WHERE product_id = p_product_id FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Product not found'
            USING ERRCODE = 'P0002';
    END IF;

    SELECT * INTO v_existing
      FROM reservations
     WHERE order_id = p_order_id
       AND product_id = p_product_id;

    IF FOUND THEN
        IF v_existing.quantity <> p_quantity THEN
            RAISE EXCEPTION 'Idempotency payload conflict'
                USING ERRCODE = '23505';
        END IF;
        RETURN v_existing.id;
    END IF;

    UPDATE inventory
       SET available = available - p_quantity
     WHERE product_id = p_product_id
       AND available >= p_quantity;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Insufficient stock'
            USING ERRCODE = 'P0001';
    END IF;

    INSERT INTO reservations(
        id, order_id, product_id, quantity, status
    ) VALUES (
        v_id, p_order_id, p_product_id,
        p_quantity, 'Reserved'
    );

    RETURN v_id;
END;
$$;
```

**Phạm vi bảo đảm:** Cách khóa row inventory trước khi kiểm tra reservation serialize các request cùng SKU, kể cả retry cùng order. Unique index là defense-in-depth và bảo vệ trước các writer khác. Function phải được gọi trong transaction; lỗi sẽ rollback decrement và insert cùng nhau. Nếu reservation cũ có status `Released` hoặc `Expired`, trả ID cũ không đồng nghĩa giữ tồn mới: cần quy tắc nghiệp vụ rõ ràng về việc retry sau release (thường trả trạng thái cũ hoặc từ chối, không tự tạo lại). Với nhiều SKU trong một order, lock theo thứ tự product_id nhất quán để giảm deadlock. Không triển khai migration constraint trực tiếp nếu dữ liệu cũ vi phạm; phải audit, reconcile và lên kế hoạch index build phù hợp.

## Giải thích thiết kế sau khi sửa

Atomic conditional decrement loại bỏ stale-value update. Lock trước lookup idempotency tránh hai request cùng SKU đi qua nhánh chưa tồn tại. Unique constraint bảo vệ invariant ở database thay vì chỉ tin code API. Transaction giữ thay đổi tồn và reservation cùng commit/rollback. State machine cho cancel/expire phải dùng conditional transition và ghi audit, không dựa trên thao tác đọc rồi cập nhật tách rời.

## Trade-offs

Row locking làm giảm throughput SKU nóng nhưng bảo vệ correctness; đo contention trước khi cân nhắc reservation queue hoặc inventory partitioning. Unique key `(order_id, product_id)` đơn giản nhưng không phù hợp nếu một order cho phép nhiều line cùng SKU; khi đó phải dùng line ID ổn định. Isolation `SERIALIZABLE` có thể hỗ trợ phát hiện anomaly nhưng đòi hỏi retry serialization failures; không thay thế business idempotency. Pre-reservation giữ tồn có thể tăng abandoned holds, cần expiry policy.

## Cách kiểm thử

1. **Concurrency:** 100 request cho SKU có 2 đơn vị, mỗi request quantity 1; đúng 2 reservation mới thành công, tồn bằng 0.
2. **Idempotency:** 50 retry cùng order/product/quantity trả cùng ID, tồn chỉ giảm một lần.
3. **Conflict:** retry cùng key nhưng quantity khác bị từ chối, không đổi tồn.
4. **Constraint:** zero/negative quantity, inventory âm và duplicate business key đều bị database từ chối.
5. **Failure-path:** transaction rollback sau decrement, timeout sau commit và cancel/expire race không tạo double release.

## Quan sát trong production

Ghi trace với order ID, product ID, reservation ID, outcome và correlation ID; tránh thông tin thanh toán nhạy cảm. Đo lock wait duration, transaction latency p95/p99, deadlock count, retry rate, unique conflicts, insufficient-stock conflicts, duplicate-idempotent hits và số reservation Pending/Expired. Theo dõi PostgreSQL `pg_stat_activity`, `pg_locks` và query statistics nếu extension được bật; cảnh báo khi contention tăng hoặc invariant đối soát `inventory + active reservations` lệch khỏi nguồn tồn ban đầu. Tránh log mỗi lần retry ở mức quá chi tiết gây noise.

## Câu hỏi phỏng vấn mở rộng

3. Nếu 20.000 request/giây cùng tranh một SKU, khi nào nên chuyển từ row-lock transaction sang hàng đợi và chấp nhận trade-off gì?
