# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân lên dưới tải

**Loại câu hỏi:** Internal mechanism trong tình huống thực tế  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, Change Tracker, SQL, performance diagnosis, observability

## Bối cảnh

Một ASP.NET Core API trả danh sách nhân viên kèm trạng thái cấu hình mailbox. Sau một thay đổi refactor, endpoint vẫn đúng ở môi trường test nhưng production tăng từ khoảng 150 ms lên vài giây khi số bản ghi lớn. CPU ứng dụng không tăng đáng kể, nhưng database có nhiều query hơn trước. Code sử dụng `IQueryable`, navigation properties và cập nhật một số entity sau khi đọc. Team cho rằng “LINQ chỉ chạy một lần khi gọi `ToListAsync`, nên tracking không thể ảnh hưởng nhiều”.

## Câu hỏi chính

Hãy giải thích điều gì có thể xảy ra bên trong EF Core từ lúc xây dựng `IQueryable` đến lúc materialize kết quả; vì sao số query, memory và latency có thể tăng; misconception nào trong nhận định của team; production risk là gì; và bạn sẽ chứng minh từng giả thuyết bằng cách nào trước khi sửa?

## Câu hỏi làm rõ nên cân nhắc

- Query có `Include`, projection hay truy cập navigation sau materialization không?
- Lazy loading có được bật không?
- Endpoint chỉ đọc hay có thay đổi entity rồi `SaveChangesAsync`?
- Số bản ghi, cardinality của navigation và SQL thực tế là gì?
- Có khác biệt nào về dữ liệu/index giữa test và production?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “xây expression tree” khỏi “thực thi query”.
- **Gợi ý 2:** Kiểm tra tracking, materialization, navigation loading, số round-trip và kích thước result set.
- **Gợi ý 3:** So sánh SQL/log/trace của projection + `AsNoTracking()` với cách hiện tại; đừng tối ưu dựa trên phỏng đoán.

## Cấu trúc trả lời đề xuất

1. Làm rõ query và dữ liệu.
2. Mô tả lifecycle của `IQueryable`.
3. Phân tích translation, execution, materialization và tracking.
4. Liệt kê nhiều giả thuyết gây latency.
5. Thu thập bằng chứng.
6. Đề xuất các phương án sửa.
7. So sánh trade-off.
8. Kiểm thử và giám sát sau triển khai.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` thường biểu diễn query chưa thực thi; terminal operation như `ToListAsync` mới kích hoạt execution.
- Tracking tạo state cho entity được materialize và hữu ích khi cần cập nhật, nhưng là overhead không cần thiết cho read-only query.
- Không kết luận N+1 nếu chưa xác nhận cách navigation được load.
- Kiểm tra SQL thực tế, query count, duration, rows và execution plan.

### Điểm cộng

- Dùng projection để chỉ lấy cột cần thiết.
- Nhận ra eager loading collection lớn có thể làm tăng dữ liệu trả về; cân nhắc split/single query theo hình dạng dữ liệu.
- Đo allocation và Change Tracker khi cần.

### Nâng cao

- Phân biệt application latency với DB execution, network round-trip và materialization cost.
- Thiết kế benchmark bằng dữ liệu có cardinality gần production.

## Hướng giải quyết tham khảo

**Giả định:** endpoint chủ yếu read-only. Trước hết capture generated SQL, số command mỗi request, DB duration, rows returned và trace end-to-end. Nếu có nhiều command phát sinh do navigation loading thì xử lý query shape thay vì chỉ thêm index. Nếu một query trả result set phình lớn do nhiều collection, đánh giá projection hoặc query splitting. Nếu entity không cần update, projection DTO và/hoặc `AsNoTracking()` giúp tránh tracking overhead.

Không nên mặc định `AsNoTracking()` là “fix mọi performance issue”: query vẫn có thể chậm vì scan, join xấu, cardinality lớn hoặc thiếu index. Ngược lại, nếu cùng DbContext cần sửa entity sau đó thì tracking có giá trị. Kiểm tra bằng integration test SQL shape, load test, query plan và metrics trước/sau. Với dữ liệu nhạy cảm, tránh log parameter/raw payload không cần thiết.

Recommendation thay đổi nếu endpoint thực sự cần unit-of-work cập nhật nhiều entity hoặc identity resolution có ý nghĩa; khi đó cần cân bằng correctness và overhead thay vì loại tracking một cách máy móc.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ chưa kết luận đây là lỗi EF Core hay thiếu index. Đầu tiên tôi muốn biết SQL thực tế và mỗi request phát bao nhiêu database command. `IQueryable` chủ yếu xây expression; khi materialize, EF Core dịch phần có thể dịch sang SQL, gửi query, materialize kết quả và nếu tracking thì đưa entity vào Change Tracker. Vì vậy câu nói ‘chỉ có một ToListAsync nên tracking không ảnh hưởng’ chưa đủ: navigation loading có thể tạo thêm round-trip, result shape có thể bị phình, và tracking vẫn tốn CPU/memory theo số entity. Với endpoint read-only tôi ưu tiên projection DTO và cân nhắc `AsNoTracking`, nhưng chỉ sau khi đo. Tôi sẽ dùng EF command logs/tracing, DB execution plan, query count, rows returned và load test để phân biệt DB cost, network cost và materialization cost. Sau sửa tôi đặt regression test cho query shape và theo dõi p95 latency cùng DB command count.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTracking()` không phải lựa chọn phù hợp?
2. Nếu `Include` một collection lớn nhưng chỉ một SQL command, tại sao vẫn có thể chậm?
3. Nếu projection nhanh hơn 5 lần, bạn có triển khai ngay không hay vẫn cần kiểm tra điều gì?

## Lỗi trả lời thường gặp

- Khẳng định mọi vấn đề navigation đều là N+1 mà không kiểm tra.
- Chỉ nói “thêm `AsNoTracking`” mà không giải thích mechanism.
- Không xem SQL/query plan.
- Benchmark bằng dữ liệu quá nhỏ.
- Bật verbose SQL logging chứa dữ liệu nhạy cảm ở production mà không kiểm soát.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 2 — Sự cố duplicate Hangfire job sau khi scale-out

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire, idempotency, concurrency, database consistency, observability

## Bối cảnh

Một background job đồng bộ thay đổi lịch họp sang hệ thống bên ngoài. Sau khi ứng dụng scale từ một lên nhiều instance và có một đợt timeout từ external API, support nhận báo cáo một số người dùng nhận hai notification và một số bản ghi external bị cập nhật lặp. Dashboard cho thấy một số job được retry. Business yêu cầu giảm tác động ngay nhưng không được mất update hợp lệ.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ impact assessment đến root cause, mitigation, short-term fix và long-term prevention như thế nào, khi chưa biết duplicate đến từ retry, enqueue hai lần, concurrent execution hay hành vi của external API?

## Câu hỏi làm rõ nên cân nhắc

- “Duplicate” được xác định bằng business key nào?
- Job có side effect nào và external API có hỗ trợ idempotency/versioning không?
- Retry policy và timeout hiện tại ra sao?
- Job được enqueue từ transaction nào; có khả năng enqueue trước khi DB commit không?
- Nhiều worker có thể xử lý cùng logical operation không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách delivery semantics khỏi business idempotency.
- **Gợi ý 2:** Correlate job ID, logical operation ID, retry attempt, DB transaction và external request.
- **Gợi ý 3:** Thiết kế “retry-safe side effect”: stable idempotency key + durable state/unique constraint/outbox khi phù hợp.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius và business impact.
2. Stabilize mà không làm mất dữ liệu.
3. Thu thập timeline/evidence.
4. Lập nhiều giả thuyết.
5. Reproduce và loại trừ từng giả thuyết.
6. Fix ngắn hạn.
7. Thiết kế idempotency/recovery dài hạn.
8. Verify bằng test và production metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định retry framework đồng nghĩa exactly-once business processing.
- Side effect phải chịu được retry/duplicate delivery.
- Có correlation/logging đủ để phân biệt duplicate enqueue và duplicate execution.
- Mitigation phải cân bằng duplicate với nguy cơ mất update.

### Điểm cộng

- Stable operation key, unique constraint hoặc processed-operation table.
- Transactional outbox khi cần gắn DB state change với việc phát work item/event.
- External idempotency key nếu API hỗ trợ.

### Nâng cao

- State machine cho operation (`Pending`, `Processing`, `Succeeded`, `Failed`) với lease/version phù hợp.
- Reconciliation job để phát hiện side effect chưa đồng bộ thay vì dựa hoàn toàn vào retry.

## Hướng giải quyết tham khảo

Đầu tiên xác định số user/bản ghi bị ảnh hưởng và tạm giảm concurrency hoặc pause loại job gây side effect nếu blast radius đang tăng, nhưng giữ durable work để không mất update. Thu thập job ID, logical operation ID, attempt, worker, timestamps, DB commit và external response.

Các giả thuyết gồm: cùng business event enqueue nhiều lần; retry sau timeout dù external side effect đã thành công; concurrent worker chạy cùng logical operation; hoặc upstream gửi duplicate. Fix nên đặt correctness ở business layer: tạo stable operation key, enforce uniqueness/durable processed state, chỉ đánh dấu thành công sau khi có bằng chứng phù hợp, và dùng external idempotency mechanism nếu có. Nếu việc enqueue phụ thuộc DB transaction, transactional outbox là một lựa chọn mạnh để tránh dual-write gap.

Không dùng distributed lock như giải pháp duy nhất: lock có thể giảm concurrency nhưng không tự giải quyết replay sau crash hay timeout không rõ kết quả. Cần failure-path tests: timeout sau khi remote commit, worker crash, duplicate enqueue, concurrent delivery. Theo dõi duplicate-suppressed count, retries, queue age, success/failure và reconciliation mismatch.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây trước hết là incident về side-effect correctness, không phải chỉ là Hangfire retry. Tôi sẽ xác định blast radius, correlation theo logical operation và nếu duplicate đang tăng thì giảm/pause processing có kiểm soát nhưng không xóa work. Sau đó tôi phân biệt bốn khả năng: enqueue trùng, retry sau ambiguous timeout, concurrent processing và upstream duplicate. Dù root cause là gì, long-term tôi muốn operation retry-safe. Mỗi thay đổi có stable idempotency key; DB enforce uniqueness hoặc lưu processed state; nếu DB change và enqueue phải atomic về mặt nghiệp vụ thì cân nhắc outbox. Nếu external API hỗ trợ idempotency key tôi truyền cùng key đó. Lock chỉ là lớp phụ, không phải guarantee exactly-once. Tôi sẽ test case remote đã commit nhưng client timeout, crash giữa các bước và hai worker nhận cùng operation, rồi monitor retries, suppressed duplicates và reconciliation mismatches.”

## Câu hỏi đào sâu

1. Vì sao distributed lock không đủ để bảo đảm exactly-once side effect?
2. Nếu external API không hỗ trợ idempotency key thì thiết kế recovery thế nào?
3. Outbox tăng complexity; khi nào bạn không chọn nó?

## Lỗi trả lời thường gặp

- Tắt retry ngay mà không đánh giá lost updates.
- Chỉ thêm lock.
- Dùng job ID làm business idempotency key dù retry/re-enqueue có semantics khác.
- Không xử lý ambiguous timeout.
- Không có reconciliation path.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **1.5**
- Trade-off analysis: **1.5**
- Production readiness: **2.5**
- Communication: **1.0**

# Câu 3 — Thiết kế AI code-review agent có quyền truy cập repository và CI

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool security, deterministic validation, evaluation, auditability

## Bối cảnh

Team muốn một AI agent review pull request C#/.NET: đọc diff và repository context, phát hiện bug/security/performance issue, chạy một số test, rồi đề xuất comment. Mục tiêu là giảm review toil nhưng không được để agent tự merge hoặc thực thi lệnh tùy ý trên production credentials. Repository có source code, CI config và một số tài liệu nội bộ. Team muốn chất lượng đủ cao để reviewer tin dùng nhưng ngân sách inference có giới hạn.

## Câu hỏi chính

Bạn sẽ thiết kế agent này như thế nào để AI chỉ xử lý phần cần reasoning, còn security, validation, permissions, evaluation và failure recovery vẫn có kiểm soát deterministic?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ draft comment hay được phép publish comment tự động?
- Repository có secret/material nhạy cảm nào mà model không được thấy?
- PR size, ngôn ngữ và SLA review dự kiến?
- Test nào an toàn để chạy trong sandbox và timeout bao lâu?
- False positive và missed critical issue được business đánh trọng số thế nào?

## Gợi ý tư duy

- **Gợi ý 1:** Thiết kế trust boundary trước khi thiết kế prompt.
- **Gợi ý 2:** Tách context retrieval, reasoning, tool execution và validation thành các bước có contract.
- **Gợi ý 3:** Least privilege + sandbox + structured output + deterministic checks + human approval cho side effects.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu và threat model.
2. Chọn phần cần LLM và phần deterministic.
3. Thiết kế context pipeline.
4. Thiết kế tool/permission boundary.
5. Định nghĩa output schema và validators.
6. Thiết kế human approval/fallback.
7. Xây evaluation dataset và metrics.
8. Audit, monitor cost/latency/quality.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI cần cho reasoning trên diff/context; authz, schema validation, policy và secret handling phải deterministic.
- Repository content và tool output đều là untrusted input đối với agent.
- Tool permissions theo least privilege; không cấp production credential hoặc merge permission nếu không cần.
- Output phải được validate trước side effect.

### Điểm cộng

- Context budget dựa trên diff + dependency/symbol relevance thay vì nhét toàn repo.
- Sandbox cho test execution, allowlist command/tool, resource/time limits.
- Human approval trước publish ở giai đoạn đầu.

### Nâng cao

- Evaluation corpus từ historical PR/bugs, phân tầng severity.
- Theo dõi precision/recall-like metrics theo taxonomy, reviewer acceptance, escaped defect, latency và cost.
- Canary/shadow mode trước automation sâu hơn.

## Hướng giải quyết tham khảo

**AI cần thiết** vì review bug/design issue thường cần reasoning xuyên diff và context; nhưng việc fetch PR, kiểm tra permission, parse schema, secret redaction, command allowlist, timeout và publish comment nên deterministic.

Pipeline có thể gồm: ingest diff → classify changed areas → retrieve bounded repository context → model tạo findings theo schema (`file`, `line`, `severity`, `claim`, `evidence`, `suggestion`, `confidence`) → deterministic validation rằng file/line tồn tại và evidence khớp context → optional sandboxed tests/static analyzers → deduplicate/rank → human approval → publish.

Không coi repository instructions là trusted system instruction: source/documentation có thể chứa prompt injection. Tool layer enforce permission độc lập với model. Agent chỉ có read repo + sandbox test và quyền tạo draft; không merge, không secret store, không production network nếu không cần. Hallucination được giảm bằng evidence requirement, source-grounded checks và reject finding không map được vào diff/context.

Quality đo trên bộ PR lịch sử có known defects và human labels; theo dõi acceptance rate, false-positive rate, critical miss rate, latency/cost. Fallback: nếu context quá lớn, tool fail hoặc confidence thấp thì trả trạng thái “needs human review”, không tự suy diễn. Audit log lưu model/version, context references, tool calls, policy decisions và final action với quy tắc retention phù hợp.

Recommendation thay đổi nếu agent chỉ chạy local cho một developer so với service đa tenant; mức isolation, authz và audit phải tăng theo blast radius.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng prompt mà bắt đầu bằng trust boundary. LLM phù hợp để reasoning trên diff và context, còn authorization, secret filtering, schema validation, command allowlist và publish policy phải deterministic. Pipeline của tôi lấy diff, retrieve context liên quan theo symbol/dependency, yêu cầu model trả structured findings kèm evidence, rồi validator kiểm tra file/line/evidence trước khi cho finding đi tiếp. Test chỉ chạy trong sandbox với allowlist, timeout và không có production credentials. Repository text được coi là untrusted vì có thể chứa instruction injection. Ban đầu agent chỉ tạo draft để human approve; khi evaluation đủ tốt mới tự động hóa các finding low-risk. Tôi đo reviewer acceptance, false positives, critical misses, latency và cost trên historical PR set. Nếu tool fail hoặc context không đủ, agent fail closed sang human review thay vì tự bịa kết luận.”

## Câu hỏi đào sâu

1. Nếu attacker thêm instruction vào README yêu cầu agent đọc secret và gửi ra ngoài, lớp nào chặn việc đó?
2. Human approval làm giảm automation benefit; khi nào bạn cho phép auto-publish?
3. Làm sao đánh giá một finding “đúng” khi reviewer cũng có thể bất đồng?

## Lỗi trả lời thường gặp

- Cho model quyền shell/repository quá rộng vì “agent cần linh hoạt”.
- Dùng prompt “không được làm xấu” thay cho enforcement ở tool layer.
- Đưa toàn repository vào context mà không có budget/relevance strategy.
- Không có evidence/structured validation.
- Chỉ đo số comment được tạo thay vì chất lượng và escaped defects.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **1.5**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.5**
