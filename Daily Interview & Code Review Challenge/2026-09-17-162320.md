# Code Review Challenge 1 — Service Bus consumer hoàn tất message trước khi business transaction thực sự an toàn

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, at-least-once delivery, idempotency, transaction boundary, failure handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một order-processing service nhận `OrderPaid` từ Azure Service Bus. Mỗi message phải cập nhật trạng thái order trong SQL Server và tạo một `FulfillmentJob`. Production chạy nhiều instances. Message có thể được delivery lại khi processing thất bại hoặc lock không còn hợp lệ.

Sau một incident, team thấy một số order được tạo hai fulfillment jobs, trong khi một số message khác biến mất khỏi active queue nhưng order vẫn chưa chuyển sang `Paid`. Log cho thấy dependency SQL thỉnh thoảng timeout. Business chấp nhận at-least-once delivery nhưng không chấp nhận duplicate fulfillment hoặc mất business event.

## Đoạn code cần review

```csharp
public sealed class OrderPaidProcessor : IAsyncDisposable
{
    private readonly ServiceBusProcessor _processor;
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<OrderPaidProcessor> _logger;

    public OrderPaidProcessor(
        ServiceBusClient client,
        IServiceScopeFactory scopeFactory,
        ILogger<OrderPaidProcessor> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;

        _processor = client.CreateProcessor("order-paid", new ServiceBusProcessorOptions
        {
            AutoCompleteMessages = false,
            MaxConcurrentCalls = 16
        });

        _processor.ProcessMessageAsync += ProcessMessageAsync;
        _processor.ProcessErrorAsync += ProcessErrorAsync;
    }

    private async Task ProcessMessageAsync(ProcessMessageEventArgs args)
    {
        var message = args.Message.Body.ToObjectFromJson<OrderPaidMessage>();

        await args.CompleteMessageAsync(args.Message);

        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var order = await db.Orders
            .SingleAsync(x => x.Id == message.OrderId);

        order.Status = "Paid";
        order.PaidUtc = message.PaidUtc;

        db.FulfillmentJobs.Add(new FulfillmentJob
        {
            OrderId = order.Id,
            CreatedUtc = DateTime.UtcNow
        });

        await db.SaveChangesAsync();

        _logger.LogInformation(
            "Processed OrderPaid {MessageId} for {OrderId}",
            args.Message.MessageId,
            message.OrderId);
    }

    private Task ProcessErrorAsync(ProcessErrorEventArgs args)
    {
        _logger.LogError(args.Exception, "Service Bus processor error");
        return Task.CompletedTask;
    }

    public Task StartAsync(CancellationToken ct) => _processor.StartProcessingAsync(ct);

    public async ValueTask DisposeAsync()
    {
        await _processor.DisposeAsync();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems quanh message settlement và database transaction.
2. Xác định duplicate-processing, concurrency và reliability risks.
3. Giải thích production impact khi SQL timeout, process crash hoặc message được redeliver.
4. Ưu tiên các vấn đề có thể gây mất event hoặc duplicate fulfillment.
5. Đề xuất corrected design phù hợp at-least-once delivery.
6. Giải thích cách test duplicate delivery và failure windows.
7. Nêu telemetry cần theo dõi ở Service Bus và application.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu `CompleteMessageAsync` thành công nhưng process crash trước `SaveChangesAsync`?
2. Nếu cùng `MessageId` được delivery hai lần, database hiện có gì ngăn tạo hai `FulfillmentJob`?
3. `MaxConcurrentCalls = 16` thay đổi race surface như thế nào khi nhiều messages liên quan cùng order?
4. Cancellation và message lock lifecycle cần được truyền/quan sát ở đâu?
5. Khi business update đã commit nhưng settlement thất bại, lần delivery sau phải có semantics gì?

## Gợi ý

### Gợi ý 1

Primary risk là business state và message settlement đang nằm ở hai failure domains nhưng code xử lý như một atomic operation.

### Gợi ý 2

At-least-once delivery yêu cầu consumer chịu được duplicate. Hãy tìm một durable idempotency boundary thay vì dựa vào việc handler “thường chỉ chạy một lần”.

## Kết quả code review tham khảo

### Critical — Message được complete trước khi business state commit

**Vấn đề:** handler settlement message trước database work.  
**Tại sao xảy ra:** Service Bus settlement và SQL transaction là hai operations độc lập.  
**Ảnh hưởng production:** nếu complete thành công rồi SQL timeout/process crash, broker không còn delivery message nhưng order chưa được cập nhật: business event bị mất ở application layer.  
**Cách sửa:** chỉ complete sau khi durable business transaction thành công. Nếu settlement sau commit thất bại, consumer phải chịu được redelivery bằng idempotency.

### Critical — Không có durable idempotency protection

**Vấn đề:** mỗi delivery luôn thêm `FulfillmentJob`.  
**Tại sao xảy ra:** code giả định handler chỉ chạy một lần, trong khi messaging có thể redeliver.  
**Ảnh hưởng production:** duplicate fulfillment có thể tạo shipment/work thực tế nhiều lần.  
**Cách sửa:** persist processed-message identity hoặc business idempotency key trong cùng SQL transaction với order/job update. Thêm unique constraint để database enforce invariant, không chỉ check-then-insert trong application.

### High — Concurrent messages cho cùng order không có business concurrency policy

**Vấn đề:** nhiều handlers có thể load/update cùng order đồng thời.  
**Tại sao xảy ra:** `MaxConcurrentCalls` và multiple instances tăng parallelism; không có optimistic concurrency/version/invariant enforcement.  
**Ảnh hưởng production:** state transitions hoặc downstream job creation có thể conflict/out-of-order.  
**Cách sửa:** xác định ordering requirement. Dùng optimistic concurrency/business transition validation, hoặc Service Bus sessions nếu ordering theo key là requirement và trade-off phù hợp; không mặc định serialize toàn queue.

### High — Failure sau DB commit nhưng trước settlement chưa được thiết kế

**Vấn đề:** corrected ordering “DB trước, complete sau” vẫn có window DB commit thành công nhưng settlement fail.  
**Tại sao xảy ra:** distributed atomicity không tự xuất hiện.  
**Ảnh hưởng production:** message được redeliver. Nếu consumer không idempotent, duplicate side effect vẫn xảy ra.  
**Cách sửa:** idempotent transaction làm redelivery trở thành no-op business-wise, sau đó complete message.

### Medium — CancellationToken không propagate vào database/settlement

**Vấn đề:** EF và settlement calls không dùng `args.CancellationToken`.  
**Tại sao xảy ra:** handler bỏ qua processor lifecycle cancellation.  
**Ảnh hưởng production:** shutdown/lock-loss scenarios khó dừng sạch và work có thể kéo dài ngoài lifecycle mong muốn.  
**Cách sửa:** truyền cancellation token qua EF queries, SaveChanges và settlement nơi API hỗ trợ.

### Medium — Message validation/deserialization failure không có policy rõ ràng

**Vấn đề:** malformed payload có thể throw lặp lại mà không phân biệt poison message.  
**Tại sao xảy ra:** không có validation/dead-letter decision.  
**Ảnh hưởng production:** repeated delivery tiêu tốn capacity và tạo noise.  
**Cách sửa:** validate schema/business-required fields; dead-letter permanent-invalid messages với reason phù hợp; transient failures nên abandon/retry theo policy.

### Medium — Không kiểm soát invariant bằng database constraint

**Vấn đề:** duplicate fulfillment prevention nếu chỉ làm application check vẫn có race.  
**Tại sao xảy ra:** hai concurrent transactions có thể cùng quan sát “chưa tồn tại”.  
**Ảnh hưởng production:** duplicate row dưới concurrency.  
**Cách sửa:** unique index/constraint trên business key phù hợp, ví dụ một fulfillment job cho `(OrderId, JobType)` nếu đó thực sự là invariant.

### Medium — Telemetry thiếu delivery metadata và processing outcome

**Vấn đề:** success log chỉ có MessageId/OrderId; error callback quá generic.  
**Tại sao xảy ra:** không capture delivery count, queue/entity, duration, duplicate/no-op outcome hoặc settlement failure.  
**Ảnh hưởng production:** khó phân biệt poison messages, transient DB failures, lock/settlement problems và duplicate delivery.  
**Cách sửa:** structured logs/traces/metrics với message ID, correlation/business key, delivery count, processing duration, DB outcome, idempotency outcome và settlement outcome.

## Phiên bản đề xuất

Ví dụ dưới đây dùng SQL inbox record làm durable idempotency key. Giả định `ProcessedMessage.MessageId` có unique index và `FulfillmentJob` có unique business constraint phù hợp requirement.

```csharp
private async Task ProcessMessageAsync(ProcessMessageEventArgs args)
{
    var ct = args.CancellationToken;
    OrderPaidMessage message;

    try
    {
        message = args.Message.Body.ToObjectFromJson<OrderPaidMessage>();
    }
    catch (Exception ex) when (ex is JsonException or InvalidOperationException)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "InvalidPayload",
            "OrderPaid payload could not be deserialized.",
            ct);
        return;
    }

    await using var scope = _scopeFactory.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

    var alreadyProcessed = await db.ProcessedMessages
        .AsNoTracking()
        .AnyAsync(x => x.MessageId == args.Message.MessageId, ct);

    if (!alreadyProcessed)
    {
        await using var transaction = await db.Database.BeginTransactionAsync(ct);

        try
        {
            var order = await db.Orders
                .SingleAsync(x => x.Id == message.OrderId, ct);

            if (order.Status != "Paid")
            {
                order.Status = "Paid";
                order.PaidUtc = message.PaidUtc;

                db.FulfillmentJobs.Add(new FulfillmentJob
                {
                    OrderId = order.Id,
                    CreatedUtc = DateTime.UtcNow
                });
            }

            db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = args.Message.MessageId,
                ProcessedUtc = DateTime.UtcNow
            });

            await db.SaveChangesAsync(ct);
            await transaction.CommitAsync(ct);
        }
        catch (DbUpdateException ex) when (IsIdempotencyConstraintViolation(ex))
        {
            await transaction.RollbackAsync(ct);
            _logger.LogInformation(
                "Message {MessageId} was already committed by another consumer",
                args.Message.MessageId);
        }
    }

    await args.CompleteMessageAsync(args.Message, ct);
}
```

`IsIdempotencyConstraintViolation` phải kiểm tra provider-specific unique-constraint signal một cách chính xác; không được nuốt mọi `DbUpdateException`. Việc `order.Status != "Paid"` chỉ là minh họa và không thay thế business state machine nếu order có nhiều transitions.

## Giải thích thiết kế sau khi sửa

Business update và inbox/idempotency marker được commit trong cùng database transaction. Settlement chỉ xảy ra sau durable commit. Nếu process chết sau commit nhưng trước complete, message được delivery lại; unique idempotency key khiến lần xử lý sau không lặp business side effect rồi có thể complete.

Không cần distributed transaction giữa Service Bus và SQL để đạt mục tiêu này. Điều quan trọng là thiết kế failure window thành safe redelivery. Nếu downstream fulfillment lại publish message khác, Outbox Pattern có thể cần thiết để đảm bảo database state và intent-to-publish cùng durable.

## Trade-offs

Inbox table tăng storage và cần retention/index maintenance. Unique constraints yêu cầu chọn business key đúng. Service Bus sessions có thể đơn giản hóa ordering theo entity nhưng giảm parallelism và tăng operational constraints; chỉ dùng khi ordering thực sự là requirement. Tăng `MaxConcurrentCalls` cải thiện throughput đến một điểm nhưng có thể tăng DB contention và lock pressure.

## Cách kiểm thử

1. **Integration test:** inject failure sau `CompleteMessageAsync` trong code cũ để chứng minh lost event; corrected design không settlement trước commit.
2. **Duplicate-delivery concurrency test:** xử lý cùng `MessageId` đồng thời từ hai handlers; assert đúng một fulfillment business effect.
3. **Failure-path test:** DB commit thành công rồi settlement throw; redelivery tiếp theo phải no-op business-wise và complete được.
4. **Poison-message test:** malformed payload được dead-letter theo policy, không retry vô hạn.
5. **Load test:** tăng concurrency và theo dõi DB waits, handler p95/p99, queue depth và duplicate/idempotency rate.

## Quan sát trong production

Theo dõi active message count, dead-letter count, delivery count distribution, processing latency, settlement failures, lock-related failures, DB dependency duration, SQL timeout/deadlock, idempotency-hit count và fulfillment uniqueness violations. Correlate Service Bus `MessageId` với business `OrderId` trong Application Insights/structured logs nhưng tránh log payload nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu handler cần gọi external fulfillment API thay vì chỉ ghi SQL, bạn đặt idempotency boundary ở đâu?
2. Khi nào Service Bus sessions đáng đổi lấy throughput thấp hơn?
3. Inbox retention có thể xóa record sau bao lâu mà vẫn giữ được idempotency guarantee cần thiết?

# Code Review Challenge 2 — SQL pagination chậm dần theo page và trả record trùng khi dữ liệu thay đổi

**Chủ đề:** SQL Server, query plan, composite index, OFFSET pagination, keyset pagination, consistency  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 6–8

## Bối cảnh

Một admin portal hiển thị audit events. Bảng `AuditEvents` có khoảng 80 triệu rows và tăng liên tục. API cho phép filter theo `TenantId`, `CreatedUtc` range và optional `EventType`. UI dùng page number, mỗi page 100 rows.

Page đầu thường dưới 150 ms, nhưng page 5.000 có thể mất nhiều giây. Trong lúc users paging, events mới tiếp tục được insert nên đôi khi UI thấy record bị lặp hoặc bỏ sót giữa hai pages. Team đề xuất tăng SQL command timeout và thêm index riêng cho từng column.

## Đoạn code cần review

```sql
CREATE INDEX IX_AuditEvents_TenantId
ON dbo.AuditEvents(TenantId);

CREATE INDEX IX_AuditEvents_CreatedUtc
ON dbo.AuditEvents(CreatedUtc);

CREATE INDEX IX_AuditEvents_EventType
ON dbo.AuditEvents(EventType);
GO

CREATE PROCEDURE dbo.GetAuditEvents
    @TenantId uniqueidentifier,
    @FromUtc datetime2,
    @ToUtc datetime2,
    @EventType nvarchar(100) = NULL,
    @Page int = 1
AS
BEGIN
    SELECT
        Id,
        TenantId,
        CreatedUtc,
        EventType,
        ActorId,
        Summary
    FROM dbo.AuditEvents
    WHERE TenantId = @TenantId
      AND CreatedUtc >= @FromUtc
      AND CreatedUtc < @ToUtc
      AND (@EventType IS NULL OR EventType = @EventType)
    ORDER BY CreatedUtc DESC
    OFFSET (@Page - 1) * 100 ROWS
    FETCH NEXT 100 ROWS ONLY;
END
```

## Nhiệm vụ của ứng viên

1. Xác định performance và correctness risks của query/pagination.
2. Giải thích vì sao deep page có thể đắt dù chỉ trả 100 rows.
3. Phân tích index theo query shape thay vì đề xuất “thêm index” chung chung.
4. Giải thích record duplication/omission khi concurrent inserts xảy ra.
5. Đề xuất query/API contract tốt hơn nếu requirement cho phép.
6. Nêu tests với production-like cardinality và concurrent writes.
7. Nêu database telemetry/evidence cần capture trước và sau fix.

## Câu hỏi gợi mở

1. Database phải làm bao nhiêu work trước khi trả 100 rows ở page 5.000?
2. `ORDER BY CreatedUtc` có deterministic không nếu nhiều events có cùng timestamp?
3. Ba single-column indexes có khớp equality/range/order shape của query không?
4. Page number có thể giữ stable meaning khi rows mới được insert ở đầu result set không?
5. Optional `EventType` ảnh hưởng plan/selectivity như thế nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính gồm cả deep-offset cost và unstable ordering/pagination semantics.

### Gợi ý 2

Hãy thiết kế index bắt đầu từ predicate/order thực tế và cân nhắc cursor chứa đủ columns để tạo strict ordering.

## Kết quả code review tham khảo

### High — Deep OFFSET buộc engine xử lý/bỏ qua lượng rows ngày càng lớn

**Vấn đề:** page number được chuyển thành `OFFSET` lớn.  
**Tại sao xảy ra:** engine vẫn phải tìm/order và skip các rows trước target page; cost không cố định chỉ vì `FETCH NEXT` là 100.  
**Ảnh hưởng production:** latency và reads tăng theo depth, tạo p99 xấu và DB pressure.  
**Cách sửa:** nếu UX không bắt buộc random page jumps, dùng keyset/seek pagination dựa trên sort key ổn định.

### High — Sort key không unique nên pagination không deterministic

**Vấn đề:** chỉ `ORDER BY CreatedUtc DESC`.  
**Tại sao xảy ra:** nhiều rows có thể cùng `CreatedUtc`; SQL không phải giữ thứ tự ổn định giữa ties nếu không có tie-breaker.  
**Ảnh hưởng production:** duplicate/missing records giữa calls, đặc biệt khi concurrent inserts/plan changes.  
**Cách sửa:** dùng strict order như `ORDER BY CreatedUtc DESC, Id DESC` và cursor chứa cả hai values.

### High — Page-number pagination không ổn định dưới concurrent inserts

**Vấn đề:** vị trí ordinal của rows thay đổi giữa requests.  
**Tại sao xảy ra:** event mới insert ở đầu result set đẩy rows cũ sang page sau.  
**Ảnh hưởng production:** user có thể thấy lại row hoặc bỏ qua row dù query từng page đều đúng tại thời điểm riêng của nó.  
**Cách sửa:** keyset pagination neo vào last seen `(CreatedUtc, Id)`, hoặc nếu business cần snapshot-consistent browsing thì phải định nghĩa snapshot boundary/consistency strategy rõ ràng.

### Medium — Single-column indexes không phản ánh query access pattern

**Vấn đề:** indexes tách riêng TenantId, CreatedUtc, EventType có thể không hỗ trợ tốt filter + order combined.  
**Tại sao xảy ra:** query thường equality trên tenant rồi range/order theo CreatedUtc.  
**Ảnh hưởng production:** extra reads/sort/key lookups tùy plan/cardinality.  
**Cách sửa:** kiểm tra actual execution plan và workload; candidate index thường bắt đầu `(TenantId, CreatedUtc DESC, Id DESC)` với INCLUDE columns phù hợp. `EventType` placement/index riêng phụ thuộc selectivity và workload, không có universal answer.

### Medium — Optional OR predicate có thể tạo plan không phù hợp cho mọi parameter shape

**Vấn đề:** `(@EventType IS NULL OR EventType = @EventType)` gộp hai selectivity patterns.  
**Tại sao xảy ra:** một cached plan có thể không tối ưu cho cả filtered và unfiltered cases tùy distribution/statistics.  
**Ảnh hưởng production:** latency variance.  
**Cách sửa:** đo actual plans/query store trước; cân nhắc separate query branches/dynamic parameterized SQL hoặc compilation strategy khi evidence cho thấy plan sensitivity thực sự là vấn đề.

### Medium — Không validate page/range inputs

**Vấn đề:** `@Page <= 0`, range quá rộng hoặc overflow expression không được guard.  
**Tại sao xảy ra:** procedure tin caller.  
**Ảnh hưởng production:** errors hoặc intentionally expensive queries.  
**Cách sửa:** validate inputs và áp business limits cho query window/page behavior.

### Low — Timeout increase chỉ che work amplification

**Vấn đề:** tăng command timeout không giảm reads/sort/skip cost.  
**Tại sao xảy ra:** timeout là failure threshold, không phải optimization.  
**Ảnh hưởng production:** requests giữ resources lâu hơn và có thể làm incident nặng hơn.  
**Cách sửa:** tối ưu access path/API semantics rồi đặt timeout theo SLO và failure budget.

## Phiên bản đề xuất

Giả định UI chấp nhận next/previous cursor thay vì random jump tới page 5.000. Cursor gồm `CreatedUtc` và `Id` của row cuối page trước.

```sql
CREATE INDEX IX_AuditEvents_Tenant_Created_Id
ON dbo.AuditEvents(TenantId, CreatedUtc DESC, Id DESC)
INCLUDE (EventType, ActorId, Summary);
GO

CREATE PROCEDURE dbo.GetAuditEventsSeek
    @TenantId uniqueidentifier,
    @FromUtc datetime2,
    @ToUtc datetime2,
    @EventType nvarchar(100) = NULL,
    @CursorCreatedUtc datetime2 = NULL,
    @CursorId bigint = NULL
AS
BEGIN
    SET NOCOUNT ON;

    SELECT TOP (100)
        Id,
        TenantId,
        CreatedUtc,
        EventType,
        ActorId,
        Summary
    FROM dbo.AuditEvents
    WHERE TenantId = @TenantId
      AND CreatedUtc >= @FromUtc
      AND CreatedUtc < @ToUtc
      AND (@EventType IS NULL OR EventType = @EventType)
      AND (
            @CursorCreatedUtc IS NULL
            OR CreatedUtc < @CursorCreatedUtc
            OR (CreatedUtc = @CursorCreatedUtc AND Id < @CursorId)
          )
    ORDER BY CreatedUtc DESC, Id DESC;
END
```

Kiểu của `Id` trong ví dụ là `bigint`; nếu schema thật dùng kiểu khác thì parameter phải khớp. INCLUDE list phải được đánh giá theo row width/write cost; không mặc định cover mọi column nếu `Summary` rất lớn.

## Giải thích thiết kế sau khi sửa

Seek predicate tiếp tục từ row cuối đã thấy thay vì đếm/skipping toàn bộ prefix. `(CreatedUtc, Id)` tạo strict ordering và cursor ổn định hơn khi events mới được insert phía trước. Composite index align với tenant equality và descending traversal theo sort keys.

Nếu product requirement bắt buộc jump tới arbitrary page number, keyset pagination không đáp ứng trực tiếp; khi đó cần cân nhắc giới hạn deep paging, precomputed navigation/search UX khác hoặc chấp nhận cost có đo lường. Nếu requirement cần một snapshot tuyệt đối không đổi qua nhiều requests, cursor alone không tạo full snapshot isolation xuyên requests; cần snapshot boundary/data-version design riêng.

## Trade-offs

Composite covering index tăng storage và write amplification trên bảng append-heavy. INCLUDE `Summary` có thể làm index rất rộng. Keyset pagination làm API contract phức tạp hơn và không hỗ trợ random page jump tự nhiên. Optional EventType có thể cần index/query variant riêng nếu workload chứng minh filter này rất phổ biến/selective.

## Cách kiểm thử

1. **Database performance test:** seed cardinality gần production; so logical reads/duration của first page và deep OFFSET với seek pagination.
2. **Correctness test:** nhiều rows cùng `CreatedUtc`; verify cursor traversal không duplicate/miss do tie ordering.
3. **Concurrent-write test:** insert events mới giữa page requests; verify already-traversed sequence không bị dịch như page-number approach.
4. **Plan test:** capture actual execution plans cho `EventType = NULL` và selective values; kiểm tra statistics/parameter sensitivity bằng evidence.
5. **Load test:** concurrent tenants/query ranges; theo dõi CPU, reads, waits, memory grants và p95/p99.

## Quan sát trong production

Theo dõi query duration p50/p95/p99, logical reads, rows examined/returned, execution plans/Query Store, sort spills, memory grants, waits và timeout rate. Ở API layer theo dõi cursor usage, requested time-window width và dependency telemetry. Alert dựa trên latency/error SLO thay vì chỉ CPU tổng.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc user nhảy trực tiếp tới page 5.000, bạn giữ page-number semantics nhưng giảm rủi ro thế nào?
2. Nếu `EventType` chỉ có vài giá trị và distribution rất skewed, index/query strategy có thể thay đổi ra sao?
3. Keyset pagination có đảm bảo snapshot-consistent result xuyên nhiều requests không? Nếu không, khi nào điều đó quan trọng?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Message processing an toàn không dựa vào giả định “mỗi message chỉ đến một lần”; phải thiết kế transaction/idempotency quanh các failure windows giữa broker và database. Với data access, API pagination semantics quyết định cả correctness lẫn performance: deep OFFSET và non-unique ordering có thể trở thành vấn đề production dù query nhìn rất đơn giản.

## Mẫu tư duy cần nhớ

- Thiết kế retry/redelivery cùng durable idempotency.
- Tìm failure window giữa các hệ thống không cùng transaction boundary.
- Dùng database constraint để enforce invariant quan trọng dưới concurrency.
- Thiết kế index từ query shape và evidence, không từ danh sách columns.
- Khi dữ liệu thay đổi liên tục, xác định rõ pagination consistency semantics trước khi tối ưu query.
