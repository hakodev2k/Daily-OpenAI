# Câu 1 — Tenant isolation và Dependency Injection trong ASP.NET Core

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** C#/.NET, DI lifetimes, concurrency, ASP.NET Core authorization, EF Core.

## Bối cảnh

API .NET 8 quản lý nhân sự đa tenant, chạy nhiều Azure App Service instances. `TenantResolver` được đăng ký Singleton và lưu tenant ID vào một mutable field để “tránh resolve lại”. Một số request đồng thời trả dữ liệu sai tenant; mỗi request có JWT và DbContext Scoped. Chưa rõ tenant lấy từ token hay header và SQL có tenant predicate hay không.

## Câu hỏi chính

Giải thích chính xác cơ chế tạo và chia sẻ Singleton, Scoped, concurrent request; điều tra và thiết kế lại tenant isolation sao cho không thể chỉ sửa một lifetime rồi coi như đã an toàn.

## Câu hỏi làm rõ nên cân nhắc

1. Tenant ID đến từ authenticated principal hay input client?
2. Resolver có lưu `HttpContext`, `DbContext` hoặc mutable state không?
3. Có cache, background worker hoặc raw SQL truy cập dữ liệu không?
4. Tenant dùng shared database hay database-per-tenant?

## Gợi ý tư duy

### Gợi ý 1
Lifetime của service không phải lifetime của request data.

### Gợi ý 2
Một mutable field trong Singleton có thể được đọc/ghi từ nhiều request cùng lúc.

### Gợi ý 3
Theo dõi tenant identity qua authorization, cache key, EF Core query và write boundary.

## Cấu trúc trả lời đề xuất

1. Xác định data exposure và trust boundary.
2. Diễn giải DI lifetime, captive dependency, concurrency.
3. Đề xuất competing hypotheses và instrumentation.
4. Thiết kế authorization và tenant isolation.
5. Kiểm thử concurrent và rollout an toàn.

## Ý chính của câu trả lời tốt

### Bắt buộc
Singleton được chia sẻ; mutable tenant field không request-safe. Scoped DbContext không tự bảo vệ khi tenant đã sai. Client-supplied tenant phải được xác minh membership. Mọi read/write phải enforce tenant.

### Điểm cộng
Scope validation, cache namespace per tenant, background jobs có explicit tenant, correlation ID, integration tests.

### Senior+
Defense in depth qua database policies khi thích hợp, kiểm tra `IgnoreQueryFilters`, raw SQL và audit log không lộ PII.

## Hướng giải quyết tham khảo

**Giả thuyết:** shared mutable Singleton field có race; một cached tenant không được reset; cache key không chứa tenant; authorization chỉ check login mà không check tenant membership; SQL thiếu tenant predicate. Chưa thể kết luận nếu chưa có traces.

**Cơ chế:** Singleton sống suốt DI container và được nhiều request truy cập; Scoped thường được tạo một lần cho mỗi HTTP request scope. Một Singleton giữ mutable tenant ID sẽ làm request A/B tranh chấp hoặc tái sử dụng dữ liệu cũ. Nếu Singleton inject Scoped dependency, scope validation có thể phát hiện captive dependency khi được bật, nhưng không phát hiện mọi lỗi shared mutable state. `IHttpContextAccessor` không thay thế authorization.

**Khắc phục:** resolve tenant từ identity tin cậy hoặc kiểm tra tenant route/header với membership trên server; xây `ITenantContext` Scoped bất biến và fail closed. Enforce tenant predicates và ownership trên mọi query/write; thêm tenant vào cache keys. Background jobs truyền tenant từ job payload đã xác thực và tạo DI scope mới. Nếu dùng global query filter, audit mọi đường bypass và raw SQL. Đặt metrics cho denied access, tenant mismatch, cache anomalies; tránh log token/PII.

**Xác minh:** integration test chạy đồng thời hai principal với record ID trùng nhau; test unauthorized tenant switch; kiểm tra SQL parameters, cache keys và write ownership. Canary release, quan sát cross-tenant violations, rollback khi xuất hiện mismatch. Nếu database-per-tenant, cần kiểm tra connection routing thay vì chỉ query filters.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là security incident vì có thể lộ dữ liệu tenant. Singleton là shared object; mutable tenant field có thể bị request khác đọc hoặc ghi, trong khi Scoped DbContext không sửa được identity sai ở tầng trên. Tôi sẽ trace principal, resolved tenant, SQL predicate và cache key, rồi chạy concurrent tests với hai tenant. Tôi dùng scoped immutable tenant context nhưng quan trọng hơn là xác minh membership và enforce tenant trên cả read/write. Với background jobs tôi truyền tenant explicit. Sau đó chạy security regression, canary và alert tenant mismatch. Trade-off là thêm validation và test, đổi lại giảm nguy cơ data leak.”

## Câu hỏi đào sâu

1. `IHttpContextAccessor` bên trong Singleton có bảo đảm tenant isolation không?
2. EF Core global query filter có bảo vệ được mọi raw SQL và update không?
3. Khi throughput rất cao, explicit tenant parameter có ưu điểm gì so với scoped context?

## Lỗi trả lời thường gặp

- Chỉ đổi Singleton thành Scoped.
- Tin `X-Tenant-Id` mà không xác minh membership.
- Bỏ qua cache và background jobs.
- Kết luận root cause khi chưa có evidence.
- Log toàn bộ JWT để debug.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Requirement clarification | 1.5 |
| Technical correctness / DI mechanism | 2 |
| Debugging evidence và reasoning | 2 |
| Trade-offs / isolation design | 2 |
| Production readiness, tests, monitoring | 1.5 |
| Communication | 1 |

# Câu 2 — Cosmos DB: báo cáo cross-branch gây 429 và RU spike

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition keys, RU, Azure Monitor, ASP.NET Core, incident management.

## Bối cảnh

Booking API dùng Cosmos DB lưu event history. Sau khi thêm báo cáo “tất cả chi nhánh”, p95 từ 250 ms lên 4 giây, 429 tăng và RU consumption tăng (số liệu giả định). Booking chính còn hoạt động, nhưng dashboard lỗi. Chưa biết partition key, query plan, throughput mode, SDK retry hoặc data skew.

## Câu hỏi chính

Điều hành incident từ business impact đến prevention, phân biệt cross-partition query, hot partition, indexing, pagination và retry amplification bằng evidence trước khi đưa ra remediation.

## Câu hỏi làm rõ nên cân nhắc

1. Query mới có filter partition key không?
2. 429 phân bố theo partition và workload thế nào?
3. Có thay đổi indexing policy, RU capacity hoặc data volume cùng thời điểm không?
4. Báo cáo cần real-time hay chấp nhận eventual consistency?
5. Có feature flag để tắt riêng report không?

## Gợi ý tư duy

### Gợi ý 1
Bảo vệ booking traffic trước khi tối ưu report.

### Gợi ý 2
Đo RU/request, 429, SDK diagnostics và partition distribution.

### Gợi ý 3
Hot partition và fan-out query có nguyên nhân và giải pháp khác nhau.

## Cấu trúc trả lời đề xuất

1. Impact, severity, stakeholder update.
2. Stabilize bằng feature flag/rollback/rate limit.
3. Thu thập p95/p99, RU, 429, dependency traces.
4. Đặt competing hypotheses và kiểm chứng.
5. Short-term mitigation và long-term data model.
6. Regression, load test, alert, postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không tăng RU theo phản xạ. Kiểm tra partition key, query charge, retry, throughput và dữ liệu phân bố. Giới hạn blast radius để booking không bị ảnh hưởng.

### Điểm cộng
Continuation tokens, projections, indexes theo query pattern, bounded concurrency, query cost budgets.

### Senior+
Reporting read model, freshness SLA, partition migration có backfill/reconciliation, cost và consistency trade-offs.

## Hướng giải quyết tham khảo

**Impact:** xác định tỷ lệ report lỗi, nguy cơ ảnh hưởng booking khi cùng container/throughput; chỉ định incident owner và thông báo phạm vi đã xác minh.

**Stabilize:** disable bộ lọc mới hoặc giới hạn time range, giảm concurrency, rollback nếu cần. Không tăng RU vô hạn vì hot logical partition có thể vẫn bị giới hạn.

**Evidence:** Application Insights request/dependency traces, Cosmos SDK diagnostics, request charge, normalized RU consumption, 429 per partition, retry count, query shape, indexing metrics, data skew và API connection pressure.

**Competing hypotheses:** (A) thiếu partition key làm query fan-out; (B) một chi nhánh hot; (C) `ORDER BY` và filters thiếu index phù hợp; (D) query scan hoặc trả quá nhiều records; (E) nested retries khuếch đại traffic; (F) capacity thiếu. Dùng representative queries trên staging và đo RU, latency, continuation behavior. Chỉ công bố root cause khi chứng cứ loại trừ giả thuyết cạnh tranh.

**Fix:** dùng partition-key equality nếu requirement cho phép; projection và continuation token cho pagination; index theo access pattern có đo chi phí index/write. Nếu cross-branch reporting thường xuyên, cân nhắc materialized read model/aggregate bất đồng bộ, công bố freshness SLA. Nếu partition key thiết kế sai, lên kế hoạch container mới, backfill, reconciliation, cutover, rollback; không giả định thay key tại chỗ. Retry theo SDK và `Retry-After`, bounded timeout/concurrency, tránh retry chồng tầng.

**Verify/prevent:** load test đồng thời report + booking, fault injection 429, canary, alert 429/p95/RU cost, quota budget và runbook. Nếu yêu cầu strict real-time, read model eventual consistency có thể không đạt và phải cân nhắc query/capacity cost khác.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ cô lập ảnh hưởng của report, tạm tắt filter hoặc rollback để bảo vệ booking. Tôi thu thập 429 theo partition, RU/request, SDK diagnostics và dependency latency trước khi quyết định. Cross-partition fan-out, hot partition, index và retry amplification cần được kiểm chứng riêng. Nếu báo cáo toàn chi nhánh là yêu cầu lâu dài và chấp nhận độ trễ, tôi đánh giá read model pre-aggregated. Nếu cần real-time, tôi tối ưu query và capacity dựa trên đo đạc. Tôi chỉ đóng incident sau load test, canary và alert theo latency, throttling, RU.”

## Câu hỏi đào sâu

1. Vì sao tăng provisioned RU vẫn có thể không giải quyết 429?
2. Nếu Product yêu cầu strict consistency, bạn có giữ read model bất đồng bộ không?
3. Bạn migrate partition key như thế nào mà không mất hoặc nhân đôi event?

## Lỗi trả lời thường gặp

- Chỉ tăng RU mà không xem partition skew.
- Retry 429 không giới hạn.
- Không bảo vệ critical booking workload.
- Kết luận thiếu index mà không có diagnostics.
- Không xác định freshness SLA hoặc cost.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact / requirement clarification | 1.5 |
| Cosmos partition, RU, 429 correctness | 2 |
| Evidence, competing hypotheses | 2 |
| Trade-offs và design | 2 |
| Tests, rollback, monitoring | 1.5 |
| Incident communication | 1 |

# Câu 3 — Optimizely CMS, React và Akamai: có nên chuyển marketing site thành SPA?

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, React, Akamai CDN, SEO, Azure App Service, content delivery, migration.

## Bối cảnh

Marketing website hoạt động ở 8 thị trường, dùng Optimizely server-rendered pages và một số jQuery widgets. Nhóm frontend đề xuất rewrite toàn bộ thành React SPA. SEO team lo mất crawlability, editor cần draft preview và publish trong vài phút. Akamai cache HTML/assets; campaign traffic có spike. Chưa có baseline Lighthouse, Core Web Vitals, cache hit ratio hay editorial workflow map. Budget vận hành hạn chế.

## Câu hỏi chính

Chọn rendering strategy, content architecture, cache invalidation và migration plan bảo đảm SEO, editorial preview, performance và rollback. So sánh các lựa chọn mà không mặc định microservices hoặc headless SPA tốt hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Trang nào SEO-critical, trang nào cần personalization hoặc tương tác?
2. Publish freshness và preview authorization SLA là gì?
3. Content blocks có được reuse giữa nhiều page/locale không?
4. Akamai cache key, TTL, purge, cookies và query parameters đang cấu hình thế nào?
5. Có dữ liệu crawlability, LCP/INP/CLS và conversion baseline không?

## Gợi ý tư duy

### Gợi ý 1
Framework UI và chiến lược rendering là hai quyết định khác nhau.

### Gợi ý 2
Draft preview không được đi qua shared public cache.

### Gợi ý 3
Một shared block update có thể ảnh hưởng nhiều page; purge failure cũng cần recovery.

## Cấu trúc trả lời đề xuất

1. Phân loại page và acceptance criteria.
2. Đánh giá traditional rendering, hybrid/SSR, client SPA.
3. Content modeling, API boundaries, preview/publish workflow.
4. CDN/cache keys, invalidation, fallback.
5. SEO/security/performance.
6. Incremental rollout, tests, telemetry, rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc
Public SEO pages cần crawlable HTML, metadata, canonical/redirects phù hợp; draft preview phải authorization và không bị public cache. Không đánh đồng SPA với modernization.

### Điểm cộng
React islands, locale-specific sitemap/hreflang khi cần, hashed static assets, CDN origin shielding, content dependency invalidation.

### Senior+
Architecture decision record dựa trên measurable outcomes, cache purge reconciliation, migration strangler pattern, ownership và operational costs.

## Hướng giải quyết tham khảo

**Assumptions:** phần lớn pages là public marketing content và SEO-critical; chỉ vài components cần interactive React. Nếu phần lớn là authenticated application, lựa chọn có thể khác.

**Option A — giữ server-rendered Optimizely:** giữ workflow, preview và ít moving parts; giới hạn khả năng tái sử dụng UI đa kênh. **Option B — hybrid:** server-rendered HTML cho SEO, React islands cho widgets; nếu có nhiều kênh thật sự, cân nhắc headless API/SSR. Đổi lại là thêm API contracts, deployment và monitoring. **Option C — full SPA:** hợp với authenticated applications nhưng cần chứng minh crawlability, initial content, metadata và performance; không mặc định tốt cho marketing pages.

**Content:** versioned page/block types, locale variants, editorial permissions, preview token handling, publish events. Draft preview qua authenticated origin/bypass shared CDN, `Cache-Control: private, no-store` khi phù hợp. Chặn XSS trong rich text, giữ least privilege cho CMS và purge credentials.

**Cache:** public HTML TTL theo freshness SLA, purge theo page/block dependency, hashed assets TTL dài; cache key phải xét locale và những biến thể thực sự cần thiết. Không cache personalized responses công khai. Khi purge timeout, dùng retry có idempotency, audit/reconciliation và TTL fallback; không hứa edge cập nhật tức thời.

**SEO:** SSR/crawlable HTML, canonical, redirects 301, hreflang cho bản địa hóa nếu phù hợp, sitemaps, robots policy, structured data, Core Web Vitals. Đo Lighthouse cùng real-user metrics, crawl logs và cache hit ratio.

**Migration:** inventory URL/content blocks, baseline, chọn một page type, implement hybrid slice, Playwright E2E cho preview/publish/redirects, crawl comparison, canary và rollback theo route. Không rewrite tất cả khi chưa chứng minh ROI. Nếu CMS API lỗi, dùng cached published snapshot/fallback theo freshness requirement; không để preview draft leak vào edge.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không quyết định SPA trước khi biết trang nào cần SEO và tương tác. Tôi đo crawlability, Core Web Vitals, CDN cache hit và publish latency. Với marketing pages, tôi ưu tiên HTML server-rendered, dùng React islands cho tương tác; nếu multi-channel thật sự cần, tôi đánh giá hybrid/headless với chi phí rõ ràng. Preview phải tách khỏi public cache; publish cần invalidation theo content dependencies và recovery khi purge thất bại. Tôi migrate từng page type, chạy Playwright và SEO parity tests, canary theo route, giữ rollback. Chỉ mở rộng khi số liệu xác nhận lợi ích.”

## Câu hỏi đào sâu

1. Shared block cập nhật trên 10.000 pages thì purge thế nào để tránh origin overload?
2. Trường hợp nào full React SPA tốt hơn hybrid/SSR?
3. Nếu purge Akamai timeout sau publish, bạn thiết kế convergence và audit thế nào?

## Lỗi trả lời thường gặp

- Mặc định React SPA là cải tiến bắt buộc.
- Cache cả draft/personalized HTML ở public CDN.
- Không thiết kế purge failure recovery.
- Bỏ qua canonical, redirects và locale SEO.
- Không có baseline, canary hoặc rollback.
