# Code Review Challenge 1 — `Task.WhenAll` làm endpoint nhanh hơn trong test nhưng production lại nổ `DbContext` concurrency và overload external API

**Chủ đề:** C#/.NET, ASP.NET Core, Entity Framework Core, `Task.WhenAll`, `DbContext` lifetime, async/concurrency, external API, cancellation, bounded concurrency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 API dùng EF Core để tổng hợp dashboard cho một tenant. Endpoint cần:

- lấy tối đa 200 active employees từ SQL Server;
- với mỗi employee, đọc một số dữ liệu nội bộ từ database;
- gọi external HR provider để lấy leave balance;
- trả dashboard trong khoảng thời gian chấp nhận được;
- client có thể hủy request;
- external provider giới hạn throughput và đôi lúc timeout/429;
- nhiều users có thể mở dashboard đồng thời;
- application chạy nhiều App Service instances;
- không được làm connection pool, ThreadPool hoặc external dependency bị overload;
- nếu một employee lỗi không nghiêm trọng, product cho phép trả partial result với trạng thái rõ ràng thay vì fail toàn bộ response.

Ban đầu code chạy tuần tự và khá chậm. Một developer refactor bằng `Task.WhenAll`:

## Đoạn code cần review

```csharp
[Authorize]
[HttpGet("dashboard/employees")]
public async Task<IActionResult> GetEmployeeDashboard(
    CancellationToken cancellationToken)
{
    var tenantId = User.FindFirst("tenant_id")!.Value;

    var employees = await _db.Employees
        .Where(x => x.TenantId == tenantId && x.IsActive)
        .OrderBy(x => x.Id)
        .Take(200)
        .ToListAsync(cancellationToken);

    var tasks = employees.Select(async employee =>
    {
        var latestTimesheet = await _db.Timesheets
            .Where(x => x.EmployeeId == employee.Id)
            .OrderByDescending(x => x.WorkDate)
            .FirstOrDefaultAsync();

        var approvals = await _db.Approvals
            .CountAsync(x =>
                x.EmployeeId == employee.Id &&
                x.Status == ApprovalStatus.Pending);

        var leaveBalance = await _hrClient.GetLeaveBalanceAsync(
            employee.ExternalEmployeeId,
            CancellationToken.None);

        return new EmployeeDashboardItem(
            employee.Id,
            employee.DisplayName,
            latestTimesheet?.WorkDate,
            approvals,
            leaveBalance.RemainingDays);
    });

    var result = await Task.WhenAll(tasks);

    return Ok(result);
}
```

Sau khi deploy:

- test với 5–10 employees thường nhanh;
- production thỉnh thoảng xuất hiện `InvalidOperationException` liên quan tới một operation mới bắt đầu trên `DbContext` trước operation trước hoàn tất;
- external HR provider thấy burst request lớn và bắt đầu trả 429;
- p95 endpoint dao động mạnh;
- khi browser đóng tab, nhiều HR calls vẫn tiếp tục;
- một HR request timeout làm toàn bộ `Task.WhenAll` throw và response fail;
- SQL Server có nhiều round trips dù query đầu tiên chỉ lấy tối đa 200 employees;
- team đề xuất tăng connection pool và retry mọi 429 ngay lập tức;
- chưa có metric về số concurrent HR calls, số SQL queries/request hoặc partial failures.

## Nhiệm vụ của ứng viên

Hãy review đoạn code theo góc nhìn production và:

1. xác định các vấn đề correctness, concurrency, database access, dependency pressure, cancellation và failure handling;
2. giải thích vì sao `Task.WhenAll` trên các lambdas này có thể dùng cùng một scoped `DbContext` đồng thời;
3. phân tích N+1/database round trips và external-call fan-out;
4. chỉ ra vì sao “async” không đồng nghĩa “unbounded parallelism là an toàn”;
5. ưu tiên findings theo severity;
6. đề xuất implementation/design đơn giản hơn nhưng bounded và production-safe;
7. mô tả test strategy cho concurrency, 429, timeout, cancellation và partial result;
8. đề xuất telemetry đủ để biết bottleneck nằm ở SQL, HR provider hay application coordination.

## Câu hỏi gợi mở

1. `AddDbContext` thường tạo lifetime nào trong ASP.NET Core, và 200 lambdas đang tham chiếu tới object `_db` nào?
2. Nếu tất cả 200 tasks cùng bắt đầu gần nhau, external HR provider sẽ thấy traffic shape ra sao khi có 20 users mở dashboard cùng lúc?
3. Có thực sự cần hai SQL queries riêng cho từng employee hay có thể reshape dữ liệu trước khi fan-out external calls?
4. Nếu một HR call trả 429 hoặc timeout, `Task.WhenAll` ảnh hưởng response tổng thể thế nào?
5. Khi client hủy request, tại sao `CancellationToken.None` làm work tiếp tục dù caller không còn chờ kết quả?

## Kết quả code review tham khảo

### Critical — Dùng cùng một scoped `DbContext` cho nhiều EF Core operations chạy song song

**Vấn đề:**  
Các tasks trong `employees.Select(...)` đều capture cùng field `_db`. Khi `Task.WhenAll` kích hoạt nhiều asynchronous flows, nhiều query có thể chạy song song trên cùng `DbContext` instance.

**Tại sao xảy ra:**  
`DbContext` không hỗ trợ multiple parallel operations trên cùng instance. ASP.NET Core thường đăng ký `DbContext` theo scoped lifetime, nên một request có một context; việc tạo 200 tasks không tạo 200 contexts.

**Ảnh hưởng production:**  
Có thể nhận `InvalidOperationException`, operation bị fail giữa chừng hoặc tạo behavior không an toàn nếu concurrent access không được detect đầy đủ.

**Cách sửa:**  
Ưu tiên reshape database work thành ít queries tuần tự trên một context. Nếu thực sự cần chạy DB operations song song, mỗi operation phải có context riêng, ví dụ qua `IDbContextFactory<TContext>`, nhưng không nên dùng parallel database fan-out nếu một set-based query giải quyết được đơn giản hơn.

Tài liệu tham khảo: Microsoft Learn — DbContext lifetime và threading: `https://learn.microsoft.com/ef/core/dbcontext-configuration/`

---

### Critical — External API fan-out không có giới hạn concurrency

**Vấn đề:**  
Tối đa 200 employees tương đương tối đa khoảng 200 HR calls gần như đồng thời cho một request.

**Tại sao xảy ra:**  
`Task.WhenAll` không tự giới hạn concurrency. Khi nhiều users/instances cùng gọi endpoint, tổng concurrency tăng theo phép nhân.

**Ảnh hưởng production:**  
429, timeout, queueing trong `HttpClient`/network stack, latency tail tăng và có thể tạo retry storm nếu application retry thiếu backoff.

**Cách sửa:**  
Dùng bounded concurrency phù hợp với provider contract và measured capacity, ví dụ `SemaphoreSlim`, `Parallel.ForEachAsync` với `MaxDegreeOfParallelism`, hoặc resilience handler/rate limiter ở outbound client. Giới hạn phải được chọn theo provider quota, latency và total application scale, không theo một con số tùy ý.

---

### High — N+1 x2 database queries

**Vấn đề:**  
Sau query employees, code chạy thêm tối đa hai database queries cho mỗi employee:

```text
1 employee query
+ 200 latest-timesheet queries
+ 200 pending-approval queries
```

**Tại sao xảy ra:**  
Business aggregation được thực hiện row-by-row thay vì set-based projection/grouping.

**Ảnh hưởng production:**  
Nhiều round trips, tăng connection usage, latency và database command volume; khi kết hợp parallelism còn làm spike load thay vì chỉ làm endpoint nhanh hơn.

**Cách sửa:**  
Đưa dữ liệu nội bộ về một hoặc vài set-based queries/projections. Ví dụ project employee + latest date + pending count bằng query phù hợp, hoặc query aggregates theo employee IDs rồi join trong memory. Inspect generated SQL và execution plan thay vì giả định một LINQ expression luôn tối ưu.

---

### High — Cancellation không được propagate tới phần external I/O

**Vấn đề:**  
HR client dùng:

```csharp
CancellationToken.None
```

**Tại sao xảy ra:**  
Request cancellation chỉ có tác dụng với operations nhận và honor token.

**Ảnh hưởng production:**  
Client disconnect nhưng server vẫn tiếp tục hàng trăm outbound calls, làm tốn quota/capacity và kéo dài resource lifetime.

**Cách sửa:**  
Truyền request token tới outbound calls. Nếu cần timeout riêng cho dependency, link timeout token với request token. Cancellation là cooperative; nếu provider đã thực hiện side effect thì token không đảo ngược được side effect, nhưng ở đây request là read nên semantics đơn giản hơn.

---

### High — Một dependency failure làm fail toàn bộ aggregation

**Vấn đề:**  
Nếu một task fault, `await Task.WhenAll(tasks)` sẽ fault và action không trả partial dashboard theo product requirement.

**Tại sao xảy ra:**  
Failure policy không được biểu diễn trong từng item; exceptions được để bubble lên aggregate boundary.

**Ảnh hưởng production:**  
Một employee/provider timeout có thể biến toàn bộ 200-item dashboard thành 500, làm availability phụ thuộc vào worst single HR call.

**Cách sửa:**  
Nếu business cho phép partial result, catch/classify failure per employee, trả status như `Unavailable`/`TimedOut` cho leave balance và vẫn giữ internal data. Không swallow toàn bộ exception; telemetry phải phân biệt partial dependency failure với total request failure.

---

### High — Retry 429 ngay lập tức có thể khuếch đại overload

**Vấn đề:**  
Team muốn retry mọi 429 ngay.

**Tại sao xảy ra:**  
429 là tín hiệu dependency đang giới hạn load. Immediate retry trên hàng trăm concurrent requests tạo thêm traffic đúng lúc provider quá tải.

**Ảnh hưởng production:**  
Retry storm, latency dài hơn và quota exhaustion.

**Cách sửa:**  
Tôn trọng `Retry-After` khi provider có hỗ trợ, dùng bounded retry/backoff/jitter phù hợp và quan trọng hơn là giới hạn concurrency/rate từ đầu. Không retry vô hạn.

---

### Medium — Query ban đầu materialize entity đầy đủ và tracking có thể không cần thiết

**Vấn đề:**  
Read-only dashboard dùng `ToListAsync` trên entity query mà không cho thấy `AsNoTracking` hay projection.

**Tại sao xảy ra:**  
EF Core có thể track entities và load nhiều columns hơn response cần.

**Ảnh hưởng production:**  
Allocation/change-tracker overhead không cần thiết, đặc biệt khi endpoint có traffic cao.

**Cách sửa:**  
Projection đúng columns cần thiết và `AsNoTracking()` khi không update entities. Đây là optimization thứ cấp sau khi sửa concurrency/N+1.

---

### Medium — Không có explicit timeout/failure budget cho external dependency

**Vấn đề:**  
Code chỉ truyền token, không thể hiện timeout budget cho từng HR call hoặc cho toàn aggregation.

**Tại sao xảy ra:**  
Một dependency chậm có thể kéo tail latency của endpoint dù phần lớn items đã sẵn sàng.

**Ảnh hưởng production:**  
p95/p99 cao và resource bị giữ lâu.

**Cách sửa:**  
Đặt timeout dựa trên endpoint SLO và partial-result semantics. Nếu dashboard budget là vài giây, mỗi HR call hoặc cả fan-out cần budget nhỏ hơn tổng request deadline.

---

### Medium — Thiếu telemetry để phân biệt bottleneck và overload source

**Vấn đề:**  
Không có metrics về SQL query count, HR concurrency, 429, timeout, partial items hoặc request cancellation.

**Tại sao xảy ra:**  
Request duration tổng không nói phần nào gây chậm.

**Ảnh hưởng production:**  
Team dễ chữa sai bằng tăng connection pool hoặc retry nhiều hơn.

**Cách sửa:**  
Instrument dependency duration/status, active outbound concurrency, queue/wait time trước semaphore, SQL command count/duration, partial failure count và cancellation reason.

## Phiên bản đề xuất

Một hướng đơn giản là gom dữ liệu SQL trước, sau đó chỉ fan-out phần HR với bounded concurrency.

```csharp
public sealed record EmployeeBaseData(
    Guid Id,
    string DisplayName,
    string ExternalEmployeeId,
    DateTime? LatestWorkDate,
    int PendingApprovals);

public sealed record EmployeeDashboardItem(
    Guid Id,
    string DisplayName,
    DateTime? LatestWorkDate,
    int PendingApprovals,
    decimal? RemainingLeaveDays,
    string LeaveStatus);

[Authorize]
[HttpGet("dashboard/employees")]
public async Task<IActionResult> GetEmployeeDashboard(
    CancellationToken cancellationToken)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    var employees = await _db.Employees
        .AsNoTracking()
        .Where(e => e.TenantId == tenantId && e.IsActive)
        .OrderBy(e => e.Id)
        .Take(200)
        .Select(e => new EmployeeBaseData(
            e.Id,
            e.DisplayName,
            e.ExternalEmployeeId,
            e.Timesheets
                .OrderByDescending(t => t.WorkDate)
                .Select(t => (DateTime?)t.WorkDate)
                .FirstOrDefault(),
            e.Approvals.Count(a => a.Status == ApprovalStatus.Pending)))
        .ToListAsync(cancellationToken);

    var results = new EmployeeDashboardItem[employees.Count];

    await Parallel.ForEachAsync(
        Enumerable.Range(0, employees.Count),
        new ParallelOptions
        {
            MaxDegreeOfParallelism = 8,
            CancellationToken = cancellationToken
        },
        async (index, ct) =>
        {
            var employee = employees[index];

            try
            {
                using var timeoutCts =
                    CancellationTokenSource.CreateLinkedTokenSource(ct);
                timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

                var leave = await _hrClient.GetLeaveBalanceAsync(
                    employee.ExternalEmployeeId,
                    timeoutCts.Token);

                results[index] = new EmployeeDashboardItem(
                    employee.Id,
                    employee.DisplayName,
                    employee.LatestWorkDate,
                    employee.PendingApprovals,
                    leave.RemainingDays,
                    "Available");
            }
            catch (OperationCanceledException) when (!ct.IsCancellationRequested)
            {
                results[index] = new EmployeeDashboardItem(
                    employee.Id,
                    employee.DisplayName,
                    employee.LatestWorkDate,
                    employee.PendingApprovals,
                    null,
                    "TimedOut");
            }
            catch (HrProviderException ex) when (ex.IsTransient)
            {
                results[index] = new EmployeeDashboardItem(
                    employee.Id,
                    employee.DisplayName,
                    employee.LatestWorkDate,
                    employee.PendingApprovals,
                    null,
                    "Unavailable");
            }
        });

    return Ok(results);
}
```

`MaxDegreeOfParallelism = 8` chỉ là ví dụ minh họa, không phải recommendation universal. Giá trị thực tế phải dựa trên provider quota, latency, number of application instances và expected concurrent users. Nếu provider có rate limit toàn cluster, per-request semaphore là chưa đủ; cần rate limiting ở outbound-client/application boundary hoặc coordination phù hợp hơn.

Query projection cũng cần inspect SQL thực tế. Nếu generated query cho correlated subqueries không phù hợp workload, có thể dùng ba set-based queries tuần tự:

1. lấy 200 employee IDs;
2. aggregate latest timesheet theo IDs;
3. aggregate pending approvals theo IDs;

rồi join trong memory. Ba round trips ổn định vẫn tốt hơn 401 round trips.

Tài liệu tham khảo:

- Microsoft Learn — DbContext lifetime, configuration and threading: `https://learn.microsoft.com/ef/core/dbcontext-configuration/`
- Microsoft Learn — EF Core asynchronous programming: `https://learn.microsoft.com/ef/core/miscellaneous/async`

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách hai resource domains:

- SQL work dùng một `DbContext` theo cách tuần tự/set-based;
- external HR work dùng parallelism có giới hạn.

Điều này tránh dùng `DbContext` concurrent và đồng thời tránh burst 200 calls/request. Partial-result requirement được thể hiện trong result contract thay vì để một exception phá toàn response.

Nếu business yêu cầu leave balance phải tuyệt đối đầy đủ, failure policy sẽ khác: endpoint có thể fail hoặc chuyển sang asynchronous aggregation/cache. Nhưng không được silently giả định partial result luôn chấp nhận được.

## Trade-offs

- Bounded concurrency làm request có thể chậm hơn unbounded `Task.WhenAll` khi dependency rất khỏe, nhưng đổi lại latency/capacity dễ dự đoán hơn.
- Partial result tăng complexity trong API contract và frontend phải hiển thị trạng thái unavailable rõ ràng.
- Set-based LINQ query có thể tạo SQL phức tạp; cần xem generated SQL/execution plan thay vì tối ưu chỉ ở C#.
- Caching leave balance có thể giảm external traffic nếu business chấp nhận stale data, nhưng cache invalidation/freshness phải được định nghĩa; không nên thêm Redis chỉ vì endpoint chậm.

## Cách kiểm thử

1. **Concurrency test:** 200 employees, verify không có concurrent-use exception của cùng `DbContext`; instrument query count để bảo đảm không quay lại N+1.
2. **Load test:** nhiều concurrent dashboard requests qua nhiều application instances; đo HR active calls, 429 rate, p95/p99 và SQL connection usage.
3. **Failure-path test:** HR provider trả 429/500/timeout cho một subset employees; verify partial result đúng contract và không fail toàn response nếu đó là requirement.
4. **Cancellation test:** abort request giữa fan-out; verify pending outbound work nhận cancellation và active call count giảm.
5. **Database test:** inspect generated SQL/execution plan với realistic cardinality và index data distribution.

# Code Review Challenge 2 — API phân trang PostgreSQL chạy ổn ở page đầu nhưng page 50.000 rất chậm và còn có thể lặp/mất record

**Chủ đề:** PostgreSQL, SQL, REST API pagination, `LIMIT/OFFSET`, deterministic ordering, keyset pagination, composite index, query planning, consistency, performance observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một event-management platform có API list audit events. Dữ liệu được lưu trong PostgreSQL.

Bảng rút gọn:

```sql
CREATE TABLE audit_events (
    id uuid PRIMARY KEY,
    tenant_id uuid NOT NULL,
    event_type text NOT NULL,
    actor_name text NOT NULL,
    created_at timestamptz NOT NULL,
    payload jsonb NOT NULL
);

CREATE INDEX ix_audit_events_tenant
    ON audit_events (tenant_id);

CREATE INDEX ix_audit_events_created_at
    ON audit_events (created_at DESC);
```

API hỗ trợ:

- filter bắt buộc theo `tenant_id`;
- filter optional theo `event_type`;
- sort newest-first;
- page size tối đa 100;
- UI ban đầu dùng numbered pages;
- table đã có khoảng 120 triệu rows, một tenant lớn có hơn 15 triệu rows;
- audit data vẫn được insert liên tục trong lúc user browse;
- payload có thể khá lớn;
- phần lớn users chỉ xem vài page đầu, nhưng export/support tooling đôi lúc nhảy tới page rất sâu;
- endpoint p95 page đầu khoảng 80–150 ms nhưng page sâu có thể mất nhiều giây;
- CPU database tăng khi nhiều support users mở page sâu;
- đôi khi user thấy một event lặp lại giữa hai pages hoặc một event “biến mất” khi dữ liệu mới được insert trong lúc đang browse.

Query hiện tại:

## Đoạn code cần review

```sql
SELECT
    id,
    tenant_id,
    event_type,
    actor_name,
    created_at,
    payload
FROM audit_events
WHERE tenant_id = :tenant_id
  AND (:event_type IS NULL OR event_type = :event_type)
ORDER BY created_at DESC
LIMIT :page_size
OFFSET (:page_number - 1) * :page_size;
```

Một endpoint khác chạy thêm query sau để trả `totalPages` cho mọi request:

```sql
SELECT COUNT(*)
FROM audit_events
WHERE tenant_id = :tenant_id
  AND (:event_type IS NULL OR event_type = :event_type);
```

Team đề xuất:

- tăng `work_mem` để query page sâu nhanh hơn;
- thêm Redis cache cho mọi page;
- giữ `OFFSET` vì frontend đã dùng page numbers;
- thêm index riêng cho mọi combination của filters;
- chưa chạy `EXPLAIN (ANALYZE, BUFFERS)` trên representative tenant;
- chưa đo rows scanned/skipped hoặc cost của `COUNT(*)`.

## Nhiệm vụ của ứng viên

Hãy review query và API design theo góc nhìn production và:

1. xác định các vấn đề correctness, performance và pagination consistency;
2. giải thích vì sao `OFFSET` lớn vẫn tốn work dù chỉ trả 100 rows;
3. chỉ ra vì sao `ORDER BY created_at DESC` chưa tạo total deterministic order;
4. phân tích việc inserts mới có thể làm numbered offset pages bị shift;
5. đánh giá indexes hiện tại so với filter + ordering pattern;
6. đề xuất keyset/cursor pagination hoặc một design thay thế phù hợp;
7. phân tích trade-off giữa cursor pagination và requirement “jump to page 50.000”;
8. đề xuất cách đo bằng execution plan, buffers, latency và rows processed trước khi tối ưu.

## Câu hỏi gợi mở

1. Database phải làm gì với 4.999.900 rows đứng trước 100 rows cần trả ở page 50.000?
2. Nếu hai events có cùng `created_at`, database có đảm bảo thứ tự giữa chúng ổn định giữa các requests không?
3. Nếu 50 events mới được insert trước khi user load page tiếp theo, OFFSET cũ còn trỏ tới cùng logical boundary không?
4. Index `(tenant_id)` và index `(created_at DESC)` riêng lẻ có tương đương một index phù hợp trực tiếp với `WHERE tenant_id = ... ORDER BY created_at DESC` không?
5. `COUNT(*)` chính xác trên hàng triệu rows có thật sự cần ở mọi page request không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **deep OFFSET + mutable ordered dataset**: vừa expensive, vừa không giữ ổn định logical boundary giữa pages.

### Gợi ý 2

Hãy nghĩ tới một cursor đại diện cho **last seen sort key** thay vì “skip N rows”. Muốn cursor đúng thì ordering phải unique và index phải phục vụ access pattern đó.

## Kết quả code review tham khảo

### High — Deep `OFFSET` buộc database xử lý các rows bị bỏ qua

**Vấn đề:**  
Page 50.000 với page size 100 tạo offset gần 5 triệu rows.

**Tại sao xảy ra:**  
`OFFSET` không biến các rows trước boundary thành miễn phí. PostgreSQL vẫn phải compute/scan theo execution plan rồi bỏ qua chúng trước khi trả phần `LIMIT`.

**Ảnh hưởng production:**  
Latency tăng theo page depth, buffer reads/CPU tăng và nhiều deep-page requests có thể gây noisy-neighbor effect.

**Cách sửa:**  
Với browsing tuần tự, dùng keyset/cursor pagination dựa trên sort key ổn định. Nếu business bắt buộc random access tới arbitrary page number, cần nhận rằng keyset không hỗ trợ jump trực tiếp theo ordinal; cân nhắc workflow khác như time-range navigation, search/filter, asynchronous export hoặc materialized snapshot tùy requirement.

Tài liệu tham khảo: PostgreSQL Documentation — `LIMIT` and `OFFSET`: `https://www.postgresql.org/docs/current/queries-limit.html`

---

### High — Ordering không deterministic khi nhiều rows có cùng `created_at`

**Vấn đề:**  
Query chỉ:

```sql
ORDER BY created_at DESC
```

**Tại sao xảy ra:**  
`created_at` không unique. Khi nhiều rows có cùng timestamp, thứ tự tương đối giữa chúng không được contract hiện tại xác định.

**Ảnh hưởng production:**  
Rows có thể xuất hiện lại hoặc bị bỏ qua giữa pages, đặc biệt khi execution plan/data state thay đổi.

**Cách sửa:**  
Dùng total order, ví dụ:

```sql
ORDER BY created_at DESC, id DESC
```

Cursor phải chứa cả hai values.

---

### High — Offset pagination không ổn định trên dataset đang được insert

**Vấn đề:**  
User load page 1, sau đó rows mới được insert ở đầu result set trước khi user load page 2.

**Tại sao xảy ra:**  
`OFFSET 100` ở request thứ hai tính trên một dataset đã shift. Nó không đại diện cho “sau row cuối cùng user vừa xem”.

**Ảnh hưởng production:**  
Duplicate/missing-visible rows trong browsing session dù từng query riêng lẻ hoàn toàn đúng SQL semantics.

**Cách sửa:**  
Keyset pagination dùng cursor từ row cuối cùng đã thấy. Nếu audit browsing yêu cầu một snapshot tuyệt đối cố định qua nhiều phút, cần snapshot/version boundary riêng; keyset chỉ giúp giữ boundary theo sort key, không tự biến nhiều HTTP requests thành một database transaction snapshot dài hạn.

---

### High — Index hiện tại chưa trực tiếp phục vụ tenant-filtered newest-first access pattern

**Vấn đề:**  
Có index riêng trên `tenant_id` và riêng trên `created_at`, nhưng workload chính kết hợp cả filter và order.

**Tại sao xảy ra:**  
Optimizer có thể dùng bitmap/index scan/sort tùy statistics và cardinality, nhưng hai single-column indexes không đảm bảo access path tối ưu như một composite index phù hợp query shape.

**Ảnh hưởng production:**  
Có thể đọc/sort nhiều rows hơn cần thiết cho một tenant lớn.

**Cách sửa:**  
Đánh giá composite index theo access pattern, ví dụ:

```sql
CREATE INDEX ix_audit_events_tenant_created_id
    ON audit_events (tenant_id, created_at DESC, id DESC);
```

Nếu `event_type` là filter phổ biến và selective, có thể cần strategy/index khác. Không tạo index cho mọi combination một cách máy móc vì mỗi index tăng storage/write amplification/maintenance cost. Quyết định dựa trên query frequency, selectivity và plans.

---

### Medium — Optional-filter predicate có thể tạo plan không tối ưu cho các parameter distributions khác nhau

**Vấn đề:**  
Pattern:

```sql
(:event_type IS NULL OR event_type = :event_type)
```

trộn hai query shapes: không filter và có filter.

**Tại sao xảy ra:**  
Cardinality/selectivity khác nhau có thể cần access path khác; một generic query shape không phải lúc nào cũng cho plan tốt nhất cho cả hai trường hợp.

**Ảnh hưởng production:**  
Một số tenant/event types có thể dùng plan đọc nhiều rows hơn cần thiết.

**Cách sửa:**  
Đo actual plans cho cả hai paths. Nếu cần, phát SQL shape riêng khi có `event_type`, hoặc dùng index phù hợp workload. Không optimize trước khi có evidence.

---

### Medium — Trả `payload` lớn trong list endpoint có thể tạo I/O không cần thiết

**Vấn đề:**  
Mỗi list row trả toàn bộ `jsonb payload` dù UI có thể chỉ cần metadata.

**Tại sao xảy ra:**  
List API dùng cùng row representation với detail API.

**Ảnh hưởng production:**  
Tăng heap/table page access, database-to-app bytes, serialization và network payload.

**Cách sửa:**  
Projection list chỉ trả fields cần hiển thị. Lấy `payload` qua detail endpoint khi user mở event. Đo trước/sau vì storage layout và payload size distribution ảnh hưởng thực tế.

---

### Medium — Exact `COUNT(*)` trên mỗi request có thể trở thành workload riêng đáng kể

**Vấn đề:**  
Mọi page chạy thêm count trên toàn result set của tenant/filter.

**Tại sao xảy ra:**  
Numbered pagination contract yêu cầu `totalPages`, nhưng exact count trên hàng triệu matching rows có thể tốn đáng kể dù list query đã tối ưu.

**Ảnh hưởng production:**  
Database phải làm thêm work không trực tiếp cần để trả 100 rows; p95 có thể bị chi phối bởi count.

**Cách sửa:**  
Xác minh UX có thật sự cần exact total ở mọi request. Có thể dùng `hasNextPage`, cursor, count theo yêu cầu, cached/approximate count hoặc background summary nếu business chấp nhận. Không đổi semantics mà chưa hỏi requirement.

---

### Medium — Thêm Redis cho mọi page không sửa bản chất pagination

**Vấn đề:**  
Cache page number trên dataset append liên tục làm invalidation rất khó: insert mới ở đầu có thể shift gần như mọi offset page.

**Tại sao xảy ra:**  
Cache đang bọc một unstable ordinal mapping thay vì giảm work tại đúng boundary.

**Ảnh hưởng production:**  
Stale/incorrect-looking pages, cache churn và complexity mà deep query vẫn tồn tại trên cache miss.

**Cách sửa:**  
Sửa query/access pattern trước. Chỉ cache nếu hit ratio/freshness requirement chứng minh giá trị, ưu tiên cache immutable/detail data hoặc stable cursor results khi semantics cho phép.

## Phiên bản đề xuất

Một cursor API có thể dùng `(created_at, id)` làm stable total ordering key.

Page đầu:

```sql
SELECT
    id,
    event_type,
    actor_name,
    created_at
FROM audit_events
WHERE tenant_id = :tenant_id
  AND (:event_type IS NULL OR event_type = :event_type)
ORDER BY created_at DESC, id DESC
LIMIT :page_size_plus_one;
```

Page tiếp theo:

```sql
SELECT
    id,
    event_type,
    actor_name,
    created_at
FROM audit_events
WHERE tenant_id = :tenant_id
  AND (:event_type IS NULL OR event_type = :event_type)
  AND (
        created_at < :cursor_created_at
        OR (created_at = :cursor_created_at AND id < :cursor_id)
      )
ORDER BY created_at DESC, id DESC
LIMIT :page_size_plus_one;
```

Nếu PostgreSQL/query layer hỗ trợ row-value comparison phù hợp với data types/order semantics, condition có thể được biểu diễn gọn hơn, nhưng implementation phải được test với actual plan và ordering contract.

Composite index candidate:

```sql
CREATE INDEX ix_audit_events_tenant_created_id
    ON audit_events (tenant_id, created_at DESC, id DESC);
```

Nếu filter `event_type` xuất hiện thường xuyên và đủ selective, có thể đánh giá thêm:

```sql
CREATE INDEX ix_audit_events_tenant_type_created_id
    ON audit_events (
        tenant_id,
        event_type,
        created_at DESC,
        id DESC
    );
```

Không mặc định giữ cả hai. Dùng `pg_stat_*`, query frequency, index size/write cost và `EXPLAIN (ANALYZE, BUFFERS)` để quyết định.

API response có thể là:

```json
{
  "items": [],
  "nextCursor": "opaque-token",
  "hasNextPage": true
}
```

Cursor nên opaque với client, encode đủ sort/filter context cần thiết và được validate/sign nếu tampering có thể tạo security/correctness issue. Tenant scope phải luôn lấy từ authorized server-side identity/context thay vì tin tenant ID tùy ý trong cursor.

Nếu support thật sự cần “jump tới page 50.000”, tôi không giả định cursor là drop-in replacement. Cần hỏi mục đích:

- nếu họ tìm event theo ngày → thêm time-range/date jump;
- nếu tìm actor/type cụ thể → thêm filters/search;
- nếu cần extract hàng triệu rows → dùng export workflow;
- nếu yêu cầu ordinal page snapshot là bắt buộc → cân nhắc snapshot/materialized result set có lifecycle/cost rõ ràng.

PostgreSQL documentation nêu rằng rows bị `OFFSET` bỏ qua vẫn phải được compute, nên large offset có thể inefficient; đây là lý do architectural requirement “arbitrary deep page” cần được xem lại chứ không chỉ tuning memory.

Tài liệu tham khảo:

- PostgreSQL Documentation — `LIMIT` and `OFFSET`: `https://www.postgresql.org/docs/current/queries-limit.html`

## Giải thích thiết kế sau khi sửa

Keyset pagination không đếm “row thứ N”. Nó nói “hãy lấy các rows đứng sau boundary cuối cùng tôi đã thấy trong total order”. Vì vậy performance thường phụ thuộc nhiều hơn vào index seek/range scan thay vì skip hàng triệu rows.

Thêm `id` vào ordering giải tie. Tuy nhiên cursor browsing trên mutable dataset vẫn cần semantics rõ: keyset giúp tránh shift do rows mới insert ở phía trước boundary, nhưng không bảo đảm snapshot tuyệt đối nếu rows cũ có thể bị update/delete/reorder. Audit table thường append-mostly nên đây có thể là trade-off tốt, nhưng phải xác nhận data mutability.

## Trade-offs

- Cursor pagination không hỗ trợ jump tới arbitrary page number theo cách offset làm.
- Cursor token làm API/client phức tạp hơn một chút và phải version/validate.
- Composite indexes tăng write amplification và storage; audit table write-heavy cần cân bằng read performance.
- Exact total count dễ hiểu với UX nhưng có thể đắt; bỏ count đổi API/UX semantics.
- Nếu dataset nhỏ hoặc chỉ vài pages, offset pagination có thể hoàn toàn đủ; complexity của cursor chỉ đáng dùng khi workload thực sự cần.

## Cách kiểm thử

1. **Database performance test:** chạy page 1, page 1.000 và page 50.000 trên representative tenant; so `EXPLAIN (ANALYZE, BUFFERS)`, rows processed và latency giữa OFFSET và cursor.
2. **Correctness test:** tạo nhiều rows có cùng `created_at`; verify `(created_at, id)` không duplicate/miss khi đi tuần tự qua pages.
3. **Concurrent insert test:** insert rows mới giữa page 1 và page 2; so behavior offset với cursor theo documented semantics.
4. **Filter test:** benchmark cả `event_type = null` và selective/non-selective values; inspect plan choice/index usage.
5. **API test:** invalid/tampered cursor, cursor của tenant khác, changed filter + old cursor và page-size limits phải bị reject đúng contract.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Task.WhenAll` không tự biến shared objects thành thread-safe và không cung cấp bounded concurrency. Với EF Core, cùng một `DbContext` không được dùng cho multiple parallel operations.
- Tối ưu async endpoint phải nhìn cả **fan-out shape**: số SQL round trips, outbound concurrency, dependency quota, cancellation và partial-failure semantics.
- Set-based database work thường đáng ưu tiên trước việc parallelize hàng trăm row-by-row queries.
- PostgreSQL `OFFSET` lớn vẫn phải xử lý các rows bị skip; latency có thể tăng mạnh theo page depth.
- Pagination đúng cần **deterministic total order**. Keyset/cursor pagination dựa trên last-seen boundary thường ổn định hơn OFFSET trên dataset đang insert liên tục.
- Index phải đi theo query access pattern và workload, không phải “thêm index càng nhiều càng tốt”.

## Mẫu tư duy cần nhớ

- **Bound concurrency before scaling it:** async không đồng nghĩa unlimited parallelism.
- **Remove N+1 before tuning pools:** giảm số work trước khi tăng capacity để chịu work không cần thiết.
- **Design failure semantics explicitly:** một dependency lỗi có làm fail toàn response hay chỉ một phần?
- **Stable pagination requires a stable boundary:** total order + cursor thường quan trọng hơn page number ở deep datasets.
- **Measure query plans and rows processed before adding cache/indexes.**
