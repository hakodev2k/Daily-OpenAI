# Code Review Challenge 1 — Phê duyệt chi phí bị thực hiện hai lần

## Bối cảnh

Một nền tảng quản lý chi phí có API phê duyệt yêu cầu thanh toán. Mỗi yêu cầu chỉ được phê duyệt một lần; một khi phê duyệt, hệ thống tạo một bản ghi lệnh chi trả để worker xử lý. API chạy 4 instances, PostgreSQL là source of truth. Trong giờ cao điểm, người quản lý có thể nhấn nút hai lần hoặc hai người phê duyệt gần như đồng thời. Có báo cáo xuất hiện hai lệnh chi trả cho cùng một yêu cầu và một số lệnh được tạo bởi người không thuộc đơn vị quản lý. Đội sản phẩm yêu cầu giữ tương thích với client hiện tại.

Giả định các entity `ExpenseRequest` và `PayoutCommand` có các thuộc tính được dùng bên dưới; `AppDbContext` là EF Core DbContext; `IUserContext` cung cấp user ID và tenant ID đã xác thực.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/expenses")]
[Authorize]
public sealed class ExpensesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IUserContext _user;
    private readonly ILogger<ExpensesController> _log;

    public ExpensesController(
        AppDbContext db, IUserContext user,
        ILogger<ExpensesController> log)
        => (_db, _user, _log) = (db, user, log);

    [HttpPost("{id:guid}/approve")]
    public async Task<IActionResult> Approve(Guid id)
    {
        var request = await _db.ExpenseRequests
            .FirstOrDefaultAsync(x => x.Id == id);

        if (request is null) return NotFound();
        if (request.Status == "Approved") return Ok();

        request.Status = "Approved";
        request.ApprovedBy = _user.UserId;
        request.ApprovedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        var payout = new PayoutCommand
        {
            Id = Guid.NewGuid(),
            ExpenseRequestId = request.Id,
            Amount = request.Amount,
            Status = "Pending"
        };
        _db.PayoutCommands.Add(payout);
        await _db.SaveChangesAsync();

        _log.LogInformation("Approved expense {Id} for {Amount}",
            request.Id, request.Amount);

        return Ok(new { payout.Id });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Thiếu kiểm tra quyền trên từng expense và tenant

**Vấn đề:** `[Authorize]` chỉ yêu cầu người dùng đăng nhập, không xác nhận người đó được phê duyệt expense thuộc tenant, đơn vị và hạn mức tương ứng.  
**Tại sao xảy ra:** Truy vấn bằng `Id` không giới hạn tenant và không áp dụng approval policy.  
**Ảnh hưởng production:** Broken object-level authorization; phê duyệt trái phép, rủi ro mất tiền.  
**Cách sửa:** Query có tenant scope từ identity đáng tin cậy, kiểm tra policy dựa trên expense, role, delegation, limit; trả `Forbid` hoặc `NotFound` theo chính sách chống enumeration. Không tin tenant ID từ request body.

### [Critical] — Race condition tạo nhiều payout

**Vấn đề:** Hai requests có thể cùng thấy `Pending` rồi tạo hai `PayoutCommand`.  
**Tại sao xảy ra:** Read-check-write không atomic, không có concurrency token, conditional update hoặc unique constraint.  
**Ảnh hưởng production:** Thanh toán trùng, khó đối soát.  
**Cách sửa:** Enforce unique index trên `PayoutCommands.ExpenseRequestId`; chuyển trạng thái bằng conditional update và kiểm tra affected rows; hoặc optimistic concurrency token; xử lý conflict thành kết quả idempotent có kiểm soát.

### [High] — Hai lần SaveChanges không có transaction chung

**Vấn đề:** Expense đã `Approved` nhưng tiến trình chết trước khi ghi payout.  
**Tại sao xảy ra:** Hai `SaveChangesAsync` là hai đơn vị commit riêng biệt khi không có transaction bên ngoài.  
**Ảnh hưởng production:** Request bị kẹt ở trạng thái approved nhưng không có lệnh chi.  
**Cách sửa:** Cùng một transaction database cho state transition và payout insert; cân nhắc transactional outbox nếu sau đó cần phát message.

### [High] — Không kiểm tra trạng thái nghiệp vụ hợp lệ

**Vấn đề:** Mọi trạng thái khác `Approved` đều được phê duyệt, kể cả `Rejected`, `Cancelled`, `Paid`.  
**Tại sao xảy ra:** Chỉ có một guard.  
**Ảnh hưởng production:** Phá vỡ state machine và audit.  
**Cách sửa:** Chỉ cho phép transition từ `PendingApproval` theo business rules; conflict trả `409` hoặc trạng thái idempotent phù hợp.

### [High] — Không truyền CancellationToken

**Vấn đề:** Database calls tiếp tục sau khi request bị hủy.  
**Tại sao xảy ra:** Không sử dụng `HttpContext.RequestAborted`.  
**Ảnh hưởng production:** Tăng áp lực tài nguyên và khó quản lý timeout; không đồng nghĩa tự động rollback khi client ngắt kết nối.  
**Cách sửa:** Truyền token tới truy vấn và transaction; sau commit, response có thể thất lạc nên client phải retry an toàn.

### [Medium] — Response không nhất quán khi retry

**Vấn đề:** Lần đầu trả payout ID, lần sau trả `Ok()` rỗng.  
**Tại sao xảy ra:** Không truy xuất payout hiện có cho yêu cầu đã approved.  
**Ảnh hưởng production:** Client không biết kết quả cuối cùng, dễ retry mù.  
**Cách sửa:** Trả cùng resource/result khi đã tồn tại; định nghĩa contract rõ cho retry, conflict và authorization.

### [Medium] — Thiếu audit và correlation

**Vấn đề:** Log chỉ ghi amount và ID, không có outcome, actor, tenant, trace ID hay conflict reason.  
**Tại sao xảy ra:** Telemetry không phản ánh transition và transaction outcome.  
**Ảnh hưởng production:** Khó điều tra thanh toán trùng và truy vết phê duyệt.  
**Cách sửa:** Audit immutable hoặc append-only cho transition; structured logs tránh PII; metric duplicate/conflict và trace DB.

### [Medium] — Chưa có kiểm soát việc thực thi payout downstream

**Vấn đề:** Unique payout command không tự bảo đảm external payment provider không chi hai lần.  
**Tại sao xảy ra:** Worker có thể retry sau timeout không biết kết quả phía provider.  
**Ảnh hưởng production:** Thanh toán trùng dù API đã được sửa.  
**Cách sửa:** Dùng stable idempotency key với provider nếu hỗ trợ, worker idempotent, reconciliation và trạng thái không chắc chắn cần xác minh.

## Phiên bản đề xuất

Ví dụ minh họa dựa trên PostgreSQL và EF Core; tên entity, policy và trạng thái phải được ánh xạ vào domain thực tế. Giả định `PayoutCommands.ExpenseRequestId` có unique index và chỉ một payout cho mỗi expense. `IExpenseApprovalPolicy` kiểm tra quyền đối với expense đã load, bao gồm tenant và hạn mức.

```csharp
[HttpPost("{id:guid}/approve")]
public async Task<IActionResult> Approve(
    Guid id, CancellationToken ct)
{
    var tenantId = _user.TenantId;
    await using var tx = await _db.Database
        .BeginTransactionAsync(ct);

    var expense = await _db.ExpenseRequests
        .SingleOrDefaultAsync(x => x.Id == id &&
            x.TenantId == tenantId, ct);
    if (expense is null) return NotFound();

    if (!await _approvalPolicy.CanApproveAsync(
            _user.UserId, expense, ct))
        return Forbid();

    if (expense.Status == "Approved")
    {
        var existing = await _db.PayoutCommands
            .Where(x => x.ExpenseRequestId == id)
            .Select(x => new { x.Id })
            .SingleOrDefaultAsync(ct);
        if (existing is null)
            return Conflict("Approval requires reconciliation.");
        return Ok(existing);
    }

    if (expense.Status != "PendingApproval")
        return Conflict("Invalid state transition.");

    // Atomic compare-and-set; avoids trusting the earlier read.
    var changed = await _db.ExpenseRequests
        .Where(x => x.Id == id &&
            x.TenantId == tenantId &&
            x.Status == "PendingApproval")
        .ExecuteUpdateAsync(s => s
            .SetProperty(x => x.Status, "Approved")
            .SetProperty(x => x.ApprovedBy, _user.UserId)
            .SetProperty(x => x.ApprovedAt, DateTime.UtcNow), ct);

    if (changed != 1)
        return Conflict("Concurrent state transition.");

    var payout = new PayoutCommand
    {
        Id = Guid.NewGuid(),
        ExpenseRequestId = id,
        Amount = expense.Amount,
        Status = "Pending"
    };
    _db.PayoutCommands.Add(payout);
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return Ok(new { payout.Id });
}
```

**Điều kiện triển khai:** Controller cần inject `IExpenseApprovalPolicy` và `IUserContext`; schema phải có unique index. `ExecuteUpdateAsync` bỏ qua EF change tracker: không được dùng entity `expense` đã load để `SaveChanges` thay đổi trạng thái lần nữa. Trong transaction này, authorization phải được xác thực lại nếu policy phụ thuộc dữ liệu có thể thay đổi đồng thời (ví dụ hạn mức hoặc quyền bị thu hồi); có thể cần khóa, conditional predicate hoặc thiết kế policy/transaction mạnh hơn. Cần bắt và phân loại unique violation, concurrency conflict ở tầng xử lý lỗi; không trả raw database error. Không retry transaction một cách mù nếu có side effect ngoài database. Việc trả `Conflict` trong transaction chưa commit sẽ dispose/rollback.

## Giải thích thiết kế sau khi sửa

Conditional update là điểm tuyến tính hóa cho transition. Transaction kết hợp state transition và payout insert; unique index là tuyến phòng thủ cuối cùng khi có code path khác. Approval policy là domain boundary, không chỉ role check. Nếu worker xử lý payout qua Azure Service Bus, transaction database không bao gồm broker; dùng outbox để publish eventual-consistently và inbox/idempotent consumer. Nếu business cho phép nhiều payout một expense, unique constraint phải đổi sang khóa nghiệp vụ phù hợp.

## Trade-offs

Conditional update giảm nguy cơ lost update nhưng cần xử lý conflict rõ ràng. Transaction giữ lock lâu hơn; tránh gọi external API bên trong. Unique constraint đòi hỏi dọn dữ liệu trùng trước migration. Nếu yêu cầu strict serial ordering giữa approval và policy changes, cần thiết kế isolation/locking cụ thể; không mặc định `ReadCommitted` giải quyết mọi race. Outbox tăng vận hành nhưng cần thiết khi phát sự kiện qua hệ thống khác.

## Cách kiểm thử

1. **Concurrency integration test:** 50 requests đồng thời trên nhiều instances, xác minh đúng một payout và trạng thái hợp lệ.
2. **Security test:** người dùng tenant khác và approver vượt hạn mức không thể phê duyệt.
3. **Failure injection:** lỗi sau transition nhưng trước insert, xác minh transaction rollback.
4. **State-machine test:** `Rejected`, `Cancelled`, `Paid` không thể được phê duyệt lại.
5. **Retry test:** response bị mất sau commit, request lặp trả cùng payout ID; worker/provider không tạo side effect trùng.

## Quan sát trong production

Theo dõi `approval_attempts_total` theo outcome, `approval_conflicts_total`, `payout_duplicate_prevented_total`, transaction duration, deadlock/lock wait, DB constraint violations, số expense approved không có payout, queue backlog và provider reconciliation. Gắn `trace_id`, `tenant_id` đã chuẩn hóa, `expense_id` vào structured logs; không log secrets hoặc thông tin thanh toán nhạy cảm. Alert khi invariant bị vi phạm dù chỉ một trường hợp.

## Câu hỏi phỏng vấn mở rộng

1. Nếu approval phải phát sự kiện sang Azure Service Bus, làm thế nào tránh trạng thái DB commit nhưng message chưa được gửi?
2. Nếu người quản lý bị thu hồi quyền đúng lúc request đang xử lý, bạn định nghĩa và bảo vệ authorization consistency như thế nào?
3. Khi provider timeout sau khi đã nhận lệnh chi, worker phải làm gì trước khi retry?

## Bối cảnh

Một cổng CRM dùng Vue 3 và ASP.NET Core REST API cho phép tìm kiếm khách hàng theo tên, email và tenant. Search endpoint hỗ trợ `q` và trả `CustomerDto[]`. Họ báo kết quả cũ đôi khi ghi đè kết quả mới; UI thỉnh thoảng đứng khi search; dữ liệu khách hàng cũ vẫn hiện sau logout. Lượng truy cập tăng mạnh vào giờ làm việc.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from "vue";

type Customer = {
  id: string;
  name: string;
  email: string;
  notesHtml: string;
};

const query = ref("");
const customers = ref<Customer[]>([]);
const error = ref("");
const loading = ref(false);
const token = ref(localStorage.getItem("access_token") ?? "");

async function searchCustomers() {
  loading.value = true;
  error.value = "";
  try {
    const response = await fetch(
      `/api/customers/search?q=${query.value}`,
      { headers: { Authorization: `Bearer ${token.value}` } }
    );
    const result = await response.json();
    customers.value = result;
  } catch (e) {
    error.value = "Search failed";
  }
  loading.value = false;
}

watch(query, searchCustomers);
onMounted(searchCustomers);
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search customers" />
    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>
    <ul>
      <li v-for="customer in customers" :key="customer.id">
        <strong>{{ customer.name }}</strong>
        <span>{{ customer.email }}</span>
        <div v-html="customer.notesHtml"></div>
      </li>
    </ul>
  </section>
</template>
```

## Kết quả code review tham khảo

### [Critical] — `v-html` với nội dung không được kiểm soát

**Vấn đề:** HTML từ `notesHtml` được render trực tiếp.  
**Tại sao xảy ra:** `v-html` bỏ qua escaping mặc định của interpolation.  
**Ảnh hưởng production:** Stored XSS nếu dữ liệu chứa markup/script nguy hiểm hoặc event handlers; có thể tác động đến phiên đăng nhập và dữ liệu CRM.  
**Cách sửa:** Render plain text bằng `{{ }}`; nếu bắt buộc rich text, sanitize bằng thư viện được duy trì với policy nghiêm ngặt tại boundary phù hợp và áp dụng CSP phòng thủ bổ sung.

### [High] — Out-of-order response ghi đè kết quả mới

**Vấn đề:** Request cũ hoàn thành sau request mới và cập nhật `customers`.  
**Tại sao xảy ra:** `watch` gọi nhiều asynchronous functions không có cancellation hoặc request identity.  
**Ảnh hưởng production:** Kết quả không tương ứng input, có thể dẫn tới thao tác trên bản ghi sai.  
**Cách sửa:** Abort request trước và dùng sequence ID để chỉ response mới nhất được commit.

### [High] — Dữ liệu cũ tồn tại khi account thay đổi

**Vấn đề:** `token` chỉ đọc một lần từ `localStorage`, không phản ứng với logout/login; kết quả đã tải không được clear.  
**Tại sao xảy ra:** State auth không gắn với search lifecycle.  
**Ảnh hưởng production:** Hiển thị dữ liệu từ account trước trên thiết bị dùng chung; token cũ tiếp tục được dùng.  
**Cách sửa:** Dùng auth store reactive, clear data và abort request khi session thay đổi; backend bắt buộc tenant scoping và object authorization. Không coi việc ẩn UI là biện pháp bảo mật server.

### [High] — Không xử lý HTTP error đúng

**Vấn đề:** `fetch` resolve cả 401/403/500; code parse body lỗi như danh sách khách hàng.  
**Tại sao xảy ra:** Không kiểm tra `response.ok`, content type và shape.  
**Ảnh hưởng production:** UI crash hoặc hiển thị sai; lỗi auth bị che giấu.  
**Cách sửa:** Kiểm tra status, xử lý 401/403 theo auth flow, validate payload; phân biệt abort với network failure.

### [Medium] — Request storm khi gõ nhanh

**Vấn đề:** Mỗi thay đổi ký tự gửi một request ngay lập tức.  
**Tại sao xảy ra:** Không debounce hoặc minimum query policy.  
**Ảnh hưởng production:** Tăng load, p95 latency và API cost; cancellation ở browser không bảo đảm server đã dừng query.  
**Cách sửa:** Debounce, minimum length khi hợp nghiệp vụ, pagination/limit phía API, rate limiting phù hợp.

### [Medium] — Loading state bị sai

**Vấn đề:** Request cũ đặt `loading=false` khi request mới vẫn chạy.  
**Tại sao xảy ra:** Boolean chung bị cập nhật từ mọi invocation.  
**Ảnh hưởng production:** UX gây hiểu nhầm, người dùng thao tác khi dữ liệu chưa sẵn sàng.  
**Cách sửa:** Chỉ invocation mới nhất được cập nhật state; dùng `finally` với identity check.

### [Medium] — URL query không encode

**Vấn đề:** Ký tự `&`, `#`, `?` trong search term thay đổi ý nghĩa URL.  
**Tại sao xảy ra:** Nội suy trực tiếp vào query string.  
**Ảnh hưởng production:** Search sai, logs/metrics khó giải thích.  
**Cách sửa:** `URLSearchParams`; giới hạn độ dài và validate input phía server.

## Phiên bản đề xuất

Ví dụ dùng `useAuthStore` là abstraction giả định của ứng dụng, có `sessionVersion` tăng mỗi lần login/logout/switch account, `accessToken` và `isAuthenticated` reactive. Server phải enforce tenant authorization độc lập. DTO trả về không chứa HTML bắt buộc render.

```vue
<script setup lang="ts">
import { ref, watch, onUnmounted } from "vue";
import { useAuthStore } from "@/stores/auth";

type Customer = { id: string; name: string; email: string };
const auth = useAuthStore();
const query = ref("");
const customers = ref<Customer[]>([]);
const loading = ref(false);
const error = ref("");
let controller: AbortController | undefined;
let sequence = 0;
let timer: ReturnType<typeof setTimeout> | undefined;

watch(
  () => [query.value, auth.sessionVersion] as const,
  () => {
    if (timer) clearTimeout(timer);
    controller?.abort();
    const current = ++sequence;
    customers.value = [];
    error.value = "";
    loading.value = false;

    if (!auth.isAuthenticated || !auth.accessToken) return;
    const term = query.value.trim();
    if (term.length < 2) return;
    const session = auth.sessionVersion;

    timer = setTimeout(async () => {
      const request = new AbortController();
      controller = request;
      loading.value = true;
      try {
        const params = new URLSearchParams({ q: term });
        const response = await fetch(
          `/api/customers/search?${params.toString()}`,
          {
            signal: request.signal,
            headers: { Authorization: `Bearer ${auth.accessToken}` }
          }
        );
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const payload: unknown = await response.json();
        if (!Array.isArray(payload)) throw new Error("Invalid response");
        if (current !== sequence ||
            session !== auth.sessionVersion) return;
        customers.value = payload as Customer[];
      } catch (e) {
        if (current === sequence && !request.signal.aborted)
          error.value = "Unable to search customers";
      } finally {
        if (current === sequence) loading.value = false;
      }
    }, 250);
  },
  { immediate: true }
);

onUnmounted(() => {
  if (timer) clearTimeout(timer);
  controller?.abort();
  ++sequence;
});
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search customers" />
    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>
    <ul>
      <li v-for="customer in customers" :key="customer.id">
        <strong>{{ customer.name }}</strong>
        <span>{{ customer.email }}</span>
      </li>
    </ul>
  </section>
</template>
```

**Lưu ý:** Cast `payload as Customer[]` chỉ là TypeScript assertion, không phải runtime schema validation; production nên dùng schema validator hoặc mapping/validation rõ ràng cho từng field. Cần bảo đảm auth store cập nhật `sessionVersion` đúng với mọi thay đổi identity/token có ý nghĩa. Nếu token được refresh mà session không đổi, cần chiến lược retry/refresh tập trung và tránh dùng token cũ trong request đang chờ. Với yêu cầu bảo mật cao, cân nhắc cookie HttpOnly/SameSite và CSRF protection phù hợp thay vì lưu access token trong localStorage.

## Giải thích thiết kế sau khi sửa

`sequence` bảo đảm chỉ request hiện hành được cập nhật state; `AbortController` giảm công việc dư thừa nhưng không thay thế sequence check. Watcher theo auth session khiến logout/switch account xóa ngay kết quả và vô hiệu hóa responses cũ. `URLSearchParams` encode query đúng; debounce giới hạn request storm. Interpolation của Vue escape text mặc định. API vẫn là nơi quyết định user được xem bản ghi nào.

## Trade-offs

Debounce tăng độ trễ trước khi search; 250 ms chỉ là giá trị giả định cần đo UX. Abort không bảo đảm hủy truy vấn SQL đã chạy phía server; backend nên propagate `CancellationToken` và giới hạn query. Xóa kết quả ngay khi gõ tránh stale data nhưng có thể tạo cảm giác nhấp nháy; có thể giữ kết quả cũ với nhãn stale nếu yêu cầu UX cho phép, nhưng phải xóa ngay khi identity đổi. Schema validation và auth store làm tăng code nhưng giảm lỗi integration.

## Cách kiểm thử

1. **Unit test với deferred promises:** request `a` trả sau request `ab`; kết quả cuối vẫn thuộc `ab`.
2. **Component test:** logout/switch account khi request đang chạy, data cũ bị xóa và response cũ không cập nhật.
3. **Security test:** malicious `notesHtml` không thực thi; server từ chối cross-tenant access ngay cả khi sửa client request.
4. **API integration test:** 401/403/500, malformed JSON, network timeout và abort không làm UI hiển thị dữ liệu sai.
5. **Playwright E2E + load test:** gõ nhanh, ký tự đặc biệt, kiểm tra request volume, UI và p95 API latency.

## Quan sát trong production

Thu thập browser request duration, aborted count, HTTP status, search error rate, auth-session transitions (không log token), UI stale-response suppression count và Core Web Vitals nếu liên quan. Phía ASP.NET Core: Application Insights dependency traces, SQL query duration, search request count/user, p95/p99, 401/403, rate limit responses. Dùng correlation ID xuyên browser–API; không log nguyên search query nếu chứa PII.

## Câu hỏi phỏng vấn mở rộng

1. Khi backend search trả dữ liệu phân trang, làm sao chống kết quả page 2 của query cũ trộn với page 1 của query mới?
2. Nếu cần hỗ trợ rich text từ CMS, bạn thiết kế sanitization và CSP ra sao?
3. Nếu app dùng cookie authentication thay vì Bearer token, cần xem xét CSRF và SameSite như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Database invariant cần được bảo vệ ở transaction boundary và bằng constraint, không chỉ bằng `if` trong controller.
- Authentication khác object-level authorization; multi-tenant data cần kiểm tra quyền tại server.
- Async request lifecycle ở browser phải xử lý out-of-order responses, cancellation và thay đổi identity.
- Retry, timeout và partial failure phải được thiết kế cùng idempotency và observability.
- Render untrusted HTML là trust-boundary decision, không phải vấn đề hiển thị đơn thuần.

## Mẫu tư duy cần nhớ

1. Xác định invariant và nơi thực thi invariant trước khi tối ưu code.
2. Giả định concurrent requests và partial failures ngay cả khi demo chạy đúng.
3. Đặt authorization ở boundary sở hữu dữ liệu, không dựa vào UI.
4. Phân biệt cancellation với guarantee rằng side effect chưa xảy ra.
5. Kiểm chứng bằng concurrency tests, failure injection và production telemetry.
