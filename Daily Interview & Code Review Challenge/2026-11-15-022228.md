# Code Review Challenge 1 — Import file làm mất tính nhất quán giữa Blob và database

**Chủ đề:** ASP.NET Core 8, Azure Blob Storage, EF Core, multi-tenant authorization, failure recovery  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35 phút

## Bối cảnh

Ứng dụng quản lý tài liệu nội bộ nhận file từ người dùng, lưu nội dung lên Azure Blob Storage và metadata vào PostgreSQL. API chạy nhiều instance trên Azure App Service. File phải thuộc đúng tenant và người dùng chỉ được truy cập tài liệu mà họ được phép sở hữu. Khi Blob Storage chập chờn hoặc request bị ngắt, hệ thống đôi khi có blob không có metadata; có người báo file cũ bị thay thế. Yêu cầu chưa xác định: file tối đa bao nhiêu MB, có cần antivirus, thời gian giữ bản nháp, và có cho phép tên trùng hay không. Hãy nêu các giả định trước khi kết luận.

## Đoạn code cần review

~~~csharp
app.MapPost("/api/documents/upload", async (
    HttpContext http,
    IFormFile file,
    string tenantId,
    AppDbContext db,
    BlobServiceClient blobs,
    CancellationToken ct) =>
{
    var userId = http.User.FindFirst("sub")?.Value;
    if (userId is null) return Results.Unauthorized();

    var name = file.FileName;
    var key = $"{tenantId}/{name}";
    var container = blobs.GetBlobContainerClient("documents");
    var blob = container.GetBlobClient(key);

    await using (var input = file.OpenReadStream())
    {
        await blob.UploadAsync(input, overwrite: true);
    }

    var entity = new Document
    {
        Id = Guid.NewGuid(),
        TenantId = tenantId,
        OwnerId = userId,
        FileName = name,
        BlobKey = key,
        Size = file.Length,
        CreatedAt = DateTime.UtcNow
    };

    db.Documents.Add(entity);
    await db.SaveChangesAsync(ct);

    return Results.Ok(new { entity.Id, entity.BlobKey });
}).RequireAuthorization();
~~~

## Kết quả code review tham khảo

### [Critical] — Tenant ID lấy trực tiếp từ request

**Vấn đề:** Client điều khiển tenantId mà endpoint không kiểm tra membership/permission.  
**Tại sao xảy ra:** RequireAuthorization chỉ xác thực danh tính, không cấp quyền tenant.  
**Ảnh hưởng production:** Ghi dữ liệu vào tenant khác, phá isolation và làm sai audit.  
**Cách sửa:** Tenant được resolve từ trusted authorization context; kiểm tra policy theo resource và permission upload; không tin claim nếu chưa validate issuer/audience/signature.

### [High] — Blob key dễ va chạm và ghi đè

**Vấn đề:** Key chỉ dựa trên tenantId và tên file, overwrite=true.  
**Tại sao xảy ra:** Nhiều request hợp lệ có thể trùng tên.  
**Ảnh hưởng production:** Mất file trước, metadata trỏ sang nội dung mới.  
**Cách sửa:** Tạo immutable opaque key bằng document ID, không overwrite, lưu tên hiển thị riêng.

### [High] — Dual-write không atomic

**Vấn đề:** Upload Blob thành công rồi SaveChanges thất bại để lại orphan; nếu DB thành công nhưng response mất, client retry tạo bản ghi mới.  
**Tại sao xảy ra:** Hai dịch vụ không có transaction chung.  
**Ảnh hưởng production:** Rò storage, duplicate và trạng thái khó đối soát.  
**Cách sửa:** Metadata Pending trước, upload vào key riêng, xác nhận Ready sau khi upload; background reconciliation, TTL cleanup và idempotency key cho retry.

### [High] — Thiếu giới hạn và kiểm soát file

**Vấn đề:** Không có chính sách size, extension/MIME thực tế, content scanning, quota.  
**Tại sao xảy ra:** Tin file do client cung cấp.  
**Ảnh hưởng production:** DoS, chi phí storage, phát tán nội dung độc hại nếu phục vụ trực tiếp.  
**Cách sửa:** Request size limits tại proxy và app, quota tenant, kiểm tra nội dung, quarantine và malware scanning trước khi Ready.

### [Medium] — Cancellation và timeout không nhất quán

**Vấn đề:** Blob upload không nhận ct, trong khi database có.  
**Tại sao xảy ra:** SDK call bỏ qua request cancellation.  
**Ảnh hưởng production:** Tiếp tục upload khi client đã hủy, chiếm tài nguyên.  
**Cách sửa:** Truyền ct vào thao tác upload; phân biệt hủy request và cleanup bắt buộc bằng worker độc lập.

### [Medium] — Tên file chưa được chuẩn hóa để hiển thị

**Vấn đề:** file.FileName do client cung cấp và được đưa vào storage key/metadata.  
**Tại sao xảy ra:** Không tách display name khỏi identifier.  
**Ảnh hưởng production:** Tên khó kiểm soát, ký tự đặc biệt, nguy cơ lỗi khi downstream hiển thị không encode.  
**Cách sửa:** Chỉ lưu basename đã validate làm display name, HTML encode khi render; storage key không phụ thuộc tên file.

### [Medium] — Không có trạng thái xử lý và telemetry

**Vấn đề:** Không phân biệt pending, scanned, ready, failed.  
**Tại sao xảy ra:** Mọi upload đều được coi là hoàn tất sau SaveChanges.  
**Ảnh hưởng production:** Người dùng tải file chưa được kiểm duyệt, sự cố không truy vết được.  
**Cách sửa:** State machine, correlation ID, retry counter, reconciliation metrics và alert.

## Phiên bản đề xuất

Đây là skeleton minh họa; các interface bảo mật, scanning và repository cần implementation cụ thể. Phần cleanup và scanning chạy qua worker riêng, không coi skeleton là giải pháp production hoàn chỉnh.

~~~csharp
app.MapPost("/api/documents/upload", async (
    HttpContext http, IFormFile file,
    ITenantAccess access, AppDbContext db,
    BlobServiceClient storage, CancellationToken ct) =>
{
    var userId = http.User.FindFirst("sub")?.Value;
    if (string.IsNullOrWhiteSpace(userId))
        return Results.Unauthorized();

    var tenant = await access.ResolveWritableTenantAsync(http.User, ct);
    if (tenant is null) return Results.Forbid();
    if (file.Length is <= 0 or > 20 * 1024 * 1024)
        return Results.BadRequest("Invalid file size");

    var id = Guid.NewGuid();
    var key = $"{tenant.Id}/{id:N}";
    var displayName = Path.GetFileName(file.FileName);
    if (string.IsNullOrWhiteSpace(displayName))
        return Results.BadRequest("Invalid filename");

    var document = new Document
    {
        Id = id, TenantId = tenant.Id, OwnerId = userId,
        FileName = displayName, BlobKey = key,
        Size = file.Length, Status = DocumentStatus.Pending,
        CreatedAt = DateTime.UtcNow
    };
    db.Documents.Add(document);
    await db.SaveChangesAsync(ct);

    try
    {
        var blob = storage.GetBlobContainerClient("quarantine")
                          .GetBlobClient(key);
        await using var stream = file.OpenReadStream();
        await blob.UploadAsync(stream,
            new BlobUploadOptions
            {
                Conditions = new BlobRequestConditions
                {
                    IfNoneMatch = ETag.All
                }
            }, ct);
        document.Status = DocumentStatus.Scanning;
        await db.SaveChangesAsync(ct);
        return Results.Accepted($"/api/documents/{id}", new { id });
    }
    catch (Exception) when (!ct.IsCancellationRequested)
    {
        document.Status = DocumentStatus.Failed;
        await db.SaveChangesAsync(CancellationToken.None);
        throw;
    }
}).RequireAuthorization();
~~~

**Giới hạn của skeleton:** Không dùng CancellationToken.None không giới hạn trong production; thao tác ghi trạng thái thất bại cũng có thể lỗi và phải được reconciliation xử lý. Cần validate file type bằng signature, malware scan trước Ready, download authorization, quota, idempotency key với unique constraint, chống concurrent retries, worker quét Pending/Scanning/Failed và lifecycle cleanup. Đảm bảo xử lý lỗi ở worker bằng backoff và bounded retries. Khi streaming trực tiếp từ request cần xem xét giới hạn multipart buffering của IFormFile; với file lớn nên cân nhắc direct-to-Blob upload qua SAS giới hạn quyền/thời gian và quy trình finalize có xác thực.

## Giải thích thiết kế sau khi sửa

Opaque key bảo vệ dữ liệu trước collision; Pending/Scanning làm rõ vòng đời; quarantine tránh phân phối nội dung chưa kiểm duyệt. Reconciliation giải quyết trạng thái bị kẹt khi process chết giữa hai lần ghi. Authorization là yêu cầu độc lập với authentication.

## Trade-offs

Thêm DB writes, worker và state machine tăng chi phí vận hành nhưng đổi lại khả năng khôi phục. Direct upload giảm tải App Service nhưng tăng độ phức tạp xác nhận hoàn tất, giới hạn quyền SAS và kiểm tra nội dung. Nếu file rất nhỏ, lưu DB có thể đơn giản hơn nhưng cần đo chi phí, giới hạn và backup.

## Cách kiểm thử

1. **Security integration:** Người dùng tenant A không thể ghi hoặc đọc tài liệu tenant B.
2. **Concurrency:** 50 upload trùng tên không ghi đè nhau; retry cùng idempotency key chỉ tạo một logical document.
3. **Failure injection:** Upload xong rồi DB lỗi, worker phát hiện và xử lý orphan/stale status.
4. **Security:** File vượt quota, MIME giả và nội dung độc hại không được Ready.
5. **E2E:** Client ngắt kết nối, sau đó retry và kiểm tra trạng thái nhất quán.

## Quan sát trong production

Structured logs có documentId, tenantId dạng đã kiểm soát, operationId, status transition; không log nội dung file hoặc SAS. Metrics: pending age, orphan count, scan latency, upload failures theo dependency, Blob 409/429/5xx, storage growth, API p95, DB errors. Trace từ request tới Blob và DB; alert khi Pending quá SLA hoặc quarantine tăng bất thường.

1. Khi nào nên dùng SAS direct upload thay vì proxy qua backend?
2. Nếu scanner unavailable 30 phút, nên fail-open hay fail-closed và tại sao?
3. Bạn thiết kế reconciliation để không xóa nhầm upload đang chạy như thế nào?

## Đoạn code cần review

~~~tsx
type Product = { id: string; name: string; price: number };
type SearchResult = { items: Product[]; total: number };

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [products, setProducts] = useState<Product[]>([]);
  const [total, setTotal] = useState(0);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  useEffect(() => {
    setLoading(true);
    setError("");
    const url = "/api/products/search?q=" + query +
      "&category=" + category + "&page=" + page;
    fetch(url)
      .then(response => response.json())
      .then((result: SearchResult) => {
        setProducts(result.items);
        setTotal(result.total);
      })
      .catch(() => setError("Search failed"))
      .finally(() => setLoading(false));
  }, [query, category, page]);

  return <section>
    <input value={query}
      onChange={e => setQuery(e.target.value)} />
    <select value={category}
      onChange={e => setCategory(e.target.value)}>
      <option value="all">All</option>
      <option value="books">Books</option>
      <option value="games">Games</option>
    </select>
    {loading && <p>Loading...</p>}
    {error && <p role="alert">{error}</p>}
    <ul>{products.map(p => <li key={p.id}>
      {p.name}: {p.price}
    </li>)}</ul>
    <button disabled={page <= 1}
      onClick={() => setPage(page - 1)}>Previous</button>
    <button disabled={page * 20 >= total}
      onClick={() => setPage(page + 1)}>Next</button>
  </section>;
}
~~~

## Kết quả code review tham khảo

### [High] — Stale response ghi đè kết quả mới

**Vấn đề:** Request cũ hoàn thành sau request mới và setProducts.  
**Tại sao xảy ra:** Promise không đảm bảo completion order.  
**Ảnh hưởng production:** UI hiển thị catalog không khớp từ khóa/filter.  
**Cách sửa:** Cleanup abort request cũ và guard kết quả trước khi set state.

### [High] — HTTP errors bị coi là dữ liệu hợp lệ

**Vấn đề:** fetch resolve khi HTTP 4xx/5xx; response.json() không kiểm tra response.ok.  
**Tại sao xảy ra:** fetch chỉ reject cho một số lỗi network/abort, không tự reject theo HTTP status.  
**Ảnh hưởng production:** Kết quả undefined, UI lỗi ngầm hoặc hiện dữ liệu cũ.  
**Cách sửa:** Kiểm tra response.ok, validate response schema nếu API không đáng tin cậy.

### [Medium] — Không debounce

**Vấn đề:** Mỗi keystroke tạo request.  
**Tại sao xảy ra:** Effect phụ thuộc query trực tiếp.  
**Ảnh hưởng production:** API load cao, rate limit, trải nghiệm kém.  
**Cách sửa:** Debounce 250–400ms tùy UX đo thực tế.

### [Medium] — Pagination không reset khi đổi filter

**Vấn đề:** page giữ giá trị cũ sau khi query/category thay đổi.  
**Tại sao xảy ra:** State transitions không phối hợp.  
**Ảnh hưởng production:** Empty page dù có kết quả, người dùng tưởng không có sản phẩm.  
**Cách sửa:** Reset page về 1 trong cùng event thay đổi filter.

### [Medium] — Loading và error state không gắn với request hiện hành

**Vấn đề:** Request cũ có thể setLoading(false) khi request mới đang chạy; error cũ có thể xuất hiện.  
**Tại sao xảy ra:** Không cleanup và guard.  
**Ảnh hưởng production:** Spinner sai, thông báo lỗi sai ngữ cảnh.  
**Cách sửa:** Abort + active guard và chỉ update khi effect còn active.

### [Medium] — URL không encode tham số

**Vấn đề:** Query chứa &, #, dấu + hoặc Unicode có thể làm sai tham số.  
**Tại sao xảy ra:** Nối string thủ công.  
**Ảnh hưởng production:** Search không chính xác, log khó đối soát.  
**Cách sửa:** URLSearchParams.

### [Low] — Điều hướng trang có thể hiển thị stale content

**Vấn đề:** Dữ liệu trang cũ vẫn hiện trong lúc tải trang mới, không có nhãn trạng thái rõ ràng.  
**Tại sao xảy ra:** Không phân biệt previous data với current query.  
**Ảnh hưởng production:** Người dùng thao tác nhầm sản phẩm.  
**Cách sửa:** Clear data khi đổi key hoặc đánh dấu stale, tùy UX.

## Phiên bản đề xuất

~~~tsx
import { useEffect, useState } from "react";

type Product = { id: string; name: string; price: number };
type SearchResult = { items: Product[]; total: number };

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [debounced, setDebounced] = useState("");
  const [category, setCategory] = useState("all");
  const [page, setPage] = useState(1);
  const [result, setResult] = useState<SearchResult>({ items: [], total: 0 });
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(query), 300);
    return () => clearTimeout(timer);
  }, [query]);

  useEffect(() => {
    const controller = new AbortController();
    let active = true;
    const params = new URLSearchParams({
      q: debounced, category, page: String(page)
    });
    setLoading(true);
    setError("");
    setResult({ items: [], total: 0 });

    async function load() {
      try {
        const response = await fetch(
          "/api/products/search?" + params.toString(),
          { signal: controller.signal }
        );
        if (!response.ok) throw new Error("HTTP " + response.status);
        const data = (await response.json()) as SearchResult;
        if (active) setResult(data);
      } catch (e) {
        if (active && !controller.signal.aborted)
          setError("Search failed");
      } finally {
        if (active) setLoading(false);
      }
    }
    void load();
    return () => { active = false; controller.abort(); };
  }, [debounced, category, page]);

  const changeQuery = (value: string) => {
    setQuery(value);
    setPage(1);
  };
  const changeCategory = (value: string) => {
    setCategory(value);
    setPage(1);
  };

  return <section>
    <input aria-label="Search products" value={query}
      onChange={e => changeQuery(e.target.value)} />
    <select aria-label="Category" value={category}
      onChange={e => changeCategory(e.target.value)}>
      <option value="all">All</option>
      <option value="books">Books</option>
      <option value="games">Games</option>
    </select>
    {loading && <p role="status">Loading...</p>}
    {error && <p role="alert">{error}</p>}
    {!loading && !error && <ul>{result.items.map(p =>
      <li key={p.id}>{p.name}: {p.price}</li>)}</ul>}
    <button disabled={loading || page <= 1}
      onClick={() => setPage(p => Math.max(1, p - 1))}>Previous</button>
    <button disabled={loading || page * 20 >= result.total}
      onClick={() => setPage(p => p + 1)}>Next</button>
  </section>;
}
~~~

**Lưu ý:** Bản sửa vẫn có một UX edge case: khi query mới đang debounce, effect của query cũ có thể tạm hiển thị kết quả cũ. Nếu yêu cầu tuyệt đối không hiển thị kết quả không khớp input hiện tại, cần key kết quả theo raw query hoặc chuyển loading sang trạng thái pending ngay khi input thay đổi; chỉ render dữ liệu khi key của response khớp filter hiện tại. Cần kiểm tra schema response ở runtime nếu backend có thể trả dữ liệu không hợp lệ. Phân trang giả định page size 20 được đồng bộ với API; tốt hơn lấy hasNext/total/pageSize từ contract. Abort chỉ hạn chế client processing, không đảm bảo backend ngừng xử lý.

## Giải thích thiết kế sau khi sửa

Effect cleanup ngăn request cũ cập nhật state sau khi dependencies thay đổi. Debounce giảm request không cần thiết; URLSearchParams đảm bảo encoding. Reset page tránh truy vấn sai ngữ cảnh. Functional setPage tránh dùng closure state cũ.

## Trade-offs

Debounce tăng latency cảm nhận với người gõ xong; cần đo. Abort không thay thế server-side cancellation/rate limit. TanStack Query hoặc thư viện tương đương có thể quản lý cache, dedup và stale states, nhưng thêm dependency không cần thiết cho màn hình nhỏ. Cache cần key đầy đủ theo query/category/page và TTL hợp lý.

## Cách kiểm thử

1. **Component test:** Mock response A chậm hơn B, xác nhận chỉ B được render.
2. **Failure-path:** 401/429/500 và malformed JSON hiển thị error, không giữ spinner vô hạn.
3. **Interaction test:** Đổi query/category ở page 8 đưa về page 1.
4. **Playwright E2E:** Gõ nhanh, thay filter và kiểm tra Network request count, URL encoding và state cuối.
5. **Load/API test:** So sánh request rate trước/sau debounce, kiểm tra server rate limiting.

## Quan sát trong production

Browser RUM: search latency, abandoned searches, error rate theo HTTP status, request count per interaction; backend: p95/p99, 429, query latency, DB CPU, correlation IDs và cancellation telemetry. Không log raw query nếu chứa dữ liệu nhạy cảm; dùng sampling và aggregation.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào nên giữ previous data thay vì clear ngay?
2. Nếu backend trả cursor thay vì page number, bạn thay đổi UI và cache key ra sao?
3. Làm thế nào tránh duplicate request trong React Strict Mode development mà không che giấu side effects?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication không thay thế resource-level authorization.
- Dual-write giữa database và object storage cần lifecycle, reconciliation và idempotency, không thể giả định atomicity.
- Promise completion order khác request initiation order; UI phải loại bỏ stale results.
- HTTP errors, cancellation và retries cần được thiết kế rõ ràng từ client đến server.
- Kiểm chứng bằng failure injection, concurrency tests và production telemetry thay vì chỉ kiểm tra happy path.

## Mẫu tư duy cần nhớ

1. Xác định trust boundary trước khi dùng dữ liệu client.
2. Liệt kê từng failure window giữa các dependency.
3. Thiết kế retry cùng idempotency và reconciliation.
4. Gắn state update với request identity.
5. Đo và quan sát failure path trước khi tuyên bố đã sửa xong.
