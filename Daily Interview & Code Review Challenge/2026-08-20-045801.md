# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong tình huống production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, query execution, change tracking, SQL, performance, observability

## Bối cảnh

Một ASP.NET Core API đọc danh sách 2.000–10.000 nhân viên, sau đó áp dụng một số rule và trả DTO. Sau một đợt refactor, latency P95 tăng từ khoảng 300 ms lên vài giây, SQL Server ghi nhận nhiều query giống nhau, memory của pod tăng rõ rệt. Developer nói: “`IQueryable` chỉ là collection nên enumerate vài lần không sao; EF Core cũng tự cache kết quả.” Endpoint chỉ đọc dữ liệu nhưng không dùng `AsNoTracking()`.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong từ lúc xây dựng `IQueryable` đến khi enumerate; vì sao cùng một query có thể chạy nhiều lần; tracking ảnh hưởng gì; misconception nào đang tồn tại; rủi ro production là gì; và bạn sẽ chứng minh từng giả thuyết bằng cách nào trước khi sửa?

## Câu hỏi làm rõ nên cân nhắc

- Query được enumerate bao nhiêu lần và ở đâu (`ToListAsync`, `Count`, `Any`, `foreach`)?
- Có navigation property/lazy loading hoặc client-side processing không?
- Endpoint có cần update entity sau khi đọc không?
- SQL thực tế, số row và kích thước entity là bao nhiêu?
- Regression xuất hiện chính xác từ commit/deployment nào?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt “xây expression tree” và “thực thi query”.
- **Gợi ý 2:** Xem deferred execution, materialization, tracking/identity resolution và navigation loading.
- **Gợi ý 3:** Đếm số round-trip DB bằng SQL/logging/tracing rồi so sánh tracked query với no-tracking và materialize-once.

## Cấu trúc trả lời đề xuất

1. Làm rõ luồng enumerate.
2. Mô tả lifecycle của `IQueryable`.
3. Phân tích tracking và materialization.
4. Xác định các nguồn query lặp/N+1.
5. Đưa ra phương án sửa theo bằng chứng.
6. So sánh trade-off.
7. Test tải và correctness.
8. Theo dõi query count, latency và allocation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` giữ biểu thức; query thường được dịch/thực thi khi terminal operation/enumeration xảy ra.
- Enumerate lại có thể tạo một lần thực thi DB khác; không nên giả định EF Core cache result set.
- Tracking query đưa entity vào change tracker; read-only workload có thể chịu thêm CPU/memory.
- Materialize một lần khi cần reuse; projection chỉ lấy cột cần thiết.
- Phải đo SQL/query count trước và sau thay đổi.

### Điểm cộng

- Phân biệt `AsNoTracking()` với `AsNoTrackingWithIdentityResolution()` theo nhu cầu.
- Nhắc tới N+1/navigation loading, query splitting/join explosion như các giả thuyết riêng cần kiểm chứng.
- Dùng `ToQueryString()`, EF Core command logs, OpenTelemetry/APM và DB execution plan.

### Nâng cao

- Phân tích compiled query/query-plan cache khác hoàn toàn result caching.
- Đánh giá allocation/change-tracker growth bằng `dotnet-counters`, profiler hoặc trace.
- Đề xuất benchmark với dataset đại diện thay vì micro-optimization mù.

## Hướng giải quyết tham khảo

**Giả định:** endpoint thực sự read-only và query bị enumerate nhiều lần sau refactor.

EF Core xây expression tree khi các operator LINQ tiếp tục nối vào `IQueryable`. Khi gọi terminal operation như `ToListAsync`, `FirstAsync`, `CountAsync` hoặc enumerate, provider dịch biểu thức sang SQL và thực hiện truy vấn. Nếu cùng `IQueryable` được enumerate lại, không có cơ sở để coi kết quả trước đó là cache dữ liệu ứng dụng; một truy vấn khác có thể được gửi xuống DB.

Với tracking query, EF Core theo dõi entity được materialize trong `DbContext`. Điều này hữu ích khi entity sẽ được sửa rồi `SaveChanges`, nhưng endpoint chỉ đọc có thể tránh chi phí đó bằng `AsNoTracking()` và tốt hơn nữa là project thẳng sang DTO. Nếu logic cần nhiều phép tính trên cùng snapshot, materialize đúng một lần rồi reuse collection; nếu phép tính có thể thực hiện hiệu quả ở DB, giữ chúng trong SQL thay vì kéo toàn bộ dữ liệu về memory.

Không kết luận ngay tracking là root cause. Thu thập command count, duration, generated SQL, execution plan, rows returned và allocation. Kiểm tra lazy loading/N+1, include quá lớn, thiếu index hoặc thay đổi cardinality. Sau fix, chạy integration/load test và so P50/P95/P99, DB duration, query/request, allocated bytes và GC.

**Trade-off:** no-tracking không phù hợp nếu cùng entity cần được sửa trong context. Materialize sớm giảm query lặp nhưng có thể tăng memory nếu result set lớn. Projection thường tốt cho read API nhưng cần thiết kế DTO/query rõ ràng.

**Điều kiện đổi khuyến nghị:** nếu endpoint cần cập nhật aggregate trong cùng unit of work, tracking có thể hợp lý; nếu dữ liệu quá lớn, pagination/streaming hoặc query-side aggregation quan trọng hơn materialize toàn bộ.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ không giả định EF Core chậm vì tracking. Tôi muốn xác nhận query đang được enumerate mấy lần và SQL thực tế. `IQueryable` chủ yếu biểu diễn query; khi terminal operation hoặc enumeration xảy ra thì EF Core mới dịch và gửi SQL. Vì vậy nếu code gọi `CountAsync`, rồi `ToListAsync`, hoặc foreach nhiều lần trên cùng query, chúng ta có thể tạo nhiều DB round-trip. EF Core có các cơ chế cache liên quan đến query compilation/DB plan nhưng đó không phải cache result set cho lần enumerate tiếp theo.

Vì endpoint read-only, tôi sẽ thử projection trực tiếp sang DTO và `AsNoTracking`, đồng thời tránh enumerate lặp. Tuy nhiên tôi cũng kiểm tra N+1, generated SQL, execution plan và số row vì tracking có thể chỉ là một phần. Tôi sẽ dùng EF command logs/APM để đo query count và duration, rồi load test trước/sau. Nếu endpoint sau đó cần update entity trong cùng `DbContext`, tôi sẽ cân nhắc giữ tracking cho phần đó thay vì áp dụng no-tracking một cách máy móc.”

## Câu hỏi đào sâu

1. `AsNoTrackingWithIdentityResolution()` khác `AsNoTracking()` về mục tiêu sử dụng như thế nào?
2. Nếu materialize một lần làm memory tăng mạnh, bạn thiết kế lại endpoint ra sao?
3. Thách thức: nếu query count chỉ là 1 nhưng latency vẫn tăng 10 lần, bạn chuyển hướng điều tra thế nào?

## Lỗi trả lời thường gặp

- Nói `IQueryable` luôn chạy ngay khi khai báo.
- Cho rằng EF Core tự cache result set.
- Áp dụng `AsNoTracking()` cho mọi query mà không xét update workflow.
- Chỉ nhìn application code mà không xem generated SQL/execution plan.
- Tối ưu trước khi đo query count, row count và latency.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.5**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **1.5**
- Communication: đánh giá xuyên suốt; câu trả lời 8+ cần rõ giả định, bằng chứng và thứ tự điều tra.

# Câu 2 — Incident: Hangfire job gửi email bị trùng sau khi hệ thống chập chờn

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** Hangfire, idempotency, distributed systems, database consistency, retry, incident response, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire để gửi email/thực hiện cập nhật Microsoft 365 sau các thay đổi nghiệp vụ. Sau một khoảng thời gian database/network chập chờn, một số người dùng nhận email hai lần; một số job hiển thị retry; business yêu cầu “đảm bảo không bao giờ gửi trùng”. Có nhiều Hangfire worker instance. Chưa rõ duplicate được tạo từ enqueue, retry, timeout sau side effect hay thao tác thủ công.

## Câu hỏi chính

Bạn sẽ xử lý incident, điều tra root cause và thiết kế lại workflow như thế nào để giảm duplicate xuống mức có thể kiểm soát, đồng thời không làm mất tác vụ hợp lệ?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate có cùng business operation ID/job ID hay là hai job khác nhau?
- Side effect nào có idempotency key/API hỗ trợ deduplication?
- Job được enqueue trong cùng transaction với business data hay sau `SaveChanges`?
- Retry policy, timeout và worker concurrency hiện tại thế nào?
- “Không bao giờ trùng” là yêu cầu kỹ thuật tuyệt đối hay mục tiêu business có thể định nghĩa bằng outcome?

## Gợi ý tư duy

- **Gợi ý 1:** Tách delivery semantics khỏi business effect.
- **Gợi ý 2:** Xem retry, crash sau side effect nhưng trước acknowledgement, concurrent enqueue và transaction boundary.
- **Gợi ý 3:** Thiết kế idempotency/deduplication bằng business key + durable state; cân nhắc transactional outbox cho enqueue consistency.

## Cấu trúc trả lời đề xuất

1. Đánh giá impact và khoanh vùng.
2. Stabilize hệ thống, tránh retry storm.
3. Correlate job/business IDs.
4. Lập nhiều giả thuyết.
5. Reproduce failure window.
6. Sửa ngắn hạn.
7. Thiết kế idempotency/outbox dài hạn.
8. Test failure paths và monitor duplicate rate.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không hứa “exactly once” chỉ bằng retry/job framework.
- Idempotency phải dựa trên business operation, không chỉ Hangfire job ID.
- Xử lý trường hợp side effect thành công nhưng worker không ghi nhận thành công.
- Có unique constraint/durable dedup state khi thích hợp.
- Điều tra bằng correlation ID, job history, DB transaction và external provider logs.

### Điểm cộng

- Transactional outbox cho việc đồng bộ business commit và scheduling/publication.
- State machine (`Pending/Processing/Succeeded/Failed`) với atomic transition/versioning.
- Retry có backoff/jitter và phân loại transient/permanent failure.

### Nâng cao

- Nêu giới hạn: external email side effect có thể không hỗ trợ true idempotency.
- Thiết kế reconciliation để phát hiện trạng thái không chắc chắn.
- Phân biệt deduplication window với idempotent business operation lâu dài.

## Hướng giải quyết tham khảo

Trước hết xác định blast radius: số user bị ảnh hưởng, loại side effect và khoảng thời gian. Nếu retry storm đang diễn ra, giảm/đình chỉ có chọn lọc queue liên quan thay vì tắt toàn bộ hệ thống. Không xóa job hàng loạt trước khi có snapshot/audit.

Correlate `BusinessOperationId`, Hangfire job ID, attempt, worker, timestamps và provider response. Các giả thuyết gồm: enqueue hai lần, concurrent handlers, automatic retry, worker mất kết nối sau khi external call thành công, hoặc business transaction commit nhưng enqueue logic chạy lại.

Thiết kế dài hạn: tạo stable idempotency key theo operation, ví dụ `EmployeeId + ActionType + Version`. Lưu operation/outbox trong cùng DB transaction với thay đổi business. Worker claim operation atomically; DB unique constraint chặn duplicate logical operation. Trước side effect, trạng thái durable phải đủ để retry an toàn. Nếu external API hỗ trợ idempotency key thì truyền key đó. Nếu không, không thể tuyệt đối chứng minh “email chỉ gửi đúng một lần” trong mọi crash boundary; cần làm rõ SLA và có reconciliation/audit.

Retry chỉ áp dụng transient errors, có backoff. Permanent errors đi dead-letter/manual review. Monitoring gồm attempts/job, duplicate-key conflicts, queue age, success/failure, external latency và operations ở trạng thái không xác định quá lâu.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ bắt đầu bằng việc phân biệt duplicate job với duplicate business effect. Hai thứ đó không giống nhau. Trong hệ thống có retry và nhiều worker, tôi giả định at-least-once execution là tình huống phải chịu được. Tôi sẽ correlate business operation ID, Hangfire job ID, attempt và log từ provider để xác định duplicate đến từ enqueue hai lần hay retry sau một failure window.

Ngắn hạn, tôi sẽ chặn retry storm nếu có và thêm guard bằng durable business key. Dài hạn, tôi muốn business change và outbox record commit trong cùng transaction. Worker xử lý operation với idempotency key và unique constraint; nếu provider hỗ trợ idempotency thì truyền key xuống. Tôi cũng không hứa exactly-once email nếu provider không cung cấp primitive tương ứng, vì crash có thể xảy ra sau khi provider đã nhận request nhưng trước khi chúng ta lưu success. Khi đó cần reconciliation và audit. Tôi sẽ test bằng cách inject timeout/crash ở từng boundary và theo dõi duplicate rate, retry count, queue age và stuck operations.”

## Câu hỏi đào sâu

1. Bạn đặt idempotency key ở cấp job, user, event hay business version? Vì sao?
2. Nếu external API không hỗ trợ idempotency và không có API query trạng thái, bạn làm gì?
3. Thách thức: outbox có giải quyết duplicate side effect hoàn toàn không? Vì sao?

## Lỗi trả lời thường gặp

- Tắt retry để “hết duplicate”, dẫn đến mất tác vụ.
- Dùng distributed lock như giải pháp duy nhất cho idempotency.
- Hứa exactly-once end-to-end mà không xét external side effect.
- Không có unique business key/durable state.
- Không test crash giữa external success và local commit.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 3 — Thiết kế AI Code Review Agent có quyền đọc repo và tạo review

**Loại câu hỏi:** AI engineering / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** AI agents, tool permissions, context engineering, structured output, evaluation, security, auditability, CI/CD

## Bối cảnh

Team muốn xây AI code-review agent cho pull request .NET. Agent có thể đọc diff, một phần repository, coding rules và CI results; sau đó đề xuất review comments. Product owner muốn sau này agent tự sửa code và push commit để tiết kiệm thời gian. Repository có business logic và secrets/config references; PR có thể chứa nội dung không đáng tin cậy. Team muốn dùng agent qua CI hoặc MCP/tool integration nhưng chưa thống nhất permission model, evaluation và human approval.

## Câu hỏi chính

Hãy thiết kế phiên bản production-safe của agent: AI thực sự cần ở đâu, phần nào phải deterministic, context nào được cung cấp, tools/permissions nào được phép, cách validate/hallucination detection, evaluation, fallback, audit và lộ trình từ read-only review đến write capability.

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được phép sửa/push/merge?
- Repo public/private và loại dữ liệu nhạy cảm nào có thể xuất hiện?
- Review quality được đo bằng metric/business outcome nào?
- Latency/cost budget trên mỗi PR là bao nhiêu?
- Có mandatory human approval trước write/merge không?

## Gợi ý tư duy

- **Gợi ý 1:** Đừng bắt đầu bằng model; bắt đầu bằng trust boundary và failure impact.
- **Gợi ý 2:** Tách deterministic pipeline (diff, build, tests, analyzers, policy) khỏi probabilistic reasoning.
- **Gợi ý 3:** Least privilege + structured findings + evidence anchoring + eval set + human gate trước destructive/write actions.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu và threat model.
2. Chia deterministic vs AI tasks.
3. Thiết kế context pipeline.
4. Định nghĩa tool allowlist và permissions.
5. Structured output + validation.
6. Human approval/fallback.
7. Offline/online evaluation.
8. Audit, monitoring và rollout theo cấp quyền.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho reasoning/ngữ nghĩa, không thay compiler/tests/security policy.
- PR/repo content là untrusted input; không để nội dung trong code tự mở rộng quyền agent.
- Read-only token/tooling ở giai đoạn đầu, scope tối thiểu.
- Findings phải gắn file/line/evidence và validate schema/range.
- Human approval trước write action ở giai đoạn rollout.
- Có eval dataset và đo precision/usefulness, không chỉ “cảm thấy review tốt”.

### Điểm cộng

- Context selection theo changed files/dependency graph thay vì gửi toàn repo.
- Secret/PII filtering và data-retention policy.
- Sandbox cho build/test; network egress/tool allowlist.
- Severity threshold và confidence không được coi là proof.

### Nâng cao

- Adversarial eval cho indirect prompt injection trong source/docs/issues.
- Canary rollout, shadow mode, false-positive/accepted-comment rate.
- Capability-based tool authorization per step và immutable audit log.

## Hướng giải quyết tham khảo

**Giả định:** mục tiêu MVP là review comment, chưa cần autonomous write.

Pipeline deterministic lấy PR metadata/diff, chạy build/tests/static analyzers và chọn context liên quan. Model nhận system policy tách biệt với repository content; code, README, issue text và tool output đều được coi là dữ liệu không đáng tin cậy. Agent chỉ có read tools cần thiết và quyền tạo draft review/comment thông qua một mediator kiểm tra target repository/PR/action.

Model trả structured findings gồm file, line/range, category, severity, explanation, evidence và suggested fix. Validator kiểm tra schema, file/line tồn tại trong diff, không cho comment vào resource ngoài scope; có thể yêu cầu evidence từ code/analyzer/test. Những claim có thể kiểm tra deterministic như compile/test/API existence phải được tool kiểm chứng thay vì tin model.

Evaluation dùng bộ PR lịch sử đã gắn nhãn và các synthetic/adversarial cases. Theo dõi precision, actionable/accepted comment rate, false-positive rate, latency, token/cost và security-policy violations. MVP chạy shadow/draft mode; human duyệt trước publish nếu risk cao.

Write capability chỉ mở sau khi quality/security đạt ngưỡng: branch riêng, không push default branch, token giới hạn repo/action, sandbox, mandatory tests, diff-size limit và human approval trước push/merge. Merge vẫn nên là policy-controlled deterministic action, không trao quyền chỉ vì model yêu cầu.

Fallback: nếu model/tool timeout hoặc validation fail, agent trả trạng thái review incomplete và giữ CI deterministic chạy bình thường; không “fail open” sang write.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không thiết kế đây là một LLM có token GitHub rộng. MVP của tôi là read-only review agent. Build, test, analyzer, permission checks và schema validation vẫn deterministic; model chỉ làm phần reasoning như nhận diện logic risk hoặc giải thích trade-off. Diff và repository content phải được coi là untrusted vì chúng có thể chứa prompt injection, nên chúng không được phép thay đổi policy hay cấp thêm tool.

Context sẽ gồm diff, symbol/dependency liên quan, coding rules đã kiểm soát và CI evidence, thay vì toàn repo. Output phải structured, có file/line/evidence rồi validator kiểm tra target có thật. Tôi sẽ đánh giá trên PR lịch sử và adversarial cases bằng precision, accepted-comment rate, false positives, latency và cost.

Ban đầu agent chỉ tạo draft hoặc suggestion cho người review. Nếu sau này mở quyền sửa, tôi dùng branch riêng, scoped credential, sandbox, test bắt buộc và human approval trước push/merge. Nếu model hoặc tool fail thì pipeline deterministic vẫn chạy; agent không được fail-open. Trade-off là ít tự động hơn, nhưng blast radius và khả năng audit tốt hơn.”

## Câu hỏi đào sâu

1. Bạn phát hiện indirect prompt injection trong source code hoặc README như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` và deferred execution phải được hiểu theo lifecycle thực thi; query compilation/cache không đồng nghĩa result caching.
- Read-only EF Core workloads nên cân nhắc projection/no-tracking dựa trên nhu cầu, nhưng phải đo generated SQL và DB behavior.
- Retry và distributed execution đòi hỏi idempotency được thiết kế cùng business operation; outbox giải quyết transaction boundary nhưng không tự tạo exactly-once external side effect.
- AI agent production-safe cần phân tách deterministic controls khỏi probabilistic reasoning, coi external/repository content là untrusted và áp dụng least privilege.
- Testing failure boundaries và observability là một phần của thiết kế, không phải bước bổ sung sau cùng.

## Mẫu tư duy cần nhớ

- **Clarify before designing:** xác định requirement, failure semantics và trust boundary trước khi chọn công nghệ.
- **Measure before optimizing:** query count, SQL, allocation và latency trước khi sửa EF Core.
- **Design retries together with idempotency:** retry không thể được thêm độc lập với side-effect semantics.
- **Assume failure between any two durable steps:** đặc biệt giữa external side effect và local acknowledgement.
- **Validate AI output deterministically:** schema, scope, evidence, permissions và policy không giao hoàn toàn cho model.
