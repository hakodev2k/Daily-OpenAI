# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý cấu hình offboarding mailbox. Job tìm các cấu hình đến hạn, gọi một external mail service để reset forwarding rồi cập nhật database. Hệ thống chạy nhiều application instances để tăng availability.

Thông thường job chạy ổn, nhưng production đôi lúc ghi nhận cùng một mailbox bị reset hai lần. Một số record vẫn ở trạng thái `Pending` dù external operation đã thành công. Khi external service chậm, số job retry tăng mạnh. Business yêu cầu không được bỏ sót record và việc chạy lại phải an toàn.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IMailService _mailService;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IMailService mailService,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _mailService = mailService;
        _logger = logger;
    }

    public async Task RunAsync()
    {
        var expired = await _db.MailConfigurations
            .Where(x => x.Status == "Pending" && x.EndTime <= DateTime.UtcNow)
            .ToListAsync();

        foreach (var item in expired)
        {
            try
            {
                await _mailService.ResetForwardingAsync(item.UserEmail);

                item.Status = "Completed";
                item.CompletedAt = DateTime.UtcNow;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Reset forwarding completed for {Email}", item.UserEmail);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed to reset forwarding for {Email}", item.UserEmail);
                throw;
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không có cơ chế claim record nguyên tử

- **Problem:** nhiều worker có thể cùng query một record `Pending`.
- **Why:** query và chuyển trạng thái không được thực hiện như một thao tác cạnh tranh có điều kiện.
- **Production impact:** cùng mailbox có thể được xử lý nhiều lần.
- **Severity:** Critical.
- **Recommended fix:** claim record bằng conditional update/locking phù hợp database hoặc optimistic concurrency; chỉ worker claim thành công mới xử lý.

### 2. External side effect và DB update không atomic

- **Problem:** mail service có thể thành công rồi DB commit thất bại.
- **Why:** transaction database không thể tự bao phủ external system.
- **Production impact:** record vẫn `Pending`; retry thực hiện side effect lần nữa.
- **Severity:** Critical.
- **Recommended fix:** thiết kế operation idempotent bằng operation/idempotency key; lưu state machine rõ ràng và reconcile các trạng thái không chắc chắn.

### 3. Không có idempotency contract với external operation

- **Problem:** retry mặc định được giả định là an toàn.
- **Why:** code không truyền operation ID và không kiểm tra trạng thái đích.
- **Production impact:** duplicate side effects hoặc lỗi khó phân biệt giữa retry hợp lệ và duplicate.
- **Severity:** High.
- **Recommended fix:** nếu external API hỗ trợ idempotency key thì sử dụng; nếu không, thiết kế `ResetForwardingAsync` theo desired-state semantics hoặc kiểm tra trạng thái trước/sau một cách có kiểm soát.

### 4. Một record lỗi làm dừng cả batch

- **Problem:** `throw` trong `catch` kết thúc vòng lặp.
- **Why:** failure isolation không được thiết kế.
- **Production impact:** các record phía sau không được xử lý cho đến lần chạy sau.
- **Severity:** High.
- **Recommended fix:** xử lý từng item độc lập, ghi trạng thái retry/failure; chỉ throw khi lỗi cấp hệ thống khiến tiếp tục không còn an toàn.

### 5. Không có cancellation/timeout contract rõ ràng

- **Problem:** method không nhận `CancellationToken`.
- **Why:** shutdown/deployment hoặc external call treo không được propagate cancellation từ job xuống I/O.
- **Production impact:** shutdown chậm, worker bị chiếm lâu, recovery khó dự đoán.
- **Severity:** Medium.
- **Recommended fix:** nhận token khi integration hỗ trợ; đặt timeout có chủ đích cho external call và phân loại transient/permanent failure.

### 6. Batch không giới hạn

- **Problem:** `ToListAsync()` tải toàn bộ record đến hạn.
- **Why:** không paging/batching.
- **Production impact:** memory tăng và job kéo dài khi backlog lớn.
- **Severity:** Medium.
- **Recommended fix:** claim theo batch có giới hạn và tiếp tục cho đến khi hết backlog hoặc đạt execution budget.

### 7. Retry không phân loại lỗi

- **Problem:** mọi exception được rethrow giống nhau.
- **Why:** không phân biệt timeout, throttling, validation, authorization và permanent business error.
- **Production impact:** retry storm hoặc retry vô ích.
- **Severity:** Medium.
- **Recommended fix:** retry transient errors với backoff/jitter; permanent errors chuyển trạng thái cần can thiệp.

### 8. Observability thiếu correlation/business identifiers

- **Problem:** log chủ yếu dựa vào email.
- **Why:** thiếu configuration ID, operation ID, attempt và duration.
- **Production impact:** khó reconstruct một execution qua nhiều retry.
- **Severity:** Medium.
- **Recommended fix:** structured logging với non-sensitive identifiers; hạn chế PII trong log.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa state machine và claim abstraction. Chi tiết atomic claim phải được implement phù hợp SQL Server/PostgreSQL thay vì chỉ dựa vào in-memory synchronization.

```csharp
public sealed class OffboardingJob
{
    private readonly IMailConfigurationStore _store;
    private readonly IMailService _mailService;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        IMailConfigurationStore store,
        IMailService mailService,
        ILogger<OffboardingJob> logger)
    {
        _store = store;
        _mailService = mailService;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        const int batchSize = 50;

        while (!cancellationToken.IsCancellationRequested)
        {
            var items = await _store.ClaimExpiredAsync(
                batchSize,
                DateTime.UtcNow,
                cancellationToken);

            if (items.Count == 0)
                return;

            foreach (var item in items)
            {
                cancellationToken.ThrowIfCancellationRequested();
                var operationId = $"offboarding-reset:{item.Id}";

                try
                {
                    await _mailService.ResetForwardingAsync(
                        item.UserEmail,
                        operationId,
                        cancellationToken);

                    await _store.MarkCompletedAsync(
                        item.Id,
                        operationId,
                        DateTime.UtcNow,
                        cancellationToken);

                    _logger.LogInformation(
                        "Offboarding reset completed. ConfigurationId={ConfigurationId} OperationId={OperationId}",
                        item.Id,
                        operationId);
                }
                catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
                {
                    throw;
                }
                catch (Exception ex)
                {
                    await _store.MarkAttemptFailedAsync(
                        item.Id,
                        operationId,
                        ex.GetType().Name,
                        cancellationToken);

                    _logger.LogError(
                        ex,
                        "Offboarding reset failed. ConfigurationId={ConfigurationId} OperationId={OperationId}",
                        item.Id,
                        operationId);
                }
            }
        }
    }
}
```

`ClaimExpiredAsync` cần đảm bảo nhiều worker không cùng claim một item, ví dụ bằng conditional state transition `Pending -> Processing` và concurrency control ở database. Cần có recovery policy cho record mắc kẹt ở `Processing`, chẳng hạn lease/claimed-at cùng reconciliation.

## Trade-offs

Atomic claiming làm state model và repository phức tạp hơn nhưng loại bỏ race condition quan trọng. Distributed lock có thể giảm duplicate execution nhưng không thay thế idempotency vì process vẫn có thể chết sau external side effect. Outbox rất hữu ích cho reliable publication từ DB, nhưng không tự biến một external API bất kỳ thành exactly-once. Với operation “đưa mailbox về desired state”, API idempotent theo trạng thái thường đơn giản hơn cố xây exactly-once delivery.

## Cách kiểm thử

1. **Concurrency test:** chạy 10 workers cùng claim một record; xác nhận chỉ một worker nhận quyền xử lý tại một thời điểm.
2. **Failure-path test:** external call thành công nhưng DB completion update thất bại; retry không tạo side effect nguy hiểm.
3. **Retry test:** timeout/transient failure được retry theo policy; permanent error không retry vô hạn.
4. **Recovery test:** worker chết sau khi claim; record được reclaim/reconcile sau lease timeout.
5. **Load test:** backlog lớn được xử lý theo batch mà memory và execution duration vẫn kiểm soát được.

## Quan sát trong production

Theo dõi `pending_count`, `processing_count`, `failed_count`, oldest pending age, processing lease age, attempts per operation, external latency/error rate và completion throughput. Trace nên liên kết job execution → configuration ID → external call → DB transition. Alert khi backlog age vượt SLA, duplicate operation tăng, hoặc record mắc `Processing` quá lâu.

3. Nếu cần throughput gấp 20 lần, bạn sẽ scale worker và partition workload thế nào mà vẫn giữ correctness?

Một internal ASP.NET Core API cho phép portal tìm audit logs theo tenant. Người dùng đăng nhập bằng bearer token. Endpoint mới được thêm nhanh để hỗ trợ support team tìm theo email hoặc action. public sealed class AuditController : ControllerBase

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization

- **Problem:** caller tự truyền `tenantId`; code không xác minh quyền với tenant đó.
- **Why:** authentication/authorization policy ở mức resource không xuất hiện trong flow.
- **Production impact:** authenticated user có thể đọc audit logs của tenant khác nếu đoán/biết ID.
- **Severity:** Critical.
- **Recommended fix:** derive tenant từ trusted claims khi role chỉ có một tenant, hoặc thực hiện resource-based authorization đối với tenant được request trước khi query.

### 2. SQL injection

- **Problem:** `tenantId` và `text` được interpolate trực tiếp vào raw SQL.
- **Why:** user-controlled values trở thành một phần cú pháp SQL.
- **Production impact:** đọc/sửa dữ liệu trái phép tùy quyền DB account; có thể gây incident nghiêm trọng.
- **Severity:** Critical.
- **Recommended fix:** ưu tiên LINQ query có parameterization; nếu cần raw SQL, dùng API parameterized thay vì nối/interpolate thành raw command text.

### 3. Trả toàn bộ entity bằng `SELECT *`

- **Problem:** endpoint trả entity database trực tiếp.
- **Why:** không có explicit projection/DTO contract.
- **Production impact:** field nội bộ hoặc sensitive metadata có thể bị lộ khi schema thay đổi.
- **Severity:** High.
- **Recommended fix:** projection whitelist sang response DTO chỉ chứa field cần thiết.

### 4. `take` không bounded

- **Problem:** caller có thể yêu cầu số lượng rất lớn hoặc giá trị bất thường.
- **Why:** không validate range.
- **Production impact:** query nặng, response lớn, memory/network pressure và abuse dễ dàng.
- **Severity:** High.
- **Recommended fix:** enforce giới hạn, ví dụ 1–200 tùy SLA; dùng pagination/cursor phù hợp.

### 5. Search pattern `%text%` có thể rất đắt

- **Problem:** contains search trên cột lớn có thể khó tận dụng B-tree index thông thường.
- **Why:** wildcard ở đầu pattern và search term quá rộng.
- **Production impact:** scans, CPU/I/O cao khi bảng audit lớn.
- **Severity:** Medium.
- **Recommended fix:** xác định requirement search; giới hạn minimum term length, time range; cân nhắc full-text/search technology nếu workload thực sự cần substring search ở quy mô lớn.

### 6. Log nguyên search term

- **Problem:** `text` có thể chứa email, identifier hoặc dữ liệu nhạy cảm và được ghi nguyên văn.
- **Why:** logging policy chưa phân loại user input.
- **Production impact:** PII/secrets có thể lan sang log store và tăng compliance exposure.
- **Severity:** Medium.
- **Recommended fix:** log metadata cần thiết như tenant authorization result, normalized query type, length/hash khi phù hợp; không log raw sensitive search value mặc định.

### 7. Không truyền cancellation token

- **Problem:** request bị client hủy nhưng DB query không nhận `RequestAborted`.
- **Why:** action không propagate cancellation.
- **Production impact:** server/database tiếp tục làm việc vô ích với query đắt.
- **Severity:** Medium.
- **Recommended fix:** nhận `CancellationToken` và truyền vào async database operation.

### 8. Không có bounded time range/cursor cho audit workload

- **Problem:** query có thể tìm trên toàn lịch sử rồi sort.
- **Why:** API contract không buộc caller thu hẹp dataset.
- **Production impact:** latency và DB cost tăng theo dữ liệu.
- **Severity:** Medium.
- **Recommended fix:** thiết kế time-window + stable cursor `(CreatedAt, Id)` khi dữ liệu lớn và index phù hợp với tenant/time access pattern.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AppDbContext db,
        ITenantAccessService tenantAccess,
        ILogger<AuditController> logger)
    {
        _db = db;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        string tenantId,
        string? text,
        DateTime? fromUtc,
        int take = 100,
        CancellationToken cancellationToken = default)
    {
        if (take is < 1 or > 200)
            return BadRequest("take must be between 1 and 200.");

        text = text?.Trim();
        if (text is { Length: > 0 and < 3 })
            return BadRequest("Search text must contain at least 3 characters.");

        if (!await _tenantAccess.CanReadAuditAsync(
                User, tenantId, cancellationToken))
        {
            return Forbid();
        }

        var query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (fromUtc.HasValue)
            query = query.Where(x => x.CreatedAt >= fromUtc.Value);

        if (!string.IsNullOrEmpty(text))
            query = query.Where(x => x.Message.Contains(text));

        var rows = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(take)
            .Select(x => new AuditLogDto(
                x.Id,
                x.Action,
                x.CreatedAt,
                x.ActorId))
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Authorized audit search. TenantId={TenantId} ResultCount={ResultCount} HasText={HasText}",
            tenantId,
            rows.Count,
            !string.IsNullOrEmpty(text));

        return Ok(rows);
    }
}

public sealed record AuditLogDto(
    long Id,
    string Action,
    DateTime CreatedAt,
    string ActorId);
```

Đây là hướng tham khảo, không phải tuyên bố rằng `Contains` luôn đủ nhanh. Với dataset lớn, query plan và index phải được đo trên database thực tế. Nếu yêu cầu là full-text/sub-string search quy mô lớn, nên đánh giá công cụ/search index phù hợp thay vì giả định một LINQ expression tự giải quyết performance.

## Trade-offs

Resource-based authorization thêm một lookup hoặc policy evaluation nhưng là boundary bắt buộc trong multi-tenant system. Projection DTO tăng code nhưng giảm coupling và accidental exposure. Offset pagination đơn giản nhưng không lý tưởng cho audit stream lớn/thay đổi liên tục; keyset/cursor pagination ổn định hơn nhưng API phức tạp hơn. Full-text/search engine tăng operational cost, vì vậy chỉ nên dùng khi query workload và measurement chứng minh cần thiết.

## Cách kiểm thử

1. **Security integration test:** user tenant A request tenant B phải bị từ chối trước khi dữ liệu được trả.
2. **Injection test:** search text chứa quotes/SQL metacharacters chỉ được xử lý như dữ liệu, không thay đổi semantics của query.
3. **Data exposure test:** response contract không bao gồm internal/sensitive fields dù entity có thêm property mới.
4. **Boundary test:** `take=0`, `take=201`, search term quá ngắn và cancellation đều có behavior xác định.
5. **Database/load test:** dữ liệu lớn với tenant/time distributions thực tế; capture query plan, duration, reads và CPU trước khi quyết định index/search strategy.

## Quan sát trong production

Theo dõi request count, forbidden count, latency p50/p95/p99, DB query duration, rows scanned/returned khi có telemetry phù hợp, cancellation rate và error rate. Security audit nên ghi actor ID, tenant ID, authorization outcome và correlation ID nhưng tránh raw search text. Alert khi forbidden attempts tăng bất thường hoặc query latency/DB CPU vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support user được phép truy cập 500 tenants, bạn sẽ model authorization thế nào để tránh nhét toàn bộ tenant list vào token?
2. Vì sao parameterized SQL không giải quyết vấn đề broken authorization?
3. Khi nào bạn chọn PostgreSQL full-text/trigram hoặc một search service thay vì `LIKE`/`Contains`?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào hai trust boundary rất khác nhau. Với background processing, correctness phải tồn tại qua retry, crash và nhiều worker; distributed scheduling không đồng nghĩa exactly-once business effect. Với multi-tenant API, authentication không thay thế resource authorization, và parameterization chỉ giải quyết injection chứ không giải quyết quyền truy cập. Cả hai trường hợp đều yêu cầu thiết kế failure state và observability ngay từ đầu.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng idempotency; đừng giả định scheduler đảm bảo exactly-once.
- Tách database atomicity khỏi external side effects và xác định failure window.
- Authentication xác định caller; authorization quyết định caller được phép làm gì với resource nào.
- Parameterize mọi user-controlled SQL value, nhưng vẫn kiểm tra business authorization riêng biệt.
- Measure query plan, latency và backlog trước khi tối ưu; observability là một phần của design.
