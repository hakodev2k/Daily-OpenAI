# Code Review Challenge 1 — Service Bus consumer mất message và tạo duplicate side effect khi dependency chậm

**Chủ đề:** C#/.NET, Azure Service Bus, message settlement, idempotency, retry, failure handling  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Số vấn đề ước lượng:** 9–11

## Bối cảnh

Một order service publish `OrderPaid` vào Azure Service Bus. Consumer tạo shipment trong SQL Server rồi gọi REST API của warehouse. Production đôi lúc warehouse nhận cùng order hai lần; một số message biến mất dù shipment chưa hoàn tất. Warehouse có lúc latency 40–90 giây. Hệ thống scale nhiều consumer instances.

## Đoạn code cần review

```csharp
public sealed class OrderPaidConsumer : BackgroundService
{
    private readonly ServiceBusReceiver _receiver;
    private readonly ShippingDbContext _db;
    private readonly HttpClient _warehouse;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await _receiver.ReceiveMessageAsync(
                TimeSpan.FromSeconds(5));

            if (message is null)
                continue;

            await _receiver.CompleteMessageAsync(message);

            var evt = JsonSerializer.Deserialize<OrderPaid>(message.Body)!;

            _db.Shipments.Add(new Shipment
            {
                Id = Guid.NewGuid(),
                OrderId = evt.OrderId,
                Status = "Creating"
            });
            await _db.SaveChangesAsync();

            var response = await _warehouse.PostAsJsonAsync(
                "/api/shipments", evt);
            response.EnsureSuccessStatusCode();

            var shipment = await _db.Shipments
                .SingleAsync(x => x.OrderId == evt.OrderId);
            shipment.Status = "Created";
            await _db.SaveChangesAsync();
        }
    }
}
```

## Nhiệm vụ của ứng viên

Xác định correctness, reliability, concurrency, idempotency và observability issues; mô tả production impact; ưu tiên severity; đề xuất thiết kế sửa; nêu tests và telemetry chứng minh fix hoạt động.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu process chết ngay sau `CompleteMessageAsync`?
2. Nếu warehouse đã nhận request nhưng HTTP response bị timeout thì consumer biết side effect đã xảy ra chưa?
3. Message lock hết hạn trong lúc xử lý dài có thể dẫn tới điều gì?
4. `OrderId` nên được bảo vệ bằng constraint nào?
5. Poison message nên đi đâu sau nhiều lần thất bại?

## Gợi ý

### Gợi ý 1

Phân biệt message delivery guarantee với external side-effect guarantee.

### Gợi ý 2

Xem settlement, lock lifetime, idempotency boundary và trạng thái durable như bốn vấn đề riêng.

## Dừng lại và tự review

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

### Critical — Complete message trước khi business processing thành công

**Vấn đề:** Message được settle trước khi SQL và warehouse hoàn tất.  
**Tại sao xảy ra:** Consumer coi việc receive là thành công.  
**Ảnh hưởng production:** Crash hoặc exception sau `Complete` làm mất cơ hội retry dù workflow chưa hoàn tất.  
**Cách sửa:** Chỉ complete sau khi đạt durable success state; failure phù hợp thì abandon/retry hoặc dead-letter theo policy.

### High — External side effect không idempotent

**Vấn đề:** Timeout sau khi warehouse đã nhận request tạo trạng thái ambiguous.  
**Tại sao xảy ra:** HTTP retry không biết request trước đã commit hay chưa.  
**Ảnh hưởng production:** Duplicate shipment.  
**Cách sửa:** Dùng stable idempotency key như `OrderId`/operation ID nếu warehouse hỗ trợ; nếu không, thiết kế reconciliation và chấp nhận/document at-least-once semantics.

### High — Không bảo vệ duplicate message ở database

**Vấn đề:** Mỗi delivery luôn `Add` shipment mới.  
**Tại sao xảy ra:** Không có unique business key/idempotency record.  
**Ảnh hưởng production:** Redelivery hoặc concurrent consumers tạo duplicate rows/side effects.  
**Cách sửa:** Unique constraint trên business idempotency key và transactionally record processing state.

### High — Lock/processing duration không được thiết kế

**Vấn đề:** Warehouse có thể chậm lâu hơn processing assumptions.  
**Tại sao xảy ra:** Code không thể hiện lock renewal/processor configuration hoặc bounded execution.  
**Ảnh hưởng production:** Lock mất, message redeliver trong khi instance cũ vẫn đang xử lý.  
**Cách sửa:** Dùng Service Bus processor/lock renewal phù hợp, giới hạn processing duration, và vẫn bắt buộc idempotency vì lock không tạo exactly-once side effect.

### High — Scoped DbContext lifetime không phù hợp với long-lived worker

**Vấn đề:** Một DbContext bị giữ qua vòng đời worker nếu được inject trực tiếp.  
**Tại sao xảy ra:** Hosted service là singleton.  
**Ảnh hưởng production:** Tracking state kéo dài, concurrency/lifetime bugs.  
**Cách sửa:** Tạo scope hoặc `IDbContextFactory` cho từng message/operation.

### Medium — Cancellation không propagate

**Vấn đề:** Receive, settlement, SQL và HTTP calls không nhận `stoppingToken`.  
**Tại sao xảy ra:** Token bị bỏ qua.  
**Ảnh hưởng production:** Shutdown kéo dài và operation tiếp tục sau termination request.  
**Cách sửa:** Propagate cancellation nơi API hỗ trợ và thiết kế shutdown semantics rõ ràng.

### Medium — Deserialization/poison message không được phân loại

**Vấn đề:** Invalid payload ném exception như transient failure.  
**Tại sao xảy ra:** Không validate schema/version.  
**Ảnh hưởng production:** Retry vô ích, queue churn.  
**Cách sửa:** Validate payload; permanent invalid messages chuyển dead-letter với diagnostic metadata phù hợp.

### Medium — Thiếu retry classification và observability

**Vấn đề:** Không phân biệt transient/permanent errors và không có correlation telemetry.  
**Tại sao xảy ra:** Failure policy chưa được mô hình hóa.  
**Ảnh hưởng production:** Khó điều tra backlog/duplicate/dependency outage.  
**Cách sửa:** Structured logs + traces + metrics theo MessageId/OrderId, delivery count, processing duration, lock loss, retry/DLQ và warehouse dependency.

## Phiên bản đề xuất

```csharp
async Task HandleAsync(ProcessMessageEventArgs args)
{
    var ct = args.CancellationToken;
    var evt = DeserializeAndValidate(args.Message);

    await using var db = await _dbFactory.CreateDbContextAsync(ct);

    var state = await db.ShipmentOperations
        .SingleOrDefaultAsync(x => x.OrderId == evt.OrderId, ct);

    if (state?.Status == "Completed")
    {
        await args.CompleteMessageAsync(args.Message, ct);
        return;
    }

    if (state is null)
    {
        db.ShipmentOperations.Add(new ShipmentOperation
        {
            OrderId = evt.OrderId,
            Status = "Pending",
            OperationId = evt.OrderId.ToString()
        });
        await db.SaveChangesAsync(ct); // unique OrderId enforced by DB
    }

    using var request = new HttpRequestMessage(HttpMethod.Post, "/api/shipments");
    request.Headers.Add("Idempotency-Key", evt.OrderId.ToString());
    request.Content = JsonContent.Create(evt);

    using var response = await _warehouse.SendAsync(request, ct);
    response.EnsureSuccessStatusCode();

    await db.ShipmentOperations
        .Where(x => x.OrderId == evt.OrderId)
        .ExecuteUpdateAsync(s => s.SetProperty(x => x.Status, "Completed"), ct);

    await args.CompleteMessageAsync(args.Message, ct);
}
```

Đây là skeleton, không phải exactly-once proof. Nếu warehouse không hỗ trợ idempotency, timeout sau side effect vẫn ambiguous; cần reconciliation/business compensation thay vì tuyên bố exactly-once.

## Giải thích thiết kế sau khi sửa

Database giữ durable processing state và unique business key. Message chỉ complete sau durable success. External call dùng stable idempotency key khi provider hỗ trợ. Lock renewal giảm redelivery do xử lý dài nhưng idempotency vẫn là correctness boundary.

## Trade-offs

Giữ message lock trong external call đơn giản nhưng tăng lock duration. Tách workflow thành durable state machine/outbox có khả năng recovery tốt hơn nhưng tăng complexity. Không nên thêm distributed transaction nếu dependencies không hỗ trợ; cần chọn guarantee thực tế và reconciliation.

## Cách kiểm thử

1. Crash sau receive nhưng trước SQL commit: message phải được xử lý lại.
2. Warehouse nhận request rồi client timeout: retry không tạo duplicate khi idempotency được hỗ trợ.
3. Hai consumers nhận duplicate delivery: unique constraint giữ một operation.
4. Dependency chậm vượt lock window: kiểm tra lock-loss/redelivery behavior.
5. Invalid payload và max delivery: message đi DLQ, không loop vô hạn.

## Quan sát trong production

Theo dõi active/dead-letter message count, delivery count, processing p95/p99, lock-lost count, warehouse latency/errors, duplicate-key conflicts, retry count và correlation trace theo MessageId/OrderId.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao Service Bus duplicate detection vẫn không thay thế consumer idempotency?
2. Nếu warehouse không hỗ trợ idempotency key, bạn thiết kế reconciliation thế nào?
3. Khi nào bạn tách external call khỏi consumer bằng durable outbox/workflow?

# Code Review Challenge 2 — CI/CD chạy EF Core migration đồng thời trên nhiều replicas

**Chủ đề:** EF Core, SQL Server, CI/CD, Kubernetes, deployment safety, schema migration, rollback  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Số vấn đề ước lượng:** 7–9

## Bối cảnh

Team deploy ASP.NET Core API lên Kubernetes. Để “tự động hóa”, mỗi pod chạy migration lúc startup. Release mới thêm non-null column và đổi cách đọc dữ liệu. Khi rollout 6 replicas, đôi lúc pod startup timeout, SQL blocking tăng mạnh và rollback image cũ không chạy được với schema mới.

## Đoạn code cần review

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("App")));

var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    await db.Database.MigrateAsync();
}

app.MapControllers();
app.Run();
```

Deployment excerpt:

```yaml
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 3
      maxUnavailable: 0
```

Migration:

```csharp
migrationBuilder.AddColumn<string>(
    name: "NormalizedCode",
    table: "Products",
    type: "nvarchar(64)",
    nullable: false,
    defaultValue: "");

migrationBuilder.CreateIndex(
    name: "IX_Products_NormalizedCode",
    table: "Products",
    column: "NormalizedCode",
    unique: true);
```

## Nhiệm vụ của ứng viên

Review deployment/migration như production change: correctness, concurrency, lock/blocking, backward compatibility, rollback, observability và test strategy. Không giả định “migration chạy được trên local” nghĩa là an toàn production.

## Câu hỏi gợi mở

1. Có bao nhiêu pod có thể gọi `MigrateAsync` gần như cùng lúc?
2. Unique index sẽ ra sao khi mọi existing row nhận cùng default `""`?
3. Schema mới có tương thích với old pods còn chạy trong rolling deployment không?
4. Rollback application binary có đồng nghĩa rollback database an toàn không?
5. Migration dài ảnh hưởng startup/readiness và SQL workload thế nào?

## Gợi ý

### Gợi ý 1

Tách schema evolution thành expand → migrate/backfill → contract.

### Gợi ý 2

Deployment artifact và database migration có lifecycle/rollback semantics khác nhau.

## Dừng lại và tự review

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

### Critical — Unique index không hợp lệ với dữ liệu hiện hữu

**Vấn đề:** Mọi row cũ nhận `NormalizedCode = ""` rồi tạo unique index.  
**Tại sao xảy ra:** Migration trộn schema addition, data backfill assumption và uniqueness enforcement.  
**Ảnh hưởng production:** Migration fail giữa deployment.  
**Cách sửa:** Expand bằng nullable/non-enforced schema, backfill dữ liệu hợp lệ theo batch, verify duplicates, rồi mới enforce NOT NULL/unique ở bước sau.

### High — Mỗi replica tự migrate database

**Vấn đề:** Nhiều startup instances cạnh tranh schema migration.  
**Tại sao xảy ra:** Migration gắn vào application startup.  
**Ảnh hưởng production:** Lock contention, startup timeout, khó kiểm soát ownership/failure.  
**Cách sửa:** Chạy migration bằng một deployment step/job có ownership rõ, trước/sau app rollout theo compatibility plan; không để mọi replica tự quyết định schema.

### High — Thiếu backward/forward compatibility trong rolling deployment

**Vấn đề:** Old và new binaries cùng tồn tại nhưng schema contract không được thiết kế cho cả hai.  
**Tại sao xảy ra:** Migration và code switch diễn ra như một atomic release giả định.  
**Ảnh hưởng production:** Old pod có thể lỗi trong rollout hoặc rollback.  
**Cách sửa:** Expand-contract; new schema ban đầu additive, deploy code hỗ trợ cả states, backfill, switch reads/writes, cuối cùng contract ở release sau.

### High — Rollback strategy không tồn tại

**Vấn đề:** Rollback image được coi như rollback toàn release.  
**Tại sao xảy ra:** Database state không tự quay lại theo Deployment.  
**Ảnh hưởng production:** Binary cũ có thể không chạy với schema/data mới.  
**Cách sửa:** Xác định roll-forward ưu tiên cho schema changes, compatibility window và tested recovery plan; destructive contract tách riêng.

### Medium — Migration duration nằm trên startup critical path

**Vấn đề:** DDL/backfill có thể kéo dài trước khi app start.  
**Tại sao xảy ra:** `MigrateAsync` chạy đồng bộ với boot.  
**Ảnh hưởng production:** Startup probes/timeouts và capacity rollout bị ảnh hưởng.  
**Cách sửa:** Dedicated migration stage với timeout/telemetry riêng.

### Medium — Không có preflight data validation

**Vấn đề:** Không kiểm tra duplicate/invalid source data trước uniqueness enforcement.  
**Tại sao xảy ra:** Migration giả định dữ liệu sạch.  
**Ảnh hưởng production:** Failure chỉ xuất hiện khi DDL đang chạy.  
**Cách sửa:** Pre-deploy query/validation và deterministic backfill rules.

### Medium — Thiếu observability cho database deployment

**Vấn đề:** Không có duration, lock/blocking, migration version hay failure telemetry riêng.  
**Tại sao xảy ra:** Migration bị coi như implementation detail.  
**Ảnh hưởng production:** Khó xác định rollout chậm vì app hay database.  
**Cách sửa:** Log migration ID, duration/result; monitor SQL blocking, waits, CPU/IO và application compatibility errors.

## Phiên bản đề xuất

```text
Release N:
1. Preflight: kiểm tra duplicate/source data và ước lượng backfill volume.
2. Migration job (single owner): thêm NormalizedCode nullable, chưa unique.
3. Deploy code có thể đọc schema cũ/mới và ghi NormalizedCode cho records mới.
4. Backfill theo batch có checkpoint, throttling và telemetry.
5. Verify: NULL count = 0, duplicate count = 0.

Release N+1:
6. Tạo unique index bằng strategy phù hợp workload/DB capability.
7. Enforce NOT NULL sau khi data invariant đã đúng.
8. Sau compatibility window mới xóa code/path cũ.
```

## Giải thích thiết kế sau khi sửa

Migration là production operation độc lập, không phải side effect của mỗi pod startup. Expand-contract giữ old/new binaries tương thích trong rolling rollout và cho phép backfill/verification trước khi enforce invariant.

## Trade-offs

Expand-contract cần nhiều release và code tạm thời nhưng giảm blast radius. One-shot migration đơn giản hơn cho database nhỏ/downtime window được chấp nhận; nếu chọn cách đó phải explicit maintenance window, backup/recovery, duration estimate và rollback/roll-forward plan.

## Cách kiểm thử

1. Clone production-like dataset có duplicates và chạy migration rehearsal.
2. Test old + new application versions cùng schema expanded.
3. Load test trong lúc backfill để đo blocking/latency.
4. Fail migration job giữa chừng rồi rerun/recover.
5. Rollback binary trong compatibility window và xác minh API vẫn hoạt động.

## Quan sát trong production

Theo dõi migration version/result/duration, SQL blocking/waits, CPU/IO, deadlocks, API p95/p99/5xx, pod readiness và backfill progress. Có stop criteria rõ nếu latency/error budget vượt ngưỡng.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận downtime migration thay vì expand-contract?
2. Backfill hàng trăm triệu rows cần throttle/checkpoint thế nào?
3. Nếu tạo index gây blocking lớn hơn rehearsal, bạn dừng/khôi phục rollout ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message settlement không đồng nghĩa external side effect exactly-once.
- Idempotency phải được bảo vệ ở business/database boundary, không chỉ bằng retry logic.
- Schema migration và application rollout có lifecycle khác nhau.
- Expand-contract giúp rolling deployment và rollback giữ compatibility.

## Mẫu tư duy cần nhớ

- Side effect trước/after acknowledgement luôn phải phân tích crash window.
- Timeout của external dependency tạo trạng thái ambiguous.
- Dùng database constraint để bảo vệ invariant quan trọng.
- Schema: expand → backfill/verify → contract.
- Migration phải có owner, telemetry, recovery và compatibility plan.
