# Câu 1 — User đã đăng nhập nhưng API vẫn trả 401/403: Authentication, Authorization, claims và policy thực sự chạy qua pipeline thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Authentication, Authorization, JWT, claims, policy-based authorization, middleware pipeline, 401/403 semantics, Microsoft Entra ID concepts, API security, production diagnostics

## Bối cảnh

Một ASP.NET Core .NET 8 API được bảo vệ bằng JWT bearer authentication. Frontend đăng nhập qua một identity provider và gửi access token tới backend.

Một endpoint nội bộ:

```csharp
[Authorize(Policy = "CanApproveExpense")]
[HttpPost("expenses/{id:guid}/approve")]
public async Task<IActionResult> Approve(
    Guid id,
    CancellationToken cancellationToken)
{
    await _service.ApproveAsync(id, User, cancellationToken);
    return NoContent();
}
```

Policy được cấu hình:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanApproveExpense", policy =>
        policy.RequireClaim("permission", "expense.approve"));
});
```

Production xuất hiện các tình huống:

- một số request không có token trả 401;
- một số user đăng nhập bình thường nhưng endpoint trả 403;
- một nhóm user có claim tương đương trong UI nhưng API vẫn từ chối;
- một developer nói “403 nghĩa là token invalid”;
- một developer khác muốn bỏ policy và chỉ check role bằng `User.IsInRole("Admin")` trong controller;
- logs hiện chưa ghi authentication scheme, authorization failure reason hoặc correlation ID đầy đủ;
- token được phát từ nhiều environments/tenants trong quá trình migration;
- chưa xác minh issuer, audience, claim mapping, token type, policy registration và middleware order của production deployment.

Không giả định trước root cause là policy sai hay token sai.

## Câu hỏi chính

Hãy giải thích request đi qua **Authentication** và **Authorization** trong ASP.NET Core như thế nào, `HttpContext.User` được hình thành ra sao, và vì sao một request có thể trả 401 hoặc 403 trong các failure modes khác nhau. Sau đó trình bày cách bạn điều tra một incident mà user “đã login” nhưng API vẫn bị từ chối, cách thiết kế policy/claims hợp lý hơn, và những assumption nào cần tránh khi dùng JWT hoặc Microsoft Entra ID.

## Câu hỏi làm rõ nên cân nhắc

1. Frontend đang gửi access token hay ID token, và token có đúng audience dành cho API không?
2. 401/403 xảy ra ở mọi instance hay chỉ một subset deployment/configuration?
3. Claim `permission` trong token thực tế có tên/value đúng như policy mong đợi không, hay bị namespace/mapping khác?
4. User cần quyền theo role toàn cục hay permission theo resource/business context?
5. Authentication scheme mặc định và middleware order hiện tại là gì, có custom handler/policy nào can thiệp không?

## Gợi ý tư duy

### Gợi ý 1

Tách hai câu hỏi: **“Ai đang gọi?”** và **“Principal này có được phép làm hành động này không?”**.

### Gợi ý 2

“User đã login ở frontend” không chứng minh access token gửi tới API hợp lệ cho API đó.

### Gợi ý 3

Đừng debug từ UI label hoặc role name. Hãy kiểm tra token claims, scheme, authorization requirement và failure result thực tế.

## Cấu trúc trả lời đề xuất

1. Clarify token type, issuer, audience và endpoint policy.
2. Giải thích authentication handler tạo `ClaimsPrincipal`.
3. Giải thích authorization policy đánh giá principal/requirements.
4. Phân biệt 401 và 403 theo authentication/authorization state.
5. Thu evidence từ trace/log/token metadata an toàn.
6. So sánh hypotheses: invalid token, wrong audience, missing claim, mapping, policy/config drift.
7. Đề xuất policy/resource-based authorization nếu cần.
8. Test bằng integration/security tests.
9. Add production telemetry nhưng không log secrets/token đầy đủ.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Authentication xác định identity và tạo/đặt principal vào `HttpContext.User` thông qua configured authentication scheme/handler.
- Authorization chạy sau khi identity được thiết lập và đánh giá policy/requirements đối với principal và đôi khi resource.
- 401 thường liên quan việc request chưa được authenticate thành principal phù hợp hoặc challenge được phát ra; 403 thường có nghĩa caller đã được authenticate nhưng không đáp ứng authorization requirement.
- “Đã login” ở client không đồng nghĩa token gửi cho API có issuer/audience/scope/claim phù hợp.
- ID token và access token có mục đích khác nhau; API cần validate access token dành cho chính API đó.
- Role không phải luôn thay thế được permission/policy; business authorization nên phản ánh requirement thực tế.
- Không nên log raw bearer token vào production logs.

### Điểm cộng

- Kiểm tra middleware order và endpoint metadata nhưng không đổ lỗi cho order nếu evidence không hỗ trợ.
- Phân biệt authentication failure, challenge, forbid và business-level resource authorization.
- Nhận ra claim names/role mapping có thể khác giữa identity providers/tenants/configurations.
- Đề xuất custom `IAuthorizationHandler` hoặc resource-based authorization khi quyền phụ thuộc expense owner, department, amount hoặc workflow state.
- Ghi structured telemetry như scheme, policy name, failure category, subject identifier đã pseudonymize, tenant, issuer/audience validation result và correlation ID.

### Senior+

- Không đặt toàn bộ authorization business logic vào token nếu quyền thay đổi nhanh hoặc phụ thuộc resource state.
- Nhận ra token lifetime tạo khoảng stale authorization state; cần quyết định claim-based snapshot có chấp nhận được hay cần server-side policy/data lookup.
- Phân biệt identity boundary và application authorization boundary khi nhiều tenants/environments cùng phát token.
- Thiết kế deny-by-default, least privilege và explicit policy naming thay vì hard-coded role checks rải rác.

## Hướng giải quyết tham khảo

Trong ASP.NET Core, authentication và authorization là hai bước khác nhau.

Authentication handler đọc credential phù hợp với scheme đã cấu hình, ví dụ bearer token. Handler validate token theo các rule như signature, issuer, audience và lifetime theo configuration. Nếu thành công, application có một `ClaimsPrincipal`; principal này được gán vào `HttpContext.User`.

Sau đó authorization đánh giá endpoint metadata như `[Authorize(Policy = "CanApproveExpense")]`. Policy ở ví dụ yêu cầu claim:

```text
permission = expense.approve
```

Nếu caller không authenticate được và endpoint yêu cầu authorization, framework thường challenge authentication scheme, dẫn đến 401. Nếu caller đã authenticate nhưng policy fail, framework thường forbid, dẫn đến 403.

Vì vậy câu “403 nghĩa là token invalid” là assumption sai. Token có thể valid nhưng user thiếu required permission. Ngược lại, token được frontend chấp nhận không có nghĩa backend phải chấp nhận. Ví dụ frontend có thể đang giữ ID token, hoặc access token có audience của một API khác.

Kế hoạch điều tra production:

1. Lấy một request correlation ID cụ thể.
2. Xác định response là 401 hay 403 và endpoint policy nào được áp dụng.
3. Xác minh request có Authorization header hay không nhưng không ghi raw token vào log.
4. Decode token trong môi trường an toàn để xem `iss`, `aud`, expiry và relevant claims; không coi decode là validation.
5. Xác minh authentication configuration của instance bị lỗi.
6. So sánh token từ user pass và user fail.
7. Kiểm tra claim mapping/normalization giữa tenants/providers.
8. Nếu 403, inspect authorization failure requirement thay vì chỉ kiểm tra token signature.
9. Nếu policy phụ thuộc domain data, thêm explicit resource authorization tests.

Role check trực tiếp trong controller có thể đơn giản cho một số use case, nhưng nếu requirement là capability như `expense.approve`, policy giúp centralize intent và giảm coupling với identity-provider role names. Nếu approval còn phụ thuộc amount hoặc department, policy có thể dùng custom handler:

```csharp
public sealed record ApproveExpenseRequirement()
    : IAuthorizationRequirement;

public sealed class ApproveExpenseHandler
    : AuthorizationHandler<ApproveExpenseRequirement, Expense>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        ApproveExpenseRequirement requirement,
        Expense resource)
    {
        var department = context.User.FindFirst("department")?.Value;
        var canApprove = context.User.HasClaim(
            "permission",
            "expense.approve");

        if (canApprove && department == resource.DepartmentCode)
        {
            context.Succeed(requirement);
        }

        return Task.CompletedTask;
    }
}
```

Nếu permission có thể bị revoke ngay lập tức nhưng token còn sống nhiều phút, claim trong token là snapshot tại thời điểm phát token. Khi requirement không cho phép stale permission, cần server-side authorization state, shorter token strategy hoặc mechanism khác phù hợp threat model; không giả định JWT tự cập nhật sau khi phát hành.

Tài liệu tham khảo:

- Microsoft Learn — ASP.NET Core security and authorization: `https://learn.microsoft.com/aspnet/core/security/authorization/introduction`
- Microsoft Learn — Policy-based authorization in ASP.NET Core: `https://learn.microsoft.com/aspnet/core/security/authorization/policies`

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách authentication khỏi authorization. Authentication xác minh credential và tạo `ClaimsPrincipal`; authorization lấy principal đó rồi đánh giá endpoint policy. Vì vậy 401 thường nghĩa là caller chưa authenticate thành công hoặc bị challenge, còn 403 thường nghĩa là đã authenticate nhưng không đủ quyền.

Việc user login được ở frontend chưa chứng minh token gửi tới API đúng. Em sẽ xác minh đây là access token, kiểm tra issuer, audience, expiry và claim thực tế của request fail. Với 403, em kiểm tra policy requirement và claim mapping chứ không chỉ signature.

Em cũng không đổi ngay sang `IsInRole("Admin")`. Nếu business requirement là quyền approve expense thì policy theo capability rõ hơn; nếu quyền còn phụ thuộc department hoặc resource state thì dùng resource-based authorization/custom handler. Em sẽ thêm integration tests cho 401, 403 và success cases, log failure category + policy + correlation ID nhưng tuyệt đối không log raw bearer token. Nếu quyền phải revoke tức thì, em cũng không dựa hoàn toàn vào long-lived token claims vì chúng là snapshot.”

## Câu hỏi đào sâu

1. Nếu token valid và có claim `expense.approve` nhưng user chỉ được approve expense dưới 10 triệu đồng, bạn sẽ encode rule vào token hay evaluate server-side? Vì sao?
2. Nếu frontend đang gửi ID token và API hiện vẫn “thỉnh thoảng chạy được”, bạn sẽ điều tra configuration/security risk nào?
3. Một teammate đề xuất cache authorization result 30 phút để giảm database lookup. Bạn chấp nhận khi nào và cần invalidation/risk controls gì?

## Lỗi trả lời thường gặp

- Đồng nhất Authentication với Authorization.
- Nói 403 luôn là token invalid.
- Tin rằng login thành công ở frontend đồng nghĩa API token đúng audience.
- Thay mọi policy bằng role `Admin` để “đơn giản”.
- Log full JWT để debug production.

## Thang điểm 0–10

- **0–2:** chỉ nói kiểm tra token/role.
- **3–4:** biết 401 khác 403 nhưng chưa giải thích pipeline và principal.
- **5–6:** giải thích đúng authentication/authorization, claims, policy và investigation flow.

# Câu 2 — Upload file lớn làm App Service memory tăng và 5xx: lỗi ở Azure Blob, ASP.NET Core proxy path hay cách cấp quyền upload?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure App Service, Azure Blob Storage, file streaming, large-file upload, memory pressure, request timeout, Managed Identity, SAS, Azure RBAC, security, failure recovery, Application Insights, production troubleshooting

## Bối cảnh

Một document portal cho phép user upload file lên Azure Blob Storage. API chạy ASP.NET Core trên Azure App Service Linux, nhiều instances.

Implementation hiện tại nhận multipart upload qua backend, đọc toàn bộ file vào memory rồi upload Blob:

```csharp
[Authorize]
[HttpPost("documents")]
public async Task<IActionResult> Upload(
    IFormFile file,
    CancellationToken cancellationToken)
{
    await using var buffer = new MemoryStream();
    await file.CopyToAsync(buffer, cancellationToken);

    buffer.Position = 0;

    var blob = _containerClient.GetBlobClient(
        $"{User.FindFirst("sub")!.Value}/{Guid.NewGuid()}/{file.FileName}");

    await blob.UploadAsync(buffer, overwrite: false, cancellationToken);

    return Ok();
}
```

Hệ thống ổn với file 5–20 MB. Khi business mở limit lên 500 MB, production xuất hiện:

- memory mỗi instance tăng nhanh trong giờ cao điểm;
- p95 upload tăng mạnh;
- một số request bị client disconnect hoặc gateway timeout;
- App Service có restart ở vài thời điểm;
- upload retry của frontend đôi khi tạo orphan blobs hoặc duplicate logical documents;
- một developer đề xuất tăng instance memory;
- developer khác muốn cho browser upload thẳng bằng Storage Account key để bỏ backend bottleneck;
- team chưa có checksum/idempotency key hay upload session record;
- backend hiện dùng Storage connection string chứa account key;
- chưa rõ virus/malware scanning requirement, maximum file size thực tế, supported browser behavior hoặc liệu user có cần resume upload hay không.

## Câu hỏi chính

Bạn đang xử lý incident. Hãy trình bày cách **ổn định hệ thống, thu evidence, xác định bottleneck và redesign upload flow**. So sánh backend-proxy streaming với direct-to-Blob upload bằng limited SAS/user delegation SAS, giải thích vì sao đưa Storage Account key cho browser là không chấp nhận được, và cách thiết kế authorization, idempotency, validation, malware-scanning workflow, failure cleanup và observability cho file lớn.

## Câu hỏi làm rõ nên cân nhắc

1. File size distribution và concurrent uploads thực tế trên mỗi instance là bao nhiêu?
2. Business có cần backend inspect bytes synchronously trước khi upload hoàn tất hay scanning có thể asynchronous/quarantine?
3. Client có yêu cầu resumable/chunked upload và retry ở network không ổn định không?
4. Blob phải private hoàn toàn hay có downstream sharing/download flow nào?
5. Một logical document có cần exactly one active blob hay duplicate physical blob có thể được cleanup theo session state?

## Gợi ý tư duy

### Gợi ý 1

Tách **control plane** của upload khỏi **data plane bytes**. Backend không nhất thiết phải relay toàn bộ payload chỉ để quyết định user có quyền upload.

### Gợi ý 2

Memory spike phải được lượng hóa theo file size × concurrent uploads × buffering behavior trước khi chọn scale-up.

### Gợi ý 3

Direct upload chỉ an toàn khi credential được giới hạn scope, permissions và lifetime; account key không phải browser credential.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact và temporarily constrain risky upload sizes/concurrency.
2. Thu memory/request/dependency telemetry.
3. Phân biệt application buffering, network bottleneck, Blob latency và client retries.
4. Stabilize bằng bounded concurrency/size hoặc temporary rollback limit nếu cần.
5. Chọn proxy streaming hay direct upload theo security/business constraints.
6. Thiết kế upload session/idempotency.
7. Thiết kế validation/quarantine/scanning.
8. Thiết kế authorization bằng Managed Identity/SAS/RBAC phù hợp.
9. Thiết kế cleanup và retry.
10. Test failure paths và load.
11. Monitor production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Copy file lớn vào `MemoryStream` làm application giữ payload lớn trong managed memory; nhiều upload song song có thể khuếch đại memory pressure mạnh.
- Tăng memory chỉ có thể là mitigation tạm thời nếu architecture vẫn buffer payload lớn không giới hạn.
- Storage Account key không được đưa cho browser vì quyền quá rộng và khó giới hạn theo từng upload.
- Backend có thể dùng Managed Identity để gọi Blob Storage thay vì long-lived account key khi deployment/environment hỗ trợ.
- Direct upload có thể dùng SAS có scope, permissions và expiry giới hạn; Microsoft khuyến nghị Microsoft Entra ID/Managed Identity và user delegation SAS khi phù hợp.
- Direct upload không có nghĩa bỏ authorization: backend vẫn phải authorize user trước khi cấp upload capability.
- Retry cần idempotency/session semantics để tránh duplicate logical documents và orphan blobs.
- File upload security phải xét type validation, filename handling, size limit, malware/quarantine và access policy.

### Điểm cộng

- Nếu backend phải proxy, dùng streaming/bounded buffers thay vì copy toàn bộ payload vào memory.
- Tạo server-generated blob path thay vì tin `file.FileName` làm storage key trực tiếp.
- Dùng staged state như `PendingUpload → Uploaded → Scanning → Ready/Rejected`.
- Ghi expected size/content type/hash metadata ở upload session, sau upload verify server-side trước khi publish file.
- Cấp short-lived write-only SAS cho một blob/path cụ thể, không cấp container-wide broad permissions nếu không cần.
- Có cleanup job cho expired sessions/orphan blobs với retention safety margin.

### Senior+

- Phân biệt authentication/authorization của application với authorization trực tiếp của Blob Storage.
- Nhận ra direct-to-Blob giảm App Service bandwidth/memory nhưng làm client orchestration, CORS, retries, chunking và upload-state reconciliation phức tạp hơn.
- Không coi upload “complete” chỉ vì blob bytes tồn tại; business readiness phụ thuộc validation/scanning/metadata commit.
- Có immutable operation ID/idempotency key và state transition chống race giữa retry/callback/scanner.
- Xem scanning service là failure-prone dependency và thiết kế quarantine + retry/DLQ thay vì expose file trước scan.

## Hướng giải quyết tham khảo

### 1. Stabilize

Nếu 500 MB vừa được bật và đang gây restart/5xx, giảm temporary file-size limit hoặc concurrent uploads có thể là biện pháp ổn định nhanh hơn scale-up mù. Đồng thời giữ các upload nhỏ đang hoạt động nếu có thể.

Collect:

- App Service working set/private bytes;
- .NET GC heap/LOH/allocation rate;
- concurrent request count;
- request body size distribution;
- upload duration p50/p95/p99;
- Blob dependency duration/error;
- client disconnect rate;
- restart reason;
- network throughput.

Nếu memory tăng gần tuyến tính với tổng payload đang upload, code `MemoryStream` là hypothesis mạnh nhưng vẫn verify bằng trace/profile.

### 2. Proxy streaming option

Nếu business bắt buộc backend inspect/transform bytes synchronously, backend có thể stream trực tiếp sang Blob thay vì materialize toàn bộ file.

Conceptually:

```csharp
[Authorize]
[HttpPost("documents")]
public async Task<IActionResult> Upload(
    IFormFile file,
    CancellationToken ct)
{
    if (file.Length <= 0 || file.Length > _limits.MaxBytes)
        return BadRequest();

    var userId = User.FindFirst("sub")?.Value;
    if (string.IsNullOrWhiteSpace(userId))
        return Forbid();

    var documentId = Guid.NewGuid();
    var safeBlobName = $"quarantine/{userId}/{documentId}";
    var blob = _containerClient.GetBlobClient(safeBlobName);

    await using var stream = file.OpenReadStream();
    await blob.UploadAsync(stream, cancellationToken: ct);

    await _repository.CreatePendingScanAsync(
        documentId,
        userId,
        safeBlobName,
        file.Length,
        ct);

    return Accepted(new { documentId });
}
```

Đây chỉ là baseline. Cần kiểm tra framework/server multipart buffering settings và request limits; `IFormFile` abstraction không tự bảo đảm end-to-end zero buffering. Với file rất lớn hoặc resumable upload, direct-to-Blob thường đáng cân nhắc hơn.

### 3. Direct upload option

Một flow tốt hơn cho file lớn:

```text
Browser
  → POST /api/upload-sessions
Backend
  → authorize user
  → create UploadSession + server-generated BlobName
  → generate short-lived scoped upload SAS
Browser
  → upload bytes directly to Blob Storage
Browser
  → POST /api/upload-sessions/{id}/complete
Backend
  → verify blob metadata/size/state
  → enqueue scanning
Scanner
  → Ready or Rejected
```

Backend trên Azure có thể authenticate tới Blob bằng Managed Identity. Nếu backend cần cấp delegated client access, user delegation SAS là một option phù hợp khi requirements cho phép. SAS phải giới hạn:

- blob/resource scope;
- write/create permissions cần thiết;
- short expiry;
- HTTPS;
- expected path controlled bởi server.

Không gửi Storage Account key xuống browser.

Microsoft Learn hiện khuyến nghị Microsoft Entra ID với Managed Identity khi có thể; khi dùng SAS, user delegation SAS được ưu tiên hơn account-key-signed SAS trong nhiều scenarios.

Tài liệu tham khảo:

- Microsoft Learn — Authorize access to blobs using Microsoft Entra ID: `https://learn.microsoft.com/azure/storage/blobs/authorize-access-azure-active-directory`
- Microsoft Learn — Create a user delegation SAS: `https://learn.microsoft.com/azure/storage/blobs/storage-blob-user-delegation-sas-create-dotnet`

### 4. Idempotency và state

Tạo `UploadSession`:

```text
UploadSession
- Id
- UserId
- BlobName
- Status
- ExpectedSize
- ExpectedHash? 
- CreatedAt
- ExpiresAt
- CompletedAt
```

Client retry `create session` có thể dùng idempotency key. Complete endpoint phải idempotent. Scanner cũng phải xử lý lại an toàn.

Nếu client upload thành công nhưng mất network trước `complete`, reconciliation job có thể detect blob của expired/pending session, verify hoặc cleanup theo policy.

### 5. Security

- container private;
- server-generated blob names;
- không trust extension/MIME từ client như security proof;
- enforce size limit ở application/storage flow;
- quarantine trước scan;
- download chỉ từ `Ready` state;
- avoid path traversal semantics từ user filename;
- preserve original display filename riêng trong metadata/database sau sanitization;
- principle of least privilege cho Managed Identity/RBAC.

### 6. Testing

- 500 MB upload với N concurrent clients theo expected peak;
- client disconnect ở 25%, 80%, 99%;
- duplicate `complete` requests;
- expired SAS;
- Blob transient 5xx/timeout;
- scanner unavailable;
- malicious filename/content-type mismatch;
- orphan cleanup và retry race.

## Mẫu trả lời trong phỏng vấn

“Em sẽ stabilize trước bằng cách giảm temporary size/concurrency nếu release 500 MB đang gây restart. Sau đó em correlate upload size và concurrency với working set, GC/LOH, request duration và Blob dependency. Code hiện tại copy toàn file vào MemoryStream nên 10 upload 500 MB có thể tạo memory pressure rất lớn trước cả overhead khác.

Nếu backend không cần inspect toàn bộ bytes synchronously, em tách control plane khỏi data plane: backend authorize user, tạo upload session và server-generated blob path, rồi cấp short-lived scoped SAS để browser upload trực tiếp. Backend itself dùng Managed Identity/RBAC thay vì connection string account key. Em tuyệt đối không đưa account key cho browser.

Sau upload, backend verify session/blob rồi đưa file vào quarantine/scanning; chỉ `Ready` mới được download. Session + idempotency key xử lý retries và orphan cleanup. Nếu backend bắt buộc proxy, em stream với bounded buffers thay vì materialize toàn payload.

Em load-test concurrency thật, inject disconnect/Blob/scanner failures và monitor working set, GC, upload p95/p99, failure rate, orphan count, scan backlog và App Service restarts.”

## Câu hỏi đào sâu

1. Nếu security yêu cầu virus scan trước khi bất kỳ byte nào được persisted vào primary storage, direct upload architecture phải thay đổi thế nào?
2. Nếu user delegation SAS bị cấp 15 phút nhưng upload 500 MB trên mạng di động kéo dài 25 phút, bạn thiết kế renewal/resume thế nào mà không mở quyền quá rộng?
3. Một teammate nói “direct-to-Blob giải quyết hết scalability nên backend không cần lưu UploadSession”. Bạn phản biện ra sao?

## Lỗi trả lời thường gặp

- Chỉ tăng App Service memory mà không đo buffering/concurrency.
- Gửi Storage Account key xuống frontend.
- Cho rằng direct upload nghĩa là không cần backend authorization.
- Không thiết kế retry/idempotency nên tạo duplicate/orphan blobs.
- Expose file ngay sau upload mà bỏ qua scanning/validation requirement.

## Thang điểm 0–10

- **0–2:** chỉ scale App Service hoặc tăng timeout.
- **3–4:** nhận ra MemoryStream issue nhưng security/retry design còn thiếu.
- **5–6:** có streaming/direct upload, scoped SAS, Managed Identity và basic upload state.
- **7–8:** có quarantine, idempotency, cleanup, failure tests và telemetry.
- **9–10:** phân tích control/data plane, resumability, permission scope, ambiguous completion và chọn proxy/direct architecture conditional theo security/business constraints.

# Câu 3 — Modernize .NET Framework 4.5 monolith lên modern .NET: big-bang rewrite hay incremental migration với shared database?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET Framework 4.5, ASP.NET MVC, modern .NET, ASP.NET Core, migration strategy, backward compatibility, IIS, Windows Server, Azure App Service, architecture boundaries, shared database, API contracts, rollout, rollback, testing, observability, AI-assisted modernization

## Bối cảnh

Một enterprise management portal đã chạy hơn 8 năm trên:

- .NET Framework 4.5;
- ASP.NET MVC 5;
- IIS/Windows Server;
- SQL Server dùng chung cho khoảng 25 business modules;
- nhiều stored procedures;
- một số libraries nội bộ phụ thuộc `System.Web`;
- authentication/session phụ thuộc legacy pipeline;
- frontend gồm Razor + jQuery + một ít Angular cũ;
- nightly jobs chạy trong cùng application/process;
- deployment qua TeamCity + Octopus Deploy;
- production có nhiều integrations với CRM, file shares và internal APIs.

Business muốn modernize lên modern .NET/ASP.NET Core để giảm technical debt và dễ cloud hosting hơn. Leadership đưa hai đề xuất:

**Option A:** dừng feature development 9 tháng, rewrite toàn bộ sang .NET 10 + React + microservices + Kubernetes.

**Option B:** tiếp tục maintain system hiện tại, migrate từng capability/module theo giai đoạn, chấp nhận một khoảng thời gian legacy và modern application cùng tồn tại.

Constraints:

- hệ thống không thể downtime dài;
- team 8 developers vẫn phải giao business features;
- test automation hiện chưa tốt;
- database schema có nhiều coupling giữa modules;
- một số third-party libraries chưa rõ compatibility;
- business chưa yêu cầu Kubernetes;
- một số module ổn định, ít thay đổi;
- một số module đang phát triển mạnh;
- security/supportability của .NET Framework version cũ là concern;
- chưa có inventory đầy đủ về dependencies, traffic, critical workflows hay code ownership.

Microsoft documentation hiện mô tả incremental side-by-side migration là một lựa chọn cho ASP.NET applications phức tạp; đồng thời .NET Upgrade Assistant cũ đã được đánh dấu deprecated trong tài liệu hiện hành, nên tooling không được coi là strategy tự thân.

## Câu hỏi chính

Hãy đề xuất modernization strategy thực tế cho hệ thống này. Bạn cần quyết định **migration sequencing, application boundaries, routing giữa legacy/modern app, database strategy, authentication/session transition, background jobs, testing, observability, deployment và rollback**. So sánh big-bang rewrite với incremental migration, giải thích khi nào shared database tạm thời chấp nhận được, khi nào cần tách data ownership, và vì sao “modern .NET + microservices + Kubernetes” không phải một quyết định duy nhất.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào có business change rate cao, incident rate cao và dependency coupling thấp nhất để làm migration candidate đầu tiên?
2. Có endpoint/UI boundary nào có thể route độc lập mà không cần shared in-process session không?
3. Stored procedures và schema nào được nhiều modules cùng write, và transaction boundaries hiện nằm ở đâu?
4. Authentication hiện tại có thể được externalize/standardize trước migration hay phụ thuộc sâu vào System.Web/session?
5. RTO/RPO, acceptable rollback time và yêu cầu coexistence old/new versions là gì?

## Gợi ý tư duy

### Gợi ý 1

Modernization là bài toán **risk reduction và boundary discovery**, không chỉ là đổi target framework.

### Gợi ý 2

Chọn migration slice dựa trên coupling, business value, operational risk và khả năng rollback; không nhất thiết bắt đầu từ module lớn nhất.

### Gợi ý 3

Shared database có thể là migration bridge, nhưng nếu không có ownership rules nó dễ biến “side-by-side” thành distributed monolith khó thoát.

## Cấu trúc trả lời đề xuất

1. Inventory và baseline current system.
2. Xác định business/technical migration goals.
3. Chọn migration shape: in-place, side-by-side, module extraction hoặc combination.
4. Xác định routing/coexistence boundary.
5. Xử lý authentication/session.
6. Xử lý database ownership/compatibility.
7. Tách background jobs khỏi web lifecycle khi phù hợp.
8. Thiết kế testing/observability trước migration lớn.
9. Plan rollout/canary/rollback.
10. Xác định criteria để App Service/container/Kubernetes hoặc microservices trở nên justified.
11. Dùng AI/tooling cho inventory/refactoring nhưng verify deterministically.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không bắt đầu bằng rewrite toàn bộ nếu chưa inventory dependencies, workflows, data coupling và test coverage.
- Big-bang rewrite có risk cao về requirement drift, hidden behavior và long feedback cycle.
- Incremental migration cho phép giảm blast radius và tạo rollback path tốt hơn khi boundaries đủ rõ.
- Shared database có thể chấp nhận tạm thời trong coexistence, nhưng cần explicit table/schema ownership và backward-compatible changes.
- Không để hai applications tự do write cùng domain tables theo semantics khác nhau nếu không có contract.
- Authentication/session là cross-cutting dependency cần giải quyết sớm; route endpoint nhưng vẫn phụ thuộc in-memory legacy session có thể phá migration boundary.
- Background jobs không nên mặc định tiếp tục chạy ở cả old và new app sau scale/migration; phải có single ownership/idempotency.
- Microservices và Kubernetes là decisions riêng, chỉ chọn khi scale, ownership, deployment hoặc operational requirements justify complexity.
- Testing và observability phải được tăng trước hoặc song song migration, không chờ sau cùng.

### Điểm cộng

- Dùng strangler/side-by-side routing cho selected endpoints/modules.
- Bắt đầu từ vertical slice có business value nhưng manageable coupling để học migration mechanics.
- Tạo compatibility layer/adapters quanh System.Web-specific dependencies thay vì copy chúng sang modern code.
- Dùng expand/contract DB changes trong coexistence window.
- Có contract tests cho external integrations và characterization tests cho legacy behavior trước refactor.
- Tách scheduler/background work thành Worker Service/Functions chỉ khi lifecycle/reliability requirements phù hợp.

### Senior+

- Xem modernization thành portfolio các decisions: runtime upgrade, web framework migration, frontend modernization, hosting, architecture decomposition và data ownership có thể có tốc độ khác nhau.
- Không buộc React rewrite vào backend migration nếu Razor/jQuery page ổn định chưa tạo risk/value đủ lớn.
- Định nghĩa “migration complete” theo operational/business outcomes, không theo số project đổi target framework.
- Có telemetry so sánh old/new paths cùng business operation để detect semantic drift.
- Thiết kế decommission criteria rõ cho legacy path để tránh permanent dual-stack.

## Hướng giải quyết tham khảo

### 1. Inventory trước khi chọn architecture

Tạo migration inventory:

```text
Module
- business criticality
- change frequency
- incident frequency
- request volume
- System.Web dependency
- DB tables/SPs owned/read/written
- external integrations
- session dependency
- background jobs
- automated test coverage
- candidate boundary
```

Dependency graph này giúp chọn slice thay vì đoán.

### 2. Big-bang vs incremental

Big-bang có thể phù hợp nếu system nhỏ, requirements ổn định, thời gian chấp nhận freeze và migration surface thấp. Scenario này ngược lại: 25 modules, shared DB, 8 năm hidden behavior, test automation yếu và business vẫn cần features. Vì vậy incremental side-by-side thường có risk profile tốt hơn.

Một target architecture giai đoạn đầu có thể rất đơn giản:

```text
Client
  → Reverse proxy / routing layer
      → Modern ASP.NET Core app   (/new-capabilities, migrated routes)
      → Legacy ASP.NET MVC app    (remaining routes)

SQL Server
  → temporarily shared with explicit ownership rules
```

Không cần microservices để làm side-by-side migration.

Microsoft Learn hiện mô tả side-by-side incremental upgrading cho complicated ASP.NET applications, trong đó modern .NET project chạy cạnh legacy application và endpoints được migrate dần. Tooling có thể hỗ trợ nhưng migration plan vẫn phải dựa vào application-specific dependencies.

Tài liệu tham khảo:

- Microsoft Learn — Upgrade .NET apps overview: `https://learn.microsoft.com/dotnet/core/porting/`
- Microsoft Learn — .NET Upgrade Assistant overview: `https://learn.microsoft.com/dotnet/core/porting/upgrade-assistant-overview`

Theo tài liệu Microsoft cập nhật năm 2026, .NET Upgrade Assistant được đánh dấu deprecated và Microsoft hướng người dùng sang modernization tooling mới. Vì vậy không nên xây migration governance quanh assumption một tool cụ thể sẽ tự động giải quyết compatibility.

### 3. Chọn slice đầu tiên

Không chọn “module dễ nhất” hoặc “module lớn nhất” một cách máy móc. Candidate tốt thường có:

- boundary có thể route riêng;
- dependency vừa phải;
- business value đủ để justify;
- telemetry có thể so sánh;
- rollback rõ;
- team học được migration mechanics.

Ví dụ migrate read-heavy reporting module trước nếu nó ít transaction coupling, nhưng nếu reporting dựa trên shared session sâu thì có thể không phải candidate tốt.

### 4. Authentication và session

Nếu legacy dùng Forms Authentication/System.Web session/in-process state, cần plan cross-app identity.

Một direction là externalize authentication sang identity provider/common token/cookie mechanism phù hợp, nhưng exact approach phụ thuộc constraints. Không nên “share Session object” giữa ASP.NET Framework và ASP.NET Core như migration strategy mặc định.

Giảm server-side session dependency dần. State quan trọng nên chuyển về explicit database/cache/application contracts, nhưng chỉ khi business semantics rõ.

### 5. Database coexistence

Shared DB bridge có thể chấp nhận nếu:

- schema changes backward-compatible;
- ownership table/aggregate rõ;
- new app không bypass invariants legacy đang enforce trong code;
- migration has finite lifetime.

Ví dụ:

```text
Legacy owns: Orders write path
Modern app: read-only projection initially
```

Sau khi migrate business write logic và tests:

```text
Modern owns: Orders write path
Legacy calls modern API or becomes read-only
```

Tránh trạng thái cả hai apps cùng write cùng aggregate với business rules khác nhau.

Schema changes trong coexistence nên expand/contract:

1. add compatible structure;
2. deploy code hiểu cả old/new representation nếu cần;
3. backfill;
4. switch ownership;
5. remove legacy schema sau khi old consumers gone.

### 6. Background jobs

Legacy jobs đang chạy trong web app là migration risk. Inventory từng job:

- trigger semantics;
- idempotency;
- concurrency;
- transaction boundary;
- restart behavior;
- SLA.

Không copy job sang modern app rồi chạy song song. Từng job phải có single active owner hoặc distributed/idempotent coordination phù hợp. Một số jobs có thể chuyển sang Worker Service/Functions, nhưng không phải tất cả chỉ vì “cloud native”.

### 7. Testing

Trước mỗi migration slice:

- characterization tests cho behavior cũ;
- integration tests với SQL/stored procedures;
- contract tests cho external APIs;
- security tests cho auth transition;
- Playwright cho vài critical user journeys;
- migration/rollback validation;
- load test nếu runtime/hosting behavior thay đổi.

AI có thể hỗ trợ inventory, tìm System.Web usage, draft characterization tests và classify dependencies. Nhưng generated findings phải grounded bằng repository search/build/tests; không chấp nhận hallucinated compatibility claims.

### 8. Deployment và rollback

Mỗi migrated slice cần:

- feature/routing switch;
- health check;
- correlation ID xuyên old/new paths;
- version telemetry;
- canary hoặc limited user rollout khi có thể;
- rollback bằng routing switch nếu DB state còn compatible;
- explicit rule cho irreversible data migrations.

### 9. Hosting

ASP.NET Core app có thể chạy trên App Service trước nếu requirements phù hợp. Container/Kubernetes chỉ nên xem xét khi có clear need về orchestration, portability, scaling patterns hoặc platform standards. Chuyển từ IIS/Windows sang App Service/Linux là một migration dimension khác với domain decomposition; không cần làm mọi thứ cùng một release.

### 10. Decommission legacy

Đặt exit criteria cho mỗi module:

- all traffic moved;
- data ownership moved;
- jobs moved;
- operational dashboards stable;
- rollback window passed;
- legacy endpoint disabled;
- dependencies removed;
- documentation updated.

Nếu không có decommission criteria, side-by-side dễ trở thành trạng thái vĩnh viễn.

## Mẫu trả lời trong phỏng vấn

“Với hệ thống 25 modules, shared SQL và test automation yếu, em sẽ không gắn modernization với big-bang rewrite + React + microservices + Kubernetes. Đây là nhiều decisions khác nhau và mỗi decision phải có value/risk riêng.

Em bắt đầu bằng inventory dependency, database writes, System.Web/session, jobs và critical journeys. Sau đó chọn một vertical slice có boundary route được, business value đủ và rollback rõ. Modern ASP.NET Core app chạy side-by-side với legacy app; reverse proxy route những endpoints đã migrate. Shared DB có thể là bridge tạm thời nhưng phải có explicit ownership và backward-compatible schema; em không để old/new apps cùng write một aggregate với rules khác nhau.

Auth/session là dependency cần xử lý sớm, background jobs phải có single owner để tránh duplicate execution. Trước mỗi slice em thêm characterization/integration/security tests, correlation + version telemetry, canary/routing switch và rollback plan.

Em chỉ tách microservice khi domain ownership, independent scale/release hoặc failure isolation justify nó; Kubernetes cũng chỉ chọn khi orchestration need justify operational cost. Mục tiêu là giảm risk và decommission legacy từng phần, không phải đổi thật nhiều công nghệ trong một lần.”

## Câu hỏi đào sâu

1. Nếu hai modules có transaction SQL xuyên cùng 12 tables và không thể tách trong ngắn hạn, bạn vẫn ép chúng thành hai services trong migration đầu không? Vì sao?
2. Nếu leadership yêu cầu “100% React” nhưng 60% Razor pages ổn định và gần như không thay đổi, bạn sẽ ưu tiên modernization budget thế nào?
3. Nếu migrated endpoint cần rollback nhưng đã ghi data theo schema mới mà legacy code không hiểu, bạn thiết kế rollout trước đó thế nào để giữ rollback khả thi?

## Lỗi trả lời thường gặp

- Đồng nhất modern .NET với microservices/Kubernetes/frontend rewrite.
- Chọn big-bang rewrite mà không tính hidden behavior và long feedback cycle.
- Cho old/new applications cùng write shared tables mà không xác định ownership.
- Copy background jobs sang app mới trước khi disable/coordinate app cũ.
- Tin migration tool/AI output mà không build, test và verify compatibility.

## Thang điểm 0–10

- **0–2:** chỉ đề xuất rewrite hoặc “nâng framework”.
- **3–4:** hiểu incremental migration nhưng boundary/data/auth plan còn mơ hồ.
- **5–6:** có inventory, side-by-side routing, DB compatibility, testing và rollback.
- **7–8:** có ownership transitions, job/auth strategy, telemetry và evolutionary deployment.
- **9–10:** tách rõ runtime/framework/frontend/hosting/service decomposition decisions, quản lý irreversible state changes và định nghĩa measurable decommission criteria.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication trả lời identity; Authorization quyết định principal có quyền thực hiện hành động hay không. 401 và 403 phản ánh failure semantics khác nhau.
- “Frontend login thành công” không chứng minh access token hợp lệ cho backend API.
- Large-file upload cần kiểm soát buffering, concurrency và credential scope; direct-to-Blob có thể giảm App Service pressure nhưng phải có authorization, upload state và failure recovery.
- Managed Identity/RBAC phù hợp cho service-to-service Azure access; browser không được nhận Storage Account key.
- Modernization nên chia nhỏ theo boundary và risk. Runtime upgrade, frontend rewrite, microservices, Kubernetes và hosting migration là các decisions độc lập.
- Shared database có thể là migration bridge, nhưng phải có ownership và backward-compatible change strategy.

## Mẫu tư duy cần nhớ

- **Separate identity from permission, then inspect evidence at each boundary.**
- **Separate control plane from large data transfer when it reduces operational risk.**
- **Treat retries as state transitions that require idempotency and reconciliation.**
- **Modernize incrementally around explicit ownership boundaries.**
- **Do not bundle unrelated complexity into one architecture decision.**
