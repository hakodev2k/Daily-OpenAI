# Câu 1 — HTTP cancellation, timeout và vòng đời tài nguyên trong ASP.NET Core

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, CancellationToken, HttpClient, EF Core, resource lifetime, observability.

## Bối cảnh

API .NET 8 phục vụ tra cứu báo cáo đơn hàng. Endpoint nhận `CancellationToken`, truy vấn PostgreSQL qua EF Core, rồi gọi dịch vụ định giá qua `HttpClient`. Khi trình duyệt đóng tab, Application Insights vẫn ghi nhận nhiều outbound request chạy lâu. Sau một đợt traffic tăng, p99 latency tăng và connection pool thường xuyên bận. Chưa rõ timeout đặt ở proxy, HttpClient hay database; chưa rõ truy vấn và outbound call chạy tuần tự hay song song.

## Câu hỏi chính

Giải thích từ HTTP disconnect đến `HttpContext.RequestAborted`, propagation của `CancellationToken`, cơ chế cancellation trong EF Core và `HttpClient`; chỉ ra vì sao request phía server có thể tiếp tục chạy và cách chứng minh nguyên nhân bằng telemetry thay vì đoán.

## Câu hỏi làm rõ nên cân nhắc

1. Token có được truyền xuyên qua controller, service, EF Core và `SendAsync` không?
2. Client disconnect hay gateway timeout, và có phân biệt được hai trường hợp không?
3. Provider database, driver và external API có hỗ trợ cancellation ở mức nào?
4. Có retry policy, background fire-and-forget hoặc timeout độc lập nào không?

## Gợi ý tư duy

### Gợi ý 1
Cancellation là tín hiệu hợp tác, không phải lệnh giết thread.

### Gợi ý 2
Theo dấu token và thời điểm bắt đầu/kết thúc của từng dependency call.

### Gợi ý 3
Phân biệt timeout budget của request với timeout từng dependency và việc giải phóng connection.

## Cấu trúc trả lời đề xuất

1. Làm rõ symptom và boundaries.
2. Mô tả cơ chế signal/cancellation.
3. Lập sơ đồ token propagation và dependency timing.
4. Đưa ra các giả thuyết có thể kiểm chứng.
5. Thiết kế timeout budget, cleanup và telemetry.
6. Thử nghiệm disconnect, timeout, overload.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `RequestAborted` được signal khi request bị hủy/connection bị ngắt theo cơ chế server; không bảo đảm mọi thao tác lập tức dừng.
- `await` không tự hủy I/O; cần truyền token và dependency phải hỗ trợ.
- Phân biệt `OperationCanceledException` do request abort với dependency timeout; không gộp tất cả thành lỗi 500.
- Dùng tracing để tìm dependency nào không tuân thủ cancellation.

### Điểm cộng
- Timeout budget tổng thể, `CancellationTokenSource.CreateLinkedTokenSource`, cleanup bằng `using`/`await using`.
- Cân nhắc idempotency nếu downstream đã thực hiện side effect trước khi caller hủy.

### Senior+
- Chỉ ra cancellation không rollback side effect đã commit và không thay thế backpressure, rate limiting, bulkhead.
- Đề xuất đo active database connections, HTTP connections, in-flight requests và latency distribution.

## Hướng giải quyết tham khảo

Giả định request thông thường cần kết quả đồng bộ, không phải job dài hạn. Khi client disconnect, ASP.NET Core có thể signal `HttpContext.RequestAborted`. Framework không thể cưỡng bức chấm dứt arbitrary work. Nếu service tạo `CancellationToken.None`, quên truyền token cho `ToListAsync(token)`, hoặc gọi `HttpClient.SendAsync(request)` mà không truyền token, downstream có thể tiếp tục. Ngay cả khi truyền token, driver/server có thể cần thời gian để nhận và thực thi cancel; kết quả không được coi là atomic rollback.

Một luồng phù hợp:

```csharp
app.MapGet("/reports/{id:guid}", async (
    Guid id, AppDbContext db, IHttpClientFactory factory,
    HttpContext http) =>
{
    using var budget = CancellationTokenSource
        .CreateLinkedTokenSource(http.RequestAborted);
    budget.CancelAfter(TimeSpan.FromSeconds(8));
    var ct = budget.Token;

    var report = await db.Reports.AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new { x.Id, x.Total })
        .SingleOrDefaultAsync(ct);
    if (report is null) return Results.NotFound();

    using var request = new HttpRequestMessage(
        HttpMethod.Get, $"prices/{id}");
    using var response = await factory.CreateClient("pricing")
        .SendAsync(request, HttpCompletionOption.ResponseHeadersRead, ct);
    response.EnsureSuccessStatusCode();
    var price = await response.Content
        .ReadFromJsonAsync<decimal>(cancellationToken: ct);
    return Results.Ok(new { report.Id, report.Total, Price = price });
});
```

Ví dụ giả định `pricing` có BaseAddress hợp lệ, endpoint trả JSON decimal và không có side effect; trong hệ thống thực tế cần xác thực, kiểm tra schema và quyết định response lỗi phù hợp. Không nhất thiết đặt `CancelAfter(8s)` nếu đã có end-to-end deadline đáng tin cậy; tránh timeout chồng chéo khó chẩn đoán. `HttpClient.Timeout` cũng là nguồn cancellation riêng và cần phân biệt trong logging.

Instrument request span, dependency spans, elapsed time, cancellation reason (nếu xác định được), DB pool saturation, HTTP pending connections. Không log token hay dữ liệu nhạy cảm. Test đóng tab trước/trong DB query và HTTP call, giả lập provider chậm, đo xem active work có giảm. Nếu client hủy sau khi external side effect thành công, thiết kế idempotency/reconciliation riêng.

**Trade-offs:** timeout ngắn giảm tài nguyên bị giữ nhưng tăng false timeout; cancellation sâu làm API phức tạp hơn; background work phải có queue bền vững, không dùng `Task.Run` fire-and-forget để né request lifecycle.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ kiểm tra xem `RequestAborted` có được truyền tới từng dependency hay không, thay vì mặc định đóng tab sẽ hủy toàn bộ server work. Cancellation trong .NET là cooperative: `await` không tự động hủy query hoặc HTTP call. Tôi sẽ đối chiếu request trace với dependency duration và số connection đang hoạt động để tìm nơi token bị bỏ qua hoặc provider phản hồi chậm. Sau đó tôi áp dụng deadline hợp lý, truyền token nhất quán, dispose response và kiểm thử disconnect/timeout dưới tải. Nếu một downstream call tạo side effect, cancellation không đảm bảo rollback nên cần idempotency hoặc reconciliation.”

## Câu hỏi đào sâu

1. Nếu `HttpClient.Timeout` và request cancellation xảy ra gần nhau, phân loại lỗi như thế nào?
2. Khi DB command đã gửi nhưng token bị cancel, có thể khẳng định transaction đã rollback không?
3. Khi nào nên chuyển endpoint sang async job thay vì kéo dài HTTP timeout?

## Lỗi trả lời thường gặp

- Cho rằng `async/await` tự hủy toàn bộ work.
- Catch `OperationCanceledException` rồi trả 500 hoặc retry vô điều kiện.
- Đặt timeout lớn hơn mà không đo bottleneck.
- Bỏ qua side effect đã xảy ra sau khi caller hủy.

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ yêu cầu và giả định | 1 |
| Cơ chế cancellation chính xác | 2 |
| Độ sâu runtime và dependency | 2 |
| Điều tra bằng evidence | 2 |
| Trade-offs và production readiness | 2 |
| Diễn đạt rõ ràng | 1 |

# Câu 2 — Playwright E2E thất bại sau triển khai nhưng API health vẫn xanh

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** React, Playwright, Azure App Service, deployment slots, authentication, browser/network debugging, incident response.

## Bối cảnh

Cổng đặt lịch dùng React frontend, ASP.NET Core API và Microsoft Entra ID. Sau một release, tỷ lệ hoàn tất đặt lịch giảm 18% trong 30 phút. Health check API vẫn 200; Playwright E2E ở môi trường staging thỉnh thoảng timeout sau redirect login. Một số người dùng thấy spinner vô hạn; số khác đặt lịch thành công. Deployment dùng Azure App Service slot swap và CDN cho static assets. Chưa rõ cookie policy, API CORS, cache headers và frontend build artifact có đồng nhất hay không.

## Câu hỏi chính

Bạn là incident lead: sẽ ổn định hệ thống, thu thập bằng chứng, phân biệt các giả thuyết về frontend/auth/CDN/deployment và xác nhận remediation như thế nào mà không biến một Playwright timeout thành kết luận root cause?

## Câu hỏi làm rõ nên cân nhắc

1. 18% giảm tính theo funnel nào, phân đoạn browser/region/version ra sao?
2. Có rollback artifact và database migration tương thích ngược không?
3. Playwright chạy cùng domain, cookie, identity tenant và CDN path với production không?
4. Có correlation ID nối browser request tới API, identity redirect và dependency telemetry?
5. Lỗi chỉ xuất hiện với session cũ hay cả incognito?

## Gợi ý tư duy

### Gợi ý 1
Business impact và stabilization trước root-cause analysis.

### Gợi ý 2
So sánh phiên bản asset, cookie, redirect, network waterfall và API trace.

### Gợi ý 3
Xác định ranh giới cache/CDN, slot settings và auth callback; test từng giả thuyết độc lập.

## Cấu trúc trả lời đề xuất

1. Xác nhận impact, blast radius và incident ownership.
2. Freeze rollout; chọn rollback/traffic mitigation theo khả năng tương thích.
3. Thu thập RUM, browser errors, HAR, Playwright trace, App Insights.
4. Nêu ít nhất ba giả thuyết cạnh tranh.
5. Thiết kế phép thử bác bỏ từng giả thuyết.
6. Khắc phục, verify funnel, giao tiếp và postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không đồng nhất health check 200 với user journey thành công.
- Đề xuất rollback có điều kiện; tránh rollback schema không tương thích.
- So sánh failed/successful sessions bằng network waterfall và correlation IDs.
- Đưa ra nhiều giả thuyết và phép thử độc lập.

### Điểm cộng
- Phân tích cached HTML tham chiếu chunk cũ, cookie SameSite/Secure, redirect URI, CORS, slot-specific settings.
- Phân biệt flaky test do test harness với regression thực tế.

### Senior+
- Xây dựng release gates bằng synthetic journey, canary, error budget và automated rollback có guardrails.
- Giải thích trade-off giữa CDN purge, immutable hashed assets và backward-compatible deploy.

## Hướng giải quyết tham khảo

**Impact:** xác thực số lượt bắt đầu/hoàn tất booking, conversion theo browser, geo, build version, auth status; đánh giá số booking có thể đã tạo nhưng UI không hiển thị. Đặt incident severity theo ảnh hưởng thực tế.

**Stabilize:** dừng rollout, bảo toàn logs/traces; cân nhắc swap back nếu frontend/API/schema tương thích. Nếu có migration phá vỡ tương thích, ưu tiên forward fix hoặc routing mitigation thay vì rollback mù quáng. Cung cấp status update rõ ràng cho support và Product.

**Evidence:** từ Playwright lấy trace, screenshot, console errors, request/response, redirect chain, cookies (chỉ metadata an toàn), version của HTML và JS chunks. Từ production lấy browser telemetry, API 4xx/5xx, login callback error, dependency spans, cache status, deployment events. Correlate session qua opaque request ID; không log authorization codes, access tokens hoặc PII.

**Giả thuyết A — mixed assets:** HTML cũ trỏ tới JS chunk đã bị xóa. Kiểm tra 404 chunk và cache headers; so sánh asset hashes theo region. Fix bằng immutable hashed assets, giữ phiên bản cũ đủ lâu, HTML cache ngắn/revalidation thích hợp; purge có kiểm soát.

**Giả thuyết B — authentication configuration:** slot swap thay đổi redirect URI, domain, cookie settings hoặc secrets không được đánh dấu slot-specific. Kiểm tra login callback failures và effective configuration không tiết lộ secrets; test session mới/cũ, Safari/Chrome.

**Giả thuyết C — frontend race/state:** React effect xử lý redirect hoặc booking promise sai, dẫn tới spinner không kết thúc; test slow network, expired token, concurrent navigation; dùng error boundary và explicit loading/error state.

**Giả thuyết D — API incompatibility:** frontend gọi contract mới nhưng backend instance còn version cũ; kiểm tra version headers, OpenAPI contract tests, rollout timeline.

Chỉ tuyên bố root cause sau khi có chứng cứ tái hiện và chứng minh fix. Verify bằng production canary, conversion recovery, auth success rate, JS error rate, p95 booking journey và Playwright test có dữ liệu cô lập. Chạy postmortem không đổ lỗi cá nhân.

**Trade-offs:** purge CDN nhanh nhưng có thể tăng origin load; rollback nhanh nhưng rủi ro khi schema đã thay đổi; Playwright E2E có chi phí bảo trì và không thay thế contract tests hoặc real-user monitoring.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xem đây là incident ảnh hưởng conversion, không phải chỉ là test Playwright bị flaky. Đầu tiên đo phạm vi ảnh hưởng, dừng rollout và đánh giá khả năng rollback an toàn. Sau đó nối browser console/network với API traces và deployment timeline. Tôi ưu tiên kiểm tra mixed CDN assets, redirect/cookie configuration và frontend race condition vì mỗi giả thuyết có bằng chứng riêng. Health endpoint 200 không chứng minh login-to-booking journey hoạt động. Chỉ khi tái hiện và xác minh remediation bằng canary, synthetic test và funnel metric tôi mới đóng incident.”

## Câu hỏi đào sâu

1. Nếu rollback slot nhưng booking vẫn lỗi trên một số browser, bạn làm gì tiếp?
2. Có nên purge toàn bộ CDN ngay lập tức không? Vì sao?
3. Thiết kế Playwright tests thế nào để tránh false alarm do identity provider và test data?

## Lỗi trả lời thường gặp

- Khẳng định root cause là CDN khi chưa có evidence.
- Coi Playwright timeout là bằng chứng API hỏng.
- Rollback bất chấp migration compatibility.
- Chỉ đo API 5xx, bỏ qua client-side failure.
- Log token/cookie để debug.

## Thang điểm 0–10

| Tiêu chí | Điểm |

| Stabilization an toàn | 2 |
| Evidence và competing hypotheses | 2 |

# Câu 3 — Thiết kế upload tài liệu lớn: Blob Storage, metadata và kiểm duyệt

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, ASP.NET Core, PostgreSQL, Managed Identity, Azure Service Bus, security, consistency, deployment.

## Bối cảnh

Nền tảng nội bộ cho phép nhân viên upload PDF và hình ảnh 20 MB–2 GB. File chỉ được tải xuống sau khi qua malware scanning và kiểm duyệt metadata. Người dùng có thể mất kết nối giữa upload; cùng một file có thể được gửi lại. Hệ thống đang chạy ASP.NET Core trên Azure App Service, metadata ở PostgreSQL. Team cân nhắc (A) proxy toàn bộ byte qua API, (B) direct-to-Blob bằng SAS ngắn hạn, (C) chuyển sang một microservice riêng. Chưa có số lượng upload/giây, yêu cầu residency hoặc SLA scanning.

## Câu hỏi chính

Hãy thiết kế end-to-end upload, finalize, scanning, publish và download với state machine, security boundary và failure recovery; so sánh ba lựa chọn triển khai và nêu điều kiện khiến bạn đổi quyết định.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent uploads, file size distribution và băng thông ở từng vùng?
2. Ai được upload/download; cần audit, retention, legal hold hoặc residency?
3. File chưa scan có được preview không; SLA scanning là bao lâu?
4. Có yêu cầu resumable upload, checksum, deduplication và versioning không?
5. File có chứa dữ liệu nhạy cảm và malware engine có giới hạn kích thước không?

## Gợi ý tư duy

### Gợi ý 1
Tách data plane (bytes) và control plane (authorization/state).

### Gợi ý 2
Upload hoàn tất không đồng nghĩa file đã được phép download.

### Gợi ý 3
Thiết kế state transitions, idempotent finalize, retry và cleanup orphan blobs.

## Cấu trúc trả lời đề xuất

1. Chốt security/scale assumptions.
2. Định nghĩa API và state machine.
3. Phân định quyền truy cập Blob và metadata ownership.
4. Chọn upload transport và xử lý partial failure.
5. Thiết kế scan, retry, poison và reconciliation.
6. So sánh cost/complexity, rollout, test và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không public Blob trước khi scan/authorize.
- State machine rõ ràng, finalize idempotent, verify blob properties.
- Quyền upload hạn chế theo blob name, permission, expiry; backend kiểm tra identity.
- Recovery cho uploaded-but-not-finalized và scanned-but-not-published.

### Điểm cộng
- Block Blob chunk upload, content hash/length validation, quota, per-tenant isolation, lifecycle cleanup.
- Outbox hoặc reconciliation để tránh DB commit thành công nhưng queue publish thất bại.

### Senior+
- Threat model SAS leakage, race giữa scan và overwrite, TOCTOU, malware scanning limits.
- So sánh simplicity với cost vận hành, consistency, auditability, regional compliance.

## Hướng giải quyết tham khảo

**Giả định:** workload có file lớn và browser/mobile có thể upload trực tiếp; security policy cho phép client dùng scoped short-lived SAS. Chọn **B** với API control plane trong Modular Monolith hiện tại; chưa đủ lý do tạo microservice.

**APIs:** `POST /uploads` nhận metadata dự kiến, trả `uploadId`, blob key server-generated và SAS chỉ cho upload vào staging container. `POST /uploads/{id}/finalize` nhận checksum/ETag nếu contract hỗ trợ; `GET /uploads/{id}` trả trạng thái; `GET /documents/{id}/download` authorize rồi trả short-lived read SAS hoặc proxy có kiểm soát. Với browser chunk upload dùng Blob block upload SDK; xác định permission phù hợp với operation và không cho phép client ghi lại object sau khi finalize.

**Data model:** `Uploads(Id, OwnerId, BlobKey, ExpectedSize, ObservedSize, State, Version, CreatedAt, ExpiresAt, ScanAttempt, ScanVerdict)`; unique uploadId và concurrency token. State: `Issued → Uploading → Quarantined → Scanning → Approved → Published`, nhánh `Rejected/Expired/Failed`. `Issued` và `Uploading` có thể chỉ là trạng thái metadata; không tin client tự khai upload hoàn tất. Transition phải atomic ở DB với optimistic concurrency. Một file được approve nhưng chưa published vẫn không download được.

**Finalize:** xác thực owner, kiểm tra Blob existence, size, metadata, ETag/version và quota; ngăn thay đổi sau finalize bằng cách revoke/expire upload grant, dùng immutable/version-specific scan input hoặc copy sang quarantine key chỉ backend ghi. Chú ý SAS đã phát hành thường không thể thu hồi tức thời chỉ bằng thay đổi DB; phải thiết kế staging isolation, expiry ngắn và không dùng blob mutable làm nguồn publish. Kiểm tra file signature, MIME thực tế, malware verdict; không tin extension hay Content-Type do client gửi.

**Async scan:** sau transition `Quarantined`, publish scan work bằng outbox + worker hoặc reliable reconciliation; Azure Service Bus chỉ là lựa chọn nếu workload thực sự cần. Worker idempotent theo `uploadId + blobVersion`, retry bounded, DLQ và manual review cho file không scan được. Scan có thể tốn tài nguyên và cần service riêng có quyền đọc quarantine; Managed Identity/least privilege. Approved object được copy sang protected published container hoặc lưu immutable reference; chỉ cấp download khi state `Published`. Nếu DB và Blob không đồng bộ, scheduled reconciler tìm orphan/stuck records và dọn dẹp theo retention.

**Phương án A:** proxy bytes qua API đơn giản hơn khi policy yêu cầu server kiểm soát luồng, nhưng tăng bandwidth, memory/connection pressure và timeout; phải stream thay vì buffer. **B:** giảm tải App Service, hỗ trợ chunk/resume nhưng phức tạp hơn về SAS, CORS, lifecycle và cleanup. **C:** tách service khi có ownership, scaling, compliance hoặc release cadence khác biệt; không mặc định microservice tốt hơn.

**Security:** identity authorization ở control plane, per-tenant ownership, deny public access, private containers, encryption, safe file naming, malware quarantine, audit events, rate limits, SAS HTTPS và expiry tối thiểu, no SAS in logs. Đánh giá networking/private endpoints theo yêu cầu; direct browser upload cần đường truy cập tương ứng.

**Testing:** unit tests state transitions và duplicate finalize; integration tests size/hash mismatch và SAS scope; concurrency tests finalize đồng thời; failure injection DB/Blob/queue; E2E resumable upload, malware rejection và download authorization; load test theo file size/concurrency thực tế.

**Telemetry:** upload completion/failure, scan duration/p95, queue age/DLQ, stuck-state count, orphan bytes, SAS authorization errors, Blob dependency latency, storage cost và end-to-end publish SLA. Correlate bằng uploadId không nhúng PII.

**Trade-offs:** strong consistency giữa PostgreSQL và Blob không có distributed transaction mặc định; thiết kế eventual consistency có trạng thái rõ ràng. Deduplication theo hash có thể tiết kiệm storage nhưng dễ gây cross-tenant information leak nếu không phân quyền đúng. Chỉ thêm cache/CDN cho published public-safe content khi có nhu cầu và cache policy phù hợp.

## Mẫu trả lời trong phỏng vấn

“Với file tới 2 GB, tôi nghiêng về direct-to-Blob upload để API chỉ xử lý quyền và metadata, nhưng trước tiên phải xác nhận compliance và network constraints. API cấp upload session cùng SAS hạn chế, client upload vào staging, rồi finalize kiểm tra blob thực tế. Tôi dùng state machine để đảm bảo file chưa scan không được download. Worker xử lý scan idempotent; outbox hoặc reconciler xử lý failure giữa database và queue. Tôi không tạo microservice ngay nếu team chưa có nhu cầu scaling/ownership độc lập. Tôi sẽ đo upload success, stuck states, scan latency và kiểm thử retry, concurrent finalize, SAS leakage.”

## Câu hỏi đào sâu

1. Nếu SAS upload vẫn còn hiệu lực sau finalize, bạn ngăn scan/publish nhầm version như thế nào?
2. Nếu Service Bus unavailable trong một giờ, làm sao không mất scan jobs?
3. Khi nào proxy qua backend lại an toàn hoặc phù hợp hơn direct-to-Blob?

## Lỗi trả lời thường gặp

- Cho client quyền ghi/đọc Blob quá rộng hoặc vô thời hạn.
- Cho download ngay sau khi upload hoàn tất.
- Cho rằng DB transaction có thể atomic với Blob và queue.
- Thiếu xử lý orphan upload, duplicate finalize, stuck scanning.
- Đề xuất microservices mà không phân tích operational cost.
