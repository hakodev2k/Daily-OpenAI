# Code Review Challenge 1 — Multi-tenant report API trả nhầm dữ liệu giữa các tenant

**Chủ đề:** ASP.NET Core authorization, EF Core global query filter, `IMemoryCache`, tenant isolation, CancellationToken  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một SaaS nội bộ chạy ASP.NET Core và EF Core phục vụ khoảng 180 tenant. Mỗi tenant có user và dữ liệu báo cáo riêng. Hệ thống dùng một database chung; entity `Report` có `TenantId`, và `AppDbContext` đã cấu hình global query filter để mặc định chỉ đọc dữ liệu của tenant hiện tại.

Endpoint dưới đây phục vụ màn hình chi tiết report. Team vừa thêm cache để giảm tải SQL vì một số report được mở nhiều lần. Sau release, support nhận một ticket nghiêm trọng: một user của tenant B mở một URL report và thấy `CustomerName`, `Total` cùng `InternalNotes` của tenant A. Sự cố không tái hiện ổn định trên local. Production chạy nhiều application instances sau load balancer.

Business yêu cầu tenant isolation tuyệt đối. Report ID hiện là số nguyên tăng dần toàn hệ thống. Cache chỉ là optimization; tính đúng và authorization quan trọng hơn cache hit ratio.

## Đoạn code cần review

```csharp
public sealed class ReportService
{
    private readonly AppDbContext _db;
    private readonly IMemoryCache _cache;
    private readonly ITenantContext _tenant;

    public ReportService(
        AppDbContext db,
        IMemoryCache cache,
        ITenantContext tenant)
    {
        _db = db;
        _cache = cache;
        _tenant = tenant;
    }

    public Task<ReportDetailsDto?> GetAsync(
        int reportId,
        CancellationToken cancellationToken)
    {
        return _cache.GetOrCreateAsync(
            $"report:{reportId}",
            async entry =>
            {
                entry.AbsoluteExpirationRelativeToNow =
                    TimeSpan.FromMinutes(20);

                var tenantId = _tenant.TenantId;

                return await _db.Reports
                    .IgnoreQueryFilters()
                    .AsNoTracking()
                    .Where(x => x.Id == reportId)
                    .Select(x => new ReportDetailsDto(
                        x.Id,
                        x.TenantId,
                        x.CustomerName,
                        x.Total,
                        x.InternalNotes))
                    .SingleOrDefaultAsync(CancellationToken.None);
            });
    }
}

[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly ReportService _service;

    public ReportsController(ReportService service)
    {
        _service = service;
    }

    [Authorize(Policy = "Reports.Read")]
    [HttpGet("{id:int}")]
    public async Task<ActionResult<ReportDetailsDto>> Get(
        int id,
        CancellationToken cancellationToken)
    {
        var report = await _service.GetAsync(id, cancellationToken);

        return report is null
            ? NotFound()
            : Ok(report);
    }
}
```

## Kết quả code review tham khảo

### Critical — Bypass tenant filter nhưng không thêm tenant predicate thay thế

**Vấn đề:** Query gọi `.IgnoreQueryFilters()` rồi chỉ lọc theo `Id`. Biến `tenantId` được đọc nhưng hoàn toàn không được dùng.

**Tại sao xảy ra:** Global query filter vốn là safety boundary mặc định cho tenant-scoped entities. Sau khi bỏ filter, query trở thành lookup toàn hệ thống. Vì report IDs tăng dần và dùng chung namespace, user có quyền `Reports.Read` có thể yêu cầu ID thuộc tenant khác.

**Ảnh hưởng production:** Cross-tenant data disclosure. Đây là lỗi security/correctness nghiêm trọng; `InternalNotes` và dữ liệu business có thể bị lộ. Không nên coi GUID hay ID khó đoán là authorization control ngay cả khi sau này ID đổi kiểu.

**Cách sửa:** Với luồng tenant-scoped bình thường, không dùng `IgnoreQueryFilters()`. Nếu có lý do business bắt buộc bypass filter, phải có một privileged path riêng với explicit authorization và explicit tenant predicate/audit, không tái sử dụng endpoint thông thường.

### Critical — Cache key không chứa tenant/security scope

**Vấn đề:** Cache key chỉ là `report:{reportId}`.

**Tại sao xảy ra:** Cache đang coi report ID là toàn bộ identity của dữ liệu trong khi response phụ thuộc vào tenant authorization context. Một request tenant A có thể populate key, request tenant B sau đó nhận lại cùng DTO mà không chạy query hay authorization theo object.

**Ảnh hưởng production:** Cache có thể biến một lần đọc sai thành nhiều lần cross-tenant disclosure. Bug phụ thuộc thứ tự request và instance nhận traffic nên có thể “lúc có, lúc không” khi production có nhiều process và mỗi process có `IMemoryCache` riêng.

**Cách sửa:** Trước hết bảo đảm query luôn tenant-scoped. Nếu vẫn cache, key tối thiểu phải bao gồm tenant và report identity, ví dụ `report:{tenantId}:{reportId}`. Nếu response còn phụ thuộc role, locale hoặc permission dimension khác, key phải phản ánh dimension đó hoặc không cache DTO authorization-sensitive ở layer này.

### High — Policy chỉ kiểm tra capability, chưa chứng minh quyền truy cập object

**Vấn đề:** `[Authorize(Policy = "Reports.Read")]` có thể chỉ xác minh user có claim/role đọc report chung.

**Tại sao xảy ra:** Resource-level authorization đang bị ngầm giao cho service/query. Khi query bỏ tenant boundary, controller vẫn trả `200 OK` vì policy không biết resource thuộc tenant nào.

**Ảnh hưởng production:** Một permission tưởng an toàn trở thành broken object-level authorization.

**Cách sửa:** Giữ defense in depth. Tenant-scoped query phải là mặc định; nếu quyền truy cập phức tạp hơn tenant ownership, dùng resource-based authorization hoặc explicit access predicate trước khi trả dữ liệu. Không dựa vào controller policy như bằng chứng đầy đủ cho object authorization.

### High — `CancellationToken.None` cắt đứt request cancellation

**Vấn đề:** Method nhận `cancellationToken` nhưng EF query dùng `CancellationToken.None`.

**Tại sao xảy ra:** Client disconnect hoặc request timeout không truyền cancellation xuống database operation.

**Ảnh hưởng production:** Query vô ích có thể tiếp tục chạy, giữ connection và tài nguyên sau khi request đã bị hủy. Dưới load hoặc khi database chậm, hành vi này làm tăng resource pressure.

**Cách sửa:** Truyền token đến `SingleOrDefaultAsync(cancellationToken)`. Phân biệt cancellation mong đợi với failure khi logging.

### High — Cache lifetime không gắn với data update/invalidation

**Vấn đề:** DTO được cache tuyệt đối 20 phút nhưng không có invalidation khi report thay đổi.

**Tại sao xảy ra:** TTL được chọn như một con số tĩnh mà không dựa trên freshness requirement.

**Ảnh hưởng production:** User có thể thấy report cũ trong tối đa khoảng TTL dù update đã commit. Với dữ liệu nhạy cảm, thay đổi permission/visibility cũng có thể không phản ánh ngay nếu cache layer lưu kết quả sau authorization.

**Cách sửa:** Xác định freshness SLO. Với dữ liệu thay đổi ít, TTL ngắn có thể đủ. Nếu cần read-after-update, invalidate key sau write thành công hoặc dùng versioned key. Không thêm invalidation phức tạp nếu business không cần strong freshness.

### Medium — `IMemoryCache` tạo behavior khác nhau giữa nhiều app instances

**Vấn đề:** Mỗi process có cache riêng.

**Tại sao xảy ra:** Load balancer phân phối request đến các instances khác nhau; một instance có entry tenant A, instance khác chưa có entry hoặc có entry khác.

**Ảnh hưởng production:** Sự cố trở nên nondeterministic; người test có thể refresh và lúc đúng lúc sai. Cache hit ratio và stale state cũng không đồng nhất.

**Cách sửa:** Không nhất thiết phải chuyển sang distributed cache. Nếu cache nhỏ và eventual consistency chấp nhận được, per-instance cache vẫn hợp lý sau khi key đúng. Chỉ dùng Redis/distributed cache khi cần shared cache semantics và chấp nhận thêm operational complexity.

### Medium — Không nên giả định `GetOrCreateAsync` là single-flight cho mọi concurrent miss

**Vấn đề:** Nhiều request miss cùng một key có thể làm factory chạy nhiều lần tùy timing; code không nên dựa vào cache API như một distributed/exclusive lock.

**Tại sao xảy ra:** Cache-aside helper nhằm tiện lookup/create, không phải một cross-request distributed synchronization contract.

**Ảnh hưởng production:** Hot report vừa expire có thể tạo burst query xuống SQL. Đây không phải nguyên nhân của data leak nhưng có thể gây load spike.

**Cách sửa:** Đo trước. Nếu thực sự có stampede, cân nhắc per-key single-flight trong process, bounded concurrency hoặc một cache strategy phù hợp. Không thêm distributed lock nếu chưa có evidence.

### Medium — DTO đang trả `TenantId` và `InternalNotes` mà chưa chứng minh client cần chúng

**Vấn đề:** Projection đưa cả `TenantId` và `InternalNotes` ra API.

**Tại sao xảy ra:** DTO được xây gần giống entity hơn là từ contract tối thiểu cần cho màn hình.

**Ảnh hưởng production:** Tăng blast radius nếu authorization sai; có thể lộ dữ liệu nội bộ không cần thiết.

**Cách sửa:** Áp dụng data minimization: chỉ trả fields UI cần. Nếu internal notes cần permission riêng, tách policy/endpoint hoặc conditional projection có kiểm soát.

## Phiên bản đề xuất

```csharp
public sealed class ReportService
{
    private readonly AppDbContext _db;
    private readonly IMemoryCache _cache;
    private readonly ITenantContext _tenant;

    public ReportService(
        AppDbContext db,
        IMemoryCache cache,
        ITenantContext tenant)
    {
        _db = db;
        _cache = cache;
        _tenant = tenant;
    }

    public async Task<ReportDetailsDto?> GetAsync(
        int reportId,
        CancellationToken cancellationToken)
    {
        var tenantId = _tenant.TenantId;
        var cacheKey = $"report:{tenantId}:{reportId}";

        return await _cache.GetOrCreateAsync(
            cacheKey,
            async entry =>
            {
                entry.AbsoluteExpirationRelativeToNow =
                    TimeSpan.FromMinutes(2);

                // Giữ global tenant query filter hoạt động.
                return await _db.Reports
                    .AsNoTracking()
                    .Where(x => x.Id == reportId)
                    .Select(x => new ReportDetailsDto(
                        x.Id,
                        x.CustomerName,
                        x.Total))
                    .SingleOrDefaultAsync(cancellationToken);
            });
    }

    public void Invalidate(int tenantId, int reportId)
        => _cache.Remove($"report:{tenantId}:{reportId}");
}

public sealed record ReportDetailsDto(
    int Id,
    string CustomerName,
    decimal Total);
```

Nếu permission model phức tạp hơn tenant ownership, implementation cần thêm resource-based authorization. Nếu support/admin thật sự cần cross-tenant lookup, nên tạo use case riêng, ví dụ `SupportReportService`, yêu cầu privileged policy, bắt buộc target tenant rõ ràng và ghi audit event; không dùng `IgnoreQueryFilters()` âm thầm trong service chung.

TTL `2 phút` phía trên chỉ là ví dụ minh họa chứ không phải giá trị mặc định đúng cho mọi hệ thống. Giá trị thực tế phải theo freshness requirement, write frequency và đo load. Nếu update cần phản ánh ngay, invalidate entry sau transaction thành công.

## Giải thích thiết kế sau khi sửa

Thiết kế mới đưa tenant isolation trở lại thành invariant của query thay vì một convention dễ quên. Cache key chứa tenant để response của tenant A không thể được dùng như entry của tenant B. DTO giảm dữ liệu để giới hạn blast radius.

Điểm quan trọng là không dùng cache như authorization layer. Request vẫn phải có authorization hợp lệ ngay cả khi cache hit. Nếu authorization phụ thuộc từng resource/role phức tạp, nên kiểm tra trước khi lấy dữ liệu hoặc cache một representation không chứa permission-sensitive fields.

`IMemoryCache` có thể tiếp tục được dùng nếu per-instance semantics phù hợp; không cần mặc định chuyển Redis. Nếu load test cho thấy hot-key expiration gây database burst, lúc đó mới thêm single-flight hoặc strategy khác dựa trên evidence.

## Trade-offs

- Tenant-aware keys làm tăng số cache entries nếu nhiều tenant đọc cùng report shape; đây là chi phí cần thiết để giữ security boundary.
- TTL ngắn hoặc invalidation chủ động giảm stale window nhưng tăng database traffic và complexity.
- Resource-based authorization tăng correctness nhưng có thể thêm query/dependency; cần thiết kế để tránh một authorization query dư trên mọi request nếu tenant predicate đã đủ.
- Per-instance cache đơn giản và nhanh nhưng cache warm-up/invalidation không đồng nhất giữa nodes. Distributed cache đồng nhất hơn ở một số use case nhưng thêm network dependency, serialization và failure mode mới.

## Cách kiểm thử

1. **Security/integration test:** tạo tenant A và B, user B gọi report ID thuộc A; phải nhận `404` hoặc `403` theo contract và tuyệt đối không nhận payload A.
2. **Cache isolation test:** request A populate cache trước, sau đó B gọi cùng numeric ID; kết quả vẫn không thể cross tenant. Đảo thứ tự và lặp lại.
3. **Concurrency test:** nhiều request của A/B chạy song song trên cùng report IDs để phát hiện cache-key leakage và race.
4. **Cancellation/failure-path test:** hủy request khi EF query đang chờ và xác minh operation nhận cancellation phù hợp.
5. **Freshness test:** update report rồi xác minh invalidation/TTL đáp ứng freshness SLO đã thống nhất.

## Quan sát trong production

- Structured log có `TenantId`, `ReportId`, authorization result, cache hit/miss và request correlation ID; không log `InternalNotes` hay dữ liệu nhạy cảm.
- Metric theo endpoint: p50/p95/p99, 4xx/5xx, cache hit ratio và DB dependency duration.
- Security alert/audit cho privileged cross-tenant support access nếu chức năng đó tồn tại.
- Theo dõi query count và SQL load quanh thời điểm cache expiration để phát hiện stampede thực tế.
- Có thể thêm invariant telemetry ở tầng response/service để phát hiện trường hợp resource tenant khác request tenant, nhưng telemetry không được thay thế authorization enforcement.

# Code Review Challenge 2 — Vue search page đôi lúc hiển thị kết quả cũ và render HTML không tin cậy

## Bối cảnh

Traffic bình thường không lớn, nhưng người dùng thường gõ nhanh và network latency dao động từ 80 ms đến hơn 1 giây vì API search gọi tiếp Elasticsearch.

Sau release, QA ghi nhận ba symptom:

- gõ `iphone`, sau đó nhanh chóng đổi thành `ipad`, đôi lúc UI cuối cùng lại hiển thị kết quả `iphone`;
- khi một request lỗi, spinner đôi lúc biến mất dù request mới hơn vẫn đang chạy;
- security review phát hiện backend highlight field có thể chứa text do seller nhập và không cam kết là trusted HTML.

Team muốn giữ UX search-as-you-type. Không được giả định backend luôn trả response đúng thứ tự. Backend có thể trả `429`, `500` hoặc timeout.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue';

interface SearchItem {
  id: string;
  name: string;
  highlight: string;
}

const query = ref('');
const items = ref<SearchItem[]>([]);
const loading = ref(false);
const error = ref('');

watch(query, async value => {
  if (!value) {
    items.value = [];
    return;
  }

  loading.value = true;
  error.value = '';

  try {
    const response = await fetch(
      `/api/products/search?q=${value}`,
      {
        headers: {
          Authorization: `Bearer ${localStorage.getItem('access_token')}`
        }
      }
    );

    const data = await response.json();
    items.value = data.items;
  } catch (e) {
    error.value = String(e);
    items.value = [];
  } finally {
    loading.value = false;
  }
});
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in items" :key="item.id">
        <strong>{{ item.name }}</strong>
        <span v-html="item.highlight"></span>
      </li>
    </ul>
  </section>
</template>
```

## Kết quả code review tham khảo

### Critical — `v-html` render dữ liệu không được tin cậy

**Vấn đề:** `item.highlight` được đưa thẳng vào `v-html` trong khi backend không cam kết nội dung đã được sanitize theo policy an toàn.

**Tại sao xảy ra:** `v-html` yêu cầu raw HTML được chèn vào DOM. Nếu payload chứa markup/script-capable content phù hợp với browser context, ứng dụng có thể mở đường cho XSS.

**Ảnh hưởng production:** Kẻ tấn công có thể thực thi nội dung không mong muốn trong origin của ứng dụng, đọc dữ liệu mà trang có quyền truy cập hoặc thực hiện hành động dưới phiên user tùy kiến trúc auth và browser controls.

**Cách sửa:** Tốt nhất đổi API contract để trả plain text + structured highlight ranges/tokens, rồi render bằng text interpolation. Nếu business thật sự cần HTML, sanitize ở một boundary được kiểm soát bằng allowlist phù hợp và coi đây là security feature cần test riêng. Không tự viết regex sanitizer.

### High — Race condition: response cũ có thể ghi đè response mới

**Vấn đề:** Mỗi thay đổi `query` khởi tạo request mới nhưng mọi request đều được phép gán `items.value` khi hoàn thành.

**Tại sao xảy ra:** Network completion order không đảm bảo giống request creation order. Request A cho `iphone` có thể chậm hơn B cho `ipad` và hoàn thành sau B.

**Ảnh hưởng production:** UI hiển thị dữ liệu không khớp input hiện tại, gây thao tác sai hoặc mất niềm tin vào search.

**Cách sửa:** Hủy request cũ bằng `AbortController` khi query đổi và/hoặc dùng generation/request ID để chỉ latest request được commit state. Với correctness cao, generation check vẫn hữu ích ngay cả khi cancellation không hoàn thành tức thời ở mọi layer.

### High — `loading` bị race giữa nhiều requests

**Vấn đề:** `finally` của bất kỳ request nào cũng đặt `loading = false`.

**Tại sao xảy ra:** Một request cũ có thể hoàn thành trong khi request mới vẫn pending.

**Ảnh hưởng production:** Spinner biến mất sớm, UI trông như đã ổn định dù search mới chưa hoàn thành.

**Cách sửa:** Chỉ latest generation được cập nhật `loading`, hoặc quản lý active request count nếu UI thực sự cần phản ánh nhiều operations.

### High — Không kiểm tra `response.ok`

**Vấn đề:** Code gọi `response.json()` và dùng payload ngay cả khi server trả `429`, `400`, `500`.

**Tại sao xảy ra:** `fetch` thường resolve promise khi nhận HTTP response; HTTP status error không đồng nghĩa network exception tự động.

**Ảnh hưởng production:** Error payload có thể bị hiểu như success shape, gây exception thứ cấp hoặc state sai. User không nhận thông báo phù hợp cho throttling/server failure.

**Cách sửa:** Kiểm tra `response.ok`; map status có ý nghĩa như `429` sang UX phù hợp. Không retry vô hạn ở browser; nếu retry thì phải bounded và tôn trọng semantics/server guidance.

### Medium — Không debounce input

**Vấn đề:** Mỗi keystroke phát request ngay.

**Tại sao xảy ra:** `watch` chạy theo từng thay đổi model.

**Ảnh hưởng production:** Tăng request volume, tải Elasticsearch/API và khả năng chạm rate limit, đặc biệt khi user gõ nhanh.

**Cách sửa:** Debounce khoảng thời gian phù hợp với UX đã đo, ví dụ 200–300 ms chỉ là điểm khởi đầu để thử nghiệm, không phải con số bắt buộc. Có thể yêu cầu minimum query length nếu product phù hợp.

### Medium — Query parameter không được encode đúng

**Vấn đề:** URL ghép trực tiếp `?q=${value}`.

**Tại sao xảy ra:** User input có thể chứa ký tự mang ý nghĩa trong URL query string.

**Ảnh hưởng production:** Search sai, query bị cắt hoặc tạo thêm params ngoài ý muốn.

**Cách sửa:** Dùng `URLSearchParams` hoặc `encodeURIComponent` đúng ngữ cảnh.

### Medium — Error message thô bị đưa thẳng ra UI

**Vấn đề:** `String(e)` được hiển thị cho user.

**Tại sao xảy ra:** Error handling chưa phân tách diagnostic detail và user-facing message.

**Ảnh hưởng production:** UX kém; trong một số trường hợp có thể lộ detail implementation không cần thiết. Đồng thời thiếu classification giữa abort, offline, timeout và server error.

**Cách sửa:** Hiển thị message thân thiện theo error category; gửi diagnostic detail vào telemetry. Abort của request cũ không nên hiện như lỗi cho user.

### Medium — Token trong `localStorage` làm tăng blast radius của XSS

**Vấn đề:** Access token được lấy từ `localStorage`.

**Tại sao xảy ra:** JavaScript chạy cùng origin có thể truy cập localStorage. Nếu ứng dụng có XSS, token trở thành tài sản dễ bị đọc hơn so với một số mô hình cookie bảo vệ bởi `HttpOnly`.

**Ảnh hưởng production:** XSS có thể dẫn tới token theft tùy auth architecture.

**Cách sửa:** Không thể kết luận chỉ từ snippet rằng phải đổi auth ngay. Cần xem architecture tổng thể. Nếu dùng cookie session/token, cân nhắc `HttpOnly`, `Secure`, `SameSite` phù hợp và CSRF model tương ứng. Nếu SPA bắt buộc giữ token phía client, cần giảm XSS surface, token lifetime/scope và dùng flow theo security architecture đã chọn.

## Phiên bản đề xuất

Ví dụ dưới đây tránh raw HTML, debounce request, hủy request cũ và chỉ cho latest generation commit state. API giả định đổi contract từ `highlight: string` thành `highlightText: string` plain text.

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue';

interface SearchItem {
  id: string;
  name: string;
  highlightText: string;
}

const query = ref('');
const items = ref<SearchItem[]>([]);
const loading = ref(false);
const error = ref('');

let controller: AbortController | null = null;
let debounceTimer: ReturnType<typeof setTimeout> | null = null;
let generation = 0;

function clearPendingWork() {
  controller?.abort();
  controller = null;

  if (debounceTimer !== null) {
    clearTimeout(debounceTimer);
    debounceTimer = null;
  }
}

watch(query, value => {
  const currentGeneration = ++generation;
  clearPendingWork();

  const normalized = value.trim();

  if (normalized.length < 2) {
    items.value = [];
    loading.value = false;
    error.value = '';
    return;
  }

  debounceTimer = setTimeout(async () => {
    controller = new AbortController();

    loading.value = true;
    error.value = '';

    try {
      const params = new URLSearchParams({ q: normalized });
      const response = await fetch(`/api/products/search?${params}`, {
        signal: controller.signal,
        headers: {
          Authorization: `Bearer ${localStorage.getItem('access_token') ?? ''}`
        }
      });

      if (!response.ok) {
        if (response.status === 429) {
          throw new Error('RATE_LIMITED');
        }

        throw new Error(`HTTP_${response.status}`);
      }

      const data = await response.json() as { items: SearchItem[] };

      if (currentGeneration === generation) {
        items.value = data.items;
      }
    } catch (e) {
      if (e instanceof DOMException && e.name === 'AbortError') {
        return;
      }

      if (currentGeneration === generation) {
        error.value = e instanceof Error && e.message === 'RATE_LIMITED'
          ? 'Too many searches. Please try again shortly.'
          : 'Search is temporarily unavailable.';
        items.value = [];
      }
    } finally {
      if (currentGeneration === generation) {
        loading.value = false;
      }
    }
  }, 250);
});

onBeforeUnmount(() => {
  ++generation;
  clearPendingWork();
});
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in items" :key="item.id">
        <strong>{{ item.name }}</strong>
        <span>{{ item.highlightText }}</span>
      </li>
    </ul>
  </section>
</template>
```

Trong production code có thể tách debounce/search thành composable để test dễ hơn và dùng auth client tập trung thay vì tự gắn token ở từng component. Giá trị `250 ms` và minimum length `2` cần điều chỉnh dựa trên UX, search cost và telemetry.

## Giải thích thiết kế sau khi sửa

Hai cơ chế giải quyết hai lớp vấn đề khác nhau. `AbortController` giảm work không còn cần thiết; generation ID đảm bảo state correctness bằng cách ngăn response cũ commit vào state mới. Không nên coi cancellation một mình là invariant duy nhất cho UI state.

`response.ok` làm HTTP failure path explicit. Query được encode bằng `URLSearchParams`. Raw `v-html` được loại bỏ bằng cách thay đổi contract về plain text; nếu UI cần highlight thực sự, có thể trả structured match positions và render các text segments bằng Vue template mà không inject raw HTML.

Auth storage cần được review ở cấp ứng dụng. Đoạn sửa vẫn giữ cách hiện tại để không giả vờ có đủ context thay toàn bộ auth architecture, nhưng XSS finding làm rõ rằng token storage và content rendering phải được đánh giá cùng nhau.

## Trade-offs

- Debounce giảm traffic nhưng thêm một chút perceived latency; quá dài sẽ làm search cảm giác chậm.
- Abort + generation logic phức tạp hơn implementation naïve nhưng đổi lại state deterministic hơn dưới network reordering.
- Structured highlights làm API/UI contract phức tạp hơn raw HTML, nhưng security boundary rõ hơn và dễ kiểm soát render.
- Nếu dùng một search library/composable có sẵn, code component ngắn hơn nhưng phải hiểu cancellation/error semantics của library thay vì giả định nó xử lý mọi race.
- Chuyển từ localStorage token sang cookie-based model có thể cải thiện một số XSS-related properties nhưng đưa CSRF/cookie configuration considerations vào thiết kế; cần quyết định theo toàn bộ auth architecture.

## Cách kiểm thử

1. **Race-condition test:** mock `iphone` response chậm hơn `ipad`; sau khi cả hai hoàn thành, UI phải hiển thị `ipad` và input phải khớp state.
2. **Loading-state test:** request cũ hoàn thành/abort trong khi request mới pending; spinner không được tắt sớm.
3. **Security test:** backend trả highlight chứa hostile markup; UI chỉ hiển thị text hoặc structured safe rendering, không tạo executable DOM.
4. **Failure-path test:** mô phỏng `429`, `500`, network error và abort; UX/error state phải đúng, không dùng error payload như success.
5. **E2E/Playwright test:** gõ nhanh nhiều query trên network throttling giả lập và xác minh kết quả cuối luôn tương ứng query mới nhất.

## Quan sát trong production

- Frontend telemetry cho search request duration, status category, abort count, rate-limit count và error rate.
- Correlation/request ID nối browser request với API/Application Insights/Elasticsearch dependency trace nếu hệ thống hỗ trợ.
- Theo dõi requests-per-search-session để đánh giá debounce hiệu quả thay vì chỉ nhìn tổng API volume.
- Browser error reporting không gửi access token, query nhạy cảm hoặc full payload vào log.
- Dashboard backend nên theo dõi p95/p99 search latency, Elasticsearch dependency latency, `429/5xx` và concurrency để phân biệt frontend race với backend degradation.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend bắt buộc phải trả HTML highlight vì Elasticsearch đã tạo markup, bạn sẽ thiết kế trust/sanitization boundary ở đâu?
2. Nếu cancellation request ở browser không làm Elasticsearch query phía server dừng ngay, bạn vẫn giữ `AbortController` chứ? Vì sao?
3. Nếu product muốn kết quả cập nhật sau mỗi ký tự với latency dưới 100 ms, bạn sẽ đánh đổi debounce, caching và backend capacity như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge đầu tập trung vào việc tenant isolation phải là một security invariant xuyên suốt authorization, data access và caching. Bypass EF Core query filter mà không thay bằng explicit tenant predicate có thể trực tiếp tạo cross-tenant data leak; cache key thiếu tenant scope còn khuếch đại lỗi và khiến symptom phụ thuộc request ordering/application instance. Cache không được dùng như authorization boundary.

Challenge thứ hai nhấn mạnh rằng asynchronous UI cần bảo vệ **latest user intent**, không chỉ “await request”. Network completion có thể reorder; state update phải có cancellation/generation semantics rõ ràng. Đồng thời raw HTML từ dữ liệu không đáng tin cậy là security boundary, không phải formatting convenience.

Cả hai challenge đều cho thấy bug production thường xuất hiện ở **boundary giữa các cơ chế**: authorization + cache, async requests + shared UI state, rendering + untrusted data. Review Senior cần xem invariant của toàn flow thay vì từng dòng riêng lẻ.

## Mẫu tư duy cần nhớ

- Security boundary phải được enforce ở nơi dữ liệu được truy cập; đừng dựa vào ID khó đoán hoặc cache behavior.
- Cache key phải chứa mọi dimension làm thay đổi correctness/security của response.
- Với async UI, phân biệt thứ tự request bắt đầu và thứ tự response hoàn thành; latest intent phải thắng.
- Treat untrusted HTML as hostile until a controlled sanitization/rendering contract proves otherwise.
- Test concurrency, failure path và adversarial input; happy-path test không đủ chứng minh production correctness.
