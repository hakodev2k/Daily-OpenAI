# Câu 1 — SQL Server: phân trang đúng khi dữ liệu liên tục thay đổi

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** SQL Server, isolation, execution plan, ASP.NET Core, pagination, correctness.

## Bối cảnh

Một API .NET 8 phục vụ trang lịch sử đơn hàng, bảng `Orders(Id bigint PK, TenantId, CreatedAt datetime2, Status, Total)` có 18 triệu hàng. Client gọi `GET /orders?page=4000&pageSize=50`, backend dùng `ORDER BY CreatedAt DESC OFFSET 199950 ROWS FETCH NEXT 50 ROWS ONLY`. Khi có đơn mới, người dùng đôi khi thấy bản ghi trùng hoặc bỏ sót giữa hai trang. p95 tăng mạnh ở trang sâu. API cần lọc theo tenant và status, không được rò dữ liệu tenant khác. Chưa rõ yêu cầu snapshot xuyên nhiều request.

## Câu hỏi chính

Hãy giải thích cơ chế SQL Server xử lý kiểu phân trang này, phân biệt vấn đề hiệu năng với tính đúng đắn, đề xuất API/query/index và phương pháp chứng minh cải thiện trong production.

## Câu hỏi làm rõ nên cân nhắc

1. UX cần nhảy đến trang bất kỳ hay chỉ next/previous?
2. Cần danh sách nhất quán tại một thời điểm hay chấp nhận thay đổi giữa các request?
3. `CreatedAt` có trùng và có bị sửa không?
4. Tenant/status nào có cardinality lớn; predicate thực tế và execution plan ra sao?
5. SLA latency và độ mới dữ liệu là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1
Tách thứ tự ổn định khỏi số lượng hàng phải đi qua.

### Gợi ý 2
Xem điều gì xảy ra khi hàng mới được chèn trước vị trí OFFSET.

### Gợi ý 3
So sánh `(CreatedAt, Id)` với cursor có tie-breaker; đánh giá isolation và predicate SARGable.

## Cấu trúc trả lời đề xuất

1. Chốt semantics phân trang và độ nhất quán.
2. Mô tả sort/seek/scan, OFFSET và concurrent inserts.
3. Đề xuất deterministic ordering, cursor, index.
4. Đối chiếu trade-offs, security và backfill.
5. Đo execution plan, logical reads, p95; kiểm thử concurrency.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `ORDER BY CreatedAt` không tạo total order nếu timestamp trùng.
- OFFSET sâu có thể phải đọc/bỏ qua nhiều hàng; cost tùy plan/index, không khẳng định luôn full scan.
- Chèn/xóa giữa request làm vị trí trang dịch chuyển; index không tự sửa tính đúng đắn.
- Tenant predicate bắt buộc từ server-side authorization context.

### Điểm cộng
- Cursor keyset với cặp `CreatedAt, Id` và seek predicate.
- Composite index theo filter/order; kiểm tra plan và covering thay vì đoán.
- Cursor được ký hoặc kiểm tra tenant/filter để ngăn sửa tham số.

### Senior+
- Nêu rõ keyset không đảm bảo snapshot xuyên request nếu hàng bị cập nhật/xóa; cần watermark/snapshot contract riêng.
- Đề xuất đo riêng p50/p95/p99, logical reads, waits, index maintenance, kế hoạch rollout.

## Hướng giải quyết tham khảo

Giả sử UI chỉ cần duyệt tiếp và `CreatedAt` bất biến. Dùng thứ tự `ORDER BY CreatedAt DESC, Id DESC`. Trang đầu:

```sql
SELECT TOP (@Take) Id, CreatedAt, Status, Total
FROM dbo.Orders
WHERE TenantId = @TenantId AND Status = @Status
ORDER BY CreatedAt DESC, Id DESC;
```

Trang sau, cursor gồm `LastCreatedAt` và `LastId` từ hàng cuối của trang trước:

```sql
SELECT TOP (@Take) Id, CreatedAt, Status, Total
FROM dbo.Orders
WHERE TenantId = @TenantId AND Status = @Status
  AND (CreatedAt < @LastCreatedAt
       OR (CreatedAt = @LastCreatedAt AND Id < @LastId))
ORDER BY CreatedAt DESC, Id DESC;
```

Index ứng viên: `CREATE INDEX IX_Orders_Tenant_Status_Created_Id ON dbo.Orders(TenantId, Status, CreatedAt DESC, Id DESC) INCLUDE (Total);`. Đây là giả thuyết cần kiểm tra trên workload thực: status selectivity, writes, key lookups, memory grants, fragmentation, filtered indexes và kích thước INCLUDE có thể thay đổi quyết định. Không trả `TenantId` từ request như nguồn tin cậy; lấy tenant đã xác thực và kiểm tra quyền ở backend.

Keyset tránh việc offset tăng theo số trang trong mô hình truy cập tuần tự và hạn chế dịch chuyển do insert mới ở đầu danh sách. Nó không đóng băng dữ liệu: nếu `Status` đổi hoặc record bị xóa, membership có thể đổi. Nếu cần consistent export, chọn snapshot materialization hoặc snapshot boundary phù hợp nghiệp vụ, cân nhắc chi phí lưu snapshot và thời gian sống. Một timestamp watermark chỉ giới hạn dữ liệu mới, không đảm bảo bất biến với update/delete. Với yêu cầu nhảy trang ngẫu nhiên, OFFSET hoặc anchor table có thể vẫn phù hợp.

Đo trước/sau bằng actual execution plan, `SET STATISTICS IO, TIME ON` trong môi trường thử nghiệm, Query Store, CPU/reads, p95 theo page depth, kiểm tra lock/waits. Rollout API cursor song song với page API; hỗ trợ backward compatibility, giới hạn page size, encode cursor có version và filter fingerprint, ghi metric nhưng không log dữ liệu nhạy cảm.

## Mẫu trả lời trong phỏng vấn

“Trước hết tôi xác nhận UI có cần nhảy đến trang bất kỳ và có yêu cầu snapshot không. OFFSET có thể ngày càng tốn chi phí vì engine phải đi qua các hàng trước trang đích; đồng thời dữ liệu chèn giữa hai request làm các vị trí dịch chuyển. Ngoài ra `CreatedAt` trùng khiến thứ tự không xác định. Nếu UI chỉ cần next page, tôi dùng `CreatedAt DESC, Id DESC` và cursor seek, kiểm tra index theo TenantId, Status, CreatedAt, Id. Tôi sẽ lấy tenant từ claims đã kiểm tra, giới hạn page size, benchmark logical reads và p95 trên dữ liệu giống production. Keyset cải thiện traversal nhưng không hứa snapshot khi status thay đổi; nếu nghiệp vụ yêu cầu ảnh chụp nhất quán, tôi thiết kế contract riêng và chấp nhận chi phí lưu/duy trì snapshot.”

## Câu hỏi đào sâu

1. Khi `CreatedAt` có thể bị chỉnh sửa, keyset còn đảm bảo gì?
2. Nếu product yêu cầu đi trực tiếp tới trang 8.000, bạn đổi giải pháp thế nào?
3. Nếu `Status` có 99% hàng cùng giá trị, index đề xuất có còn tối ưu?

## Lỗi trả lời thường gặp

- Chỉ thêm index rồi khẳng định hết duplicate.
- Dùng timestamp làm sort key duy nhất.
- Xem cursor là snapshot transaction xuyên HTTP request.
- Tin `TenantId` từ query string.
- Không đo plan và logical reads.

## Thang điểm 0–10

- Làm rõ semantics và scale: 1.5
- Cơ chế sort/OFFSET/concurrency: 2
- Query/index/cursor chính xác: 2.5
- Điều kiện và trade-offs: 1.5
- Test/telemetry/rollout: 1.5
- Trình bày mạch lạc: 1

# Câu 2 — Azure Blob Storage: upload thành công nhưng file tải về lỗi hoặc thiếu

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, HTTP streaming, security, observability, incident response.

## Bối cảnh

Dịch vụ .NET 8 chạy Azure App Service trên Linux cho phép khách hàng upload PDF 10–600 MB. Sau bản release mới, 2% request trả 200/201 nhưng một số file tải về thiếu byte hoặc không mở được. p95 tăng, memory instance tăng; một vài lần deploy trùng thời điểm lỗi. Client React upload qua backend, metadata lưu SQL Server. Chưa có bằng chứng lỗi nằm ở Blob, proxy, DB hay client. Yêu cầu ưu tiên bảo toàn dữ liệu và hạn chế ảnh hưởng upload đang diễn ra.

## Câu hỏi chính

Bạn là incident lead. Hãy tổ chức điều tra, giảm tác động ngay, xác định giả thuyết cạnh tranh, sửa đúng nguyên nhân và ngăn tái diễn mà không vội kết luận Azure Blob Storage bị lỗi.

## Câu hỏi làm rõ nên cân nhắc

1. 201 được trả trước hay sau khi upload/commit Blob hoàn tất?
2. Client gửi Content-Length/chunked; có reverse proxy hay timeout nào?
3. Correlation giữa lỗi và file size, instance, deployment slot, SDK version?
4. Blob length/hash được xác minh khi nào, metadata DB có trạng thái gì?
5. Có retry, resumable upload, virus scanning hay background post-processing không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt “HTTP success” với “object đã được kiểm chứng”.

### Gợi ý 2
Theo dõi từng ranh giới: browser → App Service → Blob → DB → download.

### Gợi ý 3
Xem cancellation, stream lifetime, upload completion, retry, idempotency và release rollout.

## Cấu trúc trả lời đề xuất

1. Khoanh vùng impact và dừng luồng gây corruption.
2. Đặt timeline với deployment và dependency traces.
3. So sánh nhiều giả thuyết bằng length/checksum, status, logs.
4. Khôi phục/retry có kiểm soát, tránh công bố file chưa hợp lệ.
5. Sửa protocol upload và dữ liệu trạng thái.
6. Test failure injection, rollout canary, alerting.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Stabilize: tạm rollback/disable phiên bản nghi vấn nếu bằng chứng phù hợp; không xóa file lỗi trước khi điều tra.
- So sánh bytes client gửi, server đọc, Blob properties, bytes download; phân biệt content corruption với metadata/content encoding.
- Chỉ đánh dấu `Ready` sau khi upload thành công và validation hoàn tất.
- Không nuốt exception rồi trả 201.

### Điểm cộng
- Streaming thay vì buffer toàn file, size limits, content validation, tenant authorization.
- Staging blob + publish state machine; idempotency key và cleanup orphan.
- Managed Identity với quyền tối thiểu, tránh log SAS/token.

### Senior+
- Kiểm tra race khi deploy/restart, abort, cancellation và DB/Blob không có atomic transaction chung.
- SLO theo verified completion, audit reconciliation, recovery playbook.

## Hướng giải quyết tham khảo

**Impact:** Tạm vô hiệu luồng upload mới nếu corruption tiếp diễn; cho download file đã xác minh hoạt động. Nếu tỷ lệ lỗi gắn chặt bản deploy, rollback hoặc chuyển traffic về slot trước, đồng thời giữ log và mẫu object bị lỗi để đối chiếu. Thông báo rõ trạng thái file chưa xác minh thay vì giả 201.

**Evidence:** Tạo `uploadId` liên kết request, DB row và Blob metadata; thu thập `requestBodyBytesRead`, `blobContentLength`, expected length, digest do client cung cấp (không tin digest làm bằng chứng bảo mật), SDK response status, request ID, duration, cancellation reason. Kiểm tra upload task có được await; stream có bị dispose trước khi hoàn tất; `CopyToAsync`/SDK upload có dùng `CancellationToken` đúng; có `Task.Run` fire-and-forget không; SQL metadata có được commit trước upload không; download có cắt stream do response timeout không. So sánh raw Blob download với file gốc để loại trừ lỗi React rendering/PDF viewer.

**Giả thuyết cạnh tranh:** (A) backend trả success trước upload completion; (B) request bị ngắt/restart giữa chừng và code đánh dấu thành công; (C) DB metadata gắn sai blob version/key do retry; (D) client gửi file lỗi; (E) download proxy/content transformation. Không coi giả thuyết nào là root cause khi chưa có chứng cứ.

**Thiết kế sửa:** Lưu bản ghi `Pending` cùng tenant, expected size và uploadId duy nhất. Stream request vào blob staging bằng SDK và await đến khi operation kết thúc; kiểm tra properties/length và checksum được tính từ luồng dữ liệu khi có yêu cầu integrity. Với file lớn cần hash streaming hoặc một bước verification riêng, không buffer toàn bộ vào RAM. Chuyển DB sang `Ready` bằng conditional update chỉ sau validation. Nếu DB update thất bại, blob staging còn orphan và job reconciliation sẽ xử lý; không giả định distributed transaction. Dùng idempotency key để retry trả cùng kết quả hoặc tiếp tục an toàn. Download chỉ phục vụ `Ready` và xác thực quyền tenant. Nếu dùng direct-to-Blob upload với SAS ngắn hạn, backend vẫn phải verify trước publish. Giới hạn MIME/extension không đủ để bảo đảm nội dung an toàn; áp dụng scanning theo risk.

**Rollout:** Unit test state transitions, integration test upload/verify/download, failure injection lúc client disconnect/instance restart/SQL failure, load test 600 MB nhiều upload đồng thời, canary theo phiên bản. Metric `verified_upload_success_rate`, orphan count, length mismatch, memory, p95 và error rate; alert khi mismatch > 0 trong cửa sổ thích hợp.

## Mẫu trả lời trong phỏng vấn

“Đây là sự cố integrity nên tôi ưu tiên ngừng tạo thêm file sai và giữ evidence. Tôi sẽ đối chiếu release timeline, correlation ID và byte counts ở client, API, Blob và download; chưa kết luận Blob lỗi. Các giả thuyết gồm trả 201 trước khi await upload, stream bị hủy khi restart, metadata DB sai sau retry hoặc download bị cắt. Tôi sẽ xác nhận bằng traces và tải raw blob đối chiếu. Về lâu dài tôi đưa upload qua trạng thái Pending → Verified → Ready, chỉ publish sau validation, thiết kế idempotency và reconciliation vì SQL và Blob không cùng transaction. Tôi chọn streaming, Managed Identity và canary release; đo tỷ lệ verified completion thay vì chỉ HTTP 2xx.”

## Câu hỏi đào sâu

1. Nếu Blob upload xong nhưng SQL commit thất bại, làm sao tránh mất dữ liệu hoặc orphan vĩnh viễn?
2. Khi client upload trực tiếp bằng SAS, backend chứng minh file hợp lệ trước khi cho download ra sao?
3. Khi traffic tăng gấp 10 và file 1 GB, bạn thay đổi protocol, memory budget và retry thế nào?

## Lỗi trả lời thường gặp

- Quy mọi lỗi cho Blob hoặc CDN mà không kiểm chứng.
- Trả 201 ngay sau khi tạo DB row.
- Buffer file 600 MB vào một byte array.
- Log SAS hoặc token trong structured logs.
- Không thử client disconnect và restart.

## Thang điểm 0–10

- Impact/stabilization: 1.5
- Evidence/hypotheses: 2
- Correctness và state model: 2
- Security/reliability: 1.5
- Test/observability/rollout: 2
- Giao tiếp incident: 1

# Câu 3 — Hiện đại hóa portal Angular/jQuery sang Vue.js mà không dừng vận hành

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Vue.js, ASP.NET MVC, .NET Framework 4.5, .NET 8, authentication, modernization, CI/CD, architecture trade-offs.

## Bối cảnh

Portal nhân sự nội bộ chạy ASP.NET MVC trên .NET Framework 4.5/IIS, giao diện gồm Angular cũ và nhiều màn jQuery. Có 60 workflow duyệt đơn, file upload và báo cáo. Một phần API đã chuyển sang ASP.NET Core .NET 8. Công ty muốn chuyển dần sang Vue.js để giảm chi phí bảo trì, không thể dừng hệ thống, 400 người dùng hoạt động đồng thời; ngân sách và deadline còn chưa chốt. Auth hiện dùng cookie ở ứng dụng legacy; yêu cầu audit, quyền theo phòng ban, rollback theo từng module.

## Câu hỏi chính

Thiết kế chiến lược incremental modernization, ranh giới frontend/backend và rollout an toàn. Khi nào nên giữ MVC, dùng Vue island, xây SPA mới, hoặc tách backend? Trình bày các điều kiện khiến bạn đổi quyết định.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào thay đổi thường xuyên và module nào rủi ro nghiệp vụ cao?
2. Browser support, SEO, accessibility và yêu cầu offline?
3. Auth cookie hiện có SameSite, CSRF protection, session storage và SSO như thế nào?
4. Có shared components/API contract, test coverage, audit trail và release automation chưa?
5. Thời gian được phép chạy song song, đội ngũ và ngân sách vận hành hai stack?

## Gợi ý tư duy

### Gợi ý 1
Đặt migration seam ở ranh giới route/module thay vì rewrite toàn bộ.

### Gợi ý 2
Xem auth, CSRF, deep link, state ownership và rollback trước khi chọn framework.

### Gợi ý 3
Thiết kế contract tests, feature flags, strangler routing và deployment độc lập có kiểm soát.

## Cấu trúc trả lời đề xuất

1. Inventory module, dependencies, risks, metrics.
2. Đề xuất target boundaries và các phương án.
3. Thiết kế auth/session, API contract, authorization.
4. Lộ trình pilot → expand → retire; data migration.
5. Testing, observability, rollback và tiêu chí thành công.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không mặc định full rewrite hoặc microservices.
- Phân tách UX modernization với backend modernization; migrate theo vertical slice.
- Authorization nằm ở server; frontend route guard không thay thế API checks.
- Xác định rollback khi module mới gây lỗi.

### Điểm cộng
- Vue islands hoặc route-level strangler tùy coupling; BFF nếu có lý do rõ.
- API versioning/contract tests và Playwright E2E cho critical workflows.
- Shared design system, feature flags, telemetry theo phiên bản.

### Senior+
- Đánh giá chi phí dual-run, cookie/session boundary, CSRF, SSO, audit, consistency.
- Xác định kill criteria, ownership và kế hoạch loại bỏ legacy dependencies.

## Hướng giải quyết tham khảo

**Giả định:** Portal nội bộ không cần SEO public; 400 concurrent users chưa đủ biện minh Kubernetes/microservices. Ưu tiên một module ít phụ thuộc, nhiều thay đổi, có test fixtures làm pilot. Inventory routes, permissions, shared jQuery globals, Angular services, form validation, file upload và server-side rendering dependencies; đo error rate, deployment frequency, lead time, page latency và lỗi người dùng trước khi thay.

**Phương án A — Vue islands:** Gắn component Vue vào trang MVC hiện tại. Ít thay đổi routing và auth, rollback đơn giản; nhưng phải quản lý lifecycle, tránh jQuery/Vue cùng mutate một DOM, bundle duplication và CSS collisions. Phù hợp form/widget nhỏ.

**Phương án B — Route-level strangler:** Chuyển một nhóm route sang frontend Vue mới qua routing/reverse proxy, API .NET 8 giữ ownership nghiệp vụ. Dễ tách build/test/deploy hơn nhưng phức tạp hơn ở navigation, auth và asset versioning. Ưu tiên khi module có boundary rõ và nhu cầu UX lớn.

**Phương án C — Big-bang SPA rewrite:** Chỉ cân nhắc nếu legacy không thể cô lập, phạm vi nhỏ và tổ chức chấp nhận rủi ro. Với 60 workflow và yêu cầu uptime, không phải lựa chọn mặc định.

**Security:** Nếu giữ cookie cùng origin, kiểm tra cookie scope, Secure, HttpOnly, SameSite, CSRF token trên state-changing requests, session fixation và logout propagation. Nếu frontend/backend khác origin, đánh giá CORS với credentials và CSRF rõ ràng; CORS không phải cơ chế authorization. Có thể dùng BFF khi cần tránh browser giữ access token và giảm complexity; không thêm chỉ vì xu hướng. API .NET 8 phải kiểm tra quyền theo phòng ban và resource, không tin frontend claims hay disabled button. Với SSO migration, chạy contract và security tests trước khi thay cookie flow.

**Architecture:** Giữ domain workflows và transaction ownership ở backend; không copy business rules sang Vue. Chốt API schema bằng OpenAPI, version/compatibility policy, error contract `ProblemDetails`, correlation ID và idempotency cho submit quan trọng. Shared components/design tokens được version hóa; tránh shared mutable frontend store xuyên các app không kiểm soát.

**Rollout:** Feature flag theo nhóm người dùng, pilot 1 workflow, canary, đo task completion, JS errors, Core Web Vitals nội bộ, API 4xx/5xx và audit completeness. Playwright E2E cho approval, role boundary, back navigation, upload và rollback; integration tests kiểm tra backward compatibility với MVC cũ. Mỗi slice có owner, data migration plan nếu cần, rollback routing/flag và kill criteria. Sau khi đạt SLO mới loại bỏ route và jQuery dependency tương ứng. CI/CD tạo artifact bất biến, kiểm tra môi trường staging gần production; không yêu cầu chuyển IIS sang container đồng thời.

**Khi đổi quyết định:** Nếu đa số màn hình là server-rendered đơn giản, giữ MVC hoặc Vue islands. Nếu các module có state phức tạp, cần UX tương tác mạnh và API contract ổn định, route-level Vue hợp lý. Nếu auth/session coupling quá lớn, ưu tiên tách authentication seam trước. Nếu thiếu E2E/observability, đầu tư nền tảng kiểm chứng trước migration diện rộng.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không rewrite 60 workflow cùng lúc. Đầu tiên tôi lập dependency map và chọn một vertical slice ít rủi ro để pilot. Với widget nhỏ, Vue island giữ được MVC và rollback dễ; với module độc lập, route-level strangler giúp deploy riêng. Tôi giữ nghiệp vụ và authorization trong backend, chuẩn hóa API contract và kiểm tra cookie/CSRF trước khi thay navigation. Tôi sẽ chạy Playwright cho workflow quan trọng, canary bằng feature flag, theo dõi error rate và task completion, đồng thời duy trì rollback theo module. Tôi chỉ tách service hoặc đổi hạ tầng nếu có bằng chứng về nhu cầu scaling, ownership hay release isolation đủ bù operational cost.”

## Câu hỏi đào sâu

1. Nếu cookie legacy không thể dùng an toàn qua frontend mới, bạn thiết kế migration auth thế nào?
2. Nếu mỗi module Vue cần release độc lập, micro-frontends có đáng giá hơn route-level app không?
3. Nếu pilot cải thiện tốc độ nhưng tăng lỗi approval, tiêu chí go/no-go của bạn là gì?

- Không có chiến lược rollback từng workflow.
- Đo thành công chỉ bằng số màn hình đã migrate.
