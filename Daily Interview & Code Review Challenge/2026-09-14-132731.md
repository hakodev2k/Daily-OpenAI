# Câu 1 — Hai transaction cùng “đặt chỗ thành công”: `READ COMMITTED`, lock và optimistic concurrency thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** SQL Server, EF Core, transaction isolation, locking, optimistic concurrency, correctness, production debugging

## Bối cảnh

Một booking API dùng ASP.NET Core + EF Core + SQL Server. Bảng `BookingSlots` lưu số lượng chỗ còn lại:

```text
BookingSlots
------------
Id
EventId
RemainingSeats
Version rowversion
```

Endpoint hiện tại:

```csharp
public async Task<Result> ReserveAsync(
    Guid slotId,
    int quantity,
    CancellationToken cancellationToken)
{
    await using var tx = await _db.Database
        .BeginTransactionAsync(cancellationToken);

    var slot = await _db.BookingSlots
        .SingleAsync(x => x.Id == slotId, cancellationToken);

    if (slot.RemainingSeats < quantity)
        return Result.SoldOut();

    slot.RemainingSeats -= quantity;

    await _db.SaveChangesAsync(cancellationToken);
    await tx.CommitAsync(cancellationToken);

    return Result.Success();
}
```

Production xuất hiện case hiếm:

- slot còn 1 chỗ;
- hai requests gần như đồng thời đều đọc thấy `RemainingSeats = 1`;
- business log cho thấy cả hai caller đều nhận success ở một số version trước đây;
- team sau đó thêm `rowversion`, và bắt đầu thấy `DbUpdateConcurrencyException` ở một request;
- một developer cho rằng “đã có transaction thì không thể oversell”;
- người khác đề xuất đổi toàn bộ database sang `SERIALIZABLE`;
- DBA nói database đang dùng mặc định `READ COMMITTED`; team chưa rõ có bật `READ_COMMITTED_SNAPSHOT` hay không;
- Product muốn correctness cao nhưng vẫn phải chịu được burst hàng trăm reservation/second cho cùng event.

## Câu hỏi chính

Hãy giải thích cơ chế khiến hai transactions có thể cùng đọc một giá trị khả dụng nhưng không đồng nghĩa cả hai update đều an toàn. Phân biệt transaction boundary, isolation level, shared/exclusive locks, row-versioning-based reads và EF Core optimistic concurrency. Sau đó đề xuất cách đảm bảo invariant “không bao giờ bán vượt quá số chỗ” với throughput hợp lý và nêu cách xác minh behavior thực tế trên production database.

## Câu hỏi làm rõ nên cân nhắc

1. `READ_COMMITTED_SNAPSHOT` hiện có bật không?
2. `rowversion` đã được map thành concurrency token trong EF Core chưa?
3. Một reservation có thể giữ nhiều loại slot trong cùng transaction không?
4. Business có chấp nhận retry ngắn khi conflict không?
5. Hotspot tập trung trên một `slotId` hay phân tán nhiều rows?

## Gợi ý tư duy

### Gợi ý 1

“Có transaction” không tự xác định transaction sẽ serialize mọi read/write với transaction khác.

### Gợi ý 2

Một read ở `READ COMMITTED` có thể chỉ bảo vệ việc đọc tại thời điểm đó; invariant nhiều bước `read → check → update` cần cơ chế concurrency rõ ràng.

### Gợi ý 3

Hãy nghĩ theo invariant ở database layer: update chỉ được phép xảy ra nếu số chỗ vẫn đủ tại thời điểm write.

## Cấu trúc trả lời đề xuất

1. Clarify isolation/database settings.
2. Dựng timeline hai concurrent requests.
3. Giải thích read/write locking hoặc row-versioned read tùy database option.
4. Phân biệt transaction với serial execution.
5. Giải thích EF Core concurrency token.
6. So sánh optimistic concurrency với atomic conditional update.
7. Xem xét `SERIALIZABLE`/locking khi contention cao.
8. Thiết kế retry policy có giới hạn.
9. Kiểm thử concurrency thật trên SQL Server.
10. Theo dõi conflict rate, lock waits và business invariant.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Transaction chỉ đảm bảo atomicity/isolation theo isolation semantics đang dùng; nó không có nghĩa các transactions chạy lần lượt.
- `READ COMMITTED` ngăn đọc uncommitted data nhưng không mặc định biến một chuỗi `SELECT` rồi `UPDATE` thành một reservation lock kéo dài tới commit.
- Nếu database dùng row-versioning cho `READ COMMITTED`, read có thể không block writer theo cách developer kỳ vọng; cần xác minh setting thực tế.
- `rowversion` + EF Core concurrency token khiến `UPDATE` có điều kiện theo version cũ; nếu row đã đổi, affected rows = 0 và EF Core báo `DbUpdateConcurrencyException`.
- Concurrency exception phải được xử lý như business conflict/retry, không phải 500 ngẫu nhiên.
- Invariant có thể được enforce tốt bằng atomic conditional update, ví dụ chỉ decrement khi `RemainingSeats >= quantity`.

### Điểm cộng

- Đề xuất SQL dạng:

```sql
UPDATE BookingSlots
SET RemainingSeats = RemainingSeats - @quantity
WHERE Id = @slotId
  AND RemainingSeats >= @quantity;
```

và kiểm tra affected rows.
- Nhận ra atomic conditional update tránh read-check-write race và thường đơn giản hơn giữ lock dài.
- Nếu vẫn cần đọc thêm state, dùng concurrency token và bounded retry với re-read.
- Có database constraint như `CHECK (RemainingSeats >= 0)` làm defense-in-depth.
- Không retry vô hạn trên hot row vì có thể tạo retry storm.

### Senior+

- Phân tích trade-off giữa optimistic conflict retries và pessimistic/serializable locking khi contention cực cao.
- Nếu reservation chạm nhiều rows, cần lock ordering hoặc transaction design để giảm deadlock.
- Tách temporary hold với final purchase nếu business có payment window, expiration và release semantics.
- Đo conflict rate/hot keys trước khi thay isolation toàn database.
- Nhận ra `SERIALIZABLE` toàn hệ thống có thể tăng blocking/deadlock và không phải default answer.

## Hướng giải quyết tham khảo

Vấn đề cốt lõi là transaction không đồng nghĩa với “critical section toàn cục”. Hai requests có thể bắt đầu hai transactions khác nhau và cùng quan sát trạng thái phù hợp tại các thời điểm gần nhau. Behavior chính xác của read phụ thuộc isolation level và database options, nên trước hết phải xác minh `READ_COMMITTED_SNAPSHOT` thay vì giả định.

Với optimistic concurrency, `rowversion` là cơ chế phát hiện write conflict. EF Core thường gửi `UPDATE ... WHERE Id = @id AND Version = @originalVersion`. Nếu transaction khác đã update row trước, version đổi và request sau update 0 rows; EF Core phát `DbUpdateConcurrencyException`. Điều này biến silent lost update thành explicit conflict.

Tuy nhiên, với invariant đơn giản “không decrement xuống dưới 0”, tôi ưu tiên atomic conditional update tại database thay vì `SELECT` rồi quyết định trong application:

```sql
UPDATE dbo.BookingSlots
SET RemainingSeats = RemainingSeats - @quantity
WHERE Id = @slotId
  AND RemainingSeats >= @quantity;
```

Nếu affected rows = 1 thì reservation thành công; nếu 0 thì sold out hoặc row không tồn tại. Có thể thêm `CHECK (RemainingSeats >= 0)` để database bảo vệ invariant ngay cả khi có code path khác.

Nếu domain cần nhiều validation khác hoặc update nhiều rows, optimistic concurrency vẫn hữu ích. Khi conflict, application re-read state rồi retry tối đa một số lần nhỏ với jitter nếu business operation còn hợp lệ. Conflict cao trên cùng hot row là signal kiến trúc/workload cần xem lại, không phải lý do retry vô hạn.

`SERIALIZABLE` có thể bảo vệ một số read-range invariants nhưng đổi lại blocking cao hơn và deadlock risk. Tôi chỉ dùng cho transaction thật sự cần semantics đó, không bật blanket cho toàn database.

Để xác minh production, tôi lấy database setting thực tế, execution/lock waits, deadlock graphs nếu có, và chạy integration concurrency test với SQL Server thật: 100–1000 tasks cùng reserve từ một slot có N seats, rồi assert tổng success không vượt N và `RemainingSeats` không âm.

## Mẫu trả lời trong phỏng vấn

“Transaction không có nghĩa hai requests được serialize. Với `READ COMMITTED`, mỗi transaction vẫn có thể đọc một trạng thái hợp lệ rồi cạnh tranh update. Nếu dùng row-versioned reads thì read còn có thể không block writer như team tưởng. Vì vậy tôi phải xác minh database setting thực tế.

`rowversion` trong EF Core là optimistic concurrency: update chỉ thành công nếu version vẫn giống lúc đọc. Nếu row đã đổi, EF báo concurrency exception. Tôi xử lý đó như conflict chứ không phải 500.

Với invariant đơn giản về số ghế, tôi thích atomic conditional update `RemainingSeats = RemainingSeats - quantity WHERE RemainingSeats >= quantity`, kiểm tra affected rows và thêm check constraint. Nếu domain phức tạp hơn tôi kết hợp concurrency token với bounded retry. Tôi không bật `SERIALIZABLE` toàn hệ thống nếu chưa đo contention và lock impact.”

## Câu hỏi đào sâu

1. Nếu cần reserve đồng thời ba loại ticket trong một order, atomic update từng row có còn đủ không?
2. Trong trường hợp contention cực cao trên một row, khi nào bạn chuyển từ optimistic sang pessimistic coordination?
3. Nếu API retry sau timeout nhưng transaction trước thực ra đã commit, bạn ngăn duplicate reservation bằng cách nào?

## Lỗi trả lời thường gặp

- Nghĩ có transaction là tự động tránh mọi race condition.
- Đề xuất `SERIALIZABLE` cho toàn database mà không đo blocking.
- Catch `DbUpdateConcurrencyException` rồi retry vô hạn.
- Chỉ kiểm tra `RemainingSeats` trong application mà không enforce invariant ở write/database layer.
- Không xác minh `READ_COMMITTED_SNAPSHOT` trước khi giải thích behavior.

## Thang điểm 0–10

- **0–2:** Đồng nhất transaction với serial execution.
- **3–4:** Biết concurrency conflict nhưng không giải thích isolation/write invariant.
- **5–6:** Giải thích đúng optimistic concurrency và đưa ra conditional update hợp lý.
- **7–8:** Có retry policy, constraint, lock/contention analysis và integration concurrency test.
- **9–10:** Reasoning tốt về isolation variants, hot-row contention, multi-row invariants và operational evidence.

# Câu 2 — IIS application pool recycle liên tục: memory leak, configuration hay health-monitoring loop?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET Core hosting, process lifecycle, memory, health checks, logs, observability, incident response

## Bối cảnh

Một legacy-modernized ASP.NET Core application vẫn chạy trên Windows Server sau IIS. Hệ thống phục vụ khoảng 2.000 concurrent users giờ cao điểm.

Sáng thứ Hai, user báo login ngẫu nhiên bị mất session và một số request nhận 502/503 trong vài chục giây. Operations quan sát:

- `w3wp.exe` PID thay đổi nhiều lần trong một giờ;
- application startup log xuất hiện lặp lại;
- memory của process thường tăng lên khoảng vài GB trước một số lần recycle, nhưng không phải lần nào cũng vậy;
- Windows Event Viewer có cả IIS/WAS events và một vài event liên quan application crash;
- Application Insights có spike 5xx trùng với startup periods;
- một health-monitor script nội bộ gọi endpoint `/health` mỗi 5 giây và có quyền recycle App Pool nếu 3 lần liên tiếp fail;
- `/health` hiện kiểm tra SQL, Redis và một external CRM API;
- CRM API đôi lúc timeout 20–30 giây;
- App Pool cũng có cấu hình recycling theo private-memory threshold và periodic interval do operations thiết lập từ lâu;
- một developer kết luận memory leak;
- operations muốn tăng threshold và tắt health monitor ngay;
- Product yêu cầu ổn định dịch vụ trước, sau đó mới RCA.

## Câu hỏi chính

Hãy xử lý incident theo **impact → stabilize → evidence → hypotheses → verification → root cause → remediation → prevention**. Bạn phải phân biệt ít nhất ba khả năng: process bị recycle do IIS policy, process crash do application/runtime, và external health-monitor tự recycle vì dependency failure. Nêu evidence cụ thể cần lấy, cách giảm user impact ngay lập tức, và thiết kế health checks/recycling/observability để một CRM outage không biến thành restart loop của toàn application.

## Câu hỏi làm rõ nên cân nhắc

1. Session state nằm in-process hay externalized?
2. Exact IIS App Pool recycle settings và event reason codes là gì?
3. `/health` là liveness hay readiness, và dependency nào được coi là critical?
4. Crash dumps hoặc Windows Error Reporting data có tồn tại không?
5. CRM timeout có saturate ThreadPool/connections trước khi health endpoint fail không?

## Gợi ý tư duy

### Gợi ý 1

“PID đổi” là symptom của process replacement; chưa chứng minh nguyên nhân là memory leak.

### Gợi ý 2

Một health check dùng dependency không critical có thể tự tạo cascading failure nếu fail dẫn đến process recycle.

### Gợi ý 3

Hãy correlate IIS/WAS events, application exit/crash evidence và health-monitor actions theo cùng timeline.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact.
2. Stabilize restart loop an toàn.
3. Lập timeline PID/recycle/crash/health actions.
4. Thu thập IIS/WAS/Event Viewer/dump evidence.
5. So sánh memory-trigger, scheduled recycle, crash và monitor-trigger.
6. Điều tra dependency timeout/ThreadPool nếu liên quan.
7. Sửa health semantics.
8. Sửa recycle policy/session behavior.
9. Load/failure test.
10. Dashboard/alerts/runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận memory leak chỉ vì process memory tăng trước recycle.
- IIS recycle reason, process exit code/crash dump và external monitor action phải được phân biệt bằng evidence.
- Health endpoint không nên biến temporary failure của một optional/degraded dependency thành liveness failure buộc process restart.
- Restart process thường không chữa external CRM outage và có thể làm outage nặng hơn do cold start/cache warm-up/session loss.
- Immediate stabilization có thể là tạm ngừng auto-recycle từ non-critical health failure, nhưng phải giữ monitoring và guardrails.
- Nếu session in-process, recycle trực tiếp ảnh hưởng user; cần hiểu persistence strategy.

### Điểm cộng

- Tách liveness (`process có sống/serving được không`) khỏi readiness/dependency health.
- External CRM có thể được báo `Degraded` thay vì `Unhealthy` nếu core app vẫn phục vụ được.
- Health check cần timeout ngắn, bounded và không serially chờ nhiều dependency lâu.
- Capture dump khi private bytes/GC heap vượt threshold trước khi recycle để điều tra leak.
- Correlate process start time, PID, recycle reason và deployment/config changes.

### Senior+

- Xem memory pattern theo private bytes, managed heap, native allocations, handle count và working set thay vì một metric duy nhất.
- Nếu health checker tự recycle, thêm backoff/circuit breaker cho remediation action để tránh restart storm.
- Dùng graceful shutdown/drain và external session store nếu availability requirement cần chịu recycle.
- Tách dependency availability khỏi application process health trong SLO/alerts.
- Xây runbook xác định khi nào recycle là valid remediation và khi nào phải preserve process để capture evidence.

## Hướng giải quyết tham khảo

Trước hết tôi giảm blast radius. Nếu evidence ban đầu cho thấy health-monitor đang recycle app vì CRM timeout, tôi tạm disable **remediation action** của monitor hoặc đổi CRM failure thành degraded signal, nhưng vẫn giữ alert. Tôi không tắt toàn bộ monitoring.

Sau đó tôi dựng timeline theo phút/giây gồm PID, App Pool recycle events, WAS reasons, Windows crash events, application shutdown/start logs, health-monitor decisions và CRM latency. Nếu IIS recycle do periodic schedule hoặc private-memory limit, event logs/config sẽ cho bằng chứng khác với process crash. Nếu process crash, cần exit code, exception/runtime event và dump. Nếu external monitor chủ động recycle, audit log/script execution phải cho thấy action.

Memory cần điều tra riêng. “Memory tăng” chưa đủ nói leak. Tôi xem private bytes, managed heap, LOH, GC collections, handles, native memory và trend qua nhiều cycles. Nếu nghi leak, capture dump trước threshold thay vì cứ recycle rồi mất evidence.

Health design phải tách semantics. Liveness chỉ nên fail khi process không thể tiếp tục phục vụ. Readiness có thể phản ánh critical dependencies. CRM nếu không phải dependency bắt buộc cho mọi request nên có status degraded riêng. Health calls cần timeout nhỏ hơn đáng kể so với request timeout và không để một API ngoài treo 20–30 giây mỗi probe.

Nếu CRM là feature-specific dependency, application nên degrade feature đó bằng timeout/circuit-breaker/fallback hợp lý thay vì làm toàn site unhealthy. Auto-remediation như recycle cần rate limit/backoff và chỉ dựa trên signal phù hợp.

IIS recycle policy cũng cần review: periodic recycle có thể hợp lệ về operations nhưng phải biết impact; private-memory threshold không nên là substitute cho leak fix. Nếu session đang in-process, cần externalize session hoặc chấp nhận rõ user impact khi recycle.

Sau RCA, tôi thêm dashboard cho process uptime/PID changes, recycle reasons, crash count, private bytes/managed heap, health state per dependency, CRM latency/error rate, startup duration và 5xx. Alert riêng cho restart frequency để phát hiện loop sớm.

## Mẫu trả lời trong phỏng vấn

“PID đổi chỉ cho tôi biết process bị thay thế, chưa cho biết tại sao. Tôi sẽ correlate IIS/WAS recycle reasons, Event Viewer crash events, application exit/start logs và health-monitor audit. Đồng thời tôi stabilize bằng cách ngăn non-critical CRM health failure tự recycle App Pool nếu đó đang tạo restart storm, nhưng vẫn giữ alert.

Tôi tách liveness khỏi readiness/dependency health. CRM timeout không nên làm liveness fail nếu core app vẫn hoạt động. Memory cũng phải được chứng minh bằng private bytes, managed/native heap và dump trước recycle chứ không chỉ nhìn working set.

Sau đó tôi sửa auto-remediation có backoff, health timeout ngắn, graceful recycle và session strategy phù hợp. Mục tiêu là external dependency outage không biến thành process restart loop.”

## Câu hỏi đào sâu

1. Nếu CRM thực sự là dependency bắt buộc cho login, bạn thay đổi readiness/liveness strategy thế nào?
2. Khi nào private-memory recycling là guardrail hợp lý dù leak chưa được fix?
3. Nếu app chuyển từ IIS/Windows sang App Service Linux, những nguyên tắc điều tra nào vẫn giữ nguyên?

## Lỗi trả lời thường gặp

- Thấy memory cao là kết luận memory leak.
- Restart liên tục external dependency outage thay vì degrade dependency.
- Gộp liveness và readiness thành một endpoint với mọi dependency.
- Tắt toàn bộ monitoring để “hết recycle”.
- Không lấy crash dump/recycle reason trước khi thay config.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/tăng memory.
- **3–4:** Biết xem Event Viewer nhưng không phân biệt recycle/crash/monitor action.
- **5–6:** Có timeline evidence, health semantics và stabilization hợp lý.
- **7–8:** Có memory diagnostics, graceful behavior, session/restart-loop analysis và telemetry.
- **9–10:** Incident reasoning rõ ràng, guardrails tốt và thiết kế operational health/remediation có điều kiện.

# Câu 3 — Modernize .NET Framework 4.5 monolith: in-place migration, Strangler hay rewrite?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, architecture, ASP.NET, migration strategy, dependency analysis, database boundaries, testing, rollout, rollback, observability, technical debt

## Bối cảnh

Một enterprise portal 9 năm tuổi đang chạy:

- .NET Framework 4.5;
- ASP.NET MVC + Web API;
- IIS/Windows Server;
- SQL Server dùng chung cho toàn hệ thống;
- khoảng 1,2 triệu lines code;
- nhiều class libraries nội bộ;
- một số dependencies cũ không còn maintained;
- authentication tích hợp với corporate identity cũ;
- frontend pha trộn Razor, jQuery và một ít Angular legacy;
- deploy mỗi 2–3 tuần bằng TeamCity + Octopus Deploy;
- test automation yếu, phần lớn regression dựa vào QA manual;
- uptime requirement cao vì portal dùng bởi nhiều business units.

Business muốn chuyển dần sang modern .NET để:

- giảm security/support risk;
- chạy được ASP.NET Core;
- cải thiện deployment/observability;
- mở đường cho Linux/App Service/container nếu hợp lý;
- vẫn ship feature mới trong quá trình migration.

Ba đề xuất đang cạnh tranh:

1. **Big-bang rewrite** sang .NET 10 + React + microservices.
2. **In-place incremental migration** solution hiện tại lên các target/framework mới từng bước.
3. **Strangler-style modernization**: giữ monolith, tách dần capability có boundary rõ sang ASP.NET Core modules/services mới.

Không proposal nào mặc định đúng. Team có khoảng 10 developers và không thể freeze feature development hơn vài tuần.

## Câu hỏi chính

Hãy xây migration strategy thực tế cho hệ thống này. Bạn phải phân loại dependencies và code theo mức độ migratable, xác định testing/observability baseline trước khi thay đổi lớn, chọn khi nào nên migrate in-place và khi nào nên strangler/tách boundary, xử lý shared database/authentication/deployment coexistence, và thiết kế rollout/rollback theo nhiều phase. Cuối cùng hãy giải thích tại sao bạn chọn hoặc không chọn rewrite/microservices trong bối cảnh cụ thể này.

## Câu hỏi làm rõ nên cân nhắc

1. Những dependencies nào khóa .NET Framework/Windows-only và có replacement không?
2. Các modules hiện có coupling qua database tables hay qua application APIs/interfaces?
3. Business capability nào có thay đổi nhiều nhất và capability nào ổn định nhất?
4. Authentication hiện tại có thể được bridge sang modern identity/OIDC hay cần coexistence dài hạn?
5. Deployment topology có cho phép old/new applications chạy song song dưới cùng domain không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng target architecture. Bắt đầu bằng **inventory + dependency graph + regression safety**.

### Gợi ý 2

Migration strategy có thể là hybrid: một số libraries migrate in-place, một số capability strangler, một số legacy code giữ nguyên tạm thời.

### Gợi ý 3

Shared database và identity thường là hai coupling points quyết định tốc độ tách hệ thống.

## Cấu trúc trả lời đề xuất

1. Inventory runtime/dependencies/Windows coupling.
2. Xây baseline tests và production telemetry.
3. Phân loại migration units theo risk/coupling/business value.
4. Modernize shared libraries nơi khả thi.
5. Thiết kế coexistence routing old/new.
6. Xử lý database ownership và transaction boundaries.
7. Xử lý authentication/session/user context.
8. Rollout theo vertical slices.
9. Rollback/feature flags/traffic controls.
10. Xác định trigger cho service extraction hoặc hosting change.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Big-bang rewrite có risk lớn vì feature freeze, regression surface và parity khó chứng minh.
- Trước migration lớn cần dependency inventory, critical user-flow tests và observability baseline.
- Không phải mọi component cần thành microservice; service extraction chỉ hợp lý khi boundary/ownership/scale/deploy need biện minh được.
- Có thể migrate libraries/components từng bước nếu compatibility cho phép, đồng thời strangler các capability có boundary rõ.
- Shared database cần kế hoạch ownership dần dần; tách HTTP service nhưng vẫn sửa cùng tables có thể chỉ tạo distributed monolith.
- Old/new systems cần coexistence routing và rollback plan thực tế.
- Authentication/authorization semantics phải giữ nhất quán trong giai đoạn coexistence.

### Điểm cộng

- Dùng characterization/integration tests cho behavior legacy chưa có test.
- Ưu tiên capability có business value cao nhưng coupling thấp làm pilot.
- Đặt API façade/reverse proxy/routing layer để chuyển traffic dần thay vì cutover toàn bộ.
- Tách read path trước write path nếu giúp giảm risk trong một số modules.
- Giữ deployment artifacts độc lập nhưng không nhất thiết tạo microservices domain ngay.

### Senior+

- Phân loại dependencies: source-compatible, replaceable, Windows-only, unsupported, protocol/database coupling.
- Dùng anti-corruption layer khi modern module phải gọi legacy concepts/API.
- Định nghĩa migration success metrics: deployment frequency, failure rate, p95, incident rate, test coverage của critical flows, percentage traffic/capabilities moved.
- Có database evolution strategy theo expand-contract để old/new code coexist.
- Hosting move sang Linux/container chỉ thực hiện khi application compatibility và operational benefit đủ rõ; không trộn mọi modernization dimension trong một release.

## Hướng giải quyết tham khảo

Tôi sẽ không chọn big-bang rewrite mặc định. Với 1,2 triệu lines code, test automation yếu, 10 developers và requirement tiếp tục ship feature, rewrite toàn bộ tạo một khoảng thời gian dài nơi team phải duy trì old system nhưng vẫn xây parity ở new system. Risk lớn nhất không phải viết code mới mà là behavior ẩn chưa được capture.

Phase đầu là **discovery + safety net**. Tôi inventory assemblies, NuGet/vendor dependencies, COM/Windows-specific integrations, configuration, authentication, scheduled jobs, database access và deployment. Đồng thời thêm Application Insights/structured logging nếu chưa có, và dựng characterization/integration tests cho critical business flows thay vì cố unit-test toàn bộ legacy code.

Sau đó tôi phân loại:

- libraries có thể multi-target hoặc port tương đối độc lập;
- web/API layers cần ASP.NET Core migration;
- capability có boundary tốt để strangler;
- dependencies Windows-only/unsupported cần replacement;
- code quá coupled cần refactor seam trước khi migrate.

Một hybrid path hợp lý có thể là:

1. nâng compiler/libraries và dependencies nơi an toàn;
2. cô lập business logic khỏi `System.Web`/IIS-specific APIs;
3. tạo ASP.NET Core application mới cho một capability pilot;
4. route một subset URL/traffic sang new app qua reverse proxy/gateway;
5. bridge identity bằng protocol/token hoặc shared trusted identity abstraction;
6. dùng expand-contract cho schema changes để old/new cùng chạy;
7. dần chuyển table ownership/API boundary thay vì cho mọi service truy cập DB chung vô thời hạn.

Tôi không tách microservice chỉ vì đang migrate. Nếu một capability cần independent scale, ownership, release cadence hoặc fault isolation rõ, service extraction có thể hợp lý. Nếu không, ASP.NET Core modular monolith mới vẫn có thể là destination tốt hơn.

Rollback phải tồn tại ở từng slice. Traffic có thể chuyển lại old route nếu new capability lỗi, miễn database change vẫn backward-compatible. Feature flags/canary traffic giúp giảm blast radius. Mỗi phase cần telemetry so sánh old/new latency, error rate và business correctness.

Frontend cũng không cần rewrite đồng loạt. Có thể giữ Razor/jQuery nơi ổn định, rồi modernize màn hình có business churn cao sang Vue/React khi ROI rõ. Nếu cố đồng thời đổi runtime, architecture, frontend framework, database ownership và hosting model, failure surface sẽ quá lớn.

Sau khi application đã portable và vận hành ổn trên modern .NET, mới đánh giá Linux/App Service/container dựa trên cost/operations/compatibility. Hosting migration không phải mục tiêu tự thân.

## Mẫu trả lời trong phỏng vấn

“Tôi chọn incremental/hybrid migration chứ không rewrite mặc định. Việc đầu tiên là inventory dependencies và dựng safety net: critical-flow tests, structured logs và baseline production metrics. Sau đó tôi phân loại component nào port in-place được, capability nào có boundary tốt để strangler, và dependency nào khóa Windows/.NET Framework.

Tôi sẽ tạo một ASP.NET Core pilot cho vertical slice coupling thấp, route traffic dần sang nó, giữ auth semantics nhất quán và dùng expand-contract cho database để old/new cùng chạy. Shared DB ownership được tách dần; nếu new service vẫn sửa cùng tables với monolith thì chưa thật sự độc lập.

Microservices chỉ dùng khi có ownership/scale/deployment/fault-isolation need cụ thể. Frontend và hosting cũng không đổi đồng loạt. Mỗi slice phải rollback được và có metrics chứng minh tốt hơn trước khi tiếp tục.”

## Câu hỏi đào sâu

1. Nếu dependency business-critical chỉ chạy trên .NET Framework/Windows và vendor không có roadmap, bạn cô lập nó thế nào?
2. Nếu old và new modules cần update cùng một transaction trong shared database, bạn có tách service ngay không?
3. Khi nào bạn quyết định dừng strangler và chấp nhận giữ một phần monolith lâu dài?

## Lỗi trả lời thường gặp

- Chọn rewrite vì code cũ “xấu” mà không định lượng risk/parity.
- Tách microservices trước khi hiểu domain/database coupling.
- Migrate runtime, frontend, DB và infrastructure cùng một cutover.
- Không dựng regression safety net trước modernization.
- Gọi shared-database services là microservices hoàn chỉnh mà không nói tới coupling.

## Thang điểm 0–10

- **0–2:** Chỉ chọn rewrite hoặc nâng version mà không có rollout strategy.
- **3–4:** Có incremental idea nhưng thiếu dependency/testing/database reasoning.
- **5–6:** Có hybrid migration, coexistence, testing và rollback hợp lý.
- **7–8:** Có boundary/data/auth/deployment strategy và criteria cho service extraction.
- **9–10:** Migration roadmap có thể vận hành thực tế, đo được progress/risk và tránh over-engineering.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Transaction không đồng nghĩa các requests được serialize; correctness phụ thuộc isolation semantics và write invariant.
- EF Core optimistic concurrency với `rowversion` biến lost-update risk thành explicit conflict cần xử lý.
- Atomic conditional update thường là cách đơn giản, mạnh để enforce inventory/seat invariant.
- IIS process restart phải được điều tra bằng recycle reason/crash/monitor evidence, không suy luận từ PID hoặc memory đơn lẻ.
- Liveness, readiness và dependency health cần semantics khác nhau để tránh auto-remediation tạo restart loop.
- Legacy modernization hiệu quả thường là hybrid, incremental và reversible thay vì big-bang rewrite.
- Shared database, identity và regression safety là các coupling points quyết định migration speed.

## Mẫu tư duy cần nhớ

- **Enforce business invariants tại write boundary, không chỉ trong application check.**
- **Stabilize trước, rồi dựng timeline evidence trước khi kết luận RCA.**
- **Phân biệt process health với dependency health.**
- **Migration lớn phải có coexistence window và rollback ở từng bước.**
- **Không tăng architectural complexity nếu boundary/scale/ownership chưa biện minh được.**
