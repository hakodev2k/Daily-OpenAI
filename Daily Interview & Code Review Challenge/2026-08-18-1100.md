# Câu 1 — EF Core Tracking và truy vấn chậm bất thường trong API production

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** EF Core internals, query analysis, performance troubleshooting

## Bối cảnh

Một ASP.NET Core API quản lý đơn hàng sử dụng EF Core. Sau khi thêm màn hình báo cáo mới, một số endpoint tăng latency từ 300ms lên 8-10 giây khi dữ liệu tăng. Developer cho rằng nguyên nhân là database chậm.

Code hiện tại sử dụng LINQ projection kết hợp Include và tracking mặc định. Chưa rõ dữ liệu thực tế, execution plan và lượng entity được load.

## Câu hỏi chính

Hãy giải thích EF Core thực hiện những gì bên trong khi truy vấn này chạy. Vì sao một query có thể trở nên chậm dù SQL nhìn có vẻ hợp lý? Những hiểu nhầm nào thường gặp về tracking, Include và projection? Bạn sẽ xác minh giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- API này phục vụ bao nhiêu request/phút?
- Số lượng record trung bình và lớn nhất là bao nhiêu?
- Query có cần update entity sau khi đọc không?
- SQL generated là gì?

## Gợi ý tư duy

- Gợi ý 1: Đừng chỉ nhìn C# code, hãy xem pipeline từ LINQ đến SQL.
- Gợi ý 2: Quan tâm tracking, materialization và execution plan.
- Gợi ý 3: Tách read model khỏi update model nếu cần.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu deferred execution.
- Biết EF Core translate LINQ thành SQL.
- Biết tracking tạo overhead.

### Điểm cộng
- Đề cập AsNoTracking, projection, query plan.

### Nâng cao
- Thiết kế read/write model riêng.

# Câu 2 — Thiết kế hệ thống notification platform

**Loại câu hỏi:** System design
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 30 phút
**Kỹ năng được đánh giá:** Architecture, scalability, reliability

## Bối cảnh

Một hệ thống SaaS cần gửi email, push notification và Microsoft Teams notification cho hàng triệu sự kiện mỗi ngày. Hiện tại một API gọi trực tiếp provider bên ngoài gây timeout khi traffic tăng.

## Câu hỏi chính

Thiết kế giải pháp mới. Hãy trình bày yêu cầu, kiến trúc, data flow, xử lý retry, idempotency, monitoring và trade-off.

## Câu hỏi làm rõ nên cân nhắc

- Notification có cần gửi đúng thứ tự không?
- Có tenant isolation không?
- Có SLA nào không?
- Provider lỗi trong bao lâu?

## Gợi ý tư duy

- Tách request path và processing path.
- Retry phải đi cùng idempotency.
- Observability là một phần của design.

## Hướng giải quyết tham khảo

Có thể bắt đầu bằng modular monolith với background worker, queue abstraction, database lưu trạng thái notification. Chỉ tách service khi có nhu cầu scale độc lập.

# Câu 3 — Xây dựng AI coding review agent

**Loại câu hỏi:** AI engineering
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 25 phút
**Kỹ năng được đánh giá:** AI architecture, evaluation, security

## Bối cảnh

Team muốn xây dựng agent hỗ trợ review pull request cho repository .NET. Agent có quyền đọc source code, issue, documentation và chạy một số tool.

## Câu hỏi chính

Thiết kế agent này như thế nào để tạo giá trị thực tế nhưng tránh hallucination và rủi ro bảo mật?

## Câu hỏi làm rõ nên cân nhắc

- Agent có quyền comment trực tiếp không?
- Context repository lớn đến mức nào?
- Có dữ liệu nhạy cảm không?

## Gợi ý tư duy

- Không để LLM tự quyết định mọi thứ.
- Tool permission cần giới hạn.
- Output cần validation.

## Hướng giải quyết tham khảo

Sử dụng workflow gồm collect context → analyze → generate structured findings → validate → human approval. Đo quality bằng precision của issue tìm được, false positive và developer feedback.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Hiểu runtime behavior quan trọng hơn ghi nhớ API.
- Architecture cần bắt đầu từ requirement và trade-off.
- AI system cần deterministic validation.

## Mẫu tư duy cần nhớ

- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Treat observability as part of design.
