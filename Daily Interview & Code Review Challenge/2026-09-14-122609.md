# Câu 1 — API bị p99 latency tăng mạnh dù CPU trung bình thấp: LOH, Gen 2 GC hay chỉ là “memory nhiều”?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** C#, .NET memory management, GC, LOH, allocations, ASP.NET Core, serialization, buffering, performance profiling, production diagnostics

## Bối cảnh

Một ASP.NET Core API sinh file export JSON cho khách hàng doanh nghiệp. Endpoint đọc khoảng 30.000–120.000 records từ SQL Server, map sang DTO rồi serialize toàn bộ payload trước khi trả về client.

Code rút gọn:

```csharp
public async Task<IActionResult> ExportAsync(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    var rows = await _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
        .OrderBy(x => x.CreatedAt)
        .Select(x => new ExportRow
        {
            Id = x.Id,
            ReferenceNo = x.ReferenceNo,
            CustomerName = x.CustomerName,
            Notes = x.Notes,
            Total = x.Total,
            CreatedAt = x.CreatedAt
        })
        .ToListAsync(cancellationToken);

    var json = JsonSerializer.Serialize(rows);
    var bytes = Encoding.UTF8.GetBytes(json);

    return File(bytes, "application/json", "orders.json");
}
```

Production có workload như sau:

- request bình thường dưới 500 ms;
- export lớn mất 4–20 giây;
- khi có nhiều export đồng thời, p99 của **các endpoint không liên quan** cũng tăng mạnh;
- CPU trung bình toàn process chỉ 35–50%, nhưng đôi lúc có các khoảng pause rõ rệt;
- memory tăng nhanh khi export chạy rồi giảm không đều;
- Application Insights không cho thấy SQL luôn chậm tương ứng;
- GC metrics có thời điểm Gen 2 collections tăng;
- process không OOM;
- một developer kết luận “GC không thể là nguyên nhân vì CPU chưa cao”;
- developer khác muốn gọi `GC.Collect()` sau mỗi export;
- một người đề xuất tăng RAM trước rồi tối ưu sau;
- business vẫn cần hỗ trợ export lớn nhưng chấp nhận response theo stream hoặc background download nếu UX hợp lý.

Bạn chưa được phép giả định LOH là root cause cuối cùng. Cần phân biệt ít nhất các khả năng:

- allocations lớn và short-lived;
- LOH pressure;
- string + byte[] duplication do serialize toàn bộ;
- EF materialization tạo object graph lớn;
- JSON serialization CPU;
- SQL query chậm;
- ThreadPool pressure;
- network/backpressure;
- compression overhead;
- GC pause chỉ là symptom phụ.

## Câu hỏi chính

Hãy giải thích cơ chế memory/GC nào có thể khiến một endpoint export lớn làm p99 toàn process tăng dù CPU trung bình không cao. Phân tích các allocation trong code, vai trò của LOH và Gen 2 GC, tại sao `GC.Collect()` là một “fix” nguy hiểm, cách phân biệt GC pressure với SQL/network/serialization bottleneck bằng evidence, rồi đề xuất thiết kế export production-safe hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Kích thước payload điển hình và lớn nhất là bao nhiêu MB?
2. Có bật response compression không, và export được tải qua CDN/reverse proxy nào không?
3. Endpoint cần trả file ngay trong request hay business chấp nhận background export + download link?
4. Memory counters nào đã có: allocation rate, GC heap size, LOH size, pause time, Gen 2 frequency?
5. SQL query đang stream từ provider hay đã materialize toàn bộ vào memory trước serialization?

## Gợi ý tư duy

### Gợi ý 1

Đừng nhìn chỉ vào “memory used”. Hãy nhìn **allocation pattern**, object lifetime và pause behavior.

### Gợi ý 2

Code hiện tạo ít nhất ba representations lớn của cùng logical dataset: entity/DTO list, JSON string và UTF-8 byte array.

### Gợi ý 3

Nếu workload có thể stream, hãy giảm peak live set thay vì cố ép GC chạy thường xuyên hơn.

## Cấu trúc trả lời đề xuất

1. Clarify payload size/concurrency/SLO.
2. Liệt kê allocation lifecycle trong request hiện tại.
3. Giải thích GC generations và vì sao object lớn gây pressure khác object nhỏ.
4. Nêu hypothesis về LOH/Gen 2 nhưng không kết luận trước evidence.
5. Xác định metrics/profiler cần dùng.
6. So sánh streaming vs full buffering.
7. Xem lại query shape/materialization.
8. Đề xuất concurrency control hoặc background export nếu cần.
9. Thiết kế failure/cancellation path.
10. Load/soak test và production telemetry sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `ToListAsync()` materialize toàn bộ DTO set vào memory trước khi serialize.
- `JsonSerializer.Serialize(rows)` tạo một string lớn; sau đó `Encoding.UTF8.GetBytes` tạo thêm byte array lớn, làm peak live memory cao hơn payload cuối.
- Object lớn có thể đi vào Large Object Heap; LOH thường liên quan tới Gen 2 collection behavior và có chi phí GC/fragmentation khác allocation nhỏ.
- CPU trung bình không loại trừ GC pause; latency tail có thể tăng do stop-the-world pauses hoặc allocation bursts dù average CPU chưa saturation.
- `GC.Collect()` thủ công sau mỗi request thường làm throughput/latency xấu hơn và phá heuristic của GC; chỉ nên dùng trong use case rất đặc biệt có evidence.
- Cần đo allocation rate, heap size, LOH, Gen 2 collections/pause duration cùng request traces trước khi kết luận.
- Streaming hoặc background export có thể giảm peak live set và blast radius.

### Điểm cộng

- Dùng server-side projection nhưng cân nhắc streaming async enumeration thay vì materialize toàn bộ.
- Serialize trực tiếp ra response stream bằng `JsonSerializer.SerializeAsync` hoặc `Utf8JsonWriter` khi format cho phép.
- Không tạo intermediate giant string nếu đích cuối là UTF-8 bytes/network stream.
- Propagate cancellation khi client disconnect để không tiếp tục query/serialize vô ích.
- Với export cực lớn, tách sang background job, lưu file ở Blob Storage và trả link/download token có thể giúp request path ổn định hơn.

### Senior+

- Phân biệt **allocation rate** với **retained heap**: request có thể không leak nhưng vẫn gây GC churn lớn.
- Xem GC pause time/pause percentage thay vì chỉ collection count.
- Recognize rằng streaming giảm peak memory nhưng giữ DB connection/request lifetime lâu hơn, cần cân nhắc backpressure và timeout.
- Nếu background export, áp dụng bounded concurrency để tránh nhiều jobs lớn đồng thời phá memory budget.
- Đo p95/p99 của toàn API trong load test hỗn hợp, không chỉ benchmark riêng export endpoint.

## Hướng giải quyết tham khảo

Trong code hiện tại, request lớn có ít nhất ba memory phases đáng chú ý.

Đầu tiên, `ToListAsync` materialize toàn bộ rows thành một `List<ExportRow>` cùng hàng chục hoặc hàng trăm nghìn DTO và strings. Sau đó `JsonSerializer.Serialize(rows)` tạo một JSON string lớn. Tiếp theo `Encoding.UTF8.GetBytes(json)` tạo một `byte[]` mới có thể rất lớn. Trong một khoảng thời gian, cả object graph, string JSON và byte array đều có thể cùng sống.

Điều này có thể tạo allocation bursts lớn. Những arrays/strings đủ lớn có thể được allocation trên LOH. Tôi không cần giả định exact threshold trong câu trả lời để chẩn đoán incident; điều cần làm là đo object sizes/LOH counters trong runtime đang chạy. LOH collection thường gắn với Gen 2 collection, và Gen 2 collection có thể pause rộng hơn Gen 0/1. Vì vậy tail latency của các requests khác có thể tăng dù CPU trung bình không ở 90–100%.

Tôi sẽ không gọi `GC.Collect()` sau export. Nó biến application code thành GC scheduler mà không giải quyết nguyên nhân peak live set. Nếu nhiều exports liên tục, forced full collections có thể làm p99 tệ hơn.

Evidence cần correlate theo thời gian:

- request rate + export concurrency;
- allocation bytes/sec;
- GC heap size;
- Gen 0/1/2 collections;
- GC pause time / pause percentage;
- LOH size;
- CPU;
- SQL dependency duration;
- serialization span nếu instrument được;
- response send duration/network throughput.

Nếu SQL dependency ổn nhưng allocation + Gen 2 pause tăng đúng lúc p99 tăng, GC hypothesis mạnh. Nếu GC ổn nhưng SQL waits tăng, cần đi hướng DB. Nếu serialization CPU tăng mạnh, optimize data shape/serializer/concurrency.

Một phiên bản request-streaming có thể tránh giant intermediate string:

```csharp
public async Task ExportAsync(
    HttpResponse response,
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    response.ContentType = "application/json";
    response.Headers.ContentDisposition =
        "attachment; filename=orders.json";

    var query = _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
        .OrderBy(x => x.CreatedAt)
        .Select(x => new ExportRow
        {
            Id = x.Id,
            ReferenceNo = x.ReferenceNo,
            CustomerName = x.CustomerName,
            Notes = x.Notes,
            Total = x.Total,
            CreatedAt = x.CreatedAt
        })
        .AsAsyncEnumerable();

    await JsonSerializer.SerializeAsync(
        response.Body,
        query,
        cancellationToken: cancellationToken);
}
```

Tôi vẫn phải test xem serializer/provider thật sự giữ memory thấp và query lifecycle hợp lý; không mặc định `AsAsyncEnumerable()` tự giải quyết mọi thứ. Streaming cũng giữ request và DB reader lâu hơn, nên slow client có thể tạo resource pressure. Có thể cần timeout, max export size và bounded concurrent exports.

Nếu export mất 20 giây và file hàng trăm MB, tôi sẽ nghiêng sang background architecture:

1. API validate request và tạo export job.
2. Worker xử lý với bounded concurrency.
3. Stream query → serializer/file writer thay vì build giant object graph.
4. Upload vào Blob Storage.
5. Trả status + short-lived download access theo authorization policy.

Điều đó tách workload nặng khỏi interactive request SLO. Nhưng nó thêm job lifecycle, cleanup, retry, storage cost và user workflow complexity — chỉ đáng nếu export thật sự lớn/không phù hợp request-response.

Testing cần mixed load: 95% normal API + 5% large exports, tăng concurrency dần. Success criterion không chỉ “export thành công” mà là p99 normal endpoints, peak heap, GC pause, allocation rate và process stability vẫn trong budget.

## Mẫu trả lời trong phỏng vấn

“Code hiện tại buffer cùng dataset nhiều lần: DTO list, JSON string rồi UTF-8 byte array. Với export lớn, peak live set tăng rất mạnh và các object lớn có thể gây LOH/Gen 2 pressure. Điều đó có thể làm tail latency của cả process tăng dù average CPU chưa cao.

Tôi không gọi `GC.Collect()` vì nó không giảm allocation source và có thể tạo thêm full-GC pauses. Tôi sẽ correlate allocation rate, heap/LOH, Gen 2 pause với SQL dependency và serialization timing để chứng minh bottleneck.

Nếu requirement cho phép, tôi serialize trực tiếp ra response stream để bỏ giant string/byte[] trung gian, propagate cancellation và giới hạn concurrent exports. Với file rất lớn hoặc duration dài, tôi chuyển sang background export + Blob Storage để bảo vệ interactive API SLO. Sau đó load test mixed traffic và theo dõi p99 cùng GC pause, không chỉ đo endpoint export riêng.”

## Câu hỏi đào sâu

1. Nếu streaming giảm memory nhưng request duration tăng vì client tải chậm, bạn bảo vệ DB connection pool và app resources thế nào?
2. Nếu profiler cho thấy LOH thấp nhưng allocation rate rất cao ở Gen 0, recommendation của bạn thay đổi ra sao?
3. Nếu business bắt buộc synchronous download, bạn sẽ chọn giới hạn nào về rows/concurrency và giải thích trade-off với Product thế nào?

## Lỗi trả lời thường gặp

- Thấy memory tăng là kết luận memory leak.
- Cho rằng CPU trung bình thấp nghĩa là GC không thể ảnh hưởng latency.
- Gọi `GC.Collect()` sau request như permanent fix.
- Chỉ tăng RAM mà không giảm peak live set hoặc concurrency.
- Đổi sang streaming nhưng bỏ qua slow-client backpressure và DB connection lifetime.

## Thang điểm 0–10

- **0–2:** Chỉ nói “tăng RAM” hoặc “GC.Collect”.
- **3–4:** Biết LOH/Gen 2 nhưng thiếu evidence và allocation-lifecycle reasoning.
- **5–6:** Phân tích đúng buffering/allocations, có profiler metrics và streaming fix.
- **7–8:** Có mixed-load reasoning, backpressure, cancellation và bounded concurrency.
- **9–10:** Phân biệt allocation vs retention, thiết kế sync/background export theo SLO và chứng minh bằng production-representative telemetry.

# Câu 2 — Search trả dữ liệu cũ sau khi catalog update: Elasticsearch lag, bulk rejection hay lỗi đồng bộ?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, eventual consistency, indexing pipeline, background workers, observability, retry, performance, incident response

## Bối cảnh

Một e-commerce platform dùng SQL Server làm source of truth cho product/catalog. Elasticsearch được dùng để search/filter/sort trên website.

Flow hiện tại:

```text
Product update in SQL
    ↓
ProductChanged row inserted into IntegrationEvents table
    ↓
Background worker polls events
    ↓
Worker builds search document
    ↓
Bulk indexing to Elasticsearch
```

Normal SLA: product update xuất hiện trong search trong vòng dưới 60 giây.

Sáng nay merchandising team chạy mass update khoảng 600.000 products. Sau đó:

- product detail page đọc từ SQL nên hiển thị giá/category mới;
- search results vẫn giữ dữ liệu cũ 20–45 phút với một subset products;
- queue/event table backlog tăng mạnh;
- worker CPU không max nhưng throughput giảm;
- Elasticsearch client logs có cả successful bulk requests lẫn một số rejected/timeout items;
- overall cluster health vẫn `green`;
- search query latency của end users chỉ tăng nhẹ;
- một số events retry nhiều lần;
- operations restart workers, backlog giảm nhanh một lúc rồi lại tăng;
- developer A kết luận “Elasticsearch refresh chậm”;
- developer B muốn gọi explicit refresh sau mỗi bulk;
- developer C muốn tăng số workers từ 8 lên 80;
- Product muốn trước tiên biết dữ liệu nào đang stale, thời gian hội tụ và cách tránh việc catalog update lớn làm search freshness mất kiểm soát.

Bạn chưa được phép coi refresh interval là root cause. Các hypothesis có thể gồm:

- ingestion backlog trước khi request tới Elasticsearch;
- bulk item rejection/partial failure không được handle đúng;
- retry storm;
- Elasticsearch indexing pressure;
- shard hotspot;
- document build chậm;
- SQL polling contention;
- mapping/indexing regression;
- explicit refresh làm throughput tệ hơn;
- event ordering khiến older update ghi đè newer update.

## Câu hỏi chính

Hãy xử lý incident theo **impact → stabilize → evidence → hypotheses → verification → remediation → prevention**. Bạn sẽ phân biệt “event chưa được xử lý”, “bulk request đã gửi nhưng một số item fail”, “document indexed nhưng chưa searchable”, và “older event overwrite newer state” như thế nào? Đề xuất immediate mitigation, rồi thiết kế indexing pipeline có backpressure, retry/idempotency/versioning, freshness observability và recovery phù hợp.

## Câu hỏi làm rõ nên cân nhắc

1. Mỗi event chứa full snapshot hay chỉ delta? Worker build document từ event hay re-read canonical product từ SQL?
2. Bulk API handling hiện kiểm tra status của từng item hay chỉ HTTP-level success?
3. Search document có source version/updated timestamp nào để ngăn stale overwrite không?
4. Event table được claim/lock thế nào khi nhiều workers chạy đồng thời?
5. Freshness hiện được đo bằng queue age hay chỉ queue length?

## Gợi ý tư duy

### Gợi ý 1

Một bulk request thành công ở HTTP level không đồng nghĩa tất cả documents trong bulk đều index thành công.

### Gợi ý 2

`green` cluster health không có nghĩa indexing throughput/freshness đang tốt.

### Gợi ý 3

Đừng dùng explicit refresh như default solution cho ingestion backlog; hãy xác định stage nào đang tạo lag.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và freshness SLO.
2. Đo backlog bằng age, không chỉ count.
3. Instrument từng stage từ SQL event → claimed → built → bulk sent → item result → searchable.
4. Tách các hypothesis ingestion/rejection/refresh/order.
5. Stabilize bằng rate control/concurrency tuning có evidence.
6. Sửa partial-failure handling.
7. Thiết kế idempotent/index-version-safe processing.
8. Xử lý retries/DLQ hoặc poison items.
9. Capacity/load test cho mass update.
10. Dashboard/alert freshness end-to-end.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Cluster health `green` chủ yếu nói shard allocation/availability, không chứng minh indexing latency/freshness tốt.
- Queue length một mình không đủ; cần oldest-event age / processing lag để đo freshness.
- Elasticsearch bulk response phải được kiểm tra theo **từng item**, vì request có thể trả response nhưng một subset operations fail/reject.
- Retry phải bounded/backoff; retry ngay lập tức với concurrency cao có thể làm indexing pressure nặng hơn.
- Explicit refresh sau mỗi bulk có thể làm throughput xấu và không giải quyết backlog upstream.
- Pipeline phải có cách tránh older update overwrite newer data, ví dụ index canonical latest snapshot hoặc dùng version/sequence invariant phù hợp.
- Cần distinguish source-of-truth correctness với search eventual consistency.

### Điểm cộng

- Worker có bounded concurrency và adaptive batch size thay vì “80 workers” cố định không đo capacity.
- Re-read canonical product state từ SQL khi xử lý event giúp coalesce nhiều updates và giảm stale-delta ordering risk trong một số designs.
- Poison documents/mapping errors đi sang quarantine/DLQ thay vì retry vô hạn chặn pipeline.
- Metrics theo outcome category: indexed, rejected, mapping failure, timeout, retry, skipped stale version.
- Có replay/rebuild strategy từ SQL source of truth.

### Senior+

- Dùng freshness marker (`sourceUpdatedAt`, source version, sequence) trong index document để đo end-to-end lag trực tiếp.
- Nếu event storm gồm nhiều updates cùng product, coalescing/debounce theo product id có thể giảm redundant writes, nhưng phải giữ correctness.
- Xem shard/indexing pressure và routing distribution trước khi scale workers.
- Recovery path có thể tạo new index + reindex/build + alias swap cho large schema changes thay vì mutate production index mù quáng.
- Có capacity model: updates/sec input, docs/sec sustainable indexing, backlog burn-down rate và SLA recovery time.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng việc xác định lag nằm ở stage nào.

Một event nên có timestamps hoặc trace metadata như:

```text
source_updated_at
integration_event_created_at
worker_claimed_at
bulk_sent_at
bulk_item_completed_at
```

Search document có thể chứa `sourceVersion` hoặc `sourceUpdatedAt` để query/debug biết indexed state tương ứng source version nào.

Nếu oldest unprocessed event age đã 20 phút, vấn đề rõ ràng nằm trước search visibility. Nếu backlog thấp nhưng bulk item rejection cao, indexing side là bottleneck. Nếu item indexing success và document GET/index state mới đã có nhưng search query chưa thấy trong một khoảng ngắn, mới điều tra refresh/search visibility. Nếu document version trong Elasticsearch nhỏ hơn SQL/source version dù events đã processed, điều tra ordering/stale overwrite.

Bulk API phải parse từng item. Pseudocode:

```csharp
var response = await elasticClient.BulkAsync(request, cancellationToken);

foreach (var item in response.Items)
{
    if (item.IsValid)
    {
        MarkSucceeded(item.Id);
        continue;
    }

    if (IsTransient(item))
        ScheduleRetryWithBackoff(item.Id);
    else
        Quarantine(item.Id, item.Error);
}
```

Tôi không tăng workers từ 8 → 80 ngay. Nếu Elasticsearch đã reject vì indexing pressure, tăng producer concurrency chỉ tạo retry storm. Tôi sẽ đo throughput hiện tại, rejection rate, batch size, node indexing metrics và tune theo bounded concurrency.

Explicit refresh sau mỗi bulk cũng thường đi sai hướng. Search visibility có refresh semantics riêng, nhưng mass-update SLA 60 giây không cần mỗi batch lập tức force refresh nếu bottleneck là 600k-event backlog. Force refresh thường đánh đổi indexing throughput lấy immediate visibility; cần dùng khi product requirement thật sự cần, không phải incident placebo.

Ordering phải có invariant. Nếu event 101 và 102 của cùng product chạy song song, 101 không được ghi sau 102 rồi làm index quay về state cũ. Có vài designs defensible:

1. Event chỉ là “product X changed”; worker luôn re-read latest canonical state từ SQL và index latest snapshot.
2. Event chứa version, indexing layer chỉ chấp nhận update mới hơn version hiện tại theo mechanism được chọn.
3. Serialize updates per aggregate/product partition nếu ordering business-critical, đổi throughput lấy simplicity.

Tôi sẽ chọn dựa trên event volume, ability to re-read SQL và correctness requirement.

Immediate stabilization có thể gồm:

- pause mass-update producer nếu business cho phép;
- giảm indexing concurrency nếu rejection/retry storm đang tự khuếch đại;
- tăng batch size vừa phải nếu requests quá nhỏ và cluster còn capacity;
- isolate poison documents;
- scale Elasticsearch/index capacity nếu metrics chứng minh saturation;
- temporarily relax freshness SLO có communication rõ với Product nếu burn-down mất thời gian.

Lâu dài cần dashboard:

- event input rate;
- processing throughput;
- backlog count;
- oldest-event age;
- bulk reject/timeout rate;
- retry age/count;
- document source-version lag;
- end-to-end freshness p50/p95/p99;
- search query latency.

Load test phải có burst 600k hoặc representative spike, không chỉ steady-state 100 updates/sec. Success criterion là backlog burn-down và freshness recovery trong SLA.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi không gọi đây là refresh issue chỉ vì search stale. Tôi đo pipeline theo từng stage. Nếu oldest event chưa claim đã 20 phút thì bottleneck upstream; nếu bulk đã gửi nhưng item-level rejection tăng thì indexing pressure; nếu item success nhưng query chưa thấy mới là refresh/visibility; nếu indexed version thấp hơn source version thì nghi ordering/stale overwrite.

Tôi kiểm tra bulk response theo từng item và retry transient failures với backoff/bounded concurrency. Tôi không scale workers 10x khi Elasticsearch đang reject và không force refresh mỗi bulk vì hai việc đó có thể giảm throughput hơn.

Về correctness, mỗi product update phải có source version hoặc worker re-read latest canonical SQL state để older event không ghi đè newer state. Tôi thêm freshness telemetry end-to-end, poison-item quarantine và replay/rebuild capability. Sau đó capacity test với mass update để biết sustainable docs/sec và thời gian burn down backlog.”

## Câu hỏi đào sâu

1. Nếu worker luôn re-read latest SQL state, event coalescing giúp gì và có trade-off gì với database load?
2. Nếu Product yêu cầu price update searchable trong 5 giây nhưng description update có thể 5 phút, bạn sẽ thiết kế pipeline/SLA khác nhau thế nào?
3. Nếu Elasticsearch indexing capacity đã dư nhưng backlog vẫn tăng, những evidence nào khiến bạn chuyển focus về SQL polling/worker code?

## Lỗi trả lời thường gặp

- Thấy stale search là gọi explicit refresh ngay.
- Kiểm tra chỉ HTTP status của bulk request, bỏ item-level failures.
- Tăng workers mạnh khi downstream đang reject.
- Dùng queue count nhưng không đo oldest-event age.
- Retry poison mapping error vô hạn.

## Thang điểm 0–10

- **0–2:** Chỉ restart worker hoặc refresh index.
- **3–4:** Biết có backlog/retry nhưng không tách pipeline stages.
- **5–6:** Có item-level bulk handling, lag metrics, bounded retry và ordering strategy.
- **7–8:** Có capacity/burn-down model, poison handling, replay và freshness SLO.
- **9–10:** Incident reasoning end-to-end, phân biệt source/index/search visibility rõ và thiết kế pipeline resilient dưới burst production scale.

# Câu 3 — Thiết kế approval workflow platform: Modular Monolith hay Microservices, sync hay async ở đâu?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 45–60 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, SQL Server, architecture boundaries, Modular Monolith, Microservices, background processing, REST, messaging, transactions, audit, security, observability, deployment, failure recovery

## Bối cảnh

Một công ty muốn xây một approval workflow platform dùng chung cho nhiều internal products.

Use cases ban đầu:

- leave request;
- purchase request;
- document approval;
- access request.

Core flow:

```text
Requester submits request
→ determine approval steps
→ approver approves/rejects
→ next step activates
→ final outcome emitted
→ email/in-app notification sent
```

Requirements hiện có:

- 5.000–15.000 active employees;
- peak khoảng vài chục submissions/second, không phải internet-scale;
- mỗi request có audit trail phải truy vết được;
- approval action không được xử lý hai lần do double-click/retry;
- một số workflow có 2–7 sequential/parallel approval steps;
- notification có thể delay vài giây nhưng approval state phải chính xác ngay;
- reminders/escalations chạy theo SLA;
- một số products muốn webhook/event khi workflow hoàn tất;
- Microsoft Entra ID được dùng cho user identity;
- SQL Server là database quen thuộc của team;
- platform team có Azure Service Bus nhưng không bắt buộc phải dùng;
- deployment hiện tại chủ yếu Azure App Service;
- engineering team chỉ khoảng 6 backend developers;
- Product muốn ship first production version trong 4 tháng;
- một architect đề xuất tách ngay `WorkflowService`, `ApprovalService`, `AuditService`, `NotificationService`, `IdentityService` thành microservices;
- một developer muốn một ASP.NET Core app duy nhất với tất cả logic trong controllers để “ship nhanh”;
- team cần chọn kiến trúc đủ đơn giản cho hiện tại nhưng không khóa đường phát triển sau này.

## Câu hỏi chính

Hãy thiết kế kiến trúc cho approval workflow platform này. Bạn phải làm rõ domain boundaries, data model/transaction boundaries, idempotency, sync-vs-async decisions, audit, reminders, notifications, integrations, authorization, observability và deployment. Sau đó so sánh **layered/modular monolith** với **microservices** trong bối cảnh team/scale hiện tại và đưa ra recommendation có điều kiện thay vì mặc định chọn kiến trúc phức tạp hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Workflow definitions có thay đổi runtime bởi business users hay được deploy cùng code?
2. Approval cần delegation, substitute approver hoặc group-based approval không?
3. Audit trail có requirement pháp lý/retention/immutability cụ thể không?
4. External products cần synchronous confirmation hay event/webhook eventually consistent là đủ?
5. Có requirement cross-region/high availability vượt khả năng App Service + SQL hiện tại không?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu từ **business invariants và transaction boundary**, không bắt đầu từ số lượng services.

### Gợi ý 2

Approval state transition cần strong local correctness; notification thường không cần nằm trong cùng synchronous transaction.

### Gợi ý 3

Một modular monolith có module boundaries rõ có thể là bước đầu hợp lý hơn microservices nếu scale/team chưa buộc phải phân tách deployment.

## Cấu trúc trả lời đề xuất

1. Clarify workflow flexibility, SLA và audit requirements.
2. Xác định domain modules/bounded responsibilities.
3. Thiết kế core relational data model.
4. Xác định approval state-transition transaction.
5. Thiết kế idempotency/concurrency control.
6. Tách sync path khỏi async notifications/reminders/integrations.
7. Authorization + Entra identity mapping.
8. Observability/audit/recovery.
9. Deployment/scale model.
10. So sánh modular monolith vs microservices và migration triggers.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Core approval state nên có transaction boundary rõ trong SQL; không phân tán transaction qua nhiều services nếu không cần.
- Double-click/client retry phải được xử lý bằng idempotency key hoặc optimistic/pessimistic concurrency invariant phù hợp.
- Notification/email không nên làm approval transaction fail chỉ vì provider tạm lỗi.
- Audit trail phải ghi actor, action, before/after state hoặc event semantics đủ để reconstruct history.
- Reminder/escalation là background concern có retry/idempotency.
- Authorization không chỉ kiểm tra user authenticated; phải kiểm tra user có quyền approve **step cụ thể** ở state hiện tại.
- Kiến trúc phải cân nhắc team size, deployment complexity, observability và transaction boundaries, không chỉ “scalability”.

### Điểm cộng

- Dùng modules như Workflow Definition, Request/Execution, Approval, Notification, Integration/Audit trong cùng deployable ban đầu.
- Outbox pattern có thể dùng để phát event sau SQL commit mà không mất notification/integration event nếu requirement reliability cần.
- Background worker có thể nằm cùng solution/process hoặc tách worker process khi workload cần, không nhất thiết tách thành microservice domain riêng.
- Unique constraint trên idempotency key hoặc `(WorkflowInstanceId, StepId, ActionId)` giúp enforce duplicate prevention ở DB layer.
- Dùng optimistic concurrency/version column cho state transition để detect stale approver action.

### Senior+

- Không biến “audit” thành service call synchronous trong critical transaction; audit data cần atomic với state nếu business yêu cầu, có thể cùng database transaction rồi project ra analytics sau.
- Webhook delivery dùng delivery record + retry/backoff/signature + replay protection; external failure không rollback completed workflow.
- Nếu workflow definition runtime-editable, version definition và bind instance vào immutable version để running workflow không đổi semantics giữa chừng.
- Migration trigger sang microservices phải concrete: independent scaling, ownership by separate teams, deploy cadence conflict, regulatory/data boundary, runtime isolation — không phải “dự kiến sẽ lớn”.
- Có operational plan cho poison reminders/webhooks, stuck workflows, manual reconciliation và replay.

## Hướng giải quyết tham khảo

Với team 6 backend developers, traffic vài chục submissions/second và deadline 4 tháng, tôi sẽ không bắt đầu bằng 5 microservices. Scale hiện tại nằm rất xa mức buộc phải phân tán domain. Chi phí microservices sẽ xuất hiện ngay ở deployment, tracing, retries, versioning, service discovery, distributed failure và data ownership.

Tôi chọn **modular monolith** hoặc layered architecture có module boundaries rõ, chạy ASP.NET Core trên App Service và SQL Server. Quan trọng là module boundary trong code/data access, không phải chỉ chia folder.

Một model đơn giản:

```text
WorkflowDefinition
WorkflowDefinitionVersion
WorkflowInstance
ApprovalStep
ApprovalAction
OutboxMessage
NotificationDelivery
WebhookDelivery
```

`WorkflowInstance` reference một immutable `WorkflowDefinitionVersion`. Khi business sửa workflow definition, instance đang chạy vẫn dùng version cũ.

Approval endpoint:

```http
POST /workflow-instances/{id}/steps/{stepId}/actions
Idempotency-Key: <client-generated-key>
```

Transaction logic:

1. Load instance/step theo expected version/state.
2. Verify actor được phép approve/reject step đó.
3. Check idempotency key.
4. Apply state transition.
5. Insert audit/action record.
6. Nếu step/workflow state đổi, insert outbox event trong cùng DB transaction.
7. Commit.

Với EF Core, optimistic concurrency token/version có thể giúp reject stale concurrent actions:

```text
Approver A reads step Pending
Approver B reads step Pending
A approves → version 5
B attempts approve with version 4 → concurrency conflict
```

Application trả semantic response phù hợp thay vì silently apply action hai lần.

Notification không nằm trong critical transaction với email provider. Sau commit, worker đọc OutboxMessage và gửi:

```text
WorkflowStepActivated
WorkflowCompleted
WorkflowRejected
```

Notification delivery có own idempotency/delivery status để retry mà không gửi spam vô hạn. Nếu reliability requirement thấp hơn, simple DB-backed background jobs cũng có thể đủ; không bắt buộc Service Bus ngày đầu. Nếu platform đã vận hành Service Bus tốt và cần decouple consumers/process recovery, có thể publish từ outbox sang Service Bus.

Reminders/escalations không nên scan toàn bảng mỗi phút vô điều kiện khi scale lên. Có thể lưu `NextActionAt`/`ReminderDueAt`, query indexed due items theo batch, claim work idempotently, rồi update next schedule. Nếu sau này volume lớn, tách scheduler/worker process riêng.

Audit có hai lớp:

- authoritative audit/action rows được ghi atomic cùng workflow state transition;
- operational logs/traces ở Application Insights cho debugging.

Không dùng application log thay cho business audit.

Authorization:

- Entra ID chứng minh identity;
- application map claims/user tới employee/internal principal;
- mỗi action check assignment/group/delegation và current workflow state;
- không trust `approverId` từ request body.

Webhook integration:

- sign payload;
- delivery records;
- retries with backoff;
- stable event id để consumers deduplicate;
- timeout ngắn;
- DLQ/manual replay cho failures dài.

Observability:

- workflow submissions/completions;
- approval latency by type/step;
- stuck instance count;
- outbox age;
- reminder backlog;
- notification/webhook failure rate;
- concurrency conflicts;
- authorization denials;
- correlation id từ API request tới background deliveries.

Deployment ban đầu:

```text
ASP.NET Core Web App
+ optional Worker process
+ SQL Server
+ Entra ID
+ Application Insights
```

Tôi chỉ tách microservices khi có pressure cụ thể. Ví dụ Notification module cần scale/ownership độc lập bởi team khác; Integration delivery có failure/isolation profile khác; hoặc Workflow Execution cần release cadence tách khỏi product APIs. Vì module contracts đã rõ, extraction sau này có path tốt hơn một monolith controllers-heavy không có boundaries.

Tôi cũng không chọn “mọi thứ trong controller” dù ship nhanh, vì state transition, audit, authorization và idempotency là business invariants cần test được ở application/domain layer. Nhưng tôi không cần DDD/CQRS/Event Sourcing đầy đủ nếu complexity chưa justified.

## Mẫu trả lời trong phỏng vấn

“Với 6 developers, traffic vài chục submissions/second và deadline 4 tháng, tôi ưu tiên modular monolith trên ASP.NET Core + SQL Server. Core invariant là approval state transition, audit và duplicate prevention phải atomic trong một local transaction.

Mỗi action có idempotency key và concurrency/version check. Trong cùng transaction tôi update workflow state, ghi audit/action và ghi outbox event. Email, reminders và webhooks xử lý async sau commit vì dependency failure không được rollback approval đã hợp lệ.

Entra ID chỉ là identity source; application vẫn kiểm tra actor có quyền trên step hiện tại. Workflow definition nếu editable runtime phải versioned để instance đang chạy không đổi semantics.

Tôi không dùng microservices ngay vì chưa có scale/team boundary justify chi phí distributed system. Nhưng tôi thiết kế module contracts đủ rõ để sau này extract Notification hoặc Integration khi có independent scaling/ownership/release pressure thật sự.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu một approval phải gọi external ERP **synchronously trước khi được coi là completed**, transaction/failure model của bạn thay đổi thế nào?
2. Nếu two approvers trong một parallel step đều có thể approve và workflow chỉ cần “2 trong 3”, bạn model concurrency/invariant thế nào?
3. Điều kiện cụ thể nào khiến bạn quyết định tách Notification/Integration khỏi modular monolith thành service riêng?

## Lỗi trả lời thường gặp

- Chọn microservices chỉ vì “dễ scale”.
- Cho email/webhook vào cùng synchronous DB transaction path.
- Dùng authentication như thể nó đã đủ authorization.
- Không có idempotency/concurrency strategy cho double-click/retry.
- Gọi application logs là audit trail chính thức.

## Thang điểm 0–10

- **0–2:** Chỉ vẽ nhiều services hoặc một controller CRUD đơn giản mà không có invariants.
- **3–4:** Có modules/database nhưng thiếu idempotency, audit hoặc async failure reasoning.
- **5–6:** Thiết kế transaction boundary, outbox/worker, authorization và audit hợp lý.
- **7–8:** Có definition versioning, concurrency control, webhook reliability, observability và migration triggers.
- **9–10:** Recommendation cân bằng đúng team/scale/complexity, có failure/recovery model rõ và kiến trúc có đường tiến hóa mà không over-engineer.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Performance memory problem cần phân biệt **allocation rate**, **retained memory**, GC pause và peak live set thay vì chỉ nhìn RAM/CPU trung bình.
- Full buffering có thể tạo nhiều representation lớn của cùng dữ liệu; streaming/background processing thường giảm blast radius nhưng có trade-off về connection lifetime và complexity.
- Search freshness phải được đo end-to-end qua pipeline; `green` cluster health không chứng minh indexing lag thấp.
- Elasticsearch bulk indexing cần xử lý result theo từng item, retry có backoff và bảo vệ khỏi stale event overwrite.
- Approval workflow correctness nằm ở transaction boundary, idempotency, concurrency và authorization — không nằm ở số lượng microservices.
- Modular Monolith có thể là lựa chọn Senior hơn Microservices khi team/scale chưa justify distributed-system complexity.

## Mẫu tư duy cần nhớ

- **Đo allocation/GC pause trước khi kết luận memory leak.**
- **Tách pipeline thành stages và đo lag ở từng stage trước khi tối ưu.**
- **Retry phải đi cùng idempotency, backoff và downstream capacity awareness.**
- **Đặt business invariant vào transaction boundary nhỏ nhất có thể.**
- **Chỉ trả cost của distributed architecture khi có pressure cụ thể justify nó.**
