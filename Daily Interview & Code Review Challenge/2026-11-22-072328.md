# Câu 1 — Cosmos DB: cùng một truy vấn, vì sao RU và latency chênh lệch lớn?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18 phút  
**Kỹ năng được đánh giá:** Cosmos DB partitioning, query routing, indexing, .NET SDK, performance investigation

## Bối cảnh

Một dịch vụ ASP.NET Core .NET 8 cung cấp lịch sử hoạt động của khách hàng. Dữ liệu ở Azure Cosmos DB for NoSQL; container `ActivityEvents` có partition key `/tenantId`. API `GET /tenants/{tenantId}/events?from=...&to=...` trả tối đa 100 bản ghi. Một phiên bản mới bổ sung endpoint dành cho nhân viên hỗ trợ, tìm theo `customerId` trên nhiều tenant. Trong kiểm thử, truy vấn cho một tenant phản hồi nhanh; truy vấn hỗ trợ có p95 cao, RU tiêu thụ biến động mạnh và đôi khi trả 429. Nhóm đề xuất tăng RU hoặc thêm Redis ngay.

Giả định dữ liệu được ghi liên tục, hàng triệu sự kiện và một số tenant có traffic lớn. Chưa biết RU provisioned/autoscale, số physical partitions, cardinality của tenant, composite index hay mức độ đồng thời.

## Câu hỏi chính

Giải thích cơ chế định tuyến partition, tính RU và xử lý 429 có thể tạo ra hành vi này; bạn sẽ xác minh nguyên nhân và quyết định thay đổi data model, query hoặc capacity thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Query có truyền partition key trong request options và có ORDER BY/filter nào?
2. Distribution kích thước, request rate và RU theo tenant/partition key ra sao?
3. Chỉ số RU, diagnostics, 429, p95 được đo theo từng endpoint hay toàn container?
4. Support search cần độ tươi, giới hạn phạm vi tenant và phân trang thế nào?
5. Có chấp nhận duy trì read model riêng và eventual consistency không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt logical partition, physical partition và phạm vi query.

### Gợi ý 2
Kiểm tra partition key equality, query metrics, request charge, continuation token và hot partition.

### Gợi ý 3
Một cross-partition query có thể fan out; tăng throughput tổng không luôn giải quyết giới hạn trên một vùng dữ liệu nóng.

## Cấu trúc trả lời đề xuất

1. Làm rõ query, SLA và traffic.
2. Mô tả partition routing và RU.
3. Thu thập diagnostics, metrics và query plan/index utilization.
4. Phân biệt scan rộng, index kém, hot key và client concurrency.
5. Đề xuất phương án ít thay đổi nhất; so sánh read model.
6. Kiểm thử tải, 429, pagination và authorization.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Equality trên partition key giúp giới hạn phạm vi định tuyến; query không có key có thể phải fan out.
- RU là đơn vị chi phí request, không phải thời gian cố định; 429 là throttling, cần xem SDK retry và retry-after.
- Phân tích RU/request, số partition được truy vấn, latency, throughput và distribution trước khi tăng capacity.
- Tránh trả toàn bộ dữ liệu rồi lọc ở ứng dụng; bảo đảm phân trang và quyền truy cập.

### Điểm cộng
- Phân biệt point read theo id + partition key với query.
- Đề cập continuation token, composite index phù hợp với filter/sort và diagnostics từ SDK.
- Đánh giá data duplication/materialized view cho support search.

### Senior+
- Phân tích trade-off giữa tenant isolation, hot tenant, khả năng phân phối key và chi phí migration partition key.
- Đặt SLO riêng cho endpoint support; có chiến lược backpressure và rate limiting theo tenant.

## Hướng giải quyết tham khảo

**Giả định cần xác minh:** Container dùng partition key `/tenantId` và endpoint hỗ trợ thực hiện truy vấn `WHERE c.customerId = @customerId` mà không có tenantId. Với query tenant-specific, nếu truyền chính xác tenantId trong query options, SDK/service có thể giới hạn truy vấn đến logical partition tương ứng. Với query support, hệ thống có thể phải truy vấn nhiều physical partitions, tăng tổng RU, network work và độ biến thiên latency. Chi phí còn phụ thuộc số item được kiểm tra, kích thước document, index, filter, sort và mức độ đồng thời. Không được kết luận mọi cross-partition query đều chậm hoặc mọi 429 đều do fan-out.

**Xác minh:** Gắn `ActivityId`/correlation ID, ghi nhận `RequestCharge`, elapsed time, status/substatus, diagnostics (loại bỏ thông tin nhạy cảm), query text dạng parameterized, page count và continuation behavior. Trên Azure Monitor xem normalized RU consumption, throttled requests và phân phối theo partition key khi có telemetry tương ứng. Đối chiếu truy vấn thật với index policy, đặc biệt khi có ORDER BY nhiều trường. Chạy cùng dataset và concurrency để phân biệt scan rộng, hot tenant và quota toàn container.

**Các lựa chọn:** (A) Nếu support search hiếm: bắt buộc chọn tenant trước hoặc giới hạn phạm vi tenant, tối ưu filter, projection và paging. (B) Nếu search xuyên tenant là critical: thiết kế read model/index phục vụ customer lookup, có thể lưu ánh xạ customer→tenant hoặc đồng bộ dữ liệu sang search service; chấp nhận độ trễ cập nhật và chi phí vận hành. (C) Nếu capacity thực sự thiếu: điều chỉnh throughput/autoscale sau khi chứng minh RU saturation. (D) Nếu một tenant rất nóng: xem lại chiến lược partitioning cho dữ liệu mới; thay partition key hiện hữu không phải sửa cấu hình đơn giản, cần kế hoạch migrate và dual-read/dual-write có kiểm soát.

**Retry:** SDK có xử lý retry cho các response retryable theo chính sách của nó; không thêm vòng retry vô hạn ở controller. Thiết lập timeout/cancellation, giới hạn concurrency và đo số lần retry, tránh retry storm. Redis chỉ hợp lý nếu có access pattern lặp lại và quy tắc freshness/invalidation rõ ràng.

**Bảo mật:** Support query phải xác thực authorization theo scope của nhân viên, audit truy cập và hạn chế PII trong logs. Test multi-tenant isolation, pagination xuyên partitions, peak load, 429, index changes và rollback. Alert dựa trên p95, RU/request, 429 ratio và failure rate, không chỉ CPU ứng dụng.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa tăng RU ngay vì cần tách nguyên nhân từ query routing, index và throughput. Với partition key tenantId, request có tenantId có thể chỉ truy vấn partition liên quan, trong khi tìm customer xuyên tenant có thể fan out. Tôi sẽ so sánh RequestCharge, diagnostics, latency và 429 theo từng endpoint, đồng thời kiểm tra distribution traffic và index. Nếu support search ít dùng, tôi ưu tiên thu hẹp tenant và paging. Nếu nó là nghiệp vụ trọng tâm, tôi cân nhắc read model cho customer lookup với eventual consistency được công bố rõ. Tăng RU chỉ khi telemetry chứng minh capacity là nút thắt; với hot tenant, tôi phải xem lại mô hình partitioning. Sau thay đổi tôi load test, đo RU/request và bảo đảm không rò rỉ dữ liệu giữa tenant.”

## Câu hỏi đào sâu

1. Nếu một tenant chiếm 70% traffic, tại sao tăng tổng RU có thể không giải quyết hết throttling?
2. Khi chuyển sang read model, bạn xử lý event đến muộn, duplicate và reindex thế nào?
3. Nếu business yêu cầu tìm kiếm chính xác ngay sau write, kiến trúc sẽ thay đổi ra sao?

## Lỗi trả lời thường gặp

- Cho rằng 429 đồng nghĩa service bị lỗi và retry càng nhiều càng tốt.
- Tăng RU mà không đo RequestCharge hoặc query distribution.
- Nghĩ chỉ cần thêm index là loại bỏ mọi chi phí cross-partition.
- Đổi partition key trực tiếp mà không tính migration.
- Bỏ qua authorization xuyên tenant và continuation token.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ SLA, query shape, partitioning | 1.5 |
| Giải thích routing, RU, throttling chính xác | 2.5 |
| Diagnostics và kiểm chứng giả thuyết | 2 |
| Trade-off data model/capacity/index | 2 |
| Security, test, telemetry, diễn đạt | 2 |

# Câu 2 — Service Bus backlog tăng sau khi triển khai phiên bản mới

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 22 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, .NET worker, retries, database transactions, incident management, observability

## Bối cảnh

Một nền tảng xử lý đơn hàng nhận message `OrderPaid` qua Azure Service Bus queue. .NET BackgroundService/ServiceBusProcessor trên Azure App Service xử lý message rồi ghi SQL Server và gọi API fulfillment. Sau deploy, số message active tăng, dead-letter queue tăng, khách hàng báo đơn bị xử lý chậm; một số đơn xuất hiện hai yêu cầu fulfillment. App Insights cho thấy dependency timeout tăng, nhưng không rõ nguyên nhân. Hai instance cùng chạy, một API bên thứ ba gần đây thay đổi timeout. Không biết lock duration, prefetch, max concurrent calls, auto-complete, transaction boundaries hoặc retry policy.

## Câu hỏi chính

Bạn sẽ chỉ huy điều tra và ổn định sự cố theo trình tự nào, phân biệt những nguyên nhân nào, và thiết kế xử lý message thế nào để không gây side effect trùng khi retry?

## Câu hỏi làm rõ nên cân nhắc

1. Backlog, oldest message age, DLQ reason và tỷ lệ failure thay đổi từ thời điểm nào?
2. Handler hoàn tất message trước hay sau DB commit và external call?
3. Fulfillment API có idempotency key hoặc lookup status không?
4. Lock lost, delivery count, processing duration và max concurrency ra sao?
5. Có thể tạm ngừng fulfillment hoặc chuyển sang manual reconciliation mà vẫn đáp ứng SLA không?

## Gợi ý tư duy

### Gợi ý 1
Đừng bắt đầu bằng tăng số instance; xem side effects và khả năng xử lý lại.

### Gợi ý 2
At-least-once delivery, message lock, timeout và completion không tạo distributed transaction với external API.

### Gợi ý 3
Phân biệt duplicate message, duplicate processing và duplicate business action; dùng business key và trạng thái bền vững.

## Cấu trúc trả lời đề xuất

1. Xác định impact và phạm vi đơn hàng.
2. Giảm rủi ro duplicate, ổn định consumer và dependency.
3. Thu thập queue metrics, traces, DLQ reason, deploy diff.
4. Đặt các giả thuyết cạnh tranh và phép thử.
5. Xác nhận root cause bằng timeline.
6. Hotfix có rollback và kiểm chứng.
7. Thiết kế idempotency/reconciliation, runbook và alert.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Ưu tiên ngăn duplicate fulfillment và bảo toàn message; không purge queue.
- Đánh giá lock expiry, abandon/defer/dead-letter, retry, max delivery count và handler duration.
- Không coi exactly-once business side effect là guarantee tự động của Service Bus.
- Thiết kế idempotency có durable storage và key ổn định.

### Điểm cộng
- Phân biệt poison message, dependency outage, DB contention, ThreadPool starvation và deployment regression.
- Dùng bounded concurrency, circuit breaker/backoff phù hợp, graceful shutdown.
- Đưa ra quy trình DLQ replay an toàn.

### Senior+
- Giải thích atomicity gap giữa DB transaction, message settlement và fulfillment API.
- Đề xuất outbox/inbox hoặc state machine + reconciliation tùy ràng buộc, tránh áp dụng pattern máy móc.

## Hướng giải quyết tham khảo

**Impact/stabilize:** Xác định số đơn chậm, số đơn có thể bị fulfillment trùng, tốc độ backlog tăng và mức độ ảnh hưởng khách hàng. Nếu duplicate có thể gây thiệt hại, tạm dừng phần gọi fulfillment hoặc giới hạn concurrency có kiểm soát; giữ queue và DLQ để phục hồi. Rollback phiên bản mới nếu có bằng chứng regression và schema tương thích; không xóa message để “hết backlog”.

**Bằng chứng:** Correlate `MessageId`, business `OrderId`, `DeliveryCount`, lock-lost exceptions, handler duration, settlement outcome, dependency telemetry, SQL waits, API status/timeout, worker restarts và deployment timeline. Đo active messages, dead-lettered messages, oldest age và throughput. Không ghi payload chứa PII/payment data vào logs.

**Giả thuyết:** (1) API fulfillment chậm khiến processing vượt lock/renewal và message được giao lại; (2) handler gọi API thành công nhưng thất bại trước `CompleteMessageAsync`; (3) tăng concurrency làm SQL/API nghẽn; (4) poison payload dẫn đến DLQ; (5) worker restart giữa xử lý; (6) DB transaction/connection pool bão hòa. Kiểm chứng từng giả thuyết bằng trace và tái hiện có fault injection. Root cause chưa thể xác định chỉ từ symptom.

**Thiết kế:** Dùng `OrderId` + loại action làm idempotency key ở fulfillment nếu API hỗ trợ. Lưu bảng `FulfillmentRequests` với unique constraint trên business key và state `Pending/Requested/Confirmed/NeedsReconciliation`. Tránh đánh dấu `Confirmed` trước khi xác nhận kết quả. Một timeout sau khi gửi request là kết quả **không xác định**, không được coi là thất bại chắc chắn rồi gửi lại bằng key mới. Query trạng thái fulfillment hoặc reconcile trước retry. DB unique constraint bảo vệ concurrent consumers, nhưng không tự tạo atomic transaction với external API; dùng stable idempotency key để phía đối tác dedupe hoặc thiết kế manual reconciliation nếu họ không hỗ trợ. Có thể dùng outbox cho phát hành event nội bộ khi DB commit; inbox cho dedupe incoming event; cả hai vẫn cần giải quyết external side effect.

**Message settlement:** Chỉ complete khi trạng thái xử lý đã được lưu bền vững và có đường phục hồi hợp lệ. Nếu lỗi transient, backoff có giới hạn và theo dõi retry; poison message đi DLQ kèm reason tối thiểu, replay sau khi fix và xác minh idempotency. Cấu hình lock renewal và concurrency dựa trên duration đo được, không dựa vào giả định. Graceful shutdown phải ngừng nhận mới và chờ/cancel xử lý có kiểm soát.

**Triển khai:** Canary/slot rollout với compatibility, rollback nếu p95/duplicate rate tăng. Test concurrent duplicate, timeout sau side effect, crash trước settlement, DLQ replay, third-party 429/5xx, DB deadlock và high load. Alert backlog age, DLQ growth, duplicate business attempts, lock lost, fulfillment reconciliation backlog.

## Mẫu trả lời trong phỏng vấn

“Ưu tiên đầu tiên là bảo vệ đơn hàng khỏi fulfillment trùng, đồng thời không làm mất message. Tôi sẽ xác định backlog age, DLQ reason, delivery count và trace xuyên worker, SQL, external API. Các giả thuyết chính là dependency timeout, lock expiry, handler crash sau side effect hoặc concurrency quá cao. Tôi không giả định Service Bus đảm bảo exactly-once business operation: complete message và gọi API ngoài không atomic. Tôi sẽ dùng business idempotency key, durable state và reconciliation khi timeout không rõ kết quả. Sau khi ổn định, tôi thử fault injection ở từng điểm crash, kiểm tra DLQ replay và cảnh báo theo độ tuổi backlog cùng tỷ lệ duplicate, không chỉ số message.”

## Câu hỏi đào sâu

1. Nếu đối tác không hỗ trợ idempotency key và không có status API, bạn có thể bảo đảm không gửi duplicate bằng cách nào?
2. Nếu tăng `MaxConcurrentCalls` khiến throughput giảm, bạn chứng minh bottleneck ở đâu?
3. Khi một message đã gọi API thành công nhưng process crash trước khi ghi SQL, recovery flow sẽ xử lý thế nào?

## Lỗi trả lời thường gặp

- Tăng consumer instances mà không kiểm tra downstream capacity.
- Giả định queue deduplication thay thế idempotency của business action.
- Replay toàn bộ DLQ mà không kiểm tra trạng thái đơn.
- Retry vô hạn khi timeout, bỏ qua kết quả không xác định.
- Không liên kết logs/traces bằng business ID.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact và stabilization | 1.5 |
| Giải thích delivery/lock/settlement | 2 |
| Evidence và competing hypotheses | 2 |
| Idempotency, transaction gap, recovery | 2.5 |
| Testing, observability, rollout, giao tiếp | 2 |

# Câu 3 — Quyết định chiến lược triển khai an toàn cho hệ thống .NET Framework và .NET 8

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** legacy modernization, IIS, Windows Server, TeamCity, Octopus Deploy, Azure App Service, CI/CD, database migration

## Bối cảnh

Một portal quản lý nhân sự chạy ASP.NET MVC trên .NET Framework 4.5 và IIS/Windows Server. Nhóm đã tách một API mới trên ASP.NET Core .NET 8, sử dụng chung SQL Server trong giai đoạn chuyển đổi. Pipeline TeamCity build portal cũ, Jenkins build API mới, Octopus Deploy triển khai portal; API mới được deploy thủ công lên Azure App Service. Hiện release yêu cầu downtime 30 phút, rollback code đôi khi không rollback được database. Product yêu cầu triển khai nhiều lần mỗi tuần, không mất dữ liệu, giữ URL/login cũ và có thể quay lại phiên bản trước. Ngân sách vận hành hạn chế, đội 6 developer và 2 QA. Chưa rõ coupling schema, session state, integration contract, data volume hoặc RTO/RPO.

## Câu hỏi chính

Bạn sẽ chọn kiến trúc chuyển đổi và release strategy nào trong 6 tháng để giảm downtime và rollback risk mà không làm tăng complexity quá mức?

## Câu hỏi làm rõ nên cân nhắc

1. Những bảng nào được cả portal và API ghi, và migration nào không backward-compatible?
2. Authentication/session/cookie và URL routing đang phụ thuộc IIS như thế nào?
3. RTO/RPO, downtime thực tế cho phép, audit/compliance và rollback window là bao nhiêu?
4. Có automated tests, artifact versioning, database backup/restore drill và staging giống production không?
5. Có thể chuyển từng module và dùng reverse proxy theo route không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt deploy artifact, chuyển traffic và thay đổi schema.

### Gợi ý 2
Tìm cách cho phiên bản N và N+1 cùng chạy được với một schema trong transition window.

### Gợi ý 3
Xem xét expand–migrate–contract, feature flags, smoke tests và rollback theo lớp; đừng mặc định microservices/Kubernetes.

## Cấu trúc trả lời đề xuất

1. Làm rõ SLA, coupling và critical flows.
2. Vẽ dependency và ownership.
3. Chọn incremental migration boundary.
4. Chuẩn hóa build artifact và release gates.
5. Thiết kế schema evolution tương thích.
6. Rollout, rollback, monitoring và runbook.
7. Ước lượng effort, risks và milestone.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không rewrite toàn bộ hay containerize mọi thứ chỉ vì công nghệ mới.
- Tách database migration khỏi rollback code; dùng backward-compatible schema changes.
- Immutable artifact, config/secrets separation, automated smoke/regression tests.
- Phân định ownership bảng và các đường ghi chung.

### Điểm cộng
- Có reverse proxy/route migration, auth/session compatibility strategy.
- Có release gates, deployment health, rollback rehearsal và schema compatibility matrix.
- Ưu tiên automation bằng công cụ hiện hữu thay vì thay toàn bộ CI/CD.

### Senior+
- Nêu giới hạn của expand–contract với destructive data transformation.
- Đánh giá trade-off dual-write, strangler pattern, shared DB và eventual ownership separation.
- Đề xuất delivery plan có risk register, measurable SLO và decision checkpoints.

## Hướng giải quyết tham khảo

**Giả định:** Chưa có bằng chứng portal phải di chuyển khỏi IIS ngay. Trong 6 tháng, giữ portal ổn định trên IIS và phát triển API .NET 8 trên App Service là phương án có thể bảo vệ delivery speed. Dùng incremental migration theo module (strangler-style routing) nếu reverse proxy, authentication và session cho phép. Không cần Kubernetes hoặc microservices mới chỉ để giải quyết release safety.

**Kiến trúc:** Lập inventory module, shared tables, scheduled jobs, authentication, dependencies và integration contract. Chọn một module ít coupling làm pilot. Nếu cả portal và API ghi cùng bảng, xác định authoritative writer và contract; tránh dual-write không có reconciliation. Giữ stable URL thông qua reverse proxy/route mapping đã test, bảo vệ redirect/cookie/SameSite và CSRF. Kiểm tra ASP.NET MVC legacy auth có tương thích token/cookie với API hay cần BFF/identity gateway; không tự giả định cookie dùng chung được.

**Database:** Áp dụng expand–migrate–contract: thêm cột/bảng mới tương thích, deploy code đọc được cả định dạng cũ/mới, backfill có checkpoint, chuyển writer, xác minh dữ liệu, sau khi hết rollback window mới xóa schema cũ. Với thay đổi destructive hoặc data semantics khác, phải có kế hoạch forward-fix, backup và restore rehearsal; rollback binary không thể khôi phục dữ liệu đã bị chuyển đổi. SQL migration có kiểm tra lock duration, execution plan, long-running transaction và downtime. Không coi backup là cơ chế rollback tức thời.

**Delivery:** Duy trì TeamCity/Jenkins nếu chưa có business case hợp nhất; cả hai xuất immutable versioned artifacts có build provenance, test results và dependency scan. Dùng Octopus Deploy hoặc pipeline deployment thống nhất theo môi trường, approval gates phù hợp, config/secrets từ store an toàn, không commit secret. App Service deployment slots có thể hỗ trợ warm-up và swap cho API khi plan/config hỗ trợ; kiểm tra slot-specific settings và database compatibility trước swap. Với IIS, triển khai blue/green hoặc rolling qua nhiều node nếu hạ tầng cho phép; nếu chỉ có một server, không hứa zero downtime.

**Rollout:** Feature flags cho từng module, canary theo nhóm nội bộ hoặc traffic segment khi routing hỗ trợ; smoke tests cho login, payroll/approval, CRUD và API contract. Quan sát p95, error rate, SQL locks, auth failures, business reconciliation và deployment correlation. Rollback bằng cách chuyển traffic/flag về code cũ chỉ khi schema tương thích; nếu không, kích hoạt forward-fix runbook.

**Lộ trình:** Tháng 1 inventory/SLO/baseline và pilot selection; tháng 2–3 build/test/release automation và expand–contract pilot; tháng 4–5 migrate module tiếp theo với canary và observability; tháng 6 rehearsal rollback, đo lead time/change failure rate/MTTR, quyết định có nên tiếp tục di chuyển IIS. Milestone là đề xuất, phải hiệu chỉnh theo effort và dependency thực tế.

**Trade-off:** Shared database giúp giảm migration risk ngắn hạn nhưng giữ coupling. Reverse proxy tăng routing/identity complexity. Dual-running tăng chi phí tạm thời. Một pipeline chuẩn hóa giúp audit và repeatability nhưng đổi toàn bộ công cụ cùng lúc làm tăng rủi ro. Nếu business bắt buộc zero downtime, cần bổ sung hạ tầng redundant và chiến lược traffic switching; nếu không, planned short maintenance có thể kinh tế hơn.

**Kiểm thử:** Contract test portal–API, migration upgrade/downgrade compatibility, Playwright login/approval flows, load test lúc deploy, backup/restore drill, canary failure/rollback drill. Theo dõi dashboard deployment markers, IIS/App Service health, SQL waits và customer-visible failures.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn rewrite hay Kubernetes trước khi đo coupling và downtime thực tế. Tôi sẽ giữ IIS cho portal cũ, chuẩn hóa artifact và release gates, rồi chuyển từng module sang .NET 8 nếu auth, URL và data ownership cho phép. Rủi ro lớn nhất là database dùng chung: rollback code không đồng nghĩa rollback schema, nên tôi dùng expand–migrate–contract và giữ compatibility trong cửa sổ chuyển đổi. Tôi ưu tiên một pilot ít coupling, tự động hóa smoke test và theo dõi error rate, latency, SQL waits theo deployment. App Service slot và reverse proxy có thể hỗ trợ chuyển traffic nhưng cần kiểm tra điều kiện hạ tầng. Sau pilot tôi đánh giá lead time, change failure rate và rollback rehearsal trước khi mở rộng.”

## Câu hỏi đào sâu

1. Nếu hai ứng dụng cùng ghi một bảng với semantics khác nhau, bạn xử lý ownership và transaction boundary thế nào?
2. Nếu hệ thống chỉ có một IIS server, bạn sẽ cam kết zero downtime không và cần đầu tư gì?
3. Khi migration đã xóa dữ liệu cũ, rollback code an toàn còn khả thi không?

## Lỗi trả lời thường gặp

- Đề xuất rewrite toàn bộ mà không phân tích dependency và business risk.
- Gộp schema migration phá tương thích với code rollout.
- Giả định deployment slot tự động rollback database.
- Bỏ qua legacy auth/session và URL compatibility.
- Đổi tất cả CI/CD tools cùng lúc mà không có lợi ích đo được.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cosmos DB cần tối ưu theo access pattern và partition routing chứ không chỉ RU provisioned. Service Bus at-least-once delivery đòi hỏi idempotency ở business boundary và reconciliation cho external side effects. Modernization an toàn phụ thuộc schema compatibility, immutable artifacts, traffic control và khả năng quan sát production.

## Mẫu tư duy cần nhớ

1. Đo RU/request, distribution và query shape trước khi tăng capacity.
2. Stabilize business impact trước khi mở rộng consumer hoặc replay queue.
3. Thiết kế retry cùng idempotency và trạng thái kết quả không xác định.
4. Phân biệt rollback code với rollback data; kiểm tra compatibility window.
5. Chọn kiến trúc đơn giản nhất đáp ứng SLA, rồi chứng minh bằng telemetry và failure tests.
