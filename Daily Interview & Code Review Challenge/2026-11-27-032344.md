# Code Review Challenge 1 — Hoàn điểm thưởng khi nhận sự kiện hủy đơn hàng

## Bối cảnh

Một nền tảng thương mại điện tử hoàn lại điểm thưởng khi đơn hàng bị hủy. Worker chạy trên ba instance, nhận sự kiện từ Azure Service Bus theo chế độ PeekLock, với auto-completion tắt. Mỗi sự kiện chứa định danh nghiệp vụ ổn định do hệ thống đơn hàng cấp. SQL Server lưu số dư và lịch sử xử lý. Giả định số điểm là số nguyên dương, mỗi sự kiện hợp lệ chỉ được hoàn một lần. Các lớp entity, DbContext và record RefundEvent đã được định nghĩa; bảng Accounts có khóa chính Id, Processed có khóa chính tự tăng, EventId chưa có unique constraint.

Sau một đợt gián đoạn mạng, một số khách hàng được hoàn điểm nhiều lần, trong khi một số khách hàng có nhiều đơn hủy gần nhau lại thiếu điểm. Khoảng 20.000 sự kiện mỗi ngày, có đợt tăng lên 100 sự kiện/giây. Chưa biết producer có tái sử dụng MessageId hay không, thời gian xử lý thực tế và yêu cầu thứ tự giữa các sự kiện.

```csharp
public sealed class RefundHandler(
    IServiceScopeFactory scopes,
    ILogger<RefundHandler> logger)
{
    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        using var scope = scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<RewardsDb>();
        var evt = args.Message.Body.ToObjectFromJson<RefundEvent>()!;
        var ct = args.CancellationToken;

        if (await db.Processed.AnyAsync(
            x => x.EventId == evt.EventId, ct))
        {
            await args.CompleteMessageAsync(args.Message, ct);
            return;
        }

        var account = await db.Accounts.SingleAsync(
            x => x.Id == evt.AccountId, ct);

        account.Points += evt.Points;
        await db.SaveChangesAsync(ct);

        db.Processed.Add(new ProcessedEvent
        {
            EventId = evt.EventId,
            AccountId = evt.AccountId
        });

        await db.SaveChangesAsync(ct);

        logger.LogInformation(
            "Refund applied: {Payload}", args.Message.Body.ToString());

        await args.CompleteMessageAsync(args.Message, ct);
    }
}
```

## Kết quả code review tham khảo

### Critical — Hai lần ghi không cùng transaction

**Vấn đề:** Số dư được commit trước bản ghi Processed.

**Tại sao xảy ra:** Hai lần SaveChangesAsync độc lập không tự động tạo một transaction bao trùm cả handler. Nếu lần thứ hai thất bại, số dư đã thay đổi.

**Ảnh hưởng production:** Message được giao lại và hoàn thêm điểm; việc Complete thất bại cũng tạo ra redelivery.

**Cách sửa:** Ghi Inbox và thay đổi số dư trong cùng database transaction. Chỉ Complete sau commit; không giả định transaction SQL bao gồm broker.

### Critical — Check-then-act không bảo đảm idempotency

**Vấn đề:** AnyAsync không ngăn hai worker cùng thấy chưa xử lý.

**Tại sao xảy ra:** Hai transaction có thể cùng đọc trạng thái chưa tồn tại trước khi bất kỳ worker nào ghi. Không có unique constraint để phân xử.

**Ảnh hưởng production:** Hoàn trùng điểm, kể cả khi từng handler được bọc transaction thông thường.

**Cách sửa:** Unique index trên định danh sự kiện nghiệp vụ; insert Inbox trước khi thay đổi số dư. Xử lý conflict bằng cách kiểm tra bản ghi đã commit từ context mới.

### High — Lost update giữa hai sự kiện khác nhau

**Vấn đề:** Hai worker đọc số dư 100, lần lượt cộng 10 và 20 rồi ghi 110 và 120.

**Tại sao xảy ra:** EF Core ghi giá trị tính từ snapshot đã đọc; nếu không có concurrency token, lần ghi sau có thể ghi đè lần trước.

**Ảnh hưởng production:** Kết quả 120 thay vì 130, khách hàng thiếu điểm.

**Cách sửa:** Dùng atomic SQL increment hoặc optimistic concurrency với retry toàn transaction. Không dùng lock trong process vì có nhiều instance.

### High — Payload không hợp lệ không có chính sách xử lý

**Vấn đề:** Null, JSON lỗi, số điểm âm, tài khoản không tồn tại hoặc EventId trống chưa được phân loại.

**Tại sao xảy ra:** Handler giả định mọi message đều hợp lệ.

**Ảnh hưởng production:** Poison message lặp lại; có thể trừ điểm thay vì hoàn, hoặc làm backlog tăng.

**Cách sửa:** Validate contract, phân biệt lỗi vĩnh viễn với dependency failure. Dead-letter dữ liệu sai; tài khoản chưa đồng bộ có thể cần retry nếu nghiệp vụ cho phép. Kiểm tra producer identity và quyền gửi message tại boundary.

### High — Không phát hiện EventId trùng nhưng nội dung khác

**Vấn đề:** Bất kỳ message nào có EventId đã tồn tại đều được Complete.

**Tại sao xảy ra:** Không đối chiếu AccountId và Points.

**Ảnh hưởng production:** Producer lỗi hoặc xung đột định danh có thể làm mất một lần hoàn hợp lệ mà không có cảnh báo.

**Cách sửa:** Lưu các trường nghiệp vụ bất biến, so sánh khi duplicate; đưa conflict vào DLQ để điều tra.

### Medium — Log toàn payload và thiếu telemetry nghiệp vụ

**Vấn đề:** Log raw payload, không phân biệt duplicate, commit, settlement failure.

**Tại sao xảy ra:** Logging tập trung vào nội dung message thay vì kết quả xử lý.

**Ảnh hưởng production:** Có thể lộ dữ liệu khách hàng; khó đối soát khi broker và database không đồng nhất.

**Cách sửa:** Structured logging với EventId, outcome, delivery count và correlation ID; không log dữ liệu cá nhân hoặc payload đầy đủ.

## Phiên bản đề xuất

Ví dụ dưới đây dùng EF Core 8 và SQL Server. Giả định EventId là Guid, AccountId là Guid, Points là long; ProcessedEvent bổ sung Points. Unique index phải được triển khai trước khi bật handler mới. Giả định không bật retrying execution strategy cho DbContext này; nếu bật, phải chạy toàn bộ transaction qua execution strategy và vẫn giữ idempotency.

```csharp
// OnModelCreating
modelBuilder.Entity<ProcessedEvent>()
    .HasIndex(x => x.EventId).IsUnique();
```

```csharp
public sealed class RefundHandler(
    IDbContextFactory<RewardsDb> factory,
    ILogger<RefundHandler> logger)
{
    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var ct = args.CancellationToken;
        RefundEvent? evt;
        try
        {
            evt = args.Message.Body.ToObjectFromJson<RefundEvent>();
        }
        catch (System.Text.Json.JsonException)
        {
            await args.DeadLetterMessageAsync(args.Message,
                "InvalidJson", cancellationToken: ct);
            return;
        }

        if (evt is null || evt.EventId == Guid.Empty ||
            evt.AccountId == Guid.Empty || evt.Points <= 0)
        {
            await args.DeadLetterMessageAsync(args.Message,
                "InvalidContract", cancellationToken: ct);
            return;
        }

        try
        {
            await ApplyAsync(evt, ct);
        }
        catch (DbUpdateException ex) when (
            ex.InnerException is Microsoft.Data.SqlClient.SqlException
                { Number: 2601 or 2627 })
        {
            await using var check = await factory.CreateDbContextAsync(ct);
            var existing = await check.Processed.AsNoTracking()
                .SingleOrDefaultAsync(x => x.EventId == evt.EventId, ct);
            if (existing is null) throw;
            if (existing.AccountId != evt.AccountId ||
                existing.Points != evt.Points)
            {
                logger.LogWarning("Conflicting event {EventId}", evt.EventId);
                await args.DeadLetterMessageAsync(args.Message,
                    "ConflictingEvent", cancellationToken: ct);
                return;
            }
            logger.LogInformation("Duplicate {EventId}", evt.EventId);
        }

        await args.CompleteMessageAsync(args.Message, ct);
    }

    private async Task ApplyAsync(RefundEvent evt, CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        await using var tx = await db.Database.BeginTransactionAsync(ct);
        db.Processed.Add(new ProcessedEvent
        {
            EventId = evt.EventId, AccountId = evt.AccountId,
            Points = evt.Points
        });
        await db.SaveChangesAsync(ct);

        var changed = await db.Accounts
            .Where(x => x.Id == evt.AccountId)
            .ExecuteUpdateAsync(s => s.SetProperty(
                x => x.Points, x => x.Points + evt.Points), ct);
        if (changed != 1)
            throw new InvalidOperationException("Account not available");

        await tx.CommitAsync(ct);
        logger.LogInformation("Committed refund {EventId}", evt.EventId);
    }
}
```

## Giải thích thiết kế sau khi sửa

Unique index là điểm phân xử giữa các instance. Nếu insert thất bại, ApplyAsync thoát và dispose transaction trước khi context mới kiểm tra duplicate. Nếu update tài khoản thất bại, Inbox cũng rollback. Atomic increment thực hiện phép cộng tại database, tránh lost update giữa các sự kiện độc lập. Nếu commit thành công nhưng response bị mất, lần giao lại sẽ gặp unique conflict và kiểm tra nội dung trước khi Complete.

Cần xác minh giới hạn số dư, overflow, định danh theo tenant nếu EventId không duy nhất toàn hệ thống và quy tắc hoàn điểm theo đơn. Nếu tài khoản không tồn tại vĩnh viễn, bổ sung phân loại lỗi nghiệp vụ và DLQ; ví dụ hiện tại để lỗi lan ra nhằm không xác nhận mất message. Không retry vô hạn; cấu hình delivery limit, lock renewal và quy trình xử lý DLQ phù hợp. Đối soát dữ liệu cũ trước khi tạo unique index, không tự động xóa lịch sử trùng khi chưa xác minh số dư.

## Trade-offs

Inbox tăng dung lượng và chi phí ghi; thời gian lưu phải bao phủ thời gian replay nghiệp vụ. Atomic update phù hợp với phép cộng độc lập, nhưng nếu có giới hạn số dư hoặc quy tắc phức tạp cần conditional update hoặc concurrency token. Nếu cần phát sự kiện tiếp theo, cân nhắc Outbox cùng transaction thay vì gửi trực tiếp trước commit. Không cần distributed lock chỉ để thực hiện phép cộng trong một database.

```typescript
async function getHistory(req: Request, res: Response) {
  const employeeId = String(req.query.employeeId);
  const from = String(req.query.from);
  const to = String(req.query.to);
  const page = Number(req.query.page ?? 1);
  const size = Number(req.query.size ?? 50);

  const query = {
    query: `
      SELECT * FROM c
      WHERE c.employeeId = @employeeId
        AND c.occurredAt >= @from
        AND c.occurredAt < @to
      ORDER BY c.occurredAt DESC
      OFFSET @offset LIMIT @size
    `,
    parameters: [
      { name: "@employeeId", value: employeeId },
      { name: "@from", value: from },
      { name: "@to", value: to },
      { name: "@offset", value: (page - 1) * size },
      { name: "@size", value: size }
    ]
  };

  const { resources } = await container.items
    .query(query).fetchAll();

  res.json({ page, size, items: resources });
}
```

### Critical — Broken object-level authorization và thiếu tenant filter

**Vấn đề:** API tin employeeId do client cung cấp và không lọc tenantId.

### High — Pagination không giới hạn và thiếu validation

**Vấn đề:** size, page và khoảng ngày không được kiểm tra.

**Tại sao xảy ra:** Chuyển kiểu Number không bảo đảm số nguyên hợp lệ; ngày dạng chuỗi không được chuẩn hóa.

**Tại sao xảy ra:** OFFSET LIMIT không giữ vị trí duyệt ổn định giữa các request.

**Ảnh hưởng production:** RU và latency tăng, có thể bỏ sót hoặc lặp mục.

**Cách sửa:** Dùng continuation token, sort theo occurredAt và id; không cam kết snapshot xuyên nhiều request. Nếu cần báo cáo nhất quán, tạo snapshot hoặc quy trình export riêng.

### Medium — Projection và partition routing chưa rõ ràng

**Vấn đề:** SELECT * trả cả metadata, không truyền partitionKey rõ ràng.

### Medium — Không có telemetry và xử lý dependency failure

**Vấn đề:** Không ghi nhận request charge, throttling hoặc lỗi dependency.

**Tại sao xảy ra:** Handler chỉ lấy resources và trả JSON.

**Ảnh hưởng production:** Khó phân biệt hot partition, truy vấn đắt và thiếu throughput.

**Cách sửa:** Thu thập RU, latency, status và diagnostics phù hợp; xử lý lỗi qua middleware, không trả raw exception.

```typescript
  const identity = requireEmployeeIdentity(req);
  const input = parseHistoryQuery(req.query);
  const scope = {
    tenantId: identity.tenantId,
    employeeId: identity.employeeId,
    from: input.from,

  const continuationToken = input.cursor
    ? verifyCursor(input.cursor, scope)
    : undefined;

  const query = {
    query: `
      SELECT c.id, c.occurredAt, c.type
      FROM c
      WHERE c.tenantId = @tenantId
        AND c.employeeId = @employeeId
        AND c.occurredAt >= @from
        AND c.occurredAt < @to
      ORDER BY c.occurredAt DESC, c.id DESC
    `,
    parameters: [
      { name: "@tenantId", value: scope.tenantId },
      { name: "@employeeId", value: scope.employeeId },
      { name: "@from", value: scope.from },
      { name: "@to", value: scope.to }
    ]
  };

  const result = await container.items.query(query, {
    partitionKey: scope.employeeId,
    maxItemCount: scope.size,
    continuationToken
  }).fetchNext();

  recordHistoryMetrics(result.requestCharge, result.resources.length);
  res.json({
    items: result.resources,
    nextCursor: result.continuationToken
      ? signCursor(result.continuationToken, scope)
      : null
  });
}
```

## Giải thích thiết kế sau khi sửa

requireEmployeeIdentity lấy thông tin từ principal đã xác thực và ánh xạ quyền nhân viên; từ chối nếu thiếu mapping. parseHistoryQuery chỉ chấp nhận from/to hợp lệ, UTC chuẩn hóa, from nhỏ hơn to, size nguyên 1–100 và khoảng ngày tối đa theo chính sách (ví dụ 90 ngày). Không nhận employeeId tùy ý. verifyCursor xác minh chữ ký, expiry, version và toàn bộ scope; signCursor tạo token có integrity protection, không log token. Nếu token chứa dữ liệu nhạy cảm, dùng encryption hoặc opaque server-side handle. Middleware chuyển lỗi validation thành 400, authorization thành 403, dependency failure thành lỗi phù hợp mà không lộ nội bộ.

Continuation token là opaque và phải được sử dụng với query tương thích. Một lần fetchNext có thể trả ít hơn size, thậm chí trang rỗng nhưng vẫn còn token; client tiếp tục theo nextCursor, không dựa vào số lượng mục. Không bảo đảm snapshot nếu dữ liệu thay đổi. Chuẩn hóa occurredAt khi ghi để thứ tự chuỗi phù hợp thời gian.

Partition key /employeeId có thể gom nhân viên trùng mã từ nhiều tenant vào cùng logical partition. Nếu đo thấy vấn đề đáng kể, cân nhắc container mới với synthetic key tenantId + employeeId được mã hóa không nhập nhằng. Đổi partition key là migration dữ liệu, cần backfill, đồng bộ thay đổi, đối soát, chuyển đọc/ghi và rollback. HR query theo tenant có thể cần read model riêng nếu workload chứng minh chi phí đáng kể; không tự động nhân bản dữ liệu.

## Trade-offs

Continuation token không hỗ trợ nhảy trực tiếp đến trang bất kỳ như offset; UI nên dùng next/load more. Composite index tăng chi phí ghi và dung lượng. Giới hạn khoảng ngày giảm tải nhưng cần endpoint export riêng nếu nghiệp vụ yêu cầu lịch sử dài. Synthetic partition key tăng isolation về phân bố dữ liệu, không thay thế authorization. Chỉ tăng throughput khi số liệu chứng minh thiếu capacity, không dùng để che truy vấn sai.

## Cách kiểm thử

1. Security integration test: hai tenant cùng employeeId, người dùng chỉ thấy dữ liệu của tenant mình; sửa cursor hoặc dùng cursor tenant khác phải bị từ chối.
2. Contract test: size âm, NaN, ngày sai, khoảng quá dài và cursor hết hạn.
3. Database test: nhiều document cùng occurredAt, duyệt hết dữ liệu tĩnh không trùng hoặc thiếu; kiểm tra cả trang rỗng có token.
4. Load test: so sánh RU và p95 của offset sâu với continuation token trên cùng dataset, kiểm tra index và phân bố partition.
5. Failure-path test: dependency throttling hoặc timeout, API trả lỗi an toàn và client không tạo retry storm.

## Quan sát trong production

Đo request charge mỗi trang, p95/p99 latency, 429, retry count nếu có telemetry SDK, normalized RU consumption theo partition và kích thước response. Dùng Azure Monitor và Application Insights để tương quan API trace với dependency. Alert khi RU/request tăng bất thường, throttling kéo dài hoặc phát hiện authorization failure tăng. Không log JWT, cursor, dữ liệu chấm công hoặc employeeId dưới dạng metric label.

## Câu hỏi phỏng vấn mở rộng

- Nếu HR cần thống kê toàn tenant theo ngày, bạn chọn query trực tiếp hay read model?
- Khi nào SQL Server hoặc PostgreSQL phù hợp hơn Cosmos DB cho nghiệp vụ này?
- Làm sao triển khai migration partition key mà không mất dữ liệu trong lúc ghi liên tục?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Idempotency nghiệp vụ cần constraint và transaction tại nơi lưu trạng thái; broker settlement không nằm trong SQL transaction.
- Atomic increment tránh lost update đối với phép cộng độc lập.
- Tenant isolation là authorization và data filtering, không phải partition routing.
- Continuation token, projection và index phải được đánh giá bằng RU và latency thực tế.

## Mẫu tư duy cần nhớ

1. Xác định invariant trước khi chọn concurrency mechanism.
2. Thiết kế retry cùng idempotency và kiểm thử commit không rõ kết quả.
3. Kiểm tra authorization trước tối ưu hiệu năng.
4. Đo workload thực tế trước khi đổi partition key.
5. Kiểm thử failure path và quan sát kết quả nghiệp vụ, không chỉ HTTP status.
