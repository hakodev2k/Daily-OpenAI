# Code Review Challenge 1 — Checkout vượt tồn kho trong SQL Server

**Chủ đề:** C#/.NET 8, ASP.NET Core, SQL Server, transactional correctness  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút

## Bối cảnh

API checkout của một hệ thống e-commerce chạy 6 instances trên Azure App Service. SQL Server là source of truth cho tồn kho. Một SKU còn 3 đơn vị nhưng chiến dịch flash sale nhận 400 checkout đồng thời; đơn hàng có trạng thái PendingPayment, cổng thanh toán được gọi qua HTTP. Vài đơn cùng được xác nhận dù không đủ hàng; đôi lúc khách bị trừ tiền nhưng không có đơn hàng. Mỗi request có header Idempotency-Key do client gửi, song mobile app có thể retry sau timeout. Chưa xác minh payment provider hỗ trợ idempotency hay refund API. Yêu cầu: không bán vượt kho; tránh thu tiền lặp; có đường phục hồi sau lỗi từng phần.

## Đoạn code cần review

~~~csharp
[ApiController]
[Route("api/checkout")]
public sealed class CheckoutController : ControllerBase
{
    private readonly ShopDbContext _db;
    private readonly HttpClient _payment;

    public CheckoutController(ShopDbContext db, IHttpClientFactory clients)
    {
        _db = db;
        _payment = clients.CreateClient("payment");
    }

    [HttpPost]
    public async Task<IActionResult> Checkout(
        CheckoutRequest request, CancellationToken ct)
    {
        var item = await _db.Products
            .SingleOrDefaultAsync(x => x.Id == request.ProductId, ct);

        if (item == null || item.Stock < request.Quantity)
            return Conflict("Out of stock");

        item.Stock -= request.Quantity;

        var order = new Order
        {
            Id = Guid.NewGuid(),
            ProductId = item.Id,
            Quantity = request.Quantity,
            Amount = item.Price * request.Quantity,
            Status = "PendingPayment"
        };
        _db.Orders.Add(order);

        var paymentResponse = await _payment.PostAsJsonAsync(
            "/charges",
            new { OrderId = order.Id, Amount = order.Amount },
            ct);

        if (!paymentResponse.IsSuccessStatusCode)
            return StatusCode(502);

        order.Status = "Paid";
        await _db.SaveChangesAsync(ct);
        return Ok(new { order.Id, order.Status });
    }
}
~~~

Giả định: authentication middleware có sẵn; entity Product/Order và DTO tồn tại; SQL Server mặc định READ COMMITTED; payment endpoint có thể timeout sau khi đã xử lý charge.

## Kết quả code review tham khảo

### [Critical] — Race condition làm bán vượt tồn kho

**Vấn đề:** Hai request đọc cùng Stock rồi cùng trừ trên entity đã load.  
**Tại sao xảy ra:** Read và write không được bảo vệ bởi điều kiện cập nhật atomic; EF change tracking không tự serialize requests.  
**Ảnh hưởng production:** Oversell hoặc lost update, tùy mapping và concurrency configuration.  
**Cách sửa:** Conditional UPDATE Stock = Stock - quantity WHERE Id = ... AND Stock >= quantity; yêu cầu affected rows = 1, chạy cùng transaction tạo order. Có thể dùng rowversion với retry có kiểm soát, nhưng phải chứng minh không oversell.

### [Critical] — Charge xảy ra trước khi lưu order

**Vấn đề:** Payment thành công trước khi DB commit.  
**Tại sao xảy ra:** Không có atomic transaction giữa HTTP payment provider và SQL Server.  
**Ảnh hưởng production:** Khách bị thu tiền nhưng DB không có order; retry có thể charge tiếp.  
**Cách sửa:** Commit reservation/order trước; thực hiện payment qua workflow có trạng thái, reconciliation và compensation khi cần. Không coi timeout là thất bại chắc chắn.

### [High] — Không xử lý idempotency của request

**Vấn đề:** Header Idempotency-Key không được sử dụng.  
**Tại sao xảy ra:** Mỗi retry tạo Guid mới và gọi charge mới.  
**Ảnh hưởng production:** Duplicate order và duplicate charge.  
**Cách sửa:** Unique constraint trên (CustomerId, IdempotencyKey), lưu request fingerprint; cùng key/cùng payload trả lại trạng thái hiện có, khác payload trả conflict. Nếu provider hỗ trợ, dùng stable payment idempotency key.

### [High] — Không có transaction cho reservation và order

**Vấn đề:** Trừ stock và tạo order chưa được commit trước external call.  
**Tại sao xảy ra:** SaveChanges nằm sau payment; exception hoặc cancellation bỏ lại trạng thái không rõ ràng.  
**Ảnh hưởng production:** Không thể biết có reservation hợp lệ trước khi thu tiền.  
**Cách sửa:** Gói conditional decrement và insert order trong một DB transaction ngắn; commit trước network call.

### [High] — Không có state machine và recovery cho payment

**Vấn đề:** Chỉ có PendingPayment/Paid; thiếu trạng thái Unknown, Failed, Expired hoặc reconciliation.  
**Tại sao xảy ra:** Xem một HTTP response là nguồn chân lý duy nhất.  
**Ảnh hưởng production:** Reservation treo, hoàn kho sai hoặc đơn bị mất.  
**Cách sửa:** Worker reconcile qua provider status API/webhook (nếu có), transition có guard, expiry và hoàn kho một lần theo transaction.

### [Medium] — Giá và danh tính khách chưa được ràng buộc rõ

**Vấn đề:** Order không ghi CustomerId và price snapshot rõ ràng; không xác nhận quantity dương.  
**Tại sao xảy ra:** Endpoint tin DTO và trạng thái hiện tại mà thiếu validation/authorization.  
**Ảnh hưởng production:** Negative quantity có thể làm tăng kho; idempotency key bị dùng chéo người; giá audit khó.  
**Cách sửa:** Validate Quantity > 0, lấy CustomerId từ authenticated principal, snapshot giá và currency từ server, kiểm tra business constraints.

### [Medium] — Timeout/cancellation bị hiểu sai

**Vấn đề:** Client ngắt kết nối có thể cancel request giữa các bước không thể đảo ngược.  
**Tại sao xảy ra:** Truyền trực tiếp request CancellationToken cho charge rồi giả định việc hủy local tương đương hủy remote.  
**Ảnh hưởng production:** Payment hoàn tất nhưng application không nhận kết quả.  
**Cách sửa:** Sau DB commit, giao xử lý cho durable worker; ghi trạng thái và reconcile. Cancellation chỉ dừng công việc local an toàn, không kết luận remote rollback.

### [Medium] — Thiếu telemetry và giới hạn external dependency

**Vấn đề:** Không có correlation, timeout policy được mô tả, metric reservation/payment.  
**Tại sao xảy ra:** Flow synchronous che khuất các failure mode.  
**Ảnh hưởng production:** Không phân biệt DB contention, gateway timeout và double charge.  
**Cách sửa:** Structured logs không chứa dữ liệu thẻ, trace order/payment attempt, alert pending age và reconciliation backlog.

## Phiên bản đề xuất

Thiết kế dưới đây là **core reservation transaction**, không phải toàn bộ checkout production. Giả định Product.Stock là số nguyên, IdempotencyKey và CustomerId có unique index, Order có PaymentState và PriceSnapshot. Phần gọi provider được chuyển ra worker, cần bổ sung durable outbox trong cùng transaction nếu worker được kích hoạt qua queue.

~~~csharp
public async Task<CheckoutResult> ReserveAsync(
    Guid customerId, Guid productId, int quantity,
    string idempotencyKey, CancellationToken ct)
{
    if (quantity <= 0 || quantity > 100)
        throw new ValidationException("Invalid quantity");
    if (string.IsNullOrWhiteSpace(idempotencyKey) ||
        idempotencyKey.Length > 128)
        throw new ValidationException("Invalid idempotency key");

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var previous = await _db.Orders.SingleOrDefaultAsync(
        x => x.CustomerId == customerId &&
             x.IdempotencyKey == idempotencyKey, ct);

    if (previous != null)
    {
        if (previous.ProductId != productId ||
            previous.Quantity != quantity)
            throw new IdempotencyConflictException();

        await tx.CommitAsync(ct);
        return new CheckoutResult(previous.Id, previous.PaymentState);
    }

    var product = await _db.Products.AsNoTracking()
        .Where(x => x.Id == productId)
        .Select(x => new { x.Id, x.Price, x.Currency })
        .SingleOrDefaultAsync(ct);
    if (product == null) throw new NotFoundException();

    var changed = await _db.Products
        .Where(x => x.Id == productId && x.Stock >= quantity)
        .ExecuteUpdateAsync(s => s.SetProperty(
            p => p.Stock, p => p.Stock - quantity), ct);

    if (changed != 1) throw new OutOfStockException();

    var order = new Order
    {
        Id = Guid.NewGuid(),
        CustomerId = customerId,
        IdempotencyKey = idempotencyKey,
        ProductId = productId,
        Quantity = quantity,
        PriceSnapshot = product.Price,
        Currency = product.Currency,
        PaymentState = "Pending"
    };
    _db.Orders.Add(order);
    _db.OutboxMessages.Add(OutboxMessage.PaymentRequested(order.Id));

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return new CheckoutResult(order.Id, order.PaymentState);
}
~~~

**Lưu ý bắt buộc:** Concurrent requests cùng key vẫn có thể cùng vượt qua bước kiểm tra trước khi insert. Unique index là hàng rào cuối; khi gặp unique violation, rollback toàn bộ transaction (bao gồm stock decrement), đọc lại order đã commit trong DbContext mới rồi so khớp fingerprint. Worker phải dùng payment attempt ID ổn định, kiểm tra trạng thái provider và chỉ chuyển state theo guarded transition. Outbox dispatcher phải chịu được gửi lặp. Price có thể thay đổi giữa read và reserve; nếu cần giá nhất quán tuyệt đối, đưa price snapshot và stock reservation vào cùng statement/locking strategy hoặc xác minh version trước commit.

## Giải thích thiết kế sau khi sửa

SQL Server đảm bảo conditional decrement thực thi atomic đối với cùng row. Transaction ngắn giữ reservation, order và outbox cùng commit. Payment nằm ngoài transaction để không giữ DB locks trong lúc network chậm. Order là bản ghi phục hồi; outbox là durable intent, không phải bảo đảm exactly-once delivery. Reconciliation xử lý trạng thái remote không chắc chắn; compensation hoàn stock chỉ khi xác minh không có successful charge hoặc đã refund theo chính sách.

## Trade-offs

Reservation làm tăng complexity: cần expiry policy, worker, state machine và reconciliation. Nếu throughput thấp và provider hỗ trợ synchronous idempotent payment, có thể dùng flow đơn giản hơn nhưng vẫn cần transaction, persisted state và recovery. Reservation có thể giữ kho khi payment chậm; cần SLA và fairness. SQL conditional update tạo contention trên hot SKU, phải đo lock waits trước khi shard hoặc queue theo SKU.

## Cách kiểm thử

1. **Concurrency integration:** 400 requests mua cùng SKU Stock=3; tổng Quantity được reserve không vượt 3; assert DB invariant.
2. **Idempotency:** 100 retry cùng customer/key/payload chỉ có một order; khác payload trả conflict; mô phỏng race trước unique insert.
3. **Failure injection:** DB commit lỗi, worker crash, provider timeout sau charge; không double charge, trạng thái có thể reconcile.
4. **Database test:** Xác minh rollback stock khi unique constraint violation và kiểm tra transaction isolation/lock waits.
5. **Recovery test:** Reservation hết hạn, webhook đến trễ, refund thất bại; không hoàn kho hai lần.

## Quan sát trong production

Theo dõi reservation attempts/success/conflict, stock-negative invariant, payment attempts per order, pending age, outbox backlog, duplicate-key rate, SQL deadlocks/lock waits và gateway timeout. Dùng Application Insights dependency tracing, correlation theo OrderId/PaymentAttemptId; không log thông tin thanh toán nhạy cảm. Alert khi pending vượt SLA hoặc tổng successful charge khác tổng paid order sau reconciliation window.

1. Nếu flash sale tạo hot row với 10.000 requests/giây, bạn đo gì trước khi cân nhắc serialized reservation queue?

3. Nếu phải hỗ trợ nhiều SKU trên một order, làm thế nào tránh deadlock và partial reservation?

<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Hit = { id: string; title: string; snippet: string; url: string }
const query = ref('')
const hits = ref<Hit[]>([])
const loading = ref(false)
const error = ref('')
const history = ref<string[]>([])

async function search(value: string) {
  loading.value = true
  error.value = ''
  const response = await fetch(
    '/api/search?q=' + encodeURIComponent(value),
    { credentials: 'include' }
  )
  const body = await response.json()
  hits.value = body.items
  history.value.push(value)
  loading.value = false
}

watch(query, value => {
  if (value.trim().length > 0) search(value)
  else hits.value = []
})

onMounted(() => {
  const saved = localStorage.getItem('search-history')
  if (saved) history.value = JSON.parse(saved)
})

watch(history, value => {
  localStorage.setItem('search-history', JSON.stringify(value))
}, { deep: true })
</script>

<template>
  <section>
    <label for="search">Search documents</label>
    <input id="search" v-model="query" autocomplete="off">
    <p v-if="loading">Searching...</p>
    <p v-if="error">{{ error }}</p>
    <ul>
      <li v-for="hit in hits" :key="hit.id">
        <a :href="hit.url" v-html="hit.title"></a>
        <div v-html="hit.snippet"></div>
      </li>
    </ul>
  </section>
</template>

## Kết quả code review tham khảo

### [Critical] — Render HTML không đáng tin cậy

**Vấn đề:** title/snippet từ API được đưa thẳng vào v-html.  
**Tại sao xảy ra:** v-html chèn HTML, không tự sanitize nội dung.  
**Ảnh hưởng production:** Stored/reflected XSS nếu dữ liệu search bị nhiễm HTML nguy hiểm; có thể thực hiện hành động trong session tùy các defense khác.  
**Cách sửa:** Render text bằng interpolation; nếu highlight cần thiết, render tokenized text qua VNodes/text nodes, không dùng raw HTML. CSP là defense-in-depth, không thay thế encoding.

### [High] — URL của kết quả không được giới hạn scheme/host

**Vấn đề:** href nhận trực tiếp từ dữ liệu search.  
**Tại sao xảy ra:** API response bị tin là safe navigation target.  
**Ảnh hưởng production:** Link có thể trỏ đến scheme hoặc domain không được phép, tạo phishing hoặc script execution tùy browser và context.  
**Cách sửa:** Validate bằng URL parser, allowlist https/http và origin hoặc host được duyệt; ưu tiên API trả route nội bộ theo document ID.

### [High] — Race giữa các request làm stale results

**Vấn đề:** Request cũ có thể ghi đè kết quả mới.  
**Tại sao xảy ra:** Promise hoàn thành không theo thứ tự khởi chạy.  
**Ảnh hưởng production:** Người dùng thấy kết quả của từ khóa khác, có thể mở nhầm tài liệu.  
**Cách sửa:** Debounce và AbortController; thêm monotonically increasing request sequence để chặn response cũ kể cả abort không kịp.

### [High] — Không kiểm tra HTTP status và không catch/finally

**Vấn đề:** 401/403/500 có thể bị parse thành items sai; network error làm loading bị treo.  
**Tại sao xảy ra:** fetch chỉ reject với network-level errors, không tự reject trên HTTP error status.  
**Ảnh hưởng production:** Empty/broken UI, unhandled promise rejection và misleading loading.  
**Cách sửa:** Kiểm tra response.ok, validate payload shape, catch lỗi thực, finally chỉ cập nhật request hiện hành.

### [Medium] — Request storm và thiếu cleanup

**Vấn đề:** Mỗi keystroke gửi một request; không hủy request khi component unmount.  
**Tại sao xảy ra:** Watcher không debounce, không cleanup.  
**Ảnh hưởng production:** Tốn backend resources, tăng latency và làm UI khó dự đoán.  
**Cách sửa:** Debounce 250–350 ms theo nhu cầu thực tế, abort khi query đổi/unmount, giới hạn length và API rate limiting.

### [Medium] — Lưu search history vô hạn trong localStorage

**Vấn đề:** Mọi query được giữ lâu dài, không có consent/retention, không giới hạn dung lượng.  
**Tại sao xảy ra:** Local storage là persistence shared theo origin, không phải kho bí mật.  
**Ảnh hưởng production:** Lộ truy vấn nhạy cảm cho script cùng origin/người dùng chung browser; quota exception.  
**Cách sửa:** Bỏ lưu mặc định cho nội dung nội bộ; nếu có requirement, dùng opt-in, TTL/limit, clear khi sign-out và privacy review.

### [Medium] — Thiếu accessibility và trạng thái empty/keyboard

**Vấn đề:** Không có role/status cho live results, không có empty state hay keyboard selection.  
**Tại sao xảy ra:** UI chỉ render list động.  
**Ảnh hưởng production:** Screen reader không biết kết quả đổi; UX keyboard không đầy đủ.  
**Cách sửa:** aria-live, loading/empty state; nếu là combobox autocomplete thì triển khai WAI-ARIA combobox pattern đầy đủ, không chỉ thêm role.

<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

type Hit = { id: string; title: string; snippet: string; url: string }
const query = ref('')
const hits = ref<Hit[]>([])
const loading = ref(false)
const error = ref('')
let timer: ReturnType<typeof setTimeout> | undefined
let controller: AbortController | undefined
let version = 0

function safeHref(value: string): string | null {
  try {
    const url = new URL(value, window.location.origin)
    if (url.origin !== window.location.origin) return null
    if (!['http:', 'https:'].includes(url.protocol)) return null
    return url.pathname + url.search + url.hash
  } catch {
    return null
  }
}

watch(query, raw => {
  version++
  const current = version
  if (timer) clearTimeout(timer)
  controller?.abort()
  hits.value = []
  error.value = ''
  loading.value = false

  const value = raw.trim()
  if (value.length < 2 || value.length > 100) return

  timer = setTimeout(async () => {
    const abort = new AbortController()
    controller = abort
    loading.value = true
    try {
      const response = await fetch(
        '/api/search?q=' + encodeURIComponent(value),
        { signal: abort.signal, credentials: 'include' }
      )
      if (!response.ok) throw new Error('Search unavailable')
      const body: unknown = await response.json()
      if (!body || typeof body !== 'object' ||
          !('items' in body) || !Array.isArray(body.items))
        throw new Error('Invalid response')
      const items = body.items as unknown[]
      if (current === version) {
        hits.value = items.filter((x): x is Hit => {
          if (!x || typeof x !== 'object') return false
          const v = x as Record<string, unknown>
          return typeof v.id === 'string' &&
            typeof v.title === 'string' &&
            typeof v.snippet === 'string' &&
            typeof v.url === 'string'
        }).slice(0, 20)
      }
    } catch (e) {
      if (current === version && !abort.signal.aborted)
        error.value = 'Không thể tìm kiếm. Vui lòng thử lại.'
    } finally {
      if (current === version) loading.value = false
    }
  }, 300)
})

onBeforeUnmount(() => {
  version++
  if (timer) clearTimeout(timer)
  controller?.abort()
})
</script>

<template>
  <section>
    <label for="search">Search documents</label>
    <input id="search" v-model="query" autocomplete="off"
           maxlength="100" aria-controls="results">
    <p role="status" aria-live="polite">
      {{ loading ? 'Searching...' : error ||
         (query.trim().length >= 2 ? hits.length + ' results' : '') }}
    </p>
    <ul id="results">
      <li v-for="hit in hits" :key="hit.id">
        <a v-if="safeHref(hit.url)" :href="safeHref(hit.url)!">
          {{ hit.title }}
        </a>
        <span v-else>{{ hit.title }}</span>
        <div>{{ hit.snippet }}</div>
      </li>
    </ul>
  </section>
</template>
~~~

**Giới hạn rõ ràng:** Đây là search results list, chưa phải fully accessible autocomplete/combobox. URL allowlist same-origin là giả định sản phẩm; nếu tài liệu nằm trên trusted external domains thì cần allowlist riêng. Type guard chỉ xác minh shape, không chứng minh quyền truy cập hay tính an toàn của nội dung; backend vẫn phải lọc theo user và tenant.

## Giải thích thiết kế sau khi sửa

Sequence guard quyết định response nào được phép thay đổi state; AbortController giảm tải nhưng không đảm bảo server đã ngừng xử lý. Debounce giảm request rate. Text interpolation ngăn HTML trở thành executable DOM. UI không persist query nội bộ. Backend cần enforce authorization trên search và document detail, kiểm soát cache header và không trả snippet của tài liệu không được phép đọc.

## Trade-offs

Debounce thêm độ trễ có chủ đích; giá trị 300 ms phải đo bằng UX telemetry. Abort giảm network nhưng có thể không giảm DB load đã bắt đầu. Không dùng v-html làm mất highlight rich HTML; thay bằng token spans tăng code và test. Same-origin URL policy có thể loại link hợp lệ sang CMS khác. Không lưu history giảm tiện ích nhưng bảo vệ privacy. Nếu kết quả lớn, cân nhắc pagination/virtualization dựa trên đo lường thay vì mặc định.

## Cách kiểm thử

1. **Race test:** Dùng Playwright intercept hai response A/B, trả B trước A; chỉ kết quả B được hiển thị.
2. **Security test:** API trả title/snippet chứa HTML và URL javascript:/external domain; không thực thi script, không render link nguy hiểm.
3. **Failure-path test:** 401/403/500, malformed JSON, network offline và component unmount; không unhandled rejection/loading treo.
4. **Load test:** Gõ nhanh 20 ký tự, đo request count, backend query rate và cancellation.
5. **Authorization E2E:** Hai user/tenant khác nhau tìm cùng keyword; không lộ title/snippet của tài liệu ngoài quyền, kể cả qua cache.

## Quan sát trong production

Theo dõi search request rate per session, aborted requests, HTTP 4xx/5xx, p95 response latency, empty-result ratio và frontend errors; dùng browser network waterfall và Application Insights correlation ID. Theo dõi access-denied search attempts mà không log raw sensitive keywords. Nếu có CDN, kiểm tra Cache-Control và cache key có phân biệt authorization; mặc định không shared-cache personalized search.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend dùng Elasticsearch eventual consistency, UI nên giải thích tài liệu vừa cập nhật chưa xuất hiện thế nào?
2. Nếu cần highlight keyword trong snippet do API trả về, bạn thiết kế contract token ranges và escape như thế nào?
3. Nếu API search dùng cookie auth, những kiểm soát CSRF/CORS và cache nào cần xem xét theo HTTP method và deployment thực tế?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Atomic conditional update và unique constraint là hàng rào correctness trong checkout concurrent; HTTP payment không thuộc SQL transaction.
- Idempotency phải được thiết kế end-to-end, có persisted state và recovery khi timeout tạo trạng thái không chắc chắn.
- Vue async state cần chống out-of-order responses; hủy request không thay thế sequence validation.
- Untrusted search data phải được render thành text và authorization luôn được enforce ở backend.

## Mẫu tư duy cần nhớ

1. **Đặt invariant trước implementation:** stock không âm, mỗi idempotency key không tạo nhiều đơn.
2. **Thiết kế failure path trước happy path:** remote success + local timeout là trạng thái cần reconcile.
3. **Phân biệt cancellation với rollback:** hủy request không có nghĩa side effect đã bị hủy.
4. **Không tin dữ liệu qua trust boundary:** API response cũng cần output encoding, URL policy và quyền truy cập.
5. **Đo trước khi thêm complexity:** contention, request storm và p95 quyết định cần queue/cache/virtualization hay không.
