# Code Review Challenge 1 — Optimizely page hiển thị nhầm nội dung Premium và stale content sau publish vì cache chồng cache

**Chủ đề:** C#/.NET 8, ASP.NET Core, Optimizely CMS, custom caching, multi-instance behavior, personalization, Akamai/CDN caching, language variants, security boundary, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một marketing website chạy Optimizely CMS 12 trên nhiều ASP.NET Core instances sau load balancer. Website có:

- nội dung theo ngôn ngữ `vi` và `en`;
- một số promo chỉ dành cho user thuộc nhóm Premium;
- Akamai đứng trước origin để cache HTML public;
- editor có thể publish page nhiều lần trong ngày;
- business yêu cầu nội dung mới phải xuất hiện trong vài phút sau publish;
- nội dung Premium tuyệt đối không được lộ cho user thường.

Team vừa tối ưu trang landing vì cho rằng gọi Optimizely content API quá nhiều. Họ thêm `IMemoryCache` cho ViewModel và set `Cache-Control` để Akamai giữ HTML 10 phút.

Sau release, production xuất hiện các triệu chứng:

- đôi lúc user thường thấy promo Premium;
- refresh lại có lúc đúng, lúc sai tùy request rơi vào instance nào;
- editor publish nội dung mới nhưng một số user vẫn thấy bản cũ khá lâu;
- đổi ngôn ngữ từ `vi` sang `en` nhưng đôi khi title/promo vẫn là tiếng Việt;
- origin CPU giảm nhưng support tickets về “nội dung sai người/sai ngôn ngữ” tăng mạnh.

Team hiện chưa biết lỗi nằm ở Optimizely cache, `IMemoryCache`, Akamai hay tất cả cùng tương tác.

## Đoạn code cần review

```csharp
public sealed class LandingPageController : PageController<LandingPage>
{
    private readonly IContentLoader _contentLoader;
    private readonly IMemoryCache _cache;

    public LandingPageController(
        IContentLoader contentLoader,
        IMemoryCache cache)
    {
        _contentLoader = contentLoader;
        _cache = cache;
    }

    public IActionResult Index(LandingPage currentPage)
    {
        var cacheKey = $"landing:{currentPage.ContentLink.ID}";

        var model = _cache.GetOrCreate(cacheKey, entry =>
        {
            entry.AbsoluteExpirationRelativeToNow =
                TimeSpan.FromMinutes(30);

            var promoBlocks = _contentLoader
                .GetChildren<PromoBlock>(currentPage.PromoFolder)
                .ToList();

            var isPremium = User.IsInRole("Premium");

            var selectedPromo = isPremium
                ? promoBlocks.FirstOrDefault(x => x.PremiumOnly)
                : promoBlocks.FirstOrDefault(x => !x.PremiumOnly);

            return new LandingPageViewModel
            {
                Title = currentPage.Name,
                HeroText = currentPage.HeroText,
                PromoTitle = selectedPromo?.Title,
                PromoBody = selectedPromo?.Body,
                IsPremium = isPremium
            };
        });

        Response.Headers.CacheControl =
            "public,max-age=600,s-maxage=600";

        return View(model);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, security, freshness, multi-instance và maintainability trong implementation hiện tại.
2. Giải thích cách cùng một cache key có thể làm user thường nhận ViewModel được tạo từ request Premium.
3. Phân tích tương tác giữa Optimizely object cache, custom `IMemoryCache` và CDN/edge cache.
4. Giải thích tại sao bug có thể xuất hiện không ổn định giữa các application instances.
5. Review cách cache key đang xử lý language/culture và các dimensions ảnh hưởng output.
6. Đề xuất design sửa đúng security boundary trước khi tối ưu cache hit ratio.
7. Đề xuất cách xử lý publish invalidation/freshness mà không tạo một hệ thống cache quá phức tạp.
8. Nêu tests và production telemetry cần có để chứng minh không còn cross-user/cross-language leakage.

## Câu hỏi gợi mở

1. Output của action phụ thuộc vào những dimensions nào ngoài `ContentLink.ID`?
2. `User.IsInRole("Premium")` được evaluate khi nào: mỗi request hay chỉ khi cache miss?
3. Nếu instance A cache ViewModel từ user Premium còn instance B cache ViewModel từ user thường, load balancer sẽ tạo trải nghiệm gì?
4. Optimizely đã có object cache và invalidation riêng cho content; custom cache này có biết page vừa publish hay không?
5. Header `public,s-maxage=600` nói gì với CDN khi HTML chứa nội dung phụ thuộc user?

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — ViewModel personalized bị cache bằng key chỉ chứa page ID

**Vấn đề:** `cacheKey` chỉ là `landing:{ContentLink.ID}`, trong khi ViewModel còn phụ thuộc `User.IsInRole("Premium")`.

**Tại sao xảy ra:** `isPremium` chỉ được tính bên trong factory khi cache miss. Request đầu tiên populate cache quyết định `PromoTitle`, `PromoBody` và `IsPremium` cho mọi request sau dùng cùng key trên instance đó.

**Ảnh hưởng production:** Nếu user Premium populate cache trước, user thường có thể nhận nội dung Premium. Đây là lỗi security/correctness, không chỉ là cache stale.

**Cách sửa:** Không cache personalized ViewModel bằng shared key. Phương án an toàn nhất là chỉ cache phần content thực sự public/identity-independent, rồi quyết định personalization theo request. Nếu buộc phải cache theo segment, segment phải là một dimension được kiểm soát trong key và phải chứng minh không có dimension authorization nào bị bỏ sót. Với dữ liệu nhạy cảm, ưu tiên không shared-cache response personalized.

### Critical — `Cache-Control: public,s-maxage=600` cho response phụ thuộc user có thể làm CDN leak nội dung

**Vấn đề:** Controller tuyên bố toàn bộ HTML là public-cacheable trong 10 phút.

**Tại sao xảy ra:** Akamai/CDN có thể reuse response theo cache key ở edge. Nếu response body phụ thuộc role/user nhưng cache policy không phân biệt context tương ứng, edge có thể phát lại HTML của request trước cho request khác.

**Ảnh hưởng production:** Cross-user content disclosure có blast radius lớn hơn application `IMemoryCache` vì edge có thể phục vụ cùng response cho lượng lớn traffic.

**Cách sửa:** Không public-cache HTML có personalized/sensitive content. Có thể tách trang thành public shell được CDN cache và personalized fragment được fetch riêng với private/no-store semantics, hoặc chỉ cache public variant khi chắc chắn output độc lập user. Nếu sử dụng cache variation ở CDN, phải thiết kế bounded dimensions rõ ràng và kiểm chứng cấu hình thực tế; không mặc định `Vary: Cookie` là một giải pháp tốt vì có thể phá hit ratio và vẫn khó reasoning.

### High — Cache key thiếu language/culture dimension

**Vấn đề:** `ContentLink.ID` không thể hiện ngôn ngữ hiện tại.

**Tại sao xảy ra:** Một content item có thể có nhiều language variants nhưng custom cache coi page ID là toàn bộ identity của rendered model.

**Ảnh hưởng production:** Request `vi` có thể populate cache rồi request `en` nhận title/promo tiếng Việt trên cùng instance.

**Cách sửa:** Nếu cache public content model, key tối thiểu phải phản ánh language branch/culture thực sự ảnh hưởng output. Tuy nhiên trước khi thêm dimensions, cần xác định cache này có thật sự cần thiết hay không vì Optimizely đã có object-level caching cho content.

### High — Custom `IMemoryCache` không tự được invalidated khi editor publish content mới

**Vấn đề:** ViewModel sống 30 phút độc lập với lifecycle publish của CMS.

**Tại sao xảy ra:** Custom application cache không mặc nhiên tham gia Optimizely content invalidation. Optimizely có object cache cho content và cơ chế invalidation giữa front-end servers, nhưng cache do ứng dụng tự tạo cần lifecycle riêng nếu muốn bám publish events.

**Ảnh hưởng production:** Editor publish thành công nhưng users tiếp tục thấy model cũ tới khi TTL hết. Giữa nhiều instances, mỗi instance còn có expiration timing khác nhau.

**Cách sửa:** Trước tiên đánh giá bỏ custom cache và dựa vào CMS object cache + CDN cho public response phù hợp. Nếu custom derived-data cache thực sự cần thiết, kết nối invalidation với content publish/change events hoặc dùng versioned key dựa trên content version hợp lệ. Không chỉ giảm TTL tùy ý mà không có freshness SLO.

### High — Multi-instance `IMemoryCache` tạo behavior không đồng nhất

**Vấn đề:** Mỗi process có cache riêng.

**Tại sao xảy ra:** Instance A và B có thể được populate bởi các user/locale khác nhau và expire ở thời điểm khác nhau.

**Ảnh hưởng production:** Refresh có lúc đúng, lúc sai; bug khó tái hiện local; support thấy behavior phụ thuộc load balancing.

**Cách sửa:** Không nhất thiết phải chuyển sang Redis. Vấn đề gốc là cache semantics sai. Sau khi output/key/invalidation đúng, per-instance cache có thể vẫn hợp lý cho dữ liệu non-sensitive. Chỉ dùng distributed cache nếu cần shared semantics và operational cost được biện minh.

### High — Cache chồng lên Optimizely object cache mà chưa có evidence cần thiết

**Vấn đề:** Team thêm caching ở ViewModel layer chỉ vì giả định content API “quá nhiều”.

**Tại sao xảy ra:** Tối ưu dựa trên số lần gọi API ở code thay vì đo database/cache miss/origin latency. Optimizely CMS đã cache content objects đọc từ API và quản lý invalidation cho lớp đó.

**Ảnh hưởng production:** Tăng complexity, thêm stale/security bugs nhưng chưa chắc giảm bottleneck thực tế.

**Cách sửa:** Đo query/content-load latency, CMS cache hit behavior, CPU, render cost và edge hit ratio trước. Nếu bottleneck là expensive derived computation thì cache đúng phần đó; nếu chỉ là `IContentLoader` read đã được CMS cache tốt, bỏ custom layer có thể là thiết kế tốt hơn.

### Medium — `GetChildren<PromoBlock>` lấy toàn bộ collection rồi `ToList` dù chỉ cần một candidate

**Vấn đề:** Toàn bộ children được materialize trước khi chọn promo.

**Tại sao xảy ra:** Code tối ưu cache ở mức lớn nhưng chưa xác định actual cardinality/query cost.

**Ảnh hưởng production:** Nếu folder có rất nhiều blocks, allocation và render preparation không cần thiết tăng. Tuy nhiên đây chưa chắc là bottleneck nếu CMS object cache đã warm và số block nhỏ.

**Cách sửa:** Đo cardinality và load cost. Thiết kế content model để số child items phù hợp use case hoặc query/search theo criteria nếu collection rất lớn. Không micro-optimize nếu evidence không cho thấy vấn đề.

### Medium — Authorization/personalization logic bị trộn vào caching/rendering service

**Vấn đề:** Role decision, CMS loading, cache strategy và HTTP cache header nằm chung trong controller.

**Tại sao xảy ra:** Optimization được thêm trực tiếp vào request path mà không phân tách security policy và cacheability policy.

**Ảnh hưởng production:** Khó review boundary nào bảo vệ nội dung Premium, khó test độc lập, dễ thêm dimension mới mà quên update cache key.

**Cách sửa:** Tách public content composition khỏi personalized decision. Cacheability nên được explicit: response nào public, response nào private, fragment nào personalized. Authorization phải đúng ngay cả khi tất cả cache bị tắt.

### Medium — Cache policy chưa có purge/invalidation contract với CDN

**Vấn đề:** HTML được giữ 10 phút ở edge nhưng business muốn publish xuất hiện trong vài phút.

**Tại sao xảy ra:** TTL được chọn độc lập với editorial freshness requirement.

**Ảnh hưởng production:** Ngay cả origin đã có content mới, edge vẫn có thể trả bản cũ tới khi TTL hết nếu không purge/revalidate.

**Cách sửa:** Xác định freshness SLO. Có thể chọn TTL ngắn phù hợp, purge/invalidate URL khi publish, hoặc versioned URLs/keys tùy loại content. Không build purge phức tạp nếu TTL nhỏ đã đáp ứng business.

### Low — Thiếu telemetry để phân biệt origin cache và edge cache

**Vấn đề:** Không có dấu hiệu trong response/log cho biết model đến từ cache layer nào, content version/language nào.

**Tại sao xảy ra:** Cache được coi là optimization nội bộ không cần quan sát.

**Ảnh hưởng production:** Incident khó khoanh vùng: CDN hit, app cache hit hay CMS content stale.

**Cách sửa:** Ghi structured fields như page ID, language, personalization variant, app-cache hit/miss, content version marker, instance ID và CDN cache status từ response headers/log pipeline phù hợp. Không log user-sensitive content.

## Phiên bản đề xuất

Một hướng đơn giản hơn là **không cache personalized ViewModel** và chỉ cho CDN cache response khi chắc chắn page hoàn toàn public.

```csharp
public sealed class LandingPageController : PageController<LandingPage>
{
    private readonly IContentLoader _contentLoader;

    public LandingPageController(IContentLoader contentLoader)
        => _contentLoader = contentLoader;

    public IActionResult Index(LandingPage currentPage)
    {
        var promoBlocks = _contentLoader
            .GetChildren<PromoBlock>(currentPage.PromoFolder)
            .ToList();

        var isPremium = User.Identity?.IsAuthenticated == true
            && User.IsInRole("Premium");

        var selectedPromo = isPremium
            ? promoBlocks.FirstOrDefault(x => x.PremiumOnly)
            : promoBlocks.FirstOrDefault(x => !x.PremiumOnly);

        var model = new LandingPageViewModel
        {
            Title = currentPage.Name,
            HeroText = currentPage.HeroText,
            PromoTitle = selectedPromo?.Title,
            PromoBody = selectedPromo?.Body,
            IsPremium = isPremium
        };

        if (isPremium)
        {
            Response.Headers.CacheControl =
                "private,no-store";
        }
        else
        {
            Response.Headers.CacheControl =
                "public,max-age=60,s-maxage=120";
        }

        return View(model);
    }
}
```

Đoạn trên vẫn chỉ là một bước cải thiện minh họa. Nếu anonymous/public response và authenticated non-Premium response khác nhau ở bất kỳ field nào khác, không được gom chúng vào cùng public variant. Một design rõ hơn là:

- public page shell chứa nội dung không phụ thuộc identity và có thể CDN-cache;
- personalized promo được render/fetch qua một endpoint riêng với authorization và private cache policy;
- editor publish trigger purge/revalidation cho public URLs nếu freshness SLO yêu cầu;
- application không cache lại `IContentLoader` output chỉ để “giảm CMS calls” khi chưa có evidence;
- nếu có expensive derived model thật sự, cache theo explicit dimensions như `content identity + language + public variant + content version`, và nối invalidation vào content lifecycle.

Optimizely CMS có object cache cho content instances và cơ chế invalidation hỗ trợ nhiều front-end servers; vì vậy custom cache layer cần được biện minh bằng bottleneck cụ thể thay vì giả định mọi `IContentLoader` call đều xuống database.

## Giải thích thiết kế sau khi sửa

Security boundary phải đúng ngay cả khi cache bị warm bởi request “xấu nhất”. Nguyên tắc là shared cache chỉ được dùng khi hai request có cùng cache key thực sự được phép nhận cùng representation.

Với personalized content, cách reasoning dễ nhất là không public-cache nguyên HTML. Tách public shell và private fragment giúp cacheability contract rõ hơn, nhưng đổi lại tăng một request hoặc tăng complexity ở rendering flow.

Language cũng là representation dimension. Nếu output tiếng Việt và tiếng Anh khác nhau thì cache identity phải phản ánh điều đó ở mọi layer liên quan: application và CDN.

Publish invalidation nên theo business freshness SLO. Nếu “trong 2 phút” là đủ, TTL ngắn có thể đơn giản hơn integration purge. Nếu yêu cầu gần tức thời ở traffic lớn, purge/invalidation event có thể đáng giá.

## Trade-offs

Bỏ application ViewModel cache có thể tăng CPU/render work ở origin. Tuy nhiên nếu bottleneck không nằm ở đó, đây là trade-off tốt để giảm correctness risk.

Tách personalized fragment có thể làm UI phức tạp hơn và tăng network round trip. Đổi lại public shell có cache hit ratio cao mà không leak user-specific content.

Cache theo segment có thể tăng hit ratio nếu số segment nhỏ, ổn định và không phải security role phức tạp. Nhưng mỗi dimension làm key cardinality và invalidation khó hơn.

TTL ngắn giảm stale window nhưng tăng origin traffic. Purge nhanh hơn nhưng tạo coupling giữa CMS publish pipeline và CDN operations. Chọn dựa trên traffic, editorial SLO và failure behavior khi purge thất bại.

## Cách kiểm thử

1. **Security integration test:** Premium request populate mọi cache layer có thể kiểm soát, sau đó gửi request non-Premium cùng URL; xác minh không bao giờ thấy Premium promo.
2. **Language test:** gọi cùng page bằng `vi` và `en` theo nhiều thứ tự khác nhau; xác minh output không bị cross-language contamination.
3. **Multi-instance test:** route requests xen kẽ qua hai instances với cache cold/warm khác nhau; output phải ổn định theo request context.
4. **Publish freshness test:** publish version mới, đo thời gian tới khi origin và edge phục vụ content mới; xác minh đạt SLO.
5. **CDN validation:** kiểm tra response headers/cache-status cho anonymous và authenticated/personalized paths; personalized response không được public-cache ngoài policy.

## Quan sát trong production

Theo dõi:

- origin request count và Akamai cache hit/miss ratio;
- application instance ID;
- page/content ID và language;
- public/personalized variant marker không chứa PII;
- app-cache hit/miss nếu còn custom cache;
- content version/publish timestamp hiện đang render;
- CDN age/cache-status headers;
- p95/p99 origin render latency;
- publish-to-visible latency;
- số incident mismatch giữa expected segment/language và rendered variant.

Dashboard nên giúp trả lời nhanh: “response này đến từ edge hay origin?”, “origin dùng content version nào?”, “instance nào phục vụ?”, “variant nào đã được chọn?”.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business muốn một phần trang personalized nhưng vẫn muốn 95% HTML được CDN-cache, bạn chia boundary rendering/cache như thế nào?
2. Nếu Optimizely object cache đã tốt nhưng p95 vẫn cao, bạn sẽ đo gì tiếp theo trước khi thêm Redis?
3. Nếu Akamai purge API thỉnh thoảng fail, bạn thiết kế fallback/freshness guarantee như thế nào?

# Code Review Challenge 2 — Octopus deploy lên IIS “thành công” nhưng release làm downtime, rollback không an toàn và schema lệch giữa các node

**Chủ đề:** IIS, Windows Server, Octopus Deploy, TeamCity artifact, CI/CD, immutable artifact, rolling deployment, EF Core migration strategy, configuration/secrets, rollback, health validation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một enterprise management portal vẫn chạy ASP.NET Core trên Windows Server + IIS. Production có 3 web nodes sau load balancer. TeamCity build artifact, Octopus Deploy đẩy release tới từng server.

Hiện process release được viết thành một PowerShell step và Octopus chạy step này trên cả 3 targets gần như đồng thời. Database là SQL Server dùng chung.

Sau vài release gần đây, team gặp:

- 2–5 phút downtime dù có 3 nodes;
- đôi lúc node A chạy code mới còn node B/C vẫn code cũ nhưng database đã đổi schema;
- rollback package cũ nhưng application vẫn lỗi vì migration đã chạy;
- một release “success” trên Octopus nhưng health check user-facing vẫn 500;
- support khó xác định chính xác artifact/version nào đang chạy trên từng node;
- connection string từng xuất hiện trong task log khi script fail.

Script hiện tại:

## Đoạn code cần review

```powershell
$siteName = "EmployeePortal"
$appPool = "EmployeePortalPool"
$deployPath = "C:\inetpub\EmployeePortal"
$artifact = "C:\packages\EmployeePortal-latest.zip"
$backup = "C:\backup\EmployeePortal"

Write-Host "Deploying $artifact"
Write-Host "Connection: $env:ConnectionStrings__MainDb"

Stop-WebAppPool -Name $appPool

if (Test-Path $backup) {
    Remove-Item $backup -Recurse -Force
}

Copy-Item $deployPath $backup -Recurse -Force
Remove-Item "$deployPath\*" -Recurse -Force
Expand-Archive $artifact -DestinationPath $deployPath -Force

Set-Location $deployPath

dotnet ef database update `
    --connection "$env:ConnectionStrings__MainDb"

Start-WebAppPool -Name $appPool

Start-Sleep -Seconds 5

$response = Invoke-WebRequest `
    -Uri "https://employee.company.com/health" `
    -UseBasicParsing

if ($response.StatusCode -ne 200) {
    throw "Health check failed"
}

Write-Host "Deployment completed"
```

Octopus project hiện có một step duy nhất chạy script trên toàn bộ web targets. TeamCity publish file theo tên cố định `EmployeePortal-latest.zip` lên package share.

## Kết quả code review tham khảo

### Critical — Connection string bị ghi plaintext vào deployment log

**Vấn đề:** Script `Write-Host` toàn bộ `ConnectionStrings__MainDb`.

**Tại sao xảy ra:** Secret được debug như config thông thường.

**Ảnh hưởng production:** Credential có thể bị lưu trong Octopus task logs và được đọc bởi người có quyền xem deployment logs. Rotation/audit trở nên khó khăn.

**Cách sửa:** Không log secret. Dùng sensitive variables/secret management của deployment platform và least privilege. Khi cần troubleshoot, log tên environment/target hoặc secret source, không log giá trị.

### Critical — Mọi web node cùng chạy database migration

**Vấn đề:** `dotnet ef database update` nằm trong per-target web deployment step.

**Tại sao xảy ra:** Migration ownership bị gắn vào từng node thay vì release workflow.

**Ảnh hưởng production:** Nhiều nodes có thể tranh chấp migration, chờ lock hoặc fail không đồng nhất. Quan trọng hơn, schema có thể thay đổi khi các node cũ vẫn đang serve traffic.

**Cách sửa:** Tách migration thành một release step có owner duy nhất và explicit ordering. Migration phải được review như production change riêng. Với rolling rollout, dùng backward-compatible expand/contract khi schema change không thể đồng thời tương thích old/new code.

### High — Deploy đồng thời trên cả 3 targets làm mất redundancy

**Vấn đề:** Octopus chạy cùng script gần như đồng thời, và mỗi target stop App Pool ngay đầu step.

**Tại sao xảy ra:** Multi-node topology tồn tại nhưng deployment strategy không dùng nó để giữ availability.

**Ảnh hưởng production:** Toàn bộ pool có thể offline cùng lúc, gây downtime dù có 3 servers.

**Cách sửa:** Dùng rolling/serial deployment hoặc batch nhỏ. Drain một node khỏi load balancer, deploy, validate trực tiếp node đó, đưa lại vào traffic rồi mới tiếp tục node kế tiếp. Batch size tùy capacity headroom và SLO.

### High — Health check qua public hostname không xác minh node vừa deploy

**Vấn đề:** `https://employee.company.com/health` có thể được load balancer route sang bất kỳ healthy node nào.

**Tại sao xảy ra:** Validation target không gắn với deployment target.

**Ảnh hưởng production:** Node vừa deploy có thể trả 500 nhưng script vẫn thấy 200 từ node khác và đánh dấu success.

**Cách sửa:** Có node-local readiness check hoặc cơ chế LB-aware validation nhắm đúng target. Sau khi node-local pass, mới re-enable traffic và thực hiện smoke test qua public endpoint.

### High — Artifact tên `latest` không immutable và làm mất traceability

**Vấn đề:** TeamCity publish file cố định `EmployeePortal-latest.zip`.

**Tại sao xảy ra:** Build artifact identity không gắn với commit/build/release version.

**Ảnh hưởng production:** Không biết chính xác package nào đã deploy; file có thể bị overwrite; rollback/audit kém tin cậy.

**Cách sửa:** Publish immutable versioned package, ví dụ `EmployeePortal.2026.09.13.812.nupkg/zip` hoặc semantic/build version gắn commit SHA. Octopus release tham chiếu đúng package version, không copy “latest”.

### High — Rollback binary không đồng nghĩa rollback schema

**Vấn đề:** Script backup folder app nhưng migration có thể đã thay database irreversibly.

**Tại sao xảy ra:** Team coi release như file-copy transaction, trong khi database là shared persistent state.

**Ảnh hưởng production:** Restore package cũ có thể fail nếu column/table/contracts đã đổi. Downtime kéo dài vì rollback path giả định không còn hợp lệ.

**Cách sửa:** Thiết kế migration theo expand/contract khi cần zero/low downtime. Rollback plan phải nói rõ schema compatibility. Với destructive migration, thường tách thành release sau khi old code không còn phụ thuộc field cũ và có backup/restore strategy phù hợp.

### High — File replacement trực tiếp trong live deploy path không atomic

**Vấn đề:** Script xóa toàn bộ files rồi expand package vào cùng directory.

**Tại sao xảy ra:** Deployment directory vừa là staging area vừa là runtime directory.

**Ảnh hưởng production:** Nếu extract fail giữa chừng, node nằm ở trạng thái partial deployment. Restore backup lại là một step thủ công/chưa tự động hóa.

**Cách sửa:** Extract vào versioned/staging directory, validate package/config, rồi switch deployment target theo mechanism phù hợp với IIS/process layout. Ít nhất phải có transactional-ish rollback procedure đã test thay vì `Remove-Item` destructive trước khi biết package tốt.

### High — Script dừng App Pool trước khi package/migration preconditions được kiểm chứng

**Vấn đề:** Service bị stop ngay đầu flow trước khi verify artifact tồn tại, unzip được, secret/config hợp lệ hoặc migration plan an toàn.

**Tại sao xảy ra:** Downtime window bắt đầu quá sớm.

**Ảnh hưởng production:** Một lỗi artifact đơn giản cũng làm node offline lâu không cần thiết.

**Cách sửa:** Preflight trước: checksum/version, disk space, config presence, package extraction vào staging, migration prerequisite. Chỉ drain/stop node ở thời điểm cần switch runtime.

### Medium — `dotnet ef` trên production server tạo dependency không cần thiết vào SDK/tooling

**Vấn đề:** Production web node phải có EF tooling/project metadata phù hợp để chạy migration command.

**Tại sao xảy ra:** Build-time/deployment-time concerns bị đẩy vào runtime server.

**Ảnh hưởng production:** Environment drift, tool version mismatch, deployment failure khó đoán.

**Cách sửa:** Migration artifact/job nên được build/versioned cùng release và chạy từ controlled deployment context. Web node chỉ cần runtime dependencies để serve application.

### Medium — Backup bị overwrite mỗi lần deploy và chưa chứng minh restore procedure

**Vấn đề:** Chỉ giữ một folder backup, xóa backup cũ trước deploy.

**Tại sao xảy ra:** Backup được coi là “copy trước khi sửa” chứ không phải versioned rollback artifact.

**Ảnh hưởng production:** Nếu release liên tiếp hoặc backup đã hỏng, không có provenance/version rõ ràng để rollback.

**Cách sửa:** Dùng immutable release packages làm nguồn rollback chính. Nếu giữ local backup, gắn version/timestamp và retention policy. Quan trọng hơn là test rollback path thật.

### Medium — Không có traffic drain/graceful shutdown semantics

**Vấn đề:** Stop App Pool có thể cắt request đang xử lý tùy lifecycle hiện tại.

**Tại sao xảy ra:** Deployment flow chỉ nghĩ “node on/off”, không nghĩ in-flight work.

**Ảnh hưởng production:** User request fail giữa chừng, duplicate submission hoặc partial side effects nếu client retry.

**Cách sửa:** Drain node khỏi load balancer trước, chờ bounded period cho in-flight requests hoàn tất, rồi stop/recycle process. Với background jobs trên web node, phải có strategy ownership/cancellation riêng.

### Medium — Health check chỉ kiểm tra một HTTP 200 sau fixed sleep

**Vấn đề:** `Start-Sleep 5` + một request không phản ánh startup time, dependency readiness hoặc smoke-test behavior.

**Tại sao xảy ra:** Validation dựa trên timing assumption.

**Ảnh hưởng production:** App khởi động 20 giây thì false failure; hoặc `/health` trả 200 nhưng route quan trọng vẫn lỗi config/database.

**Cách sửa:** Poll readiness với bounded timeout, rồi chạy smoke test nhỏ có correlation ID. Health endpoint phải lightweight nhưng có semantics rõ ràng; deployment validation có thể thêm dependency/config checks phù hợp.

## Phiên bản đề xuất

Thay vì một per-node script chứa toàn bộ release workflow, tách thành các phase rõ ràng:

```text
1. Build (TeamCity)
   - compile + tests
   - tạo immutable package có version + commit SHA
   - tạo migration artifact cùng version

2. Pre-deploy validation
   - xác minh package checksum/version
   - xác minh required variables/secrets tồn tại
   - kiểm tra migration compatibility/backup policy

3. Database migration step — chạy một lần
   - chạy expand/backward-compatible migration nếu cần
   - verify schema version
   - fail release nếu migration không thành công

4. Rolling IIS deployment — từng node một
   a. disable/drain node khỏi load balancer
   b. chờ in-flight requests trong bounded timeout
   c. stage + validate package
   d. switch/deploy version
   e. start/recycle App Pool
   f. poll node-local readiness
   g. smoke test node
   h. enable node vào load balancer
   i. quan sát error rate ngắn trước node kế tiếp

5. Post-deploy validation
   - smoke test public endpoint
   - compare deployed versions trên cả nodes
   - monitor error rate/latency

6. Contract/destructive migration — release sau
   - chỉ chạy khi tất cả old code đã được loại bỏ
```

Một PowerShell deploy step ở mức node có thể chỉ chịu trách nhiệm stage/switch/validate node, ví dụ:

```powershell
param(
    [string]$PackagePath,
    [string]$ReleaseVersion,
    [string]$DeployRoot = "C:\inetpub\EmployeePortal"
)

$staging = Join-Path $DeployRoot "releases\$ReleaseVersion"
$health = "http://localhost:8080/health/ready"

if (-not (Test-Path $PackagePath)) {
    throw "Package not found: $PackagePath"
}

New-Item -ItemType Directory -Path $staging -Force | Out-Null
Expand-Archive $PackagePath -DestinationPath $staging -Force

# Config/secrets được inject bằng cơ chế deployment phù hợp.
# Không log secret values.

# Sau bước traffic drain bên ngoài script:
Stop-WebAppPool -Name "EmployeePortalPool"

# Switch/copy deployment theo versioned staging đã validate.
# Chi tiết mechanism tùy layout IIS hiện tại.

Start-WebAppPool -Name "EmployeePortalPool"

$deadline = (Get-Date).AddSeconds(60)
$ready = $false

while ((Get-Date) -lt $deadline) {
    try {
        $response = Invoke-WebRequest -Uri $health -UseBasicParsing -TimeoutSec 3
        if ($response.StatusCode -eq 200) {
            $ready = $true
            break
        }
    }
    catch {
        Start-Sleep -Seconds 2
    }
}

if (-not $ready) {
    throw "Node did not become ready for release $ReleaseVersion"
}
```

Script minh họa không tự chạy migration. Octopus release orchestration chịu trách nhiệm migration-once và rolling deployment. Cách disable/enable node ở load balancer phụ thuộc infrastructure hiện tại; đó phải là explicit step, không giả định stop App Pool là đủ.

## Giải thích thiết kế sau khi sửa

CI tạo immutable artifact; CD chỉ promote đúng artifact đó. Điều này tách “build what?” khỏi “deploy where?” và cho phép audit/rollback chính xác.

Database là shared state nên migration cần ownership riêng. Với rolling deploy, old/new code có thể chạy đồng thời một khoảng thời gian. Vì vậy schema change phải tương thích cả hai version hoặc rollout phải có maintenance window explicit.

Rolling deployment tận dụng redundancy của 3 IIS nodes. Mỗi node chỉ được đưa lại vào traffic sau khi node-local readiness pass. Public smoke test sau cùng xác nhận end-to-end route qua load balancer.

Rollback phải được thiết kế trước release. Nếu chỉ đổi binary và schema backward-compatible, rollback package cũ khả thi. Nếu đã destructive migration thì rollback có thể yêu cầu restore/forward-fix; không được giả định copy backup folder là đủ.

## Trade-offs

Rolling deploy lâu hơn parallel deploy. Đổi lại availability và blast radius tốt hơn. Nếu traffic thấp và có maintenance window, deploy đồng thời có thể vẫn là lựa chọn hợp lý nhưng phải explicit.

Expand/contract migration làm schema tồn tại tạm thời với cả field cũ và mới, tăng complexity và thời gian cleanup. Nhưng nó giảm coupling giữa deployment của code và schema.

Node-local health endpoint giúp validate đúng target nhưng cần network/security design để deployment agent truy cập được mà không public expose endpoint nội bộ.

Immutable packages tốn storage hơn `latest.zip`, nhưng chi phí này thường nhỏ so với lợi ích traceability và rollback.

## Cách kiểm thử

1. **Pipeline validation:** mỗi TeamCity build tạo versioned artifact bất biến; Octopus release phải pin đúng package version và commit SHA.
2. **Rolling deployment test:** dưới representative load, deploy qua 3 IIS nodes; xác minh luôn còn đủ healthy capacity và không có spike 5xx bất thường.
3. **Migration compatibility test:** chạy old app trên expanded schema, rồi new app trên cùng schema; xác minh cả hai hoạt động trong rollout window.
4. **Rollback test:** sau khi deploy code mới nhưng trước destructive contract migration, rollback về package cũ và verify end-to-end behavior.
5. **Secret/logging test:** inject fake secret chứa marker đặc biệt; scan task logs/artifacts để đảm bảo value không bị lộ.

## Quan sát trong production

Theo dõi:

- release ID, package version, commit SHA theo từng IIS node;
- App Pool start/recycle failures;
- node readiness state và thời gian startup;
- load balancer healthy backend count;
- request p50/p95/p99 và 5xx trong rollout;
- active requests khi node drain;
- database migration version/duration/failure;
- SQL blocking/lock waits trong migration;
- public smoke-test outcome;
- config/secret resolution errors nhưng không log secret value;
- rollback event và version transition.

Alert nên phân biệt deployment failure trên một node với systemic incident trên cả cluster.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Shared cache chỉ an toàn khi mọi request có cùng cache key thực sự được phép nhận cùng representation.
- Personalized content và public CDN caching phải được thiết kế cùng security boundary; cache hit ratio không được ưu tiên hơn authorization/correctness.
- Optimizely đã có object cache và invalidation cho content; custom cache layer phải được biện minh bằng evidence và có key/invalidation semantics riêng rõ ràng.
- Multi-instance `IMemoryCache` có thể làm bug nondeterministic nhưng distributed cache không tự sửa được cache key sai.
- IIS multi-node chỉ cung cấp high availability nếu deployment strategy thật sự rolling/draining; stop tất cả App Pools cùng lúc làm mất redundancy.
- Database migration là shared-state change, cần ownership và backward-compatibility plan riêng; rollback binary không đồng nghĩa rollback schema.
- Immutable artifact + node-specific health validation là nền tảng cho traceable và safe deployment.

## Mẫu tư duy cần nhớ

- Xác định đầy đủ output dimensions trước khi thiết kế cache key.
- Security boundary phải đúng ngay cả khi cache bị populate bởi request bất lợi nhất.
- Measure before adding another cache layer.
- Tách build artifact, schema migration và node rollout thành các concerns riêng.
- Thiết kế rollback trước khi chạy migration/destructive change.
