# Câu 1 — EF Core optimistic concurrency: vì sao đọc đúng dữ liệu vẫn có thể ghi đè thay đổi của người khác?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** EF Core, change tracking, optimistic concurrency, SQL, HTTP API semantics

## Bối cảnh

Một ASP.NET Core approval API dùng EF Core và SQL Server. Hai quản lý mở cùng một approval request gần như đồng thời. Người A đổi `Status` sang `Approved`; người B sửa `Comment` rồi lưu sau đó. Team nhận thấy đôi lúc thay đổi trước bị ghi đè hoặc request sau thành công dù UI đang hiển thị dữ liệu cũ.

Entity hiện được load bằng tracking query, DTO từ client chứa toàn bộ fields và controller map toàn bộ DTO trở lại entity trước `SaveChangesAsync`. Team cho rằng “EF Core tracking sẽ tự phát hiện người khác đã sửa row nên không cần làm gì thêm”.

## Câu hỏi chính

Bạn hãy giải thích internal mechanism của EF Core change tracking và optimistic concurrency trong scenario này: vì sao tracking tự nó không ngăn lost update, concurrency token thay đổi SQL update như thế nào, production behavior khi conflict xảy ra, và API nên xử lý conflict ra sao?

## Câu hỏi làm rõ nên cân nhắc

1. Business muốn merge các field độc lập hay bất kỳ concurrent modification nào cũng phải conflict?
2. Entity hiện có `rowversion`/concurrency token hay không?
3. Client có gửi version đã đọc cùng request update không?
4. API đang dùng PUT-like full replacement hay PATCH-like partial update?
5. Khi conflict, UX mong muốn reload, merge hay yêu cầu người dùng xác nhận lại?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt “EF biết entity nào đã thay đổi trong một `DbContext`” với “EF biết database đã bị transaction khác thay đổi”.

### Gợi ý 2

Hãy xem `UPDATE ... WHERE ...` cần điều kiện gì để phát hiện row không còn ở version ban đầu.

### Gợi ý 3

Concurrency token biến conflict thành một observable outcome; nó không tự quyết định business merge policy.

## Cấu trúc trả lời đề xuất

1. Làm rõ conflict semantics.
2. Giải thích tracking/original/current values.
3. Giải thích SQL update khi không có concurrency token.
4. Giải thích concurrency token và affected-row check.
5. Xử lý `DbUpdateConcurrencyException` theo business policy.
6. Thiết kế HTTP response/client retry hoặc merge.
7. Test concurrent writes và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Change tracking chủ yếu theo dõi state trong `DbContext`; không tự tạo cross-request locking.
- Không có concurrency predicate phù hợp, update sau có thể ghi đè giá trị dựa trên stale state.
- Concurrency token làm original token tham gia điều kiện update; nếu không row nào match, EF Core có thể báo concurrency conflict.
- Không blindly retry toàn bộ update vì có thể tái áp dụng stale intent.
- API cần explicit conflict semantics.

### Điểm cộng

- Phân biệt full DTO overwrite với field-specific update.
- Đề cập HTTP `409 Conflict` hoặc semantics phù hợp của API contract thay vì trả 500 chung chung.
- Giải thích reload database values và merge có điều kiện.

### Senior+

- Nhận ra concurrency granularity là business decision: row-level token có thể conflict cả khi hai người sửa hai field độc lập.
- Đề xuất audit/correlation để điều tra conflict rate.
- Phân biệt optimistic concurrency với transaction isolation/locking.

## Hướng giải quyết tham khảo

EF Core tracking không phải distributed lock. Một `DbContext` giữ original/current values và entity state cho unit of work của nó. Request A và B thường dùng hai contexts khác nhau; cả hai có thể load cùng version của row. Nếu update SQL chỉ dựa trên primary key, write sau vẫn có thể match row và overwrite dữ liệu dù row đã thay đổi kể từ lúc nó được đọc.

Với một concurrency token, ví dụ SQL Server `rowversion` được cấu hình phù hợp, EF Core giữ original token và đưa nó vào concurrency predicate của `UPDATE`. Conceptually update sẽ yêu cầu cả key và version ban đầu match. Nếu transaction khác đã cập nhật row, version thay đổi; update không match row và EF Core có thể phát sinh `DbUpdateConcurrencyException`.

Điều đó chỉ phát hiện conflict. Business vẫn phải quyết định: reject và yêu cầu reload, merge các field độc lập, hay cho user override có chủ ý. Blind retry bằng cách reload rồi map lại toàn bộ stale DTO có thể biến conflict detection thành lost update lần nữa.

Nếu API dùng full DTO và map mọi field, nguy cơ overwrite càng lớn. Nếu business cho phép field-level independent edits, PATCH/command-specific contract hoặc merge policy có thể phù hợp hơn. Nếu mọi thay đổi cần review lại khi version đổi, row-level token là đơn giản và rõ ràng.

Testing nên chạy hai contexts thật trên database integration test: cùng đọc một version, A commit, B commit và xác minh conflict. Cũng test UX/API response và merge policy. Production telemetry nên đo conflict count theo operation/entity type, không log sensitive values.

## Mẫu trả lời trong phỏng vấn

“EF tracking chỉ biết state mà `DbContext` của request hiện tại đã load và thay đổi; nó không tự biết một request khác đã commit sau đó. Nếu SQL update chỉ có `WHERE Id = ...`, request B vẫn có thể update row dù dữ liệu B đọc đã stale.

Tôi sẽ dùng concurrency token nếu business cần phát hiện lost update. EF giữ original token và dùng nó trong update predicate. Nếu A đã sửa row thì token đổi, B update zero rows và EF báo concurrency exception. Sau đó API phải có policy rõ: thường tôi trả conflict và cung cấp cách reload/reconcile; tôi không blindly retry stale DTO.

Tôi cũng xem contract. Nếu DTO chứa toàn entity và map lại mọi field, một edit nhỏ có thể overwrite field không liên quan. Nếu requirement cho phép merge field độc lập, tôi thiết kế command/patch semantics phù hợp. Cuối cùng tôi test bằng hai DbContexts thật và monitor conflict rate để biết đây là expected contention hay UX/problematic workflow.”

## Câu hỏi đào sâu

1. Nếu A sửa `Status`, B chỉ sửa `Comment`, bạn có muốn row-level conflict không?
2. Tại sao tăng transaction isolation không nhất thiết là replacement trực tiếp cho optimistic concurrency token?
3. Nếu client tự động retry sau `DbUpdateConcurrencyException`, điều gì có thể sai?

## Lỗi trả lời thường gặp

- Nghĩ tracking tự khóa row giữa các requests.
- Bắt concurrency exception rồi retry vô điều kiện.
- Không làm rõ business merge semantics.
- Trả 500 cho expected concurrency conflict.

## Thang điểm 0–10

- **0–2:** Nhầm tracking với concurrency protection.
- **3–4:** Biết concurrency token nhưng chưa giải thích mechanism.
- **5–6:** Giải thích đúng predicate/affected rows và conflict handling.
- **7–8:** Có API semantics, merge policy, testing và telemetry.
- **9–10:** Phân tích tốt granularity, transaction semantics và business trade-offs.

# Câu 2 — Azure Function xử lý file backlog tăng nhanh: retry, poison work hay downstream saturation?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Functions, Blob Storage, retry/failure handling, SQL, observability, production incident reasoning

## Bối cảnh

Một file-processing pipeline nhận metadata về tài liệu mới và kích hoạt Azure Function để đọc file từ Azure Blob Storage, parse metadata rồi ghi kết quả vào SQL Server. Bình thường mỗi file hoàn thành trong vài giây.

Sau một batch import lớn, backlog tăng liên tục trong 40 phút. Một số file xuất hiện nhiều processing attempts; SQL latency tăng; Function executions có cả success, timeout và transient exceptions. Blob Storage không có outage được xác nhận. Team đề xuất tăng concurrency và retry count để “xử lý backlog nhanh hơn”.

Business cần ưu tiên không làm mất file; duplicate processing có thể chấp nhận nếu không tạo duplicate business records. Một số file có thể malformed.

## Câu hỏi chính

Bạn sẽ stabilize và điều tra incident theo thứ tự nào để phân biệt insufficient capacity, downstream saturation, retry amplification và poison work; và bạn sẽ thay đổi pipeline thế nào để backlog recover an toàn mà không biến retry/concurrency thành load amplifier?

## Câu hỏi làm rõ nên cân nhắc

1. Trigger/source semantics và retry/dead-letter/poison behavior hiện tại cụ thể là gì?
2. Backlog age, arrival rate và completion rate thay đổi thế nào?
3. SQL dependency p95/p99, connection waits và error rate ra sao?
4. Những file retry nhiều có chung size/schema/source không?
5. Processing có idempotency key hoặc unique business constraint không?

## Gợi ý tư duy

### Gợi ý 1

Backlog chỉ là symptom. So sánh arrival rate, service rate và dependency saturation.

### Gợi ý 2

Retry có thể tăng offered load đúng lúc dependency yếu nhất.

### Gợi ý 3

Tách transient failure khỏi permanent malformed input; hai loại không nên có cùng retry policy.

## Cấu trúc trả lời đề xuất

1. Định lượng impact/backlog age.
2. Stabilize downstream trước khi tăng concurrency.
3. Phân rã success/failure/retry theo loại.
4. Correlate Function và SQL telemetry.
5. Identify poison/large-file cohorts.
6. Xác minh idempotency/data constraints.
7. Tune concurrency/retry có giới hạn.
8. Isolate permanent failures.
9. Drain backlog có kiểm soát.
10. Load/failure tests và alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tăng concurrency/retry trước khi biết bottleneck.
- Đo queue/backlog age, throughput, retry rate và dependency latency.
- Phân biệt transient với permanent malformed work.
- Idempotency/unique constraints để duplicate processing không tạo duplicate records.
- Có poison isolation/manual reconciliation path.
- Verify recovery sau mitigation.

### Điểm cộng

- Xem file size distribution, parse CPU/memory và SQL connection pool.
- Bounded concurrency theo downstream capacity.
- Exponential backoff/jitter hoặc platform-appropriate retry policy sau khi xác minh semantics hiện hành.

### Senior+

- Nêu retry budget và load amplification.
- Thiết kế admission/backpressure thay vì scale consumer vô hạn.
- Có replay tooling cho failed files và audit trail.

## Hướng giải quyết tham khảo

Đầu tiên đo backlog age/count, arrival rate và completion rate. Nếu completion thấp hơn arrival lâu dài, phải tìm resource/service bottleneck. Trong lúc incident, nếu SQL latency và errors tăng theo Function concurrency, tăng concurrency có thể làm tình hình tệ hơn. Có thể tạm giảm/bound concurrency hoặc throttle import để SQL phục hồi, tùy business impact.

Phân loại attempts theo outcome: transient SQL/network timeout, deterministic parse failure, cancellation/timeout, success. Những file luôn fail cùng một parser error là poison candidates; retry chúng nhiều lần chỉ tiêu tốn capacity. Chúng nên được isolate theo cơ chế phù hợp của trigger/pipeline và có metadata/reason để replay sau khi sửa.

Với transient failures, retry cần bounded backoff và phải xét idempotency. Nếu Function đã ghi một phần dữ liệu rồi timeout, lần chạy sau không được tạo duplicate business records. Unique constraint/business operation key và transaction boundary rõ ràng quan trọng hơn việc kỳ vọng trigger chỉ chạy một lần.

Nếu SQL là bottleneck, kiểm tra dependency duration, active connections/pool waits, blocking, query plans và write pattern. Nếu parser là bottleneck, kiểm tra file sizes, CPU/memory và duration distribution. Nếu Blob read latency tăng, dependency telemetry sẽ cho evidence thay vì suy đoán outage.

Sau khi isolate poison work và ổn định dependency, drain backlog với concurrency tăng dần, theo dõi SQL p95/p99, error rate, Function duration và backlog slope. Long-term cần load test theo batch size thực tế, failure injection, dashboards cho backlog age/retry ratio và alert khi retry amplification xuất hiện.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tăng retry và concurrency ngay. Tôi đo arrival rate, completion rate, backlog age và phân loại failures. Nếu SQL p95 tăng cùng concurrency thì consumer đang có thể overload downstream; lúc đó tôi throttle import hoặc giảm/bound concurrency để stabilize trước.

Tiếp theo tôi tách transient failures khỏi deterministic malformed files. Poison work không nên retry vô hạn; tôi isolate nó để pipeline còn capacity cho work tốt và có replay/reconciliation sau. Với transient retry, tôi dùng bounded backoff và kiểm tra idempotency vì một attempt timeout không có nghĩa side effect chưa xảy ra.

Tôi correlate Function traces với Blob và SQL dependencies, kiểm tra SQL waits/pool/query behavior, đồng thời xem file-size/error cohorts. Khi root bottleneck được xử lý, tôi drain backlog tăng dần và verify backlog slope, p95/p99 và error rate. Sau incident tôi thêm load/failure tests, retry budget và alert trên backlog age/retry ratio.”

## Câu hỏi đào sâu

1. Nếu 1% malformed files chiếm 40% total executions vì retry, bạn thay đổi pipeline thế nào?
2. Nếu SQL khỏe nhưng Function duration tăng theo file size, hypotheses của bạn thay đổi ra sao?
3. Business yêu cầu xử lý nhanh hơn; tại sao không đơn giản tăng Function concurrency gấp 10 lần?

## Lỗi trả lời thường gặp

- Scale consumer trước khi đo downstream capacity.
- Retry mọi exception giống nhau.
- Không thiết kế idempotency.
- Chỉ nhìn execution count, không nhìn backlog age/rate.
- Không có replay/reconciliation cho poison work.

## Thang điểm 0–10

- **0–2:** Chỉ tăng scale/retry.
- **3–4:** Có telemetry nhưng thiếu failure classification.
- **5–6:** Điều tra đúng backlog/dependencies và poison work.
- **7–8:** Có idempotency, backpressure, drain strategy và tests.
- **9–10:** Hiểu retry amplification, capacity model và operational recovery sâu.

# Câu 3 — Thiết kế upload tài liệu lớn: backend proxy hay direct-to-Blob?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS, security, API design, reliability, observability

## Bối cảnh

Một enterprise portal cần cho người dùng upload tài liệu từ 1 MB đến vài GB. Hiện frontend gửi file qua ASP.NET Core API; API giữ request lâu rồi stream lên Azure Blob Storage. Khi traffic tăng, App Service instances có nhiều long-lived requests và deployment/restart làm một số uploads thất bại.

Team đề xuất cho browser upload trực tiếp lên Blob Storage bằng một credential có quyền ghi rộng để “bỏ backend khỏi đường truyền”. Security team yêu cầu user chỉ được upload vào đúng tenant/object được cấp phép. Business cần progress, retry/resume hợp lý, malware scanning trước khi file được xem là usable, metadata trong SQL Server và audit trail.

## Câu hỏi chính

Bạn sẽ thiết kế upload architecture và authorization boundary thế nào, so sánh backend-proxy với direct upload, để hỗ trợ file lớn, multi-tenant security, failure recovery và scanning mà không cấp quyền storage quá rộng cho client?

## Câu hỏi làm rõ nên cân nhắc

1. Maximum file size và browser/mobile clients thực tế là gì?
2. File phải usable ngay sau upload hay có thể ở trạng thái `PendingScan`?
3. Có requirement resume/chunk upload không?
4. Tenant isolation nằm ở container/path/logical metadata nào và threat model ra sao?
5. Retention, delete, legal/audit requirements là gì?

## Gợi ý tư duy

### Gợi ý 1

Tách control plane (authorize/create upload intent) khỏi data plane (bytes transfer).

### Gợi ý 2

Direct upload không đồng nghĩa với public storage credential.

### Gợi ý 3

Upload hoàn tất về mặt bytes chưa có nghĩa business object đã an toàn/usable.

## Cấu trúc trả lời đề xuất

1. Clarify size/security/lifecycle requirements.
2. So sánh proxy vs direct data path.
3. Thiết kế upload intent và scoped authorization.
4. Define object naming/tenant boundary.
5. Upload completion verification.
6. Malware scanning/state machine.
7. Metadata transaction/consistency strategy.
8. Retry/resume/orphan cleanup.
9. Observability/audit.
10. Security/load/failure testing.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không đưa storage account key/credential rộng cho browser.
- Backend vẫn authorize upload intent dù bytes có thể đi direct.
- Dùng narrowly scoped, short-lived access mechanism phù hợp nếu direct upload được chọn.
- File có lifecycle như `PendingUpload → Uploaded → PendingScan → Available/Rejected`.
- Xử lý orphan blob/metadata mismatch và retries.
- Validate authorization khi download/read, không chỉ upload.

### Điểm cộng

- Managed Identity cho backend-to-storage access.
- Object name do server kiểm soát thay vì tin client path.
- Verify size/content metadata/checksum theo requirement.
- Lifecycle cleanup cho abandoned uploads.

### Senior+

- Phân biệt security boundary với naming convention.
- Có threat model cho cross-tenant overwrite, replay, oversized upload và malicious content.
- Chọn proxy cho trường hợp compliance/inspection yêu cầu bytes đi qua trusted service, thay vì coi direct upload luôn tốt hơn.

## Hướng giải quyết tham khảo

Với file vài GB, proxy toàn bộ bytes qua ASP.NET Core có chi phí rõ: long-lived requests, bandwidth đi qua app tier, pressure khi scale/deploy và failure surface lớn hơn. Một thiết kế thường đáng cân nhắc là backend làm control plane: authenticate user, authorize tenant/object, tạo upload record và cấp quyền upload giới hạn cho đúng object trong thời gian ngắn. Browser chuyển bytes trực tiếp tới Blob Storage bằng access mechanism được scope chặt; không bao giờ nhận account key hay credential rộng.

Backend nên quyết định blob identity/path từ trusted tenant/user context, không nhận arbitrary path rồi ký. Upload record có ID và state. Client có thể báo completion nhưng server không tin thông báo đó một cách mù quáng; server xác minh object tồn tại và metadata/size theo policy.

Sau upload, file ở `PendingScan`, chưa được expose như tài liệu hợp lệ. Một asynchronous scanner/process kiểm tra malware và business validation rồi chuyển `Available` hoặc `Rejected`. Metadata SQL và blob state không có distributed transaction mặc định, vì vậy workflow cần reconciliation: blob có nhưng DB missing, DB pending nhưng upload abandoned, scan timeout, delete failure. Scheduled cleanup/lifecycle policy có thể xử lý orphan theo retention rules.

Backend dùng Managed Identity khi truy cập storage từ server nếu environment hỗ trợ. Read/download cũng phải authorize tenant/object; không biến blob URL dài hạn thành authorization model. Audit logs cần upload intent ID, tenant, user, object ID, status transitions và scan result nhưng không log secrets/tokens.

Proxy vẫn có thể hợp lý nếu compliance bắt buộc inline inspection hoặc clients không hỗ trợ direct upload/resume, nhưng phải stream chứ không buffer toàn file và cần timeout/resource model phù hợp. Với browser và multi-GB files, direct data path thường giảm app-tier load nếu security/lifecycle được thiết kế đúng.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách authorization/control plane khỏi data plane. Backend vẫn authenticate user và quyết định tenant, object ID, allowed size/type. Với file vài GB, tôi nghiêng về direct-to-Blob để bytes không phải đi qua App Service, nhưng client chỉ nhận quyền ngắn hạn, scope đúng object; tuyệt đối không nhận account key hay quyền ghi rộng.

Tôi tạo một upload intent trong SQL với state `PendingUpload`, server quyết định blob name. Sau khi bytes upload xong, backend xác minh blob rồi chuyển `PendingScan`; file chưa được download như content hợp lệ cho đến khi scanner chuyển nó sang `Available`. Vì SQL và Blob không có một transaction chung, tôi thiết kế reconciliation và cleanup cho orphan/abandoned uploads.

Backend dùng Managed Identity cho server-side storage operations. Download cũng phải authorize lại theo tenant. Tôi test cross-tenant attempts, oversized/malicious files, interrupted upload, duplicate completion và scanner failure. Nếu compliance bắt buộc mọi bytes qua trusted service thì proxy có thể đúng, nhưng tôi sẽ coi đó là requirement-driven trade-off chứ không phải default.”

## Câu hỏi đào sâu

1. Nếu client upload thành công nhưng crash trước khi gọi completion API, bạn recover thế nào?
2. Tại sao blob path chứa `tenantId` chưa đủ để bảo đảm tenant isolation?
3. Nếu security team cấm direct browser-to-storage hoàn toàn, bạn tối ưu backend proxy cho file vài GB thế nào?

## Lỗi trả lời thường gặp

- Cấp storage account key cho frontend.
- Tin arbitrary blob path từ client.
- Coi upload completion là đủ để publish file.
- Bỏ qua orphan/reconciliation vì SQL và Blob khác resource.
- Chỉ bảo vệ upload nhưng download URL lại bypass authorization.

## Thang điểm 0–10

- **0–2:** Chỉ chọn proxy/direct mà không có security/lifecycle.
- **3–4:** Có SAS-like scoped access nhưng thiếu failure model.
- **5–6:** Có authorization, state machine, scan và cleanup.
- **7–8:** Có tenant threat model, Managed Identity, reconciliation và tests.
- **9–10:** Thiết kế cân bằng data plane, security, operability và conditional trade-offs rất rõ.

# Tổng kết hôm nay

## Kiến thức trọng tâm

EF Core tracking không tự giải quyết lost update giữa nhiều requests; concurrency phải được biểu diễn bằng explicit token và business conflict policy. Production backlog cần được điều tra bằng arrival/service rate, downstream saturation và failure classification thay vì tăng retry/concurrency theo phản xạ. Với large-file upload, tách control plane khỏi data plane giúp giảm app-tier pressure nhưng authorization, lifecycle, scanning và reconciliation vẫn phải được thiết kế như first-class concerns.

## Mẫu tư duy cần nhớ

- Phân biệt local state tracking với cross-request concurrency guarantee.
- Retry chỉ an toàn khi failure classification và idempotency được thiết kế cùng nhau.
- Stabilize downstream trước khi tăng offered load.
- Tách control plane khỏi data plane khi data transfer lớn nhưng giữ authorization ở trusted boundary.
- Thiết kế reconciliation khi workflow đi qua nhiều durable resources.
