# Code Review Challenge 1 — Export 1,5 triệu rows ra CSV: API vẫn đúng logic nhưng vì sao App Service memory tăng mạnh và request chết dưới tải?

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, SQL Server, streaming, memory allocation, LOH, async I/O, cancellation, API performance, production observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một enterprise reporting portal có endpoint cho phép user xuất transaction history ra CSV.

Business vừa tăng giới hạn export từ khoảng 50.000 rows lên tối đa 1.500.000 rows. API chạy ASP.NET Core .NET 8 trên Azure App Service Linux với nhiều instances.

Yêu cầu:

- export phải giữ đúng filter theo tenant và date range;
- file lớn có thể mất vài chục giây nhưng request không được làm application mất ổn định;
- nếu client đóng browser hoặc reverse proxy hủy request, backend nên dừng work càng sớm càng tốt;
- nhiều users có thể export đồng thời;
- không bắt buộc toàn bộ dataset phải được giữ trong memory trước khi download;
- SQL Server là source of truth;
- một export có thể trả hàng trăm MB dữ liệu;
- p95 của các API khác không được tăng đáng kể chỉ vì có vài export lớn.

Sau khi feature lên production, team quan sát:

- memory của một số App Service instances tăng từ khoảng 700 MB lên hơn 3 GB khi có 4–6 exports đồng thời;
- GC time tăng rõ rệt;
- đôi lúc process recycle hoặc trả 502/503;
- SQL Server CPU không tăng nhiều;
- export nhỏ vẫn chạy bình thường;
- Application Insights cho thấy request duration rất dài nhưng chưa có telemetry về rows exported, bytes written hay cancellation;
- developer cho rằng “đã dùng `await` nên memory không thể là vấn đề lớn”.

Code hiện tại:

## Đoạn code cần review

```csharp
[Authorize]
[HttpGet("exports/transactions")]
public async Task<IActionResult> ExportTransactions(
    DateTime fromUtc,
    DateTime toUtc,
    CancellationToken cancellationToken)
{
    var tenantId = User.FindFirst("tenant_id")!.Value;

    var transactions = await _db.Transactions
        .Where(x =>
            x.TenantId == tenantId &&
            x.CreatedAtUtc >= fromUtc &&
            x.CreatedAtUtc < toUtc)
        .OrderBy(x => x.CreatedAtUtc)
        .ToListAsync();

    var csv = new StringBuilder();
    csv.AppendLine("Id,CreatedAtUtc,CustomerName,Amount,Currency");

    foreach (var transaction in transactions)
    {
        var customer = await _db.Customers
            .SingleAsync(x => x.Id == transaction.CustomerId);

        csv.Append(transaction.Id).Append(',')
           .Append(transaction.CreatedAtUtc.ToString("O")).Append(',')
           .Append(customer.Name).Append(',')
           .Append(transaction.Amount).Append(',')
           .Append(transaction.Currency)
           .AppendLine();
    }

    var bytes = Encoding.UTF8.GetBytes(csv.ToString());
    var stream = new MemoryStream();
    await stream.WriteAsync(bytes);
    stream.Position = 0;

    return File(
        stream,
        "text/csv",
        $"transactions-{DateTime.UtcNow:yyyyMMddHHmmss}.csv");
}
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code dưới góc nhìn production và:

1. xác định các vấn đề correctness, performance, memory, database access và cancellation;
2. giải thích vì sao code hoàn toàn `async` vẫn có thể gây memory pressure/GC pressure nghiêm trọng;
3. xác định các điểm copy/materialize dữ liệu không cần thiết;
4. phân tích N+1 database access và ảnh hưởng khi export hàng triệu rows;
5. đề xuất implementation có khả năng stream dữ liệu theo bounded memory;
6. giải thích cách bảo vệ hệ thống khi nhiều exports chạy đồng thời;
7. đề xuất test strategy và production telemetry đủ để chứng minh improvement.

## Câu hỏi gợi mở

1. Dataset đang tồn tại bao nhiêu bản sao trong managed memory từ lúc query xong tới lúc response bắt đầu gửi?
2. `await` giải quyết việc chờ I/O như thế nào, và điều gì nó không giải quyết về object lifetime/allocation?
3. Nếu client disconnect sau khi backend đã xử lý 800.000 rows, code hiện tại có dừng database/query/serialization work không?
4. Việc query `Customers` trong từng iteration tạo bao nhiêu database round trips ở worst case?
5. Nếu stream trực tiếp response nhưng cho phép 100 export lớn chạy cùng lúc, hệ thống đã an toàn chưa?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **full materialization + multiple large in-memory representations**. Hãy theo dõi lifetime của `List<Transaction>`, `StringBuilder`, `string`, `byte[]` và `MemoryStream`.

### Gợi ý 2

Streaming giúp bounded memory, nhưng production-safe design còn cần query shape, cancellation, concurrency control, timeout và backpressure. Đừng biến “streaming” thành một từ khóa thay cho capacity planning.

## Kết quả code review tham khảo

### Critical — Toàn bộ dataset được materialize vào memory trước khi gửi response

**Vấn đề:**  
`ToListAsync()` tải toàn bộ transactions vào một `List<Transaction>` trước khi CSV generation bắt đầu.

**Tại sao xảy ra:**  
EF Core materialize tất cả entities trong result set. Với hàng trăm nghìn tới hơn một triệu rows, riêng object graph đã chiếm lượng memory lớn. Nếu entity có nhiều fields hơn những columns cần export, memory còn tăng thêm.

**Ảnh hưởng production:**  
Working set tăng mạnh, Gen 2/LOH pressure tăng, GC pause nhiều hơn, nhiều exports đồng thời có thể khiến process bị recycle hoặc OOM trước khi response được gửi.

**Cách sửa:**  
Projection chỉ lấy fields cần thiết và stream query bằng `AsAsyncEnumerable()`/asynchronous enumeration thay vì materialize toàn bộ list. Đồng thời cần xem execution behavior của database provider và đảm bảo connection/query lifecycle phù hợp với streaming request.

---

### Critical — CSV được giữ thành nhiều bản sao lớn trong memory

**Vấn đề:**  
Code lần lượt giữ:

```text
StringBuilder internal buffers
→ csv.ToString()
→ UTF-8 byte[]
→ MemoryStream backing buffer
```

**Tại sao xảy ra:**  
`csv.ToString()` tạo một `string` lớn. `Encoding.UTF8.GetBytes(...)` tạo thêm `byte[]`. Sau đó `MemoryStream.WriteAsync(bytes)` copy bytes vào buffer riêng của `MemoryStream`.

**Ảnh hưởng production:**  
Một export vài trăm MB có thể tạm thời giữ nhiều trăm MB hoặc hơn chỉ cho payload representations. Nhiều allocations lớn đi vào Large Object Heap và tạo GC/fragmentation pressure.

**Cách sửa:**  
Ghi từng row hoặc từng buffer nhỏ trực tiếp vào response stream bằng `StreamWriter`/`PipeWriter` phù hợp, tránh tạo full payload trước.

### High — N+1 query khi load Customer

**Vấn đề:**  
Mỗi transaction chạy thêm:

```csharp
await _db.Customers.SingleAsync(...)
```

**Tại sao xảy ra:**  
Nếu có 1.000.000 transactions, application có thể tạo tới khoảng 1.000.000 customer queries ngoài transaction query ban đầu.

**Ảnh hưởng production:**  
Database round trips tăng cực lớn, export duration kéo dài, connection pool bị chiếm, SQL load tăng và các API khác bị ảnh hưởng dù từng query đơn lẻ nhanh.

**Cách sửa:**  
Project customer data trong cùng query nếu relation/query plan phù hợp:

```csharp
.Select(x => new ExportRow(
    x.Id,
    x.CreatedAtUtc,
    x.Customer.Name,
    x.Amount,
    x.Currency))
```

Sau đó inspect generated SQL/execution plan để bảo đảm query shape hiệu quả.

---

### High — Cancellation token không được propagate vào database và response writing

**Vấn đề:**  
Method nhận `cancellationToken` nhưng `ToListAsync`, `SingleAsync` và `WriteAsync` không dùng token.

**Tại sao xảy ra:**  
Client disconnect hoặc request aborted không tự động khiến mọi downstream operation dừng nếu token không được truyền tiếp.

**Ảnh hưởng production:**  
Server tiếp tục query, allocate và serialize một file không còn consumer; connection/CPU/memory bị giữ không cần thiết.

**Cách sửa:**  
Truyền `cancellationToken` vào database operations và stream writing. Với ASP.NET Core có thể dùng `HttpContext.RequestAborted` hoặc action token đã được bind từ request-abort semantics.

---

### High — Tracking không cần thiết cho read-only export

**Vấn đề:**  
Query entity mặc định có thể bị tracked bởi `DbContext`.

**Tại sao xảy ra:**  
Change tracker giữ metadata/references cho entities dù export không sửa chúng.

**Ảnh hưởng production:**  
Tăng allocation và memory lifetime, đặc biệt tệ với result set lớn.

**Cách sửa:**  
Dùng `AsNoTracking()` và tốt hơn nữa là projection chỉ lấy scalar fields cần export.

---

### High — CSV escaping/culture chưa được xử lý đúng

**Vấn đề:**  
`customer.Name`, `Amount`, `Currency` được nối trực tiếp bằng dấu phẩy.

**Tại sao xảy ra:**  
Tên customer có comma, quote hoặc newline sẽ phá cấu trúc CSV. `Amount.ToString()` còn phụ thuộc culture nếu không chỉ định invariant format.

**Ảnh hưởng production:**  
File parse sai, columns lệch, downstream import lỗi hoặc dữ liệu hiển thị không đúng.

**Cách sửa:**  
Dùng CSV escaping đúng chuẩn: field chứa comma/quote/newline phải quote và duplicate internal quotes. Format numeric/date bằng `CultureInfo.InvariantCulture` theo contract export.

---

### Medium — Không có bounded concurrency/capacity control cho expensive exports

**Vấn đề:**  
Dù chuyển sang streaming, mỗi export vẫn giữ database connection, request slot và outbound response trong thời gian dài.

**Tại sao xảy ra:**  
Nếu nhiều users mở export cùng lúc, tổng resource consumption vẫn có thể vượt capacity.

**Ảnh hưởng production:**  
Connection pool pressure, bandwidth contention, long-running requests và degradation của API khác.

**Cách sửa:**  
Thiết lập product/capacity guard phù hợp: giới hạn concurrent exports per tenant/user/instance hoặc đưa very-large export sang asynchronous export job + Blob Storage nếu UX cho phép. Không mặc định cần queue nếu export streaming hiện tại đã đáp ứng scale.

---

### Medium — Không validate phạm vi export và thiếu policy chống accidental full-table scan

**Vấn đề:**  
Code không cho thấy validation `fromUtc`, `toUtc`, maximum time range hoặc row limit.

**Tại sao xảy ra:**  
User có thể yêu cầu khoảng thời gian quá rộng, tạo expensive query và file khổng lồ.

**Ảnh hưởng production:**  
Resource exhaustion hoặc noisy-neighbor behavior giữa tenants.

**Cách sửa:**  
Validate business limits, authorize tenant scope và có quota/concurrency policy. Nếu business thật sự cần 1,5 triệu rows thì capacity phải được thiết kế cho requirement đó thay vì chỉ giảm limit tùy ý.

---

### Medium — Ordering chưa hoàn toàn deterministic khi nhiều rows cùng `CreatedAtUtc`

**Vấn đề:**  
Chỉ `OrderBy(x => x.CreatedAtUtc)`.

**Tại sao xảy ra:**  
Nhiều rows có cùng timestamp có thể được database trả theo thứ tự không xác định giữa executions.

**Ảnh hưởng production:**  
Không nhất thiết làm mất row trong một single streaming query, nhưng làm export ordering thiếu deterministic và gây khó nếu sau này chuyển sang keyset/chunked pagination.

**Cách sửa:**  
Dùng total ordering, ví dụ:

```csharp
.OrderBy(x => x.CreatedAtUtc)
.ThenBy(x => x.Id)
```

Nếu chunking theo pages, dùng `(CreatedAtUtc, Id)` làm stable cursor.

## Phiên bản đề xuất

Một implementation bounded-memory có thể stream trực tiếp response. Ví dụ rút gọn:

```csharp
[Authorize]
[HttpGet("exports/transactions")]
public async Task ExportTransactions(
    DateTime fromUtc,
    DateTime toUtc,
    CancellationToken cancellationToken)
{
    ValidateExportRange(fromUtc, toUtc);

    var tenantId = User.FindFirst("tenant_id")?.Value
        ?? throw new UnauthorizedAccessException();

    Response.StatusCode = StatusCodes.Status200OK;
    Response.ContentType = "text/csv; charset=utf-8";
    Response.Headers.ContentDisposition =
        $"attachment; filename=transactions-{DateTime.UtcNow:yyyyMMddHHmmss}.csv";

    await using var writer = new StreamWriter(
        Response.Body,
        new UTF8Encoding(encoderShouldEmitUTF8Identifier: false),
        bufferSize: 64 * 1024,
        leaveOpen: true);

    await writer.WriteLineAsync(
        "Id,CreatedAtUtc,CustomerName,Amount,Currency".AsMemory(),
        cancellationToken);

    var query = _db.Transactions
        .AsNoTracking()
        .Where(x =>
            x.TenantId == tenantId &&
            x.CreatedAtUtc >= fromUtc &&
            x.CreatedAtUtc < toUtc)
        .OrderBy(x => x.CreatedAtUtc)
        .ThenBy(x => x.Id)
        .Select(x => new ExportRow(
            x.Id,
            x.CreatedAtUtc,
            x.Customer.Name,
            x.Amount,
            x.Currency))
        .AsAsyncEnumerable();

    var rows = 0L;

    await foreach (var row in query.WithCancellation(cancellationToken))
    {
        await writer.WriteAsync(Escape(row.Id.ToString()));
        await writer.WriteAsync(",");
        await writer.WriteAsync(Escape(row.CreatedAtUtc.ToString("O")));
        await writer.WriteAsync(",");
        await writer.WriteAsync(Escape(row.CustomerName));
        await writer.WriteAsync(",");
        await writer.WriteAsync(Escape(
            row.Amount.ToString(CultureInfo.InvariantCulture)));
        await writer.WriteAsync(",");
        await writer.WriteLineAsync(Escape(row.Currency));

        rows++;

        if (rows % 1000 == 0)
        {
            await writer.FlushAsync(cancellationToken);
        }
    }

    await writer.FlushAsync(cancellationToken);
}

private static string Escape(string? value)
{
    value ??= string.Empty;

    if (!value.Contains(',') &&
        !value.Contains('"') &&
        !value.Contains('\r') &&
        !value.Contains('\n'))
    {
        return value;
    }

    return $"\"{value.Replace("\"", "\"\"")}\"";
}
```

Điểm chính của phiên bản này:

- không `ToListAsync()` toàn bộ dataset;
- không tạo một `StringBuilder` cho cả file;
- không tạo full `string` + `byte[]` + `MemoryStream`;
- query chỉ project columns cần thiết;
- không chạy N+1 customer lookup;
- cancellation đi xuyên database enumeration và response writing;
- memory chủ yếu bị giới hạn bởi EF/provider buffers, writer buffer và một row/current materialization thay vì toàn file.

Tuy nhiên streaming không tự giải quyết mọi vấn đề. Một request kéo dài 1–2 phút vẫn có thể giữ SQL connection lâu. Nếu scale thực tế có hàng chục export đồng thời, cần đo:

- active exports;
- DB connection usage;
- response bandwidth;
- query duration;
- per-instance memory;
- impact tới p95/p99 API khác.

Nếu requirement yêu cầu file cực lớn, retry/resume hoặc người dùng không cần chờ browser request mở liên tục, architecture khác có thể hợp lý hơn:

```text
POST /exports
  -> create export job
  -> background worker streams DB -> Blob Storage
  -> user polls/downloads completed file via authorized URL/SAS
```

Nhưng asynchronous job tăng thêm queue/job state, lifecycle, cleanup, Blob authorization và UX complexity. Chỉ chọn khi scale/UX/SLO chứng minh lợi ích vượt chi phí.

Một điểm correctness khác là **snapshot consistency**. Streaming một query dài không mặc định đảm bảo business snapshot theo nghĩa “mọi rows phản ánh cùng một thời điểm” nếu dữ liệu thay đổi trong lúc export; behavior phụ thuộc transaction/isolation/database semantics. Nếu business yêu cầu snapshot chính xác, cần chốt requirement rồi chọn isolation/snapshot strategy phù hợp thay vì ngầm giả định.

Tài liệu tham khảo:

- Microsoft Learn — Efficient Querying in EF Core: `https://learn.microsoft.com/ef/core/performance/efficient-querying`
- Microsoft Learn — ASP.NET Core request and response operations: `https://learn.microsoft.com/aspnet/core/fundamentals/middleware/request-response`

## Giải thích thiết kế sau khi sửa

Thiết kế mới biến export thành một pipeline:

```text
SQL row
→ lightweight projection
→ CSV escape/format
→ small writer buffer
→ HTTP response
```

Thay vì:

```text
SQL
→ all entities
→ all customer queries
→ giant StringBuilder
→ giant string
→ giant byte[]
→ another MemoryStream buffer
→ response
```

`async` giúp thread không phải block trong lúc chờ database/network I/O. Nó không làm object biến mất khỏi heap và không giới hạn lượng dữ liệu đã được materialize. Vì vậy vấn đề memory phải được giải bằng data-flow/lifetime design, không phải chỉ thêm `await`.

Nếu tenant isolation là security boundary, tenant filter phải nằm trong query do server xây dựng từ authenticated context. Không nhận tenant ID tùy ý từ query string rồi tin caller.

## Trade-offs

Streaming response có một trade-off quan trọng: sau khi response headers/body đã bắt đầu gửi, khả năng đổi sang structured HTTP error bị hạn chế. Nếu database lỗi ở row thứ 900.000, client có thể nhận file partial. API contract cần quy định cách user nhận biết partial download, hoặc chọn background-file architecture nếu atomic downloadable artifact là requirement.

Một streaming query dài cũng giữ database resources lâu. Chunked/keyset reading có thể giảm duration của từng DB command nhưng làm snapshot consistency phức tạp hơn nếu dữ liệu thay đổi giữa pages.

Asynchronous export-to-Blob giúp retries và download decoupling tốt hơn, nhưng tăng operational components. Không nên chuyển sang queue chỉ vì “file lớn” nếu measured load vẫn chạy an toàn với bounded concurrency + streaming.

## Cách kiểm thử

1. **Load test:** chạy đồng thời 1, 5, 10 exports với dataset representative; đo peak working set, GC pause, DB connections, throughput và p95 của API bình thường.
2. **Cancellation test:** client abort sau một phần file; xác minh query/serialization dừng nhanh và connection được release.
3. **Correctness test:** customer name có comma, quote, CR/LF; CSV vẫn parse đúng và amount dùng invariant format.
4. **Large-data integration test:** export >1 triệu rows; row count/file integrity đúng, memory không tăng tuyến tính theo file size.
5. **Failure-path test:** database/network fail giữa stream; xác minh partial-file behavior được detect/document và telemetry ghi rõ bytes/rows đã gửi.

## Quan sát trong production

Nên bổ sung structured telemetry:

- `export_id` và correlation ID;
- tenant identifier theo policy an toàn;
- requested date range;
- rows exported;
- bytes written;
- query duration;
- total export duration;
- canceled/aborted count;
- concurrent exports gauge;
- process working set/GC heap size/Gen 2 collections/GC pause;
- SQL connection pool usage và dependency duration;
- response status + partial failure category;
- p95/p99 của normal APIs khi export traffic tăng.

Alert quan trọng là memory/GC + concurrent export pressure + impact tới shared APIs, không chỉ timeout riêng của export endpoint.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business yêu cầu export phản ánh đúng một snapshot dữ liệu tại thời điểm bắt đầu request, streaming/chunking strategy của bạn thay đổi thế nào?
2. Nếu response streaming dùng bounded memory nhưng 50 users cùng export và SQL connection pool bị cạn, bạn ưu tiên giải pháp nào trước: tăng pool, semaphore, background job hay read replica? Evidence nào quyết định?
3. Khi nào bạn chấp nhận buffer toàn file trong memory thay vì streaming?

# Code Review Challenge 2 — Redis cache quyền truy cập: cache hit rất nhanh nhưng có thể trả dữ liệu của tenant khác và cho phép quyền đã bị revoke

**Chủ đề:** Redis, ASP.NET Core authorization, multi-tenant security, cache key design, invalidation, TTL, fail-open/fail-closed, cache stampede, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal SaaS có nhiều tenants. User có thể thuộc nhiều tenants với roles/permissions khác nhau ở từng tenant.

ASP.NET Core API kiểm tra permission trước các thao tác nhạy cảm. Để giảm số lần đọc SQL Server, team cache permission set trong Redis.

Yêu cầu:

- permission phải được tính theo `(tenant, user)`;
- khi admin revoke một permission quan trọng, hệ thống mong muốn thay đổi có hiệu lực trong vài phút;
- Redis là performance optimization, không phải source of truth;
- Redis outage không được biến thành cơ chế bypass authorization;
- hệ thống chạy nhiều App Service instances;
- một user có thể chuyển tenant context trong cùng browser session;
- có burst traffic sau giờ làm việc khi nhiều users login cùng lúc;
- một số permissions bảo vệ các thao tác tài chính và export dữ liệu nhạy cảm.

Production xuất hiện hai symptom riêng biệt:

- một user chuyển từ Tenant A sang Tenant B nhưng trong một số request vẫn có permission mà user chỉ được cấp ở Tenant A;
- sau khi admin revoke `finance.approve`, user đôi khi vẫn approve được trong khoảng 20–30 phút;
- khi Redis bị timeout, một developer thấy request “vẫn chạy được” vì code fallback cho rằng unavailable cache không nên chặn user;
- chưa có metric cho cache key cardinality, permission-cache age, fallback-to-database hoặc authorization-denied reason.

{
    private readonly IDistributedCache _cache;
    private readonly AppDbContext _db;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        IDistributedCache cache,
        AppDbContext db,
        ILogger<PermissionService> logger)
    {
        _cache = cache;
        _db = db;
        _logger = logger;
    }

    public async Task<bool> HasPermissionAsync(
        string tenantId,
        string userId,
        string permission,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"permissions:{userId}";

        try
        {
            var cached = await _cache.GetStringAsync(
                cacheKey,
                cancellationToken);

            HashSet<string> permissions;

            if (cached is null)
            {
                permissions = await _db.UserPermissions
                    .Where(x => x.UserId == userId && x.TenantId == tenantId)
                    .Select(x => x.Permission)
                    .ToHashSetAsync(cancellationToken);

                await _cache.SetStringAsync(
                    cacheKey,
                    JsonSerializer.Serialize(permissions),
                    new DistributedCacheEntryOptions
                    {
                        AbsoluteExpirationRelativeToNow =
                            TimeSpan.FromMinutes(30)
                    },
                    cancellationToken);
            }
            else
            {
                permissions = JsonSerializer.Deserialize<HashSet<string>>(cached)
                    ?? new HashSet<string>();
            }

            return permissions.Contains(permission);
        }
        catch (Exception ex)
        {
            _logger.LogWarning(
                ex,
                "Permission cache failed for UserId={UserId}",
                userId);

            return true;
        }
    }
}

Hãy review design và code theo góc nhìn security + distributed caching:

1. tìm các lỗi có thể tạo cross-tenant authorization leakage;
2. đánh giá semantics khi permission bị revoke;
3. phân tích behavior khi Redis timeout/outage;
4. chỉ ra race conditions/cache stampede khi nhiều instances gặp cache miss cùng lúc;
5. ưu tiên findings theo severity;
6. đề xuất design an toàn hơn nhưng không biến mỗi request thành một hệ thống phân tán quá phức tạp;
7. giải thích cách test revoke, tenant switching, Redis failure và high-concurrency cache miss;
8. đề xuất production telemetry cho authorization cache mà không log dữ liệu nhạy cảm quá mức.

## Câu hỏi gợi mở

1. Cache key có chứa đầy đủ authorization context quyết định permission set hay chưa?
2. `AbsoluteExpirationRelativeToNow = 30 phút` có phù hợp với requirement revoke trong vài phút nếu không có explicit invalidation?
3. Trong một security check, Redis failure nên dẫn đến “allow”, “deny” hay fallback source of truth? Điều gì phụ thuộc business risk?
4. Nếu 500 requests từ cùng user/tenant gặp cache miss đồng thời, SQL Server sẽ nhận bao nhiêu query?
5. Nếu revoke DB thành công nhưng cache invalidation thất bại, system nên hành xử ra sao?

## Gợi ý

### Gợi ý 1

Primary risk là **authorization context bị cache với key quá hẹp** và **failure path fail-open**. Đây không còn là performance bug mà là security boundary bug.

### Gợi ý 2

TTL là một freshness policy, không phải invalidation guarantee. Với revoke nhạy cảm, hãy reasoning về source of truth, invalidation, versioning và acceptable stale window.

## Kết quả code review tham khảo

### Critical — Cache key thiếu `tenantId`, tạo cross-tenant permission leakage

**Vấn đề:**  
Key hiện tại:

```text
permissions:{userId}
```

trong khi permission set phụ thuộc cả `tenantId` và `userId`.

**Tại sao xảy ra:**  
Nếu user truy cập Tenant A trước, cache được populate bằng permissions của A. Khi cùng user chuyển sang Tenant B, lookup dùng đúng cùng key và có thể reuse permission set của A.

**Ảnh hưởng production:**  
User có thể thực hiện operation ở tenant khác với quyền không được cấp tại tenant đó. Đây là broken authorization/cross-tenant isolation issue.

**Cách sửa:**  
Cache key phải encode đầy đủ authorization scope, tối thiểu:

```text
authz:{tenantId}:{userId}
```

Nếu permission còn phụ thuộc resource, role version, environment hoặc authz policy version thì key/value design phải phản ánh đúng context tương ứng.

---

### Critical — Redis failure trả `true`, tức fail-open authorization

**Vấn đề:**  
Catch mọi exception rồi:

```csharp
return true;
```

**Tại sao xảy ra:**  
Redis timeout, deserialization error hoặc database failure đều trở thành authorization success.

**Ảnh hưởng production:**  
Một cache outage có thể biến thành privilege escalation diện rộng. Attacker hoặc incident infrastructure có thể dẫn tới bypass permission checks.

**Cách sửa:**  
Không fail-open cho sensitive authorization. Redis miss/failure nên fallback source of truth nếu có thể; nếu source of truth cũng unavailable thì protected operation thường phải fail closed theo threat model/business requirement. Availability-vs-security trade-off cần explicit, không được ngầm chọn bằng `return true`.

---

### High — Revoke không invalidate cache nên stale permission có thể sống đủ 30 phút

**Vấn đề:**  
`RevokePermissionAsync` chỉ xóa SQL row, không tác động cache.

**Tại sao xảy ra:**  
Cache entry cũ giữ permission set cho tới expiration.

**Ảnh hưởng production:**  
User tiếp tục có quyền đã bị revoke, vi phạm requirement “có hiệu lực trong vài phút”. Với quyền tài chính, blast radius có thể lớn.

**Cách sửa:**  
Sau successful source-of-truth change, invalidate key `(tenant,user)` hoặc dùng permission-version strategy. TTL chỉ là backstop; invalidation/versioning mới kiểm soát revoke freshness tốt hơn.

---

### High — Database commit và cache invalidation có failure window

**Vấn đề:**  
Ngay cả khi bổ sung `RemoveAsync(cacheKey)`, vẫn có thể xảy ra:

```text
DB revoke commit succeeds
→ process/network fails
→ cache invalidation never happens
```

**Tại sao xảy ra:**  
SQL Server và Redis không nằm trong cùng atomic transaction.

**Ảnh hưởng production:**  
Stale authorization vẫn tồn tại tới TTL dù code “có invalidate”.

**Cách sửa:**  
Chọn strategy theo risk:

- với stale window vài phút có thể chấp nhận: explicit invalidation + short TTL/backstop;
- với revoke cần mạnh hơn: store/increment authorization version trong source of truth và gắn version vào cache entry/key, hoặc dùng durable invalidation event/outbox nếu complexity được justify;
- critical operation có thể revalidate server-side khi policy yêu cầu freshness cao.

Không cần tự động đưa mọi permission change vào messaging nếu requirement không cần.

---

### High — Cache miss burst gây stampede vào SQL Server

**Vấn đề:**  
Mọi request miss cache đều query DB rồi set cùng key.

**Tại sao xảy ra:**  
Khi entry hết hạn hoặc Redis vừa recover, hàng trăm requests có thể cùng lúc thấy miss.

**Ảnh hưởng production:**  
DB query burst, connection-pool pressure và latency spike đúng lúc hệ thống đang hồi phục.

**Cách sửa:**  
Có thể dùng local single-flight/per-key coordination trong mỗi instance, TTL jitter, preload cho hot principals hoặc bounded fallback concurrency. Distributed lock chỉ nên thêm nếu measured stampede thực sự cần; đừng biến permission lookup thành complex distributed lock protocol không cần thiết.

---

### High — Generic exception handling trộn cache failure, database failure và corrupt payload

**Vấn đề:**  
Toàn bộ method nằm trong một `try/catch` lớn.

**Tại sao xảy ra:**  
Redis timeout, SQL timeout, JSON corruption và programming bug đều đi vào cùng đường `return true`.

**Ảnh hưởng production:**  
Vừa bypass security, vừa làm telemetry không phân biệt failure layer.

**Cách sửa:**  
Tách cache read failure khỏi source-of-truth lookup. Cache failure → log/metric + DB fallback. DB failure → return authorization failure/service unavailable theo contract an toàn. Corrupt cache → remove entry + DB reload, không allow mặc định.

---

### Medium — TTL cố định tạo synchronized expiry bursts

**Vấn đề:**  
Mọi entry dùng đúng 30 phút.

**Tại sao xảy ra:**  
Nếu lượng lớn users login/populate cache trong cùng một window, entries có thể expire gần nhau và tạo burst DB reads.

**Ảnh hưởng production:**  
Periodic load spikes, đặc biệt sau deploy/restart hoặc đầu giờ làm việc.

**Cách sửa:**  
Nếu cache volume đủ lớn để đáng quan tâm, thêm bounded jitter quanh TTL hoặc refresh strategy phù hợp. Không dùng TTL dài chỉ để tránh stampede nếu security freshness bị đánh đổi.

---

### Medium — Cache value thiếu metadata về version/freshness

**Vấn đề:**  
Value chỉ là `HashSet<string>`.

**Tại sao xảy ra:**  
Không thể biết permission snapshot được tạo khi nào, từ policy/version nào hoặc có còn phù hợp với source-of-truth revision không.

**Ảnh hưởng production:**  
Khó điều tra stale authorization và khó triển khai version-based invalidation sau này.

**Cách sửa:**  
Nếu requirement cần, cache một envelope như:

```json
{
  "version": 42,
  "loadedAtUtc": "...",
  "permissions": ["finance.read"]
}
```

Version phải xuất phát từ authoritative authorization state, không phải `DateTime.UtcNow` tùy ý nếu muốn dùng cho correctness.

---

### Medium — Logging identifier cần policy rõ

**Vấn đề:**  
Code log raw `UserId` trong warning.

**Tại sao xảy ra:**  
Tùy identity scheme và logging retention, user identifier có thể được coi là dữ liệu nhạy cảm/personal data.

**Ảnh hưởng production:**  
Tăng exposure trong Application Insights/Kibana và compliance burden.

**Cách sửa:**  
Theo logging policy: pseudonymize/hash stable identifier khi phù hợp, log tenant/user key ở dạng được phê duyệt và tuyệt đối không log full permission payload/token/secrets.

## Phiên bản đề xuất

Một phiên bản đơn giản hơn nhưng an toàn về security boundary có thể là:

```csharp
public sealed class PermissionService
{
    private readonly IDistributedCache _cache;
    private readonly AppDbContext _db;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        IDistributedCache cache,
        AppDbContext db,
        ILogger<PermissionService> logger)
    {
        _cache = cache;
        _db = db;
        _logger = logger;
    }

    public async Task<bool> HasPermissionAsync(
        string tenantId,
        string userId,
        string permission,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"authz:v1:{tenantId}:{userId}";

        try
        {
            var cached = await _cache.GetStringAsync(
                cacheKey,
                cancellationToken);

            if (cached is not null)
            {
                var permissions = JsonSerializer
                    .Deserialize<HashSet<string>>(cached);

                if (permissions is not null)
                {
                    return permissions.Contains(permission);
                }

                await SafeRemoveCacheAsync(cacheKey, cancellationToken);
            }
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(
                ex,
                "Authorization cache read failed. TenantKey={TenantKey}",
                SafeTenantKey(tenantId));
        }

        // Redis is an optimization. SQL remains authoritative.
        var permissionsFromDb = await _db.UserPermissions
            .AsNoTracking()
            .Where(x =>
                x.UserId == userId &&
                x.TenantId == tenantId)
            .Select(x => x.Permission)
            .ToHashSetAsync(cancellationToken);

        try
        {
            var ttl = TimeSpan.FromMinutes(3)
                + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

            await _cache.SetStringAsync(
                cacheKey,
                JsonSerializer.Serialize(permissionsFromDb),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow = ttl
                },
                cancellationToken);
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(
                ex,
                "Authorization cache write failed. TenantKey={TenantKey}",
                SafeTenantKey(tenantId));
        }

        return permissionsFromDb.Contains(permission);
    }

    public async Task RevokePermissionAsync(
        string tenantId,
        string userId,
        string permission,
        CancellationToken cancellationToken)
    {
        var row = await _db.UserPermissions.SingleAsync(
            x => x.TenantId == tenantId &&
                 x.UserId == userId &&
                 x.Permission == permission,
            cancellationToken);

        _db.UserPermissions.Remove(row);
        await _db.SaveChangesAsync(cancellationToken);

        var cacheKey = $"authz:v1:{tenantId}:{userId}";

        try
        {
            await _cache.RemoveAsync(cacheKey, cancellationToken);
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogError(
                ex,
                "Authorization cache invalidation failed. TenantKey={TenantKey}",
                SafeTenantKey(tenantId));
        }
    }
}
```

Phiên bản này sửa ba điểm nền tảng:

1. cache key bao gồm tenant context;
2. Redis failure không cho phép request tự động pass authorization;
3. revoke cố gắng invalidate cache và TTL ngắn trở thành bounded stale backstop.

Tuy nhiên vẫn còn failure window giữa DB commit và Redis invalidation. Có nhiều mức design tùy requirement.

### Option A — Explicit invalidation + short TTL

Phù hợp nếu business chấp nhận stale tối đa vài phút.

```text
DB commit
→ remove cache entry
→ nếu remove fail, short TTL giới hạn stale window
```

Đơn giản, dễ vận hành.

### Option B — Authorization version

Source of truth giữ version theo `(tenant,user)` hoặc role assignment revision.

Ví dụ:

```text
UserAuthorizationVersion
TenantId | UserId | Version
```

Khi grant/revoke:

```text
permission change + Version++ trong cùng SQL transaction
```

Cache key/value có version:

```text
authz:{tenant}:{user}:v42
```

Request cần biết current version theo một strategy hợp lý. Nếu phải đọc DB version mỗi request thì cache benefit giảm; có thể dùng signed/session claims với short lifetime, local version cache hoặc durable invalidation depending requirements. Không có một version trick miễn phí giải mọi consistency problem.

### Option C — Durable invalidation event

Nếu security requirement nghiêm và hệ thống đã có reliable messaging/outbox, permission change có thể commit cùng an outbox event:

```text
AuthorizationChanged(tenant, user, version)
```

Consumers invalidate/update caches. Vẫn cần fallback/TTL vì invalidation delivery có thể chậm hoặc fail.

Không nên thêm messaging chỉ vì cache tồn tại nếu product chỉ yêu cầu stale window vài phút và short TTL đã đủ.

### Critical operations

Một số operation như `finance.approve` có thể cần stronger freshness hơn read-only UI permission. Có thể tách policy:

- ordinary read permissions: cache vài phút;
- critical financial approval: revalidate authoritative state hoặc version gần operation time;
- administrative changes: invalidate immediately + audit.

Đây là risk-based authorization design, không phải tất cả permissions phải dùng cùng consistency level.

### Redis outage

Nếu Redis unavailable:

```text
cache read fails
→ query SQL source of truth
→ authorize from DB result
```

Nếu cả Redis lẫn SQL đều unavailable, protected write operation nên fail closed/service unavailable theo threat model, không `return true`.

Để tránh Redis outage biến thành SQL stampede, fallback path có thể có:

- bounded concurrency;
- circuit breaker quanh clearly failing cache dependency chỉ để giảm repeated timeout cost;
- short local cache nếu threat model cho phép;
- capacity reserve cho authoritative authorization lookup.

Nhưng circuit breaker không được chuyển failure thành allow.

- Microsoft Learn — Policy-based authorization in ASP.NET Core: `https://learn.microsoft.com/aspnet/core/security/authorization/policies`

## Giải thích thiết kế sau khi sửa

Authorization result phụ thuộc vào security context. Cache key vì vậy phải phản ánh context đó. Trong multi-tenant system, `(userId)` không đủ nếu cùng identity có roles khác nhau theo tenant.

Redis chỉ nên giảm latency/load. Nó không được trở thành nơi quyết định “khi lỗi thì user được phép”. Source of truth vẫn là database hoặc authorization authority đã được xác định.

Revoke semantics phải được thiết kế rõ:

```text
What is the maximum acceptable stale authorization window?
```

Nếu câu trả lời là 5 phút, TTL 3–4 phút + explicit invalidation có thể đủ. Nếu câu trả lời là “gần như ngay lập tức” cho financial approval, cần stronger validation/versioning ở critical path.

## Trade-offs

TTL ngắn tăng DB/cache churn nhưng giảm stale window. TTL dài giảm load nhưng kéo dài permission staleness.

Per-key locking/single-flight giảm stampede nhưng thêm state/coordination. Distributed lock qua Redis có thể phức tạp hơn chính lookup mà nó bảo vệ và tạo failure modes mới; chỉ dùng khi evidence cho thấy cần.

Versioning cho authorization tăng correctness visibility nhưng cần source-of-truth version lifecycle và strategy để client/request biết version hiện tại. Durable invalidation messaging tăng reliability nhưng cũng tăng operational complexity.

Fail-closed có thể làm một số protected operations unavailable khi authority unavailable. Đó là availability cost có chủ đích cho security-sensitive actions; với low-risk read path, product có thể chọn degraded semantics khác nếu threat model cho phép.

## Cách kiểm thử

1. **Tenant isolation test:** cùng `userId` có quyền khác nhau ở Tenant A/B; switch tenant liên tục và chạy concurrent requests; không bao giờ reuse permission set sai tenant.
2. **Revoke test:** warm cache với `finance.approve`, revoke trong DB, invalidate cache; đo thời gian tối đa tới khi request bị deny, bao gồm case invalidation cố tình fail.
3. **Redis failure test:** Redis timeout/unavailable; protected action fallback DB và không bao giờ auto-allow. Nếu DB cũng fail, behavior đúng fail-closed/service-unavailable contract.
4. **Stampede/load test:** expire một hot key rồi phát hàng trăm concurrent requests; đo số DB queries, latency và connection usage trước/sau single-flight/jitter strategy.
5. **Corrupt-cache test:** inject invalid JSON/wrong schema; system không authorize mặc định, cache entry bị bỏ/reload an toàn và telemetry phân loại đúng lỗi.

## Quan sát trong production

Nên theo dõi:

- authorization allow/deny counts theo policy, không log raw sensitive claims;
- cache hit/miss/error rate;
- DB fallback count/duration;
- cache invalidation success/failure;
- permission-cache age/version nếu design hỗ trợ;
- Redis latency/timeouts;
- per-key hotness ở dạng privacy-safe aggregation;
- SQL authorization query p95/p99;
- denied-after-revoke latency metric cho critical policies;
- cross-tenant invariant violations phải bằng 0;
- correlation ID cho admin permission change → cache invalidation → subsequent authorization decision.

Alert nên ưu tiên:

- fail-open path nếu bất kỳ code path nào còn tồn tại;
- invalidation failures liên tục;
- Redis outage kéo theo DB saturation;
- bất thường allow-rate của sensitive permission sau admin revoke.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business yêu cầu revoke `finance.approve` có hiệu lực dưới 10 giây trên 20 App Service instances, short TTL còn đủ không? Bạn sẽ thiết kế consistency boundary thế nào?
2. Nếu Redis outage làm toàn bộ traffic fallback SQL và SQL bắt đầu quá tải, bạn bảo vệ availability mà vẫn không bypass authorization bằng cách nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `async/await` không làm một pipeline tự động memory-efficient. Full materialization, large buffers và object lifetime vẫn tạo memory/GC pressure như thường.
- Export lớn nên được thiết kế theo bounded-memory data flow: projection → asynchronous enumeration → incremental serialization → response/file stream.
- Database round-trip count quan trọng không kém query latency; N+1 có thể biến một export logic đơn giản thành hàng triệu calls.
- Cancellation phải được propagate qua database, serialization và network boundary để client disconnect không tạo orphaned work.
- Cache key là một phần của correctness/security contract. Multi-tenant authorization cache thiếu tenant scope có thể trở thành broken authorization.
- Redis là optimization, không phải lý do để fail-open. Security-sensitive authorization cần source of truth, explicit stale-window policy và safe failure behavior.
- TTL chỉ giới hạn freshness theo thời gian; nó không thay thế invalidation/versioning khi revoke semantics nghiêm hơn.

## Mẫu tư duy cần nhớ
