# Câu 1 — Vì sao một `DbContext` scoped vẫn có thể gây lỗi concurrency khi dùng `Task.WhenAll`?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, async/await, EF Core, dependency injection lifetime, DbContext, concurrency, production debugging

## Bối cảnh

Một ASP.NET Core API dùng EF Core và đăng ký `OrdersDbContext` theo scoped lifetime mặc định. Team muốn giảm latency của endpoint dashboard nên chạy ba truy vấn độc lập song song:

```csharp
public async Task<DashboardDto> GetDashboardAsync(CancellationToken ct)
{
    var recentOrdersTask = _db.Orders
        .OrderByDescending(x => x.CreatedAtUtc)
        .Take(20)
        .ToListAsync(ct);

    var pendingCountTask = _db.Orders
        .CountAsync(x => x.Status == OrderStatus.Pending, ct);

    var revenueTask = _db.Orders
        .Where(x => x.Status == OrderStatus.Paid)
        .SumAsync(x => x.TotalAmount, ct);

    await Task.WhenAll(recentOrdersTask, pendingCountTask, revenueTask);

    return new DashboardDto(
        recentOrdersTask.Result,
        pendingCountTask.Result,
        revenueTask.Result);
}
```

Ở local endpoint thường chạy được khi dữ liệu nhỏ. Trong staging, thỉnh thoảng request fail với lỗi liên quan tới một operation thứ hai bắt đầu trên cùng context trước khi operation trước hoàn tất. Một developer đề xuất đổi `OrdersDbContext` thành singleton để “mọi task dùng cùng instance ổn định hơn”. Developer khác đề xuất bọc toàn bộ bằng `lock`.

Chưa biết database latency, connection-pool pressure và việc ba query thực sự có đáng chạy song song hay không.

## Câu hỏi chính

Hãy giải thích internal behavior dẫn đến lỗi, phân tích các giả định sai trong hai đề xuất trên, và đưa ra cách thiết kế/điều tra phù hợp trước khi quyết định có parallelize ba database operations hay không.

## Câu hỏi làm rõ nên cân nhắc

1. Endpoint hiện có latency breakdown nào cho từng query và tổng request chưa?
2. Database/provider và connection-pool pressure ở staging ra sao?
3. Ba query có cần cùng transaction/snapshot consistency không?
4. Endpoint có throughput cao đến mức tăng số concurrent DB commands sẽ gây pressure đáng kể không?
5. Có thể thay ba round trips bằng một projection/query phù hợp hay không?

## Gợi ý tư duy

### Gợi ý 1

Scoped lifetime có nghĩa là một context cho request scope; nó không biến object đó thành thread-safe hoặc cho phép nhiều operations đồng thời.

### Gợi ý 2

Phân biệt concurrency ở tầng `Task` với khả năng một `DbContext`/database connection thực thi nhiều operations đồng thời. Xem thêm change tracker, connection usage và unit-of-work semantics.

### Gợi ý 3

Nếu thật sự cần parallel database work, mỗi operation cần independent context/lifetime phù hợp; nhưng trước đó phải đo xem parallelism có cải thiện end-to-end latency hay chỉ chuyển bottleneck xuống database/pool.

## Cấu trúc trả lời đề xuất

1. Xác nhận triệu chứng và scope/lifetime hiện tại.
2. Giải thích `DbContext` concurrency semantics.
3. Phân tích `Task.WhenAll` trong đoạn code.
4. Bác bỏ singleton và global locking.
5. Đo latency/query plan/pool trước khi tối ưu.
6. So sánh sequential queries, query consolidation và independent contexts.
7. Chọn phương án dựa trên consistency + load.
8. Test dưới concurrency/load.
9. Theo dõi production telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `DbContext` không được thiết kế cho multiple parallel operations trên cùng instance.
- Scoped không đồng nghĩa thread-safe.
- Singleton `DbContext` còn nguy hiểm hơn vì chia sẻ mutable change tracker/state qua requests và lifetime quá dài.
- `lock` quanh asynchronous database work là sai hướng; serialize work có thể loại concurrency nhưng tạo contention và không giải quyết thiết kế/lifetime đúng.
- Không mặc định parallel query nhanh hơn; phải đo database/pool impact.

### Điểm cộng

- Nhận ra mỗi independent context thường lấy connection riêng từ pool khi operation cần connection, nên parallelism có thể tăng pool/database pressure.
- Đề xuất `IDbContextFactory<TContext>` hoặc scope riêng khi có lý do chính đáng cho independent concurrent units of work.
- Cân nhắc consistency: ba contexts/query ở các thời điểm khác nhau có thể tạo dashboard không cùng snapshot.
- Cân nhắc projection/aggregate query hoặc read model nếu dashboard là hot path.

### Senior+

- Phân tích queueing effect: giảm latency một request bằng cách tăng DB concurrency có thể làm p95/p99 toàn hệ thống xấu hơn.
- Phân biệt CPU parallelism với I/O concurrency.
- Đề xuất load test theo realistic connection-pool/database capacity thay vì microbenchmark method đơn lẻ.

## Hướng giải quyết tham khảo

`DbContext` đại diện một unit of work có mutable state như change tracker và không hỗ trợ việc khởi chạy nhiều EF Core operations song song trên cùng instance. Trong đoạn code, ba `ToListAsync`/`CountAsync`/`SumAsync` được khởi động trước khi operation trước được await hoàn tất. `Task.WhenAll` không làm context trở nên concurrency-safe.

Scoped lifetime phù hợp với nhiều web request scenarios vì mỗi request có context riêng, nhưng trong chính request đó ba tasks vẫn chia sẻ `_db`. Chuyển sang singleton sẽ mở rộng sharing sang nhiều requests, tăng concurrency bugs, stale tracked entities và memory/lifetime problems. Đây không phải fix.

`lock` cũng không phải giải pháp tốt cho async I/O. Nếu serialize ba query thì viết sequential awaits rõ ràng hơn; không nên giữ monitor lock qua async boundary. Nếu mục tiêu là giảm latency, trước hết đo duration từng query, SQL generated, execution plan, database waits và connection-pool metrics.

Có ba hướng hợp lý tùy evidence:

- Nếu query nhanh và endpoint không critical: chạy sequential để giữ solution đơn giản.
- Nếu có thể lấy dữ liệu bằng projection/read-model/query consolidation với semantics rõ ràng: giảm round trips thay vì tăng concurrency.
- Nếu ba operations thực sự độc lập, latency cao do I/O và database có capacity: dùng independent `DbContext` instances, ví dụ qua `IDbContextFactory<OrdersDbContext>`, rồi `Task.WhenAll`. Mỗi context là independent unit of work. Phải load-test vì mỗi concurrent operation có thể cần một pooled connection và tạo thêm database concurrency.

Nếu requirement cần consistent snapshot giữa các số liệu, ba independent contexts có thể không đáp ứng. Khi đó cần xác định isolation/transaction/read-model strategy thay vì chỉ tối ưu latency.

Testing nên gồm integration test với database thật, concurrent requests, cancellation và load test. Production telemetry cần request p50/p95/p99, dependency durations, SQL/query identifiers, pool exhaustion symptoms, DB CPU/waits và error rate.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không đổi `DbContext` sang singleton. Vấn đề là ba EF operations đang chạy đồng thời trên cùng scoped context; scoped chỉ xác định lifetime theo request, không làm context thread-safe. `Task.WhenAll` khởi tạo concurrency nhưng context có mutable state và EF Core không cho phép multiple parallel operations trên cùng instance.

Trước khi sửa bằng parallel contexts, em sẽ đo từng query và database pressure. Nếu ba query chỉ vài milliseconds thì sequential có thể đơn giản và throughput tốt hơn. Nếu round trip là bottleneck, em sẽ xem có thể projection hoặc tạo read model để giảm query không. Chỉ khi các query độc lập, consistency cho phép và database còn capacity, em mới tạo context riêng cho từng operation bằng factory rồi chạy concurrent.

Em cũng kiểm tra connection pool, DB CPU/waits và p95/p99 vì tối ưu latency một request bằng ba concurrent DB commands có thể làm throughput toàn hệ thống tệ hơn. Sau thay đổi em sẽ integration/load test và theo dõi dependency telemetry trong Application Insights.”

## Câu hỏi đào sâu

1. Nếu dùng ba `DbContext` riêng nhưng connection pool bắt đầu exhaustion dưới load, bạn sẽ xử lý thế nào?
2. Nếu Product yêu cầu ba giá trị dashboard phải phản ánh cùng một logical snapshot, thiết kế parallel contexts còn phù hợp không?
3. Một developer nói “database hỗ trợ Multiple Active Result Sets nên một `DbContext` chắc chắn chạy parallel được”; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Nói scoped context là thread-safe vì mỗi request chỉ có một thread.
- Chuyển context thành singleton.
- Dùng `Task.Run` cho EF Core I/O để “tạo thread riêng”.
- Mặc định ba query song song luôn nhanh hơn.
- Chỉ sửa exception mà không đo pool/database impact và consistency.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất `lock`, singleton hoặc `Task.Run`, không hiểu context concurrency.
- **3–4:** Nhận ra không dùng cùng context song song nhưng giải thích cơ chế/impact còn yếu.
- **5–6:** Đề xuất context riêng hoặc sequential đúng, có testing cơ bản.
- **7–8:** Có measurement, connection-pool/database reasoning, consistency và trade-offs.
- **9–10:** Phân tích end-to-end throughput/p95, unit-of-work semantics, alternatives đơn giản hơn và verification/observability rõ ràng.

# Câu 2 — Sau deployment, API p99 tăng mạnh nhưng CPU vẫn thấp

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure App Service, Application Insights, SQL Server, HTTP dependencies, connection pooling, incident investigation, observability

## Bối cảnh

Một ASP.NET Core API chạy trên Azure App Service on Linux, nhiều instances sau autoscale. Sau một deployment buổi sáng, median latency gần như không đổi nhưng p99 của endpoint `POST /api/bookings/confirm` tăng từ mức bình thường lên nhiều giây. Một phần requests trả 5xx/timeouts. CPU trên App Service chỉ khoảng mức trung bình và memory không tăng rõ rệt.

Endpoint thực hiện validation, đọc/ghi SQL Server và gọi một third-party reservation API qua HTTP. Deployment có cả application code và configuration changes. Team đã rollback application artifact nhưng triệu chứng chỉ giảm một phần. Không có bằng chứng đủ để kết luận SQL hay third-party là root cause.

Business impact: một số users không confirm được booking; retry từ frontend có nguy cơ tạo duplicate confirmations nếu backend/downstream không idempotent.

## Câu hỏi chính

Bạn sẽ điều hành investigation và stabilization như thế nào để thu hẹp root cause dựa trên evidence, đồng thời giảm user impact mà không tạo thêm duplicate booking?

## Câu hỏi làm rõ nên cân nhắc

1. 5xx cụ thể là application exception, gateway timeout hay client cancellation?
2. Deployment thay đổi những configuration nào ngoài artifact: connection string, HTTP timeout, DNS/network, feature flags, instance settings?
3. Dependency telemetry cho SQL và third-party thay đổi ra sao ở p95/p99?
4. Request có idempotency key hoặc booking state transition chống retry duplicate không?
5. Có correlation giữa slow requests với một App Service instance, region, SQL connection, downstream host hoặc deployment slot không?

## Gợi ý tư duy

### Gợi ý 1

CPU thấp không loại trừ saturation. Request có thể đang chờ I/O, connection, socket, lock hoặc downstream dependency.

### Gợi ý 2

Tách request latency thành server processing và dependency spans. So sánh trước/sau deployment, theo instance và outcome.

### Gợi ý 3

Rollback artifact không rollback mọi thứ. Configuration, schema, external dependency behavior và retry traffic có thể tồn tại độc lập với binary version.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và duplicate risk.
2. Stabilize: traffic/retry controls, feature rollback/disable nếu an toàn.
3. Xác định deployment/config/schema delta.
4. Phân đoạn telemetry theo dependency, instance, status và percentile.
5. Lập nhiều hypotheses.
6. Kiểm chứng từng hypothesis bằng traces/metrics/database/network evidence.
7. Thực hiện remediation nhỏ, reversible.
8. Verify bằng p95/p99 và business success rate.
9. Bổ sung idempotency/tests/alerts để ngăn tái diễn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không suy luận “CPU thấp nên app không có vấn đề”.
- Stabilization phải tránh blind retries gây duplicate.
- So sánh before/after deployment và dependency telemetry.
- Điều tra cả SQL, HTTP dependency, connection pools, configuration và instance-specific behavior.
- Rollback binary không đủ để chứng minh code không liên quan hoặc rollback hoàn chỉnh.

### Điểm cộng

- Dùng distributed tracing/correlation để phân rã latency.
- Kiểm tra SQL waits/blocking, connection acquisition, query duration và pool symptoms.
- Kiểm tra HTTP connection reuse, timeout/retry configuration, DNS/network và downstream latency/error rate.
- Phân tích p50 ổn nhưng p99 xấu như dấu hiệu tail-latency/partial saturation/failure subset.
- Có deployment slot/canary/feature flag strategy.

### Senior+

- Đặt business metric như successful confirmations/minute cạnh technical metrics.
- Phân tích retry amplification: timeout → client retry → thêm load → tail latency tăng → thêm retry.
- Thiết kế idempotency boundary cho confirmation để stabilization/retry an toàn.
- Xác định telemetry nào có thể falsify từng hypothesis thay vì chỉ “check logs”.

## Hướng giải quyết tham khảo

Đầu tiên cần giảm blast radius. Nếu có feature flag cho phần mới hoặc configuration có thể revert độc lập, revert thay đổi nhỏ nhất có khả năng liên quan. Nếu downstream đang timeout, không tăng retry một cách mù quáng. Confirmation cần idempotency key/business constraint để user retry không tạo booking thứ hai. Nếu chưa có guarantee đó, UI/backend retry policy phải thận trọng trong incident.

Tiếp theo lấy deployment diff đầy đủ: artifact, environment variables, App Service settings, connection strings, timeout/retry configuration, database migration và feature flags. Việc rollback artifact chỉ giảm một phần triệu chứng gợi ý configuration/schema/traffic hoặc external dependency vẫn có thể tham gia, nhưng chưa đủ để kết luận.

Trong Application Insights, tách slow traces của endpoint theo instance và xem dependency spans. Nếu request 8 giây trong đó HTTP dependency chiếm 7.5 giây, hướng điều tra khác với việc SQL dependency chờ 7 giây. So sánh percentile trước/sau release thay vì average.

Các hypothesis nên chạy song song có kiểm soát:

- SQL blocking/slow plan/connection-pool wait.
- Third-party latency hoặc timeout/retry thay đổi.
- HTTP connection handling/configuration regression.
- Một subset App Service instances có config/network khác.
- Application-level lock/semaphore hoặc ThreadPool/queueing dù CPU thấp.
- Database migration/schema/index change.
- Retry storm sau initial failure.

Với SQL, kiểm tra dependency duration, active connections, waits/blocking/deadlocks, execution plans và query regression. Với HTTP, kiểm tra downstream duration/status, timeout/retry count, connection reuse và network/DNS evidence. Với app, kiểm tra request queueing, ThreadPool metrics nếu có, exceptions và per-instance distribution.

Fix nên reversible và evidence-driven. Sau remediation, verify không chỉ average latency mà p95/p99, success rate, timeout rate, duplicate confirmation count và downstream/database health. Sau incident bổ sung idempotency, release/config diff auditability, synthetic confirmation path nếu phù hợp, failure injection và alert theo tail latency/business failures.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xử lý đây là tail-latency incident chứ không nhìn CPU rồi loại app ra. Trước tiên em bảo vệ business flow: hạn chế retry không kiểm soát và xác minh confirmation có idempotency để user retry không tạo booking trùng. Nếu release có feature/config mới có thể disable an toàn, em rollback phần đó theo blast radius nhỏ nhất.

Sau đó em lấy full deployment diff, vì rollback artifact không rollback environment settings hay migration. Trong Application Insights em chọn slow traces và phân rã thời gian giữa app, SQL và third-party, đồng thời group theo instance/status. Em tạo vài hypothesis cạnh tranh: SQL blocking/pool wait, downstream latency, HTTP timeout/retry regression, instance config mismatch hoặc queueing trong app.

Mỗi hypothesis phải có evidence: SQL waits/execution plan, dependency spans, connection metrics, downstream status và per-instance correlation. Khi có root cause em áp dụng fix reversible rồi verify p95/p99, confirmation success rate và duplicate count. Sau incident em bổ sung idempotency, release telemetry và failure-path/load tests để retry không biến một dependency failure thành retry storm.”

## Câu hỏi đào sâu

1. Nếu traces cho thấy SQL duration thấp nhưng request duration vẫn cao trước khi SQL span bắt đầu, bạn sẽ điều tra gì tiếp?
2. Nếu third-party API chậm nhưng business không cho phép bỏ call đó, bạn thiết kế timeout/retry/circuit behavior thế nào mà không duplicate confirmation?
3. Bạn có tăng App Service instance count ngay không? Trong trường hợp nào scale-out giúp và trường hợp nào làm SQL/downstream tệ hơn?

## Lỗi trả lời thường gặp

- Scale-out ngay chỉ vì latency cao.
- Kết luận SQL chậm mà không có dependency/query evidence.
- Tăng timeout và retry đồng thời, làm incident kéo dài hơn.
- Chỉ xem average latency thay vì p95/p99 và slow traces.
- Bỏ qua configuration/migration vì artifact đã rollback.

## Thang điểm 0–10

- **0–2:** Guess root cause và đưa fix ngay.
- **3–4:** Có logs/metrics nhưng investigation không có structure.
- **5–6:** Có stabilization, dependency tracing và multiple hypotheses.
- **7–8:** Có percentile, SQL/HTTP/pool reasoning, retry/idempotency và verification.
- **9–10:** Điều hành incident theo evidence, falsifiable hypotheses, business metrics, reversible remediation và prevention hoàn chỉnh.

# Câu 3 — Chọn kiến trúc cho nền tảng xử lý tài liệu: App Service, Functions hay Kubernetes?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** architecture, Azure App Service, Azure Functions, Azure Blob Storage, Azure Service Bus, background processing, security, reliability, observability, cost of complexity

## Bối cảnh

Một enterprise portal cần thêm chức năng upload tài liệu và xử lý nền. User upload file từ web; hệ thống cần virus/security validation do một service nội bộ đảm nhiệm, trích metadata, tạo preview và cập nhật trạng thái để frontend hiển thị. Một số file xử lý vài giây, một số có thể mất vài phút. Traffic bình thường thấp nhưng có burst vào cuối tháng.

Hệ thống hiện là ASP.NET Core modular monolith chạy Azure App Service. Team đã dùng Azure Blob Storage và Azure Service Bus ở một số integration khác. Một architect đề xuất tách toàn bộ thành microservices chạy Kubernetes vì “sắp có workload background”. Một developer khác muốn xử lý mọi thứ trực tiếp trong HTTP request để giữ consistency đơn giản.

Yêu cầu chưa rõ về maximum file size, throughput peak, preview SLA, data residency, retry policy và khả năng security scanner bị unavailable.

## Câu hỏi chính

Hãy thiết kế solution phù hợp và giải thích khi nào bạn chọn App Service + background worker, Azure Functions, hoặc Kubernetes. Bạn phải nêu rõ assumptions, boundaries, failure behavior, security, observability và lý do không tự động chọn kiến trúc phức tạp nhất.

## Câu hỏi làm rõ nên cân nhắc

1. File size distribution, peak uploads/minute và processing duration thực tế là bao nhiêu?
2. User cần synchronous result hay chỉ cần upload acknowledgement + eventual processing status?
3. Scanner/preview dependencies có idempotent không, timeout và rate limit thế nào?
4. File có dữ liệu nhạy cảm, retention/residency/authorization constraints nào?
5. Team hiện có operational maturity và nhu cầu nào thực sự đòi Kubernetes-specific capabilities?

## Gợi ý tư duy

### Gợi ý 1

Tách lifecycle của upload khỏi lifecycle của processing. HTTP request không nên sở hữu công việc nhiều phút nếu business cho phép asynchronous completion.

### Gợi ý 2

Blob Storage phù hợp lưu file; queue/message có thể decouple processing. Nhưng messaging kéo theo retry, duplicate delivery, poison work và idempotency.

### Gợi ý 3

Hosting choice là hệ quả của workload/operational requirements. Kubernetes không phải prerequisite cho background processing.

## Cấu trúc trả lời đề xuất

1. Làm rõ SLA, file/traffic/security constraints.
2. Xác định API và user-visible state machine.
3. Chọn upload path và storage permissions.
4. Thiết kế asynchronous processing boundary.
5. Thiết kế idempotency/retry/DLQ.
6. So sánh Worker/App Service, Functions và Kubernetes.
7. Thiết kế data/state consistency.
8. Security và least privilege.
9. Observability/operations.
10. Testing, rollout và criteria để thay đổi architecture sau này.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giữ HTTP request nhiều phút nếu asynchronous UX được chấp nhận.
- Blob + durable work queue/message là một option tự nhiên nhưng phải xử lý duplicate/retry.
- Có trạng thái processing rõ ràng: Uploaded/Queued/Scanning/Processing/Completed/Failed hoặc tương đương.
- Managed Identity/least privilege và upload authorization.
- So sánh hosting theo requirement, không theo trend.

### Điểm cộng

- Cân nhắc direct-to-Blob upload bằng scoped access mechanism khi phù hợp để giảm backend proxy load, nhưng authorization và upload completion phải được thiết kế cẩn thận.
- Idempotent processing theo document ID + processing version.
- DLQ/manual recovery cho poison work.
- Worker có backpressure/concurrency limits theo scanner/downstream capacity.
- Correlation ID từ upload → message → processing → status.

### Senior+

- Phân tích state transition và race giữa re-upload/reprocess/delete.
- Xem malware scan như trust boundary: file chưa scan không được phục vụ như trusted content.
- Nêu migration trigger cụ thể từ App Service/Functions sang Kubernetes thay vì “scale lớn”.
- Định nghĩa SLO và queue-age alert thay vì chỉ CPU alert.

## Hướng giải quyết tham khảo

Một thiết kế ban đầu hợp lý có thể giữ modular monolith cho API và thêm asynchronous processor thay vì lập tức chuyển microservices/Kubernetes.

Upload API xác thực user và tạo `Document` record với trạng thái ban đầu. File được đưa vào Blob Storage với naming/metadata không dựa vào filename không tin cậy. Nếu dùng direct upload, backend cấp quyền upload scope/time giới hạn phù hợp và chỉ chuyển state sau khi xác minh blob hợp lệ. File chưa security scan không được expose như trusted downloadable content.

Sau upload completion, hệ thống enqueue một work message chứa document ID/version, không nhét file bytes lớn vào message. Processor lấy blob, gọi scanner, trích metadata/preview, lưu outputs và update state. Consumer phải idempotent vì message có thể được deliver lại. Retry chỉ áp dụng transient failures; poison/permanent failures đi DLQ hoặc state Failed với recovery workflow.

Về hosting:

- **App Service + Worker/BackgroundService riêng:** phù hợp nếu team đã vận hành App Service tốt, workload không đòi event-specific serverless scaling và muốn operational model đơn giản. Nên tách worker process/deployment nếu CPU/memory/scale characteristics khác web API.
- **Azure Functions:** hợp lý nếu trigger-driven processing, bursty workload và execution model của từng processing step phù hợp với Functions. Cần xác minh runtime/hosting constraints hiện hành cho workload cụ thể trước khi chọn, đặc biệt với long-running/CPU-heavy processing.
- **Kubernetes:** chỉ nên chọn nếu organization đã có platform maturity hoặc workload cần scheduling/isolation/networking/deployment capabilities mà simpler hosting không đáp ứng. Background job tự nó không đủ lý do.

Service Bus giúp decouple và buffer burst, nhưng phải thiết kế message lock/retry/idempotency/DLQ theo processing duration. Nếu một processing step mất lâu hoặc dependency scanner giới hạn concurrency, worker cần explicit concurrency/backpressure. Có thể chia pipeline thành stages chỉ khi ownership/retry characteristics thực sự cần; không tách microservice chỉ vì mỗi bước có tên khác nhau.

State database cần optimistic concurrency/version để tránh processor cũ overwrite kết quả của một re-upload/reprocess mới. Security dùng Managed Identity cho Blob/Service Bus/Key Vault access với least privilege. Không log file contents hoặc sensitive metadata.

Observability gồm upload success rate, queue depth/oldest message age, processing duration percentile theo stage, scanner dependency failures, retry/DLQ count, document stuck-state count và end-to-end time-to-ready. Distributed tracing/correlation gắn document ID/version với message và dependency calls.

## Mẫu trả lời trong phỏng vấn

“Em sẽ chưa chọn Kubernetes. Trước hết em làm rõ file size, burst, processing SLA và security constraints. Nếu user chỉ cần upload rồi chờ trạng thái, em tách HTTP lifecycle khỏi processing: API xác thực và lưu metadata, file vào Blob, sau đó enqueue document ID/version lên Service Bus. Worker xử lý scan, metadata và preview rồi cập nhật state.

Consumer phải idempotent vì message có thể retry. Em có state machine và version để một retry hoặc job cũ không overwrite re-upload mới. File chưa scan sẽ ở untrusted boundary và không được serve như content an toàn. Managed Identity cấp least privilege tới Blob, queue và secrets.

Về hosting, nếu workload vừa phải và team đã quen App Service, em có thể chạy worker deployment riêng trên App Service/appropriate worker host. Functions hợp lý nếu trigger/burst model phù hợp sau khi xác minh execution constraints. Kubernetes chỉ khi có requirement cụ thể như platform standard, isolation/scheduling hoặc operational capabilities mà hai lựa chọn đơn giản không đáp ứng.

Em sẽ theo dõi queue age, processing p95/p99, retries, DLQ và time-to-ready. Nếu telemetry sau này chứng minh hosting hiện tại là bottleneck, lúc đó mới nâng architecture dựa trên evidence.”

## Câu hỏi đào sâu

1. Nếu scanner nội bộ unavailable 30 phút, hệ thống nên phản hồi user và xử lý queue như thế nào?
2. Nếu preview generation trở thành CPU-heavy và ảnh hưởng worker throughput, bạn thay đổi topology/hosting ra sao?
3. Product yêu cầu “upload xong phải thấy preview trong 2 giây”; bạn có bỏ asynchronous architecture không, hay thay đổi contract/pipeline thế nào?

## Lỗi trả lời thường gặp

- Chọn Kubernetes/microservices chỉ vì workload background.
- Đưa file bytes lớn trực tiếp vào queue message mà không cân nhắc storage/message contract.
- Có retry nhưng không có idempotency/DLQ.
- Cho phép download file trước security scan mà không xác định trust boundary.
- Chỉ monitor CPU thay vì queue age và end-to-end processing SLO.

# Tổng kết hôm nay

## Kiến thức trọng tâm

`DbContext` lifetime và concurrency là hai khái niệm khác nhau: scoped lifetime không làm một mutable unit of work trở nên concurrency-safe. Parallel I/O chỉ có giá trị khi bottleneck, consistency và downstream capacity cho phép.

Trong production incident, tail latency phải được phân rã bằng telemetry thay vì suy đoán từ CPU. Rollback application binary không nhất thiết rollback configuration, schema hoặc external-system behavior.

Ở architecture level, asynchronous processing không đồng nghĩa phải dùng Microservices hoặc Kubernetes. Hosting phải được chọn từ workload, failure modes, operational maturity và SLO; complexity là một cost cần chứng minh.

## Mẫu tư duy cần nhớ

- Lifetime không đồng nghĩa thread safety.
- Measure before parallelizing or optimizing.
- Stabilize, collect evidence, then narrow competing hypotheses.
- Design retry together with idempotency and failure recovery.
- Chọn kiến trúc đơn giản nhất đáp ứng requirement và chỉ tăng complexity khi có evidence.
