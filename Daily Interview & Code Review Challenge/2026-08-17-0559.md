# Code Review Challenge 1 — Consumer RabbitMQ xử lý thanh toán trùng khi retry

**Chủ đề:** Idempotency, concurrency, EF Core transaction, message processing, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core worker nhận sự kiện `PaymentConfirmed` từ RabbitMQ. Mỗi sự kiện phải cập nhật invoice, ghi payment history và gửi email xác nhận. RabbitMQ có thể redeliver message nếu consumer mất kết nối hoặc process chết trước khi ACK. Hệ thống chạy 4 replica, khoảng 30–100 message/giây lúc cao điểm.

Production thỉnh thoảng xuất hiện hai `PaymentHistory` cho cùng một payment, email gửi hai lần, và hiếm hơn là invoice có trạng thái không khớp với history. Team cho rằng kiểm tra `AnyAsync()` trước khi insert đã đủ chống duplicate.

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly BillingDbContext _db;
    private readonly IEmailService _emailService;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        BillingDbContext db,
        IEmailService emailService,
        ILogger<PaymentConsumer> logger)
    {
        _db = db;
        _emailService = emailService;
        _logger = logger;
    }

    public async Task HandleAsync(PaymentConfirmed message)
    {
        if (await _db.PaymentHistories
            .AnyAsync(x => x.ExternalPaymentId == message.PaymentId))
        {
            return;
        }

        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == message.InvoiceId);

        invoice.Status = InvoiceStatus.Paid;
        invoice.PaidAt = DateTime.UtcNow;

        _db.PaymentHistories.Add(new PaymentHistory
        {
            InvoiceId = invoice.Id,
            ExternalPaymentId = message.PaymentId,
            Amount = message.Amount,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        await _emailService.SendPaymentConfirmationAsync(
            invoice.CustomerEmail,
            invoice.Id,
            message.Amount);

        _logger.LogInformation(
            "Payment {PaymentId} processed for invoice {InvoiceId}",
            message.PaymentId,
            message.InvoiceId);
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-insert không atomic

- **Problem:** `AnyAsync()` và `SaveChangesAsync()` tách rời.
- **Why:** Hai consumer có thể cùng đọc trạng thái “chưa tồn tại”, sau đó cùng insert.
- **Impact:** duplicate payment history và side effect lặp.
- **Severity:** Critical.
- **Fix:** đặt unique constraint/index trên `ExternalPaymentId` (hoặc business idempotency key thích hợp), coi database là hàng rào correctness cuối cùng và xử lý unique-violation như duplicate hợp lệ.

### 2. Không có idempotency guarantee ở database

- **Problem:** correctness phụ thuộc hoàn toàn vào query phía application.
- **Why:** application-level pre-check không bảo vệ trước concurrency, nhiều process hoặc code path khác.
- **Impact:** dữ liệu tài chính trùng và khó reconcile.
- **Severity:** Critical.
- **Fix:** unique constraint phù hợp business invariant.

### 3. DB commit và gửi email tạo dual-write problem

- **Problem:** database đã commit nhưng email có thể fail hoặc process có thể chết trước khi hoàn thành side effect.
- **Why:** DB transaction không bao phủ external email provider.
- **Impact:** retry có thể skip message vì history đã tồn tại nhưng email chưa từng được gửi; hoặc cách retry khác có thể gửi email lặp.
- **Severity:** High.
- **Fix:** transactional outbox: cùng transaction ghi business state và `OutboxMessage`; dispatcher riêng gửi email với retry/idempotency.

### 4. Không truyền `CancellationToken`

- **Problem:** database và external call không nhận cancellation signal.
- **Why:** shutdown/cancel không propagate xuống I/O.
- **Impact:** graceful shutdown chậm, công việc có thể tiếp tục sau khi consumer đang bị dừng.
- **Severity:** Medium.
- **Fix:** nhận và truyền `CancellationToken` xuyên suốt.

### 5. Không validate quan hệ giữa invoice và payment

- **Problem:** code tin rằng `InvoiceId`, amount và payment ID đều hợp lệ.
- **Why:** message được xem như trusted state.
- **Impact:** có thể đánh dấu paid cho invoice sai hoặc amount không đúng business rule.
- **Severity:** High.
- **Fix:** validate business invariants, currency/amount và trạng thái invoice; quy định rõ partial/over-payment nếu có.

### 6. `SingleAsync()` biến missing invoice thành exception không được phân loại

- **Problem:** không có policy cho permanent failure và transient failure.
- **Why:** mọi lỗi có thể bị broker/job framework retry giống nhau.
- **Impact:** poison message retry vô hạn hoặc tạo noise.
- **Severity:** Medium.
- **Fix:** phân loại lỗi, retry transient có backoff; permanent failure đưa DLQ/quarantine và alert.

### 7. Side effect không có identity riêng

- **Problem:** email không gắn một operation/message ID để deduplicate.
- **Why:** retry dispatcher có thể gọi provider nhiều lần.
- **Impact:** khách hàng nhận email lặp.
- **Severity:** Medium.
- **Fix:** outbox record có stable ID; nếu provider hỗ trợ idempotency key thì dùng nó, nếu không phải lưu trạng thái gửi và thiết kế retry phù hợp.

### 8. Observability chưa đủ cho message lifecycle

- **Problem:** chỉ log success cuối cùng.
- **Why:** không có message ID, delivery attempt, duplicate detection, processing duration hoặc failure classification.
- **Impact:** khó xác định duplicate bắt nguồn từ broker, consumer hay side effect dispatcher.
- **Severity:** Medium.
- **Fix:** structured logging + tracing + metrics theo message/outbox lifecycle.

## Phiên bản code đề xuất

```csharp
public sealed class PaymentConsumer
{
    private readonly BillingDbContext _db;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        BillingDbContext db,
        ILogger<PaymentConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        PaymentConfirmed message,
        CancellationToken cancellationToken)
    {
        var invoice = await _db.Invoices
            .SingleOrDefaultAsync(
                x => x.Id == message.InvoiceId,
                cancellationToken);

        if (invoice is null)
            throw new PermanentMessageException("Invoice does not exist.");

        if (message.Amount <= 0)
            throw new PermanentMessageException("Invalid payment amount.");

        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        try
        {
            invoice.Status = InvoiceStatus.Paid;
            invoice.PaidAt = DateTime.UtcNow;

            _db.PaymentHistories.Add(new PaymentHistory
            {
                InvoiceId = invoice.Id,
                ExternalPaymentId = message.PaymentId,
                Amount = message.Amount,
                CreatedAt = DateTime.UtcNow
            });

            _db.OutboxMessages.Add(new OutboxMessage
            {
                Id = Guid.NewGuid(),
                Type = "PaymentConfirmationEmail",
                AggregateId = invoice.Id.ToString(),
                Payload = JsonSerializer.Serialize(new
                {
                    invoice.CustomerEmail,
                    InvoiceId = invoice.Id,
                    message.Amount,
                    message.PaymentId
                }),
                CreatedAt = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
            await transaction.CommitAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsDuplicatePayment(ex))
        {
            await transaction.RollbackAsync(cancellationToken);

            _logger.LogInformation(
                "Duplicate payment ignored. PaymentId={PaymentId}",
                message.PaymentId);
        }
    }

    private static bool IsDuplicatePayment(DbUpdateException exception)
    {
        // Provider-specific inspection should identify the unique-constraint violation.
        return exception.InnerException is not null;
    }
}
```

Database phải enforce business invariant, ví dụ unique index trên `ExternalPaymentId`. Hàm `IsDuplicatePayment` ở trên chỉ minh họa boundary; production code phải kiểm tra mã lỗi/constraint cụ thể của SQL Server hoặc PostgreSQL thay vì coi mọi `DbUpdateException` là duplicate.

Outbox dispatcher xử lý email độc lập, retry có kiểm soát và đánh dấu outbox record đã hoàn thành.

## Trade-offs

Transactional outbox thêm table, dispatcher và cleanup policy nhưng loại bỏ khoảng hở giữa commit business data và enqueue side effect. Nếu hệ thống nhỏ và email không quan trọng, có thể chấp nhận eventual retry đơn giản hơn, nhưng payment state vẫn cần idempotency ở database. Distributed transaction với email provider thường không phải lựa chọn thực tế.

Unique constraint giải quyết correctness tốt hơn lock trong process vì hệ thống chạy nhiều replica. Nếu cùng một payment ID hợp lệ trên nhiều payment provider, key phải bao gồm provider hoặc tenant thay vì unique toàn cục.

## Cách kiểm thử

1. **Concurrency integration test:** gửi cùng `PaymentId` đồng thời qua nhiều consumer; DB chỉ có một payment history.
2. **Crash-window test:** giả lập process chết sau DB commit; outbox vẫn tồn tại và email được dispatcher xử lý sau restart.
3. **Duplicate delivery test:** redeliver cùng message nhiều lần; business state không thay đổi thêm.
4. **Failure-path test:** email provider timeout nhiều lần; payment vẫn đúng, outbox retry theo policy và không mất message.
5. **Database test:** xác nhận unique constraint thực sự chặn duplicate từ hai transaction cạnh tranh.

## Quan sát trong production

Theo dõi `payment_consumer_duration`, duplicate count, retry count, DLQ depth, outbox pending/oldest age, outbox failure count và email send latency. Trace nên liên kết broker message ID → DB transaction → outbox ID → email attempt. Alert khi oldest outbox age vượt SLO hoặc DLQ tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `SERIALIZABLE` transaction có thể giải quyết một phần race nhưng vẫn không thay thế business unique constraint và outbox?
2. Nếu payment provider gửi hai event khác ID nhưng đại diện cùng một giao dịch, bạn thiết kế idempotency key thế nào?
3. Outbox dispatcher chạy 5 replica thì làm sao tránh nhiều worker cùng claim một outbox record?

# Code Review Challenge 2 — API tìm nhân viên biến filter thành SQL injection và query quá tải

## Bối cảnh

Một internal ASP.NET Core API cho phép portal tìm nhân viên theo tên, office và sort field. Endpoint được gọi thường xuyên bởi autocomplete và admin page. Bảng `Employees` có hơn một triệu bản ghi lịch sử và active/inactive. Sau khi bổ sung dynamic sorting, production ghi nhận một số query chạy vài giây và CPU SQL tăng mạnh.

Endpoint trả cả email và số điện thoại. Team nói đây là “internal API” nên không cần quá nhiều validation. Authorization policy và giới hạn page size chưa được nêu rõ.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeeSearchController : ControllerBase
{
    private readonly SqlConnection _connection;
    private readonly ILogger<EmployeeSearchController> _logger;

    public EmployeeSearchController(
        SqlConnection connection,
        ILogger<EmployeeSearchController> logger)
    {
        _connection = connection;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? keyword,
        string? office,
        string sortBy = "DisplayName",
        int page = 1,
        int pageSize = 100)
    {
        var offset = (page - 1) * pageSize;

        var sql = $@"
            SELECT Id, DisplayName, Email, Mobile, OfficeCode
            FROM Employees
            WHERE IsDeleted = 0
              AND ('{keyword}' IS NULL OR DisplayName LIKE '%{keyword}%')
              AND ('{office}' IS NULL OR OfficeCode = '{office}')
            ORDER BY {sortBy}
            OFFSET {offset} ROWS
            FETCH NEXT {pageSize} ROWS ONLY";

        _logger.LogInformation("Executing employee search SQL: {Sql}", sql);

        var employees = (await _connection.QueryAsync<EmployeeDto>(sql)).ToList();

        return Ok(new
        {
            page,
            pageSize,
            employees
        });
    }
}
```

## Kết quả code review tham khảo

### 1. SQL injection qua `keyword` và `office`

- **Problem:** input được interpolate trực tiếp vào SQL.
- **Why:** user-controlled values trở thành SQL text.
- **Impact:** đọc/sửa dữ liệu trái phép tùy quyền DB account, query phá hoại hoặc data exfiltration.
- **Severity:** Critical.
- **Fix:** parameterized query.

### 2. SQL injection qua `sortBy`

- **Problem:** dynamic identifier được chèn trực tiếp vào `ORDER BY`.
- **Why:** SQL parameter thường dùng cho values, không phải tùy ý thay identifier/syntax.
- **Impact:** injection hoặc query ngoài dự kiến.
- **Severity:** Critical.
- **Fix:** map một allowlist API sort key → literal column expression do server kiểm soát.

### 3. Không thể hiện authorization cho dữ liệu PII

- **Problem:** endpoint trả `Email` và `Mobile` nhưng snippet không có authorization policy.
- **Why:** “internal” là network/location property, không phải authorization guarantee.
- **Impact:** người dùng không đủ quyền có thể enumerate PII.
- **Severity:** High.
- **Fix:** policy/role/permission phù hợp; cân nhắc field-level exposure theo use case.

### 4. Pagination không có validation/bounds

- **Problem:** `page <= 0`, `pageSize <= 0` hoặc page size rất lớn không bị chặn.
- **Why:** arithmetic/query cost phụ thuộc trực tiếp input.
- **Impact:** lỗi SQL, excessive memory/network, resource exhaustion.
- **Severity:** High.
- **Fix:** validate page >= 1 và giới hạn page size theo contract, ví dụ tối đa 100 nếu business chấp nhận.

### 5. `%keyword%` có thể tạo query scan đắt

- **Problem:** contains search trên bảng lớn thường khó tận dụng B-tree index thông thường để seek theo prefix.
- **Why:** wildcard ở đầu làm search pattern kém sargable đối với index thông thường.
- **Impact:** CPU/I/O SQL tăng khi traffic autocomplete lớn.
- **Severity:** High.
- **Fix:** xác định requirement; ưu tiên prefix search nếu phù hợp, search-specific indexing/full-text/search engine nếu thực sự cần contains ở scale lớn; đo execution plan trước khi chọn.

### 6. OFFSET pagination suy giảm ở deep pages

- **Problem:** database phải đi qua ngày càng nhiều row trước khi trả page sâu.
- **Why:** offset tăng theo page number.
- **Impact:** latency tăng với deep pagination.
- **Severity:** Medium.
- **Fix:** nếu use case cần duyệt sâu, cân nhắc keyset/cursor pagination với deterministic ordering.

### 7. Logging raw SQL chứa input và có thể chứa PII/search terms

- **Problem:** log toàn bộ SQL sau interpolation.
- **Why:** keyword/office được copy vào log.
- **Impact:** sensitive input leakage, log injection/noise và tăng log volume.
- **Severity:** Medium.
- **Fix:** structured log các metadata cần thiết; không log raw user-composed SQL.

### 8. Không truyền request cancellation

- **Problem:** query tiếp tục dù client disconnect hoặc request bị hủy.
- **Why:** `HttpContext.RequestAborted` không được truyền vào command.
- **Impact:** query tốn tài nguyên không còn giá trị dưới load.
- **Severity:** Medium.
- **Fix:** dùng `CommandDefinition` hoặc API tương đương có `CancellationToken`.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "EmployeeDirectory.Read")]
[ApiController]
[Route("api/employees")]
public sealed class EmployeeSearchController : ControllerBase
{
    private readonly SqlConnection _connection;
    private readonly ILogger<EmployeeSearchController> _logger;

    private static readonly IReadOnlyDictionary<string, string> SortColumns =
        new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
        {
            ["name"] = "DisplayName",
            ["office"] = "OfficeCode",
            ["id"] = "Id"
        };

    public EmployeeSearchController(
        SqlConnection connection,
        ILogger<EmployeeSearchController> logger)
    {
        _connection = connection;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? keyword,
        string? office,
        string sortBy = "name",
        int page = 1,
        int pageSize = 50,
        CancellationToken cancellationToken = default)
    {
        if (page < 1)
            return BadRequest("page must be >= 1");

        if (pageSize is < 1 or > 100)
            return BadRequest("pageSize must be between 1 and 100");

        if (!SortColumns.TryGetValue(sortBy, out var sortColumn))
            return BadRequest("Unsupported sort field");

        keyword = string.IsNullOrWhiteSpace(keyword) ? null : keyword.Trim();
        office = string.IsNullOrWhiteSpace(office) ? null : office.Trim();

        var offset = checked((page - 1) * pageSize);

        var sql = $@"
            SELECT Id, DisplayName, Email, Mobile, OfficeCode
            FROM Employees
            WHERE IsDeleted = 0
              AND (@Keyword IS NULL OR DisplayName LIKE @KeywordPattern)
              AND (@Office IS NULL OR OfficeCode = @Office)
            ORDER BY {sortColumn}, Id
            OFFSET @Offset ROWS
            FETCH NEXT @PageSize ROWS ONLY";

        var parameters = new
        {
            Keyword = keyword,
            KeywordPattern = keyword is null ? null : $"%{keyword}%",
            Office = office,
            Offset = offset,
            PageSize = pageSize
        };

        _logger.LogInformation(
            "Employee search requested. Office={Office}, Sort={Sort}, Page={Page}, PageSize={PageSize}",
            office,
            sortBy,
            page,
            pageSize);

        var command = new CommandDefinition(
            sql,
            parameters,
            cancellationToken: cancellationToken);

        var employees = (await _connection
            .QueryAsync<EmployeeDto>(command))
            .AsList();

        return Ok(new { page, pageSize, employees });
    }
}
```

`sortColumn` vẫn được interpolate, nhưng chỉ sau khi lấy từ server-controlled allowlist; user không cung cấp SQL fragment trực tiếp. Nếu autocomplete không cần `Mobile`, nên bỏ field này khỏi projection thay vì trả rồi để client bỏ qua.

## Trade-offs

OFFSET pagination đơn giản và phù hợp khi user chỉ xem vài page đầu. Keyset pagination hiệu quả hơn cho traversal sâu nhưng API phức tạp hơn và cần sort key ổn định.

Prefix search như `keyword%` thường dễ tối ưu bằng index hơn contains search, nhưng thay đổi semantics. Nếu business thực sự cần contains/fuzzy search thì phải chọn giải pháp dựa trên workload và execution plan, không chỉ đổi query vì performance.

Allowlist dynamic sort làm API ít linh hoạt hơn nhưng biến query shape thành thứ server kiểm soát. Đây là trade-off hợp lý cho public/internal HTTP boundary.

## Cách kiểm thử

1. **Security test:** thử payload injection ở `keyword`, `office`, `sortBy`; không payload nào thay đổi SQL structure.
2. **Authorization test:** user thiếu `EmployeeDirectory.Read` bị từ chối và không nhận PII.
3. **Boundary test:** page 0, pageSize 0, pageSize > max, unsupported sort đều trả lỗi contract phù hợp.
4. **Database/load test:** đo execution plan, logical reads và p95 latency với bảng có cardinality gần production, đặc biệt keyword contains.
5. **Cancellation test:** hủy request khi query đang chạy và xác nhận command nhận cancellation theo khả năng provider.

## Quan sát trong production

Theo dõi p50/p95/p99 latency, DB duration, timeout count, rows returned, page-size distribution, query execution statistics và authorization failures. Không ghi keyword nhạy cảm nếu không cần thiết. Trace HTTP request → SQL span để xác định thời gian nằm ở application hay database. Alert khi timeout/error rate hoặc DB CPU/reads vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao parameter hóa `ORDER BY @SortBy` không tương đương với việc parameter hóa một value trong `WHERE`?
2. Nếu requirement bắt buộc tìm substring trên vài triệu employee record, bạn sẽ benchmark và chọn giữa database full-text/search feature với search service như thế nào?
3. Nếu API cần sort theo `DisplayName` nhưng có nhiều tên giống nhau, vì sao cần secondary stable key cho pagination?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào một nguyên tắc production quan trọng: broker retry và multiple replicas khiến duplicate delivery trở thành tình huống phải thiết kế cho, không phải exception hiếm. Idempotency cần business key được enforce ở persistence layer; external side effect cần được tách khỏi DB commit bằng cơ chế như transactional outbox khi yêu cầu reliability đủ cao.

Challenge 2 nhấn mạnh rằng parameterization, authorization và query performance là ba lớp khác nhau. SQL values phải parameterize; dynamic identifiers phải allowlist; internal endpoint vẫn cần authorization; và một query an toàn về injection chưa chắc đã hiệu quả trên dataset lớn.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; đừng giả định message chỉ đến một lần.
- Đưa business invariant quan trọng xuống database constraint khi có concurrency.
- Khi có DB + external side effect, luôn tìm “failure window” giữa hai thao tác.
- Phân biệt user-controlled **value** với user-controlled **SQL syntax/identifier**.
- Security, performance và observability phải được xem là một phần của design, không phải bước bổ sung cuối cùng.
