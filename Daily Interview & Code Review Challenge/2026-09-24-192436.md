# Câu 1 — Vì sao Akamai vẫn trả nội dung cũ dù origin đã deploy đúng?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** HTTP caching, Akamai/CDN, Cache-Control, browser cache, validators, cache key, origin, ASP.NET Core, production debugging

## Bối cảnh

Một marketing website dùng ASP.NET Core làm origin và Akamai làm CDN. HTML của product landing page được render server-side. Sau một content release, Product team xác nhận gọi trực tiếp origin đã thấy nội dung mới, nhưng một số user ở các khu vực khác nhau vẫn thấy nội dung cũ trong khoảng 20–40 phút.

Response hiện có header tương tự:

```http
Cache-Control: public, max-age=300, s-maxage=1800
ETag: "product-481-v17"
Vary: Accept-Encoding
```

Team có cơ chế purge Akamai nhưng chưa rõ release vừa rồi purge URL nào. Một developer nói: “`max-age=300` nghĩa là mọi cache chắc chắn phải lấy lại dữ liệu sau 5 phút.” Người khác muốn thêm query string `?v=timestamp` vào mọi URL. Người thứ ba cho rằng `ETag` làm CDN không bao giờ giữ stale response.

Website còn có browser cache, CDN edge cache và origin. Một số URL có thể được truy cập với hostname, query string hoặc redirect khác nhau. Chưa có evidence về `Age`, cache-status headers, cache key thực tế hay purge result của affected URL.

## Câu hỏi chính

Hãy giải thích request có thể đi qua browser cache → CDN edge → origin như thế nào; phân biệt vai trò của `max-age`, `s-maxage`, `ETag`, cache key và purge; sau đó mô tả cách bạn chứng minh **layer nào đang trả stale content** trước khi thay đổi caching strategy.

## Câu hỏi làm rõ nên cân nhắc

1. Akamai property/config hiện override hoặc normalize những cache headers nào từ origin?
2. Affected user truy cập chính xác hostname/path/query nào và URL đó map vào cache key ra sao?
3. Purge được gửi theo URL, cache tag/key hay cơ chế nào, và có kết quả xác nhận không?
4. Browser reload bình thường, hard reload và request bằng client bỏ cache có cho cùng kết quả không?
5. Requirement freshness của HTML là bao nhiêu và static assets có dùng fingerprinted URLs riêng không?

## Gợi ý tư duy

### Gợi ý 1

Đừng coi “cache” là một nơi duy nhất. Cùng một response có thể được giữ ở browser và shared cache với freshness rules khác nhau.

### Gợi ý 2

`max-age` và `s-maxage` không có cùng audience. `ETag` là validator cho revalidation; nó không tự biến response thành non-cacheable.

### Gợi ý 3

Muốn tìm layer gây stale, hãy quan sát cùng một URL qua các đường đi khác nhau và so response body/version cùng các headers như `Age`, validators và CDN-specific cache diagnostics được cấu hình cho môi trường đó.

## Cấu trúc trả lời đề xuất

1. Làm rõ exact URL và freshness requirement.
2. Vẽ request path browser → edge → origin.
3. Giải thích freshness lifetime cho private/shared caches.
4. Giải thích cache key và variant.
5. So sánh origin với CDN và browser-bypass requests.
6. Thu thập cache headers/diagnostics và purge evidence.
7. Xác định stale layer thay vì đoán.
8. Chọn TTL/purge/versioning strategy theo loại content.
9. Test release và purge end-to-end.
10. Monitor cache hit/freshness và origin load.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `max-age` không thể được đọc đơn giản thành “mọi cache refresh sau 5 phút” khi response còn có shared-cache directives và CDN configuration.
- `s-maxage` áp dụng cho shared caches và có thể khác browser freshness behavior.
- `ETag` hỗ trợ validation/revalidation; không phải cơ chế purge và không cấm cache.
- Cache key quyết định object nào thực sự được cached/purged.
- Phải xác định stale ở browser, edge hay origin path bằng evidence.

### Điểm cộng

- Nhận ra CDN configuration có thể thay đổi effective caching behavior; cần kiểm tra property/rules thực tế thay vì chỉ origin header.
- Phân biệt immutable fingerprinted assets với mutable HTML.
- Cân nhắc `stale-while-revalidate`/stale behavior chỉ khi freshness requirement cho phép, không dùng như mặc định.
- Không dùng timestamp query parameter đại trà nếu cache key/query handling chưa được hiểu rõ.

### Senior+

- Reason về purge correctness theo canonical URL/cache key và deployment workflow.
- Đưa freshness SLO và origin-protection trade-off vào quyết định TTL.
- Thiết kế synthetic validation sau release từ nhiều edge locations thay vì chờ user report.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng việc tách ba lớp. Browser có thể giữ response theo HTTP caching semantics. Shared cache như CDN có thể dùng shared-cache directives; trong scenario này `s-maxage=1800` cho thấy shared cache có thể có freshness lifetime khác `max-age=300`. Tuy nhiên effective behavior còn phụ thuộc Akamai property/rules, nên không được suy từ origin header một cách tuyệt đối nếu CDN có override.

`ETag` là validator. Khi cached representation cần revalidate, cache có thể gửi conditional request như `If-None-Match`; nếu representation vẫn hợp lệ origin có thể trả `304`. Việc có `ETag` không có nghĩa CDN luôn gọi origin và cũng không purge object đang fresh.

Tôi sẽ chọn một URL affected cụ thể và một content version có thể nhận diện. So response trực tiếp từ origin với response qua CDN, rồi kiểm tra từ browser sạch hoặc request không dựa vào browser cache. Ở CDN path, tôi xem `Age` và các diagnostic/cache-status headers thực sự được Akamai/property cho phép expose. Tôi cũng kiểm tra hostname/path/query/redirect vì purge một URL không nhất thiết đồng nghĩa mọi variant/cache key liên quan đã bị invalidated.

Nếu origin mới nhưng edge trả body cũ với evidence cache hit/age, investigation tập trung vào TTL, purge hoặc cache-key mismatch. Nếu edge đã mới nhưng browser vẫn cũ, xem browser caching/revalidation. Nếu một hostname mới còn hostname khác stale, xem property/routing/cache key và purge scope. Nếu purge workflow báo success nhưng URL canonical thực tế khác URL purge, fix release automation thay vì giảm toàn bộ TTL.

Strategy phụ thuộc content. Fingerprinted JS/CSS/image assets có thể dùng long-lived caching vì URL thay đổi khi content thay đổi. Mutable HTML thường cần TTL/freshness phù hợp business requirement và purge/invalidation đáng tin cậy khi publish. TTL quá ngắn giảm stale window nhưng tăng origin load; TTL dài tăng cache efficiency nhưng làm purge correctness quan trọng hơn.

Tôi sẽ test bằng một release canary có version marker: origin → CDN trước purge → purge → poll edge cho tới khi expected version xuất hiện, đồng thời xác minh các canonical variants. Production telemetry nên có CDN hit/miss/offload, origin request rate, purge failures và synthetic freshness checks. Không thêm cache-busting query string đại trà trước khi biết query string có nằm trong cache key và hậu quả lên hit ratio.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không kết luận từ `max-age=300` rằng mọi user phải thấy mới sau 5 phút, vì response còn đi qua shared CDN cache và có `s-maxage=1800`, chưa kể Akamai property có thể override policy. `ETag` chỉ là validator cho revalidation, không phải purge.

Em chọn một URL stale cụ thể, so cùng content version ở origin, CDN và browser-clean request. Em xem `Age`, cache diagnostics, hostname/path/query và purge record để xác định stale nằm ở browser hay edge. Nếu origin mới nhưng edge vẫn cache hit body cũ, em kiểm tra effective TTL, cache key và purge scope. Nếu edge mới mà browser cũ thì investigation chuyển sang browser cache/revalidation.

Về design, em tách mutable HTML khỏi fingerprinted assets. Assets có thể cache dài; HTML dùng TTL theo freshness SLO và purge đáng tin cậy. Em sẽ test release/purge end-to-end và monitor cache hit, origin load, purge failures cùng synthetic freshness thay vì giảm TTL hoặc thêm timestamp query một cách mù quáng.”

## Câu hỏi đào sâu

1. Nếu giảm `s-maxage` từ 30 phút xuống 30 giây giải quyết stale nhưng origin traffic tăng 20 lần, bạn sẽ thiết kế lại thế nào?
2. Nếu purge URL báo thành công nhưng một query variant vẫn stale, bạn cần xác minh gì về cache key và query handling?
3. Khi nào bạn dùng versioned URL thay vì purge cho một resource?

## Lỗi trả lời thường gặp

- Coi browser cache và CDN cache là cùng một layer.
- Khẳng định `ETag` ngăn stale content.
- Giảm TTL về gần 0 trước khi đo origin impact.
- Thêm random query string mà không hiểu cache key.
- Không kiểm tra exact URL/hostname/variant đã purge.

## Thang điểm 0–10

- **0–2:** Chỉ nói clear cache/purge lại.
- **3–4:** Hiểu TTL nhưng nhầm shared/private cache hoặc validators.
- **5–6:** Phân biệt layers, directives, cache key và có investigation plan.
- **7–8:** Có evidence-driven debugging, purge correctness, testing và telemetry.
- **9–10:** Kết nối freshness SLO, cache efficiency, deployment workflow và multi-layer verification với trade-offs rõ ràng.

# Câu 2 — IIS Application Pool recycle làm API mất session và background job chạy lại

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET legacy hosting, App Pool recycling, process lifetime, in-memory state, scheduled/background jobs, observability, incident investigation

## Bối cảnh

Một internal approval system cũ chạy ASP.NET trên .NET Framework 4.5 trong IIS/Windows Server. Hệ thống có khoảng vài trăm concurrent users trong giờ cao điểm. Một số session state và cache hiện nằm trong process memory. Ngoài request handling, application còn có một timer khởi động khi web application start để quét database và gửi reminder email mỗi 10 phút.

Gần đây user báo thỉnh thoảng bị mất trạng thái giữa workflow và phải đăng nhập/làm lại một số bước. Cùng thời điểm, business phát hiện một số reminder email bị gửi hai lần. IIS logs cho thấy request vẫn chủ yếu `200`; monitoring hiện tại chỉ theo dõi HTTP error rate và CPU. Team nói “server không reboot nên process chắc chắn không restart”.

Một engineer đề xuất tắt toàn bộ App Pool recycling. Người khác muốn tăng session timeout. Một người khác muốn thêm static boolean để đảm bảo reminder job chỉ chạy một lần.

Chưa rõ App Pool recycle do schedule, idle timeout, config change, memory threshold, deployment hay crash. Cũng chưa rõ production có một hay nhiều worker/process/server ở mọi thời điểm.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào theo **impact → stabilize → evidence → competing hypotheses → verification → remediation → prevention**, đặc biệt để chứng minh có hay không process/App Pool lifecycle event và giải thích vì sao in-process session/background timer có thể gây hai loại symptom trên?

## Câu hỏi làm rõ nên cân nhắc

1. Session mode thực tế là InProc hay external/out-of-process, và authentication state có phụ thuộc process-local data không?
2. App Pool settings hiện có periodic recycle, idle timeout, private memory limit hoặc overlapping recycle như thế nào?
3. Có bao nhiêu IIS servers/worker processes và load balancer có affinity không?
4. Reminder job có durable ownership/idempotency record trong database hay chỉ dựa vào timer/process memory?
5. Deployment/configuration change có trùng thời điểm symptom không, và Windows/IIS event logs ghi gì về worker lifecycle?

## Gợi ý tư duy

### Gợi ý 1

Windows Server uptime và IIS worker-process lifetime là hai thứ khác nhau. Process có thể recycle mà OS không reboot.

### Gợi ý 2

Nếu correctness phụ thuộc process-local memory, hãy reason về điều gì xảy ra khi process restart, overlap hoặc hệ thống có nhiều instances.

### Gợi ý 3

Timer trong web process không phải durable scheduler. Duplicate prevention cần dựa trên ownership/idempotency/durable state phù hợp với topology, không dựa vào static field của một process.

## Cấu trúc trả lời đề xuất

1. Xác định business impact và affected workflows.
2. Stabilize duplicate side effects nếu cần.
3. Xây timeline session-loss/email-duplicate/deployment events.
4. Thu thập IIS/Windows/process lifecycle evidence.
5. Xác minh topology và session mode.
6. Lập nhiều hypotheses: recycle, multi-instance routing, app restart, auth/session expiration, job retry/data issue.
7. Reproduce lifecycle behavior ở staging.
8. Fix session/state ownership và background-job execution model.
9. Test restart/overlap/multi-instance/failure paths.
10. Bổ sung lifecycle/job/session telemetry và alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không đồng nhất server uptime với worker-process uptime.
- In-process state có thể mất khi worker/application restart.
- Web-hosted timer có lifecycle gắn với web process và không đảm bảo exactly-once.
- Static boolean không bảo vệ giữa nhiều processes/servers và mất khi restart.
- Phải chứng minh recycle/restart bằng logs/events/process identity/timeline, không chỉ suy từ symptom.

### Điểm cộng

- Xem xét overlapping recycle: old/new worker có thể tồn tại trong một khoảng chuyển tiếp tùy cấu hình/lifecycle, làm process-local job ownership nguy hiểm hơn.
- Tách session correctness khỏi load-balancer affinity khi có thể bằng external/durable state phù hợp.
- Reminder email có business idempotency key/deduplication record.
- Di chuyển scheduler/work ra khỏi web lifecycle nếu requirement đòi durability/retry/scale.

### Senior+

- Không “tắt recycle” như blanket fix; recycle có operational/security/deployment reasons và root cause phải được xác định.
- Thiết kế migration giảm risk cho legacy app thay vì rewrite toàn hệ thống.
- Phân biệt scheduler trigger semantics với side-effect idempotency: ngay cả scheduler tốt hơn vẫn phải chống duplicate khi retry/failure xảy ra.

## Hướng giải quyết tham khảo

Tôi sẽ ưu tiên business impact: session loss có làm mất dữ liệu hay chỉ mất UI state, duplicate reminder có gây compliance/customer impact không. Nếu email duplicate đang tiếp tục, có thể tạm disable reminder sender hoặc đặt guard ở durable database level trong khi điều tra, tùy mức độ ảnh hưởng.

Tiếp theo xây timeline. Tôi cần IIS/Windows event logs, deployment/configuration history, worker process start/stop/recycle evidence, application-start logs nếu có, process ID/instance identity và thời điểm user/session symptom. HTTP `200` không loại trừ recycle vì một worker khác có thể tiếp tục phục vụ request hoặc recycle diễn ra nhanh.

Các hypotheses không chỉ có recycle: InProc session có thể mất do application restart; multi-server routing có thể đưa request sang process không có state nếu state/affinity design không phù hợp; auth/session timeout có thể bị nhầm với recycle; duplicate email có thể do nhiều process cùng khởi động timer, overlapping lifecycle, deployment, hoặc data/query logic chọn lại cùng reminder.

Nếu session thực sự là InProc, process restart làm state đó biến mất. Nếu production có nhiều workers/servers, process-local state còn tạo consistency problem giữa instances. Tăng session timeout không sửa process lifetime. Một hướng incremental là đưa session/state cần tồn tại qua restart sang một store phù hợp hoặc, tốt hơn khi khả thi, giảm phụ thuộc vào server-side conversational state và persist business workflow state trong database. Không phải mọi UI cache đều cần externalize; chỉ state có correctness/lifetime requirement tương ứng.

Reminder job cần rời khỏi assumption “web app luôn sống và chỉ có một process”. Có thể dùng một scheduler/Worker Service/job platform phù hợp với environment, nhưng trigger vẫn có thể chạy lại. Side effect gửi email nên có durable idempotency identity, ví dụ reminder/business occurrence key được ghi/claim atomically để retry hoặc concurrent execution không gửi lại ngoài policy. Nếu vẫn tạm chạy trong legacy environment, cần database-backed lease/claim và recovery semantics rõ, nhưng đó có thể chỉ là bước chuyển tiếp.

Tôi sẽ không dùng static boolean: mỗi process có bản riêng, restart reset nó, và nó không tạo durable coordination. Tôi cũng không tắt recycle vĩnh viễn trước khi biết nguyên nhân. Nếu recycle bất thường do memory pressure thì tắt recycle có thể chỉ che symptom và làm outage nặng hơn; nếu do deployment/config change thì fix lifecycle assumptions mới là đúng hướng.

Testing phải chủ động recycle App Pool trong staging dưới traffic, restart worker khi job đang chạy, chạy hai instances cùng lúc và inject failure sau khi email provider nhận request nhưng trước khi local status commit. Kiểm tra user workflow không mất business state và email deduplication vẫn đúng.

Monitoring cần worker/process start-stop/recycle reason, process ID/instance identity trong structured logs, session/auth failures, job start/completion/duplicate-suppressed count, email occurrence ID, duration, errors và backlog/last-success age. Correlation giúp nối user symptom với lifecycle event thay vì chỉ nhìn CPU/HTTP error.

## Mẫu trả lời trong phỏng vấn

“Em không dùng server uptime để kết luận IIS worker không restart. Em sẽ dựng timeline từ IIS/Windows events, deployment/config changes, application start logs và process/instance identity, rồi correlate với session loss và duplicate email.

Nếu session là InProc thì recycle hoặc app restart có thể mất state. Nếu có nhiều workers/servers, process-local state còn có vấn đề routing. Tăng timeout không sửa được lifecycle này. Với reminder timer, web process không phải durable scheduler; restart, overlap hoặc nhiều instances có thể làm job chạy lại. Static boolean chỉ bảo vệ một process và mất sau restart.

Em sẽ stabilize duplicate side effects bằng durable dedup/claim nếu cần, rồi đưa business state cần tồn tại qua restart vào durable store và tách scheduled work khỏi web lifecycle khi requirement yêu cầu. Dù dùng scheduler nào, email sender vẫn cần idempotency vì retry/failure có thể tạo duplicate. Cuối cùng em test App Pool recycle, multi-instance và crash window, đồng thời thêm process lifecycle/job telemetry để lần sau có evidence trực tiếp.”

## Câu hỏi đào sâu

1. Nếu business bắt buộc giữ legacy app thêm 18 tháng, bạn chọn thay đổi tối thiểu nào để giảm rủi ro mà không rewrite?
2. Nếu chuyển reminder sang một scheduler mới, tại sao vẫn chưa thể tuyên bố email sẽ “exactly once”?
3. Nếu không thấy recycle event nhưng session vẫn mất, ba hypothesis tiếp theo của bạn là gì?

## Lỗi trả lời thường gặp

- Tắt App Pool recycling ngay mà không tìm reason.
- Tăng session timeout để sửa process restart.
- Dùng static lock/boolean như distributed coordination.
- Chuyển job sang scheduler khác nhưng bỏ qua idempotency.
- Chỉ xem HTTP error rate, không quan sát process lifecycle.

## Thang điểm 0–10

- **0–2:** Chỉ đổi IIS timeout/recycle settings.
- **3–4:** Nhận ra InProc session nhưng thiếu job/multi-instance reasoning.
- **5–6:** Có lifecycle evidence, competing hypotheses và durable-state direction.
- **7–8:** Có idempotency, restart/multi-instance tests và observability tốt.
- **9–10:** Stabilize theo business risk, phân biệt scheduler/side-effect semantics và đưa ra incremental legacy remediation với trade-offs rõ ràng.

# Câu 3 — Optimizely CMS: giữ traditional rendering hay chuyển headless cho toàn bộ website?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, content modeling, headless vs traditional rendering, CDN/cache, SEO, frontend/backend integration, deployment, observability, complexity trade-offs

## Bối cảnh

Một enterprise marketing/e-commerce website đang dùng Optimizely CMS. Editors quản lý landing pages, campaign content, navigation và reusable content blocks. Một phần product data đến từ hệ thống commerce/PIM bên ngoài. Website hiện render server-side bằng ASP.NET Core và có CDN phía trước.

Product muốn frontend team có tốc độ phát triển độc lập hơn và đang đề xuất chuyển **toàn bộ** site sang React headless. Lý do được đưa ra là “headless hiện đại hơn, scale tốt hơn và sẽ làm Core Web Vitals tốt hơn”. Editorial team lại phụ thuộc nhiều vào preview, page composition và publish workflow hiện tại. SEO/crawlability rất quan trọng vì phần lớn traffic đến từ search. Một mobile app trong roadmap cũng muốn tái sử dụng một phần content.

Chưa có số liệu cho thấy server-side rendering hiện là bottleneck. Cũng chưa rõ bao nhiêu content thực sự cần dùng đa kênh, frontend deployment independence mang lại value bao nhiêu, hay preview/personalization/search integration sẽ hoạt động thế nào sau khi tách rendering.

## Câu hỏi chính

Bạn sẽ quyết định giữa **traditional CMS rendering**, **headless**, hoặc một **hybrid/composable approach** như thế nào? Hãy thiết kế decision framework và một target architecture khả thi, đồng thời giải thích content boundaries, API/cache/CDN, editorial preview, SEO, failure modes, deployment và cost of complexity.

## Câu hỏi làm rõ nên cân nhắc

1. Những content types nào cần tái sử dụng cho mobile/other channels, và những content nào chỉ phục vụ website page composition?
2. Editorial preview/on-page editing/personalization hiện quan trọng tới mức nào và target solution phải giữ những capability nào?
3. Core Web Vitals hiện đang bị bottleneck bởi server render, JavaScript bundle, images, third-party scripts, CDN/cache hay yếu tố khác?
4. SEO requirement có đòi server-rendered/pre-rendered HTML cho những route nào, và frontend target sẽ cung cấp rendering strategy gì?
5. Ownership/deployment của CMS team và frontend team hiện gây pain cụ thể nào có thể đo được?

## Gợi ý tư duy

### Gợi ý 1

Đừng biến “headless” thành mục tiêu. Bắt đầu từ channel reuse, editorial workflow, SEO, performance evidence và team ownership.

### Gợi ý 2

Headless thay đổi boundary: CMS trở thành content source/API, còn rendering, routing, preview integration, cache invalidation và failure handling chuyển sang các thành phần khác.

### Gợi ý 3

Hybrid có thể giữ page-oriented rendering nơi editorial experience có giá trị và expose structured content cho channel cần reuse. Complexity chỉ đáng trả khi boundary/value rõ ràng.

## Cấu trúc trả lời đề xuất

1. Clarify business/editorial/channel requirements.
2. Baseline current performance/deployment pain.
3. Phân loại content theo page-oriented vs channel-neutral.
4. So sánh traditional/headless/hybrid theo decision criteria.
5. Xác định API/content contract và ownership.
6. Thiết kế rendering/cache/CDN/preview strategy.
7. Xử lý SEO, security và dependency failures.
8. Chọn migration slice và coexistence model.
9. Test editorial + technical journeys.
10. Measure outcomes và chỉ mở rộng nếu evidence tốt.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định headless nhanh hơn hoặc scale tốt hơn nếu chưa đo bottleneck.
- Content model cho multi-channel nên tránh phụ thuộc quá mạnh vào presentation/page layout.
- Headless thêm API/network/cache/preview/deployment boundaries chứ không xóa complexity.
- SEO/rendering strategy phải explicit.
- Editorial workflow/preview là architecture requirement, không phải chi tiết UI phụ.

### Điểm cộng

- Hybrid: giữ page rendering cho marketing composition nhưng expose structured content cho mobile/reusable domains.
- CDN/cache invalidation gắn với publish lifecycle.
- Bounded integration với commerce/PIM thay vì nhét toàn bộ product domain vào CMS.
- Contract/versioning cho content API và graceful degradation khi CMS/content delivery dependency lỗi.

### Senior+

- Phân biệt content ownership với product/commerce ownership.
- Có migration pilot và measurable exit criteria thay vì big-bang frontend rewrite.
- Đánh giá organizational cost: thêm frontend hosting/runtime, observability, preview bridge, API governance và cross-team incident ownership.

## Hướng giải quyết tham khảo

Tôi sẽ không chọn headless chỉ vì “modern”. Trước tiên đo current pain: deployment coupling làm chậm release bao nhiêu, CMS render chiếm bao nhiêu latency, Core Web Vitals bottleneck nằm ở đâu, editors dùng preview/composition đến mức nào và content reuse cho mobile thực sự gồm những domain nào.

Sau đó phân loại content. Navigation, campaign messaging, FAQs hoặc structured editorial content có thể có giá trị đa kênh nếu model theo meaning thay vì HTML/layout. Ngược lại, landing page với rich composition và editor-driven blocks có thể nhận nhiều value từ traditional page rendering/editorial tooling. Product price/inventory nên có ownership rõ ở commerce/PIM/domain service; CMS có thể tham chiếu product identity và compose presentation nhưng không nhất thiết trở thành source of truth cho commerce state.

Traditional rendering có lợi thế simplicity: một runtime/render path, preview/editor integration trực tiếp và ít network boundary hơn. Headless có thể giúp channel reuse và frontend deployment independence, nhưng thêm content API, authentication/authorization nếu applicable, frontend hosting/rendering, preview integration, cache invalidation, contract evolution và observability giữa systems. React client-side rendering thuần cũng không tự đảm bảo SEO/Core Web Vitals; rendering strategy cần được chọn theo route/use case, ví dụ server rendering/static generation hoặc tương đương nếu requirement cần HTML crawlable/fast first render.

Với scenario này, tôi có xu hướng đánh giá hybrid trước: giữ CMS-driven server-rendered pages cho phần marketing/editorial composition đang hoạt động tốt, đồng thời tạo structured content APIs cho mobile và những component/domain thật sự cần multi-channel. Nếu frontend independence là pain lớn ở một section, pilot headless cho section đó thay vì rewrite toàn site.

Caching phải đi cùng publish semantics. CDN có thể cache public rendered output/content responses theo freshness requirement, nhưng cần invalidation/purge strategy khi publish. Cache key phải xét locale, route và các dimensions thực sự ảnh hưởng representation; personalized content không được cache public một cách vô ý. Nếu CMS/content delivery unavailable, quyết định rõ phần nào có thể serve stale cached content và phần nào phải fail/degrade.

Preview là một use case riêng: draft/unpublished content không được rò vào public cache; preview request cần identity/authorization và frontend phải render đúng draft context. Đây là thứ cần prototype sớm nếu headless vì nó có thể quyết định editor acceptance.

SEO validation gồm status codes, canonical URLs, metadata, structured data, redirects, sitemap/crawlability và rendered HTML thực tế. Performance validation dùng Lighthouse/Core Web Vitals cùng RUM/field data nếu có; không dùng framework choice làm proxy cho performance.

Migration nên pilot một bounded section. Success criteria có thể gồm deployment lead time, editor workflow satisfaction, p75 Core Web Vitals, cache hit/offload, error rate, SEO parity và incident complexity. Nếu pilot không tạo đủ value để bù operational complexity, giữ traditional hoặc hybrid nhỏ hơn là quyết định hợp lý.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không coi headless là upgrade mặc định. Em bắt đầu từ ba câu hỏi: content nào thật sự cần đa kênh, editorial workflow nào phải giữ, và bottleneck performance/deployment hiện nằm ở đâu.

Em phân tách page-oriented marketing content với channel-neutral structured content và product domain. Product price/inventory vẫn thuộc commerce/PIM; CMS compose presentation. Nếu mobile chỉ cần một phần structured content, em có thể expose phần đó qua API mà không rewrite toàn website.

Headless cho frontend independence nhưng đổi lại có thêm API, cache invalidation, preview integration, rendering/SEO strategy và cross-system observability. React cũng không tự làm Core Web Vitals tốt hơn. Với site đang phụ thuộc mạnh vào page composition và chưa chứng minh server render là bottleneck, em sẽ pilot hybrid: giữ traditional rendering cho phần editor-heavy, headless cho bounded use case cần reuse hoặc independent deployment.

Em test preview/draft isolation, publish-to-CDN invalidation, SEO parity, dependency failure và performance bằng field/lab metrics. Chỉ mở rộng headless nếu pilot cho measurable value lớn hơn complexity.”

## Câu hỏi đào sâu

1. Nếu frontend team yêu cầu deploy độc lập mỗi ngày nhưng editors cần instant preview của unpublished content, bạn thiết kế preview boundary thế nào mà không leak draft content?
2. Nếu mobile app cần 80% CMS content sau sáu tháng, điều đó có làm bạn đổi từ hybrid sang headless toàn bộ không? Vì sao?
3. Nếu Lighthouse tăng sau migration nhưng field Core Web Vitals và conversion không cải thiện, bạn đánh giá thành công thế nào?

## Lỗi trả lời thường gặp

- “Headless scale tốt hơn” mà không nêu bottleneck hay topology.
- Đồng nhất React với SEO/performance tốt.
- Bỏ qua editor preview/publish workflow.
- Để CMS sở hữu cả commerce domain chỉ vì UI cần hiển thị product.
- Big-bang rewrite thay vì pilot/coexistence và measurable criteria.

## Thang điểm 0–10

- **0–2:** Chọn framework/architecture theo xu hướng.
- **3–4:** Nêu traditional vs headless nhưng thiếu editorial/SEO/failure reasoning.
- **5–6:** Có content boundaries, rendering/cache và trade-offs hợp lý.
- **7–8:** Có hybrid option, preview/security, deployment, testing và measurable pilot.
- **9–10:** Cân bằng content ownership, editor experience, channel reuse, operational complexity và business outcomes với conditional decision rõ ràng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Ba câu hôm nay tập trung vào những kỹ năng dễ bị bỏ qua khi chỉ học backend framework: hiểu HTTP/CDN caching như một chuỗi nhiều lớp thay vì một TTL đơn lẻ; xem IIS worker process như một runtime có lifecycle độc lập với Windows Server và không đặt correctness của session/job vào process-local memory; và đánh giá CMS headless/traditional theo content ownership, editorial workflow, SEO, performance evidence và operational complexity thay vì xu hướng kiến trúc.

## Mẫu tư duy cần nhớ

- **Trace từng layer trước khi sửa:** browser → CDN → origin; process → durable state; CMS → rendering → edge.
- **Đừng dùng một metric làm proxy cho cơ chế:** server uptime không chứng minh worker uptime; framework choice không chứng minh Core Web Vitals; origin freshness không chứng minh edge freshness.
- **Correctness không nên phụ thuộc process-local state khi lifecycle hoặc topology vượt quá một process.**
- **Measure before optimizing:** đo cache behavior, recycle evidence và performance bottleneck trước khi đổi architecture.
- **Complexity phải mua được giá trị cụ thể:** headless, external scheduler hay cache strategy chỉ đáng thêm khi requirement và evidence biện minh.
