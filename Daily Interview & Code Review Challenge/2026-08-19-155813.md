# Code Review Challenge 1 — Consumer thanh toán bị xử lý trùng khi retry

**Chủ đề:** Concurrency, idempotency, EF Core transaction, message processing  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một dịch vụ ASP.NET Core nhận message `PaymentCompleted` từ RabbitMQ. Mỗi message phải đánh dấu đơn hàng đã thanh toán, ghi lịch sử và gửi email xác nhận. Consumer có thể chạy trên nhiều instance. Broker dùng cơ chế at-least-once nên message có thể được giao lại nếu consumer mất kết nối hoặc process chết trước khi ACK.

Sau khi tăng từ 1 lên 4 replicas, production thỉnh thoảng ghi hai `PaymentHistory` cho cùng một payment và khách hàng nhận hai email. Log cho thấy cùng `MessageId` đôi khi được xử lý gần như đồng thời. Database là PostgreSQL qua EF Core. Business yêu cầu không được bỏ mất payment hợp lệ và việc retry phải an toàn.

## Đoạn code cần review

```csharp
public sealed class PaymentCompletedConsumer
{
    private readonly AppDbContext _db;
    private readonly IEmailService _email;
    private readonly ILogger<PaymentCompletedConsumer> _logger;

    public PaymentCompletedConsumer(
        AppDbContext db,
        IEmailService email,
        ILogger<PaymentCompletedConsumer> logger)
    {
        _db = db;
        _email = email;
        _logger = logger;
    }

    public async Task HandleAsync(PaymentCompleted message)
    {
        var processed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId);

        if (processed)
            return;

        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId);

        order.Status = OrderStatus.Paid;
        order.PaidAt = DateTime.UtcNow;

        _db.PaymentHistories.Add(new PaymentHistory
        {
            OrderId = order.Id,
            PaymentId = message.PaymentId,
            Amount = message.Amount,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        await _email.SendPaymentConfirmationAsync(
            order.CustomerEmail,
            order.Id,
            message.Amount);

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Processed payment message {MessageId} for order {OrderId}",
            message.MessageId,
            message.OrderId);
    }
}
```

## Câu hỏi gợi mở

- Hai consumer cùng đọc `ProcessedMessages` trước khi một consumer insert thì chuyện gì xảy ra?
- Database commit và gửi email có nằm trong cùng một atomic boundary không?
- Process chết ngay sau khi gửi email nhưng trước lần `SaveChangesAsync()` thứ hai thì retry sẽ làm gì?
- `MessageId` và `PaymentId` hiện có uniqueness guarantee nào ở database chưa?
- Cancellation từ consumer/broker nên được truyền xuống EF Core và external I/O như thế nào?

## Kết quả code review tham khảo

### 1. Check-then-act trên `ProcessedMessages` bị race condition

- **Problem:** `AnyAsync()` và insert `ProcessedMessage` là hai operation tách rời.
- **Why it happens:** Hai replicas có thể cùng quan sát “chưa xử lý” rồi cùng tiếp tục.
- **Production impact:** Duplicate history, duplicate side effects và trạng thái khó dự đoán.
- **Severity:** Critical
- **Recommended fix:** Tạo unique constraint/index trên `ProcessedMessages.MessageId`; coi database constraint là invariant cuối cùng. Đặt dedup record và business changes trong cùng transaction, xử lý unique violation như duplicate delivery đã được xử lý.

### 2. Email được gửi trước khi dedup marker được commit

- **Problem:** External side effect xảy ra giữa hai lần commit.
- **Why it happens:** Nếu process chết sau email nhưng trước khi lưu `ProcessedMessage`, broker retry và email được gửi lại.
- **Production impact:** Khách hàng nhận duplicate notification dù database có thể đã cập nhật.
- **Severity:** Critical
- **Recommended fix:** Không gửi email trực tiếp trong transaction consumer. Ghi một OutboxMessage trong cùng transaction với order/history/dedup; worker riêng dispatch email và dùng idempotency/dedup phù hợp ở delivery layer.

### 3. Business changes và dedup marker không cùng transaction

- **Problem:** `Order` và `PaymentHistory` được commit trước marker.
- **Why it happens:** Có hai `SaveChangesAsync()` độc lập.
- **Production impact:** Crash ở giữa khiến retry thực hiện lại business mutation.
- **Severity:** High
- **Recommended fix:** Bao order update, payment history, processed-message marker và outbox insert trong một database transaction hoặc một `SaveChangesAsync()` atomic transaction phù hợp.

### 4. Không có uniqueness guarantee cho `PaymentId`

- **Problem:** Duplicate event với `MessageId` khác nhưng cùng payment vẫn có thể tạo nhiều history.
- **Why it happens:** Dedup chỉ dựa trên transport message identity.
- **Production impact:** Một payment logic có thể được áp dụng nhiều lần nếu producer republish với message ID mới.
- **Severity:** High
- **Recommended fix:** Nếu business invariant là một `PaymentId` chỉ được áp dụng một lần, tạo unique constraint thích hợp, ví dụ `(OrderId, PaymentId)` hoặc `PaymentId` tùy domain.

### 5. Không validate transition/trạng thái hiện tại của Order

- **Problem:** Code luôn gán `Paid` mà không kiểm tra trạng thái hiện tại hoặc payment tương ứng.
- **Why it happens:** Handler giả định event luôn đến đúng thứ tự và đúng một lần.
- **Production impact:** Event cũ hoặc sai thứ tự có thể ghi đè state mới hơn.
- **Severity:** High
- **Recommended fix:** Xác định state-transition invariant; từ chối hoặc no-op các transition không hợp lệ, hoặc dùng version/concurrency token nếu nhiều workflow cùng cập nhật order.

### 6. Không truyền `CancellationToken`

- **Problem:** DB và email I/O tiếp tục dù consumer đang shutdown/cancel.
- **Why it happens:** Method không nhận token.
- **Production impact:** Shutdown kéo dài, operation dở dang và khả năng redelivery khó kiểm soát hơn.
- **Severity:** Medium
- **Recommended fix:** Nhận `CancellationToken` và truyền cho EF Core/outbox operations. Việc ACK chỉ nên diễn ra sau khi durable transaction thành công.

### 7. Timestamp business lấy từ thời điểm consumer xử lý

- **Problem:** `PaidAt = DateTime.UtcNow` có thể không phản ánh thời điểm payment thực sự hoàn tất.
- **Why it happens:** Event không dùng timestamp nguồn.
- **Production impact:** Retry hoặc queue delay làm sai audit/business timeline.
- **Severity:** Medium
- **Recommended fix:** Nếu event có `OccurredAt`, dùng timestamp đó sau khi validate; lưu thêm `ProcessedAt` riêng cho thời điểm consumer xử lý.

### 8. Logging thiếu thông tin outcome và duplicate

- **Problem:** Duplicate path return im lặng; không có duration/outcome/retry metadata.
- **Why it happens:** Logging chỉ ở happy path.
- **Production impact:** Khó chứng minh dedup hoạt động và khó điều tra spike retry.
- **Severity:** Low
- **Recommended fix:** Structured log cho outcome `processed/duplicate/failed`, message ID, payment ID, order ID, retry count/correlation ID; không log dữ liệu nhạy cảm không cần thiết.

## Phiên bản code đề xuất

```csharp
public sealed class PaymentCompletedConsumer
{
    private readonly AppDbContext _db;
    private readonly ILogger<PaymentCompletedConsumer> _logger;

    public PaymentCompletedConsumer(
        AppDbContext db,
        ILogger<PaymentCompletedConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        PaymentCompleted message,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        try
        {
            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = message.MessageId,
                ProcessedAt = DateTime.UtcNow
            });

            var order = await _db.Orders
                .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

            if (order.Status != OrderStatus.Paid)
            {
                order.Status = OrderStatus.Paid;
                order.PaidAt = message.OccurredAt;
            }

            _db.PaymentHistories.Add(new PaymentHistory
            {
                OrderId = order.Id,
                PaymentId = message.PaymentId,
                Amount = message.Amount,
                CreatedAt = message.OccurredAt
            });

            _db.OutboxMessages.Add(OutboxMessage.Create(
                type: "PaymentConfirmationRequested",
                payload: new
                {
                    order.Id,
                    order.CustomerEmail,
                    message.Amount,
                    message.PaymentId
                },
                idempotencyKey: $"payment-confirmation:{message.PaymentId}"));

            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);

            _logger.LogInformation(
                "Processed payment {PaymentId}, message {MessageId}, order {OrderId}",
                message.PaymentId,
                message.MessageId,
                message.OrderId);
        }
        catch (DbUpdateException ex) when (IsDuplicateMessageOrPayment(ex))
        {
            await tx.RollbackAsync(cancellationToken);

            _logger.LogInformation(
                "Ignored duplicate payment message {MessageId}, payment {PaymentId}",
                message.MessageId,
                message.PaymentId);
        }
    }

    private static bool IsDuplicateMessageOrPayment(DbUpdateException ex)
    {
        // Production code: inspect provider-specific unique-constraint metadata.
        return ex.InnerException is not null;
    }
}
```

Giả định schema có unique constraint cho `ProcessedMessages.MessageId` và business key thích hợp của payment. `OutboxMessage` được một dispatcher riêng đọc, gửi email, retry có backoff và lưu trạng thái delivery. Helper bắt duplicate ở ví dụ trên chỉ mang tính minh họa; production phải nhận diện chính xác unique-constraint violation của provider, không nuốt mọi `DbUpdateException`.

## Trade-offs

Transactional outbox thêm bảng, worker, cleanup và độ trễ nhỏ trước khi email được gửi, đổi lại database state và ý định tạo side effect được commit atomically. Nếu email provider hỗ trợ idempotency key thì nên truyền key ổn định để tăng khả năng exactly-once-effect; nếu không, hệ thống thực tế vẫn thường là at-least-once delivery với dedup ở boundary phù hợp. Isolation level cao hơn có thể giảm một số race nhưng không thay thế unique business constraint và có thể làm tăng contention.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 20 handler đồng thời với cùng `MessageId`; chỉ một transaction tạo business effect.
2. **Logical duplicate test:** hai `MessageId` khác nhau nhưng cùng `PaymentId`; invariant payment vẫn chặn double apply.
3. **Failure-path test:** crash sau DB commit nhưng trước ACK; redelivery không tạo thêm history/outbox.
4. **Outbox retry test:** email provider timeout rồi thành công; không mất notification và idempotency behavior đúng thiết kế.
5. **Load test:** nhiều orders/payment song song để đo lock contention, DB latency, duplicate rate và outbox lag.

## Quan sát trong production

Theo dõi structured logs theo `MessageId`, `PaymentId`, `OrderId`, correlation ID và outcome; metrics gồm consumer throughput, duplicate count, retry count, handler latency, unique-constraint conflicts, outbox backlog/age, delivery failures và dead-letter count. Trace nên nối broker receive → DB transaction → outbox dispatch → email provider. Alert khi outbox oldest-message age hoặc retry/DLQ rate vượt ngưỡng. Ở database, theo dõi lock waits, transaction duration và constraint violations.

## Câu hỏi phỏng vấn mở rộng

1. Nếu RabbitMQ redeliver message sau khi DB commit nhưng trước ACK, flow mới phản ứng thế nào?
2. Nếu email provider không hỗ trợ idempotency key, bạn thiết kế delivery semantics ra sao?
3. Có nên dùng distributed lock thay unique constraint không? Trong trường hợp nào distributed lock thực sự cần thiết?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log vừa chậm vừa có nguy cơ lộ dữ liệu

**Chủ đề:** Authorization, EF Core query execution, input handling, sensitive-data exposure, performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API nội bộ cho phép quản trị viên của từng tenant tìm audit log. Bảng `AuditLogs` đã có khoảng 35 triệu rows. Mỗi tenant có từ vài nghìn đến vài triệu records. Sau một đợt mở rộng quyền cho support team, security review phát hiện có request trả về record của tenant khác. Đồng thời p95 của endpoint tăng lên nhiều giây khi người dùng tìm kiếm theo text.

API dùng ASP.NET Core + EF Core. `TenantId` nằm trong authenticated claims. Request cho phép filter theo thời gian và keyword. Payload audit có thể chứa email, object IDs và một số metadata nhạy cảm. Client chỉ cần tối đa 100 bản ghi gần nhất.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        [FromQuery] Guid? tenantId,
        [FromQuery] string? keyword,
        [FromQuery] DateTime? from,
        [FromQuery] DateTime? to)
    {
        var logs = await _db.AuditLogs
            .Include(x => x.User)
            .ToListAsync();

        if (tenantId.HasValue)
            logs = logs.Where(x => x.TenantId == tenantId.Value).ToList();

        if (!string.IsNullOrWhiteSpace(keyword))
            logs = logs.Where(x =>
                x.Action.Contains(keyword) ||
                x.Payload.Contains(keyword)).ToList();

        if (from.HasValue)
            logs = logs.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            logs = logs.Where(x => x.CreatedAt <= to.Value).ToList();

        _logger.LogInformation(
            "Audit search tenant={TenantId} keyword={Keyword} results={Count}",
            tenantId,
            keyword,
            logs.Count);

        return Ok(logs.OrderByDescending(x => x.CreatedAt).Take(100));
    }
}
```

## Kết quả code review tham khảo

### 1. Tenant scope được lấy từ user-controlled query parameter

- **Problem:** Caller có thể truyền `tenantId` khác hoặc bỏ hẳn filter.
- **Why it happens:** Endpoint không ràng buộc tenant bằng authenticated identity/authorization policy.
- **Production impact:** Cross-tenant data exposure; đây là lỗi authorization nghiêm trọng.
- **Severity:** Critical
- **Recommended fix:** Lấy tenant ID từ trusted claims/context và enforce authorization server-side. Nếu support có cross-tenant capability, dùng policy/role riêng và explicit audited tenant selection thay vì mặc định tin query parameter.

### 2. Nếu không truyền `tenantId`, endpoint trả dữ liệu của mọi tenant

- **Problem:** Tenant filtering là optional.
- **Why it happens:** `Guid? tenantId` quyết định có filter hay không.
- **Production impact:** Mass disclosure có thể xảy ra chỉ bằng một request.
- **Severity:** Critical
- **Recommended fix:** Tenant predicate phải luôn tồn tại cho tenant-scoped endpoint; fail closed nếu claim thiếu/invalid.

### 3. Materialize toàn bộ bảng trước khi filter

- **Problem:** `ToListAsync()` chạy trước mọi predicate.
- **Why it happens:** Các `Where` sau đó là LINQ-to-Objects.
- **Production impact:** Đọc hàng chục triệu rows, memory pressure/GC, DB/network saturation, timeout và có thể gây outage.
- **Severity:** High
- **Recommended fix:** Xây `IQueryable`, thêm predicates rồi `OrderByDescending`, `Take(100)`, projection và cuối cùng mới `ToListAsync()`.

### 4. Truy vấn tải entity `User` không cần thiết

- **Problem:** `Include(x => x.User)` tăng dữ liệu và tracking graph.
- **Why it happens:** Response trả entity thay vì DTO được thiết kế rõ.
- **Production impact:** Query nặng hơn, allocation nhiều hơn và tăng nguy cơ lộ field của `User`.
- **Severity:** High
- **Recommended fix:** Project trực tiếp sang DTO chỉ gồm field cần thiết; dùng `AsNoTracking()` cho read-only query.

### 5. Trả trực tiếp persistence entity/audit payload

- **Problem:** API contract phụ thuộc entity và có thể serialize field nhạy cảm ngoài ý muốn.
- **Why it happens:** `Ok(logs...)` trả model DB trực tiếp.
- **Production impact:** Sensitive-data exposure khi schema/entity thay đổi hoặc navigation được serialize.
- **Severity:** High
- **Recommended fix:** Explicit DTO projection, redact/mask payload theo policy và quyền của caller.

### 6. Logging raw keyword

- **Problem:** User search text được ghi nguyên văn.
- **Why it happens:** Structured logging không đồng nghĩa dữ liệu tự động an toàn.
- **Production impact:** PII/secrets có thể bị copy vào centralized logs với retention/access khác database gốc.
- **Severity:** High
- **Recommended fix:** Không log raw keyword; log boolean `hasKeyword`, normalized category hoặc hash nếu thực sự cần correlation và đã đánh giá privacy.

### 7. Keyword search trên large free-text payload không có strategy rõ ràng

- **Problem:** `Contains` trên text lớn có thể tạo query đắt khi chuyển xuống DB.
- **Why it happens:** Pattern search không nhất thiết tận dụng B-tree index thông thường.
- **Production impact:** CPU/I/O database cao và latency khó dự đoán.
- **Severity:** Medium
- **Recommended fix:** Xác định requirement tìm kiếm; PostgreSQL có thể dùng full-text search hoặc index phù hợp như trigram cho use case thích hợp. Không chọn index trước khi đo query plan và pattern thực tế.

### 8. Không giới hạn/validate time range

- **Problem:** Caller có thể yêu cầu range cực rộng hoặc giá trị không hợp lệ.
- **Why it happens:** Không có guard `from <= to`, max range hay default window.
- **Production impact:** Expensive scans và UX không ổn định.
- **Severity:** Medium
- **Recommended fix:** Validate range, đặt default recent window và giới hạn range nếu phù hợp business; privileged export nên là workflow riêng.

### 9. Thiếu cancellation token

- **Problem:** Query không nhận `HttpContext.RequestAborted`.
- **Why it happens:** Action không truyền token cho EF Core.
- **Production impact:** Client disconnect nhưng DB work vẫn tiếp tục cho đến khi query hoàn tất/timeout.
- **Severity:** Medium
- **Recommended fix:** Nhận `CancellationToken` và truyền vào `ToListAsync`.

### 10. Không có deterministic tie-breaker cho newest records

- **Problem:** Chỉ sort theo `CreatedAt` có thể không ổn định khi nhiều records cùng timestamp.
- **Why it happens:** Không có secondary key.
- **Production impact:** Pagination/keyset sau này có thể duplicate/miss records giữa pages.
- **Severity:** Low
- **Recommended fix:** Sort thêm unique key như `Id` và dùng keyset pagination nếu endpoint cần paging sâu.

```csharp
[Authorize(Policy = "AuditReader")]
public sealed class AuditController : ControllerBase
{

    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        [FromQuery] string? keyword,
        [FromQuery] DateTimeOffset? from,
        [FromQuery] DateTimeOffset? to,
        CancellationToken cancellationToken)
    {
        var tenantClaim = User.FindFirst("tenant_id")?.Value;
        if (!Guid.TryParse(tenantClaim, out var tenantId))
            return Forbid();

        var effectiveTo = to ?? DateTimeOffset.UtcNow;
        var effectiveFrom = from ?? effectiveTo.AddDays(-7);

        if (effectiveFrom > effectiveTo ||
            effectiveTo - effectiveFrom > TimeSpan.FromDays(31))
        {
            return BadRequest("Invalid audit time range.");
        }

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId)
            .Where(x => x.CreatedAt >= effectiveFrom && x.CreatedAt <= effectiveTo);

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            var term = keyword.Trim();
            query = query.Where(x =>
                x.Action.Contains(term) ||
                x.Payload.Contains(term));
        }

        var result = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Select(x => new AuditLogDto(
                x.Id,
                x.CreatedAt,
                x.Action,
                x.UserId,
                RedactPayload(x.Payload)))
            .Take(100)
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Audit search completed for tenant {TenantId}; HasKeyword={HasKeyword}; Count={Count}",
            tenantId,
            !string.IsNullOrWhiteSpace(keyword),
            result.Count);

        return Ok(result);
    }

    private static string RedactPayload(string payload)
    {
        // Production code should use a domain-specific structured redaction policy.
        return payload;
    }
}
```

Lưu ý: `RedactPayload` ở ví dụ chỉ thể hiện boundary cần có, không phải implementation bảo mật hoàn chỉnh. Nếu `Payload` là JSON, nên project/redact theo schema hoặc lưu các searchable fields riêng thay vì parse/redact tùy tiện sau query. Với PostgreSQL, strategy cho keyword search phải được chọn dựa trên search semantics và execution plan thực tế. Index nền tảng thường nên bắt đầu từ tenant/time access pattern, ví dụ composite index phù hợp với `TenantId` và `CreatedAt`, rồi đo bằng `EXPLAIN (ANALYZE, BUFFERS)` trên dữ liệu gần production.

## Trade-offs

Giới hạn time range bảo vệ hệ thống nhưng có thể không đáp ứng điều tra lịch sử dài; khi đó nên có export/report workflow riêng với authorization và resource limits rõ ràng. `AsNoTracking` phù hợp read-only endpoint nhưng không dùng nếu cùng query result cần được sửa và persist trong cùng context. Full-text/trigram index tăng storage và write cost, nên chỉ thêm sau khi xác định semantics tìm kiếm và đo workload. Redaction giảm rủi ro disclosure nhưng có thể làm support thiếu context; có thể dùng permission tier riêng cho field nhạy cảm.

## Cách kiểm thử

1. **Security integration test:** user tenant A không thể lấy record tenant B bằng bất kỳ query parameter nào; thiếu/invalid tenant claim phải fail closed.
2. **Authorization test:** role không có `AuditReader` bị từ chối; support cross-tenant nếu có phải đi qua policy riêng và có audit trail.
3. **Database/query test:** kiểm tra generated SQL chứa tenant/time predicates, projection và `LIMIT`; không materialize toàn bảng.
4. **Load test:** dataset hàng triệu rows/tenant, đo p50/p95/p99, DB CPU/I/O và query plan cho có/không keyword.
5. **Privacy test:** response DTO và application logs không chứa field/payload/keyword nhạy cảm ngoài policy cho phép.

## Quan sát trong production

Log tenant/correlation ID, duration, result count, filter shape nhưng tránh raw keyword/payload. Metrics gồm request latency, timeout/cancellation rate, rows returned, DB query duration, slow-query count và search-with-keyword ratio. Distributed trace nối HTTP request với EF Core/database span. PostgreSQL nên theo dõi slow queries, execution plans, sequential scans, rows examined, buffer reads/hits và index usage. Alert khi latency/error rate hoặc DB resource consumption tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support engineer thực sự cần xem nhiều tenant, bạn thiết kế authorization model và audit trail thế nào?
2. Với PostgreSQL, khi nào bạn chọn full-text search, trigram index hoặc một search engine riêng?
3. Nếu client cần phân trang hàng triệu audit records, vì sao keyset pagination thường phù hợp hơn offset pagination?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào ranh giới transaction trong hệ thống at-least-once: idempotency không thể chỉ dựa vào `SELECT` trước `INSERT`; invariant quan trọng cần được database bảo vệ, còn side effect bên ngoài thường cần outbox và delivery strategy riêng. Challenge 2 nhấn mạnh security boundary phải được enforce từ trusted identity trước mọi tối ưu; đồng thời EF Core query phải giữ ở `IQueryable` đủ lâu để database thực hiện filtering, ordering, projection và limiting.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; đừng coi retry là concern độc lập.
- Đưa invariant concurrency xuống database bằng constraint phù hợp thay vì chỉ check trong application.
- Tách database atomicity khỏi external side effects; cân nhắc transactional outbox.
- Authorization phải fail closed và dựa trên trusted identity, không dựa vào user-controlled filter.
- Filter/project/limit trước khi materialize; đo query plan trước khi tối ưu index/search.
