# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân lên dưới tải

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core query pipeline, change tracking, LINQ deferred execution, SQL diagnostics, performance, observability

## Bối cảnh

Một ASP.NET Core API trả danh sách 200 nhân viên cùng trạng thái mailbox. Sau một thay đổi nhỏ, p95 tăng từ khoảng 180 ms lên hơn 2 giây khi tải cao. CPU ứng dụng không tăng đáng kể nhưng số lệnh SQL/request tăng mạnh. Code tạo `IQueryable<Employee>`, áp dụng filter theo quyền người dùng, sau đó một helper duyệt query để tính thống kê; cuối cùng controller tiếp tục `ToListAsync()` để tạo response. Một developer cho rằng “`IQueryable` đã lấy dữ liệu từ DB rồi nên enumerate thêm không đáng kể”. Endpoint chỉ đọc dữ liệu nhưng entity vẫn được tracking.

Chưa biết helper enumerate bao nhiêu lần, query có navigation nào, execution plan ra sao và DbContext lifetime hiện tại thế nào.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong từ lúc tạo `IQueryable` đến khi enumerate, vì sao số SQL có thể tăng, misconception nào đang tồn tại, tracking có chi phí gì, rủi ro production là gì và bạn sẽ chứng minh từng giả thuyết bằng evidence nào trước khi sửa.

## Câu hỏi làm rõ nên cân nhắc

1. Helper gọi `Count`, `Any`, `foreach` hay materialize query bao nhiêu lần?
2. Có lazy loading, explicit loading hoặc navigation access sau materialization không?
3. Endpoint có cần cập nhật entity sau khi đọc không?
4. SQL thực tế, số round trip và execution plan thay đổi thế nào so với phiên bản trước?
5. DbContext có đúng scoped lifetime và có bị chia sẻ giữa concurrent operations không?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt xây dựng expression tree với thời điểm query thực sự được thực thi.
- **Gợi ý 2:** Theo dõi mỗi terminal operation/enumeration, generated SQL, tracking và navigation loading.
- **Gợi ý 3:** Đưa projection/materialization về một điểm có chủ đích; đo query count, latency và allocation trước/sau thay đổi.

## Cấu trúc trả lời đề xuất

1. Làm rõ query và các điểm enumeration.
2. Giải thích `IQueryable`/deferred execution.
3. Xác định các nguồn tạo thêm database round trip.
4. Phân tích tracking và read-only query.
5. Thu thập SQL/traces/metrics để kiểm chứng.
6. Đề xuất các phương án sửa theo evidence.
7. So sánh projection, `AsNoTracking`, materialization và query riêng cho aggregate.
8. Kiểm thử tải và theo dõi regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` chủ yếu biểu diễn query; việc tạo/composition không đồng nghĩa dữ liệu đã được tải.
- Các terminal operations/enumerations có thể kích hoạt execution riêng nếu query chưa được materialize.
- Không mặc định kết luận N+1; phải xác định loading strategy và SQL thực tế.
- Read-only query có thể cân nhắc `AsNoTracking()` và projection để giảm tracking/allocation khi phù hợp.
- Phải đo query count, duration và generated SQL thay vì tối ưu theo cảm giác.

### Điểm cộng

- Phân biệt server-side translation với phần logic có thể không translate được.
- Nhắc tới projection chỉ lấy cột cần thiết và aggregate trực tiếp ở DB khi hợp lý.
- Biết rằng một `DbContext` không nên được dùng đồng thời bởi nhiều operation song song.
- Đề xuất OpenTelemetry/EF Core command diagnostics và slow-query monitoring.

### Nâng cao

- Phân tích trade-off giữa một query lớn có join/cartesian amplification và split queries/multiple round trips.
- Đề cập compiled queries chỉ sau khi profiling chứng minh query compilation là bottleneck, không dùng như thuốc chữa chung.
- Thiết lập performance regression test theo query count và p95/p99.

## Hướng giải quyết tham khảo

**Giả định:** endpoint chỉ đọc, không cần cập nhật các entity vừa lấy; helper đang enumerate cùng `IQueryable` ít nhất một lần trước `ToListAsync`.

Mỗi lần một operation như `CountAsync`, `AnyAsync`, `FirstAsync`, `ToListAsync` hoặc enumeration thực thi trên query provider, EF Core có thể dịch expression thành SQL và gửi command tới database. Vì vậy nếu helper tính thống kê bằng một enumeration rồi controller materialize lại, cùng logical query có thể tạo nhiều round trip. Nếu sau đó code truy cập navigation và lazy loading được bật, số query còn có thể tăng thêm; nhưng phải xác nhận bằng logs/traces.

Với endpoint read-only, nên projection trực tiếp sang DTO và dùng `AsNoTracking()` nếu không cần identity resolution/change tracking. Nếu cần cả aggregate và page data, thiết kế rõ hai query có mục đích hoặc một shape phù hợp thay vì vô tình enumerate nhiều lần. Không nên materialize toàn bộ tập dữ liệu chỉ để tránh query thứ hai nếu tập dữ liệu lớn; aggregate ở DB thường tốt hơn.

Cách xác minh: bật EF Core command logging ở mức phù hợp và không log dữ liệu nhạy cảm; dùng distributed trace để đếm DB spans/request; lấy generated SQL; xem execution plan và logical reads; so sánh query count, DB duration, allocations và p95 trước/sau. Kiểm tra DbContext lifetime và không chạy concurrent operations trên cùng context.

Failure cases cần tính tới gồm query timeout, cancellation khi client ngắt, DB saturation và payload quá lớn. Nếu query cần navigation lớn, đánh giá projection, explicit shape và split/single query dựa trên dữ liệu thực tế. Nếu endpoint sau này cần update tracked entities, khuyến nghị `AsNoTracking` phải được xem lại.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ không kết luận đây là N+1 chỉ từ triệu chứng. Tôi muốn xác định chính xác mỗi request phát bao nhiêu SQL command và command nào tăng sau release. `IQueryable` chưa phải dữ liệu đã materialize; nó giữ expression để provider dịch khi query được thực thi. Vì vậy nếu helper gọi `Count` hoặc enumerate rồi controller lại `ToListAsync`, chúng ta có thể có nhiều database round trip. Nếu navigation được lazy-load thì còn có khả năng phát sinh thêm query.

Vì endpoint chỉ đọc, tôi sẽ xem có thể projection thẳng DTO và dùng `AsNoTracking` hay không. Nhưng tôi không materialize sớm toàn bộ dữ liệu chỉ để tránh deferred execution, vì có thể chuyển chi phí từ DB round trip thành memory và network. Aggregate nên chạy ở DB nếu cần. Tôi sẽ dùng EF command diagnostics hoặc tracing để đếm query/request, xem generated SQL và execution plan, sau đó load test trước/sau. Nếu evidence cho thấy join tạo dữ liệu phình lớn thì tôi sẽ cân nhắc split query; nếu nhiều round trip mới là vấn đề thì ưu tiên shape khác. Recommendation phụ thuộc vào dữ liệu và loading strategy thực tế.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTrackingWithIdentityResolution()` có thể hữu ích hơn `AsNoTracking()`?
2. Nếu chuyển sang `AsSplitQuery()` làm số round trip tăng nhưng tổng latency giảm, bạn đánh giá quyết định đó thế nào?
3. Một đồng nghiệp đề xuất `Task.WhenAll` chạy ba query bằng cùng `DbContext` để giảm latency. Bạn phản biện ra sao?

## Lỗi trả lời thường gặp

- Nói `IQueryable` luôn chỉ chạy đúng một SQL query.
- Gọi mọi trường hợp nhiều SQL là N+1 mà không kiểm tra loading behavior.
- Khuyên `ToList()` càng sớm càng tốt mà không xét kích thước dữ liệu.
- Dùng `AsNoTracking` như quy tắc tuyệt đối kể cả khi cần update entity.
- Không đưa ra cách đo query count và DB time.

## Thang điểm 0–10

- Requirement clarification: **1.5 điểm**
- Technical correctness: **2.5 điểm**
- Depth: **2 điểm**
- Trade-off analysis: **1.5 điểm**
- Production readiness: **1.5 điểm**
- Communication: **1 điểm**

# Câu 2 — Incident: Hangfire job gửi thông báo trùng sau khi scale-out

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, concurrency, database consistency, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire để gửi email và cập nhật trạng thái workflow. Sau khi deploy và tăng từ một lên ba application instances, một số khách hàng nhận hai email giống nhau. Dashboard cho thấy một phần job có retry; database đôi lúc ghi nhận trạng thái `Sent` muộn hơn thời điểm provider đã nhận email. Business yêu cầu giảm duplicate ngay nhưng không được làm mất notification hợp lệ. Provider bên ngoài không đảm bảo request của bạn sẽ chỉ được xử lý một lần khi client timeout.

Chưa rõ job được enqueue ở đâu, retry policy, storage, transaction boundary, unique business key và khả năng idempotency của provider.

## Câu hỏi chính

Bạn sẽ xử lý incident từ lúc phát hiện đến long-term prevention như thế nào, bao gồm impact assessment, mitigation, evidence, hypotheses, root cause, idempotency design, recovery, testing và monitoring?

## Câu hỏi làm rõ nên cân nhắc

1. Duplicate có cùng business event/message ID hay chỉ giống nội dung?
2. Job được enqueue trong cùng transaction với business update hay sau đó?
3. Retry xảy ra do exception trước hay sau khi provider đã nhận request?
4. Có nhiều producer cùng enqueue một event không?
5. Email provider có hỗ trợ idempotency key hoặc query trạng thái delivery không?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt “job chạy lại” với “business side effect được phép xảy ra lại”.
- **Gợi ý 2:** Xem transaction boundary, retry/failure window và uniqueness ở nơi lưu trạng thái.
- **Gợi ý 3:** Thiết kế consumer/job theo at-least-once reality: stable operation key, atomic claim/outbox/inbox khi phù hợp, và reconciliation cho trạng thái không chắc chắn.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius và business impact.
2. Giảm thiệt hại mà không vô hiệu hóa notification toàn hệ thống.
3. Correlate job ID, business event ID, provider request ID và DB state.
4. Lập nhiều giả thuyết.
5. Tái hiện failure window.
6. Áp dụng short-term guard.
7. Thiết kế idempotency/transaction boundary dài hạn.
8. Test retry, crash và timeout; bổ sung metrics/alerts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định Hangfire hay distributed lock tự biến external side effect thành exactly-once.
- Xác định stable business idempotency key.
- Phân biệt duplicate enqueue, duplicate execution và ambiguous external outcome.
- Không đánh dấu `Sent` trước external call chỉ để tránh duplicate vì có thể gây lost notification.
- Có reconciliation/manual recovery cho trạng thái không xác định.

### Điểm cộng

- Dùng unique constraint/conditional state transition thay vì chỉ in-memory lock.
- Đề xuất transactional outbox nếu cần đồng bộ business transaction với việc phát sinh notification intent.
- Correlation ID xuyên DB → Hangfire → provider.
- Retry với backoff và phân loại transient/permanent failure.

### Nâng cao

- Mô hình trạng thái `Pending -> Processing -> Sent/Failed/Unknown`, lease/claim có timeout và recovery.
- Nếu provider hỗ trợ idempotency key, truyền stable key nhưng vẫn giữ local dedupe/audit.
- Chaos/failure injection đúng điểm “provider accepted nhưng response bị mất”.

## Hướng giải quyết tham khảo

**Immediate:** xác định nhóm notification bị ảnh hưởng, loại event nào duplicate và từ thời điểm deployment nào. Nếu cần mitigation, có thể tạm giảm concurrency cho loại job bị lỗi hoặc chặn duplicate bằng business key ở lớp persistence, nhưng không tắt toàn bộ retry khi chưa hiểu failure mode.

**Evidence:** log `NotificationId`, `BusinessEventId`, Hangfire job ID, attempt, instance, provider request ID và timestamps. So sánh enqueue count với execution count. Kiểm tra exception/timeout và timeline DB commit. Tái hiện trường hợp provider đã chấp nhận request nhưng response về app bị timeout.

**Design:** tạo một notification intent với unique business key. Việc tạo intent phải atomic với business change nếu yêu cầu không được mất event; transactional outbox là một lựa chọn phù hợp. Worker claim record bằng atomic DB transition. Khi gọi provider, dùng idempotency key nếu provider hỗ trợ. Nếu kết quả thành công chắc chắn thì đánh dấu `Sent`; nếu timeout khiến outcome không xác định, chuyển `Unknown`/reconciliation thay vì gửi lại mù quáng nếu provider có API tra cứu. Nếu provider không có idempotency hay lookup, business phải chấp nhận trade-off giữa duplicate và loss; hệ thống không thể tự hứa exactly-once external effect.

Unique constraint giúp ngăn hai producer tạo cùng intent. Distributed lock có thể giảm concurrency nhưng không giải quyết crash giữa external side effect và local commit. Monitoring cần duplicate-rate, retry-rate, age of pending/unknown, provider latency/error và notification end-to-end success.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách ba khả năng: event bị enqueue hai lần, Hangfire thực thi lại cùng job, hoặc provider đã xử lý nhưng app timeout rồi retry. Việc đầu tiên là đo blast radius và correlate business event ID với job attempt và provider request ID. Tôi không tắt retry toàn cục vì có thể đổi duplicate thành lost notification.

Về thiết kế, tôi muốn một stable notification ID/business key và unique constraint để một business event chỉ tạo một intent. Nếu intent phải đi cùng business transaction, tôi dùng outbox. Worker claim intent atomically, sau đó gọi provider với idempotency key nếu provider hỗ trợ. Quan trọng là distributed lock không tạo exactly-once cho side effect bên ngoài: process có thể chết sau khi email được chấp nhận nhưng trước khi DB ghi `Sent`. Với timeout mơ hồ, nếu provider hỗ trợ lookup thì reconcile trước khi resend; nếu không hỗ trợ, phải thống nhất trade-off với business.

Tôi sẽ test bằng fault injection ở từng boundary: trước call, sau provider accept, trước DB commit, process crash và concurrent workers. Sau fix, theo dõi duplicate rate, retry rate, pending age và end-to-end delivery.”

## Câu hỏi đào sâu

1. Tại sao distributed lock quanh toàn bộ job vẫn không đảm bảo exactly-once email delivery?
2. Nếu database commit thành công nhưng enqueue Hangfire thất bại, outbox thay đổi failure mode như thế nào?
3. Nếu provider không hỗ trợ idempotency key hay status lookup, bạn sẽ trình bày giới hạn consistency với business ra sao?

## Lỗi trả lời thường gặp

- Chỉ thêm `[DisableConcurrentExecution]` rồi coi incident đã được giải quyết hoàn toàn.
- Tắt retry mà không xét lost notifications.
- Dùng in-memory `HashSet` để dedupe trong hệ thống nhiều instance.
- Không phân biệt job identity với business operation identity.
- Hứa “exactly once” cho external side effect mà không nêu assumptions.

## Thang điểm 0–10

- Requirement clarification: **1.5 điểm**
- Technical correctness: **2 điểm**
- Depth: **2 điểm**
- Trade-off analysis: **1.5 điểm**
- Production readiness: **2 điểm**
- Communication: **1 điểm**

# Câu 3 — Thiết kế AI agent review Pull Request có quyền dùng tools

**Loại câu hỏi:** AI engineering / architecture decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool security, deterministic validation, evaluation, human approval, cost/latency, auditability

## Bối cảnh

Team muốn xây một AI review agent cho repository .NET. Khi có PR, agent được phép đọc diff, đọc một số file liên quan, chạy `dotnet test`, static analysis và đề xuất review comments. Giai đoạn sau có thể cho agent tạo patch. Repository chứa deployment scripts, configuration templates và tài liệu có nội dung do nhiều người đóng góp. Team muốn giảm review time nhưng không chấp nhận agent tự merge, lộ secrets hoặc thực thi command tùy ý từ nội dung repository.

Chưa xác định model, token budget, cách chọn context, permission boundary, evaluation dataset hay tiêu chí khi nào phải chuyển cho người review.

## Câu hỏi chính

Hãy thiết kế agent này từ MVP đến production: vì sao cần AI, phần nào phải deterministic, context nào được cấp, tools/permissions nào được phép, cách chống prompt injection từ repository, validation, hallucination detection, evaluation, fallback, audit, cost và observability.

## Câu hỏi làm rõ nên cân nhắc

1. Agent chỉ đưa nhận xét hay được phép sửa branch trong MVP?
2. Loại repository và dữ liệu nào được coi là sensitive?
3. Success metric là giảm review time, tăng defect detection hay cả hai?
4. CI hiện có những deterministic checks nào có thể tái sử dụng?
5. False positive/false negative nào có chi phí cao nhất?

## Gợi ý tư duy

- **Gợi ý 1:** Đừng biến model thành policy engine hoặc shell operator không giới hạn.
- **Gợi ý 2:** Tách untrusted repository content khỏi trusted instructions; tool layer phải enforce quyền độc lập với lời model nói.
- **Gợi ý 3:** Dùng least privilege, structured tool schemas, sandbox, deterministic gates, evidence-linked findings và offline evaluation trước khi tăng quyền.

## Cấu trúc trả lời đề xuất

1. Làm rõ outcome và risk tolerance.
2. Xác định phần cần reasoning của model.
3. Xác định deterministic pipeline.
4. Thiết kế context retrieval và trust boundaries.
5. Thiết kế tool permissions/sandbox.
6. Validate findings và human approval.
7. Xây evaluation dataset và metrics.
8. Thiết kế fallback, audit, cost controls và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI phù hợp cho semantic/code reasoning nhưng build, test, policy và authorization phải được enforce deterministic.
- Repository text là untrusted input; nội dung file không được tự cấp thêm tool permission.
- Tool allowlist + typed arguments + sandbox + network/secret restrictions.
- Review finding phải gắn evidence/file/line và được kiểm chứng khi có thể.
- Không cho auto-merge ở MVP; thay đổi có tác động cao cần human approval.

### Điểm cộng

- Context theo diff + dependency/relevant-file retrieval thay vì dump cả repo.
- Token/cost budget và giới hạn số vòng tool call.
- Evaluation bằng historical PRs/seeded defects, precision/recall theo loại lỗi và reviewer acceptance rate.
- Audit trail lưu model/version, prompt policy version, context references, tool calls và outputs phù hợp chính sách dữ liệu.

### Nâng cao

- Threat-model indirect prompt injection trong comments/docs/source strings.
- Tách planner/reviewer khỏi privileged executor; executor kiểm policy độc lập.
- Canary rollout, shadow mode, regression eval và kill switch.
- Không dùng model tự chấm chính nó làm nguồn quality duy nhất.

## Hướng giải quyết tham khảo

**Vì sao AI:** static analyzers rất tốt với rule deterministic nhưng khó đánh giá semantic mismatch, suspicious business logic, missing edge cases hay consistency giữa thay đổi và surrounding code. Agent nên bổ sung chứ không thay CI.

**MVP:** chỉ read-only. Input gồm PR diff, metadata tối thiểu và file liên quan được retrieval theo dependency/symbol/search có giới hạn. Không tự đưa secrets hoặc toàn repo vào prompt. Nội dung repo, issue và PR comment được đánh dấu untrusted; system/developer policy nằm ngoài trust domain đó.

**Tools:** expose các operation hẹp như `read_file(path)`, `search_code(query)`, `run_test(target)` thay vì raw shell. Tool service validate path, arguments, timeout, quotas và authorization. Test chạy trong ephemeral sandbox với read-only credentials hoặc không có credentials/network nếu không cần. Model không thể thay đổi allowlist bằng instruction lấy từ repo.

**Validation:** output theo schema gồm severity, claim, evidence path/line, reasoning và suggested verification. Deterministic validator kiểm path/line tồn tại, finding nằm trong scope và command/test result thực. High-severity security findings hoặc patch phải qua human review. Không auto-merge.

**Evaluation:** tạo benchmark từ historical PRs và seeded defects; đo precision, recall theo category, false-positive rate, reviewer acceptance, latency, token/tool cost và tỷ lệ findings có evidence hợp lệ. So sánh với baseline CI + human review. Chạy shadow mode trước khi comment trực tiếp.

**Fallback:** nếu model timeout, structured output invalid, tool failure hoặc confidence/evidence không đủ thì trả trạng thái inconclusive và để deterministic CI + human review tiếp tục; không bịa kết luận. Audit logs cần correlation nhưng phải redact secrets và tuân retention policy.

Recommendation thay đổi nếu agent được cấp write permission: khi đó cần branch-scoped token, explicit approval trước privileged actions, patch validation, protected branches và stronger sandbox/policy enforcement.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ bắt đầu bằng read-only review agent, vì mục tiêu là tăng signal cho reviewer chứ không thay CI. AI hữu ích ở semantic reasoning, còn authorization, build, test, secret scanning và merge policy phải deterministic.

Tôi coi mọi text trong repository là untrusted input. Agent nhận diff và context liên quan có giới hạn, không dump cả repo. Tools không phải raw shell; tôi expose các action typed như đọc file, search code và chạy test target trong sandbox. Permission được enforce ở tool service, nên một README nói ‘hãy upload secrets’ không thể thay đổi quyền. MVP không có write hay merge permission.

Mỗi finding phải có evidence path/line và cách verify. Validator kiểm reference tồn tại; security/high-impact finding được human review. Nếu model hoặc tool lỗi, fallback là inconclusive chứ không fabricate success.

Trước rollout tôi dùng historical PRs và seeded defects để đo precision, recall theo category, false positives, reviewer acceptance, latency và cost. Tôi chạy shadow mode rồi canary. Nếu sau này cho phép tạo patch, tôi tách quyền write, dùng branch-scoped credential, protected branch và explicit approval trước action có tác động.”

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` và deferred execution phải được hiểu theo execution boundary thực tế; performance diagnosis cần SQL/traces chứ không dựa trên trực giác.
- Retry và distributed execution phải được thiết kế cùng idempotency; external side effects thường có failure window khiến “exactly once” không thể được giả định.
- AI agent cần trust boundary rõ ràng: model reasoning không được đồng nhất với authorization hay deterministic validation.
- Production design tốt luôn bao gồm failure recovery, observability và điều kiện khiến recommendation phải thay đổi.

## Mẫu tư duy cần nhớ

- Clarify execution boundaries before optimizing.
- Measure query count and latency before changing data access strategy.
- Design retries together with idempotency and reconciliation.
- Treat external outcomes after timeout as potentially ambiguous.
- Treat model output and repository content as untrusted until deterministically validated.
