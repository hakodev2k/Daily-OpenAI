# Code Review Challenge 1 — Rate limiter in-memory bị bypass trên nhiều instance và tự tạo race condition dưới burst traffic

**Chủ đề:** Concurrency và race conditions, caching/state management, authentication & authorization, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API có endpoint tạo báo cáo lương khá tốn CPU và database I/O. Để tránh một tenant gửi quá nhiều request, team thêm rate limiter đơn giản: tối đa 20 request/phút cho mỗi tenant.

Hệ thống chạy trên 8 instance sau load balancer. Traffic bình thường khoảng 30–50 request/giây nhưng đầu tháng có burst cao hơn nhiều. Sau khi deploy rate limiter, production vẫn ghi nhận:

- một tenant có thể vượt xa 20 request/phút khi request được phân phối qua nhiều instance,
- thỉnh thoảng xuất hiện exception liên quan collection khi nhiều request cùng vào một tenant,
- memory của process tăng dần theo số tenant/key đã từng gọi API,
- một số tenant bị chặn bất thường dù request rate thực tế thấp,
- metric hiện tại chỉ đếm tổng số `429`, không biết tenant nào hoặc instance nào đang bị giới hạn,
- security review phát hiện `tenantId` được lấy trực tiếp từ header do client gửi.

Business yêu cầu quota theo tenant phải dựa trên tenant identity đáng tin cậy, phải chịu được multi-instance deployment và không được khiến chính rate limiter trở thành điểm nghẽn hoặc nguồn lỗi.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class PayrollReportsController : ControllerBase
{
    private static readonly ConcurrentDictionary<string, Queue<DateTime>> Requests = new();

    private readonly PayrollReportService _service;
    private readonly ILogger<PayrollReportsController> _logger;

    public PayrollReportsController(
        PayrollReportService service,
        ILogger<PayrollReportsController> logger)
    {
        _service = service;
        _logger = logger;
    }

    [Authorize]
    [HttpPost("payroll")]
    public async Task<IActionResult> Generate(
        PayrollReportRequest request,
        CancellationToken cancellationToken)
    {
        var tenantId = Request.Headers["X-Tenant-Id"].ToString();
        var now = DateTime.UtcNow;

        var queue = Requests.GetOrAdd(
            tenantId,
            _ => new Queue<DateTime>());

        while (queue.Count > 0 &&
               now - queue.Peek() > TimeSpan.FromMinutes(1))
        {
            queue.Dequeue();
        }

        if (queue.Count >= 20)
        {
            _logger.LogWarning(
                "Rate limit exceeded for tenant {TenantId}",
                tenantId);

            return StatusCode(StatusCodes.Status429TooManyRequests);
        }

        queue.Enqueue(now);

        var result = await _service.GenerateAsync(
            tenantId,
            request,
            cancellationToken);

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Tenant identity lấy từ header do client kiểm soát

**Problem:** `tenantId` lấy trực tiếp từ `X-Tenant-Id`.  
**Why it happens:** Code coi transport input như security context.  
**Production impact:** Client có thể đổi tenant key để bypass quota hoặc làm tăng số key vô hạn trong limiter.  
**Severity:** Critical  
**Recommended fix:** Lấy tenant từ authenticated claims/server-side tenant context đã được xác minh; không dùng arbitrary client header làm nguồn authority.

### 2. Quota chỉ tồn tại trên từng instance

**Problem:** `static` chỉ chia sẻ trong một process.  
**Why it happens:** Mỗi application instance có dictionary riêng.  
**Production impact:** Với 8 instance, một tenant có thể thực tế gửi gần nhiều lần quota thiết kế tùy cách load balancer phân phối request.  
**Severity:** High  
**Recommended fix:** Nếu quota phải mang nghĩa toàn cụm, dùng distributed rate-limit state/coordination phù hợp hoặc gateway/API management hỗ trợ quota tập trung. Nếu quota per-instance là chấp nhận được thì phải mô tả đúng semantics và sizing tương ứng.

### 3. `Queue<DateTime>` không thread-safe

**Problem:** Nhiều request cùng tenant có thể gọi `Count`, `Peek`, `Dequeue`, `Enqueue` đồng thời.  
**Why it happens:** `ConcurrentDictionary` chỉ đảm bảo thao tác trên dictionary; object `Queue<DateTime>` bên trong vẫn mutable và không thread-safe.  
**Production impact:** Race condition, dữ liệu cửa sổ sai hoặc exception dưới burst traffic.  
**Severity:** High  
**Recommended fix:** Dùng primitive/data structure có synchronization đúng, hoặc tránh tự triển khai bằng rate-limiting abstraction đã được thiết kế cho concurrency.

### 4. Check-then-enqueue không atomic

**Problem:** Hai request có thể cùng thấy `queue.Count == 19` rồi cả hai đều enqueue.  
**Why it happens:** Việc purge, check và add là chuỗi thao tác tách rời.  
**Production impact:** Limit bị vượt ngay cả trên một instance, đặc biệt khi burst cùng tenant.  
**Severity:** High  
**Recommended fix:** Toàn bộ state transition của một key phải atomic theo thiết kế limiter.

### 5. Dictionary tăng không giới hạn

**Problem:** Tenant/key đã từng xuất hiện được giữ vĩnh viễn.  
**Why it happens:** Không có eviction/expiration của key khi queue rỗng hoặc tenant không còn hoạt động.  
**Production impact:** Memory tăng theo lifetime của process; attacker còn có thể tạo nhiều tenant key giả nếu identity chưa được bảo vệ.  
**Severity:** High  
**Recommended fix:** Dùng state có TTL/eviction hoặc limiter implementation quản lý partition lifecycle; không giữ dictionary key mãi mãi.

### 6. Sliding window dùng clock wall-time không được đóng gói/test tốt

**Problem:** Logic phụ thuộc trực tiếp `DateTime.UtcNow`.  
**Why it happens:** Không có time abstraction.  
**Production impact:** Khó test boundary của cửa sổ; thay đổi clock hệ thống có thể làm behavior khó dự đoán.  
**Severity:** Medium  
**Recommended fix:** Inject time provider/clock abstraction cho logic tự viết; tốt hơn nữa dùng limiter có semantics đã kiểm chứng.

### 7. Không phân biệt quota admission với giới hạn tài nguyên thực thi

**Problem:** Rate 20/phút không bảo đảm chỉ có số lượng nhỏ report chạy đồng thời.  
**Why it happens:** Rate limiting và concurrency limiting bị xem là cùng một vấn đề.  
**Production impact:** 20 request có thể cùng lọt vào trong vài giây và vẫn tạo spike CPU/DB.  
**Severity:** Medium  
**Recommended fix:** Nếu tài nguyên đắt, cân nhắc thêm concurrency limiter/backpressure hoặc chuyển sang queued background processing.

### 8. Không trả metadata hữu ích cho client khi bị giới hạn

**Problem:** Chỉ trả `429` trống.  
**Why it happens:** Endpoint không biểu đạt retry semantics.  
**Production impact:** Client retry mù, có thể tạo retry storm.  
**Severity:** Medium  
**Recommended fix:** Trả thông tin retry phù hợp theo API contract và tránh để nhiều client đồng loạt retry cùng thời điểm.

### 9. Logging tenant id cần policy và cardinality phù hợp

**Problem:** Tenant id có thể hữu ích trong logs nhưng không nên tùy tiện dùng làm metric dimension nếu tenant cardinality rất lớn.  
**Why it happens:** Chưa tách rõ logs, traces và metrics.  
**Production impact:** Có thể làm telemetry cardinality/chi phí tăng.  
**Severity:** Low  
**Recommended fix:** Log tenant theo policy nếu cần; metrics nên dùng labels hữu hạn hoặc aggregation phù hợp, còn điều tra chi tiết đi qua trace/log.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng thiết kế: tenant identity lấy từ context đáng tin cậy và rate limiter được tách thành dependency có thể dùng implementation local hoặc distributed tùy yêu cầu hệ thống.

```csharp
public interface ITenantRateLimiter
{
    Task<RateLimitDecision> AcquireAsync(
        string tenantId,
        CancellationToken cancellationToken);
}

public sealed record RateLimitDecision(
    bool Allowed,
    TimeSpan? RetryAfter);

[ApiController]
[Route("api/reports")]
public sealed class PayrollReportsController : ControllerBase
{
    private readonly ITenantContext _tenantContext;
    private readonly ITenantRateLimiter _rateLimiter;
    private readonly PayrollReportService _service;

    public PayrollReportsController(
        ITenantContext tenantContext,
        ITenantRateLimiter rateLimiter,
        PayrollReportService service)
    {
        _tenantContext = tenantContext;
        _rateLimiter = rateLimiter;
        _service = service;
    }

    [Authorize]
    [HttpPost("payroll")]
    public async Task<IActionResult> Generate(
        PayrollReportRequest request,
        CancellationToken cancellationToken)
    {
        var tenantId = _tenantContext.TenantId;

        var decision = await _rateLimiter.AcquireAsync(
            tenantId,
            cancellationToken);

        if (!decision.Allowed)
        {
            if (decision.RetryAfter is { } retryAfter)
            {
                Response.Headers.RetryAfter =
                    Math.Max(1, (int)Math.Ceiling(retryAfter.TotalSeconds)).ToString();
            }

            return StatusCode(StatusCodes.Status429TooManyRequests);
        }

        var result = await _service.GenerateAsync(
            tenantId,
            request,
            cancellationToken);

        return Ok(result);
    }
}
```

Implementation của `ITenantRateLimiter` nên được chọn theo semantics thật:

- single instance: limiter in-process có atomic partition state và eviction,
- nhiều instance nhưng quota chỉ cần per-instance: vẫn có thể local nhưng phải sizing rõ,
- quota toàn cụm: dùng distributed coordination/gateway phù hợp,
- workload rất đắt: kết hợp rate limit với concurrency limit hoặc queue.

## Trade-offs

- Limiter distributed tăng network round-trip và thêm dependency, nhưng đổi lại quota có semantics toàn cụm.
- Limiter local nhanh và đơn giản hơn, phù hợp nếu quota per-instance là đủ hoặc traffic đã được sticky partitioning có chủ đích.
- Queue background cho report nặng giúp backpressure tốt hơn nhưng thay đổi UX từ synchronous sang asynchronous polling/notification.
- Quota cực chính xác có thể tốn coordination cao; một số hệ thống chấp nhận approximate rate limiting để đổi lấy throughput và availability.

## Cách kiểm thử

1. **Concurrency test:** 100 request đồng thời cho cùng tenant trên một process; verify không crash và số request được accept đúng semantics.
2. **Multi-instance test:** Bắn load qua nhiều instance; verify quota toàn cụm nếu đó là requirement.
3. **Security test:** Client thay `X-Tenant-Id`; quota và authorization vẫn dựa trên tenant claim/server context.
4. **Memory test:** Tạo nhiều tenant/key theo thời gian rồi để idle; verify state được eviction và memory không tăng vô hạn.
5. **Burst/load test:** Tenant gửi burst lớn; đo CPU, DB concurrency, `429`, retry behavior và p95/p99 latency.

## Quan sát trong production

- Metric: allowed/denied count, current concurrency, queue depth nếu có, limiter decision latency.
- Log structured cho decision bị deny với tenant/correlation theo policy, không log arbitrary client header như authority.
- Trace span quanh rate-limit decision và report generation để phân biệt latency do admission hay business logic.
- Alert nếu deny rate tăng bất thường, limiter dependency lỗi hoặc DB concurrency vượt ngưỡng vận hành.
- Nếu dùng distributed store, theo dõi latency/error rate của store vì limiter không nên trở thành single point of failure không được quan sát.

3. Nếu một tenant mua gói cao hơn và có quota động, bạn cập nhật limiter state thế nào mà không gây race hoặc reset quota sai?

# Code Review Challenge 2 — Stream dữ liệu lớn từ EF Core nhưng giữ DB connection quá lâu và bỏ qua client cancellation

**Chủ đề:** async/await và cancellation, EF Core query execution, resource lifetime, performance, error handling, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core endpoint export audit events dưới dạng NDJSON để tránh tạo một `List` hàng triệu record trong memory. Team chuyển sang `AsAsyncEnumerable()` và ghi từng record trực tiếp xuống `Response.Body`.

Mỗi export có thể từ 100.000 đến hơn 2 triệu row. Production ghi nhận:

- khi nhiều người export đồng thời, connection pool database cạn dần,
- request có thể chạy hàng chục phút,
- user đóng browser nhưng server đôi lúc vẫn tiếp tục query và serialize,
- client mạng chậm làm transaction/read query kéo dài,
- deploy/shutdown mất nhiều thời gian vì export đang chạy,
- một lỗi ghi response giữa chừng làm log chỉ có `ObjectDisposedException` hoặc `IOException` mà không rõ đã gửi bao nhiêu row.

Business chấp nhận export kéo dài, nhưng không muốn một vài client chậm giữ tài nguyên database quá lâu. Dữ liệu phải được lọc theo tenant và cần có strategy rõ cho cancellation/failure.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditExportController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<AuditExportController> _logger;

    public AuditExportController(
        AppDbContext db,
        ITenantContext tenantContext,
        ILogger<AuditExportController> logger)
    {
        _db = db;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    [Authorize]
    [HttpGet("export")]
    public async Task Export(
        DateTime from,
        DateTime to)
    {
        Response.ContentType = "application/x-ndjson";

        var tenantId = _tenantContext.TenantId;

        var query = _db.AuditEvents
            .Where(x => x.TenantId == tenantId &&
                        x.CreatedAt >= from &&
                        x.CreatedAt < to)
            .OrderBy(x => x.CreatedAt)
            .AsAsyncEnumerable();

        var count = 0;

        await foreach (var item in query)
        {
            var json = JsonSerializer.Serialize(new
            {
                item.Id,
                item.CreatedAt,
                item.EventType,
                item.ActorId,
                item.Payload
            });

            await Response.WriteAsync(json);
            await Response.WriteAsync("\n");

            count++;

            if (count % 100 == 0)
                await Response.Body.FlushAsync();
        }

        _logger.LogInformation(
            "Exported {Count} audit events for tenant {TenantId}",
            count,
            tenantId);
    }
}
```

## Kết quả code review tham khảo

### 1. Không dùng request cancellation cho query và response write

**Problem:** Method không nhận `CancellationToken`; query enumeration và `WriteAsync` không được truyền token.  
**Why it happens:** `RequestAborted` không đi xuyên suốt pipeline.  
**Production impact:** User đóng browser nhưng server vẫn có thể tiếp tục đọc DB, serialize và ghi cho tới khi I/O fail hoặc query kết thúc.  
**Severity:** High  
**Recommended fix:** Nhận `CancellationToken` từ action và truyền vào async enumeration, serializer/write/flush khi API hỗ trợ.

### 2. Database connection/reader có thể bị giữ suốt thời gian client download

**Problem:** `await foreach` đọc từng row và ngay lập tức chờ network write trước khi đọc tiếp.  
**Why it happens:** Database enumeration và response streaming nằm trên cùng một backpressure path.  
**Production impact:** Slow client kéo dài lifetime của data reader/connection, dễ làm cạn connection pool khi nhiều export đồng thời.  
**Severity:** High  
**Recommended fix:** Với export lớn, tách database read khỏi network delivery bằng chunked paging, staging file/blob hoặc background export. Nếu vẫn stream trực tiếp, cần concurrency limit và hiểu rõ connection lifetime.

### 3. Query read-only vẫn tracking entity

**Problem:** Query không dùng `AsNoTracking()`.  
**Why it happens:** DbContext mặc định tracking entity materialized.  
**Production impact:** Change tracker có thể giữ reference tới rất nhiều entity trong suốt request, làm memory tăng đáng kể dù code “streaming”.  
**Severity:** High  
**Recommended fix:** Dùng `AsNoTracking()` hoặc projection trực tiếp sang export DTO.

### 4. Không có giới hạn khoảng thời gian/export size

**Problem:** Client có thể yêu cầu range rất lớn.  
**Why it happens:** `from`/`to` chưa có policy.  
**Production impact:** Một request hợp lệ về auth vẫn có thể tạo query hàng triệu/mười triệu row và giữ tài nguyên lâu.  
**Severity:** High  
**Recommended fix:** Validate range, quota, max rows/size hoặc chuyển large export sang background workflow.

### 5. Thứ tự chỉ theo `CreatedAt` không deterministic nếu nhiều row cùng timestamp

**Problem:** Nhiều event có cùng `CreatedAt` có thể có order không ổn định.  
**Why it happens:** Sort key không unique.  
**Production impact:** Nếu sau này chuyển sang paging/chunking có thể gây duplicate/missing row giữa page.  
**Severity:** Medium  
**Recommended fix:** Dùng deterministic ordering như `OrderBy(CreatedAt).ThenBy(Id)`; nếu paging lớn, cân nhắc keyset pagination theo `(CreatedAt, Id)`.

### 6. Serialize thành `string` cho từng record tạo allocation không cần thiết

**Problem:** Mỗi row tạo JSON string trung gian.  
**Why it happens:** `JsonSerializer.Serialize` trả string rồi mới write.  
**Production impact:** Với hàng triệu row, allocation/GC tăng đáng kể.  
**Severity:** Medium  
**Recommended fix:** Serialize trực tiếp xuống stream/writer khi phù hợp hoặc dùng reusable buffer/writer có kiểm soát.

### 7. Flush quá thường xuyên có thể giảm throughput

**Problem:** Flush mỗi 100 row không dựa trên kích thước byte hoặc network behavior.  
**Why it happens:** Chọn threshold theo row count tùy ý.  
**Production impact:** Tăng syscall/transport overhead; payload nhỏ/lớn khác nhau rất nhiều.  
**Severity:** Medium  
**Recommended fix:** Để buffering của server xử lý hoặc flush theo byte/time policy có đo đạc; chỉ flush sớm nếu UX yêu cầu.

### 8. Không có failure-progress telemetry

**Problem:** Chỉ log khi export hoàn tất.  
**Why it happens:** Failure path không ghi count/elapsed/bytes đã gửi.  
**Production impact:** Khi client disconnect hoặc DB fail, khó biết failure xảy ra ở row thứ bao nhiêu và tài nguyên bị giữ bao lâu.  
**Severity:** Medium  
**Recommended fix:** Structured completion/failure log với tenant, export id, rows, elapsed, cancellation reason và bytes approximate; tránh log payload nhạy cảm.

## Phiên bản code đề xuất

Một hướng vẫn stream trực tiếp nhưng giảm rủi ro bằng cancellation, no-tracking, projection, deterministic ordering và limit rõ ràng:

```csharp
public sealed record AuditExportRow(
    Guid Id,
    DateTime CreatedAt,
    string EventType,
    string? ActorId,
    string Payload);

[ApiController]
[Route("api/audit")]
public sealed class AuditExportController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;

    public AuditExportController(
        AppDbContext db,
        ITenantContext tenantContext)
    {
        _db = db;
        _tenantContext = tenantContext;
    }

    [Authorize]
    [HttpGet("export")]
    public async Task<IActionResult> Export(
        DateTime from,
        DateTime to,
        CancellationToken cancellationToken)
    {
        if (to <= from || to - from > TimeSpan.FromDays(31))
            return BadRequest("Invalid export range.");

        Response.ContentType = "application/x-ndjson";

        var tenantId = _tenantContext.TenantId;

        var query = _db.AuditEvents
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId &&
                        x.CreatedAt >= from &&
                        x.CreatedAt < to)
            .OrderBy(x => x.CreatedAt)
            .ThenBy(x => x.Id)
            .Select(x => new AuditExportRow(
                x.Id,
                x.CreatedAt,
                x.EventType,
                x.ActorId,
                x.Payload));

        await foreach (var item in query
            .AsAsyncEnumerable()
            .WithCancellation(cancellationToken))
        {
            await JsonSerializer.SerializeAsync(
                Response.Body,
                item,
                cancellationToken: cancellationToken);

            await Response.Body.WriteAsync(
                "\n"u8.ToArray(),
                cancellationToken);
        }

        return new EmptyResult();
    }
}
```

Với export hàng triệu row hoặc client thường chậm, hướng production-ready hơn thường là:

1. API tạo `ExportRequest` và trả `202 Accepted`.
2. Background worker đọc DB theo chunk/keyset pagination.
3. Ghi file vào durable storage.
4. Client tải file sau khi hoàn tất.
5. DB connection chỉ được giữ cho từng chunk, không phụ thuộc tốc độ download của client.

## Trade-offs

- Direct streaming cho time-to-first-byte tốt và không cần storage trung gian, nhưng DB lifetime bị gắn vào tốc độ client.
- Background export tăng độ phức tạp, storage cost và cleanup lifecycle, nhưng cô lập tốt hơn giữa database và network download.
- Chunked paging giảm connection hold time nhưng cần deterministic ordering và xử lý consistency giữa các page.
- Nếu yêu cầu snapshot tuyệt đối tại một thời điểm, background export có thể cần snapshot/versioning/transaction strategy riêng, làm tăng chi phí.

## Cách kiểm thử

1. **Client disconnect test:** Bắt đầu export rồi hủy request; verify DB command dừng và connection được trả pool nhanh.
2. **Slow-client test:** Throttle bandwidth; đo connection hold time và số export đồng thời trước khi pool saturation.
3. **Large-data test:** 1–2 triệu row; đo memory, GC, allocations, rows/sec và total duration.
4. **Failure-path test:** Inject DB timeout hoặc response I/O failure; verify cancellation/failure log có export id, count và elapsed.
5. **Correctness test:** Nhiều row cùng `CreatedAt`; verify ordering/paging không duplicate hoặc bỏ sót khi dùng chunk strategy.

## Quan sát trong production

- Metric: active exports, export duration, rows exported, bytes written, canceled exports, failures by stage.
- DB observation: active connections/readers, command duration, connection pool saturation, rows read.
- Trace: export request span + DB query spans/chunk spans.
- Structured log khi start/completed/canceled/failed với export id, tenant, range, row count, elapsed; không log raw payload.
- Alert khi active export vượt ngưỡng, pool gần cạn hoặc p95 export DB chunk duration tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Nếu export phải phản ánh snapshot nhất quán trong 30 phút xử lý, bạn thiết kế consistency thế nào?
2. Khi nào keyset pagination tốt hơn offset pagination cho export lớn?
3. Nếu file export chứa dữ liệu nhạy cảm, bạn xử lý authorization, encryption, retention và download link expiration ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `ConcurrentDictionary<TKey,TValue>` không làm cho mutable `TValue` bên trong tự động thread-safe.
- Rate limiting cần xác định rõ scope: per-process, per-instance hay toàn cluster; security identity phải đến từ nguồn đáng tin cậy.
- Rate limiting, concurrency limiting và backpressure là các cơ chế khác nhau dù cùng phục vụ bảo vệ tài nguyên.
- Streaming giúp giảm peak memory nhưng có thể kéo dài lifetime của DB reader/connection nếu gắn trực tiếp với tốc độ network client.
- Với read-only EF Core query lớn, `AsNoTracking`, projection, deterministic ordering, cancellation và chunking là những yếu tố cần xem xét sớm.

## Mẫu tư duy cần nhớ

- Xác định scope của state trước khi dùng `static` hoặc in-memory coordination.
- Không dùng client-controlled input làm security boundary.
- Thread-safe container không đồng nghĩa thread-safe object graph.
- Tách database lifetime khỏi network lifetime cho workload dài.
- Streaming không thay thế cho cancellation, backpressure và observability.
