# Code Review Challenge 1 — Optimizely publish event gọi search + CDN đồng bộ: editor bấm Publish một lần nhưng production chậm, timeout và đôi lúc side effect chạy lặp

**Chủ đề:** C#/.NET 8, Optimizely CMS, `IContentEvents`, ASP.NET Core, synchronous event handling, external dependencies, background processing, idempotency, multi-instance behavior, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một marketing website chạy Optimizely CMS trên nhiều application instances. Khi editor publish một `ArticlePage`, team muốn:

- cập nhật search index;
- purge CDN cho URL của page;
- gửi webhook sang CRM nếu page thuộc campaign;
- editor không phải chờ quá lâu sau khi bấm Publish;
- một transient network failure không được làm content publish thất bại một cách khó hiểu;
- side effect có thể eventual-consistent trong vài chục giây;
- nếu event bị xử lý lại, search/CDN/CRM không được tạo kết quả sai hoặc duplicate business action;
- deployment/restart không được làm mất durable work quan trọng;
- production cần biết publish latency, failed side effects, retry backlog và duplicate-processing rate.

Sau khi traffic editorial tăng và site scale-out, production xuất hiện:

- editor đôi lúc phải chờ 10–20 giây khi publish;
- nếu CRM chậm, publish request có thể timeout;
- một số page đã publish nhưng search/CDN cập nhật muộn hoặc không cập nhật;
- CRM đôi lúc nhận cùng webhook hai lần;
- restart trong lúc deploy có thể khiến một số side effect không chạy;
- team cho rằng `PublishedContent` là “event” nên mọi thứ bên trong handler mặc nhiên đã asynchronous và retry-safe.

## Đoạn code cần review

```csharp
[InitializableModule]
public sealed class ContentPublishModule : IInitializableModule
{
    private IContentEvents? _contentEvents;
    private SearchClient? _search;
    private CdnClient? _cdn;
    private CrmClient? _crm;
    private ILogger<ContentPublishModule>? _logger;

    public void Initialize(InitializationEngine context)
    {
        _contentEvents = context.Locate.Advanced
            .GetInstance<IContentEvents>();
        _search = context.Locate.Advanced.GetInstance<SearchClient>();
        _cdn = context.Locate.Advanced.GetInstance<CdnClient>();
        _crm = context.Locate.Advanced.GetInstance<CrmClient>();
        _logger = context.Locate.Advanced
            .GetInstance<ILogger<ContentPublishModule>>();

        _contentEvents.PublishedContent += OnPublished;
    }

    private void OnPublished(
        object? sender,
        ContentEventArgs e)
    {
        if (e.Content is not ArticlePage article)
            return;

        _search!.IndexArticleAsync(article)
            .GetAwaiter()
            .GetResult();

        _cdn!.PurgeAsync(article.ContentLink)
            .GetAwaiter()
            .GetResult();

        if (!string.IsNullOrWhiteSpace(article.CampaignId))
        {
            _crm!.SendPublishedWebhookAsync(new
            {
                ArticleId = article.ContentGuid,
                CampaignId = article.CampaignId,
                PublishedAtUtc = DateTime.UtcNow
            })
            .GetAwaiter()
            .GetResult();
        }

        _logger!.LogInformation(
            "Processed publish side effects for {ContentGuid}",
            article.ContentGuid);
    }

    public void Uninitialize(InitializationEngine context)
    {
        if (_contentEvents is not null)
            _contentEvents.PublishedContent -= OnPublished;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems và lifecycle concerns trong publish handler.
2. Xác định reliability, performance, multi-instance và failure-handling issues.
3. Giải thích production impact khi external dependency chậm, timeout hoặc application restart.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa, tránh biến publish path thành distributed transaction giả.
6. Giải thích testing cho duplicate event, dependency failure, restart và high editorial load.
7. Đề xuất production telemetry để chứng minh side effects được xử lý đúng.

## Câu hỏi gợi mở

1. Việc gọi `.GetAwaiter().GetResult()` trong content event handler ảnh hưởng gì tới publish latency và request/thread đang thực thi?
2. Nếu search thành công nhưng CDN hoặc CRM thất bại, state cuối cùng của business operation là gì?
3. Nếu application restart sau khi content đã publish nhưng trước khi CRM call hoàn tất, đâu là durable record chứng minh công việc còn phải làm?
4. Nếu cùng content event được quan sát nhiều lần hoặc xử lý ở nhiều nơi, điều gì làm các side effects idempotent?
5. Side effect nào thực sự cần nằm trên critical publish path, và side effect nào có thể eventual-consistent?

## Gợi ý

### Gợi ý 1

Primary risk là **gắn external I/O trực tiếp vào content lifecycle event**, làm editorial path phụ thuộc vào latency và reliability của nhiều hệ thống khác.

### Gợi ý 2

Reasoning theo transaction boundary: CMS publish là một state change; search/CDN/CRM là các side effects ngoài transaction đó. Nếu chúng cần retry/recovery, cần một durable intent thay vì chỉ fire-and-forget trong process.

## Kết quả code review tham khảo

### Critical — External side effects không có durable recovery boundary

**Vấn đề:**  
Sau khi content publish event chạy, search/CDN/CRM được gọi trực tiếp nhưng không có durable queue/outbox/job record ghi rằng các side effects phải hoàn tất.

**Tại sao xảy ra:**  
In-process event callback chỉ tồn tại trong lifetime hiện tại của process. Nếu process crash/restart ở giữa chuỗi side effects, công việc còn lại không có state durable để resume.

**Ảnh hưởng production:**  
Page có thể đã publish nhưng search/CDN/CRM ở trạng thái không đồng bộ vô thời hạn cho tới khi có một thao tác khác vô tình sửa lại.

**Cách sửa:**  
Trong publish handling, chỉ ghi một durable intent tối thiểu vào storage/queue phù hợp, sau đó worker xử lý side effects retry-safe. Nếu platform/integration hiện có đã cung cấp durable synchronization cho một dependency, tận dụng cơ chế đó thay vì tự tạo thêm pipeline.

### High — Blocking async I/O trên synchronous event path

**Vấn đề:**  
Ba async calls bị ép thành synchronous bằng `.GetAwaiter().GetResult()`.

**Tại sao xảy ra:**  
Publish thread phải chờ từng network operation hoàn thành. Dù không nhất thiết deadlock trong mọi ASP.NET Core context, nó vẫn biến I/O latency thành blocking latency trên critical path.

**Ảnh hưởng production:**  
Editor publish chậm, request timeout dễ xảy ra, throughput editorial giảm, và khi dependency chậm nhiều concurrent publish có thể làm thread/resource pressure tăng mạnh.

**Cách sửa:**  
Không thực hiện remote side effects tuần tự trên publish path. Capture durable work rồi trả control sớm; worker dùng async end-to-end.

### High — Không có idempotency contract cho CRM webhook

**Vấn đề:**  
Mỗi lần handler chạy sẽ gửi một webhook mới với timestamp mới.

**Tại sao xảy ra:**  
Không có stable event ID/idempotency key đại diện cho cùng một logical publish revision.

**Ảnh hưởng production:**  
Retry, replay hoặc duplicate event có thể tạo duplicate campaign action ở CRM.

**Cách sửa:**  
Tạo stable event identity, ví dụ dựa trên content identity + published revision/version + side-effect type. Downstream request nên mang idempotency key nếu API hỗ trợ; nếu không, consumer-side deduplication/ledger cần được xem xét theo business risk.

### High — Partial success không được mô hình hóa

**Vấn đề:**  
Search có thể thành công, CDN fail, CRM chưa chạy; exception chỉ cắt ngang chuỗi.

**Tại sao xảy ra:**  
Ba external systems không nằm trong cùng transaction nhưng code xử lý chúng như một atomic block.

**Ảnh hưởng production:**  
Retry toàn handler có thể chạy lại side effect đã thành công, trong khi không retry có thể bỏ sót side effect còn thiếu.

**Cách sửa:**  
Persist trạng thái/intent theo từng side effect hoặc dùng job handler idempotent có thể retry toàn event an toàn. Chấp nhận eventual consistency thay vì giả định all-or-nothing xuyên nhiều systems.

### High — Retry semantics không tồn tại hoặc không được kiểm soát

**Vấn đề:**  
Transient timeout/5xx hiện biến thành exception trong publish flow; code không classify transient/permanent failures, backoff hay retry budget.

**Tại sao xảy ra:**  
Reliability policy bị bỏ trống ở integration boundary.

**Ảnh hưởng production:**  
Một outage ngắn của CDN/CRM có thể làm editorial operation thất bại hàng loạt; thêm retry mù ngay trong request path lại có thể kéo dài timeout và nhân tải downstream.

**Cách sửa:**  
Worker áp dụng bounded retry với backoff/jitter cho transient errors, permanent failures chuyển sang failed/dead-letter state có operational workflow. Retry phải đi cùng idempotency.

### Medium — Handler phụ thuộc trực tiếp vào concrete integration clients

**Vấn đề:**  
Module biết cả search, CDN và CRM implementation details.

**Tại sao xảy ra:**  
CMS lifecycle hook vừa capture domain event vừa orchestration tất cả integrations.

**Ảnh hưởng production:**  
Khó test failure windows, khó thay integration, và mỗi dependency mới làm publish hook phình to.

**Cách sửa:**  
Thu hẹp hook thành `IContentPublishWorkRecorder`/application service có trách nhiệm ghi durable intent. Worker handlers phụ trách từng side effect qua interface nhỏ.

### Medium — Không phân biệt publish revision/version

**Vấn đề:**  
Log và webhook chỉ dùng `ContentGuid`; nếu cùng article publish nhiều phiên bản, không có identity rõ của revision đang được xử lý.

**Tại sao xảy ra:**  
Content identity bị dùng như event identity.

**Ảnh hưởng production:**  
Out-of-order retry có thể khiến search/CRM xử lý revision cũ sau revision mới nếu downstream không có version guard.

**Cách sửa:**  
Persist publish version/revision/timestamp hoặc monotonically comparable source version khi platform/domain cho phép; downstream update cần reject/ignore stale version nếu ordering quan trọng.

### Medium — Không có cancellation/shutdown strategy cho background work

**Vấn đề:**  
Current handler không nhận lifecycle cancellation; nếu chuyển sang worker mà vẫn bỏ qua cancellation, deployment shutdown có thể kéo dài hoặc cắt work giữa chừng.

**Tại sao xảy ra:**  
Cancellation là responsibility của worker/process lifecycle, không tự xuất hiện từ event callback.

**Ảnh hưởng production:**  
Noisy shutdown, duplicate retry sau restart và khó biết outcome của in-flight calls.

**Cách sửa:**  
Background worker propagate `CancellationToken` tới outbound operations, dừng nhận work mới khi shutdown, và chỉ đánh dấu success sau durable completion.

### Medium — Logging không cho biết từng side effect đã xảy ra thế nào

**Vấn đề:**  
Chỉ có một success log cuối cùng.

**Tại sao xảy ra:**  
Không có event-level state machine/telemetry cho search, purge, CRM.

**Ảnh hưởng production:**  
Không thể trả lời “page đã publish nhưng CRM chưa nhận vì sao” bằng evidence.

**Cách sửa:**  
Structured telemetry theo event ID, content ID/version, side-effect type, attempt, duration, outcome và dependency status; tránh log content nhạy cảm không cần thiết.

### Low — Service location làm dependency graph khó thấy

**Vấn đề:**  
Dependencies được resolve thủ công trong initialization module.

**Tại sao xảy ra:**  
Service locator che dependency graph và làm test setup phức tạp hơn constructor-injected application services.

**Ảnh hưởng production:**  
Không trực tiếp gây outage nhưng tăng maintainability cost.

**Cách sửa:**  
Giữ initialization module tối thiểu và delegate sang service đã được DI quản lý; dùng standard ASP.NET Core/hosted-service patterns khi phù hợp với version/platform.

## Phiên bản đề xuất

Một hướng đơn giản là content event chỉ ghi durable work item. Ví dụ dùng SQL table nếu site đã có relational database và throughput editorial không lớn tới mức cần thêm messaging riêng.

```csharp
[InitializableModule]
public sealed class ContentPublishModule : IInitializableModule
{
    private IContentEvents? _events;
    private IContentPublishWorkRecorder? _recorder;

    public void Initialize(InitializationEngine context)
    {
        _events = context.Locate.Advanced.GetInstance<IContentEvents>();
        _recorder = context.Locate.Advanced
            .GetInstance<IContentPublishWorkRecorder>();

        _events.PublishedContent += OnPublished;
    }

    private void OnPublished(object? sender, ContentEventArgs e)
    {
        if (e.Content is not ArticlePage article)
            return;

        var work = new ContentPublishedWork(
            EventId: $"article:{article.ContentGuid}:{article.ContentLink.ID}",
            ContentGuid: article.ContentGuid,
            ContentLink: article.ContentLink,
            CampaignId: article.CampaignId,
            CreatedAtUtc: DateTime.UtcNow);

        _recorder!.Record(work);
    }

    public void Uninitialize(InitializationEngine context)
    {
        if (_events is not null)
            _events.PublishedContent -= OnPublished;
    }
}
```

`Record` phải là operation nhỏ, local và durable; implementation thực tế cần chọn event identity có chứa đúng publish revision/version mà CMS/domain cung cấp, không chỉ copy ví dụ trên một cách máy móc.

Worker xử lý work item:

```csharp
public async Task HandleAsync(
    ContentPublishedWork work,
    CancellationToken ct)
{
    await _search.UpsertAsync(
        work.ContentGuid,
        work.EventId,
        ct);

    await _cdn.PurgeAsync(
        work.ContentLink,
        work.EventId,
        ct);

    if (!string.IsNullOrWhiteSpace(work.CampaignId))
    {
        await _crm.SendPublishedWebhookAsync(
            work.CampaignId,
            work.ContentGuid,
            idempotencyKey: work.EventId,
            ct);
    }
}
```

Worker chỉ đánh dấu work item hoàn tất sau khi các required side effects đã đạt success semantics. Nếu các side effects có SLA/criticality khác nhau, có thể tách thành các child work items để một CRM outage không chặn search/CDN retry.

## Giải thích thiết kế sau khi sửa

Thiết kế mới coi content publish và external integration là hai consistency domains khác nhau. Publish không cần chờ tất cả downstream systems. Durable work item là bridge giữa hai domains và cho phép restart/retry.

Không bắt buộc phải đưa Azure Service Bus vào chỉ vì có background work. Với editorial throughput thấp, SQL-backed outbox/work table + một hosted worker có thể đơn giản hơn và đủ tin cậy. Nếu workload, isolation hoặc operational requirements lớn hơn, queue/message broker có thể hợp lý.

Idempotency phải nằm ở logical event/side-effect boundary. Search `upsert` thường dễ retry-safe hơn webhook business action; mỗi downstream cần contract riêng.

## Trade-offs

- Durable work table thêm cleanup, retry state và worker vận hành.
- Eventual consistency nghĩa là editor có thể thấy page live trước khi search/CDN/CRM đồng bộ hoàn toàn.
- Tách side effects giúp failure isolation tốt hơn nhưng tăng số trạng thái cần quan sát.
- Message broker có thể tăng durability/scalability nhưng cũng tăng infrastructure/operational complexity.
- Strict ordering theo content revision chỉ nên thêm nếu business realmente cần; nếu có, cần version semantics rõ ràng.

## Cách kiểm thử

1. **Integration test:** publish một article và xác minh chỉ một durable work item cho đúng logical publish revision được ghi.
2. **Duplicate/concurrency test:** gửi cùng event identity nhiều lần hoặc từ nhiều execution paths; xác minh unique constraint/dedup logic không tạo duplicate durable work.
3. **Failure-path test:** search success nhưng CRM timeout; xác minh retry không làm hỏng search state và CRM dùng stable idempotency key.
4. **Restart test:** kill process sau khi work item được ghi nhưng trước khi side effects hoàn tất; restart phải tiếp tục xử lý backlog.
5. **Load test:** burst nhiều publish operations, đo editor latency, worker backlog age, downstream concurrency và error rate.

## Quan sát trong production

Theo dõi:

- CMS publish duration p50/p95/p99;
- work items created/completed/failed/retried;
- oldest pending work age;
- per-dependency latency/error/timeout rate cho search, CDN và CRM;
- duplicate/idempotency-hit count;
- worker concurrency và shutdown/restart recovery;
- distributed trace/correlation bằng `EventId` + content identifier/version;
- alert khi backlog age hoặc permanent failure vượt ngưỡng business cho phép.

## Câu hỏi phỏng vấn mở rộng

1. Nếu CDN purge phải xảy ra trước khi page được coi là “published successfully”, bạn sẽ thay đổi boundary nào và chấp nhận trade-off gì?
2. Nếu CMS chạy nhiều instances và cùng logical event có thể được quan sát lặp, bạn đặt deduplication guard ở đâu?
3. Khi nào bạn chọn SQL outbox/work table thay vì Azure Service Bus cho flow này?

# Code Review Challenge 2 — Migration SQL chạy trong deployment pipeline: staging ổn nhưng production khóa bảng Orders hàng chục phút và rollback gần như không thể

**Chủ đề:** SQL Server, schema migration, indexes, locking/blocking, backward-compatible deployment, CI/CD, TeamCity/Octopus-style release flow, rollback, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core order system deploy bằng CI/CD pipeline. Production có bảng `Orders` khoảng hàng trăm triệu rows và vẫn nhận write traffic liên tục.

Release mới cần:

- thêm `ExternalReference` cho integration mới;
- sau rollout, code mới sẽ query nhiều theo `ExternalReference`;
- zero/minimal downtime là mục tiêu;
- old app version và new app version có thể cùng chạy trong rolling deployment;
- rollback application phải khả thi nếu release lỗi;
- migration không được giữ blocking lock lâu ngoài maintenance budget;
- production cần telemetry về migration duration, blocking, DB CPU/log growth và rollout health.

Staging chỉ có khoảng 100.000 rows nên migration hoàn tất nhanh. Production release gần đây chạy script dưới đây trước khi deploy application. Database CPU và transaction log tăng mạnh; nhiều API timeout; deploy bị dừng giữa chừng và team không chắc có thể rollback schema an toàn hay không.

## Đoạn code cần review

```sql
BEGIN TRANSACTION;

ALTER TABLE dbo.Orders
ADD ExternalReference nvarchar(200) NOT NULL
    CONSTRAINT DF_Orders_ExternalReference DEFAULT('');

UPDATE dbo.Orders
SET ExternalReference = CONCAT('LEGACY-', Id)
WHERE ExternalReference = '';

CREATE UNIQUE INDEX UX_Orders_ExternalReference
ON dbo.Orders(ExternalReference);

ALTER TABLE dbo.Orders
DROP CONSTRAINT DF_Orders_ExternalReference;

COMMIT TRANSACTION;
```

Deployment flow hiện tại:

```text
1. Stop deployment slots / prevent app rollout
2. Run full migration script
3. Deploy new application version
4. Run smoke tests
5. If smoke tests fail, redeploy old application package
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và availability risks trong migration/script.
2. Xác định locking, logging, index-build, rollback và compatibility concerns.
3. Giải thích production impact trên bảng lớn có live write traffic.
4. Ưu tiên findings theo severity.
5. Đề xuất expand/contract deployment plan an toàn hơn.
6. Giải thích cách test migration trên dữ liệu/scale gần production và failure windows.
7. Đề xuất production telemetry để rollout có go/no-go evidence rõ ràng.

## Câu hỏi gợi mở

1. Vì sao một script chạy nhanh trên 100.000 rows có thể hoàn toàn khác trên hàng trăm triệu rows?
2. Một transaction chứa schema change + full-table update + index build làm transaction duration/log/locking thay đổi thế nào?
3. Old app version sẽ phản ứng ra sao nếu schema mới yêu cầu `ExternalReference NOT NULL` nhưng code cũ không biết field này?
4. “Rollback bằng cách redeploy old package” có rollback được data/schema mutation đã commit không?
5. Có bắt buộc backfill toàn bộ dữ liệu và build unique index trong cùng một release step không?

## Gợi ý

### Gợi ý 1

Primary risk là **big-bang migration**: schema change, full backfill, constraint semantics và index build bị gom vào một transaction trên hot table.

### Gợi ý 2

Hãy nghĩ theo **expand → backfill → verify → enforce → contract**, đồng thời giữ old/new application versions tương thích trong rollout window.

## Kết quả code review tham khảo

### Critical — Big-bang transaction làm blast radius rất lớn

**Vấn đề:**  
DDL, update toàn bảng và index creation nằm trong một explicit transaction.

**Tại sao xảy ra:**  
Transaction sống lâu trong khi chạm lượng dữ liệu rất lớn; transaction log, lock duration và recovery/rollback cost đều tăng.

**Ảnh hưởng production:**  
Blocking kéo dài, log growth, API timeout, replica/HA lag tùy topology và rollback có thể mất rất lâu nếu deployment bị hủy giữa chừng.

**Cách sửa:**  
Tách migration thành nhiều bước independently observable/retryable. Schema expand nhỏ trước, backfill theo batches, index/enforcement ở bước riêng sau khi dữ liệu đã sẵn sàng.

### Critical — `NOT NULL` ngay từ đầu phá backward compatibility với old application

**Vấn đề:**  
Old app version có thể insert row mà không cung cấp `ExternalReference`; script còn drop default trước khi rolling window kết thúc.

**Tại sao xảy ra:**  
Schema contract mới được enforce trước khi toàn fleet/application path tương thích.

**Ảnh hưởng production:**  
Old instances có thể bắt đầu fail inserts trong rollback/rolling deployment; redeploy old package không còn an toàn.

**Cách sửa:**  
Expand schema thành nullable hoặc có compatible default/dual-write strategy trước. Deploy code biết cả old/new schema. Chỉ enforce `NOT NULL` khi toàn data + toàn application path đã tương thích.

### High — Full-table backfill trong một statement tạo load và log burst

**Vấn đề:**  
`UPDATE` chạm mọi legacy row cùng lúc.

**Tại sao xảy ra:**  
Không có batching/throttling/checkpointing; transaction log và lock footprint tăng theo khối lượng work.

**Ảnh hưởng production:**  
DB CPU/IO/log pressure tăng mạnh, blocking lâu và maintenance window khó dự đoán.

**Cách sửa:**  
Backfill theo deterministic batches có checkpoint, pause/throttle theo production metrics, và có thể chạy ngoài deploy critical path.

### High — Unique index build bị gắn trực tiếp vào critical release path

**Vấn đề:**  
Index lớn được create ngay sau backfill trong cùng transaction.

**Tại sao xảy ra:**  
Index build trên bảng lớn là operation nặng; online/resumable capabilities phụ thuộc SQL Server edition/version/index characteristics và phải được xác minh thay vì giả định.

**Ảnh hưởng production:**  
Có thể kéo dài deployment, gây blocking/resource pressure và khiến rollback phức tạp.

**Cách sửa:**  
Đo size/time trên production-like dataset; dùng index strategy phù hợp platform đã xác minh. Có thể build index ở release riêng sau backfill, với monitoring và abort criteria.

### High — Uniqueness được enforce trước khi semantics của dữ liệu được chứng minh

**Vấn đề:**  
Script tạo `LEGACY-{Id}` cho old rows nhưng không thể hiện validation rằng future `ExternalReference` source không collide hoặc normalization/case semantics phù hợp.

**Tại sao xảy ra:**  
Technical uniqueness bị áp trước khi domain uniqueness contract được định nghĩa.

**Ảnh hưởng production:**  
Migration/index build có thể fail giữa release hoặc future inserts gây production errors khó hiểu.

**Cách sửa:**  
Define key semantics, max length/collation/case behavior, validate duplicates trước khi unique index, và có migration/report cho bad data.

### High — Rollback plan chỉ rollback application binary, không rollback schema/data

**Vấn đề:**  
Pipeline coi “redeploy old package” là rollback đầy đủ.

**Tại sao xảy ra:**  
Database migration thường là stateful transformation; reverse migration có thể expensive hoặc unsafe sau khi new code đã ghi data mới.

**Ảnh hưởng production:**  
Team có thể mắc kẹt giữa release: app cần rollback nhưng old app không tương thích schema/data mới.

**Cách sửa:**  
Thiết kế forward-compatible migrations để rollback application không cần rollback schema ngay. Contract/drop destructive changes ở release sau khi rollout ổn định.

### Medium — Default `''` tạo invalid sentinel state

**Vấn đề:**  
Empty string được dùng như placeholder cho required business identifier.

**Tại sao xảy ra:**  
Database constraint “NOT NULL” không đồng nghĩa business value hợp lệ.

**Ảnh hưởng production:**  
Concurrent writes trong migration window có thể tạo placeholder rows; unique index có thể fail nếu nhiều rows cùng `''` tồn tại tại thời điểm build.

**Cách sửa:**  
Cho phép `NULL` trong expand phase hoặc dùng explicit migration state. New app chỉ ghi valid values khi feature path có reference thật.

### Medium — Không có explicit preflight/capacity checks

**Vấn đề:**  
Pipeline chỉ chạy script rồi chờ kết quả.

**Tại sao xảy ra:**  
Không kiểm tra free log/disk capacity, active blocking, estimated rows, HA lag/headroom hay current traffic load.

**Ảnh hưởng production:**  
Migration bắt đầu trong điều kiện không phù hợp và chỉ dừng sau khi user impact đã xảy ra.

**Cách sửa:**  
Preflight checks + abort thresholds + change window phù hợp; expose row progress và DB health trước/trong từng phase.

### Medium — Staging dataset không đại diện production risk

**Vấn đề:**  
Validation trên 100.000 rows được dùng để suy luận cho bảng hàng trăm triệu rows.

**Tại sao xảy ra:**  
Algorithmic/data-volume/locking behavior không scale tuyến tính một cách an toàn trong live workload.

**Ảnh hưởng production:**  
Deployment estimates sai, blocking/resource consumption bị đánh giá thấp.

**Cách sửa:**  
Benchmark trên anonymized/synthetic production-scale dataset và load pattern gần thực tế; nếu không thể, ít nhất đo batch rate/resource cost từ canary backfill nhỏ trước.

### Low — Pipeline thiếu explicit verification gate cho dữ liệu

**Vấn đề:**  
Smoke test application không chứng minh backfill completeness/uniqueness/data quality.

**Tại sao xảy ra:**  
Release verification chỉ nhìn application behavior bề mặt.

**Ảnh hưởng production:**  
Có thể deploy thành công nhưng để lại partial backfill hoặc bad data.

**Cách sửa:**  
Thêm data verification queries/metrics: remaining NULL count, duplicate count, invalid length/format count, backfill lag và index state.

## Phiên bản đề xuất

Một expand/contract plan an toàn hơn:

```sql
-- Phase 1: EXPAND — nhanh, backward compatible
ALTER TABLE dbo.Orders
ADD ExternalReference nvarchar(200) NULL;
```

Deploy application version A:

```text
- Old reads vẫn hoạt động.
- New writes bắt đầu ghi ExternalReference khi integration cung cấp giá trị.
- Read path chưa bắt buộc field này cho legacy rows.
```

Backfill theo batches, ngoài critical deployment transaction:

```sql
DECLARE @BatchSize int = 5000;

WHILE 1 = 1
BEGIN
    ;WITH batch AS
    (
        SELECT TOP (@BatchSize) Id
        FROM dbo.Orders WITH (READPAST)
        WHERE ExternalReference IS NULL
        ORDER BY Id
    )
    UPDATE o
    SET ExternalReference = CONCAT('LEGACY-', o.Id)
    FROM dbo.Orders o
    INNER JOIN batch b ON b.Id = o.Id;

    IF @@ROWCOUNT = 0 BREAK;

    WAITFOR DELAY '00:00:00.200';
END
```

Batch size/delay ở trên chỉ là scenario example, không phải production tuning value. Cần điều chỉnh bằng telemetry thực tế.

Sau backfill:

```sql
SELECT COUNT_BIG(*) AS RemainingNulls
FROM dbo.Orders
WHERE ExternalReference IS NULL;

SELECT ExternalReference, COUNT_BIG(*) AS Cnt
FROM dbo.Orders
WHERE ExternalReference IS NOT NULL
GROUP BY ExternalReference
HAVING COUNT_BIG(*) > 1;
```

Sau khi verification pass và index strategy đã được test trên đúng SQL Server environment:

```sql
CREATE UNIQUE INDEX UX_Orders_ExternalReference
ON dbo.Orders(ExternalReference)
WHERE ExternalReference IS NOT NULL;
```

Sau đó deploy application version B bắt đầu require field cho relevant business paths. Chỉ ở **contract phase** sau khi old versions không còn khả năng quay lại và legacy data đã clean mới cân nhắc `NOT NULL`/constraint tightening nếu requirement thực sự cần.

Nếu cần online/resumable index operation, phải xác minh capability/limitations của SQL Server edition/version và schema cụ thể trước khi đưa option đó vào production script; không coi đó là universal switch.

## Giải thích thiết kế sau khi sửa

Expand/contract tách schema compatibility khỏi data migration. Application rollback sau phase expand vẫn dễ vì old code có thể bỏ qua nullable column. Backfill trở thành operation có progress, có thể throttle/pause và không giữ một transaction khổng lồ.

Unique constraint/index chỉ được enforce sau khi dữ liệu đã được validate. Điều này đổi release từ một bước “thành công hoặc phá production” thành nhiều bước nhỏ có evidence và recovery point rõ.

Đây không phải lý do để mọi migration đều kéo dài qua nhiều release. Với bảng nhỏ, low traffic và operation metadata-only đã được xác minh, migration đơn giản hơn có thể hoàn toàn phù hợp. Complexity phải tỷ lệ với blast radius.

## Trade-offs

- Expand/contract tăng số deployment phases và thời gian tồn tại của transitional schema.
- Nullable temporary state yêu cầu application handling rõ ràng.
- Batch backfill chạy lâu hơn wall-clock nhưng giảm peak resource pressure và cho phép pause.
- Filtered unique index có semantics khác `NOT NULL + unique`; cần map đúng business requirement.
- Giữ schema backward-compatible lâu hơn tiêu tốn discipline nhưng làm application rollback thực tế hơn.

## Cách kiểm thử

1. **Production-scale database test:** chạy migration/backfill trên dataset gần production size, đo rows/sec, log growth, CPU, IO và lock waits.
2. **Concurrency test:** chạy representative insert/update traffic trong lúc backfill; xác minh không mất update và new rows có semantics đúng.
3. **Rollback/deployment validation:** chạy old + new app versions cùng schema expand; rollback application sau từng phase phải vẫn hoạt động.
4. **Failure-path test:** kill backfill giữa chừng rồi resume; progress phải idempotent và không corrupt data.
5. **Index validation:** build index strategy trên môi trường tương đồng production, đo blocking/duration/resource pressure và xác minh capability đúng edition/version.

## Quan sát trong production

Theo dõi:

- backfill rows completed/remaining và throughput;
- SQL CPU, IO, transaction-log utilization/growth;
- blocking sessions, lock waits, deadlocks và query latency;
- application p95/p99, timeout/5xx trong migration window;
- HA/replica lag nếu topology có replica;
- index creation progress/state theo công cụ phù hợp;
- data-quality metrics: NULL count, duplicate count, invalid reference count;
- release version mix giữa old/new application instances;
- explicit go/no-go thresholds để pause backfill hoặc rollout khi user impact tăng.

## Câu hỏi phỏng vấn mở rộng

1. Nếu `ExternalReference` chỉ unique trong từng merchant/tenant, index và migration design cần đổi thế nào?
2. Nếu business bắt buộc migration hoàn tất trong một maintenance window ngắn, bạn sẽ thu thập dữ liệu nào để quyết định online/resumable index hay downtime có kiểm soát?
3. Nếu backfill cần gọi external API để lấy reference thay vì derive từ local data, bạn sẽ tách workflow và idempotency như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- CMS lifecycle event không tự động biến external side effects thành durable, asynchronous hay retry-safe work.
- Khi một local state change kéo theo nhiều external systems, cần thiết kế rõ transaction boundary, durable intent, idempotency và recovery.
- Large-table database migration phải được đánh giá theo data volume, locking, transaction log, live traffic và rollback semantics chứ không chỉ dựa trên staging runtime.
- Backward-compatible schema deployment thường an toàn hơn big-bang migration khi old/new application versions có thể cùng tồn tại.
- CI/CD rollback của application binary không đồng nghĩa database state cũng rollback được.

## Mẫu tư duy cần nhớ

- Tách critical path khỏi side effects có thể eventual-consistent.
- Design retry cùng idempotency và durable state.
- Với migration lớn, ưu tiên expand → backfill → verify → enforce → contract.
- Test theo production scale và failure windows, không chỉ happy path trên dataset nhỏ.
- Mọi rollout quan trọng cần evidence, thresholds và recovery point rõ ràng.
