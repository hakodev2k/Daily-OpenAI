# Code Review Challenge 1 — Export báo cáo trên IIS gây nghẽn request và lộ dữ liệu

**Chủ đề:** C#/.NET Framework 4.5, ASP.NET MVC, IIS, SQL Server, file streaming, authorization  
**Độ khó:** Senior+

## Bối cảnh

Một portal timesheet nội bộ vẫn chạy ASP.NET MVC trên .NET Framework 4.5, IIS/Windows Server. Người dùng có thể xuất CSV theo phòng ban và tháng; chỉ quản lý được phép xuất dữ liệu của phòng ban được phân quyền. Mỗi báo cáo có thể chứa 500.000 dòng. Trong kỳ chốt công, 80 người xuất đồng thời: p95 tăng, IIS App Pool thỉnh thoảng recycle, một số file chứa dữ liệu phòng ban khác. Database là SQL Server, hệ thống phải giữ API cũ trong giai đoạn hiện đại hóa. Chưa biết memory limit, SQL execution plan, timeout và cấu hình reverse proxy.

## Đoạn code cần review

```csharp
public class ReportsController : Controller
{
    private static readonly Dictionary<string, byte[]> Cache =
        new Dictionary<string, byte[]>();

    private readonly string _connection =
        ConfigurationManager.ConnectionStrings["Timesheet"].ConnectionString;

    [HttpGet]
    public ActionResult Export(int departmentId, string month)
    {
        var key = month;
        if (Cache.ContainsKey(key))
            return File(Cache[key], "text/csv", "timesheet.csv");

        var csv = new StringBuilder();
        csv.AppendLine("Employee,Hours,Email");

        var sql = "SELECT EmployeeName, Hours, Email FROM Timesheets " +
                  "WHERE DepartmentId = " + departmentId +
                  " AND MonthKey = '" + month + "'";

        var connection = new SqlConnection(_connection);
        connection.Open();
        var command = new SqlCommand(sql, connection);
        var reader = command.ExecuteReader();

        while (reader.Read())
        {
            csv.Append(reader["EmployeeName"]).Append(',')
               .Append(reader["Hours"]).Append(',')
               .Append(reader["Email"]).AppendLine();
        }

        var bytes = Encoding.UTF8.GetBytes(csv.ToString());
        Cache[key] = bytes;
        Response.Headers["Cache-Control"] = "public,max-age=3600";
        return File(bytes, "text/csv", "timesheet.csv");
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Thiếu authorization theo department

**Vấn đề:** Action tin vào `departmentId` từ query string mà không kiểm tra quyền người gọi.

**Tại sao xảy ra:** Authentication, nếu có, không thay thế object-level authorization.

**Ảnh hưởng production:** Người dùng có thể tải timesheet và email của phòng ban khác.

**Cách sửa:** Bắt buộc authentication, kiểm tra server-side quyền export với departmentId, trả 403 và audit sự kiện bị từ chối; không dùng claim client tự khai làm nguồn quyền duy nhất.

### [Critical] — SQL injection

**Vấn đề:** Ghép `month` trực tiếp vào SQL và ghép cả `departmentId` vào chuỗi.

**Tại sao xảy ra:** SQL được xây từ dữ liệu request thay vì parameters.

**Ảnh hưởng production:** Đọc trái phép, làm thay đổi dữ liệu tùy quyền DB account, gây gián đoạn.

**Cách sửa:** Dùng `SqlParameter` với kiểu và kích thước xác định, validate tháng và áp dụng least-privilege DB credentials.

### [High] — Cache trộn dữ liệu giữa phòng ban

**Vấn đề:** Cache key chỉ có tháng, không có department hoặc security context.

**Tại sao xảy ra:** Các báo cáo khác nhau cùng chia sẻ một entry.

**Ảnh hưởng production:** Cross-department data leak ngay cả khi bổ sung authorization trước cache.

**Cách sửa:** Tốt nhất bỏ cache dữ liệu nhạy cảm cho export; nếu thực sự cần, cache phải scope theo quyền, department, filter, version, có giới hạn và invalidation rõ ràng.

### [High] — Dictionary static không thread-safe

**Vấn đề:** Nhiều request đồng thời đọc/ghi `Dictionary` mà không đồng bộ.

**Tại sao xảy ra:** Dictionary không hỗ trợ concurrent writes.

**Ảnh hưởng production:** Race, exception hoặc kết quả không nhất quán; cache chỉ tồn tại trong một App Pool process.

**Cách sửa:** Không dùng static mutable dictionary; dùng cache framework phù hợp và giới hạn dung lượng, hoặc bỏ cache cho luồng này.

### [High] — Materialize toàn bộ báo cáo trong RAM

**Vấn đề:** `StringBuilder`, `ToString()` và `GetBytes()` tạo nhiều bản sao dữ liệu lớn.

**Tại sao xảy ra:** Kết quả SQL được tích lũy rồi encode một lần, sau đó giữ thêm trong cache.

**Ảnh hưởng production:** Memory pressure, LOH/GC, latency và nguy cơ recycle khi load cao; cần memory counters để xác nhận nguyên nhân cụ thể.

**Cách sửa:** Stream theo từng dòng ra response hoặc tạo export bất đồng bộ vào storage có kiểm soát; đặt row/time/size limits và concurrency limit.

### [High] — Không dispose SQL resources

**Vấn đề:** `SqlConnection`, `SqlCommand`, `SqlDataReader` không được dispose.

**Tại sao xảy ra:** Không có `using` hay `finally`.

**Ảnh hưởng production:** Connection pool pressure, timeout và tài nguyên không được trả về kịp thời.

**Cách sửa:** Bao bọc cả ba bằng `using`, kiểm soát timeout, log duration.

### [Medium] — CSV không escape và có nguy cơ formula injection

**Vấn đề:** Ghép thẳng text với dấu phẩy và xuống dòng; dữ liệu bắt đầu bằng `=`, `+`, `-`, `@` có thể bị spreadsheet diễn giải như công thức.

**Tại sao xảy ra:** CSV serialization không xử lý quoting và spreadsheet-specific safety.

**Ảnh hưởng production:** File sai cột, sai record hoặc gây rủi ro khi người dùng mở trong spreadsheet.

**Cách sửa:** Quote field đúng RFC 4180-style, escape dấu nháy kép, có chính sách neutralize formula với dữ liệu không tin cậy; test tương thích Excel.

### [Medium] — Public HTTP caching cho dữ liệu nhạy cảm

**Vấn đề:** `Cache-Control: public` cho CSV chứa thông tin nhân viên.

**Tại sao xảy ra:** Response có thể được shared cache lưu trữ tùy điều kiện.

**Ảnh hưởng production:** Tăng nguy cơ rò rỉ dữ liệu.

**Cách sửa:** `private, no-store` cho export nhạy cảm; xác minh behavior tại proxy/CDN.

### [Medium] — Thiếu validation và giới hạn tải

**Vấn đề:** `month` không có format check, export không có row cap, timeout policy, cancellation hoặc throttling.

**Tại sao xảy ra:** Endpoint giả định input nhỏ và người dùng đáng tin cậy.

**Ảnh hưởng production:** Truy vấn tốn tài nguyên, request dài và ảnh hưởng các API khác.

**Cách sửa:** Validate `yyyy-MM`, áp dụng rate/concurrency limits, index/query tuning dựa trên execution plan; cân nhắc job export cho dataset lớn.

## Phiên bản đề xuất

Giải pháp sau là **minh họa kiến trúc cải tiến** cho ứng dụng MVC legacy; `IAuthorizationService`, `ITimesheetExportQuery` và `ICsvWriter` là các abstraction của ứng dụng, không phải API có sẵn của .NET Framework. Với báo cáo lớn, triển khai streaming hoặc background export qua service riêng; không cache byte[].

```csharp
[Authorize]
public sealed class ReportsController : Controller
{
    private readonly IAuthorizationService _auth;
    private readonly ITimesheetExportQuery _query;
    private readonly ICsvWriter _csv;

    public ReportsController(IAuthorizationService auth,
        ITimesheetExportQuery query, ICsvWriter csv)
    {
        _auth = auth;
        _query = query;
        _csv = csv;
    }

    [HttpGet]
    public async Task<ActionResult> Export(
        int departmentId, string month, CancellationToken cancellationToken)
    {
        if (departmentId <= 0 ||
            !Regex.IsMatch(month ?? "", @"^\d{4}-(0[1-9]|1[0-2])$"))
            return new HttpStatusCodeResult(400);

        if (!await _auth.CanExportAsync(User, departmentId,
            cancellationToken))
            return new HttpStatusCodeResult(403);

        Response.ContentType = "text/csv; charset=utf-8";
        Response.AddHeader("Content-Disposition",
            "attachment; filename=timesheet.csv");
        Response.Cache.SetCacheability(HttpCacheability.NoCache);
        Response.Cache.SetNoStore();

        await _csv.WriteHeaderAsync(Response.OutputStream, cancellationToken);

        // Query phải dùng SQL parameters, sequential reader, using/disposal,
        // command timeout và cancellation ở tầng data access.
        using (var rows = await _query.OpenRowsAsync(
            departmentId, month, cancellationToken))
        {
            while (await rows.ReadAsync(cancellationToken))
            {
                await _csv.WriteRowAsync(Response.OutputStream,
                    rows.EmployeeName, rows.Hours, rows.Email,
                    cancellationToken);
            }
        }
        return new EmptyResult();
    }
}
```

`ICsvWriter` phải quote/escape field, áp dụng chính sách spreadsheet formula injection và không đóng `Response.OutputStream`. Với ASP.NET MVC/.NET Framework, cần kiểm tra khả năng truyền cancellation khi client disconnect, hành vi buffering của IIS/proxy và cách xử lý exception sau khi response đã bắt đầu. Không thể trả JSON error chuẩn nếu đã gửi một phần CSV. Với hàng trăm nghìn dòng và thời gian dài, phương án bền vững hơn có thể là trả `202 Accepted` + job ID, tạo file qua worker, lưu tại storage bảo vệ và cho tải qua endpoint có authorization.

Ví dụ tầng data access phải sử dụng parameterized query, như sau:

```csharp
using (var command = new SqlCommand(
    @"SELECT EmployeeName, Hours, Email
      FROM dbo.Timesheets
      WHERE DepartmentId = @departmentId AND MonthKey = @month
      ORDER BY EmployeeId", connection))
{
    command.Parameters.Add("@departmentId", SqlDbType.Int).Value = departmentId;
    command.Parameters.Add("@month", SqlDbType.Char, 7).Value = month;
    using (var reader = await command.ExecuteReaderAsync(
        CommandBehavior.SequentialAccess, cancellationToken))
    {
        // Đọc từng row và ghi CSV; connection được dispose ở outer using.
    }
}
```

## Giải thích thiết kế sau khi sửa

Authorization xảy ra trước truy vấn; database access là parameterized; dữ liệu không còn nằm trong static cache; tài nguyên SQL có vòng đời rõ. Streaming giảm peak memory nhưng không giải quyết tự động long-running requests, DB load hoặc client chậm. Nếu requirement cho phép asynchronous export, tách tạo báo cáo khỏi HTTP request giúp retry và kiểm soát concurrency tốt hơn.

## Trade-offs

Streaming có memory footprint thấp nhưng giữ kết nối HTTP/SQL lâu, có thể bị timeout hoặc client ngắt. Background export tăng storage, job lifecycle, cleanup và authorization lúc download, đổi lại kiểm soát tài nguyên và retry tốt hơn. Caching CSV có thể hữu ích cho dữ liệu public/immutable nhưng rất khó an toàn với timesheet có phân quyền và cập nhật.

## Cách kiểm thử

1. **Security test:** user A export department B nhận 403; dữ liệu của B không xuất hiện trong response/cache.
2. **Injection test:** month chứa payload SQL, dữ liệu dấu phẩy/newline/quotes và spreadsheet formula; kiểm tra DB và CSV.
3. **Load test:** 80 export đồng thời, theo dõi IIS private bytes, GC, p95, SQL connections và request queue.
4. **Failure-path test:** client disconnect, SQL timeout, worker/storage failure (nếu dùng job), không leak resources.
5. **Deployment validation:** chạy trên staging IIS với proxy buffering và rollback, đối chiếu row count/file checksum.

## Quan sát trong production

Structured logs: request ID, user/department (không log PII hoặc toàn bộ CSV), row count, bytes, duration, cancellation. Metrics: IIS requests queued, App Pool recycles, private bytes, .NET GC/LOH, SQL pool usage, query duration, blocking và timeouts. SQL execution plan và wait statistics dùng để phân biệt database bottleneck với memory hoặc network; alert khi 403 bất thường, export failures hoặc p95 vượt SLO.

# Code Review Challenge 2 — React tìm kiếm sản phẩm hiển thị sai kết quả và lộ token

## Bối cảnh

Frontend React/TypeScript của một e-commerce portal gọi `GET /api/products/search?q=...` sau khi người dùng nhập từ khóa. API trả `{ items: Product[] }`; mỗi item có `id`, `name`, `descriptionHtml`. Khi gõ nhanh, UI đôi khi hiện kết quả từ từ khóa cũ; khi logout rồi login tài khoản khác, đôi lúc dữ liệu cũ vẫn còn. Sản phẩm có nội dung từ CMS do editor quản lý; chưa xác nhận policy sanitize HTML và cơ chế auth API.

## Đoạn code cần review

```tsx
type Product = {
  id: string;
  name: string;
  descriptionHtml: string;
};

export function ProductSearch() {
  const [query, setQuery] = React.useState("");
  const [items, setItems] = React.useState<Product[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");
  const token = localStorage.getItem("access_token");

  React.useEffect(() => {
    setLoading(true);
    fetch("/api/products/search?q=" + query, {
      headers: { Authorization: "Bearer " + token }
    })
      .then(r => r.json())
      .then(data => {
        setItems(data.items);
        setLoading(false);
      })
      .catch(e => {
        setError(String(e));
        setLoading(false);
      });
  }, [query]);

  return <section>
    <input value={query}
      onChange={e => setQuery(e.target.value)} />
    {loading && <span>Loading...</span>}
    {error && <p>{error}</p>}
    <ul>
      {items.map((item, index) =>
        <li key={index}>
          <h3>{item.name}</h3>
          <div dangerouslySetInnerHTML={{
            __html: item.descriptionHtml
          }} />
        </li>)}
    </ul>
  </section>;
}
```

## Kết quả code review tham khảo

### [Critical] — Render HTML không tin cậy dẫn tới XSS

**Vấn đề:** `dangerouslySetInnerHTML` đưa `descriptionHtml` từ API vào DOM.

**Tại sao xảy ra:** React escaping mặc định bị bỏ qua với raw HTML.

**Ảnh hưởng production:** Nếu nội dung CMS bị chèn script/event handler hoặc payload khác, có thể chạy mã trong origin của ứng dụng; mức độ phụ thuộc CSP và sanitization hiện có.

**Cách sửa:** Ưu tiên plain text; nếu bắt buộc rich HTML, sanitize bằng thư viện được bảo trì với allowlist chặt ở boundary phù hợp, thêm CSP defense-in-depth, test payload.

### [High] — Response cũ ghi đè kết quả mới

**Vấn đề:** Mọi request có thể `setItems` bất kể query hiện tại.

**Tại sao xảy ra:** Promise hoàn tất không theo thứ tự gửi.

**Ảnh hưởng production:** Hiện kết quả không đúng với từ khóa, có thể làm người dùng thao tác nhầm.

**Cách sửa:** AbortController trong cleanup và guard request identity; bỏ qua response stale ngay cả khi abort không ngăn server xử lý.

### [High] — Auth state không đồng bộ với effect

**Vấn đề:** Token lấy trực tiếp từ localStorage mỗi render, nhưng effect chỉ phụ thuộc `query`.

**Tại sao xảy ra:** Auth transition không được model thành reactive state.

**Ảnh hưởng production:** Request dùng token cũ, UI giữ dữ liệu của phiên trước khi account thay đổi; API vẫn phải enforce authorization.

**Cách sửa:** Auth context/session state là dependency, clear items khi identity thay đổi; ưu tiên kiến trúc credential giảm phơi bày token trước XSS, ví dụ BFF với HttpOnly Secure SameSite cookies và CSRF protection khi phù hợp.

### [High] — Không kiểm tra HTTP status và response shape

**Vấn đề:** `fetch` resolve với 401/500, `r.json()` có thể thành công nhưng payload không có `items`.

**Tại sao xảy ra:** HTTP errors không tự reject promise.

**Ảnh hưởng production:** UI hiển thị sai, crash khi `items.map`, hoặc lỗi auth bị che khuất.

**Cách sửa:** Kiểm tra `response.ok`, validate schema runtime, xử lý 401 riêng.

### [Medium] — Không cleanup request khi unmount

**Vấn đề:** Request vẫn chạy khi component không còn cần kết quả.

**Tại sao xảy ra:** Effect không return cleanup.

**Ảnh hưởng production:** Lãng phí network/server và làm state lifecycle khó kiểm soát.

**Cách sửa:** AbortController và guard cancellation trong async handler.

### [Medium] — Gọi API cho mọi keystroke

**Vấn đề:** Không debounce hoặc minimum query length.

**Tại sao xảy ra:** Mỗi lần query thay đổi tạo một fetch.

**Ảnh hưởng production:** Request volume cao, API search bị tải không cần thiết.

**Cách sửa:** Debounce theo UX, minimum length, rate limiting ở backend; không xem debounce là thay thế cancellation.

### [Medium] — Query không được URL encode

**Vấn đề:** Ghép query string trực tiếp.

**Tại sao xảy ra:** Ký tự `&`, `#`, `?` thay đổi cấu trúc URL.

**Ảnh hưởng production:** Kết quả sai hoặc request bất ngờ.

**Cách sửa:** `URLSearchParams`.

### [Medium] — Loading/error state không gắn với request hiện hành

**Vấn đề:** Request cũ có thể set loading=false khi request mới còn chạy; error cũ không được clear.

**Tại sao xảy ra:** Shared state cập nhật bởi nhiều request không có ownership.

**Ảnh hưởng production:** Loading indicator và lỗi không phản ánh query hiện tại.

**Cách sửa:** Reset state theo request identity, chỉ request active được cập nhật.

### [Low] — Dùng index làm React key

**Vấn đề:** `key={index}` không ổn định khi danh sách đổi thứ tự.

**Tại sao xảy ra:** Key theo vị trí thay vì identity.

**Ảnh hưởng production:** Component con có local state có thể gắn nhầm item.

**Cách sửa:** `key={item.id}`.

## Phiên bản đề xuất

Ví dụ dùng API trả plain-text `description` thay cho HTML, với `useAuth` là hook của ứng dụng cung cấp `sessionId` và `fetchWithAuth` (không phải React API có sẵn). Backend phải enforce authorization, không dựa vào frontend. `fetchWithAuth` nhận `AbortSignal` và tự xử lý credential theo kiến trúc auth đã chọn.

```tsx
type Product = { id: string; name: string; description: string };
type SearchResult = { items: Product[] };

function isResult(value: unknown): value is SearchResult {
  if (!value || typeof value !== "object") return false;
  const items = (value as { items?: unknown }).items;
  return Array.isArray(items) && items.every(x =>
    x && typeof x === "object" &&
    typeof x.id === "string" &&
    typeof x.name === "string" &&
    typeof x.description === "string");
}

export function ProductSearch() {
  const { sessionId, fetchWithAuth } = useAuth();
  const [query, setQuery] = React.useState("");
  const [items, setItems] = React.useState<Product[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");
  const [debounced, setDebounced] = React.useState("");

  React.useEffect(() => {
    const timer = window.setTimeout(() => setDebounced(query.trim()), 300);
    return () => window.clearTimeout(timer);
  }, [query]);

  React.useEffect(() => {
    const controller = new AbortController();
    let active = true;
    setItems([]);
    setError("");
    setLoading(false);

    if (!sessionId || debounced.length < 2) return;

    async function load() {
      setLoading(true);
      try {
        const params = new URLSearchParams({ q: debounced });
        const response = await fetchWithAuth(
          "/api/products/search?" + params, { signal: controller.signal });
        if (!response.ok) throw new Error(
          response.status === 401 ? "Unauthorized" : "Search failed");
        const data: unknown = await response.json();
        if (!isResult(data)) throw new Error("Invalid response");
        if (active) setItems(data.items);
      } catch (err) {
        if (active && !controller.signal.aborted)
          setError(err instanceof Error ? err.message : "Unknown error");
      } finally {
        if (active) setLoading(false);
      }
    }
    void load();
    return () => { active = false; controller.abort(); };
  }, [debounced, sessionId, fetchWithAuth]);

  return <section>
    <input aria-label="Tìm sản phẩm" value={query}
      onChange={e => setQuery(e.target.value)} />
    {loading && <span role="status">Loading...</span>}
    {error && <p role="alert">{error}</p>}
    <ul>{items.map(item => <li key={item.id}>
      <h3>{item.name}</h3><p>{item.description}</p>
    </li>)}</ul>
  </section>;
}
```

**Điều kiện tích hợp:** `fetchWithAuth` phải là stable reference (ví dụ memoized trong provider), nếu không effect có thể chạy lại không cần thiết. Khi session thay đổi, cần đảm bảo component bị remount theo identity hoặc clear kết quả ngay khi identity đổi; nếu debounce đang chờ, không để UI cũ xuất hiện trong khoảng chuyển phiên. Một cách chắc chắn là key component theo `sessionId` ở parent, hoặc dùng state machine keyed by session và query. Server vẫn cần enforce tenant/account authorization trên mỗi request. Nếu rich HTML bắt buộc, thay plain text bằng pipeline sanitize được kiểm chứng; không chỉ đổi tên field.

## Giải thích thiết kế sau khi sửa

Request cleanup loại bỏ stale updates; URLSearchParams bảo toàn query; runtime schema validation tránh tin payload tùy ý; React render text mặc định escape HTML. Debounce giảm tải nhưng không bảo đảm server đã hủy tác vụ. Auth state phải là nguồn sự thật có thể quan sát và được backend kiểm tra.

## Trade-offs

Debounce 300 ms thêm latency UX nhưng giảm request volume; nên đo thay vì cố định mọi thiết bị. Abort không hoàn tác server-side side effects; search GET nên read-only. BFF cookie giảm token exposure trước JavaScript nhưng yêu cầu CSRF design và vận hành session; SPA bearer-token có thể hợp lý với threat model khác nếu bảo vệ XSS chặt chẽ. Runtime schema validation tăng code và overhead nhỏ nhưng cải thiện resilience.

## Cách kiểm thử

1. **Race test:** giả lập request `a` chậm, `ab` nhanh; UI chỉ hiển thị `ab`.
2. **Auth test:** logout/login user khác trong khi request đang chạy; không lộ kết quả cũ; 401 được xử lý.
3. **Security test:** HTML payload từ CMS được hiển thị như text, không thực thi; nếu rich text, kiểm tra sanitizer và CSP.
4. **Failure-path test:** 500, malformed JSON, payload sai schema, offline, unmount; loading/error đúng.
5. **E2E/Playwright:** nhập nhanh, backspace, query chứa `&` và `#`, kiểm tra URL và kết quả; đo request count.

## Quan sát trong production

Browser telemetry: search request duration, debounce-to-render latency, abort count, 401/403/5xx, validation errors và UI error rate; không log token hoặc full query chứa dữ liệu nhạy cảm. Backend: p95/p99, search request rate, cancellation, cache/search dependency latency và correlation ID. Alert theo error budget, không alert mỗi abort bình thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu API dùng cookie auth, bạn thiết kế CSRF protection và CORS như thế nào?
2. Nếu search backend là Elasticsearch với eventual consistency, UI nên diễn đạt kết quả chậm cập nhật ra sao?
3. Nếu React Strict Mode khiến effect được setup/cleanup thêm trong development, bạn phân biệt bug thực với hành vi kiểm tra lifecycle thế nào?
