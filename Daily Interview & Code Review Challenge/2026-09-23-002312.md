# Code Review Challenge 1 — Service Bus consumer hoàn tất message trước khi business transaction thực sự an toàn

**Chủ đề:** C#/.NET, Azure Service Bus, idempotency, EF Core, retry, message settlement, distributed failure  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một worker .NET xử lý message `OrderPaid` từ Azure Service Bus. Mỗi message cập nhật trạng thái order trong SQL Server rồi gọi API của hệ thống loyalty để cộng điểm. Queue có thể redeliver message khi processing thất bại hoặc lock/connection gặp vấn đề. Worker chạy nhiều replicas để tăng throughput.

Production thỉnh thoảng ghi nhận khách hàng được cộng điểm hai lần. Một số order lại ở trạng thái `Paid` nhưng loyalty chưa được cộng điểm. Team cho rằng `MessageId` là duy nhất nên duplicate không thể xảy ra và retry toàn bộ handler là đủ.

## Đoạn code cần review

```csharp
public sealed class OrderPaidProcessor
{
    private readonly OrdersDbContext _db;
    private readonly HttpClient _loyaltyClient;
    private readonly ILogger<OrderPaidProcessor> _logger;

    public OrderPaidProcessor(
        OrdersDbContext db,
        HttpClient loyaltyClient,
        ILogger<OrderPaidProcessor> logger)
    {
        _db = db;
        _loyaltyClient = loyaltyClient;
        _logger = logger;
    }

    public async Task ProcessAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var json = args.Message.Body.ToString();
        var message = JsonSerializer.Deserialize<OrderPaidMessage>(json)!;

        await args.CompleteMessageAsync(args.Message, cancellationToken);

        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

        if (order.Status == "Paid")
        {
            _logger.LogInformation("Order {OrderId} already paid", order.Id);
            return;
        }

        order.Status = "Paid";
        order.PaidAtUtc = message.PaidAtUtc;
        await _db.SaveChangesAsync(cancellationToken);

        var response = await _loyaltyClient.PostAsJsonAsync(
            "/api/points/add",
            new { message.CustomerId, message.Points },
            cancellationToken);

        response.EnsureSuccessStatusCode();

        _logger.LogInformation(
            "Processed payment {MessageId} for {OrderId}",
            args.Message.MessageId,
            message.OrderId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và data consistency.
2. Xác định reliability/concurrency concerns khi queue redeliver hoặc nhiều replicas xử lý đồng thời.
3. Giải thích production impact của từng vấn đề quan trọng.
4. Ưu tiên finding theo severity thay vì chỉ liệt kê style issue.
5. Đề xuất implementation/design tốt hơn, bao gồm settlement và idempotency boundary.
6. Nêu cách kiểm thử retry, duplicate delivery và partial failure.
7. Nêu telemetry cần có để chứng minh consumer hoạt động đúng trong production.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu process chết ngay sau `CompleteMessageAsync` nhưng trước `SaveChangesAsync`?
2. Điều gì xảy ra nếu SQL commit thành công nhưng loyalty API timeout sau khi server phía loyalty đã thực hiện cộng điểm?
3. Hai replicas có thể cùng đọc trạng thái order chưa `Paid` trong những điều kiện nào?
4. `MessageId` tồn tại có đồng nghĩa application đã thực hiện deduplication không?
5. Business operation nào cần exactly-once effect, và component nào có thể thực sự enforce nó?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **settlement order, idempotency và partial failure giữa SQL transaction với external API**.

### Gợi ý 2

At-least-once delivery và network ambiguity yêu cầu consumer chịu được duplicate/retry; một `if` trên business status chưa đủ để tạo atomic deduplication cho mọi side effect.

## Kết quả code review tham khảo

### Critical — Complete message trước khi xử lý business logic

**Vấn đề:** Message được complete ngay sau deserialize.

**Tại sao xảy ra:** Settlement thành công làm broker coi message đã xử lý, trong khi SQL update và loyalty call vẫn chưa xảy ra.

**Ảnh hưởng production:** Nếu process crash, SQL lỗi hoặc dependency lỗi sau settlement, message có thể không còn được redeliver và business event bị mất về mặt processing.

**Cách sửa:** Chỉ complete sau khi durable processing boundary cần thiết đã thành công. Nếu dùng processor với auto-complete thì cấu hình settlement strategy phải nhất quán với handler design; không settlement sớm.

### Critical — External loyalty side effect không idempotent trước retry/network ambiguity

**Vấn đề:** Request cộng điểm không mang idempotency key/business operation identifier có semantics rõ ràng.

**Tại sao xảy ra:** Client có thể timeout sau khi loyalty server đã commit. Consumer không biết request đã thành công hay chưa; retry có thể cộng điểm lần nữa.

**Ảnh hưởng production:** Duplicate financial/reward-like side effect, khó reconcile và có thể ảnh hưởng trực tiếp khách hàng.

**Cách sửa:** Thiết kế loyalty operation idempotent theo stable operation ID, ví dụ payment/event ID; phía loyalty lưu và reject/replay-safe duplicate. Nếu external provider không hỗ trợ idempotency, cần workflow/reconciliation phù hợp thay vì giả định retry an toàn.

### High — SQL commit và external HTTP call tạo dual-write inconsistency

**Vấn đề:** `SaveChangesAsync` commit `Paid` trước khi loyalty call hoàn tất.

**Tại sao xảy ra:** SQL transaction không bao phủ remote HTTP side effect.

**Ảnh hưởng production:** Order có thể `Paid` nhưng loyalty chưa được cộng; lần redelivery sau gặp `order.Status == "Paid"` và return, khiến side effect còn thiếu không được retry.

**Cách sửa:** Không cố tạo distributed transaction qua HTTP. Một thiết kế phù hợp là commit order state cùng durable outbox record trong một local transaction; publisher/worker riêng gửi `AwardLoyaltyPoints` từ outbox. Consumer loyalty phải idempotent. Nếu complexity chưa justify outbox, ít nhất cần durable operation state/reconciliation rõ ràng.

### High — `Status == "Paid"` không phải deduplication record đáng tin cậy

**Vấn đề:** Business state được dùng để suy ra message đã xử lý hoàn chỉnh.

**Tại sao xảy ra:** Một order có thể đã `Paid` nhưng các side effects downstream chưa hoàn tất; nhiều event khác nhau cũng có thể liên quan cùng order.

**Ảnh hưởng production:** Retry có thể bị skip sai hoặc không phân biệt event đã xử lý với business state hiện tại.

**Cách sửa:** Dùng stable event/operation ID và durable inbox/deduplication record khi cần. Insert dedupe marker và business mutation trong cùng transaction, với unique constraint để chống race giữa replicas.

### High — Check-then-update có race giữa nhiều consumers

**Vấn đề:** Hai handlers có thể cùng đọc `Status != Paid`, sau đó cùng tiếp tục.

**Tại sao xảy ra:** Read và update không có concurrency control/deduplication constraint đủ mạnh; horizontal replicas không chia sẻ in-process lock.

**Ảnh hưởng production:** Duplicate downstream calls hoặc last-write-wins behavior khó dự đoán.

**Cách sửa:** Dùng database-enforced concurrency/unique operation key/conditional update phù hợp với invariant. Không dùng process-local lock để giải quyết cross-instance race.

### Medium — Poison/invalid message path chưa được xử lý rõ

**Vấn đề:** Deserialization dùng null-forgiving operator và không có validation/schema handling.

**Tại sao xảy ra:** Invalid payload có thể throw lặp lại nếu message được retry mà không có strategy cho non-transient error.

**Ảnh hưởng production:** Delivery count tăng, queue noise, cuối cùng DLQ mà thiếu diagnostic context; hoặc handler có failure mode không rõ.

**Cách sửa:** Validate payload, phân biệt transient/non-transient failure, dead-letter malformed message với reason/diagnostic an toàn khi phù hợp.

### Medium — Logging thiếu operation correlation và outcome states

**Vấn đề:** Chỉ log success cuối cùng và một nhánh `already paid`.

**Tại sao xảy ra:** Không có structured lifecycle cho attempt, delivery count, operation ID, SQL/outbox state và dependency outcome.

**Ảnh hưởng production:** Khó phân biệt duplicate delivery hợp lệ, duplicate effect và lost processing.

**Cách sửa:** Log structured identifiers như `MessageId`, business event ID, order ID, delivery count và processing outcome; kết nối với trace/dependency telemetry.

### Low — String status làm invariant kém rõ ràng

**Vấn đề:** `"Paid"` là magic string.

**Tại sao xảy ra:** Domain state không được biểu diễn chặt.

**Ảnh hưởng production:** Chủ yếu maintainability/correctness risk khi state names thay đổi hoặc typo.

**Cách sửa:** Dùng enum/value/domain transition phù hợp và enforce transition invariant ở domain/database khi cần.

## Phiên bản đề xuất

Một phương án an toàn là để consumer payment chỉ commit business state và outbox atomically. Downstream worker xử lý outbox với idempotent loyalty operation.

```csharp
public sealed class OrderPaidProcessor
{
    private readonly OrdersDbContext _db;
    private readonly ILogger<OrderPaidProcessor> _logger;

    public OrderPaidProcessor(
        OrdersDbContext db,
        ILogger<OrderPaidProcessor> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task ProcessAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        OrderPaidMessage message;
        try
        {
            message = JsonSerializer.Deserialize<OrderPaidMessage>(
                args.Message.Body.ToString())
                ?? throw new JsonException("Empty payload");
        }
        catch (JsonException ex)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                "InvalidPayload",
                ex.Message,
                cancellationToken);
            return;
        }

        var eventId = args.Message.MessageId;

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == eventId, cancellationToken);

        if (!alreadyProcessed)
        {
            var order = await _db.Orders
                .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

            if (order.Status != OrderStatus.Paid)
            {
                order.Status = OrderStatus.Paid;
                order.PaidAtUtc = message.PaidAtUtc;
            }

            _db.OutboxMessages.Add(new OutboxMessage
            {
                Id = Guid.NewGuid(),
                OperationId = eventId,
                Type = "AwardLoyaltyPoints",
                Payload = JsonSerializer.Serialize(new
                {
                    message.CustomerId,
                    message.Points,
                    OperationId = eventId
                }),
                CreatedAtUtc = DateTime.UtcNow
            });

            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = eventId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);
        }

        await args.CompleteMessageAsync(args.Message, cancellationToken);

        _logger.LogInformation(
            "OrderPaid handled. MessageId={MessageId}, OrderId={OrderId}, DeliveryCount={DeliveryCount}",
            eventId,
            message.OrderId,
            args.Message.DeliveryCount);
    }
}
```

`ProcessedMessages.MessageId` phải có unique constraint. Outbox publisher cần retry-safe và loyalty endpoint cần dùng `OperationId` như idempotency key nếu contract hỗ trợ. Nếu outbox publisher gửi thành công nhưng crash trước khi đánh dấu outbox row complete, message có thể được gửi lại; vì vậy idempotency vẫn cần ở consumer/downstream boundary.

## Giải thích thiết kế sau khi sửa

Local SQL transaction bảo đảm order mutation, inbox marker và outbox intent cùng commit hoặc cùng rollback. Broker message chỉ được complete sau durable commit. Điều này không biến toàn workflow thành exactly-once transport; thay vào đó thiết kế chấp nhận redelivery và tạo **idempotent effect** tại business boundaries.

Outbox loại bỏ dual-write trực tiếp giữa SQL commit và HTTP call. Nó đổi consistency model: loyalty có thể cập nhật sau một khoảng thời gian thay vì đồng bộ trong request/consumer transaction. Nếu business bắt buộc loyalty hoàn tất trước khi xác nhận payment, requirement phải được làm rõ vì failure semantics sẽ khác.

## Trade-offs

Outbox/inbox thêm schema, publisher, cleanup, monitoring và eventual consistency. Với hệ thống nhỏ, có thể chọn durable operation table đơn giản hơn nếu vẫn đáp ứng invariant. Unique constraint và transaction tăng database work nhưng đổi lại correctness dưới concurrency. Không nên triển khai architecture phức tạp chỉ để “đúng pattern”; complexity phải tương xứng hậu quả của duplicate/lost side effect.

## Cách kiểm thử

1. **Integration test duplicate:** gửi cùng `MessageId` hai lần song song, xác minh chỉ một processed marker/outbox operation được tạo.
2. **Failure-path test:** crash/throw sau SQL commit nhưng trước broker completion; redelivery không tạo duplicate business effect.
3. **Dependency ambiguity test:** loyalty mock thực hiện side effect rồi trả timeout; retry với cùng `OperationId` không cộng điểm lần hai.
4. **Concurrency/load test:** nhiều replicas xử lý duplicate/interleaved events cho cùng order, kiểm tra unique constraints và invariant.
5. **DLQ test:** malformed payload được dead-letter với reason phù hợp và không tạo partial SQL state.

## Quan sát trong production

Theo dõi Service Bus active message count, dead-letter count, delivery count distribution và processing failures; Application Insights traces/dependencies cho SQL và loyalty; metric outbox backlog/oldest-message age; duplicate-deduped count; loyalty idempotency conflict/replay count; structured logs có `MessageId`, `OperationId`, `OrderId`, correlation ID. Alert khi DLQ/backlog tăng, outbox age vượt SLO hoặc duplicate-effect reconciliation phát hiện sai lệch.

## Câu hỏi phỏng vấn mở rộng

1. Nếu loyalty provider không hỗ trợ idempotency key và không có API query trạng thái operation, bạn sẽ thiết kế reconciliation thế nào?
2. Outbox publisher gửi event thành công nhưng crash trước khi đánh dấu row đã gửi; tại sao outbox một mình chưa tạo exactly-once delivery?
3. Khi nào bạn sẽ không dùng outbox cho workflow này?

# Code Review Challenge 2 — Kubernetes rollout “xanh” nhưng Pod nhận traffic trước khi ứng dụng thực sự sẵn sàng

**Chủ đề:** Kubernetes, ASP.NET Core hosting, readiness/liveness, resource management, configuration/secrets, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API được chuyển từ Azure App Service sang Kubernetes. Deployment báo rollout thành công nhưng ngay sau mỗi release có một đợt 502/503 ngắn. Khi SQL Server chậm trong vài phút, Pods đôi khi restart liên tục làm incident nặng hơn. Team cũng thấy latency tăng mạnh khi traffic cao dù HPA đã được bật ở cluster level.

Manifest dưới đây deploy được và ứng dụng thường chạy bình thường sau vài phút.

```yaml

metadata:
  name: orders-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
  selector:
    matchLabels:
```

## Câu hỏi gợi mở

1. `/health` đang kiểm tra điều gì: process sống, app initialized, hay tất cả dependencies đều healthy?

## Gợi ý

### Gợi ý 1

## Kết quả code review tham khảo

### Critical — Production database credential được hard-code trong manifest

**Vấn đề:** Username/password nằm trực tiếp trong YAML.

**Tại sao xảy ra:** Configuration và secret management bị trộn vào deployment artifact.

**Ảnh hưởng production:** Credential có thể lộ qua repository, CI/CD logs, review history hoặc người có quyền đọc manifest; rotation khó và blast radius lớn.

**Cách sửa:** Dùng Kubernetes Secret hoặc external secret/identity mechanism phù hợp với platform. Secret object bản thân không nên được coi là giải pháp hoàn chỉnh nếu access control/encryption/rotation chưa được thiết kế; áp dụng least privilege và rotation.

### High — Cùng `/health` cho readiness và liveness có thể restart app vì dependency outage

**Vấn đề:** Nếu endpoint trả unhealthy khi SQL lỗi, cả readiness và liveness cùng fail.

**Tại sao xảy ra:** Hai probe có semantics khác nhau nhưng bị đồng nhất.

**Ảnh hưởng production:** SQL degradation có thể làm toàn bộ Pods bị restart, tăng startup load và làm outage nặng hơn thay vì phục hồi.

**Cách sửa:** Tách endpoint/check semantics. Liveness nên chủ yếu phát hiện process không thể tự phục hồi; readiness có thể phản ánh khả năng phục vụ traffic, tùy architecture. Dependency failure cần degradation/retry/circuit behavior phù hợp, không mặc định restart process.

### High — Không có `startupProbe`/startup allowance phù hợp

**Vấn đề:** Probe bắt đầu rất sớm trong khi app có thể cần thời gian initialize/JIT/load configuration.

**Tại sao xảy ra:** `initialDelaySeconds` ngắn không mô hình hóa startup variability tốt.

**Ảnh hưởng production:** Pod có thể bị đánh giá unhealthy trong startup, đặc biệt khi node/dependency chậm, gây rollout instability.

**Cách sửa:** Khi application có startup đáng kể, dùng `startupProbe` với threshold phù hợp dựa trên measurement; readiness chỉ thành công khi app thật sự sẵn sàng.

### High — Image tag `latest` làm release và rollback không deterministic

**Vấn đề:** Manifest không pin immutable artifact version/digest.

**Tại sao xảy ra:** Cùng tag có thể trỏ đến image khác theo thời điểm/node cache/pull policy.

**Ảnh hưởng production:** Khó xác định code version đang chạy, rollback/reproduce incident không đáng tin cậy.

**Cách sửa:** Dùng immutable version tag hoặc digest từ CI artifact; record commit/build metadata và deploy đúng artifact đã test.

### High — Chỉ có resource limits, không có requests

**Vấn đề:** Scheduler thiếu resource request contract; CPU/memory-based autoscaling semantics cũng có thể không phản ánh đúng intent tùy HPA configuration.

**Tại sao xảy ra:** Limits không thay thế requests.

**Ảnh hưởng production:** Scheduling/capacity planning kém; CPU throttling hoặc OOM behavior có thể xuất hiện dưới load. Nếu HPA dùng utilization percentage dựa trên requests, requests thiếu làm metric/target không hoạt động như team kỳ vọng.

**Cách sửa:** Đặt requests và limits dựa trên load/profile measurement; kiểm tra HPA target metric và capacity của cluster. Không copy giá trị tùy ý.

### Medium — RollingUpdate không khai báo availability/surge policy

**Vấn đề:** Manifest phụ thuộc defaults thay vì explicit rollout SLO.

**Tại sao xảy ra:** Không xác định acceptable unavailable capacity và surge capacity.

**Ảnh hưởng production:** Với workload nhạy capacity, rollout có thể giảm headroom hoặc tạo resource pressure không mong muốn.

**Cách sửa:** Chọn `maxUnavailable`/`maxSurge` theo replica count, capacity và availability requirement; kết hợp readiness đúng.

### Medium — Probe quá dày nhưng thiếu timeout/failure thresholds được thiết kế theo evidence

**Vấn đề:** `periodSeconds: 2` cho readiness và 5 cho liveness được chọn mà không thể hiện failure tolerance.

**Tại sao xảy ra:** Probe tuning không dựa trên startup/dependency latency/SLO.

**Ảnh hưởng production:** Transient latency có thể làm endpoints bị loại khỏi traffic quá nhanh hoặc tạo probe load/noise.

**Cách sửa:** Chọn `timeoutSeconds`, `failureThreshold`, `periodSeconds` từ measured behavior và desired detection/recovery window.

### Medium — Health design chưa phân biệt internal app health và downstream availability

**Vấn đề:** Một endpoint tổng hợp có thể biến dependency transient failure thành Pod failure.

**Tại sao xảy ra:** Health checks được xem như danh sách “ping mọi dependency” thay vì routing/recovery contract.

**Ảnh hưởng production:** Cascading failure và khó xác định component nào thực sự hỏng.

**Cách sửa:** Thiết kế health checks theo mục đích; expose telemetry dependency riêng và quyết định readiness behavior theo khả năng app phục vụ request/degrade an toàn.

## Phiên bản đề xuất

Các giá trị threshold/resource dưới đây là **ví dụ cấu trúc**, không phải production sizing; cần hiệu chỉnh bằng measurement.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: orders-api
          image: registry.example.com/orders-api:2026.09.23-abc123
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Orders
              valueFrom:
                secretKeyRef:
                  name: orders-api-db
                  key: connection-string
            - name: ASPNETCORE_ENVIRONMENT
              value: "Production"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: "250m"
              memory: "192Mi"
            limits:
              cpu: "750m"
              memory: "384Mi"
```

Các resource/probe values phải được thay bằng số liệu từ profiling/load test. Nếu platform hỗ trợ workload identity/Managed Identity cho SQL và application architecture cho phép, identity-based access có thể giảm secret credential handling; không nên giả định khả năng đó nếu chưa xác minh môi trường và database configuration.

## Giải thích thiết kế sau khi sửa

`startupProbe` bảo vệ giai đoạn startup trước khi liveness quyết định restart. `readinessProbe` điều khiển traffic routing, còn `livenessProbe` chỉ nên fail khi process ở trạng thái restart có khả năng giúp phục hồi. Điều này tránh biến SQL outage thành restart storm.

Immutable image version giúp trace release và rollback deterministic. Resource requests tạo scheduling/autoscaling contract rõ hơn; limits bảo vệ node nhưng CPU limit quá thấp có thể gây throttling, memory limit quá thấp có thể dẫn đến OOM kill, nên phải profile thay vì chọn số đẹp.

Secret reference loại credential khỏi manifest chính, nhưng vẫn cần RBAC, encryption-at-rest/platform secret strategy, audit và rotation. Nếu có identity-based access phù hợp, có thể giảm static secrets hơn nữa.

## Trade-offs

Readiness nhạy hơn có thể giảm traffic vào Pod lỗi nhưng cũng giảm capacity trong dependency degradation. Liveness quá bảo thủ giữ process thật sự deadlocked lâu hơn; quá aggressive gây restart storm. `maxUnavailable: 0` tăng availability khi rollout nhưng cần surge capacity. Resource requests cao hơn cải thiện scheduling predictability nhưng có thể giảm bin-packing efficiency. Secret management tốt hơn thêm operational setup nhưng giảm credential exposure.

## Cách kiểm thử

1. **Deployment validation:** rollout image mới dưới traffic liên tục, xác minh không route request trước readiness và không xuất hiện 502/503 do startup.
2. **Failure injection:** làm SQL unavailable tạm thời; xác minh readiness/degradation behavior đúng nhưng liveness không tạo restart storm nếu process vẫn healthy.
3. **Load test:** đo p95/p99, CPU throttling, memory working set, GC và Pod restarts để chọn requests/limits bằng evidence.
4. **Rollback test:** deploy version lỗi rồi rollback; xác minh image version deterministic và database/config vẫn backward-compatible.
5. **Security test/review:** xác minh manifest/repository/CI logs không chứa production credential và service account/secret access tuân theo least privilege.

## Quan sát trong production

Theo dõi readiness/liveness/startup probe failures, Pod restart count/reasons, OOMKilled events, CPU throttling, CPU/memory usage so với requests/limits, HPA desired/current replicas, rollout duration, 5xx rate và p95/p99. Ở application layer dùng Application Insights/structured logs/traces để phân biệt startup failure, SQL dependency failure và request failure. Alert nên dựa trên user-impact/service symptoms cùng cluster signals, không chỉ một lần probe fail.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL outage kéo dài 15 phút, readiness của API nên fail hay vẫn ready để trả degraded response? Bạn cần requirement nào để quyết định?
2. Khi nào `livenessProbe` có thể gây hại nhiều hơn lợi ích?
3. Nếu HPA tăng replicas nhưng latency vẫn tăng, bạn sẽ đo những bottleneck nào trước khi tiếp tục scale?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message broker có thể redeliver; correctness phải đến từ idempotent business processing và durable state, không phải assumption rằng handler chỉ chạy một lần.
- Settlement quá sớm có thể biến transient processing failure thành lost work; settlement quá muộn mà side effect không idempotent có thể tạo duplicate effect.
- SQL + external HTTP là dual-write boundary; local transaction không thể tự làm remote side effect atomic. Outbox/inbox là một lựa chọn khi risk justify complexity.
- Kubernetes readiness, liveness và startup probes phục vụ các quyết định khác nhau; dùng chung một dependency-heavy health check có thể khuếch đại outage.
- Immutable artifacts, resource contracts, secret handling và observability là một phần của deployment correctness.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; không xem retry là độc lập.
- Xác định durable commit boundary trước khi settlement message.
- Phân biệt “process sống” với “instance sẵn sàng nhận traffic”.
- Dùng immutable artifact để release và rollback có thể tái hiện.
- Test failure path và concurrency path, không chỉ happy path.
