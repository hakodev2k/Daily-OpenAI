# Code Review Challenge 1 — BackgroundService đồng bộ search index bị nhân bản sau horizontal scaling

**Chủ đề:** C#/.NET, BackgroundService, EF Core, Elasticsearch, concurrency, idempotency, graceful shutdown  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40–50 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core application đồng bộ product changes từ SQL Server sang Elasticsearch mỗi phút. Khi chạy một instance, job có vẻ ổn. Sau khi Azure App Service scale từ 1 lên 6 instances, SQL load tăng, cùng product bị index nhiều lần, đôi lúc search trả dữ liệu cũ hơn database và deployment mất nhiều thời gian để shutdown.

Team muốn giữ kiến trúc đơn giản và chưa chứng minh rằng cần thêm message broker.

## Đoạn code cần review

```csharp
public sealed class ProductIndexWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly IElasticClient _elastic;
    private readonly ILogger<ProductIndexWorker> _logger;

    public ProductIndexWorker(
        IServiceProvider services,
        IElasticClient elastic,
        ILogger<ProductIndexWorker> logger)
    {
        _services = services;
        _elastic = elastic;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var products = await db.Products
                .Where(x => x.UpdatedAtUtc > DateTime.UtcNow.AddMinutes(-2))
                .ToListAsync();

            foreach (var product in products)
            {
                await _elastic.IndexDocumentAsync(product);
            }

            _logger.LogInformation("Indexed {Count} products", products.Count);
            await Task.Delay(TimeSpan.FromMinutes(1));
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, concurrency và lifecycle problems.
2. Giải thích behavior khi có 6 application instances.
3. Phân tích vì sao time-window polling có thể vừa duplicate vừa miss update.
4. Ưu tiên production risks.
5. Đề xuất thiết kế cải thiện mà không mặc định thêm Service Bus.
6. Giải thích testing cho overlap, restart, cancellation và Elasticsearch failure.
7. Đề xuất telemetry để chứng minh đồng bộ đúng và đủ nhanh.

## Câu hỏi gợi mở

1. Mỗi application instance sẽ tạo bao nhiêu worker?
2. `UpdatedAtUtc > now - 2 minutes` có tạo durable checkpoint không?
3. Điều gì xảy ra nếu indexing fail ở product thứ 50/100?
4. `stoppingToken` hiện ảnh hưởng tới query, indexing và delay ở đâu?
5. Nếu hai updates của cùng product được xử lý out of order, document cuối cùng có chắc là version mới nhất không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **scheduler ownership + non-durable progress**.

### Gợi ý 2

Tách ba vấn đề: ai được quyền chạy job, làm sao biết chính xác batch nào đã xử lý, và làm sao retry mà không làm version cũ ghi đè version mới.

## Kết quả code review tham khảo

### Critical — Mỗi instance chạy một scheduler độc lập

**Vấn đề:** `BackgroundService` được khởi động trong từng application process.

**Tại sao xảy ra:** Horizontal scaling nhân số worker theo số instances; code không có ownership/coordination.

**Ảnh hưởng production:** SQL query và indexing traffic bị nhân lên, duplicate processing và race giữa các workers.

**Cách sửa:** Trước tiên xác định requirement. Nếu chỉ một scheduler được chạy, chuyển ownership sang một execution unit riêng hoặc dùng coordination/lease có semantics rõ. Nếu cho phép nhiều workers, workload phải được partition/claimed an toàn và idempotent.

### High — Time-window polling không phải durable checkpoint

**Vấn đề:** Query luôn nhìn lại hai phút dựa trên wall clock.

**Tại sao xảy ra:** Không lưu watermark/checkpoint của batch đã hoàn thành.

**Ảnh hưởng production:** Overlap gây duplicate; downtime dài hơn window có thể làm miss changes; clock/timestamp precision làm boundary khó reasoning.

**Cách sửa:** Dùng durable cursor/watermark hoặc change table/outbox phù hợp. Chỉ advance checkpoint sau khi batch đạt completion semantics đã định nghĩa.

### High — CancellationToken bị bỏ qua

**Vấn đề:** Loop `while (true)`, EF query, Elasticsearch call và `Task.Delay` không nhận `stoppingToken`.

**Tại sao xảy ra:** Worker không tham gia cooperative cancellation.

**Ảnh hưởng production:** Deployment/recycle shutdown chậm, operation tiếp tục trong lúc host đang dừng.

**Cách sửa:** Dùng `while (!stoppingToken.IsCancellationRequested)`, truyền token tới I/O APIs hỗ trợ và `Task.Delay(..., stoppingToken)`; xử lý `OperationCanceledException` đúng lifecycle.

### High — Partial batch failure không có progress semantics

**Vấn đề:** Nếu item giữa batch fail, các item trước đã được index nhưng không có state cho biết batch xử lý tới đâu.

**Tại sao xảy ra:** Database read và external indexing không nằm trong một atomic transaction.

**Ảnh hưởng production:** Retry có thể reprocess; item phía sau có thể bị trì hoãn; incident khó reconstruct.

**Cách sửa:** Thiết kế item/batch idempotency và durable progress. Không cố tạo distributed transaction với Elasticsearch.

### High — Stale version có thể ghi đè version mới

**Vấn đề:** Nhiều workers/batches có thể index cùng product theo thứ tự khác nhau.

**Tại sao xảy ra:** Không có version ordering/optimistic concurrency contract giữa source và search projection.

**Ảnh hưởng production:** Search có thể kết thúc ở state cũ dù database mới hơn.

**Cách sửa:** Mang source version/change sequence vào projection và dùng version-aware update strategy phù hợp Elasticsearch/client contract, hoặc serialize ownership theo product/partition.

### Medium — Load toàn entity và batch không bounded rõ ràng

**Vấn đề:** `ToListAsync()` có thể lấy lượng lớn rows khi update burst.

**Tại sao xảy ra:** Không có batch size, ordering hoặc projection.

**Ảnh hưởng production:** Memory, SQL duration và indexing latency tăng theo burst.

**Cách sửa:** Đọc ordered bounded batches, chỉ project fields cần cho search document và đo batch duration/throughput.

### Medium — Failure handling và backoff thiếu

**Vấn đề:** Một transient Elasticsearch error có thể thoát `ExecuteAsync` tùy exception flow.

**Tại sao xảy ra:** Không có retry classification/backoff hay worker-level recovery policy.

**Ảnh hưởng production:** Worker có thể dừng hoặc hammer dependency khi lỗi.

**Cách sửa:** Phân loại transient/permanent failure, bounded retry với backoff/jitter khi an toàn, alert khi lag vượt SLO.

### Medium — Observability chỉ có count

**Vấn đề:** Log không cho biết watermark, lag, batch duration, failures hoặc product/version.

**Tại sao xảy ra:** Telemetry không mô hình hóa pipeline state.

**Ảnh hưởng production:** Không chứng minh được search freshness hay xác định gap.

**Cách sửa:** Structured logs/metrics cho checkpoint, source-to-index lag, batch size/duration, success/failure/retry và dependency latency.

## Phiên bản đề xuất

Một hướng đơn giản là tách scheduler ownership khỏi web replicas và dùng durable change cursor. Ví dụ worker dưới đây giả định `ProductChanges.Sequence` tăng đơn điệu và checkpoint được lưu bền vững:

```csharp
public sealed class ProductIndexWorker : BackgroundService
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IProductSearchIndexer _indexer;
    private readonly ICheckpointStore _checkpoints;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var checkpoint = await _checkpoints.GetAsync("product-index", stoppingToken);

            await using var db = await _dbFactory.CreateDbContextAsync(stoppingToken);
            var batch = await db.ProductChanges
                .AsNoTracking()
                .Where(x => x.Sequence > checkpoint)
                .OrderBy(x => x.Sequence)
                .Take(200)
                .Select(x => new ProductIndexChange(x.Sequence, x.ProductId, x.Version))
                .ToListAsync(stoppingToken);

            if (batch.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
                continue;
            }

            foreach (var change in batch)
            {
                await _indexer.UpsertLatestAsync(change, stoppingToken);
                await _checkpoints.SetAsync("product-index", change.Sequence, stoppingToken);
            }
        }
    }
}
```

Ví dụ này chưa tự giải quyết multi-worker ownership. Nếu nhiều instances cùng chạy nó, `ICheckpointStore` phải cung cấp lease/claim semantics hoặc worker phải được deploy như singleton execution unit. Nếu throughput sau đo đạc yêu cầu parallelism, partitioning/queue có thể hợp lý hơn.

## Giải thích thiết kế sau khi sửa

Durable sequence loại bỏ phụ thuộc vào rolling time window. Ordered bounded batch làm progress có thể quan sát và kiểm thử. Checkpoint chỉ tiến sau successful projection của item tương ứng, vì vậy crash tạo replay thay vì silent loss; replay phải an toàn nhờ idempotent/version-aware index operation.

Không tự động thêm messaging. Nếu change rate thấp và một worker đáp ứng freshness SLO, polling với durable cursor có thể đơn giản hơn. Khi cần decoupling, burst absorption hoặc nhiều consumers, transactional outbox + messaging mới đáng cân nhắc.

## Trade-offs

- Durable checkpoint thêm state và recovery logic.
- Single worker đơn giản nhưng giới hạn throughput.
- Lease/partitioning tăng concurrency nhưng tăng coordination complexity.
- Outbox/messaging tăng reliability options nhưng thêm broker, operations và eventual consistency.
- Search projection vốn eventual consistent; business cần định nghĩa freshness SLO thay vì giả định instant consistency.

## Cách kiểm thử

1. **Concurrency test:** chạy nhiều worker instances và xác minh ownership/claim không xử lý cùng change ngoài semantics cho phép.
2. **Failure-path test:** fail Elasticsearch giữa batch, restart worker và xác minh không mất change.
3. **Ordering test:** phát hai versions liên tiếp của cùng product và làm completion đảo thứ tự; version cũ không được thắng.
4. **Shutdown test:** cancel host trong query/index/delay; worker dừng trong budget mà không corrupt checkpoint.
5. **Load test:** burst changes lớn, đo source-to-index lag và database/index dependency pressure.

## Quan sát trong production

Theo dõi `index_lag_seconds`, last committed sequence, batch throughput, retry rate, Elasticsearch dependency p95/p99, SQL query duration và worker ownership. Application Insights/Kibana logs cần correlation theo product/change sequence và deployment instance. Alert khi checkpoint đứng yên trong khi source sequence tiếp tục tăng hoặc freshness lag vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào polling + durable cursor không còn đủ và bạn chuyển sang Service Bus/outbox?
2. Nếu Elasticsearch outage kéo dài hai giờ, bạn ưu tiên bảo vệ database, freshness hay recovery throughput như thế nào?
3. Bạn sẽ thiết kế reindex toàn bộ catalog mà không phá incremental indexing ra sao?

# Code Review Challenge 2 — SQL pagination chậm dần và trả duplicate/missing rows khi dữ liệu thay đổi

**Chủ đề:** SQL Server/PostgreSQL, pagination, composite indexes, query plans, consistency, API performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một admin API hiển thị audit events. Table có khoảng 180 triệu rows và tăng nhanh. UI cho phép lọc theo tenant và thời gian, sort newest-first. Ở page đầu API thường dưới 200 ms, nhưng page sâu có thể mất nhiều giây. Users cũng báo đôi lúc thấy một event lặp lại ở hai pages hoặc một event biến mất khi events mới được insert trong lúc họ đang duyệt.

Query hiện tại:

## Đoạn code cần review

```sql
SELECT
    Id,
    TenantId,
    CreatedAtUtc,
    EventType,
    ActorId,
    PayloadJson
FROM AuditEvents
WHERE TenantId = @TenantId
  AND CreatedAtUtc >= @FromUtc
  AND CreatedAtUtc < @ToUtc
ORDER BY CreatedAtUtc DESC
OFFSET @Offset ROWS
FETCH NEXT @PageSize ROWS ONLY;
```

Index hiện có:

```sql
CREATE INDEX IX_AuditEvents_TenantId
ON AuditEvents (TenantId);

CREATE INDEX IX_AuditEvents_CreatedAtUtc
ON AuditEvents (CreatedAtUtc);
```

API tính `@Offset = (@PageNumber - 1) * @PageSize` và cho phép `PageSize` tối đa 500.

## Nhiệm vụ của ứng viên

1. Xác định correctness và performance risks.
2. Giải thích vì sao page sâu chậm dù có indexes.
3. Phân tích duplicate/missing rows khi concurrent inserts xảy ra.
4. Đề xuất index/query/pagination contract phù hợp hơn.
5. Nêu trade-offs giữa offset pagination và keyset/cursor pagination.
6. Giải thích cách test bằng execution plan và production-like data distribution.
7. Đề xuất database/API telemetry cần theo dõi.

## Câu hỏi gợi mở

1. `ORDER BY CreatedAtUtc` có tạo total deterministic order khi nhiều rows có cùng timestamp không?
2. Database phải làm gì với hàng trăm nghìn rows trước `OFFSET`?
3. Hai single-column indexes có tương đương một composite index khớp filter + order không?
4. Nếu một event mới được insert trước khi user tải page 2, offset của các rows cũ thay đổi thế nào?
5. `PayloadJson` có ảnh hưởng gì tới index coverage và I/O decision?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **deep offset cost + unstable ordering under concurrent writes**.

### Gợi ý 2

Tìm một deterministic tuple dùng làm cursor, ví dụ `(CreatedAtUtc, Id)`, rồi thiết kế index theo equality predicate trước, range/order sau.

## Kết quả code review tham khảo

### High — Deep OFFSET có cost tăng theo vị trí page

**Vấn đề:** Query yêu cầu database bỏ qua `@Offset` rows trước khi trả page.

**Tại sao xảy ra:** OFFSET không biến page 10000 thành lookup trực tiếp; engine vẫn phải locate/order/scan đủ rows để skip theo plan thực tế.

**Ảnh hưởng production:** Latency và CPU/read I/O tăng ở deep pages; p95/p99 xấu khi users/export tools duyệt sâu.

**Cách sửa:** Nếu product cần sequential navigation, dùng keyset/cursor pagination với last-seen sort key. Giữ offset nếu random page access là requirement thực sự và cost chấp nhận được.

### High — ORDER BY không deterministic khi timestamps trùng nhau

**Vấn đề:** Chỉ sort `CreatedAtUtc`.

**Tại sao xảy ra:** Nhiều events có thể cùng timestamp; database không có tie-breaker được contract hóa.

**Ảnh hưởng production:** Row ordering giữa executions có thể thay đổi, gây duplicate/missing ngay cả ngoài concurrent inserts.

**Cách sửa:** Dùng total order, ví dụ `ORDER BY CreatedAtUtc DESC, Id DESC` nếu `Id` unique và phù hợp semantics.

### High — Offset pagination không ổn định trước concurrent inserts

**Vấn đề:** Page boundary được định nghĩa bằng vị trí tương đối, không bằng identity của last row.

**Tại sao xảy ra:** Insert mới ở đầu result set dịch chuyển offsets giữa request page 1 và page 2.

**Ảnh hưởng production:** User thấy duplicate hoặc skip rows.

**Cách sửa:** Cursor chứa last `(CreatedAtUtc, Id)` và page kế tiếp dùng predicate lexicographic tương ứng.

### High — Indexes không khớp access pattern tổng thể

**Vấn đề:** Hai indexes đơn cột không nhất thiết hỗ trợ hiệu quả equality filter trên tenant + time range + ordered retrieval.

**Tại sao xảy ra:** Query pattern cần xem xét key order và sort direction cùng cardinality/statistics.

**Ảnh hưởng production:** Sort, scans hoặc nhiều reads hơn cần thiết.

**Cách sửa:** Đánh giá composite index như `(TenantId, CreatedAtUtc DESC, Id DESC)` bằng actual execution plan và workload thật. Không khẳng định index đúng chỉ từ syntax.

### Medium — Payload lớn có thể làm covering index quá đắt

**Vấn đề:** `PayloadJson` có thể lớn.

**Tại sao xảy ra:** Cố INCLUDE mọi selected column có thể làm index phình, tăng write amplification/storage/cache pressure.

**Ảnh hưởng production:** Tối ưu read một query nhưng làm writes và buffer efficiency xấu hơn.

**Cách sửa:** Đo lookup cost. Có thể page IDs/summary fields trước rồi fetch payload khi cần, hoặc chấp nhận key lookup nếu plan tốt. Không mặc định INCLUDE large payload.

### Medium — PageSize 500 có thể khuếch đại response/database cost

**Vấn đề:** API cho page lớn bất kể payload size.

**Tại sao xảy ra:** Query cost, serialization, network và client rendering cùng tăng.

**Ảnh hưởng production:** Tail latency/memory tăng, nhất là với JSON payload lớn.

**Cách sửa:** Chọn maximum dựa trên measured response size/use case; tách export workflow nếu cần tải lượng dữ liệu lớn.

### Medium — Không có evidence-driven plan analysis

**Vấn đề:** Có indexes không chứng minh query đang dùng access path tốt.

**Tại sao xảy ra:** Statistics, tenant skew, parameter values và data distribution ảnh hưởng optimizer.

**Ảnh hưởng production:** Team có thể thêm index sai và không sửa bottleneck.

**Cách sửa:** Thu actual execution plan, logical reads, duration, row estimates/actuals, waits và test representative tenants/time ranges.

## Phiên bản đề xuất

Ví dụ keyset pagination với deterministic order:

```sql
SELECT TOP (@PageSize)
    Id,
    TenantId,
    CreatedAtUtc,
    EventType,
    ActorId,
    PayloadJson
FROM AuditEvents
WHERE TenantId = @TenantId
  AND CreatedAtUtc >= @FromUtc
  AND CreatedAtUtc < @ToUtc
  AND (
        @CursorCreatedAtUtc IS NULL
        OR CreatedAtUtc < @CursorCreatedAtUtc
        OR (CreatedAtUtc = @CursorCreatedAtUtc AND Id < @CursorId)
      )
ORDER BY CreatedAtUtc DESC, Id DESC;
```

Candidate index để **đo và xác minh**, không phải chân lý mặc định:

```sql
CREATE INDEX IX_AuditEvents_Tenant_Created_Id
ON AuditEvents (TenantId, CreatedAtUtc DESC, Id DESC)
INCLUDE (EventType, ActorId);
```

`PayloadJson` cố ý không INCLUDE trong ví dụ vì kích thước chưa biết. Cần đo key lookup/base-table access so với index bloat trước khi quyết định.

Cursor API có thể encode immutable last-seen values thay vì cho client tự sửa raw fields. Server phải validate cursor thuộc cùng filter/sort contract.

## Giải thích thiết kế sau khi sửa

Equality predicate `TenantId` đứng đầu index candidate, sau đó là ordered/range keys phục vụ time filtering và newest-first traversal. `Id` tạo tie-breaker deterministic. Keyset predicate tiếp tục từ identity/order của last row thay vì đếm lại vị trí, nên concurrent inserts ở phía trước không đẩy các rows đã duyệt sang page khác.

Keyset không tự tạo snapshot consistency. Rows bị update/delete trong lúc duyệt vẫn cần semantics được product định nghĩa. Với immutable audit events, model này thường phù hợp hơn; nếu business yêu cầu một frozen snapshot của toàn bộ result set, cần giải pháp khác và đánh giá storage/transaction cost.

## Trade-offs

- Keyset rất tốt cho next/previous traversal nhưng không thuận tiện cho “jump to page 937”.
- Cursor contract phức tạp hơn page number và phải version/validate.
- Composite index cải thiện target read pattern nhưng tăng storage/write amplification.
- Không INCLUDE payload lớn có thể tạo lookups; INCLUDE lại có thể làm index quá nặng.
- Snapshot consistency mạnh hơn có operational cost; audit browsing thường có thể chấp nhận cursor semantics nếu UX được định nghĩa rõ.

## Cách kiểm thử

1. **Database performance test:** so sánh logical reads/duration của offset page 1, 1000, 10000 với keyset trên production-like cardinality.
2. **Execution-plan test:** kiểm tra actual rows, estimates, sort/scan/seek behavior cho nhiều tenant distributions.
3. **Concurrency test:** insert events giữa page requests và xác minh cursor không duplicate các rows đã duyệt.
4. **Tie test:** tạo nhiều rows cùng `CreatedAtUtc`; ordering theo `(CreatedAtUtc, Id)` phải deterministic.
5. **API load test:** đo p95/p99, response bytes, serialization và DB dependency latency với realistic `PageSize`.

## Quan sát trong production

Theo dõi query duration, logical reads, CPU, waits, execution-plan regressions và rows returned theo endpoint/filter shape. Application Insights nên ghi pagination mode, bounded page size và database dependency duration nhưng không log payload nhạy cảm. Dashboard nên phân tách shallow/deep offset nếu legacy endpoint còn tồn tại để chứng minh migration có cải thiện tail latency.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc jump tới arbitrary page number, bạn sẽ giữ offset hay thiết kế UX/data access khác?
2. Nếu `Id` là random GUID thay vì monotonic key, điều gì thay đổi trong cursor/index reasoning?
3. Nếu audit records có thể bị chỉnh sửa `CreatedAtUtc`, keyset guarantee sẽ thay đổi ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 kiểm tra khả năng reasoning về background processing khi application scale-out: một in-process scheduler không tự có single-owner semantics, rolling time window không phải durable progress, và search projection phải chịu được retry, restart, ordering và dependency failure.

Challenge 2 kiểm tra data-access reasoning ở production scale: index phải xuất phát từ query pattern và execution evidence; deep offset có intrinsic traversal cost; stable pagination cần deterministic ordering và cursor semantics phù hợp với concurrent writes.

## Mẫu tư duy cần nhớ

- Khi scale-out, luôn hỏi **ai sở hữu background work và ownership được enforce ở đâu**.
- Retry-safe processing cần durable progress và idempotent/version-aware side effects.
- Với performance, **measure execution behavior before adding infrastructure or indexes**.
- Pagination cần total order; concurrent data changes phải là một phần của API contract.
- Test failure path và production-scale data distribution, không chỉ happy path/local dataset.
