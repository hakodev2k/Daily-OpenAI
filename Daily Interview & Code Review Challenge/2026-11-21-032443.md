# Code Review Challenge 1 — Upload chứng từ nhân sự vào Azure Blob Storage

## Bối cảnh

Portal nhân sự nhiều tenant chạy trên 4 Azure App Service instances, cho phép upload PDF/JPEG/PNG tối đa 20 MiB vào hồ sơ nghỉ phép. Chỉ chủ hồ sơ và HR được xem. Khi 100 người upload đồng thời, memory tăng và đôi lúc SQL không có metadata dù Blob đã tồn tại. Một khách hàng báo thấy chứng từ của tenant khác. Hotfix không được sửa bảng hồ sơ hiện có.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/leave/{leaveId:guid}/attachments")]
public sealed class AttachmentsController : ControllerBase
{
    private readonly HrDbContext _db;
    private readonly BlobContainerClient _container;
    private readonly ILogger<AttachmentsController> _log;

    public AttachmentsController(HrDbContext db,
        BlobContainerClient container, ILogger<AttachmentsController> log)
    {
        _db = db;
        _container = container;
        _log = log;
    }

    [HttpPost]
    public async Task<IActionResult> Upload(Guid leaveId, IFormFile file)
    {
        var leave = await _db.LeaveRequests.FindAsync(leaveId);
        if (leave is null) return NotFound();

        var name = file.FileName;
        var blob = _container.GetBlobClient($"leave/{leaveId}/{name}");
        using var memory = new MemoryStream();
        await file.CopyToAsync(memory);
        memory.Position = 0;
        await blob.UploadAsync(memory, overwrite: true);

        var item = new LeaveAttachment {
            Id = Guid.NewGuid(),
            LeaveRequestId = leaveId,
            FileName = name,
            BlobPath = blob.Name,
            Size = file.Length
        };
        _db.LeaveAttachments.Add(item);
        await _db.SaveChangesAsync();
        _log.LogInformation("Uploaded {Name} {Path}", name, blob.Name);
        return Ok(new { item.Id, Url = blob.Uri.ToString() });
    }

    [HttpGet("{attachmentId:guid}")]
    public async Task<IActionResult> Download(Guid leaveId, Guid attachmentId)
    {
        var item = await _db.LeaveAttachments
            .FirstOrDefaultAsync(x => x.Id == attachmentId);
        if (item is null) return NotFound();
        var result = await _container.GetBlobClient(item.BlobPath)
            .DownloadStreamingAsync();
        return File(result.Value.Content,
            result.Value.Details.ContentType ?? "application/octet-stream",
            item.FileName);
    }
}
```

## Kết quả code review tham khảo

### Critical — Thiếu resource-level authorization

**Vấn đề:** Upload chỉ kiểm tra leave tồn tại; Download chỉ tra attachmentId mà không kiểm tra tenant, leaveId hay principal.  
**Tại sao xảy ra:** GUID được dùng như quyền truy cập ngầm.  
**Ảnh hưởng production:** IDOR và cross-tenant disclosure, thay đổi hồ sơ người khác.  
**Cách sửa:** Xác thực principal, lấy tenant từ trusted claims, kiểm tra owner/HR policy, truy vấn attachment theo tenant + leaveId + attachmentId trước khi đọc Blob.

### High — Không giới hạn upload và kiểm tra nội dung

**Vấn đề:** Không kiểm tra file null, kích thước, extension, signature hoặc malware policy.  
**Tại sao xảy ra:** Tin vào input và metadata của client.  
**Ảnh hưởng production:** Resource exhaustion, file nguy hiểm, chi phí storage.  
**Cách sửa:** Request/multipart size limits ở proxy và app; validate extension, magic bytes, size; quarantine/scan tùy threat model.

### High — MemoryStream cho toàn bộ file

**Vấn đề:** Copy toàn bộ payload vào memory.  
**Tại sao xảy ra:** Buffer thêm một bản ngoài buffering có thể đã xảy ra trong model binding.  
**Ảnh hưởng production:** LOH allocations, GC pause, OOM và 5xx dưới tải.  
**Cách sửa:** Stream từ `OpenReadStream` tới Blob, truyền cancellation; nếu cần true streaming multipart, dùng MultipartReader và giới hạn bytes đọc thực tế.

### High — Overwrite theo tên client

**Vấn đề:** Hai uploads cùng filename vào cùng leave ghi đè Blob.  
**Tại sao xảy ra:** Storage key dựa vào `file.FileName` và `overwrite: true`.  
**Ảnh hưởng production:** Mất tài liệu, race giữa requests.  
**Cách sửa:** Sinh opaque unique key bằng GUID, giữ sanitized display name riêng, dùng conditional create `IfNoneMatch`.

### High — Không có recovery cho Blob/SQL partial failure

**Vấn đề:** Blob thành công nhưng `SaveChangesAsync` thất bại tạo orphan; retry có thể overwrite.  
**Tại sao xảy ra:** Không có atomic transaction xuyên Blob và SQL.  
**Ảnh hưởng production:** Mất metadata, tài liệu khó truy xuất và chi phí lưu trữ tăng.  
**Cách sửa:** Durable upload registry với `Pending/Ready/Failed`, idempotency key, reconciliation và orphan cleanup; lease cho concurrent retry.

### Medium — Thiếu cancellation

**Vấn đề:** Không truyền `RequestAborted` cho DB/Blob.  
**Tại sao xảy ra:** Các overload không nhận cancellation.  
**Ảnh hưởng production:** Tốn I/O khi client disconnect, shutdown chậm.  
**Cách sửa:** Truyền CancellationToken, thiết kế recovery nếu cancellation sau Blob commit.

### Medium — Metadata và download policy không an toàn

**Vấn đề:** Filename do client đặt và Blob ContentType chưa được chuẩn hóa; raw URI được trả về.  
**Tại sao xảy ra:** Không tách display name, MIME đã kiểm chứng và access mechanism.  
**Ảnh hưởng production:** Browser xử lý content không mong muốn hoặc URL không truy cập được; nếu container public thì lộ file.  
**Cách sửa:** Content-Disposition attachment, nosniff, private container, authorized download API hoặc SAS ngắn hạn sau authorization.

### Medium — Thiếu idempotency và telemetry

**Vấn đề:** Retry không có operation identity; log filename có thể chứa PII.  
**Tại sao xảy ra:** Không tracking trạng thái và correlation.  
**Ảnh hưởng production:** Duplicate metadata, khó truy nguyên incident.  
**Cách sửa:** Unique idempotency key scoped theo tenant, structured operation ID, duration, Pending age và orphan metrics.

## Phiên bản đề xuất

Đây là service-layer sketch, giả định `IAccessPolicy` kiểm tra tenant/owner/HR từ trusted principal, `IUploadRegistry` có unique idempotency constraint, lease có expiry/fencing và reconciliation worker; `IFileValidator` kiểm tra signature/size mà không làm hỏng stream upload.

```csharp
public sealed class UploadService(
    IAccessPolicy access,
    IUploadRegistry registry,
    IFileValidator validator,
    BlobContainerClient container)
{
    public async Task<Guid> UploadAsync(
        ClaimsPrincipal principal, Guid leaveId, IFormFile file,
        string idempotencyKey, CancellationToken ct)
    {
        if (file is null || file.Length is <= 0 or > 20 * 1024 * 1024)
            throw new InvalidDataException("Invalid file size");

        var tenant = await access.RequireUploadAsync(principal, leaveId, ct);
        var contentType = await validator.ValidateAsync(file, ct);
        var op = await registry.GetOrCreateAsync(
            tenant, leaveId, idempotencyKey,
            Path.GetFileName(file.FileName), ct);

        if (op.Status == UploadStatus.Ready) return op.AttachmentId;
        if (!await registry.TryLeaseAsync(op.Id, ct))
            throw new UploadInProgressException();

        var key = $"tenants/{tenant}/leave/{leaveId}/{op.AttachmentId:N}";
        try
        {
            await using var stream = file.OpenReadStream();
            await container.GetBlobClient(key).UploadAsync(stream,
                new BlobUploadOptions {
                    HttpHeaders = new BlobHttpHeaders {
                        ContentType = contentType
                    },
                    Conditions = new BlobRequestConditions {
                        IfNoneMatch = ETag.All
                    }
                }, ct);
            await registry.MarkReadyAsync(op.Id, key, ct);
            return op.AttachmentId;
        }
        catch
        {
            await registry.FlagForReconciliationAsync(
                op.Id, CancellationToken.None);
            throw;
        }
    }
}
```

`FlagForReconciliationAsync` cũng có thể lỗi: periodic worker phải quét Pending quá hạn và đối chiếu Blob existence/ETag. Nếu upload timeout nhưng Blob đã được tạo, retry gặp precondition failure cần reconcile, không coi là thất bại vĩnh viễn. `IFileValidator` phải mở stream riêng hoặc reset offset; giới hạn bytes thực đọc nếu không tin declared length. Download phải kiểm tra tenant/leave/attachment cùng quyền, chỉ trả record Ready và stream với attachment disposition. Không dùng Blob URL làm quyền truy cập.

## Giải thích thiết kế sau khi sửa

Opaque key tránh collision và không đưa tên client vào đường dẫn storage. Authorization thực thi trước storage access. State machine xử lý partial failure thay vì giả định distributed transaction. Conditional create và registry lease xử lý các tầng concurrency khác nhau. Dùng direct SAS upload chỉ khi chấp nhận thêm finalize, scan và cleanup workflow.

## Trade-offs

Proxy streaming giữ kiểm soát tập trung nhưng tốn bandwidth App Service và có thể vẫn buffer multipart. Direct-to-Blob SAS giảm tải nhưng tăng độ phức tạp bảo mật và orphan cleanup. Registry thêm schema và background job; với lưu lượng thấp có thể bắt đầu bằng state machine tối giản.

## Cách kiểm thử

1. **Security integration:** cross-tenant upload/download và attachmentId hợp lệ với leaveId sai đều bị chặn.
2. **Concurrency:** 20 retries cùng idempotency key không tạo hai Ready records; cùng filename không overwrite.
3. **Failure injection:** Blob success + SQL failure và timeout sau commit được reconcile.
4. **Load:** 100 uploads 20 MiB, đo memory, GC, temp disk, p95, HTTP 413 và restarts.
5. **Validation:** spoof MIME, file rỗng, oversized, tên Unicode, client cancellation.

## Quan sát trong production

Application Insights trace theo operationId và tenant pseudonym, không log filename nhạy cảm; metrics bytes, upload duration, 4xx/5xx, Blob 409/412, SQL errors, Pending age, orphan count, memory/GC, temp disk. Alert khi Pending vượt SLA hoặc cross-tenant denial tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu upload 2 GiB, bạn chọn proxy streaming hay direct SAS và vì sao?
2. Nếu Blob đã commit nhưng API timeout, retry an toàn ra sao?
3. Nếu phải xóa tài liệu theo retention policy, xử lý orphan và backup thế nào?

```tsx
type Customer = { id: string; name: string; status: string };

export function CustomerSearch({ accessToken }: { accessToken: string }) {
  const [term, setTerm] = React.useState("");
  const [status, setStatus] = React.useState("all");
  const [page, setPage] = React.useState(1);
  const [items, setItems] = React.useState<Customer[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");

  React.useEffect(() => {
    setLoading(true);
    fetch(`/api/customers?q=${term}&status=${status}&page=${page}`, {
      headers: { Authorization: `Bearer ${accessToken}` }
    })
      .then(response => response.json())
      .then((data: { items: Customer[] }) => {
        setItems(page === 1 ? data.items : [...items, ...data.items]);
        setError("");
      })
      .catch(() => setError("Không tải được dữ liệu"))
      .finally(() => setLoading(false));
  }, [term, status, page]);

  const changeTerm = (value: string) => {
    setTerm(value);
    setPage(1);
  };

  return <section>
    <input value={term} onChange={e => changeTerm(e.target.value)} />
    <select value={status} onChange={e => {
      setStatus(e.target.value);
      setPage(1);
    }}>
      <option value="all">All</option>
      <option value="active">Active</option>
      <option value="inactive">Inactive</option>
    </select>
    {error && <p role="alert">{error}</p>}
    {items.map(c => <div key={c.id}>{c.name}</div>)}
    <button disabled={loading} onClick={() => setPage(page + 1)}>
      Next
    </button>
  </section>;
}
```

## Kết quả code review tham khảo

### High — Stale response overwrite

**Vấn đề:** Request cũ có thể ghi đè kết quả mới.  
**Tại sao xảy ra:** Network không bảo đảm response order.

### High — Stale closure và duplicate rows

**Vấn đề:** `[...items, ...data.items]` dùng snapshot cũ.  
**Tại sao xảy ra:** Effect capture `items` từ render tạo callback.  
**Ảnh hưởng production:** Missing/duplicate rows, race giữa pages.

**Tại sao xảy ra:** Effect phụ thuộc trực tiếp `term`.

## Phiên bản đề xuất

Bản sửa chọn **single-page navigation**, không append; giả định API trả `{items, hasMore}` và server enforce tenant authorization. Để bảo đảm UI không hiện dữ liệu của query trước trong thời gian debounce, render results chỉ khi `term === debounced` và key của response khớp query hiện tại.

```tsx
type Customer = { id: string; name: string; status: string };
type Result = { items: Customer[]; hasMore: boolean };
const empty: Result = { items: [], hasMore: false };

function CustomerSearch({ accessToken }: { accessToken: string }) {
  const [term, setTerm] = React.useState("");
  const [debounced, setDebounced] = React.useState("");
  const [status, setStatus] = React.useState("all");
  const [page, setPage] = React.useState(1);
  const [data, setData] = React.useState<Result>(empty);
  const [dataKey, setDataKey] = React.useState("");
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");
  const requestId = React.useRef(0);

  React.useEffect(() => {
    const timer = setTimeout(() => setDebounced(term), 300);
    return () => clearTimeout(timer);
  }, [term]);

  const key = JSON.stringify([debounced, status, page, accessToken]);
  React.useEffect(() => {
    const controller = new AbortController();
    const id = ++requestId.current;
    const params = new URLSearchParams({
      q: debounced, status, page: String(page)
    });
    setLoading(true);
    setError("");
    setDataKey("");
    (async () => {
      try {
        const response = await fetch(`/api/customers?${params}`, {
          headers: { Authorization: `Bearer ${accessToken}` },
          signal: controller.signal
        });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const body: unknown = await response.json();
        if (!isResult(body)) throw new Error("Invalid response");
        if (id === requestId.current && !controller.signal.aborted) {
          setData(body);
          setDataKey(key);
        }
      } catch (e) {
        if (id === requestId.current && !controller.signal.aborted)
          setError(e instanceof Error ? e.message : "Network error");
      } finally {
        if (id === requestId.current && !controller.signal.aborted)
          setLoading(false);
      }
    })();
    return () => { controller.abort(); requestId.current++; };
  }, [key, debounced, status, page, accessToken]);

  const valid = term === debounced && dataKey === key;
  return <section>
    <input value={term} onChange={e => {
      setTerm(e.target.value); setPage(1);
    }} />
    <select value={status} onChange={e => {
      setStatus(e.target.value); setPage(1);
    }}>
      <option value="all">All</option>
      <option value="active">Active</option>
      <option value="inactive">Inactive</option>
    </select>
    {(loading || term !== debounced) && <p>Loading…</p>}
    {error && <p role="alert">{error}</p>}
    {valid && data.items.map(c => <div key={c.id}>{c.name}</div>)}
    <button disabled={!valid || loading || page === 1}
      onClick={() => setPage(p => p - 1)}>Previous</button>
    <button disabled={!valid || loading || !data.hasMore}
      onClick={() => setPage(p => p + 1)}>Next</button>
  </section>;
}

function isResult(x: unknown): x is Result {
  if (!x || typeof x !== "object") return false;
  const r = x as Record<string, unknown>;
  return typeof r.hasMore === "boolean" &&
    Array.isArray(r.items) &&
    r.items.every((c: unknown) =>
      !!c && typeof c === "object" &&
      typeof (c as Customer).id === "string" &&
      typeof (c as Customer).name === "string");
}
```

`key` ở đây chứa accessToken chỉ trong memory để invalidation; không log hoặc persist key. Trong hệ thống thực, ưu tiên token version/session identity thay vì nhét token thô vào cache key. Guard `dataKey` ngăn render response thuộc query cũ; `AbortController` giúp giảm tài nguyên nhưng không bảo đảm server dừng công việc. Backend vẫn phải enforce authorization và cancellation.

## Giải thích thiết kế sau khi sửa

Mỗi request có identity và cleanup, response lỗi HTTP được xử lý rõ ràng, query được encode, page có hasMore. Chuyển sang single-page tránh append race. Nếu business yêu cầu infinite scroll và back navigation, cần cache theo query key/cursor và merge theo thứ tự server thay vì chỉ dùng một array.

## Trade-offs

Debounce giảm request nhưng tăng 300 ms latency. Abort giảm work phía client nhưng backend có thể vẫn xử lý. Single-page đơn giản hơn infinite scroll; cursor API đòi thay đổi contract. Thư viện data fetching có thể giảm boilerplate nhưng cần quản lý cache key và auth scope chính xác.

## Cách kiểm thử

1. **Race:** mock response A chậm hơn B; UI không hiện kết quả A.
2. **Component:** gõ nhanh nhiều ký tự; xác minh debounce và request count.
3. **Failure:** 401/403/500, malformed payload và network error không làm crash.
4. **Pagination integration:** insert/delete giữa pages, xác minh stable ordering/cursor.
5. **Playwright E2E:** đổi term/status liên tục, back/next, token refresh và browser navigation.

## Quan sát trong production

Browser request count, abort rate, latency, HTTP status, frontend errors không chứa token/PII. Application Insights correlation ID, p95/p99 API latency, SQL duration, 401/403/429 rate, cancellation, user-visible search error rate. Alert khi requests per session tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu phải hỗ trợ infinite scroll và restore scroll position, bạn thiết kế cache/cursor thế nào?
2. Nếu token refresh xảy ra giữa request, retry sao để tránh retry storm?
3. Nếu backend thay đổi thứ tự kết quả giữa các pages, frontend có tự bảo đảm không trùng được không?

## Kiến thức trọng tâm

Resource authorization phải gắn với tenant, principal và record; GUID không phải quyền. Blob và SQL có partial failure nên cần idempotency và reconciliation.
