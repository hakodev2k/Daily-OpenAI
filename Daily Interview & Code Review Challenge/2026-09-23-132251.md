# Code Review Challenge 1 — API multi-tenant cho phép đọc và sửa dữ liệu tenant khác

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, authorization, multi-tenancy, mass assignment, optimistic concurrency, observability  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–12

## Bối cảnh

Một SaaS quản lý approval workflow chạy ASP.NET Core và SQL Server. Người dùng đăng nhập qua Microsoft Entra ID; JWT chứa `sub`, `tenant_id` và role. Mỗi `ApprovalRequest` thuộc đúng một tenant. API chạy nhiều instances nhưng dùng chung database.

Support nhận được báo cáo rằng một user biết GUID của request thuộc tenant khác có thể xem metadata của request đó. Chưa có bằng chứng dữ liệu đã bị sửa trái phép. Team cho rằng `[Authorize]` đã đủ vì endpoint chỉ dành cho user đăng nhập.

Product cũng cho phép editor cập nhật `Title` và `Description`, nhưng chỉ tenant admin mới được đổi `Status` sang `Approved`.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/approvals")]
[Authorize]
public sealed class ApprovalsController : ControllerBase
{
    private readonly WorkflowDbContext _db;
    private readonly ILogger<ApprovalsController> _logger;

    public ApprovalsController(
        WorkflowDbContext db,
        ILogger<ApprovalsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{id:guid}")]
    public async Task<ActionResult<ApprovalRequest>> Get(
        Guid id,
        CancellationToken cancellationToken)
    {
        var request = await _db.ApprovalRequests
            .AsNoTracking()
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        return request is null ? NotFound() : Ok(request);
    }

    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id,
        ApprovalRequest input,
        CancellationToken cancellationToken)
    {
        if (id != input.Id)
            return BadRequest();

        _db.Entry(input).State = EntityState.Modified;
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Approval {ApprovalId} updated by {User}",
            id,
            User.Identity!.Name);

        return NoContent();
    }
}

public sealed class ApprovalRequest
{
    public Guid Id { get; set; }
    public Guid TenantId { get; set; }
    public string Title { get; set; } = "";
    public string Description { get; set; } = "";
    public string Status { get; set; } = "Draft";
    public Guid CreatedByUserId { get; set; }
    public DateTime CreatedAtUtc { get; set; }
    public DateTime UpdatedAtUtc { get; set; }
}
```

2. Giải thích production impact và điều kiện khai thác.

4. Đề xuất implementation/design sửa mà không over-engineer.
5. Nêu testing strategy chứng minh tenant isolation và field-level authorization.
6. Nêu telemetry/audit cần có nhưng không làm lộ dữ liệu nhạy cảm.

## Câu hỏi gợi mở

1. `[Authorize]` xác nhận điều gì và không xác nhận điều gì?

## Kết quả code review tham khảo

### Critical — Query không enforce tenant boundary

**Vấn đề:** `GET` lookup chỉ bằng `Id`; `PUT` thậm chí không load resource thuộc tenant hiện tại.  
**Tại sao xảy ra:** `[Authorize]` chỉ yêu cầu principal đã authenticated; nó không tự áp resource ownership.  
**Ảnh hưởng production:** User đã đăng nhập có thể đọc hoặc sửa resource tenant khác nếu biết/đoán/thu được ID. Đây là broken object-level authorization.  
**Cách sửa:** Resolve tenant từ trusted claim/server context và đưa tenant predicate vào data access: `x.Id == id && x.TenantId == tenantId`. Với update, load entity trong tenant scope rồi mutate field được phép. Có thể dùng global query filter nếu team hiểu rõ bypass semantics, nhưng không được coi filter là lớp bảo vệ duy nhất nếu có code path bỏ filter.

### Critical — Over-posting/mass assignment cho phép sửa field đặc quyền

**Vấn đề:** Request body bind trực tiếp vào `ApprovalRequest`, sau đó toàn entity được đánh `Modified`.  
**Tại sao xảy ra:** API contract và persistence model là cùng một type.  
**Ảnh hưởng production:** Client có thể gửi `TenantId`, `Status`, `CreatedByUserId`, timestamps và các field khác mà business không cho phép.  
**Cách sửa:** Dùng request DTO chỉ chứa mutable fields; server load entity và gán explicit. Action `Approve` nên có authorization policy/business transition riêng thay vì cho editor gửi arbitrary `Status`.

### High — Không có resource/action authorization cho approve

**Vấn đề:** Không phân biệt editor với tenant admin.  
**Tại sao xảy ra:** Chỉ có controller-level authentication.  
**Ảnh hưởng production:** User có quyền edit thông thường có thể tự chuyển trạng thái nếu endpoint cho phép mass assignment.  
**Cách sửa:** Policy/authorization handler hoặc application-layer permission check dựa trên trusted claims và resource tenant; validate state transition server-side.

### High — Client có thể thay đổi TenantId

**Vấn đề:** `TenantId` nằm trong entity nhận từ request.  
**Tại sao xảy ra:** Server tin ownership field từ client.  
**Ảnh hưởng production:** Có thể chuyển resource sang tenant khác hoặc phá isolation/invariants.  
**Cách sửa:** Tenant ownership immutable đối với endpoint này; lấy tenant từ server-side identity context.

### High — Lost update do không có optimistic concurrency

**Vấn đề:** Không có `rowversion`/concurrency token hoặc precondition.  
**Tại sao xảy ra:** Last writer wins mà client không biết dữ liệu đã thay đổi.  
**Ảnh hưởng production:** Hai editor có thể âm thầm ghi đè thay đổi của nhau.  
**Cách sửa:** Dùng SQL Server `rowversion` làm EF Core concurrency token; expose version/ETag phù hợp API contract và trả `409 Conflict` hoặc `412 Precondition Failed` theo semantics đã chọn.

### Medium — Trả persistence entity trực tiếp

**Vấn đề:** `GET` serialize entity database.  
**Tại sao xảy ra:** Không có response DTO/projection.  
**Ảnh hưởng production:** Dễ vô tình expose field nội bộ khi entity được mở rộng; coupling API contract với schema.  
**Cách sửa:** Projection sang response DTO chứa field thực sự được phép công khai.

### Medium — Không validate state/input

**Vấn đề:** Không thấy validation length/content/business state.  
**Tại sao xảy ra:** Endpoint dựa vào model binding tối thiểu.  
**Ảnh hưởng production:** Invalid data, oversized strings hoặc transition không hợp lệ đi sâu tới DB/business logic.  
**Cách sửa:** Validate DTO và business transition; DB constraints vẫn cần cho invariant quan trọng.

### Medium — Audit log chưa đủ và identity field không ổn định

**Vấn đề:** Log `User.Identity.Name` nhưng thiếu tenant, subject/object ID, action/result và correlation.  
**Tại sao xảy ra:** Log phục vụ debug hơn audit.  
**Ảnh hưởng production:** Khó điều tra cross-tenant access hoặc privilege misuse.  
**Cách sửa:** Audit immutable identifiers như subject ID, tenant ID, approval ID, action, outcome và correlation/trace ID; không log token hoặc document body.

### Low — `UpdatedAtUtc` không được server quản lý rõ ràng

**Vấn đề:** Client có thể gửi timestamp tùy ý.  
**Tại sao xảy ra:** Full entity update.  
**Ảnh hưởng production:** Audit/history thiếu tin cậy.  
**Cách sửa:** Set timestamp server-side hoặc interceptor/domain mechanism nhất quán.

## Phiên bản đề xuất

```csharp
public sealed record UpdateApprovalRequest(
    string Title,
    string Description,
    byte[] Version);

public sealed record ApprovalResponse(
    Guid Id,
    string Title,
    string Description,
    string Status,
    byte[] Version);

[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(
    Guid id,
    UpdateApprovalRequest input,
    CancellationToken cancellationToken)
{
    var tenantId = _currentUser.RequireTenantId();

    var entity = await _db.ApprovalRequests
        .SingleOrDefaultAsync(
            x => x.Id == id && x.TenantId == tenantId,
            cancellationToken);

    if (entity is null)
        return NotFound();

    var auth = await _authorizationService.AuthorizeAsync(
        User, entity, "Approval.Edit");

    if (!auth.Succeeded)
        return Forbid();

    entity.Title = input.Title;
    entity.Description = input.Description;
    entity.UpdatedAtUtc = DateTime.UtcNow;

    _db.Entry(entity)
        .Property(x => x.Version)
        .OriginalValue = input.Version;

    try
    {
        await _db.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateConcurrencyException)
    {
        return Conflict(new ProblemDetails
        {
            Title = "The approval was changed by another user."
        });
    }

    _logger.LogInformation(
        "Approval updated {ApprovalId} {TenantId} {SubjectId}",
        entity.Id,
        tenantId,
        _currentUser.SubjectId);

    return NoContent();
}
```

Entity có thể thêm:

```csharp
[Timestamp]
public byte[] Version { get; set; } = Array.Empty<byte>();
```

`Approve` nên là command/endpoint riêng hoặc application operation riêng có policy `Approval.Approve`, validate allowed state transition và vẫn query resource trong tenant boundary.

## Giải thích thiết kế sau khi sửa

Tenant được lấy từ authenticated server context, không lấy từ payload. Query scope tenant ngay tại database để resource tenant khác không được materialize. DTO là allow-list field. Resource-level policy kiểm soát action. Optimistic concurrency bảo vệ lost update nhưng không thay thế business authorization.

Không nhất thiết phải thêm Repository Pattern chỉ để đạt mục tiêu này; direct `DbContext` trong application boundary có thể đủ nếu tenant scoping, authorization và testability được tổ chức rõ ràng.

## Trade-offs

Global query filter giảm nguy cơ quên tenant predicate nhưng có thể bị bypass bởi `IgnoreQueryFilters()` và tạo false confidence; cần conventions/tests. Trả `404` cho cross-tenant resource có thể giảm resource enumeration so với `403`, nhưng API semantics phải nhất quán. Tách endpoint `Approve` làm contract rõ hơn nhưng tăng số operation; đổi lại permission và transition dễ audit hơn.

## Cách kiểm thử

1. Integration test user tenant A gọi `GET/PUT` với ID tenant B: không đọc/sửa được dữ liệu.
2. API test editor cố gửi `TenantId`, `Status`, `CreatedByUserId`: contract không bind hoặc không thay đổi các field đó.
3. Authorization test editor không approve được nhưng tenant admin có thể theo policy.
4. Concurrency integration test hai clients dùng cùng version: một update thành công, update còn lại nhận conflict.
5. Security regression test toàn bộ resource endpoints bằng ma trận tenant/role/action, không chỉ controller này.

## Quan sát trong production

Theo dõi `401/403/404` theo endpoint và tenant-safe dimensions, authorization failures, concurrency conflicts, audit events, trace/correlation ID và anomalous repeated access tới nhiều resource IDs. Không log JWT, document description hoặc secrets. Alert cần tránh biến mọi `404` thành security incident nhưng phải phát hiện pattern enumeration đáng ngờ.

## Câu hỏi phỏng vấn mở rộng

1. Bạn chọn global query filter hay explicit tenant predicate cho hệ thống lớn như thế nào?
2. Nếu một support admin được phép cross-tenant access, bạn thiết kế exception path thế nào để không phá default isolation?
3. Nếu tenant ID trong token có thể thay đổi theo identity provider mapping, đâu là source of truth cho internal tenant ownership?

# Code Review Challenge 2 — CI/CD chạy EF Core migration từ mọi replica và làm rollout thất bại

**Chủ đề:** .NET deployment, EF Core migrations, TeamCity/Octopus Deploy, Kubernetes/App Service, release safety, backward compatibility, rollback, observability  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core API được build bằng TeamCity và deploy qua Octopus Deploy. Production có 6 replicas. Team muốn “tự động hóa hoàn toàn” nên application gọi EF Core migrations khi startup. Release mới đổi cột `Customer.FullName` thành `DisplayName` và xóa cột cũ trong migration.

Trong rolling deployment, một số pod mới start được, một số pod cũ bắt đầu trả `500`. Có lần hai pod mới cùng startup và migration báo database object already exists. Rollback application image cũng thất bại vì schema cũ đã bị thay đổi.

## Đoạn code cần review

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("Default")));

var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    db.Database.Migrate();
}

app.MapControllers();
app.Run();
```

Migration:

```csharp
public partial class RenameCustomerName : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropColumn(
            name: "FullName",
            table: "Customers");

        migrationBuilder.AddColumn<string>(
            name: "DisplayName",
            table: "Customers",
            type: "nvarchar(200)",
            nullable: false,
            defaultValue: "");
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropColumn(
            name: "DisplayName",
            table: "Customers");

        migrationBuilder.AddColumn<string>(
            name: "FullName",
            table: "Customers",
            type: "nvarchar(200)",
            nullable: false,
            defaultValue: "");
    }
}
```

Octopus deployment step hiện tại:

```text
1. Deploy application package to all targets using rolling deployment
2. Wait for health endpoint
3. Mark release successful
```

## Nhiệm vụ của ứng viên

1. Xác định deployment, data-loss, compatibility và concurrency issues.
2. Giải thích vì sao “migration tự chạy khi startup” nguy hiểm hơn khi horizontal scale.
3. Phân tích old-version/new-version compatibility trong rolling deployment.
4. Đề xuất release sequence an toàn hơn.
5. Nêu rollback strategy khi schema change không dễ reverse.
6. Đề xuất testing/telemetry để phát hiện lỗi trước và trong production rollout.

## Câu hỏi gợi mở

1. Trong rolling deployment, version cũ và mới có chạy đồng thời không?
2. Drop `FullName` trước khi tất cả instance cũ biến mất gây điều gì?
3. `Down()` có thực sự khôi phục dữ liệu đã drop không?
4. Migration nên được thực thi bởi bao nhiêu actor trong một release?
5. Expand/contract migration giải quyết compatibility window thế nào?

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Destructive migration làm mất dữ liệu

**Vấn đề:** `FullName` bị drop trước khi dữ liệu được chuyển sang `DisplayName`.  
**Tại sao xảy ra:** Migration thực hiện drop/add thay vì rename có chủ đích hoặc expand/backfill/contract.  
**Ảnh hưởng production:** Tên khách hàng bị mất; `Down()` chỉ tạo lại cột rỗng và không thể khôi phục dữ liệu.  
**Cách sửa:** Thiết kế migration bảo toàn dữ liệu. Với zero/low-downtime rollout, thường add `DisplayName` nullable/compatible trước, backfill, deploy code tương thích cả hai, chuyển read/write, xác minh rồi mới drop `FullName` ở release sau.

### Critical — Schema mới phá application version cũ trong rolling deployment

**Vấn đề:** Old replicas vẫn kỳ vọng `FullName` khi cột đã bị drop.  
**Tại sao xảy ra:** Migration không backward-compatible trong khoảng thời gian hai versions cùng chạy.  
**Ảnh hưởng production:** Old pods trả SQL errors/500 ngay trong rollout.  
**Cách sửa:** Expand/contract; mọi schema mutation ở phase đầu phải tương thích với old và new binaries cho tới khi old version đã rời production.

### High — Mỗi replica tự chạy migration khi startup

**Vấn đề:** Nhiều process có thể cùng cố mutate schema.  
**Tại sao xảy ra:** `Database.Migrate()` nằm trong startup path của application.  
**Ảnh hưởng production:** Contention, startup failure, unpredictable release timing; migration dài còn có thể làm health/startup timeout.  
**Cách sửa:** Thực thi migration bằng một controlled deployment step/job với single-writer semantics trước/giữa rollout theo migration phase. Application identity bình thường không nhất thiết cần DDL permission.

### High — Rollback binary không đồng nghĩa rollback schema/data

**Vấn đề:** Release plan giả định deploy image cũ là đủ.  
**Tại sao xảy ra:** Schema mutation đã xảy ra và có thể destructive.  
**Ảnh hưởng production:** Rollback app tiếp tục fail hoặc dữ liệu không thể phục hồi.  
**Cách sửa:** Ưu tiên forward-compatible migration; backup/PITR và tested recovery cho destructive operations; rollback plan phải chỉ rõ app/schema/data compatibility thay vì tự động chạy `Down()`.

### High — Application startup bị coupling với migration duration/failure

**Vấn đề:** API chưa start cho tới khi migration hoàn tất.  
**Tại sao xảy ra:** Migration nằm trước `app.Run()`.  
**Ảnh hưởng production:** Schema lock/long migration làm pod fail startup/readiness hoặc kéo dài rollout.  
**Cách sửa:** Tách migration lifecycle khỏi serving process; đặt timeout, telemetry và approval/risk gates phù hợp trong release pipeline.

### Medium — `Migrate()` synchronous trong startup

**Vấn đề:** Blocking synchronous DB operation ở startup và không có cancellation/timeout flow rõ.  
**Tại sao xảy ra:** Dùng sync API trực tiếp.  
**Ảnh hưởng production:** Khó kiểm soát shutdown/deployment timeout. Đây không phải root cause chính nhưng làm startup behavior kém kiểm soát hơn.  
**Cách sửa:** Tốt nhất loại migration khỏi app startup; migration runner riêng có explicit timeout/cancellation.

### Medium — Migration và application dùng cùng database privilege

**Vấn đề:** Runtime connection có khả năng DDL nếu nó có thể chạy migration.  
**Tại sao xảy ra:** Không tách deployment identity khỏi runtime identity.  
**Ảnh hưởng production:** Tăng blast radius khi runtime credential bị compromise hoặc bug chạy schema operation.  
**Cách sửa:** Runtime principal least privilege cho DML cần thiết; migration principal riêng với DDL, secret/identity quản lý trong deployment platform.

### Medium — Pipeline không có explicit migration/compatibility gate

**Vấn đề:** Octopus chỉ deploy package rồi health check.  
**Tại sao xảy ra:** Schema evolution không được coi là release artifact/risk riêng.  
**Ảnh hưởng production:** Breaking migration chỉ được phát hiện khi app đã rollout.  
**Cách sửa:** Generate/review migration SQL, test against production-like schema/data, chạy controlled migration phase, verify telemetry rồi rollout application.

## Phiên bản đề xuất

Application startup không tự migrate:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("Default")));

var app = builder.Build();
```

Release theo expand/contract có thể chia thành:

```text
Release A — Expand
1. Build immutable application + migration artifacts.
2. Review/test generated migration SQL against production-like data.
3. Single migration runner adds DisplayName in a backward-compatible form.
4. Backfill DisplayName from FullName in bounded batches; monitor locks/log growth.
5. Deploy application version that can coexist with both columns.
6. Verify error rate, DB waits, data parity and application telemetry.

Release B — Transition
1. New application reads DisplayName.
2. During compatibility window, write strategy preserves required data for old/new versions.
3. Verify all production instances are on compatible version.
4. Stop legacy writes after evidence confirms no old consumer remains.

Release C — Contract
1. Verify FullName is no longer read/written.
2. Take required recovery point/backup according to operational policy.
3. Single controlled migration drops FullName.
4. Deploy/verify and monitor.
```

Một migration runner có thể là pipeline step, one-off Kubernetes Job hoặc deployment task; công cụ cụ thể ít quan trọng hơn việc chỉ có một controlled actor, identity/permissions riêng, artifact version rõ và failure handling rõ.

## Giải thích thiết kế sau khi sửa

Schema là shared contract. Expand/contract cho phép version cũ và mới coexist trong rolling window. Migration được tách khỏi serving process để replica scale không làm tăng số schema writers. Destructive change được trì hoãn cho tới khi telemetry và deployment state chứng minh legacy contract không còn được dùng.

## Trade-offs

Expand/contract cần nhiều release và temporary duplication nên chậm hơn một migration rename trực tiếp. Nếu hệ thống chấp nhận maintenance window, single-step migration có thể đơn giản hơn; nhưng phải nói rõ downtime, backup/recovery và rollback semantics. Dual-write cũng có consistency risk nên cần thời gian ngắn, test và reconciliation; không nên giữ vĩnh viễn chỉ vì “an toàn”.

## Cách kiểm thử

1. Migration integration test từ snapshot schema/data giống production: xác minh không mất `FullName` khi chuyển dữ liệu.
2. Compatibility test: old binary chạy với expanded schema và new binary chạy trong cùng schema window.
3. Rolling deployment test: giữ một old instance hoạt động trong khi new instances rollout; không có SQL schema errors.
4. Failure test migration dừng giữa backfill: rerun/recovery phải deterministic và không corrupt data.
5. Rollback drill: rollback application trước contract phase; sau destructive contract phase phải dùng documented recovery/forward-fix plan thay vì giả định `Down()` khôi phục dữ liệu.

## Quan sát trong production

Theo dõi migration duration/result, SQL blocking/waits, deadlocks, transaction log growth, DB CPU/IO, API 5xx, dependency failures, startup/readiness, version distribution giữa replicas và data-parity metrics trong transition. Correlate deployment version với Application Insights/Kibana telemetry. Migration logs không được chứa connection strings hoặc secrets.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận maintenance window thay vì expand/contract?
2. Nếu backfill 200 triệu rows mất nhiều giờ, bạn chia batch và kiểm soát lock/log growth thế nào?
3. Nếu release mới phải rollback sau khi đã bắt đầu ghi dữ liệu chỉ có schema mới hiểu, bạn thiết kế compatibility boundary ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authentication không thay thế resource-level authorization; multi-tenant isolation phải được enforce trên trusted tenant context và data access boundary.
- API DTO nên là allow-list cho mutable fields; persistence entity không nên mặc định là write contract.
- Optimistic concurrency bảo vệ lost update nhưng không thay thế authorization hoặc business-state validation.
- Database schema là shared contract giữa application versions trong rolling deployment.
- Migration production cần reasoning về data preservation, backward compatibility, single-writer execution, rollback/recovery và least privilege.

## Mẫu tư duy cần nhớ

- **Authenticated → authorized action → authorized resource → authorized fields.**
- **Client-controlled identifiers/fields không phải trust boundary.**
- **Shared schema: expand → migrate/backfill → transition → verify → contract.**
- **Rollback binary ≠ rollback dữ liệu.**
- **Deployment automation phải giảm concurrency ambiguity, không nhân nó theo số replica.**
