# Code Review Challenge 1 — MongoDB profile update “thành công” nhưng mất dữ liệu khi nhiều request cập nhật cùng lúc

**Chủ đề:** C#/.NET 8, ASP.NET Core, MongoDB, single-document atomicity, read-modify-replace race condition, document modeling, bounded history, optimistic concurrency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal employee platform chạy ASP.NET Core .NET 8. Thông tin profile của mỗi employee được lưu trong MongoDB. Team chọn document model vì phần lớn màn hình cần đọc profile cùng một số preferences trong một lần.

Document hiện có dạng rút gọn:

```json
{
  "_id": "emp-10482",
  "displayName": "An Nguyen",
  "phone": "+84...",
  "preferences": {
    "language": "vi",
    "timeZone": "Asia/Ho_Chi_Minh"
  },
  "changeHistory": [
    {
      "field": "phone",
      "changedAt": "2026-09-01T08:13:00Z",
      "changedBy": "emp-10482"
    }
  ],
  "version": 17,
  "updatedAt": "2026-09-01T08:13:00Z"
}
```

Production chạy nhiều application instances. Sau khi thêm mobile app và một background synchronization job, support bắt đầu thấy các hiện tượng khó tái hiện:

- user đổi `phone` trên web, gần như cùng lúc mobile app đổi `language`; sau đó một trong hai thay đổi biến mất;
- `version` đôi khi chỉ tăng một lần dù có hai request cùng báo `200 OK`;
- `changeHistory` ngày càng lớn với những employee lâu năm và response/profile update bắt đầu nặng hơn;
- background job chỉ muốn cập nhật `timeZone` nhưng đôi khi ghi đè `phone` mới hơn;
- team đề xuất bọc mọi update trong MongoDB transaction để “chắc chắn không mất dữ liệu”.

Business yêu cầu:

- các thay đổi độc lập trên cùng profile không được âm thầm làm mất nhau;
- nếu hai request thực sự cạnh tranh trên cùng một field, API phải có một policy rõ ràng thay vì last-write-wins ngẫu nhiên;
- audit history cần giữ lâu dài nhưng không bắt buộc phải nằm toàn bộ trong profile document;
- hệ thống ưu tiên thiết kế đơn giản, không dùng transaction nếu single-document operation đã giải quyết được vấn đề.

## Đoạn code cần review

```csharp
public sealed record UpdateProfileRequest(
    string? DisplayName,
    string? Phone,
    string? Language,
    string? TimeZone,
    long Version);

public sealed class EmployeeProfileService
{
    private readonly IMongoCollection<EmployeeProfile> _profiles;

    public EmployeeProfileService(
        IMongoDatabase database)
    {
        _profiles = database.GetCollection<EmployeeProfile>("employeeProfiles");
    }

    public async Task<EmployeeProfile?> UpdateAsync(
        string employeeId,
        UpdateProfileRequest request,
        string changedBy,
        CancellationToken cancellationToken)
    {
        var profile = await _profiles
            .Find(x => x.Id == employeeId)
            .FirstOrDefaultAsync(cancellationToken);

        if (profile is null)
            return null;

        if (request.DisplayName is not null)
            profile.DisplayName = request.DisplayName;

        if (request.Phone is not null)
            profile.Phone = request.Phone;

        if (request.Language is not null)
            profile.Preferences.Language = request.Language;

        if (request.TimeZone is not null)
            profile.Preferences.TimeZone = request.TimeZone;

        profile.Version++;
        profile.UpdatedAt = DateTimeOffset.UtcNow;

        profile.ChangeHistory.Add(new ProfileChange
        {
            Field = "profile",
            ChangedAt = DateTimeOffset.UtcNow,
            ChangedBy = changedBy
        });

        await _profiles.ReplaceOneAsync(
            x => x.Id == employeeId,
            profile,
            cancellationToken: cancellationToken);

        return profile;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các correctness problem trong read-modify-replace flow hiện tại.
2. Giải thích vì sao hai request đều có thể trả thành công nhưng một thay đổi vẫn bị mất.
3. Review việc truyền `Version` từ client nhưng không sử dụng nó trong write filter.
4. Đề xuất cách dùng MongoDB single-document atomic update và/hoặc optimistic concurrency phù hợp.
5. Review thiết kế `changeHistory` tăng không giới hạn trong profile document.
6. Giải thích khi nào transaction thực sự cần thiết và khi nào nó chỉ thêm complexity.
7. Đề xuất tests và production telemetry để chứng minh fix hoạt động dưới concurrency.

## Câu hỏi gợi mở

1. Atomicity của một `ReplaceOne` có đồng nghĩa toàn bộ chuỗi **read → mutate in memory → replace** là atomic không?
2. Nếu request A và B cùng đọc `version = 17`, điều gì xảy ra khi filter write chỉ dùng `_id`?
3. Nếu mỗi request chỉ thay đổi một field khác nhau, có cần replace toàn bộ document không?
4. `changeHistory` là dữ liệu truy cập cùng profile trong mọi request hay là một workload riêng có lifecycle khác?
5. Một transaction có tự động phát hiện business-level lost update nếu filter vẫn không kiểm tra expected version không?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **read-modify-write race** và replacement của toàn bộ snapshot cũ. Hãy tách atomicity của một database command khỏi atomicity của cả application workflow.

### Gợi ý 2

MongoDB có thể atomically cập nhật một document. Hãy nghĩ tới conditional filter trên expected state/version, `$set`, `$inc`, và việc chỉ update đúng fields thay vì replace toàn bộ document.

## Kết quả code review tham khảo

### Critical — Read-modify-replace gây lost update dưới concurrency

**Vấn đề:** Code đọc toàn bộ profile thành một snapshot, mutate trong memory rồi `ReplaceOneAsync` toàn bộ document bằng filter chỉ theo `Id`.

**Tại sao xảy ra:** Giả sử A và B cùng đọc document ở `version = 17`. A đổi `phone`, B đổi `language`. A replace document và ghi `version = 18`. B vẫn giữ snapshot cũ của `phone`, sau đó replace toàn bộ document bằng snapshot của B cũng có `version = 18`. Write B có thể ghi đè thay đổi `phone` của A dù B không chủ đích sửa field đó.

Một single-document write của MongoDB là atomic ở mức operation, nhưng sequence gồm **read rồi write sau đó** không tự trở thành một atomic compare-and-swap operation.

**Ảnh hưởng production:** Silent data loss. Đây là correctness bug nghiêm trọng vì cả hai client có thể nhận response thành công trong khi final state không chứa đầy đủ các thay đổi đã xác nhận.

**Cách sửa:** Không replace toàn bộ stale snapshot cho partial update. Dùng atomic update chỉ trên fields được request thay đổi. Khi conflict trên cùng logical version cần được phát hiện, đưa `Version` dự kiến vào filter và atomically `$inc` version.

### Critical — Client gửi `Version` nhưng server hoàn toàn không dùng để enforce concurrency

**Vấn đề:** `UpdateProfileRequest.Version` không xuất hiện trong query/filter update.

**Tại sao xảy ra:** Version đang chỉ là metadata trong contract chứ không phải concurrency precondition.

**Ảnh hưởng production:** Client có thể submit state dựa trên version cũ nhưng server vẫn trả success. UI không biết dữ liệu đã stale.

**Cách sửa:** Nếu API chọn optimistic concurrency, filter phải bao gồm cả identity và expected version, ví dụ `Id == employeeId && Version == request.Version`. Sau update, kiểm tra `ModifiedCount`/returned document. Nếu không match thì trả conflict/precondition failure theo API contract và cho client reload/review.

### High — `profile.Version++` không bảo vệ version khỏi concurrent writers

**Vấn đề:** Version được tăng trong memory từ snapshot đã đọc.

**Tại sao xảy ra:** Hai writers cùng đọc 17 thì cả hai đều tính 18. Replacement không có compare condition nên final version có thể là 18 dù đã có hai write attempts.

**Ảnh hưởng production:** Version không còn biểu diễn sequencing đáng tin cậy và không thể dùng để phát hiện stale client.

**Cách sửa:** Dùng server-side atomic increment (`$inc`) trong cùng update operation. Nếu cần strict optimistic concurrency thì kết hợp expected version trong filter.

### High — Full-document replacement mở rộng blast radius của mỗi update

**Vấn đề:** Một request chỉ muốn đổi `TimeZone` nhưng replacement vẫn gửi lại toàn bộ profile từ snapshot cũ.

**Tại sao xảy ra:** Implementation map PATCH-like semantics sang replace semantics.

**Ảnh hưởng production:** Các field không thuộc trách nhiệm của request cũng có thể bị rollback về giá trị cũ. Payload/network/write amplification cũng lớn hơn cần thiết.

**Cách sửa:** Build `UpdateDefinition<EmployeeProfile>` từ các fields thực sự được phép thay đổi. Điều này giảm vùng cạnh tranh và giúp independent field updates có thể cùng tồn tại nếu business cho phép.

### High — `changeHistory` tăng không giới hạn trong hot profile document

**Vấn đề:** Mọi update append một entry vào array nằm trong document được đọc/ghi thường xuyên.

**Tại sao xảy ra:** Audit lifecycle được gộp vào aggregate document dù access pattern khác nhau.

**Ảnh hưởng production:** Document ngày càng lớn, serialization/network/write cost tăng; write contention và storage overhead tăng theo tuổi profile. Ngoài ra MongoDB document có giới hạn kích thước hữu hạn nên unbounded array là một thiết kế cần tránh cho lịch sử dài hạn.

**Cách sửa:** Chỉ giữ một bounded recent-history nếu UI thật sự cần. Audit dài hạn nên nằm ở collection riêng, ví dụ `profileChanges`, với index theo `EmployeeId` + timestamp và retention/archival policy riêng. Nếu audit bắt buộc commit atomically cùng profile update thì lúc đó mới đánh giá transaction/mô hình dữ liệu phù hợp.

### High — Audit entry quá thô và có thể không phản ánh field thực sự thay đổi

**Vấn đề:** Mọi request ghi `Field = "profile"` dù có thể chỉ đổi `Language`, hoặc thậm chí request chứa giá trị giống hiện tại.

**Tại sao xảy ra:** Audit được append cơ học thay vì dựa trên mutation thực tế.

**Ảnh hưởng production:** Audit kém giá trị khi điều tra incident hoặc compliance; khó biết field nào đã đổi và từ version nào sang version nào.

**Cách sửa:** Ghi rõ changed fields, actor, timestamp và version/resulting version. Tránh log raw sensitive value nếu không cần thiết.

### Medium — Return object có thể không chắc chắn đại diện final persisted state

**Vấn đề:** Method trả object `profile` từ memory ngay sau replace.

**Tại sao xảy ra:** Dưới concurrent writes, một write khác có thể xảy ra sau operation này; ngoài ra object trả về không phản ánh server-side update nếu chuyển sang `$inc`/atomic operators mà không fetch updated document.

**Ảnh hưởng production:** Client có thể tin response là canonical latest state trong khi nó chỉ là state của write attempt đó.

**Cách sửa:** Nếu API cần trả updated state, dùng atomic find-and-update operation với return-document-after semantics hoặc thực hiện read có chủ đích sau write, đồng thời nói rõ consistency contract. Nếu chỉ cần acknowledgement/version, trả representation tối thiểu.

### Medium — Validation/authorization boundary chưa thể hiện rõ

**Vấn đề:** Service cho phép thay đổi nhiều fields chỉ dựa vào request input; snippet chưa chứng minh field-level authorization/validation.

**Tại sao xảy ra:** Partial-update contract thường dễ mở rộng thành mass-assignment nếu mapping quá generic.

**Ảnh hưởng production:** Một caller có thể thay đổi field ngoài quyền của mình hoặc lưu `language/timeZone/phone` không hợp lệ.

**Cách sửa:** Whitelist explicit fields, validate format/business rules, và enforce authorization trước update. Không biến request body trực tiếp thành generic Mongo update paths.

### Medium — Không phân biệt not-found với concurrency conflict trong write result

**Vấn đề:** Hiện implementation read trước rồi replace; khi chuyển sang conditional update, nếu không đọc/write result cẩn thận có thể trả cùng một response cho missing document và stale version.

**Tại sao xảy ra:** Identity existence và expected-version match là hai conditions khác nhau.

**Ảnh hưởng production:** Client không biết cần refresh vì conflict hay resource đã biến mất.

**Cách sửa:** Thiết kế API contract rõ ràng. Có thể dùng `FindOneAndUpdate` với filter version; nếu null, tùy requirement thực hiện lightweight existence check để phân biệt `404` và `409/412`, hoặc chấp nhận một semantic thống nhất nếu không muốn thêm round trip.

## Phiên bản đề xuất

Một hướng đơn giản là giữ profile trong một document, nhưng update bằng atomic field operators và optimistic concurrency.

```csharp
public sealed class EmployeeProfileService
{
    private readonly IMongoCollection<EmployeeProfile> _profiles;
    private readonly IMongoCollection<ProfileChangeDocument> _changes;

    public EmployeeProfileService(IMongoDatabase database)
    {
        _profiles = database.GetCollection<EmployeeProfile>("employeeProfiles");
        _changes = database.GetCollection<ProfileChangeDocument>("profileChanges");
    }

    public async Task<UpdateProfileResult> UpdateAsync(
        string employeeId,
        UpdateProfileRequest request,
        string changedBy,
        CancellationToken cancellationToken)
    {
        var updates = new List<UpdateDefinition<EmployeeProfile>>();
        var changedFields = new List<string>();

        if (request.DisplayName is not null)
        {
            updates.Add(Builders<EmployeeProfile>.Update
                .Set(x => x.DisplayName, request.DisplayName));
            changedFields.Add(nameof(EmployeeProfile.DisplayName));
        }

        if (request.Phone is not null)
        {
            updates.Add(Builders<EmployeeProfile>.Update
                .Set(x => x.Phone, request.Phone));
            changedFields.Add(nameof(EmployeeProfile.Phone));
        }

        if (request.Language is not null)
        {
            updates.Add(Builders<EmployeeProfile>.Update
                .Set(x => x.Preferences.Language, request.Language));
            changedFields.Add("Preferences.Language");
        }

        if (request.TimeZone is not null)
        {
            updates.Add(Builders<EmployeeProfile>.Update
                .Set(x => x.Preferences.TimeZone, request.TimeZone));
            changedFields.Add("Preferences.TimeZone");
        }

        if (updates.Count == 0)
            return UpdateProfileResult.NoChanges();

        var now = DateTimeOffset.UtcNow;

        updates.Add(Builders<EmployeeProfile>.Update
            .Set(x => x.UpdatedAt, now));
        updates.Add(Builders<EmployeeProfile>.Update
            .Inc(x => x.Version, 1));

        var filter = Builders<EmployeeProfile>.Filter.And(
            Builders<EmployeeProfile>.Filter.Eq(x => x.Id, employeeId),
            Builders<EmployeeProfile>.Filter.Eq(x => x.Version, request.Version));

        var updated = await _profiles.FindOneAndUpdateAsync(
            filter,
            Builders<EmployeeProfile>.Update.Combine(updates),
            new FindOneAndUpdateOptions<EmployeeProfile>
            {
                ReturnDocument = ReturnDocument.After
            },
            cancellationToken);

        if (updated is null)
            return UpdateProfileResult.NotUpdated();

        await _changes.InsertOneAsync(
            new ProfileChangeDocument
            {
                Id = ObjectId.GenerateNewId(),
                EmployeeId = employeeId,
                ChangedFields = changedFields,
                ChangedBy = changedBy,
                ChangedAt = now,
                ResultingVersion = updated.Version
            },
            cancellationToken: cancellationToken);

        return UpdateProfileResult.Success(updated);
    }
}
```

Điểm quan trọng không phải class/result names cụ thể mà là invariants:

1. write filter bao gồm expected version;
2. update chỉ chạm các fields request thực sự sở hữu;
3. version tăng atomically trong database;
4. write result quyết định success/conflict;
5. long-lived audit không làm profile document tăng vô hạn.

Theo behavior được MongoDB document chính thức mô tả, write trên một document là atomic ở mức operation và conditional filter có thể được dùng để tránh concurrent update áp dụng lên state không còn phù hợp. Vì vậy với profile nằm trong một document, không cần mặc định dùng multi-document transaction chỉ để thực hiện compare-and-update.

Nếu audit record trong collection riêng **bắt buộc** phải tồn tại atomically cùng profile update, lúc đó design cần quyết định rõ: dùng MongoDB transaction cho hai documents/collections, transactional outbox/audit pipeline, hoặc chấp nhận audit eventual consistency với retry. Không nên thêm transaction nếu business chỉ yêu cầu best-effort operational history.

Một nuance quan trọng: optimistic concurrency trên **toàn document version** sẽ làm hai updates ở hai fields khác nhau conflict dù về lý thuyết có thể merge an toàn. Đây là policy bảo thủ nhưng dễ hiểu. Nếu business muốn independent fields cùng cập nhật, có thể dùng targeted atomic updates không yêu cầu global version cho một số operations, hoặc version theo sub-resource. Phức tạp hơn chỉ đáng dùng khi evidence cho thấy conflict rate/UX cần nó.

## Giải thích thiết kế sau khi sửa

Thiết kế sửa không cố biến MongoDB thành relational transaction engine. Nó tận dụng đúng invariant mạnh sẵn có: atomic operation trên một document.

Nếu A và B cùng gửi expected version 17, chỉ write đầu tiên chuyển version 17 → 18 có thể match. Write còn lại không match version 17 và API có thể yêu cầu client reload. Không còn trường hợp cả hai cùng báo thành công nhưng silently overwrite nhau.

Nếu product muốn merge independent field changes thay vì conflict toàn profile, API có thể tách command theo field/sub-resource và chỉ update đúng path. Khi đó decision về concurrency phải được mô tả thành business rule, không để nó vô tình phụ thuộc timing.

Audit được tách vì access pattern khác profile. Profile là hot document phục vụ request path; audit là append/read-by-history workload. Tách lifecycle giúp document chính bounded và query/index riêng rõ hơn.

## Trade-offs

Global `Version` rất dễ reason và test nhưng có thể tạo false conflict: user đổi language và background job đổi timezone cùng lúc vẫn chỉ một write thắng. Nếu tần suất này cao và fields độc lập, field-level concurrency hoặc command-specific conditional filters có thể hợp lý hơn.

Tách audit sang collection riêng làm một update business có hai writes. Nếu yêu cầu audit strong atomicity, cần transaction hoặc một durable coordination mechanism; nếu không, có thể retry audit independently. Mỗi lựa chọn có cost vận hành khác nhau.

`FindOneAndUpdate` trả updated document tiện cho API nhưng tăng response/read cost so với chỉ `UpdateOne` + acknowledgement. Nếu caller chỉ cần version mới, contract có thể nhỏ hơn.

Không nên thêm distributed lock chỉ vì có nhiều app instances. Database conditional write/uniqueness thường là correctness boundary đơn giản và bền vững hơn in-memory coordination.

## Cách kiểm thử

1. **Concurrency integration test:** tạo profile version 17; chạy đồng thời hai requests cùng expected version 17 nhưng sửa hai field khác nhau. Với global optimistic concurrency, xác minh chỉ một write success, write còn lại nhận conflict và không overwrite winner.
2. **Lost-update regression test:** mô phỏng stale request chứa snapshot cũ; xác minh update chỉ chạm field được phép, không rollback các field khác.
3. **Atomic increment test:** chạy nhiều sequential successful writes và xác minh version tăng đúng một đơn vị mỗi accepted mutation.
4. **History growth test:** tạo hàng nghìn audit entries ở collection history; xác minh profile document không tăng theo số entries và profile read latency/payload vẫn bounded.
5. **Failure-path test:** làm audit insert thất bại sau profile update; xác minh behavior đúng với contract đã chọn: retry/eventual audit hoặc transaction rollback nếu strong atomicity thực sự được yêu cầu.

## Quan sát trong production

Theo dõi:

- update count theo field/use case;
- optimistic-concurrency conflict rate;
- p50/p95/p99 update latency;
- MongoDB command duration và error codes;
- document size distribution của profile;
- profile read/write payload size;
- audit insert failure/retry count;
- version gaps hoặc duplicate resulting-version trong audit nếu contract không cho phép;
- correlation ID gồm request ID, employee ID đã hash/chuẩn hóa phù hợp và resulting version;
- không log phone hoặc sensitive profile data nếu không cần thiết.

Alert nếu conflict rate tăng đột biến sau một release, document size tăng bất thường hoặc audit failure backlog vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product muốn hai request sửa hai fields độc lập đều thành công thay vì một request bị conflict bởi global version, bạn thay concurrency model như thế nào?
2. Nếu audit bắt buộc phải commit atomically cùng profile update vì compliance, bạn chọn transaction hay remodel document, và dựa trên access pattern nào?
3. Nếu background sync có authority thấp hơn user edit, bạn ngăn background job ghi đè user value bằng version hay bằng field-specific ownership/precondition?

## Bối cảnh

Một public product-catalog website dùng ASP.NET Core làm API + web host và React.js cho frontend. Đây không phải checkout system; mục tiêu chính là marketing/catalog discovery, vì vậy organic search có giá trị business lớn.

Các URL hợp lệ dạng:

`https://www.example.com/products/{slug}`

Website cũng nhận traffic qua các URL có tracking/query parameters, ví dụ:

`/products/road-bike?utm_source=newsletter&color=red`

Sau một đợt refactor SPA routing, team nhận thấy:

- Search Console báo nhiều duplicate URLs;
- một số product đã xóa vẫn trả HTTP `200` với màn hình React “Product not found”;
- canonical đôi lúc chứa `utm_source` hoặc `color` tùy URL user mở;
- bot không chạy JavaScript đầy đủ vẫn chỉ thấy shell HTML gần như trống;
- internal product links được render bằng `<div onClick>` nên không có `href` thật;
- metadata được update sau khi API call hoàn tất;
- team đề xuất chỉ thêm `<meta name="robots" content="noindex">` bằng JavaScript cho mọi trường hợp lỗi.

Business yêu cầu:

- một product public có một canonical URL ổn định;
- product không tồn tại phải có HTTP semantics đúng;
- internal links phải crawlable và usable bằng keyboard;
- không được tạo một SSR framework mới chỉ vì “SEO best practice” nếu ASP.NET Core hiện tại có thể giải quyết requirement đơn giản hơn;
- solution phải cân bằng SEO, frontend maintainability và performance.

```tsx
import { useEffect, useState } from 'react';

export function ProductPage() {
  const [product, setProduct] = useState<Product | null>(null);
  const [loading, setLoading] = useState(true);

  const slug = window.location.pathname.split('/').pop()!;

  useEffect(() => {
    fetch(`/api/products/${slug}`)
      .then(r => r.ok ? r.json() : null)
      .then(data => {
        setProduct(data);
        setLoading(false);

        document.title = data
          ? `${data.name} | Example`
          : 'Product not found | Example';

        let canonical = document.querySelector(
          'link[rel="canonical"]'
        ) as HTMLLinkElement | null;

        if (!canonical) {
          canonical = document.createElement('link');
          canonical.rel = 'canonical';
          document.head.appendChild(canonical);
        }

        canonical.href = window.location.href;
      });
  }, [slug]);

  if (loading)
    return <div>Loading...</div>;

  if (!product)
    return <h1>Product not found</h1>;

  return (
    <main>
      <h1>{product.name}</h1>

      <div
        className="related-product"
        onClick={() => window.location.href = `/products/${product.relatedSlug}`}
      >
        View related product
      </div>

      <img src={product.heroImageUrl} />

      <section>
        {product.description}
      </section>
    </main>
  );
}
```

## Câu hỏi gợi mở

1. Khi ASP.NET Core luôn gửi `200` + `index.html`, JavaScript có thể thay đổi HTTP status mà crawler đã nhận từ server hay không?

## Kết quả code review tham khảo

### Critical — Product không tồn tại vẫn trả HTTP 200

**Vấn đề:** ASP.NET Core catch-all route luôn trả `200` và `index.html`. React chỉ render text “Product not found”.

**Tại sao xảy ra:** HTTP status được quyết định ở server response; client-side rendering sau đó không biến response đã nhận thành một server-side `404`.

**Ảnh hưởng production:** Crawler có thể coi URL không tồn tại là soft 404 hoặc index tín hiệu không mong muốn. Monitoring cũng khó phân biệt product page thật với not-found page nếu mọi route đều `200`.

**Cách sửa:** Product route cần resolve existence đủ sớm để server trả `404`/`410` theo policy, hoặc có server-render/prerender boundary cho route SEO-critical. Không nên dùng SPA fallback `200` cho mọi product slug khi business coi HTTP semantics là requirement.

### High — Canonical lấy nguyên `window.location.href`

**Vấn đề:** URL canonical bao gồm `utm_source`, color/filter query hoặc các parameter không định nghĩa identity của product.

**Tại sao xảy ra:** Implementation dùng current navigation URL thay vì canonical URL được tính từ business identity.

**Ảnh hưởng production:** Cùng một product phát ra nhiều self-canonical variants, làm tín hiệu duplicate/normalization kém rõ ràng.

**Cách sửa:** Xây canonical từ origin chuẩn + canonical slug, loại các query parameters không thuộc content identity. Nếu slug có canonical normalization về lowercase/trailing slash, áp dụng nhất quán ở server và link generation.

### High — Canonical/title chỉ xuất hiện sau client-side fetch

**Vấn đề:** Metadata được tạo trong `useEffect` sau khi JavaScript chạy và API hoàn tất.

**Tại sao xảy ra:** Initial `index.html` gần như không chứa route-specific metadata.

**Ảnh hưởng production:** Crawler/link preview/tool không execute JavaScript hoặc render chậm có thể thấy generic title, thiếu canonical và thiếu content. Ngay cả crawler có rendering, metadata phụ thuộc network/API timing làm system khó predict hơn.

**Cách sửa:** Với public SEO-critical product routes, trả route-specific title/canonical và ideally meaningful product content trong initial HTML bằng server rendering hoặc targeted prerender/server template. Không nhất thiết phải đổi toàn bộ app sang framework SSR.

### High — SPA catch-all xóa distinction giữa valid route, redirect và missing route

**Vấn đề:** Tất cả `/products/*` đều map về cùng shell.

**Tại sao xảy ra:** Routing ở server không biết product canonical identity/existence.

**Ảnh hưởng production:** Slug cũ, typo và deleted product đều giống nhau ở transport layer. Không thể áp dụng redirect policy rõ ràng.

**Cách sửa:** Server route nên có contract với product catalog: active product → `200`, known old slug → permanent redirect phù hợp policy, deleted/missing → `404` hoặc `410` khi business có đủ certainty. Không dùng redirect mọi missing slug về homepage vì điều đó làm mất semantics.

### High — Internal navigation dùng `<div onClick>` thay vì link semantics

**Vấn đề:** Related product không có `<a href>`.

**Tại sao xảy ra:** Navigation bị implement như event handler UI thuần túy.

**Ảnh hưởng production:** Crawler khó discover link hơn; keyboard navigation, open-in-new-tab, copy link và accessibility semantics bị giảm.

**Cách sửa:** Render `<a href="/products/...">`. Client router có thể intercept click để SPA navigation nhanh hơn, nhưng DOM vẫn giữ real link semantics.

### Medium — Không xử lý fetch failure tách biệt với `404`

**Vấn đề:** `r.ok ? r.json() : null` gom mọi non-2xx thành “not found”; promise rejection/network failure cũng không có `.catch/.finally` thích hợp.

**Tại sao xảy ra:** Transport failure, authorization/server error và domain absence bị collapse thành một UI state.

**Ảnh hưởng production:** API `500` có thể hiển thị “Product not found”, làm che incident. Network failure có thể để loading state không kết thúc và metadata không được update.

**Cách sửa:** Phân biệt `404` với retryable/network/5xx errors. Trên route public server-rendered, status chính nên do server quyết định; client API vẫn cần error state rõ ràng cho hydration/navigation sau đó.

### Medium — Không có request cancellation/race protection khi slug đổi nhanh

**Vấn đề:** `fetch` không dùng `AbortController`.

**Tại sao xảy ra:** Nếu component tồn tại qua navigation và slug thay đổi nhanh, request cũ có thể resolve sau request mới rồi ghi state/metadata stale.

**Ảnh hưởng production:** UI/title/canonical có thể tạm thời phản ánh product trước đó; analytics và automated tests trở nên nondeterministic.

**Cách sửa:** Abort request cũ trong effect cleanup hoặc dùng data-loading layer có stale-request protection. Đây là correctness concern, nhưng không phải root cause của server-side HTTP semantics.

### Medium — Image thiếu accessibility và performance hints tối thiểu

**Vấn đề:** `<img>` không có `alt`, dimensions hoặc loading strategy rõ ràng.

**Tại sao xảy ra:** Image được coi chỉ là visual output.

**Ảnh hưởng production:** Accessibility kém; thiếu dimensions có thể góp phần layout shift. Hero image strategy không phù hợp có thể ảnh hưởng loading performance/Core Web Vitals.

**Cách sửa:** Cung cấp meaningful `alt`, width/height hoặc aspect-ratio reservation, và chọn eager/lazy/fetch priority theo vai trò ảnh. Hero/LCP image thường cần strategy khác thumbnail dưới fold. Đo bằng Lighthouse/RUM thay vì áp rule mù quáng.

### Medium — Canonical được mutate imperative ở nhiều navigation state

**Vấn đề:** Component tự tìm/tạo DOM node canonical.

**Tại sao xảy ra:** Metadata ownership không tập trung.

**Ảnh hưởng production:** Khi nhiều route/components cùng sửa `<head>`, stale metadata có thể survive navigation hoặc test khó dự đoán.

**Cách sửa:** Đặt metadata generation tại một boundary duy nhất. Nếu initial HTML do ASP.NET Core render, canonical/title chủ yếu được server sở hữu; client route transitions có thể dùng một head-management abstraction rõ ràng.

### Low — `window.location.pathname.split('/').pop()` là parsing route dễ vỡ

**Vấn đề:** Slug được parse thủ công từ global location.

**Tại sao xảy ra:** Component không nhận route parameter từ router contract.

**Ảnh hưởng production:** Trailing slash, encoded path hoặc route shape thay đổi có thể tạo slug sai.

**Cách sửa:** Lấy route parameter từ routing layer đã chuẩn hóa. Canonical slug nên đến từ product data/server contract, không chỉ từ raw requested path.

## Phiên bản đề xuất

Một solution tối thiểu không cần đổi toàn bộ stack là để ASP.NET Core chịu trách nhiệm cho **SEO-critical first response** của product route, còn React vẫn hydrate/handle interaction sau đó.

Ví dụ server route có thể resolve product summary và render một HTML template chứa status/metadata/content tối thiểu:

```csharp
app.MapGet("/products/{slug}", async (
    string slug,
    HttpContext context,
    IProductPageRepository products,
    CancellationToken cancellationToken) =>
{
    var result = await products.ResolveAsync(slug, cancellationToken);

    if (result.Kind == ProductResolutionKind.Redirect)
    {
        var target = $"/products/{result.CanonicalSlug}";
        return Results.Redirect(target, permanent: true);
    }

    if (result.Kind == ProductResolutionKind.NotFound)
        return Results.NotFound();

    var product = result.Product!;
    var canonicalUrl =
        $"https://www.example.com/products/{product.CanonicalSlug}";

    var html = await ProductHtmlRenderer.RenderAsync(new ProductHtmlModel
    {
        Title = $"{product.Name} | Example",
        CanonicalUrl = canonicalUrl,
        Name = product.Name,
        Description = product.Description,
        HeroImageUrl = product.HeroImageUrl,
        HeroImageAlt = product.HeroImageAlt,
        InitialStateJson = ProductInitialState.Serialize(product)
    });

    return Results.Content(
        html,
        "text/html; charset=utf-8",
        statusCode: StatusCodes.Status200OK);
});
```

export function ProductPage({ initialProduct }: Props) {

Nếu team chưa muốn hydrate SSR markup, một bước nhỏ hơn vẫn có giá trị: ASP.NET Core resolve route và trả đúng `status`, `title`, canonical/meta trong HTML template, rồi React mount cho interactive content. Nhưng cần đo xem initial content/crawlability requirement có được đáp ứng hay không.

Query parameters như `utm_source` hoặc UI-only filter không nên tự động trở thành canonical identity. Canonical URL phải được build từ canonical product slug theo rule ổn định.

Google documentation hiện hành nhấn mạnh việc dùng redirects/canonical signals nhất quán cho duplicate URLs và trả HTTP status phù hợp cho nội dung không tồn tại. Recommendation ở đây không dựa vào việc “Google luôn luôn không chạy JavaScript”; thay vào đó, system nên phát tín hiệu đúng ngay ở HTTP/initial HTML boundary để giảm phụ thuộc vào crawler rendering behavior.

## Giải thích thiết kế sau khi sửa

Điểm chính là ownership boundary:

- ASP.NET Core sở hữu requested URL resolution, HTTP status, redirect và initial SEO metadata;
- React sở hữu interaction phía client sau khi initial page đã có semantics đúng;
- product catalog/repository sở hữu canonical slug và existence state;
- link generation luôn dùng canonical route.

Cách này không đòi hỏi Microservices hay một SSR framework mới. Nếu public catalog chỉ có vài SEO-critical route types, targeted server rendering/template có thể rẻ hơn migration frontend lớn.

Nếu sau này số page types và frontend complexity tăng mạnh, team có thể đánh giá framework SSR/SSG như một engineering decision mới dựa trên build complexity, caching, deployment, developer experience và performance—not vì keyword “SEO”.

## Trade-offs

Server phải resolve product trước khi trả HTML, nên TTFB phụ thuộc catalog lookup/cache. Cần đo p95 và cân nhắc cache phù hợp. Nhưng trả shell ngay rồi fetch client-side cũng có cost: content xuất hiện muộn và metadata phụ thuộc JavaScript.

Targeted server template tạo duplicate rendering logic nếu React component và server markup phát triển độc lập. Có thể giảm bằng shared view model/schema và test contract; nếu duplication trở nên lớn, đó là evidence để cân nhắc SSR framework chứ chưa phải lý do ngay từ đầu.

Permanent redirect cho slug cũ chỉ đúng khi mapping thực sự ổn định. Nếu redirect chỉ tạm thời, status/policy phải khác. Product deletion cũng cần business decision giữa `404` và `410`; không nên mặc định `410` nếu hệ thống không chắc resource đã bị xóa vĩnh viễn.

Canonical không phải access control hoặc redirect. Nó là indexing signal; application vẫn cần normalize/redirect URLs khi UX và URL hygiene yêu cầu.

## Cách kiểm thử

1. **HTTP integration test:** request active product, missing product và old slug; xác minh status `200`, not-found status và redirect status/location đúng contract trước khi chạy JavaScript.
2. **HTML contract test:** parse initial response của product page; xác minh title, canonical, heading và primary product content tồn tại, canonical không chứa tracking parameters.
3. **Playwright E2E test:** navigate từ related product bằng keyboard và mouse; xác minh real anchor behavior, back/forward navigation và canonical/title sau client transition nếu app hỗ trợ SPA navigation.
4. **SEO regression test:** crawl một sample URL set gồm canonical, UTM variants, old slugs và missing slugs; phát hiện duplicate canonical, soft-404-like responses và redirect chains.
5. **Performance/accessibility test:** chạy Lighthouse/automated accessibility checks trên representative pages, đồng thời theo dõi LCP/CLS thay vì chỉ kiểm tra score một lần trong CI.

## Quan sát trong production

Theo dõi:

- HTTP status distribution cho `/products/*`;
- tỷ lệ `404`, redirect và redirect-chain depth;
- canonical URL mismatch giữa requested URL và generated canonical;
- count các product URLs có tracking parameter được crawler truy cập;
- server-side product resolution latency p50/p95/p99;
- API/catalog dependency latency/error rate;
- real-user LCP/CLS và page-load failure rate;
- Search Console/indexing signals theo thời gian;
- logs cho slug resolution với correlation ID, nhưng tránh log toàn bộ query string nếu có sensitive campaign/user parameters.

Alert khi tỷ lệ product-route `200` tăng bất thường cùng lúc catalog not-found tăng, hoặc khi canonical generation bắt đầu phát domain/path không hợp lệ sau release.

## Câu hỏi phỏng vấn mở rộng

1. Nếu catalog lookup làm TTFB tăng đáng kể, bạn chọn server cache, CDN cache hay client rendering, và metric nào quyết định?
2. Nếu cùng product có locale-specific content `/vi/products/...` và `/en/products/...`, canonical/hreflang ownership nên nằm ở layer nào?
3. Khi nào bạn sẽ chấp nhận migrate sang một SSR/SSG framework thay vì tiếp tục targeted rendering trong ASP.NET Core?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- MongoDB single-document write atomicity không biến một chuỗi application-level `read → modify → replace` thành atomic workflow; stale snapshot vẫn có thể gây lost update.
- Optimistic concurrency chỉ có tác dụng khi expected state/version thực sự nằm trong conditional write filter và kết quả write được kiểm tra.
- Partial update nên thay đổi đúng fields mà command sở hữu; full-document replacement làm tăng blast radius của stale data.
- Unbounded history trong hot document là dấu hiệu cần xem lại document boundary và access pattern, không phải mặc định thêm transaction.
- SEO engineering phụ thuộc vào HTTP status, redirects, canonical identity, crawlable links và initial document semantics; không thể sửa mọi vấn đề bằng DOM mutation sau `useEffect`.
- Architecture tốt không đồng nghĩa thêm framework. Một targeted server-rendering boundary có thể đáp ứng requirement với ít complexity hơn full-stack migration.

## Mẫu tư duy cần nhớ

- Phân biệt atomic database operation với atomic business workflow.
- Đưa concurrency precondition vào nơi database thực sự enforce nó.
- Thiết kế data model theo access pattern và growth lifecycle, không chỉ theo object shape.
- Đặt HTTP semantics ở server boundary; đừng kỳ vọng client-side UI sửa được response đã gửi.
- Chọn solution nhỏ nhất đáp ứng requirement, rồi đo evidence trước khi tăng complexity.
