# Code Review Challenge 1 — Middleware ghi log response làm tăng memory và vô tình ghi dữ liệu nhạy cảm

**Chủ đề:** C#/.NET, ASP.NET Core middleware, HTTP pipeline, memory allocation, logging, security, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ mobile app và web frontend. Team muốn ghi lại request/response để điều tra production incident nhanh hơn.

Hệ thống:

- chạy nhiều instance trên Azure App Service;
- có endpoint trả JSON nhỏ nhưng cũng có endpoint export dữ liệu từ vài MB đến hàng trăm MB;
- authentication dùng bearer token;
- một số response chứa email, phone number và dữ liệu tài khoản;
- production đang có các triệu chứng:
  - memory tăng mạnh khi export chạy đồng thời;
  - latency p95 tăng khi bật middleware logging;
  - một số response lỗi không còn body như trước;
  - Kibana xuất hiện access token và dữ liệu cá nhân;
  - request bị client hủy nhưng middleware đôi lúc vẫn tiếp tục đọc/copy dữ liệu.

Team hiện dùng middleware sau:

## Đoạn code cần review

```csharp
public sealed class RequestResponseLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestResponseLoggingMiddleware> _logger;

    public RequestResponseLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestResponseLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var requestReader = new StreamReader(
            context.Request.Body,
            Encoding.UTF8,
            detectEncodingFromByteOrderMarks: false,
            leaveOpen: true);

        var requestBody = await requestReader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        var originalBody = context.Response.Body;
        await using var responseBuffer = new MemoryStream();
        context.Response.Body = responseBuffer;

        await _next(context);

        responseBuffer.Position = 0;
        var responseBody = await new StreamReader(responseBuffer)
            .ReadToEndAsync();
        responseBuffer.Position = 0;

        _logger.LogInformation(
            "HTTP {Method} {Path} Authorization={Authorization} Request={RequestBody} Status={Status} Response={ResponseBody}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers.Authorization.ToString(),
            requestBody,
            context.Response.StatusCode,
            responseBody);

        await responseBuffer.CopyToAsync(originalBody);
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review middleware trên như một Senior .NET Developer phụ trách production API.

Bạn cần:

1. xác định correctness problems trong HTTP pipeline;
2. đánh giá memory/allocation impact;
3. đánh giá behavior với large body/streaming response;
4. xác định security/privacy risks;
5. đánh giá cancellation và exception path;
6. ưu tiên finding theo severity;
7. đề xuất implementation/design tốt hơn;
8. giải thích testing;
9. giải thích telemetry cần quan sát trong production.

Không mặc định rằng mọi request/response đều cần log full body.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu response là file export 300 MB?
2. Nếu `_next(context)` throw exception thì `context.Response.Body` được khôi phục ở đâu?
3. Có nên log `Authorization` header nguyên văn không?
4. Việc `EnableBuffering` và `ReadToEndAsync` ảnh hưởng request body lớn thế nào?
5. Middleware này có phù hợp với streaming endpoint hoặc Server-Sent Events không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **full buffering + sensitive logging + không bảo toàn response stream trong mọi execution path**.

### Gợi ý 2

Hãy nghĩ theo hướng **metadata-first observability**, redaction, size limit, sampling và chỉ capture body trong các trường hợp thực sự cần thiết.

## Kết quả code review tham khảo

### Critical — Ghi access token nguyên văn vào log

**Vấn đề:**  
`Authorization` header được ghi trực tiếp vào structured log.

**Tại sao xảy ra:**  
Middleware coi request metadata là dữ liệu an toàn để log mà không áp dụng redaction policy.

**Ảnh hưởng production:**  
Bearer token trong Kibana/Application Insights có thể bị người có quyền đọc log sử dụng lại trong thời gian token còn hiệu lực. Phạm vi truy cập log thường rộng hơn phạm vi truy cập secret store nên blast radius tăng đáng kể.

**Cách sửa:**  
Không log credential, token, cookie, API key hoặc secret. Nếu cần correlation với authentication, log các identifier đã được phép như authenticated subject/user ID sau authorization, không log raw credential.

---

### Critical — Full request/response body có thể chứa dữ liệu nhạy cảm

**Vấn đề:**  
Middleware ghi toàn bộ request và response vào log.

**Tại sao xảy ra:**  
Không có classification, allowlist, redaction hay route-specific policy.

**Ảnh hưởng production:**  
PII, dữ liệu tài khoản, password reset token, payment-related data hoặc nội dung business-sensitive có thể bị đưa vào logging backend và retention dài hạn.

**Cách sửa:**  
Mặc định không log body. Chỉ capture trên route/data type được approve, giới hạn kích thước, redact field nhạy cảm và có retention/access-control phù hợp.

---

### High — Response bị buffer toàn bộ trong memory

**Vấn đề:**  
Mọi response đều đi qua `MemoryStream` trước khi được gửi ra network.

**Tại sao xảy ra:**  
Middleware thay `context.Response.Body` bằng in-memory buffer để đọc lại nội dung.

**Ảnh hưởng production:**  
Large export và nhiều request đồng thời làm tăng allocation, LOH/Gen 2 pressure, GC pause và peak working set. API cũng mất khả năng stream dần dữ liệu tới client vì response chỉ được copy sau khi endpoint hoàn tất.

**Cách sửa:**  
Không full-buffer mặc định. Log metadata như status, duration, content length và trace ID. Nếu cần sample body, dùng giới hạn byte nhỏ và tee/capture có bounded buffer, đồng thời bypass streaming/file endpoints.

---

### High — Request body cũng bị đọc toàn bộ

**Vấn đề:**  
`ReadToEndAsync` đọc toàn bộ request body thành `string`.

**Tại sao xảy ra:**  
`EnableBuffering` chỉ cho phép đọc lại stream; nó không làm full-body logging trở thành rẻ hoặc an toàn.

**Ảnh hưởng production:**  
Upload hoặc payload lớn tạo memory pressure và tăng latency trước khi request tới controller. Có thể khiến request bị xử lý chậm dù business code rất nhanh.

**Cách sửa:**  
Chỉ đọc body khi route/content type/size đáp ứng explicit policy. Đặt maximum capture size và bỏ qua binary/multipart/large payload.

---

### High — Không khôi phục `Response.Body` bằng `finally`

**Vấn đề:**  
Nếu `_next(context)` throw, code không chạy tới bước copy và không reset `context.Response.Body`.

**Tại sao xảy ra:**  
Stream replacement không được bảo vệ bởi `try/finally`.

**Ảnh hưởng production:**  
Exception-handling middleware phía ngoài có thể ghi response vào stream tạm thay vì response thật, làm client nhận body rỗng hoặc behavior khó đoán tùy pipeline ordering.

**Cách sửa:**  
Nếu vẫn thay response stream, luôn restore stream gốc trong `finally`. Tốt hơn nữa là tránh thay stream cho các response không cần capture.

---

### High — Streaming semantics bị phá vỡ

**Vấn đề:**  
Client không nhận byte nào cho tới khi `_next` hoàn tất.

**Tại sao xảy ra:**  
Mọi dữ liệu được ghi vào `MemoryStream` nội bộ thay vì network response stream.

**Ảnh hưởng production:**  
File streaming, chunked response, SSE hoặc long-running output mất lợi ích streaming; time-to-first-byte tăng và memory usage tăng theo response size.

**Cách sửa:**  
Bypass body capture cho streaming endpoint hoặc dùng bounded tee stream khi thực sự cần sample một phần nhỏ mà vẫn forward dữ liệu ngay.

---

### Medium — Cancellation không được propagate rõ ràng

**Vấn đề:**  
Các thao tác đọc/copy không sử dụng `context.RequestAborted`.

**Tại sao xảy ra:**  
Code dùng overload không gắn request cancellation.

**Ảnh hưởng production:**  
Sau khi client disconnect, middleware có thể tiếp tục làm việc với payload lớn hoặc copy response không còn caller chờ.

**Cách sửa:**  
Dùng cancellation-aware APIs khi phù hợp và truyền `context.RequestAborted`. Đồng thời phân biệt operation nào cần hoàn tất để giữ consistency với operation chỉ phục vụ current request.

---

### Medium — Logging full success traffic tạo chi phí I/O và storage lớn

**Vấn đề:**  
Mọi request đều ghi log mức Information với body lớn.

**Tại sao xảy ra:**  
Không có sampling, route policy hoặc error-focused capture.

**Ảnh hưởng production:**  
Tăng CPU serialization, network tới log backend, ingestion cost và làm signal quan trọng bị chìm trong noise.

**Cách sửa:**  
Ưu tiên structured metadata; dùng sampling và conditional detail khi lỗi hoặc khi bật diagnostic window có kiểm soát.

---

### Medium — Không giới hạn log payload và không phân biệt content type

**Vấn đề:**  
Binary content cũng có thể bị cố đọc như text.

**Tại sao xảy ra:**  
Không kiểm tra `Content-Type`, `Content-Length` hay endpoint semantics.

**Ảnh hưởng production:**  
Log vô nghĩa, encoding issues, memory waste và có thể làm logging backend phình nhanh.

**Cách sửa:**  
Allowlist JSON/text nhỏ; denylist multipart, binary, file, compressed và streaming content.

## Phiên bản đề xuất

Ví dụ sau chọn hướng **metadata-first**. Body logging chỉ bật cho JSON nhỏ, có allowlist route và capture tối đa 4 KB. Token/cookie không bao giờ được log.

```csharp
public sealed class SafeHttpLoggingMiddleware
{
    private const int MaxCapturedChars = 4096;
    private readonly RequestDelegate _next;
    private readonly ILogger<SafeHttpLoggingMiddleware> _logger;

    public SafeHttpLoggingMiddleware(
        RequestDelegate next,
        ILogger<SafeHttpLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? error = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            error = ex;
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            _logger.Log(
                error is null ? LogLevel.Information : LogLevel.Error,
                error,
                "HTTP {Method} {Path} => {StatusCode} in {ElapsedMs} ms TraceId={TraceId} User={UserId}",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                context.TraceIdentifier,
                context.User.FindFirst("sub")?.Value);
        }
    }
}
```

Nếu business thực sự yêu cầu diagnostic body capture, nên xây riêng một bounded capture policy, ví dụ:

- chỉ route cụ thể;
- chỉ `application/json`;
- chỉ khi content length dưới ngưỡng;
- redact field theo schema;
- không capture auth/payment/upload endpoints;
- chỉ giữ prefix giới hạn thay vì toàn bộ body;
- bật theo feature flag có audit;
- có sampling và retention ngắn.

## Giải thích thiết kế sau khi sửa

### 1. Observability không đồng nghĩa full payload logging

Phần lớn incident có thể điều tra từ method, route, status, duration, trace/correlation ID, dependency telemetry và user/resource ID phù hợp.

### 2. Body capture phải là exception, không phải default

Body có chi phí memory, privacy và compliance lớn. Chỉ nên bật khi giá trị diagnostic vượt chi phí và risk.

### 3. Streaming endpoint giữ nguyên streaming semantics

Middleware không thay response stream, do đó file/SSE có thể gửi dữ liệu dần ra client.

### 4. Secret redaction là invariant

Credential không được phép đi vào log dù diagnostic mode bật.

## Trade-offs

- Không log full body khiến một số incident thiếu dữ liệu tức thời; đổi lại giảm đáng kể memory, privacy và ingestion risk.
- Sampling có thể bỏ lỡ request hiếm; cần kết hợp trace ID, metrics và targeted diagnostic mode.
- Bounded body capture phức tạp hơn simple middleware vì phải hiểu content type, encoding và redaction.
- Diagnostic feature flag cần access control và audit để tránh trở thành backdoor thu thập dữ liệu.

## Cách kiểm thử

1. **Security test:** gửi bearer token và PII; log không được chứa raw token hoặc field nhạy cảm.
2. **Load test:** chạy nhiều response lớn đồng thời; so sánh working set, allocation rate, GC và p95/p99 khi middleware bật/tắt.
3. **Streaming test:** endpoint stream file phải bắt đầu gửi dữ liệu trước khi toàn bộ content được tạo xong.
4. **Exception-path test:** endpoint throw; error middleware vẫn trả response đúng và response stream không bị hỏng.
5. **Cancellation test:** client abort giữa request; server không tiếp tục unnecessary capture/copy kéo dài.

## Quan sát trong production

Theo dõi:

- request rate, p95/p99 latency;
- process memory, GC heap, allocation rate, Gen 2 collections;
- response size distribution;
- log event size và ingestion volume;
- exception rate;
- client-aborted request count;
- time-to-first-byte với streaming/export endpoints;
- sampling/body-capture activation count;
- automated scan/redaction alerts cho token, cookie hoặc known sensitive fields trong log.

## Câu hỏi phỏng vấn mở rộng

1. Nếu security team yêu cầu audit một số request body, bạn sẽ thiết kế redaction và access control thế nào?
2. Khi nào dùng ASP.NET Core built-in HTTP logging thay vì custom middleware, và vẫn cần policy gì quanh sensitive data?
3. Nếu cần capture 2 KB đầu response mà không phá streaming, bạn sẽ thiết kế bounded tee stream ra sao?

# Code Review Challenge 2 — Cosmos DB partition key tạo hot partition và query fan-out dưới tải

**Chủ đề:** Cosmos DB, document modeling, partition key, RU consumption, query patterns, consistency, application scalability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một attendance platform lưu check-in events vào Cosmos DB.

Business behavior:

- mỗi employee có thể check-in/check-out vài lần mỗi ngày;
- dashboard quản lý thường query theo `companyId` + khoảng thời gian;
- employee app thường query lịch sử gần nhất của chính employee;
- vài customer enterprise có hơn 100.000 employees;
- traffic cao nhất tập trung vào 8:00–9:00 và 17:00–18:00;
- hệ thống có nhiều application instance;
- production đang thấy:
  - RU consumption tăng mạnh vào giờ cao điểm;
  - một số request bị throttled dù tổng data size chưa lớn;
  - dashboard query chậm hơn nhiều ở customer lớn;
  - một số operation update event phải gửi thêm request chỉ để tìm document;
  - team định tăng RU toàn container nhưng chưa có bằng chứng rõ đó là bottleneck duy nhất.

Data model và repository hiện tại:

## Đoạn code cần review

```csharp
public sealed class AttendanceEvent
{
    public string Id { get; set; } = default!;
    public string CompanyId { get; set; } = default!;
    public string EmployeeId { get; set; } = default!;
    public string Type { get; set; } = default!;
    public DateTime TimestampUtc { get; set; }
    public string PartitionKey { get; set; } = "attendance";
}

public sealed class AttendanceRepository
{
    private readonly Container _container;

    public AttendanceRepository(Container container)
    {
        _container = container;
    }

    public Task CreateAsync(
        AttendanceEvent item,
        CancellationToken cancellationToken)
    {
        return _container.CreateItemAsync(
            item,
            new PartitionKey(item.PartitionKey),
            cancellationToken: cancellationToken);
    }

    public async Task<IReadOnlyList<AttendanceEvent>> GetCompanyEventsAsync(
        string companyId,
        DateTime fromUtc,
        DateTime toUtc,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.CompanyId = @companyId " +
            "AND c.TimestampUtc >= @fromUtc AND c.TimestampUtc < @toUtc")
            .WithParameter("@companyId", companyId)
            .WithParameter("@fromUtc", fromUtc)
            .WithParameter("@toUtc", toUtc);

        var iterator = _container.GetItemQueryIterator<AttendanceEvent>(query);
        var results = new List<AttendanceEvent>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            results.AddRange(page);
        }

        return results;
    }

    public async Task ReplaceAsync(
        AttendanceEvent item,
        CancellationToken cancellationToken)
    {
        await _container.ReplaceItemAsync(
            item,
            item.Id,
            new PartitionKey(item.PartitionKey),
            cancellationToken: cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review design trên như một Senior Developer/Architect đang xử lý Cosmos DB performance incident.

Bạn cần:

1. phân tích partition-key choice;
2. giải thích hot partition và query fan-out risk;
3. đánh giá query pattern hiện tại;
4. đánh giá data model theo access patterns;
5. phân tích point read/update requirements;
6. đánh giá consistency và concurrency concerns nếu event có thể bị chỉnh sửa;
7. đề xuất cách đo trước khi tăng throughput;
8. đề xuất migration/design tốt hơn;
9. giải thích testing và production telemetry.

Không mặc định rằng một partition key mới là đúng chỉ vì nó tạo nhiều partition hơn. Thiết kế phải dựa trên access pattern và cardinality/distribution thực tế.

## Câu hỏi gợi mở

1. Mọi document dùng cùng `PartitionKey = "attendance"` nghĩa là gì về distribution?
2. Dashboard query theo `companyId` có được route tới một logical partition cụ thể không?
3. Nếu partition key thay đổi, `ReplaceItemAsync` cần biết điều gì?
4. `SELECT *` và việc đọc toàn bộ time range ảnh hưởng RU/network thế nào?
5. Trước khi tăng RU, bạn cần xem metric nào để biết đang bị hot partition, inefficient query hay cả hai?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **partition key có cardinality bằng 1**, khiến toàn bộ workload tập trung vào cùng logical partition.

### Gợi ý 2

Hãy bắt đầu từ access pattern: employee history, company dashboard, write distribution, point read/update và retention. Một partition strategy tốt phải cân bằng **distribution + query locality + partition growth**.

## Kết quả code review tham khảo

### Critical — Partition key có cardinality bằng 1

**Vấn đề:**  
Mọi item đều dùng `PartitionKey = "attendance"`.

**Tại sao xảy ra:**  
Developer tạo property partition key nhưng không chọn một business dimension có cardinality/distribution phù hợp.

**Ảnh hưởng production:**  
Toàn bộ writes và nhiều reads tập trung vào một logical partition. Khi traffic burst vào giờ check-in/check-out, workload dễ chạm giới hạn của partition đó dù tổng throughput container còn dư ở nơi khác.

**Cách sửa:**  
Thiết kế partition key dựa trên access patterns và distribution thực tế. Candidate cần cân nhắc các lựa chọn như `companyId`, `employeeId`, hoặc hierarchical/composite strategy nếu platform/version/configuration đang dùng hỗ trợ và requirement phù hợp. Không chọn chỉ theo một rule chung.

---

### High — Query theo `companyId` không có partition routing với key hiện tại

**Vấn đề:**  
Repository không truyền partition key cho query và partition key hiện tại cũng không liên quan tới `companyId`.

**Tại sao xảy ra:**  
Storage partitioning không align với primary query dimension.

**Ảnh hưởng production:**  
Query có thể phải scan/fan-out rộng hơn cần thiết khi dữ liệu phân bố qua physical partitions trong design tương lai, hoặc hiện tại vẫn phải đọc lượng dữ liệu lớn trong một hot logical partition. Cả hai đều không tốt.

**Cách sửa:**  
Align query locality với partitioning strategy. Nếu dashboard theo company là dominant high-volume access pattern, `companyId` là candidate cần benchmark. Nếu một company quá lớn gây skew, cần partitioning scheme sâu hơn theo time bucket/employee hoặc mô hình read projection riêng.

---

### High — Không giới hạn result set và đọc toàn bộ time range vào memory

**Vấn đề:**  
Method gom tất cả pages vào `List` rồi trả toàn bộ.

**Tại sao xảy ra:**  
API repository không có pagination/continuation contract.

**Ảnh hưởng production:**  
Customer lớn + time range rộng gây RU cao, network lớn, memory pressure và latency dài. Caller cũng không thể consume page-by-page.

**Cách sửa:**  
Dùng continuation token/pagination ở API boundary, giới hạn maximum time window hoặc page size hợp lý và chỉ select field thực sự cần.

---

### High — `SELECT *` làm tăng dữ liệu đọc/truyền không cần thiết

**Vấn đề:**  
Dashboard có thể chỉ cần subset field nhưng query materialize cả document.

**Tại sao xảy ra:**  
Repository expose entity trực tiếp thay vì projection theo use case.

**Ảnh hưởng production:**  
Tăng payload, deserialization và RU/network cost tùy kích thước document.

**Cách sửa:**  
Projection các field cần cho dashboard, ví dụ event ID, employee ID, type và timestamp.

---

### High — Data model chưa thể hiện strategy cho company cực lớn

**Vấn đề:**  
Ngay cả khi đổi sang `companyId`, enterprise tenant rất lớn có thể vẫn tạo logical partition nóng hoặc tăng trưởng lớn theo thời gian.

**Tại sao xảy ra:**  
Partition design chưa xem xét skew và time growth.

**Ảnh hưởng production:**  
Một vài tenant lớn có thể chi phối throughput và latency toàn workload.

**Cách sửa:**  
Đo distribution theo tenant, writes/sec và query range. Có thể cần bucket theo time, employee hoặc read-optimized projection tùy access pattern. Đừng áp dụng một partition key duy nhất mà không benchmark tenant lớn nhất.

---

### Medium — Update yêu cầu đúng item ID và partition key nhưng model cho phép partition key như field mutable

**Vấn đề:**  
`PartitionKey` nằm trong entity như property business-normal và có thể bị thay đổi nhầm.

**Tại sao xảy ra:**  
Storage identity và business model bị trộn lẫn.

**Ảnh hưởng production:**  
Code update có thể truyền partition key không khớp với item hiện có, khiến operation fail và team phải query trước chỉ để tìm partition location.

**Cách sửa:**  
Partition key phải được derivable ổn định từ immutable business identity/access pattern. Repository contract nên yêu cầu key rõ ràng và tránh flow “query để tìm item rồi mới point update” nếu có thể.

---

### Medium — Chưa có concurrency strategy cho chỉnh sửa event

**Vấn đề:**  
`ReplaceAsync` ghi đè mà không thể hiện optimistic concurrency policy.

**Tại sao xảy ra:**  
Nếu hai actor cùng chỉnh một event, last writer có thể thắng mà không phát hiện conflict.

**Ảnh hưởng production:**  
Correction từ manager có thể ghi đè thay đổi khác mà không audit rõ.

**Cách sửa:**  
Nếu business yêu cầu conflict detection, dùng ETag/conditional write và audit/version semantics phù hợp. Nếu attendance event là immutable, thiết kế append/correction event có thể tốt hơn replace trực tiếp.

---

### Medium — Chưa đo RU theo operation trước khi scale throughput

**Vấn đề:**  
Team muốn tăng RU toàn container nhưng chưa phân loại expensive operation.

**Tại sao xảy ra:**  
Thiếu request-charge telemetry theo query/use case.

**Ảnh hưởng production:**  
Có thể tăng cost nhưng hot key/query inefficiency vẫn còn. Scaling throughput không sửa data model sai.

**Cách sửa:**  
Collect request charge, throttling rate, latency, partition-key distribution, query metrics và hot partition indicators trước khi chọn scale-up hay redesign.

## Phiên bản đề xuất

Không có một partition key duy nhất chắc chắn đúng từ scenario. Ví dụ dưới đây giả định benchmark cho thấy:

- phần lớn dashboard query theo company + ngày;
- customer lớn nhất đủ lớn để `companyId` đơn lẻ có nguy cơ skew;
- employee history thường query trong khoảng thời gian gần;
- event phần lớn immutable sau khi ghi.

Một phương án là đưa time bucket vào storage key và expose pagination rõ ràng:

```csharp
public sealed class AttendanceEvent
{
    public string Id { get; init; } = default!;
    public string CompanyId { get; init; } = default!;
    public string EmployeeId { get; init; } = default!;
    public string CompanyDayKey { get; init; } = default!;
    public string Type { get; init; } = default!;
    public DateTime TimestampUtc { get; init; }
    public string? ETag { get; set; }
}

public sealed record AttendancePage(
    IReadOnlyList<AttendanceSummary> Items,
    string? ContinuationToken);

public async Task<AttendancePage> GetCompanyDayAsync(
    string companyId,
    DateOnly day,
    string? continuationToken,
    CancellationToken cancellationToken)
{
    var companyDayKey = $"{companyId}:{day:yyyyMMdd}";

    var query = new QueryDefinition(
        "SELECT c.id, c.EmployeeId, c.Type, c.TimestampUtc " +
        "FROM c WHERE c.CompanyDayKey = @key " +
        "ORDER BY c.TimestampUtc")
        .WithParameter("@key", companyDayKey);

    var options = new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(companyDayKey),
        MaxItemCount = 100
    };

    using var iterator = _container.GetItemQueryIterator<AttendanceSummary>(
        query,
        continuationToken,
        options);

    var page = await iterator.ReadNextAsync(cancellationToken);

    return new AttendancePage(
        page.Resource.ToList(),
        page.ContinuationToken);
}
```

Đây chỉ là **scenario recommendation**, không phải universal best practice. Nếu dominant access pattern là employee history xuyên nhiều ngày, strategy trên tạo fan-out theo day bucket cho employee query. Khi đó có thể cần:

- một partition strategy khác;
- duplicated read model/projection;
- hoặc một container riêng cho use case dashboard vs employee history nếu business value biện minh cho complexity.

## Giải thích thiết kế sau khi sửa

### 1. Partitioning bắt đầu từ access pattern

Không chọn key chỉ để tăng cardinality. Cần biết query nào cần locality, tenant nào skew, write burst ở đâu và partition sẽ tăng lớn đến mức nào.

### 2. Time bucket giúp giới hạn growth nhưng tạo trade-off fan-out

Bucket theo ngày có thể phân phối load tốt hơn cho tenant rất lớn và phù hợp dashboard theo ngày, nhưng query nhiều ngày phải đọc nhiều partition key.

### 3. Pagination là phần của API contract

Continuation token tránh materialize hàng chục nghìn document vào memory và giúp caller kiểm soát latency/payload.

### 4. Point operation cần stable key

Storage identity nên derivable từ dữ liệu immutable để tránh query chỉ nhằm tìm partition key.

## Trade-offs

- `companyId` đơn giản và query locality tốt, nhưng tenant cực lớn có thể hot/skew.
- `employeeId` phân phối tốt hơn theo user nhưng company dashboard có thể fan-out mạnh.
- `companyId + day` giới hạn partition growth và burst theo ngày, nhưng multi-day/employee queries phức tạp hơn.
- Duplicated read projection tối ưu nhiều access pattern nhưng tăng consistency/operational complexity.
- Tăng provisioned throughput có thể hợp lý nếu workload thực sự cần capacity; nhưng không nên dùng để che partition/query design kém.

## Cách kiểm thử

1. **Load test:** mô phỏng giờ cao điểm với tenant nhỏ và tenant enterprise; đo throttling, request charge và latency theo partition-key distribution.
2. **Query-cost test:** so sánh RU và latency giữa current model và candidate partition strategies trên dataset đại diện.
3. **Pagination test:** query customer lớn với continuation token; memory của API không tăng tuyến tính theo toàn result set.
4. **Concurrency test:** hai update dùng cùng ETag; conflict phải được phát hiện nếu business yêu cầu optimistic concurrency.
5. **Skew test:** tạo một tenant chiếm phần lớn traffic; xác minh partition strategy không biến tenant đó thành bottleneck không thể scale hợp lý.

## Quan sát trong production

Theo dõi:

- request charge theo operation/query type;
- throttled requests và retry rate;
- p50/p95/p99 latency;
- throughput theo partition-key range/logical key dimension;
- top tenants/keys theo request volume;
- query page count và continuation usage;
- result count và payload size;
- SDK retry duration;
- dashboard vs employee-history RU breakdown;
- item size distribution;
- alert khi một key/tenant chiếm tỷ lệ throughput bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu 95% query là employee history và chỉ 5% là manager dashboard, bạn có còn chọn company-oriented partition key không?
2. Nếu business yêu cầu dashboard xuyên 90 ngày cho tenant 100.000 employees, bạn sẽ cân nhắc read model nào để tránh query operational events trực tiếp?
3. Khi nào tăng throughput là giải pháp đúng thay vì đổi partition/data model?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- ASP.NET Core middleware nằm trong critical request pipeline; full request/response buffering có thể biến một tính năng observability thành bottleneck production.
- Credentials và sensitive payload không được phép đi vào logs theo default policy.
- Streaming response, cancellation và exception path phải được bảo toàn khi middleware can thiệp vào request/response body.
- Với Cosmos DB, partition key quyết định cả distribution lẫn query locality; cardinality thấp hoặc skew lớn có thể tạo hot partition.
- Query optimization không chỉ là thêm throughput: cần đo request charge, throttling, result size, continuation behavior và access-pattern alignment.
- Storage design tốt phải xuất phát từ workload thực tế, không từ một partition-key recipe cố định.

## Mẫu tư duy cần nhớ

1. **Observe with metadata first; capture payload only by explicit policy.**
2. **Never trade production secrets for easier debugging.**
3. **Preserve streaming and cancellation semantics in cross-cutting middleware.**
4. **Choose partition keys from access patterns, cardinality and skew.**
5. **Measure request cost and hot spots before scaling throughput.**
