# Code Review Challenge 1 — Export file lớn giữ toàn bộ dữ liệu trong memory và bỏ qua cancellation

**Chủ đề:** C#/.NET, ASP.NET Core, streaming, memory/GC, IAsyncDisposable, CancellationToken, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép người dùng export lịch sử giao dịch thành CSV. Với khách hàng lớn, kết quả có thể đạt vài trăm nghìn dòng. Production chạy nhiều instances và có lúc nhiều export đồng thời. Sau khi tính năng được mở rộng, team thấy working set tăng mạnh, Gen 2 GC tăng, một số request vẫn tiếp tục chạy sau khi client đóng kết nối và database connection bị giữ lâu.

Requirement hiện tại chỉ cần CSV được tải trực tiếp; không yêu cầu lưu file lâu dài. Nếu export quá lớn hoặc cần resumable download, team có thể cân nhắc background job/Blob Storage sau, nhưng chưa có bằng chứng cần thêm complexity đó ngay.

## Đoạn code cần review

```csharp
[HttpGet("customers/{customerId}/transactions/export")]
public async Task<IActionResult> Export(
    Guid customerId,
    CancellationToken cancellationToken)
{
    var rows = await _db.Transactions
        .Where(x => x.CustomerId == customerId)
        .OrderBy(x => x.CreatedAtUtc)
        .ToListAsync();

    var stream = new MemoryStream();
    var writer = new StreamWriter(stream, Encoding.UTF8);

    await writer.WriteLineAsync("Id,CreatedAt,Amount,Description");

    foreach (var row in rows)
    {
        await writer.WriteLineAsync(
            $"{row.Id},{row.CreatedAtUtc:o},{row.Amount},{row.Description}");
    }

    await writer.FlushAsync();
    stream.Position = 0;

    return File(stream, "text/csv", "transactions.csv");
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/resource-lifetime issues.
2. Phân tích memory/allocation behavior dưới nhiều export đồng thời.
3. Xác định cancellation propagation còn thiếu ở đâu và production impact.
4. Review CSV correctness/security concerns đối với dữ liệu text.
5. Đề xuất implementation đơn giản hơn theo hướng streaming nếu phù hợp.
6. Nêu tests cho large result, client disconnect, database failure và special characters.
7. Nêu telemetry để chứng minh bottleneck nằm ở memory, database hay network.

## Câu hỏi gợi mở

1. `ToListAsync()` và `MemoryStream` khiến cùng dataset tồn tại trong memory theo những representation nào?
2. Cancellation token hiện có thực sự đi tới database và write operations không?
3. Ai sở hữu lifetime của `StreamWriter` và `MemoryStream`?
4. CSV field chứa dấu phẩy, quote hoặc newline sẽ ra sao?
5. Nếu client disconnect sau 10% response, server nên tiếp tục export không?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **buffering toàn bộ pipeline** và resource/cancellation semantics.

### Gợi ý 2

Xem xét liệu dữ liệu có thể được đọc và ghi dần thay vì materialize toàn bộ trước khi response bắt đầu.

## Kết quả code review tham khảo

### High — Dataset được materialize toàn bộ trước khi gửi response

**Vấn đề:** `ToListAsync()` tải toàn bộ rows vào memory rồi code lại tạo toàn bộ CSV trong `MemoryStream`.

**Tại sao xảy ra:** Pipeline có hai lớp buffering lớn thay vì producer-consumer streaming.

**Ảnh hưởng production:** Working set/allocation tăng theo số rows và số export concurrent; GC pressure và latency của các request khác có thể tăng.

**Cách sửa:** Project đúng fields và enumerate asynchronously; ghi dần ra response stream khi business/API contract cho phép.

### High — Cancellation không được truyền tới database query

**Vấn đề:** `ToListAsync()` không nhận `cancellationToken` dù action đã có token.

**Tại sao xảy ra:** Token bị bỏ tại dependency boundary.

**Ảnh hưởng production:** Query có thể tiếp tục dùng DB/network/CPU sau khi request bị hủy.

**Cách sửa:** Truyền token vào EF Core async operation và các write/flush operation hỗ trợ cancellation.

### High — Client disconnect không dừng toàn bộ pipeline một cách có chủ đích

**Vấn đề:** Code không thiết kế quanh request-abort cancellation trong quá trình tạo output.

**Tại sao xảy ra:** Toàn bộ file được dựng trước response nên cancellation ở network layer tới quá muộn.

**Ảnh hưởng production:** Expensive work tiếp tục dù consumer không còn nhận dữ liệu.

**Cách sửa:** Streaming response và propagate request cancellation xuyên query/enumeration/write path; xử lý `OperationCanceledException` theo semantics request abort thay vì log như server error.

### High — CSV escaping không đúng

**Vấn đề:** Interpolation ghi trực tiếp `Description` và các fields khác.

**Tại sao xảy ra:** CSV có quoting/escaping rules cho comma, quote, CR/LF.

**Ảnh hưởng production:** File bị lệch cột hoặc dữ liệu bị diễn giải sai; nếu file mở bằng spreadsheet, dữ liệu do user kiểm soát bắt đầu bằng formula marker còn có thể cần policy riêng về CSV injection.

**Cách sửa:** Dùng CSV serializer/library phù hợp hoặc escaping function được test kỹ; xác định spreadsheet-safety requirement thay vì tự chế format mơ hồ.

### Medium — Resource ownership/disposal không rõ

**Vấn đề:** `StreamWriter` và `MemoryStream` không được dispose trong method; đồng thời dispose writer quá sớm có thể đóng underlying stream nếu không cấu hình `leaveOpen`.

**Tại sao xảy ra:** Lifetime của stream được chuyển cho MVC response nhưng writer ownership không được thể hiện rõ.

**Ảnh hưởng production:** Resource lifetime khó reasoning và dễ tạo bug khi code thay đổi.

**Cách sửa:** Tốt hơn là tránh intermediate stream. Nếu vẫn dùng stream, quản lý `using/await using` và ownership rõ ràng.

### Medium — Query lấy entity đầy đủ và tracking không cần thiết

**Vấn đề:** Export chỉ cần vài fields nhưng query materialize entity; mặc định tracking có thể thêm memory overhead nếu context/query không được cấu hình khác.

**Tại sao xảy ra:** Không projection theo read model.

**Ảnh hưởng production:** Thêm allocation/change-tracker overhead trên dataset lớn.

**Cách sửa:** `AsNoTracking()` và `Select` đúng fields; đo generated SQL/query plan trước khi tối ưu sâu hơn.

### Medium — Response bắt đầu muộn

**Vấn đề:** User phải chờ database query + toàn bộ CSV generation hoàn tất trước byte đầu tiên.

**Tại sao xảy ra:** Full buffering.

**Ảnh hưởng production:** Time-to-first-byte cao và timeout risk tăng.

**Cách sửa:** Stream khi phù hợp, đồng thời xác định timeout/export-size policy.

### Low — File naming/content metadata quá tĩnh

**Vấn đề:** Tất cả exports dùng cùng tên và chưa thể hiện encoding/content-disposition policy rõ.

**Tại sao xảy ra:** Happy-path implementation.

**Ảnh hưởng production:** Chủ yếu usability/interop, không phải root cause incident.

**Cách sửa:** Đặt filename an toàn/có ngữ cảnh và test client compatibility.

## Phiên bản đề xuất

Một hướng đơn giản là ghi trực tiếp vào response, projection dữ liệu và enumerate bất đồng bộ:

```csharp
[HttpGet("customers/{customerId}/transactions/export")]
public async Task Export(
    Guid customerId,
    CancellationToken cancellationToken)
{
    Response.ContentType = "text/csv; charset=utf-8";
    Response.Headers.ContentDisposition =
        "attachment; filename=transactions.csv";

    await using var writer = new StreamWriter(
        Response.Body,
        new UTF8Encoding(encoderShouldEmitUTF8Identifier: false),
        bufferSize: 16 * 1024,
        leaveOpen: true);

    await writer.WriteLineAsync("Id,CreatedAt,Amount,Description".AsMemory(), cancellationToken);

    var query = _db.Transactions
        .AsNoTracking()
        .Where(x => x.CustomerId == customerId)
        .OrderBy(x => x.CreatedAtUtc)
        .Select(x => new
        {
            x.Id,
            x.CreatedAtUtc,
            x.Amount,
            x.Description
        })
        .AsAsyncEnumerable();

    await foreach (var row in query.WithCancellation(cancellationToken))
    {
        var line = Csv.Format(
            row.Id,
            row.CreatedAtUtc,
            row.Amount,
            row.Description);

        await writer.WriteLineAsync(line.AsMemory(), cancellationToken);
    }

    await writer.FlushAsync(cancellationToken);
}
```

`Csv.Format` ở đây đại diện cho implementation/library có escaping được kiểm thử; không nên hiểu là API framework có sẵn. Authorization cho `customerId` cũng phải được enforce ở layer phù hợp nhưng scenario này tập trung vào streaming/resource behavior.

## Giải thích thiết kế sau khi sửa

Pipeline mới không giữ toàn bộ result và toàn bộ output cùng lúc. Projection giảm dữ liệu được materialize; `AsNoTracking` phù hợp với read-only export. `WithCancellation` và write cancellation giúp request abort lan xuống work đang diễn ra.

Streaming không miễn phí: database reader/connection có thể sống lâu theo tốc độ client. Nếu client rất chậm hoặc exports kéo dài hàng phút, cần đo connection occupancy và cân nhắc batch/keyset hoặc chuyển sang asynchronous export + Blob Storage. Chỉ thêm background architecture khi workload/SLO thực sự yêu cầu.

## Trade-offs

- Streaming giảm peak memory nhưng có thể giữ DB connection lâu hơn.
- Response đã bắt đầu thì khó trả một structured HTTP error nếu failure xảy ra giữa stream.
- Batching có thể giải phóng DB resources giữa các chunk nhưng tăng query complexity và cần stable ordering/keyset semantics.
- Background export + Blob hỗ trợ rất lớn/resumable workload nhưng thêm persistence, cleanup, status API, authorization và operational complexity.

## Cách kiểm thử

1. **Load test:** nhiều exports lớn đồng thời; đo working set, allocation rate, GC pause và p95/p99.
2. **Cancellation test:** disconnect client giữa export; xác minh query/write dừng và connection được trả về pool.
3. **Database failure test:** dependency fail giữa stream; xác minh telemetry và resource cleanup.
4. **CSV correctness test:** comma, quote, CR/LF, Unicode và spreadsheet-sensitive values theo policy.
5. **Integration test:** dataset lớn được xuất đúng thứ tự và không thiếu/trùng rows.

## Quan sát trong production

Theo dõi request duration, time-to-first-byte, bytes sent, active exports, cancellations, SQL dependency duration, connection-pool pressure, process working set, allocation rate và GC. Correlate bằng request/trace ID trong Application Insights. Nếu p99 tăng, phân biệt database read time, serialization/write time và client/network backpressure trước khi đổi architecture.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển từ direct streaming sang background export + Blob Storage?
2. Nếu client tải rất chậm, direct streaming ảnh hưởng database connection pool thế nào và bạn giảm rủi ro ra sao?
3. Nếu cần snapshot consistency trong suốt export dài, transaction/isolation decision sẽ thay đổi thế nào?

# Code Review Challenge 2 — Playwright E2E pass local nhưng flaky khi CI chạy parallel

**Chủ đề:** Playwright, TypeScript, E2E testing, test isolation, parallel execution, deterministic test data, CI observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một portal nội bộ dùng React frontend và ASP.NET Core API. Team có Playwright suite chạy trên CI với 6 workers. Local thường pass khi chạy tuần tự; CI thỉnh thoảng fail ở test chỉnh sửa profile hoặc approval workflow. Team đã tăng retry lên 3 và thêm `waitForTimeout`, khiến pipeline lâu hơn nhưng flakiness vẫn còn.

Các tests dùng chung một account seeded `qa-user@example.test` và cùng một approval record. CI giữ trace chỉ khi test fail cuối cùng.

## Đoạn code cần review

```typescript
import { test, expect } from '@playwright/test';

const userEmail = 'qa-user@example.test';

test.describe('profile and approval', () => {
  test('updates display name', async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', userEmail);
    await page.fill('#password', process.env.E2E_PASSWORD!);
    await page.click('button[type=submit]');

    await page.goto('/profile');
    await page.fill('#displayName', 'Automation User');
    await page.click('button:has-text("Save")');

    await page.waitForTimeout(2000);
    await expect(page.locator('.toast')).toContainText('Saved');
  });

  test('approves pending request', async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', userEmail);
    await page.fill('#password', process.env.E2E_PASSWORD!);
    await page.click('button[type=submit]');

    await page.goto('/approvals/1001');
    await page.click('button:has-text("Approve")');
    await page.waitForTimeout(1500);

    await expect(page.locator('.status')).toHaveText('Approved');
  });

  test('profile starts with seeded name', async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', userEmail);
    await page.fill('#password', process.env.E2E_PASSWORD!);
    await page.click('button[type=submit]');

    await page.goto('/profile');
    await expect(page.locator('#displayName')).toHaveValue('QA User');
  });
});
```

## Nhiệm vụ của ứng viên

1. Xác định các nguồn nondeterminism và shared mutable state.
2. Phân tích tại sao parallel workers làm suite fail dù từng test pass riêng.
3. Review synchronization strategy và selector quality.
4. Đánh giá retry: khi nào retry hữu ích và khi nào chỉ che bug.
5. Đề xuất test-data/isolation design tốt hơn.
6. Nêu cách test suite chính nó dưới parallel/repeat execution.
7. Đề xuất artifacts/telemetry giúp RCA flaky tests.

## Câu hỏi gợi mở

1. Ba tests có thực sự độc lập nếu chúng dùng cùng user và cùng mutable state không?
2. `waitForTimeout(2000)` đang chờ điều kiện gì?
3. Nếu approval `1001` đã được worker khác approve, test thứ hai sẽ thấy gì?
4. Retry một test destructive có thể làm trạng thái backend thay đổi thế nào?
5. Bạn cần dữ liệu gì trong trace để phân biệt frontend race, API failure và test-data collision?

### Gợi ý 1

Rủi ro chính là **test isolation**, không phải thiếu sleep.

### Gợi ý 2

Playwright auto-wait có thể chờ UI condition, nhưng nó không thể tự sửa shared backend state giữa parallel workers.

## Kết quả code review tham khảo

### High — Tests chia sẻ mutable user state

**Vấn đề:** Test update display name và test kỳ vọng seeded name dùng cùng account.

**Tại sao xảy ra:** Test order không phải dependency contract; parallel execution có thể interleave mutations.

**Ảnh hưởng production:** CI fail không ổn định theo timing; retry có thể pass ngẫu nhiên và che coupling.

**Cách sửa:** Mỗi test/worker có isolated user hoặc deterministic reset fixture/API. Không phụ thuộc test khác chạy trước/sau.

### High — Shared approval record là single-use mutable fixture

**Vấn đề:** Approval `1001` có thể chỉ được approve một lần nhưng nhiều runs/workers dùng chung.

**Tại sao xảy ra:** Test data không scoped theo test execution.

**Ảnh hưởng production:** Một worker làm thay đổi precondition của worker khác; rerun/retry cũng có thể tự phá precondition.

**Cách sửa:** Provision approval riêng với unique ID cho mỗi test, hoặc reset state qua supported test fixture mechanism.

### High — Fixed sleeps không đồng bộ với system condition

**Vấn đề:** `waitForTimeout` giả định backend/UI hoàn thành trong một số milliseconds cố định.

**Tại sao xảy ra:** Timing thay đổi theo CI load/network/dependency latency.

**Ảnh hưởng production:** Sleep quá ngắn gây flaky; quá dài làm pipeline chậm mà vẫn không bảo đảm correctness.

**Cách sửa:** Chờ observable condition: response cụ thể, UI state hoặc locator assertion có auto-wait phù hợp.

### Medium — Retry có thể che deterministic shared-state bug

**Vấn đề:** Retry 3 lần được dùng như mitigation chung.

**Tại sao xảy ra:** Team chưa phân loại flake do infrastructure/transient issue với test-design bug.

**Ảnh hưởng production:** Pipeline chậm, false confidence và state bị mutate thêm qua mỗi attempt.

**Cách sửa:** Giữ retry policy nhỏ/có chủ đích; RCA từ trace/artifacts và sửa isolation. Theo dõi first-attempt pass rate riêng với final pass rate.

### Medium — Login bị lặp và tạo thêm dependency/noise

**Vấn đề:** Mỗi test đi qua UI login dù mục tiêu chính không phải authentication.

**Tại sao xảy ra:** Setup không tái sử dụng authenticated state/fixture phù hợp.

**Ảnh hưởng production:** Tăng runtime và thêm failure surface không liên quan.

**Cách sửa:** Nếu authentication không phải subject under test, dùng fixture/storage state được tạo an toàn theo test strategy; vẫn giữ dedicated auth E2E tests riêng.

### Medium — Selectors gắn vào implementation/text dễ thay đổi

**Vấn đề:** CSS IDs và text selector được dùng không nhất quán với semantic/test contract.

**Tại sao xảy ra:** Test không có locator strategy ổn định.

**Ảnh hưởng production:** UI refactor nhỏ gây test noise.

**Cách sửa:** Ưu tiên role/label/test-id khi phù hợp và coi selector contract là một phần testability design.

### Medium — Thiếu assertion về network/business outcome

**Vấn đề:** Toast/status UI là signal cuối nhưng khi fail khó biết API request có gửi, status code gì hay backend state ra sao.

**Tại sao xảy ra:** Test chỉ quan sát DOM cuối cùng.

**Ảnh hưởng production:** RCA chậm; frontend/backend failures bị trộn.

**Cách sửa:** Với flow quan trọng, kết hợp UI assertion với targeted network wait/response evidence hoặc API verification, tránh over-couple test với mọi internal call.

## Phiên bản đề xuất

Ví dụ dùng fixture tạo dữ liệu riêng qua test-support API. Endpoint dưới đây là giả định của test environment, không phải API có sẵn của Playwright:

```typescript
import { test, expect } from '@playwright/test';

test('updates display name', async ({ page, request }) => {
  const fixture = await createIsolatedUser(request, test.info().testId);

  await login(page, fixture.email, fixture.password);
  await page.goto('/profile');

  await page.getByLabel('Display name').fill('Automation User');

  const saveResponse = page.waitForResponse(r =>
    r.url().includes('/api/profile') && r.request().method() === 'PUT');

  await page.getByRole('button', { name: 'Save' }).click();
  expect((await saveResponse).ok()).toBeTruthy();
  await expect(page.getByRole('status')).toContainText('Saved');
});

test('approves pending request', async ({ page, request }) => {
  const fixture = await createApprovalFixture(request, test.info().testId);

  await login(page, fixture.approverEmail, fixture.password);
  await page.goto(`/approvals/${fixture.approvalId}`);

  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByTestId('approval-status')).toHaveText('Approved');

  const state = await request.get(`/test-support/approvals/${fixture.approvalId}`);
  expect((await state.json()).status).toBe('Approved');
});
```

`createIsolatedUser`, `createApprovalFixture` và `/test-support/...` là application-specific test infrastructure phải được bảo vệ/chỉ tồn tại ở test environment. Một lựa chọn khác là database fixture provisioning hoặc worker-scoped accounts; quyết định dựa trên isolation, speed và security constraints.

## Giải thích thiết kế sau khi sửa

Mỗi test sở hữu precondition riêng nên parallelism không thay đổi correctness. Test chờ business-observable conditions thay vì elapsed time. UI login có thể được tối ưu bằng authenticated fixture nếu login không phải subject của test.

Test-support API giúp setup nhanh và deterministic nhưng phải được tách khỏi production exposure. Nếu setup qua public UI để giống user hoàn toàn, realism tăng nhưng suite chậm và dễ tạo cascading failures hơn.

## Trade-offs

- Per-test provisioning tăng setup/cleanup cost.
- Worker-scoped fixtures nhanh hơn nhưng cần tránh state leakage giữa tests trong cùng worker.
- Test-support API tăng maintainability burden và phải được security-gated.
- Network assertions tăng diagnostic value nhưng over-specifying internal requests có thể làm tests brittle.
- Retry vẫn hữu ích cho một số transient infrastructure failures, nhưng không thay thế deterministic isolation.

## Cách kiểm thử

1. Chạy suite với `--workers=6` lặp nhiều lần; theo dõi first-attempt pass rate.
2. Randomize/order-independent execution; mỗi test phải pass độc lập.
3. Cố tình tăng backend latency; assertions dựa trên condition vẫn pass trong timeout hợp lý mà không dùng sleep.
4. Chạy retries và xác minh fixture provisioning tạo state mới hoặc retry-safe state.
5. Failure injection cho API 500/timeout; trace phải đủ để xác định request, response và UI state.

## Quan sát trong production

Đối với CI, lưu trace/video/screenshot/network artifacts theo policy phù hợp, ít nhất cho first failure để không mất evidence sau retry. Theo dõi flake rate, first-attempt pass rate, retry recovery rate, duration theo test và worker. Correlate test run ID với backend structured logs/Application Insights ở test environment để phân biệt frontend timing, API error, data collision và infrastructure issue.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn worker-scoped fixture thay vì per-test fixture?
2. Retry bao nhiêu là hợp lý và metric nào cho biết retry đang che chất lượng test kém?
3. Làm sao thiết kế test-support endpoints mà không tạo security backdoor vào production?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 nhấn mạnh rằng large-data HTTP path phải được reasoning theo toàn bộ resource pipeline: database materialization, allocations, GC, stream ownership, cancellation và network backpressure. Streaming có thể giảm memory nhưng đổi lại connection/resource lifetime cần được đo và quản lý.

Challenge 2 tập trung vào deterministic E2E engineering. Parallel execution không tạo ra flakiness từ hư không; nó thường làm lộ shared mutable state, hidden ordering dependency và synchronization dựa trên thời gian thay vì condition.

## Mẫu tư duy cần nhớ

- Tránh **buffer everything** khi workload có kích thước lớn và có thể stream.
- Propagate cancellation xuyên mọi expensive dependency boundary.
- Test chạy parallel phải sở hữu hoặc reset mutable state một cách deterministic.
- Chờ **observable condition**, không chờ một số milliseconds tùy ý.
- Dùng telemetry để phân biệt application bug, dependency latency và test/infrastructure failure.
