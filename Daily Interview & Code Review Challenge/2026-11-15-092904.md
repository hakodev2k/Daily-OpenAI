# Code Review Challenge 1 — Azure Service Bus retry làm hoàn tiền hai lần

## Bối cảnh

```csharp
public sealed class RefundConsumer
{
    private readonly AppDbContext _db;
    private readonly HttpClient _http;
    private readonly ILogger<RefundConsumer> _log;

    public RefundConsumer(AppDbContext db, HttpClient http,
        ILogger<RefundConsumer> log)
    {
        _db = db;
        _http = http;
        _log = log;
    }

    public async Task Handle(
        ServiceBusReceivedMessage message,
        ServiceBusMessageActions actions,
        CancellationToken ct)
    {
        var evt = JsonSerializer.Deserialize<RefundApproved>(
            message.Body.ToString())!;

        var existing = await _db.Refunds
            .FirstOrDefaultAsync(x => x.OrderId == evt.OrderId, ct);

        if (existing?.Status == "Completed")
        {
            await actions.CompleteMessageAsync(message, ct);
            return;
        }

        var refund = existing ?? new Refund
        {
            Id = Guid.NewGuid(),
            OrderId = evt.OrderId,
            Amount = evt.Amount,
            Status = "Processing"
        };
        if (existing is null) _db.Refunds.Add(refund);
        await _db.SaveChangesAsync(ct);

        var response = await _http.PostAsJsonAsync(
            "/refunds", new { evt.PaymentId, evt.Amount }, ct);
        response.EnsureSuccessStatusCode();

        refund.Status = "Completed";
        refund.ProviderReference =
            await response.Content.ReadAsStringAsync(ct);
        await _db.SaveChangesAsync(ct);
        _log.LogInformation("Refund completed for {OrderId}", evt.OrderId);
        await actions.CompleteMessageAsync(message, ct);
    }
}

public sealed record RefundApproved(
    Guid OrderId, string PaymentId, decimal Amount);
```

## Kết quả code review tham khảo

### [Critical] — Provider call không có idempotency key

**Vấn đề:** Retry gửi một yêu cầu hoàn tiền mới.  
**Tại sao xảy ra:** Timeout không chứng minh provider chưa thực hiện giao dịch; HTTP và DB không atomic.  
**Ảnh hưởng production:** Hoàn tiền trùng, thất thoát tài chính.  
**Cách sửa:** Gắn một operation ID bền vững vào provider idempotency key, lưu và tra cứu provider reference; với kết quả không rõ phải reconcile trước khi gửi lại, nhất là khi key hết hạn.

### [Critical] — Race condition khi kiểm tra rồi insert

**Vấn đề:** Hai worker đều có thể thấy chưa có row.  
**Tại sao xảy ra:** `FirstOrDefaultAsync` không phải distributed lock hoặc uniqueness guarantee.  
**Ảnh hưởng production:** Hai operation cạnh tranh và hai HTTP call.  
**Cách sửa:** Unique index theo refund operation ID, atomic claim/lease với concurrency token hoặc conditional update; chỉ một owner được phép gửi.

### [High] — Dùng OrderId làm identity của refund

**Vấn đề:** Gộp các partial refund hợp lệ hoặc các event khác nhau của cùng order.  
**Tại sao xảy ra:** Business identity không được định nghĩa.  
**Ảnh hưởng production:** Bỏ sót refund hoặc hoàn sai số tiền.  
**Cách sửa:** Yêu cầu `RefundRequestId` ổn định từ upstream; kiểm tra amount/currency/payment ID khi duplicate.

### [High] — Crash window giữa provider và database

**Vấn đề:** Provider thành công nhưng DB chưa lưu `Completed`.  
**Tại sao xảy ra:** External side effect không thuộc DB transaction.  
**Ảnh hưởng production:** Trạng thái sai và retry nguy hiểm.  
**Cách sửa:** State machine `Pending → InFlight → Succeeded/Unknown/Failed`, reconciliation theo operation ID, outbox cho intent gửi.

### [High] — Không xử lý lock expiry và concurrent redelivery

**Vấn đề:** Worker khác có thể xử lý cùng message khi lock hết hạn.  
**Tại sao xảy ra:** Message settlement và provider latency không đồng bộ.  
**Ảnh hưởng production:** Concurrent side effects.  
**Cách sửa:** Cấu hình lock renewal phù hợp, giới hạn concurrency, dùng DB ownership và provider idempotency; lock renewal chỉ là hỗ trợ, không phải correctness guarantee.

### [High] — Không phân loại lỗi provider

**Vấn đề:** Mọi non-2xx đều ném exception.  
**Tại sao xảy ra:** Không tách permanent rejection, throttling, timeout và ambiguous result.  
**Ảnh hưởng production:** Retry vô ích, poison message, nguy cơ trùng.  
**Cách sửa:** Phân loại response, retry có backoff/jitter theo policy, DLQ và manual investigation; tuyệt đối không retry mù trường hợp ambiguous.

### [Medium] — Thiếu validation event và authorization boundary

**Vấn đề:** Deserialize dùng null-forgiving và tin amount/payment ID.  
**Tại sao xảy ra:** Thiếu schema, currency, amount, source verification và mapping tới giao dịch gốc.  
**Ảnh hưởng production:** Poison message hoặc sai số tiền.  
**Cách sửa:** Validate schema/version, amount, currency, payment identity và quyền của event producer.

### [Medium] — Thiếu cancellation/telemetry có ngữ cảnh

**Vấn đề:** Không có trace ID, operation ID, retry count hoặc provider latency.  
**Tại sao xảy ra:** Logging chỉ khi hoàn tất.  
**Ảnh hưởng production:** Không thể xác minh double refund hoặc điều tra unknown outcome.  
**Cách sửa:** Structured logs, distributed tracing, metrics theo trạng thái; không log secrets hoặc PII.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa **application service** sau khi đã có unique constraint trên `RefundRequestId`, một `IRefundStore` hỗ trợ atomic claim và một `IProviderGateway` có lookup theo operation key. Các interface là contract đề xuất, không phải API có sẵn của .NET. Consumer Service Bus chỉ validate/enqueue intent và settle sau khi intent được persist; dispatcher riêng xử lý intent.

```csharp
public sealed class RefundDispatcher
{
    private readonly IRefundStore _store;
    private readonly IProviderGateway _provider;

    public RefundDispatcher(IRefundStore store, IProviderGateway provider)
    {
        _store = store;
        _provider = provider;
    }

    public async Task Dispatch(Guid requestId, CancellationToken ct)
    {
        var lease = await _store.TryClaimAsync(requestId, ct);
        if (lease is null) return;

        try
        {
            var known = await _provider.LookupAsync(
                lease.OperationKey, ct);

            if (known is { Succeeded: true })
            {
                await _store.MarkSucceededAsync(
                    lease, known.Reference, ct);
                return;
            }

            if (known is null && lease.PreviousAttemptWasAmbiguous)
            {
                await _store.MarkUnknownAsync(lease, ct);
                return;
            }

            var result = await _provider.RefundAsync(
                lease.PaymentId, lease.Amount, lease.Currency,
                lease.OperationKey, ct);

            await _store.MarkSucceededAsync(
                lease, result.Reference, ct);
        }
        catch (ProviderOutcomeUnknownException)
        {
            await _store.MarkUnknownAsync(lease, ct);
        }
        catch (ProviderPermanentException ex)
        {
            await _store.MarkFailedAsync(lease, ex.Code, ct);
        }
        finally
        {
            await _store.ReleaseLeaseIfOwnedAsync(lease, ct);
        }
    }
}
```

`TryClaimAsync` phải là atomic conditional update có lease token/fencing và expiry; `MarkSucceededAsync` chỉ chấp nhận đúng token. `LookupAsync` phải có semantics đã xác nhận với provider. Nếu provider không hỗ trợ lookup đáng tin, trạng thái `Unknown` phải được đưa vào quy trình đối soát thủ công trước retry. Một unique index trên business operation ID và outbox record được commit cùng intent là điều kiện triển khai, không được suy ra từ snippet.

## Giải thích thiết kế sau khi sửa

DB bảo vệ identity và ownership; provider idempotency giảm rủi ro duplicate side effect; outbox bảo đảm intent không biến mất khi worker crash; reconciliation xử lý khoảng không chắc chắn giữa hai hệ thống. Không có exactly-once end-to-end chỉ nhờ queue settlement.

## Trade-offs

State machine, lease và reconciliation tăng độ phức tạp vận hành, schema và latency. Với volume nhỏ vẫn có thể dùng một database-backed worker thay vì microservices, nhưng không được bỏ uniqueness và ambiguous-outcome handling. Provider có thời hạn idempotency ngắn đòi hỏi retention/reconciliation policy nghiêm ngặt.

```csharp
{

    private readonly ISearchAdmin _search;
    private readonly ILogger<CatalogReindexJob> _log;

    public CatalogReindexJob(CatalogDbContext db,
        ISearchAdmin search, ILogger<CatalogReindexJob> log)

        _search = search;
        _log = log;

    public async Task Run(CancellationToken ct)
    {
        var index = "products-v2";
        await _search.CreateIndexAsync(index, ct);

        var offset = 0;
        const int size = 500;
        while (true)
        {
            var products = await _db.Products
                .OrderBy(x => x.Id)
                .Skip(offset)
                .Take(size)

                    Name = x.Name,
                    Price = x.Price,
                    UpdatedAt = x.UpdatedAt

                .ToListAsync(ct);

            if (products.Count == 0) break;
            await _search.BulkIndexAsync(index, products, ct);
            offset += products.Count;
            _log.LogInformation("Indexed {Offset} products", offset);
        }

        await _search.SetAliasAsync("products", index, ct);
        await _search.DeleteIndexAsync("products-v1", ct);
    }
}
```

## Phiên bản đề xuất

Đây là pseudocode C# ở mức orchestration; các interface `IChangeFeed`, `IIndexWriter` và `IReindexState` là abstraction thiết kế, không phải SDK có sẵn. Cần bảo đảm outbox/CDC ghi thay đổi đồng bộ với DB transaction và có monotonic sequence.

```csharp
public sealed class CatalogRebuilder
{
    private readonly ICatalogReader _catalog;
    private readonly IChangeFeed _changes;
    private readonly IIndexWriter _index;
    private readonly IReindexState _state;

    public CatalogRebuilder(ICatalogReader catalog,
        IChangeFeed changes, IIndexWriter index,
        IReindexState state)
    {
        _catalog = catalog;
        _changes = changes;
        _index = index;
        _state = state;
    }

    public async Task RebuildAsync(string runId, CancellationToken ct)
    {
        await using var lease = await _state.AcquireLeaseAsync(runId, ct);
        var target = await _index.CreateVersionedIndexAsync(runId, ct);
        var cursor = await _changes.CaptureCursorAsync(ct);
        var lastId = 0L;

        while (true)
        {
            var batch = await _catalog.ReadAfterIdAsync(lastId, 500, ct);
            if (batch.Count == 0) break;
            await _index.BulkUpsertCheckedAsync(target, batch, ct);
            lastId = batch[^1].Id;
            await _state.SaveCheckpointAsync(runId, lastId, ct);
        }

        await _changes.ReplayToAsync(target, cursor, ct);
        await _index.ValidateAsync(target, ct);
        await _changes.EnterCutoverBarrierAsync(ct);
        try
        {
            await _changes.DrainThroughBarrierAsync(target, ct);
            await _index.AtomicSwapAliasAsync("products", target, ct);
        }
        finally
        {
            await _changes.ExitCutoverBarrierAsync(ct);
        }
    }
}
```

Giả định `EnterCutoverBarrierAsync` phối hợp với write pipeline để ngăn change event vượt qua cutover chưa được áp dụng; nó không được chỉ là lock cục bộ trong process. Nếu không thể đặt barrier mà không ảnh hưởng ghi, chọn dual-write có version fencing và quy trình chứng minh lag/consistency trước cutover; không tuyên bố zero-loss chỉ từ `ReplayToAsync`. `BulkUpsertCheckedAsync` phải hỗ trợ delete tombstones, version ordering, retries và item-level failures. Khi resume phải dùng checkpoint cùng target index và source cursor đã lưu, không tạo index khác rồi dùng checkpoint cũ.

## Giải thích thiết kế sau khi sửa

Backfill xử lý dữ liệu nền; change feed lấp khoảng thay đổi trong khi scan; versioned writes chống event cũ ghi đè mới; alias swap atomic chuyển search traffic; checkpoint và lease hỗ trợ restart. PostgreSQL vẫn là source of truth.

## Trade-offs

CDC/outbox, watermark và cutover coordination tăng chi phí vận hành và schema. Với catalog nhỏ có maintenance window, có thể chọn tạm ngừng ghi ngắn hạn và backfill đơn giản hơn. Keyset cải thiện chi phí scan nhưng không tự giải quyết consistency.

## Cách kiểm thử

1. **Integration test:** cập nhật giá sau khi row được backfill nhưng trước cutover; search sau swap phải là version mới.
2. **Failure-path test:** bulk có một item lỗi và HTTP 200; job không được cutover.
3. **Concurrency test:** hai reindex jobs đồng thời; chỉ một lease holder được swap.
4. **Recovery test:** kill worker giữa backfill rồi resume; không mất deletes/updates.
5. **Load test:** 2 triệu rows với concurrent writes; đo DB latency, indexing lag và sample correctness.

## Quan sát trong production

Metrics: rows scanned/sec, bulk item failure rate, DB p95/query plan, indexing queue lag, last applied change sequence, index count theo trạng thái, mismatch samples, alias version, cutover duration và rollback readiness. Structured logs gắn `runId`, `indexName`, `cursor`; alert khi lag tăng hoặc validation gate fail.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Elasticsearch cluster mất kết nối trong cutover, điều kiện nào cho phép retry an toàn?
2. Khi nào nên dùng PostgreSQL full-text search thay vì Elasticsearch?
3. Thiết kế reindex thế nào khi product document tổng hợp từ nhiều nguồn cập nhật độc lập?
